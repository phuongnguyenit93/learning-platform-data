# Testing Mapping in the Neo4j Java Driver and Spring Data Neo4j

## 1. Why is correct mapping just as critical as correct Cypher?

A Cypher query can succeed and return the right nodes and relationships in Neo4j while the Java application still returns wrong data. Bugs do not only live in the database: they also appear when Java code reads the wrong `Value` type, forgets a `null` check, maps the wrong relationship direction, assumes collection ordering, or uses a Spring Data Neo4j (SDN) entity that does not accurately reflect the graph.

In the `DATABASE_ENGINE_GRAPH_NEO4J` module, this **Testing** lesson focuses on two data paths:

- **Neo4j Java Driver:** the application runs Cypher directly, receives `Record` and `Value` objects, and maps them into Java DTOs.
- **Spring Data Neo4j:** the application declares entities via `@Node`, `@Id`, `@Relationship`, and repositories/`Neo4jClient`; the framework converts graph results into objects according to mapping rules.

Both rely on Neo4j and Cypher, yet **their mapping boundaries differ**. A test proving only `RETURN count(n)` works does not guarantee a `Book` entity includes all its authors. Conversely, a unit test with a mocked repository returning `Book` does not prove Neo4j actually converts a `DATE` property to `LocalDate` or reads the right relationship direction.

**Learning goals:**

1. Define a *mapping contract* from graph to Java.
2. Build a fixture with an independent answer key covering nodes, relationships, data types, nulls, and collections.
3. Integration-test the Java Driver, including `Record`, `Value`, sessions, and target database selection.
4. Test SDN entities and repositories against real Neo4j in Testcontainers.
5. Spot divergences between Driver and SDN results without confusing them with Cypher or transaction bugs.
6. Design negative tests, regression tests, and a reproducible CI workflow.

> **Example scope:** Java 17+, Neo4j 5.x, Spring Boot 3.x / Spring Data Neo4j 7.x, and a compatible Testcontainers version. Package names and test lifecycles may change in newer Spring Boot or Testcontainers releases; always check your project's BOM and APIs. The code below is instructional; this lesson **does not claim to have executed these tests against a live Neo4j instance**.

## 2. Two mapping paths to test

~~~mermaid
flowchart LR
    C["Cypher + graph data"] --> D["Neo4j Server"]
    D --> B["Bolt protocol"]
    B --> V["Java Driver: Record / Value"]
    V --> M["Custom mapper"]
    M --> T["DTO / API response"]
    B --> S["Spring Data Neo4j"]
    S --> E["@Node / @Relationship entity"]
    E --> U["Service / API response"]
    T --> A["Same data contract"]
    U --> A
~~~

Sharing the same database does not mean both paths automatically return identical structures:

| Aspect | Plain Java Driver | Spring Data Neo4j |
|---|---|---|
| Cypher query | Written directly by developer | Generated by repository, provided via `@Query`, or run via `Neo4jClient` |
| Intermediate data | `Record` / `Value` / `Node` / `Relationship` | Query result mapped by converter to entity/projection |
| Type conversion | Explicit calls to `asString()`, `asLong()`, `asLocalDate()`, etc. | SDN relies on metadata and conversion service |
| Null / missing property | Explicit `Value.isNull()` checks | Mapped per field type and converter rules |
| Relationships | Manual `MATCH` or path traversal, manually assembled into DTO | `@Relationship` declares direction, type, and collection type |
| ID | Reads property/`elementId` explicitly via Cypher | `@Id` / `@GeneratedValue` per entity mapping |
| Transactions | `Session` + `executeRead/executeWrite` | Spring transaction manager, repository, `Neo4jClient` |
| Specific risks | Wrong alias, wrong Value type, closed Result | Wrong annotation, query missing relationships, `save` mutating the graph unexpectedly |

**One shared data contract** serves as the benchmark for testing both paths: a book with `isbn`, `title`, `pages`, `publishedOn`, `subtitle`, and a set of authors linked by a directed relationship.

## 3. Choosing test levels: mocks do not prove real mapping

| Test level | Should verify | Cannot prove |
|---|---|---|
| **Pure mapper unit test** | Conversion logic from existing objects to DTOs, null checks, field checks | That Neo4j driver returns expected `Record` or SDN hydrates the graph properly |
| **Repository/Driver integration** | Real queries, Bolt, data conversion, annotations, repositories, constraints | Production network performance or cluster failover |
| **Service/API integration** | Transactions, JSON responses, validation, paging, application auth flows | Full production topology if container is a single instance |
| **Contract/regression test** | Stability across schema and Java Driver/SDN/Neo4j versions | Does not replace monitoring p95/locks/I/O under real load |

For "mapping testing", **integration tests against real Neo4j are mandatory for at least the critical cases**. Mocking a `BookRepository` with `when(findById(...)).thenReturn(book)` only verifies how the service uses a pre-built object. It **never exercises** SDN converters or the Java Driver's Bolt serialization.

Neo4j in **Testcontainers** provides a pinned database version, isolated data fixtures, and CI-ready test configuration. Never use production databases or mutate data in a teammate's database for testing.

## 5. Creating an isolated fixture on the test database

The statements below are solely for seeding data **in a dedicated test database**. Never run cleanup/seed scripts if labels `QA007Book` and `QA007Author` are used by anyone else.

### 5.1. Cleaning the fixture's own data

~~~cypher
MATCH (n)
WHERE n:QA007Book OR n:QA007Author
~~~

You can create unique constraints to ensure business keys never collide:

~~~cypher
CREATE CONSTRAINT qa007_book_isbn IF NOT EXISTS
FOR (b:QA007Book) REQUIRE b.isbn IS UNIQUE;
~~~

~~~cypher
CREATE CONSTRAINT qa007_author_id IF NOT EXISTS
FOR (a:QA007Author) REQUIRE a.authorId IS UNIQUE;
~~~

Wait for constraint-backing indexes to reach `ONLINE` when testing performance or loading large volumes.

### 5.3. Independent reference query without Java mappers

~~~cypher
MATCH (b:QA007Book)
OPTIONAL MATCH (b)-[:QA007_WRITTEN_BY]->(a:QA007Author)
RETURN b.isbn AS isbn,
       count(a) AS authorCount,
       collect(a.authorId) AS authorIds
ORDER BY isbn;
~~~

| isbn | authorCount | authorIds |
|---|---:|---|
| B001 | 2 | A01, A02 |
| B002 | 1 | A02 |
| B003 | 0 | [] |

Element order inside `collect(...)` **must not be assumed guaranteed** unless explicitly sorted prior to aggregation. In tests, compare a **set** of author IDs or sort the list before asserting. By contrast, row ordering by `isbn` is guaranteed by `ORDER BY isbn`.

Verify node/relationship counts:

~~~cypher
MATCH (b:QA007Book)
WITH count(b) AS books
MATCH (a:QA007Author)
WITH books, count(a) AS authors
MATCH ()-[r:QA007_WRITTEN_BY]->()
RETURN books, authors, count(r) AS relationships;
~~~

Answer: `books = 3`, `authors = 2`, `relationships = 3`.

## 6. Mapping with the Java Driver: Record and Value are typed data

In the Java Driver, `Record` holds the column/alias names from `RETURN`; `Value` holds a specific Neo4j type. Avoid calling `toString()` to convert arbitrary properties, as it may produce quoted representations, `"NULL"`, or composite strings rather than the desired typed values.

### 6.1. Common data type mapping table

| Cypher/Neo4j | Java Driver | Java DTO |
|---|---|---|
| `STRING` | `value.asString()` | `String` |
| `INTEGER` | `value.asLong()` | `long`/`Long` |
| `FLOAT` | `value.asDouble()` | `double`/`Double` |
| `BOOLEAN` | `value.asBoolean()` | `boolean`/`Boolean` |
| `DATE` | `value.asLocalDate()` | `LocalDate` |
| `DATETIME` with timezone | `value.asZonedDateTime()` | `ZonedDateTime` |
| `LIST<STRING>` | `value.asList(Value::asString)` | `List<String>` |
| `null` | `value.isNull()` | `null` / `Optional` per API |
| Node | `value.asNode()` | Driver `Node`, not an SDN entity |

**Choose types intentionally:** Neo4j stores integers as 64-bit; do not blindly cast everything to `int`. `DATE` is not `DATETIME`: using `LocalDate` preserves the calendar date without inventing a timezone. Both missing fields and fields explicitly set to `null` appear as a null `Value` when querying `b.subtitle AS subtitle`.

### 6.2. Shared DTO to compare both mapping approaches

~~~java
import java.time.LocalDate;
import java.util.Set;

public record BookView(
    String isbn,
    String title,
    long pages,
    LocalDate publishedOn,
    String subtitle,
    Set<String> authorIds
) {}
~~~

`BookView` is an application contract, **not** an SDN entity. It holds no `Node`, `Record`, or `Result` tied to an open connection or session.

### 6.3. Mapper function converting Record to BookView

~~~java
import java.util.Set;
import org.neo4j.driver.Record;
import org.neo4j.driver.Value;

public final class BookRecordMapper {
    public static BookView from(Record record) {
        String subtitle = record.get("subtitle").isNull()
            ? null
            : record.get("subtitle").asString();

        Set<String> authors = Set.copyOf(
            record.get("authorIds").asList(Value::asString)
        );

        return new BookView(
            record.get("isbn").asString(),
            record.get("title").asString(),
            record.get("pages").asLong(),
            record.get("publishedOn").asLocalDate(),
            subtitle,
            authors
        );
    }
}
~~~

This mapper depends on the query contract: the columns `isbn`, `title`, `pages`, `publishedOn`, `subtitle`, and `authorIds` must exist. If an alias changes, tests should fail loudly rather than silently returning bad data.

### 6.4. Querying via the Java Driver

~~~java
import java.util.List;
import org.neo4j.driver.Driver;
import org.neo4j.driver.Session;
import org.neo4j.driver.SessionConfig;

public static List<BookView> readBooks(Driver driver) {
    String cypher = """
        MATCH (b:QA007Book)
        OPTIONAL MATCH
          (b)-[:QA007_WRITTEN_BY]->(a:QA007Author)
        RETURN b.isbn AS isbn,
               b.title AS title,
               b.pages AS pages,
               b.publishedOn AS publishedOn,
               b.subtitle AS subtitle,
               collect(a.authorId) AS authorIds
        ORDER BY isbn
        """;

    try (Session session = driver.session(
            SessionConfig.forDatabase("neo4j"))) {
        return session.executeRead(tx ->
            tx.run(cypher).list(BookRecordMapper::from)
        );
    }
}
~~~

Here the Driver consumes the entire `Result` **inside the transaction and session**. The method returns mapped DTOs, preventing cursor-closed errors after the Session closes. For very large datasets, do not call `list()` on everything; use pagination or streaming within proper transaction boundaries.

### 6.5. Concrete assertions

Assuming `books = readBooks(driver)`:

~~~java
import static org.junit.jupiter.api.Assertions.*;
~~~

This test simultaneously catches **alias**, **null**, **date type**, **integer type**, and **relationship direction** bugs. However, if you construct `books` manually in Java instead of querying Neo4j, it does not test driver/DB integration.

## 7. Spring Data Neo4j mapping with annotations

Spring Data Neo4j maps labels to Java entities via `@Node`, identifiers via `@Id`, and relationships via `@Relationship`. For our fixture, an appropriate read model is:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.neo4j.core.schema.Node;

@Node("QA007Author")
public class Author {
    @Id
    private String authorId;

    private String name;

    protected Author() {}

    public String getAuthorId() { return authorId; }
    public String getName() { return name; }
}
~~~

~~~java
import java.time.LocalDate;
import java.util.LinkedHashSet;
import java.util.Set;
import org.springframework.data.annotation.Id;
import org.springframework.data.neo4j.core.schema.Node;
import org.springframework.data.neo4j.core.schema.Relationship;

@Node("QA007Book")
public class Book {
    @Id
    private String isbn;

    private String title;
    private Long pages;
    private LocalDate publishedOn;
    private String subtitle;

    @Relationship(
        type = "QA007_WRITTEN_BY",
        direction = Relationship.Direction.OUTGOING
    )
    private Set<Author> authors = new LinkedHashSet<>();

    protected Book() {}

    public String getIsbn() { return isbn; }
    public String getTitle() { return title; }
    public Long getPages() { return pages; }
    public LocalDate getPublishedOn() { return publishedOn; }
    public String getSubtitle() { return subtitle; }
    public Set<Author> getAuthors() { return authors; }
}
~~~

These entities have `protected` no-arg constructors for framework instantiation and getters for assertions. In production apps you can use constructors/`@PersistenceCreator`, immutable objects, or records with matching mapping requirements; **do not** treat these example entities as a complete production domain model.

### 7.1. What is actually verified?

- `@Node("QA007Book")` matches the node label.
- `@Id String isbn` maps to the `isbn` property; **not** the internal `elementId`.
- `Long pages` receives integer `120` from Neo4j.
- `LocalDate publishedOn` receives the `DATE` value.
- `String subtitle` receives `null` when the property is absent.
- `@Relationship(... OUTGOING)` fetches authors along `(b)-[:QA007_WRITTEN_BY]->(a)`.
- `Set<Author>` does not guarantee author ordering. Compare via `authorId`.

**Do not assume Hibernate/JPA-style lazy loading.** How SDN hydrates relationships depends on the query and converter; a custom query returning only the root node may not load the full relationship structure declared on the entity.

### 7.2. Relationships with properties: a separate case

If a relationship carries business properties such as `role`, you may need a `@RelationshipProperties` class with `@TargetNode`:

~~~java
import org.springframework.data.neo4j.core.schema.RelationshipId;
import org.springframework.data.neo4j.core.schema.RelationshipProperties;
import org.springframework.data.neo4j.core.schema.TargetNode;

@RelationshipProperties
public class Authorship {
    @RelationshipId
    private Long graphRelationshipId;

    @TargetNode
    private Author author;

    private String role;

    protected Authorship() {}
}
~~~

To use this class, change the field on `Book` to `Set<Authorship>` per the corresponding domain model. **Never declare two fields mapping the same relationship type and direction simultaneously without verifying mapping behavior.** `@RelationshipId` lets SDN manage relationship identity; never treat the internal ID as a stable long-term business key. This extension **does not apply directly** to our fixture, which has no `role` property.

## 8. Repositories: how do they differ from Driver queries?

~~~java
import java.util.Optional;
import org.springframework.data.neo4j.repository.Neo4jRepository;
import org.springframework.data.neo4j.repository.query.Query;
import org.springframework.data.repository.query.Param;

public interface BookRepository
        extends Neo4jRepository<Book, String> {

    Optional<Book> findByIsbn(String isbn);

    @Query("""
        MATCH (b:QA007Book {isbn: $isbn})
        OPTIONAL MATCH
          (b)-[r:QA007_WRITTEN_BY]->(a:QA007Author)
        RETURN b, collect(r) AS rels, collect(a) AS authors
        """)
    Optional<Book> findBookWithAuthors(
        @Param("isbn") String isbn
    );
}
~~~

In `findByIsbn`, SDN derives Cypher from the method name. In `findBookWithAuthors`, the custom Cypher query returns the root node `b` along with **collected relationships and target nodes** so SDN can hydrate the entity graph.

**Why collect relationships?** If a query returns one row per `b, r, a` and is paginated or mapped carelessly, root `B001` can appear twice or be partially hydrated. SDN custom entity mapping requires a compatible shape: a root record/node paired with its related nodes and relationships collected per mapping rules. If the entity declares additional relationship types, this custom query **does not prove** those other relationships are loaded.

In this lesson, tests favor `findBookWithAuthors` to verify an **explicit** contract. For derived queries like `findByIsbn`, you should also test how your specific SDN version generates queries and hydrates relationships.

## 9. Testcontainers: why use a real database?

Unit tests cannot fully simulate Bolt, Neo4j `DATE`, null semantics, graph hydration, or transactions. Testcontainers runs Neo4j in Docker for integration testing, allowing you to:

- Pin the server version to reproduce bugs reliably.
- Seed fixtures with Cypher rather than hand-built fake graph objects.
- Test both the Java Driver and SDN **against the exact same database**.
- Clean data between tests to eliminate order dependencies.
- Run the same suite in CI with Docker or a compatible container runtime.

A test class can share **one static `Neo4jContainer` across the class** rather than starting a new container per test method. Never use this container for production; keep test passwords and databases separate from real secrets.

### 9.1. Reference Maven dependencies

When a Spring Boot 3.x app manages versions via its BOM, typical dependencies are:

### 9.2. Using `@DataNeo4jTest` and `@DynamicPropertySource`

~~~java
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.AfterEach;
import org.neo4j.driver.Driver;
import org.neo4j.driver.Session;
import org.neo4j.driver.SessionConfig;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.neo4j.DataNeo4jTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;
import org.testcontainers.containers.Neo4jContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import java.time.LocalDate;
import java.util.Set;
import java.util.stream.Collectors;

import static org.junit.jupiter.api.Assertions.*;

@DataNeo4jTest
@Testcontainers
@Transactional(propagation = Propagation.NOT_SUPPORTED)
class BookMappingIT {

    private static final String PASSWORD = "test-only-password";

    @Container
    static final Neo4jContainer<?> neo4j =
        new Neo4jContainer<>("neo4j:5.26")
            .withAdminPassword(PASSWORD);

    @DynamicPropertySource
    static void properties(DynamicPropertyRegistry registry) {
        registry.add("spring.neo4j.uri", neo4j::getBoltUrl);
        registry.add("spring.neo4j.authentication.username",
                     () -> "neo4j");
        registry.add("spring.neo4j.authentication.password",
                     () -> PASSWORD);
        registry.add("spring.data.neo4j.database",
                     () -> "neo4j");
    }

    @Autowired Driver driver;
    @Autowired BookRepository repository;

    @BeforeEach
    void seed() {
        try (Session session = driver.session(
                SessionConfig.forDatabase("neo4j"))) {
            session.executeWrite(tx -> {
                tx.run("""
                    MATCH (n)
                    WHERE n:QA007Book OR n:QA007Author
                    DETACH DELETE n
                    """).consume();
                tx.run("""
                    CREATE
                      (b1:QA007Book {
                        isbn:'B001', title:'Cypher Foundations',
                        pages:120, publishedOn:date('2025-01-05'),
                        subtitle:'An introduction'
                      }),
                      (b2:QA007Book {
                        isbn:'B002', title:'Spring Data Mapping',
                        pages:200, publishedOn:date('2025-01-06')
                      }),
                      (b3:QA007Book {
                        isbn:'B003', title:'Driver Essentials',
                        pages:80, publishedOn:date('2025-01-07')
                      }),
                      (a1:QA007Author {authorId:'A01', name:'An'}),
                      (a2:QA007Author {authorId:'A02', name:'Bình'}),
                      (b1)-[:QA007_WRITTEN_BY]->(a1),
                      (b1)-[:QA007_WRITTEN_BY]->(a2),
                      (b2)-[:QA007_WRITTEN_BY]->(a2)
                    """).consume();
                return null;
            });
        }
    }

    @AfterEach
    void clean() {
        try (Session session = driver.session(
                SessionConfig.forDatabase("neo4j"))) {
            session.executeWrite(tx -> {
                tx.run("""
                    MATCH (n)
                    WHERE n:QA007Book OR n:QA007Author
                    DETACH DELETE n
                    """).consume();
                return null;
            });
        }
    }

    @Test
    void driverMapsDateNullAndRelationships() {
        var rows = BookQueries.readBooks(driver);
        assertEquals(3, rows.size());
        assertEquals("B001", rows.get(0).isbn());
        assertEquals(120L, rows.get(0).pages());
        assertEquals(LocalDate.of(2025, 1, 5),
                     rows.get(0).publishedOn());
        assertEquals(Set.of("A01", "A02"),
                     rows.get(0).authorIds());
        assertNull(rows.get(1).subtitle());
        assertTrue(rows.get(2).authorIds().isEmpty());
    }

    @Test
    void sdnHydratesTheSameBook() {
        Book book = repository.findBookWithAuthors("B001")
            .orElseThrow();

        assertEquals("Cypher Foundations", book.getTitle());
        assertEquals(120L, book.getPages());
        assertEquals(LocalDate.of(2025, 1, 5),
                     book.getPublishedOn());

        Set<String> ids = book.getAuthors().stream()
            .map(Author::getAuthorId)
            .collect(Collectors.toSet());
        assertEquals(Set.of("A01", "A02"), ids);
    }

    @Test
    void emptyRelationshipAndMissingPropertyAreHandled() {
        Book book = repository.findBookWithAuthors("B003")
            .orElseThrow();

        assertNull(book.getSubtitle());
        assertTrue(book.getAuthors().isEmpty());
        assertEquals(80L, book.getPages());
    }
}
~~~

**Connecting the snippets:** In this test, `BookQueries.readBooks(driver)` is the method from Section 6.4 (which can live in a `BookQueries` class); `BookView`, `BookRecordMapper`, `Book`, `Author`, and `BookRepository` come from previous sections. Ensure all classes sit in packages visible to Spring component/repository scanning. If you do not use a `BookQueries` wrapper class, substitute the actual class holding `readBooks`.

Here `@Transactional(propagation = NOT_SUPPORTED)` is used to **avoid relying on the test slice's automatic rollback when seeding directly with the Driver**. Every seed/cleanup executes as an independent commit; do not expect a Spring test transaction to roll back writes performed by a separate `Driver.session()`. Never run two test classes sharing the same labels in parallel against one `Neo4jContainer` without isolation.

**Example limitations:** Do not use these credentials or floating/illustrative image tags in production. The purpose is demonstrating deterministic integration tests. Depending on your Spring Boot version, you may need explicit package scanning, repository scanning, bean imports, and classpath adjustments.

## 10. One data source, two assertions: comparing Driver and SDN

Instead of maintaining two separate expectations for Driver and SDN, assert against the **same expected contract**:

~~~java
import java.time.LocalDate;
import java.util.Set;

BookView expected = new BookView(
    "B001",
    "Cypher Foundations",
    120L,
    LocalDate.of(2025, 1, 5),
    "An introduction",
    Set.of("A01", "A02")
);
~~~

Convert the SDN entity to the same DTO:

~~~java
import java.util.stream.Collectors;

static BookView fromEntity(Book book) {
    return new BookView(
        book.getIsbn(),
        book.getTitle(),
        book.getPages(),
        book.getPublishedOn(),
        book.getSubtitle(),
        book.getAuthors().stream()
            .map(Author::getAuthorId)
            .collect(Collectors.toSet())
    );
}
~~~

Compare the results read from the graph:

~~~java
BookView fromDriver = BookQueries.readBooks(driver)
    .stream()
    .filter(b -> b.isbn().equals("B001"))
    .findFirst()
    .orElseThrow();

BookView fromSdn = fromEntity(
    repository.findBookWithAuthors("B001").orElseThrow()
);

assertEquals(expected, fromDriver);
assertEquals(expected, fromSdn);
~~~

A Java `record` implements value-based `equals`; `Set` compares elements regardless of order. This is a *differential contract test*: if either branch maps differently from expected, investigate **Cypher → converter → DTO** instead of accepting two inconsistent standards.

Be careful: both branches can still **fail in the exact same way** and compare equal to each other; therefore always keep an independent **expected literal** rather than writing only `assertEquals(fromDriver, fromSdn)`.

## 11. Common mapping mistakes and negative tests

### 11.1. Wrong relationship direction

The fixture only creates `(Book)-[:QA007_WRITTEN_BY]->(Author)`. If the annotation specifies `INCOMING` instead of `OUTGOING`, or Cypher matches `(Author)-[:QA007_WRITTEN_BY]->(Book)`, authors silently vanish from results.

Tests should assert that B001 contains **specifically A01 and A02**, rather than only checking non-nullness. If flipping direction drops data, the test must fail.

### 11.2. Wrong property name or alias

A Driver query returns `RETURN b.isbn AS bookId` while the mapper reads `record.get("isbn")`: alias mismatch. An SDN entity renames field `publishedOn` to `publicationDate` without `@Property("publishedOn")`: the date property fails to map as expected.

Example intentionally mapping a different field name:

~~~java
import org.springframework.data.neo4j.core.schema.Property;

@Property("publishedOn")
private LocalDate publicationDate;
~~~

This illustrates **replacing the field** in the entity—do not declare both `publicationDate` and `publishedOn` simultaneously.

### 11.3. Nulls, absent properties, and Java primitives

Because `b.subtitle` has no property on B002, the Driver receives a null `Value`, and SDN populates `null` in `String subtitle`. Conversely, declaring primitive `long pages` makes it impossible to represent "pages unknown"; use `Long` when properties may be missing.

Tests should include **one node missing the property** and **one node with the property present**, rather than testing only the "happy path" with complete data.

### 11.4. 64-bit integers and value ranges

Neo4j `INTEGER` is 64-bit. Calling `asInt()` on values outside the 32-bit range or mapping to Java `Integer` can lose precision or fail conversion. Unit tests using `1` and `2` will miss this bug.

For fields that can exceed 2,147,483,647, use `Long`/`asLong()` and test boundary values. For `FLOAT`, never assert exact floating-point equality when tolerance is expected; use a justified tolerance.

### 11.5. Dates and timezones

`date('2025-01-05')` maps to `LocalDate`; `datetime(...)` carries timezone information and requires types like `ZonedDateTime` or `OffsetDateTime` where supported by converters. Never convert a `DATE` into an `Instant` using the test machine's local timezone.

Temporal tests should specify explicit timezones and boundary cases such as date rollover across zones. Our fixture uses `DATE` to avoid timezone ambiguity; `DATETIME` tests are a natural extension.

### 11.6. Null, empty, and duplicate collections

`OPTIONAL MATCH` when B003 has no authors produces one row with `a = null`; `collect(a.authorId)` skips nulls and produces an empty list. This differs from a query returning zero records.

A `Set<Author>` can mask duplicate relationships forbidden by your data model. If business rules require single-valued or non-duplicate relationships, assert the **actual relationship count** via Cypher and enforce constraints/modeling rather than checking only the `Set` size.

### 11.7. Reading works, but saving drops relationships

In SDN, `repository.save(book)` is not always a simple "UPDATE one property"; depending on graph mapping and entity state, saving can update relationships managed by the entity. If a custom query hydrates only part of the graph and you then pass that entity to `save`, unloaded relationships may be affected.

Therefore, maintain **separate read tests** and **write tests**. When updating a single property by key, a targeted Cypher update is often safer than round-tripping a partially hydrated entity.

## 12. Transactions, rollbacks, and test isolation

### 12.1. Driver transactions do not auto-sync with Spring transactions

~~~mermaid
sequenceDiagram
    participant T as JUnit Test
    participant S as Spring Transaction Manager
    participant D as Java Driver
    participant N as Neo4j
    T->>S: @Transactional test
    T->>D: driver.session().executeWrite()
    D->>N: Separate transaction → COMMIT
    T->>S: test ends, rolls back Spring transaction
    Note over N: Data committed by Driver may still exist
~~~

Never assume `@Transactional` on a test rolls back writes executed directly through the Driver. Depending on configuration, the Driver opens an independent transaction; rolling back Spring's transaction manager cannot undo a separate committed transaction. Our example disables automatic test transactions and cleans fixtures explicitly.

### 12.2. Specify the target database explicitly

~~~java
try (var session = driver.session(
        SessionConfig.forDatabase("neo4j"))) {
    // Seed/read the right test database.
}
~~~

If integration tests seed the `neo4j` database while the SDN repository is configured to point at another database, tests can return `Optional.empty()` even when the fixture exists. Verify `spring.data.neo4j.database`, Testcontainers URIs, and database permissions.

When testing multi-database setups, use a **real test database** supported by your edition. Never assume every Neo4j instance supports database-creation commands in every edition.

### 12.3. Every test must be independent

- `@BeforeEach` resets and seeds the exact fixture; `@AfterEach` cleans up if needed.
- Never rely on `testA` running before `testB`.
- Never use `MERGE` with reused IDs and assume the newly created node count is always 1.
- If JUnit parallel execution is enabled, give each test its own database/label namespace or synchronization lock; prevent tests from wiping each other's fixtures.
- For external side effects, use mock endpoints and never rely on database transaction rollback to undo HTTP calls.

## 13. Testing custom `@Query` and partial relationship hydration

Suppose a repository defines two methods:

~~~java
@Query("""
    MATCH (b:QA007Book {isbn:$isbn})
    RETURN b
    """)
Optional<Book> findRootOnly(String isbn);

@Query("""
    MATCH (b:QA007Book {isbn:$isbn})
    OPTIONAL MATCH
      (b)-[r:QA007_WRITTEN_BY]->(a:QA007Author)
    RETURN b, collect(r) AS rels, collect(a) AS authors
    """)
Optional<Book> findWithAuthors(String isbn);
~~~

The first returns only the root node, so **you cannot assume** the entity is hydrated with its full author graph unless the framework performs extra steps. The second provides explicit node/relationship structures for entity hydration.

Tests should verify:

1. `findWithAuthors("B001")` includes A01 and A02.
2. `findWithAuthors("B003")` has no authors.
3. Missing ISBN returns `Optional.empty()`.
4. The query does not produce two separate `Book` entities for B001 when two relationships match.
5. If the domain adds more relationship types, test loading **each type** explicitly rather than assuming one `collect` covers all.

If a page only needs book details and author count, a **scalar DTO** with `count(a)` is lighter than hydrating the entire entity graph. Mapping tests should verify the **exact payload needed**, rather than forcing every endpoint to hydrate full entity graphs.

## 14. Testing write behavior: `CREATE`, `MERGE`, and `save`

Read mapping can work while write persistence is still broken. Build separate tests for write contracts:

| Test case | Input condition | Expectation |
|---|---|---|
| Create new nonexistent ID | `B004` not yet in graph | Exactly one `B004` node with expected fields |
| Update property | Change B001 title | ISBN unchanged; node count unchanged; new title persisted |
| Save same ID again | Retry a processed operation | No duplicate node if designed idempotently |
| Attach author | Add A01 to B003 | Directed edge created; other relationships intact |
| Remove author | Detach A02 from B001 per business rule | Only the targeted relationship is modified |
| Violate unique constraint | Create duplicate ISBN via non-MERGE write path | Transaction fails and graph contains no duplicate |
| Mid-transaction rollback | Second statement fails in the same transaction | Changes from that transaction are not committed |

For SDN `repository.save`, verify how the entity determines new vs. existing state (`@Id`, `@GeneratedValue`, `@Version`, or entity state checks), rather than assuming pre-assigning an ID always inserts or always updates. Assert on the **final node/relationship state in Neo4j**, not merely the object returned by `save`.

Example controlled Cypher update and verification:

~~~cypher
MATCH (b:QA007Book {isbn:'B001'})
SET b.title = 'Cypher Foundations Revised'
RETURN b.isbn AS isbn, b.title AS title;
~~~

~~~cypher
MATCH (b:QA007Book)
RETURN count(b) AS books,
       count(DISTINCT b.isbn) AS uniqueIsbns;
~~~

**Answer:** B001 has the updated title, `books = 3`, and `uniqueIsbns = 3`. Reset the fixture before subsequent tests so the expected title does not drift across the suite.

## 15. Testing interaction bugs between Driver and SDN

### 15.1. Returning a `Result` outside a closed session

~~~java
// ANTI-PATTERN: do not copy into application code.
static org.neo4j.driver.Result queryBad(Driver driver) {
    try (var session = driver.session(
            SessionConfig.forDatabase("neo4j"))) {
        return session.run("MATCH (b:QA007Book) RETURN b");
    }
}
~~~

The session closes before the caller consumes the cursor. Tests should invoke services that **return DTOs or lists** after closing the session, proving the data is complete and independent of live connections.

### 15.2. Mixing Spring and Driver transactions

If a Spring `@Transactional` service calls an SDN repository and then calls `driver.session().executeWrite` independently, the two operations **do not automatically share one transaction**. A failure after the Driver commits can leave half-written state. Write integration tests simulating failures between the two steps to understand the boundary; when atomicity is required, use a unified transaction manager/scope.

### 15.3. Ignoring results and summaries

For Driver writes, call `consume()` or fully process results before closing the transaction. For SDN, verify committed state by re-reading in a new transaction. Never treat an in-memory Java object as proof that the database persisted the write.

### 15.4. Mismatched tenant or database

Driver tests reading from `neo4j` while SDN tests target another database can create the illusion of a mapping bug. Specify the target database explicitly in both paths and verify state with a read-only query pinned to that database name.

## 16. Testing query quality alongside mapping

Results can be accurate on a 3-node fixture yet painfully slow on a large graph. Separate the two assertion groups:

| Category | What to assert | How to measure |
|---|---|---|
| **Functional mapping** | IDs, properties, date types, nulls, author counts, direction | JUnit/Testcontainers, expected literals |
| **Query plan** | Index usage, Rows/DB Hits, expand vs. scan | `EXPLAIN`, `PROFILE` on representative datasets |
| **N+1** | Extra queries issued as root count grows | Query logging/tracing in tests |
| **Over-fetch** | Records/relationships actually loaded vs. API needs | Driver summary, tracing, response payload |
| **Latency** | p50/p95 with warm/cold DB, network, connection pool | Standalone benchmarks, no brittle millisecond assertions in every JUnit test |
| **Concurrency** | Unique ID conflicts, transaction retries, no duplicates | Thread-controlled integration tests with isolated data |

Avoid `assertTrue(elapsed < 10 ms)` as a pass/fail check in mapping tests: slow CI runners, Docker startup, or OS scheduling cause flakiness. Mapping tests should verify **values**, while quantitative benchmarks belong in dedicated suites with controlled conditions.

Example to inspect relationship expansion cost:

~~~cypher
PROFILE
MATCH (b:QA007Book)
OPTIONAL MATCH (b)-[:QA007_WRITTEN_BY]->(a:QA007Author)
RETURN b.isbn AS isbn,
       collect(a.authorId) AS authorIds
ORDER BY isbn;
~~~

Inspect `Rows`, `DB Hits`, and index/scan operators on large datasets. On a 3-node fixture, the plan is not representative of production workloads; all you can confirm there is **three returned records** and accurate author lists.

## 17. Pitfalls when upgrading libraries

Components evolve independently: Neo4j server, Java Driver, Spring Data Neo4j, Spring Boot, Testcontainers, and JDK. When upgrading:

1. Pin versions in the BOM and container image for your release branch.
2. Run mapping tests for both **Driver** and **SDN** against the same fixture.
3. Verify compatibility of `DATE`/`DATETIME`, numeric types, converters, and getters.
4. Check repository-generated queries, especially cycles, relationship properties, and custom `@Query`.
5. Verify transaction retries, bookmarks, database selection, and TLS configuration.
6. Retain regression tests for past bugs: nulls, changed aliases, wrong directions, duplicated root records, and overwritten relationships.
7. If query counts or payloads jump after an upgrade, check for N+1 or over-fetching before blaming the mapper.

In newer Spring Boot 4 / SDN generations, **test annotation packages and test-slice dependencies may change**. Do not cling to old imports across major upgrades; consult official release guides, update test wiring, and **keep the expected contract intact**.

## 18. Practice exercises with answers

### Exercise 1 — Count after `OPTIONAL MATCH`

The fixture has 3 Books with 2, 1, and 0 authors respectively. How many rows and how many distinct Books does `OPTIONAL MATCH` from Book to Author return?

**Answer:** 4 intermediate rows (2 + 1 + 1 null row), yet **3 distinct Books**.

### Exercise 2 — Nulls during mapping

B002 has no `subtitle` property. The Driver reads `RETURN b.subtitle AS subtitle`; SDN has a `String subtitle` field. What is expected?

**Answer:** Driver `Value.isNull() == true`, mapper returns Java `null`; SDN `getSubtitle() == null`. Never convert null into the literal string `"null"`.

### Exercise 3 — Wrong relationship direction

`@Relationship(type="QA007_WRITTEN_BY", direction=INCOMING)` is placed on `Book`. Why does B001 fail to include A01/A02 as expected?

**Answer:** The fixture uses **OUTGOING** edges from Book to Author; the reversed direction does not match. Tests must assert the exact ID set `A01/A02` to catch this bug.

### Exercise 4 — Date type conversion

What Java types should `publishedOn = date('2025-01-06')` map to?

**Answer:** Driver `Value.asLocalDate()` and SDN `LocalDate`. Do not depend on the server timezone for `DATE` values.

### Exercise 5 — Are repository mocks enough?

A test mocks `BookRepository.findByIsbn` to return a hand-built `Book` with two authors. Can you conclude SDN maps relationships properly from Neo4j?

**Answer:** No. Mocks bypass Cypher, Bolt, and converters. You need an integration test with a Neo4j fixture and real repository.

### Exercise 6 — Transaction independence

A Spring test has `@Transactional`, while `@BeforeEach` seeds data via `driver` `executeWrite` and commits. After the test rolls back Spring's transaction, is the Driver-seeded data guaranteed to be deleted?

**Answer:** No. They are independent transactions; perform explicit cleanup or move seeding into a controlled shared transaction.

### Exercise 7 — Both paths failing identically

Both Driver and SDN return `authorIds = []` for B001, and the test only runs `assertEquals(fromDriver, fromSdn)`. Does the test serve its purpose?

**Answer:** No. Both can share the exact same relationship-direction bug. Compare against an independent expected literal `Set.of("A01","A02")`.

### Exercise 8 — Collection ordering

`collect(a.authorId)` returns A02 before A01, while the test expects A01 before A02. Is this definitely a mapping bug?

**Answer:** No. Without controlled sorting, collection order is not guaranteed. Compare sets or add an appropriate `ORDER BY` before aggregation.

### Exercise 9 — Saving a partially loaded entity

A custom query returns only the `Book` node, while the entity also declares an `Authors` relationship. A service edits the title and calls `save(book)`. What is the risk?

**Answer:** Entity state may omit loaded relationships; depending on version and mapping, saving may alter the graph beyond just the title. Separate read/write tests and consider a keyed Cypher update when only changing title.

## 19. Mapping test checklist for CI

- [ ] Neo4j runs in an isolated test environment with pinned container images and dependency versions.
- [ ] Fixtures include nodes with full properties, missing properties, multiple relationships, one relationship, and **no relationships**.
- [ ] Independent expected literals exist rather than only comparing two mappers against each other.
- [ ] Tests verify aliases, `String`, `Long`, `LocalDate`, nulls, IDs, and collections.
- [ ] Tests verify relationship direction/type and never assume Set/List order without `ORDER BY`.
- [ ] Integration tests exist for both real Driver and real SDN repositories, not mocks alone.
- [ ] Driver consumes `Result` before closing Session/Transaction.
- [ ] Tests specify the target database explicitly and never use production credentials.
- [ ] Fixtures reset cleanly between tests; no order dependence; no parallel runs on shared labels without isolation.
- [ ] Negative tests exist: missing node, wrong ID, unique constraint, rollback, and altered mapper alias.
- [ ] Writes and reads are verified **after commit**, not from in-memory objects alone.
- [ ] Unit tests, integration tests, and benchmarks are separated, avoiding brittle latency thresholds.
- [ ] Regression tests run whenever upgrading Neo4j/Driver/SDN/Spring Boot.
