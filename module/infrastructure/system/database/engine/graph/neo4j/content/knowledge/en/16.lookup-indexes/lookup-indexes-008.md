# Creating, Inspecting Status, Awaiting Readiness, and Dropping Lookup Indexes in Neo4j

## 1. What Are Lookup Indexes Used For?

In Neo4j's **property graph**, each node can carry one or more *labels* and each relationship has a *type*. When a Cypher query looks up nodes by label or relationships by type, the system can use a **lookup index** to identify elements carrying the matching token.

Two main kinds of lookup indexes:

| Scope | Looked-Up Element | Common Query | Index Declaration Syntax |
| --- | --- | --- | --- |
| Node | Labels attached to nodes, such as `:Person`, `:Order` | `MATCH (p:Person) RETURN p` | `FOR (n) ON EACH labels(n)` |
| Relationship | Relationship types, such as `:FOLLOWS`, `:PURCHASED` | `MATCH ()-[r:PURCHASED]->() RETURN r` | `FOR ()-[r]-() ON EACH type(r)` |

Lookup indexes are also called **token lookup indexes**. Each node lookup index covers **labels across all nodes in the database**, while each relationship lookup index covers **types across all relationships**. Therefore, you do not create one lookup index for `:Person` and another separate lookup index for `:Order`.

Key distinctions:

- A lookup index searches by **label** or **relationship type**; it is not an index for properties like `email`, `name`, or `createdAt`.
- To filter by `p.email = $email` or compare date ranges, consider a *range index* or property-backed constraint depending on the query.
- An `ONLINE` lookup index may be chosen by the query planner; the index's existence **does not guarantee every query will use it**. To see the actual plan, use `EXPLAIN` or `PROFILE`.

For example, consider a graph with `(:Person {id: 1})`, `(:Product {id: 20})`, and `[:BOUGHT]` relationships. The node lookup index helps find nodes carrying `:Person` or `:Product`; the relationship lookup index helps find `:BOUGHT` relationships. It does not directly optimize `p.id = 1`.

## 2. Check Before Creating: The Index Likely Already Exists

In many modern Neo4j versions and configurations, **a new database already comes with default lookup indexes** for node labels and relationship types. Default index names may be generated by Neo4j, vary across databases, and should not be guessed from examples.

Before running DDL commands, confirm:

1. You are connected to the right database (especially when multiple databases exist in the same DBMS).
2. Your account has privileges to view schema and to create/drop indexes when performing those steps.
3. Which lookup indexes already exist, their actual names, entity types, and states.
4. Your Neo4j version supports `CREATE LOOKUP INDEX`, `SHOW LOOKUP INDEXES`, and the corresponding wait procedures. The commands below use Neo4j 5.x and compatible current syntax; for older environments, check the documentation for that exact version.

Run:

```cypher
SHOW LOOKUP INDEXES;
```

Or project only the key columns:

```cypher
SHOW LOOKUP INDEXES
YIELD name, entityType, state, populationPercent
RETURN name, entityType, state, populationPercent
ORDER BY entityType, name;
```

Illustrative output (actual index names are determined by each system):

| name | entityType | state | populationPercent |
| --- | --- | --- | --- |
| `index_node_labels` | `NODE` | `ONLINE` | `100.0` |
| `index_rel_types` | `RELATIONSHIP` | `ONLINE` | `100.0` |

If both indexes exist and are `ONLINE`, you usually **do not need to create more**. Avoid writing scripts that rely on a hardcoded default name; read `name` from `SHOW` output when awaiting or dropping a specific index.

You can also view lookup indexes within the full list of all index types:

```cypher
SHOW INDEXES
YIELD name, type, entityType, state, populationPercent
WHERE type = 'LOOKUP'
RETURN name, entityType, state, populationPercent
ORDER BY entityType, name;
```

During broader performance investigations, `SHOW INDEXES` also reveals property indexes such as range, text, point, full-text, or vector indexes (depending on version). Do not confuse them with lookup indexes.

## 3. Creating Lookup Indexes with Cypher

### 3.1. Creating a Node Label Lookup Index

```cypher
CREATE LOOKUP INDEX app_node_label_lookup IF NOT EXISTS
FOR (n)
ON EACH labels(n);
```

Meaning of each clause:

- `CREATE LOOKUP INDEX`: declares a token lookup index.
- `app_node_label_lookup`: an explicit index name aiding operations and tracking. Names must be unique within the same database's schema.
- `IF NOT EXISTS`: lets the statement be re-run when a matching index or an index with the same name already exists; if the statement skips creation, **inspect the schema again** to see what object actually exists.
- `FOR (n) ON EACH labels(n)`: defines a lookup index over **node labels**, not a property of `n`.

If the database already has a default node label lookup index with a different name, Neo4j will not create a duplicate for the same scope. A command with `IF NOT EXISTS` may create nothing; that **does not mean** an index named `app_node_label_lookup` now exists. Always run `SHOW LOOKUP INDEXES` afterward.

### 3.2. Creating a Relationship Type Lookup Index

```cypher
CREATE LOOKUP INDEX app_relationship_type_lookup IF NOT EXISTS
FOR ()-[r]-()
ON EACH type(r);
```

`FOR ()-[r]-()` specifies the relationship pattern being indexed; `ON EACH type(r)` specifies the type token. **Do not use** `labels(r)` for relationships, because labels belong to nodes; relationships have types.

This is likewise a lookup index for **all relationship types**, not an index solely for `:FOLLOWS`. If an index of this kind already exists, a second lookup index with the same scope cannot be created.

### 3.3. Why `IF NOT EXISTS` Alone Is Not Enough to Confirm Success

An index creation step must satisfy two independent conditions:

1. **Right schema:** Neo4j has a lookup index for `NODE` or `RELATIONSHIP` as expected.
2. **Ready for use:** the index is in the `ONLINE` state.

`IF NOT EXISTS` primarily handles repeated DDL execution or preexisting names/schemas. It does not verify that the proposed index name was newly created, does not guarantee all indexes are `ONLINE`, and does not replace post-creation state checks.

Additional note: Cypher does not allow multiple concurrent lookup indexes for the same entity type. If you want to rename a Neo4j-created default index, evaluate real requirements, permissions, and operational risk; avoid dropping default indexes purely for cosmetic naming.

## 4. Viewing Index Status and Build Progress

Immediately after creation, Neo4j may need time to build/populate the index from existing data. Completing the `CREATE` command does not automatically mean the index is ready to serve queries.

```cypher
SHOW LOOKUP INDEXES
YIELD name, entityType, state, populationPercent
RETURN name, entityType, state, populationPercent
ORDER BY name;
```

Reading the fields:

| Field | Meaning |
| --- | --- |
| `name` | Actual index name used to reference it in `db.awaitIndex` or `DROP INDEX` |
| `entityType` | `NODE` or `RELATIONSHIP` |
| `state` | Index lifecycle state |
| `populationPercent` | Percentage of population progress reported by Neo4j |

Important states:

| State | Interpretation | Appropriate Action |
| --- | --- | --- |
| `POPULATING` | Index is currently building | Wait for completion; check progress and system resources if unusually prolonged |
| `ONLINE` | Built and ready for query usage | Safe to proceed with deployment steps depending on the index |
| `FAILED` | Index build or maintenance failed | Inspect error details, Neo4j logs, configuration, and resources before fixing or recreating |

Typically, when `state = 'ONLINE'`, `populationPercent` reaches `100.0`. Do not assume an index is ready merely because progress is near 100%; **prioritize checking `state = 'ONLINE'`**.

To filter specifically for indexes still building:

```cypher
SHOW LOOKUP INDEXES
YIELD name, entityType, state, populationPercent
WHERE state <> 'ONLINE'
RETURN name, entityType, state, populationPercent
ORDER BY name;
```

An empty result here means no lookup index is outside `ONLINE` **among the indexes returned by the command**. It does not prove both lookup index types exist; verify both `NODE` and `RELATIONSHIP` in the previous query.

## 5. Awaiting Index Readiness Before Use

Avoid writing tight loops polling `SHOW` rapidly. Neo4j provides procedures to wait until an index transitions to `ONLINE`.

### 5.1. Awaiting One Index by Actual Name

For example, when `SHOW LOOKUP INDEXES` shows an index named `app_node_label_lookup`:

```cypher
CALL db.awaitIndex('app_node_label_lookup', 300);
```

In this example, `300` is the maximum wait timeout in **seconds**. If the index fails to become ready within the deadline, the procedure raises a timeout/error; applications or migrations must not ignore that error and treat the index as `ONLINE`.

**Naming note:** when `CREATE ... IF NOT EXISTS` is skipped because Neo4j already has a lookup index of the same scope under a different name, calling `db.awaitIndex('app_node_label_lookup', 300)` will fail to find an index by that name. Read `SHOW LOOKUP INDEXES` first and substitute the **actual** name of the index to await.

### 5.2. Awaiting All Indexes in the Database

```cypher
CALL db.awaitIndexes(300);
```

This command suits database initialization or post-schema-migration checks when the application needs **all** indexes ready. On a large database with many range/full-text/vector indexes currently building, this can wait much longer than awaiting a single lookup index.

A clear operational sequence:

```cypher
// 1. Check existing names, scopes, and states.
SHOW LOOKUP INDEXES
YIELD name, entityType, state, populationPercent
RETURN name, entityType, state, populationPercent;
```

```cypher
// 2. Create only when actually needed; the name might not be created due to IF NOT EXISTS.
CREATE LOOKUP INDEX app_node_label_lookup IF NOT EXISTS
FOR (n) ON EACH labels(n);
```

```cypher
// 3. Wait for all indexes or choose the exact name from SHOW in step 1/2.
CALL db.awaitIndexes(300);
```

```cypher
// 4. Confirm ONLINE state and presence of all required index types.
SHOW LOOKUP INDEXES
YIELD name, entityType, state, populationPercent
RETURN name, entityType, state, populationPercent
ORDER BY entityType;
```

Run the blocks above as **separate** statements, ensuring schema creation completes before calling the wait procedure. Waiting and verification belong to schema management; they do not replace transactions and data validation when the application updates nodes/relationships.

### 5.3. Handling Wait Failures

If `db.awaitIndex`/`db.awaitIndexes` times out or an index enters `FAILED`:

1. Re-run `SHOW LOOKUP INDEXES` to obtain the exact `name` and `state`, confirming the index still exists and you are not connected to the wrong database.
2. Inspect schema diagnostics or Neo4j server logs; check disk space, memory, storage errors, and cluster member status if applicable.
3. Determine whether the failure is transient or requires intervention. Recreate only after evaluating the impact on live queries.
4. In a deployment pipeline, mark the migration/initialization as **failed**; never report the application's indexes as ready while `state` is not `ONLINE`.

Do not configure infinite timeouts without monitoring. Increasing the timeout can help on large datasets, yet will not fix a `FAILED` index.

## 6. Dropping a Lookup Index by Name

Neo4j uses the **index name**—not `labels(n)` or `type(r)` expressions—to identify which index to drop:

```cypher
DROP INDEX app_node_label_lookup IF EXISTS;
```

For a relationship lookup index:

```cypher
DROP INDEX app_relationship_type_lookup IF EXISTS;
```

`IF EXISTS` prevents an error if that **name** does not exist. It is not a wildcard search to drop every index of that kind. If `CREATE ... IF NOT EXISTS` previously skipped creating `app_node_label_lookup` because a differently named default index already existed, `DROP INDEX app_node_label_lookup IF EXISTS` will not drop that default index either.

Safe procedure:

1. Run `SHOW LOOKUP INDEXES`; record the **actual name**, `entityType`, and `state` of the target index.
2. Confirm the environment, fallback plan, and performance impact. Lookup indexes can be a critical access path for many label/type queries.
3. Run `DROP INDEX <index-name> IF EXISTS` using the verified name; never guess names or accidentally drop default indexes.
4. Re-run `SHOW LOOKUP INDEXES` to confirm the target index is gone. If needed, recreate it following Sections 3–5.

Dropping a lookup index **does not delete nodes, relationships, or properties**. However, it changes the query planner's data access options and can slow down queries searching by label/type. In production environments, manage this operation as a planned schema migration with performance evaluation.

## 7. Illustration from Query to Execution Plan

Suppose an application has `Person` and `Product` nodes and `BOUGHT` relationships:

```cypher
CREATE (:Person {personId: 'p-01', name: 'Lan'});
CREATE (:Product {productId: 'sku-01', name: 'Notebook'});
```

Add a relationship for testing:

```cypher
MATCH (p:Person {personId: 'p-01'})
MATCH (x:Product {productId: 'sku-01'})
MERGE (p)-[:BOUGHT]->(x);
```

Token-based queries:

```cypher
MATCH (p:Person)
RETURN p.name;
```

```cypher
MATCH ()-[r:BOUGHT]->()
RETURN type(r) AS relationshipType, count(r) AS total;
```

To observe how Neo4j plans them:

```cypher
EXPLAIN
MATCH (p:Person)
RETURN p.name;
```

```cypher
EXPLAIN
MATCH ()-[r:BOUGHT]->()
RETURN count(r);
```

Depending on version, data statistics, and the cost planner, plans may use label/type scan operators (such as `NodeByLabelScan` or a relationship-type scan operator). Do not conclude a plan uses a specific index solely from an operator name; combine `SHOW LOOKUP INDEXES` with `EXPLAIN`/`PROFILE` details and query characteristics.

**Distinguishing `EXPLAIN` and `PROFILE`:** `EXPLAIN` builds a plan without executing; `PROFILE` actually executes the query and also reports rows and DbHits. For write statements, `PROFILE` modifies the graph, so never run it casually to probe important data.

When a query has a property predicate:

```cypher
MATCH (p:Person {personId: 'p-01'})
RETURN p.name;
```

The lookup index helps identify the `:Person` label, but does not individually index `personId` values. A range index on `:Person(personId)` or a uniqueness constraint may be more appropriate when data grows large and queries frequently seek by exact ID:

```cypher
CREATE CONSTRAINT person_id_unique IF NOT EXISTS
FOR (p:Person)
REQUIRE p.personId IS UNIQUE;
```

That is a **property constraint/index**, differing in purpose and syntax from a lookup index. Choices should be grounded in queries and execution plans rather than mechanically creating every index type.

## 8. Java Driver and Spring Data Neo4j Integration

Java applications should generally manage schema before serving business traffic: a migration initializes indexes, awaits `ONLINE`, and only then exposes features relying on query performance. Example with the **Neo4j Java Driver** (running on compatible Neo4j 5.x):

```java
import org.neo4j.driver.AuthTokens;
import org.neo4j.driver.Driver;
import org.neo4j.driver.GraphDatabase;
import org.neo4j.driver.Record;
import org.neo4j.driver.Session;
import org.neo4j.driver.SessionConfig;

public class VerifyLookupIndexes {
    public static void main(String[] args) {
        try (
            Driver driver = GraphDatabase.driver(
                "neo4j://localhost:7687",
                AuthTokens.basic("neo4j", "change-me")
            );
            Session session = driver.session(
                SessionConfig.forDatabase("neo4j")
            )
        ) {
            session.run("""
                CREATE LOOKUP INDEX app_node_label_lookup IF NOT EXISTS
                FOR (n) ON EACH labels(n)
                """).consume();

            session.run("""
                CREATE LOOKUP INDEX app_relationship_type_lookup IF NOT EXISTS
                FOR ()-[r]-() ON EACH type(r)
                """).consume();

            // Execute after DDL statements have completed.
            session.run("CALL db.awaitIndexes(300)").consume();

            var indexes = session.run("""
                SHOW LOOKUP INDEXES
                YIELD name, entityType, state
                RETURN name, entityType, state
                """).list();

            boolean hasNode = false;
            boolean hasRelationship = false;
            for (Record row : indexes) {
                String entityType = row.get("entityType").asString();
                String state = row.get("state").asString();
                String name = row.get("name").asString();
                System.out.printf("%s: %s -> %s%n", name, entityType, state);

                if (!"ONLINE".equals(state)) {
                    throw new IllegalStateException(
                        "Index is not ready: " + name
                    );
                }
                if ("NODE".equals(entityType)) hasNode = true;
                if ("RELATIONSHIP".equals(entityType)) hasRelationship = true;
            }

            if (!hasNode || !hasRelationship) {
                throw new IllegalStateException(
                    "Missing lookup index for NODE or RELATIONSHIP"
                );
            }
        }
    }
}
```

Key takeaways:

- `session.run(...).consume()` consumes the command's result stream, ensuring the auto-commit transaction finishes before moving to the next statement in the example.
- `IF NOT EXISTS` allows re-running migrations, yet **does not guarantee the two custom index names will exist**. That is why the example validates by `entityType` and `state` rather than asserting the proposed names.
- `db.awaitIndexes(300)` waits for all indexes in the database. To await only one index, fetch its exact name from `SHOW LOOKUP INDEXES` and call `db.awaitIndex`.
- Schema creation/deletion requires appropriate privileges. In real systems, retrieve credentials from configuration or a secret manager; never hardcode real passwords in source code.

With **Spring Data Neo4j**, repositories and `Neo4jClient` handle business graph operations. Managing lookup indexes is usually better placed in a migration step or dedicated initialization component (especially when multiple application instances start concurrently). Repository `save(...)` does not create lookup indexes for each label/type on every entity save. Whether using Spring or the Java Driver directly, observe index states via Cypher and only mark initialization complete once required indexes are `ONLINE`.

## 9. Common Errors and Misconceptions

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Creation with `IF NOT EXISTS` succeeds without error, yet the new name is missing | A lookup index of the same scope already exists under another name | Use `SHOW LOOKUP INDEXES` to identify the actual index and state |
| Creation without `IF NOT EXISTS` reports schema conflict | A `NODE` or `RELATIONSHIP` lookup index already exists | Keep the existing index; do not try to create a duplicate of the same kind |
| `db.awaitIndex` reports index name not found | Wrong name used, wrong database, or creation was skipped | Read actual `name` from `SHOW LOOKUP INDEXES` |
| Index stays `POPULATING` for a long time | Large data volume or resource/storage bottleneck | Monitor progress, logs, resources, and use an appropriate timeout |
| `db.awaitIndexes` times out even though lookup indexes are `ONLINE` | Another index type in the database is not `ONLINE` yet | Run `SHOW INDEXES` to inspect all indexes; await only the lookup index if appropriate |
| Index is `FAILED` | Error during population or maintenance | Inspect diagnostics, logs, and resources; plan remediation |
| `DROP INDEX ... IF EXISTS` runs, yet the lookup index remains | The dropped name did not match the existing index's name | Retrieve the exact name from `SHOW LOOKUP INDEXES` |
| After dropping an index, label/type queries slow down | Query planner lost token-based access path | Inspect plans; recreate the lookup index if needed |
| Lookup index is `ONLINE`, yet filtering `email` stays slow | Lookup indexes do not index `email` property values | Check `EXPLAIN`; consider a range/text index or suitable constraint |
| `SHOW LOOKUP INDEXES` fails on a very old system | Different Cypher version or missing schema privileges | Consult Neo4j docs for that version and verify account privileges |

## 10. Hands-On Practice

Run on a **test database** where schema modifications are permitted:

1. Run `SHOW LOOKUP INDEXES`. Record `name`, `entityType`, `state`, and `populationPercent`. Confirm whether both `NODE` and `RELATIONSHIP` scopes are present.
2. Run both `CREATE LOOKUP INDEX ... IF NOT EXISTS` statements from Section 3. Re-run them. Explain why duplicate lookup indexes of the same scope are not created.
3. Run `CALL db.awaitIndexes(300)`, then re-check `SHOW LOOKUP INDEXES`. If an index is not `ONLINE`, describe the diagnostic steps to take.
4. Create `:Person`, `:Product` nodes and a `:BOUGHT` relationship. Use `EXPLAIN` on label and type queries; compare against a query filtering on `personId`.
5. Only in a test database with a recovery plan, take the **actual name** of one lookup index, run `DROP INDEX <index-name> IF EXISTS`, confirm the index disappears, recreate it, and wait for `ONLINE`.

**Completion criteria:** learners can distinguish lookup indexes from property indexes, write correct syntax for nodes and relationships, verify state with `SHOW LOOKUP INDEXES`, use `db.awaitIndex`/`db.awaitIndexes` appropriately, and drop/recreate indexes by **actual name** without losing graph data.
