# Vector Indexes: Configuration, Querying, and Version Capabilities

## 1. What Problem Does a Vector Index Solve?

In Neo4j, nodes and relationships represent entities and their connections. Standard indexes help look up entities by property value or label/relationship type, whereas a **vector index** helps find entities whose **embedding is close to a query vector**. This is a key technique in semantic search, content recommendations, and GraphRAG applications, where users may phrase questions with words different from the stored text.

For example, a learner asks "How do I find relationships using Cypher?" while a document is titled "Querying edges in a property graph". If the same embedding model represents both texts with nearby vectors, vector search can include that document in the candidate list even without exact keyword overlap.

In the `DATABASE_ENGINE_GRAPH_NEO4J` module, this lesson belongs to **Advanced Search** and builds on nodes, relationships, indexes, and Cypher queries. The goal is to understand how to **create, configure, query, inspect, and operate vector indexes**, especially differences across Neo4j generations. The examples use small precomputed numeric vectors; no embedding API, LLM, APOC, or Graph Data Science library is required.

After this lesson, you will be able to:

- Distinguish embeddings, similarity metrics, and approximate vector indexes.
- Create a vector index for nodes, check `dimensions`, `similarity_function`, and `ONLINE` status.
- Query using `db.index.vector.queryNodes()` and `SEARCH` where supported.
- Explain why the same task may require different syntax on Neo4j 5.x versus Neo4j 2025–2026.
- Identify the limits of ANN, invalid vector data, dimension mismatches, filter interactions, and embedding model changes.

> **Version scope:** The compatibility table in Section 3 is based on Neo4j 5 documentation and current Cypher documentation, verified up to **25/11/2026**. New Cypher 25 features and new configuration options must be verified against the actual Neo4j version you are running rather than copied blindly to every server.

## 2. Embeddings, Similarity, and ANN

### 2.1. Embeddings Are Data; a Vector Index Is a Search Structure

An **embedding** is a sequence of numbers representing an object such as a text passage, image, product, or graph structure. The example below illustrates the shape of a node (not a standalone Cypher statement):

~~~text
(:Document {
  id: 'DOC-01',
  title: 'Introduction to Graphs',
  embedding: [1.0, 0.0, 0.0]
})
~~~

In real applications, embeddings usually have hundreds to thousands of dimensions. The sample dataset uses **3 dimensions** so learners can check values by hand; these numbers are not generated by an AI model.

A **vector index** takes a vector as a signal to return nodes or relationships with the nearest vectors under a similarity metric. Neo4j uses an approximate nearest neighbor (ANN) search structure based on HNSW (*Hierarchical Navigable Small Worlds*). Using the index can accelerate queries on large datasets, at the trade-off of not guaranteeing the exact `k` nearest neighbors under brute-force computation.

### 2.2. Two Fundamental Similarity Functions

| Index Config Function | Idea | Things to Note |
|---|---|---|
| `'cosine'` | Compares the **direction** of two vectors | Commonly used for text embeddings; vectors must not have zero length |
| `'euclidean'` | Evaluates proximity by **Euclidean distance** | Vector magnitude affects proximity |

For vectors `a` and `b`, geometric cosine is computed as:

\[
\cos(\theta)=\frac{a \cdot b}{\|a\|\,\|b\|}
\]

This formula explains the **direction** between two vectors. The `score` returned by Neo4j after search is normalized according to the index similarity function, lies in the range **0 to 1**, and higher values indicate greater similarity; it is **not a probability** that the document contains the right answer.

An intuitive example with query `q = [1, 0, 0]`:

| Document Vector | Geometric Cosine with q | Interpretation |
|---|---:|---|
| `[1.0, 0.0, 0.0]` | 1.0 | Same direction |
| `[0.8, 0.6, 0.0]` | 0.8 | Highly similar |
| `[0.0, 1.0, 0.0]` | 0.0 | Orthogonal |

The similarity order by cosine is row 1, row 2, row 3. In an indexed query, the actual order is an **ANN result**, so it can differ on larger datasets or when `k` approaches the total number of indexed vectors.

### 2.3. How Vector Indexes Differ from Standard and Full-Text Indexes

| Mechanism | Primary Signal | Example |
|---|---|---|
| `RANGE INDEX` | Property value comparison | `WHERE d.id = 'DOC-01'` |
| `TEXT INDEX` | Certain string predicates | `WHERE d.title CONTAINS 'graph'` |
| `FULLTEXT INDEX` | Keyword/term relevance | Search for the word "Cypher" in title or body |
| `VECTOR INDEX` | Proximity between vectors | Find documents whose embedding is close to the query vector |

Vector search **does not automatically infer graph relationships**. A common pattern is to find a candidate group of nodes by vector, then expand with `MATCH` across relationships, filter access permissions, or apply business rules.

## 3. Capabilities by Version: Check Syntax Before Running

Neo4j has the following major milestones:

| Version | Vector Index Changes |
|---|---|
| **5.11–5.12** | Node vector index introduced in **public beta**; create node indexes via `db.index.vector.createNodeIndex()`. |
| **5.13–5.14** | Node vector index reaches **GA**; still uses procedure to create indexes because `CREATE VECTOR INDEX` syntax is not yet available. |
| **5.15–5.17** | Cypher `CREATE VECTOR INDEX` syntax for nodes; queried via `db.index.vector.queryNodes()`. |
| **5.18–5.22** | Adds vector indexes for **relationships** and `db.index.vector.queryRelationships()`; adds `vector.similarity.*` functions for direct calculation. |
| **5.23 onward (5.x branch)** | `vector.dimensions` and `vector.similarity_function` become optional on creation; supports HNSW and quantization settings depending on provider capabilities. Still **declare dimensions explicitly** in applications. |
| **2025.10 (Cypher 25)** | Adds native `VECTOR` property type alongside `LIST` numeric properties, depending on edition and store format. |
| **2026.01 (Cypher 25)** | Adds `SEARCH` for querying vector indexes; supports multi-label/multi-relationship-type vector indexes and additional filter properties. |
| **2026.04** | `db.index.vector.queryNodes()` and `db.index.vector.queryRelationships()` marked **deprecated**; migrate to `SEARCH` on supported systems. |
| **2026.06** | Adds `vector.quantization.type` (`'none'`, `'scalar'`, `'binary'`); `vector.quantization.enabled` marked deprecated. |
| **2026.07** | Adds **High Fidelity Quantized** (HFQ) search and `vector.default_search_expansion_factor`. |
| **2026.08** | New provider continues quantization improvements; default `vector.quantization.type` changes to `'binary'`. |

**How to read this table:**

- The `CREATE VECTOR INDEX` syntax in the main examples below targets **Neo4j 5.15+**. If you are on 5.11–5.14, see Section 10 before creating indexes.
- `SEARCH` syntax is only usable when both **Neo4j 2026.01+** and **Cypher 25** are available; do not use it in environments supporting only Cypher 5.
- `queryNodes`/`queryRelationships` procedures remain useful for backward compatibility, though they are deprecated in newer releases. *Deprecated* means you should plan a migration, not that the procedures vanish immediately.
- `indexProvider` names such as `vector-1.0`, `vector-2.0`, or `vector-2026.08` describe the **actual provider**; indexes created in older versions may retain their old provider after upgrades. Never infer index capabilities solely from the server version.

> **Edition:** Vector indexes on `LIST<INTEGER | FLOAT>` properties work in both Community and Enterprise Edition. The native `VECTOR` type requires the **block** store format, available in Enterprise/Aura. If broad compatibility across exercises is the goal, use numeric lists as shown below.

## 4. Key Configuration Parameters

Basic syntax:

~~~cypher
CREATE VECTOR INDEX ten_index IF NOT EXISTS
FOR (d:TenLabel) ON (d.embedding)
OPTIONS { indexConfig: {
  `vector.dimensions`: 1536,
  `vector.similarity_function`: 'cosine'
}};
~~~

Both properties inside `OPTIONS` are wrapped in backticks because their names contain dots. The example above assumes real embeddings have **1536 dimensions**; the hands-on exercise in Section 5 uses `dimensions = 3`.

### 4.1. Vector Dimensions and Similarity Function

| Parameter | Purpose | Values / Notes |
|---|---|---|
| `vector.dimensions` | Expected vector dimensionality | **1–4096**. Match the exact embedding dimensionality; required prior to 5.23. |
| `vector.similarity_function` | How vectors are compared | `'cosine'` or `'euclidean'`; required prior to 5.23, defaults to `'cosine'` from 5.23 onward. |

If dimensions are set to 3, a list of 2 or 4 numbers **does not fit the index**. In versions enforcing fixed dimensions, querying with a differently sized vector raises an error; property data with a mismatched dimension is not indexed under that schema. A vector index is not a constraint forcing every node to hold a properly sized embedding.

Do not pass `null`, `NaN`, infinity, or zero-norm vectors into searches requiring cosine similarity. When designing an embedding ingestion pipeline, validate numeric types, dimensionality, and finiteness **before writing**.

### 4.2. HNSW: Trading Off Accuracy and Resources

| Option | Effect | Current Documentation Default |
|---|---|---|
| `vector.hnsw.m` | Maximum links per element in the HNSW graph; increasing can improve recall at higher memory and build-time cost | **16** |
| `vector.hnsw.ef_construction` | Number of neighbors tracked when inserting an element; increasing can improve HNSW graph quality at higher build cost | **100** |

These are **advanced** parameters; no tuning is needed for small datasets. When optimizing a system, measure search latency, index build speed, disk/RAM usage, and **recall@k** on a labeled query evaluation set together.

### 4.3. Quantization: Saving Resources While Measuring Recall

Quantization compresses vector representations inside the index. It can reduce memory footprint and improve performance, but it can also degrade approximate search accuracy.

- For **5.23 through before 2026.06**, documentation specifies the boolean option `vector.quantization.enabled`.
- From **2026.06**, `vector.quantization.type` supports `'none'`, `'scalar'`, and `'binary'`; `vector.quantization.enabled` is marked deprecated.
- From **2026.07**, `vector.default_search_expansion_factor` expands the candidate pool to improve search quality; HFQ rescores candidates using unquantized vectors in supported configurations.
- By **2026.08**, the default quantization type changed to `'binary'`. Do not assume existing indexes automatically switch providers or adopt new defaults.

Example **only for versions that support these options**:

~~~cypher
// Reference for Neo4j 2026.06+; no need to run in the practice exercise.
CREATE VECTOR INDEX demoVectorNewOptions IF NOT EXISTS
FOR (d:DemoVectorNew) ON (d.embedding)
OPTIONS { indexConfig: {
  `vector.dimensions`: 1536,
  `vector.similarity_function`: 'cosine',
  `vector.quantization.type`: 'scalar',
  `vector.hnsw.m`: 16,
  `vector.hnsw.ef_construction`: 100
}};
~~~

Unless you have specific benchmark data showing otherwise, using the provider defaults while explicitly declaring dimensions and similarity is usually the most maintainable starting point.

## 5. Hands-On: Creating a Fixture and Node Vector Index

### 5.1. Five-Document Dataset

This lesson uses a dedicated label `QA005Doc` and index name `qa005_doc_embedding`. Each embedding has 3 elements, all finite numbers, and non-zero norm.

| docId | Title | topic | embedding |
|---|---|---|---|
| D01 | Introduction to Graphs | graph | `[1.0, 0.0, 0.0]` |
| D02 | Cypher and Relationships | graph | `[0.8, 0.6, 0.0]` |
| D03 | Java Driver for Neo4j | java | `[0.6, 0.8, 0.0]` |
| D04 | UI Design | ui | `[0.0, 1.0, 0.0]` |
| D05 | Image Classification | ai | `[0.0, 0.0, 1.0]` |

Use a **dedicated practice database** and execute each Cypher block as a separate transaction. If you have run this exercise before, drop the test index and test nodes first:

~~~cypher
DROP INDEX qa005_doc_embedding IF EXISTS;
~~~

~~~cypher
MATCH (d:QA005Doc)
DETACH DELETE d;
~~~

Create the data:

~~~cypher
CREATE
  (:QA005Doc {
    docId: 'D01', title: 'Introduction to Graphs',
    topic: 'graph', embedding: [1.0, 0.0, 0.0]
  }),
  (:QA005Doc {
    docId: 'D02', title: 'Cypher and Relationships',
    topic: 'graph', embedding: [0.8, 0.6, 0.0]
  }),
  (:QA005Doc {
    docId: 'D03', title: 'Java Driver for Neo4j',
    topic: 'java', embedding: [0.6, 0.8, 0.0]
  }),
  (:QA005Doc {
    docId: 'D04', title: 'UI Design',
    topic: 'ui', embedding: [0.0, 1.0, 0.0]
  }),
  (:QA005Doc {
    docId: 'D05', title: 'Image Classification',
    topic: 'ai', embedding: [0.0, 0.0, 1.0]
  });
~~~

Verify before creating the index:

~~~cypher
MATCH (d:QA005Doc)
RETURN count(d) AS totalDocs,
       count(d.embedding) AS withEmbeddings,
       collect(DISTINCT size(d.embedding)) AS dimensions;
~~~

Expected answer: `totalDocs = 5`, `withEmbeddings = 5`, `dimensions = [3]`. This dataset is solely for learning queries; the titles and vectors were not produced by a real embedding model.

### 5.2. Creating the Index

Using Neo4j **5.15+**:

~~~cypher
CREATE VECTOR INDEX qa005_doc_embedding IF NOT EXISTS
FOR (d:QA005Doc) ON (d.embedding)
OPTIONS { indexConfig: {
  `vector.dimensions`: 3,
  `vector.similarity_function`: 'cosine'
}};
~~~

There is no need to create a separate node index on `embedding`; a `VECTOR INDEX` serves similarity search, not a `RANGE` index for element-wise comparisons.

### 5.3. Checking Status and Metadata

~~~cypher
SHOW VECTOR INDEXES
YIELD name, type, state, populationPercent,
      entityType, labelsOrTypes, properties, indexProvider, options
WHERE name = 'qa005_doc_embedding'
RETURN name, type, state, populationPercent,
       entityType, labelsOrTypes, properties, indexProvider, options;
~~~

Check the key fields:

| Field | Expected |
|---|---|
| `name` | `qa005_doc_embedding` |
| `type` | `VECTOR` |
| `entityType` | `NODE` |
| `labelsOrTypes` | `['QA005Doc']` |
| `properties` | `['embedding']` |
| `state` | `ONLINE` when ready, or `POPULATING` while building |
| `populationPercent` | Usually `100.0` once population completes |
| `indexProvider` | Depends on version/provider; do not hardcode a fixed name |
| `options` | Includes `vector.dimensions = 3` and `vector.similarity_function = 'cosine'`, plus provider defaults |

**Only run search queries once the index is `ONLINE`**. Index building happens in the background; an index in `POPULATING` state is not ready. If no rows are returned, verify your current database, index privileges, and any errors from the creation command.

On Neo4j 5.11–5.14, filtering `SHOW INDEXES WHERE type = 'VECTOR'` may be more compatible than `SHOW VECTOR INDEXES`, depending on the exact version.

## 6. Querying a Vector Index with Neo4j 5.x Compatible Procedures

The following command requests the three nodes whose embeddings are closest to `[1.0, 0.0, 0.0]`:

~~~cypher
CALL db.index.vector.queryNodes(
  'qa005_doc_embedding',
  3,
  [1.0, 0.0, 0.0]
)
YIELD node, score
RETURN node.docId AS docId, node.title AS title, score
ORDER BY score DESC, docId;
~~~

The three arguments are:

1. Vector index name.
2. `k` — number of nearest neighbors requested.
3. Query vector, compatible with the index dimensionality and similarity function.

The procedure yields `node` and `score` pairs. With this standard fixture and query, **under exact cosine math**, the expected top three order is **D01, D02, D03**. D01 aligns with the query vector. However, because this is an **ANN** search, do not turn a specific order or `k` count into a hard guarantee across all datasets or providers.

### Parameterized Queries from an Application

Never concatenate user vector strings directly into Cypher. Parameterized query:

~~~cypher
CALL db.index.vector.queryNodes(
  'qa005_doc_embedding', $topK, $queryEmbedding
)
YIELD node, score
RETURN node.docId AS docId,
       node.title AS title,
       score
ORDER BY score DESC, docId;
~~~

Example parameters passed via the Neo4j Java Driver or repository layer:

~~~json
{
  "topK": 3,
  "queryEmbedding": [1.0, 0.0, 0.0]
}
~~~

In a Java / Spring Data Neo4j application, the service layer should validate upfront that `topK` is a reasonable positive integer and that the embedding is a list of finite numbers with exactly 3 dimensions (or the real model's dimensionality). The driver transmits parameters with proper types; results can be mapped to a DTO containing `docId`, `title`, and `score`. Procedure examples still work in many Cypher 5 projects, but on Neo4j 2026.04+ plan to migrate to `SEARCH`.

## 7. Querying with SEARCH in Neo4j 2026.01+ and Cypher 25

This is Neo4j's recommended way to perform vector search in newer releases:

~~~cypher
CYPHER 25
MATCH (d:QA005Doc)
SEARCH d IN (
  VECTOR INDEX qa005_doc_embedding
  FOR [1.0, 0.0, 0.0]
  LIMIT 3
) SCORE AS score
RETURN d.docId AS docId, d.title AS title, score
ORDER BY score DESC, docId;
~~~

Breaking down each part:

- `MATCH (d:QA005Doc)` declares the node variable to search.
- `SEARCH d IN (...)` searches inside the index named `qa005_doc_embedding`.
- `FOR [1.0, 0.0, 0.0]` is the query vector; in an application, replace with `$queryEmbedding`.
- `LIMIT 3` sets the desired ANN result count inside the search clause itself.
- `SCORE AS score` binds the similarity score to `score` for `RETURN` or sorting.

`SEARCH` is a **subclause of `MATCH` or `OPTIONAL MATCH`**, not an automatic search mechanism triggered by arbitrary `WHERE` clauses. You cannot replace `SEARCH` with `MATCH (d) WHERE d.embedding = $queryEmbedding` to get equivalent behavior: equality tests exact value match, not nearest neighbors.

### 7.1. Pre-Filtering vs. Post-Filtering Top-k Are Different Problems

Suppose you only want documents with topic `'java'`. In the sample data, D03 belongs to that topic, yet D01 and D02 have higher cosine similarity to the query vector than D03. If you fetch `k = 2` first and filter afterward:

~~~cypher
CALL db.index.vector.queryNodes(
  'qa005_doc_embedding', 2, [1.0, 0.0, 0.0]
)
YIELD node, score
WITH node, score
WHERE node.topic = 'java'
RETURN node.docId AS docId, score;
~~~

The query may return **zero results** because the two closest candidates were filtered out. Increasing `k` and post-filtering is a backward-compatible workaround on older versions, but it does not guarantee receiving top-k results **within the filtered subset**.

### 7.2. Integrated Filters in Vector Indexes (2026.01+)

Starting in Neo4j 2026.01, you can include filter properties inside the vector index. **Do not create a second vector index on an already indexed schema**. To test on the lesson data, drop the old index first and recreate it with `WITH [d.topic]`:

~~~cypher
DROP INDEX qa005_doc_embedding IF EXISTS;
~~~

~~~cypher
CYPHER 25
CREATE VECTOR INDEX qa005_doc_embedding IF NOT EXISTS
FOR (d:QA005Doc) ON (d.embedding)
WITH [d.topic]
OPTIONS { indexConfig: {
  `vector.dimensions`: 3,
  `vector.similarity_function`: 'cosine'
}};
~~~

Check `SHOW VECTOR INDEXES` again and wait for `ONLINE`. Then:

~~~cypher
CYPHER 25
MATCH (d:QA005Doc)
SEARCH d IN (
  VECTOR INDEX qa005_doc_embedding
  FOR [1.0, 0.0, 0.0]
  WHERE d.topic = 'java'
  LIMIT 2
) SCORE AS score
RETURN d.docId AS docId, d.title AS title, score
ORDER BY score DESC;
~~~

Here, `WHERE` sits **inside `SEARCH`**, so the index evaluates `topic = 'java'` while locating candidates; on the standard fixture, **D03** matches. Search remains ANN. The index still has only **one vector property** (`embedding`); `WITH [d.topic]` adds metadata for filtering, not extra vector dimensions from multiple fields.

Predicates supported inside `SEARCH ... WHERE` are more restricted than general Cypher `WHERE`. Check the *Predicates for vector search with filters* section for your server version before putting complex expressions into an index filter.

## 8. Vector Indexes on Relationships

Nodes are not the only entities that can hold embeddings. Starting in **Neo4j 5.18**, relationships also support vector indexes. For example, a recommendation system storing interaction features between users and content on relationships:

~~~cypher
CREATE VECTOR INDEX qa005_link_embedding IF NOT EXISTS
FOR ()-[r:QA005_RELATED]-() ON (r.embedding)
OPTIONS { indexConfig: {
  `vector.dimensions`: 3,
  `vector.similarity_function`: 'cosine'
}};
~~~

Example creating two relationships in the practice database using existing nodes:

~~~cypher
MATCH (a:QA005Doc {docId: 'D01'}),
      (b:QA005Doc {docId: 'D02'}),
      (c:QA005Doc {docId: 'D03'})
CREATE (a)-[:QA005_RELATED {embedding: [1.0, 0.0, 0.0]}]->(b),
       (a)-[:QA005_RELATED {embedding: [0.7, 0.7, 0.0]}]->(c);
~~~

Once the index is `ONLINE`, query on 5.18+:

~~~cypher
CALL db.index.vector.queryRelationships(
  'qa005_link_embedding', 2, [1.0, 0.0, 0.0]
)
YIELD relationship, score
RETURN startNode(relationship).docId AS fromDoc,
       endNode(relationship).docId AS toDoc,
       score
ORDER BY score DESC;
~~~

In Cypher 25 from Neo4j 2026.01 onward, you can replace the procedure with:

~~~cypher
CYPHER 25
MATCH ()-[r:QA005_RELATED]->()
SEARCH r IN (
  VECTOR INDEX qa005_link_embedding
  FOR [1.0, 0.0, 0.0]
  LIMIT 2
) SCORE AS score
RETURN startNode(r).docId AS fromDoc,
       endNode(r).docId AS toDoc,
       score;
~~~

A node index **cannot be used to search relationships** and vice versa. The index argument must point to the matching entity type and configured property. Because the fixture has very few relationships, ANN search may return fewer results than `k`; see Section 9.

## 9. Verifying Results and Understanding ANN Limits

### 9.1. Exact Calculation on a Small Dataset (Neo4j 5.18+)

On the 5-node dataset, you can compute cosine similarity **without the vector index** as a reference baseline:

~~~cypher
MATCH (d:QA005Doc)
RETURN
  d.docId AS docId,
  vector.similarity.cosine(
    d.embedding, [1.0, 0.0, 0.0]
  ) AS exactScore
ORDER BY exactScore DESC, docId;
~~~

Expected **ordering**: D01, D02, D03, followed by D04 and D05 with equal geometric cosine similarity to the query vector. Do not assert exact floating-point equality to the last decimal digit in tests; minor floating-point representation differences can occur across scoring methods and providers.

On larger datasets, measure **recall@k**:

\[
\operatorname{recall@k}
=\frac{\left|\operatorname{ANNTopK}\cap\operatorname{ExactTopK}\right|}{k}
\]

For instance, if the exact top-10 contains 10 nodes and ANN retrieves 9 of them, recall@10 is `0.9`. Monitor **latency**, `k`, valid record counts, vector sizes, and HNSW/quantization settings alongside recall.

### 9.2. Important Operational Limits

1. **Approximate:** `k` is only the requested count; fewer than `k` results can be returned, especially when `k` is close to the total number of indexed vectors.
2. **Transaction consistency:** vector changes **within the same transaction** are not immediately reflected in vector index queries inside that same transaction. Write and commit first, then query in a separate read transaction.
3. **Readiness:** an index in `POPULATING` state cannot be used; wait for `ONLINE` before testing queries.
4. **One vector index per schema:** you cannot simultaneously create two different vector indexes on the same schema—one with `cosine` and one with `euclidean`. Choose the metric based on the embedding model and business goal.
5. **Embedding incompatibility:** never arbitrarily compare vectors generated by two different models or versions, even if they share the same dimensionality. When upgrading embedding models, plan a coordinated data and index rebuild.
6. **Score is not trustworthiness:** a high `score` does not prove an answer is accurate or safe. Applications still need access-control filtering, source verification, and business rules.
7. **Hybrid search:** when combining full-text and vector search, scores from the two mechanisms do not share a common scale. Rank or normalize each source before combining—for example, using rank fusion—instead of summing raw scores directly.

### 9.3. Indexes Do Not Replace Data Constraints

A vector index does not enforce that every node has an `embedding` of the right dimensionality or model. A node missing `embedding` can still exist in the graph while being excluded from vector search. Therefore, the ingestion layer should validate:

- Length and numeric type of every embedding element.
- Finite values; for cosine, avoid zero-length vectors.
- Embedding model/version, update timestamp, and migration handling when models change.
- User permissions to view returned documents post-query.

In Neo4j, `UNIQUE` or key constraints on `docId` remain separate concerns; they do not turn a vector index into an identifier constraint mechanism.

## 10. Neo4j 5.11–5.14 Compatibility: Creating Indexes with the Legacy Procedure

If you run a version that supports vector indexes **without** `CREATE VECTOR INDEX` syntax (prior to 5.15), you may encounter:

~~~cypher
// Only use on Neo4j 5.11–5.14 supporting this procedure.
// Do not run alongside the same-named index created in Section 5.
CALL db.index.vector.createNodeIndex(
  'qa005_doc_embedding',
  'QA005Doc',
  'embedding',
  3,
  'cosine'
);
~~~

Limitations of the legacy approach:

- Only creates **node** vector indexes and requires explicit dimensionality and similarity function.
- Does not support modern `SEARCH` syntax or filtered vector indexes.
- After upgrading, use `CREATE VECTOR INDEX` for new indexes; Neo4j notes compatibility issues in certain 5.18+ versions when calling the legacy index creation procedure on databases upgraded from pre-5.11 releases.

If a query fails with a syntax error, check **server version**, **Cypher version**, availability of `CREATE VECTOR INDEX`, and available procedures first. Never add 2026.x options onto a 5.x system assuming they will be silently ignored.

## 11. Using with the Neo4j Java Driver and Spring Data Neo4j

A practical workflow:

~~~mermaid
flowchart LR
  A["Text / entity"] --> B["Embedding model"]
  B --> C["Validate dimensions, numeric types, model version"]
  C --> D["Write node/relationship + embedding to Neo4j"]
  D --> E["Vector index updates after commit"]
  F["User query"] --> G["Embed with the same model"]
  G --> H["SEARCH or queryNodes"]
  E --> H
  H --> I["Filter permissions / traverse edges / rank"]
  I --> J["Return documents and sources"]
~~~

In the Java Driver, use **parameterized** queries to pass `$queryEmbedding` and `$topK` as a list of numbers and an integer. Separate writing embeddings from search queries into distinct transactions; map each returned record into a DTO, such as `DocumentHit(docId, title, score)`.

With Spring Data Neo4j, you can place the query inside a repository `@Query` method or a service calling the driver. Ensure the index name matches the deployed schema, and keep the embedding model and dimensionality consistent between ingestion and search pipelines.

Document operational decisions in application configuration: index name, label/relationship type, embedding property name, dimensionality, cosine/euclidean, model version, and data filtering strategy. Avoid scattering these constants across multiple Java classes where changing models could easily introduce mismatched results.

## 12. Diagnosing Common Errors

| Symptom | Common Cause | Fix |
|---|---|---|
| `CREATE VECTOR INDEX` fails with syntax error | Server older than 5.15 or mismatched syntax | Check Neo4j version; 5.11–5.14 has the legacy procedure |
| `SEARCH` reported as invalid | Neo4j older than 2026.01 or not using Cypher 25 | Use `queryNodes`/`queryRelationships` procedures, or upgrade to a supported version |
| Index query fails right after creation | `state = 'POPULATING'` | Check `SHOW VECTOR INDEXES` and wait for `ONLINE` |
| Query reports mismatched vector dimensions | Query differs from `vector.dimensions` | Generate embeddings with matching dimensionality and a consistent model |
| Vector missing from results | Missing embedding, wrong dimension/type, invalid cosine vector | Check property and input values, and confirm the node qualifies for indexing |
| Index exists, but `MATCH ... WHERE` does not run semantic search | Vector index is a search index invoked explicitly | Use `SEARCH` or vector query procedures |
| Top-2 followed by `WHERE topic` returns empty | Post-filtering drops needed candidates | On newer versions, include the property in the vector index and filter inside `SEARCH ... WHERE` |
| Writing a vector and querying in the same transaction sees nothing | Index does not reflect uncommitted changes within the same transaction | Commit the write and open a new read transaction |
| Scores and order change after upgrade | Provider, quantization, ANN, and data changed | Measure recall@k, inspect `indexProvider` and `options`, and re-evaluate config |
| `CREATE` quantization option not recognized | Using a new option on an older version | Check version compatibility table; remove unsupported options or upgrade |

## 13. Practice Exercises with Answers

**Exercise 1 — Predict the order.** Given `q = [1.0, 0.0, 0.0]` and the five vectors in Section 5, which three documents are closest under **exact** cosine similarity?

**Answer:** D01, D02, D03. In an ANN environment, run the query and compare rather than asserting all three will always appear in every case.

**Exercise 2 — Choose the syntax.** A Neo4j 5.16 system needs an embedding index on `(:Article)` and top-5 queries. Can you use `SEARCH`?

**Answer:** Not yet. You can create the index using `CREATE VECTOR INDEX`, but use `db.index.vector.queryNodes()` to query it. `SEARCH` for vector indexes arrived in Neo4j 2026.01 and requires Cypher 25.

**Exercise 3 — Distinguish pre-filtering from post-filtering.** When you only want `topic = 'java'` and the initial ANN query fetches global top-2 across all data, what is the risk?

**Answer:** The global top-2 may be D01 and D02, causing post-filtering to return zero rows even though D03 is valid. Use a filter directly inside `SEARCH` with indexed metadata on 2026.01+, or evaluate fetching a broader candidate pool on older versions.

**Exercise 4 — Choose vector storage.** An application runs Community Edition and needs Neo4j 5.x compatibility. Which property type should it start with?

**Answer:** `LIST<INTEGER | FLOAT>`. The native `VECTOR` type is only available from Neo4j 2025.10 with Cypher 25 and requires the appropriate block store format.

**Exercise 5 — Changing embedding models.** Model A outputs 768 dimensions and Model B outputs 1536 dimensions. Can you keep the 768-dimension index, write B's vectors into the same property, and continue querying reliably?

**Answer:** No. The new data does not match the index schema's dimensionality; you need model version management, a new property/index, or a planned rebuild of data and indexes.
