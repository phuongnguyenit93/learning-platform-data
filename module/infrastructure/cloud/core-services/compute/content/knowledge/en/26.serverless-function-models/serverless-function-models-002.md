# Packaging functions with source packages or container images

A serverless function is more than just a few lines of source code. For the platform to initialize the function and process events, the source code must be accompanied by a runtime, dependent libraries, handler configuration, and required assets. That bundle is packaged into a deployment artifact.

Two common packaging approaches are **source packages** and **container images**. A source package typically contains source code and dependencies in a format supported by the platform, such as a ZIP archive or language-specific package. A container image packages the application in an OCI-compliant image containing the filesystem, runtime, and dependencies. Each approach has different build workflows, size limits, testing methods, and startup characteristics.

This lesson belongs to the **CLOUD_CORE_SERVICES_COMPUTE** module, chapter **Serverless function models**. It helps you choose the right packaging format, organize handlers and dependencies, produce reproducible artifacts, verify architecture compatibility, optimize startup time, deploy safely, and secure the software supply chain.

## 1. Deployment artifacts of a serverless function

When an event arrives, the serverless platform needs to know where the executable code lives, which runtime is used, which handler receives the event, which libraries must be loaded, which configuration applies, and how to start the application.

The deployment artifact is what gets built and published for the platform to execute. An artifact can be a source package or a container image. Some platforms accept source code and build it into an internal artifact; others let developers build images themselves and push them to a registry.

### 1.1. Components typically included in an artifact

| Component | Role | Example |
|---|---|---|
| Handler code | Entry point for event processing | Function handling an HTTP request or queue message |
| Runtime | Language execution environment | Python, Node.js, Java, .NET |
| Dependencies | Libraries needed by the application | SDKs, parsers, frameworks |
| Native libraries | Libraries compiled for OS/CPU | OpenSSL, image codecs, database clients |
| Assets | Files needed by the application at runtime | Templates, schemas, small models |
| Entrypoint/handler configuration | Defines how the application is invoked | Module and function name, executable, or command |
| Metadata | Build and release information | Version, commit, checksum, SBOM |

Not every platform requires developers to package the runtime. With managed runtimes, the provider supplies a compatible runtime; the source package only needs the code and required dependencies. With custom runtimes or container images, the development team takes greater responsibility for the execution environment.

### 1.2. Source packages and container images in the deployment flow

~~~mermaid
flowchart TD
    S["Source code + dependency manifest"] --> B["Build / Resolve dependencies"]
    B --> P["Source package"]
    B --> I["Container image"]
    P --> V["Validate package layout and handler"]
    I --> R["Build OCI layers and image metadata"]
    V --> A["Publish artifact"]
    R --> A
    A --> D["Deploy function configuration"]
    D --> T["Invoke with test event"]
    T --> M["Monitor errors, latency and cold start"]
~~~

Building and deploying are two distinct responsibilities. Building creates an immutable artifact; deploying binds that artifact to function settings such as handler, memory, timeout, environment, triggers, and execution permissions. Separating these two steps lets the exact same artifact be promoted through test, staging, and production without rebuilding differently per environment.

## 2. What is a source package?

A source package is a bundle containing source code and the files needed for the platform to load the function. Common formats include a ZIP archive with source code and installed libraries, a JAR for Java applications, a deployment package generated by the platform’s build tool, or a source bundle built by the platform via buildpacks.

Source packages are usually a good fit when the platform offers a compatible managed runtime and dependencies can be packaged according to that runtime’s conventions.

### 2.1. Package structure

Example of a Python source package:

~~~text
function-package/
  app.py
  handlers/
    __init__.py
    orders.py
  common/
    __init__.py
    validation.py
  requests/
    ...
  certifi/
    ...
~~~

The `app.py` file can define the handler:

~~~python
import json

def handle_order(event, context):
    order_id = event.get("order_id")
    if not order_id:
        return {
            "statusCode": 400,
            "body": json.dumps({"error": "missing order_id"}),
        }

    return {
        "statusCode": 200,
        "body": json.dumps({"accepted": True, "order_id": order_id}),
    }
~~~

The module name and handler function must match the platform configuration. One platform may require a string pointing to the module and function; another may use conventions or a dedicated manifest. Do not assume all providers use the same handler syntax.

### 2.2. Including dependencies in the package

A source package must include dependencies not already provided by the runtime. You can use a package manager to install libraries into a build directory:

~~~bash
python -m pip install --requirement requirements.txt --target build/package
Copy-Item app.py build/package/app.py
Compress-Archive -Path build/package/* -DestinationPath function.zip
~~~

The commands above illustrate the workflow on Windows PowerShell. In Linux CI, use the corresponding ZIP tool. Inspect the archive contents afterward to ensure the handler file and libraries sit at the exact directory level the runtime expects.

Do not include the entire development environment in the package. Virtual environments, test data, pip caches, Git metadata, IDE configs, and unneeded build files bloat the artifact and increase download/load times.

### 2.3. Dependency manifest and lock file

A manifest declares the direct libraries an application needs. A lock file records resolved versions along with transitive dependencies so builds are reproducible.

Example requirements with pinned versions:

~~~text
requests==2.32.3
pydantic==2.9.2
~~~

For other ecosystems, use the corresponding lock file such as package-lock.json, pnpm-lock.yaml, poetry.lock, uv.lock, packages.lock.json, or the dependency lock file of your Java build tool.

Pinning only direct libraries may not be enough if transitive dependencies change. Generate and commit lock files, update them deliberately, and record runtime/toolchain versions in the pipeline.

## 3. What is a container image?

A container image is an immutable template used to create containers. An image typically includes filesystem layers, a runtime or base operating system userspace, application code and dependencies, native libraries, plus metadata for entrypoint, command, default environment, and user.

An OCI-compliant image can be stored in a container registry and referenced by tag or digest. A serverless platform supporting container images pulls the image from the registry and initializes an execution environment according to the platform’s contract.

Container images fit well when you need control over the runtime, native dependencies, OS userspace, or want a unified packaging format shared with other container environments.

### 3.1. Basic Dockerfile

~~~dockerfile
FROM python:3.12-slim

WORKDIR /function

COPY requirements.txt .
RUN pip install --no-cache-dir --requirement requirements.txt

COPY app.py .
COPY common/ ./common/

# The actual command must comply with the serverless platform's runtime contract.
CMD ["python", "-m", "app"]
~~~

The Dockerfile above only illustrates packaging a Python application into an image. A function container platform may require a dedicated base image, runtime interface client, bootstrap executable, or HTTP server matching its protocol. You cannot assume an arbitrary CMD will be invoked by the platform just like a standard web container.

### 3.2. Base image

The base image largely determines the initial userspace environment. Choose an image compatible with the platform’s runtime and CPU architecture, with a clear publisher and update policy, minimal unnecessary components, regular security patching, and digest pinning for reproducible builds.

Slim or distroless images can reduce size and attack surface, but verify they include required CA certificates, timezone data, shell/tooling, or runtime libraries needed by the application. Validate with tests on the final image before stripping components.

## 4. Comparing source packages and container images

| Criterion | Source package | Container image |
|---|---|---|
| Runtime | Usually uses a managed runtime or platform-provided runtime | Can package runtime/userspace as required by the platform |
| Controlled components | Source code, dependencies, and supporting files | Filesystem, runtime, dependencies, native libraries, and metadata |
| Build | Package manager, ZIP/JAR, or build service | Container build engine producing an OCI image |
| Complexity | Usually lower with standard runtimes | Higher due to managing base images, layers, and registries |
| Native dependencies | Must be built for the exact runtime/ABI/CPU environment | Easier to control userspace, though OS/ABI/CPU must still match |
| Size | Usually small when dependencies are lean | Can be larger due to base image and layers |
| Startup | Can be fast when the package is small and runtime is pre-warmed | Depends on image size, caching, runtime bootstrap, and platform |
| Consistency | Depends on managed runtime and build environment | Can package a more consistent environment |
| Reusability | Easy to use within the corresponding function runtime ecosystem | Reusable across compatible OCI environments |
| Best suited for | Small functions, standard runtimes, pure-language dependencies | Complex native dependencies, custom runtimes, userspace control |

Neither option is universally better. Source packages generally reduce operational burden when a managed runtime meets requirements. Container images increase control, but the development team assumes greater responsibility for base image updates, vulnerability scanning, runtime compatibility, and registry management.

## 5. How to choose a packaging format

Choose based on workload requirements:

| Question | Prefer source package when... | Prefer container image when... |
|---|---|---|
| Runtime | Provider’s standard runtime meets needs | Custom runtime or userspace is required |
| Dependencies | Pure-language libraries, easy to install | Native libraries or specialized OS packages exist |
| Environment control | Managed environment is acceptable | Userspace and image configuration must be pinned |
| Size | Artifact can be kept small | Layers can be optimized and larger images are acceptable |
| Build tooling | Package manager is sufficient | A Docker/OCI build pipeline already exists |
| Operations | Want to minimize OS image management | Processes exist for patching, scanning, and publishing images |
| Reusability | Primarily within one function platform | Same artifact is needed across multiple OCI environments |

A practical rule of thumb: start with a source package if the platform provides a suitable runtime and dependencies are simple. Move to a container image when there is a concrete reason such as hard-to-package native libraries, a custom runtime, userspace requirements, or a shared build flow with container platforms.

### 5.1. Do not choose a container image just because the app already has a Dockerfile

A Dockerfile meant for a web service is not automatically compatible with a function platform. A function platform may require a runtime interface or adapter to receive invocations, handler specification via environment variables or metadata, specific request/response conventions, an internal port, dedicated bootstrap and health checks, or filesystem and startup-time limits.

Before choosing an image, verify the platform’s image contract: entrypoint, command, handler, port, protocol, signals, and event delivery mechanism.

## 6. Handler and runtime contract

The handler is the entry point called by the platform when an invocation arrives. The runtime contract specifies how the platform passes events, context, deadlines, and results to the application.

A handler may receive an event payload, context containing request ID/deadline, environment variables, and framework-specific runtime context.

### 6.1. Separating business logic from the adapter

~~~python
def handle_order(event, context):
    command = parse_order_event(event)
    result = order_service.accept(command)
    return format_response(result)
~~~

`order_service` does not need to know whether the event came from an API gateway, a queue, or a scheduler. The adapter handles parsing the payload, validating structure, and formatting the result per trigger.

Benefits:

- Unit test business logic without needing the cloud runtime.
- Swap triggers with minimal code changes.
- Easily run the same logic in local tests and the function runtime.
- Reduce coupling to provider-specific SDKs or context objects.

### 6.2. Initializing outside the handler

Some platforms keep execution environments around to reuse across invocations. Clients, connection pools, or schema caches can be initialized at module scope to avoid repeated overhead.

However, do not assume the same instance will always receive the next invocation; do not store business data solely in global memory; check for expired connections; do not share mutable state across invocations without synchronization; and use lazy initialization if a dependency is only needed on certain branches.

## 7. Building source packages for the target runtime

A source package must be compatible with the runtime the platform will execute. That includes language version, operating system, CPU architecture, ABI, and native libraries.

### 7.1. Build dependencies in a compatible environment

A Python dependency with a native extension built for Windows x86-64 will not run on Linux ARM64 just because the ZIP file uploaded successfully. Likewise, Java JNI libraries or Node.js native addons depend on OS and architecture.

Build dependencies inside a runtime-compatible build container, a CI runner matching the OS/architecture, a provider-supported build service, or a tested cross-compilation toolchain.

For pure-language packages, building is usually simpler, though runtime and dependency versions still need verification.

### 7.2. Example: building a Python package inside a Linux container

~~~bash
docker run --rm --platform linux/amd64 -v "$PWD:/workspace" -w /workspace python:3.12-slim sh -c "python -m pip install -r requirements.txt -t build/package"
~~~

This example illustrates building dependencies for Linux AMD64. Substitute the platform and runtime image for your target environment. Do not use an AMD64 build output for ARM64 if dependencies contain native binaries.

### 7.3. Inspecting archive layout

~~~bash
unzip -l function.zip
~~~

Check that the handler is in the right location, dependencies sit in the directory the runtime searches, there is no unintended extra wrapper folder, no test/cache/credential files were packaged, native files match the target architecture, and required config/certificate files are present.

Creating an archive from a parent directory instead of the package directory contents can prevent the runtime from finding the module/handler even though the files are inside the ZIP.

## 8. Dependencies and native libraries

Dependencies fall into pure-language libraries, libraries with native extensions, OS packages, and runtime tools. Source packages generally require teams to ensure native dependencies match the managed runtime environment. Container images allow packaging extra OS packages, but still require kernel interface, architecture, and runtime contract compatibility.

### 8.1. Avoiding reliance on build-machine libraries

A common failure is a package that works on a laptop but lacks system libraries in the serverless runtime. The build machine may have preinstalled shared libraries that the artifact did not carry along.

~~~bash
ldd path/to/native-extension.so
~~~

The `ldd` command is a Linux tool and only works for compatible binaries. Inspect the output for missing shared libraries; for untrusted binaries, use appropriate static analysis tools instead of executing arbitrarily.

### 8.2. CA certificates and timezones

Applications making HTTPS calls may need a CA bundle. Date/time processing may need a timezone database. Minimal base images sometimes omit these components to save space.

If HTTPS requests fail with certificate verification errors or time logic behaves incorrectly, check the CA bundle, timezone data, and runtime configuration before concluding the remote endpoint is at fault.

## 9. Building reproducible container images

A solid image should be built from defined source and dependencies, traceable to a commit, tested, and published by digest. Do not build images directly on personal machines and push to production without a verification pipeline.

### 9.1. Multi-stage builds

Multi-stage builds separate the compilation environment from the runtime image. Compilers, headers, package manager caches, and build tools do not belong in the final image.

~~~dockerfile
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --requirement requirements.txt --target /install

FROM python:3.12-slim AS runtime
WORKDIR /function
COPY --from=builder /install /opt/python
ENV PYTHONPATH=/opt/python
COPY app.py .
COPY common/ ./common/
CMD ["python", "-m", "app"]
~~~

This example shows dependencies being installed in the builder stage and only the required artifacts copied into the runtime stage. Base images across both stages should be compatible in ABI and native libraries. For function container platforms, replace the command with the entrypoint/runtime interface required by the platform.

### 9.2. Pinning base images

Tags like `python:3.12-slim` can point to different contents over time as images are updated. Pinning by digest ensures builds use the exact approved base image content.

~~~dockerfile
FROM python:3.12-slim@sha256:REPLACE_WITH_APPROVED_DIGEST
~~~

The digest here is a placeholder. The pipeline should retrieve the real digest from a trusted registry, verify it, and update it deliberately. Pinning digests provides reproducibility but does not automatically apply patches; establish a periodic process to detect new base images and rebuild.

### 9.3. Build context and .dockerignore

The build context is the set of files sent to the container builder. A `.dockerignore` file excludes unnecessary content:

~~~text
.git
.venv
__pycache__
.pytest_cache
tests
coverage
.env
*.pem
*.key
~~~

Do not include credentials, personal env files, private keys, or test data in the build context. Ignoring a file in the image does not erase sensitive data previously committed to Git or stored in build logs; remediate exposed secrets at the source and in history.

## 10. CPU architecture and ABI

Function runtimes can run on architectures such as x86-64/AMD64 or ARM64. The artifact must match the architecture configured for the function.

Items to verify:

- Architecture of the function configuration.
- Architecture of binaries inside a source package.
- Architecture and manifest of a container image.
- ABI and libc required by native dependencies.
- Runtime version and compiler target.
- Native libraries loaded at startup.

### 10.1. Multi-architecture container images

An OCI image index/manifest list can reference multiple image manifests for different architectures. Both the registry and the platform must support multi-architecture images; not every function platform accepts all manifest lists.

~~~bash
docker buildx build --platform linux/amd64,linux/arm64 --tag registry.example.com/orders-function:1.4.0 --push .
~~~

This command illustrates Buildx. Verify that the builder supports the target platforms, native dependencies compile for both architectures, and the serverless platform supports that manifest format. If a provider requires a specific architecture, publish an image for that exact target rather than relying on defaults.

### 10.2. Inspecting binaries

~~~bash
file path/to/native-library.so
readelf -h path/to/native-library.so
~~~

The output confirms the ELF format and machine architecture. Also check the required dynamic linker and shared libraries; a binary with the right architecture can still fail to run if the ABI or system libraries are incompatible.

## 11. Artifact size and cold starts

A cold start is the time needed by the platform to prepare an execution environment before the function handles an invocation. Part of that time can involve downloading the artifact, extracting or mounting the package, initializing the runtime, importing dependencies, creating clients, and connecting to external services.

Package/image size can influence download and initialization time, though it is not the only factor. Runtime choice, dependency count, native initialization, networking, registry caching, and platform internals all play a role.

### 11.1. Optimizing source packages

- Package only dependencies that are actually used.
- Exclude tests, caches, unnecessary bytecode, and developer docs.
- Avoid copying an entire virtual environment.
- Split shared dependencies into layers if supported by the platform.
- Use a lock file and install dependencies in the build stage.
- Avoid heavy module-scope imports if only one branch needs them.
- Check artifact size and load time after every change.

### 11.2. Optimizing container images

- Use a minimal base image that still satisfies runtime dependencies.
- Apply multi-stage builds.
- Consolidate package installation steps to minimize extra layers.
- Remove package caches and build files from the final stage.
- Never copy the source tree, test data, or unnecessary credentials.
- Target the exact architecture to avoid shipping redundant binaries.
- Use a registry close to the deployment environment if the platform supports regional placement.

### 11.3. Measure rather than guess

Track source package or compressed image size separately, along with artifact publish and download times, runtime bootstrap, module imports, dependency initialization, p50/p95/p99 cold-start latency, warm invocation latency, and cold-start rate under traffic patterns.

Do not sacrifice security or correctness just to shave off a few megabytes. Removing a required native library can break function startup; stripping too much logging can destroy troubleshooting visibility.

## 12. Runtime and environment configuration

Artifacts should contain code and dependencies; per-environment configuration is usually supplied via function configuration or environment variables.

Common settings:

- Handler or runtime entrypoint.
- Timeout and memory.
- CPU/architecture if selectable on the platform.
- Environment variables.
- Network/VPC attachment.
- Execution role or service identity.
- Triggers and concurrency.
- Temporary storage.

Do not hard-code endpoints, account identifiers, passwords, or tokens inside a source package or image. The exact same artifact should deploy across environments via external configuration.

### 12.1. Environment variables

Environment variables suit non-secret configuration such as environment names, feature flags, or endpoints. For secrets, use a secret manager or the platform’s secret management mechanism and grant least-privilege read access to the execution identity.

Do not print the entire environment to logs while debugging. Some variables may hold credentials or internal details.

### 12.2. Execution identity

Resource access permissions should be granted to the identity used by the function runtime. Artifacts should not carry static access keys. Use a role/managed identity/service account with least privilege for required queues, storage, databases, or secret managers.

## 13. Testing artifacts before deployment

Unit testing source code is not enough to prove the deployment artifact works. A package may miss files, have the wrong handler, or lack dependencies; an image might run on a developer machine yet violate the runtime contract.

Test across multiple layers:

1. Unit tests: verify business logic.
2. Handler tests: verify event/context parsing and response format.
3. Package inspection: verify files, dependencies, size, and metadata.
4. Runtime compatibility tests: run the artifact against a matching runtime/architecture.
5. Invocation tests: invoke with events representing real triggers.
6. Failure tests: dependency timeouts, malformed payloads, retries, and timeouts.
7. Performance tests: cold starts, warm latency, memory, and concurrency.
8. Security scans: check dependencies, base images, and secrets.

### 13.1. Inspecting a ZIP

~~~bash
unzip -t function.zip
unzip -l function.zip
~~~

The first command verifies archive integrity; the second lists its contents. Afterward, run a smoke test in a matching runtime to confirm the handler actually loads.

### 13.2. Inspecting a container image

~~~bash
docker image inspect registry.example.com/orders-function:1.4.0
docker run --rm registry.example.com/orders-function:1.4.0
~~~

The `run` command only applies if the image has a local execution mode or standalone default command. For function images, you may need the provider’s runtime emulator or local invocation harness to deliver events using the proper protocol.

### 13.3. Representative test events

Test events should include a minimal valid payload, a large payload within limits, missing required fields, wrong value types, Unicode characters and boundary data, dependency timeouts or errors, and retried requests or redelivered messages.

For queue triggers, test acknowledgement semantics and batch failures. For HTTP triggers, test status codes, headers, bodies, and timeouts. For scheduled triggers, test timezones and idempotency.

## 14. CI/CD workflow for function artifacts

A reliable pipeline builds an artifact once, validates it, stores it, and promotes that exact artifact across environments.

~~~mermaid
flowchart LR
    C["Commit"] --> L["Lint + Unit tests"]
    L --> B["Build package/image"]
    B --> V["Inspect + Compatibility tests"]
    V --> S["Security scan + SBOM"]
    S --> P["Publish immutable artifact"]
    P --> D["Deploy to test"]
    D --> I["Invocation / integration tests"]
    I --> A["Approval / promotion"]
    A --> R["Deploy same digest/version"]
    R --> O["Observe and rollback if needed"]
~~~

Key steps:

- Check out the exact commit and inspect dependency manifests.
- Install pinned toolchain/runtime versions.
- Run linting, unit tests, and source security checks.
- Build the source package or OCI image.
- Validate structure, size, and architecture.
- Generate checksums, an SBOM, and scan dependencies/images.
- Publish the immutable artifact.
- Deploy to test/staging and invoke with representative events.
- Promote the same artifact to production.
- Monitor errors and latency, and roll back to a known version if needed.

### 14.1. Do not rebuild separately for staging and production

If staging and production use artifacts built in two separate runs, dependencies or base images may have drifted. During an incident, it becomes hard to prove both environments run identical contents.

Publish artifacts with an immutable version or digest and reference that exact artifact in each environment. Runtime configuration may vary, but the binary/package/image should remain identical.

### 14.2. Versions and digests

Human-readable tags like `1.4.0` are convenient for operators but can be overwritten if the registry permits it. Digests pinpoint the exact image content. For source packages, store checksums and artifact versions in the release system.

Deployment records should capture the source commit, build ID and builder identity, runtime/toolchain version, dependency lock file hash, package checksum or image digest, SBOM and scan results, and function configuration version.

## 15. Artifact supply-chain security

Both source packages and container images can carry malicious dependencies, vulnerable libraries, or accidentally packaged secrets. Security must apply from dependency resolution through deployment.

### 15.1. Dependency hygiene

- Use trusted package registries.
- Pin versions and review updates.
- Minimize unnecessary dependencies.
- Track vulnerabilities and licenses.
- Never install packages from unverified URLs.
- Lock compiler, runtime, and build tool versions.

### 15.2. SBOM

A Software Bill of Materials (SBOM) describes the software components inside an artifact. An SBOM aids dependency inventory, impact queries when vulnerabilities emerge, and license checks.

An SBOM should be tied to the exact artifact version/digest. If you rebuild or change dependencies, generate a corresponding new SBOM.

### 15.3. Image scanning and signing

For container images, scan both the base image and packages across layers. The final image may still retain files or packages from earlier stages if multi-stage copies are poorly designed.

Images or artifacts can be signed and verified prior to deployment. Signing is only effective when trust policies, signer identities, and verification workflows are properly configured.

### 15.4. Secret scanning

Inspect source packages, image layers, and build contexts for private keys, tokens, passwords, or environment files. Deleting a file in a later layer does not necessarily remove content stored in an earlier image layer; keep secrets out of the build context from the start.

## 16. Registries and artifact access permissions

Container images are typically stored in a registry. Source packages can reside in an artifact repository or the provider’s code/deployment package store.

Operational requirements:

- Authentication and authorization on the registry/repository.
- Function deployment identity has pull access only to needed artifacts.
- CI identity has push access only to designated repositories.
- No long-lived registry credentials embedded inside images.
- Retention policies that do not delete currently deployed or rollback-needed artifacts.
- Replication/caching if the platform requires artifacts to reside in specific regions.
- Audit logging for publish, delete, and pull actions where supported.

For source packages, retain artifacts with their checksums and metadata so exact redeployments are possible. Do not rely on ephemeral build directories on CI runners.

## 17. Platform deployment models

Cloud providers offer several packaging paths. Service names and runtime details vary, but three general models stand out:

| Model | How developers supply artifacts | Primary responsibilities |
|---|---|---|
| Managed language runtime | Source package or language bundle | Correct handler, runtime version, and dependencies |
| Custom runtime | Source package with bootstrap/runtime adapter | Runtime contract compliance and bootstrap management |
| Container-based function | OCI image from registry | Image build, entrypoint, runtime interface, patching, and scanning |

Examples in the cloud ecosystem:

- AWS Lambda supports ZIP deployment packages and container images; each format has its own handler/runtime requirements or image contract.
- Azure Functions supports package deployment for eligible runtimes and offers a custom container model on supported hosting plans.
- Google Cloud Functions (newer generation, also offered within the Cloud Run functions ecosystem) can build from source via managed build pipelines; Cloud Run also supports container image deployment.

These are illustrative examples, not an exhaustive list of current features or limits. Before choosing, check supported runtime versions, CPU architectures, artifact sizes, triggers, image protocols, registry locations, and hosting plans for the specific service.

### 17.1. Managed builds vs. self-managed builds

Managed builds reduce the work of maintaining builders, runtimes, and dependency installation. However, teams still need to pin dependencies and control source revisions, understand build logs and environments, inspect post-build artifacts, know how to recreate artifacts for rollback, and verify runtime and native dependency compatibility.

Building container images yourself grants greater control, but requires pipelines for base image patching, scanning, signing, and registry management.

## 18. Versioning, rollout, and rollback

Artifacts need immutable identifiers so operators know precisely what code a function is running. You can use semantic versions, build numbers, commit SHAs, checksums, or image digests.

A release should link source revision, artifact version and checksum/digest, runtime version and architecture, dependency lock file, function configuration, trigger mappings and execution identity, plus test and scan results.

### 18.1. Separating artifact versions from function configuration

The artifact holds code and dependencies; function configuration governs how the platform executes it. Both can change independently, but they must be versioned and reviewed together.

| Component | Change | Artifact rebuild required? |
|---|---|---|
| Handler logic | Changed | Yes |
| Dependencies | Library added/updated | Yes |
| Base image | Changed | Yes |
| Runtime version required by package | Changed | Usually yes, or requires rebuild/retest |
| Non-secret environment variable | Changed | Usually no |
| Execution role/permissions | Changed | No, but permissions must be tested |
| Timeout/memory | Changed | No, but performance must be tested |
| Trigger/concurrency | Changed | No, but behavior must be tested |

Never modify artifact contents after release. If code or dependencies need changes, produce a new artifact with a new version.

### 18.2. Canary and traffic shifting

If the platform supports versions/aliases or traffic splitting, release the new version to a fraction of traffic first. Monitor invocation error rate, timeouts and throttling, p95/p99 latency, cold-start latency, memory/CPU usage, downstream errors, and retries.

Increase traffic only when metrics meet criteria. If errors climb, shift traffic back to the prior stable version and retain the faulty artifact for investigation.

### 18.3. Rollback

Rollback requires the previous artifact to still exist and remain compatible with current data/configuration. If the new version altered database schemas or message formats, reverting to old code may be unsafe.

Before rollout, identify the prior stable artifact, check package/image registry retention, verify whether schema changes are backward-compatible, check triggers and permissions for the old version, prepare traffic-shifting or redeploy actions, and document automatic rollout stop conditions.

## 19. Common packaging failures and diagnostics

| Symptom | Likely cause | How to check |
|---|---|---|
| Handler not found | Wrong module path, function name, or package layout | List archive, check handler config and import paths |
| Module import failed | Missing dependency or wrong version | Check lock file, package contents, and runtime logs |
| Native library load failed | Wrong architecture, ABI, or missing shared library | Inspect binary, dynamic linker, and base image |
| Image pull failed | Registry permissions, wrong digest, or missing image | Check pull identity, repository, and manifest |
| Container fails to start | Wrong entrypoint, command, or runtime interface | Check startup logs and image contract |
| HTTPS certificate error | Missing CA bundle or wrong trust store | Check certificate store and base image |
| Increased cold starts | Large artifact, heavy imports, or slow initialization | Measure download, bootstrap, imports, and dependency initialization |
| Works locally, fails in cloud | Local environment differs from cloud runtime/architecture | Run smoke test inside matching image/runtime |
| Out of temporary disk space | Function writes too many files to temporary storage | Check temporary storage usage and cleanup |
| Behavior differs between staging/prod | Artifacts built differently or configs differ | Compare checksums/digests, runtime versions, and configuration |

### 19.1. Handler is not invoked

Check in order:

1. Was the artifact published to the right function/version?
2. Does the handler configuration specify the right module and function?
3. Is the handler file at the root or expected package path?
4. Does the runtime version support the syntax/APIs used in code?
5. Is an import error occurring before the handler runs?
6. Is the trigger sending events matching the expected schema?

### 19.2. Image pull or startup failure

Check registry authorization, image digest, architecture, manifest, entrypoint, and runtime interface. If the platform runs images in a private network, verify the image can be pulled from the registry through a provider-supported mechanism.

Do not diagnose solely from a successful deploy status. The deployment control plane may accept an artifact, yet the first invocation still fails when the runtime pulls the image or initializes the handler.

### 19.3. Abnormal cold starts

Break down timing into artifact download, runtime startup, imports, initialization, and dependency connections. If image download dominates, optimize the image/registry. If imports or initialization dominate, trim dependencies, defer unnecessary initialization, or adjust connection strategies.

## 20. Practical example: packaging an order-processing function

A function receives order events from a queue, validates the payload, calls an inventory service, and writes results to storage. The team must choose between a source package and a container image.

### 20.1. Evaluating requirements

- The platform’s managed Python runtime meets the application’s version needs.
- Primary dependencies are pure Python libraries.
- No specialized OS packages are required.
- The package size is small.
- The function needs fast startup and frequent deployments.

In this case, a source package is the simpler choice. If hard-to-build native libraries or a custom runtime are needed later, the team can evaluate container images.

### 20.2. Source package layout

~~~text
orders-function/
  app.py
  order_service.py
  requirements.txt
  tests/
~~~

The `tests` folder is only for the pipeline and is excluded from the production artifact.

Dependency manifest:

~~~text
requests==2.32.3
pydantic==2.9.2
~~~

Handler:

~~~python
import json
from order_service import accept_order

def handle(event, context):
    order_id = event.get("order_id")
    if not order_id:
        raise ValueError("order_id is required")

    result = accept_order(order_id)
    return {
        "statusCode": 200,
        "body": json.dumps({"accepted": True, "result": result}),
    }
~~~

### 20.3. Recommended pipeline

1. Check out the reviewed commit.
2. Install the matching runtime/toolchain.
3. Install dependencies from the lock file.
4. Run unit tests and handler tests.
5. Build the ZIP from the contents of the package directory.
6. Verify ZIP structure, checksum, and size.
7. Scan dependencies and secrets.
8. Publish the artifact with an immutable version.
9. Deploy to the test environment and send a sample queue event.
10. Verify acknowledgements, retries, latency, and access permissions.
11. Promote the same artifact to production.
12. Monitor metrics and retain the prior artifact for rollback.

### 20.4. When moving to a container image

If the application later requires native image codecs or specialized OS libraries, the team can switch to an image. When doing so:

- Choose a base image matching the runtime and architecture.
- Install pinned OS packages and dependencies.
- Use a multi-stage build if a compiler is needed.
- Configure the runtime interface per the function platform.
- Build the image and publish by digest.
- Scan the image, generate an SBOM, and sign if required by policy.
- Run local invocation tests using an appropriate harness.
- Test-deploy and verify cold starts before moving to production.

## 21. Checklist for choosing and packaging function artifacts

Before releasing, confirm:

- [ ] Source package or container image was chosen based on actual runtime and dependencies.
- [ ] Handler and runtime contract match the platform.
- [ ] Runtime version and architecture are explicitly defined.
- [ ] Dependency manifest and lock file are managed in source control.
- [ ] Native libraries match the OS, ABI, and CPU.
- [ ] Source package contains no test data, caches, credentials, or extraneous files.
- [ ] Container image uses a trusted base image with a patching process.
- [ ] Build context excludes secrets and unnecessary files.
- [ ] Artifact has an immutable version, checksum, or digest.
- [ ] Package/image has been inspected and tested in a compatible environment.
- [ ] Cold starts, warm latency, memory, and concurrency have been checked.
- [ ] Environment configuration and secrets are managed outside the artifact.
- [ ] Execution identity has least-privilege permissions.
- [ ] SBOM, vulnerability scans, and secret scans have been completed.
- [ ] Artifact is stored in an access-controlled repository/registry.
- [ ] Staging and production use the exact same artifact version/digest.
- [ ] Canary, rollback, and retention plans are in place.

## 22. Long-term operational process

1. **Inventory:** catalog deployed functions, runtimes, architectures, and artifacts.
2. **Dependency review:** monitor library versions, vulnerabilities, and licenses.
3. **Runtime lifecycle:** track provider runtime support and deprecation schedules.
4. **Base image lifecycle:** periodically update, rebuild, and scan images.
5. **Artifact retention:** keep versions needed for rollback while enforcing retention policies.
6. **Performance review:** measure cold starts, warm latency, package/image size, and memory.
7. **Security review:** verify signatures, SBOMs, registry permissions, and secret handling.
8. **Recovery:** rehearse redeploying older artifacts and checking triggers/configurations.
9. **Retirement:** remove old artifacts per policy after verifying no function/version still depends on them.

## 23. Key takeaways

Source packages and container images are two ways to package serverless functions with different levels of control and operational responsibility. Source packages fit when a managed runtime suffices and dependencies are simple; container images are valuable when custom runtimes, native libraries, or userspace control are needed.

Artifacts must match the platform’s handler, runtime, OS/ABI, and CPU architecture. Build from dependency lock files, exclude unnecessary files, test in a compatible environment, and measure cold starts. For container images, manage base images, layers, registries, digests, and the runtime interface. For both approaches, keep configuration and secrets outside the artifact, use a least-privilege execution identity, generate SBOMs/scans, publish immutable artifacts, and promote the same artifact across environments. This workflow keeps functions easy to deploy, straightforward to roll back, and traceable during incidents.
