# Optimizing JVM, Heap, and Garbage Collection on Cloud Resources

## Lesson Objectives

Java applications running on VMs or containers must share CPU and memory resources with the operating system, monitoring agents, and other workloads. The JVM manages the heap, threads, class metadata, code cache, and several native memory regions. Setting the heap as large as possible or picking a garbage collector by guesswork can lead to long pauses, CPU throttling, container OOM kills, or higher compute costs without performance gains.

Optimizing the JVM on the cloud is a process of measuring real workloads, allocating memory with headroom, selecting a garbage collector suited to latency/throughput targets, and verifying each change under production-like conditions.

After this lesson, you can:

- Distinguish JVM heap, non-heap, and native memory.
- Size the heap appropriately for VM or container RAM limits.
- Understand how CPU quotas and cgroups affect the JVM and garbage collection.
- Choose a collector based on throughput, latency, and heap size targets.
- Collect GC logs, JFR, JMX, and key JVM metrics.
- Design benchmarks, run load tests, and roll out changes safely.
- Diagnose memory leaks, allocation pressure, long pauses, and OOMs.

## 1. Why Optimize the JVM on Cloud?

The JVM provides the execution runtime and memory management for Java applications. The garbage collector (GC) automatically reclaims unreferenced objects, sparing developers manual memory management. However, GC still consumes CPU, uses auxiliary memory, and can introduce pauses or latency variance.

In the cloud, resources are typically constrained by VM size, instance type, CPU quotas, memory limits, or orchestrator policies. A JVM may observe different CPU or RAM counts than expected if the JDK version does not properly detect cgroups. A container with free heap space can still be terminated by the OS if total RSS, direct buffers, thread stacks, and native memory exceed its memory limit.

Common symptoms:

- High CPU usage despite steady request rate because GC runs frequently.
- Rising p99 latency during stop-the-world pauses or CPU throttling.
- Heap climbing steadily after each GC cycle due to live-set growth or a memory leak.
- Continuous Full GCs, stalled allocations, or a near-frozen application.
- Containers getting `OOMKilled` even when heap has not reached `Xmx`.
- Slow JVM startup or warm-up causing latency spikes after scale-out.
- Increasing heap or vCPUs raises cloud costs without improving throughput.

A good configuration balances three goals: throughput, latency, and resource consumption. You cannot optimize one metric in isolation while ignoring the other two.

~~~mermaid
flowchart TD
    A["Application load and SLOs"] --> B["Measure CPU, heap, native memory, and GC"]
    B --> C["Identify bottleneck"]
    C --> D["Adjust heap, collector, or CPU"]
    D --> E["Benchmark under representative load"]
    E --> F{"Meets SLOs and headroom?"}
    F -->|Yes| G["Canary and rollout"]
    F -->|No| C
    G --> H["Monitor production"]
~~~

## 2. Which Memory Regions Does the JVM Use?

Not all memory of a Java process lives in the heap. When calculating memory limits for a VM or container, account for both JVM-managed regions and native memory used by the JVM or libraries.

| Component | Contents | Signals to Monitor |
|---|---|---|
| Java heap | Objects, arrays, and most application-allocated data | Used, committed, max, old/young generations, allocation rate |
| Metaspace | Class and classloader metadata | Used/committed, loaded class count, retained classloaders |
| Code cache | Machine code generated by the JIT compiler | Used, free, and code cache exhaustion |
| Thread stacks | Stack per Java thread | Thread count, stack size, and native memory |
| Direct/off-heap buffers | Off-heap buffers, commonly used for I/O and networking | Direct memory usage, buffer count, and limits |
| GC/JIT/native structures | Internal JVM and collector structures | Native memory, GC worker and compiler threads |
| JNI/native libraries | C/C++ libraries, drivers, and off-heap allocations | RSS, native allocations, and library leaks |
| Memory-mapped files | Files mapped into address space | Mapped memory, page residency, and OS limits |

The heap is the easiest region to inspect via Java tooling, yet it does not represent total process memory. Process RSS also depends on resident pages in RAM, native allocations, mapped files, and OS memory management.

### 2.1. Heap Reserved, Committed, and Used

Distinguish these three concepts:

- **Max/reserved:** maximum limit the JVM may use for the heap based on flags and ergonomics.
- **Committed:** portion of the heap the JVM has committed for potential use.
- **Used:** portion of the heap currently holding allocated objects.

Used is typically less than or equal to committed; committed does not necessarily equal max. Reserved address space also does not mean all of it occupies physical RAM.

After GC, used memory may drop while committed remains high so the JVM can reuse it quickly. Thus, a flat committed-heap chart does not automatically prove a memory leak.

### 2.2. Live Set and Allocation Rate

**Live set** is the amount of objects remaining after GC reclaims unreachable objects at a specific load level. A live set growing steadily across GC cycles can indicate the application is retaining more data or using an unbounded cache.

**Allocation rate** is the speed at which the application creates objects, typically measured in bytes/second. A high allocation rate can trigger frequent young GCs, though if objects die quickly and GC handles them efficiently, it is not necessarily a problem.

To size the heap, observe live set, allocation rate, object lifetimes, promotion rate to old generation, and burst headroom together. Do not pick `Xmx` solely from heap used at a single point in time.

## 3. Allocating Heap Within Cloud RAM Limits

### 3.1. Account for Off-Heap Memory

Suppose a container has a 4 GiB memory limit. The JVM cannot use all 4 GiB as heap because memory is also needed for:

- Metaspace and code cache.
- Thread stacks for request threads, workers, GC, and compiler threads.
- Direct buffers from NIO, HTTP clients, and frameworks.
- Native libraries, TLS, compression, and drivers.
- GC bookkeeping and JVM internal structures.
- Monitoring agents, sidecars, and helper processes if they share the cgroup limit.
- Headroom for spikes, page cache, and runtime fluctuations.

An initial estimation approach allocates most RAM to the heap while preserving ample headroom for native memory and variance. For example, on a 4 GiB container you might start testing a max heap around 2.5–2.8 GiB, then measure RSS, native memory, GC, and real load to adjust. This is not a fixed ratio for every application.

~~~mermaid
flowchart TD
    A["Container / VM memory limit"] --> B["Heap"]
    A --> C["Metaspace and code cache"]
    A --> D["Thread stacks"]
    A --> E["Direct buffers and native libraries"]
    A --> F["GC/JIT and runtime overhead"]
    A --> G["Agents, sidecars, and headroom"]
~~~

If `Xmx` is set right up against the memory limit, the application may get OOM-killed before Java throws `OutOfMemoryError`. The OS or container runtime enforces total cgroup memory, not just the heap.

### 3.2. Configuring `Xms` and `Xmx`

- `Xms` sets the initial heap size.
- `Xmx` sets the maximum heap limit.

Example:

~~~bash
java -Xms1g -Xmx3g -jar orders-service.jar
~~~

Initial heap is 1 GiB and maximum is 3 GiB. The JVM can expand the heap as needed. Setting `Xms` equal to `Xmx` keeps heap size steadier for some workloads, but increases early memory commitment and reduces elasticity. Do not set `Xms = Xmx` out of habit when containers have tight memory limits.

When sizing, test multiple `Xmx` values and measure:

- Live set after steady GC cycles.
- Allocation rate and GC frequency.
- Pause times and tail latency.
- RSS/working set and native memory.
- OOMs or cgroup memory pressure.
- Throughput per vCPU and cost per request.

### 3.3. Using RAM Percentages Instead of Fixed `Xmx`

Modern JVMs support RAM percentage flags such as:

~~~bash
java -XX:InitialRAMPercentage=30.0 \
     -XX:MaxRAMPercentage=65.0 \
     -jar orders-service.jar
~~~

`MaxRAMPercentage` lets the JVM compute max heap from the RAM detected by the runtime. `InitialRAMPercentage` controls initial heap. Flag names, defaults, and container detection depend on JDK version and vendor.

This approach is useful when the same image runs under multiple memory limits. However, verify that the JVM actually detects cgroup limits. On older JDKs or unusual container setups, the JVM might calculate from host RAM instead of the container's memory limit.

Inspect flags and JVM details:

~~~bash
java -XX:+PrintFlagsFinal -version
~~~

On JDKs supporting cgroup awareness, also inspect runtime and container details via JVM tools or startup logs. Do not infer max heap solely from Kubernetes YAML; verify the value the process actually uses.

### 3.4. Sizing Example in Kubernetes

A Deployment with a 3 GiB memory request and 4 GiB limit might start with max heap around 65% of the limit:

~~~yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders-service
  template:
    metadata:
      labels:
        app: orders-service
    spec:
      containers:
        - name: app
          image: registry.example.com/orders-service:2.1.0
          env:
            - name: JAVA_TOOL_OPTIONS
              value: "-XX:InitialRAMPercentage=30.0 -XX:MaxRAMPercentage=65.0 -XX:+UseG1GC"
          resources:
            requests:
              cpu: "1"
              memory: 3Gi
            limits:
              cpu: "2"
              memory: 4Gi
~~~

This example is only a starting point. Requests and limits must be based on load, QoS, node capacity, and cluster policies. Kubernetes normally enforces memory requests/limits per container; size heap against the app container's limit and size sidecars against their own limits. If the platform or runtime applies additional Pod-level cgroup limits, verify the actual limit visible to the process. Check that containers are not `OOMKilled` and max heap is detected correctly by the JVM.

## 4. CPU Quotas and the JVM on VMs/Containers

The JVM uses available CPU count to decide thread counts for GC, the JIT compiler, `ForkJoinPool`, and certain runtime mechanisms. In containers, CPU limits may be enforced via quotas/cgroups. If the JVM fails to detect the CPU quota accurately, it can spawn far more threads than actual CPU capacity warrants.

Consequences can include:

- Increased context switching.
- GC workers competing with application threads for CPU.
- Concurrent GC lacking enough CPU to finish on time.
- CPU throttling stretching pauses or request latency.
- Default thread pools sized larger than suitable for the container.

Modern JDKs support container awareness, though support levels vary by version and vendor. Verify the processor count observed by the JVM rather than assuming the JVM always reads quotas properly.

Useful inspection commands:

~~~bash
# View CPU info seen by the guest OS
nproc
lscpu

# View JVM flags and runtime details
jcmd <pid> VM.info
jcmd <pid> VM.flags
~~~

If needed, the JVM provides `ActiveProcessorCount` to specify the CPU count the JVM should treat as available:

~~~bash
java -XX:ActiveProcessorCount=2 -jar orders-service.jar
~~~

Use this only after confirming auto-detection is wrong or when simulating a specific limit. Setting it lower than reality can reduce parallelism; setting it above the quota can increase CPU contention.

When adjusting CPU limits, measure CPU throttling, run queues, GC worker activity, request throughput, and p99 latency. Adding CPU does not always speed up GC if the bottleneck lies in memory bandwidth, lock contention, or I/O.

## 5. How Garbage Collection Works

GC locates and reclaims objects no longer reachable from GC roots such as stacks, static fields, and JNI references. Collectors differ in how they partition the heap, identify live objects, relocate objects, and trade off pauses against throughput.

Common concepts:

- **Young generation:** region typically holding newly allocated objects; short-lived objects can be reclaimed cheaply.
- **Old generation:** holds long-lived or promoted objects.
- **Minor/young collection:** reclaims the young region per collector design.
- **Major/old/full collection:** terminology and scope depend on the collector; not all JVMs define them identically.
- **Stop-the-world pause:** GC phases that temporarily pause application threads.
- **Concurrent phase:** GC runs alongside the application, still consuming CPU.
- **Promotion:** long-lived objects moved to another managed region, usually the old generation.
- **Allocation failure:** the JVM cannot allocate an object normally and may trigger GC or throw an error.

GC is not free work. Collectors need CPU to mark, sweep, relocate objects, and maintain metadata. Collectors minimizing pauses may use more CPU or memory; collectors optimizing throughput may tolerate longer pauses.

## 6. Choosing a Garbage Collector by Target

No single collector is best for all applications. Selection depends on JDK version, heap size, object lifetimes, allocation rate, available CPU, and latency SLOs.

| Collector | Key Characteristics | When to Consider |
|---|---|---|
| G1 GC | Splits heap into regions, balances throughput and pauses; typically the default on modern server JDKs | General server workloads, medium to large heaps, targeted pauses |
| Parallel GC | Parallel collection, prioritizes throughput; may produce longer pauses | Batch or workloads prioritizing total throughput over tail latency |
| ZGC | Collector with concurrent phases targeting ultra-short pauses on supported JDKs | Latency-sensitive workloads, large heaps, or low-pause requirements |
| Shenandoah | Concurrent collector targeting low pauses; availability depends on JDK distribution | Supported JDK environments and workloads needing low latency |
| Serial GC | Simple collector using few threads; suits small applications | Small JVMs, low CPU, or lightweight workloads |
| Epsilon GC | Does not reclaim objects; for specialized testing | Allocation benchmarks or testing GC-free behavior, not for long-running services |

G1 is usually a sensible starting point unless data indicates another collector is needed. ZGC and Shenandoah can reduce pauses without automatically raising throughput or cutting total cost. Parallel GC can deliver strong throughput, but pauses must be evaluated against SLOs.

CMS has been removed from modern JDKs; do not pick legacy configurations based on guides for outdated Java versions. ZGC flags, generational capabilities, and defaults vary across JDK versions; always verify against the actual runtime version.

### 6.1. G1 GC

Enable G1 explicitly:

~~~bash
java -XX:+UseG1GC -Xms1g -Xmx3g -jar orders-service.jar
~~~

G1 divides the heap into many regions and attempts to reclaim regions with the most garbage within a pause goal. `MaxGCPauseMillis` sets a pause target, not a guarantee that every pause stays below that threshold.

~~~bash
java -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -Xms1g -Xmx3g \
     -jar orders-service.jar
~~~

Do not repeatedly lower the pause goal without measuring. Overly aggressive pause goals can force GC to work harder or reduce throughput. Inspect pause distributions, allocation rate, old generation, and CPU before tuning.

### 6.2. Parallel GC

Enable Parallel GC:

~~~bash
java -XX:+UseParallelGC -Xms1g -Xmx3g -jar batch-worker.jar
~~~

Parallel GC typically fits batch jobs, background processing, or workloads that can tolerate longer pauses for higher throughput. GC thread count is selected by the JVM based on available CPUs; in containers, verify CPU detection and quotas.

### 6.3. ZGC and Shenandoah

Example enabling ZGC on a supported JDK:

~~~bash
java -XX:+UseZGC -Xms2g -Xmx8g -jar low-latency-api.jar
~~~

Some JDK versions support a generational ZGC option with a separate flag; in newer versions defaults may have changed. Check documentation for your exact version before adding flags.

Shenandoah can be enabled via `UseShenandoahGC` on JDK builds that include it. Not all vendors/builds ship Shenandoah.

Before switching collectors, check:

- JDK vendor and version.
- Whether the collector is included in the build.
- Heap size and memory headroom.
- CPU quota and CPU required by concurrent GC.
- Throughput, p95/p99 latency, and pause distribution.
- Compatibility with frameworks, native agents, and operational requirements.

## 7. Reading GC Logs and Key Metrics

GC logs are vital for understanding heap and collector behavior. On JDK 9+, unified logging can be enabled with:

~~~bash
java -Xlog:gc*,safepoint:file=/var/log/orders/gc.log:time,uptime,level,tags:filecount=5,filesize=20M \
     -Xms1g -Xmx3g \
     -jar orders-service.jar
~~~

This logs GC and safepoint events to files with rotation by file count and size. The directory must exist and the JVM user must have write permissions. In containers, logs may be written to stdout/stderr for platform collection, provided retention is configured to avoid unbounded log growth.

On JDK 8, GC log syntax differs, for example:

~~~bash
java -Xloggc:/var/log/orders/gc.log \
     -XX:+PrintGCDetails \
     -XX:+PrintGCDateStamps \
     -XX:+UseGCLogFileRotation \
     -XX:NumberOfGCLogFiles=5 \
     -XX:GCLogFileSize=20M \
     -jar orders-service.jar
~~~

Logging flags and behavior depend on the JDK 8 update release; verify runtime version and supported flags before applying.

Metrics to monitor:

| Metric | Operational Question |
|---|---|
| Heap used/committed/max | Does the heap still have headroom? |
| Old generation occupancy | Is the live set growing across cycles? |
| Allocation rate | How fast is the application creating objects? |
| GC count and GC time | How often does GC run and how much time does it spend? |
| Pause duration p50/p95/p99/max | How does GC impact tail latency? |
| Promotion rate | Are objects moving to old generation too quickly? |
| Full GC count | Are abnormal full-heap collections occurring? |
| Metaspace/code cache | Is there a classloader leak or code cache pressure? |
| Direct buffer usage | Are off-heap buffers climbing toward limits? |
| Process RSS/container working set | Is total real memory approaching the memory limit? |
| CPU throttling | Are GC and application threads being CPU-throttled? |

Do not look only at GC count. One long GC can be far worse than many brief GCs. Likewise, low total GC time can still hide a single large pause that breaks the p99 SLO.

## 8. Using JFR, JMX, and Diagnostic Tools

### 8.1. Java Flight Recorder (JFR)

JFR captures runtime events such as allocations, GC, thread scheduling, lock contention, class loading, and some I/O activity. It is useful for diagnosing high CPU, allocation pressure, or latency spikes.

Start a short recording on a running JVM using `jcmd`:

~~~bash
jcmd <pid> JFR.start name=performance settings=profile duration=5m filename=/tmp/performance.jfr
~~~

Once finished, open the file in Java Mission Control or a compatible tool. The `profile` settings capture more events; assess overhead, file size, and sensitive data before running long-term in production.

JFR helps answer:

- Which threads consume CPU?
- Which objects are allocated most heavily?
- Is there lock contention or thread parking?
- Do GC pauses and allocations coincide with latency spikes?
- Are there class loading or compilation spikes after scale-out?

### 8.2. JMX and Metrics Endpoints

JMX can expose heap pools, GC counts/times, thread counts, class loading, and runtime information. For production apps, never expose JMX ports directly to the Internet. Use local attach, tunneling, or secured collectors; enforce permissions and authentication per policy.

Micrometer, Spring Boot Actuator, or the OpenTelemetry Java agent can export JVM metrics to your monitoring system. Control endpoints and labels to prevent information leakage or high cardinality.

### 8.3. `jcmd` and `jstat`

Useful commands:

~~~bash
# JVM info
jcmd <pid> VM.version
jcmd <pid> VM.info
jcmd <pid> VM.flags

# Heap summary
jcmd <pid> GC.heap_info

# Periodic GC statistics
jstat -gcutil <pid> 1000 10

# Thread dump
jcmd <pid> Thread.print
~~~

Commands may require running as the same user, attach permissions, and matching JDK tools. Heap histograms or dumps can consume CPU, I/O, and disk space; run them only per an approved runbook.

### 8.4. Heap Dumps and `OutOfMemoryError`

You can configure the JVM to write a heap dump on OOME:

~~~bash
java -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/var/lib/orders/dumps \
     -XX:+ExitOnOutOfMemoryError \
     -Xmx3g \
     -jar orders-service.jar
~~~

Ensure the directory exists, has sufficient space, and is writable. Heap dumps can contain tokens, personal data, payloads, or sensitive business information. Encrypt them, restrict access and retention, and never upload production dumps to public analysis services.

`ExitOnOutOfMemoryError` lets the process terminate cleanly on OOME so the orchestrator can replace the instance per policy. Evaluate readiness, restart backoff, and crash-loop risks before enabling it automatically.

## 9. Distinguishing Java Heap OOM from Container `OOMKilled`

These two situations have different causes and footprints.

**Java heap `OutOfMemoryError`:** the JVM cannot allocate objects in the heap. You may see the exception, a heap dump if enabled, GC logs, and heap near `Xmx`.

**Metaspace `OutOfMemoryError`:** class metadata cannot be allocated within limits or available resources. May relate to classloader leaks, dynamic class generation, or metaspace sizing.

**Direct buffer memory:** the application cannot allocate direct buffers within limits or available native memory.

**Native thread creation failure:** the JVM cannot create more threads due to native memory limits, process/thread limits, or OS resources.

**Container `OOMKilled`:** the kernel or runtime terminates the container because total cgroup memory exceeded the limit. The JVM may not have time to write a heap dump or log a Java exception.

When investigating, correlate:

- Exit code and `OOMKilled` status from the orchestrator.
- Container memory usage/limits and cgroup memory events.
- Process RSS, heap used/committed, and non-heap metrics.
- Kernel logs or node events if accessible.
- GC logs, application logs, and load surge timestamps.
- Sidecars or other processes sharing the cgroup/Pod.

If heap is still low when the container gets `OOMKilled`, investigate direct buffers, thread stacks, native libraries, mapped files, agents, and side processes. Increasing `Xmx` in this situation usually makes things worse.

## 10. Detecting Memory Leaks and Allocation Pressure

Memory leaks in Java usually occur when objects are no longer needed by business logic yet remain reachable from GC roots. Heap dumps can help trace the reference chains retaining objects.

Common signs:

- Post-GC heap used climbs gradually across similar cycles.
- Old generation occupancy rises steadily.
- Object or collection counts grow over time.
- Metaspace grows due to uncollected classloaders.
- Caches, listeners, `ThreadLocal`s, or static collections retain unexpected references.

Allocation pressure differs from a memory leak. An application may create many short-lived objects, causing frequent GC runs while the post-GC live set remains stable. In that case, inspect allocation profiles, object churn, and data processing paths.

An investigation workflow:

1. Record load, throughput, and latency at the time of the incident.
2. Pull GC logs and heap metrics over time.
3. Compare post-GC live sets across equivalent GC cycles.
4. If needed, capture a heap dump at a representative moment.
5. Analyze the dominator tree, retained sizes, and reference paths to GC roots.
6. Check caches, collections, listeners, `ThreadLocal`s, classloaders, and buffer pools.
7. Fix the root cause in the application, then re-benchmark.

Do not conclude a leak solely because committed heap does not shrink. Observe post-GC used memory and live-set trends across many cycles.

## 11. Data-Driven Optimization Workflow

JVM optimization should change one variable at a time against a baseline for comparison.

### Step 1: Define SLOs and Workload

Record:

- Throughput or requests/second.
- p50, p95, and p99 latency.
- Error rate and timeouts.
- CPU, memory limits, disk, and network.
- Normal load, peak, bursts, and batch windows.
- Readiness and warm-up time during scale-out.

### Step 2: Collect Baseline

Run a representative workload long enough to observe steady state. Collect GC logs, JFR or JVM metrics, container stats, and application metrics. Record JDK vendor/version, flags, image digest, VM type, and CPU/memory limits.

### Step 3: Locate the Bottleneck

- CPU saturated: check application CPU, GC CPU, throttling, and thread contention.
- Heap growing after GC: check live set, caches, and leaks.
- Long GC pauses: identify collector phase, heap size, object distribution, and CPU.
- Container OOM: inspect total memory, not just heap.
- Rising tail latency: correlate GC pauses, safepoints, locks, networking, and dependency latencies.

### Step 4: Tune One Variable

For example, change max heap, initial heap, collector, pause goal, or CPU limit. Avoid changing multiple GC flags at once, as it becomes difficult to know which change caused the result.

### Step 5: Re-Benchmark

Use the same data, load, warm-up duration, and infrastructure configuration. Compare throughput, p99, GC pauses, CPU, RSS, OOMs, and cost. Repeat enough times to avoid drawing conclusions from a single run.

### Step 6: Canary and Rollout

Deploy the new configuration to a small subset of instances. Monitor the same metric set against the baseline group. Establish clear rollback criteria if p99, error rate, OOMs, or CPU exceed agreed thresholds.

~~~mermaid
flowchart TD
    A["Define SLOs and representative load"] --> B["Collect baseline"]
    B --> C["Analyze GC, heap, CPU, and RSS"]
    C --> D["Pick one change"]
    D --> E["Repeat benchmark"]
    E --> F{"Better with headroom?"}
    F -->|No| G["Revert and try another hypothesis"]
    G --> C
    F -->|Yes| H["Canary"]
    H --> I{"Production metrics stable?"}
    I -->|No| G
    I -->|Yes| J["Roll out and monitor"]
~~~

## 12. Benchmarking and Load Testing the JVM

Benchmarks must represent how the application is actually used. A test allocating objects in a tight loop does not reflect databases, networking, serialization, lock contention, or request concurrency.

Test types:

| Test Type | Purpose | Example |
|---|---|---|
| Load test | Measure performance at expected load | Sustain 500 requests/second for 30 minutes |
| Stress test | Find limits and degradation behavior | Step load upward until SLOs fail |
| Spike test | Evaluate sudden bursts | Triple load for a short burst |
| Soak test | Detect leaks or degradation over time | Sustain steady load for several hours |
| Startup/warm-up test | Measure time-to-ready after creating instances | Scale from 0 or few replicas up to many |
| Microbenchmark | Measure a small JVM code path | Use JMH for valid microbenchmarks |

For Java microbenchmarks, JMH handles warm-up, forking, and JIT optimization pitfalls. Do not use hand-written loops to judge a method's performance, as the JIT can inline, eliminate, or transform computations.

When benchmarking GC:

- Use the same JDK and flags across runs.
- Keep CPU quotas, memory limits, and instance family identical.
- Run warm-up before measuring.
- Record allocation rate and live set.
- Use a workload with object lifetimes similar to production.
- Measure multiple runs and report distributions, not just a single mean.
- Inspect both p99 and error rate, not throughput alone.
- Ensure test data and dependencies do not skew results.

## 13. Configuration Selection Examples by Workload

### 13.1. Latency-Sensitive REST API

The goal is keeping p99 low and stable. Start with G1 unless evidence justifies another collector. Size the heap to hold the live set and bursts while leaving headroom for direct buffers, thread stacks, and native memory. If GC pauses clearly drive tail latency, test ZGC or Shenandoah on a supported JDK and re-benchmark.

Monitor request p99, GC pause p99, allocation rate, old generation, CPU throttling, and RSS. Do not lower `MaxGCPauseMillis` solely for prettier numbers if throughput drops or CPU rises.

### 13.2. Throughput-Oriented Batch Worker

Batch jobs can tolerate longer pauses if total completion time is good. Parallel GC is a candidate worth benchmarking. A larger heap can reduce GC frequency, though it can also lengthen certain cycle times and increase memory footprint.

Measure records/second, total job duration, CPU-seconds, GC time, and retry counts. Check whether the batch creates huge objects or retains data longer than necessary.

### 13.3. Small Containers with Many Replicas

For containers with tight memory limits, preserve native headroom and avoid letting the heap occupy nearly the whole cgroup. Optimize allocations, bound thread pools, direct buffers, and agent overhead. Many small replicas can improve fault isolation while increasing total baseline memory and scheduling overhead.

Measure cost per request or completed task, not just CPU/memory of a single Pod.

## 14. Common JVM Flags and Usage Principles

| Flag | Purpose | Notes |
|---|---|---|
| `Xms` | Initial heap | Large `Xms` raises committed memory at startup |
| `Xmx` | Maximum heap limit | Leave native headroom inside memory limit |
| `InitialRAMPercentage` | RAM percentage for initial heap | Depends on container awareness and JDK |
| `MaxRAMPercentage` | RAM percentage for maximum heap | Verify JVM detects RAM/cgroup properly |
| `UseG1GC` | Select G1 | Common general-purpose choice on modern server JDKs |
| `UseParallelGC` | Select Parallel GC | Consider for throughput-oriented workloads |
| `UseZGC` | Select ZGC | Check JDK support and CPU/memory overhead |
| `MaxGCPauseMillis` | Pause target for supported collectors | It is a goal, not an SLA |
| `ActiveProcessorCount` | CPU count JVM treats as available | Override only if auto-detection fails or control is needed |
| `HeapDumpOnOutOfMemoryError` | Write heap dump on OOME | Requires disk space, permissions, and data protection |
| `ExitOnOutOfMemoryError` | Terminate JVM on OOME | Requires suitable restart policy and backoff |
| `NativeMemoryTracking` | Track native memory via JVM | Adds overhead; enable as needed and measure impact |

Do not copy long lists of flags from blogs or other systems. Internal flags change across JDKs and may be removed. Prefer documented flags supported by your version, keep configurations simple, and record the rationale for every flag.

To investigate native memory on HotSpot, enable Native Memory Tracking at startup and query via `jcmd`:

~~~bash
java -XX:NativeMemoryTracking=summary -jar orders-service.jar

jcmd <pid> VM.native_memory summary
~~~

Native Memory Tracking tracks only native regions observable by the JVM; it does not replace RSS/cgroup metrics and may not account for all allocations in external native libraries. This feature adds overhead, so evaluate it before enabling long-term in production.

## 15. Common Mistakes

**Setting `Xmx` equal to the entire memory limit:** the JVM still needs native memory, thread stacks, direct buffers, and agents. Leave headroom and measure RSS.

**Raising heap to solve every OOM:** if the cause is native memory, thread leaks, or container limits, raising `Xmx` increases the risk of `OOMKilled`.

**Setting `Xms` equal to `Xmx` on every container:** a large initial heap raises memory commitment and reduces replica density. Use only when workload and headroom justify it.

**Picking a collector by reputation:** low-pause collectors can consume extra CPU or memory. Benchmark on the target JDK and workload.

**Looking only at average GC pause:** a single long pause can ruin p99. Inspect distributions, max, safepoints, and application latency.

**Looking only at heap used:** ignores metaspace, direct buffers, thread stacks, and native allocations. Cross-check RSS and cgroup memory.

**Enabling too many GC flags:** makes configuration hard to understand and upgrade. Change one flag at a time, measure impact, and remove obsolete flags.

**Disabling GC logs:** leaves you blind when analyzing pauses and allocations. Enable logs with proper rotation and retention.

**Writing heap dumps on a filesystem without enough space:** can worsen an incident or lose the dump. Reserve space and protect sensitive data beforehand.

**Benchmarking without warm-up:** results are skewed by JIT compilation and class loading. Run warm-up and multiple repetitions.

**Ignoring CPU throttling:** GC and application threads get throttled together, lengthening pauses and latency. Monitor quotas and throttled time.

**Optimizing one instance while ignoring fleet cost:** better heap/GC tuning may allow fewer replicas or higher density. Measure cost per unit of work at the service level.

## 16. Cloud JVM Operations Checklist

- [ ] Documented JDK vendor, version, runtime flags, and workload type.
- [ ] Verified JVM detects VM/container CPU and memory limits accurately.
- [ ] `Xmx` leaves sufficient headroom for metaspace, code cache, thread stacks, direct buffers, and native memory.
- [ ] `Xms` fits scale-out behavior and memory commitment levels.
- [ ] Measured live set, allocation rate, and old generation after warm-up.
- [ ] Collector selected based on latency/throughput SLOs and benchmarked.
- [ ] GC logging enabled with proper rotation or retention.
- [ ] JVM metrics collected for heap, GC, threads, class loading, and direct buffers.
- [ ] Process RSS/container memory and CPU throttling monitored.
- [ ] JFR or diagnostic data collection procedure ready for investigations.
- [ ] Heap dumps secured with adequate storage capacity.
- [ ] Java OOME distinguished from container `OOMKilled`.
- [ ] Benchmarks include warm-up, representative load, multiple runs, and p99.
- [ ] Every JVM change rolled out via canary with rollback criteria.
- [ ] Cost per request/job measured alongside performance.

Optimizing the JVM on cloud resources starts with understanding total process memory, verifying the CPU and memory limits seen by the JVM, and measuring live set, allocation rate, and GC pauses under representative load. Reserve off-heap headroom, pick a collector aligned with your SLOs and JDK version, enable GC logs/JFR for evidence, and change one variable at a time. Benchmarking, canary rollouts, and tracking cost per unit of work keep JVM configurations performing reliably as cloud load and scale change.
