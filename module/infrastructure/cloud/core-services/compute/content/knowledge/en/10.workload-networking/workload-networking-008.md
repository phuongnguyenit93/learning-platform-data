# Multiple Network Interfaces, Multiple IP Addresses, and OS-Level Routing

A cloud virtual machine typically starts with one network interface and one IP address. However, production workloads often need multiple connectivity paths: one for user traffic, one for administration, one to a private data tier, or multiple IP addresses to serve different services. In such cases, the server must be configured with multiple network interfaces (multi-NIC), multiple IP addresses, and appropriate routing rules.

Adding a new NIC or IP is only part of the configuration. Packets must also pass through cloud route tables, virtual network security policies, host OS firewalls, and the server's own routing table. If these layers are misaligned, the machine may receive a request on one interface yet send the response out another, fail to reach a gateway, or create asymmetric paths.

This lesson belongs to the **Workload Networking** chapter of the **CLOUD_CORE_SERVICES_COMPUTE** module. The module covers cloud compute models from virtual machines to containers and serverless; how to choose CPU, memory, networking, and security configurations; deploying applications, scaling load, ensuring availability, and optimizing operational cost. Within that scope, understanding multi-NICs, IP addressing, and OS-level routing helps design clear traffic paths, control inbound/outbound flows, and operate multi-homed workloads safely.

## 1. Network Interfaces and IP Addresses

### 1.1. What Is a Network Interface?

A **network interface (NIC)** is the interface the operating system uses to send and receive network frames. On a physical server, a NIC is typically a network card or port. On a cloud VM, a NIC is usually a virtual network device provisioned by the platform and attached to the virtual machine.

Each NIC has attributes such as:

- Interface name inside the OS, such as **eth0**, **ens5**, **ens192**, or another predictable name generated by the OS.
- MAC address.
- One or more IPv4/IPv6 addresses.
- MTU (Maximum Transmission Unit).
- Link state and link speed observed by the OS.
- Network-related routes, gateways, and DNS settings.
- Security policies and corresponding subnet in the cloud control plane.

Interface names are not stable identifiers across all systems. NIC ordering can change across machine image updates, kernel upgrades, or hardware profile changes. When automating, rely on predictable names, MAC addresses, metadata, or platform-supplied identifiers instead of assuming the first NIC is always **eth0**.

### 1.2. Multiple IP Addresses on One NIC

One NIC can carry multiple IP addresses. For example, a server might use:

- A primary IP for administration or internal connectivity.
- A secondary IP for a dedicated service.
- Multiple IPs to serve multiple virtual hosts, listeners, or applications binding to specific addresses.
- IPv6 addresses alongside IPv4.

Multiple IPs on the same NIC still share the same physical or virtual link and typically belong to the same subnet. Adding more IPs does not create extra bandwidth or an independent network path.

In the cloud, IP addresses usually must be declared or attached in the provider's control plane before being configured inside the guest OS. Some platforms validate source/destination addresses at the virtualization layer; arbitrarily assigning an unallocated IP inside the OS can cause packets to be dropped. Follow the workflow for your specific NIC and service.

### 1.3. Multiple NICs on One Machine

A machine can attach multiple NICs, each connected to a different subnet or virtual network. For example:

| NIC | Illustrative subnet | Role |
|---|---|---|
| **ens5** | **10.10.1.0/24** | Receives application traffic from the frontend network |
| **ens6** | **10.20.1.0/24** | Connects to databases or backend services |
| **ens7** | **10.30.1.0/24** | Management or monitoring network |

This design helps separate network flows, apply distinct security policies, and control traffic paths. However, all NICs still share the VM's CPU, memory, kernel, and potentially underlying host infrastructure. Multi-NIC does not automatically deliver high availability or aggregate bandwidth.

### 1.4. Distinguishing NIC, IP, and Subnet

- **NIC:** interface that sends and receives frames.
- **IP address:** logical address assigned to an interface or endpoint.
- **Subnet:** IP address range and network policy domain an endpoint belongs to.
- **Gateway:** forwarding point for packets destined to other networks.
- **Route:** rule selecting the next hop or output interface to forward a packet.
- **Route table:** collection of routes used by the OS or cloud control plane.

One NIC can hold multiple IPs; one subnet can hold multiple NICs; one route table can hold paths to many subnets and gateways. Do not confuse IP count with NIC count or independent network path count.

## 2. When Do You Need Multiple NICs or Multiple IPs?

### 2.1. Separating Frontend and Backend Traffic

An application may accept requests from a frontend network and access a database over a backend network. Attaching separate NICs for each network lets you apply dedicated security groups, routes, and firewalls per flow.

Example:

- **ens5** receives HTTPS connections from the load balancer.
- **ens6** connects to the database in a private subnet.
- The application listens only on the frontend address for user requests.
- Database connections originate from the backend address.

This layout reduces the risk of backend services accidentally being exposed to user-facing networks. Still, firewalls at both the cloud and OS levels must be configured properly.

### 2.2. Separating Management and Data Networks

A management network can carry SSH/RDP, monitoring, backups, or operational tooling. A data network serves application requests. Separating NICs restricts which ports and addresses are reachable for each purpose.

Avoid giving the management network a default route or public exposure unnecessarily. Restrict administrative connections to a bastion, VPN, or centralized management system.

### 2.3. Connecting Multiple Networks or Tenants

A network appliance, proxy, gateway, or data-processing machine may need connectivity to multiple VPCs/VNets, subnets, or partner networks. Each NIC attaches to a separate network while the OS performs routing or firewalling between interfaces.

This case requires verifying trust boundaries, IP overlaps, route propagation, source/destination checks, and forwarding permissions. Not every multi-NIC VM is permitted to act as a router between subnets.

### 2.4. Multiple IPs for Multiple Services

A server can use multiple IPs on the same NIC to:

- Bind services to dedicated addresses.
- Keep a service IP portable during application moves or platform-supported failover.
- Serve multiple endpoints, certificates, or virtual hosts per application architecture.
- Differentiate outbound traffic by source address.

Multiple IPs on one NIC fit when you need multiple endpoints without separating physical paths or subnets.

### 2.5. Separating Traffic Paths and Policies

A machine may need to send certain traffic classes through different gateways. For example, internal network traffic exits via the backend NIC while Internet traffic exits via the frontend NIC. In that scenario, OS route tables and policy routing must reflect the intended policy.

Merely attaching another NIC does not guarantee the kernel picks the right NIC for each connection. You must define routes, source addresses, and server response behavior.

## 3. Routing Flow Across Network Layers

A packet leaving a workload can be affected by multiple layers:

~~~mermaid
flowchart TB
    APP["Application / process"]
    OS["OS network stack and route table"]
    NIC["NIC and source IP address"]
    VNET["Cloud subnet, route table, and network policy"]
    GW["Gateway / NAT / Firewall / Peering"]
    DEST["Destination network or service"]

    APP --> OS
    OS --> NIC
    NIC --> VNET
    VNET --> GW
    GW --> DEST
~~~

For inbound traffic, processing flows from the source network through cloud route tables, security policies, and the NIC, then to the host firewall and application socket.

Distinguish two levels of routing:

1. **Guest OS routing:** the kernel selects the NIC, next hop, and source address to transmit packets.
2. **Cloud network routing:** subnet/VPC/VNet route tables, gateways, peering, NAT, or firewalls decide how packets are forwarded across the virtual fabric.

Correct routes inside Linux cannot compensate for missing cloud routes. Likewise, accurate cloud route tables cannot fix a kernel sending responses out the wrong NIC.

### 3.1. Route Selection Order in Linux

Linux uses its Forwarding Information Base (FIB) to determine paths. In standard configurations, the kernel evaluates:

- Policy routing rules in priority order.
- The routing table specified by the matching rule, commonly including **local**, **main**, and **default** tables.
- Most specific prefix (longest prefix match).
- Metrics and route attributes when multiple routes tie on specificity.
- Source address and output interface from the route lookup result.

**ip rule** defines table lookup order. **ip route** displays or modifies routes within a selected table. Inspecting **ip route** alone while ignoring **ip rule** can fail to explain the actual traffic path.

Status inspection commands:

~~~bash
ip -br link
ip -br addr
ip rule show
ip route show table main
ip route show table local
~~~

**ip -br link** shows brief interface states; **ip -br addr** shows IP addresses; **ip rule show** lists policy rules; **ip route** inspects routing tables.

### 3.2. Longest Prefix Match and Metrics

When multiple routes match, Linux prefers the route with the more specific prefix. For example, a route to **10.20.1.0/24** is chosen over the default route **0.0.0.0/0** when the destination falls inside that subnet.

Metrics break ties between routes of equal specificity within the same lookup context. Lower metrics are typically preferred. However, metrics do not replace source-based policy routing and cannot resolve all multi-homing cases on their own.

### 3.3. Default Routes

A default route is used when no more specific route matches. On a single-NIC machine, there is usually one default gateway. On a multi-NIC machine, multiple default routes can make traffic paths unpredictable, especially when requests enter one NIC and responses exit another.

If two NICs connect to two gateways, simply setting two default routes with different metrics can force all locally initiated outbound traffic onto one NIC, whereas responses to connections arriving on the other NIC must leave via that same NIC. Policy routing is usually clearer when paths must be chosen by source address or policy.

## 4. Source Addresses and Asymmetric Routing

### 4.1. How Source Addresses Are Chosen

When an application opens a connection without binding a source address, the kernel typically chooses the source IP based on the selected route and output interface. If the machine has multiple NICs, the chosen source IP may differ from what the operator expected.

An application can bind to a specific IP address. However, binding a source IP only sets the socket's source address; route lookup must still provide a valid path for that address.

Check the route to a destination:

~~~bash
ip route get 203.0.113.80
~~~

Check the route with a specific source IP:

~~~bash
ip route get 203.0.113.80 from 10.20.1.10
~~~

**203.0.113.80** belongs to documentation example address space, not a real service address. Substitute an actual environment destination when testing.

### 4.2. What Is Asymmetric Routing?

**Asymmetric routing** occurs when outbound and return packets follow different paths. For example:

1. A client sends a request to **10.20.1.10** arriving on **ens6**.
2. The server receives the packet on **ens6**.
3. The application generates a response.
4. The kernel selects the default route out **ens5**.
5. The response exits via **ens5**, while the client or firewall expects it back via **ens6**.

Some networks tolerate asymmetric routing; stateful firewalls, NATs, or source-validation policies may drop the response. Always verify both outbound and return paths rather than confirming only that packets arrived at the host.

### 4.3. Source-Based Policy Routing

Linux can use **ip rule** to select a routing table based on source IP, interface, firewall mark, or other attributes. A common multi-NIC approach creates a separate table per NIC and adds rules matching source addresses.

For example, a VM with two NICs:

| NIC | IP | Gateway | Role |
|---|---|---|---|
| **ens5** | **10.10.1.10/24** | **10.10.1.1** | Frontend |
| **ens6** | **10.20.1.10/24** | **10.20.1.1** | Backend |

The goal is for traffic with source IP **10.10.1.10** to use table 100 and exit via **ens5**; traffic with source IP **10.20.1.10** uses table 200 and exits via **ens6**.

~~~bash
# Frontend network routes in table 100
ip route add 10.10.1.0/24 dev ens5 src 10.10.1.10 table 100
ip route add default via 10.10.1.1 dev ens5 table 100

# Backend network routes in table 200
ip route add 10.20.1.0/24 dev ens6 src 10.20.1.10 table 200
ip route add default via 10.20.1.1 dev ens6 table 200

# Select table by source address
ip rule add priority 100 from 10.10.1.10/32 table 100
ip rule add priority 110 from 10.20.1.10/32 table 200
~~~

This is an illustrative example. Gateways must actually exist and be reachable in their respective subnets; cloud route tables must also allow the paths. If directly connected routes already reside in other tables, design rules and routes carefully to avoid loops or bypassing critical routes.

Verify the configuration:

~~~bash
ip rule show
ip route show table 100
ip route show table 200
ip route get 203.0.113.80 from 10.10.1.10
ip route get 203.0.113.80 from 10.20.1.10
~~~

Route lookup output should report the expected interface and gateway. Follow up with live connectivity tests, because route lookup shows only the kernel's decision—not whether the gateway, firewall, or target network is operational.

### 4.4. Routing Tables and Table Names

Linux includes predefined routing tables:

- **local** (ID 255): routes for local addresses and broadcasts.
- **main** (ID 254): the standard routing table.
- **default** (ID 253): default table rarely used in typical setups.
- Custom tables: referenced by numeric ID or by names declared in **/etc/iproute2/rt_tables**.

You can define readable names:

~~~text
100 frontend
200 backend
~~~

Then reference table names in **ip route** and **ip rule** commands once configured. When automating, keep table IDs and names consistent across all machines.

## 5. Configuring Multiple IP Addresses on One NIC

### 5.1. Adding Secondary Addresses

On Linux, **ip addr** can attach additional addresses to an interface:

~~~bash
ip addr add 10.10.1.11/24 dev ens5
ip -br addr show dev ens5
~~~

This example uses an illustrative private address. Before running it, ensure the IP is allocated or permitted in the cloud control plane, is unused by another host, and has a prefix matching the subnet configuration.

Removing a secondary address:

~~~bash
ip addr del 10.10.1.11/24 dev ens5
~~~

The **ip** command modifies runtime state only. Changes may be lost after reboot or when a network manager or cloud-init rewrites configuration. To persist changes, declare them in the OS's network management tool.

### 5.2. Binding Applications to Specific Addresses

An application can listen on:

- **0.0.0.0**: all local IPv4 addresses.
- **127.0.0.1**: IPv4 loopback.
- A specific address such as **10.10.1.11**: accepts connections only on that address.
- **::**: all IPv6 addresses, depending on socket and OS configuration.

Binding to a specific address restricts which logical interface a service accepts traffic on. Still, firewalls must allow the proper sources, destinations, and ports. Binding to **0.0.0.0** does not automatically make a service reachable from the Internet; reachability still depends on public IPs, routes, NAT, and security policies.

### 5.3. Source Address Selection with Multiple IPs

When a NIC holds multiple IPs, the kernel must pick a source IP for outbound connections. An application can bind its source IP explicitly; otherwise, the kernel selects based on the route and OS source-address-selection rules.

This matters for:

- Services that must respond from the exact IP the client connected to.
- Mail servers or servers connecting to partners with IP allowlists.
- Applications hosting multiple endpoints or tenants.
- Systems with multiple NAT/public IPs mapped to different private IPs.

Test both inbound and outbound connectivity after adding IPs. Attaching an IP to a NIC does not automatically grant NAT or public reachability.

### 5.4. ARP and Multiple IPs in the Same Subnet

In IPv4, ARP maps local network IP addresses to MAC addresses. When a host has multiple IPs across multiple NICs in the same subnet, or multiple NICs attached to the same broadcast domain, ARP replies can cause unpredictable behavior (such as ARP flux) unless the kernel and network are tuned accordingly.

Cloud designs typically isolate NICs onto separate subnets. If you need multiple NICs in the same subnet or multiple same-subnet addresses across interfaces, understand how the provider implements virtual networking and test ARP behavior, source address selection, and relevant kernel parameters. Do not add same-subnet NICs solely to boost bandwidth without a clear design.

## 6. Configuring Multiple NICs on Linux

### 6.1. Discovering Interfaces

Before editing configuration, inspect current NIC names, MACs, IPs, MTUs, and routes:

~~~bash
ip -br link
ip -br addr
ip -d link show
ip route
ip rule
~~~

You can use **ethtool** to view NIC properties if supported by the driver:

~~~bash
ethtool ens5
ethtool -S ens5
~~~

Not all virtual NICs expose full speed details or hardware counters via **ethtool**. Use cloud provider metrics to verify bandwidth and service limits.

### 6.2. Runtime Configuration with iproute2

Bring up an interface and assign an IP:

~~~bash
ip link set ens6 up
ip addr add 10.20.1.10/24 dev ens6
~~~

Add a route to a specific network if needed:

~~~bash
ip route add 10.30.0.0/16 via 10.20.1.1 dev ens6
~~~

If a route already exists, **add** can return **File exists**; inspect current state before making changes. Never delete routes or flush an entire routing table on a production machine without understanding the impact, as you can sever your active administrative session.

### 6.3. Persistent Configuration

**ip** commands usually alter runtime state only. To persist configuration across reboots, use the OS's standard network management tool, such as:

- Netplan on modern Ubuntu releases.
- NetworkManager on many Linux desktop/server distributions.
- systemd-networkd on systems using systemd-networkd.
- Network configs managed by cloud-init or a provider guest agent.

Do not let multiple management tools write to the same NIC simultaneously. Cloud-init may regenerate network files from metadata at boot; editing generated files directly risks being overwritten. Establish a single source of truth and store changes in IaC or image bootstrap configs.

A safe workflow:

1. Back up current **ip addr**, **ip route**, and **ip rule** outputs.
2. Identify the tool managing the NIC.
3. Add addresses, routes, and policy rules in persistent configuration.
4. Validate syntax before applying.
5. Apply via console or an administrative session with a rollback plan.
6. Re-verify after reboot or after cloud-init runs.

### 6.4. Initialization Order and DHCP

A NIC can obtain its IP, routes, and DNS via DHCP. When multiple NICs enable DHCP simultaneously, the OS may install multiple default routes or alter route precedence by metric. This can cause outbound paths to shift after a reboot or lease renewal.

You may need to configure DHCP on secondary NICs to acquire an IP without installing a default route, or configure explicit route metrics and policy routing. Syntax differs by network manager and distribution; never copy one OS's configuration directly to another without checking documentation.

## 7. Reverse Path Filtering and Firewalls

### 7.1. Reverse Path Filtering (rp_filter)

Linux implements **reverse path filtering** to sanity-check source addresses against the reverse route. This helps mitigate certain source-address spoofing attacks, though strict mode can drop legitimate packets in asymmetric routing architectures.

Three common values of **rp_filter**:

| Value | Mode | Meaning |
|---|---|---|
| **0** | Disabled | No reverse-path check performed by this mechanism |
| **1** | Strict | Best reverse route must exit via the interface that received the packet |
| **2** | Loose | Any route to the source address via any interface suffices |

Inspect current settings:

~~~bash
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.default.rp_filter
sysctl net.ipv4.conf.ens5.rp_filter
sysctl net.ipv4.conf.ens6.rp_filter
~~~

If a multi-NIC host uses policy routing or asymmetric return paths, strict mode can drop packets. Loose mode may fit some designs, though it weakens source validation. Do not disable **rp_filter** host-wide out of habit; evaluate actual traffic paths, security requirements, and the effective value derived from **all** and the per-interface setting. **default** provides the initial value for newly created interfaces.

### 7.2. Guest OS Firewalls

Firewalls such as **nftables**, **iptables**, **firewalld**, or **ufw** can enforce policies by interface, source IP, destination IP, protocol, and port.

Example policy:

- Allow HTTPS to the frontend NIC from the load balancer.
- Allow database connections only over the backend NIC.
- Allow SSH/RDP only over the management network.
- Block forwarding between NICs unless the machine acts as a router.
- Rate-limit logging for dropped packets to aid investigation.

Do not treat a dedicated NIC as the sole security boundary. Combine cloud security groups/firewalls, subnet ACLs, guest OS firewalls, and application-layer authentication.

### 7.3. IP Forwarding

If a server only runs applications, it typically does not need to forward packets between NICs. If a machine acts as a router, NAT gateway, firewall, or network appliance, enable forwarding and configure routes, firewalls, NAT, and corresponding cloud policies.

On Linux, check:

~~~bash
sysctl net.ipv4.ip_forward
sysctl net.ipv6.conf.all.forwarding
~~~

Enabling IP forwarding does not automatically build a secure router. Define trusted interfaces, permitted routes, forwarding policies, source/destination validation, and bidirectional traffic controls.

Some cloud platforms enforce source/destination checks on NICs or VMs. When using a VM as a router, enable or adjust the corresponding setting per provider documentation. Otherwise, packets forwarded by Linux may still be dropped by the cloud fabric.

## 8. Multi-NIC in Containers and Kubernetes

### 8.1. Network Namespaces

Linux containers typically run in separate network namespaces. Consequently, routing tables and interface lists inside a container can differ from those on the host.

Inspect from inside a container:

~~~bash
ip -br addr
ip route
ip rule
~~~

Having two NICs on the host does not mean containers automatically see both. The CNI determines which interfaces and routes are injected into a Pod or container's network namespace.

### 8.2. Multiple Networks for One Pod

In Kubernetes, the default CNI typically provides one primary network interface per Pod. If a workload needs multiple networks, solutions like Multus CNI can combine secondary CNIs to attach extra interfaces to Pods.

Conceptual example:

- Primary interface handles cluster and `Service` communication.
- Secondary interface connects to a data network or specialized device.
- The Pod carries specific routes to send certain traffic over the secondary interface.

Verify plugins, `NetworkAttachmentDefinition`, IPAM addressing, routes, and permissions for your CNI version. Multi-NIC on a node does not automatically create multi-NICs for every Pod.

### 8.3. Routing Inside a Pod

A Pod's routing table belongs to the Pod's network namespace. If a Pod has multiple interfaces, inspect routes directly inside the Pod and ensure the application picks the right interface/source IP.

Do not alter host routes to fix a Pod-only issue without verifying the namespace boundary. Similarly, policy routing inside a Pod may require CNI support or privileges; never grant **NET_ADMIN** to containers casually.

## 9. Designing and Testing a Dual-NIC Server

### 9.1. Design Goals

Suppose a Linux VM needs two NICs:

- Frontend NIC receives HTTPS from a load balancer in the frontend subnet.
- Backend NIC connects to a database in the backend subnet.
- Responses to frontend connections must return via the frontend.
- Database connections must traverse the backend.
- Arbitrary forwarding between the two subnets is disallowed.

~~~mermaid
flowchart TB
    CLIENT["Client / Load balancer"]
    DB["Database"]
    subgraph VM["Linux VM"]
      APP["Application"]
      F["ens5<br/>10.10.1.10"]
      B["ens6<br/>10.20.1.10"]
      APP --> F
      APP --> B
    end
    CLIENT -->|"HTTPS"| F
    B -->|"Database connection"| DB
~~~

### 9.2. Configuration Steps

**Step 1: Configure the cloud control plane**

- Create or choose two subnets matching each purpose.
- Attach two NICs to the VM within instance-type limits.
- Assign primary and secondary IPs in the control plane if needed.
- Configure route tables for each subnet.
- Configure security groups/firewalls to allow only required flows.
- Confirm both NICs reside within the platform-supported zone/region scope.

**Step 2: Verify the guest OS**

~~~bash
ip -br link
ip -br addr
ip route
ip rule
~~~

Cross-check NIC names, MACs, and IPs against cloud metadata or configuration. Never guess interface ordering.

**Step 3: Configure routes and policy rules**

If both NICs have separate gateways and responses must exit the matching NIC by source IP, create separate routing tables and policy rules as shown in Section 4.3. If the backend only needs to reach a single internal subnet, a specific route to that backend subnet may suffice without adding a second default route.

**Step 4: Configure firewalls**

Allow HTTPS via the frontend NIC and the database port via the backend NIC. Block forwarding if the VM is not acting as a router. Verify both cloud firewalls and guest OS firewalls.

**Step 5: Verify the application**

Confirm the application binds to the right addresses, the database client uses the backend route, and listeners do not open on unintended interfaces.

### 9.3. Testing Traffic Paths

Useful commands:

~~~bash
# Inspect addresses and routes
ip -br addr
ip rule show
ip route show table main

# Inspect route by source IP
ip route get 203.0.113.80 from 10.10.1.10
ip route get 203.0.113.80 from 10.20.1.10

# Inspect listening sockets
ss -lntup

# Observe packets on each NIC
tcpdump -ni ens5
tcpdump -ni ens6
~~~

Route lookup output should report the expected interface and gateway. Follow up with live connectivity tests, because route lookup shows only the kernel's decision—not whether the gateway, firewall, or target network is operational.

**tcpdump** requires elevated privileges and can capture sensitive traffic. Capture only necessary interfaces, hosts, and ports; bound capture duration and protect capture files per operational policy.

## 10. Common Mistakes

**Assuming adding a NIC automatically adds bandwidth.** Bandwidth depends on VM type, NIC/vNIC limits, CPU, and cloud infrastructure. Multiple NICs may share the instance's aggregate cap.

**Setting multiple default routes without policy rules.** The kernel may send outbound traffic out a different interface than the inbound connection arrived on, causing asymmetric routing. Check source IPs and route lookups.

**Configuring routes only in the guest OS.** Cloud route tables, security groups, NAT, and source/destination checks can still drop packets.

**Assigning IPs inside Linux without registering them in the cloud.** The platform may reject unallocated source IPs. Always keep control plane and guest OS synchronized.

**Using metrics to replace all policy rules.** Metrics prioritize among equivalent routes; they do not distinguish flows by source IP or tenant.

**Ignoring rp_filter.** Strict reverse path filtering can drop packets in certain multi-homing architectures. Verify the active setting and evaluate security impact before adjusting.

**Placing multiple NICs in the same subnet without understanding ARP.** This can trigger ARP flux or unpredictable routing. Deploy only when explicitly supported by both the platform and OS.

**Assuming a management NIC is inherently secure.** If firewalls or routes permit access from untrusted networks, a separate NIC alone provides incomplete protection.

**Editing routes over an SSH session that depends on those routes.** A misstep can sever administrative access. Keep out-of-band console access, rollback mechanisms, or a controlled change window ready.

**Testing only the request direction.** Stateful firewalls, NAT, or source validation can drop return packets. Always test both directions and verify actual paths.

- [ ] Defined the role of each NIC and each IP address.
- [ ] Checked limits on NIC count, subnets, zones, and VM type.
- [ ] Registered primary/secondary IPs in the cloud control plane before guest OS configuration.
- [ ] Verified MACs, interface names, MTUs, and actual addresses.
- [ ] Checked both cloud route tables and OS routing tables.
- [ ] Defined default routes, metrics, and required policy routing.
- [ ] Verified the source IP selected for each flow.
- [ ] Verified return paths and asymmetric routing risks.
- [ ] Checked **rp_filter** and its impact on multi-homing design.
- [ ] Configured firewalls by NIC, source, destination, and port.
- [ ] Enabled IP forwarding only when the machine genuinely acts as a router.
- [ ] Synchronized persistent configs with NetworkManager, Netplan, systemd-networkd, or cloud-init.
- [ ] Inspected routes and interfaces inside container/Pod network namespaces.
- [ ] Tested packets on each NIC in both directions.
- [ ] Prepared console access or rollback procedures before modifying production routes.

## 12. Key Takeaways

- **NIC** is the network interface; **IP** is the logical address; **subnet** defines the IP range and network policy boundary.
- One NIC can hold multiple IPs and one VM can hold multiple NICs, but IP/NIC counts do not automatically increase bandwidth or availability.
- Routing occurs in both the cloud network and the guest OS; both layers must align.
- Linux uses **ip route** to manage routes and **ip rule** to select tables by policy.
- Multi-NIC setups with multiple gateways require careful handling of source IPs, default routes, and asymmetric routing.
- Source-based policy routing keeps responses exiting through the matching NIC for each source address.
- Strict **rp_filter** can affect asymmetric paths; any adjustment must weigh security trade-offs.
- Runtime changes via **ip** can be lost on reboot; persist configuration in standard network management tools.
- Containers and Pods have their own network namespaces; verify interfaces and routes inside the proper namespace.
- Always test outbound paths, return paths, firewalls, and cloud route tables before moving configurations to production.

| NIC | Network Interface Card/Controller, a server or VM network interface. |

| Default route | Route used when no more specific route matches. |
