# Observing with Cloud Logging, Cloud Monitoring, and Cloud Trace

A serverless application can spin up many instances in a short period, process concurrent requests, and call across multiple cloud services. When a request is slow or fails, reading logs from a single container is rarely enough to tell where the failure started. Engineering teams need to combine three observability signals: **logs** tell you what happened, **metrics** tell you how the system behaves over time, and **traces** show which components a request traversed and how long each step took.

On Google Cloud, Cloud Logging collects platform and application logs; Cloud Monitoring aggregates metrics, dashboards, alerts, and SLOs; Cloud Trace stores distributed traces across services. For Java running on Cloud Run or other serverless environments, you need standardized structured logging, trace context propagation across HTTP/message boundaries, metrics with bounded label cardinality, and alerts tied to service objectives.

This lesson explains how to combine these three services to observe serverless Java applications, from structured log formatting and OpenTelemetry instrumentation to dashboards, alerts, investigative queries, and cost control.

## Learning objectives

After this lesson, you will be able to:

- Distinguish logs, metrics, and traces, and the questions each signal answers.
- Read request logs generated by Cloud Run and container logs written by the application.
- Emit structured JSON logs so Cloud Logging parses fields automatically.
- Correlate logs with traces using trace ID and span ID.
- Use OpenTelemetry to create traces and propagate context over HTTP or messages.
- Create application metrics with Micrometer or OpenTelemetry.
- Design dashboards, alert policies, and SLIs/SLOs in Cloud Monitoring.
- Write Cloud Logging queries to investigate errors by service, revision, request, and trace.
- Limit sensitive data, label cardinality, and observability costs.

## 1. The three observability signals

The three signals are typically used together, each providing a distinct perspective.

| Signal | Question answered | Example |
|---|---|---|
| **Logs** | What happened at a specific point in time? | Request rejected for missing permissions; database timed out |
| **Metrics** | How often does an event occur, and what is the trend? | 5xx rate rose from 0.2% to 4%; p95 latency exceeded 1 second |
| **Traces** | Which steps did a request pass through, and where was time spent? | API took 800 ms, of which 650 ms was spent waiting on the database |

Visualizing how they fit together:

~~~mermaid
flowchart LR
    A["Java service / Cloud Run"] --> B["Logs"]
    A --> C["Metrics"]
    A --> D["Traces"]
    B --> E["Cloud Logging"]
    C --> F["Cloud Monitoring"]
    D --> G["Cloud Trace"]
    E --> H["Investigate a request"]
    F --> H
    G --> H
~~~

For example, a dashboard shows p95 latency rising. Metrics confirm whether the issue affects the whole service or just one revision. Traces identify the slow span, such as a database query. Logs carrying the trace ID reveal which specific request failed along with relevant business context.

No single signal can replace the other two. Detailed logs are ill-suited for computing high-volume load trends; aggregated metrics lack per-request context; traces are not an archival store for every business event.

## 2. What types of logs does Cloud Run generate?

When deploying a service to Cloud Run, Cloud Logging can receive logs from both the platform and the container.

### Request logs

Cloud Run generates request logs for incoming service requests. These logs typically contain details such as:

- HTTP method, URL, and status code.
- Request latency.
- Response size.
- User agent and network details as configured.
- Service, revision, location, and related resource labels.

Request logs help answer which endpoints are failing or slow, even when the application crashes before writing its own log entry.

### Container logs

The application writes to stdout or stderr; Cloud Run collects these as container logs. In Java, loggers are usually configured to write to the console. If a log line is valid single-line JSON, Cloud Logging parses its fields into `jsonPayload`.

Emit structured logs instead of free-form string concatenation:

~~~json
{
  "severity": "INFO",
  "message": "Order accepted",
  "event": "order.accepted",
  "orderId": "ORD-1042",
  "tenant": "tenant-42",
  "revision": "orders-api-00012-abc",
  "durationMs": 34
}
~~~

Business fields can be filtered and grouped easily. Avoid logging full request bodies, tokens, passwords, secrets, payment details, or unnecessary personal data.

### Structured logging and special fields

Cloud Logging recognizes several special fields inside JSON payloads. Commonly used fields:

| JSON field | Meaning |
|---|---|
| `severity` | Log level such as DEBUG, INFO, WARNING, ERROR |
| `message` | Human-readable log message |
| `logging.googleapis.com/trace` | Trace path linking the log entry to Cloud Trace |
| `logging.googleapis.com/spanId` | Span ID associated with the log entry |
| `logging.googleapis.com/trace_sampled` | Indicates whether the trace is sampled |
| `httpRequest` | HTTP metadata if the application logs structured request details itself |

When the trace field is recognized, Cloud Logging displays a link to open the corresponding trace in Cloud Trace. The trace path has the form:

~~~text
projects/PROJECT_ID/traces/TRACE_ID
~~~

If logs contain only an unstructured message string, filtering by `orderId`, event type, or trace ID becomes much harder. Standardize a log schema across services and keep field names consistent.

## 3. Structured logging in Java applications

In Java, you can use SLF4J with a Logback backend and a JSON encoder to write single-line JSON to stdout. An encoder such as Logstash Logback Encoder serializes the message, level, and MDC fields into JSON.

Minimal Logback configuration example:

~~~xml
<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder class="net.logstash.logback.encoder.LogstashEncoder"/>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
~~~

The application can emit logs as follows:

~~~java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class OrderService {
    private static final Logger log =
            LoggerFactory.getLogger(OrderService.class);

    public void accept(String orderId) {
        log.atInfo()
                .addKeyValue("event", "order.accepted")
                .addKeyValue("orderId", orderId)
                .log("Order accepted");
    }
}
~~~

For key-value pairs to be emitted as JSON fields, use an SLF4J version and encoder that support structured arguments/key-value pairs, and verify the actual output. If the backend only prints plain text messages, Cloud Logging cannot infer those fields automatically.

### Attaching trace context to logs

When using OpenTelemetry, you can read the current trace context and put the trace ID and span ID into MDC. The Logback JSON encoder outputs MDC entries as JSON fields; Cloud Logging recognizes the special field names listed above.

Illustrative example:

~~~java
import io.opentelemetry.api.trace.Span;
import io.opentelemetry.api.trace.SpanContext;
import org.slf4j.MDC;

import java.util.Map;

public final class TraceLogContext {
    private TraceLogContext() {
    }

    public static void runWithTraceFields(
            String projectId, Runnable action) {

        Map<String, String> previous = MDC.getCopyOfContextMap();
        try {
            SpanContext span = Span.current().getSpanContext();

            if (span.isValid()) {
                MDC.put(
                        "logging.googleapis.com/trace",
                        "projects/" + projectId + "/traces/"
                                + span.getTraceId());
                MDC.put(
                        "logging.googleapis.com/spanId",
                        span.getSpanId());
            }

            action.run();
        } finally {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    }
}
~~~

Wrap logging-sensitive execution blocks with this helper or integrate equivalent logic into a servlet filter/interceptor. You must restore MDC in `finally` because request-handling threads can be reused for subsequent requests. If the application runs asynchronous tasks or switches executors, MDC does not propagate automatically to new threads; use proper context propagation.

If you also want to emit `logging.googleapis.com/trace_sampled`, configure the encoder to output it as a JSON boolean; standard MDC stores values as strings.

The project ID must come from controlled environment configuration. Never log access tokens or full span attributes.

## 4. Querying Cloud Logging

Cloud Logging Logs Explorer supports querying by resource type, labels, severity, and payload fields.

### Finding errors for a Cloud Run service

~~~text
resource.type="cloud_run_revision"
resource.labels.service_name="orders-api"
severity>=ERROR
~~~

This query scopes logs to a service and severity ERROR or higher.

### Finding HTTP 5xx requests

~~~text
resource.type="cloud_run_revision"
resource.labels.service_name="orders-api"
httpRequest.status>=500
~~~

Request logs contain HTTP fields for locating status codes, latency, and affected endpoints.

### Finding an order in structured logs

~~~text
resource.type="cloud_run_revision"
resource.labels.service_name="orders-api"
jsonPayload.orderId="ORD-1042"
~~~

### Finding logs for a trace

~~~text
trace="projects/PROJECT_ID/traces/TRACE_ID"
~~~

Replace `PROJECT_ID` and `TRACE_ID` with actual values. If the application does not emit trace fields or context is not propagated to logs, this query will not match container logs even though request logs still exist.

### Filtering by revision

~~~text
resource.type="cloud_run_revision"
resource.labels.service_name="orders-api"
resource.labels.revision_name="orders-api-00012-abc"
severity>=WARNING
~~~

Revision labels are helpful during canary rollouts or rollbacks: compare errors on the new revision against the stable revision.

### Investigation tips

- Start with the affected service and time window.
- Filter for 5xx requests or severity ERROR.
- Open a log entry and grab its trace ID/correlation ID.
- Open the trace to inspect spans and dependencies.
- Return to logs filtered by trace ID to read specific errors.
- Compare revisions and deployment timestamps to spot correlations.

Avoid querying high-cardinality IDs across the entire log retention window without scoping resource and time range first. Narrow filters speed up investigations and reduce scanned data volume.

## 5. Cloud Monitoring: metrics, dashboards, and alerts

Cloud Monitoring ingests metrics from Google Cloud services and application instrumentation. Metrics are stored as time series with a metric type, resource type, labels, and timestamped data points.

A time series is typically identified by a metric together with its monitored resource and label set. Labels let you slice by service, revision, region, or outcome, yet every unique label combination creates a distinct time series. Therefore, never put `orderId`, `userId`, `email`, or `requestId` into metric labels.

### Key Cloud Run metrics

Cloud Run emits platform metrics for tracking requests and containers. Exact metric names can vary by service type and documentation version; check Metrics Explorer or the metric catalog in your project before creating policies.

| Group | What it tracks | How to use |
|---|---|---|
| Request count | Requests by service/revision/status | Detect traffic spikes or abnormal drops |
| Request latency | Request latency distribution | Track p50/p95/p99 and SLOs |
| Instance count | Running instance count | Observe autoscaling and capacity limits |
| CPU utilization | CPU consumption | Identify CPU-saturated instances |
| Memory utilization | Memory consumption | Detect memory pressure or OOM risk |
| Startup latency | Instance startup duration | Evaluate cold starts and optimization gains |
| Container/request errors | Container and serving failures | Spot unstable revisions or dependencies |

Analyze metrics by service, region, and revision. If one revision shows noticeably higher latency after deployment, you can isolate the regression without averages from other revisions masking it.

### Application business metrics

Platform metrics tell you how the service is running; business metrics tell you whether the application is accomplishing its business work.

Examples:

- Number of accepted or rejected orders.
- Payment success rate.
- Order processing duration.
- Number of retried or dead-lettered messages.
- Number of failed dependency calls.

You can use Micrometer in Spring Boot:

~~~java
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;

public final class OrderMetrics {
    private final Counter accepted;
    private final Counter rejected;
    private final Timer processingTime;

    public OrderMetrics(MeterRegistry registry) {
        this.accepted = Counter.builder("orders.accepted")
                .description("Accepted order requests")
                .register(registry);

        this.rejected = Counter.builder("orders.rejected")
                .description("Rejected order requests")
                .register(registry);

        this.processingTime = Timer.builder("orders.processing")
                .description("Order processing duration")
                .register(registry);
    }

    public void markAccepted() {
        accepted.increment();
    }

    public void markRejected() {
        rejected.increment();
    }

    public void recordProcessing(Runnable operation) {
        processingTime.record(operation);
    }
}
~~~

This snippet illustrates instrumentation; you must configure an appropriate registry/exporter so metrics reach the observability backend, such as Google Cloud Monitoring via a supported exporter or an OpenTelemetry Collector. Simply adding `MeterRegistry` in the application does not automatically send metrics to Cloud Monitoring.

### Cardinality and metric labels

Metrics should use labels with small, bounded value sets:

| Good label | Why |
|---|---|
| `operation=read_order/write_order` | Finite set of operations |
| `outcome=success/failure` | Bounded number of states |
| `dependency=database/payment` | Small dependency catalog |
| `revision=stable/canary` or platform-provided revision label | Supports release comparisons |

Never use `orderId`, `email`, `userId`, `requestId`, or raw URLs containing path parameters as metric labels. Creating a new time series for every `orderId` drives up cardinality and cost rapidly. Those values belong in logs or controlled trace attributes.

## 6. Dashboards for serverless services

A useful dashboard should help on-call engineers quickly answer four questions: is the service healthy, are users impacted, do instances have enough capacity, and which dependency is causing slowdowns?

Suggested layout:

| Dashboard section | Widgets | Purpose |
|---|---|---|
| Traffic | Request count over time | Spot bursts, traffic drops, or missing requests |
| Reliability | 4xx, 5xx, and error rates | Track errors per revision |
| Latency | p50/p95/p99 request latency | Detect user experience degradation |
| Capacity | Instance count, concurrency, CPU, memory | See whether the service is hitting limits |
| Startup | Startup latency and new instance count | Monitor cold starts |
| Dependencies | Database/API latency and error rates | Separate application errors from dependency failures |
| Business | Orders accepted, payment success, queue age | Confirm business workflows are completing |
| Release | Stable vs. canary revision comparison | Detect regressions after deployment |

Add filters for project, region, service, and revision so the dashboard is reusable across staging and production. With many services, build an overview dashboard plus detail dashboards for each critical workload.

## 7. Alerting and SLOs

Good alerts are tied to real impact. Alerting solely on CPU spikes creates false positives if requests remain fast and error-free. Conversely, rising error rates or p95 latency breaching targets directly affects users.

### Common alerts to configure

- HTTP 5xx rate exceeding threshold over a time window.
- p95 or p99 latency continuously breaching target.
- Instance count hitting max instances while request latency or error rate rises.
- Sustained high CPU or memory utilization.
- Startup probe failures or rising container restarts.
- Increasing queue age or message retry counts for event-driven services.
- Business metrics such as payment success dropping abnormally.
- Missing metric data when the service is expected to receive traffic.

Alerts need appropriate duration windows, thresholds, alignment/reducers, and notification channels. Avoid paging on brief spikes with no user impact. For critical alerts, include the service/revision, relevant query or dashboard link, and the first triage step.

### SLIs and SLOs

**SLI (Service Level Indicator)** is a measurement of service quality, such as the proportion of successful requests or the proportion of requests completing under a latency threshold.

**SLO (Service Level Objective)** is an internal target for an SLI over a time window, such as 99.9% of valid requests succeeding over 30 days. This is an illustrative target, not a default Cloud Run guarantee.

Examples:

- Availability SLI = good requests / total eligible requests.
- Latency SLI = requests under latency threshold / total eligible requests.
- Error budget = remaining error allowance within the SLO window.

You can use Cloud Monitoring Service Monitoring to define services, SLIs, and SLOs, and track error budgets. When the error budget burns down too quickly, teams can slow feature releases and prioritize reliability work.

Define clearly which requests count in the denominator. Do not exclude server errors from an SLI just to make numbers look better; exclude only predefined categories with valid business justification.

## 8. Cloud Trace and distributed tracing

A request typically traverses an API Gateway/load balancer, Cloud Run services, databases, caches, and other services. Distributed tracing represents that journey using parent-child **spans**.

- **Trace:** the end-to-end journey of a request or distributed unit of work.
- **Span:** an operation with start/end timestamps, a name, and attributes.
- **Parent/child:** relationship between a calling span and a called span.
- **Trace context:** metadata enabling downstream services to continue the same trace.

Example request:

~~~mermaid
flowchart TD
    A["HTTP server span"] --> B["Validate order span"]
    B --> C["Database query span"]
    B --> D["Payment API client span"]
    D --> E["Payment service span"]
    A --> F["HTTP response"]
~~~

Traces help pinpoint whether time is spent in Java code, database queries, or external API calls. They also reveal which service errored and whether a request was retried across multiple hops.

### Instrumentation with OpenTelemetry

OpenTelemetry provides standard APIs and SDKs for traces, metrics, and context propagation. Java can use the Java agent to auto-instrument supported HTTP frameworks, clients, and libraries, while adding manual spans for critical business steps.

Launching an application with the Java agent looks like:

~~~bash
java -javaagent:/otel/opentelemetry-javaagent.jar -jar app.jar
~~~

The agent must be packaged into the container image and configured with an appropriate exporter, resource attributes, endpoint, and sampling. You can export telemetry to Google Cloud using a compatible exporter or an OpenTelemetry Collector configured to forward to Cloud Trace/Cloud Monitoring. Pick a single clear pipeline and avoid double-instrumenting the same library.

### Creating manual spans in Java

~~~java
import io.opentelemetry.api.GlobalOpenTelemetry;
import io.opentelemetry.api.trace.Span;
import io.opentelemetry.api.trace.StatusCode;
import io.opentelemetry.api.trace.Tracer;
import io.opentelemetry.context.Scope;

public final class OrderValidator {
    private static final Tracer TRACER =
            GlobalOpenTelemetry.getTracer("orders-api");

    public void validate(String orderType) {
        Span span = TRACER.spanBuilder("order.validate").startSpan();

        try (Scope scope = span.makeCurrent()) {
            span.setAttribute("order.type", orderType);
            // Perform business validation.
            validateRules(orderType);
        } catch (RuntimeException error) {
            span.recordException(error);
            span.setStatus(StatusCode.ERROR, "Order validation failed");
            throw error;
        } finally {
            span.end();
        }
    }

    private void validateRules(String orderType) {
        if (orderType == null || orderType.isBlank()) {
            throw new IllegalArgumentException("orderType is required");
        }
    }
}
~~~

This snippet uses the OpenTelemetry API; the application must configure an SDK or agent so an active tracer provider and exporter exist. Calling the API without configuring an SDK/exporter means spans may never reach Cloud Trace.

Add only attributes useful for investigation. Never put passwords, tokens, personal data, or large payloads on spans. For high-cardinality IDs like `orderId`, weigh security, retention, and cost requirements before attaching them.

## 9. Propagating trace context over HTTP and messages

Traces link services together only when context is propagated across call boundaries.

### HTTP

W3C Trace Context uses the `traceparent` header and optional `tracestate`. Some Google Cloud components also use the compatible `X-Cloud-Trace-Context` header. OpenTelemetry instrumentation for HTTP servers/clients can extract and inject context automatically when libraries are supported and properly configured.

When service A calls service B:

1. A has an active span for the current request.
2. HTTP instrumentation injects trace context into the outbound request.
3. B extracts the context from incoming request headers.
4. B creates a server span as a child of the current trace.
5. Logs in B record the same trace ID, enabling cross-service investigation.

Do not generate a brand-new trace ID in every service if your goal is one distributed trace. If a gateway or proxy strips headers, the trace breaks into disconnected traces.

### Queues and events

With Pub/Sub or queues, a message may be processed later or by a different instance. HTTP instrumentation does not automatically carry context through message brokers in all cases.

When publishing an event, you can place trace context into message attributes using an agreed convention, for example:

~~~text
traceparent: 00-<trace-id>-<span-id>-01
eventId: evt-8f31
correlationId: corr-71a9
~~~

The consumer reads the attributes, extracts context, and starts a consumer span. If events are processed in batches, a single batch may hold multiple trace contexts; create per-message spans or use span links according to the processing model rather than forcing every message under a single parent trace.

Keep `eventId` and `correlationId` separate from trace IDs. Traces may be sampled or expire from retention; `eventId` remains the business identifier for deduplication and replay.

## 10. Sampling and bounding trace data

You do not necessarily need to store every trace. Sampling decides which traces are recorded and exported, based on SDK/agent or backend configuration.

- Low sampling reduces cost and data volume.
- High sampling increases visibility, at higher ingestion/storage cost.
- Probabilistic sampling can miss rare failing requests.
- Tail-based sampling can retain error or high-latency traces if your collector architecture supports it.

If a trace does not appear in Cloud Trace, that does not prove the request never ran. The trace may not have been sampled, context may not have propagated, or the exporter may have failed. Cross-check with request logs and metrics.

Avoid recording full payloads or sensitive data in spans. Add only analytical attributes: operation, dependency, result category, revision, or event type. Personally identifiable information must be stripped or protected per policy.

## 11. Combining logs, metrics, and traces during investigations

An investigation workflow can progress from high-level symptoms down to an exact request:

1. **Check metrics:** pinpoint when latency or error rates started climbing.
2. **Isolate the revision:** determine whether the issue occurs on a new revision or all revisions.
3. **Find request logs:** filter for 5xx requests or high latency in Cloud Logging.
4. **Open the trace:** follow the trace ID to locate the slow or failing span.
5. **Read container logs:** filter by the same trace ID or correlation ID to inspect exceptions and context.
6. **Check dependencies:** compare database/API latency and errors during the same time window.
7. **Verify business state:** check whether the event/order committed, retried, or landed in a DLQ.

Example: p95 latency rises after deploying a new revision. The dashboard shows high request latency and low CPU on the new revision. Traces show the database span accounts for most of the duration. Container logs sharing the same trace ID report connection acquisition timeouts. Further inspection uncovers an undersized connection pool or an exhausted database connection limit.

Looking only at CPU might lead the team to over-provision CPU needlessly. Looking only at logs makes it hard to tell what percentage of requests are affected. Combining all three signals narrows scope and root cause much faster.

## 12. Practical alerts for serverless Java

An initial alert set might include:

| Alert | Suggested condition | First action |
|---|---|---|
| High error rate | 5xx rate breaches SLO for several minutes | Compare revisions, inspect error traces and exception logs |
| High latency | p95 continuously breaches threshold | Locate slow spans and check dependency latency |
| Instance limit reached | Instance count near max while latency rises | Inspect concurrency, quotas, and backend capacity |
| Memory pressure | Sustained high memory or rising restarts | Inspect heap, threads, leaks, and payload sizes |
| Startup failure | Startup probes fail or startup latency spikes | Inspect image, startup logs, and dependency initialization |
| Message backlog | Queue age/depth rises | Check consumer errors, retries, concurrency, and DLQs |
| Business failure | Payment success or order completion drops | Check business errors and payment dependencies |

Specific thresholds must be grounded in your service's baseline and SLOs. Never copy one generic number across all services because traffic, SLAs, and cost profiles differ.

Every alert should have an owner, severity, notification channel, dashboard, and runbook. If an alert requires no action, turn it into a dashboard panel or lower-severity notification to prevent alert fatigue.

## 13. Access permissions for observability

Cloud Run automatically collects stdout/stderr and request logs into Cloud Logging via platform integration. If the application writes logs directly via the Logging API, the runtime service account needs log-writing permissions, typically `roles/logging.logWriter`.

Similarly:

- Exporting custom metrics directly to Cloud Monitoring requires metric-writing permissions, typically `roles/monitoring.metricWriter`.
- Sending traces directly via the Cloud Trace API requires trace-writing permissions, typically `roles/cloudtrace.agent`.
- If telemetry flows through an OpenTelemetry Collector or intermediary pipeline, permissions are granted to whichever identity actually sends the data.

Grant only the required permissions to the runtime service account or collector identity. Do not grant Editor/Owner just to make telemetry appear. Check IAM policies, the service account attached to the revision, and exporter configuration when telemetry is missing.

## 14. Controlling cost and retention

Observability is valuable, yet it also incurs ingestion, storage, query, and export costs.

### Cloud Logging

- Write structured logs and keep only fields needed for investigation.
- Avoid overly verbose step-by-step logging on every production request.
- Use log exclusions for noisy data while preserving sufficient operational signals.
- Choose log buckets, retention, and regions aligned with storage requirements.
- Use sinks to export logs to BigQuery or another system when long-term analytics are needed.

### Cloud Monitoring

- Keep metric label cardinality low.
- Never create per-user, per-order, or per-request time series.
- Use aggregate dashboards instead of creating separate metrics for every business entity.
- Audit and remove unused custom metrics.

### Cloud Trace

- Select sampling aligned with traffic volume and investigation needs.
- Create spans only at meaningful boundaries; avoid tiny spans for every line of code.
- Never attach large payloads or sensitive data.
- Keep attributes stable and useful.

Do not slash sampling or drop logs blindly just to cut costs during an incident. Determine which data is genuinely needed, how long it must be retained, and who uses it before changing retention or exclusions.

## 15. Observability checklist for serverless Java

- [ ] Cloud Run request logs and container logs appear in the right project.
- [ ] Application emits structured JSON with severity, message, and useful business fields.
- [ ] Logs contain no tokens, secrets, passwords, or unnecessary sensitive data.
- [ ] Logs include trace ID/span ID whenever an active trace context exists.
- [ ] HTTP instrumentation propagates trace context across services.
- [ ] Message attributes preserve trace context, `eventId`, and `correlationId` across queues/events.
- [ ] OpenTelemetry SDK/agent is configured with appropriate exporter and sampling.
- [ ] Custom metrics have stable names, units, descriptions, and labels.
- [ ] Metric labels never contain `userId`, `orderId`, `email`, or `requestId`.
- [ ] Dashboards cover traffic, error rates, latency, instances, CPU/memory, and dependencies.
- [ ] Alert policies tie to SLOs or user impact and link to runbooks.
- [ ] Logs can be queried by service, revision, severity, and trace.
- [ ] Runtime identity holds only the permissions needed to emit telemetry.
- [ ] Log retention, exclusions, metric cardinality, and trace sampling have been reviewed for cost.
- [ ] Team has rehearsed investigating a failing request from metrics to logs and traces.
