# Consumer Inbox and Recording Processed Events

In event-driven architectures, a message can be delivered multiple times. A consumer may finish updating data and crash before acknowledging; a broker may miss the ack; a function may time out after the database commits; or the producer may publish the same event repeatedly. Consequently, "every message arrives only once" is never a safe assumption.

The **consumer inbox** is a design pattern that records received or processed events inside the consumer's own database. Combining an inbox with unique constraints and transactions enables consumers to detect duplicates and avoid applying the same business mutation multiple times. In Java serverless architectures, an inbox is especially valuable for functions triggered by queues, streams, event buses, or webhooks.

An inbox does not by itself create system-wide exactly-once delivery. It provides deduplication by event identity within a defined consumer scope. To guarantee that side effects execute once in business terms, inbox writes must be properly coordinated with data transactions and external systems.

This lesson covers defining event identity, designing an inbox table, handling concurrent duplicates, writing the inbox inside the business transaction, coordinating acks and retries, handling external side effects, retention, replays, and failure testing.

## 1. Why Record Processed Events?

Messaging systems generally favor at-least-once delivery to reduce message loss. That means the same message may be redelivered if the consumer fails to acknowledge in time.

Common scenarios:

1. The consumer receives a message and updates the database.
2. The database commit succeeds.
3. The function terminates before acknowledging the message.
4. The broker redelivers the message.
5. The consumer executes the same business logic again.

Without deduplication, a balance could be debited twice, an order created twice, or a counter incremented twice.

Another scenario is when a function processes a message successfully but the response/ack is lost on the network. The consumer does not know whether the broker recorded the ack, so the message may reappear.

### Failure Window

~~~mermaid
sequenceDiagram
    participant B as Broker
    participant F as Java Function
    participant D as Database

    B->>F: Deliver event E-42
    F->>D: Update business data
    D-->>F: Commit success
    Note over F: Function terminated before ACK
    B->>F: Redeliver event E-42
    F->>D: Update business data again
    Note over D: Without inbox: side effect repeats
~~~

The consumer inbox closes this failure window by storing the event identity in the same transaction as the business data change. When the event is redelivered, the unique key indicates the consumer already processed it.

## 2. What Is an Inbox and How Does It Differ from Broker Acknowledgment?

An inbox is a durable table or store on the consumer side. It answers the question: "Has this logical consumer already recorded this event identity?"

Broker acknowledgment answers a different question: "Can the broker delete this message or advance the consumer offset past it?"

The two are related, but neither replaces the other:

- Recording the inbox entry and applying business updates is the responsibility of the application/database.
- Acknowledging, deleting messages, or committing offsets is the responsibility of consumer-broker integration.
- Acks should occur only after the transaction containing the inbox and business update has committed.
- If commit succeeds and ack fails, the message may redeliver; the inbox detects the duplicate.
- If ack happens before commit and the transaction subsequently rolls back, the message may be lost from the pipeline even though business state was never saved.

The safe sequence is typically:

1. Receive the event.
2. Validate the envelope and determine event identity.
3. Begin the database transaction.
4. Claim the event identity using a unique constraint.
5. Apply business changes.
6. Mark the inbox entry processed.
7. Commit the transaction.
8. Acknowledge the message per broker semantics.

If the database and broker do not share a distributed transaction, a commit/ack window still exists. The inbox solves that window by making redeliveries safe.

## 3. Identifying a Stable Event Identity

An inbox can deduplicate only if it can tell whether two deliveries represent the same event. Therefore, events need a stable identity.

An event envelope might look like:

~~~json
{
  "eventId": "evt-8f31a2",
  "source": "orders-service",
  "eventType": "order.paid",
  "schemaVersion": 2,
  "aggregateId": "order-918",
  "occurredAt": "2026-11-17T10:20:00Z",
  "payload": {
    "paymentReference": "pay-774"
  }
}
~~~

Key fields:

- **eventId:** unique identifier generated by the producer and preserved across retries/replays.
- **source:** system or namespace producing the event.
- **eventType:** event classification for consumer routing.
- **schemaVersion:** contract version.
- **aggregateId:** business entity identifier such as an order or account.
- **occurredAt:** business occurrence timestamp; do not use it in place of event ID.

Never use timestamps, raw JSON formatting, or newly generated random IDs per delivery as deduplication keys.

### Event ID Differs from Business ID

One order can produce multiple events: `order.created`, `order.paid`, `order.shipped`. Using only `orderId` as the inbox key would cause the consumer to treat distinct events as duplicates.

Conversely, a single business operation might be emitted by a producer under two different event IDs due to a bug or producer-level retry. An inbox keyed only by `eventId` will not recognize that those two events trigger the same business side effect. For sensitive operations, you may also need a business idempotency key or per-operation unique constraint.

### Namespacing Identity

Not all event sources guarantee globally unique event IDs. A safe key typically combines:

```text
consumer identity + source namespace + event ID
```

Consumer identity is the logical name of the handler/subscription performing deduplication. Two independent consumers may both need to process the same event once each; therefore, do not use a global table unique only on `eventId` when consumers serve different purposes.

## 4. Event IDs by Broker Type

| Source | Usable Identity | Notes |
|---|---|---|
| CloudEvents / event bus | `source + id` | Per the CloudEvents spec, this pair identifies the event |
| SQS | Message ID or application event ID | A producer retrying with a new send call may generate a new message ID; application event IDs are more stable |
| Kafka | `topic + partition + offset`, or application event ID | Offsets identify records in the log; replaying the same record keeps its offset, whereas a producer republishing creates a new offset |
| Kinesis | Stream + shard/sequence number, or application event ID | Sequence numbers bind to records; republished producer events become new records |
| Pub/Sub | Service-assigned message ID or application event ID | Republishing identical content may yield a new message ID |
| Webhook provider | Event ID in payload/header per contract | Verify that the provider preserves the ID on retries |
| Database change stream | Stream identity + record sequence/version | Define semantics across snapshots, restores, or reprocessing |

When the provider supplies a stable application event ID, prefer it. Broker-assigned IDs remain useful for distinguishing specific deliveries/records. Storing both aids traceability.

In Kafka, if a consumer group resets offsets to replay, `topic + partition + offset` still identifies the exact record. If a producer re-emits a business fact as a new record, an application event ID or business operation ID reveals that relationship.

## 5. Designing the Inbox Table

A minimal relational schema:

~~~sql
CREATE TABLE consumer_inbox (
    consumer_name  VARCHAR(128) NOT NULL,
    event_source   VARCHAR(256) NOT NULL,
    event_id       VARCHAR(256) NOT NULL,
    payload_hash   VARCHAR(128) NOT NULL,
    event_type     VARCHAR(128) NOT NULL,
    status         VARCHAR(24) NOT NULL,
    received_at    TIMESTAMP NOT NULL,
    processed_at   TIMESTAMP NULL,
    PRIMARY KEY (consumer_name, event_source, event_id)
);
~~~

Field meanings:

- `consumer_name`: logical identifier of the consumer/subscription.
- `event_source`: producer or event source namespace.
- `event_id`: stable event identity.
- `payload_hash`: detects cases where the same identity arrives with a different payload.
- `event_type`: supports investigation and routing.
- `status`: processing state per the state machine.
- `received_at`, `processed_at`: receipt and completion timestamps.

The unique constraint across consumer/source/event provides database-level duplicate prevention. Never rely on "SELECT to check then INSERT" code because two concurrent invocations can both find no record and both execute business logic.

### Should You Store the Full Payload?

Not necessarily. If the message broker or event store already retains payloads, the inbox can store only identity, hash, and metadata. If auditing or standalone replay is needed, store an encrypted payload or a reference to an immutable object.

Do not store sensitive data in the inbox unnecessarily. Apply retention, encryption, access controls, and masking aligned with business data policies.

## 6. Atomic Inbox Pattern: Claim and Business Update in the Same Transaction

For consumers making changes solely within one relational database, the simplest and strongest pattern is:

- Insert the inbox row inside the transaction.
- If insert succeeds, execute the business logic.
- Mark processed.
- Commit everything together.
- If any step fails, roll back both the inbox row and the business update.

PostgreSQL can use:

~~~sql
INSERT INTO consumer_inbox (
    consumer_name,
    event_source,
    event_id,
    payload_hash,
    event_type,
    status,
    received_at
)
VALUES (?, ?, ?, ?, ?, 'PROCESSING', CURRENT_TIMESTAMP)
ON CONFLICT (consumer_name, event_source, event_id)
DO NOTHING;
~~~

If 1 row is inserted, this transaction claimed the event. If 0 rows are inserted, another transaction or earlier execution already recorded that identity.

After updating business data successfully:

~~~sql
UPDATE consumer_inbox
SET status = 'PROCESSED',
    processed_at = CURRENT_TIMESTAMP
WHERE consumer_name = ?
  AND event_source = ?
  AND event_id = ?
  AND status = 'PROCESSING';
~~~

In this atomic pattern, the `PROCESSING` row remains uncommitted while business logic executes. Another transaction encountering the unique conflict may wait for the first transaction to commit or roll back. If the first commits, the second sees a duplicate; if the first rolls back, a redelivery can claim and process it.

Do not commit a `PROCESSING` row and run business updates in a separate transaction unless you have designed leasing and recovery. Otherwise, you need a mechanism to detect and reclaim abandoned claims.

## 7. Java JDBC: Inbox and Business Update in One Transaction

The example below uses PostgreSQL and JDBC. `applyBusinessChange` must use the exact `Connection` passed in so all changes share the same transaction.

~~~java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import javax.sql.DataSource;

public final class OrderEventConsumer {

    private static final String CONSUMER = "order-projection-v2";

    private final DataSource dataSource;

    public OrderEventConsumer(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public boolean handle(OrderPaidEvent event) throws SQLException {
        try (Connection connection = dataSource.getConnection()) {
            connection.setAutoCommit(false);

            try {
                int claimed;

                try (PreparedStatement statement =
                        connection.prepareStatement("""
                            INSERT INTO consumer_inbox (
                                consumer_name, event_source, event_id,
                                payload_hash, event_type, status, received_at
                            )
                            VALUES (?, ?, ?, ?, ?, 'PROCESSING', CURRENT_TIMESTAMP)
                            ON CONFLICT (
                                consumer_name, event_source, event_id
                            ) DO NOTHING
                            """)) {
                    statement.setString(1, CONSUMER);
                    statement.setString(2, event.source());
                    statement.setString(3, event.eventId());
                    statement.setString(4, event.payloadHash());
                    statement.setString(5, "order.paid");
                    claimed = statement.executeUpdate();
                }

                if (claimed == 0) {
                    verifyExistingEvent(
                            connection, event, CONSUMER);
                    connection.commit();
                    return false; // Duplicate: no business update.
                }

                applyBusinessChange(connection, event);

                try (PreparedStatement statement =
                        connection.prepareStatement("""
                            UPDATE consumer_inbox
                            SET status = 'PROCESSED',
                                processed_at = CURRENT_TIMESTAMP
                            WHERE consumer_name = ?
                              AND event_source = ?
                              AND event_id = ?
                              AND status = 'PROCESSING'
                            """)) {
                    statement.setString(1, CONSUMER);
                    statement.setString(2, event.source());
                    statement.setString(3, event.eventId());

                    if (statement.executeUpdate() != 1) {
                        throw new SQLException(
                                "Inbox state transition failed");
                    }
                }

                connection.commit();
                return true;
            } catch (SQLException | RuntimeException error) {
                connection.rollback();
                throw error;
            }
        }
    }

    private void applyBusinessChange(
            Connection connection,
            OrderPaidEvent event) throws SQLException {
        // Update order/projection using this same connection.
    }

    private void verifyExistingEvent(
            Connection connection,
            OrderPaidEvent event,
            String consumer) throws SQLException {
        // Read stored payload_hash. If the same identity has a
        // different hash, fail and alert instead of treating it
        // as a normal duplicate.
    }
}
~~~

This example assumes `OrderPaidEvent` and the payload hash verification method are defined in your application. In production, `verifyExistingEvent` must query the existing record and compare hashes; if the same identity carries a different payload, that is a contract violation or anomaly and must not be silently ignored.

On an insert conflict, PostgreSQL may wait for the transaction holding the unique key to finish. Therefore, keep transactions short and never call external APIs or sleep while holding a transaction.

### Why Commit First and ACK Afterward?

The listener acknowledges only after `handle` returns successfully, meaning the transaction has committed. If the function terminates after commit but before ACK, the message redelivers and `claimed == 0`; the consumer verifies the duplicate and returns success without applying business updates again.

If the transaction rolls back, the inbox claim also rolls back. Retried messages can reclaim and execute the business logic.

## 8. Spring Transactions and Message Listeners

In Spring, inbox logic and business updates can sit inside a service method managed by the transaction manager:

~~~java
@Service
public class OrderEventHandler {

    private final JdbcTemplate jdbc;
    private final OrderProjectionRepository repository;

    public OrderEventHandler(
            JdbcTemplate jdbc,
            OrderProjectionRepository repository) {
        this.jdbc = jdbc;
        this.repository = repository;
    }

    @Transactional
    public ProcessingResult process(OrderPaidEvent event) {
        int claimed = jdbc.update("""
            INSERT INTO consumer_inbox (
                consumer_name, event_source, event_id,
                payload_hash, event_type, status, received_at
            )
            VALUES (?, ?, ?, ?, ?, 'PROCESSING', CURRENT_TIMESTAMP)
            ON CONFLICT (consumer_name, event_source, event_id)
            DO NOTHING
            """,
            "order-projection-v2",
            event.source(),
            event.eventId(),
            event.payloadHash(),
            "order.paid");

        if (claimed == 0) {
            verifyPayloadHash(event);
            return ProcessingResult.DUPLICATE;
        }

        repository.applyPaidEvent(event);

        jdbc.update("""
            UPDATE consumer_inbox
            SET status = 'PROCESSED',
                processed_at = CURRENT_TIMESTAMP
            WHERE consumer_name = ?
              AND event_source = ?
              AND event_id = ?
              AND status = 'PROCESSING'
            """,
            "order-projection-v2",
            event.source(),
            event.eventId());

        return ProcessingResult.PROCESSED;
    }

    private void verifyPayloadHash(OrderPaidEvent event) {
        // Query and compare the stored hash.
        // Throw a non-retryable contract error on mismatch.
    }
}
~~~

The listener invokes the service and only then ACKs per the framework/provider mechanism. Never catch exceptions inside the listener and still ACK if the transaction rolled back. Also ensure transactional methods are invoked through the Spring proxy; self-invocation within the same bean can bypass transaction interception.

For Lambda or non-Spring function handlers, apply the exact same principle with explicit JDBC transactions. What matters is that the inbox row and business state share the same database transaction.

## 9. Handling Concurrent Duplicates

During scale-out, two execution environments may receive the same event nearly simultaneously. Checking duplicates in Java memory or local caches fails because each instance has isolated memory.

The unique constraint coordinates across instances:

~~~mermaid
sequenceDiagram
    participant A as Consumer A
    participant B as Consumer B
    participant DB as Database

    A->>DB: INSERT inbox key E-42
    DB-->>A: Inserted
    B->>DB: INSERT same inbox key E-42
    Note over B,DB: B waits for unique-key outcome
    A->>DB: Apply business update
    A->>DB: Mark PROCESSED + COMMIT
    DB-->>B: Conflict / no row inserted
    B->>DB: Read existing hash/status
    DB-->>B: Already processed
    B-->>B: Return duplicate without side effect
~~~

Do not use a `static Set`, `ConcurrentHashMap`, or local cache as the authoritative deduplication store. They can at best reduce repeated reads within one instance; they provide zero protection across scale-out, cold starts, restarts, or multi-region execution.

When two invocations race on one key, the database transaction and unique constraint must decide which single invocation wins the claim. Configure lock/statement timeouts so waiting invocations do not tie up concurrency slots too long; on timeout, let the message retry per policy.

## 10. Same Event ID, Different Payload

An event identity must represent immutable content. If a producer resends the same `source + eventId` with a different payload, the consumer must not treat it as a normal duplicate.

You can store a hash of the canonical payload:

- Serialize following a defined schema and deterministic field order.
- Or hash raw event bytes if the producer preserves exact bytes on retry.
- Do not hash non-deterministic JSON serialization and assume hashes will match.
- Do not write secrets or sensitive data into logs on a hash mismatch.

When identity matches but hashes differ:

1. Do not apply business updates.
2. Record a contract/security error.
3. Route the message to quarantine or a DLQ per policy.
4. Alert producer/consumer owners.
5. Investigate event ID reuse or post-publish payload mutation.

A hash only detects payload differences; it does not prove the producer is trustworthy or the event is semantically valid.

## 11. When `PROCESSING` Must Be Committed Early: Leases and Recovery

The atomic inbox fits when business updates fit in a short single-database transaction. Sometimes processing takes longer, spans multiple steps, or requires another worker to resume work. In such cases, you can commit the claim first and progress via a state machine, provided you use leases.

Example extended schema:

~~~sql
CREATE TABLE consumer_inbox_jobs (
    consumer_name VARCHAR(128) NOT NULL,
    event_source  VARCHAR(256) NOT NULL,
    event_id      VARCHAR(256) NOT NULL,
    payload_hash  VARCHAR(128) NOT NULL,
    status        VARCHAR(24) NOT NULL,
    lease_owner   VARCHAR(128) NULL,
    lease_until   TIMESTAMP NULL,
    attempt_count INTEGER NOT NULL DEFAULT 0,
    received_at   TIMESTAMP NOT NULL,
    processed_at  TIMESTAMP NULL,
    PRIMARY KEY (consumer_name, event_source, event_id)
);
~~~

A possible state machine:

~~~text
RECEIVED -> PROCESSING -> PROCESSED
                  |
                  +-> RETRYABLE_FAILURE -> PROCESSING
                  |
                  +-> FAILED_TERMINAL
~~~

When a worker claims a job:

- Use a transaction and row lock or conditional update so only one worker holds a valid lease.
- Record lease owner, lease expiration, and increment attempt count.
- Extend the lease if processing continues.
- If the worker dies, the lease expires so another worker can claim it.
- Upon completion, allow only the holder of the valid owner/lease token to transition to `PROCESSED`.

### Leases Require Fencing Tokens

Lease expiration does not guarantee the old worker stopped. For instance, worker A pauses for a long time, its lease expires, worker B claims and processes; then A resumes. Both could write data.

Use a monotonically increasing fencing token or version/lease generation. Every state update must validate the current token. Downstream systems also need idempotency or version checks so an old worker cannot overwrite newer results.

Do not rely purely on worker-local clocks for lease timestamps if clocks can skew; use database time or database-managed compare-and-set.

## 12. An Inbox Does Not Cover External Side Effects

A database transaction cannot automatically span partner HTTP APIs, email providers, or payment gateways. If a consumer:

1. Writes the inbox.
2. Calls an external API successfully.
3. Crashes before committing the inbox.

The message redelivers and the external API may be called again.

If it commits the inbox first and then calls the external API, crashing after commit but before calling drops the side effect.

This is the dual-write problem. An inbox alone cannot solve it.

### Combining Inbox with Transactional Outbox

Inside the same database transaction:

- Insert/claim the inbox.
- Update business state.
- Insert an outbox command describing the external side effect to perform.
- Mark the inbox processed.
- Commit.

An outbox dispatcher then sends the command to the external API. The dispatcher may resend if it crashes after the provider executes but before marking the outbox delivered, so provider-side idempotency keys or status lookup APIs are still necessary.

~~~mermaid
flowchart TD
    Event[Incoming event]
    Consumer[Java consumer]
    Tx[DB transaction]
    Inbox[(Inbox)]
    Business[(Business state)]
    Outbox[(Outbox)]
    Dispatcher[Outbox dispatcher]
    Provider[External API/provider]

    Event --> Consumer --> Tx
    Tx --> Inbox
    Tx --> Business
    Tx --> Outbox
    Outbox --> Dispatcher --> Provider
~~~

If the provider supports idempotency keys, pass a stable key derived from the outbox command or business operation. If not, design reconciliation or an "outcome unknown" state instead of claiming exactly-once.

## 13. How Do Inbox and Outbox Differ?

| Pattern | Direction | Purpose |
|---|---|---|
| Inbox | Events entering a consumer | Deduplicate and record processed events |
| Outbox | Events/commands leaving a service | Ensure business updates and publish intent commit in one transaction |
| Inbox + Outbox | Inbound and outbound | Handle duplicate events safely and emit follow-up side effects/events reliably |

Example when the order service receives `payment.authorized`:

- Inbox records that `payment.authorized` was processed by this consumer.
- Business transaction transitions the order to `PAID`.
- Outbox records `order.paid` to be published.
- Dispatcher publishes `order.paid`.
- Downstream consumers use their own inboxes to deduplicate `order.paid`.

Do not confuse the outbox as the place to record received events. Outbox solves reliable outbound publishing; inbox solves reliable inbound consumption.

## 14. Ordering and Event Versioning

An inbox prevents processing the same event identity twice, but it does not automatically guarantee events arrive in order.

Example:

- `order.updated` version 4 arrives before version 3.
- The consumer processes version 4.
- Version 3 is later redelivered or replayed.

If the consumer checks only `eventId`, it could overwrite newer state with older data.

Mitigations:

- Attach an aggregate version or sequence number.
- Perform conditional updates, e.g. apply an event only if the new version exceeds the current version.
- Use aggregate ID as the partition key when the broker supports per-key ordering.
- Handle gaps by waiting, retrying, fetching a snapshot, or reconciling.
- Never assume global ordering when the provider guarantees ordering only within a partition/message group.

Example conditional update:

~~~sql
UPDATE order_projection
SET status = ?,
    version = ?
WHERE order_id = ?
  AND version < ?;
~~~

A 0-row result must be classified: was a newer event already applied, is the version duplicated, or does the aggregate not exist yet? Never automatically treat every 0-row update as success if an earlier event might be missing.

## 15. Retention, Replays, and Consumer Version Changes

Inbox records must be kept long enough to span redelivery and replay windows. Deleting records too early allows old replayed events to repeat side effects.

Size retention based on:

- Broker message retention.
- DLQ retention and redrive windows.
- Stream replay windows.
- Backup/restore windows that could reintroduce old events.
- Backfill or reprocessing procedures.
- External provider idempotency retention.
- Audit and legal compliance requirements.

### Consumer Version as Part of Identity

If consumer v2 is a brand-new projection that must reprocess all historical events, it can use a distinct `consumer_name` such as `order-projection-v2`. Then v2 has its own inbox namespace and is not blocked by v1's processed records.

However, do not change `consumer_name` on every routine deployment. If release v2 is just a bug fix meant to continue v1's processing state, changing the namespace discards deduplication history and risks rerunning all events. Distinguish logical consumer identity from code release version.

### Intentional Replays

Replaying to rebuild a projection may require a new namespace and separate target storage. Replaying to recover unprocessed messages must preserve the original identity. Clarify the goal before deleting inbox rows or changing consumer identity.

## 16. Poison Events and Terminal States

An event can fail consistently due to a malformed schema, missing data, violated business invariants, or unsupported event versions. Infinite retries do not cure poison events.

Classification:

- **Retryable:** transient dependency errors, lock conflicts, or throttling.
- **Permanent / terminal:** invalid payload, unsupported event type, contract violation.
- **Ambiguous:** unclear whether side effects occurred; requires idempotency/lookup.
- **Out-of-order:** valid event that cannot yet apply because a prior version is missing.

For terminal failures, record the terminal/quarantine state and acknowledge per policy after ensuring proper auditing and DLQ routing. Never mark `PROCESSED` if business updates did not occur; use a dedicated `FAILED_TERMINAL` state to reflect the outcome.

For retryable errors in the atomic inbox pattern, roll back the transaction so the event can be redelivered. In the lease pattern, update to `RETRYABLE_FAILURE` and set `next_attempt_at`/lease state for the scheduler.

## 17. Observing the Inbox and Duplicate Handling

The inbox is on the critical reliability path and needs metrics and alerts.

Track:

- Count of newly claimed events.
- Count of duplicates skipped.
- Count of payload hash mismatches.
- Count of transaction rollbacks during processing.
- Count of inbox records stuck in `PROCESSING` too long.
- Count of expired leases and reclaims.
- Count of `FAILED_TERMINAL` events.
- Count of events sent to DLQ and successfully redriven.
- Latency from `received_at` to `processed_at`.
- Inbox table size and growth rate.

Logs should include consumer name, source, event ID or pseudonymized identifier, operation ID, attempt, and outcome. Never log sensitive payloads. Avoid putting high-cardinality event IDs or tenant IDs in metric labels; use aggregated metrics with logs/traces for deep dives.

Alert when `PROCESSING` exceeds expected duration, leases repeatedly expire, hash mismatches rise, or DLQ depth grows abnormally. A high duplicate rate may simply reflect normal delivery semantics, whereas sudden spikes can indicate ack timeouts, consumer latency, or producer retry bugs.

## 18. Testing the Consumer Inbox

Testing must cover sequential duplicates, concurrent duplicates, and crashes at every critical point.

| Scenario | Expected Outcome |
|---|---|
| New event | Inbox and business state commit together |
| Redelivery of processed event | Business update is not applied again |
| Crash before commit | Inbox and business update roll back; event can retry |
| Crash after commit, before ACK | Redelivery is recognized as a duplicate |
| Two invocations with same event | Unique constraint lets only one transaction claim |
| Same identity, different payload | Not processed; contract error logged and quarantined |
| Business update fails | Transaction rolls back or moves to retryable state per pattern |
| External API succeeds, dispatcher crashes | Outbox retries with the same idempotency key |
| Lease expires | Another worker reclaims with fencing/version |
| Old worker resumes after lease expiry | Fencing token prevents overwrite |
| Out-of-order event arrives | Version check prevents state regression |
| Inbox record past retention | Tests verify replay policy avoids duplicate side effects |
| Consumer v2 replays history | Separate namespace matching reprocessing goal |
| DLQ redrive | Preserves original event/business identity |

### Fault Injection

Inject deliberate pauses or failures in test environments:

1. After receiving the message, before starting the transaction.
2. After inserting the inbox row, before business updates.
3. After business updates, before commit.
4. Immediately after commit, before ack.
5. After external provider success, before marking outbox delivered.
6. While a lease expires and a new worker reclaims.

Each point must prove final state correctness and zero unintended duplicate side effects. Testing only the happy-path single execution does not prove the inbox works.

## 19. Common Implementation Mistakes

- **Unstable event IDs:** generating a new ID per retry renders deduplication useless; preserve the application event ID across all deliveries.
- **Global uniqueness on `eventId` alone:** independent consumers can block each other; add consumer identity and source namespace.
- **`SELECT` then `INSERT`:** creates a race condition when two invocations process concurrently; use unique constraints and atomic inserts.
- **Committing inbox before business updates:** crashes can mark an event received without applying business logic; use the same transaction or full leasing/recovery.
- **ACKing before database commit:** messages can be lost if the transaction rolls back; commit first, then ACK.
- **Calling external APIs inside long transactions:** holds locks/connections and remains non-atomic with the provider; use an outbox.
- **Treating duplicates as retryable errors:** causes pointless retry loops; already-processed duplicates should be ACKed / return success.
- **Ignoring payload hash mismatches:** reused event IDs can silently corrupt or drop data; enforce contract checks.
- **Using a `static Set` for deduplication:** not shared across instances and lost on restart; use durable storage.
- **Purging the inbox too early:** old replays can re-execute side effects; retention must cover the replay window.
- **Changing consumer names on every release:** wipes out deduplication history; change only when intentionally introducing a new logical consumer.
- **Assuming an inbox guarantees system-wide exactly-once:** external side effects can still repeat; add provider idempotency/reconciliation.
- **Ignoring event ordering:** stale events can overwrite newer state; use aggregate versions/sequences.
- **Committing `PROCESSING` without leases:** worker crashes leave stuck records; use leases, fencing, and recovery.
- **Skipping post-commit, pre-ACK crash tests:** misses the most common failure window.

## 20. Implementing an Inbox in Java Serverless

When building a new consumer, follow this sequence:

1. Define the logical consumer identity and event source namespace.
2. Select a stable event ID; distinguish event ID, broker message ID, and business operation ID.
3. Define payload hashing/canonicalization and identity collision handling.
4. Create the inbox table with a composite unique key.
5. For single-database business updates, claim the inbox and apply updates inside one transaction.
6. Mark `PROCESSED` before commit; roll back both inbox and business state on error.
7. Acknowledge the message only after the transaction commits.
8. Handle duplicates by verifying the hash and returning success without repeating side effects.
9. For long or multi-step processing, use a state machine, leases, fencing tokens, and recovery.
10. For external side effects, write an outbox inside the transaction and use provider idempotency/reconciliation.
11. Protect ordering with aggregate versions or partition keys when needed.
12. Size retention to cover redelivery, DLQs, backup restores, and replay windows.
13. Monitor duplicates, hash mismatches, processing age, lease expiries, DLQs, and completion latency.
14. Test concurrent duplicates and crashes before/after commits, ACKs, and external side effects.

## 21. Key Takeaways

A consumer inbox durably records event identities so consumers recognize already-processed messages. Unique constraints enforce deduplication across multiple execution environments; Java in-memory caches or `static Set`s are insufficient for serverless scale-out.

For business updates within the same database, record the inbox entry, apply business state updates, and mark processed in a single transaction before ACKing the message. If the transaction rolls back, the event can retry; if commit succeeds but ACK fails, the redelivery is recognized as a duplicate.

An inbox does not by itself guarantee exactly-once delivery for HTTP APIs, emails, or payment providers. Combine it with a transactional outbox, provider idempotency keys, and reconciliation for external side effects. Align retention with replay windows, guard ordering with versions, and test crashes between commit and ACK. Proper design lets consumers withstand at-least-once delivery without duplicating business side effects.
