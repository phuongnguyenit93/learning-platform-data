# Building AWS Infrastructure with AWS CDK in Java

## 1. Infrastructure as Code and AWS CDK

Infrastructure as Code (IaC) is the practice of describing infrastructure in source code so it can be verified, reused, reviewed, and deployed repeatably. Instead of creating Lambdas, API Gateways, SQS queues, IAM roles, and databases manually in the Console, the development team defines resources in a repository. Pipelines can validate changes, generate a plan, and deploy the same configuration across multiple environments.

AWS Cloud Development Kit (AWS CDK) is an IaC framework for describing infrastructure using programming languages. With Java, developers use classes, objects, methods, and type safety to build constructs. CDK synthesizes Java code into CloudFormation templates; CloudFormation is responsible for creating, updating, and managing the lifecycle of AWS resources.

In the CLOUD_SERVERLESS module, CDK helps model the components that commonly accompany Java functions:

- AWS Lambda for HTTP, queue, and event triggers.
- API Gateway to receive HTTP requests.
- SQS and dead-letter queues to buffer work, retry, and isolate failing messages.
- EventBridge for event routing.
- DynamoDB or other storage services to hold durable state.
- IAM roles/policies to grant least-privilege permissions.
- CloudWatch Logs, metrics, and tracing for observability.
- VPCs, subnets, security groups, and endpoints when functions require private networking.

CDK does not replace knowledge of AWS services. CDK code only describes the desired configuration; designers must still understand timeout, concurrency, retries, idempotency, retention, access permissions, and cost for each service.

## 2. Core Concepts: App, Stack, and Construct

CDK organizes code around three core concepts:

| Concept | Role | Example |
|---|---|---|
| `App` | Entry point of the CDK application; contains one or more stacks | Application deploying the entire orders platform |
| `Stack` | CloudFormation deployment unit in an account/region | `OrdersServerlessStack` |
| `Construct` | Component describing one or more resources and behaviors | Lambda function, queue, API, or custom construct |

A construct can represent a single CloudFormation resource or group multiple resources into a higher-level component. For example, `Function` creates a Lambda function with its associated configuration; `LambdaRestApi` creates an API Gateway and the permission for the API to invoke the function. Custom constructs help encapsulate organizational conventions, such as ensuring every Lambda has standard timeout, tracing, log retention, and tags.

CDK defines three commonly referenced construct levels:

- **L1 (Cfn*):** maps almost directly to a CloudFormation resource, e.g. `CfnFunction`. Used when you need CloudFormation properties not yet supported by higher-level abstractions.
- **L2:** constructs with an object-oriented API, sensible defaults, and permission helpers, e.g. `Function`, `Queue`, `Table`.
- **L3 (pattern):** combines multiple constructs into a complete architecture, e.g. `LambdaRestApi` or event-processing patterns.

Prefer L2/L3 when they meet your requirements to reduce configuration boilerplate. Use L1 when you need fine-grained control or new features not yet available in L2/L3. Do not drop down to L1 merely to avoid learning a higher-level construct's API.

## 3. Setting Up the Java and AWS CDK Environment

A development machine typically needs:

- A JDK compatible with the CDK project version and target Lambda runtime; for example, JDK 21 for Java 21 applications.
- Apache Maven or Gradle to build Java code.
- Node.js and npm to install the AWS CDK CLI.
- AWS CLI to authenticate and inspect accounts.
- AWS CDK Toolkit (`cdk`) to synth, diff, bootstrap, and deploy.
- Appropriate AWS permissions for development and deployment environments.

Install the CDK CLI via npm:

```bash
npm install -g aws-cdk
cdk --version
```

Create a new Java application:

```bash
mkdir orders-infrastructure
cd orders-infrastructure
cdk init app --language java
```

The init command generates a Maven structure, application class, sample stack, CDK configuration, and sample test. If the repository already has a Maven project, you can integrate CDK into a dedicated module instead of nesting a separate project.

Sign in to AWS using your organization's standard mechanism, such as AWS IAM Identity Center:

```bash
aws configure sso
aws sso login --profile dev
aws sts get-caller-identity --profile dev
```

Do not commit access keys, secret keys, or session tokens into `pom.xml`, `cdk.json`, `context.json`, or source code. Use profiles, credential processes, or CI/CD identity mechanisms.

## 4. Structure of a Java CDK Project

A Maven project generated by `cdk init app --language java` typically looks like this:

```text
orders-infrastructure/
├── cdk.json
├── pom.xml
├── README.md
├── src/
│   ├── main/java/com/example/
│   │   ├── MyApp.java
│   │   └── OrdersServerlessStack.java
│   └── test/java/com/example/
│       └── OrdersServerlessStackTest.java
└── target/
```

Key files:

- `cdk.json`: configures how the CDK CLI runs the CDK application and default context.
- `pom.xml`: AWS CDK dependencies, constructs, and Maven plugins.
- `MyApp.java`: creates the `App`, instantiates stacks, and calls `synth()`.
- `OrdersServerlessStack.java`: describes AWS resources.
- `src/test`: verifies that the generated template has the expected resources and properties.

The `cdk.json` generated by the Java template typically uses a Maven command similar to:

```json
{
  "app": "mvn -e -q compile exec:java"
}
```

Keep the configuration generated by your template version if additional plugins or arguments are present. When the CDK CLI runs `synth`, it executes the Java application to produce the Cloud Assembly.

## 5. CDK Dependencies and Versions

AWS CDK v2 bundles service modules into the `aws-cdk-lib` artifact; construct interfaces reside in the `constructs` artifact. A Maven project typically includes dependencies similar to:

```xml
<dependencies>
    <dependency>
        <groupId>software.amazon.awscdk</groupId>
        <artifactId>aws-cdk-lib</artifactId>
        <version>${cdk.version}</version>
    </dependency>
    <dependency>
        <groupId>software.constructs</groupId>
        <artifactId>constructs</artifactId>
        <version>${constructs.version}</version>
    </dependency>
</dependencies>
```

The `${cdk.version}` and `${constructs.version}` properties must be declared in `pom.xml` with compatible versions. Projects initialized by the CDK CLI come with matching versions; update deliberately and inspect release notes before upgrading.

Do not mix CDK v1 APIs (`@aws-cdk/...`) with CDK v2 (`software.amazon.awscdk:aws-cdk-lib`). CDK v2 is the choice for new projects. Pin versions in the build so local machines and pipelines synthesize the exact same template.

## 6. Creating an App and Stack in Java

The entry point class creates `App`, instantiates the stack, and synthesizes the Cloud Assembly:

```java
package com.example;

import software.amazon.awscdk.App;
import software.amazon.awscdk.Environment;
import software.amazon.awscdk.StackProps;

public final class MyApp {
    public static void main(final String[] args) {
        App app = new App();

        Environment deploymentEnv = Environment.builder()
                .account(System.getenv("CDK_DEFAULT_ACCOUNT"))
                .region(System.getenv("CDK_DEFAULT_REGION"))
                .build();

        new OrdersServerlessStack(
                app,
                "OrdersServerlessStack",
                StackProps.builder().env(deploymentEnv).build());

        app.synth();
    }
}
```

`account` and `region` identify the deployment environment. CDK also supports environment-agnostic stacks, though certain features require knowing the account/region at synth time. For multi-environment applications, pass the environment explicitly from the pipeline or managed configuration.

A stack extends `Stack`:

```java
package com.example;

import software.amazon.awscdk.Stack;
import software.constructs.Construct;
import software.amazon.awscdk.StackProps;

public class OrdersServerlessStack extends Stack {
    public OrdersServerlessStack(
            final Construct scope,
            final String id,
            final StackProps props) {
        super(scope, id, props);

        // Declare resources and constructs here.
    }
}
```

A construct ID must be unique within its parent scope. CDK uses the construct path to generate logical IDs in CloudFormation. Changing the construct tree or ID can change the logical ID and cause CloudFormation to treat the old resource as needing replacement. For stateful databases, queues, or buckets, unexpected replacement can cause disruption or data loss.

## 7. Modeling a Java Lambda

The CDK L2 `Function` models Lambda runtime, handler, artifact, timeout, memory, architecture, environment, and execution permissions. Example:

```java
import java.util.Map;

import software.amazon.awscdk.Duration;
import software.amazon.awscdk.services.lambda.Architecture;
import software.amazon.awscdk.services.lambda.Code;
import software.amazon.awscdk.services.lambda.Function;
import software.amazon.awscdk.services.lambda.Runtime;

Function orderApi = Function.Builder.create(this, "OrderApiFunction")
        .runtime(Runtime.JAVA_21)
        .architecture(Architecture.ARM_64)
        .handler("com.example.orders.ApiHandler::handleRequest")
        .code(Code.fromAsset("../orders-function/target/orders-function.jar"))
        .memorySize(1024)
        .timeout(Duration.seconds(15))
        .environment(Map.of(
                "APP_ENV", "dev",
                "LOG_LEVEL", "INFO"))
        .tracing(software.amazon.awscdk.services.lambda.Tracing.ACTIVE)
        .build();
```

The values above are only initial examples. Choose a runtime still supported by AWS, an architecture compatible with native libraries and the build artifact, and memory/timeout based on measurements. The Java handler must exist in the JAR and conform to the interface expected by the Lambda Java runtime.

`Code.fromAsset` packages a file or directory as an asset. Paths are resolved from the CDK app's working directory during synth. Therefore, the pipeline must build the function before running `cdk synth`; if the JAR does not exist yet, CDK cannot package the asset as intended.

If the function needs environment variables containing resource ARNs or names, retrieve values from constructs such as `table.getTableName()` or `queue.getQueueUrl()` rather than hardcoding them. CDK generates CloudFormation references and deploys the right values per stack.

## 8. Building an API Gateway for Lambda

For a simple REST API, `LambdaRestApi` creates an API Gateway REST API and Lambda integration:

```java
import software.amazon.awscdk.services.apigateway.LambdaRestApi;

LambdaRestApi api = LambdaRestApi.Builder.create(this, "OrdersApi")
        .handler(orderApi)
        .proxy(true)
        .build();
```

`proxy(true)` forwards paths/methods without explicit declarations to the Lambda handler. The application can route within its framework or parse paths directly. CDK creates the Lambda resource-based permission allowing API Gateway to invoke the function.

If choosing API Gateway HTTP API, use the `HttpApi` and `HttpLambdaIntegration` constructs:

```java
import software.amazon.awscdk.services.apigatewayv2.HttpApi;
import software.amazon.awscdk.aws_apigatewayv2_integrations.HttpLambdaIntegration;
import software.amazon.awscdk.services.apigatewayv2.AddRoutesOptions;
import software.amazon.awscdk.services.apigatewayv2.HttpMethod;
import java.util.List;

HttpApi httpApi = new HttpApi(this, "OrdersHttpApi");
HttpLambdaIntegration integration = new HttpLambdaIntegration(
        "OrdersIntegration", orderApi);

httpApi.addRoutes(AddRoutesOptions.builder()
        .path("/")
        .methods(List.of(HttpMethod.ANY))
        .integration(integration)
        .build());
httpApi.addRoutes(AddRoutesOptions.builder()
        .path("/{proxy+}")
        .methods(List.of(HttpMethod.ANY))
        .integration(integration)
        .build());
```

`LambdaRestApi` and `HttpApi` represent two different API Gateway types. REST API offers richer API management features; HTTP API generally has leaner configuration and lower cost for simple proxies/routes. Choose based on requirements for authorizers, mapping, validation, logging, throttling, and pricing.

If you need a REST API with specific methods/models/authorizers, you can instantiate `RestApi`, `Resource`, `Method`, and `LambdaIntegration` individually. If prioritizing cost and modern HTTP features, compare API Gateway HTTP API against REST API before choosing; the two differ in capabilities, logging, authorization, and pricing.

For production endpoints, consider:

- Authentication/authorization with a JWT authorizer, Cognito, or Lambda authorizer.
- Throttling and quotas to protect the function and dependencies.
- Access logging and request IDs.
- CORS if browsers make cross-origin calls.
- Custom domains, TLS certificates, and DNS.
- Request validation and payload limits.
- Timeout alignment between API Gateway and Lambda.

Do not rely on API Gateway as the sole data protection layer. The function must still enforce authorization on resources and tenants at the business level.

## 9. Creating an SQS Queue, DLQ, and Lambda Event Source Mapping

Queues decouple request ingestion speed from processing speed. A dead-letter queue retains messages after repeated processing failures.

```java
import software.amazon.awscdk.Duration;
import software.amazon.awscdk.services.sqs.DeadLetterQueue;
import software.amazon.awscdk.services.sqs.Queue;
import software.amazon.awscdk.services.lambda.eventsources.SqsEventSource;
import software.amazon.awscdk.services.lambda.eventsources.SqsEventSourceProps;

Queue ordersDlq = Queue.Builder.create(this, "OrdersDlq")
        .retentionPeriod(Duration.days(14))
        .build();

Queue ordersQueue = Queue.Builder.create(this, "OrdersQueue")
        .retentionPeriod(Duration.days(4))
        .visibilityTimeout(Duration.seconds(180))
        .deadLetterQueue(DeadLetterQueue.builder()
                .queue(ordersDlq)
                .maxReceiveCount(5)
                .build())
        .build();

Function orderWorker = Function.Builder.create(this, "OrderWorker")
        .runtime(Runtime.JAVA_21)
        .architecture(Architecture.ARM_64)
        .handler("com.example.orders.SqsHandler::handleRequest")
        .code(Code.fromAsset("../orders-function/target/orders-function.jar"))
        .memorySize(1024)
        .timeout(Duration.seconds(30))
        .build();

orderWorker.addEventSource(new SqsEventSource(
        ordersQueue,
        SqsEventSourceProps.builder()
                .batchSize(10)
                .reportBatchItemFailures(true)
                .build()));
```

The `SqsEventSource` construct creates the event source mapping and the permissions needed for Lambda to poll the queue. `reportBatchItemFailures(true)` enables partial batch responses; the handler must return the list of failed messages in the format expected by Lambda Events. If the handler throws an exception for the whole batch, the entire batch can still be redelivered.

Visibility timeout must be long enough for the function to process a batch and handle retries. AWS recommends setting the queue visibility timeout to at least six times the function timeout, plus any batching window if used. For example, a 30-second function timeout with a 180-second queue visibility timeout meets the baseline recommendation; real workloads may need additional headroom.

SQS Standard provides at-least-once semantics, so the handler must be idempotent. `maxReceiveCount` does not replace deduplication logic; it only controls how many receives occur before a message moves to the DLQ.

## 10. Creating a DynamoDB Table and Granting Permissions with Grants

CDK L2 provides helpers to grant least-privilege permissions per resource. Example creating an orders table:

```java
import software.amazon.awscdk.RemovalPolicy;
import software.amazon.awscdk.services.dynamodb.Attribute;
import software.amazon.awscdk.services.dynamodb.AttributeType;
import software.amazon.awscdk.services.dynamodb.BillingMode;
import software.amazon.awscdk.services.dynamodb.Table;

Table ordersTable = Table.Builder.create(this, "OrdersTable")
        .partitionKey(Attribute.builder()
                .name("orderId")
                .type(AttributeType.STRING)
                .build())
        .billingMode(BillingMode.PAY_PER_REQUEST)
        .removalPolicy(RemovalPolicy.RETAIN)
        .build();

ordersTable.grantReadWriteData(orderApi);
ordersTable.grantReadWriteData(orderWorker);
```

`grantReadWriteData` creates a policy for the required read/write data operations on the table. If a function only reads, use `grantReadData`; if it only writes, use `grantWriteData`. Never assign `AdministratorAccess` or account-wide `dynamodb:*` to a Lambda just to avoid permission errors.

`RemovalPolicy.RETAIN` keeps the table when the stack is deleted, which suits data that must be protected. Retained resources outlive the stack lifecycle; a separate management and deletion procedure is needed to remove them later. Test environments may use `DESTROY`, but never make that the default for production data.

## 11. Structuring a Complete Stack for a Serverless Application

A stack can combine APIs, functions, queues, DLQs, and databases. To keep code manageable, split it into small methods or constructs:

```java
public class OrdersServerlessStack extends Stack {
    public OrdersServerlessStack(
            Construct scope,
            String id,
            StackProps props) {
        super(scope, id, props);

        Table ordersTable = createOrdersTable();
        Queue ordersDlq = createOrdersDlq();
        Queue ordersQueue = createOrdersQueue(ordersDlq);

        Function apiHandler = createApiFunction(ordersTable);
        Function worker = createQueueWorker(ordersTable);

        LambdaRestApi.Builder.create(this, "OrdersApi")
                .handler(apiHandler)
                .proxy(true)
                .build();

        worker.addEventSource(new SqsEventSource(
                ordersQueue,
                SqsEventSourceProps.builder()
                        .batchSize(10)
                        .reportBatchItemFailures(true)
                        .build()));
    }

    // create... methods instantiate constructs as shown in the examples above.
}
```

This is an organizational skeleton; imports and `create...` methods must be implemented according to the project. For large stacks, create dedicated constructs such as `OrdersApi`, `OrderProcessing`, and `Persistence` to isolate responsibilities. Do not split stacks too finely if they share many cross-stack references and must be deployed together; each stack introduces another CloudFormation boundary and deployment dependency.

## 12. Environment Configuration and Keeping Secrets Out of Code

CDK can receive configuration from context, environment variables, CloudFormation parameters, or resource references. Pick a clear convention for each configuration category.

| Configuration Type | Recommended Storage |
|---|---|
| Deploy region/account | Stack environment or pipeline |
| Environment name, log level, non-sensitive feature flags | CDK context or environment variables |
| ARN/name of a resource in the same stack | Retrieved from construct references |
| Secrets, passwords, API tokens | Secrets Manager or Systems Manager Parameter Store |
| Configuration changing frequently at runtime | Parameter Store/AppConfig or a config service |

Do not put secrets in `cdk.json`, `cdk.context.json`, `pom.xml`, or Git. Context can be committed to the repository and appear in synthesized templates. If Lambda needs to read a secret, grant runtime permissions for the function to fetch the secret from Secrets Manager rather than resolving the secret to plaintext during synth.

Example granting secret read permissions:

```java
import software.amazon.awscdk.services.secretsmanager.ISecret;
import software.amazon.awscdk.services.secretsmanager.Secret;

ISecret paymentSecret = Secret.fromSecretNameV2(
        this,
        "PaymentSecret",
        "production/payment-provider");

orderApi.addEnvironment("PAYMENT_SECRET_ARN", paymentSecret.getSecretArn());
paymentSecret.grantRead(orderApi);
```

The function receives the ARN via an environment variable and uses the AWS SDK/Secrets Manager client to read the secret when needed. If caching the secret in memory to reduce latency, set a TTL and account for behavior during secret rotation. Never log secret values.

## 13. IAM Least Privilege and Resource Policies

CDK provides `grant...` helpers to assign resource-scoped permissions. Prefer specific permissions:

- `table.grantReadData(function)` instead of `dynamodb:*`.
- `queue.grantSendMessages(producer)` instead of `sqs:*`.
- `secret.grantRead(function)` instead of permission to read all secrets.
- Event source constructs grant the polling/consuming permissions the function needs.

Lambda's IAM role is an identity policy attached to the function. Some services also require resource policies to allow cross-account principals or AWS services to access them. For instance, API Gateway needs permission to invoke Lambda; an S3 bucket may need a bucket policy; a KMS key needs a key policy for principals using the key.

Do not confuse deployment permissions with runtime permissions. The developer/CI role needs CloudFormation and resource creation permissions; the Lambda execution role only needs permissions the function uses while running. Separating the two roles limits the blast radius if a function is compromised.

## 14. VPC and Private Connectivity

If a Lambda needs to reach a database or internal service inside a VPC, CDK can create a VPC, subnets, and security groups, then attach the function to the VPC:

```java
import software.amazon.awscdk.services.ec2.Vpc;
import software.amazon.awscdk.services.ec2.SubnetSelection;
import software.amazon.awscdk.services.ec2.SubnetType;
import software.amazon.awscdk.services.ec2.SecurityGroup;
import software.amazon.awscdk.services.ec2.Peer;
import software.amazon.awscdk.services.ec2.Port;
import java.util.List;

Vpc vpc = Vpc.Builder.create(this, "ApplicationVpc")
        .maxAzs(2)
        .natGateways(1)
        .build();

SecurityGroup functionSecurityGroup = SecurityGroup.Builder.create(
        this, "FunctionSecurityGroup")
        .vpc(vpc)
        .allowAllOutbound(false)
        .build();

SecurityGroup databaseSecurityGroup = SecurityGroup.Builder.create(
        this, "DatabaseSecurityGroup")
        .vpc(vpc)
        .allowAllOutbound(false)
        .build();

functionSecurityGroup.addEgressRule(
        Peer.securityGroup(databaseSecurityGroup),
        Port.tcp(5432),
        "Allow PostgreSQL traffic to database");
databaseSecurityGroup.addIngressRule(
        Peer.securityGroup(functionSecurityGroup),
        Port.tcp(5432),
        "Allow PostgreSQL traffic from function");

Function privateWorker = Function.Builder.create(this, "PrivateWorker")
        .runtime(Runtime.JAVA_21)
        .handler("com.example.orders.PrivateHandler::handleRequest")
        .code(Code.fromAsset("../orders-function/target/orders-function.jar"))
        .vpc(vpc)
        .vpcSubnets(SubnetSelection.builder()
                .subnetType(SubnetType.PRIVATE_WITH_EGRESS)
                .build())
        .securityGroups(List.of(functionSecurityGroup))
        .timeout(Duration.seconds(30))
        .build();
```

This is an illustrative configuration for PostgreSQL; the database must use `databaseSecurityGroup` and the port must match the actual service. Add outbound rules to VPC endpoints or the NAT Gateway for any AWS services or public endpoints the function needs to reach. VPC attachment requires ENIs for Lambda and affects startup time, IP capacity, NAT costs, and routing. A Lambda placed in a private subnet does not automatically have Internet access; if it needs to call public endpoints, it must have a NAT Gateway or properly designed egress path.

If the function only needs to access AWS services via PrivateLink, you can use corresponding VPC endpoints to avoid NAT for that traffic. Evaluate NAT Gateway, data processing, and endpoint costs before placing every function inside a VPC.

## 15. Logging, Tracing, and Monitoring

CDK can enable tracing for Lambda:

```java
.tracing(Tracing.ACTIVE)
```

X-Ray connects traces across integrated services. Functions also need permission to write to CloudWatch Logs; the L2 `Function` typically creates an execution role with the basic required permissions. In production, configure log retention, encryption, metric filters, and alarms per organizational policy.

Key metrics to observe:

- Lambda `Invocations`, `Errors`, `Duration`, `Throttles`, and `ConcurrentExecutions`.
- SQS message age, visible/in-flight message count, and DLQ depth.
- API Gateway 4xx/5xx errors, latency, and throttling.
- DynamoDB throttled requests, consumed capacity, and latency.
- Workflow execution failures/timeouts if using Step Functions.
- Cost broken down by function, API, queue, database, NAT, and logs.

Structured logs should include `requestId`, `eventId`, `correlationId`, `orderId`, function version, and error code. Never log tokens, secrets, or full payloads containing personal data.

## 16. Testing CDK with Assertions

CDK synth generates a CloudFormation template; tests can inspect that template without deploying live resources. CDK v2's testing utilities live in the `assertions` package.

JUnit example:

```java
package com.example;

import java.util.Map;

import org.junit.jupiter.api.Test;
import software.amazon.awscdk.App;
import software.amazon.awscdk.StackProps;
import software.amazon.awscdk.assertions.Template;

class OrdersServerlessStackTest {
    @Test
    void createsJavaFunctionsAndApi() {
        App app = new App();
        OrdersServerlessStack stack = new OrdersServerlessStack(
                app,
                "TestOrdersStack",
                StackProps.builder().build());

        Template template = Template.fromStack(stack);

        template.resourceCountIs("AWS::Lambda::Function", 2);
        template.resourceCountIs("AWS::ApiGateway::RestApi", 1);
        template.hasResourceProperties(
                "AWS::Lambda::Function",
                Map.of("Runtime", "java21"));
    }
}
```

The sample test assumes the stack creates two Lambdas and one REST API. If the stack structure changes, update assertions to reflect the expected behavior. Do not check only resource counts; also assert timeout, runtime, memory, environment variables, IAM actions/resources, queue visibility timeout, redrive policy, encryption, and retention.

Types of tests:

- **Unit tests for custom constructs:** verify resource creation logic and defaults.
- **Template assertions:** verify CloudFormation resources, properties, and outputs.
- **Snapshot tests:** detect large template changes; review diffs carefully since legitimate changes can alter snapshots.
- **Integration tests:** deploy to a test account and verify triggers, permissions, logs, and behavior.
- **Policy/security tests:** check for IAM wildcards, public exposure, encryption, and mandatory policies.

## 17. Common CDK Commands

After writing code and building artifacts:

```bash
mvn test
mvn package
cdk ls
cdk synth OrdersServerlessStack
cdk diff OrdersServerlessStack
cdk deploy OrdersServerlessStack --profile dev
```

Purpose:

| Command | Effect |
|---|---|
| `cdk ls` | Lists stacks in the application |
| `cdk synth` | Synthesizes constructs into CloudFormation templates and a Cloud Assembly |
| `cdk diff` | Compares the synthesized template against the current deployed stack state |
| `cdk deploy` | Submits the Cloud Assembly/CloudFormation change set for deployment |
| `cdk destroy` | Deletes the stack and non-retained resources |
| `cdk doctor` | Diagnoses common CDK environment issues |

Always inspect `cdk diff` before deploying. Pay special attention to resource replacement, deletion, broadened IAM policies, public endpoints, subnet/route updates, and database changes. A small change in a construct ID or logical ID can cause CloudFormation to replace a resource.

`cdk destroy` is only appropriate for disposable environments. For production, require an approval workflow and data retention controls. `RemovalPolicy.RETAIN` preserves a resource after stack deletion, which also means the resource must be managed separately afterward.

## 18. Bootstrapping Accounts and Regions

Before the first deployment into an account/region, CDK usually needs the environment bootstrapped. Bootstrapping creates supporting resources such as an S3 bucket for assets, an ECR repository for container assets, and IAM roles used during deployment.

Example:

```bash
cdk bootstrap aws://123456789012/ap-southeast-1 --profile dev
```

Bootstrapping operates at the account/region scope, not per stack. It requires permissions to create bootstrap resources and may require trust configuration if pipelines deploy from another account.

Do not run bootstrap casually in production using an over-privileged personal identity. Define bootstrap execution policies, trusted accounts, qualifiers, and versions according to your organization's platform standards. Do not delete the bootstrap stack while applications still rely on its assets or deployment roles.

## 19. Splitting Stacks and Environments

A large system can be divided into multiple stacks:

- `NetworkStack`: VPC, subnets, routes, endpoints.
- `DataStack`: DynamoDB, S3, databases, and encryption keys.
- `ApplicationStack`: Lambda, API Gateway, queues, and event routing.
- `ObservabilityStack`: dashboards, alarms, log groups, and tracing configuration.

Split stacks only when ownership boundaries, lifecycles, or deployment permissions differ. If every stack always deploys together and shares many cross-stack references, over-splitting complicates deployment.

### Dev, Staging, and Production

You can deploy the same CDK app to multiple accounts/regions using context or environment variables:

```bash
CDK_DEFAULT_ACCOUNT=111111111111 \
CDK_DEFAULT_REGION=ap-southeast-1 \
cdk synth
```

The example above illustrates environment variables in a Unix-style shell; on Windows PowerShell, use `$env:CDK_DEFAULT_ACCOUNT = "..."` and `$env:CDK_DEFAULT_REGION = "..."` before running CDK.

Do not hardcode production account IDs in source code. The pipeline should select the account and role per environment while the code uses the same constructs with different configuration. Use tags such as `Environment`, `Service`, `Owner`, and `CostCenter` to support inventory, governance, and cost allocation.

## 20. CI/CD for AWS CDK in Java

A pipeline may consist of:

1. Check out source and pin JDK, Maven, and CDK CLI versions.
2. Run unit tests for functions and constructs.
3. Build function JAR/container assets.
4. Run dependency/security scans.
5. Run `cdk synth` and store the Cloud Assembly as an artifact.
6. Run policy checks on synthesized templates (IAM, encryption, public access, retention).
7. Generate and review `cdk diff` or CloudFormation change sets.
8. Deploy to dev/staging using the pipeline's role.
9. Run integration/smoke tests.
10. Require approval before deploying to production.
11. Monitor alarms and roll back according to the release strategy.

Pipelines should use OIDC or an equivalent federation mechanism to obtain short-lived credentials rather than storing long-lived access keys. Deployment roles and runtime roles must remain separate. For cross-account deployments, restrict bootstrap trust strictly to the authorized accounts and pipeline principals.

## 21. Change Management and Avoiding Data Loss

CloudFormation updates resources based on the new template. Some properties update in-place; others require replacement. CDK does not automatically know whether data inside a resource can be safely deleted.

Before changing stateful resources:

- Inspect `cdk diff` and CloudFormation replacement behavior.
- Use `RemovalPolicy.RETAIN` on databases, buckets, or queues whose data must be preserved.
- Enable deletion protection where supported by the service.
- Plan backup/restore and migration procedures.
- Maintain schema compatibility between old and new function versions during rollouts.
- Avoid changing construct paths/IDs unless intentionally replacing a resource.
- Avoid hardcoding physical resource names unnecessarily; CloudFormation-generated names avoid collisions and simplify replacements.

For Lambda, you can use versions and aliases to shift traffic in a controlled manner. For API Gateway or event source mappings, verify whether changing an integration introduces downtime or duplicate processing. Rolling back code does not automatically undo already-processed messages or committed database transactions.

## 22. Cost and Architecture Choices

CDK makes created resources explicit, but it does not optimize cost automatically. Evaluate cost across the entire flow:

- Lambda invocations, duration, memory, architecture, and provisioned concurrency.
- API Gateway requests, data transfer, and logging.
- SQS requests, message retention, and DLQ.
- DynamoDB read/write capacity, storage, and backups.
- NAT Gateway hourly/data processing charges, VPC endpoints, and data transfer.
- CloudWatch Logs ingestion, retention, metrics, and tracing.
- KMS keys, Secrets Manager, and integrated services.

For instance, adding a NAT Gateway to every VPC can incur significant fixed hourly cost even when functions rarely run. Creating a VPC endpoint for every service also carries its own cost. If a function only calls AWS service public endpoints and does not need a private network, do not attach it to a VPC by default.

Tags and stack outputs help manage inventory, while cost allocation requires activating cost allocation tags at the account level and reviewing Cost Explorer/Billing reports. Measure cost per business transaction rather than looking only at the total bill.

## 23. Common Mistakes When Using CDK in Java

| Mistake | Consequence | Fix |
|---|---|---|
| Not building the JAR before `cdk synth` | Asset does not exist or packages a stale artifact | Add a Maven build step before synth |
| Wrong class/method name in handler | Lambda starts but fails to locate the handler | Verify JAR contents, package, and handler signature |
| Mixing CDK v1 with v2 dependencies | Compilation errors or incompatible APIs | Use matching versions of `aws-cdk-lib` and `constructs` |
| Skipping account/region bootstrap | Deployment lacks asset bucket or roles | Run `cdk bootstrap` with an appropriate role |
| Granting wildcard IAM permissions | Function gets broader permissions than needed | Use `grantReadData`, `grantConsumeMessages`, and ARN-scoped policies |
| Using `RemovalPolicy.DESTROY` for production data | Database/bucket/queue lost on stack deletion | Use RETAIN, backups, and deletion protection |
| Accidentally changing construct IDs | CloudFormation creates a new resource or replaces it | Keep construct paths stable and review diffs |
| Hardcoding secrets in context | Secrets can leak into Git/templates | Use Secrets Manager/Parameter Store and runtime grants |
| Adding an unnecessary VPC | Increases cold starts and NAT/endpoint costs | Attach VPC only when the workload needs private resources |
| Not testing synthesized templates | Wrong runtime, timeout, IAM, or redrive found only at deploy | Use CDK assertions and integration tests |
| Deploying with personal credentials | Hard to audit and control permissions | Use pipeline roles/federation and approvals |

## 24. Workflow for Building Serverless Infrastructure with CDK

A practical workflow can follow this sequence:

1. **Describe the workload:** identify HTTP/event/message triggers, data, state, and SLAs.
2. **Design the architecture:** choose API Gateway, Lambda, queues/event buses, databases, networking, and observability.
3. **Define ownership:** choose stack and construct boundaries based on resource lifecycles.
4. **Initialize CDK Java:** pin JDK, Maven, CDK CLI, and dependency versions.
5. **Write constructs:** prefer L2/L3 first, L1 when detailed properties are needed.
6. **Grant permissions:** use grant helpers and separate deployment roles from runtime roles.
7. **Set operational policies:** timeout, memory, concurrency, retries, DLQ, retention, and encryption.
8. **Configure environments:** account/region, tags, non-secret config, and secret references.
9. **Test:** unit tests, CDK assertions, synth, and policy checks.
10. **Bootstrap:** prepare accounts/regions and pipeline trust.
11. **Review diff:** inspect replacements, deletions, IAM changes, and public exposure.
12. **Deploy and verify:** deploy per environment, run smoke tests, and check metrics/logs.
13. **Monitor costs:** allocate by tags and optimize using real usage data.

## 25. Pre-Production Deployment Checklist

- [ ] Uses AWS CDK v2 with pinned dependency and CLI versions.
- [ ] App, Stack, and Constructs are organized along clear ownership boundaries.
- [ ] Lambda runtime/handler/architecture match the Java artifact.
- [ ] Artifact is built before `cdk synth` and the asset path is verified.
- [ ] API Gateway, queue/event source mappings, and DLQs match delivery semantics.
- [ ] Timeout, memory, batch size, visibility timeout, and concurrency are appropriate.
- [ ] Lambda IAM role follows least privilege; deployment role is separate.
- [ ] Secrets are absent from source, context, or CloudFormation plaintext.
- [ ] Critical databases/buckets/queues have appropriate retention, backups, and deletion protection.
- [ ] VPC is enabled only when needed; subnets, NAT, endpoints, and security groups are costed.
- [ ] Logging, tracing, metrics, alarms, and retention are configured.
- [ ] CDK assertions cover runtime, resources, IAM, encryption, and key policies.
- [ ] `cdk synth` and `cdk diff` have been reviewed.
- [ ] Account/region is bootstrapped and the pipeline uses short-lived identities.
- [ ] Tested in a non-prod deployment, integration tests passed, and a rollback plan exists.
- [ ] Tags and cost allocation support tracking cost by service and environment.

## Conclusion

AWS CDK enables building serverless infrastructure in Java in a structured, testable, and repeatable way. `App` organizes the application, `Stack` defines the CloudFormation unit, and `Construct` models resources or patterns. When combining Lambda, API Gateway, SQS, databases, and IAM, prefer higher-level constructs with least-privilege permissions, keep state in durable services, configure retries/DLQs/timeouts to match each trigger, and protect stateful resources during changes. The `test → synth → diff → bootstrap → deploy → verify` workflow turns CDK code into infrastructure that can be reviewed, audited, and operated safely across environments.
