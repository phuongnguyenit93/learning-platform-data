# Managing Test Data and Cleaning Up Resources After Testing

Serverless testing typically generates far more data and resources than an ordinary unit test. A single scenario can create HTTP requests, queue messages, bus events, storage objects, database records, temporary functions, logs, subscriptions, and integration resources. If data is not isolated or resources are not cleaned up after runs, test executions interfere with one another, results become hard to reproduce, costs rise, and the test environment gradually turns into an unmanageable sprawl.

Test data management and cleanup must be designed as part of the test lifecycle: create data intentionally, tag it with a run identifier, maintain isolation across parallel tests, wait for asynchronous processing to finish, clean up strictly within scope, and verify no unexpected resources remain. For Java functions triggered by HTTP, messages, or events, this is especially critical because a single test can produce side effects across multiple services, and an invocation can continue processing after the test method has already exited.

## 1. Goals of test data management

A strong test data strategy must satisfy these goals:

- **Deterministic:** identical fixtures, inputs, and configurations produce predictable results.
- **Isolated:** one test run never reads, modifies, or deletes another test run's data.
- **Representative:** data reflects key business cases, including boundary, error, and missing-data conditions.
- **Safe:** never exposes production data, secrets, or unnecessary personal information.
- **Disposable:** temporary data and resources have an explicit lifecycle, owner, and deletion mechanism.
- **Traceable:** all data and resources created by a test run can be located.
- **Cost-aware:** queues, databases, logs, functions, or test environments never linger indefinitely.

Test data is more than database rows. It also includes queue messages, events, objects, files, dummy secrets, identities, webhook endpoints, API sandbox records, logs, and resources provisioned by Infrastructure as Code.

## 2. Classifying test data

Choose how to generate data based on testing goals and sensitivity:

| Data type | Description | Use case | Notes |
|---|---|---|---|
| Synthetic data | Newly generated data not representing real people | Unit, integration, load, and end-to-end tests | Preferred default |
| Fixture | Fixed, named, versioned dataset | Regression, contract, and scenario tests | Stored alongside source or test artifacts |
| Generated data | Data generated by seed, size, and rules | Boundary, property-based, and load tests | Log the seed for reproducibility |
| Masked data | Real data with sensitive fields masked or replaced | Testing compatibility with realistic data distributions | Must check re-identification risk |
| Anonymized data | Data processed so individuals are no longer identifiable under applicable standards | Selected analytical testing | Never assume masking equals anonymization |
| Snapshot/copy | Copy from another environment | Migration or compatibility tests | Control source, access, retention, and deletion |

Prefer synthetic data. Pseudonymized or masked data can still constitute personal data if it can be linked back or re-identified. If a copy of real data is unavoidable, require approval, minimize fields, restrict access, encrypt, and enforce an explicit deletion schedule.

### Creating business-meaningful fixtures

Fixtures should describe scenarios rather than arbitrary random values. For example, for an order workflow:

| Fixture | Purpose |
|---|---|
| `order-standard` | Valid order, sufficient stock, payment succeeds |
| `order-no-stock` | Verifies rejection when inventory is insufficient |
| `order-payment-timeout` | Verifies indeterminate outcome handling and idempotent retries |
| `order-duplicate-event` | Verifies consumers receiving the same event multiple times |
| `order-cross-tenant` | Verifies tenant data isolation |
| `order-invalid-schema` | Verifies malformed-schema message handling and DLQ |

Fixture names should be stable, human-readable, and independent of test execution order. Avoid sharing one mutable record across multiple tests; one test can alter data another test relies on.

## 3. Designing test data by test layer

Not every test type needs to provision real cloud resources.

| Test layer | Appropriate test data | Resources to use |
|---|---|---|
| Unit test | In-memory objects/fixtures | Fakes, stubs, or mocked dependencies |
| Component test | Small datasets, real schemas | Local/container database or emulator |
| Integration test | Data isolated per test run | Dedicated test cloud resources or containers |
| Contract test | Versioned sample events/requests | Schema registry or contract artifacts |
| End-to-end test | Cross-service scenarios | Ephemeral stack/environment with dedicated namespace |
| Load test | Large datasets, seed-generated | Dedicated load-test environment with capped quotas |
| Resilience test | Error, duplicate, poison, and timeout data | Queues/DLQs and dependency sandboxes |

Unit tests should not create real cloud queues merely to test a Java function. Conversely, testing event source mappings, IAM permissions, retries, and DLQs requires integration tests on AWS/Azure/GCP or clearly bounded simulated environments. Emulators accelerate feedback without guaranteeing complete parity with real services; keep a real cloud test suite as well.

## 4. Namespacing per test run

When CI runs multiple jobs or parallel tests, assign a unique namespace per run. A namespace can be a UUID, a CI run ID paired with an attempt ID, or a short identifier derived from the build and worker.

Example:

```text
testRunId = ci-4821-attempt-2
tenantId  = test-ci-4821-attempt-2
orderId   = test-ci-4821-attempt-2-order-001
queue     = orders-test-ci-4821-attempt-2
bucketKey = test/ci-4821-attempt-2/orders/order-001.json
```

All test-created resources and data should carry this identifier appropriately:

- Database records include `testRunId`, a test tenant, or a dedicated partition/prefix.
- S3/object storage uses a test-run prefix.
- Event bodies include test-run metadata or a testing correlation ID.
- Temporary queues/topics/rules/resources embed the test run ID in their name or tags.
- Logs and traces record `testRunId` to filter activity from a single run.
- Dummy secrets/configs use dedicated names and scopes, never putting real values in tags.

`testRunId` exists solely for isolation and cleanup—never as a credential or proof of authorization. Do not allow any caller passing an arbitrary `testRunId` to delete someone else's data. The cleanup service must validate ownership and scope created by that exact test run.

### Resource naming and tagging

A common tag/label set:

| Key | Example value | Purpose |
|---|---|---|
| `managed-by` | `integration-test` | Distinguishes test-created resources |
| `test-run-id` | `ci-4821-attempt-2` | Groups resources by run |
| `owner` | `orders-platform-ci` | Identifies the responsible team |
| `created-at` | UTC timestamp | Investigates lingering resources |
| `expires-at` | UTC timestamp | Tells the janitor when deletion is eligible |
| `environment` | `ephemeral-test` | Distinguishes from staging/production |

Not all cloud resources support tags/labels identically. For untaggable resources, record the resource ID/ARN/URL in a test-run manifest or prefix the resource name uniquely. A manifest also drives cleanup strictly over the list of created resources rather than searching and deleting with an overly broad filter.

## 5. Creating deterministic data

Tests must be reproducible when they fail in CI. Record factors affecting outcomes:

- Fixture version or commit SHA.
- Random seed used to generate data.
- Fixed timestamp or injected `Clock`.
- Locale, timezone, currency, and number formatting.
- Event schema version and serialization options.
- Feature flags and application configuration.
- Dependency/emulator/runtime versions.

Avoid sprinkling `Instant.now()` in domain logic when tests require stable results. Inject `Clock` to control time. For randomized data, derive a seed from the test case or accept a seed from CI; on test failure, log the seed so the run can be replayed.

```java
import java.time.Clock;
import java.time.Instant;
import java.time.ZoneOffset;

Clock testClock = Clock.fixed(
        Instant.parse("2026-01-15T10:00:00Z"),
        ZoneOffset.UTC);
```

Avoid relying on ID generation order, returned record order, or message arrival order unless business semantics guarantee them. When ordering is required, specify an explicit sort key in queries or assertions.

## 6. Isolating data in databases

Common isolation approaches:

1. **Dedicated database/schema:** ideal for integration/E2E tests with permission to create and drop schemas.
2. **Dedicated tenant or partition:** fits when multiple test runs share one database; every query must filter by namespace.
3. **Dedicated table/prefix:** used for temporary data or object storage.
4. **Transaction rollback:** suitable for synchronous tests within a single transaction; insufficient for external side effects or asynchronous workers.
5. **Ephemeral database/container:** spun up fresh for the test suite and destroyed afterward.

Never rely on cleanup to compensate for weak isolation. If test runs A and B can read or delete each other's records, a mis-scoped cleanup can corrupt an active run's data.

### Cleanup by testRunId

Every insert in integration tests should carry the namespace. Repository cleanup must use exact conditions, bounded batches, and safe idempotency.

```java
public interface TestDataRepository {
    void deleteByTestRunId(String testRunId);
    long countByTestRunId(String testRunId);
}

public final class TestDataCleanup {
    private final TestDataRepository repository;

    public TestDataCleanup(TestDataRepository repository) {
        this.repository = repository;
    }

    public void cleanup(String testRunId) {
        if (testRunId == null
                || !testRunId.matches("(ci|it)-[A-Za-z0-9-]{1,80}")) {
            throw new IllegalArgumentException("Invalid test run namespace");
        }
        repository.deleteByTestRunId(testRunId);
    }
}
```

This snippet only illustrates the contract. In real implementations, the repository must restrict delete permissions to test tables/schemas, use parameterized queries, paginate/batch deletions, and verify tenant/owner. Prefix checks are not authorization; enforce deletion rights via database roles and resource scopes.

### Using TTLs properly

TTLs are useful for automatically expiring temporary data when active cleanup fails to run. However, in many services TTL is eventual cleanup, not a precision timer. For instance, DynamoDB TTL deletes expired items asynchronously; items may remain present and readable for a window afterward.

Therefore:

- Run active post-test cleanup to keep environments clean promptly.
- Use TTL as a secondary safety net for missed data.
- Never write assertions requiring a record to vanish the exact second its TTL expires.
- Never rely on TTL as an authorization mechanism or to purge sensitive data by a hard deadline.
- When data has relational links, verify deletion order or design appropriate cascade/cleanup jobs.

## 7. Managing data for queues and events

Asynchronous messages have their own lifecycle. A test may finish while messages still sit in a queue or are mid-flight in a consumer. When sharing a queue, stale messages can be picked up by the next test or cleanup can wipe another run's messages.

Principles:

- Provision dedicated queues/topics/event buses or subscriptions per test run whenever feasible.
- If a shared broker is unavoidable, tag messages with `testRunId` and filter consumers by namespace; never rely on filters as a security boundary.
- Use stable event IDs to test duplicates and idempotency.
- Wait for consumer completion via observable state/acks, not fixed `Thread.sleep` calls.
- Cap wait times and, on expiry, log message IDs, correlation IDs, queue depth, and worker status.
- Handle failed messages in DLQs per test run; clean up DLQ items only after confirming they belong to that run.
- Tear down temporary subscriptions, rules, and event source mappings once producers stop sending.

### Never purge a shared queue

Purging an entire SQS queue wipes messages belonging to other tests or workloads and cannot target only a specific `testRunId`. Never call `PurgeQueue` on a shared queue to clean up one test. Use a dedicated queue per test run or a conditional drain consumer. If purging is ever needed, run it strictly on an ephemeral test-owned queue after confirming no other consumers/tests use it.

Similarly, never delete a shared topic, event bus, or subscription just because one test finished. Delete only temporary resources created by the run and leave shared resources untouched.

## 8. Managing object storage and test files

Object storage often holds uploaded files, event payloads, exports, and artifacts. Use a dedicated prefix per run, for example:

```text
test-data/<testRunId>/input/
test-data/<testRunId>/expected/
test-data/<testRunId>/output/
```

Cleanup deletes only the run's prefix. With bucket versioning, deleting the current object creates a delete marker while older versions remain; full deletion requires removing object versions and delete markers per retention policies. With object locks or legal holds, never bypass retention policies just to clean up a test.

If tests create multipart uploads, ensure incomplete uploads are aborted. Use lifecycle rules as automated backstops for multipart uploads or test prefixes where appropriate, without replacing active cleanup when confirming a clean environment.

## 9. Cleaning up cloud resources by ownership boundary

There are two primary strategies:

### Ephemeral stack/project/resource group

Provision a temporary infrastructure unit per test suite or test run, then delete that unit after testing. Examples:

- AWS: dedicated CloudFormation/SAM stack whose name embeds the run ID.
- Azure: dedicated Resource Group per suite or run.
- Google Cloud: dedicated project when isolation demands are high and organizational quotas/workflows allow it.

Pros include cleanup aligned to ownership boundaries and easy detection of orphaned resources. Cons include slower stack creation/deletion, quota consumption, and resources that cannot be provisioned rapidly per test case. Typically provision stacks per integration suite or pipeline job rather than spinning up an entire cloud environment for each unit test.

### Shared test environment with namespacing

Some slow or expensive resources can be shared while data remains strictly namespaced. Examples include a shared test database hosting isolated schemas/tenants, or a dedicated test queue carrying messages tagged with run IDs. Restrict delete permissions by namespace and run a janitor to sweep expired runs.

Never place production resources inside the same cleanup scope as tests. A single command deleting a resource group/stack/project wipes everything inside it; use ephemeral units only where ownership is unambiguous and zero shared resources reside inside.

## 10. AWS: ephemeral stacks, tags, SQS, and storage

With AWS SAM, you can deploy a stack per CI run:

```bash
sam build
sam deploy \
  --stack-name orders-it-ci-4821-attempt-2 \
  --parameter-overrides EnvironmentName=test \
  --no-confirm-changeset
```

After tests finish, delete the stack with:

```bash
sam delete --stack-name orders-it-ci-4821-attempt-2
```

In CI, always pass a unique stack name. Check CloudFormation deletion policies, retain policies, and stateful resources before deleting. `sam delete` does not guarantee that out-of-stack or retained resources vanish automatically.

AWS resources to watch carefully:

- **SQS:** dedicated queue per run; delete after consumers stop and messages are processed or intentionally drained.
- **SNS:** delete run-created subscriptions/topics; never delete shared topics.
- **EventBridge:** delete rules, targets, and temporary event buses in order; archives/replays carry separate retention.
- **S3:** use prefixes; handle versions/delete markers and multipart uploads.
- **DynamoDB:** tag with test run ID, clean up via batch deletes or TTL; TTL is not instantaneous.
- **Lambda:** stack-created functions, layers/versions/aliases, and event source mappings; watch for log groups that may remain depending on configuration.
- **CloudWatch Logs:** configure short retention for tests; delete log groups only when owned by the stack/run and no longer needed for investigation.

Tag resources with `test-run-id`, `owner`, `expires-at`, and stack name whenever the resource type supports tagging. For untaggable or out-of-stack resources, record ARNs/IDs in a manifest.

## 11. Azure and Google Cloud: cleanup by resource group/project

### Azure

A dedicated Resource Group can bundle the Function App, Storage Account, Service Bus namespace, Application Insights, and supporting resources for a test suite. Once tests finish, delete the resource group if every resource inside belongs exclusively to that suite.

If a resource is shared, place it in a separate resource group and put only ephemeral resources in the temporary group. Apply tags such as `testRunId`, `owner`, and `expiresAt` where supported. Never assume deleting a Resource Group removes out-of-group items such as role assignments, DNS records, or referenced external resources.

### Google Cloud

A dedicated project provides strong boundaries for APIs, IAM, billing, and quotas, though creating/deleting projects has its own workflow and latency. Reserve ephemeral projects for test suites or pipelines needing high isolation. For frequent runs, use a dedicated test project with isolated data/queue namespaces.

Apply labels such as `test_run`, `owner`, and `environment` on supported resources. Before deleting a project, verify no resources are shared or exported to other projects. Cloud Storage, Pub/Sub, Cloud Run/Functions, Eventarc, and log sinks have differing lifecycles; manifests and post-cleanup verification remain essential.

## 12. Java/JUnit: managing lifecycle with setup and teardown

JUnit provides `@BeforeEach`, `@AfterEach`, `@BeforeAll`, and `@AfterAll` for managing data and resources. `@AfterEach` works for normal cleanup, yet it cannot run if the JVM is killed, the runner disconnects, or the pipeline is canceled. Therefore, pair in-process cleanup with an external TTL/janitor.

```java
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import java.util.UUID;

class OrderIntegrationTest {
    private String testRunId;
    private TestDataFixture fixture;

    @BeforeEach
    void setUp() {
        testRunId = "ci-" + UUID.randomUUID();
        fixture = new TestDataFixture(testRunId);
        fixture.createCustomerAndInventory();
    }

    @AfterEach
    void tearDown() {
        if (fixture != null) {
            fixture.cleanup();
        }
    }
}
```

This example illustrates the lifecycle. `fixture.cleanup()` must be idempotent, scoped strictly to the test's namespace, and must not throw exceptions that mask the original assertion failure. If cleanup fails, log the test run ID and leftover resources for the janitor to handle.

### Cleanup must never mask the root failure

If a test fails and cleanup also fails, preserve both pieces of information. Attach the cleanup exception as a suppressed exception or log it as a secondary error, never turning a failing test into a passing one. Set timeouts on cleanup so pipelines cannot hang forever.

```java
@Test
void processesOrderAndCleansFixture() throws Exception {
    try (TestFixtureScope ignored = fixture.openScope()) {
        runAssertions();
    }
}
```

`TestFixtureScope` implements `AutoCloseable`, and `close()` runs cleanup scoped to the test run. Java's try-with-resources automatically preserves the assertion exception as the primary failure and attaches any exception thrown by `close()` as suppressed. This prevents cleanup failures from silently turning failures into passes or hiding the original root cause.

## 13. Java: test fixtures with a test run namespace

Create a small context so every repository, event publisher, and resource helper shares the same test run ID:

```java
import java.util.UUID;

public record TestRunContext(String id) {
    public static TestRunContext create() {
        return new TestRunContext("it-" + UUID.randomUUID());
    }

    public String resourceName(String base) {
        return base + "-" + id;
    }

    public String objectPrefix() {
        return "test-data/" + id + "/";
    }
}
```

Parallel tests receive distinct namespaces. If cloud resource names have strict character limits, normalize and truncate the ID while keeping a mapping back to the full test run ID in the manifest.

Fixtures should expose clear actions such as `createOrder`, `publishOrderCreated`, `awaitOrderStatus`, and `cleanup`. Avoid giant `TestUtils` classes capable of wiping arbitrary databases or queues; overly broad helpers invite accidental cleanup mistakes.

## 14. Cleaning up data and resources in dependency order

Cleanup must respect the dependency graph. For an order-flow test:

1. Stop producers or triggers so no new events are generated.
2. Wait for workers to finish or stop temporary event source mappings/consumers as designed.
3. Collect final results, logs, traces, and DLQ items needed for investigation.
4. Delete remaining test messages/events from the run's dedicated queue.
5. Delete database records, storage objects, and temporary files.
6. Delete subscriptions, rules, mappings, and dependent resources.
7. Delete ephemeral functions, queues, topics, storage, and stacks.
8. Verify resources are gone or record items intentionally retained.

Exact ordering depends on the resource type. For example, delete EventBridge targets before rules; stop producers before deleting queues; never drop databases while workers are still writing. Persist a manifest of resource IDs so cleanup does not search blindly.

### Cleanup is an idempotent operation

Cleanup may run multiple times due to CI retries or janitor sweeps. If a resource is already deleted, treat that as success when appropriate. If a resource still exists but does not belong to the test run, cleanup must halt and raise an error.

Never run wildcard deletions such as `DELETE FROM orders` or `aws sqs purge-queue` on shared resources. Always require explicit namespaces and scopes; verify ownership before deleting.

## 15. Asynchronous tests and waiting for completion conditions

An HTTP function may return `202 Accepted` immediately after enqueuing a message. Tests must wait for the worker to finish before asserting database state or running cleanup. Poll on a condition with a deadline rather than using long fixed sleeps.

Example status-polling helper:

```java
import java.time.Duration;
import java.time.Instant;
import java.util.function.Supplier;

public final class Await {
    public static <T> T until(
            Supplier<T> read,
            java.util.function.Predicate<T> condition,
            Duration timeout,
            Duration interval) throws InterruptedException {

        Instant deadline = Instant.now().plus(timeout);
        T last = null;
        while (Instant.now().isBefore(deadline)) {
            last = read.get();
            if (condition.test(last)) {
                return last;
            }
            Thread.sleep(interval.toMillis());
        }
        throw new AssertionError("Condition not met before timeout; last=" + last);
    }

    private Await() {}
}
```

In production test suites, inject `Clock` or use a polling library to control timing and record poll attempts. `Thread.sleep` in this example is merely a short pause between reads; never use it as a substitute for checking state. On timeout, log the correlation ID, test run ID, queue depth, message ID, and function status for diagnosis.

Never clean up immediately after sending a message. First confirm the consumer committed the side effect or routed the message to the DLQ per the scenario under test. If a test intentionally verifies timeouts/retries, cleanup must stop or isolate the worker before deleting related data.

## 16. Testcontainers and emulators

Testcontainers spins up dependencies such as PostgreSQL, Redis, or local brokers in containers for Java integration tests. Containers typically start before the suite and stop afterward; data is isolated using dedicated databases/schemas or dedicated containers.

Emulators/local services help with:

- Testing serialization and application logic.
- Testing queries/repositories against a real matching database engine.
- Testing message contracts, routing logic, or event handlers.
- Accelerating tests executed on every commit.

However, emulators do not prove real cloud IAM/resource policies, managed identities, network routing, quotas, retry semantics, or service-specific edge cases. Maintain a focused integration suite on a test account/project/subscription to verify real behavior.

Never pass production credentials to emulators or local tests. Use dedicated profiles, dummy credentials, and explicit local endpoints; fail fast if a test accidentally points at a production account/resource.

## 17. Cleaning up when CI is canceled or runners fail

`@AfterEach` does not run if the process is killed, the runner loses power, or the job is force-canceled. Therefore, cleanup requires a mechanism outside the test process.

### TTLs and janitor jobs

A scheduled janitor scans for resources tagged `managed-by=integration-test` whose `expires-at` has passed. Before deleting, the janitor verifies:

- The resource resides in an authorized test account/project/subscription.
- An owner and test run ID exist in the manifest or metadata.
- The resource is not marked `retain=true` or holding an active lease renewed by another job.
- The resource does not hold data preserved for incident investigation.
- Expiration has passed a grace period so slow-running jobs are not killed prematurely.

The janitor needs narrow deletion permissions, audit logs, and a dry-run mode. Never grant delete permissions across a production organization just to clean up tests. Start by reporting expired resources, then enable auto-deletion strictly within dedicated accounts/projects.

### Leases/heartbeats for long-running test runs

Test suites can extend `expires-at` while active. The janitor deletes only when the lease expires with no recent heartbeat. Use UTC timestamps and synchronized clocks. Leases do not replace ownership checks; they only distinguish active runs from abandoned ones.

### CI cleanup stage

Pipelines should run a cleanup step whether tests pass or fail. Use your CI provider's `always()`/post-job/finally mechanism. The cleanup stage receives the stack name and manifest from setup and archives logs/diagnostics before deleting resources.

## 18. Resource inventory checklist before deletion

Serverless resources commonly overlooked:

| Category | Examples | What to inspect |
|---|---|---|
| Compute | Lambda, Function App, Cloud Run/Functions | Versions, aliases, revisions, deployment slots, and triggers |
| API | API Gateway routes, Function URLs, HTTP endpoints | Stages, mappings, authorizers, custom domain associations |
| Messaging | SQS, SNS, Pub/Sub, Service Bus, Event Grid | Queues/subscriptions, backlog, DLQs, retention, and policies |
| Event routing | EventBridge rules/buses/archives, Eventarc triggers | Targets, permissions, replays, and event source mappings |
| Storage | S3, Blob Storage, Cloud Storage | Objects, versions, delete markers, multipart uploads, lifecycles |
| Database | DynamoDB, Cosmos DB, Cloud SQL, RDS | Test records, tables/schemas, snapshots, and backup retention |
| Security | IAM roles, service accounts, managed identities, secrets | Role assignments, trust, access policies, secret versions, and keys |
| Observability | Log groups, dashboards, alarms, traces | Retention, subscription filters, metric alarms, and exports |
| Network | Security groups, endpoints, VPC connectors, DNS records | Shared resources, attachments, routes, and private zones |
| Build/test | Artifact buckets, images, temporary registry tags | Artifact retention and image cleanup |

Never delete security/audit logs before investigations finish. Certain resources enforce deletion protection, retention locks, or soft deletion; follow those policies rather than trying to bypass them.

## 19. Safe cleanup for external side effects

Some side effects cannot be erased by deleting test resources:

- Emails/SMS already sent to real recipients.
- Payments already authorized/captured.
- Webhooks already delivered to partners.
- Files already downloaded or copied to external systems.
- Events already consumed by external subscribers.

Use sandbox accounts, test recipients, fake providers, or stub servers. If calling a payment sandbox is mandatory, use the provider's test tokens/cards and confirm no real transactions occur. Attach test-run metadata to requests when supported. For webhooks, deliver to dummy endpoints or allowlisted test hosts.

Never treat database cleanup as a rollback for external side effects. If a test creates reversible external effects, define explicit compensations (void authorization, sandbox refund, token revocation). If irreversible, design tests to use synthetic data and fake destinations exclusively.

## 20. Security and permissions for test data

Test environments are not places to skip security. Test data can contain tokens, synthetic yet valid-looking emails, sandbox secrets, or internal details.

- Use dedicated IAM roles/service accounts for CI testing and cleanup.
- Test runners hold create/delete rights strictly within test accounts/projects/resource groups.
- Separate permissions for running tests from permissions for cleaning shared environments.
- Never allow forked or untrusted-branch test jobs to access cloud secrets.
- Never store production credentials in fixtures, snapshots, or artifacts.
- Encrypt test data and restrict who can read logs/queues/DLQs.
- Mask or strip sensitive data from reports and failure output.
- Audit cleanups and redrives; retain manifests of resource IDs for traceability.
- Block tests if the account ID, project ID, or subscription ID is not on the test allowlist.

Before deleting, verify the target environment against pipeline-provided configuration and a trusted allowlist. Never rely on an `ENV=dev` variable set by test code itself to decide whether resources may be deleted.

## 21. Cost and retention

Test resources can accrue costs even without invocations:

- Queues, topics, event buses, and archives incur request, storage, or retention charges.
- Databases, caches, NATs, private endpoints, and provisioned capacity often bill by lifetime.
- Lambda/function invocations, logs, traces, and metrics multiply with retries.
- Object versions, snapshots, backups, and artifacts retain storage long after tests finish.
- Orphaned resources lacking owners continue consuming quotas or budget.

Set appropriate TTLs/retention on logs, objects, queues, test records, and artifacts. Set budgets/alerts per test account/project; monitor active ephemeral resource counts, oldest resource age, and cleanup failure rates. Measure cost per pipeline run or test suite to uncover unnecessary resource creation.

Never set retention so short that diagnostic evidence vanishes before investigating a test failure. A sound strategy retains diagnostic artifacts intentionally for a brief window and sweeps them on schedule.

## 22. Verifying cleanup

Successful cleanup means more than a delete command returning exit code 0. Verify actual state:

1. Ephemeral resources no longer exist or have entered the deleted state per provider APIs.
2. No test messages remain in queues/DLQs belonging to the finished run.
3. No test records/objects remain outside intentional retention.
4. No unnecessary temporary subscriptions, rules, mappings, or identities linger.
5. The manifest is marked `CLEANED`, or retained resources and reasons are recorded explicitly.
6. Cleanup failures raise alerts or appear in CI reports.

Some deletion APIs are asynchronous; poll status with a timeout. Never report clean immediately upon receiving HTTP 202 from a resource deletion API. Where providers exhibit eventual consistency, verify after a bounded wait and mark `pending` explicitly if the deadline expires.

### Cleanup report

A per-run report can record:

```json
{
  "testRunId": "ci-4821-attempt-2",
  "status": "CLEANED",
  "createdResources": 12,
  "deletedResources": 12,
  "retainedResources": [],
  "failedResources": [],
  "completedAt": "2026-11-17T12:30:00Z"
}
```

Never record secrets or sensitive payloads in manifests. Store resource IDs, owners, creation timestamps, and cleanup outcomes; retain manifests per policy to investigate orphans.

## 23. Implementation checklist

### Test data

- [ ] Use synthetic data or approved fixtures; never copy production PII arbitrarily.
- [ ] Give fixtures explicit names, versions, and business goals.
- [ ] Pin random seeds, clocks, timezones, and configuration for reproducibility.
- [ ] Give each test run a unique namespace propagated across records, events, objects, and logs.
- [ ] Always scope database queries/cleanups to the test run or a dedicated schema.
- [ ] Ensure parallel tests never share mutable fixtures or resources that could delete one another.
- [ ] Treat TTLs strictly as a backup cleanup layer, not a precision deletion deadline.

### Serverless resources

- [ ] Isolate queues/topics/event buses and subscriptions, or filter strictly by namespace.
- [ ] Never purge shared queues or delete shared topics/resources.
- [ ] Drain backlogs, DLQs, retries, and active consumers before cleanup.
- [ ] Handle object prefixes, versioning, delete markers, and multipart uploads.
- [ ] Ensure ephemeral stacks/projects/resource groups contain zero shared resources.
- [ ] Record resource manifests with IDs, owners, `testRunId`, and `expiresAt`.

### Lifecycle and cleanup

- [ ] Scope setup and teardown clearly, keeping cleanup idempotent.
- [ ] Run cleanup on both pass and fail, backed by a janitor for canceled jobs.
- [ ] Use leases/expiries so the janitor never deletes still-active runs.
- [ ] Clean up in dependency order and stop producers before deleting consumers/resources.
- [ ] Route external side effects to sandboxes/fakes or implement explicit compensations.
- [ ] Emit cleanup reports verifying deleted resources or listing retained/failed items.
- [ ] Ensure cleanup failures never mask original test failures.

### Security and cost

- [ ] Restrict CI roles to test environments and run-owned resources.
- [ ] Fail tests fast if the target account/project/subscription is outside the allowlist.
- [ ] Keep production secrets out of fixtures, logs, artifacts, and local settings.
- [ ] Enforce retention on logs, objects, snapshots, and artifacts.
- [ ] Set up budgets/alerts and dashboards for orphaned resources, cleanup failures, and test costs.

Test data management and cleanup are integral to serverless system reliability. Dedicated namespaces let tests run in parallel without collisions; deterministic fixtures make bugs reproducible; idempotent cleanup and janitors handle even canceled CI runs; and manifests plus post-deletion verification catch orphaned resources. For Java functions processing HTTP, messages, and events, manage both data and asynchronous side effects under one cohesive test-run lifecycle while scoping cleanup permissions so tests can never accidentally delete shared or production resources.
