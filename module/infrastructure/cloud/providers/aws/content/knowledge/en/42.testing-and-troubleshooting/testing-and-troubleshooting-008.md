# Diagnosing 4xx and 5xx Errors Across CloudFront, ALB, and API Gateway

When an API or website returns HTTP 4xx/5xx, the status code alone only tells you the request failed in some manner. It does not reveal which layer generated the error. The exact same 502 could mean CloudFront failed the TLS handshake with its origin, Application Load Balancer (ALB) received a TCP reset from a target, API Gateway could not parse a Lambda proxy response, or the application itself returned 502. A 403 could come from AWS WAF, a CloudFront signed URL, S3 permissions, an API Gateway authorizer, a listener rule, or the application.

Accurate diagnosis requires tracing the request along its actual topology, identifying the first layer that emitted the error, and correlating status codes with access logs, metrics, request IDs, target health, and application logs. Never increase timeouts, open security groups, or disable WAF simply upon seeing 502/504.

This lesson explains how to read errors across three common components: Amazon CloudFront, Application Load Balancer, and Amazon API Gateway. These components can be combined in various topologies; not every request passes through all three. The focus is on diagnostic workflows, log examples, common causes, remediation, and post-fix verification.

## 1. Learning Objectives

After this lesson, learners will be able to:

- Distinguish 4xx errors generated by clients, authentication, authorization, WAF, routing, and applications.
- Distinguish 5xx errors generated by edge, load balancer, integration, target, and application layers.
- Recognize topologies such as CloudFront → ALB, CloudFront → API Gateway, and API Gateway → VPC Link → ALB/NLB.
- Use request IDs/correlation IDs to join logs across CloudFront, ALB, API Gateway, and backends.
- Read CloudFront standard logs and interpret `x-edge-result-type`, `x-edge-detailed-result-type`, and `x-edge-request-id`.
- Distinguish `elb_status_code` from `target_status_code` in ALB access logs.
- Use ALB CloudWatch metrics to separate load balancer errors from target errors.
- Enable and read API Gateway access logs, execution logs, and integration latency.
- Diagnose 400, 401, 403, 404, 429, 500, 502, 503, and 504 errors.
- Inspect DNS, TLS, listeners/rules, target health, security groups, NACLs, and timeout budgets.
- Build runbooks, alarms, regression tests, and rollback procedures.

## 2. Understand Topology Before Investigating

CloudFront, ALB, and API Gateway do not always sit in a fixed sequence along a request path. Inspect the actual architecture and determine each component's origin/integration before reading logs.

### 2.1 CloudFront → ALB → application

    Browser / Mobile client
             |
          CloudFront
             |
          HTTPS origin
             |
            ALB
             |
       Target group
        /    |     \
      ECS   EC2    EKS ingress
             |
        Application

CloudFront acts as an edge cache/reverse proxy. ALB routes requests to targets via listener rules and target groups. 4xx/5xx responses can be generated by CloudFront, AWS WAF, ALB, or the application.

### 2.2 CloudFront → API Gateway → integration

    Browser / Mobile client
             |
          CloudFront
             |
        API Gateway
             |
      Lambda / HTTP integration
             |
       Application / service

API Gateway authenticates, authorizes, validates requests, and invokes integrations. CloudFront can cache responses per cache behavior; for dynamic APIs, check cache policies, origin request policies, and forwarded methods.

### 2.3 API Gateway → VPC Link → ALB/NLB → service

    Client / CloudFront
             |
        API Gateway
             |
          VPC Link
             |
          ALB/NLB
             |
       ECS / EKS / EC2
             |
        Application

For private integrations, API Gateway uses a VPC Link to reach resources inside a VPC. VPC Link V2 supports ALB and NLB for REST APIs; HTTP APIs also support ALB, NLB, and AWS Cloud Map. VPC Link V1 is legacy for REST APIs and supports only NLB. In this topology, API Gateway and ALB maintain separate logs; failures can happen at the integration layer before reaching targets.

### 2.4 First Rules

1. Identify the URL called by the client and domain mapping.
2. Identify whether a CloudFront distribution/cache behavior handles that path.
3. Identify the actual CloudFront origin: ALB, API Gateway, S3, or custom origin.
4. If API Gateway is present, identify the API type (REST, HTTP, WebSocket), stage, route/resource, and integration type.
5. If ALB is present, identify the listener, rules, target group, and target type.
6. Record the request ID, UTC timestamp, method, path, status, and response headers.

Do not assume every error visible in a browser came from the service closest to the browser. The edge may serve a cached error from the origin or replace the response body with a custom error page.

## 3. What Do HTTP 4xx and 5xx Tell You?

| Class | General Meaning | Examples |
|---|---|---|
| 4xx | Request rejected due to client request, identity, permissions, policy, or resource | 400, 401, 403, 404, 405, 409, 413, 429 |
| 5xx | Gateway/server/integration failed to complete the request | 500, 502, 503, 504 |

### 3.1 4xx Is Not Always a User Error

A 403 may stem from a bad policy, missing IAM role permissions, a WAF false positive, an expired CloudFront signed cookie, or a misconfigured API Gateway authorizer. A 404 may result from path mapping, stage configuration, listener rules, or a deployment missing a route. Therefore, do not tell users to retry if the root cause is system misconfiguration.

### 3.2 5xx Is Not Always an Application Error

ALB can return 502 when a target resets the connection, CloudFront can return 502 when a TLS handshake fails, and API Gateway can return 502 when a Lambda proxy returns a malformed response. A 504 can occur when one layer times out before downstream layers respond.

### 3.3 One Status Code Can Have Multiple Sources

HTTP status is a contract between layers. Each gateway can:

- Generate a response directly.
- Forward a response from an origin/target.
- Map an integration error to a different status.
- Replace the body with a custom error page.
- Cache error responses for a period.

Look for log fields identifying which layer emitted the response instead of guessing from the status code.

## 4. General Diagnostic Workflow

### 4.1 Gathering Evidence

Before altering configuration, collect:

- UTC timestamp and error window.
- Request method, host, path, query, and content type.
- HTTP status, response body, and response headers.
- Request/correlation IDs from the client and each gateway.
- CloudFront distribution ID/cache behavior.
- ALB ARN, listener, target group, and target IP/port if available.
- API ID, stage, route/resource, and integration.
- Recent changes: deployments, certificates, DNS, WAF rules, security groups, timeouts, scaling, or policies.

Never include access tokens, cookies, API keys, personal data, or sensitive bodies in shared tickets or logs.

### 4.2 Isolating by Layer

    Client receives 4xx/5xx
             |
       Inspect response headers
             |
       Is CloudFront present?
          /       \
        Yes        No
        |            |
   CloudFront log   Gateway/ALB log
        |
   Did origin request happen?
       /       \
     Yes        No
     |            |
 Origin logs   WAF/cache/function/
     |         edge configuration
     |
   ALB or API Gateway?
       /              \
     ALB              API Gateway
      |                   |
 ELB vs target        Gateway vs integration
      |                   |
 Target/app logs      Backend/Lambda logs

This diagram is a mental model; real topologies may reorder or omit some components.

### 4.3 Controlled Reproduction

- Use the exact method, path, headers, and body of the failing request.
- Compare requests traversing CloudFront against requests calling the origin directly in an authorized environment.
- Compare across Regions/AZs, tenants, identities, user-agents, and payload sizes.
- Use a fresh request ID per attempt while preserving a shared correlation ID to tie retries together.
- Test one change at a time and record outcomes.

Never bypass WAF, authentication, or network controls in production for a "quick test." Use a test environment or an approved endpoint.

### 4.4 Pinpointing the First Layer Generating the Error

A request can traverse multiple gateways. Examples:

- CloudFront log records 403, no origin request occurred, and WAF log shows `BLOCK`: failure is at WAF/edge.
- CloudFront log records 502, ALB has no matching access log: inspect CloudFront-to-origin DNS/TLS/networking.
- ALB log shows `elb_status_code=502`, `target_status_code=-`: ALB generated the error before receiving a valid response from a target.
- ALB log shows `elb_status_code=500`, `target_status_code=500`: target returned 500 and ALB forwarded it.
- API Gateway log shows `INTEGRATION_TIMEOUT`: integration/time budget issue.
- API Gateway shows status 502 yet zero backend invocations: check mapping, permissions, and the integration path.

The absence of logs is not absolute proof a request never reached that layer: logging may be disabled, or log delivery may be delayed or best-effort. Correlate with metrics, traces, and application evidence.

## 5. Diagnosing Errors at Amazon CloudFront

CloudFront receives viewer requests, applies cache behaviors, viewer/origin request policies, function associations, WAF, and distribution rules; then it either returns a cache hit or calls the origin. Thus, determine whether the request reached the origin or was handled at the edge.

### 5.1 Signals to Read

| Header/Log Field | Meaning | Used For |
|---|---|---|
| HTTP response status | Code returned to viewer | Initial classification |
| `X-Cache` | Typically shows Hit/Miss/Error from cloudfront | Identifying cache/edge errors |
| `Via` | Shows response traversed CloudFront | Confirming edge path |
| `X-Amz-Cf-Id` | CloudFront request identifier | Joining response to access logs |
| `sc-status` | Status sent to viewer in standard logs | Finding failed requests |
| `x-edge-result-type` | Final processing outcome | Hit, Miss, Error, CapacityExceeded... |
| `x-edge-response-result-type` | Classification right before returning response | Comparing against final result |
| `x-edge-detailed-result-type` | Deeper detail when Error occurs | Distinguishing origin, viewer, internal errors |
| `x-edge-request-id` | Request ID, also appears in `X-Amz-Cf-Id` | Correlation |
| `time-taken` / `time-to-first-byte` | Processing/first-byte timing | Separating slow origin vs. slow viewer |

CloudFront standard logging is optional and has delivery latency. Logs may be written per edge location; one time window can span multiple files. Do not treat logs as an exact accounting system.

### 5.2 CloudFront 400 Bad Request

Possible causes:

- Invalid request headers, URI, or method.
- `Host` header or path mismatches origin behavior.
- Headers/queries/cookies forwarded improperly or exceeding limits.
- Origin rejects the request due to `Host`, content type, or request signature.
- AWS WAF or edge function modifies the request improperly.

Check method, `Host`, URI encoding, content length, header sizes, query strings, cookie forwarding, and WAF logs. Compare a valid request against the failing request under the same behavior.

### 5.3 CloudFront 401/403

Common causes:

- CloudFront signed URL/signed cookie expired, wrong policy, or invalid signature.
- Geo restriction denies the viewer.
- AWS WAF blocks the request.
- S3 origin access control/origin access identity or bucket policy is misconfigured.
- Origin returns `AccessDenied`, API Gateway authorizer denies, or application returns 403.
- Origin request policy fails to forward headers/cookies needed for authorization.

Distinguish edge 403 from origin 403. Inspect WAF sampled requests/logs, CloudFront Functions/Lambda@Edge, origin logs, and S3/API access permissions. For S3 origins, verify OAC, bucket policy, object key, and KMS key policy.

### 5.4 CloudFront 404 Not Found

Check:

- Does the path pattern/cache behavior select the right origin?
- Does the origin path add or strip a prefix?
- Are API base path mapping, stage, or routes accurate?
- Is the object key case-sensitive?
- Does the deployed application include the route/resource?
- Is a 404 error cached at the edge?

If the origin is fixed yet viewers still receive a stale 404, check error caching minimum TTL and cache policies. Invalidation clears cached entries only; it does not fix missing routes or objects at the origin.

### 5.5 CloudFront 502 Bad Gateway

502 typically means CloudFront could not connect to the origin or received an invalid response. Cause categories:

| Category | Symptom | What to Check |
|---|---|---|
| DNS | `NonS3OriginDnsError`, origin domain fails to resolve | DNS records, authoritative NS/SOA, resolvers |
| TLS certificate | Certificate expired/self-signed/invalid, hostname mismatch, incomplete chain | SAN/CN, chain, expiry, SNI |
| TLS protocol/cipher | Handshake mismatch | Origin TLS policy/protocols/ciphers |
| Port/network | Origin not listening on port, firewall blocking | Origin port, security groups/NACLs/firewalls |
| Invalid response | Malformed headers/status/response | Web server/application response |
| Edge function | Lambda@Edge/CloudFront Function validation error | Function logs, response schema, read-only headers |
| Origin service | ALB/API Gateway itself returned 502 | Request IDs and origin-layer logs |

For custom HTTPS origins, the certificate must match the origin domain or `Host` header CloudFront uses when connecting. Check SNI and `Host` forwarding; a certificate can be valid for the viewer domain yet invalid for the origin domain.

Diagnostic commands from an authorized environment:

    nslookup origin.example.com
    dig origin.example.com A
    openssl s_client -connect origin.example.com:443 -servername origin.example.com
    curl -sv https://origin.example.com/health

Test DNS/TLS from the public Internet when investigating custom public origins because CloudFront resolves and connects over public configuration. For VPC origins, inspect private connectivity and appropriate security settings.

### 5.6 CloudFront 503 Service Unavailable

Distinguish:

- CloudFront capacity/quota: log result type may be `CapacityExceeded` or `LimitExceeded`.
- Origin returns 503 due to insufficient capacity or maintenance.
- ALB returns 503 due to zero available targets.
- API Gateway/backend returns 503 due to integration unavailable.
- WAF custom responses can return custom status codes.

Correlate CloudFront result types with origin logs, ALB ELB/target metrics, and API Gateway 5XX metrics. If errors occur on only one path/cache behavior, check origin mappings; if across all paths, examine edge/origin capacity and service health.

### 5.7 CloudFront 504 Gateway Timeout

CloudFront can time out when:

- It cannot establish a connection to the origin.
- The origin fails to return the first byte within the origin response timeout.
- The origin starts responding then pauses data transfer too long.
- The origin/API Gateway/ALB has a shorter timeout of its own.
- The backend is saturated, dependencies are slow, or connection pools are exhausted.

Check Origin Connection Timeout, Connection Attempts, and Origin Response Timeout. For GET/HEAD, CloudFront may retry connections per configuration; for DELETE/OPTIONS/PATCH/PUT/POST, retry behavior differs and clients may have to retry. Never raise timeouts before checking backend latency and capacity.

### 5.8 Error Caching and Stale Responses

CloudFront can cache certain origin errors. Per current documentation, statuses 404, 414, 500, 501, 502, 503, and 504 are cacheable by default. Statuses 400, 403, 405, 412, and 415 are cached only when the origin returns `Cache-Control` `max-age` or `s-maxage`. The `CachingDisabled` managed policy does not cache these statuses/custom error pages.

If the origin recovers yet viewers still see errors:

1. Check response headers and `X-Cache`.
2. Check Error Caching Minimum TTL.
3. Check custom error pages and error page cache behavior.
4. Check origin `Cache-Control`.
5. Invalidate only after confirming the error response is cached and understanding invalidation scope.

CloudFront can continue serving stale objects when the origin returns 5xx if the object remains in edge cache and stale-serving conditions apply. This improves availability yet means viewers may receive outdated content while the origin is failing.

## 6. Diagnosing Errors at Application Load Balancer

ALB can generate responses directly or forward responses from targets. The most critical evidence in access logs is the status pair:

- `elb_status_code`: status generated by the load balancer, fixed-response rule, or AWS WAF custom response.
- `target_status_code`: status returned by the target; populated only when ALB connected to a target and the target sent a response.

If `target_status_code` is a hyphen (`-`), no HTTP response from a target was recorded. Also inspect `target:port`, `actions_executed`, `error_reason`, `request_processing_time`, `target_processing_time`, and `response_processing_time`.

### 6.1 Enabling and Reading ALB Access Logs

ALB access logs are disabled by default. They can be delivered to S3 via log delivery settings; AWS also provides enhanced logging options via CloudWatch Logs/Firehose/S3 in the console Integrations tab. Access logs are best-effort, can arrive delayed, and should not be used for strict accounting.

Useful fields:

| Field | Meaning |
|---|---|
| `type`/`time` | Protocol and response timestamp |
| `client:port` | Direct client or proxy in front of ALB |
| `target:port` | Target that handled the request; hyphen if not dispatched |
| `request` | Method, URL, and protocol |
| `request_processing_time` | Time ALB spent receiving/preparing the request |
| `target_processing_time` | Time ALB waited for the target to respond |
| `response_processing_time` | Time ALB spent processing response before sending to client |
| `elb_status_code` | Status generated by ALB/WAF/fixed response |
| `target_status_code` | Status from target |
| `actions_executed` | `forward`, `redirect`, `fixed-response`, `authenticate`, `waf`... |
| `error_reason` | Reason for error in supported cases |
| `trace_id` | `X-Amzn-Trace-Id` used to correlate traces |

### 6.2 Separating ALB Errors from Target Errors via Metrics

| CloudWatch Metric | Meaning |
|---|---|
| `HTTPCode_ELB_4XX_Count` | 4xx generated by ALB |
| `HTTPCode_ELB_5XX_Count` | 5xx generated by ALB |
| `HTTPCode_Target_4XX_Count` | 4xx returned by targets |
| `HTTPCode_Target_5XX_Count` | 5xx returned by targets |
| `HealthyHostCount` | Count of healthy targets |
| `UnHealthyHostCount` | Count of unhealthy targets |
| `TargetResponseTime` | Target response latency |
| `TargetConnectionErrorCount` | Connection errors from ALB to targets |
| `RejectedConnectionCount` | Connections rejected by ALB due to capacity/connection limits |

ELB and Target metrics are tracked separately. If `HTTPCode_Target_5XX_Count` spikes, check application logs and target health. If `HTTPCode_ELB_5XX_Count` spikes, inspect ALB access logs, target registration, security groups, connections, and timeouts.

### 6.3 ALB 400 Bad Request

Possible causes:

- Invalid or missing request line/headers.
- Invalid `Content-Length`/`Transfer-Encoding`.
- Client sent oversized headers or an overly long URI.
- Unsupported HTTP protocol/version.
- Desync mitigation classified the request as ambiguous/severe.

Inspect the raw request, headers, body size, protocol, and `classification_reason` in access logs. If only one client/proxy fails, compare headers injected by that proxy.

If payload exceeds limits or the URI is too long, ALB can return `413 Payload Too Large` or `414 URI Too Long`; read the actual status and request size instead of lumping everything into 400.

### 6.4 ALB 401/403

Possible causes:

- Listener rule uses an authenticate action with an invalid session/token.
- AWS WAF blocks the request (default is usually 403 or a custom response).
- Fixed-response action returns 401/403.
- Target application returns 401/403.

Use `actions_executed` and `target_status_code` to differentiate. If `actions_executed` includes `waf` and `target:port` is `-`, check WAF logs/rule matches. If `target_status_code=403`, inspect application authorization.

### 6.5 ALB 404 Not Found

ALB does not provide a single default routing 404 for all cases. 404 typically originates from the target/application or a fixed-response listener rule. Check:

- Host/path conditions on listener rules.
- Rule priorities and default actions.
- Rewrite/redirect transforms if configured.
- Target application routes and deployment versions.
- Target group/port mappings.

If the ALB access log shows `target_status_code=404`, the target returned 404. If `target_status_code` is absent and the action is `fixed-response`, the listener rule generated it.

### 6.6 ALB 502 Bad Gateway

Common causes:

- Target sent a TCP RST when ALB initiated a connection.
- Target closed the connection with RST/FIN while ALB had an in-flight request.
- Malformed response or invalid/oversized headers.
- Target deregistered while a long request was running; insufficient deregistration delay.
- TLS handshake failed between ALB and an HTTPS target.
- Lambda target returned an invalid response, timed out, or was throttled.

Check:

1. Whether `elb_status_code=502` and whether `target_status_code` is populated.
2. `target:port` and target group health.
3. Whether application logs show the request arrived.
4. Whether target keep-alive is shorter than ALB idle timeout.
5. Whether target response headers exceed limits.
6. Whether target group protocol/port/certificate are correct.
7. Deregistration delay and deployment draining behavior.

If `target_status_code` is a hyphen (`-`), investigate connections/TLS/target resets before modifying business logic.

### 6.7 ALB 503 Service Unavailable

ALB can return 503 when a target group has no registered targets or all targets are in the `unused` state. Check:

- Does the target group have registered targets?
- Are targets in `healthy`/`initial`/`draining`/`unused` state?
- Are health check path, port, protocol, and matcher accurate?
- Do ECS/EKS/Auto Scaling have enough tasks/pods/instances?
- Does deployment deregister all old targets before new ones become healthy?
- Does the listener rule forward to the right target group?

Inspect `HealthyHostCount`, `UnHealthyHostCount`, target health reasons, and deployment events. If target count drops to zero during rollouts, adjust deployment minimum healthy percentage, readiness/health checks, and capacity.

### 6.8 ALB 504 Gateway Timeout

Common causes:

- ALB could not connect to the target within connection timeout.
- Target accepted the connection yet failed to respond before idle timeout.
- Network ACL blocks return traffic from targets to ALB on ephemeral ports `1024–65535`.
- Target returned a `Content-Length` larger than the actual body, leaving ALB waiting for missing bytes.
- Lambda target failed to respond within allowed time.

Correlate `request_processing_time`, `target_processing_time`, and `response_processing_time`. If `target_processing_time` approaches idle timeout, inspect databases, thread pools, locks, dependencies, and queues. If no target connection succeeded, check routes, SGs, NACLs, ports, and listener protocols.

### 6.9 Verifying Target Health

Health checks are separate requests, not exact replicas of user requests. Verify:

- Health check path returns the expected status code matcher.
- Application binds to `0.0.0.0`/private interface rather than only `localhost`.
- Security groups allow traffic from the ALB security group to the target port.
- Startup grace/readiness periods are sufficient.
- Health endpoints do not over-depend on downstream services if merely verifying process liveness.
- Target deregistration delay accommodates long-running requests.

A healthy target can still return 500 for a specific route; passing health checks proves only that the health endpoint satisfies configured criteria.

## 7. Diagnosing Errors at Amazon API Gateway

API Gateway can emit errors before calling an integration or forward errors from the integration. REST API, HTTP API, and WebSocket API differ in logging capabilities, response types, and context variables; know the API type and stage when reading logs.

### 7.1 Distinguishing Gateway Errors from Integration Errors

| Category | Examples | Diagnostic Focus |
|---|---|---|
| Request validation | `400 BAD_REQUEST_BODY`/`PARAMETERS` | Request models, required parameters, validators |
| Authentication/authorization | 401/403 | Authorizers, JWT/Cognito/IAM, resource policies, API keys |
| Route/resource | `403 MISSING_AUTHENTICATION_TOKEN` or 404 | Methods, routes, stages, base path mappings |
| Throttling/quota | `429 THROTTLED`/`QUOTA_EXCEEDED` | Account, stage, method, usage plans |
| Integration response | 4xx/5xx from backend | Integration status and backend logs |
| Integration failure | 5xx/504 | Unavailable endpoints, permissions, networking, response mapping |
| Integration timeout | 504 | Integration latency, timeout settings, and backend runtime |
| API configuration | 500 | Integration URIs, mapping templates, authorizer configs, deployments |

Status codes can be customized via GatewayResponse or integration response mappings. Inspect response types, gateway logs, and integration status rather than only the returned body.

### 7.2 API Gateway 400 Bad Request

Common causes:

- Request validator rejects query/path/header parameters.
- Body fails JSON schema/model validation.
- Mapping template or request transformation mishandles inputs.

Check methods/routes, request models, required fields, content types, binary media types, and mapping templates. Compare the actual payload against a valid request.

In REST APIs, oversized requests can return `413 REQUEST_TOO_LARGE`; unsupported media types can return `415 UNSUPPORTED_MEDIA_TYPE`. Distinguish these response types from 400 validation errors.

### 7.3 API Gateway 401 Unauthorized

Check:

- Is the token expired, wrong issuer/audience, or invalid signature?
- Does the JWT/Cognito authorizer configure the right identity source?
- Does the Lambda authorizer return a valid policy/context?
- Is an IAM SigV4 request signed for the right service/Region/path?
- Did custom domains, stages, or authorization types change?

Never log raw bearer tokens. Log request IDs, authorizer status, error categories, and anonymized principals.

### 7.4 API Gateway 403 Forbidden

REST API Gateway has multiple 403 response types:

| Gateway Response Type | Common Cause |
|---|---|
| `ACCESS_DENIED` | Authorizer, Cognito/JWT scope, or resource policy denied |
| `INVALID_API_KEY` | API key invalid or missing |
| `INVALID_SIGNATURE` | Invalid AWS Signature |
| `EXPIRED_TOKEN` | Expired AWS token |
| `MISSING_AUTHENTICATION_TOKEN` | Method/resource does not exist or request hit wrong path/method |
| `WAF_FILTERED` | AWS WAF blocked the request |

403 does not always mean an expired token. Check API Gateway access logs, authorizer logs, WAF logs, resource policies, API keys/usage plans, and custom domain mappings.

### 7.5 API Gateway 404 and `MISSING_AUTHENTICATION_TOKEN`

REST APIs can return `403 MISSING_AUTHENTICATION_TOKEN` when clients call an unsupported method or resource. HTTP APIs typically return route-not-found per their own behavior. Verify:

- API ID and stage.
- Resource path/route key.
- HTTP method.
- Custom domain API mapping/base path.
- Whether the latest deployment updated the stage.
- Whether CloudFront origin paths or API mappings add/strip prefixes.

Do not modify authorizers when the actual root cause is a path/method mismatch.

### 7.6 API Gateway 429 Too Many Requests

429 can stem from throttling or quotas:

- Account-level throttle quotas.
- Stage/method/route throttling.
- Usage plan quotas for API keys (REST API).
- Backend or integration returning 429 directly.

Correlate API Gateway metrics, usage plans, stage settings, integration logs, and backend throttling. Use exponential backoff with jitter, respect `Retry-After` if provided, and cap concurrency. Never retry aggressively on the client, as it worsens throttling.

### 7.7 API Gateway 500 Internal Server Error

Response types can include `API_CONFIGURATION_ERROR`, `AUTHORIZER_CONFIGURATION_ERROR`, `AUTHORIZER_FAILURE`, or `DEFAULT_5XX`. Check:

- Is the integration URI/endpoint valid?
- Does the API deployment include the latest configuration?
- Are there mapping template errors?
- Did the authorizer time out or throw an exception?
- Are IAM permissions allowing API Gateway to invoke Lambda/integrations correct?
- Did the backend throw an exception or return an error response?

Separate gateway logs from integration logs. If the backend never received the request, investigate API configuration/permissions/networking; if it did, use the request ID to find the stack trace.

### 7.8 API Gateway 502 Bad Gateway

With Lambda proxy integration, Lambda must return a schema-compliant response. Example:

    {
      "statusCode": 200,
      "headers": {
        "Content-Type": "application/json"
      },
      "body": "{\"message\":\"ok\"}",
      "isBase64Encoded": false
    }

If the function returns an improperly formatted object, a non-string body where required, non-serializable JSON, or throws an exception, API Gateway may return 502. With HTTP/custom integrations, invalid responses or bad mappings can also produce 502.

Check:

1. Did a Lambda invocation occur?
2. Did Lambda hit an exception, timeout, throttle, or out-of-memory error?
3. Do `statusCode`, `headers`, `body`, and `isBase64Encoded` match the required format?
4. Does the body serialize properly with valid headers/content type?
5. Do mapping templates produce invalid responses?
6. For VPC Links, are endpoints/target groups/listeners healthy and reachable?

Do not confuse an intentional HTTP 502 returned by Lambda with a 502 emitted because API Gateway could not parse the response. Inspect integration status, integration error, and Lambda logs.

### 7.9 API Gateway 503 Service Unavailable

503 typically signals an unavailable or overloaded integration/backend. Check:

- Backend capacity, connection pools, and deployments/maintenance.
- VPC Link status, subnets/ENIs, and security groups.
- ALB/NLB target health when using private integrations.
- Lambda concurrency/throttling when integrating with Lambda.
- Service discovery/DNS when using HTTP integrations.
- Integration errors and backend response statuses.

If the backend is temporarily unavailable, return 503 intentionally and instruct clients to retry with backoff. If 503 stems from gateway/integration networking, fix connectivity/capacity before sending heavy retry traffic.

### 7.10 API Gateway 504 Gateway Timeout

504 occurs when an integration request exceeds the configured maximum integration timeout. For REST APIs, the default is typically 29 seconds. AWS allows quota increase requests for Regional and private REST APIs; raising it may require lowering account-level throttle quotas. After increasing the quota, update the timeout on the integration and redeploy the API for changes to take effect.

For HTTP APIs or WebSocket APIs, check timeout limits specific to that API type and integration; do not apply REST API numbers universally.

Workflow:

1. Inspect API Gateway `IntegrationLatency`/`Latency` and access logs.
2. Verify whether the integration was invoked.
3. For Lambda, compare Lambda Duration against timeout.
4. For HTTP/VPC Link, measure connect time, time to first byte, and backend duration.
5. Check ALB `target_processing_time`, target health, and database/dependency latency.
6. Offload non-essential post-processing from synchronous requests.
7. If work is long-running, switch to an asynchronous job pattern: return `202` + job ID, process in the background, and expose a status endpoint.

### 7.11 REST API Execution Logs and Access Logs

REST APIs support execution logging and access logging:

- Execution logs detail request execution, mapping, and integration errors; enable `ERROR` or `INFO` as needed.
- Access logs write one structured record per request using chosen context variables.
- Data tracing can log sensitive payloads; avoid enabling it broadly on production APIs without strict controls.

HTTP APIs support access logging via CloudWatch Logs; execution logging capabilities and context fields differ from REST APIs. Consult documentation for the exact API type.

### 7.12 Recommended Access Log Format

Example JSON format for REST APIs; context variables must be specified as literal strings when configuring access logs:

    {
      "requestId": "$context.requestId",
      "extendedRequestId": "$context.extendedRequestId",
      "requestTime": "$context.requestTime",
      "httpMethod": "$context.httpMethod",
      "resourcePath": "$context.resourcePath",
      "status": "$context.status",
      "responseLatency": "$context.responseLatency",
      "integrationStatus": "$context.integration.status",
      "integrationLatency": "$context.integration.latency",
      "integrationError": "$context.integration.error",
      "authorizerStatus": "$context.authorizer.status",
      "wafStatus": "$context.waf.status"
    }

Avoid logging `Authorization` headers, cookies, API keys, request bodies, or sensitive data in access logs. `extendedRequestId` is generated by API Gateway; `requestId` can be client-supplied in some scenarios, so rely on `extendedRequestId` as the gateway-controlled ID.

### 7.13 API Gateway CloudWatch Metrics

Key metrics:

| Metric | Meaning |
|---|---|
| `Count` | Total requests |
| `4XXError` | Count of 4xx errors |
| `5XXError` | Count of 5xx errors |
| `Latency` | Time from when API Gateway receives a request to when it returns a response |
| `IntegrationLatency` | Time from when the gateway sends a request to the backend to when it receives a response |

If `Latency` is high while `IntegrationLatency` is low, inspect gateway overhead, authorization, mapping, or network paths. If `IntegrationLatency` dominates `Latency`, investigate the backend. Enable detailed metrics per method/resource/stage when deeper analysis is needed; detailed metrics may incur charges.

## 8. Correlation IDs and Multi-Layer Tracing

When requests cross multiple gateways, each service maintains its own request identifier. Do not expect a single ID to appear automatically in every log. Retain native IDs and propagate an application correlation ID via allowed headers.

### 8.1 Common Identifiers

| Component | ID/Header | Purpose |
|---|---|---|
| CloudFront | `x-amz-cf-id` / `x-edge-request-id` | Identifies request at the edge |
| ALB | `X-Amzn-Trace-Id` / `trace_id` in access logs | Links requests to traces |
| API Gateway REST | `extendedRequestId` / `requestId` | Locates access/execution logs |
| API Gateway | `x-amzn-RequestId` or `x-amz-apigw-id` when returned | Helps clients record gateway requests |
| AWS X-Ray | Trace ID | Links segments/subsegments across traced services |
| Application | `X-Correlation-ID` generated/maintained by app | Joins logs across services and workflows |

Do not merge these IDs into a single value. Log each ID separately in structured logs so you can search requests at every layer.

### 8.2 Propagating Correlation IDs

An application gateway can generate a correlation ID if the client omits one. If accepting IDs from clients, validate character set and length, enforce caps, and never treat it as an identity or authorization token. Also log AWS native request IDs for direct native log lookups.

Example application log:

    {
      "timestamp": "2026-11-20T08:15:30.123Z",
      "level": "ERROR",
      "service": "orders-api",
      "correlation_id": "req-7f4d3c",
      "cloudfront_request_id": "opaque-edge-id",
      "api_gateway_extended_request_id": "gateway-id",
      "alb_trace_id": "Root=1-...",
      "route": "POST /orders",
      "status": 500,
      "error_code": "DB_POOL_EXHAUSTED"
    }

This illustrates structure; omit payloads, tokens, or PII unless strictly required. Across distributed services, preserve correlation IDs in message attributes, workflow inputs, and downstream requests.

### 8.3 X-Ray and Service Maps

AWS X-Ray visualizes segments/subsegments and latency across instrumented components. API Gateway REST APIs support X-Ray tracing per stage configuration; Lambda, application SDKs, and certain AWS services emit related segments.

X-Ray does not automatically replace access logs. Use traces for timing and dependency graphs; use access logs for request/status/target facts; use application logs for stack traces and business errors. Check sampling rates because not every request is traced.

## 9. Timeout Budgets Across CloudFront, API Gateway, ALB, and Backends

Many 504 errors happen because an outer layer's timeout is shorter than a valid inner layer's processing time. Design timeouts along the actual request path.

### 9.1 Principles

For synchronous requests, each inner step's timeout should be shorter than its caller's deadline, leaving margin for networking, serialization, and response transfer. Example:

    Database/dependency timeout
              <
       Application deadline
              <
       ALB target idle budget
              <
       API Gateway integration timeout
              <
       CloudFront origin response timeout
              <
       Client deadline

This ordering illustrates one specific topology, not a universal default for every system. Omit any layer not present in your topology. For streaming responses, timeouts may apply to idle gaps between bytes rather than total request duration.

### 9.2 Example: CloudFront → API Gateway → ALB → Service

Suppose a service needs up to 8 seconds to finish a request:

- Database query deadline: 5 seconds.
- Application deadline: 10 seconds.
- ALB idle timeout: long enough for the application to finish and send the response.
- API Gateway integration timeout: longer than valid ALB/backend execution time.
- CloudFront origin response timeout: longer than API Gateway timeout plus response transfer.
- Client timeout: longer than CloudFront timeout.

These numbers illustrate sizing, not AWS defaults. Measure p95/p99 and budget margins around SLAs. For REST APIs, default integration timeout is typically 29 seconds; if requesting a quota increase for Regional/private APIs, review account throttle quota trade-offs and redeploy the API.

### 9.3 When Should You Increase Timeouts?

Increase timeouts only after confirming:

- The backend genuinely needs longer processing time and has capacity.
- No deadlocks, connection pool exhaustion, or abnormally slow dependencies exist.
- Clients and all outer gateways have matching timeouts.
- Workers/threads/concurrency can sustain longer-held requests.
- Requests can retry safely if connections drop.

If tasks take several minutes, switch to an asynchronous pattern: accept the request, enqueue a job, return `202 Accepted` + job ID, process in the background, and expose a status/result API.

### 9.4 Retries and Side Effects

A timeout does not prove the backend failed to act. For instance, `POST /payments` may have committed the transaction while the response was lost at CloudFront/API Gateway. Blind client retries can create duplicate transactions.

For `POST`/`PUT` requests with side effects:

- Use idempotency keys per business request.
- Persist results keyed by idempotency key before returning responses.
- Retry only when permitted by the API contract.
- Use exponential backoff and jitter for transient/429/503 errors.
- Never retry 4xx validation/authentication errors.
- Cap retry attempts and total retry budgets.

## 10. Quick Status Code Comparison Matrix

| Status | CloudFront | ALB | API Gateway |
|---|---|---|---|
| 400 | Invalid request/headers/URI or origin returned 400 | Malformed request/headers/content length | Request validation, body/parameter/schema |
| 401 | Origin/auth response or custom behavior | Authenticate action/target response | Authorizer/token authentication |
| 403 | WAF, geo, signed URL/cookie, S3/OAC, or origin | WAF, authenticate/fixed response, or target | Authorizer, resource policy, API key/signature, WAF |
| 404 | Object/path/origin route or cached error | Usually target/fixed response/listener route | Resource/route/stage/base path mapping |
| 429 | Origin/WAF/quota behavior | Target or WAF/custom response | Throttle/usage quota or integration |
| 500 | Origin/application/function error | Target response or LB internal/config error | API configuration, authorizer/integration/backend |
| 502 | DNS/TLS/connection/malformed origin response | Target reset/malformed response/TLS | Lambda proxy format, integration response/network |
| 503 | Edge capacity/quota or origin unavailable | No usable targets | Backend/integration unavailable |
| 504 | Origin connect/read timeout | Target connection/idle timeout | Integration timeout |

Status codes are only hints. Always inspect log fields that identify the response source.

## 11. Symptom-Based Diagnostic Runbooks

### 11.1 Viewer Receives 403 Yet Origin Sees No Request

1. Capture `X-Amz-Cf-Id` and the UTC timestamp.
2. Search CloudFront standard/real-time logs by `x-edge-request-id`.
3. Inspect `x-edge-detailed-result-type`, `x-edge-result-type`, and `sc-status`.
4. Check AWS WAF sampled requests/logs and geo restrictions.
5. Check signed URLs/cookies, CloudFront Functions/Lambda@Edge.
6. If the origin is S3, inspect OAC/OAI, bucket policy, object key, and KMS.
7. Fix the identified rule/policy, run regression tests, and monitor block rates.

### 11.2 CloudFront Returns 502, ALB Has No Matching Log

1. Confirm the request was a cache miss and CloudFront attempted to call the origin.
2. Check origin domain DNS.
3. Check TLS certificate expiration, SAN/CN, chain, and SNI.
4. Check CloudFront origin protocol/port.
5. Check security groups/firewalls/network ACLs and origin reachability.
6. Check function associations if any.
7. Call the origin directly from an authorized environment to compare.

### 11.3 ALB Returns 502

1. Find access logs by timestamp, path, and `trace_id`.
2. Compare `elb_status_code` against `target_status_code`.
3. If `target_status_code` is `-`, check target resets, SGs/NACLs, ports, TLS, and connections.
4. If `target_status_code` is 5xx, search application logs.
5. Check keep-alive, idle timeout, header sizes, and deregistration delay.
6. Check `TargetConnectionErrorCount` and target health.

### 11.4 ALB Returns 503 After Deployment

1. Check `HealthyHostCount`/`UnHealthyHostCount` per target group.
2. Inspect ECS service events, EKS rollout/pod readiness, or Auto Scaling activities.
3. Check target group registration/deregistration.
4. Verify health check path, matcher, port, and security groups.
5. Confirm deployments maintain sufficient healthy capacity during rollouts.
6. Roll back if healthy targets cannot be restored within SLA.

### 11.5 API Gateway Returns 502

1. Find access logs by `extendedRequestId`.
2. Check `integration.status`, `integration.integrationStatus`, and `integration.error`.
3. Confirm whether the backend received the request.
4. If Lambda proxy, check Lambda logs and response format.
5. If VPC Link, check VPC Link status, listeners, target health, and networking.
6. Check mapping templates, content types, and binary/base64 handling.

### 11.6 API Gateway Returns 504

1. Check `IntegrationLatency` and `Latency`.
2. Search execution logs for timeout errors (if REST API).
3. Join with Lambda/ALB/application logs via `extendedRequestId`.
4. Confirm whether the integration was invoked.
5. Compare Lambda Duration, ALB `target_processing_time`, and database latency.
6. Optimize the backend or offload long tasks to asynchronous processing.
7. Request an integration timeout increase only with evidence and SLA justification.

### 11.7 Sudden 5xx Spike

- Identify exact start time and correlate with deployments/configuration changes.
- Break down by status code, API route, cache behavior, target group, and AZ.
- Inspect CloudFront 5XX metrics, `HTTPCode_ELB_5XX_Count`, `HTTPCode_Target_5XX_Count`, and API Gateway `5XXError`.
- Check `HealthyHostCount`, CPU/memory, connection pools, throttling, and dependency latency.
- Shift traffic/canary rollback if a recent change caused the spike.
- Avoid scaling multiple tiers simultaneously before identifying the bottleneck, as it can overload downstream dependencies further.

## 12. Case Study: Order API Returning 502/504 After Deployment

### 12.1 Architecture

An e-commerce application uses CloudFront as its public entry point, API Gateway REST API for auth and routing, VPC Link to an internal ALB, and ALB forwarding to an order-processing ECS service. The database resides in a private subnet.

### 12.2 Symptoms

- Users see 504 on some `POST /orders` requests.
- Other requests return 502.
- CloudFront standard logs show status 504 and `x-edge-result-type=Error`.
- API Gateway metrics show a sharp jump in `IntegrationLatency`.
- ALB target group still shows `HealthyHostCount` above zero.

### 12.3 Investigation

1. Use `x-edge-request-id` to find CloudFront logs and confirm requests were `Miss` and forwarded to the origin.
2. Use API Gateway `extendedRequestId` to locate access logs; integration status indicates timeouts.
3. Use timestamps and correlation IDs to locate ALB access logs.
4. ALB logs show `target_status_code=200` on some requests, while `target_processing_time` approaches timeout limits on others.
5. Application logs reveal database connection pool exhaustion after deployment; each request holds a connection waiting on a slow query.
6. Some requests wrote orders successfully yet responses never reached clients before gateway timeouts.

### 12.4 Root Cause and Remediation

The root cause was connection pool exhaustion and increased query latency after deployment. API Gateway timed out before the backend finished; CloudFront can also time out if its response timeout is shorter than or close to API Gateway's integration timeout.

Remediation:

- Roll back the release containing the query regression.
- Optimize the query and cap concurrency.
- Enforce explicit application/database deadlines.
- Order ALB/API Gateway/CloudFront timeouts properly relative to SLAs.
- Add idempotency keys to `POST /orders` because timed-out requests may have persisted orders.
- Add alarms on API Gateway `IntegrationLatency`, ALB `TargetResponseTime`, target 5xx, and database connection pools.

### 12.5 Lessons Learned

`HealthyHostCount` only indicates targets pass health checks; it does not prove every route runs fast. Nor does a CloudFront 504 prove CloudFront itself is broken. Trace request IDs across every layer to find the first component exceeding deadlines or throwing errors.

## 17. Self-Check Questions

**Question 1.** Why can't you determine root cause solely from status 502?

**Answer:** CloudFront, ALB, API Gateway, or the application can all emit 502 for different reasons; you must identify which layer generated the response using logs and request IDs.

**Question 2.** Are CloudFront, ALB, and API Gateway always on the same request path?

**Answer:** No. Multiple topologies exist, such as CloudFront → ALB, CloudFront → API Gateway, or API Gateway → VPC Link → ALB/NLB.

**Question 3.** Which CloudFront fields link responses to access logs?

**Answer:** `X-Amz-Cf-Id` in the response and `x-edge-request-id` in standard logs.

**Question 4.** What is `x-edge-detailed-result-type` used for?

**Answer:** It provides granular details on CloudFront errors, such as origin, viewer, or internal errors.

**Question 5.** What commonly causes CloudFront 502?

**Answer:** DNS, TLS/certificates, ports/networking, malformed origin responses, or Lambda@Edge/CloudFront Function validation errors.

**Question 6.** Why might CloudFront keep returning 404 after the origin is fixed?

**Answer:** The error response may still be cached under Error Caching Minimum TTL or `Cache-Control`.

**Question 7.** How do `elb_status_code` and `target_status_code` differ?

**Answer:** `elb_status_code` is the response emitted by ALB/WAF/fixed-response; `target_status_code` is the status returned by the target when a target responded.

**Question 8.** Which metric indicates 5xx errors generated by ALB?

**Answer:** `HTTPCode_ELB_5XX_Count`.

**Question 9.** Which metric indicates 5xx errors returned by targets?

**Answer:** `HTTPCode_Target_5XX_Count`.

**Question 10.** What does ALB 503 usually mean?

**Answer:** The target group has no registered targets or all targets are unused/unavailable.

**Question 11.** What commonly causes ALB 504?

**Answer:** Failing to connect to targets within connection timeout, targets failing to respond before idle timeout, or Network ACLs blocking return traffic.

**Question 12.** Does API Gateway 403 always mean an expired token?

**Answer:** No. It can come from authorizers, API keys, signatures, resource policies, WAF, or a wrong method/resource triggering `MISSING_AUTHENTICATION_TOKEN`.

**Question 13.** Why might a Lambda proxy integration return 502?

**Answer:** Lambda returned a response violating the proxy schema, threw an exception, or returned unserializable/unparseable output.

**Question 14.** What commonly causes API Gateway 429?

**Answer:** Account/stage/method throttling, usage plan quotas, or the backend returning 429 itself.

**Question 15.** How does `IntegrationLatency` differ from `Latency`?

**Answer:** `IntegrationLatency` measures time the gateway waits for the backend; `Latency` measures total time from receiving the request at the gateway to sending the response.

**Question 16.** What is the typical default REST API integration timeout?

**Answer:** Typically 29 seconds; increases can be requested for Regional/private REST APIs, though they may affect account throttle quotas.

**Question 17.** Why avoid enabling broad data tracing on production APIs?

**Answer:** Execution data can contain payloads, tokens, or sensitive information; logging it risks data exposure and increases cost.

**Question 18.** Why are idempotency keys needed when retrying `POST` after a timeout?

**Answer:** The backend may have already performed the side effect while the response was lost; idempotency keys prevent duplicate transactions or records.

**Question 19.** If CloudFront returns 502 yet ALB has no matching access log, what should you check first?

**Answer:** CloudFront origin DNS, TLS certificates/SNI, ports, network/firewalls, and edge functions before investigating the application.

**Question 20.** When should long-running API processing move to an asynchronous job?

**Answer:** When processing exceeds synchronous timeouts or can run unpredictably long; the API accepts the job, returns `202` + job ID, and processes in the background.

## 18. Production Readiness Checklist

- [ ] Actual topology and gateway ordering are documented.
- [ ] Every API route/path maps to the right CloudFront behavior, origin, API stage, and ALB target group.
- [ ] CloudFront standard/real-time logging is enabled per needs and retention.
- [ ] ALB access logging or enhanced logging is enabled.
- [ ] API Gateway access logging is configured for the exact API type.
- [ ] REST API execution logging uses appropriate levels; data tracing is not broadly enabled in production.
- [ ] Response headers/request IDs are preserved in client diagnostics.
- [ ] Correlation IDs are validated and propagated across services.
- [ ] Tokens, cookies, API keys, PII, and unnecessary sensitive payloads are excluded from logs.
- [ ] CloudFront origin DNS, TLS, SNI, certificate chains, and ports are tested.
- [ ] CloudFront caching, error caching, and custom error pages are reviewed.
- [ ] ALB listener rules, target groups, target health, and deregistration delays are tested.
- [ ] ALB `elb_status_code` and `target_status_code` are included in log analysis.
- [ ] ALB ELB/Target 4xx/5xx metrics have dashboards and alarms.
- [ ] API Gateway authorizers, resource policies, API keys, WAF, and route mappings are tested.
- [ ] Lambda proxy response formats and integration mappings have regression tests.
- [ ] VPC Links, security groups, NACLs, subnet IPs, and target reachability are verified.
- [ ] Timeout budgets across dependencies, applications, ALB, API Gateway, CloudFront, and clients are aligned.
- [ ] Retries use backoff/jitter, attempt caps, and idempotency for side effects.
- [ ] 429/503 responses have proper backpressure and retry policies.
- [ ] 502/503/504 runbooks specify logs, metrics, owners, and rollback steps.
- [ ] Non-production tests cover WAF blocks, malformed responses, unavailable targets, and timeouts.
- [ ] Alarms monitor error rates, latency, target health, integration latency, and queue/connection saturation.
- [ ] A rollback plan exists when errors rise after deployments/configuration changes.

**Conclusion:** Diagnosing 4xx/5xx errors requires identifying the exact layer that generated the response. CloudFront logs reveal edge/cache/origin outcomes; ALB access logs and metrics separate load balancer failures from target failures; API Gateway access/execution logs show what the gateway, authorizer, and integration did. Correlate evidence with request IDs/correlation IDs, align timeouts along the request path, fix the root cause, and verify with regression tests before closing the incident.
