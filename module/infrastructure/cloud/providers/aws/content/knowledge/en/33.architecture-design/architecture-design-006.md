# Retry Budget, Circuit Breaker, and Bulkhead

In a distributed system, a single API call may traverse a load balancer, service mesh, application, database, queue, and an external service. Even one slow dependency can cause requests to hold connections, threads, and memory longer than normal. If every layer retries, request volume can grow exponentially; if a shared service becomes congested, unrelated features may stop working as well.

Three mechanisms are commonly combined to contain cascading failures:

- **Retry budget** limits the amount of retry work permitted, preventing retries from adding load while the system is degrading.
- **Circuit breaker** stops calling a failing dependency for a period of time, giving the system breathing room to recover and allowing requests to fail fast or fall back.
- **Bulkhead** partitions resources into isolated compartments so a failure or overload in one request group does not consume all capacity of other groups.

Within the **CLOUD_PROVIDERS_AWS** ecosystem, these mechanisms apply to applications running on EC2, ECS, EKS, and Lambda; calls to RDS, DynamoDB, S3, API Gateway, or external services; and asynchronous processing via SQS, EventBridge, or Step Functions. The goal of the module is to help learners design and deploy secure, observable, resilient, and cost-controlled applications. Therefore, retries, timeouts, circuit breakers, and bulkheads should be designed as a cohesive policy across all layers rather than enabling retries independently in each library.

## 1. Why Limit Cascading Failures?

Suppose an Orders API receives 500 requests per second. Each request must call Inventory and Payment. The Inventory database begins responding slowly. Orders requests wait longer, threads and connection pools stay occupied, and in-flight requests pile up. When timeouts occur, the application retries immediately. Retries keep hitting Inventory, increasing load at the exact moment the dependency is weakest.

If API Gateway, the Orders service, the SDK, and the Inventory service all retry, the original request count can multiply across each layer. For example, three layers each allowing three total attempts can generate up to 27 calls at the deepest layer in the worst case. This is why retries must be bounded and coordinated along the entire request path.

The three patterns solve three distinct problems:

| Mechanism | Question It Answers | Goal |
|---|---|---|
| Retry budget | How many extra attempts is the system allowed to generate? | Bound load generated by retries |
| Circuit breaker | When a dependency is failing, should we keep calling it? | Stop piling requests onto a degraded dependency |
| Bulkhead | Should one request group be allowed to consume all shared resources? | Isolate failures and preserve capacity for the rest |

These mechanisms do not replace timeouts, idempotency, rate limiting, load shedding, or autoscaling. They must work alongside those controls to protect both callers and dependencies.

## 2. Starting with Timeouts and Deadlines

Retries are only meaningful when every call is time-bounded. Without timeouts, requests can wait indefinitely, holding connections and threads and exhausting resources even without retries.

Distinguish two concepts:

- **Timeout:** a time limit on a specific operation, such as a TCP connection or an HTTP request.
- **Deadline:** the absolute cutoff by which the entire unit of work must finish, including attempts, backoff, and response handling.

For example, an API has a 2-second deadline. It calls a dependency with a 400 ms timeout and allows at most two retries. If the two maximum backoff intervals are 100 ms and 200 ms respectively, the theoretical budget is:

\[
3 \times 400\text{ ms} + 100\text{ ms} + 200\text{ ms} = 1.5\text{ s}
\]

The remainder is reserved for serialization, network overhead, breaker checks, and returning the response. If each call's timeout were 1 second, three attempts would exceed the deadline before even counting backoff. In that case, the retry policy cannot meet the latency target.

### Layered Timeout Design

A useful rule of thumb is that a dependency timeout must be shorter than the caller's remaining deadline. For example:

| Layer | Example Limit |
|---|---:|
| Client API deadline | 2,000 ms |
| Overall Orders processing | 1,800 ms |
| Single Inventory call | 400 ms |
| TCP/TLS handshake | 100 ms |
| Total backoff time | Max 300 ms |

These numbers are design examples only. Measure p95/p99 latency, connection times, and business requirements to choose suitable values. Never set timeouts based solely on average latency.

When the deadline is nearly exhausted, the client should not start a new retry if insufficient time remains to complete it. Propagating deadlines or remaining time across services lets downstream layers know how much budget a request still has.

## 3. Retries: When to Retry?

A retry resends an operation after a prior attempt fails. Retries help with transient failures such as:

- Connection resets or brief network glitches.
- Timeouts caused by a sudden load spike.
- HTTP 5xx responses from a dependency.
- Throttling or rate limits, if the response allows retrying after a delay.
- Certain transient service errors recognized by the AWS SDK.

Do not retry every error. The following usually require direct handling:

- Invalid input data.
- Missing permissions or invalid credentials.
- Non-existent resources unlikely to appear due to eventual consistency.
- Business rule violations.
- Requests exceeding fixed quotas without a wait or adjustment mechanism.

Retrying an error that cannot resolve itself wastes time and capacity. Classify errors by HTTP status, exception, error code, and service context—not merely by whether "an exception occurred."

### Retries Are Only Safe When Operations Are Idempotent

An idempotent operation can be executed multiple times with the same input without changing the final outcome beyond the first execution. `GET` usually has this property; `PUT` can be idempotent when designed properly; `POST` creating an order or charging money is typically not automatically idempotent.

Dangerous scenario: the server creates an order and commits to the database, but the response is lost on the return path. The client sees a timeout and resends the `POST`. If the server does not recognize the duplicate request, the order may be created twice.

How to protect:

1. The client generates a unique idempotency key for the business intent.
2. The server stores the key along with the outcome or processing state in a data store with appropriate consistency.
3. Repeated requests with the same key return the recorded result or in-progress status.
4. Requests with the same key but a different payload must be rejected or flagged for investigation.
5. Keep the key retention period long enough relative to retry windows, queue redelivery, and reconciliation windows.

With SQS, messages can be redelivered. Consumers must be idempotent or use deduplication/conditional writes to avoid executing transactions twice.

## 4. Exponential Backoff and Jitter

If many clients retry simultaneously right after a failure, they create a synchronized load wave called a retry storm or thundering herd. Exponential backoff increases the wait between attempts; jitter adds randomness so clients do not wake up at the same instant.

A common full-jitter formula:

\[
d_n = U\left(0,\ \min(d_{\max}, d_0 \times 2^n)\right)
\]

Where:

- \(d_n\) is the wait time before the next attempt.
- \(d_0\) is the initial base delay.
- \(d_{\max}\) is the maximum backoff cap.
- \(n\) is the retry attempt index.
- \(U(0,x)\) is a uniformly distributed random value from 0 to \(x\).

Example with \(d_0=100\) ms and \(d_{\max}=2\) seconds:

| Retry Attempt | Max Backoff Before Jitter | Actual Delay |
|---|---:|---|
| 1 | 100 ms | Random 0–100 ms |
| 2 | 200 ms | Random 0–200 ms |
| 3 | 400 ms | Random 0–400 ms |
| 4 | 800 ms | Random 0–800 ms |
| 5 | 1,600 ms | Random 0–1,600 ms |

Thereafter the cap does not exceed \(d_{\max}\). Combine backoff with deadlines and retry budgets; waiting indefinitely longer is not a recovery strategy.

### Respect `Retry-After`

Some APIs return a `Retry-After` header or equivalent hint when throttling. If the API contract instructs clients to honor this duration, wait as directed while still checking application deadlines and upper bounds. Do not retry sooner simply because internal backoff is shorter.

## 5. What Is a Retry Budget?

A retry budget caps the total volume of retries permitted within a scope and time window. Rather than only setting "at most three attempts per request," a budget controls the aggregate retry volume across an entire service or dependency.

Budgets can be defined by:

- Ratio of retries to original requests.
- Maximum retries per minute.
- A token bucket refilled at the rate of successful requests or a configured rate.
- Separate budgets per dependency, tenant, or endpoint group.

For example, a service handling 1,000 original requests per minute with a 5% retry budget policy allows up to roughly 50 retry attempts in that window. If retries exhaust the budget, clients stop retrying, fail fast, or switch to a designed fallback.

The 5% figure is an internal example, not an AWS default. Organizations must set budgets based on baseline traffic, dependency capacity, SLOs, and acceptable error levels.

### Retry Budget vs. Max Attempts

| Limit | Scope |
|---|---|
| Max attempts | Number of times a single request can execute, including the initial try or per library convention |
| Retry budget | Total retry attempts allowed within a time window or scope |
| Deadline | Total wall-clock time a request is permitted to spend |
| Rate limit | Total new requests permitted to enter the system |

A request may still have remaining attempts under max attempts while the service's retry budget is exhausted. Conversely, the service may have budget remaining, yet an expired request deadline still forbids retrying.

### Token Bucket for Retry Budgets

One implementation uses a token bucket:

1. The bucket starts with a bounded number of tokens.
2. Each retry consumes one token.
3. Tokens replenish at a configured rate or proportionally to successful requests.
4. When the bucket is empty, requests cannot retry.

A token bucket permits small bursts while capping sustained retry load. It can run in the client process, an internal library, or a coordination tier. If a budget is shared across a fleet, weigh the cost and latency of distributed counters; per-instance local counters can allow fleet-wide retry totals higher than expected.

## 6. What Is a Circuit Breaker?

A circuit breaker monitors dependency call outcomes and temporarily stops sending requests when failure rates or counts exceed a threshold. The goal is to stop callers from spending resources waiting on an unhealthy dependency.

A circuit breaker typically has three states:

| State | Behavior |
|---|---|
| **Closed** | Requests are allowed through; the breaker tracks successes/failures |
| **Open** | Requests fail fast or route to fallback; dependency is not called |
| **Half-open** | Allows a limited number of probes to test whether the dependency has recovered |

State flow:

~~~mermaid
stateDiagram-v2
    [*] --> Closed
    Closed --> Open: Failures exceed threshold
    Open --> HalfOpen: Wait timeout expires
    HalfOpen --> Closed: Probe succeeds
    HalfOpen --> Open: Probe fails
~~~

### Closed

In the Closed state, the breaker lets requests reach the dependency. It tracks errors by consecutive failures, error rate over a time window, or a combination of conditions. Count only errors reflecting dependency health, such as timeouts, connection failures, or 5xx responses.

Do not count every business error as a breaker failure. HTTP 400 from invalid input or 403 from missing caller permissions usually does not indicate the dependency is overloaded.

### Open

Once the threshold is breached, the breaker transitions to Open for a cooldown period. New requests fail fast to free threads and connections. The application can return a controlled error, serve safe stale cache, or enqueue work if business rules permit.

Never use a fallback that fabricates success if it corrupts business data. For example, do not return "paid" when the Payment service is down and the transaction was never confirmed.

### Half-Open

After the wait duration, the breaker permits a small number of test requests. If probes meet success criteria, the breaker returns to Closed. If probes keep failing, the breaker returns to Open.

Limit the number of probes to prevent thousands of clients from probing the dependency simultaneously. Add jitter to breaker retry timing or coordinate via rate limits.

## 7. Configuring a Sensible Circuit Breaker

A breaker requires these parameters:

- Observation window: by recent request count or time interval.
- Minimum volume threshold: evaluate error rate only after sufficient samples exist.
- Open threshold: error rate, consecutive failures, or timeout count.
- Open duration: how long the Open state persists.
- Half-open permits: concurrent probes allowed.
- Success threshold: number or percentage of successful probes to close again.
- Exception/response classification: which errors count toward opening.

Illustrative example: over a 30-second window, if there are at least 20 requests and more than 50% end in timeouts or 5xx errors, open the breaker for 10 seconds. Then allow only two concurrent probes. If both succeed, close the breaker; if any fails, reopen it.

This is an illustrative policy, not recommended values for every application. Account for low-traffic periods, dependency recovery time, SLOs, and fallback behavior.

### Per-Dependency Breakers

Do not use a single global breaker for all downstream services. Inventory, Payment, and Notification have different latency profiles, criticality, and fallbacks. Separating breakers per dependency or critical endpoint ensures Payment failures do not block calls to Inventory.

For multi-tenant services, isolating per tenant or pool may be needed if one tenant causes overload. However, creating per-tenant breakers with very high cardinality consumes memory and complicates monitoring; choose boundaries based on real risk.

## 8. What Is a Bulkhead?

Bulkheads borrow their name from ship compartments: if one compartment floods, the rest of the ship stays afloat. In software, a bulkhead partitions resources or execution paths into independent pools so one dependency or request group cannot consume all shared capacity.

Resources that can be isolated:

- Thread pools or executors.
- Semaphores and concurrency limits.
- Connection pools per database/service.
- Queues and consumer groups.
- Processes/containers/tasks or instance groups.
- Capacity per tenant, API, or job type.

For instance, the Orders service calls Payment and Recommendation. If both share one thread pool, a slow Recommendation service can exhaust all threads and starve payment requests. Separating pools and concurrency caps per dependency protects the payment path.

### Thread-Pool and Semaphore Bulkheads

A thread-pool bulkhead assigns a dedicated pool per dependency. When the pool is full, new requests are rejected or placed in a bounded queue. A semaphore bulkhead limits concurrent operations while potentially sharing an executor.

| Approach | Advantage | Risks / Considerations |
|---|---|---|
| Separate thread pool | Isolates threads and queues per dependency | Consumes threads; must avoid unbounded queues |
| Semaphore | Lightweight, clear concurrency limit | Does not isolate blocking I/O threads on its own |
| Separate connection pool | Caps connections and prevents one DB from exhausting pools | Needs proper sizing and acquisition timeouts |
| Separate queue | Isolates load and retries by work type | Must manage backlogs, ordering, and DLQs |
| Separate compute/service | Isolates CPU/memory and scaling | Increases cost and operational overhead |

An unbounded queue or pool is not a safe bulkhead. If requests keep queuing while a dependency does not recover, latency and memory climb until the system runs out of resources. Always bound capacity, queue length, wait timeouts, and full-queue behavior.

## 9. Combining Retry Budgets, Circuit Breakers, and Bulkheads

The three mechanisms must operate in a clear sequence:

1. Check the deadline and capacity eligibility.
2. Check the circuit breaker; if Open, fail fast or invoke fallback.
3. Acquire a slot from the bulkhead; if full, reject fast or wait within bounds.
4. Execute the request with a timeout.
5. If a retryable error occurs, check the deadline, max attempts, and retry budget.
6. Wait for backoff with jitter, then retry if the breaker/bulkhead still permit.
7. Emit metrics and return the final result.

~~~mermaid
flowchart TD
    A[Request arrives] --> B{Deadline remaining?}
    B -->|No| X[Timeout / fail fast]
    B -->|Yes| C{Circuit breaker allows?}
    C -->|Open| F[Fallback or controlled error]
    C -->|Yes| D{Bulkhead capacity available?}
    D -->|No| F
    D -->|Yes| E[Call dependency with timeout]
    E --> G{Succeeded?}
    G -->|Yes| H[Return result]
    G -->|No| I{Retryable error?}
    I -->|No| X
    I -->|Yes| J{Retry budget and deadline remaining?}
    J -->|No| X
    J -->|Yes| K[Backoff + jitter]
    K --> C
~~~

Exact ordering may vary by library. What matters is that retries must never bypass the breaker, bulkhead, or deadline. Every retry attempt must pass through the same protective controls as the first attempt.

## 10. Applying with the AWS SDK

The AWS SDK includes retry strategies for certain transient errors and throttling. Understand the SDK's retry mode, max attempts, backoff, and retry quota instead of wrapping an unbounded outer retry loop around it.

Common modes:

- **Standard retry mode:** applies backoff and a retry quota to limit retries. The retry quota is an internal SDK token/quota mechanism that stops retries once retry cost exceeds limits; it is not an organization-wide service retry budget.
- **Adaptive retry mode:** adds client-side rate limiting based on throttling responses on top of standard retries. It suits workloads interacting with a specific resource or endpoint; if sharing one client across unrelated resources, throttling on one can throttle others.
- **Legacy retry mode:** older behavior retained for compatibility; prefer `standard` for new applications per current SDK guidance.

Avoid stacking multiple retry layers without accounting for total attempts. For example, if the SDK retries three times, a service wrapper retries three times, and API Gateway/clients retry again, total load can far exceed expectations.

### Practical Rules

1. Pick one primary layer responsible for retries per dependency.
2. Set SDK max attempts and timeouts to fit within the deadline.
3. Review each service's error codes and throttling behavior.
4. Never retry authentication, authorization, or validation errors.
5. For writes, use idempotency or conditional operations.
6. Monitor SDK retry counts, throttling, and latency to tune settings.

The AWS SDK retry quota only caps retries within a client instance. It does not replace a circuit breaker or bulkhead, and it does not prevent large numbers of independent clients from overloading a dependency together.

## 11. SQS and Asynchronous Processing

SQS decouples producers from consumers, absorbs bursts, and lets workers process at a sustainable pace. It acts as an architectural bulkhead when workloads use separate queues and consumers.

Mechanisms to coordinate:

- **Visibility timeout:** duration a message stays hidden after a consumer receives it. If processing fails to finish and delete the message, it can be redelivered.
- **Redrive policy:** routes messages to a dead-letter queue after exceeding maximum receives.
- **`MaxReceiveCount`:** caps how many times a message is received before moving to the DLQ.
- **Batch size/concurrency:** limits throughput and concurrent messages processed.
- **Idempotent consumer:** ensures redelivered messages do not cause duplicate transactions.

Do not set `MaxReceiveCount` excessively high just to avoid the DLQ. Poison messages will be retried repeatedly, occupying workers and delaying healthy messages. DLQs need alarms, owners, and a replay procedure after fixing root causes.

### Visibility Timeout and Retries

Visibility timeout should be long enough for expected processing time, accounting for heartbeats/visibility extensions for long tasks. If too short, another consumer may receive the message while the first is still processing, causing duplicate work. If too long, failed messages wait excessively before retrying.

With Lambda event source mappings for SQS, consider partial batch responses to retry only failed messages rather than the entire batch. Regardless of mechanism, consumers still need idempotency because SQS standard queues provide at-least-once semantics.

## 12. Retries in AWS Step Functions and EventBridge

Step Functions lets you declare `Retry` and `Catch` blocks inside the state machine. This provides explicit retry management for multi-step workflows instead of writing uncontrolled loops inside Lambda.

Example Task state with backoff, max attempts, and jitter:

~~~json
{
  "CallInventory": {
    "Type": "Task",
    "Resource": "arn:aws:states:::lambda:invoke",
    "Parameters": {
      "FunctionName": "CheckInventory",
      "Payload.$": "$"
    },
    "Retry": [
      {
        "ErrorEquals": ["TransientDependencyError", "States.Timeout"],
        "IntervalSeconds": 2,
        "BackoffRate": 2.0,
        "MaxAttempts": 3,
        "MaxDelaySeconds": 20,
        "JitterStrategy": "FULL"
      }
    ],
    "Catch": [
      {
        "ErrorEquals": ["States.ALL"],
        "Next": "HandleFailure"
      }
    ],
    "End": true
  }
}
~~~

This snippet illustrates Amazon States Language structure. Verify the actual error names returned by Lambda and match retryable errors accurately. Do not retry `States.ALL` by default because data or permission errors will not heal on their own.

EventBridge provides retry policies and dead-letter queues for target delivery. This governs delivery retries to the target, distinct from retries inside the Lambda or service handling the event. When designing, sum retries across all layers and enforce deduplication so one event does not trigger multiple side effects.

## 13. Bulkheads Across AWS Compute Services

### Lambda

Reserved concurrency caps a function's maximum concurrency and reserves capacity for it within the account/Region. It helps isolate critical functions from other functions and protects downstream systems from excessive request bursts.

Reserved concurrency does not automatically split internal thread pools or connection pools inside a function. Combine timeouts, concurrency caps, SQS event source scaling, idempotency, and in-code circuit breakers. Provisioned concurrency mainly keeps execution environments warm to reduce cold starts; it is not a bulkhead substitute for reserved concurrency.

### ECS

You can split workloads into separate ECS services by dependency or criticality. Each service has its own desired count, autoscaling, CPU/memory, and task role. Capping task counts or consumer concurrency protects databases. A congested recommendation service should never exhaust checkout service capacity.

### EKS

Use namespaces, resource requests/limits, `ResourceQuota`, `LimitRange`, dedicated node groups, or workload pools to reduce CPU/memory contention. `NetworkPolicy` and service accounts isolate access permissions. HPA can scale on metrics, but cap max replicas and align with downstream capacity; scaling out too aggressively can overwhelm databases.

### EC2

Separate Auto Scaling groups or process pools by workload, and maintain separate connection pools per dependency. Cap worker counts and queue lengths so one request type cannot monopolize an entire instance.

## 14. Circuit Breakers and Fallbacks

When a breaker opens, the system must decide whether to return an error, serve stale data, or enqueue work. Fallbacks must align with business semantics.

| Dependency | Fallback to Consider | What to Avoid |
|---|---|---|
| Recommendation | Return a default list or omit recommendations | Blocking entire checkout just because recommendations failed |
| Product catalog cache | Serve cached data within a safe staleness window | Using stale price or stock data when business rules require accuracy |
| Notification | Enqueue the request for later delivery | Reporting sent successfully before the request is durably saved |
| Payment | Return `pending` status or ask for controlled retry | Claiming payment succeeded without confirmation |
| Inventory | Reject or transition to pending confirmation | Overselling stock via an unreliable fallback |

Fallbacks can shift load onto caches, queues, or other services. Protect fallbacks with their own timeouts, bulkheads, and capacity. If a fallback depends on the same failing database, it is not an independent recovery path.

## 15. Observability and Alerting

You cannot tune retries, breakers, and bulkheads by guesswork. Measure original requests, retries, and resource states together.

| Metric | Meaning | Operational Question |
|---|---|---|
| Request rate | Incoming original request volume | Is traffic spiking abnormally? |
| Retry attempts / retry ratio | Retry count and ratio to original requests | Are retries amplifying load? |
| Retry budget remaining/exhausted | Remaining budget or exhaustion count | Is the policy too tight or too loose? |
| Timeout rate | Percentage of requests timing out | Which dependency is timing out? |
| Circuit state / open count | Breaker state and open transitions | Is a dependency degrading? |
| Half-open probe result | Outcome of recovery probes | Is the dependency healthy enough for traffic? |
| Bulkhead rejection / saturation | Requests rejected due to full slots | Is capacity insufficient or dependency too slow? |
| Pool utilization | Thread/connection pool usage | Are local resources exhausting? |
| Queue age / DLQ depth | Message age and backlog | Are consumers keeping up with producers? |
| Downstream latency p95/p99 | Tail latency of dependencies | Do timeouts fit the latency distribution? |

Use Amazon CloudWatch metrics, logs, and alarms to monitor. AWS X-Ray or OpenTelemetry/ADOT can pinpoint which span in a call chain is slow. Include trace IDs, request IDs, and idempotency keys in logs without exposing sensitive data.

Alarms should target trends and impact: sustained rise in retry ratio, repeated breaker openings, rising bulkhead rejections, queue age breaching SLOs, or growing DLQ depth. Avoid paging on every single breaker trip, since a brief open transition may be healthy protective behavior.

## 16. Design Example: Orders Calling Payment and Recommendation

Suppose the Orders API has a 1.5-second deadline. It calls two dependencies:

- Payment is critical; orders must never be confirmed as paid without a definitive result.
- Recommendation is non-critical; it can be skipped if slow or failing.

Design:

1. Set Payment's timeout below the remaining deadline; retry only recoverable network/5xx errors with an idempotency key.
2. Dedicated circuit breaker for Payment; when Open, return `pending` or a controlled error, and reconcile via webhook/status API.
3. Separate bulkheads for Payment and Recommendation so recommendations cannot consume payment threads/connections.
4. Recommendation has its own breaker and falls back to a default list or skips recommendations.
5. Separate retry budgets per dependency capping aggregate load.
6. Emit metrics for retries, timeouts, breaker state, and bulkhead saturation.
7. For asynchronous work like sending emails, push messages to a dedicated SQS queue with a DLQ.

~~~mermaid
flowchart LR
    A[Client] --> B[Orders API]
    B --> C[Payment Bulkhead]
    C --> D[Payment Circuit Breaker]
    D --> E[Payment Service]
    B --> F[Recommendation Bulkhead]
    F --> G[Recommendation Circuit Breaker]
    G --> H[Recommendation Service]
    B --> I[Notification SQS]
    I --> J[Notification Worker]
    B --> K[Retry Budget + Deadline]
~~~

If Recommendation slows down, the request still finishes without waiting on it. If Payment fails, the system never fakes success; it returns an appropriate status and reconciles transaction state. This is an example of intentional degraded mode.

## 17. Calculating a Retry Budget for a Dependency

Suppose the Orders service sends 2,000 original requests per minute to Inventory. The target retry budget is 3% of original requests in a one-minute window:

\[
2,000 \times 0.03 = 60\ \text{retry attempts/minute}
\]

If error rates climb and 500 requests want to retry, the system permits only 60 retries in the window; the rest fail fast or route to fallback. This causes some requests to fail earlier, but avoids sending 440 extra requests into a degrading dependency.

In distributed deployments, per-instance local budgets must be scaled against maximum instance count. If 10 instances each allow 60 retries/minute, the fleet-wide total can reach 600 retries/minute. Allocate budgets proportionally to instance capacity or use a shared coordinator if strict fleet-wide limits are needed. A shared counter is itself a dependency needing HA and timeouts; never let the retry budget store become a new point of failure.

## 18. Common Mistakes

### Retrying at Every Layer

SDKs, service wrappers, API Gateway, and callers all retrying multiplies request volume. Designate one primary layer, calculate total attempts, and document retry ownership in API contracts.

### Missing Timeouts

Requests can hold threads and connections indefinitely. Set timeouts for connect/read/request operations and an overall deadline.

### Fixed Backoff Without Jitter

Many clients retry at the exact same time. Use exponential backoff with jitter and a cap.

### Retrying Non-Idempotent Writes

Can create duplicate orders or double charges. Use idempotency keys, conditional writes, and deduplication.

### Overly Sensitive Circuit Breakers

A few isolated errors trip the breaker even when the dependency is healthy. Use minimum request thresholds, suitable windows, and accurate error classification.

### Circuit Breakers Without Bounded Half-Open Probes

When Open duration expires, all clients probe simultaneously. Limit probe concurrency and add jitter.

### Thread Bulkheads with Unbounded Queues

Requests keep piling up and consuming memory. Bound queue length, wait times, and rejection behavior when full.

### Sharing Connection Pools Across Dependencies

One slow dependency exhausts all connections. Separate pools and configure max connections and acquisition timeouts.

### Unsafe Fallbacks

Returning fake success or stale data for accuracy-critical transactions corrupts business state. Clearly define what is safe to degrade.

### Looking Only at Error Rates Without Load

A low retry ratio at very high request volume can still overload a dependency. Monitor absolute retry counts, concurrency, latency, and saturation together.

## 19. Resilience Design Checklist

- [ ] Overall request deadline and per-dependency timeouts are defined.
- [ ] Downstream timeouts fit within the caller's remaining deadline.
- [ ] Only transient, eligible errors are retried.
- [ ] Retries use exponential backoff, jitter, and upper caps.
- [ ] Max attempts, retry budgets, and deadlines are calculated separately and coordinated.
- [ ] Write operations carry idempotency keys or deduplication mechanisms.
- [ ] Multiple retry layers do not stack unexpectedly.
- [ ] Circuit breakers distinguish dependency failures from client/business errors.
- [ ] Breakers have closed/open/half-open states, bounded probes, and safe fallbacks.
- [ ] Bulkheads isolate pools/concurrency/queues by dependency or critical workload.
- [ ] Queues and pools are bounded; full-capacity behavior is defined.
- [ ] SQS consumers are idempotent with proper visibility timeouts, redrive policies, and DLQs.
- [ ] Step Functions/EventBridge retries are factored into the total retry path.
- [ ] AWS SDK retry mode is explicitly chosen and not wrapped in unbounded retries.
- [ ] CloudWatch/X-Ray/ADOT measure retries, timeouts, breakers, bulkheads, and queue age.
- [ ] Load tests, fault injection, and game days validate behavior under dependency degradation.
- [ ] Degraded modes and operational runbooks for budget exhaustion are documented.

## 20. Key Takeaways

Retry budgets cap retry volume to avoid adding load while a dependency degrades. Circuit breakers stop requests from hitting failing dependencies and enable controlled recovery probing. Bulkheads partition resources so one group of requests cannot exhaust total system capacity.

These three mechanisms must pair with timeouts, deadlines, exponential backoff with jitter, and idempotency. On AWS, leverage SDK retry strategies, SQS/DLQs, Step Functions retries, Lambda reserved concurrency, ECS/EKS resource isolation, and CloudWatch/X-Ray to implement and observe them. Service features do not replace application-level policies.

A resilient architecture does not try to retry every failure until it succeeds. It bounds work, fails fast when necessary, preserves capacity for critical functions, and uses fallbacks only when business semantics allow. Measure retry ratios, latency, saturation, and game day results to tune thresholds against real traffic.
