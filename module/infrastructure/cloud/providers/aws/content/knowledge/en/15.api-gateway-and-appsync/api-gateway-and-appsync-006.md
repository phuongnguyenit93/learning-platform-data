# Validation, CORS, and API Error Handling on API Gateway and AppSync

## Learning Objectives

After this lesson, you will be able to:

- Distinguish **protocol-level validation**, **input validation**, **business rules**, **authentication**, and **authorization** in APIs.
- Choose the right request-validation approach for **Amazon API Gateway REST API**, **API Gateway HTTP API**, and **AWS AppSync GraphQL API**.
- Configure and test **CORS**, including origins, `OPTIONS` preflight, allowed methods/headers, credentials, caching, and error responses.
- Explain why a `curl` request can succeed while a browser still reports a **CORS error**, or why `OPTIONS` gets blocked by an authorizer.
- Design a consistent HTTP error contract with **status code, error code, message, and request ID** without leaking internal details.

- Test via the AWS Console, AWS CLI, `curl`, browser DevTools, CloudWatch, CloudTrail, and negative test cases.
- Design secure APIs with **IAM, Cognito/JWT, VPC, AWS Lambda, S3/DynamoDB/RDS**, logging, retries, monitoring, and budgets.

## 1. Sample Architecture: Which Layers Does a Request Traverse?

Suppose an e-commerce application exposes data in two ways:

- **REST API:** `POST /orders` and `GET /orders/{id}` through API Gateway → Java AWS Lambda or HTTP backend.
- **GraphQL API:** `mutation createOrder` and `query getOrder` through AppSync → DynamoDB/Lambda/HTTP data sources.

~~~mermaid
flowchart TB
    Browser[Web app at https://shop.example.com] --> CORS{Browser CORS policy}
    CORS --> REST[API Gateway REST / HTTP API]
    CORS --> GQL[AWS AppSync GraphQL]
    REST --> Auth[AuthN/AuthZ, throttling, routing]
    Auth --> Validate[Gateway validation if supported by API type]
    Validate --> Lambda[Lambda / HTTP integration]
    Lambda --> Data[(DynamoDB / RDS / S3)]
    GQL --> Schema[GraphQL parsing + schema validation]
    Schema --> Resolver[Resolver / pipeline logic]
    Resolver --> Data
    REST --> Logs[CloudWatch / access logs]
    GQL --> Logs
~~~

**CORS is not a gateway sitting in front of all traffic.** It is a policy enforced by **browsers** on cross-origin JavaScript requests, governed by headers the server returns. An AWS backend can still receive requests from `curl`, SDKs, or server-to-server callers even when a browser blocks a page from reading the response.

### Four Questions When an API Request Fails

1. **Did the browser send the actual request, or did it stop at preflight?** Inspect DevTools Network.
2. **Did the gateway accept the request and pass authentication/authorization?** Check HTTP status codes and gateway logs.
3. **Is the request structurally/schema-valid?** Check request validators, GraphQL schemas, and mappings.
4. **Did the backend succeed in executing the business operation?** Check Lambda/resolver/data-source logs, DBs, and downstream services.

Without separating these four questions, engineers easily waste time "fixing CORS" when the real error is `401`/`403`/`500`, or opening up broad IAM permissions when only an `Access-Control-Allow-Origin` header is missing.

## 2. Quick Comparison of the Three API Types Before Configuring

| Criterion | API Gateway **REST API** | API Gateway **HTTP API** | **AppSync GraphQL** |
| --- | --- | --- | --- |
| Endpoint model | Resources, methods, stages, integrations | Routes, integrations, stages | Single GraphQL endpoint/schema with Query/Mutation/Subscription |
| Built-in validation | **Request validators + Models** for body/required params | **No equivalent REST request validators/models**; typically handled in backend/authorizer | **GraphQL parser and schema type system** validate queries/variables before resolvers |
| Business validation | Lambda/HTTP integration, service layer | Lambda/HTTP integration, service layer | Resolvers, pipeline functions, Lambda/data sources |
| CORS | Depends on integration: `OPTIONS` preflight, method/integration headers, gateway responses | **API-level CORS configuration** handles preflight and adds headers | AppSync manages the GraphQL endpoint/responses; custom CORS is not set per resolver like REST |
| Auth | IAM, Cognito, Lambda authorizers, plus API keys/usage plans | IAM, JWT/Lambda authorizers | API key, AWS IAM, Cognito User Pools, OIDC, Lambda authorizer per config |
| Typical errors | HTTP status + body; includes **Gateway Responses** for gateway-generated errors | HTTP status + body; lacks REST-style Gateway Responses | GraphQL envelope (`data`, `errors`); do not infer status solely from HTTP `200` |
| Logging | Access + execution logs per REST capabilities | Access logs/metrics | AppSync field logs, CloudWatch/X-Ray per config |
| When to choose | Need traditional REST governance, models/validators/gateway responses | Simple HTTP APIs with lower latency/cost | Clients need GraphQL field selection, schemas, and resolvers |

**Never assume HTTP API supports all REST API features.** Before designing around request validators, usage plans, mapping templates, or gateway responses, verify the exact **API type**.

## 3. Validation Is More Than Valid JSON

Validation should be divided by **condition type** and **responsible layer**.

| Layer | Examples | Appropriate location |
| --- | --- | --- |
| HTTP protocol/size/content type | Wrong method, `Content-Type`, oversized payload | Gateway and backend |
| Required path/query/header | Missing `orderId`, missing required header | REST method validator or backend |
| JSON/schema/type | `quantity` is not a number, missing `customerId` | REST model validator, GraphQL schema, backend |
| Business invariant | Quantity 1–20, item in stock, delivery date not in the past | **Backend/domain service** or AppSync resolver/pipeline |
| Authentication | Missing token, expired token, bad signature | API authorizer/Cognito/IAM |
| Authorization | May caller view another tenant's order? | API auth + backend row/resource-level policy |
| Replay/idempotency | Same `Idempotency-Key` submitted twice | Backend and durable storage |
| Rate/abuse control | Excessive requests or overly deep queries | Gateway throttling/WAF/AppSync query controls |

**Validation ≠ authorization.** A payload `{"orderId":"O-1"}` can match the schema while the caller is still forbidden from reading someone else's order. **CORS ≠ authorization**: an allowed origin never replaces token or tenant checks.

### The "Fail Early, Verify Again" Principle

- Reject **obviously malformed** data as early as possible to avoid pointless backend invocations.
- Validate **business invariants and permissions** in the layer that owns the data, because backends may also be called via SDKs, event sources, internal services, or other entry points.
- Return error messages that help clients fix requests without exposing stack traces, SQL queries, ARNs/secrets, or user-existence details when sensitive.
- Always bound sizes, depths, and item counts to prevent CPU-heavy regexes or massive payloads from exhausting resources.

## 4. What Can a REST API Gateway Request Validator Do?

**API Gateway REST API** provides **request validators** attached to **methods**. When a request fails validation, the gateway rejects it with **HTTP `400`** before calling the integration.

Common validator modes:

- **Validate body:** Validates the body against a **Model JSON Schema** mapped to the request's `Content-Type`.
- **Validate query string parameters and headers:** Checks that parameters marked required are present.
- **Validate body, query string parameters, and headers:** Combines both checks.

**Limits to remember:**

1. For required path/query/header parameters, the gateway mainly verifies **presence and non-emptiness**; it **does not automatically validate format, numeric ranges, or semantic values** for those parameters.
2. For request bodies, the gateway selects a model by the request's **`Content-Type`**. If **no matching model exists**, body validation can be **skipped**; configure content-type mappings or a `$default` model appropriately.
3. API Gateway models use a **subset of JSON Schema Draft 4**; do not assume newer Draft keywords or every Java validator library feature is supported.
4. Gateway validation never checks business rules such as stock levels, ownership, order pricing, or tenant quotas.
5. After modifying REST API models or validators, you must **deploy/redeploy the stage** for clients to see the updated configuration.

### Structurally Invalid Request Example

~~~http
POST /orders HTTP/1.1
Host: abc123.execute-api.ap-southeast-1.amazonaws.com
Content-Type: application/json

{"customerId":"C-100", "quantity":"five"}
~~~

If the model requires `quantity` to be an integer and body validation is properly enabled, the gateway rejects it with `400 Bad Request` **before invoking Lambda**.

## 5. REST Model Example: Valid Order Request

Suppose `POST /orders` requires:

- `customerId`: non-empty string.
- `quantity`: integer, minimum 1.
- `sku`: required string.
- `note`: optional string.

File `order-request-model.json`:

~~~json
{
  "$schema": "http://json-schema.org/draft-04/schema#",
  "title": "CreateOrderRequest",
  "type": "object",
  "required": ["customerId", "sku", "quantity"],
  "properties": {
    "customerId": {
      "type": "string",
      "minLength": 1
    },
    "sku": {
      "type": "string",
      "minLength": 1
    },
    "quantity": {
      "type": "integer",
      "minimum": 1
    },
    "note": {
      "type": "string"
    }
  }
}
~~~

**Why still validate in the backend?** API Gateway checks JSON Schema syntax/types where supported before invoking the integration, but "does `sku` exist in inventory?", "does `quantity` exceed available stock?", and "is the caller authorized to order for this `customerId`?" must be enforced in the domain service.

### Configuring REST API Validation in the Console

1. Open **API Gateway → REST API** with the `POST /orders` method.
2. Under **Models**, create `CreateOrderRequest` with the schema above and content type `application/json`.
3. Create a **Request Validator** with **Validate request body** enabled (and required headers/params if needed).
4. In `POST`'s **Method Request**, bind the request model to `application/json` and select the validator.
5. Ensure requests cannot bypass validation via mismatched `Content-Type` headers; configure `$default` model behavior if appropriate per docs.
6. **Deploy the API** to the lab stage.
7. Send valid and invalid requests, checking Lambda Invocations and gateway responses; invalid payloads rejected by the validator must never reach the backend.

### Reference CLI Commands

~~~bash
aws apigateway create-model \
  --rest-api-id a1b2c3d4e5 \
  --name CreateOrderRequest \
  --content-type application/json \
  --schema file://order-request-model.json \
  --region ap-southeast-1 \
  --profile lab

aws apigateway create-request-validator \
  --rest-api-id a1b2c3d4e5 \
  --name validate-orders-body \
  --validate-request-body \
  --no-validate-request-parameters \
  --region ap-southeast-1 \
  --profile lab
~~~

These two commands create the resources **without attaching the validator or model to the method**. Set `requestValidatorId` and `requestModels` on the target REST method (via Console, IaC, or `aws apigateway update-method`), then deploy the stage. Do not repeatedly re-run resource creation commands if validation appears inactive before attaching and deploying.

## 6. JSON Schemas Must Match the Right Content-Type

Easy-to-miss pitfall:

~~~text
Request Content-Type: application/json
Method Request Model: application/json → CreateOrderRequest
Result: body is validated against the model when the validator is enabled.

Request Content-Type: text/plain
Method Request Model: application/json only
Result: body validation can be skipped depending on configuration.
~~~

A **`$default` model** can apply validation even when clients send another `Content-Type`. However, if an API strictly accepts JSON, enforce **`415 Unsupported Media Type`** via gateway/backend policy rather than blindly attempting to parse arbitrary payloads.

Distinguish clearly:

- **Body validation:** checks structure/constraints against the model.
- **Passthrough behavior / mapping templates:** governs how bodies are forwarded when an integration lacks a matching mapping template.
- **Content negotiation:** `Content-Type` describes the request body; `Accept` describes the response format the client wants.

A body `{"quantity":1}` is syntactically valid JSON that fails schema validation because `customerId` and `sku` are missing. A body `{quantity: 1}` is not valid JSON at all. Test both cases separately.

## 7. HTTP API Gateway: Validate in the Backend, Do Not Assume REST Models Exist

**HTTP API** is streamlined for common HTTP workloads and does not offer **REST API Request Validators/Models** with the same method-level setup. Therefore:

- Parse and validate request bodies inside **Lambda**, ECS/HTTP backends, or the application layer.
- Use **JWT/Lambda authorizers**, route-level IAM auth, and WAF/throttling where supported to block unauthorized or abusive traffic.
- Treat OpenAPI/JSON Schema/Bean Validation as the **application contract** and CI test suite rather than assuming importing an OpenAPI spec into HTTP API automatically enables full JSON body validation.
- Return `400` or `422` consistently per team standards with minimal, well-structured error details.

**Example:** HTTP API `POST /orders` → Java Lambda. Lambda must parse JSON, validate `quantity` and `sku`, and check caller permissions; the gateway handles authentication and routing, not REST-style schema validation.

### Never Push Business Validation into an Authorizer

An authorizer verifies identity and access scope—it should not query inventory stock or validate every order line item. Cramming business validation into an authorizer causes:

- Difficulty returning accurate field-level validation errors.
- Caching headaches and stale authorization decisions.
- Higher latency and unnecessary cost.
- Tangled responsibilities between validation and authorization.

Run AuthN/AuthZ at the appropriate gateway/security layer, and enforce business invariants in the backend service or resolver with consistent data access.

## 8. Java Lambda: Returning Structured HTTP 400 for Bad Input

With an API Gateway **Lambda proxy integration**, Lambda returns a response envelope such as:

~~~json
{
  "statusCode": 400,
  "headers": {
    "Content-Type": "application/problem+json",
    "Access-Control-Allow-Origin": "https://shop.example.com"
  },
  "body": "{\"type\":\"https://api.example.com/problems/validation\",\"title\":\"Invalid request\",\"status\":400,\"code\":\"VALIDATION_FAILED\"}"
}
~~~

**Important:** `body` in a proxy response is a **JSON string**, not an arbitrary nested Java object. While HTTP API payload format `2.0` supports inferred responses in simple cases, **returning an explicit response envelope** ensures compatibility, clarity, and exact control over status codes and headers.

### Java Handler Example with Input Validation

This example assumes the project packages `aws-lambda-java-core` and Jackson `ObjectMapper`. It expects an API Gateway proxy event containing `body`.

~~~java
package com.example.api;

import com.amazonaws.services.lambda.runtime.Context;
import com.amazonaws.services.lambda.runtime.RequestHandler;
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;

import java.util.LinkedHashMap;
import java.util.Map;

public final class CreateOrderHandler
    implements RequestHandler<Map<String, Object>, Map<String, Object>> {

    private static final ObjectMapper JSON = new ObjectMapper();
    private static final String ORIGIN = "https://shop.example.com";

    @Override
    public Map<String, Object> handleRequest(
        Map<String, Object> event, Context context) {

        String requestId = context.getAwsRequestId();

        try {
            String body = (String) event.getOrDefault("body", "");
            JsonNode input = JSON.readTree(body);

            if (input == null || !input.isObject()) {
                return problem(400, "INVALID_JSON",
                    "Request body must be a JSON object", requestId);
            }

            JsonNode customerId = input.path("customerId");
            JsonNode quantity = input.path("quantity");
            JsonNode sku = input.path("sku");

            if (!customerId.isTextual() || customerId.asText().isBlank()
                || !sku.isTextual() || sku.asText().isBlank()
                || !quantity.isIntegralNumber() || quantity.asInt() < 1) {
                return problem(400, "VALIDATION_FAILED",
                    "customerId, sku and positive quantity are required",
                    requestId);
            }

            // Production: verify auth/tenant, inventory, and idempotency,
            // persist the order in a transaction, then return the identifier.
            Map<String, Object> result = Map.of(
                "orderId", "ORD-LAB-1",
                "status", "ACCEPTED"
            );

            return reply(201, result, requestId, "application/json");
        } catch (com.fasterxml.jackson.core.JsonProcessingException ex) {
            return problem(400, "INVALID_JSON",
                "Request body is not valid JSON", requestId);
        } catch (Exception ex) {
            context.getLogger().log(
                "Unexpected error; requestId=" + requestId);
            // Never send stack traces or secrets back to clients.
            return problem(500, "INTERNAL_ERROR",
                "Internal server error", requestId);
        }
    }

    private Map<String, Object> problem(
        int status, String code, String detail, String requestId) {

        Map<String, Object> fields = new LinkedHashMap<>();
        fields.put("type", "https://api.example.com/problems/" + code);
        fields.put("title", "Request failed");
        fields.put("status", status);
        fields.put("code", code);
        fields.put("detail", detail);
        fields.put("requestId", requestId);

        return reply(status, fields, requestId, "application/problem+json");
    }

    private Map<String, Object> reply(
        int status, Object data, String requestId, String contentType) {
        try {
            return Map.of(
                "statusCode", status,
                "headers", Map.of(
                    "Content-Type", contentType,
                    "Access-Control-Allow-Origin", ORIGIN,
                    "Vary", "Origin",
                    "X-Request-Id", requestId
                ),
                "isBase64Encoded", false,
                "body", JSON.writeValueAsString(data)
            );
        } catch (Exception ex) {
            throw new IllegalStateException("Cannot serialize response", ex);
        }
    }
}
~~~

**Intentional limitations of this example:**

- This is an **illustrative handler**, not a production API: it omits authentication/authorization, transactions, idempotency, full schemas, and real order logic.
- The handler emits a static CORS header for an approved origin—**never blindly echo an arbitrary `Origin` header**. With multiple origins, match against an exact allowlist and include `Vary: Origin` when responses vary dynamically.
- On an **HTTP API with gateway CORS configured**, API Gateway **ignores CORS headers returned by the backend integration**; avoid conflicting logic in two places.
- `JsonNode.asInt()` can overflow or coerce unexpectedly on out-of-range numbers; in production, enforce explicit range and size checks.
- The Lambda artifact must bundle Jackson and configure the handler name and dependencies properly. Runtime serialization exceptions must still surface in logs/alarms and be handled cleanly.

## 9. AppSync GraphQL: What Does the Schema Validate Before Resolvers Run?

**AWS AppSync GraphQL APIs** rely on a schema defining **types, fields, arguments, input types, enums, and nullability**. The GraphQL engine parses and validates incoming operations before invoking field resolvers.

Schema example:

~~~graphql
schema {
  query: Query
  mutation: Mutation
}

enum OrderStatus {
  CREATED
  PAID
  CANCELLED
}

input CreateOrderInput {
  customerId: ID!
  sku: String!
  quantity: Int!
  note: String
}

type Order {
  id: ID!
  customerId: ID!
  sku: String!
  quantity: Int!
  status: OrderStatus!
}

type Query {
  getOrder(id: ID!): Order
}

type Mutation {
  createOrder(input: CreateOrderInput!): Order!
}
~~~

Conditions the GraphQL engine rejects before running resolvers:

- Querying a field that **does not exist** in the schema.
- Omitting or passing `null` for a non-null argument like `ID!`.
- Passing an input with an incompatible type or an undefined enum value.
- Syntax errors or invalid selection sets.
- Requests exceeding configured query complexity, depth, or resolver count limits.

**However, a GraphQL schema cannot inherently enforce that `quantity` must be between 1 and 20**, that `sku` is in stock, or which tenant owns the customer. Those checks belong in resolvers, pipelines, or backend services.

### Non-Null Matters on Both Inputs and Outputs

- `quantity: Int!`: clients must supply a non-null integer, **which does not mean `> 0`**.
- `status: OrderStatus!`: the resolver must return a valid, non-null enum value. If a data source returns `null` unexpectedly, GraphQL raises an error and **propagates null up to the nearest nullable parent field** per GraphQL rules.

Design nullable fields and error strategies deliberately so one minor field error does not wipe out the entire operation's `data` payload unnecessarily.

## 10. AppSync Business Validation in `APPSYNC_JS` Resolvers

AWS AppSync supports **`APPSYNC_JS`** and VTL resolvers. In `APPSYNC_JS`, use built-in utilities:

- `util.error(message, errorType, ...)`: raises a field error and **halts evaluation** at that point.
- `util.appendError(message, errorType, ...)`: records an error **without halting execution**, enabling partial data responses.
- `ctx.args`: GraphQL field arguments.
- `ctx.identity`: identity claims/context when authenticated.
- `ctx.result`, `ctx.error`: data-source result or error in the resolver context.

### Example Using a `NONE` Data Source to Illustrate Validation

Attach a **unit resolver `Mutation.createOrder`** to a **`NONE` data source** using the **`APPSYNC_JS`** runtime. No real database write occurs in this example.

~~~javascript
import { util } from '@aws-appsync/utils';

export function request(ctx) {
  const input = ctx.args.input;

  if (input.quantity < 1 || input.quantity > 20) {
    util.error(
      'quantity must be between 1 and 20',
      'VALIDATION_FAILED'
    );
  }

  if (input.sku.trim().length === 0) {
    util.error('sku must not be blank', 'VALIDATION_FAILED');
  }

  // NONE data source: payload becomes available at ctx.result in response().
  return {
    payload: {
      id: 'ORD-LAB-1',
      customerId: input.customerId,
      sku: input.sku,
      quantity: input.quantity,
      status: 'CREATED'
    }
  };
}

export function response(ctx) {
  if (ctx.error) {
    util.error('Unable to process order', 'INTERNAL_ERROR');
  }
  return ctx.result;
}
~~~

**This is strictly a learning example**; test string helpers and operators against the actual `APPSYNC_JS` runtime and schema. Never use a `NONE` data source to pretend an order was persisted. Production resolvers must verify user/tenant permissions, stock, and idempotency, writing through DynamoDB, Lambda, or HTTP data sources.

**Do not use `throw new Error(...)` as if running in Node.js:** `APPSYNC_JS` is a restricted runtime providing `util.error` for field errors and does not support all Web/Node APIs. It cannot open raw HTTP sockets or access a filesystem directly; all I/O flows through configured AppSync data sources.

### Equivalent VTL Snippet

For legacy VTL resolvers, you might write:

~~~vtl
#if($ctx.args.input.quantity < 1)
  $util.error("quantity must be positive", "VALIDATION_FAILED")
#end
$util.toJson($ctx.args.input)
~~~

This is a **validation snippet**, not a complete mapping template for every data source. Never copy this VTL request mapping straight onto DynamoDB and expect a valid `operation`/key payload.

## 11. AppSync Pipeline Resolvers and Step-Level Errors

With a pipeline resolver, you can separate stages cleanly:

~~~mermaid
flowchart LR
    Query[GraphQL createOrder] --> Schema[Schema validation]
    Schema --> Auth[AuthN/AuthZ]
    Auth --> R[Pipeline resolver]
    R --> V[Function 1: validate input / tenant]
    V --> I[Function 2: inventory check]
    I --> D[Function 3: DynamoDB conditional write]
    D --> Out[GraphQL response data/errors]
~~~

**Why are pipelines useful?**

- Business validation logic is reused across multiple field resolvers instead of duplicated.
- Validation → authorization → data operations stay cleanly separated via `ctx.stash` and `ctx.prev.result`.
- `util.error` aborts the pipeline immediately so invalid inputs never trigger writes.
- `util.appendError` lets the pipeline continue and return partial data **when doing so is business-safe**.

**Be careful:** Allowing a pipeline to continue after detecting an error during order creation can cause unwanted side effects. For state-changing mutations, **fail fast** and enforce database transactions/idempotency. `appendError` is better suited to partial reads or deliberately optional fields.

### GraphQL Resolver Errors Are Not Always HTTP 500

A GraphQL response can return HTTP `200` **with an `errors` array** when GraphQL execution runs but a field resolver fails. Parse/validation errors, auth failures, or transport errors may use other HTTP codes. **Clients must inspect HTTP status, `data`, and `errors`**, not just `response.ok`.

## 12. What Is CORS, and How Do Browsers Decide?

**Cross-Origin Resource Sharing (CORS)** is a mechanism where a server uses **response headers** to tell a browser which origins are allowed to read cross-origin responses from JavaScript.

An **origin** is defined by:

~~~text
scheme + host + port
~~~

Examples:

- `https://shop.example.com`
- `http://shop.example.com`
- `https://api.example.com`
- `https://shop.example.com:8443`

These four origins are all **distinct** due to differences in scheme, host, or port.

**CORS does not stop malicious requests from reaching your server.** Browsers may send certain requests before checking response headers, and non-browser clients ignore browser CORS altogether. **Never treat CORS as a firewall, CSRF defense, or IAM policy.**

### Simple Requests vs. Requests Requiring Preflight

Requests meeting *CORS-safelisted/simple* criteria can be sent directly by the browser—for instance, a `GET` with simple headers usually triggers no preflight.

Requests that typically trigger an **`OPTIONS` preflight**:

- `POST` with `Content-Type: application/json`;
- Requests carrying an `Authorization` header;
- Methods such as `PUT` or `DELETE`;
- Custom headers such as `X-Idempotency-Key`.

Exact rules follow the browser Fetch/CORS specification, so verify actual network behavior in DevTools rather than guessing from the HTTP method alone.

## 13. `OPTIONS` Preflight and Actual Response Flow

Suppose a frontend at `https://shop.example.com` executes:

~~~javascript
fetch('https://api.example.com/orders', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer <access-token>'
  },
  body: JSON.stringify({ customerId: 'C-100', sku: 'SKU-1', quantity: 2 })
});
~~~

The browser typically sends a **preflight** request first:

~~~http
OPTIONS /orders HTTP/1.1
Host: api.example.com
Origin: https://shop.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,content-type
~~~

Example server/gateway preflight response:

~~~http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://shop.example.com
Access-Control-Allow-Methods: GET,POST,OPTIONS
Access-Control-Allow-Headers: authorization,content-type
Access-Control-Max-Age: 300
Vary: Origin
~~~

Only if the browser accepts the preflight does it send the actual `POST`. The `POST` response must also carry matching CORS headers, for example:

~~~http
HTTP/1.1 201 Created
Content-Type: application/json
Access-Control-Allow-Origin: https://shop.example.com
Vary: Origin

{"orderId":"ORD-1001","status":"CREATED"}
~~~

**Configuring `OPTIONS` alone is not enough.** If the backend returns `201` without `Access-Control-Allow-Origin`, the browser still blocks JavaScript from reading the response. Similarly, if the backend returns `400`/`401`/`403`/`500` without CORS headers, the client sees a generic "CORS error" instead of the real error payload.

~~~mermaid
sequenceDiagram
    participant Browser as Browser frontend
    participant API as API Gateway / AppSync endpoint
    participant Backend as Backend / Resolver
    Browser->>API: OPTIONS + Origin + requested method/headers
    API-->>Browser: CORS preflight response
    alt Allowed
      Browser->>API: POST /orders + token + JSON
      API->>Backend: Invoke if auth/validation pass
      Backend-->>API: 201 or 4xx/5xx
      API-->>Browser: Response + CORS headers
    else Rejected
      Note over Browser: Does not send actual fetch request
    end
~~~

## 14. REST API Gateway CORS: Proxy vs. Non-Proxy Differences

### 14.1. Non-Proxy Integration

For REST API **non-proxy integrations** (using mapping templates), setup usually involves:

1. Creating an unauthenticated `OPTIONS` method for standard preflight requests.
2. Using a **MOCK integration** (or suitable backend) returning:
   - `Access-Control-Allow-Origin`
   - `Access-Control-Allow-Methods`
   - `Access-Control-Allow-Headers`
3. Ensuring **method response / integration response mappings** inject CORS headers into **actual responses** across supported status codes.
4. Checking whether binary media types like `*/*` require `contentHandling=CONVERT_TO_TEXT` on preflight if applicable.
5. **Redeploying the REST API stage** for changes to take effect.

The Console's **Enable CORS** wizard does not guarantee every integration and error response is configured completely. After enabling it, always **test both preflight and all actual responses**.

### 14.2. Lambda Proxy Integration

With REST API **Lambda proxy**, the backend must return CORS headers on actual responses. The gateway **does not run typical integration response mappings** to add CORS headers automatically on proxy responses.

Example (Node.js, illustrating response shape only):

~~~javascript
export const handler = async (event) => ({
  statusCode: 400,
  headers: {
    'Content-Type': 'application/problem+json',
    'Access-Control-Allow-Origin': 'https://shop.example.com',
    'Vary': 'Origin'
  },
  body: JSON.stringify({
    code: 'VALIDATION_FAILED',
    message: 'quantity must be positive'
  })
});
~~~

`OPTIONS` can be handled by a `MOCK` `OPTIONS` method or a backend route depending on design. **Never require a JWT/Lambda authorizer token on standard preflight `OPTIONS` requests**, since browsers do not send bearer tokens during preflight.

### 14.3. Gateway-Generated Errors: Gateway Responses

Even when Lambda returns full CORS headers, API Gateway itself can still generate errors:

- `UNAUTHORIZED`, `ACCESS_DENIED`;
- `BAD_REQUEST_BODY`, `BAD_REQUEST_PARAMETERS`;
- `MISSING_AUTHENTICATION_TOKEN`;
- `THROTTLED`, `DEFAULT_4XX`, `DEFAULT_5XX`;
- Configuration/integration failures.

On **REST API**, **Gateway Responses** let you customize bodies, status codes, and headers for these gateway-generated responses. Add `Access-Control-Allow-Origin` there so browsers see the real `4xx`/`5xx` status instead of a misleading CORS error.

**Be careful:** Gateway Responses do not override responses returned by Lambda itself. If your backend returns `400` or `409`, ensure the **backend/integration response** includes CORS headers. When using **WAF custom responses** on REST API, verify precedence relative to Gateway Responses.

## 15. HTTP API Gateway CORS: API-Level Configuration

In **HTTP API**, the CORS configuration includes:

- `allowOrigins`
- `allowMethods`
- `allowHeaders`
- `allowCredentials`
- `exposeHeaders`
- `maxAge`

When CORS is enabled on an HTTP API, **API Gateway automatically handles `OPTIONS` preflight** and attaches configured CORS headers to integration responses. **Once gateway CORS is configured, API Gateway ignores any CORS headers returned by the backend** during CORS processing. This is a major difference from REST Lambda proxy.

### HTTP API CORS Configuration Example

File `http-api-cors.json`:

~~~json
{
  "AllowOrigins": ["https://shop.example.com"],
  "AllowMethods": ["GET", "POST", "OPTIONS"],
  "AllowHeaders": [
    "content-type",
    "authorization",
    "x-idempotency-key"
  ],
  "AllowCredentials": false,
  "ExposeHeaders": ["x-request-id"],
  "MaxAge": 300
}
~~~

Apply to an existing lab API:

~~~bash
aws apigatewayv2 update-api \
  --api-id a1b2c3d4 \
  --cors-configuration file://http-api-cors.json \
  --region ap-southeast-1 \
  --profile lab
~~~

This uses the **API Gateway v2 AWS CLI** for HTTP API, not `aws apigateway` (REST API v1). Check your stage's auto-deploy setting; changes may require a manual deployment if auto-deploy is disabled.

### When a `$default` Route Has an Authorizer

`$default` catches unmatched paths and methods, including `OPTIONS`. If `$default` has an authorizer attached and a preflight request lacks a token, the preflight fails with `401`.

Per AWS HTTP API guidance, create an unauthenticated **`OPTIONS /{proxy+}`** route pointing to an appropriate integration, which takes routing priority over `$default`. Exempt only the preflight route from auth; **actual `POST`/`GET` routes must remain authenticated and authorized**.

**Never open all methods to public access** just to fix an `OPTIONS` error.

## 16. AppSync GraphQL and CORS: Not Configured Like REST

AWS AppSync exposes a managed **GraphQL HTTPS endpoint** handling GraphQL requests and responses; browser clients typically `POST` JSON containing queries, variables, and authorization/API-key headers.

Key distinctions for CORS in AppSync:

- AppSync manages the protocol and headers of its **managed GraphQL endpoint**. There is no REST-style `OPTIONS` `MOCK` method to toggle on like API Gateway REST.
- `APPSYNC_JS`/VTL includes helpers for **certain custom response headers**, but you **cannot arbitrarily override standard CORS headers** like `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, or `Access-Control-Allow-Headers` via `util.http.addResponseHeader` because they are **restricted response headers**.
- If you must **restrict frontend origins** under a custom policy, evaluate placing **CloudFront** or a secure proxy in front of AppSync using a proper **response headers policy + origin request/cache policy** compatible with GraphQL per AWS-supported patterns.
- Avoid custom proxies that break **authorization headers, API keys/Host headers, WebSocket subscription handshakes**, caching, or response content types.
- Never treat CORS as access control for **who may call your GraphQL API**; AppSync authentication modes and field-level authorization enforce access control.

**Practical steps:** Inspect requests to the AppSync endpoint in DevTools; if CloudFront or a custom domain sits in front, determine **which layer emits the CORS headers**. A CORS error may stem from a proxy caching headers for the wrong origin, WAF/CloudFront blocking preflight, or a `403` lacking headers—do not tweak resolver business validation to cure a browser policy issue.

## 17. CORS, Cookies, Credentials, and Security Issues

### 17.1. Never Use Wildcards with Credentialed CORS Responses

When a browser sends a cross-origin request with **credentials mode `include`** (cookies or ambient HTTP auth), responses must specify an **exact origin**, never:

~~~http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
~~~

That combination is **rejected by browsers for credentialed CORS**. Configure instead:

~~~http
Access-Control-Allow-Origin: https://shop.example.com
Access-Control-Allow-Credentials: true
Vary: Origin
~~~

Match incoming origins strictly against an approved allowlist. **Never blindly reflect any arbitrary `Origin` header** alongside `Allow-Credentials: true`, or a malicious site could read user data whenever cookies/auth permit.

### 17.2. Cookies, `SameSite`, and CSRF

CORS governs **whether scripts can read cross-origin responses**, not full **Cross-Site Request Forgery (CSRF)** protection. For cookie-based sessions:

- Set **`Secure`, `HttpOnly`, and `SameSite`** per your threat model;
- enforce CSRF tokens or origin checks on state-changing endpoints where needed;
- never allow untrusted origins with credentials;
- manage cookie domain, path, expiration, and session invalidation carefully.

For bearer tokens in `Authorization` headers, protect frontend tokens against XSS; properly configured CORS alone does not mitigate XSS or token theft.

### 17.3. Preflight Caching and Per-Origin Headers

`Access-Control-Max-Age` lets browsers cache preflight responses up to browser-enforced caps. If your server sets `Access-Control-Allow-Origin` dynamically based on `Origin`, include **`Vary: Origin`** so HTTP caches do not serve origin A's CORS headers to origin B.

Behind **CloudFront/CDNs**, inspect cache keys and origin forwarding, especially for credentialed requests or per-user data. **Never cache authenticated GraphQL or REST responses in a shared CDN layer** without an explicit cache-partitioning and authorization strategy.

### 17.4. CORS Cannot Stop Non-Browser Clients

An attacker using scripts, servers, or CLIs is unaffected by browser CORS. Securing an API requires:

- Authentication (JWT/Cognito/IAM/OIDC/Lambda authorizer);
- Resource- and tenant-level authorization;
- Rate limiting/WAF and input validation;
- VPC network boundaries where appropriate;
- Logging, monitoring, and abuse detection.

**Never rely on an allowed-origins list as your API's sole security control.**

## 18. Consistent REST/HTTP Error Contracts

APIs should publish and test a documented **error contract**. For example, basing errors on **RFC 9457 Problem Details for HTTP APIs**:

~~~http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
Access-Control-Allow-Origin: https://shop.example.com
X-Request-Id: req-7ac21
~~~

~~~json
{
  "type": "https://api.example.com/problems/validation",
  "title": "Invalid request",
  "status": 400,
  "detail": "One or more fields are invalid",
  "instance": "/orders",
  "code": "VALIDATION_FAILED",
  "requestId": "req-7ac21",
  "invalidParams": [
    {
      "name": "quantity",
      "reason": "must be between 1 and 20"
    }
  ]
}
~~~

**`code`, `requestId`, and `invalidParams` are application-defined extension fields**, not all required by the RFC. `title` and `detail` are client-facing and must never dump stack traces publicly.

### Choosing Status Codes

| Scenario | Typical HTTP status | Suggested error code |
| --- | --- | --- |
| Invalid JSON syntax or schema | **`400 Bad Request`** | `INVALID_JSON` / `VALIDATION_FAILED` |
| Unsupported content type | **`415 Unsupported Media Type`** | `UNSUPPORTED_MEDIA_TYPE` |
| Missing or invalid credentials | **`401 Unauthorized`** | `UNAUTHENTICATED` |
| Authenticated identity lacks permission | **`403 Forbidden`** | `ACCESS_DENIED` |
| Resource does not exist | **`404 Not Found`** | `ORDER_NOT_FOUND` |
| Conflicting resource state | **`409 Conflict`** | `ORDER_ALREADY_EXISTS` |
| Syntactically valid input violating business rules | **`400`** or **`422 Unprocessable Content`** per contract | `INVALID_QUANTITY` |
| Too many requests | **`429 Too Many Requests`** | `RATE_LIMITED` |
| Unexpected service failure | **`500 Internal Server Error`** | `INTERNAL_ERROR` |
| Gateway or integration error | **`502 Bad Gateway`** | `UPSTREAM_ERROR` |
| Backend temporarily unavailable | **`503 Service Unavailable`** | `SERVICE_UNAVAILABLE` |
| Integration timeout | **`504 Gateway Timeout`** | `UPSTREAM_TIMEOUT` |

**Do not mechanically use `422` for every business error.** If your API standardizes on `400` for input/business validation, stay consistent; reserve `409` for resource state conflicts and `403` for genuine permission denials.

### Correlation IDs and Retry Hints

- Generate or propagate a **request ID / correlation ID** linking gateway logs → Lambda → RDS/SQS.
- On **`429`/`503`**, consider returning `Retry-After` when a useful backoff window is known.
- On timeouts or transient failures, clients should use **exponential backoff + jitter** and **idempotency keys** to prevent duplicate side effects.
- Avoid sending a fixed `Retry-After` when the backend has no estimate of recovery time.

## 19. Distinguishing Gateway Errors, Integration Errors, and Application Errors

### 19.1. Gateway Rejects Before Reaching the Backend

For example, REST request model validation fails. Lambda **is never invoked**, and API Gateway returns `400` directly. To customize bodies and CORS headers on these errors, configure **REST Gateway Responses** for the relevant response types.

### 19.2. Lambda Intentionally Returns a Business Error

Lambda executes and returns:

~~~json
{
  "statusCode": 409,
  "headers": {
    "Content-Type": "application/problem+json",
    "Access-Control-Allow-Origin": "https://shop.example.com"
  },
  "body": "{\"code\":\"ORDER_ALREADY_EXISTS\",\"detail\":\"Order already exists\"}"
}
~~~

This is an **application-level response**. With Lambda proxy returning a valid status and body, API Gateway passes it through per the integration mode—it does not convert `409` into `500`.

### 19.3. Lambda Throws an Exception or Returns a Malformed Envelope

If Lambda throws an unhandled exception, times out, or returns an invalid proxy structure, API Gateway can return **`5xx` such as `502`** depending on the integration. **A runtime crash is not equivalent to returning `{"statusCode":400}`.**

In REST **non-proxy** mode, response mappings and integration response selection patterns map backend errors to status codes; misconfiguration can cause unexpected `5xx` or wrong statuses. Inspect integration logs and status codes before mistakenly editing business logic.

### 19.4. Authentication and Throttling

Authorizers, IAM, WAF, or throttling can reject requests **before Lambda executes**. Check:

- `401`: missing, malformed, or expired token;
- `403`: explicit deny, missing scope, resource/method policy, WAF block, or insufficient permissions;
- `429`: throttled by API/usage limits or backend per actual response;
- `5xx`: integration/config failure or backend error.

**Classify `401`/`403` using the actual API type and authorizer behavior**, as certain AWS response names/codes have quirks. Never assume `Missing Authentication Token` always means the client forgot a header—on REST API, it also appears when calling a nonexistent route, method, or stage.

## 20. How Do GraphQL Error Contracts Differ from HTTP Status Codes?

A typical AppSync/GraphQL response:

~~~json
{
  "data": {
    "getOrder": null
  },
  "errors": [
    {
      "path": ["getOrder"],
      "locations": [
        {"line": 2, "column": 3}
      ],
      "message": "Order not found",
      "errorType": "NOT_FOUND"
    }
  ]
}
~~~

**Characteristics:**

- `data` can contain **partial success** alongside `null` fields.
- `errors` lists GraphQL errors; AppSync adds `errorType` and other AWS-specific fields.
- `path` pinpoints which field failed, vital when a single query fetches multiple branches.
- If a failing field is **non-null**, GraphQL **bubbles `null` up** to the nearest nullable parent, potentially yielding `data: null`.
- **HTTP `200` can still contain `errors`**; meanwhile, auth, validation, or transport failures may return non-200 HTTP codes. Clients must check both.

### Partial Data Example

Suppose a query runs:

~~~graphql
query HomePage {
  getOrder(id: "ORD-1001") {
    id
    status
  }
  listProducts {
    id
    name
  }
}
~~~

If `getOrder` fails while `listProducts` succeeds, the response can carry product data alongside the order error. This is an **intentional GraphQL feature**, not a mistake that should automatically be turned into HTTP `500`.

### `util.error` vs. `util.appendError`

- **`util.error`:** Right when a field cannot proceed, such as validation/auth failures or required data errors.
- **`util.appendError`:** Right when returning partial useful data plus an error notice for the client, provided non-null constraints are respected and no unsafe side effects occur.

**Never pass raw `ctx.error.message` or full AWS SDK exceptions straight to clients**: responses can leak table ARNs, keys, internal data, or permission details.

## 21. AppSync Authorization Does Not Replace Schema Validation

AppSync supports configurable authorization modes: **`API_KEY`**, **`AWS_IAM`**, **`AMAZON_COGNITO_USER_POOLS`**, **`OPENID_CONNECT`**, and **`AWS_LAMBDA`** as supported. Schema directives restrict which modes may access individual fields.

Key distinctions:

- **Authentication:** Who is the caller? Enforced via JWT, IAM SigV4, API key, or Lambda authorizer per API config.
- **Authorization:** May the caller invoke `Mutation.createOrder` or read `Order.customerId`?
- **Schema validation:** Does the operation match declared types, fields, and arguments?
- **Business validation:** Is quantity valid, can the order be created, and does the tenant own the resource?

**An API key is not trustworthy user authentication for sensitive data.** API keys suit appropriate lab or public scenarios, whereas production requires proper authn/authz modes and key lifecycle hygiene.

### Query Complexity and Abuse Protection

GraphQL clients can send deeply nested fields, aliases, and fragments triggering expensive resolver trees. Beyond schema validation:

- Configure **query depth limits** and **resolver count limits** per AppSync features;
- authenticate and authorize every operation and field;
- enforce pagination and list size caps;
- optimize DynamoDB/RDS queries to eliminate N+1 backend calls;
- enable logging/metrics and WAF where supported.

**A schema-valid query can still overload your backend** if resource consumption is unbounded.

## 22. CORS and GraphQL Subscriptions Over WebSockets

GraphQL subscriptions use a **WebSocket/real-time endpoint** with a different authorization handshake from regular HTTP `POST` calls. With AppSync:

- Do not treat **`fetch` CORS preflight** as governing WebSocket connections.
- When placing **CloudFront, a custom domain, or a proxy** in front of AppSync, properly handle `Origin`/`Host` headers, connection upgrades, WebSocket handshakes, and auth tokens.
- Browsers apply `Origin` headers differently on WebSockets; servers/proxies must still validate allowed origins and authentication.
- Working queries/mutations do not prove **subscriptions** work; test connection setup, reconnects, token expiration, and error handling separately.

**Security takeaway:** CORS response headers do not replace authentication or authorization on WebSocket subscriptions.

## 24. CORS Lab with `OPTIONS`, `curl`, and DevTools

### 24.1. Send a Manual Preflight

~~~bash
curl -i -X OPTIONS \
  "https://api.example.com/orders" \
  -H "Origin: https://shop.example.com" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type,authorization"
~~~

Verify the response:

- Preflight HTTP status succeeds per configuration;
- `Access-Control-Allow-Origin` matches the origin;
- `Access-Control-Allow-Methods` includes `POST`;
- `Access-Control-Allow-Headers` permits `content-type,authorization`;
- `Access-Control-Allow-Credentials` is present only if credentials are used, without invalid wildcards.

**`curl` does not enforce browser CORS policies.** It only shows raw HTTP headers; to prove a browser accepts the response, open DevTools and run a real `fetch`.

### 24.2. Test a Disallowed Origin

~~~bash
curl -i -X OPTIONS \
  "https://api.example.com/orders" \
  -H "Origin: https://evil.invalid" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"
~~~

The response must not grant CORS access to this origin if only `https://shop.example.com` is allowed.

### 24.3. Test Actual `401`/`400`/`500` Responses

In browser DevTools Network:

1. Verify whether the `OPTIONS` preflight succeeded.
2. If so, inspect the actual `POST` response status and CORS headers.
3. Test missing/expired tokens (`401`/`403`), invalid payloads (`400`), and simulated backend errors (`500`) in lab.
4. Confirm the client can **read the error body** on approved origins, not just `2xx` responses.
5. Check `Vary: Origin` and CloudFront caching when supporting multiple origins.

**A `curl -i` returning `200` does not prove CORS works** until you test with `Origin` and verify the actual response in a browser.

## 26. Observability: Find the Exact Fault Before Fixing

### API Gateway

Monitor:

- `4XXError` and `5XXError` by API/stage;
- **`Latency`** and **`IntegrationLatency`** to separate gateway overhead from backend slowness;
- request counts, throttling, and cache metrics where supported;
- **access logs** with request ID, route/method, status, integration status, and latency;
- **REST execution logs** when enabled appropriately, avoiding sensitive payload logging.

**Never turn on full request/response data tracing permanently in production** if it risks logging tokens, PII, or secrets. Align logging granularity with security and cost policies.

### AppSync

Monitor:

- request, latency, and error metrics emitted by AppSync per configuration;
- resolver errors and field-level logs at appropriate verbosity;
- DynamoDB throttling/conditional check failures, Lambda errors, and RDS/data-source latency;
- schema updates, query depth/complexity rejections, and auth failures;
- tracing/X-Ray where supported.

### Lambda / Backend

Monitor:

- **`Invocations`, `Errors`, `Duration`, `Throttles`**;
- structured error logs and correlation IDs;
- DB connection pools, transaction failures, `ConditionalCheckFailed`, rate limits, and retries;
- downstream call costs and cache efficiency.

## 27. Troubleshooting: Symptom → Cause Map

| Symptom | High-probability cause | How to verify |
| --- | --- | --- |
| Browser reports CORS, `curl` returns body | `OPTIONS` or actual response missing/wrong CORS headers | DevTools, `curl` with `Origin`, check both `2xx` and `4xx` responses |
| Preflight returns `401` | Authorizer applied to `OPTIONS`, or `$default` catches it | Exempt `OPTIONS` route from auth while keeping auth on actual methods |
| Preflight `204`, yet `POST` still CORS-blocked | Actual `POST` response lacks `Access-Control-Allow-Origin` | Inspect backend proxy / Gateway Responses / CDN |
| `Access-Control-Allow-Origin: *` with credentials | Wildcards are invalid for credentialed requests | Match exact origin, `Allow-Credentials`, cookies/`SameSite` |
| Origin A works, Origin B gets wrong header | CDN/cache ignores `Origin`, missing `Vary` | Cache key/policy, `Vary: Origin`, edge layer |
| REST validator never runs | Validator/model not attached to method, wrong `Content-Type`, or stage not redeployed | Method Request, Model content type, deployment/stage |
| REST returns `400` before Lambda | Required params/body failed model schema | Gateway execution logs, request validator settings |
| HTTP API lacks REST validator options | Different API type | Validate in Lambda/backend; do not look for REST Models |
| REST API returns `Missing Authentication Token` | Wrong route/method/stage or auth issue | URL, base path mapping, method/route, authorizer |
| HTTP API returns `404`/`403` via `$default` | Route/authorizer/default priority | Routes, JWT config, `OPTIONS` precedence |
| Lambda proxy returns `502` | Handler crash or invalid response format (`body` not a string) | Lambda logs, proxy event/response contract |
| API Gateway `504` | Integration timeout or slow downstream | `IntegrationLatency`, Lambda/DB/network logs, timeouts |
| Backend `400` lacks CORS | App only sets headers on success responses | Error middleware / response mapping on `4xx`/`5xx` |
| AppSync field returns `null` with errors | Resolver/data source/GraphQL non-null propagation | GraphQL `errors.path`/`errorType`, resolver logs |
| AppSync query rejected for wrong field | Schema parsing/validation | Query + variables vs. schema, Console schema |
| GraphQL `200` treated as success by client | Client only checks HTTP status, ignoring `errors` | Parse `data` and `errors` envelope, test partial data |
| AppSync `MappingTemplate` error | Invalid VTL/JS request or response mapping | Resolver runtime, code, test/evaluate, logs |
| AppSync returns `Unauthorized` | Auth mode, API key, JWT, IAM, or field directive mismatch | Headers, token claims, IAM action, schema auth directives |
| Rising timeouts/`5xx` under load | DB locks, throttling, Lambda concurrency, overly deep queries | Logs/traces, DB metrics, AppSync limits, retries |
| Lambda retries create duplicate orders | Missing idempotency on client `POST` retries | Idempotency keys, conditional writes/transactions, logs |

### 9-Step Investigation Workflow

~~~text
1. Identify API type: API Gateway REST / HTTP / AppSync GraphQL.
2. Identify client: browser vs. curl/server; URL, method, origin, auth mode.
3. For browsers: inspect OPTIONS preflight and the actual request separately in DevTools.
4. Check HTTP status, CORS headers, request ID, and response body.
5. For REST: check Model/Validator, method/stage deployment, and Gateway Responses.
6. For HTTP API: check Routes/$default, authorizer, and CORS config.
7. For AppSync: check schema/variables/auth and data/errors/path/errorType.
8. Inspect backend/resolver logs, data sources, and network/IAM/KMS as needed.
9. Fix one root cause, re-run happy-path + negative tests, and monitor metrics.
~~~

**Never "fix" errors by** allowing all origins with credentials, disabling authorizers API-wide, granting `AdministratorAccess`, raising timeouts indefinitely, or returning HTTP `200` for every business failure.

## 28. API Security: Validation and CORS Cannot Stand Alone

An AWS API requires defense in depth:

1. **IAM/Cognito/OIDC/Lambda authorizers:** Authenticate callers per API type and enforce method/field/resource permissions.
2. **Backend authorization:** Ensure tenants/users cannot access other users' records, even when inputs are schema-valid.
3. **Input validation:** Validate types, ranges, and required fields; normalize/encode inputs; bound payload sizes, query depth, and batch sizes.
4. **CORS allowlist:** List exact frontend origins, never echo arbitrary origins, and handle cookies carefully.
5. **Throttling/WAF:** Cap request rates and protect APIs against abuse and cost spikes.
6. **TLS:** Enforce HTTPS endpoints with ACM custom domain certificates, plus backend TLS/PrivateLink/VPC controls as needed.
7. **IAM/KMS/data:** Least-privilege Lambda execution roles, Secrets Manager, S3 SSE-KMS, DynamoDB/RDS authorization, and auditing.
8. **Logging/tracing:** Log request IDs, statuses, and error codes without secrets or PII, with bounded retention.
9. **Resilience:** Retries with backoff and idempotency, DLQs/queues for async processing, backups, and Multi-AZ data durability.
10. **CI/CD:** Manage request models, validators, CORS, gateway responses, and AppSync schemas/resolvers in IaC, tested before production.

### Tenant Isolation Example

A GraphQL client sends:

~~~graphql
query {
  getOrder(id: "ORDER-OF-OTHER-TENANT") {
    id
    customerId
  }
}
~~~

This query is **schema-valid**, yet the resolver/backend must compare the caller's verified tenant/user identity against the order owner. Without that check, valid CORS, valid JWTs, and passing schema validation **will not prevent unauthorized access (BOLA/IDOR)**.

**Never rely solely on the frontend** hiding UI buttons or passing a client-supplied `tenantId`; the backend must read `sub`/tenant from verified auth claims and authorize against the real resource.

## 29. Reliability, Availability, and Cost Control

### Illustrative E-Commerce Architecture via REST and GraphQL

~~~mermaid
flowchart TB
    Web[Frontend HTTPS / CloudFront] --> Rest[API Gateway /orders]
    Web --> Gql[AppSync GraphQL]
    Rest --> Validation[REST validator / backend validation]
    Validation --> Lambda[Lambda Orders API]
    Gql --> Resolver[AppSync schema + resolvers]
    Resolver --> DDB[(DynamoDB)]
    Lambda --> DDB
    Lambda --> Queue[(SQS: OrderCreated)]
    Queue --> Worker[Lambda invoice worker]
    Worker --> S3[(S3 invoices / SSE-KMS)]
    Rest --> CW[CloudWatch / alarms]
    Gql --> CW
    Lambda --> CW
    Resolver --> CW
~~~

**Design points:**

- REST and GraphQL maintain distinct **validation contracts**; keep auth and business rules consistent if both serve the same underlying data.
- **Throttling**, API limits, and AppSync query depth protect backends from unreasonable traffic; a single resolver bug does not automatically make a system HA.
- Lambda scales quickly, while **RDS/DB/SQS/KMS have quotas and costs**; apply backpressure, retries, and idempotency.
- DynamoDB has service/Region characteristics; S3 backups/versioning and RDS Multi-AZ or replication must align with RTO/RPO targets.
- For multi-Region or multi-origin frontends, align CORS allowlists, custom domains, DNS, and disaster recovery with real environments.
- CloudWatch logs and traces connect failed client requests across gateway, resolver, and data layers.
- AWS Budgets, Cost Explorer, and CloudWatch alarms detect traffic bursts, retry loops, and runaway logging costs.

### Cost Components to Estimate

| Component | When costs increase |
| --- | --- |
| **API Gateway API requests** | Request volume, API type, caching/data transfer per features |
| **AppSync operations and real-time** | GraphQL queries/mutations/subscriptions, connection minutes/messages per pricing |
| **Lambda** | Invocations, GB-seconds duration, provisioned concurrency, logs |
| **DynamoDB/RDS** | Reads/writes, throughput/capacity, connections, storage |
| **CloudWatch/X-Ray** | Access/execution logs, field logs, metrics/traces |
| **WAF/CloudFront** | Rules/requests, caching, Internet data transfer |
| **KMS/S3/SQS** | Data/API calls, encryption key requests, retries/DLQs |

**Sensible validation reduces wasted backend invocations**, though gateway/resolver calls and logs still incur charges. Never leave verbose field-level logging enabled indefinitely across all of production just to debug a minor issue—use sampling, masking, and bounded retention.

## 30. Practice Exercises

### Exercise 1 — REST Validator Fails to Block Request

**Prompt:** A REST API has `POST /orders` with model `CreateOrderRequest` mapped to `application/json`. A client sends `Content-Type: text/plain` with JSON missing `sku`, and the request still reaches Lambda.

**Task:** Explain why body validation was bypassed; propose `$default` model usage, content-type enforcement, and test cases; distinguish this from backend parser errors. Confirm the stage was redeployed.

### Exercise 2 — Misleading CORS Error Hides a `401`

A frontend at `https://shop.example.com` calls the API with an expired Bearer token. The browser reports a CORS block, while CloudWatch API Gateway logs show `401`.

Inspect `OPTIONS` preflight, the actual `401` response, the authorizer, and Gateway Responses / HTTP API CORS settings. The goal is to **return `401` with valid CORS headers**, not disable auth.

### Exercise 3 — `$default` Route Blocks `OPTIONS`

An HTTP API attaches a JWT authorizer to the `$default` route. A browser `POST`s JSON from an allowed origin, but `OPTIONS` preflight fails with `401`.

**Task:** Explain route matching, create an unauthenticated `OPTIONS /{proxy+}` route per AWS docs, and verify actual `POST` requests still enforce the JWT authorizer.

### Exercise 4 — GraphQL Schema Passes, Business Rule Fails

A mutation passes `quantity: -10` to an `Int!` input. GraphQL accepts the type, and the resolver writes negative data.

**Task:** Add `quantity >= 1` validation, distinguish it from schema validation, use `util.error`, and test `data`/`errors`. If both REST and GraphQL APIs create orders, propose sharing domain invariants in a common service/transaction layer.

### Exercise 5 — GraphQL HTTP `200` with `errors`

A GraphQL query requests `getOrder` and `listProducts`. `getOrder` errors while `listProducts` succeeds, returning HTTP `200`.

**Task:** Draft a response showing partial `data` and `errors.path`, update client logic so `response.ok` is not equated with "every field succeeded," and explain null bubbling when the schema specifies `Order!`.

### Exercise 6 — CORS and Cookies

A frontend sets `credentials: 'include'`, and the server returns `Access-Control-Allow-Origin: *` alongside `Access-Control-Allow-Credentials: true`.

**Task:** Identify the Fetch/CORS violation, fix it with exact origin + credentials + `Vary`, evaluate CSRF/`SameSite`/`HttpOnly`/`Secure`, and explain why arbitrary origin reflection is unsafe.

### Exercise 7 — Lambda Proxy Returns `502`

A Java Lambda behind an HTTP API returns `body` as a `Map` instead of a JSON string in its proxy response depending on handler/version, causing `502` errors in production.

**Task:** Check `payloadFormatVersion` `1.0`/`2.0`, raw Lambda output, CloudWatch logs, and response envelope shape/status/headers, then test both a `400` and a `201` response with CORS.

### Exercise 8 — Cost and Abuse

AppSync receives deeply nested GraphQL queries where each resolver fetches many DynamoDB items, causing rapid spikes in gateway and DB call volume.

**Task:** Recommend query depth/resolver count limits, pagination, auth, WAF, metrics, appropriate caching, budgets, and load testing; explain why "schema-valid query" does not guarantee "cost-safe query."

## 31. Pre-Production Checklist

- [ ] Confirmed whether **REST API, HTTP API, or AppSync GraphQL** is used and verified which features that type actually supports.
- [ ] Defined clear request/response contracts and validation policies: schema, required fields, types, ranges, and business invariants.
- [ ] REST API models and request validators attached to the right methods and content types, stage redeployed, and tested.
- [ ] HTTP API validates payloads in the backend without assuming REST Request Validators exist.
- [ ] AppSync schema validates queries/variables, while resolvers/pipelines enforce business rules and authorization.
- [ ] CORS is never confused with authentication/authorization; backend enforces resource/tenant checks.
- [ ] Allowed origins use an explicit allowlist; never use wildcards with credentialed CORS.
- [ ] `OPTIONS` preflight works without unnecessary auth while actual requests enforce auth properly.
- [ ] CORS headers are present on both **`2xx` and `4xx`/`5xx`** responses per API/integration type and verified in a browser.
- [ ] For REST proxy, backend returns CORS headers; for HTTP API with CORS enabled, gateway manages headers; AppSync does not override CORS inside resolvers.
- [ ] For multiple origins/caching, `Vary: Origin` and a proper CloudFront cache policy are configured.
- [ ] Error contracts include HTTP status/GraphQL errors, error code, message, and request ID without leaking stack traces or PII.
- [ ] GraphQL clients check `errors` even on HTTP `200`, handling partial data and non-null propagation.
- [ ] Lambda proxy response `body` is a JSON string matching the contract, with integration mappings tested.
- [ ] Tested `401`/`403`/`404`/`409`/`429`/`500`/`502`/`504` cases along with retry/backoff/idempotency rules.
- [ ] AppSync enforces auth modes/field directives, query depth/resolver limits, and scoped data-source permissions.
- [ ] CloudWatch access/field logs, metrics/traces, and alarms are configured with sensitive fields masked.
- [ ] VPC, IAM, KMS, RDS/S3/DynamoDB, and quotas are reviewed holistically alongside the API—not just gateway settings.
- [ ] IaC, code review, deployment versioning/rollbacks, and negative tests are integrated into CI/CD.
- [ ] Budgets monitor API requests, resolver/DB calls, Lambda, CloudWatch, and WAF/CloudFront spend.

## 32. Summary

**Validation**, **CORS**, and **error handling** are three distinct responsibilities that directly shape API reliability and security:

- **Validation**: API Gateway REST can reject invalid bodies and required params via **Models and Request Validators**; HTTP API typically delegates validation to the backend; AppSync uses the **GraphQL schema** and **resolvers/pipelines** for structural and business checks.
- **CORS**: Browsers validate origin, preflight, and response headers; **REST proxy**, **HTTP API CORS configuration**, and **AppSync GraphQL** each handle CORS differently. CORS **never grants permissions and never blocks non-browser clients**.
- **Error handling**: HTTP APIs need clear status codes and contracts; **REST Gateway Responses** customize gateway-level errors; **AppSync GraphQL** returns `data` and `errors`, where HTTP `200` can still carry field errors.

A trustworthy API **rejects invalid inputs as early as practical, enforces authorization in the backend, returns consistent errors on both success and failure paths, supports diagnostics via request IDs/logs/traces, and protects data and costs**. Combined with AWS Lambda, IAM, VPCs, RDS/DynamoDB/S3, CloudWatch, and AWS Budgets, these practices keep applications **secure, observable, and resilient**.
