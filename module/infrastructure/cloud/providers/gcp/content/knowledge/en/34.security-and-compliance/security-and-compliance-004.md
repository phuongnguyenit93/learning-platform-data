# Event Threat Detection and Anomalous Behavior Detection

An attack on Google Cloud often begins with actions that appear legitimate: an account logs in, a service account calls an API, an IAM permission is granted, or a VM connects to an IP address. When these actions occur in isolation, they can be hard to recognize as dangerous. When placed in the context of the actor, affected resource, timing, and preceding sequence of activities, they can reveal signs of compromise.

Event Threat Detection (ETD) is the log-based threat detection service of Security Command Center (SCC). It analyzes Google Cloud log streams and, when SCC is activated at the organization level, can also analyze Google Workspace logs. ETD combines detection rules, threat intelligence, indicators of compromise, sliding-window profiling, machine learning, and anomaly detection to generate findings in near real time.

This lesson focuses on how ETD works, what kinds of behavior can be detected, how to prepare logs, read and investigate findings, and how to integrate alerts into incident response workflows.

## Learning Objectives

After this lesson, you will be able to:

- Describe the role of Event Threat Detection within Security Command Center.
- Explain how logs, indicators of compromise, and behavioral analysis combine to detect threats.
- Distinguish Event Threat Detection from Anomaly Detection and other runtime detection services.
- Identify the required tier, activation scope, IAM permissions, and log sources.
- Read findings, assess severity, and investigate related activity.
- Set up workflows to route findings to Pub/Sub, Cloud Logging, or incident handling systems.
- Design custom detection rules using custom modules when supported templates exist.

## 1. What Is Event Threat Detection?

Event Threat Detection is a built-in service in Security Command Center, available in the Premium tier. It continuously monitors Cloud Logging streams for the organization or project within its activation scope and looks for events indicating threats. When SCC is activated at the organization level, ETD can also monitor Google Workspace logs, including login activity and Admin Console actions.

ETD is an event- and log-based detection mechanism. It does not require installing agents on every VM to analyze individual running processes. Instead, it uses log data generated by services, applies detection logic, and writes results as findings in Security Command Center.

Key characteristics:

- **Near real time:** ETD ingests logs as they arrive and processes them according to enabled detectors. Detection latency is typically under 15 minutes from log write time until the finding appears in SCC.
- **Multi-source analysis:** can use Cloud Audit Logs, network logs, VM authentication logs, database service logs, and Google Workspace logs depending on the detector.
- **Multi-technique approach:** rules, indicators of compromise (IoCs), threat intelligence, sliding-window profiling, machine learning, and anomaly detection.
- **Centralized results:** findings are surfaced in SCC, where security teams can filter, investigate, label, and forward them to response workflows.
- **Extensible:** custom modules allow organizations to define certain detection parameters, severity levels, and custom remediation guidance.

ETD generates alerts for humans or automated response systems. Creating a finding does not automatically mean an account was locked, an IP was blocked, or a VM was isolated. Containment actions must be executed according to runbooks or response systems configured by the organization.

### Product Scope and Tiers

According to current Security Command Center documentation:

| Tier | Event Threat Detection |
|---|---|
| Standard | Does not include ETD |
| Premium | Includes ETD |
| Enterprise (Deprecated) | Includes ETD; this tier is scheduled for deprecation |

Security Command Center Premium can be activated at the project or organization level. Project scope is suitable for piloting a subset of detection capabilities. However, some logs and detectors only operate when activated at the organization level; Google Workspace logs and certain organization-level detectors are examples. Therefore, if enterprise-wide monitoring is required, design for organization-level activation and check each log type.

Google Cloud documentation announces that Enterprise will be discontinued on May 21, 2027; organizations using Enterprise will be automatically transitioned to Premium on or after that date. For long-term planning, use Premium as the baseline for new ETD architectures and verify current service terms.

## 2. How ETD Detects Anomalous Behavior

ETD receives logs from services and analyzes events based on log content, resource context, and threat signals. Techniques described by Google include:

- **Rule-based detection:** checks whether a sequence of events or attributes matches a known dangerous pattern.
- **Indicator of Compromise (IoC):** compares domains, IPs, or technical indicators in logs against threat intelligence data.
- **Sliding-window profiling:** examines activity within a time window to identify anomalous sequences or frequencies.
- **Machine learning and anomaly detection:** identifies activity differing from typical patterns or exhibiting suspicious characteristics according to detector logic.

Not every detector uses all of these techniques. The exact detection logic depends on the detector type, log source, and rules maintained by Google.

For example, a single login from an unfamiliar IP is not necessarily an attack. However, if that same identity logs in anomalously, creates a key for a long-dormant service account, and uses that key to access sensitive data, the event sequence becomes far more notable. ETD can detect behaviors or event combinations supported by detectors and write findings for security teams to investigate.

### High-Level Processing Flow

~~~mermaid
flowchart TD
    A[Users, service accounts, and workloads] --> B[Cloud Audit Logs]
    A --> C[Cloud DNS, NAT, VPC Flow, and auth logs]
    A --> D[Google Workspace logs]
    B --> E[Cloud Logging streams]
    C --> E
    D --> F[Workspace logging stream]
    E --> G[Event Threat Detection]
    F --> G
    G --> H[Rules, IoCs, profiling, ML, and anomaly detection]
    H --> I{Threat indicators present?}
    I -->|No| J[Continue monitoring]
    I -->|Yes| K[Finding in Security Command Center]
    K --> L[Triage and investigate]
    L --> M[Remediate or escalate]
    K --> N[Pub/Sub, Cloud Logging, or SOC tools]
~~~

This process centralizes security events across multiple projects. Operations teams do not have to write separate custom queries for every behavior type before receiving baseline alerts.

### Examples of Detector Categories

| Behavior Category | Example Detector or Indicator | What to Verify |
|---|---|---|
| Initial access | Use of a leaked service account key; activity from an anomalous account | Who owns the identity, which key was used, and access scope |
| Privilege escalation | Granting sensitive permissions to external members; granting service account impersonation permissions | Who granted the permission, which role was granted, and level (organization/folder/project) |
| Persistence | Disabling two-factor authentication; creating keys for an inactive service account | Whether an approved change exists |
| Malware and command-and-control | Connecting to known malicious domains/IPs, DNS tunneling, cryptomining | Associated VM, workload, processes, and network connections |
| Authentication attacks | SSH brute force leading to successful login; database login from an anonymous proxy | Source IP, account, timestamp, and consecutive login attempts |
| Data access | Anomalous data access or export in supported services | Dataset/bucket/database, identity, and data volume |
| Impact on recoverability | Deleting backups, backup plans, or modifying protection policies | Actor, affected resources, and recovery capability |

Detector names, availability states, and default severities can change over time. Some detectors are marked Preview or temporarily unavailable. When designing controls, inspect the current list of Event Threat Detection rules rather than hardcoding the entire detector list into runbooks.

## 3. Distinguishing Event Threat Detection from Anomaly Detection

The names are similar, but these two capabilities have different signal sources and scopes.

**Event Threat Detection** uses logs generated inside the Google Cloud environment and, at the organization level, Google Workspace logs. It looks for attack behaviors or suspicious events such as anomalous permission grants, leaked key usage, malicious domain access, or risky authentication behavior. ETD belongs to SCC Premium.

**Anomaly Detection** is a separate capability in Security Command Center. It uses behavioral signals from outside the system to detect specific anomalies related to service accounts, such as service account credentials discovered leaked on the Internet. An example is GitHub reporting that credentials committed appear to be a GCP service account private key. The finding may have category `account_has_leaked_credentials` and `Critical` severity. Anomaly Detection spans a broader tier scope than ETD according to the current tier table.

| Criterion | Event Threat Detection | Anomaly Detection |
|---|---|---|
| Primary signal source | Internal logs from Cloud Logging and Google Workspace | External behavioral signals, such as leaked credential reports |
| Goal | Detect many types of threat activity in logs | Detect specific anomalies related to accounts and credentials |
| Examples | Anomalous IAM grant, malicious domain, SSH brute force, data access | Service account key discovered publicly |
| Tier scope | Premium and Enterprise (Deprecated) | Standard-legacy, Standard, Premium, and Enterprise (Deprecated), per current tier table |
| Output | Finding in Security Command Center | Finding in Security Command Center |

ETD also uses anomaly detection as a technique inside some detectors. That does not make ETD and the Anomaly Detection service the same service.

In addition, Security Command Center has other services with distinct goals:

- **Sensitive Actions Service** detects sensitive administrative operations that could harm the organization.
- **Container Threat Detection** analyzes runtime activity at the container/node level within supported scope.
- **Virtual Machine Threat Detection** detects malicious applications on virtual machines.
- **Cloud Run Threat Detection** detects selected runtime attacks on Cloud Run.

A complete security architecture may combine several of these services. ETD is the log-based detection layer; runtime services add signals that administrative event logs cannot fully observe.

## 4. Log Sources and Prerequisites for Detectors to Operate

Detection quality depends directly on log sources. Enabling ETD does not mean every detector will automatically have complete input data.

### Cloud Audit Logs

Cloud Audit Logs record activity on resources and APIs:

- **Admin Activity audit logs:** record operations that modify configuration or metadata. This log type is always recorded and cannot be disabled.
- **Data Access audit logs:** record data read or data access operations. Many services do not enable this log type by default; organizations must explicitly configure it if they want to detect behaviors requiring that data.
- **System Event audit logs:** record system actions performed by Google Cloud on behalf of users.

For example, detectors identifying IAM grants may use Admin Activity logs. Detectors related to data reads, database access, or credential usage may require Data Access logs for the corresponding service.

Do not indiscriminately enable Data Access logs for every service. Identify which services are in use, which threats need detection, and which logs detectors actually consume. If a log is not in the list of logs supported by ETD, enabling it will not cause detectors to analyze it automatically.

### Network Logs

ETD can use the following sources for certain network detectors:

- Cloud DNS logging.
- Cloud NAT logging.
- Firewall Rules logging.
- VPC Flow Logs.

For malware detection based on network connections, Cloud DNS logging often already provides valuable information about queried domains. If additional connection flow data is needed, VPC Flow Logs or Cloud NAT/Firewall Rules logging can be enabled where appropriate.

You do not need to simultaneously enable Cloud NAT logging, Firewall Rules logging, and VPC Flow Logs just to have more log sources for the same detector group. Choose based on investigation needs and cost.

An important operational detail: ETD can analyze an internal VPC Flow Logs stream even when the organization has not enabled VPC Flow Logs. However, if you want to open links from a finding into Logs Explorer and Flow Analyzer for deep investigation, VPC Flow Logs must be enabled. Enabling it after a finding has already been created will not retroactively add those investigation links to older findings.

VPC Flow Logs can incur cost. Google recommends considering increasing the aggregation interval to 15 minutes and reducing the sample rate to around 5%–10% to control cost; lower sampling rates may reduce visibility into certain connections.

### Google Workspace Logs

When SCC Premium is activated at the organization level, ETD can use Google Workspace logs to detect activities such as suspicious logins, two-factor authentication changes, or administrative actions. Some Workspace detectors are unavailable when SCC is only activated at the project level.

### Selecting Logs by Detector

| Log Source | Threat Example | What to Verify |
|---|---|---|
| Admin Activity audit logs | IAM changes, disabling APIs, security config changes | Always recorded; verify detector is enabled |
| Data Access audit logs | Data access or anomalous service behavior | Enable the right services and log types needed |
| Cloud DNS logs | Connecting to malicious or cryptomining domains | Enable DNS query logging for relevant VPCs |
| VPC Flow Logs / NAT / Firewall logs | Connections to suspicious IPs | Choose appropriate source, consider sampling and cost |
| VM auth logs | SSH brute force | Install Ops Agent or appropriate Logging agent to ship auth logs |
| Google Workspace logs | Suspicious Workspace logins and admin actions | Activate SCC at the organization level and grant appropriate permissions |

Some log sources and detectors only operate at the organization level. If SCC is activated only at the project level, ETD will not scan organization-only log sources and will not generate findings from them. Check the scope column in the log types and activation requirements documentation.

### Cost and Storage Capacity

According to Google Cloud documentation, ETD log scanning itself incurs no additional scanning fee. However, Cloud Logging may charge ingestion and storage fees depending on the volume of logs the organization generates. VPC Flow Logs, Cloud DNS, Data Access logs, and high-volume log sources should be evaluated before enabling organization-wide.

SCC Premium also has its own pricing structure. During design, account for total costs across the SCC tier, Cloud Logging, log storage, Pub/Sub, and alert processing systems. Set log retention periods aligned with investigation, audit, and data policies.

## 5. Enabling and Configuring Event Threat Detection

The configuration process should begin with the protection scope and required log sources.

### Step 1: Determine Security Command Center Scope

Choose project-level SCC Premium activation if you only need to test or protect a single project. Choose organization-level activation if you need visibility across multiple projects, Workspace logs, and organization-scoped detectors.

Before activating, prepare:

- The organization or project to protect.
- IAM permissions to activate and manage the service.
- Appropriate tier and billing method.
- Data residency requirements, if used by the organization.
- List of logs and services to protect.

### Step 2: Check Service Status

In the Google Cloud Console:

1. Open Security Command Center.
2. Select the target organization or project.
3. Open Settings and go to Services.
4. Locate Event Threat Detection.
5. Verify the service is set to Enable or Inherit according to organizational policy.
6. Open the Modules section to inspect configurable detectors and their states.

ETD is typically enabled by default when the appropriate tier is activated, but actual state may have been changed by an administrator or inherited configuration. Verify before relying on findings to conclude a system is monitored.

### Step 3: Grant IAM Permissions

Permissions are separated by responsibility:

| Task | Reference Role or Permission |
|---|---|
| Enable or modify SCC services | Security Center Admin (roles/securitycenter.admin), Security Center Settings Admin (roles/securitycenter.settingsAdmin), or Security Center Settings Editor (roles/securitycenter.settingsEditor) |
| View findings | Security Center Findings Viewer (roles/securitycenter.findingsViewer) |
| Update findings | Security Center Findings Editor (roles/securitycenter.findingsEditor) |
| Manage custom modules | Event Threat Detection Custom Modules Editor (roles/securitycentermanagement.etdCustomModulesEditor) or equivalent admin role |

Grant roles at the narrowest scope that satisfies the job. Investigators typically only need permissions to view findings and logs; they do not need admin permissions over the entire security service. The SCC service agent is created and granted required permissions upon tier activation. If the organization uses VPC Service Controls, you may need ingress/egress rules so the service agent can access services inside the perimeter per SCC guidance.

### Step 4: Enable Required Logs

Based on active detectors and services:

- Enable Data Access audit logs for services where the organization needs to monitor data reads.
- Enable Cloud DNS logging if domain-based malware detection is desired.
- Enable a supplementary network log source such as VPC Flow Logs, Cloud NAT, or Firewall Rules if corresponding investigation data is needed.
- Configure auth logs on VMs if SSH brute-force detection is needed.
- Confirm Google Workspace logs can be consumed by ETD when activation scope is organization-level.

After changing log configurations, wait for new data to arrive and verify by inspecting actual logs. ETD cannot analyze events that were dropped before being recorded.

### Step 5: Verify Detectors and Findings

Open Security Command Center > Findings and select the right organization or project. Under Quick filters, filter by Source display name:

- Event Threat Detection: findings from built-in detectors.
- Event Threat Detection Custom Modules: findings from custom modules.

When opening a finding, check event timestamp, data source, severity, detected action, and the principal performing the action. If log export is configured, open Logs Explorer to inspect related records.

## 6. Reading and Investigating a Finding

A finding is a record describing a security issue detected by the service. A finding is not raw log data; it is a structured assessment bound to a resource or scope within the system.

A finding typically includes these attributes:

| Attribute | Meaning |
|---|---|
| category | Name of the detection group or type, e.g., Malware: Bad Domain |
| severity | Severity level: LOW, MEDIUM, HIGH, or CRITICAL |
| state | Handling state, typically ACTIVE or INACTIVE |
| eventTime | Timestamp of the event or finding update |
| createTime | Timestamp when the finding was created |
| resourceName | Full name of the associated resource |
| source | Detection source, e.g., Event Threat Detection |
| sourceProperties | Detector-specific properties, which may contain IP, domain, method, or contextual details |
| principal email | User or service account identity performing the action, if present in the finding |

`sourceProperties` fields depend on each detector and are not standardized uniformly across all finding sources. For automated integrations, rely on standard finding fields and read each detector's schema before depending on a specific property.

### Investigation Workflow

**1. Confirm Scope and Timeline**

Record the category, severity, eventTime, resourceName, principal email, source, and relevant attributes. Identify the affected project, folder, or organization.

**2. Open Original Logs**

Locate the corresponding logs in Cloud Logging. Inspect method/API, outcome, source IP, user agent, authenticated identity, and target resource. An IAM finding requires checking who modified the policy, which role was granted, and at which level the policy sits.

**3. Compare Against Legitimate Activity**

Cross-check against change requests, release schedules, administrative tasks, automation, and on-call schedules. Creating a key or changing IAM may be legitimate if performed by an approved pipeline. Still, verify the identity and scope of change rather than relying solely on the existence of a ticket.

**4. Search for Related Activity**

Search for other findings sharing the same principal, IP, service account, project, or resource. For a single principal, filter related findings and logs to build a timeline. If multiple consecutive anomalous actions appear, escalate investigation priority.

**5. Assess and Classify**

Classify the finding as a confirmed incident, legitimate activity, alert requiring continued monitoring, or false positive. Document evidence, verifier, classification rationale, and next steps.

**6. Respond and Recover**

Depending on the incident, you may revoke IAM permissions, disable or rotate credentials, block domains/IPs, isolate VMs, revoke sessions, or restore configurations. Before taking actions impacting production, preserve necessary evidence, assess impact, and follow the organization's incident approval workflow.

**7. Update Finding and Runbook**

Set state to INACTIVE once the issue is resolved. You may mute a finding after assessment if you want to remove it from the active triage queue. Muting does not fix resources or prevent attacks; it only changes how the finding is displayed and managed. Document the mute reason so others understand the decision.

### Example: Detecting an Anomalous IAM Permission Grant

An external member outside the organization is granted a sensitive role in a project. The detector may generate a finding under Privilege Escalation or IAM anomalous grant.

The investigator should:

1. Check which principal granted the permission and which principal received it.
2. Identify the granted role, such as Owner, Editor, or a role allowing service account impersonation.
3. Check whether the policy was changed at the project, folder, or organization level.
4. Cross-check against a ticket or approved change.
5. If unauthorized, revoke the binding, review activity of the receiving principal, and inspect related service accounts/keys.
6. Search for subsequent API calls from the same identity and document investigation results.

A finding with HIGH severity does not by itself prove an attacker has gained control. Severity helps prioritize triage; incident conclusions must rest on logs, resources, identities, and corroborating evidence.

## 7. Finding Logs in Cloud Logging and Forwarding Alerts

Security Command Center is where findings are viewed and managed. When integration with monitoring systems or response workflows is needed, continuous export can be used.

### Viewing Findings Exported to Cloud Logging

If SCC Premium is activated at the organization level and Continuous Exports are configured, ETD findings can be written to Cloud Logging. These logs use the resource type `threat_detector`.

Example query in Logs Explorer:

~~~text
resource.type="threat_detector"
~~~

You can filter further by detector or timestamp to narrow results. Exporting findings to Cloud Logging can incur ingestion and storage costs depending on finding volume.

### Sending Findings to Pub/Sub

Continuous Exports to Pub/Sub forward new findings to a topic for downstream processing. General workflow:

1. Create a Pub/Sub topic and subscription.
2. Open Security Command Center > Findings.
3. Select the organization, folder, or project.
4. Filter findings by category, severity, state, or detection source.
5. Choose Export > Continuous > Pub/Sub.
6. Select the target project and topic, name the export, and save.
7. Create a subscription and verify messages are received.

You can set a filter to send only ACTIVE findings or only detector groups requiring rapid response. SCC creates a notification service account and grants the required role to publish to the topic. If data residency is enabled, the continuous export must be created in the same SCC location as the findings being exported; also verify Pub/Sub message retention policies.

A reference response architecture:

~~~mermaid
flowchart LR
    A[Event Threat Detection] --> B[Security Command Center finding]
    B --> C[Continuous export]
    C --> D[Pub/Sub topic]
    D --> E[Cloud Run service]
    E --> F[Enrichment: IAM, Asset, log context]
    F --> G{Severity and conditions}
    G -->|Action needed| H[Ticket or SOC queue]
    G -->|Eligible for automation| I[Controlled response runbook]
    G -->|Unclear| J[Security analyst review]
~~~

Do not automatically delete accounts, revoke all permissions, or shut down VMs based solely on a single finding. Automation should start by enriching context, creating tickets, notifying on-call staff, and suggesting actions. Automate containment only after defining strict conditions, scope, and rollback procedures.

## 8. Custom Modules for Organization-Specific Requirements

Built-in detectors cover many common attack patterns. However, an organization may have specific rules, such as allowing workloads to connect only to an approved IP list or restricting resource creation to specific regions.

Event Threat Detection custom modules allow configuring additional detectors based on supported templates. A module can define:

- Parameters used to evaluate logs.
- Severity level for findings.
- Description of the detected event.
- Remediation recommendations to include in finding next steps.

For example, the Configurable Bad IP module can detect connections to IPs on an organization-maintained list. Illustrative JSON template:

~~~json
{
  "metadata": {
    "severity": "HIGH",
    "description": "Workload connected to a restricted IP address",
    "recommendation": "Verify the workload owner and investigate the network connection"
  },
  "ips": [
    "203.0.113.10",
    "198.51.100.20"
  ]
}
~~~

The two addresses in the example belong to reserved documentation ranges and are illustrative only. In real configurations, replace them with IPs verified and managed by the security team.

Custom modules run alongside built-in detectors. Enabled modules process new logs in real time. Modules can be created at the organization, folder, or project level; modules at a parent level can be inherited by child nodes as configured. Module management permissions should be restricted to the responsible security team.

Not every type of logic has a custom module template. If an unsupported detection pattern is needed, export logs to BigQuery and build scheduled SQL queries or custom analytics pipelines. Avoid creating redundant rules; each module should have a clear owner, objective, log source, test method, and remediation guide.

## 9. Hands-On: Testing ETD with the Malware: Bad Domain Detector

This exercise uses Google's official test domain to verify the DNS log and finding pipeline. Perform this in a dedicated test project under your control that contains no production data.

### Prerequisites

- SCC Premium activated for the test project or organization.
- Event Threat Detection set to Enable.
- One VPC and one VM for the lab.
- Cloud DNS query logging enabled for the VPC.
- Operator has permissions to create VMs and configure DNS server policies.

### Step 1: Enable DNS Query Logging

In the Google Cloud Console, open Cloud DNS > DNS server policies. Create or edit a policy applying to the VM's VPC, enable logging, and save the configuration. Confirm the VM's project falls within ETD scope.

### Step 2: Create a Test VM

Create a small VM inside the VPC configured for DNS logging. Do not use a production VM or a VM containing sensitive data. Confirm the VM can resolve DNS and query logs are recorded.

### Step 3: Query the Test Domain

Open a terminal on the VM and run:

~~~bash
curl etd-malware-trigger.goog
~~~

The domain above is the test domain designated in Google Cloud documentation for the Malware: Bad Domain detector. It is not meant for normal website testing.

### Step 4: Inspect the Finding

Open Security Command Center > Findings and filter Source display name to Event Threat Detection. Locate the `Malware: Bad Domain` finding and open its details.

Verify:

- Category or corresponding detector.
- Event time and associated project/resource.
- Domain in `sourceProperties`.
- Severity and log source.
- Original DNS log in Cloud Logging.

Detection latency is typically under 15 minutes from log creation. If no finding appears, check in order: whether ETD is set to Enable, whether the project is within activation scope, whether DNS logging applies to the VPC, whether logs were recorded, and whether the detector requires another log source.

### Step 5: Clean Up

After verification:

- Delete the test VM.
- Remove or adjust the DNS server policy if it was created only for the lab.
- Disable test logging if no longer needed.
- Save a screenshot of the finding and record detection latency.
- Confirm no test resources or configurations remain.

Do not run this test procedure in production. If you want to test the IAM Anomalous Grant or SSH Brute Force detectors, follow the official testing instructions in an isolated environment and delete test permissions/resources immediately after verification.

## 10. Limitations and Common Misconfigurations

| Scenario | Possible Cause | How to Handle |
|---|---|---|
| No findings appear | ETD disabled, wrong tier, or project outside scope | Check tier, scope, and Services settings |
| Expected behavior not detected | Log required by detector is not enabled | Cross-check rule against log types and activation requirements |
| No findings from Google Workspace | SCC only activated at project level | Evaluate organization-level activation |
| No Data Access logs visible | Data Access audit logs not enabled for service | Configure audit logs for required services and scopes |
| No Flow Analyzer link from finding | VPC Flow Logs was not enabled when finding was created | Enable VPC Flow Logs to support investigating subsequent findings |
| Delayed finding appearance | Ingestion or detector latency; logs not yet in Cloud Logging | Check timestamps, log ingestion, and typical sub-15-minute latency |
| Finding priority misassessed | Default severity does not reflect actual impact | Review resource, data, and context; use enrichment if appropriate |
| Unexpected spike in log costs | Too many Data Access or network logs enabled | Reduce scope, adjust sampling, retention, and monitor ingestion |
| Pub/Sub not receiving findings | Wrong topic, publish permission, filter, or location | Check notification service account, IAM, export filter, and data residency |
| Custom module produces no findings | Invalid template, missing logs, or module not Enabled | Validate template, check input logs, and verify module state |

ETD does not scan every log in a project. A log being present in Cloud Logging does not mean it is in the list of data sources consumed by detectors. This is a key reason an organization can enable extensive logging yet still see no findings for a particular behavior.

## 11. Operational Best Practices

- **Start from risk:** identify accounts, workloads, data, and behaviors requiring detection before enabling more logs.
- **Protect identities:** prioritize monitoring IAM, service accounts, keys, impersonation permissions, and authentication changes.
- **Maintain right-sized logging:** enable logs aligned with detectors and investigation needs, and periodically review costs.
- **Centralize findings:** use SCC as the aggregation hub, then export to Pub/Sub or Cloud Logging as needed.
- **Assign owners and SLAs:** every HIGH or CRITICAL finding needs a responsible team, response deadline, and escalation path.
- **Reduce repeat noise:** use documented mutes, tune custom modules, and eliminate duplicate rules.
- **Test with control:** use test detectors and isolated resources, then clean up completely.
- **Preserve evidence:** protect logs, timestamps, identities, IPs, and source properties required for investigations.
- **Review periodically:** detectors and log sources evolve over time; update runbooks against current Google Cloud documentation.

## Conclusion

Event Threat Detection helps organizations detect suspicious activity from Google Cloud and Google Workspace logs within supported scope. The service combines rules, threat intelligence, IoCs, temporal profiling, machine learning, and anomaly detection to generate near-real-time findings in Security Command Center.

ETD's value depends on three factors: choosing the right protection scope, supplying the right log sources, and maintaining clear investigation and response processes. A finding is the starting point for incident verification; security teams still must correlate identities, resources, original logs, and approved changes before concluding or taking containment action.
