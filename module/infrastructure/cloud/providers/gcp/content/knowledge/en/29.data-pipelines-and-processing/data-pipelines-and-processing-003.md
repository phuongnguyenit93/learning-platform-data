# Windows, Watermarks, Triggers, and Late Data in Dataflow

A retail system receives `order.paid` events from **Cloud Run**, routes them through **Pub/Sub**, and uses **Dataflow** to aggregate revenue by product every 5 minutes for display in **BigQuery**. A mobile device loses connectivity at 10:02 and only sends the event generated at 10:02 when it reconnects at 10:14. Grouped by arrival time, the order falls into the 10:10–10:15 period; grouped by occurrence time, it belongs to 10:00–10:05. Once the 10:00–10:05 report has already been published, what should happen to the late-arriving event?

**Apache Beam** is the pipeline programming model; **Dataflow** is the Google Cloud service that executes Beam pipelines. Four concepts work together to solve unbounded streaming problems:

- **Window**: divides data into time intervals or activity sessions.
- **Watermark**: estimates processing progress in *event time*, indicating that the system believes most older events have arrived.
- **Trigger**: decides when to emit the results of a window.
- **Late data**: events arriving after the watermark has passed the window closing boundary; handling depends on `allowed_lateness` and triggers.

This lesson belongs to the **Data Pipelines and Processing** chapter of the **CLOUD_PROVIDERS_GCP** module, connecting Pub/Sub, Cloud Run, GKE, BigQuery, IAM, release automation, reliability observability, and cost. Examples use Python Apache Beam and synthetic data; the goal is understanding the exact semantics rather than merely running a Dataflow command.

## 1. Learning Objectives

After this lesson, you will be able to:

1. Distinguish **event time**, **processing time**, **Pub/Sub publish time**, and **window timestamp**.
2. Choose **fixed**, **sliding**, or **session windows** for each type of report.
3. Explain that a watermark is an **estimate**, not a promise that no older events remain.
4. Design **early/on-time/late** triggers and choose between **accumulating** and **discarding panes**.
5. Configure `allowed_lateness` and determine when data is no longer retained in window state.
6. Test with `TestStream`, and design Pub/Sub ingestion, Dataflow monitoring, and duplicate-safe BigQuery sinks.
7. Trade off **data freshness, completeness, state, cost**, and business SLO requirements.

## 2. Four Time Axes and Overall Architecture

### 2.1. Event Time Is Not Processing Time

| Time | Definition | Payment event example |
| --- | --- | --- |
| **Event time** | When the event **actually occurred** according to the data source. | `10:02:10`, generated by the payment system. |
| **Pub/Sub publish time** | When Pub/Sub receives/publishes the message. | `10:14:00` after the device reconnects. |
| **Processing time** | When the Dataflow worker processes the message at a step. | `10:14:03`. |
| **Window interval** | The event-time interval to which Beam assigns the element. | `[10:00, 10:05)` when using 5-minute fixed windows. |

Do not blindly treat the time an HTTP server receives a request as event time. Producers may have clock drift or replay very old events: identify a **trusted time source**, normalize to UTC, check clock skew, and store both `event_time` and `ingested_at` when auditing is needed.

~~~mermaid
flowchart LR
    SRC["Cloud Run / IoT: event + event_time"] --> PS["Pub/Sub"]
    PS --> BEAM["Dataflow: assign timestamp"]
    BEAM --> WIN["WindowInto: 5 minutes"]
    WIN --> AGG["Group/Combine by SKU"]
    AGG --> TR["Trigger: early, on-time, late"]
    TR --> SINK["BigQuery: pane/revision"]
    MON["Cloud Monitoring"] -. "Watermark, lag, errors, cost" .-> BEAM
~~~

An event can arrive late due to an offline device, network retries, a Pub/Sub backlog, or a slow stage; not every event with an old timestamp is a duplicate. **Deduplication** and **late-data handling** are two distinct problems.

### 2.2. Unbounded Collections Need Windows for Aggregation

Pub/Sub is an **unbounded** source, so you cannot wait to "receive every order" before running `GroupByKey`/`CombinePerKey`. Beam splits data into finite windows or uses triggers suitable for `GlobalWindow`. Conversely, finite files/batches can complete the entire job and aggregate without real-time windowing.

**Distinguishing examples:**

- Counting total orders for **a completed day** from Cloud Storage is batch.
- Counting orders **every 5 minutes, continuously updated** from Pub/Sub is streaming.
- The same SQL `GROUP BY sku` does not specify how windows, watermarks, and late events are handled; those rules live in the pipeline's semantics.

## 3. Choosing Windows: Fixed, Sliding, and Session

### 3.1. Fixed (Tumbling) Windows

**5-minute fixed windows** divide the event-time axis into non-overlapping intervals:

~~~text
10:00           10:05           10:10           10:15
|------- W1 -------|------- W2 -------|------- W3 -------|
      10:02 → W1        10:06 → W2        10:14 → W3
~~~

Windows generally use **half-open** intervals `[start, end)`: an event at **10:05:00** belongs to W2, not W1. In Beam Python:

~~~python
import apache_beam as beam
from apache_beam.transforms.window import FixedWindows

# Apply after a PCollection has proper timestamps.
windowed = events | "FiveMinuteWindows" >> beam.WindowInto(
    FixedWindows(5 * 60))
~~~

Suited for reports across discrete periods: orders per 5 minutes, daily revenue, hourly SLAs. If you need boundaries aligned to a **local timezone** or business calendar, verify window types and timezones; fixed windows in seconds do not automatically account for daylight saving time or "Vietnam calendar days".

### 3.2. Sliding Windows

**10-minute sliding windows with a 5-minute period** serve reports like "last 10 minutes, updated every 5 minutes". Windows **overlap**, so **one event can belong to multiple windows**:

~~~text
Window A: [10:00, 10:10)
Window B:       [10:05, 10:15)
Event 10:07 → belongs to both A and B.
~~~

~~~python
from apache_beam.transforms.window import SlidingWindows

windowed = events | "RollingTenMinutes" >> beam.WindowInto(
    SlidingWindows(size=10 * 60, period=5 * 60))
~~~

**Do not sum totals of A and B directly** to compute the 10:00–10:15 total: event 10:07 appears twice. Combinations of long windows and short periods can sharply increase **state, pane counts, and cost**; benchmark beforehand.

### 3.3. Session Windows

**Session windows** group events sharing the same **key** when gaps between events do not exceed an inactivity threshold (*gap*). Suitable for clickstreams by `session_id`/`customer_id`, device activity, or shopping-cart interactions.

~~~python
from apache_beam.transforms.window import Sessions

# Group by key in a step after WindowInto.
windowed = events_by_customer | "SessionsFiveMinutes" >> beam.WindowInto(
    Sessions(gap_size=5 * 60))
~~~

If customer A interacts at 10:00, 10:03, and 10:07, the events can merge into one session; a late-arriving event can **merge two sessions previously considered separate**. Session windows are **merging windows**; designing outputs/upserts and event-time correctness is harder than with fixed windows, especially when early results have already been emitted. Do not use a session gap as a security login timeout unless explicitly defined by business requirements.

| Type | How many windows does an event belong to? | When to use | Pitfall |
| --- | --- | --- | --- |
| Fixed | One window per windowing specification. | 5-minute periodic reports. | Late arrivals after watermark, backfill data. |
| Sliding | Potentially multiple windows. | Rolling metrics. | Double-counting when summing overlapping windows. |
| Session | Per-key windows; can merge. | User/device behavior. | Window boundaries shift when late events arrive. |

## 4. Watermark: Estimating Event-Time Progress

### 4.1. What Does a Watermark Mean?

A watermark `W = 10:05` is the pipeline/source's estimate that most events with event times **before that mark** have already passed through the relevant processing step. A watermark is **not** a guarantee that *every* older event has appeared. A message with event time 10:02 arriving after the watermark has passed 10:05 is **late** for fixed window `[10:00,10:05)`.

~~~text
Event time ──────────────────────────────────────────>
10:00             10:05             10:10
|---- Window A ----|---- Window B ----|
                   ^
                 watermark

Message (event_time 10:02) arriving past this point ⇒ late for A.
~~~

The watermark of **a step** depends on upstream sources and prior steps; a slow stage, backlog, timers/state, or low-traffic source can hold the watermark back. A pipeline reading from multiple Pub/Sub sources can be held back by a **very quiet or idle source**. Read `data watermark lag`, `system lag`, and traffic together to diagnose the cause.

### 4.2. A Watermark Is Not Allowed Lateness

| Mechanism | Question it answers |
| --- | --- |
| Watermark | "How far does the system **estimate** older data has arrived?" |
| Trigger | "When should a **result pane** be emitted?" |
| Allowed lateness | "After the window end, up to what watermark point should **state be retained and late events accepted**?" |
| Pub/Sub retention | "How long does a message remain in the source before policy expiration?" |

**Allowed lateness is not measured in minutes since a worker received a message**, nor is it Pub/Sub retention duration. Example: window `[10:00,10:05)` with `allowed_lateness=10 minutes` can accept late data until **the watermark passes roughly 10:15**. If wall-clock processing time is 10:20 while the watermark is still stuck at 10:06, the event-time window has not expired under that rule.

### 4.3. How the Pub/Sub Source Determines Event Timestamps

By default, `ReadFromPubSub` typically uses the **Pub/Sub publish time** as the element timestamp. When `timestamp_attribute="event_time"` is set, the connector reads the timestamp attached by the publisher in that attribute instead of publish time. Supported formats include **RFC 3339 UTC** or **milliseconds since Unix epoch**. Example:

~~~json
{
  "data": {"event_id": "evt-123", "sku": "SKU-A", "amount_vnd": 120000},
  "attributes": {"event_time": "2026-11-19T10:02:10Z", "event_id": "evt-123"}
}
~~~

The snippet above is a **conceptual representation** of a Pub/Sub message, not a single raw JSON payload sent verbatim to the Pub/Sub API: `data` and `attributes` are separate fields. For device-generated event times, validate timestamps and clock skew; malformed or excessively old attributes can fail the pipeline or stall the watermark.

When Dataflow uses a timestamp attribute, the connector may create a **tracking subscription** to estimate event-time backlog. Therefore, the Dataflow service account may require permissions to manage that tracking subscription and attach it to the topic, beyond basic consume permissions. See [Read from Pub/Sub to Dataflow](https://cloud.google.com/dataflow/docs/concepts/streaming-with-cloud-pubsub).

## 5. Triggers: Emitting Results Before and After the Watermark

### 5.1. Triggers Produce One or More Panes

By default, Beam waits for the watermark to pass the **end of the window** before emitting aggregated results. However, dashboards wanting estimates before a window closes can enable **early firing**. Accepted late events can trigger **late firing** to update published reports. Each trigger emission produces a **pane**: a version or incremental update of the result for a `(key, window)` pair.

| Firing type | Illustrative condition | Meaning for dashboards |
| --- | --- | --- |
| **EARLY** | 20 seconds of processing time from the first element in the pane. | **Provisional** figures; not all events have arrived yet. |
| **ON_TIME** | Watermark passes the window end. | Result at the point the system **estimates completeness**. |
| **LATE** | Late event arrives within the allowed window. | Revision to previously published numbers. |

**ON_TIME does not mean strictly final** when allowed lateness is configured or upstream replays occur later. Panes carry metadata such as **`PaneInfo.timing`**, `index`, `is_first`, and `is_last`; these are useful for logs and sinks, but **they are not immutable transaction IDs across full pipeline reruns**.

### 5.2. Primary Trigger Types

| Beam Trigger | Based on which clock/event? | When to use |
| --- | --- | --- |
| `AfterWatermark` | Event time/watermark. | On-time result emission. |
| `AfterProcessingTime(delay=...)` | Processing clock, measured from the pane's first element. | Early provisional updates while the event-time window is still open. |
| `AfterCount(n)` | Element count. | Emit a pane after N messages. |
| `AfterAny`, `AfterAll`, `Repeatedly` | Composite conditions. | Balance count and time thresholds, per runner support. |

A common pattern:

~~~python
from apache_beam.transforms.trigger import (
    AfterWatermark, AfterProcessingTime, AfterCount, AccumulationMode)
from apache_beam.transforms.window import FixedWindows
import apache_beam as beam

windowed = events | "WindowsWithEarlyLateUpdates" >> beam.WindowInto(
    FixedWindows(5 * 60),
    trigger=AfterWatermark(
        early=AfterProcessingTime(delay=30),
        late=AfterCount(1)),
    allowed_lateness=10 * 60,
    accumulation_mode=AccumulationMode.ACCUMULATING)
~~~

Interpretation: when data arrives, Beam can emit an **early pane** after 30 seconds of processing time, emit an **on-time pane** when the watermark passes the window end, and re-emit updated results when late elements arrive within the 10-minute allowance. You cannot predict the exact number of early panes by formula alone: parallelism, first-element arrival times, composite triggers, and runner behavior affect actual panes. When you only need post-watermark results, the **default configuration is simpler** and usually incurs lower state/output overhead.

### 5.3. Triggers Differ from Timeouts and Cron Schedules

- `AfterProcessingTime(30)` does not mean "fire at the 30th second of every minute"; it is relative to when an element arrives in the pane.
- `AfterCount(100)` does not guarantee output if a pane only receives 99 elements without another trigger; use a composite trigger to bound wait time.
- Cloud Scheduler creates **cron jobs**; it does not replace Beam triggers for streaming windows.
- Triggers can emit **multiple outputs for the same key/window**, so downstream consumers must distinguish provisional outputs from revisions.

## 6. Accumulating vs. Discarding: Total or Delta?

### 6.1. Single-Window Illustration

Suppose `SKU-A` in window `[10:00,10:05)` receives:

| Pipeline arrival | Event time | Order value (thousand VND) | Status |
| --- | --- | ---: | --- |
| 10:01 | 10:00:30 | 100 | Arrived early. |
| 10:02 | 10:01:10 | 50 | Arrived early. |
| 10:06 | 10:03:40 | 50 | Arrived before on-time firing under assumed watermark. |
| 10:09 | 10:02:00 | 20 | Arrived after watermark passed 10:05: **late**. |

Assume three firings occur for illustration: **early** after the first two events, **on-time** after the third event, and **late** after the fourth event. Results:

| Pane | `ACCUMULATING` | `DISCARDING` |
| --- | ---: | ---: |
| EARLY | 150 | 150 |
| ON_TIME | **200** (`150 + 50`) | **50** new since prior pane |
| LATE | **220** (`200 + 20`) | **20** new since prior pane |

Units are in thousand VND. With **accumulating**, each firing represents the **cumulative total** for the key/window so far; with **discarding**, subsequent panes include only elements **not yet emitted in previous panes**. In this example, summing `150 + 200 + 220 = 570` is **wrong** if the goal is final total revenue: the true sum across the four events is **220**.

### 6.2. Choosing by Sink Contract

| Mode | When suitable | Downstream responsibility |
| --- | --- | --- |
| `ACCUMULATING` | Dashboard wants the **latest total** per `(window, key)`. | Upsert/replace prior version; do not sum all panes. |
| `DISCARDING` | Sink wants a **delta** per firing. | Sum idempotently, protecting against duplicate panes/deliveries. |
| `ACCUMULATING_AND_RETRACTING` | Some runners/SDKs support retractions to cancel prior versions. | Verify SDK/sink support; do not assume Dataflow Python supports it by default. |

Do not treat Dataflow processing an input message once as a guarantee that BigQuery receives **only one aggregate row**: triggers themselves can emit multiple panes. **Exactly-once processing, output semantics, and exactly-once side effects are three separate layers**.

## 7. Allowed Lateness, Expired Data, and State Retention

### 7.1. Acceptance Limit by Watermark

For window `[10:00,10:05)` with `allowed_lateness=10 minutes`, the runner can retain key/window state to process late data until **the watermark advances past `10:15`**. Beyond that limit, overly late data **cannot be expected to update old window results** in that transform.

~~~text
Window A: [10:00, 10:05)
                          watermark = 10:05 → on-time can fire
             [10:05, 10:15] → event-time window for late data
                          watermark > 10:15 → window state eligible for GC
~~~

In practice, the watermark may advance unevenly; the **wall-clock** duration that state remains alive can exceed 10 minutes. **Allowed lateness increases state storage costs**, causes sinks to receive more corrections, and delays when a window is considered settled. `allowed_lateness=0` is typically the default: late events are not folded back into that window.

### 7.2. Pub/Sub Retention Is Independent of Window State

A Pub/Sub subscription can retain unacked messages for days, while a Beam window might accept late events for only 10 minutes **by watermark**. A message replayed after several days can still be delivered by Pub/Sub, yet **no longer be eligible to update an expired aggregate window**. Conversely, setting `allowed_lateness` to several days does not preserve Pub/Sub messages past their retention limit.

When late data carries financial or legal significance:

1. **Persist immutable raw events** with business `event_id`, event time, ingest time, and schema version in BigQuery/Cloud Storage per retention policy.
2. Separate real-time dashboards (with a lateness budget) from **reconciliation/backfill** built on the raw source.
3. Use **window key + business ID** for idempotent writes; audit discrepancies against end-of-day batch reports.
4. Build quarantine/DLQ handling for **malformed schemas**, unreasonable clock skew, or events too old per business rules; do not mistake this for an automatic feature of `allowed_lateness`.

### 7.3. Extending Lateness Does Not Fix a Stuck Watermark

A stalled watermark may be caused by a Pub/Sub backlog, an idle source, a hot key, slow transforms/stateful timers, or downstream backpressure. The solution is **inspecting per-step lag, throughput, errors, and capacity**, not merely raising `allowed_lateness`. Holding state longer while the bottleneck remains unresolved usually only increases memory/disk usage and cost.

## 8. Testing Example with Beam `TestStream`

### 8.1. Why `TestStream`?

In a normal `beam.Create(...)` batch test, the watermark jumps to infinity once the source finishes; that **does not controllably simulate** events arriving before or after the watermark. **`TestStream`** lets you set event timestamps, advance processing time, and manually advance the watermark in tests.

The Python snippet below is a **DirectRunner/Beam** demo and creates no Google Cloud resources. Install `apache-beam` in an authorized practice environment, keeping versions consistent with your target runner. Timestamps **5, 20, 35... are seconds since the Unix epoch in the simulated environment**, not real transaction times.

~~~python
import apache_beam as beam
from apache_beam.options.pipeline_options import PipelineOptions
from apache_beam.testing.test_stream import TestStream
from apache_beam.transforms.trigger import (
    AfterWatermark, AfterProcessingTime, AfterCount, AccumulationMode)
from apache_beam.transforms.window import FixedWindows, TimestampedValue


class InspectPane(beam.DoFn):
    def process(
        self, item,
        window=beam.DoFn.WindowParam,
        pane_info=beam.DoFn.PaneInfoParam
    ):
        sku, total = item
        print(
            f"sku={sku}, total={total}, "
            f"window=[{float(window.start)},{float(window.end)}), "
            f"timing={pane_info.timing}, index={pane_info.index}")
        yield item


def main():
    source = (
        TestStream()
        .advance_watermark_to(0)
        .add_elements([
            TimestampedValue(("SKU-A", 100), 5),
            TimestampedValue(("SKU-A", 50), 20),
        ])
        .advance_processing_time(12)  # Give early firing an opportunity to trigger.
        .add_elements([TimestampedValue(("SKU-A", 50), 35)])
        .advance_watermark_to(60)     # Past end of window [0,60).
        .add_elements([TimestampedValue(("SKU-A", 20), 40)])  # Late.
        .advance_watermark_to(181)    # Past end + allowed lateness.
        .add_elements([TimestampedValue(("SKU-A", 900), 45)])  # Too late.
        .advance_watermark_to_infinity()
    )

    options = PipelineOptions(streaming=True)
    with beam.Pipeline(options=options) as p:
        (
            p
            | "SyntheticEvents" >> source
            | "OneMinuteWindow" >> beam.WindowInto(
                FixedWindows(60),
                trigger=AfterWatermark(
                    early=AfterProcessingTime(delay=10),
                    late=AfterCount(1)),
                accumulation_mode=AccumulationMode.ACCUMULATING,
                allowed_lateness=120)
            | "SumPerSku" >> beam.CombinePerKey(sum)
            | "InspectOutputPanes" >> beam.ParDo(InspectPane())
        )


if __name__ == "__main__":
    main()
~~~

**Expected observations:** the illustrative accumulating panes show totals **150 → 200 → 220**; the element with value **900** arrives after the watermark has passed the window's deadline and is excluded from that aggregate. Exact log counts, order, and firing timings **may vary by SDK/DirectRunner version and timer scheduling**, so write assertions in automated tests inspecting `PaneInfo` rather than relying on `print` line order.

### 8.2. Try Modifying a Setting

Modify the demo yourself:

- Change `ACCUMULATING` to `DISCARDING` and explain which panes are deltas.
- Try `allowed_lateness=0`: observe whether the event with value `20` still produces a late pane.
- Change `FixedWindows(60)` to `SlidingWindows(120, 60)` and explain why the same element appears in multiple windows.
- Delay advancing the watermark until after emitting event `35` to verify that **lateness depends on the watermark**, not wall-clock time.
- Add key `SKU-B` and confirm aggregation is per key **and** window, not just per window.

## 9. Applying This in Pub/Sub → Dataflow → BigQuery

### 9.1. Setting Event Time Properly at the Source

Suppose the producer sends each Pub/Sub message with JSON `{"event_id":"evt-123","sku":"SKU-A","amount_vnd":120000}` and **attributes** `event_time=2026-11-19T10:02:10Z`, `event_id=evt-123`. In Python Beam, reading and mapping to key/value pairs can be written as:

~~~python
import json
import apache_beam as beam

SUBSCRIPTION = (
    "projects/REPLACE_PROJECT/subscriptions/REPLACE_SUBSCRIPTION"
)

def parse_order(raw: bytes):
    event = json.loads(raw.decode("utf-8"))
    # Demo: real apps need schema validation, quarantine, and currency rules.
    return event["sku"], int(event["amount_vnd"])

# Snippet placed INSIDE a configured Beam Pipeline.
events = (
    p
    | "ReadOrders" >> beam.io.ReadFromPubSub(
        subscription=SUBSCRIPTION,
        timestamp_attribute="event_time",
        id_label="event_id")
    | "ParseOrders" >> beam.Map(parse_order)
)
~~~

`p` is a **Beam Pipeline** created outside the snippet, not a pre-existing variable if pasted directly into a Python REPL. `ReadFromPubSub` takes `subscription` **or** `topic` (never both). Omitting `timestamp_attribute` causes the source to use Pub/Sub publish time, placing delayed devices into the **wrong business window**.

`id_label="event_id"` lets the connector use a stable identifier when present for source-level deduplication. It **does not replace business idempotency** when the same transaction is published under **two different event IDs**, or when output produces multiple early/late panes. For potentially malformed data, production pipelines should use a `ParDo` splitting **valid** and **invalid** records into two outputs, quarantining safe metadata without logging raw PII/tokens. With Pub/Sub sources, **each Dataflow pipeline should use its own dedicated subscription** to avoid randomly splitting messages across pipelines.

### 9.2. Windowed Aggregation and Output Records

After parsing:

~~~python
from apache_beam.transforms.trigger import (
    AfterWatermark, AfterProcessingTime, AfterCount, AccumulationMode)
from apache_beam.transforms.window import FixedWindows

totals = (
    events
    | "Window5m" >> beam.WindowInto(
        FixedWindows(300),
        trigger=AfterWatermark(
            early=AfterProcessingTime(30),
            late=AfterCount(1)),
        allowed_lateness=600,
        accumulation_mode=AccumulationMode.ACCUMULATING)
    | "SumBySkuAndWindow" >> beam.CombinePerKey(sum)
)
~~~

Every output must carry **window_start, window_end, SKU, total, pane timing, emit time, and run identifier** so downstream consumers know whether a row is a **metric revision** or a **raw event**. In Beam, `DoFn.WindowParam` and `DoFn.PaneInfoParam` expose this metadata. For production, define **deadlines, retry policies, quotas, and schemas** for the sink; the snippet above does not yet write to BigQuery.

### 9.3. A Very Common Trap: One BigQuery Row per Pane

Suppose you use `ACCUMULATING` and append rows:

~~~text
window_start | sku   | pane_timing | total_vnd
10:00        | SKU-A | EARLY       | 150000
10:00        | SKU-A | ON_TIME     | 200000
10:00        | SKU-A | LATE        | 220000
~~~

Running `SELECT SUM(total_vnd)` over all three rows yields **570000** instead of **220000**. The three rows represent **three versions of the same window+SKU**, not three independent transactions.

Three implementation approaches depending on requirements:

| Sink pattern | Usage | Controls needed |
| --- | --- | --- |
| **Append all panes to staging** | Supports auditing; expose latest result via view/aggregation. | Use revision/ordering metadata and idempotency; never sum all panes. |
| **Upsert current results table** | Each `(window_start, sku)` holds only the latest value. | `MERGE`/transactions or upsert-capable sink; handle races, duplicates, and out-of-order revisions. |
| **Raw events + batch reconciliation** | Store event IDs/raw events; recompute end-of-day reports in BigQuery. | Deduplicate business events and verify source of truth; higher latency. |

The **BigQuery Storage Write API** offers different write modes for **exactly-once vs. at-least-once**; even when choosing exactly-once per record, **early/on-time/late panes remain distinct business outputs**. Never confuse single-row transport guarantees with guarantees against triple-counting aggregates. For financial dashboards, prefer a raw event ledger paired with **finalized confirmed figures** or versioned recomputation/upsert workflows.

### 9.4. SQL Reconciliation from a Raw Event Table

Suppose `retail-lab.raw_events.order_payments` stores `event_id`, `event_time TIMESTAMP`, `ingested_at TIMESTAMP`, `sku`, `amount_vnd INT64`, and `source_message_id`. The illustrative query below selects the **first record per business event ID** and then computes 5-minute fixed windows:

~~~sql
WITH deduplicated AS (
  SELECT
    event_id, event_time, sku, amount_vnd
  FROM `retail-lab.raw_events.order_payments`
  WHERE event_time >= TIMESTAMP('2026-11-19 00:00:00+00')
    AND event_time < TIMESTAMP('2026-11-20 00:00:00+00')
  QUALIFY ROW_NUMBER() OVER (
    PARTITION BY event_id
    ORDER BY ingested_at, source_message_id
  ) = 1
)
SELECT
  TIMESTAMP_SECONDS(DIV(UNIX_SECONDS(event_time), 300) * 300)
    AS window_start_utc,
  sku,
  SUM(amount_vnd) AS total_vnd
FROM deduplicated
GROUP BY window_start_utc, sku
ORDER BY window_start_utc, sku;
~~~

This is a **reconciliation query**, not an automatic exactly-once design. You need rules for **two records sharing an `event_id` with different payloads**, handling negative/reversal events, and partition-pruning predicates on production tables. An element whose timestamp falls exactly on a 5-minute boundary belongs to the window **starting at that boundary**. If using local timestamps, standardize UTC conversion and daylight saving rules.

## 10. Monitoring Watermarks, Lag, Throughput, and State

### 10.1. Signals That Are Easily Confused

| Dataflow signal | Meaning | Question to answer |
| --- | --- | --- |
| **Data watermark** per step | Event-time mark estimated as completed/processed. | Which step is holding back the watermark? |
| **Data watermark lag** | Gap between the latest event time and the step's watermark. | Is older data stuck and unreleased? |
| **System lag** | Duration data spends waiting or being processed inside the system. | Is there a throughput/CPU/hot-key bottleneck? |
| **Data freshness** | Difference between event time in the pipeline and current wall-clock time. | Is the dashboard growing stale? |
| **Element counts / throughput** | Elements received/processed/emitted and rate over time. | Is any stage dropping output due to filters or errors? |
| **User counters** | Malformed, duplicate, late, or rejected event counts from app logic. | Is data quality degrading? |
| **Sink metrics** | BigQuery load/write failures, backlog, commit latency. | Are metrics reaching the destination on time? |

The Dataflow Console provides **job metrics**, **per-step metrics**, the execution graph, logs, worker CPU/memory, and lag states. Cloud Monitoring can alert on system lag and related metrics; metrics have sampling delays, so **do not treat a brief single-point spike as an immediate incident**. When using event-time timestamps, also record `ingested_at` to separate **slow producers** from a **slow pipeline**.

### 10.2. Setting Alerts by Business Need

Suppose the dashboard SLO is **95% of orders displayed within 2 minutes**, with zero end-of-day reconciliation discrepancy per business rules (both **hypothetical** targets):

1. Alert on **system lag** if queued data continuously exceeds acceptable bounds.
2. Alert on **watermark lag** if on-time panes are abnormally delayed, even when CPU/throughput look normal.
3. Alert on **no input** if publishers/sources stop sending (avoid mistaking empty output for success).
4. Alert on **late/invalid rates** if delayed or malformed events spike abnormally.
5. Alert on **sink failures** and discrepancies among raw-event counts, processed counts, and BigQuery rows.

Do not automatically increase worker counts when an **idle** source holds back the watermark or a **hot key** blocks processing: inspect step topology, source watermark behavior, key skew, and state/timers first. The watermark can stall even with plenty of spare workers.

## 11. Production Design: Correctness, Security, and Cost

### 11.1. Event IDs, Replay, and Exactly-Once

An event may be redelivered due to publisher retries or Pub/Sub redelivery. In another scenario, **a single real purchase** is re-emitted by the publisher under a new event ID. Therefore:

| Layer | What must be addressed |
| --- | --- |
| **Producer** | Stable business ID, event ID, trusted timestamp source, and schema version. |
| **Pub/Sub/Dataflow source** | Connector ID deduplication and retry handling; never treat publish time as event time if business logic forbids it. |
| **Window/trigger** | Accept late events up to allowed lateness; define panes as totals or deltas. |
| **BigQuery sink** | Choose appropriate Storage Write API mode, handle multiple panes, upserts, and idempotent commits. |
| **Reconciliation** | Retain raw immutable history/backfill and maintain financial reconciliation queries. |

Dataflow offers an **exactly-once streaming processing mode** and an at-least-once mode trading off throughput/cost, but neither prevents a producer from emitting **two business events with different IDs**, nor makes external operations outside Dataflow transactions exactly-once. **Seeking a Pub/Sub subscription while a Dataflow pipeline is actively reading it is not recommended**: backward seeks can break watermark/state assumptions and cause duplicates or drops. For replay, follow a **snapshot/new subscription + drain or cancel and launch a new job** procedure, with controlled sinks and IDs.

### 11.2. Choosing a Lateness Budget from Actual Distributions

Do not set `allowed_lateness=24h` just because it feels "safer". Collect histograms of:

~~~text
arrival_delay = Pub/Sub publish_time - event_time
pipeline_delay = output_emit_time - Pub/Sub publish_time
end_to_end_delay = output_emit_time - event_time
~~~

Then evaluate **p50/p95/p99/p99.9 and outliers** by device, region, and network path. Decide:

- **Real-time dashboard:** return early results quickly, accepting bounded revisions.
- **Operational reports:** on-time plus late panes, retaining state across typical outage durations.
- **Accounting/closing:** raw ledger + cutoff reconciliation; excessively late events go through a dedicated adjustment/backfill workflow.

If 99.9% of events arrive within 8 minutes, a 10-minute lateness allowance may be a reasonable **initial hypothesis**, but you must still account for watermarks, prolonged outages, state size, and business impact. **There is no single default value for every pipeline**.

### 11.3. Hop-by-Hop IAM and Networking

| Component | Identity | Permissions to verify |
| --- | --- | --- |
| Cloud Run publisher | Runtime service account | `roles/pubsub.publisher` on the target topic. |
| Dataflow worker | Dedicated Dataflow worker SA | `roles/dataflow.worker`, `roles/pubsub.subscriber`, IAM to create/read tracking subscriptions when using timestamp attributes, plus required GCS/BigQuery roles. |
| BigQuery sink | Dataflow worker SA or connector identity | BigQuery write permissions on the table/dataset and job creation permissions if required; do not grant project-wide BigQuery Admin by default. |
| CI/deployer | Release identity | Permissions to create/update Dataflow jobs and `iam.serviceAccounts.actAs` on the worker SA. |
| SRE/auditor | Read-only operations identity | Scoped Monitoring/Logging/Dataflow Viewer; separate drain/cancel permissions. |

Paths to **Pub/Sub, BigQuery, Cloud Storage, and Google APIs** require appropriate DNS, egress, and VPC Service Controls. If workers lack public IPs, verify Private Google Access/Private Service Connect and NAT/proxy topology. **`PERMISSION_DENIED` cannot be fixed by raising `max_num_workers`**, and DNS failures are not solved by granting Project Owner.

### 11.4. The Cost of "Continuous Real-Time Updates"

~~~text
Total cost ≈
  Dataflow worker compute + Streaming Engine / state / shuffle
  + Pub/Sub message throughput and retention
  + BigQuery writes, queries, storage / upserts
  + Cloud Storage staging/raw archival
  + network transfer and Cloud Logging/Monitoring
~~~

Firing early every few seconds, heavily overlapping sliding windows, and multi-day allowed lateness can significantly increase **pane counts, state, writes, and BigQuery query costs**. Compare configurations by **p95/p99 latency, correctness, and cost per event or per completed window**; never optimize latency at the expense of blowing the budget or multiplying duplicate aggregates.

## 12. Troubleshooting and Runbook

| Symptom | Possible cause | First action |
| --- | --- | --- |
| Event at 10:02 counted in 10:10–10:15 | Source uses Pub/Sub publish time instead of event time. | Check `timestamp_attribute`, payload/attributes, and timezone. |
| Window never emits on-time pane | Watermark hasn't passed window end, idle source, backlog, or slow stage. | Per-step watermark/data lag, logs, source metrics. |
| Dashboard shows values that keep changing after period end | Early/late triggers or accumulating panes are active. | Check `PaneInfo.timing`, allowed lateness, sink revisions. |
| Revenue is 2–3× too high | Appending multiple **accumulating panes** and running `SUM`. | Use upsert/latest version; never sum cumulative totals. |
| Late event is not counted | Watermark already passed `window_end + allowed_lateness`. | Event timestamp, late policy, raw store/reconciliation. |
| Raised allowed lateness yet events still missing | Messages dropped upstream, retention expired, or parse failed. | Pub/Sub retention/backlog, invalid-payload logs. |
| Watermark stuck while CPU is low | Idle source, state/timers, or a very hot key. | Per-stage watermark, hottest keys, parallelism, source behavior. |
| Session windows merge unexpectedly | Late event bridged previously separated sessions. | Session gap, merging semantics, downstream corrections. |
| BigQuery query shows duplicate window+key rows | Early/on-time/late panes or sink write retries. | `window_start`, `key`, `pane_timing`, run ID, write semantics. |
| Streaming job keeps retrying the same message | Poison event throws in DoFn, causing repeated bundle retries. | Schema validation, quarantine/DLQ, exact error in worker logs. |
| Dataflow cannot read Pub/Sub | SA lacks subscriber role or tracking-subscription permissions. | Effective IAM and Pub/Sub source config. |
| `PERMISSION_DENIED` writing BigQuery | Dataflow SA lacks dataset/table write or job permissions. | IAM/resource policies, location, logs. |
| Replay corrupts watermarks/aggregates | Seeking a subscription while the live job is reading it. | Stop the replay attempt; follow snapshot/new-job runbook. |
| Cost spikes sharply | Early firing frequency, sliding overlap, state retention, sink writes. | Check panes per window, shuffle/state, Billing SKUs. |

**7-step runbook when late data skews reports:**

1. Isolate affected **business event IDs** and event-time ranges; never "fix" by wiping all metrics.
2. Inspect **source timestamp configuration** and sample events for clock skew.
3. Check the **aggregation stage watermark**, `allowed_lateness`, trigger, accumulation mode, and emitted panes.
4. Check **Pub/Sub backlog/retention**, invalid-event counts, sink failures, and BigQuery state.
5. Recompute the report from **deduplicated raw events** across a controlled range.
6. Fix timestamp/trigger/sink semantics in staging, run `TestStream`, and validate against the raw ledger.
7. Deploy with approval, monitor lag, correctness, cost, and keep a rollback plan ready. **Never seek directly on a running streaming job's subscription** outside a supported replay procedure.
