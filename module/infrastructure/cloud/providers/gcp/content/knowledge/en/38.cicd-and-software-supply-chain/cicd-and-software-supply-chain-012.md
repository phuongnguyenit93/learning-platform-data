# Artifact Analysis, SBOM, and Build Provenance

A build is only trustworthy when an organization can answer three questions: **what components does the artifact contain, which vulnerabilities must be addressed, and from which source code and process was the artifact created?** Artifact Analysis, Software Bill of Materials (SBOM), and build provenance provide distinct pieces of evidence to answer those questions. When combined with attestations and Binary Authorization, development teams can enforce verification gates before containers are deployed to Cloud Run or Google Kubernetes Engine (GKE).

In the CLOUD_PROVIDERS_GCP module, these capabilities help secure the software supply chain from source code, dependencies, and build processes to registries and runtime environments. Learners need to know how to scan images in Artifact Registry, generate and store SBOMs, inspect provenance generated by Cloud Build, verify origin by digest, and use attestations as deployment prerequisites.

The module scope spans project organization, IAM and VPC, Compute Engine, GKE, Cloud Run, storage services, and databases. Through deployment scenarios, learners choose services, secure resources, automate releases, and monitor reliability and cost; this lesson focuses on artifact security evidence within that release workflow.

After this lesson, you will be able to:

- Distinguish between Artifact Analysis, SBOM, vulnerability occurrences, build provenance, and attestations.
- Enable vulnerability scanning for images in Artifact Registry and read results by digest.
- Generate or upload SBOMs in supported formats, store them, and retrieve them using the Google Cloud CLI.
- Configure Cloud Build to generate build provenance and verify source, builder, build arguments, and image digest.
- Verify provenance against SLSA using the slsa-verifier tool.
- Use Binary Authorization and attestors to allow only policy-compliant artifacts to deploy.

## 1. Big Picture of Software Supply Chain Security

The software supply chain spans multiple components: source code repositories, third-party libraries, builders, build configurations, artifact registries, testing processes, and deployment platforms. A vulnerability or unauthorized change at any stage can compromise the final artifact.

Google Cloud services serve distinct roles:

| Component | Question to Answer | Role |
|---|---|---|
| Artifact Registry | Which artifact is stored and distributed? | Stores container images and packages by version/tag/digest |
| Artifact Analysis | Which packages and vulnerabilities exist in the artifact? | Scans images/packages, stores vulnerability occurrences, metadata, and SBOMs |
| SBOM | Which dependencies compose the artifact? | Inventory of packages, versions, origins, and related metadata |
| Cloud Build provenance | By what process was the artifact built? | Verifiable evidence of source, builder, build definition, parameters, and digest |
| Attestation | Which security conditions have been verified for the artifact? | Signature confirming an action or check passed on a digest |
| Binary Authorization | Is the artifact eligible for deployment? | Evaluates policies and attestations at deploy time |

~~~mermaid
flowchart TD
    SRC["Source repository<br/>commits and dependencies"] --> BUILD["Cloud Build<br/>build, test, scan"]
    BUILD --> IMAGE["Container image<br/>immutable digest"]
    BUILD --> PROV["SLSA build provenance"]
    IMAGE --> AR["Artifact Registry"]
    AR --> AA["Artifact Analysis"]
    AA --> VULN["Vulnerability occurrences"]
    AA --> SBOM["SBOM / dependency inventory"]
    BUILD --> TEST["Tests and security checks"]
    PROV --> VERIFY["Verify source, builder, digest"]
    TEST --> SIGN["Signer creates attestation"]
    VERIFY --> SIGN
    SIGN --> ATTEST["Binary Authorization attestor"]
    AR --> DEPLOY["Cloud Run / GKE deployment"]
    ATTEST --> POLICY["Binary Authorization policy"]
    POLICY --> DEPLOY
~~~

This workflow can be adopted incrementally. Initially, teams can enable vulnerability scanning and generate SBOMs to understand image composition. Next, add provenance to verify origin and builders. Finally, attestations and Binary Authorization turn verification checks into mandatory pre-deployment gates.

## 2. Why Use Image Digest as the Identifier?

Container images are commonly referenced by tag, for example:

~~~text
asia-southeast1-docker.pkg.dev/acme-prod/apps/orders-api:v1.4.0
~~~

A tag is a human-readable label and can be moved to another image. If someone pushes a new image and reuses the tag v1.4.0, the same tag can point to different content over time.

A digest identifies image content by its SHA-256 hash:

~~~text
asia-southeast1-docker.pkg.dev/acme-prod/apps/orders-api@sha256:0123456789abcdef...
~~~

When image content changes, the digest changes as well. This is the right identifier for binding scan results, SBOMs, provenance, attestations, and deployments.

**Operational rule:** use tags for naming and release organization; use digests to identify the exact artifact verified and deployed.

For example, a pipeline can build an image tagged with the commit SHA, push it to Artifact Registry, retrieve the digest returned by the registry, and pass that digest through subsequent steps:

1. Artifact Analysis scans the exact image digest.
2. An SBOM is generated and linked to that image.
3. Provenance confirms the digest was built from the expected commit and builder.
4. A test signer creates an attestation for that exact verified digest.
5. Cloud Run or GKE deploys the same digest.

If a pipeline inspects an image by tag and then deploys a mutable tag, inspection evidence may no longer describe the running artifact.

## 3. Artifact Analysis and Vulnerability Scanning

Artifact Analysis is a service that manages security metadata for artifacts. For container images in Artifact Registry, the service can scan OS packages, language packages, and detect certain publicly tracked malicious packages.

### 3.1. Enabling APIs and Preparing the Repository

APIs typically required for container scanning and provenance workflows:

~~~bash
gcloud services enable \
  artifactregistry.googleapis.com \
  containeranalysis.googleapis.com \
  containerscanning.googleapis.com \
  cloudbuild.googleapis.com \
  --project=PROJECT_ID
~~~

The project needs billing enabled and a Docker repository in Artifact Registry. Images must be pushed to a compatible repository. The build identity needs write permissions for images; the operational identity needs permissions to view metadata and vulnerability occurrences.

Separate permissions by duty:

- Builders are permitted to build and push artifacts to the target repository.
- Security teams have permissions to view scan results, SBOMs, and metadata.
- Signers have permissions to create attestations once checks complete.
- Deployers have permissions to deploy workloads and read necessary policies.

Do not grant project-wide admin permissions to every pipeline just to read scan results or push images.

### 3.2. Automatic Scanning and On-Demand Scanning

Artifact Analysis supports two main scanning modes:

| Scan Mode | Timing | Best Suited When |
|---|---|---|
| Automatic scanning | When a new image is pushed to Artifact Registry | Wanting baseline results and ongoing risk monitoring |
| On-demand scanning | When a pipeline or operator explicitly invokes a scan command | Wanting a check gate at a specific point in CI/CD |

Automatic scanning consists of two phases:

- **On-push scanning**: scans newly pushed images and creates vulnerability occurrences for identified packages.
- **Continuous analysis**: updates metadata as vulnerability feeds receive new information, adding or removing occurrences accordingly.

Artifact Analysis scans by image digest. Changing a tag without changing image content does not trigger a new scan. Results cover only packages and vulnerabilities recognizable from supported data sources.

For images or packages not tracked publicly, zero findings does not prove an artifact is completely secure.

### 3.3. Reading Vulnerability Occurrences

Artifact Analysis stores vulnerability data as notes and occurrences. A note describes a class of issue, such as a CVE; an occurrence links that issue to a specific package or image.

You can list vulnerability occurrences for an image:

~~~bash
gcloud artifacts docker images list \
  --show-occurrences \
  --occurrence-filter='kind="VULNERABILITY"' \
  --format=json \
  asia-southeast1-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE
~~~

To view metadata for a specific image by digest:

~~~bash
gcloud artifacts docker images describe \
  asia-southeast1-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE@sha256:DIGEST \
  --show-package-vulnerability \
  --format=json
~~~

Results can include severity, CVE, package name, installed version, and fixed version. When analyzing findings, check:

- Is the package actually present in the deployed image?
- Does the affected version fall within the CVE's scope?
- Is a compatible update or patch available?
- Is the package used at runtime or only during a build stage?
- Has the image been rebuilt after updating dependencies?

### 3.4. Continuous Analysis Does Not Replace Proactive Rescanning

Artifact Analysis continues updating vulnerability metadata for images/packages pulled within the last 30 days. After 30 days without being pulled, metadata can become stale; metadata stale for more than 90 days may be archived and queryable only via API. Pulling the image again can trigger metadata refresh, though updates can take up to 24 hours.

This matters for older images running in production that are rarely pulled. Operations teams should have a process to check result freshness, periodically pull/scan critical images, and avoid treating stale results as current proof.

## 4. SBOM: Inventory of Artifact Components

An SBOM (Software Bill of Materials) is a machine-readable inventory describing packages and dependencies that make up software. An SBOM may include:

- OS packages such as Debian packages or Alpine packages.
- Application libraries such as Maven dependencies, npm packages, or Go modules.
- Package names, versions, and suppliers.
- Dependency relationships, license metadata, and package origins when determinable by tools.

An SBOM answers **what the artifact contains**. It helps assess impact when a dependency gets a new CVE, check licenses, and satisfy audit requirements. An SBOM alone does not determine whether a package is safe; pair it with vulnerability scanning, VEX, and security policies.

### 4.1. SBOM Formats

Common formats:

| Format | Characteristics |
|---|---|
| SPDX | Standard describing packages, licenses, files, and relationships; Artifact Analysis generates SBOMs in SPDX 2.3 |
| CycloneDX | SBOM standard focused on components, dependencies, and risk management metadata |

Artifact Analysis generates SBOMs in SPDX 2.3. When uploading SBOMs from external tools to Artifact Analysis, supported JSON formats include SPDX 2.2/2.3 and CycloneDX 1.4/1.5. Confirm format versions with downstream systems before defining data contracts.

### 4.2. Generating an SBOM from an Image in Artifact Registry

After an image is pushed and Artifact Analysis holds package metadata, use the Google Cloud CLI to export an SBOM:

~~~bash
gcloud artifacts sbom export \
  --uri=asia-southeast1-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE@sha256:DIGEST
~~~

Artifact Analysis stores SBOMs in Cloud Storage within the project. If no suitable bucket exists in the same region as the image, the service may automatically create a bucket named:

~~~text
artifactanalysis-REGION-PROJECT_NUMBER
~~~

Other SBOMs in the same region of the project are stored in the corresponding bucket. Because SBOMs can reveal internal library names, dependency graphs, and product details, manage bucket access permissions like sensitive engineering data.

You can inspect an image's SBOM reference metadata:

~~~bash
gcloud artifacts docker images describe \
  asia-southeast1-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE@sha256:DIGEST \
  --show-sbom-references \
  --format=json
~~~

Artifact Analysis's SBOM reference occurrence can contain the SBOM storage location, SBOM hash, and a signature over the reference payload. That signature helps verify the SBOM's generation origin from Artifact Analysis.

### 4.3. Uploading SBOMs Generated by Other Tools

An organization may generate SBOMs in the build pipeline using Syft, cdxgen, or tools suited to its language and container build. After verifying the file format, upload it to Artifact Analysis:

~~~bash
gcloud artifacts sbom load \
  --source=./orders-api.spdx.json \
  --uri=asia-southeast1-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE@sha256:DIGEST
~~~

Artifact Analysis supports SPDX 2.2/2.3 and CycloneDX 1.4/1.5 for SBOM uploads. The `uri` parameter identifies the image described by the SBOM; prefer using a digest to avoid attaching the SBOM to the wrong image.

To use a custom bucket, specify `--destination`. You can pass `--kms-key-version` to sign the SBOM reference occurrence payload with a Cloud KMS key version. This signs the SBOM reference; it does not mean the SBOM contents have undergone security review.

### 4.4. Reading and Using SBOMs

SBOMs are valuable when a new CVE is disclosed. Security teams can search for all artifacts containing the affected package and version, then cross-reference against running images.

For example, when a library like Log4j or an OS package has a new vulnerability:

1. Identify the affected package and versions from the advisory.
2. Query SBOMs of production images.
3. Identify image digests containing the package.
4. Check vulnerability occurrences for severity and patch availability.
5. Prioritize rebuilding/redeploying high-risk workloads.
6. Record check results and replaced image digests.

An SBOM reflects components only at creation time. When an image changes, generate or associate a new SBOM with the new digest. Never reuse an old SBOM for a new image simply because the tag is the same.

## 5. VEX: Explaining Vulnerability Exploitability

VEX (Vulnerability Exploitability eXchange) is security advisory data indicating whether a product is actually affected by a known vulnerability. VEX adds context that a raw CVE list cannot express.

Common VEX statuses:

| Status | Meaning |
|---|---|
| Not affected | The product is not impacted by this vulnerability |
| Affected | The product is affected; remediation action is required |
| Fixed | This version already contains a fix |
| Under investigation | Under investigation; conclusion will be updated later |

For instance, a scanner may report a package with a CVE, yet that package sits in an unenabled module or the vulnerable code path is unreachable in the product configuration. The publisher can provide a VEX statement explaining why the artifact is unaffected, accompanied by justification and scope.

Artifact Analysis supports storing and viewing VEX statements; current documentation marks this capability as Preview. When using VEX:

- Bind statements to the exact artifact and vulnerability.
- Specify publisher, justification, and product scope.
- Use Not affected only when backed by reliable technical analysis.
- Track expiration and update statements when product versions or configurations change.

VEX does not delete the underlying vulnerability occurrence and does not replace updating packages when patches exist. It helps prioritize remediation and prevent false conclusions from isolated findings.

## 6. Build Provenance and SLSA

Build provenance is verifiable data describing how an artifact was created. For container images, provenance can describe:

- Generated image digest.
- Source repository and revision/commit.
- Builder or build execution system.
- Build configuration and build type.
- Input parameters, resolved dependencies, and build timestamps.
- Build invocation ID to trace the run.

Provenance answers **how and from where the artifact was built**. SBOMs describe components; provenance describes the creation process of that artifact. These two forms of evidence complement one another.

### 6.1. What Is SLSA?

SLSA (Supply-chain Levels for Software Artifacts) is a framework of practices and assurance levels designed to improve software supply chain integrity. SLSA levels define requirements on build processes, builders, and provenance tamper-resistance.

Cloud Build supports generating build provenance meeting SLSA Build Level 3 under SLSA v0.1 and v1.0 specifications. SLSA v1.0 provenance includes a `buildType` describing the build template and parameter sources. Actual assurance still depends on builder configuration, source repositories, IAM permissions, and pipeline protections.

Do not look solely at a SLSA badge and conclude the entire software is secure. SLSA provenance strengthens origin and build-process verification; it does not prove dependencies are vulnerability-free or that business tests are thorough.

### 6.2. Conditions to Generate Provenance in Cloud Build

For Cloud Build to generate provenance for container images:

1. Enable the Cloud Build API, Container Analysis API, and Artifact Registry API.
2. Store the image in Artifact Registry.
3. Declare the image in the `images` field of the build configuration.
4. Enable `requestedVerifyOption: VERIFIED` to request provenance generation and presence verification.
5. Do not push the image via an explicit `docker push` step if you want Cloud Build to automatically generate provenance following the documented flow.

Example `cloudbuild.yaml`:

~~~yaml
steps:
  - name: gcr.io/cloud-builders/docker
    args:
      - build
      - -t
      - asia-southeast1-docker.pkg.dev/PROJECT_ID/apps/orders-api:$SHORT_SHA
      - .

images:
  - asia-southeast1-docker.pkg.dev/PROJECT_ID/apps/orders-api:$SHORT_SHA

options:
  requestedVerifyOption: VERIFIED
~~~

The `images` field instructs Cloud Build to push the built image to Artifact Registry after build completion. `requestedVerifyOption: VERIFIED` enables provenance generation and verifies that metadata was produced. The build is marked successful only when the requested provenance is generated.

Run the build:

~~~bash
gcloud builds submit \
  --project=PROJECT_ID \
  --config=cloudbuild.yaml \
  .
~~~

Cloud Build provenance for containers is generated only for artifacts stored in Artifact Registry. For non-container applications, Cloud Build also supports provenance for certain standalone artifacts such as Go, Java Maven, Python, and Node.js npm when uploading artifacts to Artifact Registry.

### 6.3. Viewing Provenance by Image Digest

After building, record the digest from output or Artifact Registry. Query provenance:

~~~bash
gcloud artifacts docker images describe \
  asia-southeast1-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE@sha256:DIGEST \
  --show-provenance \
  --format=json
~~~

Output may contain:

- `fully_qualified_digest` of the image.
- `buildType` and SLSA provenance predicate.
- Source repository, branch, and commit SHA.
- Build ID and trigger.
- Builder ID.
- Resolved dependencies and builder image digest.
- Build start/end timestamps.

You can use Security insights in Cloud Build Build History or Artifact Registry to view consolidated build, dependency, SBOM, vulnerability, and provenance details.

### 6.4. Verifying Provenance with SLSA Verifier

Reading provenance JSON is not enough to prove the data was not forged. Verify signatures, builder, and source against a trust policy.

SLSA verifier is an open-source tool for checking provenance. Google Cloud documentation directs using version 2.1 or newer.

Install the tool per the `slsa-verifier` project instructions, then fetch the image's provenance by digest:

~~~bash
export IMAGE="asia-southeast1-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE@sha256:DIGEST"

gcloud artifacts docker images describe "$IMAGE" \
  --format=json \
  --show-provenance > provenance.json
~~~

Verify provenance:

~~~bash
slsa-verifier verify-image "$IMAGE" \
  --provenance-path provenance.json \
  --source-uri "github.com/ORG/REPOSITORY" \
  --builder-id="https://cloudbuild.googleapis.com/GoogleHostedWorker"
~~~

Replace the source URI with your actual repository and the builder ID with your organization-approved builder. A `PASSED` result indicates the provenance meets the supplied verification conditions. If the source or builder does not match, the verifier fails with an error.

When designing policies, explicitly define:

- Which repositories are permitted as sources.
- Which branches/tags/revisions are permitted to build.
- Which builder IDs are trusted.
- Which build definitions and parameters are allowed.
- Whether the image digest matches the artifact being deployed.

## 7. Attestations and Binary Authorization

Provenance describes the build process. An attestation typically certifies that a condition or activity was completed on an artifact, for example:

- The image passed regression tests.
- Vulnerability scans did not exceed policy thresholds.
- License review was completed.
- The artifact was approved by the security team.
- The image was built by a trusted-list builder.

Attestations are created by signing the image digest. Because signatures bind to the digest, altering image contents yields a different digest, preventing reuse of the old image's attestation.

### 7.1. Binary Authorization Components

| Component | Role |
|---|---|
| Attestation | Signed evidence bound to an image digest |
| Signer | Identity or service generating signatures |
| Attestor | Resource defining signature verification and attestation checks |
| Policy | Rules requiring attestors or allowing/exempting images |
| Deployer | Deployment platform invoking policy checks |

Binary Authorization can verify attestations at deploy time. If an image lacks an attestation from a required attestor or has an invalid signature, deployment is rejected per policy.

Cloud Build includes the `built-by-cloud-build` attestor for scenarios wishing to deploy only images built by Cloud Build. For custom workflows, organizations can create attestors and signers for their own verification criteria.

### 7.2. Post-Test Attestation Flow

A pipeline can execute:

1. Build the image and obtain its digest.
2. Wait for Artifact Analysis to finish scanning.
3. Evaluate findings against policy.
4. Generate an SBOM and verify provenance.
5. Run tests and policy checks.
6. If all conditions pass, the signer creates an attestation for the digest.
7. Binary Authorization verifies the attestation at deployment time.

~~~mermaid
sequenceDiagram
    participant CB as Cloud Build
    participant AR as Artifact Registry
    participant AA as Artifact Analysis
    participant QA as Test / Security gate
    participant SG as Attestation signer
    participant BA as Binary Authorization
    participant CR as Cloud Run or GKE

    CB->>AR: Push image and generate provenance
    AR->>AA: New image digest
    AA-->>QA: Vulnerability findings and SBOM
    CB-->>QA: Build provenance
    QA->>QA: Check tests, CVEs, licenses, source
    QA->>SG: Request digest signing if passed
    SG->>AR: Write attestation for digest
    CR->>BA: Request image verification
    BA->>AR: Locate attestation and verify signature
    BA-->>CR: Allow or deny deployment
~~~

Separating signer permissions from regular build permissions reduces the risk of a compromised build step signing its own artifact. Signers should accept verified results from a controlled pipeline and sign only digests that satisfied criteria.

### 7.3. Enforcing Policies on Cloud Run and GKE

Binary Authorization supports policies for GKE and Cloud Run. On a Cloud Run service, policies are evaluated when deploying a new revision. If the revision fails policy, deployment fails; the previously serving revision continues serving in its current state.

On a Cloud Run job, policy is checked at job execution time. A job configuration can be updated, yet execution fails if the image violates policy.

In emergencies requiring policy bypass, Cloud Run supports breakglass. This is an intentional exception logged in Cloud Audit Logs; use it only under emergency procedures with an approver and follow-up remediation.

Do not confuse Binary Authorization with a vulnerability scanner. Scanners produce vulnerability metadata; Binary Authorization evaluates policies and attestations. To block images with CVEs, pipelines must turn scan results into pass/fail gates and issue attestations only when policy passes.

## 8. Building Verification Policies in CI/CD

A practical policy should organize checks into categories:

| Category | Example Condition | Evidence |
|---|---|---|
| Origin | Built from allowed repository and branch | Build provenance |
| Builder | Used trusted Cloud Build worker | Builder ID in provenance |
| Components | SBOM generated and bound to exact digest | SBOM reference |
| Vulnerabilities | No unapproved Critical or High findings | Vulnerability occurrences and VEX |
| Testing | Unit, integration, and security tests passed | CI test results / attestation |
| Approval | Production release approved by authorized personnel | Approval record / attestation |

Simple policy example:

- Critical vulnerability: block release immediately unless an approved and recorded exception exists.
- High vulnerability: require a patch or a justified VEX statement.
- Medium/Low: create backlog items with remediation SLAs.
- Invalid provenance: block deployment.
- Missing SBOM or digest mismatch: block promotion.
- Missing attestation from trusted signer: Binary Authorization rejects deployment.

Severity thresholds are examples only. Organizations must weigh exploitability, exposure, data sensitivity, environment, and remediation timelines. Never rely solely on CVSS scores while ignoring exploitability and runtime context.

## 9. Real-World Scenario: Securing the Orders API

Suppose a development team deploys the Orders API as a container to Cloud Run. They want to prove images originate from the official repository, know internal dependencies, and block unverified images.

Workflow:

1. Cloud Build checks out a reviewed commit.
2. Builds the image tagged with the commit SHA and stores it in Artifact Registry.
3. Cloud Build generates provenance containing source commit, builder, build configuration, and digest.
4. Artifact Analysis scans the image, creates vulnerability occurrences, and supplies dependency metadata.
5. Pipeline exports an SPDX 2.3 SBOM linked to the digest.
6. SLSA verifier validates the source repository and builder ID.
7. Test stage runs regression and security tests.
8. Policy gate evaluates CVEs and licenses. Any finding assessed as unaffected gets a VEX statement or exception record.
9. Signer creates an attestation for the digest once all gates pass.
10. Cloud Run Binary Authorization checks the attestation before admitting the new revision.

When a new CVE emerges after an image is already running in production, operations uses SBOMs to locate images containing the affected package, uses Artifact Analysis to view occurrences and severity, and builds a new image with updated dependencies. New provenance and attestations must be created for the new digest before deployment.

This workflow lets the team answer three questions during an incident: which image is affected, which dependencies it contains, and which commit/builder produced it.

## 10. Permissions Governance, Retention, and Auditing

### 10.1. IAM by Responsibility

Common roles in the workflow:

- Builder: reads source, runs builds, and writes images to Artifact Registry.
- Artifact reader: reads images, SBOMs, provenance, and vulnerability occurrences.
- Security reviewer: views findings, assesses VEX, and approves exceptions.
- Signer: signs digests and creates attestations.
- Deployer: deploys policy-accepted images.

Separate artifact read permissions from artifact write permissions. Tightly restrict attestation creation permissions because signers sit inside the trust boundary. Permissions to edit Binary Authorization policies should also be restricted to platform/security administrators.

### 10.2. Retaining Evidence

Artifact Registry cleanup policies can delete old images. Provenance and SBOMs may be stored as attachments or objects in Cloud Storage; their lifecycles can differ.

Cloud Build provenance attachments are not governed by standard Artifact Registry cleanup policies on their own; attachments are deleted when the image they attach to is deleted. SBOMs generated by Artifact Analysis remain in Cloud Storage until the object or bucket is deleted.

For auditing, define separate retention windows for:

- Image digests and release tags.
- SBOMs, provenance, and attestations.
- Build logs and test reports.
- Vulnerability findings, VEX statements, and exception records.
- Cloud Audit Logs for deploy and breakglass actions.

Do not delete images purely to save storage before confirming whether linked evidence must be retained for compliance policies.

### 10.3. Cost and Performance

Costs can arise from Artifact Analysis scanning, Cloud Storage holding SBOMs, Artifact Registry storage, Cloud Build execution, and log retention.

To control costs:

- Select repositories and images to scan based on criticality.
- Strip unnecessary packages and optimize multi-stage Docker builds.
- Use digests to avoid redundant checks triggered by tag moves.
- Design appropriate retention for images and evidence.
- Monitor scan volume, storage, and build times.
- Do not skip continuous analysis for production images just because they were scanned at build time.

## 11. Common Errors and Troubleshooting

| Symptom | Possible Cause | Resolution |
|---|---|---|
| No vulnerability findings shown | Scan incomplete, API disabled, or image lacks supported packages | Check Artifact Analysis API, repository, digest, and scan status |
| Tag changed but no new scan runs | Scans are keyed by image digest | Confirm whether the tag points to a new digest |
| Vulnerability metadata is stale | Image has not been pulled for a long time | Pull image and wait for metadata refresh; check freshness status |
| Cannot export SBOM | Image lacks package metadata or missing Cloud Storage API/permissions | Check scan, Container Analysis API, Container Scanning API, and SBOM storage permissions |
| SBOM attached to wrong image | Used a mutable tag or wrong URI | Use image digest when exporting/uploading and verify SBOM reference |
| Cloud Build does not generate provenance | Missing `images` field, missing `requestedVerifyOption`, or manual `docker push` | Use `images` field, set `VERIFIED`, and let Cloud Build push via the supported flow |
| Provenance not visible | Artifact not stored in Artifact Registry or queried wrong digest | Check registry, image digest, and metadata read permissions |
| SLSA verifier reports wrong source | Source URI in command mismatches provenance | Check allowed repository URI, commit, and builder ID |
| Binary Authorization rejects deploy | Missing attestation or signature not trusted by attestor | Verify digest, attestor, public key, policy, and access permissions |
| Cloud Run revision deploy fails | Image violates Binary Authorization policy | Inspect policy and attestation errors; use breakglass only under emergency procedures |
| Cannot locate old SBOM | Cloud Storage object or bucket was deleted | Check retention, audit logs, and evidence storage policies |

- [ ] Container images are stored in Artifact Registry and identified by digest.
- [ ] Artifact Analysis API and Container Scanning API are enabled for needed scopes.
- [ ] Vulnerability scan results are complete with clear freshness status.
- [ ] Vulnerability findings are assessed by severity, exploitability, and runtime context.
- [ ] SBOMs are generated or uploaded in supported formats, bound to the exact image digest.
- [ ] SBOMs are stored in Cloud Storage with proper IAM and retention.
- [ ] Cloud Build uses the `images` field and `requestedVerifyOption: VERIFIED` to produce provenance.
- [ ] Provenance is verified for source repository, commit, builder, and build parameters.
- [ ] `slsa-verifier` or an equivalent mechanism verifies provenance prior to promotion.
- [ ] Attestations are signed for digests that passed tests and policy checks.
- [ ] Signers have isolated identities and permissions, never sharing signing rights with untrusted builders.
- [ ] Binary Authorization policies are configured for Cloud Run or GKE.
- [ ] Breakglass has approval, audit, and remediation procedures.
- [ ] Build logs, SBOMs, provenance, attestations, and exception records have proper retention.
- [ ] Processes exist to locate and rebuild all affected images when a new CVE emerges.

## 13. Self-Check Questions

**1. How do Artifact Analysis and Artifact Registry differ?**

Artifact Registry stores and distributes artifacts. Artifact Analysis scans and manages security metadata such as vulnerability occurrences, package details, SBOMs, and certain attestations/metadata.

**2. What two distinct types of information do SBOMs and build provenance provide?**

An SBOM describes an artifact's components and dependencies. Build provenance describes the source code, builder, build definition, parameters, and digest of the produced artifact.

**3. Why bind SBOMs, provenance, and attestations to image digests?**

Digests identify specific image content. Tags can move, whereas digests guarantee all evidence describes the exact artifact inspected and deployed.

**4. What must Cloud Build configure to generate provenance for container images?**

Store the image in Artifact Registry via the `images` field in the build config and set `options.requestedVerifyOption` to `VERIFIED`. Do not use a manual `docker push` step in the documented provenance generation flow.

**5. What does SLSA verifier check?**

It verifies image provenance, including the validity of build evidence and the source URI and builder ID conditions required by the operator.

**6. How does Binary Authorization use attestations?**

An attestation certifies that an activity completed on an image digest. Binary Authorization verifies the signature via an attestor and evaluates it against policy before allowing deployment.

**7. If a scanner finds zero vulnerabilities, can we conclude the image is completely safe?**

No. Results only reflect packages and vulnerabilities supported by the data sources and scanner at check time. Combine SBOMs, provenance, testing, policies, and continuous monitoring.
