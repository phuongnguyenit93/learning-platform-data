# Cloud KMS Audit Logs and Key Usage Monitoring

In the `CLOUD_PROVIDERS_GCP` module, you explore Google Cloud from organizations, projects, IAM, and VPCs to Compute Engine, GKE, Cloud Run, storage services, and databases. Deployment scenarios help you select services, protect resources, automate releases, and monitor reliability and cost. In the **Encryption Keys and Secrets** chapter, Cloud Key Management Service (Cloud KMS) provides centralized encryption key management; Cloud Audit Logs provide evidence showing who called administrative or key-usage APIs, when, and on which resources.

This lesson focuses on enabling, querying, and monitoring Cloud KMS audit logs. The goal is to detect unauthorized configuration changes, identify principals using keys, investigate anomalous decryption activity, and retain evidence for operations or auditing.

## 1. Why Monitor Key Activity?

A KMS key can be used by many workloads: applications calling `Encrypt` or `Decrypt`, Google Cloud services using customer-managed encryption keys (CMEK), or a pipeline signing data with an asymmetric key. By monitoring only key state in Cloud KMS, operators know whether a key is enabled, rotated, or disabled, but lack enough information to answer questions such as:

- Which identity or service account called the decrypt operation?
- Which key was used, which API was called, and when did the call happen?
- Who changed the IAM policy, switched the primary key version, or requested destroying a version?
- Was an operation denied or did it fail?
- Did key usage volume spike compared to normal activity?

Cloud Audit Logs record API activity for which Google Cloud supports auditing. For Cloud KMS, logs typically indicate the API method, resource, calling identity, and outcome. Logs are not copies of application data: you do not use them to read encrypted plaintext or extract secret key material. To fully understand an event, correlate audit logs with application logs, workload logs, and related systems.

## 2. Cloud Audit Log Types Related to Cloud KMS

Cloud Audit Logs have four types. They answer different questions:

| Log Type | Content | Default Status |
| --- | --- | --- |
| **Admin Activity** | Operations performed by users or workloads to create, update, delete resources, or modify configuration and access permissions. | Always written; cannot be disabled or excluded. |
| **Data Access** | Calls reading metadata/configuration or accessing user-provided data. | Usually disabled by default, except for certain BigQuery services; must be explicitly enabled. |
| **System Event** | Changes performed by Google Cloud systems or managed service agents. | Always written. |
| **Policy Denied** | Access attempts denied due to security policy violations. | Generated by default; cannot be disabled, though exclusion filters can prevent storage in Cloud Logging. |

A key point when working with Cloud KMS is that **key usage typically appears in Data Access logs**. If you inspect only Admin Activity, you can see who created or modified keys, but you will not see complete `Encrypt`, `Decrypt`, or signing calls.

### 2.1. Admin Activity: configuration and key lifecycle changes

Administrative operations requiring `ADMIN_WRITE` IAM permissions generate Admin Activity audit logs. Examples:

| Cloud KMS Method | Operational Meaning |
| --- | --- |
| `CreateKeyRing`, `CreateCryptoKey` | Creates a key ring or crypto key. |
| `UpdateCryptoKey` | Modifies key configuration, such as automatic rotation settings. |
| `UpdateCryptoKeyPrimaryVersion` | Switches the key's primary version to another version. |
| `CreateCryptoKeyVersion`, `UpdateCryptoKeyVersion` | Creates or updates a key version. |
| `DestroyCryptoKeyVersion`, `RestoreCryptoKeyVersion` | Schedules destruction or restores a key version per allowed lifecycle states. |
| `SetIamPolicy` | Modifies IAM permissions on a key ring or crypto key. |

These logs help investigate changes that may impact data protection. For example, an unexpected `SetIamPolicy` might grant key usage permissions to a new service account; an `UpdateCryptoKeyPrimaryVersion` might relate to a planned rotation or an operational incident.

### 2.2. Data Access: reading metadata and using keys

Cloud KMS categorizes methods based on the IAM permission type checked by each method. `ADMIN_READ`, `DATA_READ`, and `DATA_WRITE` permissions generate Data Access audit logs; `ADMIN_WRITE` permissions generate Admin Activity audit logs. Therefore, metadata-reading operations such as `GetCryptoKey`, `GetCryptoKeyVersion`, and `ListCryptoKeys` also belong to Data Access, even though they do not directly encrypt data.

Common key-usage methods include:

| Method | Purpose | Log Type |
| --- | --- | --- |
| `Encrypt`, `RawEncrypt` | Encrypts data using a symmetric key. | Data Access (`DATA_READ`) |
| `Decrypt`, `RawDecrypt` | Decrypts data. | Data Access (`DATA_READ`) |
| `AsymmetricSign` | Creates a signature using an asymmetric private key. | Data Access (`DATA_READ`) |
| `AsymmetricDecrypt` | Decrypts using an asymmetric private key. | Data Access (`DATA_READ`) |
| `MacSign`, `MacVerify` | Generates or verifies a Message Authentication Code (MAC). | Data Access (`DATA_READ`) |
| `GetPublicKey` | Retrieves the public key corresponding to an asymmetric key version. | Data Access (`DATA_READ`) |
| `GetCryptoKey`, `GetCryptoKeyVersion`, `ListCryptoKeys` | Reads metadata or lists keys and versions. | Data Access (`ADMIN_READ`) |

The permission type labels in the table reflect the IAM classification of the Cloud KMS API; do not assume every `DATA_READ` method returns plaintext user data to the caller. For example, `Encrypt` and `Decrypt` are logged under the permission classification Cloud KMS defines for those methods.

**Note:** `GenerateRandomBytes` is a Cloud KMS method that does not generate an audit log. Do not treat the absence of logs for this method as proof that the API was never called. The list of audited methods can change by API; cross-check Cloud KMS audit logging documentation when designing controls.

## 3. Enabling Data Access Audit Logs for Cloud KMS

Admin Activity is recorded automatically. To track key usage and metadata read operations, you must enable Data Access logs for the Cloud Key Management Service.

### 3.1. Configuring in Google Cloud Console

1. Open Google Cloud Console and select the appropriate organization, folder, or project to configure.
2. Open **IAM & Admin → Audit Logs**.
3. Locate the **Cloud Key Management Service** (`cloudkms.googleapis.com`).
4. Enable the Data Access log types matching your monitoring objectives:
   - **Admin Read** to record metadata/configuration read operations such as describing keys or listing versions.
   - **Data Read** to record key usage operations such as encrypting, decrypting, signing, or verifying.
   - **Data Write** if Cloud KMS APIs in your scope check permissions of this type.
5. Save the configuration and perform an authorized test operation to confirm logs appear.

You can enable configuration at the organization, folder, or project level. Settings inherited from parent levels apply to child projects; a project cannot disable a Data Access log type already enabled at a parent organization or folder. When changing configuration at the project level, check inherited policies to understand the effective scope.

### 3.2. Configuring via IAM AuditConfig

In an IAM policy, the audit configuration for Cloud KMS looks like this:

```json
{
  "auditConfigs": [
    {
      "service": "cloudkms.googleapis.com",
      "auditLogConfigs": [
        { "logType": "ADMIN_READ" },
        { "logType": "DATA_READ" },
        { "logType": "DATA_WRITE" }
      ]
    }
  ]
}
```

This is an illustrative snippet to merge into an existing IAM policy. When updating a policy via API or CLI tools, read the current policy and preserve all existing `auditConfigs`, bindings, and other configurations. Do not replace the entire IAM policy with this sample JSON alone, as doing so can accidentally drop permissions or audit settings for other services.

### 3.3. Permissions to view logs

Permission to configure audit logs and permission to read logs are separate. To read Admin Activity, System Event, and Policy Denied logs, operators typically need `roles/logging.viewer`. To also read Data Access logs in the `_Default` bucket, permissions including `logging.privateLogEntries.list` are required; the suitable predefined role is **Private Logs Viewer** (`roles/logging.privateLogViewer`). This role includes Logs Viewer permissions plus Data Access log read permissions. The Editor role (`roles/editor`) does not automatically grant the permissions required to read Data Access logs.

Grant log viewing permissions following least privilege. Audit logs can reveal identities, resource names, caller IP addresses, and sensitive operational metadata; do not grant broader view access than job duties require.

### 3.4. Planning log volume and cost

Data Access logs can generate large log volumes and incur Cloud Logging costs. A system using CMEK can generate logs for many key operations from services and service agents. Before enabling organization-wide, define the audit questions to answer, estimate traffic, review ingestion/storage costs, and decide where to retain logs.

In environments needing comprehensive monitoring, Data Access can be enabled broadly and routed to centralized storage. In high-volume environments, clearly define which permission types, services, and resource scopes need observation to balance investigative capability against cost. Never exclude logs mandated by audit requirements or organizational security policies.

## 4. Querying Cloud KMS Audit Logs in Logs Explorer

Open **Logging → Logs Explorer** in the project storing the logs. The baseline filter to view Cloud KMS audit logs is:

```text
protoPayload.serviceName="cloudkms.googleapis.com"
```

`protoPayload.serviceName` scopes results to Cloud KMS. You can combine filters on `logName`, `methodName`, `resourceName`, caller identity, or status to narrow your investigation.

### 4.1. Finding decryption calls

```text
log_id("cloudaudit.googleapis.com/data_access")
protoPayload.serviceName="cloudkms.googleapis.com"
protoPayload.methodName="Decrypt"
```

To find encryption calls, replace `Decrypt` with `Encrypt`. You can repeat this pattern for `AsymmetricSign`, `AsymmetricDecrypt`, `MacSign`, or `MacVerify` when workloads use those corresponding APIs.

### 4.2. Monitoring permission and key lifecycle changes

Example finding IAM policy modification operations:

```text
log_id("cloudaudit.googleapis.com/activity")
protoPayload.serviceName="cloudkms.googleapis.com"
protoPayload.methodName="SetIamPolicy"
```

Example finding key version destruction requests:

```text
log_id("cloudaudit.googleapis.com/activity")
protoPayload.serviceName="cloudkms.googleapis.com"
protoPayload.methodName="DestroyCryptoKeyVersion"
```

Similarly, filter `UpdateCryptoKeyPrimaryVersion` to check when the primary version changed, or `UpdateCryptoKey` to investigate key configuration changes.

### 4.3. Filtering by identity and resource

To inspect activity by a service account, add a principal filter:

```text
protoPayload.serviceName="cloudkms.googleapis.com"
protoPayload.authenticationInfo.principalEmail="orders-api@PROJECT_ID.iam.gserviceaccount.com"
```

To scope to a specific crypto key, filter by resource path:

```text
protoPayload.serviceName="cloudkms.googleapis.com"
protoPayload.resourceName:"projects/PROJECT_ID/locations/LOCATION/keyRings/KEY_RING/cryptoKeys/KEY_NAME"
```

Replace the sample values with the actual project ID, location, key ring, and key name. Combine the filters above with `methodName` to determine whether a specific identity performed a specific operation on a given key.

### 4.4. Finding calls with errors

```text
protoPayload.serviceName="cloudkms.googleapis.com"
severity>=ERROR
```

When inspecting a record, examine `protoPayload.status` to understand the error code and message. If a call was denied, also inspect `authorizationInfo` and the IAM policy at the time of the event. Some events denied by security policies may appear under the Policy Denied log type; distinguish them from application errors or other configuration errors.

## 5. Reading Important Fields in an Audit Log Entry

An audit log entry is wrapped in a `LogEntry` structure; the `protoPayload` section holds the `AuditLog` data. The following fields are typically helpful when investigating Cloud KMS:

| Field | Investigative Meaning |
| --- | --- |
| `timestamp` | Time the event was recorded. Normalize time zones when correlating with application logs. |
| `logName` | Indicates the log group such as `cloudaudit.googleapis.com/activity` or `cloudaudit.googleapis.com/data_access`. |
| `protoPayload.serviceName` | Service generating the audit log; for Cloud KMS this is `cloudkms.googleapis.com`. |
| `protoPayload.methodName` | API method called, such as `Decrypt` or `SetIamPolicy`. |
| `protoPayload.resourceName` | Related Cloud KMS resource, identifying the key ring, crypto key, or key version. |
| `protoPayload.authenticationInfo.principalEmail` | Authenticated identity, usually a user email or service account. |
| `protoPayload.requestMetadata.callerIp` | Caller IP address if present in the event. |
| `protoPayload.requestMetadata.callerSuppliedUserAgent` | Caller-supplied user agent if present; useful for distinguishing clients or workloads. |
| `protoPayload.authorizationInfo` | Permissions checked and their corresponding allow/deny outcomes. |
| `protoPayload.status` | Result status; when an error occurs, inspect the code and message for root cause. |

Not every record contains all fields. For instance, the IP address of internal calls between Google Cloud services may be masked as `private` or a placeholder value; do not assume `callerIp` is always the end user's original IP address. For workloads using CMEK, the principal in the log may be the service agent of the service using the key rather than the end user initiating the business request. Identify the workload identity and cross-check that service's logs before concluding unauthorized access occurred.

Cloud KMS is updating certain fields within `protoPayload` of Data Access logs. For new log analysis applications, prefer the fields recommended by current documentation: use `protoPayload.status.details` instead of `protoPayload.metadata` when reading error details for Cloud EKM key operations; use `protoPayload.metadata.entries.caller_provided_context` instead of `protoPayload.request.caller_provided_context` when reading caller-provided context. Transitions may roll out in phases, so log parsers should tolerate schema differences during compatibility periods.

## 6. Turning Audit Logs into Monitoring Signals

Manual log searches work well when investigating a known event. To detect events early, convert key query patterns into log-based metrics or alerting policies.

### 6.1. Establishing normal behavior

Before setting alert thresholds, establish a baseline per workload:

- Which service accounts are permitted to use each crypto key?
- Does the workload normally call `Encrypt`, `Decrypt`, or signing methods?
- Which keys are used by Google Cloud services via CMEK?
- What are normal usage frequencies and time windows?
- Who is authorized to modify IAM policies, rotation settings, or key version states?

A baseline helps distinguish legitimate traffic from truly anomalous changes. For example, an order-processing service account might decrypt frequently during peak hours; a deployment service account might only call admin operations during releases. Alerts should reflect the role and operating cadence of each workload.

### 6.2. Signals to monitor

| Signal | Question to Investigate |
| --- | --- |
| Sudden spike in `Decrypt` | Is there a new workload, retry loop, or anomalous data-reading behavior? |
| Unfamiliar principal calling `Decrypt` or `AsymmetricSign` | Was that identity granted key usage permissions by design? |
| Calls from unusual IP or user agent | Does the caller belong to approved infrastructure and network paths? |
| `SetIamPolicy` on a crypto key | Were new permissions granted or sensitive permissions broadened? |
| `DestroyCryptoKeyVersion` or primary version change | Was the operation part of an approved key lifecycle/recovery plan? |
| Consecutive errors | Are there IAM errors, key version misconfigurations, service limits, or permission probing? |

Do not alert on a single isolated event if that operation is normally part of a release workflow. Combine principal, resource name, method, timing, caller metadata, and status to reduce false positives.

### 6.3. Creating metrics, alerts, and log routing

A practical monitoring workflow can include:

1. Create a log-based metric counting `Decrypt` calls per project or per resource group.
2. Create dedicated metrics or queries for sensitive changes such as `SetIamPolicy`, `DestroyCryptoKeyVersion`, and `UpdateCryptoKeyPrimaryVersion`.
3. Set thresholds or alert conditions based on each workload's baseline; route alerts to on-call channels per organizational procedures.
4. Use log sinks to route audit logs to a centralized monitoring project, BigQuery, Cloud Storage, or Pub/Sub depending on retention and analytics needs.
5. Verify access controls, retention, and queryability at the log destination; periodically test retrieving a sample event to ensure evidence remains usable.

For multi-project organizations, centralizing Admin Activity logs helps security teams view Cloud KMS changes across the entire scope. Data Access logs can additionally be routed for projects or keys with strict usage-control requirements. Protect the log-storage project with dedicated IAM, restrict permissions to delete or modify sinks, and monitor the log routing configuration itself.

## 7. Real-World Scenario: Investigating an Anomalous Decryption Spike

Suppose the `orders-api` application uses the service account `orders-api@PROJECT_ID.iam.gserviceaccount.com` to decrypt data with the `orders-key` key. The operations team receives an alert that `Decrypt` calls spiked sharply overnight.

Investigate in the following sequence:

1. Open Logs Explorer and filter `serviceName="cloudkms.googleapis.com"`, `methodName="Decrypt"`, along with the `resourceName` path for `orders-key`.
2. Group results by `principalEmail` to identify which identity generated the majority of calls. If the principal is a service agent of a CMEK-enabled service, identify that service before attributing the spike to the application.
3. Compare `timestamp`, `callerIp`, and `callerSuppliedUserAgent` against the workload baseline. For fields absent from the log, check application or infrastructure logs.
4. Check `status` to distinguish successful calls from failed calls. Correlate timestamps with IAM changes or key configuration changes, especially `SetIamPolicy` and `UpdateCryptoKeyPrimaryVersion`.
5. If the principal or caller origin is unrecognized, verify the service account, IAM permissions, running workloads, and deployment history. Collect relevant logs before revoking permissions or disabling workloads to avoid losing investigative evidence.
6. After identifying root cause, tighten permissions to least privilege, update baselines/alerts, and document remediation decisions.

Audit logs provide a trace of Cloud KMS calls. They do not by themselves prove which end user initiated the business decryption request or which specific business data was read. To complete the investigation, correlate KMS events with request IDs, user identities, and business logs at the application layer if the system records those details.

## 8. Limitations and Best Practices

- **Enable the right log types:** Admin Activity does not replace Data Access. If the goal is tracking `Encrypt`/`Decrypt`, verify Data Read is enabled for Cloud KMS at the right scope.
- **Verify logs after configuration:** Run an authorized test call, then check `serviceName`, `methodName`, principal, and resource name in Logs Explorer.
- **Do not over-interpret missing logs:** Data Access might not be enabled, settings might be inherited from a parent level, or the method might not generate an audit log. `GenerateRandomBytes` is an explicit example noted by Cloud KMS.
- **Protect audit data:** Restrict read access to Data Access logs, manage retention and log sinks, and protect log-storage projects from unauthorized modifications.
- **Control costs:** Monitor log volume when enabling Data Access in projects with many CMEK-enabled workloads. Re-evaluate scope and retention against audit requirements.
- **Read logs in context:** A service agent can be a legitimate principal when Google Cloud services use CMEK. Correlate identity, resource name, and the calling service's logs before drawing conclusions.
- **Prepare for schema changes:** Parse logs using fields recommended by current Cloud KMS documentation and avoid long-term reliance on fields marked deprecated.
- **Verify read permissions:** Users with `roles/logging.viewer` may not be able to view Data Access logs in `_Default`; grant `roles/logging.privateLogViewer` when a role genuinely requires reading those logs.

- [ ] Identify the crypto keys, workloads, service accounts, and operations to monitor.
- [ ] Enable appropriate Data Access logs (`ADMIN_READ`, `DATA_READ`, and `DATA_WRITE` when needed) for `cloudkms.googleapis.com`.
- [ ] Confirm inherited settings from organization or folder levels and verify log read permissions.
