# BigQuery Architecture and Separation of Storage and Compute

## Learning Objectives

After this lesson, you will be able to:

1. Explain BigQuery's two layers—**storage** and **compute**—and the roles of **Colossus/Capacitor**, **Dremel**, **Jupiter**, and **slots** without confusing them with user-provisioned VM resources.
2. Describe the lifecycle of a query from SQL → planning → reading columnar data → distributed processing → returning results; distinguish between **logical bytes**, **bytes processed**, **slot-ms**, and execution duration.
3. Compare **on-demand pricing** based on data processed with **capacity-based reservations** based on allocated slots over time and the **BigQuery editions**.
4. Create datasets and partitioned/clustered tables, run SQL and dry runs, and read job/storage statistics to optimize performance and cost.
5. Distinguish managed tables from external tables, choose batch/streaming ingestion, and manage regions, IAM, data protection, and operations.
6. Apply the model to Java applications on Cloud Run/GKE, enterprise scenarios, practice questions, and exercises with solutions.

## 1. What Is BigQuery and What Problem Does It Solve?

**BigQuery** is Google Cloud's serverless data platform and **analytical data warehouse**. You submit GoogleSQL queries, load data, call APIs, or create jobs; Google Cloud manages most of the storage and execution infrastructure. In the **CLOUD_PROVIDERS_GCP** module, BigQuery provides the analytics layer for data generated by Cloud Run, GKE, Cloud SQL, Pub/Sub, and Cloud Storage, alongside IAM, reliability monitoring, and cost optimization.

Example retail system:

- **Cloud SQL PostgreSQL** serves individual low-latency payment/order transactions.
- **Pub/Sub** carries events emitted by the Java orders-api.
- **Cloud Storage** stores exported CSV/Parquet files.
- **BigQuery** aggregates billions of events by date, product, region, and sales channel.
- **Looker/BI tools** query reports; data teams run ETL/ELT SQL.

BigQuery **does not replace by default** Cloud SQL or Spanner for small transactional record reads/writes requiring low OLTP latency. BigQuery's focus is reading/aggregating large volumes of data and performing distributed analytical processing.

### 1.1. Guiding Question

An enterprise stores **20 TB of historical data**, but only runs summary reports nightly; during campaigns, dozens of analysts run SQL queries concurrently. If a traditional database tightly couples disk with CPU, increasing storage often forces compute decisions. **BigQuery separates storage and compute**: stored data volume can be large while compute is used flexibly per job or reservation.

## 2. Architecture Diagram: Storage and Compute as Two Independent Layers

~~~mermaid
flowchart TB
    CLIENT["BigQuery Studio / bq CLI / Java SDK / BI"] --> API["BigQuery API + Metadata + IAM"]
    API --> JOB["Query job: parser, optimizer, scheduler"]
    JOB --> CPU["Compute layer: Dremel execution tree<br/>distributed workers + slots + shuffle"]
    CPU <-->|"Jupiter high-bandwidth network"| STORE["Storage layer: Colossus<br/>Capacitor columnar data + metadata"]
    LOAD["Batch load / BigQuery Storage Write API / DML"] --> STORE
    GCS["Cloud Storage external data / BigLake"] -. "read outside managed storage when querying" .-> CPU
    CPU --> RESULT["Query result / cached result / destination table"]
    RESULT --> CLIENT
~~~

| Component | Practical Role | What Does the User Control? |
|---|---|---|
| **Colossus** | Distributed storage system managing BigQuery data, replication/recovery | Datasets, tables, partitions, retention, encryption, location |
| **Capacitor** | Columnar storage format optimized for reading/compressing analytical data | Schema, types, clustering, partitioning; does not manage Capacitor files |
| **Jupiter** | Very high-throughput network connecting compute and storage | Location, data paths, and network costs; does not provision Jupiter networking |
| **Dremel** | Parallel query execution engine with execution tree, scans/aggregations | SQL, query plan, job priority, reservations |
| **Slot** | Virtual compute unit BigQuery uses to run queries and supporting jobs | On-demand: BigQuery allocates automatically; capacity: configure reservation |
| **Metadata, scheduler, shuffle** | Catalog, stage scheduling, and intermediate data exchange | SQL/schema, jobs, reservation assignment, observability |

**The decoupled architecture is a resource management principle, not two services that customers must wire together manually.** BigQuery manages the coordination between Dremel and Colossus. You do not provision a Dremel machine or attach a Colossus disk to a VM.

### 2.1. Comparison with Coupled Storage/Compute Architectures

| Characteristic | Traditional Database/Server | BigQuery |
|---|---|---|
| Increasing data volume | Often requires expanding disks on server/cluster | Managed storage scales independently of purchasing slots |
| Increasing query parallelism | Add nodes/CPUs or reconfigure cluster | BigQuery allocates slots per job or reservation |
| When no SQL jobs are running | May still pay continuously for servers | Managed storage persists/incurs charges; **on-demand query compute** is not charged when no jobs run |
| Multiple concurrent SQL jobs | Compete for CPU/RAM, requiring cluster tuning | Scheduler distributes slots; contention can still occur if capacity is constrained |
| Querying massive datasets | Depends on partitioning, indexing, clustering | Columnar scans/partition pruning and parallel execution |

**Do not misunderstand:** decoupling **does not mean compute is free** or that a query is always fast regardless of the SQL. Storage bytes, slots, network, concurrency, shuffle, data location, and the SQL query itself all affect performance and cost.

## 3. Storage Layer: Colossus and Capacitor

BigQuery presents data hierarchically as **project → dataset → table → rows/columns**, while physical managed storage is optimized **by column**, using **Capacitor**, stored on **Colossus**.

### 3.1. Why Is Columnar Storage Suitable for OLAP?

Suppose a table has 200 columns and 1 billion rows, but the SQL query only uses **order_date, region, amount**. BigQuery can read only the required columns instead of reading all 200 columns and discarding the rest. Values within the same column also typically compress better.

~~~sql
SELECT
  region,
  SUM(amount) AS revenue
FROM `shop-dev-001.commerce_analytics.orders`
WHERE order_date BETWEEN DATE '2026-11-01' AND DATE '2026-11-07'
GROUP BY region;
~~~

**There is no guarantee of "reading only three columns and seven days" if the table design is wrong:** filters only enable **partition pruning** when the table is partitioned appropriately; bytes scanned also depend on types, clustering, storage format, and the query plan. Adding **LIMIT 10** does not automatically reduce bytes scanned for an aggregation that must read the entire dataset.

### 3.2. Storage Is Independent but Still Has Location and Cost

- A **dataset** has a location such as **asia-southeast1** or **US**; tables reside in that dataset. Location must be decided at creation time because it cannot be changed in place.
- Managed data uses BigQuery's replication/durability mechanisms appropriate to the location; **do not assume a regional dataset automatically provides multi-region DR**.
- BigQuery supports **logical storage billing** (uncompressed bytes) and **physical storage billing** (compressed bytes). The model is selected at the **dataset level**; changing the billing model **does not move or reformat the data**.
- Storage has **active/long-term** tiers: data in a table/partition unmodified for **90 days** can transition to the corresponding long-term rate. Operations that modify the affected data can move that portion back to active.
- **Time travel** defaults to 7 days and is configurable from 2–7 days; after that, there is a non-configurable **7-day fail-safe** period. Under physical billing, time-travel/fail-safe bytes can be billed separately.

**Separating storage and compute does not eliminate** retention, encryption, regional planning, and sensitive data management.

### 3.3. Partitioning and Clustering Optimize Read Paths

| Technique | Effect | Example |
|---|---|---|
| **Partition by DATE** | Reads only partitions matching the date filter | orders by order_date |
| **Clustering** | Sorts/groups data blocks by filter columns, reducing block scans | customer_id, region |
| **Column projection** | Reads only columns actually referenced in SQL | SELECT region, amount instead of SELECT * |
| **Materialized view** | Stores/maintains eligible aggregated results for reuse | Daily revenue by day |
| **Query result cache** | Returns identical query results if eligible | Repeated dashboard queries |

**Partition ≠ cluster:** partition pruning can be estimated from partition filters before the job runs; clustering block pruning may only reduce bytes during execution, so dry runs for clustered tables may **overestimate compared to actual bytes scanned**.

## 4. Compute Layer: Dremel and Slots

A **slot** is BigQuery's **virtual compute unit**, not a fixed vCPU or Kubernetes Pod. Each query can be broken into stages and parallel work units:

~~~mermaid
flowchart TB
    Q["SELECT ... GROUP BY region"] --> PLAN["Optimizer: stages / distributed plan"]
    PLAN --> S1["Slots: scan partitions + needed columns"]
    PLAN --> S2["Slots: scan partitions + needed columns"]
    PLAN --> S3["Slots: scan partitions + needed columns"]
    S1 --> SH["Shuffle + partial aggregation"]
    S2 --> SH
    S3 --> SH
    SH --> FIN["Final aggregation / ordering"]
    FIN --> OUT["Result"]
~~~

1. **Parser/optimizer** validates syntax and permissions and generates a plan for reading/transforming/joining/aggregating.
2. The scheduler splits the query into dependent stages; BigQuery allocates appropriate **slots** based on workload and available capacity.
3. **Workers** read columns/partitions from Colossus over the internal network, decompress them, and execute operators.
4. **Shuffle** transfers intermediate data by key for joins/grouping, which can consume significant compute/network if data is large or skewed.
5. Results are returned to the client, stored in **temporary result cache**, or written to a **destination table**.

**Using more slots does not mean execution time decreases linearly.** Bottlenecks can come from **large scans, shuffle, skew, serial stages, slot contention, UDFs, or external source latency**; some stages cannot run completely in parallel.

### 4.1. Slot-ms vs. Wall Time

BigQuery tracks the metric **total_slot_ms** = total slot time consumed during the job. For example, suppose a query runs for **10 seconds** and consumes **50,000 slot-ms**:

\[
\text{Average slots used} \approx \frac{50{,}000\ \text{slot-ms}}{10{,}000\ \text{ms}} = 5.
\]

This is only an **estimated average utilization**, not a guarantee that the query held exactly five slots continuously. A job may use many slots in one stage and few in another. **total_bytes_processed** and **total_slot_ms** measure two different aspects; under on-demand pricing, query charges are generally based on **bytes billed**, not directly on slot-ms.

## 5. Query Lifecycle and BigQuery Job Types

In BigQuery, heavy operations are executed as **jobs**. A job has a **project, location, job ID, type, state, labels, and statistics**:

| Job type | Examples | Processing path |
|---|---|---|
| **QUERY** | SELECT, CREATE TABLE AS SELECT, INSERT, MERGE | Dremel query execution; reads/writes BigQuery storage |
| **LOAD** | Load CSV/Parquet from Cloud Storage | Ingestion into managed storage |
| **COPY** | Copy a table/snapshot under supported conditions | BigQuery managed job |
| **EXTRACT** | Export table/query result to Cloud Storage | Reads managed data and exports data |

**A query job** transitions through states such as **PENDING → RUNNING → DONE**. DONE can still include an error, so you must check **errorResult**, not just state. Job metadata is separate from **table storage**: after a query finishes, the table still exists and incurs storage charges unless deleted or expired.

### 5.1. Execution Timeline

~~~mermaid
sequenceDiagram
    participant C as bq / SDK / BI
    participant B as BigQuery API & scheduler
    participant D as Dremel compute
    participant S as Colossus storage
    C->>B: Submit query job
    B->>B: Verify IAM, location, SQL, optimize
    B->>D: Schedule stages and allocate slots
    D->>S: Read referenced columns/partitions
    S-->>D: Compressed columnar blocks
    D->>D: Scan, filter, shuffle, aggregate
    D-->>B: Result + job statistics
    B-->>C: Rows / result destination / job ID
~~~

If a query gets a **result cache hit**, BigQuery can return cached results and avoid re-running the execution pipeline. Cached query results typically have a lifetime of **about 24 hours** and are not guaranteed for nondeterministic queries, tables with recent streaming writes, or when underlying data has changed. Cached results **do not incur storage charges**, and a valid cache hit **does not incur query compute charges**.

**Cache is not a durable data source:** if downstream pipelines require a persistent table, write to a destination table or materialized view instead of relying on temporary result tables.

### 5.2. Interactive vs. Batch Priority

**INTERACTIVE** queries are prioritized to run promptly according to current capacity and quotas. **BATCH** queries may be queued in a scheduling window to leverage available system capacity; suitable for ETL without immediate latency requirements. **Batch does not mean the query consumes no slots or is always free**; costs still follow the pricing model and job resource usage.

## 6. Resource Hierarchy, Location, and Ownership

~~~text
Google Cloud project: shop-dev-001
├── BigQuery dataset: commerce_analytics (asia-southeast1)
│   ├── Managed table: orders
│   ├── View: daily_revenue
│   └── Other tables / materialized views / routines
├── Query jobs (location asia-southeast1)
└── Optional: Reservations + assignments (same location)
~~~

| Resource | Role | Example |
|---|---|---|
| **Project** | IAM, APIs, billing, where jobs are submitted | shop-dev-001 |
| **Dataset** | Container for tables/views, data location, retention, storage billing model | commerce_analytics |
| **Table** | Schema and managed data stored in BigQuery | orders |
| **View** | Saved SQL logic; generally does not copy underlying data | daily_revenue |
| **Job** | Executes an operation; has location, query plan, job stats | query job ID |
| **Reservation** | Pool of slots/edition in a location to process assigned workloads | etl-reservation |
| **Assignment** | Assigns project/folder/organization or job type to a reservation | analytics jobs → etl-reservation |

### 6.1. Location Applies to Both Data and Compute

- Datasets are created in a **region** (such as asia-southeast1) or eligible **multi-region** (US/EU). A dataset's location **cannot be changed directly**; moving it requires copying/replicating/migrating via supported methods.
- Jobs must run in a **compatible location** with the queried datasets; standard queries cannot directly join two datasets in different locations.
- When using reservations, **slot capacity is bound to the reservation's location**. A job running outside the reservation's location may be billed as **on-demand** if no matching assignment exists.
- Use **bq --location** or job configuration to specify location explicitly, especially for jobs that do not reference a dataset from which location can be inferred.
- BigQuery offers cross-region dataset replication/DR features under specific conditions; **this does not mean every dataset has independent multi-region backups by default**.

**Example:** if a table is in asia-southeast1 but the Java SDK submits a query job with location **US**, it may fail with **Not found: Dataset ... was not found in location US** even though the dataset actually exists. This is a **location** error, not necessarily an IAM error.

## 7. Decoupling Storage and Compute Creates Two Separate Billing Models

### 7.1. Storage Pricing

In **managed BigQuery storage**, costs are tied to stored data and depend on **logical/physical billing**, active/long-term bytes, time travel/fail-safe, snapshots/clones, and configured retention policies. Data persists even when no SQL is running.

For example, an enterprise has **20 TiB of stored data** in a month, but runs only one report: **20 TiB stored does not automatically mean 20 TiB query processed or 20 TiB billed for compute**. Conversely, if a 1 TiB table is scanned 30 times, total query processing can exceed the stored volume many times over.

### 7.2. Compute Pricing: On-Demand vs. Capacity

| Criterion | **On-demand** | **Capacity-based / reservations** |
|---|---|---|
| Billing basis | Per **TiB processed/billed** by each query | Per **allocated slot capacity over time**, tied to edition |
| Slots | BigQuery allocates automatically based on demand and system limits | Baseline + autoscaled slots up to max reservation |
| Initial setup | No need to create a reservation | Create reservation and assignments by workload/location |
| When no queries run | No **query processing** charges if no queries are executed | Baseline may still be billed while idle; autoscale follows scaling rules |
| Best suited for | Exploratory SQL, small/variable workloads, minimal setup | Steady workloads or workloads needing capacity/SLO management and compute predictability |
| Cost controls | Dry run, maximum bytes billed, quotas, optimizing bytes scanned | Baseline, max autoscale, commitments, job/slot metrics |

**Every query uses slots**, including on-demand queries; the main difference is **how you pay and control capacity**, not two different SQL execution engines.

**BigQuery editions** for reservations include **Standard, Enterprise, and Enterprise Plus** with different features and pricing. You can use **on-demand for one workload** and **capacity reservations for another** within the same system; you do not have to move tables between them. A **reservation assignment** must match the project/folder/organization and location for jobs to use that slot pool.

### 7.3. Reservations, Baseline, and Autoscaling

~~~mermaid
flowchart LR
  JOBS["ETL / BI jobs<br/>assigned in matching location"] --> RES["Reservation: Enterprise"]
  BASE["Baseline slots<br/>billed once provisioned"] --> RES
  AS["Autoscaled slots<br/>scale up to max and billed by capacity"] --> RES
  RES --> DRE["Dremel slots running queries"]
  DATA["BigQuery managed tables"] -. "no data migration when changing model" .-> DRE
~~~

With autoscaling, BigQuery can scale slots based on demand up to the **max reservation size**; autoscaled slots are rounded in increments and subject to quota/capacity. **Baseline slots are always billed under the capacity model**, and autoscaled capacity has scale-down/minimum billing rules depending on options (such as fluid scaling). Do not assume **actual slots used by a single query equals billed slots**.

**Commitments** can reduce costs for steady baseline usage, but they are long-term financial commitments. Measure **job slot-ms, peak concurrency, pending time, and reservation utilization** before purchasing commitments or raising max slots.

### 7.4. Illustrative Calculation Without Fixed Prices

Suppose:

- A **1 TiB** table is fully scanned **40 times** in a month.
- An optimized dashboard reads only **10% of partitions**, reducing scans to roughly **0.1 TiB/query** when selecting the right columns and filters.
- Query frequency remains 40 queries.

| Query Pattern | Illustrative Total Bytes Processed |
|---|---:|
| Full scan 1 TiB × 40 | **40 TiB** |
| Optimized scan 0.1 TiB × 40 | **4 TiB** |

Under on-demand pricing, partition/column optimization can significantly reduce query costs. Under reservations, **reducing scans also shortens slot time and frees capacity**, though the baseline bill may **not drop immediately** if you keep the same purchased baseline slots.

**Do not treat 0.1 TiB as guaranteed** just by adding `WHERE date`: verify actual partitions, columns selected, job statistics, and bytes billed. Cloud Billing, rather than hypothetical multiplication, is the authoritative source for charges.

## 8. Ingestion and Reading Data: Managed Storage Does Not Cover Every Data Source

| Method | Data Flow | Storage/Compute Role |
|---|---|---|
| **Batch load job** | Cloud Storage CSV/JSON/Parquet/Avro → BigQuery table | Converts into managed storage; suited for periodic loads |
| **Storage Write API/streaming** | Applications/connectors write in near real time | Has dedicated quotas/pricing/commit modes and visibility semantics |
| **SQL DML/CTAS/MERGE** | Query → modifies BigQuery managed table | Uses query execution and writes to managed storage |
| **External table / BigLake** | Queries data directly in Cloud Storage/open table formats | Data remains in external source; does not become Capacitor managed storage |
| **Materialized view** | Stores and refreshes supported aggregated results | Incurs storage for results and compute for refreshes |
| **Export job** | BigQuery table → Cloud Storage | Extracts data to external systems/object storage |

**External tables are not the same as managed BigQuery tables:** data in Cloud Storage has its own lifecycle, storage billing, and permissions; query speed, caching, statistics, and feature limits can differ. If the same dataset is queried repeatedly for demanding OLAP workloads, evaluate **loading it into managed tables** to leverage columnar optimizations.

### 8.1. Do Not Confuse the BigQuery Storage API

- **BigQuery Storage Read API** enables high-throughput data reads to clients/processing frameworks over streams; it is **different** from running a SQL query without a separate server.
- **BigQuery Storage Write API** supports batch/streaming writes via streams/offsets; review pricing/quotas and delivery guarantees.
- **Cloud Storage** is an object storage service separate from BigQuery managed storage; a bucket containing Parquet files does not automatically become a BigQuery table until loaded or defined as an external table.

### 8.2. BigQuery Is OLAP, Not the Default Choice for OLTP

Sending every web request to BigQuery to look up a single small row introduces inappropriate latency/job overhead and cost. For a **Spring Boot orders-api**, write transactions to **Cloud SQL/Spanner**; then forward events via Pub/Sub/Dataflow/BigQuery according to data freshness SLAs. BigQuery supports ACID/DML/transactions, but **do not assume its latency, indexing, and locking model matches PostgreSQL/MySQL OLTP**.

## 9. Lab A — Creating a Dataset and a Partitioned Managed Table

**Prerequisites:** project **shop-dev-001** is an illustrative name; the BigQuery API is enabled, billing/quotas are active, and the operator has permissions to create datasets, tables, and query jobs. Commands may create resources and incur charges; use only an approved lab project. Do not create new projects/datasets if resources with the same names already exist.

### 9.1. Verify Project and Location

~~~bash
gcloud config get-value project
gcloud auth list
bq version
bq ls --project_id=shop-dev-001
~~~

**Example location:** **asia-southeast1** (Singapore), not a guarantee that "data resides in Vietnam." Choose a region/multi-region actually supported by BigQuery that meets residency and data source/consumer locality requirements before creation.

### 9.2. Create a Dataset

~~~bash
# Create the dataset only after verifying IAM, billing, and data placement.
bq --location=asia-southeast1 mk \
  --dataset \
  --description="Lab commerce analytics; non-production data" \
  --label=env:lab \
  shop-dev-001:commerce_analytics

bq show --format=prettyjson shop-dev-001:commerce_analytics
~~~

Once created, **dataset location cannot be changed in place**. The `bq` command to create a dataset does not automatically create a slot reservation or VM. A **dataset** is a logical container that can hold multiple tables in the same location.

### 9.3. Sample DDL in BigQuery Studio (GoogleSQL)

~~~sql
CREATE TABLE IF NOT EXISTS `shop-dev-001.commerce_analytics.orders` (
  order_id STRING NOT NULL,
  customer_id STRING NOT NULL,
  order_date DATE NOT NULL,
  amount NUMERIC NOT NULL,
  region STRING
)
PARTITION BY order_date
CLUSTER BY customer_id
OPTIONS (
  require_partition_filter = TRUE,
  description = 'Orders data for storage/compute lab'
);
~~~

**Design explanation:**

- **PARTITION BY order_date** creates daily partitions, enabling time-based read filtering.
- **CLUSTER BY customer_id** helps reduce block scans when filtering by customer; it **does not** create a B-tree index like PostgreSQL.
- **require_partition_filter = TRUE** forces queries reading the table to include a filter capable of pruning partitions, preventing accidental full scans.
- BigQuery manages columnar data in managed storage; no disk needs to be created or attached.

### 9.4. Insert Sample Rows

~~~sql
INSERT INTO `shop-dev-001.commerce_analytics.orders`
  (order_id, customer_id, order_date, amount, region)
VALUES
  ('ord-001', 'cust-1', DATE '2026-11-17', 120000, 'north'),
  ('ord-002', 'cust-2', DATE '2026-11-17', 350000, 'south'),
  ('ord-003', 'cust-1', DATE '2026-11-18',  80000, 'north'),
  ('ord-004', 'cust-3', DATE '2026-11-18', 200000, 'south'),
  ('ord-005', 'cust-2', DATE '2026-11-19', 150000, 'north');
~~~

**Do not run INSERT repeatedly** if you want accurate revenue totals: BigQuery does not automatically enforce unique constraints like Cloud SQL on standard tables. Use an empty lab table/check row counts and manage ingestion idempotency; business keys must be handled in ETL.

### 9.5. Query Revenue by Region

~~~sql
SELECT region, COUNT(*) AS order_count, SUM(amount) AS revenue
FROM `shop-dev-001.commerce_analytics.orders`
WHERE order_date BETWEEN DATE '2026-11-17' AND DATE '2026-11-19'
GROUP BY region
ORDER BY revenue DESC;
~~~

**Expected sample result:** north = **3 orders / 350,000**, south = **2 orders / 550,000** (currency units are illustrative). Total **900,000**, five rows. On a table with only a few rows, bytes billed has a **minimum threshold per the pricing model**, so do not use a small lab to draw conclusions about exact USD savings from partition pruning.

## 10. Lab B — Dry Run, Maximum Bytes Billed, and Query Plan Inspection

### 10.1. Dry Run (Without Executing SELECT)

From **Cloud Shell/bash**:

~~~bash
bq --location=asia-southeast1 query \
  --use_legacy_sql=false \
  --dry_run \
  'SELECT region, SUM(amount) AS revenue
   FROM `shop-dev-001.commerce_analytics.orders`
   WHERE order_date BETWEEN DATE(2026, 11, 17) AND DATE(2026, 11, 19)
   GROUP BY region'
~~~

**Dry run** validates SQL and estimates **bytes processed** before execution without producing query results. It **does not guarantee exact latency, slot-ms, or the final bill**; clustered tables, materialized views, metadata changes, and caching can cause actual execution to differ from estimates.

### 10.2. Run a Query with a Cost Guardrail

~~~bash
bq --location=asia-southeast1 query \
  --use_legacy_sql=false \
  --maximum_bytes_billed=104857600 \
  'SELECT region, SUM(amount) AS revenue
   FROM `shop-dev-001.commerce_analytics.orders`
   WHERE order_date BETWEEN DATE(2026, 11, 17) AND DATE(2026, 11, 19)
   GROUP BY region
   ORDER BY revenue DESC'
~~~

**maximum_bytes_billed** here is **100 MiB** (an illustrative value). Queries exceeding the allowed byte estimate **fail before execution and incur no query charges**. For real large datasets, choose a threshold based on actual budget and table size instead of copying this value.

### 10.3. Compare Two Filter Ranges

On a real table with substantial data, compare **dry run** and job statistics for:

~~~sql
-- Query 1: three-day range, reading 2 relevant columns.
SELECT customer_id, SUM(amount) AS revenue
FROM `shop-dev-001.commerce_analytics.orders`
WHERE order_date BETWEEN DATE '2026-11-17' AND DATE '2026-11-19'
GROUP BY customer_id;

-- Query 2: one-month range, same two columns and expression.
SELECT customer_id, SUM(amount) AS revenue
FROM `shop-dev-001.commerce_analytics.orders`
WHERE order_date BETWEEN DATE '2026-11-01' AND DATE '2026-11-30'
GROUP BY customer_id;
~~~

**Expectation:** Query 1 prunes more partitions than Query 2 when data is distributed across days. However, a lab table with only three days of data may show **no noticeable difference**. An empty or heavily compressed table behaves differently from a production table; never fabricate benchmark numbers.

### 10.4. View Query Execution Details

In **BigQuery Studio → Job information / Execution graph**:

- **Bytes processed / billed:** estimates storage data scanned and on-demand compute cost.
- **Slot time:** total compute consumed; helps evaluate workloads for reservations.
- **Stages**: scan, shuffle, join, aggregation; inspect **shuffle bytes, spill, skew, wait time** when available.
- **Cache hit:** if TRUE and the query is eligible, BigQuery returned cached results; do not use cached runs to benchmark compute.

To benchmark two SQL queries, record **dataset size, filters, slot assignment, job location, and caching behavior**, and measure multiple times under comparable conditions. **Changing query text or data can invalidate the cache**; queries using `CURRENT_TIMESTAMP()` may not be cached.

## 11. Lab C — Java BigQuery Client with ADC and Cost Limits

A Java application can submit a **query job** and read results using **com.google.cloud:google-cloud-bigquery** with Application Default Credentials. The sample below queries a dataset in **asia-southeast1**; it does not require downloading a long-lived JSON key.

~~~java
import com.google.cloud.bigquery.BigQuery;
import com.google.cloud.bigquery.BigQueryOptions;
import com.google.cloud.bigquery.FieldValueList;
import com.google.cloud.bigquery.JobId;
import com.google.cloud.bigquery.QueryJobConfiguration;
import com.google.cloud.bigquery.QueryParameterValue;
import com.google.cloud.bigquery.TableResult;
import java.util.UUID;

public final class BigQueryRevenueReport {
    private BigQueryRevenueReport() {}

    public static void main(String[] args) throws Exception {
        BigQuery client = BigQueryOptions.newBuilder()
            .setProjectId("shop-dev-001")
            .build()
            .getService(); // Local / Cloud Run / GKE ADC

        String sql = "SELECT region, SUM(amount) AS revenue "
            + "FROM `shop-dev-001.commerce_analytics.orders` "
            + "WHERE order_date BETWEEN @from_date AND @to_date "
            + "GROUP BY region ORDER BY revenue DESC";

        QueryJobConfiguration config = QueryJobConfiguration.newBuilder(sql)
            .setUseLegacySql(false)
            .addNamedParameter("from_date",
                QueryParameterValue.date("2026-11-17"))
            .addNamedParameter("to_date",
                QueryParameterValue.date("2026-11-19"))
            .setMaximumBytesBilled(104857600L)
            .build();

        JobId jobId = JobId.newBuilder()
            .setProject("shop-dev-001")
            .setLocation("asia-southeast1")
            .setJob("revenue_" + UUID.randomUUID().toString().replace("-", "_"))
            .build();

        TableResult results = client.query(config, jobId);
        for (FieldValueList row : results.iterateAll()) {
            System.out.println(row.get("region").getStringValue()
                + ": " + row.get("revenue").getNumericValue());
        }
    }
}
~~~

**Prerequisites to run:** Java 21, a compatible version of the BigQuery client library, ADC with **bigquery.jobs.create** on the job project and read access to the table, and the dataset/table already created. This example runs a short query; production services need **deadlines, job retry/cancellation, pagination/large result handling, and monitoring**. Check library compatibility when upgrading versions.

### 11.1. Why Does Java Specify the JobId Location?

With the Java client, when the dataset resides outside **US/EU**, using the query overload with an explicit **JobId location** prevents submitting the query to the wrong location. **Dataset location and job location must be compatible**; a Cloud Run service's region does not automatically determine the BigQuery query location.

**Do not create a new BigQuery client/connection per HTTP request.** For large reports, run batch/asynchronous jobs, write to a destination table, return job status, and handle quotas/throttling instead of blocking an HTTP request for minutes.

## 12. IAM, Encryption, Sensitive Data, and Responsibility Boundaries

Separating storage and compute creates two permission scopes that should not be merged: **who can create query jobs** and **who can read/modify data**.

| Principal | Required Permissions | Not Automatically Granted |
|---|---|---|
| **Analyst** | Create jobs in the query project; read authorized datasets/tables | Delete datasets, grant broad IAM roles |
| **Java Cloud Run runtime SA** | Create query jobs and read tables needed by the service | BigQuery Admin or Owner |
| **Data engineer / pipeline** | Create/update tables/partitions and load data | Read access to sensitive data outside scope |
| **Capacity administrator** | Manage reservations, assignments, commitments | Access to table data unless explicitly granted |
| **Security/metadata viewer** | View metadata and audit logs per duty | Read all table rows |

### 12.1. Least-Privilege IAM Examples

- **roles/bigquery.jobUser** on the execution project grants **bigquery.jobs.create**.
- **roles/bigquery.dataViewer** on the dataset containing tables to SELECT.
- **roles/bigquery.dataEditor** only for principals that write/manage data; avoid granting it to read-only analysts.
- **roles/bigquery.resourceAdmin** (or specific permissions) for slot/reservation administrators, **not** for regular Cloud Run runtimes.

If the job execution project differs from the data storage project, grant **jobUser on the query project** and **dataViewer on the source dataset**. Query billing typically applies to the **project running the job** (or the associated capacity reservation/billing arrangement), not by default to the project owning the table.

**Server identity:** Cloud Run uses a runtime service account; GKE uses Workload Identity Federation for GKE. **Never embed JSON private keys** in Docker images, Git, or shared notebooks. ADC does not grant data permissions automatically; it only identifies the principal for BigQuery IAM checks.

### 12.2. Security Does Not Stop at the Dataset

| Layer | Mechanism | Key Consideration |
|---|---|---|
| Dataset/table data | IAM/resource policies | Different tables/projects may have different owners |
| Sensitive columns | Policy tags, column-level security/data masking | Review column read permissions regularly |
| Data rows | Row-level access policies | Do not rely on dataset Viewer instead of row filtering |
| Storage encryption | Google-managed encryption; CMEK when required | CMEK key availability affects data access |
| Data egress | VPC Service Controls, locations, export permissions | IAM alone does not control every egress path |
| Audit | Cloud Audit Logs and job history | Watch Data Access logs/retention/PII in query text |

**Location is not automatically "data security."** An analyst with query permissions may export results elsewhere if policies allow it. Combine IAM, org policies, dataset locations, CMEK, policy tags, and export controls according to data classification.

### 12.3. Query Costs Can Occur Even Across Projects

If an analyst in **analytics-project** queries a table from **data-project**, billing, IAM, and reservation assignment are independent decisions. Do not grant users **Owner** just to bypass jobUser or dataViewer errors. Test negative IAM cases in staging to confirm principals cannot read financial data outside their role.

## 13. Observing Storage and Compute via BigQuery INFORMATION_SCHEMA

BigQuery provides metadata views to inspect **jobs**, **slots**, and **storage**. These views have their own permissions and location scopes; metadata queries are not guaranteed to be free in all cases.

### 13.1. Query Jobs by Region

In BigQuery Studio, select **query location asia-southeast1**:

~~~sql
SELECT
  job_id,
  creation_time,
  state,
  total_bytes_processed,
  total_bytes_billed,
  total_slot_ms,
  cache_hit,
  reservation_id
FROM `shop-dev-001.region-asia-southeast1.INFORMATION_SCHEMA.JOBS_BY_PROJECT`
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 DAY)
  AND job_type = 'QUERY'
  AND (statement_type IS NULL OR statement_type != 'SCRIPT')
ORDER BY creation_time DESC
LIMIT 50;
~~~

**Interpreting the fields accurately:**

- **total_bytes_processed**: amount of data processed, not the stored table size.
- **total_bytes_billed**: amount of data billed under on-demand logic when applicable; can be **0** due to caching or pricing model; do not use this single field to reconstruct a full reservations bill.
- **total_slot_ms**: total compute consumed by the job; **not the baseline slots** being billed.
- **cache_hit**: indicates whether the result came from the query cache.
- **reservation_id**: identifies the assigned slot reservation when an assignment applies.

For jobs still PENDING/RUNNING, some fields may be NULL or incomplete. **INFORMATION_SCHEMA.JOBS_BY_PROJECT** requires the matching region qualifier and query location; visible rows depend on the principal's job-viewing permissions.

### 13.2. Managed Table Storage Statistics

~~~sql
SELECT
  table_schema,
  table_name,
  total_rows,
  active_logical_bytes,
  long_term_logical_bytes,
  active_physical_bytes,
  long_term_physical_bytes,
  time_travel_physical_bytes
FROM `shop-dev-001.region-asia-southeast1.INFORMATION_SCHEMA.TABLE_STORAGE_BY_PROJECT`
WHERE table_schema = 'commerce_analytics'
ORDER BY active_logical_bytes DESC;
~~~

The **logical** and **physical** fields allow comparing storage pricing models—do not add them together as a bill. **TABLE_STORAGE views have update latency**; byte/partition counts may differ from a point-in-time billing snapshot. Table snapshots/clones may report full logical/physical bytes informationally while billing charges deltas under separate rules.

### 13.3. Operational Metrics to Monitor

| Metric | Used to Detect |
|---|---|
| **Query latency p95/p99**, pending time | Slow BI, slot contention, queueing |
| **Bytes processed/billed** | SELECT * or filters not pruning partitions |
| **Total slot-ms, slot utilization** | Opportunities to tune SQL or adjust capacity |
| **Reservation baseline/autoscale slots** | Billed slot capacity and scaling behavior |
| **Shuffle bytes/spill/skew** | Large joins/groups, data skew |
| **Table logical/physical bytes** | Storage growth, compression, long-term savings |
| **Failed jobs/permission errors** | SQL errors, quotas, IAM, location mismatches |
| **Billing service/SKU** | Variance between job estimates and actual costs |

For reservations, use **BigQuery Capacity Management / Slot Estimator** and reservation metadata/Monitoring to compare **allocated vs. utilized slots**. **Do not treat total job slot-ms as the exact autoscaling bill**, because autoscaling is billed based on allocated capacity and specific billing rules.

## 14. Availability, Data Retention, and Lifecycle Management

**Serverless BigQuery does not mean immunity from outages or human error.** Distinguish between:

- **Managed storage durability/replication**: Google manages the infrastructure and protects against many hardware failures.
- **Compute availability/latency**: jobs can still queue, fail, or slow down due to quotas, regional issues, slot limits, or inefficient SQL.
- **Time travel/fail-safe**: supports recovering recent modifications/deletions within eligible windows; **not long-term immutable archival**.
- **Table snapshots/copies/backups/data exports**: support retention/DR according to architecture and supported features.
- **Cross-region dataset replication/managed disaster recovery**: conditional features requiring explicit configuration, cost, and failover procedures; not enabled automatically for every project.

### 14.1. Runbook for Accidental DELETE

1. Stop the job/pipeline deleting the wrong data; preserve the job ID, UTC timestamp, and SQL.
2. Identify the dataset/table, **time travel window**, recovery permissions, and any subsequent changes.
3. Restore into a **new table/dataset** using supported time travel/restore mechanisms—do not overwrite production immediately.
4. Verify row counts, checksums, business invariants, and schema.
5. Cut over downstream readers according to plan, preserve forensic evidence, and report RPO/RTO.

If the incident falls outside the **time travel window**, a separate backup/export/DR plan is required; the 7-day fail-safe **is not an instant self-service restore interface** and involves conditional support intervention.

### 14.2. Strategy to Prevent Expired Data Accumulation

Configure **partition expiration/table expiration/lifecycle** per legal and business requirements. Expired data may still remain in time travel/fail-safe windows depending on storage mode and billing. **Do not switch storage billing models** as a way to delete data; changing the billing model neither moves data nor resets retention.

## 15. Troubleshooting: Correctly Identifying Storage vs. Compute Issues

| Symptom | First Likely Cause | Check |
|---|---|---|
| **Dataset not found in location US** | Job in wrong location, not a missing table | Dataset location and **bq --location** / JobId |
| **Access Denied: Table** | Principal lacks read permission on source | Dataset/table IAM, row/column policies |
| **Access Denied: Project / jobs.create** | Execution project lacks jobUser role | Job project and service identity |
| **Resources exceeded during query execution** | Large shuffle/aggregation, skew, memory limits | Execution graph, partitioning/clustering design |
| Very slow queries, long pending time | Insufficient slots, queueing, or quotas | Slot utilization, reservation assignment, job priority |
| Query scans too many bytes | SELECT *, missing partition filter, or non-pruning WHERE | Query validator/dry run, schema, partitions |
| **maximum bytes billed exceeded** | Estimated scan exceeds guardrail | Dry run and optimize; only raise limit after review |
| Query returns stale results for repeated SQL | Cached result, or ETL has not updated | cache_hit, last modified, freshness SLO |
| Repeated queries still incur charges despite unchanged table | Query ineligible for cache or text changed | Query cache rules, nondeterministic functions |
| Storage bill grows while few jobs run | Increased data/retention/physical time travel | TABLE_STORAGE views, dataset billing model |
| Reservation baseline incurs cost when idle | Allocated capacity is still billed | Baseline/autoscale pricing and assignment |
| Query unexpectedly billed on-demand | Job location/assignment differs from reservation | Project/folder assignment, reservation location |
| Java Cloud Run gets 403 while console user succeeds | Runtime ADC differs from user principal | Cloud Run service account, IAM, job project |
| Join across US and asia-southeast1 datasets fails | BigQuery requires compatible data locations | Copy/replicate/migrate first; do not join directly |
| Recently streamed data missing in query | Ingestion/commit semantics and pipeline lag | Storage Write API stream mode, job state, source telemetry |
| Dashboard slow only for one customer | Filter misses partition pruning or data skew | Query plan, cluster keys, job stats |

### 15.1. Layered Troubleshooting Flow

~~~mermaid
flowchart TD
    ISSUE["BigQuery query failed or slow"] --> CODE{"Error code / state?"}
    CODE -->|"403"| IAM["IAM: jobUser + dataViewer + runtime SA"]
    CODE -->|"Not found in location"| LOC["Compare dataset location, job location, reservation"]
    CODE -->|"Bytes billed exceeded"| BYTES["Dry run, partition/column pruning"]
    CODE -->|"Slow / resources exceeded"| PLAN["Execution graph, skew/shuffle/slots"]
    CODE -->|"Wrong results"| DATA["Ingestion freshness, SQL semantics, cache"]
    IAM --> VERIFY["Retest + record job ID/metrics"]
    LOC --> VERIFY
    BYTES --> VERIFY
    PLAN --> VERIFY
    DATA --> VERIFY
~~~

**Do not try to fix everything by granting BigQuery Admin, adding slot reservations, or raising maximum bytes billed.** Those three shortcuts can escalate privileges or costs without resolving wrong locations, missing filters, or data skew.

## 16. Case Study: 20 TB of Retail Data and Two Workload Profiles

Enterprise **Binh Minh** has 20 TB of historical data, a BI team using Looker, and a Java orders-api generating 2 million events/day. There are three workload groups:

| Workload | Requirements | Initial Decision |
|---|---|---|
| **OLTP orders-api** | Fast per-order writes, transactional guarantees | Cloud SQL/Spanner, **not** BigQuery as primary OLTP DB |
| **Nightly ETL** | Load and aggregate by order_date partition | Pub/Sub/Dataflow or batch GCS → BigQuery managed tables |
| **BI dashboards** | Many queries during business hours | Query partitioned/clustered tables; consider reservations for steady load |

### 16.1. Why Not Size Compute Based on 20 TB of Storage?

BigQuery storage can hold 20 TB even when ETL runs once a day. As BI workload grows, compute scales via slots/on-demand or reservations **without copying 20 TB to a larger server cluster**.

In a data residency environment, datasets and reservations are placed in the required location; Cloud Run Java services and GCS buckets are colocated nearby to avoid unexpected latency/egress. **Changing the pricing model does not change database schemas or data location**, though IAM/assignments and reporting tools must be verified.

### 16.2. Release and Monitoring Workflow

~~~mermaid
flowchart TD
    SOURCE["Cloud SQL + Pub/Sub + Cloud Storage"] --> INGEST["Load / streaming / Dataflow"]
    INGEST --> TABLE["BigQuery managed orders table<br/>partition by date"]
    TABLE --> ETL["Scheduled queries / ETL"]
    TABLE --> BI["Looker dashboard / BI"]
    ETL --> OUT["Daily revenue table"]
    BI --> WATCH["Job metrics + Billing + SLO"]
    OUT --> WATCH
    WATCH --> TUNE{"Scan/slot/latency exceeds target?"}
    TUNE -->|Yes| FIX["Fix filters/partitions/clustering/data layout<br/>or reservation sizing"]
    TUNE -->|No| OK["Continue monitoring"]
~~~

### 16.3. Comparing Two Cost Scenarios

**Scenario A – on-demand:** variable BI load and analysts run relatively few queries. Prioritize **dry runs, maximum bytes billed, quota limits**, and reducing bytes scanned.

**Scenario B – reservation:** continuous BI usage, high query concurrency, predictable peaks. Measure **total_slot_ms, pending time, p95** and evaluate **baseline + autoscaling**; set max slots, SLOs, and financial budgets. Shift workloads onto reservations via assignments without migrating tables.

**Telemetry-driven decisions:** no fixed TB storage threshold automatically mandates reservations. The payment model should be chosen based on **query volume, scan size, concurrency, performance needs, and compute utilization over time**.

### 16.4. Acceptance Criteria Across Storage and Compute

| Test | Expected Outcome |
|---|---|
| Create dataset in asia-southeast1 | Location is accurate and immutable in place |
| Load data into partitioned table | Data lands in expected partitions |
| SQL reading three days | Appropriate pruning; bytes processed drops on a sufficiently large dataset |
| Java query with JobId location | Executes in the correct region when IAM is valid |
| Switch on-demand → reservation | Managed tables do not need to be recreated |
| Run cached query | cache_hit is verified; never assume cache is always available |
| Separate analyst from write permissions | User can read authorized tables but cannot delete datasets |
| Baseline slots with no queries | Capacity charges may still accrue |
| Restore accidentally deleted table | Succeeds within valid retention window when prepared |
| Billing reports | Storage bytes and compute SKUs are clearly separated |

## 17. Exercises and Suggested Answers

### Exercise A — Distinguishing Storage and Compute

A company stores 5 TB of logs in BigQuery but runs zero queries for seven days.

**Question:** Does BigQuery still have to keep "five Dremel nodes" running corresponding to 5 TB?

**Answer:** **No.** Managed storage is independent of provisioning compute proportionally to stored bytes. The data still incurs **storage charges**; on-demand query processing consumes nothing when no queries run. If **baseline slots** were purchased, capacity charges may still apply.

### Exercise B — Calculating Slot Utilization

A query runs for 12 seconds with total_slot_ms = 96,000.

**Answer:** Average slots used ≈ 96,000 / 12,000 = **8 slots**. This is neither a fixed number of slots held for all 12 seconds nor a count of physical BigQuery nodes.

### Exercise C — Why Does SELECT * Cost Money?

A 1 TB table has 100 columns. A dashboard only needs date, region, and revenue but uses SELECT *.

**Answer:** BigQuery is columnar; **select only the three required columns** and add a filter on the partition date to reduce bytes scanned. **LIMIT 10** does not guarantee fewer bytes processed for `SELECT *`.

### Exercise D — Region Mismatch

The dataset is in **asia-southeast1**, but the Java query job is created with location **US**.

**Answer:** Set **JobId location to asia-southeast1** and ensure dataset/tables are in a compatible location. Do not grant IAM Admin to fix a region error.

### Exercise E — Pricing Model

A table stores 2 TiB; a query scans 0.25 TiB and runs 100 times without cache hits.

**Answer:** Total query data processed is **25 TiB** under the assumption, **not 2 TiB**. Storage remains 2 TiB under the applicable billing model; on-demand query fees depend on bytes billed, minimum thresholds, and location pricing—not simply stored volume.

### Exercise F — Are Reservations Free When Idle?

A team creates a reservation with 300 baseline slots, but BI runs only one hour per day.

**Answer:** **Baseline capacity** is billed even when no queries run. Consider lowering the baseline, using appropriate autoscaling, or reverting to on-demand based on workload patterns and pricing.

### Exercise G — Reading Cached Results

A repeated query shows total_bytes_billed = 0 and cache_hit = TRUE.

**Answer:** The query likely used the **query result cache**, avoiding a fresh scan/compute execution. Do not use cache-hit metrics to benchmark SQL performance under a full scan; caching also depends on data mutations and eligibility rules.

### Exercise H — IAM for Java

A Cloud Run service account has **roles/bigquery.dataViewer** on the dataset, but calling the jobs API fails with **bigquery.jobs.create permission denied**.

**Answer:** It lacks permission to **create jobs** in the execution project, such as **roles/bigquery.jobUser**. DataViewer only grants data read access and does not grant `jobs.create`. BigQuery Admin is not needed.

### Exercise I — Managed vs. External Storage

A Cloud Storage bucket holds 20 TB of Parquet files; the team defines a BigLake external table and assumes the bytes moved into Colossus and the bucket is no longer billed.

**Answer:** Incorrect. **External tables read data from the external source**; the bucket still retains and bills for storage and enforces its own access permissions. To use managed BigQuery storage, **load/copy the data** into an appropriate BigQuery table and evaluate data transfer costs.

### Exercise J — Data Recovery

A table was deleted 3 days ago. The dataset has the default 7-day time travel window.

**Answer:** You can use **time travel/table restore** as eligible to recover into a new table, validate integrity, and switch downstream consumers. Do not treat **fail-safe** as an instant queryable endpoint or an independent off-project backup.

### Exercise K — Choosing What to Optimize First

A query scans 8 TB per run and has high p95 latency; the team proposes immediately buying 1,000 more slots.

**Answer:** First inspect the **query plan, partition/cluster pruning, SELECT *, and shuffle/skew**. Optimizing SQL and data layout can reduce both bytes scanned and slot time. Only adjust reservations after measuring utilization, queueing, and SLOs.

## 18. Summary and References

**Six key takeaways:**

1. **Colossus/Capacitor** manage columnar storage; **Dremel/slots** execute queries; the **Jupiter** network connects both layers with high bandwidth.
2. **Storage and compute scale independently**, yet remain governed by **location, IAM, quotas, data layout, and billing**.
3. **On-demand** typically bills per **bytes billed** by queries; **capacity reservations** bill per **allocated slot capacity over time**, tied to BigQuery editions.
4. **Partition pruning, column projection, clustering, query plans, and caching** determine bytes processed and performance; **LIMIT** is not a reliable way to avoid full scans.
5. **Managed BigQuery storage differs from Cloud Storage/external tables**; ingestion, streaming, caching, backups, and BI each have distinct semantics.
6. **Dry runs, maximum bytes billed, INFORMATION_SCHEMA, least-privilege IAM, and Billing** form the foundation for safe, cost-effective operations for Java and cloud analytics.
