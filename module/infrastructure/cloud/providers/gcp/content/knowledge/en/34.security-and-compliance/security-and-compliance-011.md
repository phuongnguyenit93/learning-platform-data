# Collecting Audit Evidence and Retaining Logs

A Google Cloud system may run smoothly for months yet still fail to satisfy an audit if the organization cannot prove who modified a resource, when the action occurred, which services were affected, and how evidence was protected. Audit evidence collection must therefore be designed directly into the operational architecture, from enabling the right audit log types to routing, access control, retention, and retrieval during investigations.

In Google Cloud, Cloud Audit Logs record administrative activity and data access across supported services. Cloud Logging ingests, queries, routes, and retains log entries. Combining these two components with IAM, Log Router, log buckets, BigQuery, Cloud Storage, and evidence management workflows lets an organization build an auditable chain of controls.

This lesson focuses on Google Cloud security and compliance scope. Upon completion, you will be able to:

- Distinguish Cloud Audit Logs types and identify which ones to enable for each service.
- Configure Data Access audit logs and verify recorded activity.
- Centralize log collection at the project, folder, or organization level.
- Design log sinks, log buckets, and storage destinations aligned with retention requirements.
- Assign separate permissions for log viewers, logging administrators, and evidence custodians.
- Query, export, and preserve evidence for audits or incident investigations.

## 1. Why Is Audit Evidence Needed?

Audit evidence is verifiable data confirming that an activity occurred, a control operated, or an operational decision was approved. In cloud environments, evidence typically comes from audit logs, IAM configurations, change history, security scan results, and incident handling records.

For example, when a firewall rule on a production VM is modified, the security team must be able to answer:

- Which user or service account submitted the change request?
- When did the operation happen and via which service?
- Which resource was affected?
- Did the request succeed or get denied?
- Which IAM policy granted the access permission?
- Were the logs retained for the required period and retrievable intact?

Relying solely on employee notes or screenshots makes it hard to verify data origin and completeness. Audit logs supply events generated by Google Cloud services, while evidence management procedures add collection scope, access controls, retention periods, and custody records.

A sound workflow must guarantee four properties:

1. **Completeness:** required event categories are recorded across the right scope.
2. **Traceability:** logs capture principal, timestamp, service, resource, and operation outcome where provided by the service.
3. **Protection:** ordinary users cannot silently alter or delete evidence.
4. **Retrievability:** audit teams can locate, export, and interpret logs within required timeframes.

Audit logs alone do not prove every organizational control functioned properly. They are a vital evidence source that must be combined with policy configurations, monitoring outputs, change tickets, and approval records.

## 2. What Do Cloud Audit Logs Record?

Cloud Audit Logs record activities related to using Google Cloud resources. Each audit log entry typically contains details about the service, API method, resource, calling identity, timestamp, and outcome status. Specific fields depend on the service and event type.

Google Cloud classifies audit logs into four main categories:

| Log Type | Contents | Default State |
|---|---|---|
| Admin Activity | Administrative operations or resource configuration changes | Always recorded; cannot be disabled |
| Data Access | Reading or writing user data and reading controlled metadata | Disabled by default for most services; BigQuery has its own rules and records Data Access by default |
| System Event | Changes performed by Google Cloud systems on behalf of users | Always recorded; cannot be disabled |
| Policy Denied | Requests denied by security policies, such as IAM or VPC Service Controls | Generated when supported by the service and a policy denies the request |

### 2.1. Admin Activity

Admin Activity audit logs record resource configuration changes or administrative operations, for example:

- Creating, updating, or deleting a Compute Engine instance.
- Modifying firewall rules or network configurations.
- Modifying IAM policies.
- Creating or updating Cloud Storage buckets.
- Updating configurations of supported services or resources.

This log type is always enabled and cannot be turned off. Therefore, it forms the critical baseline for auditing infrastructure changes.

### 2.2. Data Access

Data Access audit logs record data access operations or reading information protected by a service. For example:

- A principal reads an object in Cloud Storage.
- A user queries data in an audit-supported service.
- An application reads a secret or sensitive metadata.
- A principal reads configuration or data of a resource audited by the service.

Data Access typically comprises three log types:

- DATA_READ: reading data.
- DATA_WRITE: writing or modifying data.
- ADMIN_READ: reading administrative metadata or configuration.

Most Data Access logs are disabled by default because they can generate high log volumes. BigQuery is a notable exception: it records Data Access audit logs by default. When an organization needs to prove who read data, review audit settings for each service and enable the appropriate log types.

### 2.3. System Event

System Event audit logs record actions executed by Google Cloud systems to manage resources, such as maintenance operations or automated service actions. This log type is always enabled and cannot be disabled.

During investigations, distinguish actions requested by users or workloads from actions initiated by the system. Both event types may appear close together while carrying different meanings.

### 2.4. Policy Denied

Policy Denied audit logs help identify requests blocked by security policies. For instance, a request rejected by VPC Service Controls or an operation failing an access policy.

This log type is useful for detecting misconfigurations, anomalous access attempts, and security boundary violations. Exact logging support and payload fields depend on the service or policy mechanism generating the event.

### 2.5. Access Transparency

For eligible services and organizations, Access Transparency logs can provide information about certain Google personnel accesses to customer content during support or operations. This provides supplementary evidence when organizations need oversight over provider-side data access. Availability depends on service, region, and product prerequisites; verify supported scope before committing to compliance requirements.

## 3. Structure of an Audit Log Entry

Audit log entries are written to Cloud Logging. Common fields include:

| Field | Meaning |
|---|---|
| logName | Log name, e.g., activity or data_access |
| resource | Resource type and resource-identifying labels |
| timestamp | Time the event occurred |
| receiveTimestamp | Time Cloud Logging received the log entry |
| severity | Severity level if the entry includes this field |
| insertId | Entry identifier for log processing |
| protoPayload.serviceName | Service that emitted the audit event |
| protoPayload.methodName | API method or operation |
| protoPayload.resourceName | Associated resource name |
| protoPayload.authenticationInfo | Authenticated identity details |
| protoPayload.authorizationInfo | Authorization check details |
| protoPayload.requestMetadata | Request metadata, potentially including caller information |
| protoPayload.status | Operation status or error details |

For example, an audit entry might show that a deployment application's service account called the VM creation API in a production project. Auditors can use principal, method, resource, and timestamp to reconcile against release tickets.

Not every service populates every field. Certain request details may be redacted or obfuscated for security and privacy reasons. When designing evidence workflows, confirm which fields a service actually emits rather than assuming every log shares the exact same schema.

## 4. Enabling Data Access Audit Logs

Admin Activity and System Event logs are recorded automatically. For Data Access, organizations must decide which services need `DATA_READ`, `DATA_WRITE`, and `ADMIN_READ` enabled.

For instance, an organization wanting to log data reads and writes across supported services can configure `auditConfigs` in an IAM policy:

~~~yaml
auditConfigs:
  - service: allServices
    auditLogConfigs:
      - logType: DATA_READ
      - logType: DATA_WRITE
      - logType: ADMIN_READ
~~~

The configuration above is part of an IAM policy. Before applying it at the project, folder, or organization level, inspect the current policy so you do not accidentally overwrite existing bindings or audit configurations. Per-service configurations can be used if the organization only needs specific log types.

The rollout process should include:

1. Listing sensitive data and services requiring access evidence.
2. Identifying appropriate `DATA_READ`, `DATA_WRITE`, or `ADMIN_READ` settings.
3. Checking whether services support the corresponding audit log types.
4. Configuring `auditConfigs` at the appropriate governance scope.
5. Performing a controlled test action to generate logs.
6. Querying Cloud Logging and confirming principal, resource, method, and timestamp.
7. Monitoring log volume and cost after enabling.

Example retrieving a project's IAM policy:

~~~bash
gcloud projects get-iam-policy acme-prod-123 --format=json
~~~

After updating the reviewed policy, apply it with:

~~~bash
gcloud projects set-iam-policy acme-prod-123 policy-with-audit-config.json
~~~

Never overwrite a newer policy with a stale policy file when concurrent edits occur. In enterprise environments, manage policies through Infrastructure as Code or controlled change workflows.

### 4.1. Audit Configuration Scope

Audit configurations can be managed at the organization, folder, or project level. IAM policies are inherited, so higher-level configurations apply to child resources. Lower-level configurations can add to or adjust behaviors following IAM audit config merging rules.

Choose scope based on how the organization governs:

- Organization: suitable for uniform collection requirements across the entire organization.
- Folder: suitable when teams or environments maintain separate policies.
- Project: suitable for exceptions or specific workload requirements.

If `exemptedMembers` is used, review it carefully. A principal exempted from Data Access audit logging can weaken the ability to prove access activity. Use exemptions only with clear justification, an approver, and a review expiration.

## 5. Centralizing Log Collection with Log Router

Cloud Logging can receive logs from many projects and route them to storage or analytics destinations. The component performing routing is Log Router. A routing configuration is called a log sink.

Common destinations:

| Destination | Use Case |
|---|---|
| Cloud Logging log bucket | Centralized storage, querying via Logs Explorer or Log Analytics |
| BigQuery dataset | Analyzing audit events with SQL and joining audit datasets |
| Cloud Storage bucket | Long-term archival, exporting evidence packages, and enforcing retention policies |
| Pub/Sub topic | Near-real-time log forwarding to a SIEM or event processing system |

High-level diagram:

~~~mermaid

    P1["Production project A"] --> LR["Cloud Logging / Log Router"]
    P2["Production project B"] --> LR
    P3["Security project"] --> LR
    LR --> LB["Central audit log bucket"]
    LR --> BQ["BigQuery audit dataset"]
    LR --> GCS["Cloud Storage archive"]
    LR --> PS["Pub/Sub"]
    PS --> SIEM["SIEM / Security analytics"]
    LB --> EX["Auditors / Investigators"]
~~~

### 5.1. Project Log Sinks and Aggregated Sinks

A project sink routes logs generated within a single project. An aggregated sink is created at the folder or organization level and can collect logs from child projects when the `include children` option is enabled.

For organizations with many projects, aggregated sinks standardize where evidence is stored. For example, the security team can create a log bucket in a dedicated project to receive audit logs from production projects.

A sink can use a filter to select which logs to route. The example filter below selects Compute Engine Admin Activity and Data Access audit logs. When writing actual filters, group conditions with parentheses to guarantee intended OR/AND logic:

~~~text
(log_id("cloudaudit.googleapis.com/activity")
 OR log_id("cloudaudit.googleapis.com/data_access"))
 AND protoPayload.serviceName="compute.googleapis.com"
~~~

For compliance evidence, avoid accidentally dropping audit logs through inclusion or exclusion filters. Exclusions can prevent entries from reaching the intended destination. Review filter edits like security changes and test against real log entries.

### 5.2. Destination Write Permissions

When creating a sink, Cloud Logging uses a writer identity to write logs to the destination. This principal needs appropriate permissions on the target storage, such as write permissions to a log bucket, BigQuery dataset, Cloud Storage bucket, or Pub/Sub topic.

Deployment workflow:

1. Create the destination in the security or archive project.
2. Create the sink at the source project, folder, or organization.
3. Retrieve the sink's writer identity.
4. Grant exact write permissions for the writer identity on the destination.
5. Verify new log entries appear at the destination.
6. Monitor routing errors in sink configuration and system logs.

Do not grant broad administrative permissions to the writer identity. The sink only needs write access to the designated destination.

Note that sinks only route logs generated after the sink is created and active. Creating a sink does not automatically backfill historical logs that already existed. To collect historical data, query and export from sources still holding logs within their retention window.

## 6. Designing Log Buckets and Retention Periods

A log bucket is where Cloud Logging stores log entries. Organizations can use default buckets or create custom buckets segmented by environment, evidence type, and retention requirements.

Within a project, Cloud Logging typically has two system buckets:

| Bucket | Primary Contents | Default Retention |
|---|---|---|
| _Required | Admin Activity, System Event, and Access Transparency logs | 400 days, fixed |
| _Default | Remaining logs routed to the default bucket, including many Data Access and application logs | 30 days, configurable |

User-created log buckets can configure custom retention periods per requirements. Retention for standard log buckets can typically be set between 1 and 3650 days; the `_Required` bucket follows dedicated rules and retains logs for 400 days.

Do not assume 30 or 400 days satisfies every regulation. Actual retention periods must reflect applicable laws, contracts, internal policies, incident detection timelines, and investigative needs.

### 6.1. Choosing Retention by Purpose

A sample policy matrix might look like:

| Log Group | Purpose | Reference Policy |
|---|---|---|
| Admin Activity | Trace infrastructure and IAM changes | Retain per mandatory audit period; export to archive if longer retention is needed |
| Data Access | Prove who read/wrote data | Select based on data sensitivity, compliance requirements, and cost |
| Policy Denied | Analyze blocked access attempts | Retain long enough to detect anomalous patterns and investigate |
| Application security logs | Investigate application activity | Per operational policy and data classification |
| Security incident evidence | Specific incident records | Retain under legal hold or incident policy |

This is an illustrative design, not a universal mandatory schedule for all organizations.

### 6.2. Configuring Retention for a Log Bucket

You can update a bucket's retention using gcloud:

~~~bash
gcloud logging buckets update audit-evidence --location=global --retention-days=2555 --project=security-archive-123
~~~

The example command sets roughly seven years of retention for the `audit-evidence` bucket. Before applying, verify the location and project are correct, the duration aligns with policy, and the destination has proper write permissions.

Verify the live configuration after updating:

~~~bash
gcloud logging buckets describe audit-evidence --location=global --project=security-archive-123
~~~

For the `_Required` bucket, the 400-day retention is managed by Google Cloud under dedicated rules; do not apply this retention update example to that bucket.

### 6.3. Retention Lock

Cloud Logging supports retention locking on log buckets. Once a bucket is locked, the retention period cannot be reduced and logs cannot be deleted before the retention period expires. Locking is irreversible, so review carefully before enabling.

Retention lock is useful when an organization must prove logs are retained for a committed timeframe. Still, carefully evaluate:

- Does the selected duration match regulations and contracts?
- Have storage capacity and costs been estimated?
- Who is allowed to create buckets, alter retention, or lock buckets?
- Are processes in place for legal holds and retention expiration?

Retention lock does not prevent every kind of unauthorized access. Organizations still need IAM controls, protection of the storage project, and monitoring of configuration changes.

## 7. Long-Term Archival and Protecting Evidence Integrity

Cloud Logging log buckets suit querying and analysis during the active retention window. For records needing long-term storage or separation from operational environments, route logs to Cloud Storage.

Cloud Storage lets you apply a retention policy to a bucket and lock it with Bucket Lock. Once a retention policy is locked, the retention period cannot be reduced or removed prior to expiration. Bucket Lock has permanent consequences; test on a dedicated bucket and review policies before locking.

An evidence storage architecture can be split into two tiers:

- **Operational logs:** log buckets serving Logs Explorer, rapid investigations, and operational analysis.
- **Evidence archive:** Cloud Storage buckets in a dedicated security project, with retention policies, Bucket Lock where required, and separate IAM.

Storage flow diagram:

~~~mermaid
flowchart LR
    A["Cloud Audit Logs"] --> R["Log Router"]
    R --> O["Operational log bucket"]
    R --> G["Cloud Storage archive"]
    G --> RP["Retention policy / Bucket Lock"]
    G --> EV["Evidence package"]
    EV --> H["Manifest and SHA-256"]
    EV --> RV["Reviewer / Auditor"]
~~~

### 7.1. Separating Permissions Between Source and Evidence Store

Someone with administrative privileges on a workload project should not by default have permissions to delete the evidence archive. Place archives in a dedicated security project and restrict permissions by duty.

Example separation:

- Platform team manages sinks and routing configurations.
- Security team manages log bucket access permissions and retention policies.
- Audit team has read-only or retrieval permissions scoped to authorized records.
- Application teams have no permissions to delete or modify archives.

Assign IAM roles at the narrowest scope. Roles such as Logging Viewer, Private Logs Viewer, and Logging Admin can be assigned by responsibility. Data Access audit logs may require Private Logs Viewer permissions to read. Logging Admin carries broad administrative rights and should not be granted to personnel who only need to read evidence.

### 7.2. Preserving Retrieval Records and Chain of Custody

When exporting logs for audits or investigations, capture metadata enabling others to reproduce the retrieval:

- Case ID or audit request ID.
- Queried project, folder, or organization.
- Time range, time zone, and exact filter used.
- Retrieval timestamp and operator.
- Source log bucket or dataset.
- Number of exported entries and file format.
- SHA-256 checksum of each file or evidence package.
- Reviewer, handover timestamp, and subsequent accesses.

Checksums detect modifications to file contents after export. They do not by themselves prove source data was complete or unaltered prior to export. To protect the entire chain of evidence, combine checksums with retention locks, separated IAM, audit trails, and documented handover procedures.

## 8. Access Control for Logs and Evidence

Logs may contain principal emails, IP addresses, resource names, queries, or sensitive metadata. Not every operator needs to read every log.

Common roles:

| IAM Role | Purpose |
|---|---|
| roles/logging.viewer | View log entries and query logs within granted scope |
| roles/logging.privateLogViewer | View private logs, including Data Access audit logs |
| roles/logging.admin | Administer Cloud Logging, including configuring and managing logs |
| roles/logging.logWriter | Write logs to Cloud Logging within permitted scope |

Log viewing permissions and log administration permissions must be separated. Auditors may need read access, while only a small group may alter sinks or retention. Application principals writing logs also do not need permission to read all logs.

Log views can restrict the subset of logs a user group is permitted to access. For example, an auditor assigned to a subset of projects only needs to see audit logs for those projects. Combining log views with IAM reduces the risk of leaking information from unrelated workloads.

Enable audit logging for critical logging administrative actions and monitor changes to:

- Log bucket IAM policies.
- Log sinks and filters.
- Retention periods and retention locks.
- Log views and access permissions.
- Destination buckets, datasets, or topics.

## 9. Querying and Analyzing Evidence

Logs Explorer supports querying logs using the Logging query language. Start with time range, resource type, and log name; then filter by principal, service, method, or resource under investigation.

Example locating a project's Admin Activity logs:

~~~text
logName="projects/acme-prod-123/logs/cloudaudit.googleapis.com%2Factivity"
timestamp >= "2026-11-01T00:00:00Z"
timestamp < "2026-11-02T00:00:00Z"
~~~

Find activities performed by a service account:

~~~text
logName="projects/acme-prod-123/logs/cloudaudit.googleapis.com%2Factivity"
protoPayload.authenticationInfo.principalEmail="deployer@acme-prod-123.iam.gserviceaccount.com"
~~~

Find Cloud Storage Data Access logs:

~~~text
logName="projects/acme-prod-123/logs/cloudaudit.googleapis.com%2Fdata_access"
protoPayload.serviceName="storage.googleapis.com"
~~~

You can use gcloud to read logs matching a filter:

~~~bash
gcloud logging read 'logName="projects/acme-prod-123/logs/cloudaudit.googleapis.com%2Factivity" AND protoPayload.serviceName="compute.googleapis.com"' --project=acme-prod-123 --freshness=7d --limit=1000 --format=json
~~~

During investigations, do not search solely by principal email. A workload may act through a service account, service agent, or federated identity. Correlate `authenticationInfo`, `serviceName`, `methodName`, `resourceName`, and `status`. If logs include `delegationInfo` or impersonation details, trace the entire identity chain.

### 9.1. Analyzing in BigQuery

If a log sink routes audit logs to BigQuery, audit teams can use SQL to analyze event counts by principal, service, or date. Exact schemas and field representations depend on export configuration; inspect the dataset schema before running sample queries.

Illustrative query when the dataset contains corresponding columns:

~~~sql
SELECT
  DATE(timestamp) AS event_date,
  protopayload_auditlog.authenticationInfo.principalEmail AS principal,
  protopayload_auditlog.serviceName AS service,
  COUNT(*) AS event_count
FROM
  `security-archive-123.audit_logs.cloudaudit_googleapis_com_activity_*`
WHERE
  timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY
  event_date, principal, service
ORDER BY
  event_date DESC, event_count DESC;
~~~

Aggregated results help identify principals with unusually high operation counts or services modified outside deployment windows. When evidence for a specific event is needed, retrieve original log entries rather than storing only summary tables.

### 9.2. Log-Based Metrics and Alerts

Cloud Logging can generate log-based metrics from matching entries, then use Cloud Monitoring to fire alerts. For example:

- Sudden spikes in Policy Denied counts.
- IAM policy changes outside maintenance windows.
- A service account performing unusual administrative operations.
- Unusual spikes in sensitive data access counts.

Metrics and alerts enable early detection, but do not replace retaining raw logs. Metrics typically store only aggregated counts; investigations require returning to the original audit log entries.

## 10. Evidence Collection Workflow for an Audit

Suppose an auditor requests evidence of IAM permission changes in the production project over the past month. The workflow can be executed as follows:

1. **Define scope:** project, folder, or organization; time range; types of changes to prove.
2. **Verify sources:** confirm Admin Activity audit logs were recorded and the log bucket still holds data for the requested range.
3. **Query:** filter audit logs by IAM-related services, methods, principals, and resources.
4. **Reconcile:** compare events against change tickets, approvals, and release schedules.
5. **Export data:** save original log entries in an appropriate format, such as JSON.
6. **Generate manifest:** record filter, time range, source, entry count, export timestamp, and checksums.
7. **Review:** accountable reviewer validates completeness, interpretation, and approves the evidence package.
8. **Archive:** place the evidence package in storage with appropriate retention and restricted access.
9. **Record handover:** log recipient, timestamp, purpose, and subsequent accesses.

Example structure of an evidence package:

~~~text
IAM-CHANGE-REVIEW-2026-11/
  README.md
  query-filter.txt
  audit-entries.json
  manifest.json
  checksums.sha256
  review-notes.pdf
~~~

The manifest can contain metadata without sensitive payloads:

~~~json
{
  "caseId": "IAM-CHANGE-REVIEW-2026-11",
  "sourceProject": "acme-prod-123",
  "logType": "ADMIN_ACTIVITY",
  "timeRangeUtc": {
    "start": "2026-11-01T00:00:00Z",
    "end": "2026-12-01T00:00:00Z"
  },
  "queryFile": "query-filter.txt",
  "exportFile": "audit-entries.json",
  "reviewStatus": "approved"
}
~~~

This is an illustrative record structure. In practice, add checksums computed from exported files along with operator and reviewer details per internal procedures.

## 11. Real-World Scenario: Building a Multi-Project Audit Archive

An organization has dev, staging, and production projects. Security needs to collect Admin Activity, Data Access, and Policy Denied logs into an independent location for audits.

Proposed design:

- Each source project enables required Data Access audit logs.
- The organization creates an aggregated sink with `include children` to collect logs from child projects.
- The sink routes matching logs to a central log bucket in the security project.
- Another sink can export long-term copies to Cloud Storage.
- The security project uses IAM separated from workload teams.
- The archive bucket applies a retention policy and Bucket Lock when immutable retention is required.
- Auditors are granted read-only access to scoped log views or evidence packages within their assigned scope.
- Alerts monitor changes to IAM, sinks, retention, and archive access permissions.

Configuration change flow:

~~~mermaid
sequenceDiagram
    participant OP as Operations team
    participant GCP as Google Cloud resource
    participant LOG as Cloud Audit Logs
    participant ROUTER as Log Router
    participant ARCH as Security archive
    participant AUD as Auditor

    OP->>GCP: Apply approved IAM change
    GCP->>LOG: Record Admin Activity event
    LOG->>ROUTER: Forward log entry
    ROUTER->>ARCH: Write to central bucket
    AUD->>ARCH: Query or receive evidence package
    ARCH-->>AUD: Return logs per granted permissions
~~~

During rollout, test a controlled change in each project. Confirm the log entry appears in the source project, is routed by the sink, and is queryable in the archive. Also test a principal without archive access permissions to confirm IAM works properly.

## 12. Common Mistakes

| Symptom | Possible Cause | How to Fix |
|---|---|---|
| Missing data read logs | Data Access not enabled for service or log type | Check `auditConfigs`, service support, and event timestamps |
| Logs exist in source project but missing in archive | Incorrect sink filter or writer identity lacks destination permissions | Check filter, sink status, and destination IAM |
| Auditors cannot view Data Access logs | Missing Private Logs Viewer role or log view restricts scope | Grant appropriate role or update log view per approval |
| Older logs missing after creating sink | Sinks only route logs generated after creation | Query sources still within retention and export history separately |
| Archive expires prematurely | Retention misaligned with requirements or wrong bucket configured | Check bucket retention and archive policy |
| Log entries missing certain fields | Service does not emit that field or data is redacted | Review service audit log schema and supplement with other evidence sources |
| Logging costs spike | Too many Data Access logs enabled or long uncategorized retention | Evaluate services, filters, retention, and actual volume; never drop mandatory logs |
| Logs contain sensitive data | Application logs improper fields or request metadata carries private info | Trim logged content at source, restrict view permissions, and handle per data policy |

A particularly dangerous mistake is creating an exclusion filter to cut costs that accidentally drops audit logs. Every filter change must be reviewed, tested, and logged as a security control change.

- [ ] Identified projects, folders, and organization in audit scope.
- [ ] Inventoried services holding critical data or resources.
- [ ] Defined Admin Activity, Data Access, System Event, and Policy Denied logs to monitor.
- [ ] Enabled `DATA_READ`, `DATA_WRITE`, and `ADMIN_READ` for appropriate services.
- [ ] Reviewed `exemptedMembers` and any exceptions in `auditConfigs`.
- [ ] Created aggregated sinks when collecting logs across multiple projects.
- [ ] Verified writer identities hold exact write permissions on destinations.
- [ ] Confirmed exclusion filters do not drop required audit logs.
- [ ] Selected log buckets and retention aligned with laws, contracts, and internal policies.
- [ ] Separated the archive project from workload projects.
- [ ] Applied retention lock or Cloud Storage Bucket Lock after thorough review.
- [ ] Separated log viewing, logging administration, and archive custodian permissions.
- [ ] Enabled alerts for IAM, sink, retention, and archive permission changes.
- [ ] Periodically verified routing and queryability.
- [ ] Preserved filters, time ranges, manifests, checksums, and handover records on export.
- [ ] Prevented logging secrets, tokens, or unnecessary sensitive data in application logs.
- [ ] Monitored ingestion, storage, query, and export costs.

## 14. Self-Check Questions

**1. How do Admin Activity and Data Access audit logs differ?**

Admin Activity logs record administrative operations and resource configuration changes. Data Access logs record data read/write operations or reading metadata for supported services. Admin Activity is always enabled; most Data Access logs must be configured.

**2. Why should an organization use an aggregated sink at the organization or folder level?**

Aggregated sinks collect logs from multiple child projects into a centralized destination. This enables uniform retention policies, access controls, and monitoring while reducing the risk of overlooking a project.

**3. Do log sinks automatically export older logs created before the sink existed?**

No. Sinks route new log entries matching the filter after the sink becomes active. To export historical data, query sources still retaining logs and perform a separate export.

**4. How does retention lock help protect evidence?**

Retention lock prevents reducing retention periods or deleting logs before the configured expiration. In Cloud Logging, locking a bucket is irreversible; in Cloud Storage, Bucket Lock locks the retention policy. Review retention durations carefully before locking.

**5. Is a checksum sufficient to prove evidence integrity?**

Checksums detect file modification after the hash was computed. They do not prove source data was complete or unaltered before export. Pair checksums with audit trails, retention locks, separated IAM, and chain-of-custody procedures.
