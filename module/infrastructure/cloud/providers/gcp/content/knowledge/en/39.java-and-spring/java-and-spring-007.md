# Synchronous, Asynchronous, and Streaming Calls with Google Cloud Java Clients

Java applications on Google Cloud often invoke a variety of APIs: reading an object, creating a record, publishing a message, querying data, or consuming a continuous event stream. Java client libraries provide multiple ways to perform these operations. Choosing among synchronous, asynchronous, and streaming calls directly impacts thread consumption, latency, high-load handling, error management, and application lifecycle.

Synchronous calls fit when a result is needed immediately in the current execution path and wait times are predictable. Asynchronous calls fit when you want to continue other work while waiting for an API to complete. Streaming fits when data moves in multiple chunks or events arrive continuously. These three are distinct execution models; do not choose one merely on a hunch that it is always faster than the others.

Within Google Cloud, distinguish high-level service clients—such as Pub/Sub `Publisher` or `Storage`—from clients generated by Google API Client Libraries (GAPIC) built on GAX. Each library has its own APIs and capabilities for synchronous, asynchronous, and streaming execution. Always check the documentation for the specific service and library version before designing.

## 1. Three API Invocation Models

| Model | How it works | When to use |
| --- | --- | --- |
| Synchronous | Calls a method and waits for the result or exception before continuing | Simple operations, immediate result needed, bounded traffic and wait times |
| Asynchronous | Sends a request, receives a future or callback, and continues other work | Many independent requests, long-wait I/O tasks, message publishing, or background work |
| Streaming | Exchanges multiple data chunks in one stream rather than a single request/response | Large datasets, incremental results, continuous events, or bidirectional communication |

A synchronous API can still be called from a thread pool to avoid blocking a request thread. However, moving a blocking call onto an executor merely shifts where blocking happens; it does not make the API non-blocking. Likewise, receiving an `ApiFuture` does not mean data is being streamed.

## 2. Synchronous Calls with Google Cloud Java Clients

With synchronous calls, the program invokes a method and waits for the response. For example, the Cloud Storage client can read object metadata:

~~~java
import com.google.cloud.storage.Blob;
import com.google.cloud.storage.BlobId;
import com.google.cloud.storage.Storage;
import com.google.cloud.storage.StorageOptions;

public class ReadObjectMetadata {
  public static void main(String[] args) {
    Storage storage = StorageOptions.getDefaultInstance().getService();

    Blob blob = storage.get(BlobId.of("orders-data", "exports/orders.csv"));
    if (blob == null) {
      throw new IllegalStateException("Object does not exist");
    }

    System.out.println("Generation: " + blob.getGeneration());
    System.out.println("Size: " + blob.getSize());
  }
}
~~~

The `get` method returns once the result arrives or an error occurs. This calling style is easy to read, easy to test, and fits tasks needing metadata immediately. Inside an HTTP request, the time spent calling Cloud Storage occupies the request-handling thread.

Synchronous calls are appropriate when:

- Business logic needs the result to decide the next step.
- Concurrent calls are reasonably bounded.
- Wait times and timeouts are explicitly configured.
- Source code prioritizes sequential readability over orchestrating multiple tasks.

Avoid long blocking calls on the Spring WebFlux event loop or threads multiplexing many connections. If a library offers only a synchronous API, run it on a dedicated executor with bounded threads and queues. Limit concurrency to prevent queues from growing unbounded when a Google Cloud service slows down.

## 3. Asynchronous Calls with ApiFuture and Callbacks

Many Google Cloud Java clients use `ApiFuture` to represent a future result. Calling code can register a callback to receive the result or error upon completion instead of blocking a thread with `get()`.

Pub/Sub `Publisher` is a common example. `Publisher` accepts messages to send and returns an `ApiFuture` containing the message ID once publishing finishes:

~~~java
import com.google.api.core.ApiFuture;
import com.google.api.core.ApiFutureCallback;
import com.google.api.core.ApiFutures;
import com.google.cloud.pubsub.v1.Publisher;
import com.google.common.util.concurrent.MoreExecutors;
import com.google.protobuf.ByteString;
import com.google.pubsub.v1.PubsubMessage;
import com.google.pubsub.v1.TopicName;

import java.io.IOException;
import java.util.concurrent.TimeUnit;

public class PublishAsync {
  public static void main(String[] args) throws IOException, InterruptedException {
    TopicName topic = TopicName.of("my-project", "orders");
    Publisher publisher = Publisher.newBuilder(topic).build();

    try {
      PubsubMessage message = PubsubMessage.newBuilder()
          .setData(ByteString.copyFromUtf8("{\"orderId\":\"A-1024\"}"))
          .putAttributes("source", "orders-api")
          .build();

      ApiFuture<String> messageId = publisher.publish(message);

      ApiFutures.addCallback(
          messageId,
          new ApiFutureCallback<String>() {
            @Override
            public void onSuccess(String id) {
              System.out.println("Published message: " + id);
            }

            @Override
            public void onFailure(Throwable error) {
              System.err.println("Publish failed: " + error.getMessage());
            }
          },
          MoreExecutors.directExecutor());
    } finally {
      publisher.shutdown();
      if (!publisher.awaitTermination(1, TimeUnit.MINUTES)) {
        System.err.println("Publisher did not terminate within the timeout");
      }
    }
  }
}
~~~

This snippet illustrates registering a callback and closing the `Publisher` when the sample program exits. In a long-running server application, `Publisher` should be a shared component managed by the application lifecycle; never create and shut down a `Publisher` per HTTP request. Callbacks running on `directExecutor` must be fast and perform no blocking I/O, as they may execute directly on the thread completing the future. For heavy processing, offload work to a separate bounded executor.

You can call `get()` on an `ApiFuture`, yet that blocks the thread until the result arrives. If the goal is asynchronous execution, use callbacks or future composition rather than calling `get()` immediately after publishing.

### Using GAX Callables

GAPIC clients typically expose synchronous convenience methods alongside callables for each RPC type. On a unary callable, `call()` executes synchronously, while `futureCall()` returns an `ApiFuture`:

~~~java
ApiFuture<Response> future =
    client.someUnaryCallable().futureCall(request);

ApiFutures.addCallback(
    future,
    new ApiFutureCallback<Response>() {
      @Override
      public void onSuccess(Response response) {
        handleResponse(response);
      }

      @Override
      public void onFailure(Throwable error) {
        handleFailure(error);
      }
    },
    callbackExecutor);
~~~

This is a general GAX pattern; replace `Request`, `Response`, and the callable name with the types and methods exposed by your specific client. Not every method on every service provides the same set of callables or supports asynchronous execution.

## 4. What Is Streaming?

Streaming transfers data in multiple parts within a single session. Rather than waiting for the entire result before processing, the application can process each chunk as it arrives. This reduces the need to hold the full dataset in memory and suits large or continuous data flows.

There are four common streaming communication styles in RPC APIs:

| Style | Data direction | Example use case |
| --- | --- | --- |
| Unary | One request, one response | Reading metadata or creating a resource |
| Server streaming | One request, multiple responses | Reading a dataset block by block |
| Client streaming | Multiple requests, one response | Sending multiple data chunks and receiving an aggregated result |
| Bidirectional streaming | Multiple requests and responses in one session | Continuously sending events and receiving corresponding results |

The streaming style describes the wire protocol. A server-streaming method can still be consumed synchronously via an iterator, even though the server sends multiple responses. An asynchronous API can return a future yet still exchange only one response. Evaluate two separate questions: does the call block a thread, and how many messages does the API exchange in one session?

Not every Google Cloud service supports all four styles. Cloud Storage offers chunked read/write channels; Pub/Sub provides `Publisher` and `Subscriber` for continuous messaging; the BigQuery Storage Read API returns results as a server stream; GAPIC clients expose streaming callables when the service API defines matching RPCs.

## 5. Reading Large Objects with Cloud Storage ReadChannel

When reading a large object, you do not need to load the entire payload into a byte array. Storage `ReadChannel` reads data incrementally via `ByteBuffer`:

~~~java
import com.google.cloud.storage.BlobId;
import com.google.cloud.ReadChannel;
import com.google.cloud.storage.Storage;

import java.io.IOException;
import java.nio.ByteBuffer;

public class StreamObject {
  public static void copyToProcessor(Storage storage, String bucket, String objectName)
      throws IOException {
    try (ReadChannel channel = storage.reader(BlobId.of(bucket, objectName))) {
      ByteBuffer buffer = ByteBuffer.allocate(64 * 1024);
      int bytesRead;

      while ((bytesRead = channel.read(buffer)) != -1) {
        buffer.flip();
        if (buffer.hasRemaining()) {
          processChunk(buffer);
        }
        buffer.clear();
      }
    }
  }

  private static void processChunk(ByteBuffer chunk) {
    // Process data currently in the buffer before reading the next chunk.
  }
}
~~~

A 64 KiB buffer is an illustrative value, not the optimal size for every workload. Buffer sizing must balance read syscall count, per-request memory, and processing latency. `processChunk` must consume the data before the buffer is cleared for reuse.

For uploads, `WriteChannel` writes chunks to an object. Close the channel properly to finalize the write and release resources. For large files, account for retries, resumable uploads, checksums, and handling mid-transfer application restarts.

## 6. Server Streaming with the BigQuery Storage Read API

The BigQuery Storage Read API returns data in response blocks. A read session can provide multiple read streams, each read independently. The example below illustrates reading one stream:

~~~java
import com.google.api.gax.rpc.ServerStream;
import com.google.cloud.bigquery.storage.v1.BigQueryReadClient;
import com.google.cloud.bigquery.storage.v1.ReadRowsRequest;
import com.google.cloud.bigquery.storage.v1.ReadRowsResponse;

public class ReadBigQueryStream {
  public static void read(String readStreamName) throws Exception {
    try (BigQueryReadClient client = BigQueryReadClient.create()) {
      ReadRowsRequest request = ReadRowsRequest.newBuilder()
          .setReadStream(readStreamName)
          .build();

      ServerStream<ReadRowsResponse> responses =
          client.readRowsCallable().call(request);

      for (ReadRowsResponse response : responses) {
        processResponseBlock(response);
      }
    }
  }

  private static void processResponseBlock(ReadRowsResponse response) {
    // Decode Arrow or Avro according to the format selected in the read session.
  }
}
~~~

`readStreamName` must come from a `ReadSession` previously created with the BigQuery Storage Read API. The payload format depends on the format chosen at session creation—typically Avro or Arrow; the application must decode it accordingly. Each response is a block of data, not necessarily a single row.

`ServerStream` iterates responses sequentially. If processing each block takes substantial time, consider parallel coordination while capping the number of blocks buffered in memory. Never collect all responses into a large `List` when the goal is processing large datasets.

## 7. Client Streaming and Bidirectional Streaming

Some gRPC APIs allow clients to send multiple requests within one session. Client streaming fits when the client sends multiple data chunks and receives a single final result. Bidirectional streaming allows both client and server to send messages independently in the same session, progressing concurrently.

GAX represents these callables with abstractions such as `ClientStreamingCallable` and `BidiStreamingCallable`. With bidirectional streaming, a callable can create a `BidiStream` to send requests and read responses. Callable names, message types, and stream termination depend on the specific API.

Conceptual pattern:

~~~java
BidiStream<Request, Response> stream = streamingCallable.call();

try {
  stream.send(firstRequest);
  stream.send(secondRequest);
} finally {
  stream.closeSend();
}

for (Response response : stream) {
  handle(response);
}
~~~

This illustrates a finite sending session, not drop-in code for a specific client. Check the service's API documentation for closing the send half, receiving terminal stream errors, message size limits, and flow control requirements. For long-lived bidirectional streams, sender and receiver typically run concurrently; close the send stream only when permitted by the protocol or business logic. With client streaming, the application sends multiple requests and closes the send stream so the server can complete the aggregated response.

If a stream fails midway, determine whether it can resume from a checkpoint or must start a new session. Never assume resending all requests is safe: operations may have already been processed by the server before the connection dropped. Use request IDs, sequence numbers, or service idempotency mechanisms when duplicate processing must be avoided.

## 8. Pub/Sub: Asynchronous Publishing and Continuous Message Processing

Pub/Sub clearly illustrates the difference between asynchronous publishing and continuous message consumption. `Publisher` batches and sends messages in the background; `Subscriber` delivers incoming messages through callbacks as data arrives.

Example message-handling receiver:

~~~java
import com.google.cloud.pubsub.v1.Subscriber;
import com.google.cloud.pubsub.v1.AckReplyConsumer;
import com.google.pubsub.v1.ProjectSubscriptionName;
import com.google.pubsub.v1.PubsubMessage;
import com.google.cloud.pubsub.v1.MessageReceiver;

public class SubscribeOrders {
  public static void start() {
    ProjectSubscriptionName subscription =
        ProjectSubscriptionName.of("my-project", "orders-worker-sub");

    MessageReceiver receiver = (PubsubMessage message, AckReplyConsumer consumer) -> {
      try {
        processOrder(message.getData().toStringUtf8());
        consumer.ack();
      } catch (Exception error) {
        consumer.nack();
      }
    };

    Subscriber subscriber = Subscriber.newBuilder(subscription, receiver).build();
    subscriber.startAsync().awaitRunning();
  }

  private static void processOrder(String payload) {
    // Validate and process business logic; should be idempotent.
  }
}
~~~

This example focuses on the callback; production applications must keep a reference to `Subscriber` and stop it in a shutdown lifecycle hook. Import `AckReplyConsumer` from the matching Pub/Sub client package. Never start a new `Subscriber` per HTTP request.

On success, call `ack` to acknowledge the message. On failure, if Pub/Sub should redeliver per subscription policy, call `nack`. Messages can be redelivered, so handlers should be idempotent or track processing state by message ID/business key. Never `ack` before critical business state is durably persisted if message loss is unacceptable.

`Subscriber` can receive many messages concurrently. Use `FlowControlSettings` to cap outstanding message counts and total bytes. These limits apply consumer-side backpressure: when the app is busy, the client curtails buffered messages rather than letting memory grow unchecked. Tune values based on message size, processing time, and downstream database capacity.

## 9. Backpressure and Resource Limits

Streaming and asynchronous execution do not solve overload automatically. If producers emit data faster than consumers process it, queues and memory grow continuously. Backpressure regulates intake rate or queued volume so the system never accepts more work than it can handle.

Common controls:

- Cap in-flight requests and unacknowledged messages.
- Bound buffer, batch, and queue sizes.
- Use executors with bounded thread counts and queue capacities.
- Pause reading or reduce demand when consumers slow down, if supported by the API.
- Partition streams or split across independent streams when supported by the service.
- Monitor processing latency, queue depth, outstanding bytes, and error rates.

With Pub/Sub, flow control bounds outstanding messages and bytes. With Storage `ReadChannel`, the application paces reads through its buffer-processing loop. With server streaming, sequential response processing keeps memory stable; if processing in parallel, use bounded queues and preserve ordering rules when required by business logic.

Never spawn a new thread per message or per callback. Unbounded thread pools can exhaust memory and amplify context switching under load. Size concurrency based on CPU count, I/O latency, service quotas, and downstream capacity.

## 10. Timeouts, Deadlines, Retries, and Cancellation

Every call from an application to Google Cloud needs a time limit. An application-level HTTP timeout does not necessarily replace an RPC deadline. If a client keeps waiting after the user's request has expired, work continues consuming resources even though nobody wants the result anymore.

| Mechanism | Purpose | Notes |
| --- | --- | --- |
| Timeout | Bounds wait time for an operation or connection layer | Distinguish connect, read, and total operation timeouts |
| Deadline | Final timestamp by which an RPC must finish | Should match the remaining time budget of the request |
| Retry | Re-attempts recoverable transient errors | Retry only appropriate errors and repeat-safe operations |
| Cancellation | Stops work that is no longer needed | Verify whether the API propagates cancellation down to transport |

GAX supports configuring retries and timeouts on many GAPIC clients through client settings or callable contexts. Default settings vary by API method; do not assume all methods retry identically. When tuning, keep total retry duration shorter than the business deadline and use exponential backoff with jitter where appropriate.

Errors like `UNAVAILABLE` or some cases of `DEADLINE_EXCEEDED` can be transient, but check method semantics. `INVALID_ARGUMENT` cannot be fixed by retrying. `RESOURCE_EXHAUSTED` may reflect quotas or load limits; aggressive retries can worsen the situation.

In particular, if the client loses the connection after the server executed the operation but before the response arrives, the app does not know whether the operation succeeded. For writes or resource creation, use idempotency keys, request IDs, or status checks before retrying to prevent duplicate records.

With `ApiFuture`, you can register error handlers and cancel the future when work is no longer needed. However, client-side cancellation does not guarantee the server halted execution; rely on the API contract and design recoverable operations.

## 11. Managing Clients and Lifecycles in Spring Applications

Google Cloud clients often allocate internal transports, channels, executors, or connection pools. Creating a new client per request increases initialization overhead, connection counts, and thread counts. For thread-safe clients, create a shared application-wide instance and close it when the application stops.

Example configuring a shared GAPIC client in Spring:

~~~java
import com.google.cloud.bigquery.storage.v1.BigQueryReadClient;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.io.IOException;

@Configuration
public class GcpClientConfiguration {
  @Bean(destroyMethod = "close")
  BigQueryReadClient bigQueryReadClient() throws IOException {
    return BigQueryReadClient.create();
  }
}
~~~

Spring closes the client when the context shuts down. For Pub/Sub `Publisher` and `Subscriber`, manage their specific lifecycle methods such as `shutdown`/`awaitTermination` or `startAsync`/`stopAsync`/`awaitTerminated` according to client type. If using Spring Cloud GCP, abstractions like `PubSubTemplate` can reduce transport boilerplate and integrate with dependency injection; pick one clear ownership layer and avoid creating duplicate Publishers or Subscribers.

In Spring MVC, synchronous calls can work well if wait times and thread counts are controlled. In Spring WebFlux, never invoke blocking APIs directly on the event loop. Use non-blocking APIs when supported by the library, or offload blocking calls onto a dedicated bounded-concurrency scheduler for blocking I/O.

The `@Async` annotation only dispatches execution to another executor; it does not change the underlying Google client's semantics. If the method still calls a blocking API, the executor thread stays blocked while waiting. Choose among futures, streams, or blocking executors based on the real API and load profile.

## 12. Choosing a Model by Service and Scenario

| Service or task | Usually suitable model | Reason |
| --- | --- | --- |
| Cloud Storage reading object metadata | Synchronous | Small single response, immediate result needed |
| Cloud Storage reading or writing large objects | Channel/streaming | Incremental processing, lowers peak memory |
| Pub/Sub publishing messages | Asynchronous | Publisher batches and returns a future |
| Pub/Sub consuming subscriptions | Continuous callback and flow control | Messages arrive over time; consumer acks individually |
| BigQuery Storage Read API | Server streaming | Data returns in blocks and supports multiple streams |
| GAPIC unary RPC | Synchronous or `ApiFuture` | Choose based on thread-blocking constraints and orchestration needs |
| gRPC client/bidirectional stream | Streaming | Exchanges multiple messages in one session |

These are task-oriented guidelines, not a guarantee that every library version exposes identical methods. Check the API reference and code samples for the exact service before deciding.

## 13. Observability and Operations

For stable operations, observe both API calls and how the application consumes results:

- Record latency by service, method, and operation type.
- Count succeeded, failed, retried, and cancelled requests.
- Track pending futures and completion durations.
- Track open streams, stream durations, response counts, and terminal errors.
- Measure outstanding messages, queue depth, buffer sizes, and callback processing time.
- Attach correlation IDs or trace context to link application requests with logs.
- Never log sensitive payloads, access tokens, or secrets.

When errors rise, distinguish network, quota, IAM, deadline, input data, and downstream issues. A failed callback should not log only a generic message; logs need the service, operation, safe resource identifier, status code, and correlation ID for investigation.

## 14. Common Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Calling `get()` right after receiving `ApiFuture` | Thread still blocks; loses async benefits | Use callbacks or future composition |
| Creating a client per request | Wastes connections, threads, and startup time | Share clients and close on app shutdown |
| Loading large datasets entirely into memory | Spikes heap and risks `OutOfMemoryError` | Read/write via channels or streams |
| Leaving in-flight messages unbounded | Queues and memory grow when consumers slow down | Use flow control and bounded queues |
| Retrying every error | Amplifies load, repeats side effects, prolongs incidents | Retry selectively with backoff and idempotency |
| Never closing `Publisher`, `Subscriber`, or clients | Leaks threads, channels, and connections | Manage explicit lifecycles in Spring |
| Running blocking calls on the WebFlux event loop | Degrades request throughput | Use non-blocking APIs or a dedicated scheduler |
| Treating all streaming APIs identically | Incorrect stream closing, error handling, or flow control | Follow each API's and RPC type's contract |

## 15. Production Readiness Checklist

Before deploying a Java client integration, confirm:

- Chosen synchronous, asynchronous, or streaming model matches data characteristics and latency requirements.
- Verified the API reference for the exact service and library version.
- Clients are safely reused and closed at the right lifecycle stage.
- Timeouts/deadlines fit within the request's time budget.
- Retries apply only to appropriate errors and repeat-safe operations.
- Future callbacks run on an appropriate executor without blocking completion threads.
- Streams process data incrementally with bounded buffers and concurrency.
- Pub/Sub consumers enforce flow control, ack/nack semantics, and idempotent handling.
- Cancellation, mid-stream errors, and restart recovery are handled.
- Spring WebFlux is never blocked by synchronous blocking calls.
- Logs, metrics, and traces suffice to observe latency, errors, queues, and streams.
- Secrets and sensitive payloads are never written to logs.

When used with the right model, Java clients make integrating Google Cloud efficient and easier to operate. Synchronous calls keep business flows simple, futures leverage I/O wait time, and streaming supports large datasets and continuous events. The key decision is managing threads, deadlines, retries, backpressure, and lifecycles alongside the chosen API.
