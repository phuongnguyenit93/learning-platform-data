# Designing Backpressure, Replay, and Late-Event Handling

An event-processing system may run smoothly at a few hundred events/second yet break down when traffic spikes, a consumer goes down for several minutes, or offline devices send delayed data later. The issue is not merely “reading fast enough”: scaling concurrency indefinitely can exhaust memory; writing checkpoints before saving results can lose work; and aggregating by receive time instead of occurrence time can assign business metrics to the wrong day.

Three critical design capabilities are:

- **Backpressure:** keeping ingestion, processing, and result persistence rates within the sustainable capacity of downstream components.
- **Replay:** re-reading retained events within the retention window or from an archive to recompute, fix bugs, or feed a new consumption branch.
- **Late-event handling:** distinguishing **event time** from **processing time**, designing watermarks/windows, and deciding how to update, drop, or compensate for late data.

On Microsoft Azure, these challenges typically arise with **Azure Event Hubs**, **Azure Stream Analytics**, **Azure Functions Event Hubs triggers**, **Java** applications reading Event Hubs via SDK, and target stores such as Azure Data Explorer, Azure SQL Database, Azure Cosmos DB, or Azure Storage.

This lesson belongs to the **Events and Streaming Data** chapter of the **CLOUD_PROVIDERS_AZURE** module. Alongside Azure fundamentals—subscriptions, resource groups, Microsoft Entra ID, networking, compute, storage, monitoring, security, and cost—you will design a pipeline capable of withstanding load spikes, recovering cleanly, and explaining figures when events arrive out of order.

> **Core point:** Event Hubs is an **append-only event stream with retention**, not a queue that deletes messages when a consumer receives them. Consumer checkpoints record **how far processing has progressed**; they do not remove data from the broker. And an event received at 10:20 may belong to the 10:00–10:05 business window if it actually happened at 10:03.

## 2. Running Scenario: Multi-Branch Orders

A retail system emits events such as:

~~~json
{
  "eventId": "evt-9b82",
  "orderId": "order-481",
  "storeId": "hcm-07",
  "eventType": "OrderPaid",
  "eventTimeUtc": "2026-11-20T03:03:20Z",
  "schemaVersion": 1,
  "amount": 350000,
  "currency": "VND"
}
~~~

This is a **sample event** containing no real customer data. 03:03:20 UTC corresponds to 10:03:20 Vietnam time on the same day.

Suppose a store loses network connectivity for 15 minutes:

- `OrderPaid` actually occurred at **10:03:20**.
- The device manages to send the event to Event Hubs at **10:18:10**.
- The consumer processes it at **10:18:13**.
- The dashboard aggregates revenue into **5-minute windows based on payment time**.

If the data team uses consumer read time, the payment lands in the 10:15–10:20 window instead of 10:00–10:05. If the 10:00–10:05 window has already closed and published, the system needs a **late-event policy**: revise the metrics, emit a correction record, or route the event to an inspection branch.

Meanwhile, traffic triples and the downstream database slows down on writes. Consumers need **backpressure** to avoid exhausting RAM; and if a billing calculation bug is fixed, the team needs **replay** over raw historical data to recompute accurately.

## 3. Timestamps and Positions in a Stream

### 3.1. Event time

**Event time** is when the event occurred in the business domain, typically generated by the producer, device, or source system.

For example, **`eventTimeUtc = 03:03:20Z`** in `OrderPaid` records when payment occurred at the source.

Points to guard against:

- Device or source-service clock skew.
- Timezone conversions and daylight saving time across regions.
- Producers accidentally or deliberately sending future/past timestamps.
- Schema versions and timestamp precision.
- Which business milestone is the source of truth: when the customer paid, when the bank settled, or when the order hit the database?

**Event time is not automatically trustworthy merely because it sits in JSON.** Validate timestamps, bound acceptable skew, and define policies for anomalous clocks.

### 3.2. Enqueued time

**Enqueued time** is when the Event Hubs broker appended the event to a partition. This is service-side metadata, distinct from application-supplied timestamps.

~~~text
eventTimeUtc       = 2026-11-20T03:03:20Z
enqueuedTimeUtc    = 2026-11-20T03:18:10Z
processingTimeUtc  = 2026-11-20T03:18:13Z
~~~

An event can reach Event Hubs 14 minutes 50 seconds late even though the consumer only takes 3 seconds to process it after broker receipt.

### 3.3. Processing time

**Processing time** is when a processor executes a step in the system. It is shaped by:

- Backlog and throttling.
- Worker and partition counts.
- Network and target-service latency.
- Batch size, retries, GC, and CPU/memory.
- Consumer restarts and partition ownership rebalances.

Aggregating by processing time measures **when the system processed**, not necessarily **when events occurred**.

### 3.4. Offset and sequence number

Each **Event Hubs partition** is an ordered log within that partition:

~~~text
Partition 0:
  sequence 101 → 102 → 103 → 104 → ...

Partition 1:
  sequence 77  → 78  → 79  → 80  → ...
~~~

- **Sequence numbers** are assigned by Event Hubs, increasing per partition.
- **Offsets** denote positions within a partition log for reading/seeking.
- They are meaningful only when qualified by **Event Hub + partition ID**.
- There is no global total order across multiple partitions.
- **Checkpoints** mark how far a consumer has processed, typically stored outside Event Hubs.

Never use partition 0's sequence number to judge whether an event in partition 1 happened earlier or later.

| Requirement | Event Hubs | Service Bus |

| Event-time windowing | Combine with ASA / Spark / Flink / ADX | Requires custom pipeline depending on use case |

## 5. Azure Event Hubs: Partitions, Consumer Groups, and Retention

### 5.1. Partitions

Event Hubs distributes events across multiple **partitions**. With identical partition keys, producers route related events into the same partition per partitioning rules, helping consumers needing per-key order.

Example:

~~~text
Partition key = storeId

hcm-07 → partition P1
hcm-08 → partition P0
hn-03  → partition P2
~~~

Partition keys do not guarantee every event from `hcm-07` arrives before every event from `hcm-08`. Highly skewed keys create **hot partitions**.

### 5.2. Consumer groups

Each **consumer group** provides an independent consumption view over the same Event Hub:

~~~text
Event Hub orders-stream
    ├── cg-orders-realtime → dashboard
    ├── cg-finance-v1      → financial reports
    └── cg-backfill-2026   → controlled replay
~~~

Consumer groups do not physically copy the stream into new logs. They let consumers track separate progress over the same retained source.

**Note:** with `EventProcessorClient`, progress/checkpoints are typically persisted in Azure Blob Storage keyed by consumer group and partition. A consumer group **does not automatically persist durable checkpoints for every SDK** unless the app configures a checkpoint store.

### 5.3. Retention

Event Hubs retains data for a **finite retention window** per tier and configuration. Consumers can re-read events within retention. Once the broker purges events past retention, **seeking an offset or creating a new consumer group cannot bring that data back**.

Never hardcode default or maximum retention values in production designs: limits depend on tier, namespace, and service version. Inspect your exact Event Hub config before committing to RPO or replay windows.

### 5.4. Capture

**Event Hubs Capture** automatically archives events to **Azure Blob Storage or Azure Data Lake Storage Gen2** per configuration, creating storage outlasting broker retention for audits and backfills.

However, Capture does not mean “rewind a checkpoint and read archive files through the Event Hubs SDK.” Replaying from Capture requires an **archive-reading pipeline** that either:

- Recomputes directly into a versioned output; or
- Re-publishes into a separate Event Hub/stream if architecture demands it.

Protect schemas, partition/time metadata, ordering, idempotency, and re-ingestion costs.

## 6. What Is Backpressure?

**Backpressure** is the set of mechanisms ensuring work does not enter a system faster than it can be sustainably processed and persisted.

Let:

- **λ (lambda):** average incoming event rate, events/sec.
- **μ (mu):** average completed processing rate, events/sec.
- **B(t):** backlog at time `t`, measured in events.

Under a simplified model with zero dropped events:

~~~text
If λ > μ:
    backlog grows at roughly (λ - μ) × t

If λ < μ:
    consumer drains backlog at roughly (μ - λ)
~~~

When data continuously arrives faster than service rate, **enlarging memory buffers cannot solve the problem long-term**. It merely delays the crash.

### 6.1. Backlog calculation example

An Event Hub ingests **18,000 events/s**. The database only sustains **12,000 events/s** for 3 minutes.

~~~text
λ = 18,000 events/s
μ = 12,000 events/s
t = 3 × 60 = 180 seconds

Backlog growth = (18,000 - 12,000) × 180
               = 1,080,000 events
~~~

Once the database recovers, the system processes **20,000 events/s** while producers keep sending 18,000/s:

~~~text
Backlog drain rate = 20,000 - 18,000
                   = 2,000 events/s

Time to catch up ≈ 1,080,000 / 2,000
                 = 540 seconds = 9 minutes
~~~

This is an **idealized model**, excluding retry overhead, partition skew, batch latency, message size, checkpoints, and scaling warm-up. While `μ < λ`, the system **cannot catch up** even if you restart the consumer.

### 6.2. Overload diagnostic table

| Condition | Signals | Appropriate response |
|---|---|---|
| Producer faster than Event Hubs quota | Throttled requests, rising send latency/retries | Check capacity/tier, batching, quotas, exponential backoff |
| Event Hubs ingests cleanly yet consumer lags | Rising per-partition lag, stale checkpoints | Optimize/scale consumers, check downstream |
| Consumer fast yet database slow | DB 429s/timeouts, pool contention | Bounded concurrency, backoff retries, batched upserts |
| One partition is hot | Lag spikes on a single partition | Adjust partition key/distribution, speed up per-partition handling |
| Consumer RAM keeps climbing | Unbounded queues, GC/heap growth | Bound buffers/in-flight work, slow down polling |
| Watermark advances slowly | Delayed window outputs | Check idle partitions, out-of-order tolerances, ingestion skew |
| Retention nears exhaustion before catch-up | Log head approaches checkpoint | Trigger backfill plan from Capture / source archive |

## 7. Backpressure by Layer

### 7.1. Producer

Producers cannot always stop instantly. IoT devices or third-party services may keep emitting. Therefore implement:

- **Batched sends** respecting SDK/service size caps.
- **Retries with exponential backoff and jitter** for transient errors—never infinite retries.
- **Client-side bounded queues** to prevent OOM.
- Track send wait times, retry rates, and dropped events against SLAs.
- Use **durable local buffers or outboxes** when producers must never drop events.
- When telemetry permits sampling, apply **source-side sampling/aggregation** per business rules.
- Enforce **classified load shedding**: drop only permissible non-critical events; never drop mandatory payment or audit events.

**Event Hubs does not automatically push a stop signal back to every producer** when consumers slow down. It provides bounded capacity and retention; applications must regulate rates and plan source buffering.

### 7.2. Broker

Event Hubs absorbs rate mismatches temporarily via provisioned capacity and retention, though it is not an **infinite backlog store**.

Parameters to check:

- Throughput units / processing units / capacity matching tier.
- Partition count and partition key distribution.
- Average and peak event sizes.
- Retention long enough for worst-case outage + catch-up.
- Capture when archival beyond retention is needed.
- Incoming/outgoing throughput caps and throttling limits.

Scaling broker capacity does not fix every bottleneck: a hot partition, slow database, or sequential consumer still constrains throughput.

### 7.3. Consumer

At the consumer, backpressure means bounding:

- Concurrent **in-flight** events.
- Event batches buffered in memory.
- Concurrent connections/requests to databases.
- Internal queue sizes.
- Timeouts and retry budgets.
- Checkpoint and flush frequencies.

In pull models, consumers **slow down or pause reads** instead of endlessly stuffing work into RAM queues. With SDK event processor callbacks, understand how the SDK dispatches events and ensure processing/buffering stays bounded per thread rather than submitting to an unbounded executor.

### 7.4. Sink / downstream

If a database sustainably writes **2,000 records/s**, scaling Java workers from 4 to 40 simply crushes the DB harder. Apply:

- Batched writes and upserts.
- Connection pool and concurrent-request caps.
- Rate limiting aligned with shared quotas.
- Honoring **Retry-After** headers where APIs provide them.
- Circuit breakers during prolonged dependency outages.
- Idempotent writes so retries never duplicate data.
- Isolating hot read paths from batch/backfill sinks when needed.

### 7.5. Flow-control diagram

~~~mermaid
flowchart LR
    P["Producers"] -->|"Bounded batching"| E["Event Hubs"]
    E --> C["Consumer: bounded in-flight"]
    C --> Q{"Sink latency / 429?"}
    Q -->|Normal| W["Batch/upsert durable output"]
    Q -->|Overloaded| BK["Reduce concurrency + backoff"]
    BK --> C
    W --> CP["Checkpoint after durable persistence"]
    CP -. "Consumer continues reading" .-> E
~~~

**Backpressure does not mean “hold events in RAM forever.”** When downstream slows, Event Hubs holds events in retention while consumers throttle down; ensure retention and capacity suffice for recovery.

## 8. Scale-Out Limits: Partitions and Hot Keys

### 8.1. More Pods does not mean infinite throughput

With **EventProcessorClient** using a checkpoint/ownership store, each partition at any moment is typically owned by one processor instance in the consumer group to coordinate reads and checkpoints.

Example for a 6-partition Event Hub:

~~~text
Consumer group: realtime

Worker A: P0, P1
Worker B: P2, P3
Worker C: P4, P5

Adding Workers D/E/F:
    partitions rebalance across workers.

Adding Workers G/H/I:
    not enough partitions for every worker to own one.
~~~

Maximum useful partition-owning instances per **EventProcessorClient consumer group** generally equals the partition count, though internal per-partition concurrency introduces ordering and checkpoint trade-offs.

Never scale AKS replicas endlessly merely because lag appears.

### 8.2. Hot partitions

If partition key is a massive store, most traffic may funnel into P2:

| Partition | Incoming events/s | Consumer capacity/s | Lag |
|---|---:|---:|---|
| P0 | 500 | 2,000 | Low |
| P1 | 700 | 2,000 | Low |
| P2 | 8,000 | 2,000 | Climbing fast |
| P3 | 600 | 2,000 | Low |

Even with spare cluster capacity overall, **P2 falls behind** due to key skew and single-owner ordering.

Mitigations:

1. Pick a more evenly distributed partition key where ordering rules permit.
2. Split ultra-hot workloads across subkeys/shards that re-aggregate downstream.
3. Optimize per-partition throughput: batching, reduced I/O, bounded async work.
4. Provision a new hub with higher partition count/config when major redesign is needed.
5. Plan migration carefully so business ordering/sequences remain intact.

Ability to **change partition count** depends on Event Hubs tier and features at deployment time; never assume arbitrary resizing leaves partition-key hashing unchanged.

### 8.3. Ordering and backpressure

To preserve **strict per-partition processing order**, never dispatch events from one partition onto a parallel executor and checkpoint a higher sequence before earlier events finish.

Parallelize **across partitions** or track contiguous completed ranges; otherwise, premature checkpoints drop unfinished work after crashes.

## 9. Checkpoints: The “Completed So Far” Contract

A **checkpoint** records the position a consumer persists so the next startup resumes at the right spot. With Azure `EventProcessorClient`, checkpoints typically live in **Azure Blob Storage** alongside ownership/load-balancing metadata.

### 9.1. Safe workflow

~~~mermaid
flowchart LR
    R["Read event N"] --> V["Validate"]
    V --> P["Process"]
    P --> S["Durable, idempotent sink commit"]
    S --> C["Checkpoint N"]
    C --> NEXT["Continue reading"]
~~~

If a checkpoint is written **before** sink confirmation, a crash drops unpersisted events because the consumer marked them done. This is **silent data loss risk**.

### 9.2. At-least-once and crash windows

| Order | On crash | Consequence | Protection |
|---|---|---|---|
| Read → checkpoint → sink | Crash after checkpoint, before sink | Event skipped permanently on restart | **Never checkpoint before durable output** |
| Read → sink → checkpoint | Crash after sink, before checkpoint | Event re-read | Idempotent sink / unique keys |
| Read → sink → checkpoint | No crash | Clean progress | Monitor and persist checkpoints |
| Read → sink fails | No checkpoint | Event can be retried | Bounded retries, quarantine/poison policy |
| Read → async multi-writes → checkpoint far ahead | Earlier event still unfinished | Unfinished event lost on restart | Commit only on contiguous completion |

**Event Hubs does not deliver end-to-end exactly-once business effects across external databases via checkpoints alone.** Standard designs use **at-least-once + idempotent sinks**, or verified stateful/transactional stream engines.

### 9.3. Choosing checkpoint intervals

Checkpointing every event minimizes post-crash reprocessing at the expense of heavy Blob Storage writes and latency.

Checkpointing every 100 events or 30 seconds cuts I/O while increasing replay window on crashes. Balance based on:

- Event rate.
- Blob transaction cost.
- Acceptable reprocessing count.
- Target replay/catch-up time.
- Sink idempotency guarantees.
- Frequency of partition ownership rebalances.

No single “checkpoint every N events” rule fits every workload.

### 9.4. Per-consumer-group checkpoint stores

Processors sharing one consumer group share a checkpoint container to coordinate ownership per SDK conventions. However, **an independent replay job must never share production's consumer group or checkpoint store**, as it will contend for ownership and corrupt production positions.

Recommendation: use a separate **consumer group**, separate **checkpoint store path/container** for replays, and separate output targets to avoid overwrites.

## 11. Java Producer: Batched Sends and Partition Keys

When sending to Event Hubs, the SDK provides **`EventDataBatch`** bounded by allowed size. Producers should check **`tryAdd`** return values instead of building oversized batches.

### 11.1. Illustrative Java example

~~~java
import com.azure.identity.DefaultAzureCredentialBuilder;
import com.azure.messaging.eventhubs.EventData;
import com.azure.messaging.eventhubs.EventDataBatch;
import com.azure.messaging.eventhubs.EventHubClientBuilder;
import com.azure.messaging.eventhubs.EventHubProducerClient;
import com.azure.messaging.eventhubs.models.CreateBatchOptions;

import java.util.UUID;

public final class OrdersProducerDemo {
    public static void main(String[] args) {
        String fqdn = System.getenv("EVENTHUBS_FQDN");
        String hub = System.getenv("EVENTHUB_NAME");

        if (fqdn == null || hub == null) {
            throw new IllegalArgumentException("Missing Event Hubs config");
        }

        try (EventHubProducerClient sender =
                new EventHubClientBuilder()
                  .credential(fqdn, hub,
                      new DefaultAzureCredentialBuilder().build())
                  .buildProducerClient()) {

            String storeId = "hcm-07";
            EventDataBatch batch = sender.createBatch(
                new CreateBatchOptions().setPartitionKey(storeId));

            for (int i = 0; i < 10; i++) {
                String eventId = UUID.randomUUID().toString();
                EventData event = new EventData(
                    "{\"eventId\":\"" + eventId +
                    "\",\"storeId\":\"hcm-07\"," +
                    "\"eventType\":\"OrderPaid\"}");
                event.getProperties().put("eventId", eventId);

                if (!batch.tryAdd(event)) {
                    if (batch.getCount() == 0) {
                        throw new IllegalStateException(
                            "Single event exceeds batch size");
                    }
                    sender.send(batch);
                    batch = sender.createBatch(
                        new CreateBatchOptions()
                          .setPartitionKey(storeId));
                    if (!batch.tryAdd(event)) {
                        throw new IllegalStateException(
                            "Cannot add event to empty batch");
                    }
                }
            }

            if (batch.getCount() > 0) {
                sender.send(batch);
            }
        }
    }
}
~~~

**Notes:**

- This demo producer sends simplified payloads; event-time pipelines must include a reliable **`eventTimeUtc`** and formal schema.
- **`eventId`** must remain constant across producer retries of the same business event; generating random UUIDs inside the loop illustrates distinct new events.
- **Partition key** routes by `storeId`, though one busy store can create a hot partition.
- A failed send leaves ambiguous whether the broker accepted the message; Event Hubs has no Service Bus queue-style duplicate detection. Consumers must be idempotent.
- The SDK retries certain errors per config, yet producers still need retry/buffer caps and send-latency telemetry.

### 11.2. When a single event does not fit a batch

If **`batch.tryAdd(event)`** returns false on an empty batch, the event exceeds allowed limits: never retry endlessly. Consider:

- Compressing or trimming payload size per rules.
- Offloading large payloads to Blob Storage and sending **reference + checksum** via Event Hubs.
- Splitting into smaller events with explicit reassembly schemas when truly needed.
- Checking message size caps for your tier and settings.

Never silently drop mandatory transactional events.

### 12.2. EventProcessorClient example

~~~java
import com.azure.identity.DefaultAzureCredentialBuilder;
import com.azure.core.credential.TokenCredential;
import com.azure.messaging.eventhubs.EventHubClientBuilder;

import com.azure.storage.blob.BlobContainerAsyncClient;

public final class RealtimeOrdersConsumer {
    public static void main(String[] args) throws Exception {
        TokenCredential identity =
                new DefaultAzureCredentialBuilder().build();

        String fqdn = required("EVENTHUBS_FQDN");
        String hub = required("EVENTHUB_NAME");
        String blobEndpoint = required("CHECKPOINT_BLOB_ENDPOINT");
        String checkpointContainer = required("CHECKPOINT_CONTAINER");

        BlobContainerAsyncClient blobs =
                new BlobContainerClientBuilder()
                    .endpoint(blobEndpoint)
                    .containerName(checkpointContainer)
                    .credential(identity)
                    .buildAsyncClient();

        EventProcessorClient processor =
                new EventProcessorClientBuilder()
                    .credential(fqdn, hub, identity)
                    .consumerGroup("cg-orders-realtime")
                    .checkpointStore(new BlobCheckpointStore(blobs))
                    .processEvent(context -> {
                        String partition =
                                context.getPartitionContext()
                                       .getPartitionId();
                        String body =
                                context.getEventData()
                                       .getBodyAsString();

                        try {
                            // LAB: log simulating processing.
                            // PRODUCTION: validate, write idempotently
                            // to DB/Storage, WAIT for durable commit,
                            // and only then call updateCheckpoint().
                            System.out.printf(
                                "partition=%s event=%s%n",
                                partition, body);

                            context.updateCheckpoint();
                        } catch (RuntimeException error) {
                            System.err.println(
                                "Event failed: " + error.getMessage());
                            // Do not checkpoint failed event.
                            // Implement separate stop/retry/quarantine.
                        }
                    })
                    .processError(errorContext ->
                        System.err.println(
                            "Event processor error: "
                              + errorContext.getThrowable()))
                    .buildEventProcessorClient();

        processor.start();
        try {
            Thread.sleep(60_000);
        } finally {
            processor.stop();
        }
    }

    static String required(String name) {
        String value = System.getenv(name);
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(
                    "Missing " + name);
        }
        return value;
    }
}
~~~

**Important:** this example **logs and immediately checkpoints to demonstrate the API**, so **it is unsafe for real workloads if stdout is the only record**. In production, replace logging with **durable, idempotent persistence**, wait for commit confirmation, and then checkpoint. Also note the `catch` block **does not automatically trigger an immediate retry** of that event if the processor advances to subsequent events; implement explicit error handling—stopping partition processing/pipeline or durably quarantining poison events—before advancing checkpoints.

### 12.3. Permissions and networking for the Blob checkpoint store

- The Blob container must exist.
- The identity needs read/write/lease permissions for checkpoints and ownership.
- If the storage account uses a Private Endpoint, consumers must resolve private DNS and connect cleanly.
- Never apply lifecycle policies that delete checkpoint blobs prematurely.
- Plan for ownership rebalances, Blob connectivity blips, and position rollbacks.
- Independent replays must use a separate consumer group and checkpoint namespace.

### 12.4. Checkpointing by batch or time interval

In production, you do not have to update on every single event. A policy might checkpoint **after 100 durably committed events** or **every 30 seconds**, provided checkpoints only advance to the **highest contiguous completed position** on that partition.

Watch out for:

- Async writes finishing out of order.
- Two workers contesting a partition during rebalancing.
- A failing event whose failure is bypassed when later events update the checkpoint.
- Checkpoint storage throttling or authorization errors.
- Shutdown occurring while writes remain in flight.

**Advancing a checkpoint past event N means accepting that the consumer pipeline will not automatically re-read prior events.** Never checkpoint across an unprocessed gap.

## 13. Designing Practical Bounded Processing

### 13.1. Semaphore pattern

For async I/O consumers, use a **semaphore** to cap concurrent in-flight records:

~~~java
import java.util.concurrent.Semaphore;

Semaphore permits = new Semaphore(16);

// Illustrative flow-control pseudocode:
// Inside the event callback:
//   permits.acquire()
//   try {
//       durableSink.writeIdempotently(event)
//       contiguousCheckpointTracker.markCommitted(event.partition, event.sequence)
//   } finally {
//       permits.release()
//   }
~~~

**This is pseudocode inside comments, not a complete program.** Never call `updateCheckpoint` for event `N` simply because `N` finished if `N-1` is still running.

### 13.2. Bounded queue and worker pool

Another pattern:

~~~text
EventProcessor callback
    |
    v
Bounded work queue: capacity = 5,000
    |
    v
Fixed worker pool: 16 workers
    |
    v
DB connection pool: max 20
    |
    v
Durable output + per-partition contiguous checkpoint
~~~

When the queue fills:

- Slow down dispatching/polling at the appropriate SDK layer.
- Pause accepting additional work into the queue.
- Alert on backlog rather than growing RAM indefinitely.
- Never drop mandatory data.
- If shedding is unavoidable, enforce transparent policies per event type and SLO.

**In-memory queues are not durable storage.** After a crash, uncheckpointed events can be re-read within retention; events checkpointed before commit face permanent loss.

### 13.3. Where should retries live?

- **Producer retries:** transient send failures, using a stable `eventId`.
- **Broker throttling retries:** respect backoff, rate limits, and capacity.
- **Consumer processing retries:** transient database/API errors with deadlines and jitter.
- **Poison events:** bad schemas or invalid values; never retry forever.
- **Replay / backfill:** separate process with planned output isolation and deduplication.

Event Hubs **has no per-message DLQ like Service Bus**. To quarantine poison events, build a **poison topic/hub, Blob container, or failure table** capturing metadata and correlation IDs for investigation, then advance checkpoints per approved policy.

## 14. What Is Replay and When Is It Needed?

**Replay** means re-reading historical events to re-run processing logic, rebuild state, or test a new algorithm.

Common cases:

1. A deployed bug miscalculated revenue; need to recompute the last 24 hours.
2. A processor stopped for 40 minutes; need to drain the backlog.
3. A new data warehouse sink needs historical events.
4. A new business rule must be applied retroactively to events still within retention.
5. Audits demand before/after comparisons for a logic change.
6. Late events arrived past watermarks/windows and require backfilling.

### 14.1. Replay does not mean re-sending from the producer

While data remains inside **Event Hubs retention**, a new consumer reads partitions from an earlier position without asking producers to resend. That keeps the original log intact.

Once data **ages past retention**, read from **Capture / Blob / ADLS / source archives** if previously retained. Republishing into a fresh Event Hub is an option, though not always needed.

### 14.2. Checkpoints and replay

Example:

~~~text
Partition P0 retains sequences 1000 ... 5000

Production consumer:
    checkpoint = 4800
    → resumes after checkpointed region

New replay consumer:
    start = 2000
    → re-reads from 2000 across retained log

A separate consumer group never alters
production's checkpoint.
~~~

Sharing **production's consumer group and checkpoint store** for a replay disrupts progress, causes ownership fights, and risks duplicate/overwritten production outputs. Keep them separate.

## 15. Three Replay Starting Positions: Offset, Sequence, and Enqueued Time

In Event Hubs, consumers select **`EventPosition`** via API:

- **Earliest:** oldest event **still within retention**.
- **Latest:** tail position at startup; receives only new events per SDK semantics.
- **Offset:** specific position within a partition.
- **Sequence number:** position by sequence number and inclusive/exclusive flag.
- **Enqueued time:** position based on when the broker enqueued the event.

### 15.1. Do not confuse event time with enqueued time

If asked to “recompute all payments occurring between 10:00 and 11:00 business time,” seeking **enqueued time** to 10:00–11:00 is not enough. A payment from 10:05 uploaded at 10:25 sits at enqueued time 10:25; one uploaded at 11:15 sits after 11:00.

Therefore, backfilling an **event-time interval** usually requires reading a **sufficiently wide enqueued-time window**, then filtering by `eventTimeUtc` and accounting for late arrivals.

### 15.2. Inclusivity and starting position

When seeking by sequence/offset, SDKs specify whether the starting position is inclusive or exclusive. Check **`isInclusive`** and verify with lab data so you neither skip nor accidentally double-read boundary events.

When seeking by timestamp, events across partitions can be enqueued simultaneously; never assume a single global sequence number exists across partitions.

### 15.3. Retention does not guarantee infinite history

A newly created consumer group seeking earliest reads from **the start of the retained window**, not from the day the Event Hub was created. To replay 6 months back when retention is only a few days, set up Capture/archival beforehand.

## 17. Replaying via Event Hubs Capture or Archives

### 17.1. When retention is insufficient

If an outage lasted 5 days while Event Hubs retention is shorter:

1. Stop trying to rewind checkpoints to expired offsets.
2. Identify the missing range using the last checkpoint, enqueued times, and metrics.
3. Inspect **Capture** archives or original event stores.
4. Confirm archive coverage across all partitions, timestamps, and schemas.
5. Run backfill from archives into a **separate output**, or emit through a **dedicated replay Event Hub**.
6. Reconcile event counts and IDs by partition and time range.
7. Promote results after validation, protecting overlap boundaries with real-time streams.

### 17.2. Capture file format and storage layout

Event Hubs Capture typically writes per partition and time window to Blob/ADLS in formats/settings configured on the service. Never assume a Capture file is plain JSON lines; parse using supported formats such as Avro per active Capture configuration.

Preserve:

- Hub/partition and capture timestamps.
- Enqueued time, sequence, and offset metadata if pipelines depend on them.
- Event body, content type, and properties.
- Schema version and serialization definition.
- Checksums / content hashes.
- Access permissions, retention, and encryption.

### 17.3. Never blindly republish into the production hub

Republishing archived events into **the same production hub** assigns **brand-new enqueued times, offsets, and sequences**, triggering every live consumer and risking duplicate emails or charges.

If republishing is mandatory, target an isolated hub/consumer path tagged with **`replayRunId`**, **`originalEventId`**, and **`originalEventTime`**, and ensure sinks distinguish replay traffic from live business events.

### 17.4. Throttling replay rate

A backfill can read vastly faster than the output DB can sustain. Cap replay throughput and prioritize real-time SLOs:

~~~text
Realtime sink budget: 8,000 writes/s
Replay sink budget:   2,000 writes/s
Total target:        10,000 writes/s
~~~

This is an illustrative allocation, not an Azure limit. Apply dynamic throttling, monitor latency/429s, and pause replay if real-time workloads degrade.

## 18. Event Time and Late Events

### 18.1. What is a late event?

An event is **late relative to an event-time window** if the system receives or processes it **after the watermark / window-close condition** has passed, even though its **`eventTime`** belongs to an earlier window.

Do not conflate:

- **Late ingress:** `eventTime` lags far behind `enqueuedTime` because the source sent late.
- **Consumer lag:** event enqueued on time, yet the processor read it late due to backlog.
- **Out-of-order arrival:** event times do not increase monotonically in broker/processing order.
- **Clock skew:** source stamped an inaccurate clock value.
- **Replay:** intentionally re-reading historical data.

Each root cause needs a different fix. Raising Streaming Units reduces consumer lag, yet **cannot fix an IoT device's wrong clock**.

### 18.2. Example timeline table

| Event | eventTime (VN time) | enqueuedTime | processingTime | Notes |
|---|---|---|---|---|
| A | 10:01 | 10:01:02 | 10:01:03 | Near real-time |
| B | 10:04 | 10:04:01 | 10:04:02 | Near real-time |
| C | 10:03 | 10:05:10 | 10:05:11 | Out of order, slightly delayed |
| D | 10:02 | 10:18:10 | 10:18:13 | Very late due to offline branch |
| E | 10:17 | 10:17:01 | 10:21:40 | Consumer lag post-ingestion |

For 10:00–10:05 revenue, A, B, C, and D all belong to **the same event-time window**, while E belongs to another. However, watermark policy may cause D to arrive **after the window's initial result was emitted**.

## 19. What Is a Watermark?

A **watermark** is an event-time marker the system uses to estimate that events older than that timestamp **have mostly arrived**, enabling windows to close and emit. It is a **processing heuristic**, not an absolute guarantee that no producer will ever send an older event.

A simple model for **a steadily progressing stream**:

~~~text
watermark ≈ maxObservedEventTime - allowedOutOfOrderDelay
~~~

Example:

~~~text
Max event time seen:  10:20
Allowed out-of-order: 3 minutes
Reference watermark:  10:17
~~~

Real streaming engines compute watermarks using per-partition state, incoming data, event-time policies, idle-source handling, and engine-specific rules. **Never treat that simplified formula as universal truth across all engines.**

### 19.1. Window closure and watermarks

A **tumbling window** covers:

~~~text
Window [10:00, 10:05)
    contains events with:
    10:00 <= eventTime < 10:05
~~~

Once the engine's watermark passes the window's closing boundary, it emits the window result. If an event with **`eventTime=10:03`** arrives afterward, handling follows the **late-event policy**.

### 19.2. Watermarks and idle partitions

Across multiple partitions:

- A quiet partition emits no fresh event times.
- Another partition receives thousands of events/s.
- If the engine waits strictly on the idle partition, watermarks stall.
- If the engine advances past idle partitions too eagerly, delayed events arriving later look late.

Engines handle idle partitions differently. Test both steady traffic and prolonged silent-partition scenarios.

### 19.3. Allowed lateness is not retention

- **Allowed lateness:** how the pipeline handles events arriving behind event-time/window progress.
- **Event Hubs retention:** how long the broker retains history for reading.

Extending retention does not make windows wait longer. Raising allowed lateness cannot recover events already purged from retention.

## 20. Late-Event Handling Strategies

No single policy fits every system.

| Strategy | Behavior | Fits | Trade-off |
|---|---|---|---|
| **Drop** | Exclude event from real-time result, log reason | Near-real-time telemetry tolerating approximation | Loses stats unless backfilled |
| **Adjust timestamp** | Rewrite timestamp per engine policy | Dashboards valuing speed over exact event time | Numbers no longer reflect exact occurrence time |
| **Side output / quarantine** | Route late events to a separate store | Audits, investigations, manual review | Requires a compensating pipeline |
| **Update / retract** | Emit updates/corrections for closed windows | Finance/metering needing exactness | Sink must support upserts/versions/retractions |
| **Recompute / backfill** | Re-run windows/intervals from archive | Historical datasets needing consistency | Costs compute, I/O, and reconciliation effort |
| **Late grace period** | Keep windows open longer for late arrivals | Workloads with measurable lateness tails | Increases latency, state, and memory |

### 20.1. Real-time dashboards and financial reports need different policies

**Operational dashboards:** can emit fast early figures labeled **provisional** and revise them later.

**Revenue / reconciliation reports:** require accurate event times and audit trails; late arrivals may require versioned/transactional adjustments to historical windows.

Never use **Adjust event time to processing time** for financial reporting without explicitly documenting the change in data semantics.

### 20.2. Marking provisional vs. final results

Example output:

~~~json
{
  "storeId": "hcm-07",
  "windowStartUtc": "2026-11-20T03:00:00Z",
  "windowEndUtc": "2026-11-20T03:05:00Z",
  "revenue": 12500000,
  "revision": 3,
  "isFinal": false,
  "computedAtUtc": "2026-11-20T03:07:40Z"
}
~~~

If a late event later alters the total, the processor emits **`revision=4`**. Sinks upsert on **`storeId + windowStart + windowEnd`**, comparing revisions so an older replay never overwrites a newer revision.

**`isFinal`** is a business contract flag, not an absolute promise that later corrections can never happen. For accounting period closes, build a dedicated reconciliation and ledger workflow.

## 21. Azure Stream Analytics: Event-Time Windowing

**Azure Stream Analytics (ASA)** is a managed stream processing option on Azure supporting SQL-like queries, temporal/window functions, and event ordering policies. It reads from Event Hubs, processes windows, and writes to supported outputs.

### 21.1. Basic window query

Suppose input events carry **`storeId`**, **`eventTimeUtc`**, and **`amount`**:

~~~sql
SELECT
    storeId,
    System.Timestamp() AS windowEndUtc,
    COUNT(*) AS eventCount,
    SUM(CAST(amount AS bigint)) AS totalAmount
INTO
    output
FROM
    input TIMESTAMP BY eventTimeUtc
GROUP BY
    storeId,
    TumblingWindow(minute, 5)
~~~

Meaning:

- **`TIMESTAMP BY eventTimeUtc`** picks **event time inside the payload**.
- **`TumblingWindow(minute, 5)`** groups into non-overlapping 5-minute intervals.
- **`System.Timestamp()`** supplies the logical window timestamp per engine semantics.
- **`COUNT/SUM`** compute event counts and amounts per window.

**Verify the schema and timestamp types** ASA receives. If **`eventTimeUtc`** is a JSON string, confirm formatting, serialization, and parser behavior instead of assuming every ISO 8601 variant works identically across all expressions.

### 21.2. Event ordering policies

ASA provides **event ordering policies** covering:

- **Late arrival tolerance.**
- **Out-of-order tolerance.**
- Handling action such as **Drop** or **Adjust** per configured policy.

These address two distinct issues:

| Policy | Targets | Question |
|---|---|---|
| Late arrival | Event time far behind enqueued time | How late can an event reach the broker and still count? |
| Out-of-order | Event times arriving out of sequence | How should the engine buffer, adjust, or drop when event time steps backward? |

Check the exact meaning and limits of each setting in your **deployed ASA job**; never assume the two tolerances simply add together into one universal “allowed lateness.”

### 21.3. Drop or Adjust?

- **Drop:** events violating policy are dropped from the target output.
- **Adjust:** processing timestamps are shifted per engine rules so events continue through the pipeline.

If dashboards must reflect true event time, document explicitly when timestamp adjustment is acceptable. For auditable datasets, pair **raw archives** with reconciliation instead of keeping only Adjusted outputs.

### 21.4. Watermark delay

**Watermark delay** reflects how far event-time/output progress lags behind wall-clock time per engine semantics. It grows with late inputs, idle partitions, processing bottlenecks, or wide out-of-order tolerances.

An empty dashboard does not automatically mean “ASA hung.” Windows may simply be waiting for watermarks to advance. Inspect watermark delay, input/output events, late/out-of-order metrics, errors, and compute utilization in Azure Monitor per supported resource metrics.

## 22. Designing Watermarks for Multi-Source Data

### 22.1. Sources with different lateness SLAs

Example:

| Source | Typical lateness | Max expected outage | Recommendation |
|---|---|---|---|
| Datacenter API | Seconds | Few minutes | Low-latency windows |
| Store POS | 1–2 minutes | 30 minutes | Grace period, corrections |
| Offline mobile | 10–60 minutes | Hours | Raw store + late backfill |
| Periodic partner feeds | Hours | Days | Separate batch reconciliation |

Combining all sources into one pipeline sized for the slowest watermark delays real-time dashboards excessively. Conversely, a 30-second watermark drops mobile events constantly.

A clean solution is **two branches**:

~~~mermaid
flowchart TD
    INPUT["Event Hubs: raw events"] --> FAST["Realtime stream<br/>short watermark"]
    INPUT --> RAW["Capture/ADLS raw archive"]
    FAST --> DASH["Provisional dashboard"]
    RAW --> LATE["Reconciliation / backfill<br/>historical windows"]
    LATE --> FINAL["Corrected aggregates + audit"]
    DASH --> FINAL
~~~

### 22.2. Pick lateness thresholds from measured data, not intuition

Measure **`ingestion lateness = enqueuedTime - eventTime`** by source, store, device type, and percentile.

Example measurements over one week:

~~~text
p50 lateness:       2 seconds
p95 lateness:      35 seconds
p99 lateness:       4 minutes
p99.9 lateness:    25 minutes
extreme outage:    several hours
~~~

If the dashboard SLO requires updates within 60 seconds, do not hold every window open for 25 minutes. Deliver **fast results within 60 seconds**, backed by **late correction / reconciliation** over a longer horizon.

### 22.3. Future timestamps

Event times can lie **in the future** due to misconfigured device clocks. Blindly advancing watermarks to `maxObservedEventTime` lets one future-dated event prematurely close older windows and misclassify valid events as late.

Validation should:

- Compare `eventTime` against `enqueuedTime` and system time.
- Cap acceptable future clock skew by policy.
- Quarantine events with severe clock errors.
- Track timestamp-error rates per source.
- Never overwrite original timestamps without recording the reason and adjusted value.

## 23. End-to-End Idempotency and State Consistency

### 23.1. Designing output keys

For individual events, deduplicate on **`eventId`**.

For 5-minute aggregates, key computed rows on **`(storeId, windowStartUtc, metricVersion)`**, tracking **`revision`** or generation for corrections.

Illustrative SQL concept:

~~~sql
-- Conceptual model; exact UPSERT syntax depends on database.
UPSERT INTO SalesWindow(
    storeId,
    windowStartUtc,
    windowEndUtc,
    metricVersion,
    revision,
    totalAmount
)
KEY (storeId, windowStartUtc, metricVersion)
ONLY IF incoming.revision > stored.revision;
~~~

This is **SQL pseudocode**, not runnable Azure SQL T-SQL. Production code must use engine-appropriate transactions, unique indexes, or `MERGE` patterns verified for concurrency and isolation.

### 23.2. At-least-once does not have to mean double-counting

When the same event is re-read, consumers can guard writes:

~~~text
BEGIN database transaction
    IF eventId is not yet in ProcessedEvents:
        INSERT ProcessedEvents(eventId)
        UPDATE totals OR INSERT delta ledger
COMMIT database transaction

After DB commit succeeds:
    checkpoint Event Hubs
~~~

On a crash after DB commit and before checkpoint, the event is re-read, yet **`ProcessedEvents`** prevents double-counting.

For windowed totals, keep an **eventId-keyed ledger** or recompute from raw events rather than blindly incrementing an irreversible counter.

### 23.3. Late corrections and retractions

A published window with `total=100` may receive a late `+20` event, updating to `120`.

If the sink supports **upserts**:

~~~text
(storeId, windowStart, revision=1, total=100)
(storeId, windowStart, revision=2, total=120)
~~~

If downstream is an append-only ledger, emit a compensating entry:

~~~text
Correction:
    windowKey = ...
    adjustment = +20
    correctionId = unique
    originalRevision = 1
    newRevision = 2
~~~

Correction consumers must be idempotent and respect version order. No single correction style fits every sink; financial ledgers typically require audited adjustment records rather than silent overwrites.

### 23.4. Replays must never overwrite newer outputs

If a backfill of an older algorithm finishes after real-time algorithm v2, replay writes could overwrite accurate results with stale ones.

Safeguards:

- Tag outputs with **`runId`**, **`algorithmVersion`**, and **`generation/revision`**.
- Write to staged/versioned outputs.
- Verify source ranges and completeness.
- Promote via transaction or atomic pointer switch where supported by the sink.
- Allow only approved generations to become current.
- Preserve audit logs and rollback paths.

## 24. When Does Backpressure Become a Data-Loss Risk?

Event Hubs retains data for a finite retention period. If a consumer lags continuously long enough, old events age out of the log before being read.

### 24.1. Retention budget

Let:

- **`R`:** actual retention window.
- **`T_outage`:** pipeline downtime duration.
- **`T_catchup`:** time required to drain accumulated backlog.
- **`T_margin`:** safety buffer for retries, maintenance, and variance.

Rough planning constraint:

~~~text
R > T_outage + T_catchup + T_margin
~~~

This is a **planning bound**, not an absolute guarantee; verify actual per-event retention and service eviction semantics. As `T_outage + T_catchup` nears `R`, data-loss risk spikes.

### 24.2. Risk example

A pipeline stops for **8 hours**, then needs **10 hours** to catch up. If configured retention is shorter than their sum, the earliest queued events expire before consumers reach them.

Options:

1. Raise effective throughput to shorten catch-up.
2. Increase retention **where tier, quotas, and budget allow**.
3. Enable Capture/archival ahead of incidents.
4. Build backfill pipelines from the source of truth.
5. Pause competing replay workloads during real-time catch-up.
6. Alert on **estimated time to retention boundary**, not CPU alone.

### 24.3. Do not treat lag as one global number

A single partition can approach retention expiration while average lag looks fine. Measure:

- Max lag per partition.
- Oldest unprocessed event age.
- Last successful checkpoint timestamp.
- Gap between last enqueued and last processed sequence.
- Event-time skew per source.
- Time-to-catch-up at current headroom.

## 25. Azure Functions Event Hubs Trigger and Backpressure

The **Azure Functions Event Hubs trigger** manages scaling, checkpointing, and leases via extension and host settings. It suits smaller or event-driven workloads where teams prefer not operating `EventProcessorClient` directly.

However:

- Scale-out still depends on partition counts, hosting plan, and runtime.
- Concurrency, batch size, prefetch, and checkpoint behavior vary by extension version.
- When downstream is slow, scaling Function instances does not speed up the database.
- Function retries can trigger duplicate processing.
- Monitor execution timeouts, host restarts, and checkpoint ownership.
- Event Hubs is a stream; there is no automatic per-event DLQ like Service Bus queues.

### 25.1. Choosing Functions vs. long-running Java workers

| Criterion | Azure Functions trigger | Java App Service / AKS worker |
|---|---|---|
| Infrastructure management | Less hands-on management | Team manages apps, containers, and scaling |
| Checkpoints / triggers | Managed by runtime and extension | App configures EventProcessor / checkpoint store |
| Concurrency / batching | Governed by host settings, extension, plan | Full code flexibility with manual control |
| Networking / identity | Follows Functions hosting plan | Follows App Service / AKS networking |
| Late-event logic | Must implement in code or call external engine | Can use Java libraries or ASA |
| Best suited for | Simple event-driven workloads | Long-running jobs, custom pipelines, strict latency/concurrency |

Never copy **`host.json`** blindly from a different extension version. When tuning checkpoint or batch settings, consult docs for the exact **Event Hubs extension** version deployed.

| Event Hubs | Incoming/Outgoing Messages/Bytes | Measuring traffic and capacity |
| Event Hubs | Throttled requests, server/user errors | Detecting quota, auth, or network errors |
| Consumer SDK | Events processed/s, processing latency | Comparing μ against λ |
| Consumer SDK | Checkpoint age and last processed position | Detecting lag or stalled workers |
| Consumer SDK | Ownership rebalance / lease errors | Spotting unstable load balancing |
| Blob checkpoint store | Blob API errors/latency/throttling | Detecting checkpoint store bottlenecks |
| Downstream DB | 429/5xx, write latency, pool saturation | Identifying sink backpressure |
| Stream Analytics | Input/Output Events, Watermark Delay | Diagnosing event-time latency |
| Stream Analytics | Late/Out-of-order events, conversion errors | Auditing data policy behavior |
| Capture / Storage | Capture status, archive completeness | Verifying long-term replay readiness |
| Azure Monitor | Alerts, Log Analytics, diagnostics | Operations and auditing |
| Cost Management | Event Hubs tier/capacity, storage, compute | Budgeting and optimization |

Exact metric names vary by resource type, tier, and version. Never assume Event Hubs brokers automatically emit a ready-made **consumer lag** metric for **every consumer group**; consumers should emit telemetry/checkpoint progress compared against partition last-enqueued sequences.

### 26.2. Minimum viable dashboard

An operational dashboard should display:

~~~text
Ingress rate (events/s)
Processing completion rate (events/s)
Backlog / max + p95 lag by partition
Oldest unprocessed event age
Last successful checkpoint per partition
Consumer error and retry rate
Downstream p95/p99 write latency
Late event ratio by source
Watermark delay and window correction rate
Remaining replay/retention safety margin
Capture health / archive gaps
Total cost by component
~~~

### 26.3. Actionable alerts

Avoid 20 generic CPU-only alerts. Tie every alert to a runbook:

| Alert | Suggested action |
|---|---|
| Lag climbs steadily for 10–15 minutes | Compare λ/μ, find hot partitions and sink bottlenecks |
| Throttled requests spike | Check TU/PU, send batching, retries, and quotas |
| Checkpoints stall | Inspect processor ownership, Blob storage, exceptions |
| Oldest event age approaches retention | Prioritize raising μ, open backfill/retention incident |
| Watermark delay climbs | Check event-time skew, idle partitions, ASA job |
| Late events spike from one store | Check that store's network connectivity and clock |
| Replay drives up DB latency | Throttle or pause replay budget |
| Capture shows gaps | Investigate and preserve source data before retention expires |

Tune minutes and thresholds to your SLOs, normal traffic, retention, and environment; never treat illustrative numbers as Azure defaults.

## 27. Practical Troubleshooting

| Symptom | Possible causes | Remediation |
|---|---|---|
| Consumer memory climbs steadily | Unbounded queues / in-flight tasks | Bound buffers/concurrency and inspect GC |
| Lag grows on only one partition | Hot key, per-partition bottleneck | Check partition key distribution and per-partition handling |
| Adding replicas does not cut lag | More instances than partitions, DB bottleneck | Inspect ownership and downstream throughput |
| Checkpoints advance yet data is missing | Checkpointed before durable sink commit | Fix ordering; replay from raw/retained data to recover |
| Data double-counted after restart | At-least-once delivery, non-idempotent sink | Deduplicate on `eventId`/unique index, issue corrections |
| Replay misses older events | Event Hubs retention expired | Read Capture/archive/source; don't seek expired offsets |
| Replay corrupts dashboard | Wrote directly to production without versioning | Use staged outputs / atomic promotion |
| 10:00–10:05 window misses 10:18 arrival | Event-time late after window closed | Apply late policy, correction/reconciliation |
| Watermark stops advancing | Idle partition, oversized out-of-order tolerance | Check engine watermark / idle-partition handling |
| Future timestamps distort windows | Producer clock skew | Validate/quarantine, enforce future skew caps |
| ASA output delayed | Backpressure, watermark delay, SU saturation | Inspect metrics, input partitions, sink capacity, policies |
| Producer hits 429 / throttling | Event Hubs capacity/quota | Rate limit, backoff, capacity planning |
| Consumer gets 403 | Missing Data Receiver or Storage RBAC | Verify identity, role, scope, propagation |
| Blob checkpoint store errors | Storage auth/network/lease/throttling | Check Blob roles, private DNS, container health |
| Capture misses expected files | Disabled, window rules, permission/network error | Check Capture config and archive paths |
| Replay consumer group disrupts real-time | Shared ownership/checkpoint store | Isolate consumer groups, checkpoints, and outputs |

### 27.1. 10-step lag debugging flow

1. Measure **incoming events/s** per partition if available.
2. Measure **completed processing events/s**, not just poll rate.
3. Verify sink throughput and error rates.
4. Identify the partition with maximum lag.
5. Inspect partition key distribution and hot sources.
6. Inspect GC, memory, in-flight counts, and bounded queues.
7. Check Blob checkpoint success and ownership rebalances.
8. Check throttled requests and Event Hubs capacity.
9. Estimate **`T_catchup`** and remaining retention margin.
10. Test small changes in staging, re-measure, and scale strictly at the bottleneck.

### 27.2. Debugging a late-event spike

1. Collect `eventTime`, `enqueuedTime`, `processingTime`, and source ID.
2. Split lateness by segment: **producer → broker** vs. **broker → consumer**.
3. Check clock skew and timezones.
4. Check if the source experienced offline buffering or retries.
5. Determine whether consumer lag or stream processor slowdowns contributed.
6. Inspect watermark and event-ordering policies.
7. Determine if target windows already closed or remain updatable.
8. Trigger late correction, quarantine, or replay per business SLA.
9. Recompute accurate figures and audit all revisions.
10. Add per-source lateness alerts instead of global averages alone.

### 27.3. Debugging replay cost spikes

1. Check whether replay is reading the broker or Capture/ADLS.
2. Check replay time range, partition count, and data volume.
3. Check for repeated reads across consumer groups.
4. Check sink writes, egress, and retries.
5. Check cross-region ingestion/egress traffic.
6. Confirm replay has throughput caps and deadlines.
7. Throttle or pause replay if real-time workloads suffer.
8. Inspect Cost Management by resource and meter once updated.
9. Consider recomputing only affected windows instead of full history.
10. Log cost per run and count of corrected records.

## 28. Cost, Security, and Operational Boundaries

### 28.1. Total cost components

| Component | Cost drivers |
|---|---|
| Event Hubs | Tier/capacity, throughput/processing units, and retention per model |
| Capture | Storage capacity, transactions, and retention lifecycle |
| Consumer App Service / AKS / Functions | CPU/memory, instance count, executions per plan |
| Blob checkpoint store | Storage capacity and Blob transactions |
| Azure Stream Analytics | Streaming Units / compute and inputs/outputs per config |
| Azure Data Explorer / SQL / Cosmos DB | Ingestion, storage, writes, queries, or provisioned throughput |
| Data egress | Cross-region, cross-zone, or Internet transfers per service |
| Azure Monitor | Log ingestion, retention, alerts |
| Replay / backfill | Compute, data scans, reads/writes, and sink load |

There is no single flat “one message = X” unit price across services and tiers. Use the Azure Pricing Calculator and current Cost Management data.

### 28.2. Least-privilege permissions

- Producers need only **Azure Event Hubs Data Sender**.
- Consumers need only **Azure Event Hubs Data Receiver**.
- Checkpoint identities get scoped Blob data permissions; avoid storage account keys where possible.
- Capture/archive access uses separate read/write roles per design.
- Replay operators do not automatically get write access to production serving tables; write to staging outputs.
- Azure resource-management roles differ from data-plane permissions.

### 28.3. Networking

Components supporting VNet / private endpoints per tier and region include:

- Event Hubs namespaces.
- Checkpoint / Archive Storage accounts.
- Database / ADX / ASA outputs.
- App Service / AKS / Functions VNet integration.
- Azure Monitor / diagnostics log shipping.

Verify TLS, DNS, routing, firewalls, and AMQP/TCP or WebSockets where applicable. Never open public access across namespaces or storage accounts just to bypass an undiagnosed connectivity error.

### 28.4. Data and compliance

- Document event schemas and retention classifications.
- Exclude sensitive personal data from partition keys, `MessageId`, or logs unless required.
- Enforce deletion/archival policies and historical access controls.
- Replays can reintroduce data previously subject to deletion requests; build compliance-aware filtering for privacy regulations.
- Prevent replays from triggering unintended side effects such as payments or emails.
- Enforce encryption, Azure RBAC, auditing, and code/image provenance.
- Require owner approval before replaying production data.

## 29. Production Design Checklist

- [ ] Distinguished event time, enqueued time, and processing time in schemas and telemetry.
- [ ] Partition keys distribute evenly enough while preserving needed business order.
- [ ] Confirmed actual Event Hub partition count, tier, capacity, and retention.
- [ ] Sized peak ingress `λ` and sustained processing rate `μ`.
- [ ] Backpressure implements bounded queues, in-flight caps, backoff retries, and circuit breakers.
- [ ] Concurrency does not scale blindly when sinks throttle.
- [ ] Dashboards track per-partition lag, checkpoint age, and oldest unprocessed event age.
- [ ] Checkpoints update strictly after durable, idempotent output commits.
- [ ] Never checkpoint past a failed event not yet handled or quarantined per policy.
- [ ] Clear separation between poison events and transient errors.
- [ ] Consumer groups and Blob checkpoint stores isolated by purpose.
- [ ] Replays specify `runId`, time range, isolated output, rate limits, and validation.
- [ ] Capture/archival or source replay exists if recovery exceeds broker retention.
- [ ] `eventId` checks and upserts/retractions prevent replay double-counting.
- [ ] Allowed lateness, watermarks, and late-event handling policies grounded in measured lateness data.
- [ ] Handling defined for bad timestamps, future clock skew, and idle partitions.
- [ ] ASA or processing engine configured with appropriate event-ordering policies.
- [ ] Aggregates include window keys, algorithm version/revision, and audit trails.
- [ ] Alerts configured for retention risk, watermark delay, hot partitions, and checkpoint failures.
- [ ] Least-privilege RBAC and private networking/DNS configured for Event Hubs, Storage, and sinks.
- [ ] Recovery runbooks exist for consumer outages, replay failures, and downstream outages.
- [ ] Estimated costs across Event Hubs capacity, Capture, compute, logs, and replays.
- [ ] Practiced crash drills **after sink commit yet before checkpoint**.
- [ ] Tested late events arriving after window closure and emitting corrections.

## 30. Hands-On Exercises

### Exercise 1: Backpressure math

Event Hubs ingests 10,000 events/s. A sink only processes 6,000/s for 15 minutes.

1. Calculate backlog growth.
2. If sink throughput rises to 14,000/s while ingress stays 10,000/s, how long does catch-up take in the ideal model?
3. Why can a hot partition invalidate that estimate?
4. If retention is shorter than outage + catch-up, what is the recovery plan?

### Exercise 2: Designing a Java consumer

With `EventProcessorClient`:

1. Define the consumer group and Blob checkpoint store.
2. Specify required identities and Event Hubs / Blob permissions.
3. Cap concurrent database requests at 16.
4. Write idempotent outputs keyed by `eventId`.
5. Checkpoint strictly after durable commit.
6. Explain how to handle event `N` failing while `N+1` completes.
7. Simulate a crash after DB commit and before checkpointing.

### Exercise 3: Hot partitions

Data is keyed by `storeId`, and one flagship store sends 60% of traffic. The cluster runs 12 Pods while the Event Hub has 4 partitions.

- Why won't scaling out more Pods help?
- How do you measure the hot partition?
- How could you change the partition key if ordering is only required per `orderId`?
- Why must key migration be tested on consumers and outputs?

### Exercise 4: Replaying historical events

A bug caused a consumer to double-count revenue over the past 3 hours.

1. Determine the affected data range in both event time and enqueued time.
2. Create a separate consumer group and checkpoint store.
3. Replay from Event Hubs if within retention.
4. Write results to a versioned table.
5. Compare checksums/counts and lock the version.
6. Apply corrections to production without re-sending emails or charging cards again.

### Exercise 5: Data past retention

A consumer went down for 2 days and retention did not cover the full outage.

- Which data may be gone from the broker?
- How do you read from Capture?
- Why isn't resetting offsets enough?
- If republishing, what prevents triggering live production consumers?
- How do you reconcile overlap between real-time and backfill streams?

### Exercise 6: Watermarks and event time

A 10:00–10:05 window sees these events:

~~~text
Event A: eventTime 10:01, processed 10:01
Event B: eventTime 10:04, processed 10:05
Event C: eventTime 10:03, processed 10:06
Event D: eventTime 10:02, processed 10:18
~~~

1. Which events belong to the window by event time?
2. Why might C fit within out-of-order tolerance while D counts as late?
3. For a real-time dashboard, how do you model provisional/correction outputs?
4. For financial reports, how do you revise totals while keeping an audit trail?
5. If a device clock jumps to 11:00 while real time is 10:00, how can watermarks be affected?

### Exercise 7: Comparing Azure Stream Analytics with Java consumers

Design the same 5-minute tumbling window:

- ASA uses `TIMESTAMP BY`, event ordering policies, and output adapters.
- Java manages window state, watermarks, checkpoints, and idempotent sinks directly.

Compare operational burden, logic control, correction capability, monitoring, and cost. When should you pick Spark/ADX or add batch reconciliation?

### Exercise 8: Designing FinOps for replay

A 7-day backfill must read 500 million events from archive.

- Estimate total data scanned from average event size.
- Separate read, compute, sink write, logging, and network costs.
- Set a replay budget that avoids degrading real-time workloads.
- How do you pause and resume the backfill via `runId` and chunk checkpoints?
- Which KPIs prove completion without double-counting?
