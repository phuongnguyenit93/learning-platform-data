# Blob Versioning, Snapshots, and Soft Delete

An application running on Azure writes documents, product images, and processing outputs to Blob Storage. On Monday, a file is overwritten with incorrect content; on Tuesday, another file is deleted; on Wednesday, an administrator accidentally deletes an entire container. These three incidents look similar, yet **the right recovery mechanism differs for each**: **Blob versioning** preserves historical data versions, a **blob snapshot** captures a blob's content at a specific point in time, and **soft delete** enables restoring deleted objects within a configured retention window.

This lesson belongs to the **Object Storage with Blob Storage** chapter of the `CLOUD_PROVIDERS_AZURE` module. The module spans Microsoft Azure from subscriptions, resource groups, and Entra ID to virtual networking, compute, storage, and data, while guiding deployment, monitoring, security, and cost control for application architectures. Here, the objective is designing **the ability to roll back to a pre-incident data state**, separate from access permissions, availability, and encryption.

> Examples primarily use **block blobs** in general-purpose v2 storage accounts. Support for versioning, snapshots, soft delete, change feed, and point-in-time restore can vary by blob type, account type, hierarchical namespace (ADLS Gen2), region, and current service constraints. Verify support on your actual account before finalizing policies or running data-modifying commands.

## 1. Learning Objectives

After this lesson, you will be able to:

1. Distinguish **current blob**, **previous version**, **snapshot**, **soft-deleted blob**, and **soft-deleted container**.
2. Explain why versioning protects against overwrites and why snapshots are not created automatically before every edit.
3. Enable and manage **versioning**, **blob soft delete**, and **container soft delete** policies for supported workloads.
4. Choose the right operation—**undelete** vs. **copy/restore from version/snapshot**—for each scenario.
5. Define retention periods, RPO/RTO, replication limitations, and storage-account-level accidental deletion risks.
6. Use Azure Portal and illustrative Azure CLI commands to inspect recovery points, download older versions, and verify configurations.
7. Design lifecycle management to retain necessary versions without unbounded cost growth.
8. Combine least privilege, logging, immutability, and recovery testing when higher data safety is required.
9. Write an incident runbook for blob overwrites/deletions, container deletions, or bulk corruption without destroying remaining valid versions.

## 2. How Does Blob Storage Store Data?

Blob Storage stores **object** data inside containers within a storage account. A blob has a **name**, **content**, **properties**, and **metadata**; when supported features are enabled, a blob can also have **versions** or **snapshots**.

```text
Subscription / Resource group
└── Storage account: stdocumentsdemo
    ├── Container: invoices
    │   ├── 2026/invoice-001.pdf
    │   ├── 2026/invoice-002.pdf
    │   └── reports/summary.csv
    └── Container: images
        ├── products/a.png
        └── products/b.png
```

The path `2026/invoice-001.pdf` is a blob name in the `invoices` container. In standard Blob accounts, the `/` character creates a virtual folder hierarchy for display; do not assume blob names represent files in a true POSIX filesystem. With hierarchical namespace (ADLS Gen2), directory semantics and available features differ and must be verified.

### Block Blobs, Append Blobs, and Page Blobs

| Type | Use case | Version protection notes |
|---|---|---|
| **Block blob** | Files, images, videos, artifacts, data lake objects. | Focus of versioning and recovery examples in this lesson. |
| **Append blob** | Sequential append-only data streams. | Do not assume identical versioning behavior as block blobs. |
| **Page blob** | Random-access data, certain specialized disk workloads. | Snapshot/versioning support and APIs differ; do not blindly apply all block blob commands. |

**Key point:** recovering files in Azure Files using *file share snapshots* is a separate topic; here we work with **Blob Storage**, where versions and snapshots are typically defined **per blob**.

## 3. Core Vocabulary: Current State and Recovery Points

| Term | Meaning | Common identifier |
|---|---|---|
| **Current blob** | The blob version accessed by a standard GET request by name when the object exists. | Container + blob name, no version specified. |
| **Previous version** | An older version generated by versioning when data changes via supported operations. | **Version ID**, typically represented as a service-issued timestamp. |
| **Snapshot** | A **read-only** point-in-time capture, typically created explicitly on demand. | **Snapshot timestamp**, distinct from Version ID. |
| **Soft-deleted blob/snapshot/version** | A deleted object retained during the retention window of the applicable soft delete mechanism. | Blob name combined with deletion/version/snapshot info. |
| **Soft-deleted container** | An entire deleted container retained for possible recovery if container soft delete was enabled. | Container name and corresponding deletion metadata. |
| **Recovery point** | A selectable data point for recovery. | Can be a version, snapshot, or managed backup. |

**Version ID is not Snapshot ID.** Although both may look like timestamp strings, their creation, listing, API parameters, and lifecycles differ.

### Encryption, Redundancy, and Historical Data

Azure Storage Service Encryption protects data **at rest**; LRS/ZRS/GRS/GZRS increase durability according to the redundancy model. However, when a valid overwrite or delete operation is accepted, the new content or deletion state can be replicated. **Encryption and redundancy do not automatically replace versioning, snapshots, or historical backups.**

## 4. What Is Blob Versioning?

**Blob versioning** allows Azure Storage to preserve previous states of a block blob whenever its content or state changes through service-supported operations. When enabled and a blob is overwritten, the prior state becomes a **previous version** with a distinct **Version ID**, while the new content becomes the **current version**.

Timeline example:

```text
09:00  reports/summary.csv = A       (current)
       │
10:00  Overwrite upload with B
       ├── Previous version V1 = A
       └── Current = B
       │
11:00  Overwrite upload with C
       ├── Previous version V1 = A
       ├── Previous version V2 = B
       └── Current = C
       │
12:00  Need to recover B
       └── Select V2, verify, then restore/copy as current
```

Version IDs are assigned by the service, not arbitrary labels like `V1` or `V2` in the diagram. Via the API, you can read a specific version without altering the current blob.

### What Versioning Solves Well

- An application uploads to the same blob name and **accidentally overwrites** prior content.
- You need to inspect change history to restore an older version.
- You want automatic recovery points during blob updates without remembering to take a manual snapshot before each write.
- Combining with lifecycle policies to keep previous versions for an agreed duration.

### What Versioning Does Not Guarantee on Its Own

- **Not** an off-account backup isolated from the storage account.
- **Does not automatically stop** a highly privileged principal from deleting all data/versions or deleting the account without other safeguards.
- **Does not replace** application consistency testing, especially when a transaction updates multiple blobs.
- **Does not guarantee** infinite retention: previous versions can be deleted by authorized actions or configured lifecycle/retention rules.
- **Does not equate to** file locking, Git-style version control, or multi-object transactions.

When enabling versioning on an account that already holds data, **do not assume the system retroactively creates version history for pre-existing versions**. Record the timestamp when the policy took effect.

## 5. What Is a Blob Snapshot?

A **blob snapshot** is a read-only capture of a blob at a specified point in time. Snapshots are usually created explicitly by an operator, SDK, tool, or workflow, rather than generated automatically on every upload like versioning.

Example before updating a configuration file:

```text
14:00  configs/appsettings.json = A
       │
14:05  Create snapshot S1     → S1 = A
       │
14:10  Deploy writes current = B
       │
14:15  Discover B is broken
       └── Retrieve S1 to compare, then restore A per procedure
```

Snapshots are useful when you want to **proactively freeze a milestone** ahead of a risky change, such as an application upgrade, data file edit, or transformation job.

### Snapshots Are Not Independent Full Copies

Azure manages snapshots by storing changed blocks/data and reusing unchanged data under its service model. Creating a snapshot can therefore be faster and more economical than duplicating a large blob in many cases, yet **historical data still incurs storage charges** based on changes and retention time.

Snapshots are **tied to the blob in the source storage account**. Do not treat having snapshots as proof you hold an independent copy in another account, subscription, or region.

### Read-Only Captures

You cannot edit a snapshot's content directly the way you edit the current blob. To revert to snapshot content, you must **copy the snapshot's content** to a target blob or invoke a supported restore operation. Restoring over the current name can create additional version history if versioning is enabled.

### Snapshots vs. Versioning

| Criterion | Versioning | Snapshot |
|---|---|---|
| When created | Automatically on supported blob-modifying operations when enabled. | Upon explicit snapshot request. |
| Identifier | Version ID. | Snapshot timestamp. |
| Common use case | Protection against unintended overwrites. | Checkpointing before deployments, migrations, or data edits. |
| Scope | Per-blob version history; depends on account configuration. | Single blob at a specific instant. |
| Lifecycle | Retain/delete previous versions via policy and authorized actions. | Manage snapshot retention/deletion via policy and authorized actions. |
| Independent backup? | No. | No. |

Do not use the term "snapshot" to refer to all previous versions: their mechanisms and recovery parameters are distinct.

## 6. Soft Delete: "Deleted" Does Not Always Mean Permanently Gone

**Blob soft delete** helps protect blobs, snapshots, or versions deleted under feature-supported conditions by retaining the data for a configured **retention period**. Within this window, objects can be recovered via supported operations; after expiration or permanent deletion through an authorized mechanism, recoverability may be lost.

Keep two features strictly distinct:

1. **Blob soft delete:** focuses on deleted blobs/versions/snapshots inside a container.
2. **Container soft delete:** protects against **deleting an entire container** within the retention window.

Enabling blob soft delete **does not mean** container soft delete is enabled. Deleting a container can require a different recovery mechanism than deleting an individual blob.

### Blob Deletion Incident Example

```text
09:00  images/products/a.png exists
09:30  Cleanup job accidentally deletes a.png
10:00  Incident detected
       |
       ├── Blob soft delete still within retention?
       |      └── Yes: check supported undelete/restore method
       |
       └── If previous versions exist:
              select clean version → copy/promote to current
```

**Important check:** recovery differs between accounts **with versioning** and **without versioning**. With versioning enabled, deleting the current blob can leave no current version while previous versions still exist; to restore older content as current, you typically must **copy a valid version**. Do not assume `undelete` always automatically promotes the desired version to current.

### Retention Period

Retention is how long soft delete keeps deleted objects recoverable. For example, an organization might choose **30 days** for blob soft delete and **14 days** for container soft delete; these are **illustrative policies**, not Azure defaults across all accounts.

Evaluate:

- How long does it typically take to notice an accidental deletion?
- Might you need to recover data corrupted a month ago?
- Does the retention window satisfy RPO/RTO, audit, or contractual mandates?
- Could lifecycle policies purge versions/snapshots and other backups earlier than needed?
- Have storage costs for retaining deleted objects during retention been budgeted?

Never assume raising retention today will **recover** objects that were permanently deleted or whose retention expired prior to the change.

## 7. Scenarios Combining Versioning, Snapshots, and Soft Delete

Real-world architectures often enable **multiple layers simultaneously**, because each mechanism guards against different failure modes.

| Incident | Preferred mechanism | What to verify |
|---|---|---|
| Upload overwrites blob with wrong content | **Previous version** if versioning is enabled; prior snapshot if available. | Does a pre-incident version/snapshot exist and remain within retention? |
| Need to freeze state before an upgrade | Proactive **snapshot**. | Exact blob name, timestamp, and all related blobs covered? |
| Accidental deletion of a blob without versioning | **Blob soft delete** if enabled and within retention. | Is the blob still in the soft-deleted list; is undelete valid? |
| Accidental deletion of current blob with versioning enabled | **Previous version** and appropriate copy/promote action; check soft delete for deleted versions. | Version ID, current status, and version deletion rules. |
| Accidental deletion of an entire container | **Container soft delete** if enabled, or independent backup. | Is the container in deleted containers and within retention? |
| All blobs corrupted within minutes | Selecting multiple previous versions or **point-in-time restore** where supported and configured. | Scope, clean timestamp, change feed, and feature prerequisites. |
| Storage account deleted or unavailable | **Independent backup/protection layer** if configured. | Does an independent copy exist; is the restore target valid? |
| Ransomware encrypts content | Clean versions/snapshots, independent backups, immutability protection as needed. | Did recovery points predate the attack and avoid deletion by the attacker? |

Never give a blanket answer like "just turn on soft delete." Critical workloads need **automatic overwrite protection + deletion protection + independent or immutable copies** alongside tested runbooks.

## 8. Difference Between Deleting the Current Blob and Deleting a Previous Version

This is a frequent source of confusion during incident response:

- When **versioning is disabled**, deleting a blob moves it to a soft-deleted state if blob soft delete is enabled; undelete can restore the blob via supported mechanisms.
- When **versioning is enabled**, deleting the current blob typically preserves data in previous versions, leaving **no current blob** afterward. To restore current, pick an appropriate previous version and **copy it back to the original blob name**.
- When **deleting a specific version**, if soft delete and version deletion are supported, retention and recovery behavior can differ from deleting the current blob.
- **Permanent deletion** or policy-driven deletion can remove recovery options; understand permissions and retention before acting.

### Why Does GET Return 404 After "Undelete"?

You may have restored soft-deleted auxiliary objects/versions **without recreating a current version** at the blob name. Inspect the version list and select the right version to copy/promote to current.

Do not try to fix the 404 by uploading an empty file to the same name before identifying the version to recover: that creates an extra version and complicates investigation.

## 9. Multi-Blob Consistent Recovery Points

A blob version/snapshot is a recovery point **for a single object**. If an application updates `orders.json`, `customers.json`, and `manifest.json` concurrently, picking the "latest version" of each file independently can yield an **inconsistent** state.

Example:

```text
10:00  orders = A        customers = A        manifest = A
10:05  orders = B
10:06                    customers = B
10:07                                         manifest = B
10:08  Valid data publish completes
```

If failure strikes at 10:06, picking arbitrary versions mixes A and B. To recover a cohesive dataset:

1. Design applications to emit data under **job ID/versioned directories** or a manifest/commit-marker pattern.
2. Record the set of Version IDs or snapshot timestamps belonging to the **same valid publish**.
3. During incidents, restore the verified consistent state rather than "newest per blob."
4. Restore into a **staging container/prefix**, validate business integrity, and only then switch read traffic.
5. If container/account-wide point-in-time recovery is required, evaluate **point-in-time restore** for supported data types.

Versioning does not provide ACID transactions spanning thousands of blobs; applications remain responsible for logical consistency.

## 10. Point-in-Time Restore as an Additional Capability

**Point-in-time restore (PITR) for block blobs**, in supported accounts and configurations, can restore a range of block blobs back to their state at an earlier timestamp. It differs from picking a single previous version or snapshot manually.

PITR typically has **prerequisites**, such as coordination across **versioning, change feed, and soft delete**, along with limits on account kind, namespace, restore range, and retention. These requirements evolve with service capabilities: verify support in Azure Portal and official service documentation before planning around it.

Do not assume "versioning is on" means "PITR is ready." If PITR was not enabled beforehand or its restore window does not cover the incident, you cannot retroactively use PITR to recover past states.

### When Should You Use PITR?

- A buggy script overwrites thousands of block blobs in a short window.
- You need to roll back a defined range to a consistent clean timestamp within feature capabilities.
- You have planned for impact on newer writes, restore scope, and job execution duration.

When an application writes continuously, account for **quiescing/freezing writes** and handling concurrent changes generated during restoration. Never execute PITR directly in Production without evaluating scope and potential overwrites of valid newer data.

## 11. Configuring Data Protection Policies in Azure Portal

The steps below describe a **feature-supported** storage account and should only be performed in an authorized subscription. Menu layouts may vary across Portal updates.

### Step 1: Select the right account and workload

1. Open [Azure Portal](https://portal.azure.com/) and verify your tenant/subscription.
2. Open **Storage accounts** and select the account hosting Blob Storage.
3. Check **Account kind**, redundancy, access tier, and whether hierarchical namespace is enabled.
4. Match blob types, workloads, and protection requirements against compatible features.

### Step 2: Open Data protection

1. Inside the storage account, locate **Data protection** or the corresponding data protection settings section.
2. Under blob settings, inspect **Enable versioning for blobs**, **Enable soft delete for blobs**, **Enable soft delete for containers**, and additional supported options.
3. Enable versioning for workloads requiring overwrite history.
4. Set blob soft delete and container soft delete retention periods as required.
5. If PITR is needed, verify and configure its prerequisites/supporting features.
6. Save changes and reload the settings to confirm.

**Note:** enabling account-level features can affect data and costs across many containers. Before enabling on Production accounts, estimate capacity for previous versions/snapshots and review existing lifecycle policies.

### Step 3: Test with a dedicated container

1. Create a lab container, e.g., `recovery-lab`.
2. Upload a test blob `reports/weekly.csv` with content A.
3. Overwrite it with content B; open **Versions** to verify the previous version.
4. Create a **snapshot** and record its timestamp.
5. Delete the test blob, then inspect current blob, previous versions, and soft-deleted entries.
6. Restore using the appropriate mechanism and verify content by downloading.
7. Clean up lab data after confirming no retention/immutability policies block removal.

Do not test on real customer data, run bulk deletions, or alter policies on shared accounts without approval.

## 12. Azure CLI: Inspecting Account Configuration

Use Azure CLI to inspect Blob Storage protection settings. The commands below are primarily **read-only**, except where snapshot creation or policy changes are explicitly noted.

### Verify context

```bash
az account show \
  --query "{Subscription:id,Tenant:tenantId,Name:name}" \
  --output table
```

Confirm the exact subscription and tenant before working with any storage account.

### Read data protection configuration

```bash
az storage account blob-service-properties show \
  --account-name "<STORAGE_ACCOUNT>" \
  --resource-group "<RESOURCE_GROUP>" \
  --output json
```

In the JSON output, look for fields related to:

- `isVersioningEnabled` or the current API's versioning property name.
- `deleteRetentionPolicy` and blob soft delete retention days.
- `containerDeleteRetentionPolicy` for container soft delete.
- `restorePolicy` and `changeFeed` if present.
- Other properties depending on account, SDK, and CLI version.

Do not infer status solely from a field's **absence**. Field names/schemas can change; verify CLI version or Portal settings when needed.

### Check containers and blobs using data permissions

```bash
az storage container list \
  --account-name "<STORAGE_ACCOUNT>" \
  --auth-mode login \
  --output table

az storage blob list \
  --account-name "<STORAGE_ACCOUNT>" \
  --container-name "recovery-lab" \
  --auth-mode login \
  --output table
```

Data-plane read commands with `--auth-mode login` require the signed-in account to hold an appropriate **Azure RBAC data role**, such as `Storage Blob Data Reader` or higher. Control-plane account management roles **do not automatically** allow reading blob contents via Microsoft Entra OAuth.

### List versions and snapshots

Azure CLI supports `--include` for additional record types. Flags and syntax can vary by CLI version; in several versions, `v` lists versions and `s` lists snapshots.

```bash
az storage blob list \
  --account-name "<STORAGE_ACCOUNT>" \
  --container-name "recovery-lab" \
  --include v \
  --auth-mode login \
  --output json

az storage blob list \
  --account-name "<STORAGE_ACCOUNT>" \
  --container-name "recovery-lab" \
  --include s \
  --auth-mode login \
  --output json
```

Carefully examine blob names, version IDs, snapshot timestamps, current flags, and deleted items. Do not treat `--include v` as guaranteeing visibility into **all soft-deleted objects**; use CLI/API-supported deleted-item include flags and appropriate permissions when investigating deletions.

To verify exact syntax in your environment, run:

```bash
az storage blob list --help
```

## 13. Azure CLI: Creating a Snapshot and Downloading an Older Version

This section uses an **authorized lab container**; do not run against critical Production blobs.

### Create a snapshot (modifies metadata state)

When the current blob exists:

```bash
az storage blob snapshot \
  --account-name "<STORAGE_ACCOUNT>" \
  --container-name "recovery-lab" \
  --name "reports/weekly.csv" \
  --auth-mode login \
  --output json
```

Record the snapshot timestamp from the output. Snapshots create a **recovery point** and can incur storage costs, though they do not re-encrypt data into an independent off-account copy.

### Download a blob snapshot for verification

```bash
az storage blob download \
  --account-name "<STORAGE_ACCOUNT>" \
  --container-name "recovery-lab" \
  --name "reports/weekly.csv" \
  --snapshot "<SNAPSHOT_TIMESTAMP>" \
  --file "./weekly-from-snapshot.csv" \
  --auth-mode login
```

The destination file resides on the **CLI host**, not overwriting the current blob. Never download sensitive data onto unmanaged personal devices.

### Download a previous version

```bash
az storage blob download \
  --account-name "<STORAGE_ACCOUNT>" \
  --container-name "recovery-lab" \
  --name "reports/weekly.csv" \
  --version-id "<VERSION_ID>" \
  --file "./weekly-from-version.csv" \
  --auth-mode login
```

`--snapshot` and `--version-id` represent **two distinct identifier types**. Do not pass both in the same request unless explicitly supported by the tool/API.

### Restoring to current: safe approach

After downloading the older copy, prefer:

1. Verify checksums/content of the older copy and confirm with the data owner.
2. Create a **staging target blob** such as `restored/weekly-reviewed.csv` for user validation.
3. Only upon approval, copy/overwrite back to `reports/weekly.csv`.
4. If versioning is enabled, confirm a **new current version** exists and historical versions to keep remain intact.
5. Log the source Version ID or timestamp, operator, and execution time.

You can also use supported **server-side copy** operations from versions/snapshots to avoid downloading data to an admin workstation. Syntax depends on source/target, account, auth, and API: check `az storage blob copy --help` or your SDK instead of concatenating arbitrary URLs and embedding secrets in scripts.

## 14. Deleting and Undeleting a Blob: Choosing the Right Action

Suppose `reports/weekly.csv` was deleted at 10:00. The first rule is **do not rush to re-upload an empty file** or delete remaining visible versions.

### Case A: Versioning disabled, blob soft delete enabled

In the Portal or supported API:

1. Enable showing soft-deleted blobs.
2. Locate the exact container/blob and deletion timestamp.
3. Verify the blob is still within retention.
4. Execute **Undelete** to restore if supported for the scenario and blob type.
5. Verify by downloading/reading the content again.

Illustrative CLI example on a supported account:

```bash
az storage blob undelete \
  --account-name "<STORAGE_ACCOUNT>" \
  --container-name "recovery-lab" \
  --name "reports/weekly.csv" \
  --auth-mode login
```

This command **mutates data state**. Run it only after confirming the target blob and verifying data permissions.

### Case B: Versioning enabled

1. List the blob's previous versions.
2. Choose the Version ID from **before the incident occurred**.
3. Inspect/download that version to confirm its data.
4. **Copy/promote** the selected content back to the current blob name via a supported operation.
5. Verify the current blob is readable; inspect version history and application permissions.

If deleting a specific version created a soft-deleted version, check the recovery conditions for that version. **Undelete and promote are not synonymous operations.**

### Case C: Retention expired or permanently deleted

If no valid version, snapshot, or soft-deleted entry remains, no built-in Blob Storage mechanism guarantees recovery. Look for external sources: independent copies, backups, intact object replication targets, or original application artifacts. Never promise every blob is recoverable just because the storage account uses GRS.

## 15. Container Deletion: Requires Container Soft Delete

When someone deletes the `invoices` container, single-blob recovery actions may be unreachable because the source container is gone. If **container soft delete** was previously enabled and the container remains within retention, Azure Storage can allow **restoring/undeleting the container** via supported API/Portal operations.

Procedure:

1. Confirm the storage account still exists and the error is not simply permissions or DNS/networking.
2. Verify container soft delete was enabled on the account at the time of deletion.
3. Inspect the **deleted containers** list and match the name and deletion timestamp.
4. Restore the target container using the supported operation.
5. Verify the container reappears with its blobs, metadata, and permissions as required by the app.
6. Inspect current blobs, versions, snapshots, and soft-deleted entries if layered protection was active.
7. Document the change, recovery timestamp, and measures to prevent future accidental deletion.

**Never enable container soft delete after an incident and expect to recover a container deleted earlier.** Protection only applies when the policy was active before the deletion occurred.

## 16. Lifecycle Management: Retaining Old Data Without Retaining Forever

When versioning and snapshots are widely used, **historical capacity** can grow rapidly. Azure Blob lifecycle management lets you define rules based on data age, blob type, and supported prefix/tag filters to **transition access tiers or delete** eligible objects.

Object groups can be managed independently:

- **Base/current blobs**.
- **Previous versions**.
- **Snapshots**.

Do not assume a rule defined for current blobs automatically applies identically to snapshots and versions. Inspect **filters, actions, age conditions, and object types** in the actual policy.

### Illustrative Policy Example

Suppose the organization wants:

| Data group | Retention goal | Approach |
|---|---|---|
| Temporary artifacts | Current version 30 days; little history needed | Lifecycle delete rule once permitted. |
| Invoices | Previous versions minimum 90 days per business mandate | Versioning + clear retention rules; verify legal/regulatory rules. |
| Application configs | Snapshot before each deploy, keep key milestones | Named/procedural snapshots and creation-age lifecycle. |
| Research datasets | Keep history by release, not every intermediate step | Versioning or periodic exports to dedicated versioned prefixes/datasets. |

These are **design targets**, not a tested production policy. When legal mandates require longer retention, lifecycle rules must comply with regulations and organizational policy.

### Purging Old Versions Can Break Recoverability

For example, suppose soft delete retention is 30 days while lifecycle deletes previous versions after 7 days: an overwrite discovered 15 days later may **have no previous version left**, even though blob soft delete retains certain deleted objects under its own rules. Therefore verify all of:

- Creation timestamps of versions/snapshots;
- Delete actions capable of affecting them;
- Conflicts between lifecycle rules and retention policies;
- Immutability/hold states if present;
- Daily data churn volume.

**Lifecycle does not replace backups**; it manages object lifecycles, including deletions that can remove recovery points.

## 17. Cost Model: Why Can Versioning Get Expensive?

Suppose a 10 GiB blob is overwritten daily. If each day's update changes most of the content and 30 previous versions are retained, historical storage can significantly exceed the 10 GiB of the current blob.

Illustrative example:

- Current blob size: 10 GiB.
- Each update generates **roughly 4 GiB of changed data retained** under a hypothetical model.
- Keep 20 previous updates.

```text
Estimated historical data ≈ 20 × 4 GiB = 80 GiB
Total current + history ≈ 10 + 80 = 90 GiB
```

This is an **illustrative** calculation, not an official billing formula: actual snapshot/version footprint depends on blob type, change patterns, service storage representation, access tiers, and applicable billing mechanics.

Beyond capacity:

- Creating, reading, or deleting versions or snapshots can incur transaction fees.
- Data in different tiers carries different storage, retrieval, and minimum retention charges.
- Replication, independent backup destinations, and egress can raise total cost.
- Lifecycle can curb growth, provided it does not purge versions still needed.

For real estimates, use the Azure Pricing Calculator, actual churn rates, object counts, retention windows, and exact region/SKU rates. **Do not optimize costs by shrinking retention without checking your organization's incident detection lead time.**

## 18. Security: Restricting Who Can Delete Recovery Points

If an application account can write/delete all blobs and administrators can alter data protection policies freely, versioning and soft delete offer only partial protection. To reduce risk:

1. Apply Microsoft Entra ID and **Azure RBAC** with **least privilege** across both control plane and data plane.
2. Avoid sharing account keys, unrestricted SAS tokens, or delete-capable credentials when only reads are needed.
3. Separate **storage configuration administrators** from **applications that only perform data operations**.
4. Restrict network access with private endpoints/firewalls where required.
5. Enable and monitor logs for object create/delete actions, retention changes, lifecycle edits, and role assignments.
6. Evaluate **immutable storage** and **legal holds** for data requiring tamper/delete protection per policy.
7. Maintain independent account/region-level backups/replicas if scenarios require surviving major outages.
8. Use approval workflows/PIM/MFA for privileged administrative roles where supported by your organization.

### Immutability Is Not Soft Delete

| Feature | Purpose |
|---|---|
| Versioning | Preserves prior blob states across modifications. |
| Snapshot | Freezes a blob state on demand. |
| Soft delete | Enables recovering deleted objects/containers within retention. |
| **Immutability policy / legal hold** | Restricts modifying/deleting protected data per rules and service capabilities. |
| Independent backup | Improves recoverability when the source resource is lost or destroyed. |

Version-level immutability and WORM/retention locks carry constraints across accounts, containers, versions/snapshots, and admin operations. Never enable them in Production without understanding impacts on deletion, lifecycle, costs, and policy mutability. **An immutable copy alone does not guarantee application recovery** without permissions, runbooks, or target systems.

### Appropriate Log Sources

- **Azure Activity Log:** control-plane changes to storage accounts, policies, or resource configurations.
- **Storage resource logs/diagnostic settings:** data-plane operations and error codes when enabled, exportable to Log Analytics/Storage/Event Hubs.
- **Azure Monitor metrics:** transactions, errors, capacity, and traffic as supported.
- **Microsoft Entra sign-in/audit logs:** audit identity activity and Entra administrative changes when relevant.

Do not assume Azure Activity Log records every blob upload or deletion. You must configure **data-plane logging** to investigate blob-level operations.

## 19. Recovery Runbook: Finding the Right Version Before Restoring

When users report "the file is corrupted":

1. **Identify the object:** storage account, container, blob name, blob type, and time zone.
2. **Narrow the timeline:** ask when the data was last known good, when corruption was noticed, and what recent deployments/jobs ran.
3. **Prevent further harm:** pause related overwrite/cleanup jobs; preserve existing versions/snapshots.
4. **Check Data protection:** were versioning/soft delete/container soft delete/PITR/retention enabled when the incident occurred?
5. **List recovery points:** current blob, Version IDs, snapshot timestamps, soft-deleted items.
6. **Pick a clean copy:** compare content and metadata; avoid points taken after corruption began.
7. **Restore to an alternate path first:** download/copy to `restored/<incident-id>/...` or an isolated container.
8. **Verify:** checksums, file structure, access permissions, business content, and related blobs.
9. **Approve and cut over:** copy/promote to current or update application manifests/paths once safe.
10. **Monitor post-restore:** confirm clients GET the corrected content, caches/CDNs are not serving stale versions, and write jobs do not reintroduce the bug.
11. **Record evidence:** source, Version ID/timestamp, time, operator, and verification test results.
12. **Prevent recurrence:** adjust policies, permissions, lifecycles, and application safeguards.

### Why Check Caches and CDNs?

Even after the current blob is restored, applications may keep seeing old or broken content due to **client, proxy, or CDN caches**. Inspect URLs, ETags, Cache-Control headers, and cache invalidation workflows; do not repeat restores just because a cache has not expired yet.

### Restoring to the Original Name Can Alter Metadata

Some copy/restore paths can affect metadata, content type, tags, ACL/authorization semantics, ETag, or modification timestamps. Runbooks should verify application-critical attributes, not just raw byte equality.

## 20. Real-World Scenario A: Upload Overwrites a Report

**Symptom:** An analytics app exports `reports/weekly.csv` at 09:00 with valid data, then a 10:00 job overwrites it with a table missing rows.

**Investigation:**

1. Verify container, blob name, and timeline.
2. Open the blob's **Versions** if versioning is enabled on the account.
3. Select the previous version from before 10:00, download it, and compare row counts/hashes.
4. Check if a proactive snapshot was taken before the job.
5. Stage the valid copy under a recovery prefix for data-owner sign-off.
6. Copy/promote back to current and monitor subsequent job runs.

**Takeaway:** versioning is usually faster and more direct for overwrite protection; snapshots also work if a timely snapshot was created. Soft delete should not be treated as the sole defense against overwrites, especially without version history.

## 21. Real-World Scenario B: Accidental Deletion of a Blob and a Container

**Symptom:** A cleanup script deletes `images/products/a.png` and then deletes the `images-archive` container.

**Investigation and action:**

- For `a.png`: check versioning/soft delete, previous versions or deleted blobs list, and retention.
- For `images-archive`: check **container soft delete** and the deleted containers list.
- If no valid version or soft-deleted object remains within retention, locate external copies or pipeline artifacts.
- After restoring, verify URLs/app configs, permissions, and CDN caches.

**Lesson:** blob soft delete and container soft delete must be treated as **two separate settings**. Testing single-blob recovery does not prove protection against whole-container deletion.

## 22. Real-World Scenario C: A Job Corrupts Thousands of Blobs

**Symptom:** A misconfigured deployment script overwrites 8,000 JSON blobs in the `datasets` container. Blobs were updated at varying times, and some writes after the incident are valid.

Response steps:

1. Halt the faulty script and freeze write pipelines that risk further corruption.
2. Identify the affected prefix/blob scope and exact start timestamp of corruption.
3. If **PITR** is configured and eligible, evaluate restore scope and impact on valid newer changes.
4. Without PITR, build a clean per-blob Version ID list from manifests/logs before copying.
5. Restore a sample into a separate container and validate schema, record counts, and hashes.
6. Plan controlled batch restoration while monitoring errors and rollback options.
7. Check whether lifecycle rules already purged any needed previous versions.
8. Re-enable the application after validating data and running end-to-end tests.

**Never blindly batch-restore to "the previous version"** when a faulty job may have written multiple times; some blobs may need to roll back more than one version while others should remain untouched.

## 23. RPO/RTO, Backups, and Major Incident Planning

- **RPO (Recovery Point Objective):** maximum tolerable data loss measured back to the recovery point timestamp.
- **RTO (Recovery Time Objective):** maximum tolerable time until the application resumes using recovered data.
- **Retention:** duration objects/recovery points remain preserved for rollback.
- **Independent backup:** a mechanism storing copies outside the source storage account's failure domain as supported by design.

Example:

| Workload | Illustrative target | Controls |
|---|---|---|
| Weekly-updated product images | Recover overwrites/deletions within 30 days. | Versioning, blob soft delete, container soft delete, and lifecycle. |
| Financial records | Long history, strict edit/delete controls. | Versions/snapshots, suitable immutability policies, and independent backups. |
| Recomputable pipeline data | Minimal history, cost-focused. | Shorter retention if regenerable from upstream sources. |
| Bulk-modified datasets | Ability to roll back an entire blob set. | PITR if supported, or manifests/versioned datasets and restore workflows. |

Retention days are **design parameters**, not guarantees that features automatically meet every RPO/RTO. With Blob Storage, a previous version may exist on overwrite, yet **the RTO to restore 100,000 blobs** can still be long without automation and operational practice.

### Why Replication Is Not Enough

GRS/GZRS protects data durability geographically, yet an accepted delete or bad write **can be replicated**. Versioning/snapshots protect history inside the account; independent backups or appropriate immutability controls reduce the risk of losing all recovery points during severe source incidents.

To recover if an entire **storage account is deleted**, prove beforehand that a genuinely independent data copy exists alongside a tested restore procedure to a new account. Never rely on blob/container soft delete as your sole defense against account-level disasters.

## 24. Hands-On Exercise: Design, Simulate Failures, and Recover

**Context:** An operations team stores monthly reports in Blob Storage. The lab environment includes a storage account supporting required features and a container named `recovery-lab`.

Goals:

- Preserve overwrite history via **Blob versioning**.
- Guard against accidental blob deletion via 30-day **blob soft delete**.
- Guard against accidental container deletion via 14-day **container soft delete**.
- Take a **snapshot** prior to a data update step.
- Restore an older version without corrupting current data during testing.

### Test Data

Initial blob `reports/weekly.csv`:

```csv
week,totalOrders
2026-W45,120
```

After update:

```csv
week,totalOrders
2026-W45,130
```

### Tasks

1. Verify the correct tenant, subscription, storage account, and lab container.
2. Confirm the storage account **supports** versioning, snapshots, and soft delete for the blob type in use.
3. Enable or verify versioning; set both retention periods as requested where permitted.
4. Upload the initial data, then create snapshot S1.
5. Overwrite the blob with the second version and list previous versions.
6. Point out the difference between **Version ID** and **snapshot timestamp**.
7. Download the previous version/snapshot to a separate local destination and inspect its content.
8. Delete the test blob and practice distinguishing **undelete** from **copy/promote previous version**.
9. If permissions and lab rules permit, test deleting/undeleting a **dedicated test container**, never a shared container.
10. Draft a lifecycle plan ensuring critical recovery points are not purged prematurely.
11. Propose a protection measure for when the entire account becomes unavailable.
12. Calculate average monthly version accumulation if a job overwrites a blob daily, and assess historical storage cost.

### Guided Solution

- **After overwrite:** the current blob holds `130`, while the previous version retains `120` when versioning operates on that blob type.
- **Snapshot S1:** points to the content at capture time with an identifier independent of previous versions; S1 remains read-only.
- **After deletion:** inspect version lists and soft-deleted records; with versioning enabled, copying a previous version back to current may be required.
- **When deleting a container:** container soft delete must have been enabled **before** deletion and the container must still be within retention.
- **With 1 overwrite/day:** after 30 days, roughly 30 previous versions accumulate per blob if no version cleanup runs and each operation creates a version as expected; billed capacity depends on changed data.
- **Account-level outage:** an appropriate independent copy/backup is required; never treat versions and snapshots inside the same account as an isolated backup.

**Acceptance criteria:** accurately identify Version ID, snapshot timestamp, current blob, and deleted entries; download the content to recover; avoid overwriting current data prior to verification; and document retention/lifecycle policies.

## 25. Knowledge Self-Check

**Question 1.** When versioning is enabled and a block blob is overwritten, what typically happens?

A. The old version is always permanently deleted.  
B. The old version can be saved as a previous version with a Version ID.  
C. The entire storage account automatically replicates to another region.

**Answer: B.** Versioning preserves history across supported blob-modifying operations.

**Question 2.** How does a blob snapshot differ from a previous version?

**Answer:** A snapshot is typically created explicitly on demand at a point in time; a previous version is automatically created by versioning when a blob changes via supported operations. They have separate identifiers and lifecycles.

**Question 3.** Does enabling blob soft delete automatically protect against deleting an entire container?

**Answer:** No. You need **container soft delete** or another appropriate backup mechanism.

**Question 4.** Why might deleting the current blob with versioning enabled not be resolved by a single undelete command?

**Answer:** There may no longer be a current blob while previous versions still exist; you must select a valid version and copy/promote it to current.

**Question 5.** Can Version ID and snapshot timestamp be used interchangeably in download commands?

**Answer:** No. They represent two distinct recovery point types; APIs/CLIs use separate parameters.

**Question 6.** Does GRS/ZRS replace blob versioning when an application overwrites data with bad content?

**Answer:** No. Redundancy protects durability at the storage tier but can replicate bad changes; versioning retains older copies if enabled and still present.

**Question 7.** Why does taking a snapshot of one blob not guarantee consistency across a set of 1,000 blobs?

**Answer:** Snapshots/versions are typically per-object recovery points. Multiple blobs updated at different instants require manifests, commit markers, supported PITR, or dedicated consistency workflows.

**Question 8.** Does enabling versioning automatically allow restoring all block blobs to an arbitrary point in time?

**Answer:** No. PITR is a separate feature with prerequisites and retention bounds; it must be explicitly enabled/configured where supported.

**Question 9.** Why shouldn't you rely solely on a lifecycle rule "delete previous versions after 7 days" for data needing 90-day rollback?

**Answer:** The rule can purge recovery points before the business window expires. Retention of versions/snapshots must align with incident detection times and actual policy.

**Question 10.** Are immutability and soft delete the same thing?

**Answer:** No. Immutability restricts modification/deletion by policy, whereas soft delete retains certain deleted objects for recovery within a retention period.

**Question 11.** When a blob is overwritten, why download the previous version to a new name before officially restoring?

**Answer:** To verify data accuracy, avoid destroying valid newer changes, facilitate owner sign-off, and reduce the risk of picking the wrong Version ID.

**Question 12.** An account has 30-day blob soft delete enabled, but container soft delete is disabled. An admin deleted a container yesterday. Is recovery guaranteed?

**Answer:** No. Blob soft delete does not substitute for container soft delete; you must look for another copy/recovery source if no recoverable deleted container exists.

**Question 13.** Does a Microsoft Entra RBAC role on the control plane automatically allow downloading blobs with `--auth-mode login`?

**Answer:** No. Appropriate **data-plane** permissions are required to access Blob content via OAuth.

**Question 14.** Why might an account hold older versions while the app still sees 404 after deleting the current blob?

**Answer:** There may be no current blob. The app requests the blob name without specifying a version; a valid previous version must be copied to recreate current.

**Question 15.** When is an independent backup required instead of relying solely on in-account snapshots?

**Answer:** When you must withstand source account loss/corruption/deletion or privileged destruction of recovery points; backups must be configured and restore-tested beforehand.

**Summary:** Blob versioning provides an automatic safeguard against many overwrite operations; snapshots proactively capture point-in-time milestones for a blob; blob/container soft delete reduces accidental deletion risk within retention windows. Combining them with lifecycle management, least privilege, monitoring, immutability, and independent backups where needed produces a **verifiable, version-accurate, properly scoped recovery plan without additional data loss**.
