# Access control, secrets, and protecting the software supply chain

## Lesson objectives

In the **DevOps and CI/CD on OCI** chapter of the **CLOUD_PROVIDERS_ORACLE** module, this lesson explains how to scope pipeline permissions, use secrets properly, and verify software package provenance before deployment.

In an OCI tenancy, pipelines can read Git, download dependencies, call Vault, push images, and update workloads. Those capabilities directly connect the development workflow to Compute, storage, and Oracle databases. Therefore, CI/CD identities must be governed as strictly as infrastructure operations identities.

After this lesson, you will be able to:

- Distinguish users, build pipelines, deployment pipelines, and application identities.
- Design IAM by task, compartment, resource, and code trust level.
- Inject secrets from OCI Vault without writing values to Git, logs, or artifacts.
- Protect source code, dependencies, build tools, artifact repositories, and deployment steps.
- Distinguish checksums, signatures, SBOMs, scan results, and provenance.
- Design tests for both permitted cases and denied cases.
- Handle leaked credentials or suspected artifact tampering while preserving investigative evidence.

The running example is a Java service built with Maven, publishing a JAR or container image and deploying to a lab environment. IAM, YAML, and CLI snippets are learning templates; replace placeholders with real objects inside the lab scope before use.

## 1. Which points in the software supply chain need protection?

The software supply chain spans far more than the application source repository:

~~~mermaid
flowchart LR
    A["Git accounts and changes"] --> B["App code and pipeline config"]
    B --> C["Dependencies, plugins, and toolchain"]
    C --> D["Build runner"]
    D --> E["JAR or container image"]
    E --> F["Artifact repository"]
    F --> G["Deployment policy check"]
    G --> H["OCI workload"]
    I["Vault and signing keys"] --> D
    J["SBOM, provenance, and reports"] --> G
~~~

A dependency or Maven plugin can execute arbitrary code inside the build runner. Someone able to edit the build spec can alter build commands. Someone able to write to the artifact repository can replace the package that the deployment step downloads. Hence, protecting only the `main` branch is insufficient.

| Attack surface | Example | Consequence to prevent |
| --- | --- | --- |
| Git account | Account with merge rights compromised | Unreviewed code enters the release branch |
| Pipeline configuration | Replacing test command with a no-op always-pass command | Untested artifact gets published |
| Dependencies/plugins | Adding an unvetted library or plugin | Unexpected code executes inside the builder |
| Secrets | Token logged or baked into an image layer | Readers of logs/images reuse the credential |
| Pipeline identity | Build granted production management permissions | Code during build directly mutates live resources |
| Artifact repository | Tag repointed to another image | Wrong content deployed despite unchanged version label |
| Evidence | Reports generated by untrusted code itself | Deployment trusts unverified claims |
| Deployment policy | Allowing arbitrary signature check bypasses | Out-of-process package enters production |

Separate two objectives: **preventing unauthorized actions** and **proving the deployed package came through a trusted process**. IAM addresses part of the first objective; it does not by itself prove artifact contents are safe.

## 2. Splitting identities by task and trust level

### 2.1. Common identities that appear

| Identity | Appropriate work | Permissions not to bundle by default |
| --- | --- | --- |
| Developer | Push branches, open pull requests, view build results | Manage production secrets or edit signing keys |
| CI/CD administrator | Configure pipelines and source connections | Freely alter security policies outside scope |
| Pull-request check pipeline | Compile and run tests on proposed code | Read release secrets, sign packages, or deploy to production |
| Release build pipeline | Build trusted code, publish artifacts | Manage IAM or access production business data |
| Signing/release identity | Verify evidence then sign or promote package | Execute arbitrary scripts from pull requests |
| Deployment pipeline | Read accepted packages and update target environment | Modify source code or change trusted key lists |
| Application identity | Read/write services per runtime needs | Reuse builder permissions across the tenancy |
| Security administrator | Manage policies, keys, exceptions, and incident response | Unaudited silent modifications |

"PR check pipeline" and "release pipeline" are design roles. Implement them with genuinely distinct identities and permissions rather than merely renaming two stages.

### 2.2. Resource principals and dynamic groups on OCI

OCI DevOps uses resource principals so pipelines interact with OCI services. Dynamic groups identify which resources receive corresponding policies. Resource types and matching rule examples are documented in [DevOps IAM Policies](https://docs.oracle.com/en-us/iaas/Content/devops/using/devops_iampolicies.htm).

Example matching rule for **one specific release build pipeline**:

~~~text
ALL {
  resource.type = 'devopsbuildpipeline',
  resource.id = 'ocid1.devopsbuildpipeline.oc1..REPLACE_TRUSTED_PIPELINE'
}
~~~

Name the dynamic group `JavaReleaseBuild`. This pattern prevents every build pipeline in the compartment from automatically inheriting the release pipeline's privileges.

Another dynamic group can target deployment pipelines using resource type `devopsdeploypipeline` and its OCID. Never lump builds, deployments, and unrelated resources into one group just to write fewer policies.

OCI notes that CLI/SDK inside build runners authenticate using the build pipeline's resource principal. Therefore, **omitting a secret from YAML does not stop a build from reading it**: code inside the build can still call the API if IAM grants the principal access. See [Build Runner Runtime Details](https://docs.oracle.com/en-us/iaas/Content/devops/using/runtime_details.htm).

### 2.3. Different stages do not automatically create permission boundaries

If two steps run under the same identity that has permission to read secrets or sign packages, placing a "Verify" step before a "Sign" step does not revoke permissions from the earlier step.

Recommended design:

~~~mermaid
flowchart TD
    A["PR or unaccepted code"] --> B["Check pipeline: low privilege"]
    B --> C["Test results for review"]
    C --> D["Code merged under branch protection"]
    D --> E["Release pipeline: controlled source and config"]
    E --> F["Artifact and evidence bound to digest"]
    F --> G["Release identity verifies criteria then signs"]
    G --> H["Deployment verifies digest, signer, and policy"]
~~~

If using a separate signing system, never let it accept an arbitrary digest and sign unconditionally. It must verify the artifact came from an authorized source/build, passed checks, and carries valid evidence. Otherwise, moving keys off the builder only relocates an easily abused signing tool.

## 3. Writing resource-specific IAM

### 3.1. Reading a policy via four questions

A statement must specify:

| Question | OCI component |
| --- | --- |
| Who is permitted? | Group, dynamic group, or appropriate principal |
| What may they do? | Verb and resource type |
| Where? | Tenancy or compartment |
| Under what conditions? | Condition variables supported by the resource type/API |

The verbs `inspect`, `read`, `use`, and `manage` do not carry identical granular meanings across every service. Consult the resource type's permission/API reference rather than assuming `use` is always narrow.

### 3.2. Granting read access only to the needed secret bundle

Suppose the token secret for reading a Maven repository lives in compartment `BuildSecrets`. Example policy for the release pipeline's dynamic group:

~~~text
Allow dynamic-group JavaReleaseBuild to read secret-bundles in compartment BuildSecrets where target.secret.id = 'ocid1.vaultsecret.oc1..REPLACE_MAVEN_TOKEN_SECRET'
~~~

Substitute your group name, compartment, and OCID. For tenancies using identity domains, format domain/group names per your tenancy's IAM setup.

`secret-bundles` covers retrieving secret contents. Reading secret metadata does not equal reading the value; conversely, granting `manage secret-family` just to fetch contents is overly broad. Resource types, APIs, and `target.secret.id` conditions are documented in [Vault, Key Management, and Secret Management Policy Reference](https://docs.oracle.com/en-us/iaas/Content/Identity/policyreference/keypolicyreference.htm).

The statement above illustrates reading one secret; it is not a complete policy set for Git, builds, registries, and deployments. If using an external connection, satisfy that integration's policy requirements too.

IAM evaluates the union of active allow statements. Adding one secret-scoped statement does not revoke a broader statement granted earlier. To tighten permissions, locate and narrow or remove the broader grants.

### 3.3. Defining infrastructure resource boundaries

Example compartment layout:

~~~text
Tenancy
├── DevOpsLab       # Projects and pipelines
├── BuildSecrets    # Credentials for build/release
├── ReleaseStore    # Published artifacts
├── AppDev          # Non-production runtime resources
└── AppProd         # Production resources
~~~

Compartments do not create network isolation or block cross-access by themselves. IAM policies, VCNs, routing, network rules, and target-service permissions still must be configured.

A Java build needs no permissions to manage Compute, volumes, or Databases if it only compiles and runs local tests. If integration tests need test resources, scope those permissions separately. Never use production database admin credentials to run tests on every PR.

For OKE deployments, OCI API permissions and Kubernetes RBAC are separate layers. For Oracle Database, OCI IAM governing the database service resource does not replace SQL privileges of the application database account.

### 3.4. Auditing indirect privileges

Anyone who can edit a pipeline can change commands executed under the pipeline's identity. Anyone who can edit a dynamic group can change which resources receive its policies. Anyone who can edit verification policy can swap trusted signers.

Therefore, review permissions together across:

- Editing pipelines, stages, build sources, and triggers.
- Editing scripts, POMs, plugins, and build configurations.
- Editing IAM policies and matching rules.
- Editing secrets, secret versions, source connections, and artifact repositories.
- Editing signing keys, verification policies, and exception mechanisms.

An identity that cannot directly read a secret still poses equivalent risk if it can edit configuration to run code under an identity that can read that secret.

## 4. Protecting source code and CI/CD configuration

Require code review for both application code and execution-controlling files: `build_spec.yaml`, shell scripts, POMs, parent POMs, Maven/Gradle configs, Dockerfiles, and deployment manifests.

With OCI Code Repository, configure approval rules, merge checks, and branch protection. Oracle supports merging via pull requests and checking build status; exact behavior is documented in [Code Repository Settings](https://docs.oracle.com/en-us/iaas/Content/devops/using/reposettings.htm).

Organizational rules to clarify:

- Who can alter merge rules and reviewer lists?
- Which commit must a build result tie to?
- Do new commits pushed after review dismiss prior approvals or require re-testing?
- Who can change the build spec path, Git source, or runtime parameters?
- How are changes to security gates, trust keys, and release permissions reviewed?

Never rely solely on a branch name supplied by a PR author as proof of trusted code. Triggers and release pipelines must verify the exact repository, revision, and source conditions accepted by the organization.

When running code from untrusted forks/PRs, use a low-privilege identity with no release secrets and no signing access. Caches or workspaces from that flow must also never flow automatically into privileged builds.

Risks around pipeline configuration tampering and secrets in CI/CD are analyzed in the [OWASP CI/CD Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/CI_CD_Security_Cheat_Sheet.html). In this lesson, separating identities and trusted sources is the recommended design to contain blast radius.

## 5. Lifecycle management of secrets

### 5.1. Secrets differ from standard configuration

| Data type | Examples | Handling approach |
| --- | --- | --- |
| Non-secret config | Region, environment name, HTTP port | Can be managed in versioned configuration |
| Resource identifiers | Compartment OCID, secret OCID | Not secret values; still avoid unnecessary metadata exposure |
| External credentials | Git PAT, Maven repository token | Store in secret manager; scope access and expiration |
| Database credentials | App password, migration credentials | Separate per environment and purpose |
| Private keys | OCI API signing keys, SSH keys | Avoid long-lived distribution to runners when identity mechanisms exist |
| Artifact signing keys | Keys certifying release packages | Separate signing rights from admin rights |

A password encrypted at rest can still leak at runtime when used. Base64 is encoding, not security encryption. Masking values in a UI also does not prevent a plugin in the same process from reading that value.

Never treat pipeline parameters, regular YAML variables, or `exportedVariables` as a secret store. Never embed production passwords into a JAR, packaged `application.properties`, or image so the app "comes preconfigured."

### 5.2. Supplying secrets from OCI Vault to trusted builds

Suppose the Maven project uses a private repository with ID `corporate-maven`. Account `build-reader` only has read permission for needed dependencies. The token is stored in Vault, and the release pipeline has IAM permission to read that exact secret.

Illustrative build spec:

~~~yaml
version: 0.1
component: build
timeoutInSeconds: 1800
shell: bash
failImmediatelyOnError: true

env:
  vaultVariables:
    PRIVATE_MAVEN_TOKEN: "ocid1.vaultsecret.oc1..REPLACE_MAVEN_TOKEN_SECRET"

steps:
  - type: Command
    name: Verify trusted Java source with private dependencies
    timeoutInSeconds: 1200
    command: |
      set -euo pipefail
      set +x
      cd "${OCI_PRIMARY_SOURCE_DIR}"
      : "${PRIVATE_MAVEN_TOKEN:?Private Maven token is unavailable}"
      umask 077
      settings_path="$(mktemp)"
      trap 'rm -f "$settings_path"' EXIT

      cat > "$settings_path" <<'MAVEN_SETTINGS'
      <settings xmlns="http://maven.apache.org/SETTINGS/1.2.0">
        <servers>
          <server>
            <id>corporate-maven</id>
            <username>build-reader</username>
            <password>${env.PRIVATE_MAVEN_TOKEN}</password>
          </server>
        </servers>
      </settings>
      MAVEN_SETTINGS

      mvn --batch-mode --no-transfer-progress \
        --settings "$settings_path" clean verify
~~~

Replace the OCID, account, and repository settings with real lab objects. Your POM or mirror config must reference the matching ID `corporate-maven`. The snippet illustrates credential injection; it does not create the repository or include publishing steps.

Per [OCI Build Specification](https://docs.oracle.com/en-us/iaas/Content/devops/using/build_specs.htm), `vaultVariables` references a secret OCID and exposes its value as an environment variable across build spec steps. Vault and build pipeline must reside in the same tenancy with matching access policies.

Notable safeguards:

- The actual secret value never appears in YAML.
- `set +x` avoids shell tracing printing values during command expansion.
- Variable check reports only missing credentials without printing the value.
- The single-quoted heredoc delimiter preserves literal `${env.PRIVATE_MAVEN_TOKEN}` in settings for Bash.
- Maven resolves the environment variable when parsing settings.
- `umask 077` restricts temp file permissions; `trap` cleans up the file on shell EXIT.
- The token is never passed via `-Dpassword=...` CLI flags or written to output artifacts.

Settings `${env.NAME}` interpolation follows the [Maven Settings Reference](https://maven.apache.org/settings.html).

Even though the settings file does not contain the expanded token, Maven, plugins, and child processes can still read environment variables. Thus, this pattern applies only to controlled sources and build tools. Deleting the file or unsetting variables afterward cannot undo reads already performed by a process.

### 5.3. Places that accidentally retain secrets

| Location | Examples to avoid |
| --- | --- |
| Logs | `printenv`, `env`, shell tracing, debug HTTP headers |
| Git | PATs in remote URLs, passwords in settings or test fixtures |
| Artifacts | `.env` files, wallets, credentials inside packaged directories |
| Image layers | Copying a secret then deleting it in a later layer |
| Caches | Caching entire config directories containing credentials |
| Test reports | Connection strings containing passwords |
| Diagnostic data | Heap dumps, core dumps, or debug files carrying tokens |
| Process arguments | Credentials on command lines visible via process inspection |

Log-masking tools may fail to catch transformed, split, or encoded forms of a value. Never rely on masking as an excuse to run untrusted code with secrets present.

`.gitignore` only ignores untracked files; it neither detects credentials inside valid tracked files nor scrubs commit history.

### 5.4. Rotation must stay synchronized with target systems

A token or password rotation procedure includes:

1. Identify consumers, expiration, owners, and whether two credentials can be valid simultaneously.
2. Create the new credential in the target system or via a supported rotation mechanism.
3. Store the new version in Vault and test with a lab/canary consumer.
4. Switch consumers to the new value and confirm new builds/workloads succeed.
5. Revoke the old credential at the target system.
6. Monitor authentication errors and retain change evidence.

Vault tracks version states such as current, pending, and previous. A newly uploaded version should not be confused with the version consumers actively use. Oracle explains version transitions in [Managing Secrets](https://docs.oracle.com/en-us/iaas/Content/secret-management/Concepts/manage-secrets.htm).

Updating a value in Vault does not automatically change the password inside Oracle Database or revoke a PAT on a Git server. Running processes also do not automatically forget tokens already read. Verify rotation with a fresh consumer and confirm the old credential is rejected as planned.

When a secret leaks, prioritize revoking or disabling the exposed credential. Deleting logs or bumping a Vault version while the old credential stays active leaves the risk open.

## 6. Protecting dependencies, plugins, and build environments

### 6.1. Inputs go beyond application libraries

Inputs to a Java build include:

- Direct and transitive dependencies.
- Parent POMs, BOMs, and Maven plugins.
- Maven/Gradle distributions, wrappers, and JDKs.
- Scripts downloaded during builds.
- Base images and OS packages inside images.
- Scanners, signing tools, and their configurations.

Pin versions of critical components, review changes, and use controlled download sources. For containers, digest-pinned base images fix exact contents while still requiring patching plans when vulnerabilities are disclosed.

Avoid downloading scripts from mutable URLs and immediately executing them without verifying source and content. A checksum downloaded alongside a script from an attacker-controlled location provides no independent assurance.

For internal Maven repositories, govern package namespaces/coordinates, publish permissions, and mirrors for both dependencies and plugins. A package name or version that "looks right" does not prove publisher origin.

### 6.2. Caches and workspaces are also inputs

Caches populated by PR runs can contain tampered data designed to influence release builds. Partition caches by trust level and write permissions, not just by cache key names.

Ephemeral runners reduce leftover state, yet do not guarantee dependencies or build specs are trustworthy. Private networking also does not make code inside a runner safe.

Restrict egress to required sources, govern proxies, and enforce TLS verification. Network paths to external Maven repositories and to OCI services are distinct configurations; a Service Gateway does not replace connectivity to arbitrary Internet services.

### 6.3. Scanning the right data at the right time

| Check | Goal | What it does not replace |
| --- | --- | --- |
| Secret scanning | Find credentials that may slip into code/artifacts | Revoking exposed credentials |
| Static analysis | Find defect patterns in code | Verifying dependency origin |
| Dependency analysis | Identify libraries, versions, and known vulnerabilities | Detecting every malicious behavior |
| Container scanning | Inspect image packages/layers per scanner scope | Verifying signers and build provenance |
| Malware/policy scan | Detect specific payloads or policy violations | Guaranteeing immunity to all attacks |
| Signatures/provenance | Verify accepted package and release origin | Proving zero security bugs remain |

Gates must specify scope, vulnerability databases, scan timing, thresholds, tool-failure handling, and time-bound exceptions. Never turn "scan failed to run" into "zero vulnerabilities found."

For known vulnerabilities, weigh severity, exploitability in your application, available patches, and mitigations. Exceptions must bind to an artifact/version, accountable owner, and expiration date.

**Check OCI service lifecycles before picking tools.** Per Oracle notices checked on November 21, 2026, ADM is planned to be retired as a public OCI service; the final EOL date is unconfirmed and no earlier than December 31, 2026, with restricted onboarding of new external customers planned from October 10, 2026. Do not assume new tenancies can enable ADM per legacy guides. Choose a supported dependency analysis tool and plan migration for existing integrations. Source: [Oracle Service Change Announcements](https://docs.oracle.com/en-us/iaas/Content/servicechanges.htm).

## 7. Artifact identity and accompanying evidence

### 7.1. Distinguishing evidence types

| Component | Question answered | Limitation |
| --- | --- | --- |
| Tag or version | What does the team call the release? | Can have contents swapped if repo allows |
| Digest/checksum | Which exact byte stream is referenced? | Does not prove who created the content |
| Signature | Which key-holding principal vouched for it? | Keys or signing flows can be abused |
| SBOM | Which components are inside the package? | Does not prove every component is safe |
| Provenance | From which source, inputs, and builder was it made? | Requires trusting the generator and evidence integrity |
| Test/scan reports | Which checks ran on which object? | Can reference the wrong object or be forged |

Store JARs in Artifact Registry and images in Container Registry following team versioning practices. Verify digests after retrieving packages, not filenames alone.

Two files named `app.jar` can have different contents. Tag `release-1.4` can also move to another image if overwritten. For deterministic deployments, use digests and record their links to business versions.

### 7.2. SBOMs and provenance serve different purposes

An SBOM in a supported format like CycloneDX or SPDX helps inventory components. Provenance describes the build process and source that produced an artifact. This concept is presented in [SLSA Provenance](https://slsa.dev/spec/v1.2/provenance).

Teams should preserve at least these links:

~~~text
Artifact digest
    ├── Repository and revision actually built
    ├── Builder/pipeline identifier and build run
    ├── Build configuration and critical inputs
    ├── SBOM of the exact product
    ├── Test/scan results for the exact digest
    └── Signature/attestation from a trusted principal
~~~

Record the revision of the primary source actually built; a trigger commit may come from another repository. When multiple sources or external non-Git dependencies exist, record those inputs too.

A JSON file that self-reports a commit and is named `provenance.json` does not prove authenticity. If untrusted code can edit that file and sign with the same held permissions, the claims can still be false.

SLSA is a specific evaluation framework; merely using OCI Managed Build or generating metadata does not equal achieving a SLSA level. Evaluate builder isolation, evidence generation, tampering resistance, and verification.

### 7.3. Promoting the exact verified product

After packaging, tests/scans and signing must bind to the exact content being deployed. If a later step modifies the JAR, changes the base image, or rebuilds, the new digest must undergo evaluation per policy.

Retain artifacts long enough for rollback and investigation. Control overwrite/delete permissions, and separate unapproved staging artifacts from release artifacts when needed.

An image signature does not automatically sign standalone JARs outside the image or attached reports. If reports/SBOMs/provenance must be protected, bind them to digests and verify via appropriate attestations or signatures.

## 8. Signing and verifying container images on OCI

### 8.1. Separating push, sign, and trust permissions

Three capabilities must be governed separately:

1. Writing an image to a repository.
2. Using a key to create an image signature.
3. Modifying policy defining which keys deployments trust.

Someone with push permission should not automatically hold release-signing permission. Someone with signing permission should also not freely add new trusted keys to deployment policy without review.

OCI Container Registry supports image signatures using asymmetric RSA keys in OCI Vault. Signatures bind to a specific image in the registry; AES keys are not used for this mechanism. See [Signing Images for Security](https://docs.oracle.com/en-us/iaas/Content/Registry/Tasks/registrysigningimages_topic.htm).

Keeping keys in a key management service avoids distributing private key files. However, if a builder can call signing operations unconditionally, code compromising the builder can still sign unwanted content. Protecting signing permissions and conditions is as critical as protecting the key itself.

### 8.2. Command template for signing a verified image

Assume the image has been pushed, its digest matches the tested product, and the corresponding image OCID is known. The following variables are identifiers, not private keys:

| Bash variable | Value to supply |
| --- | --- |
| `REGISTRY_COMPARTMENT_OCID` | Compartment holding the image repository |
| `SIGNING_KEY_OCID` | RSA key designated for releases |
| `SIGNING_KEY_VERSION_OCID` | Appropriate key version |
| `IMAGE_OCID` | OCID of the exact verified image |

Run under the authorized release identity holding registry permissions and key-signing permissions:

~~~bash
oci artifacts container image-signature sign-upload \
  --compartment-id "$REGISTRY_COMPARTMENT_OCID" \
  --kms-key-id "$SIGNING_KEY_OCID" \
  --kms-key-version-id "$SIGNING_KEY_VERSION_OCID" \
  --signing-algorithm SHA_256_RSA_PKCS_PSS \
  --image-id "$IMAGE_OCID" \
  --description "Java release from approved build"
~~~

Supported flags and algorithms follow [OCI CLI: sign-upload](https://docs.oracle.com/en-us/iaas/tools/oci-cli/latest/oci_cli_docs/cmdref/artifacts/container/image-signature/sign-upload.html).

Never sign "the latest image" by looking up a tag after a delay. Resolve the image OCID from the accepted image/digest and re-verify before signing.

The description string does not substitute for review or provenance evidence; it is caller-supplied metadata.

### 8.3. Verifying with policy-designated trusted keys

Deployments must fetch trusted key lists from protected configuration, never blindly trusting a key self-declared by the artifact.

Command template:

~~~bash
oci artifacts container image-signature get-verify \
  --compartment-id "$REGISTRY_COMPARTMENT_OCID" \
  --repo-name "java/orders-api" \
  --image-digest "$EXPECTED_IMAGE_DIGEST" \
  --trusted-keys "$TRUSTED_KEY_OCID" \
  --compartment-id-in-subtree false
~~~

`EXPECTED_IMAGE_DIGEST` must be the full digest of the image intended for deployment; `TRUSTED_KEY_OCID` comes from the target environment's policy. Syntax source: [OCI CLI: get-verify](https://docs.oracle.com/en-us/iaas/tools/oci-cli/latest/oci_cli_docs/cmdref/artifacts/container/image-signature/get-verify.html).

This is a signature check, not the entire deployment gate. Integrations must check the actual verification outcome structure of the CLI/API version along with signer and digest constraints—not merely that the command returned JSON without HTTP errors or printed the word "signature."

For JARs in generic Artifact Registry, use a file-appropriate signing/verification or attestation mechanism. The `container image-signature` commands above do not apply directly to generic JAR files.

### 8.4. Enforcing policy on OKE

OKE offers an image verification policy for OCIR images signed with Vault keys. When enabled, configure at least one trusted key and reference images by digest in manifests. This policy does not automatically cover every external registry. Source: [Enforcing Signed Images on OKE](https://docs.oracle.com/en-us/iaas/Content/ContEng/Tasks/contengenforcingsignedimagesfromocir.htm).

Example image field, substituting hostname, namespace, and full digest:

~~~yaml
spec:
  containers:
    - name: orders-api
      image: "<region>.ocir.io/<namespace>/java/orders-api@sha256:<full-digest>"
~~~

This is an illustrative manifest snippet, not a complete Deployment.

Enabling the policy with an empty key list fails to restrict signers. With multiple keys, one matching valid signature may suffice; do not assume all keys must sign simultaneously. OKE also provides break-glass mechanisms that must be governed and monitored.

Organizations must audit permissions to edit policy, create workloads, and invoke exceptions. A valid signature does not prove an image is vulnerability-free; continue checking scans, provenance, and release criteria.

## 9. Designing verifiable gates

A deployment gate can be expressed as business rules:

~~~text
Permit deployment only when all hold:
  - downloaded digest matches the accepted digest;
  - artifact originates from an authorized repository/release source;
  - signature or attestation is verified;
  - signer/builder is in the trusted set;
  - source, test, and scan evidence belong to the exact artifact;
  - exception, if any, is valid and properly scoped;
  - target environment config and deployment identity are valid.
~~~

This is design logic, not a YAML block OCI parses natively. Implement it using appropriate CI/CD checks, verification tools, or admission policies.

Every condition should have both an allowed test case and a denied test case:

| Condition | Passing case | Must-deny case |
| --- | --- | --- |
| IAM secret read | Pipeline A reads lab secret A | A tries to read out-of-scope lab secret B |
| Trusted source | Build from exact accepted revision | Artifact from different source with same name |
| Integrity | Digest matches tested package | Byte-altered package or repointed tag |
| Signature | Valid signer trusted by environment | Unsigned or signed by out-of-policy key |
| Scan results | Report matches exact artifact within threshold | Missing report or scanner error |
| Identity isolation | PR runs low-privilege tests only | PR calls API to fetch release secrets |
| Exceptions | Scoped to artifact, expiry, and owner | Expired exception or blanket repo exemption |
| Gate edit rights | Designated security/governance group | Deployer modifying trusted signers unilaterally |

Designs must specify behavior when Vault, registry, or verification tools are unreachable. For production releases, never fail-open by turning verification errors into permits. Any emergency bypass process requires narrow scope, named owner, evidence, and expiration.

Minimize conflicts between security and availability by pre-staging signed good artifacts, verified registry/key paths, pull permissions, and rollback plans. Never wait for an outage to discover a rollback artifact depends on a deleted key.

## 10. Monitoring and incident response

### 10.1. Evidence to correlate

Record identifiers without storing secret values:

- Repository, revision, and associated pull requests.
- Project, pipeline, build run, and deployment IDs.
- Execution identity and resource scope.
- Artifact digest, repository version, and image OCID if applicable.
- Secret OCID/version recorded per integration capability.
- Key OCID, key version, and verification outcome.
- Test/scan results, exceptions, and change approvers.

Correlate build/deployment logs with OCI Audit and related service events. Monitor changes to IAM, pipeline configs, source connections, registry permissions, verification policies, and anomalous secret/key access.

Metadata can still reveal architecture or internal naming; restrict readers appropriately. Never log plaintext credentials in the name of investigative convenience.

### 10.2. When a secret leak is suspected

Recommended response sequence:

1. Identify which credential was exposed and which systems still accept it.
2. Stop flows that could continue leaking, handle running builds, and isolate runners per platform capabilities.
3. Revoke or disable the credential, adjusting principal permissions if needed.
4. Preserve evidence under access control; restrict access to logs/artifacts containing sensitive data.
5. Issue a new narrow-scoped credential and verify new consumers.
6. Audit actions performed during the exposure window.
7. Fix the leak path before re-enabling flows.

Never assume editing a policy immediately strips cached data or tokens from running processes. Verify revocation effectiveness and handle active processes.

If a secret entered Git, deleting it in a new commit does not purge clones and history. Credential revocation and history remediation must be coordinated together.

### 10.3. When artifact or builder tampering is suspected

Halt promotion of related packages and determine affected digests and build scopes. Preserve logs, source revisions, provenance, metadata, and suspect artifacts for investigation.

If a signing key was abused, simply re-signing all packages with a new key can legitimize tampered packages. First verify which products are trustworthy, rotate signer trust policy under control, and rebuild from verified sources as needed.

When rolling back, choose an artifact with verified provenance and integrity, and check compatibility with the current schema/database. An old JAR does not automatically reverse migrations or restore altered data.

### 10.4. Controlling costs and retention

Pipelines incur costs from repeated builds, scanning large images, provisioning test environments, and retaining logs/artifacts indefinitely. Bound triggers, runner shapes, timeouts, and test resources to actual workload scope.

Set retention periods while keeping enough artifacts and evidence for investigation and rollback. Never delete keys or secrets still serving workloads just to reduce lab resource counts; verify consumers and dependencies before cleanup.

## 11. Practice in a lab compartment

Labs should use synthetic secrets, test repositories, and images with no business data. There is no need to use production credentials to prove IAM separation works.

### Step 1: build an identity matrix

Create or designate separate identities for PR checks, releases, and deployments. Record pipeline OCIDs, dynamic groups, policies, and who can edit them.

Produce a table mapping who reads which secrets, writes to which repos, signs with which keys, and mutates which environments. Check for indirect grants from overly broad policies.

### Step 2: test IAM with two lab secrets

Create lab secrets A and B with dummy values. Allow only the release pipeline to read A. Test both allowed and denied accesses, recording outcomes without printing secret contents.

Also verify the PR pipeline cannot read A even when calling the API directly via its principal without `vaultVariables`. If that succeeds, fix IAM policies rather than merely removing environment variables.

### Step 3: inject a secret into a trusted build

Apply the Vault/Maven template to a lab repository if you have a private dependency repository. If not, keep the Maven config as a template and test secret injection with a lab consumer that never prints the value.

Confirm the secret does not appear in Git, logs, output directories, shared caches, or packaged outputs. For secret scanners, use tool-supported test patterns rather than putting real credentials in code.

### Step 4: preserve artifact identity

Build and verify a JAR or image; record digest, source, build run, and test results. Keep SBOMs/reports if corresponding tools are configured.

Modify a lab copy of the artifact or select another image and confirm digest checks catch the mismatch. Never modify shared repositories or packages serving real workloads to simulate tampering.

### Step 5: test signatures and policy

For OCIR images, sign the exact image with a lab key, verify with the trusted key, and test unsigned or differently signed cases.

If an OKE lab cluster is available, enable the verification policy with the chosen key and test allow/deny on sample workloads. Without a cluster, complete the registry/CLI verification steps and explicitly record that cluster-level enforcement was not tested.

### Step 6: test rotation and close the lab

Rotate the lab secret, run a fresh consumer, and confirm the old credential is rejected at the authenticating target. If using dummy strings in Vault only, note clearly that you verified version switching without testing external revocation.

Save evidence containing no secret values. Revoke test tokens, clean up unused lab pipelines/registries/workloads, and handle keys according to verified dependencies.

## 12. Misconceptions to avoid

| Misconception | Accurate understanding |
| --- | --- |
| "Stored in Vault means any build can use it" | Only necessary consumers at the right trust level should get access |
| "Not declaring a variable blocks reading the secret" | A principal with IAM access can still call the API directly |
| "Later stage signs, so earlier stage cannot sign" | Inspect actual identities and permissions of each stage |
| "PR passed tests so the code is trusted" | Tests and review/release-source gates serve different purposes |
| "Signed image means zero vulnerabilities" | Signatures prove signer association, not absence of bugs |
| "Checksum next to the JAR prevents tampering" | Needs a trusted source for the digest or signed attestation |
| "SBOM equals provenance" | SBOM lists components; provenance describes source and build process |
| "Building on OCI automatically achieves SLSA" | Specific framework requirements must be evaluated |
| "Deleting secret from Git revokes it" | Credentials may remain valid on target systems |
| "Having an artifact backup guarantees rollback" | Still depends on permissions, verify keys, runtime, and data state |

A controlled CI/CD supply chain binds **right-scoped identities**, **consumer-scoped secrets**, and **provenance-verified artifacts**. As you expand from a lab Java app to Compute, storage, and Oracle databases, continue verifying both allowed paths and denied paths, traceability, and recoverability.
