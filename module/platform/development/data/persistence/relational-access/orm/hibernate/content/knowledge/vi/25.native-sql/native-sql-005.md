# Trả về thực thể từ SQL với các cột cần thiết cho ánh xạ

Hibernate cho phép chạy **SQL gốc (native SQL)** khi HQL/JPQL không đủ diễn đạt nhu cầu, chẳng hạn dùng cú pháp đặc thù của hệ quản trị cơ sở dữ liệu, truy vấn legacy hoặc tận dụng một câu SQL đã được tối ưu. Nhưng có một khác biệt rất quan trọng giữa hai thao tác:

- Chạy SQL và nhận **các giá trị vô hướng**, các dòng `Object[]` hoặc một DTO.
- Chạy SQL và yêu cầu Hibernate **dựng một entity được ánh xạ** từ ResultSet.

Trường hợp thứ hai không đơn giản là đọc vài cột rồi gọi constructor. Hibernate cần đủ dữ liệu để nhận diện entity, hydrate trạng thái được ánh xạ, xử lý khóa ngoại của association, versioning, discriminator và các quy tắc mapping khác. Nếu ResultSet thiếu một cột cần thiết, truy vấn có thể thất bại ngay khi Hibernate xử lý kết quả, dù SQL tự nó chạy thành công trong công cụ database.

**Nguyên tắc chính:** khi trả về entity từ native SQL, hãy cung cấp **tất cả các cột mà mapping entity cần để hydrate đúng kết quả**. Khi chỉ cần một vài cột, hãy chọn projection scalar/DTO thay vì cố dựng entity không đầy đủ.

Bài này nằm trong chương **SQL gốc** của Hibernate ORM, trình bày theo Hibernate ORM 6.x và Jakarta Persistence. Cú pháp SQL trong ví dụ chủ yếu hướng tới database quan hệ thông thường; các trường hợp inheritance, secondary table, native function hoặc alias quoting có thể cần cách viết riêng tùy `Dialect` và phiên bản provider.

## 1. Native SQL entity result là gì?

Với HQL:

~~~java
List<Book> books = entityManager.createQuery(
        "select b from Book b where b.status = :status",
        Book.class
    )
    .setParameter("status", BookStatus.PUBLISHED)
    .getResultList();
~~~

Hibernate biết `Book` là entity và tự xây SQL dựa trên metadata mapping: tên bảng, tên cột, type descriptors, association, version và các chi tiết cần để tạo entity.

Với native SQL:

~~~java
List<?> rawResults = entityManager.createNativeQuery(
        "select id, title from books"
    )
    .getResultList();
~~~

Hibernate chỉ nhận SQL do developer viết. Nếu không khai báo entity mapping, kết quả thường là các scalar hoặc `Object[]` tùy số cột; nó không tự biến thành `Book` managed chỉ vì SQL đọc từ bảng `books`.

Muốn trả entity:

~~~java
@SuppressWarnings("unchecked")
List<Book> books = entityManager.createNativeQuery(
        "select b.* from books b",
        Book.class
    )
    .getResultList();
~~~

Đối số `Book.class` yêu cầu Hibernate áp dụng **entity result mapping**. Đó là điểm khác biệt: không chỉ chạy SQL mà còn yêu cầu Hibernate lấy những cột cần thiết để dựng trạng thái của Book.

### 1.1. Luồng thực thi khái quát

~~~mermaid
flowchart TD
    A["Native SQL do ứng dụng cung cấp"] --> B["Hibernate/JDBC thực thi SQL"]
    B --> C["ResultSet: cột + giá trị"]
    C --> D{"Đã khai báo entity result mapping?"}
    D -- Không --> E["Scalar / Object[] / projection"]
    D -- Có --> F["Đối chiếu cột với entity metadata"]
    F --> G{"Đủ cột và kiểu dữ liệu phù hợp?"}
    G -- Không --> H["Lỗi hydration / column resolution"]
    G -- Có --> I["Identity resolution trong Persistence Context"]
    I --> J["Entity managed / state theo mapping"]
~~~

Sơ đồ mô tả đường đi điển hình. Hibernate có cache và những cơ chế tối ưu khác; nhưng **thiếu mapped column không được khắc phục bằng cách hy vọng Hibernate tự đoán giá trị**.

## 2. Entity dùng xuyên suốt bài

Giả sử hệ thống bán sách có bảng:

~~~sql
create table books (
    id bigint generated by default as identity primary key,
    title varchar(200) not null,
    price numeric(12, 2) not null,
    status varchar(20) not null,
    version bigint not null
);
~~~

Đây là SQL minh họa kiểu identity; cú pháp sinh ID có thể khác theo DBMS.

Entity:

~~~java
package com.example.catalog;

import jakarta.persistence.*;
import java.math.BigDecimal;

@Entity
@Table(name = "books")
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id")
    private Long id;

    @Column(name = "title", nullable = false, length = 200)
    private String title;

    @Column(name = "price", nullable = false,
            precision = 12, scale = 2)
    private BigDecimal price;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false)
    private BookStatus status;

    @Version
    @Column(name = "version", nullable = false)
    private long version;

    protected Book() {}

    public Long getId() { return id; }
    public String getTitle() { return title; }
    public BigDecimal getPrice() { return price; }
    public BookStatus getStatus() { return status; }
    public long getVersion() { return version; }

    public void rename(String newTitle) {
        this.title = newTitle;
    }
}
~~~

Enum:

~~~java
package com.example.catalog;

public enum BookStatus {
    DRAFT, PUBLISHED, ARCHIVED
}
~~~

Trong ví dụ này, các mapped columns cần để Hibernate hydrate đầy đủ Book gồm:

| Thuộc tính Java | Cột SQL | Vì sao quan trọng? |
| --- | --- | --- |
| `id` | `id` | Primary key/identity của entity |
| `title` | `title` | Trạng thái basic đã ánh xạ |
| `price` | `price` | Trạng thái basic kiểu `BigDecimal` |
| `status` | `status` | Enum được chuyển đổi theo mapping |
| `version` | `version` | Optimistic locking và state được version hóa |

Một native SQL entity query phải cung cấp những cột tương ứng theo quy tắc result mapping. Ngược lại, nó **không cần chọn mọi cột vật lý trong database nếu cột đó không thuộc mapping cần hydrate**. Điểm cần xét là metadata ORM, không chỉ sơ đồ bảng.

## 3. Cách đơn giản nhất: SELECT đầy đủ và resultClass

### 3.1. JPA EntityManager

~~~java
import jakarta.persistence.EntityManager;
import java.util.List;

public List<Book> findPublished(EntityManager em) {
    @SuppressWarnings("unchecked")
    List<Book> books = em.createNativeQuery(
            """
            select b.id, b.title, b.price, b.status, b.version
            from books b
            where b.status = :status
            order by b.id
            """,
            Book.class
        )
        .setParameter("status", BookStatus.PUBLISHED.name())
        .getResultList();

    return books;
}
~~~

Chú ý:

1. SQL dùng **tên bảng/cột database** (books, title), không dùng entity name như HQL.
2. `Book.class` báo Hibernate rằng ResultSet cần được ánh xạ vào Book.
3. `status` được bind bằng chuỗi `PUBLISHED` vì SQL gốc đang so sánh với cột varchar; kiểu parameter cần tương thích database và driver.
4. Query trả entity Book có thể được persistence context quản lý khi thực thi trong scope phù hợp.
5. `id` và `version` cũng được chọn, không chỉ các field được hiển thị.

Một số cách viết dùng:

~~~java
@SuppressWarnings("unchecked")
List<Book> books = em.createNativeQuery(
        "select b.* from books b where b.status = :status",
        Book.class
    )
    .setParameter("status", "PUBLISHED")
    .getResultList();
~~~

`b.*` tiện khi entity được ánh xạ trên một bảng đơn giản và tất cả mapped columns cần thiết đều nằm ở bảng đó. Tuy nhiên, đây không phải giải pháp phổ quát cho entity có secondary tables, inheritance phức tạp, alias collision, derived/formula attributes hoặc cột phải được dựng từ expression.

### 3.2. Hibernate Session

Hibernate có API native query với kiểu kết quả:

~~~java
import org.hibernate.Session;

public List<Book> findBooks(Session session) {
    return session.createNativeQuery(
            """
            select b.id, b.title, b.price, b.status, b.version
            from books b
            where b.price >= :minimumPrice
            order by b.id
            """,
            Book.class
        )
        .setParameter("minimumPrice", new BigDecimal("100.00"))
        .getResultList();
}
~~~

`Session.createNativeQuery(sql, Book.class)` là cách Hibernate-specific để khai báo entity result. Nó giữ kiểu kết quả rõ ràng hơn JPA `Query` không generic của nhiều dòng API.

Có thể dùng `NativeQuery.addEntity(...)` trong các phiên bản Hibernate hỗ trợ để đăng ký entity return thay vì truyền result class từ đầu. Tuy nhiên overload và cú pháp fluent thay đổi theo version, nên với ví dụ chỉ một root entity, `createNativeQuery(sql, Book.class)` thường rõ ràng nhất.

### 3.3. Truy vấn native không tự thành HQL

Hai query sau **không giống nhau về ngôn ngữ**:

~~~java
// HQL: Book và status là entity/property names.
em.createQuery(
    "select b from Book b where b.status = :status",
    Book.class
);

// SQL gốc: books và status là table/column names.
em.createNativeQuery(
    "select b.* from books b where b.status = :status",
    Book.class
);
~~~

Native SQL có thể dùng tính năng DBMS không có trong HQL, nhưng đổi lại developer phải tự bảo đảm SQL ResultSet phù hợp với mapping ORM.

## 4. Vì sao không chỉ chọn id và title?

Đoạn sau phù hợp để lấy hai giá trị:

~~~sql
select b.id, b.title
from books b;
~~~

Nhưng nó **không phù hợp để yêu cầu trả Book entity đầy đủ** với mapping ở trên:

~~~java
// SAI VỀ MỤC ĐÍCH: Book còn price, status và version.
em.createNativeQuery(
    "select b.id, b.title from books b",
    Book.class
).getResultList();
~~~

Hibernate cần hydrate `price`, `status` và `version` theo entity mapping. Khi chúng vắng mặt, provider thường báo lỗi không tìm thấy column/column position trong JDBC ResultSet, hoặc một lỗi mapping/hydration khác.

Không có bảo đảm rằng Hibernate sẽ:

- Tự chạy SQL phụ để lấy mọi cột còn thiếu.
- Điền giá trị mặc định Java cho cột không có trong ResultSet.
- Xem một entity thiếu cột như entity read-only hợp lệ.
- Biến missing fields thành lazy attributes khi mapping chưa hỗ trợ lazy.
- Bỏ qua `@Version` chỉ vì query không muốn dùng cột version.

Ngay cả khi một phiên bản/cấu hình có hành vi đặc thù, **không thiết kế dựa trên partial entity hydration** trừ khi tính năng đó được provider/documentation cho phép rõ ràng.

### 4.1. Vì sao Hibernate cần trạng thái đầy đủ?

Một managed entity không chỉ là DTO hiển thị. Hibernate còn lưu state để phục vụ:

- Identity map và quản lý một Java instance cho cùng entity identity.
- Dirty checking: so sánh current state với loaded state.
- Optimistic locking qua `@Version`.
- Mapping enum, converter và custom types.
- Associations to-one thông qua foreign key.
- Lazy state/initialization và những chiến lược fetch khác.
- Lifecycle callback, refresh và xử lý entity update/delete.

Nếu giả định `price = 0` chỉ vì SQL không chọn price, Hibernate có thể hiểu sai trạng thái DB. Tương tự, nếu thiếu `version`, một update về sau có thể không còn thông tin đúng để kiểm tra optimistic locking.

### 4.2. Không “bổ sung” cột thiếu bằng giá trị giả

Cách sau có thể tạo ResultSet đủ **tên cột** nhưng sai **giá trị**:

~~~sql
-- KHÔNG NÊN dùng để lừa entity mapping.
select
    b.id,
    b.title,
    0 as price,
    'DRAFT' as status,
    0 as version
from books b;
~~~

Nếu DB thực tế có price khác 0 hoặc version khác 0, entity được hydrate sai. Khi flush, refresh, dirty checking hoặc business logic tiếp tục, lỗi có thể rất khó truy vết.

Đúng là chọn dữ liệu thật từ DB hoặc đổi sang projection chỉ có các giá trị cần dùng.

## 5. Chỉ cần vài cột: dùng scalar hoặc DTO projection

Nếu màn hình chỉ cần ID và title, hãy nói đúng mục đích:

~~~java
@SuppressWarnings("unchecked")
List<Object[]> rows = em.createNativeQuery(
        "select b.id, b.title from books b order by b.id"
    )
    .getResultList();

for (Object[] row : rows) {
    Number id = (Number) row[0];
    String title = (String) row[1];
    System.out.println(id.longValue() + ": " + title);
}
~~~

Đây là **scalar/multicolumn native result**, không phải entity result. Kiểu ID mà JDBC driver trả về có thể là `Long`, `BigInteger` hoặc dạng `Number` khác tùy DBMS/driver và khai báo cột; không cast tùy tiện mọi kết quả sang `Long` mà chưa hiểu result mapping.

### 5.1. DTO record cho read model

~~~java
package com.example.catalog;

public record BookPreview(
        Long id,
        String title
) {}
~~~

Có thể dựng DTO từ scalar result:

~~~java
@SuppressWarnings("unchecked")
List<Object[]> rows = em.createNativeQuery(
        "select b.id, b.title from books b"
    ).getResultList();

List<BookPreview> previews = rows.stream()
        .map(row -> new BookPreview(
                ((Number) row[0]).longValue(),
                (String) row[1]
        ))
        .toList();
~~~

Ở đây ứng dụng tự chuyển `Number` về `Long`. Với số liệu nullable hoặc decimal, cần kiểu và null handling phù hợp.

### 5.2. Vì sao DTO tốt hơn partial entity?

| Nhu cầu | Entity result | DTO/scalar result |
| --- | --- | --- |
| Đọc/chỉnh sửa trạng thái Book bằng dirty checking | Phù hợp | Không phù hợp |
| Lấy ID và title cho dropdown | Thường tải dư dữ liệu | Phù hợp |
| Cần Hibernate quản lý identity/lifecycle | Có | Không |
| Chỉ cần vài cột từ SQL legacy | Có thể thiếu mapping state | Phù hợp |
| Chọn biểu thức tính toán, aggregate hoặc window function | Không nhất thiết là entity columns | DTO/scalar phù hợp |
| Cập nhật Book về sau | Load entity đầy đủ | Dùng ID để tải Book trong unit of work mới |
| Yêu cầu memory thấp cho báo cáo lớn | Có overhead persistence context | Projection thường nhẹ hơn |

**Projection trả đúng phần dữ liệu yêu cầu**; entity result phải tôn trọng hợp đồng ánh xạ entity.

## 6. ResultSet phải khớp tên cột hay alias nào?

Với entity `Book` như ví dụ, mapping:

~~~java
@Column(name = "title")
private String title;
~~~

yêu cầu Hibernate nhận được giá trị của cột được mapping. Nếu SQL chọn:

~~~sql
select b.title from books b;
~~~

JDBC ResultSet thường có column label `title`. Nhưng nếu dùng alias:

~~~sql
select b.title as book_title from books b;
~~~

ResultSet có label `book_title`, không còn là `title` theo cách JDBC trả column label.

Khi để Hibernate tự suy luận entity result từ `Book.class`, provider cần nhận diện đúng các cột theo mapping; alias tùy ý có thể khiến Hibernate không tìm thấy column label như mong đợi.

### 6.1. Dùng alias khớp mapped column

Nếu SQL cần expression hay join nhưng muốn mapping đơn giản, alias về tên cột được mapping:

~~~sql
select
    b.id as id,
    b.title as title,
    b.price as price,
    b.status as status,
    b.version as version
from books b
where b.price > 100;
~~~

Các alias trùng mapped column names, ít gây nhầm lẫn hơn. Tuy vậy, với multi-entity result hoặc tên cột bị trùng, nên dùng result set mapping tường minh.

### 6.2. Tên thuộc tính Java và tên cột database khác nhau

Giả sử entity có:

~~~java
@Column(name = "book_title")
private String title;
~~~

Native SQL không tự nhận rằng `title` là tên cột thật. Truy vấn phải đọc `book_title` từ database và cung cấp alias/mapping phù hợp. Một HQL query dùng `b.title`, còn SQL dùng `b.book_title`.

Không ghép tên entity field vào native SQL rồi nghĩ Hibernate tự dịch chúng. Việc dịch path metadata là trách nhiệm của HQL/Criteria; native SQL là SQL gốc do developer chịu trách nhiệm.

### 6.3. Tên cột có chữ hoa, dấu nháy và dialect

Nếu schema có quoted identifiers như `"BookTitle"`, cách database và JDBC driver trả column labels có thể phụ thuộc quoting/case folding. Hibernate có quy tắc nhận diện identifier theo Dialect, nhưng native SQL result labels vẫn phải khớp result mapping.

Nên tránh alias trùng nhau, đặt tên rõ ràng, và dùng `@SqlResultSetMapping` khi alias phải khác tên cột ánh xạ.

## 7. @SqlResultSetMapping và @EntityResult

Khi SQL có alias đặc thù, hoặc cần ghép nhiều nguồn dữ liệu, Jakarta Persistence cung cấp `@SqlResultSetMapping` để khai báo cách đọc ResultSet.

### 7.1. Ví dụ alias khác mapped columns

Giả sử SQL legacy hoặc báo cáo trả:

~~~sql
select
    b.id as result_book_id,
    b.title as result_title,
    b.price as result_price,
    b.status as result_status,
    b.version as result_version
from books b
where b.status = ?;
~~~

Có thể đặt trên entity Book:

~~~java
@Entity
@Table(name = "books")
@SqlResultSetMapping(
    name = "BookFromAliasedNativeSql",
    entities = @EntityResult(
        entityClass = Book.class,
        fields = {
            @FieldResult(name = "id", column = "result_book_id"),
            @FieldResult(name = "title", column = "result_title"),
            @FieldResult(name = "price", column = "result_price"),
            @FieldResult(name = "status", column = "result_status"),
            @FieldResult(name = "version", column = "result_version")
        }
    )
)
public class Book {
    // Giữ nguyên các thuộc tính/mapping đã trình bày ở phần 2.
}
~~~

Đây là snippet minh họa phần annotations; không khai báo thêm một lớp Book trùng tên trong project. Annotation `@FieldResult` ánh xạ **tên thuộc tính entity** sang **column alias trong ResultSet**:

| FieldResult.name | FieldResult.column |
| --- | --- |
| `id` | `result_book_id` |
| `title` | `result_title` |
| `price` | `result_price` |
| `status` | `result_status` |
| `version` | `result_version` |

Gọi query với tên mapping:

~~~java
@SuppressWarnings("unchecked")
List<Book> books = em.createNativeQuery(
        """
        select
            b.id as result_book_id,
            b.title as result_title,
            b.price as result_price,
            b.status as result_status,
            b.version as result_version
        from books b
        where b.status = :status
        """,
        "BookFromAliasedNativeSql"
    )
    .setParameter("status", "PUBLISHED")
    .getResultList();
~~~

Tên mapping trong `createNativeQuery(sql, "BookFromAliasedNativeSql")` khác đối số `Book.class`: tham số thứ hai là **tên `@SqlResultSetMapping`**. Vì result mapping chỉ khai báo một `EntityResult`, mỗi row được ánh xạ thành Book; nếu mapping kết hợp nhiều entity/scalar, result shape có thể là `Object[]`.

### 7.2. Các lưu ý khi dùng @EntityResult

- `@FieldResult.name` là property path của entity, không phải SQL column name.
- `@FieldResult.column` phải trỏ tới column label/alias mà ResultSet thật sự trả về.
- Cần bao phủ những cột mapping cần để hydrate entity; không chỉ liệt kê ID và một field.
- Nếu entity có compound ID, association FK, embedded fields hoặc inheritance, quy tắc alias có thể phức tạp hơn.
- Không tự viết các giá trị giả để “đủ” field names.
- Mapping phải được đăng ký trong persistence unit, thường bằng annotation trên managed class hoặc cấu hình ORM phù hợp.

### 7.3. Khi nào nên dùng result set mapping?

Dùng `@SqlResultSetMapping` khi:

1. SQL trả alias khác với mapped column names.
2. SQL có nhiều bảng và tên cột trùng nhau.
3. Cần kết hợp một hoặc nhiều entity với scalar values.
4. Cần DTO constructor result từ native SQL.
5. SQL query được tái sử dụng và cần một hợp đồng rõ về hình dạng result.

Với query một bảng đơn giản, `createNativeQuery(sql, Book.class)` thường đủ; không cần tạo result mapping riêng cho mọi SELECT.

## 8. @NamedNativeQuery: đặt tên SQL gốc

Nếu SQL được dùng nhiều nơi, có thể khai báo named native query:

~~~java
@NamedNativeQuery(
    name = "Book.findPublishedNative",
    query = """
        select b.id, b.title, b.price, b.status, b.version
        from books b
        where b.status = :status
        order by b.id
        """,
    resultClass = Book.class
)
@Entity
@Table(name = "books")
public class Book {
    // Các mapped fields như phần 2.
}
~~~

Sử dụng:

~~~java
@SuppressWarnings("unchecked")
List<Book> books = em.createNamedQuery(
        "Book.findPublishedNative",
        Book.class
    )
    .setParameter("status", "PUBLISHED")
    .getResultList();
~~~

Ví dụ minh họa cách khai báo named query trong dự án Jakarta Persistence/Hibernate. Cú pháp/version của overload typed `createNamedQuery` phải khớp dependency JPA đang dùng.

Nếu query cần alias mapping, có thể dùng `resultSetMapping = "BookFromAliasedNativeSql"` thay cho khai báo `resultClass` tương ứng trong `@NamedNativeQuery`, theo hợp đồng annotation. Không cấu hình hai cách cạnh tranh cho một result shape mà không xác định rõ mục đích.

## 9. Khóa chính bắt buộc để Hibernate nhận diện entity

Hibernate dựa vào `@Id`/`@EmbeddedId` để phân biệt entity instances.

~~~sql
select b.id, b.title, b.price, b.status, b.version
from books b;
~~~

Nếu thiếu cột ID:

~~~sql
-- SAI: không đủ để dựng Book entity.
select b.title, b.price, b.status, b.version
from books b;
~~~

Hibernate không có định danh thực để đặt entity vào persistence context. Nó không thể chỉ dùng title hoặc row number tùy tiện, vì những giá trị này không nhất thiết duy nhất.

### 9.1. ID phải là giá trị thật

Không thay ID bằng:

~~~sql
-- KHÔNG NÊN: row_number không phải khóa chính của books.
select
    row_number() over (order by b.title) as id,
    b.title,
    b.price,
    b.status,
    b.version
from books b;
~~~

Đây là cách tạo một định danh tạm thời **không phải entity key**. Hibernate có thể nhầm identity, cập nhật sai row hoặc tạo trạng thái quản lý không hợp lệ.

Nếu cần row number cho báo cáo, dùng DTO/scalar projection; nếu cần entity Book, chọn `books.id` thật.

### 9.2. Composite key

Với `@EmbeddedId` hoặc `@IdClass`, ResultSet phải cung cấp **đủ mọi cột tham gia identifier**. Một phần của composite key không đủ để xác định entity.

Ví dụ đơn giản:

~~~java
@Embeddable
public class StockKey implements java.io.Serializable {
    private Long warehouseId;
    private Long productId;
    // equals/hashCode, constructor theo yêu cầu JPA.
}
~~~

~~~java
@Entity
public class WarehouseStock {
    @EmbeddedId
    private StockKey id;

    private int quantity;
}
~~~

Native SQL phải trả cả `warehouse_id` và `product_id` cùng các cột mapped cần thiết. Khi tên cột/field nested khác nhau, cấu hình `@SqlResultSetMapping` có thể cần field path/alias chính xác theo Jakarta Persistence và Hibernate version. Không chỉ chọn một key component rồi mong Hibernate tự suy ra phần còn lại.

## 10. @Version và optimistic locking

Trường `version` không phải cột trang trí. Hibernate dùng nó để kiểm tra optimistic locking:

~~~java
@Version
@Column(name = "version")
private long version;
~~~

Một update ORM điển hình có thể dùng:

~~~sql
update books
set title = ?, version = ?
where id = ? and version = ?;
~~~

Nếu native SQL entity result không trả `version` thật từ DB, Hibernate không có loaded version chính xác để đưa vào where clause. Vì vậy **hãy chọn version column khi entity được version hóa**.

### 10.1. Đừng cố tạo version giả

~~~sql
-- SAI: version 0 không đại diện dữ liệu thật.
select b.id, b.title, b.price, b.status, 0 as version
from books b;
~~~

Câu SQL vẫn trả một cột mang label version, nhưng mang giá trị không đúng. Về sau entity có thể gặp optimistic locking conflict giả hoặc hành vi sai về concurrency.

### 10.2. Bulk native SQL có thể bỏ qua versioning

Nếu dùng:

~~~java
em.createNativeQuery(
    "update books set title = :title where id = :id"
)
.setParameter("title", newTitle)
.setParameter("id", id)
.executeUpdate();
~~~

đây là native DML, không phải entity dirty checking. Nó không tự tăng `@Version` hay đồng bộ managed `Book` trong persistence context. Nếu database có trigger tăng version thì semantics lại phụ thuộc DBMS/trigger. Khi dùng native DML, cần chủ động xử lý optimistic locking, refresh/clear managed state và transaction boundary.

## 11. Foreign key của association to-one cũng là dữ liệu cần thiết

Giả sử Book có nhà xuất bản:

~~~java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "publisher_id")
private Publisher publisher;
~~~

Dù association được khai báo LAZY, Hibernate vẫn thường cần cột `publisher_id` để biết Book tham chiếu Publisher nào, tạo proxy/reference hoặc xác định association null.

Khi đó native SQL entity result phải bao gồm cột FK:

~~~sql
select
    b.id,
    b.title,
    b.price,
    b.status,
    b.version,
    b.publisher_id
from books b
where b.id = ?;
~~~

Không chỉ chọn `publisher.name` rồi bỏ `publisher_id`, vì entity mapping `Book.publisher` được xác định từ FK đã khai báo.

### 11.1. Lazy không có nghĩa được bỏ cột FK

Hai vấn đề khác nhau:

- **Lazy loading**: có tải entity Publisher đầy đủ ngay không?
- **Entity hydration**: có đủ thông tin để biểu diễn association của Book đúng không?

Hibernate có thể chưa tải Publisher, nhưng vẫn cần biết identifier để liên kết. Vì vậy chọn Book entity chỉ với basic fields mà bỏ FK có thể làm native query thiếu cột.

### 11.2. JOIN trong SQL không tự eager-fetch association

Giả sử:

~~~sql
select b.*
from books b
join publishers p on p.id = b.publisher_id
where p.country_code = 'VN';
~~~

Câu SQL join bảng publishers để **lọc** sách. Nó chỉ trả các cột Book từ `b.*`, không trả đầy đủ entity Publisher theo mapping riêng. Việc có JOIN không mặc nhiên làm `Book.publisher` initialized.

Muốn trả cả Book và Publisher như managed entity results, cần result mapping tương ứng cho hai entity và các column aliases không va chạm, hoặc chọn một fetch strategy khác. Native SQL không có từ khóa `join fetch` theo cú pháp HQL.

### 11.3. Association to-many là trường hợp khác

Với `@OneToMany`, collection thường được tải theo truy vấn riêng hoặc fetch plan khác. Không có một cột `items` nằm trên mỗi hàng Book mà query entity root phải chọn. **Không đồng nghĩa phải JOIN toàn bộ bảng child** để dựng Book.

Nếu SELECT JOIN một bảng child rồi trả `b.*`, có thể có nhiều result rows cho cùng Book. Hibernate identity map xử lý identity của entity, nhưng SQL vẫn trả dữ liệu trùng và result list/cardinality cần được xem xét. Đừng JOIN collection lớn chỉ để “đủ cột entity”.

## 12. Cột được chuyển đổi: enum, converter và custom types

Khi SQL trả raw column values, Hibernate vẫn áp dụng mapping type để chuyển sang Java attributes trong entity result.

### 12.1. Enum

~~~java
@Enumerated(EnumType.STRING)
@Column(name = "status")
private BookStatus status;
~~~

Database chứa chuỗi như `PUBLISHED`. Query entity result chọn cột `status`, Hibernate dùng enum mapping để tạo `BookStatus.PUBLISHED`. Nếu native SQL trả `"Published"` hoặc một số nguyên không phù hợp mapping, quá trình hydrate có thể lỗi.

Không thay giá trị DB bằng biểu thức có kiểu không tương thích rồi mong annotation tự xử lý:

~~~sql
-- Ví dụ không phù hợp với EnumType.STRING:
select 2 as status, ...
~~~

### 12.2. AttributeConverter

Một field có `@Convert` có thể được lưu dưới dạng khác trong database. Ví dụ `Money` được chuyển thành `String` hoặc `BigDecimal` qua converter. Entity result cần trả column value theo **kiểu database mà converter/mapping mong đợi** để Hibernate gọi converter phù hợp.

Nếu SQL chọn expression đã biến đổi giá trị lần nữa, converter có thể nhận sai dữ liệu và throw exception. Với scalar/DTO query, developer phải tự xác định result type; đừng giả định converter của entity tự áp dụng cho mọi arbitrary scalar expression.

### 12.3. JSON và custom JDBC type

Với `@JdbcTypeCode(SqlTypes.JSON)` hoặc custom `JavaType`/`JdbcType`, việc trả đúng column label và JDBC/database value type càng quan trọng. JSON aggregation hoặc expression có thể trả text/JSON ở định dạng khác với cột mapping gốc. Nếu mục đích là dựng Book entity, chọn đúng mapped JSON column; nếu mục đích là một biểu thức JSON report, chọn projection riêng.

## 13. @Embedded và nhiều cột cho một value object

Một `@Embeddable` có thể tương ứng với nhiều cột trong bảng:

~~~java
@Embeddable
public class Money {
    @Column(name = "amount")
    private BigDecimal amount;

    @Column(name = "currency")
    private String currency;
}
~~~

~~~java
@Embedded
private Money listPrice;
~~~

Nếu entity Book dùng Money thay cho price đơn, native SQL entity result cần cả `amount` và `currency` theo mapping/overrides. Chọn một trong hai cột không bảo đảm Hibernate dựng được value object đúng.

Với `@AttributeOverride`, tên cột vật lý có thể khác tên field của embeddable. Khi dùng `@SqlResultSetMapping`, các field paths lồng nhau và aliases phải được khai báo theo quy tắc của provider/JPA version.

## 14. Entity kế thừa: discriminator và subclass columns

Khi dùng inheritance mapping, tập cột cần thiết có thể phức tạp hơn entity đơn bảng.

### 14.1. SINGLE_TABLE

~~~java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "dtype")
public abstract class Payment {
    @Id
    private Long id;
}

@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    private String lastFourDigits;
}
~~~

Một câu SQL trả polymorphic entity `Payment` có thể cần cột discriminator `dtype` và những columns của subtype được ánh xạ để Hibernate xác định class và hydrate state. Không thể mặc định chọn chỉ `payment.id` và một vài columns của base type rồi mong Hibernate tự biết subtype.

JPA `@EntityResult` có thuộc tính `discriminatorColumn` để chỉ column label dùng làm discriminator trong result mapping khi cần:

~~~java
@EntityResult(
    entityClass = Payment.class,
    discriminatorColumn = "payment_kind"
)
~~~

Đây chỉ là snippet cấu hình discriminator. Mapping đầy đủ còn phải xét ID, common attributes và subtype fields theo inheritance strategy. Không coi một discriminator alias là đủ để giải quyết mọi inheritance hydration.

### 14.2. JOINED inheritance

Với `JOINED`, subclass state có thể trải trên nhiều bảng. Native entity query polymorphic có thể cần join các subclass tables, chọn đúng cột và mapping aliases để Hibernate dựng đúng loại entity.

`SELECT p.* FROM payments p` không phải lúc nào đủ, vì `p.*` chỉ là cột base table. HQL/Criteria thường đơn giản hơn cho polymorphic entity selection. Chỉ dùng native SQL khi hiểu rõ inheritance strategy, các columns và Dialect/version đang chạy.

### 14.3. TABLE_PER_CLASS

Với `TABLE_PER_CLASS`, dữ liệu polymorphic có thể nằm ở nhiều bảng. Hibernate có thể dùng UNION để truy vấn base class. Nếu tự viết native SQL, developer chịu trách nhiệm bảo đảm các nhánh UNION có columns/aliases và type conversions phù hợp. Đây không phải trường hợp nên áp dụng máy móc mẹo `select *`.

## 15. Secondary tables, formulas và generated columns

Một entity có thể ánh xạ nhiều bảng:

~~~java
@Entity
@Table(name = "books")
@SecondaryTable(
    name = "book_details",
    pkJoinColumns = @PrimaryKeyJoinColumn(name = "book_id")
)
public class Book {
    @Id
    private Long id;

    private String title;

    @Column(table = "book_details", name = "description")
    private String description;
}
~~~

Nếu developer viết:

~~~sql
select b.*
from books b;
~~~

nó không chứa `book_details.description`. Với native entity result hydration, Hibernate có thể cần các columns ở secondary table; tùy mapping và loading plan, phải join bảng và định nghĩa aliases/result mapping đầy đủ. Không giả định `b.*` luôn đủ cho entity nhiều bảng.

Ví dụ SQL có thể cần:

~~~sql
select
    b.id,
    b.title,
    d.description
from books b
left join book_details d on d.book_id = b.id;
~~~

Nếu có tên cột trùng hoặc SQL function, dùng aliases và `@SqlResultSetMapping`.

### 15.1. Formula và derived attributes

Hibernate-specific `@Formula` hoặc generated attributes có thể dùng SQL expressions, không chỉ columns lưu trực tiếp. Những thuộc tính này ảnh hưởng loading plan tùy cấu hình. Với native entity mapping, SQL/query mapping phải tương thích yêu cầu hydration của provider; không thể suy luận đơn giản rằng `SELECT table.*` đáp ứng mọi expression mapped.

Nếu native query quá phức tạp để tái tạo entity mapping đúng, xem xét query DTO/scalar hoặc HQL/Criteria để Hibernate tự chọn expressions cần thiết.

### 15.2. Cột read-only vẫn có thể cần được đọc

`@Column(insertable = false, updatable = false)` điều chỉnh hành vi **ghi**, không tự đồng nghĩa cột đó bị bỏ khỏi entity state lúc **đọc**. Nếu một thuộc tính được map để hiển thị hoặc dùng trong logic, native entity result có thể vẫn cần cột tương ứng.

Đừng loại column khỏi SELECT chỉ vì entity không được phép cập nhật column đó.

## 16. Trả nhiều entity từ một câu SQL JOIN

Giả sử một native SQL trả cả Book và Publisher:

~~~sql
select
    b.id as book_id,
    b.title as book_title,
    b.price as book_price,
    b.status as book_status,
    b.version as book_version,
    b.publisher_id as book_publisher_id,
    p.id as publisher_id,
    p.name as publisher_name
from books b
join publishers p on p.id = b.publisher_id;
~~~

Có ít nhất hai vấn đề:

1. `b.id` và `p.id` cùng tên gốc `id`, cần alias riêng để tránh collision.
2. Kết quả có **hai entity returns**, nên mỗi result row có thể là một cấu trúc chứa cả Book và Publisher, không phải một Book duy nhất.

Dùng `@SqlResultSetMapping` với nhiều `@EntityResult`, mỗi entity có danh sách `@FieldResult` phù hợp và aliases riêng. Những yêu cầu về FK, version và fields của từng entity vẫn phải được đáp ứng.

Ví dụ cấu trúc ý tưởng:

~~~java
@SqlResultSetMapping(
    name = "BookAndPublisher",
    entities = {
        @EntityResult(
            entityClass = Book.class,
            fields = { /* FieldResult cho toàn bộ mapped Book state */ }
        ),
        @EntityResult(
            entityClass = Publisher.class,
            fields = { /* FieldResult cho toàn bộ mapped Publisher state */ }
        )
    }
)
~~~

Đây là **pseudocode về cấu trúc mapping**, không phải annotation đầy đủ để copy vào project. Cần khai báo đúng toàn bộ `@FieldResult` của mapping cụ thể. Khi mapping có nhiều entity/scalar returns, ứng dụng có thể nhận `Object[]` theo thứ tự các kết quả đã định nghĩa.

### 16.1. Tránh SELECT * khi join nhiều bảng

~~~sql
-- Rủi ro: nhiều bảng có cột id, name, status...
select *
from books b
join publishers p on p.id = b.publisher_id;
~~~

`SELECT *` ở đây tạo column labels trùng nhau. Provider/JDBC có thể không xác định được `id` nào thuộc entity nào, dẫn đến alias collision, duplicate alias discovery hoặc hydrate sai. Chọn các cột với prefix aliases rõ ràng:

~~~sql
select b.id as book_id, p.id as publisher_id, ...
~~~

Với single-entity result, `SELECT b.* FROM ... JOIN ...` có thể tránh lấy columns của bảng khác, miễn Book mapping đơn giản và đủ columns. Nhưng nếu SQL cần trả cả hai entity, luôn thiết kế result mapping rõ ràng.

### 16.2. Một JOIN không đương nhiên tạo association loaded

Nếu trả Book và Publisher cùng một row, điều đó không tự bảo đảm quan hệ `book.publisher` được gắn đúng theo cách ứng dụng mong muốn trong mọi mapping. Entity returns và relationship initialization còn phụ thuộc entity metadata/result mapping/fetch handling. Đừng suy ra chỉ từ cú pháp SQL JOIN rằng một association đã được initialize; kiểm tra `Hibernate.isInitialized` hoặc fetch plan phù hợp khi cần.

## 17. Kết hợp entity và scalar trong ResultSet

Có những truy vấn trả entity cùng một giá trị tính toán, chẳng hạn Book và số bản bán:

~~~sql
select
    b.id,
    b.title,
    b.price,
    b.status,
    b.version,
    count(s.id) as sold_count
from books b
left join sales s on s.book_id = b.id
group by b.id, b.title, b.price, b.status, b.version;
~~~

Nếu query trả entity + scalar, result shape không còn là một Book đơn giản. Có thể khai báo `@SqlResultSetMapping` với `@EntityResult` cho Book và `@ColumnResult` cho `sold_count`:

~~~java
@SqlResultSetMapping(
    name = "BookWithSalesCount",
    entities = @EntityResult(entityClass = Book.class),
    columns = @ColumnResult(
        name = "sold_count",
        type = Long.class
    )
)
~~~

Đây là snippet khai báo gắn với entity mapping Book có columns đúng tên; nếu SQL dùng alias khác, thêm `@FieldResult` tương ứng. Kết quả thường là một `Object[]` gồm Book và scalar count. `type=Long.class` biểu diễn kiểu scalar mong đợi; các DBMS/driver có thể trả numeric types khác nếu không khai báo/conversion phù hợp.

Nếu ứng dụng chỉ cần một báo cáo Book ID, title và count, DTO projection có thể dễ hiểu hơn việc hydrate cả Book entity.

## 18. ConstructorResult cho DTO từ native SQL

Jakarta Persistence cho phép tạo DTO qua `@ConstructorResult` trong `@SqlResultSetMapping`.

DTO:

~~~java
package com.example.catalog;

public record BookPreview(
        Long id,
        String title,
        java.math.BigDecimal price
) {}
~~~

Đăng ký mapping (trên một managed class):

~~~java
@SqlResultSetMapping(
    name = "BookPreviewNative",
    classes = @ConstructorResult(
        targetClass = BookPreview.class,
        columns = {
            @ColumnResult(name = "book_id", type = Long.class),
            @ColumnResult(name = "book_title", type = String.class),
            @ColumnResult(name = "book_price",
                          type = java.math.BigDecimal.class)
        }
    )
)
~~~

SQL:

~~~sql
select
    b.id as book_id,
    b.title as book_title,
    b.price as book_price
from books b;
~~~

Gọi:

~~~java
List<?> rows = em.createNativeQuery(
        """
        select b.id as book_id,
               b.title as book_title,
               b.price as book_price
        from books b
        """,
        "BookPreviewNative"
    )
    .getResultList();

List<BookPreview> previews = rows.stream()
        .map(BookPreview.class::cast)
        .toList();
~~~

`@ColumnResult.type` giúp định nghĩa kiểu mong đợi cho constructor; kiểu thực tế và conversion phải tương thích với provider/JDBC/DBMS. `BookPreview` **không phải managed entity**, không được dirty checking.

### 18.1. EntityResult khác ConstructorResult

| Cơ chế | Đầu ra | Được quản lý? | Dữ liệu cần |
| --- | --- | --- | --- |
| `resultClass = Book.class` | Book entity | Thường managed trong persistence context | Đủ cột cần cho Book mapping |
| `@EntityResult` | Entity theo mapping tường minh | Thường managed | Đủ ID, state và aliases |
| `@ConstructorResult` | DTO Java | Không | Cột tương ứng constructor |
| `@ColumnResult` | Scalar | Không | Cột/alias đã chọn |
| Raw native query không mapping | Scalar / `Object[]` | Không tự thành entity | Chỉ các cột query thực sự trả |

Cách chọn rất quan trọng: **DTO được phép chọn ít cột theo hợp đồng DTO; entity không được giả làm DTO thiếu state.**

## 19. Khi entity được trả về, Hibernate quản lý vòng đời thế nào?

Trong một persistence context hoạt động, entity được Hibernate hydrate từ native SQL và ánh xạ thành entity result thường là **managed entity**.

~~~java
Book book = (Book) em.createNativeQuery(
        """
        select b.id, b.title, b.price, b.status, b.version
        from books b
        where b.id = :id
        """,
        Book.class
    )
    .setParameter("id", 42L)
    .getSingleResult();

boolean managed = em.contains(book); // Thường true trong context này.
book.rename("Revised title");
~~~

Nếu transaction cho phép ghi và entity vẫn managed, dirty checking có thể phát `UPDATE` khi flush. Native SQL entity result không phải DTO read-only chỉ vì nguồn là native SQL.

### 19.1. Identity map: cùng ID có thể trả cùng instance

Giả sử Book ID 42 đã được tải bằng `em.find(Book.class, 42L)`. Một native query sau đó trả Book với ID 42. Hibernate thường nhận diện cùng entity identity trong persistence context và dùng managed instance tương ứng.

Điều này có hai hệ quả:

1. Không có hai managed Java objects độc lập với cùng entity identity trong một persistence context.
2. Một native query **không bảo đảm tự làm mới field của entity đã managed** chỉ vì DB trả các giá trị mới.

Nếu cần đồng bộ dữ liệu đã thay đổi bên ngoài context, hãy cân nhắc `em.refresh(book)`, `em.clear()` hoặc scope mới tùy transaction semantics, nhưng không áp dụng mù quáng vì refresh có thể ghi đè thay đổi local chưa flush.

### 19.2. Flush và thứ tự quan sát dữ liệu

Một ứng dụng có thể đang giữ pending changes trên managed entities rồi chạy native SQL. Cách Hibernate/JPA quyết định auto-flush trước native query có thể khác theo flush mode và API sử dụng. Nếu query phải quan sát những thay đổi đang pending, thiết kế transaction boundary và gọi `flush()` có chủ đích khi phù hợp; đừng giả định mọi native query trong mọi API luôn nhìn thấy cùng state.

### 19.3. Không dùng Session lỗi để tiếp tục

Nếu native entity hydration gây lỗi thiếu column, type conversion, constraint hoặc SQL execution, transaction/persistence context có thể không còn an toàn để tiếp tục. Rollback unit of work bị ảnh hưởng và đóng/bỏ Session theo transaction owner. Đừng cố sửa câu SQL rồi chạy lại trong cùng Session đã gặp Hibernate/JDBC failure nghiêm trọng.

## 20. Query native cùng JOIN: số dòng, DISTINCT và pagination

Khi JOIN các bảng có quan hệ to-many, một Book có thể xuất hiện trên nhiều SQL rows:

~~~sql
select b.*
from books b
join book_tags t on t.book_id = b.id
where t.tag like 'java%';
~~~

Một Book có ba tags khớp điều kiện có thể tạo ba rows trong SQL ResultSet. Hibernate vẫn nhận diện cùng Book identity, nhưng result list/cardinality có thể bị ảnh hưởng bởi hình dạng query và behavior provider. Không nên dựa vào identity map để thay thế việc xác định root rows.

Nếu nhu cầu là danh sách Book duy nhất:

~~~sql
select distinct b.id, b.title, b.price, b.status, b.version
from books b
join book_tags t on t.book_id = b.id
where t.tag like :pattern
order by b.id;
~~~

Có thể dùng `EXISTS` để tránh nhân root rows:

~~~sql
select b.id, b.title, b.price, b.status, b.version
from books b
where exists (
    select 1
    from book_tags t
    where t.book_id = b.id
      and t.tag like :pattern
)
order by b.id;
~~~

Cách dùng `EXISTS` thường diễn đạt ý định “có ít nhất một tag phù hợp” rõ hơn và tránh SELECT root lặp do join, nhưng hiệu năng cần xem execution plan/index thực tế.

### 20.1. Pagination

Với native query entity result:

~~~java
@SuppressWarnings("unchecked")
List<Book> page = em.createNativeQuery(
        """
        select b.id, b.title, b.price, b.status, b.version
        from books b
        where b.status = :status
        order by b.id
        """,
        Book.class
    )
    .setParameter("status", "PUBLISHED")
    .setFirstResult(offset)
    .setMaxResults(pageSize)
    .getResultList();
~~~

Phải validate `offset` và `pageSize`, bảo đảm sort ổn định. Nếu SQL join collection làm trùng root rows, pagination có thể cắt nhầm số root entities; cân nhắc query ID trước rồi load entities theo page, hoặc dùng `EXISTS` thay join khi chỉ cần lọc.

Native query trả entity lớn còn giữ nhiều managed instances trong context, nên batch/export quy mô lớn cần scope/pagination/clear phù hợp.

## 21. SQL native và bảo mật parameter binding

Native SQL có quyền biểu đạt đầy đủ cú pháp SQL nên càng không được nối input trực tiếp.

**Không an toàn:**

~~~java
String sql = "select b.* from books b where b.title = '"
        + userTitle + "'";

em.createNativeQuery(sql, Book.class).getResultList();
~~~

**An toàn với giá trị:**

~~~java
em.createNativeQuery(
        """
        select b.id, b.title, b.price, b.status, b.version
        from books b
        where b.title = :title
        """,
        Book.class
    )
    .setParameter("title", userTitle)
    .getResultList();
~~~

Parameter binding dành cho **giá trị dữ liệu**. Nó không thể đại diện tên bảng, tên cột hoặc hướng `ASC/DESC`. Nếu cần dynamic ORDER BY, chọn column/direction từ allowlist cố định do server quản lý; không nối raw field name từ request.

### 21.1. Query đã bind vẫn có thể sai quyền

Truy vấn:

~~~sql
select b.id, b.title, b.price, b.status, b.version
from books b
where b.status = :status;
~~~

có thể an toàn trước injection nhưng vẫn trả dữ liệu của tenant khác nếu thiếu predicate tenant/owner. Authorization không tự xuất hiện vì result được ánh xạ thành entity. Hãy áp dụng tenant scope từ security context đáng tin cậy và kiểm tra quyền resource. Với Hibernate filters/multitenancy, hiểu rõ native SQL và integration cụ thể có tự áp dụng hạn chế đó hay không; không giả định mọi filter ORM tự động được chèn vào raw SQL do ứng dụng viết.

## 22. Những lỗi thường gặp khi native SQL trả entity

| Hiện tượng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| SQL chạy trong DB client nhưng Hibernate báo không thấy column | ResultSet thiếu mapped column/alias | Chọn đủ columns, khớp labels hoặc dùng `@FieldResult` |
| Thiếu `id` trong SELECT | Hibernate không xác định entity key | Chọn PK thật, kể cả composite ID đầy đủ |
| Thiếu `version` | Entity versioned cần state cho optimistic locking | Chọn DB version column thật |
| Thiếu `publisher_id` với `@ManyToOne` | FK cần cho association mapping | Chọn FK dù association LAZY |
| `select b.*, p.*` báo duplicate alias | Hai bảng có `id`/cột trùng tên | Chỉ chọn `b.*` hoặc alias và mapping tường minh |
| HQL dùng được, native SQL không tìm thấy property | Native SQL dùng DB column names, không phải Java paths | Dùng tên cột vật lý |
| Enum hydrate lỗi | SQL trả giá trị không tương thích enum mapping | Chọn nguyên cột/kiểu DB đúng |
| Converter/custom type hydrate lỗi | SQL trả expression/kiểu JDBC không đúng | Chọn mapped column hoặc projection riêng |
| `select b.*` thiếu field | Entity có secondary table/inheritance/formula | Thiết kế SQL/result mapping theo metadata |
| Chỉ cần ID/title nhưng query kết quả Book lỗi | Partial projection không đủ entity state | Dùng DTO/scalar |
| Native query trả Object[] không phải Book | Không khai báo entity result mapping | Dùng result class hoặc `@EntityResult` |
| Query trả Book nhưng association chưa initialized | JOIN để lọc không phải fetch graph | Thiết kế fetch plan, kiểm tra loaded state |
| Cùng Book ID nhưng không thấy DB change mới | Entity đã managed trong identity map | Refresh/context mới khi hợp lý |
| Kết quả bị lặp khi join to-many | Một Book tương ứng nhiều SQL rows | DISTINCT/EXISTS, thiết kế pagination |
| DTO constructor thất bại | Alias, column type hoặc constructor không khớp | Kiểm tra `@ConstructorResult`/`@ColumnResult` |
| Native UPDATE không tăng version | DML bỏ qua dirty checking ORM | Versioning thủ công/logic transaction phù hợp |

Khi debug, đọc nguyên nhân sâu nhất trong exception chain: `SQLException`/column label, Hibernate hydration error hoặc constructor resolution error. Đừng chỉ nhìn thông báo trên cùng của `PersistenceException`.

## 23. Quan sát SQL, JDBC labels và mapping

Trong Hibernate 6, logger `org.hibernate.SQL` ở mức DEBUG giúp thấy câu SQL được phát. `org.hibernate.orm.jdbc.bind` ở mức TRACE có thể hiện tham số bind khi môi trường cho phép. Không bật bind trace tùy tiện trong production nếu chứa dữ liệu cá nhân hoặc secrets.

Có thể bật Hibernate statistics trong môi trường thử nghiệm:

~~~properties
hibernate.generate_statistics=true
~~~

Khi native entity query lỗi, các câu hỏi thực tế cần xác định:

1. SQL thật trả bao nhiêu columns?
2. JDBC ResultSet trả **column labels** nào sau alias?
3. Những columns nào entity mapping yêu cầu để hydrate?
4. ID, version và association FK có được trả không?
5. Entity có inheritance, secondary table, embeddable hay custom type không?
6. Query có trả nhiều bảng với alias collisions không?
7. Có đang dùng resultClass hoặc resultSetMapping phù hợp không?
8. SQL có dùng biểu thức làm thay đổi JDBC type của cột không?
9. Entity cùng identity đã ở persistence context trước đó chưa?
10. Có native DML hoặc writer khác thay đổi DB mà entity managed chưa refresh không?

Đây là các yếu tố giải thích cơ chế. Việc kiểm thử thực thi query phải đặt trong integration test với DBMS/version tương ứng; chương trình demo chỉ giải thích cách viết chứ không bảo đảm SQL chạy giống hệt trên mọi Dialect.

## 24. Một bài toán lựa chọn kết quả

Giả sử API có ba use case dùng cùng bảng books.

### 24.1. Trang chi tiết cần sửa Book

Chọn entity đầy đủ:

~~~java
Book book = (Book) em.createNativeQuery(
        """
        select b.id, b.title, b.price, b.status, b.version
        from books b
        where b.id = :id
        """,
        Book.class
    )
    .setParameter("id", bookId)
    .getSingleResult();

book.rename("New edition");
~~~

Nếu Book vẫn managed trong transaction ghi, dirty checking có thể phát UPDATE. Cần quan tâm entity not found, optimistic locking và lifecycle.

### 24.2. Danh sách cho dropdown chỉ cần ID/title

Chọn scalar/DTO:

~~~sql
select id, title
from books
where status = 'PUBLISHED'
order by title;
~~~

Không ép ResultSet này thành Book entity vì mapping còn price/status/version.

### 24.3. Báo cáo doanh thu theo Book

Chọn DTO report hoặc `@ConstructorResult` với aggregate:

~~~sql
select
    b.id as book_id,
    b.title as title,
    count(s.id) as sales_count,
    coalesce(sum(s.amount), 0) as revenue
from books b
left join sales s on s.book_id = b.id
group by b.id, b.title;
~~~

`sales_count` và `revenue` không nhất thiết là mapped fields của Book; đây là report row, không phải entity Book. Dùng DTO hợp với semantics và kiểu dữ liệu của aggregate.

## 25. Quy trình thiết kế native entity query

1. **Xác định kết quả cần entity hay projection.** Nếu không cần dirty checking, lifecycle và full entity state, ưu tiên DTO/scalar.
2. **Đọc mapping của entity.** Bao gồm `@Id`, `@Version`, basic properties, enum/converter, to-one FKs, embedded values, inheritance và secondary tables.
3. **Liệt kê cột cần cho hydration.** Dựa trên metadata ORM, không chỉ các cột API hiển thị.
4. **Viết SQL với tên bảng/cột database đúng.** Không dùng property path HQL trong native SQL.
5. **Đảm bảo alias duy nhất và dễ nhận diện.** Một bảng đơn giản có thể dùng `b.*`; nhiều bảng/alias thì chọn cột tường minh.
6. **Chọn API result mapping.** `createNativeQuery(sql, Entity.class)` cho case đơn giản; `@SqlResultSetMapping` khi alias hoặc result shape phức tạp.
7. **Bind mọi giá trị từ request.** Tên bảng/cột/hướng sort động phải đến từ allowlist.
8. **Giữ ID/version/FK thật từ DB.** Không dùng literal giả để đủ column labels.
9. **Xác định hành vi persistence context.** Entity result có thể managed, bị ảnh hưởng bởi identity map, dirty checking và stale state.
10. **Xem join/cardinality/pagination.** Tránh duplicate aliases và root row multiplication.
11. **Kiểm tra đúng Dialect/version khi triển khai.** Inheritance, custom types, quoted identifiers và driver mappings có thể cần cấu hình riêng.
12. **Xử lý transaction lỗi đúng cách.** Không tiếp tục reuse Session đã gặp lỗi JDBC/ORM nghiêm trọng.

## 26. Câu hỏi tự kiểm tra

1. Vì sao `createNativeQuery(sql)` không tự trả Book entity, còn `createNativeQuery(sql, Book.class)` có thể trả Book?
2. Với Book có id, title, price, status và version, query chỉ chọn id/title có phù hợp để trả managed Book không?
3. Tại sao Hibernate cần cột ID thật từ database?
4. Vì sao native entity query của Book có `@Version` cần version column?
5. Một Book có `@ManyToOne(fetch=LAZY) Publisher`. Vì sao vẫn cần foreign key `publisher_id` trong ResultSet?
6. JOIN publishers trong SQL để lọc Book có bảo đảm `book.getPublisher()` đã initialized không?
7. Native SQL dùng tên field Java hay tên cột vật lý của database?
8. Khi SQL dùng alias `result_book_id` thay cho `id`, annotation nào giúp khai báo ánh xạ tường minh?
9. Vì sao `select b.*, p.*` dễ gặp lỗi column alias collision?
10. Khi nào nên dùng `@ConstructorResult` thay vì `@EntityResult`?
11. Nếu entity đã managed trong persistence context, native query có chắc refresh state của nó từ DB không?
12. Nếu Book dùng JOINED inheritance hoặc secondary table, vì sao `select b.*` có thể không đủ?
13. `@Column(insertable=false, updatable=false)` có đồng nghĩa mapped column không cần được đọc không?
14. Tại sao COUNT/aggregate report row không nên bị ép thành Book?
15. Parameter binding cho `:status` có ngăn được việc client chọn tên bảng tùy ý nếu code vẫn nối raw table name không?

**Gợi ý:** (1) result mapping; (2) không, thiếu mapped state; (3) entity identity map; (4) optimistic locking; (5) FK biểu diễn association dù target lazy; (6) không; (7) tên bảng/cột DB; (8) `@SqlResultSetMapping` + `@EntityResult`/`@FieldResult`; (9) nhiều bảng có cùng tên cột; (10) DTO/projection không managed; (11) không; (12) state trải nhiều bảng/subtype; (13) không; (14) khác kiểu dữ liệu và semantics; (15) không, identifier phải allowlist.

**Kết luận:** native SQL cho phép kiểm soát câu lệnh database nhưng **không làm mất các yêu cầu của entity mapping**. Nếu trả entity, hãy cung cấp ID thật, version nếu có, các mapped basic columns và những cột cần thiết để Hibernate dựng association, embedded values hoặc inheritance state đúng. Khi SQL chỉ có vài cột, giá trị tổng hợp hoặc biểu thức report, hãy dùng scalar/DTO projection. Khi alias khác mapping hoặc trả nhiều thực thể, dùng `@SqlResultSetMapping` tường minh. Cuối cùng, luôn nhớ entity result có thể được quản lý trong persistence context, không phải một bản sao DTO độc lập chỉ vì nguồn dữ liệu đến từ SQL gốc.
