# Dirty checking phát hiện thay đổi thuộc tính như thế nào

Trong ứng dụng Java dùng JPA/Hibernate, ta thường cập nhật dữ liệu mà **không gọi câu lệnh `UPDATE`** hoặc phương thức `save()` cho từng thuộc tính:

~~~java
Product product = em.find(Product.class, 10L);
product.changePrice(new BigDecimal("450000.00"));
~~~

Nếu `product` là **managed entity**, được sửa trong một persistence context đang hoạt động và thay đổi cần đồng bộ, Hibernate có thể tự phát hiện `price` khác giá trị đã nạp rồi phát SQL `UPDATE` khi **flush**. Cơ chế đó gọi là **dirty checking** — theo dõi và xác định những trạng thái persistent đã thay đổi.

Điều dễ nhầm là dirty checking **không đồng nghĩa Hibernate luôn quan sát từng lệnh setter rồi lập tức chạy SQL**. Cơ chế truyền thống chủ yếu dựa trên so sánh **trạng thái đã nạp (snapshot)** với **trạng thái hiện tại** tại các thời điểm đồng bộ. Trong một số cấu hình, Hibernate còn hỗ trợ **bytecode enhancement** để theo dõi thay đổi trực tiếp trên entity. Dù bằng cách nào, dirty checking, flush và commit vẫn là ba khái niệm khác nhau.

Bài học thuộc chương **Dirty Checking và Flush** của module *Data Persistence Relational Access ORM Hibernate*. Ví dụ dùng Jakarta Persistence (`jakarta.persistence.*`), Hibernate ORM, Java hiện đại và SQL minh họa theo PostgreSQL. Hành vi SQL cụ thể có thể khác tùy phiên bản Hibernate, mapping, flush mode, cache và cấu hình database.

## 1. Kết quả quan sát được: sửa object, Hibernate ghi SQL

Giả sử bảng dữ liệu:

~~~sql
CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(40) NOT NULL UNIQUE,
    name VARCHAR(160) NOT NULL,
    price NUMERIC(15, 2) NOT NULL CHECK (price >= 0),
    stock_quantity INTEGER NOT NULL CHECK (stock_quantity >= 0),
    version BIGINT NOT NULL DEFAULT 0
);
~~~

Một hàng đang có:

| id | sku | name | price | stock_quantity | version |
| ---: | --- | --- | ---: | ---: | ---: |
| 10 | SP-010 | Bàn phím | 400000.00 | 25 | 3 |

Ứng dụng tải entity rồi đổi giá:

~~~java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Product product = em.find(Product.class, 10L);
    product.changePrice(new BigDecimal("450000.00"));

    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
} finally {
    em.close();
}
~~~

Ta **không gọi `em.persist(product)` lần nữa**; `product` được `find` trả về đã là managed. Khi flush xảy ra, Hibernate nhận biết giá đã thay đổi và có thể gửi SQL tương đương:

~~~sql
UPDATE products
SET price = 450000.00, version = 4
WHERE id = 10 AND version = 3;
~~~

Đây là câu SQL **minh họa**. Mặc định, tùy mapping và cấu hình, Hibernate có thể đưa thêm các cột updatable không đổi vào `SET`; với `@DynamicUpdate`, nó thường giới hạn các cột được gán theo trạng thái thực sự dirty. Điểm chắc chắn về mặt ý nghĩa là **hàng có ID 10 được đồng bộ từ thay đổi của managed entity**, chứ không phải ứng dụng phải viết SQL thủ công.

**`@Version`** trong ví dụ giúp phát hiện cập nhật đồng thời; việc số phiên bản tăng từ 3 lên 4 là một chủ đề liên quan nhưng khác với chính bước phát hiện `price` bị thay đổi.

## 2. Entity minh họa và phạm vi thuộc tính được theo dõi

**`Product.java`:**

~~~java
package com.example.catalog.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;
import java.math.BigDecimal;
import java.util.Objects;

@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "sku", nullable = false, unique = true, length = 40)
    private String sku;

    @Column(name = "name", nullable = false, length = 160)
    private String name;

    @Column(name = "price", nullable = false, precision = 15, scale = 2)
    private BigDecimal price;

    @Column(name = "stock_quantity", nullable = false)
    private int stockQuantity;

    @Version
    @Column(name = "version", nullable = false)
    private Long version;

    protected Product() {
        // JPA constructor.
    }

    public Product(
        String sku,
        String name,
        BigDecimal price,
        int stockQuantity
    ) {
        this.sku = Objects.requireNonNull(sku);
        this.name = Objects.requireNonNull(name);
        this.price = requireValidPrice(price);
        changeStockQuantity(stockQuantity);
    }

    public Long getId() {
        return id;
    }

    public String getSku() {
        return sku;
    }

    public String getName() {
        return name;
    }

    public BigDecimal getPrice() {
        return price;
    }

    public int getStockQuantity() {
        return stockQuantity;
    }

    public Long getVersion() {
        return version;
    }

    public void rename(String value) {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("Tên không hợp lệ");
        }
        this.name = value.trim();
    }

    public void changePrice(BigDecimal value) {
        this.price = requireValidPrice(value);
    }

    public void changeStockQuantity(int value) {
        if (value < 0) {
            throw new IllegalArgumentException("Tồn kho phải không âm");
        }
        this.stockQuantity = value;
    }

    private static BigDecimal requireValidPrice(BigDecimal value) {
        Objects.requireNonNull(value, "price");
        if (value.signum() < 0) {
            throw new IllegalArgumentException("Giá không được âm");
        }
        return value;
    }
}
~~~

Ở đây, các field `sku`, `name`, `price` và `stockQuantity` là **persistent attributes** vì entity sử dụng field access: `@Id` được đặt trên field. `version` được Hibernate quản lý theo annotation `@Version`.

Lớp không cung cấp public `setId(...)`, vì định danh phải ổn định sau khi entity được quản lý. Hibernate có thể gán ID khi persist nhờ field access, không cần để ứng dụng tự sửa ID.

Không nên xem mọi field Java là thuộc tính persistent. Những field `static`, `transient` hoặc được đánh dấu `@Transient` không phải trạng thái database được Hibernate dirty-check theo mapping entity thông thường.

## 3. Quy trình dirty checking bằng snapshot

Cơ chế truyền thống của Hibernate có thể hiểu qua bốn bước.

### Bước 1 — Nạp và quản lý entity

~~~java
Product product = em.find(Product.class, 10L);
~~~

Hibernate nạp dữ liệu và đưa `product` vào persistence context. Đồng thời nó lưu một biểu diễn của **trạng thái persistent đã được nạp**, thường gọi là *loaded state* hoặc **snapshot**.

Ta có thể tưởng tượng:

~~~text
Managed entity: Product(id=10)
  sku            = "SP-010"
  name           = "Bàn phím"
  price          = 400000.00
  stockQuantity  = 25

Loaded snapshot (khái niệm):
  sku            = "SP-010"
  name           = "Bàn phím"
  price          = 400000.00
  stockQuantity  = 25
~~~

Snapshot ở đây là **mô hình giải thích**, không nhất thiết là một object `Product` thứ hai. Hibernate quản lý cấu trúc trạng thái và thông tin mapping nội bộ; cách tổ chức cụ thể phụ thuộc phiên bản/provider.

### Bước 2 — Ứng dụng sửa thuộc tính

~~~java
product.changePrice(new BigDecimal("450000.00"));
~~~

Bây giờ:

~~~text
Current state                  Loaded snapshot
price = 450000.00              price = 400000.00
name  = "Bàn phím"             name  = "Bàn phím"
stock = 25                     stock = 25
~~~

### Bước 3 — Hibernate xác định trạng thái khác nhau

Khi đến một lần flush, Hibernate có thể so sánh từng persistent attribute đang được theo dõi với snapshot theo quy tắc của **Hibernate type mapping**, không đơn giản là so sánh chuỗi SQL.

~~~text
sku:           bằng nhau      → không dirty
name:          bằng nhau      → không dirty
price:         khác nhau      → dirty
stockQuantity: bằng nhau      → không dirty
~~~

Kết quả là entity có ít nhất một thuộc tính dirty, và Hibernate có thể chuẩn bị entity update action.

### Bước 4 — Đồng bộ với database

Khi flush, Hibernate tạo SQL phù hợp, bind các giá trị và thực thi lệnh cần thiết. Với `@Version`, thao tác cập nhật thường có điều kiện trên version để phát hiện xung đột.

~~~mermaid
flowchart TD
    A["find Product(id=10)"] --> B["Managed entity + loaded snapshot"]
    B --> C["Ứng dụng thay đổi price"]
    C --> D["Flush được yêu cầu hoặc tự xảy ra"]
    D --> E{"Trạng thái persistent có khác snapshot?"}
    E -- "Không" --> F["Không cần entity UPDATE cho thay đổi đó"]
    E -- "Có" --> G["Xác định thuộc tính dirty"]
    G --> H["Tạo và thực thi SQL UPDATE"]
    H --> I["Cập nhật thông tin trạng thái theo cơ chế flush"]
    I --> J["Commit hoặc rollback transaction"]
~~~

**Không phải mỗi setter gọi là một câu `UPDATE`.** Nhiều lần sửa một entity trước flush có thể được gom thành một trạng thái cuối cùng được đồng bộ, thay vì một SQL cho mỗi thay đổi trung gian.

## 4. Hibernate có so sánh trực tiếp với dữ liệu hiện có trong DB không?

Thông thường là **không**. Khi thực hiện dirty checking trên managed entity, Hibernate không cần chạy thêm một `SELECT` mỗi lần flush chỉ để so sánh “giá trị mới” với “giá trị trong bảng”:

~~~text
Không phải:
  Lúc flush → SELECT giá trị cũ từ DB → so với object → UPDATE

Thường là:
  Lúc load → giữ snapshot trong persistence context
  Lúc flush → so current state với loaded snapshot → UPDATE khi cần
~~~

Điều này giải thích vì sao dirty checking gắn chặt với **persistence context**. Hibernate cần một **mốc trạng thái được quản lý** để xác định các khác biệt.

Cũng vì không phải mỗi flush đều đọc lại hàng DB, dữ liệu có thể bị sửa đồng thời bởi transaction khác. `@Version` hoặc chiến lược locking giúp phát hiện/giải quyết những trường hợp đó; snapshot đơn thuần không thay thế concurrency control.

Một số cơ chế riêng như `@SelectBeforeUpdate` có thể yêu cầu đọc dữ liệu trong tình huống cập nhật detached/reattach nhất định. Đó không phải quy trình mặc định phải áp dụng cho mọi managed entity.

## 5. Dirty checking xảy ra lúc nào?

Điểm cần nhớ: **thay đổi giá trị trong object không đồng nghĩa SQL lập tức được gửi**.

~~~java
Product product = em.find(Product.class, 10L);

product.changePrice(new BigDecimal("450000.00"));
// Ở đây chưa nhất thiết phát SQL UPDATE.

em.flush();
// Đây là yêu cầu đồng bộ những thay đổi đang chờ.
~~~

Hibernate thường kiểm tra trạng thái khi flush được kích hoạt. Flush có thể xảy ra:

- Khi ứng dụng gọi `em.flush()` hoặc `session.flush()`.
- Trước khi transaction commit, theo flush mode và cơ chế transaction đang dùng.
- Trước một số truy vấn khi provider cần bảo đảm kết quả phù hợp thay đổi đang chờ.
- Ở các thời điểm khác do Hibernate API hoặc thao tác persistence yêu cầu.

**Flush không đồng nghĩa commit.** Flush gửi các thay đổi SQL trong transaction hiện tại; chúng vẫn có thể rollback.

~~~text
BEGIN TRANSACTION
  find Product 10
  changePrice(450000)
  flush            → có thể phát UPDATE
  ...logic khác...
  ROLLBACK         → thay đổi DB bị hủy
~~~

Object Java có thể vẫn giữ giá trị mới sau rollback; rollback database không tự “đảo ngược” mọi field Java. Khi transaction thất bại, cần kết thúc context lỗi và nạp lại dữ liệu nếu cần tiếp tục.

### Một lần thay đổi, nhiều lần flush

Nếu flush đầu tiên đã đồng bộ `price=450000`, sau đó flush lại khi entity không đổi thêm, Hibernate thường không cần phát lại cùng entity update chỉ vì một flush thứ hai xảy ra. Cơ chế quản lý trạng thái đã được đồng bộ theo context.

Ngược lại, nếu sửa giá lần nữa sau flush:

~~~java
product.changePrice(new BigDecimal("480000.00"));
em.flush();
~~~

thì Hibernate có thể thấy một trạng thái dirty mới và gửi SQL cập nhật tiếp theo.

## 6. Setter không nhất thiết là thứ Hibernate “lắng nghe”

Với cơ chế snapshot comparison truyền thống, Hibernate không yêu cầu ứng dụng luôn sửa field qua setter tên `setX(...)`.

~~~java
public void increaseStock(int amount) {
    this.stockQuantity += amount;
}
~~~

Nếu entity được quản lý và thay đổi field persistent, Hibernate có thể phát hiện tại flush. Vì vậy phương thức nghiệp vụ như `increaseStock`, `rename`, `changePrice` vẫn hoạt động dù không có public setter thông thường.

Ngược lại, gọi setter nhưng giá trị cuối cùng **bằng trạng thái đã tải** có thể không dẫn tới SQL update:

~~~java
Product product = em.find(Product.class, 10L);

product.changePrice(new BigDecimal("450000.00"));
product.changePrice(new BigDecimal("400000.00"));

// Nếu trạng thái so sánh cuối cùng bằng snapshot,
// Hibernate theo cơ chế snapshot có thể không coi price là dirty.
~~~

**Ngoại lệ về theo dõi bytecode-enhanced:** Với enhanced dirty tracking, Hibernate có thể ghi nhận dấu hiệu gán field và quyết định dirty theo cơ chế được cấu hình; một lần gán rồi gán lại giá trị cũ không nên được suy luận luôn cho kết quả SQL giống snapshot comparison ở mọi phiên bản/cấu hình. Về mặt nghiệp vụ, chỉ nên dựa vào trạng thái persistent cuối cùng và hợp đồng ORM, không dựa vào số lần getter/setter được gọi.

### Field access và property access

JPA xác định access strategy theo nơi đặt annotation định danh hoặc `@Access` tường minh.

**Field access:**

~~~java
@Id
private Long id;

@Column(name = "price")
private BigDecimal price;
~~~

**Property access:**

~~~java
private BigDecimal price;

@Column(name = "price")
public BigDecimal getPrice() {
    return price;
}
~~~

Trong property access, provider tương tác qua accessor theo mapping. Trong field access, Hibernate có thể đọc/ghi trực tiếp field. Cả hai đều cho phép dirty checking đối với **persistent attributes**, nhưng access strategy ảnh hưởng nơi metadata được đọc và cách ứng dụng nên đặt annotation.

Tránh đặt một phần annotation trên field, phần khác trên getter tùy tiện mà không khai báo `@Access` rõ ràng; điều đó có thể gây metadata không mong muốn.

## 7. Phạm vi dirty checking: entity phải đang managed

Một object Java **không tự được Hibernate theo dõi** chỉ vì lớp có annotation `@Entity`.

| Trạng thái vòng đời | Được dirty-check và đồng bộ tự động? | Ghi chú |
| --- | --- | --- |
| New/transient | Chưa, nếu chưa được persist | Chỉ là object Java |
| Managed | Có, theo mapping và khả năng ghi | Context biết identity và trạng thái |
| Detached | Không được context cũ theo dõi | Thay đổi không tự lưu |
| Removed | Đang được đánh dấu xóa | Đường xử lý tập trung vào `DELETE` và vòng đời xóa |

Ví dụ object mới chưa được lưu:

~~~java
Product product = new Product(
    "SP-011",
    "Chuột",
    new BigDecimal("180000.00"),
    50
);

product.changePrice(new BigDecimal("195000.00"));
// Không tự có INSERT/UPDATE: object vẫn new.
~~~

Sau khi gọi:

~~~java
em.persist(product);
~~~

entity trở thành managed; khi flush Hibernate sẽ cần **INSERT** cho entity mới. Đối với entity new, thay đổi field trước insert không nhất thiết là một entity `UPDATE` riêng. Hibernate lấy trạng thái cần ghi từ entity tại thời điểm thích hợp.

### Entity detached không tự đồng bộ

~~~java
Product product;

EntityManager em = emf.createEntityManager();
try {
    product = em.find(Product.class, 10L);
} finally {
    em.close();
}

product.changePrice(new BigDecimal("500000.00"));
// Hibernate không còn theo dõi object detached này.
~~~

Chỉ thay đổi field của object detached **không tự gửi UPDATE**, vì không có persistence context phù hợp đang theo dõi object đó.

Có thể nạp lại entity managed và áp dụng thay đổi, hoặc dùng `merge` theo yêu cầu nghiệp vụ và chiến lược concurrency. Không nên lẫn `persist`, `merge` và dirty checking của một entity managed.

## 8. `merge` khác với dirty checking trực tiếp

JPA `merge` nhận trạng thái của một entity detached và sao chép/hợp nhất vào **một managed instance** tương ứng, rồi trả về managed instance đó:

~~~java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Product managed = em.merge(detachedProduct);

    // managed là instance thuộc context hiện tại.
    managed.changePrice(new BigDecimal("500000.00"));

    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
} finally {
    em.close();
}
~~~

Đoạn này giả định `detachedProduct` tồn tại, có định danh hợp lệ và các field phù hợp quy tắc nghiệp vụ.

Sau `merge`:

~~~java
Product managed = em.merge(detachedProduct);

System.out.println(
    managed == detachedProduct
); // Thường false với object detached.
~~~

`detachedProduct` không tự trở thành managed. Dirty checking áp dụng lên **managed instance** ở context hiện tại. Hibernate có thể phải tải trạng thái hiện có, so sánh các field và quyết định SQL khi flush.

**Cẩn trọng với bản detached thiếu field:** Nếu cập nhật API gửi một object chỉ có vài trường rồi dùng `merge` bừa bãi, những field không được cung cấp có thể bị ghi đè thành `null` hoặc giá trị mặc định theo trạng thái được merge. Thường an toàn hơn là tải managed entity và gọi các phương thức nghiệp vụ thay đổi đúng field cần thiết.

## 9. `detach` và `clear` cắt liên kết theo dõi

Với entity managed:

~~~java
Product product = em.find(Product.class, 10L);

em.detach(product);
product.changePrice(new BigDecimal("550000.00"));
~~~

Sau `detach`, entity đó không còn được context theo dõi; sửa tiếp không tự đồng bộ.

`em.clear()` detach **tất cả entity** đang managed trong context:

~~~java
Product a = em.find(Product.class, 10L);
Product b = em.find(Product.class, 11L);

em.clear();

a.changePrice(new BigDecimal("550000.00"));
b.changePrice(new BigDecimal("200000.00"));
// Những thay đổi sau clear không tự flush từ context vừa clear.
~~~

Nếu có thay đổi trước `clear` nhưng **chưa flush**, thao tác clear có thể làm mất những cập nhật đang chờ được quản lý trong context. Đây là lý do không nên dùng `clear` như một “cách tối ưu bộ nhớ” tùy tiện giữa transaction.

### `refresh` có thể ghi đè thay đổi chưa lưu

~~~java
Product product = em.find(Product.class, 10L);

product.changePrice(new BigDecimal("550000.00"));

em.refresh(product);
~~~

`refresh` yêu cầu lấy lại trạng thái entity từ database, có thể làm mất thay đổi chưa được đồng bộ của object hiện tại. Không dùng nó như thao tác “kích hoạt dirty checking”; mục đích của refresh là **đồng bộ object từ database vào context**, không phải cập nhật DB từ object.

## 10. Hibernate so sánh “bằng nhau” theo quy tắc nào?

Không có một phép `==` chung cho mọi thuộc tính. Hibernate sử dụng thông tin **basic type mapping**, Java type descriptor, JDBC type, cơ chế mutability và so sánh phù hợp để xác định trạng thái có thay đổi hay không.

Với thuộc tính bất biến quen thuộc:

| Java type | Ví dụ thay đổi | Cách hiểu thường dùng |
| --- | --- | --- |
| `String` | `"Bàn phím"` → `"Chuột"` | Nội dung chuỗi thay đổi |
| `int`/`Integer` | `25` → `30` | Giá trị số thay đổi |
| `BigDecimal` | `400000.00` → `450000.00` | Giá trị tiền theo mapping thay đổi |
| `LocalDate` | `2026-11-15` → `2026-11-16` | Ngày thay đổi |
| Enum | `DRAFT` → `PUBLISHED` | Giá trị enum thay đổi |

**Tránh giả định Hibernate chỉ gọi `Object.equals()` một cách mù quáng cho mọi kiểu.** Một số Hibernate type áp dụng quy tắc equality riêng, nhất là khi chuyển đổi kiểu số/thời gian, kiểu mảng hoặc loại dữ liệu đặc thù.

Ví dụ `BigDecimal` trong Java:

~~~java
new BigDecimal("1.0").equals(new BigDecimal("1.00"));   // false
new BigDecimal("1.0").compareTo(new BigDecimal("1.00"));// 0
~~~

Sự khác biệt giữa `equals` và `compareTo` có thể ảnh hưởng logic nghiệp vụ. Nhưng không nên suy ra trực tiếp rằng Hibernate nhất định phát `UPDATE` mỗi khi scale của BigDecimal thay đổi: kết quả dirty checking phụ thuộc type mapping và cách Hibernate so sánh giá trị. Muốn bảo toàn số tiền, cần thống nhất precision/scale, validation và mapping thay vì dựa vào tính tình cờ của equality.

### Gán lại cùng một instance không có nghĩa dirty

~~~java
Product product = em.find(Product.class, 10L);
BigDecimal oldPrice = product.getPrice();

product.changePrice(oldPrice);
~~~

Với snapshot comparison và kiểu giá trị ổn định, trạng thái giá không đổi. Nhưng với enhanced dirty tracking, các dấu hiệu field assignment và chính sách dirty có thể khác; đo SQL khi tối ưu và không viết logic nghiệp vụ phụ thuộc vào số update chính xác.

## 11. Value object bất biến giúp dirty checking rõ ràng

Ví dụ thay vì lưu email dưới dạng chuỗi tùy ý, domain có thể dùng value object:

~~~java
public final class EmailAddress {
    private final String value;

    private EmailAddress(String value) {
        this.value = value;
    }

    public static EmailAddress of(String raw) {
        if (raw == null || !raw.contains("@")) {
            throw new IllegalArgumentException("Email không hợp lệ");
        }
        return new EmailAddress(raw.trim());
    }

    public String value() {
        return value;
    }

    @Override
    public boolean equals(Object other) {
        return other instanceof EmailAddress address
            && value.equals(address.value);
    }

    @Override
    public int hashCode() {
        return value.hashCode();
    }
}
~~~

Một converter:

~~~java
@Converter(autoApply = false)
public class EmailAddressConverter
        implements AttributeConverter<EmailAddress, String> {

    @Override
    public String convertToDatabaseColumn(EmailAddress attribute) {
        return attribute == null ? null : attribute.value();
    }

    @Override
    public EmailAddress convertToEntityAttribute(String dbValue) {
        return dbValue == null ? null : EmailAddress.of(dbValue);
    }
}
~~~

Trong entity:

~~~java
@Convert(converter = EmailAddressConverter.class)
@Column(name = "contact_email", length = 200)
private EmailAddress contactEmail;

public void changeEmail(EmailAddress email) {
    this.contactEmail = Objects.requireNonNull(email);
}
~~~

Hibernate biết Java attribute có kiểu `EmailAddress` và database representation là `String`. Khi ghi, converter chuyển giá trị thành chuỗi; khi đọc, tạo lại value object.

**Converter không phải một cơ chế dirty checking độc lập.** Hibernate vẫn cần so sánh trạng thái thuộc tính dựa trên type mapping. Với value object bất biến, thay toàn bộ instance thường đơn giản hơn việc sửa trạng thái bên trong mà không đổi reference.

Lưu ý: converter không tự động chia một value object thành nhiều cột; nếu cần nhiều thành phần độc lập, `@Embeddable` thường phù hợp hơn.

## 12. Mutable object: sửa bên trong có được phát hiện không?

Hãy xem một kiểu mutable:

~~~java
public class DeliveryPreferences {
    private String instructions;

    public String getInstructions() {
        return instructions;
    }

    public void setInstructions(String instructions) {
        this.instructions = instructions;
    }
}
~~~

Nếu một field persistent chứa object kiểu này và ứng dụng làm:

~~~java
entity.getDeliveryPreferences()
      .setInstructions("Giao tại lễ tân");
~~~

thì reference của field trên entity **không đổi**, chỉ nội dung object được sửa.

Hibernate có thể phát hiện hay không tùy:

- Value object được mapping theo `@Embeddable` hay basic type/converter tùy biến.
- Cơ chế tạo bản sao snapshot của giá trị mutable.
- Quy tắc equality/mutability của Hibernate type.
- Có bytecode enhancement hay không và loại tracking được sử dụng.
- Thay đổi có đi qua field của entity hay chỉ sửa sâu trong object.

**Đây là chỗ không nên đưa ra bảo đảm đơn giản “mọi thay đổi bên trong object đều được Hibernate nhận ra”.** Đối với custom basic types hoặc `AttributeConverter` chuyển object mutable thành một cột, cần đánh giá mutability plan và khả năng deep-copy snapshot; nếu snapshot giữ cùng reference mutable, so sánh có thể không phản ánh giá trị cũ như mong muốn.

Một cách thiết kế dễ kiểm soát hơn là dùng value object bất biến:

~~~java
DeliveryPreferences newPrefs =
    new DeliveryPreferences("Giao tại lễ tân");

entity.changeDeliveryPreferences(newPrefs);
~~~

Với kiểu bất biến, ứng dụng thay cả giá trị thuộc tính, giảm nguy cơ thay đổi sâu bị bỏ qua và tránh một phần vấn đề cache/snapshot.

## 13. `@Embeddable` và thay đổi thuộc tính nhúng

Một entity có thể chứa value object nhiều cột:

~~~java
@Embeddable
public class Address {
    @Column(name = "street")
    private String street;

    @Column(name = "city")
    private String city;

    protected Address() {
    }

    public Address(String street, String city) {
        this.street = street;
        this.city = city;
    }

    public String getStreet() {
        return street;
    }

    public String getCity() {
        return city;
    }

    public void changeCity(String newCity) {
        this.city = newCity;
    }
}
~~~

Entity sở hữu:

~~~java
@Embedded
private Address deliveryAddress;

public Address getDeliveryAddress() {
    return deliveryAddress;
}
~~~

Trong ánh xạ embeddable, các field `street` và `city` được lưu như những thuộc tính thành phần của entity sở hữu. Khi chúng thay đổi, Hibernate có thể coi thành phần của persistent state đã dirty và cập nhật cột tương ứng theo mapping/SQL strategy.

~~~java
order.getDeliveryAddress().changeCity("Đà Nẵng");
~~~

Với embeddable được Hibernate quản lý như component, thay đổi thuộc tính thành phần thường có thể được phát hiện theo snapshot, nhưng chi tiết còn tùy access, mutable state và enhancement. Đừng suy rộng kết luận này sang mọi kiểu object JSON hoặc object tùy biến lưu thành một cột.

Một alternative là embeddable bất biến và thay toàn bộ:

~~~java
order.changeDeliveryAddress(
    new Address("123 Nguyễn Trãi", "Đà Nẵng")
);
~~~

Cách này giúp API nghiệp vụ diễn đạt việc thay địa chỉ rõ ràng. Nếu ứng dụng dùng immutable embeddable/record, cần chọn mapping phù hợp với phiên bản Hibernate/JPA.

## 14. Collection dirty checking: `List`, `Set`, `Map` và association

Hibernate không chỉ quản lý basic properties. Nó còn theo dõi thay đổi collection persistent như `@ElementCollection`, `@OneToMany` và `@ManyToMany`.

Ví dụ:

~~~java
@Entity
public class Article {
    @Id
    private Long id;

    @ElementCollection
    @CollectionTable(
        name = "article_tags",
        joinColumns = @JoinColumn(name = "article_id")
    )
    @Column(name = "tag")
    private Set<String> tags = new HashSet<>();

    protected Article() {
    }

    public void addTag(String tag) {
        tags.add(tag);
    }

    public void removeTag(String tag) {
        tags.remove(tag);
    }
}
~~~

Trong persistence context:

~~~java
Article article = em.find(Article.class, articleId);
article.addTag("hibernate");
~~~

Khi flush, Hibernate có thể phát hiện **membership collection** đã thay đổi và thực hiện `INSERT` vào `article_tags`, dù không có basic field nào khác của `Article` đổi.

### Collection wrappers

Hibernate thường dùng hoặc thay bằng các wrapper persistent collection để theo dõi thao tác thêm/xóa, trạng thái khởi tạo và snapshot. Những wrapper này không nhất thiết là `HashSet`/`ArrayList` chính xác, dù field được khai báo bằng `Set`/`List`.

Vì vậy không nên:

~~~java
HashSet<String> tags = (HashSet<String>) article.getTags();
~~~

vì collection runtime có thể là wrapper khác. Dùng interface `Set<String>`/`List<T>` và phương thức nghiệp vụ.

### Dirty collection không đồng nghĩa update bảng owner

Thêm một tag có thể chỉ yêu cầu:

~~~sql
INSERT INTO article_tags(article_id, tag)
VALUES (10, 'hibernate');
~~~

Chưa chắc Hibernate cần `UPDATE articles`. Có phải tăng `@Version` của owner hay không phụ thuộc collection mapping, ownership, version exclusion và cơ chế provider. Không nên mặc định mọi thay đổi collection đều dẫn tới một `UPDATE` entity cha.

### Bag và SQL xóa/chèn lại

Với bag chứa nhiều phần tử bằng nhau mà bảng collection không có khóa hàng/vị trí, Hibernate có thể khó xác định chính xác một lần xuất hiện để xóa. Tùy mapping, việc thay đổi collection có thể dẫn tới `DELETE` các hàng của owner rồi `INSERT` lại phần còn lại.

Điểm này thuộc **collection synchronization**, khác với so sánh giá trị một field `price` đơn giản.

## 15. Thay association: phía sở hữu quyết định FK

Xét entity `PurchaseOrder` có:

~~~java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "customer_id")
private Customer customer;
~~~

Nếu entity managed và ứng dụng thay customer:

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
Customer other = em.getReference(Customer.class, otherCustomerId);

order.changeCustomer(other);
~~~

Hibernate có thể phát hiện thay đổi reference association và đồng bộ cột `purchase_orders.customer_id` khi flush. Nó không nhất thiết phải đọc toàn bộ trạng thái `Customer` mới nếu chỉ cần ID để ghi FK.

Với quan hệ **hai chiều**:

~~~java
// Customer
@OneToMany(mappedBy = "customer")
private List<PurchaseOrder> orders;
~~~

thì phía `PurchaseOrder.customer` là owning side của FK trong mapping này. Chỉ gọi:

~~~java
customer.getOrders().add(order);
~~~

mà không thay `order.customer` có thể khiến object graph lệch và không tạo ra thay đổi FK như mong đợi.

**Dirty checking không tự đoán “ý định quan hệ” từ mọi phía của object graph.** Nó đồng bộ dựa trên metadata về owning side, inverse side và collection membership. Phương thức helper cập nhật cả hai phía có thể giúp model nhất quán.

## 16. Hibernate enhanced dirty tracking: theo dõi thay đổi qua bytecode

Cơ chế snapshot truyền thống có thể cần đọc và so sánh nhiều thuộc tính của managed entity tại flush. Hibernate còn hỗ trợ **bytecode enhancement** — thêm khả năng tracking vào bytecode của class entity.

Khái niệm:

~~~text
Snapshot comparison:
  Load entity → lưu snapshot
  Flush       → kiểm tra các persistent properties
                → xác định thuộc tính khác

Enhanced dirty tracking:
  Load entity → thực thể có cơ chế tracking
  Sửa field   → cơ chế enhancement ghi dấu thuộc tính đã đổi
  Flush       → sử dụng thông tin dirty flags và mapping
                → đồng bộ thay đổi phù hợp
~~~

Với enhanced dirty tracking, Hibernate có thể biết các field đã được chỉnh mà không cần thực hiện toàn bộ phép so sánh như cơ chế truyền thống trong nhiều trường hợp. Điều này có thể giảm chi phí khi persistence context chứa nhiều entity hoặc entity có rất nhiều field.

Nhưng không nên suy luận:

- Bytecode enhancement **luôn luôn bật** trong mọi dự án.
- Enhancement **loại bỏ mọi snapshot** trong mọi trường hợp.
- Mọi thay đổi bên trong nested mutable object đều được tracking trực tiếp.
- Thay đổi bất kỳ field Java nào cũng là persistent dirty state.
- Có enhancement là SQL chạy ngay khi field được gán.

Enhancement thường cần cấu hình build-time hoặc runtime phù hợp với phiên bản Hibernate và môi trường. Ví dụ cơ chế Maven/Gradle plugin enhancement phụ thuộc phiên bản; khi dùng framework có cấu hình tự động, cần xem tài liệu và thực tế build thay vì mặc định đã được kích hoạt.

### Vì sao mutable nested state vẫn cần cẩn thận?

Inline tracking thường dễ ghi dấu **thay thế field trực tiếp**:

~~~java
product.changePrice(new BigDecimal("480000.00"));
~~~

Nhưng nếu field giữ một object mutable và chỉ sửa sâu bên trong:

~~~java
product.getPayload().getMetadata().put("x", "y");
~~~

thì field `payload` không nhất thiết bị gán lại. Cách Hibernate phát hiện có thể phụ thuộc mutability plan, snapshot và mapping JSON/custom type, không chỉ bytecode enhancement.

Do đó, với custom value type, vẫn nên ưu tiên giá trị bất biến hoặc khai báo mutability/equality rõ ràng.

## 17. Dirty checking xác định có update; SQL cập nhật cột nào là chuyện khác

Một nhầm lẫn phổ biến là: “Chỉ `price` dirty thì Hibernate chắc chắn tạo `UPDATE` chỉ chứa cột `price`.” Không phải lúc nào cũng vậy.

Theo chiến lược SQL update thông thường, Hibernate có thể chuẩn bị lệnh `UPDATE` gồm nhiều cột updatable của entity ngay cả khi chỉ một field thực sự dirty:

~~~sql
UPDATE products
SET sku = ?,
    name = ?,
    price = ?,
    stock_quantity = ?,
    version = ?
WHERE id = ? AND version = ?;
~~~

**Ý nghĩa dirty checking** là quyết định entity có cần UPDATE và trạng thái nào khác snapshot. **Danh sách cột trong SQL** còn phụ thuộc SQL generation strategy, mapping và annotation.

Hibernate cung cấp annotation riêng:

~~~java
import org.hibernate.annotations.DynamicUpdate;

@Entity
@DynamicUpdate
@Table(name = "products")
public class Product {
    // Các field và mapping như ví dụ trước.
}
~~~

Với `@DynamicUpdate`, Hibernate có thể tạo SQL dựa trên các thuộc tính cần ghi, ví dụ:

~~~sql
UPDATE products
SET price = ?, version = ?
WHERE id = ? AND version = ?;
~~~

Đoạn `Product` là ví dụ về vị trí annotation; không tạo một class thứ hai trùng tên trong ứng dụng thật.

### Khi nào `@DynamicUpdate` hữu ích?

- Entity có nhiều cột nhưng mỗi transaction thường chỉ sửa một vài field.
- Cột không cần ghi lại có trigger hoặc cơ chế quản lý riêng cần tránh can thiệp.
- Giảm số giá trị bind và cột bị tác động có thể có lợi trong trường hợp cụ thể.

Nhưng `@DynamicUpdate` cũng có trade-off:

- Hibernate có thể phải tạo nhiều biến thể SQL theo các tập field dirty khác nhau.
- Khả năng tái sử dụng prepared statement/batch có thể bị ảnh hưởng.
- Chỉ định dynamic update không thay thế thiết kế transaction/locking.
- Không phải mọi mapping hay API cập nhật đều tuân thủ giống một entity update thông thường.

**Không bật `@DynamicUpdate` đại trà mà không đo hiệu năng.** Với entity nhỏ, SQL static có thể đơn giản và hiệu quả.

## 18. `@Version`: dirty checking và optimistic locking

Nếu một entity có `@Version`:

~~~java
@Version
@Column(name = "version", nullable = false)
private Long version;
~~~

Hibernate sử dụng version để bảo vệ thao tác cập nhật trước nguy cơ **lost update**.

Hai transaction cùng nạp:

~~~text
Database: Product 10, price=400000, version=3

Transaction A                  Transaction B
Load version=3                Load version=3
price=450000                   price=470000
Flush/commit UPDATE            Flush/commit UPDATE
WHERE version=3                WHERE version=3
→ thành công                   → 0 hàng vì A đã nâng version
→ version=4                    → optimistic locking failure
~~~

SQL minh họa:

~~~sql
UPDATE products
SET price = 450000, version = 4
WHERE id = 10 AND version = 3;
~~~

Nếu hàng bị transaction khác cập nhật trước, thao tác sau có thể không cập nhật hàng mong đợi. Hibernate báo lỗi optimistic locking (có thể qua `OptimisticLockException` hoặc ngoại lệ Hibernate được bọc).

**Dirty checking phát hiện trạng thái nào đã sửa; `@Version` kiểm tra có được phép ghi đè lên phiên bản đã nạp hay không.** Đây là hai nhiệm vụ khác nhau.

Khi entity không dirty, Hibernate thường không cần entity UPDATE và vì vậy cũng không tự tăng version chỉ vì transaction đọc entity rồi commit. Tuy nhiên, explicit optimistic force increment, một số collection updates hoặc cơ chế đặc biệt có thể tác động version theo mapping; cần xét API và tình huống cụ thể.

### Không tự sửa field `@Version`

Không dùng:

~~~java
product.setVersion(100L);
~~~

để “giải quyết” optimistic locking. Version thuộc cơ chế concurrency của provider. Khi conflict, cần rollback và quyết định nghiệp vụ: tải lại, báo người dùng, retry có kiểm soát hoặc hợp nhất thay đổi.

## 19. FlushMode ảnh hưởng thời điểm phát hiện và đồng bộ

JPA có các flush mode như:

- `FlushModeType.AUTO`: provider phải xử lý tính nhất quán giữa thay đổi pending và kết quả query trong những trường hợp yêu cầu; Hibernate có thể tự flush trước query.
- `FlushModeType.COMMIT`: tác động của thay đổi chưa flush lên query trước commit không được quy định đầy đủ ở JPA; provider thường trì hoãn flush đến commit nhiều hơn.

Ví dụ:

~~~java
em.setFlushMode(FlushModeType.AUTO);

Product product = em.find(Product.class, 10L);
product.changePrice(new BigDecimal("450000.00"));

Long count = em.createQuery(
    "select count(p) from Product p where p.price > :min",
    Long.class
)
.setParameter("min", new BigDecimal("440000.00"))
.getSingleResult();
~~~

Để query phản ánh thay đổi pending theo hợp đồng AUTO, Hibernate có thể flush trước khi chạy query. Không nên phát biểu rằng **mọi SELECT** đều bắt buộc flush; Hibernate có thể xét các bảng liên quan, flush mode và khả năng bảo đảm kết quả.

Hibernate Session còn có flush mode riêng như `MANUAL`, `ALWAYS`, `AUTO` và `COMMIT` tùy phiên bản. `MANUAL` có thể hữu ích cho các luồng đọc lớn nhưng cũng dễ làm quên đồng bộ thay đổi. Chọn mode dựa trên ngữ nghĩa transaction, không chỉ nhằm “giảm vài query”.

### `flush` so với `commit`

| `flush` | `commit` |
| --- | --- |
| Đồng bộ các thao tác pending xuống DB trong transaction | Xác nhận transaction thành công |
| Có thể phát `INSERT`, `UPDATE`, `DELETE` | Có thể bao gồm bước flush trước khi kết thúc |
| Không bảo đảm dữ liệu đã commit | Khi thành công, dữ liệu được xác nhận theo transaction |
| Có thể bị rollback | Sau commit thành công không rollback cùng transaction được |
| Có thể xảy ra nhiều lần trong một transaction | Mỗi transaction chỉ kết thúc một lần |

Một phép dirty checking tại flush có thể phát hiện thay đổi và gửi SQL, nhưng transaction sau đó vẫn thất bại vì ràng buộc, lock, deadlock hoặc logic khác.

## 20. Những thuộc tính không được ghi như bình thường

Không phải mọi field đã gán trong object đều được Hibernate đưa vào SQL update.

### `@Transient`

~~~java
@Transient
private String displayLabel;
~~~

`displayLabel` không phải persistent field theo mapping JPA. Thay nó không khiến Hibernate tự cập nhật một cột `display_label`.

### `@Column(updatable = false)`

~~~java
@Column(name = "created_at", updatable = false)
private LocalDateTime createdAt;
~~~

Field này được ánh xạ nhưng Hibernate không đưa cột đó vào entity SQL UPDATE qua mapping bình thường. Sửa giá trị trong memory không nhất thiết tạo cập nhật cho cột; nếu những field khác dirty, SQL vẫn có thể update các cột khác.

### `@Id`

~~~java
@Id
private Long id;
~~~

Entity identifier phải được xem là bất biến sau khi entity persistent. Thay ID không phải thao tác dirty checking bình thường để chuyển `WHERE id=10` thành `WHERE id=20`; Hibernate thường phát hiện lỗi thay identifier.

### `@Version`

Version được quản lý bởi optimistic locking, không nên sửa như giá trị nghiệp vụ.

### `@Immutable` của Hibernate

~~~java
import org.hibernate.annotations.Immutable;

@Entity
@Immutable
public class ExchangeRateSnapshot {
    @Id
    private Long id;

    private BigDecimal rate;

    protected ExchangeRateSnapshot() {
    }
}
~~~

Entity `@Immutable` có ý nghĩa Hibernate không theo dõi để cập nhật trạng thái như entity mutable thông thường. Điều này có thể giảm chi phí dirty checking; thay field của instance immutable không nên được coi là thao tác update DB đáng tin cậy.

`@Immutable` là **Hibernate-specific**, không phải annotation chuẩn JPA. Nó không thay quyền write của database hoặc ngăn mọi SQL native từ ứng dụng khác.

## 21. Transaction read-only có tắt dirty checking không?

Trong Spring:

~~~java
@Transactional(readOnly = true)
public ProductDto readProduct(Long id) {
    Product product = repository.findById(id)
        .orElseThrow();
    return ProductDto.from(product);
}
~~~

`readOnly = true` là một **gợi ý/hợp đồng transaction của Spring**, không phải bảo đảm phổ quát rằng mọi thay đổi Java sẽ bị chặn hoặc mọi JPA provider hoạt động y hệt. Với các tích hợp Spring + Hibernate, framework có thể chọn flush mode hoặc read-only session behavior để tối ưu, nhưng điều đó phụ thuộc phiên bản và cấu hình.

Không nên dùng:

~~~java
@Transactional(readOnly = true)
public void updateProduct(Long id) {
    repository.findById(id).orElseThrow()
        .changePrice(new BigDecimal("500000.00"));
}
~~~

rồi kỳ vọng chắc chắn database đã được cập nhật. Muốn thực hiện nghiệp vụ ghi, dùng transaction ghi rõ ràng và kiểm tra quyền/ràng buộc phù hợp.

Hibernate native cũng hỗ trợ đặt session/entity read-only trong một số ngữ cảnh, ví dụ `Session#setDefaultReadOnly` hoặc `Session#setReadOnly`. Khi entity được đánh dấu read-only, Hibernate có thể bỏ việc dirty-check các thuộc tính simple ở trường hợp được hỗ trợ. Nhưng quan hệ, collection, lifecycle và cách chuyển read-only về mutable cần xem kỹ quy định provider.

## 22. JPQL bulk update không đi qua dirty checking từng entity

JPA cho phép cập nhật hàng loạt:

~~~java
int changed = em.createQuery(
    "update Product p set p.stockQuantity = 0 " +
    "where p.sku like :prefix"
)
.setParameter("prefix", "OLD-%")
.executeUpdate();
~~~

Đây là **bulk JPQL update**: provider tạo thao tác SQL theo điều kiện, không bắt buộc nạp từng entity vào persistence context rồi gọi setter. Vì vậy nó **bỏ qua dirty checking và entity lifecycle bình thường cho từng hàng**.

Hệ quả quan trọng:

- Managed entities đã nạp trong context có thể vẫn giữ `stockQuantity` cũ.
- Callback/listener thông thường của từng entity có thể không chạy theo cách cập nhật managed entity.
- Version có thể không tự tăng theo cùng quy tắc entity update; nếu cần, thiết kế bulk update có điều kiện và xử lý version rõ ràng.
- Second-level cache và các vùng cache liên quan cần được hiểu theo cơ chế invalidation của provider.

Sau bulk update, đôi khi cần `em.clear()` hoặc `refresh` để tránh tiếp tục dùng managed state không còn khớp database:

~~~java
em.flush(); // Nếu có thay đổi managed cần gửi trước bulk update.
int affected = em.createQuery(/* bulk update */)
    .executeUpdate();
em.clear(); // Entity managed trước đó bị detach.
~~~

Đây là sơ đồ thao tác; `em.clear()` ảnh hưởng **tất cả entity trong context**, nên phải quyết định đúng phạm vi và đảm bảo không làm mất các pending changes chưa flush.

### Native SQL cũng có thể bỏ qua tracking entity

~~~java
em.createNativeQuery(
    "update products set stock_quantity = 0 where sku like :p"
)
.setParameter("p", "OLD-%")
.executeUpdate();
~~~

SQL này thay dữ liệu database trực tiếp. Hibernate không tự cập nhật field của tất cả Java objects đã managed chỉ vì SQL native vừa chạy. Không trộn bulk update và các entity managed được giữ lâu mà không có chiến lược đồng bộ trạng thái.

## 23. Tác động của listener, trigger và giá trị do database sinh

Một entity có thể có callback JPA:

~~~java
@PreUpdate
void beforeUpdate() {
    updatedAt = LocalDateTime.now();
}
~~~

Callback `@PreUpdate` thường được gọi trước khi thực hiện update entity khi lifecycle event phù hợp. Nếu entity **không được coi là dirty**, callback update không nhất thiết được kích hoạt chỉ vì transaction commit. Không nên dùng `@PreUpdate` để tự tạo một cập nhật từ một entity hoàn toàn sạch mà không hiểu thứ tự event và khả năng provider.

Database cũng có thể có trigger cập nhật `updated_at` hoặc tự chuẩn hóa giá trị. Khi trigger thay cột SQL:

- Managed object hiện tại không tự biết mọi giá trị do trigger tính nếu mapping không có cơ chế nạp generated value.
- Snapshot trong context có thể khác database sau trigger.
- `refresh` hoặc generated-value mapping phù hợp có thể cần thiết.
- Đọc thêm trong transaction phụ thuộc isolation level.

Dirty checking phản ánh **state của entity trong persistence context**, không phải bộ giám sát tự động mọi thay đổi do trigger/ứng dụng khác phát sinh ở database.

## 24. Hiệu năng: dirty checking có chi phí ở đâu?

Nếu persistence context chứa 50.000 entity managed, provider có thể phải xem xét lượng lớn state tại flush. Kể cả khi chỉ một phần nhỏ thay đổi, việc duy trì snapshot, entity entries và dirty tracking vẫn tiêu tốn bộ nhớ và CPU.

Những yếu tố ảnh hưởng:

- **Số managed entities** trong persistence context.
- **Số persistent attributes** của mỗi entity.
- **Kiểu thuộc tính**: bất biến đơn giản hay mutable/custom type.
- **Số collection** và cách Hibernate snapshot membership.
- **Bytecode enhancement** có được bật và dùng đúng mapping không.
- **Flush mode** và số lần flush thực sự.
- **SQL batching**, versioning, cascades và cách tạo câu UPDATE.

Một số cách tổ chức thường hữu ích:

1. Với đọc dữ liệu lớn không cần entity managed, dùng projection/DTO hoặc read-only query phù hợp.
2. Với batch xử lý dài, xem xét flush/clear theo từng lô, nhưng không detach pending changes chưa đồng bộ.
3. Tránh nạp object graph lớn không cần dùng.
4. Chọn value objects có equality/mutability rõ ràng.
5. Dùng `@DynamicUpdate` khi có lý do đo được, không bật theo thói quen.
6. Dùng `@Version` cho cập nhật cạnh tranh quan trọng.
7. Kiểm soát transaction ngắn và ranh giới service rõ ràng.

**Dirty checking không phải nguyên nhân duy nhất của hệ thống chậm.** Lưu lượng SQL, N+1, index thiếu, network latency, lock, fetch strategy và kích thước transaction cũng ảnh hưởng đáng kể.

## 25. Quan sát SQL để hiểu dirty checking

Có thể bật logging trong môi trường phát triển. Với Spring Boot + Hibernate 6:

~~~properties
logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE
~~~

Với Hibernate native:

~~~properties
hibernate.show_sql=true
hibernate.format_sql=true
~~~

Các logger và cấu hình chi tiết thay đổi theo phiên bản. Không nên bật TRACE bind parameters trên production có thông tin nhạy cảm khi chưa có chính sách bảo vệ log.

Thí nghiệm khái niệm:

~~~java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Product product = em.find(Product.class, 10L);
    System.out.println("Loaded price: " + product.getPrice());

    product.changePrice(new BigDecimal("450000.00"));
    System.out.println("Changed Java object");

    em.flush();
    System.out.println("Flush completed");

    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
} finally {
    em.close();
}
~~~

Quan sát dự kiến:

~~~text
SELECT ... FROM products WHERE id=?
Loaded price: 400000.00
Changed Java object
UPDATE products SET ... WHERE id=? ...
Flush completed
~~~

Trong trường hợp thông thường, SQL UPDATE nằm **tại `flush` hoặc một thời điểm provider đồng bộ**, không bắt buộc xuất hiện ngay giữa lời gọi `changePrice` và dòng `println` kế tiếp.

Nếu không thấy UPDATE, có thể entity không dirty, transaction không phù hợp, entity detached/read-only, mapping field không updatable, flush chưa xảy ra hoặc query/cache/SQL logger chưa cấu hình đúng. Không vội kết luận “Hibernate không theo dõi setter”.

## 26. Một số hiểu nhầm phổ biến

| Hiểu nhầm | Cách hiểu chính xác |
| --- | --- |
| Mỗi lần gọi setter trên managed entity đều sinh UPDATE | Hibernate có thể gom thay đổi và xử lý tại flush |
| Dirty checking cần query lại database để so sánh | Snapshot trong persistence context thường đủ cho entity managed |
| Hibernate chỉ nhận biết thay đổi qua setter | Field access, snapshot và bytecode enhancement đều có thể tham gia |
| Gọi `save()` mới lưu thay đổi của managed entity | Với managed entity, dirty checking + flush là cơ chế cốt lõi |
| `flush()` có nghĩa transaction đã commit | Flush gửi SQL, vẫn có thể rollback |
| Đổi field Java `@Transient` sẽ làm UPDATE | Field đó không thuộc persistent mapping |
| Đổi `@Id` được xử lý như thay thuộc tính thường | Identifier không được đổi sau khi entity persistent |
| Dirty checking luôn update đúng một cột vừa đổi | SQL static có thể gán nhiều cột; `@DynamicUpdate` là lựa chọn riêng |
| Dirty checking tự phát hiện mọi sửa đổi sâu trong custom mutable object | Phụ thuộc mutability, snapshot, equality và enhancement |
| Chỉ cần đổi phía inverse của quan hệ hai chiều | Owning side/mapping quyết định FK/association được ghi |
| Bulk JPQL update vẫn gọi setter/callback từng entity | Bulk operation bỏ qua entity-level tracking bình thường |
| `readOnly=true` luôn khóa mọi SQL UPDATE ở mọi provider | Đây là hint/cơ chế phụ thuộc framework/cấu hình |
| Tăng `@Version` xảy ra cho mọi transaction đọc | Version chủ yếu phục vụ các lần cập nhật phù hợp |
| Sau rollback object Java tự phục hồi field ban đầu | Java object có thể vẫn giữ giá trị đã sửa |
| Dirty checking tự sửa dữ liệu khi trigger ở DB thay đổi cột | Context phải nạp/refresh theo cơ chế phù hợp |

## 27. Bài tập tình huống

### Tình huống A — Không gọi `save`

Một service dùng transaction, thực hiện:

~~~java
Product p = em.find(Product.class, 10L);
p.changePrice(new BigDecimal("490000.00"));
~~~

Sau đó commit.

**Câu hỏi:** Có cần `em.persist(p)` lần nữa không?

**Trả lời:** Không. `p` là managed entity do `find` trả về; Hibernate có thể phát hiện thay đổi và đồng bộ khi flush/commit.

### Tình huống B — Sửa rồi sửa lại

~~~java
Product p = em.find(Product.class, 10L);
p.changePrice(new BigDecimal("490000.00"));
p.changePrice(new BigDecimal("400000.00"));
em.flush();
~~~

Giả sử snapshot ban đầu là `400000.00`.

**Trả lời:** Với snapshot comparison truyền thống và giá trị so sánh cuối cùng tương đương snapshot, Hibernate có thể coi price không dirty. Với enhancement hoặc type mapping khác, không nên cam kết chính xác SQL chỉ dựa vào số lần gán field.

### Tình huống C — Object detached

~~~java
Product p = em.find(Product.class, 10L);
em.detach(p);
p.changePrice(new BigDecimal("510000.00"));
em.flush();
~~~

**Trả lời:** Thay đổi sau detach không được context đó đồng bộ tự động. Cần nạp managed entity và sửa đúng field hoặc merge theo thiết kế.

### Tình huống D — Collection được thêm phần tử

~~~java
Article a = em.find(Article.class, 7L);
a.addTag("orm");
~~~

**Trả lời:** Hibernate có thể nhận ra membership của persistent collection thay đổi và chèn/xóa hàng collection table khi flush, dù basic field của `Article` không đổi.

### Tình huống E — Quan hệ hai chiều

Một entity `Order` có field `customer` là owning `@ManyToOne`. Ứng dụng chỉ sửa `customer.getOrders().add(order)`, không đổi `order.customer`.

**Trả lời:** Object graph có thể không nhất quán và FK chưa chắc được cập nhật. Cần sửa owning side và đồng bộ collection inverse bằng helper.

### Tình huống F — Flush rồi rollback

~~~java
p.changePrice(new BigDecimal("510000.00"));
em.flush();
tx.rollback();
~~~

**Trả lời:** SQL có thể đã được gửi, nhưng rollback hủy thay đổi chưa commit ở database. Object Java không nhất thiết tự trở lại giá cũ.

### Tình huống G — Read-only entity

Entity được đánh dấu `@Immutable` và ứng dụng thay một thuộc tính đơn giản.

**Trả lời:** Không được dựa vào dirty checking để ghi cập nhật đó qua entity mapping; Hibernate coi entity immutable ở những cơ chế tương ứng.

### Tình huống H — Bulk JPQL update

~~~java
em.createQuery(
    "update Product p set p.stockQuantity = 0"
).executeUpdate();
~~~

**Trả lời:** Đây không phải dirty checking trên từng managed `Product`. Các object đã nạp có thể còn giá trị cũ, cần xử lý context/cache và version rõ ràng.

### Tình huống I — Một field thay đổi nhưng SQL chứa nhiều cột

Hibernate log:

~~~sql
UPDATE products
SET name=?, sku=?, price=?, stock_quantity=?, version=?
WHERE id=? AND version=?;
~~~

Trong khi code chỉ sửa `price`.

**Trả lời:** Điều đó không phủ nhận dirty checking. Cơ chế xác định dirty state và cơ chế tạo danh sách cột SQL là hai phần khác nhau. Có thể xem `@DynamicUpdate` khi cần và sau khi đánh giá trade-off.

### Tình huống J — Value object mutable

Ứng dụng sửa nội dung trong object custom mà không gán lại field entity.

**Trả lời:** Khả năng nhận biết phụ thuộc mapping, mutability plan, snapshot và enhancement. Ưu tiên value object bất biến/thay toàn bộ giá trị hoặc cấu hình kiểu mutable đúng cách.

## 28. Quy trình xác định vì sao một UPDATE không xuất hiện

~~~mermaid
flowchart TD
    A["Đã thay đổi giá trị trên một entity?"] --> B{"Entity đang managed?"}
    B -- "Không" --> C["New/detached: cần persist hoặc thao tác trên managed instance"]
    B -- "Có" --> D{"Thuộc tính có persistent, mutable, updatable?"}
    D -- "Không" --> E["Kiểm tra @Transient, @Immutable, updatable=false, access"]
    D -- "Có" --> F{"Giá trị hiện tại có được xem là dirty?"}
    F -- "Không" --> G["Xem snapshot, equality, mutability và enhanced tracking"]
    F -- "Có" --> H{"Đã đến thời điểm flush phù hợp?"}
    H -- "Không" --> I["Kiểm tra transaction và FlushMode"]
    H -- "Có" --> J{"SQL và transaction có thành công?"}
    J -- "Không" --> K["Xem lỗi constraint, optimistic lock, rollback"]
    J -- "Có" --> L["Database được đồng bộ trong transaction"]
~~~

Sơ đồ giúp phân biệt bốn nhóm nguyên nhân: **vòng đời**, **mapping**, **phát hiện thay đổi** và **flush/transaction**. Không nên sửa mã bằng cách thêm `save()` hoặc gọi `flush()` ở mọi nơi trước khi xác định nhóm lỗi đúng.

## 29. Tổng kết

**Dirty checking là cơ chế Hibernate nhận biết trạng thái persistent của managed entity đã thay đổi so với trạng thái được quản lý trước đó.** Trong trường hợp thông dụng, Hibernate lưu snapshot khi nạp entity và so sánh với trạng thái hiện tại lúc flush; với bytecode enhancement, nó có thể sử dụng thông tin thay đổi được ghi nhận ở cấp bytecode.

Những ý quan trọng cần giữ:

1. **Managed entity là điều kiện nền tảng.** Đối tượng new hoặc detached không tự được context dirty-check để cập nhật.
2. **So sánh trạng thái không đồng nghĩa đọc lại database.** Snapshot được duy trì trong persistence context.
3. **Dirty checking thường xảy ra khi flush**, không đồng nghĩa SQL chạy tại mỗi setter.
4. **Flush khác commit.** SQL đã gửi vẫn có thể rollback.
5. **Basic attributes, embeddables và collections có cơ chế tracking liên quan nhưng khác nhau**; các thay đổi sâu trong custom mutable type cần mapping đúng.
6. **`@DynamicUpdate` điều chỉnh SQL cập nhật cột nào**, không phải điều kiện để Hibernate có thể nhận biết thay đổi.
7. **`@Version` kiểm soát cập nhật cạnh tranh**, không thay thế dirty checking.
8. **Entity bulk update và SQL native bỏ qua entity-level tracking thông thường**; cần quản lý state/cache sau thao tác.
9. **Không nhầm read-only, transient, non-updatable và identifier với thuộc tính ghi bình thường.**
10. **Hiệu năng phụ thuộc kích thước persistence context và lượng SQL**, nên đo trước khi tối ưu enhancement hoặc flush mode.

Khi hiểu vòng **nạp entity → giữ trạng thái gốc → sửa managed object → phát hiện dirty state → flush SQL → commit/rollback**, bạn có thể viết phương thức nghiệp vụ rõ nghĩa mà không phải quản lý từng câu `UPDATE` thủ công, đồng thời biết chính xác nơi cần kiểm tra khi Hibernate không ghi một thay đổi như mong đợi.
