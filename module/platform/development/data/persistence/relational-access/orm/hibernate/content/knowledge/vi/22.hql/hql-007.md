# Join tường minh, join ngầm định và ảnh hưởng của quan hệ tùy chọn

Trong HQL, một association có thể được nối bằng **join tường minh** (*explicit join*) hoặc được Hibernate suy ra từ **đường dẫn thuộc tính** (*implicit join*). Hai cách viết có thể trông tương đương, nhưng chúng ảnh hưởng trực tiếp tới những hàng gốc được giữ lại, nhất là khi quan hệ là tùy chọn và khóa ngoại có thể `NULL`.

Điểm cần nhớ nhất:

> **Implicit join khi điều hướng qua association trong HQL có semantics INNER JOIN.** Việc mapping khai báo `optional = true` không tự biến đường dẫn đó thành LEFT JOIN.

Nếu một `PurchaseOrder` không có `Customer`, truy vấn:

```hql
select o
from PurchaseOrder o
where o.customer.name = :customerName
```

điều hướng từ `o` qua `customer` để đọc `name`. Hibernate cần nối bảng customer; hàng order không có customer không thỏa inner join và không xuất hiện trong kết quả.

Nếu mục tiêu là **giữ mọi order kể cả khi chưa có customer**, hãy viết join tường minh:

```hql
select o
from PurchaseOrder o
left join o.customer c
```

Một điểm tinh tế khác: dù đã viết `LEFT JOIN`, điều kiện đặt trong `WHERE` vẫn có thể loại các hàng có phía phải là `NULL`. Khi muốn lọc association nhưng giữ hàng gốc không có association phù hợp, hãy cân nhắc đặt điều kiện vào `ON`.

Bài học giải thích cú pháp, SQL được sinh, null semantics, đường dẫn lồng nhau, fetch join, truy vấn collection, ví dụ kiểm thử và cách chọn join theo yêu cầu nghiệp vụ.

## 1. Mô hình dữ liệu để quan sát join

Giả sử hệ thống có đơn hàng và khách hàng. Một order có thể chưa được gán customer vì được tạo từ một kênh chưa xác định người mua.

```text
purchase_orders
+----+------------+-------------+
| id | order_no   | customer_id |
+----+------------+-------------+
| 10 | PO-010     | 1           |
| 11 | PO-011     | NULL        |
| 12 | PO-012     | 2           |
| 13 | PO-013     | NULL        |
+----+------------+-------------+

customers
+----+-------------+----------+
| id | name        | status   |
+----+-------------+----------+
| 1  | An          | ACTIVE   |
| 2  | Bình        | INACTIVE |
+----+-------------+----------+
```

Mapping:

```java
import jakarta.persistence.*;

@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false)
    private String status;

    protected Customer() {
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public String getStatus() {
        return status;
    }
}
```

```java
import jakarta.persistence.*;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "order_no", nullable = false, unique = true)
    private String orderNumber;

    @ManyToOne(fetch = FetchType.LAZY, optional = true)
    @JoinColumn(name = "customer_id", nullable = true)
    private Customer customer;

    protected PurchaseOrder() {
    }

    public Long getId() {
        return id;
    }

    public String getOrderNumber() {
        return orderNumber;
    }

    public Customer getCustomer() {
        return customer;
    }
}
```

Các thuộc tính quan trọng:

- `@ManyToOne` mô tả association từ nhiều order tới một customer.
- `optional = true` nói rằng association có thể không có giá trị trong mô hình object.
- `@JoinColumn(nullable = true)` mô tả cột FK có thể nhận `NULL` trong schema được sinh/quản lý theo mapping.
- `fetch = LAZY` yêu cầu provider trì hoãn tải association khi có thể; fetch strategy và join type trong HQL là hai vấn đề khác nhau.

DDL minh họa:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_no VARCHAR(40) NOT NULL UNIQUE,
    customer_id BIGINT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);
```

Trong ví dụ, `customer_id = NULL` là một trạng thái hợp lệ. Database vẫn bảo đảm nếu cột có giá trị thì giá trị đó phải tham chiếu một customer tồn tại.

## 2. Join tường minh là gì?

Join tường minh xuất hiện trực tiếp trong `FROM`:

```hql
select o
from PurchaseOrder o
join o.customer c
```

Cú pháp có các phần:

```text
join <đường dẫn association> <alias>
```

- `o` là alias của entity gốc `PurchaseOrder`.
- `o.customer` là association được ánh xạ.
- `c` là alias cho entity ở phía customer.
- `join` mặc định là **inner join**.

Có thể viết rõ:

```hql
select o
from PurchaseOrder o
inner join o.customer c
where c.status = :status
```

Nếu muốn giữ order không có customer:

```hql
select o
from PurchaseOrder o
left join o.customer c
```

`LEFT JOIN` giữ các hàng phía trái ngay cả khi không tìm được hàng phía phải. Các thuộc tính của alias `c` khi không có customer sẽ mang giá trị `NULL` trong kết quả join.

### 2.1. Alias giúp truy vấn dễ đọc và tái sử dụng

```hql
select o
from PurchaseOrder o
join o.customer c
where c.status = :status
  and c.name like :namePattern
order by c.name
```

Alias `c` cho phép tham chiếu cùng association trong nhiều biểu thức. Không cần lặp đường dẫn `o.customer.status`, `o.customer.name` ở mọi vị trí.

Với truy vấn nhiều quan hệ:

```hql
select o
from PurchaseOrder o
join o.customer c
left join o.salesRepresentative r
where c.status = :status
```

mỗi alias biểu diễn một association khác nhau. Hãy đặt tên có ý nghĩa, đặc biệt khi cùng entity type xuất hiện nhiều lần.

### 2.2. Inner join loại hàng không có association

Với dữ liệu mẫu:

```hql
select o
from PurchaseOrder o
join o.customer c
order by o.id
```

Kết quả chỉ có:

```text
PO-010 → An
PO-012 → Bình
```

`PO-011` và `PO-013` bị loại vì `customer_id` là `NULL`.

Đây không phải lỗi Hibernate. Đó là semantics của `INNER JOIN`.

### 2.3. Left join giữ hàng gốc

```hql
select o
from PurchaseOrder o
left join o.customer c
order by o.id
```

Kết quả có thể biểu diễn:

| Order | Customer |
| --- | --- |
| PO-010 | An |
| PO-011 | `NULL` |
| PO-012 | Bình |
| PO-013 | `NULL` |

Nếu chỉ `select o`, Hibernate trả các order phù hợp. Nếu select cả hai:

```hql
select o, c
from PurchaseOrder o
left join o.customer c
order by o.id
```

kết quả là các tuple `(order, customer)`; phần tử thứ hai có thể `null`.

## 3. Join ngầm định là gì?

Join ngầm định xảy ra khi HQL điều hướng qua association bằng một path expression mà không khai báo join riêng:

```hql
select o
from PurchaseOrder o
where o.customer.name = :customerName
```

Hibernate nhận thấy `customer` là association và `name` là thuộc tính của entity đích. Nó tạo join cần thiết trong SQL.

SQL minh họa:

```sql
SELECT o.id, o.order_no, o.customer_id
FROM purchase_orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.name = ?;
```

Đây là **inner join**. Order có `customer_id = NULL` không có customer row để thỏa điều kiện.

Một ví dụ trong phần select:

```hql
select o.customer.name
from PurchaseOrder o
```

Điều hướng `o.customer.name` cũng cần truy cập thuộc tính ở entity liên quan. Các order không có customer không cung cấp giá trị name và bị loại bởi semantics inner join của implicit association join.

### 3.1. Path expression lồng nhau có thể tạo nhiều join

Giả sử customer có một địa chỉ:

```java
@ManyToOne(fetch = FetchType.LAZY, optional = true)
@JoinColumn(name = "address_id")
private Address address;
```

HQL:

```hql
select o
from PurchaseOrder o
where o.customer.address.city = :city
```

điều hướng qua hai association:

```text
PurchaseOrder.customer
       ↓
Customer.address
       ↓
Address.city
```

Hibernate cần nối customer và address để đọc `city`. Các implicit association joins này có semantics inner join. Vì thế order không có customer, hoặc customer không có address, sẽ không xuất hiện trong kết quả.

Nếu nghiệp vụ muốn giữ mọi order dù customer/address vắng mặt, hãy viết các left join tương ứng:

```hql
select o
from PurchaseOrder o
left join o.customer c
left join c.address a
```

Đừng giả định một left join đầu tiên làm cho mọi path navigation phía sau tự động trở thành left join.

### 3.2. Hibernate thường tái sử dụng implicit join cùng đường dẫn

Nếu cùng một path association được tham chiếu nhiều lần trong một query, Hibernate có thể tái sử dụng cùng join thay vì tạo một join SQL độc lập cho mỗi lần xuất hiện:

```hql
select o
from PurchaseOrder o
where o.customer.status = :status
  and o.customer.name like :pattern
```

Không cần lặp join thủ công chỉ để mỗi predicate dùng một alias. Tuy nhiên, nếu cần chọn loại join, thêm điều kiện `ON`, hoặc tham chiếu association bằng alias, hãy khai báo explicit join.

### 3.3. Path tới identifier có thể được tối ưu khác

Không phải mọi biểu thức chứa dấu chấm đều nhất thiết sinh cùng một SQL join. Hibernate có thể tối ưu một số truy cập identifier/foreign-key trực tiếp, tùy mapping và phiên bản.

Ví dụ so sánh association với entity hoặc đọc identifier có thể được dịch mà không cần join đầy đủ sang bảng đích. Đừng dùng một path đơn lẻ để suy ra chính xác số JOIN; hãy xem SQL được sinh.

## 4. Khác biệt cốt lõi: implicit join không tự trở thành LEFT JOIN

Mapping:

```java
@ManyToOne(optional = true)
@JoinColumn(nullable = true)
private Customer customer;
```

cho phép order không có customer.

Nhưng query:

```hql
select o
from PurchaseOrder o
where o.customer.name = :name
```

vẫn cần inner join để đọc `name`.

**Optionality trong mapping và join type trong truy vấn trả lời hai câu hỏi khác nhau:**

- `optional = true`: association có được phép không có target trong mô hình entity không?
- `LEFT JOIN`: truy vấn có giữ hàng phía trái khi không có target phù hợp không?

Không có quy tắc nào nói rằng association tùy chọn thì Hibernate phải dùng left join mỗi khi HQL điều hướng qua nó. Nếu cần giữ order không có customer, viết rõ `left join`.

### 4.1. `optional = false` cũng không biến inner join thành yêu cầu duy nhất

Nếu mapping là:

```java
@ManyToOne(optional = false)
@JoinColumn(name = "customer_id", nullable = false)
private Customer customer;
```

thì domain/schema nói mỗi order phải có customer. Inner join thường phù hợp với invariant đó.

Nhưng explicit `LEFT JOIN` vẫn là một cú pháp truy vấn hợp lệ nếu muốn diễn đạt phép nối ngoài, ví dụ để kiểm tra dữ liệu không nhất quán, tương thích với truy vấn dùng chung, hoặc giữ hàng gốc khi điều kiện join bổ sung không khớp.

Nếu database thực sự có `NOT NULL` và FK hợp lệ, left join không tạo ra hàng có customer null trong dữ liệu bình thường; nó chỉ là một lựa chọn SQL rộng hơn.

### 4.2. `optional` và `nullable` không phải cùng một annotation

- `optional` là thuộc tính của association mapping `@ManyToOne`/`@OneToOne`.
- `nullable` là thuộc tính của `@JoinColumn`, liên quan cột join/schema.
- `optional=false` thể hiện association không được thiếu theo object model.
- `nullable=false` thể hiện cột FK không được null trong schema được sinh/kiểm soát theo mapping.

Hai thuộc tính thường được cấu hình nhất quán, nhưng một annotation không tự sửa dữ liệu hiện hữu hoặc thay thế constraint database đã triển khai. Nếu schema và mapping mâu thuẫn, kết quả có thể là lỗi lúc load/flush hoặc dữ liệu không đúng domain.

## 5. So sánh explicit và implicit join

| Tiêu chí | Join tường minh | Join ngầm định |
| --- | --- | --- |
| Cách viết | Có `join`, `left join` và alias | Điều hướng path như `o.customer.name` |
| Chọn INNER/LEFT | Có thể chọn rõ | Association path join có semantics inner |
| Alias cho target | Có | Không khai báo alias riêng |
| Thêm điều kiện `ON` | Có thể | Không có vị trí `ON` riêng |
| Dễ giữ root khi quan hệ optional | Có, với `left join` | Không khi path navigation cần target |
| Fetch association | Có thể dùng `join fetch` | Path navigation không phải fetch join |
| Phù hợp | Truy vấn cần kiểm soát join semantics | Predicate/projection ngắn, đơn giản |
| Độ rõ ràng với null | Cao | Dễ bỏ sót việc loại hàng null |

Ví dụ hai query có vẻ gần nhau nhưng khác kết quả:

```hql
-- Inner join ngầm định
select o
from PurchaseOrder o
where o.customer.status = :status
```

```hql
-- Left join tường minh, giữ order không có customer
select o
from PurchaseOrder o
left join o.customer c
```

Không nên chọn implicit join chỉ vì cú pháp ngắn hơn nếu yêu cầu nghiệp vụ là giữ các hàng có association null.

## 6. `LEFT JOIN` nhưng điều kiện trong `WHERE` vẫn loại hàng null

Đây là lỗi truy vấn rất phổ biến.

Viết:

```hql
select o
from PurchaseOrder o
left join o.customer c
where c.status = :status
```

Người viết có thể mong mọi order đều xuất hiện, và customer chỉ được gắn khi status phù hợp. Nhưng kết quả không như vậy.

Khi order không có customer, `c.status` là `NULL`. Trong logic SQL ba giá trị:

```text
NULL = 'ACTIVE'  → UNKNOWN
```

`WHERE` chỉ giữ hàng mà biểu thức là TRUE. Vì vậy order không có customer bị loại. Truy vấn này về kết quả thường tương đương inner join đối với predicate đó.

### 6.1. Chuyển điều kiện sang `ON` để giữ hàng gốc

Nếu mục tiêu là lấy mọi order, nhưng chỉ nối customer khi customer active:

```hql
select o, c
from PurchaseOrder o
left join o.customer c on c.status = :status
order by o.id
```

Kết quả:

| Order | Customer phù hợp |
| --- | --- |
| PO-010 | An (ACTIVE) |
| PO-011 | `NULL` |
| PO-012 | `NULL` vì Bình INACTIVE |
| PO-013 | `NULL` |

`ON` lọc **hàng phía phải được nối**. Nếu không có customer thỏa điều kiện, hàng phía trái vẫn được giữ và các cột phía phải là null.

### 6.2. So sánh WHERE và ON

```hql
-- WHERE lọc toàn bộ kết quả sau phép join
select o, c
from PurchaseOrder o
left join o.customer c
where c.status = 'ACTIVE'
```

```hql
-- ON lọc ứng viên ở phía phải của phép left join
select o, c
from PurchaseOrder o
left join o.customer c on c.status = 'ACTIVE'
```

Hai query **không tương đương**.

- Query thứ nhất chỉ giữ order có customer active.
- Query thứ hai giữ mọi order; customer chỉ được trả về khi active.

### 6.3. Dùng `OR c IS NULL` có luôn thay thế được `ON` không?

Có thể gặp:

```hql
select o
from PurchaseOrder o
left join o.customer c
where c.status = :status or c is null
```

Cách này giữ order không có customer, nhưng **không giữ order có customer nhưng customer không active**. Trong khi `ON c.status = :status` sẽ coi customer không active như không có target phù hợp và vẫn giữ order.

Do đó `OR c IS NULL` chỉ đúng nếu business semantics là “customer active hoặc hoàn toàn không có customer”, không phải “giữ order dù customer không phù hợp”.

## 7. `ON` trong association join bổ sung điều kiện cho quan hệ đã map

Với association:

```hql
from PurchaseOrder o
left join o.customer c on c.status = :status
```

Hibernate đã biết điều kiện nối cơ bản từ mapping:

```sql
c.id = o.customer_id
```

Điều kiện `ON` thêm vào điều kiện association, về ý nghĩa:

```sql
LEFT JOIN customers c
  ON c.id = o.customer_id
 AND c.status = ?
```

Nó không thay thế FK mapping bằng điều kiện status. Hãy dùng `ON` để bổ sung tiêu chí join.

### 7.1. `ON` khác `WHERE`

- `ON`: quyết định hàng nào ở phía phải được xem là match trong phép join.
- `WHERE`: quyết định hàng kết quả cuối cùng nào được giữ.

Với inner join, chuyển predicate giữa ON và WHERE thường có kết quả tương đương trong nhiều trường hợp đơn giản. Với left join, chuyển điều kiện từ ON sang WHERE có thể làm thay đổi kết quả vì null-extension.

### 7.2. Hibernate `with` và `on`

Hibernate HQL lịch sử hỗ trợ `with` để thêm điều kiện vào association join:

```hql
select o
from PurchaseOrder o
left join o.customer c with c.status = :status
```

Trong HQL hiện đại có thể dùng `on`:

```hql
select o
from PurchaseOrder o
left join o.customer c on c.status = :status
```

`with` là cú pháp Hibernate-specific; `on` phù hợp hơn khi muốn cú pháp tương thích với JPQL hiện đại. Kiểm tra phiên bản provider nếu dự án còn dùng HQL/JPQL cũ.

## 8. Nhiều association tùy chọn trong cùng query

Giả sử order có customer và sales representative, cả hai đều tùy chọn:

```java
@ManyToOne(fetch = FetchType.LAZY, optional = true)
@JoinColumn(name = "customer_id")
private Customer customer;

@ManyToOne(fetch = FetchType.LAZY, optional = true)
@JoinColumn(name = "sales_rep_id")
private Employee salesRepresentative;
```

Nếu muốn lấy mọi order cùng hai thông tin có thể vắng mặt:

```hql
select o, c, r
from PurchaseOrder o
left join o.customer c
left join o.salesRepresentative r
order by o.id
```

Không viết:

```hql
select o
from PurchaseOrder o
where o.customer.name like :customerPattern
  and o.salesRepresentative.fullName like :repPattern
```

rồi mong order thiếu một trong hai quan hệ vẫn xuất hiện. Các path navigation tạo implicit inner joins và có thể loại order.

### 8.1. Một left join không cứu được implicit inner join khác

Ví dụ:

```hql
select o
from PurchaseOrder o
left join o.customer c
where o.salesRepresentative.fullName = :repName
```

Dù customer dùng left join, đường dẫn `o.salesRepresentative.fullName` là implicit association join riêng, có semantics inner. Order không có representative vẫn bị loại.

Khi muốn giữ cả hai association tùy chọn:

```hql
select o, c, r
from PurchaseOrder o
left join o.customer c
left join o.salesRepresentative r
```

Nếu cần lọc một phía mà vẫn giữ order, đặt predicate phù hợp trong `ON` của join đó.

## 9. Join tường minh cho path lồng nhau

Giả sử:

```text
PurchaseOrder
    customer → Customer
                   address → Address
                                  city
```

Implicit:

```hql
select o
from PurchaseOrder o
where o.customer.address.city = :city
```

có thể loại order nếu customer hoặc address null.

Explicit left joins:

```hql
select o, c, a
from PurchaseOrder o
left join o.customer c
left join c.address a
```

Nếu chỉ muốn order có địa chỉ thuộc thành phố:

```hql
select o
from PurchaseOrder o
left join o.customer c
left join c.address a
where a.city = :city
```

Query này vẫn loại order không có address, vì predicate WHERE yêu cầu city phù hợp.

Nếu muốn giữ mọi order và chỉ lấy address khi city khớp:

```hql
select o, c, a
from PurchaseOrder o
left join o.customer c
left join c.address a on a.city = :city
```

Khi association lồng nhau đều optional, hãy quyết định riêng từng join là INNER hay LEFT. Đừng để một path implicit ở cuối vô tình biến toàn bộ ý định giữ root thành lọc mất hàng.

## 10. Join với collection: một root có thể tạo nhiều result rows

Giả sử order có nhiều dòng hàng:

```java
@OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
private List<OrderLine> lines;
```

Join:

```hql
select o, line
from PurchaseOrder o
join o.lines line
```

Nếu một order có ba lines, SQL result có ba rows cho cùng order:

```text
PO-010 | Line-1
PO-010 | Line-2
PO-010 | Line-3
```

Đây là semantics bình thường của one-to-many join.

### 10.1. Inner join collection loại parent có collection rỗng

```hql
select o
from PurchaseOrder o
join o.lines line
```

Order không có line không xuất hiện.

Nếu muốn giữ order không có line:

```hql
select o, line
from PurchaseOrder o
left join o.lines line
```

Các order không có line vẫn xuất hiện với `line = null`.

### 10.2. `distinct` khi chỉ cần root entity

```hql
select distinct o
from PurchaseOrder o
join o.lines line
where line.sku = :sku
```

`distinct` thể hiện rằng ứng dụng muốn kết quả root entity không lặp theo semantics của query. Với collection join, hãy hiểu rằng SQL vẫn có thể trả nhiều rows trước khi Hibernate assemble entity result.

Nếu chỉ cần order có ít nhất một line thỏa điều kiện, có thể cân nhắc `exists`:

```hql
select o
from PurchaseOrder o
where exists (
    select line.id
    from OrderLine line
    where line.order = o
      and line.sku = :sku
)
```

`exists` biểu đạt điều kiện tồn tại mà không nhất thiết nhân bản root rows do join.

## 11. Explicit join không đồng nghĩa fetch association

Một điểm quan trọng: **join để lọc/truy vấn** và **join để tải association** là hai ý định khác nhau.

```hql
select o
from PurchaseOrder o
join o.customer c
where c.status = :status
```

Query dùng customer để lọc order. Nó không mặc nhiên yêu cầu Hibernate đánh dấu `o.customer` là association đã được fetch đầy đủ trong mọi trường hợp.

Nếu mục tiêu là tải customer cùng order:

```hql
select o
from PurchaseOrder o
join fetch o.customer
where o.customer.status = :status
```

Hoặc nếu cần giữ order không có customer:

```hql
select o
from PurchaseOrder o
left join fetch o.customer
```

`fetch` là chỉ thị fetch plan trong HQL/JPQL. Không nhầm `join` thông thường với `join fetch`.

### 11.1. `LEFT JOIN FETCH` cho association tùy chọn

Nếu mapping `customer` là optional và muốn tải order kể cả khi customer null:

```hql
select o
from PurchaseOrder o
left join fetch o.customer
```

Order không có customer vẫn được trả; field `customer` của entity tương ứng là null.

Ngược lại:

```hql
select o
from PurchaseOrder o
join fetch o.customer
```

là inner fetch join và loại order không có customer.

### 11.2. Fetch join không tải toàn bộ graph

```hql
select o
from PurchaseOrder o
left join fetch o.customer
```

chỉ yêu cầu fetch association `customer`. Nếu `Customer.address` hoặc `Customer.orders` vẫn lazy, chúng không tự động được khởi tạo chỉ vì customer đã fetch.

Có thể cần fetch join lồng nhau hoặc entity graph phù hợp, nhưng không fetch quá nhiều association tùy tiện.

### 11.3. Fetch join collection và pagination

Fetch join collection có thể nhân số SQL rows và gây vấn đề với pagination:

```hql
select distinct o
from PurchaseOrder o
left join fetch o.lines
```

Nếu kết hợp `setFirstResult()`/`setMaxResults()` trên query fetch collection, provider có thể phải xử lý phân trang ở bộ nhớ hoặc cảnh báo tùy phiên bản/cấu hình. Với danh sách phân trang, thường cân nhắc:

1. Query page các order IDs.
2. Query fetch association cho tập IDs đó.
3. Dùng batch fetching cho collection lazy.
4. Dùng DTO projection nếu chỉ cần một số field.

Không dùng fetch join collection lớn như giải pháp mặc định cho mọi N+1.

## 12. Điều kiện lọc trong ON cho collection

Ví dụ muốn giữ mọi order, nhưng chỉ nối các line có SKU bắt đầu bằng `A`:

```hql
select o, line
from PurchaseOrder o
left join o.lines line on line.sku like :pattern
```

Nếu một order không có line phù hợp, nó vẫn xuất hiện với `line = null`.

Nếu viết:

```hql
select o, line
from PurchaseOrder o
left join o.lines line
where line.sku like :pattern
```

order không có line phù hợp bị loại.

Đây cũng là khác biệt giữa lọc tập child được nối và lọc toàn bộ result rows.

### 12.1. Không nhầm ON filter với thay đổi collection trong bộ nhớ

Join có điều kiện chỉ ảnh hưởng **kết quả query**. Nó không có nghĩa Hibernate đã xóa những collection element không thỏa điều kiện khỏi persistent collection `o.lines`.

Nếu query fetch một collection với điều kiện lọc, cần đặc biệt cẩn trọng: object graph có thể không đại diện đầy đủ collection trong database. Không dùng một collection đã fetch một phần như nguồn để merge/update toàn bộ aggregate nếu không có thiết kế rõ ràng.

## 13. Join tới entity không có association được map

Association join thông thường dựa trên đường dẫn mapping:

```hql
from PurchaseOrder o
join o.customer c
```

Trong HQL hiện đại, Hibernate còn hỗ trợ một số dạng **entity join** để nối hai entity không có association trực tiếp, bằng điều kiện `ON`:

```hql
select o, c
from PurchaseOrder o
left join Customer c on c.name = o.customerName
```

Ví dụ này giả định `PurchaseOrder` có scalar `customerName`, còn `Customer` có `name`. Đây không phải association path `o.customer`; join được viết trực tiếp giữa entity roots.

Entity join hữu ích khi:

- Schema legacy không có association mapping.
- Cần nối theo điều kiện business key.
- Query báo cáo cần liên kết hai entity độc lập.

Tuy nhiên, khả năng và cú pháp entity join phụ thuộc phiên bản HQL/provider và không nên mặc định portable sang mọi JPQL version. Nếu có thể, association mapping đúng domain thường dễ bảo trì hơn.

### 13.1. Cross join và điều kiện WHERE

Một dạng cũ:

```hql
select o, c
from PurchaseOrder o, Customer c
where c.name = o.customerName
```

có thể được hiểu là tạo tích Descartes rồi lọc theo điều kiện. Explicit entity join diễn đạt ý định join rõ hơn:

```hql
select o, c
from PurchaseOrder o
join Customer c on c.name = o.customerName
```

Hãy tránh vô tình tạo Cartesian product lớn khi thiếu predicate nối.

## 14. So sánh `INNER JOIN`, `LEFT JOIN` và `CROSS JOIN`

| Loại join | Kết quả khi không có target phù hợp | Cú pháp HQL điển hình |
| --- | --- | --- |
| INNER JOIN | Loại hàng phía trái không có match | `join o.customer c` |
| LEFT OUTER JOIN | Giữ hàng phía trái, phía phải là null | `left join o.customer c` |
| CROSS JOIN | Kết hợp mọi cặp hàng của hai nguồn | `from PurchaseOrder o, Customer c` |
| RIGHT/FULL JOIN | Không phải lựa chọn association join phổ biến; hỗ trợ tùy query/provider | Cần kiểm tra HQL/dialect/version |

Trong truy vấn nghiệp vụ thông thường:

- Dùng INNER khi chỉ quan tâm root có association phù hợp.
- Dùng LEFT khi root vẫn có ý nghĩa dù association không tồn tại/không phù hợp.
- Dùng CROSS/entity join khi thật sự cần nối nguồn không có mapping, luôn cung cấp điều kiện phù hợp để tránh tích Descartes ngoài ý muốn.

## 15. Join và null semantics

SQL sử dụng logic ba giá trị: TRUE, FALSE, UNKNOWN. So sánh với `NULL` thường cho UNKNOWN, không phải TRUE/FALSE.

Ví dụ:

```sql
NULL = 'ACTIVE'       -- UNKNOWN
NULL <> 'ACTIVE'      -- UNKNOWN
NULL IS NULL          -- TRUE
```

Vì vậy:

```hql
left join o.customer c
where c.status <> 'INACTIVE'
```

không giữ order không có customer. Với `c.status = NULL`, phép `<>` cũng cho UNKNOWN và hàng bị loại.

Nếu muốn giữ customer null hoặc customer không inactive:

```hql
left join o.customer c
where c.status <> 'INACTIVE' or c is null
```

Nếu muốn giữ mọi order và chỉ nối customer không inactive:

```hql
left join o.customer c on c.status <> 'INACTIVE'
```

Hai câu vẫn có semantics khác nhau với customer inactive: câu WHERE loại order; câu ON giữ order với `c = null`.

### 15.1. `IS NULL` trên association và trên thuộc tính khác nhau

Có thể kiểm tra order không có customer:

```hql
select o
from PurchaseOrder o
where o.customer is null
```

Đây là điều kiện về association/foreign key và không cần đọc thuộc tính `Customer.name`.

Kiểm tra customer có tồn tại nhưng name null:

```hql
select o
from PurchaseOrder o
join o.customer c
where c.name is null
```

Đây là điều kiện khác: cần một customer row match nhưng `name` null (nếu schema cho phép).

Phân biệt null của **association** với null của **cột ở entity đích** để tránh truy vấn sai ý định.

## 16. Nhiều join cùng entity type

Một order có thể có customer và người tạo order đều là `Customer`:

```java
@ManyToOne(fetch = FetchType.LAZY)
private Customer customer;

@ManyToOne(fetch = FetchType.LAZY)
private Customer createdBy;
```

Dùng alias riêng:

```hql
select o, buyer, creator
from PurchaseOrder o
left join o.customer buyer
left join o.createdBy creator
```

Không dùng chung một alias cho hai association khác nhau. Nếu cần điều kiện:

```hql
select o
from PurchaseOrder o
left join o.customer buyer on buyer.status = 'ACTIVE'
left join o.createdBy creator on creator.status = 'ENABLED'
```

Mỗi join có semantics và điều kiện riêng. Một association optional không làm ảnh hưởng tự động join còn lại.

## 17. Join path và alias trong SELECT, WHERE, ORDER BY

Explicit join cho phép dùng alias ở mọi phần query hợp lệ:

```hql
select o.orderNumber, c.name
from PurchaseOrder o
left join o.customer c
where o.createdAt >= :fromDate
order by c.name nulls last
```

`nulls first`/`nulls last` là cú pháp HQL được hỗ trợ ở các phiên bản hiện đại; khả năng dịch xuống SQL phụ thuộc dialect. Nếu query cần portable JPQL cũ hơn, kiểm tra cú pháp theo chuẩn đang dùng.

Khi sắp xếp theo cột của association optional, order không có customer có giá trị sort null. Hãy xác định vị trí null mong muốn thay vì phụ thuộc thứ tự mặc định của database.

## 18. `count()` và left join

Ví dụ muốn đếm số order và số order có customer:

```hql
select count(o), count(c.id)
from PurchaseOrder o
left join o.customer c
```

- `count(o)` đếm các root rows trong kết quả join.
- `count(c.id)` chỉ đếm các customer match vì `count(expression)` bỏ qua null.

Với association to-one, mỗi order thường tạo tối đa một row, nên ví dụ trên dễ hiểu.

Với collection to-many:

```hql
select count(o)
from PurchaseOrder o
left join o.lines line
```

một order có nhiều lines có thể tạo nhiều rows và làm count tăng. Nếu cần đếm root entity:

```hql
select count(distinct o.id)
from PurchaseOrder o
left join o.lines line
```

Nếu chỉ cần số order có ít nhất một line phù hợp, `count(distinct ...)` hoặc `exists` có thể biểu đạt chính xác hơn.

## 19. `LEFT JOIN` không có nghĩa dữ liệu phía phải luôn được tải đầy đủ

Một explicit join thường phục vụ việc lọc/chọn kết quả. Nếu query:

```hql
select o
from PurchaseOrder o
left join o.customer c
where c.status = :status
```

thì Hibernate dùng customer trong SQL để lọc. Nhưng không nên suy rằng association `o.customer` chắc chắn đã được fetch như một association được khởi tạo đầy đủ trong persistence context.

Nếu cần tải association, viết fetch join hoặc fetch plan riêng:

```hql
select o
from PurchaseOrder o
left join fetch o.customer
```

Một entity đã có trong L1 cache có thể được tái sử dụng; SQL query vẫn có thể chạy để xác định kết quả. Fetch plan và identity resolution là các cơ chế riêng.

## 20. Kết hợp join với điều kiện lọc tùy chọn

Một ví dụ tổng hợp:

Yêu cầu: lấy mọi order trong khoảng ngày, đồng thời chỉ gắn customer nếu customer đang ACTIVE; nếu không có customer hoặc customer inactive, order vẫn phải xuất hiện.

```hql
select o, c
from PurchaseOrder o
left join o.customer c on c.status = :activeStatus
where o.createdAt >= :fromDate
  and o.createdAt < :toDate
order by o.createdAt desc
```

Với tham số:

```java
query.setParameter("activeStatus", "ACTIVE");
query.setParameter("fromDate", fromDate);
query.setParameter("toDate", toDate);
```

SQL khái niệm:

```sql
SELECT o.*, c.*
FROM purchase_orders o
LEFT JOIN customers c
  ON c.id = o.customer_id
 AND c.status = ?
WHERE o.created_at >= ?
  AND o.created_at < ?
ORDER BY o.created_at DESC;
```

Order không có customer vẫn xuất hiện. Order có customer inactive cũng xuất hiện, nhưng cột phía customer là null.

Nếu thay điều kiện:

```hql
where c.status = :activeStatus
```

thì chỉ còn order có customer active.

## 21. Khi nào implicit join phù hợp?

Implicit join có ưu điểm ngắn gọn cho predicate đơn giản:

```hql
select e
from Employee e
where e.department.name = :departmentName
```

Phù hợp khi:

- Business requirement chỉ cần entity có association match.
- INNER semantics đúng ý định.
- Chỉ dùng một path đơn giản.
- Không cần alias riêng hoặc điều kiện ON.
- Không cần giữ root entity có association null.

Ví dụ:

```hql
select p
from Product p
where p.category.code = :categoryCode
```

Nếu product bắt buộc có category theo schema/domain, implicit inner join là dễ đọc.

Nhưng khi quan hệ optional, nhiều tầng association hoặc yêu cầu giữ root, explicit join thường làm ý định rõ ràng hơn.

## 22. Khi nào explicit join nên được ưu tiên?

Dùng explicit join khi:

- Muốn lựa chọn `INNER` hay `LEFT` rõ ràng.
- Cần giữ hàng gốc dù association null.
- Cần điều kiện `ON` để lọc phía phải mà không loại phía trái.
- Cần alias để tham chiếu association nhiều lần.
- Query nối nhiều association hoặc nhiều role cùng entity type.
- Cần `JOIN FETCH`.
- Muốn kiểm soát việc join collection và xử lý duplicate roots.

Ví dụ:

```hql
select distinct o
from PurchaseOrder o
left join o.customer c
left join o.lines line on line.quantity > 0
where o.createdAt >= :fromDate
```

Câu query thể hiện rõ hai quan hệ, loại join và điều kiện gắn với collection. Hãy thêm `distinct`/aggregate phù hợp nếu to-many join làm nhân bản root rows.

## 23. Criteria API biểu đạt cùng ý định

Nếu ứng dụng xây query động bằng Criteria API, join type được chỉ định tường minh:

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<PurchaseOrder> cq =
    cb.createQuery(PurchaseOrder.class);

Root<PurchaseOrder> order = cq.from(PurchaseOrder.class);

Join<PurchaseOrder, Customer> customer =
    order.join("customer", JoinType.LEFT);

cq.select(order)
  .where(cb.equal(customer.get("status"), "ACTIVE"));
```

`JoinType.LEFT` thể hiện left join. Nhưng predicate ở `where` vẫn loại hàng có customer null. Criteria API không thay đổi SQL null semantics.

Để đặt điều kiện ở ON:

```java
customer.on(cb.equal(customer.get("status"), "ACTIVE"));
```

Sau đó không thêm predicate tương tự vào `where` nếu muốn giữ order không có customer phù hợp.

Criteria API và HQL có thể tạo cùng kiểu SQL semantics; chọn theo nhu cầu query tĩnh hay động.

## 24. Kiểm thử tác động của optional association

Một integration test nên seed tối thiểu:

```text
Order#10 → Customer#1 (ACTIVE)
Order#11 → NULL
Order#12 → Customer#2 (INACTIVE)
```

### 24.1. Implicit path loại order không có customer

```java
List<PurchaseOrder> result = em.createQuery("""
    select o
    from PurchaseOrder o
    where o.customer.name = :name
    """, PurchaseOrder.class)
    .setParameter("name", "An")
    .getResultList();
```

Kỳ vọng: order có customer match được trả. Order có `customer_id = NULL` không thỏa path join.

### 24.2. Explicit inner join loại association null

```java
List<PurchaseOrder> result = em.createQuery("""
    select o
    from PurchaseOrder o
    join o.customer c
    """, PurchaseOrder.class)
    .getResultList();
```

Kỳ vọng: PO-010 và PO-012; không có PO-011/PO-013.

### 24.3. Explicit left join giữ tất cả root

```java
List<Object[]> result = em.createQuery("""
    select o, c
    from PurchaseOrder o
    left join o.customer c
    order by o.id
    """, Object[].class)
    .getResultList();
```

Kỳ vọng: có bốn order; tuple customer của PO-011/PO-013 là null.

### 24.4. Left join với WHERE vẫn loại null

```hql
select o
from PurchaseOrder o
left join o.customer c
where c.status = 'ACTIVE'
```

Kỳ vọng: chỉ PO-010. PO-011/PO-013 bị loại bởi WHERE; PO-012 bị loại do status inactive.

### 24.5. Left join với ON giữ root

```hql
select o, c
from PurchaseOrder o
left join o.customer c on c.status = 'ACTIVE'
order by o.id
```

Kỳ vọng: bốn order vẫn xuất hiện. PO-010 có customer An; các order khác có customer alias null do không match điều kiện ON.

### 24.6. Đừng chỉ kiểm tra số lượng

Khi test join, hãy kiểm tra **ID cụ thể** và giá trị alias null/non-null. Số lượng có thể vô tình bằng nhau trong dữ liệu khác và không chứng minh đúng semantics.

Ví dụ:

```java
assertEquals(
    List.of(10L, 11L, 12L, 13L),
    result.stream()
        .map(row -> ((PurchaseOrder) row[0]).getId())
        .toList()
);
```

Đây là minh họa; nếu database không bảo đảm thứ tự, phải có `order by` như query ở trên.

## 25. Quan sát SQL Hibernate sinh ra

Trong development/test, bật SQL logging:

```properties
hibernate.show_sql=true
hibernate.format_sql=true
```

Hoặc với Spring Boot:

```properties
logging.level.org.hibernate.SQL=DEBUG
```

Nếu cần quan sát bind parameters, dùng logger phù hợp với Hibernate version nhưng không bật giá trị nhạy cảm ở production.

Hãy so sánh các query:

```hql
-- Implicit inner join
select o
from PurchaseOrder o
where o.customer.name = :name
```

```hql
-- Explicit inner join
select o
from PurchaseOrder o
join o.customer c
where c.name = :name
```

```hql
-- Explicit left join
select o
from PurchaseOrder o
left join o.customer c
```

SQL có thể khác alias/column list/dialect, nhưng semantics dự kiến:

- Query đầu và thứ hai loại order không có customer.
- Query thứ ba giữ mọi order.
- Thêm predicate `where c.name = ...` vào query thứ ba có thể lại loại hàng null.
- Chuyển predicate đó vào `on` giữ order không có customer.

Đừng yêu cầu SQL text giống hệt một snippet; hãy kiểm tra join type, điều kiện và tập kết quả.

## 26. Các lỗi truy vấn thường gặp

| Triệu chứng | Nguyên nhân có thể | Cách sửa |
| --- | --- | --- |
| Order không có customer biến mất | Implicit path join hoặc explicit inner join | Dùng `left join` |
| Đã dùng LEFT JOIN nhưng vẫn mất order null | Predicate alias phía phải nằm trong WHERE | Chuyển điều kiện phù hợp sang ON |
| Customer inactive khiến order biến mất dù muốn giữ | Điều kiện status ở WHERE | Đặt status filter vào ON |
| Query nhiều path optional loại nhiều root | Các implicit joins lồng nhau đều inner | Khai báo từng `left join` |
| Collection join làm root lặp | Một root có nhiều child rows | Dùng `distinct`, aggregate hoặc `exists` |
| Query có nhiều join trùng | Điều hướng path lặp và join explicit chồng nhau | Dùng alias thống nhất; xem SQL thực tế |
| `join` không làm association được load | Join thường dùng cho query semantics, không phải fetch | Dùng `join fetch` hoặc fetch plan |
| `left join fetch` vẫn có collection lazy khác | Chỉ association được fetch được tải | Bổ sung fetch plan cần thiết |
| Pagination trả kết quả bất ngờ với fetch collection | SQL rows bị nhân theo collection | Tách query IDs/page và fetch association riêng |
| Mapping optional nhưng query vẫn mất null | Optionality không thay đổi implicit join semantics | Viết LEFT JOIN rõ ràng |
| `optional=false` nhưng dữ liệu có FK null | Mapping/schema/data không nhất quán | Sửa dữ liệu/schema và mapping |
| Dùng `OR c IS NULL` nhưng customer inactive vẫn mất | Customer tồn tại nên c không null trước WHERE | Dùng ON nếu muốn coi không match như null phía phải |

## 27. Những hiểu lầm cần tránh

**“Association `optional=true` thì implicit join tự là LEFT JOIN.”** Sai. Điều hướng association path trong HQL tạo implicit inner join semantics.

**“Dùng `left join` là mọi hàng gốc chắc chắn được giữ.”** Sai nếu WHERE có predicate loại các hàng mà alias phía phải là null.

**“`ON` và `WHERE` chỉ khác vị trí viết.”** Sai. Với outer join, ON lọc hàng phía phải trước khi hoàn tất phép nối; WHERE lọc kết quả sau join.

**“Join thường sẽ initialize association.”** Không. Dùng `join fetch` hoặc fetch plan khi cần tải association.

**“`getCustomer()` luôn là SELECT mới.”** Không. Lazy proxy, L1 cache, fetch plan và trạng thái initialized ảnh hưởng SQL.

**“Một left join đầu tiên làm mọi path tiếp theo thành left join.”** Không. Path implicit khác vẫn có inner semantics; khai báo từng left join cần thiết.

**“`distinct` luôn làm SQL chỉ còn một row cho mỗi root.”** Không nhất thiết. SQL row multiplicity và Hibernate entity result assembly là hai tầng khác nhau.

**“Dùng `LEFT JOIN ... WHERE c.status = ...` tương đương lọc customer ở ON.”** Sai. WHERE loại hàng null; ON giữ hàng gốc không có match.

**“`JOIN FETCH` là cách duy nhất tránh N+1.”** Không. Entity Graph, batch fetching, subselect và DTO projection cũng là lựa chọn.

## 28. Quy trình chọn join cho một truy vấn HQL

Trước khi viết query, xác định:

**Bước 1 — Entity gốc nào phải luôn xuất hiện?** Nếu root vẫn cần có mặt khi association null, đó là tín hiệu dùng LEFT JOIN.

**Bước 2 — Association có thể vắng mặt không?** Kiểm tra mapping, schema FK, dữ liệu thực tế và business lifecycle. Đừng chỉ nhìn `optional=true`.

**Bước 3 — Query cần lọc root theo association hay chỉ lấy association nếu phù hợp?** Nếu muốn root chỉ xuất hiện khi target match, INNER JOIN/implicit path có thể đúng. Nếu muốn giữ root, LEFT JOIN.

**Bước 4 — Điều kiện thuộc ON hay WHERE?** Predicate trong ON lọc target match; predicate trong WHERE lọc kết quả cuối cùng.

**Bước 5 — Path có nhiều tầng optional không?** Khai báo LEFT JOIN cho từng association cần giữ null.

**Bước 6 — Association cần được tải hay chỉ dùng để lọc?** Dùng JOIN FETCH/Entity Graph nếu cần fetch; join thường không phải fetch instruction.

**Bước 7 — Có to-many join không?** Kiểm tra duplicate roots, pagination, `distinct`, `exists` và số rows.

**Bước 8 — Kiểm tra SQL và dữ liệu biên.** Seed association có giá trị, null, target không thỏa ON, collection rỗng và nhiều child.

**Bước 9 — Kiểm tra trên Hibernate/DBMS thực tế.** SQL shape và tối ưu hóa có thể thay đổi theo version/dialect; semantics kết quả mới là hợp đồng cần giữ.

## 29. Bài tập tình huống

### Bài 1 — Mapping optional

`PurchaseOrder.customer` có `optional=true`. Query `where o.customer.name = :name` có giữ order không có customer không?

**Đáp án:** Không. Path navigation tạo implicit inner join semantics. Optionality không tự đổi nó thành LEFT JOIN.

### Bài 2 — Explicit inner join

```hql
from PurchaseOrder o join o.customer c
```

Order có `customer_id=NULL` có xuất hiện không?

**Đáp án:** Không. Inner join cần hàng customer match.

### Bài 3 — Explicit left join

```hql
from PurchaseOrder o left join o.customer c
```

Order không có customer có xuất hiện không?

**Đáp án:** Có. Phía customer của kết quả là null.

### Bài 4 — WHERE null rejection

```hql
from PurchaseOrder o
left join o.customer c
where c.status = 'ACTIVE'
```

Order không có customer có xuất hiện không?

**Đáp án:** Không. `NULL = 'ACTIVE'` là UNKNOWN, bị WHERE loại.

### Bài 5 — ON filter

```hql
from PurchaseOrder o
left join o.customer c on c.status = 'ACTIVE'
```

Order có customer inactive có xuất hiện không?

**Đáp án:** Có, nhưng alias `c` không match và được trả về null trong kết quả join.

### Bài 6 — Hai association optional

Order có customer nhưng không có sales rep. Query left join customer và implicit path `o.salesRepresentative.name` có giữ order không?

**Đáp án:** Không chắc; implicit join của salesRepresentative là inner và loại hàng không có representative. Muốn giữ root, khai báo left join cho cả hai.

### Bài 7 — Path lồng nhau

`o.customer.address.city` có thể loại order khi association nào null?

**Đáp án:** Cả customer và address đều là optional path joins với inner semantics; thiếu một trong hai có thể làm order không xuất hiện.

### Bài 8 — Collection join

Order có ba lines. `select o, line from Order o join o.lines line` trả bao nhiêu rows cho order đó?

**Đáp án:** Ba rows, mỗi line một row. Nếu chỉ cần root duy nhất, cân nhắc distinct/exists.

### Bài 9 — Join thường hay fetch join?

Query join customer để lọc nhưng sau đó code truy cập `o.getCustomer()` trong session. Có thể association vẫn lazy không?

**Đáp án:** Có. Join thường không phải fetch directive; dùng `join fetch`/entity graph nếu muốn yêu cầu tải association.

### Bài 10 — Left join fetch

`left join fetch o.customer` khác `join fetch o.customer` thế nào?

**Đáp án:** Left fetch join giữ order không có customer; inner fetch join loại chúng.

### Bài 11 — Đếm collection

Một order có bốn lines. `count(o)` sau join collection có thể đóng góp bao nhiêu?

**Đáp án:** Có thể bốn rows cho order đó. Dùng `count(distinct o.id)` nếu cần đếm root entities.

### Bài 12 — Điều kiện status

Muốn giữ order không customer và order có customer ACTIVE, nhưng bỏ order có customer INACTIVE. Viết join thế nào?

**Đáp án:**

```hql
select o, c
from PurchaseOrder o
left join o.customer c on c.status = 'ACTIVE'
```

Kết quả giữ mọi order; customer inactive được biểu diễn như không có target match.

## Kết luận

**Join tường minh cho phép chọn rõ `INNER JOIN` hay `LEFT JOIN`, còn implicit association joins trong HQL có semantics inner join.** Vì vậy, một path như `o.customer.name` có thể loại order không có customer, dù mapping khai báo `optional=true`. Optionality mô tả quan hệ có được phép vắng mặt hay không; nó không quyết định loại join mà query cần.

Khi cần giữ entity gốc dù association null, hãy dùng `LEFT JOIN` rõ ràng cho từng path optional. Nếu lọc association mà vẫn muốn giữ root không có target phù hợp, đặt điều kiện vào `ON`; điều kiện trong `WHERE` có thể loại hàng null sau outer join. Cuối cùng, phân biệt join thường với fetch join, chú ý duplicate rows khi nối collection, và xác nhận semantics bằng integration test cùng SQL logging trên đúng Hibernate version/DBMS.
