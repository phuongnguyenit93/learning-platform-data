# Tính bất biến của định danh sau khi đối tượng được quản lý

Trong JPA/Hibernate, mỗi entity có **định danh (identifier)** để phân biệt bản ghi mà nó đại diện. Một khi entity đã được Hibernate quản lý trong **persistence context**, định danh đó phải được xem là **bất biến**: ứng dụng không được đổi khóa chính của cùng một entity từ giá trị này sang giá trị khác.

Quy tắc này không chỉ nhằm giữ dữ liệu trong bảng SQL nhất quán. Hibernate còn dùng định danh để nhận biết đối tượng trong bộ nhớ, quản lý cache cấp một, theo dõi thay đổi, liên kết quan hệ và quyết định cần cập nhật hàng nào khi flush. Nếu thay đổi `@Id` tùy ý, ta làm sai lệch mối liên hệ giữa đối tượng Java và hàng cơ sở dữ liệu.

Bài học nằm trong chủ đề **Định danh** của module *Data Persistence Relational Access ORM Hibernate*. Các ví dụ dùng Jakarta Persistence (`jakarta.persistence.*`) và Hibernate; phần SQL sử dụng cú pháp PostgreSQL khi cần minh họa. Khái niệm áp dụng rộng rãi cho các hệ quản trị cơ sở dữ liệu quan hệ.

## 1. Định danh là gì trong mô hình entity?

Giả sử bảng sản phẩm:

~~~sql
CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(32) NOT NULL UNIQUE,
    name VARCHAR(160) NOT NULL,
    price NUMERIC(15, 2) NOT NULL CHECK (price >= 0)
);
~~~

Một trạng thái dữ liệu:

| `id` (PK) | `sku` | `name` | `price` |
| ---: | --- | --- | ---: |
| 101 | SP-001 | Bàn phím | 350000.00 |
| 102 | SP-002 | Chuột | 180000.00 |

Ở đây:

- **`id`** là khóa chính (**primary key**, PK) xác định duy nhất một hàng.
- **`sku`** là mã nghiệp vụ, cũng có ràng buộc `UNIQUE` nhưng **không phải khóa chính của entity** trong mô hình ví dụ.
- **`name`, `price`** là dữ liệu nghiệp vụ có thể thay đổi mà không cần biến sản phẩm thành một bản ghi khác.

Ở phía Java:

~~~java
package com.example.catalog.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.math.BigDecimal;
import java.util.Objects;

@Entity
@Table(name = "products")
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "sku", nullable = false, unique = true, length = 32)
    private String sku;

    @Column(name = "name", nullable = false, length = 160)
    private String name;

    @Column(name = "price", nullable = false, precision = 15, scale = 2)
    private BigDecimal price;

    protected Product() {
        // Dành cho JPA/Hibernate.
    }

    public Product(String sku, String name, BigDecimal price) {
        this.sku = Objects.requireNonNull(sku);
        this.name = Objects.requireNonNull(name);
        this.price = Objects.requireNonNull(price);
    }

    public Long getId() {
        return id;
    }

    public String getSku() {
        return sku;
    }

    public void changeSku(String sku) {
        this.sku = Objects.requireNonNull(sku);
    }

    public void rename(String name) {
        this.name = Objects.requireNonNull(name);
    }

    public void changePrice(BigDecimal price) {
        this.price = Objects.requireNonNull(price);
    }
}
~~~

Thiết kế này **không cung cấp `setId(...)`** cho mã nghiệp vụ. Đó là cách diễn đạt ý định: khi một `Product` đã gắn với hàng `products.id = 101`, ứng dụng có thể sửa `sku`, `name` và `price`, nhưng không đổi nó thành hàng `products.id = 102`.

**Không nên nhầm “khóa chính” với “bất kỳ cột nào có giá trị duy nhất”.** Ràng buộc `UNIQUE` của `sku` giúp bảo vệ nghiệp vụ. Hibernate vẫn dùng `@Id` (ở đây là `id`) làm định danh entity.

## 2. Vì sao Hibernate cần định danh không thay đổi?

### 2.1. Persistence context dùng định danh như khóa tra cứu

`EntityManager` của JPA và `Session` của Hibernate có một **persistence context**, nơi lưu các entity đang được quản lý. Về mặt khái niệm, nó duy trì ánh xạ:

~~~text
(Entity type, primary-key value)  ──>  Managed Java object

(Product, 101)                    ──>  Product object A
(Product, 102)                    ──>  Product object B
~~~

Đây là cách mô tả khái niệm, không phải cấu trúc dữ liệu public API cụ thể của Hibernate.

Khi gọi:

~~~java
Product first = em.find(Product.class, 101L);
Product second = em.find(Product.class, 101L);

System.out.println(first == second); // true trong cùng persistence context
~~~

JPA bảo đảm **tính đồng nhất của managed entity trong cùng persistence context**: với cùng kiểu entity và cùng định danh, ứng dụng làm việc với cùng một instance managed. Hibernate có thể phục vụ lần gọi sau từ context mà không cần chạy một `SELECT` mới.

Hãy tưởng tượng ứng dụng sửa trực tiếp `first.id` từ `101` thành `102` sau khi object đã được quản lý:

~~~text
Bản ghi context lúc nạp:
  (Product, 101) ──> Product object A { id = 101 }

Ứng dụng thay field id trái quy tắc:
  (Product, 101) ──> Product object A { id = 102 }
                    ↑
          Khóa lưu trong context và giá trị trong object không còn khớp
~~~

Nếu tiếp tục tra cứu, flush hoặc quản lý quan hệ, Hibernate không còn một ánh xạ định danh đáng tin cậy. Vì vậy việc đổi khóa chính của **một entity đang persistent** là hành vi bị cấm theo quy ước Hibernate.

### 2.2. Hibernate dùng định danh để sinh SQL cập nhật hàng

Giả sử `Product` có `id = 101` và ứng dụng gọi:

~~~java
product.rename("Bàn phím cơ");
~~~

Khi flush, Hibernate có thể sinh SQL tương đương:

~~~sql
UPDATE products
SET name = 'Bàn phím cơ'
WHERE id = 101;
~~~

Điều kiện `WHERE id = 101` biểu thị hàng mà entity đang đại diện. Nếu ứng dụng thay `id` thành `102`, câu hỏi “sửa hàng cũ, sửa hàng mới, hay chuyển định danh?” trở nên mơ hồ và có nguy cơ thao tác nhầm bản ghi.

Hibernate **không thiết kế việc thay `@Id` trên managed entity như một cách thực hiện `UPDATE products SET id = ...`**. Theo quy định của Jakarta Persistence, hành vi thay giá trị khóa chính của entity sau khi nó đã persistent là **không được xác định**; Hibernate thường phát hiện thay đổi định danh trong quá trình flush và ném ngoại lệ.

### 2.3. Định danh là nền tảng của quan hệ và khóa ngoại

Xét bảng đơn hàng:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id BIGINT NOT NULL REFERENCES products(id),
    quantity INTEGER NOT NULL CHECK (quantity > 0)
);
~~~

Một đơn có `product_id = 101` tham chiếu sản phẩm `101`. Nếu ứng dụng tùy tiện đổi khóa chính của sản phẩm sang `102`, các FK có thể bị vi phạm, xung đột với hàng đã có hoặc yêu cầu cập nhật toàn bộ dữ liệu liên quan.

Ngay cả khi database có hỗ trợ `ON UPDATE CASCADE` cho khóa ngoại, cơ chế đó **không cập nhật đồng bộ khóa trong persistence context và cache của Hibernate**. Cascade ở database không biến thao tác thay ID trong entity thành hành vi an toàn của ORM.

## 3. “Bất biến” bắt đầu từ khi nào?

Cần phân biệt giá trị ID **chưa được gán**, **được gán lần đầu**, và **bị đổi sau khi entity đã có định danh**.

| Thời điểm | Trạng thái object | Đối với định danh |
| --- | --- | --- |
| Mới gọi `new Product(...)` | New/transient | Với ID sinh tự động, `id` có thể là `null` |
| Gọi `persist(product)` | Trở thành managed | Provider chuẩn bị hoặc thực hiện gán ID theo chiến lược sinh khóa |
| Provider cấp ID lần đầu | Managed | Được phép: đây là **khởi tạo định danh**, không phải ứng dụng đổi ID cũ |
| Sau khi entity đã có ID và đang managed | Managed | Ứng dụng **không được** sửa từ ID A sang ID B |
| Sau khi đóng context | Detached | Vẫn cần giữ nguyên identity của entity đã từng được lưu |
| Nạp lại entity ở context khác | Managed trong context mới | ID vẫn chỉ hàng dữ liệu tương ứng, không trở thành một giá trị được tự do thay |

### ID sinh tự động không mâu thuẫn với bất biến

Với:

~~~java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
~~~

một đối tượng mới thường bắt đầu với `id == null`. Khi persist, Hibernate có thể thực hiện `INSERT` sớm để nhận ID từ database. Với chiến lược `SEQUENCE`, provider có thể lấy ID trước khi phát lệnh `INSERT`; thời điểm chính xác phụ thuộc generator và cách flush.

Vì vậy không nên viết logic nghiệp vụ mặc định rằng:

~~~java
Product p = new Product("SP-003", "Màn hình", price);
assert p.getId() != null; // Không đúng cho new entity dùng generated ID
~~~

Sau khi provider đã cấp giá trị ID, mã ứng dụng phải coi nó là **định danh cố định** cho entity đó. Việc hệ thống cấp ID lần đầu khác căn bản với hành động của lập trình viên gọi `product.setId(999L)` sau khi entity đã managed.

### Nếu tự gán ID thì sao?

Với assigned identifier:

~~~java
@Entity
public class Warehouse {
    @Id
    private String code;

    private String name;

    protected Warehouse() {}

    public Warehouse(String code, String name) {
        this.code = Objects.requireNonNull(code);
        this.name = Objects.requireNonNull(name);
    }

    public String getCode() {
        return code;
    }

    public void rename(String newName) {
        this.name = Objects.requireNonNull(newName);
    }
}
~~~

Ứng dụng chủ động cấp `code` ngay khi tạo `Warehouse`, trước khi `persist`. Khi đã dùng `code` như entity ID, **đổi mã kho đồng nghĩa cố thay primary key** và không nên được thực hiện bằng cách sửa field trên managed entity.

Nếu mã kho có thể đổi theo nghiệp vụ, nên cân nhắc một khóa chính thay thế (ví dụ `Long id`) và để `code` là thuộc tính có ràng buộc duy nhất nhưng có thể cập nhật.

## 4. Thí nghiệm ý tưởng: lỗi khi sửa khóa của managed entity

Giả sử một `Product` đã tồn tại với ID `101`:

~~~java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Product product = em.find(Product.class, 101L);
    if (product == null) {
        throw new IllegalStateException("Sản phẩm 101 không tồn tại");
    }

    product.rename("Bàn phím cơ");

    tx.commit();
} catch (RuntimeException e) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw e;
} finally {
    em.close();
}
~~~

Đây là thao tác **hợp lệ**: chỉ `name` thay đổi, ID vẫn là `101`. Hibernate có thể phát `UPDATE` cho hàng có khóa `101`.

Ngược lại, hãy xem **đoạn sai cố ý sau; không đưa vào mã sản xuất**:

~~~java
// Ví dụ phản diện: giả sử entity có setter id không được khuyến nghị.
Product product = em.find(Product.class, 101L);
product.setId(102L); // Sai: thay định danh của managed entity.
em.flush();          // Hibernate có thể báo identifier altered.
~~~

Một thông báo Hibernate thường gặp có dạng:

~~~text
identifier of an instance of ... was altered from 101 to 102
~~~

Thông điệp chính xác, loại ngoại lệ và thời điểm phát hiện có thể khác nhau giữa phiên bản Hibernate, access strategy và đường thực thi. **Không nên dựa vào việc một lệnh setter có ném lỗi ngay hay không.** Có trường hợp lỗi xuất hiện muộn ở flush, auto-flush trước query hoặc commit. Bản thân yêu cầu là **không làm thay đổi ID**.

### Nếu transaction đã lỗi

Sau một lỗi persistence như thay ID, nên rollback transaction và kết thúc hoặc loại bỏ persistence context đang lỗi theo quy tắc quản lý tài nguyên của ứng dụng. Đừng tiếp tục dùng một `EntityManager` đã ở trạng thái không tin cậy rồi thử “đổi ID về như cũ” để cứu transaction.

Trạng thái các object Java có thể không tự quay lại như trước sau rollback. Khi cần làm việc tiếp, mở context mới và nạp lại entity từ database.

## 5. Entity ID và mã nghiệp vụ là hai vai trò khác nhau

Nhiều hệ thống ban đầu lấy một mã nghiệp vụ làm khóa chính, rồi sau này phát hiện mã đó có thể đổi. Ví dụ:

- Mã sản phẩm `SKU` có thể đổi khi đổi quy chuẩn catalog.
- Email có thể đổi khi người dùng thay địa chỉ liên hệ.
- Số điện thoại có thể bị thu hồi hoặc cập nhật.
- Mã nhân viên có thể đổi khi sáp nhập tổ chức.
- Số hợp đồng có thể được gán lại theo quy trình.

Nếu một giá trị **có khả năng thay đổi**, không nên vội dùng nó làm `@Id` chỉ vì nó đang có ràng buộc duy nhất.

### Khóa thay thế và khóa nghiệp vụ

| Tiêu chí | Khóa chính thay thế, ví dụ `Long id` | Khóa nghiệp vụ, ví dụ `sku` |
| --- | --- | --- |
| Mục đích | Định danh entity ổn định | Diễn đạt mã có ý nghĩa nghiệp vụ |
| Khả năng đổi | Không nên đổi sau khi entity persistent | Có thể đổi nếu quy tắc nghiệp vụ cho phép |
| Ràng buộc | `PRIMARY KEY` | Có thể `UNIQUE` và `NOT NULL` |
| Tham chiếu FK | Thường dùng làm đích FK | Có thể được truy vấn qua unique key |
| Rủi ro khi thay đổi | Rất cao, ảnh hưởng identity ORM | Có thể cập nhật như field thường nếu thiết kế cho phép |

Ví dụ phù hợp khi SKU có thể đổi:

~~~java
@Entity
@Table(name = "products")
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "sku", nullable = false, unique = true, length = 32)
    private String sku;

    protected Product() {}

    public Long getId() {
        return id;
    }

    public void changeSku(String newSku) {
        this.sku = Objects.requireNonNull(newSku);
    }
}
~~~

Khi mã `SP-001` đổi thành `SP-2026-001`, ID `101` vẫn giữ nguyên:

~~~sql
UPDATE products
SET sku = 'SP-2026-001'
WHERE id = 101;
~~~

Hàng `products.id = 101` và các đơn hàng tham chiếu nó vẫn đại diện cùng sản phẩm.

### `@NaturalId` trong Hibernate

Hibernate có annotation riêng `org.hibernate.annotations.NaturalId` để đánh dấu một khóa tự nhiên. Chẳng hạn:

~~~java
import org.hibernate.annotations.NaturalId;

@NaturalId(mutable = true)
@Column(name = "sku", nullable = false, unique = true)
private String sku;
~~~

`@NaturalId(mutable = true)` biểu thị **natural ID có thể thay đổi**, theo cách Hibernate hỗ trợ. Nó **không thay thế `@Id`** và không có nghĩa primary key của entity được phép thay đổi. Nếu dùng annotation này, cần hiểu cơ chế tra cứu và đồng bộ natural-id resolution/cache của Hibernate, đồng thời bảo đảm ràng buộc duy nhất thực sự tồn tại ở database.

Trong một ứng dụng cần giữ tính di động giữa nhiều JPA provider, chỉ dùng `@Column(unique = true)` hoặc mapping/schema tiêu chuẩn cho business key thường đơn giản hơn phụ thuộc annotation đặc thù Hibernate.

## 6. Bất biến của định danh không có nghĩa mọi field đều bất biến

Một đối tượng entity có thể đổi trạng thái nghiệp vụ qua thời gian:

~~~java
product.rename("Bàn phím không dây");
product.changePrice(new BigDecimal("420000.00"));
product.changeSku("SP-001-NEW");
~~~

Các thay đổi này được phép nếu quy tắc nghiệp vụ, ràng buộc schema và transaction cho phép. **ID vẫn giữ nguyên**.

Cũng không cần khai báo field ID với từ khóa Java `final`:

~~~java
@Id
@GeneratedValue
private final Long id = null; // Không phải mẫu phù hợp cho JPA entity.
~~~

`final` hạn chế khả năng provider gán ID và không đáp ứng mô hình field persistent thông thường của JPA. Cách phổ biến là để field `private`, không tạo public setter và để ORM gán giá trị lần đầu:

~~~java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

public Long getId() {
    return id;
}
~~~

Như vậy, **bất biến ở đây là bất biến về identity và hợp đồng sử dụng**, không phải bắt buộc biểu diễn bằng `final` trong mã Java.

## 7. Khóa ghép cũng phải giữ nguyên từng thành phần

Một entity đôi khi dùng khóa ghép gồm nhiều trường, ví dụ dòng đơn hàng có khóa:

~~~text
(order_id, line_number)
(5001, 1)
(5001, 2)
~~~

Hai thành phần `order_id` và `line_number` kết hợp định danh từng dòng. JPA hỗ trợ `@EmbeddedId` hoặc `@IdClass`.

Ví dụ sử dụng `@EmbeddedId`:

**`OrderLineId.java`:**

~~~java
package com.example.sales.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Embeddable;
import java.io.Serializable;
import java.util.Objects;

@Embeddable
public class OrderLineId implements Serializable {
    @Column(name = "order_id")
    private Long orderId;

    @Column(name = "line_number")
    private Integer lineNumber;

    protected OrderLineId() {
        // JPA sử dụng.
    }

    public OrderLineId(Long orderId, Integer lineNumber) {
        this.orderId = Objects.requireNonNull(orderId);
        this.lineNumber = Objects.requireNonNull(lineNumber);
    }

    public Long getOrderId() {
        return orderId;
    }

    public Integer getLineNumber() {
        return lineNumber;
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) {
            return true;
        }
        if (!(other instanceof OrderLineId that)) {
            return false;
        }
        return Objects.equals(orderId, that.orderId)
            && Objects.equals(lineNumber, that.lineNumber);
    }

    @Override
    public int hashCode() {
        return Objects.hash(orderId, lineNumber);
    }
}
~~~

**`OrderLine.java`:**

~~~java
package com.example.sales.domain;

import jakarta.persistence.Column;
import jakarta.persistence.EmbeddedId;
import jakarta.persistence.Entity;
import jakarta.persistence.Table;

@Entity
@Table(name = "order_lines")
public class OrderLine {
    @EmbeddedId
    private OrderLineId id;

    @Column(nullable = false)
    private int quantity;

    protected OrderLine() {
    }

    public OrderLine(OrderLineId id, int quantity) {
        this.id = id;
        this.quantity = quantity;
    }

    public OrderLineId getId() {
        return id;
    }

    public void changeQuantity(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("Số lượng phải dương");
        }
        this.quantity = quantity;
    }
}
~~~

SQL tương ứng:

~~~sql
CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, line_number)
);
~~~

Sau khi `OrderLine` được lưu, không được sửa `id.orderId` từ `5001` sang `5002`, sửa `id.lineNumber` từ `1` sang `3`, hoặc thay cả `OrderLineId` để “chuyển” dòng hiện có thành dòng khác. **Thay đổi một thành phần trong khóa ghép vẫn là thay đổi entity identity**.

Trong ví dụ, các field của `OrderLineId` được để non-final vì yêu cầu khởi tạo/ghi của JPA, nhưng lớp không cung cấp setter. Mã nghiệp vụ tạo object ID một lần và không sửa các thành phần sau khi dòng đơn được persist.

### Trường hợp `@MapsId` và khóa ngoại tham gia khóa chính

JPA hỗ trợ **derived identity**: khóa của một entity có thể phụ thuộc vào định danh entity liên quan. Ví dụ, `OrderLine` có quan hệ tới `Order` và FK `order_id` đồng thời tham gia `@EmbeddedId`, thông qua `@MapsId("orderId")` khi mapping được thiết kế phù hợp.

Trong trường hợp đó, **đổi đối tượng `Order` tham chiếu** có thể kéo theo ý nghĩa đổi một phần PK của `OrderLine`. Không nên chỉ gán relationship sang đơn khác rồi mong Hibernate tự chuyển khóa của managed entity. Nếu nghiệp vụ cần “chuyển dòng sang đơn khác”, hãy mô hình hóa như thao tác xóa/tạo hoặc thiết kế ID thay thế ngay từ đầu.

## 8. Định danh và `equals()`/`hashCode()`

Định danh ổn định quan trọng không chỉ với Hibernate mà còn với các collection Java.

Một kiểu triển khai `hashCode()` đơn giản dựa trên ID sinh tự động có thể gặp vấn đề:

~~~java
// Ví dụ nguy hiểm nếu hashCode thay đổi theo generated id.
@Override
public int hashCode() {
    return Objects.hashCode(id);
}
~~~

Giả sử:

~~~java
Product product = new Product("SP-003", "Màn hình", price);

Set<Product> set = new HashSet<>();
set.add(product); // id hiện có thể là null.

em.persist(product); // Hibernate cấp id = 103, tùy generator.

boolean found = set.contains(product); // Có thể false nếu hashCode đã đổi.
~~~

`HashSet` dùng hash lúc thêm phần tử để xác định vị trí lưu. Nếu hash thay đổi khi ID từ `null` trở thành `103`, việc tìm lại bằng cùng object có thể thất bại.

Điều này không làm việc Hibernate cấp ID lần đầu trở thành “sai”; nó chỉ cho thấy **không nên dựa vào ID đang được sinh như một giá trị hash có thể thay đổi mà không cân nhắc vòng đời entity**.

Một vài nguyên tắc khi thiết kế equality của entity:

- Nếu entity có **business key thật sự bất biến và duy nhất**, đôi khi có thể dựa vào khóa đó, nhưng phải bảo đảm nó thực sự không đổi.
- Nếu dùng **generated ID**, cần xử lý giai đoạn `id == null`; hai entity mới có ID null không tự nhiên trở thành cùng một entity.
- Nhiều hướng triển khai sử dụng ID đã có cho `equals` và một `hashCode` ổn định theo class; cần tính đến Hibernate proxy, quan hệ kế thừa và yêu cầu cụ thể.
- Không tự động dùng toàn bộ các quan hệ hai chiều và field mutable trong `equals`/`hashCode`, vì có thể kích hoạt lazy loading, đệ quy hoặc thay đổi hash.
- Không mặc định sinh `equals`/`hashCode` bằng annotation Lombok `@Data` là phù hợp cho mọi entity.

Không có một công thức equality tối ưu cho mọi mapping. Nhưng **không thay entity ID sau khi persistent** là một tiền đề giúp các lựa chọn equality và identity dễ kiểm soát hơn.

## 9. Nếu entity đã detached thì có được đổi ID không?

Giả sử:

~~~java
EntityManager em = emf.createEntityManager();
Product product;

try {
    product = em.find(Product.class, 101L);
} finally {
    em.close();
}

// product giờ là detached nếu trước đó đã được nạp thành công.
~~~

Ở trạng thái detached, persistence context cũ không còn theo dõi object. Tuy nhiên object vẫn mang **identity của bản ghi `101`**. Việc gán `id = 202` vào object detached rồi gọi `merge` trong context khác không phải cơ chế chuẩn để “đổi primary key”.

`merge` có mục tiêu hợp nhất trạng thái của entity detached vào **một managed instance tương ứng với identity của nó**, trả về managed instance đó. Nếu lập trình viên đã tự sửa identity, JPA không có hợp đồng hỗ trợ thay khóa của cùng entity; hành vi có thể dẫn đến lỗi, nhận diện nhầm bản ghi, chèn sai hoặc không đạt kết quả mong muốn tùy provider và tình trạng database.

Ví dụ cách dùng `merge` đúng về mặt định danh:

~~~java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    // detachedProduct có ID cũ và chỉ sửa name/price/sku hợp lệ.
    Product managedCopy = em.merge(detachedProduct);

    // managedCopy là đối tượng do em hiện tại quản lý.
    // detachedProduct không tự trở thành managed instance.

    tx.commit();
} catch (RuntimeException e) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw e;
} finally {
    em.close();
}
~~~

Đoạn này giả định biến `detachedProduct` đã tồn tại và dữ liệu được kiểm tra hợp lệ. Các cập nhật đồng thời có thể cần `@Version` để tránh ghi đè thông tin mới hơn.

**Giữ nguyên ID cả khi detached.** Nếu muốn tạo một bản sao là entity khác, tạo **instance mới** với identity mới theo thiết kế, thay vì thay ID của object cũ rồi dựa vào `merge`.

## 10. Có nên đổi ID để tạo bản sao entity không?

Một tình huống dễ gặp: “Tôi muốn sao chép sản phẩm `101` thành sản phẩm mới `201`; có thể lấy entity cũ rồi set ID mới không?”

Không nên. Entity cũ có thể đang managed hoặc detached, mang liên kết và trạng thái nội bộ. Đổi ID sẽ tạo ra sự nhập nhằng giữa “cập nhật bản ghi cũ” và “tạo bản ghi mới”.

Một cách rõ ràng hơn:

~~~java
Product original = em.find(Product.class, 101L);

Product copy = new Product(
    "SP-201",
    original.getName(),
    original.getPrice()
);

em.persist(copy);
~~~

Trong ví dụ hoàn chỉnh ở trên, `getName()` và `getPrice()` là các accessor cần có trong `Product` nếu sử dụng đoạn sao chép. Nếu khóa chính tự sinh, để provider gán khóa cho `copy`. Nếu ID do ứng dụng tự cấp, tạo **object mới với ID mới được cấp trước khi persist**.

Cần chủ động quyết định các quan hệ và collection nào được sao chép; **không** phải mọi association đều nên sao chép ngầm theo `cascade`. Nếu `sku` cần duy nhất, bản sao phải có SKU mới phù hợp ràng buộc.

## 11. Nếu thật sự cần đổi giá trị khóa chính trong database thì sao?

Đôi khi yêu cầu đến từ di chuyển dữ liệu, sửa thiết kế schema hoặc hợp nhất hệ thống, chứ không phải từ nghiệp vụ cập nhật entity thường ngày. Ví dụ, muốn đổi một số khóa nguyên thủy đã nhập sai trong dữ liệu cũ.

Cần phân biệt hai tình huống:

1. **Muốn đổi mã hiển thị hoặc mã nghiệp vụ:** tốt nhất để mã đó là thuộc tính thường có unique constraint, giữ nguyên PK.
2. **Buộc phải tái cấu trúc primary key ở database:** đây là hoạt động **migration dữ liệu và schema**, phải xử lý toàn bộ tham chiếu liên quan, transaction, index/constraint, các hệ thống lưu ID và cache.

Các bước tư duy cho migration:

- Xác định mọi bảng có FK trỏ tới khóa cũ.
- Xác định tham chiếu ngoài DB: message, URL, log, dữ liệu xuất bản hoặc hệ thống tích hợp.
- Thiết kế khóa mới và cách ánh xạ từ ID cũ sang ID mới.
- Thực hiện migration trong phạm vi transaction và theo quy tắc ràng buộc database phù hợp.
- Đồng bộ ứng dụng, cache và các thành phần vẫn tham chiếu ID cũ.
- Kết thúc persistence context cũ và khởi tạo ngữ cảnh mới sau thay đổi cấu trúc dữ liệu.

SQL như:

~~~sql
UPDATE products
SET id = 201
WHERE id = 101;
~~~

**không phải lời giải dùng trong luồng cập nhật entity Hibernate thông thường.** SQL trực tiếp có thể va vào PK/FK và làm các entity đang được quản lý trở nên lỗi thời. Các hệ thống có `ON UPDATE CASCADE` vẫn cần giải quyết cache, identity map và những nơi sử dụng ID bên ngoài database.

Nếu một ứng dụng cần thay “định danh” nhiều lần theo nghiệp vụ, đó là tín hiệu nên **thiết kế lại ý nghĩa của khóa**, thay vì cố cho phép sửa `@Id`.

## 12. Bất biến của ID và optimistic locking là hai cơ chế khác nhau

Giữ nguyên ID không giải quyết mọi lỗi đồng thời. Hai transaction có thể cùng nạp `Product id=101`, mỗi bên sửa giá, rồi transaction sau ghi đè transaction trước.

Để phát hiện cập nhật cạnh tranh, JPA hỗ trợ `@Version`:

~~~java
@Version
@Column(name = "version", nullable = false)
private Long version;
~~~

Một lệnh cập nhật có thể mang điều kiện đồng thời:

~~~sql
UPDATE products
SET price = 420000.00, version = 6
WHERE id = 101 AND version = 5;
~~~

Nếu transaction khác đã tăng version, câu lệnh có thể không cập nhật hàng kỳ vọng và Hibernate báo xung đột optimistic locking.

| Cơ chế | Mục đích |
| --- | --- |
| `@Id` | Định danh bản ghi/entity, phải ổn định sau khi entity persistent |
| `@Version` | Theo dõi phiên bản để phát hiện cập nhật đồng thời |
| `@Column(unique = true)` | Mô tả/ràng buộc tính duy nhất của cột khi schema được áp dụng |
| `@NaturalId` (Hibernate) | Khóa tự nhiên phục vụ tra cứu, có thể khai báo mutable theo quy tắc riêng |
| Transaction | Gom các thay đổi thành đơn vị commit/rollback |

Không nên dùng `@Version` như một khóa chính thay thế, cũng không được sửa `@Id` như cách “giải quyết” xung đột phiên bản.

## 13. Những lỗi thường gặp liên quan tới identity

| Tình huống | Hậu quả có thể gặp | Hướng xử lý |
| --- | --- | --- |
| Tạo `setId(...)` public rồi gọi khi entity managed | Hibernate có thể báo identifier altered khi flush | Không expose setter ID; chỉ thay field nghiệp vụ |
| Sử dụng mã có thể đổi làm `@Id` | Bị kẹt khi mã cần đổi, FK và tham chiếu phụ thuộc | Dùng surrogate PK, đặt unique constraint trên mã |
| Tạo bản sao bằng cách thay ID của entity cũ | Lẫn lộn entity cũ và entity mới | Khởi tạo instance mới và persist |
| Đổi ID trong object detached rồi `merge` | Kết quả không xác định theo hợp đồng JPA | Giữ ID cũ; sửa field khác hoặc tạo entity mới |
| Sửa một thành phần của `@EmbeddedId` | Thay đổi identity khóa ghép | Giữ toàn bộ giá trị ID bất biến trong vòng đời entity |
| Đổi entity parent khi FK đồng thời là PK qua `@MapsId` | Vô tình đổi khóa của dependent entity | Thiết kế lại thao tác nghiệp vụ hoặc tạo dependent entity mới |
| `hashCode` dựa vào ID từ null sang generated ID | `HashSet`/`HashMap` có thể không tìm được object | Thiết kế equality nhất quán qua vòng đời |
| Tự viết SQL đổi PK khi context còn mở | Cache/context giữ identity cũ, có thể tham chiếu sai | Xử lý như migration riêng, đóng/làm mới context |
| Dùng `@GeneratedValue` nhưng tự chèn ID vào managed entity | Xung đột với trách nhiệm generator | Để provider gán ID lần đầu |
| Tưởng rollback sẽ xóa ID khỏi object Java | Java object có thể vẫn mang ID đã được cấp | Đóng context lỗi, xác định lại trạng thái bằng truy vấn mới |

### Phân biệt lỗi mất bản ghi với lỗi đổi identifier

Khi gọi `em.find(Product.class, 101L)` mà không tồn tại hàng, kết quả thường là `null`. Điều đó khác hoàn toàn với chuyện đã nạp entity ID `101` rồi gán ID `102`: trường hợp sau là **lỗi quy tắc identity của entity**, không phải “truy vấn không có dữ liệu”.

### Phân biệt định danh của Java object và khóa của hàng SQL

Toán tử `==` kiểm tra **cùng tham chiếu Java**. Giá trị `@Id` là **định danh entity theo dữ liệu**. Hai object từ hai persistence context khác nhau có thể biểu diễn cùng hàng SQL và cùng ID, nhưng `a == b` là `false`.

Vì vậy, việc quy định ID bất biến **không làm tất cả Java object trở thành cùng một instance**; nó giúp provider nhận diện ổn định entity bên trong từng context.

## 14. Thiết kế API để tránh sửa ID ngoài ý muốn

Một lớp entity có thể đặt quy tắc ở mức API:

~~~java
@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "display_name", nullable = false)
    private String displayName;

    protected Customer() {
    }

    public Customer(String displayName) {
        rename(displayName);
    }

    public Long getId() {
        return id;
    }

    public void rename(String newName) {
        if (newName == null || newName.isBlank()) {
            throw new IllegalArgumentException("Tên không hợp lệ");
        }
        this.displayName = newName.trim();
    }
}
~~~

Các lựa chọn thiết kế có chủ đích:

- **`id` là `private`** để mã bên ngoài không thể gán trực tiếp.
- **Không có public `setId(...)`**. Provider vẫn có thể dùng field access để gán ID lần đầu.
- **`getId()` chỉ đọc**: các tầng khác có thể dùng ID để truy vấn, lập URL hoặc ghi log.
- **Phương thức nghiệp vụ `rename(...)`** thay đổi đúng phần dữ liệu được phép đổi.
- **Không dùng `final` trên trường ID persisted** chỉ để đạt vẻ “immutable” của Java; quy tắc bất biến đến từ vòng đời entity.

Nếu dùng công cụ sinh mã getter/setter như Lombok, cần tránh vô tình sinh setter public cho `@Id`. Với entity có quan hệ hai chiều hoặc collection, cũng tránh sinh tự động equality/toString dựa trên toàn bộ graph vì có thể gây vòng lặp hoặc truy vấn lazy ngoài ý muốn.

### Nếu cần setter để hỗ trợ import dữ liệu?

Với **assigned ID**, có thể cấp ID qua constructor/factory lúc tạo **entity mới**, trước khi persist:

~~~java
public static ExternalRecord newRecord(String externalId, String payload) {
    return new ExternalRecord(externalId, payload);
}
~~~

Nếu dùng entity ID sinh tự động, không cần setter công khai chỉ để nhập dữ liệu. Mã import có thể lưu mã bên ngoài ở một cột riêng, ví dụ `external_reference` có ràng buộc unique, còn ID nội bộ vẫn do Hibernate/database cấp.

## 15. Minh họa vòng đời ID theo thời gian

~~~mermaid
flowchart TD
    A["new Product(...): id = null"] --> B["persist(product)"]
    B --> C["Provider gán ID lần đầu theo generator"]
    C --> D["Managed Product: id = 101"]
    D --> E["Thay name/price/sku"]
    E --> F["flush / commit: UPDATE WHERE id = 101"]
    D --> G["Thử thay id = 102"]
    G --> H["Vi phạm quy tắc identity; có thể lỗi khi flush"]
    F --> I["Đóng EntityManager"]
    I --> J["Detached Product: vẫn id = 101"]
    J --> K["Mở context mới và nạp/merge theo id = 101"]
~~~

Một phiên làm việc đúng với entity ID `101` không có bước “chuyển nó thành entity ID `102`”. Nếu muốn tạo entity `102`, hãy tạo instance mới và để provider hoặc ứng dụng cấp ID theo chiến lược của **entity mới**.

### Liên hệ với thao tác `remove`

`em.remove(product)` đánh dấu entity managed để xóa. Xóa một entity rồi tạo entity khác có ID mới là **hai hoạt động riêng**; nó không được thực hiện bằng cách sửa giá trị `@Id` của entity bị xóa. Việc xóa có thể thất bại do FK, cascade, optimistic locking hoặc các ràng buộc khác, nên cần xác định ranh giới transaction và điều kiện nghiệp vụ cho mỗi thao tác.

## 16. Bài tập tình huống

### Tình huống A: cập nhật giá sản phẩm

Đã nạp `Product id=101` với giá 350.000 đồng. Người dùng muốn đổi giá thành 400.000 đồng.

**Cách làm:** gọi phương thức đổi giá trên entity đang managed trong transaction phù hợp. Hibernate giữ `id=101` và cập nhật cột `price` của hàng đó. Không liên quan đến việc đổi identifier.

### Tình huống B: đổi mã SKU

Sản phẩm `id=101` có `sku="SP-001"` và công ty muốn đổi thành `"SP-NEW-001"`.

**Cách làm:** nếu SKU là thuộc tính thường có unique constraint, cập nhật SKU như một trường nghiệp vụ. Nếu SKU đang được dùng làm `@Id`, đó là dấu hiệu cần xem lại mô hình: muốn cho phép đổi mã một cách thường xuyên nên tách surrogate primary key khỏi mã nghiệp vụ.

### Tình huống C: hai lần gọi `find`

Trong cùng `EntityManager`:

~~~java
Product a = em.find(Product.class, 101L);
Product b = em.find(Product.class, 101L);
~~~

**Kết quả:** nếu entity tồn tại và đang được quản lý, `a == b` là `true`. Persistence context giữ một managed instance theo identity của entity.

### Tình huống D: đổi khóa ghép

Một `OrderLine` có `@EmbeddedId(orderId=5001, lineNumber=2)`. Ứng dụng muốn chuyển dòng đó sang đơn `5002` bằng cách gọi `line.getId().setOrderId(5002L)`.

**Đánh giá:** sai nếu `OrderLine` đã persistent. Thay một thành phần của `EmbeddedId` làm thay đổi identity của entity. Nghiệp vụ “chuyển dòng” cần mô hình hóa thành các thao tác riêng hoặc thiết kế khóa thay thế.

### Tình huống E: bản sao entity

Cần tạo sản phẩm mới có tên/giá giống `id=101` nhưng với SKU khác.

**Cách làm:** khởi tạo `new Product(newSku, original.getName(), original.getPrice())` rồi `persist`. Không được thay ID của `original`.

### Tình huống F: provider đã phát ID nhưng transaction rollback

`persist` đã làm IDENTITY generator gán `id=103`; sau đó một ràng buộc khác khiến transaction rollback.

**Giải thích:** việc cấp số ID không đảm bảo transaction commit. Object Java có thể vẫn giữ ID `103` dù hàng tương ứng chưa được commit; ID có thể bị bỏ qua trong sequence/identity. Đóng context lỗi và thiết kế lại đường retry, **không** dùng `setId(null)` hoặc `setId(otherValue)` như một cách phục hồi tùy tiện.

## 17. Tự kiểm tra kiến thức

**1. Vì sao không được sửa `@Id` khi entity đã managed?**

Vì Hibernate/JPA dùng ID làm khóa nhận diện entity trong persistence context, phục vụ quan hệ, cache và phát SQL. Thay ID phá vỡ hợp đồng identity; JPA không xác định hành vi này và Hibernate thường phát hiện lỗi.

**2. Provider gán ID từ `null` thành `101` khi persist có vi phạm bất biến không?**

Không. Đây là lần **khởi tạo** định danh theo generator. Điều bị cấm là ứng dụng sửa identity đã được thiết lập của một persistent entity.

**3. Có nên khai báo `private final Long id` để ngăn đổi ID không?**

Không nên trong entity JPA thông thường. JPA/provider cần khả năng gán ID. Hãy dùng field `private`, getter đọc và không cung cấp public setter ID.

**4. Với khóa ghép, có được sửa một thành phần nếu các thành phần còn lại không đổi không?**

Không. Bất kỳ thành phần nào đổi đều có thể làm thay đổi toàn bộ primary key/identity.

**5. Entity đã detached thì có được đổi ID rồi `merge` để di chuyển bản ghi không?**

Không. Detached không làm ID trở thành giá trị được tự do đổi; `merge` không phải API đổi primary key.

**6. Tại sao mã nghiệp vụ có thể thay đổi không nên làm PK?**

Vì thay mã sẽ cần đổi entity identity và có thể ảnh hưởng FK, cache, tham chiếu ngoài. Một PK ổn định cùng cột mã nghiệp vụ unique có thể cập nhật sẽ tách được hai vai trò.

**7. `@Version` có cho phép đổi ID mà vẫn tránh xung đột không?**

Không. `@Version` hỗ trợ phát hiện xung đột khi cập nhật, còn `@Id` xác định entity. Hai annotation giải quyết hai vấn đề khác nhau.

**8. `ON UPDATE CASCADE` ở database có làm `product.setId(...)` hợp lệ trong Hibernate không?**

Không. Cascade ràng buộc database không điều phối lại entity key của persistence context và cache ORM.

## 18. Quy tắc áp dụng vào thiết kế

Khi thiết kế entity JPA/Hibernate, hãy đặt câu hỏi: **giá trị nào thực sự định danh bản ghi trong suốt vòng đời của nó?** Một giá trị dùng làm `@Id` cần ổn định. Với dữ liệu nghiệp vụ có thể đổi, đặt nó trong thuộc tính khác, thêm ràng buộc duy nhất khi cần và cho phép thay đổi qua phương thức nghiệp vụ đúng.

Một entity đang managed có thể **thay đổi trạng thái**, nhưng vẫn phải **giữ nguyên identity**. Với ID sinh tự động, để provider gán lần đầu; với ID tự cấp, cấp trước khi persist; với khóa ghép, giữ nguyên toàn bộ thành phần. Nếu cần một identity khác, đó thường là **một entity mới hoặc một migration dữ liệu riêng**, không phải một lần gọi setter.

Hiểu và tuân thủ tính bất biến của định danh giúp persistence context hoạt động nhất quán, câu lệnh cập nhật nhắm đúng hàng, quan hệ không bị phá vỡ và logic nghiệp vụ không phụ thuộc vào những hành vi ngoài hợp đồng JPA.
