# Phân biệt bỏ liên kết, đặt khóa ngoại null và xóa bản ghi con

> **Chủ đề:** Data Persistence Relational Access ORM JPA  
> **Chương:** Quan hệ một-nhiều

Khi gọi `parent.getChildren().remove(child)`, lập trình viên có thể kỳ vọng rằng đối tượng con sẽ biến mất khỏi cơ sở dữ liệu. Trong JPA, hành động này **không mặc nhiên tương đương với một câu lệnh `DELETE`**. Tùy mô hình quan hệ, bên sở hữu liên kết (*owning side*), tính bắt buộc của khóa ngoại, và cấu hình `orphanRemoval`, kết quả có thể là:

- Chỉ thay đổi collection Java trong bộ nhớ, chưa có thay đổi quan hệ ở database.
- Bỏ quan hệ bằng cách **đặt cột khóa ngoại về `NULL`** qua `UPDATE`.
- Bỏ một hàng trong **bảng liên kết** nếu association được lưu qua join table.
- **Xóa bản ghi con** qua `DELETE` nếu đó là vòng đời mong muốn và JPA được yêu cầu thực hiện.

Ba khái niệm trong tên bài — **bỏ liên kết**, **đặt khóa ngoại null**, và **xóa bản ghi con** — liên quan với nhau nhưng không đồng nhất. Muốn dự đoán đúng SQL và bảo vệ dữ liệu, cần xác định **ai sở hữu quan hệ**, **cơ sở dữ liệu lưu quan hệ ở đâu** và **vòng đời của entity con phụ thuộc entity cha đến mức nào**.

## 1. Mục tiêu bài học

Sau bài học, bạn có thể:

1. Giải thích được sự khác nhau giữa bỏ liên kết ở object graph, cập nhật FK thành `NULL`, và xóa hàng con.
2. Đọc annotation `@OneToMany`, `@ManyToOne`, `mappedBy`, `@JoinColumn`, `optional`, `nullable` và dự đoán bên nào ghi khóa ngoại.
3. Hiểu vì sao `collection.remove(child)` có thể không làm thay đổi FK khi collection là phía inverse và `orphanRemoval=false`.
4. Viết helper thêm/xóa quan hệ hai chiều nhằm giữ collection của cha và tham chiếu của con đồng bộ.
5. Dùng `orphanRemoval=true` cho **child thuộc sở hữu vòng đời của parent**, phân biệt với `CascadeType.REMOVE`.
6. Phân tích trường hợp FK cho phép `NULL`, FK `NOT NULL` và quan hệ lưu bằng join table.
7. Xử lý việc xóa con, xóa cha, chuyển con sang cha khác và rollback transaction.
8. Quan sát SQL `UPDATE`, `DELETE` và constraint violation để xác nhận mapping trong một database thật.

## 2. Mô hình quan hệ một-nhiều trước khi nhìn Java

Giả sử hệ thống quản lý phòng ban và nhân viên:

```text
departments
+----+------------+
| id | name       |
+----+------------+
| 10 | Engineering|
| 20 | Support    |
+----+------------+

employees
+----+------+---------------+
| id | name | department_id |
+----+------+---------------+
|  1 | An   | 10            |
|  2 | Binh | 10            |
|  3 | Chi  | 20            |
+----+------+---------------+
```

Một phòng ban có nhiều nhân viên (`Department 1—N Employee`), còn mỗi nhân viên được phân vào tối đa một phòng ban tại một thời điểm. Nếu nhân viên có thể tạm thời chưa thuộc phòng ban nào, cột `employees.department_id` có thể cho phép `NULL`.

DDL minh họa:

```sql
CREATE TABLE departments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE employees (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    department_id BIGINT NULL,
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id) REFERENCES departments(id)
);
```

Điều cần nhận ra: **bảng `employees` chứa khóa ngoại**. Dù API Java biểu diễn `department.getEmployees()`, quyền ghi liên kết ở mức quan hệ thường nằm tại `employee.department` nếu mapping hai chiều dùng `mappedBy`.

### 2.1. Ba kết quả khác nhau đối với nhân viên An

Ban đầu hàng An là:

```text
employees(id=1, name="An", department_id=10)
```

**Kết quả A — Bỏ liên kết tại object graph**

```java
department.getEmployees().remove(an);
```

Trong bộ nhớ, collection có thể không còn An. Tuy nhiên nếu `Department.employees` là phía inverse và mã không thay đổi `an.department`, trạng thái FK vẫn được xác định bởi owning side. Khi `orphanRemoval=false`, **không nên kỳ vọng lệnh này tự làm `department_id` thành null hoặc xóa An**.

**Kết quả B — Tháo quan hệ bằng cách đặt khóa ngoại null**

```sql
UPDATE employees
SET department_id = NULL
WHERE id = 1;
```

An **vẫn tồn tại** trong `employees`, nhưng không còn phòng ban. Đây là hành động “unassign employee” trong mô hình cho phép nhân viên chưa thuộc department.

**Kết quả C — Xóa bản ghi con**

```sql
DELETE FROM employees
WHERE id = 1;
```

An **không còn tồn tại** như một hàng của bảng `employees`. Đây là một quyết định nghiệp vụ mạnh hơn việc tháo quan hệ.

| Kết quả | Hàng con còn tồn tại? | FK của con | Ý nghĩa nghiệp vụ |
|---|---|---|---|
| Chỉ sửa collection inverse | Có | Có thể vẫn là `10` | Thay đổi tạm trong object graph; chưa biểu đạt đủ việc cập nhật quan hệ |
| `UPDATE ... department_id=NULL` | Có | `NULL` | Nhân viên không còn thuộc phòng ban |
| `DELETE FROM employees` | Không | Không còn hàng để chứa FK | Nhân viên bị xóa khỏi hệ thống |
| Gỡ hàng ở join table | Có | FK ở bảng liên kết bị xóa | Hai entity vẫn tồn tại nhưng quan hệ kết thúc |

**Từ khóa quan trọng:** thao tác `remove` của **`java.util.Collection`** chỉ có nghĩa “loại phần tử khỏi collection Java”. Nó không phải cùng API với `EntityManager.remove(entity)`, thao tác đánh dấu entity cần xóa khỏi persistence.

## 3. Quan hệ một-nhiều hai chiều: ai là owning side?

Cách ánh xạ phổ biến nhất là:

```java
// Trong Department:
@OneToMany(mappedBy = "department")
private List<Employee> employees = new ArrayList<>();

// Trong Employee:
@ManyToOne
@JoinColumn(name = "department_id")
private Department department;
```

Ý nghĩa:

- `@ManyToOne` ở `Employee.department` là **phía owning side**, bởi bảng `employees` chứa FK.
- `@OneToMany(mappedBy = "department")` ở `Department.employees` là **phía inverse**; `mappedBy` là tên field Java `department` trong `Employee`.
- Việc cập nhật cột `department_id` thường dựa trên thay đổi ở **`employee.department`**.
- Collection trên phía cha hỗ trợ điều hướng và diễn đạt aggregate, nhưng hai phía phải được cập nhật nhất quán nếu ứng dụng dùng mapping hai chiều.

### 3.1. Vì sao thay collection một phía dễ gây nhầm?

Ví dụ code:

```java
Department department = em.find(Department.class, 10L);
Employee an = em.find(Employee.class, 1L);

department.getEmployees().remove(an);

// Có thể department.employees không còn An,
// nhưng an.getDepartment() vẫn là Department#10.
```

Hai phía trong bộ nhớ đang mâu thuẫn. Với `mappedBy` ở phía collection và **`orphanRemoval=false`**, thay collection inverse mà không cập nhật owning side không phải cách đáng tin cậy để đổi FK.

Ở thời điểm flush, provider sẽ đồng bộ các mapping theo quy tắc sở hữu. Tùy state đã được load và các thao tác khác, ứng dụng có thể nhìn thấy hành vi khó hiểu. Thiết kế đúng là **không để object graph mâu thuẫn**.

## 4. Ví dụ 1: tháo nhân viên khỏi phòng ban nhưng vẫn giữ nhân viên

Đây là bài toán **liên kết tùy chọn**, không có yêu cầu xóa nhân viên khi họ rời phòng ban.

### 4.1. Entity Department

```java
package demo.domain;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "departments")
public class Department {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @OneToMany(mappedBy = "department", orphanRemoval = false)
    private List<Employee> employees = new ArrayList<>();

    protected Department() {
        // JPA
    }

    public Department(String name) {
        this.name = Objects.requireNonNull(name);
    }

    public Long getId() {
        return id;
    }

    public List<Employee> getEmployees() {
        return Collections.unmodifiableList(employees);
    }

    public void addEmployee(Employee employee) {
        Objects.requireNonNull(employee);

        if (employee.getDepartment() == this) {
            return;
        }

        Department previous = employee.getDepartment();
        if (previous != null) {
            previous.removeEmployee(employee);
        }

        employees.add(employee);
        employee.assignDepartment(this);
    }

    public void removeEmployee(Employee employee) {
        Objects.requireNonNull(employee);

        if (employee.getDepartment() == this) {
            employees.remove(employee);
            employee.assignDepartment(null);
        }
    }
}
```

### 4.2. Entity Employee

```java
package demo.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

import java.util.Objects;

@Entity
@Table(name = "employees")
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String name;

    @ManyToOne(fetch = FetchType.LAZY, optional = true)
    @JoinColumn(name = "department_id", nullable = true)
    private Department department;

    protected Employee() {
        // JPA
    }

    public Employee(String name) {
        this.name = Objects.requireNonNull(name);
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public Department getDepartment() {
        return department;
    }

    void assignDepartment(Department department) {
        this.department = department;
    }
}
```

Trong ví dụ:

1. `Department` và `Employee` đều có identity riêng. Việc nhân viên rời phòng ban không làm mất identity của nhân viên.
2. `orphanRemoval=false` vì nhân viên được phép tồn tại độc lập khỏi phòng ban.
3. `Employee.department` có `optional=true` và cột `department_id` có `nullable=true`, phù hợp schema.
4. Phương thức `Department.removeEmployee` vừa gỡ phần tử khỏi collection, vừa đặt owning reference thành `null`.
5. Phương thức `addEmployee` chuyển một nhân viên từ phòng ban cũ sang phòng ban mới và đồng bộ hai phía; cách chuyển này chỉ phù hợp vì association **không có orphan removal**.
6. Không expose setter tùy tiện ở mọi phía để tránh trạng thái collection và FK reference lệch nhau.

Trong mô hình đơn giản này, equality của `Employee` giữ mặc định `Object.equals`, phù hợp khi làm việc với những managed instance nhất quán trong cùng persistence context. Nếu domain yêu cầu equality theo ID qua nhiều context, cần thiết kế `equals()/hashCode()` riêng, đặc biệt vì ID được sinh sau khi tạo entity.

### 4.3. Thao tác tháo liên kết trong một transaction

Ví dụ ứng dụng Java SE có persistence unit `RESOURCE_LOCAL`:

```java
EntityManager em = emf.createEntityManager();

try {
    EntityTransaction tx = em.getTransaction();
    tx.begin();

    try {
        Department department = em.find(Department.class, 10L);
        Employee employee = em.find(Employee.class, 1L);

        if (department == null || employee == null) {
            throw new IllegalArgumentException("Not found");
        }
        if (employee.getDepartment() != department) {
            throw new IllegalStateException(
                "Employee is not assigned to this department");
        }

        department.removeEmployee(employee);

        tx.commit();
    } catch (RuntimeException ex) {
        if (tx.isActive()) {
            tx.rollback();
        }
        throw ex;
    }
} finally {
    em.close();
}
```

`EntityManager`/`EntityManagerFactory` và biến `emf` ở đây giả sử đã được khai báo theo môi trường Java SE. Khi flush hoặc commit, provider sẽ đồng bộ thay đổi owning association. SQL thường có ý nghĩa tương đương:

```sql
UPDATE employees
SET department_id = NULL
WHERE id = 1;
```

Kết quả mong muốn sau commit:

```text
Employee#1 vẫn tồn tại.
Employee#1.department == null.
Department#10 không còn Employee#1 trong quan hệ.
```

Để xác minh dữ liệu đã commit, nên mở một `EntityManager` mới và đọc lại Employee; không dựa vào collection đang có trong persistence context cũ làm bằng chứng duy nhất cho trạng thái database.

### 4.4. Chuyển nhân viên sang phòng ban khác

Vì nhân viên có lifecycle độc lập, thao tác chuyển là hợp lệ:

```java
Department support = em.find(Department.class, 20L);
Employee an = em.find(Employee.class, 1L);

support.addEmployee(an);
```

Helper thực hiện gỡ từ phòng ban cũ và gán vào phòng ban mới; database thường chỉ cần một thay đổi FK cuối cùng, ví dụ:

```sql
UPDATE employees
SET department_id = 20
WHERE id = 1;
```

JPA không cam kết số lệnh SQL chính xác hay thời điểm phát SQL trong mọi provider. Điều cần giữ là mô hình cuối cùng: **bản ghi nhân viên vẫn tồn tại, FK chuyển từ phòng ban cũ sang phòng ban mới**.

## 5. FK cho phép NULL hay NOT NULL quyết định điều gì?

Dữ liệu quan hệ có ràng buộc vật lý. Nếu khai báo:

```sql
department_id BIGINT NOT NULL
```

thì thao tác “tháo nhân viên khỏi department bằng cách đặt FK thành null” không hợp lệ. Ngay cả khi Java cho phép gọi `employee.assignDepartment(null)`, lúc provider thực thi `UPDATE`, database sẽ từ chối. Provider cũng có thể phát hiện một số vi phạm trước khi SQL được gửi.

### 5.1. Mapping bắt buộc ở Java và database

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "department_id", nullable = false)
private Department department;
```

Với mapping này:

- `optional=false` diễn đạt quan hệ bắt buộc ở cấp mô hình JPA.
- `nullable=false` là metadata cho join column và có thể ảnh hưởng việc tạo schema.
- `NOT NULL` trên database là ràng buộc cuối cùng bảo vệ dữ liệu khi có nhiều nguồn ghi.
- `@NotNull` của Jakarta Validation có thể bổ sung kiểm tra ở tầng ứng dụng, nhưng không thay thế transaction và constraint database.

Nếu nhân viên **bắt buộc** luôn thuộc một department, thao tác hợp lệ thường là **chuyển sang department khác** hoặc **xóa nhân viên** nếu nghiệp vụ cho phép. Không có lý do để cố đặt FK thành null.

### 5.2. Một bảng so sánh thiết kế

| Nghiệp vụ | FK ở bảng child | Hành vi khi bỏ liên kết |
|---|---|---|
| Nhân viên có thể chưa phân phòng ban | `NULL` được phép | `UPDATE child SET department_id = NULL` |
| Dòng đơn hàng bắt buộc thuộc một đơn hàng | `NOT NULL` | Không để dòng đơn hàng thành orphan; thường xóa dòng |
| Ticket bắt buộc có chủ sở hữu | `NOT NULL` | Chuyển sang owner khác hoặc áp dụng chính sách xóa riêng |
| Địa chỉ lịch sử độc lập có thể gỡ khỏi khách hàng | Tùy mô hình | Bỏ association nhưng giữ bản ghi địa chỉ nếu nó là entity độc lập |
| Association dùng join table | FK nằm ở bảng nối | Xóa hàng trong bảng nối; bản ghi child thường vẫn còn |

**Điểm cốt lõi:** nếu FK `NOT NULL` và child phải được giữ lại, cần một **parent mới hợp lệ** trước khi đồng bộ, hoặc quy trình nghiệp vụ khác. “Chỉ xóa khỏi List” không làm biến mất constraint.

## 6. Ví dụ 2: dòng đơn hàng phải bị xóa khi bị loại khỏi Order

Một dòng đơn hàng (`OrderLine`) thường chỉ có ý nghĩa bên trong đơn hàng mà nó thuộc về. Nếu người dùng xóa một dòng khỏi đơn đang chỉnh sửa, nghiệp vụ có thể yêu cầu **xóa luôn dòng đó trong database**, vì không tồn tại khái niệm “dòng đơn hàng không thuộc đơn hàng nào”.

Mô hình này phù hợp với `@OneToMany(orphanRemoval = true)`.

### 6.1. Schema

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    sku VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id),
    CONSTRAINT chk_quantity_positive
        CHECK (quantity > 0)
);
```

Vì `order_lines.order_id` `NOT NULL`, không thể “đặt FK thành null” rồi để hàng dòng đơn tồn tại. Khi bỏ dòng khỏi order, hệ thống phải quyết định **xóa dòng** hoặc áp dụng một quy trình khác. Trong ví dụ này chọn xóa.

### 6.2. Entity PurchaseOrder

```java
package demo.order;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "order_number", nullable = false, unique = true)
    private String orderNumber;

    @OneToMany(
        mappedBy = "order",
        cascade = CascadeType.ALL,
        orphanRemoval = true
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
        // JPA
    }

    public PurchaseOrder(String orderNumber) {
        this.orderNumber = Objects.requireNonNull(orderNumber);
    }

    public Long getId() {
        return id;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }

    public void addLine(String sku, int quantity) {
        OrderLine line = new OrderLine(this, sku, quantity);
        lines.add(line);
    }

    public void removeLine(OrderLine line) {
        Objects.requireNonNull(line);

        if (lines.remove(line)) {
            line.detachFromOrder();
        }
    }
}
```

### 6.3. Entity OrderLine

```java
package demo.order;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

import java.util.Objects;

@Entity
@Table(name = "order_lines")
public class OrderLine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @Column(name = "sku", nullable = false, length = 40)
    private String sku;

    @Column(name = "quantity", nullable = false)
    private int quantity;

    protected OrderLine() {
        // JPA
    }

    OrderLine(PurchaseOrder order, String sku, int quantity) {
        this.order = Objects.requireNonNull(order);
        this.sku = Objects.requireNonNull(sku);
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive");
        }
        this.quantity = quantity;
    }

    public Long getId() {
        return id;
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }

    void detachFromOrder() {
        this.order = null;
    }
}
```

Đoạn này dùng `CascadeType.ALL` để minh họa vòng đời của child thuộc về parent, bao gồm `PERSIST`, `MERGE`, `REMOVE` và các thao tác được định nghĩa bởi cascade này. Trong ứng dụng thật, chỉ bật cascade phù hợp với nghiệp vụ; `ALL` không phải lựa chọn mặc định cho mọi association.

**Điểm thiết kế quan trọng:** `removeLine` gỡ child khỏi collection được JPA quản lý và làm object graph nhất quán trong bộ nhớ. `orphanRemoval=true` chỉ thị JPA **xóa entity con khi nó bị tách khỏi association do parent sở hữu vòng đời**, thay vì giữ một hàng child có FK null. Việc đặt field `order=null` trong object Java không đồng nghĩa yêu cầu database phải nhận một lệnh `UPDATE order_id=NULL`; provider có thể xử lý orphan bằng `DELETE` tại flush. Mã không dựa vào thứ tự SQL cụ thể.

### 6.4. Xóa một dòng trong transaction

```java
EntityManager em = emf.createEntityManager();

try {
    EntityTransaction tx = em.getTransaction();
    tx.begin();

    try {
        PurchaseOrder order = em.find(PurchaseOrder.class, orderId);

        if (order == null) {
            throw new IllegalArgumentException("Order not found");
        }

        OrderLine selected = order.getLines().stream()
            .filter(line -> line.getId().equals(lineId))
            .findFirst()
            .orElseThrow(() ->
                new IllegalArgumentException("Line not found"));

        order.removeLine(selected);

        tx.commit();
    } catch (RuntimeException ex) {
        if (tx.isActive()) {
            tx.rollback();
        }
        throw ex;
    }
} finally {
    em.close();
}
```

`emf`, `orderId`, `lineId` là các giá trị do phần khởi tạo ứng dụng cung cấp; persistence unit là `RESOURCE_LOCAL`. Trong phần lớn use case với `OrderLine` đã được lưu và đang managed, provider sẽ xử lý orphan khi flush/commit để bản ghi con **không còn tồn tại** sau commit, với SQL mang ý nghĩa:

```sql
DELETE FROM order_lines
WHERE id = ?;
```

Nếu child **chưa từng được persist** và chỉ là object mới được thêm rồi gỡ trong cùng một chuỗi thao tác, quy tắc orphan removal của đặc tả không nhất thiết áp dụng theo cách xóa một bản ghi chưa tồn tại. Không cần suy luận rằng phải phát `DELETE` cho một hàng chưa có trong database.

### 6.5. Vì sao không dùng orphanRemoval cho Employee?

Khác biệt là **vòng đời nghiệp vụ**:

- Employee có identity độc lập. Rời Department không có nghĩa con người đó bị xóa.
- OrderLine chỉ tồn tại như một phần của Order. Bỏ khỏi Order có thể nghĩa là xóa OrderLine.

Nếu vô tình bật `orphanRemoval=true` trên `Department.employees` rồi gọi `removeEmployee`, provider có thể xóa luôn hàng Employee, gây mất dữ liệu ngoài mong muốn.

## 7. Bảng quyết định: cùng hành động remove nhưng kết quả khác nhau

| Mapping / dữ liệu | Thao tác Java | Kết quả mong muốn khi flush/commit |
|---|---|---|
| Hai chiều, `mappedBy` ở parent, `orphanRemoval=false`, child FK nullable | Chỉ `parent.children.remove(child)` | Collection Java đổi; FK có thể không đổi nếu owning side chưa đổi |
| Cùng mapping, FK nullable | `parent.children.remove(child)` + `child.parent=null` | `UPDATE` FK thành `NULL`; child vẫn tồn tại |
| Cùng mapping, FK `NOT NULL` | Cố đặt `child.parent=null` | Không hợp lệ; có thể lỗi validation/constraint khi flush |
| `orphanRemoval=true`, managed child thuộc parent | Gỡ child khỏi collection và đồng bộ hai phía | Xóa hàng child khi flush; không giữ orphan |
| Không dùng `orphanRemoval` | `em.remove(child)` trên managed entity | Đánh dấu xóa bản ghi con |
| `cascade=REMOVE` trên parent | `em.remove(parent)` | Truyền remove tới child theo cascade |
| Unidirectional `@OneToMany` dùng join table, không orphan removal | Gỡ phần tử khỏi association | Xóa hàng liên kết; child entity vẫn tồn tại |
| Chuyển child giữa hai parent độc lập, không orphan removal | Đổi owning `child.parent` | `UPDATE` FK sang parent mới |

**Mốc thời gian:** kết quả SQL thường được đồng bộ khi flush hoặc commit, không phải tại thời điểm thao tác collection trong Java. Một provider có thể thực thi câu lệnh sớm hơn khi cần (ví dụ lấy generated ID, flush trước query). Transaction phải commit thành công thì dữ liệu mới được xác nhận.

## 8. orphanRemoval hoạt động chính xác ở phạm vi nào?

Trong JPA, `orphanRemoval` được khai báo trên `@OneToOne` hoặc `@OneToMany`. Với `@OneToMany`, khi **managed child đang được liên kết với parent** bị gỡ khỏi association mà parent sở hữu vòng đời, JPA sẽ áp dụng thao tác remove cho orphan theo quy tắc của đặc tả.

```java
@OneToMany(mappedBy = "order", orphanRemoval = true)
private List<OrderLine> lines = new ArrayList<>();
```

### 8.1. Những việc orphanRemoval làm

- Biểu đạt “child thuộc vòng đời của parent”.
- Khi child đã được quản lý và bị tháo khỏi association, yêu cầu provider áp dụng remove cho child.
- Giúp API domain `order.removeLine(line)` diễn đạt trực tiếp nghiệp vụ “không còn dòng đó trong đơn”.
- Hạn chế nguy cơ tạo child mồ côi không hợp lệ trong mô hình child không thể tồn tại độc lập.

### 8.2. Những việc orphanRemoval không làm

- **Không** thay thế việc đặt quan hệ đúng phía owning side trong object graph.
- **Không** phải một cách mặc định để quản lý mọi quan hệ one-to-many.
- **Không** phải thao tác “xóa mềm” (soft delete) trừ khi provider có cấu hình riêng thay đổi semantics của DELETE.
- **Không** bảo đảm một chuỗi SQL INSERT/UPDATE/DELETE cố định trong mọi provider.
- **Không** tạo ràng buộc `ON DELETE CASCADE` trong database theo nghĩa portable chỉ vì annotation có mặt.
- **Không** nên dùng để chuyển child từ parent A sang parent B bằng cách gỡ rồi gán lại trong cùng persistence context; orphan đã được xác định để xóa có semantics khác với child chỉ đang đổi owner.

### 8.3. Gỡ child rồi gán ngay cho parent khác có an toàn không?

Với association có `orphanRemoval=true`:

```java
orderA.removeLine(line);
orderB.getLines().add(line); // Không nên làm như một phép chuyển owner.
```

Nếu `removeLine` đã làm entity trở thành orphan theo quy tắc JPA, việc reassign entity đó vào association khác **không có bảo đảm portable**. JPA mô tả orphan removal cho entity thuộc sở hữu riêng của parent; ứng dụng không nên phụ thuộc thứ tự xóa hay tự tái sử dụng orphan vừa bị gỡ.

Nếu domain thật sự cho phép chuyển child giữa hai parent, hãy xem lại chính sách ownership: có thể **không dùng orphanRemoval**, chuyển owning FK rõ ràng và áp dụng constraint tương ứng. Nếu child chỉ là phần của aggregate Order, nhiều khi nghiệp vụ đúng là tạo **một OrderLine mới** ở order đích, thay vì “chuyển” dòng cũ.

### 8.4. Trạng thái của entity mới, detached và removed

Tại thời điểm orphanRemoval được áp dụng, entity con phải đáp ứng điều kiện vòng đời theo JPA. Với child ở trạng thái **new**, **detached** hoặc đã **removed**, đặc tả không yêu cầu xử lý orphan như đối với một managed entity hợp lệ.

Vì vậy, một test chỉ tạo object mới trong bộ nhớ rồi gọi `collection.remove` chưa đủ chứng minh SQL `DELETE` hoạt động. Khi muốn quan sát orphan removal, hãy persist và commit dữ liệu nền, sau đó **mở persistence context mới, tải parent/child managed, gỡ child rồi commit**.

## 9. orphanRemoval khác CascadeType.REMOVE như thế nào?

Hai tính năng thường xuất hiện cạnh nhau nhưng có **điểm kích hoạt khác nhau**.

### 9.1. CascadeType.REMOVE

```java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.REMOVE
)
private List<OrderLine> lines = new ArrayList<>();
```

Khi ứng dụng gọi:

```java
em.remove(order);
```

thao tác remove được **truyền từ parent sang các child** theo cascade, và các row liên quan có thể được xóa trong một transaction.

Nhưng nếu ứng dụng chỉ làm:

```java
order.getLines().remove(line);
```

thì **`CascadeType.REMOVE` một mình không có nghĩa là dòng đã gỡ sẽ bị xóa**. Tác nhân kích hoạt cascade là thao tác remove trên parent, không phải việc thay nội dung collection.

### 9.2. orphanRemoval=true

```java
@OneToMany(
    mappedBy = "order",
    orphanRemoval = true
)
private List<OrderLine> lines = new ArrayList<>();
```

Khi một child managed bị gỡ khỏi association, orphanRemoval được áp dụng. Ngoài ra, theo quy tắc JPA, khi parent được remove, thao tác remove được áp dụng cho các child của association có orphan removal, nên không nhất thiết phải thêm `CascadeType.REMOVE` chỉ để đạt hành vi xóa child khi xóa parent.

### 9.3. So sánh bằng trigger

| Cấu hình | `order.removeLine(line)` | `em.remove(order)` |
|---|---|---|
| Không cascade remove, không orphanRemoval | Không tự động xóa child; cần xử lý quan hệ/FK | Không tự động remove các child |
| `cascade=REMOVE`, `orphanRemoval=false` | Không xóa child chỉ vì bị gỡ khỏi collection | Cascade remove từ Order xuống các OrderLine |
| `orphanRemoval=true`, không `cascade=REMOVE` | Remove orphan child | Remove các child theo quy tắc orphan removal |
| `cascade=ALL` và `orphanRemoval=true` | Remove orphan child | Cascade remove và quy tắc orphan removal cùng định hướng xóa child; provider xử lý không xóa hai lần |

Mẫu `cascade=ALL, orphanRemoval=true` thường được dùng cho aggregate cha–con có lifecycle hoàn toàn phụ thuộc. Không nên đưa mẫu này lên `@ManyToOne` hoặc quan hệ giữa các entity dùng chung nếu việc xóa dây chuyền không phù hợp.

**Quy tắc dễ nhớ:**

```text
CascadeType.REMOVE:
    "Khi xóa cha, hãy truyền thao tác xóa xuống con."

orphanRemoval = true:
    "Khi con bị loại khỏi quan hệ sở hữu, hãy xóa con."
```

## 10. Xóa con trực tiếp bằng EntityManager.remove

Ngay cả khi association không có `orphanRemoval`, ứng dụng vẫn có thể quyết định **xóa thực thể con**:

```java
Employee employee = em.find(Employee.class, employeeId);

if (employee != null) {
    Department parent = employee.getDepartment();
    if (parent != null) {
        parent.removeEmployee(employee);
    }

    em.remove(employee);
}
```

`em.remove(employee)` đánh dấu một **managed entity** cần xóa. Provider phát SQL DELETE khi đồng bộ/flush theo quy tắc persistence, và transaction phải commit thành công để dữ liệu bị xóa bền vững.

Trong ví dụ trên, `parent.removeEmployee` làm owning reference thành null trong bộ nhớ, sau đó `em.remove(employee)` xóa bản ghi. Provider có thể tối ưu hoặc sắp xếp khác nhau, nên không được dự đoán cứng rằng chắc chắn có một lệnh `UPDATE SET NULL` trước `DELETE`. Mục tiêu của helper là **giữ object graph nhất quán** trong cùng context.

### 10.1. Không gọi remove trên detached entity một cách máy móc

Đoạn này có thể không hợp lệ:

```java
Employee detached = obtainFromClosedEntityManager();
em.remove(detached); // Detached entity không phải managed entity của em.
```

Phương án thường rõ hơn là tìm lại theo ID trong transaction hiện tại:

```java
Employee managed = em.find(Employee.class, detached.getId());
if (managed != null) {
    em.remove(managed);
}
```

Với concurrency, cần kiểm tra quyền xóa, phiên bản entity nếu có `@Version` và các ràng buộc nghiệp vụ trước khi thực hiện. Việc entity tồn tại lúc `find` không bảo đảm không có transaction khác thay đổi nó trước commit.

## 11. Khi quan hệ được lưu qua join table

Không phải mọi `@OneToMany` đều dùng khóa ngoại trên bảng child. Một `@OneToMany` **đơn chiều không khai báo `@JoinColumn`** thường được ánh xạ bằng **join table** theo mặc định JPA.

Ví dụ:

```java
@Entity
public class Project {

    @Id
    @GeneratedValue
    private Long id;

    @OneToMany
    @JoinTable(
        name = "project_documents",
        joinColumns = @JoinColumn(name = "project_id"),
        inverseJoinColumns = @JoinColumn(name = "document_id")
    )
    private List<Document> documents = new ArrayList<>();
}
```

Bảng dữ liệu:

```text
projects               documents
  id                     id
  ...                    filename

project_documents
  project_id   -> projects.id
  document_id  -> documents.id
```

Nếu ứng dụng gỡ một document khỏi `project.documents`, nhưng không có orphan removal và không gọi `em.remove(document)`, thao tác này thường sẽ xóa **hàng liên kết**:

```sql
DELETE FROM project_documents
WHERE project_id = ? AND document_id = ?;
```

**Hàng `documents` vẫn còn**. Trong mô hình này, không có cột `documents.project_id` để đặt `NULL`. Do đó “bỏ liên kết” không nhất thiết luôn tạo `UPDATE FK=NULL`; SQL phụ thuộc nơi quan hệ được lưu.

Nếu `Document` được chia sẻ giữa nhiều project, cấu trúc quan hệ có thể cần xét lại cardinality: thường một quan hệ many-to-many hoặc một entity bảng nối có metadata sẽ phù hợp hơn. Không bật orphan removal trên mối quan hệ có entity con được chia sẻ và cần tồn tại độc lập.

### 11.1. Unidirectional OneToMany với @JoinColumn

JPA cũng hỗ trợ:

```java
@OneToMany
@JoinColumn(name = "project_id")
private List<Document> documents = new ArrayList<>();
```

Trong thiết kế này, bảng `documents` chứa `project_id` và phía parent quản lý collection/association theo mapping đơn chiều. Khi gỡ document mà không có orphan removal, ý nghĩa thường là đặt FK thành null nếu schema cho phép.

Tuy nhiên, số câu SQL và thời điểm cập nhật FK có thể khác so với quan hệ hai chiều `@ManyToOne + mappedBy`; một số provider có thể phải thực hiện lệnh riêng để cập nhật FK. Vì vậy cần quan sát SQL thực tế và tránh áp dụng quy tắc owning side của **mô hình hai chiều** cho mọi `@OneToMany` đơn chiều.

### 11.2. Cách nhận diện nhanh trong code

- Có `@OneToMany(mappedBy = "parent")` và child có `@ManyToOne`: **child thường là phía owning side** và nắm FK.
- Có `@OneToMany @JoinColumn(...)` đơn chiều: collection ở parent tham gia quản lý FK theo mapping.
- Có `@OneToMany @JoinTable(...)` hoặc mapping mặc định tạo join table: liên kết nằm tại bảng phụ.
- Có `orphanRemoval=true`: thao tác gỡ managed child có thể **xóa child entity**, bất kể chi tiết SQL liên kết như thế nào.

## 12. Xóa parent: điều gì xảy ra với các child?

Khi xóa `Department` hoặc `PurchaseOrder`, database phải bảo đảm không còn FK hợp lệ trỏ đến parent bị xóa. Có nhiều cách xử lý khác nhau:

### 12.1. Child tiếp tục tồn tại và FK có thể null

Ví dụ xóa một department nhưng giữ nhân viên. Có thể cần chủ động tháo từng nhân viên:

```java
Department dept = em.find(Department.class, departmentId);

for (Employee employee : new ArrayList<>(dept.getEmployees())) {
    dept.removeEmployee(employee);
}

em.flush(); // Khi cần đồng bộ FK null trước khi xóa parent.
em.remove(dept);
```

Trong trường hợp `employees.department_id` nullable, SQL có thể gồm các `UPDATE` đặt FK null trước rồi `DELETE departments`. Không phải mọi database đều cho phép xóa parent trước khi FK được cập nhật; thứ tự flush và constraint cần được xử lý đúng. `em.flush()` ở đây được dùng có chủ đích để đồng bộ unlink trước khi `em.remove(dept)`, nhưng vẫn chưa phải commit.

**Không** đặt `cascade=REMOVE` cho `Department.employees` nếu nhân viên phải được giữ lại.

### 12.2. Child phải bị xóa cùng parent

Nếu mọi dòng OrderLine đều thuộc vòng đời PurchaseOrder, `cascade=REMOVE` hoặc `orphanRemoval=true` đúng mục đích có thể khiến provider xóa các row child khi `em.remove(order)`. Database FK `NOT NULL` sẽ được bảo vệ thông qua thứ tự và thao tác xóa do provider thực hiện.

### 12.3. Database ON DELETE CASCADE

DDL có thể khai báo:

```sql
FOREIGN KEY (order_id)
REFERENCES purchase_orders(id)
ON DELETE CASCADE
```

Khi database xóa một hàng parent, nó có thể tự xóa các hàng child tương ứng. Đây là **cơ chế của database**, khác với `CascadeType.REMOVE` của JPA:

| Cơ chế | Ai xử lý | Kích hoạt |
|---|---|---|
| `CascadeType.REMOVE` | JPA provider | `EntityManager.remove(parent)`/cascade operation |
| `orphanRemoval=true` | JPA provider | Child bị bỏ khỏi association sở hữu |
| `ON DELETE CASCADE` | Database | Câu lệnh xóa parent ở database |
| `ON DELETE SET NULL` | Database, nếu được hỗ trợ | Câu lệnh xóa parent; FK child được đặt null theo constraint |

**Không nhầm `ON DELETE CASCADE` với orphanRemoval.** Gỡ một child khỏi collection không làm database phát sinh hành động ON DELETE CASCADE nếu **không có lệnh xóa parent**. Ngoài ra, các callback JPA, persistence context và cache có thể không được đồng bộ theo cách mong muốn nếu row bị xóa trực tiếp bởi database; nên chọn chính sách rõ ràng và kiểm tra thực tế với provider.

### 12.4. Điều gì xảy ra với ON DELETE SET NULL?

Nếu schema dùng:

```sql
FOREIGN KEY (department_id)
REFERENCES departments(id)
ON DELETE SET NULL
```

thì khi một department bị xóa **ở database**, các FK liên quan có thể được đặt null tự động. Nó là một cơ chế khác với mã Java `employee.setDepartment(null)`. JPA có thể vẫn giữ managed entity với association cũ trong persistence context nếu database thay đổi ngoài cơ chế tracking thông thường; truy vấn trong context mới sẽ phản ánh trạng thái đã commit.

Không áp dụng `ON DELETE SET NULL` nếu cột `department_id` `NOT NULL`; schema và nghiệp vụ sẽ mâu thuẫn.

## 13. Transaction, flush và rollback

Các thao tác thêm/gỡ liên kết, cập nhật FK và xóa entity đều cần được đặt trong ranh giới transaction phù hợp.

```text
tx.begin()
  |
  +-- load parent và child (managed)
  |
  +-- thực hiện domain operation
  |       remove association
  |       hoặc thay parent
  |       hoặc đánh dấu remove child
  |
  +-- flush theo nhu cầu/provider
  |       UPDATE FK?
  |       DELETE child?
  |       DELETE join row?
  |
  +-- commit()  -> xác nhận kết quả nếu thành công
      rollback() -> hủy các thay đổi chưa commit
```

**Flush không phải commit.** Nếu `em.flush()` phát SQL `DELETE FROM order_lines` nhưng transaction sau đó rollback, bản ghi con có thể xuất hiện trở lại khi đọc từ transaction mới, theo quy tắc database.

### 13.1. Ví dụ rollback khi gặp constraint

Giả sử `order_lines.order_id` `NOT NULL` và không có orphan removal:

```java
tx.begin();
try {
    OrderLine line = em.find(OrderLine.class, lineId);
    line.setOrder(null); // Giả định entity có phương thức mutator.
    em.flush();          // Có thể lỗi constraint.
    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
}
```

Nếu không thể null FK, **không nên “chữa” bằng cách bỏ `flush()`**. Lỗi chỉ bị dời tới lần flush khác hoặc commit. Cần thay đổi hành vi nghiệp vụ: xóa child, gán parent khác hợp lệ hoặc sửa mô hình/schema nếu child thật sự được phép tồn tại độc lập.

Sau một lỗi persistence có thể khiến transaction bị đánh dấu rollback-only, không cố dùng tiếp cùng transaction để xử lý nghiệp vụ khác. Rollback và tạo unit of work mới.

## 14. Spring Data JPA: thao tác tương đương trong @Transactional

Trong ứng dụng Spring, ranh giới transaction thường được đặt ở service:

```java
@Service
public class OrderService {

    private final PurchaseOrderRepository orderRepository;

    public OrderService(PurchaseOrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    @Transactional
    public void removeLine(Long orderId, Long lineId) {
        PurchaseOrder order = orderRepository.findById(orderId)
            .orElseThrow(() -> new IllegalArgumentException(
                "Order not found"));

        OrderLine line = order.getLines().stream()
            .filter(item -> item.getId().equals(lineId))
            .findFirst()
            .orElseThrow(() -> new IllegalArgumentException(
                "Line not found"));

        order.removeLine(line);
    }
}
```

Giả sử `PurchaseOrder`/`OrderLine` dùng mapping `orphanRemoval=true` ở phần 6 và repository là:

```java
public interface PurchaseOrderRepository
        extends JpaRepository<PurchaseOrder, Long> {
}
```

Trong transaction, `order` là entity managed. Khi `removeLine` gỡ child, JPA theo dõi thay đổi collection và áp dụng orphan removal khi flush/commit. Không cần gọi `orderRepository.save(order)` chỉ để “kích hoạt” dirty checking trên managed entity. API có thể vẫn gọi save vì convention dự án, nhưng không nên nhầm save với yêu cầu duy nhất để đồng bộ orphan.

Các import Spring thông dụng: `org.springframework.stereotype.Service`, `org.springframework.transaction.annotation.Transactional`, `org.springframework.data.jpa.repository.JpaRepository`.

Trong `@Transactional` do Spring quản lý, **không dùng `em.getTransaction().begin()/commit()`** để tự điều khiển một resource-local transaction bên trong service. Quản lý transaction là trách nhiệm của Spring transaction manager trong cấu hình đó.

### 14.1. Nếu repository gọi deleteById thì sao?

`repository.deleteById(lineId)` là yêu cầu xóa entity/bản ghi theo cơ chế repository; nó **khác** với `order.getLines().remove(line)` khi không có orphanRemoval.

Trong mô hình hai chiều, xóa trực tiếp child mà không cập nhật collection đã load có thể khiến object graph của transaction hiện tại **tạm thời vẫn hiển thị child cũ**. Vì vậy nên đặt thao tác xóa vào service và quản lý state của aggregate nhất quán.

Không tự động gọi `deleteById` khi yêu cầu chỉ là “tháo liên kết và vẫn giữ child”, bởi đó là hành động phá hủy bản ghi.

## 15. Bulk JPQL/SQL không đi qua cơ chế orphanRemoval thông thường

Ví dụ:

```java
int count = em.createQuery(
    "update Employee e set e.department = null " +
    "where e.department.id = :departmentId")
    .setParameter("departmentId", departmentId)
    .executeUpdate();
```

Đây là **bulk update**. JPA bulk JPQL tác động trực tiếp lên database và **không đồng bộ từng managed entity như các thao tác thay đổi object bình thường**. Nó cũng không kích hoạt orphan removal hay entity lifecycle callback theo cùng con đường xử lý entity.

Tương tự:

```java
em.createQuery(
    "delete from OrderLine l where l.order.id = :orderId")
    .setParameter("orderId", orderId)
    .executeUpdate();
```

Bulk delete có thể vượt qua những cơ chế cascade/collection tracking ở mức entity. Nếu trong persistence context đang có `Order` với `lines` đã load, collection đó có thể **stale** sau bulk operation. Một số chiến lược ứng dụng gồm flush trước bulk, clear context sau bulk, chạy bulk ở unit of work riêng và đọc lại từ database khi cần.

Bulk query có thể phù hợp để xử lý dữ liệu lớn, nhưng **không thay thế thao tác domain** khi cần invariant, lifecycle callback, optimistic locking hoặc orphan removal cho từng child.

## 16. Các sai lầm thường gặp

### 16.1. Cho rằng tên phương thức remove có nghĩa xóa DB

```java
order.getLines().remove(line);
```

`List.remove` chỉ là thao tác collection. Kết quả persistence tùy mapping. Muốn gỡ FK hay xóa row phải hiểu owning side và orphan removal.

### 16.2. Chỉ sửa phía inverse

```java
department.getEmployees().remove(employee);
// employee.department vẫn giữ department cũ.
```

Với quan hệ hai chiều mà child nắm FK, cách này không tạo object graph nhất quán. Nên dùng helper cập nhật cả hai phía.

### 16.3. Bật orphanRemoval cho dữ liệu có lifecycle độc lập

```java
@OneToMany(mappedBy = "department", orphanRemoval = true)
private List<Employee> employees;
```

Nếu Employee cần tồn tại khi chuyển bộ phận hoặc nghỉ việc, orphanRemoval có thể xóa nhầm hàng. Chỉ dùng khi child thực sự thuộc ownership của parent.

### 16.4. Nghĩ orphanRemoval và CascadeType.REMOVE là một

- `CascadeType.REMOVE` được kích hoạt bởi thao tác remove trên parent.
- `orphanRemoval` được kích hoạt bởi việc child bị gỡ khỏi association owned.

Hai tính năng có thể đi cùng nhau, nhưng phải chọn dựa vào nghiệp vụ.

### 16.5. Cố đặt FK null trong cột NOT NULL

```sql
UPDATE order_lines SET order_id = NULL WHERE id = 10;
```

Nếu `order_id` `NOT NULL`, database sẽ từ chối. Không bỏ constraint để che lỗi mô hình nếu OrderLine không được phép tồn tại độc lập.

### 16.6. Dùng orphanRemoval để chuyển con từ parent này sang parent khác

Đây có thể là một thao tác xóa orphan thay vì chuyển owner, và không được đặc tả bảo đảm portable. Nếu chuyển owner là nghiệp vụ bình thường, chọn mô hình không orphan hoặc quy trình tạo mới phù hợp.

### 16.7. Xóa parent nhưng quên các FK con

Với `department_id` `NOT NULL` và không có cascade, xóa Department đang có Employee thường sẽ bị database từ chối vì FK. Cần chính sách rõ: chuyển child, tháo liên kết nếu nullable hoặc xóa child theo ownership.

### 16.8. Nghĩ `CascadeType.ALL` luôn vô hại

`ALL` bao gồm REMOVE. Nếu một parent sở hữu reference đến child dùng chung, xóa parent có thể kéo theo xóa child mà thành phần khác còn sử dụng. Cascade là quy tắc lifecycle, không phải annotation “cho tiện”.

### 16.9. Không đồng bộ collection khi xóa child trực tiếp

`em.remove(child)` có thể xóa row nhưng collection parent đã load vẫn còn tham chiếu child. Trong cùng transaction, object graph gây nhầm lẫn. Nên cung cấp domain helper hoặc tổ chức thao tác nhất quán.

### 16.10. Kiểm tra sau commit trong cùng persistence context

Nếu muốn biết row còn tồn tại ở database, việc nhìn một entity managed/cached trong cùng context không phải bằng chứng chắc chắn. Hãy commit, mở `EntityManager` mới rồi `find` theo ID; hoặc dùng SQL từ một kết nối/transaction mới phù hợp.

### 16.11. Nhầm quan hệ một-nhiều qua join table với FK trên child

Khi quan hệ nằm trong bảng nối, gỡ liên kết thường xóa hàng ở bảng nối. Không có cột child FK để đặt null. Xem DDL thực tế thay vì suy luận chỉ từ `@OneToMany`.

## 17. Bảng phân tích trước khi viết remove()

Để thiết kế một phương thức như `removeChild`, hãy lần lượt trả lời:

| Câu hỏi | Tác động đến thiết kế |
|---|---|
| Child có cần tồn tại độc lập khi rời parent không? | Có: gỡ FK/chuyển owner; không: cân nhắc orphan removal |
| Association có lưu qua FK trên child hay join table? | Quyết định `UPDATE FK` hay `DELETE` hàng bảng nối |
| FK có cho phép `NULL` không? | Nếu không, không thực hiện unlink-to-null |
| Phía nào là owning side? | Cần sửa tham chiếu/collection nào để JPA ghi đúng |
| Hai phía object graph có được đồng bộ không? | Tránh trạng thái mâu thuẫn trong bộ nhớ |
| Child có được dùng chung bởi parent khác không? | Nếu có, không xóa dây chuyền tùy tiện |
| Parent bị xóa thì child phải ra sao? | Chọn cascade remove, FK null, chuyển owner hoặc DB cascade |
| Có transaction và rollback rõ ràng không? | Bảo đảm thay đổi liên quan thành công/thất bại cùng nhau |
| Có hoạt động bulk SQL/JPQL không? | Cần xử lý persistence context stale và thiếu callbacks |
| Cần giữ audit/history không? | Có thể phải soft delete hoặc lưu snapshot, không phải xóa vật lý |

Một tên phương thức domain tốt diễn đạt **ý nghĩa kinh doanh**, chẳng hạn `unassignEmployee`, `transferEmployee` hoặc `removeOrderLine`. Ba thao tác này không nên dùng chung một implementation chỉ vì đều có chữ “remove”.

## 18. Bài thực hành: quan sát UPDATE và DELETE

Hãy dùng database học tập H2/PostgreSQL và JPA provider tương thích. Bật SQL logging để quan sát những câu lệnh được phát. Có thể thực hành bằng JPA thuần với `EntityManager`/`EntityTransaction`, hoặc Spring Data JPA với `@Transactional`.

### Phần A — Child vẫn tồn tại khi gỡ liên kết

1. Tạo bảng `departments` và `employees` với `department_id NULL` được phép.
2. Persist Department A và Employee An, Binh thuộc A.
3. Commit, mở persistence context mới, tải Department A.
4. Gọi helper `department.removeEmployee(an)`.
5. Commit và đọc lại từ context mới.
6. Ghi nhận câu SQL cập nhật FK, số hàng employee và `department_id` của An.
7. Chuyển Binh từ A sang B, xem FK đổi sang ID của B mà không mất hàng.

Kỳ vọng: **Employee vẫn tồn tại**, chỉ quan hệ thay đổi.

### Phần B — Điều gì xảy ra nếu không sửa owning side?

1. Tải Department A và Employee Binh.
2. Chỉ xóa Binh khỏi collection `Department.employees` bằng cách truy cập collection trong code thử nghiệm.
3. Không gọi `employee.assignDepartment(null)`.
4. Flush/commit, mở context mới và kiểm tra `employees.department_id`.
5. Giải thích tại sao phía inverse không quyết định trực tiếp FK khi `orphanRemoval=false`.

Với thiết kế helper ở phần 4, getter trả collection không sửa được. Bài thực hành này yêu cầu tạo một **biến thể thử nghiệm riêng** cho phép thao tác collection trực tiếp để quan sát lỗi, không nên giữ API đó trong domain production.

### Phần C — FK NOT NULL

1. Đổi schema `employees.department_id` thành `NOT NULL` trong database thử nghiệm.
2. Thử đặt owning association thành `null` rồi flush.
3. Quan sát exception hoặc constraint violation.
4. Sửa use case theo một trong các phương án hợp lệ: chuyển nhân viên sang department khác hoặc xóa bản ghi nếu nghiệp vụ cho phép.

Giải thích vì sao bỏ `em.flush()` không xử lý được bản chất lỗi.

### Phần D — orphanRemoval=true

1. Tạo PurchaseOrder có hai OrderLine, commit.
2. Trong transaction mới, tải Order và collection lines.
3. Gọi `order.removeLine(firstLine)`.
4. Flush/commit.
5. Mở context mới: `em.find(OrderLine.class, firstLineId)` trả gì?
6. Kiểm tra parent vẫn tồn tại và line còn lại không đổi.

Kỳ vọng với child managed hợp lệ: bản ghi firstLine bị **DELETE**, không còn row orphan trong bảng `order_lines`.

### Phần E — CascadeType.REMOVE

1. Tạo PurchaseOrder có hai OrderLine với mapping cascade remove thích hợp.
2. Gọi `em.remove(order)`.
3. Commit, kiểm tra cả parent và children bằng context mới.
4. So sánh với việc **chỉ gỡ một line khỏi collection** khi không có orphanRemoval.
5. Giải thích hai loại trigger khác nhau.

### Phần F — Join table

1. Tạo Project/Document với bảng `project_documents`.
2. Gỡ một Document khỏi collection Project khi không có orphanRemoval.
3. Commit.
4. Kiểm tra bảng nối và bảng `documents`.
5. Giải thích vì sao bản ghi Document vẫn tồn tại và không có `documents.project_id` để đặt null.

### Phần G — Rollback

1. Bắt đầu transaction và gỡ một OrderLine với orphan removal.
2. `flush()` để quan sát SQL.
3. `rollback()`.
4. Mở context mới và kiểm tra lại row.
5. Giải thích sự khác nhau giữa SQL đã thực thi trong transaction và dữ liệu đã commit.

### Bảng ghi nhận thực nghiệm

| Thao tác | Cột FK có thể NULL? | orphanRemoval | SQL có ý nghĩa gì? | Row child còn sau commit? |
|---|---|---|---|---|
| Unassign Employee | Có | false | `UPDATE FK = NULL` | Có |
| Transfer Employee | Có/Không | false | `UPDATE FK = new_parent_id` | Có |
| Gỡ Employee, chỉ inverse side | Có | false | Không bảo đảm cập nhật FK | Thường còn |
| Gỡ OrderLine | Không | true | `DELETE child` | Không |
| Xóa Order có cascade remove | Không | tùy mapping | `DELETE children` và parent | Không |
| Gỡ Document khỏi join table | Không áp dụng ở child | false | `DELETE join row` | Có |
| Gỡ child rồi rollback | Tùy | true | SQL có thể chạy nhưng rollback | Hàng được khôi phục theo transaction |

Thời điểm và số lượng statement cần **quan sát** trên stack đang dùng. Bảng này ghi **ý nghĩa của kết quả**, không cam kết cú pháp SQL chính xác hay một lệnh duy nhất ở mọi provider.
