# Ánh xạ OneToMany đơn hướng qua cột khóa ngoại hoặc bảng liên kết

## 1. OneToMany đơn hướng là quan hệ gì?

Trong Jakarta Persistence (JPA), `@OneToMany` biểu diễn mối quan hệ **một entity nguồn tham chiếu tới nhiều entity đích**. Khi quan hệ **đơn hướng (unidirectional)**, chỉ lớp nguồn giữ thuộc tính collection; lớp đích không có thuộc tính Java tham chiếu ngược về lớp nguồn.

Ví dụ, một `PurchaseOrder` chứa nhiều `OrderLine`:

```text
Mô hình đối tượng Java

PurchaseOrder
  id = 42
  lines ─────────────┬─────> OrderLine(id=501, sku="KEYBOARD")
                     └─────> OrderLine(id=502, sku="MOUSE")

OrderLine không khai báo field PurchaseOrder order.
```

Ở phía Java, ta có:

```java
@Entity
public class PurchaseOrder {

    @Id
    private Long id;

    @OneToMany
    private List<OrderLine> lines = new ArrayList<>();
}
```

và:

```java
@Entity
public class OrderLine {

    @Id
    private Long id;

    private String sku;
}
```

Quan hệ này là **đơn hướng** vì chỉ có đường truy cập `order.getLines()`. Không thể gọi `line.getOrder()` nếu lớp `OrderLine` không tự khai báo quan hệ ngược.

Điểm dễ nhầm là **đơn hướng chỉ mô tả mô hình Java, chưa quyết định cấu trúc SQL**. Cùng một collection `@OneToMany` có thể được lưu bằng:

1. **Khóa ngoại tại bảng đích**: bảng `order_lines` có cột `purchase_order_id`.
2. **Bảng liên kết riêng**: bảng `purchase_order_line_links` giữ cặp `(purchase_order_id, order_line_id)`, còn bảng `order_lines` không cần cột FK về đơn hàng.

Hai cách có cùng hướng điều hướng trong Java nhưng khác **schema, SQL ghi liên kết, ràng buộc và chi phí vận hành**.

## 2. Hai mô hình quan hệ trong cơ sở dữ liệu

### 2.1. Phương án A: khóa ngoại nằm ở bảng con

```text
purchase_orders                  order_lines
+----+----------------+          +-----+-------------------+----------+
| id | status         |          | id  | purchase_order_id | sku      |
+----+----------------+          +-----+-------------------+----------+
| 42 | DRAFT          | <--------| 501 |                42 | KEYBOARD |
|    |                | <--------| 502 |                42 | MOUSE    |
+----+----------------+          +-----+-------------------+----------+
       PK                                       FK -> purchase_orders.id
```

Ví dụ DDL PostgreSQL:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(24) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    purchase_order_id BIGINT NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (purchase_order_id)
        REFERENCES purchase_orders(id)
);

CREATE INDEX ix_order_lines_purchase_order_id
    ON order_lines(purchase_order_id);
```

Với mô hình này, mỗi `OrderLine` chỉ liên kết tới **tối đa một** `PurchaseOrder` vì trên mỗi hàng con chỉ có một giá trị `purchase_order_id`. Nếu cột là `NOT NULL`, mỗi dòng hàng phải thuộc về một đơn hàng hợp lệ sau khi transaction hoàn tất.

Khi ứng dụng cần đọc tất cả dòng hàng của đơn 42, SQL có thể là:

```sql
SELECT id, purchase_order_id, sku, quantity
FROM order_lines
WHERE purchase_order_id = 42;
```

**Ưu điểm:** không cần bảng liên kết bổ sung; truy vấn theo FK đơn giản và index dễ dự đoán. **Đánh đổi:** mọi lần gỡ hoặc chuyển liên kết phải sửa cột FK trên chính hàng con; ràng buộc `NOT NULL` có thể làm thao tác “gỡ nhưng vẫn giữ con” không hợp lệ.

### 2.2. Phương án B: dùng bảng liên kết riêng

```text
purchase_orders         purchase_order_line_links          order_lines
+----+----------+       +-------------------+--------------+ +-----+----------+
| id | status   |       | purchase_order_id | order_line_id| | id  | sku      |
+----+----------+       +-------------------+--------------+ +-----+----------+
| 42 | DRAFT    | <-----| 42                | 501          |-| 501 | KEYBOARD |
|    |          | <-----| 42                | 502          |-| 502 | MOUSE    |
+----+----------+       +-------------------+--------------+ +-----+----------+
```

Ví dụ DDL:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(24) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL
);

CREATE TABLE purchase_order_line_links (
    purchase_order_id BIGINT NOT NULL,
    order_line_id BIGINT NOT NULL,
    CONSTRAINT pk_purchase_order_line_links
        PRIMARY KEY (purchase_order_id, order_line_id),
    CONSTRAINT uq_order_line_owner
        UNIQUE (order_line_id),
    CONSTRAINT fk_line_link_order
        FOREIGN KEY (purchase_order_id)
        REFERENCES purchase_orders(id),
    CONSTRAINT fk_line_link_line
        FOREIGN KEY (order_line_id)
        REFERENCES order_lines(id)
);
```

Điểm quan trọng là ràng buộc **`UNIQUE(order_line_id)`**: một dòng hàng không thể được gán cho hai đơn khác nhau qua bảng nối. Nếu bỏ ràng buộc này, schema có thể cho phép nhiều đơn cùng liên kết một dòng, mang ý nghĩa gần với nhiều-nhiều dù phía Java dùng `@OneToMany`. Một số provider có thể tạo unique constraint theo metadata; với schema quản lý bằng migration, phải xác nhận constraint thực tồn tại.

Khi đọc các dòng của đơn 42, truy vấn phải đi qua bảng nối:

```sql
SELECT l.id, l.sku, l.quantity
FROM order_lines l
JOIN purchase_order_line_links link
  ON link.order_line_id = l.id
WHERE link.purchase_order_id = 42;
```

Gỡ một dòng ra khỏi đơn có thể chỉ xóa **hàng liên kết**:

```sql
DELETE FROM purchase_order_line_links
WHERE purchase_order_id = 42
  AND order_line_id = 501;
```

Lúc này `order_lines.id = 501` vẫn có thể tồn tại, trừ khi ứng dụng còn yêu cầu xóa entity đích, chẳng hạn qua `orphanRemoval` hoặc thao tác `remove`.

### 2.3. Đối chiếu ý nghĩa

| Tiêu chí | FK trong bảng con | Bảng liên kết |
|---|---|---|
| Vị trí lưu quan hệ | `order_lines.purchase_order_id` | `purchase_order_line_links(order_id, line_id)` |
| Số bảng cho một entity cha và một entity con | 2 | 3 |
| Đọc các con theo cha | Lọc FK trên bảng con | JOIN bảng nối và bảng con |
| Gỡ con nhưng vẫn giữ hàng con | `UPDATE child SET parent_id=NULL` nếu cho phép | `DELETE` hàng nối |
| Chuyển con sang cha khác | `UPDATE` FK trên hàng con | Thay cặp liên kết trong bảng nối |
| Child không có cha | FK `NULL` nếu schema cho phép | Không có hàng liên kết |
| Ràng buộc child tối đa một cha | Tự nhiên từ một cột FK đơn | Cần bảo đảm unique theo `child_id` |
| Chi phí SQL/DDL | Ít bảng, cấu trúc trực tiếp | Thêm JOIN, bảng/index và ghi hàng liên kết |
| Có thể giữ bảng child độc lập khỏi association | Khó hơn nếu child schema thuộc quyền một quan hệ | Có, association nằm ở bảng riêng |
| Khai báo JPA tiêu biểu | `@OneToMany` + `@JoinColumn` | `@OneToMany` + `@JoinTable` hoặc mapping mặc định |

**Không nên chọn một phương án chỉ theo số annotation.** Cần xét quyền sở hữu dữ liệu, thao tác gỡ/chuyển liên kết, yêu cầu FK, cấu trúc schema đang tồn tại và mô hình nghiệp vụ.

## 3. Ánh xạ OneToMany đơn hướng qua cột khóa ngoại

### 3.1. Hai entity và một collection

Ví dụ Java dùng Jakarta Persistence và field access, với một `PurchaseOrder` là nguồn và `OrderLine` là đích.

**`OrderLine.java`**

```java
package com.example.shop.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "order_lines")
public class OrderLine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 80)
    private String sku;

    @Column(nullable = false)
    private int quantity;

    protected OrderLine() {
        // JPA sử dụng constructor không tham số.
    }

    public OrderLine(String sku, int quantity) {
        if (sku == null || sku.isBlank() || quantity <= 0) {
            throw new IllegalArgumentException("SKU và số lượng không hợp lệ");
        }
        this.sku = sku;
        this.quantity = quantity;
    }

    public Long getId() {
        return id;
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }

    public void changeQuantity(int newQuantity) {
        if (newQuantity <= 0) {
            throw new IllegalArgumentException("Số lượng phải dương");
        }
        this.quantity = newQuantity;
    }
}
```

Lưu ý rằng **`OrderLine` không có field `PurchaseOrder order`** và cũng không có `@ManyToOne`: đây là yêu cầu quan trọng của ví dụ đơn hướng.

**`PurchaseOrder.java`**

```java
package com.example.shop.domain;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 24)
    private String status = "DRAFT";

    @OneToMany(
        cascade = CascadeType.PERSIST,
        orphanRemoval = true
    )
    @JoinColumn(name = "purchase_order_id")
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public void addLine(OrderLine line) {
        if (line == null) {
            throw new IllegalArgumentException("Dòng hàng không được null");
        }
        lines.add(line);
    }

    public void removeLine(OrderLine line) {
        lines.remove(line);
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }

    public Long getId() {
        return id;
    }
}
```

Giải thích:

- `@OneToMany` cho JPA biết `lines` là collection những **entity `OrderLine`**, không phải tập hợp giá trị basic.
- **Không có `mappedBy`**. Đây là quan hệ đơn hướng; `PurchaseOrder.lines` là phía sở hữu liên kết theo mô hình mapping này.
- `@JoinColumn(name = "purchase_order_id")` đặt FK **ở bảng `order_lines`**, dù `@JoinColumn` được viết trên field của `PurchaseOrder`.
- `cascade = PERSIST` lan truyền thao tác persist từ đơn hàng tới những line mới khi phù hợp, giúp tạo cha cùng con trong một đơn vị công việc.
- `orphanRemoval = true` biểu diễn yêu cầu nghiệp vụ rằng dòng bị gỡ khỏi order thì **không tồn tại độc lập**. Việc gỡ khỏi list có thể dẫn tới xóa entity con tại flush.
- `getLines()` trả về view chỉ đọc để người gọi thực hiện thay đổi qua `addLine`/`removeLine`. Bản thân JPA vẫn quản lý field collection.

Trong trường hợp **chỉ muốn cập nhật liên kết và giữ nguyên line sau khi gỡ**, cần bỏ `orphanRemoval = true` và bảo đảm schema có thể cho phép line không có order, hoặc sử dụng mô hình bảng liên kết. Không nên sao chép cấu hình orphanRemoval nếu domain có nhu cầu chuyển line giữa các đơn hàng.

### 3.2. Vì sao `@JoinColumn` đặt trên cha nhưng FK nằm ở con?

`@JoinColumn` mô tả cột SQL dùng để nối hai bảng. Với **unidirectional OneToMany có FK**, cột đó nằm trong **target table** vì một hàng con lưu khóa của hàng cha.

```text
PurchaseOrder.java
    @OneToMany
    @JoinColumn(name="purchase_order_id")
    List<OrderLine> lines;
               |
               | ánh xạ
               v
order_lines.purchase_order_id
               |
               +---- FOREIGN KEY --> purchase_orders.id
```

Không cần thêm field `Long purchaseOrderId` vào `OrderLine` chỉ để JPA biết FK. Nếu ứng dụng tự khai báo cả field scalar và quan hệ tới cùng một cột mà không thiết kế rõ writable mapping, có thể gặp lỗi “repeated column” hoặc trạng thái hai thuộc tính không đồng bộ. Đối với ví dụ này, **JPA quản lý FK thông qua collection**.

### 3.3. Có thể dùng `nullable=false` không?

Nếu schema yêu cầu mọi line luôn thuộc một order, ta muốn FK `NOT NULL`:

```java
@OneToMany(cascade = CascadeType.PERSIST, orphanRemoval = true)
@JoinColumn(name = "purchase_order_id", nullable = false)
private List<OrderLine> lines = new ArrayList<>();
```

Tuy nhiên, với **unidirectional OneToMany qua FK**, cách provider phát SQL khi tạo cha và con có thể gồm `INSERT` line rồi `UPDATE` FK, hoặc một chuỗi lệnh tối ưu khác. Nếu schema `NOT NULL` mà provider thực hiện INSERT line lúc FK chưa có, thao tác có thể thất bại; các provider và phiên bản không bắt buộc phải tạo cùng chuỗi SQL.

Điều cần đánh giá là **tính tương thích thực tế giữa chiến lược sinh khóa, thứ tự INSERT/UPDATE, trạng thái nullability và SQL do provider sinh ra**. Trong một số trường hợp, chuyển sang mô hình **hai chiều với `@ManyToOne` sở hữu FK** hoặc đổi thiết kế nguồn lưu trữ sẽ làm thao tác ghi dễ kiểm soát hơn.

Không nên chỉ bỏ ràng buộc `NOT NULL` ở production để “cho ORM chạy” nếu nghiệp vụ thực sự yêu cầu line phải có order. Khi đó phải chọn mapping và kế hoạch ghi dữ liệu thực thi được ràng buộc.

## 4. Ánh xạ OneToMany đơn hướng qua bảng liên kết

### 4.1. Khai báo `@JoinTable` tường minh

Giữ nguyên lớp `OrderLine` ở trên, nhưng dùng một **phương án mapping thay thế** cho collection của `PurchaseOrder`:

```java
@OneToMany(
    cascade = CascadeType.PERSIST,
    orphanRemoval = false
)
@JoinTable(
    name = "purchase_order_line_links",
    joinColumns = @JoinColumn(
        name = "purchase_order_id",
        referencedColumnName = "id"
    ),
    inverseJoinColumns = @JoinColumn(
        name = "order_line_id",
        referencedColumnName = "id",
        unique = true
    )
)
private List<OrderLine> lines = new ArrayList<>();
```

Các import liên quan:

```java
import jakarta.persistence.CascadeType;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.JoinTable;
import jakarta.persistence.OneToMany;
```

Cách đọc:

- `@JoinTable(name = ...)` chỉ định **bảng chứa các cặp liên kết**, không phải bảng entity `OrderLine`.
- `joinColumns` chỉ cột FK trong bảng nối **trỏ về nguồn** `PurchaseOrder`.
- `inverseJoinColumns` chỉ cột FK trong bảng nối **trỏ tới đích** `OrderLine`.
- `unique = true` ở FK của đích mô tả yêu cầu một line chỉ liên kết một order qua bảng này. Trong môi trường migration, đặt unique constraint thực trong schema để bảo đảm.
- `orphanRemoval = false` cho phép minh họa rõ ý nghĩa **gỡ một liên kết nhưng không tự xóa entity line**.

Các annotation ở hai phương án **không phải dùng chung trên cùng một field**. Chọn `@JoinColumn` cho FK trực tiếp **hoặc** `@JoinTable` cho bảng nối; đừng lắp cả hai để thử “ưu tiên cách nào” mà không có lý do cụ thể.

### 4.2. Mặc định JPA khi không khai báo `@JoinColumn` hoặc `@JoinTable`

Với một `@OneToMany` **đơn hướng** và không khai báo cách lưu association bằng FK, mô hình JPA mặc định thường dùng **join table**, với tên bảng và tên cột được suy ra theo quy tắc mặc định của provider/spec:

```java
@OneToMany
private List<OrderLine> lines = new ArrayList<>();
```

Nhưng **không nên dựa vào tên bảng/cột suy ra** khi đã có schema legacy, migration hoặc yêu cầu naming ổn định. Khai báo `@JoinTable` với tên rõ ràng giúp SQL và DDL dễ đối chiếu. Nếu dự án dùng một naming strategy riêng (ví dụ Hibernate/Spring Boot), tên vật lý có thể chịu ảnh hưởng của strategy đó.

Điểm cần nhớ: **`@OneToMany` không mặc nhiên đặt FK trong bảng đích**. Nếu muốn dùng FK trực tiếp trong quan hệ đơn hướng, phải thể hiện cấu hình phù hợp, điển hình `@JoinColumn`.

### 4.3. Vì sao vẫn là OneToMany dù có join table?

Sự có mặt của bảng nối **không tự biến quan hệ thành `@ManyToMany`**. Khác biệt nằm ở cardinality và constraint:

```text
ONE-TO-MANY qua join table

purchase_order_id    order_line_id
         42                 501
         42                 502
         43                 503

UNIQUE(order_line_id) => line 501 chỉ thuộc tối đa một order.


MANY-TO-MANY qua join table

student_id           course_id
    1                   10
    2                   10     (cùng course 10 có nhiều student)
    2                   11

UNIQUE(student_id, course_id) ngăn trùng cặp,
nhưng course_id riêng lẻ không unique.
```

Với one-to-many, một parent có nhiều child, một child thuộc tối đa một parent thông qua association đó. Với many-to-many, một child có thể được chia sẻ bởi nhiều parent. Khi nhìn vào schema, hãy kiểm tra **unique trên FK của child ở bảng nối** và các quy tắc liên quan, không chỉ nhìn số lượng bảng.

## 5. Thêm và đọc entity trong hai mô hình

### 5.1. Tạo order cùng các line

Giả sử `PurchaseOrder` và `OrderLine` đều là entity mới, `PurchaseOrder.lines` có `cascade=PERSIST`:

```java
PurchaseOrder order = new PurchaseOrder();
order.addLine(new OrderLine("KEYBOARD", 1));
order.addLine(new OrderLine("MOUSE", 2));

EntityTransaction tx = em.getTransaction();
tx.begin();
try {
    em.persist(order);
    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
}
```

Đoạn mã minh họa Java SE với `EntityManager` mở và transaction `RESOURCE_LOCAL`. Trong Jakarta EE hoặc Spring, giao dịch có thể do runtime quản lý.

Cùng một đoạn Java có thể sinh những dạng SQL khác nhau:

**FK trong bảng con:**

```sql
INSERT INTO purchase_orders (status) VALUES ('DRAFT');
INSERT INTO order_lines (sku, quantity, purchase_order_id)
VALUES ('KEYBOARD', 1, 42);
INSERT INTO order_lines (sku, quantity, purchase_order_id)
VALUES ('MOUSE', 2, 42);
```

Provider cũng có thể phát `INSERT` con rồi `UPDATE` FK; các câu trên là **SQL diễn giải kết quả mong muốn**, không phải cam kết câu lệnh đúng thứ tự từ mọi JPA provider.

**Bảng liên kết:**

```sql
INSERT INTO purchase_orders (status) VALUES ('DRAFT');

INSERT INTO order_lines (sku, quantity)
VALUES ('KEYBOARD', 1);
INSERT INTO order_lines (sku, quantity)
VALUES ('MOUSE', 2);

INSERT INTO purchase_order_line_links (
    purchase_order_id, order_line_id
) VALUES (42, 501);

INSERT INTO purchase_order_line_links (
    purchase_order_id, order_line_id
) VALUES (42, 502);
```

Các ID `42`, `501` và `502` chỉ là minh họa. Mã Java dùng `@GeneratedValue` nên giá trị thật do database/provider cấp. Bảng liên kết làm tăng số thao tác ghi nhưng tách riêng việc **tạo entity con** khỏi việc **gắn association**.

### 5.2. Đọc collection và lazy loading

Đối với `@OneToMany`, fetch mặc định là **`LAZY`** theo JPA. Khi truy vấn `PurchaseOrder`, collection có thể chưa được nạp:

```java
PurchaseOrder order = em.find(PurchaseOrder.class, 42L);

// Việc dùng collection có thể phát SQL để tải các line.
int count = order.getLines().size();
```

Tùy provider, đường truy vấn có thể là:

**FK trực tiếp:**

```sql
SELECT *
FROM order_lines
WHERE purchase_order_id = 42;
```

**Join table:**

```sql
SELECT l.*
FROM purchase_order_line_links link
JOIN order_lines l ON l.id = link.order_line_id
WHERE link.purchase_order_id = 42;
```

Cần hiểu rằng `LAZY` là **gợi ý/hợp đồng fetch** của JPA theo semantics tương ứng, không phải bảo đảm rằng mọi thao tác đọc kích thước collection luôn tạo đúng một câu SQL cụ thể. Hành vi còn tùy provider, cache và fetch plan.

Nếu service nạp hàng trăm order rồi lần lượt đọc `getLines()`, cả hai mô hình có thể gặp **N+1**. Sự tồn tại của một join table hay FK trực tiếp không tự giải quyết vấn đề fetch. Nên chọn truy vấn theo use case: projection, batch fetching, entity graph, join fetch có kiểm soát và phân trang phù hợp.

### 5.3. Tìm OrderLine không có đường truy cập ngược

Vì entity con không có field `order`, không thể viết JPQL chuẩn dưới dạng:

```jpql
select l
from OrderLine l
where l.order.id = :orderId
```

`l.order` không tồn tại trong mô hình Java. Có thể truy cập collection từ entity cha:

```jpql
select l
from PurchaseOrder o join o.lines l
where o.id = :orderId
```

Hoặc viết SQL trực tiếp khi cần lọc theo FK hoặc join table. **Một cột FK nằm trong database không tự tạo thuộc tính Java tương ứng trong lớp đích.**

Đây là một đánh đổi quan trọng: đơn hướng đơn giản khi chỉ cần điều hướng **cha → các con**, nhưng nếu nghiệp vụ thường cần **con → cha**, quan hệ hai chiều có `@ManyToOne` ở con có thể biểu diễn domain thuận tiện hơn.

## 6. Thay đổi collection: thêm, gỡ và chuyển liên kết

### 6.1. Thêm một con đã tồn tại

Nếu một `OrderLine` đã được lưu và chưa thuộc order nào theo schema, ta có thể thêm vào collection của order đã managed:

```java
PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
OrderLine line = em.find(OrderLine.class, lineId);

if (order == null || line == null) {
    throw new IllegalArgumentException("Không tìm thấy dữ liệu");
}
order.addLine(line);
```

Khi flush:

- **FK trực tiếp:** JPA có thể cập nhật `order_lines.purchase_order_id`.
- **Join table:** JPA có thể chèn một row vào bảng liên kết.

Nếu line đã thuộc order khác, unique constraint/semantics “một con tối đa một cha” phải được giữ. Với FK trực tiếp, chuyển chủ là đổi giá trị FK; với join table, cần đảm bảo hàng nối cũ được gỡ trước hoặc đồng thời với hàng mới theo cách không vi phạm unique constraint.

### 6.2. Gỡ con mà vẫn muốn giữ con

Giả sử nghiệp vụ chỉ muốn bỏ line khỏi danh sách nhưng giữ bản ghi line để phục hồi hoặc chuyển chủ:

```java
order.removeLine(line);
```

Điều kiện để thao tác có ý nghĩa “chỉ gỡ liên kết”:

- **Không bật `orphanRemoval=true`** trên association đó.
- Nếu dùng FK trực tiếp, cột `purchase_order_id` phải **cho phép null**, hoặc phải gán một owner khác phù hợp thay vì để orphan.
- Nếu dùng join table, xóa hàng nối vẫn có thể giữ row con nguyên vẹn.

Mô tả SQL:

```sql
-- FK trực tiếp, khi cột cho phép null:
UPDATE order_lines
SET purchase_order_id = NULL
WHERE id = 501;

-- Bảng liên kết:
DELETE FROM purchase_order_line_links
WHERE purchase_order_id = 42
  AND order_line_id = 501;
```

Đừng nhầm rằng lệnh `List.remove` luôn xóa dòng hàng. Nó chỉ thay đổi collection Java; tác động đến database phụ thuộc association mapping, trạng thái managed, orphan removal, cascade và transaction.

### 6.3. Gỡ con và xóa luôn con

Nếu line chỉ có ý nghĩa khi còn thuộc order, cấu hình `orphanRemoval=true` là một cách thể hiện lifecycle ownership:

```java
@OneToMany(orphanRemoval = true)
@JoinColumn(name = "purchase_order_id")
private List<OrderLine> lines = new ArrayList<>();
```

Khi gỡ một line được quản lý khỏi collection, JPA có thể đánh dấu line đó để xóa vào thời điểm flush. Với bảng liên kết, provider phải xử lý cả row liên kết lẫn row entity con sao cho tôn trọng FK.

Đây không chỉ là thay đổi association: nó **gắn thay đổi liên kết với việc xóa entity đích**. Chỉ dùng khi domain thật sự muốn xóa line, và lưu ý semantics của orphan removal không dành cho thao tác tự do “gỡ ở cha A rồi gắn ngay sang cha B”. Nếu cần chuyển owner thường xuyên, không nên dựa vào cách đó.

### 6.4. Chuyển con từ cha A sang cha B

**FK trực tiếp, không orphan removal:** thường về mặt dữ liệu chỉ cần:

```sql
UPDATE order_lines
SET purchase_order_id = :newOrderId
WHERE id = :lineId;
```

Nhưng ở Java, hai collection `oldOrder.lines` và `newOrder.lines` có thể đều đang được quản lý. Cần cập nhật một cách nhất quán, tránh để cùng line nằm trong cả hai collection. Khi flush, provider có thể phát SQL riêng cho việc remove và add; **thứ tự và số lần UPDATE không phải bất biến của JPA**. Nếu có yêu cầu chuyển owner thường xuyên và FK `NOT NULL`, quan hệ hai chiều với owning `@ManyToOne` ở child thường có thể biểu đạt một thay đổi FK trực tiếp và rõ ràng hơn.

**Join table:** phải xóa liên kết cũ và tạo liên kết mới; constraint `UNIQUE(order_line_id)` giữ quy tắc một owner. Thứ tự SQL có thể quan trọng nếu constraint không deferrable; cần chọn thao tác/service tương thích provider hoặc thực hiện thay đổi join table bằng cơ chế được kiểm soát.

**Khi có `orphanRemoval=true`:** không được giả định thao tác chuyển owner là an toàn. Việc gỡ ở parent cũ có thể kích hoạt DELETE child. Hãy chọn mô hình có lifecycle đúng với nghiệp vụ.

## 7. Cascade và orphanRemoval: hai trách nhiệm khác nhau

`@OneToMany` có hai nhóm cấu hình thường được đặt cạnh nhau nhưng phục vụ mục tiêu riêng.

| Cấu hình | Khi nào có tác dụng? | Ảnh hưởng chính |
|---|---|---|
| `cascade=PERSIST` | Gọi `persist` trên parent có các child mới phù hợp | Lan truyền trạng thái new → managed cho child |
| `cascade=MERGE` | Gọi `merge` trên parent với graph detached | Sao chép/hợp nhất trạng thái child theo ngữ nghĩa merge |
| `cascade=REMOVE` | Gọi `remove` trên parent | Lan truyền remove sang child |
| `cascade=REFRESH` | Gọi `refresh` trên parent | Làm mới trạng thái child |
| `cascade=DETACH` | Gọi `detach` trên parent | Tách child khỏi persistence context |
| `cascade=ALL` | Tập hợp các thao tác trên | Lan truyền toàn bộ các loại cascade |
| `orphanRemoval=true` | Một child bị gỡ khỏi quan hệ sở hữu lifecycle | Child có thể bị xóa dù parent vẫn tồn tại |

Lưu ý ba khác biệt:

1. **Cascade không quyết định chỗ đặt FK**. Dùng `@JoinColumn` hay `@JoinTable` là quyết định cấu trúc association.
2. **`cascade=REMOVE` không tự xóa child chỉ vì gọi `collection.remove(child)`**. Nó lan truyền thao tác `remove(parent)`.
3. **`orphanRemoval` có thể xóa child khi collection bị thay đổi**. Quy tắc này khác với xóa một hàng join table đơn thuần.

Ví dụ nghiệp vụ:

- Xóa một đơn hàng nháp cùng các dòng hàng thuộc sở hữu của nó: `cascade=REMOVE` hoặc `orphanRemoval` có thể phù hợp, tùy thiết kế.
- Gỡ một ảnh dùng chung giữa các album: không nên xóa entity ảnh nếu nó còn có giá trị độc lập; thậm chí quan hệ thực sự có thể là `ManyToMany`.
- Quản lý danh sách các line chỉ tồn tại cùng đơn: `orphanRemoval` có thể phù hợp, nhưng phải cân nhắc thao tác gỡ/sửa/chuyển line.

Cấu hình `cascade=ALL` không nên được thêm mặc định chỉ để “dễ lưu”. Nó bao gồm `REMOVE`, có thể xóa các entity đích ngoài mong đợi khi parent bị xóa.

## 8. Owning side, `mappedBy` và khác biệt với quan hệ hai chiều

### 8.1. OneToMany đơn hướng

```java
@Entity
public class PurchaseOrder {
    @OneToMany
    @JoinColumn(name = "purchase_order_id")
    private List<OrderLine> lines;
}

@Entity
public class OrderLine {
    // Không có thuộc tính PurchaseOrder order.
}
```

Ở đây **collection `PurchaseOrder.lines` sở hữu association**. Do không có quan hệ ngược ở entity con, không có field nào để `mappedBy` tham chiếu.

### 8.2. OneToMany hai chiều

```java
@Entity
public class PurchaseOrder {

    @OneToMany(mappedBy = "order")
    private List<OrderLine> lines = new ArrayList<>();
}

@Entity
public class OrderLine {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "purchase_order_id")
    private PurchaseOrder order;
}
```

Ở mô hình hai chiều này:

- `OrderLine.order` là **owning side**, ghi FK trên bảng con.
- `PurchaseOrder.lines` là **inverse side**, được đánh dấu bằng `mappedBy="order"`.
- Khi thay liên kết, thường phải gọi `line.setOrder(order)` và đồng bộ collection ở cả hai phía.

Cùng lưu FK trong bảng con, nhưng **vị trí sở hữu ORM association khác nhau**. Đây là lý do không thể sao chép `mappedBy` từ ví dụ hai chiều vào một `@OneToMany` đơn hướng chỉ có collection ở parent.

### 8.3. Khi nào nên chuyển sang hai chiều?

Một số tín hiệu:

- Nhiều use case truy vấn “dòng hàng này thuộc đơn nào?”.
- Việc chuyển chủ và giữ FK `NOT NULL` xảy ra thường xuyên.
- Cần kiểm soát rõ SQL gán FK ngay khi persist line.
- Nghiệp vụ của child cần sử dụng parent trực tiếp.

Nếu chỉ duyệt parent → children, không cần truy cập ngược và dữ liệu có vòng đời giản dị, đơn hướng có thể dễ hiểu hơn. Đừng thêm association ngược chỉ để đúng một “mẫu chuẩn” thiếu lý do.

## 9. So sánh chi phí SQL và hiệu năng

### 9.1. Số bảng và lượt ghi

Trong FK trực tiếp, một hàng `OrderLine` chứa cột owner FK. Khi thay owner, thông thường cần update một hàng con. Với join table, thêm/gỡ association tác động vào bảng liên kết, thường thêm thao tác write và có thể thêm JOIN khi đọc.

| Thao tác | FK trực tiếp | Bảng liên kết |
|---|---|---|
| Tạo parent | INSERT parent | INSERT parent |
| Tạo child và liên kết | INSERT child chứa FK hoặc INSERT rồi UPDATE FK | INSERT child, sau đó INSERT link |
| Đọc children của một parent | SELECT theo FK | SELECT qua link và child |
| Gỡ liên kết, giữ child | UPDATE FK về NULL/chủ mới | DELETE link |
| Xóa child | DELETE child (và xử lý quan hệ FK) | DELETE link rồi DELETE child, tùy constraint/SQL |
| Đổi owner | UPDATE FK | Xóa link cũ, thêm link mới |
| Index thường cần | FK của child | FK parent, unique/index trên child FK trong link |

Đây là hình dạng SQL **thường gặp**, không phải số câu SQL cố định. JPA provider có thể phải recreate một phần join table khi thao tác trên một số kiểu collection (đặc biệt khi không có định danh/cách theo dõi thứ tự phù hợp), hoặc tối ưu batch khác nhau.

### 9.2. N+1 không phụ thuộc riêng cấu trúc bảng

Giả sử tải 100 order và duyệt `getLines()` của từng order. Cả hai kiểu ánh xạ đều có thể gây 1 truy vấn order + nhiều truy vấn lấy lines. Tối ưu có thể gồm:

- Truy vấn theo projection nếu chỉ cần aggregate như số line hoặc tổng số lượng.
- `JOIN FETCH`/entity graph khi kích thước kết quả phù hợp.
- Batch fetching (tùy provider), hoặc hai bước tải tập ID rồi tải collection cần thiết.
- Giới hạn lượng order và kích thước collection trước khi render API.

Không nên dùng `FetchType.EAGER` cho mọi collection với mục tiêu tránh N+1: eager có thể tạo dữ liệu trùng lặp từ JOIN, tăng bộ nhớ và tác động phân trang. **Fetch plan phải gắn với use case**.

### 9.3. Phân trang với collection

Ví dụ:

```jpql
select distinct o
from PurchaseOrder o
left join fetch o.lines
order by o.id
```

Nếu áp dụng `setMaxResults(20)` trực tiếp cùng fetch join collection, tùy provider có thể phải phân trang trong bộ nhớ hoặc tạo hiệu năng kém do một order xuất hiện nhiều dòng SQL. Đây không phải điểm khác biệt quyết định giữa FK và join table; nguyên nhân nằm ở **multiplicity của collection JOIN**.

Với danh sách lớn, thường nên phân trang parent trước, sau đó lấy các collection cần thiết theo lô, hoặc dùng DTO projection.

### 9.4. Quan sát SQL thật

Khi đánh giá phương án, theo dõi:

1. Bao nhiêu `INSERT/UPDATE/DELETE` phát sinh khi thêm, gỡ, sắp xếp lại collection?
2. Đọc một parent và 100 child dùng bao nhiêu SQL và row transfer?
3. Index nào được dùng để lọc theo parent/child? Cơ sở dữ liệu có thực sự dùng index trong execution plan?
4. Có transaction bị kéo dài vì collection lớn hay provider phải tải toàn bộ để xóa một phần tử?
5. Có constraint nào khiến một bước cập nhật FK trung gian không hợp lệ?
6. Khi thay đổi từ 1.000 thành 10.000 children, độ trễ và bộ nhớ tăng như thế nào?

Một mô hình có nhiều bảng hơn không mặc định chậm trong mọi trường hợp. Ví dụ nếu “gỡ liên kết nhưng giữ child” là thao tác chính, xóa một hàng join table có thể phù hợp hơn việc đặt FK null trên một hàng child với ràng buộc phức tạp.

## 10. Collection type, thứ tự và dữ liệu trùng lặp

### 10.1. `List` không tự lưu thứ tự bền vững

Một `List<OrderLine>` trong Java có thứ tự ở bộ nhớ, nhưng database không bảo đảm cùng thứ tự khi truy vấn nếu không có cách lưu/sắp xếp:

```java
@OneToMany
@JoinTable(name = "purchase_order_line_links")
private List<OrderLine> lines = new ArrayList<>();
```

Nếu thứ tự line là một phần nghiệp vụ, có thể dùng `@OrderColumn`:

```java
@OneToMany
@JoinTable(
    name = "purchase_order_line_links",
    joinColumns = @JoinColumn(name = "purchase_order_id"),
    inverseJoinColumns = @JoinColumn(name = "order_line_id")
)
@OrderColumn(name = "line_position")
private List<OrderLine> lines = new ArrayList<>();
```

Với join table, `line_position` thường nằm trong **bảng liên kết**. Với FK trực tiếp, cột thứ tự có thể được đặt ở **bảng child**. Cần đồng bộ DDL với mapping và chú ý chi phí update lại thứ tự khi chèn/xóa ở đầu danh sách lớn.

`@OrderBy("sku ASC")` khác `@OrderColumn`: `@OrderBy` yêu cầu sắp xếp theo thuộc tính lúc truy vấn, không ghi vị trí độc lập cho thao tác reorder. Không nên chọn annotation dựa trên tên mà bỏ qua ý nghĩa thứ tự.

### 10.2. `Set` dùng `equals`/`hashCode`

Nếu dùng:

```java
@OneToMany
@JoinTable(name = "purchase_order_line_links")
private Set<OrderLine> lines = new HashSet<>();
```

thì `add`/`remove` phụ thuộc vào tính bằng nhau và hash của entity. Với ID được sinh sau persist, một `hashCode` dựa trực tiếp trên ID có thể thay đổi khi entity nằm trong `HashSet`, khiến thao tác remove thất bại ngay tại Java.

Việc dùng `Set` có thể ngăn một số phần tử trùng theo Java equality nhưng **không thay thế unique constraint ở database**. Với join table, ràng buộc unique(child FK) còn có nhiệm vụ bảo đảm cardinality một-nhiều. Khi ID và semantics entity thay đổi theo vòng đời, cần chọn một chính sách equals/hash ổn định hoặc tổ chức code phù hợp.

### 10.3. Không đồng nhất `@ElementCollection` với `@OneToMany`

`@ElementCollection` dùng cho các **giá trị** như `String` hoặc `@Embeddable`, thường cũng dùng bảng phụ:

```java
@ElementCollection
@CollectionTable(
    name = "order_tags",
    joinColumns = @JoinColumn(name = "order_id")
)
@Column(name = "tag")
private Set<String> tags = new HashSet<>();
```

Nhưng `OrderLine` là **entity có `@Id` và vòng đời riêng**, nên association của nó dùng `@OneToMany`. Không thay `@OneToMany` bằng `@ElementCollection` chỉ để tránh bảng join hoặc vì cả hai đều là collection.

## 11. Ràng buộc dữ liệu và các trường hợp cần cân nhắc

### 11.1. Một child có thể bị tham chiếu bởi nhiều parent không?

Nếu một product catalog được đưa vào nhiều đơn hàng, quan hệ thực tế **không phải `PurchaseOrder → Product` một-nhiều độc quyền**. Một sản phẩm có thể xuất hiện trong nhiều đơn; nên có entity `OrderLine` riêng chứa số lượng, giá chụp tại thời điểm đặt và tham chiếu tới `Product`.

```text
PurchaseOrder 1 ----> OrderLine A ----> Product #10
PurchaseOrder 2 ----> OrderLine B ----> Product #10
```

Mỗi `OrderLine` thuộc một order, nhưng `Product` được chia sẻ. Nếu đặt `@OneToMany` trực tiếp từ `PurchaseOrder` tới `Product` và thêm unique(product_id) trong bảng nối, hệ thống sẽ không thể thêm cùng một sản phẩm vào nhiều đơn. Nếu bỏ unique, cardinality thực tế thành nhiều-nhiều.

**Chọn target entity đúng ngữ nghĩa trước khi chọn FK hay join table.**

### 11.2. Child có được tồn tại độc lập không?

- Nếu `OrderLine` chỉ tồn tại cùng `PurchaseOrder`: FK `NOT NULL`, lifecycle ownership và orphan removal có thể phù hợp, cần xem xét SQL khi persist.
- Nếu `Attachment` có thể được tải lên trước rồi gán vào hồ sơ sau: join table hoặc FK nullable có thể phù hợp.
- Nếu `Document` được nhiều folder chia sẻ: quan hệ nhiều-nhiều hoặc entity liên kết có thể đúng hơn one-to-many.
- Nếu association có metadata như `addedAt`, `sortOrder`, `role` và `addedBy`: bảng nối có thể cần trở thành **entity liên kết** thay vì chỉ `@JoinTable`.

Ví dụ `Folder → Document` chỉ nên là unidirectional OneToMany nếu mỗi document thuộc tối đa một folder trong phạm vi mapping; nếu một document được phép nằm ở nhiều folder, hãy xét `@ManyToMany` hoặc entity `FolderDocument` có định danh và thuộc tính riêng.

### 11.3. Index và khóa ngoại

Đối với FK trực tiếp, index trên `order_lines.purchase_order_id` thường hữu ích khi tìm con theo cha. Đối với join table, khóa chính `(purchase_order_id, order_line_id)` hỗ trợ tìm link theo parent; ràng buộc `UNIQUE(order_line_id)` vừa bảo vệ one-to-many vừa hỗ trợ tìm link theo child.

Không nên tạo index trùng hoàn toàn với những index đã được database tạo cho primary/unique constraint. Cần kiểm tra execution plan và workload thực tế.

### 11.4. Đổi schema cần migration, không chỉ đổi annotation

Nếu ban đầu lưu FK tại bảng child nhưng chuyển sang join table, các bước dữ liệu có thể gồm:

1. Tạo bảng liên kết và các constraint cần thiết.
2. Sao chép từng cặp `(purchase_order_id, order_line_id)` từ child sang join table.
3. Kiểm tra số lượng, trùng, null và ràng buộc one-to-many.
4. Triển khai mapping có khả năng tương thích theo kế hoạch release.
5. Sau khi xác nhận dữ liệu được chuyển đúng, mới xem xét bỏ cột FK cũ.
6. Lập kế hoạch rollback và xử lý các phiên bản ứng dụng còn chạy trên schema cũ.

Đổi `@JoinColumn` sang `@JoinTable` trong Java **không tự chuyển dữ liệu hiện hữu**. Với production, nên quản lý schema bằng migration và thử trên bản sao dữ liệu thực tế.

## 12. Các lỗi thường gặp

| Triệu chứng | Nguyên nhân hay gặp | Cách xử lý |
|---|---|---|
| JPA sinh bảng nối dù muốn FK trong child | `@OneToMany` đơn hướng không có `@JoinColumn` và đang dùng join-table default | Khai báo `@JoinColumn(name="...")` ở collection, đồng bộ migration |
| Child không có trường parent trong Java | Đây là thiết kế đơn hướng, không nhất thiết là lỗi | Chỉ thêm `@ManyToOne` nếu cần quan hệ ngược và điều chỉnh ownership |
| Đặt `mappedBy` nhưng child không có field được tham chiếu | `mappedBy` dành cho inverse side của quan hệ hai chiều | Bỏ `mappedBy` với unidirectional mapping |
| Đặt `@JoinColumn` ở parent rồi tưởng FK nằm trong parent | Với unidirectional OneToMany, FK được đặt tại bảng target | Kiểm tra DDL và tên cột trên child |
| Không thể gỡ child khi FK là NOT NULL | Gỡ liên kết dẫn tới FK null không hợp lệ nếu child vẫn tồn tại | Xóa child bằng orphan removal/remove, chuyển chủ hoặc chọn mô hình bảng nối |
| INSERT child thất bại vì FK null | Provider tạo SQL theo nhiều bước, schema cấm bước trung gian | Đối chiếu generated SQL, nullability và cân nhắc bidirectional FK owning side |
| Gỡ item nhưng entity vẫn còn | `orphanRemoval=false` nghĩa là gỡ association không tự xóa child | Quyết định rõ muốn unlink hay delete entity |
| Gỡ item rồi child bị xóa | `orphanRemoval=true` đang gắn lifecycle với association | Bỏ orphan removal nếu child cần tồn tại độc lập |
| Xóa parent làm xóa child ngoài ý muốn | `cascade=REMOVE/ALL` trên quan hệ không phù hợp | Xem lại ownership vòng đời; tránh cascade xóa entity chia sẻ |
| Join table cho một child xuất hiện ở nhiều parent | Thiếu unique trên child FK hoặc mô hình thật là nhiều-nhiều | Bổ sung ràng buộc phù hợp hoặc đổi cardinality |
| Reorder `List` không tồn tại sau khi load lại | Không có mapping thứ tự bền vững | Dùng `@OrderColumn` nếu thứ tự theo vị trí mang ý nghĩa |
| Đọc nhiều parent gây N+1 | Lazy collection được tải lần lượt | Thiết kế fetch plan/batch/projection theo use case |
| JPQL `line.order.id` không hợp lệ | `OrderLine` đơn hướng không có property `order` | Join từ parent qua `o.lines` hoặc thêm mapping ngược có chủ đích |
| SQL xóa/reinsert nhiều link hơn dự kiến | Provider và kiểu collection quyết định cách đồng bộ bảng nối | Theo dõi SQL; chọn collection, mapping, provider và thao tác phù hợp |
| Hai phiên làm việc đổi cùng collection gây mất thay đổi | Không có kiểm soát đồng thời phù hợp | Dùng transaction, version/locking và xác định semantics cập nhật |
| Sau bulk DELETE vẫn thấy entity cũ trong context | Bulk operation bỏ qua quản lý vòng đời từng entity | Clear/refresh hoặc tách transaction theo thiết kế |

### 12.1. Ví dụ sai: ép thành hai chiều nhưng thiếu owning side

```java
@Entity
class PurchaseOrder {
    @OneToMany(mappedBy = "purchaseOrder")
    private List<OrderLine> lines;
}

@Entity
class OrderLine {
    // Không có field purchaseOrder.
}
```

Provider không thể tìm thuộc tính `purchaseOrder` trong `OrderLine` để xác định owning side; cấu hình không hợp lệ. Nếu muốn đơn hướng, dùng `@OneToMany` cùng `@JoinColumn` hoặc `@JoinTable` mà không có `mappedBy`.

### 12.2. Ví dụ sai: dùng cascade để thay thế mapping

```java
@OneToMany(cascade = CascadeType.ALL)
private List<OrderLine> lines;
```

`CascadeType.ALL` **không nói** phải dùng FK trong bảng con. Nếu không chỉ định cách lưu, provider vẫn có thể dùng join table. Cascade và cấu trúc liên kết là hai trục thiết kế khác nhau.

### 12.3. Ví dụ sai: unique parent FK trong bảng con

```sql
-- Không đúng nếu muốn một order có nhiều lines:
ALTER TABLE order_lines
ADD CONSTRAINT uq_order_line_parent UNIQUE (purchase_order_id);
```

Constraint trên khiến mỗi `purchase_order_id` xuất hiện tối đa một lần, mang ý nghĩa một-một thay vì một-nhiều. Với FK trực tiếp, **không unique parent_id**. Với join table, cần unique **child_id** để giữ một child tối đa một parent; parent_id phải được phép lặp.

## 13. Quyết định theo use case

| Nhu cầu | Phương án thường hợp lý | Lý do |
|---|---|---|
| Child thuộc đúng một parent, thường cần truy vấn qua FK, số lượng lớn | Unidirectional OneToMany với `@JoinColumn` hoặc bidirectional OneToMany/ManyToOne | Bớt join table, lọc FK trực tiếp |
| Child không được tồn tại thiếu parent, FK NOT NULL rất quan trọng | Cân nhắc bidirectional `@ManyToOne` ở child hoặc xác nhận provider hỗ trợ ghi FK trực tiếp | Kiểm soát INSERT/FK và integrity rõ |
| Child có thể tồn tại trước khi được gắn, cần gỡ mà không sửa row child | Unidirectional OneToMany với `@JoinTable` | Association lưu riêng |
| Cần tách bảng child khỏi cấu trúc quản lý quan hệ | `@JoinTable` | Không thêm FK cột owner vào bảng child |
| Quan hệ được chuyển chủ thường xuyên | FK trực tiếp với owning side rõ, hoặc service kiểm soát join table | Tránh trạng thái trung gian vi phạm unique/orphan removal |
| Child dùng chung bởi nhiều parent | `@ManyToMany` hoặc entity liên kết | Đây không còn là OneToMany độc quyền |
| Link có metadata riêng | Entity liên kết (association entity) | Có identity, thuộc tính và vòng đời riêng |
| Parent chỉ cần hiển thị số lượng child | Projection/count query thay vì luôn load collection | Tránh truyền và quản lý cả object graph |
| Child bị gỡ là phải bị xóa hẳn | `orphanRemoval=true` khi lifecycle ownership đúng | Gỡ association cũng xóa entity đích |

Một câu hỏi hữu ích là: **khi người dùng bỏ một phần tử khỏi danh sách của parent, hàng child có còn là dữ liệu hợp lệ cần giữ không?**

- Nếu **không**, hãy biểu diễn ownership vòng đời rõ ràng và cân nhắc orphan removal.
- Nếu **có**, cần mô hình cho phép unlink không xóa child: FK nullable, đổi owner hoặc bảng liên kết.
- Nếu child có thể thuộc **nhiều parent cùng lúc**, hãy đánh giá lại cardinality vì `@OneToMany` không phản ánh quan hệ thật.

## 14. Thực hành theo hai phương án

### Bài 1: FK trong bảng con

Tạo `PurchaseOrder` và `OrderLine` theo mục 3. Dùng `@OneToMany` + `@JoinColumn(name="purchase_order_id")`. Tạo đơn cùng hai line trong transaction.

Quan sát kết quả logic:

```sql
SELECT id, purchase_order_id, sku
FROM order_lines
ORDER BY id;
```

Hãy xác định:

1. Cột nào giữ foreign key?
2. Có bảng nối hay không?
3. Entity `OrderLine` có cần field `PurchaseOrder` không?
4. Thêm dòng hàng mới làm thay đổi những hàng nào?
5. Thứ tự `INSERT/UPDATE` nào do provider thực tế tạo ra?

### Bài 2: Chuyển sang `@JoinTable`

Thay mapping của collection bằng `@JoinTable` như mục 4, chuẩn bị migration/schema phù hợp. Tạo một order có hai line.

Kiểm tra hai truy vấn:

```sql
SELECT * FROM order_lines;
SELECT * FROM purchase_order_line_links;
```

Sau đó gỡ một line với `orphanRemoval=false` và kiểm tra hàng `order_lines` còn tồn tại, trong khi row link bị xóa. Giải thích vì sao đây là **gỡ liên kết**.

### Bài 3: So sánh orphan removal

Tạo order với hai line, bật `orphanRemoval=true`; gỡ một line và flush. Quan sát câu SQL và trạng thái hai bảng trong trường hợp join table, hoặc bảng child trong trường hợp FK trực tiếp.

Tiếp tục với `orphanRemoval=false`. Giải thích vì sao kết quả vòng đời child khác nhau dù mã `order.removeLine(line)` giống nhau.

### Bài 4: Ràng buộc và cardinality

Với join table, thử thêm cùng một `OrderLine` vào hai order khác nhau khi đã có constraint `UNIQUE(order_line_id)`. Dự đoán lỗi hoặc yêu cầu gỡ liên kết cũ.

Sau đó bỏ unique chỉ trong môi trường thử nghiệm. Đối chiếu dữ liệu và nhận xét liệu schema mới còn bảo đảm quan hệ one-to-many không.

### Bài 5: Gỡ liên kết khi FK là `NOT NULL`

Trong FK trực tiếp, đặt `purchase_order_id NOT NULL`, dùng `orphanRemoval=false` rồi cố gỡ line nhưng vẫn giữ entity con. Dự đoán lỗi constraint hoặc hành vi ORM. Đánh giá ba hướng: xóa child, đổi owner, hoặc đổi mô hình/schema.

### Bài 6: Đánh giá một trang danh sách lớn

Tải 100 `PurchaseOrder` rồi duyệt số `lines` của từng order. Quan sát query count. Thử dùng truy vấn `COUNT` theo parent, batch fetch hoặc projection phù hợp, so sánh số SQL và hàng truyền về. Thực hiện với cả FK trực tiếp và join table.

## 15. Ghi nhớ cốt lõi

**OneToMany đơn hướng nghĩa là chỉ entity cha có collection trỏ tới các entity con.** Lớp con không cần thuộc tính quan hệ ngược. JPA có hai cách phổ biến để lưu association:

- **`@OneToMany` + `@JoinColumn`**: khóa ngoại nằm trong **bảng con**. Ít bảng hơn, đọc theo FK trực tiếp; nhưng cần chú ý nullability, thứ tự SQL khi insert và thao tác gỡ/chuyển con.
- **`@OneToMany` + `@JoinTable`**: khóa ngoại của cha và con nằm trong **bảng liên kết**. Dễ tách link khỏi row child, nhưng thêm JOIN và thao tác ghi; cần unique theo FK con để giữ cardinality một-nhiều.

Trong cả hai cách, **collection ở parent là owning side**; `mappedBy` chỉ xuất hiện nếu thiết kế quan hệ hai chiều có thuộc tính sở hữu ở bên kia. `cascade` quyết định lan truyền thao tác vòng đời, còn `orphanRemoval` quyết định liệu một child bị gỡ khỏi association sở hữu có bị xóa. Chúng **không thay thế** lựa chọn FK hay join table.

Khi đánh giá một mapping, hãy xác định ba điều: **có cần đường truy cập ngược từ child không, child có được tồn tại độc lập không, và database cần bảo vệ những ràng buộc nào?** Từ đó chọn cấu trúc SQL, annotation và chính sách transaction thích hợp, rồi quan sát SQL của JPA provider trong môi trường thực tế.
