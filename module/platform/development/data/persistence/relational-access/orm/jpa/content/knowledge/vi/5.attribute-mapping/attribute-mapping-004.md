# Phân biệt trường không lưu với @Transient và từ khóa transient trong JPA

Khi viết một entity Java, không phải thuộc tính nào của đối tượng cũng cần tương ứng với cột trong cơ sở dữ liệu. Một `Customer` có thể có `firstName`, `lastName` được lưu bền vững, đồng thời có `fullName` tính toán để hiển thị, `temporaryNote` phục vụ một màn hình, hoặc `verificationCode` chỉ có giá trị trong lúc xử lý. Nếu không phân biệt rõ, JPA có thể cố ánh xạ thuộc tính không mong muốn thành cột, hoặc ứng dụng có thể nhầm một dữ liệu tạm đã được lưu lại.

Trong chương **Ánh xạ thuộc tính** của chủ đề **Data Persistence Relational Access ORM JPA**, cần phân biệt ba khái niệm:

1. **Trường hoặc thuộc tính không lưu (non-persistent attribute)**: cách gọi theo **kết quả ánh xạ JPA**. Nó không tham gia lưu/đọc trạng thái entity từ bảng.
2. **`@Transient`**: annotation của JPA, viết đầy đủ là `jakarta.persistence.Transient`, để chỉ rõ một field hoặc property **không thuộc ánh xạ persistence**.
3. **`transient`**: từ khóa của **ngôn ngữ Java**, chủ yếu liên quan đến cơ chế **Java Object Serialization**. Khi JPA ánh xạ theo field, field khai báo bằng từ khóa này cũng được loại khỏi ánh xạ mặc định.

Điểm quan trọng: **`@Transient` và `transient` không phải một cơ chế duy nhất**. Một cái là quy tắc metadata của ORM, một cái là modifier của Java; tác động của chúng đến database, Java serialization và JSON có thể khác nhau.

## 1. “Trường không lưu” có nghĩa gì?

Một **persistent attribute** là thuộc tính JPA coi là một phần trạng thái cần lưu trong cơ sở dữ liệu. Nó thường được ánh xạ thành cột với `@Column`, thành khóa chính với `@Id`, hoặc thành một quan hệ với `@ManyToOne`, `@OneToMany` và các annotation khác.

Một **non-persistent attribute** là dữ liệu tồn tại trên đối tượng Java nhưng không được JPA xem là trạng thái cần lưu. Nó có thể là:

- Giá trị hiển thị được tính từ các cột đã lưu, như họ tên đầy đủ.
- Kết quả xử lý tạm, như nhãn gợi ý, cờ trạng thái của một lần kiểm tra.
- Thông tin chỉ phục vụ tầng giao diện hoặc một thao tác đơn lẻ.
- Dữ liệu cache tính toán được tạo lại khi cần.

Ví dụ bảng dữ liệu:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    first_name VARCHAR(80) NOT NULL,
    last_name VARCHAR(80) NOT NULL
);
```

Trong Java, entity có thể mang cả dữ liệu lưu và dữ liệu không lưu:

```text
Customer object
  id               = 10             -> customers.id
  firstName        = "Nguyễn"       -> customers.first_name
  lastName         = "An"           -> customers.last_name
  fullName         = "Nguyễn An"    -> tính từ firstName và lastName
  temporaryNote    = "Đã xem"       -> chỉ tồn tại trong bộ nhớ
```

Nếu JPA chỉ ánh xạ `id`, `firstName` và `lastName`, thì bảng **không cần cột** `full_name` hoặc `temporary_note`. Sau khi đóng persistence context và đọc lại entity từ database, dữ liệu tạm không được phục hồi từ bảng; còn họ tên đầy đủ có thể được tính lại từ hai cột.

“Không lưu” ở đây nói về **JPA/database**. Thuộc tính đó vẫn có thể hiện diện trong bộ nhớ, tham gia logic nghiệp vụ, được ghi log hoặc được thư viện khác serialize; muốn ngăn các hành vi đó cần cơ chế tương ứng.

## 2. @Transient: khai báo thuộc tính không được JPA persist

`@Transient` thuộc package `jakarta.persistence`:

```java
import jakarta.persistence.Transient;
```

Nó cho phép đánh dấu một field hoặc JavaBean property là **không bền vững** theo mô hình ánh xạ JPA. Tùy chiến lược truy cập, annotation được đặt trên field hoặc getter tương ứng.

### 2.1. Ví dụ entity dùng field access

Khi `@Id` được đặt trên **field**, entity thường sử dụng **field access**: JPA đọc/ghi trạng thái qua field và tìm annotation ánh xạ tại field.

```java
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Transient;

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "first_name", nullable = false, length = 80)
    private String firstName;

    @Column(name = "last_name", nullable = false, length = 80)
    private String lastName;

    @Transient
    private String temporaryNote;

    protected Customer() {
        // JPA yêu cầu constructor không tham số.
    }

    public Customer(String firstName, String lastName) {
        this.firstName = firstName;
        this.lastName = lastName;
    }

    public Long getId() {
        return id;
    }

    public String getFirstName() {
        return firstName;
    }

    public String getLastName() {
        return lastName;
    }

    public String getFullName() {
        return firstName + " " + lastName;
    }

    public String getTemporaryNote() {
        return temporaryNote;
    }

    public void setTemporaryNote(String temporaryNote) {
        this.temporaryNote = temporaryNote;
    }
}
```

Trong ví dụ:

- `id`, `firstName` và `lastName` là trạng thái được ánh xạ, có giá trị trong các cột database.
- `temporaryNote` được ghi chú `@Transient` nên không có cột tương ứng, không được JPA lưu hoặc tải.
- `getFullName()` là **phương thức tính toán**, không có field `fullName` tương ứng. Với field access, JPA không tự tạo mapping chỉ vì có một getter này.
- `@Transient` không làm trường biến mất khỏi đối tượng Java; mã vẫn được phép gọi `getTemporaryNote()` và `setTemporaryNote()` trong thời gian đối tượng tồn tại.

Câu SQL mà provider thực thi khi lưu một entity mới sẽ có ý nghĩa tương tự:

```sql
INSERT INTO customers (first_name, last_name)
VALUES ('Nguyễn', 'An');
```

Không có `temporary_note` trong SQL, và cũng không có cột cho `getFullName()`. SQL thực tế thường dùng tham số và phụ thuộc provider, chiến lược cấp khóa cùng cấu hình.

### 2.2. Thay đổi @Transient không gây UPDATE

Giả sử một `Customer` đang được JPA quản lý:

```java
Customer customer = entityManager.find(Customer.class, 10L);

customer.setTemporaryNote("Đã xác thực hiển thị");

// Chỉ riêng thay đổi temporaryNote không tạo ra UPDATE
// cho trường này, vì nó không thuộc trạng thái persistent.
```

JPA thực hiện dirty checking đối với trạng thái **được ánh xạ**. Vì vậy, thay đổi một field `@Transient` không đủ để phát sinh SQL `UPDATE`. Nếu cùng lúc sửa `firstName`, JPA vẫn có thể cập nhật các cột được ánh xạ theo quy tắc flush/transaction.

Khi gọi `entityManager.clear()` hoặc đóng manager, đối tượng Java cũ có thể vẫn còn `temporaryNote` trong bộ nhớ nếu mã vẫn giữ tham chiếu. Nhưng khi một context mới tải lại `Customer` từ database, JPA không lấy `temporaryNote` từ bảng; nó có giá trị khởi tạo mặc định hoặc giá trị do constructor/callback/logic ứng dụng thiết lập. Không nên dựa vào `merge()` để duy trì dữ liệu `@Transient`: hợp đồng `merge` tập trung vào trạng thái persistent được ánh xạ.

## 3. Từ khóa transient trong Java

`transient` là modifier của Java được đặt trước **field**:

```java
private transient String oneTimeCode;
```

Mục đích cốt lõi của nó là đánh dấu field để cơ chế **Java serialization mặc định** không ghi giá trị vào luồng object khi lớp được serialize qua `ObjectOutputStream`. Khi đọc object trở lại, field này nhận giá trị mặc định của kiểu (ví dụ `null` cho reference, `0` cho `int`, `false` cho `boolean`), trừ khi lớp có logic serialization/khôi phục tùy biến.

`transient` có thể xuất hiện trong một class Java bình thường, không liên quan JPA:

```java
import java.io.Serializable;

public class LoginSession implements Serializable {
    private static final long serialVersionUID = 1L;

    private String username;
    private transient String oneTimeCode;

    public LoginSession(String username, String oneTimeCode) {
        this.username = username;
        this.oneTimeCode = oneTimeCode;
    }

    public String getUsername() {
        return username;
    }

    public String getOneTimeCode() {
        return oneTimeCode;
    }
}
```

Nếu serialize một `LoginSession` bằng Java Object Serialization rồi deserialize bằng cơ chế mặc định, `username` được khôi phục còn `oneTimeCode` thường là `null`.

Lưu ý: `transient` không xóa dữ liệu nhạy cảm khỏi bộ nhớ, log, JSON, HTTP response, database hoặc các cơ chế serialization tùy biến. Nó **không phải giải pháp bảo mật tổng quát**.

### 3.1. transient ảnh hưởng thế nào đến JPA?

Với **field access**, JPA không ánh xạ các field Java được khai báo `transient`. Ví dụ:

```java
import jakarta.persistence.Entity;
import jakarta.persistence.Id;

@Entity
public class SessionRecord {
    @Id
    private Long id;

    private String owner;

    private transient String localCacheKey;

    protected SessionRecord() {
    }
}
```

Vì `@Id` đặt trên field nên `localCacheKey` bị loại khỏi persistence mapping mặc định, dù không có annotation `@Transient`. Khi dùng Java Object Serialization mặc định, `localCacheKey` cũng bị bỏ qua. Như vậy, cùng một field có thể mang **hai hệ quả**:

1. Không được JPA lưu khi entity dùng field access.
2. Không được Java serialization mặc định ghi lại.

Tuy nhiên, **kết luận “cứ có từ khóa transient thì JPA sẽ không persist” không đúng cho mọi chiến lược truy cập**. Khi entity dùng **property access**, JPA ánh xạ các getter/setter thay vì các backing field; một backing field `transient` vẫn có thể được lưu thông qua property của nó nếu property đó không được loại khỏi mapping.

## 4. Bảng phân biệt @Transient, transient và trường không lưu

Bảng sau giả định entity sử dụng **field access**, không có `@Access` override trên thuộc tính; cột “Java serialization” nói về serialization mặc định khi class có `implements Serializable`:

| Khai báo | JPA lưu vào database? | Java Object Serialization ghi field? | Ghi chú |
| --- | --- | --- | --- |
| `private String note;` | Có theo ánh xạ mặc định. | Có, nếu object được serialize hợp lệ. | Field persistent bình thường. |
| `@Transient private String note;` | **Không**. | **Có** theo mặc định. | Chỉ loại khỏi JPA persistence; không mặc nhiên loại khỏi serialization. |
| `private transient String note;` | **Không** khi dùng field access. | **Không**. | Modifier Java và quy tắc field mapping của JPA. |
| `@Transient private transient String note;` | **Không**. | **Không**. | Thường dư thừa ở field access; có thể làm rõ ý định của lập trình viên. |
| `private static String note;` | **Không**. | **Không** dưới dạng instance field. | `static` là dữ liệu thuộc lớp, không phải persistent instance field. |
| `@Column(insertable = false, updatable = false) private String note;` | **Có mapping**, vẫn có thể được đọc từ database. | Có theo mặc định. | Chỉ điều khiển việc ghi cột qua INSERT/UPDATE do mapping này tạo ra. |
| `@JsonIgnore private String note;` | **Có**, nếu không có chỉ thị JPA loại bỏ. | Không do `@JsonIgnore` quyết định. | `@JsonIgnore` của Jackson điều khiển JSON, không điều khiển JPA. |

“Trường không lưu” là **nhóm kết quả** rộng hơn hai cú pháp `@Transient`/`transient`. Chẳng hạn, với field access, một giá trị chỉ được tính trong getter không có backing field persistent cũng không được lưu. Ngược lại, một field có `@Column` với `insertable = false` vẫn là **mapped attribute** và có thể đọc dữ liệu từ cột.

## 5. Mấu chốt: field access và property access quyết định đặt @Transient ở đâu

JPA hỗ trợ hai kiểu truy cập chính:

- **Field access**: JPA truy cập field; `@Id` và annotation ánh xạ đặt ở field.
- **Property access**: JPA truy cập JavaBean property qua getter/setter; `@Id` và annotation ánh xạ đặt ở getter.

Có thể chọn tường minh bằng `@Access(AccessType.FIELD)` hoặc `@Access(AccessType.PROPERTY)`. Nếu không chỉ định, vị trí `@Id` thường quyết định kiểu truy cập mặc định của entity. Trộn annotation ở field và getter mà không cấu hình `@Access` rõ ràng có thể gây mapping không như mong muốn hoặc hành vi không xác định theo đặc tả.

### 5.1. Field access: annotation ở field

```java
@Entity
@Access(AccessType.FIELD)
public class Product {
    @Id
    private Long id;

    private String name;

    @Transient
    private String displayBadge;

    public String getDisplayBadge() {
        return displayBadge;
    }
}
```

Ở đây `@Transient` đúng chỗ vì JPA đang đọc metadata trên field. Một phương thức `getDisplayBadge()` chỉ dùng để truy cập giá trị trong Java.

Nếu cố đặt `@Transient` **chỉ ở getter** trong khi field vẫn được JPA xét ánh xạ theo field access, annotation đó không bảo đảm loại field ra khỏi persistence mapping. Cần chú thích đúng điểm truy cập đang được sử dụng.

### 5.2. Property access: annotation ở getter

Xét một entity dùng property access rõ ràng:

```java
import jakarta.persistence.Access;
import jakarta.persistence.AccessType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Transient;

@Entity
@Access(AccessType.PROPERTY)
public class PriceQuote {
    private Long id;
    private String productCode;
    private transient String cachedLabel;

    protected PriceQuote() {
    }

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    @Column(name = "product_code")
    public String getProductCode() {
        return productCode;
    }

    public void setProductCode(String productCode) {
        this.productCode = productCode;
    }

    @Transient
    public String getDisplayLabel() {
        return productCode == null ? "" : "Sản phẩm: " + productCode;
    }

    // Phương thức này có getter và setter nên tạo một property
    // có thể được JPA xem xét ánh xạ dù backing field là transient.
    public String getCachedLabel() {
        return cachedLabel;
    }

    public void setCachedLabel(String cachedLabel) {
        this.cachedLabel = cachedLabel;
    }
}
```

Trong ví dụ, `getDisplayLabel()` được đánh dấu `@Transient` trên **getter**, nên JPA loại property hiển thị này khỏi mapping. Nhưng `cachedLabel` được khai báo bằng từ khóa Java `transient` trên backing field **không đủ** để loại `getCachedLabel()` khỏi property mapping. Vì entity dùng property access, nếu không muốn JPA lưu `cachedLabel`, phải đánh dấu getter tương ứng:

```java
@Transient
public String getCachedLabel() {
    return cachedLabel;
}
```

Sau khi bổ sung annotation này, `cachedLabel` vừa bị loại khỏi JPA mapping qua `@Transient` trên getter, vừa bị bỏ qua bởi Java Object Serialization mặc định vì backing field dùng `transient`.

**Quy tắc thực hành:** xác định access type trước, rồi đặt `@Transient` trên thành phần mà JPA ánh xạ. Đối với property access, một backing field dùng `transient` không thay thế việc chú thích getter.

### 5.3. Nếu getter chỉ dùng để tính toán thì sao?

Với **field access**, getter tính toán không có backing field persistent thường không phải một persistent attribute:

```java
@Entity
@Access(AccessType.FIELD)
public class Invoice {
    @Id
    private Long id;

    private java.math.BigDecimal subtotal;
    private java.math.BigDecimal tax;

    public java.math.BigDecimal getTotal() {
        return subtotal.add(tax);
    }
}
```

JPA không ánh xạ riêng `getTotal()` theo quy tắc field access; nó làm việc với `subtotal` và `tax`. Việc thêm `@Transient` trên getter trong trường hợp này thường không cần thiết cho mapping.

Với **property access**, một getter có dạng JavaBean property có thể được xem xét như thuộc tính persistent, nên cần đánh dấu `@Transient` cho những giá trị chỉ nhằm hiển thị hoặc tính toán. Đây là điểm gây bất ngờ khi đổi từ field access sang property access mà giữ nguyên các getter tiện ích.

## 6. @Transient không đồng nghĩa với “không serialize”

Một lỗi phổ biến là xem `@Transient` như từ khóa Java `transient`. Thực tế, hai cơ chế hoạt động ở hai tầng khác nhau:

```text
               Java object
             /             \
            /               \
    JPA persistence      Java Serialization
     (database)             (object stream)
          |                       |
 @Transient: bỏ qua       @Transient: không phải
 khi ánh xạ                quy tắc loại field
          |                       |
 transient field:          transient field:
 bỏ qua ở field access     bỏ qua theo mặc định
```

Ví dụ một entity có khả năng Java serialization:

```java
import java.io.Serializable;
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Transient;

@Entity
public class CustomerSession implements Serializable {
    private static final long serialVersionUID = 1L;

    @Id
    private Long id;

    @Transient
    private String uiMessage;

    private transient String temporaryToken;

    protected CustomerSession() {
    }

    public CustomerSession(Long id, String uiMessage, String temporaryToken) {
        this.id = id;
        this.uiMessage = uiMessage;
        this.temporaryToken = temporaryToken;
    }

    public String getUiMessage() {
        return uiMessage;
    }

    public String getTemporaryToken() {
        return temporaryToken;
    }
}
```

Với field access của entity này:

| Thuộc tính | Trong database qua JPA | Trong Java serialization mặc định |
| --- | --- | --- |
| `id` | Có | Có |
| `uiMessage` với `@Transient` | Không | **Có** |
| `temporaryToken` với `transient` | Không | **Không** |

Nếu dùng `ObjectOutputStream` lưu object rồi `ObjectInputStream` phục hồi, `uiMessage` có thể được phục hồi còn `temporaryToken` thường nhận `null`. Điều này đúng theo cơ chế serialization mặc định, với giả định lớp sử dụng serialization hợp lệ và không tùy biến `writeObject`/`readObject`.

**Không nhầm Java Object Serialization với JSON.** Jackson, Gson và thư viện JSON khác có quy tắc riêng, có thể chịu ảnh hưởng của getter, cấu hình field visibility và annotation. Muốn điều khiển JSON với Jackson, thường dùng `@JsonIgnore`, `@JsonProperty` hoặc DTO riêng. `@Transient` không phải cơ chế bảo đảm giá trị sẽ biến mất khỏi JSON response. Ngược lại, `@JsonIgnore` cũng không khiến JPA bỏ một cột.

## 7. “Không được JPA cập nhật” không giống “không được JPA lưu”

Một field ánh xạ read-only ở phía JPA vẫn là field persistent. Ví dụ:

```java
@Column(name = "created_by", insertable = false, updatable = false)
private String createdBy;
```

JPA biết field `createdBy` gắn với cột `created_by` và có thể đọc nó từ database. Các cờ `insertable = false` và `updatable = false` chỉ yêu cầu provider không đưa cột đó vào những câu SQL INSERT/UPDATE tạo ra từ **mapping này**. Giá trị vẫn là một phần trạng thái được ánh xạ, và có thể được database hoặc một tác nhân khác cập nhật.

So sánh:

```java
// Có mapping đến cột; không do mapping này ghi cột.
@Column(name = "created_by", insertable = false, updatable = false)
private String createdBy;

// Không có mapping đến cột.
@Transient
private String displayCreatedBy;
```

Cũng không nên coi `@Basic(fetch = FetchType.LAZY)` là “không lưu”. Cấu hình lazy chỉ yêu cầu chiến lược tải trì hoãn theo khả năng provider; thuộc tính vẫn thuộc mô hình persistence. Tương tự, thuộc tính tính toán bằng `@Formula` của Hibernate (API đặc thù provider) vẫn được ánh xạ để đọc kết quả SQL, khác với `@Transient`.

## 8. Khi nào nên dùng từng cách?

| Nhu cầu | Cách diễn đạt phù hợp | Lý do |
| --- | --- | --- |
| Giá trị UI tạm không lưu database, vẫn có thể tham gia serialization khác. | `@Transient` ở đúng field/getter. | Thể hiện ý định JPA một cách trực tiếp. |
| Cache tạm trong một entity dùng field access, cũng không muốn Java serialization mặc định ghi lại. | `private transient ...`. | Loại khỏi default field mapping và Java Object Serialization. |
| Entity dùng property access, getter chỉ tạo nhãn hiển thị. | `@Transient` trên getter. | Loại property ra khỏi JPA mapping. |
| Entity dùng property access, backing field dùng Java `transient` nhưng có getter/setter. | `@Transient` trên getter nếu không muốn lưu property. | Modifier trên field không đủ loại property khỏi JPA. |
| Giá trị tính từ nhiều field trong entity dùng field access, không có field riêng. | Getter tính toán; không nhất thiết cần `@Transient`. | Getter không được ánh xạ tự động theo field access. |
| Cột do database hoặc trigger quản lý, ứng dụng chỉ đọc. | Mapping `@Column(insertable = false, updatable = false)` khi thích hợp. | Vẫn đọc từ database, khác với không persist. |
| Không muốn thuộc tính xuất hiện trong JSON API. | DTO hoặc annotation JSON tương ứng, ví dụ Jackson `@JsonIgnore`. | Kiểm soát format đầu ra, không phải JPA mapping. |
| Không muốn giá trị nằm trong Java serialized stream. | Java `transient` hoặc cơ chế serialization tùy biến. | `@Transient` không điều khiển Java serialization. |

Nếu một thuộc tính hoàn toàn phục vụ DTO/response và không thuộc mô hình domain, cân nhắc đặt nó trong **DTO** thay vì trộn nhiều trường UI vào entity. Entity có thể giữ getter tính toán đơn giản, nhưng việc thêm trạng thái tạm phức tạp vào entity khiến vòng đời dữ liệu khó hiểu hơn.

## 9. Tác động với persist, find, merge và vòng đời entity

Cơ chế “không lưu” có thể quan sát qua những thao tác JPA phổ biến.

### 9.1. Khi persist()

Giả sử một customer mới có note tạm:

```java
Customer customer = new Customer("Nguyễn", "An");
customer.setTemporaryNote("Khách đã chọn trong màn hình");

entityManager.persist(customer);
```

Provider chỉ lưu dữ liệu thuộc mapping. `temporaryNote` vẫn tồn tại trong object hiện tại nhưng không được ghi xuống cột tương ứng vì không có mapping. Với strategy IDENTITY, SQL INSERT có thể chạy trước commit để lấy khóa chính; điều đó không làm field tạm trở thành persistent.

### 9.2. Khi find()

```java
Customer loaded = entityManager.find(Customer.class, customerId);
String fullName = loaded.getFullName();
String note = loaded.getTemporaryNote();
```

`fullName` có thể được tính từ những field đã tải. `note` không được phục hồi từ database: nếu không có logic thiết lập khác, nó có thể là `null`. Không nên thiết kế nghiệp vụ giả định các field tạm sẽ có giá trị sau khi đọc lại entity.

### 9.3. Khi merge()

```java
Customer managed = entityManager.merge(detachedCustomer);
```

`merge()` trả về một instance managed theo hợp đồng JPA, có thể không cùng tham chiếu với `detachedCustomer`. Các field không persistent như `temporaryNote` không phải trạng thái JPA bảo đảm sao chép/đồng bộ. Nếu dữ liệu tạm cần đi qua nhiều tầng hoặc nhiều transaction, hãy vận chuyển nó rõ ràng bằng DTO, tham số phương thức hoặc trạng thái nghiệp vụ được thiết kế riêng.

### 9.4. Khi dirty checking

Thay đổi `@Transient` không được xem là thay đổi cột database. Nếu entity có cả field tạm và field persistent, ORM chỉ đồng bộ trạng thái được ánh xạ khi flush. Điều này giúp tránh SQL không cần thiết cho dữ liệu trình bày, nhưng cũng có nghĩa **không thể dùng một field @Transient để lưu thông tin mà nghiệp vụ bắt buộc phải tồn tại sau commit**.

### 9.5. Lifecycle callback có thể khởi tạo dữ liệu tạm

Nếu giá trị tạm phụ thuộc dữ liệu được tải, có thể tính động trong getter. Với một phép tính tốn chi phí hơn, một số ứng dụng dùng callback JPA như `@PostLoad` để điền trường `@Transient`:

```java
import jakarta.persistence.PostLoad;
import jakarta.persistence.Transient;

@Transient
private String cachedFullName;

@PostLoad
private void afterLoad() {
    cachedFullName = firstName + " " + lastName;
}
```

Đây là đoạn minh họa đặt **bên trong entity dùng field access** như `Customer` ở trên. Nếu `firstName` hoặc `lastName` thay đổi sau khi callback chạy, cache cần được cập nhật lại; `@PostLoad` không có nghĩa giá trị này tự động tính lại sau mọi setter. Khi việc tính toán rẻ, một getter dẫn xuất trực tiếp thường dễ bảo trì hơn.

## 10. Những lỗi thường gặp khi sử dụng Transient

### Lỗi 1 — Import sai annotation

Tên `Transient` có thể xuất hiện trong nhiều thư viện:

```java
// Dùng cho Jakarta Persistence:
import jakarta.persistence.Transient;

// Annotation khác, thuộc Spring Data mapping:
import org.springframework.data.annotation.Transient;
```

Trong một dự án JPA, hãy dùng **`jakarta.persistence.Transient`** (hoặc `javax.persistence.Transient` với codebase JPA phiên bản cũ) để diễn đạt mapping JPA. `org.springframework.data.annotation.Transient` phục vụ cơ chế mapping của Spring Data và không nên coi nó là vật thay thế mặc nhiên cho annotation JPA. Luôn kiểm tra package import trước khi kết luận field đã bị loại khỏi persistence.

### Lỗi 2 — Đặt @Transient ở getter nhưng entity dùng field access

```java
@Entity
public class UserProfile {
    @Id
    private Long id;

    private String previewText;

    @Transient // Không phải vị trí ánh xạ theo field access.
    public String getPreviewText() {
        return previewText;
    }
}
```

Ở ví dụ trên, `previewText` vẫn là field được JPA xem xét ánh xạ theo field access. Cách thể hiện đúng là đặt `@Transient` ở **field**, hoặc cấu hình lại access type một cách có chủ đích.

### Lỗi 3 — Nghĩ transient field luôn loại được property trong property access

Khi `@Id` đặt ở getter hoặc entity khai báo `@Access(PROPERTY)`, JPA sẽ nhìn vào các property. Backing field mang Java `transient` có thể có getter/setter được ánh xạ như bình thường. Nếu cần bỏ property, dùng `@Transient` trên getter.

### Lỗi 4 — Nghĩ @Transient bảo đảm ẩn dữ liệu nhạy cảm

`@Transient` chỉ là chỉ thị JPA. Nó không ngăn một getter được Jackson xuất ra JSON, không ngăn Java serialization mặc định, không che log và không làm giá trị biến mất khỏi heap. Thông tin nhạy cảm cần được quản lý bằng thiết kế dữ liệu, kiểm soát quyền truy cập, cấu hình serialization và chính sách lưu trữ phù hợp.

### Lỗi 5 — Dùng @Column(insertable=false, updatable=false) để mô phỏng @Transient

`@Column` với hai cờ `false` vẫn duy trì mapping và có thể đọc cột; field `@Transient` không có mapping cột. Hai lựa chọn phục vụ hai mục đích khác nhau.

### Lỗi 6 — Dựa vào field không lưu để lưu trạng thái nhiều request

Một field `@Transient` có thể còn giá trị trong object hiện tại, nhưng sau khi ứng dụng tải lại entity, giá trị đó không được JPA khôi phục từ bảng. Nếu trạng thái cần bền vững qua request hoặc restart, hãy lưu nó theo mô hình persistent thích hợp, hoặc thiết kế nơi lưu riêng như session storage theo yêu cầu nghiệp vụ.

## 11. Ví dụ áp dụng: giỏ hàng và giá trị trình bày

Giả sử hệ thống bán hàng có entity `CartItem` cần lưu số lượng và đơn giá, nhưng màn hình cũng muốn hiển thị tổng tiền cùng thông điệp giảm giá tạm:

```java
import java.math.BigDecimal;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Transient;

@Entity
@Table(name = "cart_items")
public class CartItem {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private int quantity;

    @Column(name = "unit_price", nullable = false,
            precision = 12, scale = 2)
    private BigDecimal unitPrice;

    @Transient
    private String promotionHint;

    protected CartItem() {
    }

    public CartItem(int quantity, BigDecimal unitPrice) {
        this.quantity = quantity;
        this.unitPrice = unitPrice;
    }

    public BigDecimal getLineTotal() {
        return unitPrice.multiply(BigDecimal.valueOf(quantity));
    }

    public String getPromotionHint() {
        return promotionHint;
    }

    public void setPromotionHint(String promotionHint) {
        this.promotionHint = promotionHint;
    }
}
```

Tại đây:

- `quantity` và `unitPrice` phải được lưu vì là dữ liệu nghiệp vụ của giỏ hàng.
- `getLineTotal()` là phép tính dẫn xuất, được thực hiện từ giá trị đã lưu; với field access không cần thêm cột `line_total`.
- `promotionHint` là thông điệp tạm được tạo ở tầng nghiệp vụ hoặc hiển thị, không cần xuất hiện trong bảng `cart_items`.

Nếu hệ thống cần **đóng băng mức giảm giá hoặc tổng tiền tại thời điểm đặt hàng**, những giá trị lịch sử đó có thể phải trở thành dữ liệu persistent trên **đơn hàng** và không còn là trường chỉ tính tạm. Việc dùng `@Transient` là quyết định về lưu trữ; nó phải phản ánh đúng yêu cầu nghiệp vụ.

## 12. Câu hỏi tự kiểm tra

**1. Entity có `@Id` trên field và khai báo `private transient String temp;`. JPA có tạo cột `temp` không?**

Không, với field access mặc định, Java `transient` loại field khỏi mapping JPA. Java Object Serialization mặc định cũng bỏ field này.

**2. Field dùng `@Transient` có được serialize bằng `ObjectOutputStream` không?**

Có thể có. `@Transient` không phải modifier Java. Khi class triển khai `Serializable` và field đáp ứng quy tắc serialization mặc định, giá trị field vẫn được serialize trừ khi có cấu hình/tùy biến khác.

**3. Entity dùng property access, backing field là `private transient String label;` nhưng có `getLabel()` và `setLabel()`. Đã chắc chắn không được JPA lưu chưa?**

Chưa. Property vẫn có thể là persistent; dùng `@Transient` trên getter để loại khỏi JPA mapping.

**4. `@Column(updatable = false)` có khiến field thành non-persistent không?**

Không. Field vẫn được ánh xạ và đọc; thuộc tính `updatable` điều chỉnh cách provider ghi SQL UPDATE qua mapping đó.

**5. Với field access, tại sao một getter `getFullName()` không cần `@Transient`?**

Vì JPA ánh xạ field, không tự ánh xạ từng getter. Nếu không có field persistent riêng cho `fullName`, getter tính toán không tạo cột.

**6. Dùng `@Transient` đã đủ bảo đảm một secret không lộ qua JSON API chưa?**

Chưa. Cần thiết kế response/DTO và cấu hình JSON serialization riêng; annotation JPA chỉ điều khiển mapping database.

## 13. Ghi nhớ cốt lõi

**Trường không lưu** là kết quả của việc một thuộc tính không tham gia persistence mapping. **`@Transient`** là cách diễn đạt trực tiếp của JPA để loại một field/property khỏi mapping. **`transient`** là từ khóa Java dùng để loại field khỏi Java Object Serialization mặc định; với **field access** nó còn làm field không được JPA persist, nhưng với **property access** không thể thay thế `@Transient` trên getter.

Để sử dụng đúng, hãy luôn trả lời ba câu hỏi: **Entity đang dùng field access hay property access? Dữ liệu có cần tồn tại trong database không? Nó có cần xuất hiện trong Java serialization hoặc JSON không?** Khi phân biệt được ba phạm vi đó, việc ánh xạ thuộc tính sẽ rõ ràng và ít bất ngờ hơn khi ứng dụng phát triển.
