# Đánh dấu entity để xóa bằng remove

Trong JPA/Hibernate, xóa một hàng dữ liệu không bắt đầu bằng việc viết trực tiếp lệnh SQL `DELETE`. Ở tầng object, ứng dụng có thể gọi **`EntityManager.remove(entity)`** để báo rằng một **entity đang được quản lý (*managed*)** cần bị xóa khỏi hệ thống persistence.

Điểm quan trọng nằm ở chữ **đánh dấu**: lời gọi `remove()` chuyển entity sang trạng thái *removed* trong persistence context; câu SQL xóa thường được đồng bộ xuống database tại thời điểm **flush**, và chỉ khi **transaction commit thành công** việc xóa mới được xác nhận bền vững. Nếu rollback, thay đổi ở database không được commit. Cùng với đó, quan hệ đến entity khác, khóa ngoại, cascade, optimistic locking và quy tắc nghiệp vụ có thể quyết định một lệnh xóa hợp lệ hay bị từ chối.

Bài học này tập trung vào vòng đời entity và cách dùng `remove()` đúng ngữ cảnh: từ một bản ghi đơn giản đến entity có các quan hệ, từ ứng dụng Java SE đến Spring Data JPA, và từ *hard delete* đến các trường hợp không nên xóa vật lý.

## 1. EntityManager.remove() thực sự làm gì?

Phương thức cốt lõi:

~~~java
entityManager.remove(entity);
~~~

Đối số phải là một **entity instance**, không phải giá trị khóa chính. Thông thường, entity này phải đang được quản lý trong persistence context hiện tại.

Luồng xử lý điển hình:

~~~text
Entity tồn tại trong database
            |
            | em.find(...) hoặc truy vấn JPA
            v
      MANAGED ENTITY
            |
            | em.remove(entity)
            v
       REMOVED STATE
            |
            | flush (tường minh hoặc tại commit)
            v
      SQL DELETE được thực thi
            |
            | transaction commit thành công
            v
   Bản ghi được xóa bền vững trong DB
~~~

Cần phân biệt rõ bốn thời điểm:

1. **Tìm entity:** `find()` hoặc query đưa entity vào persistence context ở trạng thái managed.
2. **Gọi `remove()`:** JPA ghi nhận ý định xóa và chuyển entity sang trạng thái removed.
3. **Flush:** provider đồng bộ thao tác cần thiết với database, thường phát lệnh `DELETE` và có thể phát sinh lỗi constraint.
4. **Commit:** transaction được xác nhận. Trước commit, lệnh SQL DELETE đã thực thi vẫn có thể bị rollback.

Không nên viết tài liệu hoặc API với giả định rằng **`remove()` lập tức xóa vĩnh viễn dữ liệu**. Thời điểm thực thi SQL phụ thuộc provider, flush mode, transaction và các thao tác đang pending.

### 1.1. Ví dụ đơn giản

Giả sử bảng `notes` gồm `id` và `content`. Ta muốn xóa ghi chú có ID 15:

~~~java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Note note = em.find(Note.class, 15L);

    if (note != null) {
        em.remove(note);
    }

    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
} finally {
    em.close();
}
~~~

Đoạn code trên là cách dùng cơ bản trong ứng dụng Java SE với transaction kiểu `RESOURCE_LOCAL`:

- `em.find(Note.class, 15L)` tìm theo khóa chính và trả entity managed hoặc `null`.
- `em.remove(note)` yêu cầu xóa entity đã managed.
- `tx.commit()` kết thúc transaction thành công, đồng thời làm các thay đổi pending được flush theo quy tắc provider.
- Nếu có lỗi, transaction được rollback; EntityManager được đóng ở `finally`.

Nếu không tìm thấy entity, ví dụ này coi thao tác xóa là **không làm gì**. Một API khác có thể chọn trả lỗi “không tìm thấy”, nhưng đó là quyết định nghiệp vụ chứ không phải điều kiện bắt buộc của `remove()`.

## 2. Một entity hoàn chỉnh để minh họa

Định nghĩa `Note`:

~~~java
package com.example.notes;

import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "notes")
public class Note {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 1000)
    private String content;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    @Version
    private Long version;

    protected Note() {
        // Constructor cho JPA
    }

    public Note(String content, Instant createdAt) {
        if (content == null || content.isBlank()) {
            throw new IllegalArgumentException("Nội dung không được rỗng");
        }
        this.content = content;
        this.createdAt = createdAt;
    }

    public Long getId() {
        return id;
    }

    public String getContent() {
        return content;
    }

    public void changeContent(String content) {
        if (content == null || content.isBlank()) {
            throw new IllegalArgumentException("Nội dung không được rỗng");
        }
        this.content = content;
    }

    public Long getVersion() {
        return version;
    }
}
~~~

Một schema PostgreSQL tương ứng:

~~~sql
CREATE TABLE notes (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    content VARCHAR(1000) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    version BIGINT NOT NULL
);
~~~

Trong ví dụ, `@Version` giúp provider phát hiện một số xung đột cập nhật/xóa khi nhiều transaction tác động cùng bản ghi. Việc khởi tạo `version` cho bản ghi mới và cập nhật qua mỗi thay đổi do JPA provider xử lý khi entity được persist đúng cách.

### 2.1. Tạo trước rồi xóa ở transaction khác

Tạo ghi chú:

~~~java
Long noteId;

EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Note note = new Note(
        "Học về vòng đời entity",
        Instant.now()
    );

    em.persist(note);
    em.flush(); // Đảm bảo dữ liệu/ID được đồng bộ trong transaction.

    noteId = note.getId();
    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) tx.rollback();
    throw ex;
} finally {
    em.close();
}
~~~

Trong ứng dụng thực, biến `noteId` cần được khai báo và luồng lỗi cần được thiết kế để giá trị chỉ được sử dụng khi transaction commit thành công. Mẫu trên minh họa cách lấy khóa sau khi đồng bộ INSERT.

Xóa trong transaction khác:

~~~java
EntityManager deleteEm = emf.createEntityManager();
EntityTransaction deleteTx = deleteEm.getTransaction();

try {
    deleteTx.begin();

    Note managed = deleteEm.find(Note.class, noteId);
    if (managed != null) {
        deleteEm.remove(managed);
    }

    deleteTx.commit();
} catch (RuntimeException ex) {
    if (deleteTx.isActive()) deleteTx.rollback();
    throw ex;
} finally {
    deleteEm.close();
}
~~~

Điểm đáng nhớ: trong transaction xóa, ta tải **một Note managed trong context của `deleteEm`**. Đối tượng `note` từ transaction tạo trước đó không được giả định là managed trong context mới.

## 3. Removed là một trạng thái của vòng đời JPA

Vòng đời cơ bản của JPA entity có các trạng thái:

| Trạng thái | Ý nghĩa | Cách thường đi vào |
|---|---|---|
| **New / transient** | Object mới tạo, chưa được persistence context quản lý | `new Note(...)` |
| **Managed** | Entity được context theo dõi, thay đổi có thể được đồng bộ | `persist()`, `find()`, query, kết quả `merge()` |
| **Detached** | Entity từng managed, nhưng không còn thuộc context đang xét | `detach()`, `clear()`, `close()` |
| **Removed** | Entity đã được đánh dấu cần xóa trong context | `remove()` trên managed entity |

Sơ đồ khái niệm:

~~~text
          new Note(...)
                |
                | persist
                v
              MANAGED
              /     \
     detach /        \ remove
            v         v
        DETACHED    REMOVED
            |          |
            | merge    | flush -> DELETE
            v          | commit -> xác nhận xóa
         MANAGED       v
        (instance    DB không còn hàng
          trả về)
~~~

Đây là hình dung về trạng thái object và transaction; database không lưu một cột có giá trị “REMOVED” chỉ vì JPA đặt entity vào removed state.

### 3.1. Removed không đồng nghĩa object Java bị hủy

~~~java
Note note = em.find(Note.class, 15L);
em.remove(note);

// Biến note vẫn tham chiếu tới một object Java.
System.out.println(note.getId());
~~~

Gọi `remove()` không xóa object Java khỏi heap, không làm biến `note` thành `null` và không tự cắt mọi tham chiếu từ object khác. Nó thay đổi cách persistence context xử lý instance này.

Đây là lý do không nên sử dụng sự tồn tại của object Java trong một biến, một collection hoặc một DTO để kết luận bản ghi vẫn tồn tại trong database.

### 3.2. Entity đã removed có còn là managed không?

Ở cấp mô hình vòng đời JPA, **removed** là trạng thái riêng với **managed** thông thường: entity được context theo dõi cho mục đích thực hiện thao tác xóa, nhưng không còn là entity đang hoạt động để tiếp tục chỉnh sửa như bình thường.

Không nên dựa vào hành vi của `contains()`, `find()` hoặc các thao tác sửa thuộc tính trên một entity đã removed để phục hồi nó. Tốt nhất xem `remove()` là một bước chuyển trạng thái có chủ đích và kết thúc unit of work bằng commit/rollback.

### 3.3. Sau rollback, object có tự “quay lại” không?

Giả sử:

~~~java
tx.begin();

Note note = em.find(Note.class, 15L);
em.remove(note);

tx.rollback();
~~~

Rollback đảm bảo thao tác DELETE chưa commit không trở thành thay đổi bền vững trong database. Nhưng **rollback không phải nút “undo” cho object graph trong Java**. Trạng thái entity và tính hợp lệ để tiếp tục làm việc sau rollback phụ thuộc phạm vi/context và provider; với application-managed EntityManager, nên đóng context sau lỗi và mở unit of work mới.

Nếu cần xác minh bản ghi còn tồn tại sau rollback, hãy tìm lại bằng một EntityManager mới và transaction phù hợp.

## 4. Chỉ gọi remove() đúng với entity đang managed

Một lỗi phổ biến là lấy object ở transaction A, giữ nó trong controller, rồi mang sang transaction B và gọi `remove()` trực tiếp.

Ví dụ **không đúng**:

~~~java
EntityManager em1 = emf.createEntityManager();
Note detached = em1.find(Note.class, 15L);
em1.close(); // Object vừa tải trở thành detached.

EntityManager em2 = emf.createEntityManager();
EntityTransaction tx2 = em2.getTransaction();

try {
    tx2.begin();

    em2.remove(detached); // Sai: detached không thuộc em2.

    tx2.commit();
} finally {
    if (tx2.isActive()) tx2.rollback();
    em2.close();
}
~~~

JPA không yêu cầu `remove()` chấp nhận detached entity; provider có thể ném `IllegalArgumentException` ngay hoặc ở thời điểm đồng bộ tương ứng. Không nên dựa vào việc object có ID hợp lệ là đủ để xóa nó.

**Quy tắc:** tải hoặc nhận một managed instance từ **chính persistence context** sẽ thực hiện lệnh xóa.

### 4.1. Cách khuyến nghị: tìm lại rồi remove

~~~java
EntityManager em2 = emf.createEntityManager();
EntityTransaction tx2 = em2.getTransaction();

try {
    tx2.begin();

    Note managed = em2.find(Note.class, detached.getId());

    if (managed != null) {
        em2.remove(managed);
    }

    tx2.commit();
} catch (RuntimeException ex) {
    if (tx2.isActive()) tx2.rollback();
    throw ex;
} finally {
    em2.close();
}
~~~

Lợi ích:

- Phân biệt rõ ID với Java object ở transaction trước.
- Cho phép kiểm tra bản ghi còn tồn tại hay không.
- Có thể xác thực điều kiện nghiệp vụ, trạng thái, quyền của người gọi trước khi xóa.
- Object truyền vào `remove()` chắc chắn là managed nếu `find()` trả về một instance hợp lệ.

### 4.2. Có thể merge rồi remove không?

Về mặt kỹ thuật, trong tình huống phù hợp:

~~~java
Note managedCopy = em.merge(detached);
em.remove(managedCopy);
~~~

`merge()` trả về một managed instance, và ta gọi remove trên **instance trả về** chứ không phải object detached đầu vào.

Tuy nhiên, cách này thường **không phải lựa chọn ưu tiên cho thao tác xóa theo ID** vì:

- `merge()` có semantics **sao chép trạng thái** từ detached object sang managed object.
- Có thể kéo theo cascade merge hoặc thay đổi không liên quan trước khi xóa.
- Nếu dữ liệu detached đã cũ, các trường của nó không đáng tin để làm điều kiện xóa.
- Khi entity đã bị xóa hoặc có tình trạng version xung đột, merge có thể có hành vi/exception tùy trường hợp và provider.
- Xóa theo ID thường rõ nghĩa hơn khi thực hiện bằng `find()` rồi kiểm tra điều kiện trước khi `remove()`.

Nếu service nhận request “xóa Note ID 15”, **truyền ID vào service, không truyền một entity detached từ HTTP request**.

### 4.3. getReference() và remove()

Nếu biết ID và muốn tránh tải toàn bộ cột, đôi khi có thể lấy một reference:

~~~java
Note reference = em.getReference(Note.class, 15L);
em.remove(reference);
~~~

Cách này có thể phù hợp khi chỉ cần xóa theo ID và không cần kiểm tra thuộc tính, nhưng cần hiểu:

- Provider có thể cần query để xử lý `remove()`, callback, version hoặc association.
- `getReference()` không bảo đảm bản ghi thực sự tồn tại trước khi thao tác.
- Với ID không tồn tại, có thể phát sinh `EntityNotFoundException` hoặc lỗi khi flush/commit tùy hành vi provider.
- Xóa qua reference không thay việc xác thực business rule/authorization.
- Nếu có các quan hệ/cascade, SQL phát sinh có thể phức tạp hơn dự kiến.

Trong ví dụ nghiệp vụ có trạng thái hoặc cần phản hồi 404 rõ ràng, `find()` thường dễ giải thích hơn.

## 5. Khi nào SQL DELETE thật sự được phát?

JPA áp dụng mô hình *write-behind*: ứng dụng thao tác với managed entity và persistence context tích lũy những thay đổi để đồng bộ vào database khi thích hợp.

~~~java
tx.begin();

Note note = em.find(Note.class, 15L);
em.remove(note);

// Chưa nên giả định DELETE đã chạy tại đây.

em.flush();
// Các thay đổi pending liên quan được đồng bộ xuống database.
// DELETE có thể được thực thi vào thời điểm flush.

tx.commit();
// Transaction được xác nhận thành công.
~~~

Phân biệt:

| Thao tác | Mục tiêu | Có chắc đã commit? |
|---|---|---|
| `em.remove(note)` | Đánh dấu entity cần xóa | Không |
| `em.flush()` | Yêu cầu đồng bộ trạng thái pending bằng SQL | Không |
| `tx.commit()` | Xác nhận transaction, flush cần thiết | Có nếu commit thành công |
| `tx.rollback()` | Hủy thay đổi transaction chưa commit | Không |
| `em.clear()` | Bỏ quản lý các entity trong context | Không phải thao tác xóa DB |

Flush có thể diễn ra do gọi `flush()` tường minh, trước một số truy vấn tùy flush mode, hoặc trong quá trình commit. Không nên khẳng định một SQL DELETE luôn được thực thi **ngay tại dòng `remove()`** hay luôn chờ tới đúng dòng `commit()`.

### 5.1. Flush có thể phát hiện lỗi trước commit

Giả sử Note đang được một bảng khác tham chiếu bởi khóa ngoại `NOT NULL` và không có chính sách xóa phụ thuộc. Khi `em.flush()`, database có thể từ chối DELETE do vi phạm FK.

~~~java
try {
    em.remove(note);
    em.flush(); // Có thể gặp PersistenceException/constraint violation.
} catch (RuntimeException ex) {
    // Đánh dấu rollback, không tiếp tục như thể transaction vẫn hợp lệ.
    throw ex;
}
~~~

Lỗi có thể xuất hiện tại flush **hoặc** commit, tùy thứ tự SQL và provider. Vì vậy một API không được báo “đã xóa thành công” trước khi transaction thực sự commit.

### 5.2. Câu lệnh SELECT sau remove có phản ánh điều gì?

Vì entity đã bị đánh dấu removed trong context, JPA có quy tắc riêng khi tìm lại identity này; không nên dùng việc gọi lại `find()` hay query trong cùng context như một phép kiểm chứng dữ liệu đã bị xóa vĩnh viễn.

Để kiểm chứng sau commit:

~~~java
EntityManager verifyEm = emf.createEntityManager();
try {
    Note stillThere = verifyEm.find(Note.class, 15L);

    System.out.println(stillThere == null);
} finally {
    verifyEm.close();
}
~~~

Ví dụ giả định transaction xóa đã commit thành công, dùng context mới, cùng database và điều kiện đọc phù hợp. Trạng thái cache, database replication hoặc transaction isolation cũng cần được xem xét trong hệ thống phức tạp.

## 6. remove() với entity mới, detached và removed

Phân biệt theo trạng thái đầu vào:

| Trạng thái của đối số | Kỳ vọng đối với `remove()` |
|---|---|
| Managed | Đánh dấu entity cần xóa; hành vi chính của API |
| New / transient | Lệnh remove trên chính entity mới thường bị bỏ qua; cascade REMOVE nếu khai báo phù hợp vẫn có thể được xử lý |
| Detached | Không hợp lệ như managed entity; có thể nhận `IllegalArgumentException` ở thao tác hoặc tại thời điểm flush |
| Removed | Đã được đánh dấu xóa; không nên gọi lặp để kỳ vọng có tác dụng mới |
| Không phải entity object | Đối số không hợp lệ; không thể truyền `Long id` thay instance entity |

Ví dụ:

~~~java
Note newNote = new Note("Chưa persist", Instant.now());

// Đây không phải cách 'xóa khỏi DB' một object chưa được lưu.
// Không cần remove chỉ để bỏ một object transient.
~~~

Nếu chưa `persist()`, object chưa có bản ghi tương ứng cần xóa. Để “hủy tạo” trong code, thường chỉ cần không persist nó và cho object được thu gom bộ nhớ khi không còn tham chiếu.

Với entity đã removed, đừng tiếp tục sửa field rồi hy vọng dirty checking sẽ ghi lại các thay đổi như một entity đang hoạt động. Muốn tạo một bản ghi mới có thể cần entity mới với identity mới và nghiệp vụ rõ ràng; không dùng `remove()` rồi tùy tiện `persist()` lại cùng instance như một thao tác “undo”.

## 7. CascadeType.REMOVE: xóa có thể lan tới entity liên quan

Một entity thường có quan hệ với entity khác. Khi xóa entity cha, câu hỏi lớn là **entity con có bị xóa theo hay không**.

JPA hỗ trợ cascade:

~~~java
@OneToMany(
    mappedBy = "project",
    cascade = CascadeType.REMOVE
)
private List<ProjectTask> tasks;
~~~

`CascadeType.REMOVE` có nghĩa khi thao tác `remove()` được áp dụng lên Project đang managed, thao tác remove có thể được **lan truyền tới các entity ProjectTask trong quan hệ** theo quy tắc JPA.

`CascadeType.ALL` bao gồm cả `REMOVE`, nên nó cũng có thể gây xóa các entity liên quan.

### 7.1. Ví dụ Project sở hữu vòng đời của Task

Giả sử một Project chứa các Task, và mọi Task đều phải thuộc về Project đó. Khi Project bị xóa hẳn, business rule cho phép xóa toàn bộ Task.

Entity Project:

~~~java
package com.example.projects;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "projects")
public class Project {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @OneToMany(
        mappedBy = "project",
        cascade = {CascadeType.PERSIST, CascadeType.REMOVE},
        orphanRemoval = true
    )
    private List<ProjectTask> tasks = new ArrayList<>();

    protected Project() {}

    public Project(String name) {
        this.name = Objects.requireNonNull(name);
    }

    public void addTask(ProjectTask task) {
        Objects.requireNonNull(task);
        tasks.add(task);
        task.assignProject(this);
    }

    public void removeTask(ProjectTask task) {
        if (tasks.remove(task)) {
            task.assignProject(null);
        }
    }
}
~~~

Entity Task:

~~~java
package com.example.projects;

import jakarta.persistence.*;

@Entity
@Table(name = "project_tasks")
public class ProjectTask {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String title;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "project_id", nullable = false)
    private Project project;

    protected ProjectTask() {}

    public ProjectTask(String title) {
        this.title = title;
    }

    void assignProject(Project project) {
        this.project = project;
    }
}
~~~

Đây là mô hình minh họa **Task phụ thuộc vòng đời của Project**. Lưu ý `project_id` không nullable ở schema, nên phương thức `removeTask()` chỉ hợp lệ khi `orphanRemoval = true` làm provider xóa Task không còn thuộc Project; nếu bỏ orphanRemoval mà chỉ gán Project = null, có thể vi phạm NOT NULL khi flush.

Với thiết kế có lịch sử task, audit hoặc project chỉ bị archive, có thể không nên xóa tất cả Task. Cascade phải phản ánh **vòng đời nghiệp vụ thật**, không phải mặc định của mọi `@OneToMany`.

### 7.2. remove(Project) và removeTask(task) là hai thao tác khác

~~~java
Project project = em.find(Project.class, projectId);

// Xóa cả Project và các Task có cascade remove.
em.remove(project);
~~~

Khác với:

~~~java
Project project = em.find(Project.class, projectId);
ProjectTask task = ...; // Một Task thuộc project, managed theo context.

project.removeTask(task);
// Với orphanRemoval = true, Task bị tách có thể được đánh dấu xóa.
// Project vẫn tồn tại.
~~~

Bảng phân biệt:

| Thao tác | Entity bị tác động |
|---|---|
| `em.remove(project)` | Xóa Project; cascade remove có thể xóa Tasks |
| `project.removeTask(task)` và `orphanRemoval = true` | Xóa Task bị loại khỏi quan hệ; Project còn |
| Chỉ gán `task.project = null` khi DB FK NOT NULL | Có thể vi phạm ràng buộc; phải chọn quy tắc đúng |
| `em.remove(task)` | Xóa Task cụ thể; phải đồng bộ object graph nếu đang giữ list của Project |

Khi entity hai chiều còn được dùng trong cùng transaction, helper methods nên duy trì cả hai phía trong bộ nhớ. Nếu xóa trực tiếp Task bằng `em.remove(task)`, collection `Project.tasks` đã khởi tạo có thể vẫn giữ tham chiếu cho đến khi code cập nhật object graph hoặc context được làm mới.

## 8. Khi KHÔNG được cascade REMOVE

Đây là một lỗi nguy hiểm trong nhiều mô hình.

Giả sử `Student` và `Course` có quan hệ nhiều-nhiều:

~~~text
Student A ---- Course Java
Student B ---- Course Java
~~~

Nếu xóa Student A, Course Java vẫn cần tồn tại vì Student B đang học. Không được cấu hình:

~~~java
// Sai nếu Course được chia sẻ và có vòng đời độc lập:
@ManyToMany(cascade = CascadeType.ALL)
private Set<Course> courses;
~~~

`ALL` gồm `REMOVE`, có thể làm provider cố xóa Course khi xóa Student. Đó là xóa một resource được nhiều entity sử dụng, không phải chỉ xóa liên kết.

Mapping phù hợp hơn:

~~~java
@ManyToMany(fetch = FetchType.LAZY)
@JoinTable(
    name = "student_courses",
    joinColumns = @JoinColumn(name = "student_id"),
    inverseJoinColumns = @JoinColumn(name = "course_id")
)
private Set<Course> courses = new HashSet<>();
~~~

Để sinh viên rút khỏi một khóa:

~~~java
student.getCourses().remove(course);
~~~

Ví dụ này giả định getter cho phép sửa collection và đang tác động ở **owning side**. Trong code production nên dùng helper như `student.withdrawFrom(course)` để giữ object graph hai chiều nhất quán.

**Xóa một liên kết bảng nối** không phải **xóa Course**. Nếu chỉ muốn rút học, thao tác collection/association phù hợp hơn `em.remove(course)`.

### 8.1. Quan hệ ManyToOne thường không cascade REMOVE tới cha

Ví dụ mỗi `PurchaseOrder` thuộc về một `Customer`:

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "customer_id", nullable = false)
private Customer customer;
~~~

Xóa một PurchaseOrder không có nghĩa xóa Customer. Các đơn hàng khác có thể cùng tham chiếu Customer.

Không đặt `cascade = CascadeType.REMOVE` trên ManyToOne chỉ để “tiện”, vì từ entity con thao tác có thể lan ngược tới entity cha dùng chung. Cần xét quyền sở hữu vòng đời và rule nghiệp vụ ở cả hai phía.

### 8.2. Một-một vẫn cần xem vòng đời

Với `Account` và `AccountProfile`, nếu profile là một phần phụ thuộc hoàn toàn vào Account, `cascade = REMOVE` có thể hợp lý. Nhưng nếu profile có lịch sử độc lập cần giữ, hoặc là record dùng để tuân thủ chính sách dữ liệu, xóa Account không nhất thiết xóa profile vật lý.

**Bội số 1:1 không tự suy ra cascade REMOVE**. Quy tắc xóa phải dựa trên dependency/lifecycle thực tế.

## 9. Orphan removal khác CascadeType.REMOVE thế nào?

Cả hai có thể dẫn đến DELETE entity con, nhưng trigger khác nhau:

| Cơ chế | Khi nào hoạt động | Use case điển hình |
|---|---|---|
| `cascade = CascadeType.REMOVE` | Khi parent bị gọi `remove()` và operation lan tới child | Xóa Project thì xóa các Task thuộc Project |
| `orphanRemoval = true` | Khi child bị loại khỏi quan hệ thuộc quyền sở hữu của parent theo mapping phù hợp | Bỏ một Task khỏi Project, Task không còn được giữ |
| `@ManyToMany` không có orphanRemoval | Không áp dụng semantics “xóa entity bên kia khi bỏ liên kết” | Student rút khỏi Course chỉ xóa hàng join table |
| Foreign key `ON DELETE CASCADE` | Khi DB xóa hàng được tham chiếu, DB tự xóa hàng phụ thuộc | Xử lý referential integrity ở SQL, không phải JPA cascade |

Ví dụ:

~~~java
Project managedProject = em.find(Project.class, projectId);

// remove một Task khỏi collection với orphanRemoval = true:
managedProject.removeTask(task);
~~~

Nếu Task được thiết kế là thành phần sở hữu độc quyền của Project, việc xóa Task khi không còn thuộc Project có thể đúng. Nếu Task được chia sẻ giữa nhiều Project, mô hình đó có thể không phù hợp; không dùng orphanRemoval để xóa đối tượng độc lập.

Không có thuộc tính `orphanRemoval` trên `@ManyToMany` theo JPA. Với many-to-many, loại bỏ phần tử khỏi collection owning side chủ yếu thay đổi bảng nối.

## 10. Ràng buộc khóa ngoại và thứ tự xóa

SQL DELETE cuối cùng vẫn phải tuân thủ ràng buộc cơ sở dữ liệu.

Ví dụ:

~~~sql
CREATE TABLE customers (
    id BIGINT PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);
~~~

Nếu Customer 10 còn Order 100, lệnh:

~~~sql
DELETE FROM customers WHERE id = 10;
~~~

có thể bị database từ chối do foreign key, trừ khi schema có chính sách `ON DELETE` tương ứng hoặc đã xử lý hàng con.

JPA `remove(customer)` **không làm ràng buộc foreign key biến mất**. Phải chọn một chính sách nghiệp vụ:

1. **Không cho xóa Customer khi còn Order:** trả lỗi có ý nghĩa.
2. **Archive/soft delete Customer:** giữ khóa và lịch sử, hạn chế các thao tác tiếp theo.
3. **Được xóa cả dữ liệu phụ thuộc:** chỉ khi nghiệp vụ và quy định lưu trữ cho phép; phải cấu hình cascade/order/constraints hợp lý.
4. **Ẩn danh hóa dữ liệu cá nhân theo chính sách:** không đồng nghĩa xóa Order, và phải thiết kế rõ trường nào có thể thay đổi.

### 10.1. Thứ tự DELETE do ORM và DB quyết định

Khi nhiều entity có quan hệ FK, provider có thể cần xóa bản ghi con trước rồi xóa cha. JPA cascade định nghĩa ý nghĩa lan truyền thao tác, nhưng SQL được phát theo cách provider/DBMS điều phối để đáp ứng ràng buộc.

Đừng viết code trông đợi rằng thứ tự gọi `remove(a)` và `remove(b)` luôn tương ứng 1:1 với thứ tự SQL cuối cùng. Lỗi integrity constraint có thể xuất hiện tại flush/commit khi database kiểm tra các ràng buộc liên quan.

### 10.2. Database ON DELETE CASCADE không phải CascadeType.REMOVE

DDL:

~~~sql
CREATE TABLE order_items (
    id BIGINT PRIMARY KEY,
    order_id BIGINT NOT NULL
        REFERENCES orders(id) ON DELETE CASCADE
);
~~~

Nếu database xóa một hàng `orders`, database có thể tự xóa các hàng `order_items` liên quan. Đây là **cơ chế của FK trong database**.

Ngược lại:

~~~java
@OneToMany(mappedBy = "order", cascade = CascadeType.REMOVE)
private List<OrderItem> items;
~~~

là **cơ chế JPA** lan truyền lệnh remove tới các entity `OrderItem`.

Sự khác biệt quan trọng:

- DB cascade có thể thực thi xóa mà không gọi callback JPA của từng child.
- JPA cascade có thể khiến provider tải/quản lý các entity phụ thuộc để thực hiện xóa và callback tương ứng.
- Kết hợp cả hai đòi hỏi hiểu rõ flush, persistence context, callback và trạng thái cache của provider.
- DB cascade chỉ phát sinh theo quan hệ FK đã khai báo, không có nghĩa mọi association phía Java đều được xóa theo.

Không chọn cascade chỉ dựa vào mục tiêu “ít SQL”; còn phải xét audit, domain events và vòng đời dữ liệu.

## 11. @PreRemove và @PostRemove

JPA có lifecycle callbacks để thực thi logic liên quan tới vòng đời:

~~~java
import jakarta.persistence.*;

@Entity
public class Document {

    @Id
    private Long id;

    private String title;

    @PreRemove
    void beforeRemove() {
        // Kiểm tra/tác vụ cục bộ thích hợp trước khi xóa.
    }

    @PostRemove
    void afterRemove() {
        // Callback sau thao tác xóa ở persistence layer.
    }
}
~~~

Ý nghĩa khái quát:

- `@PreRemove` được gọi trước khi entity được xóa theo quy trình JPA.
- `@PostRemove` được gọi sau khi thao tác xóa entity đã được thực hiện ở tầng persistence, có thể tại thời điểm flush; **không đồng nghĩa transaction đã commit thành công**.
- Callback có thể nằm trên entity hoặc listener được cấu hình.

### 11.1. Không gửi email ngay trong callback xóa

Nếu `@PostRemove` gửi email “tài liệu đã bị xóa”, nhưng transaction cuối cùng rollback, email đã gửi không thể được rollback cùng database. Đây là sai lệch giữa external side effect và transaction.

Với nghiệp vụ cần phát thông báo sau khi commit:

- Service xác định kết quả xóa.
- Ghi event/outbox record trong cùng DB transaction nếu cần bảo đảm giao hàng.
- Worker xử lý outbox sau commit, hỗ trợ retry/idempotency.
- Hoặc dùng sự kiện sau commit của framework phù hợp, nhưng phải hiểu cơ chế đảm bảo và xử lý lỗi.

Không dùng lifecycle callback như một nơi bất kỳ để truy vấn/sửa hàng loạt entity qua EntityManager, gây phụ thuộc ngầm và có thể vi phạm hạn chế/semantics callback. Giữ callback ngắn và có chủ đích.

### 11.2. Callback không chạy cho mọi cách xóa

JPQL bulk DELETE hoặc SQL native trực tiếp có thể bỏ qua cơ chế entity lifecycle callbacks và cascade do JPA quản lý. Vì vậy nếu audit bắt buộc, không dựa hoàn toàn vào `@PreRemove/@PostRemove` khi ứng dụng cũng dùng bulk SQL hoặc có writer khác bên ngoài ORM.

## 12. Bulk DELETE khác EntityManager.remove()

JPA hỗ trợ xóa nhiều hàng qua JPQL:

~~~java
int count = em.createQuery(
        """
        DELETE FROM Note n
        WHERE n.createdAt < :cutoff
        """
    )
    .setParameter("cutoff", cutoff)
    .executeUpdate();
~~~

Lợi ích: có thể xóa nhiều hàng bằng một bulk database statement, không cần load từng entity trước. Nhưng ngữ nghĩa **khác** với gọi `remove()` trên từng managed entity.

| Đặc điểm | `em.remove(entity)` | JPQL bulk `DELETE` |
|---|---|---|
| Đầu vào | Managed entity instance | Điều kiện truy vấn |
| Có cần load entity? | Thường có, hoặc managed/reference | Không cần load từng entity |
| Thay đổi trạng thái entity trong context | Có | Bulk thao tác trực tiếp ở DB |
| JPA lifecycle callbacks | Áp dụng theo cơ chế remove của JPA | Không gọi callback cho từng entity bị xóa |
| JPA cascade remove | Có nếu mapping phù hợp | Không tự cascade JPA cho từng entity |
| Optimistic locking tự động theo `@Version` | Có thể kiểm tra version trong thao tác entity | Bulk DELETE không tự mang cùng cơ chế version của entity removal |
| Persistence context | Theo dõi entity bị xóa | Các managed entity đang có có thể trở nên stale |
| Phù hợp | Xóa một số entity có domain/lifecycle | Dọn dẹp hàng loạt có chủ đích, constraints được xử lý rõ |

### 12.1. Bulk DELETE và persistence context stale

~~~java
Note note = em.find(Note.class, 15L);

int deleted = em.createQuery(
        "DELETE FROM Note n WHERE n.id = :id"
    )
    .setParameter("id", 15L)
    .executeUpdate();

// Biến note có thể vẫn được persistence context coi như entity managed
// với trạng thái trước bulk DELETE.
~~~

Bulk operation không đi qua vòng đời entity của từng object đã managed, nên context có thể không phản ánh database sau lệnh xóa.

Một chiến lược thường dùng sau bulk DML là kiểm soát các thay đổi pending rồi `clear()`/tạo context mới, nhưng phải hiểu rằng:

- `clear()` detach toàn bộ entity và có thể bỏ các thay đổi chưa flush.
- `flush()` trước bulk operation có thể cần để đảm bảo DML pending đã đồng bộ đúng thứ tự.
- Những reference cũ vẫn tồn tại trong Java object graph nhưng không còn là dữ liệu đáng tin sau bulk.
- Dữ liệu cascade bằng foreign key ở DB và auditing phải được xem xét riêng.

Nếu dự án Spring Data JPA dùng repository delete query có `@Modifying`, có các tùy chọn flush/clear context; cách dùng cần phù hợp với transaction và toàn bộ unit of work.

### 12.2. Bulk DELETE không phải lúc nào cũng an toàn hơn

Xóa hàng loạt có thể tạo lock lớn, transaction dài, ảnh hưởng index/replication và gây constraint violation. Nếu có ràng buộc FK, SQL DELETE vẫn phải đáp ứng chúng hoặc chính sách cascade DB. Không dùng bulk delete chỉ để né cascade hay rule nghiệp vụ của entity.

## 13. Xóa trong Spring Data JPA

Trong Spring Boot/Spring Data JPA, có thể viết service với transaction:

~~~java
package com.example.notes;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class NoteService {

    private final NoteRepository notes;

    public NoteService(NoteRepository notes) {
        this.notes = notes;
    }

    @Transactional
    public void deleteById(Long id) {
        Note note = notes.findById(id)
            .orElseThrow(() ->
                new IllegalArgumentException(
                    "Không tìm thấy ghi chú: " + id
                )
            );

        notes.delete(note);
    }
}
~~~

Repository:

~~~java
import org.springframework.data.jpa.repository.JpaRepository;

public interface NoteRepository extends JpaRepository<Note, Long> {
}
~~~

Ý nghĩa:

1. Service mở/tham gia transaction theo cơ chế Spring.
2. `findById()` lấy managed Note thông thường trong persistence context của transaction.
3. `delete(note)` yêu cầu xóa entity theo cơ chế repository/provider tương ứng.
4. Transaction commit sẽ hoàn tất đồng bộ các thay đổi, hoặc rollback nếu xảy ra lỗi.

Không trộn `em.getTransaction().begin()` thủ công với transaction do Spring quản lý thông thường. Các method repository cụ thể như `deleteById()` có thể có chính sách “not found”, query và cách xử lý detached phụ thuộc phiên bản Spring Data JPA; khi nghiệp vụ cần kiểm tra trạng thái trước khi xóa, cách `findById()` rồi `delete(note)` giúp bộc lộ logic hơn.

### 13.1. Dùng trực tiếp EntityManager trong Spring

~~~java
@Service
public class NoteDeletionService {

    @PersistenceContext
    private EntityManager em;

    @Transactional
    public void delete(Long id) {
        Note note = em.find(Note.class, id);

        if (note == null) {
            throw new IllegalArgumentException("Không tìm thấy ghi chú");
        }

        em.remove(note);
    }
}
~~~

Spring có thể inject một EntityManager proxy gắn với transaction hiện tại. Đừng giữ một application-managed EntityManager dùng chung giữa mọi HTTP request. Bên trong transaction service, `em.find()` và `em.remove()` làm việc theo context thích hợp.

### 13.2. Vì sao không nên xóa trong controller?

Nếu controller nhận một entity JSON đã được deserialize, object này không phải entity managed từ persistence context. Truyền object đó trực tiếp vào `remove()` dễ gặp lỗi detached hoặc gây nhầm ID/authorization.

Thiết kế API nên nhận khóa:

~~~text
DELETE /notes/15
        |
        v
Controller nhận id = 15
        |
        v
@Transactional service
        |
        +-- kiểm tra quyền truy cập
        +-- em.find(Note.class, 15)
        +-- kiểm tra trạng thái nghiệp vụ
        +-- em.remove(note)
        +-- commit
        |
        v
Phản hồi theo kết quả transaction
~~~

Quy tắc API khi ID không tồn tại có thể là 404 hoặc một hành vi idempotent không lỗi, tùy hợp đồng ứng dụng; đừng để chi tiết repository tình cờ quyết định contract công khai.

### 13.3. Self-invocation và @Transactional

Trong cấu hình Spring proxy thông thường, lời gọi method `@Transactional` từ một method khác **trên cùng instance** có thể không đi qua proxy, khiến annotation không được áp dụng như kỳ vọng.

Nếu transaction là điều kiện thiết yếu cho xóa, nên đặt ranh giới ở public service method được gọi qua Spring-managed bean/transaction proxy thích hợp. Đây là vấn đề của transaction wiring, không phải khác biệt trong ý nghĩa `remove()` của JPA.

## 14. Soft delete: khi nghiệp vụ không nên xóa vật lý

Nhiều dữ liệu không nên biến mất chỉ vì có yêu cầu “xóa” trong giao diện:

- Đơn hàng đã thanh toán cần lưu để đối soát.
- Hóa đơn/chứng từ có quy trình hủy hoặc điều chỉnh riêng.
- Tài khoản có lịch sử tương tác cần bảo đảm ràng buộc tham chiếu.
- Bản ghi cần audit, pháp lý, khôi phục hoặc cơ chế lưu trữ có thời hạn.

Lựa chọn thường gặp là **soft delete**: cập nhật trạng thái đánh dấu không còn hoạt động thay vì SQL DELETE.

~~~java
@Entity
@Table(name = "documents")
public class Document {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String title;

    @Column(name = "deleted_at")
    private Instant deletedAt;

    protected Document() {}

    public boolean isDeleted() {
        return deletedAt != null;
    }

    public void markDeleted(Instant when) {
        if (deletedAt == null) {
            deletedAt = when;
        }
    }
}
~~~

Service:

~~~java
@Transactional
public void archiveDocument(Long id) {
    Document document = em.find(Document.class, id);
    if (document == null) {
        throw new IllegalArgumentException("Document không tồn tại");
    }

    document.markDeleted(Instant.now());
    // Dirty checking -> UPDATE deleted_at = ...
    // Không gọi em.remove(document).
}
~~~

Với cách này:

- Entity vẫn tồn tại trong DB, giữ PK và FK.
- Dữ liệu không còn hiển thị trong những truy vấn nghiệp vụ chủ động lọc `deleted_at IS NULL`.
- Có thể giữ ngày/xác định người thao tác nếu nghiệp vụ cần.
- Cần xử lý unique constraint: ví dụ mã bị soft delete có được tái sử dụng không?

### 14.1. Soft delete không phải thay đổi cú pháp của remove()

Trong mapping JPA chuẩn, `em.remove()` biểu thị xóa entity khỏi persistence. Nếu muốn hành vi “remove nhưng thật ra UPDATE deleted_at”, một số phiên bản Hibernate có cơ chế provider-specific như `@SQLDelete` hoặc hỗ trợ soft-delete chuyên biệt.

Chúng **không hoàn toàn portable theo JPA**, và có các hệ quả về cascade, filter/query, association, second-level cache và lifecycle callbacks. Cách dễ hiểu nhất trong domain là định nghĩa một method `archive()/markDeleted()` rồi cập nhật trạng thái thay vì gọi `remove()`.

Nếu tổ chức vẫn muốn override thao tác delete bằng tính năng riêng của Hibernate, cần xem tài liệu chính xác của phiên bản đang sử dụng và thiết kế nhất quán toàn bộ luồng đọc, đếm, tìm theo FK, collection và khôi phục.

### 14.2. Xóa dữ liệu cá nhân: soft delete chưa chắc đủ

Đánh dấu `deleted_at` không đồng nghĩa xóa hoặc ẩn danh hóa dữ liệu cá nhân theo chính sách bảo vệ dữ liệu. Ứng dụng có thể cần quy trình riêng về thời hạn lưu, hạn chế truy cập, ẩn danh hóa hoặc xóa thực tế. Các yêu cầu cụ thể phải được xác định theo luật và chính sách đang áp dụng.

## 15. Concurrency: điều gì xảy ra khi hai người sửa và xóa?

Giả sử hai transaction cùng đọc Note ID 15 ở version 3:

~~~text
Transaction A                  Transaction B
----------------------------------------------------
SELECT Note 15, version = 3
                               SELECT Note 15, version = 3
                               UPDATE content, version = 4
                               COMMIT
em.remove(note version 3)
DELETE theo cơ chế kiểm tra version
=> Có thể OptimisticLockException
~~~

Khi entity có `@Version`, JPA provider dùng optimistic locking để phát hiện những thao tác dựa trên state/version cũ. Xóa có thể thất bại thay vì âm thầm xóa bản ghi vừa được transaction khác cập nhật.

**Identity map chỉ bảo đảm một instance trong một context**, không giải quyết mâu thuẫn giữa hai transaction khác nhau.

### 15.1. Chọn chính sách khi gặp OptimisticLockException

Một chiến lược ứng dụng:

1. Rollback transaction thất bại.
2. Mở transaction/persistence context mới để đọc trạng thái mới.
3. Thông báo người dùng dữ liệu đã thay đổi, hoặc thực hiện retry có giới hạn nếu nghiệp vụ cho phép.
4. Nếu retry, kiểm tra lại quyền, trạng thái và điều kiện xóa; không giả định request cũ vẫn hợp lệ.
5. Không tiếp tục dùng EntityManager đang ở trạng thái transaction thất bại như thể không có gì xảy ra.

Không tự động retry mọi lệnh xóa trong mọi trường hợp. Một thao tác xóa vĩnh viễn có thể cần xác nhận lại khi entity đã được người khác chỉnh sửa.

### 15.2. Pessimistic locking

Khi cần phối hợp cập nhật/xóa chặt chẽ, có thể dùng:

~~~java
Note managed = em.find(
    Note.class,
    id,
    LockModeType.PESSIMISTIC_WRITE
);

if (managed != null) {
    em.remove(managed);
}
~~~

Lock này thường yêu cầu transaction đang hoạt động và được hiện thực qua cơ chế khóa của DBMS/provider. Nó có thể làm tăng contention, deadlock hoặc lock timeout. Không bật locking nặng trên mọi thao tác xóa nếu chưa cần thiết.

### 15.3. Bulk DELETE bỏ qua một phần bảo vệ của entity removal

Một JPQL `DELETE FROM Note n WHERE n.id = :id` không tự áp dụng cùng optimistic version check và lifecycle callbacks như `remove(managedNote)`. Nếu yêu cầu phát hiện xung đột mạnh, cần dùng entity removal có version hoặc viết DML điều kiện rõ version và kiểm tra affected row count theo chiến lược nhất quán.

## 16. Bảo vệ thao tác xóa ở tầng nghiệp vụ

Trước khi gọi `remove()`, service thường cần kiểm tra nhiều điều kiện:

~~~java
@Transactional
public void deleteDraftOrder(Long orderId, Long actorId) {
    PurchaseOrder order = em.find(PurchaseOrder.class, orderId);

    if (order == null) {
        throw new IllegalArgumentException("Đơn hàng không tồn tại");
    }

    authorization.requireCanDelete(actorId, order);

    if (!order.isDraft()) {
        throw new IllegalStateException(
            "Chỉ được xóa đơn hàng ở trạng thái DRAFT"
        );
    }

    em.remove(order);
}
~~~

Đoạn ví dụ giả định có `authorization` và entity `PurchaseOrder` với method `isDraft()`. Mục đích là tách các quy tắc rõ ràng:

- **JPA biết cách xóa một entity.**
- **Domain service quyết định entity có được xóa hay không.**
- **Database constraint bảo đảm ràng buộc dữ liệu ngay cả khi code bị gọi sai.**

Khi các điều kiện có thể thay đổi đồng thời, phải thiết kế `@Version`, locking hoặc điều kiện SQL thích hợp; kiểm tra `order.isDraft()` rồi gọi `remove()` không tự chống mọi race condition.

### 16.1. Idempotency của DELETE HTTP

Ở HTTP, DELETE được thiết kế có tính idempotent về tác động mong muốn: gọi xóa cùng một tài nguyên nhiều lần không nên tạo ra những tác động phụ không kiểm soát.

Tuy nhiên, cách trả response khi entity đã không còn có thể tùy hợp đồng API:

- Trả 204 cho việc xóa thành công và có thể cả việc xóa lặp lại nếu hệ thống coi “đã vắng mặt” là trạng thái mong muốn.
- Trả 404 nếu API cần thông báo tài nguyên không tồn tại.
- Trả 409 nếu business rule không cho phép xóa vì trạng thái hoặc tham chiếu.

Những lựa chọn này không thay đổi việc `EntityManager.find()` trả `null` khi PK không tồn tại. Cũng cần chú ý event/audit khi request retry: không phát hai lần sự kiện “đã xóa thành công” cho một hành động nếu hệ thống đòi tác động một lần.

## 17. Test hành vi remove đúng cách

Với thao tác database, test nên phân biệt:

- Lời gọi `remove()` có được thực hiện trên managed entity hay không.
- Transaction xóa có commit được không.
- Bản ghi đã biến mất trong **context mới** chưa.
- Những entity liên quan cần giữ vẫn còn không.
- Rollback có giữ dữ liệu DB như mong đợi không.

### 17.1. Test xóa một Note

Pseudocode JUnit giả định có EntityManagerFactory và helper tạo Note:

~~~java
@Test
void removeNoteDeletesItsRowAfterCommit() {
    Long id = createCommittedNote("Delete me");

    EntityManager em = emf.createEntityManager();
    EntityTransaction tx = em.getTransaction();

    try {
        tx.begin();

        Note note = em.find(Note.class, id);
        assertNotNull(note);

        em.remove(note);
        tx.commit();
    } finally {
        if (tx.isActive()) tx.rollback();
        em.close();
    }

    EntityManager verify = emf.createEntityManager();
    try {
        assertNull(verify.find(Note.class, id));
    } finally {
        verify.close();
    }
}
~~~

Đây là cấu trúc test minh họa, không phải một class có đầy đủ import/setup/teardown. Test dùng **EntityManager mới** khi kiểm chứng sau commit để tránh bị nhiễu bởi state trong context cũ.

### 17.2. Test rollback

~~~java
@Test
void rollbackKeepsRowInDatabase() {
    Long id = createCommittedNote("Keep me");

    EntityManager em = emf.createEntityManager();
    EntityTransaction tx = em.getTransaction();

    try {
        tx.begin();

        Note note = em.find(Note.class, id);
        assertNotNull(note);

        em.remove(note);
        em.flush();

        tx.rollback();
    } finally {
        if (tx.isActive()) tx.rollback();
        em.close();
    }

    EntityManager verify = emf.createEntityManager();
    try {
        assertNotNull(verify.find(Note.class, id));
    } finally {
        verify.close();
    }
}
~~~

Mục tiêu là xác nhận **lệnh xóa chưa commit được hoàn tác ở DB**. Việc dùng context mới cũng tránh nhầm lẫn với object từng bị đánh dấu removed trong transaction đã rollback.

### 17.3. Test quan hệ

Với Project–Task:

- Xóa Project -> kiểm tra Project mất và Tasks thuộc vòng đời Project bị xóa theo chính sách.
- Xóa một Task -> Project vẫn còn.
- Với Student–Course -> rút khỏi khóa học chỉ xóa hàng join table; cả hai entity vẫn tồn tại.
- Với Customer–Order -> xóa Customer có Order phải theo chính sách: chặn, archive hoặc xử lý dữ liệu phù hợp.
- Không chỉ assert vào collection trong bộ nhớ; kiểm tra dữ liệu thực tế sau commit bằng context mới.

### 17.4. Test lỗi FK và version conflict

Một bài test hữu ích là tạo hai transaction độc lập và sửa/xóa cùng một entity có `@Version`, để thấy cơ chế xung đột khi flush/commit. Cần sắp xếp transaction đúng và tránh dùng một EntityManager dùng chung giữa hai luồng.

Kiểm thử constraint cũng nên khẳng định xóa parent bị từ chối khi child còn tham chiếu và chính sách không cho phép cascade. Không nên để test auto-DDL tạo schema thiếu FK so với production.

## 18. Những sai lầm thường gặp

### Sai lầm 1: Gọi remove() với ID

~~~java
em.remove(15L); // Sai: đối số phải là entity instance.
~~~

Cách đúng:

~~~java
Note managed = em.find(Note.class, 15L);
if (managed != null) {
    em.remove(managed);
}
~~~

### Sai lầm 2: Gọi remove() với detached entity

~~~java
Note detached = previousEntityManager.find(Note.class, 15L);
previousEntityManager.close();

currentEntityManager.remove(detached); // Không phải entity managed hiện tại.
~~~

Cần tải lại entity bằng ID trong context hiện tại hoặc dùng một cách xử lý detached được thiết kế có chủ đích.

### Sai lầm 3: Nghĩ remove() lập tức là DELETE đã commit

~~~java
em.remove(managedNote);
sendDeletionSuccessEmail(); // Có thể quá sớm.
~~~

Transaction còn có thể rollback vì lỗi FK, optimistic locking hoặc sự cố khác. Gửi notification sau commit hoặc dùng outbox.

### Sai lầm 4: Dùng CascadeType.ALL trên mọi quan hệ

~~~java
@ManyToMany(cascade = CascadeType.ALL)
private Set<Tag> tags;
~~~

Xóa entity có thể lan sang Tag dùng chung. Chỉ cascade REMOVE khi entity đầu kia thực sự thuộc vòng đời của entity này.

### Sai lầm 5: Dùng remove() để gỡ một liên kết

~~~java
em.remove(course); // Không đúng nếu chỉ muốn sinh viên rút khóa.
~~~

Hãy sửa owning collection hoặc xóa entity liên kết `Enrollment` nếu đã mô hình hóa Enrollment riêng.

### Sai lầm 6: Gọi clear() để “hoàn tất xóa”

`clear()` chỉ detach các entity, không commit hoặc thực hiện xóa hàng trong database. Nếu xóa pending chưa flush rồi gọi clear, cần hiểu những thay đổi có thể không còn được đồng bộ như mong muốn.

### Sai lầm 7: Dùng bulk DELETE rồi tiếp tục tin các managed entities

JPQL bulk DML có thể bỏ qua persistence context. Sau bulk delete, context có thể giữ các entity đã bị xóa ở DB. Cần flush/clear hoặc context mới theo quy tắc transaction.

### Sai lầm 8: Dựa vào FK cascade như thể nó kích hoạt JPA callbacks

`ON DELETE CASCADE` của database có thể xóa child rows mà không chạy `@PreRemove/@PostRemove` của JPA cho từng child. Nếu cần audit, thiết kế cơ chế phù hợp ở đúng tầng.

### Sai lầm 9: Luôn hard delete dữ liệu có lịch sử

Đơn hàng, chứng từ hoặc dữ liệu cần đối soát có thể không được xóa vật lý. Cần phân tích trạng thái archive/void, luật lưu trữ và các ràng buộc nghiệp vụ trước khi gọi `remove()`.

### Sai lầm 10: Xóa entity đã bị transaction khác cập nhật mà không xử lý concurrency

Khi có `@Version`, `OptimisticLockException` là tín hiệu có xung đột cần xử lý. Không “tắt version cho xóa” chỉ để hết lỗi nếu nghiệp vụ cần bảo vệ dữ liệu.

## 19. Quy trình thực hành cho thao tác xóa

Một quy trình rõ ràng trong service:

1. **Xác định loại xóa:** hard delete, soft delete, archive/void hay chỉ xóa liên kết?
2. **Mở transaction phù hợp:** bằng `EntityTransaction` trong Java SE hoặc `@Transactional` trong Spring.
3. **Tìm entity managed:** `em.find(Entity.class, id)`; xử lý `null` có chủ đích.
4. **Kiểm tra quyền và business rule:** trạng thái, chủ sở hữu, các ràng buộc lịch sử.
5. **Xem xét quan hệ:** CascadeType.REMOVE, orphanRemoval, FK, shared entities, ON DELETE của DB.
6. **Gọi `em.remove(managedEntity)`** nếu đó thực sự là hard delete entity.
7. **Flush nếu cần phát hiện lỗi sớm:** hiểu flush chưa phải commit.
8. **Commit hoặc rollback:** không báo thành công bền vững trước commit.
9. **Xử lý side effects sau commit:** event, email, outbox, cache invalidation theo kiến trúc.
10. **Kiểm tra kết quả qua unit of work mới** khi test hoặc xác minh điều kiện sau commit.

### Bảng chọn thao tác đúng

| Mục tiêu nghiệp vụ | Thao tác JPA/domain thường phù hợp |
|---|---|
| Xóa một Note không còn cần lưu | `find()` -> `remove()` trong transaction |
| Xóa một Project và toàn bộ Tasks phụ thuộc | `remove(project)` + cascade đúng vòng đời |
| Bỏ một Task khỏi Project, Task không còn được giữ | `orphanRemoval = true` với helper phù hợp |
| Sinh viên rút khỏi Course | Bỏ association trong join table, **không remove Course** |
| Xóa một Enrollment entity | `remove(enrollment)`; giữ Student/Course |
| Hủy đơn hàng đã thanh toán | Chuyển trạng thái/có thể tạo nghiệp vụ hoàn tiền hoặc lưu lịch sử, không mặc định hard delete |
| Dọn dữ liệu log cũ rất nhiều hàng | Cân nhắc bulk DELETE với quản lý transaction, FK và cache rõ |
| Xóa theo ID nhận từ API | Service kiểm tra quyền, `find()` managed rồi `remove()` |
| Cần xóa nhưng giữ audit | Thiết kế soft delete/archive hoặc luồng audit tương thích |

## 20. Bài tập vận dụng

### Bài tập 1 — Managed và detached

Cho:

~~~java
EntityManager em1 = emf.createEntityManager();
Note n = em1.find(Note.class, 10L);
em1.close();

EntityManager em2 = emf.createEntityManager();
em2.remove(n);
~~~

Hỏi: Vì sao thao tác có thể lỗi? Sửa lại thành một transaction an toàn dùng ID và managed instance.

**Gợi ý:** `n` detached sau khi `em1.close()`; `em2` không quản lý object đó.

### Bài tập 2 — Flush và rollback

Transaction thực hiện `find()`, `remove()`, `flush()` rồi `rollback()`. Bản ghi sau đó còn không nếu trước đó đã commit tồn tại?

**Gợi ý:** SQL DELETE có thể đã chạy ở flush, nhưng chưa commit; rollback hoàn tác thay đổi database chưa commit.

### Bài tập 3 — Cascade trên nhiều-nhiều

User A và User B cùng có Role ADMIN. Một developer đặt `@ManyToMany(cascade = ALL)` trên User.roles, rồi xóa User A.

Phân tích vì sao nguy hiểm và sửa cách mapping để xóa User A mà không xóa Role ADMIN.

### Bài tập 4 — Parent/child

Một Project có ba Task và `@OneToMany(cascade = REMOVE, orphanRemoval = true)`. Hãy phân biệt:

- `em.remove(project)`;
- `project.removeTask(task1)`;
- `em.remove(task1)` mà không đồng bộ collection của Project.

Mỗi thao tác ảnh hưởng đối tượng nào và điều gì cần chú ý về object graph trong bộ nhớ?

### Bài tập 5 — Xóa Customer có Order

Bảng `orders.customer_id` là FK NOT NULL tới `customers.id`. Không có ON DELETE CASCADE. Nếu gọi `remove(customer)`, điều gì có thể xảy ra ở flush/commit?

Đề xuất ba chính sách hợp lệ tùy nghiệp vụ: chặn xóa, archive/soft delete, hoặc xử lý phụ thuộc khi thực sự được phép.

### Bài tập 6 — Bulk DELETE

Code tải Note 10 bằng `find()` rồi chạy JPQL `DELETE FROM Note n WHERE n.id = 10`. Sau đó tiếp tục dùng object Note trước đó.

Hãy giải thích vấn đề persistence context stale và cách kiểm soát transaction/clear hoặc dùng context mới.

### Bài tập 7 — Optimistic locking

Hai transaction cùng đọc Note version 3. Một transaction sửa nội dung và commit thành version 4, transaction kia muốn xóa theo instance version 3. Khi nào có thể phát sinh `OptimisticLockException`? Service nên xử lý như thế nào?

### Bài tập 8 — Soft delete

Thiết kế entity `Document` với `deletedAt` và method `markDeleted()`. Viết service xóa mềm và truy vấn chỉ trả các Document có `deletedAt IS NULL`. Giải thích vì sao gọi `em.remove(document)` không tương đương với `markDeleted()` trong JPA chuẩn.

## 21. Ghi nhớ

- **`EntityManager.remove(entity)` đánh dấu một managed entity cho thao tác xóa.**
- **Removed là trạng thái vòng đời**, không phải lệnh làm biến Java thành null hay luôn xóa DB ngay lập tức.
- **Flush thực thi đồng bộ SQL; commit mới xác nhận transaction.** Lỗi có thể xuất hiện ở flush hoặc commit.
- **Chỉ truyền entity managed**. Với detached entity, thường `find()` lại theo ID trong context hiện tại rồi mới `remove()`.
- Không gọi `persist()` hay `merge()` theo thói quen để “lưu” thao tác `remove()`; chỉ dùng khi semantics thật sự cần.
- **CascadeType.REMOVE** có thể xóa các entity liên quan; tránh dùng với đối tượng dùng chung hoặc có vòng đời độc lập.
- **Orphan removal** và **xóa liên kết nhiều-nhiều** là các hành vi khác với xóa endpoint entity.
- FK, UNIQUE, NOT NULL và ON DELETE của database vẫn quyết định DELETE có hợp lệ hay không.
- `@PreRemove/@PostRemove` là callbacks của JPA nhưng không đồng nghĩa giao dịch đã commit; bulk DML và DB cascade có thể không chạy các callback tương ứng.
- **JPQL bulk DELETE** có thể nhanh hơn cho xóa hàng loạt nhưng bỏ qua entity lifecycle/cascade và có thể làm persistence context stale.
- Với dữ liệu cần audit hoặc lưu lịch sử, cân nhắc **soft delete/archive/void** thay vì hard delete.
- Dùng `@Version`, transaction và locking phù hợp khi xóa entity có thể bị người khác cập nhật đồng thời.
- Trong Spring, đặt ranh giới `@Transactional` ở service và không xóa trực tiếp object nhận qua request như một entity managed.

**Nguyên tắc cốt lõi:** `remove()` là hành động trong **đơn vị công việc JPA**, không chỉ là bản viết tắt của SQL DELETE. Một thao tác xóa đúng phải chọn đúng đối tượng và trạng thái, giữ ranh giới transaction, xử lý quan hệ phụ thuộc và chỉ xác nhận thành công sau khi database đã commit.
