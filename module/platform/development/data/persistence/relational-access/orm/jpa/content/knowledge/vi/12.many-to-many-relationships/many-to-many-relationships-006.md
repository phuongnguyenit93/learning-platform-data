# Khi nào cần chuyển bảng liên kết thành entity riêng

> **Chủ đề:** Data Persistence – Relational Access, ORM, JPA  
> **Nhóm kiến thức:** Quan hệ nhiều-nhiều

Quan hệ **nhiều–nhiều (many-to-many)** xuất hiện rất thường xuyên trong ứng dụng: một sinh viên đăng ký nhiều khóa học và một khóa học có nhiều sinh viên; một sản phẩm gắn nhiều nhãn và một nhãn được gắn vào nhiều sản phẩm; một người dùng có nhiều vai trò và một vai trò được cấp cho nhiều người dùng.

Trong cơ sở dữ liệu quan hệ, quan hệ này thường được biểu diễn bằng **bảng liên kết (join table)** chứa ít nhất hai khóa ngoại. JPA hỗ trợ ánh xạ trực tiếp qua **@ManyToMany**. Cách ấy gọn nếu mỗi cặp chỉ diễn đạt một sự thật đơn giản: “có liên kết hay không”.

Nhưng khi liên kết bắt đầu có **thời điểm hình thành, trạng thái, vai trò, người phê duyệt, thứ tự, số lượng, thời gian hiệu lực, quy tắc nghiệp vụ hay vòng đời riêng**, bảng nối không còn là chi tiết kỹ thuật thuần túy. Nó đang biểu diễn **một sự kiện/đối tượng nghiệp vụ có dữ liệu**, và nhiều trường hợp nên được nâng thành **entity riêng**, thường gọi là **association entity**, **link entity**, **join entity** hoặc **entity đại diện quan hệ**.

Ví dụ thay vì:

~~~text
Student  * ─── @ManyToMany ─── *  Course
~~~

ta thiết kế:

~~~text
Student  1 ─── * Enrollment * ─── 1  Course
                 ├── status
                 ├── registeredAt
                 ├── withdrawnAt
                 └── version
~~~

Bài học này giúp xác định **thời điểm chuyển đổi**, thiết kế ánh xạ với **hai @ManyToOne**, lựa chọn khóa chính, xử lý ràng buộc và concurrency, thiết kế API domain, truy vấn, migration và kiểm thử. Trọng tâm không phải cứ thấy bảng nối là lập thêm class, mà là chọn mô hình phản ánh đúng **ý nghĩa nghiệp vụ và vòng đời dữ liệu**.

## 1. Bảng liên kết cơ bản và ánh xạ @ManyToMany

Giả sử có hai bảng:

~~~sql
CREATE TABLE students (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL
);

CREATE TABLE courses (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL
);

CREATE TABLE student_courses (
    student_id BIGINT NOT NULL REFERENCES students(id),
    course_id BIGINT NOT NULL REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)
);
~~~

Đây là minh họa cú pháp PostgreSQL. Hai cột **student_id** và **course_id** vừa là khóa ngoại vừa tạo **khóa chính tổng hợp** trên bảng nối, nhờ đó một cặp sinh viên–khóa học không được ghi trùng.

Dữ liệu có thể như sau:

| student_id | course_id | Ý nghĩa |
|---:|---:|---|
| 1 | 100 | Sinh viên 1 tham gia khóa 100 |
| 1 | 101 | Sinh viên 1 tham gia khóa 101 |
| 2 | 100 | Sinh viên 2 tham gia khóa 100 |

Bảng nối này không có cột mô tả bản thân việc đăng ký. Ứng dụng chỉ cần thêm hoặc bỏ liên kết.

### 1.1. Mapping trực tiếp

Phía sở hữu bảng nối:

~~~java
@Entity
@Table(name = "students")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false)
    private String fullName;

    @ManyToMany
    @JoinTable(
        name = "student_courses",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private Set<Course> courses = new HashSet<>();

    protected Student() {}

    public Set<Course> getCourses() {
        return Collections.unmodifiableSet(courses);
    }

    public void addCourse(Course course) {
        if (courses.add(Objects.requireNonNull(course))) {
            course.addStudentInternal(this);
        }
    }

    public void removeCourse(Course course) {
        if (courses.remove(course)) {
            course.removeStudentInternal(this);
        }
    }
}
~~~

Phía đối ứng:

~~~java
@Entity
@Table(name = "courses")
public class Course {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToMany(mappedBy = "courses")
    private Set<Student> students = new HashSet<>();

    protected Course() {}

    public Set<Student> getStudents() {
        return Collections.unmodifiableSet(students);
    }

    void addStudentInternal(Student student) {
        students.add(student);
    }

    void removeStudentInternal(Student student) {
        students.remove(student);
    }
}
~~~

Các ví dụ dạng rút gọn giả định các import **jakarta.persistence.\***, **java.util.\*** và **java.util.Objects** phù hợp. Với Set chứa entity, cần thiết kế **equals/hashCode** nhất quán theo vòng đời và ID; dùng khóa sinh sau khi đưa entity vào HashSet mà hashCode thay đổi có thể gây lỗi **contains/remove**. Ví dụ chỉ minh họa cấu trúc many-to-many và helper, không phải lựa chọn equality áp dụng máy móc cho mọi domain.

**@JoinTable** xác định bảng nối; **joinColumns** mô tả cột FK phía Student đang khai báo; **inverseJoinColumns** mô tả cột FK phía Course. **Course.students** có **mappedBy = "courses"** nên không tạo bảng nối thứ hai.

Khi có quan hệ mới, provider có thể ghi:

~~~sql
INSERT INTO student_courses (student_id, course_id)
VALUES (1, 100);
~~~

Khi hủy liên kết:

~~~sql
DELETE FROM student_courses
WHERE student_id = 1 AND course_id = 100;
~~~

Không cần tạo hoặc xóa Student và Course khi chỉ thay đổi bản ghi bảng nối.

### 1.2. Ưu điểm và giới hạn

Ưu điểm:

- Model ngắn gọn khi quan hệ chỉ cần tính **có/không**.
- Code dễ đọc với các thao tác **addCourse/removeCourse**.
- JPA tự quản lý các hàng của bảng nối.
- Không cần repository, ID hay entity lifecycle riêng cho từng liên kết.
- Phù hợp các quan hệ như **Product–Tag**, **Article–Keyword** khi không có metadata và không cần xử lý từng link như một đối tượng nghiệp vụ.

Giới hạn:

- Không có object JPA riêng để gán các field **registeredAt**, **status**, **approvalBy**, **validUntil** trên từng cặp.
- Không có nơi tự nhiên để đặt **@Version**, validation và business method **withdraw/approve/renew** cho một liên kết cụ thể.
- Khó truy vấn và phân trang **các liên kết cùng metadata** như “đăng ký còn hiệu lực, theo thời gian đăng ký mới nhất”.
- Nếu quan hệ cần lịch sử, nhiều lần đăng ký, soft delete hoặc sự kiện thay đổi, Set thuần túy thường không phản ánh được mô hình.
- Cascade của @ManyToMany dễ bị hiểu sai: **xóa link** khác hoàn toàn với **xóa Student/Course**.

Tóm lại, **@ManyToMany phù hợp nhất khi bảng nối thực sự chỉ là một liên kết đơn giản**.

## 2. Dấu hiệu bảng nối đã trở thành một khái niệm nghiệp vụ

Không có một quy tắc “thêm đúng bao nhiêu cột thì phải tạo entity”. Điều quan trọng là **ý nghĩa và hành vi của mối quan hệ**.

| Dấu hiệu | Ví dụ | Vì sao nghiêng về association entity? |
|---|---|---|
| Có thuộc tính của chính liên kết | registeredAt, quantity, grade, unitPrice | Không thể đặt những thuộc tính ấy đúng nghĩa lên Student hay Course |
| Có trạng thái và chuyển trạng thái | PENDING → APPROVED → EXPIRED | Link có lifecycle và quy tắc riêng |
| Có người tạo/phê duyệt hoặc nguồn gốc | assignedBy, approvedBy, sourceSystem | Cần truy vấn và kiểm toán từng lần liên kết |
| Có khoảng thời gian hiệu lực | validFrom, validTo | “Đã từng có” khác với “đang có hiệu lực” |
| Có soft delete hoặc lưu lịch sử | withdrawnAt, cancelledAt | Xóa link vật lý làm mất thông tin |
| Có định danh riêng | enrollmentId xuất hiện trong API | Link cần được tham chiếu, sửa và audit độc lập |
| Có optimistic locking | @Version trên Enrollment | Hai giao dịch có thể tranh chấp cập nhật cùng liên kết |
| Có validation/constraint riêng | amount > 0, thời gian hợp lệ | Quy tắc thuộc về relationship |
| Có tần suất query/filter trực tiếp | Đăng ký trong tháng, theo status | Repository của link rõ ràng hơn duyệt collection |
| Có quan hệ tiếp tới entity khác | Enrollment → Payment | Link là điểm trung tâm của các association khác |
| Phải có nhiều bản ghi cho cùng cặp | Nhiều lần học lại, phiên bản phân quyền | Một cặp ID duy nhất không còn biểu diễn hết lịch sử |

**Câu hỏi cốt lõi:** nếu bỏ Student và Course ra khỏi câu chuyện, liệu có thể nói một câu có ý nghĩa nghiệp vụ về **Enrollment** không? Ví dụ “đăng ký số 456 được phê duyệt lúc 09:00, sau đó rút vào ngày 10” cho thấy Enrollment là một đối tượng cần quản lý, không chỉ một dấu tick giữa hai collection.

### 2.1. Thuộc tính thuộc về mối quan hệ, không thuộc hai đầu

Giả sử Course có thuộc tính **title**, Student có **fullName**. Nhưng **grade** là điểm của **Student A trong Course X**:

~~~text
Student A ── Course X: grade = 8.5
Student A ── Course Y: grade = 9.0
Student B ── Course X: grade = 7.0
~~~

Đặt **grade** lên Student là sai vì một sinh viên có nhiều điểm; đặt lên Course cũng sai vì một khóa có nhiều sinh viên. Thuộc tính phải nằm ở **Enrollment**, tức bản ghi cho từng cặp.

Tương tự:

- **OrderItem.quantity** mô tả số lượng của một sản phẩm trong một đơn hàng.
- **ProjectMembership.role** mô tả vai trò của người dùng trong một dự án.
- **UserRoleAssignment.grantedBy** mô tả ai cấp vai trò cho một người dùng.
- **SubscriptionPlanChange.effectiveAt** mô tả thời điểm một quan hệ đăng ký gói có hiệu lực.

### 2.2. Không nhất thiết phải có cột phụ mới nên tạo entity

Đôi khi bảng nối chỉ chứa hai FK, nhưng domain đã đối xử với liên kết như một resource có lifecycle, event, approval hoặc quyền truy cập riêng. Ví dụ API trả **membershipId** để người quản lý duyệt một yêu cầu tham gia. Trong trường hợp đó, dùng entity riêng từ sớm có thể hợp lý dù hiện tại chưa có nhiều cột nghiệp vụ.

Ngược lại, chỉ có cột **created_at** để phục vụ một công việc thống kê đơn giản chưa đủ kết luận bắt buộc đổi mọi @ManyToMany. Hãy cân nhắc nhu cầu thao tác, kiểm thử, query, transaction và độ phức tạp tổng thể. Tuy nhiên khi metadata phải **được JPA đọc/ghi như một phần nghiệp vụ**, association entity thường là cách rõ ràng và bền vững nhất.

### 2.3. Khi không nên chuyển

Giữ **@ManyToMany** nếu các điều kiện sau đều đúng:

1. Liên kết chỉ có nghĩa **A gắn với B hay không**.
2. Không cần lưu thời điểm, trạng thái, người tạo, metadata theo từng link.
3. Không có lifecycle, domain event hay ID riêng cho từng liên kết.
4. Không cần query/link repository phức tạp.
5. Xóa link thực sự có nghĩa là bỏ liên kết, không có yêu cầu lịch sử.
6. Kích thước collection và fetch plan vẫn được kiểm soát.

Ví dụ đơn giản: một bài viết được gắn các nhãn; người dùng chỉ thêm/bỏ nhãn và không cần thông tin ai gắn nhãn lúc nào. Entity liên kết riêng ở đây có thể chỉ làm tăng số class và logic không cần thiết.

## 3. Sự thay đổi quan trọng: @ManyToMany thành hai @ManyToOne

Mô hình mới:

~~~mermaid
erDiagram
    STUDENT ||--o{ ENROLLMENT : has
    COURSE ||--o{ ENROLLMENT : has
    STUDENT {
        bigint id PK
        string full_name
    }
    COURSE {
        bigint id PK
        string title
    }
    ENROLLMENT {
        bigint id PK
        bigint student_id FK
        bigint course_id FK
        string status
        timestamp registered_at
        timestamp withdrawn_at
        bigint version
    }
~~~

Ở JPA:

~~~text
Student                 Enrollment                      Course
-------                 ----------                      ------
id                  *   id                              id
enrollments --------->  student: @ManyToOne             enrollments
                        course:  @ManyToOne  <---------- 
                        status, registeredAt, ...
~~~

Thay vì một association **@ManyToMany**, giờ ta có:

- **Enrollment.student**: **@ManyToOne**, sở hữu khóa ngoại **student_id**.
- **Enrollment.course**: **@ManyToOne**, sở hữu khóa ngoại **course_id**.
- **Student.enrollments**: **@OneToMany(mappedBy = "student")**, nếu cần duyệt ngược.
- **Course.enrollments**: **@OneToMany(mappedBy = "course")**, nếu cần duyệt ngược.

**Enrollment là entity**, có ID, trạng thái managed/detached, có thể được persist, query, update, remove và version theo các quy tắc JPA. Hai collection ngược là **tùy chọn**, không phải điều kiện bắt buộc để lưu Enrollment.

Một điểm đáng chú ý: bảng vật lý vẫn có thể là bảng **student_courses** hiện có. Việc chuyển mô hình object không bắt buộc đổi tên bảng; điều thay đổi là **bảng nối được ánh xạ như entity**, có metadata riêng và các quan hệ nhiều–một rõ ràng.

## 4. Thiết kế schema cho Enrollment

Giả sử nghiệp vụ quy định:

- Một sinh viên có tối đa **một bản ghi Enrollment cho một Course**.
- Đăng ký có trạng thái **ACTIVE** hoặc **WITHDRAWN**.
- Khi rút, hệ thống **giữ bản ghi** để tra cứu lịch sử; không xóa vật lý.
- Mỗi Enrollment lưu ngày đăng ký, ngày rút và version để phát hiện cập nhật cạnh tranh.
- Một sinh viên đã rút có thể được kích hoạt lại theo quy trình riêng; không tạo hàng thứ hai cho cùng cặp.

Schema PostgreSQL minh họa:

~~~sql
CREATE TABLE enrollments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,

    status VARCHAR(20) NOT NULL,
    registered_at TIMESTAMP WITH TIME ZONE NOT NULL,
    withdrawn_at TIMESTAMP WITH TIME ZONE,
    version BIGINT NOT NULL DEFAULT 0,

    CONSTRAINT fk_enrollment_student
        FOREIGN KEY (student_id) REFERENCES students(id),

    CONSTRAINT fk_enrollment_course
        FOREIGN KEY (course_id) REFERENCES courses(id),

    CONSTRAINT uk_enrollment_student_course
        UNIQUE (student_id, course_id),

    CONSTRAINT chk_enrollment_status
        CHECK (status IN ('ACTIVE', 'WITHDRAWN')),

    CONSTRAINT chk_enrollment_withdrawn_at
        CHECK (
            (status = 'ACTIVE' AND withdrawn_at IS NULL)
            OR
            (status = 'WITHDRAWN' AND withdrawn_at IS NOT NULL)
        )
);

CREATE INDEX idx_enrollments_course_status
    ON enrollments(course_id, status);

CREATE INDEX idx_enrollments_student_registered
    ON enrollments(student_id, registered_at);
~~~

**PRIMARY KEY(id)** định danh mỗi bản ghi link. **UNIQUE(student_id, course_id)** bảo vệ bất biến “một cặp chỉ có một Enrollment”. Chúng là **hai ràng buộc khác nhau**:

- ID thuận tiện cho URL, API, audit và các bảng tham chiếu Enrollment.
- Unique pair ngăn hai request đồng thời tạo hai Enrollment cho cùng Student và Course.

**Foreign key** bảo vệ tham chiếu; **CHECK** bảo vệ trạng thái và sự phù hợp của withdrawnAt. Nếu hệ thống hiện đã có bảng **student_courses** với PK tổng hợp, có thể dùng composite ID thay vì thêm id; phần khóa chính sẽ so sánh hai lựa chọn.

### 4.1. Lưu ý khi chọn trạng thái và thời gian

Ví dụ sử dụng ứng dụng làm nguồn đặt **registeredAt** và **withdrawnAt**. Vì vậy JPA cho phép INSERT các cột đó; thời gian được tạo trong service từ một **Clock** hoặc nguồn đồng hồ rõ ràng.

Nếu muốn database tự đặt timestamp bằng DEFAULT hoặc trigger, mapping JPA và cách lấy lại DB-generated value cần được thiết kế khác. Không chỉ đặt **insertable=false** khi DB chưa có DEFAULT, vì INSERT có thể vi phạm NOT NULL.

Không cần mọi quan hệ đều có **withdrawn_at**. Nếu nghiệp vụ xóa liên kết vật lý, có thể bỏ status và timestamp; tuy nhiên khi đã quyết định lưu lịch sử, thao tác **withdraw** nên đổi trạng thái, không xóa row.

## 5. Ví dụ JPA hoàn chỉnh với khóa chính surrogate

Trong ví dụ này dùng **Jakarta Persistence**, package **jakarta.persistence** và Java hỗ trợ **Instant**. Một Enrollment gồm hai @ManyToOne và dữ liệu riêng; mã dưới đây sử dụng quan hệ hai chiều để minh họa cách quản lý collections nhất quán.

### 5.1. Entity Student

~~~java
package com.example.school;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

@Entity
@Table(name = "students")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 120)
    private String fullName;

    @OneToMany(mappedBy = "student", fetch = FetchType.LAZY)
    private List<Enrollment> enrollments = new ArrayList<>();

    protected Student() { }

    public Student(String fullName) {
        if (fullName == null || fullName.isBlank()) {
            throw new IllegalArgumentException("Tên sinh viên không được trống");
        }
        this.fullName = fullName;
    }

    public Long getId() { return id; }
    public String getFullName() { return fullName; }

    public List<Enrollment> getEnrollments() {
        return Collections.unmodifiableList(enrollments);
    }

    // Phương thức package-private, chỉ dùng để đồng bộ graph.
    void attachEnrollment(Enrollment enrollment) {
        for (Enrollment current : enrollments) {
            if (current == enrollment) {
                return;
            }
        }
        enrollments.add(enrollment);
    }
}
~~~

**Student.enrollments** là inverse side, nên không tự quyết định cột **student_id**. Ví dụ không bật cascade remove hoặc orphanRemoval ở đây vì Enrollment có trạng thái lịch sử riêng; xóa Student hoặc xóa một phần tử khỏi List không được mặc nhiên xóa lịch sử đăng ký.

### 5.2. Entity Course

~~~java
package com.example.school;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

@Entity
@Table(name = "courses")
public class Course {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "title", nullable = false, length = 200)
    private String title;

    @OneToMany(mappedBy = "course", fetch = FetchType.LAZY)
    private List<Enrollment> enrollments = new ArrayList<>();

    protected Course() { }

    public Course(String title) {
        if (title == null || title.isBlank()) {
            throw new IllegalArgumentException("Tên khóa học không được trống");
        }
        this.title = title;
    }

    public Long getId() { return id; }
    public String getTitle() { return title; }

    public List<Enrollment> getEnrollments() {
        return Collections.unmodifiableList(enrollments);
    }

    void attachEnrollment(Enrollment enrollment) {
        for (Enrollment current : enrollments) {
            if (current == enrollment) {
                return;
            }
        }
        enrollments.add(enrollment);
    }
}
~~~

Nếu số Enrollment cho một Course có thể rất lớn, có thể **không khai báo Course.enrollments** và thay bằng repository query theo courseId. Quan hệ hai chiều là lựa chọn thiết kế truy cập object graph, không bắt buộc khi dùng association entity.

### 5.3. Enum trạng thái

~~~java
package com.example.school;

public enum EnrollmentStatus {
    ACTIVE,
    WITHDRAWN
}
~~~

Cần quy định trạng thái mới và migration CHECK tương ứng khi mở rộng sang **PENDING**, **APPROVED**, **COMPLETED** hoặc các trạng thái khác. Không thêm trạng thái ở Java mà quên cập nhật constraint DB và logic chuyển trạng thái.

### 5.4. Enrollment là entity thực thụ

~~~java
package com.example.school;

import jakarta.persistence.*;
import java.time.Instant;
import java.util.Objects;

@Entity
@Table(
    name = "enrollments",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_enrollment_student_course",
        columnNames = {"student_id", "course_id"}
    )
)
public class Enrollment {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "student_id", nullable = false, updatable = false)
    private Student student;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "course_id", nullable = false, updatable = false)
    private Course course;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 20)
    private EnrollmentStatus status;

    @Column(name = "registered_at", nullable = false, updatable = false)
    private Instant registeredAt;

    @Column(name = "withdrawn_at")
    private Instant withdrawnAt;

    @Version
    @Column(name = "version", nullable = false)
    private Long version;

    protected Enrollment() { }

    private Enrollment(Student student, Course course, Instant now) {
        this.student = Objects.requireNonNull(student, "student");
        this.course = Objects.requireNonNull(course, "course");
        this.registeredAt = Objects.requireNonNull(now, "now");
        this.status = EnrollmentStatus.ACTIVE;
    }

    public static Enrollment register(
            Student student, Course course, Instant now) {
        Enrollment enrollment = new Enrollment(student, course, now);

        // Giữ hai collection đối ứng nhất quán trong cùng object graph.
        student.attachEnrollment(enrollment);
        course.attachEnrollment(enrollment);

        return enrollment;
    }

    public void withdraw(Instant now) {
        Objects.requireNonNull(now, "now");
        if (status != EnrollmentStatus.ACTIVE) {
            throw new IllegalStateException("Chỉ đăng ký ACTIVE mới được rút");
        }
        if (now.isBefore(registeredAt)) {
            throw new IllegalArgumentException(
                "Thời điểm rút không thể trước thời điểm đăng ký");
        }
        this.status = EnrollmentStatus.WITHDRAWN;
        this.withdrawnAt = now;
    }

    public Long getId() { return id; }
    public Student getStudent() { return student; }
    public Course getCourse() { return course; }
    public EnrollmentStatus getStatus() { return status; }
    public Instant getRegisteredAt() { return registeredAt; }
    public Instant getWithdrawnAt() { return withdrawnAt; }
    public Long getVersion() { return version; }
}
~~~

Các điểm quan trọng:

- **Enrollment** có **@Id**, nên có thể gọi **em.find(Enrollment.class, enrollmentId)** hoặc tạo repository riêng.
- **Enrollment.student** và **Enrollment.course** đều là **owning sides** của hai FK; hai collection phía Student/Course chỉ là inverse sides.
- **updatable=false** trên join columns biểu diễn rằng **không chuyển Enrollment hiện có sang Student/Course khác bằng mapping này**. Nó không thay thế policy hoặc trigger ở DB, cũng không ngăn mọi native SQL.
- **status, registeredAt, withdrawnAt** là thông tin thuộc đúng **bản ghi Enrollment**, không phải hai entity đầu mút.
- **@Version** giúp phát hiện hai transaction tranh chấp cập nhật trạng thái cùng một Enrollment.
- **UniqueConstraint** trong @Table là mapping metadata có thể hỗ trợ schema generation; migration phải bảo đảm **UNIQUE thật** tồn tại trong DB sản xuất.
- Static factory **register** điều phối object graph, nhưng **không persist**, **không commit**, và **không tự kiểm tra duplicate trong database**.
- Không expose setter công khai cho Student/Course từ Enrollment; nếu muốn “chuyển khóa”, nghiệp vụ thường nên hủy đăng ký cũ và đăng ký khóa mới thay vì sửa liên kết đã có lịch sử.
- Nếu sau này cần **đăng ký lại** cùng một cặp, phải định nghĩa rõ chuyện **reactivate** bản ghi cũ hay tạo **attempt/version** mới; đây là thay đổi nghiệp vụ đi kèm thay đổi unique constraint, không chỉ sửa method.

### 5.5. Sử dụng EntityManager trong một transaction

~~~java
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Student student = em.find(Student.class, studentId);
    Course course = em.find(Course.class, courseId);

    if (student == null || course == null) {
        throw new IllegalArgumentException(
            "Sinh viên hoặc khóa học không tồn tại");
    }

    Enrollment enrollment = Enrollment.register(
        student, course, Instant.now());

    em.persist(enrollment);
    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
}
~~~

Đây là ví dụ cho **EntityManager resource-local**. Với Spring hoặc JTA, transaction được điều phối bằng transaction manager; không gọi **getTransaction()** trên EntityManager được container quản lý theo JTA.

**Không cần cascade từ Enrollment sang Student/Course**: cả hai entity đầu mút đã tồn tại, được load vào cùng persistence context. Việc persist Enrollment tạo hàng ở bảng **enrollments**, còn Student và Course không bị INSERT lại.

SQL có thể có dạng:

~~~sql
INSERT INTO enrollments (
    student_id, course_id, status, registered_at, withdrawn_at, version
) VALUES (
    1, 100, 'ACTIVE', ?, NULL, 0
);
~~~

Câu SQL chỉ minh họa: chi tiết version, cột và thời điểm INSERT tùy provider/chiến lược ID. Khi đổi trạng thái trên Enrollment managed rồi flush, có thể có:

~~~sql
UPDATE enrollments
SET status = 'WITHDRAWN',
    withdrawn_at = ?,
    version = ?
WHERE id = ?
  AND version = ?;
~~~

Đây là ví dụ của dirty checking và optimistic locking trên **entity liên kết**, thay vì thao tác add/remove trên Set<Course>.

## 6. Vòng đời: tạo, thay đổi trạng thái, xóa và tái đăng ký

Khi một join table trở thành entity, câu hỏi không còn đơn giản là “có link hay không?” mà là “**link đang ở trạng thái nào?**”.

Một luồng đăng ký:

~~~mermaid
stateDiagram-v2
    [*] --> ACTIVE: register
    ACTIVE --> WITHDRAWN: withdraw
    WITHDRAWN --> [*]: lưu lịch sử
~~~

Trong ví dụ, **WITHDRAWN không có nghĩa DELETE**. Hàng Enrollment vẫn tồn tại, nên có thể tra cứu đăng ký đã rút. Điều này đặc biệt hữu ích cho các miền liên quan đến học phí, quyền truy cập, báo cáo hoặc tuân thủ.

### 6.1. Tại sao không xóa liên kết khi cần lịch sử?

Với @ManyToMany thuần:

~~~java
student.getCourses().remove(course);
~~~

thường diễn đạt **DELETE hàng join table**. Nếu bảng nối không có thông tin phụ, điều này phù hợp.

Nhưng khi Enrollment lưu **registeredAt**, **withdrawnAt** và **status**, xóa row có thể làm mất bằng chứng đăng ký từng tồn tại. Vì thế thay bằng:

~~~java
Enrollment enrollment = em.find(Enrollment.class, enrollmentId);
enrollment.withdraw(Instant.now());
~~~

Có thể xuất hiện nhiều trạng thái hơn tùy nghiệp vụ:

~~~text
REQUESTED → APPROVED → ACTIVE → COMPLETED
    │           │         │
    └→ REJECTED └→ CANCELLED └→ WITHDRAWN
~~~

Mỗi bước nên có **method nghiệp vụ**, quyền thực hiện và quy tắc chuyển trạng thái rõ ràng, thay vì setter status tự do.

### 6.2. Có nên dùng orphanRemoval?

Với **Student.enrollments**:

~~~java
@OneToMany(mappedBy = "student", orphanRemoval = true)
private List<Enrollment> enrollments;
~~~

Nếu xóa một Enrollment khỏi collection, provider có thể xóa entity con theo semantics orphanRemoval. Điều này **không phù hợp** với thiết kế phải giữ lịch sử rút đăng ký.

Nếu Enrollment thật sự là thành phần chỉ tồn tại khi liên kết còn hiệu lực, không có lịch sử và phải xóa vật lý khi bỏ link, **orphanRemoval=true** có thể hợp lý. Cần chọn dựa vào **vòng đời nghiệp vụ**, không chọn chỉ vì muốn đỡ gọi repository.delete.

### 6.3. Cascade REMOVE nguy hiểm ở quan hệ đầu mút độc lập

Không đặt một cách máy móc:

~~~java
@ManyToOne(cascade = CascadeType.REMOVE)
private Course course;
~~~

trên Enrollment. Nếu xóa Enrollment, việc cascade REMOVE sang Course có thể xóa một khóa học mà nhiều Enrollment khác cũng tham chiếu.

Ngược lại, cũng cần thận trọng với:

~~~java
@OneToMany(mappedBy = "student", cascade = CascadeType.ALL)
private List<Enrollment> enrollments;
~~~

**CascadeType.ALL bao gồm REMOVE**: xóa Student có thể lan xóa tất cả Enrollment. Nếu Enrollment phải được giữ vì lịch sử, luật hoặc audit, không thể sử dụng cấu hình này một cách vô điều kiện; cần chiến lược đóng tài khoản, ẩn dữ liệu, lưu lịch sử hoặc retention policy riêng.

### 6.4. Tham chiếu entity cũ sau khi xóa

Entity liên kết đã **removed** không nên được giữ trong collection và tiếp tục dùng như thể managed bình thường. Nếu thật sự DELETE một Enrollment, code cần chủ động đồng bộ hai collection ngược trong bộ nhớ hoặc reload/clear context theo thiết kế. Với ví dụ **withdraw** chỉ đổi trạng thái, Enrollment vẫn tồn tại trong các collection, nên không có lý do tự động xóa khỏi Student.enrollments hay Course.enrollments.

## 7. Khóa chính nào cho entity liên kết?

Hai lựa chọn thông dụng:

1. **Surrogate key**: một cột **id** riêng của Enrollment, cùng **UNIQUE(student_id, course_id)** khi nghiệp vụ yêu cầu.
2. **Composite key**: **(student_id, course_id)** là khóa chính, ánh xạ bằng **@EmbeddedId + @MapsId**.

Không có lựa chọn luôn tốt nhất; chúng phù hợp các ngữ cảnh khác nhau.

### 7.1. Surrogate ID: đơn giản khi link có vòng đời và reference riêng

Ví dụ đã sử dụng:

~~~java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "student_id", nullable = false)
private Student student;

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "course_id", nullable = false)
private Course course;
~~~

Ưu điểm:

- URL và API có thể dùng **/enrollments/{id}**.
- Dễ tham chiếu một enrollment từ **Payment**, **Certificate**, **AuditEvent** hoặc bảng khác.
- Có thể thêm version, status, lịch sử và các thuộc tính mới mà identity không phụ thuộc trực tiếp hai FK.
- Dễ mở rộng tới nhiều lần đăng ký với cùng cặp nếu domain bổ sung **attemptNo** hoặc thay đổi unique constraint.

Tuy nhiên **có id riêng không làm cặp FK tự duy nhất**. Cần UNIQUE thật trong DB nếu một Student chỉ được có một Enrollment với cùng Course.

### 7.2. Composite ID: cặp FK chính là định danh

Nếu mỗi cặp Student–Course chỉ được xuất hiện một lần và không cần enrollment ID riêng, có thể dùng **EnrollmentId**:

~~~java
package com.example.school;

import jakarta.persistence.Column;
import jakarta.persistence.Embeddable;
import java.io.Serializable;
import java.util.Objects;

@Embeddable
public class EnrollmentId implements Serializable {
    @Column(name = "student_id", nullable = false)
    private Long studentId;

    @Column(name = "course_id", nullable = false)
    private Long courseId;

    protected EnrollmentId() { }

    public EnrollmentId(Long studentId, Long courseId) {
        this.studentId = Objects.requireNonNull(studentId);
        this.courseId = Objects.requireNonNull(courseId);
    }

    public Long getStudentId() { return studentId; }
    public Long getCourseId() { return courseId; }

    @Override
    public boolean equals(Object other) {
        if (this == other) return true;
        if (!(other instanceof EnrollmentId that)) return false;
        return Objects.equals(studentId, that.studentId)
                && Objects.equals(courseId, that.courseId);
    }

    @Override
    public int hashCode() {
        return Objects.hash(studentId, courseId);
    }
}
~~~

Một **entity thay thế** dùng composite ID:

~~~java
@Entity
@Table(name = "enrollments")
public class EnrollmentWithCompositeKey {
    @EmbeddedId
    private EnrollmentId id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @MapsId("studentId")
    @JoinColumn(name = "student_id", nullable = false)
    private Student student;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @MapsId("courseId")
    @JoinColumn(name = "course_id", nullable = false)
    private Course course;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private EnrollmentStatus status;

    protected EnrollmentWithCompositeKey() { }

    public EnrollmentWithCompositeKey(Student student, Course course) {
        if (student.getId() == null || course.getId() == null) {
            throw new IllegalArgumentException(
                "Các entity đầu mút phải có ID để tạo composite key");
        }
        this.student = student;
        this.course = course;
        this.id = new EnrollmentId(student.getId(), course.getId());
        this.status = EnrollmentStatus.ACTIVE;
    }

    public EnrollmentId getId() { return id; }
}
~~~

Đây là **phương án thay thế độc lập**, không phải thêm class này đồng thời vào persistence unit đang mapping cùng bảng **enrollments** bằng entity surrogate và kỳ vọng dùng lẫn hai mô hình trong một ví dụ. Nếu dùng composite schema, bảng có thể khai báo:

~~~sql
CREATE TABLE enrollments (
    student_id BIGINT NOT NULL REFERENCES students(id),
    course_id BIGINT NOT NULL REFERENCES courses(id),
    status VARCHAR(20) NOT NULL,
    PRIMARY KEY (student_id, course_id)
);
~~~

**@MapsId("studentId")** nối association Student với thành phần **studentId** của @EmbeddedId; **@MapsId("courseId")** làm điều tương tự cho Course. Đây là cách biểu diễn derived identity chuẩn JPA, không cần tạo hai mapping scalar FK cạnh tranh ghi cột và sửa lỗi bằng **insertable=false/updatable=false** tùy tiện.

Lưu ý cách tạo ID trong ví dụ yêu cầu Student và Course đã có ID, chẳng hạn đã được persisted. Trong các mô hình tạo nhiều object mới cùng lúc, thứ tự persist và chiến lược ID phải được thiết kế tương ứng.

### 7.3. So sánh thực dụng

| Tiêu chí | Surrogate ID + unique pair | Composite ID bằng hai FK |
|---|---|---|
| Identity của link | Một cột id riêng | Chính cặp student_id/course_id |
| API/repository | findById(Long) đơn giản | findById(EnrollmentId) |
| Bảo vệ trùng cặp | Cần thêm UNIQUE | PRIMARY KEY cặp đã bảo vệ |
| FK từ bảng khác trỏ đến link | Thường đơn giản bằng enrollment_id | Phải mang hai cột FK hoặc phương án riêng |
| Đổi một đầu liên kết | Nên là thao tác nghiệp vụ rõ; ID kỹ thuật vẫn giữ | Đổi FK đồng nghĩa đổi identity, không phù hợp update tại chỗ |
| Nhiều lần cho cùng cặp | Có thể mở rộng mô hình với attemptNo | Cần mở rộng composite key |
| Độ phức tạp equals/hashCode | Vẫn phải có chiến lược entity equality nếu dùng Set | Embeddable ID cần equals/hashCode theo cặp |
| Phù hợp | Link có lifecycle và identity rõ ràng | Link duy nhất theo hai FK, không cần ID riêng |

**Lựa chọn gợi ý:** nếu Enrollment là resource có lịch sử, cần tham chiếu từ nơi khác hoặc có khả năng đăng ký nhiều lần, surrogate key thường dễ tiến hóa. Nếu cặp ID là định danh ổn định, duy nhất và đủ cho mọi thao tác, composite ID có thể phản ánh model tự nhiên hơn.

## 8. Một cặp có thể xuất hiện nhiều lần: tránh unique constraint sai nghiệp vụ

Hãy phân biệt hai yêu cầu:

**Yêu cầu A: Một Student–Course chỉ có một Enrollment từng tồn tại.**

~~~text
student_id = 1
course_id  = 100
status     = WITHDRAWN
~~~

Đăng ký lại sẽ **reactivate** cùng record hoặc bị từ chối. **UNIQUE(student_id, course_id)** phù hợp.

**Yêu cầu B: Một sinh viên được học lại cùng khóa nhiều đợt.**

~~~text
student_id course_id attempt_no status
1          100       1          COMPLETED
1          100       2          WITHDRAWN
1          100       3          ACTIVE
~~~

Khi ấy **UNIQUE(student_id, course_id)** là **quá chặt**. Một thiết kế khác:

~~~sql
CREATE TABLE enrollment_attempts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id BIGINT NOT NULL REFERENCES students(id),
    course_id BIGINT NOT NULL REFERENCES courses(id),
    attempt_no INTEGER NOT NULL CHECK (attempt_no > 0),
    status VARCHAR(20) NOT NULL,
    registered_at TIMESTAMP WITH TIME ZONE NOT NULL,

    CONSTRAINT uk_enrollment_attempt
        UNIQUE (student_id, course_id, attempt_no)
);
~~~

Nếu nghiệp vụ còn quy định **tối đa một attempt ACTIVE tại một thời điểm**, có thể dùng một **partial unique index** đặc thù PostgreSQL:

~~~sql
CREATE UNIQUE INDEX uk_one_active_enrollment_per_pair
ON enrollment_attempts(student_id, course_id)
WHERE status = 'ACTIVE';
~~~

DBMS khác có cơ chế index/constraint khác; không coi partial unique index là cú pháp SQL/JPA portable. Với ứng dụng dùng nhiều loại database, cần thiết kế phương án tương ứng và test concurrency.

Điểm cần học: **identity và uniqueness là hai quyết định nghiệp vụ**, không phải chỉ chọn annotation cho đẹp. Trước khi viết entity, hãy trả lời “được phép tồn tại bao nhiêu bản ghi link cho cùng cặp, trong những điều kiện nào?”.

## 9. Service/repository khi association entity là nguồn sự thật

Đây là một lý do quan trọng để tạo entity: liên kết có thể được tìm, validate và thay đổi bằng repository chuyên biệt.

### 9.1. Spring Data JPA repository

~~~java
package com.example.school;

import java.util.Optional;
import org.springframework.data.jpa.repository.JpaRepository;

public interface StudentRepository
        extends JpaRepository<Student, Long> {
}

public interface CourseRepository
        extends JpaRepository<Course, Long> {
}

public interface EnrollmentRepository
        extends JpaRepository<Enrollment, Long> {

    boolean existsByStudent_IdAndCourse_Id(
            Long studentId, Long courseId);

    Optional<Enrollment> findByStudent_IdAndCourse_Id(
            Long studentId, Long courseId);
}
~~~

Spring Data diễn giải đường dẫn **Student.id** và **Course.id** từ tên method. Repository chỉ là phần API truy cập dữ liệu; ràng buộc duy nhất ở database vẫn cần thiết để giải quyết request đồng thời.

### 9.2. Service tạo Enrollment

~~~java
package com.example.school;

import java.time.Clock;
import java.time.Instant;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class EnrollmentService {
    private final StudentRepository students;
    private final CourseRepository courses;
    private final EnrollmentRepository enrollments;
    private final Clock clock;

    public EnrollmentService(
            StudentRepository students,
            CourseRepository courses,
            EnrollmentRepository enrollments,
            Clock clock) {
        this.students = students;
        this.courses = courses;
        this.enrollments = enrollments;
        this.clock = clock;
    }

    @Transactional
    public Long register(long studentId, long courseId) {
        Student student = students.findById(studentId)
            .orElseThrow(() ->
                new IllegalArgumentException("Sinh viên không tồn tại"));

        Course course = courses.findById(courseId)
            .orElseThrow(() ->
                new IllegalArgumentException("Khóa học không tồn tại"));

        // Thông báo lỗi sớm, KHÔNG phải biện pháp chống race condition.
        if (enrollments.existsByStudent_IdAndCourse_Id(
                studentId, courseId)) {
            throw new IllegalStateException("Đã có đăng ký cho cặp này");
        }

        Enrollment enrollment = Enrollment.register(
            student, course, Instant.now(clock));

        Enrollment saved = enrollments.saveAndFlush(enrollment);
        return saved.getId();
    }

    @Transactional
    public void withdraw(long enrollmentId) {
        Enrollment enrollment = enrollments.findById(enrollmentId)
            .orElseThrow(() ->
                new IllegalArgumentException("Đăng ký không tồn tại"));

        enrollment.withdraw(Instant.now(clock));
        // Managed entity: dirty checking sẽ cập nhật ở flush/commit.
    }
}
~~~

Ví dụ yêu cầu ứng dụng định nghĩa bean **Clock**:

~~~java
@Bean
public Clock applicationClock() {
    return Clock.systemUTC();
}
~~~

Trong môi trường thực, có thể dùng **Clock.fixed(...)** khi test để dữ liệu thời gian xác định. Class dịch vụ trên là mẫu minh họa, chưa bao gồm xác thực quyền, capacity Course, policy đóng đăng ký, idempotency key của request hoặc cách dịch lỗi DB thành HTTP response.

**saveAndFlush()** gửi SQL trước khi thoát method, hữu ích khi cần quan sát một số lỗi sớm. Nó **không đồng nghĩa transaction đã commit** và không bảo đảm tất cả constraint đều được kiểm tra trước commit (DB có thể có deferred constraints). Exception phải được xử lý ở ranh giới transaction/service thích hợp.

### 9.3. Hai request đăng ký cùng lúc

Một cách kiểm tra không đủ:

~~~java
if (!enrollments.existsByStudent_IdAndCourse_Id(studentId, courseId)) {
    enrollments.save(newEnrollment);
}
~~~

Race condition:

~~~text
T1: EXISTS(1, 100) -> false
T2: EXISTS(1, 100) -> false
T1: INSERT enrollment(1, 100) -> thành công
T2: INSERT enrollment(1, 100) -> UNIQUE violation
~~~

**UNIQUE constraint** trên cặp là lớp bảo vệ cuối cùng. Ứng dụng cần dịch lỗi trùng cặp (nếu đã rõ nguyên nhân) thành phản hồi phù hợp, ví dụ “đăng ký này đã tồn tại”, hoặc biến thao tác thành idempotent theo contract API. Đừng dựa vào một tên exception duy nhất: JPA provider và Spring có thể bọc exception theo nhiều lớp, như **PersistenceException**, **DataIntegrityViolationException**, và chi tiết constraint cần được xác định.

### 9.4. Quyền nghiệp vụ không nằm trong @ManyToOne

Với Enrollment, service có thể phải kiểm tra:

- Student đang hoạt động và được phép học Course đó?
- Course còn chỗ và còn thời gian nhận đăng ký?
- Student đã hoàn thành prerequisite?
- Người gọi có quyền đăng ký cho Student khác?
- Payment có phải thành công trước khi trạng thái chuyển ACTIVE?
- Có chính sách không thể rút sau thời hạn?
- Nếu Course bị đóng, Enrollment đang ACTIVE xử lý thế nào?

Những câu hỏi này thuộc domain/application service và transaction, không thể giải quyết chỉ bằng annotation quan hệ.

## 10. Quy tắc điều phối hai phía trong mô hình association entity

Sau khi chuyển sang Enrollment, ta không còn thao tác:

~~~java
student.getCourses().add(course);
~~~

thay vào đó:

~~~java
Enrollment enrollment =
    Enrollment.register(student, course, Instant.now(clock));
~~~

Vì **Enrollment.student** và **Enrollment.course** là hai owning sides, chính hai thuộc tính đó quyết định hai FK trong SQL. Collections **Student.enrollments** và **Course.enrollments** là các phía đối ứng giúp duyệt dữ liệu trong bộ nhớ.

Static factory ở phần 5 đã:

1. Kiểm tra Student và Course khác null.
2. Tạo Enrollment với hai reference và metadata.
3. Thêm Enrollment vào Student.enrollments.
4. Thêm Enrollment vào Course.enrollments.
5. Trả về Enrollment cho service persist.

Nếu không cần duyệt collection trên hai entity đầu mút, có thể lược bỏ collections và helper tương ứng để giảm coupling và tránh tải nhiều dữ liệu.

### 10.1. Không sửa association qua public setter tùy ý

Ví dụ thiếu an toàn:

~~~java
enrollment.setStudent(anotherStudent);
~~~

Một Enrollment đã có trạng thái, thời gian, payment hoặc history sẽ đổi nghĩa nếu chuyển Student. Điều đó có thể làm audit mất tính chính xác. Với model này, hai FK được xem là cố định sau khi tạo; muốn Student khác đăng ký thì tạo **Enrollment mới**.

**updatable=false** trên @JoinColumn giúp provider không đưa cột FK vào UPDATE từ mapping thông thường. Tuy nhiên nó không phải cơ chế DB bất biến: native SQL hoặc ứng dụng khác có thể sửa cột nếu có quyền. Nếu bất biến phải được giữ trước mọi nguồn ghi, cân nhắc trigger, policy, quyền truy cập hoặc quy trình quản trị tương ứng.

### 10.2. Tại sao không giữ hai mapping song song cùng ghi bảng?

Một thiết kế nguy hiểm:

~~~java
// Student:
@ManyToMany
@JoinTable(name = "enrollments", ...)
private Set<Course> courses;

// Student:
@OneToMany(mappedBy = "student")
private List<Enrollment> enrollments;
~~~

Nếu cả hai cùng được cho phép thay đổi, ORM có **hai con đường ghi cùng một bảng** nhưng semantics không giống nhau. Thao tác trên Set<Course> có thể INSERT/DELETE link mà không đặt các cột bắt buộc **status, registered_at**, còn thao tác trên Enrollment thực hiện lifecycle riêng. Dễ sinh inconsistency và SQL chồng chéo.

Sau khi chuyển model, nên chọn **Enrollment là nguồn ghi chính**, bỏ direct @ManyToMany hoặc cố tình giới hạn mapping chỉ đọc với lý do rất rõ (và hiểu các giới hạn provider). Với nghiệp vụ thông thường, thay bằng query/projection hoặc method đọc **student.getEnrollments()** là cách nhất quán hơn.

### 10.3. Không chuyển nguyên entity detached vào graph managed

Nếu API nhận Student ID và Course ID, service nên nạp hai entity trong cùng transaction như phần 9. Không tạo Student “giả” chỉ có ID rồi tự gán vào Enrollment mà không hiểu trạng thái entity/reference. Có thể dùng **EntityManager.getReference(...)** để tham chiếu hiệu quả khi thích hợp, nhưng một ID không tồn tại có thể chỉ gây lỗi lúc truy cập hoặc khi FK được kiểm tra; getReference không tự xác nhận tồn tại.

## 11. Query trực tiếp bảng liên kết trở nên rõ ràng hơn

Khi Enrollment là entity, bạn có thể lọc và sắp xếp theo status, registeredAt, withdrawnAt bằng JPQL mà không phải thao tác trên collection Course.

### 11.1. Đăng ký đang hoạt động của một Student

~~~java
List<Enrollment> active = em.createQuery(
    """
    select e
    from Enrollment e
    join fetch e.course
    where e.student.id = :studentId
      and e.status = :status
    order by e.registeredAt desc
    """,
    Enrollment.class
)
.setParameter("studentId", studentId)
.setParameter("status", EnrollmentStatus.ACTIVE)
.getResultList();
~~~

**join fetch e.course** tải quan hệ to-one Course khi lấy Enrollment, hữu ích nếu ngay sau đó cần course.title. Nó khác với fetch join một collection lớn, vốn có nguy cơ nhân nhiều dòng và khó phân trang.

### 11.2. Tìm toàn bộ sinh viên đăng ký một khóa học

~~~java
List<Enrollment> records = em.createQuery(
    """
    select e
    from Enrollment e
    join fetch e.student
    where e.course.id = :courseId
      and e.status = :status
    order by e.registeredAt asc
    """,
    Enrollment.class
)
.setParameter("courseId", courseId)
.setParameter("status", EnrollmentStatus.ACTIVE)
.getResultList();
~~~

Trong mô hình @ManyToMany thuần, bạn có thể lấy Course.students nhưng không lọc trực tiếp theo metadata của từng liên kết vì không có entity trung gian. Với Enrollment, status là thuộc tính first-class.

### 11.3. Trả projection DTO cho API

Giả sử có DTO:

~~~java
package com.example.school.dto;

import java.time.Instant;
import com.example.school.EnrollmentStatus;

public record EnrollmentRow(
    Long enrollmentId,
    Long studentId,
    String studentName,
    Long courseId,
    String courseTitle,
    EnrollmentStatus status,
    Instant registeredAt
) {}
~~~

JPQL constructor expression:

~~~java
List<EnrollmentRow> rows = em.createQuery(
    """
    select new com.example.school.dto.EnrollmentRow(
        e.id, s.id, s.fullName, c.id, c.title,
        e.status, e.registeredAt
    )
    from Enrollment e
    join e.student s
    join e.course c
    where e.status = :status
    order by e.registeredAt desc
    """,
    EnrollmentRow.class
)
.setParameter("status", EnrollmentStatus.ACTIVE)
.getResultList();
~~~

Cách này chỉ chọn các cột cần hiển thị, tránh phụ thuộc việc serialize một object graph JPA có lazy associations và vòng tham chiếu. Khi cần phân trang, thêm thứ tự ổn định (ví dụ registeredAt rồi id) để hạn chế thứ tự không xác định với các bản ghi cùng timestamp.

### 11.4. Thống kê

Đếm số đăng ký ACTIVE của một Course:

~~~java
Long count = em.createQuery(
    """
    select count(e)
    from Enrollment e
    where e.course.id = :courseId
      and e.status = :status
    """,
    Long.class
)
.setParameter("courseId", courseId)
.setParameter("status", EnrollmentStatus.ACTIVE)
.getSingleResult();
~~~

Nếu chỉ cần count, **không load Course.enrollments.size()** khi collection rất lớn, trừ khi hiểu rõ provider và cache. Query COUNT có thể tận dụng index và không cần dựng nhiều entity.

### 11.5. Index cho bảng liên kết có metadata

Tùy truy vấn:

~~~sql
CREATE INDEX idx_enrollments_student_status
    ON enrollments(student_id, status);

CREATE INDEX idx_enrollments_course_registered
    ON enrollments(course_id, registered_at);
~~~

Không thêm mọi index có thể nghĩ ra; mỗi index tăng chi phí ghi và lưu trữ. Chọn dựa trên workload, cardinality, EXPLAIN và đặc điểm DB. Một bảng join entity lớn có thể cần partitioning hoặc chiến lược archive khi lịch sử tăng nhanh; đó là quyết định vận hành, không phải thuộc tính riêng của JPA.

## 12. Độ lớn của collection và tránh N+1

Association entity có thể làm cấu trúc Java sâu hơn:

~~~text
Course
 └── enrollments (List<Enrollment>)
       ├── Enrollment 1 → Student
       ├── Enrollment 2 → Student
       └── ...
~~~

Nếu Course có hàng triệu Enrollment, việc tải toàn bộ collection để kiểm tra một sinh viên đã đăng ký hay chưa là không hợp lý. Dùng query theo cặp ID hoặc repository **existsByStudent_IdAndCourse_Id** sẽ hiệu quả hơn.

Ví dụ code dễ sinh N+1:

~~~java
List<Enrollment> enrollments = repository.findAll();

for (Enrollment e : enrollments) {
    System.out.println(e.getStudent().getFullName());
}
~~~

Nếu **student** là LAZY, khi duyệt mỗi Enrollment có thể phát query riêng để load Student. Giải pháp theo use case gồm:

- **join fetch** có kiểm soát cho quan hệ **to-one** cần dùng;
- DTO projection chọn cột cần thiết;
- batch fetching/entity graph nếu provider và query phù hợp;
- pagination hoặc keyset pagination khi số bản ghi lớn;
- tránh serialize entity graph trực tiếp ra API.

Với association entity, khả năng filter trực tiếp Enrollment thường giúp **tránh load các collection many-to-many khổng lồ**. Đây là một lợi ích kiến trúc đáng kể khi domain phát triển.

## 13. Đồng thời, transaction và @Version trên link entity

Khi nhiều request cùng sửa một Enrollment, cần phân biệt **hai loại xung đột**:

1. **Duplicate insert**: hai request cùng tạo link cho một cặp Student–Course.
2. **Lost update/transition conflict**: hai request sửa trạng thái của **cùng Enrollment**.

### 13.1. Duplicate insert

Đã phân tích ở phần 9: **UNIQUE(student_id, course_id)** là lớp bảo vệ quyết định. Một check tồn tại trước khi insert chỉ hỗ trợ trải nghiệm lỗi, không loại bỏ race condition.

### 13.2. Cập nhật trạng thái cùng lúc

Ví dụ:

~~~text
T1: load Enrollment #50, status ACTIVE, version 3
T2: load Enrollment #50, status ACTIVE, version 3
T1: withdraw → WITHDRAWN, version 4, commit
T2: một thao tác khác dựa trên version 3 → UPDATE
~~~

Với **@Version**, provider có thể thêm điều kiện version vào UPDATE và báo **OptimisticLockException** nếu bản ghi đã đổi. Khi gặp lỗi, transaction thường phải rollback; ứng dụng có thể báo xung đột hoặc retry **toàn bộ thao tác trong transaction mới** sau khi đọc lại trạng thái.

### 13.3. Giới hạn số chỗ học

Giả sử Course có capacity = 30. Nếu có 29 Enrollment ACTIVE và hai request mới cùng đăng ký:

~~~text
T1: COUNT(ACTIVE) = 29
T2: COUNT(ACTIVE) = 29
T1: INSERT Enrollment(student A, course X)
T2: INSERT Enrollment(student B, course X)
Kết quả: 31 ACTIVE nếu không có bảo vệ khác
~~~

Unique pair không giúp vì hai Student khác nhau; **@Version trên từng Enrollment cũng không giúp**, vì đó là hai entity mới khác nhau. Cần thiết kế concurrency ở **Course/capacity aggregate**:

- Lock Course row bằng **PESSIMISTIC_WRITE** khi kiểm tra và đặt chỗ;
- Hoặc giữ bộ đếm và cập nhật bằng câu SQL nguyên tử có điều kiện;
- Hoặc dùng isolation/constraint phù hợp với RDBMS và điều kiện đồng thời;
- Kết hợp timeout, retry và idempotency theo nghiệp vụ.

Ví dụ ý tưởng cập nhật nguyên tử bằng SQL:

~~~sql
UPDATE courses
SET reserved_seats = reserved_seats + 1
WHERE id = :course_id
  AND reserved_seats < capacity;
~~~

Chỉ khi số hàng cập nhật bằng 1 mới tiếp tục tạo Enrollment, trong **cùng database transaction**. Cột reserved_seats và capacity phải được tạo thêm nếu chọn thiết kế này; đồng bộ hủy đăng ký và xử lý rollback là trách nhiệm của service. Không dùng đoạn SQL này như giải pháp đầy đủ nếu thiếu đồng bộ và transaction.

### 13.4. Transaction không kéo dài đến HTTP response

Tạo Enrollment phải được commit thành công trước khi xác nhận đăng ký cuối cùng với người dùng. Một phương thức đã gọi **save** chưa đồng nghĩa thành công nếu lỗi constraint có thể xuất hiện ở flush/commit. Với hệ thống thanh toán hay gửi email, cần tránh phát side effect không thể rollback trước khi transaction commit; có thể dùng transactional outbox hoặc cơ chế sự kiện sau commit được thiết kế rõ.

## 14. Association entity có thể tham chiếu tới entity khác

Một mốc quan trọng: sau khi Enrollment có ID, các module khác có thể tham chiếu trực tiếp đến nó.

Ví dụ:

~~~text
Student ─── Enrollment ─── Course
              │
              ├── Payment
              ├── Certificate
              └── ApprovalDecision
~~~

**Payment** có thể chứa:

~~~java
@Entity
@Table(name = "payments")
public class Payment {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "enrollment_id", nullable = false)
    private Enrollment enrollment;

    @Column(name = "amount", precision = 19, scale = 2, nullable = false)
    private BigDecimal amount;

    protected Payment() { }
}
~~~

Với @ManyToMany thuần, không có Enrollment entity để Payment trỏ tới. Việc buộc Payment lưu cả studentId + courseId là khả thi nhưng dễ phát sinh nhiều khóa ngoại tổng hợp, logic truy vấn và ràng buộc phức tạp. Một surrogate ID của Enrollment có thể đơn giản hóa tham chiếu.

Tuy nhiên nếu payment cần theo **lần học lại** chứ không chỉ theo cặp Student–Course, phải giải quyết identity attempt ngay từ model trước khi thêm Payment. Không dùng ID kỹ thuật để che đi sự thiếu rõ ràng của nghiệp vụ.

## 15. Tình huống thực tế khác: User–Project và role của từng thành viên

Giả sử mỗi người dùng có thể tham gia nhiều dự án, và một dự án có nhiều người dùng. Lúc đầu bảng chỉ có:

~~~sql
CREATE TABLE project_users (
    project_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    PRIMARY KEY (project_id, user_id)
);
~~~

Sau một thời gian, nghiệp vụ yêu cầu:

- Người dùng có role **OWNER**, **EDITOR**, **VIEWER** khác nhau trên từng dự án.
- Một owner có thể mời người khác và phải lưu **invited_by**.
- Lời mời có trạng thái **PENDING**, **ACCEPTED**, **REVOKED**.
- Cần biết thời điểm tham gia hoặc bị thu hồi.
- Cần query “ai có quyền EDITOR trong Project X” và log thay đổi quyền.

Một entity **ProjectMembership** phản ánh domain tốt hơn:

~~~java
@Entity
@Table(
    name = "project_memberships",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_project_member",
        columnNames = {"project_id", "user_id"}
    )
)
public class ProjectMembership {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "project_id", nullable = false, updatable = false)
    private Project project;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id", nullable = false, updatable = false)
    private User user;

    @Enumerated(EnumType.STRING)
    @Column(name = "role", nullable = false)
    private ProjectRole role;

    @Enumerated(EnumType.STRING)
    @Column(name = "state", nullable = false)
    private MembershipState state;

    @Column(name = "invited_at", nullable = false, updatable = false)
    private Instant invitedAt;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "invited_by_user_id")
    private User invitedBy;

    @Version
    private Long version;

    protected ProjectMembership() { }

    // Factory invite(), accept(), revoke(), changeRole()...
}
~~~

Các class **Project**, **User**, enum **ProjectRole** và **MembershipState** được giả định tồn tại. Ví dụ nhằm cho thấy chỗ đặt metadata/association trên link, không phải toàn bộ implementation authorization.

Đây cũng là bài toán bảo mật: quyền người dùng **không thể chỉ đọc từ một Set<Project>**; cần kiểm tra **role**, **state**, phạm vi hiệu lực và giao dịch hiện tại. Nếu một user có thể được cấp nhiều role trong cùng project, unique pair sẽ quá chặt; model có thể cần **(project_id, user_id, role)** hoặc membership + bảng role assignment tùy chính sách.

## 16. Ví dụ khác: Order–Product không chỉ là many-to-many

Đơn hàng và sản phẩm thường được nghĩ là hai bên quan hệ nhiều–nhiều:

~~~text
Order A có Product X, Product Y
Product X xuất hiện trong Order A, Order B
~~~

Nhưng một cặp Order–Product còn cần:

- **quantity**;
- **unitPriceAtPurchase** (giá chốt tại thời điểm mua, không phải giá hiện tại của Product);
- **discount**;
- **tax**;
- **lineTotal**;
- thông tin trả hàng hoặc thực hiện đơn.

Vì vậy nên có **OrderLine** như entity (hoặc cấu trúc phù hợp), không đặt trực tiếp:

~~~java
@ManyToMany
private Set<Product> products;
~~~

mà mô hình:

~~~text
Order 1 ─── * OrderLine * ─── 1 Product
                   ├── quantity
                   ├── unitPriceAtPurchase
                   └── discount
~~~

Trên **OrderLine**, hai owning associations có thể là:

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "order_id", nullable = false)
private PurchaseOrder order;

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "product_id", nullable = false)
private Product product;
~~~

Điểm đặc biệt: **OrderLine** thường được sở hữu về vòng đời bởi Order, nhưng Product độc lập và dùng chung nhiều Order. Vì vậy có thể có **cascade/orphanRemoval từ Order sang OrderLine**, nhưng **không cascade REMOVE từ OrderLine sang Product**.

Ngoài ra, một đơn hàng **có thể chứa cùng Product trên nhiều dòng** nếu khác promotion, giá, batch hoặc cấu hình; trong trường hợp đó **UNIQUE(order_id, product_id)** có thể không phù hợp. Định danh và constraint phải đi theo nghiệp vụ thực sự, không theo giả định “một cặp chỉ một lần”.

## 17. Migration từ @ManyToMany sang association entity

Nếu ứng dụng đã chạy production với bảng **student_courses** chứa hai FK, chuyển sang Enrollment là **thay đổi mô hình và có thể là thay đổi schema**. Không nên chỉ xóa annotation cũ, thêm entity mới rồi hy vọng dữ liệu cũ tự có status/registeredAt hợp lệ.

### 17.1. Xác định dữ liệu đã có

Kiểm tra:

- Bảng nối tên gì, FK nào và primary/unique key nào?
- Có cặp trùng không? Có row orphan do thiếu FK không?
- Những bản ghi cũ có lịch sử ngày đăng ký thật không?
- Có ứng dụng/batch job nào khác đang INSERT/DELETE bảng nối không?
- API cũ có dùng hành vi xóa link vật lý không?
- Có FK của bảng khác tham chiếu bảng nối qua composite key không?
- Có deployment cuốn chiếu, nhiều instance chạy song song version cũ và mới không?

Nếu không có timestamp lịch sử, không được gán một thời điểm rồi gọi đó là **thời điểm đăng ký thật**. Có thể sử dụng **migratedAt** hoặc timestamp backfill được đánh dấu nguồn gốc phù hợp với yêu cầu dữ liệu.

### 17.2. Chiến lược thay đổi ít rủi ro

Một lộ trình thường là **expand → backfill → switch → contract**:

1. **Expand schema:** bổ sung metadata/ID/constraint theo cách tương thích với đường ghi cũ.
2. **Backfill dữ liệu cũ:** status, timestamp và ID hợp lệ; xử lý dữ liệu trùng hoặc sai FK.
3. **Deploy code mới:** mapping Enrollment và repository thay thế @ManyToMany; cập nhật API/service đồng thời.
4. **Chuyển nguồn ghi:** bảo đảm mọi đường ghi link đi qua Enrollment, không còn đường @ManyToMany cũ cạnh tranh.
5. **Kiểm chứng dữ liệu:** số lượng link cũ so với số Enrollment, trạng thái và constraints.
6. **Contract:** chỉ sau khi mọi instance/job đã nâng cấp mới bỏ schema/phần tương thích không còn cần thiết.

Đây là lộ trình khái niệm, không phải script migration có thể chạy nguyên xi cho mọi hệ thống.

### 17.3. Ví dụ mở rộng bảng đang tồn tại

Nếu muốn giữ tên bảng **student_courses** và bảng cũ có composite PK, một hướng minh họa PostgreSQL là bổ sung metadata:

~~~sql
ALTER TABLE student_courses
    ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE';

ALTER TABLE student_courses
    ADD COLUMN registered_at TIMESTAMP WITH TIME ZONE;

ALTER TABLE student_courses
    ADD COLUMN withdrawn_at TIMESTAMP WITH TIME ZONE;

ALTER TABLE student_courses
    ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
~~~

Cần **backfill registered_at** bằng một nguồn đáng tin cậy hoặc ghi rõ timestamp migration có tính ước định, rồi thêm NOT NULL sau khi dữ liệu hợp lệ.

Nếu chọn composite ID, có thể **giữ composite PK**, không cần thêm id. Nếu chọn surrogate ID, việc thêm cột id, bảo đảm unique/not-null, chuyển primary key và giữ unique pair phải được lên kế hoạch riêng, đặc biệt khi bảng nối hiện có được các FK khác tham chiếu. Ví dụ thao tác schema:

~~~sql
-- Minh họa một bước mở rộng cho hướng surrogate ID.
ALTER TABLE student_courses
    ADD COLUMN id BIGINT GENERATED BY DEFAULT AS IDENTITY;
~~~

**Chỉ thêm cột chưa hoàn tất migration sang @Id(id)**. Cần xác định tất cả ID đã được backfill, unique/not-null, đổi primary key khi phù hợp, giữ UNIQUE(student_id, course_id), rà soát FK phụ thuộc, và test JPA mapping với schema cuối cùng. Không dùng **hibernate.hbm2ddl.auto=create** trên database cần giữ dữ liệu.

### 17.4. Không để hai phiên bản ghi cùng bảng theo semantics khác nhau

Trong giai đoạn rolling deployment:

~~~text
Version cũ: student.getCourses().add(course)
    → INSERT student_courses(student_id, course_id)

Version mới: enrollments.save(new Enrollment(...))
    → INSERT student_courses(student_id, course_id, status, registered_at, ...)
~~~

Nếu metadata mới là NOT NULL không có default, version cũ có thể bị lỗi. Nếu version cũ DELETE link trong khi version mới coi WITHDRAWN là trạng thái lịch sử, dữ liệu có thể bị xóa bất ngờ. Cần quyết định cơ chế tương thích/điều phối rollout hoặc cửa sổ chuyển đổi, không giả định hai phiên bản tự tương thích chỉ vì chung bảng.

### 17.5. Chuyển API và query

Trước đây:

~~~java
student.getCourses().add(course);
student.getCourses().remove(course);
~~~

Sau đó:

~~~java
Long enrollmentId = enrollmentService.register(studentId, courseId);
enrollmentService.withdraw(enrollmentId);
~~~

Các query cũ dạng **JOIN student.courses** cần được đổi thành **JOIN Student.enrollments e JOIN e.course c**, hoặc query trực tiếp Enrollment. Các phép đếm phải quyết định **đếm tất cả bản ghi hay chỉ ACTIVE**. Đây là sự thay đổi semantics quan trọng, không chỉ đổi tên field.

## 19. Kiểm thử association entity

Cần test cả **domain behavior**, **mapping**, **schema constraints** và **concurrency**.

### 19.1. Tạo mới và đọc lại

Ví dụ JUnit trong transaction với EntityManager đã được cấu hình:

~~~java
@Test
void persistsEnrollmentWithMetadata() {
    Student student = new Student("Lan");
    Course course = new Course("JPA Fundamentals");
    em.persist(student);
    em.persist(course);

    Instant registeredAt = Instant.parse("2026-11-15T08:00:00Z");
    Enrollment enrollment =
        Enrollment.register(student, course, registeredAt);

    assertTrue(student.getEnrollments().contains(enrollment));
    assertTrue(course.getEnrollments().contains(enrollment));

    em.persist(enrollment);
    em.flush();

    Long id = enrollment.getId();
    em.clear();

    Enrollment loaded = em.find(Enrollment.class, id);
    assertEquals(EnrollmentStatus.ACTIVE, loaded.getStatus());
    assertEquals(registeredAt, loaded.getRegisteredAt());
    assertEquals(student.getId(), loaded.getStudent().getId());
    assertEquals(course.getId(), loaded.getCourse().getId());
}
~~~

**flush + clear** buộc provider đọc lại trạng thái từ DB, thay vì chỉ kiểm tra object còn trong persistence context. Nếu test transaction chưa commit, đây vẫn là kiểm tra trong cùng transaction; xác minh visibility ngoài transaction cần test commit/transaction khác.

### 19.2. Chuyển trạng thái

~~~java
@Test
void withdrawPreservesEnrollmentRow() {
    Student student = new Student("Minh");
    Course course = new Course("SQL");
    em.persist(student);
    em.persist(course);

    Enrollment enrollment = Enrollment.register(
        student, course, Instant.parse("2026-11-15T08:00:00Z"));
    em.persist(enrollment);
    em.flush();

    Long enrollmentId = enrollment.getId();
    Instant withdrawnAt = Instant.parse("2026-11-15T09:00:00Z");
    enrollment.withdraw(withdrawnAt);
    em.flush();
    em.clear();

    Enrollment loaded = em.find(Enrollment.class, enrollmentId);
    assertNotNull(loaded); // Không bị DELETE.
    assertEquals(EnrollmentStatus.WITHDRAWN, loaded.getStatus());
    assertEquals(withdrawnAt, loaded.getWithdrawnAt());
}
~~~

### 19.3. Duplicate pair

Tạo hai Enrollment cho cùng Student/Course trong hai transaction hoặc hai object trong một transaction; kỳ vọng database **UNIQUE** từ chối bản ghi trùng. Không chỉ test kết quả của **existsBy...** rồi kết luận đã chống được race condition.

Lưu ý với constraint SQL và JPA exception: lỗi có thể xuất hiện lúc **flush hoặc commit**. Khi dùng test framework tự rollback cuối test, hãy cố ý **flush** hoặc điều khiển transaction để lỗi thực sự phát sinh tại bước mong đợi.

### 19.4. Optimistic locking

Hai transaction đọc cùng Enrollment với version ban đầu, sau đó cùng thực hiện cập nhật. Kỳ vọng transaction thứ hai phát hiện conflict nếu transaction thứ nhất đã commit phiên bản mới trước thời điểm update của transaction thứ hai. Với Spring, lỗi có thể được dịch thành các exception concurrency của framework.

### 19.5. Tập ca kiểm thử khuyến nghị

| Test | Kỳ vọng |

| Persist Enrollment mới | Một hàng link với hai FK và metadata chính xác |

## 20. Bài tập thực hành

### Bài 1: Khi nào giữ @ManyToMany?

Một trang tin có Article–Tag. Bảng nối chỉ gồm article_id và tag_id; người dùng có thể thêm/bỏ Tag. Không lưu ai gắn, thời điểm gắn, trạng thái hay lịch sử.

**Câu hỏi:** Có cần ArticleTag entity riêng không? Hãy nêu ít nhất ba lý do giữ @ManyToMany hoặc chuyển sang entity.

**Định hướng:** giữ @ManyToMany là lựa chọn hợp lý nếu chỉ biểu diễn tính có/không của link và không có lifecycle; entity riêng vẫn có thể được cân nhắc nếu yêu cầu sắp tới như moderation, vị trí hiển thị, timestamp hay audit theo từng link.

### Bài 2: Tìm nơi đặt thuộc tính

Mô hình User–Project cần các field: **role**, **joinedAt**, **invitedBy**, **membershipStatus**.

Hãy giải thích vì sao không đặt role của user trong Project vào User.role hoặc Project.role. Phác thảo entity ProjectMembership với hai @ManyToOne, các field metadata, unique constraint và phương thức accept/revoke.

### Bài 3: Hai @ManyToOne thay cho một @ManyToMany

Cho:

~~~java
@ManyToMany
private Set<Course> courses;
~~~

Hãy thiết kế:
 
~~~text
Student 1 ── * Enrollment * ── 1 Course
~~~

và viết tên của bốn thuộc tính có thể có:

- Enrollment.student;
- Enrollment.course;
- Student.enrollments;
- Course.enrollments.

Xác định owning sides, mappedBy trên hai collection và vị trí FK của bảng Enrollment. Hãy chỉ ra rằng hai inverse collections là tùy chọn nếu không cần duyệt ngược.

### Bài 4: Chọn khóa chính

Một bảng Enrollment phải được tham chiếu từ Payment; mỗi sinh viên có thể học lại một Course nhiều đợt. Hãy so sánh:

1. PK composite (student_id, course_id);
2. surrogate id và unique(student_id, course_id);
3. surrogate id cùng unique(student_id, course_id, attempt_no).

Mô hình nào phản ánh yêu cầu nhiều lần học lại? Nếu chỉ được phép một attempt ACTIVE, bạn sẽ bảo vệ điều đó ở DB như thế nào với PostgreSQL?

### Bài 5: Tại sao kiểm tra trước không đủ?

Hai request đều chạy:

~~~java
if (!enrollments.existsByStudent_IdAndCourse_Id(sid, cid)) {
    enrollments.save(Enrollment.register(student, course, now));
}
~~~

Hãy diễn tả timeline khiến cả hai request thấy false. Constraint nào phải đặt tại database? Lỗi cần xử lý ở flush hay commit? Sau khi một request thất bại, có nên tiếp tục dùng transaction đã bị lỗi không?

### Bài 6: Xác định vòng đời và cascade

Mô hình Order–OrderLine–Product có:
- OrderLine.quantity và unitPrice;
- Product được dùng bởi hàng nghìn Order;
- Xóa một Line khỏi Order nghĩa là bỏ một mặt hàng trong đơn.

Hãy chọn cascade và orphanRemoval từ Order → OrderLine, và giải thích vì sao **không cascade REMOVE** từ OrderLine → Product. Điều này liên quan thế nào đến việc “bảng nối” đã trở thành domain entity?

### Bài 7: JPQL báo cáo

Viết JPQL lấy danh sách **Enrollment ACTIVE** thuộc Course ID X, kèm tên Student, thời điểm đăng ký, sắp xếp mới nhất trước. Hãy chọn **query entity + join fetch** hoặc **constructor projection**, giải thích vì sao không nên load cả Course.enrollments rồi lọc trong Java nếu bảng lớn.

### Bài 8: Migration an toàn

Hệ thống có bảng student_courses(student_id, course_id) với composite PK và nhiều dữ liệu production. Cần bổ sung status, registeredAt và API quản lý Enrollment.

- tránh xóa link khi user withdraw;
- cách xử lý version cũ vẫn dùng @ManyToMany;
- test sau migration trước khi cắt đường ghi cũ.

### Bài 9: Phát hiện sai khác giữa unique và capacity

## 21. Cách đưa ra quyết định trong dự án

Khi đối mặt một quan hệ nhiều–nhiều, có thể đi lần lượt:

1. **Xác định bản chất link:** liên kết đơn giản hay một khái niệm nghiệp vụ với lifecycle?
2. **Kiểm kê thuộc tính của link:** thời gian, trạng thái, quyền, số lượng, giá, thứ tự, người tạo, metadata.
3. **Xác định identity và cardinality theo thời gian:** một cặp có thể có một hàng, nhiều attempt, hoặc nhiều hàng có các khoảng hiệu lực khác nhau?
4. **Chọn mapping:** @ManyToMany trực tiếp nếu link thuần túy; association entity với hai @ManyToOne nếu link có semantics riêng.
5. **Chọn khóa chính:** surrogate ID hay composite ID; đừng quên unique constraints độc lập với ID.
6. **Xác định lifecycle:** xóa link vật lý, soft delete, state transition, lưu lịch sử hay audit event?
7. **Đặt quyền sở hữu:** hai FK thuộc association entity; inverse @OneToMany chỉ khi thực sự cần; chọn cascade hợp lý.
8. **Thiết kế API/service:** đăng ký, hủy, phê duyệt, thay vai trò, gia hạn; không để setter hoặc sửa collection tùy ý phá invariant.
9. **Bảo vệ dữ liệu tại DB:** FK, NOT NULL, UNIQUE, CHECK, index, version/concurrency phù hợp.
10. **Dự kiến query:** filter status/time, pagination, projection và fetch strategy; không tải toàn bộ object graph khi chỉ cần vài hàng.
11. **Lập kế hoạch migration:** nếu đã dùng @ManyToMany production, bảo toàn dữ liệu và tránh hai đường ghi cạnh tranh.
12. **Kiểm thử:** domain transition, round-trip flush/clear, constraints, concurrency và dữ liệu lịch sử.

Một phép nhớ nhanh:

~~~text
@ManyToMany:
    Student.courses ↔ Course.students
    Join table chỉ biểu diễn có / không có liên kết.

Association entity:
    Student ── Enrollment ── Course
    Enrollment có thuộc tính, identity và lifecycle riêng.
    Hai FK được ánh xạ bởi hai @ManyToOne.
    Có thể dùng @OneToMany(mappedBy = ...) để duyệt ngược.
    UNIQUE, FK, CHECK và transaction bảo vệ dữ liệu thực.
~~~

**Kết luận:** cần chuyển bảng liên kết thành entity riêng khi **mối liên kết đã trở thành một phần của domain với dữ liệu, trạng thái, hành vi, lịch sử hoặc định danh riêng**. @ManyToMany giúp mô hình gọn cho các cặp quan hệ thuần túy; association entity giúp biểu diễn Enrollment, Membership, OrderLine và những liên kết nghiệp vụ phức tạp một cách chính xác. Quyết định đúng không chỉ nằm ở annotation JPA mà còn ở **khóa chính, ràng buộc database, vòng đời, transaction, query và kế hoạch phát triển dữ liệu lâu dài**.
