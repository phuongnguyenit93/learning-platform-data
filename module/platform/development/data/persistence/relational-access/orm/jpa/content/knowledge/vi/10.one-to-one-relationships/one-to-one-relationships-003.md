# Ánh xạ một-một với khóa chính chia sẻ trong JPA

Trong Jakarta Persistence (JPA), quan hệ **một-một (one-to-one)** mô tả việc một entity liên kết với tối đa một entity khác. Một cách thiết kế đặc biệt là **khóa chính chia sẻ (shared primary key)**: khóa chính của entity phụ đồng thời là **khóa ngoại** tham chiếu đến khóa chính của entity chính.

Ví dụ, hệ thống quản lý người dùng lưu tài khoản ở bảng `app_users` và thông tin hồ sơ mở rộng ở bảng `user_profiles`. Mỗi hồ sơ thuộc đúng một tài khoản, mỗi tài khoản có tối đa một hồ sơ. Với shared primary key, một hồ sơ không có khóa `profile_id` độc lập: giá trị `user_profiles.user_id` vừa là **PRIMARY KEY**, vừa là **FOREIGN KEY** tới `app_users.id`.

Trong JPA, lựa chọn thường dùng và rõ ràng nhất cho kiểu ánh xạ này là kết hợp **`@OneToOne` + `@MapsId`** trên phía phụ thuộc. Nó cho phép JPA sử dụng định danh của entity chính làm định danh của entity phụ, thay vì phải tự quản lý hai bộ khóa.

Bài học trình bày cấu trúc quan hệ, cách thiết kế hai entity, vòng đời tạo/đọc/xóa, quan hệ một chiều và hai chiều, những khác biệt với quan hệ một-một dùng khóa ngoại riêng, cùng các lỗi thường gặp.

## 1. Shared primary key là gì?

Giả sử mỗi người dùng có một bản ghi tài khoản và có thể có thêm hồ sơ:

~~~text
        app_users                          user_profiles
  +---------------------+          +--------------------------+
  | id (PK)             |<---------| user_id (PK + FK)        |
  | email               |   1 : 0..1| display_name           |
  +---------------------+          | biography                |
                                   +--------------------------+

        AppUser                                 UserProfile
          id=101                                id=101
             ^                                     |
             +--------- profile.user ---------------+
~~~

Các ràng buộc được hiểu như sau:

- `app_users.id` là khóa chính của tài khoản.
- `user_profiles.user_id` là khóa chính của hồ sơ, đồng thời là khóa ngoại tới `app_users.id`.
- Một `user_id` không thể xuất hiện hai lần trong bảng hồ sơ vì có ràng buộc PRIMARY KEY.
- Hồ sơ không thể tham chiếu tới tài khoản không tồn tại nếu FOREIGN KEY được thực thi.
- Một tài khoản **có thể chưa có hồ sơ**: khóa ngoại từ bảng hồ sơ sang bảng tài khoản không buộc mọi tài khoản phải có dòng hồ sơ.

Dữ liệu minh họa:

| `app_users.id` | `email` | `user_profiles.user_id` | `display_name` |
| ---: | --- | ---: | --- |
| 101 | an@example.test | 101 | An |
| 102 | binh@example.test | 102 | Bình |
| 103 | chi@example.test | *(không có hồ sơ)* | *(không có)* |

Với user 101, cả hai entity có cùng giá trị định danh `101`, nhưng **chúng vẫn là hai entity thuộc hai bảng khác nhau**, có kiểu Java và vòng đời persistence riêng. “Chia sẻ khóa” không có nghĩa hai object Java là cùng một instance hay cùng một persistence context entry.

### 1.1. SQL minh họa

Ví dụ schema PostgreSQL:

~~~sql
CREATE TABLE app_users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(200) NOT NULL UNIQUE
);

CREATE TABLE user_profiles (
    user_id BIGINT PRIMARY KEY,
    display_name VARCHAR(120) NOT NULL,
    biography VARCHAR(1000),
    CONSTRAINT fk_user_profiles_user
        FOREIGN KEY (user_id)
        REFERENCES app_users(id)
);
~~~

Điểm quyết định là **một cột duy nhất `user_id`** của `user_profiles` đảm nhận cả hai vai trò. Không có `id BIGINT GENERATED ...` riêng trong bảng `user_profiles`.

Ví dụ dữ liệu:

~~~sql
INSERT INTO app_users (email)
VALUES ('an@example.test');

-- Giả sử tài khoản vừa tạo có id = 101.
INSERT INTO user_profiles (user_id, display_name, biography)
VALUES (101, 'An', 'Yêu thích công nghệ');
~~~

SQL trên minh họa nguyên tắc: chỉ tạo hồ sơ **sau khi** đã có tài khoản và biết ID của tài khoản. Khi dùng JPA với `@MapsId` và cascade phù hợp, provider có thể thực hiện việc sắp xếp này.

## 2. So sánh với one-to-one có khóa ngoại riêng

Cùng một quan hệ nghiệp vụ có thể được ánh xạ bằng hai cách thiết kế database.

### 2.1. Khóa ngoại riêng

~~~sql
CREATE TABLE user_profiles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL UNIQUE,
    display_name VARCHAR(120) NOT NULL,
    FOREIGN KEY (user_id) REFERENCES app_users(id)
);
~~~

Một profile có ID riêng `id`, còn `user_id` chỉ đóng vai trò foreign key. Ràng buộc `UNIQUE(user_id)` giới hạn tối đa một profile cho một user.

### 2.2. Khóa chính chia sẻ

~~~sql
CREATE TABLE user_profiles (
    user_id BIGINT PRIMARY KEY,
    display_name VARCHAR(120) NOT NULL,
    FOREIGN KEY (user_id) REFERENCES app_users(id)
);
~~~

Khóa riêng `id` không còn cần thiết; định danh hồ sơ chính là định danh user được liên kết.

| Tiêu chí | One-to-one có FK riêng | One-to-one dùng shared PK |
| --- | --- | --- |
| Khóa chính của hồ sơ | `id` riêng | `user_id`, lấy từ khóa cha |
| Khóa ngoại | `user_id` | Chính `user_id` đó |
| Cần `UNIQUE(user_id)` riêng? | Có, để cưỡng chế tối đa một hồ sơ/user | Không, PRIMARY KEY đã bảo đảm unique |
| Vòng đời ID của hồ sơ | Có thể độc lập với user | Phụ thuộc định danh của user |
| Có thể chuyển hồ sơ sang user khác? | Có thể cập nhật FK nếu nghiệp vụ cho phép | Thay user đồng nghĩa đổi PK, thường không làm trực tiếp |
| Ánh xạ JPA phổ biến | `@OneToOne` + `@JoinColumn(unique=true)` | `@OneToOne` + `@MapsId` |
| Phù hợp | Hồ sơ có định danh/đời sống riêng | Hồ sơ là phần mở rộng một-một của chính user |

**Shared PK phù hợp khi định danh của entity phụ có ý nghĩa hoàn toàn phụ thuộc entity chính.** Nếu entity phụ cần được chuyển giữa các entity chính hoặc phải có ID độc lập, khóa ngoại riêng thường dễ thích ứng hơn.

## 3. Mô hình entity với @MapsId

Ví dụ dùng Java 17+ và Jakarta Persistence 3.x, với các class ở package `com.example.shop.domain`. Cách tiếp cận này cũng có trong JPA 2.x, nhưng các phiên bản cũ dùng import `javax.persistence.*` thay vì `jakarta.persistence.*`.

### 3.1. Entity chính: AppUser

~~~java
package com.example.shop.domain;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToOne;
import jakarta.persistence.Table;
import java.util.Objects;

@Entity
@Table(name = "app_users")
public class AppUser {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 200)
    private String email;

    @OneToOne(
        mappedBy = "user",
        cascade = CascadeType.PERSIST,
        fetch = FetchType.LAZY
    )
    private UserProfile profile;

    protected AppUser() {
        // Constructor cho JPA.
    }

    public AppUser(String email) {
        this.email = Objects.requireNonNull(email);
    }

    public void attachProfile(UserProfile newProfile) {
        Objects.requireNonNull(newProfile);

        if (this.profile != null) {
            throw new IllegalStateException(
                "User already has a profile");
        }

        newProfile.linkToUser(this);
        this.profile = newProfile;
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public UserProfile getProfile() {
        return profile;
    }
}
~~~

Ở đây, `AppUser` là **entity chính**, có ID sinh bằng `IDENTITY`. Thuộc tính `profile` là phía **inverse** của quan hệ hai chiều, được đánh dấu `mappedBy = "user"`.

`mappedBy` phải tham chiếu **tên trường liên kết ở entity còn lại** (là `UserProfile.user`), không phải tên cột `user_id` trong database. Vì là phía inverse, `AppUser.profile` **không khai báo `@JoinColumn`** để quản lý khóa ngoại.

`cascade = CascadeType.PERSIST` cho phép gọi `em.persist(user)` và đồng thời persist hồ sơ mới được gắn vào user. Ở ví dụ này, chúng ta chủ động chỉ cascade PERSIST để các thao tác xóa và cập nhật có ranh giới riêng; `CascadeType.ALL` không phải lựa chọn bắt buộc cho mọi quan hệ một-một.

### 3.2. Entity phụ: UserProfile

~~~java
package com.example.shop.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.MapsId;
import jakarta.persistence.OneToOne;
import jakarta.persistence.Table;
import java.util.Objects;

@Entity
@Table(name = "user_profiles")
public class UserProfile {

    @Id
    @Column(name = "user_id")
    private Long id;

    @MapsId
    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(
        name = "user_id",
        referencedColumnName = "id",
        nullable = false
    )
    private AppUser user;

    @Column(name = "display_name", nullable = false, length = 120)
    private String displayName;

    @Column(name = "biography", length = 1000)
    private String biography;

    protected UserProfile() {
        // Constructor cho JPA.
    }

    public UserProfile(String displayName, String biography) {
        this.displayName = Objects.requireNonNull(displayName);
        this.biography = biography;
    }

    void linkToUser(AppUser user) {
        Objects.requireNonNull(user);

        if (this.user != null && this.user != user) {
            throw new IllegalStateException(
                "A profile cannot change its owner");
        }
        this.user = user;
    }

    public Long getId() {
        return id;
    }

    public AppUser getUser() {
        return user;
    }

    public String getDisplayName() {
        return displayName;
    }

    public String getBiography() {
        return biography;
    }
}
~~~

Đây là **phía owning** của quan hệ: `UserProfile.user` có `@JoinColumn` và chịu trách nhiệm biểu diễn khóa ngoại trong DB. Cũng chính trường đó được gắn `@MapsId` để ràng buộc khóa của profile với khóa user.

### 3.3. Ý nghĩa từng annotation trên UserProfile

| Annotation/field | Vai trò |
| --- | --- |
| `@Id private Long id` | Đây vẫn là khóa chính của entity `UserProfile` |
| `@Column(name="user_id")` trên `id` | Thể hiện khóa chính của profile nằm tại cột `user_id` |
| `@OneToOne(optional=false)` trên `user` | Mỗi profile phải có một user tham chiếu; không thể có profile hợp lệ không có cha |
| `@JoinColumn(name="user_id", referencedColumnName="id")` | Cột `user_profiles.user_id` tham chiếu `app_users.id` |
| `@MapsId` | Giá trị khóa chính `UserProfile.id` được suy ra từ ID của `UserProfile.user` |
| Không có `@GeneratedValue` ở profile | Profile không tự sinh ID bằng sequence/identity riêng |
| `@OneToOne(mappedBy="user")` ở AppUser | Định nghĩa chiều truy cập ngược; không sở hữu FK |
| `cascade = PERSIST` ở AppUser | Cho phép tạo profile cùng user qua thao tác persist trên cha |

**Không tạo thêm `@GeneratedValue` cho `UserProfile.id`.** Hai generator độc lập có thể sinh ra hai số khác nhau, làm mất ý nghĩa chia sẻ định danh. Với `@MapsId`, JPA provider đồng bộ ID của entity phụ từ đối tượng cha được tham chiếu.

### 3.4. @MapsId không có tham số nghĩa là gì?

Trong ví dụ này, khóa của `UserProfile` chỉ gồm một `Long`, và toàn bộ khóa đó được mượn từ `AppUser.id`. Vì vậy chỉ cần:

~~~java
@MapsId
@OneToOne(optional = false)
@JoinColumn(name = "user_id")
private AppUser user;
~~~

`@MapsId` **không đối số** được dùng khi association cung cấp **toàn bộ khóa** của entity phụ.

Với một khóa ghép `@EmbeddedId` mà chỉ **một thành phần** được lấy từ entity khác, JPA có thể dùng `@MapsId("tenThanhPhan")`. Đây là trường hợp derived identity phức tạp hơn, không phải cú pháp bắt buộc cho shared PK đơn giản.

## 4. Trình tự tạo dữ liệu: một ID cho hai entity

Giả sử đã có `EntityManagerFactory emf` với persistence unit được cấu hình theo `RESOURCE_LOCAL`.

~~~java
import com.example.shop.domain.AppUser;
import com.example.shop.domain.UserProfile;
import jakarta.persistence.EntityManager;
import java.util.Objects;

EntityManager em = emf.createEntityManager();

try {
    em.getTransaction().begin();

    AppUser user = new AppUser("an@example.test");
    UserProfile profile =
        new UserProfile("An", "Kỹ sư phần mềm");

    user.attachProfile(profile);

    // CascadeType.PERSIST sẽ persist cả profile.
    em.persist(user);

    em.flush();

    Long userId = user.getId();
    Long profileId = profile.getId();

    if (!Objects.equals(userId, profileId)) {
        throw new IllegalStateException("IDs are not shared");
    }

    em.getTransaction().commit();
} catch (RuntimeException ex) {
    if (em.getTransaction().isActive()) {
        em.getTransaction().rollback();
    }
    throw ex;
} finally {
    em.close();
}
~~~

Trong ví dụ này:

1. `new AppUser(...)` tạo user mới, chưa có ID từ database.
2. `new UserProfile(...)` tạo profile mới, cũng chưa có ID.
3. `user.attachProfile(profile)` thiết lập **cả hai phía của quan hệ trong Java**: `user.profile` và `profile.user`.
4. `em.persist(user)` đưa user vào trạng thái managed; `CascadeType.PERSIST` áp dụng tới profile.
5. Provider lấy ID của user từ cơ chế `IDENTITY`, rồi dùng ID đó cho profile theo `@MapsId`.
6. Sau `flush()` thành công, hai ID khớp nhau; transaction `commit()` hoàn tất thay đổi.

SQL minh họa về mặt phụ thuộc:

~~~sql
INSERT INTO app_users (email)
VALUES ('an@example.test');
-- DB cấp id của user, ví dụ 101.

INSERT INTO user_profiles (user_id, display_name, biography)
VALUES (101, 'An', 'Kỹ sư phần mềm');
~~~

**Không suy luận rằng cả hai lệnh SQL luôn chạy đúng lúc gọi `persist()`.** Với `IDENTITY`, provider thường cần INSERT cha để lấy ID, nhưng thứ tự flush và thời điểm lấy khóa là chi tiết do provider điều phối phù hợp với ràng buộc. Điều có ý nghĩa là sau khi transaction thành công, child ID phải trùng parent ID.

Nếu không cấu hình cascade, ứng dụng cần chủ động persist cả hai entity trong transaction hợp lệ. Ví dụ:

~~~java
em.persist(user);
em.persist(profile);
~~~

Nhưng trước đó vẫn cần thiết lập `profile.user`, vì chỉ đặt giá trị `profile.id` mà không đặt quan hệ owning side sẽ không tạo đầy đủ một derived identity hợp lệ.

### 4.1. Vì sao phải đồng bộ cả hai phía trong Java?

JPA quan hệ hai chiều có **owning side** và **inverse side**. Ở cấu hình này, owning side là `UserProfile.user`. Nếu code chỉ gán:

~~~java
// Ý tưởng sai: chỉ cập nhật quan hệ phía inverse.
// user.profile = profile;
~~~

mà `profile.user` vẫn `null`, provider thiếu dữ liệu cần thiết để lấy shared ID và khóa ngoại cho profile.

Ngược lại, chỉ gán `profile.user = user` có thể đủ để mapping DB xác định FK, nhưng `user.getProfile()` ở object graph trong cùng phiên làm việc có thể không phản ánh quan hệ mới. Phương thức tiện ích `attachProfile(...)` giúp giữ cả hai chiều nhất quán trong bộ nhớ.

Một quy tắc hữu ích: **quan hệ owning side quyết định ghi FK**, còn helper method đảm bảo **trạng thái Java hai chiều** nhất quán.

## 5. Đọc dữ liệu qua ID chia sẻ

Do `UserProfile.id` có cùng kiểu và giá trị với `AppUser.id`, khi đã biết user ID có thể tìm trực tiếp profile:

~~~java
Long userId = 101L;

AppUser user = em.find(AppUser.class, userId);
UserProfile profile = em.find(UserProfile.class, userId);

if (profile != null) {
    System.out.println(profile.getDisplayName());
}
~~~

Hai lệnh `find` tìm **hai loại entity khác nhau** bằng cùng giá trị khóa. Persistence context vẫn quản lý chúng riêng theo **entity type + ID**.

Ngoài cách dùng `find`, có thể viết JPQL:

~~~java
UserProfile profile = em.createQuery(
    """
    SELECT p
    FROM UserProfile p
    WHERE p.user.id = :userId
    """,
    UserProfile.class
)
.setParameter("userId", 101L)
.getResultStream()
.findFirst()
.orElse(null);
~~~

`p.user.id` là đường dẫn Java từ profile sang user. Do quan hệ chia sẻ khóa, `p.id` cũng chính là ID của user:

~~~jpql
SELECT p
FROM UserProfile p
WHERE p.id = :userId
~~~

Trong trường hợp chỉ lấy một profile bằng khóa đã biết, `em.find(UserProfile.class, userId)` thường gọn hơn JPQL.

### 5.1. Đọc từ phía user khi profile có thể chưa tồn tại

Để tải một user cùng profile (nếu có):

~~~java
List<AppUser> results = em.createQuery(
    """
    SELECT u
    FROM AppUser u
    LEFT JOIN FETCH u.profile
    WHERE u.id = :id
    """,
    AppUser.class
)
.setParameter("id", 101L)
.getResultList();

AppUser user = results.isEmpty() ? null : results.get(0);

if (user != null && user.getProfile() != null) {
    System.out.println(user.getProfile().getDisplayName());
}
~~~

`LEFT JOIN FETCH` giữ lại user ngay cả khi không có profile. Dùng `JOIN FETCH` (inner join) sẽ loại user không có profile khỏi kết quả truy vấn, điều này đôi khi **không đúng** yêu cầu nghiệp vụ.

Một điểm cần chú ý: với quan hệ một-một, nhất là **phía inverse có thể null**, provider có thể cần truy vấn bổ sung để xác định có child tồn tại hay không. `FetchType.LAZY` trong annotation là lựa chọn định hướng tải; khả năng lazy thật sự còn phụ thuộc provider, enhancement và cách truy vấn. Không mặc định rằng `@OneToOne(fetch = LAZY)` luôn loại bỏ mọi truy vấn phụ.

### 5.2. Projection chỉ lấy dữ liệu cần cho API

Nếu màn hình chỉ cần email và display name:

~~~java
package com.example.shop.dto;

public record UserSummary(
    Long userId,
    String email,
    String displayName
) {
}
~~~

Có thể truy vấn bằng constructor expression:

~~~java
List<UserSummary> summaries = em.createQuery(
    """
    SELECT new com.example.shop.dto.UserSummary(
        u.id,
        u.email,
        p.displayName
    )
    FROM AppUser u
    LEFT JOIN u.profile p
    ORDER BY u.id
    """,
    UserSummary.class
).getResultList();
~~~

`UserSummary` chỉ là DTO record, **không phải entity**. Projection thường giúp trả đúng các trường cần hiển thị và tránh serializer vô tình duyệt toàn bộ quan hệ.

## 6. Phân biệt quan hệ một chiều và hai chiều

### 6.1. Một chiều từ profile sang user

Nếu nghiệp vụ thường tìm profile bằng user ID và không cần `user.getProfile()`, chỉ cần ánh xạ owning side:

~~~java
@Entity
@Table(name = "user_profiles")
public class UserProfile {

    @Id
    @Column(name = "user_id")
    private Long id;

    @MapsId
    @OneToOne(optional = false, fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", referencedColumnName = "id")
    private AppUser user;

    // Các thuộc tính, constructor/getters...
}
~~~

Lúc này `AppUser` **không cần** thuộc tính `profile` và không khai báo `mappedBy`. Tạo và persist user, profile phải do service xử lý rõ ràng hoặc bằng cascade ở một hướng khác phù hợp.

Ưu điểm: object model đơn giản hơn, tránh phải giữ hai tham chiếu nhất quán, phù hợp khi profile chủ yếu là phần mở rộng truy cập riêng. Vẫn giữ **một-một với shared PK**, vì constraint SQL không thay đổi.

### 6.2. Hai chiều: cho phép đi từ cả hai phía

Khi cần `user.getProfile()` và `profile.getUser()`, dùng hai field:

~~~java
// Bên AppUser: inverse
@OneToOne(mappedBy = "user")
private UserProfile profile;

// Bên UserProfile: owning
@MapsId
@OneToOne(optional = false)
@JoinColumn(name = "user_id")
private AppUser user;
~~~

Không đặt `@MapsId` ở bên `AppUser.profile`: ID của **profile** mới là ID được suy ra từ **user**, và foreign key nằm ở bảng `user_profiles`.

Không nên đồng thời đặt `@JoinColumn` ở cả hai phía của cùng quan hệ nếu mục tiêu là một FK/shared PK duy nhất. Làm vậy có thể khiến provider hiểu thành hai liên kết độc lập hoặc tạo mapping không như ý.

## 7. Shared PK và vòng đời xóa dữ liệu

Để xóa riêng hồ sơ mà giữ tài khoản:

~~~java
em.getTransaction().begin();

UserProfile profile = em.find(UserProfile.class, 101L);
if (profile != null) {
    em.remove(profile);
}

em.getTransaction().commit();
~~~

Nếu đang giữ một instance `AppUser` managed và đã tải `profile` trong cùng persistence context, ứng dụng cần giữ object graph nhất quán với thay đổi quan hệ; sau khi xóa trực tiếp child, tham chiếu inverse `user.profile` có thể vẫn giữ object cũ cho tới khi đồng bộ hoặc làm mới phù hợp. Vì thế nên chọn một API nghiệp vụ có trách nhiệm cập nhật trạng thái hai chiều rõ ràng.

Khi xóa **user**, schema đang có FOREIGN KEY từ profile sang user. Nếu profile còn tồn tại, xóa user đơn lẻ có thể vi phạm ràng buộc khóa ngoại. Có một số chiến lược:

1. **Xóa profile trước rồi xóa user** trong cùng transaction.
2. Cấu hình cascade remove từ user sang profile, ví dụ `cascade = {CascadeType.PERSIST, CascadeType.REMOVE}` nếu child hoàn toàn thuộc vòng đời parent.
3. Sử dụng chính sách `ON DELETE CASCADE` ở database nếu kiến trúc và ORM/provider đồng ý với việc DB thực hiện cascade; cần tránh trạng thái persistence context bị lệch khi database tự xóa dữ liệu.

Cấu hình `CascadeType.ALL` sẽ bao gồm cả REMOVE; chỉ dùng khi việc xóa user **phải kéo theo xóa profile** đúng theo nghiệp vụ.

### 7.1. orphanRemoval khác cascade remove

Có thể khai báo ở phía parent:

~~~java
@OneToOne(
    mappedBy = "user",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private UserProfile profile;
~~~

- `CascadeType.REMOVE` truyền lệnh xóa parent sang child khi `em.remove(parent)` được gọi.
- `orphanRemoval = true` biểu diễn ý định xóa child khi quan hệ sở hữu bị ngắt, với các điều kiện và ngữ nghĩa vòng đời mà JPA quy định.

Với shared primary key, **không chuyển một profile hiện có sang user khác bằng cách đổi association**, bởi điều đó đồng thời thay đổi primary key của profile. Nếu cần chuyển, nên mô hình hóa thành xóa profile cũ rồi tạo profile mới, hoặc xem lại việc dùng shared PK.

Không áp dụng `orphanRemoval` chỉ để khắc phục một lỗi constraint; hãy dùng nó khi đúng với ý nghĩa **child phụ thuộc hoàn toàn vào owner** và việc ngắt liên kết phải dẫn tới xóa child.

### 7.2. Xóa hồ sơ có làm mất user không?

Không. Quan hệ phụ thuộc theo FK là **profile → user**. Xóa profile không buộc phải xóa user. Chỉ khi ứng dụng định nghĩa cascade remove từ profile tới user (thường không mong muốn) hoặc logic nghiệp vụ riêng mới xuất hiện hành vi xóa user. Tránh khai báo `CascadeType.REMOVE` trên phía child `UserProfile.user` khi user là entity chính được nhiều nghiệp vụ sử dụng.

## 8. Optionality: 1–1 có phải luôn bắt buộc cả hai phía?

Một shared PK relationship phổ biến thể hiện **AppUser (1) → UserProfile (0..1)**:

~~~text
User 101 -------- Profile 101
User 102 -------- Profile 102
User 103 -------- (chưa có profile)
~~~

Bảng `user_profiles` có `user_id` là PK/FK và `NOT NULL`, nên **mọi hồ sơ phải tham chiếu một user**. Nhưng hệ thống vẫn có thể tạo user trước, hoàn thiện hồ sơ sau. `optional=false` đặt trên `UserProfile.user` đúng với điều kiện phụ thuộc đó.

Ngược lại, đặt `optional=false` tại phía `AppUser.profile` chỉ thể hiện kỳ vọng ở cấp mapping/object model và có thể ảnh hưởng behavior của provider; **không tự làm database bảo đảm mỗi user luôn có profile**, vì FK được khai báo theo chiều profile → user. Để cưỡng chế có profile cho mọi user ngay từ đầu, cần thiết kế nghiệp vụ, transaction hoặc ràng buộc bổ sung thích hợp, khó thực hiện bằng một FK thông thường từ child.

**Ràng buộc tối đa một** được PRIMARY KEY của child bảo đảm. **Ràng buộc tối thiểu một** ở chiều user → profile là vấn đề khác, không thể suy ra chỉ từ tên “one-to-one”.

## 9. Hiểu đúng @MapsId và derived identity

`@MapsId` là cơ chế JPA cho **derived identity**: định danh của một entity được suy ra từ quan hệ tới entity khác.

Tại thời điểm tạo:

~~~java
AppUser user = new AppUser("new@example.test");
UserProfile profile = new UserProfile("New", null);
user.attachProfile(profile);

// Trước khi JPA cấp khóa, cả user.id và profile.id
// có thể chưa có giá trị.
~~~

Sau khi persist/flush với provider tương thích:

~~~text
AppUser.id = 505
    |
    +--> UserProfile.user -> AppUser#505
    |
    +--> UserProfile.id = 505

SQL:
app_users.id         = 505 (PK)
user_profiles.user_id = 505 (PK và FK)
~~~

Một số lưu ý:

- `@MapsId` không phải một chiến lược `@GeneratedValue` mới.
- Provider vẫn dùng chiến lược sinh ID được khai báo trên **AppUser**.
- `UserProfile` mượn ID đó để làm khóa của chính nó.
- Chỉ lưu một quan hệ Java đủ để xác định nguồn ID; không cần tạo generator thứ hai.
- Giá trị khóa sau khi tạo cần ổn định trong vòng đời managed entity.
- `@MapsId` không tạo ràng buộc PK/FK trong một database đã có schema nếu ứng dụng không dùng schema generation; cần migration thực tế.

### 9.1. Khi parent dùng khóa tự cấp

Shared PK không bắt buộc parent phải có `IDENTITY`. Nếu ứng dụng cấp ID trước khi persist:

~~~java
@Entity
public class AppUser {

    @Id
    private java.util.UUID id;

    protected AppUser() {
    }

    public AppUser(java.util.UUID id) {
        this.id = id;
    }

    public java.util.UUID getId() {
        return id;
    }
}
~~~

Ở phía child, ID và cột FK phải có kiểu tương thích:

~~~java
@Id
@Column(name = "user_id")
private java.util.UUID id;

@MapsId
@OneToOne(optional = false)
@JoinColumn(name = "user_id", referencedColumnName = "id")
private AppUser user;
~~~

Đây là **biến thể về kiểu khóa**. Nếu triển khai biến thể UUID này, toàn bộ entity/schema và các constructor phải được điều chỉnh đồng bộ, không trộn với định nghĩa `Long id` của ví dụ chính.

Điều kiện cơ bản vẫn là: **PK của child và PK được tham chiếu của parent phải tương thích về kiểu và giá trị**.

### 9.2. Khóa ghép với @MapsId

Trong mô hình đa tenant, khóa của user có thể là một kiểu ghép:

~~~java
@Embeddable
public class UserId implements java.io.Serializable {
    private String tenantCode;
    private Long userNumber;

    protected UserId() {
    }

    // Constructor, getters, equals và hashCode tương ứng.
}
~~~

Nếu `AppUser` có:

~~~java
@EmbeddedId
private UserId id;
~~~

thì `UserProfile` có thể dùng cùng kiểu khóa:

~~~java
@EmbeddedId
private UserId id;

@MapsId
@OneToOne(optional = false)
@JoinColumns({
    @JoinColumn(
        name = "tenant_code",
        referencedColumnName = "tenant_code"
    ),
    @JoinColumn(
        name = "user_number",
        referencedColumnName = "user_number"
    )
})
private AppUser user;
~~~

Đoạn code trên là **minh họa một biến thể**: các cột khóa của `UserId` cần được ánh xạ tường minh và nhất quán ở cả hai entity, đồng thời bảng phải có PK/FK ghép đúng cặp cột. Khi **toàn bộ embedded ID của profile** được dẫn xuất từ parent, `@MapsId` không cần chỉ ra tên thành phần.

Trái lại, khi child có composite ID gồm **một phần từ parent, một phần riêng**, có thể dùng `@MapsId("tenThanhPhan")` để chỉ định thành phần ID nào do association cung cấp. Đó là thiết kế khóa ghép phụ thuộc, khác với trường hợp hai bảng có **toàn bộ khóa chính giống nhau** đang học.

## 10. Phân biệt @MapsId với @PrimaryKeyJoinColumn

Trong một số code JPA/Hibernate cũ, shared primary key có thể được mô tả bằng `@PrimaryKeyJoinColumn`:

~~~java
@Entity
@Table(name = "user_profiles")
public class LegacyProfile {

    @Id
    @Column(name = "user_id")
    private Long id;

    @OneToOne(optional = false)
    @PrimaryKeyJoinColumn(
        name = "user_id",
        referencedColumnName = "id"
    )
    private AppUser user;

    // Constructor/getters, cách đồng bộ id cần tự quản lý...
}
~~~

`@PrimaryKeyJoinColumn` diễn tả phép nối sử dụng cột khóa chính; **nó không tự mang ý nghĩa sao chép định danh của parent sang trường `id` giống `@MapsId`** trong mọi trường hợp. Nếu chọn cách cấu hình cũ, ứng dụng thường phải gán và đồng bộ ID của child theo ID của parent, dễ gặp khó khăn khi parent sử dụng `IDENTITY` và chưa có khóa trước khi insert.

Đối với derived identity của shared PK, `@MapsId` thường cho biểu đạt rõ hơn:

~~~java
@Id
private Long id;

@MapsId
@OneToOne(optional = false)
@JoinColumn(name = "user_id")
private AppUser user;
~~~

Hai phong cách đều liên quan đến quan hệ qua PK nhưng không nên trộn các cấu hình chỉ vì chúng cùng nhắc tới primary key. Chọn một chiến lược mapping nhất quán và kiểm tra schema phù hợp với nó.

## 11. Cách truy vấn và tính năng lazy loading

### 11.1. Truy vấn từ child sang parent

~~~java
UserProfile profile = em.find(UserProfile.class, 101L);
AppUser user = profile == null ? null : profile.getUser();
~~~

`UserProfile.user` là phía owning có khóa FK chính là PK, vì thế provider đã biết giá trị ID của user. Tuy nhiên, thời điểm nó cần thực hiện SQL để tải object user tùy cách fetch.

### 11.2. Truy vấn từ parent sang child

~~~java
AppUser user = em.find(AppUser.class, 101L);
UserProfile profile =
    user == null ? null : user.getProfile();
~~~

Với quan hệ một-một phía inverse, nếu không phải mọi user đều có profile, provider có thể cần xác định **có hay không** dòng profile. Ngay cả khi khai báo `fetch = FetchType.LAZY`, hành vi thực tế còn phụ thuộc provider và bytecode enhancement.

Khi cần profile trong một màn hình cụ thể, có thể dùng:

~~~jpql
SELECT u
FROM AppUser u
LEFT JOIN FETCH u.profile
WHERE u.id = :id
~~~

Khi chỉ cần một vài cột, dùng DTO projection để giảm ràng buộc vào lifecycle của entity. Không dựa vào việc shared PK tự động loại mọi trường hợp N+1 queries.

### 11.3. First-level cache không biến hai entity thành một

Cả `AppUser#101` và `UserProfile#101` đều được lưu trong persistence context theo **entity class + primary key**. Một giá trị số `101` trùng nhau không làm JPA trả về cùng một object ở cả hai loại.

Nếu ứng dụng gọi lặp `em.find(UserProfile.class, 101L)` trong cùng persistence context, provider có thể trả lại cùng managed instance của **UserProfile** mà không cần query lại DB. Tính chất này tách biệt với việc `AppUser` và `UserProfile` chia sẻ giá trị ID.

## 12. Transaction và thứ tự thao tác khi cập nhật

Giả sử một user đã có profile ID `101`. Cập nhật tên hiển thị:

~~~java
em.getTransaction().begin();

UserProfile profile = em.find(UserProfile.class, 101L);
if (profile == null) {
    throw new IllegalArgumentException("Profile not found");
}
profile.changeDisplayName("An Nguyen");

em.getTransaction().commit();
~~~

Để hỗ trợ đoạn này, thêm phương thức nghiệp vụ vào `UserProfile`:

~~~java
public void changeDisplayName(String newDisplayName) {
    if (newDisplayName == null || newDisplayName.isBlank()) {
        throw new IllegalArgumentException(
            "Display name must not be blank");
    }
    this.displayName = newDisplayName;
}
~~~

Trong transaction, JPA theo dõi thay đổi trên managed `UserProfile` và có thể thực hiện `UPDATE user_profiles ... WHERE user_id = 101` khi flush/commit.

**Không đổi `profile.user` sang một user khác** để “chuyển hồ sơ” bởi `profile.id` sẽ phải đổi theo, mà JPA không thiết kế cập nhật primary key của một managed entity như sửa một trường thông thường. Thiết kế nghiệp vụ phù hợp hơn là tạo profile mới theo owner mới và xóa/cập nhật profile cũ theo quy tắc toàn vẹn.

### 12.1. Tạo profile sau khi user đã tồn tại

Một account có thể được tạo trước, chưa có hồ sơ. Sau đó ứng dụng thêm profile trong một transaction:

~~~java
em.getTransaction().begin();

AppUser existing = em.find(AppUser.class, 101L);
if (existing == null) {
    throw new IllegalArgumentException("User not found");
}
if (em.find(UserProfile.class, existing.getId()) != null) {
    throw new IllegalStateException("Profile already exists");
}

UserProfile profile = new UserProfile("An", null);
existing.attachProfile(profile);
em.persist(profile);

em.getTransaction().commit();
~~~

Ở đây, `em.persist(profile)` là thao tác trực tiếp để bảo đảm profile mới được đưa vào context. `@MapsId` cho phép provider sử dụng ID của `existing` để cấp `profile.id`.

Nếu code cũng dùng helper `attachProfile` và cascade PERSIST như ví dụ chính, không nên mặc định rằng việc chỉ gắn thêm child vào một parent **đã managed từ trước** sẽ luôn tự được cascade persist ngay như thao tác `em.persist(parent)` trên entity mới. Persist child một cách tường minh làm ranh giới tạo dữ liệu dễ hiểu.

Để chống hai transaction đồng thời cùng thêm profile, constraint `PRIMARY KEY(user_id)` là lớp bảo vệ cuối cùng. Kiểm tra `find(...) != null` giúp báo lỗi sớm nhưng không thay thế ràng buộc database trong trường hợp race condition.

## 13. Kiểm tra schema và ràng buộc khi triển khai

Một số quy tắc có thể được triển khai ở cả Java và SQL, nhưng chức năng của hai tầng không giống nhau:

| Quy tắc | JPA | Database |
| --- | --- | --- |
| User có ID riêng | `@Id`, `@GeneratedValue` trên AppUser | `app_users.id PRIMARY KEY` |
| Profile dùng ID của user | `@Id` + `@MapsId` trên UserProfile | `user_profiles.user_id PRIMARY KEY` |
| Profile tham chiếu user | `@OneToOne(optional=false)` + `@JoinColumn` | `FOREIGN KEY (user_id) REFERENCES app_users(id)` |
| Không có hai profile cùng user | Ánh xạ one-to-one | PRIMARY KEY của `user_profiles.user_id` bảo đảm unique |
| User có thể chưa có profile | Inverse association có thể null | Không có child row tương ứng |
| Xóa user khi đang có profile | Cần thao tác/cascade thích hợp | FK có thể chặn nếu chưa xóa child |
| Cập nhật thông tin profile | Dirty checking của managed entity | UPDATE hàng có `user_id` tương ứng |

JPA annotation **không tự sửa một schema đã tồn tại** trừ khi hệ thống có cấu hình schema generation thích hợp. Khi dùng migration tool như Flyway hoặc Liquibase, cần tạo PK/FK và tên cột thật nhất quán với annotation. Với môi trường production, quản lý thay đổi schema bằng migration thường dễ kiểm soát hơn việc để ORM thay đổi tự động không có kế hoạch.

### 13.1. Migration từ khóa ngoại riêng sang shared primary key

Giả sử bảng hiện hữu:

~~~sql
CREATE TABLE user_profiles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL UNIQUE,
    display_name VARCHAR(120) NOT NULL,
    FOREIGN KEY (user_id) REFERENCES app_users(id)
);
~~~

Nếu muốn chuyển sang shared PK, **không chỉ đổi annotation Java**. Cần xem:

1. Có dữ liệu profile nào chứa `user_id` null hoặc tham chiếu user không tồn tại không?
2. Có bảng khác đang tham chiếu `user_profiles.id` cũ không?
3. Có dữ liệu trùng `user_id` chưa được unique constraint bảo vệ không?
4. API/client có phụ thuộc vào `profile.id` độc lập trước đây không?
5. Việc đổi primary key ảnh hưởng index, FK, audit table và các event lưu ID như thế nào?

Mô hình đích là `user_profiles.user_id` có PRIMARY KEY và FOREIGN KEY tới `app_users.id`. Để migration an toàn, trước hết phải chuyển hoặc cập nhật tất cả liên kết đang dùng profile ID cũ, rồi mới bỏ cột ID cũ và chuyển ràng buộc. Thao tác đổi primary key cần kế hoạch theo database, dung lượng dữ liệu và khả năng downtime, không thể xem như một lệnh tự động vô hại.

## 14. Những lỗi thường gặp

| Dấu hiệu | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Profile được tạo với ID khác user | Profile đang có generator ID riêng | Dùng `@MapsId`, bỏ `@GeneratedValue` của child |
| Lỗi `null value in column user_id` | Chưa gán `profile.user` ở owning side | Dùng helper thiết lập hai phía trước persist |
| Lỗi duplicate key trên `user_profiles.user_id` | Đã có profile cho user đó | Kiểm tra quy tắc nghiệp vụ và constraint PK |
| Lỗi foreign key khi persist profile | Parent chưa tồn tại hoặc chưa được persist đúng thứ tự | Persist parent trước hoặc cascade persist phù hợp |
| Lỗi foreign key khi xóa user | Profile vẫn tham chiếu user | Xóa child trước hoặc dùng cascade/remove policy có chủ đích |
| `mappedBy` không hoạt động | Nhầm tên cột `user_id` với tên field `user` | Viết `mappedBy = "user"` |
| ORM tạo hai cột `id` và `user_id` ở profile | Mapping PK/FK không thống nhất | Khai báo `@Id` và `@JoinColumn` cùng ý nghĩa cột, dùng `@MapsId` đúng phía |
| `user.getProfile()` là null sau khi gắn child | Chỉ gán phía owning hoặc phía inverse | Duy trì nhất quán hai phía bằng helper |
| Lấy profile của user chưa có profile trả null | Quan hệ là 1 → 0..1 | Xử lý thiếu profile như tình huống hợp lệ nếu nghiệp vụ cho phép |
| `LAZY` nhưng vẫn có SQL bổ sung | Provider cần xác định child tồn tại, hoặc chưa có enhancement | Đánh giá fetch join/projection và cấu hình provider |
| Đổi `profile.user` gây lỗi định danh | Shared PK khiến đổi owner tương đương đổi PK | Không reparent managed profile; thiết kế lại thao tác |
| Schema khác với annotation | Chưa chạy migration hoặc đang trỏ nhầm schema | Kiểm tra table, PK, FK, column và cấu hình persistence unit |
| Hai user tạo profile cùng lúc gây race | Kiểm tra tồn tại tại ứng dụng không khóa được cạnh tranh | Dùng ràng buộc PRIMARY KEY/unique và xử lý lỗi giao dịch |

## 15. Khi nào nên chọn shared primary key?

**Nên cân nhắc shared PK** khi:

- Entity phụ là **phần mở rộng thông tin 1–1** của entity chính, ví dụ tài khoản và hồ sơ, đơn hàng và metadata đặc thù, hợp đồng và thông số bổ sung.
- Entity phụ không cần ID độc lập và không cần chuyển sang owner khác.
- Việc child phụ thuộc vào parent là một invariant ổn định lâu dài.
- Muốn schema ràng buộc một-một gọn: một cột vừa PK vừa FK.

**Cân nhắc khóa ngoại riêng** khi:

- Child có định danh nghiệp vụ riêng được API hoặc các bảng khác tham chiếu.
- Child có thể được chuyển cho owner khác mà không phải tạo entity mới.
- Child cần có vòng đời độc lập với owner.
- Hệ thống đã có nhiều liên kết tới khóa chính riêng của child và chi phí migration lớn.

Nếu hai đối tượng không có lý do lưu riêng bảng và vòng đời riêng, đôi khi **`@Embedded`** hoặc nhóm cột trong cùng bảng là thiết kế phù hợp hơn. `@Embedded` dành cho **value object không có identity riêng**, còn `@OneToOne @MapsId` vẫn biểu diễn **hai entity có bảng và persistence identity riêng**, dù trùng giá trị khóa chính.

## 16. Câu hỏi thực hành

### Bài 1. Vì sao profile không có @GeneratedValue?

Có hai bảng:

~~~text
app_users.id = 10
user_profiles.user_id = 10
~~~

**Trả lời:** User được cấp ID theo chiến lược riêng; `UserProfile` phải nhận ID đó nhờ `@MapsId`. Nếu profile tự sinh ID khác, không còn bảo đảm PK của profile đúng bằng PK của user.

### Bài 2. Ai sở hữu FK?

~~~java
// AppUser
@OneToOne(mappedBy = "user")
private UserProfile profile;

// UserProfile
@MapsId
@OneToOne
@JoinColumn(name = "user_id")
private AppUser user;
~~~

**Trả lời:** `UserProfile.user` là owning side, vì FK nằm ở bảng `user_profiles`. `AppUser.profile` là inverse side, dùng `mappedBy` để trỏ về field owning đó.

### Bài 3. Có thể tồn tại user không có profile?

**Trả lời:** Có, trong schema của bài. PK/FK ở bảng profile chỉ yêu cầu **profile phải thuộc một user tồn tại**. Nó không yêu cầu mọi user đều có profile. Ở Java, `user.getProfile()` có thể null.

### Bài 4. Đã biết user ID thì tìm profile bằng cách nào?

~~~java
UserProfile profile = em.find(UserProfile.class, userId);
~~~

**Trả lời:** Đúng, vì `UserProfile.id` bằng `AppUser.id`. Cần dùng đúng loại entity `UserProfile.class` để JPA tra cứu trong bảng profile.

### Bài 5. Mọi one-to-one có thể dùng shared PK?

**Trả lời:** Không phải mọi trường hợp đều phù hợp. Shared PK ràng buộc identity child với identity parent. Nếu child cần ID độc lập, có thể chuyển owner hoặc có lifecycle riêng, dùng one-to-one với khóa ngoại riêng và ràng buộc UNIQUE thường linh hoạt hơn.

### Bài 6. Xóa user có tự xóa profile?

**Trả lời:** Không tự động chỉ vì có `@MapsId`. Cần cascade remove/orphan removal được cấu hình phù hợp, thao tác xóa child rõ ràng hoặc chính sách database như `ON DELETE CASCADE`. Nếu không, FOREIGN KEY có thể chặn việc xóa user khi child còn tồn tại.

### Bài 7. Chỉ thêm @PrimaryKeyJoinColumn có tự đồng bộ ID?

**Trả lời:** Không được xem `@PrimaryKeyJoinColumn` như công cụ sinh/đồng bộ ID child theo parent. Với derived identity chuẩn, `@MapsId` biểu diễn việc lấy ID từ association rõ ràng hơn.

### Bài 8. Cần cập nhật cả hai phía của quan hệ hai chiều?

**Trả lời:** Có. Khi tạo, `profile.user` phải trỏ về user để owning side có cơ sở ánh xạ FK. `user.profile` nên đồng thời trỏ về profile để object graph Java nhất quán. Helper `attachProfile(...)` giúp thực hiện cả hai.

## 17. Ghi nhớ

- **Shared primary key one-to-one** dùng một cột của bảng child làm **vừa PRIMARY KEY, vừa FOREIGN KEY** tới parent.
- Với JPA, **`@Id` + `@MapsId` + `@OneToOne` + `@JoinColumn`** ở child là cách chuẩn và rõ để mô hình hóa định danh phụ thuộc.
- **Không sinh khóa độc lập cho child**; child dùng giá trị ID của parent.
- Phía child có `@JoinColumn` là **owning side**. Nếu quan hệ hai chiều, phía parent có `mappedBy` và nên dùng helper để đồng bộ hai tham chiếu.
- Ràng buộc PK của child bảo đảm **tối đa một** profile trên một user; nó **không** tự buộc mọi user phải có profile.
- Cascade và orphan removal là lựa chọn **vòng đời** riêng; shared PK không tự động xóa child khi xóa parent.
- Shared PK là lựa chọn phù hợp khi child là phần mở rộng 1–1 và **định danh luôn gắn với parent**. Khi cần ID hoặc vòng đời độc lập, hãy cân nhắc one-to-one với FK riêng.

Cách hình dung cốt lõi: **`AppUser#101` và `UserProfile#101` là hai entity khác nhau, nhưng profile “mượn” chính khóa `101` của user làm khóa của mình**. `@MapsId` khai báo sự phụ thuộc đó ở tầng JPA, còn **PRIMARY KEY + FOREIGN KEY trên cùng cột** bảo vệ nó ở tầng cơ sở dữ liệu.
