# Phân biệt tập hợp entity và tập hợp giá trị trong JPA

Trong mô hình hướng đối tượng, một entity thường chứa các tập hợp như `List`, `Set` hoặc `Map`. Nhìn ở phía Java, hai khai báo sau đều là tập hợp:

```java
private List<Task> tasks;
private Set<String> tags;
```

Nhưng khi lưu vào cơ sở dữ liệu bằng **Jakarta Persistence (JPA)**, chúng có thể biểu diễn **hai mô hình hoàn toàn khác nhau**:

- **Tập hợp entity (*entity collection*)** chứa các đối tượng là `@Entity`. Mỗi phần tử có **định danh entity** riêng, được JPA quản lý qua persistence context. Các ánh xạ thường gặp là `@OneToMany` và `@ManyToMany`.
- **Tập hợp giá trị (*value collection*)** chứa các giá trị cơ bản như `String`, `Integer`, `Enum` hoặc đối tượng thuộc kiểu `@Embeddable`. Các phần tử **không có định danh entity độc lập**; chúng là một phần trạng thái của entity sở hữu. Annotation tiêu biểu là **`@ElementCollection`**.

Sự khác biệt không nằm ở việc Java dùng `List` hay `Set`, mà nằm ở **bản chất của phần tử và mô hình persistence**. Một `List<Task>` có thể là tập hợp entity, trong khi `List<Milestone>` có thể là tập hợp giá trị nếu `Milestone` là `@Embeddable`. Cùng một Java collection interface không quyết định annotation JPA.

Bài học này giải thích cách ánh xạ, định danh, vòng đời, cập nhật, xóa, truy vấn, fetching, ordering và ánh xạ `Map` của hai loại tập hợp, cùng cách chọn mô hình thích hợp.

## 1. Entity và giá trị khác nhau về danh tính

Hãy xem một ứng dụng quản lý dự án. Một `Project` chứa những nhiệm vụ có ID riêng, các nhãn (*tag*) và các mốc thời gian:

```text
Project#10 "Website mới"
    |
    +-- tasks: List<Task>
    |      +-- Task#501 "Thiết kế giao diện"
    |      +-- Task#502 "Tích hợp thanh toán"
    |
    +-- tags: Set<String>
    |      +-- "java"
    |      +-- "backend"
    |
    +-- milestones: List<Milestone>
           +-- ("MVP", 2027-01-10)
           +-- ("Release", 2027-02-20)
```

Ở đây:

- `Task#501` có một **khóa chính** và có thể được truy vấn độc lập theo ID; khi title đổi, đó vẫn có thể là cùng một `Task#501`.
- Chuỗi `"java"` trong `tags` không phải một entity. Nó là một **giá trị thuộc tập hợp** của `Project#10`.
- `Milestone("MVP", date)` là một nhóm thuộc tính; nếu dùng `@Embeddable`, nó không có khóa chính riêng. Hai mốc có cùng các trường có thể được coi là cùng giá trị theo thiết kế lớp, nhưng JPA không cấp cho từng mốc một định danh entity.

So sánh khái niệm:

| Đặc điểm | Phần tử của tập hợp entity | Phần tử của tập hợp giá trị |
| --- | --- | --- |
| Kiểu của phần tử | `@Entity` | Kiểu cơ bản hoặc `@Embeddable` |
| Có `@Id` riêng | Có, trên entity đích | Không, với phần tử giá trị |
| Có vòng đời entity độc lập | Có thể có; phụ thuộc quy tắc domain/cascade | Không; gắn với entity sở hữu |
| `EntityManager.find(ElementType.class, id)` | Có thể dùng với entity đích | Không thể dùng để tìm một phần tử value như entity |
| Được JPA quản lý độc lập trong persistence context | Có | Không; các giá trị thuộc trạng thái persistent của owner |
| Tên ánh xạ thường gặp | `@OneToMany`, `@ManyToMany` | `@ElementCollection` |
| Cần cascade để `persist` entity con mới cùng cha | Thường cần `CascadeType.PERSIST` hoặc gọi `persist` riêng | Không khai báo cascade JPA cho các phần tử value |
| Gỡ phần tử khỏi tập hợp | Tùy quan hệ: có thể chỉ gỡ liên kết hoặc xóa entity nhờ `orphanRemoval` | Thay đổi tập hợp giá trị được đồng bộ vào lưu trữ của owner |
| Có thể được nhiều owner cùng tham chiếu | Có thể, tùy quan hệ và domain | Mỗi phần tử value thuộc trạng thái owner; không có entity identity để chia sẻ |

Cần tránh một nhầm lẫn: **Entity có định danh riêng không có nghĩa nó phải sống độc lập về nghiệp vụ**. Một `Task` vẫn có thể là entity có `@Id` nhưng bị xóa cùng `Project` nếu domain xem task thuộc vòng đời của project. Ngược lại, giá trị `String` giống nhau có thể xuất hiện trong nhiều tập hợp, nhưng đó là các giá trị bằng nhau chứ không phải cùng một entity được tham chiếu.

## 2. Tập hợp entity: @OneToMany và @ManyToMany

Một tập hợp entity biểu diễn **association giữa entity này với các entity khác**. Phần tử phải được ánh xạ bằng `@Entity` và có primary key phù hợp.

Ví dụ `Project` có nhiều `Task`, mỗi task thuộc một project:

```text
Project (1) ----------------- (*) Task
    id                             id
    name                           title
    tasks                          project_id
```

SQL có thể biểu diễn bằng khóa ngoại trong bảng `tasks`:

```sql
CREATE TABLE projects (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE tasks (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id BIGINT NOT NULL REFERENCES projects(id),
    title VARCHAR(200) NOT NULL
);
```

Mỗi dòng của `tasks` là một **entity có ID riêng**. Cột `project_id` biểu diễn mối liên hệ đến project.

### 2.1. Entity Task

```java
package com.example.project;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "tasks")
public class Task {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 200)
    private String title;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "project_id", nullable = false)
    private Project project;

    protected Task() {
    }

    public Task(String title) {
        this.title = title;
    }

    void assignProject(Project project) {
        this.project = project;
    }

    public Long getId() {
        return id;
    }

    public String getTitle() {
        return title;
    }

    public Project getProject() {
        return project;
    }

    public void rename(String newTitle) {
        this.title = newTitle;
    }
}
```

`Task` có `@Id`. Sau khi lưu, một task được nhận diện bằng ID ngay cả khi `title` thay đổi. Quan hệ `Task.project` là phía sở hữu khóa ngoại `project_id` trong mapping hai chiều đang dùng.

### 2.2. Tập hợp Task trong Project

```java
import java.util.ArrayList;
import java.util.List;
import jakarta.persistence.CascadeType;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;

@Entity
public class Project {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @OneToMany(
        mappedBy = "project",
        cascade = CascadeType.ALL,
        orphanRemoval = true
    )
    private List<Task> tasks = new ArrayList<>();

    protected Project() {
    }

    public Project(String name) {
        this.name = name;
    }

    public void addTask(Task task) {
        tasks.add(task);
        task.assignProject(this);
    }

    public void removeTask(Task task) {
        if (tasks.remove(task)) {
            task.assignProject(null);
        }
    }

    public List<Task> getTasks() {
        return tasks;
    }

    public Long getId() {
        return id;
    }
}
```

Đoạn này là **phiên bản đơn giản chỉ chứa quan hệ entity**; các mục sau sẽ bổ sung những tập hợp giá trị vào cùng ý tưởng Project.

`mappedBy = "project"` chỉ ra `Project.tasks` là phía không sở hữu, còn `Task.project` điều khiển khóa ngoại. Hai phương thức helper cập nhật cả hai phía association. Lưu ý `removeTask()` phù hợp với **mô hình task thuộc vòng đời project và `orphanRemoval = true`**; nếu muốn chuyển task giữa hai project mà giữ ID, cần thiết kế chính sách orphan removal khác.

`CascadeType.ALL` lan truyền các thao tác JPA (`PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, `DETACH`) từ Project sang Task. Điều đó có thể thích hợp nếu toàn bộ vòng đời Task phụ thuộc Project. **Cascade không có nghĩa Task mất ID hoặc trở thành giá trị nhúng**: nó vẫn là entity riêng, có thể có relation, version và được truy vấn theo ID.

### 2.3. @ManyToMany cũng là tập hợp entity

Giả sử một `Student` học nhiều `Course`, và một `Course` có nhiều sinh viên. Cả hai phía đều là entity độc lập, nên có thể ánh xạ:

```java
@ManyToMany
@JoinTable(
    name = "student_courses",
    joinColumns = @JoinColumn(name = "student_id"),
    inverseJoinColumns = @JoinColumn(name = "course_id")
)
private Set<Course> courses = new HashSet<>();
```

Đây là đoạn khai báo bên trong entity `Student`, giả định `Course` cũng là `@Entity`. Database thường có bảng liên kết:

```text
students(id, ...)
courses(id, ...)
student_courses(student_id, course_id)
```

Thêm hoặc gỡ một course khỏi `student.courses` thường tương ứng **thêm/xóa một dòng liên kết**. Nó không có nghĩa course được tạo mới hoặc bị xóa khỏi bảng `courses`. Không nên bật `CascadeType.REMOVE` hoặc `CascadeType.ALL` trên quan hệ nhiều-nhiều chỉ vì muốn xóa liên kết: course có thể được nhiều student khác tham chiếu.

**Kết luận ở phần này:** Một tập hợp entity có thể được lưu qua **khóa ngoại trong bảng con** (`@OneToMany`) hoặc **bảng liên kết** (`@ManyToMany` hoặc một số `@OneToMany`), nhưng phần tử luôn là entity có định danh JPA riêng.

## 3. Tập hợp giá trị: @ElementCollection

`@ElementCollection` dùng để ánh xạ tập hợp của **các giá trị cơ bản** hoặc **embeddable**:

```java
@ElementCollection
private Set<String> tags = new HashSet<>();
```

hoặc:

```java
@ElementCollection
private List<Milestone> milestones = new ArrayList<>();
```

Trong cả hai trường hợp, JPA xem các phần tử là **một phần trạng thái của entity sở hữu**, không phải những entity riêng.

Một `String` không có `@Id`. Một lớp `Milestone` dùng `@Embeddable` cũng không có `@Id` độc lập. Vì thế JPA không quản lý `"java"` hoặc `Milestone("MVP", ...)` như một entity độc lập có thể `find`/`remove` theo primary key.

### 3.1. Tập hợp giá trị cơ bản: Set<String>

Ví dụ khai báo trong `Project`:

```java
import java.util.HashSet;
import java.util.Set;
import jakarta.persistence.CollectionTable;
import jakarta.persistence.Column;
import jakarta.persistence.ElementCollection;
import jakarta.persistence.FetchType;
import jakarta.persistence.JoinColumn;

@ElementCollection(fetch = FetchType.LAZY)
@CollectionTable(
    name = "project_tags",
    joinColumns = @JoinColumn(name = "project_id")
)
@Column(name = "tag", nullable = false, length = 40)
private Set<String> tags = new HashSet<>();
```

`@CollectionTable` xác định bảng lưu các giá trị cùng khóa ngoại đến `Project`. Với mapping trên, bảng có thể được thiết kế như sau:

```sql
CREATE TABLE project_tags (
    project_id BIGINT NOT NULL REFERENCES projects(id),
    tag VARCHAR(40) NOT NULL,
    CONSTRAINT pk_project_tags PRIMARY KEY (project_id, tag)
);
```

Khóa chính `(project_id, tag)` là **ràng buộc schema do ví dụ chủ động chọn** để giữ một tag duy nhất trong mỗi project; không được suy luận rằng JPA luôn tự tạo đúng constraint ấy chỉ vì field dùng `Set<String>`.

Khi project 10 có tags `"java"` và `"backend"`:

| project_id | tag |
| ---: | --- |
| 10 | java |
| 10 | backend |

Không có bảng `tags` với ID riêng, cũng không có một entity `Tag#...`. Mỗi hàng trong `project_tags` chỉ lưu **giá trị gắn với project**.

Thêm phần tử:

```java
Project project = entityManager.find(Project.class, 10L);
project.getTags().add("jpa");
```

Bên trong một transaction và persistence context phù hợp, JPA theo dõi thay đổi collection và đồng bộ vào bảng `project_tags` khi cần. Ứng dụng **không gọi `entityManager.persist("jpa")`** vì `"jpa"` không phải entity.

Gỡ phần tử:

```java
project.getTags().remove("backend");
```

Giá trị bị gỡ khỏi collection của project; provider thực hiện thao tác lưu trữ thích hợp trên collection table. Cách sinh SQL cụ thể có thể là cập nhật theo hàng hoặc sắp xếp lại collection theo chiến lược provider.

### 3.2. Tập hợp giá trị phức hợp: @Embeddable

Một value object có thể gồm nhiều thuộc tính:

```java
package com.example.project;

import java.time.LocalDate;
import jakarta.persistence.Column;
import jakarta.persistence.Embeddable;

@Embeddable
public class Milestone {
    @Column(name = "title", nullable = false, length = 120)
    private String title;

    @Column(name = "target_date")
    private LocalDate targetDate;

    protected Milestone() {
    }

    public Milestone(String title, LocalDate targetDate) {
        this.title = title;
        this.targetDate = targetDate;
    }

    public String getTitle() {
        return title;
    }

    public LocalDate getTargetDate() {
        return targetDate;
    }
}
```

Khác với `Task`, `Milestone` **không phải entity**: nó không có `@Id`, không có EntityManager riêng và không thể được tìm bằng `EntityManager.find(Milestone.class, ...)`.

Bên trong `Project`:

```java
import java.util.ArrayList;
import java.util.List;
import jakarta.persistence.CollectionTable;
import jakarta.persistence.ElementCollection;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.OrderColumn;

@ElementCollection
@CollectionTable(
    name = "project_milestones",
    joinColumns = @JoinColumn(name = "project_id")
)
@OrderColumn(name = "milestone_position")
private List<Milestone> milestones = new ArrayList<>();
```

Schema minh họa:

```sql
CREATE TABLE project_milestones (
    project_id BIGINT NOT NULL REFERENCES projects(id),
    milestone_position INTEGER NOT NULL,
    title VARCHAR(120) NOT NULL,
    target_date DATE,
    CONSTRAINT pk_project_milestones
        PRIMARY KEY (project_id, milestone_position)
);
```

Ở đây `milestone_position` lưu **vị trí trong List**, không phải một `@Id` của lớp `Milestone`. Nếu phần tử được chuyển vị trí, chỉ số có thể thay đổi. Vì thế không nên coi nó như định danh nghiệp vụ bền vững của mốc.

Dữ liệu ví dụ:

| project_id | milestone_position | title | target_date |
| ---: | ---: | --- | --- |
| 10 | 0 | MVP | 2027-01-10 |
| 10 | 1 | Release | 2027-02-20 |

Nếu cần một mốc có **ID bền vững để bình luận, phân quyền, tham chiếu từ entity khác hoặc theo dõi lịch sử độc lập**, nên cân nhắc chuyển `Milestone` thành `@Entity` thay vì chỉ dùng `@Embeddable`.

## 4. Đặt hai loại tập hợp trong cùng một Project

Có thể tổng hợp mapping dưới dạng một entity `Project` vừa chứa entity collection, vừa chứa value collections:

```java
package com.example.project;

import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;
import jakarta.persistence.CascadeType;
import jakarta.persistence.CollectionTable;
import jakarta.persistence.Column;
import jakarta.persistence.ElementCollection;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.OneToMany;
import jakarta.persistence.OrderColumn;
import jakarta.persistence.Table;

@Entity
@Table(name = "projects")
public class Project {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String name;

    // Tập hợp entity: từng Task có ID riêng.
    @OneToMany(
        mappedBy = "project",
        cascade = CascadeType.ALL,
        orphanRemoval = true,
        fetch = FetchType.LAZY
    )
    private List<Task> tasks = new ArrayList<>();

    // Tập hợp giá trị cơ bản: các String.
    @ElementCollection(fetch = FetchType.LAZY)
    @CollectionTable(
        name = "project_tags",
        joinColumns = @JoinColumn(name = "project_id")
    )
    @Column(name = "tag", nullable = false, length = 40)
    private Set<String> tags = new HashSet<>();

    // Tập hợp giá trị nhúng: các Milestone.
    @ElementCollection(fetch = FetchType.LAZY)
    @CollectionTable(
        name = "project_milestones",
        joinColumns = @JoinColumn(name = "project_id")
    )
    @OrderColumn(name = "milestone_position")
    private List<Milestone> milestones = new ArrayList<>();

    protected Project() {
    }

    public Project(String name) {
        this.name = name;
    }

    public void addTask(Task task) {
        tasks.add(task);
        task.assignProject(this);
    }

    public void addTag(String tag) {
        tags.add(tag);
    }

    public void addMilestone(Milestone milestone) {
        milestones.add(milestone);
    }

    public List<Task> getTasks() {
        return tasks;
    }

    public Set<String> getTags() {
        return tags;
    }

    public List<Milestone> getMilestones() {
        return milestones;
    }

    public Long getId() {
        return id;
    }
}
```

Đây là **phiên bản hoàn chỉnh thay thế** cho `Project` tối giản ở mục 2.2, không cần tạo hai lớp `Project` khác nhau trong cùng một ứng dụng.

Cấu trúc bảng tương ứng có thể hình dung:

```text
projects
  id (PK)
  name

tasks
  id (PK)                  <-- mỗi Task có identity riêng
  project_id (FK)
  title

project_tags
  project_id (FK)          <-- tập hợp value thuộc Project
  tag

project_milestones
  project_id (FK)          <-- tập hợp value thuộc Project
  milestone_position
  title
  target_date
```

Nhìn từ SQL, `tasks` và `project_milestones` đều có các hàng liên kết tới `projects`. Nhưng ý nghĩa JPA khác nhau: hàng `tasks` là một **entity** có primary key `id`; hàng `project_milestones` là một **phần lưu trữ của value collection**, không tạo ra entity `Milestone` độc lập.

## 5. Vòng đời: persist, merge và remove khác nhau thế nào?

Một điểm quyết định là **JPA thao tác trên entity hay trên trạng thái giá trị thuộc owner**.

### 5.1. Persist Project có Task mới

```java
Project project = new Project("Website mới");
project.addTask(new Task("Tạo trang đăng nhập"));

entityManager.persist(project);
```

Vì mapping `Project.tasks` sử dụng `cascade = CascadeType.ALL`, trong đó có `PERSIST`, JPA lan truyền persist tới `Task` mới. Nếu không cấu hình cascade PERSIST, cần persist task riêng hoặc có một quy trình quản lý liên kết phù hợp.

`Task` vẫn có `id` riêng, được provider/database cấp khi lưu. Về sau nó có thể được tìm trực tiếp:

```java
Task task = entityManager.find(Task.class, taskId);
```

### 5.2. Persist Project có tags và milestones mới

```java
Project project = new Project("Website mới");

project.addTag("java");
project.addTag("jpa");
project.addMilestone(
    new Milestone("MVP", java.time.LocalDate.of(2027, 1, 10))
);

entityManager.persist(project);
```

Giá trị `String` và `Milestone` được lưu như một phần trạng thái của `Project`. **Không cần, và cũng không có ý nghĩa, gọi `persist` riêng trên từng phần tử của `@ElementCollection`**.

`@ElementCollection` **không có thuộc tính `cascade`**, vì các phần tử không phải entity riêng để nhận `CascadeType.PERSIST` hay `CascadeType.REMOVE`. Provider đồng bộ collection cùng trạng thái persistent của owner.

### 5.3. Khi xóa Project

Trong cấu hình ví dụ:

```java
Project project = entityManager.find(Project.class, projectId);
entityManager.remove(project);
```

Kết quả nghiệp vụ mong đợi:

- Các **giá trị** thuộc `tags` và `milestones` không còn owner; những hàng collection table liên quan phải được xử lý/xóa theo mapping và ràng buộc lưu trữ.
- Các **Task entity** được lan truyền thao tác REMOVE vì `cascade = ALL` và `orphanRemoval = true` trong mapping ví dụ.
- Nếu bỏ cascade REMOVE và orphan removal của `tasks` trong khi database có FK `tasks.project_id NOT NULL`, việc xóa Project có thể vi phạm ràng buộc nếu các Task vẫn còn tham chiếu tới nó.

Không nên cho rằng tất cả entity collection đều tự động xóa phần tử khi owner bị xóa. **Đối với entity, lựa chọn cascade và vòng đời quan hệ rất quan trọng. Đối với value collection, các phần tử là một phần trạng thái của owner và không tồn tại như entity độc lập.**

### 5.4. Gỡ một phần tử khi Project vẫn tồn tại

| Hành động | Với tập hợp entity | Với tập hợp giá trị |
| --- | --- | --- |
| `collection.add(x)` | Có thể tạo association; entity mới cần được persist hoặc cascade thích hợp. | Thêm một giá trị vào trạng thái collection của owner. |
| `collection.remove(x)` | Có thể chỉ gỡ association; nếu `orphanRemoval = true` thì entity con có thể bị xóa. | Bỏ giá trị khỏi collection được lưu; không có entity để gọi remove riêng. |
| Sửa field của `x` | Nếu `x` là entity managed, dirty checking có thể cập nhật hàng của entity ấy. | Nếu `x` là embeddable thuộc collection, thay đổi thuộc trạng thái value collection; provider quyết định cách đồng bộ. |
| `EntityManager.find(X.class, id)` | Dùng được nếu X là entity có định danh. | Không áp dụng cho giá trị cơ bản/embeddable. |
| Đổi owner của `x` | Có thể là thay foreign key/association, nếu domain và orphan removal cho phép. | Không có identity riêng để “chuyển cùng một entity”; giá trị có thể được loại khỏi owner cũ rồi thêm vào owner mới. |

Không nên hiểu “thêm cùng một `Milestone` object Java vào hai list” là hai owner cùng chia sẻ **một entity**. Các giá trị đó thuộc hai tập hợp và được lưu dưới hai khóa ngoại khác nhau; để tránh lỗi mutable shared object, thường nên xem `Milestone` như một value object và **sao chép giá trị** khi dùng ở owner khác nếu có thể bị sửa.

## 6. @ElementCollection không phải @OneToMany viết ngắn

Hai annotation nhìn giống nhau vì đều chứa nhiều phần tử, nhưng không thể thay thế trực tiếp cho nhau:

```java
// Đúng khi TagValue là @Embeddable hoặc kiểu basic.
@ElementCollection
private Set<TagValue> tags;
```

```java
// Đúng khi Tag là @Entity.
@OneToMany
private Set<Tag> tags;
```

Nếu `Tag` đã được khai báo `@Entity`, không nên sử dụng nó như phần tử `@ElementCollection` rồi kỳ vọng provider quản lý `@Id` của từng Tag. Ngược lại, một `String` không phải entity để trở thành target của `@OneToMany`.

### 6.1. Cùng là nhãn nhưng có hai mô hình nghiệp vụ

**Mô hình A — Tag chỉ là một chuỗi trong mỗi Project**

```text
Project#10.tags = {"java", "jpa"}
Project#20.tags = {"java", "testing"}
```

Có thể dùng `@ElementCollection Set<String>`. Giá trị `"java"` xuất hiện ở nhiều project vì các project có các **giá trị bằng nhau**, không phải vì mọi project trỏ đến một entity Tag#7.

**Mô hình B — Tag là đối tượng dùng chung có dữ liệu riêng**

```text
Tag#7  {name="java", description="Ngôn ngữ Java"}
Tag#9  {name="jpa", description="Jakarta Persistence"}

Project#10 -> Tag#7, Tag#9
Project#20 -> Tag#7
```

Nếu Tag có mô tả được quản lý tập trung, quyền chỉnh sửa, lịch sử, thống kê hoặc được nhiều project tham chiếu, có thể dùng entity `Tag` với quan hệ `@ManyToMany` và join table `project_tags` (một schema khác với collection table của `Set<String>`).

Trong mô hình B, đổi tên Tag#7 có thể ảnh hưởng đến tất cả project đang tham chiếu nó vì chúng cùng trỏ đến một entity. Trong mô hình A, mỗi project chỉ lưu chuỗi của riêng mình; đổi `"java"` sang `"java-language"` ở Project#10 không làm thay đổi tags của Project#20.

### 6.2. Không dựa vào số bảng để quyết định

`@ElementCollection` thường có một **collection table** riêng. `@OneToMany` cũng có thể dùng một bảng liên kết hoặc bảng con. Do đó, **có bảng riêng không đủ chứng minh phần tử là entity**. Phân biệt bằng **identity và lifecycle** của phần tử, không chỉ nhìn sơ đồ SQL.

## 7. Cascade và orphanRemoval chỉ áp dụng theo quan hệ entity

Với tập hợp entity, cascade quyết định thao tác JPA nào lan truyền từ owner đến phần tử:

| CascadeType | Khi áp dụng vào tập hợp entity |
| --- | --- |
| `PERSIST` | Persist entity nguồn có thể persist những entity đích mới. |
| `MERGE` | Merge trạng thái của entity nguồn có thể lan truyền tới entity đích. |
| `REMOVE` | Remove nguồn có thể lan truyền remove tới entity đích. |
| `REFRESH` | Refresh nguồn có thể lan truyền tới entity đích. |
| `DETACH` | Detach nguồn có thể lan truyền tới entity đích. |
| `ALL` | Bao gồm mọi loại cascade tiêu chuẩn ở trên. |

`orphanRemoval = true` trên `@OneToMany` hoặc `@OneToOne` có ý nghĩa khi một entity con bị tách khỏi association sở hữu vòng đời chặt. Đừng lạm dụng nó nếu cùng một entity con có thể chuyển giữa các owner mà vẫn giữ ID: việc tách ra có thể khiến JPA lên lịch xóa con, và tái gán orphan không được bảo đảm portable.

Đối với `@ElementCollection`:

```java
@ElementCollection
private Set<String> tags;
```

không có `cascade = ...` và cũng không có `orphanRemoval = ...`. Những phần tử không phải entity con. Xóa một phần tử khỏi collection chỉ là thay đổi trạng thái collection giá trị, được provider phản ánh vào collection table.

**Không nhầm với `ON DELETE CASCADE` ở database**: đó là ràng buộc khóa ngoại ở tầng SQL, không phải `CascadeType.REMOVE` của JPA. Hai cơ chế có thể cùng xuất hiện nhưng không thay thế cách hiểu lifecycle của entity và value.

## 8. Thay đổi một phần tử giá trị khác với cập nhật một entity

Giả sử cần đổi ngày của mốc `"MVP"`:

```java
Project project = entityManager.find(Project.class, projectId);

List<Milestone> milestones = project.getMilestones();

Milestone oldValue = milestones.get(0);
Milestone newValue = new Milestone(
    oldValue.getTitle(),
    java.time.LocalDate.of(2027, 1, 15)
);

milestones.set(0, newValue);
```

Vì `Milestone` là value object, cách **thay thế giá trị** như trên thể hiện rõ rằng phần tử ở vị trí 0 có giá trị mới. Provider sẽ đồng bộ collection theo mapping. Với những embeddable mutable, provider có thể phát hiện thay đổi field trong các tình huống được hỗ trợ, nhưng việc thay thế phần tử thường làm ý định cập nhật rõ ràng hơn, nhất là khi ứng dụng muốn coi value object là bất biến về mặt domain.

So sánh với Task:

```java
Task task = entityManager.find(Task.class, taskId);
task.rename("Hoàn thành giao diện mới");
```

`Task` vẫn là cùng entity `taskId`. JPA có thể cập nhật cột `tasks.title` khi flush, mà không cần xóa Task cũ rồi tạo một Task mới.

Với `@ElementCollection`, SQL đồng bộ có thể thay đổi tùy cấu trúc collection và provider:

- Đối với một collection có khóa nhận diện hàng rõ, provider có thể cập nhật hoặc xóa/chèn phần tử liên quan.
- Với một số bag/list thiếu khóa hàng thuận tiện, provider có thể xóa nhiều hàng thuộc owner rồi chèn lại các giá trị hiện tại.
- Khi list có `@OrderColumn`, thêm/gỡ hoặc di chuyển phần tử có thể khiến nhiều chỉ số vị trí phải cập nhật.

Vì vậy, một **value collection rất lớn và thay đổi thường xuyên từng phần tử** có thể kém thuận lợi hơn một tập hợp entity có primary key riêng, tùy mapping/provider và nhu cầu truy cập. Không nên giả định rằng `collection.set(i, value)` luôn tạo đúng **một câu `UPDATE`**.

## 9. List, Set, Collection và vấn đề bằng nhau

JPA ánh xạ tập hợp dựa trên các Java collection interface, nhưng **lựa chọn `List` hay `Set` không tự xác định phần tử là entity hay value**.

### 9.1. Set<String>: so sánh theo giá trị

```java
Set<String> tags = new HashSet<>();
tags.add("jpa");
tags.add("jpa");

System.out.println(tags.size()); // 1
```

`String` có `equals()`/`hashCode()` theo nội dung, nên `Set<String>` ngăn trùng giá trị trong bộ nhớ. Nhưng để chặn dữ liệu trùng trong database khi có nhiều writer, nên tạo **unique constraint** phù hợp, như `UNIQUE(project_id, tag)`.

### 9.2. Set<Embeddable>: nên xác định value equality

Nếu dùng:

```java
@ElementCollection
private Set<Milestone> milestones = new HashSet<>();
```

thì tính duy nhất trong `HashSet` phụ thuộc `Milestone.equals()` và `hashCode()`. Đối với value object, các phương thức này thường so sánh những thuộc tính mang ý nghĩa định danh giá trị.

Ví dụ lớp giá trị đơn giản:

```java
import java.io.Serializable;
import java.time.LocalDate;
import java.util.Objects;
import jakarta.persistence.Embeddable;

@Embeddable
public class Milestone implements Serializable {
    private String title;
    private LocalDate targetDate;

    protected Milestone() {
    }

    public Milestone(String title, LocalDate targetDate) {
        this.title = title;
        this.targetDate = targetDate;
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) return true;
        if (!(other instanceof Milestone that)) return false;
        return Objects.equals(title, that.title)
            && Objects.equals(targetDate, that.targetDate);
    }

    @Override
    public int hashCode() {
        return Objects.hash(title, targetDate);
    }
}
```

Đây là **phiên bản minh họa riêng của lớp `Milestone`** dành cho `Set`; không đưa trùng class này và lớp `Milestone` ở mục 3 vào cùng một package. Với một `Set`, tránh thay đổi thuộc tính được dùng trong `hashCode()` khi object đang nằm trong tập hợp, vì `HashSet` có thể không tìm lại được phần tử bằng cách tra cứu thông thường. Khi thay đổi giá trị, nên remove giá trị cũ rồi add một instance mới.

### 9.3. Set<Entity>: không sao chép máy móc equals của Embeddable

Với `Set<Task>`, phần tử có **entity identity**. Cách viết `equals()`/`hashCode()` cần xét khóa chính sinh tự động, proxy và trạng thái new/managed/detached; chỉ so sánh mọi field nghiệp vụ có thể khiến một entity bị xem là “khác object” sau khi cập nhật tiêu đề.

Không nên kết luận rằng mọi `@Entity` phải có `equals()`/`hashCode()` so sánh toàn bộ field như value object. Trong thực tế cần quy ước nhất quán cho entity equality, nhất là khi dùng `Set` và các khóa do database sinh.

### 9.4. List có cho phép trùng phần tử không?

`List` có thể giữ hai phần tử bằng nhau, trong khi `Set` dùng equality để ngăn trùng. Nhưng trong JPA, cách lưu hai giá trị trùng nhau còn phụ thuộc cấu trúc collection table và khóa của hàng. Nếu nghiệp vụ cần giữ **hai lần xuất hiện giống hệt nhau và thứ tự ổn định**, có thể sử dụng `List` với `@OrderColumn` và schema hỗ trợ vị trí.

Ví dụ:

```java
@ElementCollection
@CollectionTable(
    name = "project_tags_in_order",
    joinColumns = @JoinColumn(name = "project_id")
)
@OrderColumn(name = "position_idx")
@Column(name = "tag")
private List<String> tagsInOrder = new ArrayList<>();
```

Hai giá trị `"jpa"` tại vị trí 0 và 1 có thể được lưu bằng hai hàng riêng có chỉ số khác nhau. Cách này khác với `Set<String>` chỉ biểu diễn một giá trị `"jpa"` trong tập hợp.

## 10. @OrderColumn và @OrderBy không biến giá trị thành entity

Cấu trúc `List` thường cần thứ tự. Trong JPA có hai cơ chế dễ nhầm:

- **`@OrderColumn`**: dùng một cột thứ tự để JPA lưu vị trí phần tử trong `List`. Khi thêm, xóa hoặc sắp xếp lại list, provider quản lý những chỉ số tương ứng.
- **`@OrderBy`**: xác định thứ tự đọc dựa trên thuộc tính/cột được sắp xếp; nó không mặc nhiên tạo một cột vị trí do JPA duy trì.

Ví dụ value collection:

```java
@ElementCollection
@OrderColumn(name = "milestone_position")
private List<Milestone> milestones = new ArrayList<>();
```

Với `@OrderColumn`, phần tử tại index 0 và 1 có một thứ tự được lưu. Nhưng `milestone_position` **không phải entity ID**; xóa phần tử đầu có thể khiến vị trí của phần tử sau được đánh lại.

Ví dụ tập hợp entity có thứ tự đọc theo title:

```java
@OneToMany(mappedBy = "project")
@OrderBy("title ASC")
private List<Task> tasks = new ArrayList<>();
```

Mục đích là đọc Task theo `title`. Một Task vẫn có ID riêng dù thứ tự hiển thị của nó thay đổi khi đổi title.

**Không nên cho rằng một `List` không khai báo ordering sẽ luôn được tải theo thứ tự đã add trong bộ nhớ.** Cần cấu hình ordering rõ ràng nếu thứ tự là một phần hợp đồng nghiệp vụ.

## 11. Map cũng có thể chứa entity hoặc giá trị

Chương **Tập hợp và Map** còn có một trường hợp quan trọng: bản thân `Map<K, V>` không cho biết value là entity hay kiểu giá trị. Cần xem kiểu `V` và annotation ánh xạ.

### 11.1. Map<String, String> với @ElementCollection

Giả sử mỗi Project có những thuộc tính mở rộng dạng key-value:

```text
project.attributes
  "theme"    -> "dark"
  "priority" -> "high"
```

Có thể ánh xạ:

```java
import java.util.HashMap;
import java.util.Map;
import jakarta.persistence.CollectionTable;
import jakarta.persistence.Column;
import jakarta.persistence.ElementCollection;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.MapKeyColumn;

@ElementCollection
@CollectionTable(
    name = "project_attributes",
    joinColumns = @JoinColumn(name = "project_id")
)
@MapKeyColumn(name = "attribute_name", length = 80)
@Column(name = "attribute_value", length = 300)
private Map<String, String> attributes = new HashMap<>();
```

Schema minh họa:

```sql
CREATE TABLE project_attributes (
    project_id BIGINT NOT NULL REFERENCES projects(id),
    attribute_name VARCHAR(80) NOT NULL,
    attribute_value VARCHAR(300),
    PRIMARY KEY (project_id, attribute_name)
);
```

Mỗi entry có **key** là tên thuộc tính và **value** là chuỗi. Cả key và value đều không phải entity riêng; đây là **Map của các giá trị cơ bản**. Thao tác:

```java
project.getAttributes().put("theme", "dark");
```

là thay đổi trạng thái collection của Project, không tạo một entity `Attribute` được quản lý riêng.

`@MapKeyColumn` biểu diễn cột khóa của map trong collection table. `@Column` ở ví dụ này biểu diễn cột lưu giá trị `String`.

### 11.2. Map<String, Task> với @OneToMany và @MapKey

Nếu mỗi Task có mã `code`, Project có thể tra Task theo mã:

```java
// Trong entity Task:
@Column(name = "code", nullable = false, length = 40)
private String code;
```

Và trong Project, thay cho `List<Task>` ở các ví dụ trên, dùng mapping **thay thế**:

```java
@OneToMany(mappedBy = "project", fetch = FetchType.LAZY)
@MapKey(name = "code")
private Map<String, Task> tasksByCode = new HashMap<>();
```

`@MapKey(name = "code")` yêu cầu JPA dùng **thuộc tính `Task.code`** làm map key khi hình thành Map. Value vẫn là **entity `Task` có `@Id` riêng**, và khóa ngoại `project_id` vẫn do phía `Task.project` điều khiển.

Hai annotation có ý nghĩa khác:

| Annotation | Dùng trong ví dụ | Map key đến từ đâu? |
| --- | --- | --- |
| `@MapKeyColumn(name = "attribute_name")` | `@ElementCollection Map<String,String>` | Cột khóa map được lưu trực tiếp trong collection table. |
| `@MapKey(name = "code")` | `@OneToMany Map<String,Task>` | Giá trị thuộc tính persistent `Task.code` của entity đích. |

Nếu `Task.code` thay đổi sau khi `tasksByCode` đã được tải, key trong `Map` đang ở bộ nhớ **không nhất thiết tự được re-index** theo mã mới ngay lập tức. Nên dùng mã ổn định hoặc viết logic đồng bộ Map rõ ràng, và đặt ràng buộc `UNIQUE(project_id, code)` nếu mã phải duy nhất trong project.

`@MapKeyColumn` và `@MapKey` không phải hai cách viết tương đương trong mọi mapping. Chúng thể hiện nguồn của map key khác nhau; cách dùng phụ thuộc quan hệ và schema.

### 11.3. Map<K, Embeddable> vẫn là value collection

Nếu cần một Map có value là kiểu phức hợp:

```java
@ElementCollection
@CollectionTable(
    name = "project_contacts",
    joinColumns = @JoinColumn(name = "project_id")
)
@MapKeyColumn(name = "contact_role")
private Map<String, ContactInfo> contacts = new HashMap<>();
```

trong đó `ContactInfo` được khai báo `@Embeddable`, thì value vẫn **không có entity ID**. Các thuộc tính của `ContactInfo` được lưu thành những cột trong collection table, còn `contact_role` là map key.

Sử dụng `@OneToMany` nếu `ContactInfo` trở thành một `@Entity` có identity và vòng đời riêng. Việc có key của Map không đồng nghĩa value tự trở thành entity.

## 12. Fetching: cả hai loại tập hợp đều có thể LAZY

Theo JPA, các collection association phổ biến như `@OneToMany` và `@ManyToMany` mặc định sử dụng `LAZY`. `@ElementCollection` cũng có mặc định `FetchType.LAZY`.

Do đó, cả hai khai báo sau đều có thể được provider tải trì hoãn:

```java
@OneToMany(mappedBy = "project", fetch = FetchType.LAZY)
private List<Task> tasks;
```

```java
@ElementCollection(fetch = FetchType.LAZY)
private Set<String> tags;
```

Tuy nhiên, **LAZY là một hint về chiến lược tải**, không phải bảo đảm số câu SQL cụ thể. Provider có thể xử lý khác nhau tùy mapping, cache, batch fetching và phiên bản.

Ví dụ:

```java
Project project = entityManager.find(Project.class, projectId);

String projectName = project.getName();

// Có thể kích hoạt tải các tag nếu collection chưa được khởi tạo:
int numberOfTags = project.getTags().size();

// Có thể kích hoạt tải tập entity Task nếu collection chưa tải:
int numberOfTasks = project.getTasks().size();
```

Hai collection có thể tạo ra những truy vấn khác nhau:

```sql
-- Ví dụ minh họa tải tập hợp giá trị:
SELECT tag
FROM project_tags
WHERE project_id = ?;

-- Ví dụ minh họa tải các entity liên quan:
SELECT id, project_id, title
FROM tasks
WHERE project_id = ?;
```

Cả hai loại collection đều có thể dẫn đến **N+1 query problem** nếu ứng dụng tải hàng loạt Project rồi truy cập từng collection ở mỗi Project.

### 12.1. N+1 với value collection cũng xảy ra

```java
List<Project> projects = entityManager.createQuery(
    "SELECT p FROM Project p",
    Project.class
).getResultList();

for (Project project : projects) {
    System.out.println(project.getTags().size());
}
```

Nếu có 100 Project và chưa có collection nào trong cache, provider có thể thực hiện một truy vấn lấy Project và nhiều truy vấn lấy từng bộ tags. N+1 **không chỉ liên quan đến `@OneToMany` entity**.

Tùy mục đích, có thể:

- Dùng fetch join hoặc entity graph cho một collection cần thiết.
- Sử dụng batch fetching của provider để giảm số lượt SQL.
- Viết truy vấn aggregate/DTO nếu chỉ cần đếm hoặc kiểm tra tồn tại.
- Tránh fetch join nhiều collection lớn cùng lúc do nguy cơ nhân số dòng kết quả.
- Cẩn thận với phân trang khi fetch join collection: giới hạn hàng SQL không nhất thiết bằng số entity cha mong muốn.

### 12.2. Fetch plan không thay thế cascade

`JOIN FETCH`, `@EntityGraph` hoặc `fetch = EAGER` điều chỉnh **cách dữ liệu được tải**. Chúng không thay đổi việc entity Task có được persist/xóa cùng Project hay không. Với `@ElementCollection` cũng không xuất hiện `cascade` chỉ vì eager loading được bật.

### 12.3. Lazy loading sau khi đóng EntityManager

Nếu collection chưa được tải và context đã đóng, việc truy cập có thể thất bại với lỗi lazy initialization tùy provider, ví dụ `LazyInitializationException` của Hibernate:

```java
Project detached;

EntityManager em = factory.createEntityManager();
try {
    detached = em.find(Project.class, projectId);
} finally {
    em.close();
}

// getTags() hoặc getTasks() có thể yêu cầu tải lazy;
// không thể dựa vào context đã đóng để tiếp tục truy vấn.
```

Để phục vụ API, thường nên tải dữ liệu cần thiết trong service transaction rồi trả DTO. Không nên bật EAGER cho mọi collection chỉ để tránh lỗi khi serialization JSON ở tầng web.

## 13. Truy vấn entity collection và value collection

### 13.1. Có thể truy vấn Task độc lập

Vì Task là entity:

```java
Task task = entityManager.find(Task.class, taskId);
```

Hoặc truy vấn tất cả Task thuộc một Project:

```java
List<Task> tasks = entityManager.createQuery(
        "SELECT t FROM Task t " +
        "WHERE t.project.id = :projectId",
        Task.class
    )
    .setParameter("projectId", projectId)
    .getResultList();
```

`Task` có thể là root entity trong JPQL vì nó là `@Entity`.

### 13.2. Value collection phải được truy cập thông qua owner hoặc collection path

Không thể gọi:

```java
// Sai: String không phải entity.
entityManager.find(String.class, "jpa");

// Sai: Milestone là @Embeddable, không phải entity root.
entityManager.find(Milestone.class, milestoneId);
```

Thay vào đó, có thể join vào value collection từ `Project`:

```java
List<Project> projects = entityManager.createQuery(
        "SELECT DISTINCT p FROM Project p " +
        "JOIN p.tags tag " +
        "WHERE tag = :tag",
        Project.class
    )
    .setParameter("tag", "jpa")
    .getResultList();
```

Truy vấn này tìm Project có giá trị `"jpa"` trong tags, chứ không tìm entity `Tag`.

Với embeddable collection, có thể đi qua đường dẫn thuộc tính của value, chẳng hạn:

```java
List<Project> projects = entityManager.createQuery(
        "SELECT DISTINCT p FROM Project p " +
        "JOIN p.milestones milestone " +
        "WHERE milestone.title = :title",
        Project.class
    )
    .setParameter("title", "MVP")
    .getResultList();
```

Chi tiết khả năng dùng nhiều phần tử collection và hình dạng SQL phụ thuộc provider, nhưng về mô hình, đường đi vẫn bắt đầu từ **entity owner**.

### 13.3. Khác nhau về việc sửa một phần tử

Với entity Task, mã có thể tải task riêng theo ID để đổi tiêu đề trong transaction. Với value Milestone, không có một ID entity chuẩn để gửi vào endpoint như `/milestones/{id}`. Nếu ứng dụng cần endpoint cập nhật từng mốc riêng, có các lựa chọn:

- Cập nhật thông qua Project và một key nghiệp vụ/position trong collection, với cơ chế concurrency phù hợp.
- Thiết kế Milestone thành entity có ID riêng nếu cần truy cập/khóa/phân quyền và vòng đời độc lập.
- Xem Milestone chỉ là value object, thay toàn bộ giá trị khi chỉnh sửa.

Không nên dùng một **vị trí trong List** như định danh bền vững khi list có thể bị sắp xếp lại.

## 14. Tính chia sẻ và quan hệ nhiều owner

Một value collection thích hợp khi phần tử **phụ thuộc về ý nghĩa vào owner**. Ví dụ, `"backend"` là một nhãn được lưu trong danh sách tags của từng Project. Hai Project cùng có chuỗi `"backend"` nhưng không có một thực thể `Tag` chung bắt buộc được quản lý tập trung.

Nếu yêu cầu nghiệp vụ là:

- Một tag có tên, mô tả, người tạo và trạng thái riêng.
- Quản trị viên đổi tên tag và mọi Project phải thấy tên mới.
- Một tag được sử dụng bởi nhiều Project.
- Có quyền truy cập, thống kê hoặc khóa riêng cho tag.

thì Tag nên được cân nhắc như **entity độc lập**, có thể qua `@ManyToMany` hoặc một entity liên kết nếu quan hệ có thuộc tính.

Ngược lại, nếu một `ContactInfo` chỉ là bộ `(name, email, phone)` được lưu cho từng Project, không có ID và không được truy cập độc lập, `@ElementCollection` là lựa chọn tự nhiên.

Một `Task` có thể là entity nhưng chỉ được gắn với **một Project**. Khác biệt cốt lõi không phải **số owner**, mà là **Task có identity riêng và JPA quản lý nó như entity**.

## 15. Cân nhắc khóa, uniqueness và constraints ở database

Tập hợp giá trị không có ID entity, nhưng **collection table vẫn cần thiết kế ràng buộc dữ liệu**. Một số lựa chọn:

| Tập hợp | Ràng buộc SQL thường cân nhắc | Mục tiêu |
| --- | --- | --- |
| `Set<String> tags` | `UNIQUE(project_id, tag)` hoặc PK ghép phù hợp | Không lặp tag trong cùng Project ở database. |
| `List<Milestone>` có `@OrderColumn` | `UNIQUE(project_id, milestone_position)` | Mỗi vị trí trong list có một hàng. |
| `Map<String, String> attributes` | `UNIQUE(project_id, attribute_name)` | Không có hai value cho cùng map key trong một Project. |
| `List<Task>` có FK | `PRIMARY KEY(tasks.id)` và FK `project_id` | Mỗi Task có identity riêng và tham chiếu Project hợp lệ. |
| `Set<Course>` many-to-many | `UNIQUE(student_id, course_id)` | Không có liên kết lặp giữa hai entity. |

Các constraint là **quyết định schema có chủ đích**. Việc dùng `Set` ở Java chỉ ngăn thêm phần tử trùng trong một collection đang ở bộ nhớ theo `equals()`/`hashCode()`, không tự bảo vệ dữ liệu mà script hoặc hệ thống khác ghi thẳng vào database.

Với embeddable collection có phần tử chứa nhiều trường nullable, cần xem xét cách database phân biệt các giá trị và cách provider nhận diện hàng khi cập nhật. Nếu một phần tử cần có danh tính riêng để tham chiếu hoặc concurrency control, kiểu entity có khóa chính rõ ràng thường phù hợp hơn.

## 16. Transaction, dirty checking và concurrency

Cả hai loại collection đều là **trạng thái persistent** của owner, nên thao tác ghi phải diễn ra trong transaction phù hợp.

Ví dụ Java SE với `RESOURCE_LOCAL`:

```java
import jakarta.persistence.EntityManager;
import jakarta.persistence.EntityManagerFactory;
import jakarta.persistence.EntityTransaction;

public final class ProjectService {
    private final EntityManagerFactory factory;

    public ProjectService(EntityManagerFactory factory) {
        this.factory = factory;
    }

    public void addTag(long projectId, String tag) {
        EntityManager em = factory.createEntityManager();
        try {
            EntityTransaction tx = em.getTransaction();
            try {
                tx.begin();

                Project project = em.find(Project.class, projectId);
                if (project == null) {
                    throw new IllegalArgumentException(
                        "Project not found: " + projectId
                    );
                }

                project.addTag(tag);

                tx.commit();
            } catch (RuntimeException ex) {
                if (tx.isActive()) {
                    tx.rollback();
                }
                throw ex;
            }
        } finally {
            em.close();
        }
    }
}
```

Ở ví dụ, `Project` đã là managed entity, nên việc thêm tag vào `@ElementCollection` được JPA theo dõi theo quy tắc provider khi flush/commit; không cần `em.merge(project)` chỉ để lưu một managed entity.

Trong Spring, service thường dùng `@Transactional` thay cho `EntityTransaction` thủ công, nhưng ranh giới giao dịch vẫn cần xác định. Nếu sửa một collection trên **detached entity** ngoài persistence context, JPA không tự ghi thay đổi vào database.

### 16.1. Entity con có thể có @Version riêng

Một `Task` entity có thể khai báo:

```java
@Version
private Long version;
```

Khi hai transaction cùng sửa Task, optimistic locking có thể phát hiện cập nhật dựa trên version cũ. Đây là một lợi ích khi phần tử cần **theo dõi đồng thời độc lập**.

Một `Milestone` embeddable trong `@ElementCollection` không có `@Version` riêng như một entity. Có thể dùng `@Version` trên Project hoặc cơ chế transaction/locking thích hợp để bảo vệ tập giá trị, nhưng hành vi tăng version khi thay đổi collection và cách khóa cần được xác nhận với mapping/provider thực tế.

### 16.2. Một giá trị không có identity riêng vẫn có thể cần bảo vệ cập nhật

Hai request cùng sửa `project.attributes` có thể ghi đè nhau nếu xử lý thiếu kiểm soát. Việc không có entity `Attribute` không có nghĩa không cần concurrency control.

Ví dụ, hai giao dịch cùng đọc map rồi một bên cập nhật `"theme"`, bên kia cập nhật `"priority"`. Tùy cách provider đồng bộ bảng giá trị, thao tác đồng thời có thể gây xung đột hoặc mất cập nhật. Thiết kế transaction và version ở owner khi phù hợp là trách nhiệm của ứng dụng.

## 17. Hiệu năng: khi value collection trở nên lớn

`@ElementCollection` thích hợp khi tập giá trị **nhỏ hoặc có quy mô quản lý được**, thuộc vòng đời owner và thường được làm việc cùng owner. Tuy nhiên, nếu chứa hàng chục nghìn giá trị được cập nhật lẻ tẻ thường xuyên, một số vấn đề có thể xuất hiện:

1. **Chi phí tải collection:** truy cập một phần tử có thể dẫn tới tải nhiều phần tử nếu dùng collection LAZY thông thường.
2. **Chi phí đồng bộ:** provider có thể cần xóa/chèn lại nhiều hàng khi không có định danh hàng thuận lợi.
3. **Không có ID riêng:** khó cập nhật một phần tử cụ thể qua API/JPQL như một entity bình thường.
4. **Không có version riêng:** kiểm soát concurrency ở mức từng phần tử không tự có.
5. **Không có vòng đời độc lập:** không thể tìm hoặc phân quyền riêng một phần tử như entity.

Trong những tình huống đó, biến phần tử thành entity có `@Id` có thể giúp xây dựng truy vấn, cập nhật và locking theo từng phần tử. Nhưng **không phải cứ có nhiều phần tử là bắt buộc dùng entity**: quyết định còn phụ thuộc loại dữ liệu, mô hình đọc/ghi, provider, ràng buộc nghiệp vụ và nhu cầu vận hành.

Một cách đánh giá thiết thực là hỏi: “Ứng dụng cần sửa/xem/lưu lịch sử/khóa **phần tử này như một đối tượng độc lập** hay chỉ coi nó là một thuộc tính nhiều giá trị của owner?”

## 18. Những lỗi thường gặp

### Lỗi 1 — Dùng @ElementCollection cho một lớp @Entity

```java
// Task là @Entity, mapping dưới đây không đúng ý nghĩa:
@ElementCollection
private List<Task> tasks;
```

Nếu `Task` có primary key và vòng đời entity, dùng `@OneToMany` hoặc quan hệ thích hợp. `@ElementCollection` dành cho kiểu basic/embeddable.

### Lỗi 2 — Dùng @OneToMany cho List<String>

```java
// String không phải @Entity:
@OneToMany
private List<String> tags;
```

Muốn lưu một tập hợp chuỗi, dùng `@ElementCollection`. Nếu mỗi tag cần ID và metadata riêng, định nghĩa entity `Tag` trước khi ánh xạ quan hệ.

### Lỗi 3 — Nghĩ @ElementCollection cần CascadeType.ALL

```java
@ElementCollection
private List<Milestone> milestones;
```

Không có tham số `cascade` trên `@ElementCollection`. Giá trị thuộc trạng thái owner, nên được persist và đồng bộ theo vòng đời owner.

### Lỗi 4 — Nghĩ @OneToMany mặc định persist mọi entity con

Không. `@OneToMany` không khai báo cascade có mặc định không cascade. Nếu tạo Task mới trong collection, cần `CascadeType.PERSIST` hoặc gọi `persist` rõ ràng trên Task theo mapping và transaction.

### Lỗi 5 — Dùng CascadeType.REMOVE cho entity được chia sẻ

Với `@ManyToMany` giữa Student và Course, xóa Student không nên xóa các Course khác đang sử dụng. Xóa liên kết khác với xóa entity đích.

### Lỗi 6 — Nhầm @OrderColumn là khóa chính của element

`milestone_position` là vị trí trong `List` và có thể thay đổi khi list được sắp xếp lại. Nó không cho `Milestone` một JPA `@Id` bền vững.

### Lỗi 7 — Tin rằng Set tự tạo UNIQUE constraint

`Set` dùng equality trong Java. Dữ liệu database vẫn cần constraint riêng nếu quy tắc tính duy nhất phải được bảo vệ trước nhiều nguồn ghi.

### Lỗi 8 — Nghĩ dữ liệu @ElementCollection luôn nằm trong bảng owner

Tập hợp giá trị thường được lưu vào **collection table**, nối bằng khóa ngoại đến owner. Nó không nhất thiết là một cột JSON hoặc một chuỗi đã nối trong bảng `projects`. Lưu JSON/ARRAY là chiến lược khác cần mapping và hỗ trợ provider/database phù hợp.

### Lỗi 9 — Nhầm LAZY với cascade

`fetch = LAZY` là yêu cầu trì hoãn tải; nó không cấm persist/remove lan truyền trên entity collection. Ngược lại, `CascadeType.ALL` không tự biến association thành EAGER.

### Lỗi 10 — Sửa Map key rồi nghĩ Map tự cập nhật index

Với `@MapKey(name = "code")`, Map key đến từ thuộc tính của entity đích. Thay đổi `Task.code` không nhất thiết khiến một Map đã tải trong bộ nhớ tự chuyển entry sang key mới. Cần thiết kế key ổn định hoặc đồng bộ lại Map.

### Lỗi 11 — Cho rằng embeddable không thể có nhiều field

`@ElementCollection` có thể chứa `@Embeddable` nhiều thuộc tính, các cột của embeddable được lưu trong collection table. Không cần biến value object thành entity chỉ vì nó chứa nhiều field.

### Lỗi 12 — Không xét concurrency khi hai request sửa collection

Một value collection không có version riêng; đồng thời hai transaction vẫn có thể xảy ra lost update hoặc xung đột ràng buộc. Cần thiết kế locking và transaction ở owner hoặc chuyển phần tử thành entity nếu domain cần.

## 19. Hướng lựa chọn theo yêu cầu nghiệp vụ

| Tình huống | Lựa chọn thường phù hợp | Vì sao? |
| --- | --- | --- |
| Project có vài chuỗi tag, không có metadata riêng. | `@ElementCollection Set<String>` | Mỗi tag chỉ là giá trị của Project. |
| Project có danh sách mốc (title, date) nhỏ, không cần ID từng mốc. | `@ElementCollection List<Milestone>` với `@Embeddable` | Mốc là giá trị gồm nhiều thuộc tính. |
| Task có ID, trạng thái, người phụ trách, version và được truy vấn riêng. | `@OneToMany List<Task>` | Mỗi Task là entity có identity. |
| Course được nhiều Student chia sẻ. | `@ManyToMany Set<Course>`, hoặc entity liên kết khi cần thuộc tính quan hệ | Course độc lập, không phải một value nằm riêng trong mỗi Student. |
| Map tùy chọn giao diện như `theme → dark`. | `@ElementCollection Map<String,String>` | Key/value là các giá trị basic. |
| Tra Task theo mã ổn định trong từng Project. | `@OneToMany Map<String,Task>` với `@MapKey(name="code")` | Map value vẫn là entity Task. |
| Một phần tử cần được tham chiếu bằng khóa ngoại từ entity khác. | Entity riêng | Phần tử cần identity có thể tham chiếu. |
| Một phần tử cần optimistic locking, audit và cập nhật độc lập. | Entity riêng với `@Id` và có thể `@Version` | Cần vòng đời và concurrency ở mức phần tử. |
| Danh sách giá trị có thứ tự ổn định nhưng không cần ID từng phần tử. | `@ElementCollection List<...>` với `@OrderColumn` | Lưu vị trí, không tạo entity identity. |
| Tập hợp giá trị rất lớn và thường xuyên chỉnh sửa từng hàng. | Cân nhắc entity collection | Có thể thuận lợi cho truy vấn, cập nhật và kiểm soát từng phần tử. |

**Quy tắc quyết định ngắn:** Nếu phần tử chỉ có ý nghĩa như **một giá trị trong trạng thái của owner**, ưu tiên `@ElementCollection` cho kiểu được hỗ trợ. Nếu phần tử có **danh tính, tham chiếu, vòng đời hoặc thao tác độc lập**, mô hình `@Entity` và association tương ứng thường phù hợp hơn.

## 20. Bài tập tự kiểm tra

**1. Tại sao `List<Task>` và `List<Milestone>` có thể cần hai annotation khác nhau dù cùng dùng List?**

Vì `Task` là `@Entity` có primary key, còn `Milestone` là `@Embeddable` không có identity riêng. Interface `List` không quyết định bản chất phần tử.

**2. Gỡ một `Task` khỏi `Project.tasks` có luôn xóa hàng tasks không?**

Không. Với `@OneToMany`, điều đó phụ thuộc ownership và `orphanRemoval`. Nếu không bật orphan removal, gỡ khỏi inverse collection không mặc nhiên gọi `EntityManager.remove(task)`.

**3. Gỡ chuỗi `"jpa"` khỏi `Project.tags` là xóa entity nào?**

Không xóa entity `Tag` nào, vì đây là `@ElementCollection Set<String>`. JPA đồng bộ thay đổi value collection của Project vào collection table.

**4. Có cần CascadeType.PERSIST cho `@ElementCollection` không?**

Không. Các phần tử basic/embeddable là trạng thái persistent của owner, không phải entity để cascade.

**5. Một `@ManyToMany Set<Course>` có nghĩa Course là value collection không?**

Không. `Course` vẫn là entity độc lập, còn join table lưu quan hệ. Cùng một Course có thể được nhiều Student tham chiếu.

**6. `@OrderColumn` có giúp từng `Milestone` có ID bền vững không?**

Không. Nó lưu vị trí trong list. Vị trí có thể đổi khi thêm, xóa hoặc sắp xếp lại.

**7. Với `Map<String,String>` dùng `@ElementCollection`, key của map nằm ở đâu trong database?**

Thường ở cột được xác định bởi `@MapKeyColumn` trong collection table, còn value nằm ở cột của value.

**8. Với `Map<String,Task>` dùng `@MapKey(name="code")`, value có còn là entity không?**

Có. `Task` là entity được tham chiếu qua `@OneToMany`; `MapKey` chỉ quy định cách lấy key của Map.

**9. Tại sao `Set<String>` có thể cần `UNIQUE(project_id, tag)` trong database?**

Vì Java Set không ngăn được dữ liệu trùng do các transaction, script hoặc service khác ghi trực tiếp vào bảng. Database constraint bảo vệ tính duy nhất ở tầng lưu trữ.

**10. Nếu cần sửa một phần tử bằng ID, có lịch sử và `@Version` riêng, nên chọn mô hình nào?**

Thường nên dùng entity có `@Id` độc lập và association thích hợp, thay vì một value object chỉ nằm trong `@ElementCollection`.

## 21. Ghi nhớ cốt lõi

**Tập hợp entity** (`@OneToMany`, `@ManyToMany`) chứa các phần tử là `@Entity`, có ID và được JPA quản lý như những entity riêng. Quan hệ đến chúng được lưu qua khóa ngoại hoặc bảng liên kết; khi tạo, merge, xóa hoặc gỡ phần tử cần hiểu rõ **owning side, cascade và orphanRemoval**.

**Tập hợp giá trị** (`@ElementCollection`) chứa những giá trị basic hoặc `@Embeddable`. Các phần tử là **một phần trạng thái của entity sở hữu**, không có entity ID, không được `EntityManager.find()` độc lập và không cần cấu hình cascade như entity. Chúng thường được lưu trong **collection table** có khóa ngoại đến owner.

`List`, `Set` và `Map` chỉ quyết định cấu trúc collection ở Java; **chúng không tự xác định entity hay value**. Thứ tự `@OrderColumn`, key của Map, tính bằng nhau của Set, hiệu năng LAZY và ràng buộc database đều cần được thiết kế theo đúng mô hình phần tử.

Hãy bắt đầu từ câu hỏi nghiệp vụ: **Phần tử này là một đối tượng có danh tính riêng, hay chỉ là một giá trị thuộc trạng thái của owner?** Trả lời được câu hỏi đó sẽ giúp chọn đúng mapping JPA, bảo toàn vòng đời dữ liệu và tránh những thao tác ghi/xóa ngoài dự kiến.
