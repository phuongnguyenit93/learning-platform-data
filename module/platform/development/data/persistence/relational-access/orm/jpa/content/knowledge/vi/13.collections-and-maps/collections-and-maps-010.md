# Theo dõi thay đổi tập hợp và chi phí SQL khi cập nhật

Trong JPA/Hibernate, entity không chỉ chứa các thuộc tính đơn như `name`, `price` hay `status`. Nó còn có thể chứa **tập hợp** như `Set<OrderLine>`, `List<Comment>`, `List<String>` hoặc `Map<String, String>`. Khi chương trình gọi `add()`, `remove()`, `clear()` hoặc thay một phần tử, câu hỏi không chỉ là “collection trong Java đã thay đổi chưa?” mà còn là:

- Entity có đang được **persistence context** quản lý không?
- Quan hệ có **phía sở hữu** nào thực sự được ghi vào database?
- Hibernate theo dõi thay đổi collection bằng cơ chế nào?
- Sau `flush()`, provider sẽ sinh **INSERT, UPDATE hay DELETE**, và bao nhiêu câu lệnh?
- Một thao tác thay đổi một phần tử có làm xóa rồi chèn lại **nhiều hàng trong bảng nối/bảng collection** không?
- Cách chọn `Set`, `List`, bag, `Map`, khóa hàng, index và cascade ảnh hưởng thế nào tới SQL?

Bài học này đi từ **dirty checking và collection snapshot** tới thiết kế mapping và quan sát SQL, giúp lựa chọn cấu trúc collection phù hợp với nghiệp vụ thay vì giả định một lời gọi Java luôn tương đương đúng một câu SQL.

> Cần phân biệt hai tầng: **JPA** quy định các trạng thái entity, quan hệ và ngữ nghĩa đồng bộ persistence context; **Hibernate** là một JPA provider có các cơ chế cụ thể như `PersistentBag`, `PersistentSet`, snapshot, batching và chiến lược recreate collection. SQL thực tế còn phụ thuộc phiên bản Hibernate, dialect, loại bảng, ràng buộc, trạng thái collection và thời điểm flush. Các SQL trong bài là **minh họa có điều kiện**, không phải cam kết provider luôn sinh đúng từng câu.

## 1. Từ collection Java tới hàng trong database

Giả sử một đơn hàng `PurchaseOrder` có nhiều dòng `OrderLine`:

~~~text
PurchaseOrder #500
    |
    +-- OrderLine #9001: Product A, quantity 2
    +-- OrderLine #9002: Product B, quantity 1
    +-- OrderLine #9003: Product C, quantity 4
~~~

Trong Java:

~~~java
order.getLines();         // Tập các dòng hàng
order.addLine(newLine);   // Thêm dòng
order.removeLine(line);   // Bỏ dòng
~~~

Trong database, quan hệ thường được lưu qua **khóa ngoại trên bảng con**:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code VARCHAR(40) NOT NULL UNIQUE,
    version BIGINT NOT NULL DEFAULT 0
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES purchase_orders(id),
    product_code VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0)
);

CREATE INDEX idx_order_lines_order_id ON order_lines(order_id);
~~~

Khi thêm một `OrderLine` vào đơn hàng, ta thường mong thêm **một hàng ở `order_lines`**. Khi sửa số lượng một dòng, ta mong **UPDATE một hàng**. Khi xóa một dòng không còn thuộc đơn hàng và có `orphanRemoval = true`, ta mong **DELETE dòng đó**.

Nhưng với `@ElementCollection`, `@ManyToMany` hoặc `List` không có cột định danh/phân biệt từng phần tử, Hibernate có thể cần thao tác SQL khác. Để hiểu, trước hết cần biết **persistence context theo dõi collection thế nào**.

## 2. Dirty checking của entity và collection

### 2.1. Entity managed là gì?

Entity được tải bằng `EntityManager.find(...)` trong một persistence context đang hoạt động thường ở trạng thái **managed**:

~~~java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    PurchaseOrder order = em.find(PurchaseOrder.class, 500L);
    // order đang managed nếu hàng tồn tại.

    // Thay đổi thuộc tính hoặc collection ở đây...

    tx.commit(); // Thường kích hoạt flush trước commit.
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
} finally {
    em.close();
}
~~~

Trong một context đang quản lý entity, Hibernate có thể **phát hiện thay đổi** và tạo SQL khi `flush()`, dù không có lệnh `repository.save(...)` cho từng field. Đây là *dirty checking*.

Đối với scalar field, provider có thể so sánh trạng thái hiện tại với trạng thái đã ghi nhận khi load hoặc dùng cơ chế bytecode enhancement để theo dõi thay đổi. Đối với collection, Hibernate thường dùng các wrapper collection chuyên biệt, kết hợp **snapshot** hoặc tín hiệu mutation, để biết tập hợp đã thay đổi thế nào.

### 2.2. Persistent collection là gì?

Khai báo trong entity:

~~~java
private Set<OrderLine> lines = new HashSet<>();
~~~

không bảo đảm sau khi entity được tải từ database, field vẫn giữ đúng instance `HashSet` do constructor tạo. Hibernate có thể đặt vào đó một wrapper triển khai giao diện collection tương ứng, ví dụ `PersistentSet`, để quản lý trạng thái.

~~~text
Ứng dụng nhìn thấy:
    Set<OrderLine> lines
          |
          v
Hibernate wrapper quản lý collection
          |
          +-- Trạng thái hiện tại trong Java
          +-- Snapshot / thông tin dirty
          +-- Owner và collection role
          +-- Trạng thái initialized / uninitialized
          |
          v
Flush -> tính toán và tạo SQL thích hợp
~~~

Các tên lớp như `PersistentBag`/`PersistentSet` là chi tiết triển khai của Hibernate; code domain nên phụ thuộc vào giao diện `List`, `Set` hoặc `Map`, không ép kiểu collection sang một lớp wrapper cụ thể.

### 2.3. Snapshot dùng để làm gì?

Một cách hình dung đơn giản:

~~~text
Khi load:
    snapshot = [A, B, C]

Trong transaction:
    remove(B)
    add(D)

Trước flush:
    current = [A, C, D]

Provider xác định:
    removed = B
    added   = D
~~~

Nếu mapping và khóa hàng hỗ trợ cập nhật từng phần tử, provider có thể tạo:

~~~sql
DELETE FROM order_tags WHERE order_id = 500 AND tag = 'B';
INSERT INTO order_tags (order_id, tag) VALUES (500, 'D');
~~~

Tuy nhiên, **snapshot không phải là một cam kết SQL diff tối ưu cho mọi kiểu collection**. Nếu provider không thể nhận diện từng hàng để xóa/cập nhật an toàn, nó có thể chọn xóa tập hàng của owner rồi chèn lại phần còn tồn tại.

Các khác biệt phụ thuộc vào: loại collection, định danh phần tử, schema, vị trí owning side, thứ tự, duplicate semantics và thuật toán của provider.

### 2.4. Khi nào flush diễn ra?

Thông thường flush xảy ra:

- Khi gọi `em.flush()`.
- Trước commit một transaction có thay đổi cần đồng bộ.
- Trước một số truy vấn khi `FlushModeType.AUTO` yêu cầu đồng bộ để bảo đảm ngữ nghĩa truy vấn.
- Theo những điểm do provider/transaction manager quản lý.

`flush()` **không phải commit**. Nó đồng bộ SQL vào transaction đang mở, nhưng transaction vẫn có thể rollback. Nhìn log SQL sau flush không có nghĩa dữ liệu đã được commit hoặc các hệ thống khác đã thấy kết quả.

Không dùng `em.flush()` sau mỗi `add()` chỉ để “lưu chắc chắn” mà không có lý do. Việc flush liên tục có thể phá khả năng gom thao tác/batching và làm tăng round-trip.

## 3. Mẫu mapping một-nhiều dễ kiểm soát thay đổi

Một cách phổ biến là để child sở hữu khóa ngoại bằng `@ManyToOne` và parent có `@OneToMany(mappedBy = "...")`.

### 3.1. Entity PurchaseOrder

~~~java
package com.example.shop;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 40)
    private String code;

    @Version
    private long version;

    @OneToMany(
        mappedBy = "order",
        cascade = CascadeType.ALL,
        orphanRemoval = true
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {}

    public PurchaseOrder(String code) {
        this.code = Objects.requireNonNull(code);
    }

    public Long getId() {
        return id;
    }

    public String getCode() {
        return code;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }

    public void addLine(OrderLine line) {
        Objects.requireNonNull(line);
        if (line.getOrder() != null && line.getOrder() != this) {
            throw new IllegalArgumentException(
                "Dòng hàng đã thuộc đơn hàng khác"
            );
        }
        if (!lines.contains(line)) {
            lines.add(line);
            line.attachTo(this);
        }
    }

    public void removeLine(OrderLine line) {
        if (lines.remove(line)) {
            line.detach();
        }
    }
}
~~~

### 3.2. Entity OrderLine

~~~java
package com.example.shop;

import jakarta.persistence.*;

@Entity
@Table(name = "order_lines")
public class OrderLine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @Column(name = "product_code", nullable = false, length = 40)
    private String productCode;

    @Column(nullable = false)
    private int quantity;

    protected OrderLine() {}

    public OrderLine(String productCode, int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity phải > 0");
        }
        this.productCode = productCode;
        this.quantity = quantity;
    }

    public Long getId() {
        return id;
    }

    public PurchaseOrder getOrder() {
        return order;
    }

    void attachTo(PurchaseOrder order) {
        this.order = order;
    }

    void detach() {
        this.order = null;
    }

    public void changeQuantity(int newQuantity) {
        if (newQuantity <= 0) {
            throw new IllegalArgumentException("quantity phải > 0");
        }
        this.quantity = newQuantity;
    }
}
~~~

Trong ví dụ, `OrderLine.order` là **owning side** vì nó chứa `@JoinColumn`; `PurchaseOrder.lines` là phía nghịch đảo vì có `mappedBy = "order"`. Helper trên parent đồng bộ cả hai phía trong Java object graph.

`cascade = ALL` và `orphanRemoval = true` có ý nghĩa ở đây vì **OrderLine phụ thuộc vào vòng đời của PurchaseOrder**, không phải đối tượng chia sẻ như Product hoặc Course. Một dòng hàng rời khỏi đơn hàng sẽ được coi là orphan để xóa khi flush. Đây không phải cấu hình nên sao chép sang mọi `@OneToMany`.

### 3.3. Thêm một dòng mới

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, 500L);
order.addLine(new OrderLine("JAVA-BOOK", 2));
~~~

Nếu mapping và transaction đang hoạt động đúng, khi flush provider có thể phát:

~~~sql
INSERT INTO order_lines (order_id, product_code, quantity)
VALUES (500, 'JAVA-BOOK', 2);
~~~

Do khóa ngoại được đặt ở `order_lines.order_id`, hệ thống thường không cần một bảng join riêng. Chi tiết số câu SQL có thể thay đổi theo chiến lược sinh ID, versioning, cascade và provider.

### 3.4. Thay đổi thuộc tính của phần tử

~~~java
OrderLine line = em.find(OrderLine.class, 9001L);
line.changeQuantity(3);
~~~

Nếu `OrderLine` managed, Hibernate phát hiện thay đổi của **entity child**. SQL về cơ bản có thể là:

~~~sql
UPDATE order_lines
SET quantity = 3
WHERE id = 9001;
~~~

Đây là dirty checking **thuộc tính của OrderLine**, không nhất thiết là “collection bị thay đổi”. Số phần tử của `PurchaseOrder.lines` không thay đổi; chỉ giá trị của một phần tử entity đổi.

Điểm này quan trọng khi phân tích hiệu năng: **sửa một thuộc tính của entity trong collection** có thể là UPDATE child, còn **thêm hoặc bỏ một phần tử** thường thay đổi cấu trúc association và có SQL khác.

### 3.5. Xóa một dòng hàng

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, 500L);

OrderLine lineToRemove = order.getLines().stream()
    .filter(line -> Long.valueOf(9002L).equals(line.getId()))
    .findFirst()
    .orElseThrow();

order.removeLine(lineToRemove);
~~~

Với `orphanRemoval = true`, việc loại một child khỏi collection có thể khiến provider DELETE hàng child:

~~~sql
DELETE FROM order_lines WHERE id = 9002;
~~~

Không được nhầm với thao tác chỉ tháo một FK để child tiếp tục tồn tại. Trong mô hình đơn hàng này, một OrderLine không có đơn hàng không hợp lệ, nên xóa child là semantics đã chọn.

Nếu child **được chia sẻ**, hoặc cần giữ lịch sử riêng, tránh `orphanRemoval = true` và thiết kế thay đổi association theo đúng vòng đời nghiệp vụ.

## 4. Vì sao owning side ảnh hưởng SQL?

Trong quan hệ hai chiều, JPA phân biệt owning side và inverse side. Ví dụ:

~~~java
// OrderLine — owning side
@ManyToOne
@JoinColumn(name = "order_id")
private PurchaseOrder order;

// PurchaseOrder — inverse side
@OneToMany(mappedBy = "order")
private List<OrderLine> lines;
~~~

Nếu chỉ gọi:

~~~java
order.getLines().add(line);
~~~

mà không đặt `line.order = order`, trạng thái hai phía trong Java bị lệch nhau. Provider căn cứ vào owning side khi đồng bộ khóa ngoại. Vì vậy cần helper duy trì nhất quán cả hai phía.

Với `@ManyToMany`, owning side thường là field có `@JoinTable`, còn bên kia có `mappedBy`. Thao tác thêm/xóa trên collection inverse **không được bảo đảm** sẽ thay đổi join table nếu owning collection không đổi.

### 4.1. Ví dụ nhiều-nhiều: Student và Course

~~~java
@Entity
class Student {
    @Id
    private Long id;

    @ManyToMany
    @JoinTable(
        name = "student_courses",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private Set<Course> courses = new HashSet<>();

    public void enroll(Course course) {
        if (courses.add(course)) {
            course.addStudentFromStudent(this);
        }
    }

    public void withdraw(Course course) {
        if (courses.remove(course)) {
            course.removeStudentFromStudent(this);
        }
    }
}

@Entity
class Course {
    @Id
    private Long id;

    @ManyToMany(mappedBy = "courses")
    private Set<Student> students = new HashSet<>();

    void addStudentFromStudent(Student student) {
        students.add(student);
    }

    void removeStudentFromStudent(Student student) {
        students.remove(student);
    }
}
~~~

Join table:

~~~sql
CREATE TABLE student_courses (
    student_id BIGINT NOT NULL REFERENCES students(id),
    course_id BIGINT NOT NULL REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)
);
~~~

Khi rút một Course từ Student managed trên owning side, nghiệp vụ thường muốn:

~~~sql
DELETE FROM student_courses
WHERE student_id = 10 AND course_id = 100;
~~~

**Không phải**:

~~~sql
DELETE FROM courses WHERE id = 100;
~~~

Với endpoint là entity độc lập được nhiều đối tượng sử dụng, không cấu hình `CascadeType.REMOVE` hoặc `CascadeType.ALL` một cách vô điều kiện. Xóa một **liên kết** là chuyện khác với xóa entity ở đầu kia.

## 5. Set, List, bag và Map: khác nhau về ý nghĩa và cách cập nhật

Loại collection trong Java ảnh hưởng khả năng nhận diện phần tử và chiến lược SQL, nhưng còn phụ thuộc schema và mapping.

| Collection | Semantics trong Java | Cách sử dụng thường gặp | Điều cần chú ý khi ghi |
|---|---|---|---|
| `Set<E>` | Không chứa hai phần tử bằng nhau theo `equals/hashCode` | Quan hệ không trùng, các nhãn/tags | Hash ổn định; DB vẫn cần UNIQUE; có thể diff phần tử khi row identifiable |
| `List<E>` | Có thứ tự truy cập qua index, cho phép trùng | Các bước xử lý, dòng hiển thị theo vị trí | Phải phân biệt bag không có index với indexed list có `@OrderColumn` |
| **Bag** (khái niệm Hibernate) | Cho phép phần tử trùng, không có index persistence riêng | List không lưu vị trí trong DB | Một số mapping có thể DELETE toàn bộ link rows rồi INSERT lại |
| `Map<K,V>` | Tra cứu bằng key, mỗi key xuất hiện tối đa một lần trong Map | Cài đặt theo tên thuộc tính, bản dịch theo locale | Key phải ổn định; DB cần constraint về (owner, key); thay key có thể là DELETE + INSERT |
| `Collection<E>` | Không yêu cầu thứ tự/index hoặc uniqueness | Danh sách không cần semantics đặc biệt | Cách Hibernate biểu diễn có thể là bag, chi phí tùy row identifier |

**Đừng kết luận “dùng `Set` luôn nhanh hơn `List`”.** Với `@OneToMany` có child entity mang PK riêng, `List` và `Set` đều có thể phát SQL hiệu quả khi thay từng child. Vấn đề “xóa hết rồi chèn lại” thường nổi bật ở một số **bảng nối và bảng collection không có khóa định danh hàng phù hợp**, đặc biệt với bag hoặc list không được đánh index.

### 5.1. List không có @OrderColumn có thể được Hibernate coi là bag

Ví dụ:

~~~java
@ManyToMany
@JoinTable(
    name = "playlist_tracks",
    joinColumns = @JoinColumn(name = "playlist_id"),
    inverseJoinColumns = @JoinColumn(name = "track_id")
)
private List<Track> tracks = new ArrayList<>();
~~~

Nếu không có cột index thứ tự và không có ràng buộc/định danh phù hợp, cùng một `Track` có thể xuất hiện nhiều lần trong bag. Để xóa **một occurrence**, ORM có thể không có cột nào phân biệt nó với occurrence còn lại.

Một chiến lược có thể gặp ở Hibernate là:

~~~sql
DELETE FROM playlist_tracks
WHERE playlist_id = 42;

INSERT INTO playlist_tracks (playlist_id, track_id) VALUES (42, 7);
INSERT INTO playlist_tracks (playlist_id, track_id) VALUES (42, 8);
INSERT INTO playlist_tracks (playlist_id, track_id) VALUES (42, 9);
-- Chèn lại các phần tử còn lại.
~~~

Tức là thao tác Java `tracks.remove(track)` có thể dẫn đến **recreate nhiều hàng**, không phải một DELETE. Mức độ và điều kiện phụ thuộc Hibernate version, mapping và loại collection; không coi mẫu SQL trên là quy tắc bắt buộc cho mọi `List`.

Nếu nghiệp vụ yêu cầu không có track trùng trong một playlist, dùng `Set<Track>` với unique constraint `(playlist_id, track_id)` có thể phản ánh domain và cho provider khả năng nhận diện link row tốt hơn.

Nếu nghiệp vụ **cần trùng và cần thứ tự cụ thể**, nên thiết kế row có identity hoặc index rõ ràng thay vì dựa vào bag vô danh.

### 5.2. @OrderColumn tạo indexed list

Với danh sách có thứ tự persistence:

~~~java
@ElementCollection
@CollectionTable(
    name = "playlist_titles",
    joinColumns = @JoinColumn(name = "playlist_id")
)
@OrderColumn(name = "position")
@Column(name = "title", nullable = false)
private List<String> titles = new ArrayList<>();
~~~

Schema minh họa:

~~~sql
CREATE TABLE playlist_titles (
    playlist_id BIGINT NOT NULL REFERENCES playlists(id),
    position INTEGER NOT NULL,
    title VARCHAR(255) NOT NULL,
    CONSTRAINT pk_playlist_titles
        PRIMARY KEY (playlist_id, position)
);
~~~

Khi gọi:

~~~java
titles.add(0, "Intro");
~~~

các phần tử cũ có thể phải chuyển vị trí index. Với `n` phần tử, chèn vào đầu hoặc xóa giữa danh sách có thể gây **nhiều UPDATE index** hoặc các thao tác DELETE/INSERT liên quan, không nhất thiết một INSERT.

Vì có constraint `PRIMARY KEY(playlist_id, position)`, thứ tự thay đổi index phải được sắp xếp an toàn để không tạm thời tạo vị trí trùng. Provider và schema cần tương thích. Nếu cần thao tác reorder phức tạp với concurrency cao, entity riêng có trường `position` và khóa rõ ràng có thể dễ kiểm soát hơn.

### 5.3. @OrderBy không giống @OrderColumn

Hai annotation giải quyết các việc khác nhau:

- `@OrderBy("name ASC")` yêu cầu sắp xếp kết quả theo **thuộc tính/cột dữ liệu** khi tải collection; không nhất thiết tạo cột vị trí và lưu lại thứ tự do người dùng kéo-thả.
- `@OrderColumn(name = "position")` ánh xạ **vị trí của phần tử trong List** thành cột thứ tự trong bảng quan hệ/collection.

Nếu user kéo phần tử từ vị trí 10 lên vị trí 1, `@OrderBy("name ASC")` không có cơ chế lưu “ý định kéo thả” trừ khi thay đổi thuộc tính dùng để sắp xếp. `@OrderColumn` lưu vị trí nhưng có thể phát sinh SQL cập nhật nhiều hàng.

## 6. @ElementCollection: lưu value collection

Không phải tập hợp nào cũng chứa entity. Ví dụ `UserProfile` có nhiều nhãn (tags) và cài đặt nhỏ:

~~~java
@Entity
@Table(name = "user_profiles")
public class UserProfile {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ElementCollection(fetch = FetchType.LAZY)
    @CollectionTable(
        name = "user_profile_tags",
        joinColumns = @JoinColumn(name = "user_profile_id")
    )
    @Column(name = "tag", nullable = false, length = 60)
    private Set<String> tags = new HashSet<>();

    protected UserProfile() {}

    public void addTag(String tag) {
        tags.add(tag);
    }

    public void removeTag(String tag) {
        tags.remove(tag);
    }
}
~~~

Schema:

~~~sql
CREATE TABLE user_profile_tags (
    user_profile_id BIGINT NOT NULL
        REFERENCES user_profiles(id),
    tag VARCHAR(60) NOT NULL,
    CONSTRAINT pk_user_profile_tags
        PRIMARY KEY (user_profile_id, tag)
);
~~~

`String` không có entity identity; mỗi tag là giá trị thuộc owner. Với bảng có khóa ghép `(user_profile_id, tag)`, provider có thể xác định từng row để thêm/xóa:

~~~sql
INSERT INTO user_profile_tags (user_profile_id, tag)
VALUES (15, 'jpa');

DELETE FROM user_profile_tags
WHERE user_profile_id = 15 AND tag = 'hibernate';
~~~

Nhưng vì `@ElementCollection` không dùng entity ID riêng cho value, chi phí SQL vẫn có thể phụ thuộc collection type, thuộc tính nullable, duplicate semantics và Hibernate version.

### 6.1. Nếu phần tử là @Embeddable?

Giả sử mỗi địa chỉ nhận hàng có `street`, `city`, `countryCode` và nằm trong `List<Address>`:

~~~java
@Embeddable
public class Address {
    private String street;
    private String city;
    private String countryCode;

    protected Address() {}
}

@Entity
class Customer {
    @Id
    private Long id;

    @ElementCollection
    @CollectionTable(
        name = "customer_addresses",
        joinColumns = @JoinColumn(name = "customer_id")
    )
    private List<Address> addresses = new ArrayList<>();
}
~~~

Nếu bảng `customer_addresses` không có ID hoặc khóa hàng ổn định và có thể chứa hai địa chỉ giống nhau, việc xóa riêng một occurrence có thể không xác định duy nhất row cần xóa. ORM có thể dùng cách xóa rồi chèn lại các hàng của owner.

Nếu địa chỉ cần ID, nhãn “HOME/WORK”, trạng thái xác minh, lịch sử, hoặc được nhiều bảng tham chiếu, nên cân nhắc **entity Address riêng** thay vì `@ElementCollection`.

### 6.2. Thay đổi một value trong collection khác với sửa entity

Với `Set<String> tags`, để đổi nhãn “old” thành “new”, về mặt dữ liệu tập hợp đó là:

~~~java
tags.remove("old");
tags.add("new");
~~~

Không có entity `Tag` managed để UPDATE từng field. Tùy mapping, SQL có thể là DELETE hàng giá trị cũ và INSERT hàng giá trị mới.

Với `List<Address>` chứa embeddable mutable, việc sửa field bên trong một phần tử có thể được phát hiện qua snapshot, nhưng provider không phải lúc nào cũng có row ID để UPDATE chính xác một hàng; có thể phải recreate nhiều row. Dùng value object bất biến hoặc thay cả giá trị giúp biểu đạt domain rõ ràng, nhưng không tự bảo đảm SQL tối ưu.

## 7. Map được lưu như thế nào và khi nào bị cập nhật hàng loạt?

JPA có thể ánh xạ `Map` như value collection. Ví dụ các thiết lập dạng `settingKey -> settingValue` thuộc `UserProfile`:

~~~java
@Entity
@Table(name = "user_profiles")
public class UserProfile {
    @Id
    private Long id;

    @ElementCollection
    @CollectionTable(
        name = "user_settings",
        joinColumns = @JoinColumn(name = "user_profile_id")
    )
    @MapKeyColumn(name = "setting_key", length = 80)
    @Column(name = "setting_value", length = 500)
    private Map<String, String> settings = new HashMap<>();

    public void putSetting(String key, String value) {
        settings.put(key, value);
    }

    public void removeSetting(String key) {
        settings.remove(key);
    }
}
~~~

Schema minh họa:

~~~sql
CREATE TABLE user_settings (
    user_profile_id BIGINT NOT NULL REFERENCES user_profiles(id),
    setting_key VARCHAR(80) NOT NULL,
    setting_value VARCHAR(500),
    PRIMARY KEY (user_profile_id, setting_key)
);
~~~

Map có key duy nhất trong phạm vi owner nên cặp `(user_profile_id, setting_key)` là một định danh row tự nhiên ở database.

Một thao tác:

~~~java
profile.putSetting("theme", "dark");
~~~

có thể tương ứng với:

- INSERT nếu chưa có key “theme”.
- UPDATE `setting_value` nếu đã có key và provider có thể định vị row.
- Hoặc chuỗi SQL khác khi Hibernate chọn recreate collection theo metadata.

Không nên xem `put` là câu SQL `UPSERT` chuẩn. Phía ứng dụng chỉ thay đổi Java Map; provider tự quyết định các thao tác đồng bộ khi flush.

### 7.1. Đổi key là thay đổi định danh của phần tử Map

Nếu cần đổi key từ `"theme"` sang `"ui.theme"`:

~~~java
String value = settings.remove("theme");
if (value != null) {
    settings.put("ui.theme", value);
}
~~~

Ở tầng database, thường hợp lý để DELETE hàng key cũ rồi INSERT key mới. Vì key tham gia PK của bảng collection, không giả định `Map` sẽ tạo một UPDATE PK duy nhất.

### 7.2. @MapKey và @MapKeyColumn khác nhau

Đối với Map chứa entity, JPA có:

- `@MapKey(name = "code")`: dùng một **thuộc tính của entity đích** như key trong Map.
- `@MapKeyColumn(name = "setting_key")`: lưu key trong **cột map-key riêng** của bảng chứa quan hệ/collection.

Ví dụ với entity đích có mã ngôn ngữ:

~~~java
@OneToMany(mappedBy = "article")
@MapKey(name = "localeCode")
private Map<String, Translation> translations = new HashMap<>();
~~~

Key được suy ra từ `Translation.localeCode`. Nếu `localeCode` bị thay đổi sau khi collection đã được tải, Java Map trong bộ nhớ có thể không tự cập nhật key để phản ánh giá trị mới. Nên coi map key là ổn định hoặc có method nghiệp vụ duy trì nhất quán khi thay đổi.

Map không tự thay thế constraint tại DB. Với `Translation`, vẫn cần unique constraint bảo đảm không có hai bản dịch cùng locale cho một bài viết nếu domain đòi hỏi vậy.

## 8. Chi phí SQL: một thao tác Java không đồng nghĩa một câu lệnh

Xét một collection có `n` hàng đang lưu.

| Thay đổi | Mapping có thể tối ưu theo từng row | Mapping phải recreate collection |
|---|---|---|
| Thêm một phần tử | Thường 1 INSERT | Có thể DELETE nhiều hàng + INSERT lại nhiều hàng |
| Bỏ một phần tử | Thường 1 DELETE | Có thể DELETE cả collection của owner rồi INSERT lại `n-1` hàng |
| Sửa value của một row có khóa | Có thể 1 UPDATE, hoặc DELETE + INSERT | Có thể recreate hàng loạt |
| Xóa toàn bộ collection | Một DELETE theo owner hoặc nhiều DELETE tùy mapping | Có thể DELETE tất cả hàng của owner |
| Đổi vị trí một item trong indexed List | Có thể nhiều UPDATE index hoặc chiến lược tương đương | Phụ thuộc index/constraint/provider |
| Thay toàn bộ collection Java | Provider phải phân tích trạng thái cũ và mới; có thể phát nhiều SQL | Có thể làm mất tối ưu delta hoặc gây lỗi wrapper orphan |

Ví dụ với collection ban đầu `[A, B, C, D, E]` và bỏ `C`:

**Trường hợp có khóa hàng rõ ràng:**

~~~sql
DELETE FROM owner_items
WHERE owner_id = 1 AND item_id = 3;
~~~

**Trường hợp không thể định vị occurrence an toàn:**

~~~sql
DELETE FROM owner_items WHERE owner_id = 1;

INSERT INTO owner_items (owner_id, item_value) VALUES (1, 'A');
INSERT INTO owner_items (owner_id, item_value) VALUES (1, 'B');
INSERT INTO owner_items (owner_id, item_value) VALUES (1, 'D');
INSERT INTO owner_items (owner_id, item_value) VALUES (1, 'E');
~~~

Hai phương án khác nhau rất lớn khi `n` là 10 so với 100.000. Phương án thứ hai còn tạo thêm ghi WAL/redo, index maintenance, lock và có thể kích hoạt trigger/audit, không chỉ tốn thêm round-trip.

**Đây là so sánh hành vi có thể xảy ra**, không phải lời hứa rằng bất kỳ `List` nào cũng xóa toàn bộ và bất kỳ `Set` nào cũng cập nhật từng row. Hãy xem mapping thực tế và SQL mà provider phát ra.

### 8.1. Chi phí network round-trip và số hàng bị chạm

Một batch 100 câu INSERT có thể được JDBC gửi hiệu quả hơn 100 round-trip độc lập, nhưng database vẫn phải xử lý 100 hàng. Vì vậy hãy phân tích ít nhất ba chỉ số:

1. **Số statement SQL** được thực thi.
2. **Số row** bị insert/update/delete.
3. **Số round-trip** và thời gian giữ lock/transaction.

Chỉ đếm câu SQL không đủ đánh giá chi phí tổng; một lệnh DELETE theo `owner_id` có thể xóa hàng chục nghìn dòng và kéo theo cập nhật nhiều index.

### 8.2. Index giúp truy vấn và xóa nhưng cũng có chi phí ghi

Với bảng join:

~~~sql
CREATE TABLE student_courses (
    student_id BIGINT NOT NULL REFERENCES students(id),
    course_id BIGINT NOT NULL REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)
);

CREATE INDEX idx_student_courses_course_id
    ON student_courses(course_id);
~~~

PK giúp tra cứu một cặp `(student_id, course_id)` và thường hỗ trợ lấy các course theo student. Index theo `course_id` giúp truy vấn các student của một course, nhưng mỗi INSERT/DELETE link cũng phải cập nhật index.

Đừng thêm index thiếu kiểm soát chỉ để tối ưu một truy vấn; cần cân bằng đọc/ghi theo workload thực tế và DBMS.

## 9. clear(), removeIf() và thay hẳn collection: cẩn thận

### 9.1. clear() không phải câu lệnh SQL tức thì

~~~java
order.getMutableLines().clear();
~~~

Nếu method domain cho phép clear ở owning/inverse collection thích hợp, Java collection có thể trống ngay nhưng database chỉ được đồng bộ khi flush. Với `orphanRemoval = true`, clear có thể dẫn đến DELETE tất cả child. Với join table, có thể DELETE các hàng liên kết; entity đầu kia vẫn tồn tại nếu không có cascade remove.

Trong code domain, nên cung cấp method có tên thể hiện rule, ví dụ `removeAllLines()`, để tránh caller xóa hàng loạt ngoài ý muốn.

### 9.2. Thay collection bằng HashSet/List mới có thể làm mất quản lý wrapper

Một lỗi hay thấy:

~~~java
// Nguy cơ với managed entity có Hibernate persistent collection:
order.setLines(new ArrayList<>(incomingLines));
~~~

Nếu entity đã managed, field `lines` có thể đang trỏ đến wrapper Hibernate. Thay reference bằng một collection hoàn toàn mới có thể:

- Làm provider coi collection cũ bị dereference và collection mới thay thế.
- Gây SQL diff lớn, recreate hoặc thay đổi không như mong muốn.
- Với một số mapping dùng `orphanRemoval` trong Hibernate, có thể gây lỗi dạng “collection with cascade all-delete-orphan was no longer referenced”.

**Không phải mọi phép gán collection mới đều lỗi theo JPA**, nhưng việc giữ wrapper managed và dùng helper thêm/bỏ phần tử thường an toàn và dễ kiểm soát hơn trong domain.

Một cách cập nhật theo yêu cầu mới:

~~~java
public void replaceTags(Set<String> incoming) {
    Set<String> wanted = new HashSet<>(incoming);

    tags.removeIf(existing -> !wanted.contains(existing));
    for (String tag : wanted) {
        tags.add(tag);
    }
}
~~~

Đoạn này là ví dụ method bên trong entity có field `Set<String> tags`. Nó giữ nguyên object collection đang được provider quản lý và thể hiện một phép cập nhật theo delta, nhưng SQL cuối cùng vẫn tùy mapping/optimizer.

### 9.3. Không sửa collection qua getter không kiểm soát

Nếu getter trả collection mutable trực tiếp:

~~~java
order.getLines().remove(line);
~~~

caller có thể bỏ phần tử ở phía inverse nhưng quên cập nhật `line.order`. Thay vào đó cung cấp helper:

~~~java
order.removeLine(line);
~~~

Helper đồng bộ cả object graph và thực thi validation nghiệp vụ. Nếu dùng getter trả `Collections.unmodifiableList(...)`, cần cung cấp method domain để thay đổi hợp lệ.

### 9.4. removeIf có thể load nhiều phần tử

~~~java
order.removeLinesMatching(line -> line.isCanceled());
~~~

Nếu thao tác này lặp qua collection lazy, Hibernate có thể phải tải toàn bộ collection rồi mới lọc. Với hàng trăm nghìn child, chi phí memory và truy vấn có thể lớn hơn một câu DELETE theo predicate ở database.

Nếu mục tiêu chỉ là xóa tất cả child thỏa điều kiện, có thể cần một bulk operation riêng và kế hoạch đồng bộ persistence context phù hợp.

## 10. Bulk JPQL/native SQL bypass persistence context như thế nào?

Khi dùng bulk DML:

~~~java
int deleted = em.createQuery(
        """
        DELETE FROM OrderLine l
        WHERE l.order.id = :orderId
          AND l.quantity = 0
        """
    )
    .setParameter("orderId", orderId)
    .executeUpdate();
~~~

Đây là bulk delete entity row (ví dụ minh họa, dữ liệu mẫu ở trên vốn có CHECK quantity > 0). Bulk JPQL DML **không vận hành giống thao tác loại phần tử khỏi collection managed**. Nó có thể bỏ qua per-entity callbacks, cascade/orphanRemoval và không tự cập nhật các entity/collection đã được load trong persistence context.

Nếu `order.lines` đã được initialize trước bulk delete, collection trong bộ nhớ có thể vẫn chứa các child vừa bị xóa ở DB. Để tránh inconsistency:

1. Quy định ranh giới transaction và điểm flush trước khi bulk DML khi cần.
2. Không tiếp tục sử dụng các entity/collection stale mà không `clear()`, `refresh()` hoặc tải lại phù hợp.
3. Nắm rõ bulk DML có thể bypass optimistic locking/per-entity events; nếu cần kiểm soát version, thiết kế điều kiện/update version thích hợp.
4. Với bảng join thuần, JPQL bulk delete thường nhắm tới entity chứ không trực tiếp một join table ẩn; cần native SQL hoặc entity liên kết khi muốn thao tác trực tiếp từng row.

Ví dụ native SQL:

~~~java
int removed = em.createNativeQuery(
        """
        DELETE FROM student_courses
        WHERE student_id = :studentId
          AND course_id = :courseId
        """
    )
    .setParameter("studentId", studentId)
    .setParameter("courseId", courseId)
    .executeUpdate();
~~~

Nếu trong cùng EntityManager, `Student.courses` đã được load trước đó, native delete không làm collection tự giảm phần tử trong bộ nhớ. Không trộn native DML và sửa object graph tùy tiện; cần cơ chế đồng bộ rõ ràng.

## 11. N+1 khi đọc collection và chi phí cập nhật

Hai bài toán thường bị gom chung nhưng cần phân biệt:

- **N+1 SELECT**: tải `N` parent, sau đó truy cập collection của từng parent dẫn tới thêm `N` câu SELECT.
- **SQL write amplification**: sửa một collection có thể gây nhiều INSERT/UPDATE/DELETE hơn số thay đổi về nghiệp vụ.

### 11.1. Ví dụ N+1

~~~java
List<PurchaseOrder> orders = em.createQuery(
        "SELECT o FROM PurchaseOrder o",
        PurchaseOrder.class
    )
    .getResultList();

for (PurchaseOrder order : orders) {
    System.out.println(order.getLines().size());
}
~~~

Nếu `lines` lazy và từng collection được tải riêng, có thể phát N truy vấn để biết size/lấy dữ liệu, tùy trạng thái collection và Hibernate capabilities.

Các cách cải thiện cho nhu cầu đọc:

- Query projection/DTO theo dữ liệu thật cần hiển thị.
- `JOIN FETCH` khi số collection phù hợp và không gây Cartesian product khổng lồ.
- Batch fetch hoặc subselect fetch theo cơ chế Hibernate được cấu hình.
- Truy vấn aggregate/count ở database nếu chỉ cần số lượng.

Tuy nhiên, fetch tất cả child để thay một liên kết nhỏ có thể tăng chi phí update path. Mỗi use case nên được thiết kế với yêu cầu đọc/ghi riêng.

### 11.2. JOIN FETCH nhiều collection có thể gây vấn đề khác

~~~java
SELECT o FROM PurchaseOrder o
JOIN FETCH o.lines
JOIN FETCH o.tags
~~~

Nếu một order có 50 lines và 40 tags, join có thể tạo tới 2.000 row ở result set trước khi ORM ghép lại object graph. Với nhiều bag trong Hibernate, còn có thể gặp hạn chế như `MultipleBagFetchException` tùy mapping/version.

Không giải quyết N+1 bằng cách fetch-join mọi collection trên mọi trang. Cần pagination, projection, batch/subselect hoặc chia truy vấn phù hợp.

## 12. Batching khi ghi nhiều phần tử

Khi cần chèn nhiều child, JDBC batching có thể giảm round-trip. Với Hibernate, các cấu hình thường gặp:

~~~properties
hibernate.jdbc.batch_size=50
hibernate.order_inserts=true
hibernate.order_updates=true
~~~

Ý nghĩa khái quát:

- `hibernate.jdbc.batch_size`: kích thước batch JDBC khi các thao tác phù hợp có thể gom.
- `hibernate.order_inserts`: có thể nhóm các INSERT theo entity/table để tăng khả năng batching.
- `hibernate.order_updates`: có thể sắp xếp UPDATE để tăng khả năng batching và giảm một số kiểu deadlock.

Đây là cấu hình **Hibernate-specific**, không phải thuộc tính chuẩn của JPA. Tác dụng phụ thuộc phiên bản, JDBC driver, khóa chính, provider và trình tự thao tác.

### 12.1. IDENTITY có thể hạn chế JDBC insert batching

Với `GenerationType.IDENTITY`, provider thường phải thực thi INSERT để lấy ID do database sinh; ở một số phiên bản Hibernate, điều này hạn chế hoặc vô hiệu hóa khả năng batch insert cho entity tương ứng.

Nếu ứng dụng tạo hàng nghìn child entity một lúc, chiến lược `SEQUENCE` với cơ chế cấp phát tương thích có thể giúp batching hơn trong một số môi trường. Nhưng việc đổi ID generator liên quan tới schema/migration và không nên quyết định chỉ dựa trên ví dụ.

### 12.2. Batch không chữa được recreate không cần thiết

Nếu xóa một phần tử khỏi bag khiến 10.000 row bị DELETE rồi INSERT lại 9.999 row, batching có thể giảm round-trip của INSERT, nhưng vẫn phải ghi lại gần 10.000 row. Để giảm bản chất chi phí phải **đổi mô hình collection/khóa hàng hoặc cách cập nhật**, không chỉ tăng batch size.

## 13. Collection lớn: chọn cấu trúc phù hợp với thao tác chính

Nếu một parent có hàng chục nghìn child nhưng nghiệp vụ chỉ thêm hoặc xóa từng child theo ID, việc giữ một collection lớn và thường xuyên initialize nó để sửa một phần tử có thể không phù hợp.

Một số phương án:

### 13.1. Entity liên kết có primary key riêng

Với membership giữa User và Group có ngày tham gia, vai trò và trạng thái:

~~~text
User 1 ---- n Membership n ---- 1 Group
~~~

Bảng:

~~~sql
CREATE TABLE memberships (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    group_id BIGINT NOT NULL REFERENCES groups(id),
    joined_at TIMESTAMP WITH TIME ZONE NOT NULL,
    role VARCHAR(30) NOT NULL,
    CONSTRAINT uq_membership_user_group UNIQUE (user_id, group_id)
);

CREATE INDEX idx_memberships_group_id ON memberships(group_id);
~~~

Entity `Membership` có hai quan hệ `@ManyToOne`, một khóa riêng và các field nghiệp vụ. Khi rút khỏi nhóm, xóa hoặc cập nhật **một Membership** là thao tác rõ ràng; không cần tải tất cả group của User.

### 13.2. Truy vấn từng child thay vì duyệt collection

Nếu `OrderLine` là entity có ID, service có thể tải thẳng:

~~~java
OrderLine line = em.find(OrderLine.class, lineId);

if (line == null ||
    !line.getOrder().getId().equals(orderId)) {
    throw new IllegalArgumentException("Không đúng dòng hàng");
}

line.changeQuantity(newQuantity);
~~~

Cách này không cần duyệt toàn bộ `order.getLines()` để tìm phần tử, dù có thể phát sinh truy vấn association tùy proxy. Nên xác thực quyền và quan hệ sở hữu qua query hoặc điều kiện database thích hợp trong hệ thống thực.

Nếu sử dụng `orphanRemoval`, thao tác xóa child trực tiếp phải phối hợp object graph đã load và quy tắc aggregate; không dùng `em.remove(line)` tùy tiện khi collection owner còn giữ reference stale.

### 13.3. Map/Set với khóa ổn định

Nếu use case là thêm/bỏ **một cặp** mà không có metadata khác, dùng `Set` hoặc `Map` với khóa row rõ ràng (kết hợp unique DB constraint) thường cho schema dễ cập nhật theo cặp hơn bag không định danh. Nhưng SQL thực tế vẫn phải đo theo provider.

### 13.4. Chia collection theo phạm vi nếu nghiệp vụ cho phép

Thay vì một collection chứa mọi sự kiện từ khi tạo tài khoản, có thể lưu event thành bảng entity độc lập và query theo trang/thời gian. Không nên biến một entity thành aggregate khổng lồ chỉ để duyệt hết mọi dữ liệu qua một getter.

## 14. Concurrency và optimistic locking của collection

Một collection managed không có nghĩa mọi cập nhật đồng thời được bảo vệ.

Ví dụ:

~~~text
Transaction A tải Student 10 với courses = {100}
Transaction B tải Student 10 với courses = {100}

A thêm Course 101.
B thêm Course 102.

Cả hai cùng commit gần nhau.
~~~

Kết quả phụ thuộc mapping, SQL sinh ra, constraint và cơ chế locking. Với thao tác insert độc lập vào join table, có thể cả hai liên kết được thêm thành công; với cách recreate collection, một transaction có thể tạo trạng thái không mong muốn nếu concurrency không được kiểm soát.

### 14.1. @Version có bảo vệ collection không?

~~~java
@Entity
public class Student {
    @Id
    private Long id;

    @Version
    private long version;
}
~~~

`@Version` là optimistic locking cho entity. Việc cập nhật một collection có làm tăng version của owner hay không **phụ thuộc association ownership, mapping và provider**. Không mặc định rằng mọi thay đổi inverse collection hay bulk/native DML đều increment version.

Nếu domain rule cần kiểm soát đồng thời một cách chặt chẽ, hãy thiết kế rõ:

- Ai là aggregate root của quy tắc?
- Row nào mang version và điều kiện cập nhật?
- Khi nào xảy ra optimistic lock exception và retry?
- Có cần pessimistic lock trong transaction không?
- Constraint nào ở database bảo vệ trạng thái cuối cùng?

### 14.2. Quy tắc giới hạn số phần tử

Ví dụ “mỗi khóa học chỉ có tối đa 30 sinh viên”. Hai transaction cùng thấy đang có 29 sinh viên rồi cùng đăng ký, dẫn tới 31. Dùng `Set` và unique constraint không ngăn được tình huống này vì hai sinh viên khác nhau.

Cần một cơ chế đồng bộ cho **quy tắc tổng số**, như row lock trên Course, counter/slot constraint hoặc chiến lược concurrency khác. Không trông đợi dirty checking collection tự đảm bảo một bất biến nhiều hàng trong database.

### 14.3. Nguy cơ deadlock khi ghi nhiều collection

Hai transaction cập nhật cùng các bảng theo thứ tự khác nhau có thể gây deadlock, nhất là khi xóa/insert nhiều hàng join và cập nhật nhiều index. Thiết kế transaction ngắn, thứ tự thao tác nhất quán, index phù hợp và chính sách retry đối với deadlock/serialization failure có thể cần thiết.

## 15. Theo dõi SQL thực tế của Hibernate

Vì SQL phụ thuộc provider/version, cách ra quyết định đáng tin cậy là **quan sát mapping và SQL trên workload điển hình**. Các tùy chọn Hibernate hay dùng trong môi trường phát triển:

~~~properties
hibernate.show_sql=true
hibernate.format_sql=true
hibernate.generate_statistics=true
~~~

Trong ứng dụng Spring Boot sử dụng Hibernate, có thể cấu hình qua thuộc tính vendor tương ứng:

~~~properties
spring.jpa.properties.hibernate.format_sql=true
spring.jpa.properties.hibernate.generate_statistics=true
logging.level.org.hibernate.SQL=DEBUG
~~~

Tùy phiên bản Hibernate, logging bind parameters có category khác nhau. Với Hibernate 6, một category phổ biến là:

~~~properties
logging.level.org.hibernate.orm.jdbc.bind=TRACE
~~~

**Chỉ bật log tham số có kiểm soát trong môi trường phù hợp**, vì bind values có thể chứa email, token, địa chỉ hoặc dữ liệu nhạy cảm. Không bật TRACE toàn hệ thống production một cách vô điều kiện.

### 15.1. Cần quan sát những gì?

Với một thao tác thay đổi collection, ghi nhận:

1. Bao nhiêu SELECT phát sinh để initialize/tra cứu collection?
2. Có bao nhiêu INSERT/UPDATE/DELETE?
3. Những SQL nào có điều kiện `WHERE owner_id = ?`, và SQL nào nhắm chính xác một row bằng PK/unique key?
4. Có hiện tượng DELETE cả collection rồi INSERT lại không?
5. Có UPDATE cột index do `@OrderColumn` không?
6. Có UPDATE owner/version hoặc trigger nào bị kích hoạt không?
7. Thời gian flush/commit và số row bị ảnh hưởng là bao nhiêu?
8. Có batch JDBC thực sự hay chỉ có nhiều statement độc lập?

Đừng chỉ nhìn một dòng log `Hibernate: insert into ...` và kết luận chi phí O(1). Cần xem toàn bộ transaction và dữ liệu tương ứng.

### 15.2. Hibernate Statistics

Hibernate có API thống kê có thể hỗ trợ quan sát lượng entity load/insert/update/delete, collection load/update/recreate/remove và query statistics tùy phiên bản.

Trong môi trường phù hợp, có thể lấy `SessionFactory` và `Statistics` bằng API Hibernate tương ứng. Đây là tính năng riêng của Hibernate, không phải API portable của JPA.

Các con số thống kê thường phản ánh hoạt động ở một session factory và có cách đếm riêng; không thay thế việc đọc SQL, execution plan hoặc đo thời gian database khi phân tích một mapping cụ thể.

### 15.3. Phân biệt số câu SQL với chi phí database

Nếu một transaction phát:

~~~sql
DELETE FROM user_profile_tags WHERE user_profile_id = 15;
~~~

đó chỉ là **một câu SQL**, nhưng nó có thể xóa hàng nghìn row. Vì vậy số SQL nhỏ không chắc chi phí nhỏ. Ngược lại, 100 INSERT được batch có thể có nhiều thao tác row nhưng ít round-trip.

Khi cần đánh giá performance, xem thêm index, khóa, row count, WAL/redo, CPU/I/O, lock wait, độ dài transaction và khối lượng dữ liệu trả về.

## 16. So sánh thiết kế của ba use case phổ biến

### 16.1. Tags của người dùng

Yêu cầu: mỗi user có một tập tag không trùng; thêm/bỏ từng tag thường xuyên; không có metadata riêng.

**Mapping phù hợp:** `@ElementCollection Set<String>` với bảng collection có PK `(user_id, tag)`.

**Dự kiến hành vi:** thêm/bỏ giá trị trong Set managed; provider có thể cập nhật riêng các link rows nếu schema/mapping hỗ trợ. DB unique constraint bảo vệ tính không trùng giữa các transaction.

### 16.2. Các dòng đơn hàng

Yêu cầu: mỗi dòng có ID, số lượng, giá, lifecycle thuộc đơn hàng; sửa số lượng thường xuyên.

**Mapping phù hợp:** entity `OrderLine`, `@ManyToOne` sở hữu FK, `@OneToMany(mappedBy = ..., orphanRemoval = true)` ở `PurchaseOrder` nếu child phụ thuộc owner.

**Dự kiến hành vi:** thay quantity dẫn tới UPDATE một child; thêm dòng INSERT child; bỏ dòng DELETE child theo orphanRemoval. Dù field trên parent là `List`, mapping này khác bag join table vô danh.

### 16.3. Playlist có thứ tự, cho phép bài hát trùng

Yêu cầu: playlist có thể chứa cùng một bài hát nhiều lần ở vị trí khác nhau; cần kéo-thả reorder.

**Mapping nên cân nhắc:** entity `PlaylistEntry` có ID riêng, `playlist_id`, `track_id`, `position` và constraint phù hợp; hoặc indexed list với `@OrderColumn` nếu hành vi update/index của provider thỏa nhu cầu.

**Không nên mặc định:** `@ManyToMany List<Track>` không có index rồi trông đợi SQL chỉ sửa một hàng và bảo toàn mọi occurrence theo vị trí.

## 17. Những sai lầm thường gặp

### 17.1. Coi `List`, `Set` và `Map` chỉ khác cú pháp Java

Chúng có semantics về trùng lặp, index, key và khả năng nhận diện hàng khác nhau. Chọn collection phải dựa trên domain và cách lưu dữ liệu, không chỉ vì `List` dễ thêm vào cuối.

### 17.2. Đặt `cascade = ALL` lên mọi association

Cascade REMOVE trên entity dùng chung có thể xóa đối tượng đầu kia. Orphan removal dùng với child phụ thuộc vòng đời owner, không nên áp dụng vô điều kiện. Chi phí SQL xóa cũng có thể lan rộng.

### 17.3. Không giữ hai phía quan hệ nhất quán

Chỉ sửa inverse collection trong quan hệ hai chiều có thể không cập nhật khóa ngoại/join table. Helper methods nên sửa owning side và đồng bộ object graph.

### 17.4. Dùng `equals/hashCode` chứa collection

Một `equals()` hoặc `hashCode()` tự sinh bao gồm các quan hệ lazy có thể gây truy vấn N+1, đệ quy vô hạn trong quan hệ hai chiều hoặc hash thay đổi khi thêm/bỏ phần tử. Với `Set`, việc hash thay đổi có thể làm `remove/contains` thất bại.

### 17.5. Thay hẳn wrapper managed bằng collection mới

Thao tác `setChildren(new HashSet<>(...))` có thể khiến Hibernate mất khả năng quản lý delta hoặc báo lỗi orphan collection tùy mapping. Dùng helper trên collection managed khi phù hợp.

### 17.6. Nghĩ Hibernate luôn làm diff từng hàng

Với một số bag/element collections không có khóa hàng ổn định, provider có thể xóa toàn bộ và chèn lại phần còn lại. Phải quan sát SQL thực tế.

### 17.7. Dùng `@OrderBy` để lưu thứ tự kéo-thả

`@OrderBy` sắp xếp khi đọc theo thuộc tính; `@OrderColumn` lưu vị trí. Reorder indexed list có thể phải update nhiều index.

### 17.8. Dùng `clear()` trên collection lớn để xóa một phần tử

`clear()` là xóa tất cả phần tử của collection trong bộ nhớ, không phải tối ưu thay đổi một item. Với orphanRemoval, có thể DELETE nhiều child; với bảng nối, có thể DELETE mọi link của owner.

### 17.9. Chạy bulk SQL rồi tiếp tục tin vào entity đã load

Bulk JPQL/native SQL không tự cập nhật persistence context. Phải quản lý flush/clear/refresh hoặc tách transaction cho nhất quán.

### 17.10. Tăng `hibernate.jdbc.batch_size` để giải quyết mọi vấn đề

Batching giảm round-trip, nhưng không loại bỏ write amplification do recreate hoặc UPDATE index hàng loạt. Trước tiên cần chọn mapping/schema phù hợp với thao tác thực tế.

## 18. Quy trình thiết kế và cập nhật collection

Khi gặp một collection mới trong entity, áp dụng thứ tự suy nghĩ:

1. **Xác định semantics:** có trùng không, có thứ tự không, có key hay metadata riêng không?
2. **Xác định phần tử:** entity độc lập, child thuộc owner, hay value object?
3. **Chọn mapping:** `@ManyToMany`, `@OneToMany/@ManyToOne`, `@ElementCollection` hoặc entity liên kết.
4. **Xác định owning side** và viết helper để duy trì object graph.
5. **Thiết kế khóa hàng:** PK/UNIQUE/FK/index để database nhận diện và bảo vệ liên kết.
6. **Chọn collection:** `Set` cho uniqueness, indexed `List` cho thứ tự, `Map` cho key, bag khi trùng lặp thực sự cần thiết và chi phí chấp nhận được.
7. **Quy định vòng đời:** cascade và orphanRemoval phải phù hợp domain.
8. **Cập nhật trên managed entity trong transaction**; không tùy tiện thay collection wrapper hay trộn bulk SQL.
9. **Đo số SELECT và write statements** khi thêm/bỏ một item, đổi thứ tự, `clear()` và sửa value.
10. **Đánh giá concurrency:** optimistic/pessimistic locking, unique constraint, rule tổng số, transaction retry.
11. **Tối ưu theo bottleneck thật:** cấu trúc bảng và row identity trước, batching và fetch sau.
12. **Xem xét lại mô hình nếu collection quá lớn:** entity liên kết, phân trang hoặc thao tác theo ID có thể phù hợp hơn.

### Bảng chọn nhanh

| Tình huống | Hướng ban đầu | Cảnh báo chính |
|---|---|---|
| Một đơn hàng có nhiều dòng riêng biệt | `@OneToMany(mappedBy)` + child `@ManyToOne` | Helper duy trì FK; orphanRemoval chỉ khi child thực sự phụ thuộc |
| Tập tag không trùng | `@ElementCollection Set<String>` | Constraint PK(owner, tag), equality và SQL provider |
| User tham gia nhiều Group dùng chung | `@ManyToMany Set<Group>` | Không cascade REMOVE endpoint |
| Playlist cần vị trí và cho phép trùng Track | `PlaylistEntry` entity hoặc indexed List | Reorder có thể UPDATE nhiều hàng |
| Các cài đặt theo khóa | `@ElementCollection Map<String,String>` | Map key ổn định, unique(owner, key) |
| Link có role/status/createdAt | Entity liên kết | Không ép metadata vào join table ẩn của @ManyToMany |
| Rất nhiều link, thao tác theo từng ID | Entity liên kết hoặc DML chuyên biệt | Không initialize toàn collection vô ích; tránh PC stale |

## 19. Bài tập vận dụng

### Bài 1 — Dirty checking và flush

Một `PurchaseOrder` managed chứa ba `OrderLine`. Trong transaction, bạn gọi `line.changeQuantity(5)` trên một child managed rồi `em.flush()`.

Hỏi:

- Đây là thay đổi scalar field hay thay đổi membership của collection?
- SQL thường tác động vào bảng nào?
- Sau flush có chắc transaction đã commit không?

**Gợi ý:** đây là cập nhật child entity; thường UPDATE `order_lines`. Flush không phải commit.

### Bài 2 — Set và bag trên bảng nối

Hai mapping đều liên kết Student với Course:

~~~java
@ManyToMany
private Set<Course> coursesSet;

@ManyToMany
private List<Course> coursesList;
~~~

Giả sử DB có bảng join và List không có `@OrderColumn`. Hãy giải thích vì sao không nên tự cho rằng hai mapping sẽ phát SQL y hệt khi xóa một Course, và dữ liệu nào cần quan sát.

**Gợi ý:** bag có thể chứa duplicate và thiếu định danh occurrence; provider có thể recreate collection. Quan sát SQL/row count, DB constraints và collection classification theo version.

### Bài 3 — Reorder playlist

Một playlist có 500 bài được lưu bằng `List<Track>` và cột `position`. Người dùng chuyển bài cuối lên đầu.

Hỏi vì sao có thể phát nhiều UPDATE index thay vì chỉ một UPDATE, và khi nào entity `PlaylistEntry` với position riêng có thể phù hợp hơn.

### Bài 4 — Thêm một phần tử vào Map

`UserProfile.settings` là `Map<String, String>` lưu theo bảng `(user_id, setting_key, setting_value)`. Bạn đổi key từ `theme` thành `ui.theme`.

Hỏi cần có constraint nào trên database, và vì sao thay key có thể là xóa row cũ/chèn row mới.

### Bài 5 — Replace collection và orphanRemoval

Một service tải `PurchaseOrder` managed rồi gọi `order.setLines(new ArrayList<>(dto.lines()))`. Mapping có `orphanRemoval = true`.

Hãy giải thích rủi ro mất wrapper, SQL xóa/chèn hàng loạt và cách sử dụng helper để cập nhật theo phần tử dựa trên ID.

### Bài 6 — Bulk DELETE và persistence context

Transaction đã load `order.lines`, sau đó gọi native DELETE xóa một `order_lines` row nhưng không refresh/clear context.

Hỏi vì sao collection Java có thể còn chứa child cũ và cách tổ chức transaction để tránh dùng dữ liệu stale.

### Bài 7 — Concurrency giới hạn chỗ

Một khóa học còn 1 chỗ. Hai người khác nhau cùng đăng ký; mỗi request đọc thấy 29/30 sinh viên.

Hỏi `Set<Student>` và unique(student, course) có tự ngăn vượt 30 không? Cần loại cơ chế đồng bộ nào cho rule tổng số?

**Gợi ý:** unique chỉ ngăn cặp trùng, không ngăn hai cặp khác nhau. Cần locking/constraint hoặc protocol capacity trong database.

## 20. Kết luận

**Một lời gọi `add()` hay `remove()` không có nghĩa JPA sẽ phát đúng một INSERT/DELETE.** Hibernate cần biết collection đang managed, owning side, snapshot, khóa từng hàng và kiểu semantics của `Set`, `List`, bag hoặc `Map` để quyết định SQL.

Những nguyên tắc nên nhớ:

- **Dirty checking** giúp đồng bộ thay đổi trong persistence context, nhưng SQL thực tế chỉ được tạo khi flush.
- **Phía sở hữu quan hệ** quyết định khóa ngoại hoặc join table được cập nhật thế nào; helper methods giữ hai phía Java nhất quán.
- `Set`, indexed `List`, bag và `Map` không tương đương; khác biệt về row identity và thứ tự có thể dẫn tới SQL delta hoặc recreate nhiều hàng.
- `@ElementCollection` chứa giá trị, không có entity ID riêng; khi phần tử thiếu định danh hàng ổn định, thay đổi nhỏ có thể tốn nhiều SQL.
- `@OneToMany` với child entity có PK và FK ở child thường dễ cập nhật theo từng hàng; `orphanRemoval` chỉ dùng khi child thật sự thuộc vòng đời parent.
- `@OrderColumn` lưu vị trí và có chi phí reorder; `@OrderBy` chỉ yêu cầu sắp xếp khi đọc.
- **Batching không chữa được mapping gây write amplification**; hãy xác định cấu trúc dữ liệu trước khi tối ưu round-trip.
- Native/bulk SQL có thể làm persistence context stale; concurrency còn cần ràng buộc, locking và transaction phù hợp.
- **Quan sát SQL, số row bị ảnh hưởng và thời gian thực tế** là cách kết luận chi phí của mapping cụ thể, không suy đoán từ một annotation.

Khi thiết kế collection JPA, hãy chọn mô hình phản ánh đúng nghiệp vụ và có khóa hàng rõ ràng ở database. Một quyết định nhỏ như `Set` so với bag, `@OrderColumn` hay entity liên kết có thể quyết định việc một thay đổi một phần tử tạo ra một câu DELETE hay hàng nghìn thao tác ghi.
