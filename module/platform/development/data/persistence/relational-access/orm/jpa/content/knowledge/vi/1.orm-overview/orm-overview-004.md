# JPA là đặc tả và vai trò của Jakarta Persistence

Khi một ứng dụng Java cần lưu dữ liệu vào cơ sở dữ liệu quan hệ, lập trình viên thường phải giải quyết hai mô hình khác nhau: **đối tượng Java** có thuộc tính, phương thức và quan hệ tham chiếu; trong khi **cơ sở dữ liệu quan hệ** tổ chức dữ liệu thành bảng, hàng, cột, khóa chính và khóa ngoại. Jakarta Persistence đưa ra một chuẩn chung để làm việc với dữ liệu bền vững trong Java, đặc biệt thông qua kỹ thuật ánh xạ đối tượng–quan hệ (Object–Relational Mapping, ORM).

Điểm cần nắm ngay từ đầu: **JPA là một đặc tả (specification), không phải một thư viện ORM hoàn chỉnh tự thực thi việc lưu dữ liệu.** Đặc tả quy định API, annotation và hành vi mà một *persistence provider* phải tuân thủ. Hibernate ORM, EclipseLink và các provider tương thích mới là những thành phần thực hiện thao tác với cơ sở dữ liệu.

## 1. Bài toán mà JPA giải quyết

Giả sử hệ thống có đối tượng Java biểu diễn một quyển sách:

~~~java
public class Book {
    private Long id;
    private String title;
    private java.math.BigDecimal price;
}
~~~

Trong cơ sở dữ liệu, thông tin tương ứng có thể nằm ở bảng:

~~~sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    price DECIMAL(12, 2) NOT NULL
);
~~~

Với JDBC thuần, ứng dụng thường phải tự viết câu SQL, truyền tham số, chạy truy vấn, đọc từng cột trong ResultSet và chuyển kết quả thành đối tượng. Ví dụ, đoạn đọc dữ liệu có thể cần các bước:

1. Mở kết nối đến cơ sở dữ liệu.
2. Chuẩn bị câu lệnh SELECT và gán tham số.
3. Thực thi câu lệnh, duyệt ResultSet.
4. Lấy giá trị từ cột id, title, price và tạo đối tượng Book.
5. Quản lý transaction, đóng tài nguyên và xử lý lỗi.

Khi số lượng thực thể tăng lên, thao tác ánh xạ lặp đi lặp lại, đặc biệt khi có quan hệ một–nhiều, nhiều–một hoặc nhiều–nhiều. JPA chuẩn hóa cách mô tả ánh xạ và cách thao tác với các đối tượng được quản lý, giúp ứng dụng tập trung hơn vào mô hình miền nghiệp vụ.

Điều này **không xóa bỏ SQL, JDBC hay thiết kế cơ sở dữ liệu**. Một provider JPA vẫn thường tạo và thực thi SQL thông qua JDBC; người phát triển vẫn cần hiểu khóa ngoại, chỉ mục, transaction và hiệu năng truy vấn.

## 2. JPA là gì? Vì sao gọi là Jakarta Persistence?

**JPA** ban đầu là viết tắt của *Java Persistence API*, tên quen thuộc từ hệ sinh thái Java EE. Sau khi nền tảng Java EE chuyển thành **Jakarta EE**, tên đặc tả hiện đại là **Jakarta Persistence**. Trong tài liệu, dự án và trao đổi kỹ thuật, người ta vẫn thường dùng chữ “JPA” để chỉ chuẩn này.

Một đặc tả định nghĩa **hợp đồng chung** giữa mã ứng dụng và các nhà cung cấp triển khai. Jakarta Persistence quy định, trong phạm vi chuẩn:

- Những annotation và metadata ánh xạ thực thể, thuộc tính, khóa và quan hệ.
- Các giao diện như EntityManager, EntityManagerFactory, EntityTransaction, Query và TypedQuery.
- Vòng đời thực thể và ngữ nghĩa của các thao tác persist, find, merge, remove, flush.
- Persistence context, cơ chế đồng bộ thay đổi với cơ sở dữ liệu và quy tắc nhận dạng thực thể.
- Ngôn ngữ truy vấn JPQL, Criteria API, các lựa chọn transaction và cấu hình persistence unit.

Để ứng dụng thật sự chạy được, cần có **một implementation/provider tương thích**, driver cơ sở dữ liệu và cơ sở dữ liệu đích. Chỉ thêm API Jakarta Persistence vào classpath chưa đủ để thực hiện truy vấn.

### Ba lớp cần phân biệt

~~~text
Mã ứng dụng Java
  ├── Entity: Book, Author, Order...
  ├── API: EntityManager, Query, annotation...
  └── Mã nghiệp vụ dùng hợp đồng Jakarta Persistence
                     │
                     ▼
           Jakarta Persistence
            (đặc tả/API chuẩn)
                     │
                     ▼
     Persistence provider tương thích
         (ví dụ: Hibernate ORM,
                  EclipseLink)
                     │
                     ▼
             JDBC / DataSource
                     │
                     ▼
            Cơ sở dữ liệu quan hệ
~~~

Sơ đồ thể hiện **vai trò logic**, không ngụ ý Jakarta Persistence là một tầng dịch vụ chạy độc lập ở giữa. Mã ứng dụng gọi API chuẩn; provider hiện thực API đó và phối hợp với JDBC hoặc hạ tầng kết nối để làm việc với cơ sở dữ liệu.

| Thành phần | Vai trò | Ví dụ |
| --- | --- | --- |
| Jakarta Persistence (JPA) | Đặc tả và API chuẩn về persistence/ORM | EntityManager, @Entity, JPQL |
| Persistence provider | Cài đặt đặc tả, quản lý thực thể và sinh/thực thi SQL | Hibernate ORM, EclipseLink |
| JDBC | API cấp thấp để kết nối và thực thi SQL với cơ sở dữ liệu | Connection, PreparedStatement |
| Cơ sở dữ liệu | Lưu dữ liệu thực tế, áp dụng ràng buộc và transaction | PostgreSQL, MySQL, H2 |
| Spring Data JPA | Tầng thư viện hỗ trợ repository dựa trên JPA, thuộc hệ sinh thái Spring | JpaRepository |

**Hibernate ORM không đồng nghĩa với JPA:** Hibernate có thể đóng vai trò provider JPA, đồng thời có API và tính năng riêng ngoài phạm vi chuẩn. **Spring Data JPA cũng không phải provider JPA:** thư viện này giảm mã viết cho tầng repository, nhưng vẫn cần provider bên dưới.

## 3. Vai trò cốt lõi của Jakarta Persistence trong ORM

### 3.1. Chuẩn hóa ánh xạ đối tượng sang bảng

Một lớp Java được đánh dấu @Entity có thể được ánh xạ tới một bảng. Các annotation giúp mô tả quy tắc ánh xạ một cách tường minh:

| Khái niệm quan hệ | Biểu diễn trong JPA |
| --- | --- |
| Bảng | @Entity, @Table |
| Hàng | Một instance của entity với định danh cụ thể |
| Khóa chính | @Id, có thể kết hợp @GeneratedValue |
| Cột | Thuộc tính entity, tùy chỉnh bằng @Column |
| Khóa ngoại, quan hệ | @ManyToOne, @OneToMany, @OneToOne, @ManyToMany, @JoinColumn |
| Thuộc tính không lưu | @Transient |
| Khóa phiên bản chống ghi đè đồng thời | @Version |

Annotation **mô tả ánh xạ**, không tự biến Java thành cơ sở dữ liệu và không đảm bảo bảng được tạo sẵn. Tạo schema có thể do công cụ migration, DBA hoặc tính năng sinh schema khi được cấu hình.

### 3.2. Quản lý vòng đời của entity

Một entity không chỉ là POJO chứa dữ liệu. Khi nằm trong **persistence context**, entity được provider quản lý: provider biết instance nào tương ứng với bản ghi nào và có thể phát hiện các thay đổi cần đồng bộ.

Các trạng thái thường gặp:

| Trạng thái | Ý nghĩa | Tình huống điển hình |
| --- | --- | --- |
| New / transient | Đối tượng mới, chưa thuộc persistence context | new Book(...) |
| Managed / persistent | Đang được EntityManager quản lý | Sau persist(...) hoặc find(...) |
| Detached | Đã từng được quản lý, hiện ở ngoài context | Sau detach(...), clear() hoặc đóng context |
| Removed | Đã được đánh dấu xóa trong context | Sau remove(...) với entity managed |

Ví dụ, khi lấy một Book bằng EntityManager.find(...), thay đổi giá qua setter trong transaction, provider có thể nhận biết thay đổi và phát lệnh UPDATE lúc đồng bộ. Đây thường được gọi là **dirty checking**.

### 3.3. Cung cấp API thống nhất để thao tác dữ liệu

EntityManager là giao diện trọng tâm để:

- **persist(entity):** đưa entity mới vào trạng thái managed và lên lịch chèn dữ liệu.
- **find(EntityClass, id):** tìm entity theo khóa chính.
- **merge(entity):** chuyển trạng thái từ đối tượng mới hoặc detached vào một instance managed và trả về instance đó.
- **remove(entity):** đánh dấu entity managed để xóa.
- **createQuery(...):** tạo truy vấn JPQL hoặc Criteria.
- **flush():** yêu cầu đồng bộ những thay đổi đang chờ xuống cơ sở dữ liệu.

Lưu ý: **flush không đồng nghĩa với commit**. SQL có thể đã được gửi xuống cơ sở dữ liệu trong transaction nhưng vẫn bị rollback. Thời điểm provider gửi từng câu SQL còn phụ thuộc chiến lược sinh khóa, chế độ flush và ngữ cảnh thực thi.

### 3.4. Định nghĩa ngôn ngữ truy vấn dựa trên entity

**JPQL (Jakarta Persistence Query Language)** truy vấn theo tên entity và tên thuộc tính Java thay vì trực tiếp theo tên bảng và cột:

~~~java
List<Book> books = em.createQuery(
        "SELECT b FROM Book b WHERE b.price >= :minimum ORDER BY b.title",
        Book.class)
    .setParameter("minimum", new BigDecimal("100000"))
    .getResultList();
~~~

Trong câu trên, Book là tên entity, còn price và title là thuộc tính của entity. Provider chuyển truy vấn thành SQL phù hợp với dialect cơ sở dữ liệu. Jakarta Persistence cũng hỗ trợ **Criteria API** để xây dựng truy vấn bằng đối tượng Java và **native SQL** khi cần khả năng đặc thù của hệ quản trị.

### 3.5. Tạo ranh giới chung giữa ứng dụng và provider

Vì mã nghiệp vụ chủ yếu dựa trên API và annotation chuẩn, ứng dụng có thể thay provider hoặc cơ sở dữ liệu với mức thay đổi hợp lý hơn so với khi phụ thuộc hoàn toàn vào API riêng. Tuy nhiên, **tính di động có giới hạn thực tế**: dialect SQL, hành vi sinh khóa, hàm truy vấn, hiệu năng, hỗ trợ tính năng và phần cấu hình riêng của provider vẫn có thể khác nhau.

## 4. Những khái niệm cấu thành một ứng dụng JPA

### Entity và định danh

Entity là lớp Java được ánh xạ để lưu trữ bền vững. Thông thường entity cần:

- Annotation @Entity hoặc khai báo tương đương qua XML.
- Một khóa chính được mô tả bằng @Id hoặc khóa phức hợp thích hợp.
- Constructor không tham số với mức truy cập public hoặc protected.
- Các quy tắc truy cập trường/getter và ánh xạ phù hợp.

Entity phản ánh **định danh nghiệp vụ/kỹ thuật** của một bản ghi. Vì vậy không nên mặc định sử dụng entity như DTO trả về mọi API; entity còn mang trạng thái và quan hệ do persistence context quản lý.

### Persistence unit

**Persistence unit** là một tập cấu hình logic mô tả các entity, provider và thông tin kết nối/transaction mà ứng dụng sử dụng. Trong Java SE hoặc cấu hình trực tiếp, nó thường được khai báo trong file META-INF/persistence.xml. Một ứng dụng có thể có nhiều persistence unit khi có nhu cầu tách nhóm entity hoặc nguồn dữ liệu.

### EntityManagerFactory và EntityManager

- **EntityManagerFactory:** tạo các EntityManager cho một persistence unit. Việc khởi tạo thường tốn chi phí nên thông thường factory được tái sử dụng và đóng khi ứng dụng dừng.
- **EntityManager:** thực hiện thao tác với entity và giữ/gắn với một persistence context. EntityManager **không an toàn để dùng đồng thời từ nhiều thread**; thường cấp theo request, transaction hoặc một đơn vị công việc.
- **Persistence context:** tập các entity managed cùng cơ chế nhận dạng và theo dõi thay đổi. Trong một context, hai lần tìm cùng kiểu entity và cùng khóa chính thường trả về cùng một instance managed.

### Transaction và tính nhất quán

Các thay đổi dữ liệu cần được thực hiện bên trong transaction để bảo đảm tính nguyên tử. Có hai kiểu quản lý thường gặp:

| Kiểu | Đặc điểm | Ngữ cảnh phổ biến |
| --- | --- | --- |
| RESOURCE_LOCAL | Ứng dụng quản lý transaction qua EntityTransaction | Ứng dụng Java SE, chương trình minh họa |
| JTA | Transaction được quản lý bởi hạ tầng/container hoặc transaction manager | Ứng dụng Jakarta EE và hệ thống có quản lý transaction tích hợp |

Trong môi trường Jakarta EE, EntityManager có thể được container tiêm và quản lý; khi đó cách tạo/đóng EntityManager và ranh giới transaction khác ví dụ Java SE bên dưới. API được dùng trong ứng dụng vẫn theo hợp đồng của Jakarta Persistence.

## 5. Ví dụ hoàn chỉnh: lưu và đọc Book với Jakarta Persistence

Ví dụ dùng **Java SE + Jakarta Persistence + Hibernate ORM (provider) + H2 (cơ sở dữ liệu trong bộ nhớ)**. Hibernate là một lựa chọn triển khai để minh họa rằng đặc tả cần provider; mã nghiệp vụ thao tác chủ yếu qua API Jakarta Persistence.

Giả sử cấu trúc mã nguồn:

~~~text
src/main/
├── java/com/example/persistence/
│   ├── Book.java
│   └── Demo.java
└── resources/
    └── META-INF/
        └── persistence.xml
~~~

Để chạy, dự án cần có **Jakarta Persistence API**, một phiên bản **Hibernate ORM hỗ trợ namespace jakarta.persistence**, và **H2 JDBC driver** tương thích. Phiên bản phụ thuộc phải được chọn đồng bộ; file XML bên dưới khai báo chuẩn Jakarta Persistence 3.x.

### Bước 1 — Định nghĩa entity

~~~java
package com.example.persistence;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.math.BigDecimal;

@Entity
@Table(name = "books")
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 200)
    private String title;

    @Column(nullable = false, precision = 12, scale = 2)
    private BigDecimal price;

    protected Book() {
        // Constructor không tham số mà JPA yêu cầu.
    }

    public Book(String title, BigDecimal price) {
        this.title = title;
        this.price = price;
    }

    public Long getId() {
        return id;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public BigDecimal getPrice() {
        return price;
    }

    public void setPrice(BigDecimal price) {
        this.price = price;
    }
}
~~~

Ý nghĩa của một số dòng quan trọng:

- **@Entity:** xác định Book là entity thuộc mô hình persistence.
- **@Table(name = "books"):** ánh xạ entity đến bảng books.
- **@Id:** đánh dấu khóa chính.
- **@GeneratedValue(strategy = IDENTITY):** yêu cầu cơ chế sinh khóa theo cột identity khi provider và cơ sở dữ liệu hỗ trợ.
- **@Column:** cấu hình ràng buộc cột và độ chính xác; ràng buộc dữ liệu thật sự còn phụ thuộc schema trong cơ sở dữ liệu.

Đặt @Id trên field khiến ví dụ này sử dụng **field access**: provider đọc/ghi trạng thái các field theo metadata ánh xạ; getter và setter phục vụ mã ứng dụng.

### Bước 2 — Khai báo persistence unit

Đặt file sau tại **src/main/resources/META-INF/persistence.xml**:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<persistence xmlns="https://jakarta.ee/xml/ns/persistence"
             version="3.0">
    <persistence-unit name="booksPU" transaction-type="RESOURCE_LOCAL">
        <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
        <class>com.example.persistence.Book</class>

        <properties>
            <property name="jakarta.persistence.jdbc.driver"
                      value="org.h2.Driver"/>
            <property name="jakarta.persistence.jdbc.url"
                      value="jdbc:h2:mem:books;DB_CLOSE_DELAY=-1"/>
            <property name="jakarta.persistence.jdbc.user" value="sa"/>
            <property name="jakarta.persistence.jdbc.password" value=""/>
            <property name="jakarta.persistence.schema-generation.database.action"
                      value="create"/>
        </properties>
    </persistence-unit>
</persistence>
~~~

Ở đây:

- **booksPU** là tên persistence unit mà chương trình sẽ tìm.
- **RESOURCE_LOCAL** cho phép ví dụ tự điều khiển transaction qua EntityTransaction.
- Dòng **provider** chỉ rõ implementation Hibernate; đây là chi tiết triển khai, không làm Hibernate trở thành định nghĩa của JPA.
- Các thuộc tính **jakarta.persistence.jdbc.*** cung cấp thông tin kết nối.
- **schema-generation.database.action=create** yêu cầu tạo schema trong môi trường demo. Không nên bật chế độ tự tạo hoặc xóa schema tùy tiện trên cơ sở dữ liệu sản xuất; dự án thực tế thường quản lý thay đổi schema bằng migration.

### Bước 3 — Persist, tìm kiếm, cập nhật và truy vấn

~~~java
package com.example.persistence;

import jakarta.persistence.EntityManager;
import jakarta.persistence.EntityManagerFactory;
import jakarta.persistence.EntityTransaction;
import jakarta.persistence.Persistence;
import java.math.BigDecimal;
import java.util.List;

public class Demo {
    public static void main(String[] args) {
        EntityManagerFactory emf =
                Persistence.createEntityManagerFactory("booksPU");

        try {
            EntityManager em = emf.createEntityManager();
            try {
                EntityTransaction tx = em.getTransaction();
                Long bookId;

                // INSERT: đưa entity mới vào persistence context.
                try {
                    tx.begin();
                    Book book = new Book(
                            "Nhap mon Jakarta Persistence",
                            new BigDecimal("129000.00"));
                    em.persist(book);
                    tx.commit();
                    bookId = book.getId();
                } catch (RuntimeException ex) {
                    if (tx.isActive()) {
                        tx.rollback();
                    }
                    throw ex;
                }

                // UPDATE: thay đổi entity managed trong transaction.
                try {
                    tx.begin();
                    Book managed = em.find(Book.class, bookId);
                    managed.setPrice(new BigDecimal("119000.00"));
                    tx.commit();  // Provider đồng bộ thay đổi khi cần.
                } catch (RuntimeException ex) {
                    if (tx.isActive()) {
                        tx.rollback();
                    }
                    throw ex;
                }

                // SELECT bằng JPQL: dùng tên entity và thuộc tính Java.
                List<Book> results = em.createQuery(
                                "SELECT b FROM Book b "
                                + "WHERE b.price >= :minimum "
                                + "ORDER BY b.title",
                                Book.class)
                        .setParameter(
                                "minimum", new BigDecimal("100000.00"))
                        .getResultList();

                for (Book book : results) {
                    System.out.println(
                            book.getId() + " | "
                            + book.getTitle() + " | "
                            + book.getPrice());
                }
            } finally {
                em.close();
            }
        } finally {
            emf.close();
        }
    }
}
~~~

Luồng thực thi chính:

1. **Persistence.createEntityManagerFactory("booksPU")** đọc cấu hình và khởi tạo provider cho persistence unit.
2. **em.persist(book)** khiến Book trở thành managed và được lưu trong transaction.
3. **em.find(Book.class, bookId)** lấy entity theo định danh; khi setter thay đổi price, provider có thể nhận biết và tạo UPDATE lúc flush/commit.
4. **createQuery(...)** tạo JPQL; provider chuyển thành SQL để lấy dữ liệu.
5. **em.close()** và **emf.close()** giải phóng tài nguyên khi hoàn tất.

Khi sử dụng chiến lược IDENTITY, việc sinh id có thể khiến provider thực thi INSERT sớm hơn thời điểm commit. Ví dụ vẫn cần transaction và xử lý rollback để có ý nghĩa nhất quán.

## 6. Persistence context: cơ chế quan trọng hơn các annotation

Một lỗi hiểu nhầm phổ biến là nghĩ JPA chỉ giúp tránh tự viết INSERT/UPDATE/SELECT. Giá trị lớn của mô hình nằm ở **việc provider quản lý trạng thái đối tượng trong persistence context**.

Xét trình tự:

~~~java
Book first = em.find(Book.class, 10L);
Book second = em.find(Book.class, 10L);

System.out.println(first == second);
// Thông thường là true nếu cả hai đang được quản lý
// trong cùng một persistence context.
~~~

Nếu cùng context đã chứa entity Book với id = 10, provider có thể trả về instance đang managed thay vì tạo một bản sao không liên quan. Điều này hỗ trợ tính nhất quán giữa các tham chiếu trong một đơn vị công việc.

Khi entity còn managed, gọi setter trong transaction có thể đủ để provider phát hiện thay đổi. Sau khi entity chuyển sang **detached**, thay đổi trên đối tượng đó không được tự động theo dõi nữa. Lúc cần đưa trạng thái detached trở lại context, có thể dùng **merge**, nhưng phải nhớ:

~~~java
Book managedCopy = em.merge(detachedBook);
// managedCopy mới là instance managed được trả về.
// Không mặc định coi detachedBook đã trở thành managed.
~~~

Không nên giữ EntityManager hoặc entity managed lâu hơn phạm vi công việc cần thiết. Context quá lớn có thể khiến việc theo dõi thay đổi tốn bộ nhớ, khó hiểu transaction và phát sinh truy vấn ngoài dự kiến.

## 7. Quan hệ thực thể, tải dữ liệu và transaction

Trong thực tế, một Book có thể thuộc về một Author. JPA cung cấp annotation để biểu diễn quan hệ:

~~~java
// Đoạn minh họa đặt bên trong entity Book;
// giả sử đã định nghĩa entity Author với khóa chính phù hợp.
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "author_id", nullable = false)
private Author author;
~~~

Annotation **@ManyToOne** biểu diễn nhiều sách tham chiếu đến một tác giả, còn **@JoinColumn** xác định cột khóa ngoại. Với quan hệ hai chiều, phải hiểu phía sở hữu quan hệ (owning side) và cách đồng bộ hai phía trong mã Java.

JPA cũng quy định cách tải quan hệ **EAGER** hoặc **LAZY**, nhưng cách provider sinh SQL phụ thuộc truy vấn và ánh xạ. Chẳng hạn, truy cập lần lượt tác giả của hàng trăm cuốn sách có thể tạo vấn đề **N+1 queries**. Có thể xử lý bằng truy vấn join fetch, entity graph hoặc thiết kế truy vấn phù hợp:

~~~java
List<Book> books = em.createQuery(
        "SELECT b FROM Book b JOIN FETCH b.author",
        Book.class).getResultList();
~~~

Đây là ví dụ truy vấn cho mô hình có quan hệ Book–Author như mô tả trên; không phải phần của ví dụ Book độc lập ở mục 5.

Cần phân biệt:

- **Fetch:** quyết định khi nào dữ liệu liên quan được nạp.
- **Cascade:** quyết định thao tác trên một entity có được lan tới entity liên quan hay không.
- **Transaction:** xác định ranh giới nguyên tử và khả năng commit/rollback các thay đổi.

Đánh dấu quan hệ LAZY không bảo đảm truy cập ở mọi nơi đều thành công. Nếu entity đã detached và dữ liệu liên quan chưa được tải, thao tác truy cập có thể thất bại tùy provider. Vì vậy nên tải dữ liệu cần thiết khi context còn hợp lệ và chọn DTO/projection phù hợp cho tầng API.

## 8. Jakarta Persistence và Jakarta EE

Jakarta Persistence là **một đặc tả trong hệ sinh thái Jakarta EE**, nhưng không bắt buộc toàn bộ ứng dụng phải chạy trong application server. Nó có thể được dùng:

| Môi trường | Cách dùng thường gặp |
| --- | --- |
| Java SE | Tạo EntityManagerFactory bằng Persistence, quản lý EntityManager và RESOURCE_LOCAL transaction trực tiếp |
| Jakarta EE | Container hỗ trợ quản lý persistence context, tiêm EntityManager và tích hợp JTA |
| Spring / Spring Boot | Framework cấu hình provider, quản lý transaction và có thể kết hợp Spring Data JPA |

Vai trò của Jakarta Persistence trong Jakarta EE là tạo **chuẩn persistence chung** để nhiều framework, thư viện và application server có thể làm việc với entity và provider theo hợp đồng ổn định. Nó bổ sung cho các đặc tả khác như Jakarta Transactions; bản thân Jakarta Persistence không thay thế transaction manager hay database engine.

## 9. Chuyển từ Java Persistence API sang Jakarta Persistence

Một thay đổi thực tế dễ gặp là **namespace của API**:

~~~java
// Dự án JPA/Java EE thế hệ cũ:
import javax.persistence.Entity;
import javax.persistence.EntityManager;

// Dự án Jakarta Persistence thế hệ mới:
import jakarta.persistence.Entity;
import jakarta.persistence.EntityManager;
~~~

Đoạn trên chỉ nhằm so sánh tên package; trong một file nguồn thực tế phải chọn **một bộ import tương thích** với phiên bản framework và provider. Không thể giả định thay chuỗi javax thành jakarta là đủ để nâng cấp mọi ứng dụng. Cần đồng bộ dependency, provider, framework, cấu hình XML và API liên quan.

Ở cả hai thế hệ, nguyên tắc kiến trúc vẫn giống nhau: **đặc tả xác định API và hành vi; provider hiện thực việc lưu và truy vấn dữ liệu**.

## 10. Phạm vi của JPA và những điều vẫn phải tự thiết kế

JPA hữu ích khi ứng dụng có mô hình thực thể rõ ràng và cần thao tác dữ liệu quan hệ theo cách nhất quán. Tuy nhiên, đặc tả không tự giải quyết mọi yêu cầu hệ thống:

| JPA hỗ trợ | Lập trình viên vẫn cần quyết định |
| --- | --- |
| Ánh xạ entity và quan hệ | Thiết kế bảng, ràng buộc, chỉ mục và mô hình domain |
| Quản lý persistence context | Phạm vi transaction, thời điểm tải dữ liệu và giới hạn bộ nhớ |
| JPQL và Criteria API | Truy vấn nào phù hợp, cách phân trang, tránh N+1 |
| Đồng bộ thay đổi managed entity | Xử lý xung đột cập nhật, khóa lạc quan/bi quan khi cần |
| API tương đối độc lập với provider | Chọn provider, phiên bản, dialect và phần mở rộng riêng |
| Khả năng sinh schema theo cấu hình | Chính sách migration, backup và vận hành database |

Đối với thao tác SQL tối ưu chuyên biệt, báo cáo phức tạp hoặc xử lý hàng loạt, việc dùng native SQL, JDBC hay công cụ khác có thể phù hợp hơn. JPA và JDBC có thể cùng tồn tại trong một ứng dụng; quyết định nên dựa trên yêu cầu truy vấn, tính nhất quán và chi phí vận hành.

## 11. Tự kiểm tra mức hiểu

**Tình huống 1:** Dự án chỉ khai báo dependency jakarta.persistence-api nhưng chưa có provider. Liệu EntityManager có chạy được không?

**Giải thích:** API cung cấp kiểu và hợp đồng; cần một provider thực thi tương thích cùng hạ tầng truy cập dữ liệu để thực sự tạo EntityManager và truy vấn cơ sở dữ liệu.

**Tình huống 2:** Gọi setter thay đổi giá Book vừa lấy bằng find(...) nhưng chưa gọi persist(...). Liệu thay đổi có thể được lưu?

**Giải thích:** Có, nếu Book vẫn đang managed trong persistence context, thay đổi xảy ra trong transaction và provider đồng bộ trước hoặc khi commit. Persist chủ yếu dành cho entity mới.

**Tình huống 3:** Gọi flush() xong có đồng nghĩa dữ liệu đã commit vĩnh viễn?

**Giải thích:** Không. Flush đồng bộ trạng thái pending với cơ sở dữ liệu trong transaction; transaction vẫn có thể rollback.

**Tình huống 4:** Thay Hibernate bằng một provider tương thích khác có chắc chắn không phải sửa gì?

**Giải thích:** Không chắc. Mã sử dụng API chuẩn có tính di động cao hơn, nhưng cấu hình provider, dialect, tính năng mở rộng và hành vi hiệu năng có thể cần điều chỉnh.

## Kết luận

**Jakarta Persistence (thường gọi là JPA) là đặc tả chuẩn cho persistence trong Java, tập trung vào ánh xạ đối tượng–quan hệ và quản lý vòng đời entity.** Đặc tả định nghĩa các annotation, API, persistence context, truy vấn và hành vi transaction. **Provider** như Hibernate ORM hoặc EclipseLink hiện thực hợp đồng đó và tương tác với cơ sở dữ liệu qua hạ tầng phù hợp.

Khi học ORM, hãy luôn tách bạch ba câu hỏi: **JPA quy định điều gì? Provider thực hiện điều đó ra sao? Cơ sở dữ liệu thực sự lưu và truy vấn dữ liệu như thế nào?** Hiểu rõ ba lớp này sẽ giúp đọc cấu hình, chẩn đoán lỗi và tối ưu ứng dụng một cách có cơ sở.
