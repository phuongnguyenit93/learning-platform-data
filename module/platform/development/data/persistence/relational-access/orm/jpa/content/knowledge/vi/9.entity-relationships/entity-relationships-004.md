# Mối liên hệ giữa khóa ngoại, JoinColumn và bảng liên kết trong JPA

Khi hai đối tượng Java có quan hệ với nhau, chẳng hạn một `Employee` thuộc một `Department`, ta có thể viết một trường tham chiếu:

~~~java
private Department department;
~~~

Nhưng trong cơ sở dữ liệu quan hệ, một hàng trong bảng `employees` không chứa nguyên đối tượng `Department`. Quan hệ thường được biểu diễn bằng **khóa ngoại (foreign key, FK)** hoặc thông qua **bảng liên kết (join table/association table)**. Jakarta Persistence (JPA) cung cấp `@JoinColumn` và `@JoinTable` để mô tả cách các tham chiếu Java tương ứng với các cột và bảng đó.

Ba khái niệm dễ bị nhầm nhất là:

- **Foreign key** là cấu trúc và ràng buộc ở **cơ sở dữ liệu**, bảo đảm giá trị tham chiếu tồn tại theo quy tắc schema.
- **`@JoinColumn`** là metadata của **JPA**, mô tả cột dùng để nối một quan hệ giữa các entity; annotation tự nó không phải một foreign key vật lý.
- **`@JoinTable`** là metadata JPA mô tả **một bảng trung gian** chứa các cột liên kết hai phía; bảng đó có thể có các FK và ràng buộc khác trong database.

Hiểu đúng quan hệ giữa ba khái niệm này giúp thiết kế quan hệ một–một, một–nhiều và nhiều–nhiều, xác định phía sở hữu quan hệ, tránh lưu trùng và xử lý lỗi ràng buộc một cách nhất quán.

## 1. Từ tham chiếu Java sang cấu trúc quan hệ

Giả sử doanh nghiệp có một phòng ban với nhiều nhân viên:

~~~text
Đối tượng Java                        Bảng quan hệ
----------------------------         --------------------------------
Department(id=10)                     departments
    |                                 +----+-----------+
    +-- Employee(id=101)              | id | name      |
    +-- Employee(id=102)              +----+-----------+
                                      | 10 | Sales     |
                                      +----+-----------+

                                      employees
                                      +-----+------+---------------+
                                      | id  | name | department_id |
                                      +-----+------+---------------+
                                      | 101 | An   | 10            |
                                      | 102 | Binh | 10            |
                                      +-----+------+---------------+
                                                   |
                                                   +--> departments.id
~~~

Trong mô hình trên:

1. Trường `Employee.department` diễn tả quan hệ tham chiếu bằng **ngôn ngữ đối tượng**.
2. Cột `employees.department_id` mang **giá trị khóa** của phòng ban được tham chiếu.
3. Ràng buộc `FOREIGN KEY (department_id) REFERENCES departments(id)` do **DBMS** thực thi.
4. `@ManyToOne` mô tả **bội số của quan hệ**; `@JoinColumn(name = "department_id")` mô tả **cột nối**.

Trong trường hợp này, hai nhân viên có thể cùng mang `department_id = 10`; do đó cột FK ở bảng `employees` **không được đặt UNIQUE** nếu muốn duy trì quan hệ nhiều–một.

### SQL minh họa

~~~sql
CREATE TABLE departments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE employees (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    department_id BIGINT NOT NULL,
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id) REFERENCES departments(id)
);

CREATE INDEX idx_employees_department_id
    ON employees(department_id);
~~~

Ví dụ DDL dùng cú pháp PostgreSQL. Ràng buộc FK bảo đảm không thể lưu `department_id = 999` khi phòng ban 999 không tồn tại, trong giới hạn quy tắc và transaction của database. Index cho FK được đưa ra riêng để hỗ trợ truy vấn và một số thao tác kiểm tra liên kết; **không phải DBMS nào cũng tự tạo index cho cột FK**.

## 2. Ba câu hỏi cần trả lời trước khi chọn annotation

Mỗi quan hệ entity cần làm rõ:

| Câu hỏi | Các lựa chọn | Tác động |
| --- | --- | --- |
| **Bội số?** | `@OneToOne`, `@OneToMany`, `@ManyToOne`, `@ManyToMany` | Quy định mỗi bên có thể tham chiếu bao nhiêu đối tượng |
| **Lưu liên kết ở đâu?** | FK trong một bảng entity, hoặc cột FK trong bảng liên kết | Quyết định dùng `@JoinColumn` hay `@JoinTable` và cách thiết kế schema |
| **Phía nào sở hữu quan hệ?** | Owning side và, nếu có, inverse side với `mappedBy` | Quyết định thay đổi phía nào được provider dùng để ghi liên kết |

Ví dụ, `Department.employees` là một collection không đủ để cho biết liệu database sử dụng `employees.department_id` hay bảng `department_employees`. Cần xem toàn bộ mapping.

**Bội số quan hệ là khái niệm domain; vị trí FK là một quyết định lưu trữ.** Hai quan hệ có cùng bội số vẫn có thể chọn cấu trúc bảng khác nhau nếu JPA hỗ trợ và có lý do thiết kế.

## 3. `@ManyToOne` và `@JoinColumn`: khóa ngoại nằm ở phía “nhiều”

Đây là mẫu rất thường gặp trong JPA: mỗi nhân viên thuộc một phòng ban, nhưng một phòng ban có thể có nhiều nhân viên.

~~~java
package com.example.persistence;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "employees")
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 150)
    private String fullName;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "department_id", nullable = false)
    private Department department;

    protected Employee() {
    }

    public Employee(String fullName, Department department) {
        this.fullName = fullName;
        this.department = department;
    }

    public Long getId() {
        return id;
    }

    public Department getDepartment() {
        return department;
    }

    public void setDepartment(Department department) {
        this.department = department;
    }
}
~~~

Entity `Department`:

~~~java
package com.example.persistence;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "departments")
public class Department {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String name;

    protected Department() {
    }

    public Department(String name) {
        this.name = name;
    }

    public Long getId() {
        return id;
    }
}
~~~

Giải thích:

- `@ManyToOne` cho biết nhiều hàng `Employee` có thể tham chiếu một `Department`.
- `@JoinColumn(name = "department_id")` nói rằng cột liên kết ở **bảng employees** mang tên `department_id`.
- Theo mặc định, cột nối tham chiếu khóa chính của entity đích. Vì `Department` có PK là `id`, liên kết hướng đến `departments.id`.
- `optional = false` mô tả rằng quan hệ không nên có giá trị `null` theo ngữ nghĩa JPA.
- `nullable = false` là metadata cho cột khi sinh schema; **constraint NOT NULL phải thực sự có trong database** nếu muốn bảo vệ dữ liệu từ mọi đường ghi.
- `fetch = FetchType.LAZY` yêu cầu nạp tham chiếu theo cơ chế lazy khi provider hỗ trợ. Nó không thay đổi vị trí FK và không bảo đảm tuyệt đối thời điểm mỗi câu SELECT.

Nếu không khai báo `@JoinColumn`, JPA có quy tắc đặt tên mặc định theo thuộc tính quan hệ và cột khóa được tham chiếu, nhưng các naming strategy của provider có thể thay đổi tên vật lý. Trong dự án quản lý schema bằng migration, khai báo rõ tên cột nối giúp giảm sai lệch.

## 4. Quan hệ hai chiều: `mappedBy` và owning side

Khi cần từ phòng ban truy cập danh sách nhân viên, thêm quan hệ ngược:

~~~java
import jakarta.persistence.Entity;
import jakarta.persistence.OneToMany;
import java.util.ArrayList;
import java.util.List;

@Entity
public class Department {
    // Các field id, name và constructor như ví dụ trước.

    @OneToMany(mappedBy = "department")
    private List<Employee> employees = new ArrayList<>();
}
~~~

Ở ví dụ này, phần code được rút gọn để tập trung vào annotation; khi dùng thực tế, cần giữ nguyên định nghĩa đầy đủ của `Department` từ mục 3.

**Ý nghĩa của `mappedBy = "department"`:**

- `department` là **tên field/property Java ở entity Employee**, không phải tên cột `department_id`.
- `Employee.department` là **owning side**, vì field này xác định giá trị FK sẽ lưu.
- `Department.employees` là **inverse side** của cùng một quan hệ.
- Một quan hệ hai chiều này tương ứng **một FK `employees.department_id`**, không tạo thêm FK hoặc bảng liên kết mới.

~~~text
Department                              Employee
---------------------                   ---------------------------
employees: List<Employee>               department: Department
@OneToMany(mappedBy="department")        @ManyToOne
         │                               @JoinColumn("department_id")
         │                                      │
         +------- cùng một quan hệ -------------+
                                                │
                                             FK tại DB
                                       employees.department_id
~~~

### Tại sao phải giữ hai phía đồng bộ trong Java?

Giả sử:

~~~java
Department dept = em.find(Department.class, 10L);
Employee employee = new Employee("An", dept);
em.persist(employee);
~~~

Quan hệ được ghi qua `employee.department`. Nếu bộ sưu tập `dept.getEmployees()` đã được nạp trong cùng persistence context, nó không tự bảo đảm phản ánh mọi thao tác sửa tham chiếu nếu ứng dụng chỉ sửa một phía.

Một phương thức hỗ trợ có thể được đặt trong `Department`:

~~~java
public void addEmployee(Employee employee) {
    employees.add(employee);
    employee.setDepartment(this);
}
~~~

Đây là ví dụ tối giản khi thêm nhân viên mới. Với chức năng chuyển nhân viên giữa phòng ban, mã thực tế còn cần gỡ nhân viên khỏi collection cũ, tránh thêm trùng và duy trì bất biến quan hệ trong bộ nhớ. **Chỉ thêm vào collection ở inverse side mà không cập nhật owning side không phải cách đáng tin cậy để thay đổi FK**.

### Quy tắc owning side

Với quan hệ hai chiều theo mẫu FK này, **phía mang `@ManyToOne` và `@JoinColumn` sở hữu quan hệ**. Phía mang `@OneToMany(mappedBy = "...")` là phía ngược.

`mappedBy` không tạo khóa ngoại và không chỉ tên cột SQL. Nó chỉ ra **thuộc tính Java** đã được ánh xạ làm phía sở hữu.

## 5. `@OneToMany` một chiều: tại sao có thể cần bảng liên kết?

Không phải quan hệ nào cũng có `Employee.department`. Ứng dụng có thể muốn chỉ truy cập từ phòng ban sang nhân viên:

~~~java
@Entity
public class Department {
    @Id
    private Long id;

    @OneToMany
    private List<Employee> employees = new ArrayList<>();

    protected Department() {
    }
}
~~~

Trong quan hệ **một chiều** như vậy, không có field quan hệ ngược trên `Employee`. Theo ánh xạ mặc định của JPA, provider có thể sử dụng **join table** cho unidirectional one-to-many. Nếu muốn FK đặt trực tiếp ở bảng con, có thể khai báo tường minh `@JoinColumn` trên collection:

~~~java
@OneToMany
@JoinColumn(name = "department_id")
private List<Employee> employees = new ArrayList<>();
~~~

Khi đó JPA mô tả cột `employees.department_id` dù entity `Employee` không có field `department` tương ứng. Đây vẫn là quan hệ một chiều ở tầng Java.

| Cách ánh xạ | Lưu liên kết ở đâu? | Khi nào cân nhắc? |
| --- | --- | --- |
| `@OneToMany(mappedBy = "department")` + `@ManyToOne` | FK trong bảng nhân viên | Khi cần điều hướng hai phía và muốn owning side rõ |
| `@OneToMany @JoinColumn(name = "department_id")` | FK trong bảng nhân viên | Khi chỉ muốn điều hướng từ cha đến con |
| `@OneToMany @JoinTable(...)` | Bảng liên kết | Khi muốn tách liên kết khỏi bảng entity con |

Với `@OneToMany @JoinColumn`, provider có thể phải thực thi các câu SQL bổ sung để đồng bộ FK tùy chiến lược ghi và tình huống. Không nên mặc định cấu trúc một chiều sẽ có hành vi SQL giống hệt quan hệ hai chiều.

**Điểm dễ nhầm:** `@OneToMany` không mặc nhiên có nghĩa database phải chứa một join table. Ngược lại, `@JoinTable` cũng không đồng nghĩa quan hệ chắc chắn là `@ManyToMany`.

## 6. `@OneToOne`: khóa ngoại cần ràng buộc duy nhất

Giả sử mỗi khách hàng có tối đa một hồ sơ mở rộng, và mỗi hồ sơ thuộc đúng một khách hàng. Có thể lưu FK trong bảng hồ sơ:

~~~java
package com.example.persistence;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.OneToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "customer_profiles")
public class CustomerProfile {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(
        name = "customer_id",
        nullable = false,
        unique = true)
    private Customer customer;

    @Column(name = "display_bio", length = 500)
    private String displayBio;

    protected CustomerProfile() {
    }
}
~~~

Giả sử `Customer` là một entity có PK `Long id`. DDL tương ứng:

~~~sql
CREATE TABLE customer_profiles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL UNIQUE,
    display_bio VARCHAR(500),
    CONSTRAINT fk_customer_profiles_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);
~~~

Khác biệt với `@ManyToOne` nằm ở **ràng buộc UNIQUE trên FK**:

- Nếu không UNIQUE, nhiều hồ sơ vẫn có thể tham chiếu cùng khách hàng ở tầng database: quan hệ vật lý sẽ cho phép nhiều–một.
- Khi FK UNIQUE, tối đa một hồ sơ có thể tham chiếu một khách hàng.
- Nếu FK `NOT NULL`, mỗi hồ sơ buộc phải tham chiếu khách hàng hợp lệ.

**`@OneToOne` và `@JoinColumn(unique = true)` mô tả ý định mapping; constraint vật lý trong DB mới là cơ chế bảo vệ dữ liệu với mọi tác nhân ghi.**

### Quan hệ một–một hai chiều

Ở entity `Customer` có thể thêm:

~~~java
@OneToOne(mappedBy = "customer")
private CustomerProfile profile;
~~~

`CustomerProfile.customer` vẫn là owning side vì giữ FK. `mappedBy = "customer"` dẫn đến field Java bên kia. Khi thay đổi quan hệ, nên duy trì hai tham chiếu nhất quán trong bộ nhớ và thay đổi owning side để provider ghi đúng FK.

### Một–một có khóa chính dùng chung

Trong một số mô hình, bảng hồ sơ có thể dùng ngay `customer_id` làm cả **PK và FK**:

~~~sql
CREATE TABLE customer_settings (
    customer_id BIGINT PRIMARY KEY,
    language_code VARCHAR(10) NOT NULL,
    CONSTRAINT fk_customer_settings_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);
~~~

JPA có thể ánh xạ bằng `@MapsId`:

~~~java
@Entity
@Table(name = "customer_settings")
public class CustomerSettings {

    @Id
    private Long customerId;

    @MapsId
    @OneToOne(optional = false)
    @JoinColumn(name = "customer_id")
    private Customer customer;

    @Column(name = "language_code", nullable = false)
    private String languageCode;

    protected CustomerSettings() {
    }
}
~~~

Ở đây, ID của `CustomerSettings` được lấy từ entity `Customer` liên kết. Không cần một surrogate ID thứ hai cho bảng settings. Mẫu **shared primary key** phù hợp khi vòng đời và định danh của đối tượng phụ phụ thuộc chặt vào đối tượng chính.

## 7. `@ManyToMany`: bảng liên kết mang hai khóa ngoại

Một tài khoản người dùng có nhiều vai trò; một vai trò có thể được gán cho nhiều tài khoản. Nếu để `user_id` ngay trong bảng `roles`, mỗi role chỉ có thể liên kết một user tại một thời điểm, sai với nghiệp vụ. Nếu đặt danh sách role ID dạng chuỗi trong bảng users, database sẽ khó áp dụng FK và truy vấn quan hệ.

Giải pháp thông thường là **join table**:

~~~text
user_accounts           user_roles                roles
-------------           -------------------       ----------------
id | username           user_id | role_id         id | name
10 | an                 ------- | -------         1  | ADMIN
20 | binh               10      | 1               2  | EDITOR
                        10      | 2
                        20      | 2

                         |         |
                         v         v
                     users.id    roles.id
~~~

Bảng `user_roles` có hai cột FK. Một cặp `(user_id, role_id)` biểu diễn **một liên kết**; thông thường cần ràng buộc PRIMARY KEY hoặc UNIQUE trên cặp để tránh gán trùng.

### DDL

~~~sql
CREATE TABLE user_accounts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE roles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    role_name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE user_roles (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    PRIMARY KEY (user_id, role_id),
    CONSTRAINT fk_user_roles_user
        FOREIGN KEY (user_id) REFERENCES user_accounts(id),
    CONSTRAINT fk_user_roles_role
        FOREIGN KEY (role_id) REFERENCES roles(id)
);

CREATE INDEX idx_user_roles_role_id ON user_roles(role_id);
~~~

### JPA ở phía sở hữu

~~~java
package com.example.persistence;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.JoinTable;
import jakarta.persistence.ManyToMany;
import jakarta.persistence.Table;
import java.util.HashSet;
import java.util.Set;

@Entity
@Table(name = "user_accounts")
public class UserAccount {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String username;

    @ManyToMany
    @JoinTable(
        name = "user_roles",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "role_id")
    )
    private Set<Role> roles = new HashSet<>();

    protected UserAccount() {
    }

    public Set<Role> getRoles() {
        return roles;
    }
}
~~~

Phía còn lại có thể là:

~~~java
package com.example.persistence;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.ManyToMany;
import jakarta.persistence.Table;
import java.util.HashSet;
import java.util.Set;

@Entity
@Table(name = "roles")
public class Role {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String roleName;

    @ManyToMany(mappedBy = "roles")
    private Set<UserAccount> users = new HashSet<>();

    protected Role() {
    }
}
~~~

Ý nghĩa các phần trong `@JoinTable`:

- `name = "user_roles"`: tên **bảng trung gian**.
- `joinColumns = @JoinColumn(name = "user_id")`: cột trong bảng trung gian tham chiếu **entity ở owning side**, tức `UserAccount`.
- `inverseJoinColumns = @JoinColumn(name = "role_id")`: cột trong bảng trung gian tham chiếu **entity phía bên kia**, tức `Role`.
- `Role.users` có `mappedBy = "roles"` vì `UserAccount.roles` là thuộc tính Java sở hữu quan hệ.

**`joinColumns` và `inverseJoinColumns` luôn được hiểu tương đối theo phía đặt `@JoinTable`.** Đổi owning side có thể làm vai trò hai nhóm cột đảo lại, mặc dù tên bảng vẫn giữ nguyên.

Khi ứng dụng thực hiện:

~~~java
userAccount.getRoles().add(existingRole);
~~~

nếu `userAccount` là entity managed và hoạt động trong transaction thích hợp, provider có thể đồng bộ liên kết bằng một dòng mới trong `user_roles`. Việc sửa riêng `Role.users` ở inverse side không đảm bảo sinh ra thay đổi như mong đợi. Với quan hệ hai chiều, nên đồng bộ cả hai collection trong bộ nhớ bằng các phương thức nghiệp vụ phù hợp.

## 8. Bảng liên kết không chỉ dành cho quan hệ nhiều–nhiều

Một join table đơn giản là một bảng chứa cột khóa của hai phía. Nó có thể dùng cho nhiều kiểu quan hệ JPA khác nhau.

### 8.1. One-to-many qua join table

Giả sử một bộ sưu tập có nhiều hiện vật, nhưng mỗi hiện vật chỉ được gắn vào **tối đa một** bộ sưu tập tại một thời điểm. Nếu không muốn cột `collection_id` trong bảng hiện vật, có thể tạo bảng trung gian:

~~~java
@OneToMany
@JoinTable(
    name = "collection_artifacts",
    joinColumns = @JoinColumn(name = "collection_id"),
    inverseJoinColumns = @JoinColumn(name = "artifact_id", unique = true)
)
private List<Artifact> artifacts = new ArrayList<>();
~~~

DDL minh họa:

~~~sql
CREATE TABLE collection_artifacts (
    collection_id BIGINT NOT NULL,
    artifact_id BIGINT NOT NULL UNIQUE,
    FOREIGN KEY (collection_id) REFERENCES collections(id),
    FOREIGN KEY (artifact_id) REFERENCES artifacts(id)
);
~~~

Ở đây, `UNIQUE(artifact_id)` giữ ý nghĩa **mỗi hiện vật không thể đồng thời thuộc hai collection**. Nếu bỏ ràng buộc và cho phép một hiện vật xuất hiện ở nhiều collection, cấu trúc vật lý sẽ hỗ trợ quan hệ nhiều–nhiều, khác với cardinality được JPA khai báo.

### 8.2. One-to-one qua join table

Một quan hệ một–một cũng có thể dùng join table khi schema có lý do tách bảng liên kết khỏi cả hai entity. Khi đó thường phải bảo đảm **cả khóa của phía A lẫn khóa của phía B đều duy nhất** trong bảng liên kết. Tuy vậy, một FK UNIQUE trực tiếp hoặc shared PK thường đơn giản hơn.

### 8.3. Vì sao không mặc định luôn dùng join table?

Join table thêm một bảng và thường thêm ít nhất hai khóa ngoại cùng các index. Nó hữu ích khi:

- Quan hệ thật sự nhiều–nhiều.
- Không muốn thêm cột FK vào bảng entity hiện hữu.
- Cần quản lý liên kết tách biệt trong schema đang có.
- Cần thiết kế quan hệ theo cách mà một bảng trung gian thể hiện rõ tính duy nhất.

Với quan hệ nhiều–một phổ biến, FK trực tiếp ở bảng phía nhiều thường dễ đọc và ít join hơn. Quyết định nên theo domain, schema và nhu cầu truy vấn, không chỉ theo sở thích annotation.

## 9. `@JoinColumn` có những thuộc tính quan trọng nào?

Một khai báo minh họa:

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(
    name = "department_id",
    referencedColumnName = "id",
    nullable = false,
    foreignKey = @ForeignKey(name = "fk_employee_department")
)
private Department department;
~~~

Trong file Java đầy đủ, cần import `jakarta.persistence.ForeignKey` cùng các annotation liên quan.

| Thuộc tính | Ý nghĩa thực tế | Lưu ý |
| --- | --- | --- |
| `name` | Tên cột FK **ở bảng chứa liên kết** hoặc bảng trung gian | Nên khớp migration/schema |
| `referencedColumnName` | Tên cột **ở bảng entity được tham chiếu** | Mặc định thường là cột PK; khi không cần không nhất thiết khai báo |
| `nullable` | Metadata tính cho phép NULL của cột | Không phải bằng chứng schema đang chạy có NOT NULL |
| `unique` | Metadata cột được yêu cầu duy nhất khi sinh schema | Thường phù hợp one-to-one; phải có constraint DB tương ứng |
| `insertable` | Quyền tham gia SQL INSERT do JPA tạo cho cột | Dùng sai có thể làm FK không được ghi |
| `updatable` | Quyền tham gia SQL UPDATE do JPA tạo cho cột | Không đồng nghĩa khóa/giá trị bất biến ở mọi đường ghi |
| `table` | Tên bảng chứa cột join khi mapping có secondary table thích hợp | Không dùng để tùy tiện thay thế `@JoinTable` |
| `foreignKey` | Metadata về tên/chế độ DDL của constraint FK | Không tự thêm FK vào schema đang tồn tại |

### 9.1. `name` và `referencedColumnName` là hai đầu khác nhau

~~~java
@JoinColumn(
    name = "department_id",
    referencedColumnName = "id")
~~~

Nghĩa là:

~~~text
employees.department_id  --->  departments.id
       ^                           ^
       |                           |
      name               referencedColumnName
~~~

Nếu entity đích có PK tên `dept_code`, có thể khai báo:

~~~java
@JoinColumn(
    name = "department_code",
    referencedColumnName = "dept_code")
private Department department;
~~~

Trong thực tế, liên kết tới PK là lựa chọn di động và dễ hiểu nhất. Liên kết tới một cột khác không phải PK yêu cầu cột đích có tính duy nhất và cần kiểm tra khả năng ánh xạ của provider/DBMS; không nên coi việc đổi `referencedColumnName` là đủ để biến một cột không duy nhất thành định danh hợp lệ.

### 9.2. `optional = false` khác `nullable = false`

~~~java
@ManyToOne(optional = false)
@JoinColumn(nullable = false)
private Department department;
~~~

- `optional = false` diễn đạt mối quan hệ **bắt buộc** trong mô hình JPA.
- `nullable = false` là metadata về **cột** phục vụ schema generation.
- `NOT NULL` tại database mới chặn hàng thiếu FK đối với mọi SQL writer.
- `FOREIGN KEY` tại database mới chặn FK không tham chiếu hàng hợp lệ.

Muốn bảo đảm nhân viên phải thuộc phòng ban hợp lệ, cả **NOT NULL và FOREIGN KEY** đều quan trọng. Chỉ `NOT NULL` vẫn cho phép ghi một mã phòng ban không tồn tại nếu không có FK.

### 9.3. Cẩn thận với `insertable = false, updatable = false`

Thỉnh thoảng cùng một cột được ánh xạ thành cả scalar ID và quan hệ:

~~~java
@Column(name = "department_id")
private Long departmentId;

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(
    name = "department_id",
    insertable = false,
    updatable = false)
private Department department;
~~~

Trong mô hình này, thuộc tính `departmentId` mới là mapping ghi cột, còn quan hệ `department` chỉ đọc tham chiếu theo giá trị FK. **Gán `employee.department = otherDepartment` không mặc nhiên cập nhật `department_id` bằng mapping chỉ đọc ấy.**

Trừ khi có yêu cầu cụ thể, nên ưu tiên **một nguồn ghi rõ ràng cho FK** thay vì duy trì đồng thời scalar ID và entity reference dễ bị lệch trong bộ nhớ.

## 10. Khóa ngoại ghép và `@JoinColumns`

Nếu entity đích có khóa chính nhiều cột, liên kết thường cần nhiều cột FK tương ứng.

Giả sử phòng ban được nhận diện bởi `(company_id, dept_code)`:

~~~sql
CREATE TABLE departments (
    company_id BIGINT NOT NULL,
    dept_code VARCHAR(30) NOT NULL,
    display_name VARCHAR(150) NOT NULL,
    PRIMARY KEY (company_id, dept_code)
);

CREATE TABLE employees (
    id BIGINT PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    dept_company_id BIGINT NOT NULL,
    dept_code VARCHAR(30) NOT NULL,
    CONSTRAINT fk_employee_dept
        FOREIGN KEY (dept_company_id, dept_code)
        REFERENCES departments(company_id, dept_code)
);
~~~

JPA phía `Employee` có thể dùng:

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumns({
    @JoinColumn(
        name = "dept_company_id",
        referencedColumnName = "company_id",
        nullable = false),
    @JoinColumn(
        name = "dept_code",
        referencedColumnName = "dept_code",
        nullable = false)
})
private Department department;
~~~

Đoạn mã là một phần của entity; để chạy cần `Department` có khóa ghép được định nghĩa chính xác bằng `@EmbeddedId` hoặc `@IdClass` theo yêu cầu JPA, và các import `ManyToOne`, `FetchType`, `JoinColumns`, `JoinColumn` tương ứng.

Điểm cần nhớ:

- `@JoinColumns` là một **nhóm cột nối tạo thành cùng một FK logic**; không phải hai quan hệ độc lập.
- Mỗi `name` là cột ở bảng `employees`, mỗi `referencedColumnName` là cột trong khóa được tham chiếu ở `departments`.
- Database thường dùng một **foreign key constraint nhiều cột** cho tổ hợp tương ứng.
- Nếu liên kết bắt buộc, phải cân nhắc nullability của **toàn bộ** thành phần khóa. Các DBMS có quy tắc riêng cho composite FK khi một phần có giá trị NULL.

### Áp dụng cho multi-tenancy

Trong hệ thống nhiều tenant, FK chỉ trỏ vào một surrogate PK duy nhất như `department_id` sẽ bảo đảm phòng ban tồn tại, nhưng **không tự bảo đảm nhân viên và phòng ban thuộc cùng tenant**. Nếu tính toàn vẹn tenant phải được DB chặn ở mức ràng buộc, có thể thiết kế FK ghép tham chiếu khóa duy nhất `(tenant_id, department_id)` hoặc chọn chiến lược isolation phù hợp.

Đừng chỉ dựa vào việc query thường có điều kiện `tenant_id` để coi mọi FK đều bảo đảm không tham chiếu chéo tenant.

## 11. Bảng liên kết có thuộc tính riêng: nên tạo entity cho liên kết

Quan hệ nhiều–nhiều đơn giản có thể ánh xạ bằng `@ManyToMany @JoinTable`. Nhưng giả sử việc gán vai trò cho user có thêm:

- Thời điểm cấp quyền.
- Người cấp quyền.
- Trạng thái phê duyệt.
- Thời gian hết hạn.

Khi đó **liên kết đã trở thành một đối tượng có dữ liệu và vòng đời riêng**. Thay vì cố chứa các cột đó trong mapping `@ManyToMany` thuần túy, có thể mô hình hóa thành entity `UserRoleAssignment`:

~~~text
UserAccount (1) ---- (*) UserRoleAssignment (*) ---- (1) Role
                            |
                            +-- grantedAt
                            +-- grantedBy
                            +-- expiresAt
~~~

### Entity liên kết

~~~java
package com.example.persistence;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;
import java.time.LocalDateTime;

@Entity
@Table(
    name = "user_role_assignments",
    uniqueConstraints = @UniqueConstraint(
        name = "uq_active_user_role",
        columnNames = {"user_id", "role_id"}
    )
)
public class UserRoleAssignment {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id", nullable = false)
    private UserAccount user;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "role_id", nullable = false)
    private Role role;

    @Column(name = "granted_at", nullable = false)
    private LocalDateTime grantedAt;

    protected UserRoleAssignment() {
    }

    public UserRoleAssignment(
            UserAccount user, Role role, LocalDateTime grantedAt) {
        this.user = user;
        this.role = role;
        this.grantedAt = grantedAt;
    }
}
~~~

Ở đây, `UserRoleAssignment` là một entity thông thường với hai `@ManyToOne @JoinColumn`. Nó **không cần `@ManyToMany`** để biểu diễn hai FK. Surrogate ID cho bản ghi gán giúp tham chiếu trực tiếp tới một lần gán; unique constraint trên `(user_id, role_id)` vẫn bảo đảm mỗi cặp có tối đa một bản ghi theo quy tắc đang mô hình hóa.

Nếu nghiệp vụ lưu **nhiều lần gán cùng vai trò theo lịch sử**, không thể giữ UNIQUE toàn bảng trên cặp đó; cần thiết kế khóa, trạng thái và tính duy nhất cho bản ghi đang hiệu lực một cách riêng biệt. Tên `uq_active_user_role` trong ví dụ là tên minh họa; để phân biệt chỉ bản ghi đang hoạt động cần thêm cột trạng thái và constraint/index tương ứng.

DDL minh họa:

~~~sql
CREATE TABLE user_role_assignments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    granted_at TIMESTAMP NOT NULL,
    CONSTRAINT uq_user_role_pair UNIQUE (user_id, role_id),
    CONSTRAINT fk_assignment_user
        FOREIGN KEY (user_id) REFERENCES user_accounts(id),
    CONSTRAINT fk_assignment_role
        FOREIGN KEY (role_id) REFERENCES roles(id)
);
~~~

Đây là minh họa mô hình **một cặp chỉ có một bản ghi gán**. Nếu cần lịch sử nhiều lần, sẽ thay unique constraint và đưa thêm chiều thời gian hoặc trạng thái vào mô hình.

## 12. Khi nào dùng `@JoinTable`, khi nào dùng entity trung gian?

| Bài toán | Lựa chọn thường hợp lý | Lý do |
| --- | --- | --- |
| User có nhiều role, role có nhiều user, liên kết không có dữ liệu riêng | `@ManyToMany @JoinTable` | Ngắn gọn, join table chỉ biểu diễn cặp |
| Gán role có thời điểm, người cấp và trạng thái | Entity liên kết với hai `@ManyToOne` | Dữ liệu và vòng đời của liên kết cần được quản lý |
| Department có nhiều Employee, Employee có một Department | `@ManyToOne @JoinColumn` và `@OneToMany(mappedBy)` | FK ở phía nhiều |
| Customer có tối đa một Profile | `@OneToOne @JoinColumn(unique=true)` | FK duy nhất diễn đạt cardinality |
| Profile có cùng định danh với Customer | `@OneToOne @MapsId` | PK của bảng phụ đồng thời là FK |
| Collection một chiều, không muốn cột FK trong bảng item | `@OneToMany @JoinTable` | Quan hệ được lưu ở bảng trung gian |
| Quan hệ có khóa phức hợp | `@JoinColumns` hoặc nhiều join columns trong `@JoinTable` | Mỗi phần của khóa được ánh xạ đúng |

**Không phải cứ nhìn thấy bảng trung gian là phải dùng `@ManyToMany`.** Nếu bảng liên kết có nhiều cột dữ liệu và được cập nhật độc lập, mô hình hóa thành entity thường rõ ràng hơn.

## 13. Cascade của JPA không đồng nghĩa cascade của foreign key

Hai từ “cascade” có thể chỉ hai cơ chế khác nhau:

### 13.1. Cascade của JPA

~~~java
@OneToMany(
    mappedBy = "department",
    cascade = CascadeType.PERSIST)
private List<Employee> employees = new ArrayList<>();
~~~

Khi persist một `Department`, provider có thể lan thao tác persist tới các `Employee` liên quan theo cấu hình cascade và trạng thái của chúng.

Các kiểu cascade JPA gồm `PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, `DETACH` và `ALL` (gộp các thao tác hỗ trợ). Cascade ở đây là **lan truyền hành động quản lý entity**, không phải lệnh database `ON DELETE CASCADE`.

### 13.2. Cascade của database

~~~sql
ALTER TABLE employees
ADD CONSTRAINT fk_employee_department
FOREIGN KEY (department_id) REFERENCES departments(id)
ON DELETE CASCADE;
~~~

Câu SQL trên minh họa cơ chế xóa các hàng con trong database khi hàng cha bị xóa. Nó không tự đảm bảo các entity đang managed trong persistence context được cập nhật trạng thái giống như JPA đã gọi `remove` trên từng entity; callback entity cũng có thể không chạy theo cách mong đợi.

**Không chạy đoạn ALTER này trên schema ở mục 1 nếu constraint đã có cùng tên**; muốn dùng chính sách cascade cần thiết kế constraint đúng ngay trong DDL hoặc migration thay thế constraint cũ.

### 13.3. `orphanRemoval`

~~~java
@OneToMany(mappedBy = "order", orphanRemoval = true)
private List<OrderItem> items = new ArrayList<>();
~~~

`orphanRemoval = true` có thể yêu cầu provider xóa một entity con khi nó bị loại khỏi quan hệ cha theo ngữ nghĩa vòng đời, trong những loại quan hệ hỗ trợ (thường `@OneToOne` và `@OneToMany`). Nó phù hợp khi entity con **thuộc sở hữu vòng đời** của cha, ví dụ dòng hàng thuộc một đơn hàng.

Không nên dùng `CascadeType.REMOVE` tùy tiện ở `@ManyToMany` như user–role: xóa một user không có nghĩa được xóa luôn đối tượng `Role` mà các user khác còn sử dụng. Thông thường chỉ cần xóa hàng liên kết.

| Cơ chế | Ai quyết định và thực hiện? | Ý nghĩa |
| --- | --- | --- |
| JPA `cascade = REMOVE` | JPA provider | Lan thao tác remove từ entity này sang entity liên quan |
| JPA `orphanRemoval = true` | JPA provider | Xóa entity con khi bị loại khỏi quan hệ sở hữu vòng đời |
| SQL `ON DELETE CASCADE` | DBMS | Xóa các hàng tham chiếu theo constraint FK |
| SQL `ON DELETE SET NULL` | DBMS | Đặt FK hàng con thành NULL nếu schema cho phép |
| SQL `RESTRICT/NO ACTION` | DBMS | Từ chối xóa hàng cha còn được tham chiếu, theo timing của constraint |

## 14. Thao tác với quan hệ: phía nào tạo ra INSERT/UPDATE?

Xem các lệnh thay đổi JPA và SQL dự kiến về mặt ý nghĩa:

| Thao tác Java | Quan hệ ánh xạ | Thay đổi SQL thường cần |
| --- | --- | --- |
| `employee.setDepartment(dept)` | Many-to-one FK ở employees | UPDATE/INSERT giá trị `employees.department_id` |
| `department.getEmployees().add(emp)` chỉ ở inverse side | One-to-many `mappedBy` | Không bảo đảm thay FK nếu owning side chưa đổi |
| `user.getRoles().add(role)` ở owning side | Many-to-many join table | INSERT hàng `user_roles(user_id, role_id)` |
| `user.getRoles().remove(role)` | Many-to-many join table | DELETE hàng liên kết tương ứng |
| `profile.setCustomer(customer)` | One-to-one FK ở profiles | INSERT/UPDATE `customer_profiles.customer_id` |
| `em.remove(dept)` với employees còn FK | Many-to-one FK và không có cascade xử lý | Có thể bị FK chặn tại DB |

Danh sách là **mô hình ý nghĩa**, không cam kết số lượng câu SQL, thứ tự phát lệnh hoặc thời điểm thực thi. Provider có thể trì hoãn tới flush, tối ưu batch và thực thi các câu bổ sung theo chiến lược ánh xạ.

### `flush` khác `commit`

~~~java
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();
    employee.setDepartment(newDepartment);
    em.flush();  // Đồng bộ SQL đang chờ; có thể phát lỗi FK.
    tx.commit(); // Kết thúc transaction.
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
}
~~~

Đoạn mã dùng `RESOURCE_LOCAL` transaction; trong ứng dụng Spring/Jakarta EE, transaction có thể do framework hoặc container quản lý. Nếu `newDepartment` là entity transient chưa được persist và quan hệ không có cascade thích hợp, việc flush có thể thất bại. Thứ tự persist các entity và cơ chế sinh khóa cũng ảnh hưởng SQL thực tế.

Lỗi FK, UNIQUE hoặc NOT NULL có thể xuất hiện khi flush hoặc khi commit, tùy cấu hình và khả năng trì hoãn constraint của DBMS. Đừng dựa vào việc thao tác Java chưa ném exception để khẳng định database đã chấp nhận liên kết.

## 15. Constraint database là nơi bảo vệ tính toàn vẹn liên kết

Annotation JPA mô tả ý định. Nhưng dữ liệu có thể đến từ JDBC, script migration, console quản trị, ETL hoặc hệ thống khác. Vì vậy schema phải bảo vệ các bất biến quan trọng:

| Quy tắc nghiệp vụ | Ràng buộc database phù hợp |
| --- | --- |
| Employee phải thuộc Department tồn tại | `department_id NOT NULL` và FK tới `departments(id)` |
| Một Customer có tối đa một Profile | `UNIQUE(customer_id)` trên FK của bảng profile |
| Một cặp User–Role chỉ được gán một lần | `PRIMARY KEY(user_id, role_id)` hoặc UNIQUE cặp |
| Một Role có thể gán nhiều User | Không đặt UNIQUE chỉ riêng `role_id` trong join table |
| Một Artifact chỉ thuộc tối đa một Collection | UNIQUE trên `artifact_id` trong bảng liên kết |
| FK ghép phải khớp một Department hợp lệ | Composite FK tham chiếu khóa ứng viên của Department |

### Một số điểm thiết kế schema

- FK nên có **tên rõ ràng** để hỗ trợ migration và phân tích exception.
- Các cột FK thường cần index theo mẫu truy vấn, đặc biệt ở bảng nhiều hàng; tác động index phụ thuộc DBMS.
- Tính duy nhất có thể theo tổ hợp cột, không chỉ từng cột.
- `NULL` có ngữ nghĩa riêng trong FK và UNIQUE; chỉ định NOT NULL khi quan hệ bắt buộc.
- Việc xóa hàng cha cần có chính sách nhất quán: chặn xóa, xóa con, đặt NULL, hoặc lưu trạng thái xóa mềm.
- Schema generation của JPA thuận tiện cho demo, nhưng migration có kiểm soát thường phù hợp hơn ở môi trường vận hành.

**Có `@JoinColumn(foreignKey = @ForeignKey(...))` không có nghĩa database đã tồn tại FK tương ứng.** Annotation có thể tác động DDL khi provider được yêu cầu tạo schema. Nếu bảng đã có trước, cần migration và xác nhận constraint vật lý.

## 16. Bảng liên kết và SQL JOIN không phải cùng một khái niệm

Tên gọi *join* dễ gây nhầm:

- **Join column:** cột lưu giá trị liên kết; dùng trong metadata ánh xạ.
- **Join table:** bảng vật lý lưu liên kết giữa hai tập bản ghi.
- **SQL JOIN:** phép kết hợp các quan hệ trong một truy vấn SQL; có thể dùng **có hoặc không** có join table vật lý.
- **JPQL JOIN / JOIN FETCH:** cú pháp truy vấn ở mức entity; có thể được provider chuyển thành SQL JOIN.

Ví dụ truy vấn nhân viên và phòng ban thông qua FK trực tiếp:

~~~sql
SELECT e.id, e.full_name, d.name AS department_name
FROM employees e
JOIN departments d ON d.id = e.department_id;
~~~

Không có bảng trung gian nào ở đây, nhưng SQL vẫn dùng `JOIN`.

Ngược lại, truy vấn user–role cần kết hợp ba bảng vì quan hệ nằm trong `user_roles`:

~~~sql
SELECT u.username, r.role_name
FROM user_accounts u
JOIN user_roles ur ON ur.user_id = u.id
JOIN roles r ON r.id = ur.role_id;
~~~

Vì vậy không thể suy ra “cứ có `JOIN` trong JPQL thì phải có `@JoinTable`”, hoặc “có `@JoinTable` thì mọi truy vấn đều phải viết `JOIN` bằng tay”.

## 17. Ánh xạ liên kết khác với chiến lược fetch

Một relation khai báo `@JoinColumn` chỉ nói **cách nối**, không nói **khi nào dữ liệu phải được tải**.

Ví dụ:

~~~java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "department_id")
private Department department;
~~~

Và truy vấn:

~~~java
List<Employee> employees = em.createQuery(
        "SELECT e FROM Employee e JOIN FETCH e.department",
        Employee.class)
    .getResultList();
~~~

`JOIN FETCH` trong JPQL yêu cầu provider tải quan hệ cùng truy vấn. Dữ liệu vẫn được ánh xạ qua cùng cột `department_id`. **Fetch strategy không làm thay đổi FK hoặc quyền sở hữu quan hệ**.

Mặc định theo JPA:

| Annotation | Fetch mặc định |
| --- | --- |
| `@ManyToOne` | `EAGER` |
| `@OneToOne` | `EAGER` |
| `@OneToMany` | `LAZY` |
| `@ManyToMany` | `LAZY` |

Trong JPA, `LAZY` là gợi ý mà provider có thể có giới hạn thực thi, nhất là với một số quan hệ to-one và chế độ bytecode enhancement. Thiết kế truy vấn nên dựa vào SQL thật và nhu cầu dữ liệu, không chỉ dựa vào annotation.

### Vấn đề N+1

Giả sử lấy 100 `Employee`, sau đó lần lượt gọi `getDepartment().getName()`. Nếu mỗi tham chiếu cần tải riêng, có thể phát sinh nhiều câu SELECT ngoài truy vấn ban đầu. Phương án phù hợp có thể là:

- `JOIN FETCH` khi thực sự cần cả entity liên quan.
- Entity graph khi muốn định nghĩa fetch plan tách biệt với truy vấn.
- Projection/DTO cho màn hình chỉ cần vài cột.
- Batch fetching theo khả năng provider.

Với fetch collection nhiều–nhiều hoặc một–nhiều, phép JOIN có thể nhân số hàng trả về, ảnh hưởng phân trang và bộ nhớ. Không nên dùng `JOIN FETCH` mọi collection theo mặc định.

## 18. Đọc và sửa mapping ở dự án có schema từ trước

Trong dự án có database đang chạy, thứ tự an toàn để hiểu một quan hệ là:

1. **Xác định cardinality nghiệp vụ:** một–một, một–nhiều hay nhiều–nhiều? Quan hệ bắt buộc hay tùy chọn?
2. **Đọc schema thực tế:** FK nằm ở bảng nào, có bảng trung gian không, PK/UNIQUE/NOT NULL ra sao?
3. **Đọc annotation JPA:** phía nào dùng `@JoinColumn` / `@JoinTable`, phía nào dùng `mappedBy`?
4. **Đối chiếu tên:** `name` và `referencedColumnName` có khớp cột thực tế không? Với khóa ghép có đủ cột?
5. **Xem thao tác ghi:** ứng dụng đang sửa owning side hay chỉ sửa inverse side? Có cascade hoặc orphanRemoval được cấu hình không?
6. **Xem transaction và SQL:** provider phát INSERT/UPDATE/DELETE nào khi flush? Database có chặn do constraint không?
7. **Xem mẫu truy vấn:** quan hệ có tạo N+1, join ngoài ý muốn hoặc cần index bổ sung không?

Trong việc nâng cấp schema, thay đổi annotation mà không migration có thể gây:

- Lỗi “column not found” nếu `@JoinColumn(name = "...")` không đúng.
- Lỗi NOT NULL khi cột FK không được gán.
- Lỗi FK khi tham chiếu hàng cha chưa tồn tại.
- Lỗi UNIQUE khi mapping `@OneToOne` bị dùng như `@ManyToOne` trong dữ liệu hiện có.
- Dữ liệu trùng trong join table nếu thiếu unique constraint.
- Đường truy vấn đổi hiệu năng khi cấu trúc bảng hoặc index thay đổi.

JPA provider có thể giúp phát hiện một số vấn đề khi khởi động hoặc chạy query, nhưng **database schema là nguồn xác nhận cuối cùng cho constraint vật lý**.

## 19. Những nhầm lẫn thường gặp

| Nhận định sai | Cách hiểu đúng |
| --- | --- |
| “`@JoinColumn` là một foreign key ở database.” | Nó là metadata JPA về cột liên kết; database FK là constraint riêng |
| “Có `@JoinColumn` thì luôn cần `@JoinTable`.” | FK trực tiếp trong bảng entity thường chỉ cần `@JoinColumn` |
| “`@ManyToMany` lưu hai ID trong một cột của entity.” | Quan hệ N–N thông thường dùng bảng trung gian có hai FK |
| “`mappedBy` là tên cột FK.” | `mappedBy` là tên thuộc tính Java của owning side |
| “Thêm vào inverse collection là đủ để lưu liên kết.” | Owning side mới quyết định cập nhật liên kết theo mapping hai chiều |
| “`@OneToOne` tự đảm bảo FK duy nhất dù DB không có constraint.” | Cần UNIQUE thực tế ở DB nếu yêu cầu toàn vẹn cho mọi đường ghi |
| “`@JoinTable` chỉ dùng với `@ManyToMany`.” | Có thể dùng với one-to-many hoặc one-to-one khi mô hình cần |
| “Hai cột FK trong join table luôn tự ngăn bản ghi trùng.” | Cần UNIQUE/PK trên cặp FK theo cardinality mong muốn |
| “`cascade = REMOVE` giống `ON DELETE CASCADE`.” | Một bên là hành động của JPA, bên kia là cơ chế của DBMS |
| “Có liên kết JPA thì lúc nào cũng JOIN để đọc.” | Fetch plan và query riêng quyết định cách dữ liệu được tải |
| “Chỉ cần đổi annotation để chuyển từ FK sang join table.” | Cần migration dữ liệu và constraint khi cấu trúc lưu thay đổi |
| “Gán quan hệ tới entity chưa có trong DB sẽ luôn tự lưu entity đó.” | Cần persist entity phù hợp hoặc cascade PERSIST có chủ đích |

## 20. Bài tập áp dụng

### Bài 1 — Quan hệ phòng ban và nhân viên

Mỗi nhân viên thuộc đúng một phòng ban, mỗi phòng ban có nhiều nhân viên. Thiết kế bảng, annotation và ràng buộc cần thiết.

**Gợi ý:** sử dụng `employees.department_id NOT NULL` với FK đến `departments.id`. Ở JPA, phía Employee dùng `@ManyToOne @JoinColumn(name="department_id")`, Department tùy nhu cầu có `@OneToMany(mappedBy="department")`.

### Bài 2 — Hồ sơ cá nhân một–một

Mỗi tài khoản có tối đa một hồ sơ, một hồ sơ chỉ thuộc một tài khoản. Nếu bảng profiles có cột `user_id`, tại sao phải thêm UNIQUE?

**Gợi ý:** FK chỉ bảo đảm user được tham chiếu có tồn tại; UNIQUE mới chặn hai profile khác nhau cùng tham chiếu một user.

### Bài 3 — Gán nhiều vai trò

Một user có nhiều role và một role gắn với nhiều user. Hãy đặt tên bảng trung gian và hai FK.

**Gợi ý:** `user_roles(user_id, role_id)`, mỗi cột là FK tới một bảng, tổ hợp là PK hoặc UNIQUE; JPA phía user dùng `@JoinTable(joinColumns = ..., inverseJoinColumns = ...)`.

### Bài 4 — Join table có thêm thời hạn

Quan hệ user–role cần lưu ngày được gán và ngày hết hạn. Có nên giữ `@ManyToMany` đơn giản?

**Gợi ý:** mô hình hóa entity trung gian với hai `@ManyToOne` và các thuộc tính riêng, đồng thời quyết định uniqueness theo lịch sử hay bản ghi hiện hành.

### Bài 5 — Hai chiều nhưng dữ liệu không được lưu

Ứng dụng chỉ gọi `department.getEmployees().add(employee)` trên collection có `mappedBy = "department"`. Vì sao FK không đổi?

**Gợi ý:** `Employee.department` mới là owning side. Cần cập nhật phía sở hữu và đồng bộ collection để trạng thái Java nhất quán.

### Bài 6 — Khóa ngoại ghép

Phòng ban có PK `(company_id, dept_code)`. Employee cần hai cột `dept_company_id` và `dept_code`. Nên dùng annotation nào?

**Gợi ý:** `@JoinColumns` gồm hai `@JoinColumn`, mỗi thành phần chỉ rõ cột tham chiếu, đồng thời database có FK ghép.

### Bài 7 — Lỗi khi xóa phòng ban

Database từ chối xóa phòng ban vì vẫn có nhân viên tham chiếu. Có nên bật `CascadeType.REMOVE` hoặc SQL `ON DELETE CASCADE` ngay?

**Gợi ý:** phải xác định trước quy tắc nghiệp vụ. Nhân viên có thể cần chuyển phòng ban, hoặc chỉ được xóa phòng ban khi đã trống. Tự động xóa nhân viên có thể là hành vi nghiêm trọng và sai mục đích.

### Bài 8 — Tối ưu báo cáo

Màn hình chỉ cần tên nhân viên và tên phòng ban; sau khi lấy nhân viên, ứng dụng phát thêm nhiều truy vấn. Có cần đổi `@JoinColumn` thành `@JoinTable` không?

**Gợi ý:** không. Vị trí FK là vấn đề schema; hiệu năng tải dữ liệu nên được xử lý bằng JPQL JOIN, projection, fetch plan, index và kiểm tra SQL thực tế.

## Kết luận

**Foreign key, `@JoinColumn` và `@JoinTable` cùng mô tả một mối liên hệ nhưng ở các tầng trách nhiệm khác nhau.** FK là ràng buộc của database. `@JoinColumn` cho JPA biết cột nào dùng để liên kết hai entity. `@JoinTable` cho JPA biết quan hệ được lưu thông qua bảng trung gian và hai nhóm cột nối.

Khi thiết kế quan hệ entity, hãy bắt đầu từ **cardinality và vòng đời nghiệp vụ**, tiếp theo quyết định **FK nằm ở đâu**, rồi xác định **owning side, inverse side và các constraint**. Với one-to-many, FK thường nằm ở bảng phía nhiều; với one-to-one, FK thường cần UNIQUE; với many-to-many, join table thường chứa cặp FK được bảo vệ bằng PK hoặc UNIQUE. Nếu liên kết có dữ liệu và vòng đời riêng, nên cân nhắc ánh xạ nó thành một entity độc lập.

Một mô hình JPA đáng tin cậy phải đồng bộ ba lớp: **tham chiếu Java**, **metadata mapping**, và **schema SQL thật**. Hiểu được ranh giới này giúp tránh lỗi dữ liệu trùng, FK không hợp lệ, cập nhật nhầm phía sở hữu và truy vấn kém hiệu quả.
