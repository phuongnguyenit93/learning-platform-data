# Vai trò của sinh lược đồ theo chuẩn Jakarta Persistence

Trong một ứng dụng dùng **Jakarta Persistence (JPA)**, entity Java mô tả dữ liệu ở mức đối tượng, còn database lưu dữ liệu trong các **bảng, cột, khóa chính, khóa ngoại, chỉ mục và ràng buộc**. Giữa hai thế giới đó là **metadata ánh xạ** (*mapping metadata*) được khai báo qua các annotation như `@Entity`, `@Table`, `@Column`, `@Id`, `@JoinColumn` hoặc qua tệp `orm.xml`.

JPA cung cấp một khả năng tiêu chuẩn gọi là **schema generation**: dựa trên metadata và cấu hình, provider có thể **tạo hoặc xóa các đối tượng lược đồ**, hoặc **xuất các câu lệnh DDL vào tệp SQL** để người phát triển xem xét và sử dụng trong quy trình phù hợp.

Ví dụ, từ:

```java
@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String name;
}
```

provider có thể tạo DDL có ý nghĩa tương đương:

```sql
CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

**Nhưng đây chỉ là minh họa.** SQL thực tế phụ thuộc Jakarta Persistence provider, DBMS, dialect, kiểu dữ liệu, chiến lược sinh ID và các cấu hình khác. JPA không bảo đảm mọi provider phát ra cùng một cú pháp DDL byte-for-byte.

> **Thông điệp trung tâm:** Schema generation là công cụ **khởi tạo và kiểm thử ánh xạ**, đặc biệt hữu ích ở môi trường phát triển, thử nghiệm và tạo bản nháp DDL. Nó **không phải** hệ thống migration có phiên bản, không tự giải quyết các thay đổi schema đang có dữ liệu, và không thay thế việc quản lý DDL production có kiểm soát.

Bài học thuộc chương **Siêu dữ liệu và lược đồ** của module **Data Persistence Relational Access ORM JPA**. Nội dung giải thích chính xác vai trò của schema generation tiêu chuẩn, nhóm thuộc tính `jakarta.persistence.schema-generation.*`, những khác biệt giữa tạo trực tiếp database và xuất SQL script, cấu hình từ metadata hoặc script, nạp dữ liệu thử nghiệm, ví dụ Java SE và XML, các rủi ro production, migration, khả năng portable và chiến lược kiểm thử.

## 1. Cần phân biệt bốn khái niệm

Một trong những nguyên nhân gây nhầm lẫn phổ biến là coi **entity mapping**, **schema generation**, **schema validation** và **schema migration** là cùng một việc.

| Khái niệm | Mục đích | Ví dụ |
| --- | --- | --- |
| **Mapping metadata** | Mô tả Java object liên hệ với bảng/cột như thế nào | `@Table(name="products")` |
| **Schema generation** | Tạo/xóa schema objects hoặc xuất DDL từ metadata/scripts | `CREATE TABLE products ...` |
| **Schema validation** | Kiểm tra schema hiện hữu có phù hợp mapping không | Provider-specific schema validator |
| **Schema migration** | Nâng cấp schema qua các phiên bản, bảo toàn dữ liệu | `ALTER TABLE ... ADD COLUMN ...` |

JPA có cơ chế **schema generation chuẩn**, nhưng không định nghĩa một hệ thống **migration versioned** đầy đủ như Flyway hay Liquibase.

### 1.1. Mapping là bản mô tả, không phải thao tác DDL

```java
@Column(name = "price", precision = 14, scale = 2)
private BigDecimal price;
```

Annotation trên nói với provider cách ánh xạ thuộc tính `price`. Nó **không tự tạo cột trong database** chỉ vì JVM đã nạp class.

Việc JPA có thực sự yêu cầu database tạo schema hay không phụ thuộc các cấu hình schema generation.

### 1.2. Sinh lược đồ không đồng nghĩa nâng cấp lược đồ

Nếu database có bảng:

```sql
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100)
);
```

và ngày mai entity thêm:

```java
@Column(name = "sku", nullable = false, length = 50)
private String sku;
```

thì schema generation action `create` **không** có nghĩa provider sẽ biết cách bổ sung cột `sku`, backfill giá trị cho những records cũ rồi tạo `NOT NULL` một cách an toàn.

Quy trình đó là **migration**.

### 1.3. Tạo DDL khác với chạy DDL

Hai khả năng tách biệt:

```text
Mapping metadata
      |
      +-- Tạo trực tiếp ở database
      |       CREATE TABLE, CREATE SEQUENCE, ...
      |
      +-- Xuất SQL script
              create.sql, drop.sql
              (chưa nhất thiết thực thi)
```

JPA chuẩn có cấu hình riêng cho **database action** và **scripts action**. Có thể chọn một trong hai hoặc kết hợp, nhưng cần tránh chạy hai luồng thao tác gây trùng lặp ngoài ý muốn.

### 1.4. Kiểm tra mapping không có nghĩa phải bật tạo bảng

Một ứng dụng có thể sử dụng entity mappings bình thường trên database đã được migration tạo trước, trong khi:

```properties
jakarta.persistence.schema-generation.database.action=none
```

Đây là một thiết kế rất phổ biến ở production.

## 2. Schema generation giải quyết bài toán nào?

Khi mới xây dựng mô hình JPA, người phát triển có thể muốn thử:

- Entity có được provider nhận diện hay không?
- Primary key và chiến lược ID generation có hợp lệ không?
- Quan hệ `@ManyToOne` sẽ tạo khóa ngoại nào?
- `@ManyToMany` cần bảng trung gian có hình dạng gì?
- `@Embedded` tạo các cột như thế nào?
- `@UniqueConstraint` và `@Index` có được thể hiện trong DDL không?
- `@SequenceGenerator` yêu cầu database sequence nào?
- Có lỗi thiếu mapping hoặc type không được DBMS hỗ trợ?
- SQL DDL theo dialect đích khác gì so với dự đoán?

Schema generation giúp rút ngắn vòng:

```text
Java entity mapping
       |
       v
Generate schema on test database
       |
       v
Inspect tables/constraints
       |
       v
Run persist/find/update/remove
       |
       v
Improve metadata or choose migration DDL
```

Đặc biệt, khi bắt đầu một module mới, nó là **công cụ phản hồi nhanh** để khám phá metadata và kiểm thử mapping.

### 2.1. Những lợi ích thực tế

1. **Khởi tạo môi trường thử nghiệm** khi chưa có schema.
2. **Tạo test fixture database** để chạy integration tests trên entities.
3. **Lấy bản nháp DDL** hỗ trợ soạn migration.
4. **Phát hiện lỗi mapping sớm** khi bootstrap hoặc tạo bảng.
5. **Khám phá đặc điểm dialect** của database đang dùng.
6. **Tự động hóa test setup** cho databases tạm, có thể xóa an toàn.

### 2.2. Những điều schema generation không hứa hẹn

Nó không bảo đảm:

- Tự giữ toàn bộ dữ liệu khi entity thay đổi.
- Thực hiện database migrations có phiên bản.
- Nhận biết chính xác ý nghĩa của việc rename field.
- Dự đoán thứ tự triển khai tương thích nhiều phiên bản ứng dụng.
- Sinh mọi constraint nâng cao của một DBMS.
- Tự backfill dữ liệu legacy.
- Tạo trigger, stored procedure, view, partition, row-level security theo logic nghiệp vụ.
- DDL hoàn toàn giống giữa PostgreSQL, MySQL, Oracle và SQL Server.
- Schema đang tồn tại luôn phù hợp mapping.
- Tính nguyên tử khi một chuỗi DDL thất bại nửa chừng.

## 3. Một mô hình JPA để quan sát DDL

Ta dùng hệ thống danh mục sản phẩm:

```text
          Category
        +----------+
        | id       |
        | code     |
        | name     |
        +----------+
              ^ 1
              |
              | ManyToOne
              |
              * N
        +----------------+
        | Product        |
        | id             |
        | sku            |
        | name           |
        | price          |
        | active         |
        | version        |
        | category       |
        +----------------+
```

Yêu cầu:

- Category có ID do ứng dụng cung cấp.
- Product có ID được database tạo.
- Product phải tham chiếu một Category.
- SKU của Product duy nhất.
- Code của Category duy nhất.
- Giá Product dùng hai chữ số thập phân.
- Product có version để chống lost updates theo optimistic locking.
- Có index hỗ trợ tìm Product theo category.
- Database có những constraints căn bản.

### 3.1. Category entity

```java
package com.example.catalog;

import jakarta.persistence.*;

@Entity
@Table(
    name = "categories",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_category_code",
        columnNames = "code"
    )
)
public class Category {

    @Id
    @Column(name = "id")
    private Long id;

    @Column(
        name = "code",
        nullable = false,
        length = 40
    )
    private String code;

    @Column(
        name = "name",
        nullable = false,
        length = 160
    )
    private String name;

    protected Category() {
    }

    public Category(Long id, String code, String name) {
        this.id = id;
        this.code = code;
        this.name = name;
    }

    public Long getId() { return id; }
    public String getCode() { return code; }
    public String getName() { return name; }
}
```

### 3.2. Product entity

```java
package com.example.catalog;

import jakarta.persistence.*;
import java.math.BigDecimal;

@Entity
@Table(
    name = "products",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_product_sku",
        columnNames = "sku"
    ),
    indexes = @Index(
        name = "idx_product_category",
        columnList = "category_id"
    )
)
public class Product {

    @Id
    @GeneratedValue(
        strategy = GenerationType.IDENTITY
    )
    private Long id;

    @Column(
        name = "sku",
        nullable = false,
        length = 50
    )
    private String sku;

    @Column(
        name = "name",
        nullable = false,
        length = 160
    )
    private String name;

    @Column(
        name = "price",
        nullable = false,
        precision = 14,
        scale = 2
    )
    private BigDecimal price;

    @Column(name = "active", nullable = false)
    private boolean active;

    @ManyToOne(
        fetch = FetchType.LAZY,
        optional = false
    )
    @JoinColumn(
        name = "category_id",
        nullable = false,
        foreignKey = @ForeignKey(
            name = "fk_product_category"
        )
    )
    private Category category;

    @Version
    @Column(name = "version", nullable = false)
    private Long version;

    protected Product() {
    }

    public Product(
            String sku,
            String name,
            BigDecimal price,
            Category category) {

        this.sku = sku;
        this.name = name;
        this.price = price;
        this.category = category;
        this.active = true;
    }

    public Long getId() { return id; }
    public String getSku() { return sku; }
    public String getName() { return name; }
    public BigDecimal getPrice() { return price; }
    public Category getCategory() { return category; }
    public Long getVersion() { return version; }

    public void changePrice(BigDecimal value) {
        if (value == null || value.signum() < 0) {
            throw new IllegalArgumentException(
                "Price must be non-negative"
            );
        }
        price = value;
    }
}
```

### 3.3. Vì sao chỉ dùng JPA annotations chưa đủ?

Nếu database chưa có bảng `categories` và `products`, application sẽ không tự chạy thành công những lệnh `SELECT/INSERT` chỉ nhờ Java class.

Cần một trong hai cách:

- Chuẩn bị schema bằng **migrations/SQL DDL**, hoặc
- Cho provider dùng **schema generation** theo cấu hình thích hợp trong một môi trường cho phép.

Đối với production, phần lớn hệ thống nên dùng quy trình migration có version thay vì tùy tiện tạo/xóa schema lúc runtime bootstrap.

## 4. DDL có thể được sinh ra như thế nào?

Với một DBMS hỗ trợ cú pháp tương ứng, SQL minh họa có thể có dạng:

```sql
CREATE TABLE categories (
    id BIGINT NOT NULL,
    code VARCHAR(40) NOT NULL,
    name VARCHAR(160) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uk_category_code UNIQUE (code)
);

CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    sku VARCHAR(50) NOT NULL,
    name VARCHAR(160) NOT NULL,
    price NUMERIC(14, 2) NOT NULL,
    active BOOLEAN NOT NULL,
    category_id BIGINT NOT NULL,
    version BIGINT NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uk_product_sku UNIQUE (sku),
    CONSTRAINT fk_product_category
        FOREIGN KEY (category_id)
        REFERENCES categories(id)
);

CREATE INDEX idx_product_category
    ON products(category_id);
```

Đây là **DDL được viết để giải thích**, không phải cam kết về SQL JPA provider thực sự sinh ra.

Provider có thể:

- Tạo ràng buộc FK bằng `ALTER TABLE` sau khi tạo các bảng.
- Chọn kiểu `BIGINT`, `INTEGER`, `NUMERIC` hoặc kiểu native khác.
- Sinh IDENTITY syntax khác.
- Dùng tên constraint/index được transform theo naming strategy.
- Sắp thứ tự các câu lệnh khác.
- Đưa schema/catalog vào định danh.
- Không hỗ trợ đầy đủ một tùy chọn schema generation nào đó.

### 4.1. Vì sao quan sát DDL thực tế quan trọng?

Nếu entity dùng:

```java
@Column(precision = 14, scale = 2)
private BigDecimal price;
```

nhưng database đích có quy tắc riêng cho precision/scale, cần xác nhận actual DDL và cách dữ liệu được round-trip.

Tương tự, `GenerationType.IDENTITY` trên PostgreSQL, MySQL và SQL Server có cách diễn đạt DDL khác nhau. **JPA chuẩn hóa mapping intent, không chuẩn hóa mọi cú pháp SQL DDL.**

### 4.2. Một số constraints không phải mọi business rule

Trong ví dụ `price >= 0` được kiểm tra trong domain method, nhưng JPA 3.1 `@Column(precision=..., nullable=...)` tự nó **không đồng nghĩa có DB CHECK(price >= 0)**.

Nếu business invariant cần bảo vệ ở DB, hãy dùng migration tương ứng:

```sql
ALTER TABLE products
ADD CONSTRAINT ck_product_price
CHECK (price >= 0);
```

Không tự giả định một annotation Bean Validation `@DecimalMin("0")` được chuyển thành `CHECK` theo chuẩn JPA trên mọi provider.

## 5. Jakarta Persistence chuẩn hóa những gì?

Trong Jakarta Persistence 3.x, nhóm properties `jakarta.persistence.schema-generation.*` cho phép yêu cầu provider thực hiện hành vi schema generation theo chuẩn.

Các khả năng nổi bật:

1. Chọn **database action**: không làm gì, tạo, xóa hoặc xóa rồi tạo.
2. Chọn **scripts action**: không xuất, xuất DDL tạo, xuất DDL xóa hoặc cả hai.
3. Chọn **nguồn tạo/xóa**: mapping metadata, script có sẵn hoặc kết hợp.
4. Chọn **đích xuất SQL script**.
5. Cung cấp **kết nối schema generation** trong những trường hợp cần.
6. Yêu cầu tạo database schemas/namespaces khi được hỗ trợ.
7. Cung cấp thông tin DB product/version để sinh DDL phù hợp trong tình huống không có kết nối xác định.
8. Chạy SQL load script theo cơ chế tiêu chuẩn sau khi tạo schema phù hợp.

**Đây là API/cấu hình về sinh lược đồ, không phải API của EntityManager để thay đổi một bảng mỗi lần gọi repository.**

### 5.1. Khả năng hỗ trợ phụ thuộc provider/DBMS

JPA định nghĩa contract cho các property chuẩn, nhưng **khả năng hỗ trợ đầy đủ từng action và cú pháp DDL thực tế** có thể phụ thuộc provider, DBMS, quyền kết nối và version.

Đặc biệt, các đối tượng database không thể biểu diễn bằng metadata JPA chuẩn sẽ cần migrations hoặc vendor-specific cơ chế khác.

### 5.2. Namespace javax và jakarta

Dự án JPA cũ có thể gặp:

```properties
javax.persistence.schema-generation.database.action
```

Trong Jakarta Persistence hiện đại, dùng:

```properties
jakarta.persistence.schema-generation.database.action
```

Không thay namespace tùy tiện nếu đang dùng một stack JPA rất cũ; toàn bộ package Java, XML namespace và API version phải phù hợp runtime.

## 6. Property quan trọng nhất: database.action

`jakarta.persistence.schema-generation.database.action` kiểm soát thao tác schema generation **trực tiếp lên database**.

| Giá trị | Ý nghĩa tổng quát | Hệ quả |
| --- | --- | --- |
| `none` | Không thực thi thao tác tạo/xóa schema từ chức năng này | Phù hợp khi DB do migrations quản lý |
| `create` | Yêu cầu tạo các đối tượng schema | Có thể lỗi nếu đã tồn tại; không phải update/diff |
| `drop` | Yêu cầu xóa những đối tượng schema tương ứng | Có nguy cơ mất dữ liệu |
| `drop-and-create` | Yêu cầu xóa rồi tạo lại | **Có tính phá hủy dữ liệu**, dùng với DB tạm |

### 6.1. Giá trị none

```properties
jakarta.persistence.schema-generation.database.action=none
```

Có thể hình dung:

```text
EntityManagerFactory bootstrap
            |
            v
Read mapping metadata
            |
            v
No standard DDL create/drop action on DB
            |
            v
Use existing schema
```

**Không nên hiểu `none` = “đã kiểm tra schema đúng”.** Nó chỉ tắt thao tác sinh DDL trực tiếp theo cơ chế này. Provider vẫn có thể có một tính năng schema validation riêng nếu được cấu hình.

### 6.2. Giá trị create

```properties
jakarta.persistence.schema-generation.database.action=create
```

Yêu cầu provider tạo schema objects theo metadata/nguồn đã chọn.

Nó **không phải**:

```text
IF table exists THEN ALTER safely;
ELSE CREATE;
```

Một số câu lệnh có thể thất bại nếu đối tượng đã tồn tại. Đừng dùng `create` để nâng cấp production schema có dữ liệu.

### 6.3. Giá trị drop

```properties
jakarta.persistence.schema-generation.database.action=drop
```

Yêu cầu xóa schema objects. Nếu chạy trên DB thật có dữ liệu, đây là thao tác có thể gây mất dữ liệu.

### 6.4. Giá trị drop-and-create

```properties
jakarta.persistence.schema-generation.database.action=drop-and-create
```

Ý định là đưa tập đối tượng schema về cấu trúc được tạo lại:

```text
Drop existing mapped objects
             |
             v
Create mapped objects
             |
             v
Fresh schema for test data
```

Đây là lựa chọn thường hợp lý với **database tạm dành riêng cho integration tests**, không phải database production hoặc shared staging có dữ liệu cần giữ.

### 6.5. Không nhầm create với Hibernate update

Một số provider có tính năng riêng như Hibernate `hbm2ddl.auto=update`. Nhưng **`update` không phải một giá trị tiêu chuẩn của `jakarta.persistence.schema-generation.database.action`**.

Không cấu hình:

```properties
jakarta.persistence.schema-generation.database.action=update
```

rồi mong nhận được schema migration tự động theo chuẩn Jakarta Persistence.

## 7. Property scripts.action: xuất SQL thay vì chạy trực tiếp

`jakarta.persistence.schema-generation.scripts.action` kiểm soát việc **sinh SQL DDL scripts**.

| Giá trị | Hành động |
| --- | --- |
| `none` | Không xuất scripts |
| `create` | Sinh script tạo schema objects |
| `drop` | Sinh script xóa schema objects |
| `drop-and-create` | Sinh cả scripts xóa và tạo |

Ví dụ mục tiêu:

```text
JPA metadata
    |
    v
Schema generation
    |
    +-- target create.sql
    |
    +-- target drop.sql
```

### 7.1. scripts.action không tự execute create.sql

Nếu đặt:

```properties
jakarta.persistence.schema-generation.database.action=none
jakarta.persistence.schema-generation.scripts.action=create
```

thì mục tiêu là **chỉ xuất DDL tạo schema** (với script target hợp lệ), không yêu cầu trực tiếp tạo bảng qua `database.action`.

Đây là một cách tốt để **xem xét SQL sinh ra trước khi quyết định chạy trên database nào**.

### 7.2. Hai nhóm action độc lập

Có thể cấu hình:

```properties
jakarta.persistence.schema-generation.database.action=drop-and-create
jakarta.persistence.schema-generation.scripts.action=drop-and-create
```

Khi được hỗ trợ, provider có thể vừa thao tác database vừa xuất scripts.

Nhưng đừng mặc định cần cả hai. Nếu mục tiêu chỉ tạo DDL để review, hãy để `database.action=none`.

### 7.3. Chọn đích xuất SQL

Hai properties:

- `jakarta.persistence.schema-generation.scripts.create-target`.
- `jakarta.persistence.schema-generation.scripts.drop-target`.

Ví dụ minh họa trong `persistence.xml`:

```xml
<property
    name="jakarta.persistence.schema-generation.scripts.action"
    value="drop-and-create"/>

<property
    name="jakarta.persistence.schema-generation.scripts.create-target"
    value="file:/tmp/catalog-create.sql"/>

<property
    name="jakarta.persistence.schema-generation.scripts.drop-target"
    value="file:/tmp/catalog-drop.sql"/>
```

Đây là một ví dụ đường dẫn **file URL** phù hợp môi trường kiểu Unix. Trên Windows hoặc trong container/CI, phải dùng URL/path hợp lệ cho runtime thật. Thư mục đích phải tồn tại hoặc được provider/ứng dụng chuẩn bị phù hợp; provider cần quyền ghi.

Các target properties theo chuẩn có thể nhận kiểu dữ liệu được quy định như **`java.io.Writer` hoặc URL chỉ đích script** tùy cách cấu hình. Việc hỗ trợ cụ thể, encoding, tạo thư mục và lỗi I/O cần được kiểm thử với provider.

## 8. Cấu hình SQL-only đầy đủ trong persistence.xml

Ví dụ xuất DDL từ metadata, không thực thi DDL lên database:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<persistence
    xmlns="https://jakarta.ee/xml/ns/persistence"
    version="3.1">

    <persistence-unit
        name="catalogPU"
        transaction-type="RESOURCE_LOCAL">

        <class>com.example.catalog.Category</class>
        <class>com.example.catalog.Product</class>

        <properties>
            <property
                name="jakarta.persistence.schema-generation.database.action"
                value="none"/>

            <property
                name="jakarta.persistence.schema-generation.scripts.action"
                value="drop-and-create"/>

            <property
                name="jakarta.persistence.schema-generation.create-source"
                value="metadata"/>

            <property
                name="jakarta.persistence.schema-generation.drop-source"
                value="metadata"/>

            <property
                name="jakarta.persistence.schema-generation.scripts.create-target"
                value="file:/tmp/catalog-create.sql"/>

            <property
                name="jakarta.persistence.schema-generation.scripts.drop-target"
                value="file:/tmp/catalog-drop.sql"/>
        </properties>
    </persistence-unit>
</persistence>
```

Đây là cấu hình minh họa phần schema generation. Để bootstrap thực tế, persistence unit còn cần **provider/connection hoặc đủ metadata database product/version và điều kiện runtime phù hợp**. Không coi đoạn trên như một dự án tự chạy được trong mọi JVM chỉ bằng copy-paste.

### 8.1. Điều gì xảy ra trong ví dụ?

Với provider hỗ trợ và đích xuất hợp lệ:

1. Provider đọc mapping của Category và Product.
2. Provider xác định những schema objects cần tạo/xóa.
3. Provider sinh nội dung create/drop SQL.
4. Nội dung được ghi vào các targets chỉ định.
5. Vì `database.action=none`, không có yêu cầu sinh DDL trực tiếp lên database từ action này.

### 8.2. Tại sao script cần được review?

Một DDL script được sinh từ metadata có thể:

- Không bao gồm CHECK constraints quan trọng.
- Không có indexes nâng cao cần thiết.
- Không phù hợp naming convention production.
- Không chứa functions/triggers/views.
- Có statement `DROP` nguy hiểm.
- Chọn kiểu dữ liệu không tối ưu với DB.
- Chưa hỗ trợ đủ custom column definitions.
- Không xử lý backfill dữ liệu hiện hữu.

Vì vậy nó là **đầu vào để review**, không phải tự động là migration production đã an toàn.

## 9. Cấu hình database.action trong môi trường test

Một integration test dùng database rỗng và tạm thời có thể cấu hình:

```xml
<property
    name="jakarta.persistence.schema-generation.database.action"
    value="drop-and-create"/>

<property
    name="jakarta.persistence.schema-generation.scripts.action"
    value="none"/>
```

### 9.1. Điều kiện an toàn

- Database dành riêng cho test.
- Không có dữ liệu production/shared.
- Tài khoản kết nối chỉ có quyền cần thiết.
- Test tự quản lý lifecycle database.
- Không dùng cùng datasource với application production.
- Cấu hình test không bị đóng gói vào profile production.

### 9.2. Vì sao chọn drop-and-create trong test?

Một test suite cần schema xác định từ metadata mỗi lần chạy, tránh phụ thuộc vào dữ liệu hoặc các bảng từ lượt chạy cũ.

Tuy nhiên, tạo schema mới **không tự tạo đủ dữ liệu tham chiếu**, nên test fixtures/seed data vẫn cần được thiết kế.

### 9.3. Khi schema được tạo bằng migration trong tests

Một cách khác là:

```text
Test database starts empty
         |
         v
Run Flyway/Liquibase migrations
         |
         v
Bootstrap JPA with database.action=none
         |
         v
Run integration tests
```

Đây là cách thường tốt hơn khi muốn tests xác nhận **đúng schema production được tạo bởi migrations**, chứ không chỉ schema provider tự sinh từ annotations.

Hai kiểu test phục vụ mục đích khác nhau và có thể cùng tồn tại trong dự án.

## 10. Nguồn DDL: create-source và drop-source

Bên cạnh việc chọn làm gì, Jakarta Persistence cho phép chọn **nguồn thông tin DDL**.

Hai properties:

- `jakarta.persistence.schema-generation.create-source`.
- `jakarta.persistence.schema-generation.drop-source`.

Những giá trị quan trọng:

| Giá trị | Ý nghĩa |
| --- | --- |
| `metadata` | Sinh DDL từ JPA mapping metadata |
| `script` | Sử dụng DDL từ script đã cung cấp |
| `metadata-then-script` | DDL từ metadata trước, sau đó từ script |
| `script-then-metadata` | DDL từ script trước, sau đó từ metadata |

### 10.1. Nguồn metadata

```properties
jakarta.persistence.schema-generation.create-source=metadata
jakarta.persistence.schema-generation.drop-source=metadata
```

Provider dựa trên effective mapping metadata, tức phần đã được tổng hợp từ annotations, `orm.xml` và defaults tương ứng.

Đây là lựa chọn dễ hiểu nhất cho nhu cầu xem DDL mà entity mapping gợi ý.

### 10.2. Nguồn script

```properties
jakarta.persistence.schema-generation.create-source=script
```

Khi chọn `script`, phải cung cấp create script source phù hợp.

Ví dụ application có tệp DDL chuẩn do DBA quản lý. Cấu hình này cho phép schema generation dùng SQL DDL từ file thay vì suy ra toàn bộ từ annotations.

### 10.3. Kết hợp metadata và script

Với `metadata-then-script`:

```text
DDL from metadata
        |
        v
Additional DDL script
```

Đây có thể là cách thêm một số câu lệnh DDL mà mapping metadata không biểu đạt đầy đủ, nhưng phải thận trọng:

- Script không được tạo bảng/constraint trùng với metadata.
- Trình tự câu lệnh phải hợp lệ.
- Quyền database đủ.
- SQL vendor-specific được xác định rõ.
- Nếu script fail, trạng thái schema có thể đang dang dở.

Với `script-then-metadata`, script được xử lý trước, nên mọi phụ thuộc vào table/sequence phải được thiết kế phù hợp.

### 10.4. Không mặc định script source và script target là một

- **Source**: nguồn SQL mà schema generation đọc từ đó.
- **Target**: đích SQL mà schema generation ghi nội dung sinh ra.

Đừng nhầm `create-script-source` với `scripts.create-target` chỉ vì cùng chứa đường dẫn file.

## 11. Cấu hình SQL script source

Hai properties chuẩn:

- `jakarta.persistence.schema-generation.create-script-source`.
- `jakarta.persistence.schema-generation.drop-script-source`.

Ví dụ:

```xml
<property
    name="jakarta.persistence.schema-generation.create-source"
    value="script"/>

<property
    name="jakarta.persistence.schema-generation.create-script-source"
    value="file:/opt/app/schema/catalog-create.sql"/>
```

Đường dẫn ví dụ cần được thay bằng file URL hợp lệ trong môi trường đang chạy. Những nguồn này có thể được cung cấp theo kiểu dữ liệu được Jakarta Persistence định nghĩa, như URL/Reader ở cấu hình programmatic phù hợp.

### 11.1. Khi dùng metadata-then-script

```xml
<property
    name="jakarta.persistence.schema-generation.create-source"
    value="metadata-then-script"/>

<property
    name="jakarta.persistence.schema-generation.create-script-source"
    value="file:/opt/app/schema/extra-objects.sql"/>
```

Ý định: tạo objects suy từ JPA metadata rồi thực hiện thêm DDL từ script.

### 11.2. Những việc nên ghi vào extra script

- Một CHECK constraint đặc thù database.
- Một index có phương thức/expression không được mapping chuẩn mô tả.
- Một view hoặc function dùng cho test.
- Một database extension cần thiết trong test environment.

Đối với production, những phần này thường cần nằm trong **versioned migration** chứ không chỉ extra DDL gắn với bootstrap.

### 11.3. Script không được giả định chạy lại an toàn

```sql
CREATE INDEX idx_products_active
ON products(active);
```

Nếu chạy lại khi index đã tồn tại, database có thể trả lỗi. Một file DDL chuẩn bị cho schema mới **không tự là idempotent migration**.

## 12. Cài đặt mặc định của source cần hiểu kỹ

Khi người dùng không khai báo `create-source`/`drop-source`, provider áp quy tắc mặc định của Jakarta Persistence, có tính đến việc có hay không khai báo script source tương ứng.

Vì điều này dễ gây nhầm, trong môi trường cần hành vi tái lập nên khai báo **tường minh**:

```properties
jakarta.persistence.schema-generation.create-source=metadata
jakarta.persistence.schema-generation.drop-source=metadata
```

hoặc:

```properties
jakarta.persistence.schema-generation.create-source=script
jakarta.persistence.schema-generation.create-script-source=...
```

### 12.1. Không suy từ sự có mặt của file SQL

Một file `create.sql` nằm trong classpath không tự chứng minh Jakarta Persistence đang sử dụng file đó. Phải xem effective property values.

### 12.2. Không tự suy hành vi từ Hibernate cũ

`hibernate.hbm2ddl.auto`, `import.sql` hay Hibernate export tools là những cơ chế/provider conventions có thể khác schema-generation properties chuẩn.

Trong một dự án có cả hai nhóm settings, cần xác định cái nào đang tác động vào bootstrap thực tế và loại bỏ cấu hình mâu thuẫn.

## 13. SQL load script cho dữ liệu ban đầu

Sau khi tạo schema, môi trường test có thể cần dữ liệu tham chiếu:

```sql
INSERT INTO categories (id, code, name)
VALUES (10, 'KEYBOARDS', 'Keyboards');

INSERT INTO categories (id, code, name)
VALUES (20, 'MICE', 'Mice');
```

Jakarta Persistence định nghĩa:

```properties
jakarta.persistence.sql-load-script-source=...
```

Ý định của property là chỉ định **SQL script để nạp dữ liệu** theo cơ chế schema generation thích hợp.

### 13.1. Ví dụ

```xml
<property
    name="jakarta.persistence.schema-generation.database.action"
    value="drop-and-create"/>

<property
    name="jakarta.persistence.sql-load-script-source"
    value="file:/opt/app/test-data/catalog-seed.sql"/>
```

Đây là ví dụ test setup. Cần bảo đảm SQL syntax, file URL, quyền đọc và thứ tự tạo schema/nạp dữ liệu phù hợp provider/DBMS.

### 13.2. Load script không phải migration data

Script seed thường giả định schema mới, rỗng:

```sql
INSERT INTO categories (id, code, name)
VALUES (10, 'KEYBOARDS', 'Keyboards');
```

Chạy lại trên database có row ID 10 sẽ có nguy cơ unique violation.

Một data migration production thường cần:

- Kiểm tra trạng thái hiện hữu.
- Idempotency hoặc version tracking.
- Rollback/roll-forward plan.
- Backfill.
- Online compatibility.
- Audit/recovery.

**Đừng dùng SQL load script của schema generation như thay thế hệ thống seed/migration production.**

### 13.3. Độ tin cậy của dữ liệu kiểm thử

Nếu tests dựa trên ID 10, ID 20, nên giữ fixtures có chủ đích và tránh để data generation ngẫu nhiên ảnh hưởng kết quả. Với test database thật, có thể chọn chạy migrations rồi fixtures thay vì SQL load script tiêu chuẩn nếu pipeline đó gần production hơn.

## 14. Kết nối được dùng cho schema generation

Schema generation có thể cần một database connection riêng hoặc đủ metadata về database product để sinh SQL đúng dialect.

Một property tiêu chuẩn là:

```properties
jakarta.persistence.schema-generation.connection
```

Khi dùng cấu hình programmatic, nó có thể nhận một `java.sql.Connection` phù hợp với contract.

### 14.1. Ví dụ Java SE về Connection

```java
import jakarta.persistence.Persistence;
import java.sql.Connection;
import java.util.HashMap;
import java.util.Map;

Map<String, Object> props = new HashMap<>();

props.put(
    "jakarta.persistence.schema-generation.connection",
    connection
);

props.put(
    "jakarta.persistence.schema-generation.database.action",
    "create"
);

boolean invoked =
    Persistence.generateSchema("catalogPU", props);
```

Đoạn code giả định `connection` là một JDBC connection hợp lệ, được tạo/quản lý bởi caller; cần chính sách lifecycle/transaction/permissions tương ứng. Không truyền connection đang được application business transaction sử dụng tùy tiện và mong provider rollback mọi DDL được.

### 14.2. Không chạy DDL trên tài khoản ứng dụng thông thường nếu không cần

Một tài khoản runtime dùng SELECT/INSERT/UPDATE/DELETE không nhất thiết cần quyền CREATE TABLE, ALTER TABLE hoặc DROP TABLE.

**Nguyên tắc least privilege:** Production runtime nên chỉ có những quyền phục vụ nghiệp vụ, còn migrations/schema changes chạy bằng identity hoặc pipeline có quyền riêng và được kiểm soát.

### 14.3. Tự động tạo database schemas

Property:

```properties
jakarta.persistence.schema-generation.create-database-schemas=true
```

liên quan đến yêu cầu tạo database schemas/namespaces khi provider/DBMS hỗ trợ.

Đừng hiểu rằng:

- Nó tạo cả database server/instance.
- Nó cấp mọi quyền cần thiết.
- Nó tạo toàn bộ application roles.
- Nó chuyển dữ liệu giữa schemas.
- Nó luôn được mọi DBMS hỗ trợ y hệt nhau.

Trong nhiều hệ thống, **schema namespace** được DBA/migration tạo trước, còn JPA schema generation chỉ tạo tables trong namespace đã tồn tại.

## 15. Sinh DDL không có connection: database product metadata

Khi cần xuất SQL nhưng chưa có connection, provider vẫn phải biết loại database đích để chọn dialect và SQL DDL thích hợp.

Những properties liên quan có thể gồm:

```properties
jakarta.persistence.database-product-name
jakarta.persistence.database-major-version
jakarta.persistence.database-minor-version
```

### 15.1. Vì sao cần database product?

```text
Same JPA Product metadata
           |
           +-- PostgreSQL-style identity DDL
           |
           +-- MySQL-style identity/auto_increment DDL
           |
           +-- Oracle-style identity/sequence DDL
           |
           +-- SQL Server identity DDL
```

JPA metadata không thể tự quyết định tất cả dialect details nếu chưa xác định database target.

### 15.2. Không bịa version cho một database khác

Nếu khai báo product name/version không đúng DBMS production, SQL sinh ra có thể không chạy hoặc khác behavior thực tế.

Đối với một pipeline xuất DDL dùng để review, nên dùng **connection tới cùng DBMS/version test** khi có thể, hoặc cấu hình product/version chính xác theo contract provider.

### 15.3. “Không có connection” không có nghĩa runtime luôn bootstrap được

Ngay cả khi chỉ muốn xuất scripts, persistence unit/provider vẫn có thể yêu cầu cấu hình bổ sung tùy runtime. Không coi ba properties product-name/version là bảo đảm có thể khởi động mọi provider trong mọi môi trường offline.

## 16. Sinh lược đồ bằng Persistence.generateSchema()

Bên cạnh cấu hình ở `persistence.xml` khi bootstrap `EntityManagerFactory`, Jakarta Persistence cung cấp API Java SE:

```java
Persistence.generateSchema(
    String persistenceUnitName,
    Map<String, Object> properties
);
```

Một ví dụ **chỉ xuất create script**:

```java
package com.example.catalog.tools;

import jakarta.persistence.Persistence;
import java.util.HashMap;
import java.util.Map;

public final class SchemaScriptExporter {

    public static void main(String[] args) {
        Map<String, Object> properties = new HashMap<>();

        properties.put(
            "jakarta.persistence.schema-generation.database.action",
            "none"
        );

        properties.put(
            "jakarta.persistence.schema-generation.scripts.action",
            "create"
        );

        properties.put(
            "jakarta.persistence.schema-generation.create-source",
            "metadata"
        );

        properties.put(
            "jakarta.persistence.schema-generation.scripts.create-target",
            "file:/tmp/catalog-create.sql"
        );

        boolean processed = Persistence.generateSchema(
            "catalogPU",
            properties
        );

        if (!processed) {
            throw new IllegalStateException(
                "No provider generated the schema for catalogPU"
            );
        }
    }
}
```

### 16.1. Điều kiện chạy ví dụ

- `catalogPU` tồn tại và được provider nhận diện.
- Classes/mappings liên quan có trên classpath.
- Runtime có JPA provider phù hợp.
- Đường dẫn target hợp lệ và có quyền ghi.
- Provider có đủ database metadata/dialect information.
- Cấu hình datasource/connection hoặc product metadata phù hợp.
- DDL generation được provider hỗ trợ cho target.

Giá trị boolean là tín hiệu về việc xử lý lời gọi theo contract API/provider; **không thay thế việc kiểm tra file output hoặc chạy SQL trên database đích**.

### 16.2. Tại sao API programmatic hữu ích?

Có thể tạo một tooling command riêng:

```text
schema-export
    |
    +-- bootstrap mapping
    +-- generate create.sql
    +-- generate drop.sql
    +-- save artifacts
    +-- CI review / compare
```

Điều này tách việc xuất DDL khỏi runtime application startup.

### 16.3. Không dùng generateSchema() trong HTTP request

Một endpoint runtime:

```text
POST /admin/generateSchema
```

trỏ tới production DB là rủi ro vận hành lớn, đặc biệt khi có action `drop` hoặc `drop-and-create`. Schema generation nên thuộc **build/deployment/test tooling**, không phải yêu cầu người dùng cuối.

### 16.4. Không cần tạo EntityManager để sinh DDL

API `Persistence.generateSchema()` cung cấp con đường schema generation riêng trong Java SE. Nhưng trong thực tế provider bootstrap, các thao tác schema generation vẫn có thể xảy ra trong quá trình khởi tạo `EntityManagerFactory` nếu schema generation properties được cấu hình.

## 17. Bootstrap EntityManagerFactory và tác động startup

Trong một ứng dụng Java SE:

```java
EntityManagerFactory emf =
    Persistence.createEntityManagerFactory("catalogPU");
```

Nếu schema generation database action đã được cấu hình, provider có thể thực hiện DDL trong quá trình bootstrap theo contract đó.

### 17.1. Rủi ro khi mọi application instance cùng khởi động

Một hệ thống có ba nodes:

```text
Application A startup ---+
                         |
Application B startup ---+--> Same production database
                         |
Application C startup ---+
```

Nếu mỗi node đều có:

```properties
jakarta.persistence.schema-generation.database.action=create
```

chúng có thể cạnh tranh chạy DDL, gặp lỗi “table already exists”, lock schema hoặc gây gián đoạn. Với `drop-and-create`, rủi ro nghiêm trọng hơn rất nhiều.

### 17.2. Quy trình triển khai hợp lý

```text
Deployment pipeline
       |
       v
Run versioned migrations once / controlled
       |
       v
Start application instances
       |
       v
JPA runtime database.action=none
```

JPA schema generation có thể vẫn dùng ở các test/preview jobs, nhưng **không tự động đóng vai trò migration coordinator giữa các nodes**.

### 17.3. DDL và transactions

Tùy DBMS, một số DDL statements có thể tự commit, không rollback như business DML hoặc yêu cầu locks cấp schema. Không nên kỳ vọng:

```java
tx.begin();
generateSchema();
tx.rollback();
```

luôn phục hồi database về trạng thái cũ. Hành vi DDL transactions tùy DBMS/driver và không phải một bảo đảm chung từ EntityTransaction.

## 18. Schema generation từ annotations hoặc orm.xml

Schema generation dùng **effective mapping metadata**, bất kể mapping được khai báo trong Java hay XML.

### 18.1. Annotation metadata

```java
@Entity
@Table(name = "products")
public class Product {
    @Id
    private Long id;
}
```

### 18.2. XML metadata

Một mapping XML tương đương có thể là:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<entity-mappings
    xmlns="https://jakarta.ee/xml/ns/persistence/orm"
    version="3.1">

    <entity
        class="com.example.catalog.Product"
        access="FIELD"
        metadata-complete="true">

        <table name="products"/>

        <attributes>
            <id name="id">
                <column name="id"/>
            </id>
        </attributes>
    </entity>
</entity-mappings>
```

Trong `persistence.xml`:

```xml
<mapping-file>META-INF/orm.xml</mapping-file>
```

Nếu hai mapping mô tả cùng entity structure, provider có thể sinh DDL có ý nghĩa tương đương theo cùng dialect.

### 18.3. XML override cũng ảnh hưởng generated schema

Nếu Java có:

```java
@Table(name = "products")
```

nhưng `orm.xml` override table thành `catalog_products`, schema generation dựa trên **effective mapping** có thể tạo/nhắm tới bảng `catalog_products`, không phải tên source annotation đang thấy.

Do đó khi debug tên bảng/cột bất ngờ phải kiểm tra cả annotations, XML và naming strategy.

### 18.4. metadata-complete cần thận trọng

Nếu XML bật `metadata-complete` mà không khai báo đủ các mapping cần thiết, generated DDL có thể không có các cột/quan hệ như developer tưởng tượng.

Đừng đánh đồng “EntityManagerFactory bootstrap không báo lỗi” với “schema generated đúng mọi business requirement”.

## 19. Những thành phần lược đồ JPA có thể gợi ý tạo

Một số mapping metadata tiêu chuẩn đóng góp vào schema generation.

| Metadata | Schema element thường liên quan |
| --- | --- |
| `@Entity`, `@Table` | Bảng entity |
| `@Id` | Khóa chính |
| `@GeneratedValue` | IDENTITY/sequence/table generator infrastructure |
| `@Column` | Cột cơ bản, nullability, length, precision, scale |
| `@ManyToOne`, `@JoinColumn` | Foreign key column, FK constraint |
| `@OneToOne`, `@JoinColumn` | FK/uniqueness tùy quan hệ |
| `@ManyToMany`, `@JoinTable` | Bảng liên kết |
| `@ElementCollection`, `@CollectionTable` | Bảng value collection |
| `@Version` | Version column |
| `@UniqueConstraint` | Unique constraint |
| `@Index` | Index |
| `@SequenceGenerator` | Sequence hoặc cấu trúc ID generation |
| `@Inheritance` | Bảng theo inheritance strategy |
| `@Embedded` | Cột của embeddable trong owner |
| `@AttributeOverride` | Tên/đặc tính cột được override |

### 19.1. “Gợi ý tạo” không đồng nghĩa vendor hỗ trợ y hệt

Các DBMS có khác biệt về:

- Generated columns.
- Constraints và index types.
- Case-sensitive identifiers.
- Schema/catalog.
- Sequence semantics.
- Column length và Unicode.
- Temporal precision.
- Identity syntax.
- Table options, storage engines, partitions.

Provider/dialect quyết định cách chuyển metadata thành SQL.

### 19.2. Một số đối tượng vượt ngoài phạm vi JPA metadata chuẩn

Ví dụ:

- Partial indexes, functional indexes hoặc index INCLUDE.
- Materialized views.
- Advanced CHECK constraints.
- Triggers/functions/procedures.
- Row-level security policies.
- Partitioned tables.
- Exclusion constraints.
- Database grants/roles.
- Advanced collation/compression settings.

Các nhu cầu đó thường cần **SQL migrations** hoặc provider-specific schema tooling.

## 20. Foreign keys, unique constraints và indexes

Ví dụ Product dùng:

```java
@ManyToOne(optional = false)
@JoinColumn(
    name = "category_id",
    nullable = false,
    foreignKey = @ForeignKey(
        name = "fk_product_category"
    )
)
private Category category;
```

### 20.1. Tác dụng với DDL

Provider có thể tạo column và foreign key liên quan. Nhưng trong DBMS thật, tên constraint và cách thực hiện DDL cần được kiểm tra.

### 20.2. Nullability không phải business validation đầy đủ

```java
@Column(nullable = false)
private String sku;
```

metadata này có thể góp phần sinh `NOT NULL`. Nó không chứng minh:

- SKU không chứa whitespace.
- SKU theo đúng format.
- SKU được phép trong tenant.
- SKU chưa bị chọn bởi transaction khác trước commit.

Bean Validation, domain checks và DB unique constraint vẫn có vai trò riêng.

### 20.3. Unique constraint cho tranh chấp đồng thời

```java
@Table(
    uniqueConstraints = @UniqueConstraint(
        columnNames = "sku"
    )
)
```

có thể hướng provider tạo unique constraint. Nếu database production đã được migration tạo, phải kiểm tra constraint thật sự tồn tại. Java check “SKU chưa có” không bảo vệ hoàn toàn dưới concurrency.

### 20.4. Index không tự là giải pháp performance

```java
@Table(
    indexes = @Index(
        columnList = "category_id"
    )
)
```

chỉ mô tả ý định có index. Có nên dùng index đó, có đủ để tối ưu truy vấn không, hoặc có làm UPDATE chậm hơn không là câu hỏi cần đo bằng query plans và workload thật.

### 20.5. FK không phải CascadeType.REMOVE

`CascadeType.REMOVE` của JPA là propagation của entity lifecycle operation. Một database `ON DELETE CASCADE` là cơ chế SQL schema khác. Đừng suy `cascade = CascadeType.ALL` luôn làm DDL FK có `ON DELETE CASCADE`.

## 21. Quan hệ nhiều-nhiều và bảng trung gian

Giả sử:

```java
@Entity
public class Student {

    @Id
    private Long id;

    @ManyToMany
    @JoinTable(
        name = "student_courses",
        joinColumns = @JoinColumn(
            name = "student_id"
        ),
        inverseJoinColumns = @JoinColumn(
            name = "course_id"
        )
    )
    private Set<Course> courses = new HashSet<>();
}
```

Entity Course:

```java
@Entity
public class Course {
    @Id
    private Long id;
}
```

Schema generation có thể tạo bảng trung gian:

```sql
CREATE TABLE student_courses (
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student(id),
    FOREIGN KEY (course_id) REFERENCES course(id)
);
```

Đây là DDL minh họa; chi tiết key/constraints có thể phụ thuộc mapping/provider.

### 21.1. @JoinTable là metadata cho liên kết

JPA có thể sinh bảng liên kết nếu metadata và action yêu cầu. Nhưng không tự quyết định mọi business constraint trên registration, như hạn mức số môn được đăng ký hoặc uniqueness theo học kỳ.

### 21.2. Khi bảng liên kết có dữ liệu riêng

Nếu quan hệ cần `enrolledAt`, `grade`, `status`, thường nên xem xét **association entity** thay vì `@ManyToMany` thuần. Schema generation sẽ phản ánh mô hình đã chọn, không thay quyết định domain này.

## 22. ElementCollection, Embedded và inheritance

### 22.1. Embedded value object

```java
@Embeddable
public class Dimensions {
    private BigDecimal width;
    private BigDecimal height;
    private BigDecimal depth;
}
```

```java
@Embedded
private Dimensions dimensions;
```

Các attributes của embeddable thường được map thành columns trong bảng owner theo metadata và `@AttributeOverride` nếu có.

### 22.2. ElementCollection

```java
@ElementCollection
@CollectionTable(
    name = "product_tags",
    joinColumns = @JoinColumn(
        name = "product_id"
    )
)
@Column(name = "tag", length = 50)
private Set<String> tags;
```

Schema generation có thể cần bảng `product_tags` riêng. Nhưng một custom uniqueness rule hoặc index đặc thù cho tag search cần được kiểm tra/thiết kế thêm.

### 22.3. Inheritance strategies

Các mapping strategies phổ biến:

- `SINGLE_TABLE`: thường một bảng cho hierarchy.
- `JOINED`: root/subclass tables liên kết qua keys.
- `TABLE_PER_CLASS`: nhiều bảng theo concrete classes, với trade-offs trong polymorphic queries.

Schema generation có thể tạo **cấu trúc bảng rất khác nhau** tùy strategy.

### 22.4. Vì sao migration inheritance nguy hiểm?

Nếu đang dùng `SINGLE_TABLE` mà đổi thành `JOINED`, đây là thay đổi storage architecture. Không thể chỉ đổi `@Inheritance` rồi dựa vào `create` để giữ dữ liệu hiện hữu.

Cần migration chuyển dữ liệu, foreign keys, indexes và xử lý compatibilities.

## 23. Sinh ID và database structures

JPA hỗ trợ:

```java
GenerationType.IDENTITY
GenerationType.SEQUENCE
GenerationType.TABLE
GenerationType.AUTO
```

### 23.1. IDENTITY

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Database có thể cần identity/auto-increment syntax đặc thù.

### 23.2. SEQUENCE

```java
@Id
@SequenceGenerator(
    name = "product_seq_gen",
    sequenceName = "product_seq",
    allocationSize = 25
)
@GeneratedValue(
    strategy = GenerationType.SEQUENCE,
    generator = "product_seq_gen"
)
private Long id;
```

Provider có thể cần một sequence phù hợp và dùng allocation strategy liên quan. Khi schema được tạo từ migration thay vì JPA, migration phải định nghĩa sequence đúng tên/cấu hình mà runtime kỳ vọng.

### 23.3. AUTO

`GenerationType.AUTO` cho phép provider chọn strategy phù hợp. Điều này làm SQL/DDL khác giữa providers/databases. Nếu muốn predictability cao trong một legacy schema, explicit strategy thường dễ kiểm soát hơn.

### 23.4. TABLE generator

Có thể dùng một bảng phụ để cấp ID theo strategy tương ứng. Nếu mapping đổi từ TABLE sang SEQUENCE, migration phải xử lý dữ liệu/trạng thái generator, tránh trùng IDs.

### 23.5. Không xóa sequence production tùy tiện

`drop-and-create` có thể tác động đến schema objects như sequence; không dùng trên DB đang giữ dữ liệu hoặc nơi phải duy trì ID continuity.

## 24. Kiểu dữ liệu SQL và giới hạn portability

Cùng một Java type có thể ánh xạ thành các SQL types khác nhau:

| Java attribute | SQL type thường gặp | Lưu ý |
| --- | --- | --- |
| `String` | VARCHAR/NVARCHAR/... | Unicode, length, collation |
| `Long` | BIGINT | Range/identity |
| `BigDecimal` | NUMERIC/DECIMAL | Precision/scale |
| `Boolean` | BOOLEAN/BIT/SMALLINT | DBMS-specific representation |
| `Instant` | TIMESTAMP/TIMESTAMP WITH TIME ZONE hoặc loại tương đương | Time zone semantics |
| `LocalDate` | DATE | DB date behavior |
| `EnumType.STRING` | VARCHAR hoặc type đặc thù | Rename enum constant, size |
| `byte[]` | VARBINARY/BLOB/... | LOB behavior, performance |
| `UUID` | UUID/BINARY/VARCHAR tùy DBMS/provider | Dialect/version |

### 24.1. columnDefinition giảm tính portable

```java
@Column(
    name = "payload",
    columnDefinition = "jsonb"
)
private String payload;
```

Trong PostgreSQL, `jsonb` có ý nghĩa cụ thể. Trên DBMS khác, SQL đó có thể không hợp lệ. Đây là lựa chọn cố ý phụ thuộc dialect, không phải một bảo đảm portable.

### 24.2. Enum ordinal vs string

```java
@Enumerated(EnumType.ORDINAL)
private Status status;
```

Schema generation có thể tạo một cột số, nhưng nếu thay thứ tự enum constants trong Java, dữ liệu cũ có thể bị hiểu sai.

`EnumType.STRING` thường dễ đọc hơn nhưng vẫn cần quy tắc migration khi đổi tên constant. Sinh schema không tự quản lý semantic migration đó.

### 24.3. Thời gian và time zones

Schema generation tạo cột timestamp theo provider mapping. Nó không tự quyết định mọi chính sách lưu timezone, hiển thị local time hoặc xử lý daylight saving. Cần thiết kế domain/time policy riêng.

## 25. Tên bảng, schema và catalog

Metadata có thể chỉ định:

```java
@Table(
    name = "products",
    schema = "shop_core"
)
```

Hoặc qua `orm.xml`:

```xml
<table
    name="products"
    schema="shop_core"/>
```

### 25.1. Điều gì có thể xảy ra?

Provider có thể đưa schema qualifier vào DDL hoặc các câu SQL khác. Nhưng schema namespace `shop_core` phải tồn tại hoặc được tạo theo cơ chế phù hợp.

### 25.2. Không hiểu nhầm create-database-schemas

`jakarta.persistence.schema-generation.create-database-schemas` không phải công cụ tự tạo database server, user/role hay migrate permissions. Cần xem khả năng hỗ trợ của provider và DBMS.

### 25.3. Vấn đề case và quoting

Tên như `Order`, `User`, `Group` có thể là SQL reserved words. Naming strategy/identifier quoting khác nhau giữa DBMS; generated DDL có thể sai hoặc khó portable nếu không có quy tắc đặt tên rõ.

### 25.4. Nhiều persistence units

Mỗi persistence unit có thể có mappings/schema generation configuration riêng. Không tự chạy `drop-and-create` cho unit A khi datasource thực tế trỏ tới shared schema của unit B.

## 26. Sự khác nhau giữa chuẩn JPA và tùy chọn Hibernate

Rất nhiều tài liệu Spring/Hibernate sử dụng:

```properties
hibernate.hbm2ddl.auto=create
hibernate.hbm2ddl.auto=update
hibernate.hbm2ddl.auto=validate
hibernate.hbm2ddl.auto=create-drop
```

Hoặc trong Spring Boot:

```properties
spring.jpa.hibernate.ddl-auto=validate
```

### 26.1. Đây không phải cùng namespace chuẩn

`hibernate.hbm2ddl.auto` và `spring.jpa.hibernate.ddl-auto` là cơ chế cấu hình Hibernate/Spring, không phải property `jakarta.persistence.schema-generation.database.action`.

### 26.2. Giá trị update/validate/create-drop

Trong Hibernate, `update`, `validate`, `create-drop` có meanings riêng theo version. Đừng mặc định JPA `database.action` hỗ trợ cùng tập giá trị.

| Nhu cầu | Jakarta Persistence schema generation | Provider/framework extensions |
| --- | --- | --- |
| Không tạo/xóa DB | `database.action=none` | Thường có giá trị tương đương |
| Tạo schema | `create` | Có |
| Xóa schema | `drop` | Có |
| Xóa rồi tạo | `drop-and-create` | Có cách riêng |
| Cập nhật schema từng phần | **Không có action `update` chuẩn** | Hibernate-specific |
| So khớp schema không sửa | **Không phải action `validate` chuẩn** | Hibernate-specific |
| Tự drop khi session factory đóng | **Không phải `create-drop` chuẩn** | Hibernate-specific |

### 26.3. Không dùng hai cơ chế chồng chéo thiếu kiểm soát

Nếu ứng dụng cấu hình cả standard schema-generation properties và Hibernate DDL settings, có nguy cơ hiểu nhầm effective behavior.

Nên chọn một chính sách rõ:

- Migration pipeline tạo/cập nhật schema.
- Runtime DDL action được tắt.
- Provider-specific validation nếu muốn kiểm tra schema.
- Tests dùng schema generation tạm khi thật sự cần.

### 26.4. Không coi validate là kiểm tra đầy đủ mọi invariant

Ngay cả công cụ provider-specific `validate` cũng có thể chỉ xác minh một phần cấu trúc bảng/cột/types. Nó không thay thế integration tests, constraints và kiểm thử business rules.

## 27. Vì sao schema generation không phải migration?

Giả sử phiên bản 1 của ứng dụng có:

```sql
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

Phiên bản 2 thêm:

```java
@Column(nullable = false, length = 50)
private String sku;
```

Trong database production, đã có 2 triệu rows.

### 27.1. Bài toán migration thật sự

Làm thế nào:

1. Thêm cột mà không làm gián đoạn hệ thống?
2. Gán giá trị `sku` hợp lệ cho 2 triệu rows?
3. Tránh ghi trùng giữa application cũ/mới?
4. Tạo UNIQUE constraint sau backfill?
5. Cho phép rollback application version nếu cần?
6. Đồng bộ APIs và consumers đang dùng schema?
7. Kiểm tra hiệu năng index build?
8. Ghi lại rằng migration đã chạy chính xác một lần?

Một lệnh `create` không giải quyết bộ câu hỏi trên.

### 27.2. Migration theo hướng expand–migrate–contract

Ví dụ:

```text
V1 existing:
  products(id, name)

Expand:
  ADD COLUMN sku nullable
  Deploy code supporting both states

Migrate:
  Backfill sku in controlled batches
  Detect/resolve duplicates
  Add indexes / unique constraints

Contract:
  Enforce NOT NULL
  Remove backward compatibility later
```

Đây là kiến trúc triển khai có phiên bản, không phải schema generation từ mapping hiện tại.

### 27.3. Công cụ migration

Trong Java ecosystem, những lựa chọn thông dụng gồm Flyway và Liquibase. Chúng theo dõi lịch sử migration và thứ tự áp dụng. Chọn công cụ nào tùy stack và vận hành.

### 27.4. Có thể dùng generated DDL làm bản nháp không?

Có. Một quy trình:

```text
Edit JPA entities
       |
       v
Generate create.sql against empty schema
       |
       v
Compare with previous schema/migrations
       |
       v
Author versioned ALTER migration manually
       |
       v
Review + test with realistic data
       |
       v
Deploy migration
```

**Không** copy một `CREATE TABLE` mới thay cho `ALTER TABLE` trên bảng production đang có dữ liệu.

## 28. Chọn chiến lược theo môi trường

| Môi trường | Mục tiêu | Gợi ý |
| --- | --- | --- |
| Local prototype | Khởi tạo nhanh database rỗng | Schema generation có thể hữu ích |
| Unit tests thuần Java | Không cần DB | Không cần sinh schema |
| Integration tests trên DB tạm | Tạo schema sạch để test mappings | `drop-and-create` trên DB tạm nếu phù hợp |
| Integration tests xác minh migrations | Cấu trúc giống production | Chạy migrations, `database.action=none` |
| Shared development DB | Bảo toàn dữ liệu nhóm | Ưu tiên migrations, không drop tự động |
| Staging | Kiểm tra rollout production | Migration pipeline có kiểm soát |
| Production | Không mất dữ liệu; deploy nhiều nodes | Migration có version; runtime `none` |
| SQL DDL preview job | Sinh DDL để review | `scripts.action=create`, `database.action=none` |

### 28.1. Cấu hình test mẫu

```properties
jakarta.persistence.schema-generation.database.action=drop-and-create
jakarta.persistence.schema-generation.scripts.action=none
```

Chỉ dùng với datasource tạm mà test sở hữu.

### 28.2. Cấu hình production mẫu

```properties
jakarta.persistence.schema-generation.database.action=none
jakarta.persistence.schema-generation.scripts.action=none
```

Kết hợp migration và kiểm tra schema theo workflow sản phẩm.

### 28.3. Nguy hiểm khi copy config test sang production

Chỉ một biến môi trường hoặc profile sai có thể khiến runtime cố `DROP TABLE` lúc khởi động.

Cần tách cấu hình test/prod, giới hạn database privileges và có kiểm tra deployment nhằm ngăn action phá hủy.

## 29. Quyền database và tách trách nhiệm

Một account runtime app có thể chỉ cần:

```text
SELECT
INSERT
UPDATE
DELETE
EXECUTE (nếu dùng procedure)
```

Một migration job lại cần:

```text
CREATE
ALTER
DROP
CREATE INDEX
...
```

### 29.1. Vì sao least privilege quan trọng?

Nếu production runtime vô tình mang cấu hình `drop-and-create` nhưng DB user không có quyền DROP TABLE, nguy cơ mất dữ liệu do cấu hình sai có thể giảm đáng kể.

Tuy nhiên, thiếu quyền khiến schema generation lỗi khi thực sự cần. Cần **separation of duties** rõ:

- Migration identity có quyền DDL có kiểm soát.
- App identity có quyền DML tối thiểu.
- Test DB identity có quyền tạo/xóa trên DB tạm.

### 29.2. Không tự động sinh schema trên database chung

Một database dùng chung nhiều applications có thể có những tables không thuộc JPA mapping của một ứng dụng. `drop`/`drop-and-create` với cấu hình sai có thể gây tác động không mong muốn.

### 29.3. Backup không thay thế migration review

Có backup là cần thiết nhưng không có nghĩa có thể chạy DDL phá hủy tùy ý. Restore production có thể làm mất các giao dịch mới hơn điểm backup và tốn nhiều thời gian.

## 30. Tính tái lập và ổn định của generated DDL

Cùng model nhưng khác:

- JPA provider version.
- Database dialect.
- JDBC driver version.
- Naming strategy.
- Default schema/catalog.
- Mapping XML.
- Identifier quoting.
- Generator strategy.
- Enum mapping.
- Time precision.
- Cấu hình custom type.

có thể tạo DDL khác nhau.

### 30.1. Vì sao generated DDL diff có thể nhiễu?

Provider có thể đổi thứ tự `CREATE TABLE` hoặc tên constraint tự sinh khi nâng version, dù schema semantics không đổi.

Không coi một diff dài của SQL export là bằng chứng rằng domain model đã thay đổi nhiều như vậy. Cần so sánh semantics và schema thật.

### 30.2. Cố định những thông số quan trọng

Để DDL preview ổn định:

- Cố định provider và version.
- Cố định DBMS/dialect đích.
- Sử dụng explicit table/column/index/constraint names khi quan trọng.
- Cố định effective mapping resources.
- Ghi rõ schema/catalog.
- Dùng integration test DBMS gần production.
- Giữ migration làm nguồn sự thật về schema đã triển khai.

### 30.3. Đừng dùng DDL export làm checksum duy nhất

Một SQL export khác do thứ tự câu lệnh không nhất thiết là schema khác. Ngược lại, script trông giống nhưng DB hiện hữu có data, triggers hoặc custom indexes khác vẫn có rủi ro.

## 31. Kiểm thử schema generation trên database thật

Một test tốt không chỉ xác nhận `EntityManagerFactory` tạo thành công. Nó kiểm tra **hành vi lưu trữ**.

### 31.1. Kiểm thử bootstrap

- Persistence unit được nhận diện.
- Entities Category/Product được map.
- Metadata source annotations/orm.xml được load.
- Schema generation action được áp dụng đúng cấu hình.
- Nếu export scripts, file được tạo và không rỗng.

### 31.2. Kiểm thử cấu trúc

- Bảng `categories` và `products` tồn tại.
- Product ID column có behavior generation phù hợp.
- Cột `price` có precision/scale mong đợi.
- `category_id` không null và FK hợp lệ.
- SKU unique constraint tồn tại.
- Index phục vụ category lookup tồn tại nếu được yêu cầu.
- Version mapping phù hợp.

### 31.3. Kiểm thử persist và đọc lại

```java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Category category = new Category(
        10L, "KEYBOARDS", "Keyboards"
    );

    em.persist(category);

    Product product = new Product(
        "KB-101",
        "Mechanical Keyboard",
        new BigDecimal("120.00"),
        category
    );

    em.persist(product);
    em.flush();

    Long productId = product.getId();

    tx.commit();

    // Một EntityManager khác sẽ xác nhận round-trip.
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
} finally {
    em.close();
}
```

Đoạn code minh họa; `EntityManagerFactory` và imports cần được cung cấp. Trong test thật, dùng DB/IDs độc lập để tránh va chạm với fixtures khác.

### 31.4. Xác nhận từ EntityManager mới

Nếu cùng `EntityManager` vừa persist rồi `find()` lại, L1 có thể trả object đang managed mà không cần SELECT. Để kiểm thử mapping và data round-trip, hãy tạo **EntityManager mới sau commit** và query lại.

### 31.5. Kiểm thử lỗi constraint

Thử:

- Product thiếu Category.
- Hai Products trùng SKU.
- Category ID không tồn tại ở FK.
- Tạo Product có column data vượt giới hạn.
- Cập nhật Product với version cũ.
- Lưu OrderLine không hợp lệ nếu có mapping tương ứng.

Những lỗi có thể lộ ở flush/commit. Dùng transaction riêng và rollback/cleanup đúng.

### 31.6. Thực thi với DBMS đích

Nếu production dùng PostgreSQL, test JPA schema generation trên H2 chỉ chứng minh behavior của H2/Hibernate configuration tương ứng, không bảo đảm PostgreSQL tương đương.

Có thể dùng database container hoặc test instance của cùng DBMS/version, nhưng vẫn phải kiểm soát dữ liệu và permissions.

## 32. Kiểm thử migration khác kiểm thử schema generation

Hai quy trình:

**A — Entity mapping smoke test**

```text
Blank temporary DB
     |
     v
JPA drop-and-create
     |
     v
Persist/read/update test
```

**B — Production schema contract test**

```text
Blank temporary DB
     |
     v
Run real Flyway/Liquibase migrations
     |
     v
JPA database.action=none
     |
     v
Persist/read/update test
```

### 32.1. Vì sao cần bài test B?

Vì application production thường chạy trên **schema do migrations tạo**, không phải schema được JPA sinh từ annotations. Hai schema có thể lệch:

- Migration thiếu một cột mới.
- Annotation nullable=false nhưng DB chưa enforce NOT NULL.
- Foreign key chưa được tạo.
- Index chưa có.
- Tên sequence khác.
- Enum storage không đồng bộ.
- Lược đồ có view/trigger/business constraint do migration bổ sung.

Bài test B giúp phát hiện khoảng cách giữa mapping runtime và schema thật.

### 32.2. Không chạy cả hai cách trên cùng DB test một cách ngẫu nhiên

Nếu test chạy migrations rồi JPA lại `drop-and-create`, nó có thể phá schema vừa được tạo và làm kết quả test sai ý định.

Chọn rõ ai là **schema owner** của mỗi test suite.

## 33. Tạo SQL script để code review

Một workflow thực dụng:

1. Developer đổi mapping.
2. Tool gọi schema generation `scripts.action=create` và `database.action=none`.
3. Generated SQL được lưu làm artifact CI.
4. Reviewer xem kiểu cột, FK, index, sequence.
5. Developer soạn migration versioned nếu database schema thật phải đổi.
6. Migration được kiểm thử với dữ liệu mẫu hoặc snapshot an toàn.
7. Deploy migration theo quy trình.
8. Runtime JPA chạy với `database.action=none`.

### 33.1. Vì sao không commit generated create.sql thành migration luôn?

Một create script mô tả **schema cuối** khi bắt đầu từ database rỗng; migration thường mô tả **phần thay đổi** từ phiên bản trước.

Ví dụ:

```sql
CREATE TABLE products (...);
```

không phải câu lệnh thích hợp để thêm một cột vào bảng Products đã có 2 triệu rows.

### 33.2. Khi nào generated SQL có thể chạy trực tiếp?

Trong database test mới tinh, hoặc lúc bootstrap một instance hoàn toàn rỗng được kiểm soát, generated create.sql có thể hữu ích. Vẫn cần xem DB dialect, object permissions và thiếu các custom schema objects.

### 33.3. Cần xem xét drop script riêng

Drop script chứa những câu lệnh phá hủy. Không gộp việc review `create.sql` và `drop.sql` thành một “DDL artifact an toàn” nếu môi trường có dữ liệu cần giữ.

## 34. Sự khác nhau giữa quyền sinh schema và trách nhiệm dữ liệu

Schema generation biết metadata:

```text
Product.price -> NUMERIC(14,2)
Product.category -> category_id FK
Product.version -> version column
```

Nhưng nó không biết toàn bộ những câu hỏi nghiệp vụ:

- Giá có được âm không?
- Product có được chuyển tenant không?
- Có được xóa Category còn Products không?
- Những Product cũ phải có SKU gì sau migration?
- Dữ liệu cần mã hóa khi lưu không?
- Audit history phải được giữ bao lâu?
- Có cần row-level security không?
- Có thể cho bản ứng dụng cũ chạy song song không?

Các câu hỏi đó cần domain design, database rules, migrations, security và transaction strategy.

### 34.1. Không nên suy từ @Column(nullable=false) ra quality data

Một cột NOT NULL có thể chứa chuỗi rỗng, SKU sai format, hoặc giá không hợp lệ nếu schema không có ràng buộc tương ứng. Bean Validation/domain methods vẫn cần thiết.

### 34.2. Constraint do JPA sinh có thể chưa đủ

Một database production có thể cần thêm CHECK, partial unique index, FK ON DELETE behavior, custom function hoặc policy. Những đối tượng đó phải được quản lý bên ngoài metadata JPA chuẩn nếu không diễn đạt được.

### 34.3. Schema generation không thay transaction isolation

Dù FK/UNIQUE được tạo đúng, ứng dụng vẫn có thể gặp lock waits, deadlocks, stale writes hoặc business invariants nhiều hàng. Cần transaction, locking, versioning và error handling riêng.

## 35. Những sai lầm thường gặp

### Sai lầm 1 — Coi schema generation là schema migration

`create` không có nghĩa “thêm cột thiếu và giữ tất cả dữ liệu”.

### Sai lầm 2 — Dùng drop-and-create trên production

Có thể xóa tables và dữ liệu. Chỉ dùng trên DB tạm không chứa dữ liệu cần giữ.

### Sai lầm 3 — Nghĩ database.action=none sẽ validate schema

Không. Nó chỉ không yêu cầu tạo/xóa DDL qua action chuẩn.

### Sai lầm 4 — Dùng giá trị update cho property chuẩn

`update` không thuộc tập action tiêu chuẩn của `jakarta.persistence.schema-generation.database.action`.

### Sai lầm 5 — Nhầm scripts.action với database.action

Scripts action sinh file SQL; database action yêu cầu thao tác DB trực tiếp.

### Sai lầm 6 — Đặt scripts.action=create nhưng không cung cấp create-target phù hợp

Nếu không có đích output hợp lệ, provider có thể không ghi được script hoặc báo lỗi.

### Sai lầm 7 — Nhầm create-script-source với scripts.create-target

Source là file SQL đầu vào; target là nơi ghi SQL đầu ra.

### Sai lầm 8 — Cung cấp script mà không xác định create-source

Defaults có thể khiến hành vi khác dự đoán. Cấu hình source rõ ràng khi cần reproducibility.

### Sai lầm 9 — Nghĩ @DecimalMin tự tạo CHECK theo mọi provider

Bean Validation và DDL schema generation là những cơ chế khác nhau.

### Sai lầm 10 — Nghĩ @Column(nullable=false) bảo vệ tất cả business rules

NOT NULL chỉ là một constraint cụ thể; cần validation/domain checks khác.

### Sai lầm 11 — Nghĩ @Index tự tối ưu mọi query

Index là một cấu trúc có chi phí và hiệu quả phụ thuộc workload.

### Sai lầm 12 — Nghĩ CascadeType.REMOVE tự thành ON DELETE CASCADE

JPA cascade lifecycle không giống FK cascade ở database.

### Sai lầm 13 — Quên schema/catalog khi dùng default khác

Provider có thể tạo bảng ở namespace khác nơi migration/ứng dụng mong đợi.

### Sai lầm 14 — Quên quyền DDL

Ứng dụng dùng runtime DML account có thể không tạo/xóa được schema objects.

### Sai lầm 15 — Cho mỗi app node tự tạo schema khi startup

Dễ xung đột DDL, tranh locks và gây rủi ro dữ liệu.

### Sai lầm 16 — Dựa vào khả năng rollback DDL mà không kiểm chứng DBMS

Một số DDL có autocommit hoặc hành vi transaction đặc thù; không có bảo đảm chung để rollback mọi thay đổi.

### Sai lầm 17 — Thay annotation rồi tin DB đã đổi

Mapping metadata và schema database có thể lệch cho tới khi migration chạy.

### Sai lầm 18 — Đổi IDENTITY sang SEQUENCE mà không migrate schema

Generated ID infrastructure có thể không tương thích.

### Sai lầm 19 — Đổi inheritance strategy bằng annotation rồi khởi động lại

Schema/data layout thay đổi lớn, cần migration có kế hoạch.

### Sai lầm 20 — Dùng columnDefinition vendor-specific và gọi DDL portable

Cú pháp SQL có thể không hợp lệ trên DBMS khác.

### Sai lầm 21 — Coi SQL export là migration production hoàn chỉnh

Nó thường mô tả schema mới, không giải quyết dữ liệu/rollout/version history.

### Sai lầm 22 — Chỉ test với DB in-memory khác production

Các SQL types, constraints và identity semantics có thể khác.

### Sai lầm 23 — Dùng cùng EntityManager để khẳng định round-trip database

L1 cache có thể che lỗi đọc từ DB.

### Sai lầm 24 — Nhầm Hibernate ddl-auto với Jakarta Persistence standard schema generation

Chúng là những tập cấu hình khác nhau, có hành vi và giá trị riêng.

### Sai lầm 25 — Dùng SQL load script cho data migrations production

Seed scripts thường giả định DB rỗng; không có version tracking hay backfill strategy.

### Sai lầm 26 — Tin mọi XML mapping sẽ tự được load

`orm.xml` phải nằm đúng resource/path và persistence unit phải nhận metadata tương ứng.

### Sai lầm 27 — Quên kiểm tra effective mapping khi có XML override

Generated schema phản ánh effective mapping, không nhất thiết annotation đơn lẻ đang nhìn thấy.

### Sai lầm 28 — Cho rằng generateSchema trả true = DDL production đã an toàn

Phải kiểm tra file, SQL syntax, schema thực, privileges và migration requirements.

### Sai lầm 29 — Không phân biệt DDL preview và DB execution

Một script được sinh không có nghĩa nó đã chạy; một DDL đã chạy không có nghĩa application data đã được seed.

### Sai lầm 30 — Cho rằng schema generation tạo đủ triggers, views, roles và security policies

Nhiều đối tượng vượt ngoài metadata JPA chuẩn và cần migrations/vendor tooling.

## 36. Bài tập thực hành

### Bài 1 — Chọn action cho production

Production DB đã có dữ liệu và Flyway migrations.

**Đáp án:** `jakarta.persistence.schema-generation.database.action=none`; dùng migrations để thay đổi schema.

### Bài 2 — Database test rỗng

Một integration test sở hữu database tạm, muốn mỗi lần chạy có schema sạch.

**Gợi ý:** Có thể dùng `drop-and-create` nếu provider/DBMS hỗ trợ, nhưng xác nhận datasource đúng DB tạm.

### Bài 3 — Xuất DDL mà không thao tác DB

Muốn tạo `create.sql` để review.

**Đáp án:** `database.action=none`, `scripts.action=create`, `create-source=metadata` và `scripts.create-target` hợp lệ.

### Bài 4 — Chỉ muốn DROP script

Muốn xem những objects mà provider dự kiến xóa.

**Đáp án:** `scripts.action=drop` với `scripts.drop-target`, còn `database.action=none` để không xóa database thật.

### Bài 5 — Tạo schema từ script có sẵn

Một DBA đã cung cấp `catalog-create.sql`.

**Gợi ý:** `create-source=script` và `create-script-source` phù hợp; xác định database action hoặc scripts action theo ý định.

### Bài 6 — Tạo bảng và custom CHECK

Metadata sinh bảng Product, cần thêm CHECK(price >= 0) trong test.

**Gợi ý:** Có thể dùng `metadata-then-script` với script DDL bổ sung đúng thứ tự, hoặc migrations nếu mục tiêu là production.

### Bài 7 — Thêm cột NOT NULL cho dữ liệu legacy

Có 1 triệu Product rows, cần thêm `sku` bắt buộc.

**Đáp án:** Dùng versioned migration/backfill/constraint rollout, không dùng `create` như auto-update.

### Bài 8 — DB chưa có schema namespace

Mapping dùng `@Table(schema="shop_core")` nhưng namespace chưa tồn tại.

**Đáp án:** Tạo namespace qua migration/DBA hoặc schema generation có hỗ trợ/permissions rõ. `create-database-schemas` không là lời hứa tạo cả database server.

### Bài 9 — Hibernate update

Team cấu hình:

```properties
jakarta.persistence.schema-generation.database.action=update
```

**Đáp án:** Sai tập giá trị chuẩn. Hibernate `update` là extension/provider configuration, không phải Jakarta Persistence standard action.

### Bài 10 — Source và target

`create-script-source` và `scripts.create-target` khác nhau thế nào?

**Đáp án:** Một bên là SQL DDL nguồn để đọc, bên kia là file/Writer đích để ghi generated script.

### Bài 11 — Test thực sự đọc DB

Persist Product rồi `find` ngay trong cùng EntityManager.

**Hỏi:** Đã kiểm tra mapping đọc database chưa?

**Đáp án:** Chưa chắc; L1 có thể trả managed instance. Tạo EntityManager mới sau commit.

### Bài 12 — Enum migration

Entity đổi từ ORDINAL sang STRING.

**Đáp án:** Cần migration dữ liệu/cột phù hợp; schema generation không tự chuyển ý nghĩa dữ liệu cũ.

### Bài 13 — Một index cần dùng function

DBA cần index trên `lower(sku)` cho tìm kiếm không phân biệt hoa/thường.

**Đáp án:** Có thể phải dùng vendor-specific SQL migration; `@Index` chuẩn không biểu đạt mọi loại functional index.

### Bài 14 — DDL xuất từ DBMS khác

Team sinh DDL MySQL rồi chạy trên PostgreSQL.

**Đáp án:** Không an toàn; dialect và cú pháp SQL có thể khác. Chọn DB product/version chính xác.

### Bài 15 — Nhiều nodes startup

Ba app instances cùng có `database.action=create`.

**Đáp án:** Không nên; tách migration job ra khỏi runtime startup và bật `none`.

### Bài 16 — Sequence

Entity dùng `GenerationType.SEQUENCE`, production DB chưa có sequence tương ứng.

**Đáp án:** Migration hoặc setup schema phải tạo đúng sequence/object mà provider mong đợi.

### Bài 17 — ORM XML override

Java `@Table(name="products")` nhưng `orm.xml` hiệu lực nói `<table name="catalog_products"/>`.

**Đáp án:** Generated DDL dựa trên effective mapping; cần xem cả annotation và XML.

### Bài 18 — CHECK constraint

Java có `@DecimalMin("0")` trên price.

**Hỏi:** Database production chắc chắn có CHECK(price >= 0) không?

**Đáp án:** Không thể suy như vậy từ Bean Validation; thêm/kiểm tra database constraint trong migration nếu cần.

### Bài 19 — Schema diff

Provider xuất file DDL mới đổi thứ tự các CREATE TABLE statements.

**Đáp án:** Không nhất thiết schema semantics khác; kiểm tra actual structures/constraints.

### Bài 20 — Review test strategy

Team chỉ có tests tạo schema bằng Hibernate, production dùng Liquibase migrations.

**Gợi ý:** Thêm integration test chạy chính Liquibase migrations và bật `database.action=none` để xác nhận contract production.

## 37. Câu hỏi tự kiểm tra

**1. Schema generation trong Jakarta Persistence là gì?**

Là cơ chế chuẩn cho provider tạo/xóa schema objects hoặc xuất DDL scripts dựa trên mapping metadata/scripts được cấu hình.

**2. Mapping metadata có giống schema generation không?**

Không. Mapping mô tả ánh xạ, schema generation quyết định phát DDL từ các nguồn đó.

**3. Tại sao schema generation đặc biệt hữu ích trong tests?**

Giúp tạo database rỗng có cấu trúc phù hợp mapping nhanh và tái lập.

**4. Property chọn database DDL action là gì?**

`jakarta.persistence.schema-generation.database.action`.

**5. Các giá trị tiêu chuẩn quan trọng của database.action?**

`none`, `create`, `drop`, `drop-and-create`.

**6. Giá trị update có thuộc chuẩn không?**

Không.

**7. database.action=none có tự kiểm tra schema đúng không?**

Không.

**8. create có nghĩa upgrade schema không mất dữ liệu không?**

Không.

**9. Vì sao drop-and-create nguy hiểm với production?**

Vì nó có thể xóa schema objects và dữ liệu.

**10. Property dùng để xuất DDL script?**

`jakarta.persistence.schema-generation.scripts.action`.

**11. scripts.action=create có tự tạo bảng trực tiếp không?**

Không thông qua scripts action; database action được cấu hình riêng.

**12. Property định nghĩa output create file?**

`jakarta.persistence.schema-generation.scripts.create-target`.

**13. Property định nghĩa input create SQL script?**

`jakarta.persistence.schema-generation.create-script-source`.

**14. create-source=metadata nghĩa là gì?**

Sinh DDL từ JPA mapping metadata.

**15. create-source=script nghĩa là gì?**

Sử dụng SQL DDL được cung cấp trong script source tương ứng.

**16. metadata-then-script nghĩa là gì?**

Xử lý DDL từ metadata trước, sau đó SQL script bổ sung.

**17. SQL load script được chỉ qua property nào?**

`jakarta.persistence.sql-load-script-source`.

**18. SQL load script có phải migration production có phiên bản không?**

Không.

**19. API Java SE nào dùng để yêu cầu schema generation?**

`Persistence.generateSchema(...)`.

**20. Mỗi lần gọi EntityManager.persist() có tự chạy CREATE TABLE không?**

Không. Schema generation được điều khiển bởi cấu hình/bootstrap/tooling, không phải một phần bình thường của persist từng entity.

**21. Generated SQL có chắc giống nhau giữa DBMS không?**

Không.

**22. JPA @Column(nullable=false) và DB CHECK có giống nhau không?**

Không. NOT NULL khác ràng buộc biểu thức như CHECK(price >= 0).

**23. JPA cascade REMOVE có tương đương DB ON DELETE CASCADE không?**

Không.

**24. @Index tự bảo đảm performance tốt không?**

Không. Hiệu quả cần đo bằng workload/query plan.

**25. @Table(schema="...") có tự tạo database schema namespace không?**

Không mặc nhiên; còn cần cơ chế/permissions thích hợp.

**26. Database action nào thích hợp khi schema được migration quản lý?**

`none`.

**27. Vì sao nên tách quyền DDL khỏi application runtime?**

Giảm rủi ro sửa/xóa schema do cấu hình sai và thực hiện least privilege.

**28. Schema generation có version history như Flyway không?**

Không.

**29. Vì sao ALTER/backfill khác CREATE TABLE?**

Migration xử lý schema/dữ liệu đã tồn tại và tương thích triển khai, còn create script thường nhắm database mới.

**30. DDL export từ annotation có phản ánh orm.xml override không?**

Có thể; provider dùng effective mapping metadata.

**31. Property create-database-schemas có tạo cả database server không?**

Không.

**32. Khi schema generation tạo tables, có chắc triggers/views/roles cũng được tạo không?**

Không. Nhiều đối tượng ngoài phạm vi metadata JPA chuẩn.

**33. Test round-trip nên dùng EntityManager mới khi nào?**

Sau commit, để buộc kiểm tra trạng thái đọc lại thay vì L1 instance sẵn có.

**34. Vì sao integration tests nên dùng DBMS gần production?**

Vì SQL types, DDL, constraints, identity, sequences và locking behavior khác nhau giữa DBMS.

**35. Câu phân biệt quan trọng nhất là gì?**

**Schema generation giúp tạo lược đồ hoặc DDL từ metadata; schema migration là quy trình thay đổi database có dữ liệu theo phiên bản và có kiểm soát.**

## 38. Tình huống tổng hợp: xây dựng catalog từ prototype tới production

Một team xây dựng `Category` và `Product` với JPA 3.x.

### 38.1. Giai đoạn prototype

Ban đầu cần thử mappings và JPQL trên database tạm:

```properties
jakarta.persistence.schema-generation.database.action=drop-and-create
jakarta.persistence.schema-generation.create-source=metadata
jakarta.persistence.schema-generation.drop-source=metadata
```

Lợi ích:

- Không phải viết toàn bộ DDL ngay lập tức.
- Thử được primary key, FK, unique constraints.
- Chạy nhanh tests.
- Phát hiện lỗi field mappings và association.

**Điều kiện:** Không có dữ liệu nào cần giữ, và datasource thực sự là test database.

### 38.2. Giai đoạn chuẩn bị migration

Khi bắt đầu chuẩn hóa schema, team xuất DDL:

```properties
jakarta.persistence.schema-generation.database.action=none
jakarta.persistence.schema-generation.scripts.action=drop-and-create
jakarta.persistence.schema-generation.create-source=metadata
jakarta.persistence.schema-generation.drop-source=metadata
```

Với create/drop targets tương ứng, team có hai SQL artifacts để review.

DBA và developers kiểm tra:

- Cột SKU và unique constraint.
- FK Product → Category.
- Precision/scale của price.
- Sequence/identity.
- Các indexes theo truy vấn thực tế.
- Constraints nâng cao không có trong metadata.
- Triggers, views hoặc security policies đặc thù.

### 38.3. Giai đoạn production ban đầu

Team tạo migrations:

```text
V1__create_categories.sql
V2__create_products.sql
V3__add_product_indexes.sql
V4__add_business_check_constraints.sql
```

Sau đó cấu hình application:

```properties
jakarta.persistence.schema-generation.database.action=none
jakarta.persistence.schema-generation.scripts.action=none
```

Database migration job chạy một lần theo pipeline có kiểm soát trước khi nhiều app nodes khởi động.

### 38.4. Giai đoạn đổi schema sau khi có dữ liệu

Phiên bản sau cần thêm `Product.currency` và `Product.taxCategory`.

Không được đổi annotations rồi bật `drop-and-create`.

Thay vào đó:

1. Soạn migrations thêm cột ở chế độ tương thích.
2. Backfill dữ liệu nếu cần.
3. Deploy code có khả năng đọc/ghi theo trạng thái chuyển tiếp.
4. Thêm constraints sau khi dữ liệu đã đúng.
5. Dọn nhánh backward compatibility khi an toàn.
6. Xác nhận application JPA khớp schema cuối.
7. Duy trì runtime schema generation action bằng `none`.

### 38.5. Hai nhóm integration tests

**Mapping smoke tests:**

```text
Temporary DB
  -> JPA-generated schema
  -> Product/Category CRUD
```

**Migration contract tests:**

```text
Temporary DB
  -> apply all versioned migrations
  -> JPA schema generation disabled
  -> Product/Category CRUD + constraints
```

Nhóm đầu xác nhận mappings có thể tạo lược đồ dùng được. Nhóm sau xác nhận production schema pipeline tương thích application.

### 38.6. Chỉ số và tín hiệu vận hành

- Tỷ lệ fail khi bootstrap persistence unit.
- SQL errors do thiếu table/column.
- Migration version đang triển khai.
- Thời gian chạy migration.
- DDL locks ảnh hưởng application.
- Number of schema drift incidents.
- FK/unique/check constraint violations.
- Tỷ lệ test failures do mapping mismatch.
- Thời gian khôi phục khi schema deployment thất bại.

Schema generation hữu ích cho chất lượng phát triển, nhưng sự an toàn production phụ thuộc phối hợp giữa code, migrations, database và release process.

## 39. Nguyên tắc thực hành cuối bài

1. **Hiểu schema generation là tạo/xóa schema hoặc xuất DDL**, không phải công cụ migrate database có dữ liệu.
2. **Tách `database.action` và `scripts.action`.** Một bên thao tác DB, một bên xuất scripts.
3. **Dùng `none` ở production khi migrations quản lý schema**, và không coi `none` là schema validator.
4. **Chỉ dùng `drop` hoặc `drop-and-create` trên databases thực sự được phép xóa dữ liệu.**
5. **Khai báo `create-source`/`drop-source` rõ ràng** khi cần kết quả tái lập; phân biệt script nguồn với script target.
6. **Dùng SQL load script cho fixtures theo mục tiêu**, không thay data migrations có phiên bản.
7. **Quan sát generated DDL trên DBMS/dialect đích**, đặc biệt IDENTITY, SEQUENCE, ENUM, timestamps, FK và indexes.
8. **Giữ database constraints riêng cho những invariants cần bảo vệ**, không giả định mọi validation annotation tự thành CHECK.
9. **Không để nhiều application instances tự chạy DDL cùng lúc**; dùng deployment migration job có kiểm soát.
10. **Tách DDL permissions khỏi runtime application** và có guardrails bảo vệ production datasource.
11. **Kiểm thử cả schema JPA-generated và schema do real migrations tạo** khi sản phẩm yêu cầu.
12. **Xem generated SQL là bản nháp/đầu vào để review** nếu mục tiêu là database production đã có dữ liệu.
13. **Đối chiếu effective metadata** từ annotations, `orm.xml`, provider settings và naming strategy.
14. **Dùng integration tests, không chỉ unit tests của entity**, để kiểm tra columns, constraints và round-trip persistence.

## 40. Kết luận

Sinh lược đồ theo chuẩn **Jakarta Persistence** là một cầu nối hữu ích giữa **metadata ánh xạ JPA** và **các đối tượng schema thực tế của relational database**. Nó giúp ứng dụng tạo cấu trúc thử nghiệm nhanh, xuất DDL để xem xét và phát hiện những vấn đề mapping trong giai đoạn phát triển.

Tuy nhiên, cùng một entity model có thể được triển khai trên nhiều DBMS và nhiều phiên bản schema khác nhau. Vì vậy, **schema generation không phải lời hứa về DDL giống nhau trên mọi database, và càng không phải quy trình migration không mất dữ liệu**.

Hãy nhớ ba câu hỏi trước khi bật bất kỳ cấu hình nào:

- **Nguồn DDL là gì?** JPA metadata, SQL script hay kết hợp?
- **Đích tác động là gì?** Database đang chạy hay một SQL file để review?
- **Môi trường có cho phép tạo/xóa đối tượng không?** Database test tạm, shared staging hay production?

Khi trả lời rõ ba câu hỏi đó, việc lựa chọn `jakarta.persistence.schema-generation.database.action`, `scripts.action` và các source/target properties trở nên có chủ đích. Trong môi trường phát triển và thử nghiệm, schema generation tạo ra tốc độ và khả năng quan sát. Trong môi trường production, schema migrations, database privileges, release choreography và integration tests vẫn là những thành phần thiết yếu để bảo vệ dữ liệu đang tồn tại.
