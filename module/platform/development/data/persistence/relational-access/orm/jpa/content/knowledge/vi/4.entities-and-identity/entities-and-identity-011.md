# Phân biệt ánh xạ entity và ánh xạ DTO dạng record trong JPA

Trong ứng dụng Java sử dụng **Jakarta Persistence (JPA)**, cùng một dữ liệu về khách hàng có thể được biểu diễn bằng một **entity class** hoặc một **DTO dạng `record`**. Hai kiểu này có mục đích và vòng đời hoàn toàn khác nhau:

- **Entity** đại diện cho một đối tượng thuộc mô hình dữ liệu bền vững. JPA nhận biết định danh của nó, ánh xạ thuộc tính và quan hệ xuống cơ sở dữ liệu, đưa instance vào persistence context và theo dõi thay đổi để thực hiện `INSERT`, `UPDATE` hoặc `DELETE`.
- **DTO (Data Transfer Object) dạng `record`** là một cấu trúc dữ liệu dùng để mang các giá trị giữa các tầng ứng dụng hoặc trả về kết quả truy vấn. Nó thường chỉ chứa các trường cần cho một tác vụ, có cách khởi tạo gọn và các thành phần không thể gán lại sau khi tạo.

Điểm cốt lõi: **entity ánh xạ giữa mô hình đối tượng và dữ liệu được quản lý bởi JPA; record DTO ánh xạ dữ liệu từ entity/kết quả truy vấn sang một hình dạng phục vụ trao đổi**. Cùng có trường `id` và `name` không khiến DTO trở thành entity.

## 1. Đặt hai loại ánh xạ vào luồng xử lý

Giả sử ứng dụng quản lý khách hàng với bảng `customers`:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    email VARCHAR(180) NOT NULL UNIQUE,
    version BIGINT NOT NULL
);
~~~

Một quy trình đọc dữ liệu có thể trông như sau:

~~~text
       PostgreSQL / relational database
                bảng customers
                      |
                      | JDBC, SQL
                      v
                 JPA provider
                      |
               metadata @Entity
                      |
                      v
               Customer entity
             (managed nếu nằm
           trong persistence context)
                      |
             mapping / projection
                      |
                      v
       CustomerCard record DTO
         (id, fullName)
                      |
                      v
          JSON / API / giao diện
~~~

Ở chiều ghi:

~~~text
    JSON request -> RenameCustomerRequest (record)
                           |
                     kiểm tra dữ liệu
                           |
                 Application service
                           |
               EntityManager.find(id)
                           |
                    Customer entity
                    (đang managed)
                           |
                customer.rename(...)
                           |
              flush / commit transaction
                           |
                 UPDATE customers
~~~

Ứng dụng có thể **không cần tải một entity đầy đủ** cho một truy vấn chỉ lấy dữ liệu để đọc: JPA hỗ trợ projection bằng biểu thức tạo DTO trực tiếp trong JPQL. Ngược lại, các thao tác cập nhật cần xử lý theo định danh, transaction và trạng thái managed của entity.

## 2. Entity: ánh xạ dữ liệu bền vững có định danh

### 2.1. Khai báo entity chuẩn JPA

Ví dụ dùng Java 17+, Jakarta Persistence 3.x và một persistence unit tên `shopPU`:

~~~java
package com.example.shop.entity;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;

@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 120)
    private String fullName;

    @Column(nullable = false, unique = true, length = 180)
    private String email;

    @Version
    private long version;

    protected Customer() {
        // JPA cần constructor không tham số, public/protected.
    }

    public Customer(String fullName, String email) {
        this.fullName = fullName;
        this.email = email;
    }

    public void rename(String newName) {
        if (newName == null || newName.isBlank()) {
            throw new IllegalArgumentException("Tên không được trống");
        }
        this.fullName = newName;
    }

    public Long getId() {
        return id;
    }

    public String getFullName() {
        return fullName;
    }

    public String getEmail() {
        return email;
    }

    public long getVersion() {
        return version;
    }
}
~~~

Các annotation và cấu trúc ở trên tạo nên **metadata ORM**:

| Khai báo | Ý nghĩa với entity |
| --- | --- |
| `@Entity` | Đánh dấu class là entity do JPA quản lý khi được đưa vào persistence unit |
| `@Table(name = "customers")` | Chọn bảng ánh xạ; đây là tên bảng, không phải tên DTO |
| `@Id` | Xác định thuộc tính định danh (primary key ở schema tương ứng) |
| `@GeneratedValue` | Khai báo cách sinh khóa chính |
| `@Column` | Ánh xạ thuộc tính Java sang cột, quy tắc null, độ dài… |
| `@Version` | Hỗ trợ optimistic locking để phát hiện cập nhật đồng thời |
| Constructor không tham số | Cho phép provider khởi tạo entity theo yêu cầu của JPA |

JPA yêu cầu entity class đáp ứng những ràng buộc nhất định, trong đó có constructor không tham số với khả năng truy cập phù hợp và class entity không phải `final`. Các thuộc tính và hành vi được thiết kế để provider có thể tạo instance, quản lý vòng đời và theo dõi trạng thái. Những yêu cầu này khác bản chất với kiểu dữ liệu `record`.

### 2.2. Định danh entity và persistence context

`Customer` có một định danh bền vững là `id`. Trong cùng một persistence context, JPA bảo đảm một entity có cùng loại và cùng khóa chính được biểu diễn bằng cùng managed instance:

~~~java
Customer first = em.find(Customer.class, 42L);
Customer second = em.find(Customer.class, 42L);

System.out.println(first == second); // true, nếu entity tồn tại
~~~

Trong một transaction, sửa thuộc tính trên managed instance sẽ được provider phát hiện:

~~~java
em.getTransaction().begin();

Customer customer = em.find(Customer.class, 42L);
if (customer == null) {
    throw new IllegalArgumentException("Không tìm thấy khách hàng");
}
customer.rename("Nguyễn Minh Anh");

em.getTransaction().commit(); // Có thể flush SQL UPDATE.
~~~

Đoạn mã transaction thủ công giả định `em` là **application-managed EntityManager** dùng `RESOURCE_LOCAL`. Trong Jakarta EE với EntityManager do container quản lý, transaction có thể được điều phối bởi EJB hoặc JTA thay vì gọi `getTransaction()` trực tiếp.

**Có ID không tự làm một object trở thành managed.** Một entity có thể ở trạng thái mới (new), managed, detached hoặc removed. Việc một instance có được JPA theo dõi hay không phụ thuộc persistence context và thao tác quản lý, không chỉ phụ thuộc giá trị của trường `id`.

## 3. DTO dạng record: ánh xạ dữ liệu để trao đổi

### 3.1. Cấu trúc record

Java `record` phù hợp với DTO chỉ cần chứa một tập giá trị rõ ràng:

~~~java
package com.example.shop.dto;

public record CustomerCard(Long id, String fullName) {
}
~~~

Java cung cấp tự động constructor nhận các thành phần, accessor và một số phương thức giá trị:

~~~java
CustomerCard card = new CustomerCard(42L, "Nguyễn Minh Anh");

Long id = card.id();
String name = card.fullName();

System.out.println(card);
// CustomerCard[id=42, fullName=Nguyễn Minh Anh]
~~~

Record không cần khai báo thủ công `getId()`, `getFullName()`, `equals()`, `hashCode()` hoặc `toString()` cho trường hợp thông thường. Accessor mặc định mang tên thành phần: `id()`, `fullName()`.

Các thành phần của record là `final`: không thể gọi `card.setFullName(...)` hoặc gán lại `card.fullName`. Nếu cần một giá trị mới, tạo record mới:

~~~java
CustomerCard updated = new CustomerCard(card.id(), "Tên hiển thị mới");
~~~

Đây là **bất biến nông (shallow immutability)**. Nếu một thành phần chứa đối tượng có thể thay đổi, ví dụ `List<String>`, bản thân dữ liệu bên trong có thể vẫn bị sửa qua tham chiếu. Khi cần DTO thực sự an toàn với collection, nên sao chép phòng vệ:

~~~java
import java.util.List;

public record CustomerWithTags(Long id, List<String> tags) {
    public CustomerWithTags {
        tags = List.copyOf(tags);
    }
}
~~~

`List.copyOf(...)` tạo danh sách không thể sửa qua các phương thức của `List`, nhưng nếu phần tử bên trong là object mutable thì vẫn phải cân nhắc sao chép sâu.

### 3.2. Tại sao không dùng record làm entity JPA tiêu chuẩn?

Java record được khai báo là một class `final`, các component có trường `final` và không có constructor không tham số theo mẫu entity truyền thống. Trong khi đó, entity JPA tiêu chuẩn có các yêu cầu về class, constructor và khả năng provider quản lý state không tương thích với record.

Đoạn sau **không phải entity JPA portable hợp lệ**:

~~~java
// KHÔNG dùng làm JPA entity tiêu chuẩn:
@Entity
@Table(name = "customers")
public record CustomerEntity(Long id, String fullName) {
}
~~~

Dù có thể thêm một số annotation lên record hoặc component, **gắn `@Entity` vào một record không biến nó thành entity hợp lệ theo đặc tả JPA**. Không nên dựa vào hành vi đặc thù của provider để thay thế quy tắc này khi xây dựng mô hình entity portable.

Lưu ý phạm vi: một số provider hoặc phiên bản có hỗ trợ dùng record làm **value object/embeddable** trong các điều kiện nhất định. Điều đó **không đồng nghĩa** record có thể được dùng làm JPA entity có vòng đời và định danh riêng.

### 3.3. DTO có trường ID nhưng không có identity map

Hai record có cùng các giá trị sẽ bằng nhau theo cơ chế `equals()` do Java tạo:

~~~java
CustomerCard a = new CustomerCard(42L, "Mai");
CustomerCard b = new CustomerCard(42L, "Mai");
CustomerCard c = new CustomerCard(42L, "Mai Anh");

System.out.println(a.equals(b)); // true
System.out.println(a.equals(c)); // false
~~~

`c` có cùng ID `42L` nhưng `equals()` vẫn trả về `false` vì tên khác nhau. Record so sánh **tập giá trị thành phần**, không áp dụng khái niệm định danh bền vững của JPA.

Ngược lại, **JPA identity** được xác định theo loại entity và primary key trong persistence context. Chính sách `equals()`/`hashCode()` của entity class là quyết định thiết kế riêng; không được mặc định Java `equals()` của mọi entity luôn dựa trên primary key. Nếu tự cài đặt bằng ID, phải cân nhắc ID chưa được cấp, entity proxy và thay đổi hash code khi persist.

## 4. So sánh ánh xạ entity và ánh xạ record DTO

| Tiêu chí | JPA entity | DTO dạng `record` |
| --- | --- | --- |
| Mục đích | Biểu diễn trạng thái bền vững và quan hệ dữ liệu | Mang dữ liệu phù hợp với một màn hình, API hoặc tác vụ |
| Nguồn ánh xạ | Annotation/XML ORM giữa class và bảng/cột/quan hệ | Mã chuyển đổi hoặc projection từ kết quả truy vấn |
| Annotation chính | `@Entity`, `@Id`, `@Column`, `@ManyToOne`, `@Version`… | Thường không cần annotation JPA |
| Quan hệ với persistence unit | Được đăng ký/quét thành managed entity | Không phải managed entity trong PU |
| Định danh | Có khóa định danh JPA, ví dụ `@Id` | Có thể mang `id` như một giá trị thông thường |
| Vòng đời JPA | New, managed, detached, removed | Không có vòng đời entity JPA |
| Dirty checking | Có trên managed entity | Không có |
| `persist/remove` | Hoạt động với entity hợp lệ trong context/transaction tương ứng | Không dùng trực tiếp cho DTO record |
| Khả năng thay đổi thuộc tính | Có thể thiết kế phương thức thay đổi trạng thái | Component không gán lại được |
| Constructor | Cần constructor không tham số theo yêu cầu JPA | Canonical constructor nhận các component |
| Kế thừa | Có cơ chế inheritance mapping của JPA | Record là `final`, không làm superclass cho class khác |
| `equals/hashCode` | Do thiết kế entity quyết định | Sinh tự động dựa trên tất cả component |
| Tải quan hệ lazy | Có thể có thông qua cơ chế ORM | Không tự lazy-load; nhận dữ liệu đã ánh xạ |
| Trả dữ liệu ra API | Cần kiểm soát field, graph và serialization | Dễ tạo response chỉ gồm các field cần công khai |
| Tối ưu truy vấn đọc | Có thể tải cả entity và quan hệ tùy truy vấn | Projection trực tiếp có thể chỉ lấy cột cần thiết |

Bảng trên mô tả **vai trò thường dùng**, không có nghĩa mọi lần đọc entity đều tải tất cả cột hoặc mọi projection đều nhanh hơn trong mọi tình huống. Hiệu năng còn phụ thuộc SQL, index, số lượng dòng, join và cách dùng persistence context.

## 5. Ba cách ánh xạ từ dữ liệu JPA sang DTO record

Một record DTO có thể được tạo thủ công từ entity, được xây từ JPQL constructor expression, hoặc được tạo bằng Criteria API. Chọn cách phù hợp với nhu cầu đọc dữ liệu.

### 5.1. Mapping thủ công sau khi tải entity

~~~java
package com.example.shop.dto;

import com.example.shop.entity.Customer;

public final class CustomerMapper {
    private CustomerMapper() {
    }

    public static CustomerCard toCard(Customer customer) {
        return new CustomerCard(
            customer.getId(),
            customer.getFullName()
        );
    }
}
~~~

Trong service hoặc query handler:

~~~java
Customer customer = em.find(Customer.class, 42L);
if (customer == null) {
    return null;
}

CustomerCard card = CustomerMapper.toCard(customer);
~~~

Cách này dễ đọc, cho phép áp dụng quy tắc chuyển đổi phức tạp và tái sử dụng mapping. Tuy nhiên, nếu đã tải entity đầy đủ chỉ để trả hai trường, truy vấn có thể phải xử lý nhiều metadata/trạng thái hơn so với một projection trực tiếp. Khi entity chứa quan hệ lazy, truy cập quan hệ trong mapper còn có thể phát sinh truy vấn bổ sung hoặc lỗi nếu context đã đóng.

### 5.2. JPQL constructor expression: ánh xạ trực tiếp từ truy vấn

Nếu chỉ cần `id` và `fullName` cho danh sách khách hàng, có thể yêu cầu JPA khởi tạo record trực tiếp:

~~~java
import com.example.shop.dto.CustomerCard;

List<CustomerCard> cards = em.createQuery(
    """
    SELECT new com.example.shop.dto.CustomerCard(
        c.id,
        c.fullName
    )
    FROM Customer c
    ORDER BY c.id
    """,
    CustomerCard.class
).getResultList();
~~~

**Cách đọc câu JPQL:**

1. `FROM Customer c` sử dụng **tên entity**, không phải tên bảng SQL `customers`.
2. `c.id` và `c.fullName` là **thuộc tính Java được ánh xạ**, không phải tên cột vật lý `full_name`.
3. `new com.example.shop.dto.CustomerCard(...)` gọi constructor của record theo đúng thứ tự component: `Long id` rồi `String fullName`.
4. Kết quả là danh sách `CustomerCard`, không phải danh sách managed `Customer`. JPA không theo dõi sửa đổi trên các record này.

Constructor expression là cú pháp JPQL tiêu chuẩn. Tên class DTO cần là tên đầy đủ mà provider có thể truy cập; số lượng, thứ tự và kiểu tham số phải tương thích với constructor. Vì record có canonical constructor, nó phù hợp tự nhiên với kiểu projection này.

Ví dụ chỉ lấy một khách hàng:

~~~java
List<CustomerCard> result = em.createQuery(
    """
    SELECT new com.example.shop.dto.CustomerCard(c.id, c.fullName)
    FROM Customer c
    WHERE c.id = :id
    """,
    CustomerCard.class
).setParameter("id", 42L)
 .getResultList();

CustomerCard card = result.isEmpty() ? null : result.get(0);
~~~

Không cần khai báo `@Entity`, `@Table` hoặc `@Column` trên `CustomerCard`: record được tạo từ giá trị của truy vấn. Tránh viết `em.persist(card)` hay `em.find(CustomerCard.class, ...)` vì nó không phải entity.

### 5.3. Projection bằng Criteria API

Khi cần xây dựng query động, Criteria API hỗ trợ tạo DTO qua `CriteriaBuilder.construct`:

~~~java
import jakarta.persistence.criteria.CriteriaBuilder;
import jakarta.persistence.criteria.CriteriaQuery;
import jakarta.persistence.criteria.Root;

CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<CustomerCard> query =
    cb.createQuery(CustomerCard.class);

Root<Customer> customer = query.from(Customer.class);

query.select(cb.construct(
    CustomerCard.class,
    customer.get("id"),
    customer.get("fullName")
));

List<CustomerCard> cards = em.createQuery(query).getResultList();
~~~

Cách này vẫn tạo **record DTO**, không làm record trở thành entity. Nếu dùng thêm JPA static metamodel, có thể giảm việc viết tên thuộc tính dưới dạng chuỗi khi lập Criteria query.

### 5.4. Native SQL cần cách ánh xạ riêng

Biểu thức `SELECT new ...` ở trên thuộc **JPQL**, không phải cú pháp SQL chuẩn để chạy trực tiếp trong PostgreSQL/MySQL. Với native SQL:

~~~sql
SELECT id, full_name
FROM customers
WHERE id = ?;
~~~

Kết quả có thể được JPA trả về dưới dạng scalar/`Object[]` hoặc được ánh xạ bằng `@SqlResultSetMapping` kết hợp `@ConstructorResult`. Một số provider/framework hỗ trợ trực tiếp record projection với native query, nhưng mức độ hỗ trợ phụ thuộc phiên bản và cấu hình.

Do đó, không nên giả định rằng:

~~~java
// Không bảo đảm portable cho mọi JPA provider:
em.createNativeQuery(
    "SELECT id, full_name FROM customers",
    CustomerCard.class
);
~~~

sẽ tự gọi canonical constructor của mọi record DTO. Khi dùng native SQL, hãy chọn cơ chế mapping được provider hỗ trợ rõ ràng hoặc tự chuyển đổi kết quả theo kiểu dữ liệu thực tế.

## 6. Ánh xạ record khi có quan hệ entity

Entity thường biểu diễn quan hệ qua các reference hoặc collection:

~~~java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {
    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;

    @Column(nullable = false, precision = 12, scale = 2)
    private BigDecimal total;

    // Constructor, getters và logic nghiệp vụ.
}
~~~

Với một bảng danh sách đơn hàng, giao diện chỉ cần số đơn, tên khách hàng và tổng tiền. Ta có thể tạo record:

~~~java
package com.example.shop.dto;

import java.math.BigDecimal;

public record OrderRow(
    Long orderId,
    String customerName,
    BigDecimal total
) {
}
~~~

Sau đó truy vấn trực tiếp các giá trị cần thiết:

~~~java
List<OrderRow> rows = em.createQuery(
    """
    SELECT new com.example.shop.dto.OrderRow(
        o.id,
        c.fullName,
        o.total
    )
    FROM PurchaseOrder o
    JOIN o.customer c
    ORDER BY o.id DESC
    """,
    OrderRow.class
).getResultList();
~~~

Trong ví dụ này, `o.customer` là **đường dẫn quan hệ entity** trong JPQL; `JOIN` là kết hợp dữ liệu theo mapping của JPA. DTO chỉ chứa `customerName`, không tự mang một proxy `Customer` hoặc tham gia lazy loading.

Nếu chọn cách tải nhiều `PurchaseOrder` rồi gọi `order.getCustomer().getFullName()` cho từng dòng khi quan hệ customer đang lazy, ứng dụng có thể phát sinh **N+1 queries**. Projection trực tiếp với join thường dễ kiểm soát hình dạng SQL hơn khi chỉ cần một số trường. Tuy nhiên cần kiểm tra truy vấn cuối cùng theo nhu cầu thực tế, đặc biệt với phân trang và quan hệ collection.

**Không đưa toàn bộ entity graph vào record chỉ để “đổi tên kiểu”.** Ví dụ `record OrderView(PurchaseOrder order)` vẫn chứa tham chiếu tới entity, có thể kéo theo lazy loading và làm lộ field không mong muốn khi serialization. DTO nên dùng các giá trị hoặc cấu trúc con đã chọn có chủ đích.

## 7. Record cho request và response: khác với entity dùng để ghi

Trong ứng dụng có HTTP API, thường tách rõ hai loại DTO:

~~~java
// Dữ liệu đầu vào của yêu cầu đổi tên.
public record RenameCustomerRequest(String fullName) {
    public RenameCustomerRequest {
        if (fullName == null || fullName.isBlank()) {
            throw new IllegalArgumentException("Tên không được trống");
        }
    }
}

// Dữ liệu đầu ra cho client.
public record CustomerCard(Long id, String fullName) {
}
~~~

Phương thức service dưới đây chạy trong **Jakarta EE EJB container**; container-managed transaction mặc định của `@Stateless` thường là `REQUIRED`:

~~~java
package com.example.shop.service;

import com.example.shop.dto.CustomerCard;
import com.example.shop.dto.RenameCustomerRequest;
import com.example.shop.entity.Customer;
import jakarta.ejb.Stateless;
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;

@Stateless
public class CustomerService {

    @PersistenceContext(unitName = "shopPU")
    private EntityManager em;

    public CustomerCard rename(
            Long id,
            RenameCustomerRequest request) {

        Customer customer = em.find(Customer.class, id);
        if (customer == null) {
            throw new IllegalArgumentException("Customer not found");
        }

        customer.rename(request.fullName());

        return new CustomerCard(
            customer.getId(),
            customer.getFullName()
        );
    }
}
~~~

Dòng xử lý là: **request record → kiểm tra nghiệp vụ → managed entity → transaction commit → response record**.

Đặc biệt, **không nên dùng request DTO như một entity rồi gọi `persist()` hoặc `merge()` trực tiếp**. Ví dụ client có thể gửi trường `id`, `role` hoặc `balance` giả mạo. Service cần lấy entity bằng định danh hợp lệ, kiểm tra quyền và chỉ áp dụng những thuộc tính được phép sửa. Ranh giới DTO giúp giới hạn dữ liệu API nhận/trả nhưng không thay thế kiểm tra bảo mật và nghiệp vụ.

Nếu có optimistic locking bằng `@Version`, có thể đưa phiên bản dữ liệu vào DTO phù hợp và dùng nó khi kiểm tra cập nhật cạnh tranh. Annotation `@Version` vẫn nằm trên entity, nơi JPA quản lý version; record chỉ mang giá trị phiên bản cho giao tiếp.

## 8. Những khác biệt về identity và equality cần ghi nhớ

### 8.1. ID của entity là định danh persistence

Với `@Id`, JPA dựa vào ID để xác định hàng dữ liệu và quản lý instance trong persistence context. Sau khi `em.persist(new Customer(...))` và khóa chính được tạo, object entity có thể được quản lý ngay cả khi chưa kết thúc transaction.

### 8.2. ID trong record DTO chỉ là một trường dữ liệu

~~~java
CustomerCard before = new CustomerCard(42L, "Mai");
CustomerCard after = new CustomerCard(42L, "Mai Anh");

System.out.println(before.id().equals(after.id())); // true
System.out.println(before.equals(after));             // false
~~~

Hai DTO này có thể chỉ cùng một khách hàng ở hai thời điểm nhưng không bằng nhau theo record value equality. Ngược lại, hai entity instance từ hai persistence context có thể cùng đại diện cho một bản ghi nhưng là hai reference Java khác nhau.

### 8.3. Record không tự động nhận cập nhật

Khi record được tạo từ entity:

~~~java
CustomerCard snapshot =
    new CustomerCard(customer.getId(), customer.getFullName());

customer.rename("Tên khác");
~~~

`snapshot.fullName()` vẫn trả về **giá trị tại lúc tạo record**. Record không liên kết hai chiều với entity; JPA không cập nhật record khi entity thay đổi. Đây là đặc tính hữu ích cho response snapshot và khả năng dự đoán dữ liệu, đồng thời đòi hỏi tạo DTO mới nếu muốn lấy trạng thái mới.

## 9. Các lỗi thiết kế thường gặp

| Dấu hiệu | Nguyên nhân thường gặp | Cách xử lý |
| --- | --- | --- |
| Gắn `@Entity` lên một `record` | Record không đáp ứng yêu cầu entity JPA tiêu chuẩn | Dùng entity class phù hợp; giữ record ở tầng DTO |
| `Not a managed type: CustomerCard` | Gọi repository/`EntityManager` như thể DTO là entity | Truy vấn entity và tạo DTO bằng projection hoặc mapper |
| `Cannot resolve constructor` trong JPQL | Sai tên package, thứ tự hoặc kiểu tham số của record | Khớp chính xác constructor với các biểu thức `SELECT new` |
| DTO có đầy đủ field nhưng sửa không ghi DB | DTO không được dirty checking | Tải managed entity trong transaction rồi áp dụng thay đổi |
| API trả trực tiếp entity, gây lỗi lazy serialization | Serializer duyệt quan hệ khi persistence context đã đóng | Trả DTO có field cần dùng, chọn dữ liệu trong transaction/query phù hợp |
| Danh sách DTO chậm do N+1 | Mapper duyệt quan hệ lazy từng dòng | Dùng projection với join phù hợp hoặc tối ưu fetch strategy |
| Dùng `equals()` record như so sánh database identity | Record so sánh toàn bộ component | So sánh khóa định danh khi yêu cầu nghiệp vụ là “cùng bản ghi” |
| Client có thể đổi trường không được phép | Gắn request trực tiếp vào entity hoặc merge object không kiểm soát | Kiểm tra quyền và chỉ map các trường hợp lệ trong service |
| Đọc bảng native SQL rồi ép trực tiếp sang record | Provider không hỗ trợ mapping constructor tự động | Dùng mapping tường minh hay cơ chế native projection đã được kiểm chứng |

## 10. Chọn cách ánh xạ theo tình huống

**Tình huống A: thay đổi email khách hàng.** Entity là lựa chọn cần thiết để thực hiện cập nhật theo ID trong transaction. Record request chỉ mang email mới; logic nghiệp vụ xác thực email, quyền chỉnh sửa và tính duy nhất trước khi commit.

**Tình huống B: hiển thị 100 khách hàng với tên và ID.** DTO record với JPQL constructor expression thường phù hợp: chỉ chọn những cột cần dùng, kết quả không được JPA quản lý, dễ chuyển thành JSON.

**Tình huống C: trang chi tiết khách hàng có lịch sử đơn hàng.** Có thể thiết kế nhiều DTO nhỏ, ví dụ `CustomerDetail` và `OrderRow`, để biểu diễn đúng dữ liệu được phép hiển thị. Lên kế hoạch join, batch, phân trang hoặc các truy vấn riêng cho collection; tránh tải bừa toàn bộ quan hệ rồi để serializer tự duyệt.

**Tình huống D: thực hiện một nghiệp vụ miền phức tạp.** Nên giữ entity với phương thức hành vi rõ nghĩa, invariant và lifecycle JPA; record DTO chỉ là đầu vào/đầu ra. Nếu biến mọi entity thành DTO và tự viết SQL cho tất cả, ứng dụng có thể đánh mất lợi ích dirty checking và mapping quan hệ của ORM.

**Tình huống E: tích hợp service khác chỉ nhận JSON.** DTO record tạo ranh giới API ổn định hơn entity nội bộ: có thể đổi tên cột, tối ưu mapping DB hay thay đổi quan hệ nội bộ mà vẫn giữ hợp đồng JSON khi cần.

## 11. Bài tập đọc code

### Bài 1 — Record có được `persist` không?

~~~java
CustomerCard card = new CustomerCard(1L, "Lan");
em.persist(card);
~~~

**Giải thích:** Không hợp lệ vì `CustomerCard` là DTO, không phải entity managed của JPA. Muốn tạo khách hàng, hãy tạo `Customer` với dữ liệu hợp lệ, rồi `em.persist(customer)` trong transaction.

### Bài 2 — JPQL nào trả DTO?

~~~java
// A
SELECT c FROM Customer c

// B
SELECT new com.example.shop.dto.CustomerCard(c.id, c.fullName)
FROM Customer c
~~~

**Giải thích:** A trả về entity `Customer`. B tạo `CustomerCard` từ hai thuộc tính. Kết quả B không tham gia persistence context dưới dạng entity.

### Bài 3 — Thay tên sau khi tạo record

~~~java
CustomerCard card =
    new CustomerCard(customer.getId(), customer.getFullName());

customer.rename("Tên mới");
~~~

**Giải thích:** `card.fullName()` không tự thay đổi. Muốn phản ánh tên mới, tạo `new CustomerCard(customer.getId(), customer.getFullName())` hoặc thực hiện query projection mới.

### Bài 4 — Hai record có ID giống nhau

~~~java
new CustomerCard(7L, "A")
    .equals(new CustomerCard(7L, "B"));
~~~

**Giải thích:** Kết quả `false` vì value equality của record so sánh cả tên. Khi chỉ muốn biết cùng định danh khách hàng, hãy so sánh trường `id` theo logic nghiệp vụ; không coi record equality là JPA entity identity.

## 12. Kết luận

- **Entity** là mô hình persistence: có `@Id`, mapping bảng/cột/quan hệ, được quản lý trong persistence context và có thể được JPA theo dõi thay đổi.
- **Record DTO** là mô hình truyền dữ liệu: được tạo từ giá trị truy vấn hoặc entity, có component bất biến ở mức tham chiếu và không được JPA quản lý như entity.
- Có thể tạo record từ entity bằng mapper thủ công, hoặc **projection trực tiếp** qua JPQL `SELECT new ...`/Criteria `construct(...)`. Truy vấn native SQL cần cơ chế ánh xạ riêng phù hợp provider.
- Với luồng ghi, nhận request DTO, truy xuất entity managed, áp dụng nghiệp vụ trong transaction, rồi trả response DTO. Với luồng đọc, chọn projection phù hợp dữ liệu màn hình để tránh lộ field hoặc tải quan hệ không cần thiết.

Nhớ một phép phân biệt: **“đối tượng này có được JPA quản lý theo định danh và trạng thái để ghi xuống DB không?”** Nếu có, đó là vai trò của **entity**; nếu chỉ mang dữ liệu của một yêu cầu/kết quả, đó là vai trò của **DTO record**.
