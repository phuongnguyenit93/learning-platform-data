# Đánh giá thứ tự cập nhật và ràng buộc khóa ngoại trong quan hệ một-nhiều JPA

Trong **Jakarta Persistence (JPA)**, quan hệ **một-nhiều (one-to-many)** thường xuất hiện khi một đơn hàng chứa nhiều dòng hàng, một phòng ban có nhiều nhân viên, hoặc một khách hàng có nhiều địa chỉ giao dịch. Ở mô hình Java, thao tác có thể rất đơn giản: thêm phần tử vào `List`, chuyển một child sang parent khác, hoặc xóa phần tử khỏi collection. Nhưng trong cơ sở dữ liệu quan hệ, mỗi thao tác phải được biến thành những lệnh **`INSERT`, `UPDATE`, `DELETE`** tuân thủ **PRIMARY KEY**, **FOREIGN KEY**, `NOT NULL` và đôi khi cả `UNIQUE`.

Hai vấn đề cần đánh giá cùng nhau:

1. **Ai sở hữu quan hệ trong JPA?** Đó là phía quyết định giá trị khóa ngoại được ghi xuống DB.
2. **SQL phải được thực thi theo thứ tự nào để giữ ràng buộc hợp lệ?** Thứ tự code gọi `persist`/`remove` không nhất thiết là thứ tự các câu SQL được provider phát ra.

Ví dụ trung tâm là quan hệ `PurchaseOrder` 1–N `OrderLine`, với cột `order_lines.order_id` là khóa ngoại **`NOT NULL`** tới `purchase_orders.id`.

## 1. Quan hệ object khác với ràng buộc trong database

Trong Java:

~~~text
PurchaseOrder #1001
    |
    +-- List<OrderLine>
          |
          +-- OrderLine #501
          +-- OrderLine #502
          +-- OrderLine #503
~~~

Trong database:

~~~text
purchase_orders                       order_lines
+----------------+           +---------------------------------+
| id  (PK)       | <-------- | order_id (FK, NOT NULL)         |
| status         |       1:N | id (PK), sku, quantity           |
+----------------+           +---------------------------------+
~~~

SQL mô phỏng:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(30) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id)
        REFERENCES purchase_orders(id),
    CONSTRAINT ck_order_lines_quantity CHECK (quantity > 0)
);

CREATE INDEX idx_order_lines_order_id
    ON order_lines (order_id);
~~~

Ràng buộc của schema có ý nghĩa:

- Không được chèn một dòng `order_lines` tham chiếu `order_id` chưa tồn tại trong `purchase_orders`.
- Không được gán `order_id = NULL` vì cột `NOT NULL`.
- Không được xóa một đơn hàng đang được các dòng tham chiếu nếu chưa xử lý những dòng đó và FK không khai báo hành vi xóa phù hợp.
- `order_lines.id` là khóa riêng của child; nó khác với khóa ngoại `order_id`.

**Mô hình Java mô tả tham chiếu và collection; database bảo vệ tính toàn vẹn bằng các ràng buộc.** JPA provider phải kết nối hai phía này khi flush.

## 2. Mô hình ánh xạ hai chiều khuyến nghị

Đối với bảng child có FK, cách thông dụng là **child sở hữu quan hệ** qua `@ManyToOne` và `@JoinColumn`. Parent có `@OneToMany(mappedBy = "...")` để truy cập danh sách từ chiều ngược lại.

### 2.1. Parent: PurchaseOrder

~~~java
package com.example.shop.domain;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 30)
    private String status = "DRAFT";

    @OneToMany(
        mappedBy = "order",
        cascade = CascadeType.PERSIST,
        orphanRemoval = true
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public void addLine(OrderLine line) {
        Objects.requireNonNull(line);
        if (line.getOrder() != null && line.getOrder() != this) {
            throw new IllegalArgumentException(
                "Line already belongs to another order");
        }
        if (!lines.contains(line)) {
            lines.add(line);
        }
        line.attachTo(this);
    }

    public void removeLine(OrderLine line) {
        if (lines.remove(line)) {
            line.detachFromOrder();
        }
    }

    public Long getId() {
        return id;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }
}
~~~

### 2.2. Child: OrderLine

~~~java
package com.example.shop.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;
import java.util.Objects;

@Entity
@Table(name = "order_lines")
public class OrderLine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @Column(nullable = false, length = 80)
    private String sku;

    @Column(nullable = false)
    private int quantity;

    protected OrderLine() {
    }

    public OrderLine(String sku, int quantity) {
        this.sku = Objects.requireNonNull(sku);
        if (quantity <= 0) {
            throw new IllegalArgumentException(
                "Quantity must be positive");
        }
        this.quantity = quantity;
    }

    void attachTo(PurchaseOrder order) {
        this.order = Objects.requireNonNull(order);
    }

    void detachFromOrder() {
        this.order = null;
    }

    public PurchaseOrder getOrder() {
        return order;
    }

    public Long getId() {
        return id;
    }
}
~~~

Trong mô hình này:

| Thành phần | Vai trò | Tác động lên FK |
| --- | --- | --- |
| `OrderLine.order` | **Owning side** của quan hệ hai chiều | Quyết định giá trị `order_lines.order_id` |
| `PurchaseOrder.lines` | **Inverse side**, có `mappedBy = "order"` | Phản ánh danh sách phía Java; bản thân collection không sở hữu FK |
| `CascadeType.PERSIST` | Truyền thao tác persist từ parent tới child | Không đồng nghĩa database có `ON DELETE CASCADE` |
| `orphanRemoval = true` | Child rời khỏi quan hệ sở hữu được xem là orphan cần xóa | Thường dẫn tới `DELETE` child khi flush phù hợp |
| `optional = false` và `nullable = false` | Định hướng mapping về quan hệ bắt buộc | Cần phối hợp với `NOT NULL` thực tế của database |

**Giữ đồng bộ hai phía của quan hệ**: nếu chỉ thêm child vào `lines` mà không đặt `line.order = parent`, owning side vẫn không có giá trị khóa ngoại. Phương thức `addLine` giúp tránh tình huống collection hiển thị một quan hệ nhưng SQL không thể ghi FK đúng.

Ví dụ cố ý chọn `orphanRemoval = true` vì `OrderLine` là thành phần phụ thuộc vào `PurchaseOrder`; khi bỏ dòng khỏi đơn thì dòng phải bị xóa. Với quan hệ cho phép chuyển child giữa nhiều parent, thiết kế khác ở mục 7 sẽ không dùng orphan removal.

## 3. Thứ tự INSERT: parent phải tồn tại trước khi child tham chiếu

Tạo một đơn hàng kèm hai dòng:

~~~java
PurchaseOrder order = new PurchaseOrder();

order.addLine(new OrderLine("BOOK-01", 2));
order.addLine(new OrderLine("PEN-02", 5));

em.getTransaction().begin();
em.persist(order);
em.getTransaction().commit();
~~~

Đoạn mã giả định `em` là application-managed `EntityManager` dùng transaction `RESOURCE_LOCAL`; trong Jakarta EE hoặc Spring, transaction thường được container/framework quản lý.

Với `cascade = PERSIST`, provider có thể đưa cả parent và child vào trạng thái managed. Để đáp ứng FK `NOT NULL` và tham chiếu tới khóa chính, SQL cần tạo ra các dòng parent/child hợp lệ; thứ tự logic thường là:

~~~sql
INSERT INTO purchase_orders (status)
VALUES ('DRAFT');
-- Database sinh id = 1001.

INSERT INTO order_lines (order_id, sku, quantity)
VALUES (1001, 'BOOK-01', 2);

INSERT INTO order_lines (order_id, sku, quantity)
VALUES (1001, 'PEN-02', 5);
~~~

Provider có thể điều chỉnh thời điểm chạy SQL và thứ tự một số thao tác, nhưng không thể thành công với lệnh chèn child tham chiếu parent chưa tồn tại nếu DB kiểm tra FK ngay.

### 3.1. Thứ tự gọi persist không quyết định trực tiếp thứ tự SQL

Hai câu lệnh Java:

~~~java
em.persist(order);
em.persist(line);
~~~

không bảo đảm chính xác thứ tự SQL sẽ được thực thi giống thứ tự dòng code. Provider có **action queue/unit of work** để gom và đồng bộ thay đổi tại các thời điểm phù hợp.

Thời điểm tạo ID cũng ảnh hưởng:

- Với `GenerationType.IDENTITY`, provider thường phải thực hiện INSERT để nhận ID từ database, có thể sớm hơn kỳ vọng.
- Với `SEQUENCE` hoặc ID ứng dụng tự cấp, provider có thể biết ID trước và trì hoãn INSERT tới flush.
- Batching, sắp xếp INSERT và tối ưu hóa SQL có thể thay đổi thứ tự SQL quan sát được, miễn thỏa ràng buộc dữ liệu và hợp đồng của provider.

Không nên viết nghiệp vụ dựa vào giả định “lệnh `persist()` thứ nhất luôn tạo SQL INSERT đầu tiên”.

### 3.2. Lỗi khi child chưa có parent

Ví dụ không nhất quán:

~~~java
OrderLine line = new OrderLine("BOOK-01", 2);

// Không gán line.order, cũng không gắn line vào PurchaseOrder.
em.persist(line);
~~~

Cột `order_id` thiếu giá trị. Kết quả có thể là lỗi phía ORM trước khi SQL chạy hoặc vi phạm `NOT NULL` khi flush/commit.

Lỗi kiểu:

~~~text
null value in column "order_id" violates not-null constraint
~~~

có thể xuất hiện khi một child được đưa vào context mà owning side vẫn null.

Cách xử lý là thiết lập **quan hệ hợp lệ trong Java** trước khi persist, chẳng hạn `order.addLine(line)`, và bảo đảm parent được persist theo cascade hoặc thao tác tường minh.

## 4. Thứ tự DELETE: child và ràng buộc khóa ngoại

Đối với schema trên, nếu đơn hàng `1001` vẫn có child:

~~~sql
DELETE FROM purchase_orders WHERE id = 1001;
~~~

thì database mặc định thường **từ chối** nếu còn `order_lines.order_id = 1001`, vì FK đang tham chiếu parent.

Trình tự SQL logic để xóa toàn bộ aggregate với FK không có `ON DELETE CASCADE`:

~~~sql
DELETE FROM order_lines WHERE order_id = 1001;

DELETE FROM purchase_orders WHERE id = 1001;
~~~

Trong JPA, nếu muốn xóa parent kéo theo child, cần khai báo rõ cascade remove phù hợp với mô hình vòng đời:

~~~java
@OneToMany(
    mappedBy = "order",
    cascade = {CascadeType.PERSIST, CascadeType.REMOVE},
    orphanRemoval = true
)
private List<OrderLine> lines = new ArrayList<>();
~~~

Sau đó:

~~~java
em.getTransaction().begin();

PurchaseOrder managed = em.find(PurchaseOrder.class, 1001L);
if (managed != null) {
    em.remove(managed);
}

em.getTransaction().commit();
~~~

Provider chịu trách nhiệm biến các thao tác remove đã được cascade thành các lệnh phù hợp. Khi DB kiểm tra FK ngay, child cần được xử lý trước khi parent bị xóa; **không nên tự giả định mọi provider sẽ luôn phát SQL đúng một thứ tự cố định trên mọi mapping**. Chọn mapping vòng đời rõ ràng và kiểm tra SQL theo provider thực tế nếu nghiệp vụ phụ thuộc vào hành vi xóa.

### 4.1. CascadeType.REMOVE, orphanRemoval và ON DELETE CASCADE là ba cơ chế khác nhau

| Cơ chế | Nơi khai báo | Khi nào được kích hoạt | Ai thực hiện hành động chính? |
| --- | --- | --- | --- |
| `CascadeType.REMOVE` | Mapping JPA | Gọi `remove(parent)` và cascade tới child | JPA provider |
| `orphanRemoval = true` | Mapping quan hệ JPA | Child không còn thuộc quan hệ sở hữu tương ứng | JPA provider |
| `ON DELETE CASCADE` | Ràng buộc FK của DB | SQL DELETE parent làm database xóa child tham chiếu | Database |

Không thể suy luận rằng `cascade = CascadeType.ALL` sẽ tự thêm `ON DELETE CASCADE` vào schema đã tồn tại. Ngược lại, database có `ON DELETE CASCADE` không tự khiến JPA gọi callback `@PreRemove` trên mọi child bị database xóa ngầm.

Nếu trộn cơ chế xóa của provider và database, cần đánh giá tương tác với persistence context, entity callbacks, second-level cache và trạng thái các entity đã được nạp. Một child bị DB xóa ngầm có thể vẫn tồn tại dưới dạng managed object trong context nếu provider không được thông báo.

### 4.2. Xóa child khỏi danh sách bằng orphanRemoval

Với mapping chính `orphanRemoval = true`:

~~~java
em.getTransaction().begin();

PurchaseOrder order = em.find(PurchaseOrder.class, 1001L);
OrderLine removedLine = order.getLines().get(0);

order.removeLine(removedLine);

em.getTransaction().commit();
~~~

Ý định nghiệp vụ là xóa dòng đã bị bỏ khỏi đơn. Provider có thể phát SQL tương đương:

~~~sql
DELETE FROM order_lines WHERE id = ?;
~~~

Trong quá trình thao tác Java, helper đặt `removedLine.order` về null để đồng bộ object graph. Đó là **trạng thái trung gian của object**, không có nghĩa phải có một `UPDATE order_lines SET order_id = NULL` được commit. Với child là orphan và mapping `orphanRemoval`, provider xử lý việc xóa theo lifecycle phù hợp.

**Không dùng orphanRemoval để “chuyển” cùng một child sang parent khác.** Khi đã bị xóa khỏi quan hệ sở hữu, child có thể được lên lịch remove; thêm nó vào collection mới trong cùng transaction không bảo đảm JPA sẽ hiểu đây là thao tác đổi owner an toàn.

## 5. Flush và commit: lúc nào ràng buộc được kiểm tra?

Ba khái niệm thường bị nhầm:

- **Thay đổi object:** gọi `order.addLine(...)`, `order.removeLine(...)` hay sửa `line.order` trong bộ nhớ.
- **Flush:** JPA provider đồng bộ trạng thái đang managed thành SQL, thực thi những lệnh cần thiết trong transaction.
- **Commit:** transaction được hoàn tất; database quyết định các thay đổi có được ghi bền vững hay rollback.

~~~text
begin transaction
     |
     +--> persist parent
     +--> persist child
     +--> remove another child
     |
     v
  flush / SQL execution
     |
     +--> DB có thể kiểm tra NOT NULL, FK, UNIQUE
     |
     v
  commit
     |
     +--> DB hoàn tất các ràng buộc được trì hoãn (nếu có)
     +--> commit thành công hoặc transaction thất bại
~~~

SQL có thể được thực thi tại:

1. `em.flush()` được gọi tường minh.
2. Trước hoặc trong một truy vấn khi provider cần bảo đảm kết quả đúng theo flush mode.
3. `commit()` nếu còn thay đổi chờ đồng bộ.
4. Thời điểm khác do chiến lược sinh khóa hoặc hành vi provider yêu cầu.

Vì thế, **không phải lỗi FK nào cũng xuất hiện ngay tại dòng `em.persist(...)`**. Một lỗi có thể chỉ xuất hiện tại `flush()`, một truy vấn phía sau hoặc lúc `commit()`.

### 5.1. Flush không tự sửa mọi thứ tự nghiệp vụ sai

Nếu application giữ `line.order = null` và cột `order_id NOT NULL`, gọi:

~~~java
em.flush();
~~~

không tự đoán được child thực sự thuộc đơn hàng nào. Provider chỉ có thể đồng bộ quan hệ dựa trên mapping và trạng thái object.

Nếu một quy trình đòi hỏi **thứ tự thao tác tách biệt** để thỏa unique constraint hoặc quan hệ vòng, đôi khi cần chia thành các giai đoạn thao tác có flush có chủ đích. Tuy nhiên `flush()` không phải `commit()` và cũng không là công cụ bảo đảm SQL action queue sẽ sắp xếp theo thứ tự tùy ý của người viết code.

### 5.2. Ràng buộc kiểm tra ngay và kiểm tra trì hoãn

Nhiều database kiểm tra FK/NOT NULL ngay khi SQL statement được thực thi. Một số database, ví dụ PostgreSQL, hỗ trợ **DEFERRABLE foreign key** cho phép hoãn việc kiểm tra tới cuối transaction trong phạm vi được cấu hình:

~~~sql
ALTER TABLE order_lines
ADD CONSTRAINT fk_order_lines_order_deferred
FOREIGN KEY (order_id)
REFERENCES purchase_orders(id)
DEFERRABLE INITIALLY DEFERRED;
~~~

Đây là **một phương án cấu hình riêng** của schema: nếu dùng đoạn SQL này, phải bỏ/thay thế constraint FK cũ để tránh khai báo trùng. Không phải mọi DB/dialect có cú pháp hoặc hành vi giống nhau.

Cần phân biệt:

- FK deferrable có thể cho phép một trạng thái **tạm thời** chưa thỏa tham chiếu trong transaction, nếu kết quả cuối transaction hợp lệ.
- `NOT NULL` vẫn có thể được kiểm tra ngay; không thể dựa vào deferrable FK để chèn `NULL` vào cột NOT NULL.
- Deferred constraint không thay thế thiết kế association và lifecycle đúng trong JPA.
- Lỗi vi phạm ràng buộc hoãn có thể chỉ xuất hiện ở **commit**, dù flush trước đó không báo lỗi.

Trong ứng dụng thông thường, cách tốt nhất vẫn là xây dựng **thứ tự nghiệp vụ và mapping hợp lệ** mà không dựa vào deferred constraints, trừ khi quy trình/migration thực sự cần chúng.

## 6. Thao tác UPDATE FK khi đổi owner

Khóa ngoại có thể thay đổi khi child được chuyển từ parent A sang parent B. Tuy nhiên trước hết phải quyết định **child có được chuyển owner hay không**.

Nếu `OrderLine` là thành phần của đơn hàng và bật `orphanRemoval = true`, việc chuyển một dòng từ đơn A sang đơn B thường không phù hợp mô hình nghiệp vụ: dòng là thành phần được xóa khi rời A. Muốn **chuyển** một đối tượng độc lập giữa các parent, nên dùng quan hệ một-nhiều **không orphan removal**.

Ví dụ khác: `Department` 1–N `Employee`. Nhân viên có thể chuyển phòng ban, và `employee.department_id` bắt buộc có giá trị.

~~~java
@Entity
@Table(name = "departments")
public class Department {

    @Id
    private Long id;

    @OneToMany(mappedBy = "department")
    private List<Employee> employees = new ArrayList<>();

    // Constructor và API nghiệp vụ...
}
~~~

~~~java
@Entity
@Table(name = "employees")
public class Employee {

    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "department_id", nullable = false)
    private Department department;

    // Constructor và API nghiệp vụ...
}
~~~

Trong transaction, thay đổi quan hệ bằng **owning side**:

~~~java
Department oldDepartment =
    em.find(Department.class, oldDepartmentId);

Department newDepartment =
    em.find(Department.class, newDepartmentId);

Employee employee = em.find(Employee.class, employeeId);

// Cả hai Department phải tồn tại và được phép nhận nhân viên.
oldDepartment.getEmployees().remove(employee);
employee.changeDepartment(newDepartment);
newDepartment.getEmployees().add(employee);
~~~

Đây là **đoạn minh họa thao tác**, giả định collection có API phù hợp và `Employee.changeDepartment(...)` gán trường `department`. Trong model thực tế, nên dùng các helper method nhất quán để giữ cả hai collection và owning side, thay vì để tầng service sửa trực tiếp collection nội bộ.

Provider có thể thực thi:

~~~sql
UPDATE employees
SET department_id = :newDepartmentId
WHERE id = :employeeId;
~~~

Vì FK không null, chuyển trực tiếp từ ID A sang ID B thường tránh trạng thái SQL `department_id = NULL` tạm thời. **Không cần xóa nhân viên rồi chèn lại** nếu identity và lifecycle của nhân viên độc lập với phòng ban.

Nếu viết `oldDepartment.employees.remove(employee)` mà không cập nhật `employee.department`, owning side có thể vẫn giữ phòng ban cũ; bảng DB có thể không nhận đúng thay đổi mong muốn. Hai phía của quan hệ phải được đồng bộ trong object model.

### 6.1. Chú ý chuyển owner với unique constraint hoặc khóa ghép

Nếu child có khóa chính được dẫn xuất từ parent bằng `@MapsId`, việc đổi parent có thể làm thay đổi **primary key** của child. Đây không còn là UPDATE FK thông thường; khóa entity không nên bị sửa trong trạng thái managed. Khi đó, cần thiết kế quy trình xóa/tạo hoặc xem lại việc gắn identity child với parent.

Nếu database có ràng buộc `UNIQUE(parent_id, position)` cho thứ tự item trong từng parent, chuyển child có thể va chạm vị trí ở parent đích; cần bố trí thứ tự và thao tác phù hợp, không chỉ đổi FK.

## 7. @OneToMany một chiều dùng @JoinColumn có thể phát sinh thêm UPDATE

Không phải mọi mapping one-to-many đều có `@ManyToOne` ở child. Một cách khác là khai báo **unidirectional one-to-many** từ parent:

~~~java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(cascade = CascadeType.PERSIST)
    @JoinColumn(name = "order_id")
    private List<OrderLine> lines = new ArrayList<>();

    // Constructors và methods...
}
~~~

Trong biến thể này, `OrderLine` **không có** thuộc tính `order`. Quan hệ được quản lý qua collection của parent; `@JoinColumn(name="order_id")` ánh xạ FK tại bảng child.

Một số provider/cấu hình có thể thực hiện:

~~~sql
INSERT INTO purchase_orders (...);   -- Tạo parent
INSERT INTO order_lines (...);       -- Tạo child
UPDATE order_lines
SET order_id = ?
WHERE id = ?;                        -- Thiết lập FK sau
~~~

Nếu child được INSERT với `order_id = NULL` trong khi schema có `order_id NOT NULL`, database có thể từ chối INSERT **trước khi** provider kịp UPDATE FK.

Không thể khẳng định mọi provider sẽ phát sinh chính xác chuỗi SQL trên; hành vi tùy ORM, kiểu ID, mapping, cascade và phiên bản. Nhưng đây là tình huống quan trọng khi **đánh giá thứ tự cập nhật**: việc nhìn thấy một collection trong Java không bảo đảm provider sẽ chèn ngay child với FK hợp lệ.

| Tiêu chí | Hai chiều `@ManyToOne` + `mappedBy` | Một chiều `@OneToMany @JoinColumn` |
| --- | --- | --- |
| Phía quản lý FK | Field `child.parent` | Collection `parent.children` |
| Có reference từ child tới parent? | Có | Không |
| Có thể gán FK khi INSERT child? | Mapping owning side có thông tin parent trực tiếp | Tùy provider/cách thực thi, có thể cần UPDATE |
| Rủi ro với FK `NOT NULL` | Chủ yếu khi code không gán parent hoặc cascade sai | Có thể gặp INSERT rồi UPDATE FK theo provider |
| Phù hợp | Mô hình có mối liên hệ hai chiều rõ, FK bắt buộc | Khi không muốn child tham chiếu parent trong object model và đã đánh giá SQL |

Trong hệ thống có FK bắt buộc và cần kiểm soát hành vi INSERT, ánh xạ **`@ManyToOne` phía child + `@OneToMany(mappedBy)` phía parent** thường thể hiện cấu trúc relational rõ hơn.

### 7.1. Một chiều không khai báo @JoinColumn

Nếu chỉ viết:

~~~java
@OneToMany
private List<OrderLine> lines;
~~~

JPA có thể sử dụng **join table** theo quy tắc mapping mặc định:

~~~text
purchase_orders      purchase_order_lines       order_lines
      id ---------> order_id | line_id <--------- id
~~~

Khi đó, quan hệ được biểu diễn bởi các hàng trong join table, không phải cột `order_lines.order_id` của ví dụ đầu bài. Thứ tự thao tác có thể gồm INSERT vào parent, INSERT vào child và **INSERT vào join table**. Ràng buộc FK nằm ở bảng liên kết; cách xóa/reorder cũng khác.

Cần biết **mapping thực tế có FK ở bảng child hay join table** trước khi suy ra SQL và vị trí constraint cần xử lý.

## 8. @OrderBy và @OrderColumn ảnh hưởng thứ tự UPDATE khác nhau

Tên “thứ tự” trong JPA có ít nhất hai nghĩa:

1. **Thứ tự các câu SQL chạy khi flush**: do dependency, provider và ràng buộc DB ảnh hưởng.
2. **Thứ tự phần tử trong collection**: do `@OrderBy` hoặc `@OrderColumn` quy định.

Hai nghĩa này không đồng nhất.

### 8.1. @OrderBy: sắp kết quả truy vấn

~~~java
@OneToMany(mappedBy = "order")
@OrderBy("id ASC")
private List<OrderLine> lines = new ArrayList<>();
~~~

`@OrderBy` yêu cầu thứ tự khi truy xuất collection theo thuộc tính của entity. Nó **không tự thêm cột vị trí** để ghi lại thứ tự phần tử theo thao tác kéo thả ở UI.

### 8.2. @OrderColumn: lưu thứ tự thành dữ liệu

~~~java
@OneToMany(mappedBy = "order")
@OrderColumn(name = "position_index")
private List<OrderLine> lines = new ArrayList<>();
~~~

Với `@OrderColumn`, hệ thống có thể lưu một chỉ số vị trí trong bảng child:

~~~text
id   order_id   position_index   sku
501     1001          0          BOOK-01
502     1001          1          PEN-02
503     1001          2          BAG-03
~~~

Khi chèn hoặc xóa một phần tử ở giữa `List`, provider có thể cần cập nhật vị trí của **nhiều dòng khác**, ví dụ:

~~~sql
UPDATE order_lines SET position_index = 1 WHERE id = 503;
UPDATE order_lines SET position_index = 2 WHERE id = 502;
~~~

Các câu trên chỉ minh họa việc thay đổi chỉ số, không đại diện cho thứ tự SQL cố định của Hibernate hay provider bất kỳ.

Nếu áp dụng constraint `UNIQUE(order_id, position_index)`, các bước đổi vị trí có thể **tạm trùng chỉ số**, ngay cả khi trạng thái cuối cùng là một hoán vị hợp lệ. Provider có thể sử dụng chiến lược cập nhật khác nhau, nhưng application vẫn cần cân nhắc ràng buộc:

- Khi swap hai vị trí, liệu DB kiểm tra unique ngay ở từng UPDATE?
- Có cần đặt giá trị vị trí tạm, chia bước flush hoặc dùng ràng buộc deferrable khi DB hỗ trợ?
- Khi nhiều người sửa thứ tự đồng thời, có cần `@Version` hoặc cơ chế khóa phù hợp?
- Có nên dùng một trường `sortOrder` do nghiệp vụ quản lý thay cho `@OrderColumn`?

**`@OrderColumn` có thể làm số lượng UPDATE tăng mạnh khi reorder.** Không chọn annotation này chỉ vì muốn danh sách hiển thị theo một tiêu chí cố định; `@OrderBy` thường đủ nếu không cần lưu thứ tự vị trí riêng.

## 9. Sắp xếp và batching SQL của provider

Một số provider có các tùy chọn tối ưu thứ tự INSERT/UPDATE hoặc JDBC batching. Ví dụ với Hibernate, các thuộc tính như:

~~~properties
hibernate.order_inserts=true
hibernate.order_updates=true
hibernate.jdbc.batch_size=30
~~~

có thể giúp gom những thao tác tương tự để giảm số lần round-trip, tùy phiên bản Hibernate, dialect, chiến lược ID và mapping thực tế.

Các tùy chọn này **không biến code gọi `persist()` thành SQL chạy đúng thứ tự mong muốn**, và không sửa được mapping FK sai.

Cần phân biệt:

- **Thứ tự nghiệp vụ**: thao tác nào được phép xảy ra theo luật domain, ví dụ không xóa đơn hàng trước khi xử lý các dòng tham chiếu.
- **Thứ tự SQL của provider**: do action queue, dependency, flush và tối ưu hóa thực hiện.
- **Thứ tự khóa/ràng buộc database**: khi nào DB cho phép INSERT/UPDATE/DELETE với FK, unique, NOT NULL.

Có thể dùng SQL logging trong môi trường phát triển để quan sát:

~~~text
BEGIN
INSERT purchase_orders ...
INSERT order_lines ...
UPDATE order_lines ...
DELETE order_lines ...
COMMIT
~~~

Đây là sơ đồ quan sát, không phải khẳng định thứ tự thực tế. Để đánh giá chính xác, cần xem câu SQL provider phát ra, giá trị tham số và schema đang chạy; không dựa vào thứ tự các dòng code Java để kết luận.

## 10. Quan hệ vòng và hai FK bắt buộc

Một tình huống khó hơn là hai bảng tham chiếu bắt buộc lẫn nhau:

~~~text
Table A: b_id NOT NULL -> B.id
Table B: a_id NOT NULL -> A.id
~~~

Khi cả hai bảng chưa có hàng nào, câu hỏi xuất hiện: phải INSERT A hay INSERT B trước? Với FK được kiểm tra ngay và cả hai cột đều NOT NULL, **không có thứ tự chèn đơn giản nào hợp lệ** nếu cả hai ID đều phải tham chiếu hàng đã tồn tại.

Đây không chỉ là vấn đề chọn lệnh `persist` đầu tiên. Có thể cần:

1. **Thiết kế lại quan hệ**, ví dụ bỏ FK dư thừa, chỉ giữ một owning side thực sự cần thiết.
2. **Cho phép một liên kết tạm null** trong lúc tạo dữ liệu, rồi UPDATE khi cả hai hàng đã tồn tại (nếu nghiệp vụ cho phép).
3. **Dùng ràng buộc FK deferrable** trên DB hỗ trợ, kết hợp giá trị khóa đã biết và quy trình transaction được kiểm soát.
4. **Tách quy trình tạo dữ liệu** thành những trạng thái nghiệp vụ hợp lệ.

Đặc biệt, việc đặt `cascade = ALL` ở cả hai chiều không tự giải quyết một chu trình phụ thuộc SQL không thể thỏa về mặt ràng buộc.

## 11. Gỡ liên kết khác với xóa child

Xét hai mô hình:

**A. Child phụ thuộc parent**, ví dụ dòng đơn hàng:

~~~java
@OneToMany(mappedBy = "order", orphanRemoval = true)
private List<OrderLine> lines;
~~~

Khi bỏ một dòng khỏi collection, ý định là **xóa dòng**. Không có trạng thái nghiệp vụ “dòng hàng tồn tại nhưng không thuộc đơn hàng” vì FK `NOT NULL`.

**B. Child độc lập có thể đổi owner**, ví dụ nhân viên chuyển phòng ban:

~~~java
@OneToMany(mappedBy = "department")
private List<Employee> employees;
~~~

Khi employee chuyển từ phòng ban A sang B, ý định là **UPDATE FK** chứ không xóa employee. Với `department_id NOT NULL`, chỉ “gỡ khỏi A” mà không gắn vào B sẽ tạo trạng thái không hợp lệ.

| Nghiệp vụ | Mapping nên cân nhắc | Thao tác SQL logic |
| --- | --- | --- |
| Bỏ dòng hàng khỏi đơn | `orphanRemoval = true` nếu child thuộc vòng đời parent | DELETE child |
| Chuyển nhân viên sang phòng khác | Không orphanRemoval; cập nhật owning side | UPDATE child.department_id |
| Xóa đơn và toàn bộ dòng hàng | Cascade REMOVE hoặc xóa child có kiểm soát | DELETE child trước parent, hoặc DB cascade |
| Xóa đơn nhưng giữ dòng không có parent | Chỉ phù hợp nếu schema và domain cho phép nullable FK | UPDATE child.order_id = NULL rồi DELETE parent |
| Di chuyển child có PK chứa parent ID | Cần thiết kế lại identity/procedure | Thường không phải UPDATE FK đơn giản |

Nhìn vào **vòng đời thực sự của child** trước khi chọn cascade và nullable. Chỉ sửa mapping để hết lỗi constraint mà không xác định đúng nghiệp vụ sẽ tạo ra nhiều lỗi khó hơn sau này.

## 12. Bulk JPQL UPDATE/DELETE và trạng thái persistence context

JPA hỗ trợ bulk operations, ví dụ:

~~~java
int deleted = em.createQuery(
    """
    DELETE FROM OrderLine l
    WHERE l.order.id = :orderId
    """
).setParameter("orderId", 1001L)
 .executeUpdate();
~~~

Bulk JPQL tác động trực tiếp tới dữ liệu tương ứng và **không vận hành giống cách gọi `remove()` trên từng managed entity**. Chúng có thể bỏ qua cascade entity, orphan removal và lifecycle callback theo cơ chế thao tác entity thông thường; managed instances đã được tải trước đó cũng có thể giữ trạng thái cũ trong persistence context.

Nếu sau bulk DELETE tiếp tục gọi `em.remove(parent)`, có thể cần `flush()`/`clear()` hoặc thay đổi thứ tự thao tác và ngữ cảnh để bảo đảm provider không giữ child stale trong bộ nhớ. Không xóa/clear bừa khi còn các thay đổi khác chưa flush, vì `clear()` detach toàn bộ entity và có thể làm mất những cập nhật đang chờ.

Một ví dụ transaction có kiểm soát:

~~~java
em.getTransaction().begin();

// Không giữ trước đó một graph OrderLine đang managed.
em.createQuery(
    "DELETE FROM OrderLine l WHERE l.order.id = :orderId"
).setParameter("orderId", 1001L)
 .executeUpdate();

PurchaseOrder parent =
    em.find(PurchaseOrder.class, 1001L);

if (parent != null) {
    em.remove(parent);
}

em.getTransaction().commit();
~~~

Kịch bản trên phù hợp để minh họa **bulk delete child trước parent** khi không có child đang managed từ trước. Nếu provider/lifecycle sử dụng collection đã nạp hoặc second-level cache, cần thiết kế và xác nhận cách phối hợp riêng; bulk operation không phải giải pháp thay thế chung cho cascade và entity lifecycle.

## 13. Concurrency: tại sao thứ tự đúng vẫn có thể gặp lỗi?

Giả sử T1 chuẩn bị xóa đơn hàng, trong khi T2 đang thêm một `OrderLine` cho cùng đơn:

~~~text
T1                                  T2
-----------------------------       -----------------------------
SELECT order_lines WHERE ...        SELECT purchase_orders ...
DELETE old order_lines              INSERT new order_line(...)
DELETE purchase_orders              COMMIT?
COMMIT?
~~~

Thứ tự hợp lệ trong một transaction **không tự ngăn transaction khác chèn thêm child** vào giữa các bước. Database có thể khóa, đợi hoặc báo lỗi FK/serialization tùy isolation level và thứ tự transaction; application cần xử lý tình huống cạnh tranh hợp lý.

Các lựa chọn tùy bài toán:

- Thực hiện thay đổi trạng thái đơn hàng trong transaction và ngăn thao tác thêm dòng sau khi đơn bị hủy.
- Dùng optimistic locking với `@Version` để phát hiện cập nhật cạnh tranh trên entity phù hợp; lưu ý thay đổi tập child không phải lúc nào cũng tự tăng version parent trong mọi mapping/provider.
- Khi cần đồng bộ chặt, cân nhắc pessimistic lock theo đặc điểm DB và mức cô lập transaction.
- Dựa vào FK, CHECK, UNIQUE và các ràng buộc database như tuyến phòng vệ cuối.
- Xử lý ngoại lệ transaction bằng rollback, thông báo nghiệp vụ và retry có kiểm soát nếu thao tác thực sự an toàn để thử lại.

Không nên “giải quyết” lỗi khóa ngoại bằng cách tắt constraint trong production. Khóa ngoại đang cung cấp bảo vệ mà object model không thể thay thế khi có nhiều transaction và nhiều ứng dụng cùng truy cập database.

## 14. Quan sát thứ tự SQL khi điều tra lỗi thực tế

Một quy trình phân tích thủ công có thể bắt đầu từ **schema**, sau đó tới **mapping**, cuối cùng mới xem các lệnh SQL:

| Cần kiểm tra | Câu hỏi |
| --- | --- |
| `FOREIGN KEY` | Cột nào tham chiếu bảng nào? Có `ON DELETE CASCADE`/`SET NULL` không? |
| `NOT NULL` | FK có được phép null ở bất cứ bước trung gian nào không? |
| `UNIQUE` | Có ràng buộc cặp `(parent_id, position)` hoặc thứ tự khác không? |
| Owning side | `@ManyToOne` nào ghi cột FK? Hay collection `@OneToMany @JoinColumn` sở hữu FK? |
| Cascade | Có truyền `PERSIST`/`REMOVE` theo vòng đời nghiệp vụ không? |
| Orphan removal | Gỡ child khỏi collection có được hiểu là DELETE không? |
| ID generation | Parent ID có ngay hay phải INSERT để lấy ID? |
| Flush point | Lỗi xảy ra ở `persist`, `flush`, truy vấn hay `commit`? |
| Provider | Có batching, ordering, bytecode enhancement, API riêng ảnh hưởng hành vi không? |
| Concurrency | Có giao dịch khác đồng thời thêm/xóa/chuyển child không? |

Ví dụ thấy SQL:

~~~text
INSERT INTO order_lines (id, order_id, ...) VALUES (..., NULL, ...)
ERROR: order_id violates NOT NULL
~~~

Điều cần tìm là **vì sao phía sở hữu FK chưa có parent** hoặc mapping buộc provider thực hiện insert rồi update; không phải chỉ đổi thứ tự hai dòng `persist` trong source code.

Ví dụ thứ hai:

~~~text
DELETE FROM purchase_orders WHERE id = 1001
ERROR: foreign key violation on order_lines.order_id
~~~

Điều cần xem là **child đã được xóa chưa**, có cascade remove/orphan removal đúng mục đích không và database có chính sách xóa phù hợp hay không.

Ví dụ thứ ba:

~~~text
UPDATE order_lines SET position_index = 1 WHERE id = 503
ERROR: duplicate key for (order_id, position_index)
~~~

Ở đây nguyên nhân là **UNIQUE trong quá trình reorder**; đánh giá `@OrderColumn` và từng giai đoạn cập nhật thay vì chỉ nhìn FK.

## 15. Bài tập tình huống

### Bài 1. Persist hai entity mới nhưng chưa gán owning side

~~~java
PurchaseOrder order = new PurchaseOrder();
OrderLine line = new OrderLine("PEN-01", 3);

// Chỉ thêm vào collection, không set line.order.
order.getInternalLines().add(line);

em.persist(order);
~~~

**Hỏi:** Nếu `order_id NOT NULL`, rủi ro chính là gì?

**Giải thích:** Nếu owning side `line.order` vẫn null, provider không có association hợp lệ để ghi `order_id`. Có thể gặp lỗi mapping/lifecycle hoặc vi phạm `NOT NULL`. Dùng helper thống nhất hai phía, ví dụ `order.addLine(line)`, và cascade persist theo mô hình.

Đoạn `getInternalLines()` chỉ biểu diễn hành vi thêm trực tiếp vào collection để minh họa lỗi; class `PurchaseOrder` chính ở mục 2 không cung cấp API này nhằm tránh thao tác không nhất quán.

### Bài 2. Xóa parent khi còn child

Schema: `order_lines.order_id NOT NULL` có FK tới `purchase_orders.id`, không có `ON DELETE CASCADE`. Code gọi `em.remove(order)` nhưng mapping không cascade REMOVE và không xóa child.

**Hỏi:** Điều gì có thể xảy ra?

**Giải thích:** Database từ chối DELETE parent vì vẫn còn child tham chiếu. Cần xóa child trước, hoặc cấu hình cascade remove đúng với vòng đời dữ liệu, hoặc chính sách cascade ở database nếu đó là thiết kế được lựa chọn.

### Bài 3. Chuyển nhân viên giữa hai phòng ban

`Employee.department_id NOT NULL`; Employee là entity độc lập, không dùng orphan removal.

**Hỏi:** Nên xóa rồi insert Employee hay update FK?

**Giải thích:** Thông thường cập nhật owning side `employee.department = newDepartment` trong transaction để provider tạo `UPDATE employees SET department_id = ...`. Đồng bộ collection của hai Department để object graph nhất quán, tránh giai đoạn ghi FK null.

### Bài 4. Chèn giữa danh sách có @OrderColumn

Danh sách có vị trí `0, 1, 2`. Người dùng chèn phần tử mới vào index 1 và database có `UNIQUE(order_id, position_index)`.

**Hỏi:** Vì sao có thể cần nhiều UPDATE và có thể gặp lỗi unique?

**Giải thích:** Cần dời các phần tử cũ để nhường vị trí. Trong quá trình cập nhật, các dòng có thể tạm thời cùng `position_index`; unique constraint kiểm tra trước khi toàn bộ hoán vị hoàn tất. Cần cân nhắc cơ chế reorder và ràng buộc tương ứng.

### Bài 5. Có @OneToMany nhưng không có @ManyToOne

Parent dùng `@OneToMany @JoinColumn(name="order_id")`, child không có field parent.

**Hỏi:** Có thể kết luận một câu INSERT child luôn chứa `order_id` không?

**Giải thích:** Không. Một số provider có thể INSERT child trước rồi UPDATE FK qua collection mapping; điều này dễ xung đột với FK NOT NULL. Phải quan sát SQL thực tế và cân nhắc mapping owning side ở child nếu cần.

### Bài 6. Lỗi chỉ xuất hiện ở commit

Transaction đã gọi `em.flush()` nhưng không gặp lỗi FK; `commit()` báo vi phạm khóa ngoại.

**Hỏi:** Có phải chắc chắn JPA không flush gì không?

**Giải thích:** Không thể kết luận. Nếu FK là constraint **deferrable** và được trì hoãn tới commit, SQL ở flush vẫn có thể đã chạy. Cần xem cấu hình ràng buộc của DB và log transaction.

### Bài 7. Dùng cascade REMOVE và ON DELETE CASCADE cùng lúc

Hệ thống có `CascadeType.REMOVE` trong JPA và FK `ON DELETE CASCADE` trong DB.

**Hỏi:** Có nên mặc định DB cascade sẽ gọi `@PreRemove` trên từng child?

**Giải thích:** Không. DB cascade thực thi ở database; lifecycle callback của JPA phụ thuộc thao tác remove được provider quản lý. Cần hiểu rõ ai thực hiện việc xóa và hiệu ứng với managed context/caches.

## 16. Ghi nhớ

- Quan hệ **1–N ở Java** được lưu bằng **FK ở bảng child** hoặc join table, tùy mapping.
- Trong mapping hai chiều phổ biến, **`@ManyToOne` ở child sở hữu FK**, còn `@OneToMany(mappedBy)` là phía inverse.
- **Thứ tự gọi các lệnh JPA không bảo đảm trùng thứ tự SQL** vì provider có cơ chế flush, action queue, sinh ID và batching.
- Khi FK được kiểm tra ngay, **parent phải tồn tại trước child tham chiếu**; khi xóa parent, phải xử lý child đang tham chiếu hoặc có chính sách xóa phù hợp.
- **`CascadeType.REMOVE`, `orphanRemoval` và `ON DELETE CASCADE`** có vai trò, thời điểm và chủ thể thực thi khác nhau.
- Với child có **FK NOT NULL**, tháo association mà không xóa hoặc chuyển sang parent hợp lệ sẽ tạo dữ liệu không hợp lệ.
- **`@OneToMany @JoinColumn` một chiều** có thể dẫn đến INSERT rồi UPDATE FK ở một số provider, cần cân nhắc khi FK NOT NULL.
- **`@OrderColumn`** quản lý vị trí phần tử, có thể gây thêm UPDATE và va chạm UNIQUE; nó không phải quy tắc thứ tự SQL action.
- **Flush không phải commit**; một số constraint được kiểm tra tại SQL statement, một số có thể được hoãn tới commit tùy database.
- Muốn phân tích đúng một lỗi, cần xem đồng thời **schema constraint, owning side, lifecycle/cascade, điểm flush và SQL thực tế**.

Cách đặt câu hỏi hữu ích nhất là: **“Khi dòng SQL này chạy, parent đã tồn tại chưa, FK có giá trị hợp lệ chưa và child có đang được xử lý đúng vòng đời hay không?”** Từ đó mới lựa chọn mapping, transaction boundary và thao tác dữ liệu phù hợp, thay vì dựa vào thứ tự các dòng Java để suy ra an toàn ràng buộc.
