# JDBC 4.2: LocalDate, LocalTime và LocalDateTime với kiểu SQL tương ứng

## 1. Học đúng ba ánh xạ hiện hành

JDBC 4.2 mở rộng các ánh xạ ngày giờ cho **java.time** có từ Java 8. Khi thiết kế cột SQL với ý nghĩa đúng, những cặp điển hình là:

| Kiểu SQL | Java 8+ (java.time) | Mang thông tin gì? |
| --- | --- | --- |
| **DATE** | **LocalDate** | Ngày lịch ISO, không có giờ và múi giờ |
| **TIME** không kèm timezone | **LocalTime** | Giờ–phút–giây và phần giây, không có ngày |
| **TIMESTAMP** không kèm timezone | **LocalDateTime** | Ngày cộng giờ địa phương, không có offset/zone |

Chẳng hạn lịch vận hành có **event_date = 2025-05-20**, **start_time = 09:08:07**, **created_local = 2025-05-20 14:30:45**. Mỗi trường cần một loại khác nhau; không nên chỉ lưu tất cả dưới dạng String hoặc java.util.Date.

**Mẫu chính của JDBC 4.2:**

~~~java
ps.setObject(1, LocalDate.of(2025, 5, 20));
ps.setObject(2, LocalTime.of(9, 8, 7));
ps.setObject(3, LocalDateTime.of(2025, 5, 20, 14, 30, 45));

LocalDate d = rs.getObject("event_date", LocalDate.class);
LocalTime t = rs.getObject("start_time", LocalTime.class);
LocalDateTime dt = rs.getObject("created_local", LocalDateTime.class);
~~~

Đây là **snippet trong method có PreparedStatement ps, ResultSet rs đã đứng ở một row**, cùng các column và driver hỗ trợ java.time. Nó không chạy độc lập.

**Giới hạn quan trọng:** compiler chấp nhận các method này không chứng minh mọi driver/database đều hỗ trợ đầy đủ việc bind và convert. Bài sẽ phân biệt **unit test API**, **bridge test Java SE** và **integration test DB thật**, tránh đưa ra các cam kết không kiểm chứng.

Các API java.time/JDBC 4.2 vẫn được hỗ trợ trong Java SE hiện hành. Bài không chọn API legacy làm cách triển khai chính; những lớp java.sql.Date, java.sql.Time, java.sql.Timestamp chỉ được dùng khi cần liên thông với code/hệ thống hiện có.

## 2. Hiểu LocalDate, LocalTime và LocalDateTime trước khi lưu

**LocalDate** biểu diễn một ngày theo lịch ISO:

~~~java
LocalDate day = LocalDate.of(2025, 5, 20);
System.out.println(day);
// 2025-05-20
~~~

Nó phù hợp ngày sinh, hạn đăng ký, ngày làm việc, ngày đặt lịch. Không chứa giờ, múi giờ hoặc instant.

**LocalTime** biểu diễn giờ trong ngày:

~~~java
LocalTime start = LocalTime.of(9, 8, 7, 123_456_000);
System.out.println(start);
// 09:08:07.123456
~~~

Nó không có ngày và không thể tự xác định một instant trên timeline. Không nhầm LocalTime với **Duration**, kiểu biểu diễn khoảng thời gian.

**LocalDateTime** có ngày và giờ **theo trường địa phương**:

~~~java
LocalDateTime entered =
        LocalDateTime.of(2025, 5, 20, 14, 30, 45, 123_456_000);
System.out.println(entered);
// 2025-05-20T14:30:45.123456
~~~

Nó **không mang ZoneId/ZoneOffset**. Hai thành phố khác múi giờ có thể cùng local datetime nhưng khác instant. Nếu cần lưu một sự kiện trên timeline toàn cầu, phải thiết kế theo một mô hình có offset/instant hoặc quy ước timezone chính xác.

Cả ba đều immutable; chúng không có setter sửa trực tiếp giá trị. Phép cộng hay thay field tạo một value mới. Java có precision nanos, nhưng precision của SQL TIME/TIMESTAMP có thể thấp hơn và phải kiểm tra DB riêng.

## 3. Schema SQL phù hợp với mục tiêu

Một ví dụ schema theo cú pháp SQL cơ bản:

~~~sql
CREATE TABLE jdbc42_local_demo (
    id INTEGER PRIMARY KEY,
    event_date DATE NOT NULL,
    start_time TIME,
    created_local TIMESTAMP
);
~~~

**Đọc schema:**

- event_date dùng DATE, bắt buộc có giá trị.
- start_time dùng TIME và có thể SQL NULL.
- created_local dùng TIMESTAMP không timezone và có thể SQL NULL.
- id chỉ phục vụ tìm row, không phải một phần của mô hình ngày giờ.

Không nên mặc nhiên coi mọi sản phẩm DB đều có semantics giống hệt chỉ vì dùng tên **DATE/TIME/TIMESTAMP**. Ví dụ một vài hệ quản trị có loại DATE chứa cả thành phần giờ, hoặc có cấu hình timezone/session và fractional precision khác nhau. Hãy kiểm tra DDL, JDBC driver docs và version thật.

Nếu DB hỗ trợ cú pháp **TIMESTAMP(p)** hay **TIME(p)**, p xác định fractional-second precision theo product; không tự áp dụng một giá trị p cho mọi DB. Một hệ thống đòi bảo toàn nanos cần xác minh thực tế có cột/driver hỗ trợ mức chính xác mong muốn.

## 4. setObject: ghi giá trị java.time mà không tự format chuỗi

Giả sử **Connection connection** và bảng **schedule** đã được tạo đúng schema. Cách bind thông dụng:

~~~java
String sql = "INSERT INTO schedule " +
        "(event_date, start_time, created_local) VALUES (?, ?, ?)";

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setObject(1, LocalDate.of(2025, 5, 20));
    ps.setObject(2, LocalTime.of(9, 8, 7));
    ps.setObject(3, LocalDateTime.of(2025, 5, 20, 14, 30, 45));
    ps.executeUpdate();
}
~~~

Đoạn này là **snippet trong method có connection**. Dùng import java.sql.* và java.time.*.

**PreparedStatement placeholders được đánh số từ 1**, không từ 0. **setObject** gắn tham số có kiểu; **executeUpdate** mới thực thi INSERT/UPDATE.

**Ưu điểm:** không phải tự dùng toString rồi ghép SQL literals, không tạo date string từ locale, không cần chuyển xuống java.sql.Date/Timestamp khi driver hỗ trợ JDBC 4.2 trực tiếp.

Có thể dùng loại đích explicit:

~~~java
ps.setObject(1, LocalDate.of(2025, 5, 20), Types.DATE);
ps.setObject(2, LocalTime.of(9, 8, 7), Types.TIME);
ps.setObject(3, LocalDateTime.of(2025, 5, 20, 14, 30), Types.TIMESTAMP);
~~~

**Types.DATE/TIME/TIMESTAMP** là mã int của java.sql.Types. Chỉ dùng overload này khi driver công bố hỗ trợ conversion tương ứng.

## 5. SQLType/JDBCType: Java 8 có API nhưng driver mới quyết định hỗ trợ

JDBC 4.2 thêm **java.sql.SQLType** và enum **java.sql.JDBCType**:

~~~java
ps.setObject(1, LocalDate.of(2025, 5, 20), JDBCType.DATE);
ps.setObject(2, LocalTime.of(9, 8, 7), JDBCType.TIME);
ps.setObject(3, LocalDateTime.of(2025, 5, 20, 14, 30),
        JDBCType.TIMESTAMP);
~~~

**Không coi overload có JDBCType là luôn hoạt động trên mọi driver.** Phương thức **PreparedStatement.setObject(int,Object,SQLType)** là một default method; implementation mặc định có thể ném **SQLFeatureNotSupportedException**. Driver cần triển khai support thực tế.

Nếu setObject(index, localDate) chạy nhưng setObject(index, localDate, JDBCType.DATE) bị từ chối, đừng kết luận LocalDate không thể lưu; kiểm tra đúng overload mà driver hỗ trợ và dùng một lựa chọn có kiểm thử.

Tương tự, **setObject(index, Object, int targetSqlType)** cũng có thể cần driver hỗ trợ một conversion cụ thể. Nếu thiếu mapping, cập nhật driver hoặc chọn đường chuyển đổi được nhà cung cấp hướng dẫn; **không tự nối chuỗi SQL** như một workaround.

Một quy trình chọn API an toàn:

1. Schema xác định DATE, TIME và TIMESTAMP đúng nghĩa.
2. Chọn driver JDBC được hỗ trợ.
3. Thử **setObject(index,javaTime)** và **typed getObject** ở integration test.
4. Khi cần target type, thử overload **Types** hoặc **JDBCType** theo docs của driver.
5. Ghi lại precision/timezone và cách xử lý SQL NULL.

## 6. getObject với Class: yêu cầu driver đọc đúng Java type

**ResultSet** ban đầu có cursor ở trước dòng đầu tiên. Cần gọi **rs.next()** trước khi truy cập column:

~~~java
try (PreparedStatement ps = connection.prepareStatement(
        "SELECT event_date, start_time, created_local " +
        "FROM schedule WHERE id = ?")) {
    ps.setLong(1, id);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            LocalDate day = rs.getObject("event_date", LocalDate.class);
            LocalTime time = rs.getObject("start_time", LocalTime.class);
            LocalDateTime stamp =
                    rs.getObject("created_local", LocalDateTime.class);
            System.out.println(day + " / " + time + " / " + stamp);
        }
    }
}
~~~

Đây là snippet có connection/id/schema. **getObject(columnLabel, Class<T>)** yêu cầu conversion từ SQL column sang Java class mong muốn **nếu driver hỗ trợ**.

Có thể chọn index thay label:

~~~java
LocalDate day = rs.getObject(1, LocalDate.class);
LocalTime time = rs.getObject(2, LocalTime.class);
LocalDateTime stamp = rs.getObject(3, LocalDateTime.class);
~~~

Column indexes cũng bắt đầu từ 1. Nếu SELECT JOIN có nhãn trùng nhau, dùng alias rõ ràng trong query để tránh đọc nhầm cột.

**Không viết (LocalDateTime) rs.getObject("created_local") rồi tin rằng driver luôn trả LocalDateTime.** Overload getObject không có Class có thể trả java.sql.Timestamp hoặc kiểu driver-specific. Dùng typed getObject và test conversion thật.

Khi driver chưa hỗ trợ, **SQLException** hoặc **SQLFeatureNotSupportedException** là một kết cục cần được xử lý, không phải lý do bỏ qua kiểm tra kiểu.

## 7. SQL NULL khác với không có row

Một bảng có thể không chứa id cần tìm, hoặc có row nhưng column start_time là SQL NULL.

**Hai điều kiện không giống nhau:**

- **rs.next() == false**: không có row kế tiếp.
- **rs.next() == true, rs.getObject("start_time", LocalTime.class) == null**: có row, nhưng cột đó có SQL NULL.

Ví dụ:

~~~java
LocalTime start = rs.getObject("start_time", LocalTime.class);
if (start == null) {
    // Column SQL NULL ở row hiện tại.
}
~~~

Sau một lần getter, **rs.wasNull()** có thể xác nhận liệu giá trị getter vừa đọc có phải SQL NULL không:

~~~java
LocalDateTime value =
        rs.getObject("created_local", LocalDateTime.class);
boolean nullFromSql = rs.wasNull();
~~~

wasNull chỉ nói về **getter gần nhất**. Với kiểu tham chiếu LocalDateTime, kiểm tra **value == null** thường đã đủ rõ; wasNull đặc biệt hữu ích khi dùng getter trả primitive (như getInt).

Để ghi NULL vào cột, dùng **setNull** với SQL type tường minh:

~~~java
ps.setNull(2, Types.TIME);
ps.setNull(3, Types.TIMESTAMP);
~~~

**Không dùng LocalTime.MIDNIGHT hay LocalDateTime.MIN thay cho SQL NULL** trừ khi nghiệp vụ chủ động định nghĩa sentinel như vậy (và chấp nhận nó là một ngày giờ hợp lệ theo kiểu Java).

Nếu column DATE được khai báo NOT NULL, việc setNull sẽ bị constraint chặn ở bước chạy SQL. Đừng dùng một null Object mơ hồ qua setObject rồi trông đợi mọi driver suy được SQL type.

## 8. LocalDateTime không chứa Instant — lỗi timezone thường gặp

~~~java
LocalDateTime wall =
        LocalDateTime.of(2025, 5, 20, 14, 30, 45);
~~~

Giá trị trên **không tự biểu thị 14:30 UTC**. Khi gắn một timezone khác nhau, ta thu được các instant khác nhau:

~~~java
Instant asUtc = wall.atZone(ZoneOffset.UTC).toInstant();
Instant asVietnam =
        wall.atZone(ZoneId.of("Asia/Ho_Chi_Minh")).toInstant();

System.out.println(Duration.between(asUtc, asVietnam).toHours());
// -7 với ngày và hai zone của ví dụ.
~~~

**Cùng một LocalDateTime, hai cách diễn giải khác nhau.** Vì thế không lưu LocalDateTime với ý nghĩa "instant toàn cầu" nếu hệ thống chưa có convention minh bạch.

**Nếu domain thật sự là ngày–giờ địa phương**, lưu nó như local datetime và phải mang theo địa điểm/ZoneId nếu sau này cần biến thành instant. Với các vùng có DST, một local datetime tại thời điểm chuyển giờ có thể **mơ hồ hoặc không tồn tại** theo ZoneId cụ thể.

**Nếu domain thật sự là sự kiện ở một instant**, cân nhắc storage model/SQL type giữ timeline/offset đúng thiết kế, và kiểm thử driver/database. Không giả định **TIMESTAMP không timezone = UTC** trừ khi đó là một quy ước được bảo đảm từ đầu đến cuối pipeline.

## 9. TIME khác Duration; các SQL type kèm timezone khác mapping này

**TIME** biểu thị giờ trong ngày. Nếu lịch làm việc bắt đầu **22:30** và kết thúc **01:00**, so sánh LocalTime đơn thuần không đủ để quyết định khoảng thời gian vì có thể qua nửa đêm.

**Duration** là độ dài thời gian, không phải "giờ trong ngày"; **Instant** là điểm trên timeline, không phải đồng nghĩa với LocalTime/LocalDateTime.

JDBC 4.2 còn có các ánh xạ:

| SQL type | Java type phổ biến |
| --- | --- |
| TIME WITH TIME ZONE | **OffsetTime** |
| TIMESTAMP WITH TIME ZONE | **OffsetDateTime** |

Đừng thay **LocalTime** bằng OffsetTime khi SQL column thực sự là TIME không timezone rồi mong offset được giữ lại. Ngược lại, đưa LocalDateTime vào TIMESTAMP WITH TIME ZONE có thể làm mất hoặc suy diễn timezone/offset theo driver/session.

**Không tự suy mọi driver hỗ trợ Instant hoặc ZonedDateTime qua setObject/getObject**. Ngay cả các driver phổ biến cũng có khác biệt hỗ trợ và cách chuẩn hóa offset khi round-trip.

## 10. Precision của phần giây: Java nanos, SQL có thể ít hơn

LocalTime và LocalDateTime lưu phần giây với mức nanosecond:

~~~java
LocalTime fine = LocalTime.of(9, 8, 7, 123_456_789);
LocalDateTime fineTimestamp =
        LocalDateTime.of(2025, 5, 20, 14, 30, 45, 123_456_789);
~~~

Nhưng một DB có thể dùng TIME/TIMESTAMP với precision giới hạn theo giây, millisecond hay microsecond. JDBC driver có thể làm tròn hoặc cắt phần dư.

**Không hứa round-trip 123_456_789 nano** khi không biết column precision.

Một integration test nên INSERT giá trị có nano không tròn số, SELECT typed lại, rồi so sánh theo chính sách **đã xác nhận** của DB:

~~~java
LocalDateTime stored =
        rs.getObject("created_local", LocalDateTime.class);
int nanosObserved = stored.getNano();
~~~

Nếu schema được thiết kế giữ đến microsecond và nghiệp vụ chấp nhận **cắt** trước khi lưu, có thể chủ động chuẩn hóa:

~~~java
LocalDateTime normalized =
        fineTimestamp.truncatedTo(ChronoUnit.MICROS);
~~~

Đây là snippet cần java.time.temporal.ChronoUnit. **Đừng dùng cách cắt này mặc định cho mọi DB**, vì một DB có thể làm tròn thay vì cắt. Test các giá trị gần ranh giới fraction.

Với DATE, không có phần giây. Với TIME, còn phải kiểm tra xem column không timezone có được phép fraction ở DB sản phẩm đang dùng hay không.

## 11. Mẫu database thật: đã biên dịch, cần driver/DB để chạy

Chương trình sau xây một bảng test riêng, ghi hai hàng và đọc lại qua JDBC 4.2. Nó có thể được chạy nếu **JDBC_URL trỏ tới một database test cô lập**, driver được thêm vào classpath, SQL DDL được hỗ trợ và bảng chưa tồn tại.

Tạo tệp **Jdbc42DatabaseRoundTrip.java**:

~~~java
import java.sql.*;
import java.time.*;

public class Jdbc42DatabaseRoundTrip {
    public static void main(String[] args) throws Exception {
        String url = System.getenv("JDBC_URL");
        if (url == null || url.trim().isEmpty()) {
            throw new IllegalArgumentException("Set JDBC_URL for an isolated test DB");
        }

        try (Connection connection = DriverManager.getConnection(url)) {
            try (Statement ddl = connection.createStatement()) {
                ddl.executeUpdate("CREATE TABLE jdbc42_local_demo (" +
                        "id INTEGER PRIMARY KEY, " +
                        "event_date DATE NOT NULL, " +
                        "start_time TIME, " +
                        "created_local TIMESTAMP)");
            }

            String insert = "INSERT INTO jdbc42_local_demo " +
                    "(id, event_date, start_time, created_local) VALUES (?, ?, ?, ?)";
            try (PreparedStatement ps = connection.prepareStatement(insert)) {
                ps.setInt(1, 1);
                ps.setObject(2, LocalDate.of(2025, 5, 20));
                ps.setObject(3, LocalTime.of(9, 8, 7));
                ps.setObject(4, LocalDateTime.of(2025, 5, 20, 14, 30, 45));
                ps.executeUpdate();

                ps.setInt(1, 2);
                ps.setObject(2, LocalDate.of(2025, 5, 21));
                ps.setNull(3, Types.TIME);
                ps.setNull(4, Types.TIMESTAMP);
                ps.executeUpdate();
            }

            String select = "SELECT id, event_date, start_time, created_local " +
                    "FROM jdbc42_local_demo ORDER BY id";
            try (PreparedStatement ps = connection.prepareStatement(select);
                 ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    int id = rs.getInt("id");
                    LocalDate day = rs.getObject("event_date", LocalDate.class);
                    LocalTime time = rs.getObject("start_time", LocalTime.class);
                    LocalDateTime stamp =
                            rs.getObject("created_local", LocalDateTime.class);
                    System.out.println(id + " | " + day + " | " + time + " | " + stamp);
                }
            }
        }
    }
}
~~~

Lệnh biên dịch với JDK 17+:

~~~bash
javac Jdbc42DatabaseRoundTrip.java
~~~

**Bản source này đã được biên dịch bằng javac --release 17**, nhưng **chưa chạy với database thật**, do không có JDBC_URL/driver được cung cấp trong môi trường biên soạn. Không tuyên bố đã test round-trip DB khi chưa thực thi.

Nếu có test DB và driver được cấu hình, chạy theo công cụ build của dự án hoặc thêm driver vào classpath, ví dụ trên Unix:

~~~bash
java -cp ".:path/to/jdbc-driver.jar" Jdbc42DatabaseRoundTrip
~~~

Trên Windows, phân cách classpath thường là dấu chấm phẩy thay vì dấu hai chấm. **Đường dẫn JAR chỉ là minh họa**: dùng driver thật mà dự án đã cài. Dùng bảng test riêng, **không chạy lệnh CREATE TABLE thử nghiệm trên production**; lifecycle schema ở hệ thống thật cần migration.

**Kết quả kỳ vọng nếu DB/driver hỗ trợ các ánh xạ đã chọn và không thay đổi các trường giờ:**

~~~text
1 | 2025-05-20 | 09:08:07 | 2025-05-20T14:30:45
2 | 2025-05-21 | null | null
~~~

Đây là **expected output có điều kiện, chưa phải stdout từ DB thật**. Nếu DDL khác hoặc driver chưa hỗ trợ getObject kiểu java.time, kết quả có thể là SQLException/SQLFeatureNotSupportedException và test phải phản ánh điều đó. DDL có thể gây implicit commit tùy DBMS; không coi script mẫu là migration portable hoàn toàn.

## 12. Unit test tự chạy trên Java 17: xác nhận cách gọi API

Để kiểm tra code gọi **PreparedStatement.setObject** và **ResultSet.getObject(..., Class)** mà chưa có DB, có thể tạo **dynamic proxy** Java. Đây chỉ là **mock JDBC**: handler ghi nhận các tham số và mô phỏng hàng kết quả, không có SQL engine, không chứng minh driver có thể lưu java.time vào cột thật.

Tạo tệp **Jdbc42TemporalDemo.java**:

~~~java
import java.lang.reflect.*;
import java.sql.*;
import java.time.*;
import java.util.*;

public class Jdbc42TemporalDemo {
    static final class StatementRecorder implements InvocationHandler {
        final Map<Integer, Object> values = new LinkedHashMap<>();
        final Map<Integer, String> targets = new LinkedHashMap<>();
        boolean closed;
        @Override public Object invoke(Object proxy, Method method, Object[] args) {
            String name = method.getName();
            if (name.equals("setObject")) {
                int index = (Integer) args[0];
                values.put(index, args[1]);
                targets.put(index, args.length == 3 ? String.valueOf(args[2]) : "inferred");
                return null;
            }
            if (name.equals("setNull")) {
                int index = (Integer) args[0];
                values.put(index, null);
                targets.put(index, "SQL NULL/" + args[1]);
                return null;
            }
            if (name.equals("executeUpdate")) return 1;
            if (name.equals("close")) { closed = true; return null; }
            if (name.equals("isClosed")) return closed;
            throw new UnsupportedOperationException(name);
        }
    }

    static final class ResultRecorder implements InvocationHandler {
        private final Map<String, Object> row;
        boolean advanced;
        boolean lastWasNull;
        boolean closed;
        ResultRecorder(Map<String, Object> row) { this.row = row; }
        @Override public Object invoke(Object proxy, Method method, Object[] args)
                throws SQLException {
            String name = method.getName();
            if (name.equals("next")) {
                if (!advanced) { advanced = true; return true; }
                return false;
            }
            if (name.equals("getObject")) {
                if (!advanced) throw new SQLException("Call next first");
                Object value = row.get((String) args[0]);
                lastWasNull = value == null;
                return ((Class<?>) args[1]).cast(value);
            }
            if (name.equals("wasNull")) return lastWasNull;
            if (name.equals("close")) { closed = true; return null; }
            if (name.equals("isClosed")) return closed;
            throw new UnsupportedOperationException(name);
        }
    }

    public static void main(String[] args) throws Exception {
        LocalDate date = LocalDate.of(2025, 5, 20);
        LocalTime time = LocalTime.of(9, 8, 7, 123_456_000);
        LocalDateTime timestamp = LocalDateTime.of(2025, 5, 20, 14, 30, 45, 123_456_000);

        StatementRecorder recorder = new StatementRecorder();
        PreparedStatement ps = (PreparedStatement) Proxy.newProxyInstance(
                Jdbc42TemporalDemo.class.getClassLoader(),
                new Class<?>[] {PreparedStatement.class}, recorder);
        try (ps) {
            ps.setObject(1, date);
            ps.setObject(2, time, JDBCType.TIME);
            ps.setObject(3, timestamp, Types.TIMESTAMP);
            ps.setNull(4, Types.TIMESTAMP);
            System.out.println("mock update count: " + ps.executeUpdate());
        }
        System.out.println("bound classes: " +
                recorder.values.get(1).getClass().getSimpleName() + ", " +
                recorder.values.get(2).getClass().getSimpleName() + ", " +
                recorder.values.get(3).getClass().getSimpleName());
        System.out.println("bind targets: " +
                recorder.targets.get(1) + ", " +
                recorder.targets.get(2) + ", " +
                recorder.targets.get(3));
        System.out.println("bound SQL NULL: " + (recorder.values.get(4) == null));

        Map<String, Object> row = new LinkedHashMap<>();
        row.put("event_date", date);
        row.put("start_time", time);
        row.put("local_timestamp", timestamp);
        row.put("optional_timestamp", null);
        ResultRecorder resultRecorder = new ResultRecorder(row);
        ResultSet rs = (ResultSet) Proxy.newProxyInstance(
                Jdbc42TemporalDemo.class.getClassLoader(),
                new Class<?>[] {ResultSet.class}, resultRecorder);
        try (rs) {
            if (!rs.next()) throw new AssertionError("Missing row");
            System.out.println("typed date: " +
                    rs.getObject("event_date", LocalDate.class));
            System.out.println("typed time: " +
                    rs.getObject("start_time", LocalTime.class));
            System.out.println("typed timestamp: " +
                    rs.getObject("local_timestamp", LocalDateTime.class));
            System.out.println("typed SQL NULL: " +
                    (rs.getObject("optional_timestamp", LocalDateTime.class) == null));
            System.out.println("wasNull after null: " + rs.wasNull());
        }

        Instant asUtc = timestamp.atZone(ZoneOffset.UTC).toInstant();
        Instant asPlusSeven = timestamp.atZone(ZoneOffset.ofHours(7)).toInstant();
        System.out.println("same local fields, UTC offset difference hours: " +
                Duration.between(asUtc, asPlusSeven).toHours());
        System.out.println("DATE/TIME/TIMESTAMP codes: " +
                JDBCType.DATE.getVendorTypeNumber() + "/" +
                JDBCType.TIME.getVendorTypeNumber() + "/" +
                JDBCType.TIMESTAMP.getVendorTypeNumber());
        System.out.println("closed statement/result: " +
                recorder.closed + "/" + resultRecorder.closed);
        System.out.println("mock is not a JDBC driver: true");
    }
}
~~~

## 13. Bridge test Java 8: java.sql.Date, Time, Timestamp khi cần tích hợp

Đường JDBC 4.2 hiện đại vẫn ưu tiên java.time. Nhưng nếu một API khác trả **java.sql.Date / Time / Timestamp**, Java 8 đã có phương thức chuyển đổi:

| Đầu vào java.time | Tương tác java.sql được hỗ trợ |
| --- | --- |
| LocalDate | **java.sql.Date.valueOf(date)** → **toLocalDate()** |
| LocalTime | **java.sql.Time.valueOf(time)** → **toLocalTime()** |
| LocalDateTime | **java.sql.Timestamp.valueOf(dateTime)** → **toLocalDateTime()** |

Các wrapper kiểu cũ không nên được đẩy sâu qua domain model khi có java.time. **Đặc biệt, java.sql.Time có thể làm mất phần nano**. Test sau chạy được không cần database.

Tạo tệp **Jdbc42Java8BridgeDemo.java**:

~~~java
import java.sql.Date;
import java.sql.JDBCType;
import java.sql.Time;
import java.sql.Timestamp;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;
import java.time.ZoneOffset;

public class Jdbc42Java8BridgeDemo {
    public static void main(String[] args) {
        LocalDate date = LocalDate.of(2025, 5, 20);
        LocalTime time = LocalTime.of(9, 8, 7, 123_456_000);
        LocalDateTime timestamp =
                LocalDateTime.of(2025, 5, 20, 14, 30, 45, 123_456_000);

        System.out.println("DATE bridge: " +
                Date.valueOf(date).toLocalDate());
        System.out.println("TIME bridge: " +
                Time.valueOf(time).toLocalTime());
        System.out.println("TIME fractional second lost: " +
                (Time.valueOf(time).toLocalTime().getNano() == 0));
        System.out.println("TIMESTAMP bridge: " +
                Timestamp.valueOf(timestamp).toLocalDateTime());
        System.out.println("TIMESTAMP nanos: " +
                Timestamp.valueOf(timestamp).toLocalDateTime().getNano());
        System.out.println("DATE type: " + JDBCType.DATE.getName());
        System.out.println("TIME type: " + JDBCType.TIME.getName());
        System.out.println("TIMESTAMP type: " + JDBCType.TIMESTAMP.getName());
        System.out.println("local has no instant: " +
                timestamp.atOffset(ZoneOffset.UTC).toInstant());
    }
}
~~~

**Nói chính xác:** Java SE bridge giữ được field trong phép thử local này (trừ phần fraction qua java.sql.Time), nhưng **không chứng minh precision của dữ liệu đã qua database thực**.

## 14. Tương thích driver JDBC và database

JDBC 4.2 định nghĩa ánh xạ nhưng mức hỗ trợ tùy **driver cụ thể, phiên bản, DBMS, DDL và cấu hình connection/session**.

Các lỗi thường gặp:

- Driver không chấp nhận LocalDate/Time/DateTime khi gọi setObject.
- Driver không convert DATE/TIME/TIMESTAMP sang Class<T> qua getObject.
- Overload SQLType/JDBCType chưa được triển khai.
- Một cột tên DATE của vendor có semantics khác SQL chuẩn.
- TIME/TIMESTAMP bị làm tròn hoặc cắt fractional seconds.
- getObject không typed trả kiểu java.sql.Date/Time/Timestamp khác mong đợi.
- TIMESTAMP WITH TIME ZONE có policy normalization UTC/offset riêng ở DB.
- Cấu hình timezone của DB session ảnh hưởng cách dịch thời gian ở một số kiểu đường chuyển.

Có thể lấy metadata phục vụ chẩn đoán:

~~~java
DatabaseMetaData meta = connection.getMetaData();
System.out.println(meta.getDriverName());
System.out.println(meta.getDriverVersion());
System.out.println(meta.getJDBCMajorVersion() + "." +
                   meta.getJDBCMinorVersion());
~~~

Đây là snippet có Connection và throws SQLException. **Metadata cho biết điều driver công bố, không thay thế kiểm thử conversion thực tế**.

Không sử dụng **(LocalDateTime) rs.getObject(...)** như một fallback an toàn; kiểu object thực tế có thể khác. Kiểm tra driver docs và nâng driver nếu hỗ trợ java.time không đạt yêu cầu.

## 15. Test matrix: ngày, giờ, precision, NULL, timezone

Một bộ integration test nên bao phủ:

| Nhóm | Input | Kiểm chứng |
| --- | --- | --- |
| DATE | 2024-02-29 | Ngày nhuận hợp lệ, không trôi ngày |
| DATE | Cuối tháng/năm | Không tự thêm time hoặc lệch timezone |
| TIME | 00:00:00 | Midnight không bị nhầm với SQL NULL |
| TIME | 23:59:59 | Giá trị sát cuối ngày được giữ |
| TIME | 09:08:07.123456789 | Chính sách fractional precision đúng |
| TIMESTAMP | Midnight và cuối ngày | Giữ đúng trường local datetime |
| TIMESTAMP | Nano không tròn | Round/truncate theo schema |
| TIMESTAMP | Giá trị tại DST gap/overlap | Không tự suy Instant khi thiếu zone |
| Nullable | SQL NULL ở TIME/TIMESTAMP | getObject typed trả null |
| Driver | getObject(Class) không được hỗ trợ | Fail rõ ràng, không cast sai |
| Driver | setObject(index,value,JDBCType) | Xác minh overload này thật sự hoạt động |
| Session | Đổi timezone/session settings | Quan sát hành vi trên driver mục tiêu |
| Lifecycle | Đóng ResultSet/Statement | Không dùng object đã close |

**Quy tắc về precision:** nếu DB cắt đến microsecond, 123456789 nano có thể thành 123456000; nếu làm tròn, có thể thành 123457000. Test phải dựa trên contract documented, không chọn expected tùy ý.

Cần đặt fixture trong DB test cô lập và cleanup ở cuối. Không chạy DDL hoặc truncate các bảng nghiệp vụ thật để test.

## 16. Timezone/DST và mô hình dữ liệu

Một sai lầm phổ biến là lưu LocalDateTime vào TIMESTAMP rồi ngầm giả định đây là thời điểm UTC. Khi service khác lại diễn giải theo múi giờ máy, cùng một value có thể tương ứng các Instant khác nhau.

**Có hai thiết kế khác nhau:**

- **Wall-clock local:** giữ ngày–giờ như người dùng nhìn trên lịch, kèm ZoneId nếu sau này cần xác định instant; phù hợp lịch trình tại một địa điểm.
- **Timeline instant:** lưu một mốc duy nhất trên timeline, thiết kế theo offset/UTC/Instant và kiểu SQL/driver có semantics tương ứng; phù hợp event processing hoặc audit thời điểm xảy ra.

Đừng biến local timestamp thành instant bằng cách gắn UTC **không có căn cứ nghiệp vụ**. DST có thể tạo local time không tồn tại hoặc trùng hai lần. Việc chuyển sang instant cần quy tắc xử lý gap/overlap rõ ràng.

**Không dùng global TimeZone.setDefault một cách tùy tiện trong unit test chạy chung JVM**; nó có thể ảnh hưởng các test khác. Với những DB session timezone có tác động, test bằng môi trường/connection tách biệt theo chính sách DB.

## 17. SQL parameter hóa và đóng tài nguyên

Tránh tự nối ngày giờ vào SQL text:

~~~java
// Không nên dùng để sinh SQL nghiệp vụ từ data:
String sql = "SELECT id FROM schedule WHERE event_date = '" + day + "'";
~~~

Mặc dù LocalDate.toString thường có dạng ISO, nối literal có thể gây lỗi SQL dialect/quote/collation và mở ra lỗi injection khi code tương lai ghép dữ liệu input khác.

Dùng **PreparedStatement** và bind:

~~~java
try (PreparedStatement ps = connection.prepareStatement(
        "SELECT id FROM schedule WHERE event_date = ?")) {
    ps.setObject(1, day);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            System.out.println(rs.getLong(1));
        }
    }
}
~~~

Đây là snippet cần connection/day và schema. **PreparedStatement** bind value, không bind identifier (tên table/column) theo placeholder; tên động phải được whitelist theo SQL dialect.

**Đóng Connection, PreparedStatement và ResultSet** theo ownership. Try-with-resources giảm rò tài nguyên và xử lý exception lúc đóng. **Không coi try-with-resources là transaction**: commit/rollback, auto-commit và DDL lifecycle là vấn đề riêng của Connection/DBMS.

Nếu insert nhiều row phải atomic, thiết kế transaction và rollback đúng; JDBC mapping tự nó không bảo đảm nhiều statement cùng commit.

**Business meaning:** từng cột thật sự là ngày lịch, giờ trong ngày, local timestamp hay instant? Chọn model trước khi chọn database type.

**Schema:** kiểm tra DATE/TIME/TIMESTAMP, fractional precision, NULL/NOT NULL, timezone và đặc thù vendor.

**JDBC:** dùng driver được hỗ trợ, có test **setObject** java.time và **getObject(Class)** tương ứng, không chỉ kiểm tra compiler.

**Precision/timezone:** chọn chính sách round/truncate, test timezone context và DST khi domain cần; LocalDateTime không tự có Instant.

**Resources:** try-with-resources đóng statement/result set, quản lý connection theo ứng dụng/pool.

## 20. Bài tập và đáp án

**1.** SQL DATE tương ứng kiểu Java gì? — **LocalDate**.

**2.** SQL TIME không timezone tương ứng kiểu gì? — **LocalTime**.

**3.** SQL TIMESTAMP không timezone tương ứng kiểu gì? — **LocalDateTime**.

**4.** SQL TIMESTAMP WITH TIME ZONE có nên dùng LocalDateTime để bảo toàn offset? — **Không**; xem **OffsetDateTime** và kiểm thử DB/driver.

**5.** Ghi LocalDate vào PreparedStatement cách nào? — **setObject(index, localDate)** khi driver hỗ trợ.

**6.** Đọc DATE sang LocalDate cách nào? — **rs.getObject(column, LocalDate.class)** sau rs.next().

**7.** Có thể cast trực tiếp (LocalDate) rs.getObject(column) trên mọi driver không? — **Không**.

**8.** rs.next()==false và getObject(...)=null khác nhau? — **Không có row** khác **có row nhưng SQL NULL**.

**9.** Bind SQL NULL nên làm gì? — **ps.setNull(index, Types.TIME/DATE/TIMESTAMP)** theo cột.

**10.** LocalDateTime có tự là UTC? — **Không**, thiếu timezone.

**11.** Fractional nanoseconds có được DB giữ trọn không? — **Tùy precision column và driver**.

**12.** java.sql.Time bridge giữ nanos trong demo Java 8 không? — **Không**, in TIME fractional second lost: true.

**13.** Mock dynamic proxy đã chạy; có thể tuyên bố DB thật hỗ trợ typed getObject chưa? — **Chưa**, phải integration test.

**14.** Vì sao dùng PreparedStatement thay vì nối String SQL? — Bind dữ liệu đúng kiểu và an toàn hơn khi có input.

**15.** SQLType overload chưa được driver hỗ trợ thì nên làm gì? — Kiểm tra driver/overload, dùng cách bind có support và test; không nối SQL text để lách.

**16.** Một chương trình compile với java.sql.* nhưng chưa có JDBC driver có được coi là DB round-trip pass? — **Không**; compiler chỉ xác minh cú pháp, integration test cần driver/database.

## 21. Tổng kết và tài liệu Oracle hiện hành
