# Map.putIfAbsent và thêm có điều kiện

`putIfAbsent(K key, V value)` là phương thức của `java.util.Map` có từ Java 8 và **vẫn còn áp dụng trong các phiên bản Java hiện hành**. Đây là giải pháp khi ta muốn gắn **một giá trị mặc định hoặc giá trị khởi tạo** cho khóa mà **không ghi đè giá trị khác null đã tồn tại**.

Ví dụ: cấu hình `"theme"` đã có giá trị do người dùng chọn. Lúc khởi động, ứng dụng muốn điền mặc định `"light"` **chỉ nếu chưa có giá trị phù hợp**, không được hủy lựa chọn của người dùng.

Bài học giải thích chính xác khái niệm “vắng mặt” trong `Map`, giá trị trả về, trường hợp `null`, cách chọn giữa `putIfAbsent` và các thao tác thêm có điều kiện khác, cũng như tính nguyên tử khi có nhiều thread. Đây là các hợp đồng API vẫn được hỗ trợ, không dựa trên kỹ thuật cũ hoặc không còn phù hợp.

## 1. Cách hoạt động của putIfAbsent

Cú pháp:

~~~java
V previous = map.putIfAbsent(key, candidate);
~~~

Đây là **mẫu tổng quát**, giả sử `map` có kiểu `Map<K,V>` hỗ trợ cập nhật và các biến đã được khai báo.

`putIfAbsent` áp dụng quy tắc:

1. Nếu `map.get(key)` trả **giá trị khác null**, giữ nguyên mapping, trả giá trị ấy.
2. Nếu chưa có mapping, hoặc key đã có nhưng value bằng **`null`**, cố gắng gắn `candidate`, rồi trả **`null`**.
3. Nếu Map không cho phép cập nhật hoặc không chấp nhận kiểu/key/value đề xuất, thao tác có thể ném exception đúng theo hợp đồng implementation.

Nói cách khác: điều kiện là **chưa có giá trị khác null**, *không đơn thuần* là `!containsKey(key)`.

Ví dụ:

~~~java
Map<String, Integer> limits = new HashMap<>();
Integer first = limits.putIfAbsent("batch", 10);  // null
Integer second = limits.putIfAbsent("batch", 20); // 10
Integer effective = limits.get("batch");          // 10
~~~

Mảnh mã trên đặt trong một phương thức với import `java.util.*;`. Lần đầu ghi 10, lần thứ hai trả 10 và **không thay bằng 20**.

So với `put`:

~~~java
limits.put("batch", 30);         // Ghi đè giá trị thành 30.
limits.putIfAbsent("batch", 40); // Vẫn là 30.
~~~

Không dùng `putIfAbsent` nếu mục tiêu là cập nhật vô điều kiện. Ngược lại, không dùng `put` để ghi cấu hình mặc định khi người dùng có thể đã thiết lập giá trị riêng.

## 2. Bảng chân trị: key thiếu, null và value đã có

Với một Map **có thể sửa và cho phép null**, khi gọi `putIfAbsent("k", "new")`:

| Trạng thái trước | Giá trị trả về | Trạng thái sau |
|---|---|---|
| Chưa có key `"k"` | `null` | `"k" → "new"` |
| Đã có `"k" → null` | `null` | `"k" → "new"` |
| Đã có `"k" → "old"` | `"old"` | Vẫn là `"k" → "old"` |
| Đã có `"k" → "new"` | `"new"` | Giữ nguyên |

Hai hàng đầu tiên là khác biệt quan trọng: **`putIfAbsent` trả null không cho biết key trước đó thực sự vắng hay đã ánh xạ tới null**.

Ví dụ:

~~~java
Map<String, String> names = new HashMap<>();
names.put("nickname", null);

boolean hadKey = names.containsKey("nickname"); // true
String before = names.get("nickname");          // null
String old = names.putIfAbsent("nickname", "An"); // null
String now = names.get("nickname");             // "An"
~~~

Đây là mảnh Java có thể chạy trong một phương thức.

### 2.1. `containsKey` là điều kiện khác

`containsKey(key)` hỏi **có mapping cho key hay không**, dù value null. `get(key)` có thể trả null cả khi key thiếu **và** khi key có value null. `putIfAbsent` dựa vào trạng thái giá trị như mô tả ở trên.

Nếu nghiệp vụ đòi **chỉ thêm khi key thực sự chưa từng xuất hiện**, kể cả nếu giá trị hiện tại null, `putIfAbsent` không đáp ứng đầy đủ điều kiện ấy. Với Map đơn luồng có thể kiểm `containsKey` trước khi `put`, nhưng đây là **hai thao tác riêng**; trong ứng dụng concurrent, chúng không tạo bảo đảm atomic nếu không có cơ chế phối hợp thích hợp.

### 2.2. Có thể truyền null làm value không?

Phụ thuộc Map cụ thể:

- `HashMap` cho phép giá trị null và một key null. Truyền null cho `putIfAbsent` trên key mới có thể tạo mapping với null.
- `ConcurrentHashMap` **không cho phép key hoặc value null**, sẽ báo `NullPointerException` nếu truyền giá trị không được phép.
- Những Map không sửa được như kết quả từ `Map.of(...)` hoặc `Map.copyOf(...)` không thể dùng để thêm mapping. Chúng không hỗ trợ cập nhật trạng thái.

Bởi vậy không viết code chung với giả định “Map luôn chấp nhận null” hoặc “Map luôn có thể ghi”.

## 3. Giá trị trả về: phân biệt trước và sau

`putIfAbsent` trả **giá trị cũ khác null nếu có**, hoặc **null** nếu không có value cũ khác null. Không trả boolean.

Ví dụ xử lý giá trị hiệu lực trong trường hợp `candidate` khác null:

~~~java
String previous = map.putIfAbsent(key, candidate);
String effective = previous != null ? previous : candidate;
~~~

Đây là đoạn minh họa, giả sử biến đã tồn tại. `effective` nhận value cũ nếu Map đã chứa value khác null; ngược lại là candidate vừa được đưa vào Map theo cơ chế thông thường.

Nếu ứng dụng dùng `ConcurrentHashMap`, `putIfAbsent` có hợp đồng atomic với **từng lần gọi**. Nhưng sau khi lời gọi hoàn tất, thread khác vẫn có thể xóa hoặc thay value; không đồng nhất “giá trị hiệu lực lúc vừa gọi” với “giá trị được giữ vĩnh viễn”.

Đừng kiểm tra `map.get(key)` nhiều lần rồi suy ra một cuộc đua đã diễn ra thế nào. Trên Map concurrent, các lần đọc có thể nhìn thấy các trạng thái khác nhau theo thời gian. Giá trị trả về của thao tác atomic mới phản ánh điều kiện tại thời điểm thao tác ấy.

### 3.1. Pseudocode của Map mặc định

Theo hợp đồng `Map`, triển khai mặc định tương đương về ngữ nghĩa với:

~~~java
V existing = map.get(key);
if (existing == null) {
    existing = map.put(key, candidate);
}
return existing;
~~~

Đây là **pseudocode**, không phải Java độc lập vì `V`, `map`, `key` và `candidate` cần ngữ cảnh. Nó giải thích tại sao null-mapping được điền lại.

**Cực kỳ quan trọng:** phiên bản mặc định **không cam kết đồng bộ hoặc tính nguyên tử**. Không xem việc đổi hai dòng `get + put` thành một lời gọi `Map.putIfAbsent` là tự động giải quyết race khi Map implementation không hỗ trợ concurrent update.

## 4. putIfAbsent khác getOrDefault

Cả hai đều có khái niệm giá trị fallback nhưng mục đích khác nhau:

~~~java
Map<String, String> config = new HashMap<>();

String displayed = config.getOrDefault("theme", "light");
// "light"; key theme vẫn không tồn tại trong Map.

String old = config.putIfAbsent("theme", "light");
// null; key theme đã được thêm với value "light".
~~~

Đoạn trên chạy trong một phương thức.

- `getOrDefault`: **chỉ đọc**, trả default khi không có mapping cho key.
- `putIfAbsent`: **có thể ghi**, gắn giá trị nếu không có value cũ khác null.

Với một `HashMap` có `put("x", null)`, `getOrDefault("x", "fallback")` trả **null**, vì key `x` thực sự có mapping. Trong khi `putIfAbsent("x", "fallback")` sẽ thay mapping null bằng fallback.

Nếu chỉ cần hiển thị fallback mà không muốn dữ liệu thay đổi, dùng `getOrDefault`; nếu cần lưu fallback cho các lần gọi tiếp theo, dùng `putIfAbsent` khi phù hợp chính sách.

## 5. putIfAbsent và computeIfAbsent: sẵn giá trị hay tạo lười?

Đây là điểm thiết kế thường gặp khi làm cache.

### 5.1. Giá trị của putIfAbsent được đánh giá trước khi gọi

~~~java
map.putIfAbsent(key, loadProfileFromService(key));
~~~

Đây là mảnh mã phụ thuộc `map`, `key` và `loadProfileFromService`. Trong Java, **đối số được tính trước khi gọi phương thức**. Vì vậy `loadProfileFromService(key)` vẫn chạy ngay cả khi key đã có một value khác null và `putIfAbsent` sẽ bỏ qua đề xuất mới.

Hậu quả có thể là gọi API/DB thừa, tạo object đắt đỏ, cấp tài nguyên không cần thiết hoặc side effect không mong muốn.

Nếu value đã sẵn có hoặc rất rẻ như một hằng số, `putIfAbsent` lại rất dễ đọc:

~~~java
settings.putIfAbsent("language", "vi");
~~~

### 5.2. computeIfAbsent chỉ tính khi cần

~~~java
map.computeIfAbsent(key, k -> loadProfileFromService(k));
~~~

`computeIfAbsent` nhận **mapping function** thay vì một value đã được tính. Với key đang ánh xạ value khác null, nó trả value hiện tại và không cần gọi function. Khi key thiếu hoặc value đang null, nó tính value mới.

Các quy tắc cần nhớ:

- Function trả value khác null → gắn mapping và trả value đó.
- Function trả null → **không ghi mapping mới**. Nếu key đã có value null, đừng tự suy ra mapping null cũ bị xóa.
- Function ném exception không kiểm tra → lỗi được truyền lên, không dùng null để thay cho thông tin lỗi.
- Mapping function **không nên sửa chính Map đang được tính**. Đặc biệt với Map concurrent, tránh phụ thuộc vào recursion và các side effect khó kiểm soát.
- `computeIfAbsent` có thể được gọi lại trong tương lai nếu key bị xóa hoặc hàm tính không tạo ra value hợp lệ. Không xem nó là bộ nhớ cache có hiệu lực vĩnh viễn.

Ví dụ khởi tạo danh sách bằng `HashMap`:

~~~java
Map<String, List<String>> groups = new HashMap<>();
groups.computeIfAbsent("java", k -> new ArrayList<>())
      .add("streams");
groups.computeIfAbsent("java", k -> new ArrayList<>())
      .add("maps");
~~~

Đây là đoạn chạy được khi có `import java.util.*;`. Danh sách ở key `java` chứa hai giá trị. Nó phù hợp một luồng thao tác.

**Lưu ý concurrency:** thay `HashMap` thành `ConcurrentHashMap<String,List<String>>` và dùng `computeIfAbsent(...).add(...)` **không làm `ArrayList.add` an toàn đa luồng**. Việc khởi tạo mapping và việc sửa object lưu dưới key là **hai phạm vi atomic khác nhau**. Cần kiểu collection concurrent hoặc cơ chế đồng bộ/đại diện dữ liệu bất biến thích hợp.

## 6. Những thao tác “có điều kiện” liên quan

`putIfAbsent` dành cho trường hợp chỉ muốn thêm khi chưa có value khác null. Nếu muốn cập nhật theo điều kiện khác, chọn API đúng:

| Nhu cầu | API | Khác biệt |
|---|---|---|
| Không ghi đè value cũ khác null | `putIfAbsent(k, v)` | Trả value cũ hoặc null |
| Chỉ tính value khi chưa có value khác null | `computeIfAbsent(k, f)` | Factory lazy |
| Đọc fallback nhưng không thêm | `getOrDefault(k, fallback)` | Không thay Map |
| Ghi đè vô điều kiện | `put(k, v)` | Có thể thay value cũ |
| Chỉ cập nhật khi đã tồn tại mapping | `replace(k, newV)` | Không tạo mapping mới |
| Chỉ cập nhật khi value cũ khớp | `replace(k, oldV, newV)` | Trả boolean |
| Chỉ xóa khi value cũ khớp | `remove(k, expectedV)` | Trả boolean |
| Gắn value hoặc kết hợp với value cũ | `merge(k, v, f)` | Phù hợp đếm/tổng hợp |
| Tính lại với cả trạng thái hiện có và không có | `compute(k, f)` | Linh hoạt, phải xử lý null/exception |

Từng phương thức có thể là **optional operation** với Map không sửa được; độ an toàn concurrent và null phụ thuộc implementation.

### 6.1. replace có điều kiện theo value cũ

~~~java
Map<String, String> states = new HashMap<>();
states.put("order-1", "PENDING");

boolean wrong = states.replace(
        "order-1", "DONE", "PROCESSING"); // false
boolean right = states.replace(
        "order-1", "PENDING", "PROCESSING"); // true
~~~

Đây là mảnh code trong phương thức. Với lời gọi có ba đối số, Java chỉ thay value khi key hiện tại ánh xạ tới `oldValue` phù hợp. Đó là ý nghĩa khác `putIfAbsent`.

### 6.2. remove(k, expected) tránh xóa nhầm value đã đổi

~~~java
boolean notRemoved = states.remove(
        "order-1", "PENDING");    // false
boolean removed = states.remove(
        "order-1", "PROCESSING"); // true
~~~

Tiếp theo đoạn `states` ở mục trên. Khi value không còn bằng expected, không xóa. Với `ConcurrentHashMap`, các phép điều kiện này có bảo đảm atomic theo hợp đồng của lớp cho mỗi thao tác; Map mặc định không hứa atomic.

### 6.3. merge để đếm hoặc cộng dồn

~~~java
Map<String, Integer> counts = new HashMap<>();
counts.merge("login", 1, Integer::sum);
counts.merge("login", 1, Integer::sum);

System.out.println(counts.get("login")); // 2
~~~

Nếu key chưa có value khác null, `merge` gắn value đề xuất. Nếu đã có value khác null, function kết hợp value cũ và value mới. Nếu function trả null, mapping bị xóa. Lời gọi `merge` yêu cầu value đề xuất khác null.

Dùng `putIfAbsent("login", 1)` hai lần **không** tạo bộ đếm 2: nó chỉ thêm lần đầu. Nếu mỗi sự kiện phải tăng count, `merge` có ngữ nghĩa đúng hơn. Với counter lớn, phải lưu ý tràn `Integer::sum`.

## 7. Atomicity và thread-safety: chọn đúng Map

### 7.1. Map.putIfAbsent mặc định không bảo đảm atomic

Nếu hai thread chia sẻ một `HashMap` mutable và đồng thời sửa cùng một key, việc đọc/ghi không đồng bộ **không an toàn**. Hai thread có thể đều quan sát không có key rồi cùng tìm cách ghi; thậm chí thao tác trên HashMap với sửa đổi đồng thời có thể vi phạm những giả định khác của ứng dụng.

Phản ví dụ trong xử lý song song:

~~~java
if (!sharedMap.containsKey(jobId)) {
    sharedMap.put(jobId, workerId);
}
~~~

Đây là đoạn minh họa một **race check-then-act**. Giữa lúc `containsKey` và `put`, thread khác có thể thay đổi Map. Chuyển thành `sharedMap.putIfAbsent(jobId, workerId)` trên một implementation không có cam kết atomic cũng không tự bảo đảm chỉ một thread thắng.

### 7.2. ConcurrentHashMap.putIfAbsent là atomic

`ConcurrentHashMap` được thiết kế để cập nhật concurrent. Lời gọi:

~~~java
ConcurrentHashMap<String, String> reservations =
        new ConcurrentHashMap<>();

String previous = reservations.putIfAbsent(
        "task-123", "worker-A");

if (previous == null) {
    // Key chưa có; value của worker-A được đăng ký.
} else {
    // Key đã được một chủ khác gắn trước đó.
}
~~~

Đây là mảnh code cần `java.util.concurrent.ConcurrentHashMap`. Vì `ConcurrentHashMap` không cho phép value null, kết quả `previous == null` ở thao tác này không bị mơ hồ bởi một mapping null cũ.

**Nhưng atomicity của một lời gọi không phải transaction của cả workflow.** Một thread khác có thể xóa key sau khi lời gọi hoàn tất. Ghi dữ liệu vào database, gửi thông báo hoặc thực hiện nghiệp vụ bên ngoài ConcurrentHashMap không tự nhiên trở thành atomic với việc đặt key.

Với ứng dụng phân tán, hai process có thể có hai `ConcurrentHashMap` khác nhau: cơ chế chống trùng xuyên process cần lưu trữ dùng chung, unique constraint, lease, idempotency key hoặc transaction phù hợp.

### 7.3. ConcurrentHashMap.computeIfAbsent

`ConcurrentHashMap.computeIfAbsent` cung cấp cơ chế tính và gắn mapping khi chưa có key với tính nguyên tử theo hợp đồng của lớp. Hàm tính nên **ngắn và đơn giản**, không cập nhật đệ quy chính Map. Một số cập nhật của thread khác có thể bị chặn trong thời gian tính.

Đừng gọi dịch vụ mạng rất chậm bên trong mapping function mà không cân nhắc thời gian chặn, retry và side effect. Việc xây dựng cache lâu dài cần thêm quy tắc timeout, dọn dữ liệu, quản lý lỗi và khả năng hủy/thay giá trị.

### 7.4. Bảng so sánh một số Map hiện hành

| Map | Khóa/giá trị null | Cập nhật đa luồng |
|---|---|---|
| `HashMap` | Cho phép một null key và các null value | Không an toàn khi sửa đồng thời không đồng bộ |
| `LinkedHashMap` | Cho phép null theo cơ chế tương tự HashMap | Không an toàn khi sửa đồng thời không đồng bộ |
| `ConcurrentHashMap` | Cấm null key và null value | Có hợp đồng atomic cho `putIfAbsent` và cập nhật điều kiện |
| `Map.of(...)` / `Map.copyOf(...)` | Không chấp nhận null trong Map được tạo | Không sửa được; thao tác thêm không được hỗ trợ |

Với `TreeMap` hoặc Map chuyên biệt/tùy biến, khả năng chấp nhận null và chi tiết concurrency phải xem tài liệu implementation, không suy diễn từ tên interface.

## 8. Chương trình Java hoàn chỉnh, có stdout

Tạo file **`MapConditionalInsertDemo.java`**. Ví dụ dùng `LinkedHashMap` để có thể minh họa key ánh xạ null và thứ tự kết quả ổn định; dùng `ConcurrentHashMap` cho tình huống thêm atomic. Chương trình chạy trên **JDK 17+**, và các API được minh họa vẫn được hỗ trợ.

~~~java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class MapConditionalInsertDemo {
    static String make(AtomicInteger calls, String result) {
        calls.incrementAndGet();
        return result;
    }

    public static void main(String[] args) {
        Map<String, String> config = new LinkedHashMap<>();

        System.out.println("First put: "
                + config.putIfAbsent("mode", "safe"));
        System.out.println("Second put: "
                + config.putIfAbsent("mode", "fast"));
        System.out.println("Mode: " + config.get("mode"));

        config.put("locale", null);
        System.out.println("Null mapping exists: "
                + config.containsKey("locale"));
        System.out.println("Fill null mapping: "
                + config.putIfAbsent("locale", "vi-VN"));
        System.out.println("Locale: " + config.get("locale"));

        AtomicInteger calls = new AtomicInteger();
        config.putIfAbsent("mode", make(calls, "eager"));
        config.computeIfAbsent("mode",
                k -> make(calls, "lazy"));
        System.out.println("Factories with existing key: "
                + calls.get());

        String token = config.computeIfAbsent("token",
                k -> make(calls, "generated"));
        System.out.println("Computed token: " + token);
        System.out.println("Factory calls total: " + calls.get());

        config.computeIfAbsent("nothing", k -> null);
        System.out.println("Null result stored: "
                + config.containsKey("nothing"));
        System.out.println("getOrDefault: "
                + config.getOrDefault("missing", "fallback"));
        System.out.println("getOrDefault inserted: "
                + config.containsKey("missing"));

        System.out.println("Replace wrong value: "
                + config.replace("mode", "wrong", "fast"));
        System.out.println("Replace matching value: "
                + config.replace("mode", "safe", "fast"));
        System.out.println("Remove wrong value: "
                + config.remove("mode", "wrong"));
        System.out.println("Remove matching value: "
                + config.remove("mode", "fast"));

        Map<String, List<String>> groups = new HashMap<>();
        groups.computeIfAbsent("java",
                k -> new ArrayList<>()).add("A");
        groups.computeIfAbsent("java",
                k -> new ArrayList<>()).add("B");
        System.out.println("Grouped: " + groups.get("java"));

        ConcurrentHashMap<String, Integer> cache =
                new ConcurrentHashMap<>();
        System.out.println("Concurrent first: "
                + cache.putIfAbsent("sku", 10));
        System.out.println("Concurrent second: "
                + cache.putIfAbsent("sku", 20));
        System.out.println("Concurrent value: "
                + cache.get("sku"));
        cache.merge("sku", 2, Integer::sum);
        System.out.println("Merged value: " + cache.get("sku"));

        try {
            cache.putIfAbsent("bad", null);
        } catch (NullPointerException e) {
            System.out.println("Concurrent null rejected");
        }
    }
}
~~~

**Đọc kết quả:**

- `Null mapping exists: true` nhưng `Fill null mapping: null`: key có tồn tại vẫn được điền lại vì value trước đó là null.
- `Factories with existing key: 1`: lời gọi `putIfAbsent` đã chạy phương thức tạo value dù key đã tồn tại; lời gọi `computeIfAbsent` cho cùng key không tính value mới.
- `Computed token: generated` và `Factory calls total: 2`: một value thực sự mới được tính khi key còn thiếu.
- `Null result stored: false`: mapping function của `computeIfAbsent` trả null cho key chưa có, nên không thêm mapping mới.
- `getOrDefault inserted: false`: fallback chỉ là giá trị đọc.

## 9. Trường hợp sử dụng thực tế và cách chọn API

### 9.1. Điền mặc định vào cấu hình có thể ghi

~~~java
settings.putIfAbsent("language", "vi");
settings.putIfAbsent("theme", "light");
~~~

Các biến ở ví dụ là Map có thể ghi. Cấu hình do người dùng đã nhập sẽ không bị mặc định ghi đè khi value khác null.

### 9.2. Lazy initialization hoặc memoization

~~~java
profiles.computeIfAbsent(id, key -> loadProfile(key));
~~~

Phù hợp khi chỉ tải profile khi chưa có value. Cần định nghĩa khi hàm tải trả null: `computeIfAbsent` không lưu mapping mới, lần yêu cầu sau có thể tải lại. Nếu cần cache cả “không tìm thấy”, hãy lưu trạng thái rõ ràng (ví dụ wrapper có các nhánh) thay vì giả định null được cache như một value.

### 9.3. Khởi tạo cấu trúc lưu nhiều phần tử

~~~java
Map<String, List<String>> byTag = new HashMap<>();
byTag.computeIfAbsent("java", k -> new ArrayList<>()).add("A");
byTag.computeIfAbsent("java", k -> new ArrayList<>()).add("B");
~~~

Đoạn này phù hợp một luồng. Trên Map concurrent, việc thêm vào **List bên trong** vẫn cần chiến lược thread-safety riêng.

### 9.4. Chỉ nhận một job trong một JVM

~~~java
String existingOwner = jobOwners.putIfAbsent(
        jobId, workerId);
if (existingOwner != null) {
    // Job đã có chủ nhận trước đó.
}
~~~

Giả định `jobOwners` là `ConcurrentHashMap` và `jobId`/`workerId` khác null. Phù hợp cho một bước đăng ký atomic **trong Map đang dùng chung**. Nếu job cần sống qua restart hoặc giao cho nhiều máy, phải thiết kế cơ chế lưu trạng thái bền vững riêng.

### 9.5. Bộ đếm theo key

~~~java
counts.merge(errorCode, 1, Integer::sum);
~~~

Không dùng `putIfAbsent(errorCode, 1)` để đếm nhiều lần vì nó chỉ gắn lần đầu. `merge` tích lũy theo quy tắc; phải cân nhắc tràn kiểu số nếu khối lượng quá lớn.

## 10. Kiểm thử và các trường hợp biên

Một bộ kiểm thử tốt nên bao gồm cả **giá trị trả về** và **trạng thái Map sau khi gọi**:

| Dữ liệu hoặc thao tác | Kỳ vọng |
|---|---|
| Key chưa tồn tại | `putIfAbsent` trả null và ghi value |
| Key đã có value khác null | Trả value cũ, không ghi đè |
| Key đã có value null trên HashMap | Trả null và điền value mới |
| Key null trên ConcurrentHashMap | Bị từ chối bằng `NullPointerException` |
| Value null trên ConcurrentHashMap | Bị từ chối bằng `NullPointerException` |
| Giá trị tính đắt khi key đã có | `putIfAbsent` vẫn đánh giá đối số; `computeIfAbsent` không cần gọi function |
| Hàm computeIfAbsent trả null khi key chưa có | Không tạo mapping |
| getOrDefault với key chưa có | Trả fallback, Map không thay đổi |
| replace(k, expected, newV) không khớp | Trả false, giữ nguyên mapping |
| remove(k, expected) khớp | Trả true, xóa mapping |
| Hai thread cùng dùng CHM.putIfAbsent một key | Chỉ một value được gắn trong khoảng không có xóa/thay khác |
| Map không sửa được | Thao tác thêm/thay được từ chối |
| Tính toán trên value mutable của Map concurrent | Phải kiểm thread-safety của chính value |

Với test đa luồng, có thể dùng `CountDownLatch` để các thread bắt đầu gần cùng lúc, rồi kiểm **bất biến**: các lời gọi không ghi đè value sau lần gắn đầu nếu key không bị xóa/thay. Không dựa vào `Thread.sleep(...)` để quyết định thread nào chắc chắn thắng.

## 11. Những sai lầm phổ biến

**1. Nhầm “absent” với “không có key”.** `putIfAbsent` cũng thay value null có sẵn. Muốn phân biệt cần xét `containsKey` và chính sách null.

**2. Diễn giải `return null` là “key chưa từng tồn tại”.** Với Map cho phép null, trước đó có thể đã có mapping null.

**3. Gọi `putIfAbsent(k, expensive())` để tránh tính toán thừa.** Biểu thức `expensive()` vẫn được đánh giá; `computeIfAbsent` mới là lựa chọn thông thường khi cần tính lười.

**4. Nghĩ `getOrDefault` có tác dụng ghi.** Nó chỉ đọc giá trị thay thế, không đưa fallback vào Map.

**5. Dùng `HashMap.putIfAbsent` như thao tác atomic.** `Map` mặc định không cam kết atomic, và HashMap không an toàn cho các cập nhật không đồng bộ đa luồng.

**6. Cho rằng `ConcurrentHashMap` hỗ trợ null.** Nó không cho phép key/value null; kiểm dữ liệu trước khi lưu.

**7. Dùng putIfAbsent để tăng counter.** Nó giữ giá trị cũ, không cộng dồn; dùng `merge` hoặc `compute` theo nghĩa nghiệp vụ.

**8. Cho rằng atomic insert làm mọi bước sau đó atomic.** Các thao tác khác trên database, danh sách trong value hay hệ thống phân tán vẫn cần cơ chế riêng.

**9. Ghi vào `Map.of`.** Map được factory tạo ra không sửa được; nếu cần chèn phải chọn cấu trúc dữ liệu mutable ngay từ thiết kế.

**10. Cho rằng `computeIfAbsent` luôn chỉ chạy một lần trong vòng đời hệ thống.** Key có thể bị xóa, mapping function có thể trả null, hoặc cache được tái khởi tạo; không dựa vào side effect để suy ra “exactly once” nghiệp vụ.

## 12. Bài tập tự luyện

1. Với Map trống, gọi `putIfAbsent("a", 1)` rồi `putIfAbsent("a", 2)`. Hai lần trả về gì, value cuối là bao nhiêu?
2. Trên `HashMap<String,String>` có `put("k", null)`, tại sao `putIfAbsent("k", "v")` vẫn ghi? `containsKey("k")` trước lời gọi là true hay false?
3. Vì sao `putIfAbsent(k, load())` có thể gây truy vấn thừa, còn `computeIfAbsent(k, key -> load())` có thể tránh?
4. Khi cần tăng số lần một sự kiện, nên chọn `merge` hay `putIfAbsent`? Vì sao?
5. Nếu hai worker trong hai process dùng hai `ConcurrentHashMap` riêng, có thể ngăn xử lý trùng xuyên hai process không?
6. Cần làm gì nếu giá trị dưới key là `ArrayList` nhưng nhiều thread cùng thêm phần tử?

**Gợi ý đáp án:** (1) Null rồi 1; value cuối 1. (2) Vì value cũ null được coi là thiếu value; `containsKey` trước đó true. (3) Lập luận theo thời điểm đánh giá tham số so với mapping function lazy. (4) `merge` vì phải cập nhật giá trị đã có. (5) Không; cần trạng thái dùng chung bền vững/idempotency. (6) Sử dụng collection thread-safe hoặc cơ chế đồng bộ thích hợp, không chỉ dựa vào ConcurrentHashMap.

## Ghi nhớ

`Map.putIfAbsent` **chỉ điền khi key chưa có value khác null**; nó không phải `containsKey + put` atomic trên mọi Map. Giá trị trả về là **value cũ** hoặc **null**, và null có thể đến từ mapping đã tồn tại nhưng value null. Với factory đắt, cân nhắc `computeIfAbsent`; với đếm/tích lũy, dùng `merge`; với thay/xóa theo expected value, dùng `replace`/`remove` có điều kiện. Khi nhiều thread thao tác, cần chọn Map có **hợp đồng concurrent rõ ràng** như `ConcurrentHashMap`; vẫn phải phân biệt atomic của thao tác trong Map với toàn bộ workflow nghiệp vụ.
