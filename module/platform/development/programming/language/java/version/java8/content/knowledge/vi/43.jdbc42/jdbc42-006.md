# JDBC 4.2 — Đọc kiểu đích và kiểm tra khả năng của driver

## 1. Vấn đề: kiểu SQL, kiểu Java và năng lực driver không phải một

Khi làm việc với JDBC, ứng dụng thường cần một đối tượng Java có nghĩa nghiệp vụ rõ ràng: ngày khai sinh là `LocalDate`; mốc ngày-giờ không kèm múi giờ là `LocalDateTime`; mốc có UTC offset là `OffsetDateTime`; số tiền là `BigDecimal`. Tuy nhiên dữ liệu nằm trong cột SQL, còn việc chuyển đổi sang kiểu Java được **JDBC driver** thực hiện.

Xem hai lời gọi:

```java
Object raw = resultSet.getObject("signup_day");

LocalDate day =
        resultSet.getObject("signup_day", LocalDate.class);
```

- Với `getObject(column)`, driver trả Java object **theo mapping mặc định** của SQL type.
- Với `getObject(column, Class<T>)`, caller yêu cầu **Java target type cụ thể**; driver phải thực hiện chuyển đổi nếu nó hỗ trợ.
- **Không phải phép ép kiểu Java đơn thuần**: driver có thể chuyển SQL DATE thành `LocalDate` dù untyped getter thông thường trả `java.sql.Date`.
- Không phải driver nào cũng thực thi mọi tổ hợp SQL type → Java target, dù phương thức đã tồn tại trong interface.

**Mốc phiên bản cần ghi đúng:** `ResultSet.getObject(int,Class<T>)` và `ResultSet.getObject(String,Class<T>)` đã có từ **Java 7/JDBC 4.1** (Javadoc ghi `Since 1.7`). **JDBC 4.2**, đi cùng Java 8, mở rộng mapping với các lớp `java.time` và có các JDBC types, `SQLType`/`JDBCType` tương ứng. Những kiến thức này vẫn đang được dùng trong JDK hiện đại.

Đây là bài Knowledge thuộc chủ đề cha **JDBC 4.2**, đề mục trực tiếp **Đọc kiểu đích và kiểm tra khả năng của driver**. Nội dung tập trung vào hợp đồng typed getter, metadata, thẩm định khả năng thật của driver, SQL NULL, fallback an toàn và Java time mapping. Không dựa vào API đã lỗi thời hoặc lời hứa không được Javadoc đảm bảo.

### Mục tiêu học tập

1. Phân biệt SQL type, default Java class và requested Java target class.
2. Biết overload typed `getObject`, indexes 1-based, labels/aliases và checked exceptions.
3. Nhận diện năm mapping `java.time` thường gặp từ JDBC 4.2.
4. Hiểu vì sao `DatabaseMetaData.supportsConvert` không phải công cụ kiểm tra typed getter.
5. Hiểu `ResultSetMetaData.getColumnClassName` nói về **untyped getObject**, không liệt kê tất cả target classes.
6. Biết dùng driver/DB metadata để ghi nhận môi trường, không biến version thành guarantee.
7. Thực hiện capability probe trên **driver và database thật**, với giá trị không NULL và đúng SQL type.
8. Phân biệt `SQLFeatureNotSupportedException` với các `SQLException` do lỗi dữ liệu, SQL hoặc kết nối.
9. Tổ chức fallback `getDate().toLocalDate()`, `getTime().toLocalTime()` và `getTimestamp().toLocalDateTime()` đúng nghĩa.
10. Biết giới hạn khi map timezone, precision/scale và nullable primitive values.
11. Chạy ví dụ Java 17+ có sẵn trong JDK, không cần DB/driver ngoài, để kiểm thử conversion logic.
12. Xây checklist tương thích đa driver và tránh bị mất dữ liệu âm thầm.

## 2. Ba khái niệm cần tách bạch

Một phép đọc JDBC liên quan tới ba tầng:

```text
SQL schema / query expression
          |
          v
SQL/JDBC type: DATE / TIMESTAMP / NUMERIC / ...
          |
          v
JDBC driver: mapping và conversion implementation
          |
          +--> getObject(column): Java default object
          |
          +--> getObject(column, T.class): target Java T (nếu hỗ trợ)
```

**SQL type** là loại dữ liệu mà query thực sự trả. Nó có thể khác type của table gốc nếu SQL có CAST, function, join, union, view hoặc expression.

**Default Java class** là class do driver tạo khi `ResultSet.getObject(column)` không truyền Class. Với SQL DATE, nó thường là `java.sql.Date`; với TIMESTAMP thường là `java.sql.Timestamp`, nhưng driver có thể có mapping hoặc extension riêng.

**Requested Java target** là điều `Class<T>` yêu cầu. Bạn có thể muốn `LocalDate` hoặc `LocalDateTime` vì domain không muốn làm việc trực tiếp với java.sql time wrappers.

Một cột có default class `java.sql.Date` **không chứng minh** typed `getObject(...,LocalDate.class)` không hoạt động. Ngược lại, nếu driver hỗ trợ `LocalDate`, không được suy ra nó cũng hỗ trợ `Instant`/`ZonedDateTime` hoặc arbitrary application classes.

### 2.1. Đừng cast thay cho conversion

```java
LocalDate good =
        rs.getObject("day", LocalDate.class);

LocalDate risky =
        (LocalDate) rs.getObject("day");
```

Dòng thứ hai chỉ cast object đã nhận từ driver. Nếu untyped `getObject` trả `java.sql.Date`, cast sang `LocalDate` sẽ ném `ClassCastException`. Dòng thứ nhất yêu cầu driver thực sự chuyển đổi SQL→Java target.

Khi typed getter thiếu, một phương án có kiểm soát là:

```java
java.sql.Date raw = rs.getDate("day");
LocalDate value =
        raw == null ? null : raw.toLocalDate();
```

Không thay bằng `LocalDate.parse(rs.getString(...))` tùy tiện: định dạng string có thể phụ thuộc type/dialect/session. Parse chuỗi chỉ hợp lý khi schema thật sự định nghĩa một format text ổn định.

## 3. ResultSet.getObject(column, Class<T>) có hợp đồng gì?

Hai overload được dùng:

```java
<T> T getObject(int columnIndex, Class<T> type)
        throws SQLException;

<T> T getObject(String columnLabel, Class<T> type)
        throws SQLException;
```

Ý nghĩa:

- `columnIndex` bắt đầu từ **1**; index 0 không hợp lệ.
- `columnLabel` là nhãn cột của query, có thể được xác định bằng `AS`.
- Nếu query có nhiều cột trùng label, JDBC có thể chọn cột khớp đầu tiên; nên đặt aliases duy nhất.
- `type` không được là null; không phải `Class<T>` nào cũng được hỗ trợ.
- Nếu conversion không hỗ trợ hoặc type không hợp lệ, method có thể ném `SQLException`.
- Nếu driver **không hỗ trợ chính phương thức này**, `SQLFeatureNotSupportedException` là subtype báo unsupported.
- SQL NULL thông thường được thể hiện bằng Java null khi đọc qua getter trả object.
- Driver có thể ném SQLException vì lỗi SQL/cột, result set đã đóng, dữ liệu không đổi được, mất kết nối, timeout, lỗi hạ tầng; không mặc định đó là unsupported feature.

### 3.1. Đọc qua label, nên chọn alias

```sql
SELECT signup_day AS date_value,
       created_at AS created_value
FROM example_events
WHERE event_id = ?
```

```java
LocalDate date =
        rs.getObject("date_value", LocalDate.class);

LocalDateTime timestamp =
        rs.getObject("created_value", LocalDateTime.class);
```

Đây là **snippets cho một bảng minh họa**; không phải query có thể chạy ngay nếu dự án chưa có bảng/cột như vậy. Trong ứng dụng thật, đảm bảo `signup_day` là SQL DATE, `created_at` là TIMESTAMP không có timezone và driver đã được kiểm chứng.

### 3.2. Đọc qua index bắt đầu từ 1

```java
try (ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {
        LocalDate day = rs.getObject(1, LocalDate.class);
    }
}
```

`ps` là PreparedStatement đã cấu hình, query phải có cột đầu thuộc SQL type phù hợp. Vì ResultSet cursor ban đầu nằm **trước dòng đầu**, phải gọi `next()` trước getter.

### 3.3. Getter target object và getter primitive

```java
Integer count = rs.getObject("count_value", Integer.class);
int raw = rs.getInt("count_value");
boolean missing = rs.wasNull();
```

`Integer.class` là wrapper thể hiện SQL NULL bằng Java null khi conversion được hỗ trợ. `getInt` trả 0 nếu SQL NULL; chỉ `wasNull` ngay sau nó mới phân biệt được **NULL** với **số 0 thực**. `wasNull` nói về **getter gần nhất**, nên không đọc cột khác trước khi kiểm tra.

Không giả định `getObject(col, int.class)` tương đương `getObject(col,Integer.class)` trên mọi driver; dùng wrapper class cho nullable data.

## 4. Bảng ánh xạ java.time của JDBC 4.2

| SQL/JDBC type | Java target chính trong chuẩn JDBC 4.2 | Ý nghĩa |
| --- | --- | --- |
| `DATE` | `LocalDate` | Ngày lịch, không có giờ |
| `TIME` | `LocalTime` | Giờ trong ngày, không có offset |
| `TIMESTAMP` | `LocalDateTime` | Ngày và giờ cục bộ, không có offset |
| `TIME_WITH_TIMEZONE` | `OffsetTime` | Giờ trong ngày cộng UTC offset |
| `TIMESTAMP_WITH_TIMEZONE` | `OffsetDateTime` | Ngày và giờ cộng UTC offset |

Những lớp này có từ Java 8, phần mapping được JDBC 4.2 chuẩn hóa. Tuy nhiên khả năng dùng trực tiếp còn tùy SQL type **thật sự tồn tại** trong DB và implementation/version của driver.

### 4.1. Không đồng nhất tất cả các kiểu thời gian

- `LocalDate`: `2025-04-09`, không mang giờ và time zone.
- `LocalTime`: `13:14:15`, không biết ngày.
- `LocalDateTime`: `2025-04-09T13:14:15`, không có UTC offset; **chưa phải Instant**.
- `OffsetTime`: `13:14:15+07:00`, có offset nhưng không biết ngày.
- `OffsetDateTime`: `2025-04-09T13:14:15+07:00`, có offset, có thể chuyển sang `Instant`.

`OffsetDateTime` không giữ nguyên **ZoneId theo tên vùng** (chẳng hạn `Asia/Ho_Chi_Minh`). Nó chỉ giữ numeric offset. CSDL/driver có thể còn chuẩn hóa offset về UTC; vì vậy nếu domain cần cả original zone ID thì phải lưu thêm hoặc có schema phù hợp.

### 4.2. Instant và ZonedDateTime không phải năm mapping cơ bản

`Instant` và `ZonedDateTime` không nằm trong năm target `java.time` được JDBC 4.2 chuẩn hóa như bảng trên. Một số driver/framework hỗ trợ thêm, nhưng không được suy luận chỉ vì JDBC major=4:

```java
// Không đảm bảo khả chuyển trên mọi driver:
Instant instant = rs.getObject("created_at", Instant.class);
ZonedDateTime zoneValue =
        rs.getObject("created_at", ZonedDateTime.class);
```

Nếu SQL type thực sự có offset và driver trả `OffsetDateTime` đúng nghĩa:

```java
OffsetDateTime dateTime =
        rs.getObject("occurred_at", OffsetDateTime.class);

Instant instant =
        dateTime == null ? null : dateTime.toInstant();
```

Đây là conversion trên Java side và cần dữ liệu offset thật. Không dùng cho SQL TIMESTAMP không timezone rồi tự đoán UTC/ZoneId.

### 4.3. JDBC 4.2 không tự đảm bảo DB có TIME_WITH_TIMEZONE

Driver có thể hỗ trợ API nhưng backend không có SQL type tương ứng hoặc dùng kiểu vendor-specific. Phải xem schema và metadata của result set; không chỉ dựa vào tên cột, SQL dialect hoặc thông báo “JDBC 4.2 compliant”.

## 5. ResultSetMetaData: kiểm tra kiểu SQL thật của query

`ResultSetMetaData` mô tả các **cột trong ResultSet của query đang chạy**:

```java
ResultSetMetaData meta = rs.getMetaData();

int count = meta.getColumnCount();
int sqlCode = meta.getColumnType(1);
String sqlName = meta.getColumnTypeName(1);
String label = meta.getColumnLabel(1);
String defaultClass = meta.getColumnClassName(1);
```

Cụ thể:

| API | Trả về | Cách diễn giải |
| --- | --- | --- |
| `getColumnCount()` | int | Số cột của ResultSet |
| `getColumnLabel(index)` | String | Label/alias đầu ra của query |
| `getColumnType(index)` | int | Mã SQL type theo `java.sql.Types` hoặc mã driver |
| `getColumnTypeName(index)` | String | Tên SQL type theo DB/vendor |
| `getColumnClassName(index)` | String | Java class của **untyped getObject** theo driver |
| `getPrecision(index)` | int | Precision/column size được metadata báo |
| `getScale(index)` | int | Scale với dữ liệu decimal/time khi có nghĩa |
| `isNullable(index)` | int | Trạng thái cho phép NULL/không rõ, không phải kiểm tra giá trị row hiện tại |

### 5.1. getColumnClassName không có nghĩa “supports target”

Đây là một bẫy phổ biến. Ví dụ `getColumnClassName(2)` báo:

```text
java.sql.Date
```

Nó không nói `rs.getObject(2, LocalDate.class)` chắc chắn fail. Nó chỉ mô tả class mà untyped `rs.getObject(2)` dự kiến tạo. Typed overload **có thể convert** sang một class khác nếu driver hỗ trợ.

Tương tự, `getColumnClassName` báo LocalDate cũng không chứng minh driver hỗ trợ các kiểu đích bất kỳ như `OffsetDateTime`, `ZonedDateTime` hoặc `MyDomainEvent`.

### 5.2. Metadata của expression có thể khác type cột gốc

Một query dùng `CAST` hoặc function có thể biến SQL DATE thành VARCHAR hoặc một type khác. Vì vậy code đọc phải dựa vào **SQL output type** thật, không suy luận chỉ từ schema table trong một query phức tạp.

Ví dụ:

```sql
SELECT CAST(signup_day AS VARCHAR(30)) AS displayed_day
FROM example_events
```

Tùy DB hỗ trợ cú pháp cast đó, result set column `displayed_day` là text output; muốn đọc `LocalDate` từ text cần một format conversion cụ thể, không thể dùng hợp đồng SQL DATE→LocalDate một cách máy móc.

### 5.3. In metadata chẩn đoán có kiểm soát

```java
ResultSetMetaData meta = rs.getMetaData();
for (int i = 1; i <= meta.getColumnCount(); i++) {
    System.out.println(
            meta.getColumnLabel(i) + " | "
            + meta.getColumnType(i) + " | "
            + meta.getColumnTypeName(i) + " | "
            + meta.getColumnClassName(i));
}
```

Đây là snippet với `ResultSet rs` hợp lệ và đang mở. Nó giúp debug mismatch giữa môi trường test và production; đừng log dữ liệu row/credentials nhạy cảm.

## 6. DatabaseMetaData: ghi lại tổ hợp driver và DBMS

`DatabaseMetaData` cung cấp thông tin về khả năng của **driver kết hợp với DBMS mà nó kết nối**.

```java
DatabaseMetaData db = connection.getMetaData();

String driverName = db.getDriverName();
String driverVersion = db.getDriverVersion();
int jdbcMajor = db.getJDBCMajorVersion();
int jdbcMinor = db.getJDBCMinorVersion();

String product = db.getDatabaseProductName();
String productVersion = db.getDatabaseProductVersion();
```

Những thông tin này nên được ghi nhận khi hỗ trợ nhiều datasource hoặc điều tra sự khác biệt kết quả giữa CI, staging và production.

**Nhưng version không phải chứng cứ mọi phép chuyển kiểu đích đều hỗ trợ.** Một driver báo JDBC 4.2 vẫn có thể có hạn chế với một SQL type, server version hoặc cách mapping thời gian có timezone.

### 6.1. Không dùng một boolean theo JDBC major để quyết định hỗ trợ

```java
// Sai về logic: JDBC version không đảm bảo riêng phép chuyển này.
boolean supportsLocalDate =
        db.getJDBCMajorVersion() >= 4;
```

Nếu muốn phân loại mức JDBC version tối thiểu 4.2, so sánh cặp (major,minor) đúng thứ tự, nhưng vẫn cần probe **cặp SQL type → Java target** thực tế.

### 6.2. DatabaseMetaData.getTypeInfo

`getTypeInfo()` trả một ResultSet liệt kê các SQL types mà DB/driver mô tả. Dùng để biết DB có DATE, TIMESTAMP_WITH_TIMEZONE hay vendor type nào.

```java
try (ResultSet types = db.getTypeInfo()) {
    while (types.next()) {
        String typeName = types.getString("TYPE_NAME");
        int code = types.getInt("DATA_TYPE");
        // Thu thập metadata, nếu cần.
    }
}
```

**Không suy luận** có type trong `getTypeInfo` tức `getObject(col, LocalDate.class)` sẽ hoạt động. Nó mô tả **SQL type support**, không phải typed Java extraction.

## 7. supportsConvert không phải capability của getObject(Class)

`DatabaseMetaData` cung cấp:

```java
boolean supportsConvert();
boolean supportsConvert(int fromType, int toType);
```

Theo Javadoc, chúng hỏi DB/driver có hỗ trợ **JDBC scalar function CONVERT** để chuyển **một JDBC SQL type sang JDBC SQL type khác** không.

```java
boolean dateToVarcharInSql =
        db.supportsConvert(Types.DATE, Types.VARCHAR);
```

Nó trả lời về **SQL DATE → SQL VARCHAR trong SQL expression**. Nó **không trả lời** liệu Java có thể gọi:

```java
LocalDate value =
        rs.getObject("signup_day", LocalDate.class);
```

và nhận LocalDate.

| Tình huống | Cơ chế | Kiểm tra |
| --- | --- | --- |
| SQL DATE → SQL VARCHAR | Scalar SQL CONVERT | `db.supportsConvert(Types.DATE, Types.VARCHAR)` |
| SQL DATE → `LocalDate` | JDBC ResultSet Java target conversion | `rs.getObject(label, LocalDate.class)` trên cột DATE thật |
| `LocalDate` → SQL DATE | JDBC parameter binding | `PreparedStatement.setObject(...)` và conversion support |
| `java.sql.Date` → `LocalDate` | Java-side conversion | `sqlDate.toLocalDate()` |

**Không dùng supportsConvert như supportsGetObjectTarget**, vì hai câu hỏi độc lập. JDBC không có một phương thức metadata công khai tổng quát kiểu `supportsGetObject(Types.DATE,LocalDate.class)`.

### 7.1. Không nhầm với getColumnClassName

`ResultSetMetaData.getColumnClassName` cũng không phải danh sách target classes được typed getter chấp nhận. Muốn biết, cần kiểm tra mapping standard và test thật trên implementation.

### 7.2. Không nhầm với SQLType/JDBCType

`java.sql.JDBCType` là enum chuẩn SQL types, có từ Java 8; `SQLType` là interface. Chúng cung cấp **cách biểu diễn SQL type**, không phải bằng chứng Java target extraction được mọi driver triển khai.

```java
System.out.println(JDBCType.valueOf(Types.DATE));
// DATE.
```

Nếu mã vendor-specific không có trong enum, `JDBCType.valueOf(int)` có thể ném `IllegalArgumentException`. Khi làm tool chẩn đoán, dự phòng code thô và `getColumnTypeName` thay vì crash.

## 8. Kiểm tra khả năng driver một cách đáng tin

Một capability probe đúng nên có các bước:

1. Xác định **SQL type thực** của cột/expression trong query.
2. Xác định **Java target class** và nhu cầu về precision, timezone, nullability.
3. Ghi **driver version, database version và connection settings**.
4. Dùng một **fixture non-null** với giá trị kiểm soát, trên database/driver thực sự.
5. Gọi `getObject(column, Target.class)` và so sánh **class/semantics/value** với expected.
6. Thử SQL NULL riêng.
7. Với time/decimal, thử boundary, fractional seconds, timezone và scale liên quan.
8. Ghi rõ kết quả theo **cặp SQL type → target Java**, không gộp mọi thứ vào một boolean.
9. Nếu có fallback, kiểm thử fallback trên chính backend đó.
10. Khi thay DB version/driver/config/schema, chạy probe lại.

### 8.1. Một query integration test — không giả là portable SQL cho mọi DB

Giả sử project có bảng thật chứa ngày:

```sql
SELECT signup_day AS day_value
FROM customer_records
WHERE customer_id = ?
```

Với `Connection connection` và một fixture `knownCustomerId` mà ứng dụng đã tạo:

```java
try (PreparedStatement ps = connection.prepareStatement(
        "SELECT signup_day AS day_value " +
        "FROM customer_records WHERE customer_id = ?")) {
    ps.setLong(1, knownCustomerId);

    try (ResultSet rs = ps.executeQuery()) {
        if (!rs.next()) {
            throw new IllegalStateException("Fixture missing");
        }
        LocalDate target =
                rs.getObject("day_value", LocalDate.class);
        if (!LocalDate.of(2025, 4, 9).equals(target)) {
            throw new AssertionError("Unexpected DATE conversion");
        }
    }
}
```

Đây là **snippet integration**, không phải chương trình độc lập: cần DB/schema/fixture thực. Nó không tự tạo datasource, không được xem như test universal cho Oracle/PostgreSQL/MySQL/SQL Server. Thay bảng và dữ liệu bằng fixture của dự án.

### 8.2. Vì sao chỉ test SQL NULL là thiếu?

Một driver có thể trả null cho target getter mà chưa thực hiện conversion meaningful nào. Vì thế **phải có non-null row** để đánh giá mapping. Sau đó vẫn cần test NULL để xác định domain behavior.

### 8.3. Vì sao test chỉ một DATE cũng chưa đủ?

Thành công với DATE→LocalDate không bảo đảm TIME→LocalTime, TIMESTAMP→LocalDateTime, TIMESTAMP_WITH_TIMEZONE→OffsetDateTime, NUMERIC→BigDecimal hoặc custom types đều hỗ trợ. Đừng có một flag global `supportsJavaTime=true` thiếu chi tiết.

### 8.4. Khi cần kiểm tra lúc startup

Nếu kiểu target là bắt buộc và thiếu support khiến app không thể hoạt động đúng, thực hiện **fail-fast integration/capability check** lúc bootstrap hoặc CI deployment, thay vì đợi row lỗi đầu tiên ở production.

Nếu dùng cache support matrix, gắn với driver, DB product/version, config, SQL type và Java target. Không sao chép kết quả probe của một datasource cho tất cả tenant/backend.

## 9. Xử lý SQLException và fallback không che lỗi

Các tình huống có thể gây lỗi:

| Nguyên nhân | Exception có thể gặp | Hướng xử lý |
| --- | --- | --- |
| Overload typed getter không được driver triển khai | `SQLFeatureNotSupportedException` | Fallback nếu có mapping đúng và test |
| Conversion từ SQL type sang target không hỗ trợ | `SQLException`, có thể là subtype riêng | Phân loại bằng driver docs/SQLState |
| Column label/index sai | `SQLException` | Sửa query/alias |
| ResultSet/Statement/Connection đã đóng | `SQLException` | Sửa lifecycle |
| Dữ liệu lỗi hoặc nằm ngoài miền target | `SQLException` | Kiểm tra schema/precision/data |
| Mất kết nối, lỗi DB, timeout | `SQLException` và subclasses | Xử lý hạ tầng/retry theo policy |
| Java cast sai type mặc định | `ClassCastException` | Không cast untyped getObject bừa |

**SQLFeatureNotSupportedException là subclass của SQLException.** Bắt subtype trước nếu có nhiều nhánh catch.

### 9.1. Fallback hẹp, không swallow mọi lỗi

```java
static LocalDate readLocalDate(
        ResultSet rs, String column) throws SQLException {
    try {
        return rs.getObject(column, LocalDate.class);
    } catch (SQLFeatureNotSupportedException unsupported) {
        java.sql.Date d = rs.getDate(column);
        return d == null ? null : d.toLocalDate();
    }
}
```

Như vậy **chỉ** khi driver báo method unsupported mới thực hiện conversion Java-side qua getter DATE cổ điển nhưng vẫn hợp lệ. Các `SQLException` khác được propagate; không biến lỗi mất kết nối thành dữ liệu giả.

**Quan trọng:** Một driver có thể báo conversion unsupported bằng `SQLException` tổng quát, vì Javadoc cho phép điều đó. Catch hẹp này **không phải universal fallback**. Với driver như vậy, dùng capability flag đã probe hoặc một nhánh phân loại theo SQLState/vendor error code **đã xác minh**. Không mặc định mọi SQLException đồng nghĩa unsupported feature.

### 9.2. Fallback DATE/TIME/TIMESTAMP

```java
static LocalTime readLocalTime(
        ResultSet rs, String column) throws SQLException {
    try {
        return rs.getObject(column, LocalTime.class);
    } catch (SQLFeatureNotSupportedException unsupported) {
        Time t = rs.getTime(column);
        return t == null ? null : t.toLocalTime();
    }
}

static LocalDateTime readLocalDateTime(
        ResultSet rs, String column) throws SQLException {
    try {
        return rs.getObject(column, LocalDateTime.class);
    } catch (SQLFeatureNotSupportedException unsupported) {
        Timestamp t = rs.getTimestamp(column);
        return t == null ? null : t.toLocalDateTime();
    }
}
```

Các helper cần `java.sql.*` và `java.time.*`. Chúng có ý nghĩa với SQL DATE/TIME/TIMESTAMP **không timezone**, có thể cần lưu ý conversion theo timezone setting của driver/JVM/session. Không dùng chúng để dựng lại một `OffsetDateTime` khi dữ liệu không có offset.

### 9.3. Các fallback không nên làm

- Không trả `LocalDate.now()` khi không đọc được ngày từ DB.
- Không bắt mọi `SQLException` rồi giả như row rỗng.
- Không lấy `Timestamp.toLocalDateTime().atOffset(UTC)` như khôi phục một offset vốn không được lưu.
- Không convert `DECIMAL` sang `double` chỉ để đơn giản hóa khi cần precision.
- Không dùng `getString()` rồi tự parse một format không được schema quy định.
- Không thay đổi kết quả từ SQL NULL thành default ngày/giờ/số mà không có business rule.

## 10. SQL NULL: kiểu đích và getter primitive

Với SQL NULL:

```java
Integer boxed = rs.getObject("score", Integer.class);
```

Nếu typed conversion hỗ trợ, `boxed` có thể là Java `null`. Điều này khác với:

```java
int raw = rs.getInt("score");
boolean sqlNull = rs.wasNull();
```

`getInt` trả **0** cho SQL NULL; `wasNull()` trả true khi **lần getter vừa thực hiện** đọc một SQL NULL. Phải gọi `wasNull` **ngay sau** `getInt`, trước khi đọc cột khác.

### 10.1. Helper nullable Integer qua primitive getter

```java
static Integer getNullableInt(
        ResultSet rs, String label) throws SQLException {
    int v = rs.getInt(label);
    return rs.wasNull() ? null : v;
}
```

Đoạn này không phụ thuộc typed INTEGER→Integer conversion. Nhưng chỉ phù hợp nếu SQL type thực sự có thể đọc qua `getInt` mà không mất nghĩa hoặc overflow.

### 10.2. NULL không phải bằng chứng typed getter hỗ trợ đầy đủ

Nếu probe chỉ gọi `rs.getObject(col,LocalDate.class)` trên một NULL, kết quả null có thể không kiểm tra conversion thật. Cần có non-null fixture riêng như đã giải thích.

### 10.3. Java null và Optional

Nếu domain muốn `Optional<LocalDate>`, có thể tạo `Optional.ofNullable(value)` **sau** khi đọc, nhưng đừng cố yêu cầu JDBC driver trả trực tiếp `Optional.class` từ SQL DATE. `Optional` là cơ chế ở tầng Java domain, không phải JDBC 4.2 target mapping chuẩn.

## 11. Timezone và precision: code chạy không có nghĩa dữ liệu đúng nghĩa

### 11.1. SQL DATE

`DATE` là ngày trên lịch, không phải instant. `LocalDate` phù hợp cho ngày sinh, ngày đáo hạn hoặc ngày xuất hóa đơn theo lịch. Không tự chuyển ngày thành midnight ở system-default zone rồi coi đó là cùng một mốc toàn cầu.

### 11.2. SQL TIMESTAMP không timezone

`LocalDateTime` không biết offset. Khi cần `Instant`, **phải có một zone/offset policy từ nghiệp vụ**. Không tự mặc định mọi timestamp database đều là UTC.

### 11.3. TIMESTAMP WITH TIME ZONE

`OffsetDateTime` có offset, từ đó có thể chuyển thành `Instant`. Tuy nhiên database có thể normalize dữ liệu về UTC, không nhất thiết bảo toàn original offset/ZoneId. Nếu yêu cầu lưu **tên vùng** thì schema phải có chỗ lưu nó.

### 11.4. Fractional seconds

`LocalDateTime` hỗ trợ nanoseconds, nhưng database có thể chỉ lưu milliseconds hoặc microseconds. Capability probe cần kiểm thử cả `2025-04-09T13:14:15.123456789` trong cột có precision phù hợp, xem DB round/truncate như thế nào.

### 11.5. SQL DECIMAL và BigDecimal

`BigDecimal` giúp giữ số học thập phân chính xác nhưng schema `DECIMAL(p,s)` vẫn có precision/scale cụ thể. Nếu dùng `getObject(..., BigDecimal.class)` hoặc `getBigDecimal`, test scale/rounding và không ngầm chuyển sang double trong nghiệp vụ tài chính.

## 12. SQLType/JDBCType: chiều ghi khác chiều đọc

Từ JDBC 4.2/Java 8, `java.sql.SQLType` và `java.sql.JDBCType` cho phép biểu diễn SQL type có cấu trúc hơn.

```java
PreparedStatement ps = ...;

ps.setObject(
        1,
        LocalDate.of(2025, 4, 9),
        JDBCType.DATE);
```

Đây là snippet truyền `LocalDate` vào SQL DATE khi driver hỗ trợ dạng `setObject(...,SQLType)`. Nó không chứng minh một ResultSet khác hỗ trợ `getObject(col,LocalDate.class)`, vì đây là **hai hướng conversion khác nhau**.

Một integration test tốt nên thử round-trip:

1. Ghi một `LocalDate`/`LocalDateTime` với type hint phù hợp.
2. Đọc lại bằng typed getter.
3. So sánh expected value, NULL và precision.
4. Nếu DB/session timezone tham gia, xác minh cả instant và offset semantics.

Không viết workaround một chiều rồi cho rằng chiều kia tự đúng.

## 13. ResultSet, Statement, Connection phải được quản lý vòng đời

`ResultSet` implements `AutoCloseable`. Các đối tượng kết nối/statement có resource lifecycle. Viết:

```java
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(
             "SELECT signup_day FROM customer_records " +
             "WHERE customer_id = ?")) {

    ps.setLong(1, customerId);

    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            LocalDate date =
                    rs.getObject(
                            "signup_day", LocalDate.class);
            // Sử dụng trong phạm vi ResultSet còn mở.
        }
    }
}
```

Đây là snippet dựa vào `DataSource dataSource` và schema của ứng dụng. Khi typed conversion có thể unsupported, dùng helper/fallback hoặc capability check phù hợp.

- Không đọc getter trước khi gọi `rs.next()`.
- Không dùng ResultSet sau khi nó đóng.
- Không giữ ResultSet lâu trong stream/lambda để chạy sau khi connection trả về pool.
- Không giả định ResultSet cursor thread-safe khi bị nhiều thread truy cập đồng thời.
- Việc close tài nguyên không thay cho `commit`/`rollback` của giao dịch.
- Khi dùng connection pool, `conn.close()` thường trả connection về pool theo contract pool, không hẳn chấm dứt socket vật lý.

## 14. CachedRowSet: kiểm thử Java logic mà không cần driver ngoài

Để demo **chạy độc lập** mà không yêu cầu DB server, dùng `javax.sql.rowset.CachedRowSet` và `RowSetMetaDataImpl` từ JDK. Đây là một disconnected RowSet triển khai `ResultSet`. Ta tự dựng các cột và row trong memory.

Lợi ích:

- Biên dịch/run trên JDK 17+ không phải tải driver JAR.
- Có thể kiểm thử metadata, null/wasNull, chuyển java.sql Date/Timestamp sang java.time.
- Cho thấy interface có typed getter nhưng **implementation vẫn có thể ném `SQLFeatureNotSupportedException`**.

**Giới hạn:** CachedRowSet **không chứng minh driver production** hỗ trợ kiểu đích. Một test trên PostgreSQL/MySQL/Oracle/SQL Server vẫn phải được thực hiện với driver/database thật, schema và fixture của dự án.

Trong một thử nghiệm JDK 24, `CachedRowSet.getObject(column,LocalDate.class)` và overload cho `LocalDateTime.class` đã ném `SQLFeatureNotSupportedException`; helper fallback vẫn trả đúng giá trị. Ví dụ bên dưới **không assert fallback flag** để tránh phụ thuộc vào implementation RowSet khi JDK được nâng cấp.

## 15. Chương trình Java 17+ độc lập, có stdout kiểm chứng

Tạo file **`JdbcTargetTypeDemo.java`**:

```java
import java.sql.*;
import java.time.*;
import javax.sql.rowset.*;

public class JdbcTargetTypeDemo {
    // Ghi nhận liệu code phải dùng đường fallback.
    static final class ReadValue<T> {
        final T value;
        final boolean usedFallback;

        ReadValue(T value, boolean usedFallback) {
            this.value = value;
            this.usedFallback = usedFallback;
        }
    }

    static void check(boolean ok, String label) {
        if (!ok) {
            throw new AssertionError(label);
        }
    }

    static ReadValue<LocalDate> readDate(
            ResultSet rs, String column) throws SQLException {
        try {
            return new ReadValue<>(
                    rs.getObject(column, LocalDate.class),
                    false);
        } catch (SQLFeatureNotSupportedException unsupported) {
            java.sql.Date value = rs.getDate(column);
            return new ReadValue<>(
                    value == null ? null : value.toLocalDate(),
                    true);
        }
    }

    static ReadValue<LocalDateTime> readTimestamp(
            ResultSet rs, String column) throws SQLException {
        try {
            return new ReadValue<>(
                    rs.getObject(column, LocalDateTime.class),
                    false);
        } catch (SQLFeatureNotSupportedException unsupported) {
            Timestamp value = rs.getTimestamp(column);
            return new ReadValue<>(
                    value == null ? null : value.toLocalDateTime(),
                    true);
        }
    }

    static CachedRowSet createLocalRows() throws SQLException {
        RowSetMetaDataImpl meta = new RowSetMetaDataImpl();
        meta.setColumnCount(5);

        meta.setColumnName(1, "id");
        meta.setColumnType(1, Types.BIGINT);

        meta.setColumnName(2, "signup_day");
        meta.setColumnType(2, Types.DATE);

        meta.setColumnName(3, "created_at");
        meta.setColumnType(3, Types.TIMESTAMP);

        meta.setColumnName(4, "score");
        meta.setColumnType(4, Types.INTEGER);

        meta.setColumnName(5, "note");
        meta.setColumnType(5, Types.VARCHAR);

        CachedRowSet rows =
                RowSetProvider.newFactory().createCachedRowSet();

        rows.setMetaData(meta);
        rows.moveToInsertRow();
        rows.updateLong(1, 101L);
        rows.updateDate(
                2, java.sql.Date.valueOf("2025-04-09"));
        rows.updateTimestamp(
                3, Timestamp.valueOf("2025-04-09 13:14:15"));
        rows.updateNull(4);
        rows.updateString(5, "active");
        rows.insertRow();
        rows.moveToCurrentRow();
        rows.beforeFirst();

        return rows;
    }

    public static void main(String[] args)
            throws SQLException {
        try (CachedRowSet rows = createLocalRows()) {
            check(rows.next(), "one row");

            ResultSetMetaData meta = rows.getMetaData();
            int dayType = meta.getColumnType(2);
            int createdType = meta.getColumnType(3);

            check(dayType == Types.DATE
                    && createdType == Types.TIMESTAMP,
                    "SQL type codes");

            System.out.println(
                    "dateSqlType=" + JDBCType.valueOf(dayType));
            System.out.println(
                    "timestampSqlType="
                    + JDBCType.valueOf(createdType));
            System.out.println(
                    "dateDefaultClass="
                    + rows.getObject(2).getClass().getName());

            ReadValue<LocalDate> day =
                    readDate(rows, "signup_day");
            ReadValue<LocalDateTime> created =
                    readTimestamp(rows, "created_at");

            check(day.value.equals(
                    LocalDate.of(2025, 4, 9)),
                    "date");
            check(created.value.equals(
                    LocalDateTime.of(2025, 4, 9, 13, 14, 15)),
                    "timestamp");

            System.out.println(
                    "readTargetDate=" + day.value);
            System.out.println(
                    "readTargetTimestamp=" + created.value);

            long id = rows.getLong("id");
            check(id == 101L, "id");
            System.out.println("id=" + id);

            int score = rows.getInt("score");
            boolean scoreWasNull = rows.wasNull();
            check(score == 0 && scoreWasNull, "SQL NULL");

            System.out.println("scorePrimitive=" + score);
            System.out.println("scoreWasSqlNull=" + scoreWasNull);
            System.out.println(
                    "note=" + rows.getString("note"));

            // day.usedFallback / created.usedFallback
            // có thể dùng cho diagnostics. Không assert
            // một implementation phải đi theo nhánh nào.
            System.out.println("ALL CHECKS PASSED");
        }
    }
}
```


### 15.1. Vì sao chương trình không cần DB?

`CachedRowSet` chứa data và metadata trong memory; đây là **kiểm thử adapter** chứ không phải truy vấn một server. Các SQL type được cấu hình bởi `RowSetMetaDataImpl`, không do driver sản phẩm trả về.

### 15.2. Vì sao metadata báo java.sql.Date mặc định?

Lời gọi `rows.getObject(2)` trong fixture tạo `java.sql.Date`. Nhưng ứng dụng muốn `LocalDate`, nên helper thử typed getter, và nếu unsupported thì gọi `getDate(...).toLocalDate()`. **Không ép cast** trực tiếp object thô thành LocalDate.

### 15.3. Vì sao không in usedFallback?

`usedFallback` hữu ích cho log/probe, nhưng implementation RowSet hoặc driver có thể thay đổi mức hỗ trợ. Bài test cần assert **semantic values**, không mặc định API luôn unsupported hoặc luôn supported ở mọi phiên bản.

### 15.4. SQL NULL được phát hiện thế nào?

`getInt("score")` trả 0 cả khi SQL NULL. `wasNull` ngay sau đó trả true. Nhờ vậy code không nhầm cột không có giá trị với số 0 thật.

### 15.5. Khi cần kiểm tra thật, thay RowSet bằng ResultSet của DB

Giữ lại cách readDate/readTimestamp, nhưng tạo ResultSet từ PreparedStatement trên DB thực và ghi thông tin driver/version. Integration test cần kiểm chứng target non-null, NULL, precision và timezone theo schema của chính ứng dụng.

## 16. Một vài tình huống ứng dụng

### 16.1. Ngày sinh / ngày hết hạn: LocalDate

Ngày sinh hoặc ngày hết hạn thường là **ngày lịch**, không phải instant. SQL DATE→LocalDate là mapping tự nhiên khi driver hỗ trợ. Nếu helper fallback qua `java.sql.Date`, vẫn giữ ý nghĩa ngày, không cần tự gắn midnight UTC.

### 16.2. Audit timestamp: LocalDateTime hay OffsetDateTime?

Nếu SQL TIMESTAMP không timezone, `LocalDateTime` là một giá trị local date-time; muốn xác định UTC instant thì domain phải có **time-zone policy**. Nếu SQL TIMESTAMP_WITH_TIMEZONE, dùng `OffsetDateTime` khi backend hỗ trợ, sau đó gọi `toInstant()` nếu cần cùng trục thời gian.

Không gọi `Timestamp.toLocalDateTime().atOffset(UTC)` chỉ để làm cho một Instant “có vẻ hợp lệ” khi DB không quy định UTC.

### 16.3. Giá tiền: BigDecimal

SQL DECIMAL(p,s) nên được đọc bằng `BigDecimal` hoặc typed `getObject(...,BigDecimal.class)` khi driver hỗ trợ, không âm thầm chuyển sang double vì mất precision. Test cả scale, rounding và giá trị cực trị.

### 16.4. Nullable score: Integer hoặc getInt+wasNull

Nếu SQL INTEGER cho phép NULL, `Integer` giúp domain phân biệt absent với 0. Khi typed `getObject(...,Integer.class)` bị driver từ chối, helper `getInt` và `wasNull` ngay sau đó là một lựa chọn có kiểm soát.

## 17. Chẩn đoán khi driver không hỗ trợ target

Khi gặp lỗi, ghi lại những yếu tố kỹ thuật không chứa PII:

- `DatabaseMetaData.getDriverName/getDriverVersion`.
- `getDatabaseProductName/getDatabaseProductVersion` và JDBC reported major/minor.
- Column label/index, SQL type code/name của `ResultSetMetaData`.
- Java target class, ví dụ `LocalDate.class.getName()`.
- Exception class, SQLState, vendor error code và cause.
- Với temporal: session timezone, DB timezone policy và column precision.
- Có hay không fallback an toàn đã được test.

**Không log toàn bộ row dữ liệu người dùng, JDBC URL chứa credentials hay bí mật của connection** chỉ vì đang debug conversion.

Một driver có thể báo conversion không hỗ trợ bằng generic `SQLException` thay vì `SQLFeatureNotSupportedException`. Nếu gặp trường hợp đó, phân loại theo tài liệu driver và test thật; không catch mọi `SQLException` rồi áp fallback ngầm.

## 18. Những lỗi phổ biến và cách khắc phục

### Lỗi 1. Cho rằng typed getter được giới thiệu lần đầu trong JDBC 4.2

Overload có từ JDBC 4.1/Java 7; JDBC 4.2 bổ sung java.time mappings. **Sửa:** phân biệt mốc API và mốc mapping.

### Lỗi 2. Cast kết quả getObject mặc định

`(LocalDate)rs.getObject("day")` có thể ném ClassCastException nếu default là java.sql.Date. **Sửa:** typed getter hoặc fallback chuyển đổi.

### Lỗi 3. Dùng getColumnClassName làm bằng chứng support target

Nó báo default class, không phải accepted target classes. **Sửa:** thử conversion trên non-null fixture.

### Lỗi 4. Dùng DatabaseMetaData.supportsConvert làm phép thử LocalDate

Phương thức đó hỏi về scalar SQL CONVERT giữa SQL types. **Sửa:** thử `rs.getObject(col,LocalDate.class)`.

### Lỗi 5. Chỉ kiểm tra JDBC driver version

Version không phải bảo đảm không có giới hạn hoặc bug mapping. **Sửa:** integration test driver và DB version thật.

### Lỗi 6. Probe chỉ có SQL NULL

Có thể không thực sự kiểm tra conversion. **Sửa:** thêm non-null row với expected semantics, rồi test NULL riêng.

### Lỗi 7. Nhầm SQL DATE và TIMESTAMP

LocalDate không có giờ; LocalDateTime có giờ nhưng không có offset. **Sửa:** chọn theo SQL type và domain.

### Lỗi 8. Dùng Instant/ZonedDateTime như mapping chuẩn JDBC 4.2

Không nằm trong năm mapping Java time căn bản. **Sửa:** dùng driver extension có test hoặc chuyển từ OffsetDateTime có offset thật.

### Lỗi 9. Tự gán UTC vào TIMESTAMP không timezone

Tạo một giả định về instant có thể sai ở production. **Sửa:** xác định policy source/session zone trước khi convert.

### Lỗi 10. Nuốt SQLException rồi trả giá trị mặc định

Che data error, SQL syntax hoặc connection loss. **Sửa:** phân loại/propagate lỗi, chỉ fallback khi đã chứng minh unsupported.

### Lỗi 11. Bắt SQLException trước SQLFeatureNotSupportedException

Subtype đã bị bao phủ, gây compile error cho catch phía sau. **Sửa:** bắt subtype trước hoặc phân loại trong catch tổng.

### Lỗi 12. Nghĩ mọi unsupported conversion đều ném SQLFeatureNotSupportedException

Javadoc cũng cho phép SQLException cho conversion không được hỗ trợ. **Sửa:** dùng driver-specific test/capability matrix.

### Lỗi 13. Dùng getInt với nullable INTEGER mà quên wasNull

0 và SQL NULL bị nhầm. **Sửa:** gọi wasNull ngay sau getter.

### Lỗi 14. Gọi wasNull sau khi đọc cột khác

Nó chỉ kiểm tra giá trị của getter cuối. **Sửa:** gọi ngay lập tức.

### Lỗi 15. Dùng ResultSet index 0

JDBC dùng indexes 1-based. **Sửa:** dùng 1..getColumnCount.

### Lỗi 16. Đọc cột qua label trùng nhau

`getObject("id",...)` có thể chọn cột đầu trùng label. **Sửa:** SELECT AS aliases riêng hoặc index đã xác minh.

### Lỗi 17. Dùng CachedRowSet để tuyên bố driver sản phẩm hỗ trợ conversion

CachedRowSet in-memory không chứng minh JDBC driver/DB server. **Sửa:** integration test trên DB thực.

### Lỗi 18. Quên đóng ResultSet/Statement/Connection

Có thể leak resources/cursor. **Sửa:** try-with-resources và transaction policy đúng.

### Lỗi 19. Precision hoặc scale bị mất nhưng không test

Type Java phù hợp chưa chắc dữ liệu giữ nguyên nanos/cents. **Sửa:** test precision, scale, timezone normalization.

### Lỗi 20. Cho rằng ghi bằng setObject thành công sẽ đọc lại typed thành công

Hai chiều driver mapping có thể có giới hạn khác. **Sửa:** kiểm thử round-trip.

### Lỗi 21. Gộp mọi java.time targets thành supportsJavaTime=true

Có thể chỉ một số conversion được hỗ trợ. **Sửa:** cache theo SQL type, target, driver, DB version/config.

### Lỗi 22. Tưởng OffsetDateTime giữ original ZoneId

Nó chỉ chứa UTC offset, không chứa tên vùng đầy đủ. **Sửa:** lưu ZoneId riêng nếu nghiệp vụ cần.

### Lỗi 23. Sử dụng String parse cho mọi DATE

Format có thể thay đổi theo DB/locale. **Sửa:** dùng type-safe JDBC mapping hoặc một explicit text protocol.

### Lỗi 24. Dùng BigDecimal như double khi cần tiền tệ

Chuyển BigDecimal sang double làm mất chính xác trong nhiều trường hợp. **Sửa:** giữ BigDecimal theo schema DECIMAL.

### Lỗi 25. Cache capability không xét nâng driver/backend

Năng lực có thể thay đổi qua phiên bản hoặc config. **Sửa:** revalidate khi deploy/upgrade.

## 19. Bài tập và đáp án

**1.** `getObject("day")` và `getObject("day",LocalDate.class)` có điểm khác nhau?  
**Đáp án:** Một bên để driver chọn class mặc định; bên kia yêu cầu chuyển sang LocalDate nếu được hỗ trợ.

**2.** Typed getter có từ JDBC 4.2?  
**Đáp án:** Không, từ JDBC 4.1/Java 7. JDBC 4.2 bổ sung java.time mappings.

**3.** SQL DATE tương ứng java.time nào?  
**Đáp án:** LocalDate.

**4.** SQL TIME không timezone tương ứng class nào?  
**Đáp án:** LocalTime.

**5.** SQL TIMESTAMP không timezone tương ứng class nào?  
**Đáp án:** LocalDateTime.

**6.** SQL TIME_WITH_TIMEZONE tương ứng class nào?  
**Đáp án:** OffsetTime.

**7.** SQL TIMESTAMP_WITH_TIMEZONE tương ứng class nào?  
**Đáp án:** OffsetDateTime.

**8.** getColumnClassName trả java.sql.Date, typed LocalDate có thể chạy không?  
**Đáp án:** Có thể, vì method metadata mô tả untyped getObject, không phải mọi accepted target.

**9.** supportsConvert(Types.DATE,Types.VARCHAR) chứng minh gì?  
**Đáp án:** Khả năng SQL scalar CONVERT giữa SQL DATE và SQL VARCHAR, không phải typed SQL→Java.

**10.** Driver báo JDBC major=4 có bảo đảm `getObject(col,OffsetDateTime.class)` không?  
**Đáp án:** Không; phải kiểm tra SQL type/backend/driver thực tế.

**11.** Thử trên một SQL NULL đủ để chứng minh LocalDate mapping không?  
**Đáp án:** Không, cần thử giá trị non-null và so expected.

**12.** Driver ném SQLFeatureNotSupportedException cho DATE→LocalDate, fallback nào phù hợp?  
**Đáp án:** `getDate(col)` và `toLocalDate()` khi non-null.

**13.** Tất cả conversion unsupported có ném SQLFeatureNotSupportedException không?  
**Đáp án:** Không, Javadoc cho phép SQLException tổng quát khi phép conversion không hỗ trợ.

**14.** Vì sao không bắt mọi SQLException rồi trả LocalDate.now()?  
**Đáp án:** Có thể che lỗi kết nối/SQL/data và ghi dữ liệu sai.

**15.** getInt trên SQL NULL trả gì, làm sao biết là NULL?  
**Đáp án:** Trả 0 và gọi wasNull ngay sau getter để biết SQL NULL.

**16.** Có thể dùng getObject(col,Integer.class) và nhận null không?  
**Đáp án:** Có khi conversion được driver hỗ trợ và SQL value là NULL.

**17.** JDBC column indexes bắt đầu từ đâu?  
**Đáp án:** 1.

**18.** Vì sao dùng alias duy nhất?  
**Đáp án:** Tránh đọc nhầm cột khi tên hoặc label trùng nhau.

**19.** SQL TIMESTAMP không timezone tự biểu diễn Instant chưa?  
**Đáp án:** Chưa. Phải có zone/offset policy để chuyển thành thời điểm tuyệt đối.

**20.** OffsetDateTime có chứa original ZoneId không?  
**Đáp án:** Không, nó chứa offset; lưu tên vùng riêng nếu cần.

**21.** ResultSetMetaData.getColumnTypeName khác getColumnType thế nào?  
**Đáp án:** Một bên trả tên SQL type do DB báo, một bên trả type code JDBC.

**22.** Có nên dùng CachedRowSet test để kết luận driver Oracle/PostgreSQL production hỗ trợ?  
**Đáp án:** Không. Nó chỉ test Java-side logic, cần integration test driver/backend thật.

**23.** Khi dùng `setObject(LocalDate,JDBCType.DATE)` thì typed read chắc chạy?  
**Đáp án:** Không. Hai chiều cần kiểm chứng riêng hoặc round-trip.

**24.** Nếu DB chỉ lưu milliseconds, LocalDateTime có luôn giữ nanoseconds đầu vào?  
**Đáp án:** Không. Kiểm tra schema precision và backend rounding/truncation.

**25.** Với SQL DECIMAL chứa tiền tệ, ưu tiên class nào?  
**Đáp án:** BigDecimal và kiểm tra precision/scale.

**26.** Nếu driver trả lỗi SQL syntax, có nên chạy fallback như unsupported?  
**Đáp án:** Không. Sửa query hoặc propagate lỗi, không biến mọi lỗi thành conversion failure.

**27.** Nên cache capability theo gì?  
**Đáp án:** Cặp SQL type→Java target cùng driver/DB version, cấu hình liên quan; không một global flag.

**28.** Khi thay driver version, có cần test lại?  
**Đáp án:** Có, để xác minh conversion, precision/timezone và error behavior.

## 20. Checklist production

- [ ] Phân biệt typed getObject từ JDBC 4.1 và java.time mapping của JDBC 4.2.
- [ ] Xác định SQL output type, column label, schema và database dialect.
- [ ] Dùng `ResultSetMetaData.getColumnType/getColumnTypeName` cho SQL type của query.
- [ ] Hiểu `getColumnClassName` chỉ mô tả class của untyped `getObject`.
- [ ] Không dùng `supportsConvert` để suy ra SQL→Java target conversion.
- [ ] Ghi JDBC driver name/version và database product/version để chẩn đoán.
- [ ] Không coi getJDBCMajorVersion là bằng chứng chắc chắn.
- [ ] Probe non-null value trên driver/backend thực tế với typed getObject.
- [ ] Probe SQL NULL, boundary, precision/scale/timezone riêng.
- [ ] Mô tả đúng SQL DATE↔LocalDate, TIME↔LocalTime, TIMESTAMP↔LocalDateTime.
- [ ] Xác minh OffsetTime/OffsetDateTime chỉ khi SQL type có timezone và driver hỗ trợ.
- [ ] Không giả định Instant/ZonedDateTime là mapping cơ bản của JDBC 4.2.
- [ ] Không bịa offset/ZoneId khi nguồn không chứa thông tin đó.
- [ ] Dùng fallback hẹp cho Date/Time/Timestamp khi driver thiếu typed conversion.
- [ ] Không catch mọi SQLException rồi bỏ qua lỗi dữ liệu/SQL/connection.
- [ ] Khi driver báo unsupported bằng generic SQLException, có SQLState/vendor policy đã test.
- [ ] Với nullable primitive getters, gọi wasNull ngay sau getter.
- [ ] Dùng aliases rõ, cột bắt đầu từ 1, không đọc getter trước rs.next().
- [ ] Dùng try-with-resources cho ResultSet/Statement/Connection.
- [ ] Kiểm thử riêng binding `setObject` và typed reading `getObject`.
- [ ] Không dùng CachedRowSet in-memory làm bằng chứng driver sản phẩm.
- [ ] Có integration tests trên các phiên bản driver/backend ứng dụng công bố hỗ trợ.
- [ ] Revalidate capability khi driver/server/schema/config thay đổi.
- [ ] Không log credentials/PII khi chẩn đoán conversion failure.
