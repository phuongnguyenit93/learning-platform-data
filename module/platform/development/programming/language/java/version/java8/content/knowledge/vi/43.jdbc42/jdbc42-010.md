# Kiểm thử timezone, precision, null và dữ liệu biên với JDBC 4.2

**Chủ đề:** Java 8 → JDBC 4.2 → Kiểm thử timezone, precision, null và dữ liệu biên.

JDBC 4.2 (có từ Java 8) mở rộng khả năng làm việc với **`java.time`** và SQL temporal types qua các API như **`PreparedStatement.setObject(...)`**, **`ResultSet.getObject(..., Class<T>)`**, **`JDBCType`** và **`SQLType`**. Điều quan trọng khi kiểm thử không phải chỉ chứng minh một hàng dữ liệu bình thường insert/select thành công. Một test đúng phải xác nhận **kiểu và ý nghĩa thời gian**, **múi giờ/offset**, **precision**, **`NULL`** và các **giá trị ranh giới** trong một hệ thống gồm **JDK + JDBC driver + database engine + schema + cấu hình session**.

Các lỗi thường chỉ xuất hiện khi chuyển môi trường hoặc lúc chạy production:

- Một `LocalDateTime` bị hiểu nhầm là một instant UTC.
- `OffsetDateTime` được database chuẩn hóa sang UTC; so sánh toàn bộ object thất bại dù **instant không đổi**.
- `LocalDateTime` thuộc **DST gap/overlap** bị diễn giải sai.
- Java giữ **nanosecond (9 chữ số thập phân của giây)** nhưng cột SQL chỉ giữ **millisecond hoặc microsecond**, gây mất precision.
- SQL `NULL` bị biến thành `0`, ngày mặc định hoặc một đối tượng không hợp lệ ở tầng ứng dụng.
- Trường hợp trước 1970, ngày nhuận, cuối tháng, ranh giới ngày, cực trị kiểu SQL hoặc số âm khi tính epoch không có trong test.
- Test chỉ chạy với timezone mặc định của máy lập trình viên, nên CI/production cho kết quả khác.
- Một test “round-trip equals” thất bại không phải vì lưu sai instant, mà vì yêu cầu sai rằng **offset/region ID** phải được bảo toàn.
- Một driver quảng cáo JDBC 4.2 nhưng **không hỗ trợ tất cả phép chuyển kiểu** hoặc xử lý precision khác driver khác.

**Nguyên tắc trung tâm:**

> Hãy kiểm thử theo **ngữ nghĩa dữ liệu**. `DATE`/`LocalDate` là ngày lịch, `TIMESTAMP WITHOUT TIME ZONE`/`LocalDateTime` là ngày giờ không gắn offset, và `TIMESTAMP WITH TIME ZONE`/`OffsetDateTime` thường dùng để biểu diễn một instant. Không áp một phép so sánh cho mọi loại.

Bài tập trung vào API và kỹ thuật **vẫn đang áp dụng hiện nay**. Các ví dụ **thuần Java** chạy được trên Java 17+ không cần database; phần **integration test PostgreSQL** dùng JDBC 4.2 và cần một PostgreSQL instance cùng driver thực tế, vì không thể bịa một kết quả chạy database khi chưa có môi trường. Mọi hành vi phụ thuộc driver/DB sẽ được ghi rõ, không khái quát thành “JDBC lúc nào cũng như vậy”.

## 1. Mục tiêu học tập

Sau bài này, bạn có thể:

1. Lập **test matrix** cho SQL `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMP WITH TIME ZONE`, `NUMERIC`.
2. Chọn đúng `LocalDate`, `LocalTime`, `LocalDateTime`, `OffsetDateTime`, `Instant`, `ZonedDateTime` theo nghĩa dữ liệu.
3. Dùng `PreparedStatement.setObject` và `ResultSet.getObject(..., Class<T>)` với kiểu Java tương ứng.
4. Hiểu **JDBC 4.2 là hợp đồng API**, nhưng mapping hỗ trợ thực tế còn phụ thuộc phiên bản driver.
5. Kiểm thử timezone **JVM**, **database session**, **server** và **offset** theo các biến độc lập.
6. So sánh **instant** bằng `toInstant()`, **local timestamp** bằng `equals`, và tránh khẳng định offset gốc luôn được lưu.
7. Viết test cho **DST gap** (0 offset hợp lệ) và **DST overlap** (2 offset hợp lệ).
8. Phát hiện mất precision **nano → micro/milli**, và kiểm tra chính sách rounding/truncation.
9. Kiểm thử `BigDecimal` với `NUMERIC(p,s)` mà không dùng `double` làm giá trị expected.
10. Ghi và đọc SQL `NULL` đúng kiểu, kiểm tra `ResultSet.wasNull()` khi dùng primitive getter.
11. Test các biên: ngày nhuận, trước Unix epoch, thời điểm sát ranh giới giây/ngày, gần tràn precision, giới hạn cột.
12. Chạy integration test độc lập, cô lập dữ liệu bằng transaction/temporary table và `rollback`.
13. Dùng metadata, SQLState và báo cáo driver/version để phân tích khác biệt giữa môi trường.
14. Viết QA checklist không gắn với giả định chưa được tài liệu driver bảo đảm.

## 2. Hai lớp kiểm thử: thuần Java và integration JDBC

**Tầng A — Unit test thuần Java:** Kiểm tra các phép biến đổi/định nghĩa của `java.time`: `toInstant`, timezone, DST, truncation, rounding, `BigDecimal`, parser và dữ liệu biên. Không phụ thuộc database, nên **stdout xác định** theo JDK/tzdb được sử dụng.

**Tầng B — Integration test JDBC:** Chạy thật qua `PreparedStatement → driver → database → ResultSet`. Chỉ tầng B mới kiểm tra được **cột SQL**, **precision engine**, **session timezone**, **NULL mapping**, **driver support**, **SQL error codes** và schema thực.

Tách hai tầng này giúp tránh lỗi phân tích: một test thuần Java PASS **không chứng minh** driver/PostgreSQL/Oracle/MySQL cũng giữ y hệt precision; ngược lại một test integration FAIL cần được phân loại thành **contract sai, driver khác, schema khác hoặc biến đổi thời gian sai**.

### 2.1. Không dùng database giả như bằng chứng cho hành vi database thật

Một mock `ResultSet` trả `LocalDateTime` do test tự cấu hình chỉ kiểm tra code gọi method; nó **không kiểm tra codec của JDBC driver**. Hãy giữ unit tests cho business logic, và dùng database thật cho test round-trip.

### 2.2. Ghi lại phiên bản ngay khi test bắt đầu

Nên log (không log mật khẩu/secret):

~~~java
DatabaseMetaData meta = connection.getMetaData();

System.out.println("driver=" + meta.getDriverName());
System.out.println("driverVersion=" + meta.getDriverVersion());
System.out.println("database=" + meta.getDatabaseProductName());
System.out.println("databaseVersion=" + meta.getDatabaseProductVersion());
System.out.println("jdbc=" + meta.getJDBCMajorVersion()
        + "." + meta.getJDBCMinorVersion());
~~~

Đây là **đoạn minh họa trong method đã có `Connection connection`**; chuỗi stdout thay đổi theo môi trường, không được ghi sẵn một phiên bản giả.

Ghi thêm JDK version, timezone mặc định của JVM, database session timezone và DDL/schema. Khi một assertion sai, những dữ liệu này thường quyết định cách tái hiện.

## 3. Bảng mapping: không gán múi giờ khi dữ liệu không có múi giờ

| Dữ liệu SQL | Java thường phù hợp | Ý nghĩa | So sánh round-trip thường dùng |
|---|---|---|---|
| `DATE` | `LocalDate` | Ngày lịch, không giờ và không timezone | `expected.equals(actual)` |
| `TIME WITHOUT TIME ZONE` | `LocalTime` | Giờ địa phương trong ngày, không ngày và offset | `equals` nếu precision cho phép |
| `TIMESTAMP WITHOUT TIME ZONE` | `LocalDateTime` | Ngày giờ dạng local, không đại diện instant một cách độc lập | `equals` nếu precision cho phép |
| `TIMESTAMP WITH TIME ZONE` | `OffsetDateTime` khi driver hỗ trợ | Thông tin đủ để xác định instant; cách lưu offset phụ thuộc DB | `expected.toInstant().equals(actual.toInstant())` khi precision cho phép |
| `TIME WITH TIME ZONE` | `OffsetTime` **nếu driver hỗ trợ** | Giờ + offset, không mang ngày/ZoneId | Kiểm tra support và semantics theo driver |
| `NUMERIC(p,s)` | `BigDecimal` | Giá trị thập phân chính xác theo độ rộng/scale | `compareTo()==0` hoặc `equals` nếu scale là contract |

**Không có mapping phổ quát từ mọi SQL timestamp sang `Instant.class` hoặc `ZonedDateTime.class`.** Ví dụ, tài liệu chính thức của pgJDBC liệt kê hỗ trợ thông dụng cho `LocalDate`, `LocalTime`, `LocalDateTime`, `OffsetDateTime`; tài liệu này **không hứa** `getObject(..., Instant.class)` hay `getObject(..., ZonedDateTime.class)` hoạt động. Muốn `Instant`, hãy đọc kiểu được driver hỗ trợ rồi chuyển:

~~~java
OffsetDateTime value =
        rs.getObject("event_at", OffsetDateTime.class);

Instant instant = value == null
        ? null
        : value.toInstant();
~~~

Đây là **đoạn minh họa**, cần `ResultSet rs` và cột tương ứng; `getObject` chỉ thành công nếu driver hỗ trợ conversion được yêu cầu.

**Lưu ý đặc thù:** PostgreSQL `timestamp with time zone`/`timestamptz` lưu mốc thời gian, **không lưu nguyên `ZoneId` hoặc offset gốc**. pgJDBC thường trả `OffsetDateTime` với offset **UTC/Z**. Đây là lý do kiểm thử `toInstant` thay vì `OffsetDateTime.equals` cho cột này. Database khác có thể có contract khác; không suy PostgreSQL thành chuẩn toàn bộ SQL.

## 4. Bốn khái niệm thời gian không được trộn

### 4.1. LocalDate — ngày lịch

~~~java
LocalDate date = LocalDate.of(2024, 2, 29);
~~~

Nó chỉ biểu diễn ngày 29 tháng 2 năm nhuận. Không có thời điểm UTC, không có offset, không có giờ.

**Hợp lý:** ngày sinh, ngày hiệu lực, ngày báo cáo theo lịch, cột SQL DATE.

**Sai:** biến LocalDate thành một instant bằng cách tự coi nó luôn là nửa đêm UTC khi domain thực ra dùng một múi giờ khác.

### 4.2. LocalTime — giờ trong ngày

~~~java
LocalTime time = LocalTime.of(23, 59, 59, 123_456_000);
~~~

Nó không biết **ngày nào** hoặc timezone nào. Kết hợp với một date và zone mới có thể tạo instant.

**Cần test precision:** một số database có cột `TIME(0)`, `TIME(3)` hoặc `TIME(6)` với số chữ số phần giây khác nhau.

### 4.3. LocalDateTime — ngày giờ chưa có offset

~~~java
LocalDateTime value =
        LocalDateTime.of(2025, 1, 2, 3, 4, 5, 123_456_000);
~~~

Nó biểu diễn **03:04:05.123456 tại một ngày lịch**, nhưng không có quy tắc quy về UTC. **Không gọi `LocalDateTime.toInstant()` khi chưa có ZoneOffset**, vì chính class này không chứa offset.

**Sai phổ biến:** đọc SQL `TIMESTAMP WITHOUT TIME ZONE` vào `LocalDateTime`, rồi gọi `atZone(ZoneId.systemDefault())` mà không biết dữ liệu gốc có thực sự được hiểu trong timezone của máy chạy hay không.

### 4.4. OffsetDateTime — local time + một offset

~~~java
OffsetDateTime value = OffsetDateTime.parse(
        "2025-02-01T12:34:56.123456+07:00");
~~~

Dữ liệu trên xác định **một instant**. Cùng instant có thể được viết là `2025-02-01T05:34:56.123456Z`.

`OffsetDateTime` giữ **offset** nhưng không giữ một **region timezone ID** như `Asia/Ho_Chi_Minh` hoặc `America/New_York`.

### 4.5. Instant và ZonedDateTime

- **`Instant`**: một điểm trên timeline UTC, không mang timezone địa phương.
- **`ZonedDateTime`**: ngày giờ + region ZoneId + quy tắc múi giờ theo tzdb.
- **`OffsetDateTime`**: ngày giờ + offset cố định, không chứa toàn bộ quy tắc lịch sử/tương lai của một region.

Nếu ứng dụng cần lịch hẹn lúc 09:00 mỗi ngày theo `Asia/Ho_Chi_Minh` hoặc `Europe/Paris`, nên lưu/định nghĩa **region ZoneId** ở cấp domain; một `timestamptz` PostgreSQL không tự khôi phục được region gốc.

## 5. Test timezone: đừng chỉ thay ZoneId.systemDefault()

Có ít nhất bốn timezone/context liên quan:

| Cấp | Nguồn | Ảnh hưởng có thể có |
|---|---|---|
| **JVM default** | `-Duser.timezone` hoặc cấu hình process | Các phép chuyển đổi sử dụng default zone, đặc biệt đường code dùng `java.sql.Timestamp/Calendar` |
| **Database server** | Cấu hình instance | Một số thao tác/literals và session defaults |
| **Database session** | Ví dụ `SET TIME ZONE` trên PostgreSQL | Hiển thị/parse các giá trị khi chuyển kiểu hoặc query SQL |
| **Offset/ZoneId của dữ liệu** | `+07:00`, `Z`, `America/New_York` | Định nghĩa instant hoặc quy tắc DST trong domain |

**Không được mặc định cả bốn luôn giống nhau**. Một system chạy JVM ở UTC, database server ở timezone khác và người dùng ở múi giờ thứ ba là hoàn toàn bình thường.

### 5.1. Ma trận timezone nên chạy

1. JVM UTC, session UTC.
2. JVM UTC, session `Asia/Ho_Chi_Minh`.
3. JVM `Asia/Ho_Chi_Minh`, session UTC.
4. JVM `America/New_York`, session UTC.
5. Nếu có thể, một session timezone có DST như `America/New_York`.
6. Giá trị `OffsetDateTime` nguồn có offset `+07:00`, `Z`, `-05:00`.
7. Kiểm tra cả cột `TIMESTAMP WITHOUT TIME ZONE` và `TIMESTAMP WITH TIME ZONE`.

**Expected behavior phụ thuộc kiểu cột:** local timestamp giữ **thành phần ngày-giờ local** theo contract; instant timestamp phải giữ **cùng instant** (trong giới hạn precision), không nhất thiết giữ cùng ký tự offset.

### 5.2. Không sửa JVM timezone toàn cục trong unit test song song

`TimeZone.setDefault(...)` ảnh hưởng **toàn process** và có thể khiến test khác chạy đồng thời bị nhiễu.

Ưu tiên:

- Chạy test trong **process riêng** với `-Duser.timezone=UTC`, `-Duser.timezone=Asia/Ho_Chi_Minh`.
- Dùng `Clock.fixed(...)` và `ZoneId` truyền tường minh vào business logic.
- Kiểm soát database session timezone ở từng connection, và khôi phục/rollback sau test.
- Tránh giả định timezone của CI runner.

### 5.3. Không chuyển LocalDateTime sang Instant một cách tùy tiện

~~~java
LocalDateTime local =
        LocalDateTime.parse("2025-02-01T12:34:56");

Instant assumedUtc = local.toInstant(ZoneOffset.UTC);
~~~

`assumedUtc` chỉ đúng **nếu dữ liệu được định nghĩa là UTC local representation**. Nếu dữ liệu thật sự là 12:34:56 theo offset +07:00, instant chính xác là `2025-02-01T05:34:56Z`.

Đây là lỗi **đổi ý nghĩa dữ liệu**, không phải lỗi JDBC engine.

## 6. So sánh đúng một timestamp có timezone

Giả sử input:

~~~text
2025-02-01T12:34:56.123456+07:00
~~~

Nếu đọc từ PostgreSQL `timestamptz` qua pgJDBC, driver có thể trả:

~~~text
2025-02-01T05:34:56.123456Z
~~~

Hai `OffsetDateTime` có **toString khác**, **offset khác**, và `equals` khác, nhưng cùng instant.

**Cách assert phù hợp với PostgreSQL:**

~~~java
OffsetDateTime expected =
        OffsetDateTime.parse(
                "2025-02-01T12:34:56.123456+07:00");

OffsetDateTime actual =
        rs.getObject("event_at", OffsetDateTime.class);

if (!expected.toInstant().equals(actual.toInstant())) {
    throw new AssertionError("Instant changed");
}
~~~

Đây là **đoạn minh họa** trong code đã có `ResultSet rs`. Yêu cầu cột `event_at` có precision đủ để giữ 6 chữ số phần giây và driver hỗ trợ mapping.

**Không assert `expected.equals(actual)` trừ khi schema/driver thật sự có hợp đồng bảo toàn offset gốc**. Nếu business phải bảo toàn `+07:00` hoặc region ID, phải lưu thông tin ấy vào **cột khác** và kiểm thử riêng.

## 7. Demo thuần Java: same instant nhưng khác offset

Lưu thành **`JdbcTimeZoneSemanticsDemo.java`**:

~~~java
import java.time.OffsetDateTime;
import java.time.ZoneOffset;

public class JdbcTimeZoneSemanticsDemo {
    public static void main(String[] args) {
        OffsetDateTime input =
                OffsetDateTime.parse(
                        "2025-02-01T12:34:56.123456+07:00");

        OffsetDateTime utc =
                input.withOffsetSameInstant(ZoneOffset.UTC);

        System.out.println("input=" + input);
        System.out.println("utc=" + utc);
        System.out.println("sameInstant="
                + input.toInstant().equals(utc.toInstant()));
        System.out.println("equals=" + input.equals(utc));
    }
}
~~~

~~~bash
javac -encoding UTF-8 JdbcTimeZoneSemanticsDemo.java
java JdbcTimeZoneSemanticsDemo
~~~

**Stdout đã xác minh trên JDK:**

~~~text
input=2025-02-01T12:34:56.123456+07:00
utc=2025-02-01T05:34:56.123456Z
sameInstant=true
equals=false
~~~

**Giải thích:** `withOffsetSameInstant` đổi biểu diễn offset và giờ local để giữ **chính xác một instant**, còn `equals` của OffsetDateTime quan tâm tới local date-time và offset. Đây là cơ sở để viết round-trip test `TIMESTAMP WITH TIME ZONE` đúng semantics thay vì so chuỗi.

**Lưu ý:** Demo chưa truy cập database, nên nó chứng minh hành vi `java.time` chứ không chứng minh bất cứ driver JDBC nào đã chuẩn hóa UTC đúng cách.

## 8. DST gap và overlap: test trước khi vào database

Một `LocalDateTime` **không chứa đủ thông tin** để luôn chọn được đúng instant tại các khu vực thay đổi giờ mùa hè (DST).

Có ba trường hợp:

- **Normal:** một offset hợp lệ.
- **Gap:** không có offset hợp lệ (đồng hồ nhảy tới tương lai).
- **Overlap:** hai offset hợp lệ (đồng hồ quay lùi, cùng một giờ xuất hiện hai lần).

Với `America/New_York` trong năm 2025:

~~~text
2025-03-09 02:30  -> DST gap, không có offset hợp lệ
2025-11-02 01:30  -> DST overlap, có hai offset hợp lệ
~~~

### 8.1. Test ZoneRules.getValidOffsets

Lưu thành **`DstBoundaryDemo.java`**:

~~~java
import java.time.LocalDateTime;
import java.time.ZoneId;

public class DstBoundaryDemo {
    public static void main(String[] args) {
        ZoneId zone =
                ZoneId.of("America/New_York");

        LocalDateTime gap =
                LocalDateTime.of(2025, 3, 9, 2, 30);

        LocalDateTime overlap =
                LocalDateTime.of(2025, 11, 2, 1, 30);

        System.out.println("gapOffsets="
                + zone.getRules().getValidOffsets(gap));

        System.out.println("overlapOffsets="
                + zone.getRules().getValidOffsets(overlap));

        System.out.println("gapAtZone="
                + gap.atZone(zone));

        System.out.println("overlapAtZone="
                + overlap.atZone(zone));
    }
}
~~~

~~~bash
javac -encoding UTF-8 DstBoundaryDemo.java
java DstBoundaryDemo
~~~

**Stdout theo tzdb chứa quy tắc lịch sử US DST 2025 (đã kiểm chứng trên JDK):**

~~~text
gapOffsets=[]
overlapOffsets=[-04:00, -05:00]
gapAtZone=2025-03-09T03:30-04:00[America/New_York]
overlapAtZone=2025-11-02T01:30-04:00[America/New_York]
~~~

**Giải thích:**

1. `getValidOffsets(gap)` trả danh sách rỗng, vì 02:30 không tồn tại trong ngày nhảy giờ.
2. `getValidOffsets(overlap)` trả hai offset, vì 01:30 đã xảy ra hai lần.
3. `LocalDateTime.atZone(zone)` dùng quy tắc điều chỉnh mặc định: gap thường được đẩy qua khoảng không tồn tại, overlap chọn offset đầu theo quy tắc API.
4. Đó là **quy tắc chuyển đổi của Java**, không tự là chính sách đúng cho hệ thống thanh toán/đặt lịch.

**Cách viết test chắc chắn:** Nếu nghiệp vụ không chấp nhận giờ không tồn tại hoặc mơ hồ, kiểm tra `getValidOffsets` trước và **từ chối/chọn offset tường minh**. Đừng vô tình để JDBC hoặc `atZone` quyết định một chính sách quan trọng.

**Tính ổn định:** Timezone database được cập nhật theo luật từng nước. Với những fixture phụ thuộc chính sách lịch sử, ghi lại tzdb/JDK version trong CI; đừng lấy thời điểm tương lai nhiều năm và giả định quy tắc sẽ không bao giờ đổi.

## 9. Precision: Java nanosecond, SQL có thể chỉ microsecond

`LocalTime`, `LocalDateTime`, `OffsetDateTime` trong Java có phần **nanosecond** từ 0 đến 999.999.999.

Các cột temporal trong database có **precision** khác nhau:

| Precision | Phần giây lưu được | Ví dụ |
|---|---|---|
| `0` | Tới giây | `.000000000` |
| `3` | Tới millisecond | `.123000000` |
| `6` | Tới microsecond | `.123456000` |
| `9` | Tới nanosecond nếu engine hỗ trợ | `.123456789` |

**PostgreSQL hiện đại lưu `timestamp` và `time` với độ phân giải microsecond** và hỗ trợ `p` từ 0 tới 6. Java có thể tạo 9 chữ số; không được kỳ vọng `TIMESTAMP(6)` round-trip được mọi nano chính xác.

Database khác có quy tắc khác. **Đừng áp độ phân giải PostgreSQL cho SQL Server, Oracle, MySQL, SQLite hoặc H2** mà chưa kiểm tra kiểu cột/driver cụ thể.

### 9.1. Trường hợp round-trip exact

Đầu vào `LocalDateTime` có nano `123_456_000` đã **căn đúng microsecond**, nên nếu cột `TIMESTAMP(6)` và driver hoạt động đúng contract, giá trị có thể được round-trip chính xác.

~~~java
LocalDateTime aligned =
        LocalDateTime.of(
                2025, 1, 2, 3, 4, 5,
                123_456_000);
~~~

### 9.2. Trường hợp không exact vì precision

Đầu vào `123_456_789` nano **không trùng ranh giới microsecond**:

~~~java
LocalDateTime notAligned =
        LocalDateTime.of(
                2025, 1, 2, 3, 4, 5,
                123_456_789);
~~~

Nếu lưu vào cột chỉ cho 6 chữ số phần giây, hệ thống cần **làm tròn, cắt bớt hoặc áp một policy khác theo engine/schema/driver**. Test phải định nghĩa expected bằng đúng quy tắc thật được hỗ trợ.

**Không kiểm thử bằng `assertEquals(input, output)` rồi gọi đó là lỗi JDBC** nếu schema không đủ precision để bảo toàn input.

### 9.3. Trường hợp gần đổi giây/ngày

~~~text
23:59:59.999999500
~~~

Với một quy tắc làm tròn tới microsecond, giá trị có thể chuyển sang **giây tiếp theo**. Điều này đặc biệt quan trọng ở sát nửa đêm hoặc sát năm mới.

Test nên có:

- `00:00:00.000000000`.
- `00:00:00.000000001`.
- `12:34:56.123456000` (aligned).
- `12:34:56.123456789` (không aligned).
- `23:59:59.999999000` (aligned cuối microsecond).
- `23:59:59.999999500` (gần ranh giới làm tròn).
- Một thời điểm trước 1970 hoặc số giây âm.

**Quy tắc expected của trường hợp không aligned phải dựa trên database/driver thật, không suy đoán.**

## 10. Demo precision thuần Java và policy làm tròn

Lưu thành **`PrecisionPolicyDemo.java`**:

~~~java
import java.math.BigDecimal;
import java.math.RoundingMode;
import java.time.LocalDateTime;
import java.time.temporal.ChronoUnit;

public class PrecisionPolicyDemo {
    public static void main(String[] args) {
        LocalDateTime value =
                LocalDateTime.parse(
                        "2025-01-02T03:04:05.123456789");

        System.out.println("nanos="
                + value.getNano());

        System.out.println("micros="
                + value.truncatedTo(ChronoUnit.MICROS));

        System.out.println("millis="
                + value.truncatedTo(ChronoUnit.MILLIS));

        BigDecimal a = new BigDecimal("1.0");
        BigDecimal b = new BigDecimal("1.00");

        System.out.println("numericEqual="
                + (a.compareTo(b) == 0));

        System.out.println("objectEqual="
                + a.equals(b));

        BigDecimal half = new BigDecimal("1.005");

        System.out.println("halfEven="
                + half.setScale(2, RoundingMode.HALF_EVEN));

        System.out.println("halfUp="
                + half.setScale(2, RoundingMode.HALF_UP));
    }
}
~~~

~~~bash
javac -encoding UTF-8 PrecisionPolicyDemo.java
java PrecisionPolicyDemo
~~~

**Stdout đã kiểm chứng:**

~~~text
nanos=123456789
micros=2025-01-02T03:04:05.123456
millis=2025-01-02T03:04:05.123
numericEqual=true
objectEqual=false
halfEven=1.00
halfUp=1.01
~~~

**Giải thích:**

- `truncatedTo(MICROS)` **cắt bớt** 789 nanosecond thấp, không thực hiện một phép round tùy ý.
- `truncatedTo(MILLIS)` giữ ba chữ số phần giây.
- `BigDecimal("1.0").compareTo(BigDecimal("1.00")) == 0` vì giá trị số bằng nhau.
- `equals` còn xét scale, nên hai object trên không equal.
- `HALF_EVEN` và `HALF_UP` khác nhau ở tie `1.005` nếu làm tròn scale=2.

**Đừng tự cho rằng PostgreSQL `NUMERIC(12,2)` hoặc một SQL driver nào đó sẽ dùng HALF_EVEN chỉ vì Java code của bạn dùng HALF_EVEN.** Chính sách làm tròn bên database phải được kiểm tra hoặc chuẩn hóa ở ứng dụng **trước khi insert**.

## 11. Precision của NUMERIC và DECIMAL cũng cần test

JDBC 4.2 thường được thảo luận cùng `java.time`, nhưng bài kiểm thử **precision** không nên quên giá trị thập phân như số tiền, tỷ lệ hay đại lượng đo.

Ví dụ schema:

~~~sql
amount NUMERIC(12, 2)
~~~

Ý nghĩa là **precision 12 chữ số thập phân tổng cộng**, **scale 2 chữ số sau dấu phẩy**.

Những input nên thử:

| Input Java | Điều cần kiểm tra |
|---|---|
| `new BigDecimal("0.00")` | Giá trị 0 và scale |
| `new BigDecimal("-0.01")` | Giá trị âm nhỏ |
| `new BigDecimal("1234.50")` | Round-trip thông thường |
| `new BigDecimal("1.005")` | Quy tắc làm tròn hay báo lỗi |
| `new BigDecimal("9999999999.99")` | Sát ranh giới NUMERIC(12,2) |
| `new BigDecimal("10000000000.00")` | Vượt precision, kiểm tra DB rejection |
| `null` | SQL NULL với cột nullable |

Dùng:

~~~java
PreparedStatement ps = connection.prepareStatement(
        "INSERT INTO amounts (amount) VALUES (?)");

ps.setBigDecimal(1, new BigDecimal("1234.50"));
~~~

Đây là **đoạn minh họa**, cần bảng/schema tương ứng và đóng tài nguyên.

**Không dùng `new BigDecimal(0.1)` để tạo một expected số tiền 0.10**, vì `double` 0.1 không biểu diễn chính xác. Dùng `new BigDecimal("0.10")` hoặc `BigDecimal.valueOf(0.1)` theo semantics mong muốn.

**Khi assert:**

- Nếu nghiệp vụ chỉ cần **giá trị số bằng nhau**, dùng `compareTo()==0`.
- Nếu schema/API yêu cầu **cả scale phải bằng**, assert `scale()` riêng hoặc dùng `equals` khi appropriate.
- Nếu dữ liệu có thể bị làm tròn/cắt theo DDL, xác định trước policy thay vì dùng một epsilon “đại khái” cho tiền.

## 12. SQL NULL: giá trị vắng mặt khác giá trị mặc định

Một giá trị SQL **`NULL`** không phải:

- Số nguyên `0`.
- `false`.
- Chuỗi rỗng `""`.
- Một timestamp ở Unix epoch.
- `LocalDate.MIN`.
- `Instant.EPOCH`.
- Ngày `1970-01-01`.
- `Optional.empty()` một cách tự động khi JDBC đang trả object.

Với kiểu object phù hợp, `ResultSet.getObject(...)` trả **Java `null`** nếu dữ liệu SQL là NULL theo hợp đồng conversion. Nhưng với getter primitive như `getInt`, giá trị trả về có thể là `0` khi SQL NULL; cần gọi **`wasNull()` ngay sau lần get đó** để biết kết quả thật.

### 12.1. Ghi NULL có kiểu rõ ràng

~~~java
try (PreparedStatement ps =
         connection.prepareStatement(
                 "INSERT INTO readings (event_at) VALUES (?)")) {

    ps.setNull(1, java.sql.Types.TIMESTAMP);
    ps.executeUpdate();
}
~~~

Đây là **đoạn minh họa** có `Connection connection` và bảng `readings`.

Cũng có thể dùng:

~~~java
ps.setObject(1, null, java.sql.Types.TIMESTAMP);
~~~

Nếu muốn dùng overload nhận `SQLType`:

~~~java
ps.setObject(1, null, java.sql.JDBCType.TIMESTAMP);
~~~

**Caveat:** Overload `SQLType` được đưa vào JDBC 4.2 dưới dạng **default method** và driver có thể không hỗ trợ một conversion/overload cụ thể, ném `SQLFeatureNotSupportedException`. Đừng mặc định mọi driver hỗ trợ tương đương; `setNull(index, Types.X)` là lựa chọn rõ ràng và phổ biến cho SQL NULL.

**Không ưu tiên `setObject(index, null)` không khai báo type nếu cần tính portable.** Oracle API của PreparedStatement lưu ý một số database không chấp nhận untyped NULL.

### 12.2. Đọc object NULL

~~~java
LocalDateTime value =
        rs.getObject("event_at", LocalDateTime.class);

if (value == null) {
    // SQL NULL: không có thời điểm.
}
~~~

Đây là đoạn minh họa có ResultSet được định vị ở một hàng. **Không thay null bằng LocalDateTime.MIN** nếu nghiệp vụ không định nghĩa sentinel này.

### 12.3. Đọc primitive NULL và wasNull

~~~java
int number = rs.getInt("attempts");
boolean sqlWasNull = rs.wasNull();

if (sqlWasNull) {
    // number == 0 nhưng đó không phải số 0 thực tế.
}
~~~

**`wasNull()` phải được gọi ngay sau getter cần kiểm tra**, trước khi đọc cột khác. Nó báo trạng thái của **getter gần nhất**, không gắn vĩnh viễn vào một tên cột.

### 12.4. Test nên phân biệt ít nhất ba trạng thái

1. Cột nullable có giá trị non-NULL.
2. Cột nullable chứa SQL NULL.
3. Cột NOT NULL khi cố insert NULL (kỳ vọng database từ chối theo constraint).

Nếu có default value trong DDL, thêm case **bỏ hoàn toàn cột khỏi INSERT**: đó là hành vi khác với gửi explicit NULL.

## 13. Ngày nhuận, năm không nhuận và dữ liệu biên

Những ca quan trọng:

| Tình huống | Giá trị test | Kỳ vọng phía Java |
|---|---|---|
| Ngày nhuận hợp lệ | `2024-02-29` | Parse thành công |
| Ngày nhuận không hợp lệ | `2025-02-29` | `DateTimeParseException` |
| Năm 1900 không nhuận | `1900-02-29` | Bị từ chối |
| Năm 2000 nhuận | `2000-02-29` | Hợp lệ |
| Trước Unix epoch | `1969-12-31T23:59:59Z` | Instant âm theo epoch seconds |
| Sát nửa đêm | `23:59:59.999999...` | Test precision và chuyển ngày |
| DST gap | `2025-03-09T02:30`, New York | 0 valid offsets |
| DST overlap | `2025-11-02T01:30`, New York | 2 valid offsets |
| LocalDate/LocalDateTime quá lớn | Năm 1,000,000 hoặc gần `MAX` | Phải test **phạm vi DB**, không mặc định lưu được |
| Năm BC / năm 0 | Domain có thể cần | Cần test lịch, SQL syntax và driver riêng |
| Leap second `23:59:60` | Parser/input đặc biệt | Không giả định SQL engine và Java đều xử lý giống nhau |

**Không lấy giới hạn của `LocalDate.MAX` hay `Instant.MAX` làm giới hạn của mọi cột SQL.** Database temporal types thường có miền nhỏ hơn, khác hệ quy chiếu hoặc xử lý infinity sentinel riêng. Cần kiểm tra DDL và tài liệu engine thực dùng.

### 13.1. PostgreSQL infinity là trường hợp chuyên biệt

PostgreSQL có giá trị temporal `infinity` và `-infinity`. pgJDBC có mapping sentinel riêng cho một số kiểu. Đây là dữ liệu **đặc thù PostgreSQL**, không phải điều JDBC 4.2 chung yêu cầu.

Nếu schema sử dụng các giá trị này, viết integration tests riêng: đọc, ghi, so sánh, JSON serialization, điều kiện query và báo cáo. **Không tự suy mọi driver hoặc ORM đều dùng cùng sentinel**.

### 13.2. Không biến `1970-01-01` thành NULL

Nếu dataset có cả `NULL` và ngày 1970-01-01 thực sự, code dùng sentinel có thể làm mất thông tin. Dùng object nullable/Optional ở tầng domain nếu đó là contract; JDBC getter vẫn trả `null` khi SQL NULL.

## 15. Chọn phép so sánh theo ý nghĩa dữ liệu

Không dùng một assertion chung cho mọi SQL type.

| Kiểu mong đợi | Assertion thường đúng | Assertion thường sai |
|---|---|---|
| `LocalDate` | `expected.equals(actual)` | So timestamp epoch millis khi không cần |
| `LocalTime` | `expected.equals(actual)` nếu precision đủ | So tới nano khi cột chỉ lưu 6 chữ số |
| `LocalDateTime` | `expected.equals(actual)` nếu không có conversion và precision đủ | Tự gắn default timezone rồi so instant |
| `OffsetDateTime` | `expected.toInstant().equals(actual.toInstant())` nếu cùng precision | `expected.equals(actual)` khi DB chuẩn hóa offset |
| `Instant` qua adapter phù hợp | `expected.equals(actualInstant)` nếu precision đủ | `getObject(..., Instant.class)` nếu driver không hỗ trợ |
| `BigDecimal` | `expected.compareTo(actual)==0` nếu chỉ cần numeric value | `equals` khi scale có thể khác |
| SQL NULL | `actual == null`, hoặc primitive getter + `wasNull()` | `actual.equals(...)`, gán default mù |
| Temporal đã làm tròn | So expected đã chuẩn hóa theo **policy rõ ràng** | Giữ nguyên nano nguồn rồi kết luận DB hỏng |

**Không dùng tolerance quá rộng để che lỗi timezone**. Lệch đúng một giờ hay bảy giờ thường là sai timezone, không phải precision. Một phép tolerance 24 giờ có thể khiến test không phát hiện được lỗi nghiêm trọng.

**Không dùng `toString()` làm cơ sở duy nhất cho assert** nếu formatting/offset/session có thể đổi mà instant vẫn đúng. Thực hiện assert trực tiếp trên kiểu dữ liệu đã được định nghĩa.

## 16. Một integration test PostgreSQL thật — không yêu cầu framework ngoài JDBC driver

Đây là bài test end-to-end **có thể chạy trên Java 17+** khi bạn có:

- PostgreSQL instance test được phép tạo **temporary table**.
- Driver PostgreSQL JDBC được đưa vào classpath.
- Biến môi trường `JDBC_URL`, `JDBC_USER`, `JDBC_PASSWORD`.

**Không chạy với database production.** Chỉ dùng môi trường test. Chương trình tạo bảng tạm và dùng một transaction để cô lập; cuối cùng `rollback()` dù thành công hay lỗi. Giá trị test đã được căn **đúng microsecond** để có expected chính xác trên PostgreSQL `TIMESTAMP(6)`.

Lưu thành **`Jdbc42PgTemporalProbe.java`**:

~~~java
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.Statement;
import java.sql.Types;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;
import java.time.OffsetDateTime;

public class Jdbc42PgTemporalProbe {
    static void check(boolean valid, String message) {
        if (!valid) {
            throw new AssertionError(message);
        }
    }

    public static void main(String[] args) throws Exception {
        String url = System.getenv("JDBC_URL");

        if (url == null || url.isBlank()) {
            System.out.println("SKIP: JDBC_URL is not set");
            return;
        }

        String user =
                System.getenv().getOrDefault("JDBC_USER", "");

        String password =
                System.getenv().getOrDefault("JDBC_PASSWORD", "");

        LocalDate date =
                LocalDate.of(2024, 2, 29);

        LocalTime time =
                LocalTime.of(23, 59, 59, 123_456_000);

        LocalDateTime local =
                LocalDateTime.of(
                        2025, 1, 2,
                        3, 4, 5, 123_456_000);

        OffsetDateTime instantValue =
                OffsetDateTime.parse(
                        "2025-02-01T12:34:56.123456+07:00");

        BigDecimal amount =
                new BigDecimal("1234.50");

        try (Connection connection =
                     DriverManager.getConnection(
                             url, user, password)) {

            connection.setAutoCommit(false);

            try {
                try (Statement statement =
                             connection.createStatement()) {

                    statement.execute(
                            "CREATE TEMP TABLE jdbc42_probe ("
                            + "id INTEGER PRIMARY KEY,"
                            + "d DATE,"
                            + "t TIME(6),"
                            + "ts TIMESTAMP(6),"
                            + "tz TIMESTAMP(6) WITH TIME ZONE,"
                            + "nullable_ts TIMESTAMP(6),"
                            + "amount NUMERIC(12,2)"
                            + ") ON COMMIT DROP");
                }

                try (PreparedStatement statement =
                             connection.prepareStatement(
                                     "INSERT INTO jdbc42_probe "
                                     + "(id,d,t,ts,tz,nullable_ts,amount) "
                                     + "VALUES (?,?,?,?,?,?,?)")) {

                    statement.setInt(1, 1);
                    statement.setObject(2, date);
                    statement.setObject(3, time);
                    statement.setObject(4, local);
                    statement.setObject(5, instantValue);
                    statement.setNull(6, Types.TIMESTAMP);
                    statement.setBigDecimal(7, amount);

                    check(statement.executeUpdate() == 1,
                            "Insert failed");
                }

                for (String zone : new String[] {
                        "UTC", "Asia/Ho_Chi_Minh"
                }) {
                    // Zone chỉ đến từ danh sách cố định ở code test.
                    try (Statement statement =
                                 connection.createStatement()) {

                        statement.execute(
                                "SET LOCAL TIME ZONE '" + zone + "'");
                    }

                    try (PreparedStatement statement =
                                 connection.prepareStatement(
                                         "SELECT d,t,ts,tz,"
                                         + "nullable_ts,amount "
                                         + "FROM jdbc42_probe WHERE id=?")) {

                        statement.setInt(1, 1);

                        try (ResultSet rs =
                                     statement.executeQuery()) {

                            check(rs.next(), "Missing row");

                            check(date.equals(
                                    rs.getObject(
                                            "d", LocalDate.class)),
                                    "DATE changed");

                            check(time.equals(
                                    rs.getObject(
                                            "t", LocalTime.class)),
                                    "TIME changed");

                            check(local.equals(
                                    rs.getObject(
                                            "ts", LocalDateTime.class)),
                                    "TIMESTAMP changed");

                            OffsetDateTime fromDb =
                                    rs.getObject(
                                            "tz",
                                            OffsetDateTime.class);

                            check(fromDb != null,
                                    "timestamptz is null");

                            check(instantValue.toInstant().equals(
                                    fromDb.toInstant()),
                                    "Instant changed");

                            LocalDateTime nullValue =
                                    rs.getObject(
                                            "nullable_ts",
                                            LocalDateTime.class);

                            check(nullValue == null && rs.wasNull(),
                                    "SQL NULL mapping failed");

                            BigDecimal fromDbAmount =
                                    rs.getBigDecimal("amount");

                            check(fromDbAmount != null
                                    && amount.compareTo(
                                            fromDbAmount) == 0,
                                    "NUMERIC value changed");

                            check(!rs.next(), "Unexpected row");

                            System.out.println("PASS zone=" + zone);
                        }
                    }
                }
            } finally {
                connection.rollback();
            }
        }
    }
}
~~~

### 16.2. Vì sao dùng bảng tạm và rollback?

- `CREATE TEMP TABLE ... ON COMMIT DROP` là cú pháp **PostgreSQL**, không phải SQL portable cho mọi DB.
- `setAutoCommit(false)` tạo transaction cho một bài test.
- `finally { connection.rollback(); }` tránh để test gây thay đổi persistent, kể cả khi assert thất bại.
- Tài nguyên Connection, Statement, PreparedStatement, ResultSet được đóng qua **try-with-resources**.
- `SET LOCAL TIME ZONE` đổi session timezone **trong transaction hiện tại**, không áp dụng cấu hình toàn server.
- Insert dùng bind parameters (`?`) thay vì nối dữ liệu động vào SQL.

### 16.3. Kỹ thuật test qua hai session timezones

Mỗi vòng:

1. Đổi session timezone.
2. Đọc `DATE` → `LocalDate`.
3. Đọc `TIME(6)` → `LocalTime`.
4. Đọc `TIMESTAMP(6)` → `LocalDateTime`.
5. Đọc `TIMESTAMP(6) WITH TIME ZONE` → `OffsetDateTime`.
6. So sánh **instant**, không bắt buộc offset gốc.
7. Đọc `nullable_ts` và assert Java null.
8. Đọc `NUMERIC(12,2)` bằng `BigDecimal`, so giá trị số.

Nếu một case thất bại, cần log **driver version, JDK, database version, schema, session timezone** và exception; không “fix” bằng cách đổi toàn bộ app sang default timezone hiện tại.

### 16.4. Tại sao không test trực tiếp Instant.class?

pgJDBC chính thức hỗ trợ **`OffsetDateTime` cho `TIMESTAMP WITH TIME ZONE`**. Không có cam kết tương tự cho `ResultSet.getObject(..., Instant.class)` trong mapping công bố. Vì vậy integration test chọn kiểu được hỗ trợ rồi chuyển `.toInstant()`.

**Không hiểu nhầm test chuyên PostgreSQL thành test portable JDBC cho tất cả database.** Với Oracle Database/SQL Server/MySQL, viết một adapter/contract suite tương ứng và xác nhận mapping theo tài liệu driver thật.

## 17. Mở rộng integration test cho precision không aligned

Test chính dùng nano `123_456_000` để bảo toàn chính xác trong `TIMESTAMP(6)`. Để tìm hiểu hành vi mất precision, thêm case riêng:

~~~java
LocalDateTime input =
        LocalDateTime.parse(
                "2025-01-02T03:04:05.123456789");

// Bind input bằng PreparedStatement.setObject(...).
// Sau khi đọc lại cột TIMESTAMP(6):
LocalDateTime actual =
        rs.getObject("ts", LocalDateTime.class);

int returnedNanos = actual.getNano();

if (returnedNanos % 1_000 != 0) {
    throw new AssertionError(
            "Unexpected sub-microsecond precision");
}
~~~

Đây là **đoạn mở rộng minh họa**, cần SQL/Connection/ResultSet đang dùng. Nó kiểm tra giá trị được đọc từ một cột PostgreSQL microsecond-aligned, **không tự áp một expected cụ thể** rằng `123456789` chắc chắn sẽ bị cắt thành `123456000` hay làm tròn thành `123457000`.

### 17.1. Phân biệt test “có mất precision” và test “rounding policy”

- **Precision capacity test:** cột `TIMESTAMP(6)` chỉ bảo toàn tối đa 6 chữ số phần giây, output phải nằm trên lưới microsecond.
- **Rounding policy test:** quan sát các input `.123456499`, `.123456500`, `.123456501`, `.999999500`; assert expected theo chính sách engine/driver đã được kiểm chứng.
- **Boundary carry test:** khi rounding làm thay đổi giây/ngày, kiểm tra **toàn bộ timestamp**, không chỉ `getNano()`.
- **No-silent-loss contract:** nếu nghiệp vụ yêu cầu 9 chữ số, schema `TIMESTAMP(6)` không đáp ứng; phải điều chỉnh schema/storage representation hoặc từ chối input.

Không dùng cùng một expected cho mọi database engine.

### 17.2. Precision của metadata

Có thể xem `ResultSetMetaData.getColumnTypeName`, `getPrecision`, `getScale`, nhưng cách báo metadata đối với temporal types có thể khác driver. Dùng nó để **chẩn đoán** và so với DDL, không thay thế dữ liệu round-trip test.

~~~java
ResultSetMetaData md = rs.getMetaData();

for (int i = 1; i <= md.getColumnCount(); i++) {
    System.out.println(md.getColumnLabel(i)
            + " type=" + md.getColumnTypeName(i)
            + " precision=" + md.getPrecision(i)
            + " scale=" + md.getScale(i));
}
~~~

Đây là đoạn minh họa trong test đang có `ResultSet rs`. Output cụ thể phụ thuộc database/driver và không được đoán sẵn.

## 18. `NULL`, default, empty và zero phải có các case độc lập

Bảng test đề xuất:

| Cột | Trường hợp | Kỳ vọng |
|---|---|---|
| Nullable TIMESTAMP | `setNull(..., Types.TIMESTAMP)` | `getObject(..., LocalDateTime.class) == null` |
| Nullable DATE | `setNull(..., Types.DATE)` | `getObject(..., LocalDate.class) == null` |
| Nullable NUMERIC | `setNull(..., Types.NUMERIC)` | `getBigDecimal(...) == null` |
| Nullable INTEGER | SQL NULL | `getInt(...)` có thể trả 0, **`wasNull()` true** |
| Nullable INTEGER | giá trị 0 thật | `getInt(...) == 0`, **`wasNull()` false** |
| NOT NULL TIMESTAMP | INSERT NULL | SQLException theo constraint |
| Cột có DEFAULT | INSERT không chỉ định cột | Giá trị DEFAULT theo DDL |
| Cột có DEFAULT | INSERT explicit NULL | NULL hoặc constraint error, **không tự giống DEFAULT** |

Một lỗi thường gặp là coi `wasNull()` như một thuộc tính của mọi cột vừa đọc trước đó. Theo JDBC, nó tham chiếu tới **getter gần nhất**. Hãy assert ngay lập tức sau getter bạn cần phân biệt NULL.

### 18.1. Không dùng `Optional` trực tiếp trong ResultSet mapping nếu driver không công bố

JDBC không hứa rằng `getObject("col", Optional.class)` sẽ hoạt động. Đọc Java object nullable rồi chuyển sang Optional ở domain layer:

~~~java
LocalDateTime dbValue =
        rs.getObject("event_at", LocalDateTime.class);

Optional<LocalDateTime> value =
        Optional.ofNullable(dbValue);
~~~

Đây là đoạn minh họa. Với domain cho phép NULL, cách này giữ đúng khả năng vắng mặt mà không tạo giá trị thời gian giả.

## 19. Dữ liệu biên theo schema: không đoán giới hạn chỉ từ Java

Java `LocalDate`/`Instant` có miền rất rộng. SQL engine có thể:

- Giới hạn DATE/TIMESTAMP theo các năm khác nhau.
- Có quy tắc lịch sử (BC/AD) và cách biểu diễn năm 0 riêng.
- Làm tròn hoặc từ chối giá trị ngoài precision/scale.
- Có sentinel riêng như PostgreSQL `infinity`.
- Có kiểu temporal đặc thù chứa zone/local zone semantics khác.
- Chấp nhận hoặc từ chối các literal đặc biệt theo ngữ pháp DB.

**Thiết kế test ở ranh giới thật của cột**:

1. Một giá trị hợp lệ ở gần **min supported**.
2. Min supported chính xác.
3. Một giá trị **ngay ngoài min** nếu biểu diễn được đầu vào.
4. Giá trị hợp lệ ở gần **max supported**.
5. Max supported chính xác.
6. Một giá trị ngay ngoài max.
7. Các giá trị negative, zero, positive liên quan epoch.
8. Năm nhuận và ngày cuối tháng.
9. Fractional seconds sát ngưỡng làm tròn.
10. SQL NULL và constraint NOT NULL.

**Không dùng `LocalDate.MIN`, `Instant.MAX` như expected portable** vì phần lớn DB không có cùng miền Java. Ghi rõ schema/engine/version trước khi test.

### 19.1. Test chuyển ngày khi đổi offset

Giả sử instant gần nửa đêm UTC. Khi hiển thị ở +07:00 hoặc -05:00, **ngày local có thể đổi**.

Với `TIMESTAMP WITH TIME ZONE`, so **instant** để xác nhận giữ mốc thời gian. Nếu API trả ngày theo timezone người dùng, test bổ sung **chuyển Instant sang ZonedDateTime theo ZoneId mà domain chỉ định**, rồi mới so `LocalDate`.

### 19.2. TIME WITHOUT TIME ZONE và DST

Một `LocalTime` riêng không gắn ngày. Không thể kiểm tra một `LocalTime` có hợp lệ trong một DST gap hay không nếu chưa biết **ngày + region timezone**. Do đó test DST thuộc về chuyển đổi `LocalDateTime + ZoneId`, không phải chỉ `TIME` đơn lẻ.

### 19.3. 24:00 và leap second

Một số database có thể chấp nhận literal `24:00:00` hoặc đặc biệt về leap second. Java `LocalTime` không có dạng tương đương chung cho mọi trường hợp này. Nếu dữ liệu domain cần, hãy kiểm thử driver/engine-specific **riêng biệt** và xác định policy normalize/reject; không khẳng định Java và SQL xử lý giống nhau.

## 20. Test suite nên được chạy ở CI thế nào?

Tách theo phạm vi:

**Nhóm unit:** Chạy khi build Java, không cần DB. Bao gồm:

- Same instant / different offset.
- DST gap/overlap với timezone rules.
- `LocalDate` leap-year validity.
- `LocalDateTime` truncation micro/milli.
- BigDecimal rounding policies.
- Negative Instant/epoch.

**Nhóm integration:** Chạy với database test/ephemeral container và JDBC driver thật. Bao gồm:

- Schema đã được migrate giống production.
- INSERT/SELECT `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMP WITH TIME ZONE`.
- Các session timezone khác nhau.
- SQL NULL typed, NOT NULL constraint.
- Precision và range của từng cột.
- Dữ liệu pre-epoch, post-epoch, leap day.
- Metadata và lỗi chuyển đổi unsupported.
- Rounding/truncation theo policy.
- Đảm bảo rollback và cleanup.

**Nhóm compatibility:** Với ứng dụng hỗ trợ nhiều driver versions hoặc nhiều database engines, chạy **cùng một contract matrix** trên từng combination được hỗ trợ; đừng đánh đồng cách xử lý giữa các vendor.

### 20.1. Pin dependency versions

Ghi chính xác:

- JDK vendor/version.
- JDBC driver artifact/version.
- Database engine/version.
- DDL schema version.
- Session timezone và server timezone.
- tzdb version nếu các test phụ thuộc quy tắc timezone.

**Không sử dụng một version từ bài hướng dẫn như thể nó là version thật của dự án.** Lấy metadata và build dependencies hiện tại khi chạy.

### 20.2. Không để test thay đổi cấu hình toàn hệ thống

- Dùng database test, không gọi UPDATE/DELETE trên dữ liệu production.
- Tạo temp table hoặc schema test độc lập.
- Dùng transaction và rollback.
- Đóng Connection/Statement/ResultSet.
- Đổi timezone trong phạm vi session/transaction, không đổi server config.
- Tách JVM process nếu cần kiểm thử default timezone.
- Không làm mất dữ liệu thử nghiệm của worker khác khi chạy CI song song.

## 21. Cách chẩn đoán SQLException

Khi integration test FAIL, log có chọn lọc:

~~~java
catch (SQLException ex) {
    System.err.println("SQLState=" + ex.getSQLState());
    System.err.println("errorCode=" + ex.getErrorCode());
    System.err.println("message=" + ex.getMessage());
    throw ex;
}
~~~

Đây là đoạn minh họa. Mã `SQLState` hữu ích cho nhóm lỗi (type mismatch, constraint, connection...), còn vendor errorCode/chuỗi thông báo có thể thay đổi theo engine/driver. **Không hard-code mọi lỗi ở mọi DB theo một thông điệp exception cụ thể**.

Các nhóm thất bại cần phân loại:

- Driver không hỗ trợ `getObject(..., SomeClass.class)`.
- SQL type không tương thích kiểu Java.
- `NULL` vi phạm NOT NULL.
- Giá trị vượt miền DATE/TIMESTAMP/NUMERIC.
- Precision bị làm tròn/cắt không như contract.
- Session timezone không được set đúng connection.
- JDBC URL hoặc credentials sai.
- Schema trong CI khác production.
- Các connection pool tái sử dụng session có timezone/locale khác dự kiến.

**Không chữa lỗi bằng cách `catch(SQLException){ return null; }`**: nó biến một lỗi dữ liệu/connection thành “không có giá trị”, gây sai nghiệp vụ.

## 22. Kiểm thử tính nhất quán của default JVM timezone

Một integration test chỉ chạy trên máy có JVM UTC có thể bỏ sót lỗi chuyển đổi mặc định.

Một hướng test:

~~~bash
java -Duser.timezone=UTC \
     -cp ".:$PGJDBC_JAR" Jdbc42PgTemporalProbe

java -Duser.timezone=Asia/Ho_Chi_Minh \
     -cp ".:$PGJDBC_JAR" Jdbc42PgTemporalProbe
~~~

Đây là lệnh minh họa trên Linux/macOS với environment JDBC đã thiết lập. Trên Windows PowerShell, dùng `java -Duser.timezone=UTC -cp ".;$env:PGJDBC_JAR" ...`.

**Tại sao chạy process riêng?** Vì biến `user.timezone` trong JVM làm ảnh hưởng các chuyển đổi phụ thuộc default timezone và có thể không an toàn nếu thay trong test chạy song song. Test riêng tránh nhiễu.

**Kỳ vọng hợp lý:** Với mapping JDBC4.2 chuẩn và schema như integration demo, `LocalDateTime` không tự chuyển đổi thành instant chỉ vì default JVM timezone thay đổi; `OffsetDateTime` biểu diễn cùng instant. Nhưng không nên khẳng định với **mọi** driver/version nếu chưa chạy contract suite thật.

## 23. Kiểm thử timezone với database connection pool

Trong production, một Connection thường được lấy từ pool. Một test chạy với một connection mới có thể PASS nhưng vẫn bỏ sót lỗi **session state bị rò giữa các lượt mượn connection**:

1. Test A lấy connection, gọi `SET TIME ZONE`.
2. Trả connection cho pool nhưng không reset session state.
3. Test B mượn lại connection, mặc định nghĩ timezone là UTC.
4. Khi query/chuyển đổi dữ liệu, kết quả có thể bị diễn giải khác.

**Khuyến nghị:** Cấu hình timezone/session state thống nhất ở tầng pool hoặc thiết lập rõ ràng tại điểm mượn kết nối, theo capabilities của driver/pool. Thêm test mượn-trả connection và kiểm tra timezone trước/sau.

**Không dùng `SET TIME ZONE` là một giải pháp phổ quát** vì cú pháp cụ thể khác giữa PostgreSQL, MySQL, Oracle và SQL Server.

## 24. Unit test dựa trên expected đã làm tròn: tránh test giả

Một anti-pattern:

~~~java
// Không đúng nếu cột chỉ giữ microseconds:
LocalDateTime input =
        LocalDateTime.parse(
                "2025-01-02T03:04:05.123456789");

// Ghi vào TIMESTAMP(6), đọc lại rồi assert:
assertEquals(input, actual);
~~~

Đây là đoạn minh họa trong framework unit test, không là chương trình độc lập.

**Sửa theo contract:** Nếu domain chấp nhận precision microsecond, có thể chuẩn hóa input trước khi ghi hoặc expected trước khi so:

~~~java
LocalDateTime normalized =
        input.truncatedTo(ChronoUnit.MICROS);
~~~

Nhưng **đây là chính sách truncation do ứng dụng chọn**, không tự chứng minh database cũng sẽ truncate thay vì round. Hãy xác định chính xác rounding policy và kiểm thử nó; nếu cần cấm dữ liệu vượt precision, validate `input.getNano() % 1_000 == 0` rồi từ chối từ đầu.

### 24.1. Đừng dùng tolerance để che lỗi thiết kế precision

Nếu API hứa giữ **đúng microsecond**, kiểm tra nano phần thấp bằng 0 và so expected micro-aligned. Đừng chỉ assert hai thời điểm cách nhau ít hơn 1 giây — điều đó có thể che cả lỗi sai tính giờ hoặc sai dữ liệu.

### 24.2. Dùng loại assert phù hợp

- `LocalDateTime.equals` trên những giá trị đã căn precision đúng.
- `Instant.equals` hoặc Duration chính xác trên `OffsetDateTime.toInstant()` đã căn precision.
- `BigDecimal.compareTo` khi chỉ quan tâm numeric value.
- `wasNull` ngay sau primitive getter.
- Assertions theo SQL constraints và metadata được tài liệu driver đảm bảo.

## 25. Ma trận kiểm thử tối thiểu cần đạt

| Nhóm | Fixture | Điều kiện PASS |
|---|---|---|
| DATE cơ bản | `2024-02-29` | Round-trip đúng LocalDate |
| DATE non-leap | `2025-02-29` | Bị từ chối tại validation Java hoặc DB theo policy |
| TIME fractional | `23:59:59.123456` | Giữ microseconds với TIME(6) |
| TIMESTAMP no TZ | `2025-01-02T03:04:05.123456` | LocalDateTime giữ trường local như DDL |
| TIMESTAMPTZ offset +07 | `2025-02-01T12:34:56.123456+07:00` | Cùng Instant sau round-trip |
| JVM timezone | UTC / HCM / New York | Không bị lệch ngoài contract |
| Session timezone | UTC / HCM | Instant giữ nguyên, local semantics đúng |
| DST gap | New York 2025-03-09 02:30 | `getValidOffsets` rỗng, domain xử lý rõ |
| DST overlap | New York 2025-11-02 01:30 | Hai offset hợp lệ, chọn theo policy |
| Precision 9→6 | `.123456789` | Mất precision được phát hiện/giải thích đúng |
| Precision rollover | `.999999500` | Kết quả theo rounding policy database, kể cả đổi giây |
| SQL NULL | Nullable timestamp | getObject null, wasNull true khi kiểm tra |
| SQL NOT NULL | Insert NULL | Bị DB từ chối |
| NUMERIC value | `1234.50` | So numeric value chính xác |
| NUMERIC rounding | `1.005` vào NUMERIC(...,2) | Theo policy đã xác nhận |
| NUMERIC bound | Sát/vượt precision | Giá trị hợp lệ PASS, vượt mức bị xử lý đúng |
| Pre-epoch | 1969-12-31 | Không đổi nhầm dấu/thời gian |
| DB range | Min/max theo engine | Kết quả theo đặc tả database thực |
| Unsupported mapping | `Instant.class`, `ZonedDateTime.class` | Không assume support; kiểm tra và xử lý SQLException |
| Cleanup | Sau test lỗi | Không để lại dữ liệu persistent |

**Đừng ép test để “PASS bằng mọi giá” bằng cách bỏ các case khó.** Một test compatibility thất bại có thể chỉ ra driver/schema hiện tại không đáp ứng yêu cầu nghiệp vụ.

## 26. Những lỗi thường gặp

### Lỗi 1 — Nhầm JDBC 4.2 với hỗ trợ mọi java.time class

JDBC 4.2 có mapping chuẩn, nhưng hỗ trợ chuyển đổi chi tiết phụ thuộc driver/version. Không tự cho rằng `Instant`, `ZonedDateTime` hoặc `OffsetTime` luôn tương thích.

### Lỗi 2 — Dùng `LocalDateTime` để biểu diễn thời điểm UTC tuyệt đối

`LocalDateTime` không có offset/zone. Chỉ khi domain quy ước rõ UTC và mọi conversion tuân thủ, nó mới có thể được diễn giải thành Instant.

### Lỗi 3 — So `OffsetDateTime.equals` cho PostgreSQL timestamptz

PostgreSQL/pgJDBC có thể chuẩn hóa offset sang UTC. Nếu yêu cầu bảo toàn instant, so `toInstant`.

### Lỗi 4 — Tưởng `TIMESTAMP WITH TIME ZONE` luôn lưu region ZoneId

PostgreSQL không lưu timezone region gốc. Nếu cần vùng timezone, phải lưu riêng `ZoneId.getId()`.

### Lỗi 5 — Kiểm thử mọi thứ bằng timezone mặc định của laptop

Cần cả JVM default, DB session và dữ liệu offset khác nhau.

### Lỗi 6 — Dùng `TimeZone.setDefault` trong nhiều tests song song

Nó sửa trạng thái toàn cục, gây test flaky. Dùng process riêng hoặc truyền ZoneId.

### Lỗi 7 — Không test DST gap và overlap

Tại giờ DST overlap, một `LocalDateTime` có thể tương ứng hai instant; ở gap có thể không tương ứng instant nào.

### Lỗi 8 — Không phân biệt precision 9 digits và 6 digits

Java nano có thể cao hơn precision SQL. Test round-trip exact chỉ hợp lý với dữ liệu aligned hoặc policy được xác định.

### Lỗi 9 — Giả định mọi database làm tròn giống nhau

Rounding/truncation có thể khác theo engine, cột, driver và conversion path.

### Lỗi 10 — Chỉ kiểm tra phần nano, bỏ qua rollover

Một giá trị gần `.9999995` có thể chuyển sang giây/ngày khác khi round. Test phải đọc toàn timestamp.

### Lỗi 11 — Dùng BigDecimal từ double

`new BigDecimal(0.1)` tạo giá trị theo binary float, không phải decimal 0.1 theo kỳ vọng nghiệp vụ.

### Lỗi 12 — Dùng BigDecimal.equals khi scale không phải contract

`1.0` và `1.00` bằng giá trị số nhưng `equals` false; chọn compareTo hoặc assert scale riêng.

### Lỗi 13 — Nghĩ SQL NULL đồng nghĩa Unix epoch

NULL là vắng mặt; EPOCH là dữ liệu thời gian hợp lệ.

### Lỗi 14 — Ghi null bằng setObject không xác định SQL type

Một số DB không nhận untyped null; dùng setNull hoặc setObject typed.

### Lỗi 15 — Bỏ qua wasNull sau getInt/getLong

Getter primitive có thể trả 0 khi SQL NULL; phải kiểm tra wasNull ngay sau lời gọi.

### Lỗi 16 — Gọi wasNull sau khi đã đọc một cột khác

`wasNull()` nói về **giá trị đọc gần nhất**.

### Lỗi 17 — Giữ một DB connection chung cho các test song song

Connection/transaction/session timezone có thể gây nhiễu. Cô lập test theo pool/connection.

### Lỗi 18 — Dùng một H2/mocked ResultSet thay database mục tiêu và coi là integration PASS

Mock không kiểm tra codec PG/Oracle/MySQL; dùng DB tương ứng khi cần kết luận production.

### Lỗi 19 — Chỉ test ngày tháng năm hiện tại

Không kiểm tra trước epoch, ngày nhuận, cuối tháng, date range và các trường hợp kề ranh giới.

### Lỗi 20 — Coi LocalDate.MAX hoặc Instant.MAX sẽ luôn lưu được

Miền SQL engine có thể hẹp hơn nhiều.

### Lỗi 21 — Không xét PostgreSQL infinity/-infinity nếu schema thực dùng

Sentinels là vendor-specific, cần test riêng; không tự xem như Java time standard.

### Lỗi 22 — Dùng `TIME WITHOUT TIME ZONE` để biểu diễn instant

Nó thiếu ngày và offset; không đủ thông tin.

### Lỗi 23 — Gắn ZoneId tùy tiện cho time-only

DST phụ thuộc ngày và region; một LocalTime không cho biết mapping duy nhất.

### Lỗi 24 — Trộn `TIMESTAMP WITHOUT TIME ZONE` và `WITH TIME ZONE` trong SQL casts

Database có thể diễn giải timestamp local theo session timezone, tạo chuyển dịch instant không dự kiến.

### Lỗi 25 — Truy cập driver-specific SQL temporal types bằng class Java chưa xác nhận support

Tài liệu pgJDBC công bố mapping chính; conversion ngoài mapping cần test explicit.

### Lỗi 26 — Không ghi lại schema/driver/JDK version khi một test fail

Không đủ thông tin để tái hiện sự cố.

### Lỗi 27 — “Sửa” lỗi bằng tolerance 24 giờ

Nó che lỗi timezone nghiêm trọng. Precision cần tolerance rất nhỏ nếu chính sách cho phép, không lẫn timezone offset.

### Lỗi 28 — Không rollback dữ liệu test

Để lại row, thay session state hoặc ảnh hưởng test chạy sau.

### Lỗi 29 — Đặt secrets trực tiếp vào README/test source

Cấu hình DB qua biến môi trường/secret store, tuyệt đối không commit credential thật.

### Lỗi 30 — Bỏ qua tính tương thích version

Một phiên bản driver mới có thể sửa/đổi mapping corner cases; test suite nên được chạy lại khi nâng dependency.

## 28. Bài tập thực hành

### Bài 1 — Same instant, different offset

Dùng `OffsetDateTime.parse("2025-02-01T12:34:56+07:00")`; đổi sang UTC bằng `withOffsetSameInstant`. Vì sao `toInstant` equal nhưng `equals` không equal?

### Bài 2 — SQL types

Chọn Java type cho SQL DATE, TIME, TIMESTAMP WITHOUT TIME ZONE, TIMESTAMP WITH TIME ZONE. Giải thích tại sao `LocalDateTime` chưa xác định instant.

### Bài 3 — Precision

Lưu `2025-01-02T03:04:05.123456789` vào PostgreSQL `TIMESTAMP(6)`. Viết test cho precision capacity mà không mặc định DB truncate. Thêm test rounding ở `.123456500`.

### Bài 4 — Timezone matrix

Chạy integration probe với JVM UTC và HCM, database session UTC và HCM. Khi giá trị `timestamptz` trở về offset Z, assertion nào nên dùng?

### Bài 5 — Null

Tạo bảng có nullable timestamp và nullable integer. Ghi SQL NULL rồi đọc bằng `getObject(..., LocalDateTime.class)` và `getInt` + `wasNull`. Phân biệt NULL với giá trị 0.

### Bài 6 — DST gap

Dùng `ZoneRules.getValidOffsets` với New York 2025-03-09T02:30. Nếu hệ thống lịch hẹn không cho phép giờ không tồn tại, bạn sẽ phản hồi người dùng thế nào?

### Bài 7 — DST overlap

Kiểm thử New York 2025-11-02T01:30. Nếu ứng dụng cần biết người dùng chọn lần xuất hiện nào, nên lưu thêm thông tin gì?

### Bài 8 — Database range

Tìm giới hạn DATE/TIMESTAMP của database đang dùng. Viết 6 test boundary: min, min−1, min+1, max, max−1, max+1 (chỉ tạo input nếu phía Java biểu diễn được).

### Bài 9 — Decimal scale

So `BigDecimal("1.0")` với `BigDecimal("1.00")`. Viết test NUMERIC(12,2) với `1.005`, xác định rounding policy database và kiểm tra thay vì đoán.

### Bài 10 — Negative epoch

Vì sao `Instant.ofEpochSecond(-1, 999_999_999).toEpochMilli()` trả `-1`, không phải `0`? Bài test nào phát hiện sai lầm nếu code tự chia/cắt về 0?

### Bài 11 — Driver mapping

Thử `rs.getObject("ts", Instant.class)` với driver hiện dùng trong một integration test có xử lý SQLException; đối chiếu tài liệu driver. Thiết kế adapter đọc từ OffsetDateTime rồi chuyển toInstant khi type được hỗ trợ.

### Bài 12 — Connection pool

Thiết kế test mượn-trả hai connections từ pool, đổi session timezone trên connection thứ nhất, rồi đảm bảo connection thứ hai không bị ảnh hưởng ngoài contract cấu hình pool.

### Bài 13 — Không để lại dữ liệu test

Viết integration test tạo temporary table, setAutoCommit(false), dùng try-with-resources và rollback trong finally. Thêm một assertion cố ý fail để kiểm tra cleanup.

### Bài 14 — Special values

Nếu PostgreSQL schema cho phép `infinity`, cần test mapping và serialization thế nào? Vì sao không dùng expected của PostgreSQL để đánh giá tất cả database khác?

## 29. Câu hỏi ôn tập và đáp án

**1. JDBC 4.2 có từ Java nào?** — Java 8.

**2. API nào phổ biến để bind java.time?** — `PreparedStatement.setObject`.

**3. API nào phổ biến để đọc typed java.time?** — `ResultSet.getObject(column, SomeClass.class)` khi driver hỗ trợ.

**4. SQL DATE thường map sang gì?** — `LocalDate`.

**5. SQL TIME WITHOUT TIME ZONE thường map sang gì?** — `LocalTime`.

**6. SQL TIMESTAMP WITHOUT TIME ZONE thường map sang gì?** — `LocalDateTime`.

**7. SQL TIMESTAMP WITH TIME ZONE thường đọc thành gì trên pgJDBC?** — `OffsetDateTime`.

**8. Có nên tự cho rằng getObject(..., Instant.class) luôn chạy không?** — Không; phụ thuộc driver.

**9. PostgreSQL timestamptz lưu nguyên ZoneId đầu vào không?** — Không.

**10. OffsetDateTime.equals có bằng khi chỉ khác offset nhưng cùng instant không?** — Không.

**11. Khi cần kiểm tra cùng instant thì so gì?** — `toInstant().equals(...)` nếu precision cho phép.

**12. LocalDateTime có mang timezone không?** — Không.

**13. DST gap có bao nhiêu offset hợp lệ?** — 0.

**14. DST overlap thường có bao nhiêu offset hợp lệ?** — 2.

**15. Java time có phần giây nano tới mấy chữ số?** — 9.

**16. PostgreSQL timestamp/time có độ phân giải thường mấy chữ số?** — Microsecond, 6 chữ số.

**17. TIMESTAMP(6) có bảo toàn `.123456789` không?** — Không thể bảo toàn mọi nano ngoài 6 chữ số; cần xác định rounding/truncation.

**18. `BigDecimal("1.0").equals(BigDecimal("1.00"))`?** — false.

**19. `compareTo` của hai giá trị trên?** — 0.

**20. SQL NULL và Instant.EPOCH có giống nhau không?** — Không.

**21. Nên bind NULL kiểu temporal ra sao?** — `setNull(index, Types.TIMESTAMP)` hoặc một typed alternative được driver hỗ trợ.

**22. Getter primitive có thể trả gì cho SQL NULL?** — Giá trị mặc định primitive như 0; phải dùng `wasNull()`.

**23. Khi nào gọi wasNull?** — Ngay sau getter muốn kiểm tra.

**24. Năm 1900 có ngày 29/2 không?** — Không theo lịch Gregorian; Java LocalDate từ chối.

**25. Năm 2000 có ngày 29/2 không?** — Có.

**26. `Instant.ofEpochSecond(-1,999999999).toEpochMilli()` là bao nhiêu?** — -1.

**27. Có nên dùng `LocalDate.MAX` làm test hợp lệ portable cho SQL DATE không?** — Không; DB range khác Java.

**28. Database test với mock có xác nhận PostgreSQL driver codec không?** — Không.

**29. Integration example có thật sự chứng minh DB PASS khi không thiết lập JDBC_URL không?** — Không; nó in SKIP.

**30. Vì sao chạy nhiều JVM timezones trong processes riêng?** — Tránh shared global state và phát hiện default timezone assumptions.

## 30. Tổng kết

**Kiểm thử JDBC 4.2 đúng nghĩa là kiểm thử hợp đồng chuyển đổi giữa Java types, SQL types, driver, database và cấu hình timezone/precision/null.** Một test chỉ INSERT một timestamp hiện tại rồi SELECT ra không đủ để xác nhận hệ thống an toàn.

Những nguyên tắc cần nhớ:

1. `LocalDate`, `LocalTime`, `LocalDateTime` không tự mang timezone/instant.
2. `OffsetDateTime` đủ thông tin để xác định instant, nhưng offset gốc **không phải lúc nào được database bảo toàn**.
3. Đặc biệt trên PostgreSQL, `timestamptz` giữ instant và pgJDBC có thể trả `OffsetDateTime` ở UTC; so sánh `toInstant`.
4. DST gap/overlap phải được đưa vào policy và test; không để một chuyển đổi mặc định quyết định ý nghĩa nghiệp vụ.
5. Java có precision nanosecond, SQL schema/engine có thể thấp hơn; test theo **precision thật và rounding policy**.
6. SQL NULL phải được giữ là **không có giá trị**, không tự đổi thành epoch/0. Dùng typed setNull/getObject và wasNull đúng.
7. Test ngày nhuận, pre-epoch, ranh giới giờ/ngày, min/max database và numeric precision/scale.
8. `BigDecimal.compareTo()` thích hợp cho numeric equality, còn `equals()` xét cả scale.
9. Tách unit tests thuần Java và integration tests dùng **database + JDBC driver thật**.
10. Dùng transaction/temp table/rollback và quản lý connection lifecycle để không làm bẩn môi trường.
11. Ghi lại JDK, driver, database, DDL và timezone khi QA; chạy lại suite khi nâng dependency.
12. **Không khẳng định hành vi của một driver là bảo đảm phổ quát cho mọi database.**
