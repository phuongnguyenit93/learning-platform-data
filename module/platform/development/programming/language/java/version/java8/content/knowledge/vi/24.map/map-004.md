# `Map.remove(key, value)` và `replace` có điều kiện (Java 8+)

Trong Java, một `Map<K,V>` lưu các cặp **khóa → giá trị**. Nhiều trường hợp nghiệp vụ không muốn xóa hoặc ghi đè một khóa một cách vô điều kiện: chỉ xóa khi giá trị còn đúng như dự kiến; chỉ chuyển trạng thái đơn hàng từ `PENDING` sang `RUNNING` nếu chưa có tác vụ khác đổi nó; hoặc chỉ thay giá trị khi khóa đã tồn tại.

Java 8 bổ sung ba thao tác trực tiếp trong `Map`:

- **`remove(key, expectedValue)`:** xóa mapping **chỉ nếu** khóa đang có giá trị bằng `expectedValue`.
- **`replace(key, newValue)`:** thay giá trị **chỉ nếu khóa đang tồn tại**, không yêu cầu giá trị cũ cụ thể.
- **`replace(key, expectedOldValue, newValue)`:** thay giá trị **chỉ nếu** khóa đang có giá trị bằng `expectedOldValue`.

Các phương thức này vẫn là API được hỗ trợ ở Java hiện đại. Cần phân biệt **điều kiện khi cập nhật** với **tính nguyên tử trong đa luồng**: phiên bản default trong `Map` **không bảo đảm atomicity/synchronization**; những implementation như `ConcurrentHashMap` cung cấp thao tác so khớp và cập nhật **nguyên tử đối với một khóa** theo hợp đồng `ConcurrentMap`.

## 1. Chữ ký, điều kiện và kiểu trả về

```java
// Các chữ ký API trong java.util.Map<K, V> (Java 8+):
default boolean remove(Object key, Object value);

default V replace(K key, V value);

default boolean replace(K key, V oldValue, V newValue);
```

Bảng so sánh:

| Lời gọi | Điều kiện để thay đổi map | Hành động khi khớp | Kiểu trả về |
| --- | --- | --- | --- |
| `remove(key, value)` | Khóa **có trong map** và giá trị hiện tại bằng `value` | Xóa mapping | `boolean`: `true` nếu đã xóa |
| `replace(key, newValue)` | Khóa **có trong map** | Ghi giá trị mới cho khóa đó | `V`: giá trị **trước khi thay**, hoặc `null` |
| `replace(key, oldValue, newValue)` | Khóa **có trong map** và giá trị hiện tại bằng `oldValue` | Ghi `newValue` | `boolean`: `true` nếu đã thay |
| `remove(key)` | Chỉ cần khóa có trong map | Xóa mapping không so sánh giá trị | `V`: giá trị trước khi xóa, hoặc `null` |
| `put(key, value)` | Không có điều kiện tồn tại/giá trị cũ | Thêm hoặc ghi đè mapping | `V`: giá trị trước khi thêm/ghi đè, hoặc `null` |

**Chú ý:** `replace(key, newValue)` và `replace(key, oldValue, newValue)` khác nhau ở **số lượng tham số và hợp đồng**. Dạng hai tham số không phải là "so sánh giá trị cũ"; dạng ba tham số mới so sánh giá trị cũ mong đợi.

Không nhầm `Map.remove(Object,Object)` với `Collection.removeIf(Predicate)`: `remove(key,value)` tác động **một mapping cụ thể** khi đúng cặp khóa/giá trị, không duyệt và loại mọi entry thỏa một predicate.

### Ví dụ nhỏ

```java
Map<String, String> status = new HashMap<>();
status.put("order-1", "PENDING");

boolean wrong = status.remove("order-1", "DONE");     // false
boolean right = status.remove("order-1", "PENDING");   // true
boolean again = status.remove("order-1", "PENDING");   // false
```

Kết quả: chỉ lời gọi thứ hai xóa mapping. Nếu chỉ dùng `remove("order-1")`, mapping sẽ bị xóa bất kể giá trị hiện tại đã đổi thành gì.

## 2. Hai phần của điều kiện: khóa **tồn tại** và giá trị **bằng nhau**

Theo hợp đồng `Map`, lời gọi `remove(key, value)` chỉ trả `true` khi map chứa khóa và giá trị tương ứng so khớp với giá trị mong đợi. Cách hiểu tương đương về ngữ nghĩa của **default method**:

```java
// Mô phỏng ý nghĩa, KHÔNG thay thế lời gọi API:
if (map.containsKey(key) && Objects.equals(map.get(key), expected)) {
    map.remove(key);
    return true;
}
return false;
```

`Objects.equals(a,b)` so sánh bằng `equals` và an toàn khi một/hai tham số là `null`; không phải so **địa chỉ tham chiếu** bằng `==`.

Ví dụ:

```java
Map<String, String> values = new HashMap<>();
values.put("A", "PENDING");

String anotherInstance = new String("PENDING");
boolean removed = values.remove("A", anotherInstance);
// true: hai String có nội dung bằng nhau, dù không phải cùng object.
```

Đoạn mã tạo `new String(...)` chỉ để minh họa ngữ nghĩa `equals`; trong ứng dụng thông thường không nên chủ động tạo đối tượng String thừa.

**So sánh khóa** cũng theo ngữ nghĩa của implementation `Map`:

- `HashMap` / `LinkedHashMap` dựa trên `hashCode` và `equals` của khóa.
- `TreeMap` dựa vào `Comparator` hoặc `Comparable` để nhận diện khóa tương đương trong cây. Hai khóa có `compare(a,b) == 0` được xem là cùng vị trí map theo thứ tự cây, dù `equals` của đối tượng có thể khác. Comparator nên phù hợp quy tắc nhận diện khóa của nghiệp vụ.
- **So sánh `expectedOldValue`** trong `replace(key, old, new)` vẫn là so sánh giá trị theo `equals`, không phải điều kiện tùy ý như "số tiền lớn hơn 100".

### Trường hợp giá trị `null`: không được lẫn với khóa vắng mặt

Một số map, như `HashMap` và `LinkedHashMap`, cho phép ánh xạ một khóa tới `null`:

```java
Map<String, String> states = new HashMap<>();
states.put("A", null);

System.out.println(states.containsKey("A")); // true
System.out.println(states.get("A"));          // null
System.out.println(states.containsKey("B")); // false
System.out.println(states.get("B"));          // null
```

`get(...)` trả `null` trong **cả hai trường hợp**, nhưng `containsKey(...)` phân biệt được. Điều này ảnh hưởng các thao tác có điều kiện:

```java
boolean removedAbsent = states.remove("B", null); // false
boolean removedNull   = states.remove("A", null); // true
```

Với `replace(key,newValue)`, giá trị trả về `null` cũng mơ hồ:

```java
Map<String, String> nullable = new HashMap<>();
nullable.put("slot", null);

String old = nullable.replace("slot", "READY");  // old == null
String missed = nullable.replace("missing", "READY"); // missed == null

System.out.println(nullable.get("slot"));          // READY
System.out.println(nullable.containsKey("missing")); // false
```

Lời gọi thứ nhất **đã thực hiện thay thế** vì `slot` có mapping, dù trả về `null`. Lời gọi thứ hai **không thêm khóa mới**. Nếu cần xác định kết quả một cách rõ ràng, kiểm tra trạng thái phù hợp với hợp đồng và môi trường concurrency; đừng suy từ một giá trị trả về `null` rằng chắc chắn không có cập nhật.

Với `ConcurrentHashMap`, **khóa và giá trị `null` không được phép**. Do đó không dùng các ví dụ `null` ở trên trực tiếp với map loại này; tùy chữ ký và tham số, nó sẽ ném `NullPointerException`.

## 3. `remove(key, value)`: chỉ xóa mapping khớp kỳ vọng

Trường hợp điển hình là xóa một mục chỉ khi nó **vẫn đang ở trạng thái hoặc phiên bản đã quan sát**.

```java
Map<String, String> orderStates = new HashMap<>();
orderStates.put("order-42", "CANCELLED");

boolean deleted = orderStates.remove("order-42", "CANCELLED");
// true: mapping khớp giá trị mong đợi và đã bị xóa.
```

Một số tình huống:

| Trạng thái map | Lời gọi | Kết quả |
| --- | --- | --- |
| `{"job"="PENDING"}` | `remove("job", "PENDING")` | `true`, khóa bị xóa |
| `{"job"="RUNNING"}` | `remove("job", "PENDING")` | `false`, dữ liệu giữ nguyên |
| Không có khóa `"job"` | `remove("job", "PENDING")` | `false` |
| `{"job"=null}` ở map hỗ trợ null | `remove("job", null)` | `true`, khóa bị xóa |
| Không có khóa `"job"` | `remove("job", null)` | `false` |

Điểm hơn `remove(key)` là **không xóa một giá trị mới mà caller không mong đợi**. Tuy nhiên, với `HashMap` thông thường đang bị nhiều luồng thay đổi không đồng bộ, lời gọi này **không mặc nhiên là một compare-and-remove nguyên tử**. Phải phân biệt hợp đồng điều kiện logic với bảo đảm thực thi đồng thời (mục 7).

### "Expected value" có thể là đối tượng, nhưng cần hiểu ý nghĩa so khớp

`Map.remove(key, expectedValue)` kiểm tra **`equals` của giá trị**. Nếu giá trị là một đối tượng nghiệp vụ có thể thay đổi, hai instance có thể bằng nhau theo `equals` dù có phiên bản/sự kiện khác nhau; ngược lại, nếu lớp không override `equals` thì phép so có thể dựa vào identity.

Trong các quy trình chống ghi đè dữ liệu cũ, nên thiết kế giá trị **bất biến** hoặc một trạng thái/version có ngữ nghĩa `equals` rõ ràng. Chỉ so với một chuỗi trạng thái "PENDING" không thể bảo vệ mọi tình huống nếu một công việc đã chuyển `PENDING → RUNNING → PENDING` giữa hai lần quan sát (**vấn đề ABA**); xem thêm mục 8.

## 4. `replace(key, newValue)`: chỉ ghi đè khi **khóa đã tồn tại**

Đây là cách khác với `put`: nó không tạo mới khóa khi chưa có mapping.

```java
Map<String, Integer> limits = new HashMap<>();
limits.put("standard", 10);

Integer old = limits.replace("standard", 20); // 10
Integer missed = limits.replace("premium", 50); // null

System.out.println(limits); // {standard=20}
```

Trong ví dụ, `premium` không được tự thêm vào. `replace(key,newValue)` phù hợp khi chương trình muốn **cập nhật một mục có sẵn nhưng không quan tâm giá trị cũ là gì**.

Nhưng **không phù hợp** nếu nghiệp vụ đòi "chỉ cập nhật khi giá trị vẫn là 10". Khi đó dùng:

```java
boolean changed = limits.replace("standard", 10, 30);
// false, vì giá trị hiện tại đã là 20.
```

Nếu có nhiều luồng, `replace(key,newValue)` trên `ConcurrentMap` vẫn có thể **ghi đè một giá trị mới do tác vụ khác vừa cập nhật**, bởi nó chỉ kiểm tra sự tồn tại của khóa. Bảo đảm nguyên tử của một phép thay không đồng nghĩa bảo vệ *giá trị cũ kỳ vọng*. Dùng dạng ba tham số khi cần điều kiện so khớp phiên bản/trạng thái.

## 5. `replace(key, oldValue, newValue)`: cập nhật có điều kiện

Dạng ba tham số thực hiện một phép **so khớp và thay giá trị** theo điều kiện cụ thể.

```java
Map<String, String> jobStates = new HashMap<>();
jobStates.put("job-7", "PENDING");

boolean first = jobStates.replace("job-7", "PENDING", "RUNNING");
// true: job-7 chuyển sang RUNNING

boolean stale = jobStates.replace("job-7", "PENDING", "FAILED");
// false: trạng thái hiện tại không còn PENDING

System.out.println(jobStates.get("job-7")); // RUNNING
```

Dạng này trả `boolean`: `true` nếu có mapping khớp và đã thực hiện phép thay; `false` nếu khóa vắng mặt hoặc giá trị cũ không khớp. Không nhầm với việc kiểm tra `oldValue == newValue`: nếu cả hai giá trị cùng bằng trạng thái hiện tại, phép thay có thể vẫn trả `true` vì điều kiện khớp dù nội dung trông không đổi.

### Dùng như một bước chuyển trạng thái có bảo vệ

Giả sử một task có thể từ `PENDING` sang `RUNNING`, nhưng chỉ một worker được phép giành quyền xử lý. Với cấu trúc dữ liệu **concurrent** phù hợp:

```java
ConcurrentMap<String, String> jobs = new ConcurrentHashMap<>();
jobs.put("task-17", "PENDING");

// Nhiều worker có thể chạy dòng này:
// Chỉ worker thay được PENDING -> RUNNING mới nhận true.
boolean claimed = jobs.replace("task-17", "PENDING", "RUNNING");

if (claimed) {
    // Worker này đã đổi mapping thành RUNNING tại thời điểm update.
    // Tiếp tục logic xử lý có quản lý lỗi/timeout/retry phù hợp.
}
```

Đoạn này là ví dụ minh họa và cần `import java.util.concurrent.*;`. Với `ConcurrentHashMap`, phép thay cặp giá trị được thực hiện **nguyên tử đối với khóa đó**. Nếu hai worker đồng thời thử cùng một `oldValue` trên cùng khóa mà không có thay đổi nào khác, không thể cả hai cùng thành công khi trạng thái không quay về giá trị cũ ở giữa.

**Giới hạn:** kết quả `true` chỉ chứng minh phép cập nhật map đã thành công. Nó **không** tự giao dịch với database, message broker hay tác vụ bên ngoài; cần thiết kế xử lý thất bại, lease/version/timeout và idempotency nếu làm hàng đợi công việc thực tế.

### Giá trị `null` trong replace ba tham số

Trên `HashMap` hoặc `LinkedHashMap` (cho phép null):

```java
Map<String, String> settings = new HashMap<>();
settings.put("theme", null);

boolean changed = settings.replace("theme", null, "dark");
// true: khóa có tồn tại và giá trị cũ == null.

boolean missing = settings.replace("locale", null, "vi_VN");
// false: không hề có khóa locale.
```

Trong cả hai lời gọi, điều kiện **khóa tồn tại** vẫn bắt buộc. Với `ConcurrentHashMap`, không truyền giá trị mới/giá trị cũ `null` theo cách đó: implementation không hỗ trợ null trong map và có các kiểm tra `NullPointerException`.

## 6. Các thao tác gần giống nhưng không tương đương

| Ý định | API phù hợp | Khác biệt cần nhớ |
| --- | --- | --- |
| Xóa bất kể giá trị hiện tại | `remove(key)` | Không đối chiếu expected value |
| Xóa khi bằng giá trị dự kiến | `remove(key, expected)` | Boolean; không xóa giá trị khác |
| Ghi đè hoặc thêm mới | `put(key, value)` | Có thể tạo mapping mới |
| Chỉ cập nhật khóa đã tồn tại | `replace(key, newValue)` | Không kiểm tra giá trị cũ cụ thể |
| Chỉ cập nhật khi giá trị cũ khớp | `replace(key, old, new)` | Boolean, điều kiện cụ thể |
| Chỉ thêm khi chưa có giá trị | `putIfAbsent(key, value)` | Với `Map` mặc định, mapping tới null cũng được coi như chưa có giá trị |
| Tính lại giá trị theo hàm nếu key đã có value khác null | `computeIfPresent(key, fn)` | Đưa giá trị cũ vào hàm, có thể cập nhật/xóa theo kết quả |
| Cập nhật/tính giá trị cho một key | `compute(key, fn)` | Hàm được gọi cả khi mapping chưa có, hoặc có nhưng value null |
| Hợp nhất giá trị hiện có với value đầu vào | `merge(key, value, fn)` | Hữu ích cho cộng dồn, ghép kết quả, cần value đầu vào khác null |
| Cập nhật tất cả giá trị | `replaceAll((key,value) -> ...)` | Duyệt nhiều mapping; không phải replace có điều kiện trên một key |

**Ví dụ `putIfAbsent`:**

```java
Map<String, String> config = new HashMap<>();
config.put("env", "prod");
config.put("locale", null);

config.putIfAbsent("env", "dev");      // vẫn là "prod"
config.putIfAbsent("locale", "vi");    // từ null thành "vi"
config.putIfAbsent("missing", "new"); // tạo khóa mới
```

`putIfAbsent` không có nghĩa chỉ hoạt động nếu `containsKey(key) == false` trên mọi implementation; `Map` cho phép null thì mapping có value null cũng thỏa điều kiện đặt giá trị.

**Ví dụ `computeIfPresent`:** Khi điều kiện chuyển đổi phụ thuộc vào một thuộc tính số thay vì một expected value cố định:

```java
Map<String, Integer> stock = new HashMap<>();
stock.put("pen", 5);

stock.computeIfPresent("pen", (key, old) ->
    old > 0 ? old - 1 : old);
// "pen" trở thành 4.
```

`computeIfPresent` chỉ gọi hàm khi key có giá trị hiện tại **khác null**. Nếu hàm trả `null`, API có thể xóa mapping theo hợp đồng. Trên `HashMap` thường, không có bảo đảm nguyên tử khi các luồng sửa đồng thời; với `ConcurrentHashMap` có chính sách atomic update tương ứng. Không nên để remapping function tự thao tác thêm/xóa **cùng map đang được compute** nếu không hiểu rõ ràng buộc của implementation.

Khi chỉ cần so sánh một trạng thái cụ thể, `replace(key, old, new)` đơn giản và rõ nghĩa hơn `computeIfPresent`.

## 7. Điều kiện logic không đồng nghĩa atomicity: `Map` và `ConcurrentMap`

### Với `HashMap` thông thường

Hợp đồng **default implementation** của `Map.remove(key,value)` và `Map.replace(...)` nêu rõ: **không bảo đảm synchronization hoặc atomicity**. Ví dụ logic:

```java
// Minh họa ý tưởng, không dùng như thao tác concurrent:
if (map.containsKey("task-17")
        && Objects.equals(map.get("task-17"), "PENDING")) {
    map.put("task-17", "RUNNING");
}
```

Có một **cửa sổ race** giữa kiểm tra và ghi: luồng khác có thể thay đổi mapping khiến kết quả không đúng kỳ vọng. Việc gom logic vào một lời gọi `replace(key,old,new)` trên `HashMap` không tự khiến việc dùng map **không thread-safe** trở nên an toàn.

`HashMap` thích hợp khi được sở hữu bởi một luồng, không có thay đổi đồng thời, hoặc chương trình đã bảo vệ truy cập bằng khóa đồng bộ/thiết kế ownership nhất quán. Không dùng kết quả thử nghiệm nhỏ để kết luận tự động an toàn đa luồng.

### Với `ConcurrentMap` / `ConcurrentHashMap`

`ConcurrentMap` yêu cầu các thao tác `remove(key,value)` và `replace(...)` hoạt động nguyên tử theo hợp đồng. `ConcurrentHashMap` triển khai các operation này, cho phép sử dụng như một bước **compare-and-remove** hoặc **compare-and-replace** trên **một khóa**.

```java
ConcurrentMap<String, String> states = new ConcurrentHashMap<>();
states.put("job", "PENDING");

boolean first = states.replace("job", "PENDING", "RUNNING"); // true
boolean later = states.replace("job", "PENDING", "FAILED"); // false
```

Cả hai lời gọi tạo một kết quả hợp lý khi chưa có tác vụ ngoài thay đổi lại mapping thành `PENDING` giữa chúng. Với nhiều luồng thực sự, thứ tự của các thao tác độc lập không được đảm bảo, nhưng **mỗi lần compare-and-replace được thực hiện nguyên tử**.

**Nguyên tử trên một mapping không phải giao dịch nhiều khóa:**

```java
// Không có đảm bảo "all-or-nothing" tự động giữa hai khóa:
boolean a = states.replace("job-A", "PENDING", "RUNNING");
boolean b = states.replace("job-B", "PENDING", "RUNNING");
```

Nếu `a == true` và `b == false`, mapping A đã thay nhưng B không thay. Muốn cập nhật nhiều khóa cùng nhau hoặc phối hợp với database phải sử dụng mô hình giao dịch/khóa thích hợp, không thể dựa vào riêng một map concurrent.

### Atomic compare-and-replace vẫn có thể gặp vấn đề ABA

Giả sử một luồng đọc trạng thái `PENDING`, công việc khác chuyển `PENDING → RUNNING → PENDING`, rồi luồng đầu thực hiện `replace(key, "PENDING", "RUNNING")` thành công. Điều kiện giá trị khớp **không cho biết đã từng có thay đổi ở giữa**.

Nếu cần phát hiện trạng thái đã đổi dù quay về cùng giá trị, thiết kế value có **version tăng đơn điệu**, timestamp/sequence theo hợp đồng nghiệp vụ hoặc một cấu trúc bất biến chứa cả trạng thái và version. Sau đó thực hiện compare-and-replace trên **giá trị cũ có chứa version**, với `equals` được định nghĩa nhất quán.

Không dùng mutable object thay đổi trường nội bộ "âm thầm" rồi mong phép `replace` phát hiện: `replace` kiểm tra **mapping value** qua phép so sánh, không theo dõi lịch sử biến đổi bên trong object.

## 8. Khi nhiều luồng cùng tăng một giá trị

Với `ConcurrentHashMap`, mẫu sau **không** an toàn về logic cộng dồn mặc dù mỗi `get`/`put` riêng lẻ là thread-safe:

```java
// Không dùng để cập nhật cùng khóa từ nhiều luồng:
Integer old = counters.get("views");
counters.put("views", old + 1);
```

Hai luồng có thể cùng đọc 10, rồi đều ghi 11, khiến một lần tăng bị mất (**lost update**).

Khi khóa **được khởi tạo từ trước** và **không bị xóa** trong lúc chạy, một vòng lặp compare-and-replace giải quyết vấn đề:

```java
ConcurrentMap<String, Integer> counters = new ConcurrentHashMap<>();
counters.put("views", 0);

IntStream.range(0, 1_000).parallel().forEach(i -> {
    for (;;) {
        Integer observed = counters.get("views");
        if (counters.replace("views", observed, observed + 1)) {
            break;
        }
        // Giá trị đã đổi, đọc lại và thử với expected value mới.
    }
});
// counters.get("views") == 1000.
```

Điều kiện của ví dụ: khóa `views` đã tồn tại, value luôn khác null, số lượt tăng không làm tràn `Integer` và không có tác vụ nào xóa khóa khi vòng lặp chạy. Dạng `replace(key, old, new)` chỉ thay mapping nếu giá trị **vẫn bằng old tại thời điểm thao tác**, nên các lần tăng không bị ghi đè theo mẫu get-then-put sai. Đây là mô hình **compare-and-swap style** về ngữ nghĩa, không phải yêu cầu API phải thực hiện bằng một chỉ thị CAS phần cứng cụ thể.

**Trong ứng dụng thật**, khi chỉ cần cộng theo khóa, các lựa chọn này thường ngắn và phù hợp hơn:

```java
counters.merge("views", 1, Integer::sum);
// Hoặc sử dụng LongAdder với cấu trúc dữ liệu và lối dùng phù hợp.
```

Với tải cập nhật rất cao, cân nhắc `LongAdder` theo từng khóa và đo mức tranh chấp; việc lấy tổng `sum()` trong khi đang có cập nhật đồng thời không nhất thiết là snapshot nguyên tử. Đừng dùng vòng lặp retry không giới hạn khi nghiệp vụ yêu cầu timeout, fairness hoặc một giới hạn contention rõ ràng.

## 9. Dùng với map không cho sửa và hiểu ngoại lệ

Các lời gọi `remove`/`replace` là **optional operations** của `Map`. Một biến khai báo `Map<K,V>` không chứng minh instance bên trong cho phép sửa.

| Map / cách tạo | Cho phép thay đổi? | Lưu ý |
| --- | --- | --- |
| `new HashMap<>()` | Có | Cho phép null key/value; không thread-safe |
| `new LinkedHashMap<>()` | Có | Thứ tự chèn xác định, không thread-safe |
| `new TreeMap<>()` | Có | Khóa sắp theo comparator/natural order; chính sách null phụ thuộc comparator |
| `new ConcurrentHashMap<>()` | Có | Cập nhật concurrent; không cho null key/value |
| `Collections.unmodifiableMap(backing)` | Không thông qua wrapper | Là **unmodifiable view**; thay đổi backing map qua đường khác vẫn có thể phản ánh vào view |
| `Map.of(...)` | Không | Java 9+, không cho null keys/values |
| `Map.copyOf(map)` | Không | Java 10+, trả map không cho sửa; không cho null keys/values |

Ví dụ:

```java
Map<String, String> readOnly =
    Collections.unmodifiableMap(new HashMap<String, String>());

readOnly.replace("A", "READY"); // UnsupportedOperationException có thể ném.
```

Với một số phương thức của map không cho sửa, exception có thể xuất hiện ngay cả khi thao tác sẽ không thay đổi dữ liệu. Không thử "kiểm tra bằng cách replace/remove" để dò tính mutable nếu chưa hiểu hợp đồng. Nếu cần một bản sao **có thể chỉnh sửa**:

```java
Map<String, String> editable = new HashMap<>(readOnly);
editable.put("A", "READY");
```

Các ngoại lệ khác có thể gặp:

- `NullPointerException` nếu map không chấp nhận tham số `null` hoặc đối số có tính chất `null` bị cấm. `ConcurrentHashMap` không nhận khóa hoặc giá trị null.
- `ClassCastException` với kiểu khóa/giá trị không phù hợp mà implementation từ chối; `TreeMap` có thể ném khi không so sánh được khóa.
- `IllegalArgumentException` nếu implementation có ràng buộc đặc thù với khóa/giá trị.
- `UnsupportedOperationException` nếu map/view không hỗ trợ thay đổi.
- Không có bảo đảm chung mọi thao tác `Map` default là một giao dịch có rollback khi một phần logic tự viết bị exception.

**Thứ tự duyệt:** `HashMap` không cam kết thứ tự in mapping; dùng `LinkedHashMap` trong chương trình ví dụ để stdout ổn định. `TreeMap` duyệt khóa theo comparator; không nhầm thứ tự duyệt với điều kiện so khớp giá trị trong `replace`.

## 10. Chương trình Java hoàn chỉnh, chạy được

Tạo file **`MapConditionalUpdatesDemo.java`**. Chương trình chỉ dùng API Java 8; có thể biên dịch/chạy trên JDK 17+ mà không cần thư viện bên ngoài. Ví dụ minh họa cả map thường hỗ trợ null và `ConcurrentHashMap` không nhận null, với đầu ra xác định.

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.stream.IntStream;

public class MapConditionalUpdatesDemo {
    public static void main(String[] args) {
        Map<String, String> states = new LinkedHashMap<>();
        states.put("A", "PENDING");
        states.put("B", "READY");
        states.put("C", null);

        System.out.println("remove wrong: " + states.remove("A", "READY"));
        System.out.println("remove match: " +
                states.remove("A", new String("PENDING")));
        System.out.println("remove missing null: " +
                states.remove("MISSING", null));
        System.out.println("remove mapped null: " +
                states.remove("C", null));
        System.out.println("after removals: " + states);

        System.out.println("replace mismatch: " +
                states.replace("B", "PENDING", "DONE"));
        System.out.println("replace match: " +
                states.replace("B", "READY", "DONE"));
        System.out.println("after conditional replace: " + states);
        System.out.println("replace previous: " +
                states.replace("B", "ARCHIVED"));
        System.out.println("replace absent: " +
                states.replace("UNKNOWN", "CREATED"));
        System.out.println("after replace: " + states);

        states.put("NULL_SLOT", null);
        String previous = states.replace("NULL_SLOT", "ASSIGNED");
        System.out.println("replace mapped null old: " + previous);
        System.out.println("replace mapped null new: " +
                states.get("NULL_SLOT"));
        System.out.println("putIfAbsent existing: " +
                states.putIfAbsent("B", "IGNORED"));
        System.out.println("putIfAbsent new: " +
                states.putIfAbsent("NEW", "CREATED"));
        System.out.println("current states: " + states);

        ConcurrentMap<String, String> job = new ConcurrentHashMap<>();
        job.put("job-7", "PENDING");
        System.out.println("job transition: " +
                job.replace("job-7", "PENDING", "RUNNING"));
        System.out.println("stale transition: " +
                job.replace("job-7", "PENDING", "FAILED"));
        System.out.println("job state: " + job.get("job-7"));

        ConcurrentMap<String, Integer> counters = new ConcurrentHashMap<>();
        counters.put("views", 0);
        IntStream.range(0, 1_000).parallel().forEach(i -> {
            for (;;) {
                Integer observed = counters.get("views");
                if (counters.replace("views", observed, observed + 1)) {
                    break;
                }
            }
        });
        System.out.println("views after parallel updates: " +
                counters.get("views"));

        Map<String, String> locked =
                Collections.unmodifiableMap(new LinkedHashMap<>(states));
        try {
            locked.remove("B", "ARCHIVED");
        } catch (UnsupportedOperationException ex) {
            System.out.println("unmodifiable: UnsupportedOperationException");
        }
    }
}
```

Lệnh chạy:

```bash
javac -encoding UTF-8 MapConditionalUpdatesDemo.java
java MapConditionalUpdatesDemo
```

Kết quả chuẩn:

```text
remove wrong: false
remove match: true
remove missing null: false
remove mapped null: true
after removals: {B=READY}
replace mismatch: false
replace match: true
after conditional replace: {B=DONE}
replace previous: DONE
replace absent: null
after replace: {B=ARCHIVED}
replace mapped null old: null
replace mapped null new: ASSIGNED
putIfAbsent existing: ARCHIVED
putIfAbsent new: null
current states: {B=ARCHIVED, NULL_SLOT=ASSIGNED, NEW=CREATED}
job transition: true
stale transition: false
job state: RUNNING
views after parallel updates: 1000
unmodifiable: UnsupportedOperationException
```

Giải thích:

1. `remove("A","READY")` không khớp; `remove("A", new String("PENDING"))` khớp theo **`String.equals`**, xóa A.
2. `remove("MISSING", null)` là `false` vì khóa vắng mặt; `remove("C", null)` là `true` vì mapping C→null tồn tại.
3. `replace("B","PENDING","DONE")` trả `false` khi B đang là READY; `replace("B","READY","DONE")` chuyển thành công. Dạng hai tham số tiếp đó trả giá trị cũ `DONE` khi đổi B sang ARCHIVED.
4. `replace("UNKNOWN","CREATED")` không tạo khóa mới, nên trả `null`.
5. Mapping `NULL_SLOT → null` có tồn tại; `replace("NULL_SLOT","ASSIGNED")` trả `null` (giá trị cũ) **nhưng đã thay đổi mapping**.
6. `putIfAbsent` giữ B=ARCHIVED và thêm NEW=CREATED; `LinkedHashMap` giúp thứ tự các mục trong output ổn định.
7. `ConcurrentHashMap.replace(key,old,new)` cho phép chuyển `job-7` từ PENDING sang RUNNING, nhưng từ chối lần chuyển cũ tiếp theo.
8. Một nghìn lần tăng trong parallel stream dùng vòng lặp compare-and-replace đối với một khóa đã khởi tạo, cho giá trị cuối cùng 1000 mà không đánh rơi cập nhật.
9. Wrapper `Collections.unmodifiableMap` từ chối xóa mapping có sẵn bằng `UnsupportedOperationException`.

Không nên đánh giá hiệu năng parallel chỉ từ demo tăng bộ đếm: ví dụ dùng parallel để **chứng minh đúng đắn của cập nhật có điều kiện**, không hứa nhanh hơn tuần tự.

## 11. Những lỗi hay gặp

| Sai lầm | Hậu quả | Cách làm đúng |
| --- | --- | --- |
| Dùng `remove(key)` khi chỉ muốn xóa một trạng thái cụ thể | Có thể xóa mapping mới hơn mong đợi | `remove(key, expectedValue)` |
| Gọi `replace(key, value)` nhưng tưởng đã so sánh giá trị cũ | Dạng hai tham số chỉ kiểm tra khóa tồn tại | `replace(key, oldValue, newValue)` |
| Coi `replace(key,newValue) == null` đồng nghĩa không cập nhật | Mapping cũ có thể là `null` ở map hỗ trợ null | Hiểu `containsKey` và trạng thái mapping |
| Nghĩ `remove(missing, null)` sẽ xóa thành công vì `get(missing)==null` | Khóa vắng mặt khác khóa có value null | Kiểm tra cả `containsKey` và `Objects.equals` |
| So `expectedValue` bằng `==` | Nhầm object identity với equality | Dựa vào `Objects.equals` và `equals` được thiết kế đúng |
| Dùng `HashMap` thường với nhiều luồng và gọi `replace(key,old,new)` như CAS nguyên tử | Default `Map` không cam kết atomicity | Chọn `ConcurrentHashMap` hoặc đồng bộ phù hợp |
| Viết `if (map.get(k).equals(old)) map.put(k,new)` | Null gây NPE; còn có race giữa đọc và ghi | Dùng overload có điều kiện với implementation phù hợp |
| Dùng `replace(key,value)` khi khóa chưa có và mong nó được thêm | `replace` không insert nếu khóa absent | `put` hoặc `putIfAbsent` theo hợp đồng |
| Truyền null vào `ConcurrentHashMap` | Map này không hỗ trợ null | Dùng giá trị/sentinel có nghĩa hoặc cấu trúc khác |
| Giá trị là mutable object nhưng `equals` không biểu diễn version | Thay đổi nội bộ có thể lọt qua phép so kỳ vọng | Thiết kế value bất biến và version rõ |
| Chuyển trạng thái qua lại nhưng chỉ so status cũ | Có thể gặp ABA | Kèm version/sequence nếu cần phát hiện lịch sử |
| Coi `replace(key,old,new) == true` là giao dịch nhiều khóa | Chỉ bảo đảm cho một phép cập nhật đơn lẻ | Dùng giao dịch hoặc cơ chế đồng bộ rộng hơn |
| Cộng dồn bằng `get` rồi `put` trong `ConcurrentHashMap` | Mất cập nhật do race giữa hai lời gọi | `merge`/`compute` hoặc vòng compare-and-replace |
| Coi `unmodifiableMap` là `HashMap` có thể chỉnh sửa | Wrapper từ chối thao tác ghi | Tạo bản sao có thể sửa nếu có quyền |
| Giả định `HashMap.toString()` luôn có thứ tự cố định | Không có hợp đồng thứ tự duyệt | Dùng `LinkedHashMap`/`TreeMap` khi cần |
| Không kiểm thử null/absent/expected-mismatch | Cập nhật sai hoặc hiểu sai return value | Test rõ mỗi nhánh điều kiện |

## 12. Bài tập thực hành có lời giải

### Bài 1 — Chỉ xóa cấu hình đã xác nhận

Map chứa `"feature-A" → "DISABLED"`. Chỉ xóa mapping khi giá trị còn là `"DISABLED"`:

```java
Map<String, String> flags = new HashMap<>();
flags.put("feature-A", "DISABLED");

boolean removed = flags.remove("feature-A", "DISABLED");
// true; flags không còn "feature-A".
```

Nếu worker khác đã đổi mapping sang `ENABLED` trên một `ConcurrentMap`, phép xóa có điều kiện theo giá trị cũ phải trả `false` thay vì xóa cấu hình đang hoạt động.

### Bài 2 — Chỉ thay khi khóa tồn tại

Cho map `limits` chưa có khóa `"vip"`. `limits.replace("vip", 100)` có thêm khóa không?

**Không.** Dạng hai tham số không tạo mapping nếu absent. Muốn thêm hoặc ghi đè dùng `put("vip",100)`; muốn chỉ thêm khi chưa có value dùng `putIfAbsent`.

### Bài 3 — Chuyển trạng thái có bảo vệ

Giả sử `jobs` là `ConcurrentHashMap<String,String>` với `id-1 → PENDING`. Hai luồng cùng gọi:

```java
jobs.replace("id-1", "PENDING", "RUNNING");
```

Nếu không có tác vụ khác chuyển trạng thái trở lại PENDING, tối đa **một** luồng nhận `true`. Đây là lợi ích của cập nhật nguyên tử trên một khóa. Trong workflow thật, cần quản lý lỗi và cơ chế lease/expiry ngoài map.

### Bài 4 — Hai null khác nhau thế nào?

Trên `HashMap<String,String>`, một khóa A có value null; khóa B không tồn tại. Điều gì xảy ra khi gọi `remove("A",null)` và `remove("B",null)`?

**Đáp án:** A được xóa và trả `true`; B trả `false`. `containsKey` là ranh giới giữa mapping tới null và khóa absent.

### Bài 5 — So khớp giá trị đối tượng

Một map gắn `"name" → new String("Java")`. `remove("name", new String("Java"))` có thành công không?

**Có**, với `String` vì `equals` so nội dung. Không được dùng `==` để suy ra kết quả. Với loại value tự tạo, phải xem lớp có override `equals` hay không.

### Bài 6 — Không tạo race trong kiểm đếm

Trong `ConcurrentHashMap<String,Integer>` đã có `"hits" → 0`, ba luồng cùng làm `get("hits")` rồi `put("hits", old+1)`. Có chắc kết quả bằng 3 không?

**Không.** Các luồng có thể cùng đọc 0 rồi ghi 1. Dùng `merge("hits", 1, Integer::sum)`, `compute` phù hợp hoặc vòng `replace("hits", old, old+1)` có retry. Chỉ dùng vòng lặp như minh họa khi khóa được bảo đảm tồn tại và không bị remove giữa chừng.

## 13. Checklist trước khi sử dụng trong code thực tế

- [ ] Chỉ cần **khóa có mặt** hay phải so **giá trị cũ cụ thể**?
- [ ] Khi xóa, có thật sự muốn xóa mapping dù trạng thái đã đổi không?
- [ ] Đã chọn đúng overload: `remove(key,value)`, `replace(key,newValue)` hoặc `replace(key,old,new)`?
- [ ] Có phân biệt `null` từ mapping hiện có với `null` do khóa absent?
- [ ] Value `equals` có đúng ngữ nghĩa nghiệp vụ và version không?
- [ ] Map có cho phép null key/value không? Có map không cho sửa không?
- [ ] Có nhiều luồng cập nhật đồng thời không? Nếu có, implementation có bảo đảm atomicity phù hợp?
- [ ] Đã xử lý `false` khi expected value không còn đúng, thay vì im lặng cho là cập nhật thành công?
- [ ] Có nguy cơ ABA hoặc cần so version để tránh xử lý trên trạng thái cũ?
- [ ] Nếu thao tác nhiều khóa hoặc nhiều hệ thống, đã có transaction/đồng bộ riêng?
- [ ] Có thể dùng `compute`/`merge` gọn hơn cho bài toán cộng dồn hay điều kiện phức tạp?
- [ ] Đã kiểm thử khóa absent, giá trị null, so khớp/sai giá trị, unmodifiable map và tranh chấp nhiều luồng?

**Ghi nhớ:** `remove(key,value)` giúp **xóa khi giá trị còn khớp**, `replace(key,newValue)` giúp **chỉ thay khóa đã tồn tại**, còn `replace(key,oldValue,newValue)` giúp **chỉ thay khi giá trị hiện tại khớp giá trị mong đợi**. Đối với đa luồng, cần kết hợp đúng implementation như `ConcurrentHashMap` để có nguyên tử theo khóa; method có cùng tên trên một `Map` thông thường **không tự tạo bảo đảm đó**.

### Tài liệu API chính thức còn được duy trì

- [`Map` — Java SE 27](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/util/Map.html): chữ ký, bản default, null, return value và ngoại lệ của `remove(key,value)`, `replace`, `putIfAbsent`, `compute`/`merge`.
- [`ConcurrentMap` — Java SE 26](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/util/concurrent/ConcurrentMap.html): bảo đảm atomicity của các overload remove/replace có điều kiện.
- [`ConcurrentHashMap` — Java SE 26](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html): thực thi nguyên tử và chính sách không cho null.
- [`HashMap` — Java SE 27](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/util/HashMap.html): quy tắc key/value, null và thread-safety.
- [`Collections.unmodifiableMap` — Java SE 27](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/util/Collections.html): view không chỉnh sửa được.
