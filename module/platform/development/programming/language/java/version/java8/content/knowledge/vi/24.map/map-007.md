# Map.compute() trong Java: Khi hàm tính toán trả về null thì điều gì xảy ra?

**Chủ đề:** `Map` — thao tác cập nhật giá trị theo key bằng `compute`. Đây là một **default method** của `java.util.Map` được giới thiệu trong Java 8 và vẫn là API hiện hành trên JDK hiện đại. Các ví dụ hoàn chỉnh dưới đây dùng Java 17+ và làm rõ **hợp đồng của Map**, không dựa vào hành vi tình cờ của một thư viện đã lỗi thời.

**Điểm cần nhớ ngay:** Với `map.compute(key, remappingFunction)`, **nếu hàm remapping trả `null` thì mapping của key đó bị xóa, hoặc tiếp tục vắng mặt nếu từ đầu chưa có mapping**. Trả `null` ở đây **không có nghĩa lưu `key -> null` vào map.

## 1. Vì sao cần `compute`?

Giả sử có `Map<String, Integer>` lưu số lượng sản phẩm theo mã. Khi nhận một sự kiện mới, ta muốn tính giá trị mới dựa trên **key và giá trị đang có**. Cách cũ thường là đọc rồi ghi:

```java
Integer oldValue = counts.get("java");
int next = oldValue == null ? 1 : oldValue + 1;
counts.put("java", next);
```

Đây là **đoạn mã trong phương thức** với biến `counts` kiểu `Map<String, Integer>` đã được khởi tạo. Nó có ba bước và phải tự quyết định giá trị nào được dùng khi key chưa tồn tại. `compute` gói thao tác **lấy giá trị cũ → tính giá trị mới → áp dụng mapping** vào một lời gọi:

```java
counts.compute("java", (key, oldValue) ->
        oldValue == null ? 1 : oldValue + 1);
```

Lambda được gọi với:

- `key`: key đang được tính, ở đây là `"java"`.
- `oldValue`: giá trị đang ánh xạ tới key hoặc `null` nếu **không có giá trị hiện hữu khác null**.
- Giá trị **trả về từ lambda**: quyết định giữ/thay mapping bằng giá trị mới nếu khác null, hoặc xóa/để vắng mặt nếu là null.

**Quan trọng:** `compute` **không tự động đồng nghĩa với an toàn đồng thời** cho mọi loại `Map`. Với `HashMap` hay `LinkedHashMap`, không được dùng nó như phép tăng nguyên tử khi nhiều thread cùng cập nhật; hãy xem phần về `ConcurrentHashMap`.

## 2. Chữ ký và hợp đồng của `Map.compute`

Chữ ký rút gọn:

```java
V compute(
        K key,
        BiFunction<? super K, ? super V, ? extends V> remappingFunction
)
```

Đây là **chữ ký API minh họa**, không phải một phương thức để khai báo lại trong lớp của bạn.

`remappingFunction` nhận hai tham số, `(K key, V oldValue)`, rồi trả về giá trị mới kiểu `V`. Việc gọi `compute` nhằm **tạo, thay thế hoặc loại bỏ một mapping tùy theo kết quả tính toán**.

Hợp đồng cơ bản, khi loại map cho phép các thao tác tương ứng:

1. Hàm remapping được xem xét **cả khi key chưa có mapping**; lúc đó `oldValue == null`.
2. Nếu hàm trả **khác null**, map ghi giá trị mới cho key và `compute` trả về chính giá trị mới.
3. Nếu hàm trả **null**, mapping hiện có bị **xóa**; nếu ban đầu key vắng mặt thì vẫn vắng mặt. `compute` trả `null`.
4. Nếu hàm ném một unchecked exception, ngoại lệ được truyền ra và **mapping hiện tại được giữ nguyên**, với điều kiện hàm không tự sửa map trái hợp đồng.
5. Hàm remapping **không được tự thay đổi chính map đang được tính toán**. Các implementation có thể phát hiện thay đổi đệ quy và ném ngoại lệ; đừng dựa vào việc sửa map từ trong callback.
6. `remappingFunction` bắt buộc khác null. Quy tắc cho phép key `null` phụ thuộc implementation; `HashMap` hỗ trợ key null, còn `ConcurrentHashMap` thì không.

### 2.1. Bảng quyết định quan trọng nhất

| Trạng thái **trước** `compute` | Giá trị `oldValue` truyền vào hàm | Hàm trả về | Trạng thái **sau** |
| --- | --- | --- | --- |
| Chưa có key | `null` | `"new"` | Thêm `key -> "new"` |
| Chưa có key | `null` | `null` | Vẫn chưa có key |
| Có key với giá trị `"old"` | `"old"` | `"new"` | Thay thành `key -> "new"` |
| Có key với giá trị `"old"` | `"old"` | `null` | **Xóa hẳn key** |
| Có key với giá trị **null** trong map cho phép null | `null` | `"new"` | Thay giá trị null bằng `"new"` |
| Có key với giá trị **null** trong map cho phép null | `null` | `null` | **Xóa key đã tồn tại**, không giữ `key -> null` |

Dòng cuối đặc biệt dễ nhầm: `HashMap` có thể chứa mapping `key -> null`, nhưng `compute(key, (k, old) -> null)` không dùng để duy trì mapping null đó. Nó được định nghĩa là **remove**.

## 3. Ví dụ Java 17+ đầy đủ: thêm, sửa, xóa và giữ vắng mặt

Tạo file **`MapComputeDemo.java`**:

```java
import java.util.LinkedHashMap;
import java.util.Map;

public class MapComputeDemo {
    public static void main(String[] args) {
        Map<String, Integer> map = new LinkedHashMap<>();
        map.put("java", 2);
        map.put("legacy", null);

        Integer updated = map.compute(
                "java", (key, oldValue) -> oldValue + 3);

        Integer inserted = map.compute(
                "go", (key, oldValue) ->
                        oldValue == null ? 1 : oldValue + 1);

        Integer removed = map.compute(
                "java", (key, oldValue) -> null);

        Integer absent = map.compute(
                "rust", (key, oldValue) -> null);

        Integer replacedNull = map.compute(
                "legacy", (key, oldValue) ->
                        oldValue == null ? 7 : oldValue + 1);

        System.out.println("updated=" + updated);
        System.out.println("inserted=" + inserted);
        System.out.println("removed=" + removed);
        System.out.println("absent=" + absent);
        System.out.println("legacy=" + replacedNull);
        System.out.println("contains java="
                + map.containsKey("java")
                + ", rust=" + map.containsKey("rust"));
        System.out.println("map=" + map);
    }
}
```

Biên dịch và chạy với JDK 17+:

```bash
javac --release 17 MapComputeDemo.java
java MapComputeDemo
```

**Stdout chính xác:**

```text
updated=5
inserted=1
removed=null
absent=null
legacy=7
contains java=false, rust=false
map={legacy=7, go=1}
```

Giải thích theo từng thao tác:

- `"java"` ban đầu có giá trị 2; callback tính `2 + 3 = 5`, thay giá trị cũ và trả 5.
- `"go"` chưa có mapping nên callback nhận `oldValue == null`, trả 1, thêm `go -> 1`.
- `"java"` tiếp tục được gọi với giá trị 5, nhưng callback cố ý trả `null`, vì vậy entry **bị xóa** và kết quả lời gọi là `null`.
- `"rust"` cũng trả `null`, nhưng key này chưa từng tồn tại, do đó map không thêm entry nào.
- `"legacy"` đang được ánh xạ tới null; callback nhận oldValue null và trả 7, nên mapping trở thành `legacy -> 7`.
- `LinkedHashMap` ở constructor mặc định giữ thứ tự chèn key. Sau khi loại `java`, hai key còn lại là `legacy` rồi `go`. Chọn `LinkedHashMap` để stdout in map có thứ tự xác định; `HashMap` không cam kết iteration order.

**Không suy luận từ `compute(...) == null` rằng trước đó key không tồn tại:** cả trường hợp “đã xóa một mapping” và “vẫn không có mapping” đều trả null. Nếu cần kiểm tra **trạng thái hiện tại** ngay sau khi gọi trong bối cảnh không có cập nhật đồng thời, dùng `containsKey(key)`, không chỉ dùng `get(key) == null` khi map hỗ trợ giá trị null.

## 4. Hai loại null rất khác nhau

Cần phân biệt rõ:

- **`oldValue == null` trong callback:** không có giá trị khác null hiện hữu. Điều này có thể do key **chưa có** hoặc **đã có nhưng ánh xạ tới null**, nếu implementation hỗ trợ null values.
- **`newValue == null` do callback trả về:** một **chỉ thị thay đổi map** — xóa mapping đang có hoặc giữ trạng thái vắng mặt.

Với `HashMap`:

```java
Map<String, String> map = new java.util.HashMap<>();
map.put("a", null);

System.out.println(map.containsKey("a")); // true
System.out.println(map.get("a"));         // null

map.compute("a", (key, oldValue) -> null);

System.out.println(map.containsKey("a")); // false
```

Đây là **đoạn mã trong phương thức**, cần import `java.util.Map`. Key `"a"` tồn tại sau `put`, dù `get` trả null. Sau khi `compute` trả null, key bị xóa hẳn: `containsKey("a")` thành false.

Nếu nghiệp vụ **thực sự muốn lưu `key -> null`** trong một map cho phép giá trị null, dùng `put(key, null)` có chủ đích, không dùng `compute` với callback trả null. Tuy nhiên hãy cân nhắc thiết kế lại mô hình khi “không tồn tại”, “có key nhưng giá trị null” và “giá trị hợp lệ” là ba trạng thái có ý nghĩa riêng. `ConcurrentHashMap` **không chấp nhận** key hay value null.

### 4.1. Vì sao `getOrDefault` cũng có thể gây hiểu nhầm?

Trong map cho phép null, `getOrDefault(key, fallback)` dùng fallback **khi không có mapping**, chứ không mặc định thay mọi giá trị null:

```java
Map<String, String> data = new java.util.HashMap<>();
data.put("known", null);

System.out.println(data.getOrDefault("known", "default"));   // null
System.out.println(data.getOrDefault("missing", "default")); // default
```

Đây là đoạn mã trong phương thức. Cũng vì vậy, không nên dùng `get(key) == null` làm cách duy nhất để kết luận key chưa tồn tại trong `HashMap`, đặc biệt khi đang viết callback của `compute`.

### 4.2. Trong callback có cần gọi `map.containsKey(key)` để phân biệt?

Khi đọc bản thân map từ callback, bạn đang tạo phụ thuộc vào trạng thái bên ngoài chính phép tính; điều đó dễ làm code rối và có vấn đề về đồng thời. Nếu nghiệp vụ phải phân biệt **absent** với **mapped-to-null**, hãy chọn mô hình dữ liệu rõ ràng hoặc thực hiện logic phân nhánh ở mức phù hợp, với đồng bộ nếu có nhiều writer.

Đừng sửa chính map từ trong callback để “kiểm tra và sửa thêm một key khác”; Javadoc yêu cầu remapping function **không tự sửa map đang được compute**. Với ứng dụng concurrent, càng phải tránh side effects và logic phức tạp trong callback.

## 5. So sánh `compute` với `computeIfAbsent` và `computeIfPresent`

Cả ba đều là các API hiện hành của `Map`, nhưng chúng quyết định **khi nào gọi hàm** theo các quy tắc khác nhau.

| Phương thức | Khi key chưa có mapping hoặc đang map tới null | Khi key có giá trị khác null | Callback trả `null` |
| --- | --- | --- | --- |
| `compute(key, (k, old) -> newValue)` | **Vẫn gọi** callback với `old == null` | **Vẫn gọi** callback với old value | **Xóa entry hoặc giữ key vắng mặt** |
| `computeIfAbsent(key, k -> value)` | Gọi mapping function | **Không gọi** mapping function | Không thêm mapping mới; nếu key đã map tới null, entry null có thể vẫn ở đó |
| `computeIfPresent(key, (k, old) -> newValue)` | **Không gọi** callback | Gọi callback với giá trị khác null | Xóa entry đang có |
| `merge(key, providedValue, (old, supplied) -> newValue)` | Ghi `providedValue` khác null mà **không gọi** callback | Gọi callback với hai giá trị khác null | Xóa entry |

Một số điểm cần ghi nhớ:

- `compute` phù hợp khi muốn **xem xét mọi trạng thái** của key, kể cả absent.
- `computeIfAbsent` thường phù hợp để **khởi tạo một giá trị khi chưa có giá trị khác null**: cache, collection mới, default được tính theo key.
- `computeIfPresent` chỉ áp dụng logic khi key đang có **giá trị khác null**.
- `merge` thuận tiện khi đã có sẵn một **giá trị mới khác null** cần nhập với giá trị cũ (cộng bộ đếm, nối chuỗi...), mà không cần đọc key trong hàm gộp.

Đối số `value` cung cấp cho `merge` phải **khác null**. Nó khác với việc **hàm gộp** trả null: kết quả null từ hàm gộp là chỉ thị xóa mapping.

### 5.1. Ví dụ so sánh chạy được

Tạo file **`ComputeVariantsDemo.java`**:

```java
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.concurrent.atomic.AtomicInteger;

public class ComputeVariantsDemo {
    public static void main(String[] args) {
        Map<String, String> map = new LinkedHashMap<>();
        map.put("nullSlot", null);
        map.put("ready", "v1");

        AtomicInteger absentCalls = new AtomicInteger();
        AtomicInteger presentCalls = new AtomicInteger();

        map.computeIfPresent("nullSlot", (key, value) -> {
            presentCalls.incrementAndGet();
            return "x";
        }); // Không gọi callback: value đang null.

        map.computeIfAbsent("nullSlot", key -> {
            absentCalls.incrementAndGet();
            return "created";
        }); // Gọi callback: value trước đó null.

        map.computeIfAbsent("ready", key -> {
            absentCalls.incrementAndGet();
            return "wrong";
        }); // Không gọi callback: đã có "v1".

        map.computeIfPresent("ready", (key, value) -> {
            presentCalls.incrementAndGet();
            return null;
        }); // Xóa key "ready".

        map.merge("new", "A", String::concat); // Thêm mới.
        map.merge("new", "B", String::concat); // "AB".
        map.merge("nullSlot", "Y", (old, supplied) -> null);
        // Xóa key "nullSlot" vì hàm gộp trả null.

        System.out.println("absentCalls=" + absentCalls.get()
                + ", presentCalls=" + presentCalls.get());
        System.out.println("map=" + map);
    }
}
```

Chạy:

```bash
javac --release 17 ComputeVariantsDemo.java
java ComputeVariantsDemo
```

**Stdout:**

```text
absentCalls=1, presentCalls=1
map={new=AB}
```

Giải thích vì sao mỗi callback được gọi hoặc không được gọi:

1. `computeIfPresent("nullSlot", ...)` bỏ qua vì null không được xem là một giá trị present khác null.
2. `computeIfAbsent("nullSlot", ...)` chạy vì giá trị hiện tại là null, trả `"created"` và thay mapping.
3. `computeIfAbsent("ready", ...)` không chạy vì `"ready"` đã có `"v1"`.
4. `computeIfPresent("ready", ...)` chạy rồi **xóa** mapping vì trả null.
5. `merge("new", "A", ...)` tạo entry, lần thứ hai nối `"A" + "B"` thành `"AB"`.
6. `merge("nullSlot", "Y", ...)` gọi remapping function vì lúc này key đó chứa `"created"`; callback trả null nên xóa entry.
7. `AtomicInteger` ở đây chỉ dùng để minh họa số lần gọi callback trong một chương trình tuần tự; **không phải** lời khuyên đặt side effect trong remapping function của luồng đồng thời.

**Trường hợp tinh tế:** Nếu một `HashMap` đã chứa `"x" -> null` và bạn gọi `computeIfAbsent("x", k -> null)`, method không có giá trị mới để ghi, và entry `"x" -> null` có thể được giữ lại. Ngược lại, `compute("x", (k, v) -> null)` sẽ **xóa entry**. Đây là khác biệt ngữ nghĩa, không chỉ là khác biệt tên phương thức.

## 6. `compute` là thao tác *cập nhật có điều kiện* chứ không phải luôn xóa

Callback có thể trả một trong hai hướng theo giá trị đang có:

```java
stock.compute("apple", (key, quantity) -> {
    if (quantity == null) {
        return null; // Không có hàng để trừ, vẫn vắng mặt.
    }
    int remaining = quantity - 2;
    return remaining > 0 ? remaining : null;
});
```

Đây là **đoạn mã trong phương thức**, trong đó `stock` là map có thể sửa với value là `Integer` không âm theo invariant của ứng dụng. Ví dụ nghiệp vụ: sau khi xuất 2 sản phẩm, nếu số lượng còn lớn hơn 0 thì giữ key với số lượng mới; nếu hết hàng thì loại key khỏi map.

**Lợi ích:** không cần code `if (map.get(...) != null) ... else map.remove(...)` rời rạc. Nhưng phải rõ:

- Nếu muốn “không cập nhật” với key đã tồn tại, **trả lại old value**, không trả null.
- Nếu key chưa có và callback trả null, map vẫn vắng mặt.
- Nếu muốn **xóa vô điều kiện** bất kể giá trị cũ, `map.remove(key)` đơn giản hơn `map.compute(key, (k, v) -> null)`.
- Với tồn kho và giá trị thanh toán, cần xác nhận quy tắc không âm, overflow, transaction, cập nhật cơ sở dữ liệu và các writer bên ngoài JVM. `Map.compute` không tự giải quyết mọi vấn đề consistency nghiệp vụ.

## 7. Các lỗi sai điển hình về `null`

### 7.1. Unboxing `oldValue` khi key chưa có

**Sai:**

```java
Map<String, Integer> counts = new java.util.HashMap<>();
counts.compute("java", (key, value) -> value + 1);
```

Đây là **đoạn mã minh họa lỗi** trong phương thức. `"java"` chưa tồn tại, `value == null`; toán tử `+` yêu cầu unboxing `Integer` và gây `NullPointerException`. Không có kết quả số để dự đoán.

**Đúng:**

```java
counts.compute("java", (key, value) ->
        value == null ? 1 : value + 1);
```

Hoặc khi giá trị tăng đã biết sẵn:

```java
counts.merge("java", 1, Integer::sum);
```

`merge` thường rõ ràng hơn cho bài toán cộng dồn, vì đầu vào thêm là một giá trị **khác null**.

### 7.2. Nghĩ `return null` sẽ lưu giá trị null

**Sai về ý định:**

```java
map.compute("key", (key, old) -> null);
```

Nếu cần lưu `key -> null` trong map cho phép null, câu lệnh này **không làm được**; nó xóa key. Hãy xác định rõ mô hình giá trị thiếu hoặc, khi thật sự cần nullable value, dùng API hỗ trợ ghi null như `put` trên `HashMap`.

### 7.3. Dựa vào giá trị trả về để phân biệt xóa và không tìm thấy

Cả hai lời gọi sau có thể trả `null`:

```java
map.compute("present", (key, old) -> null); // Xóa key.
map.compute("missing", (key, old) -> null); // Vẫn vắng mặt.
```

Đây là **đoạn minh họa** khi `map` là map đã khởi tạo. Nếu muốn biết trước đó key tồn tại hay không, bạn cần một hợp đồng trả kết quả chi tiết hơn hoặc kiểm tra/tracking tại ranh giới đúng; trong môi trường concurrent, phép kiểm tra riêng `containsKey` sau compute **không** là snapshot nguyên tử cùng với compute.

### 7.4. Trả null từ callback khi muốn giữ nguyên

Nếu callback xử lý một điều kiện và muốn **giữ mapping cũ**, phải trả lại `oldValue`. Trả null là xóa; không có khái niệm “bỏ qua update” được biểu diễn bằng null cho key đang có.

## 8. Nếu hàm remapping ném exception thì sao?

Hợp đồng `Map.compute` quy định: khi remapping function ném **unchecked exception**, ngoại lệ được chuyển tiếp ra người gọi và **mapping hiện tại không thay đổi**. Đừng bắt lỗi rồi `return null` trong callback một cách tùy tiện, bởi điều đó chuyển lỗi thành **xóa dữ liệu**.

Tạo file **`ComputeExceptionDemo.java`**:

```java
import java.util.LinkedHashMap;
import java.util.Map;

public class ComputeExceptionDemo {
    public static void main(String[] args) {
        Map<String, Integer> map = new LinkedHashMap<>();
        map.put("x", 7);

        try {
            map.compute("x", (key, oldValue) -> {
                throw new IllegalStateException("bad");
            });
        } catch (IllegalStateException ex) {
            System.out.println("error=" + ex.getMessage());
        }

        System.out.println("unchanged=" + map.get("x"));
    }
}
```

Chạy:

```bash
javac --release 17 ComputeExceptionDemo.java
java ComputeExceptionDemo
```

Stdout:

```text
error=bad
unchanged=7
```

Ví dụ đúng bởi lambda **không tự thay đổi map trước khi ném lỗi**. Nếu callback tự gây side effect cho cơ sở dữ liệu, file hoặc biến bên ngoài rồi ném exception, Map không tự rollback các side effect đó. Khi logic có thể thất bại, nên tính toán nhất quán và đưa phần tác động ra ngoài callback khi có thể.

## 9. Không tự sửa map từ bên trong callback

**Không nên:**

```java
map.compute("a", (key, oldValue) -> {
    map.put("b", "side effect"); // Vi phạm khuyến nghị API.
    return "new value";
});
```

Đây là **đoạn minh họa hành vi sai**, giả định `map` là `Map<String, String>`. Javadoc yêu cầu remapping function **không sửa chính map** trong thời gian tính toán. Một số implementation không phát hiện được mọi trường hợp; `HashMap` có thể ném `ConcurrentModificationException` theo cơ chế best-effort, còn `ConcurrentHashMap` có thể ném `IllegalStateException` khi phát hiện cập nhật đệ quy gây nguy cơ không hoàn tất. Không dựa vào kiểu lỗi cụ thể để xây cơ chế nghiệp vụ.

Nếu phải thay nhiều key theo một logic phức tạp, hãy tổ chức thuật toán khác, hoặc dùng cơ chế đồng bộ/transaction phù hợp. `compute` có mục đích cập nhật **một mapping cho key đang được tính**, không phải một giao dịch sửa toàn bộ map.

Ngoài ra tránh thao tác chậm, I/O, chờ khóa hoặc truy vấn mạng trong remapping function của concurrent map: một số thao tác cập nhật khác có thể bị block trong thời gian tính toán.

## 10. Có an toàn khi gọi `compute` từ nhiều thread không?

**Phụ thuộc implementation**, không chỉ phụ thuộc tên phương thức.

### 10.1. `HashMap` và `LinkedHashMap`: không tự bảo đảm atomicity cho truy cập đồng thời

`Map.compute` là default method; hợp đồng cơ bản **không bảo đảm atomicity hoặc đồng bộ hóa**. `HashMap`/`LinkedHashMap` không phải concurrent maps. Ví dụ:

```java
Map<String, Integer> counts = new java.util.HashMap<>();

java.util.stream.IntStream.range(0, 1_000)
        .parallel()
        .forEach(n -> counts.compute(
                "hits", (key, old) -> old == null ? 1 : old + 1
        ));
```

Đây là **đoạn mã sai để phân tích**, không có stdout cố định. Nhiều thread có thể đọc cùng giá trị cũ rồi ghi đè cập nhật của nhau; đồng thời sửa `HashMap` không an toàn và có thể gây hành vi sai khác. Việc gộp `get` và `put` thành `compute` **không tự khiến `HashMap` trở thành thread-safe**.

Khi chỉ muốn đếm phần tử của một stream, `count()` hoặc các collector đúng hợp đồng sẽ phù hợp hơn việc tự ghi vào một map dùng chung.

### 10.2. `ConcurrentHashMap.compute`: một phép tính atomic theo key

`ConcurrentHashMap` có implement riêng cho `compute`. Tài liệu của implementation này nêu **toàn bộ lời gọi được thực hiện atomically**; callback được gọi **đúng một lần cho mỗi lời gọi `compute`**. Một số cập nhật khác có thể chờ trong thời gian callback chạy, nên callback phải ngắn, đơn giản và **không tự sửa map**.

Tạo file **`ConcurrentComputeDemo.java`**:

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;
import java.util.stream.IntStream;

public class ConcurrentComputeDemo {
    public static void main(String[] args) {
        ConcurrentMap<String, Integer> counts =
                new ConcurrentHashMap<>();

        IntStream.range(0, 1_000)
                .parallel()
                .forEach(n -> counts.compute(
                        "hits",
                        (key, oldValue) ->
                                oldValue == null ? 1 : oldValue + 1
                ));

        System.out.println("hits=" + counts.get("hits"));

        Integer deleted = counts.compute(
                "hits", (key, oldValue) -> null);

        System.out.println("removed=" + deleted);
        System.out.println("contains hits="
                + counts.containsKey("hits"));
    }
}
```

Chạy:

```bash
javac --release 17 ConcurrentComputeDemo.java
java ConcurrentComputeDemo
```

**Stdout chính xác sau khi stream đã hoàn tất:**

```text
hits=1000
removed=null
contains hits=false
```

**Tại sao đây là ví dụ an toàn?** Mỗi lời gọi `ConcurrentHashMap.compute("hits", ...)` được atomic theo hợp đồng của lớp này, nên phép tăng không bị mất cập nhật dù các tác vụ chạy song song. Sau khi terminal `forEach` kết thúc, các lần tăng đã hoàn thành. Cuối cùng, callback trả null nên key bị xóa.

**Điều không nên suy rộng:**

- Tính atomic trên một mapping **không biến nhiều lời gọi `compute` hoặc nhiều key thành một transaction chung**.
- Các loại `ConcurrentMap` khác có thể có đặc tả khác. Default implementation của interface có thể phải thử lại khi tranh chấp, do đó **callback có thể được gọi nhiều lần** trong một lời gọi ở một số implementation. Không đặt side effect phải chạy đúng một lần vào callback một cách thiếu cân nhắc.
- `ConcurrentHashMap` **cấm key và value null**, nhưng **cho phép callback trả null** để báo “xóa/không lưu mapping”. Hai quy tắc này không mâu thuẫn.
- Nếu chỉ cần một bộ đếm cập nhật dày đặc với contention cao, có thể cân nhắc `LongAdder` hoặc collector phù hợp thay vì làm mọi tác vụ tranh chấp cùng một key trong `ConcurrentHashMap`. Việc chọn giải pháp hiệu năng phải dựa vào benchmark và đặc tính workload.

### 10.3. Khác biệt `compute` của `ConcurrentMap` và `ConcurrentHashMap`

`ConcurrentMap` là interface mở rộng `Map` và có một số default methods với chiến lược retry khi có concurrent update. Việc bạn giữ biến với kiểu `ConcurrentMap<K,V>` **không đủ để kết luận mọi implementation sẽ gọi callback một lần**.

Ở ví dụ trên, đối tượng thực tế là `new ConcurrentHashMap<>()`, vì thế lời hứa atomic và quy tắc lời gọi callback được lấy từ Javadoc của **ConcurrentHashMap**, không phải dự đoán dựa trên tên `ConcurrentMap`.

## 11. Vì sao callback nên thuần và ngắn?

Một remapping function tốt thường chỉ dùng `key`, `oldValue` và các thông số đầu vào ổn định để tính kết quả:

```java
counts.compute("java", (key, oldValue) ->
        oldValue == null ? 1 : Math.addExact(oldValue, 1));
```

Đây là **đoạn mã trong phương thức**, với `counts` là `Map<String, Integer>` mutable. `Math.addExact` có thể ném `ArithmeticException` khi overflow, giúp không âm thầm tạo một giá trị không hợp lệ; nếu exception xảy ra, mapping đang có được giữ nguyên theo hợp đồng `compute`.

Tránh callback có tác dụng bên ngoài:

```java
counts.compute("java", (key, oldValue) -> {
    sendEmail();            // Side effect không nên phụ thuộc retry.
    updateDatabase();       // Không phải transaction cùng với map.
    return oldValue == null ? 1 : oldValue + 1;
});
```

Đây là **mã phản ví dụ**, trong đó `sendEmail` và `updateDatabase` là các phương thức giả định. Một callback có thể bị thử lại với một số `ConcurrentMap` implementation, bị ngắt bởi exception, hoặc giữ khóa/block các cập nhật khác. Vì vậy không dùng nó làm nơi thực hiện các giao dịch hệ thống bên ngoài.

Nếu cần cập nhật DB + cache nhất quán, `Map.compute` không thay thế transaction, versioning hoặc quy trình xử lý sự kiện có idempotency phù hợp.

## 12. Có phải `compute` là lựa chọn tốt nhất cho mọi bài toán?

Không. Chọn theo ý nghĩa:

| Nhu cầu | Phương thức thường rõ ràng |
| --- | --- |
| Chỉ thêm/thay giá trị đã biết, không cần old value | `put(key, value)` |
| Chỉ xóa theo key | `remove(key)` |
| Cần xét cả key absent và present để tính value mới hoặc xóa | `compute(key, remappingFunction)` |
| Chỉ khởi tạo nếu value chưa có/đang null | `computeIfAbsent(key, mappingFunction)` |
| Chỉ sửa khi value đang có khác null | `computeIfPresent(key, remappingFunction)` |
| Có giá trị mới đã biết khác null để gộp với old value | `merge(key, value, remappingFunction)` |
| Chỉ lấy giá trị, có giá trị dự phòng nếu key vắng mặt | `getOrDefault(key, defaultValue)` |
| Cần cập nhật atomic theo key trong môi trường đồng thời | Implementation có hợp đồng atomic, ví dụ `ConcurrentHashMap.compute` |
| Dữ liệu bất biến, cần tạo map mới | Dựng map/copy mới thay vì cố sửa map unmodifiable |

**Khi giá trị tính toán có thể trả null:** hãy chủ động xem xét liệu nó có nghĩa là **xóa** không. Nếu nghiệp vụ coi null là “không cập nhật”, `compute` cần một cách diễn đạt rõ ràng khác để tránh xóa dữ liệu vô ý.

## 13. Một số trường hợp biên cần kiểm tra

### 13.1. Map không cho phép thay đổi

Không phải mọi `Map` đều mutable. Các map từ `Map.of(...)`, `Map.copyOf(...)` là **unmodifiable**, do đó các thao tác cập nhật như `compute` không phải cách hợp lệ để thay đổi nội dung; có thể ném `UnsupportedOperationException` tùy implementation và tác động yêu cầu. Khi cần cập nhật, tạo một map mutable phù hợp rồi chuyển sang unmodifiable ở ranh giới xuất dữ liệu nếu cần.

### 13.2. Key hoặc value null

`HashMap` hỗ trợ key và value null; `ConcurrentHashMap` cấm cả hai. Với `TreeMap`, quy tắc key null phụ thuộc ordering/comparator; đừng mặc nhiên suy rộng một map sang mọi map. `compute` luôn yêu cầu **remappingFunction không null**, và việc callback trả null có ý nghĩa xóa ngay cả trên map **không cho phép lưu value null**.

### 13.3. Exception so với null result

Nếu callback không thể tính được vì dữ liệu sai hoặc có lỗi nghiệp vụ, cân nhắc **throw** exception phù hợp thay vì `return null`. Null result là **hành động xóa mapping**; exception là **tín hiệu thất bại** và không nên bị diễn giải thành yêu cầu xóa.

### 13.4. Thứ tự và iteration

Khi `compute` thay giá trị của một key trong `LinkedHashMap` **insertion-order mặc định**, key vẫn ở vị trí đã chèn. Khi callback trả null và key bị xóa, nếu sau đó chèn lại thì key nhận vị trí chèn mới. Trong `HashMap` không nên dự đoán thứ tự iteration. Cũng tránh sửa cấu trúc map trong khi dùng iterator thông thường của nó; iterator fail-fast có thể ném `ConcurrentModificationException` nhưng không phải cơ chế đảm bảo an toàn đồng thời.

### 13.5. Không nhầm `compute` với một phép “atomic read-modify-write” cho mọi thiết bị lưu trữ

`compute` xử lý trạng thái của **Map trong JVM**. Nếu map chỉ là cache của database, việc compute xong không đồng nghĩa database đã được cập nhật an toàn. Nếu có nhiều instance ứng dụng, một `ConcurrentHashMap` trong một JVM cũng không là khóa phân tán giữa nhiều server.

## 14. Những lỗi thường gặp và cách tránh

1. **Trả null với ý định ghi `key -> null`:** `compute` xóa key thay vì lưu null.
2. **Không kiểm tra `oldValue` null:** key absent hoặc mapped-null làm phép unboxing `old + 1` ném NPE.
3. **Nghĩ callback chỉ chạy khi key tồn tại:** `compute` vẫn chạy khi key chưa có mapping; phương thức chỉ gọi khi present là `computeIfPresent`.
4. **Nghĩ `compute` là “computeIfAbsent” viết ngắn:** `compute` tính lại cả giá trị đã tồn tại, có thể ghi đè hoặc xóa.
5. **Nhầm callback trả null với việc không thay đổi:** null xóa entry hiện có; giữ nguyên giá trị cũ bằng cách trả `oldValue` khi phù hợp.
6. **Đọc `compute(...) == null` rồi khẳng định key không từng tồn tại:** không phân biệt absent ban đầu và deletion thành công.
7. **Dùng `get(key) == null` để xác định chắc chắn key absent trong `HashMap`:** một mapping tới null vẫn có thể tồn tại; xem `containsKey`.
8. **Nghĩ `merge(key, null, fn)` hợp lệ giống callback trả null:** đối số value của `merge` phải non-null; null từ callback lại có nghĩa remove.
9. **Tự cập nhật cùng map bên trong remapping function:** vi phạm hợp đồng, có thể gây CME hoặc recursive-update exception.
10. **Dùng `HashMap.compute` từ nhiều thread và tưởng phép tăng đã atomic:** default Map.compute không bảo đảm đồng bộ.
11. **Cho rằng mọi `ConcurrentMap` chạy callback chính xác một lần:** interface default methods có thể retry; chỉ dựa vào đảm bảo của implementation cụ thể.
12. **Thực hiện I/O nặng trong `ConcurrentHashMap.compute`:** các cập nhật khác có thể bị block; hàm nên ngắn, không side effects.
13. **Bắt mọi lỗi trong callback rồi return null:** biến lỗi thành xóa dữ liệu, có thể mất mapping đang hợp lệ.
14. **Không xét overflow của `Integer`/`Long`:** phép tăng có thể overflow; dùng `Math.addExact` khi cần phát hiện, hoặc chọn miền kiểu phù hợp.
15. **Gọi `compute` trên map bất biến và mong nó cập nhật:** map unmodifiable không hỗ trợ ghi.
16. **Giả định null key dùng được trên mọi Map:** `HashMap` cho phép, `ConcurrentHashMap` không.
17. **Dựa vào thứ tự iteration của HashMap để minh họa kết quả:** dùng `LinkedHashMap` hoặc in theo key cụ thể nếu cần stdout ổn định.
18. **Nghĩ compute cập nhật DB/cache phân tán một cách atomic:** giới hạn atomicity nằm ở implementation trong JVM; cần transaction/coordination khác cho hệ thống phân tán.

## 15. Checklist trước khi chọn `compute`

Hãy trả lời các câu hỏi:

1. **Map implementation nào?** Có cho null key/value không, mutable hay unmodifiable, concurrent hay không?
2. **Key có thể absent không?** Callback phải xử lý `oldValue == null`, kể cả trường hợp mapped-to-null trong map cho phép null.
3. **Khi callback trả null, thật sự muốn xóa key chứ?** Nếu không, phải thay quy tắc trả value hoặc chọn phương thức khác.
4. **Muốn biết key từng tồn tại hay không?** Tránh suy luận từ kết quả trả null; dùng model/tracking phù hợp.
5. **Đang thực hiện thao tác thêm, chỉ-if-absent, chỉ-if-present hay merge?** Phương thức khác có thể rõ ý định hơn.
6. **Có concurrent writer không?** Chọn implementation có atomicity được tài liệu hóa; đừng dùng HashMap chia sẻ thiếu đồng bộ.
7. **Callback có thay đổi chính map hoặc gây side effect không?** Loại bỏ, vì có thể khiến map không nhất quán hoặc callback lặp.
8. **Nếu callback ném exception có muốn giữ mapping không?** Theo hợp đồng, mapping giữ nguyên khi callback ném unchecked exception mà không tự sửa map.
9. **Giá trị tính toán có thể overflow/invalid không?** Kiểm tra trước khi commit mapping.
10. **Có test đủ absent, mapped-null, nonnull, null-return và exception không?** Đây là bộ ca tối thiểu cho hành vi khó nhất của `compute`.

## 16. Câu hỏi tự kiểm tra

1. Với `Map<String, Integer> m = new HashMap<>()` và `m.put("a", 3)`, chuyện gì xảy ra khi gọi `m.compute("a", (k, v) -> null)`?
2. `m.compute("missing", (k, v) -> null)` trả gì? Có thêm key `"missing"` không?
3. `HashMap` đang có `"x" -> null`; `compute("x", (k,v) -> null)` và `computeIfAbsent("x", k -> null)` khác nhau thế nào?
4. Vì sao `compute("counter", (k,v) -> v + 1)` có thể ném `NullPointerException`?
5. `computeIfPresent` có chạy callback khi key tồn tại nhưng value là null không?
6. Vì sao `ConcurrentHashMap` từ chối lưu null value nhưng callback của `compute` vẫn có thể trả null?
7. `HashMap.compute` có tự động bảo vệ cập nhật từ nhiều thread không? Muốn cập nhật atomic một key, có thể chọn implementation nào?
8. Vì sao không nên gửi email từ trong remapping function khi có thể dùng những `ConcurrentMap` implementation có retry?

**Đáp án gợi ý:** (1) key `a` bị xóa; (2) trả null và key vẫn absent; (3) `compute` xóa entry, `computeIfAbsent` nhận null nên không ghi giá trị mới và có thể giữ mapped-null; (4) unboxing null khi key absent/mapped-null; (5) không; (6) null result là tín hiệu xóa, không phải giá trị lưu; (7) không, `ConcurrentHashMap.compute` có hợp đồng atomic cho lời gọi; (8) side effect có thể chạy không theo số lần ứng dụng mong muốn và không thuộc transaction của Map.

**Kết luận:** `Map.compute` không chỉ “tính toán giá trị”. Giá trị trả về từ remapping function **định đoạt sự tồn tại của mapping**: khác null thì ghi/thay, null thì **xóa hoặc giữ vắng mặt**. Cần phân biệt `compute` với `computeIfAbsent`, `computeIfPresent`, `merge` và hiểu implementation đang dùng, nhất là khi có null values hoặc nhiều thread. Đó là cách tránh vô tình xóa dữ liệu và tránh suy luận sai về tính nguyên tử.
