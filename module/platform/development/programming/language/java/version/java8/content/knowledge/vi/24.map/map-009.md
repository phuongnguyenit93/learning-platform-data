# Hợp đồng default method và giới hạn tính nguyên tử trong Java Map

## 1. Mục tiêu và phạm vi

Map<K,V> được Java 8 bổ sung nhiều default method hữu ích: getOrDefault, forEach, putIfAbsent, remove(key,value), replace, replaceAll, computeIfAbsent, computeIfPresent, compute và merge. Chúng cho phép biểu diễn việc tra cứu, cập nhật có điều kiện và gộp giá trị ngắn gọn hơn, nhưng **không tự động bảo đảm thao tác nguyên tử khi có nhiều thread**.

Sau bài học, bạn có thể:

1. Đọc đúng hợp đồng của từng phương thức và phân biệt kết quả của các trạng thái key vắng, key có value null và key có value non-null.
2. Giải thích vì sao một default method của interface Map không đồng nghĩa tất cả implementation có cùng thread-safety.
3. Chọn đúng computeIfAbsent, computeIfPresent, compute hay merge khi xử lý dữ liệu bình thường.
4. Phân biệt tính nguyên tử của một lời gọi riêng, một chuỗi read–modify–write, nhiều key và việc sửa object value mutable.
5. So sánh HashMap, ConcurrentMap và ConcurrentHashMap; nhận biết cơ chế retry và giới hạn của mapping/remapping function.
6. Thiết kế bộ đếm, cache hoặc dữ liệu nhóm an toàn khi xử lý đồng thời.
7. Biên dịch và chạy các chương trình Java 17+ có stdout xác định, không phụ thuộc cách lập lịch thread.

**Ghi chú phiên bản:** Tất cả default method Map được học ở đây có từ Java 8 và **vẫn còn áp dụng** trong JDK hiện hành. Map.of dùng trong một ví dụ có từ Java 9. Bài không sử dụng cách làm đã legacy; khi đề cập hành vi đồng thời, luôn phân biệt contract của interface với implementation.

## 2. Default method trong một interface là gì?

Từ Java 8, interface có thể cung cấp thân phương thức với từ khóa default. Nhờ đó, Map bổ sung thao tác tiện ích mà các class triển khai có thể nhận được mà không cần ngay lập tức cung cấp thân mới cho mỗi phương thức.

Ví dụ, mã nguồn ứng dụng viết:

~~~java
// Mảnh mã, cần import java.util.Map và java.util.HashMap.
Map<String, Integer> counts = new HashMap<>();
counts.merge("java", 1, Integer::sum);
~~~

Cú pháp này giúp mô tả gộp giá trị vào key, nhưng **không có nghĩa** HashMap trở nên thread-safe. Hợp đồng Map mô tả giá trị được trả và thay đổi mapping trong một cách dùng hợp lệ; không tự thêm lock, atomic compare-and-set hoặc transaction.

JavaDoc Map nêu rằng những triển khai mặc định không đưa ra bảo đảm về synchronization hay atomicity. Một class muốn có bảo đảm riêng phải override và ghi rõ tính chất đồng thời trong tài liệu.

**Nguyên tắc nền tảng:** Khi code khai báo biến kiểu Map<K,V>, quyết định có an toàn với nhiều thread hay không phụ thuộc **object Map thực tế** cùng thao tác cụ thể được gọi, chứ không chỉ phụ thuộc tên phương thức.

## 3. Thế nào là cập nhật nguyên tử?

Một thao tác nguyên tử nghĩa là trong phạm vi hợp đồng, việc cập nhật có thể được quan sát như một bước không bị thao tác cạnh tranh xen vào giữa.

Xét bộ đếm:

~~~java
// Mảnh mã: map là Map<String,Integer>.
int old = map.getOrDefault("hits", 0);
map.put("hits", old + 1);
~~~

Nếu hai thread cùng chạy, có thể xảy ra:

~~~text
Ban đầu: hits=0

Thread A                         Thread B
read hits -> 0                   read hits -> 0
calculate 1                      calculate 1
put hits=1                       put hits=1

Cuối cùng: hits=1, dù đã có hai yêu cầu tăng.
~~~

Đây là lỗi **lost update**. Ngay cả khi map là ConcurrentHashMap, mỗi get và put riêng lẻ thread-safe, **chuỗi gồm hai lời gọi** vẫn không phải một phép tăng nguyên tử.

Với ConcurrentHashMap, một lời gọi gộp có thể bảo vệ việc cập nhật key:

~~~java
// Mảnh mã: counts là ConcurrentHashMap<String,Integer>.
counts.merge("hits", 1, Integer::sum);
~~~

hoặc:

~~~java
counts.compute("hits", (key, old) ->
        old == null ? 1 : old + 1);
~~~

Hai mẫu dùng những override có hợp đồng atomic của ConcurrentHashMap. Nếu thay object bằng HashMap chia sẻ giữa nhiều thread, không được suy ra hai lời gọi này vẫn an toàn chỉ vì cùng tên merge/compute.

### Atomicity không phải transaction

Một phép compute cập nhật một key nguyên tử không có nghĩa hai compute trên hai key tạo thành transaction. Nó cũng không có nghĩa mọi object mutable được lưu làm value đều an toàn, mọi lời gọi HTTP/JDBC bên trong function được rollback, hoặc một vòng forEach nhìn thấy snapshot đồng bộ của cả Map.

## 4. Ba trạng thái quan trọng của một key

Với Map cho phép value null như HashMap:

| Trạng thái | containsKey(key) | get(key) |
|---|---|---|
| Key chưa có mapping | false | null |
| Key đang map đến null | true | null |
| Key map đến value khác null | true | value |

Vì vậy, get(key)==null **không luôn đồng nghĩa** key chưa tồn tại.

Những method Java 8 xử lý null như sau:

- getOrDefault(key, fallback) chỉ trả fallback khi **không có mapping**. Nếu key hiện tồn tại với value null, kết quả là null.
- putIfAbsent(key,value) có thể ghi value mới khi key vắng **hoặc** đang map đến null.
- computeIfAbsent(key,f) tính giá trị khi key vắng hoặc đang map đến null; nếu f trả null thì không ghi một value non-null mới.
- computeIfPresent(key,f) chỉ chạy f nếu value hiện tại **non-null**.
- compute(key,f) chạy f với old value hiện tại; old có thể null khi key vắng hoặc map đến null.
- merge(key,value,f) dùng trực tiếp value đầu vào (bắt buộc non-null) khi key vắng hoặc old value null; với old non-null thì gọi f.

ConcurrentHashMap không cho phép key null hoặc value null. Trên loại Map này, get trả null không mơ hồ về mapped-to-null, nhưng trạng thái vẫn có thể thay đổi ngay sau khi đọc nếu thread khác cập nhật.

## 5. Tổng quan các phương thức Map Java 8

| Method | Ý nghĩa | Kết quả và cảnh báo |
|---|---|---|
| getOrDefault(k,d) | Đọc theo key với fallback khi key vắng | Không tự thay value null bằng d |
| forEach((k,v)->...) | Duyệt từng entry | Không phải snapshot/transaction |
| putIfAbsent(k,v) | Ghi khi value cũ vắng/null | Có thể trả null cho key vắng hoặc mapped-to-null |
| remove(k,v) | Chỉ xóa nếu value đang khớp | boolean; default không cam kết atomicity |
| replace(k,v) | Thay value nếu key đang tồn tại | Trả value cũ hoặc null |
| replace(k,old,new) | Thay có điều kiện nếu old khớp | boolean; cần implementation atomic nếu concurrent |
| replaceAll((k,v)->newV) | Chuyển đổi value các entry | Không nguyên tử cho toàn bộ Map |
| computeIfAbsent(k,f) | Tạo value khi chưa có non-null mapping | f trả null thì không tạo value non-null mới |
| computeIfPresent(k,f) | Tính lại value hiện có non-null | f trả null thì xóa mapping |
| compute(k,f) | Tính lại cả khi old null | f trả null thì xóa/để absent |
| merge(k,v,f) | Thêm/gộp value non-null theo key | f trả null thì xóa mapping |

Những phương thức cần sửa dữ liệu là **optional operations** trong các trường hợp Map không hỗ trợ sửa. Ví dụ Map.of (Java 9+) tạo Map không sửa được, nên một thao tác compute muốn thay entry sẽ ném UnsupportedOperationException.

### getOrDefault không phải một phương thức chuẩn hóa null

~~~java
// Mảnh mã, map là HashMap.
map.put("nullable", null);
map.getOrDefault("nullable", 99); // null, không phải 99
map.getOrDefault("unknown", 99);  // 99
~~~

Nếu nghiệp vụ coi null như thiếu, bạn cần quyết định chính sách rõ ràng. Optional.ofNullable(map.get(key)).orElse(99) là một cách **cố tình gộp** hai trạng thái absent và mapped-to-null.

## 6. putIfAbsent, remove(key,value), replace và replaceAll

### 6.1. putIfAbsent

Mô hình ngữ nghĩa tương đương của default method thông thường:

~~~java
// Pseudo-code; không phải phương thức Java đầy đủ.
V old = map.get(key);
if (old == null) {
    old = map.put(key, value);
}
return old;
~~~

Hai thread có thể đồng thời thấy old==null và đều thực hiện put. Vì vậy một Map thường không tự bảo đảm atomicity. ConcurrentHashMap.putIfAbsent được override và có contract cập nhật nguyên tử.

### 6.2. remove(key,value)

~~~java
// Mảnh mã.
boolean removed = map.remove("session", "old-token");
~~~

Chỉ xóa khi value hiện tại khớp old-token. Đối với ConcurrentHashMap, kiểm tra và xóa có thể được thực hiện nguyên tử theo contract của implementation. Đối với Map default, không thể hứa như vậy khi nhiều thread cùng sửa.

### 6.3. replace(key, old, new)

~~~java
// Mảnh mã.
boolean ok = map.replace("state", "draft", "published");
~~~

Cách diễn đạt này giống compare-and-set ở mức ý định, nhưng không tự tạo compare-and-set nguyên tử trên HashMap thông thường. Một implementation có atomic override mới cho bảo đảm cần thiết.

### 6.4. replaceAll

~~~java
// Mảnh mã.
map.replaceAll((key, old) -> old + 1);
~~~

Đây là cập nhật theo entry; không phải transaction toàn Map. Nếu thread khác duyệt trong lúc đang thay, có thể quan sát một số key đã đổi còn số khác chưa đổi, tùy loại Map và quy tắc concurrency. JavaDoc của Map cũng không bảo đảm synchronization/atomicity của default replaceAll.

## 7. computeIfAbsent: hữu ích cho cache nhưng phải hiểu contract

~~~java
// Mảnh mã.
cache.computeIfAbsent(id, key -> loadUser(key));
~~~

Method chỉ thử tính khi value cũ vắng hoặc null. Nếu mapping function trả null thì không ghi một mapping mới có value non-null. Nếu function ném exception, exception được chuyển ra ngoài và việc tạo mapping không hoàn tất theo hợp đồng.

**Quan trọng khi chạy đồng thời:**

- **Map default:** không có bảo đảm atomicity/synchronization.
- **ConcurrentMap default:** có thể dựa trên atomic putIfAbsent để thử tạo mapping; một số implementation khác nhau về số lần function chạy khi tranh chấp.
- **ConcurrentHashMap:** computeIfAbsent có lời hứa atomicity của invocation; function được gọi chính xác một lần **trong invocation đó nếu key absent**, còn khi value đã hiện diện thì không gọi.

Điều trên **không có nghĩa** function sẽ chạy đúng một lần trong suốt đời ứng dụng: key có thể bị xóa rồi tạo lại; mapper có thể trả null, throw; hoặc code khác có thể invalidating cache. Không gắn việc tính một value với side effect không thể lặp lại ngoài Map khi chưa có giao thức idempotency phù hợp.

### Function ngắn và không sửa Map

ConcurrentHashMap document rằng mapping/remapping function không được sửa chính Map trong lúc tính. Một số recursive update có thể được phát hiện và ném IllegalStateException. Hàm dài có blocking I/O có thể chặn một số cập nhật tranh chấp, ảnh hưởng latency.

### computeIfAbsent không bảo vệ thao tác trên value mutable sau đó

~~~java
// PHẢN VÍ DỤ: map có kiểu ConcurrentHashMap<String,List<String>>.
map.computeIfAbsent("team", k -> new ArrayList<>()).add("An");
~~~

Việc lấy/tạo value có thể atomic, nhưng lời gọi ArrayList.add diễn ra **bên ngoài atomic section** và có thể được nhiều thread gọi lên cùng List. Vì vậy dữ liệu vẫn có race. Cần container value concurrent, update immutable replacement trong compute hoặc collector phù hợp.

## 8. computeIfPresent, compute và merge

### computeIfPresent

~~~java
// Mảnh mã.
map.computeIfPresent("quota", (key, old) -> old + 1);
~~~

Chỉ chạy mapper với value non-null. Function trả null thì mapping bị loại bỏ. Nếu value hiện tại null, sẽ không tự tăng từ 0.

### compute

~~~java
// Mảnh mã.
map.compute("quota", (key, old) ->
        old == null ? 1 : old + 1);
~~~

Chạy với cả trường hợp old==null, hợp với bài toán “khởi tạo nếu chưa có, còn không thì tăng”. Function trả null thì không còn mapping cho key. Nếu Map cho value null, old==null không phân biệt key vắng với key mapped-to-null.

### merge

~~~java
// Mảnh mã.
map.merge("quota", 1, Integer::sum);
~~~

Nếu không có value non-null, đặt value=1. Nếu có old value, tính tổng old và 1. Nếu remapping function trả null, mapping được xóa. **Đối số value của merge phải non-null**; không dùng merge(key,null,...) để bỏ qua cập nhật.

### Chọn phương thức thế nào?

| Nhu cầu | Gợi ý |
|---|---|
| Tạo value khi vắng/null, giữ nguyên khi present | computeIfAbsent |
| Chỉ sửa value khi đã có non-null | computeIfPresent |
| Tính dựa trên old cả khi key vắng | compute |
| Gộp một giá trị non-null vào value đã có | merge |
| Thay nếu oldValue đúng như dự kiến | replace(key,oldValue,newValue) |
| Xóa nếu value chưa thay đổi | remove(key,expectedValue) |

Trên các Map có concurrent update, hãy đối chiếu **contract của implementation**, không coi bảng chọn method là bảo đảm atomicity mặc định.

## 9. Ví dụ hoàn chỉnh 1: các default method khi chạy tuần tự

Tạo file **MapDefaultMethodsDemo.java**:

~~~java
import java.util.LinkedHashMap;
import java.util.Map;

public class MapDefaultMethodsDemo {
    public static void main(String[] args) {
        Map<String, Integer> map = new LinkedHashMap<>();
        map.put("present", 10);
        map.put("nullable", null);

        System.out.println("present=" + map.getOrDefault("present", 99));
        System.out.println("missing=" + map.getOrDefault("missing", 99));
        System.out.println("mappedNull=" + map.getOrDefault("nullable", 99));

        System.out.println("putAbsentNullable="
                + map.putIfAbsent("nullable", 3));
        System.out.println("putAbsentPresent="
                + map.putIfAbsent("present", 999));

        System.out.println("computed="
                + map.computeIfAbsent("created", key -> 5));
        System.out.println("ifPresent="
                + map.computeIfPresent("present", (key, old) -> old + 2));
        System.out.println("merged="
                + map.merge("present", 4, Integer::sum));

        System.out.println("firstMerge="
                + map.merge("temporary", 7, Integer::sum));
        System.out.println("computedTemporary="
                + map.compute("temporary", (key, old) -> old * 2));

        System.out.println("removeWrong="
                + map.remove("temporary", 13));
        System.out.println("removeRight="
                + map.remove("temporary", 14));
        System.out.println("replaceRight="
                + map.replace("present", 16, 20));

        System.out.println("final=" + map);
    }
}
~~~

Biên dịch và chạy với JDK 17+:

~~~text
javac --release 17 MapDefaultMethodsDemo.java
java MapDefaultMethodsDemo
~~~

Stdout:

~~~text
present=10
missing=99
mappedNull=null
putAbsentNullable=null
putAbsentPresent=10
computed=5
ifPresent=12
merged=16
firstMerge=7
computedTemporary=14
removeWrong=false
removeRight=true
replaceRight=true
final={present=20, nullable=3, created=5}
~~~

**Phân tích kết quả:**

1. getOrDefault của present là 10; key missing không có mapping nên nhận 99; key nullable có mapping đến null nên nhận null.
2. putIfAbsent của nullable tạo mapping 3 và trả old null. Với present đang là 10, putIfAbsent không ghi đè 999.
3. computeIfAbsent tạo key created=5.
4. computeIfPresent tăng present từ 10 lên 12, merge cộng 4 thành 16.
5. merge tạo temporary=7 khi chưa có value, compute nhân đôi thành 14.
6. remove với expected value 13 không khớp; remove với 14 xóa thành công.
7. replace có điều kiện thay present từ 16 thành 20.
8. LinkedHashMap duy trì thứ tự chèn key hiện hữu, nên dòng final xác định. HashMap thông thường không cam kết một iteration order tương đương.

**Giới hạn:** Ví dụ này chỉ kiểm chứng ngữ nghĩa tuần tự. Một Map mutable dùng đúng với một thread không phải bằng chứng nó an toàn khi chia sẻ cho nhiều thread.

## 10. Ví dụ hoàn chỉnh 2: null, xóa mapping và Map không sửa được

Tạo file **MapNullContractDemo.java**:

~~~java
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class MapNullContractDemo {
    public static void main(String[] args) {
        Map<String, String> map = new LinkedHashMap<>();
        map.put("slot", null);

        System.out.println("hadSlot=" + map.containsKey("slot"));
        System.out.println("fill=" + map.computeIfAbsent(
                "slot", key -> "filled"
        ));
        System.out.println("nullCompute=" + map.computeIfAbsent(
                "notCreated", key -> null
        ));
        System.out.println("notCreated="
                + map.containsKey("notCreated"));

        System.out.println("removeWithIfPresent="
                + map.computeIfPresent("slot", (key, old) -> null));
        System.out.println("slotExists=" + map.containsKey("slot"));

        System.out.println("mergeFirst="
                + map.merge("fresh", "x", String::concat));
        System.out.println("mergeSecond="
                + map.merge("fresh", "y", String::concat));
        System.out.println("mergeDelete="
                + map.merge("fresh", "z", (left, right) -> null));
        System.out.println("freshExists=" + map.containsKey("fresh"));

        System.out.println("computeNew="
                + map.compute("new", (key, old) ->
                        old == null ? "one" : "two"));
        map.replaceAll((key, value) -> value.toUpperCase());
        System.out.println("final=" + map);

        try {
            Map.of("a", 1).compute("a", (key, value) -> value + 1);
        } catch (UnsupportedOperationException expected) {
            System.out.println("immutable=UnsupportedOperationException");
        }

        try {
            new ConcurrentHashMap<String, Integer>().put(null, 1);
        } catch (NullPointerException expected) {
            System.out.println("concurrentNullKey=NullPointerException");
        }
    }
}
~~~

Chạy:

~~~text
javac --release 17 MapNullContractDemo.java
java MapNullContractDemo
~~~

Stdout:

~~~text
hadSlot=true
fill=filled
nullCompute=null
notCreated=false
removeWithIfPresent=null
slotExists=false
mergeFirst=x
mergeSecond=xy
mergeDelete=null
freshExists=false
computeNew=one
final={new=ONE}
immutable=UnsupportedOperationException
concurrentNullKey=NullPointerException
~~~

**Điểm cần nhớ:** computeIfAbsent xử lý key mapped-to-null như trường hợp cần tính, trong khi mapper trả null không ghi value mới. computeIfPresent và merge có thể **xóa mapping** khi remapping trả null. Map.of không sửa được nên thao tác cố thay value ném UnsupportedOperationException. ConcurrentHashMap cấm null key/value nên không dùng null làm sentinel trạng thái.

## 11. ConcurrentMap và ConcurrentHashMap có cùng bảo đảm không?

**Không nên coi interface ConcurrentMap là tên khác của ConcurrentHashMap.**

ConcurrentMap định nghĩa những thao tác conditional update dùng trong môi trường đồng thời. Một số default method của ConcurrentMap triển khai bằng vòng lặp đọc value, thử conditional replace/remove/putIfAbsent và **retry nếu có tranh chấp**.

Ví dụ diễn biến có thể xảy ra:

~~~text
Thread A đọc value=10
Thread B đổi value thành 11
Thread A tính newValue=12 từ old=10
Thread A thử conditional replace(10,12) thất bại
Thread A đọc lại value và có thể tính function lần nữa
~~~

JavaDoc ConcurrentMap cho biết khi nhiều thread update, một số default compute/merge/replaceAll **có thể gọi mapping/remapping function nhiều lần** cho cùng một key. Vì vậy function nên thuần, ngắn, không tự sửa Map và không chứa side effect không thể lặp an toàn.

Đối với **ConcurrentHashMap**, JavaDoc mô tả các override mạnh hơn:

- computeIfAbsent: nguyên tử theo invocation; mapping function gọi đúng một lần trong invocation nếu key absent, nếu present thì không gọi.
- computeIfPresent và compute: invocation nguyên tử theo key với remapping function, trong phạm vi được document.
- merge: gộp value theo key nguyên tử.
- putIfAbsent, remove(key,value), replace có các conditional update nguyên tử.

Một số update cạnh tranh có thể bị chặn khi function chạy. Mapping/remapping function không được sửa chính ConcurrentHashMap trong lúc compute; cập nhật đệ quy được phát hiện có thể ném IllegalStateException.

**Không hiểu “nguyên tử” là exactly-once cho side effect bên ngoài.** Hàm có thể throw hoặc request bị thử lại ở tầng ứng dụng; một hoạt động DB/email ngoài map có thể đã xảy ra. Nếu cần bảo đảm giao dịch, dùng idempotency hoặc transaction tương ứng.

## 12. Ví dụ hoàn chỉnh 3: lost update được chứng minh bằng CyclicBarrier

Ngay cả với ConcurrentHashMap, chuỗi get rồi put không nguyên tử. Ví dụ sau dùng CyclicBarrier để buộc cả hai task đều đọc old=0 **trước** khi ghi; không phụ thuộc một lịch lập lịch tình cờ.

Tạo file **SplitReadWriteRaceDemo.java**:

~~~java
import java.util.concurrent.Callable;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CyclicBarrier;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class SplitReadWriteRaceDemo {
    public static void main(String[] args) throws Exception {
        ConcurrentHashMap<String, Integer> map =
                new ConcurrentHashMap<>();
        map.put("hits", 0);

        CyclicBarrier bothRead = new CyclicBarrier(2);
        Callable<Void> unsafeIncrement = () -> {
            int old = map.get("hits");
            bothRead.await();
            map.put("hits", old + 1);
            return null;
        };

        ExecutorService executor = Executors.newFixedThreadPool(2);
        try {
            Future<Void> left = executor.submit(unsafeIncrement);
            Future<Void> right = executor.submit(unsafeIncrement);
            left.get();
            right.get();
        } finally {
            executor.shutdownNow();
        }

        System.out.println("afterSplitReadWrite=" + map.get("hits"));

        map.compute("hits", (key, old) -> old + 1);
        map.compute("hits", (key, old) -> old + 1);
        System.out.println("afterComputeTwice=" + map.get("hits"));
    }
}
~~~

Chạy:

~~~text
javac --release 17 SplitReadWriteRaceDemo.java
java SplitReadWriteRaceDemo
~~~

Stdout:

~~~text
afterSplitReadWrite=1
afterComputeTwice=3
~~~

Cả hai worker đã đọc 0, nên cuối cùng cả hai ghi 1, làm mất một phép tăng. Không được “sửa” bằng barrier trong code nghiệp vụ; barrier chỉ làm race dễ quan sát. Hai lời gọi compute sau đó tăng từ 1 lên 3. Đoạn compute cuối thực hiện tuần tự trong ví dụ; muốn minh họa tranh chấp thực sự, xem ví dụ kế tiếp.

## 13. Ví dụ hoàn chỉnh 4: cập nhật một key đồng thời bằng compute

Tạo file **ConcurrentMapCounterDemo.java**:

~~~java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class ConcurrentMapCounterDemo {
    public static void main(String[] args) throws Exception {
        final int workers = 4;
        final int iterations = 2500;

        ConcurrentHashMap<String, Integer> counts =
                new ConcurrentHashMap<>();
        CountDownLatch start = new CountDownLatch(1);
        ExecutorService executor = Executors.newFixedThreadPool(workers);

        try {
            List<Future<?>> futures = new ArrayList<>();
            for (int i = 0; i < workers; i++) {
                futures.add(executor.submit(() -> {
                    try {
                        start.await();
                        for (int j = 0; j < iterations; j++) {
                            counts.compute("hits",
                                    (key, old) -> old == null ? 1 : old + 1);
                        }
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        throw new IllegalStateException(e);
                    }
                }));
            }

            start.countDown();
            for (Future<?> future : futures) {
                future.get();
            }
        } finally {
            executor.shutdownNow();
        }

        counts.merge("bonus", 5, Integer::sum);
        counts.merge("bonus", 3, Integer::sum);
        counts.computeIfAbsent("seed", key -> 42);

        Map<String, Integer> ordered = new TreeMap<>(counts);
        System.out.println("hits=" + counts.get("hits"));
        System.out.println("counts=" + ordered);
    }
}
~~~

Chạy:

~~~text
javac --release 17 ConcurrentMapCounterDemo.java
java ConcurrentMapCounterDemo
~~~

Stdout:

~~~text
hits=10000
counts={bonus=8, hits=10000, seed=42}
~~~

Có 4 task, mỗi task gọi compute 2500 lần trên key hits, tổng cộng 10000 lần. ConcurrentHashMap đảm bảo từng lần cập nhật trên key theo contract nên không mất phép tăng. CountDownLatch làm các task có thể bắt đầu gần nhau nhưng không cố định thứ tự thực thi. Future.get chờ các task hoàn thành và chuyển exception về caller. Sau khi hoàn tất, merge thêm bonus thành 8 và computeIfAbsent tạo seed=42; TreeMap chỉ nhằm in các key theo thứ tự ổn định.

**Chú ý số học:** Integer có miền hữu hạn. Với counter quy mô lớn, cân nhắc long/AtomicLong/LongAdder và đánh giá tràn số, yêu cầu atomic snapshot và contention trước khi tối ưu.

## 14. Một Map concurrent không bảo vệ object value mutable

Giả sử:

~~~java
// PHẢN VÍ DỤ: groups là ConcurrentHashMap<String,List<String>>.
groups.computeIfAbsent(key, k -> new ArrayList<>()).add(item);
~~~

computeIfAbsent có thể tạo List mới nguyên tử, nhưng .add nằm **sau khi function trả về**, không thuộc atomic update. Hai thread có thể cùng add vào một ArrayList, gây race. Để giải quyết, có thể:

1. Giữ value là **immutable List** và dùng compute tạo List mới từ old, thêm phần tử trên bản sao rồi trả List.copyOf.
2. Dùng một loại concurrent value collection phù hợp nếu có nhu cầu thay đổi sau khi đọc.
3. Với bộ đếm, dùng LongAdder hoặc AtomicLong theo yêu cầu.
4. Nếu thu thập Stream, dùng collector như groupingBy/groupingByConcurrent thay vì update Map chung một cách tùy tiện.

Cập nhật đồng thời của **một mapping** khác với an toàn đồng thời của object được value tham chiếu.

## 15. Ví dụ hoàn chỉnh 5: immutable replacement và LongAdder

Tạo file **AtomicValuePatternsDemo.java**:

~~~java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.LongAdder;

public class AtomicValuePatternsDemo {
    public static void main(String[] args) {
        ConcurrentHashMap<String, List<String>> teams =
                new ConcurrentHashMap<>();

        teams.compute("dev", (key, old) -> {
            List<String> next = new ArrayList<>(
                    old == null ? List.of() : old);
            next.add("An");
            return List.copyOf(next);
        });

        teams.compute("dev", (key, old) -> {
            List<String> next = new ArrayList<>(
                    old == null ? List.of() : old);
            next.add("Binh");
            return List.copyOf(next);
        });

        System.out.println("team=" + teams.get("dev"));

        ConcurrentHashMap<String, LongAdder> frequencies =
                new ConcurrentHashMap<>();

        List.of("red", "blue", "red", "red")
                .parallelStream()
                .forEach(word -> frequencies
                        .computeIfAbsent(word, key -> new LongAdder())
                        .increment());

        Map<String, Long> counts = new TreeMap<>();
        frequencies.forEach((key, adder) ->
                counts.put(key, adder.sum()));

        System.out.println("counts=" + counts);
    }
}
~~~

Chạy:

~~~text
javac --release 17 AtomicValuePatternsDemo.java
java AtomicValuePatternsDemo
~~~

Stdout:

~~~text
team=[An, Binh]
counts={blue=1, red=3}
~~~

Trong teams.compute, logic chỉ đọc List cũ và tạo một List mới, không sửa trực tiếp shared ArrayList. Vì thế, khi hai invocation tranh chấp cùng key trên ConcurrentHashMap, việc thay mapping có thể được phối hợp nguyên tử. Đây là **copy-on-write theo key**, có chi phí sao chép; không nên dùng mù quáng nếu một key chứa danh sách rất lớn với nhiều update.

Trong phần LongAdder, computeIfAbsent đưa một object counter vào Map an toàn; bản thân LongAdder.increment hỗ trợ cập nhật đồng thời. LongAdder.sum **không phải một atomic snapshot nếu còn thread đang tăng**. Ở đây chỉ đọc sum sau khi parallelStream hoàn tất nên kết quả xác định.

## 16. Mapping/remapping function nên có tính chất gì?

JavaDoc cảnh báo function dùng cho compute và merge không nên sửa Map đang được cập nhật. Với ConcurrentHashMap, mapping function **không được cập nhật chính Map trong computation**. Khi recursion dẫn đến việc cập nhật không thể hoàn thành, có thể có IllegalStateException.

~~~java
// PHẢN VÍ DỤ:
map.computeIfAbsent("a", key -> {
    map.put("b", 2);
    return 1;
});
~~~

Hãy tránh cập nhật cùng Map trong function. Thay vì vậy, function tính value từ input đã biết, trả về value, còn các bước cập nhật khác được thực hiện ở một phạm vi có thiết kế đồng bộ riêng.

Nếu function có side effect như gửi email, trừ tiền, thanh toán, ghi message hay gọi I/O, một ConcurrentMap dùng retry có thể thực hiện function nhiều lần. Ngay cả với ConcurrentHashMap có contract invocation atomic, side effect ngoài Map **không** trở thành transaction. Khi cần exactly-once ở mức nghiệp vụ, sử dụng giao thức idempotency hoặc cơ chế transaction/outbox phù hợp.

Function nên ngắn, không block lâu để hạn chế contention và deadlock; đặc biệt không lồng cập nhật đệ quy lên cùng Map.

### Khi function trả null hoặc throw

- computeIfAbsent: null nghĩa là không tạo value non-null.
- computeIfPresent: null nghĩa là xóa mapping cũ.
- compute: null nghĩa là xóa mapping hoặc để vắng.
- merge: remapper trả null nghĩa là xóa mapping; đối số value phải non-null.
- Function ném runtime exception: lỗi được chuyển ra ngoài; không coi đó là một thành công âm thầm.
- Map.of và những Map không sửa được có thể ném UnsupportedOperationException nếu yêu cầu thay đổi mapping.

Cần kiểm tra null đầu vào tùy implementation: ConcurrentHashMap từ chối null key/value, trong khi HashMap có thể cho null; null trong Map không nên dùng để làm ba trạng thái “đang tải/lỗi tải/vắng mặt” nếu cần phân biệt rõ.

## 17. Collections.synchronizedMap vẫn có giới hạn

Collections.synchronizedMap(backing) tạo wrapper đồng bộ hóa các thao tác qua wrapper. Nhưng **nhiều lời gọi liên tiếp** không tự gộp thành một critical section.

~~~java
// Mảnh mã với synchronizedCounts là synchronizedMap.
int old = synchronizedCounts.getOrDefault("hits", 0);
synchronizedCounts.put("hits", old + 1);
~~~

Dù get và put riêng được đồng bộ bởi wrapper, thread khác vẫn có thể xen vào giữa hai lời gọi. Khi cần giữ nguyên tử cho chuỗi và tất cả thread đều dùng **cùng lock**, có thể:

~~~java
// Mảnh mã:
synchronized (synchronizedCounts) {
    int old = synchronizedCounts.getOrDefault("hits", 0);
    synchronizedCounts.put("hits", old + 1);
}
~~~

Duyệt collection views của synchronizedMap cũng phải tuân thủ hướng dẫn đồng bộ hóa trong JavaDoc; không mặc định mọi vòng lặp đã là snapshot an toàn. Khi có nhiều key cập nhật độc lập, ConcurrentHashMap có thể giảm contention so với một khóa chung, nhưng phải dùng đúng atomic method và tránh mutable value race.

## 18. Một key không bằng transaction trên nhiều key

Ví dụ chuyển 10 đơn vị từ A sang B:

~~~java
// PHẢN VÍ DỤ cho giao dịch nhiều key:
balances.compute("A", (key, old) -> old - 10);
balances.compute("B", (key, old) -> old + 10);
~~~

Ngay cả khi balances là ConcurrentHashMap, hai compute này là **hai thao tác**. Thread khác có thể đọc sau khi A bị trừ mà B chưa được cộng. Nếu có lỗi hoặc một phần transaction thất bại, hệ thống có thể vi phạm bất biến tổng số dư. Atomicity theo key **không phải transaction tài chính nhiều key**; cần database transaction, lock hoặc thiết kế trạng thái có ranh giới atomic phù hợp.

Với forEach hay replaceAll trên ConcurrentHashMap, việc duyệt entry cũng không đảm bảo snapshot nhất quán tại một thời điểm cho toàn Map; các iterator của ConcurrentHashMap thường là weakly consistent. Nếu nghiệp vụ cần snapshot nhiều key nhất quán, phải thiết kế cơ chế riêng.

## 19. Lỗi phổ biến cần tránh

### 19.1. Dùng HashMap chia sẻ giữa các thread

~~~java
// PHẢN VÍ DỤ: requests, req.key do ứng dụng định nghĩa.
Map<String, Integer> counts = new HashMap<>();
requests.parallelStream().forEach(req ->
        counts.merge(req.key(), 1, Integer::sum));
~~~

HashMap không thread-safe. Nếu đang dùng Stream, cân nhắc collector đúng như groupingBy/counting hoặc groupingByConcurrent. Nếu thật sự cần shared updates, dùng concurrent collection với atomic update theo contract.

### 19.2. Tách get rồi put trên ConcurrentHashMap

Như ví dụ 3, từng lời gọi thread-safe không làm toàn bộ phép tăng nguyên tử. Dùng merge/compute/conditional replace phù hợp.

### 19.3. Cập nhật List value sau computeIfAbsent

Một ConcurrentHashMap không làm List bên trong tự thread-safe. Dùng immutable replacement hoặc concurrent value.

### 19.4. Đặt side effect vào remapping function

ConcurrentMap default có thể retry. Side effect ngoài Map không được rollback bởi atomic map operation. Tránh những tác vụ không idempotent trong function.

### 19.5. Nhầm old==null với key không tồn tại

Trên HashMap, old==null có thể là key mapped-to-null. Khi cần phân biệt, dùng containsKey trong một phạm vi dữ liệu được kiểm soát; nếu cập nhật đồng thời, phải bảo đảm kiểm tra trạng thái cũng có ranh giới nhất quán.

### 19.6. Cho rằng replaceAll là transaction

Mỗi entry có thể được xử lý vào thời điểm khác nhau; nhiều key không tự có atomic snapshot.

### 19.7. Dùng Map.of rồi cố sửa

Map.of không sửa được. Nếu cần map mutable, khởi tạo new HashMap<>(Map.of(...)) hoặc LinkedHashMap theo yêu cầu thứ tự. Đừng bắt UOE rồi nuốt lỗi để bỏ qua cập nhật.

### 19.8. Cho rằng function của mọi ConcurrentMap chỉ chạy một lần

Một số default methods dùng retry; hãy đọc JavaDoc của implementation thay vì suy ra từ tên ConcurrentMap.

### 19.9. Tăng số thread khi một key quá nóng

Nhiều thread cùng compute một key có thể tạo contention. Xem xét batching, phân hoạch, LongAdder hoặc thay đổi mô hình dữ liệu trước khi tăng worker.

## 20. Lựa chọn theo tình huống

| Tình huống | Lựa chọn gợi ý |
|---|---|
| Map local không chia sẻ giữa thread | HashMap hoặc LinkedHashMap với default methods |
| Cập nhật counter theo key từ nhiều thread | ConcurrentHashMap.merge/compute |
| Counter thống kê throughput cao, đọc sau khi kết thúc batch | ConcurrentHashMap<K,LongAdder> |
| Tính value khi thiếu key | computeIfAbsent với function ngắn, ít side effect |
| Thay value khi old khớp | replace(key,old,new) trên implementation có atomic override |
| Xóa khi value chưa đổi | remove(key,value) trên implementation có atomic override |
| Thu thập dữ liệu Stream song song | Collector phù hợp thay vì update shared HashMap |
| Cần transaction nhiều key | Lock/transaction hoặc mô hình state thích hợp |
| Cần snapshot đồng bộ toàn Map | Cơ chế snapshot/đồng bộ ở mức ứng dụng, không chỉ forEach |
| Cache có I/O, TTL và eviction | Xem xét cache chuyên dụng và chính sách loading |
| Map có value mutable | Đồng bộ value, chọn value concurrent hoặc thay value bất biến |

## 21. Câu hỏi tự kiểm tra

**Câu 1.** Map.compute và merge có nguyên tử trên mọi Map không?

*Đáp án:* Không. Map default methods không bảo đảm synchronization/atomicity; phải xem implementation.

**Câu 2.** HashMap có key "x" -> null, getOrDefault("x",99) trả gì?

*Đáp án:* Trả null vì key có mapping. Nếu key vắng mới trả 99.

**Câu 3.** computeIfAbsent chạy function khi key đã map đến null không?

*Đáp án:* Có. Nó coi value null như chưa có value non-null.

**Câu 4.** computeIfPresent remapper trả null thì sao?

*Đáp án:* Mapping bị xóa.

**Câu 5.** Tại sao get và put trên ConcurrentHashMap đều thread-safe nhưng get+put có thể mất update?

*Đáp án:* Vì hai lần gọi không phải một atomic operation; thread khác có thể xen vào.

**Câu 6.** Tại sao function trong một số default method ConcurrentMap có thể chạy nhiều lần?

*Đáp án:* Chúng có thể dùng vòng lặp retry sau conditional update thất bại khi tranh chấp.

**Câu 7.** computeIfAbsent(... -> new ArrayList()).add(...) có bảo vệ lần add không?

*Đáp án:* Không. Lần add diễn ra trên shared mutable List ngoài atomic map update.

**Câu 8.** Hai compute trên A và B có tạo transaction hai key không?

*Đáp án:* Không. Atomicity per-key không là transaction multi-key.

**Câu 9.** LongAdder.sum có phải snapshot nguyên tử khi đang tăng không?

*Đáp án:* Không. Đọc sau khi toàn bộ cập nhật hoàn thành như ví dụ 5 cho kết quả xác định.

**Câu 10.** Nên làm gì khi muốn gửi email trong compute/merge?

*Đáp án:* Tách side effect khỏi function và thiết kế idempotency/transaction theo quy trình nghiệp vụ, không mặc nhiên coi function chạy đúng một lần trên mọi implementation.

## 22. Checklist cuối bài

- Đã xác định object runtime là HashMap, synchronizedMap, ConcurrentMap hay ConcurrentHashMap?
- Đã đọc contract atomicity **của method trong implementation đó**?
- Đã phân biệt key vắng với key mapped-to-null nếu nghiệp vụ cần?
- Đã tránh ghép get+put hoặc containsKey+put thành thao tác đòi hỏi nguyên tử không có lock?
- Mapping/remapping function có ngắn, không tự sửa Map và tránh side effect không idempotent?
- Value mutable có được bảo vệ đúng sau khi lấy từ Map?
- Có yêu cầu transaction nhiều key hoặc snapshot nhất quán không?
- Có xử lý UOE, NPE, overflow và exception theo nguồn gốc thật?
- Test concurrency có đợi tất cả task, kiểm tra kết quả và exception?
- Có dùng kiến thức JDK còn được duy trì, không suy ra từ một chi tiết implementation tình cờ?
