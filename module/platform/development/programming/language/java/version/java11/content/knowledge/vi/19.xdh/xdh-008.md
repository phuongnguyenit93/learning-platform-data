# XDH: Dẫn xuất khóa theo giao thức thay vì dùng trực tiếp mọi byte bí mật (Java 11)

## 1. Mục tiêu và lý do cần KDF

Trong Java 11, XDH cho phép hai bên thỏa thuận một **shared secret** bằng X25519 hoặc X448. Kết quả thỏa thuận khóa là **nguyên liệu đầu vào (input keying material, IKM)**, không phải “một dãy byte để sử dụng trực tiếp cho tất cả thuật toán mã hóa, MAC, nonce và hai chiều truyền”.

Giả sử Alice và Bob trao đổi public key X25519:

```text
Alice có private_A và public_A.
Bob   có private_B và public_B.

Alice tính Z_A = X25519(private_A, public_B)
Bob   tính Z_B = X25519(private_B, public_A)

Nếu trao đổi hợp lệ: Z_A == Z_B
```

Thành công ở bước này **không** đồng nghĩa đã có toàn bộ bảo mật của phiên. Còn cần giải đáp: đối tác có thực sự là Alice/Bob không, giao thức phiên bản nào, khóa nào dùng cho chiều nào, dùng AES-GCM hay thuật toán nào, mỗi message có nonce riêng không, ràng buộc khóa với transcript handshake ra sao và xử lý khóa khi phiên kết thúc thế nào.

Bài học tập trung vào **dẫn xuất khóa theo giao thức bằng HKDF** và những lỗi gây ra khi bỏ qua bước này. Sau bài, bạn sẽ:

- Hiểu raw XDH shared secret `Z` khác một khóa lưu lượng (`traffic key`).
- Biết vai trò của **HKDF-Extract(salt, IKM)**, **HKDF-Expand(PRK, info, L)** theo RFC 5869.
- Dùng `info` để tách **client→server**, **server→client**, traffic key, exporter và mục đích khác.
- Biết vì sao transcript hash, public keys, role và authentication quan trọng.
- Viết được ví dụ Java 11 với `KeyAgreement`, `Mac`/`HmacSHA256` mà không cần API chỉ xuất hiện ở JDK mới.
- Đọc và hiểu sự khác biệt giữa API Java 11 với `javax.crypto.KDF` từ Java 25.
- Kiểm thử output, lỗi all-zero, sai context, sai salt và sự không tương thích encoding.

Kiến thức từ RFC 7748 và RFC 5869 vẫn áp dụng trên các **JDK hiện đại**. Không tự thiết kế một giao thức production chỉ từ vài dòng XDH + HKDF; ưu tiên TLS 1.3, HPKE hoặc giao thức đã được phân tích và triển khai bởi thư viện được bảo trì.

## 2. XDH trong Java 11: X25519 và X448

**XDH** là thuật toán Diffie–Hellman sử dụng các hàm X25519/X448 của RFC 7748. Java 11 hỗ trợ chúng qua các API tiêu chuẩn:

| API | Cách dùng | Ý nghĩa |
| --- | --- | --- |
| `KeyPairGenerator.getInstance("X25519")` | Tạo cặp private/public key | Tạo bí mật ephemeral và public key để trao đổi |
| `NamedParameterSpec.X25519` | Chỉ rõ curve | Cố định nhóm thuật toán |
| `KeyAgreement.getInstance("X25519")` | Thỏa thuận X25519 | Tính raw shared secret từ private local + public peer |
| `agreement.doPhase(peerPublic, true)` | Một lượt phase | Đưa public key peer vào phép tính |
| `agreement.generateSecret()` | Trả `byte[]` | Raw `Z`; **chưa có key schedule theo protocol** |
| `Mac.getInstance("HmacSHA256")` | Thực thi HKDF-SHA-256 | Extract/Expand theo RFC 5869 |
| `SecretKeySpec(keyBytes, "AES")` | Dùng **key đã dẫn xuất**, không phải raw `Z` | Chuẩn bị khóa cho primitive như AES-GCM |

**Kích thước** raw output XDH: X25519 là **32 byte**, X448 là **56 byte** (RFC 7748). Đây là kích thước của hàm XDH, **không** phải lời cam kết rằng 32 byte đó nên được dùng làm AES-256 cho mọi giao thức.

Ví dụ **trích đoạn Java 11**:

```java
KeyPairGenerator generator =
        KeyPairGenerator.getInstance("X25519");
generator.initialize(
        NamedParameterSpec.X25519, new SecureRandom());
KeyPair own = generator.generateKeyPair();

KeyAgreement agreement = KeyAgreement.getInstance("X25519");
agreement.init(own.getPrivate());
agreement.doPhase(peerPublicKey, true);
byte[] z = agreement.generateSecret();
```

Đoạn trên cần các import `java.security.KeyPairGenerator`, `KeyPair`, `SecureRandom`, `java.security.spec.NamedParameterSpec` và `javax.crypto.KeyAgreement`; `peerPublicKey` là `PublicKey` X25519 hợp lệ. Đây **không phải chương trình đầy đủ**. Private key phải được giữ kín; public key có thể trao đổi nhưng phải **xác thực** theo thiết kế handshake.

Lưu ý liên thông giữa các hệ thống: `PublicKey.getEncoded()` theo JCA thường là **X.509 SubjectPublicKeyInfo/SPKI DER**, không phải dãy **32-byte raw X25519 u-coordinate** dùng ở nhiều wire protocol. Đừng coi public key nào được mã hóa bằng `getEncoded()` cũng dài 32 byte. Cần quy định rõ format, cách parse, curve ID, thứ tự các trường và test interop.

## 3. Tại sao không đưa raw `Z` vào mọi nơi cần khóa?

Đây là **anti-pattern**:

```java
byte[] z = agreement.generateSecret();

// Không dùng kiểu phân phối key material như thế này:
SecretKeySpec encryptKey = new SecretKeySpec(z, "AES");
SecretKeySpec macKey = new SecretKeySpec(z, "HmacSHA256");
byte[] otherKey = Arrays.copyOf(z, 16);
```

Đây là mã minh họa lỗi thiết kế, không phải lời khuyên dùng trong ứng dụng. Vấn đề không chỉ là độ dài `byte[]`:

1. **Không phân tách mục đích (domain separation).** Cùng byte xuất hiện trong AES key, MAC key, khóa hai chiều hoặc hai phiên bản giao thức khác nhau.
2. **Không ràng buộc handshake.** Raw secret `Z` không tự chứa protocol ID, role, direction, thuật toán, transcript hash hay danh tính peer đã xác thực.
3. **Không có lịch khóa (key schedule).** Việc cắt 16 byte, lấy nửa đầu/nửa cuối, băm SHA-256 đơn lẻ hoặc Base64 **không tự định nghĩa** quan hệ giữa traffic key, IV, exporter và rekey.
4. **Không kiểm tra input không hợp lệ.** Một số giá trị public key XDH đặc biệt có thể tạo shared secret toàn zero hoặc bị provider từ chối.
5. **Không cung cấp authentication.** MITM thay public keys vẫn có thể đàm phán thành công với từng phía riêng biệt.
6. **Không giải quyết yêu cầu của AEAD.** Ví dụ AES-GCM đòi hỏi nonce **không trùng cho mỗi encryption dưới cùng key** và kiểm tra authentication tag; raw Z không tự cung cấp nonce schedule.

Không phải mọi trường hợp đưa raw DH value vào primitive đều lập tức lộ plaintext, nhưng **đây không phải cơ sở cho một giao thức mật mã đúng và có thể đánh giá**. Thiết kế theo KDF của một giao thức được công bố, không tự suy diễn từ “Z dài 32 byte nên vừa đúng AES-256”.

## 4. HKDF theo RFC 5869: Extract rồi Expand

**HKDF (HMAC-based Extract-and-Expand Key Derivation Function)** có hai bước. Với **HKDF-SHA-256**, độ dài output của HMAC là **32 byte**.

```text
            X25519 / X448
          shared secret Z = IKM
                   |
           HKDF-Extract(salt, IKM)
                   |
              PRK (32 byte)
                   |
      +------------+-------------+
      |            |             |
    HKDF-        HKDF-         HKDF-
    Expand       Expand        Expand
    info=C2S     info=S2C      info=exporter
    L=32         L=32          L=32
      |            |             |
   K_client_    K_server_      K_export
   to_server    to_client
```

### 4.1. Extract: chuẩn hóa nguyên liệu bí mật

```text
PRK = HMAC-SHA256(key=salt, message=IKM)
```

- **IKM:** trong bài này là raw shared secret X25519/X448 `Z`.
- **salt:** giá trị theo protocol; không bắt buộc bí mật, hai bên phải dùng **cùng byte**. RFC 5869 khuyến nghị salt phù hợp, thường ngẫu nhiên công khai hoặc từ các nonces của handshake.
- **PRK:** pseudorandom key dùng làm **khóa trung gian** cho Expand. Không in log, không gửi mạng và không dùng làm một AES key “mặc định” cho mọi mục đích.

RFC 5869 cho phép bỏ salt; khi đó Extract dùng chuỗi **HashLen byte zero** (đối với SHA-256 là 32 byte). Đây là một quy tắc đã định nghĩa, không có nghĩa luôn nên dùng salt zero nếu giao thức có thiết kế nonces/salt tốt hơn.

**Salt không tạo entropy từ con số không.** Đặc biệt, HKDF không phải password KDF làm chậm dò mật khẩu. Với password do người dùng đặt, phải dùng phương thức password hashing/KDF phù hợp (ví dụ Argon2id hoặc PBKDF2 theo yêu cầu), chứ không kỳ vọng HKDF làm password yếu thành nguồn bí mật mạnh.

### 4.2. Expand: tách output theo `info` và `L`

```text
OKM = HKDF-Expand(PRK, info, L)
```

- **info:** chuỗi byte mô tả context và purpose, do giao thức định nghĩa.
- **L:** số byte output cần thiết, ví dụ 32 cho AES-256 key, 16 cho AES-128 key, hay 12 cho một base IV trong giao thức AEAD cụ thể.
- **OKM:** output keying material cho đúng nhãn.

HKDF-Expand xây các block:

```text
T(0) = empty
T(i) = HMAC-SHA256(PRK, T(i-1) || info || one_byte(i))
OKM  = first L bytes of T(1)||T(2)||...
```

`one_byte(i)` là **một byte** từ 1 đến 255, không phải chuỗi ASCII `"1"`. Với SHA-256, **`0 <= L <= 255 × 32 = 8160`**. Không tự tăng chiều dài vô giới hạn bằng cách bỏ qua counter rule.

Nếu cùng PRK và cùng `info`, output 16 byte là **prefix của output 32 byte**. Vì vậy **đổi `L` không tạo domain separation**. Muốn hai khóa độc lập theo mục đích, phải dùng `info` khác và làm đúng toàn bộ key schedule.

### 4.3. `info` phải được định nghĩa như một phần của giao thức

Ví dụ **các tên nhãn đọc cho người**, không phải wire format chuẩn:

```text
app-xdh/v1 | client-to-server | AES-256-GCM | traffic-key
app-xdh/v1 | server-to-client | AES-256-GCM | traffic-key
app-xdh/v1 | client-to-server | AES-256-GCM | base-iv
app-xdh/v1 | exporter
```

Một giao thức phải định nghĩa **byte encoding chính xác**: UTF-8, length-prefix, sequence, suite ID, transcript hash. Nếu ghép trường không có ranh giới:

```text
"ab" + "c"  -> "abc"
"a"  + "bc" -> "abc"
```

thì hai bộ tham số có thể tạo cùng `info`. Nên dùng format không mơ hồ: field length, fixed tags hoặc cấu trúc được giao thức chuẩn hóa.

## 5. Transcript binding, thứ tự và xác thực

Để khóa chỉ sử dụng cho **đúng phiên, đúng role và đúng protocol**, KDF/handshake thường ràng buộc:

| Giá trị | Vì sao quan trọng? |
| --- | --- |
| Protocol ID/version/ciphersuite | Tránh dùng khóa của giao thức khác hoặc sai thuật toán |
| Vai trò client/server | Thống nhất ai mã hóa bằng key chiều nào |
| Direction | Khác `client→server` và `server→client` |
| Mục đích | Traffic key, exporter, base IV, resumption/rekey dùng nhãn riêng |
| Public keys | Gắn vào phiên thỏa thuận cụ thể |
| Nonces/salt | Đưa randomness công khai theo thiết kế vào key schedule |
| Transcript hash | Khóa kết quả với toàn bộ handshake đúng thứ tự |
| Identity được xác thực | Tránh một đối tác giả mạo public key |

**Thứ tự phải giống nhau.** Nếu client băm `clientPublic||serverPublic` còn server băm `serverPublic||clientPublic` thì hash khác. Định nghĩa **client trước server** theo role, không lấy “public key của tôi” làm phần đầu ở cả hai phía.

**Hash transcript không tự xác thực danh tính.** Một MITM vẫn có thể đàm phán hai exchange riêng với client và server rồi tạo hai context hash riêng. Nếu không có signature/certificate/PSK đã xác thực, hai bên **không biết thật** ai sở hữu public key còn lại.

**Không thay key schedule chuẩn.** TLS 1.3 (RFC 8446) dùng `HKDF-Expand-Label` và transcript trong cấu trúc riêng; HPKE (RFC 9180) dùng labeled extract/expand gắn suite IDs. Không lấy một HKDF thông thường với `info="tls13"` rồi gọi đó là TLS-compatible. Với production hãy dùng implementation protocol đã được thẩm định.

## 6. Ví dụ Java 11 hoàn chỉnh: hai phía X25519, HKDF và tách key theo direction

Chương trình sau tạo **hai cặp khóa ephemeral** trong **cùng một JVM** để mô phỏng client và server, thực hiện `KeyAgreement` ở hai phía, tạo salt chung cho phiên, hash hai public keys theo đúng thứ tự role, HKDF-Extract rồi HKDF-Expand ra **hai key chiều truyền khác nhau**.

**Đây là ví dụ dẫn xuất khóa để học**, không phải một protocol có authentication hay một hệ thống encrypted messaging. Nó không trao đổi public key qua mạng, không xác thực peer, không xử lý AES-GCM nonce và không gửi ciphertext. Mã **không in secret** mà chỉ in các thuộc tính kiểm thử. Tạo file **`XdhHkdfProtocolDemo.java`**:

```java
import javax.crypto.KeyAgreement;
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.security.GeneralSecurityException;
import java.security.InvalidKeyException;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.MessageDigest;
import java.security.PrivateKey;
import java.security.PublicKey;
import java.security.SecureRandom;
import java.security.spec.NamedParameterSpec;
import java.util.Arrays;

public class XdhHkdfProtocolDemo {
    static final int HASH_LEN = 32;

    static byte[] agree(PrivateKey own, PublicKey peer)
            throws GeneralSecurityException {
        KeyAgreement ka = KeyAgreement.getInstance("X25519");
        ka.init(own);
        ka.doPhase(peer, true);
        byte[] z = ka.generateSecret();

        // Quét toàn bộ output và từ chối shared secret all-zero.
        int nonzero = 0;
        for (byte b : z) {
            nonzero |= b & 0xff;
        }
        if (z.length != 32 || nonzero == 0) {
            Arrays.fill(z, (byte) 0);
            throw new InvalidKeyException("Invalid X25519 secret");
        }
        return z;
    }

    static byte[] extract(byte[] salt, byte[] ikm)
            throws GeneralSecurityException {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(salt, "HmacSHA256"));
        return mac.doFinal(ikm);
    }

    static byte[] expand(byte[] prk, byte[] info, int length)
            throws GeneralSecurityException {
        if (prk.length < HASH_LEN ||
                length < 0 || length > 255 * HASH_LEN) {
            throw new IllegalArgumentException("Bad HKDF length");
        }
        byte[] result = new byte[length];
        byte[] previous = new byte[0];
        int written = 0;
        int counter = 1;

        while (written < length) {
            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(new SecretKeySpec(prk, "HmacSHA256"));
            mac.update(previous);
            mac.update(info);
            mac.update((byte) counter);
            byte[] block = mac.doFinal();

            int take = Math.min(block.length, length - written);
            System.arraycopy(block, 0, result, written, take);
            Arrays.fill(previous, (byte) 0);
            previous = block;
            written += take;
            counter++;
        }
        Arrays.fill(previous, (byte) 0);
        return result;
    }

    static void addField(MessageDigest digest, byte[] data) {
        // 4-byte big-endian length + data: tránh nhập nhằng field.
        digest.update(
                ByteBuffer.allocate(4).putInt(data.length).array());
        digest.update(data);
    }

    static byte[] context(PublicKey client, PublicKey server)
            throws GeneralSecurityException {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        addField(digest, "example-xdh-hkdf/v1"
                .getBytes(StandardCharsets.UTF_8));
        addField(digest, client.getEncoded());
        addField(digest, server.getEncoded());
        return digest.digest();
    }

    static byte[] info(String label, byte[] contextHash) {
        byte[] name = label.getBytes(StandardCharsets.UTF_8);
        return ByteBuffer.allocate(
                4 + name.length + contextHash.length)
                .putInt(name.length)
                .put(name)
                .put(contextHash)
                .array();
    }

    static void wipe(byte[] bytes) {
        if (bytes != null) {
            Arrays.fill(bytes, (byte) 0);
        }
    }

    public static void main(String[] args)
            throws GeneralSecurityException {
        KeyPairGenerator generator =
                KeyPairGenerator.getInstance("X25519");
        generator.initialize(
                NamedParameterSpec.X25519, new SecureRandom());

        KeyPair client = generator.generateKeyPair();
        KeyPair server = generator.generateKeyPair();
        byte[] zClient = null;
        byte[] zServer = null;
        byte[] prkClient = null;
        byte[] prkServer = null;
        byte[] keyC2SClient = null;
        byte[] keyC2SServer = null;
        byte[] keyS2C = null;

        try {
            zClient = agree(client.getPrivate(), server.getPublic());
            zServer = agree(server.getPrivate(), client.getPublic());

            // Chung một public salt cho phiên demo; thực tế theo protocol.
            byte[] salt = new byte[HASH_LEN];
            new SecureRandom().nextBytes(salt);

            byte[] transcript = context(
                    client.getPublic(), server.getPublic());
            prkClient = extract(salt, zClient);
            prkServer = extract(salt, zServer);

            byte[] infoC2S = info(
                    "client-to-server|AES-256-GCM|traffic-key",
                    transcript);
            byte[] infoS2C = info(
                    "server-to-client|AES-256-GCM|traffic-key",
                    transcript);

            keyC2SClient = expand(prkClient, infoC2S, 32);
            keyC2SServer = expand(prkServer, infoC2S, 32);
            keyS2C = expand(prkClient, infoS2C, 32);

            System.out.println("shared_secret_same="
                    + MessageDigest.isEqual(zClient, zServer));
            System.out.println("shared_secret_bytes=" + zClient.length);
            System.out.println("traffic_key_same="
                    + MessageDigest.isEqual(
                            keyC2SClient, keyC2SServer));
            System.out.println("traffic_key_bytes="
                    + keyC2SClient.length);
            System.out.println("directions_separated="
                    + !MessageDigest.isEqual(keyC2SClient, keyS2C));

            wipe(salt);
        } finally {
            wipe(zClient);
            wipe(zServer);
            wipe(prkClient);
            wipe(prkServer);
            wipe(keyC2SClient);
            wipe(keyC2SServer);
            wipe(keyS2C);
        }
    }
}
```

Biên dịch/chạy trên JDK 11 hoặc JDK mới có hỗ trợ target 11:

```bash
javac --release 11 -encoding UTF-8 XdhHkdfProtocolDemo.java
java XdhHkdfProtocolDemo
```

Đầu ra dự kiến (chỉ in Boolean/độ dài, không in secret):

```text
shared_secret_same=true
shared_secret_bytes=32
traffic_key_same=true
traffic_key_bytes=32
directions_separated=true
```

**Vì sao output như vậy?**

1. Hai phía sử dụng **private local + public peer** đúng hướng của Diffie–Hellman nên tính chung `Z`.
2. `Z` X25519 có độ dài 32 byte, còn `prkClient/prkServer` đều là HMAC-SHA-256 có 32 byte output.
3. Hai phía dùng cùng salt, `Z`, protocol context và `infoC2S` nên dẫn xuất cùng key cho **client→server**, bất kể role của phía đang tính.
4. Label `infoS2C` khác nên tạo key cho **server→client** khác key `C2S` (xác suất trùng do ngẫu nhiên về mặt mật mã là cực nhỏ).
5. Code dùng key pair và salt ngẫu nhiên, nên **byte bí mật thay đổi ở mỗi lần chạy**. Chỉ các bất biến được in mới có đầu ra dự kiến trên.
6. Kiểm tra all-zero sau `generateSecret()` là một lớp phòng vệ; một số provider có thể tự từ chối key trước bước này.
7. `addField` và `info` dùng độ dài 4 byte, giúp tránh nhập nhằng field. `context` băm **clientPublic trước serverPublic**, không “own trước peer”; sản phẩm thật cần bao gồm **handshake transcript đã xác thực**, không chỉ hai public keys.
8. `expand` đúng kiểu counter một byte và giới hạn `255 * 32` của RFC 5869.
9. `Arrays.fill` chỉ là biện pháp **best effort** giảm thời gian sống của một số mảng byte; JVM/crypto provider có thể giữ bản sao nội bộ. Không đảm bảo xóa sạch bí mật trong heap dump.

**Giới hạn quan trọng của code:**

- `extract(salt, ikm)` trong demo yêu cầu **salt không rỗng và được cung cấp rõ**; nếu muốn hỗ trợ chế độ “không salt” của RFC 5869 thì phải dùng `HashLen` byte zero, không truyền `new byte[0]` vào `SecretKeySpec` một cách tùy tiện.
- Đây là **code học tập HKDF**. Trong hệ thống thật nên dùng thư viện hoặc protocol đã được kiểm thử bằng test vectors và review bảo mật.
- Không có authentication, key confirmation, encrypted records, sequence number, chống replay, rotation, error response hay mạng thực.
- Hai bên ở cùng JVM cùng nhìn thấy salt. Với hai tiến trình riêng, salt và transcript phải được truyền/thống nhất theo protocol và peer identity phải được xác thực.
- Code không dùng khóa để mã hóa message; điều đó cố ý để không tạo một ví dụ AEAD dùng nonce sai.

## 7. Tách chiều và mục đích: `C2S`, `S2C`, traffic, exporter

Một protocol thực tế thường cần nhiều output:

```text
               XDH Z + salt
                     |
              HKDF-Extract
                     |
                   PRK
                     |
      +--------------+--------------+------------+
      |              |              |            |
  info(C2S,key)  info(S2C,key)  info(C2S,IV)  info(export)
      |              |              |            |
    K_C2S          K_S2C          IV_C2S      K_export
```

Tách nhãn giúp tránh tình huống cùng raw byte xuất hiện trong các primitive hoặc hướng truyền khác nhau. Khóa `K_C2S` phải dùng ở **client encrypt và server decrypt**; khóa `K_S2C` dùng ngược lại. Hai bên phải thống nhất role trong handshake.

**Nonce base khác nonce mỗi message.** Dù derive `IV_C2S` 12 byte từ HKDF, **không** được dùng cùng IV cho tất cả bản tin AES-GCM. Với AEAD, nonce cần **duy nhất trên từng phép mã hóa dưới cùng key**, thường từ base IV kết hợp sequence number theo thuật toán và record framing của giao thức chuẩn.

Trích đoạn **minh họa cách sử dụng khóa đã dẫn xuất** (không phải chương trình hoàn chỉnh):

```java
SecretKey aesKey = new SecretKeySpec(derivedTrafficKey, "AES");
GCMParameterSpec params = new GCMParameterSpec(128, uniqueNonce);
Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
cipher.init(Cipher.ENCRYPT_MODE, aesKey, params);
cipher.updateAAD(authenticatedHeader);
byte[] ciphertext = cipher.doFinal(plaintext);
```

Cần import `javax.crypto.SecretKey`, `javax.crypto.Cipher`, `javax.crypto.spec.SecretKeySpec`, `javax.crypto.spec.GCMParameterSpec` và khai báo `derivedTrafficKey` dài 32 byte, `uniqueNonce` dài 12 byte chưa từng dùng với cùng key, `authenticatedHeader`, `plaintext`. Không copy nguyên đoạn này và dùng nonce cố định; reuse nonce trong GCM có thể làm mất bí mật và integrity nghiêm trọng. Việc bảo đảm nonce, AAD, tag và sequence thuộc **giao thức record**, không được giải quyết tự động chỉ bằng HKDF.

## 8. Salt, vai trò, danh tính và transcript trong quy trình thật

Một quy trình khái niệm có thể được mô tả như sau:

1. **Thương lượng suite:** cả hai đồng ý curve, KDF, AEAD, protocol version và chính sách bảo mật.
2. **Tạo key ephemeral:** mỗi bên sinh X25519 private/public với CSPRNG/provider phù hợp; private key không được gửi.
3. **Trao đổi public keys** theo format đã định nghĩa (raw 32 byte hoặc SPKI tùy protocol), cùng các nonce công khai nếu thiết kế yêu cầu.
4. **Xác thực handshake/peer:** certificate, chữ ký transcript, authenticated PSK hoặc cơ chế khác được định nghĩa; không chấp nhận khóa chưa xác thực để thao tác nghiệp vụ nhạy cảm.
5. **Tính shared secret:** mỗi bên gọi XDH và từ chối invalid/all-zero output.
6. **HKDF-Extract:** dùng `Z` làm IKM, salt được xác định bởi key schedule.
7. **HKDF-Expand:** dùng labels và transcript/context thống nhất để tạo từng traffic key/nonce base/exporter.
8. **Key confirmation/handshake completion:** dùng cơ chế của protocol để chứng minh hai phía có cùng kết quả key schedule và handshake không bị thay.
9. **Gửi bản tin bằng AEAD:** dùng key đúng direction, nonce không trùng, xác thực AAD và không chấp nhận plaintext nếu tag sai.
10. **Dọn/rekey:** kết thúc phiên, giới hạn số record, điều khiển rekey và bảo vệ key material còn trong memory/log.

### Không nhầm authentication với transcript hashing

Nếu một attacker thay `public_B` thành `public_M` và làm tương tự ở phía còn lại, client/server có thể tính ra hai shared secrets khác nhau với attacker rồi tiếp tục handshake không được xác thực. Việc hash transcript chỉ **ràng buộc phiên với transcript đang nhìn thấy**; nó không xác minh ai đã tạo public key đó. **XDH+HKDF không tự chống MITM.**

Với hệ thống thực, ưu tiên TLS 1.3 hoặc HPKE khi phù hợp; đừng triển khai một protocol tự chế không được phân tích về MITM, downgrade, reflection, unknown-key-share, key confirmation, replay và lỗi parser.

## 9. All-zero secret, invalid keys và đồng nhất curve

RFC 7748 giải thích một số public input có bậc nhỏ có thể làm raw X25519/X448 result toàn zero. Nếu ứng dụng tiếp tục HKDF từ raw zero do đối tác kiểm soát, khóa có thể mất thuộc tính đóng góp bí mật mà ứng dụng kỳ vọng.

Cần:

- Parse peer key đúng format và curve đã thỏa thuận. Không coi mọi mảng 32 byte từ mạng là một public key “đã validate”.
- Không trộn `"X25519"`/`"X448"` hoặc các key thuộc provider khác mà không kiểm tra algorithm.
- Kiểm tra all-zero hoặc xử lý lỗi khi provider từ chối input. Các provider có thể báo lỗi ở những bước khác nhau; không dựa vào một exception message cố định.
- Không leak raw `Z`/private key khi báo lỗi; log mã lỗi an toàn.
- Test với invalid public key, khác curve, sai kích thước và các vector RFC 7748.
- Hiểu kiểm tra all-zero **không thay thế peer authentication**. RFC còn thảo luận khả năng public keys tương đương và contributory behavior.

Một cách kiểm tra all-zero không dừng sớm:

```java
int nonzero = 0;
for (byte b : sharedSecret) {
    nonzero |= b & 0xff;
}
if (nonzero == 0) {
    throw new InvalidKeyException("Invalid shared secret");
}
```

Đây là **trích đoạn**; `sharedSecret` phải là raw XDH output không rỗng, cần import `InvalidKeyException`. Không lấy private/public key bí mật làm thông điệp lỗi. Ví dụ hoàn chỉnh ở trên đã thêm điều kiện độ dài.

## 10. Java 11 và JDK hiện đại: API HKDF khác nhau thế nào?

**Java 11** có `KeyAgreement` cho XDH và `Mac` cho HMAC-SHA-256. Tuy nhiên, **không có API `javax.crypto.KDF` chuẩn** trong Java 11. Có thể triển khai HKDF theo RFC 5869 bằng `Mac` như demo hoặc dùng thư viện được kiểm thử, duy trì phiên bản phù hợp.

**Java 25** bổ sung API **`javax.crypto.KDF`**, `HKDFParameterSpec` và thuật toán `"HKDF-SHA256"`. Ví dụ từ mẫu API **chỉ JDK 25+**:

```java
// Chỉ JDK 25+; KHÔNG dùng với javac --release 11.
KDF kdf = KDF.getInstance("HKDF-SHA256");
AlgorithmParameterSpec params = HKDFParameterSpec.ofExtract()
        .addIKM(sharedSecret)
        .addSalt(salt)
        .thenExpand(infoBytes, 32);
SecretKey key = kdf.deriveKey("AES", params);
```

Đây là **trích đoạn**, cần import `javax.crypto.KDF`, `javax.crypto.SecretKey`, `javax.crypto.spec.HKDFParameterSpec`, `java.security.spec.AlgorithmParameterSpec` và khai báo `sharedSecret`, `salt`, `infoBytes`. Đừng thêm class này vào project build Java 11, vì không biên dịch được. Sau khi nâng cấp runtime, kiểm thử vector chính xác trước khi chuyển từ implementation HKDF cũ sang API KDF mới.

**Đừng nhầm** `SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256")` với HKDF: PBKDF2 có mục tiêu/đặc tả khác và không phải bản thay thế tương đương cho key schedule XDH.

## 11. Những giao thức hiện hành đã xử lý vấn đề này ra sao?

### TLS 1.3

RFC 8446 định nghĩa key schedule HKDF theo nhiều giai đoạn, kết hợp ECDHE và các bí mật khác tùy mode, cùng `HKDF-Expand-Label` có encoding và labels riêng. TLS cũng quy định transcript binding, authentication, encryption records, IV và sequence number.

Không thể thay `HKDF-Expand-Label` bằng một chuỗi `info` tự tạo rồi coi kết quả tương thích TLS. Nếu cần kết nối HTTPS an toàn trong Java 11, sử dụng TLS stack từ JDK/framework được duy trì và cấu hình xác thực đúng; không tự thay HTTPS bằng XDH+HKDF custom.

### HPKE

RFC 9180 xây **Hybrid Public Key Encryption** từ KEM, KDF và AEAD, có các suite identifiers, labeled extract/expand và context riêng. Nó hỗ trợ các mode theo yêu cầu, nhưng các key derivation và message encapsulation phải tuân thủ chính xác RFC.

Nếu nhu cầu là mã hóa payload gửi tới một public key, dùng implementation HPKE được kiểm thử và xác định authentication mode phù hợp, thay vì gọi `KeyAgreement` và tự ghép vài HKDF labels rồi xem như hoàn tất.

### HSM/KMS và non-exportable keys

Không phải mọi private key đều cho phép đưa raw shared secret ra `byte[]`: trong thiết kế dùng HSM/KMS, chính sách có thể yêu cầu secret luôn ở trong thiết bị. Chọn provider và cơ chế agreement/KDF tương ứng thay vì bắt buộc `generateSecret()` trả nguyên liệu vào heap, nếu điều đó vi phạm security requirement.

| Sai lầm | Hậu quả | Cách đúng |

## 14. Checklist trước khi triển khai

1. Đang dùng **protocol chuẩn nào**? Nếu tự thiết kế, đã được review mật mã chưa?
2. Curve X25519/X448 và key wire format có thống nhất không?
3. Peer public key có được xác thực đúng đối tác, role và handshake không?
4. Có kiểm tra invalid/all-zero XDH output hoặc lỗi từ provider không?
5. KDF có dùng đúng RFC 5869 và biến thể HMAC hash đã chọn?
6. Salt có cùng byte trên hai phía, từ nguồn protocol hợp lệ và không bị thay lén ngoài authentication?
7. `info` có protocol ID, version/suite, role, direction, purpose, transcript/context theo thiết kế không?
8. Encoding của `info` có ranh giới byte rõ và test cross-language?
9. Key AES/AEAD có length đúng, không dùng raw `Z` cho nhiều mục đích?
10. Nonce, sequence, AAD, tag verification và rekey có được thiết kế theo giao thức?
11. Có test vector XDH và HKDF, test salt/info/role sai, peer identity sai và zero output?
12. Có tránh export/log `Z`, PRK, derived key, private key và heap dump không kiểm soát?
13. Mã cần chạy Java 11 có tránh `javax.crypto.KDF` chỉ có từ JDK 25 không?
14. Key lifecycle: fresh ephemeral key, rotation, timeout, không reuse sai phiên?
15. Có giới hạn số handshake đồng thời và xử lý lỗi fail closed, không fallback tùy tiện?

## 15. Bài luyện tập và đáp án

**Bài 1.** Alice và Bob có raw `Z` X25519 32 byte, một lập trình viên sử dụng `Z` cho AES-256-GCM ở cả hai hướng. Cần sửa gì?

**Đáp án:** Theo giao thức dùng HKDF-Extract rồi HKDF-Expand có labels tách **C2S/S2C**; tiếp đó xây nonce schedule duy nhất cho mỗi hướng và kiểm tra tag. Không dùng raw `Z` cho mọi tác vụ.

**Bài 2.** Một bên dùng `info("client-to-server")`, bên kia dùng `info("server-to-client")` để xử lý cùng một bản tin client gửi. Điều gì xảy ra?

**Đáp án:** Derived keys khác và AEAD authentication sẽ fail. Mỗi hướng phải có label cố định theo **ai đang gửi**, không theo “tôi là server nên dùng server label”.

**Bài 3.** `HKDF-Expand(PRK, info, 16)` và `HKDF-Expand(PRK, info, 32)` tạo hai khóa độc lập?

**Đáp án:** Không. Với cùng PRK/info, 16 byte đầu của output 32 byte bằng output 16 byte. Tách mục đích bằng `info` khác, không chỉ bằng L.

**Bài 4.** Hai phía dùng cùng `Z` nhưng salt khác nhau. Có cho ra cùng key không?

**Đáp án:** Hầu như không. Extract cho PRK khác; salt phải được thống nhất theo protocol trước khi dẫn xuất.

**Bài 5.** XDH + HKDF + hash transcript có tự chống MITM?

**Đáp án:** Không. Cần xác thực peer/handshake bằng certificate, chữ ký hoặc cơ chế đã được thẩm định; hash chỉ ràng buộc context, không xác minh danh tính.

**Bài 6.** Có thể dùng nonce AES-GCM 12 byte dẫn xuất từ HKDF rồi lặp lại cho tất cả record không?

**Đáp án:** Không. Nonce phải duy nhất cho mỗi lần encryption dưới cùng key theo thiết kế giao thức; cần sequence/counter và rekey.

**Bài 7.** Java 11 báo lỗi không tìm thấy `javax.crypto.KDF`. Vì sao?

**Đáp án:** API KDF chung xuất hiện từ **JDK 25**. Java 11 phải dùng HKDF implementation/libraries phù hợp hoặc triển khai kiểm thử với `Mac`, không biên dịch code JDK 25 bằng `--release 11`.

**Bài 8.** Khi phải debug vì Java và Go tính khác key, có nên in `Z` và PRK lên log production?

**Đáp án:** Không. Kiểm tra encoding public key, salt, info, role, transcript, lengths bằng test vectors giả/công khai trong môi trường test; không làm lộ secret thật.

## 16. Ghi nhớ và tài liệu chính thức

- **XDH chỉ tạo raw shared secret `Z`**, không tạo một bộ khóa application protocol hoàn chỉnh.
- **HKDF-Extract** lấy `salt` và `IKM` tạo `PRK`; **HKDF-Expand** lấy `PRK`, `info` và `L` để dẫn xuất đúng khóa theo mục đích.
- **Định nghĩa `info` theo giao thức**: role, direction, protocol version/suite, transcript và purpose; encoding phải không nhập nhằng.
- **Client→server** và **server→client** nên có keys riêng; nếu cùng PRK/info, chỉ đổi L **không** tạo key độc lập.
- **All-zero/invalid input** phải fail closed; **XDH + HKDF không thay thế authentication**.
- **AEAD còn cần nonce unique, AAD và tag verification**. Chỉ có derived key chưa đủ để gửi message an toàn.
- **Java 11 hỗ trợ X25519/X448 và `Mac`**, nhưng **`javax.crypto.KDF` chỉ từ Java 25**. Không mang API mới vào module biên dịch cho JDK 11.
- **Production ưu tiên protocol được phân tích** như TLS 1.3/HPKE và thư viện được bảo trì.

Nguồn còn áp dụng:

- [RFC 7748 — Elliptic Curves for Security](https://www.rfc-editor.org/rfc/rfc7748) — X25519/X448, all-zero output, public keys.
- [RFC 5869 — HKDF](https://www.rfc-editor.org/rfc/rfc5869) — Extract, Expand, salt, info và test vectors.
- [Oracle Java SE 11 — Standard Algorithm Names](https://docs.oracle.com/en/java/javase/11/docs/specs/security/standard-names.html) — XDH/X25519/X448, HmacSHA256.
- [Oracle Java SE 11 — `NamedParameterSpec`](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/java/security/spec/NamedParameterSpec.html) — tham số X25519/X448.
- [Oracle Java SE 11 — `KeyAgreement`](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/javax/crypto/KeyAgreement.html) — init/doPhase/generateSecret.
- [Oracle Java SE 11 — `Mac`](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/javax/crypto/Mac.html) — HMAC cho HKDF.
- [RFC 8446 — TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446) — key schedule, HKDF-Expand-Label và transcript binding.
- [RFC 9180 — HPKE](https://www.rfc-editor.org/rfc/rfc9180) — KEM/KDF/AEAD và labeled key derivation.
- [Oracle Java SE 25 — `KDF`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/javax/crypto/KDF.html) — API KDF bổ sung từ JDK 25.
