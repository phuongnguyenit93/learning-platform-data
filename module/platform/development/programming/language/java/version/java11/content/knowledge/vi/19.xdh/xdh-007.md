# Truyền public key và tạo bí mật chung bằng XDH (Java 11+)

## 1. XDH giải quyết vấn đề gì?

Alice và Bob muốn tạo một khóa chung khi liên lạc qua mạng nhưng không thể gửi trực tiếp khóa bí mật cho nhau. **Diffie–Hellman key agreement** cho phép mỗi phía tự tạo **private key** và **public key**, chỉ gửi **public key** cho đối tác, rồi tính **shared secret** bằng cách kết hợp private key của mình với public key nhận được.

Trong **Java 11**, JCA (Java Cryptography Architecture) bổ sung **XDH** theo **JEP 324**, hỗ trợ hai hàm hiện đại trong **RFC 7748**:

- **X25519:** dựa trên Curve25519; raw shared secret dài **32 byte**.
- **X448:** dựa trên Curve448; raw shared secret dài **56 byte**.

Cả hai vẫn là các thuật toán được hỗ trợ trong Java hiện đại. Khi thiết kế một giao thức cụ thể, hai bên phải thống nhất cùng thuật toán/curve, cùng định dạng public key và cùng quy tắc dẫn xuất session key.

~~~text
Alice                                                Bob
-----                                                ---
Tạo (privateA, publicA)                               Tạo (privateB, publicB)
        |                                                      |
        |---------------- publicA ---------------------------->|
        |<--------------- publicB -----------------------------|
        |                                                      |
secretA = X25519(privateA, publicB)             secretB = X25519(privateB, publicA)
        |                                                      |
        +-------------------- secretA == secretB --------------+
        |                                                      |
keyA = HKDF(secretA, context)                    keyB = HKDF(secretB, context)
        |                                                      |
        +---------------------- keyA == keyB ------------------+
~~~

**Không chuyển private key qua mạng. Không gửi raw shared secret để kiểm tra xem hai bên có khớp.** Chỉ public keys cùng các thông tin cấu hình giao thức mới được truyền.

**Điểm đặc biệt quan trọng:** XDH tạo được bí mật chung nhưng **không tự xác thực danh tính đối tác**. Nếu attacker thay public keys khi truyền, mỗi phía có thể tạo ra secret với chính attacker (**man-in-the-middle, MITM**). Vì vậy trao đổi public key bằng XDH chỉ là một **primitive mật mã**, không phải một secure channel hoàn chỉnh.

## 2. Các API Java 11 và vai trò của chúng

| Thành phần | Vai trò | API thường dùng |
| --- | --- | --- |
| `KeyPairGenerator` | Sinh cặp public/private key | `getInstance("X25519")`, `"X448"` |
| `KeyPair` | Giữ public và private key | `getPublic()`, `getPrivate()` |
| `KeyFactory` | Tạo public key từ bytes được mã hóa hợp lệ | `generatePublic(new X509EncodedKeySpec(...))` |
| `KeyAgreement` | Thực hiện XDH với private local và public peer | `init`, `doPhase`, `generateSecret` |
| `NamedParameterSpec` | Chỉ rõ đường cong trong `XDH` generic | `X25519`, `X448` |
| `XECPublicKey` | Public key XEC theo RFC 7748 | `getU()`, `getParams()` |
| `XECPrivateKey` | Private scalar XEC, nhạy cảm | `getScalar()`, `getParams()` |
| `X509EncodedKeySpec` | Định dạng public key SPKI/DER | `new X509EncodedKeySpec(encoded)` |
| `Mac`, `SecretKeySpec` | HMAC để hiện thực HKDF trong demo | `HmacSHA256` |

Cách ngắn gọn để sinh X25519 key pair:

~~~java
KeyPairGenerator generator = KeyPairGenerator.getInstance("X25519");
KeyPair pair = generator.generateKeyPair();
~~~

Hoặc thông qua tên generic **`XDH`**:

~~~java
KeyPairGenerator generator = KeyPairGenerator.getInstance("XDH");
generator.initialize(NamedParameterSpec.X25519);
KeyPair pair = generator.generateKeyPair();
~~~

Đây là những **đoạn mã minh họa**, phải nằm trong method có imports `java.security.KeyPairGenerator`, `KeyPair` và `java.security.spec.NamedParameterSpec` cùng xử lý ngoại lệ. Có thể dùng `NamedParameterSpec.X448` cho X448. Khi chọn `"XDH"`, nên đặt parameter set tường minh, tránh phụ thuộc default riêng của provider.

**Không nhầm `X25519` và `Ed25519`.** X25519 là key agreement; Ed25519 là digital signature. Không sử dụng public key Ed25519 thay cho X25519 nếu chưa có một protocol chuyển đổi được chuẩn hóa, và không gọi `KeyAgreement.getInstance("Ed25519")`.

## 3. Tạo key pair an toàn

Mỗi phía tự sinh key pair ở **chính endpoint của mình**. Việc một server tạo cả Alice lẫn Bob private keys rồi gửi sang Bob sẽ phá mục tiêu của DH.

- Sử dụng `KeyPairGenerator` của provider tin cậy và nguồn ngẫu nhiên mật mã; không tự cấp private scalar bằng `java.util.Random` hoặc seed cố định.
- Nếu giao thức yêu cầu **forward secrecy**, thường dùng key pair **ephemeral cho mỗi lần handshake**, sau đó hủy/giới hạn vòng đời. Chỉ tái sử dụng static key nếu giao thức đã được phân tích về bảo mật.
- Private key không được in log, ghi vào query string, truyền qua HTTP body hay chia sẻ với peer.
- Không mặc định private key của mọi provider đều có thể export: HSM/provider có thể chỉ đưa key handle.
- KeyPairGenerator và KeyAgreement là đối tượng làm việc với khóa; chúng không tự mở kết nối mạng, tạo bản tin handshake hoặc xác minh chứng chỉ.

Nếu muốn giữ private scalar, `XECPrivateKey` của Java 11 có `getScalar()`, nhưng đó là dữ liệu nhạy cảm dạng **unpruned** theo RFC 7748; không cần truy cập scalar trong ví dụ thông thường. Hãy để provider tự xử lý việc **clamping** khi dùng khóa.

## 4. Public key phải được mã hóa đúng định dạng trước khi gửi

Một Java `PublicKey` là object, không thể tự truyền qua mạng mà không có giao ước. Dùng encoding được hai phía thống nhất:

~~~java
PublicKey publicKey = pair.getPublic();
byte[] publicDer = publicKey.getEncoded();
String format = publicKey.getFormat(); // "X.509" với provider demo.
~~~

**Đoạn mã minh họa**: `pair` đã được sinh ở bước 2. Với X25519/X448 ở JDK thông thường, `getEncoded()` trả **ASN.1 DER SubjectPublicKeyInfo (SPKI)**, bao gồm cả identifier của thuật toán/curve và bytes public key. Giá trị `"X.509"` chỉ tên **định dạng public key**, không có nghĩa object đó là một certificate X.509.

Phân biệt các format:

| Biểu diễn | Cấu trúc | Tình huống |
| --- | --- | --- |
| Raw public key X25519 | 32 bytes u-coordinate, little-endian theo RFC 7748 | Giao thức định nghĩa raw X25519 |
| Raw public key X448 | 56 bytes theo RFC 7748 | Giao thức định nghĩa raw X448 |
| X.509/SPKI DER | ASN.1 có algorithm identifier và public key | Dùng với `X509EncodedKeySpec` |
| PEM `BEGIN PUBLIC KEY` | SPKI DER được Base64 và thêm header/footer | Giao thức text/public key file |

**SPKI không phải raw 32 hoặc 56 byte.** Đừng cắt một đoạn bytes `getEncoded()` bằng offset hardcode để lấy raw X25519: encoding và độ dài phải theo chuẩn, không dựa vào một quan sát của provider.

Để khôi phục đúng public key từ SPKI:

~~~java
PublicKey peer = KeyFactory.getInstance("X25519")
        .generatePublic(new X509EncodedKeySpec(peerDer));
~~~

Đây là **mã minh họa** trong method có `peerDer` và imports phù hợp. Nếu encoding hoặc algorithm sai, `KeyFactory` có thể ném `InvalidKeySpecException`. Tuy nhiên, **parse thành công chỉ xác nhận cấu trúc/thuật toán, không xác thực người sở hữu key**.

### `XECPublicKey.getU()` không phải raw encoding

`XECPublicKey.getU()` trả `BigInteger` biểu diễn u-coordinate. Java `BigInteger.toByteArray()` sử dụng biểu diễn signed/big-endian có độ dài biến đổi, còn raw X25519/X448 theo RFC 7748 là fixed-length/little-endian. Không dùng `toByteArray()` như một cách chuyển đổi raw wire format. Nếu cần giao tiếp với thư viện chỉ nhận raw bytes, áp dụng conversion theo RFC và kiểm tra test vectors, không trộn raw với SPKI.

## 5. Truyền public key qua TCP: cần framing, giới hạn và timeout

**TCP là một byte stream**, không bảo toàn ranh giới lời gọi `write()`. Một lần `read()` có thể nhận thiếu byte dù phía gửi đã ghi xong public key. Demo dùng một dạng framing đơn giản:

~~~text
[4-byte big-endian length] [đúng length bytes public key SPKI DER]
~~~

Gửi:

~~~java
out.writeInt(publicDer.length);
out.write(publicDer);
out.flush();
~~~

Nhận:

~~~java
int len = in.readInt();
if (len <= 0 || len > 256) {
    throw new IOException("Invalid public key length");
}
byte[] peerDer = new byte[len];
in.readFully(peerDer);
~~~

Đây là **hai đoạn minh họa** giả định đã có `DataOutputStream out` và `DataInputStream in`. Giới hạn 256 byte chỉ thuộc **giao thức thử nghiệm X25519/X448 SPKI**, không phải ngưỡng chung cho mọi loại certificate, key hoặc provider.

**Trong hệ thống thật:**

1. Kiểm kích thước trước khi cấp phát `new byte[len]` để chống DoS.
2. Đặt timeout cho read/connect/handshake và giới hạn số phiên đồng thời.
3. Gửi version và algorithm hợp lệ trong message, không tự động downgrade nếu key không parse được.
4. Dùng `readFully`/framing đúng; xử lý EOF và peer đóng giữa chừng.
5. Không cho attacker gửi kích thước vô hạn hoặc khiến một worker giữ socket mãi.
6. Bản thân TCP plaintext ở demo **không xác thực public key**. Cần trust model/handshake riêng khi triển khai thật.

Public key có thể được biết công khai, nhưng vẫn cần kiểm soát khi đưa vào logs: một static public key cũng có thể trở thành định danh cố định liên kết với người dùng.

## 6. Từ private local + public remote đến shared secret

Đây là ba bước trọng tâm của JCA `KeyAgreement`:

~~~java
KeyAgreement agreement = KeyAgreement.getInstance("X25519");
agreement.init(own.getPrivate());
agreement.doPhase(peerPublic, true);
byte[] secret = agreement.generateSecret();
~~~

**Đoạn minh họa**, cần biến `own` và `peerPublic` đúng thuật toán, imports `KeyAgreement` và xử lý security exceptions.

- `init(...)`: **private key của bên đang gọi**.
- `doPhase(peerPublic, true)`: **public key nhận từ phía bên kia**. `true` đánh dấu phase cuối.
- `generateSecret()`: trả mảng bytes raw shared secret của primitive XDH. Không có network send, signature verify hay certificate check tự động.
- Alice thực hiện với privateA/publicB; Bob với privateB/publicA. Nếu không bị thay key và hai bên dùng đúng curve, kết quả giống nhau.
- Không in shared secret hoặc gửi lên mạng để so sánh. Trong một **unit test cùng process**, có thể tạm so sánh hai mảng để xác minh thuật toán.

### Trường hợp all-zero

RFC 7748 mô tả các public inputs nhỏ bậc có thể tạo **all-zero shared secret**, dẫn đến rủi ro về đóng góp private key. Provider có thể tự phát hiện và ném `InvalidKeyException`; code/giao thức phải áp dụng kiểm tra theo hợp đồng của mình. Mẫu xử lý raw result:

~~~java
int aggregate = 0;
for (byte b : secret) {
    aggregate |= b & 0xff;
}
if (aggregate == 0) {
    throw new GeneralSecurityException("All-zero shared secret");
}
~~~

Đây là **mã minh họa**. Vòng lặp OR qua toàn bộ bytes, tránh dừng sớm phụ thuộc giá trị secret. **Chặn all-zero không thay thế xác thực danh tính**. Một public key hợp lệ về mặt đường cong vẫn có thể được gửi bởi attacker.

## 7. Dẫn xuất session key từ secret bằng HKDF

Raw shared secret không nên dùng tùy tiện như một encryption key trực tiếp. Một giao thức thường dùng **KDF**, ví dụ **HKDF** trong **RFC 5869**, để dẫn xuất key có đúng kích thước và có **domain separation** theo mục đích.

~~~text
XDH raw shared secret (IKM)
           |
           v
HKDF-Extract(salt, IKM) -> PRK
           |
           v
HKDF-Expand(PRK, info, length) -> session key
           |
           v
AEAD/MAC/traffic keys theo một protocol đã xác thực
~~~

**`salt`** có thể là dữ liệu public. Khi không có salt, RFC 5869 quy định mặc định dãy zero có độ dài của hash output. **`info`** dùng để gắn algorithm, protocol version, vai trò client/server và transcript. Demo sử dụng nhãn `XDH-demo-v1/<algorithm>` cộng với public keys **theo thứ tự client trước server** ở cả hai phía.

Dùng HKDF giúp:

- Dẫn xuất output có độ dài phù hợp, ví dụ 32 byte từ X25519 **hoặc** X448.
- Không đưa trực tiếp secret thô vào nhiều mục đích mật mã khác nhau.
- Ràng buộc context, role và protocol version vào key schedule.
- Giảm nguy cơ nhầm key giữa các mục đích; để có hai hướng truyền nên tách labels/keys trong giao thức hoàn chỉnh.

**HKDF không tự làm key agreement được xác thực.** Nếu Mallory thay public key, Mallory vẫn có thể dẫn xuất key hợp lệ với mỗi bên. **Một protocol production phải xác thực public key/transcript/identity**, không chỉ chạy HKDF rồi gửi ciphertext.

### Cú pháp HKDF-SHA256 một block dùng trong demo

~~~java
Mac mac = Mac.getInstance("HmacSHA256");
byte[] salt = new byte[32];   // RFC 5869 default salt nếu không có salt.
mac.init(new SecretKeySpec(salt, "HmacSHA256"));
byte[] prk = mac.doFinal(ikm); // Extract.

mac.init(new SecretKeySpec(prk, "HmacSHA256"));
mac.update(info);
mac.update((byte) 1);
byte[] key32 = mac.doFinal();  // Expand, 32 bytes.
~~~

Đây là **mã minh họa** trong ngữ cảnh đã có `ikm`, `info`; cần `Mac`/`SecretKeySpec` imports. Demo đầy đủ có cleanup `prk`; trong Java không thể bảo đảm mọi bản sao secret ở GC/provider đều bị zeroize. Đối với giao thức có nhiều key dài hơn một block, thực hiện đúng toàn bộ thuật toán RFC 5869 hoặc dùng implementation đã kiểm chứng — không tự kéo dài mảng kết quả đơn giản.

## 8. Ví dụ Java 11 hoàn chỉnh: client/server gửi SPKI qua loopback

Ví dụ này dùng **socket thật** trên `127.0.0.1`, nhưng cả hai phía chạy trong cùng JVM để có thể kiểm chứng raw secret không cần gửi bí mật qua mạng. Chương trình làm việc **hai lần**: X25519 rồi X448. Hai phía mỗi lần tạo cặp khóa mới, trao public DER có length-prefix, dùng `KeyFactory`/`KeyAgreement`, chặn all-zero và chạy HKDF-SHA256.

**Bảo mật:** Socket trong demo chưa xác thực peer/public key, nên chương trình **chỉ để học key agreement**, không phải một secure transport để dùng với dữ liệu thật.

Tạo file **XdhExchangeDemo.java**:

~~~java
import java.io.ByteArrayOutputStream;
import java.io.DataInputStream;
import java.io.DataOutputStream;
import java.io.IOException;
import java.net.InetAddress;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;
import java.security.GeneralSecurityException;
import java.security.KeyFactory;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.MessageDigest;
import java.security.PublicKey;
import java.security.spec.X509EncodedKeySpec;
import java.util.Arrays;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.crypto.KeyAgreement;
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

public class XdhExchangeDemo {
    private static final int MAX_PUBLIC_BYTES = 256;
    private static final int HKDF_SHA256_LEN = 32;

    private static final class Result {
        final byte[] shared;
        final byte[] sessionKey;
        final boolean spkiFormat;

        Result(byte[] shared, byte[] sessionKey, boolean spkiFormat) {
            this.shared = shared;
            this.sessionKey = sessionKey;
            this.spkiFormat = spkiFormat;
        }
    }

    public static void main(String[] args) throws Exception {
        runCase("X25519", 32);
        runCase("X448", 56);
    }

    private static void runCase(String algorithm, int expectedSize)
            throws Exception {
        ExecutorService executor = Executors.newSingleThreadExecutor();
        try (ServerSocket listener = new ServerSocket(
                0, 1, InetAddress.getByName("127.0.0.1"))) {
            listener.setSoTimeout(5000);
            Future<Result> server = executor.submit(() -> {
                try (Socket socket = listener.accept()) {
                    socket.setSoTimeout(5000);
                    return exchange(socket, algorithm, false);
                }
            });

            Result client;
            try (Socket socket = new Socket(
                    "127.0.0.1", listener.getLocalPort())) {
                socket.setSoTimeout(5000);
                client = exchange(socket, algorithm, true);
            }
            Result other = server.get(5, TimeUnit.SECONDS);
            try {
                System.out.println(algorithm + " spki="
                        + (client.spkiFormat && other.spkiFormat));
                System.out.println(algorithm + " secretBytes="
                        + client.shared.length);
                System.out.println(algorithm + " sharedEqual="
                        + (client.shared.length == expectedSize
                        && MessageDigest.isEqual(client.shared, other.shared)));
                System.out.println(algorithm + " derivedBytes="
                        + client.sessionKey.length);
                System.out.println(algorithm + " derivedEqual="
                        + MessageDigest.isEqual(
                                client.sessionKey, other.sessionKey));
            } finally {
                Arrays.fill(client.shared, (byte) 0);
                Arrays.fill(other.shared, (byte) 0);
                Arrays.fill(client.sessionKey, (byte) 0);
                Arrays.fill(other.sessionKey, (byte) 0);
            }
        } finally {
            executor.shutdownNow();
        }
    }

    private static Result exchange(Socket socket, String algorithm,
                                   boolean isClient)
            throws Exception {
        KeyPairGenerator generator = KeyPairGenerator.getInstance(algorithm);
        KeyPair own = generator.generateKeyPair();

        byte[] ownPublic = own.getPublic().getEncoded();
        if (ownPublic == null || ownPublic.length > MAX_PUBLIC_BYTES) {
            throw new IOException("Unsupported public key encoding");
        }

        DataOutputStream out = new DataOutputStream(socket.getOutputStream());
        DataInputStream in = new DataInputStream(socket.getInputStream());

        out.writeInt(ownPublic.length);
        out.write(ownPublic);
        out.flush();

        int len = in.readInt();
        if (len <= 0 || len > MAX_PUBLIC_BYTES) {
            throw new IOException("Invalid public key length");
        }
        byte[] peerEncoded = new byte[len];
        in.readFully(peerEncoded);
        PublicKey peer = KeyFactory.getInstance(algorithm).generatePublic(
                new X509EncodedKeySpec(peerEncoded));

        KeyAgreement agreement = KeyAgreement.getInstance(algorithm);
        agreement.init(own.getPrivate());
        agreement.doPhase(peer, true);
        byte[] shared = agreement.generateSecret();
        int aggregate = 0;
        for (byte b : shared) {
            aggregate |= b & 0xff;
        }
        if (aggregate == 0) {
            Arrays.fill(shared, (byte) 0);
            throw new GeneralSecurityException("All-zero shared secret");
        }

        byte[] clientPublic = isClient ? ownPublic : peerEncoded;
        byte[] serverPublic = isClient ? peerEncoded : ownPublic;
        ByteArrayOutputStream transcript = new ByteArrayOutputStream();
        transcript.write(("XDH-demo-v1/" + algorithm + "/").getBytes(
                StandardCharsets.UTF_8));
        transcript.write(clientPublic);
        transcript.write(serverPublic);
        byte[] sessionKey = hkdfSha256(shared, transcript.toByteArray());
        return new Result(shared, sessionKey,
                "X.509".equals(own.getPublic().getFormat()));
    }

    private static byte[] hkdfSha256(byte[] ikm, byte[] info)
            throws GeneralSecurityException {
        Mac mac = Mac.getInstance("HmacSHA256");
        byte[] salt = new byte[HKDF_SHA256_LEN]; // RFC 5869 default salt.
        mac.init(new SecretKeySpec(salt, "HmacSHA256"));
        byte[] prk = mac.doFinal(ikm);           // HKDF-Extract.
        try {
            mac.init(new SecretKeySpec(prk, "HmacSHA256"));
            mac.update(info);
            mac.update((byte) 1);                // HKDF-Expand, block 1.
            return mac.doFinal();                // Exactly 32 bytes.
        } finally {
            Arrays.fill(prk, (byte) 0);
            Arrays.fill(salt, (byte) 0);
        }
    }
}
~~~

~~~

### Phân tích kết quả và tính đúng đắn

1. `spki=true`: public keys được provider của máy kiểm thử xuất ở định dạng `X.509` dùng với `X509EncodedKeySpec`.
2. `secretBytes=32` và `56`: độ dài raw shared secrets tương ứng X25519 và X448; **không in raw secrets**.
3. `sharedEqual=true`: client/server kết hợp private local với public remote đúng thuật toán, cho cùng kết quả.
4. `derivedBytes=32`: HKDF-SHA256 trong demo được thiết kế tạo một block output dài 32 byte ở cả hai đường cong.
5. `derivedEqual=true`: input secret, label, algorithm và thứ tự public transcript nhất quán nên session key cuối trùng nhau.

Các bytes của private keys, shared secret và session keys **không được gửi qua socket**. Trong cùng JVM, demo so sánh mảng từ hai threads chỉ nhằm kiểm thử, không phải cơ chế xác thực cần thực hiện trên mạng thật.

**Giới hạn kỹ thuật:** socket có timeout đọc nhưng chưa có tổng deadline an toàn toàn handshake; mã demo chỉ tạo một kết nối cho mỗi thuật toán. `Arrays.fill` chỉ xóa các `byte[]` được chương trình sở hữu, không bảo đảm xóa mọi bản sao secrets trong provider/heap. Việc đưa key vào `ByteArrayOutputStream` chỉ chứa **public transcript**; không có dữ liệu private trong đó. Với môi trường production phải dùng một giao thức **đã được thiết kế bảo mật hoàn chỉnh**.

## 9. MITM: tính cùng secret chưa có nghĩa kết nối đúng peer

Giả sử Mallory kiểm soát đường truyền giữa Alice và Bob:

~~~text
Alice                   Mallory                       Bob
  | -- publicA -------->  | -- publicM1 --------------> |
  | <--- publicM2 ------  | <--- publicB --------------- |
  |                       |                              |
  | secret(A, Mallory)     | secret(Mallory, Bob)         |
~~~

Alice có thể tính thành công secret với một public key do Mallory cung cấp, và Bob cũng vậy. Mallory có thể thiết lập **hai khóa khác nhau** để đọc/sửa/chuyển tiếp thông điệp. **XDH không tự phát hiện key-substitution**.

Các cách bảo vệ cần có:

- **Peer authentication:** chứng chỉ và hostname validation, chữ ký trên ephemeral public key/transcript, PSK được quản lý đúng hoặc cơ chế xác thực của protocol.
- **Transcript binding:** gắn algorithm, version, client/server roles, public keys và identity vào key schedule.
- **Key confirmation:** chứng minh peer nắm cùng khóa theo protocol đã xác thực, không gửi raw secret.
- **Chống downgrade/replay:** không chấp nhận algorithm yếu hơn do dữ liệu thương lượng chưa xác thực; định nghĩa session ID/nonce/sequence numbers.
- **Authorization:** xác thực cryptographic identity không thay cho kiểm tra quyền nghiệp vụ.

**Gửi hash public key qua cùng kênh không được xác thực không giải quyết MITM**, vì attacker có thể thay cả key và hash. Không tự thiết kế protocol mới chỉ từ các API primitives; với HTTP/TCP thực tế hãy ưu tiên TLS/JSSE.

## 10. XDH trong JCA không đồng nghĩa XDH tự bật trong TLS

Đây là điểm phiên bản dễ nhầm:

- **JDK 11** thêm X25519/X448 **JCA KeyAgreement** theo JEP 324.
- **JDK 11** cũng triển khai TLS 1.3 trong JSSE, nhưng **Oracle JDK 11 Release Notes** nói rõ XDH JCA lúc phát hành **chưa tích hợp vào triển khai TLS 1.3**.
- Các JDK/provider sau đó có khả năng key exchange khác nhau. Việc `KeyAgreement.getInstance("X25519")` tồn tại không tự nói TLS/HTTPS đã chọn curve đó.

`javax.net.ssl.SSLContext`, `java.net.http.HttpClient` và `javax.crypto.KeyAgreement` là các tầng khác nhau. **Khi chỉ muốn HTTPS, để JSSE/HttpClient quản lý TLS và thực hiện certificate/hostname validation**. Khi gọi XDH JCA trực tiếp, chính ứng dụng cần đảm bảo protocol, authentication và KDF.

**Thách thức hiện đại:** X25519/X448 là các thuật toán classical elliptic-curve DH, **không chống được máy tính lượng tử đủ mạnh**. Một số JDK mới hỗ trợ thêm hybrid post-quantum TLS key exchange. Không suy ra Java 11 có các tính năng hybrid mới, cũng không tự ghép XDH với một KEM thành giao thức chưa được đánh giá.

## 12. Checklist triển khai

1. [ ] **Thuật toán:** hai phía cùng dùng X25519 hoặc X448, thống nhất algorithm/curve/version.
2. [ ] **Sinh khóa:** mỗi bên tạo private key cục bộ bằng provider JCA và nguồn ngẫu nhiên an toàn.
3. [ ] **Truyền key:** chỉ gửi public key; định dạng SPKI DER hoặc raw RFC 7748 được quy định rõ.
4. [ ] **Đọc mạng:** có framing, giới hạn kích thước trước khi cấp phát, timeout và xử lý EOF.
5. [ ] **KeyFactory:** xác minh encoding và curve; invalid public key bị từ chối.
6. [ ] **KeyAgreement:** `init(localPrivate)`, `doPhase(remotePublic, true)`, `generateSecret()`.
7. [ ] **Secret checks:** kiểm all-zero và điều kiện hợp lệ theo RFC/protocol.
8. [ ] **KDF:** HKDF/key schedule chuẩn, context/roles/transcript/output length rõ ràng.
9. [ ] **Xác thực:** public keys và peer identity được xác minh bằng trust model thực sự.
10. [ ] **Vòng đời:** ephemeral keys khi cần forward secrecy, private keys và buffers được giữ kín/dọn phù hợp.
11. [ ] **Chống MITM:** kiểm substitution/downgrade/replay, không lầm key agreement thành authentication.
12. [ ] **Dữ liệu:** dùng AEAD với nonce/key management đúng, tốt nhất thông qua protocol đã được đánh giá.
13. [ ] **Tương thích:** mã Java 11 không phụ thuộc API mới; provider hỗ trợ X25519/X448 trong runtime triển khai.
14. [ ] **Kiểm thử:** kiểm output 32/56 bytes, same secret, same KDF result, wrong curve, malformed input, timeouts, và MITM tests.

**Tóm lại:** XDH cho phép truyền **public key** và tạo cùng một **raw shared secret** mà không lộ private key. Sau đó **HKDF** tạo khóa theo mục đích. Nhưng **key agreement không tự xác thực danh tính hoặc bảo vệ thông điệp ứng dụng**; bảo mật thực tế yêu cầu một giao thức có peer authentication, transcript validation, KDF, AEAD và quản lý phiên đúng.
