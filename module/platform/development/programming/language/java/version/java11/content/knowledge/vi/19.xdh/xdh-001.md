# X25519, X448 và key agreement theo RFC 7748 trong Java 11

**Chủ đề cha:** XDH  
**Mục tiêu:** Dùng `X25519` và `X448` để thỏa thuận một bí mật chung bằng Java Cryptography Architecture (JCA), hiểu định dạng khóa theo RFC 7748, lựa chọn thuật toán tương thích, dẫn xuất khóa phiên đúng mục đích và tránh các sai lầm bảo mật. Nội dung chỉ tập trung những kiến thức vẫn có giá trị trên Java hiện đại; khi cần bảo vệ giao tiếp thực tế nên ưu tiên giao thức tiêu chuẩn được triển khai/kiểm toán thay vì tự thiết kế handshake.

`XDH` là họ **Diffie–Hellman với các đường cong Montgomery** được đặc tả bởi [RFC 7748](https://www.rfc-editor.org/rfc/rfc7748). Hai chức năng nổi bật là `X25519` (Curve25519) và `X448` (Curve448). Mỗi bên sinh **khóa riêng** và **khóa công khai**; trao đổi khóa công khai qua kênh truyền rồi tính ra một giá trị bí mật chung:

```text
Alice                                     Bob
-----                                     ---
(a, A = X25519(a, basepoint))             (b, B = X25519(b, basepoint))
  |                                            |
  | ---------- public A --------------------> |
  | <--------- public B --------------------- |
  |                                            |
K_A = X25519(a, B)                       K_B = X25519(b, A)
                    K_A == K_B
                          |
                    KDF / key schedule
                          |
               khóa mã hóa phiên theo ngữ cảnh
```

Trong sơ đồ, `a` và `b` là private scalar, `A` và `B` là public u-coordinate; `K_A` và `K_B` là cùng một **raw shared secret**. **Tính bằng nhau của shared secret không xác thực danh tính peer.** Nếu kẻ tấn công thay thế public key trong khi truyền, họ có thể thực hiện man-in-the-middle nếu giao thức không có bước xác thực.

## 1. Mục tiêu học tập

Sau bài, bạn có thể:

1. Phân biệt `XDH`, `X25519`, `X448`, `ECDH` thông thường, `Ed25519/Ed448`, raw shared secret và symmetric session key.
2. Sinh key pair theo nhóm chỉ định bằng `KeyPairGenerator.getInstance("XDH")` và `NamedParameterSpec`, rồi thực hiện `KeyAgreement` một pha.
3. Hiểu độ dài của private scalar, public u-coordinate và raw shared secret: **32 byte cho X25519; 56 byte cho X448**.
4. Dùng `XECPrivateKeySpec` và `XECPublicKeySpec` để dựng lại vector kiểm thử RFC 7748; chuyển đổi little-endian u-coordinate sang `BigInteger` dương đúng cách.
5. Hiểu tại sao khóa `PublicKey.getEncoded()` dạng X.509 SubjectPublicKeyInfo khác với chuỗi raw u-coordinate của RFC 7748, và khi nào dùng `X509EncodedKeySpec`.
6. Từ chối shared secret toàn byte 0 (low-order peer), sai nhóm đường cong và khóa không hợp lệ theo chính sách của giao thức.
7. Dùng HKDF (extract + expand) trên raw secret với salt/context phù hợp và tránh dùng output XDH trực tiếp làm khóa ứng dụng.
8. Biết rõ giới hạn: XDH **không mã hóa**, **không ký số**, **không xác thực peer**; các vấn đề xác thực, chống MITM, replay, quản lý phiên phải do giao thức bao ngoài xử lý.
9. Chạy ba chương trình Java 11 kiểm chứng bằng vector RFC, tự động sinh khóa, HKDF và định dạng public key.

## 2. Các tên gọi và thông số quan trọng

| Thuộc tính | X25519 | X448 |
|---|---|---|
| RFC | RFC 7748 | RFC 7748 |
| Đường cong | Curve25519 | Curve448 |
| Tên nhóm/thuật toán Java | `"X25519"` | `"X448"` |
| Tên JCA tổng quát | `"XDH"` | `"XDH"` |
| Private scalar encoded | 32 byte (256 bit dữ liệu mã hóa) | 56 byte (448 bit dữ liệu mã hóa) |
| Public u-coordinate trên wire theo RFC | 32 byte, **little-endian** | 56 byte, **little-endian** |
| Raw shared secret | 32 byte | 56 byte |
| Tọa độ u của base point | 9 | 5 |
| Mục đích | Key agreement | Key agreement |
| Mức an toàn | Nhóm phù hợp nhiều giao thức hiện đại | Mức an toàn thiết kế cao hơn, đổi lại chi phí và khả năng tương tác cần xem xét |
| Định dạng SPKI (`PublicKey.getEncoded()` thông dụng) | Có metadata thuật toán, **không chỉ 32 byte** | Có metadata thuật toán, **không chỉ 56 byte** |

**Đừng hiểu số 255 trong X25519 là “khóa đối xứng 255 bit” hay mức an toàn 255 bit.** Đây là tên hàm theo đường cong/trường hữu hạn, không phải tên kích thước khóa AES. X448 tương tự: shared secret 56 byte **không** chứng minh mức an toàn 448 bit. Một khóa AES-256 được dẫn xuất từ handshake X25519 cũng không tự làm toàn bộ trao đổi đạt mức bảo mật 256 bit.

Tài liệu RFC 7748 chỉ định encoding raw public u-coordinate và raw output theo **little-endian**; không được đảo byte tùy ý khi truyền hoặc giải mã. Với X25519, đầu vào public u-coordinate có quy tắc xử lý bit cao và giá trị không chính tắc trong RFC; đừng tự viết “validator điểm trên đường cong” bằng logic không hiểu RFC để thay thế JCA provider. Hãy dùng giao thức tiêu chuẩn và KeyFactory/KeyAgreement đúng hợp đồng.

### 2.1 XDH không phải EdDSA

- **X25519/X448:** thỏa thuận khóa Diffie–Hellman, không tạo chữ ký số.
- **Ed25519/Ed448:** thuật toán **chữ ký số** khác, không dùng thay cho `KeyAgreement("XDH")`.
- **ECDH** với đường cong Weierstrass (ví dụ P-256) cũng là key agreement nhưng có kiểu khóa, điểm và `KeySpec` khác; không tự ép `ECPrivateKey`/`ECPublicKey` sang `XECPrivateKey`/`XECPublicKey`.
- Không giả định Java 11 hỗ trợ mọi API EdDSA của những bản JDK sau; bài học này sử dụng chính xác các API XDH xuất hiện trong Java 11.

### 2.2 Hỗ trợ Java 11

**JEP 324** thêm X25519/X448 key agreement vào JDK 11. Provider **SunEC** trong Java SE 11 liệt kê:

| JCA service | Tên được hỗ trợ trong SunEC |
|---|---|
| `KeyPairGenerator` | `XDH`, `X25519`, `X448` |
| `KeyFactory` | `XDH`, `X25519`, `X448` |
| `KeyAgreement` | `XDH`, `X25519`, `X448` |

Với tên `XDH`, cần xác định nhóm khi sinh khóa/nhập khóa. `NamedParameterSpec.X25519` và `NamedParameterSpec.X448` hoặc `new NamedParameterSpec("X25519")` / `"X448"` là các cách biểu diễn nhóm ở Java 11. Ví dụ trong bài dùng `new NamedParameterSpec(group)` để chạy hai nhóm bằng cùng một hàm.

**Lưu ý tương thích TLS:** JDK 11 Release Notes ghi nhận phần triển khai JEP 324 lúc phát hành **chưa được tích hợp vào TLS 1.3 mới**. Vì vậy **không suy rằng chỉ cần `KeyAgreement.getInstance("XDH")` chạy được là cấu hình JSSE trên mọi bản Java 11 sẽ tự thương lượng X25519/X448 trong TLS**. Hãy kiểm tra JDK update, provider, named groups thực tế và giao thức của runtime. Với HTTPS/TLS 1.3, ưu tiên dùng `SSLSocket`/`HttpClient` hoặc thư viện TLS chuẩn để lớp TLS quản lý key schedule, authentication và key agreement.

## 3. Thuật toán key agreement theo RFC 7748

Mỗi bên có một cặp khóa:

```text
Alice:
  private scalar a  (giữ bí mật)
  public key A = X25519(a, basepoint 9)

Bob:
  private scalar b  (giữ bí mật)
  public key B = X25519(b, basepoint 9)
```

Hai bên trao đổi **chỉ public key** rồi tính:

```text
Alice: K_A = X25519(a, B)
Bob:   K_B = X25519(b, A)

K_A = K_B
```

Với `X448`, thay hàm `X25519` bằng `X448` và u basepoint bằng **5**. RFC chỉ định các phép toán scalar multiplication theo Montgomery ladder và phép **clamping/pruning** private scalar. Khi dùng JCA, hãy để provider làm phép toán đúng chuẩn; **không tự nhân điểm, tự clamp hoặc viết thuật toán constant-time** trong ứng dụng.

Key agreement là thao tác **một pha** đối với peer public key của X25519/X448. JCA thể hiện theo chuỗi:

```java
KeyAgreement agreement = KeyAgreement.getInstance("XDH");
agreement.init(ownPrivateKey);
agreement.doPhase(peerPublicKey, true);
byte[] rawSharedSecret = agreement.generateSecret();
```

Đây là **trích đoạn**, cần import `javax.crypto.KeyAgreement`, các biến `ownPrivateKey` (PrivateKey) và `peerPublicKey` (PublicKey) đúng cùng nhóm. `true` đánh dấu pha cuối. Giá trị `rawSharedSecret` phải được kiểm tra khác toàn 0 và dẫn xuất khóa qua key schedule phù hợp, không đem in log/ghi disk. Không sử dụng một instance `KeyAgreement` đồng thời từ nhiều thread.

### 3.1 Vì sao hai phía có thể tính được cùng secret?

X25519/X448 là các hàm scalar multiplication trên đường cong Montgomery, với tính chất Diffie–Hellman:

```text
A = X(a, basepoint)
B = X(b, basepoint)
X(a, B) = X(b, A)
```

Việc có `A` và `B` ở dạng public không cho phép thực tế tính được `K` nếu không biết một private scalar tương ứng trong mô hình an toàn của thuật toán. Nhưng nếu public key bị thay bằng khóa của attacker và **không có xác thực**, hai trao đổi khác nhau vẫn có thể thành công về mặt toán học. Do đó cần authentication.

### 3.2 Public key không phải secret, nhưng phải đúng nhóm

XDH chỉ kết hợp key của **cùng đường cong**. Không ghép private key X25519 với public key X448. Metadata của khóa nhập vào phải được gắn với nhóm đã được giao thức thống nhất; không dựa vào độ dài hoặc chuỗi hiển thị một cách sơ sài.

Việc nhận public key từ client/server bên ngoài cần thêm kiểm tra kích thước, định dạng, giới hạn số byte, algorithm id và danh tính nguồn theo giao thức. Provider có thể ném `InvalidKeyException` hoặc `InvalidKeySpecException` tùy bước. Không coi dữ liệu public là bí mật, nhưng cũng không coi nó là dữ liệu **đáng tin để cấp quyền**.

## 4. Ví dụ đầy đủ 1: Alice/Bob tạo X25519/X448 và dẫn xuất khóa

Chương trình `XdhAgreementDemo` sinh hai key pair mới với provider JCA cho mỗi nhóm; mỗi bên sử dụng private key của mình và public key của bên kia để tính raw shared secret. Chương trình **không in private key hoặc shared secret**. Nó kiểm tra shared secret có kích thước 32/56 byte và trùng nhau; sau đó dẫn xuất một khóa 32 byte bằng **HKDF-Extract/HKDF-Expand** viết bằng `Mac` chuẩn của Java 11. Nhãn `info` khác nhau phải tạo ra output khác nhau (domain separation).

**Giới hạn demo bảo mật:** Salt trong ví dụ là chuỗi public cố định chỉ để diễn giải API, **không phải key schedule cho hệ thống production**. Giao thức thật cần xác thực public key và bind đầy đủ hai public key/định danh/vai trò, protocol transcript, phiên bản, nonces và ngữ cảnh vào key schedule, với salt phù hợp. Đối với một giao thức như TLS 1.3, dùng luôn key schedule của thư viện thay vì copy helper này rồi tự chế TLS.

Lưu thành **`XdhAgreementDemo.java`**:

```java
import java.nio.charset.StandardCharsets;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.spec.NamedParameterSpec;
import java.util.Arrays;
import javax.crypto.KeyAgreement;
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

public class XdhAgreementDemo {
    static byte[] shared(KeyPair own, KeyPair peer)
            throws Exception {
        KeyAgreement agreement = KeyAgreement.getInstance("XDH");
        agreement.init(own.getPrivate());
        agreement.doPhase(peer.getPublic(), true);
        byte[] secret = agreement.generateSecret();
        int nonZero = 0;
        for (byte value : secret) {
            nonZero |= value & 0xFF;
        }
        if (nonZero == 0) {
            Arrays.fill(secret, (byte) 0);
            throw new SecurityException("Rejected all-zero XDH shared secret");
        }
        return secret;
    }

    static byte[] hkdf(byte[] ikm, byte[] salt, byte[] info,
                       int length, String algorithm) throws Exception {
        Mac extractor = Mac.getInstance(algorithm);
        int hLen = extractor.getMacLength();
        if (length < 1 || length > 255 * hLen) {
            throw new IllegalArgumentException("Unsupported HKDF length");
        }
        byte[] actualSalt = salt.length == 0 ? new byte[hLen] : salt;
        extractor.init(new SecretKeySpec(actualSalt, algorithm));
        byte[] prk = extractor.doFinal(ikm);
        byte[] result = new byte[length];
        byte[] previous = new byte[0];
        int offset = 0;
        try {
            Mac expander = Mac.getInstance(algorithm);
            expander.init(new SecretKeySpec(prk, algorithm));
            int counter = 1;
            while (offset < length) {
                expander.update(previous);
                expander.update(info);
                expander.update((byte) counter++);
                byte[] block = expander.doFinal();
                Arrays.fill(previous, (byte) 0);
                previous = block;
                int take = Math.min(block.length, length - offset);
                System.arraycopy(block, 0, result, offset, take);
                offset += take;
            }
            return result;
        } finally {
            Arrays.fill(previous, (byte) 0);
            Arrays.fill(prk, (byte) 0);
            if (salt.length == 0) Arrays.fill(actualSalt, (byte) 0);
        }
    }

    static void run(String group, int expectedLength) throws Exception {
        KeyPairGenerator generator = KeyPairGenerator.getInstance("XDH");
        generator.initialize(new NamedParameterSpec(group));
        KeyPair alice = generator.generateKeyPair();
        KeyPair bob = generator.generateKeyPair();

        byte[] a = shared(alice, bob);
        byte[] b = shared(bob, alice);
        byte[] salt = "public-demo-salt".getBytes(StandardCharsets.UTF_8);
        byte[] info = ("training/" + group + "/v1/traffic")
                .getBytes(StandardCharsets.UTF_8);
        byte[] other = ("training/" + group + "/v1/other")
                .getBytes(StandardCharsets.UTF_8);
        String hmac = group.equals("X448") ? "HmacSHA512" : "HmacSHA256";
        byte[] ka = hkdf(a, salt, info, 32, hmac);
        byte[] kb = hkdf(b, salt, info, 32, hmac);
        byte[] kc = hkdf(a, salt, other, 32, hmac);
        try {
            System.out.println(group + " shared-bytes=" + a.length);
            System.out.println(group + " shared-match="
                    + Arrays.equals(a, b));
            System.out.println(group + " length-valid="
                    + (a.length == expectedLength));
            System.out.println(group + " derived-match="
                    + Arrays.equals(ka, kb));
            System.out.println(group + " domain-separated="
                    + !Arrays.equals(ka, kc));
        } finally {
            Arrays.fill(a, (byte) 0);
            Arrays.fill(b, (byte) 0);
            Arrays.fill(ka, (byte) 0);
            Arrays.fill(kb, (byte) 0);
            Arrays.fill(kc, (byte) 0);
        }
    }

    public static void main(String[] args) throws Exception {
        run("X25519", 32);
        run("X448", 56);
    }
}
```

Lệnh chạy:

```bash
javac --release 11 -encoding UTF-8 XdhAgreementDemo.java
java XdhAgreementDemo
```

**Stdout đã kiểm chứng:**

```text
X25519 shared-bytes=32
X25519 shared-match=true
X25519 length-valid=true
X25519 derived-match=true
X25519 domain-separated=true
X448 shared-bytes=56
X448 shared-match=true
X448 length-valid=true
X448 derived-match=true
X448 domain-separated=true
```

**Diễn giải đầu ra:**

- `shared-bytes=32` và `56` là độ dài raw output chuẩn của X25519 và X448.
- `shared-match=true` chứng minh hai phía tính ra cùng raw secret cho **cặp key mới được sinh trong lần chạy đó**, dù mỗi lần chạy kết quả raw sẽ khác.
- `derived-match=true` chứng minh HKDF nhận cùng IKM/salt/info và tạo cùng một khóa 32 byte cho cả hai bên.
- `domain-separated=true` chứng minh đổi chuỗi `info` khiến output HKDF khác đối với cùng IKM/salt. Đây là một property test của HKDF, không phải bằng chứng tự đủ về authentication.
- Code cố ý dùng `Arrays.fill` để xóa những bản sao `byte[]` nhạy cảm đã tạo; điều này chỉ hạn chế tồn dư trên các mảng đó, **không đảm bảo** JVM/provider xóa mọi bản sao trong bộ nhớ hoặc private key object.

### 4.1 HKDF trong ví dụ hoạt động như thế nào?

Theo [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869), HKDF gồm:

```text
extract:
    PRK = HMAC(salt, IKM)

expand:
    T(0) = empty
    T(i) = HMAC(PRK, T(i-1) || info || byte(i))
    OKM  = first L bytes of T(1) || T(2) || ...

Điều kiện: 1 <= L <= 255 * HashLen
```

`IKM` ở đây là raw secret XDH; `salt` không phải private key, có thể được gửi/đồng thuận công khai; `info` gắn nhãn mục đích và transcript. `PRK` và các block `T(i)` là vật liệu nhạy cảm cần giới hạn vòng đời. Chương trình chọn `HmacSHA256` cho X25519 và `HmacSHA512` cho X448 để minh họa HMAC phù hợp, cùng độ dài đầu ra **32 byte** để dễ so sánh. Không có quy tắc rằng mọi giao thức dùng X448 **bắt buộc** chọn SHA-512 hoặc output 32 byte; key schedule phải theo **đặc tả giao thức**.

**Không dùng `new SecretKeySpec(rawSharedSecret, "AES")` như một key schedule tùy tiện.** Giá trị trao đổi Diffie–Hellman là nguyên liệu mật mã (IKM), không phải khóa AES đã được định danh mục đích, xác thực hay tách chiều gửi/nhận. Trong hệ thống dùng AES-GCM/ChaCha20-Poly1305, phải dẫn xuất khóa đúng độ dài và quản lý **nonce duy nhất**/AAD và replay protection theo protocol.

## 5. Java 11 và định dạng khóa theo RFC 7748

XDH xuất hiện ở nhiều dạng biểu diễn; đây là nơi dễ có lỗi tương tác giữa Java, OpenSSL, Go, Rust hoặc thư viện JS:

| Biểu diễn | Chứa gì | Dùng khi nào |
|---|---|---|
| Raw private scalar X25519/X448 | 32/56 byte, theo RFC; bí mật, unpruned encoded scalar | Vector test hoặc giao thức được thiết kế kỹ, **không gửi qua mạng** |
| Raw public u-coordinate | 32/56 byte **little-endian** | Peer public key trong giao thức sử dụng raw key |
| `XECPublicKeySpec` | Nhóm + tọa độ u dưới dạng `BigInteger` | Đưa raw public vào Java `KeyFactory` |
| `XECPrivateKeySpec` | Nhóm + `byte[]` encoded scalar (unpruned) | Đưa test vector private key vào Java |
| `PublicKey.getEncoded()` dạng X.509 SPKI | DER chứa algorithm id và public bytes | Lưu/truyền key theo định dạng SPKI |
| `PrivateKey.getEncoded()` dạng PKCS#8 phổ biến | Container DER của private key và metadata | Lưu trữ riêng theo policy bảo vệ key |
| `KeyAgreement.generateSecret()` | Raw shared value 32/56 byte | Dẫn xuất key bằng KDF, **không truyền** |

**Quan trọng:** `KeyFactory.getInstance("XDH").generatePublic(new X509EncodedKeySpec(spkiBytes))` mong chờ một **SPKI DER hoàn chỉnh**, không phải chuỗi raw 32/56 byte. Ngược lại, `XECPublicKeySpec` nhận **`BigInteger u`**, không nhận raw `byte[]`. Phải chuyển **little-endian raw u** sang **unsigned BigInteger** đúng cách.

### 5.1 Quy đổi public key little-endian sang BigInteger

Ví dụ raw u-coordinate bắt đầu bằng hex `09 00 00 ... 00` cho basepoint X25519. Giá trị đại số của u là 9. Đối với raw u có bit cao set, `BigInteger(byte[])` mặc định xử lý **big-endian có dấu**, dễ tạo giá trị sai nếu đưa raw vào trực tiếp. Cách đúng:

```java
byte[] bigEndian = rawLittleEndian.clone();
for (int left = 0, right = bigEndian.length - 1;
        left < right; left++, right--) {
    byte temp = bigEndian[left];
    bigEndian[left] = bigEndian[right];
    bigEndian[right] = temp;
}
BigInteger unsignedU = new BigInteger(1, bigEndian);
PublicKey peer = KeyFactory.getInstance("XDH")
        .generatePublic(new XECPublicKeySpec(
                new NamedParameterSpec("X25519"), unsignedU));
```

Đây là **trích đoạn**, cần import `BigInteger`, `KeyFactory`, `PublicKey`, `XECPublicKeySpec`, `NamedParameterSpec`; biến `rawLittleEndian` phải là raw u-coordinate đúng định dạng/kích thước và thuộc nhóm X25519. Với X448, thay nhóm `"X448"` và raw 56 byte. Constructor `new BigInteger(1, ...)` tránh biến byte có bit cao thành một số âm. Trong ứng dụng thực, nên có helper riêng được test bằng vector, kiểm tra độ dài và lỗi input trước khi gọi `KeyFactory`.

Với **private scalar**, `XECPrivateKeySpec(params, scalarBytes)` đã nhận byte array theo encoding RFC 7748; **không đảo byte private scalar** hay tự biến nó thành `BigInteger` như public u. Tài liệu Java 11 xác định đây là **unpruned encoded scalar**: việc clamp/prune bit thuộc thuật toán/provider khi thực hiện phép toán.

### 5.2 Có phải mọi khóa đều cho phép trích xuất private scalar?

Không. `XECPrivateKey.getScalar()` trả `Optional<byte[]>` vì provider có thể giữ private key trong phần cứng/non-exportable. Một key `PrivateKey` có thể dùng cho phép ký/trao đổi mà không cho ứng dụng trích xuất bytes. **Không** tạo logic nghiệp vụ phụ thuộc `getEncoded() != null` hoặc private bytes luôn export được.

Trong code production, hạn chế ghi private material vào log, metrics, exception, crash dump hoặc file tạm. Nếu lưu dài hạn, sử dụng keystore/HSM theo yêu cầu sản phẩm, phân quyền và rotation. Trong hầu hết ECDHE handshakes, ưu tiên **ephemeral key** mới cho mỗi phiên thay vì cố tình lưu raw private bytes.

## 6. Ví dụ đầy đủ 2: kiểm chứng Alice/Bob theo RFC 7748

Khác với ví dụ sinh khóa ngẫu nhiên, bộ kiểm thử RFC 7748 cho dữ liệu **cố định**: scalar riêng tư dạng **test vector công khai**, public u-coordinate và shared secret expected. Mục tiêu của test là phát hiện lỗi encoding, đặt sai nhóm, dùng sai provider/method, sai thứ tự byte và phép toán thiếu pha.

Chương trình:

1. Dùng `KeyFactory.getInstance("XDH")` và `XECPrivateKeySpec` để tạo private key từ scalar RFC; key test này **không được dùng trong production**.
2. Tạo public key của basepoint 9 (X25519) hoặc 5 (X448), tính public của Alice/Bob bằng `KeyAgreement`.
3. Tạo peer public key từ tọa độ u theo `XECPublicKeySpec`, so Alice và Bob shared secret với expected.
4. Kiểm tra cả **ba thuộc tính** cho mỗi nhóm: Alice-public, Bob-public, shared-secret. Nếu sai, ném `AssertionError`.

Lưu thành **`Rfc7748VectorsDemo.java`**:

```java
import java.math.BigInteger;
import java.security.KeyFactory;
import java.security.PrivateKey;
import java.security.PublicKey;
import java.security.spec.NamedParameterSpec;
import java.security.spec.XECPrivateKeySpec;
import java.security.spec.XECPublicKeySpec;
import java.util.Arrays;
import javax.crypto.KeyAgreement;

public class Rfc7748VectorsDemo {
    static byte[] hex(String value) {
        String s = value.replaceAll("\\s+", "");
        if ((s.length() & 1) != 0) {
            throw new IllegalArgumentException("Odd hex string");
        }
        byte[] result = new byte[s.length() / 2];
        for (int i = 0; i < result.length; i++) {
            result[i] = (byte) Integer.parseInt(
                    s.substring(2 * i, 2 * i + 2), 16);
        }
        return result;
    }

    static BigInteger fromLittleEndian(byte[] little) {
        byte[] big = little.clone();
        for (int left = 0, right = big.length - 1;
                left < right; left++, right--) {
            byte temp = big[left];
            big[left] = big[right];
            big[right] = temp;
        }
        return new BigInteger(1, big);
    }

    static byte[] xdh(String group, byte[] scalar, byte[] peerU)
            throws Exception {
        NamedParameterSpec params = new NamedParameterSpec(group);
        KeyFactory factory = KeyFactory.getInstance("XDH");
        PrivateKey privateKey = factory.generatePrivate(
                new XECPrivateKeySpec(params, scalar));
        PublicKey publicKey = factory.generatePublic(
                new XECPublicKeySpec(params, fromLittleEndian(peerU)));
        KeyAgreement agreement = KeyAgreement.getInstance("XDH");
        agreement.init(privateKey);
        agreement.doPhase(publicKey, true);
        return agreement.generateSecret();
    }

    static void verify(String group, int size, int baseValue,
                       String alicePrivateHex, String alicePublicHex,
                       String bobPrivateHex, String bobPublicHex,
                       String secretHex) throws Exception {
        byte[] aPrivate = hex(alicePrivateHex);
        byte[] aPublic = hex(alicePublicHex);
        byte[] bPrivate = hex(bobPrivateHex);
        byte[] bPublic = hex(bobPublicHex);
        byte[] secret = hex(secretHex);
        if (aPrivate.length != size || aPublic.length != size
                || bPrivate.length != size || bPublic.length != size
                || secret.length != size) {
            throw new IllegalArgumentException("Wrong vector length");
        }
        byte[] basePoint = new byte[size];
        basePoint[0] = (byte) baseValue;

        boolean alicePublicMatch =
                Arrays.equals(aPublic, xdh(group, aPrivate, basePoint));
        boolean bobPublicMatch =
                Arrays.equals(bPublic, xdh(group, bPrivate, basePoint));
        boolean secretMatch =
                Arrays.equals(secret, xdh(group, aPrivate, bPublic))
                && Arrays.equals(secret, xdh(group, bPrivate, aPublic));
        System.out.println(group + " alice-public=" + alicePublicMatch);
        System.out.println(group + " bob-public=" + bobPublicMatch);
        System.out.println(group + " shared=" + secretMatch);
        if (!alicePublicMatch || !bobPublicMatch || !secretMatch) {
            throw new AssertionError("RFC 7748 vector mismatch");
        }
        Arrays.fill(aPrivate, (byte) 0);
        Arrays.fill(bPrivate, (byte) 0);
    }

    public static void main(String[] args) throws Exception {
        verify("X25519", 32, 9,
                "77076d0a7318a57d3c16c17251b26645df4c2f87ebc0992ab177fba51db92c2a",
                "8520f0098930a754748b7ddcb43ef75a0dbf3a0d26381af4eba4a98eaa9b4e6a",
                "5dab087e624a8a4b79e17f8b83800ee66f3bb1292618b6fd1c2f8b27ff88e0eb",
                "de9edb7d7b7dc1b4d35b61c2ece435373f8343c85b78674dadfc7e146f882b4f",
                "4a5d9d5ba4ce2de1728e3bf480350f25e07e21c947d19e3376f09b3c1e161742");

        verify("X448", 56, 5,
                "9a8f4925d1519f5775cf46b04b5800d4ee9ee8bae8bc5565d498c28d"
              + "d9c9baf574a9419744897391006382a6f127ab1d9ac2d8c0a598726b",
                "9b08f7cc31b7e3e67d22d5aea121074a273bd2b83de09c63faa73d2c"
              + "22c5d9bbc836647241d953d40c5b12da88120d53177f80e532c41fa0",
                "1c306a7ac2a0e2e0990b294470cba339e6453772b075811d8fad0d1d"
              + "6927c120bb5ee8972b0d3e21374c9c921b09d1b0366f10b65173992d",
                "3eb7a829b0cd20f5bcfc0b599b6feccf6da4627107bdb0d4f345b430"
              + "27d8b972fc3e34fb4232a13ca706dcb57aec3dae07bdc1c67bf33609",
                "07fff4181ac6cc95ec1c16a94a0f74d12da232ce40a77552281d282b"
              + "b60c0b56fd2464c335543936521c24403085d59a449a5037514a879d");
    }
}
```

**Điều gì được kiểm chứng?**

- Cùng private scalar và basepoint tạo đúng public key đã công bố trong RFC.
- Hai cách tính `X(a, B)` và `X(b, A)` đều khớp giá trị K từ RFC, không chỉ bằng nhau với nhau.
- Việc chuyển u-coordinate little-endian sang `BigInteger` dương không đảo sai byte.
- JCA `KeyAgreement` hỗ trợ cả X25519 và X448 với khóa được tạo qua `KeyFactory` trong runtime thử nghiệm.
- Vector này độc lập với `SecureRandom`, có thể đưa vào regression test. Nó **không** thay thế test authentication/transport/timeout hoặc kiểm định mật mã của toàn bộ ứng dụng.

**Không bao giờ tái sử dụng scalar hardcoded trong RFC như private key thật.** Tất cả scalar của ví dụ đều công khai; một attacker có thể tính cùng shared secret nếu bạn dùng chúng trong thực tế.

## 7. Ví dụ đầy đủ 3: round-trip X.509 và từ chối đầu vào nguy hiểm

Chương trình này tập trung các ranh giới thường gặp khi tích hợp:

- Serialize public key Java theo `getEncoded()` (thường là DER `SubjectPublicKeyInfo`), rồi parse lại bằng `X509EncodedKeySpec`. Shared secret trước và sau parse phải giống nhau.
- Kiểm tra SPKI chứa metadata nên **dài hơn raw u-coordinate** 32/56 byte; đừng gửi nguyên SPKI vào nơi yêu cầu raw public.
- Đưa public key có tọa độ u = 0 vào XDH; JDK SunEC có thể từ chối ngay khi thực hiện phép toán. Nếu provider nào đó tạo toàn-zero shared secret, ứng dụng **bắt buộc bỏ kết quả đó**.
- Kết hợp private X25519 với public X448 phải thất bại. Chương trình xác nhận không chấp nhận nhầm nhóm.

Lưu thành **`XdhEncodingSafetyDemo.java`**:

```java
import java.math.BigInteger;
import java.security.InvalidKeyException;
import java.security.KeyFactory;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.PublicKey;
import java.security.spec.NamedParameterSpec;
import java.security.spec.X509EncodedKeySpec;
import java.security.spec.XECPublicKeySpec;
import java.util.Arrays;
import javax.crypto.KeyAgreement;

public class XdhEncodingSafetyDemo {
    static byte[] secret(KeyPair own, PublicKey peer) throws Exception {
        KeyAgreement ka = KeyAgreement.getInstance("XDH");
        ka.init(own.getPrivate());
        ka.doPhase(peer, true);
        byte[] shared = ka.generateSecret();
        int nonZero = 0;
        for (byte value : shared) nonZero |= value & 0xFF;
        if (nonZero == 0) {
            Arrays.fill(shared, (byte) 0);
            throw new InvalidKeyException("All-zero shared secret rejected");
        }
        return shared;
    }

    static KeyPair keyPair(String group) throws Exception {
        KeyPairGenerator kpg = KeyPairGenerator.getInstance("XDH");
        kpg.initialize(new NamedParameterSpec(group));
        return kpg.generateKeyPair();
    }

    static void check(String group, int rawBytes) throws Exception {
        KeyPair alice = keyPair(group);
        KeyPair bob = keyPair(group);
        byte[] spki = bob.getPublic().getEncoded();
        PublicKey parsed = KeyFactory.getInstance("XDH")
                .generatePublic(new X509EncodedKeySpec(spki));
        byte[] before = secret(alice, bob.getPublic());
        byte[] after = secret(alice, parsed);
        System.out.println(group + " x509-roundtrip="
                + Arrays.equals(before, after));
        System.out.println(group + " spki-longer-than-raw="
                + (spki.length > rawBytes));
        Arrays.fill(before, (byte) 0);
        Arrays.fill(after, (byte) 0);

        PublicKey lowOrder = KeyFactory.getInstance("XDH")
                .generatePublic(new XECPublicKeySpec(
                        new NamedParameterSpec(group), BigInteger.ZERO));
        boolean rejected = false;
        try {
            byte[] zeroSecret = secret(alice, lowOrder);
            int aggregate = 0;
            for (byte b : zeroSecret) aggregate |= b & 0xff;
            rejected = aggregate == 0;
            Arrays.fill(zeroSecret, (byte) 0);
        } catch (InvalidKeyException expected) {
            rejected = true;
        }
        System.out.println(group + " all-zero-u-rejected="
                + rejected);
        if (!rejected) {
            throw new AssertionError("Dangerous peer key accepted");
        }
    }

    public static void main(String[] args) throws Exception {
        check("X25519", 32);
        check("X448", 56);
        KeyPair a = keyPair("X25519");
        KeyPair b = keyPair("X448");
        boolean mismatchRejected = false;
        try {
            secret(a, b.getPublic());
        } catch (InvalidKeyException expected) {
            mismatchRejected = true;
        }
        System.out.println("mixed-group-rejected=" + mismatchRejected);
        if (!mismatchRejected) {
            throw new AssertionError("Mismatched group unexpectedly accepted");
        }
    }
}
```

Lệnh:

```bash

java XdhEncodingSafetyDemo
```

**Kết quả trên Java runtime thử nghiệm có XDH provider tương thích SunEC:**

```text

X25519 spki-longer-than-raw=true
X25519 all-zero-u-rejected=true
X448 x509-roundtrip=true
X448 spki-longer-than-raw=true
X448 all-zero-u-rejected=true
mixed-group-rejected=true
```

**Đọc kết quả cẩn thận:**

- `x509-roundtrip=true`: cùng public key đã được parse lại cho cùng raw shared secret, chứng minh metadata/key format được hiểu đúng.
- `spki-longer-than-raw=true`: toàn bộ X.509 SPKI không phải raw public u-coordinate. Không hardcode rằng mọi provider/format của mọi loại khóa đều giống độ dài DER của SunEC.
- `all-zero-u-rejected=true`: chương trình từ chối peer low-order có u=0 qua `InvalidKeyException` từ provider **hoặc** qua bước kiểm tra raw secret toàn 0. Điều này là yêu cầu phòng vệ của chương trình, không phải lời hứa rằng mọi JCA provider sẽ ném cùng một exception ở cùng một dòng.
- `mixed-group-rejected=true`: key agreement không chấp nhận private X25519 và public X448, tránh lỗi xử lý “mọi EC key đều đổi được cho nhau”.

### 7.1 Vì sao phải kiểm tra shared secret toàn 0?

RFC 7748 mô tả một số đầu vào u-coordinate thuộc subgroup bậc nhỏ, có thể tạo shared secret **toàn zero** bất kể private scalar. Nếu chấp nhận như một bí mật mạnh, nhiều cặp khác nhau có thể bị ép dùng cùng giá trị yếu, phá giả định bảo mật của key schedule. RFC 7748 cho phép phép kiểm tra và yêu cầu hệ thống có chính sách phù hợp.

Một kiểm tra theo byte tránh dừng sớm dựa vào nội dung secret:

```java
int nonZero = 0;
for (byte value : secret) {
    nonZero |= value & 0xFF;
}
if (nonZero == 0) {
    Arrays.fill(secret, (byte) 0);
    throw new InvalidKeyException("All-zero XDH shared secret");
}
```

Đây là **trích đoạn**, cần import `Arrays` và `InvalidKeyException`, `secret` là `byte[]` vừa nhận từ `generateSecret()`. Bitwise-OR quét toàn bộ buffer, không dừng sớm ở byte đầu khác 0. Điều này giúp tránh việc check tiết lộ vị trí byte khác 0 qua nhánh dừng sớm; an toàn side-channel cuối cùng vẫn phụ thuộc JCA provider, JIT, máy và môi trường.

**Phân biệt với validation thông thường:** không tự làm phép kiểm điểm từ các công thức elliptic curve để “bổ sung bảo vệ” rồi vô tình chặn đầu vào mà RFC yêu cầu chấp nhận. Hãy dùng provider được hỗ trợ, kiểm soát raw length, nhóm, encoding, và từ chối all-zero output. Đối với giao thức ứng dụng, cần thêm authentication/binding chống MITM.

## 8. Khi nào dùng raw u-coordinate và khi nào dùng SPKI?

### Giao thức yêu cầu raw public key

Một số wire formats ghi public key là `32 byte (X25519)` hoặc `56 byte (X448)`. Đối tác phải thống nhất chính xác độ dài và little-endian. Cần parser byte của protocol, không gọi `getEncoded()` rồi coi output đó là raw key. Nếu nhận raw bytes, dựng `XECPublicKeySpec` bằng `BigInteger` dương từ little-endian như ví dụ.

### Giao thức yêu cầu X.509 SubjectPublicKeyInfo

X.509 SPKI chứa `AlgorithmIdentifier` và `subjectPublicKey` theo ASN.1/DER. Java public key thường cho `getFormat() == "X.509"` và `getEncoded()` là SPKI. Nếu nhận SPKI, dùng:

```java
PublicKey publicKey = KeyFactory.getInstance("XDH")
        .generatePublic(new X509EncodedKeySpec(spkiBytes));
```

Đây là **trích đoạn**, cần import `KeyFactory`, `PublicKey` và `X509EncodedKeySpec`; `spkiBytes` phải là DER SPKI của khóa đúng nhóm. Không trộn raw public 32/56 byte với SPKI. Không được chuyển `private.getEncoded()` (PKCS#8) lên mạng như public key; private key phải nằm phía sở hữu.

### Sơ đồ luồng đúng

```text
Đối tác A                           Đối tác B
--------------------                --------------------
KeyPairGenerator(X25519)            KeyPairGenerator(X25519)
        |                                    |
public key -> (raw u hoặc SPKI theo protocol)
        | -------------------------------> |
        | <------------------------------- |
  parser đúng định dạng                   parser đúng định dạng
        |                                    |
KeyAgreement(private_A, public_B)  KeyAgreement(private_B, public_A)
        |                                    |
      shared raw K  ===================  shared raw K
        |                                    |
  authenticated transcript + HKDF      authenticated transcript + HKDF
        |                                    |
     session keys                     session keys
```

Nếu protocol dùng `SPKI`, không đảo byte toàn bộ DER. Nếu dùng `raw u`, không đưa chuỗi đó vào `X509EncodedKeySpec`. Độ dài đúng **chưa đủ** để xác định một public key đã được xác thực danh tính.

## 9. XDH không tự xác thực: man-in-the-middle và key confirmation

### 9.1 MITM với Diffie–Hellman thuần túy

Một attacker đứng giữa thay public key của Alice bằng public key attacker khi gửi tới Bob, và ngược lại. Alice/Bob vẫn có thể tính ra một raw secret hợp lệ — nhưng **mỗi người chia sẻ secret với attacker**, không phải với nhau. Không có `KeyAgreement` exception nào cho biết danh tính peer bị giả mạo; nguyên thủy toán học không giải quyết bài toán xác thực.

Để bảo vệ kênh thực tế:

1. Sử dụng **TLS 1.3/HTTPS** hoặc giao thức đã qua rà soát, gồm certificate/trust verification, authentication, transcript binding và key schedule hoàn chỉnh.
2. Nếu tự xây tầng bảo mật ứng dụng vì yêu cầu thật sự đặc biệt, cần thiết kế được đánh giá chuyên gia: xác thực khóa công khai, ký các thông điệp trao đổi hoặc gắn với một kênh đã xác thực; bind public keys và identities vào transcript.
3. Dẫn xuất **key theo vai trò và hướng** (client→server, server→client), chức năng (encryption, authentication, exporter) và phiên bản protocol để tránh cùng khóa được dùng cho hai mục đích khác nhau.
4. Dùng symmetric AEAD tiêu chuẩn sau key schedule; kiểm soát nonce, replay, sequence number và lỗi xác thực ciphertext.
5. Quản lý key rotation, ephemeral keys, timeout, đóng phiên và hủy vật liệu bí mật. Không coi `shared-match=true` trong bài demo là xác minh danh tính.

### 9.2 Ephemeral XDH và forward secrecy

Khi mỗi phiên sinh key pair X25519/X448 **mới**, được xác thực bởi protocol đúng và key material sau đó được xử lý an toàn, key agreement dạng ephemeral có thể góp phần tạo **forward secrecy**. Tuy nhiên chỉ “dùng X25519” chưa đủ để bảo đảm forward secrecy: còn phụ thuộc việc giữ/xóa private key, authentication, key schedule và cách protocol tái sử dụng khóa.

Một private key **tĩnh** có thể là một thành phần của một số giao thức được thiết kế riêng, nhưng không nên tùy tiện thay ephemeral key bằng khóa lâu dài chỉ để giảm CPU. Rò rỉ static private có hậu quả khác với ephemeral private bị lộ sau khi phiên đã kết thúc.

## 10. Làm việc với dữ liệu bí mật trong Java

### 10.1 SecureRandom và lifecycle của khóa

Sử dụng `KeyPairGenerator` từ provider được tin cậy. Không tự tạo scalar bằng `java.util.Random`, thời gian hệ thống hoặc UUID. Nếu ứng dụng có yêu cầu tuân thủ/nhà cung cấp mật mã cụ thể, kiểm tra thuật toán, provider, key extraction policy và nguồn randomness của môi trường chạy.

Private key nên chỉ tồn tại trong thời gian cần thiết cho phiên. Không serialize hoặc log private key trừ khi đó là nghiệp vụ lưu khóa được thiết kế rõ và có bảo vệ thích hợp. Các đối tượng Java `PrivateKey` có thể không cho xuất raw bytes (HSM) và không đảm bảo mọi bản sao private key được zeroize tự động. Có thể xóa mảng `byte[]` tạm do ứng dụng sở hữu bằng `Arrays.fill` nhưng không hứa xóa được toàn bộ memory, heap copy hoặc runtime state.

### 10.2 Shared secret không phải dữ liệu để log/debug

Không in `Base64`/hex của raw shared secret, private scalar, PRK, OKM và session key vào log. Ví dụ trong bài chỉ in **boolean, độ dài**. Nếu cần chứng minh hai bên match, dùng xác nhận ở tầng giao thức/crypto hợp lệ; đừng gửi raw secret qua mạng chỉ để so sánh.

Một cách chống nhầm lẫn là định nghĩa key schedule API nhận raw shared secret và trả object key được phân quyền sử dụng; không phát tán raw byte array cho nhiều lớp ứng dụng. Với Java 11, khóa dẫn xuất có thể được gói trong `SecretKeySpec` cho thuật toán AES/HMAC phù hợp, nhưng chỉ **sau** KDF và đúng metadata/độ dài.

### 10.3 Không dùng KeyAgreement chung giữa thread

`KeyAgreement` có state: `init`, `doPhase`, `generateSecret`. Dùng riêng instance cho mỗi trao đổi/chu kỳ, không share mutable instance cho nhiều kết nối. Tương tự, `Mac` cũng có state, không tự ý dùng cùng một instance HKDF song song giữa thread.

### 10.4 Phân biệt lỗi kiểu khóa với lỗi giao thức

`InvalidKeyException` có thể đến khi private/public key không phù hợp, nhóm khác nhau hoặc nhà cung cấp từ chối điểm nguy hiểm. `NoSuchAlgorithmException` có thể phát sinh nếu provider không hỗ trợ `XDH/X448`; `InvalidKeySpecException` có thể đến khi parse nhập khóa sai định dạng. Cần báo nguyên nhân ở mức **loại lỗi** mà không lộ secret/key material. Nếu đối tác không hỗ trợ nhóm đó, dùng nhóm khác **chỉ qua negotiation được xác thực và được protocol cho phép**, không âm thầm downgrade xuống thuật toán yếu.

## 11. Ma trận kiểm thử X25519 và X448

| Ca | Đầu vào / thao tác | Kết quả cần kiểm tra |
|---|---|---|
| X25519 hai bên | Sinh hai KeyPair, trao public, tính mỗi phía | Raw secret bằng nhau, 32 byte |
| X448 hai bên | Tương tự | Raw secret bằng nhau, 56 byte |
| HKDF trùng context | Cùng IKM/salt/info | OKM trùng nhau |
| HKDF khác context | Cùng IKM/salt nhưng `info` khác | OKM không trùng cho test này |
| RFC X25519 Alice | Private scalar + basepoint 9 | Public u đúng vector |
| RFC X25519 Bob | Private scalar + basepoint 9 | Public u đúng vector |
| RFC X25519 shared | Alice private/Bob public và ngược lại | Khớp shared secret RFC |
| RFC X448 Alice | Private scalar + basepoint 5 | Public u đúng vector |
| RFC X448 Bob | Private scalar + basepoint 5 | Public u đúng vector |
| RFC X448 shared | Hai phía | Khớp shared secret RFC |
| SPKI round-trip | `getEncoded` -> `X509EncodedKeySpec` | Shared secret không đổi |
| Raw vs SPKI | So độ dài SPKI với raw | SPKI dài hơn raw |
| All-zero u | Public `u = 0` | KeyAgreement từ chối hoặc kiểm tra K=0 báo lỗi; không dùng secret đó |
| Nhầm curve | Private X25519 + public X448 | Fail rõ ràng |
| Raw length sai | 31/33 byte với X25519; 55/57 byte với X448 | Parser/protocol từ chối trước khi sử dụng |
| Nhầm endian | Đảo byte u khi import | Vector RFC mismatch |
| Public giả mạo | Thay public key bằng attacker key trong test handshake | Authentication/transcript check phải thất bại, không coi DH match là peer hợp lệ |
| Duplicate/replay | Replay thông điệp handshake cũ | Protocol có nonce/transcript/session identifier phù hợp |
| Provider thiếu thuật toán | Không có service XDH/X448 | Báo lỗi cấu hình hoặc negotiated alternative hợp lệ, không fallback âm thầm |
| Concurrent sessions | Nhiều cặp key ở nhiều thread | Không share state `KeyAgreement`, không leak secret |
| Key retirement | Hoàn tất phiên | Raw arrays được dọn trong phạm vi ứng dụng; private key lifecycle theo policy |

**Kiểm thử có giá trị nhất:** kết hợp vector chính thức RFC 7748 (đúng toán học/encoding), negative tests (wrong-group/zero peer), integration tests (serialize/parse public key), và tests cho giao thức đã xác thực. Chỉ có một test “Alice và Bob tự tính ra hai mảng giống nhau” vẫn có thể cùng sai thứ tự byte hoặc dùng sai thuật toán; test vectors giúp phát hiện.

| Log raw shared secret / private scalar | Lộ toàn bộ khóa phiên | Chỉ log metadata không nhạy cảm |
| Dùng cùng `KeyAgreement` instance cho nhiều thread | State mutable không được phối hợp | Instance riêng cho mỗi trao đổi |

| Không xử lý lỗi provider lúc nhập khóa | Lỗi có thể xảy ra ở KeyFactory hoặc doPhase | Validate input, catch đúng tầng, dừng handshake |

## 13. Bài tập tự luyện có đáp án

**1.** Trong X25519, Alice có private scalar 32 byte và public u-coordinate của Bob 32 byte. Cần gọi API JCA nào để tạo shared secret?  
**Đáp án:** `KeyAgreement.getInstance("XDH")` hoặc `"X25519"`, `init(alicePrivate)`, `doPhase(bobPublic,true)`, `generateSecret()`. Hai key phải thuộc X25519 và raw output phải được kiểm tra rồi đưa vào KDF.

**2.** X448 sử dụng bao nhiêu byte cho raw public/shared secret, và basepoint u bằng bao nhiêu?  
**Đáp án:** 56 byte, basepoint u = 5; X25519 tương ứng 32 byte và basepoint u = 9.

**3.** Khi nhập X25519 public raw theo RFC, có dùng `new BigInteger(rawBytes)` rồi `XECPublicKeySpec` ngay được không?  
**Đáp án:** không. RFC dùng little-endian, `BigInteger(byte[])` mặc định signed big-endian. Đảo byte và gọi `new BigInteger(1, bigEndian)` để lấy u dương.

**4.** Một byte array SPKI của public X25519 dài hơn 32 byte. Điều đó chứng tỏ key sai không?  
**Đáp án:** không. SPKI có metadata thuật toán/DER. Chỉ phần raw u-coordinate theo RFC mới có đúng 32 byte.

**5.** Cả Alice và Bob dùng `X25519`, hai raw secret bằng nhau. Hệ thống có được bỏ xác thực server không?  
**Đáp án:** không. MITM có thể thay public key; phải có authentication hoặc protocol chuẩn như TLS.

**6.** Peer gửi public u-coordinate thuộc bậc nhỏ tạo shared secret toàn 0. Bạn làm gì?  
**Đáp án:** từ chối key agreement, không dùng K làm đầu vào tiếp tục; provider có thể đã ném InvalidKeyException hoặc ứng dụng kiểm tra toàn-zero theo byte.

**7.** Tại sao hai bên dùng cùng raw secret nhưng HKDF tạo khóa khác nhau?  
**Đáp án:** vì `salt`, `info`, thuật toán HMAC hoặc độ dài đầu ra không giống nhau. Hai bên phải đồng thuận key schedule; có thể cố ý dùng `info` khác để tách khóa theo vai trò.

**8.** Khi dùng `KeyPairGenerator.getInstance("XDH")`, có nên dựa hoàn toàn vào nhóm mặc định của mọi provider không?  
**Đáp án:** không. Hãy chọn `NamedParameterSpec.X25519` hoặc `X448` tường minh theo giao thức.

**9.** Một thư viện Java 11 hỗ trợ `X448` trong JCA. Có chắc TLS 1.3 của runtime cũng thương lượng được X448 không?  
**Đáp án:** không; phải kiểm tra JSSE/provider/runtime hỗ trợ named group thực tế. JDK11 release notes từng phân biệt JEP324 XDH JCA với tích hợp TLS 1.3.

**10.** Có được dùng Ed25519 public key như X25519 peer key chỉ vì cùng “25519” trong tên?  
**Đáp án:** không. Ed25519 là chữ ký số, X25519 là key agreement, encoding và giao thức khác; không ép đổi kiểu tùy tiện.

**11.** KeyAgreement tính ra 32 byte rồi kết quả được in hex trong log debug. Có rủi ro gì?  
**Đáp án:** raw shared secret là bí mật mật mã; lộ nó có thể làm lộ khóa phiên dẫn xuất. Không log, dùng boolean/checksum test chỉ trong test không có private production.

**12.** Vì sao nên dùng key pair ephemeral mới cho handshake thay vì dùng cùng private key cho mọi phiên?  
**Đáp án:** giảm ảnh hưởng rò khóa lâu dài và góp phần đạt forward secrecy khi protocol xác thực đúng. Nhưng phải có key lifecycle, nonce, transcript binding và chính sách replay/refresh.

## 14. Tài liệu chính thức và tham chiếu kỹ thuật

- [RFC 7748 — Elliptic Curves for Security](https://www.rfc-editor.org/rfc/rfc7748): định nghĩa X25519, X448, encoding little-endian, basepoint, low-order considerations và vector Alice/Bob mục 6.
- [RFC 5869 — HMAC-based Extract-and-Expand Key Derivation Function](https://www.rfc-editor.org/rfc/rfc5869): HKDF-Extract/HKDF-Expand, salt, info và giới hạn output length.
- [JEP 324 — Key Agreement with Curve25519 and Curve448](https://openjdk.org/jeps/324): tính năng XDH trong Java 11.
- [Java SE 11 — SunEC Provider](https://docs.oracle.com/en/java/javase/11/security/oracle-providers.html): dịch vụ `KeyPairGenerator`, `KeyAgreement`, `KeyFactory` và tên XDH/X25519/X448.
- [Java SE 11 — Java Security Standard Algorithm Names](https://docs.oracle.com/en/java/javase/11/docs/specs/security/standard-names.html): tên thuật toán/nhóm bảo đảm tương tác API.
- [Java SE 11 — NamedParameterSpec](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/java/security/spec/NamedParameterSpec.html): tên nhóm X25519/X448.
- [Java SE 11 — KeyPairGenerator](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/java/security/KeyPairGenerator.html): `initialize` và `generateKeyPair`.
- [Java SE 11 — KeyAgreement](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/javax/crypto/KeyAgreement.html): `init`, `doPhase`, `generateSecret`.
- [Java SE 11 — XECPrivateKeySpec](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/java/security/spec/XECPrivateKeySpec.html): private encoded scalar unpruned.
- [Java SE 11 — XECPublicKeySpec](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/java/security/spec/XECPublicKeySpec.html): u-coordinate biểu diễn dưới dạng `BigInteger`.
- [Java SE 11 — XECPublicKey](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/java/security/interfaces/XECPublicKey.html) và [XECPrivateKey](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/java/security/interfaces/XECPrivateKey.html): giao diện khóa và khả năng xuất scalar.
- [Java SE 11 — X509EncodedKeySpec](https://docs.oracle.com/en/java/javase/11/docs/api/java.base/java/security/spec/X509EncodedKeySpec.html): nhập public key dạng X.509 SubjectPublicKeyInfo.
- [Java SE 11 Release Notes](https://www.oracle.com/java/technologies/javase/11-relnote-issues.html): phần JEP324 và lưu ý tình trạng tích hợp với TLS 1.3 ở bản phát hành ban đầu.
- [RFC 8446 — TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446): ví dụ một giao thức có xác thực, key schedule, transcript binding và cơ chế thương lượng nhóm.

**Tóm tắt kỹ thuật:** `X25519` và `X448` là các primitive key agreement an toàn, phù hợp Java hiện đại khi dùng qua provider đúng chuẩn. Trên Java 11, chọn nhóm tường minh, nhập public key đúng format/little-endian, thực hiện `init → doPhase → generateSecret`, từ chối raw shared secret toàn 0 và dẫn xuất khóa qua key schedule có context. Quan trọng nhất: **XDH tự thân không xác thực peer**. Giao tiếp thực tế cần protocol đã xác thực, quản lý phiên/khóa và xử lý lỗi đúng vòng đời, không chỉ một phép toán shared-secret thành công.
