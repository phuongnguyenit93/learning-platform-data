# Đánh giá CPU, RSS và bộ nhớ heap dưới tải thực với ZGC (Java 15+)

## Mục tiêu

**Z Garbage Collector (ZGC)** là bộ thu gom rác được tối ưu để giữ các lần **stop-the-world GC pause** rất ngắn bằng cách thực hiện phần lớn công việc đồng thời với luồng ứng dụng. ZGC trở thành tính năng production của HotSpot từ **Java 15 (JEP 377)**. Tuy nhiên, **GC pause thấp không có nghĩa CPU thấp, RSS thấp, hay p99 của request luôn thấp**. Concurrent GC phải dùng CPU, memory headroom và vẫn có thể khiến ứng dụng gặp *allocation stall* khi thu gom không kịp tốc độ cấp phát.

Bài này giúp bạn **đánh giá CPU, resident memory (RSS) và Java heap một cách định lượng dưới tải thực**, không suy ra từ một con số GC pause hay một screenshot của dashboard. Bạn sẽ:

1. Phân biệt **CPU time, CPU utilization, CPU quota và CPU throttling**.
2. Phân biệt **process RSS/Windows working set, virtual reserved memory, heap used/committed/max, live set và native/off-heap**.
3. Biết lấy dữ liệu từ **JMX/MXBeans, GC unified logging, JFR, OS/container và Native Memory Tracking (NMT)**.
4. Đánh giá **trade-off CPU ↔ memory ↔ latency ↔ throughput** của ZGC so với G1 bằng phép thử có đối chứng.
5. Tìm nguyên nhân khi **heap chưa đầy nhưng container OOM-kill**, hoặc GC pauses ngắn nhưng p99 tăng.
6. Chạy ví dụ **Java 17+** đã được kiểm thử, ghi CPU/heap định kỳ, đối chiếu RSS từ hệ điều hành và tạo GC log.

**Ghi chú về kiến thức hiện hành:** ZGC hiện nay là **generational ZGC**; JDK 21 giới thiệu chế độ generational (JEP 439), JDK 23 đặt chế độ này làm mặc định (JEP 474) và **JDK 24 loại bỏ non-generational ZGC (JEP 490)**. Vì vậy bài dùng `-XX:+UseZGC`, **không hướng dẫn dùng cờ `ZGenerational` cũ trên JDK 24+**. Những khuyến nghị đánh giá ở đây áp dụng cho ZGC hiện đại; thông tin Java 15 chỉ dùng để giải thích mốc phát hành.

## 1. Ba nhóm số đo trả lời ba câu hỏi khác nhau

| Nhóm | Câu hỏi | Không được đánh đồng |
| --- | --- | --- |
| **CPU** | Tiến trình Java tiêu thụ bao nhiêu thời gian xử lý? Có thiếu CPU cho GC concurrent không? | CPU process time khác CPU%, khác CPU quota |
| **RSS / Working Set** | Hệ điều hành đang báo bao nhiêu bộ nhớ vật lý cư trú cho tiến trình? | RSS khác heap used, khác memory của toàn container |
| **Java heap** | JVM đang quản lý bao nhiêu bộ nhớ object: used, committed, max? | Heap used khác live set chính xác; committed khác resident |

Các chỉ số phải được đo **cùng khoảng thời gian** với request rate, request p95/p99/p99.9, GC cycles, allocation stalls và memory pressure. Một số đo ở lúc không tải không đại diện cho trạng thái lúc đỉnh traffic.

### 1.1. Ví dụ giả định để nhận diện khác biệt

```text
-Xmx                         2048 MiB
Heap used                    810 MiB
Heap committed              1350 MiB
Process RSS                 1750 MiB
Container memory usage      1950 MiB
Virtual memory reserved    lớn hơn nhiều
```

Các giá trị trên **chỉ minh họa**, không phải kết quả thực nghiệm. Không kết luận “native memory = 1750 - 810 = 940 MiB”: RSS chứa nhiều thành phần và mapping có cách kế toán khác nhau. Không kết luận “heap đang leak” chỉ vì RSS cao hơn heap used.

**Quy tắc:** trước khi so sánh hai dashboard, ghi rõ **đơn vị (bytes/KiB/MiB), phạm vi (process/container/host), timestamp và định nghĩa metric**.

## 2. CPU: process time khác tỷ lệ sử dụng CPU

### 2.1. Process CPU time là tổng của các luồng

Trên HotSpot/OpenJDK, API quản lý công khai của JDK:

```java
var bean = java.lang.management.ManagementFactory
        .getOperatingSystemMXBean();

if (bean instanceof com.sun.management.OperatingSystemMXBean extended) {
    long cpuNanos = extended.getProcessCpuTime();
    // Giá trị >= 0 là tổng CPU nanoseconds; -1 nếu không có dữ liệu.
}
```

`com.sun.management.OperatingSystemMXBean` là **JDK Management API có tài liệu**, không phải class implementation nội bộ `sun.*`. Nhưng nó là phần mở rộng JDK, **không bắt buộc trên mọi JVM Java SE**. Vì thế chương trình cần cho phép trạng thái unavailable/`NA`. API chuẩn `ProcessHandle.Info.totalCpuDuration()` cũng trả `Optional<Duration>`, không nên mặc định giá trị luôn có.

### 2.2. Đổi CPU time thành số core tương đương

Lấy mẫu đầu và cuối trong cùng cửa sổ:

```text
deltaCpuNs  = processCpuNs(t2) - processCpuNs(t1)
deltaWallNs = monotonicTimeNs(t2) - monotonicTimeNs(t1)

cpuCoreEquivalents = deltaCpuNs / deltaWallNs
percentOfOneCore   = 100 * cpuCoreEquivalents
```

Ví dụ: trong một giây thời gian thực, các thread của JVM tiêu thụ tổng cộng **2,4 giây CPU** ⇒ khoảng **2,4 core tương đương**, hay **240% của một core**. Điều đó không có nghĩa “240% toàn máy”.

Một số dashboard chuẩn hóa CPU% theo **tất cả core host**, một số theo **một core** hoặc **quota**; đừng so hai giá trị % khác cách tính như thể chúng đồng nhất.

### 2.3. CPU time không tự chỉ ra CPU của ZGC

Process CPU time bao gồm mã Java application, ZGC worker threads, JIT, compiler, runtime threads, native work. Chỉ từ process CPU time không thể tính **chính xác CPU riêng của ZGC**.

Muốn phân tích overhead GC:

- So sánh **cùng workload, cùng JDK, CPU quota, heap và host** giữa ZGC với collector khác.
- Dùng **GC logs/JFR/profiler** để xem các pha concurrent/GC activity trùng với thời gian CPU cao.
- Kiểm tra **throughput và p99** bên cạnh CPU.
- Nếu container bị quota giới hạn, xem **CPU throttling**. CPU time có thể thấp **vì tiến trình không được chạy**, không phải vì hệ thống có nhiều CPU rảnh.

### 2.4. CPU throttling tác động tới concurrent GC

Trong container, `cpu.max` (cgroup v2) biểu diễn quota/period; `cpu.stat` có những số như `nr_throttled` và `throttled_usec` tùy OS/cgroup. Nếu GC concurrent thiếu CPU do throttling, nó có thể thu gom chậm, làm **heap headroom giảm** và tăng allocation stalls dù các STW pause riêng lẻ vẫn ngắn.

Câu hỏi cần điều tra là: “GC có cơ hội dùng CPU không, và workload có còn đủ CPU budget để xử lý request?”

## 3. Heap: used, committed, max và live set

Trong API chuẩn `java.lang.management.MemoryMXBean`:

```java
java.lang.management.MemoryUsage usage =
        java.lang.management.ManagementFactory
                .getMemoryMXBean().getHeapMemoryUsage();

long used = usage.getUsed();
long committed = usage.getCommitted();
long max = usage.getMax();
```

Mỗi lần gọi là **snapshot tại một thời điểm**, không phải báo cáo chính xác “bao nhiêu object sống sau GC”.

| Giá trị | Ý nghĩa | Lưu ý khi dùng ZGC |
| --- | --- | --- |
| `used` | Dung lượng heap JVM ghi nhận đang dùng | Tăng/giảm cùng cấp phát và GC; không phải live set chính xác ở mọi thời điểm |
| `committed` | Heap JVM đã commit để sử dụng | Không đồng nghĩa toàn bộ committed đã resident trong RAM |
| `max` | Giới hạn heap tối đa nếu biết, thường gắn `-Xmx` | Không phải RSS hay container memory limit |
| `init` | Dung lượng heap ban đầu | Không phải số trang resident của tiến trình lúc startup |

Ở cấu hình biết max, thường có **`0 <= used <= committed <= max`**. Trong một số memory pool/JVM, `max=-1` có nghĩa không xác định; **đừng viết chung một assertion “max > 0” cho mọi collector** mà không kiểm tra ngữ cảnh. Demo ở dưới có `-Xmx128m` nên kiểm tra max rõ ràng.

### 3.1. Live set và object churn

- **Live set:** dữ liệu vẫn reachable theo phân tích của GC.
- **Allocated bytes:** tổng byte được cấp phát theo thời gian, có thể lớn hơn live set rất nhiều.
- **Object churn:** nhiều object nhỏ được tạo rồi chết nhanh, phổ biến ở request processing.
- **Used heap:** trạng thái ở một thời điểm, có thể chứa object chết chưa được reclaim.

Một service có 500 MiB live set nhưng tạo hàng GB object tạm thời mỗi phút vẫn cần collector làm việc liên tục. Không thể đọc `heap used = 600 MiB` tại một giây bất kỳ rồi suy ra allocation rate hoặc chi phí GC.

### 3.2. Headroom quan trọng với concurrent GC

ZGC chạy concurrent với application, nghĩa là Java code **vẫn cấp phát trong khi collector đang làm việc**. Heap phải có khoảng trống cho đối tượng sống, allocation mới, quá trình xử lý/di chuyển và biến động tải.

Nếu heap dùng gần tới `-Xmx`, hoặc tốc độ cấp phát nhanh hơn khả năng thu gom, application có thể gặp **allocation stall** hoặc `OutOfMemoryError`. Một collector có GC pause thấp không xóa bỏ điều kiện vật lý là **phải còn memory capacity**.

Đánh giá bằng:

1. Used/committed/max theo thời gian.
2. Tốc độ cấp phát và chu kỳ GC.
3. Thời gian các pha concurrent so với lượng work.
4. Allocation stalls và tail latency.
5. Live set trend khi traffic ổn định và sau các GC cycle.

### 3.3. Xmx, Xms và SoftMaxHeapSize

Ví dụ cú pháp:

```bash
java -XX:+UseZGC -Xms512m -Xmx2g -XX:SoftMaxHeapSize=1536m -jar service.jar
```

- `-Xmx2g` giới hạn **Java heap**, không giới hạn toàn tiến trình.
- `-Xms512m` cấu hình heap ban đầu/tối thiểu.
- `SoftMaxHeapSize=1536m` là **mục tiêu mềm**, ZGC có thể vượt nếu cần tới giới hạn `-Xmx` để tránh stalls.

Các số này chỉ minh họa. Tuning phải dựa trên live set, allocation rate, CPU quota, memory footprint và giới hạn container của workload thật.

ZGC có cơ chế **uncommit** heap không dùng theo điều kiện và cấu hình. Nếu `Xms=Xmx` thì không có khoảng để co heap dưới minimum. Đừng yêu cầu RSS phải giảm **ngay lập tức** sau một chu kỳ GC: việc uncommit/physical pages còn liên quan OS, lịch GC và memory behavior.

## 4. RSS, working set và bộ nhớ container

### 4.1. RSS là chỉ số của hệ điều hành

**Resident Set Size (RSS)** thể hiện số trang resident gắn với một tiến trình theo định nghĩa/cách kế toán của OS. Nó có thể bao gồm một phần Java heap, metaspace, code cache, thread stacks, direct buffers, vùng native và thư viện/mappings.

Nó **không bằng** `heapUsed`, `heapCommitted` hay `-Xmx`. Các vùng địa chỉ ảo chỉ **reserved** không đồng nghĩa đã dùng RAM vật lý.

Với các hệ thống có nhiều mapping của cùng một physical region, shared libraries và cách kế toán khác nhau, việc cộng/trừ các con số một cách cơ học dễ sai. **Không dùng `RSS - heapUsed` như phép đo “native leak” chính xác.**

### 4.2. Linux

Với PID của JVM:

```bash
ps -o pid=,etime=,%cpu=,rss=,vsz= -p "$pid"
grep -E '^(VmRSS|VmSize|RssAnon|RssFile|RssShmem):' "/proc/$pid/status"
```

- `rss` trong `ps` trên Linux thường là **KiB**.
- `vsz` là virtual memory size, **không phải** RAM resident.
- `VmRSS` từ `/proc/PID/status` báo resident theo nguồn của kernel; `smaps_rollup` có thể giúp xem RSS/PSS/shared/private chi tiết hơn nếu được quyền.
- `%CPU` từ `ps` có ý nghĩa/cửa sổ đo riêng; không nhầm với công thức core-equivalent đo trên khoảng chính xác của Java.

### 4.3. Windows

PowerShell:

```powershell
$javaPid = 12345  # Thay bằng PID của JVM thật.
Get-Process -Id $javaPid |
    Select-Object Id, CPU, WorkingSet64, PrivateMemorySize64
```

- `WorkingSet64`: số byte working set vật lý theo Windows, **gần với resident memory** nhưng không có nghĩa bằng tuyệt đối RSS Linux.
- `CPU`: tổng số giây CPU time tích lũy, **không phải phần trăm hiện tại**.
- `PrivateMemorySize64`: chỉ số private memory theo Windows, không phải heap used.

Khi so sánh giữa Windows và Linux, ghi rõ tên metric nguồn thay vì dùng nhãn “RSS” chung nếu không cùng định nghĩa.

### 4.4. Docker / Kubernetes / cgroup

Ví dụ:

```bash
docker stats --no-stream <container-name-or-id>
```

Với cgroup v2, trong container/cgroup phù hợp:

```bash
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/cpu.max
cat /sys/fs/cgroup/cpu.stat
```

**Container memory usage khác process RSS**: số liệu cgroup có thể gồm page cache, các tiến trình khác và cách điều chỉnh working set của monitoring agent. Không dùng các giá trị của container cộng với RSS của process như những phần bộ nhớ độc lập.

CPU quota cũng thay đổi cách giải thích CPU%: một process dùng 0,8 core khi được cấp quota 1 core có thể đã gần giới hạn, dù host có 32 core.

### 4.5. Khi container OOM-kill trước Java OutOfMemoryError

Nếu `-Xmx` gần bằng container memory limit, JVM còn tiêu thụ native memory ngoài heap (thread stacks, metaspace, code cache, direct/mapped buffers, GC/JIT, libraries). Cgroup có thể vượt hạn mức và **OOM-kill tiến trình** dù heap used chưa đạt Xmx. Khi đó không nhất thiết thấy Java `OutOfMemoryError`.

Cần xem event/container restart reason, `memory.current/max`, process RSS/working set và NMT nếu cần. Giảm Xmx hoặc native footprint theo nguyên nhân; **để headroom cho toàn tiến trình**.

## 5. Native Memory Tracking: nguồn chẩn đoán, không phải RSS

HotSpot cung cấp **Native Memory Tracking (NMT)** để phân loại cấp phát JVM-native:

```bash
java -XX:+UseZGC -XX:NativeMemoryTracking=summary \
  -Xms512m -Xmx2g -jar service.jar
```

Khi JVM đang chạy, nếu công cụ attach và quyền phù hợp:

```bash
jcmd <pid> VM.native_memory summary scale=MB
```

Muốn so sự thay đổi (khi NMT được bật và lệnh hỗ trợ):

```bash
jcmd <pid> VM.native_memory baseline
jcmd <pid> VM.native_memory summary.diff scale=MB
```

**Phân biệt:**

- NMT `reserved` là địa chỉ ảo dự trữ, **không phải RSS**.
- NMT `committed` là memory commitment được theo dõi, cũng **không trực tiếp bằng resident pages**.
- NMT có **overhead** và không ghi nhận được mọi malloc/native allocation nằm ngoài phần JVM theo dõi.
- Thông tin NMT giúp khoanh vùng Thread, Class/Metaspace, Code, GC, Internal... nhưng nên đối chiếu cùng RSS, heap và thời gian.
- `jcmd` có thể bị giới hạn do quyền, container namespace, JVM attach hoặc cách deploy; lỗi attach không tự chứng minh chương trình không dùng native memory.

NMT phù hợp khi RSS cao nhưng heap used không giải thích được; **không thay thế việc lấy resident memory từ OS**.

## 6. Bài thực hành: chương trình Java đo CPU time và heap

Chương trình dưới đây hoạt động trên **JDK 17+ HotSpot/OpenJDK có ZGC**. Nó tạo workload cấp phát có giữ lại một số object để tạo áp lực heap vừa phải, xuất:

- **stdout**: các assertion `PASS` để kiểm thử mã;
- **stderr**: PID và các mẫu CPU/heap mỗi giây (dạng CSV có một dòng metadata trước header);
- **GC log**: pause/concurrent events từ JVM khi bật `-Xlog`;
- **RSS**: phải đo bên ngoài bằng OS, không được suy ra từ heap API.

Đây là một **demo instrumentation**, **không phải benchmark workload production**. Tham số thời lượng từ 2 tới 120 giây; ví dụ dùng 3 giây để có kết quả test cố định. Khi đánh giá service thực, dùng workload, tracing và metric của service thật.

### 6.1. Mã nguồn hoàn chỉnh

Tạo tệp **`ZgcResourceLoadDemo.java`** bằng UTF-8:

```java
import com.sun.management.OperatingSystemMXBean;
import java.lang.management.GarbageCollectorMXBean;
import java.lang.management.ManagementFactory;
import java.lang.management.MemoryUsage;
import java.util.ArrayDeque;
import java.util.List;
import java.util.Locale;

public final class ZgcResourceLoadDemo {
    private static void check(String label, boolean success) {
        if (!success) {
            throw new AssertionError(label + " FAILED");
        }
        System.out.println(label + "=PASS");
    }

    private static long processCpuNanos() {
        var bean = ManagementFactory.getOperatingSystemMXBean();
        if (bean instanceof OperatingSystemMXBean extended) {
            return extended.getProcessCpuTime();
        }
        return -1; // May be unavailable on another JVM/OS.
    }

    private static double mib(long bytes) {
        return bytes / 1048576.0;
    }

    public static void main(String[] args) throws Exception {
        int seconds = args.length == 0 ? 4 : Integer.parseInt(args[0]);
        if (seconds < 2 || seconds > 120) {
            throw new IllegalArgumentException("Seconds must be 2..120");
        }

        List<GarbageCollectorMXBean> collectors =
                ManagementFactory.getGarbageCollectorMXBeans();
        boolean zgc = collectors.stream().anyMatch(b -> {
            String name = b.getName().toLowerCase(Locale.ROOT);
            return name.contains("zgc") || name.contains("z garbage");
        });
        check("zgcSelected", zgc);

        long maxHeap = ManagementFactory.getMemoryMXBean()
                .getHeapMemoryUsage().getMax();
        check("maxHeapConfigured",
                maxHeap > 0 && maxHeap <= 128L * 1024 * 1024);

        System.err.println("pid=" + ProcessHandle.current().pid());
        System.err.println(
                "sample,wallMs,cpuCoreEquivalents,heapUsedMiB,"
                + "heapCommittedMiB,heapMaxMiB,retainedObjects");

        ArrayDeque<byte[]> retained = new ArrayDeque<>();
        long checksum = 0L;
        long start = System.nanoTime();
        long previousWall = start;
        long previousCpu = processCpuNanos();
        boolean cpuSamplesConsistent = true;
        boolean heapSamplesConsistent = true;
        int samples = 0;

        while (samples < seconds) {
            long deadline = start + (samples + 1L) * 1_000_000_000L;
            while (System.nanoTime() < deadline) {
                for (int i = 0; i < 384; i++) {
                    byte[] block = new byte[4096];
                    block[0] = (byte) (i + samples);
                    checksum += Byte.toUnsignedInt(block[0]);
                    if ((i & 15) == 0) {
                        retained.addLast(block);
                    }
                }
                while (retained.size() > 512) {
                    retained.removeFirst();
                }
                Thread.sleep(12);
            }

            long wall = System.nanoTime();
            long cpu = processCpuNanos();
            String cpuCoreEquivalents = "NA";
            if (previousCpu >= 0 && cpu >= 0) {
                cpuSamplesConsistent &= cpu >= previousCpu;
                if (wall > previousWall) {
                    double cores = (double) (cpu - previousCpu)
                            / (wall - previousWall);
                    cpuCoreEquivalents = String.format(Locale.ROOT,
                            "%.3f", cores);
                }
            }

            MemoryUsage heap = ManagementFactory.getMemoryMXBean()
                    .getHeapMemoryUsage();
            heapSamplesConsistent &=
                    heap.getUsed() >= 0
                    && heap.getUsed() <= heap.getCommitted()
                    && heap.getCommitted() <= heap.getMax();

            System.err.printf(Locale.ROOT,
                    "%d,%d,%s,%.2f,%.2f,%.2f,%d%n",
                    samples + 1, (wall - start) / 1_000_000L,
                    cpuCoreEquivalents, mib(heap.getUsed()),
                    mib(heap.getCommitted()), mib(heap.getMax()),
                    retained.size());

            previousWall = wall;
            previousCpu = cpu;
            samples++;
        }

        check("cpuSamplesConsistent", cpuSamplesConsistent);
        check("heapSamplesConsistent", heapSamplesConsistent);
        check("allocationsProcessed", checksum > 0);
        check("liveObjectsRetained", !retained.isEmpty());
        check("expectedSamples", samples == seconds);
        System.out.println("samples=" + samples);
        System.out.println("done");
    }
}
```

**Vì sao ví dụ dùng `com.sun.management`?** Đây là extension công khai được hỗ trợ trong các JDK tương ứng, cho phép lấy **process CPU time**. Chương trình không phản chiếu dữ liệu heap hay class JDK nội bộ. Nếu một JVM không hỗ trợ MXBean mở rộng hoặc counter trả `-1`, metric CPU in là `NA`; đừng thay bằng 0 vì 0 ngụ ý tiến trình không tiêu thụ CPU.

### 6.2. Biên dịch và chạy

Với Bash:

```bash
javac --release 17 -encoding UTF-8 ZgcResourceLoadDemo.java

java -XX:+UseZGC -Xms64m -Xmx128m \
  '-Xlog:gc*,safepoint=info:file=zgc.log:uptime,level,tags:filecount=3,filesize=10m' \
  ZgcResourceLoadDemo 3 > app.out 2> metrics.csv
```

Trên Windows PowerShell, dùng một dòng cho lệnh Java:

```powershell
javac --release 17 -encoding UTF-8 ZgcResourceLoadDemo.java

java -XX:+UseZGC -Xms64m -Xmx128m '-Xlog:gc*,safepoint=info:file=zgc.log:uptime,level,tags:filecount=3,filesize=10m' ZgcResourceLoadDemo 3 > app.out 2> metrics.csv
```

Tệp tạo ra: `app.out` (stdout của Java), `metrics.csv` (stderr chứa PID + ba mẫu metrics), `zgc.log` (GC/safepoint log). Với PowerShell có cấu hình biến `ErrorActionPreference='Stop'`, thông điệp ghi qua stderr có thể bị shell coi là NativeCommandError; cách chạy trong shell cần tách stderr phù hợp hoặc chạy tiến trình với `Start-Process -RedirectStandardError`. Đó là **cách PowerShell xử lý stderr**, không phải lỗi assertion Java.

**Stdout chính xác khi truyền tham số `3`:**

```text
zgcSelected=PASS
maxHeapConfigured=PASS
cpuSamplesConsistent=PASS
heapSamplesConsistent=PASS
allocationsProcessed=PASS
liveObjectsRetained=PASS
expectedSamples=PASS
samples=3
done
```

**Stderr dạng mẫu; mọi số thực là biến theo máy/chạy:**

```text
pid=<actual-pid>
sample,wallMs,cpuCoreEquivalents,heapUsedMiB,heapCommittedMiB,heapMaxMiB,retainedObjects
1,<elapsed>,<cores-or-NA>,<used>,<committed>,<max>,<count>
2,<elapsed>,<cores-or-NA>,<used>,<committed>,<max>,<count>
3,<elapsed>,<cores-or-NA>,<used>,<committed>,<max>,<count>
```

Dấu ngoặc góc chỉ là **ký hiệu minh họa**, không phải ký tự thực in ra. Đặc biệt, tệp `metrics.csv` có **một dòng PID nằm trước CSV header**; khi đưa vào phần mềm phân tích CSV, bỏ dòng metadata này hoặc xử lý riêng trước khi parse.

### 6.3. Ý nghĩa kết quả

| Assertion | Điều chứng minh |
| --- | --- |
| `zgcSelected=PASS` | Trên HotSpot thử nghiệm, GC MXBeans cho biết ZGC đã được chọn; tên MXBean không phải hợp đồng cố định cho mọi vendor |
| `maxHeapConfigured=PASS` | Heap max do JVM báo nằm trong giới hạn 128 MiB đã cấu hình; **không** khẳng định process RSS dưới 128 MiB |
| `cpuSamplesConsistent=PASS` | CPU counter không đi lùi nếu có giá trị; unavailable được giữ `NA` |
| `heapSamplesConsistent=PASS` | Heap snapshots thỏa quan hệ used/committed/max phù hợp với cấu hình bài |
| `allocationsProcessed=PASS` | Workload thực sự tạo/xử lý mảng, có cập nhật checksum |
| `liveObjectsRetained=PASS` | Một phần object vẫn reachable ở cuối |
| `expectedSamples=PASS` | Chương trình lấy đủ số mẫu yêu cầu |
| `samples=3` | Khớp số giây chạy mẫu trong lệnh |

**Không coi PASS là bằng chứng đạt SLO.** Ví dụ chỉ chứng minh phương pháp đo hoạt động. Độ trễ nghiệp vụ phải lấy từ request metrics/tracing của hệ thống thật.

### 6.4. Lấy RSS trong lúc Java còn chạy

Trên Linux, chạy thời lượng dài hơn để có thể lấy mẫu OS:

```bash
java -XX:+UseZGC -Xms64m -Xmx128m \
  '-Xlog:gc*,safepoint=info:file=zgc.log:uptime,level,tags:filecount=3,filesize=10m' \
  ZgcResourceLoadDemo 30 > app.out 2> metrics.csv &
pid=$!

while kill -0 "$pid" 2>/dev/null; do
  ps -o pid=,etime=,%cpu=,rss=,vsz= -p "$pid"
  sleep 1
done
wait "$pid"
```

Trên Windows dùng terminal riêng đọc `pid=...` trong `metrics.csv` và lấy `Get-Process -Id $javaPid` như phần trên. Ghi nhận **thời điểm** mỗi mẫu RSS/working set để ghép với CPU/heap CSV và GC log. RSS Windows/Linux không được ghép thành một cột mà không ghi nhãn nguồn.

## 7. Đọc GC log song song với CPU/RSS/heap

Cấu hình:

```text
-Xlog:gc*,safepoint=info:file=zgc.log:uptime,level,tags:filecount=3,filesize=10m
```

Log có nhãn thời gian JVM uptime, log level/tag và các sự kiện GC/safepoint. Khi xem:

- Dòng **`Pause ...`** cho biết một pha dừng, không phải toàn bộ chu kỳ GC.
- Dòng **`Concurrent ...`** là công việc chạy đồng thời với ứng dụng.
- Dòng tóm tắt **Garbage Collection ...** có thể phản ánh **chu kỳ**; không được đồng nhất thời lượng cycle với **STW pause**.
- Dấu hiệu **Allocation Stall** cho thấy application phải đợi khi allocation/thu gom bị áp lực.
- Các thông tin heap/cycle giúp đối chiếu used/committed và tốc độ churn.
- Dòng safepoint có thể giúp phân biệt các nguyên nhân dừng khác ngoài GC.

**Không hardcode giá trị pause tính bằng ms** trong ví dụ hay log mong đợi: số pha GC, thời gian pause, lượng bộ nhớ và tần suất cycle thay đổi theo JDK, OS, CPU và workload.

## 8. Dùng JFR để giải thích nguyên nhân, không thay thế OS RSS

Có thể bật **Java Flight Recorder (JFR)** cho service trong phép thử:

```bash
java -XX:+UseZGC -Xms512m -Xmx2g \
  -XX:StartFlightRecording=filename=zgc-load.jfr,settings=profile,dumponexit=true \
  -jar service.jar
```

Sau load test, dùng **JDK Mission Control** hoặc công cụ JFR tương thích phân tích:

- CPU hotspots/threads.
- Object allocation và GC events.
- Thread states, locks, scheduling và safepoints.
- Thời gian GC pauses/cycles.
- Tương quan với request latency traces.

JFR hỗ trợ tìm **vì sao CPU/heap/latency thay đổi**, nhưng nó không phải là nguồn duy nhất/canonical cho process RSS. Nếu dùng JFR/NMT ở production, cần giới hạn overhead, lưu trữ và thông tin nhạy cảm trong recording.

## 9. Cách benchmark ZGC với tải thực

Để trả lời “ZGC có phù hợp workload này không?”, hãy thử trên **service thật** với ít nhất hai cấu hình collector.

### 9.1. Giữ nguyên điều kiện đối chứng

- Cùng **JDK vendor/build/release**, host, OS/kernel và container base image.
- Cùng CPU quota, memory limit và heap budget `-Xms/-Xmx`.
- Cùng dữ liệu, traffic rate/concurrency, payload sizes, burst pattern.
- Cùng thời lượng warm-up JIT, steady-state và số lần lặp.
- Cùng pipeline metrics/logging hoặc ghi rõ overhead của công cụ chẩn đoán.
- Đảm bảo không dùng cùng lúc hai GC options trong một JVM.

Ví dụ service thật:

```bash
java -XX:+UseG1GC -Xms512m -Xmx2g \
  '-Xlog:gc*,safepoint=info:file=g1.log:uptime,level,tags:filecount=3,filesize=10m' \
  -jar service.jar

java -XX:+UseZGC -Xms512m -Xmx2g \
  '-Xlog:gc*,safepoint=info:file=zgc.log:uptime,level,tags:filecount=3,filesize=10m' \
  -jar service.jar
```

**Không dùng chương trình demo ở phần 6 để benchmark G1 nguyên trạng**, vì chương trình có assertion chủ đích yêu cầu **ZGC được chọn**; nó sẽ báo FAIL nếu chạy G1. Benchmark G1/ZGC phải dùng cùng service thực hoặc chương trình đo đã thay assertion chọn collector cho phù hợp từng nhánh.

### 9.2. Bảng báo cáo kết quả nên có

| Loại chỉ số | Ghi lại |
| --- | --- |
| Tải | request rate mục tiêu/thực tế, concurrency, payload và traffic mix |
| Tail latency | p50, p95, **p99**, p99.9, max, error/timeout |
| CPU | Core-equivalent, peak/baseline, CPU quota, throttling |
| Heap | Used/committed/max, allocation rate, GC cycles, live-set trend |
| Resident memory | Process RSS/working set, container memory usage/peak |
| GC | STW pause percentiles/max, concurrent duration, allocation stalls |
| Native memory | NMT summary/diff, direct buffers, metaspace, threads khi cần |
| Stability | OOM, OOM-kill, restart, swap/page faults |
| Chi phí | CPU core-hours, RAM budget, throughput tại cùng SLO |

Chạy cả **steady-state** lẫn **burst và recovery**. Nếu kết quả chỉ tốt ở 30 giây đầu nhưng xấu sau một giờ, thử nghiệm chưa đại diện. Chọn collector theo **SLO và tổng chi phí** chứ không chỉ “ai có pause nhỏ hơn”.

## 10. Những tình huống cần phân tích

### 10.1. Heap used thấp, RSS cao

Có thể do heap committed/resident khác used, native memory, direct buffers, metaspace, stack, code cache, memory mappings hoặc sai số cách OS đếm. **Không vội kết luận native leak**. So RSS với NMT, heap committed, số thread, direct/mapped buffer và trend theo thời gian.

### 10.2. CPU tăng nhưng ZGC pause thấp

Concurrent GC cần CPU. Nếu p99 cải thiện mạnh trong khi CPU tăng hợp lý, trade-off có thể được chấp nhận. Nếu throughput tụt, CPU quota hết hoặc stalls tăng, phải điều tra workload, allocation rate, concurrency và JFR.

### 10.3. Heap tiến sát Xmx, xuất hiện allocation stall

Concurrent collector có thể không thu hồi kịp. Xem headroom, allocation rate, live set, CPU throttling; thử tăng Xmx **trong memory budget an toàn** hoặc giảm object churn. Đừng nghĩ giảm STW pause là đủ.

### 10.4. Container OOM-kill khi heap chưa chạm Xmx

Cgroup tính memory rộng hơn heap: native/off-heap, page cache, các process khác. Cần phân tích memory.current, process RSS và sự kiện kill; đừng chỉ tăng Xmx — tăng có thể làm sự cố nặng hơn.

### 10.5. CPU process thấp nhưng p99 tệ

Có thể nhiều thread đang chờ DB/network/locks hoặc bị CPU throttling. Process CPU thấp không đồng nghĩa có tài nguyên rảnh. Đọc cgroup `cpu.stat`, JFR thread states, request tracing và queueing.

### 10.6. RSS không giảm ngay khi traffic hạ

Heap committed và OS pages có thể chưa được uncommit, cache có thể còn sống, hoặc native allocator giữ vùng đã từng cấp. Quan sát dài hơn, xem used/committed/NMT cùng lúc. Không gọi `System.gc()` trong production chỉ để ép biểu đồ giảm nếu chưa có lý do và đánh giá tác dụng phụ.

## 13. Bài tập tự kiểm tra

**Câu 1.** Một JVM dùng 2,2 giây CPU time trong 1 giây wall time. Kết quả là bao nhiêu core tương đương?

**Đáp án:** 2,2 core equivalents, hoặc 220% của **một core**. Không mặc nhiên là 220% tổng host hay container.

**Câu 2.** ZGC log có chu kỳ concurrent kéo dài 180 ms nhưng các dòng Pause đều rất ngắn. Có thể báo STW pause 180 ms không?

**Đáp án:** Không. Duration của cả concurrent cycle không đồng nghĩa tổng STW pause.

**Câu 3.** `-Xmx2g`, heap used 900 MiB và RSS 1.8 GiB có chứng minh native leak 900 MiB không?

**Đáp án:** Không. Heap committed, native allocations, JIT/GC metadata, thread stacks, mappings và cách kế toán RSS đều ảnh hưởng. Cần thêm nguồn đo.

**Câu 4.** Container bị OOM-kill trong khi Java heap used mới 65% Xmx. Vì sao?

**Đáp án:** Container memory gồm nhiều vùng ngoài heap; memory limit áp cho toàn cgroup, không chỉ Java heap. Cần phân tích RSS, cgroup và native footprint.

**Câu 5.** Nếu CPU time thấp nhưng p99 cao, liệu còn có thể thiếu CPU không?

**Đáp án:** Có. CPU throttling/scheduling hoặc thread chờ lock/I/O không tích lũy nhiều CPU time. Kiểm tra quota/throttling và thread states.

**Câu 6.** JDK 25 có cần cấu hình `-XX:+ZGenerational` để dùng generational ZGC không?

**Đáp án:** Không. Từ JDK 24, non-generational ZGC đã bị loại; sử dụng `-XX:+UseZGC`.

**Câu 7.** Đầu ra của chương trình demo có 7 dòng PASS nhưng service thật p99 vẫn tăng. Đã chứng minh ZGC đạt yêu cầu chưa?

**Đáp án:** Chưa. Demo chỉ kiểm tra thu mẫu và ZGC đã chọn. Phải chạy workload thực, đo request latency, CPU, RSS, heap và stalls.

**Câu 8.** Vì sao không được cộng RSS với heap used để tính memory footprint JVM?

**Đáp án:** Heap resident đã nằm trong RSS (với cách kế toán OS). Cộng sẽ đếm trùng.

**Câu 9.** NMT báo reserved 4 GiB, committed 1 GiB. Có thể kết luận process dùng 4 GiB RAM không?

**Đáp án:** Không. Reserved là không gian địa chỉ ảo, không phải số trang resident. Cần process RSS/working set từ OS.

## Ghi nhớ

**Đánh giá ZGC dưới tải thực phải đặt CPU, RSS và heap cạnh nhau**, cùng timeline GC logs/JFR và request latency. ZGC giảm thời gian stop-the-world bằng công việc concurrent, nhưng **vẫn cần CPU và heap headroom**. Dùng CPU core-equivalent đúng đơn vị, process RSS/working set từ OS, heap used/committed/max từ JMX, NMT cho chẩn đoán native và cgroup metrics cho memory/CPU quota. Chỉ kết luận ZGC tốt hơn hoặc kém hơn collector khác **sau A/B workload thật**, với cùng budget, nhiều lần đo, steady-state lẫn peak. Trên JDK hiện đại, ZGC là **generational**, không sử dụng cấu hình non-generational đã lỗi thời.
