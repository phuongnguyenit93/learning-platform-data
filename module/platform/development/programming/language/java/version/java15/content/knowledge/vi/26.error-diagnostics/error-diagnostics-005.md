# Chẩn đoán class loading, bytecode và truy cập lookup trong Java

Khi Java gặp lỗi như **`ClassNotFoundException`, `NoClassDefFoundError`, `UnsupportedClassVersionError`, `VerifyError`, `IllegalAccessError` hoặc `IllegalAccessException` khi gọi `MethodHandles.Lookup`**, nguyên nhân **không nhất thiết là thiếu một file JAR**. Một tên lớp có thể được tìm thấy nhưng **không thể khởi tạo**, bytecode có thể bị từ chối khi **link/verify**, hai phiên bản thư viện có thể không tương thích, hoặc lớp nằm trong module/package mà lookup **không đủ quyền** để truy cập.

Bài này thuộc nhóm **Chẩn đoán lỗi**, module **Java 15**. Nó tập trung vào những cơ chế **vẫn được hỗ trợ trong Java hiện đại**: class loaders và class identity; các giai đoạn loading, linking, initialization; class-file version; công cụ `javap`/`jdeps`/`-Xlog`; quyền của `MethodHandles.Lookup`, nestmates và JPMS module boundaries; cùng **hidden classes** được thêm ở Java 15 theo **JEP 371**.

**Nguyên tắc quan trọng nhất:** phải biết lỗi phát sinh ở **giai đoạn nào** và bởi **thành phần nào** — compiler, class loader, JVM verifier/linker, static initializer hay access checker của Lookup. Hai exception có tên nghe giống nhau có thể cần **hai hướng khắc phục hoàn toàn khác nhau**.

## 1. Bản đồ một lớp đi từ file .class đến khi chạy

Lộ trình khái niệm:

```text
Mã nguồn .java
      |
      v
javac --release 17 ...      [biên dịch + kiểm tra ngôn ngữ]
      |
      v
Bytecode .class / JAR       [header, constant pool, methods, attributes]
      |
      v
ClassLoader / ModuleLayer   [tìm lớp, chọn loader và module]
      |
      v
LOADING                     [đọc bytes, JVM tạo Class]
      |
      v
LINKING
    |-- Verification          [bytecode có hợp lệ/type-safe?]
    |-- Preparation           [chuẩn bị static fields]
    |-- Resolution            [liên kết tham chiếu symbolic, có thể lazy]
      |
      v
INITIALIZATION              [chạy <clinit> khi cần]
      |
      v
Thực thi và resolve member [field/method call, reflection, MethodHandle]
      |
      v
Access checks               [visibility, nest, module, lookup modes]
```

Sơ đồ không có nghĩa tất cả resolution **luôn** xảy ra trước khi init hoặc mọi class được eager-load ngay khi JVM khởi động. JVM có thể **lazy load/lazy resolve** tùy thời điểm code cần sử dụng kiểu/method. Nhưng việc tách **loading / linking / initialization** là thiết yếu khi phân tích stack trace.

| Giai đoạn | Các dạng triệu chứng | Hướng kiểm tra đầu tiên |
| --- | --- | --- |
| Tìm định nghĩa lớp | `ClassNotFoundException`, `NoClassDefFoundError` | Classpath, module path, JAR contents, tên binary, loader |
| Đọc định dạng class-file | `ClassFormatError`, `UnsupportedClassVersionError` | Bytes gốc, JDK build, major/minor, JAR bị hỏng |
| Bytecode verification | `VerifyError` | Bytecode, stack map frames, generator/transformer, Java target |
| Resolution/linking | `NoSuchMethodError`, `NoSuchFieldError`, `IncompatibleClassChangeError`, `IllegalAccessError` | API binary compatibility, runtime dependency version, member visibility |
| Static initialization | `ExceptionInInitializerError`, sau đó có thể `NoClassDefFoundError` | Root cause trong static initializer, cấu hình/side effects |
| Reflection / method handle access | `IllegalAccessException`, `InaccessibleObjectException`, `NoSuchMethodException` | Lookup class/modes, JPMS `exports`/`opens`, signature |
| Truyền/cast giữa các lớp | `ClassCastException` với tên tưởng như giống nhau | **Định danh class = binary name + defining loader** |

**Không bắt toàn bộ `LinkageError` rồi bỏ qua để ứng dụng “chạy tiếp”**. Các lỗi này thường cho thấy môi trường runtime, dependency graph hoặc generated bytecode có vấn đề. Ở tầng framework có thể catch có chủ đích để báo chẩn đoán, nhưng không coi đó là một lỗi nghiệp vụ bình thường.

## 2. ClassNotFoundException và NoClassDefFoundError khác nhau thế nào?

### ClassNotFoundException: yêu cầu tìm lớp theo tên nhưng không có định nghĩa

Ví dụ:

```java
Class.forName("com.example.MissingPlugin");
```

`Class.forName(...)` có thể ném **checked exception `ClassNotFoundException`** nếu loader không tìm được class definition cho tên đã yêu cầu. Các phương thức `ClassLoader.loadClass(...)` cũng báo lỗi này khi không tìm được lớp.

Nên kiểm tra:

- **Tên binary chính xác** (`com.example.Foo`, không phải path `com/example/Foo.class`); inner class có dấu `$` trong binary name.
- File `.class` có thực sự nằm trong JAR hoặc output directory đang chạy?
- `-cp`/`--class-path` và `--module-path` có trỏ đúng nơi không?
- Runtime đang dùng **loader nào**, loader đó có nhìn thấy JAR/module của dependency không?
- Ứng dụng có yêu cầu một **class ẩn/hidden class** bằng tên thường không? Hidden classes không tìm được theo kiểu tên binary.
- Dependency chỉ có mặt ở **compile time** nhưng bị thiếu ở runtime, hoặc có scope `provided` sai?

### NoClassDefFoundError: JVM/linkage không còn có định nghĩa dùng được

`NoClassDefFoundError` là **`Error` thuộc nhánh `LinkageError`**, thường phát sinh khi code đã compile có tham chiếu tới một lớp nhưng JVM **không thể tải định nghĩa lớp đó khi cần**. Ví dụ bỏ sót dependency trên runtime classpath.

Tuy nhiên, **đây còn là dấu hiệu điển hình sau một static initializer đã thất bại**: lần dùng đầu có thể nhận `ExceptionInInitializerError`; những lần dùng sau class đã ở trạng thái **erroneous** và có thể nhận `NoClassDefFoundError: Could not initialize class ...`.

**Vì vậy không suy ra “thiếu JAR” chỉ từ tên `NoClassDefFoundError`.** Hãy kiểm tra toàn bộ exception chain, đặc biệt lỗi **sớm nhất** trong log và thông báo `Could not initialize class`.

| Tiêu chí | `ClassNotFoundException` | `NoClassDefFoundError` |
| --- | --- | --- |
| Loại | Checked `Exception` | `LinkageError` |
| Tình huống hay gặp | Dùng API tìm lớp theo tên chuỗi, loader không tìm thấy | JVM cần một lớp đã được tham chiếu nhưng không có definition dùng được |
| Có thể liên quan initialization? | API `forName` cũng có thể trigger init với overload phù hợp, nhưng exception này nói về việc **không tìm thấy** | **Có**: sau khi class initialization thất bại |
| Debug ưu tiên | Tên/loader/classpath/module path | Lỗi đầu tiên, cause, dependency runtime, init failure |
| Cách khắc phục | Đưa đúng lớp vào phạm vi loader hoặc sửa tên/cấu hình | Tìm root cause chính xác; không tự thêm JAR nếu lớp lỗi do initializer |

### Một static initializer chỉ thất bại một lần đầu

```java
static final class FailingInit {
    static final int VALUE = fail();

    private static int fail() {
        throw new IllegalStateException("initializer failed");
    }
}
```

Đây là **đoạn minh họa nằm trong một lớp bao ngoài**. Biến `VALUE` không phải compile-time constant vì nó được khởi tạo bằng lời gọi method. Lần đầu truy cập có thể nhận `ExceptionInInitializerError`; lần tiếp theo cùng defining loader có thể nhận `NoClassDefFoundError` do class không còn khởi tạo được. Chương trình đầy đủ ở mục 8 minh họa điều đó bằng output đã kiểm chứng.

**Không thử khởi tạo lại liên tục một class ở trạng thái erroneous**; cần sửa nguyên nhân trong static initializer và khởi động/lifecycle triển khai lại đúng cách.

## 3. Class identity: cùng tên nhưng khác ClassLoader

Trong JVM, **cùng binary name chưa đủ để xác định cùng runtime class**. Class identity xét **binary name và defining class loader**. Hai loaders khác nhau có thể định nghĩa hai `Class` khác nhau với cùng tên. Một loader có thể ủy quyền tải lớp tới parent; vì vậy phải phân biệt **initiating loader** và **defining loader** khi đọc log chuyên sâu.

Các hệ thống dễ gặp vấn đề này:

- Application servers, plugin containers, modular runtimes.
- Hot-reload hoặc class redefinition trong development.
- Multi-classloader frameworks và custom class loaders.
- Shaded/duplicated dependencies.
- Hệ thống nạp các version thư viện khác nhau vào những loader scopes.

Dấu hiệu điển hình:

```text
ClassCastException: class com.example.Order cannot be cast to class com.example.Order
(... loaded by distinct class loaders ...)
```

Dù tên kiểu giống nhau, **hai Class objects có thể khác nhau**. Không sửa bằng cách ép cast nhiều lần. Cần kiểm tra **loader origin và dependency boundary**.

### Log các thông tin hữu ích

```java
Class<?> type = obj.getClass();
System.out.println("type=" + type.getName());
System.out.println("loader=" + type.getClassLoader());
System.out.println("module=" + type.getModule());
System.out.println("codeSource=" + (
        type.getProtectionDomain() == null ? null
        : type.getProtectionDomain().getCodeSource()));
```

Đây là **snippet minh họa** (giả định có `obj`); code source **có thể null**, nhất là với một số class do JVM/protocol đặc biệt tạo. Đừng dựa vào `CodeSource` như một nguồn đáng tin tuyệt đối về provenance, và đừng log những đường dẫn chứa bí mật hoặc token.

Dùng `==` để kiểm tra hai Class objects có thực sự cùng định danh:

```java
System.out.println(typeA == typeB);
```

Đó là kiểm tra identity, khác `typeA.getName().equals(typeB.getName())`.

## 4. Classpath, module path và JAR contents

Trước khi sửa mã Java, kiểm tra **artifact thực tế đang chạy**, không chỉ IDE hoặc thư mục build.

### Các lệnh hữu ích

```bash
java -version
javac -version

jar --list --file app.jar
jar --describe-module --file lib.jar
jdeps -verbose:class app.jar

javap -v -p -classpath out com.example.MyClass
javap -c -p -classpath out com.example.MyClass
```

**Đây là những lệnh chẩn đoán minh họa**: `app.jar`, `lib.jar`, `out` và `com.example.MyClass` phải được thay bằng giá trị thực tế; `jdeps` có thể cần thêm `--class-path`/`--module-path` nếu dependency không nằm trong phạm vi mặc định.

Chúng giúp trả lời:

- `jar --list`: JAR có chứa `com/example/MyClass.class` thật không?
- `jar --describe-module`: file có module descriptor hay được nhận diện thành automatic module?
- `jdeps`: class/JAR tham chiếu những package/module nào, có dependency bị thiếu?
- `javap -v -p`: class-file major/minor, constant pool, flags, methods/fields, `NestHost`/`NestMembers`, `Module` attributes nếu hiện diện.
- `javap -c`: xem mã bytecode của method; hữu ích khi gặp `VerifyError`, `NoSuchMethodError`, `IllegalAccessError`.

### Classpath khác module path

| Khía cạnh | Classpath | Module path |
| --- | --- | --- |
| Không gian tên | Thường vào **unnamed module** | Named modules (explicit hoặc automatic) |
| Kiểm soát visibility | Chủ yếu Java access rules và class loader | Thêm JPMS `requires`, `exports`, `opens` và resolution graph |
| Chẩn đoán | `-cp`, JAR contents, class loader | `--module-path`, `--show-module-resolution`, `module-info.class`, `ModuleLayer` |
| Deep reflection / private lookup | Có thể hoạt động giữa lớp cùng unnamed module khi có quyền phù hợp | Phụ thuộc package có **opens** tới module caller và quan hệ reads |

**Không giả định đặt JAR lên module path nghĩa là mọi package của nó đều accessible**. Với explicit named module, chỉ các package được export/open phù hợp mới dùng được từ ngoài. **Không tự thêm `--add-opens` cho mọi package của JDK** để “chữa” tất cả lỗi.

### Multi-release JAR

Một JAR có thể chứa `META-INF/versions/<version>/...` cùng manifest `Multi-Release: true`; runtime mới có thể chọn class bytes theo version phù hợp. Khi nghi ngờ **chạy khác version JDK cho kết quả khác**, kiểm tra những class entries đó và manifest:

```bash
jar --list --file library.jar
javap --multi-release 17 -v -classpath library.jar com.example.Feature
```

Với tooling/multi-release mode, đảm bảo lệnh và JDK đang chạy hỗ trợ tùy chọn được dùng. Không kết luận “đã kiểm tra đúng bytecode runtime” nếu chỉ đọc file base entry mà JVM thực tế chọn một entry trong `META-INF/versions`.

## 5. Java class-file format, magic và major version

Một file `.class` hợp lệ bắt đầu bằng **magic number `CA FE BA BE`**. Sau đó là **minor** và **major version** của class-file format. Nếu JVM không hỗ trợ major/minor, có thể ném **`UnsupportedClassVersionError`**.

Các mốc vẫn hữu ích khi chẩn đoán:

| Java release | Major version của class file |
| --- | ---: |
| Java 11 | 55 |
| **Java 15** | **59** |
| Java 17 | 61 |
| Java 21 | 65 |
| Java 24 | 68 |
| Java 25 | 69 |
| Java 26 | 70 |

Bảng trên theo **Java Virtual Machine Specification, Java SE 26**. Vì vậy nếu một library được compile thành major **65** (Java 21), runtime Java 17 (hỗ trợ tối đa major 61) **không thể load** class đó. Nếu dự án cần chạy trên Java 17, hãy **compile cho target phù hợp**, ví dụ:

```bash
javac --release 17 Example.java
```

`--release` yêu cầu compiler tạo class files và giới hạn API tới platform target đã chọn (khi compiler hỗ trợ release đó). **Đừng chỉ thay 2 byte major version trong class file production**; class có thể còn sử dụng bytecode semantics và API không tồn tại trên runtime cũ.

### Minor version 65535 và preview feature

Với các release Java mới, class file có minor version **65535** có thể chỉ ra sự phụ thuộc vào **preview feature** của release tương ứng. Những class files đó có giới hạn runtime nghiêm ngặt: việc bật `--enable-preview` không phải cách chạy tùy ý preview classfile từ **release khác**.

Khi gặp lỗi version, hãy kiểm tra **cả major và minor**, `java -version`, compiler build flags và runtime thực tế của container. Java 26 hiện hỗ trợ major tới **70**, nhưng runtime cũ có giới hạn thấp hơn.

### ClassFormatError và VerifyError không giống nhau

- **`ClassFormatError`:** class bytes sai cấu trúc/không thể giải thích là class-file hợp lệ (ví dụ thiếu magic/truncated).
- **`UnsupportedClassVersionError`:** subtype của `ClassFormatError` khi version không được JVM hỗ trợ.
- **`VerifyError`:** classfile đã được đọc nhưng JVM verifier phát hiện bytecode thiếu nhất quán hoặc vi phạm điều kiện cần thiết cho type safety (ví dụ stack/stack map frames không đúng).
- **`NoSuchMethodError`/`NoSuchFieldError`:** tham chiếu symbolic trong bytecode không còn resolve được với phiên bản class đang được load.
- **`IncompatibleClassChangeError`:** có thay đổi binary không tương thích, ví dụ kỳ vọng static nhưng implementation trở thành instance hoặc ngược lại theo tình huống.

**Đừng dùng `-noverify`, cờ vô hiệu hóa verification hoặc sửa JAR bytecode trực tiếp để che VerifyError.** Hướng đúng là xác định thư viện sinh bytecode/transformer, công cụ build và version compatibility rồi xây lại artifact đúng.

## 6. Dùng -Xlog để biết class thực sự đến từ đâu

Với **HotSpot JVM hiện đại**, có thể bật Unified Logging:

```bash
java -Xlog:class+load=info,class+init=info -cp out com.example.Main
```

Lệnh giả định bạn có classpath `out` và main class tương ứng. Log thường gồm nhiều lớp JDK/framework, nên có thể redirect file và lọc:

```bash
java -Xlog:class+load=info:file=classes.log:uptime,level,tags \
     -cp out com.example.Main

grep 'com.example.MyClass' classes.log
```

Trên PowerShell:

```powershell
java "-Xlog:class+load=info:file=classes.log:uptime,level,tags" -cp out com.example.Main
Select-String -Path classes.log -Pattern 'com.example.MyClass'
```

`class+load=info` cho biết **class được load** và thường có nguồn tải như `source: file:/...`, `jrt:/...` hoặc nguồn khác tùy JDK. `class+init=info` giúp tìm thời điểm JVM bắt đầu **khởi tạo** class. Các tag log hỗ trợ phụ thuộc JVM vendor/implementation, đây là **HotSpot Unified Logging**, không phải ngôn ngữ Java quy định cho mọi VM.

Khi cần thêm chi tiết và chấp nhận overhead:

```bash
java -Xlog:class+load=debug,class+resolve=debug \
     -cp out com.example.Main
```

Các log này có thể rất lớn hoặc tiết lộ đường dẫn/tên package; bật có thời hạn trong môi trường kiểm soát, dùng log rotation nếu chạy dài. Đừng kết luận “không thấy log” nghĩa là class không tồn tại khi logging level không bao phủ pha cần xem hoặc log đã bị xoay.

**Không dùng các cờ tracing VM cũ như `-XX:+TraceClassLoading` trong hướng dẫn hiện đại.** HotSpot có unified logging `-Xlog:class+load=...`, là cách áp dụng hiện nay.

## 7. Phân biệt lỗi runtime binary compatibility

Khi một thư viện được biên dịch chống lại **API version A**, nhưng runtime tải **API version B**, JVM có thể ném LinkageError ngay cả khi **JAR vẫn tồn tại**.

Ví dụ giả định:

```text
Compile:
  api.jar v2:  Service.newMethod() tồn tại
  client.jar:  invokevirtual Service.newMethod()

Runtime:
  api.jar v1:  Service.newMethod() không tồn tại
  client.jar:  gọi tới phương thức đã biên dịch

=> Có thể NoSuchMethodError
```

Bảng đối chiếu:

| Lỗi | Kiểm tra gì trước |
| --- | --- |
| `NoSuchMethodError` | Binary descriptor (params + return type), phiên bản JAR compile/runtime, method được đổi/xóa |
| `NoSuchFieldError` | Field name/type, version runtime, trường bị đổi/xóa |
| `IllegalAccessError` | Member/class visibility thay đổi, module exports, class version mới không tương thích |
| `AbstractMethodError` | Interface/abstract contract thay đổi, implementation cũ vẫn được dùng |
| `IncompatibleClassChangeError` | Static/instance/class/interface và các thay đổi binary không tương thích |
| `BootstrapMethodError` | Bootstrap method của `invokedynamic`/dynamic constant không resolve/khởi tạo được; kiểm tra generated bytecode và causes |

**`IllegalAccessError` khác `IllegalAccessException`:** loại đầu là **`LinkageError` liên quan truy cập tại runtime** (thường là binary change); loại sau là **checked exception** do reflection hoặc MethodHandles.Lookup từ chối thao tác theo quyền của caller.

Kế hoạch chẩn đoán:

1. Xem full stack trace, **dòng lỗi đầu tiên** và `Caused by`.
2. Xác định lớp/method cụ thể, **runtime ClassLoader** nào load nó.
3. Đối chiếu JAR và API versions thực tế, không dùng dependency tree “trên giấy” làm bằng chứng duy nhất.
4. Dùng `javap -v -p` / `-s` / `-c` xem binary signatures và call sites.
5. Kiểm tra shading, fat JAR packaging, `META-INF/versions`, module path.
6. Clean build và chạy lại trên **đúng JDK/runtime image**, không chỉ trên IDE.

**Không xóa tùy tiện một JAR trong production** để “ép classloader chọn JAR khác” mà chưa kiểm soát dependency graph và khả năng rollback.

## 8. Chương trình Java 17+ hoàn chỉnh: tái hiện và phân loại lỗi

Chương trình sau là một **bài lab tự chứa**. Nó minh họa:

1. `Class.forName` với tên không tồn tại → `ClassNotFoundException`.
2. Static init thất bại lần đầu → `ExceptionInInitializerError`; lần sau → `NoClassDefFoundError`.
3. `MethodHandles.lookup()` có quyền đầy đủ cho caller/nestmates; `publicLookup` không có.
4. `dropLookupMode(PRIVATE)` làm quyền lookup bị thu hẹp, không còn truy cập private member.
5. `privateLookupIn` với nestmate trong cùng unnamed module thành công; với `java.lang.String` trong module `java.base` thất bại nếu không mở package.
6. Tạo hidden class bằng `defineHiddenClass(..., NESTMATE)`; `Class.isHidden()==true` nhưng không tìm lại bằng `Class.forName(hidden.getName())`.
7. Đọc bytes của chính `.class` để kiểm tra magic và major; thử **class bytes hỏng trong memory** → `ClassFormatError`; patch major **trên byte array clone trong memory** → `UnsupportedClassVersionError`.

**Giới hạn an toàn:** demo **không sửa JAR/file nào của project**; `BytesLoader` chỉ tạo class từ dữ liệu trong memory để quan sát exception. Các lỗi được **catch có chủ đích trong lab**, không phải lời khuyên catch mọi `Error` rồi bỏ qua ở ứng dụng thật. Mã cần **JDK 17+**, được biên dịch bằng `--release 17` để major version in ra là **61**, kể cả khi compiler chạy trên JDK mới hơn.

Lưu file **`LoadingLookupDiagnosticsDemo.java`** ở UTF-8:

```java
import java.io.InputStream;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;

public final class LoadingLookupDiagnosticsDemo {
    private static final class Vault {
        private String greet(String name) {
            return "Hello, " + name;
        }
    }

    private static final class FailingInit {
        static final int VALUE = fail();

        private static int fail() {
            throw new IllegalStateException("initializer failed");
        }
    }

    private static final class BytesLoader extends ClassLoader {
        Class<?> fromBytes(byte[] bytes) {
            return defineClass(null, bytes, 0, bytes.length);
        }
    }

    private static byte[] classBytes(String resource) throws Exception {
        try (InputStream input = LoadingLookupDiagnosticsDemo.class
                .getResourceAsStream(resource)) {
            if (input == null) {
                throw new IllegalStateException("Missing resource: " + resource);
            }
            return input.readAllBytes();
        }
    }

    public static void main(String[] args) throws Throwable {
        ClassLoader loader =
                LoadingLookupDiagnosticsDemo.class.getClassLoader();

        System.out.println("namedModule=" +
                LoadingLookupDiagnosticsDemo.class.getModule().isNamed());
        System.out.println("sameLoader=" +
                (Class.forName(Vault.class.getName(), false, loader)
                        == Vault.class));

        try {
            Class.forName("missing.example.Component", false, loader);
            System.out.println("missingName=unexpected");
        } catch (ClassNotFoundException expected) {
            System.out.println("missingName=ClassNotFoundException");
        }

        try {
            System.out.println(FailingInit.VALUE);
        } catch (ExceptionInInitializerError expected) {
            System.out.println("firstInit=ExceptionInInitializerError");
        }
        try {
            System.out.println(FailingInit.VALUE);
        } catch (NoClassDefFoundError expected) {
            System.out.println("laterInit=NoClassDefFoundError");
        }

        MethodHandles.Lookup owner = MethodHandles.lookup();
        MethodType type = MethodType.methodType(
                String.class, String.class);

        System.out.println("ownerFull=" +
                owner.hasFullPrivilegeAccess());

        MethodHandle greeting = owner.findVirtual(
                Vault.class, "greet", type);
        System.out.println("privateNestmate=" +
                (String) greeting.invokeExact(new Vault(), "Lan"));

        try {
            MethodHandles.publicLookup()
                    .findVirtual(Vault.class, "greet", type);
            System.out.println("publicPrivate=unexpected");
        } catch (IllegalAccessException expected) {
            System.out.println("publicPrivate=IllegalAccessException");
        }

        MethodHandles.Lookup narrowed = owner.dropLookupMode(
                MethodHandles.Lookup.PRIVATE);
        System.out.println("narrowedFull=" +
                narrowed.hasFullPrivilegeAccess());
        try {
            narrowed.findVirtual(Vault.class, "greet", type);
            System.out.println("narrowedPrivate=unexpected");
        } catch (IllegalAccessException expected) {
            System.out.println("narrowedPrivate=IllegalAccessException");
        }

        MethodHandles.Lookup forVault =
                MethodHandles.privateLookupIn(Vault.class, owner);
        System.out.println("vaultFull=" +
                forVault.hasFullPrivilegeAccess());

        try {
            MethodHandles.privateLookupIn(String.class, owner);
            System.out.println("javaLangPrivate=unexpected");
        } catch (IllegalAccessException expected) {
            System.out.println("javaLangPrivate=IllegalAccessException");
        }

        byte[] vaultBytes = classBytes(
                "LoadingLookupDiagnosticsDemo$Vault.class");
        Class<?> hidden = owner.defineHiddenClass(
                vaultBytes,
                false,
                MethodHandles.Lookup.ClassOption.NESTMATE)
                .lookupClass();

        System.out.println("hiddenClass=" + hidden.isHidden());
        try {
            Class.forName(hidden.getName(), false, loader);
            System.out.println("hiddenByName=unexpected");
        } catch (ClassNotFoundException expected) {
            System.out.println("hiddenByName=ClassNotFoundException");
        }

        byte[] ownBytes = classBytes(
                "LoadingLookupDiagnosticsDemo.class");
        int magic = ((ownBytes[0] & 255) << 24)
                | ((ownBytes[1] & 255) << 16)
                | ((ownBytes[2] & 255) << 8)
                | (ownBytes[3] & 255);
        int major = ((ownBytes[6] & 255) << 8)
                | (ownBytes[7] & 255);

        System.out.println("classMagic=" +
                (magic == 0xCAFEBABE));
        System.out.println("classMajor=" + major);

        try {
            new BytesLoader().fromBytes(new byte[] {0, 1, 2, 3});
            System.out.println("malformed=unexpected");
        } catch (ClassFormatError expected) {
            System.out.println("malformed=ClassFormatError");
        }

        byte[] future = ownBytes.clone();
        future[6] = 0x7f;
        future[7] = (byte) 0xff;

        try {
            new BytesLoader().fromBytes(future);
            System.out.println("futureVersion=unexpected");
        } catch (UnsupportedClassVersionError expected) {
            System.out.println(
                    "futureVersion=UnsupportedClassVersionError");
        }
    }
}
```

### Tại sao các phép thử là bằng chứng hợp lệ?

- **Tên không có:** `Class.forName("missing.example.Component", false, loader)` yêu cầu tìm class theo tên, và không tìm được.
- **Static init:** `FailingInit.VALUE` không phải compile-time constant, nên lần đầu truy cập kích hoạt `<clinit>`. Thất bại khiến class ở trạng thái erroneous; lần sau có `NoClassDefFoundError`.
- **Nestmate:** `Vault` là nested class trong cùng Java nest với outer class; lookup gốc có thể truy cập member private của nestmate theo JVM access rules.
- **Lookup bị thu hẹp:** `publicLookup()` và lookup sau `dropLookupMode(PRIVATE)` không có private capability để truy cập `Vault.greet`.
- **Private lookup:** `privateLookupIn(Vault.class, owner)` được phép ở cùng unnamed module với caller full privilege; nhưng không được quyền sâu vào `java.lang` của `java.base` khi package không opens đến caller.
- **Hidden class:** được JVM định nghĩa bằng class bytes qua `Lookup.defineHiddenClass`; class là hidden và không có binary name tra cứu theo `Class.forName`.
- **Class format:** magic `0xCAFEBABE` và major byte positions được đọc trực tiếp từ `.class`.
- **Unsupported major:** patch version trên `ownBytes.clone()` thành một major giả định chưa được hỗ trợ; chỉ loader tạm trong lab đọc clone đó.

Đặc biệt, chương trình **không tạo `VerifyError`** vì để làm vậy phải chế tác bytecode vi phạm verification rules một cách cố ý; việc đó không cần thiết để học nhận diện lỗi. Với một `VerifyError` thực tế, nên xem bytecode bằng `javap -v -c`, stack map frames và thư viện sinh/transform class.

## 9. MethodHandles.Lookup là một capability, không phải “chìa khóa toàn cục”

`java.lang.invoke.MethodHandles.Lookup` là **đối tượng đại diện cho quyền truy cập của một lookup class**. Nó được dùng khi tạo `MethodHandle`, truy cập constructor/field/method có điều kiện, hoặc định nghĩa class/hidden class trong những điều kiện nhất định.

Các API quan trọng:

| API | Công dụng | Giới hạn phải nhớ |
| --- | --- | --- |
| `MethodHandles.lookup()` | Lookup gốc có quyền của **caller** | Caller-sensitive; không truyền cho code không đáng tin |
| `MethodHandles.publicLookup()` | Lookup ít đặc quyền, truy cập public members công khai phù hợp | Không có quyền private; không tương đương deep reflection |
| `lookup.lookupClass()` | Trả lookup class | Cần xem cả modes và previous lookup class, không chỉ tên |
| `lookup.lookupModes()` | Bitmask các lookup modes | Các bit quyết định phạm vi access checks |
| `lookup.hasFullPrivilegeAccess()` | Có private **và** module access | Không có nghĩa bypass mọi module/bytecode rules |
| `lookup.dropLookupMode(PRIVATE)` | Giảm quyền của lookup | Không thể dùng để nâng quyền ngược lại |
| `lookup.in(Target.class)` | Chuyển lookup context có thể **làm mất modes** | Không phải API “đổi lớp để lấy private quyền bất kỳ” |
| `MethodHandles.privateLookupIn(Target.class, caller)` | Tạo lookup deep-access sau kiểm tra | Caller cần full privilege; cross-module cần reads/opens |
| `lookup.findVirtual/findStatic(...)` | Tạo handle đúng method name/signature | Có thể `NoSuchMethodException` hoặc `IllegalAccessException` |
| `lookup.defineClass(byte[])` | Định nghĩa class ở runtime package của lookup class | Cần `PACKAGE` access, bytecode hợp lệ |
| `lookup.defineHiddenClass(...)` | Định nghĩa hidden class (Java 15+) | Cần full privilege và package/module ràng buộc |

### Access modes cần nhìn khi debug

| Mode | Ý nghĩa chung |
| --- | --- |
| `PUBLIC` | Cho phép các member/class public phù hợp quyền của lookup |
| `PRIVATE` | Cho phép private access của lookup class và nestmates khi hợp lệ |
| `PROTECTED` | Phạm vi protected theo JVM lookup rules |
| `PACKAGE` | Phạm vi package của lookup class |
| `MODULE` | Phạm vi module; kết hợp `PRIVATE` tạo full privilege |
| `UNCONDITIONAL` | Public lookup dạng unconditional, với các exported-public access rules |
| `ORIGINAL` | Lookup thực sự được tạo từ caller gốc; quyền đặc biệt với một số caller-sensitive operations |

Không nên suy nghĩa từ **một bit đơn lẻ** mà bỏ qua **lookup class, previous lookup class, module context và Java access rules**. Ví dụ lookup vẫn có `PUBLIC` không thể truy cập một private method của class khác.

### Hai lỗi thường gặp

**Lỗi A — Method không tồn tại/signature sai:**

```java
MethodHandles.Lookup lookup = MethodHandles.lookup();
MethodType wrong = MethodType.methodType(String.class, int.class);
lookup.findVirtual(SomeClass.class, "someMethod", wrong);
```

Đây là **snippet minh họa** (cần `SomeClass` và imports); nếu method name/type descriptor không khớp, lookup có thể ném **`NoSuchMethodException`**.

**Lỗi B — Method tồn tại nhưng không đủ quyền:**

```java
MethodHandles.publicLookup()
    .findVirtual(Vault.class, "greet",
        MethodType.methodType(String.class, String.class));
```

Đoạn này tham chiếu tới `Vault` trong chương trình mục 8 và sẽ bị từ chối vì private access không có. **Không “sửa” bằng việc tự tạo lookup đặc quyền rồi chia sẻ nó cho plugin không tin cậy**.

### Full-privilege lookup là dữ liệu nhạy cảm

Theo Javadoc, `MethodHandles.lookup()` trả về **capability có quyền của caller**. Nếu một framework hoặc application phát lookup này cho module/plugin không đáng tin, bên nhận có thể tìm/call private members mà người tạo lookup được phép truy cập hoặc định nghĩa class trong một số điều kiện.

**Nguyên tắc least privilege:** chỉ cung cấp API hoặc `MethodHandle` đã chọn sẵn cho thao tác cần thiết; nếu thật sự cần Lookup thì ưu tiên giới hạn quyền (ví dụ `publicLookup()` hoặc `dropLookupMode`) và kiểm tra kỹ khi chuyển qua boundary.

## 10. JPMS exports và opens: nguyên nhân phổ biến của lookup failure

Trong Java Platform Module System (**JPMS**), visibility không chỉ phụ thuộc `public/private`. Một lớp public thuộc một **named module** có thể không public-accessible từ module khác nếu package chưa được **export**, và thao tác deep reflection/private lookup có thể cần package được **open**.

Ví dụ:

```java
module orders.core {
    exports com.example.orders.api;
    opens com.example.orders.internal to orders.framework;
}
```

Đây là **module descriptor minh họa**. Trong source thật, bạn viết nó vào file `module-info.java`, cần các modules/dependencies tương ứng.

- **`exports`:** công bố public API của package cho compile/runtime ordinary access (có thể qualified export).
- **`opens`:** cho phép deep reflection vào package cho module được chỉ định (có thể qualified open).
- **`requires`:** module readability edge; trong nhiều tình huống caller cần đọc target module để thực hiện lookup liên module.

Với `privateLookupIn(Target.class, callerLookup)`, Javadoc hiện hành yêu cầu:

1. Caller lookup có **full privilege**: `PRIVATE` và `MODULE`.
2. Target không phải primitive/array.
3. Nếu hai module khác nhau, **module caller reads module target**.
4. **Target module opens package target tới module caller**.
5. Lookup trả về khi đi qua module boundary có thể giữ `PRIVATE` nhưng **mất `MODULE`**, không có nghĩa trao quyền cross-module vô hạn.

Nếu những điều kiện này không thỏa, method ném **`IllegalAccessException`**. Kể cả `Target` public và package được export, điều đó **không tự cho quyền truy cập private members**.

### Reflection khác MethodHandles Lookup

Khi gọi reflection:

```java
Field field = SomeType.class.getDeclaredField("secret");
field.setAccessible(true);
```

một module chưa `opens` package có thể gây **`InaccessibleObjectException`** (unchecked) tại `setAccessible(true)`. Mặt khác, `MethodHandles.privateLookupIn` báo **`IllegalAccessException`** theo hợp đồng. Hai API khác nhau nên loại exception có thể khác.

**Không phụ thuộc cờ `--illegal-access=permit` như một giải pháp hiện hành**: strong encapsulation của JDK internals đã được tăng cường từ Java 17 và cơ chế nới lỏng rộng cũ không còn đáng tin/còn hiệu lực như ngày trước. Trong trường hợp migration đặc biệt, `--add-opens target.module/package=caller.module` có thể là **biện pháp tạm thời, có phạm vi**, nhưng cần audit và ưu tiên `opens` có chủ đích trong module của ứng dụng.

Ví dụ ghi chú cú pháp trên classpath:

```bash
java --add-opens java.base/java.lang=ALL-UNNAMED -cp out com.example.Main
```

**Đây chỉ là ví dụ về option** và có thể thay đổi kết quả access check, **không phải lệnh khuyến nghị bật trong production**. Mở `java.lang` cho tất cả unnamed modules là mở rộng quyền lớn, không cần thiết cho chương trình demo.

## 11. Hidden classes trong Java 15: “class có tồn tại nhưng không có tên để tìm”

**JEP 371 — Hidden Classes** là tính năng chính thức của **Java 15**, giúp framework hoặc runtime sinh class mà **không cần** gán cho nó một binary name thông thường có thể được link bởi code khác. `MethodHandles.Lookup.defineHiddenClass(byte[], boolean, ClassOption...)` trả về một `Lookup` liên quan hidden class mới.

Hệ quả quan trọng cho chẩn đoán:

- `hiddenClass.isHidden()` trả **`true`.
- Tên trả về bởi `hiddenClass.getName()` **không phải binary name** thông thường, nên không thể load lại bằng `Class.forName(hiddenName)`.
- `Class.getNestMembers()` không nhất thiết liệt kê hidden nestmates được thêm động qua `defineHiddenClass(NESTMATE)`; đừng chỉ dựa vào danh sách đó để kết luận hidden class không tồn tại.
- `NESTMATE` cho phép hidden class tham gia nest phù hợp, bao gồm private access theo nest rules.
- `STRONG` thay đổi quan hệ vòng đời của hidden class với defining loader; không tự dùng STRONG nếu không cần vì ảnh hưởng khả năng unloading.
- Nếu generator sinh bytes sai, `defineHiddenClass` vẫn có thể ném **`ClassFormatError`, `VerifyError`, `IllegalAccessException` hoặc LinkageError phù hợp**.
- Hidden class vẫn có **Class object**, loader/module/package và access rules; “hidden” **không** có nghĩa bỏ qua bytecode verification hay là security sandbox.

Đối với một stack trace từ lambda/adapter/framework sinh mã, hãy kiểm tra **JDK version, code generation library, generated bytes, Lookup origin/modes và module access**. Đừng kết luận lỗi chỉ vì `Class.forName` không tìm được tên hiển thị của một hidden class.

### Tại sao hidden class có thể khó debug?

Framework có thể sinh class động, không có file `.class` nằm trên đĩa để `javap` trực tiếp theo tên. Trong trường hợp ấy:

- Dùng **logging/sự kiện class loading của JVM** và khả năng dump generated bytes từ **framework được tin cậy** nếu nó có hỗ trợ.
- Ghi lại **lookup class, module, class loader, class-file major, exception class và cause**.
- Nếu có bytes gốc từ generator, dùng công cụ phân tích bytecode trên bản sao trong môi trường test.
- Không sửa trực tiếp bytes của process đang chạy để “bắt verifier bỏ qua lỗi”.

**Class loader bình thường không tự tạo “tên để tra lại” cho hidden class**. Đó là một phần mục đích thiết kế, không phải thất bại của ClassLoader.

## 12. Nên tìm thông tin nào trước khi quyết định cách sửa?

Một quy trình điều tra có thể làm theo thứ tự:

**1. Giữ nguyên lỗi đầu tiên.** Thu full stack trace, các `Caused by` và thời điểm bắt đầu incident. Nếu process đã restart nhiều lần, tìm **exception xảy ra sớm nhất**, không chỉ `NoClassDefFoundError` lặp lại sau đó.

**2. Xác định runtime thực sự.** Ghi `java -version`, `java.home`, JDK vendor, launcher JVM flags, app image/container, OS và module classpath setup. Đảm bảo build/IDE và runtime không dùng **hai JDK khác nhau**.

**3. Ghi class identity.** In tên class, `ClassLoader`, `Module`, source location nếu có, classfile version. Classpath đã include JAR vẫn chưa đủ nếu loader thực đang dùng không thấy JAR đó.

**4. Kiểm tra packaging.** `jar --list`, dependency tree, nested/fat JAR, `META-INF/versions`. Đọc log `-Xlog:class+load` để xác nhận JAR nào đã thật sự định nghĩa class.

**5. Dò binary contract.** Với `NoSuchMethodError`, `IllegalAccessError`, `VerifyError`, dùng `javap -v -c -p` trên runtime class và phía caller. So sánh binary method descriptors, field types, modifiers, NestHost/NestMembers và module metadata.

**6. Với lookup failure:** ghi `lookup.lookupClass()`, `lookup.lookupModes()`, `lookup.hasFullPrivilegeAccess()`, target class/module/package. Không log privileged lookup objects cùng dữ liệu nhạy cảm nếu có thể tạo lộ quyền.

**7. Phân biệt not found và not allowed.** `ClassNotFoundException` khác `IllegalAccessException`; `VerifyError` khác `UnsupportedClassVersionError`. Đừng áp cùng một mẹo “add JAR”/“add opens” cho mọi lỗi.

**8. Chạy lại một test nhỏ trên cùng runtime.** Dùng `javac --release ...`, một class loader xác định, classpath/minimal module setup và test cụ thể. So sánh kết quả trên JDK/runtime image thật.

**9. Sửa nguyên nhân, không che hiện tượng.** Rebuild với `--release` phù hợp, đồng bộ dependency versions, sửa generator bytes hoặc module descriptor, hạn chế quyền Lookup, giải quyết static initializer.

**10. Regression test.** Kiểm tra lại ở runtime deployment, bật class-loading log ngắn hạn và lưu test vectors cho bytecode/library API. Khi cần JPMS `opens`, ưu tiên qualified opens đúng module thay vì mở rộng toàn bộ.

| Thông báo/hiện tượng | Bước điều tra ưu tiên | Tránh làm gì |
| --- | --- | --- |
| `ClassNotFoundException: com.acme.Plugin` | Name, jar contents, classpath/module visibility, loader | Đổi sang catch Error |
| `NoClassDefFoundError: com/acme/Api` | Dependency runtime thực tế, loader/log nguồn class | Chỉ sửa tên trong source mà không xem JAR |
| `NoClassDefFoundError: Could not initialize class...` | Tìm `ExceptionInInitializerError` đầu tiên và cause | Bổ sung JAR vô căn cứ |
| `UnsupportedClassVersionError: class file version 65` | JDK runtime bao nhiêu? target 21 có phù hợp không? | Patch major bytes trên JAR thật |
| `ClassFormatError` | JAR corrupt, generated bytes, transformer | Tắt verification |
| `VerifyError` | `javap -v -c`, stack map frames, bytecode generator, agent | Bỏ qua lỗi và tiếp tục gọi code |
| `NoSuchMethodError` | Runtime dependency, binary descriptor, duplicate classes | Chỉ tin Maven/Gradle compile report |
| `IllegalAccessError` | Visibility/binary incompatibility, module export, access class | Nhầm với reflective checked exception |
| `IllegalAccessException` từ Lookup | Lookup modes, caller/target class, module opens/reads | Chia sẻ Lookup đặc quyền cho plugin |
| `InaccessibleObjectException` từ reflection | Target package có opens tới caller không | Bật `--add-opens` vô hạn |
| `ClassCastException: X cannot be cast to X` | Hai defining loaders khác nhau hay không? | Ép cast liên tục |
| `Class.forName(hiddenName)` không thấy | Hidden class không có binary name | Coi như generator không hề tạo class |
| `BootstrapMethodError` | `invokedynamic`/condy bootstrap, linkage cause và bytecode | Bỏ qua Throwable cause |
| `ClassCircularityError` | Superclass hierarchy/bytecode loader tạo vòng | Chỉ tăng heap |

**Dùng đúng bộ công cụ cho đúng giai đoạn** giúp tránh những “fix” có tác dụng phụ bảo mật. Ví dụ `--add-opens` chỉ thay access policy theo phạm vi, **không** sửa classfile corrupt; thêm JAR **không** sửa một `Class` đã khởi tạo lỗi do DB URL sai trong static initializer.

## 14. Những hiểu nhầm thường gặp

| Hiểu nhầm | Kết luận đúng |
| --- | --- |
| `NoClassDefFoundError` luôn do không có JAR | Có thể là **class initialization thất bại trước đó** |
| `ClassNotFoundException` và `NoClassDefFoundError` hoàn toàn giống nhau | Một là checked exception thường do name-based loading; một là `LinkageError` |
| Class name bằng nhau nghĩa là cùng runtime class | Phải xét **defining class loader** |
| `Class.forName(name,false,loader)` chắc chắn khởi tạo class | Tham số `false` là **không initialize** |
| Build thành công nghĩa là runtime load mọi dependency | Runtime classpath/module path có thể khác lúc build |
| `--release 17` và `-target 17` hoàn toàn tương đương | `--release` còn ràng buộc API target platform |
| `UnsupportedClassVersionError` chữa bằng sửa major bytes | Không; bytecode/API cũng phải tương thích |
| `VerifyError` là lỗi compiler Java thông thường | Thường liên quan bytecode verification/generated/transformed code |
| `IllegalAccessError` giống `IllegalAccessException` | Loại đầu là Error linkage, loại sau là checked exception access |
| `exports` cho phép lấy tất cả private members | Deep reflection/private lookup cần `opens` và access checks |
| `publicLookup()` có private capability | Chỉ những public accesses phù hợp |
| `lookup.in(...)` là cách nâng quyền | Chỉ đổi lookup context với modes có thể **giảm** |
| `privateLookupIn` bỏ qua JPMS | Cần `PRIVATE` + `MODULE`, reads/opens liên module |
| Hidden class có `getName()` nên `Class.forName` tìm được | Hidden class **không có binary name bình thường** |
| Hidden class không cần verifier | Vẫn phải thỏa JVM class-file/verification rules |
| Cứ bật `--add-opens java.base/...=ALL-UNNAMED` là giải pháp production | Mở rộng quyền; chỉ sử dụng có kiểm soát và lý do rõ |
| Classloader là security sandbox cho bytecode không tin cậy | Loader chủ yếu là namespace/loading mechanism; không thay OS/process isolation |

## 15. Bài tập và đáp án

**Câu 1.** Code dùng `Class.forName("com.example.OptionalFeature")` và gặp `ClassNotFoundException`. Bạn nên kiểm tra những gì trước khi sửa application logic?

**Câu 2.** Lần đầu gọi `ConfigHolder.VALUE` gặp `ExceptionInInitializerError`; lần tiếp theo gặp `NoClassDefFoundError`. Có chắc JAR bị mất không?

**Câu 3.** Java 17 runtime báo `UnsupportedClassVersionError: class file version 65`. Tập tin ấy được biên dịch hướng tới Java nào? Cách khắc phục bền vững?

**Câu 4.** Cùng tên `com.acme.User`, nhưng hai ClassLoaders khác nhau định nghĩa nó. Vì sao `getName()` giống nhưng ép kiểu có thể thất bại?

**Câu 5.** Một framework dùng `MethodHandles.publicLookup()` để gọi private method của một lớp. Vì sao gặp `IllegalAccessException`?

**Câu 6.** Module A `requires` module B, và B `exports com.example.internal`, nhưng `privateLookupIn(Internal.class, lookupFromA)` vẫn lỗi. Thiếu điều kiện nào?

**Câu 7.** Một hidden class được tạo thành công từ `defineHiddenClass`, nhưng tìm lại bằng `Class.forName(hidden.getName())` lại không thấy. Có phải class bị JVM unload ngay lập tức không?

**Câu 8.** Người lập trình thay byte major của một `.class` từ 65 xuống 61 để chạy trên Java 17. Việc ấy có đáng tin không?

**Câu 9.** Khi log có `NoSuchMethodError` ở runtime nhưng compiler pass, nên tập trung vào thành phần nào?

**Câu 10.** Bạn đang chẩn đoán một `VerifyError` từ thư viện tạo bytecode; tại sao việc dùng `javap -v -c` hoặc dump generated bytes ở môi trường test hữu ích hơn việc tắt verifier?

**Câu 11.** Cách nào có thể cho biết runtime thực sự đã load một class từ JAR nào thay vì chỉ dựa trên dependency tree?

**Câu 12.** Đoạn demo in `classMajor=61` khi build bằng `javac --release 17` trên JDK 24. Điều đó có nghĩa gì về classfile, và có đồng nghĩa JVM 17 hỗ trợ mọi thư viện JDK 24 không?

**Đáp án:**

1. Kiểm tra binary class name, JAR contents, runtime classpath/module path, class loader đang dùng và dependency scope. Không tự bắt `Error` để che vấn đề.
2. Không. Trường hợp này điển hình của **static initializer thất bại**; cần tìm root cause trong initializer và trạng thái config/môi trường ở lỗi đầu tiên.
3. Major 65 tương ứng **Java 21**. Nâng runtime cho phù hợp hoặc **biên dịch/phát hành lại** cho Java 17 bằng `--release 17` với các API/tính năng tương thích.
4. Vì class identity xét cả **binary name + defining loader**; JVM xem chúng là hai runtime classes khác nhau.
5. `publicLookup` không có `PRIVATE` access; phương thức tồn tại nhưng quyền truy cập không đủ.
6. Package của module B cần **`opens` tới module A** (và caller lookup phải có `PRIVATE` + `MODULE`). Export public API không đồng nghĩa deep reflection.
7. Không. Hidden class **không có binary name** để `Class.forName` tìm; cần giữ `Class`/`Lookup` hoặc reference phù hợp. Việc unload là câu chuyện vòng đời riêng.
8. Không. Header major chỉ là một phần. Bytecode semantics, constant pool và API vẫn có thể đòi Java 21; phải build lại bằng compiler target phù hợp.
9. Runtime dependency version, class loader nào load API, method name/descriptor thực tế, các JAR trùng nhau và binary compatibility.
10. Vì verifier bảo vệ type safety; phải tìm bytecode/stack map lỗi ở generator/transformer và sửa nguyên nhân. Tắt verifier gây rủi ro và không phải hướng hiện hành.
11. HotSpot `-Xlog:class+load=info`, thông tin class loader và code source nếu có, `jar --list` hoặc `javap` trên JAR thực tế.
12. Classfile dùng **major 61**, phù hợp Java 17. Điều đó **không** bảo đảm mọi JDK 24 API/feature đều có trên Java 17; `--release 17` giúp kiểm soát API dùng khi biên dịch source phù hợp.
