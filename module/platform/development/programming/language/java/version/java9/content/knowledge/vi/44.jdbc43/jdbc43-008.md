# Trích dẫn literal, identifier và NCHAR qua Statement (JDBC 4.3, Java 9+)

## Mục tiêu bài học

Sau bài này, bạn có thể phân biệt **giá trị chuỗi trong SQL**, **tên đối tượng SQL (identifier)** và **giá trị chuỗi ký tự quốc gia (NCHAR)**; sử dụng bốn phương thức `Statement.enquoteLiteral(...)`, `Statement.enquoteIdentifier(...)`, `Statement.isSimpleIdentifier(...)` và `Statement.enquoteNCharLiteral(...)`; hiểu khi nào phải dùng `PreparedStatement` thay vì ghép chuỗi; và nhận biết giới hạn theo JDBC driver/cơ sở dữ liệu.

Bốn phương thức trên được bổ sung vào giao diện `java.sql.Statement` trong Java 9 (JDBC 4.3) và **vẫn là API Java chuẩn đang được hỗ trợ**. Chúng trả về chuỗi SQL được trích dẫn (quoted) để dùng khi xây dựng SQL, **không tự thực thi truy vấn**.

## 1. Phân biệt literal, identifier và NCHAR

Ví dụ SQL (cú pháp nháy kép identifier theo SQL chuẩn):

```sql
SELECT "display name"
FROM "customer profile"
WHERE "display name" = 'O''Brien';
```

Có ba vai trò khác nhau:

| Thành phần | Ví dụ SQL | Ý nghĩa |
| --- | --- | --- |
| **String literal** | `'O''Brien'` | Một **giá trị dữ liệu**, bao trong nháy đơn `'`; nháy đơn bên trong giá trị được viết thành hai nháy đơn liên tiếp. |
| **Delimited identifier** | `"customer profile"` | Một **tên đối tượng**: bảng, cột, schema…; nháy kép thường là ký hiệu theo SQL chuẩn nhưng dấu trích dẫn thực tế phụ thuộc hệ quản trị. |
| **National character literal** | `N'Chào bạn'` | Một **giá trị ký tự** theo cú pháp national character string literal; tiền tố `N` có ý nghĩa và mức hỗ trợ tùy hệ quản trị. |

Nhầm lẫn ba loại này sẽ tạo câu SQL sai. Ví dụ `'customers'` là dữ liệu chuỗi, không phải tên bảng `customers`; `"O'Brien"` có thể được hiểu là tên cột, không phải giá trị chuỗi. Dấu nháy đơn bên trong identifier không có cùng quy tắc với dấu nháy đơn bên trong literal.

Những phương thức `enquote...` giúp biểu diễn các chuỗi Java thành phần SQL thích hợp, nhưng không thay thế việc kiểm soát quyền truy cập, kiểm tra tên đối tượng hay chuẩn bị tham số truy vấn.

## 2. Bốn API của Statement

`Statement` trong `java.sql` có các phương thức sau, tất cả được đánh dấu `default` và có từ Java 9:

| Phương thức | Đầu vào | Kết quả/vai trò |
| --- | --- | --- |
| `String enquoteLiteral(String val)` | Giá trị chuỗi | Bao giá trị trong `'...'`, thay mọi `'` bên trong bằng `''`. |
| `String enquoteIdentifier(String identifier, boolean alwaysQuote)` | Tên đối tượng SQL; có muốn luôn đặt dấu bao không | Trả về identifier đơn giản hoặc identifier được bao bằng dấu phù hợp với dữ liệu nguồn. |
| `boolean isSimpleIdentifier(String identifier)` | Tên đối tượng SQL | Kiểm tra identifier có thể dùng ở dạng đơn giản theo quy tắc JDBC driver hay không. |
| `String enquoteNCharLiteral(String val)` | Giá trị chuỗi dành cho national character literal | Theo mặc định, tạo `N'...'` và nhân đôi `'` trong giá trị. |

Tên tham số boolean có thể được viết là `alwaysQuote` hoặc `alwaysDelimit` ở các phiên bản JavaDoc khác nhau; **kiểu, thứ tự tham số và ý nghĩa API không đổi**.

### 2.1. enquoteLiteral: trích dẫn giá trị chuỗi

Ví dụ về phương thức này trong một đối tượng `Statement st`:

```java
st.enquoteLiteral("Hello");      // 'Hello'
st.enquoteLiteral("O'Brien");    // 'O''Brien'
st.enquoteLiteral("");           // ''
```

Với cách cài đặt mặc định trong JDK, công thức tương đương:

```java
"'" + val.replace("'", "''") + "'"
```

Phép nhân đôi nháy đơn áp dụng cho **giá trị đầu vào chưa được quote**. Không tự bao `'...'` trước khi truyền vào, nếu không những dấu nháy có sẵn cũng bị nhân đôi. Ví dụ, muốn giá trị chứa đúng sáu ký tự `O'Brien` thì truyền `"O'Brien"`, không truyền một literal SQL đã trích dẫn.

**Điểm cần nhớ về an toàn:** `enquoteLiteral` chỉ là tiện ích tạo chuỗi SQL. Với điều kiện `WHERE`, dữ liệu biểu mẫu, tìm kiếm, ghi/cập nhật dữ liệu…, mặc định nên viết `PreparedStatement` với dấu giữ chỗ `?` rồi `setString(...)` hoặc setter phù hợp. Cách bind giá trị này còn giải quyết vấn đề kiểu dữ liệu, `null` và các quy tắc chuyển đổi/escape riêng của driver. Không được xem việc tự ghép chuỗi với `enquoteLiteral` là giải pháp tổng quát thay cho parameter binding.

### 2.2. enquoteIdentifier: trích dẫn tên bảng/cột/schema

Ký hiệu tên đối tượng chịu ảnh hưởng của SQL dialect. SQL chuẩn thường dùng nháy kép; một số database cấu hình hoặc hỗ trợ thêm cách khác. `Statement.enquoteIdentifier(identifier, alwaysQuote)` giúp driver quyết định cách viết theo nguồn dữ liệu:

```java
st.enquoteIdentifier("customers", false);    // customers
st.enquoteIdentifier("customers", true);     // "customers"
st.enquoteIdentifier("Order Detail", false); // "Order Detail"
```

Các ví dụ trên là **kết quả mặc định khi JDBC driver dùng dấu nháy kép `"`**, không phải cam kết cho mọi database.

- `alwaysQuote = false`: nếu được nhận diện là identifier đơn giản, có thể giữ nguyên; nếu không, cần dạng có dấu bao.
- `alwaysQuote = true`: yêu cầu dạng có dấu bao ngay cả với tên đơn giản, thường hữu ích khi muốn kiểm soát cách database hiểu tên viết hoa/viết thường.
- Các tên có dấu cách, dấu đặc biệt hoặc là SQL keyword có thể cần được bao lại; driver phải biết quy tắc identifier của hệ quản trị.
- Dấu bao được xác định qua khả năng/metadata của nguồn dữ liệu (chẳng hạn `DatabaseMetaData.getIdentifierQuoteString()`); driver có thể từ chối nếu database không hỗ trợ identifier được quote.

**Không gọi `enquoteIdentifier` một lần cho cả tên có nhiều cấp.** Ví dụ:

```java
st.enquoteIdentifier("sales.orders", true);
// "sales.orders"  -> một identifier có dấu chấm trong tên

st.enquoteIdentifier("sales", true) + "."
        + st.enquoteIdentifier("orders", true);
// "sales"."orders" -> schema và table là hai identifier
```

Đây là hai biểu thức SQL khác nghĩa. Quy tắc tương tự áp dụng cho `table.column`. Chỉ nối dấu chấm cú pháp giữa các phần **sau khi từng phần đã được kiểm tra và quote đúng**.

Ngoài ra, việc quote có thể làm thay đổi cách database đối chiếu chữ hoa/thường. Chẳng hạn `users` và `"users"` không nhất thiết chỉ đến cùng một đối tượng ở mọi hệ quản trị. Phải hiểu tên thực tế của bảng/cột đã tạo, đặc biệt khi schema vốn được tạo mà không dùng dấu bao.

### 2.3. isSimpleIdentifier: nhận diện tên đơn giản

`Statement.isSimpleIdentifier(...)` trả về `true` nếu identifier phù hợp quy tắc tên đơn giản mà driver áp dụng. Cách cài đặt mặc định trong Java xem xét tên bắt đầu bằng chữ cái Latin, theo sau là chữ/số/gạch dưới, độ dài cho phép và các quy tắc về SQL keyword (chi tiết có thể được driver điều chỉnh theo database).

```java
st.isSimpleIdentifier("customer_id"); // true với cài đặt mặc định
st.isSimpleIdentifier("Order Detail"); // false
st.isSimpleIdentifier("1customer");   // false
```

Hàm này **không xác nhận** tên bảng/cột có tồn tại, được phép truy cập, thuộc danh sách hợp lệ của ứng dụng hay không. Một identifier trông đúng cú pháp vẫn có thể trỏ đến bảng chứa dữ liệu mà người dùng không được phép xem. Khi ứng dụng cho chọn bảng/cột động, nên dùng **allowlist** ánh xạ các tùy chọn nghiệp vụ sang những tên đối tượng cố định, đã kiểm toán.

Không tự suy luận kết quả đối với SQL reserved keyword mà không kiểm tra với driver thực. Khả năng hỗ trợ ký tự không phải ASCII và giới hạn độ dài tên cũng thay đổi theo nguồn dữ liệu.

### 2.4. enquoteNCharLiteral: trích dẫn national character literal

Theo mặc định:

```java
st.enquoteNCharLiteral("Hello");    // N'Hello'
st.enquoteNCharLiteral("O'Brien"); // N'O''Brien'
```

Phép biến đổi mặc định là:

```java
"N'" + val.replace("'", "''") + "'"
```

Tiền tố `N` là ký hiệu SQL national character literal. Nó **không phải** một cách ghi Unicode phổ quát hoặc thao tác chuyển bảng mã tự động. Mức hỗ trợ cú pháp `N'...'`, kiểu `NCHAR`/`NVARCHAR`, cách lưu và chuyển đổi ký tự phụ thuộc database và JDBC driver. Driver có thể override phương thức mặc định để đáp ứng dialect của nó.

Nếu mục đích là truyền dữ liệu người dùng vào cột Unicode/national character, hãy ưu tiên bind:

```java
// ps là PreparedStatement đã tạo cho câu SQL có dấu ?.
ps.setNString(1, "Tiếng Việt");
```

`setNString` có nghĩa là yêu cầu driver gửi dữ liệu dạng national character tương ứng; driver có thể báo không hỗ trợ. Nếu cột thực là `VARCHAR`/`TEXT` theo hệ quản trị Unicode, hãy chọn setter/kiểu SQL phù hợp với thiết kế schema; không mặc nhiên dùng `NCHAR` cho mọi cột chứa tiếng Việt.

## 3. Ví dụ Java 17+ chạy độc lập, không cần cài database

Để nhìn thấy rõ **hành vi mặc định của API Java**, ví dụ sau tạo một `Statement` mô phỏng tối thiểu bằng `java.lang.reflect.Proxy`. Nó chỉ mô phỏng metadata rằng database sử dụng nháy kép cho identifier; các phương thức `enquote...` và `isSimpleIdentifier` vẫn chạy **chính phương thức `default` thật của `Statement`**. Đây là bài thử cú pháp, **không phải JDBC driver thực và không gửi bất cứ SQL nào tới database**.

Lưu thành `JdbcQuoteDemo.java`:

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;
import java.sql.Connection;
import java.sql.DatabaseMetaData;
import java.sql.SQLException;
import java.sql.Statement;

public class JdbcQuoteDemo {
    public static void main(String[] args) throws SQLException {
        DatabaseMetaData metadata = (DatabaseMetaData) Proxy.newProxyInstance(
                JdbcQuoteDemo.class.getClassLoader(),
                new Class<?>[]{DatabaseMetaData.class},
                (proxy, method, parameters) -> {
                    if (method.getName().equals("getIdentifierQuoteString")) {
                        return "\"";
                    }
                    throw new UnsupportedOperationException(method.getName());
                });

        Connection connection = (Connection) Proxy.newProxyInstance(
                JdbcQuoteDemo.class.getClassLoader(),
                new Class<?>[]{Connection.class},
                (proxy, method, parameters) -> {
                    if (method.getName().equals("getMetaData")) {
                        return metadata;
                    }
                    throw new UnsupportedOperationException(method.getName());
                });

        Statement statement = (Statement) Proxy.newProxyInstance(
                JdbcQuoteDemo.class.getClassLoader(),
                new Class<?>[]{Statement.class},
                (proxy, method, parameters) -> {
                    if (method.isDefault()) {
                        return InvocationHandler.invokeDefault(
                                proxy, method, parameters);
                    }
                    if (method.getName().equals("getConnection")) {
                        return connection;
                    }
                    throw new UnsupportedOperationException(method.getName());
                });

        System.out.println("literal="
                + statement.enquoteLiteral("O'Reilly"));
        System.out.println("identifier="
                + statement.enquoteIdentifier("Order Detail", false));
        System.out.println("simple="
                + statement.isSimpleIdentifier("customer_id"));
        System.out.println("delimited="
                + statement.enquoteIdentifier("customers", true));
        System.out.println("nchar="
                + statement.enquoteNCharLiteral("O'Reilly"));
        System.out.println("qualified="
                + statement.enquoteIdentifier("public.orders", true));

        try {
            statement.enquoteIdentifier("bad\"name", true);
            System.out.println("invalid=accepted");
        } catch (SQLException expected) {
            System.out.println("invalid=SQLException");
        }
    }
}
```

Mở terminal trong thư mục chứa file và chạy:

```sh
javac --release 17 -encoding UTF-8 JdbcQuoteDemo.java
java JdbcQuoteDemo
```

Đầu ra chính xác với các phương thức `default` của OpenJDK được thử:

```text
literal='O''Reilly'
identifier="Order Detail"
simple=true
delimited="customers"
nchar=N'O''Reilly'
qualified="public.orders"
invalid=SQLException
```

**Phân tích:**

1. `O'Reilly` chuyển thành `'O''Reilly'`, vì dấu `'` nằm trong giá trị phải được nhân đôi.
2. `Order Detail` không phải identifier đơn giản, nên được bao trong nháy kép.
3. `customer_id` được nhận diện là identifier đơn giản.
4. `alwaysQuote=true` khiến `customers` trở thành `"customers"`.
5. `enquoteNCharLiteral` thêm `N` trước literal đã quote.
6. `"public.orders"` là **một** identifier, không phải hai phần của tên đủ điều kiện.
7. Với mặc định JDK, identifier chứa nháy kép ở vị trí không hợp lệ bị từ chối bằng `SQLException`; **không giả định phương thức tự escape mọi ký tự của identifier**.

Ví dụ sử dụng `InvocationHandler.invokeDefault` để gọi triển khai mặc định của interface (API này có từ Java 16, phù hợp Java 17+). Trong ứng dụng thực tế, bạn phải lấy `Statement` từ `Connection.createStatement()`; driver có thể ghi đè các phương thức và trả kết quả khác cho database của nó.

## 4. Dùng Statement đúng cách trong ứng dụng JDBC thật

Với một kết nối JDBC đã có, cách dùng cơ bản là:

```java
try (Statement statement = connection.createStatement()) {
    String tableName = statement.enquoteIdentifier("customer", true);
    String label = statement.enquoteLiteral("O'Brien");
    String national = statement.enquoteNCharLiteral("Tiếng Việt");

    // tableName là tên đối tượng SQL.
    // label/national là literal đã được quote, chưa thực thi.
}
```

Đây là **đoạn mã minh họa**, cần có biến `connection` là `java.sql.Connection` đang mở, driver tương thích và schema thực tế. Không có lý do để ghép `label` từ dữ liệu người dùng vào điều kiện SQL thường ngày: hãy bind bằng `PreparedStatement`.

### 4.1. Tình huống đúng: tên bảng được chọn từ allowlist, giá trị được bind

Giả sử ứng dụng chỉ cho phép đọc một trong hai bảng `customer` và `supplier`, và cần lọc theo `tenant_id`. Phương thức sau là **thành viên của một class Java**, chưa phải chương trình chạy độc lập; nó sử dụng các import `java.sql.*`, `java.util.List`, `java.util.ArrayList` và `java.util.Map`:

```java
public static List<String> findNames(
        Connection connection, String tableOption, long tenantId)
        throws SQLException {

    Map<String, String> allowedTables = Map.of(
            "customers", "customer",
            "suppliers", "supplier");

    String table = allowedTables.get(tableOption);
    if (table == null) {
        throw new IllegalArgumentException("Table option is not allowed");
    }

    String sql;
    try (Statement naming = connection.createStatement()) {
        String tableSql = naming.enquoteIdentifier(table, true);
        String nameSql = naming.enquoteIdentifier("name", true);
        String tenantSql = naming.enquoteIdentifier("tenant_id", true);
        sql = "SELECT " + nameSql + " FROM " + tableSql
                + " WHERE " + tenantSql + " = ?";
    }

    List<String> names = new ArrayList<>();
    try (PreparedStatement ps = connection.prepareStatement(sql)) {
        ps.setLong(1, tenantId);

        try (ResultSet rows = ps.executeQuery()) {
            while (rows.next()) {
                names.add(rows.getString(1));
            }
        }
    }
    return names;
}
```

Đây là mẫu tích hợp đúng ranh giới trách nhiệm: **tên đối tượng** được chọn từ danh sách cố định rồi quote bằng `Statement`; **giá trị lọc** đi qua dấu `?` và `setLong`. Code sẽ chạy với kết nối JDBC và database có các bảng/cột tương ứng; kết quả truy vấn phụ thuộc dữ liệu thực tế, vì vậy không có stdout cố định.

Cần kiểm tra trước rằng tên bảng/cột được lưu trong database khớp chính xác với tên đã quote. Nếu database tạo bảng `CUSTOMER` khác chữ hoa/thường theo quy tắc riêng, `"customer"` có thể không chỉ đúng đối tượng. Khi sử dụng schema đủ điều kiện, quote từng phần rồi nối bằng `.`.

### 4.2. Khi nào thực sự cần literal đã quote?

`enquoteLiteral` hay `enquoteNCharLiteral` có ích khi xây dựng **một mảnh SQL tĩnh có kiểm soát**, ví dụ xuất bản DDL có giá trị mặc định dạng text hoặc tạo câu SQL từ cấu hình chỉ dành cho quản trị viên, trong những hệ quản trị không cho bind tại vị trí đó.

Ví dụ minh họa cách dựng chuỗi, **không phải lệnh tạo bảng có thể dùng nguyên trạng với mọi database**:

```java
String columnSql = statement.enquoteIdentifier("display name", true);
String defaultSql = statement.enquoteLiteral("Không xác định");

String fragment = columnSql + " DEFAULT " + defaultSql;
// "display name" DEFAULT 'Không xác định' (với driver dùng nháy kép)
```

DDL, loại cột, collations và khả năng dùng `DEFAULT` phụ thuộc database; phải kiểm thử trên đúng dialect. Nếu nhận text từ người dùng, ưu tiên thiết kế truy vấn có bind parameters và không dựng mệnh đề SQL từ text tùy ý.

## 5. Quy tắc bảo mật và tính di động

### 5.1. Quote không đồng nghĩa với kiểm soát an toàn toàn bộ SQL

Các phương thức `enquote...` chỉ biến đổi **một loại thành phần SQL**. Chúng không xác minh:

- Người gọi có quyền truy cập bảng, cột hoặc schema hay không.
- Identifier có trong allowlist của nghiệp vụ hay không.
- Đoạn SQL khác như `ORDER BY ... DESC`, tên hàm, toán tử, nhiều câu lệnh… có hợp lệ hay không.
- Giá trị string có đúng kiểu dữ liệu SQL, collation, mã hóa hay không.
- Trình điều khiển có thực thi quy tắc escape phù hợp với SQL dialect đang kết nối hay không.

**Khuyến nghị:** bind mọi giá trị có thể bind bằng `PreparedStatement`; dùng allowlist cho tên đối tượng/phần cú pháp cần xây dựng động; chỉ ghép những đoạn SQL cố định hoặc đã được xây dựng từ các thành phần tin cậy.

### 5.2. Tại sao không thể bind identifier bằng dấu ?

`?` trong `PreparedStatement` đại diện cho **giá trị dữ liệu**, không đại diện cho tên bảng/cột. Ví dụ:

```sql
SELECT * FROM ? WHERE id = ?
```

Đoạn trên không phải cách hợp lệ để thay tên bảng `?` bằng `ps.setString(1, "customer")`. Hãy quyết định tên bảng qua allowlist và quote identifier, rồi bind `id` bằng tham số `?` còn lại.

### 5.3. Những khác biệt giữa database/driver

- `DatabaseMetaData.getIdentifierQuoteString()` cho biết ký hiệu bao identifier; nếu trả về một dấu cách, nguồn dữ liệu báo không hỗ trợ quoted identifiers. Một số driver cần ghi đè `enquoteIdentifier` để hỗ trợ dấu bao ngoài nháy kép.
- Phương thức `default` của `Statement` có những điều kiện hợp lệ/giới hạn riêng (ví dụ có thể từ chối identifier trống, quá dài, chứa ký tự NUL hoặc dấu nháy kép đặt sai vị trí). Driver có thể dùng quy tắc chặt chẽ hoặc khác theo datasource.
- Việc quote identifier có thể ảnh hưởng đến chữ hoa/thường, tên reserved word, ký tự Unicode trong tên đối tượng và độ dài tên được database chấp nhận.
- `N'...'` và `setNString` chỉ có tác dụng theo kiểu ký tự và cú pháp SQL database thực sự hỗ trợ. Không dựa vào kết quả tạo chuỗi của JDK để khẳng định mọi server đều nhận lệnh.
- Cách database diễn giải dấu gạch chéo ngược, escape đặc biệt hoặc literal ký tự khác nhau; điều này càng củng cố việc **ưu tiên parameter binding**, thay vì tự coi `enquoteLiteral` là sanitizer toàn năng.

### 5.4. Lỗi và ngoại lệ cần xử lý

| Tình huống | Hành vi thường gặp | Cách xử lý |
| --- | --- | --- |
| Truyền `null` cho `enquoteLiteral` hoặc `enquoteNCharLiteral` | `NullPointerException` theo hợp đồng API | Sử dụng bind `setNull(...)` hoặc xử lý trạng thái không có giá trị từ trước. |
| Truyền `null` cho `enquoteIdentifier` hoặc `isSimpleIdentifier` | `NullPointerException` | Kiểm tra dữ liệu đầu vào và allowlist. |
| Identifier không hợp lệ / vượt giới hạn datasource | `SQLException` | Báo tên đối tượng không hợp lệ; không tự bỏ dấu quote hay thêm nối chuỗi tùy ý. |
| Database không hỗ trợ delimited identifier | `SQLFeatureNotSupportedException` có thể được ném | Sử dụng quy ước tên đơn giản tương thích hoặc thiết kế lại câu SQL. |
| Driver không hỗ trợ national character type | `SQLException` hoặc `SQLFeatureNotSupportedException` ở thao tác liên quan | Chọn kiểu cột, setter và driver tương thích với database. |
| SQL đã dựng đúng cú pháp nhưng database báo không có bảng | Lỗi SQL từ DB | Kiểm tra tên thật, chữ hoa/thường, schema và quyền, không nới lỏng allowlist. |

Cả `enquoteIdentifier` và `isSimpleIdentifier` đều có thể ném `SQLException`; code gọi chúng cần xử lý hoặc khai báo `throws SQLException`. Đừng nuốt ngoại lệ rồi tự nối identifier gốc vào SQL để tiếp tục truy vấn.

## 6. Các bài tập nhỏ để tự kiểm tra

1. Với `enquoteLiteral("D'Angelo")`, dự đoán `'D''Angelo'`. Giải thích vì sao Java string và SQL literal có hai lớp biểu diễn khác nhau.
2. Với `enquoteIdentifier("item name", true)` trên driver dùng nháy kép, kết quả dự kiến là `"item name"`. Tại sao nháy đơn `'item name'` lại sai ý nghĩa?
3. Với schema `sales` và bảng `order_items`, viết đúng dạng `"sales"."order_items"` bằng **hai** lần gọi `enquoteIdentifier`. So sánh với `"sales.order_items"`.
4. Với tên bảng do người dùng chọn, viết allowlist chỉ cho phép `customer` và `supplier`. Bind một giá trị `name` bằng `PreparedStatement.setString(...)` thay vì gọi `enquoteLiteral` rồi nối trực tiếp.
5. Với chuỗi Unicode cần ghi vào cột `NVARCHAR`, giải thích sự khác nhau giữa việc tạo `N'...'` bằng `enquoteNCharLiteral` và bind tham số bằng `setNString`; tra tài liệu driver để xác nhận hỗ trợ thực tế.

## 7. Checklist khi áp dụng JDBC 4.3

- [ ] Xác định rõ thành phần là **literal**, **identifier** hay **national character literal**.
- [ ] Dùng `enquoteIdentifier` cho tên đối tượng đã qua allowlist; chia riêng schema/table/column.
- [ ] Dùng `PreparedStatement` với `?` và setter thích hợp cho các giá trị đầu vào.
- [ ] Chỉ dùng `enquoteLiteral`/`enquoteNCharLiteral` khi thật sự cần sinh văn bản literal SQL và đã xác minh dialect.
- [ ] Kiểm thử quy tắc dấu trích dẫn, chữ hoa/thường, keyword, ký tự đặc biệt và giới hạn tên trên JDBC driver thực.
- [ ] Kiểm thử lỗi identifier không hợp lệ, bảng không tồn tại, quyền truy cập, và xử lý ngoại lệ có kiểm soát.
