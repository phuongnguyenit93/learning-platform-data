Nền tảng thương mại đo thời gian GC nhưng không ghi nhận tỷ lệ request timeout trong đợt thử, khiến một collector có pause ngắn hơn vẫn đi kèm lỗi nghiệp vụ cao; nhóm QA cần đánh giá đồng thời chỉ số JVM và chỉ số dịch vụ.
Ngân hàng đặt mục tiêu độ trễ thấp và giảm kích thước heap để tiết kiệm RAM trong khi chạy Generational ZGC, nhưng sau thay đổi phải thu gom thường xuyên hơn và tổng chi phí CPU tăng; nhóm kỹ thuật cần đánh giá đánh đổi giữa footprint và throughput.
Ứng dụng bảo hiểm sử dụng JFR để so Generational ZGC ở hai bản JDK, nhưng một bản đồng thời thay đổi thuật toán cache và throughput, khiến kết luận về tác dụng riêng của collector không có cơ sở; nhóm hiệu năng cần đánh giá thiết kế thực nghiệm.
Nền tảng tài chính dùng API Key Encapsulation Mechanism chuẩn từ Java 21 để thiết lập bí mật chung với đối tác, nhưng hai phía chọn thuật toán hoặc thông số khóa không tương thích và quá trình thiết lập kết nối thất bại; nhóm bảo mật cần đánh giá giao thức trao đổi khóa.
Ngân hàng tạo khóa cho KEM trên HSM thông qua provider JCA riêng, nhưng runtime mới không có provider hỗ trợ thuật toán đã thỏa thuận và dịch vụ không thể khởi tạo cơ chế đóng gói khóa; nhóm kỹ thuật cần đánh giá khả năng cung cấp thuật toán.
Nền tảng bảo hiểm trao đổi vật liệu KEM qua API nhưng một bên nhầm ciphertext được đóng gói với shared secret đã dẫn xuất và không thể giải mã bản tin tiếp theo; nhóm tích hợp cần đánh giá hợp đồng định dạng đầu ra mật mã.
Ứng dụng y tế truyền dữ liệu KEM giữa hai phiên bản ứng dụng nhưng không quản lý khóa và định danh thuật toán theo từng phiên, khiến một node mới không thể decapsulate thông tin từ node cũ; nhóm kiến trúc cần đánh giá phiên bản hóa giao thức.
Ngân hàng nâng lên Java 21 để dùng virtual threads và Sequenced Collections nhưng trong CI vẫn đặt --release 17 cho toàn bộ thư viện, khiến các lời gọi API mới bị từ chối khi biên dịch; nhóm phát hành cần đánh giá target API của artifact.
Nền tảng thương mại build ứng dụng dùng record patterns và SequencedMap trên JDK 21 rồi triển khai vào container có JDK 17, khiến classfile hoặc API cần thiết không khả dụng ở runtime; nhóm vận hành cần đánh giá phiên bản Java thực tế của image.
Ứng dụng bệnh viện thay thread pool cũ bằng virtual threads khi nâng Java 21, nhưng kiểm thử hồi quy chỉ so kết quả nghiệp vụ một request mà không kiểm tra gián đoạn, thread-local, pool database và độ trễ ở tải cao; nhóm QA cần đánh giá rủi ro nâng cấp.
Doanh nghiệp logistics sử dụng switch patterns, SequencedMap và virtual threads trong cùng một luồng xử lý, nhưng một plugin dựa vào reflection trên private JDK internals không tương thích với runtime mới và chỉ lỗi ở production; nhóm kỹ thuật cần đánh giá phụ thuộc gián tiếp.
Ngân hàng duy trì ứng dụng trên nhiều bản JDK hiện đại và giả định mọi thay đổi hiệu năng của virtual threads cùng Generational ZGC đã được giữ nguyên giữa các release, khiến biểu đồ p99 không còn so sánh được sau nâng cấp; nhóm hiệu năng cần đánh giá ma trận phiên bản.
Nền tảng bảo hiểm định nghĩa Java 21 là phiên bản tối thiểu của SDK mới, nhưng tài liệu API vẫn đưa ví dụ dùng cơ chế preview chưa ổn định và khách hàng không thể biên dịch nếu không bật chế độ đặc biệt; nhóm phát hành cần đánh giá ranh giới API chuẩn.
