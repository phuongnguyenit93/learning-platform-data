# Phân biệt định danh SQL với giá trị tham số PreparedStatement

Khi tạo câu SQL động, cần phân biệt **định danh SQL** với **giá trị dữ liệu**. Định danh là tên bảng, tên cột, schema hoặc alias; giá trị là dữ liệu được so sánh, chèn hoặc cập nhật. JDBC `PreparedStatement` dùng dấu `?` để bind giá trị tại các vị trí biểu thức mà SQL cho phép. Dấu hỏi không thể thay thế tên bảng, tên cột, từ khóa, toán tử hay hướng sắp xếp.

Vì vậy, không thể viết một truy vấn an toàn bằng cách đưa mọi phần đầu vào vào `PreparedStatement` rồi kỳ vọng driver tự hiểu phần nào là tên cột. Với giá trị, dùng parameter binding. Với định danh thay đổi theo yêu cầu, chọn từ allowlist các định danh đã được ứng dụng định nghĩa và chỉ ghép các mảnh SQL cố định đã kiểm soát.

Các quy tắc này thuộc core JDBC API và là cách sử dụng `PreparedStatement` ổn định; đây không phải API preview/incubator mới của JDK 26. Cú pháp định danh, phân trang và một số kiểu dữ liệu vẫn phụ thuộc hệ quản trị và JDBC driver đang dùng.

## 1. Phân biệt định danh, cú pháp và giá trị

SQL có nhiều loại thành phần khác nhau:

| Thành phần | Ví dụ | Có bind bằng `?` không? |
|---|---|---|
| Giá trị chuỗi | `'alice'`, `'O''Reilly'` | Có |
| Giá trị số | `42`, `19.95` | Có |
| Giá trị ngày/giờ | `DATE '2026-11-27'`, timestamp | Có |
| Giá trị trong điều kiện | `WHERE customer_id = ?` | Có |
| Giá trị cần INSERT/UPDATE | `VALUES (?, ?)`, `SET status = ?` | Có |
| Tên bảng | `FROM customer` | Không |
| Tên cột | `SELECT display_name`, `ORDER BY created_at` | Không |
| Schema hoặc alias | `sales.customer c` | Không |
| Từ khóa và hướng sắp xếp | `JOIN`, `ASC`, `DESC` | Không |
| Toán tử hoặc đoạn SQL | `LIKE`, `IS NULL`, `ON ...` | Không |

Trong truy vấn:

```sql
SELECT customer_id, display_name
FROM customer
WHERE tenant_id = ?
  AND status = ?
ORDER BY created_at DESC
```

`tenant_id`, `status`, `customer`, `display_name` và `created_at` là định danh được cố định trong câu SQL. Hai dấu `?` là vị trí giá trị sẽ được bind lúc thực thi. Hướng `DESC` là cú pháp SQL, không phải dữ liệu.

Một cách nhớ hữu ích: parameter marker đại diện cho một giá trị trong biểu thức SQL, không đại diện cho một phần của ngữ pháp SQL.

## 2. PreparedStatement bind giá trị như thế nào?

`PreparedStatement` nhận câu SQL có các parameter marker `?`. Sau khi tạo statement, ứng dụng gán giá trị theo vị trí bắt đầu từ 1 bằng các phương thức như `setString`, `setLong`, `setBigDecimal`, `setDate`, `setTimestamp` hoặc `setObject`.

Ví dụ:

```java
String sql = """
        SELECT customer_id, display_name
        FROM customer
        WHERE tenant_id = ?
          AND email = ?
        """;

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setLong(1, tenantId);
    ps.setString(2, email);

    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            long id = rs.getLong("customer_id");
            String name = rs.getString("display_name");
            // Xử lý dữ liệu trả về.
        }
    }
}
```

Giá trị `email` được truyền như dữ liệu. Nếu nó chứa dấu nháy đơn, dấu chấm phẩy hoặc chuỗi trông giống SQL, driver vẫn xử lý nó như giá trị của parameter. Không cần tự nối chuỗi, thêm dấu nháy hay thay dấu nháy đơn bằng hai dấu nháy.

Với điều kiện `LIKE`, parameter binding vẫn ngăn dữ liệu làm thay đổi cấu trúc SQL, nhưng ký tự `%` và `_` trong giá trị vẫn mang ý nghĩa wildcard của LIKE. Nếu yêu cầu tìm chuỗi literal, cần escape wildcard theo cú pháp `ESCAPE` của database thay vì nhầm rằng bind parameter sẽ vô hiệu hóa chúng.

Không làm theo cách này:

```java
// Không an toàn: input có thể thay đổi cấu trúc câu SQL.
String sql = "SELECT customer_id FROM customer WHERE email = '"
        + email + "'";
Statement statement = connection.createStatement();
ResultSet rs = statement.executeQuery(sql);
```

Và cũng không cần tự escape chuỗi rồi đưa vào SQL. Hãy để JDBC driver bind giá trị qua API.

## 3. Vì sao không thể bind tên bảng hoặc tên cột?

SQL được phân tích theo ngữ pháp trước khi các giá trị parameter được cung cấp. Ví dụ sau không có nghĩa là chọn cột có tên được truyền vào:

```java
String sql = "SELECT ? FROM customer WHERE tenant_id = ?";

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, "display_name");
    ps.setLong(2, tenantId);
}
```

Trong nhiều hệ quản trị, biểu thức `SELECT ?` trả về giá trị chuỗi hằng giống nhau cho mỗi dòng; nó không biến chuỗi `display_name` thành định danh cột. Tương tự, `FROM ?` không thể dùng để chọn bảng lúc chạy.

Một số trường hợp sai thường gặp:

```java
// Không thay thế tên bảng.
String sql1 = "SELECT * FROM ? WHERE id = ?";

// Không thay thế tên cột.
String sql2 = "SELECT id, name FROM customer ORDER BY ?";

// Không thay thế hướng sắp xếp.
String sql3 = "SELECT id, name FROM customer ORDER BY created_at ?";
```

Các câu SQL này không có ý nghĩa bind identifier/direction theo mong muốn. Driver không thể dùng giá trị bind để viết lại cấu trúc đã parse thành một câu SQL khác.

Các vị trí như tên bảng, tên cột, alias, schema, từ khóa, toán tử, loại JOIN và hướng `ASC`/`DESC` phải được xác định khi xây dựng câu SQL. Chỉ dùng mảnh cú pháp do ứng dụng kiểm soát.

## 4. Chọn định danh động bằng allowlist

Khi giao diện cho phép người dùng chọn cột sắp xếp hoặc trường lọc, hãy ánh xạ lựa chọn đó sang một tập định danh cố định. Không đưa trực tiếp chuỗi nhận từ request vào SQL.

Ví dụ với enum:

```java
enum CustomerSort {
    NAME("display_name"),
    CREATED_AT("created_at"),
    TOTAL_SPENT("total_spent");

    private final String sqlIdentifier;

    CustomerSort(String sqlIdentifier) {
        this.sqlIdentifier = sqlIdentifier;
    }

    String sqlIdentifier() {
        return sqlIdentifier;
    }
}

enum SortDirection {
    ASC("ASC"),
    DESC("DESC");

    private final String sqlToken;

    SortDirection(String sqlToken) {
        this.sqlToken = sqlToken;
    }

    String sqlToken() {
        return sqlToken;
    }
}
```

Tạo câu SQL bằng các giá trị enum đã được xác thực:

```java
String sql = """
        SELECT customer_id, display_name, created_at, total_spent
        FROM customer
        WHERE tenant_id = ?
        ORDER BY %s %s
        LIMIT ?
        """.formatted(sort.sqlIdentifier(), direction.sqlToken());

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setLong(1, tenantId);
    ps.setInt(2, pageSize);
    try (ResultSet rs = ps.executeQuery()) {
        // Đọc kết quả.
    }
}
```

Ở đây, chỉ hai mảnh đã được định nghĩa trong enum được ghép vào SQL. `tenantId` và `pageSize` vẫn được bind như giá trị. Nếu DBMS hoặc JDBC driver không hỗ trợ bind cho `LIMIT`, cần dùng cú pháp phân trang phù hợp dialect và chỉ ghép giá trị số đã được kiểm tra trong giới hạn; ưu tiên bind nếu driver hỗ trợ.

Khi parse lựa chọn từ HTTP request, hãy chuyển chuỗi sang enum một cách rõ ràng:

```java
static CustomerSort parseSort(String input) {
    return switch (input) {
        case "name" -> CustomerSort.NAME;
        case "createdAt" -> CustomerSort.CREATED_AT;
        case "totalSpent" -> CustomerSort.TOTAL_SPENT;
        default -> throw new IllegalArgumentException("Unsupported sort field");
    };
}

static SortDirection parseDirection(String input) {
    return switch (input) {
        case "asc" -> SortDirection.ASC;
        case "desc" -> SortDirection.DESC;
        default -> throw new IllegalArgumentException("Unsupported sort direction");
    };
}
```

Không dùng `input.toUpperCase()` rồi nối thẳng vào SQL. Việc chuyển chữ hoa/chữ thường không biến đầu vào tùy ý thành cú pháp đáng tin cậy.

## 5. Allowlist không thay thế kiểm tra quyền

Allowlist bảo đảm người gọi chỉ chọn được những định danh mà ứng dụng đã dự kiến. Tuy nhiên, một cột hoặc bảng hợp lệ về mặt kỹ thuật vẫn có thể chứa dữ liệu mà user hiện tại không được phép xem.

Ví dụ, ứng dụng có thể cho phép sắp xếp theo `total_spent` nhưng chỉ nhân viên thuộc nhóm tài chính được truy cập dữ liệu chi tiêu. Hãy kiểm tra quyền trên thao tác và phạm vi dữ liệu trước khi thực thi truy vấn. Phân quyền nên được áp dụng cả ở tầng ứng dụng và, khi phù hợp, bằng database role, view hoặc row-level security.

Không xây allowlist từ dữ liệu request. Danh sách phải do ứng dụng hoặc cấu hình quản trị đáng tin cậy xác định. Metadata database có thể giúp kiểm tra một bảng/cột tồn tại, nhưng việc một định danh tồn tại không có nghĩa người dùng được phép truy cập nó.

## 6. Quote identifier đúng dialect khi thực sự cần

Một số định danh chứa từ khóa SQL, ký tự đặc biệt hoặc chữ hoa/thường cần được quote theo quy tắc của hệ quản trị. JDBC cung cấp `DatabaseMetaData.getIdentifierQuoteString()` để hỏi ký tự quote identifier mà driver/database sử dụng. Giá trị trả về có thể khác nhau theo DBMS; một dấu cách đơn biểu thị việc quote identifier không được hỗ trợ.

Quote identifier là thao tác theo dialect, không phải cơ chế bind parameter và cũng không thay thế allowlist. Khi cần tạo SQL với định danh động:

1. Chọn định danh từ allowlist do ứng dụng quản lý.
2. Tách schema, table và column thành từng thành phần định danh riêng.
3. Dùng quy tắc quote/escape của dialect tương ứng nếu cần; không tự giả định mọi DB đều dùng dấu nháy kép.
4. Không đưa một chuỗi như `schema.table` vào hàm quote như một identifier đơn. Hãy quote riêng `schema` và `table`.
5. Bind mọi giá trị dữ liệu bằng `PreparedStatement` sau khi đã dựng phần cấu trúc.

Theo quy tắc SQL chuẩn, dấu nháy kép bên trong delimited identifier được biểu diễn bằng cách lặp đôi dấu nháy kép. Tuy nhiên, các DBMS có thể có quy tắc và chế độ tương thích riêng. Nên dùng thư viện/dialect layer được duy trì thay vì viết một hàm quote tổng quát rồi giả định dùng được cho mọi database.

Không coi việc quote một chuỗi tùy ý là đủ an toàn. Một identifier được quote vẫn có thể trỏ đến bảng nhạy cảm hoặc cột không được phép truy cập. Allowlist và authorization vẫn là hai kiểm soát bắt buộc.

## 7. Nhiều giá trị trong mệnh đề IN

Một parameter marker là một giá trị đơn. Câu `IN (?)` không tự mở rộng một `List` thành nhiều phần tử:

```sql
SELECT customer_id
FROM customer
WHERE customer_id IN (?)
```

Nếu bind một chuỗi `"10,20,30"`, DB xem đó là một giá trị chuỗi duy nhất, không phải ba phần tử. Với danh sách có kích thước động, tạo số lượng dấu hỏi theo kích thước danh sách rồi bind từng giá trị:

```java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

record Customer(long id, String displayName) {}

static List<Customer> findByIds(Connection connection, List<Long> ids)
        throws SQLException {
    if (ids.isEmpty()) {
        return List.of();
    }

    String markers = String.join(
            ", ",
            Collections.nCopies(ids.size(), "?"));
    String sql = """
            SELECT customer_id, display_name
            FROM customer
            WHERE customer_id IN (%s)
            """.formatted(markers);

    try (PreparedStatement ps = connection.prepareStatement(sql)) {
        for (int i = 0; i < ids.size(); i++) {
            ps.setLong(i + 1, ids.get(i));
        }

        List<Customer> result = new ArrayList<>();
        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) {
                result.add(new Customer(
                        rs.getLong("customer_id"),
                        rs.getString("display_name")));
            }
        }
        return result;
    }
}
```

Số lượng dấu hỏi ở đây chỉ phụ thuộc vào số phần tử của list; nó không chứa giá trị do người dùng nhập. Các phần tử vẫn được bind riêng bằng `setLong()`.

Xử lý list rỗng trước khi tạo SQL. Nhiều DBMS không chấp nhận `IN ()`; nếu nghiệp vụ yêu cầu list rỗng trả về không có kết quả, trả list rỗng ngay hoặc dùng một predicate luôn sai theo cách phù hợp. Với danh sách lớn, kiểm tra giới hạn số parameter của DBMS/driver và cân nhắc array parameter, temporary table, table-valued parameter hoặc bulk loading theo dialect.

## 8. Bind NULL và kiểu dữ liệu rõ ràng

Nếu parameter có thể là `null`, nên chỉ rõ SQL type khi driver hoặc database cần thông tin kiểu:

```java
ps.setNull(1, Types.VARCHAR);

// Hoặc dùng JDBCType với setObject:
ps.setObject(1, null, JDBCType.VARCHAR);
```

Với giá trị không null, chọn setter phù hợp với kiểu dữ liệu SQL:

```java
ps.setLong(1, customerId);
ps.setBigDecimal(2, amount);
ps.setDate(3, sqlDate);
ps.setTimestamp(4, timestamp);
ps.setObject(5, value, JDBCType.VARCHAR);
```

Tránh ép mọi dữ liệu thành chuỗi rồi bind bằng `setString()`. Kiểu dữ liệu rõ ràng giúp driver chuyển đổi chính xác hơn và tránh khác biệt về format số, ngày giờ, timezone hoặc collation giữa môi trường.

Khi tái sử dụng `PreparedStatement` cho nhiều lần thực thi, hãy gán đầy đủ tất cả parameter của mỗi lần chạy. Có thể gọi `clearParameters()` nếu luồng xử lý cần xóa các giá trị đang giữ trước khi bind lại; không dựa vào việc một tham số chưa gán sẽ tự nhận `null`.

## 9. Các mảnh SQL động khác cũng phải có allowlist

Ngoài tên bảng và tên cột, nhiều phần khác cũng là cú pháp chứ không phải giá trị:

- Loại phép so sánh: `=`, `<`, `LIKE`, `IS NULL`.
- Hướng sắp xếp: `ASC`, `DESC`.
- Kiểu JOIN: `INNER JOIN`, `LEFT JOIN`.
- Tên hàm, biểu thức, toán tử và các keyword.
- Mảnh điều kiện tùy chọn như một predicate hoàn chỉnh.

Nếu cần cho phép nhiều kiểu lọc, ánh xạ lựa chọn sang các nhánh SQL cố định:

```java
String predicate = switch (filterMode) {
    case EXACT -> "status = ?";
    case PREFIX -> "status LIKE ?";
    case MISSING -> "status IS NULL";
};

String sql = "SELECT id, status FROM job WHERE " + predicate;
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    switch (filterMode) {
        case EXACT -> ps.setString(1, value);
        case PREFIX -> ps.setString(1, value + "%");
        case MISSING -> {
            // Không có parameter trong predicate này.
        }
    }
    // Thực thi và đọc kết quả.
}
```

Mỗi nhánh chọn một predicate do code định nghĩa. Giá trị của điều kiện vẫn được bind. Nếu nghiệp vụ cần hỗ trợ nhiều bộ lọc tùy chọn, nên xây một query builder có API theo kiểu dữ liệu và allowlist rõ ràng thay vì ghép chuỗi request trực tiếp.

## 10. PreparedStatement không phải bộ lọc mọi SQL injection

`PreparedStatement` bảo vệ giá trị được bind. Nó không tự bảo vệ các mảnh SQL mà ứng dụng đã nối trực tiếp vào câu query. Đoạn mã sau vẫn có lỗ hổng:

```java
String table = request.getParameter("table");
String sql = "SELECT * FROM " + table + " WHERE tenant_id = ?";

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setLong(1, tenantId);
    // Table name vẫn do request điều khiển.
}
```

Parameter `tenantId` được bind an toàn, nhưng `table` vẫn có thể làm thay đổi cấu trúc SQL. Cách sửa là map lựa chọn sang identifier cố định:

```java
enum ReportSource {
    ACTIVE("active_customer"),
    ARCHIVED("archived_customer");

    final String table;

    ReportSource(String table) {
        this.table = table;
    }
}

String sql = "SELECT customer_id FROM " + source.table + " WHERE tenant_id = ?";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setLong(1, tenantId);
    // Thực thi.
}
```

Đầu vào cần được parse thành `ReportSource` trước khi đến đoạn dựng SQL; không khởi tạo enum hoặc map bằng giá trị bất kỳ từ request. Ngoài ra, kiểm tra quyền truy cập dữ liệu của người gọi và tenant vẫn phải được thực hiện.

## 11. Kiểm thử ranh giới giữa identifier và value

Khi kiểm thử truy vấn động, nên xác nhận cả câu SQL lẫn các giá trị được bind:

1. Giá trị chứa dấu nháy đơn, dấu chấm phẩy, comment marker hoặc chuỗi như `' OR 1=1 --` được xử lý như dữ liệu và không làm thay đổi số dòng trả về ngoài điều kiện nghiệp vụ.
2. Lựa chọn tên cột hợp lệ chỉ ánh xạ sang một identifier trong allowlist.
3. Tên bảng/cột không có trong allowlist bị từ chối trước khi gọi `prepareStatement()`.
4. Chuỗi `ASC; DROP TABLE ...` không thể được chấp nhận như một hướng sắp xếp.
5. List rỗng, list một phần tử, list nhiều phần tử và list vượt giới hạn parameter đều có hành vi được định nghĩa.
6. Parameter `null` có SQL type rõ ràng khi cần.
7. User không có quyền không thể truy vấn một bảng/cột chỉ vì identifier đó nằm trong allowlist chung.

Ví dụ test giá trị trông giống payload SQL:

```java
String suspiciousValue = "' OR 1=1 --";
try (PreparedStatement ps = connection.prepareStatement(
        "SELECT customer_id FROM customer WHERE email = ?")) {
    ps.setString(1, suspiciousValue);
    try (ResultSet rs = ps.executeQuery()) {
        // Chỉ tìm bản ghi có email đúng bằng chuỗi suspiciousValue.
        // Không biến payload thành một mệnh đề OR.
    }
}
```

Trong test tích hợp, có thể ghi nhận SQL template và số lượng parameter để kiểm tra câu SQL không thay đổi cấu trúc theo giá trị đầu vào. Tránh log toàn bộ giá trị parameter trong production nếu chúng chứa email, token, thông tin cá nhân hoặc bí mật.

## 12. Ranh giới JDBC và thư viện query

JDBC chuẩn sử dụng positional parameter marker `?` trong `PreparedStatement`. Tên tham số kiểu `:tenantId` không thuộc cú pháp JDBC core. Framework như Spring `NamedParameterJdbcTemplate` có thể chuyển named parameter thành các dấu `?` và bind giá trị tương ứng, nhưng cũng không làm tên bảng/cột trở thành parameter có thể bind.

Query builder hoặc ORM có thể cung cấp API an toàn để chọn thuộc tính entity, sort field hoặc table mapping. Vẫn cần kiểm tra cách thư viện tạo SQL: lựa chọn động phải đi qua metadata/mapping do ứng dụng kiểm soát, còn giá trị phải được bind. Không giả định rằng mọi API nhận `String` của ORM đều tự chống SQL injection.

Việc driver có dùng server-side prepared statement, cache execution plan hay mô phỏng parameter binding ở client là chi tiết implementation và cấu hình. Không nên hứa rằng `PreparedStatement` luôn tạo một execution plan server được lưu lâu dài. Lợi ích cốt lõi là API tách SQL template khỏi giá trị parameter và cho driver xử lý giá trị theo giao thức/implementation phù hợp.

## 13. Những điểm cần nhớ

- `PreparedStatement` bind giá trị biểu thức qua `?`; parameter index bắt đầu từ 1.
- Không thể bind table, schema, column, alias, keyword, operator, JOIN type hoặc `ASC`/`DESC` bằng parameter marker.
- Với identifier động, parse lựa chọn thành enum/map allowlist rồi chỉ ghép mảnh SQL do ứng dụng định nghĩa.
- Allowlist không thay thế authorization; người dùng vẫn phải được cấp quyền với bảng/cột và phạm vi dữ liệu.
- Quote identifier theo dialect chỉ xử lý cách biểu diễn tên; nó không biến input tùy ý thành an toàn và không thay thế allowlist.
- Một `?` trong `IN (?)` là một giá trị đơn; tạo marker theo số phần tử rồi bind từng phần tử.
- Bind `NULL` với SQL type rõ ràng khi cần; dùng setter đúng kiểu cho số, ngày giờ, chuỗi và dữ liệu khác.
- `PreparedStatement` không bảo vệ các đoạn SQL đã được nối từ input không tin cậy.
- JDBC named parameter không có trong core API; framework có thể chuyển chúng thành positional parameters nhưng vẫn chỉ bind giá trị.
