# HTTP/3 không tự được chọn khi dùng cấu hình mặc định

Java 26 bổ sung hỗ trợ HTTP/3 cho `java.net.http.HttpClient` thông qua JEP 517. Đây là API chính thức, đã hoàn tất trong JDK 26; không phải tính năng preview hay incubator. Tuy nhiên, việc JDK có thể gửi HTTP/3 không làm cho các ứng dụng hiện có tự chuyển sang giao thức này. `HttpClient` vẫn ưu tiên HTTP/2 khi dùng cấu hình mặc định. Ứng dụng cần chủ động chọn HTTP/3 và kiểm tra phiên bản giao thức thực sự được dùng.

## 1. Cấu hình mặc định vẫn ưu tiên HTTP/2

Các cách tạo client sau đều dùng cấu hình mặc định:

```java
HttpClient client1 = HttpClient.newHttpClient();

HttpClient client2 = HttpClient.newBuilder()
        .build();
```

Hai cách tương đương về thiết lập mặc định. `HttpClient.newHttpClient()` tạo client với ưu tiên HTTP/2; `HttpClient.Builder.version()` cũng ghi rõ rằng nếu không gọi phương thức này trước khi `build()`, client mới sẽ ưu tiên HTTP/2.

Điều đó có nghĩa:

- Ứng dụng đang dùng `HttpClient.newHttpClient()` hoặc `HttpClient.newBuilder().build()` không tự động chuyển sang HTTP/3 chỉ vì nâng JDK lên Java 26.
- HTTP/2 là phiên bản được ưu tiên, không phải cam kết rằng mọi phản hồi đều dùng HTTP/2. Nếu máy chủ hoặc điều kiện kết nối không đáp ứng HTTP/2, client có thể sử dụng HTTP/1.1.
- `client.version()` trả về phiên bản ưu tiên đã cấu hình. Nó không xác nhận giao thức thực tế của một response.

Có thể quan sát giá trị ưu tiên mặc định:

```java
HttpClient client = HttpClient.newHttpClient();

System.out.println(client.version());
// HTTP_2
```

Đây là hành vi tương thích quan trọng khi nâng cấp ứng dụng cũ: code không đặt phiên bản vẫn giữ lựa chọn ưu tiên HTTP/2. Java 26 mở rộng khả năng của HTTP Client, không âm thầm thay đổi lựa chọn mặc định.

## 2. Vì sao HTTP/3 không được bật mặc định?

HTTP/1.1 và HTTP/2 thường chạy trên TCP. HTTP/3 chạy trên QUIC, một giao thức truyền tải dựa trên UDP. Vì vậy, client không thể đơn giản nâng cấp một kết nối TCP đang có thành kết nối HTTP/3. Nó phải thiết lập hoặc khám phá một đường kết nối QUIC riêng.

Khả năng kết nối HTTP/3 còn phụ thuộc nhiều điều kiện bên ngoài ứng dụng:

- Máy chủ, reverse proxy hoặc CDN phải cung cấp HTTP/3 trên endpoint phù hợp.
- Đường mạng phải cho phép lưu lượng QUIC/UDP đi qua. Firewall, NAT, mạng doanh nghiệp hoặc thiết bị trung gian có thể chặn UDP.
- URI phải dùng HTTPS. JDK built-in `HttpClient` không gửi request có URI scheme `http` qua HTTP/3.
- JDK built-in `HttpClient` không hỗ trợ HTTP/3 khi request được định tuyến qua proxy.
- Cấu hình TLS tùy chỉnh, chẳng hạn `SSLContext` hoặc `SSLParameters`, phải tương thích với cách triển khai QUIC của client.

Vì mức độ hỗ trợ HTTP/3 của máy chủ và mạng không đồng đều, giữ HTTP/2 làm mặc định giúp ứng dụng tiếp tục hoạt động với các endpoint và môi trường mạng hiện có. Khi ứng dụng chủ động chọn HTTP/3, client mới thực hiện cơ chế khám phá và lựa chọn kết nối HTTP/3.

## 3. Chọn HTTP/3 ở cấp HttpClient hoặc HttpRequest

API `HttpClient.Version.HTTP_3` được thêm từ Java 26. Có hai vị trí để đặt phiên bản ưu tiên.

**Đặt ở cấp client** khi phần lớn request gửi qua client nên ưu tiên HTTP/3:

```java
HttpClient client = HttpClient.newBuilder()
        .version(HttpClient.Version.HTTP_3)
        .build();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com/"))
        .GET()
        .build();
```

Các request không tự đặt phiên bản sẽ kế thừa lựa chọn ưu tiên của client.

**Đặt ở cấp request** khi chỉ một số endpoint cần ưu tiên HTTP/3, còn các request khác vẫn dùng cấu hình chung của client:

```java
HttpClient client = HttpClient.newHttpClient();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com/"))
        .version(HttpClient.Version.HTTP_3)
        .GET()
        .build();
```

Nếu request đã đặt phiên bản riêng, lựa chọn đó được dùng cho request; nếu không, request dùng phiên bản ưu tiên của client. Cách cấu hình theo request hữu ích khi một ứng dụng gọi nhiều dịch vụ với năng lực giao thức khác nhau.

Cả hai cách đều đặt **phiên bản ưu tiên**. Chúng không khẳng định rằng response chắc chắn sẽ dùng HTTP/3. Với chế độ khám phá mặc định, client có thể sử dụng HTTP/2 hoặc HTTP/1.1 nếu kết nối HTTP/3 không được thiết lập thành công.

## 4. Kiểm tra giao thức thực tế từ HttpResponse

Để biết request đã dùng giao thức nào, đọc `HttpResponse.version()` sau khi gửi request:

```java
import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;

public class Http3Example {
    public static void main(String[] args)
            throws IOException, InterruptedException {

        URI uri = URI.create(
                args.length == 0 ? "https://example.com/" : args[0]
        );

        HttpClient client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(10))
                .version(HttpClient.Version.HTTP_3)
                .build();

        HttpRequest request = HttpRequest.newBuilder(uri)
                .timeout(Duration.ofSeconds(20))
                .GET()
                .build();

        HttpResponse<String> response = client.send(
                request,
                HttpResponse.BodyHandlers.ofString()
        );

        System.out.println("Phiên bản ưu tiên: " + client.version());
        System.out.println("Phiên bản thực tế: " + response.version());
        System.out.println("HTTP status: " + response.statusCode());
    }
}
```

Kết quả có thể cho thấy:

```text
Phiên bản ưu tiên: HTTP_3
Phiên bản thực tế: HTTP_2
HTTP status: 200
```

Đây là kết quả hợp lệ: ứng dụng yêu cầu ưu tiên HTTP/3, nhưng cơ chế khám phá đã thiết lập được kết nối HTTP/2 trước. Trên một máy chủ, mạng và cấu hình hỗ trợ HTTP/3, response có thể trả về `HTTP_3`. Không nên dùng `client.version()` để ghi nhận giao thức thực tế, vì phương thức này chỉ phản ánh cấu hình ưu tiên.

Khi cần quan sát trong production, hãy ghi nhận `response.version()` cùng hostname, thời gian kết nối, trạng thái HTTP và lỗi mạng. Việc theo dõi theo từng endpoint giúp phân biệt máy chủ chưa hỗ trợ HTTP/3, mạng chặn QUIC và trường hợp client chủ động dùng HTTP/2 theo chính sách.

## 5. Cơ chế khám phá HTTP/3

Khi HTTP/3 đã được chọn làm phiên bản ưu tiên ở client hoặc request, JDK built-in `HttpClient` sử dụng `HttpOption.H3_DISCOVERY` để điều chỉnh cách tìm hoặc thiết lập kết nối. Nếu không đặt tùy chọn này, chế độ `HttpOption.Http3DiscoveryMode.ANY` được dùng.

| Chế độ | Cách hoạt động | Khi nào phù hợp |
|---|---|---|
| `ANY` | Client tự chọn thuật toán. Có thể thử kết nối HTTP/3 qua QUIC và HTTP qua TLS/TCP; kết nối nào thành công trước có thể được dùng. | Muốn client tự tìm đường kết nối phù hợp, chấp nhận response có thể là HTTP/2 hoặc HTTP/1.1. |
| `ALT_SVC` | Chỉ dùng thông tin HTTP Alternative Services để tìm endpoint HTTP/3. Cho đến khi máy chủ quảng bá dịch vụ `h3`, request có thể tiếp tục dùng HTTP/2 hoặc HTTP/1.1. | Muốn ưu tiên khả năng tương thích và chỉ chuyển sang HTTP/3 sau khi máy chủ thông báo endpoint hỗ trợ. |
| `HTTP_3_URI_ONLY` | Chỉ thử HTTP/3 tại đúng host và port trong URI; không dùng Alt-Svc và không chuyển sang HTTP/2 hoặc HTTP/1.1. | Chỉ dùng HTTP/3 là yêu cầu bắt buộc, chẳng hạn trong kiểm thử endpoint HTTP/3. |

### Chế độ ANY: tự tìm đường kết nối

Đây là chế độ mặc định khi HTTP/3 được bật nhưng request không chỉ định `H3_DISCOVERY`. Với một origin chưa có kết nối hoặc thông tin khám phá trước đó, implementation có thể thử cả kết nối QUIC/HTTP/3 và kết nối TLS/TCP. Kết nối thành công trước có thể quyết định phiên bản response.

Nếu request đặt HTTP/3 làm phiên bản ưu tiên, implementation có thể ưu tiên thử HTTP/3 trước. Tuy nhiên, `ANY` vẫn cho phép sử dụng giao thức khác khi phù hợp. Vì thế, đây là chế độ phù hợp cho ứng dụng cần khả năng chuyển đổi linh hoạt, không phải cách ép mọi response phải là HTTP/3.

### Chế độ ALT_SVC: đợi máy chủ quảng bá HTTP/3

HTTP Alternative Services là cơ chế để một origin thông báo rằng tài nguyên của nó cũng có thể được phục vụ qua endpoint khác. Máy chủ có thể gửi header `Alt-Svc` với giao thức `h3` để quảng bá khả năng HTTP/3.

Ví dụ header:

```http
Alt-Svc: h3=":443"; ma=86400
```

Với `ALT_SVC`, client dùng HTTP/1.1 hoặc HTTP/2 cho đến khi nhận được thông tin `h3` phù hợp. Những request tiếp theo có thể sử dụng endpoint HTTP/3 đã được quảng bá. Nếu máy chủ không gửi thông tin này, request vẫn có thể dùng HTTP/1.1 hoặc HTTP/2.

Cấu hình ở cấp request:

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpOption;
import java.net.http.HttpRequest;

HttpClient client = HttpClient.newHttpClient();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com/"))
        .version(HttpClient.Version.HTTP_3)
        .setOption(
                HttpOption.H3_DISCOVERY,
                HttpOption.Http3DiscoveryMode.ALT_SVC
        )
        .GET()
        .build();
```

Lưu ý: `H3_DISCOVERY` chỉ có tác dụng khi HTTP/3 đã được đặt làm phiên bản ưu tiên ở cấp client hoặc request. Chỉ thêm `H3_DISCOVERY` trong khi cả hai vẫn ưu tiên HTTP/2 sẽ không kích hoạt HTTP/3.

### Chế độ HTTP_3_URI_ONLY: chỉ chấp nhận HTTP/3

Khi cần xác minh một endpoint có thể phục vụ HTTP/3 trực tiếp hay không, có thể dùng:

```java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com/"))
        .version(HttpClient.Version.HTTP_3)
        .setOption(
                HttpOption.H3_DISCOVERY,
                HttpOption.Http3DiscoveryMode.HTTP_3_URI_ONLY
        )
        .GET()
        .build();
```

Ở chế độ này, máy chủ phải lắng nghe HTTP/3 qua QUIC tại đúng host và port trong URI. Client không tìm endpoint thay thế bằng Alt-Svc. Nếu máy chủ không phục vụ HTTP/3 ở địa chỉ đó hoặc kết nối QUIC không thành công, request thất bại thay vì chuyển sang HTTP/2/HTTP/1.1.

Chế độ này cũng không tương thích với proxy trong implementation tích hợp của JDK. Chỉ dùng khi hệ thống mạng và endpoint đã được cấu hình để hỗ trợ kết nối HTTP/3 trực tiếp.

## 6. Điều kiện và giới hạn cần kiểm tra

| Điều kiện | Ảnh hưởng |
|---|---|
| JDK | `HttpClient.Version.HTTP_3` và `HttpOption.H3_DISCOVERY` có từ Java 26. Biên dịch ví dụ bằng JDK 26 trở lên. |
| URI | HTTP/3 chỉ được dùng với URI scheme `https`. |
| Máy chủ | Máy chủ, reverse proxy hoặc CDN phải cung cấp HTTP/3/QUIC trên endpoint phù hợp. |
| Mạng | Đường truyền phải cho phép QUIC qua UDP. Nếu UDP bị chặn, `ANY` có thể dùng đường TCP khi kết nối đó thành công; `HTTP_3_URI_ONLY` sẽ thất bại. |
| Proxy | JDK built-in `HttpClient` không dùng HTTP/3 khi một proxy được chọn. Với `ANY` hoặc `ALT_SVC`, giao thức có thể hạ xuống HTTP/2 hoặc HTTP/1.1; `HTTP_3_URI_ONLY` làm request thất bại. |
| TLS | `SSLContext` hoặc `SSLParameters` tùy chỉnh có thể không đáp ứng yêu cầu của QUIC. Khi đó có thể gặp `UnsupportedProtocolVersionException`. |
| Implementation | `HttpOption` là gợi ý cấu hình cho implementation. JDK built-in `HttpClient` hiểu `H3_DISCOVERY`; implementation khác có thể bỏ qua gợi ý hoặc từ chối request. |

HTTP/3 dùng QUIC, còn QUIC dựa trên UDP và tích hợp bảo mật TLS 1.3. Do đó, kiểm tra cấu hình HTTP/TCP đơn thuần chưa đủ để xác nhận HTTP/3 hoạt động. Hãy kiểm tra firewall, load balancer, chính sách outbound UDP, TLS và endpoint công khai của dịch vụ.

Khi cấu hình TLS riêng, không tự đặt các tham số giao thức ứng dụng nội bộ mà `HttpClient` quản lý, chẳng hạn danh sách ALPN, với kỳ vọng chúng sẽ ép được HTTP/3. Tài liệu API cảnh báo một số tham số nội bộ như application protocol list có thể bị bỏ qua. Nếu dùng `SSLContext` hoặc `SSLParameters` riêng, cần thử trên JDK đích và xử lý `UnsupportedProtocolVersionException`.

## 7. Lựa chọn cách cấu hình trong ứng dụng thực tế

- **Ứng dụng gọi nhiều API với hạ tầng không đồng nhất:** giữ cấu hình HTTP/2 mặc định hoặc chỉ bật HTTP/3 cho từng request đã xác minh. Đọc `response.version()` để biết giao thức thực tế.
- **Dịch vụ đã hỗ trợ HTTP/3 nhưng còn nhiều client/mạng khác nhau:** đặt HTTP/3 làm ưu tiên và dùng `ANY` để client lựa chọn kết nối có thể thiết lập.
- **Máy chủ công bố HTTP/3 qua Alt-Svc:** cân nhắc `ALT_SVC` để request đầu tiên tiếp tục dùng HTTP/2/HTTP/1.1, sau đó chuyển sang endpoint HTTP/3 khi có thông tin quảng bá.
- **Kiểm thử khả năng HTTP/3 thuần:** dùng `HTTP_3_URI_ONLY` và xác nhận request thất bại nếu không có endpoint HTTP/3 trực tiếp. Đây là chế độ kiểm thử tính bắt buộc, không phải mặc định tốt cho ứng dụng cần độ sẵn sàng cao.
- **Môi trường bắt buộc đi qua proxy:** kiểm tra chính sách mạng và lựa chọn HTTP client có hỗ trợ HTTP/3 qua kiến trúc proxy tương ứng, hoặc tiếp tục sử dụng HTTP/2/HTTP/1.1 với JDK built-in client.

Không nên đánh giá HTTP/3 chỉ qua một lần gọi hoặc một chỉ số tốc độ. Hãy benchmark cùng endpoint, payload, TLS, số request đồng thời, thời gian kết nối mới và kết nối được tái sử dụng. Ghi nhận cả tỷ lệ request thực sự dùng `HTTP_3` và các trường hợp fallback để biết lợi ích có xuất hiện trong môi trường vận hành hay không.

## 8. Quy trình kiểm chứng khi triển khai

1. **Xác nhận JDK:** dùng JDK 26 trở lên để biên dịch và chạy; HTTP/3 trong `java.net.http` là API ổn định nên không bật `--enable-preview` và không thêm module incubator.
2. **Kiểm tra mặc định:** tạo `HttpClient.newHttpClient()` và đọc `client.version()`. Kết quả mặc định là `HTTP_2`.
3. **Chọn phạm vi:** quyết định đặt `HTTP_3` ở cấp client hay từng request. Chỉ bật discovery sau khi đã đặt phiên bản ưu tiên HTTP/3.
4. **Kiểm tra endpoint:** xác nhận HTTPS, khả năng QUIC/UDP, endpoint HTTP/3 và thông tin Alt-Svc nếu dùng chế độ đó.
5. **Kiểm tra đường mạng:** xác nhận proxy selector, firewall, NAT và các thiết bị trung gian. Không mặc định rằng request đi trực tiếp nếu ứng dụng chưa cấu hình proxy rõ ràng; client có thể dùng proxy selector mặc định của hệ thống.
6. **Xác minh response:** ghi nhận `response.version()`, status và lỗi. Phân biệt response dùng HTTP/2 do fallback với lỗi kết nối hoàn toàn.
7. **Đánh giá trước khi mở rộng:** benchmark và theo dõi trên môi trường đại diện; giữ phương án tương thích với HTTP/2/HTTP/1.1 khi yêu cầu dịch vụ cho phép.
