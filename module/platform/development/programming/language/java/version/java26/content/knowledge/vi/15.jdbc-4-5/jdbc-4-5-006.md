# try-with-resources cùng thứ tự đóng Connection, Statement và ResultSet

Trong JDBC, một truy vấn thường tạo ra chuỗi tài nguyên phụ thuộc nhau: ứng dụng mở **Connection**, tạo **Statement** hoặc **PreparedStatement** từ connection, rồi thực thi để nhận **ResultSet**. Khi kết thúc, cần giải phóng theo thứ tự ngược với lúc tạo: đóng **ResultSet** trước, tiếp đến **Statement**, cuối cùng là **Connection**.

**Connection**, **Statement** và **ResultSet** đều triển khai **AutoCloseable**, vì vậy Java có thể tự gọi **close()** bằng try-with-resources. Cấu trúc này bảo đảm tài nguyên được đóng cả khi đọc dữ liệu thành công, câu SQL lỗi, code trong thân **try** ném exception hoặc bước khởi tạo một tài nguyên phía sau thất bại.

JDBC 4.5 là phiên bản API trong Java SE 26. Tuy nhiên, try-with-resources không phải tính năng mới của JDBC 4.5: đây là cú pháp Java từ Java 7, dựa trên **AutoCloseable**. Nó vẫn là cách hiện hành để quản lý vòng đời tài nguyên JDBC; bài học tập trung vào thứ tự đóng, phạm vi sở hữu và cách xử lý exception khi đóng.

## 1. Quan hệ phụ thuộc giữa ba tài nguyên

Một truy vấn đọc dữ liệu thường đi qua ba bước:

1. Lấy **Connection** từ **DataSource**.
2. Tạo **Statement** hoặc **PreparedStatement** trên connection đó.
3. Thực thi câu lệnh để nhận **ResultSet**.

**ResultSet** phụ thuộc vào statement đã tạo ra nó. Statement lại phụ thuộc vào connection. Vì vậy, vòng đời hợp lý là:

~~~text
Mở Connection
    |
    v
Tạo Statement / PreparedStatement
    |
    v
Thực thi SQL, nhận ResultSet
    |
    v
Đọc và ánh xạ từng hàng
    |
    v
Đóng ResultSet
    |
    v
Đóng Statement
    |
    v
Đóng Connection
~~~

Thứ tự đóng là thứ tự ngược của thứ tự khởi tạo. Khi statement đóng, result set hiện tại do statement tạo ra cũng được đóng. Dù vậy, khai báo **ResultSet** thành resource riêng giúp phạm vi sử dụng và thời điểm đóng của nó rõ ràng, đồng thời bảo đảm result set được đóng trước statement.

## 2. Vì sao dùng try-with-resources?

Các interface JDBC liên quan đều có **close()** và kế thừa **AutoCloseable**:

| Tài nguyên | API đóng | Tác dụng |
|---|---|---|
| **ResultSet** | **close()** | Giải phóng tài nguyên JDBC/database gắn với kết quả truy vấn |
| **Statement / PreparedStatement** | **close()** | Giải phóng statement; result set hiện tại do statement tạo cũng đóng |
| **Connection** | **close()** | Giải phóng connection và tài nguyên JDBC liên quan; với connection lấy từ pool, thường trả logical connection về pool |

Try-with-resources tự gọi **close()** khi rời khỏi block, kể cả khi thân **try** kết thúc bằng exception. Không cần viết **finally** để kiểm tra null và đóng từng đối tượng.

Ví dụ cơ bản:

~~~java
try (Connection connection = dataSource.getConnection();
     PreparedStatement statement =
         connection.prepareStatement(
             "SELECT id, display_name FROM customer");
     ResultSet resultSet = statement.executeQuery()) {

    while (resultSet.next()) {
        System.out.println(resultSet.getLong("id"));
    }
}
~~~

Các resource được khởi tạo từ trái sang phải:

1. **connection** được mở.
2. **statement** được tạo trên **connection**.
3. **resultSet** được tạo từ **statement**.

Khi rời block, Java đóng theo chiều ngược lại: **resultSet**, **statement**, rồi **connection**.

Nếu **prepareStatement()** thất bại, connection đã mở vẫn được đóng. Nếu **executeQuery()** thất bại, statement và connection đã tạo cũng được đóng. Nếu code trong block ném exception, cả ba resource vẫn được đóng theo thứ tự ngược.

## 3. Ví dụ đầy đủ: đọc dữ liệu và ánh xạ trước khi đóng

Không trả **ResultSet** ra ngoài block vì nó sẽ bị đóng cùng statement. Hãy đọc các hàng và chuyển thành đối tượng ứng dụng ngay trong phạm vi tài nguyên còn mở.

~~~java
import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

record Customer(long id, String displayName) { }

public final class CustomerRepository {
    private static final String FIND_ALL = """
        SELECT id, display_name
        FROM customer
        ORDER BY id
        """;

    private final DataSource dataSource;

    public CustomerRepository(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public List<Customer> findAll() throws SQLException {
        List<Customer> customers = new ArrayList<>();

        try (Connection connection = dataSource.getConnection();
             PreparedStatement statement =
                 connection.prepareStatement(FIND_ALL);
             ResultSet resultSet = statement.executeQuery()) {

            while (resultSet.next()) {
                customers.add(new Customer(
                    resultSet.getLong("id"),
                    resultSet.getString("display_name")
                ));
            }
        }

        return List.copyOf(customers);
    }
}
~~~

Sau khi block kết thúc, **ResultSet**, **PreparedStatement** và **Connection** đã được đóng. Danh sách kết quả chỉ chứa dữ liệu Java đã ánh xạ, nên caller không phụ thuộc vào connection hoặc cursor của database.

**List.copyOf()** tạo danh sách không sửa được từ dữ liệu đã đọc. Đây là lựa chọn thiết kế của ví dụ, không phải yêu cầu bắt buộc của JDBC.

### 3.1. Dùng tham số trong PreparedStatement

Khi câu SQL cần tham số, có thể dùng block ngoài cho connection/statement và block lồng bên trong cho result set:

~~~java
public Customer findById(long id) throws SQLException {
    String sql = """
        SELECT id, display_name
        FROM customer
        WHERE id = ?
        """;

    try (Connection connection = dataSource.getConnection();
         PreparedStatement statement =
             connection.prepareStatement(sql)) {

        statement.setLong(1, id);

        try (ResultSet resultSet = statement.executeQuery()) {
            if (!resultSet.next()) {
                return null;
            }

            return new Customer(
                resultSet.getLong("id"),
                resultSet.getString("display_name")
            );
        }
    }
}
~~~

Khi thoát block trong, **ResultSet** đóng trước. Sau đó block ngoài đóng **PreparedStatement** rồi **Connection**. Cách viết này cũng làm rõ rằng **ResultSet** chỉ tồn tại trong thời gian cần đọc dữ liệu.

Dùng placeholder **?** và setter phù hợp với kiểu dữ liệu để truyền giá trị. Không nối trực tiếp dữ liệu người dùng vào SQL string.

## 4. Quy tắc đóng ngược thứ tự khi khai báo nhiều resource

Với một try-with-resources có nhiều khai báo, Java:

- Khởi tạo resource theo thứ tự từ trái sang phải.
- Nếu khởi tạo một resource thất bại, đóng các resource đã khởi tạo trước đó theo thứ tự ngược.
- Khi thân **try** kết thúc, đóng tất cả resource theo thứ tự ngược khai báo.

| Thứ tự khai báo | Thời điểm đóng |
|---|---|
| **Connection connection** | Thứ ba |
| **PreparedStatement statement** | Thứ hai |
| **ResultSet resultSet** | Đầu tiên |

Không đảo thứ tự khai báo thành **ResultSet**, **Statement**, **Connection**; result set cần statement để được tạo và statement cần connection. Khai báo theo thứ tự phụ thuộc tự nhiên rồi để try-with-resources tự đóng ngược.

Có thể dùng các block lồng nhau thay vì một resource header dài. Hai cách có cùng nguyên tắc vòng đời:

~~~java
try (Connection connection = dataSource.getConnection()) {
    try (PreparedStatement statement =
             connection.prepareStatement(sql)) {
        try (ResultSet resultSet = statement.executeQuery()) {
            // Đọc dữ liệu ở đây.
        }
    }
}
~~~

Chọn cách khai báo một header khi các resource có cùng phạm vi sử dụng. Chọn block lồng nhau khi một tài nguyên chỉ cần tồn tại trong một đoạn xử lý nhỏ hơn, ví dụ connection và statement được dùng cho nhiều truy vấn nhưng mỗi result set chỉ sống trong một lần đọc.

## 5. Statement đóng ResultSet như thế nào?

Theo hợp đồng JDBC, **Statement.close()** đóng result set hiện tại nếu statement có một result set đang mở. Các phương thức thực thi khác của cùng statement cũng có thể đóng result set hiện tại trước khi trả kết quả mới.

Điều đó không có nghĩa nên bỏ qua việc quản lý **ResultSet**:

- Khai báo result set riêng trong try-with-resources làm rõ phạm vi đọc dữ liệu.
- Result set được đóng ngay khi kết thúc block đọc, ngay cả khi statement còn được dùng tiếp.
- Statement chỉ đóng sau khi result set đã được giải phóng.
- Không giữ result set để dùng sau khi statement hoặc connection đã đóng.

Ví dụ statement được tái sử dụng cho hai truy vấn:

~~~java
try (Connection connection = dataSource.getConnection();
     PreparedStatement statement =
         connection.prepareStatement(
             "SELECT id, display_name FROM customer WHERE id = ?")) {

    statement.setLong(1, 10L);
    try (ResultSet first = statement.executeQuery()) {
        if (first.next()) {
            System.out.println(first.getString("display_name"));
        }
    }

    statement.setLong(1, 20L);
    try (ResultSet second = statement.executeQuery()) {
        if (second.next()) {
            System.out.println(second.getString("display_name"));
        }
    }
}
~~~

Mỗi result set được đóng trước khi statement chạy truy vấn tiếp theo. Cuối cùng statement đóng rồi connection đóng.

Lưu ý: đóng **ResultSet** không tự gọi **free()** trên các đối tượng **Blob**, **Clob** hoặc **NClob** được lấy từ result set. Nếu ứng dụng lấy và giữ các đối tượng này, hãy giải phóng chúng theo hợp đồng **free()** và thời gian sống được JDBC driver hỗ trợ.

## 6. Điều gì xảy ra khi nhiều thao tác close cùng ném exception?

**close()** của các interface JDBC có thể ném **SQLException**. Try-with-resources vẫn tiếp tục đóng các resource còn lại nếu một lần đóng thất bại.

Quy tắc exception:

- Nếu thân **try** đã ném exception, exception đó tiếp tục là exception chính.
- Exception phát sinh trong quá trình **close()** được gắn vào exception chính dưới dạng suppressed exception.
- Nếu thân **try** kết thúc bình thường nhưng một hoặc nhiều lần **close()** thất bại, exception từ lần đóng đầu tiên theo thứ tự đóng trở thành exception chính; các lỗi đóng tiếp theo là suppressed exception.

Với thứ tự khai báo **Connection**, **Statement**, **ResultSet**, nếu cả ba lần đóng đều thất bại thì lỗi đóng **ResultSet** là lỗi đóng đầu tiên. JVM vẫn tiếp tục thử đóng **Statement** và **Connection**; lỗi sau được lưu trong **getSuppressed()**.

Có thể ghi log các lỗi phụ khi cần điều tra:

~~~java
try {
    readCustomers();
} catch (SQLException e) {
    logger.error("JDBC operation failed", e);

    for (Throwable suppressed : e.getSuppressed()) {
        logger.warn("Additional failure while closing JDBC resource",
                    suppressed);
    }

    throw e;
}
~~~

Không bắt rồi bỏ qua exception từ **close()**. Lỗi đóng connection có thể cho thấy connection không được trả về pool đúng cách hoặc driver gặp sự cố khi giải phóng tài nguyên.

## 7. Khởi tạo resource thất bại giữa chừng

Try-with-resources xử lý cả trường hợp chưa tạo đủ ba tài nguyên.

| Điểm lỗi | Resource đã được tạo | Resource được đóng |
|---|---|---|
| **dataSource.getConnection()** lỗi | Không có | Không có gì cần đóng |
| **connection.prepareStatement()** lỗi | Connection | Connection |
| **statement.executeQuery()** lỗi | Connection, Statement | Statement rồi Connection |
| Code đọc hàng trong block lỗi | Connection, Statement, ResultSet | ResultSet, Statement, Connection |
| **ResultSet.close()** lỗi | Cả ba | Vẫn thử đóng Statement và Connection |
| **Statement.close()** lỗi | Cả ba | Connection vẫn được thử đóng |

Đây là lợi ích quan trọng so với việc tạo tài nguyên trước block **try** rồi quên đóng một phần khi bước tiếp theo ném exception.

Không viết kiểu sau:

~~~java
Connection connection = dataSource.getConnection();
PreparedStatement statement = connection.prepareStatement(sql);
ResultSet resultSet = statement.executeQuery();

try {
    // Xử lý dữ liệu.
} finally {
    // Dễ quên đóng một tài nguyên hoặc đóng sai thứ tự.
}
~~~

Hãy đưa từng tài nguyên vào resource specification hoặc block lồng nhau ngay khi nó được tạo.

## 8. Connection lấy từ pool và quyền sở hữu tài nguyên

Trong ứng dụng server, **DataSource** thường được cấu hình để lấy connection từ connection pool. Mỗi lần gọi **getConnection()** trả về một logical connection. Khi gọi **close()** trên logical connection, pool thường nhận lại connection để tái sử dụng thay vì đóng socket vật lý ngay lập tức.

Vì vậy, code lấy connection trực tiếp từ **DataSource** vẫn phải đóng nó:

~~~java
try (Connection connection = dataSource.getConnection()) {
    // Thực hiện công việc JDBC.
}
~~~

Không giữ connection mở qua nhiều request hoặc lưu nó trong field dùng chung. Giữ connection lâu sẽ chiếm một slot trong pool và có thể làm request khác phải chờ.

Tuy nhiên, cần phân biệt connection do code tự lấy với connection được framework hoặc transaction manager quản lý. Nếu một API trả về connection gắn với transaction hiện tại, hãy tuân theo cơ chế quản lý tài nguyên của framework; không tự ý đóng, commit hoặc rollback một connection mà code hiện tại không sở hữu. Quy tắc cốt lõi là đóng đúng tài nguyên mà scope hiện tại chịu trách nhiệm.

**Statement** và **ResultSet** do code tạo ra nên được đóng trong phạm vi nhỏ nhất có thể. Không trả chúng ra ngoài repository để tầng service sử dụng sau khi connection đã đóng.

## 9. try-with-resources không tự commit transaction

Đóng tài nguyên và kết thúc transaction là hai việc khác nhau. Try-with-resources chỉ gọi **close()**; nó không thay thế **commit()** hoặc **rollback()**.

Mặc định, connection mới thường ở chế độ auto-commit. Khi tắt auto-commit, ứng dụng phải chủ động commit hoặc rollback transaction. JDBC quy định kết quả của việc đóng connection khi vẫn còn transaction đang hoạt động là implementation-defined; vì vậy, hãy kết thúc transaction trước khi connection rời scope.

Ví dụ transaction do code JDBC trực tiếp quản lý:

~~~java
public void renameCustomer(
        DataSource dataSource,
        long id,
        String newName) throws SQLException {

    String sql = """
        UPDATE customer
        SET display_name = ?
        WHERE id = ?
        """;

    try (Connection connection = dataSource.getConnection()) {
        connection.setAutoCommit(false);

        try {
            try (PreparedStatement statement =
                     connection.prepareStatement(sql)) {
                statement.setString(1, newName);
                statement.setLong(2, id);
                statement.executeUpdate();
            }

            // Statement đã đóng trước khi commit.
            connection.commit();

        } catch (SQLException | RuntimeException failure) {
            try {
                connection.rollback();
            } catch (SQLException rollbackFailure) {
                failure.addSuppressed(rollbackFailure);
            }

            throw failure;
        }
    }
}
~~~

Thứ tự ở đây là: đóng statement, commit hoặc rollback, rồi đóng connection. Nếu transaction do framework quản lý, để transaction manager quyết định commit/rollback và tuân thủ cách lấy/giải phóng connection mà framework quy định.

## 10. Có nên đóng thủ công ResultSet trước Statement?

Thông thường không cần gọi **close()** thủ công bên trong block nếu đã khai báo cả hai là resource:

~~~java
try (PreparedStatement statement =
         connection.prepareStatement(sql);
     ResultSet resultSet = statement.executeQuery()) {

    // Đọc dữ liệu.
}
// Tự động: ResultSet rồi PreparedStatement.
~~~

Không nên vừa khai báo trong try-with-resources vừa gọi **close()** nhiều lần ở nhiều nhánh. JDBC quy định gọi **close()** trên **ResultSet** hoặc **Statement** đã đóng là không có tác dụng; tuy nhiên, quản lý một nơi giúp code dễ đọc và giảm phụ thuộc vào hành vi driver.

Có thể đóng sớm một resource trước khi block kết thúc nếu cần giải phóng nó trước khi tiếp tục công việc khác, nhưng sau đó không sử dụng resource đã đóng nữa. Đừng bật **closeOnCompletion()** chỉ để thay thế try-with-resources; đó là hành vi phụ thuộc statement/result set và không làm rõ quyền sở hữu connection.

## 11. Những lỗi thường gặp

| Lỗi | Hậu quả | Cách sửa |
|---|---|---|
| Chỉ đóng Connection, bỏ quên Statement/ResultSet | Tài nguyên truy vấn có thể bị giữ lâu hơn cần thiết | Khai báo từng resource trong try-with-resources |
| Đóng Connection trước Statement | Statement/result set không còn connection hợp lệ để hoạt động | Đóng theo thứ tự ngược: ResultSet, Statement, Connection |
| Trả ResultSet ra khỏi phương thức đã đóng connection | Caller nhận cursor đã đóng hoặc không còn hợp lệ | Ánh xạ dữ liệu sang DTO/record bên trong block |
| Dùng **finally** nhiều nhánh để đóng thủ công | Dễ bỏ sót resource và làm mất exception gốc | Dùng try-with-resources |
| Nghĩ Statement.close không liên quan ResultSet | Có thể giữ cursor và resource của driver ngoài ý muốn | Hiểu rằng Statement.close đóng result set hiện tại; vẫn khai báo ResultSet riêng |
| Bắt exception đóng rồi bỏ qua | Mất dấu hiệu pool/driver giải phóng tài nguyên thất bại | Giữ exception chính và kiểm tra suppressed exception |
| Nghĩ TWR tự commit transaction | Có thể mất dữ liệu hoặc phụ thuộc hành vi driver | Commit/rollback tường minh trước khi Connection đóng |
| Đóng connection do transaction manager sở hữu | Có thể phá transaction hoặc vòng đời tài nguyên của framework | Tuân theo API quản lý transaction/connection của framework |
| Giữ connection trong field hoặc qua nhiều request | Chiếm pool slot, tăng nguy cơ cạn pool | Mở connection gần thao tác và đóng ngay sau đó |
| Dùng Statement nối chuỗi dữ liệu đầu vào | Có nguy cơ SQL injection và lỗi escape | Dùng PreparedStatement với parameter binding |

## 12. Checklist áp dụng

- [ ] Lấy connection từ **DataSource** hoặc cơ chế quản lý connection phù hợp của ứng dụng.
- [ ] Khai báo resource theo thứ tự phụ thuộc: Connection, Statement, ResultSet.
- [ ] Để try-with-resources tự đóng theo thứ tự ngược.
- [ ] Dùng **PreparedStatement** và parameter binding cho truy vấn có dữ liệu đầu vào.
- [ ] Đọc và ánh xạ **ResultSet** khi statement/connection còn mở.
- [ ] Không trả **ResultSet**, **Statement** hoặc connection ra khỏi scope nếu không chuyển giao quyền sở hữu rõ ràng.
- [ ] Đảm bảo resource đã tạo trước đó vẫn được đóng khi bước khởi tạo sau thất bại.
- [ ] Không nuốt exception từ **close()**; xem **getSuppressed()** khi cần điều tra.
- [ ] Commit hoặc rollback transaction trước khi connection đóng.
- [ ] Không tự đóng connection thuộc quyền sở hữu của transaction manager/framework.
- [ ] Kiểm tra pool metrics nếu ứng dụng có dấu hiệu cạn connection hoặc giữ connection quá lâu.

## Tài liệu tham khảo

- [Java SE 26 — JDBC API (java.sql)](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/package-summary.html): xác nhận JDBC 4.5 là phiên bản API trong Java SE 26.
- [Java SE 26 — Connection](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/Connection.html): vòng đời connection, close(), auto-commit, commit và rollback.
- [Java SE 26 — Statement](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/Statement.html): close() giải phóng statement và đóng result set hiện tại.
- [Java SE 26 — ResultSet](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/ResultSet.html): vòng đời cursor, close() và quan hệ với statement tạo ra nó.
- [Java SE 26 — AutoCloseable](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/lang/AutoCloseable.html): hợp đồng close() được try-with-resources gọi tự động.
- [Java Language Specification — try-with-resources](https://docs.oracle.com/javase/specs/jls/se26/html/jls-14.html#jls-14.20.3): thứ tự khởi tạo/đóng resource và suppressed exceptions.
- [Java SE 26 — DataSource](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/javax/sql/DataSource.html): cơ chế lấy connection và tích hợp với connection pooling.
