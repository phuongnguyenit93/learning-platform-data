# Array, Blob, Clob, NClob và SQLXML hỗ trợ AutoCloseable

Từ JDK 26, năm kiểu tài nguyên JDBC là `Array`, `Blob`, `Clob`, `NClob` và `SQLXML` triển khai `AutoCloseable`. Nhờ đó, có thể quản lý trực tiếp các đối tượng này bằng `try-with-resources` thay vì phải tự gọi `free()` trong khối `finally`. Phương thức `close()` mới là phương thức mặc định và gọi `free()` để giải phóng tài nguyên mà đối tượng JDBC đang giữ.

Thay đổi này thuộc JDBC 4.5 Maintenance Release và được đưa vào Java SE 26. Đây là API chính thức, không phải preview feature; không cần `--enable-preview`. Các phương thức `free()` đã tồn tại từ những phiên bản JDBC trước và vẫn được giữ lại. Điểm mới là năm interface có thêm hợp đồng `AutoCloseable`, giúp code quản lý vòng đời tài nguyên rõ ràng và an toàn hơn.

## 1. Xác định thay đổi của JDBC 4.5

Năm interface được bổ sung `AutoCloseable`:

| Interface | Kiểu SQL | Vai trò |
|---|---|---|
| `Array` | `ARRAY` | Tham chiếu đến một giá trị mảng SQL |
| `Blob` | `BLOB` | Dữ liệu nhị phân lớn |
| `Clob` | `CLOB` | Dữ liệu ký tự lớn |
| `NClob` | `NCLOB` | Dữ liệu ký tự lớn dùng national character set |
| `SQLXML` | `SQLXML` | Giá trị XML do cơ sở dữ liệu quản lý |

Các interface này có thêm phương thức mặc định:

~~~java
default void close() throws SQLException {
    free();
}
~~~

`close()` giải phóng tài nguyên mà đối tượng `Array`, `Blob`, `Clob`, `NClob` hoặc `SQLXML` đang giữ. Theo hợp đồng API:

- Gọi `close()` trên đối tượng đã đóng không làm gì thêm.
- Sau khi đóng, không được gọi các phương thức khác ngoài `close()` hoặc `free()`; thao tác khác sẽ ném `SQLException`.
- `close()` có thể ném `SQLException` nếu giải phóng tài nguyên thất bại.
- Driver có thể báo `SQLFeatureNotSupportedException` nếu không hỗ trợ thao tác tương ứng.

JDBC 4.5 được đưa vào Java SE 26. Javadoc đánh dấu API mới bằng `Since: 26`. Vì vậy, code biên dịch theo Java 26 trở lên có thể dùng năm đối tượng này trực tiếp trong `try-with-resources`.

## 2. Hiểu đúng `close()` và `free()`

Trước JDBC 4.5, ứng dụng thường phải gọi `free()` trong `finally`:

~~~java
Blob blob = resultSet.getBlob("payload");

try {
    if (blob != null) {
        process(blob);
    }
} finally {
    if (blob != null) {
        blob.free();
    }
}
~~~

Từ JDK 26, có thể viết gọn bằng `try-with-resources`:

~~~java
Blob blob = resultSet.getBlob("payload");

if (blob != null) {
    try (blob) {
        process(blob);
    }
}
~~~

`close()` là cách dùng thuận tiện cho cấu trúc quản lý tài nguyên. `free()` vẫn là API hợp lệ và là thao tác mà implementation mặc định của `close()` gọi tới. Không cần tự gọi cả `close()` lẫn `free()` cho cùng một đối tượng trong cùng một luồng xử lý.

Cần phân biệt ba hành động:

| Hành động | Tác dụng |
|---|---|
| `blob.close()` hoặc `blob.free()` | Giải phóng tài nguyên do đối tượng Blob giữ |
| `resultSet.close()` | Đóng ResultSet và tài nguyên cursor liên quan |
| `connection.close()` | Giải phóng kết nối JDBC |

Đóng một `Blob` không tự commit hoặc rollback transaction, không thay thế việc đóng `ResultSet` và không đóng `Connection`. Mỗi đối tượng có vòng đời riêng và cần được quản lý ở đúng phạm vi sở hữu.

## 3. Hiểu vòng đời của LOB và Array

Các driver thường biểu diễn `Blob`, `Clob`, `NClob`, `SQLXML` và `Array` dưới dạng locator: đối tượng Java giữ một tham chiếu logic đến dữ liệu ở cơ sở dữ liệu thay vì luôn tải toàn bộ dữ liệu vào heap. Những locator này có hiệu lực trong thời hạn transaction mà chúng được tạo ra.

Điều này dẫn đến các quy tắc:

1. Đọc hoặc ghi locator trong transaction phù hợp.
2. Không trả locator ra ngoài phạm vi `Connection` hoặc transaction rồi tiếp tục sử dụng sau khi transaction kết thúc.
3. Đóng locator sau khi hoàn thành thao tác để giải phóng tài nguyên driver/database.
4. Nếu lấy `InputStream`, `OutputStream`, `Reader`, `Writer` hoặc `ResultSet` từ locator, hãy quản lý cả đối tượng con đó.
5. Không giả định việc đóng `ResultSet` tự động giải phóng mọi locator đã lấy ra từ nó.

Một số phương thức như `Blob.getBytes()` hoặc `Clob.getSubString()` materialize dữ liệu vào Java array/String. Các phương thức stream cho phép xử lý theo từng phần, phù hợp hơn với LOB lớn để tránh giữ toàn bộ nội dung trong heap.

## 4. Lồng `try-with-resources` đúng thứ tự

Khi một locator trả về một stream, cần đóng stream trước khi đóng locator. Khai báo tài nguyên theo thứ tự locator trước, stream sau để Java đóng theo thứ tự ngược:

~~~java
try (Blob blob = resultSet.getBlob("payload");
     InputStream input = blob.getBinaryStream()) {

    input.transferTo(destination);
}
~~~

Cấu trúc trên minh họa thứ tự đóng, nhưng trong code thực tế phải xử lý trường hợp cột SQL là `NULL` trước khi gọi `getBinaryStream()`. Cách rõ ràng hơn:

~~~java
Blob blob = resultSet.getBlob("payload");

if (blob != null) {
    try (blob;
         InputStream input = blob.getBinaryStream()) {

        input.transferTo(destination);
    }
}
~~~

Thứ tự đóng:

1. `InputStream` được đóng trước.
2. `Blob.close()` được gọi sau.

Cách này cũng áp dụng cho `Clob`/`NClob` với `Reader`, `SQLXML` với reader/writer/stream, và `Array` với `ResultSet` trả về từ `getResultSet()`.

Không giữ locator đã đóng rồi tiếp tục gọi phương thức đọc. `SQLException` sau khi đóng là hành vi được API quy định.

## 5. Đọc BLOB theo stream và giải phóng cả hai tài nguyên

Ví dụ sau lấy dữ liệu nhị phân từ cột `payload` rồi sao chép sang một `OutputStream` do caller truyền vào. Phương thức không đóng stream đích vì caller vẫn sở hữu stream đó.

~~~java
import javax.sql.DataSource;
import java.io.IOException;
import java.io.InputStream;
import java.io.OutputStream;
import java.sql.Blob;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

static void copyPayload(
        DataSource dataSource,
        long documentId,
        OutputStream destination)
        throws SQLException, IOException {

    String sql = """
            SELECT payload
            FROM document_store
            WHERE document_id = ?
            """;

    try (Connection connection = dataSource.getConnection();
         PreparedStatement statement =
                 connection.prepareStatement(sql)) {

        statement.setLong(1, documentId);

        try (ResultSet resultSet = statement.executeQuery()) {
            if (!resultSet.next()) {
                return;
            }

            Blob blob = resultSet.getBlob("payload");

            if (blob == null) {
                return;
            }

            try (blob;
                 InputStream input = blob.getBinaryStream()) {
                input.transferTo(destination);
            }
        }
    }
}
~~~

Trong ví dụ:

- `Connection`, `PreparedStatement` và `ResultSet` được đóng bằng các khối TWR riêng.
- `Blob` được đóng ngay sau khi đọc xong.
- `InputStream` được đóng trước `Blob`.
- `destination` vẫn thuộc caller và không bị đóng ngoài ý muốn.
- `transferTo()` sao chép theo stream, không cần tạo một byte array chứa toàn bộ BLOB.

Tên bảng và cột trong ví dụ là minh họa. Hãy thay bằng schema của hệ thống và kiểm tra driver hỗ trợ kiểu `BLOB`.

Nếu dữ liệu rất lớn, có thể dùng buffer và xử lý từng chunk để áp dụng giới hạn tốc độ, tính checksum hoặc ghi vào file. Không gọi `getBytes(1, (int) blob.length())` một cách máy móc cho BLOB lớn vì có thể gây cấp phát mảng quá lớn hoặc tràn giới hạn kiểu `int`.

## 6. Đọc CLOB và NCLOB bằng Reader

`Clob` chứa dữ liệu ký tự lớn. `NClob` kế thừa `Clob` và biểu diễn dữ liệu dùng national character set. Cả hai có thể cung cấp `Reader` để đọc theo luồng.

Ví dụ đọc `CLOB`:

~~~java
import java.io.Reader;
import java.sql.Clob;
import java.sql.ResultSet;
import java.sql.SQLException;

static String readDescription(ResultSet resultSet)
        throws SQLException, java.io.IOException {

    Clob clob = resultSet.getClob("description");

    if (clob == null) {
        return null;
    }

    try (clob;
         Reader reader = clob.getCharacterStream()) {

        StringBuilder text = new StringBuilder();
        char[] buffer = new char[8192];
        int count;

        while ((count = reader.read(buffer)) != -1) {
            text.append(buffer, 0, count);
        }

        return text.toString();
    }
}
~~~

Ví dụ này trả về `String` nên cuối cùng vẫn materialize toàn bộ dữ liệu vào heap. Với nội dung rất lớn, thay vì `StringBuilder`, hãy ghi từng chunk sang file, parser hoặc consumer khác.

Đọc `NCLOB` theo cách tương tự:

~~~java
import java.io.Reader;
import java.sql.NClob;
import java.sql.ResultSet;

NClob nclob = resultSet.getNClob("localized_content");

if (nclob != null) {
    try (nclob;
         Reader reader = nclob.getCharacterStream()) {

        processCharacters(reader);
    }
}
~~~

Không dùng `getAsciiStream()` cho nội dung Unicode tùy ý. Chọn `getCharacterStream()` khi cần đọc ký tự; giữ đúng semantics national character set của cột `NCLOB`.

## 7. Đọc SQL ARRAY và đóng ResultSet con

`Array` có thể trả nội dung dưới dạng Java array qua `getArray()` hoặc dưới dạng `ResultSet` qua `getResultSet()`. Nếu dùng ResultSet con, phải quản lý cả ResultSet và Array.

~~~java
import java.sql.Array;
import java.sql.ResultSet;
import java.sql.SQLException;

static void readTags(ResultSet row) throws SQLException {
    Array sqlArray = row.getArray("tags");

    if (sqlArray == null) {
        return;
    }

    try (sqlArray;
         ResultSet elements = sqlArray.getResultSet()) {

        while (elements.next()) {
            long index = elements.getLong(1);
            Object value = elements.getObject(2);

            processArrayElement(index, value);
        }
    }
}
~~~

Java đóng `elements` trước `sqlArray` vì tài nguyên được đóng theo thứ tự ngược với thứ tự khai báo. Đóng `Array` giải phóng locator của SQL ARRAY; đóng ResultSet con giải phóng cursor dùng để duyệt các phần tử.

Nếu gọi `getArray()` để materialize dữ liệu thành Java array, vẫn đóng đối tượng `Array` sau khi lấy xong:

~~~java
Array sqlArray = resultSet.getArray("tags");

if (sqlArray != null) {
    try (sqlArray) {
        Object values = sqlArray.getArray();
        processValues(values);
    }
}
~~~

Kiểu Java cụ thể trả về từ `getArray()` phụ thuộc kiểu SQL và type map. Với base type ánh xạ sang primitive, API cho phép implementation trả primitive array hoặc `Object[]` trong một số trường hợp. Vì vậy, ví dụ giữ kết quả ở kiểu `Object`; chỉ ép kiểu sau khi đã xác định mapping thực tế của cột.

## 8. Đọc SQLXML và chú ý trạng thái chỉ đọc một lần

`SQLXML` cũng là locator có thời hạn gắn với transaction. Có thể đọc nội dung qua `getString()`, `getCharacterStream()`, `getBinaryStream()` hoặc `getSource()`.

Ví dụ đọc XML theo Reader:

~~~java
import java.io.Reader;
import java.sql.ResultSet;
import java.sql.SQLXML;

static void readXml(ResultSet resultSet) throws Exception {
    SQLXML xml = resultSet.getSQLXML("document_xml");

    if (xml == null) {
        return;
    }

    try (xml;
         Reader reader = xml.getCharacterStream()) {

        parseXml(reader);
    }
}
~~~

`SQLXML` có quy tắc trạng thái riêng:

- Giá trị chỉ được đọc tối đa một lần qua một trong các API đọc.
- Giá trị chỉ được ghi tối đa một lần qua một trong các API ghi.
- Sau khi gọi `getString()`, `getCharacterStream()`, `getBinaryStream()` hoặc `getSource()`, SQLXML chuyển sang trạng thái không còn đọc được.
- Sau khi gọi `setString()`, `setCharacterStream()`, `setBinaryStream()` hoặc `setResult()`, SQLXML chuyển sang trạng thái không còn ghi được.
- `close()` hoặc `free()` cũng làm đối tượng không còn đọc/ghi được.
- Tất cả stream dùng để ghi SQLXML phải được đóng trước khi gọi `execute()` trên statement.

Vì vậy, không gọi `getString()` rồi tiếp tục gọi `getCharacterStream()` trên cùng một đối tượng để đọc lại. Nếu cần nhiều cách xử lý, hãy đọc một lần vào representation do ứng dụng quản lý, hoặc tạo truy vấn/đối tượng mới theo transaction phù hợp.

## 9. Ghi SQLXML và đóng Writer trước khi execute

Khi tạo SQLXML bằng `Connection.createSQLXML()`, hãy đóng Writer trước khi truyền đối tượng cho `PreparedStatement.setSQLXML()` và thực thi câu lệnh.

~~~java
import java.io.Writer;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLXML;

static void updateXml(
        Connection connection,
        long documentId,
        String xmlText) throws Exception {

    String sql = """
            UPDATE document_store
            SET document_xml = ?
            WHERE document_id = ?
            """;

    try (PreparedStatement statement =
                 connection.prepareStatement(sql);
         SQLXML xml = connection.createSQLXML()) {

        try (Writer writer = xml.setCharacterStream()) {
            writer.write(xmlText);
        } // Phải đóng writer trước khi executeUpdate().

        statement.setSQLXML(1, xml);
        statement.setLong(2, documentId);
        statement.executeUpdate();
    }
}
~~~

Đối tượng `SQLXML` vẫn mở trong lúc statement dùng nó. Khi khối ngoài kết thúc, statement và SQLXML được đóng theo thứ tự ngược với thứ tự khai báo: SQLXML trước, PreparedStatement sau.

Nếu `setCharacterStream()` không được driver hỗ trợ, driver có thể ném `SQLFeatureNotSupportedException`. Kiểm tra tài liệu driver hoặc dùng phương thức được driver hỗ trợ như `setString()` nếu phù hợp với kích thước dữ liệu và yêu cầu bộ nhớ.

## 10. Ghi BLOB bằng OutputStream

Có thể tạo một BLOB mới qua `Connection.createBlob()`, ghi nội dung vào stream rồi gắn BLOB vào statement:

~~~java
import java.io.OutputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.sql.Blob;
import java.sql.Connection;
import java.sql.PreparedStatement;

static void insertPayload(
        Connection connection,
        long documentId,
        Path sourceFile) throws Exception {

    String sql = """
            INSERT INTO document_store (document_id, payload)
            VALUES (?, ?)
            """;

    try (PreparedStatement statement =
                 connection.prepareStatement(sql);
         Blob blob = connection.createBlob()) {

        try (OutputStream output = blob.setBinaryStream(1)) {
            Files.copy(sourceFile, output);
        } // Đóng OutputStream trước khi truyền Blob vào statement.

        statement.setLong(1, documentId);
        statement.setBlob(2, blob);
        statement.executeUpdate();
    }
}
~~~

`Blob` vẫn còn mở trong lúc `executeUpdate()` sử dụng nó. `OutputStream` được đóng trước để hoàn tất việc ghi dữ liệu vào locator. Khi kết thúc, TWR gọi `Blob.close()` để giải phóng tài nguyên tạm.

Không gọi `blob.close()` trước `setBlob()` hoặc `executeUpdate()` nếu statement còn cần đọc nội dung từ locator.

## 11. Quản lý ownership khi lồng nhiều tài nguyên

Một truy vấn có thể tạo nhiều tầng tài nguyên:

~~~text
Connection
  |
  +-- PreparedStatement
        |
        +-- ResultSet
              |
              +-- Blob / Clob / NClob / SQLXML / Array
                    |
                    +-- InputStream / OutputStream / Reader / Writer
                    +-- ResultSet (từ Array.getResultSet)
~~~

Mỗi tầng có trách nhiệm riêng:

| Tài nguyên | Ai tạo / lấy ra | Đóng ở đâu |
|---|---|---|
| Connection | DataSource hoặc DriverManager | Tầng sở hữu connection |
| PreparedStatement | Connection | Trong phạm vi connection |
| ResultSet | Statement | Trong phạm vi statement |
| Blob/Clob/NClob/SQLXML/Array | ResultSet, Statement hoặc Connection | Sau khi hoàn tất thao tác locator |
| Stream/Reader/Writer của LOB | LOB object | Sau khi đọc/ghi, trước khi đóng locator |
| ResultSet từ Array | Array | Sau khi duyệt phần tử, trước khi đóng Array |

Nguyên tắc sắp xếp:

- Khai báo tài nguyên cha trước tài nguyên con.
- Đóng tài nguyên con trước tài nguyên cha.
- Không đóng đối tượng do caller sở hữu nếu hợp đồng phương thức không chuyển quyền sở hữu.
- Không trả locator ra khỏi transaction mà locator phụ thuộc.
- Dùng TWR để exception ở bất kỳ bước nào vẫn kích hoạt đóng tài nguyên đã tạo.

Nếu một stream đích được caller truyền vào, thường không đóng stream đó trong phương thức tiện ích. Nếu phương thức tự mở file hoặc socket, phương thức phải đóng tài nguyên mà nó tạo.

## 12. `SQLException`, suppressed exception và lỗi khi đóng

`close()` khai báo `throws SQLException`, vì vậy method chứa TWR cần xử lý hoặc khai báo exception này. Khi phần thân try ném exception và quá trình đóng cũng thất bại, Java giữ exception từ phần thân làm lỗi chính và gắn lỗi đóng vào `getSuppressed()`.

Ví dụ ghi log lỗi đóng mà không che mất lỗi chính:

~~~java
try (Blob blob = resultSet.getBlob("payload")) {
    if (blob != null) {
        process(blob);
    }
} catch (SQLException failure) {
    for (Throwable suppressed : failure.getSuppressed()) {
        logger.warn("JDBC resource close failed", suppressed);
    }
    throw failure;
}
~~~

Trong code thực tế, nên kiểm tra `blob != null` trước khi tạo resource để không cần kiểm tra bên trong. Ví dụ này nhấn mạnh cách đọc suppressed exception khi cần chẩn đoán.

Các tình huống lỗi thường gặp:

| Hiện tượng | Nguyên nhân | Cách xử lý |
|---|---|---|
| `SQLException` sau khi gọi close | Driver/database gặp lỗi khi giải phóng locator | Ghi nhận lỗi đóng và kiểm tra trạng thái kết nối/transaction |
| `SQLFeatureNotSupportedException` | Driver không hỗ trợ kiểu SQL hoặc phương thức cụ thể | Kiểm tra ma trận hỗ trợ của driver và database |
| Gọi phương thức trên Blob đã đóng | Locator đã được giải phóng | Không dùng lại đối tượng sau khi rời phạm vi TWR |
| SQLXML không đọc được lần thứ hai | SQLXML đã chuyển trạng thái sau lần đọc đầu | Chỉ đọc một lần; giữ dữ liệu trong representation ứng dụng nếu cần tái sử dụng |
| Execute khi SQLXML writer còn mở | Dữ liệu XML chưa được hoàn tất | Đóng Writer trước khi execute |
| LOB không còn hợp lệ sau commit | Locator có thời hạn theo transaction | Đọc/ghi LOB trong transaction sở hữu nó |
| Dùng heap tăng mạnh | Materialize toàn bộ LOB thành byte[] hoặc String | Dùng stream/reader và xử lý theo chunk |
| ResultSet con còn mở khi đóng Array | Thứ tự đóng tài nguyên sai | Khai báo ResultSet sau Array để đóng ngược thứ tự |

## 13. Khả năng tương thích của JDBC driver

Java SE 26 công bố JDBC 4.5 API, nhưng hỗ trợ thực tế còn phụ thuộc driver và database. Package summary của JDK lưu ý nhiều tính năng JDBC là tùy chọn và mức hỗ trợ khác nhau giữa các driver.

Trước khi triển khai:

1. Xác định driver version và phiên bản database.
2. Kiểm tra driver hỗ trợ SQL type tương ứng (`ARRAY`, `BLOB`, `CLOB`, `NCLOB`, `SQLXML`).
3. Kiểm tra phương thức cần dùng: stream đọc/ghi, `createBlob()`, `createClob()`, `createNClob()`, `createSQLXML()`, `getResultSet()`.
4. Chạy integration test trên đúng driver và database triển khai.
5. Kiểm tra lỗi đóng và hành vi khi transaction commit/rollback.
6. Kiểm tra memory usage với dữ liệu lớn, không chỉ dữ liệu mẫu nhỏ.

JDK 26 bổ sung `AutoCloseable` ở API chuẩn. Điều đó không tự đảm bảo mọi driver hỗ trợ mọi kiểu LOB hoặc mọi phương thức đọc/ghi của kiểu đó. Hãy dựa vào tài liệu driver và kiểm thử thật.

Nếu dự án còn biên dịch với API JDK 25 hoặc cũ hơn, năm interface này chưa có quan hệ `AutoCloseable` trong API compile-time của các release đó. Khi cần hỗ trợ đồng thời nhiều baseline JDK, phải chọn baseline biên dịch phù hợp hoặc duy trì adapter theo phiên bản. Không giả định một source file dùng `try (Blob blob = ...)` sẽ biên dịch nguyên trạng trên JDK 25.

## 14. Phân biệt phần mới và phần đã có từ trước

Không nhầm toàn bộ JDBC resource management là tính năng mới của JDBC 4.5:

| Tài nguyên/API | Trạng thái |
|---|---|
| `Connection` dùng được với try-with-resources | Đã có từ JDBC 4.1 |
| `Statement` và `ResultSet` dùng được với try-with-resources | Đã có từ JDBC 4.1 |
| `Array.free()`, `Blob.free()`, `Clob.free()`, `NClob.free()`, `SQLXML.free()` | Đã có từ các phiên bản JDBC trước |
| Năm interface trên mở rộng `AutoCloseable` và có default `close()` | Mới trong JDBC 4.5 / Java SE 26 |

Điểm mới tập trung vào khả năng dùng chung cơ chế `try-with-resources` của Java. Không cần viết một kiểu cleanup riêng cho từng LOB object nữa, nhưng vẫn phải quản lý các stream và result set con được tạo từ chúng.

`free()` không bị thay thế hoặc đánh dấu deprecated bởi thay đổi này. Nó vẫn có thể được gọi khi cần giải phóng locator sớm trước khi kết thúc phạm vi phương thức. Trong code mới chạy trên Java 26+, TWR thường dễ đọc và ít rủi ro quên cleanup hơn.

## 15. Ma trận kiểm thử

Tạo integration test bằng driver thực tế. Dùng dữ liệu thử có kích thước vừa phải và thêm ca dữ liệu lớn để kiểm tra streaming:

| Ca kiểm thử | Cách thực hiện | Kết quả cần xác nhận |
|---|---|---|
| Blob đọc thành công | Lấy Blob, mở InputStream, copy dữ liệu | Stream đóng trước Blob; nội dung đúng |
| Blob ghi thành công | createBlob, ghi qua OutputStream, setBlob và execute | OutputStream đóng trước execute; dữ liệu được lưu |
| Clob đọc Unicode | Lấy Clob và đọc bằng Reader | Ký tự được giữ đúng; cả Reader và Clob được đóng |
| NClob đọc national characters | Lấy NClob, đọc bằng Reader | Nội dung Unicode đúng theo hỗ trợ của driver |
| Array duyệt qua ResultSet | getArray rồi getResultSet | ResultSet con đóng trước Array |
| Array materialize | Gọi getArray rồi close Array | Java array đã lấy được dùng độc lập theo mapping |
| SQLXML đọc | Gọi đúng một API đọc | Không gọi API đọc lần hai trên cùng SQLXML |
| SQLXML ghi | Mở Writer, ghi XML, đóng Writer rồi execute | Statement thực thi sau khi stream đã đóng |
| Cột SQL NULL | Getter trả null | Không gọi phương thức trên locator null |
| Exception trong khi đọc | Ném lỗi giữa lúc copy | TWR vẫn đóng stream và locator |
| Lỗi khi close | Kiểm thử driver/test double có thể phát sinh lỗi cleanup | Exception đóng được xử lý hoặc nằm trong suppressed exception |
| Transaction kết thúc | Dùng locator trong transaction rồi commit/rollback | Không tiếp tục dùng locator ngoài thời hạn hợp lệ |
| Driver không hỗ trợ | Thử kiểu/phương thức tùy chọn | Nhận diện SQLFeatureNotSupportedException và xử lý theo hợp đồng |

Một phép thử quan trọng là gây exception trong khi đang đọc stream, rồi xác nhận các tài nguyên đã được đóng. Có thể dùng wrapper/test double để ghi nhận thứ tự `close()` mà không phụ thuộc vào implementation nội bộ của driver.

## 16. Bài thực hành tổng hợp

1. Dùng JDK 26 trở lên và một JDBC driver hỗ trợ BLOB/CLOB.
2. Truy vấn một bản ghi có cột BLOB; đọc qua `getBinaryStream()` và TWR lồng với Blob.
3. Truy vấn một CLOB; đọc qua `getCharacterStream()` và xác nhận ký tự Unicode.
4. Truy vấn một NCLOB nếu database/driver hỗ trợ; xác nhận nội dung national character set.
5. Truy vấn một ARRAY; duyệt bằng `getResultSet()` và đóng ResultSet con trước Array.
6. Truy vấn SQLXML; đọc bằng một API duy nhất, ví dụ `getCharacterStream()`.
7. Tạo SQLXML mới, ghi bằng `setCharacterStream()`, đóng Writer trước khi gọi `executeUpdate()`.
8. Ghi BLOB bằng `setBinaryStream()`, đóng OutputStream trước khi thực thi statement.
9. Cố ý gây exception trong lúc copy dữ liệu và xác nhận TWR giải phóng locator.
10. Kiểm tra hành vi khi cột trả SQL NULL, khi driver không hỗ trợ kiểu dữ liệu và khi transaction kết thúc.
11. Chạy test với payload lớn để so sánh cách materialize toàn bộ với cách xử lý stream theo chunk.

**Tiêu chí hoàn thành:** giải thích được thay đổi JDBC 4.5 trong Java 26; biết năm interface nào mở rộng AutoCloseable; hiểu `close()` mặc định gọi `free()`; dùng TWR với đúng thứ tự đóng; quản lý cả locator và stream/result set con; xử lý riêng trạng thái đọc/ghi một lần của SQLXML; giữ locator trong transaction hợp lệ; xác minh khả năng hỗ trợ của driver; phân biệt API mới với `Connection`, `Statement` và `ResultSet` vốn đã hỗ trợ TWR từ trước.
