# Chế độ khám phá HTTP/3 và chính sách dùng giao thức thay thế

## 1. Mục tiêu của bài học

Java 26 mở rộng HTTP Client API để hỗ trợ HTTP/3 và bổ sung cách định hướng việc tìm endpoint HTTP/3. Khi bật HTTP/3, ứng dụng cần hiểu client sẽ tìm máy chủ bằng cách nào, lúc nào có thể chuyển sang HTTP/2 hoặc HTTP/1.1, và trường hợp nào request phải thất bại nếu HTTP/3 không dùng được.

Trọng tâm của bài là ba chế độ trong `HttpOption.Http3DiscoveryMode`:

- `ANY`: để implementation tự chọn cách tìm hoặc thiết lập kết nối.
- `ALT_SVC`: chỉ tìm HTTP/3 thông qua thông tin HTTP Alternative Services mà origin đã quảng bá.
- `HTTP_3_URI_ONLY`: chỉ thử HTTP/3 tại host và port ghi trong URI.

Các API này là API chuẩn của Java SE, có từ JDK 26 và vẫn có trong tài liệu Java SE 27. Chúng không phải preview hoặc incubator, vì vậy không cần bật `--enable-preview` hay thêm module incubator. Khi phát triển mới, hãy dùng một JDK còn được nhà cung cấp hỗ trợ; JDK 27 vẫn công bố các API này trong tài liệu chính thức.

## 2. Điều kiện để HttpClient thực sự thử HTTP/3

### 2.1. HTTP/3 phải được chọn làm phiên bản ưu tiên

`HttpClient` và `HttpRequest` đều có thể đặt phiên bản HTTP ưu tiên:

- `HttpClient.Builder.version(HttpClient.Version)`: đặt mặc định cho các request gửi bằng client đó.
- `HttpRequest.Builder.version(HttpClient.Version)`: đặt riêng cho một request và ghi đè lựa chọn mặc định của client.

Mặc định, JDK built-in `HttpClient` ưu tiên HTTP/2. Vì vậy, chỉ đặt `H3_DISCOVERY` mà không chọn `HTTP_3` sẽ không kích hoạt HTTP/3; hint bị bỏ qua.

Có thể bật HTTP/3 ở cấp client:

~~~java
HttpClient client = HttpClient.newBuilder()
        .version(HttpClient.Version.HTTP_3)
        .build();
~~~

Hoặc bật riêng cho request:

~~~java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/status"))
        .version(HttpClient.Version.HTTP_3)
        .GET()
        .build();
~~~

Tên phương thức là `version`, nhưng giá trị truyền vào là phiên bản được ưu tiên. Trong chế độ có fallback, phiên bản thực tế có thể là HTTP/2 hoặc HTTP/1.1. Hãy đọc `HttpResponse.version()` để biết giao thức đã được dùng cho response.

### 2.2. HTTP/3 yêu cầu HTTPS và QUIC

HTTP/3 chạy trên QUIC, không chạy trên TCP. QUIC dùng TLS 1.3 trở lên cho quá trình bắt tay; HTTP/3 được nhận diện qua ALPN token `h3`.

Các điều kiện cần kiểm tra:

- URI của request phải dùng scheme `https`. JDK built-in HttpClient không gửi request HTTP thuần qua HTTP/3.
- Máy chủ phải hỗ trợ HTTP/3 và QUIC tại endpoint được chọn.
- Mạng, firewall và load balancer phải cho phép lưu lượng UDP tới cổng QUIC của endpoint. Nếu UDP bị chặn, kết nối QUIC có thể không thiết lập được.
- Chứng chỉ TLS và cấu hình `SSLContext`/`SSLParameters` phải tương thích với kết nối HTTP/3.
- Phải xác nhận giao thức thực tế bằng response, không suy ra từ việc đã đặt `HTTP_3`.

HTTP/3 không phải một phép chuyển đổi HTTP/2 sang HTTP/3 ở tầng cú pháp request. Ứng dụng vẫn dùng `HttpRequest`, `HttpResponse`, `BodyPublisher` và `BodyHandler`; khác biệt chính nằm ở giao thức truyền tải và cách client tìm endpoint.

## 3. Ba chế độ khám phá HTTP/3

`HttpOption.H3_DISCOVERY` là một request option có kiểu `HttpOption.Http3DiscoveryMode`. Có thể đặt nó bằng `HttpRequest.Builder.setOption(...)`.

| Chế độ | Cách tìm kết nối | Có thể dùng HTTP/2 hoặc HTTP/1.1? | Khi phù hợp |
|---|---|---|---|
| `ANY` | Thuật toán do HttpClient implementation quyết định; có thể dùng Alt-Svc đã biết hoặc thử trực tiếp host:port trong URI | Có | Muốn client tự chọn và duy trì khả năng tương thích |
| `ALT_SVC` | Chỉ dựa vào HTTP Alternative Services do origin quảng bá | Có | Muốn server chủ động công bố endpoint HTTP/3 trước khi client chuyển sang dùng |
| `HTTP_3_URI_ONLY` | Chỉ thử QUIC tại đúng authority (host và port) của URI | Không | Muốn kiểm tra hoặc yêu cầu HTTP/3 trực tiếp tại endpoint URI |

Nếu request hoặc client đã chọn HTTP/3 nhưng không đặt `H3_DISCOVERY`, JDK built-in HttpClient sử dụng hành vi tương ứng với `ANY`. Đây là mặc định của implementation tích hợp trong JDK; không nên giả định mọi implementation HttpClient bên ngoài đều có cùng thuật toán.

### 3.1. ANY: để client tự lựa chọn

`ANY` cho phép HttpClient sử dụng thuật toán riêng để tìm hoặc thiết lập kết nối. Khi chưa có kết nối phù hợp, implementation có thể thử cả:

- Kết nối HTTP/3 qua QUIC tại authority của URI hoặc endpoint thay thế đã biết.
- Kết nối HTTP qua TLS/TCP tại authority của URI.

Kết nối nào thiết lập thành công trước có thể được dùng; exchange có thể chạy bằng HTTP/3, HTTP/2 hoặc HTTP/1.1. Khi request ưu tiên HTTP/3, JDK built-in implementation có thể ưu tiên thử QUIC trước kết nối TLS/TCP.

Ví dụ đặt rõ chế độ:

~~~java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/status"))
        .version(HttpClient.Version.HTTP_3)
        .setOption(
                HttpOption.H3_DISCOVERY,
                HttpOption.Http3DiscoveryMode.ANY
        )
        .GET()
        .build();
~~~

Dùng `ANY` khi HTTP/3 là một lựa chọn mong muốn, còn khả năng truy cập qua HTTP/2 hoặc HTTP/1.1 vẫn cần được duy trì. Đây là lựa chọn phù hợp cho rollout dần hoặc môi trường có chất lượng mạng khác nhau.

### 3.2. ALT_SVC: chờ origin quảng bá endpoint HTTP/3

HTTP Alternative Services cho phép một origin công bố rằng cùng tài nguyên của nó có thể được truy cập qua một endpoint mạng khác hoặc một cấu hình giao thức khác. Với HTTP/3, server có thể gửi header `Alt-Svc` trong response:

~~~http
Alt-Svc: h3=":443"; ma=3600
~~~

Ví dụ trên thông báo rằng origin có endpoint HTTP/3 tại cùng hostname, cổng UDP 443; thông tin có thời hạn 3.600 giây theo tham số `ma`.

Luồng hoạt động thường gặp:

1. Client gửi request đầu tiên tới origin bằng HTTP/1.1 hoặc HTTP/2.
2. Server phản hồi và quảng bá endpoint HTTP/3 bằng `Alt-Svc`.
3. Client ghi nhận thông tin alternative service theo cơ chế cache của implementation.
4. Những request sau có thể thiết lập QUIC tới endpoint đã quảng bá và dùng HTTP/3.

Khi dùng `ALT_SVC`, HttpClient chỉ sử dụng HTTP Alternative Services để tìm endpoint HTTP/3. Nếu chưa có bản ghi `h3`, request tiếp tục dùng HTTP/1.1 hoặc HTTP/2 đã thương lượng với origin. Chế độ này hữu ích khi đội vận hành muốn bật HTTP/3 ở server trước, quan sát hoạt động rồi mới để client chuyển sang endpoint mới.

Ví dụ:

~~~java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/status"))
        .version(HttpClient.Version.HTTP_3)
        .setOption(
                HttpOption.H3_DISCOVERY,
                HttpOption.Http3DiscoveryMode.ALT_SVC
        )
        .GET()
        .build();
~~~

`Alt-Svc` là response header do server gửi. Ứng dụng client không cần tự thêm `Alt-Svc` vào request. Server cũng có thể gửi `Alt-Svc: clear` để yêu cầu client xóa thông tin alternative service đã lưu cho origin.

### 3.3. HTTP_3_URI_ONLY: chỉ thử đúng endpoint trong URI

`HTTP_3_URI_ONLY` yêu cầu HttpClient chỉ thử kết nối HTTP/3 trực tiếp với authority của URI. Ví dụ URI là:

~~~text
https://api.example.com:8443/v1/orders
~~~

Client phải thiết lập QUIC tới `api.example.com:8443`. Chế độ này:

- Không dùng thông tin HTTP Alternative Services.
- Không chuyển sang HTTP/2 hoặc HTTP/1.1 nếu endpoint HTTP/3 trực tiếp không dùng được.
- Không phù hợp khi server chỉ công bố HTTP/3 ở một host hoặc port khác qua `Alt-Svc`.
- Có thể phát sinh `UnsupportedProtocolVersionException` nếu implementation hoặc cấu hình TLS của client không hỗ trợ HTTP/3.

Ví dụ:

~~~java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com:8443/v1/orders"))
        .version(HttpClient.Version.HTTP_3)
        .setOption(
                HttpOption.H3_DISCOVERY,
                HttpOption.Http3DiscoveryMode.HTTP_3_URI_ONLY
        )
        .GET()
        .build();
~~~

Chọn chế độ này khi cần kiểm thử endpoint QUIC trực tiếp hoặc khi yêu cầu nghiệp vụ quy định request phải chạy bằng HTTP/3. Không chọn nó chỉ để “ưu tiên” HTTP/3, bởi nó không cung cấp đường lui khi kết nối HTTP/3 không thành công.

## 4. Phân biệt discovery với fallback giao thức

Discovery trả lời câu hỏi “client tìm endpoint HTTP/3 bằng cách nào?”. Fallback trả lời câu hỏi “client có thể tiếp tục request bằng giao thức khác khi HTTP/3 không dùng được hay không?”.

Hai khái niệm này liên quan nhưng không giống nhau:

| Tình huống | ANY | ALT_SVC | HTTP_3_URI_ONLY |
|---|---|---|---|
| Chưa có Alt-Svc cho origin | Có thể thử trực tiếp HTTP/3 và kết nối TLS/TCP | Dùng HTTP/1.1 hoặc HTTP/2 cho tới khi nhận được quảng bá h3 | Thử QUIC trực tiếp tại host:port của URI |
| Có Alt-Svc h3 hợp lệ | Có thể dùng endpoint được quảng bá | Dùng endpoint được quảng bá | Bỏ qua Alt-Svc |
| UDP bị chặn | Có thể dùng kết nối TCP nếu kết nối đó thành công | Có thể dùng HTTP/1.1 hoặc HTTP/2 theo trạng thái khám phá/negotiation; xử lý lỗi endpoint thay thế cần kiểm thử | Request thất bại nếu không thiết lập được HTTP/3 |
| Không có HTTP/3 tại host:port URI | Có thể dùng giao thức khác nếu kết nối thay thế thành công | Có thể dùng endpoint Alt-Svc nếu đã được quảng bá; nếu chưa có thì dùng H1/H2 | Request thất bại |
| Proxy được chọn trong JDK built-in HttpClient | Hạ xuống HTTP/2 hoặc HTTP/1.1, bỏ qua hint | Hạ xuống HTTP/2 hoặc HTTP/1.1, bỏ qua hint | Request thất bại |

Trong chế độ `ANY`, JDK có thể thử kết nối QUIC và TLS/TCP; điều này cho phép sử dụng đường TCP khi QUIC không thiết lập được. RFC HTTP/3 cũng khuyến nghị client thử các phiên bản HTTP dựa trên TCP khi gặp vấn đề kết nối QUIC.

Với `ALT_SVC`, cần phân biệt hai trường hợp: chưa có bản ghi h3 thì API mô tả rõ request dùng HTTP/1.1 hoặc HTTP/2; còn khi đã có bản ghi nhưng kết nối endpoint thay thế thất bại, không nên tự suy luận mọi lỗi đều được fallback theo cùng một cách. RFC Alternative Services cho phép client quay lại origin hoặc thử alternative service khác, nhưng đây không phải cam kết rằng mọi lỗi đều sẽ được tự động retry. Hãy kiểm thử hành vi của đúng JDK và mạng triển khai.

`HTTP_3_URI_ONLY` là chế độ nghiêm ngặt: nếu HTTP/3 trực tiếp không khả dụng, request thất bại. Không có một enum riêng trong `H3_DISCOVERY` để bắt buộc “chỉ HTTP/2”; nếu ứng dụng muốn ưu tiên HTTP/2, hãy đặt `HttpClient.Version.HTTP_2` và kiểm tra `HttpResponse.version()`. Đây vẫn là phiên bản ưu tiên, nên các giới hạn của implementation có thể ảnh hưởng kết quả thực tế.

## 5. Ví dụ hoàn chỉnh: chọn mode và xác nhận giao thức thực tế

Ví dụ sau cho phép thay đổi mode ở một hằng số. Chương trình in phiên bản HTTP thực tế trong response để người vận hành có bằng chứng về giao thức được sử dụng.

~~~java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpOption;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;

public class Http3DiscoveryDemo {
    private static final HttpOption.Http3DiscoveryMode DISCOVERY_MODE =
            HttpOption.Http3DiscoveryMode.ALT_SVC;

    public static void main(String[] args) throws Exception {
        URI uri = URI.create("https://www.example.com/");

        HttpClient client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(5))
                .build();

        HttpRequest request = HttpRequest.newBuilder(uri)
                .version(HttpClient.Version.HTTP_3)
                .setOption(HttpOption.H3_DISCOVERY, DISCOVERY_MODE)
                .timeout(Duration.ofSeconds(15))
                .GET()
                .build();

        HttpResponse<String> response = client.send(
                request,
                HttpResponse.BodyHandlers.ofString()
        );

        System.out.println("Discovery mode: " + DISCOVERY_MODE);
        System.out.println("HTTP version used: " + response.version());
        System.out.println("Status: " + response.statusCode());
    }
}
~~~

Thử lần lượt ba giá trị:

~~~java
HttpOption.Http3DiscoveryMode.ANY
HttpOption.Http3DiscoveryMode.ALT_SVC
HttpOption.Http3DiscoveryMode.HTTP_3_URI_ONLY
~~~

Trong ví dụ, `HttpClient` giữ mặc định ưu tiên HTTP/2 nhưng request đặt rõ phiên bản ưu tiên HTTP/3. Phiên bản request có độ ưu tiên cao hơn cấu hình mặc định của client. Nếu bỏ lời gọi `setOption`, JDK built-in implementation sẽ sử dụng mode `ANY` khi HTTP/3 đã được chọn.

Ví dụ biên dịch và chạy với JDK 27:

~~~bash
javac --release 27 -d out Http3DiscoveryDemo.java
java -cp out Http3DiscoveryDemo
~~~

Có thể biên dịch với `--release 26` khi cần tạo bytecode và giới hạn API ở Java 26. Không cần cờ preview hoặc module incubator cho các API HTTP/3 này.

## 6. Proxy, redirect và cấu hình TLS

### 6.1. Proxy là giới hạn quan trọng của JDK built-in HttpClient

Theo tài liệu API Java SE 26 và 27, JDK built-in HttpClient chưa hỗ trợ HTTP/3 qua proxy.

Nếu proxy được chọn cho request:

- Với `ANY` hoặc `ALT_SVC`, protocol bị hạ xuống HTTP/2 hoặc HTTP/1.1 và hint `H3_DISCOVERY` bị bỏ qua.
- Với `HTTP_3_URI_ONLY`, request thất bại.

Proxy có thể được cấu hình trực tiếp qua `HttpClient.Builder.proxy(...)` hoặc được lấy từ `ProxySelector` mặc định của hệ thống. Vì vậy, cần kiểm tra cả cấu hình proxy trong JVM/container, không chỉ kiểm tra code.

Nếu môi trường doanh nghiệp bắt buộc mọi kết nối đi qua proxy, hãy xác định trước rằng JDK built-in HttpClient sẽ không truyền HTTP/3 qua proxy trong phiên bản được mô tả. Nếu HTTP/3 qua proxy là yêu cầu bắt buộc, cần đánh giá riêng một client/network stack có hỗ trợ đúng mô hình proxy đó.

### 6.2. Redirect

JDK built-in implementation chuyển tiếp option `H3_DISCOVERY` sang request mới khi xử lý redirect. Tuy nhiên, redirect có thể đưa request sang một origin khác, endpoint khác hoặc môi trường có proxy/chính sách mạng khác. Vì thế, không nên xem việc request đầu tiên dùng HTTP/3 là bằng chứng mọi request sau redirect cũng dùng HTTP/3.

Hãy kiểm tra `HttpResponse.version()`, URI cuối cùng và trạng thái response trong kiểm thử redirect. Chỉ bật tự động redirect theo chính sách phù hợp với ứng dụng; mặc định của HttpClient là không tự theo redirect.

### 6.3. SSLContext và SSLParameters

HTTP/3 dùng TLS trong QUIC. Cấu hình SSL tùy biến cần tương thích với HTTP/3. Tài liệu `HttpClient` nêu rằng `UnsupportedProtocolVersionException` có thể xảy ra khi:

- Xây dựng client với HTTP/3 là phiên bản ưu tiên nhưng implementation không hỗ trợ cấu hình đó.
- Gửi request bật HTTP/3 với `HTTP_3_URI_ONLY`, nhưng cấu hình `SSLContext` hoặc `SSLParameters` không dùng được với HTTP/3.

Không tắt xác minh chứng chỉ hoặc hostname để làm cho kết nối thành công. Nếu cần custom trust store, mutual TLS hoặc chính sách cipher/protocol riêng, hãy kiểm thử cấu hình đó với HTTP/3 và giữ nguyên xác minh danh tính server.

## 7. Alt-Svc và bảo mật origin

HTTP Alternative Services thay đổi đường đi mạng tới dịch vụ, nhưng không đổi origin của tài nguyên. Ví dụ, origin `https://shop.example.com` có thể quảng bá endpoint HTTP/3 ở `edge.example.net:443`. Ứng dụng vẫn truy cập tài nguyên của origin `shop.example.com`.

Các nguyên tắc cần giữ:

- Alternative service phải có đủ cơ sở xác thực là endpoint có thẩm quyền phục vụ origin.
- Với endpoint dùng TLS, chứng chỉ phải được xác minh cho origin trong URI theo quy tắc của giao thức; không bỏ hostname verification chỉ vì host kết nối thực tế khác.
- Chỉ tin thông tin Alt-Svc đến từ phản hồi của origin hợp lệ qua kênh được xác thực.
- Server có thể đặt thời hạn cho alternative service bằng tham số `ma`, hoặc gửi `Alt-Svc: clear` để yêu cầu xóa các alternative service đã quảng bá.
- Không tự viết lại URI ứng dụng sang host alternative chỉ vì thấy header Alt-Svc. Việc chọn đường đi là trách nhiệm của HTTP client; origin logic của request vẫn được giữ nguyên.

RFC Alternative Services cảnh báo rằng việc quảng bá host hoặc port khác có thể tạo rủi ro nếu attacker kiểm soát được header hoặc endpoint thay thế. Vì vậy, bảo vệ response header từ origin, cấu hình TLS đúng và kiểm soát quyền triển khai endpoint UDP là một phần của vận hành HTTP/3.

## 8. Các giới hạn về implementation và tính tương thích

`HttpOption.H3_DISCOVERY` là request configuration hint. JDK built-in HttpClient hiểu option này, nhưng hợp đồng của API cho phép một implementation HttpClient khác bỏ qua hint hoặc từ chối request nếu nó không hỗ trợ option.

Khi ứng dụng dùng thư viện HTTP client thay thế, không được giả định rằng:

- Tất cả implementation đều hỗ trợ HTTP/3.
- Tất cả implementation đều hiểu `H3_DISCOVERY`.
- `ANY` có cùng thuật toán giữa các implementation.
- Hành vi proxy, fallback, cache Alt-Svc và redirect giống JDK built-in HttpClient.

Nếu code cần chạy trên nhiều JDK vendor hoặc nhiều implementation, hãy kiểm thử trên runtime thực tế. Tách việc chọn mode thành cấu hình của ứng dụng sẽ giúp điều chỉnh chính sách mà không phải sửa nhiều nơi trong mã nguồn.

## 9. Chiến lược lựa chọn mode

| Nhu cầu | Lựa chọn đề xuất | Lý do |
|---|---|---|
| Muốn thử HTTP/3 nhưng vẫn ưu tiên khả năng truy cập | `ANY` | Client tự tìm endpoint và có thể dùng kết nối TCP nếu phù hợp |
| Muốn bật HTTP/3 theo lộ trình do server điều khiển | `ALT_SVC` | Client chờ origin quảng bá endpoint h3 |
| Muốn kiểm tra trực tiếp một listener QUIC cụ thể | `HTTP_3_URI_ONLY` | Không dùng Alt-Svc và không fallback |
| Hệ thống bắt buộc dùng proxy với JDK built-in HttpClient | HTTP/2 hoặc HTTP/1.1 | JDK built-in HttpClient không hỗ trợ HTTP/3 qua proxy |
| Muốn ưu tiên HTTP/2, không bật HTTP/3 | `HttpClient.Version.HTTP_2` | Không chọn HTTP/3 nên H3 discovery không hoạt động |

Một lựa chọn triển khai thực tế thường là bắt đầu với `ANY` để đo mức hỗ trợ và hành vi fallback, hoặc `ALT_SVC` khi đội server đã có quy trình quảng bá endpoint rõ ràng. Chỉ dùng `HTTP_3_URI_ONLY` khi ứng dụng có lý do cần thất bại nếu HTTP/3 không dùng được.

## 10. Checklist kiểm thử trước khi triển khai

1. Xác nhận JDK runtime và implementation HttpClient thực tế.
2. Xác nhận request dùng `https` và đã chọn HTTP/3 ở client hoặc request.
3. Xác nhận `H3_DISCOVERY` chỉ được đặt khi request/client ưu tiên HTTP/3.
4. Kiểm tra server hỗ trợ QUIC, TLS 1.3 và ALPN `h3`.
5. Kiểm tra firewall, security group, NAT, load balancer và đường mạng cho phép UDP tới cổng QUIC.
6. Kiểm thử `ANY` khi UDP mở và khi UDP bị chặn.
7. Kiểm thử `ALT_SVC` với response có và không có `Alt-Svc: h3=...`.
8. Kiểm thử `HTTP_3_URI_ONLY` khi listener QUIC hoạt động và khi listener không khả dụng.
9. Kiểm thử khi ProxySelector trả về proxy; xác nhận downgrade hoặc lỗi đúng với mode.
10. Kiểm thử redirect sang cùng origin và origin khác.
11. Kiểm thử custom SSLContext, trust store, hostname verification và client certificate nếu ứng dụng sử dụng.
12. Ghi nhận `HttpResponse.version()`, status code, URI cuối cùng, latency, timeout và lỗi kết nối để phân biệt HTTP/3 thành công với fallback.

Không nên chỉ dựa vào một request thành công trên máy phát triển. Kết quả cần được xác nhận trong mạng staging/production tương đương, đặc biệt khi UDP, proxy hoặc TLS termination được quản lý bởi hạ tầng bên ngoài.

### Cẩn trọng khi tự retry

Nếu tự viết fallback bằng cách bắt exception rồi gửi lại request qua HTTP/2, cần xét khả năng request đầu tiên đã tới server và được xử lý trước khi kết nối bị lỗi. Retry một request ghi dữ liệu có thể tạo thao tác trùng lặp.

Chỉ retry khi phương thức và nghiệp vụ cho phép, body publisher có thể phát lại, và server có cơ chế idempotency/deduplication phù hợp. Ưu tiên để JDK built-in HttpClient xử lý lựa chọn giao thức trong `ANY` khi mục tiêu là khả năng tương thích tự động.

## 11. Kết luận

`HttpOption.H3_DISCOVERY` cho phép định hướng cách JDK built-in HttpClient tìm endpoint HTTP/3. `ANY` trao quyền lựa chọn cho implementation và giữ khả năng dùng các giao thức TCP; `ALT_SVC` đợi origin quảng bá endpoint h3; `HTTP_3_URI_ONLY` chỉ thử QUIC tại host và port trong URI, không dùng Alt-Svc và không fallback.

Để sử dụng đúng, phải chọn HTTP/3 làm phiên bản ưu tiên, dùng URI HTTPS, bảo đảm mạng cho phép QUIC/UDP và xác nhận giao thức thực tế bằng `HttpResponse.version()`. Cần kiểm tra proxy, redirect, SSLContext và implementation HttpClient vì các yếu tố này có thể làm thay đổi giao thức thực tế hoặc khiến request thất bại.

Các API được giới thiệu từ JDK 26 vẫn hiện diện trong Java SE 27. Hãy dùng tài liệu của JDK đang triển khai để kiểm chứng hành vi, đồng thời kiểm thử trên hạ tầng thực tế trước khi dựa vào HTTP/3 cho yêu cầu hiệu năng hoặc độ tin cậy.
