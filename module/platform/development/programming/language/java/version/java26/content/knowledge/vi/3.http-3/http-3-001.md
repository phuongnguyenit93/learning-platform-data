# HTTP/3 là API chính thức từ Java 26

Từ Java 26, HTTP Client API trong module **java.net.http** có thể gửi yêu cầu bằng HTTP/3. Đây là phần mở rộng chính thức của API Java: **HttpClient.Version.HTTP_3**, **HttpOption.H3_DISCOVERY** và các chế độ khám phá kết nối HTTP/3 đều có trong Java API Specification với mốc **Since: 26**. Các API này không phải preview hoặc incubator, vì vậy không cần bật **--enable-preview** hay thêm module thử nghiệm.

HTTP/3 là phiên bản giao thức HTTP được chuẩn hóa trong RFC 9114. JDK 26 bổ sung khả năng sử dụng giao thức này qua **java.net.http.HttpClient**, giữ nguyên mô hình tạo client, tạo request và xử lý response quen thuộc. Cần phân biệt API Java đã ổn định với khả năng triển khai thực tế: HTTP/3 chỉ được dùng khi client, server và đường truyền đáp ứng các điều kiện cần thiết.

## 1. HTTP/3 giải quyết vấn đề gì?

HTTP/3 giữ nguyên ngữ nghĩa HTTP như method, status code, header và body. Thay đổi quan trọng nằm ở tầng truyền tải: HTTP/1.1 và HTTP/2 thường chạy trên TCP, còn HTTP/3 chạy trên **QUIC**, một giao thức truyền tải chạy trên UDP. QUIC tích hợp TLS 1.3 vào quá trình thiết lập kết nối.

| Phiên bản | Tầng truyền tải | Cách xử lý nhiều luồng | Điểm cần nhớ |
|---|---|---|---|
| HTTP/1.1 | TCP | Thường cần nhiều kết nối để xử lý nhiều yêu cầu đồng thời hiệu quả | Mô hình đơn giản, tương thích rộng |
| HTTP/2 | TCP | Multiplex nhiều stream trên một kết nối | Mất gói TCP có thể làm chậm việc giao dữ liệu của nhiều stream trên cùng kết nối |
| HTTP/3 | QUIC trên UDP | Multiplex stream ở tầng QUIC; mỗi stream có cơ chế truyền dữ liệu độc lập | Giảm ảnh hưởng head-of-line blocking giữa các stream khi mất gói; TLS 1.3 được tích hợp trong QUIC |

Trong HTTP/2, nhiều stream dùng chung một kết nối TCP. TCP phải giao dữ liệu theo thứ tự byte của toàn kết nối, nên một đoạn dữ liệu bị mất có thể khiến dữ liệu phía sau phải chờ được truyền lại, kể cả khi dữ liệu đó thuộc stream khác. QUIC tổ chức các stream độc lập ở tầng truyền tải, giúp hạn chế kiểu chờ này giữa các stream.

HTTP/3 còn sử dụng **QPACK** để nén header và tận dụng khả năng xử lý nhiều stream của QUIC. QUIC có cơ chế kiểm soát luồng, kiểm soát tắc nghẽn và xác thực mã hóa thông qua TLS 1.3. Những đặc điểm này có thể cải thiện trải nghiệm trên mạng có độ trễ hoặc mất gói, nhưng không bảo đảm mọi ứng dụng sẽ nhanh hơn HTTP/2. Hiệu năng còn phụ thuộc server, CDN, vị trí mạng, kích thước dữ liệu và thiết bị khách.

## 2. API HTTP/3 trong Java 26

Các thành phần chính nằm trong module **java.net.http**:

- **HttpClient.Version.HTTP_3**: giá trị mới trong enum HttpClient.Version, được bổ sung từ Java 26.
- **HttpClient.Builder.version(...)**: đặt phiên bản HTTP ưu tiên mặc định cho các request của client.
- **HttpRequest.Builder.version(...)**: đặt phiên bản HTTP ưu tiên cho một request cụ thể; giá trị ở request được dùng thay cho giá trị mặc định của client.
- **HttpOption.H3_DISCOVERY**: cấu hình cách client tìm hoặc thiết lập kết nối HTTP/3.
- **HttpOption.Http3DiscoveryMode**: chọn chiến lược ANY, ALT_SVC hoặc HTTP_3_URI_ONLY.
- **HttpResponse.version()**: trả về phiên bản giao thức thực tế đã được dùng cho response.

Client mặc định của JDK 26 hỗ trợ HTTP/1.1, HTTP/2 và HTTP/3. Tuy nhiên, client mặc định vẫn ưu tiên **HTTP/2**. Muốn thử HTTP/3, cần đặt phiên bản ưu tiên thành HttpClient.Version.HTTP_3.

Đặt HTTP/3 làm phiên bản ưu tiên không đồng nghĩa mọi request chắc chắn được truyền bằng HTTP/3. Việc chọn giao thức thực tế còn phụ thuộc khả năng kết nối QUIC, chế độ khám phá, proxy, URI và cấu hình TLS. Vì vậy, luôn đọc response.version() để biết request đã thực sự dùng HTTP/1.1, HTTP/2 hay HTTP/3.

## 3. Gửi request bằng HTTP/3

Ví dụ sau dùng JDK 26 để gửi một GET request. Thay https://example.com/ bằng endpoint thử nghiệm có hỗ trợ HTTP/3:

    import java.io.IOException;
    import java.net.URI;
    import java.net.http.HttpClient;
    import java.net.http.HttpRequest;
    import java.net.http.HttpResponse;
    import java.time.Duration;

    public class Http3Get {
        public static void main(String[] args)
                throws IOException, InterruptedException {

            HttpRequest request = HttpRequest.newBuilder()
                    .uri(URI.create("https://example.com/"))
                    .timeout(Duration.ofSeconds(20))
                    .GET()
                    .build();

            try (HttpClient client = HttpClient.newBuilder()
                    .version(HttpClient.Version.HTTP_3)
                    .connectTimeout(Duration.ofSeconds(10))
                    .build()) {

                HttpResponse<String> response = client.send(
                        request,
                        HttpResponse.BodyHandlers.ofString()
                );

                System.out.println("Status: " + response.statusCode());
                System.out.println("Protocol actually used: "
                        + response.version());
                System.out.println(response.body());
            }
        }
    }

Biên dịch và chạy bằng JDK 26:

    javac --release 26 -encoding UTF-8 -d out src/Http3Get.java
    java -cp out Http3Get

Trong ví dụ, HttpClient.Builder.version(HTTP_3) đặt phiên bản ưu tiên ở cấp client. Có thể đặt riêng ở cấp request nếu chỉ một số endpoint cần ưu tiên HTTP/3:

    HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create("https://example.com/"))
            .version(HttpClient.Version.HTTP_3)
            .GET()
            .build();

Nếu cả client và request đều chỉ định phiên bản ưu tiên, cấu hình tại request được dùng cho request đó. HttpClient.version() cho biết phiên bản client ưu tiên; HttpResponse.version() mới là giá trị cần kiểm tra để xác nhận giao thức thực tế của một response.

Có thể gửi bất đồng bộ bằng API sẵn có:

    client.sendAsync(request, HttpResponse.BodyHandlers.ofString())
            .thenAccept(response -> {
                System.out.println(response.statusCode());
                System.out.println(response.version());
            });

Không cần một lớp client riêng cho HTTP/3. Cùng các API HttpRequest, HttpResponse, BodyPublisher, BodyHandler, send và sendAsync tiếp tục được sử dụng.

## 4. Chọn cách khám phá kết nối HTTP/3

Java 26 bổ sung **HttpOption.H3_DISCOVERY** để điều khiển cách JDK tìm hoặc thiết lập kết nối HTTP/3. Tùy chọn này chỉ có tác dụng khi HTTP/3 đã được đặt làm phiên bản ưu tiên ở client hoặc request.

Có ba chế độ:

| Chế độ | Cách hoạt động | Khi phù hợp |
|---|---|---|
| ANY | Cho phép client tự chọn cách kết nối. JDK có thể thử QUIC và kết nối TLS/TCP, sau đó dùng kết nối thành công trước | Muốn client tự lựa chọn và có khả năng dùng HTTP/2 hoặc HTTP/1.1 khi HTTP/3 không khả dụng |
| ALT_SVC | Chỉ tìm HTTP/3 thông qua thông tin HTTP Alternative Services mà origin server quảng bá | Muốn tuân theo cơ chế khám phá HTTP/3 do server công bố |
| HTTP_3_URI_ONLY | Chỉ thử kết nối QUIC trực tiếp đến host và port của URI; không dùng Alternative Services | Cần thử endpoint HTTP/3 trực tiếp và chấp nhận thất bại nếu endpoint không hỗ trợ |

Khi đã chọn HTTP/3 nhưng không đặt H3_DISCOVERY, implementation tích hợp của JDK sử dụng hành vi tương ứng với **ANY**.

### ANY — để client tự chọn

Với ANY, implementation có thể thử thiết lập kết nối HTTP/3 qua QUIC và kết nối HTTP qua TLS/TCP. Kết nối thành công trước có thể được dùng cho exchange. Nếu HTTP/3 không sẵn sàng nhưng kết nối HTTP/2 hoặc HTTP/1.1 thành công, response có thể sử dụng một trong hai phiên bản đó.

Đây là lựa chọn phù hợp khi ứng dụng ưu tiên HTTP/3 nhưng vẫn cần hoạt động trong các môi trường mà QUIC chưa khả dụng.

### ALT_SVC — khám phá qua HTTP Alternative Services

Server có thể quảng bá endpoint HTTP/3 bằng header **Alt-Svc**, chẳng hạn:

    Alt-Svc: h3=":443"; ma=86400

Với chế độ ALT_SVC, request ban đầu có thể được gửi bằng HTTP/1.1 hoặc HTTP/2 cho đến khi client nhận được thông tin endpoint h3 hợp lệ. Những request tiếp theo có thể dùng endpoint HTTP/3 đã được quảng bá.

Cơ chế này hữu ích khi server muốn công bố endpoint QUIC riêng hoặc port HTTP/3 khác với endpoint trong URI. Ứng dụng nên để HTTP Client quản lý quá trình xử lý Alt-Svc, không tự giả lập việc thương lượng giao thức bằng cách đặt header HTTP tùy ý.

### HTTP_3_URI_ONLY — chỉ thử QUIC trực tiếp

Với HTTP_3_URI_ONLY, client chỉ thử HTTP/3 tại cùng host và port được xác định bởi URI. Chế độ này không sử dụng thông tin Alternative Services. Kết nối chỉ thành công nếu server đang lắng nghe HTTP/3 qua QUIC tại authority đó.

Ví dụ cấu hình theo từng request:

    import java.net.URI;
    import java.net.http.HttpClient;
    import java.net.http.HttpOption;
    import java.net.http.HttpRequest;

    HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create("https://example.com/"))
            .version(HttpClient.Version.HTTP_3)
            .setOption(
                    HttpOption.H3_DISCOVERY,
                    HttpOption.Http3DiscoveryMode.ALT_SVC
            )
            .GET()
            .build();

Đổi ALT_SVC thành ANY hoặc HTTP_3_URI_ONLY để thử các chiến lược tương ứng. Nếu dùng HTTP_3_URI_ONLY, hãy xác nhận endpoint thực sự nhận QUIC tại đúng host và port trước khi chạy. Chế độ này không tự chuyển sang HTTP/2 hoặc HTTP/1.1 nếu kết nối HTTP/3 không thành công.

## 5. Điều kiện để HTTP/3 hoạt động

Cần kiểm tra các điều kiện sau trước khi kết luận API không hoạt động:

1. **JDK phù hợp:** dùng JDK 26 trở lên. HttpClient.Version.HTTP_3 không tồn tại trong API của JDK 25 trở xuống.
2. **URI HTTPS:** implementation của JDK không gửi request có URI scheme http qua HTTP/3. Dùng endpoint https://.
3. **Server hỗ trợ HTTP/3:** server hoặc CDN phải triển khai HTTP/3 và có thể cung cấp endpoint QUIC theo cách khám phá đã chọn.
4. **Đường truyền cho phép QUIC:** QUIC chạy trên UDP. Firewall, NAT, mạng doanh nghiệp hoặc nhà cung cấp mạng có thể chặn UDP hoặc endpoint/port được server quảng bá.
5. **Không dùng proxy trong implementation JDK:** HTTP/3 qua proxy chưa được hỗ trợ bởi implementation tích hợp của JDK 26. Nếu proxy được chọn, ANY hoặc ALT_SVC có thể bị hạ xuống HTTP/2 hoặc HTTP/1.1; HTTP_3_URI_ONLY sẽ thất bại.
6. **Cấu hình TLS tương thích:** SSLContext hoặc SSLParameters tùy chỉnh có thể không dùng được với HTTP/3. Khi client không hỗ trợ giao thức được yêu cầu, có thể nhận UnsupportedProtocolVersionException.

HTTP/3 dùng TLS 1.3 thông qua QUIC. Ứng dụng vẫn cần xác minh chứng thư server, hostname và chuỗi tin cậy theo cấu hình bảo mật chuẩn. Không tắt hostname verification hoặc chấp nhận mọi chứng thư chỉ để làm cho kết nối thử nghiệm chạy được.

Khi dùng mạng nội bộ, cần phối hợp với đội vận hành để xác nhận UDP được cho phép đến endpoint QUIC. Nếu hệ thống bắt buộc đi qua HTTP proxy, hãy dự kiến HTTP/1.1 hoặc HTTP/2 với implementation JDK hiện tại và kiểm tra response.version() để biết phiên bản thực tế.

## 6. Cấu hình module và build tool

java.net.http là module Java SE. Nếu ứng dụng dùng Java Platform Module System, khai báo phụ thuộc trong module-info.java:

    module demo.http3 {
        requires java.net.http;
    }

Với ứng dụng trên class path, có thể dùng các lệnh javac --release 26 và java -cp như ví dụ trước. Không cần --add-modules jdk.incubator.vector, vì HTTP/3 không nằm trong Vector API hay module incubator.

Với Gradle Groovy DSL, chỉ định toolchain và release 26:

    java {
        toolchain {
            languageVersion = JavaLanguageVersion.of(26)
        }
    }

    tasks.withType(JavaCompile).configureEach {
        options.release = 26
    }

Không thêm --enable-preview cho mã chỉ dùng HTTP/3. Kiểm tra Gradle wrapper và JDK toolchain thực tế đều hỗ trợ Java 26. Với Maven, đặt maven.compiler.release thành 26 và bảo đảm compiler plugin đang chạy với JDK phù hợp.

Nếu biên dịch với --release 25 hoặc dùng compiler JDK 25, mã tham chiếu HttpClient.Version.HTTP_3 sẽ không biên dịch vì API này được bổ sung từ Java 26. Để triển khai, runtime cũng phải có API tương ứng và implementation HTTP Client hỗ trợ HTTP/3.

## 7. Kiểm chứng giao thức và xử lý lỗi

Không dựa vào cấu hình ưu tiên để khẳng định kết nối đã dùng HTTP/3. Hãy ghi nhận HttpResponse.version() trong log hoặc telemetry của ứng dụng:

    HttpResponse<String> response =
            client.send(request, HttpResponse.BodyHandlers.ofString());

    switch (response.version()) {
        case HTTP_3 -> System.out.println("Đã dùng HTTP/3");
        case HTTP_2 -> System.out.println("Đã dùng HTTP/2");
        case HTTP_1_1 -> System.out.println("Đã dùng HTTP/1.1");
    }

Đoạn switch trên dùng các enum constant đã có trong API Java 26. Nó phân loại giao thức thực tế, kể cả khi client đã ưu tiên HTTP/3 nhưng kết nối được thiết lập bằng phiên bản khác.

| Biểu hiện | Nguyên nhân có thể | Cách xử lý |
|---|---|---|
| Không tìm thấy HTTP_3 khi biên dịch | Compiler hoặc --release đang dùng release thấp hơn 26 | Chuyển sang JDK 26 và --release 26 |
| Response báo HTTP_2 hoặc HTTP_1_1 | ANY đã chọn kết nối TCP/TLS; server chưa quảng bá H3; QUIC không kết nối được; hoặc proxy được chọn | Kiểm tra response.version(), endpoint H3, Alt-Svc, UDP và proxy |
| Request dùng HTTP_3_URI_ONLY thất bại | Server không lắng nghe QUIC ở host/port của URI, UDP bị chặn hoặc TLS config không tương thích | Kiểm tra endpoint, đường truyền và SSLContext/SSLParameters |
| Nhận UnsupportedProtocolVersionException | Implementation HttpClient không hỗ trợ HTTP/3 hoặc cấu hình bảo mật không tương thích | Dùng implementation có hỗ trợ, kiểm tra SSLContext và SSLParameters |
| Chỉ lỗi trong môi trường doanh nghiệp | Proxy, firewall, NAT hoặc chính sách mạng chặn QUIC | Kiểm tra chính sách UDP và tuyến mạng với đội vận hành |

Để phân biệt lỗi ứng dụng với lỗi hạ tầng, nên thử cùng một endpoint HTTPS bằng một client HTTP/3 đã biết hỗ trợ QUIC, đồng thời kiểm tra log của JDK HTTP Client. Module java.net.http cung cấp thuộc tính logging của implementation JDK, trong đó có nhóm **http3** và **quic**. Có thể bật tạm khi chẩn đoán:

    java -Djdk.httpclient.HttpClient.log=errors,requests,http3,quic -cp out Http3Get

Log chi tiết có thể chứa URL, header hoặc thông tin kết nối. Chỉ bật trong môi trường kiểm thử phù hợp và không đưa dữ liệu nhạy cảm vào log chia sẻ.

## 8. Hiệu năng, vận hành và lựa chọn sử dụng

HTTP/3 có thể cải thiện độ trễ khi thiết lập kết nối, giảm ảnh hưởng mất gói giữa các stream và duy trì kết nối tốt hơn khi thiết bị đổi mạng nhờ các khả năng của QUIC. Tuy nhiên, kết quả thực tế phụ thuộc chất lượng mạng, server, cấu hình CDN, tải CPU và cách ứng dụng gửi dữ liệu.

Khi đánh giá HTTP/3, hãy đo trên cùng một tập request và cùng điều kiện mạng:

- Thời gian thiết lập kết nối và thời gian đến byte đầu tiên.
- Độ trễ hoàn thành request, throughput và tỷ lệ lỗi.
- Hành vi khi mạng mất gói hoặc thay đổi đường truyền.
- Chi phí CPU và mức sử dụng bộ nhớ ở client/server.
- Tỷ lệ response thực sự dùng HTTP/3 so với HTTP/2 hoặc HTTP/1.1.

Dùng lại một HttpClient cho nhiều request để tận dụng quản lý kết nối và tài nguyên nội bộ. Tránh tạo client mới cho mỗi request trong ứng dụng phục vụ nhiều người dùng. Khi ứng dụng dừng, đóng client theo vòng đời phù hợp; nếu dùng body dạng stream, hãy đọc hết hoặc đóng stream để request và tài nguyên liên quan có thể hoàn tất giải phóng.

Có thể triển khai theo từng giai đoạn: đo baseline với HTTP/2, bật HTTP/3 preference bằng ANY, ghi lại response.version() và số liệu vận hành, sau đó thử ALT_SVC nếu server đã quảng bá endpoint. Chỉ dùng HTTP_3_URI_ONLY cho bài kiểm thử cần xác nhận endpoint QUIC trực tiếp. Nếu HTTP/3 không mang lại lợi ích trong môi trường thực tế hoặc bị giới hạn bởi proxy, giữ HTTP/2 là lựa chọn phù hợp.

## 9. Checklist thực hành

1. Xác nhận compiler và runtime là JDK 26 trở lên.
2. Đặt --release 26; không bật preview cho HTTP/3.
3. Dùng URI https:// và endpoint đã bật HTTP/3.
4. Đặt HttpClient.Version.HTTP_3 ở client hoặc request.
5. Chọn ANY, ALT_SVC hoặc HTTP_3_URI_ONLY theo mục tiêu kiểm thử.
6. Kiểm tra UDP/QUIC, proxy và cấu hình TLS.
7. Đọc HttpResponse.version() để xác nhận giao thức thực tế.
8. Đo hiệu năng và tỷ lệ lỗi trước khi chuyển tải production.

HTTP/3 là phần mở rộng chính thức, ổn định của HTTP Client API từ Java 26. Mã ứng dụng vẫn dùng HttpClient, HttpRequest và HttpResponse; việc chuyển sang HTTP/3 chủ yếu là chọn phiên bản ưu tiên và xác nhận điều kiện mạng, server cùng implementation. Phân biệt phiên bản ưu tiên với giao thức thực tế giúp ứng dụng vận hành đúng ngay cả khi HTTP/3 không khả dụng.

## Tài liệu chính thức

- [Oracle — Significant Changes in JDK 26 Release](https://docs.oracle.com/en/java/javase/26/migrate/significant-changes-jdk-26-release.html): xác nhận HTTP Client API của JDK 26 hỗ trợ HTTP/3.
- [Java SE 26 API — HttpClient](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpClient.html): các phiên bản giao thức được hỗ trợ, mặc định HTTP/2, điều kiện HTTPS, proxy và lựa chọn phiên bản.
- [Java SE 26 API — HttpClient.Version](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpClient.Version.html): enum HTTP_3 có từ Java 26.
- [Java SE 26 API — HttpOption](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpOption.html): tùy chọn H3_DISCOVERY và hành vi mặc định.
- [Java SE 26 API — HttpOption.Http3DiscoveryMode](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpOption.Http3DiscoveryMode.html): ý nghĩa của ANY, ALT_SVC và HTTP_3_URI_ONLY.
- [Java SE 26 API — HttpRequest.Builder](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html): đặt phiên bản ưu tiên và discovery option theo từng request.
- [Java SE 26 API — HttpResponse](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpResponse.html): đọc phiên bản giao thức thực tế qua version().
- [Java SE 26 API — java.net.http package](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/package-summary.html): module API và đặc tả RFC 9114 về HTTP/3.
- [RFC 9114 — HTTP/3](https://www.rfc-editor.org/rfc/rfc9114): đặc tả giao thức HTTP/3.
- [RFC 9000 — QUIC: A UDP-Based Multiplexed and Secure Transport](https://www.rfc-editor.org/rfc/rfc9000): đặc tả tầng truyền tải QUIC.
- [RFC 9001 — Using TLS to Secure QUIC](https://www.rfc-editor.org/rfc/rfc9001): cách QUIC sử dụng TLS để bảo mật kết nối.

Các nội dung về API và giới hạn implementation trong bài được đối chiếu với Java SE 26 API Specification và tài liệu Oracle JDK 26 hiện hành tại ngày 27-11-2026.
