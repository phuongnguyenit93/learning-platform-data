# Chọn `HttpClient.Version.HTTP_3` ở client hoặc request

Java 26 bổ sung HTTP/3 cho `java.net.http.HttpClient` thông qua JEP 517. Ứng dụng có thể đặt `HttpClient.Version.HTTP_3` làm phiên bản ưu tiên cho toàn bộ một `HttpClient`, hoặc chỉ cho từng `HttpRequest`. Đây là API Java SE đã hoàn tất trong Java 26, không phải preview hay incubator; không cần `--enable-preview` hoặc `--add-modules` để dùng. Tại ngày 27-11-2026, API này vẫn có trong tài liệu Java 27.

Điều quan trọng là `HTTP_3` biểu thị **phiên bản ưu tiên**, không phải lời bảo đảm response sẽ luôn dùng HTTP/3. JDK phải tìm được đường kết nối QUIC phù hợp; server, mạng, proxy và cấu hình TLS đều ảnh hưởng đến kết quả. Vì vậy, cần chọn đúng phạm vi cấu hình và đọc `HttpResponse.version()` sau khi gửi request để biết giao thức thực tế. [JEP 517](https://openjdk.org/jeps/517) · [Java 26 `HttpClient`](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpClient.html) · [Java 27 `HttpClient.Version`](https://docs.oracle.com/en/java/javase/27/docs/api/java.net.http/java/net/http/HttpClient.Version.html).

## 1. Hai nơi đặt phiên bản HTTP

`HttpClient` đại diện cho một client có thể gửi nhiều request và thường quản lý pool kết nối riêng. `HttpRequest` mô tả một lần gọi cụ thể. Cả hai builder đều có phương thức `version(...)`, nhưng phạm vi tác động khác nhau.

| Nơi cấu hình | API | Phạm vi | Khi nào phù hợp |
|---|---|---|---|
| Client | `HttpClient.newBuilder().version(HttpClient.Version.HTTP_3)` | Phiên bản ưu tiên mặc định cho các request gửi bằng client đó, trừ request có đặt phiên bản riêng. | Phần lớn request tới các dịch vụ của ứng dụng đều nên ưu tiên HTTP/3. |
| Request | `HttpRequest.newBuilder(uri).version(HttpClient.Version.HTTP_3)` | Chỉ request được tạo từ builder đó. | Chỉ một số endpoint hoặc request cần thử HTTP/3; các request còn lại giữ cấu hình của client. |

Nếu request không đặt phiên bản, nó kế thừa phiên bản ưu tiên của client. Nếu request có gọi `version(...)`, giá trị ở request được dùng cho request đó và ghi đè lựa chọn mặc định của client. Đây là quy tắc giúp một client dùng chung cho nhiều loại request.

Mặc định, `HttpClient.newHttpClient()` và builder không gọi `version(...)` ưu tiên HTTP/2. HTTP/3 không tự động được chọn. [HttpClient.Builder.version](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpClient.Builder.html) · [HttpRequest.Builder.version](https://docs.oracle.com/en/java/javase/26/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html).

## 2. Đặt HTTP/3 ở cấp client

Đặt phiên bản tại client khi HTTP/3 là lựa chọn ưu tiên chung cho phần lớn request. Sau khi tạo client, có thể tái sử dụng nó để gửi nhiều request; không cần tạo một client mới cho từng lần gọi.

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;

public class ClientLevelHttp3 {
    public static void main(String[] args) throws Exception {
        HttpClient client = HttpClient.newBuilder()
                .version(HttpClient.Version.HTTP_3)
                .connectTimeout(Duration.ofSeconds(10))
                .build();

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create("https://api.example.com/products"))
                .timeout(Duration.ofSeconds(20))
                .GET()
                .build();

        HttpResponse<String> response = client.send(
                request,
                HttpResponse.BodyHandlers.ofString()
        );

        System.out.println("Status: " + response.statusCode());
        System.out.println("Protocol actually used: " + response.version());
        System.out.println(response.body());
    }
}
```

Trong ví dụ này, request không tự đặt phiên bản nên dùng preference `HTTP_3` của client. Những request khác được gửi qua cùng client cũng nhận preference đó, trừ khi request tương ứng chỉ định một phiên bản khác.

`HttpClient` là immutable sau khi `build()`. Nếu muốn đổi preference mặc định, hãy tạo một client khác với cấu hình mới và quản lý vòng đời của nó rõ ràng. Tuy nhiên, việc tạo client mới cho từng request thường làm mất lợi ích tái sử dụng pool kết nối. Nếu chỉ cần chọn HTTP/3 cho một vài request, cấu hình ở cấp request sẽ gọn hơn.

## 3. Đặt HTTP/3 ở cấp request

Đặt phiên bản ở request khi muốn giữ một client dùng chung, nhưng chỉ bật preference HTTP/3 cho một số lần gọi. Cách này hữu ích khi ứng dụng gọi nhiều dịch vụ có khả năng HTTP/3 khác nhau hoặc đang triển khai HTTP/3 theo từng endpoint.

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class RequestLevelHttp3 {
    public static void main(String[] args) throws Exception {
        // Client mặc định ưu tiên HTTP/2.
        HttpClient client = HttpClient.newBuilder().build();

        // Chỉ request này ưu tiên HTTP/3.
        HttpRequest http3Request = HttpRequest.newBuilder()
                .uri(URI.create("https://api.example.com/catalog"))
                .version(HttpClient.Version.HTTP_3)
                .GET()
                .build();

        // Request này không đặt version nên kế thừa preference của client.
        HttpRequest defaultRequest = HttpRequest.newBuilder()
                .uri(URI.create("https://legacy-api.example.com/status"))
                .GET()
                .build();

        HttpResponse<String> http3Response = client.send(
                http3Request,
                HttpResponse.BodyHandlers.ofString()
        );
        HttpResponse<String> defaultResponse = client.send(
                defaultRequest,
                HttpResponse.BodyHandlers.ofString()
        );

        System.out.println("Catalog: " + http3Response.version());
        System.out.println("Status: " + defaultResponse.version());
    }
}
```

Trong trường hợp này, `http3Request` ưu tiên HTTP/3; `defaultRequest` vẫn dùng preference HTTP/2 của client. Hai request có thể dùng chung một `HttpClient`, do đó vẫn có thể hưởng lợi từ việc tái sử dụng tài nguyên và kết nối mà client quản lý.

Request cũng có thể ghi đè preference HTTP/3 của client. Ví dụ, nếu client được tạo bằng `.version(HttpClient.Version.HTTP_3)` nhưng một endpoint cần ưu tiên HTTP/2, hãy đặt `.version(HttpClient.Version.HTTP_2)` trên request đó. Quy tắc kế thừa và ghi đè được tóm tắt như sau:

| Preference của client | Preference của request | Preference hiệu lực cho request |
|---|---|---|
| Không cấu hình (mặc định HTTP/2) | Không cấu hình | HTTP/2 |
| HTTP/3 | Không cấu hình | HTTP/3 |
| HTTP/2 | HTTP/3 | HTTP/3 |
| HTTP/3 | HTTP/2 | HTTP/2 |

## 4. Hiểu preference và protocol thực tế

HTTP/1.1 và HTTP/2 dùng TCP; HTTP/3 dùng QUIC trên UDP. Ứng dụng không thể biết chắc server có nhận QUIC hay đường mạng có cho phép UDP trước khi kết nối được thiết lập. Vì vậy, `version(HTTP_3)` là preference để `HttpClient` chọn cách kết nối, không phải lệnh tự tạo một response HTTP/3 trong mọi tình huống.

Trong JDK built-in `HttpClient`, nếu không đặt option khám phá riêng, `H3_DISCOVERY` hoạt động theo chế độ `ANY`. Thuật toán cụ thể do implementation quyết định. Khi chưa có kết nối hoặc thông tin phù hợp, client có thể thử kết nối HTTP/3 qua QUIC và kết nối HTTP qua TLS/TCP; phiên trao đổi dùng giao thức của kết nối thành công trước. Nếu request đặt preference HTTP/3 trực tiếp, implementation có thể ưu tiên thử HTTP/3 trước kết nối TCP. Kết quả vẫn phụ thuộc môi trường và không được bảo đảm chỉ bởi dòng `.version(HTTP_3)`.

Thông tin `Alt-Svc` (HTTP Alternative Services) có thể giúp client biết server cung cấp HTTP/3 ở endpoint thay thế. Khi dùng chế độ `ANY`, implementation có thể tận dụng thông tin này đã nhận từ server. Do đó, hai request liên tiếp tới cùng origin có thể dùng hai phiên bản khác nhau, chẳng hạn request đầu tiên dùng HTTP/2 còn request tiếp theo dùng HTTP/3. Đây là hành vi khám phá giao thức, không phải lỗi trong việc đặt preference.

Không kiểm tra `client.version()` để kết luận giao thức của một response. Phương thức này trả về preference của client. Hãy kiểm tra `response.version()`:

```java
HttpResponse<String> response = client.send(
        request,
        HttpResponse.BodyHandlers.ofString()
);

switch (response.version()) {
    case HTTP_3 -> System.out.println("Request completed over HTTP/3");
    case HTTP_2 -> System.out.println("Request completed over HTTP/2");
    case HTTP_1_1 -> System.out.println("Request completed over HTTP/1.1");
}
```

Nên ghi log `response.version()` trong môi trường kiểm thử và production nếu ứng dụng cần quan sát mức sử dụng HTTP/3. Việc request hoàn tất với HTTP/2 hoặc HTTP/1.1 có thể là kết quả fallback hợp lệ. Nếu yêu cầu nghiệp vụ hoặc phép đo cần xác nhận HTTP/3, chỉ xem request đã đặt `HTTP_3` là chưa đủ bằng chứng.

## 5. Điều khiển cách khám phá HTTP/3 bằng `H3_DISCOVERY`

Java 26 bổ sung `HttpOption.H3_DISCOVERY` và enum `HttpOption.Http3DiscoveryMode`. Đây là option ở cấp request, truyền qua `HttpRequest.Builder.setOption(...)`, để gợi ý cách `HttpClient` tìm hoặc thiết lập kết nối HTTP/3.

Option này chỉ có tác dụng khi preference HTTP/3 đã được đặt ở client hoặc request. Nếu cả hai đều không chọn `HTTP_3`, `H3_DISCOVERY` bị bỏ qua. Với JDK built-in implementation, nếu không đặt option, chế độ mặc định là `ANY`.

| Chế độ | Cách hoạt động | Phù hợp khi |
|---|---|---|
| `ANY` | Dùng thuật toán riêng của implementation. JDK có thể thử QUIC và TLS/TCP, tận dụng thông tin Alt-Svc và chọn kết nối thành công trước. | Muốn ưu tiên HTTP/3 nhưng vẫn cho phép dùng HTTP/2 hoặc HTTP/1.1 nếu phù hợp. Đây là mặc định của JDK khi không chỉ định option. |
| `ALT_SVC` | Chỉ dùng thông tin HTTP Alternative Services để tìm hoặc thiết lập kết nối HTTP/3. Trước khi nhận được endpoint `h3` được quảng bá, request sẽ dùng HTTP/1.1 hoặc HTTP/2. | Server đang triển khai HTTP/3 theo lộ trình, quảng bá endpoint bằng header `Alt-Svc` và muốn lần đầu tiếp tục dùng giao thức hiện có. |
| `HTTP_3_URI_ONLY` | Chỉ thử HTTP/3 tại đúng authority (host và port) trong URI request; không dùng Alt-Svc và không fallback sang HTTP/2/HTTP/1.1. | Muốn kiểm tra hoặc yêu cầu kết nối HTTP/3 trực tiếp tới endpoint đã biết chắc hỗ trợ QUIC. |

### Ưu tiên HTTP/3 với fallback mặc định

Đây là lựa chọn phù hợp cho phần lớn ứng dụng: đặt HTTP/3 ở request hoặc client và để `ANY` xử lý việc khám phá. Có thể không cần gọi `setOption`:

```java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/data"))
        .version(HttpClient.Version.HTTP_3)
        .GET()
        .build();
```

JDK built-in implementation có thể thử HTTP/3 và các lựa chọn HTTP qua TCP. Nếu QUIC không thiết lập được nhưng HTTP/2 hoặc HTTP/1.1 hoạt động, request có thể hoàn tất bằng giao thức đó. Hãy quan sát `response.version()` để biết lựa chọn thực tế.

### Chờ server quảng bá HTTP/3 bằng Alt-Svc

Nếu server đang phục vụ HTTP/2 hoặc HTTP/1.1 trước và chỉ quảng bá HTTP/3 sau khi client gửi request, chọn `ALT_SVC`:

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpOption;
import java.net.http.HttpOption.Http3DiscoveryMode;
import java.net.http.HttpRequest;

HttpClient client = HttpClient.newBuilder().build();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/data"))
        .version(HttpClient.Version.HTTP_3)
        .setOption(HttpOption.H3_DISCOVERY, Http3DiscoveryMode.ALT_SVC)
        .GET()
        .build();
```

Ở chế độ này, request đầu tiên có thể dùng HTTP/1.1 hoặc HTTP/2 để nhận thông tin `Alt-Svc` từ origin. Khi có endpoint `h3` được quảng bá, các request sau có thể sử dụng endpoint thay thế đó. Nếu server không quảng bá HTTP/3, các request tiếp tục dùng HTTP/1.1 hoặc HTTP/2. Hãy kiểm tra header response và `response.version()` khi thử nghiệm; không cần tự đặt header `Alt-Svc` trong request.

### Chỉ cho phép HTTP/3

Khi cần xác nhận endpoint trực tiếp hỗ trợ HTTP/3, có thể đặt `HTTP_3_URI_ONLY`:

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpOption;
import java.net.http.HttpOption.Http3DiscoveryMode;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

HttpClient client = HttpClient.newBuilder().build();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://h3.example.com:443/health"))
        .version(HttpClient.Version.HTTP_3)
        .setOption(HttpOption.H3_DISCOVERY, Http3DiscoveryMode.HTTP_3_URI_ONLY)
        .GET()
        .build();

HttpResponse<String> response = client.send(
        request,
        HttpResponse.BodyHandlers.ofString()
);

if (response.version() != HttpClient.Version.HTTP_3) {
    throw new IllegalStateException("Expected HTTP/3, received " + response.version());
}
```

Ở chế độ này, server phải lắng nghe HTTP/3 qua QUIC tại đúng host và port của URI. Client không dùng endpoint thay thế từ Alt-Svc. Nếu server không có HTTP/3 tại authority đó hoặc kết nối QUIC không thiết lập được, request thất bại thay vì tự chuyển sang HTTP/2/HTTP/1.1. Chỉ dùng chế độ này khi thất bại là kết quả mong muốn, ví dụ trong bài kiểm tra xác nhận endpoint HTTP/3.

## 6. Điều kiện mạng, proxy và TLS

Trước khi bật HTTP/3 trong ứng dụng, kiểm tra các điều kiện sau:

1. **URI phải dùng HTTPS.** Request có URI scheme khác `https` sẽ không được gửi bằng HTTP/3. Hãy kiểm tra URI sau khi cấu hình endpoint, redirect và service discovery.
2. **Đường mạng phải cho phép QUIC/UDP.** HTTP/3 chạy trên QUIC qua UDP. Firewall, NAT, mạng doanh nghiệp hoặc chính sách egress có thể chặn UDP trong khi TCP vẫn hoạt động. Khi đó chế độ `ANY` có thể chọn HTTP/2 hoặc HTTP/1.1 nếu kết nối TCP thành công.
3. **Server phải hỗ trợ HTTP/3.** Với kết nối trực tiếp, server phải nhận QUIC tại host và port của URI. Nếu server quảng bá endpoint khác qua Alt-Svc, chế độ `ANY` hoặc `ALT_SVC` có thể dùng thông tin đó theo quy tắc khám phá.
4. **Kiểm tra proxy được chọn thực tế.** Trong JDK built-in implementation được mô tả ở Javadoc Java 26/27, HTTP/3 qua proxy chưa được hỗ trợ. Nếu proxy được chọn, `ANY` hoặc `ALT_SVC` sẽ hạ xuống HTTP/2 hoặc HTTP/1.1 và bỏ qua `H3_DISCOVERY`; `HTTP_3_URI_ONLY` sẽ làm request thất bại. Cấu hình proxy có thể đến từ `ProxySelector` mặc định hoặc cấu hình hệ thống, không chỉ từ lời gọi `.proxy(...)` trong code.
5. **Kiểm tra `SSLContext` và `SSLParameters`.** Cấu hình TLS tùy chỉnh phải tương thích với QUIC và HTTP/3 của implementation. Một `SSLContext` hoặc `SSLParameters` không đáp ứng yêu cầu có thể khiến `UnsupportedProtocolVersionException` xuất hiện khi build client đặt HTTP/3 hoặc khi gửi request ở chế độ `HTTP_3_URI_ONLY`.
6. **Kiểm tra server và client sau redirect.** Redirect có thể đưa request sang URI hoặc authority khác. Đừng giả định endpoint đích của redirect có cùng hỗ trợ HTTP/3 như endpoint ban đầu; tiếp tục kiểm tra `response.version()` và chính sách redirect của client.

`UnsupportedProtocolVersionException` là một `IOException` báo rằng client không hỗ trợ phiên bản giao thức được yêu cầu. Với cấu hình HTTP/3 nghiêm ngặt, hãy xử lý ngoại lệ này như tín hiệu môi trường hoặc cấu hình không đáp ứng yêu cầu; không bắt ngoại lệ rồi âm thầm coi request là đã chạy HTTP/3.

## 7. Chọn cách cấu hình theo tình huống

| Tình huống | Cấu hình nên bắt đầu | Cách xác nhận |
|---|---|---|
| Hầu hết request của ứng dụng đều ưu tiên HTTP/3 | `HttpClient.Builder.version(HTTP_3)` | Log `HttpResponse.version()` cho từng response. |
| Chỉ một vài endpoint thử HTTP/3 | `HttpRequest.Builder.version(HTTP_3)` trên các request đó | So sánh response của request đặt và không đặt preference. |
| Một client mặc định HTTP/3 nhưng endpoint cụ thể dùng HTTP/2 | Client đặt `HTTP_3`, request đó đặt `HTTP_2` | Xác nhận request ngoại lệ trả về `HTTP_2` khi môi trường cho phép. |
| Server sẽ quảng bá HTTP/3 qua Alt-Svc | Chọn `HTTP_3` và `H3_DISCOVERY = ALT_SVC` | Request đầu nhận `Alt-Svc`; request sau có thể trả về `HTTP_3`. |
| Kiểm tra endpoint có QUIC trực tiếp | Chọn `HTTP_3` và `H3_DISCOVERY = HTTP_3_URI_ONLY` | Chỉ chấp nhận response `HTTP_3`; kết nối không đáp ứng phải thất bại. |
| Môi trường có proxy hoặc UDP bị chặn | Kiểm tra proxy và mạng trước; giữ fallback `ANY` nếu HTTP/2/1.1 vẫn được chấp nhận | Ghi `response.version()` và kiểm tra cấu hình proxy/network. |

Không có lựa chọn nào tự động làm HTTP/3 nhanh hơn trong mọi trường hợp. Lợi ích phụ thuộc độ trễ đường truyền, mất gói, khả năng server, tải thực tế và cách triển khai mạng. Với ứng dụng production, nên thử trên môi trường tương đương, theo dõi latency theo percentile, tỷ lệ lỗi, timeout và protocol thực tế trước khi mở rộng phạm vi cấu hình.

## 8. Tương thích JDK và cách kiểm chứng

`HttpClient.Version.HTTP_3` được giới thiệu từ Java 26. `HttpOption`, `H3_DISCOVERY` và `Http3DiscoveryMode` cũng là API từ Java 26. Các API này thuộc module Java SE `java.net.http`, không phải incubator module.

- Dùng JDK 26 trở lên để biên dịch mã tham chiếu `HTTP_3`.
- Nếu dùng compiler mới để tạo artifact cho Java 26, có thể giới hạn API nền tảng bằng `javac --release 26`.
- Nếu dự án còn phải chạy trên Java 25 hoặc thấp hơn, mã nguồn tham chiếu trực tiếp `HTTP_3` không thể biên dịch với API của target đó. Cần xác định rõ baseline JDK trước khi đưa cấu hình này vào thư viện dùng chung.
- Không thêm `--enable-preview` cho HTTP/3; đây là tính năng hoàn tất của Java 26.
- Tài liệu Java 27 tiếp tục liệt kê `HttpClient.Version.HTTP_3` và `H3_DISCOVERY`, do đó kiến thức cấu hình này vẫn áp dụng cho JDK 27. Với JDK của nhà cung cấp khác, kiểm tra tài liệu implementation và khả năng hỗ trợ HTTP/3 trước khi triển khai.

Ví dụ biên dịch khi dùng JDK 26 hoặc mới hơn:

```bash
javac --release 26 -d out src/ClientLevelHttp3.java
java -cp out ClientLevelHttp3
```

Khi kiểm thử, nên bao gồm các trường hợp sau:

- Server hỗ trợ HTTP/3 và đường UDP/QUIC thông suốt: xác nhận response thực sự dùng `HTTP_3`.
- Server chỉ hỗ trợ HTTP/2 hoặc HTTP/1.1: xác nhận `ANY` có thể fallback và ứng dụng vẫn xử lý response đúng.
- Server quảng bá `Alt-Svc`: xác nhận chế độ `ALT_SVC` dùng HTTP/1.1 hoặc HTTP/2 trước khi có thông tin, sau đó có thể dùng HTTP/3.
- Server không hỗ trợ HTTP/3 tại authority trong URI: xác nhận `HTTP_3_URI_ONLY` thất bại như mong đợi.
- Môi trường có proxy: xác nhận hành vi downgrade hoặc exception theo discovery mode.
- Client dùng TLS tùy chỉnh: kiểm tra việc tạo client và gửi request với cấu hình `SSLContext`/`SSLParameters` thực tế.

Ghi nhận cả status code và `response.version()`. Một HTTP status `200` chỉ xác nhận server đã trả lời thành công; nó không cho biết response dùng HTTP/3 hay HTTP/2. Có thể bổ sung log server, log proxy hoặc packet capture để kiểm chứng transport khi cần phân tích sâu.

## 9. Checklist triển khai

- [ ] Đã xác nhận ứng dụng biên dịch và chạy trên JDK 26 trở lên có hỗ trợ API HTTP/3.
- [ ] Đã chọn rõ preference ở cấp client hay request dựa trên phạm vi cần áp dụng.
- [ ] Đã hiểu request-level `version(...)` ghi đè preference của client.
- [ ] Đã chọn discovery mode phù hợp: `ANY`, `ALT_SVC` hoặc `HTTP_3_URI_ONLY`.
- [ ] Đã xác nhận URI dùng HTTPS và server hỗ trợ HTTP/3 tại endpoint phù hợp.
- [ ] Đã kiểm tra UDP/QUIC, firewall, NAT, proxy và cấu hình mạng thực tế.
- [ ] Đã kiểm tra `SSLContext`/`SSLParameters` nếu ứng dụng dùng cấu hình TLS tùy chỉnh.
- [ ] Đã xử lý `UnsupportedProtocolVersionException`, timeout và fallback theo yêu cầu nghiệp vụ.
- [ ] Đã quan sát `HttpResponse.version()` thay vì chỉ dựa vào preference đã cấu hình.
- [ ] Đã chạy kiểm thử trên server và môi trường gần production, đo latency, tỷ lệ lỗi và protocol thực tế.
