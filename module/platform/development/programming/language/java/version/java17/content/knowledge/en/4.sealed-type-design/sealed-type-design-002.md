# Combining `sealed interface` with `record` in Java 17

> **Topic:** Java 17  
> **Chapter:** Designing with `sealed`  
> **Goal:** Design a data type family with a controlled set of cases, represent each case using a `record`, handle them with stable Java 17 syntax, and understand the limitations of this design approach.

## 1. The Problem: One Value with Multiple Shapes, Each Carrying Different Data

Suppose a payment system must return one of two outcomes:

- **Paid:** has an order ID, an amount, and a transaction ID.
- **Declined:** has an order ID and a rejection reason.

Both are *payment outcomes*, but their accompanying data differs. We want to store and pass the result through a common type while preventing arbitrary classes elsewhere from adding new outcome kinds outside the design.

In Java 17, this can be solved by combining two features:

| Component | Role | What it guarantees |
|---|---|---|
| `sealed interface` | Declares **the set of permitted direct subtypes** | Only permitted classes/interfaces may directly `implements` or `extends` the `sealed` type |
| `record` | Represents **the data of each case** | Auto-generates the canonical constructor, accessors, `equals`, `hashCode`, `toString`; a record class is implicitly `final` |

Conceptual example:

```text
                  PaymentResult
              «sealed interface»
                      │
          ┌───────────┴───────────┐
          │                       │
    Paid (record)           Declined (record)
    - orderId               - orderId
    - amount                - reason
    - transactionId
```

In data modeling terms, this is a **sum type** (or *tagged union*): a value belongs to **one of the variants**. Each `record` carries its own set of fields (a *product type*). Java has no dedicated `sum type` keyword; a `sealed interface` combined with `record` is a clear and controlled way to express it.

## 2. Two Building Blocks to Master in Java 17

### 2.1. `sealed interface` Controls Permitted Implementations

Declaration:

```java
sealed interface PaymentResult permits Paid, Declined {
    String orderId();
}
```

The `sealed` keyword declares that `PaymentResult` is **not** an interface that any class can directly implement. The `permits` clause lists the exact permitted direct subtypes: `Paid` and `Declined`.

A type **not appearing in the list** cannot arbitrarily implement `PaymentResult`:

```java
// Invalid if Pending is not in `permits`.
record Pending(String orderId) implements PaymentResult { }
```

The compiler will report an error stating that `Pending` is not a permitted subtype of the `sealed` interface.

Important Java 17 rules:

1. A direct subtype of a `sealed` type must be listed in `permits`, unless the list can be **inferred** because all direct subtypes are in the same compilation unit.
2. A permitted direct subtype must explicitly state its further inheritance policy: `final`, `sealed`, or `non-sealed`. A `record` satisfies this rule because it is **implicitly `final`**, so you do not need to—and must not—write `final` explicitly as a requirement.
3. If the types belong to a **named module**, permitted subtypes must reside **in the same module** as the `sealed` type. If they belong to an **unnamed module** (common when compiling without `module-info.java`), they must be in the **same package**. This rule keeps the list of variants within a controllable boundary.
4. `permits` controls only **direct subtypes**. If a permitted subtype is declared `non-sealed`, it can reopen the inheritance tree along that branch.

**Terminology note:** `sealed` does not mean "only two objects can be created"; it means "only the declared direct inheritance branches exist." You can create millions of distinct `Paid` and `Declined` objects.

### 2.2. `record` Describes the Data of Each Variant

Declaring a simple record:

```java
record Declined(String orderId, String reason) implements PaymentResult { }
```

Java generates members behaviorally equivalent to:

```java
// Example using the API generated by a record; this is not code you write manually.
Declined declined = new Declined("ORD-100", "Insufficient limit");

String id = declined.orderId();    // Accessor: orderId()
String reason = declined.reason();  // Accessor: reason()
System.out.println(declined);      // toString()
```

Key characteristics of `record` to remember:

- The **record components** such as `orderId` and `reason` define the record's state data.
- A record has corresponding **`private final`** instance fields and public accessors named after the components, such as `orderId()`; no JavaBean `getOrderId()` getter is generated automatically.
- The *canonical constructor* initializes the components. You can customize it to **validate** or normalize data.
- `equals`/`hashCode` compare by record components; `toString` describes the type name along with its components. This fits value-based data objects.
- A record is implicitly **`final`**, directly extends `java.lang.Record`, and cannot explicitly `extends` another class; however, it can `implements` one or more interfaces.

Because a record is inherently `final`, combining it with `sealed interface` is very natural: the interface restricts the variant set, and each record provides a leaf variant with its corresponding data.

### 2.3. Both Features Are Stable in Java 17

- `record` has been a standard feature since **Java 16**.
- `sealed class`/`sealed interface` has been a standard feature since **Java 17**.
- **Pattern matching for `instanceof`** has been a standard feature since Java 16 and works normally in Java 17.

Therefore, the examples below compile on **JDK 17** with standard commands, without `--enable-preview`.

## 3. Complete Example: Payment Result

Place all the code below into `PaymentDemo.java`:

```java
import java.math.BigDecimal;
import java.util.Objects;

public class PaymentDemo {

    // Only Paid or Declined may directly implement PaymentResult.
    sealed interface PaymentResult permits Paid, Declined {
        String orderId();
    }

    // Record auto-generates orderId(), amount(), transactionId(),
    // equals(), hashCode(), and toString().
    record Paid(String orderId,
                BigDecimal amount,
                String transactionId) implements PaymentResult {

        // Compact canonical constructor: validates input invariants.
        Paid {
            Objects.requireNonNull(orderId, "orderId");
            Objects.requireNonNull(amount, "amount");
            Objects.requireNonNull(transactionId, "transactionId");

            if (orderId.isBlank() || transactionId.isBlank()) {
                throw new IllegalArgumentException("IDs must not be blank");
            }
            if (amount.signum() <= 0) {
                throw new IllegalArgumentException("Amount must be positive");
            }
        }
    }

    record Declined(String orderId,
                    String reason) implements PaymentResult {

        Declined {
            Objects.requireNonNull(orderId, "orderId");
            Objects.requireNonNull(reason, "reason");

            if (orderId.isBlank() || reason.isBlank()) {
                throw new IllegalArgumentException("Content must not be blank");
            }
        }
    }

    static String describe(PaymentResult result) {
        Objects.requireNonNull(result, "result");

        // Pattern matching for instanceof is a standard feature in Java 17.
        if (result instanceof Paid paid) {
            return "Order " + paid.orderId()
                    + " paid " + paid.amount()
                    + ", transaction " + paid.transactionId();
        }

        if (result instanceof Declined declined) {
            return "Order " + declined.orderId()
                    + " declined: " + declined.reason();
        }

        // Java 17 does not check exhaustiveness for if/instanceof chains.
        throw new IllegalStateException(
                "Unhandled variant: " + result.getClass().getName());
    }

    public static void main(String[] args) {
        PaymentResult first = new Paid(
                "ORD-100",
                new BigDecimal("125000"),
                "TXN-88");

        PaymentResult second = new Declined(
                "ORD-101",
                "Insufficient credit limit");

        System.out.println(describe(first));
        System.out.println(describe(second));
    }
}
```

Compile and run with JDK 17:

```bash
javac --release 17 PaymentDemo.java
java PaymentDemo
```

Expected output:

```text
Order ORD-100 paid 125000, transaction TXN-88
Order ORD-101 declined: Insufficient credit limit
```

**Things to observe:**

1. The variables `first` and `second` share the declared type `PaymentResult`, yet hold different record instances at runtime.
2. `PaymentResult` declares a common contract `orderId()`; each record automatically provides the matching method via its `orderId` component.
3. `Paid` contains only data that makes sense for a successful payment; `Declined` contains only data for a declined payment. There is no need to create a class with multiple optional fields like `amount`, `transactionId`, `reason` and then check hard-to-control `null` combinations.
4. Inside `if (result instanceof Paid paid)`, Java already narrows `paid` to `Paid`. No manual `(Paid) result` cast is needed.
5. Both records are directly permitted by `permits`; a third record would be rejected by the compiler unless added to the list.

In this single-file example, `PaymentResult`, `Paid`, and `Declined` are nested inside `PaymentDemo`. Nested records are **implicitly static**, so no `PaymentDemo` instance is needed to instantiate them.

## 4. Why Is This Better Than a Class with Many Optional Fields?

A looser way to model this is to create an object like the following:

```java
// Example of a model that easily allows contradictory states.
class PaymentResponse {
    boolean success;
    String orderId;
    BigDecimal amount;        // Only meaningful when success = true
    String transactionId;     // Only meaningful when success = true
    String failureReason;     // Only meaningful when success = false
}
```

That design allows an object with `success = true` yet a non-`null` `failureReason`, or `success = false` yet still having a transaction ID. Calling code has to manually check multiple combined conditions.

When replaced by `sealed interface PaymentResult` with two records `Paid`/`Declined`, the type structure clearly expresses the distinction:

| Criterion | One class with many optional fields | `sealed interface` + `record` |
|---|---|---|
| Set of valid cases | Usually checked with flags and runtime conditions | Expressed via permitted subtypes |
| Per-case data | Has many unrelated fields, often `null` | Each record declares only the components it needs |
| Adding another result kind | Can appear simply by adding flag or string values | Requires a controlled edit to the `permits` declaration |
| Data immutability | Must be implemented manually | Records have `final` member fields automatically, subject to *shallow immutability* |
| `equals`/`hashCode`/`toString` | Often written manually or via libraries | Auto-generated by the record |

This is a strong choice when **the set of variants is known in advance and has clear domain meaning**: processing states, system events, computation outcomes, commands, AST nodes, or internal messages.

## 5. Writing and Using `sealed interface` Records in Multi-File Projects

In real-world programs, each public type is usually placed in its own file, in the same package or same named module per Java 17 rules.

```text
src/main/java/com/example/payment/
    PaymentResult.java
    Paid.java
    Declined.java
```

`PaymentResult.java`:

```java
package com.example.payment;

public sealed interface PaymentResult permits Paid, Declined {
    String orderId();
}
```

`Paid.java`:

```java
package com.example.payment;

import java.math.BigDecimal;

public record Paid(String orderId, BigDecimal amount, String transactionId)
        implements PaymentResult { }
```

`Declined.java`:

```java
package com.example.payment;

public record Declined(String orderId, String reason)
        implements PaymentResult { }
```

Structurally, these three files produce the exact same type relationships as the earlier single-file example. For production use, add input validation and your project's nullability/serialization conventions, such as the compact constructors demonstrated earlier.

Example client code from another package:

```java
import com.example.payment.Declined;
import com.example.payment.Paid;
import com.example.payment.PaymentResult;
import java.math.BigDecimal;

class Example {
    public static void main(String[] args) {
        PaymentResult response = new Paid(
                "ORD-100", new BigDecimal("100"), "TXN-1");
        System.out.println(response.orderId());

        if (response instanceof Paid paid) {
            System.out.println(paid.transactionId());
        } else if (response instanceof Declined declined) {
            System.out.println(declined.reason());
        }
    }
}
```

You cannot create a new public `record` in an unauthorized package/module and have it directly `implements PaymentResult` if that type is not in the `permits` list.

### When Can `permits` Be Omitted?

Java 17 allows inferring the list of direct subtypes when they are declared **in the same compilation unit**. For example, a single `Message.java` file:

```java
sealed interface Message { }

record TextMessage(String text) implements Message { }

record NumberMessage(int number) implements Message { }
```

Here, the compiler infers `TextMessage` and `NumberMessage` as the permitted cases. However, when split across multiple files, `permits` should be declared explicitly. For team APIs or long-lived libraries, an explicit list also lets readers see all variants right away.

## 6. Rules for `final`, `sealed`, `non-sealed`: Where Does `record` Fit?

A sealed hierarchy can contain classes, interfaces, and records. Suppose:

```java
sealed interface Event permits Created, Retried, SystemEvent { }

record Created(String id) implements Event { }

record Retried(String id, int count) implements Event { }

non-sealed class SystemEvent implements Event { }
```

- `Created` and `Retried` are terminal branches because records are implicitly `final`.
- `SystemEvent` is marked `non-sealed`, allowing other types to extend it under standard inheritance rules.
- The restriction is enforced at the **direct** subtypes of `Event`, not across all descendants if a `non-sealed` branch has been opened.

When modeling closed data cases, **prefer records for leaf branches**, and think carefully before adding `non-sealed`: an open branch means the actual runtime types are no longer limited to the concrete classes listed in `permits`.

If one case needs to allow multiple controlled subtypes, you can declare an intermediate `sealed interface`:

```java
sealed interface Command permits UserCommand, Shutdown { }

sealed interface UserCommand extends Command permits CreateUser, DeleteUser { }

record CreateUser(String name) implements UserCommand { }
record DeleteUser(long id) implements UserCommand { }
record Shutdown() implements Command { }
```

In this hierarchy, `UserCommand` acts as an intermediate branch that remains sealed, while `CreateUser`, `DeleteUser`, and `Shutdown` are the leaf records.

**Design rule:** A `record` cannot `extends` any class other than `java.lang.Record`; therefore, you cannot use a `record` as a base class in a class inheritance hierarchy. To group records, use an **interface**, including a `sealed interface` when you want to fix the set of variants.

## 7. Handling Variants in Java 17

### 7.1. `instanceof` Pattern Matching

Java 17 supports this directly:

```java
static void printResult(PaymentResult result) {
    if (result instanceof Paid paid) {
        System.out.println("Transaction: " + paid.transactionId());
    } else if (result instanceof Declined declined) {
        System.out.println("Reason: " + declined.reason());
    } else {
        throw new IllegalStateException("Unhandled case");
    }
}
```

The pattern variables `paid`/`declined` can only be used in regions where Java knows the `instanceof` check succeeded. This is a **type pattern**, not a record pattern. In Java 17, you must call `paid.transactionId()` to retrieve a record's components; destructuring multiple components with record patterns belongs to newer Java versions.

### 7.2. Avoid `switch` Syntax from Newer Java Versions

The following example often appears in modern Java articles:

```java
// DO NOT use as stable Java 17 syntax:
// return switch (result) {
//     case Paid paid -> paid.transactionId();
//     case Declined declined -> declined.reason();
// };
```

**In Java 17, pattern matching for `switch` is still a *preview* feature** (JEP 406), requiring preview flags and not yet stable syntax/API for general Java 17 lessons. Pattern `switch` became a standard feature in **Java 21** (JEP 441); record patterns were also finalized in **Java 21** (JEP 440). Do not copy code written for Java 21 and expect `javac --release 17` to compile it.

Therefore, if a project **is compiling against Java 17**, use `if`/`else if` with `instanceof` patterns or polymorphism via interface methods.

### 7.3. Polymorphism: Put Common Behavior on the Interface

When handling logic naturally belongs to each variant, you can define a common method on the `sealed interface` and let each record provide its own implementation:

```java
public class DisplayDemo {
    sealed interface Notification permits Info, Warning {
        String displayText();
    }

    record Info(String message) implements Notification {
        @Override
        public String displayText() {
            return "[INFO] " + message;
        }
    }

    record Warning(String message, int severity) implements Notification {
        @Override
        public String displayText() {
            return "[WARNING " + severity + "] " + message;
        }
    }

    static void show(Notification notification) {
        System.out.println(notification.displayText());
    }

    public static void main(String[] args) {
        show(new Info("Saved"));
        show(new Warning("Needs review", 2));
    }
}
```

Benefit: you avoid repeating `instanceof` chains across multiple places. Adding a new variant forces the new record to implement `displayText()` per the contract, enabling the compiler to catch missing method implementations.

**Which approach should you choose?** If the behavior is a natural responsibility of the object itself (e.g., `displayText`, `amount`, `isRetryable`), polymorphism is usually cleaner. If the handling belongs to an outer layer (converting to DTOs, exporting JSON, database mapping, UI rendering), `instanceof` in a single centralized place can make sense. Avoid scattering many `instanceof` chains across the entire application.

### 7.4. Exhaustiveness of Handling Branches

An important point to remember: even though Java 17 knows `PaymentResult` directly permits only `Paid` and `Declined`, **the compiler does not verify that an `if`/`else if` chain covers all branches**. If a `Pending` record is later added to `permits`, old `if` code may still compile yet fall into the default branch when receiving `Pending`.

Practical safeguards in Java 17:

- Keep branching logic concentrated in a small number of clear functions or conversion points.
- Include a default branch that throws a specifically named exception or applies an intentional fallback rule.
- Update handler functions whenever the `permits` list changes and add tests for new variants in your **application development workflow**.
- Use polymorphism for behavior that fits a shared contract so the compiler enforces implementation in new records.

Do not advertise Java 21's pattern `switch` *exhaustiveness* checking as a built-in guarantee for Java 17.

## 8. Making Records Truly Immutable for Domain Data

### 8.1. `record` Is Reference-Immutable, Not Automatically Deeply Immutable

A record guarantees that component backing fields are `final`, but it **does not deep-copy referenced data**. For example:

```java
import java.util.ArrayList;
import java.util.List;

record Batch(List<String> ids) { }

class Example {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>();
        list.add("ORD-1");

        Batch batch = new Batch(list);
        list.add("ORD-2");

        System.out.println(batch.ids()); // [ORD-1, ORD-2]
    }
}
```

The reference `ids` cannot be reassigned after the record is created, but the original list can still change. When a record represents a snapshot or value object, make an immutable copy of mutable data:

```java
import java.util.List;
import java.util.Objects;

record Batch(List<String> ids) {
    Batch {
        Objects.requireNonNull(ids, "ids");
        ids = List.copyOf(ids);
    }
}
```

In a **compact constructor**, assigning `ids = List.copyOf(ids)` normalizes the constructor parameter; Java automatically assigns that value to the record field once the constructor body completes. Do not write `this.ids = ...` inside a compact constructor.

`List.copyOf` creates a structurally unmodifiable list and rejects `null` elements, though if the elements themselves are mutable objects, you still need an appropriate deep-copy strategy or immutable element types. Likewise, for `byte[]`, mutable `Date` objects, or nested maps/lists, consider copying on input **and** on accessor return if deep immutability is required.

### 8.2. Each Variant's Constructor Is Where Invariants Live

```java
import java.math.BigDecimal;
import java.util.Objects;

sealed interface PriceResult permits ValidPrice, InvalidPrice { }

record ValidPrice(BigDecimal value) implements PriceResult {
    ValidPrice {
        Objects.requireNonNull(value, "value");
        if (value.signum() < 0) {
            throw new IllegalArgumentException("Price must not be negative");
        }
    }
}

record InvalidPrice(String errorCode) implements PriceResult {
    InvalidPrice {
        Objects.requireNonNull(errorCode, "errorCode");
        if (errorCode.isBlank()) {
            throw new IllegalArgumentException("Error code must not be blank");
        }
    }
}
```

`sealed` protects **the shape of the variant set**; the `record` constructor protects **the valid values of each variant**. These are two distinct layers of protection and should be used together.

Note also: a record's default `equals` depends on the `equals` of its reference components. For example, `BigDecimal("10.0")` and `BigDecimal("10.00")` are not equal according to `BigDecimal.equals` because their scales differ. If the business domain considers two such values equivalent, define explicit component normalization at the data boundary rather than assuming records automatically solve domain equality.

## 9. Generic Design: Success or Failure Result

A `sealed interface` does not have to be tied to one fixed domain operation. A common reusable pattern is `Result<T>`:

```java
import java.util.Objects;

public class GenericResultDemo {

    sealed interface Result<T> permits Success, Failure { }

    record Success<T>(T value) implements Result<T> {
        Success {
            Objects.requireNonNull(value, "value");
        }
    }

    record Failure<T>(String code, String message) implements Result<T> {
        Failure {
            Objects.requireNonNull(code, "code");
            Objects.requireNonNull(message, "message");
        }
    }

    static Result<String> loadUsername(int userId) {
        if (userId == 1) {
            return new Success<>("Minh");
        }
        return new Failure<>("NOT_FOUND", "User not found");
    }

    static void print(Result<String> result) {
        if (result instanceof Success<?> success) {
            System.out.println("Name: " + success.value());
        } else if (result instanceof Failure<?> failure) {
            System.out.println(failure.code() + ": " + failure.message());
        } else {
            throw new IllegalStateException("Unhandled Result");
        }
    }

    public static void main(String[] args) {
        print(loadUsername(1));
        print(loadUsername(99));
    }
}
```

Compile/run:

```bash
javac --release 17 GenericResultDemo.java
java GenericResultDemo
```

Output:

```text
Name: Minh
NOT_FOUND: User not found
```

Here `Success<T>` holds a success value of type `T`, while `Failure<T>` carries error data yet still implements `Result<T>` so it can be returned from the same method. When using `instanceof Success<?>`, the expression `success.value()` has type `Object` due to generic type erasure at runtime; Java 17 does not allow `instanceof Success<String>` because generic type arguments are not fully preserved at runtime. If you need to return `T` with exact typing, you can design a branching method or an explicit generic handling API to avoid unchecked casts.

In real applications, `Result<T>` can add transformation methods, error handling, or a standard error structure, but weigh the scope carefully: there is no need to wrap every simple method in `Result` when exceptions or standard return types already express the contract cleanly.

## 10. Recursive Model: Expression Tree with `sealed interface` and `record`

Another application is a mathematical expression tree. Each node is one of two forms: an integer literal or the addition of two child expressions.

```java
public class ExpressionDemo {

    sealed interface Expr permits NumberExpr, Add { }

    record NumberExpr(int value) implements Expr { }

    record Add(Expr left, Expr right) implements Expr {
        Add {
            java.util.Objects.requireNonNull(left, "left");
            java.util.Objects.requireNonNull(right, "right");
        }
    }

    static int evaluate(Expr expr) {
        if (expr instanceof NumberExpr number) {
            return number.value();
        }
        if (expr instanceof Add add) {
            return Math.addExact(
                    evaluate(add.left()),
                    evaluate(add.right()));
        }
        throw new IllegalStateException("Unhandled expression type");
    }

    public static void main(String[] args) {
        Expr expression = new Add(
                new NumberExpr(2),
                new Add(new NumberExpr(3), new NumberExpr(4)));

        System.out.println(evaluate(expression)); // 9
    }
}
```

The interesting point is that `sealed interface` restricts the **node kinds** (`NumberExpr`, `Add`), yet **does not restrict the number of nodes** that can be created or the depth of the tree. Because `record Add` has two components of type `Expr`, every child expression continues to follow the same model.

`Math.addExact` causes addition to throw `ArithmeticException` on integer overflow; the example chooses this so overflow is never silently ignored. For other problems, you can use `long` or `BigInteger` if a larger range is needed.

## 11. When Should You Apply This—and When Should You Not?

### Good Fit When

- The domain has a **well-defined set of variants** expected to evolve under control: `Accepted`/`Rejected`, `Pending`/`Completed`/`Failed`, groups of events or commands.
- Each variant is expressed primarily through **data** and has a few invariants checked in its constructor.
- You want the API to publish the permitted set of types, preventing arbitrary external implementations.
- You want to reduce data-object boilerplate and get consistent `equals`/`hashCode`/`toString`.

### Consider Alternatives When

- **You only need a set of constants without per-case data:** an `enum` is usually simpler, e.g. `enum ConnectionState { NEW, OPEN, CLOSED }`.
- **Library users must supply their own implementations:** a regular `interface` may fit better because `sealed` intentionally restricts extension.
- **Objects have continuously changing state**, lifecycles, class inheritance, or distinct entity identity: regular classes or domain-designed aggregates may fit better than `record`.
- **Data comes from JSON/APIs/databases:** sealed/record can still be used, but you must determine how your serialization library distinguishes variants, handles missing fields, versioning, and constructors. Do not assume every serializer understands `sealed interface` out of the box.

`sealed interface` expresses *closing the set of types*, while `record` models value-based data. Use both together when those two properties match the true requirements of your domain.

## 12. Common Pitfalls When Combining `sealed interface` and `record`

| Mistake or misconception | Why it is wrong | How to handle it in Java 17 |
|---|---|---|
| `record C(...) implements X` when `C` is not in `X permits` | An unpermitted type cannot directly implement a sealed interface | Add `C` to `permits` when intentionally extending the model |
| Placing an implementation in an invalid package/module | Java 17 restricts where permitted subtypes live: same named module, or same package in an unnamed module | Place types in a valid module/package structure |
| Trying to make a `record` `extends SomeBaseClass` | Records already extend `java.lang.Record` and cannot extend arbitrary classes | Implement interfaces (`implements`); redesign the type hierarchy |
| Assuming all record components are deeply immutable | `final` holds the reference, not freezing a referenced `List`/`Map`/array | Make defensive copies and use immutable component types |
| Calling `getOrderId()` expecting a default record accessor | A record accessor is `orderId()` | Use `orderId()` or explicitly define extra API methods if needed |
| Writing `case Paid paid ->` in `switch` with `--release 17` | Pattern `switch` is not stable in Java 17 | Use `instanceof` patterns or polymorphic methods |
| Writing record pattern syntax like `instanceof Paid(var id, var amount, var tx)` | Record patterns are not part of stable Java 17 | Use `instanceof Paid paid` and call its accessors |
| Assuming `if/else if` is checked for variant exhaustiveness | Java 17 does not verify exhaustiveness of `if` chains | Centralize handling, provide an explicit fallback, and update tests when adding variants |
| Using `non-sealed` while assuming only records in `permits` appear at runtime | A `non-sealed` branch can be extended with other subtypes | Only open a branch intentionally; prefer leaf records for closed models |
| Using `record` with `BigDecimal`, arrays, or mutable components assuming business equality works automatically | Record `equals` compares components directly without normalizing values or deep-comparing every structure | Choose appropriate components and define data normalization/equality explicitly |

## 13. Practice Exercises

### Exercise 1 — Task State Management

Design a `TaskState` type with exactly three variants:

1. `Queued(String taskId, long createdAt)`.
2. `Running(String taskId, int percent)`; `percent` must be between `0` and `100`.
3. `Completed(String taskId, String outputPath)`.

Requirements: create a `sealed interface TaskState` declaring `taskId()`, write the corresponding `record` types, and use `instanceof` patterns to format status messages. Do not use pattern matching for `switch`.

<details>
<summary>Java 17 Solution Hint</summary>

```java
public class TaskStateDemo {
    sealed interface TaskState permits Queued, Running, Completed {
        String taskId();
    }

    record Queued(String taskId, long createdAt) implements TaskState { }

    record Running(String taskId, int percent) implements TaskState {
        Running {
            if (percent < 0 || percent > 100) {
                throw new IllegalArgumentException("percent must be in [0, 100]");
            }
        }
    }
```

## 14. Summary and Reference Documentation

In Java 17, `sealed interface` is used to **restrict variants**, while `record` describes **each variant's data** with minimal boilerplate. Permitted records directly implement the sealed interface without needing an extra `final` modifier, since records are implicitly final. Validate data via compact canonical constructors, handle variants using `instanceof` patterns or polymorphism, and remember that a `record` is only shallowly immutable if it holds references to mutable data.
