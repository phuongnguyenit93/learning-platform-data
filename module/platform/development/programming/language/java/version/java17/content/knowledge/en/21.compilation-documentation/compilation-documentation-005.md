# Annotation Processors and Compile-Time Dependencies in Java 17

Annotations in Java can carry metadata processed by compilers, frameworks, or build tools. An **annotation processor** is a program that runs during compilation to inspect annotations, validate source code, and optionally generate additional source files, class files, or resources.

Annotation processing is part of the Java Compiler API (JSR 269), not runtime Reflection. When configuring a build, separate three dependency groups cleanly:

- **Compile-time dependency:** libraries required by the compiler to compile source code, such as annotation APIs referenced in source.
- **Annotation processor dependency:** libraries containing processors and the dependencies those processors need to execute inside the compiler.
- **Runtime dependency:** libraries required when the application runs, such as when generated classes reference a runtime API.

These three groups may overlap in certain libraries, yet their roles differ. Misplacing a processor onto the runtime classpath or omitting an annotation API from the compile classpath commonly breaks builds or causes runtime failures.

## 1. What is annotation processing?

An annotation processor reads annotations in source code and performs work while the compiler is compiling. Common tasks include:

- Enforcing annotation usage rules and reporting errors immediately at compile time.
- Generating implementations, adapters, mappers, builders, or metadata.
- Generating service registration files, resources, or configuration.
- Generating helper code for serialization, dependency injection, or data access.
- Checking consistency across multiple types within a single compilation.

For example, source code contains an annotation:

~~~java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateGreeting {
}
~~~

A developer annotates a class:

~~~java
package demo;

@GenerateGreeting
public class Example {
}
~~~

A processor can detect `@GenerateGreeting` and generate an `ExampleGreeting` class in the same package. The compiler then proceeds to compile the newly generated source.

### 1.1. Processors run at compile time, not every time the application runs

~~~text
Source code + annotation API
          |
          v
       Compiler
          |
          +----> Annotation processor
          |          |
          |          +---- read annotations / model
          |          +---- validate source code
          |          +---- generate source / resource
          |                       |
          +<----------------------+
          |
          v
    Subsequent processing rounds
          |
          v
      Compile final source
          |
          v
       .class files
          |
          v
    Run application on JVM
~~~

A processor is not automatically packaged into the application. It is typically needed only during the build. Only the classes and resources generated by the processor become part of the compilation output.

### 1.2. Distinguishing annotation processing from Reflection

| Characteristic | Annotation processor | Reflection |
|---|---|---|
| Timing | During compilation | When the program runs |
| Main API | `javax.annotation.processing`, `javax.lang.model` | `java.lang.reflect` |
| Input | Source/type elements and language model | Loaded classes and objects |
| Can generate source | Yes, via `Filer` | Not the purpose of Reflection |
| Can report compile errors | Yes, via `Messager` | No; errors occur at runtime |
| Must annotation be retained at runtime? | Not necessarily | Appropriate retention is required to read via Reflection |

Annotations with `RetentionPolicy.SOURCE` are still handled by processors because they exist in the source model at compile time. After compilation, those annotations are not retained in class files.

## 2. Core annotation processor APIs

The key types in Java 17 reside in the `java.compiler` module.

| API | Role |
|---|---|
| `AbstractProcessor` | Convenient base class for writing a processor |
| `Processor` | Primary contract of an annotation processor |
| `ProcessingEnvironment` | Provides compiler utilities, filer, messager, and options |
| `RoundEnvironment` | Information about annotations and elements in a processing round |
| `Element` | Represents a class, method, field, parameter, or declared element |
| `TypeElement` | Represents a type declaration such as a class or interface |
| `TypeMirror` | Represents a type in the language model |
| `Elements` | Queries and manipulates the element model |
| `Types` | Checks relationships among types |
| `Filer` | Creates source files, class files, or resources |
| `Messager` | Emits diagnostics such as NOTE, WARNING, and ERROR |

A processor should operate on the language model rather than trying to load classes currently being compiled via `Class.forName`. Those classes might not yet be compiled to bytecode when the processor executes.

### 2.1. AbstractProcessor

A processor typically extends `AbstractProcessor`:

~~~java
public class GreetingProcessor extends AbstractProcessor {
    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {
        return false;
    }
}
~~~

Commonly overridden methods:

- `init(ProcessingEnvironment)`: receives the processing environment.
- `process(...)`: processes annotations in each round.
- `getSupportedAnnotationTypes()`: declares the annotation types the processor handles.
- `getSupportedSourceVersion()`: declares the supported Java source version.
- `getSupportedOptions()`: declares compiler options passed to the processor.

You can declare metadata using `@SupportedAnnotationTypes`, `@SupportedSourceVersion`, and `@SupportedOptions`, or by overriding the corresponding methods.

### 2.2. Supported annotation types

~~~java
@SupportedAnnotationTypes("demo.GenerateGreeting")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class GreetingProcessor extends AbstractProcessor {
    // ...
}
~~~

`@SupportedAnnotationTypes` takes fully qualified annotation type names, including packages. Multiple annotations can be supported by listing multiple names.

The wildcard `*` means the processor inspects all annotation types. Use it only when the processor genuinely needs to observe every annotation; otherwise, declaring exact target types is clearer and more efficient.

### 2.3. Language model instead of Java Reflection

Inside `process`, `Element` and `TypeElement` represent declarations currently handled by the compiler:

~~~java
for (Element element : roundEnv.getElementsAnnotatedWith(annotationType)) {
    if (element instanceof TypeElement typeElement) {
        String name = typeElement.getQualifiedName().toString();
        processingEnv.getMessager().printMessage(
                Diagnostic.Kind.NOTE,
                "Processing " + name,
                typeElement
        );
    }
}
~~~

`TypeElement` models a type declaration; it is not `java.lang.Class<?>`. Types in `javax.lang.model` let processors analyze sources and types without needing classes loaded into a JVM.

## 3. Processing rounds

Annotation processing can execute across multiple rounds. This enables a processor to generate new sources and have the compiler/processors inspect annotations inside the newly generated sources.

Simplified flow:

1. Compiler parses initial sources and locates annotations.
2. Processor receives relevant annotations and elements for the current round.
3. Processor may generate sources or resources via `Filer`.
4. Compiler parses newly generated sources.
5. Processors are invoked in the next round for annotations present in those new sources.
6. Finally, the compiler invokes a final round with `processingOver() == true`.

### 3.1. Checking the final round

~~~java
@Override
public boolean process(
        Set<? extends TypeElement> annotations,
        RoundEnvironment roundEnv) {

    if (roundEnv.processingOver()) {
        return false;
    }

    // Process annotations in the current round.
    return false;
}
~~~

In the final round, a processor can summarize results or emit diagnostics. Do not rely on generating additional sources in the final round to trigger another processing round; no subsequent round will process newly generated sources there.

### 3.2. errorRaised

`roundEnv.errorRaised()` indicates whether an error was reported in a prior round. A processor can check this to avoid generating output from broken inputs.

Not every processor needs special handling for this. However, processors synthesizing code from multiple types should consider suppressing further error-prone source generation once compilation already has fatal diagnostics.

### 3.3. The boolean return value from process

The return value does not mean "build succeeded or failed":

- `true`: the processor claims the annotation types passed to it in the current round.
- `false`: the processor does not claim those annotation types; other processors may still handle them.

If a processor owns a dedicated annotation, returning `true` after handling it is usually appropriate. If a processor only observes or intends other processors to run afterward, return `false`.

Compile errors must be reported via `Messager` with `Diagnostic.Kind.ERROR`, not merely via the boolean return value.

## 4. Generating files with Filer

`Filer` is the official API for creating files during compilation. Common operations:

- `createSourceFile(...)`: creates a source file.
- `createClassFile(...)`: creates a class file.
- `createResource(...)`: creates a resource in an output location.

Never write generated sources directly into the project's source directory with `FileWriter` or hard-coded paths. Use `Filer` so the compiler and build tool manage generated output in the proper locations.

### 4.1. Creating a source file

~~~java
JavaFileObject sourceFile =
        processingEnv.getFiler().createSourceFile(
                "demo.ExampleGreeting",
                originatingElement
        );

try (Writer writer = sourceFile.openWriter()) {
    writer.write("""
            package demo;

            public final class ExampleGreeting {
                public static String message() {
                    return "Hello from generated code";
                }
            }
            """);
}
~~~

The first argument is the qualified name of the type to generate. The `originatingElement` argument links the generated file to the source element that triggered generation; this assists build tools and incremental processing.

File names must be unique within a compilation. If a processor attempts to create the same source file multiple times, `Filer` can throw `FilerException`.

### 4.2. Avoiding duplicate output creation

~~~java
processingEnv.getFiler().createSourceFile("demo.GeneratedConfig");
processingEnv.getFiler().createSourceFile("demo.GeneratedConfig");
~~~

Creating the same name twice within one compilation is invalid. Processors should derive deterministic output names and ensure each output is created at most once.

If multiple annotations contribute to one output, aggregate the necessary data before writing the file or track generated names in processor state. For aggregated output, collect all relevant inputs before creating the final file.

### 4.3. Creating a resource

~~~java
FileObject resource = processingEnv.getFiler().createResource(
        StandardLocation.CLASS_OUTPUT,
        "",
        "META-INF/demo/generated-index.txt"
);

try (Writer writer = resource.openWriter()) {
    writer.write("demo.ExampleGreeting\n");
}
~~~

Resources are written to an output location managed by the compiler/build tool, eliminating guesswork about `build/classes` or `target/classes` paths.

### 4.4. Messager for targeted error reporting

~~~java
processingEnv.getMessager().printMessage(
        Diagnostic.Kind.ERROR,
        "@GenerateGreeting applies only to classes",
        element
);
~~~

Diagnostic kinds:

| Kind | Meaning |
|---|---|
| `ERROR` | Error; compilation fails |
| `WARNING` | Warning; compilation may still proceed |
| `MANDATORY_WARNING` | Mandatory warning per compiler rules |
| `NOTE` | Informational note |
| `OTHER` | Other diagnostic |

Passing `Element` attaches the diagnostic to the relevant declaration, making it easier to fix than plain text messages.

## 5. Complete processor example

The following example generates a class with a `message()` method for every class annotated with `@GenerateGreeting`. The processor identifies the annotation by its qualified name in the language model, so the processor does not need to import the annotation API in its own code.

### 5.1. Annotation API

File `annotation-api/src/main/java/demo/GenerateGreeting.java`:

~~~java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateGreeting {
}
~~~

### 5.2. Processor implementation

File `processor/src/main/java/demo/processor/GreetingProcessor.java`:

~~~java
package demo.processor;

import java.io.IOException;
import java.io.Writer;
import java.util.Set;

import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.Element;
import javax.lang.model.element.ElementKind;
import javax.lang.model.element.PackageElement;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;
import javax.tools.JavaFileObject;

@SupportedAnnotationTypes("demo.GenerateGreeting")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class GreetingProcessor extends AbstractProcessor {

    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {

        if (roundEnv.processingOver()) {
            return false;
        }

        TypeElement annotationType = processingEnv
                .getElementUtils()
                .getTypeElement("demo.GenerateGreeting");

        if (annotationType == null) {
            return false;
        }

        for (Element element :
                roundEnv.getElementsAnnotatedWith(annotationType)) {

            if (element.getKind() != ElementKind.CLASS) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "@GenerateGreeting applies only to classes",
                        element
                );
                continue;
            }

            TypeElement type = (TypeElement) element;
            PackageElement packageElement =
                    processingEnv.getElementUtils().getPackageOf(type);

            String packageName =
                    packageElement.isUnnamed()
                            ? ""
                            : packageElement.getQualifiedName().toString();

            String generatedName = type.getSimpleName() + "Greeting";
            String qualifiedName = packageName.isEmpty()
                    ? generatedName
                    : packageName + "." + generatedName;

            try {
                JavaFileObject file = processingEnv.getFiler()
                        .createSourceFile(qualifiedName, type);

                try (Writer writer = file.openWriter()) {
                    if (!packageName.isEmpty()) {
                        writer.write("package " + packageName + ";\n\n");
                    }

                    writer.write("public final class " + generatedName + " {\n");
                    writer.write("    private " + generatedName + "() {}\n");
                    writer.write("    public static String message() {\n");
                    writer.write("        return \"Hello from generated code\";\n");
                    writer.write("    }\n");
                    writer.write("}\n");
                }

            } catch (IOException e) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "Failed to generate " + qualifiedName + ": "
                                + e.getMessage(),
                        type
                );
            }
        }

        return true;
    }
}
~~~

The processor validates the element kind before casting, obtains the package from `Elements`, emits source via `Filer`, and reports errors via `Messager`. This example is intentionally simple to demonstrate the API; real processors must handle nested names, additional element kinds, duplicate output prevention, and domain-specific rules.

### 5.3. Registering the processor via Service Provider

Create file:

`processor/src/main/resources/META-INF/services/javax.annotation.processing.Processor`

Contents:

~~~text
demo.processor.GreetingProcessor
~~~

This is a Java Service Provider configuration. Once packaged in a JAR, `javac` can discover the processor via service loading if the JAR is on the processor path or a classpath searched for processors.

You can also specify processor names explicitly with `-processor`, even when registered as a service.

## 6. Running javac with a processor

A manual build can be split into three steps: compiling the annotation API, compiling the processor, and compiling the application.

Suppose the layout is:

~~~text
project/
├── annotation-api/
│   └── src/main/java/demo/GenerateGreeting.java
├── processor/
│   ├── src/main/java/demo/processor/GreetingProcessor.java
│   └── src/main/resources/META-INF/services/
│       └── javax.annotation.processing.Processor
└── app/
    └── src/main/java/demo/
        ├── Example.java
        └── Runner.java
~~~

### 6.1. Compile the annotation API

~~~bash
javac --release 17 -d annotation-api/out \
    annotation-api/src/main/java/demo/GenerateGreeting.java

jar --create --file annotation-api.jar \
    -C annotation-api/out .
~~~

This JAR holds the annotation type so application source can import it.

### 6.2. Compile and package the processor

~~~bash
javac --release 17 -d processor/out \
    processor/src/main/java/demo/processor/GreetingProcessor.java

jar --create --file greeting-processor.jar \
    -C processor/out . \
    -C processor/src/main/resources .
~~~

The processor in this example uses only JDK APIs, so it needs no annotation API on its compile classpath. More complex processors may need their own compile/runtime dependencies.

### 6.3. Application source

File `app/src/main/java/demo/Example.java`:

~~~java
package demo;

@GenerateGreeting
public class Example {
}
~~~

File `app/src/main/java/demo/Runner.java`:

~~~java
package demo;

public class Runner {
    public static void main(String[] args) {
        System.out.println(ExampleGreeting.message());
    }
}
~~~

### 6.4. Run annotation processing and compile

Create output directories first:

~~~bash
mkdir -p app/generated app/classes
~~~

Compile:

~~~bash
javac --release 17 \
    -classpath annotation-api.jar \
    -processorpath greeting-processor.jar \
    -processor demo.processor.GreetingProcessor \
    -s app/generated \
    -d app/classes \
    app/src/main/java/demo/Example.java \
    app/src/main/java/demo/Runner.java
~~~

Option meanings:

| Option | Role |
|---|---|
| `--release 17` | Compile against Java 17 APIs and language rules |
| `-classpath` | Classpath for application source and compile dependencies |
| `-processorpath` | Where to find processors and processor runtime dependencies |
| `-processor` | Explicitly specify processors to run |
| `-s` | Directory for generated source files |
| `-d` | Directory for output class files |

The compiler processes `Example`, the processor generates `ExampleGreeting.java` into `app/generated`, and the compiler then compiles the generated source into `app/classes`.

Run on Linux/macOS:

~~~bash
java -cp app/classes:annotation-api.jar demo.Runner
~~~

Output:

~~~text
Hello from generated code
~~~

On Windows, the classpath separator is `;` instead of `:`:

~~~powershell
java -cp "app/classes;annotation-api.jar" demo.Runner
~~~

### 6.5. Controlling annotation processing

Useful `javac` options:

| Option | Effect |
|---|---|
| `-proc:none` | Disable annotation processing |
| `-proc:only` | Run annotation processing only, without normal compilation |
| `-processor A,B` | Specify processors by fully qualified name |
| `-processorpath path` | Classpath dedicated to processors |
| `--processor-module-path path` | Module path for modular processors |
| `-s directory` | Output directory for generated sources |
| `-Akey=value` | Pass an option to processors |

In Java 17, annotation processors can be discovered automatically via service providers on appropriate paths. Nonetheless, configuring the processor path and processor explicitly makes builds reproducible and prevents accidentally running processors lurking on the compile classpath.

Starting in JDK 23, `javac` changed the default regarding automatic execution of processors found on the classpath. Builds should configure processors explicitly instead of relying on defaults across JDK versions.

## 7. Three dependency kinds to keep separate

This distinction is essential when configuring Maven or Gradle.

### 7.1. Compile-time dependency

This is a dependency application source code must see in order to compile.

~~~java
import demo.GenerateGreeting;

@GenerateGreeting
public class Example {
}
~~~

The source needs the `demo.GenerateGreeting` annotation type on the compile classpath. Without the annotation API, the compiler reports missing packages or symbols.

An annotation API might require:

- `compileOnly` if the annotation is used only at compile time and is not needed at runtime.
- `implementation` if the application module needs the annotation API at runtime.
- `api` in a library if the annotation appears in its public API and library consumers must read or compile against that annotation type.

Choose the scope according to the library's contract, not merely because an annotation processor happens to use it.

### 7.2. Annotation processor dependency

A processor runs inside the compiler. It belongs on the processor path managed by the build tool.

Processors normally do not belong on the application's runtime classpath. Including them at runtime bloats the application artifact with unneeded dependencies and pulls in the processor's helper libraries.

A processor may also need its own dependencies to execute, such as schema parsers or template engines. Those dependencies must accompany the processor on the processor path.

### 7.3. Runtime dependency

Generated code may reference a runtime API:

~~~java
public final class GeneratedMapper {
    public static Result map(Source source) {
        return RuntimeMappingSupport.convert(source);
    }
}
~~~

If `GeneratedMapper` calls `RuntimeMappingSupport`, the application needs the library containing that class on the runtime classpath. Declaring it only in `annotationProcessor` is insufficient.

Conversely, if the processor emits pure Java code referencing no runtime library, the processor artifact can be completely absent when the application executes.

### 7.4. Comparison table

| Kind | When used? | Example Gradle configuration |
|---|---|---|
| Compile-time annotation API | Source imports the annotation | `compileOnly` or `implementation` |
| Processor implementation | Compiler must run the processor | `annotationProcessor` |
| Processor for test sources | Tests use annotations requiring processing | `testAnnotationProcessor` |
| Runtime support API | Generated code calls API at runtime | `implementation` or `api` |
| Annotation API as public contract | Consumers must see annotation in public API | `api` |

A dependency may appear in multiple configurations if it genuinely serves multiple phases, but justify each configuration clearly.

## 8. Gradle configuration for Java 17

With the Gradle Java plugin, the `annotationProcessor` configuration is for processors running when compiling the main source set. `testAnnotationProcessor` is for the test source set.

Groovy DSL example:

~~~groovy
plugins {
    id 'java'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    // Annotation used by source code, not needed at runtime.
    compileOnly 'com.example:annotation-api:1.0'

    // Processor executed during compileJava.
    annotationProcessor 'com.example:greeting-processor:1.0'

    // If test sources also use this annotation:
    testCompileOnly 'com.example:annotation-api:1.0'
    testAnnotationProcessor 'com.example:greeting-processor:1.0'

    // Library called by generated code at runtime (if any).
    implementation 'com.example:generated-runtime-support:1.0'
}
~~~

If the annotation belongs to a library's public API and consumers must see it, use `api` instead of `compileOnly` when the `java-library` plugin is applied and the API contract requires it.

### 8.1. Kotlin DSL

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

dependencies {
    compileOnly("com.example:annotation-api:1.0")
    annotationProcessor("com.example:greeting-processor:1.0")

    testCompileOnly("com.example:annotation-api:1.0")
    testAnnotationProcessor("com.example:greeting-processor:1.0")

    implementation("com.example:generated-runtime-support:1.0")
}
~~~

### 8.2. Verifying dependencies landed in the right configuration

Inspect the dependency trees:

~~~bash
./gradlew dependencies --configuration compileClasspath
./gradlew dependencies --configuration annotationProcessor
./gradlew dependencies --configuration runtimeClasspath
~~~

These three dependency trees answer three different questions:

- Can the compiler see the annotation API and types required to compile?
- Are the processor and its execution dependencies resolved?
- Does the application have the libraries needed at runtime?

Do not inspect `runtimeClasspath` to verify the processor path.

### 8.3. Incremental annotation processing in Gradle

Gradle supports incremental compilation with processors that properly declare incremental support. Processors are categorized by how they produce output:

- **Isolating:** each output depends on exactly one specific input element.
- **Aggregating:** aggregated outputs depend on multiple input elements.
- **Dynamic:** the processor determines its behavior at runtime using Gradle's supported API.

Processors publish metadata in the resource:

`META-INF/gradle/incremental.annotation.processors`

Example:

~~~text
demo.processor.GreetingProcessor,isolating
~~~

Declare `isolating` only if every output genuinely depends solely on the originating element passed to `Filer`. If a processor collects all annotated classes to generate a single registry, it is aggregating.

Passing originating elements to `Filer` is crucial for informing the build tool about input-to-generated-output relationships. Misdeclaring incremental behavior can cause incremental builds to miss updates or retain stale output.

## 9. Maven configuration for Java 17

The Maven Compiler Plugin configures a dedicated processor path. Example:

~~~xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>

<dependencies>
    <!-- Annotation API so application source compiles. -->
    <dependency>
        <groupId>com.example</groupId>
        <artifactId>annotation-api</artifactId>
        <version>1.0</version>
        <scope>provided</scope>
    </dependency>

    <!-- Runtime support if generated code requires this library. -->
    <dependency>
        <groupId>com.example</groupId>
        <artifactId>generated-runtime-support</artifactId>
        <version>1.0</version>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.13.0</version>
            <configuration>
                <release>17</release>
                <annotationProcessorPaths>
                    <path>
                        <groupId>com.example</groupId>
                        <artifactId>greeting-processor</artifactId>
                        <version>1.0</version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

In this example:

- `annotation-api` is a project dependency so sources compile.
- `greeting-processor` is in `annotationProcessorPaths` as a processor dependency.
- `generated-runtime-support` is a runtime dependency because generated code uses it at runtime.
- `maven.compiler.release` and `<release>17</release>` target Java 17 compilation.

`provided` fits when the annotation API is needed during compilation while the execution environment does not need the artifact. If the annotation is part of a public API that consumers must have on their compile classpath, choose an appropriate scope and publishing setup instead of defaulting blindly to `provided`.

### 9.1. Processor path vs. regular dependencies

`annotationProcessorPaths` separates processors from the application's classpath. If a processor requires runtime dependencies to run, Maven Compiler Plugin resolves them on the processor path according to plugin configuration.

Never declare a processor as a runtime dependency just so the compiler finds it. Configure it explicitly in the plugin.

### 9.2. Inspecting generated sources

Maven Compiler Plugin typically manages generated sources under `target/generated-sources/annotations`. You can open that directory to inspect generated code while debugging.

Generated sources are build outputs. Never edit files in this directory directly because subsequent builds can regenerate and overwrite changes.

## 10. Annotation processors on the module path (JPMS)

If a processor is packaged as a named module, its module descriptor can declare a service provider.

Example `module-info.java` for the processor:

~~~java
module com.example.greeting.processor {
    requires java.compiler;

    provides javax.annotation.processing.Processor
            with demo.processor.GreetingProcessor;
}
~~~

`requires java.compiler` grants access to the annotation processing and language model APIs. `provides` registers the processor via Java's module service mechanism.

With `javac`, specify the processor module path:

~~~bash
javac --release 17 \
    --processor-module-path processor-modules \
    -processor demo.processor.GreetingProcessor \
    -classpath annotation-api.jar \
    -s generated \
    -d classes \
    src/demo/Example.java
~~~

Module path and module dependency setup depend on how the JAR is packaged. For ordinary classpath JAR processors, `-processorpath` is sufficient; there is no need to modularize just to write a simple processor.

### 10.1. Distinguishing the path options

- `--module-path`: module path for application dependencies.
- `--processor-module-path`: module path for modular processors.
- `-classpath`: regular compile classpath.
- `-processorpath`: classpath for processors.

These paths serve distinct purposes. A library may need to appear on more than one path if it provides both application APIs and a dependency needed by the processor.

## 11. Annotation retention and annotation API dependencies

`RetentionPolicy` determines where an annotation exists:

| Retention | Where does it exist? | Common purpose |
|---|---|---|
| `SOURCE` | Source during compilation; omitted from class files | Annotations solely for compilers/processors |
| `CLASS` | Stored in class files, not necessarily visible via runtime Reflection | Metadata for compilers/tools |
| `RUNTIME` | Stored in class files and readable via Reflection | Frameworks inspecting annotations at runtime |

Do not mark an annotation `RUNTIME` merely so an annotation processor can read it. Processors operate during compilation and can process `SOURCE` annotations.

Example:

~~~java
@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateGreeting {
}
~~~

Only if a runtime framework must also inspect the annotation should you consider `RUNTIME` and ensure the annotation dependency is present at runtime by design.

### 11.1. Separating the annotation API into its own artifact

~~~text
library-annotations
    +-- annotation types
    +-- no processor implementation

library-processor
    +-- AbstractProcessor implementation
    +-- service registration
    +-- depends on annotation API if needed

application
    +-- compile dependency on annotation API
    +-- annotationProcessor dependency on processor
    +-- runtime dependency on generated-code support if needed
~~~

This separation avoids pulling the processor and build-time dependencies into the final application. It also makes versioning the annotation API and processor clearer.

## 12. Common processor configuration errors

| Symptom | Common cause | Resolution |
|---|---|---|
| Annotation not found at compile time | Missing annotation API on compile classpath | Add appropriate compile dependency |
| Processor does not run | JAR lacks service registration or processor path is wrong | Check service file, `-processorpath`, and processor name |
| Processor runs but sees no annotations | Wrong `@SupportedAnnotationTypes` name or annotation is outside compiled sources | Check qualified name and source set |
| `NoClassDefFoundError` inside processor | Missing processor runtime dependency on processor path | Add that dependency to processor configuration |
| Generated source does not appear | Processor did not call `Filer`, conditions failed, or processing was over | Inspect `process`, diagnostics, and generated-source dir |
| `FilerException: Attempt to recreate a file` | Generating the same output multiple times or file already exists in compilation | Ensure unique output names and create each once |
| Generated code compiles but fails at runtime | Missing library referenced by generated code | Add the corresponding runtime dependency |
| IDE and command-line builds produce different results | IDE/build tool uses different processor path or generated source setup | Align IDE annotation processor settings with build |
| Incremental build yields stale output | Processor misdeclares incremental mode or omits originating elements | Fix isolating/aggregating metadata and Filer usage |
| Compilation is unusually slow | Processor inspects too many elements or scans broad packages | Restrict supported annotations and optimize model traversal |

## 13. Designing safe and maintainable processors

An annotation processor runs during the build, which means it executes code on developer machines or CI runners. Add processor dependencies only from trusted sources; processors can read files, access the environment, and perform actions permitted to the build process.

Recommended practices:

1. Process only annotations the processor actually supports.
2. Validate element kinds before casting.
3. Report errors via `Messager` and attach diagnostics to the appropriate element.
4. Use `Filer` instead of writing files directly.
5. Choose deterministic generated type names and avoid duplicate generation.
6. Pass originating elements so build tools can track inputs.
7. Never depend on absolute paths from a developer's machine.
8. Avoid internal `com.sun.*` APIs without compelling justification.
9. Avoid loading classes being compiled via Reflection; use `Element`, `TypeMirror`, `Elements`, and `Types`.
10. Test valid sources, invalid sources, and multi-round scenarios.
11. Keep processor artifacts separate from runtime dependencies when the application does not need them at runtime.
12. Declare incremental processing only when isolating/aggregating accurately reflects output generation.

### 13.1. Passing options to a processor

A processor can receive compiler options:

~~~bash
javac -Aconfig=production -AgeneratedPackage=demo.generated ...
~~~

Declare supported options:

~~~java
@SupportedOptions({"config", "generatedPackage"})
public class GreetingProcessor extends AbstractProcessor {
    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {

        String targetPackage = processingEnv.getOptions()
                .getOrDefault("generatedPackage", "demo.generated");

        // Use targetPackage when creating source files.
        return true;
    }
}
~~~

Declaring options lets builds configure processors without hard-coding environment settings into source. Validate option values and report clear errors for invalid configuration.

### 13.2. Do not use processors to replace runtime logic

Processors excel at structural validation, static code generation, and build-time metadata. When data exists only while the application runs, an annotation processor cannot replace runtime processing of that data.

For instance, a processor can generate a mapper from compile-time class declarations and annotations; it cannot read incoming user request payloads at runtime.

## 14. Practice exercises

### Exercise 1: Classify dependencies

A project uses `@GenerateGreeting`, and the processor generates a class calling `RuntimeSupport.print()`.

Classify:

- The JAR containing `GenerateGreeting`.
- The JAR containing `GreetingProcessor`.
- The JAR containing `RuntimeSupport`.

**Answer:**

- Annotation JAR: compile dependency, which can be `compileOnly`/`provided` if not needed at runtime.
- Processor JAR: `annotationProcessor` in Gradle or `annotationProcessorPaths` in Maven.
- RuntimeSupport JAR: runtime dependency (`implementation` or equivalent scope) because the generated class invokes it at runtime.

### Exercise 2: Why did the processor not run?

Source imports the annotation cleanly, compiling does not report a missing annotation, yet no generated source appears.

**Checklist:**

- Does the processor JAR contain the service registration file?
- Is the processor on `-processorpath` or in the `annotationProcessor` configuration?
- Is the name in the service file the exact fully qualified class name?
- Does `@SupportedAnnotationTypes` match the annotation's package and name?
- Did the processor invoke `Filer` and emit any diagnostics?

### Exercise 3: Distinguish SOURCE and RUNTIME

An annotation is used solely for compile-time code generation. Is `RetentionPolicy.RUNTIME` required?

**Answer:** No. `SOURCE` suffices for an annotation processor. Choose `RUNTIME` only if the application or a framework inspects the annotation via Reflection at runtime.

### Exercise 4: Processing rounds

A processor generates `GeneratedConfig.java` in the first round. How does the compiler handle that file?

**Answer:** The compiler parses the generated source and may invoke processors in a subsequent round if the generated source contains matching annotations. Once no new sources remain, the compiler invokes a final round with `processingOver() == true`.

### Exercise 5: FilerException

A processor receives 5 annotated classes and attempts to create `demo.Registry` all 5 times.

**Question:** Why does this fail?

**Answer:** Within a single compilation, the processor attempted to create a source file with the same qualified name multiple times. Collect data across inputs and generate the registry once, or emit distinct per-input outputs if the design requires it.

### Exercise 6: Compiles cleanly yet fails at runtime

Generated source calls `RuntimeSupport.convert`, yet the project declared RuntimeSupport only under `annotationProcessor`.

**Answer:** The processor path provides dependencies solely for running the processor at compile time. It does not place RuntimeSupport on the runtime classpath. Declare that library as a runtime dependency if generated code calls it at runtime.

## 15. Key takeaways

When using annotation processors in Java 17:

1. Annotation processing is a compile-time mechanism based on JSR 269.
2. Processors typically extend `AbstractProcessor` and work with `Element`, `TypeElement`, and `TypeMirror`.
3. `process` can run across multiple rounds; generated sources can be processed in later rounds.
4. Use `Filer` to create sources/resources and `Messager` to report errors.
5. Register processors via service providers or module `provides`.
6. Separate compile classpath, processor path, and runtime classpath.
7. In Gradle use `annotationProcessor`/`testAnnotationProcessor`; in Maven configure `annotationProcessorPaths`.
8. Use `--release 17` to maintain the Java 17 target.
9. Generated sources are build outputs; never edit generated files directly.
10. Declare incremental processing only when isolating/aggregating accurately matches output generation.
11. Use processor dependencies only from trusted sources because processors execute inside the build environment.
12. If generated code calls runtime libraries, declare separate runtime dependencies.
