# Relationship Between JARs, Runtime Images, and Installers

When distributing a Java application, three types of artifacts are frequently mentioned, yet each solves a different need:

- **JAR** packages the application's classes, resources, and optionally dependencies into a Java artifact.
- **Runtime image** is a pre-assembled Java execution environment containing the runtime modules needed to run the application.
- **Installer package (installer/package)** packages the application for installation according to operating-system conventions, potentially bundling a runtime image, launcher, and desktop or OS integration metadata.

In JDK 17, the primary tools are `jar` to create and inspect JARs, `jlink` to create custom runtime images, and `jpackage` to create application images or platform-specific installers. They can be combined into a distribution pipeline:

~~~text
Java source + resources + dependencies
                 |
                 v
             javac / build
                 |
                 v
          JAR application
                 |
                 +--------------------------+
                 |                          |
                 v                          v
       Run on existing Java         jlink creates runtime image
                                            |
                                            v
                                  jpackage creates app image
                                            |
                                            v
                                   Native installer
~~~

The JAR is the application artifact; the runtime image supplies the execution environment; the installer provides the installation experience. An application may release only a JAR, an app image with a private runtime, or an installer containing an app image. Which option to choose depends on the target audience, deployment requirements, target platforms, and version management strategy.

## 1. JAR: Packaging a Java Application

JAR (Java Archive) is a ZIP-based archive format used to hold class files, resources, metadata, and optionally digital signatures. A typical JAR may contain:

~~~text
application.jar
|
+-- META-INF/
|   +-- MANIFEST.MF
|   +-- signatures (if signed)
|
+-- com/
|   +-- example/
|       +-- Main.class
|       +-- service/
|       +-- model/
|
+-- config/
+-- images/
+-- messages/
~~~

A JAR enables distributing many files as a single artifact while preserving package and resource structures. By default, it does not contain a JVM or all external dependencies.

### 1.1. Creating a JAR with the jar Tool

Suppose sources are compiled into the `out` directory:

~~~bash
javac --release 17 -d out src/com/example/Main.java
~~~

Create the JAR:

~~~bash
jar --create --file application.jar -C out .
~~~

Options:

- `--create` creates a new archive.
- `--file application.jar` specifies the output file name.
- `-C out .` changes into the `out` directory and adds its contents to the archive.

List contents:

~~~bash
jar --list --file application.jar
~~~

For modular JARs, view the descriptor:

~~~bash
jar --describe-module --file application.jar
~~~

A JAR without an explicit module descriptor can be described as an automatic module when tools inspect it on the module path.

### 1.2. Executable JARs and Main-Class

A JAR can be launched with `java -jar` if its manifest declares a class with a valid `main` method.

Create a JAR with a main class:

~~~bash
jar --create --file application.jar --main-class com.example.Main -C out .
~~~

The manifest will contain the attribute:

~~~text
Main-Class: com.example.Main
~~~

Run:

~~~bash
java -jar application.jar
~~~

`Main-Class` only identifies the application's starting point. It does not automatically pack external dependencies into the JAR. If the application uses other libraries, the runtime still has to locate them via the classpath or another packaging mechanism.

### 1.3. A JAR Is Not Synonymous with a Fat JAR

There are two common distribution styles:

| Style | Contents | Dependencies |
| --- | --- | --- |
| Regular application JAR | Application classes and resources | Must be supplied separately via classpath/module path |
| Fat JAR / uber JAR | Application classes/resources and dependency contents packed together | Usually bundles dependencies into one artifact |

Fat JARs are typically generated by build tools or packaging plugins; the basic `jar` command does not automatically unpack and merge dependencies. When combining multiple JARs, you must properly handle duplicate resource names, service provider configurations, licenses, legacy signatures, and metadata. Do not simply unpack all dependencies and overwrite colliding file paths.

Even a fat JAR does not contain a JVM. Users still need a compatible runtime unless the artifact is distributed alongside a runtime image in another way.

### 1.4. JARs with the Classpath

Non-modular applications usually run on the classpath:

~~~bash
java -cp "application.jar:lib/*" com.example.Main
~~~

On Windows, the classpath separator is a semicolon:

~~~powershell
java -cp "application.jar;lib/*" com.example.Main
~~~

You can declare `Class-Path` in the manifest to reference dependency JARs relative to the application JAR:

~~~text
Manifest-Version: 1.0
Main-Class: com.example.Main
Class-Path: lib/library-a.jar lib/library-b.jar
~~~

Paths in the manifest are interpreted as URLs relative to the location of the JAR containing the manifest. Preserve the directory structure when distributing. For larger applications, build tools usually manage dependencies and launcher classpaths more cleanly than hand-written manifests.

### 1.5. Modular JARs

Since Java 9, a JAR can be an explicit module if it contains `module-info.class`. For example:

~~~java
module com.example.app {
    requires java.net.http;
    exports com.example.api;
}
~~~

The module descriptor declares dependencies and package boundaries. You can inspect the descriptor:

~~~bash
jar --describe-module --file application.jar
~~~

Run the module on the module path:

~~~bash
java --module-path mods -m com.example.app/com.example.Main
~~~

A JAR without `module-info.class` can still run on the classpath. When placed on the module path, it may be treated as an automatic module based on naming rules and archive contents. Automatic modules are useful for migration, but they lack an explicit module descriptor and are unsuitable as a foundation for every custom runtime image workflow.

## 2. JARs Do Not Provide a Java Runtime

When a user runs:

~~~bash
java -jar application.jar
~~~

the `java` command comes from a JDK or Java runtime installed on the machine. A JAR does not carry a JVM executable.

This imposes several operational requirements:

- The target machine must have a compatible Java runtime.
- The runtime version must support the class file version used by the application and its dependencies.
- The runtime must include the modules/APIs the application needs.
- Users or administrators must install, update, and select the appropriate runtime.
- Two machines may run the exact same JAR on runtimes with different vendors, versions, configurations, or architectures.

For Java 17 applications, compiling with `javac --release 17` constrains Java SE APIs and class files to Java 17. However, doing so does not bundle a Java 17 runtime into the JAR.

### 2.1. When Should You Release Only a JAR?

A JAR alone is appropriate when:

- Users are developers or administrators who already manage Java runtimes.
- The application runs in server/container environments that already provide Java.
- An organization wants centralized runtime management.
- The artifact is a library integrated into other systems.
- You want the application artifact decoupled from how runtimes are installed on individual machines.

If the target audience consists of desktop users unfamiliar with installing Java, distributing only a JAR creates extra setup and support overhead.

## 3. What Is a Runtime Image?

A runtime image is a directory containing a Java execution environment assembled from runtime modules and required components. It typically contains:

~~~text
runtime/
|
+-- bin/
|   +-- java
|   +-- keytool (if retained)
|
+-- conf/
+-- legal/
+-- lib/
    +-- modules
    +-- security/
    +-- ...
~~~

Actual structure depends on the JDK, operating system, and selected modules. A runtime image built with `jlink` can be smaller than a full JDK because it omits development tools like compilers and debuggers.

A runtime image is not an application JAR. It supplies the JVM and runtime modules to run the application. Typically, the application and dependency JARs are distributed alongside the runtime image or placed inside an app image built by `jpackage`.

### 3.1. JDK, Runtime Image, and JRE

These concepts should be distinguished:

| Artifact | Purpose |
| --- | --- |
| JDK | Development kit including compiler, launcher, debugger, archive tools, and runtime |
| Runtime image | Java execution environment built from runtime modules |
| Custom runtime image | Runtime image with modules tailored to an application, typically created with `jlink` |
| JRE | Familiar term for a Java runtime environment; modern workflows often build a custom runtime image instead of downloading a legacy standalone JRE |

There is no need to ship an entire JDK to end users just to run an application. An appropriately built runtime image is usually sufficient.

## 4. jlink: Creating a Custom Runtime Image

`jlink` is the JDK tool for linking modules into a runtime image. It operates exclusively on modules; therefore, the application and dependent modules must be resolvable on the module path.

Example application module:

~~~java
module com.example.app {
    requires java.logging;
    requires java.net.http;
}
~~~

After compiling the module and placing JARs into the `mods` directory, build the runtime image:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.example.app --output build/runtime
~~~

In the example above:

- `--module-path` indicates where to find JDK modules and application modules.
- `$JAVA_HOME/jmods` contains the modules of the active JDK.
- `mods` contains the application module and dependent modules.
- `--add-modules com.example.app` specifies the root module to include in the runtime; dependencies are resolved via `requires` relationships.
- `--output build/runtime` is the created runtime image directory.

On Windows, the module path separator is a semicolon. PowerShell example:

~~~powershell
jlink --module-path "$env:JAVA_HOME\jmods;mods" --add-modules com.example.app --output build\runtime
~~~

Variable names and path syntax depend on the shell. In cross-platform build scripts, construct the module path dynamically for the OS rather than hardcoding a single separator string.

### 4.1. Selecting Root Modules

`--add-modules` accepts one or more root modules. `jlink` resolves the modules they require across the module graph. You do not need to manually list every transitive module if descriptors declare them accurately.

You can inspect the modules included in the runtime:

~~~bash
build/runtime/bin/java --list-modules
~~~

On Windows:

~~~powershell
build\runtime\bin\java.exe --list-modules
~~~

If the application uses reflection, service loading, or loading classes by name at runtime, you may need to add modules not captured by static dependencies. Identify actual runtime requirements and verify them with integration tests.

### 4.2. Custom Launchers

You can create a launcher inside the runtime image:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.example.app --launcher myapp=com.example.app/com.example.Main --output build/runtime
~~~

Once built, you can run:

~~~bash
build/runtime/bin/myapp
~~~

The launcher is configured to invoke the corresponding module and main class. This is one way to deliver a runtime with a friendlier entry point for end users.

### 4.3. Service Binding

If the application uses the Java Service Provider mechanism, it may require provider modules not present in the direct dependency graph. Depending on how the application and providers are declared, `--bind-services` instructs `jlink` to link provider modules for services used by the root modules:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.example.app --bind-services --output build/runtime
~~~

Do not enable or omit this option out of habit without understanding which services need to be present. Check `uses` and `provides` in module descriptors, `ServiceLoader` usage, and test against the generated runtime image.

### 4.4. Useful jlink Options

| Option | Meaning |
| --- | --- |
| `--module-path` | Where to find JDK and application modules |
| `--add-modules` | Selects root modules to include in the image |
| `--bind-services` | Adds provider modules for used services |
| `--launcher` | Creates a launcher for a module/main class |
| `--output` | Output runtime image directory |
| `--limit-modules` | Limits the set of observable modules during resolution |
| `--strip-debug` | Removes debug information |
| `--no-header-files` | Excludes native header files from the image |
| `--no-man-pages` | Excludes man pages from the image |
| `--compress` | Selects resource compression level in the image where supported by the JDK |
| `--save-opts` | Saves `jlink` options for reuse |

You can view help and available plugins on your exact JDK 17:

~~~bash
jlink --help
jlink --list-plugins
~~~

Do not optimize image size by removing modules or resources before verifying the application does not rely on them. A smaller runtime image missing providers, charsets, locale data, or dynamically loaded modules may fail only when a specific feature branch executes.

### 4.5. jlink Requires Modularization

`jlink` builds runtime images from modules. A pure classpath JAR does not become an explicit module merely by placing it in a module path directory.

If an application still has classpath dependencies:

- Those JARs are still distributed alongside the application.
- The runtime image must include the Java SE modules required by the code and its dependencies.
- The launcher must configure the classpath so the JVM finds them.
- With full modularization, explicit descriptors and module dependencies let `jlink` resolve accurately.

You can use `jdeps` to analyze an application's module dependencies, but static results should be cross-checked against reflection, service loading, and other runtime dependencies.

## 5. Are Runtime Images Platform-Dependent?

Yes. A runtime image is created for a specific platform, including operating system and CPU architecture. For example, a runtime image created on Windows x64 cannot be used directly on Linux ARM64.

This matters when building release pipelines:

- Build a runtime image for each target OS and architecture.
- Use a JDK and modules matching the target platform.
- Test on the exact platform where users will run it.
- Do not use a single runtime image across multiple operating systems.

Use a CI matrix or platform-specific build agents to produce the corresponding runtime images. If the application relies on native libraries/JNI, each platform also needs compatible native binaries.

## 6. jpackage: Creating Application Images and Installers

`jpackage` packages a Java application into an application image or a platform-specific installer package. It is designed to let users run the application without assembling classpaths or installing a separate Java runtime.

Common outputs:

- **Application image:** a packaged application directory with a launcher and optionally a runtime image.
- **Installer:** an OS-specific installation package that can install shortcuts, application metadata, install directories, and uninstall metadata.

`jpackage` can use a runtime image prebuilt by `jlink` via `--runtime-image`. If no runtime image is provided, `jpackage` can invoke `jlink` with configured options to produce an appropriate runtime.

### 6.1. Application Image

Example packaging a classpath application with a main JAR:

~~~bash
jpackage --type app-image --name ExampleApp --input input --main-jar application.jar --main-class com.example.Main --runtime-image build/runtime --dest dist
~~~

Where:

- `--type app-image` requests building an application image.
- `--name` sets the application name.
- `--input input` points to the directory containing the JAR and needed dependency/resource files.
- `--main-jar` identifies the main JAR inside the input directory.
- `--main-class` specifies the main class.
- `--runtime-image` supplies the prebuilt runtime image.
- `--dest dist` specifies the output directory.

Output layout varies by OS, but conceptually the app image contains a launcher, application contents, and the specified runtime. Users can run the launcher inside the image directory without typing classpaths.

### 6.2. Operating-System Installers

From the same application configuration, you can request a platform-specific package type:

| Platform | Commonly Used Package Types |
| --- | --- |
| Windows | `exe` or `msi` |
| macOS | `dmg` or `pkg` |
| Linux | `deb` or `rpm` |
| Cross-platform | `app-image` (application directory, not a native installer) |

Windows example:

~~~powershell
jpackage --type msi --name ExampleApp --input input --main-jar application.jar --main-class com.example.Main --runtime-image build\runtime --dest dist --app-version 1.0.0 --vendor ExampleOrg
~~~

Linux example:

~~~bash
jpackage --type deb --name example-app --input input --main-jar application.jar --main-class com.example.Main --runtime-image build/runtime --dest dist --app-version 1.0.0 --vendor ExampleOrg
~~~

macOS example:

~~~bash
jpackage --type dmg --name ExampleApp --input input --main-jar application.jar --main-class com.example.Main --runtime-image build/runtime --dest dist --app-version 1.0.0 --vendor ExampleOrg
~~~

These examples assume the input directory, JAR, main class, and runtime image already exist, and that the build host has the required toolchain for that package type.

### 6.3. Packaging a Modular Application

For modular applications, use `--module-path` and `--module` instead of `--main-jar`/`--main-class`:

~~~bash
jpackage --type app-image --name ModularApp --module-path mods --module com.example.app/com.example.Main --dest dist
~~~

Exact configuration depends on dependencies and the runtime image. When you already have a custom runtime image, pass it via `--runtime-image`. Check `jpackage --help` on JDK 17 to confirm options compatible with your chosen packaging mode.

### 6.4. Useful jpackage Options

| Option | Meaning |
| --- | --- |
| `--type` | Selects `app-image` or a platform-supported installer type |
| `--name` | Application name |
| `--input` | Directory containing JARs and dependencies |
| `--main-jar` | Main JAR for classpath applications |
| `--main-class` | Main class |
| `--module-path` | Module path for modular applications |
| `--module` | Application module and main class |
| `--runtime-image` | Prebuilt runtime image to bundle into the app |
| `--dest` | Output directory |
| `--app-version` | Application version |
| `--vendor` | Vendor name |
| `--icon` | Application/package icon |
| `--arguments` | Default arguments passed to the application |
| `--java-options` | JVM options for the launcher |
| `--launcher` | Additional launcher configuration |
| `--resource-dir` | Custom packaging resources |
| `--license-file` | License file for the installer where supported |

Platform-specific options for Windows, macOS, or Linux can add shortcuts, menus, package metadata, signing, and installation configuration. Check `jpackage --help` on the exact platform and JDK being used:

~~~bash
jpackage --help
~~~

Do not assume every option means the same thing or is supported uniformly across all operating systems.

## 7. Distinguishing the Three Artifacts by Responsibility

| Question | JAR | Runtime image | Installer/package |
| --- | --- | --- | --- |
| Contains app classes/resources? | Yes | Not necessarily | Usually contains app image or references app contents |
| Provides JVM? | No | Yes | Can bundle a runtime image |
| Contains app dependencies? | Possibly, depending on JAR type | Does not automatically include arbitrary classpath dependencies | Can package dependencies inside the app image |
| Requires Java pre-installed on target machine? | Yes, if running JAR directly | No separate external runtime needed | No, if the installer bundles a runtime |
| Has an easy-to-use launcher? | Can run via `java -jar` | Can have launchers created by `jlink --launcher` | Usually creates native launchers |
| Integrates with OS installation? | No | No | Yes |
| Uninstalls via package manager? | No | No | Possible, depending on package type |
| Shared across all OS/CPUs? | Usually portable if free of native dependencies | No | No, typically platform-specific |

Note: installers are not strictly required to bundle a runtime. You can package an app that expects Java to be pre-installed, though for desktop apps distributed to end users, bundling a runtime typically reduces target-machine environment issues.

## 8. Three Common Distribution Models

### 8.1. Releasing Only a JAR

~~~text
Download application.jar
        |
        v
User installs compatible Java
        |
        v
java -jar application.jar
~~~

Advantages:

- Small, easy-to-store artifact.
- Easy to put into servers, containers, or CI/CD pipelines.
- Runtime is managed centrally.
- Suitable for libraries or developer-facing tools.

Considerations to manage:

- Users must install the right runtime.
- Dependencies must be supplied unless using a fat JAR.
- Launch instructions depend on shell environment and classpath.

### 8.2. Releasing an App Image with a Private Runtime

~~~text
Application JAR + dependencies
             |
             +------+
                    |
JDK modules -> jlink runtime
                    |
                    v
             jpackage app-image
                    |
                    v
          Folder with launcher + runtime
~~~

Advantages:

- Users do not need to install Java separately.
- Can carry only the necessary modules.
- Launcher and directory structure are pre-built.
- Suitable for internal distribution or downloadable archive releases.

Considerations to manage:

- App images are tied to platform/architecture.
- Must be built and tested for each target platform.
- Larger than a standalone JAR because it includes the runtime.

### 8.3. Releasing an Installer with a Private Runtime

~~~text
Application JAR + dependencies
             |
             v
      jlink runtime image
             |
             v
      jpackage app image
             |
             v
   Native installer (MSI/DMG/DEB...)
             |
             v
 Installation, launcher, OS integration
~~~

Advantages:

- Familiar installation experience.
- Can create shortcuts/menus and application metadata.
- Can install a dedicated runtime alongside the application.
- Supports OS-native install/uninstall flows.

Considerations to manage:

- Installers depend on OS and CPU architecture.
- Requires package signing and release pipelines.
- Must manage upgrades, user data, and package manager compatibility.
- Build pipelines typically need runners for each platform.

## 9. Relationship with Dependencies and the Module Graph

JARs, runtime images, and installers can hold different layers of dependencies:

- The application JAR contains the application's classes and resources.
- Dependency JARs contain external libraries.
- The runtime image contains Java platform modules.
- The app image combines application contents, dependencies, and runtime per configuration.
- The installer packages the app image and installation metadata.

A common mistake is assuming `jlink` packages all dependency JARs automatically. `jlink` links runtime modules; classpath dependencies still need to be distributed alongside the application and made discoverable by the launcher.

### 9.1. Identifying Required Runtime Modules

You can analyze module dependencies with `jdeps`:

~~~bash
jdeps --print-module-deps --class-path "input/lib/*" input/application.jar
~~~

The output lists Java platform modules identified from bytecode and the provided classpath. Use this list to see which modules the runtime needs, then verify dynamically loaded features and service providers that static analysis may miss.

For modular applications, `requires` clauses in module descriptors are the primary source `jlink` uses to resolve dependencies. For classpath applications, examine third-party libraries, reflection, resource loading, and runtime configuration as well.

### 9.2. ServiceLoader and Providers

Applications using `ServiceLoader` may look up implementations at runtime. If a provider is not represented as a direct module dependency, the runtime image may lack the provider module even though the application compiles cleanly.

Check:

- Service configuration files inside classpath JARs.
- `uses` and `provides` directives in module descriptors.
- Provider modules placed on the module path.
- How `jlink --bind-services` affects the linked module set.
- Service loading tests against the final runtime image.

Do not run the application only on a full JDK and assume a custom runtime image will contain every required module.

## 10. Launchers and Runtime Configuration

Launchers generated by `jpackage` can bake in default JVM options and arguments. For example:

~~~bash
jpackage --type app-image --name ExampleApp --input input --main-jar application.jar --main-class com.example.Main --java-options "-Xmx1g" --arguments "--config config/app.properties" --dest dist
~~~

Options in the example only illustrate how configuration is passed; heap values and config paths must fit your real environment.

When designing a launcher:

- Include only truly necessary JVM options.
- Avoid hardcoding absolute paths from build machines.
- Define where configs and user data are stored.
- Direct logs to locations that can be collected and rotated.
- Handle the working directory explicitly; never assume the current directory is the install directory.
- Provide a way to pass arguments when multiple configurations are needed.

### 10.1. User Data Should Not Live in the Installation Directory

The installation directory may be updated or replaced during upgrades. User data such as local databases, custom configs, caches, and logs should be placed in OS-appropriate data directories with proper permissions.

Do not write mutable files next to the JAR or launcher if the install folder may be read-only or overwritten by a package manager. Separate immutable bundled resources from user-generated data.

## 11. Java Versions and Runtime Compatibility

A packaging workflow must align:

- Target source/API version.
- Class file version.
- JDK used to build the runtime image.
- Bundled runtime module versions.
- Java dependencies and native libraries.
- Target OS and CPU architecture.

Example for a Java 17 application:

~~~bash
javac --release 17 -d out src/com/example/Main.java
~~~

If the runtime image is built from JDK 17, the bundled runtime carries that JDK's runtime modules. Test the application on the actual released runtime image rather than only on a full development JDK.

A JAR may run on a newer runtime if class files and APIs remain compatible, but a custom runtime image remains tied to its platform and bundled modules. Upgrading the JDK may require rebuilding the runtime image and installer to deliver new runtime/security patches.

## 12. Building per Target Platform

Because runtime images and installers are typically tied to the OS, architecture, and native tools, release pipelines should separate artifacts by target:

| Build Target | Runtime Image | Installer |
| --- | --- | --- |
| Windows x64 | Windows x64 runtime | MSI or EXE |
| macOS ARM64 | macOS ARM64 runtime | DMG or PKG |
| macOS x64 | macOS x64 runtime | DMG or PKG |
| Linux x64 | Linux x64 runtime | DEB or RPM |
| Linux ARM64 | Linux ARM64 runtime | Distribution-appropriate package |

This is an example matrix; actual targets depend on your users and supported platforms.

`jpackage` builds native packages on the corresponding platform; do not assume every installer type can be generated from a single build host. Cross-platform pipelines typically use separate Windows, macOS, and Linux runners, then collect artifacts into a single release.

Some installers require OS-native packaging tools or external toolkits. Verify package-type requirements against JDK 17 and the build environment before running the pipeline.

## 13. Signing and Verifying Artifacts

JARs can be signed with Java's JAR signing mechanism; installers may require OS code signing so users can verify the publisher and integrity.

These are two distinct layers:

- **JAR signing:** signatures stored inside JAR metadata and verified with Java tools.
- **OS code signing:** signatures attached to executables or installers following the operating system's format and trust model.

Example checking a JAR signature:

~~~bash
jarsigner -verify -verbose -certs application.jar
~~~

Output should be interpreted in light of certificate chains, timestamps, policies, and trust status. A verify command succeeding without errors does not automatically prove the signer is the expected publisher; verify the certificate identity and download source.

In addition to signatures, you can publish checksums (such as SHA-256) so recipients can check whether downloaded files match published artifacts. Checksums detect content corruption or tampering, though they do not authenticate publisher identity if obtained from the same untrusted source.

## 14. Testing the Final Artifact

Do not test only source code or the JAR. Test the actual artifact that will be distributed:

1. Build the JAR and inspect contents, manifest, and module descriptor.
2. Run the JAR on a clean Java 17 runtime with proper dependencies.
3. Build the runtime image with `jlink`.
4. Inspect the module list and launchers of the runtime image.
5. Run the application using the runtime image, without a full JDK on `PATH`.
6. Build the app image with `jpackage`.
7. Run the launcher from the app image directory on a clean machine.
8. Build the native installer on the corresponding platform runner.
9. Test installing, launching, upgrading, and uninstalling via supported flows.
10. Verify user data is preserved or removed across upgrades/uninstalls per product policy.

Tests should cover features involving reflection, `ServiceLoader`, charsets, locales, timezones, filesystem access, TLS, and native libraries if the application depends on them. A slim runtime image might lack modules accidentally supplied by a full JDK on a developer workstation.

### 14.1. Testing the Runtime Image

You can invoke executables inside the runtime image directly:

~~~bash
build/runtime/bin/java -version
build/runtime/bin/java --list-modules
build/runtime/bin/java -jar input/application.jar
~~~

If a launcher was created by `jlink`:

~~~bash
build/runtime/bin/myapp
~~~

On Windows, executables reside in `bin` with the `.exe` extension.

### 14.2. Testing the App Image and Installer

For the app image, run the launcher inside the image directory on a clean machine/VM without Java installed to confirm the runtime is bundled properly.

For the installer, verify:

- Installation under the intended user privilege level.
- Shortcuts/menus and icons.
- Install path and file permissions.
- Launching after installation.
- Upgrading from the previous version.
- Uninstalling and data retention/removal policy.
- Signatures, publisher details, and OS prompts.

Do not treat successfully producing an MSI/DMG/DEB/RPM file as proof that the application installs and runs properly on target machines.

## 15. Choosing a Distribution Model

| Audience / Environment | Usually Suitable Distribution | Reason |
| --- | --- | --- |
| Developers or servers with managed Java | JAR and dependencies | Runtime is managed centrally |
| Containerized applications | JAR in a container image with a Java runtime | Container image manages runtime and deployment |
| Internal desktop applications | App image or installer with runtime | Avoids requiring users to install Java separately |
| Broadly distributed desktop apps | OS-native installer, usually with runtime | Familiar install and update experience |
| Libraries used by other apps | Library JAR | No launcher or installer needed |
| CLI tools for controlled environments | JAR or app image with launcher | Choose based on whether the runtime is already managed |

There is no single best model for every product. JARs are simple for developers and servers; runtime images remove reliance on pre-installed Java; installers improve OS integration and installation management for end users.

## 16. Common Pitfalls

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `java -jar` reports missing classes | JAR lacks dependencies and classpath is not configured | Package dependencies or provide a launcher/classpath |
| JAR runs on dev machine but fails elsewhere | Different runtime/API or dependency version | Run on target Java version and check `--release` |
| JAR does not provide Java itself | JAR is only an application archive | Distribute a runtime image or require Java installation |
| `jlink` reports module not found | Module path lacks modules or dependencies | Check module descriptors and `--module-path` |
| Runtime image lacks providers | Service providers were not linked | Check `uses`/`provides`, service configs, and `--bind-services` |
| Runs on JDK but fails on runtime image | Runtime image lacks dynamically loaded modules | Analyze dependencies and test all feature branches |
| Expecting `jlink` to pack all dependency JARs | Confusing runtime modules with classpath dependencies | Distribute dependency JARs and configure the launcher |
| App image runs on Windows but not Linux | Runtime image/launcher is platform-specific | Build and test images for each OS/architecture |
| `jpackage` fails to build installer | Missing native tools or unsupported package type on host | Check platform requirements and `jpackage --help` |
| Installer succeeds but app won't launch | Wrong main class, runtime, paths, or JVM options | Inspect launcher config and test the app image directly |
| Upgrade erases user data | Data stored inside installation folder gets replaced | Store mutable data in a user data directory |
| Installer not trusted by OS | Missing or invalid code signing | Sign the artifact and verify publisher/certificate |
| Runtime image is too large | Excess modules or resources included | Analyze dependencies and select modules deliberately |
| Runtime image is too small and fails in secondary features | Dynamically loaded modules or service providers excluded | Add required modules and test thoroughly |

## 17. Reference Workflow for Java 17

A simple pipeline for a modular application might follow these steps:

~~~bash
# 1. Compile module for Java 17
javac --release 17 -d mods/com.example.app src/module-info.java src/com/example/Main.java

# 2. Build runtime image
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.example.app --launcher example=com.example.app/com.example.Main --output build/runtime

# 3. Create application image
jpackage --type app-image --name ExampleApp --module-path mods --module com.example.app/com.example.Main --runtime-image build/runtime --dest dist
~~~

This is an illustrative skeleton; real projects must handle source layouts, dependency modules, resources, service providers, versioning, icons, and launcher configuration. For classpath applications, replace the module options with `--main-jar` and `--main-class`, and ensure the input directory contains dependencies.

Once the app image is built, verify the launcher and runtime image in a clean environment. When an installer is needed, run `jpackage` with the matching `--type` on a runner for the target platform.

## 19. Key Principles to Remember

- **JAR** packages classes, resources, and optionally dependencies; a JAR itself does not provide a JVM.
- **Runtime image** provides a JVM and the required set of runtime modules; it can be customized with `jlink`.
- **Installer** packages the application for OS-native installation; typically created with `jpackage` and can include a runtime image.
- `jlink` links runtime modules; pure classpath dependency JARs still must be distributed and passed to the launcher.
- Runtime images and installers are typically tied to a target OS/CPU; build separate artifacts for each supported platform.
- `jpackage` can produce an app image or a native installer; installer types and toolchains depend on the OS.
- Test the actual released runtime image/app image/installer, not just source code or a JAR on a development machine.
- Keep user data separate from the installation directory so upgrades/uninstalls do not unexpectedly wipe data.
- Sign artifacts, verify publisher identity, and publish checksums where appropriate in your distribution process.

By clearly understanding the responsibilities of JARs, runtime images, and installers, development teams can choose the right release approach: using JARs in Java-managed environments, using runtime images to provide a self-contained runtime, or using `jpackage` to deliver applications with native launchers and installers for Java 17 users.
