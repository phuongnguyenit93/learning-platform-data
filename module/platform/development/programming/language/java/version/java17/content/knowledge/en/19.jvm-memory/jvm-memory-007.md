# JIT, Warmup, and Impact on Measurements in Java 17

Because Java runs on the JVM, the execution time of a piece of code is not necessarily stable from the very first invocation. On HotSpot JDK 17, a method may begin executing in the interpreter and later be compiled into machine code by the JIT compiler once the JVM gathers enough data about call frequency and runtime behavior. Subsequent runs can be faster because the JVM has optimized the method, data is in caches, classes are loaded, and much initialization work has already completed.

This process directly affects benchmarks. Measuring only a single initial run can capture class loading, initialization, JIT compilation, and startup costs. Measuring after the program has run for a while can reflect an optimized steady state. Those two numbers answer two different questions.

To measure Java 17 performance reliably, you must understand **which stages the JIT operates in, what warmup changes, which state a benchmark is measuring, and whether the JVM is actually executing the work you intend to measure**. For microbenchmarks, JMH is far more suitable than a hand-written loop timed with `System.nanoTime()`.

## 1. How does the JVM execute bytecode?

When compiling a Java program, `javac` typically produces bytecode in class files. Bytecode is not native machine code for a specific CPU. The JVM loads classes, verifies bytecode, links required types, and executes according to runtime mechanisms.

In HotSpot, the primary components can be pictured as follows:

~~~text
Java source
    |
    v
javac
    |
    v
class files (bytecode)
    |
    v
Class loading / verification / linking / initialization
    |
    v
Interpreter executes bytecode
    |
    +---- profiling: call counts, branches, type information
    |
    v
JIT compiler compiles hot methods
    |
    v
Optimized machine code
    |
    +---- more profiling / possible recompilation
    |
    +---- deoptimization if assumptions become invalid
~~~

The interpreter lets the JVM start executing without compiling the entire program to machine code beforehand. During execution, the JVM collects data about methods and common code paths. The JIT uses that data to compile frequently executed portions.

Not every method is compiled immediately, and not every method needs to be compiled. A rarely executed method may continue running in the interpreter because compiling it would not pay off.

### Bytecode and machine code are two different layers

Bytecode is designed for JVM execution and portability across compatible platforms. Machine code generated by the JIT depends on CPU architecture, runtime, and optimization assumptions at compilation time.

Therefore:

- The same class file can be JIT-compiled into different machine code on x86-64 and AArch64.
- The same application can have different runtimes across JDK builds or JVM configurations.
- Optimizations can depend on input data and actual runtime object types.
- A method can be recompiled or deoptimized while running.

The Java Language Specification and JVM Specification define program and bytecode semantics. Tiered compilation, compilation thresholds, and specific optimizations are implementation details of a JVM like HotSpot; you should not assume every JVM uses the same JIT algorithms.

## 2. What is JIT and why is it beneficial?

The JIT (Just-In-Time compiler) compiles portions of a program at runtime. Instead of compiling the entire application ahead of time, the JVM waits for runtime data to identify which code paths are actually hot and how they are used.

Example:

~~~java
static long sumSquares(int limit) {
    long sum = 0;
    for (int i = 0; i < limit; i++) {
        sum += (long) i * i;
    }
    return sum;
}
~~~

If the method is called once, compilation cost may not be worthwhile. If called millions of times, the JIT can optimize the loop and produce much more efficient machine code than repeatedly interpreting bytecode.

The JIT can use runtime information to:

- Inline small or frequently called methods.
- Eliminate certain checks or branches under valid assumptions.
- Optimize loops and expressions.
- Eliminate unnecessary allocations in certain cases.
- Exploit actual object types and stable call sites.
- Reorder instructions within the bounds of Java semantics and the memory model.

The JIT does not guarantee every method speeds up by the same factor. A method may be bound by memory bandwidth, cache misses, lock contention, I/O, or allocation/GC. If the bottleneck lies outside what the JIT optimizes, warmup will not remove that limit.

## 3. Tiered compilation in HotSpot Java 17

HotSpot JDK 17 typically enables tiered compilation by default. This model combines the interpreter and multiple compilation tiers to balance startup time, profiling overhead, and steady-state performance.

Commonly described levels:

| Level | Execution mode | Goal |
| ---: | --- | --- |
| 0 | Interpreter | Begin execution and collect initial information |
| 1 | C1, without full profiling | Fast compilation to reduce interpreter overhead |
| 2 | C1 with limited profiling | Gather partial runtime information |
| 3 | C1 with full profiling | Gather information for deeper optimizations |
| 4 | C2, optimizing compiler | Aggressive optimization for hot, stable code |

C1 is a fast compiler typically used at lower compilation tiers. C2 is HotSpot's optimizing compiler, capable of deeper optimizations at a higher compilation cost.

A method can move from the interpreter to C1, and then up to C2 once it is hot enough and has sufficient profile data. Not every method passes through every level; transitions depend on thresholds, configuration, runtime state, and compiler availability.

### Why not compile everything with C2 from the start?

Optimizing compilation takes CPU time and data for analysis. Compiling every method with the optimizing compiler at startup would:

- Slow down startup.
- Waste CPU on code that may run only once.
- Deprive the JVM of real profiling feedback.
- Produce optimization assumptions without sufficient data that might not match the workload.

Tiered compilation helps the JVM start faster and then invest optimization effort in genuinely hot code. That is why the performance of the same method can differ significantly between initial calls and later calls.

### Tiered compilation is not a Java language contract

Levels 0–4 describe HotSpot, not a mandatory rule for all JVMs. OpenJ9 or another runtime may use a different JIT architecture. When benchmarking, record the vendor, JDK version, JVM flags, and actual runtime; never generalize a HotSpot result as a rule for every JVM.

## 4. Profiling and the information JIT collects

The JIT can collect information about:

- How frequently a method is called.
- Which concrete classes a call site typically receives.
- Which conditional branches are taken most often.
- How many iterations loops execute.
- Whether certain checks consistently succeed.

Collectively, this is called the runtime profile. It enables the JIT to optimize based on how the program actually executes rather than static bytecode alone.

### Monomorphic and polymorphic call sites

Suppose you have an interface:

~~~java
interface PriceRule {
    int apply(int price);
}

final class DiscountRule implements PriceRule {
    public int apply(int price) {
        return price - price / 10;
    }
}

static int calculate(PriceRule rule, int price) {
    return rule.apply(price);
}
~~~

If a call site consistently sees only one implementation, the JIT can recognize a stable receiver type and inline the call under certain conditions. If the same call site receives multiple different implementations, optimization can become more complex.

A benchmark running only a single implementation may score very well thanks to a monomorphic profile. In production, if that same method receives multiple implementations, performance can differ.

Therefore, warmup data must represent the real workload. If warmup uses only one data type while production uses many, the collected profile may not reflect production reality.

### Branch profiles

The JIT can also optimize based on commonly taken branches. Example:

~~~java
static int classify(int value) {
    if (value >= 0) {
        return value + 1;
    }
    return -value;
}
~~~

If warmup data is always non-negative, the JVM may build a profile heavily skewed toward the first branch. When real traffic has a different distribution, performance can shift; in some cases optimization assumptions are invalidated and code must deoptimize.

Benchmarks should use data distributed like production or test across multiple representative profiles.

## 5. What is warmup?

Warmup is the phase of running a workload before collecting primary measurements. Its purpose is to bring the JVM and execution environment into the state matching the benchmark question.

Warmup can help:

- Load classes and run class initialization.
- Heat up frequently executed code paths.
- Collect runtime profiles.
- Trigger C1/C2 compilation for hot methods.
- Populate and warm data caches.
- Bring the allocator, GC, and runtime structures to representative operating state.
- Reduce first-call distortion when the benchmark targets steady state.

Warmup is not just running any arbitrary loop. It needs to execute the same kind of work with representative data so the collected profile is meaningful.

### Warmup must resemble the measured workload

Consider a search benchmark:

~~~java
static int findFirstPositive(int[] values) {
    for (int value : values) {
        if (value > 0) {
            return value;
        }
    }
    return -1;
}
~~~

If warmup always passes arrays whose first element is positive, while measurement passes arrays whose positive element is at the end, loop iteration counts and branch behavior differ. Unrepresentative warmup can skew profiles and cache state away from the measured workload.

Similarly, warming up with tiny objects, a single class, or cache-resident data does not represent a workload with large object graphs and diverse runtime types.

### Warmup does not freeze state forever

Even after warmup, the JVM can still:

- Compile other methods as they become hot.
- Recompile methods when profiles change.
- Deoptimize code when an assumption no longer holds.
- Run GC and alter heap state.
- Vary CPU utilization under system load.

Do not assume that after a fixed number of warmup iterations, the JVM stays completely static. Inspect stability across multiple measurement iterations and check logs/profiles when deeper understanding is needed.

## 6. Warmup and cold start answer two different questions

An application can be evaluated on at least two goals:

**Cold-start performance**: time from process launch until the application is ready or finishes its first task. This matters for CLIs, serverless functions, autoscaling, short-lived jobs, and frequently restarted apps.

**Steady-state performance**: performance after the application has started, loaded classes, collected profiles, and JIT-optimized hot paths. This matters for long-running services, long batch jobs, and continuous processing systems.

| Aspect | Cold start | Steady state |
| --- | --- | --- |
| JIT profile | Missing or minimal | Accumulated from workload |
| Class loading | Can be a large share | Most required classes already loaded |
| JIT compilation | Can occur during measurement | Hot code is usually compiled |
| Caches | Cold | May be warmed to workload |
| Goal | Time to readiness / first run | Stable throughput or latency |
| Method | Measure fresh process or first request | Warmup then measure many iterations |

Do not use a heavily warmed-up benchmark to answer a cold-start question. Likewise, do not use a freshly launched single run to determine steady-state throughput.

### Cold start includes many costs

Cold start is not just JIT:

- Launching the JVM process.
- Loading and verifying classes.
- Initializing static fields and singletons.
- Reading configuration, loading libraries, and resources.
- Creating connection pools or clients.
- Opening connections to databases/external services.
- JIT compilation of initial code paths.
- OS and filesystem cache costs.

If the goal is time-to-ready, measure externally from process launch until the health check passes or the first task completes. Do not measure one method in JMH and call it the application's cold-start time.

## 7. JIT optimizations that can alter measurements

### Method inlining

The JIT can replace a method call with the method body at the call site when optimization conditions allow. This removes call overhead and unlocks further optimizations.

~~~java
static int addOne(int value) {
    return value + 1;
}

static int calculate(int value) {
    return addOne(value) * 2;
}
~~~

If `addOne` is inlined, machine code may no longer contain a separate function call at that site. Measuring `addOne` in isolation does not necessarily predict its exact performance when inlined inside a real pipeline.

### Escape analysis and scalar replacement

The JIT can analyze whether an object escapes its scope. In some cases, allocation can be eliminated or the object replaced with scalar values/registers instead of existing as a full heap object.

~~~java
static int calculatePoint(int x, int y) {
    Point point = new Point(x, y);
    return point.x() + point.y();
}

record Point(int x, int y) {}
~~~

Depending on context and JIT optimizations, the intermediate object might not actually be allocated. If a benchmark only creates objects without meaningfully using the result, the compiler may eliminate the work altogether. Design benchmarks so results are properly observed or consumed.

### Constant folding and dead-code elimination

The JIT can precompute expressions depending only on constants, or remove code that has no observable effect on program semantics.

Example of a naive benchmark:

~~~java
@Benchmark
public void wrongBenchmark() {
    int result = 100 * 200;
}
~~~

The computation is unused and can be eliminated. The benchmark then fails to measure multiplication as intended.

A better benchmark returns the result:

~~~java
@Benchmark
public int calculate() {
    return 100 * 200;
}
~~~

Even so, constants can still be constant-folded into a fixed value. To measure computation on inputs, use appropriate runtime data and avoid turning all inputs into compile-time constants.

### Loop unrolling and vectorization

The JIT can transform loops, unrolling or vectorizing operations according to CPU architecture. A small loop benchmark may measure heavily transformed code that differs considerably from the original bytecode.

Do not intentionally disable all JVM optimizations just to "measure pure Java code." Usually the goal is to measure application performance when the JVM operates as it does in production. If studying a specific optimization, explicitly document the test conditions and configuration.

## 8. Deoptimization: when optimization assumptions break

The JIT uses profiles and assumptions to generate fast machine code. When an assumption becomes invalid, the JVM can deoptimize: leave optimized machine code and fall back to another execution tier to preserve program semantics.

For example, a call site previously saw only one implementation, and later a new implementation appears. Optimizations relying on that single receiver type may no longer hold. The JVM can invalidate the compiled code or revert execution to the interpreter to gather updated profiles and recompile.

Deoptimization is not a Java logic bug; it is a runtime mechanism ensuring correctness when profiles change. However, it can introduce latency or throughput jitter.

Signs observable in JIT logs:

- A method is compiled.
- An nmethod is invalidated or made not entrant.
- A deoptimization event occurs.
- A method is recompiled at a different tier.

Do not blame deoptimization based solely on a single latency spike. GC, scheduling, page faults, networking, and contention can also cause spikes. Use appropriate logs and profiles to pinpoint the cause.

## 9. Why measuring with a loop and System.nanoTime is error-prone

A common pattern:

~~~java
long start = System.nanoTime();
for (int i = 0; i < 1000; i++) {
    operation();
}
long elapsed = System.nanoTime() - start;
System.out.println(elapsed);
~~~

This snippet can be handy for a rough end-to-end check of a sufficiently long operation, but it is not a reliable JVM microbenchmark for comparing small methods.

Problems:

1. The first run may include class loading, JIT compilation, and initialization.
2. Later runs may execute optimized machine code.
3. The JIT may eliminate `operation()` if its result is unobserved.
4. Constant folding may turn calculations into constants.
5. The outer loop may be optimized or transformed differently from production.
6. GC may trigger in one measurement run and not another.
7. CPU frequency scaling and other processes introduce measurement noise.
8. A single measurement reveals nothing about distribution or stability.
9. There is no independent JVM fork to isolate profiles and runtime state between tests.

`System.nanoTime()` remains the right API for measuring elapsed intervals in applications because it uses a monotonic clock. The flaw is not `nanoTime` itself, but microbenchmark design, iteration counts, and JVM state.

## 10. Using JMH to benchmark Java code

JMH (Java Microbenchmark Harness) is a benchmarking framework built for the JVM. It handles crucial concerns such as warmup, measurement, forking, parameterization, result reporting, and techniques to prevent dead-code elimination.

Common annotations:

| Annotation | Purpose |
| --- | --- |
| @Benchmark | Marks a method to be measured |
| @State | Declares scope and lifecycle of benchmark state |
| @Setup | Prepares data before a benchmark or iteration |
| @TearDown | Cleans up after a benchmark or iteration |
| @Warmup | Configures warmup iteration count and duration |
| @Measurement | Configures formal measurement iterations |
| @Fork | Runs benchmarks in separate JVM processes |
| @BenchmarkMode | Selects AverageTime, Throughput, SampleTime, SingleShotTime, or All |
| @OutputTimeUnit | Result time unit |
| @Param | Runs benchmarks across multiple parameter values |

### Example benchmark with warmup and measurement

The following example compares two ways to sum an array:

~~~java
import java.util.concurrent.TimeUnit;
import org.openjdk.jmh.annotations.Benchmark;
import org.openjdk.jmh.annotations.BenchmarkMode;
import org.openjdk.jmh.annotations.Fork;
import org.openjdk.jmh.annotations.Measurement;
import org.openjdk.jmh.annotations.Mode;
import org.openjdk.jmh.annotations.OutputTimeUnit;
import org.openjdk.jmh.annotations.Param;
import org.openjdk.jmh.annotations.Scope;
import org.openjdk.jmh.annotations.Setup;
import org.openjdk.jmh.annotations.State;
import org.openjdk.jmh.annotations.Warmup;

@State(Scope.Thread)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 8, time = 1)
@Fork(3)
public class SumBenchmark {

    @Param({"100", "10000", "1000000"})
    public int size;

    private int[] values;

    @Setup
    public void setup() {
        values = new int[size];
        for (int i = 0; i < values.length; i++) {
            values[i] = (i * 31) % 1000;
        }
    }

    @Benchmark
    public long loopSum() {
        long sum = 0;
        for (int value : values) {
            sum += value;
        }
        return sum;
    }

    @Benchmark
    public long streamSum() {
        return java.util.Arrays.stream(values)
                .asLongStream()
                .sum();
    }
}
~~~

Configuration meaning:

- Each array size is benchmarked separately via `@Param`.
- `@Setup` builds the array once per trial, excluding array creation time from each invocation.
- 5 warmup iterations give the JVM time for class loading, profiling, and JIT compilation.
- 8 measurement iterations gather timing metrics.
- 3 forks spawn independent JVM processes, reducing interference from earlier benchmark runs on profiles/compiled code.
- `AverageTime` measures average time per invocation, displayed in microseconds.

These values are illustrative settings, not mandatory numbers. Complex benchmarks may need longer or shorter warmup. Always inspect per-iteration results and stability before drawing conclusions.

### Running JMH

In Maven/Gradle projects, configure JMH dependencies and annotation processors per official JMH instructions. Once the benchmark runner jar is built:

~~~bash
java -jar target/benchmarks.jar SumBenchmark
~~~

Exact paths depend on your build configuration. Never include JMH as a production runtime dependency; keep benchmarks in a separate source set or module so the harness stays out of application artifacts.

### Why fork?

Running multiple benchmarks in the same JVM lets earlier benchmarks warm classes, alter profiles, allocate objects, or influence JIT-compiled code for subsequent benchmarks. Forking launches a fresh JVM process to isolate runtime state between trials.

Forking does not eliminate all variance: CPU, filesystem cache, OS scheduling, thermals, and host load can still interfere. Still, it isolates JVM state far better.

## 11. Choosing warmup duration and iteration count

No single warmup configuration fits every benchmark. Consider:

- How many invocations a method needs before becoming hot.
- Whether the code path has complex branch/type profiles.
- Whether class loading and initialization are expensive.
- Whether the workload needs time for caches to stabilize.
- Whether the benchmark allocates significantly and triggers GC.
- Whether steady state across multiple operating cycles must be observed.

Warmup that is too short can leave measurement polluted by interpreter/C1 execution or ongoing JIT compilation. Overly long warmup wastes time and can measure an unrealistic steady state if production restarts often or workloads shift continuously.

### Watching individual iterations

JMH prints results for each measurement iteration. If execution time drops sharply from early iterations and then plateaus, the runtime may be settling into steady state. If results fluctuate widely throughout, examine GC, contention, host load, shifting profiles, or unstable benchmark design.

Never cherry-pick the fastest iteration as the result. The fastest number may just be a lucky run. Examine the full distribution, mean/score error, or percentiles depending on the benchmark mode.

### Warmup must not hide startup issues

If a product must serve its first request within 100 ms after process launch, a benchmark with 30 seconds of warmup does not answer that question. Measure startup or first-request latency in a fresh process, and measure steady state separately.

## 12. JMH and dead-code elimination

The JIT is allowed to remove code that produces no observable effect under program semantics. That can make a benchmark measure far less work than intended.

### Returning results from benchmarks

JMH consumes the return value of `@Benchmark` methods. This is the simplest way to keep results observable:

~~~java
@Benchmark
public int compute() {
    return calculate(input);
}
~~~

If a method returns `void` and needs to consume intermediate values, use `Blackhole`:

~~~java
@Benchmark
public void compute(Blackhole blackhole) {
    int result = calculate(input);
    blackhole.consume(result);
}
~~~

`Blackhole` prevents the JVM from eliminating computations solely because results go unused. Still, avoid consuming unrelated values excessively; harness overhead can skew tiny microbenchmarks.

### Avoiding constant folding

Do not benchmark expressions where all inputs are compile-time constants:

~~~java
@Benchmark
public int constantExpression() {
    return 12345 * 67890;
}
~~~

The JVM can precompute the result so the benchmark measures only returning a constant. Use meaningful runtime state/inputs:

~~~java
@State(Scope.Thread)
public static class Input {
    @Param({"12345", "23456"})
    int value;
}

@Benchmark
public int multiply(Input input) {
    return input.value * 31;
}
~~~

Even with runtime inputs, the JIT may still optimize if data patterns or usage allow values to be predicted. Design benchmarks closely around how the application actually calls the method.

### Avoid hand-written loops when measuring a single invocation

If the goal is measuring one operation, let JMH invoke the method via the harness. Writing a large loop inside `@Benchmark` allows the JIT to optimize the loop differently from how production invokes the method repeatedly, and makes per-invocation latency harder to isolate.

If production genuinely processes a batch inside a loop, benchmarking that batch is valid—just define clearly whether the unit of measurement is one batch or one element.

## 13. Choosing benchmark mode based on the question

JMH supports several modes:

| Mode | What it measures | When appropriate |
| --- | --- | --- |
| AverageTime | Average time per operation | Comparing mean invocation latency |
| Throughput | Operations per unit time | Measuring overall processing capacity |
| SampleTime | Sampled operation times | Observing latency distributions |
| SingleShotTime | One execution per iteration | Measuring one-shot operations, with custom setup for cold/one-shot tests |
| All | Runs supported modes | Broad exploration, takes longer |

`AverageTime` is not p99 latency. High throughput does not guarantee low individual request latency. Pick the mode matching your question and supplement with system load tests when tail latency is the target.

### SingleShotTime is not automatically application cold start

`SingleShotTime` measures a single invocation under JMH configuration. With a fresh JVM fork and zero warmup, it can reflect a first invocation in a new JVM, yet it still does not necessarily capture full production process startup, classpath scanning, dependency initialization, and readiness.

If the goal is end-to-end cold start, time from process launch externally using a process-controlling harness. If the goal is first-invocation latency inside an already-started JVM, clearly define which setup sits outside vs. inside the measurement window and build the benchmark accordingly.

## 14. JIT logging and observation tools

When you need to confirm whether a method was compiled, HotSpot logs can help. On JDK 17, unified logging supports compilation tags:

~~~bash
java -Xlog:jit+compilation=debug ...
~~~

Logs show which methods were compiled and at which tier. Output is voluminous for large apps; enable only in analysis environments and filter as needed.

Other diagnostic options:

~~~bash
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintCompilation ...
~~~

Diagnostic options may vary across builds/vendors and should not be enabled in production without understanding their impact. Never rely on internal log formats as a stable contract for application logic.

### JFR and profiling

Java Flight Recorder (JFR) records runtime events such as compilation, class loading, GC, thread activity, and more depending on configuration. Use JFR to link a latency spike to runtime events rather than guessing from an aggregate number.

JFR can be started from the command line:

~~~bash
java -XX:StartFlightRecording=filename=app.jfr,duration=60s ...
~~~

Open the file in Java Mission Control or a compatible JFR viewer. Recording also adds overhead; configure events and duration to match the investigation goal.

### Compilation logs do not replace benchmarks

Seeing a method compiled by C2 does not prove the benchmark is valid or that the code is fast. Logs explain JIT state; benchmarks measure timing/throughput; profilers locate where CPU and time go. Combine them when appropriate instead of substituting one for another.

## 15. Non-JIT factors that also change measurements

Warmup changes many states at once, not just compilation.

| Factor | Impact on measurements |
| --- | --- |
| Class loading and initialization | First runs may pay class reading, verification, and static initializer costs |
| CPU caches | Recently accessed data and instructions may stay cached |
| Branch predictor | Repeated branch patterns are predicted better |
| Heap/GC | Allocations and GC pauses introduce timing variance |
| CPU frequency | Turbo/frequency scaling and thermals alter throughput |
| OS scheduling | Threads may be preempted or contend for CPU |
| Memory bandwidth | Multiple workers may saturate RAM bandwidth |
| Lock contention | Adding threads can lower throughput |
| Filesystem/page cache | First reads vs. cached reads have different costs |
| Network connections | Fresh vs. pooled connections have different latencies |
| Common pool/executor | Other tasks may contend for workers |

Therefore, when execution gets faster after warmup, do not automatically attribute all of the gain to the JIT. Measure and inspect further if you need to isolate causes.

### GC can slow down an individual iteration

A benchmark creating many objects may trigger GC in one iteration and not another. A slow iteration is not necessarily JIT compilation; it may be a GC pause or allocation pressure.

JMH includes built-in profilers for several GC metrics:

~~~bash
java -jar target/benchmarks.jar SumBenchmark -prof gc
~~~

The profiler reports allocation rates and GC-related statistics depending on the environment. Comparing allocations/op across implementations can explain why one version is slower despite performing similar arithmetic.

## 16. Optimizing a benchmark differs from optimizing an application

A tiny benchmark may measure a method under unrealistically favorable conditions:

- Data fits in L1/L2 cache.
- Only one thread runs.
- No competing requests exist.
- Profiles observe only one implementation.
- No logging, serialization, or networking runs.

Production often looks different:

- Many concurrent requests.
- Larger datasets and skewed distributions.
- Multiple object types and branches.
- Cache misses, memory pressure, and GC.
- Lock contention or pool saturation.
- Different CPU/container limits.

An optimization that speeds up a single-threaded benchmark might raise allocations, worsening GC under load. An optimization leaning on a monomorphic call site might vanish when production is polymorphic. Microbenchmarks answer narrow questions and do not replace load tests, profiling, and production observability.

## 17. Comparing cold, warm, and steady-state measurements

A measurement plan can be split into three categories:

| Measurement type | Preparation | Target |
| --- | --- | --- |
| Cold | Fresh JVM/process, no warmup prior to measurement | Startup or first operation |
| Warm-up transition | Run workload continuously and record over time | Speed of transition from interpreter/C1 to optimized state |
| Steady state | Sufficient warmup and multiple measurement iterations | Throughput/latency after stabilization |

### External cold-start measurement

To measure application startup:

1. Spawn a fresh JVM process for each trial.
2. Start the clock immediately before launch.
3. Define a clear readiness milestone, such as a health endpoint returning success or the first job finishing.
4. Record elapsed time from launch to that milestone.
5. Repeat multiple times under comparable conditions.
6. Separately account for filesystem cache, image/container startup, and external connections.

Do not mix startup time with request-processing time once the server is already ready.

### Warm-up transition measured per iteration

To observe JIT warmup, run an iterative workload and record timing per batch/iteration. Enable compilation logs or JFR in a separate diagnostic run to see when methods compile. Avoid leaving heavy logging enabled during primary performance measurements because logging adds overhead.

### Steady-state measurement with JMH

Use warmup, measurement, and forks. Check that iteration results have stabilized and are not skewed by a stray GC event or host load. Report both benchmark settings and runtime environment.

## 18. Reading a benchmark report

Consider an illustrative report:

| Benchmark | Score | Error | Unit |
| --- | ---: | ---: | --- |
| loopSum | 120.4 | ± 3.1 | microseconds/op |
| streamSum | 135.8 | ± 4.0 | microseconds/op |

These numbers merely illustrate how to read a table, not actual run results. In this example, `loopSum` has a lower `AverageTime`, yet you should check error margins, forks, data sizes, and setup before concluding the difference is meaningful.

When reading a report:

- Verify mode and unit.
- Check fork, warmup, and measurement iteration counts.
- Check input data and `@Param` values.
- Inspect error/variance.
- Check allocation and GC figures if recorded.
- Review JDK, CPU, OS, and container limits.
- Confirm benchmarks return results and avoid dead-code elimination.
- Do not cherry-pick the best run while ignoring the others.

### Comparing ratios

For `AverageTime`, if A = 100 microseconds/op and B = 80 microseconds/op, B is roughly 20% faster in time than A. The time speedup is 100/80 = 1.25x. Do not call this a 25% throughput increase in every scenario; the relationship depends on benchmark mode and workload.

## 19. Common mistakes with warmup and JIT

| Mistake | Why it is wrong | Proper practice |
| --- | --- | --- |
| Measuring only the first call and concluding a method is slow | Includes class loading, initialization, and JIT startup | Separate cold-start and steady-state |
| Measuring only after warmup and concluding startup is fast | Warmup hides startup costs | Measure process launch separately if startup matters |
| Warming up with data unlike production | Runtime profile is unrepresentative | Use inputs/profiles matching real workloads |
| Using a `nanoTime` loop for tiny methods | JIT/GC/OS noise swamps the signal | Use JMH |
| Benchmark neither returns nor consumes results | JIT may optimize away the work | Return result or use `Blackhole` |
| Using constants in all operations | Constant folding can eliminate the calculation | Use appropriate runtime inputs |
| Running all benchmarks in one un-forked JVM | Profiles and compiled code pollute each other | Use JMH `@Fork` |
| Taking only the fastest iteration | Ignores variance and runtime behavior | Inspect multiple iterations and error margins |
| Assuming every method reaches C2 | Cold methods may never need compilation | Check compilation logs when needed |
| Assuming the JVM stops changing after warmup | Profiles, GC, and deoptimization continue | Monitor stability and runtime events |
| Blaming every spike on the JIT | GC, scheduling, I/O, and contention also spike | Use JFR/profilers/logs appropriately |
| Treating microbenchmarks as production | Lacks real concurrency, data, and resource limits | Supplement with load tests and profiling |
| Disabling JIT to measure "true Java speed" | Measures an unrealistic runtime mode | Keep production-like flags unless studying the interpreter |
| Tweaking compiler thresholds arbitrarily | Can alter startup, throughput, and profiles | Measure baseline, change one variable, and record config |

## 20. A repeatable benchmarking workflow

A practical workflow for Java 17:

### Step 1: Define the question

Do you want startup time, first-request latency, steady-state latency, batch throughput, or the cost of a single method? Never start benchmarking before defining the unit and goal.

### Step 2: Build a representative workload

Pick data, distributions, sizes, object types, branches, and concurrency resembling the application. Record input seeds or fixtures for reproducibility.

### Step 3: Write the benchmark properly

Use JMH for microbenchmarks. Separate setup from invocation when setup is outside the measured scope. Use `@State`, `@Param`, `@Setup`, `@Warmup`, `@Measurement`, and `@Fork` appropriately.

### Step 4: Verify results are used

Return results or use `Blackhole`. Avoid constant folding and dead-code elimination. Verify the benchmark executes the intended logic.

### Step 5: Run a baseline

Record JDK version/vendor, JVM flags, CPU, OS, container quotas, heap, GC, benchmark parameters, and per-iteration results.

### Step 6: Inspect JIT/GC when needed

Use JIT compilation logs or JFR in a separate diagnostic run. Use a profiler to locate CPU hotspots, allocations, and contention. Avoid enabling heavy diagnostics by default during primary timing runs.

### Step 7: Repeat and compare cleanly

Keep the environment constant and change one variable at a time. Inspect variance and error bars. If changing JDK, GC, or compiler flags, record it as a distinct experiment.

### Step 8: Validate at the application level

Microbenchmarks measure one component. Run load tests or production-like workloads to verify improvements survive concurrency, GC, I/O, and resource limits.

## 21. Documenting the environment for meaningful results

A benchmark report should include at minimum:

| Information | Examples to record |
| --- | --- |
| JDK vendor/version | OpenJDK/Oracle JDK and exact update build |
| JVM | HotSpot or another runtime |
| JVM flags | Heap, GC, tiered compilation, and modified options |
| CPU | Model, core count, SMT, and architecture |
| Operating system | Version and kernel |
| Container | CPU quota, memory limit, and container runtime |
| Benchmark tool | JMH version |
| Warmup | Iterations and duration |
| Measurement | Iterations and duration |
| Fork | Number of independent processes |
| Input | Size, distribution, seed/fixture |
| Mode | AverageTime, Throughput, SampleTime, or another mode |
| Profiler | GC/JFR/JIT logs if collected |

When comparing results across machines or JDKs, missing environment metadata can lead to false conclusions. Small differences may stem from CPU frequency, container quotas, or GC rather than code changes.

## 22. When should you change JIT settings?

HotSpot exposes many `-XX` options for compilers and tiered compilation. Most applications should start with JDK 17 defaults and adjust only when backed by benchmark/profile evidence.

Principles:

- Do not disable tiered compilation just because a short microbenchmark behaves differently.
- Do not force compiling every method at startup without measuring startup and CPU cost.
- Do not tune compiler thresholds solely to make an isolated benchmark faster and deploy that to production.
- Do not rely on diagnostic flags as an application contract.
- If you must change a flag, document the config, measure both cold start and steady state, check memory/CPU, and test on a representative workload.

Inspect supported flags in your target runtime with:

~~~bash
java -XX:+PrintFlagsFinal -version
~~~

Flag lists and defaults can differ across JDKs/vendors/builds. Never copy an "optimization flags" list from an article without verifying it in your own environment.

## 23. Example: same method, two different measurements

Method under test:

~~~java
public final class TextCounter {
    public int countDigits(String text) {
        int count = 0;
        for (int i = 0; i < text.length(); i++) {
            char ch = text.charAt(i);
            if (ch >= '0' && ch <= '9') {
                count++;
            }
        }
        return count;
    }
}
~~~

### Measuring steady state

A JMH benchmark can hold input in `@State`, warm up the method, and measure many invocations:

~~~java
@State(Scope.Thread)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5)
@Measurement(iterations = 10)
@Fork(3)
public class TextCounterBenchmark {
    private final TextCounter counter = new TextCounter();
    private String input;

    @Setup
    public void setup() {
        input = "order-2026-user-123456789";
    }

    @Benchmark
    public int countDigits() {
        return counter.countDigits(input);
    }
}
~~~

This benchmarks the method in a warmed-up state. Results primarily reflect call and string-processing cost once the runtime has warmed up to the benchmark workload.

### Measuring the first call in a fresh process

If the question is first-call cost after JVM startup, a separate harness is needed:

1. Launch a fresh JVM.
2. Load classes and instantiate objects like the real application.
3. Call the method once with a defined input.
4. Record elapsed time at the defined boundaries.
5. Exit the process and repeat multiple times.

If timing from process launch, the timer must start in the parent process before launching Java. If timing only method invocation, explicitly define whether class/object setup falls outside or inside the timing window. These two measurements are not interchangeable.

## 24. Practical principles

When analyzing JIT, warmup, and measurement in Java 17:

1. Understand that bytecode may execute in the interpreter before hot methods are JIT-compiled.
2. Recognize that HotSpot's C1/C2 tiered compilation is a runtime implementation detail, not a contract across all JVMs.
3. Warm up with workloads and data representative of the measurement target.
4. Separate cold-start, warmup transition, and steady-state into distinct measurements.
5. Use JMH for microbenchmarks, with proper warmup, measurement, forks, and consumed results.
6. Avoid dead-code elimination, constant folding, and unrepresentative benchmark loops.
7. Monitor GC, class loading, JIT compilation, CPU, and caches when measurements fluctuate.
8. Use JFR/profilers/logs to explain causes rather than guessing from a single number.
9. Record complete JDK, JVM flags, hardware, environment, and benchmark configuration.
10. Validate improvements with application-level workloads before deploying to production.

The JIT enables the JVM to optimize code from observed runtime behavior, yet that very adaptation over time makes Java measurements sensitive to runtime state. Warmup serves steady-state questions; cold start requires its own measurement. By framing the right question, using JMH, and systematically observing the runtime, benchmark numbers will reflect the work you meant to measure rather than accidental state from a given run.
