# Setting Heap Limits Appropriate for Deployment Environments

## 1. Why must you set heap limits?

The Java Virtual Machine (JVM) manages the heap memory area to allocate objects. When an application runs inside a container, virtual machine, bare-metal server, or Kubernetes, the RAM a process can consume is bounded by the deployment environment's resources.

If the heap is configured too large, the process can exceed the container's memory limit because it still needs native memory, thread stacks, metaspace, code cache, direct buffers, and other regions. The operating system or container runtime may terminate the process for exceeding its memory limit, even when the Java heap is not full.

If the heap is too small, the garbage collector must run frequently, latency rises, throughput drops, and the application may throw `OutOfMemoryError: Java heap space`.

Setting heap limits requires answering three questions:

1. How much RAM does the JVM see in the actual environment?
2. How much RAM can be allocated to the Java heap after subtracting off-heap/native needs and headroom?
3. How much heap is needed to handle peak workload with acceptable GC activity and latency?

In Java 17, the primary options are:

- `-Xms`: initial and minimum heap size.
- `-Xmx`: maximum heap limit.
- `-XX:InitialRAMPercentage`: percentage of RAM used to calculate initial heap when `-Xms` is not set.
- `-XX:MaxRAMPercentage`: percentage of RAM used to calculate maximum heap when `-Xmx` is not set.
- HotSpot container awareness: detects container resource limits on Linux so the JVM computes appropriate ergonomics.

**Max heap is not the memory limit of the entire process.** This is the single most important principle when running Java in containers.

## 2. Distinguishing heap from total process memory

### 2.1. Primary memory regions of a Java process

A JVM uses several kinds of memory:

| Memory region | Purpose | Inside Java heap? |
|---|---|---|
| Java heap | Objects, arrays, and most application data allocated with `new` | Yes |
| Metaspace | Class, method, and runtime constant pool metadata | No |
| Compressed class space | Portion of class metadata when compressed class pointers are enabled | No |
| Code cache | Machine code generated by the JIT compiler | No |
| Thread stack | Per-thread stack frames, local variables, and call state | No |
| Direct buffer | Off-heap buffers, commonly used for high-performance I/O | No |
| GC native structures | Internal data structures and metadata used by the garbage collector | No |
| JNI/native library | Memory allocated by native libraries or JNI code | No |
| JVM internal/native | Other internal VM structures | No |

Additionally, the process needs memory for system libraries, memory-mapped files, sockets, and runtime activity. How the OS/container accounts for memory usage may also include page cache or off-heap items.

### 2.2. Memory budget model

You can visualize it as:

```text
Container memory limit
|
+-- Java heap (up to Xmx)
|
+-- Metaspace and class metadata
|
+-- JIT code cache
|
+-- Thread stacks
|
+-- Direct / mapped buffers
|
+-- GC and JVM native structures
|
+-- JNI, native libraries, and other regions
|
+-- Safety reserve for load fluctuations and runtime
~~~

A simple budgeting formula:

\[
M_{limit} \geq M_{heap} + M_{native} + M_{reserve}
\]

Where:

- (M_{limit}): actual container/process memory limit.
- (M_{heap}): planned maximum heap.
- (M_{native}): off-heap and native memory components.
- (M_{reserve}): safety buffer for workload variance, GC, extra threads, and system overhead.

This is a planning model, not an exact measurement formula. Measure RSS/cgroup usage in a production-like environment to verify actual values.

### 2.3. Xmx is not RSS

`-Xmx` sets the upper bound of the Java heap. The JVM does not necessarily consume that entire amount in physical RAM immediately.

Distinct concepts:

- **Maximum heap:** upper bound the JVM is allowed to grow the heap to.
- **Committed heap:** heap memory the JVM has committed for use.
- **Used heap:** portion of the heap currently holding objects considered in use.
- **RSS (Resident Set Size):** amount of the process's memory pages currently resident in RAM.
- **Container memory usage:** memory metric reported by cgroups/container runtime according to platform rules.

Therefore, you cannot assume RSS equals `Xmx`, nor can you assume a container is safe solely because heap used is low.

## 3. Key heap options in Java 17

### 3.1. -Xms: initial heap

`-Xms` specifies the initial heap size:

```shell
java -Xms256m -jar app.jar
```

This value also sets the minimum heap the JVM maintains per configuration. The JVM can expand the heap when needed, without exceeding the maximum limit.

Example:

```shell
java -Xms512m -Xmx1024m -jar app.jar
```

The application starts with a 512 MB heap and can grow up to 1024 MB.

Do not set `-Xms` equal to the entire container limit. The heap is not the JVM's only memory region; room must remain for native memory and the runtime.

### 3.2. -Xmx: maximum heap

`-Xmx` sets the upper bound of the Java heap:

```shell
java -Xmx768m -jar app.jar
```

If the application needs to allocate objects beyond what GC can reclaim and the heap cannot expand further, the JVM can throw `OutOfMemoryError: Java heap space`.

`-Xmx` does not cap:

- Metaspace.
- Thread stacks.
- Direct buffers.
- Native allocations from JNI or libraries.
- Total process RSS.

For this reason, setting `-Xmx` equal to the container's memory limit is dangerous for most applications.

### 3.3. InitialRAMPercentage and MaxRAMPercentage

HotSpot provides percentage-based ergonomics options:

```shell
java \
  -XX:InitialRAMPercentage=20.0 \
  -XX:MaxRAMPercentage=60.0 \
  -jar app.jar
```

- `InitialRAMPercentage`: percentage of available RAM used by the JVM to compute initial heap if `-Xms` is not set.
- `MaxRAMPercentage`: percentage of available RAM used by the JVM to compute maximum heap if `-Xmx` is not set.

In HotSpot Java 17, common defaults are:

| Flag | Common HotSpot default | Role |
|---|---:|---|
| `InitialRAMPercentage` | 1.5625 | Computes initial heap |
| `MaxRAMPercentage` | 25.0 | Computes maximum heap |
| `MinRAMPercentage` | 50.0 | Proportional heap cap on small-RAM systems |

These are HotSpot defaults, not guaranteed across every JVM vendor or version/provider. Check the actual flags of your deployed runtime.

**Note on the name `MinRAMPercentage`:** this flag is not the minimum initial heap percentage. It is used to compute the maximum heap limit on systems with small amounts of RAM under HotSpot ergonomics rules.

### 3.4. Precedence between Xms/Xmx and percentage flags

When `-Xmx` is set, that explicit value determines max heap; `MaxRAMPercentage` is no longer the source for calculating max heap. Similarly, `-Xms` overrides the initial heap calculation from `InitialRAMPercentage`.

Pick one clear configuration approach:

| Goal | Configuration |
|---|---|
| Fixed-size environment needing explicit max heap | `-Xms...` and `-Xmx...` |
| Same artifact running across multiple container sizes | `InitialRAMPercentage` and `MaxRAMPercentage` |
| Fixed max heap with proportional initial heap | `-Xmx...` with `InitialRAMPercentage` |

Avoid stacking overlapping flags without verifying the final values applied by the JVM.

### 3.5. MaxRAM

`-XX:MaxRAM` affects the maximum RAM baseline HotSpot uses for ergonomics:

```shell
java -XX:MaxRAM=2g -XX:MaxRAMPercentage=60.0 -jar app.jar
```

In typical container deployments, you do not need to set `MaxRAM` manually if the JVM already detects the cgroup memory limit properly. Adjust it only with a clear operational reason and after verifying what value the JVM sees.

## 4. Container awareness in Java 17

### 4.1. The JVM needs to see container limits

If the JVM sees only the host's RAM while the container has a much lower limit, the JVM may size the heap far too large for its actual environment.

Example:

- Host machine has 64 GiB of RAM.
- Container has a 1 GiB memory limit.
- Without container-limit awareness, the JVM sizes the heap based on host RAM.

Max heap can then far exceed what the container allows. Once the container hits its limit, the runtime or OS can terminate it.

HotSpot includes **container support** to read resource limits from Linux control groups (cgroups) and feed that information into ergonomics.

### 4.2. UseContainerSupport

On Linux, `-XX:+UseContainerSupport` is enabled by default in modern HotSpot builds, including Java 17. The JVM can use container memory/CPU limits when calculating available resources.

Check the flag:

```shell
java -XX:+PrintFlagsFinal -version
```

Look for the `UseContainerSupport` line. On Linux, you can also inspect system/container settings:

```shell
java -XshowSettings:system -version
```

Output depends on the platform and cgroup provider, but can display the resource limits detected by the JVM.

There is no need to add `-XX:+UseContainerSupport` to every Java 17 command if the runtime already enables it by default. What matters is verifying the JVM actually detects the right limit, especially across different base images, JDK vendors, or special cgroup setups.

### 4.3. cgroups v1 and v2

Linux uses control groups to track and restrict resources. Depending on the host, container runtime, and kernel configuration, an environment may use cgroups v1 or v2.

Common files:

| Cgroup | Memory limit | Current memory usage |
|---|---|---|
| v1 | `memory.limit_in_bytes` | `memory.usage_in_bytes` |
| v2 | `memory.max` | `memory.current` |

Common paths:

```text
/sys/fs/cgroup/memory.max
/sys/fs/cgroup/memory.current
```

On cgroup v1, paths may be located under:

```text
/sys/fs/cgroup/memory/memory.limit_in_bytes
/sys/fs/cgroup/memory/memory.usage_in_bytes
```

Actual paths can vary by mount namespace and runtime. Do not hardcode a single path for all containers.

### 4.4. Container limit differs from host RAM

With a 1 GiB container memory limit, the JVM should base ergonomics on the limit provided to the container rather than the host's full RAM. Still, the **container limit remains the total budget**, not the heap budget.

If the JVM detects 1 GiB and `MaxRAMPercentage=75` is set, max heap can approach 768 MiB, leaving the rest to cover metaspace, stacks, direct buffers, native code, and overhead. For apps with many threads or heavy NIO/direct buffers, that percentage may be too high.

## 5. Docker and Kubernetes: which limits actually take effect?

### 5.1. Docker memory limit

Example running a container with a 1 GiB limit:

```shell
docker run --memory=1g my-java-app:17
```

The container runtime configures the cgroup limit. A Java 17 JVM can detect that limit on Linux when container support is active.

Do not inspect host RAM or `free -m` output from a different environment to decide container heap sizing.

### 5.2. Kubernetes requests and limits

Example container configuration:

```yaml
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"
```

These two fields mean different things:

- **request**: the resource amount Kubernetes uses for scheduling and deciding which node to place the Pod on.
- **limit**: the memory ceiling enforced on the container by the node/runtime.

JVM budgeting must be based on the actual memory limit. Do not treat the request as if it were the container's maximum memory cap.

If no limit is set, the JVM may see more available RAM than the operations team intends. In production deployments, understand namespace, node, and container quota/limit policies.

### 5.3. Example heap percentage config in Kubernetes

```yaml
containers:
  - name: application
    image: example/application:17
    env:
      - name: JAVA_TOOL_OPTIONS
        value: "-XX:InitialRAMPercentage=20.0 -XX:MaxRAMPercentage=60.0"
    resources:
      requests:
        memory: "512Mi"
      limits:
        memory: "1Gi"
~~~

In this example, `MaxRAMPercentage=60.0` is an **illustrative starting value for testing**, not a universal fixed recommendation. Measure peak off-heap/native usage and heap live set under realistic load before finalizing.

`JAVA_TOOL_OPTIONS` is read by the JVM to append startup options. Check startup logs to confirm options were picked up and avoid unintended duplicates or conflicts with entrypoint command-line flags.

## 6. Choosing Xmx by budget instead of guesswork

### 6.1. Start from the memory limit

Suppose a container has a 1 GiB memory limit:

```text
Container limit:           1024 MiB
Native/non-heap peak:       220 MiB (initial estimate)
Safety reserve:             120 MiB
------------------------------------
Remaining heap budget:      684 MiB
~~~

Under these assumptions, you could start testing with `-Xmx640m`. Then measure under a real workload to verify:

- Is the heap sufficient for the live set and allocation bursts?
- Is peak native/non-heap truly near 220 MiB?
- Does RSS/cgroup usage keep safe headroom?
- Do GC pauses and throughput meet targets?

If native memory scales with thread count or connection count, the 220 MiB figure will change. Do not mistake an initial subtraction for measured truth.

### 6.2. Example using MaxRAMPercentage

With a 1 GiB container:

```shell
java \
  -XX:InitialRAMPercentage=20.0 \
  -XX:MaxRAMPercentage=60.0 \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/var/diagnostics/heap \
  -jar app.jar
```

If the JVM detects 1 GiB as available RAM for ergonomics, 60% roughly corresponds to about 614 MiB by simple arithmetic. Actual size also depends on ergonomics, alignment, and runtime configuration.

Percentage flags shine when the same image runs across multiple memory tiers. When container limits change, the JVM scales max heap proportionally rather than locking every environment to one hardcoded `-Xmx`.

### 6.3. Example using fixed Xms and Xmx

If each environment has an explicit budget:

```shell
java -Xms384m -Xmx640m -jar app.jar
```

Advantages:

- Max heap is explicitly known.
- Easy to compare across deployments with the same memory limit.
- Less reliance on percentage calculations.

On the flip side, running the same artifact across differently sized containers requires per-environment configuration management.

### 6.4. When to set Xms equal to Xmx?

Some systems configure:

```shell
java -Xms640m -Xmx640m -jar app.jar
```

This keeps initial and maximum heap equal, reducing heap resizing during runtime. However:

- Initial committed heap is larger than with a lower Xms.
- The container must have adequate headroom for native/non-heap regions.
- It does not mean all 640 MiB immediately becomes physical RSS.
- It does not automatically speed up GC or eliminate memory leaks.

Set Xms equal to Xmx only once you understand startup heap needs and have measured the impact on memory footprint.

## 7. Off-heap items to account for

### 7.1. Metaspace

Metaspace stores class metadata and is allocated outside the Java heap. Applications with many classes, dynamic proxies, multiple classloaders, or hot reload can use significant metaspace.

Flag:

```shell
-XX:MaxMetaspaceSize=256m
```

caps metaspace. Do not set the limit too low just to shrink RSS; if metadata demands exceed it, the JVM can throw `OutOfMemoryError: Metaspace`. Measure before applying a cap.

### 7.2. Thread stacks

Each Java thread needs its own stack. Total stack memory can grow with thread count:

~~~text
Total thread stack budget
≈ thread count × stack size per thread
~~~

The `-Xss` flag adjusts stack size per thread:

```shell
java -Xss512k -jar app.jar
```

Do not reduce `-Xss` merely to squeeze an app into a smaller container. Too small a stack can cause `StackOverflowError` on deep call chains or framework-heavy stack frames. Cutting unnecessary threads is usually the first lever to consider.

### 7.3. Direct buffers

NIO can use off-heap direct byte buffers:

~~~java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024);
~~~

Direct buffers help certain I/O paths but consume native memory. You can set a cap with:

```shell
-XX:MaxDirectMemorySize=256m
```

This flag limits total direct buffer allocations managed by the JVM mechanism. Do not set it too low if networking/database libraries rely heavily on direct buffers; the app could hit `OutOfMemoryError: Direct buffer memory`.

Do not confuse a direct buffer with its heap wrapper object: the `ByteBuffer` object itself has metadata/object fields on the heap, while the direct data region sits off-heap.

### 7.4. Code cache and GC structures

The JIT compiler produces machine code stored in the code cache; garbage collectors also require native structures, remembered sets, mark bitmaps, or metadata depending on the collector.

These areas are generally managed automatically by the JVM. Do not arbitrarily shrink the code cache or tweak numerous GC flags just to hit an RSS number without identifying which region is growing.

### 7.5. JNI and native libraries

Native libraries can allocate memory off-heap via `malloc` or native APIs. These allocations do not necessarily appear in heap dumps.

If:

- Heap used is low.
- Metaspace is stable.
- RSS/cgroup usage keeps climbing.

then examine direct buffers, thread stacks, JNI/native libraries, and off-heap mappings. A heap dump alone cannot explain every memory issue.

## 8. Measuring actual heap and memory

### 8.1. Runtime API

Java provides basic information:

```java
public class HeapUsage {
    public static void main(String[] args) {
        Runtime runtime = Runtime.getRuntime();

        long max = runtime.maxMemory();
        long committed = runtime.totalMemory();
        long free = runtime.freeMemory();
        long used = committed - free;

        System.out.printf("Heap max: %.1f MiB%n", toMiB(max));
        System.out.printf("Heap committed: %.1f MiB%n", toMiB(committed));
        System.out.printf("Heap used: %.1f MiB%n", toMiB(used));
    }

    private static double toMiB(long bytes) {
        return bytes / 1024.0 / 1024.0;
    }
}
```

Meaning:

- `maxMemory()`: maximum heap the JVM can use, usually reflecting the heap limit after ergonomics.
- `totalMemory()`: currently committed heap.
- `freeMemory()`: free portion inside committed heap.
- `totalMemory() - freeMemory()`: estimated heap used at the time of reading.

Values change over time and can shift after GC. They do not measure total process RSS.

### 8.2. MemoryMXBean

```java
import java.lang.management.ManagementFactory;
import java.lang.management.MemoryMXBean;
import java.lang.management.MemoryUsage;

MemoryMXBean memoryBean = ManagementFactory.getMemoryMXBean();
MemoryUsage heap = memoryBean.getHeapMemoryUsage();
MemoryUsage nonHeap = memoryBean.getNonHeapMemoryUsage();

System.out.println("Heap used: " + heap.getUsed());
System.out.println("Heap committed: " + heap.getCommitted());
System.out.println("Heap max: " + heap.getMax());
System.out.println("Non-heap used: " + nonHeap.getUsed());
System.out.println("Non-heap committed: " + nonHeap.getCommitted());
```

`MemoryMXBean` reports heap and non-heap usage from the JVM's perspective. It excludes many native allocations made by third-party libraries.

### 8.3. Tracking direct and mapped buffers

```java
import java.lang.management.BufferPoolMXBean;
import java.lang.management.ManagementFactory;

for (BufferPoolMXBean pool :
        ManagementFactory.getPlatformMXBeans(BufferPoolMXBean.class)) {
    System.out.printf(
            "%s: count=%d, used=%d, capacity=%d%n",
            pool.getName(),
            pool.getCount(),
            pool.getMemoryUsed(),
            pool.getTotalCapacity()
    );
}
```

Pools are commonly named `direct` and `mapped`. These metrics help monitor off-heap buffer pools managed by the JVM.

### 8.4. Tracking thread count

```java
int threadCount = ManagementFactory.getThreadMXBean()
        .getThreadCount();
System.out.println("Live threads: " + threadCount);
```

If thread count climbs unexpectedly, total stack memory can rise too. Combine thread metrics with `-Xss` and RSS to understand memory cost.

## 9. Diagnostics with JDK 17 tools

### 9.1. Viewing effective JVM flags

When the JVM is running:

```shell
jcmd <pid> VM.flags
```

View flag values after ergonomics:

```shell
java -XX:+PrintFlagsFinal -version
```

On Linux/macOS you can filter:

```shell
java -XX:+PrintFlagsFinal -version 2>&1 | grep -E "MaxHeapSize|InitialHeapSize|MaxRAMPercentage|InitialRAMPercentage|UseContainerSupport"
```

On Windows PowerShell:

```powershell
java -XX:+PrintFlagsFinal -version 2>&1 |
    Select-String "MaxHeapSize|InitialHeapSize|MaxRAMPercentage|InitialRAMPercentage|UseContainerSupport"
```

Do not inspect only the command line; check the final flags the JVM actually applies. `-Xmx` or `-Xms` can override percentage flags.

### 9.2. Viewing current heap

```shell
jcmd <pid> GC.heap_info
```

This displays heap and collector details for the running JVM. Combine with used/committed/max heap metrics to check whether the heap is approaching its limit.

### 9.3. Viewing VM configuration and info

```shell
jcmd <pid> VM.info
jcmd <pid> VM.flags
```

These commands inspect runtime details and active flags. Attach tools may need to run as the same user or in an environment with permission to access the process.

### 9.4. Native Memory Tracking

HotSpot provides Native Memory Tracking (NMT) to inspect several native memory categories managed by the JVM. Enable it at startup:

```shell
java -XX:NativeMemoryTracking=summary -jar app.jar
```

Then query:

```shell
jcmd <pid> VM.native_memory summary
```

NMT has overhead and does not track every native allocation from third-party libraries. It is a complementary diagnostic tool, not a replacement for RSS/cgroup metrics.

### 9.5. GC logging

Java 17 uses unified logging:

```shell
java -Xlog:gc*:file=/var/log/app-gc.log:time,uptime,level,tags -jar app.jar
```

GC logs help inspect:

- Heap before and after GC.
- Collection frequency and type.
- Pause times.
- Whether the heap frequently nears its limit.
- How much live data remains after GC.

Do not conclude the heap is undersized from a single long GC. Observe trends over a long enough workload covering warm-up and peak load.

## 10. Handling OutOfMemoryError and container OOM kills

### 10.1. Different types of memory errors

| Symptom | Possible memory region / cause |
|---|---|
| `OutOfMemoryError: Java heap space` | Cannot allocate an object on the heap after GC fails to reclaim enough |
| `OutOfMemoryError: GC overhead limit exceeded` | JVM spends most of its time in GC while reclaiming very little heap |
| `OutOfMemoryError: Metaspace` | Metaspace cannot expand enough |
| `OutOfMemoryError: Direct buffer memory` | Cannot allocate a direct buffer under current limit/mechanism |
| `OutOfMemoryError: unable to create native thread` | OS/JVM cannot spawn another thread, possibly due to native memory or thread/process limits |
| Container state `OOMKilled` | Cgroup/kernel terminates the container when exceeding memory limit; JVM may not have time to throw OOME or write a heap dump |

Not every memory issue is heap exhaustion. Identify the exact error type before raising `-Xmx`.

### 10.2. Enabling heap dumps on OOME

Configuration:

```shell
java \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/var/diagnostics/heap \
  -jar app.jar
```

When the JVM hits certain forms of `OutOfMemoryError`, it attempts to write a heap dump to analyze which objects are retaining memory. The target directory must exist or be creatable appropriately, have write permissions, and have enough disk space.

Heap dumps can be very large and contain sensitive application data. Protect access permissions, retention periods, and transfer workflows; never place dumps into public logs or container image layers.

### 10.3. OOMKilled may not produce a heap dump

When the kernel kills a process due to a cgroup memory limit, the JVM can be terminated abruptly before handling an exception or writing a dump. In Kubernetes, the container may show state `OOMKilled` and a common exit code is 137.

Therefore, monitor metrics before hitting the limit:

- Container/cgroup memory usage and peak.
- Process RSS.
- Heap used/committed/max.
- Direct buffer usage.
- Metaspace.
- Thread count.
- GC pauses and allocation rate.

A heap dump is only one diagnostic source; it does not replace native memory and container metrics.

### 10.4. A heap dump does not prove a memory leak on its own

A heap dump is a point-in-time snapshot. Finding a leak requires identifying which objects remain reachable, the reference paths holding them, retained sizes, and growth trends over time.

A large heap may simply be a legitimate live set under heavy load. Conversely, post-GC heap used rising across cycles may suggest objects are retained longer than intended.

## 11. Workflow for sizing heap on a new application

### Step 1 — Determine the real memory limit

Record:

- Container memory limit.
- Kubernetes requests/limits.
- Host/VM and cgroup version.
- JDK vendor, version, and JVM options.
- Container/replica count and any sidecars.

Verify the JVM sees the right memory limit via container support.

### Step 2 — Measure startup baseline

Track:

- RSS after startup.
- Heap used, committed, and max.
- Metaspace and code cache.
- Thread count.
- Direct/mapped buffer usage.
- NMT summary if needed.

A baseline tells you how much memory the application uses before handling heavy load.

### Step 3 — Run a representative workload

Test with:

- Realistic data sizes.
- Near-peak concurrency.
- Expected connection and thread counts.
- Warm-up/JIT.
- Batch or background tasks.
- Large object creations and allocation bursts.

Do not size based on an idle run or average traffic alone.

### Step 4 — Measure live set and GC

Observe heap after GC cycles, collection frequency, pause times, and allocation rate. The heap needs enough room for the live set, allocation bursts, and GC operation.

If post-GC live set already consumes most of max heap, increasing heap may be necessary. If live set is low yet RSS is high, investigate off-heap/native memory before raising the heap.

### Step 5 — Budget for off-heap/native memory

Measure or estimate:

- Metaspace.
- Thread stacks from thread count and `-Xss`.
- Direct buffers.
- Code cache and GC structures.
- JNI/native libraries.
- Safety reserve.

Check the total against the cgroup memory limit, not just Xmx.

### Step 6 — Choose an initial configuration

Choose explicit `-Xmx` if each environment has a fixed budget. Choose `MaxRAMPercentage` if the same image runs across multiple memory tiers and the JVM detects container limits accurately.

Set `-Xms`/InitialRAMPercentage based on startup and footprint requirements. Do not default to setting it equal to Xmx.

### Step 7 — Stress test and verify headroom

Ramp load to expected peak and slightly beyond within safe test limits. Confirm:

- No OOMs.
- Container is not OOMKilled.
- GC pauses and throughput meet goals.
- RSS/cgroup usage keeps headroom.
- As threads/connections scale, native memory stays within budget.

### Step 8 — Monitor after deployment

Maintain dashboards and alerts for heap, GC, RSS/cgroup usage, thread count, direct memory, and OOM events. Revisit sizing whenever workloads, JDKs, libraries, or memory limits change.

## 12. Example configurations by environment

### 12.1. Small 512 MiB container

With a 512 MiB limit, do not set a 512 MiB heap. A trial configuration could be:

```shell
java -Xms128m -Xmx256m -jar app.jar
```

The remainder covers metaspace, stacks, direct buffers, JVM native memory, and reserve. This is only a starting point; an application may need a different heap size depending on live set and native usage.

### 12.2. 1 GiB container, same artifact across multiple tiers

```shell
java \
  -XX:InitialRAMPercentage=20.0 \
  -XX:MaxRAMPercentage=60.0 \
  -jar app.jar
```

As container memory limits change, max heap scales as a percentage of JVM-detected RAM. Re-verify native headroom at each tier.

### 12.3. Virtual machine with a fixed memory budget

```shell
java -Xms1g -Xmx2g -jar app.jar
```

Explicit settings keep heap bounds clear. Before deploying, confirm the VM has enough RAM for 2 GiB heap plus off-heap/native memory and the OS.

### 12.4. Application with heavy direct buffer usage

If profiling shows heavy direct buffer use, you can apply an appropriate cap:

```shell
java -Xmx512m -XX:MaxDirectMemorySize=256m -jar app.jar
```

Total memory still needs metaspace, stacks, code cache, GC, and other native items. Do not add just these two numbers and assume the budget is complete.

### 12.5. Application with many threads

If an application spawns thousands of threads, thread stacks can be a major share of memory footprint. Before lowering `-Xss`, consider:

- Using a bounded thread pool.
- Using async/non-blocking I/O if architecturally suitable.
- Checking for thread leaks.
- Measuring stack usage and determining the safe minimum stack size.

Reducing thread count usually addresses the root cause better than shrinking stack size alone.

## 13. Common mistakes when setting heap limits

| Mistake | Consequence | Remediation |
|---|---|---|
| Setting `-Xmx` equal to container memory limit | No headroom for off-heap/native; prone to OOMKilled | Subtract native budget and reserve before choosing heap |
| Thinking Xmx is total JVM RAM | Misses metaspace, stacks, direct buffers, JNI | Monitor heap and process/cgroup memory together |
| Sizing from host RAM instead of cgroup limit | JVM may pick a heap far too large for the container | Confirm container awareness and actual memory limit |
| Treating Kubernetes request as a hard limit | JVM may size against the wrong resource level | Budget using the container memory limit |
| Setting Xms = Xmx out of habit | Higher baseline committed heap, less initial headroom | Pick Xms based on actual startup/live set needs |
| Raising Xmx when RSS is high but heap is low | Fails to fix native memory pressure and shrinks headroom further | Measure metaspace, stacks, direct buffers, JNI, and NMT |
| Lowering Xmx solely to avoid OOMKilled | Can trigger Java heap OOME and GC thrashing sooner | Analyze total memory and workload |
| Setting MaxMetaspaceSize too low | Metaspace OOME when loading classes | Set a cap only after measuring metadata usage |
| Setting MaxDirectMemorySize too low | Direct buffer memory OOME | Measure direct buffer workload before capping |
| Lowering Xss too far | StackOverflowError | Reduce thread count or measure call depth first |
| Ignoring thread count | Stack/native memory grows with concurrency | Monitor threads and bound pools |
| Checking only heap dumps on container OOMKilled | Misses off-heap usage; dump may never be written | Combine cgroup/RSS/NMT/metrics |
| Failing to verify final JVM flags | Flags may be overridden or ignored | Use `jcmd VM.flags` and `PrintFlagsFinal` |
| Copying another app's heap ratio | Workloads and native overheads differ | Size via your own app's benchmarks/load tests |

## 14. Java 17 example: printing heap and buffer info

Save as **MemorySnapshot.java**:

```java
import java.lang.management.BufferPoolMXBean;
import java.lang.management.ManagementFactory;
import java.lang.management.MemoryMXBean;
import java.lang.management.MemoryUsage;
import java.lang.management.ThreadMXBean;

public class MemorySnapshot {

    private static double mib(long bytes) {
        return bytes / 1024.0 / 1024.0;
    }

    public static void main(String[] args) {
        MemoryMXBean memoryBean = ManagementFactory.getMemoryMXBean();
        MemoryUsage heap = memoryBean.getHeapMemoryUsage();
        MemoryUsage nonHeap = memoryBean.getNonHeapMemoryUsage();

        System.out.printf("Heap used: %.1f MiB%n", mib(heap.getUsed()));
        System.out.printf(
                "Heap committed: %.1f MiB%n",
                mib(heap.getCommitted())
        );
        System.out.printf("Heap max: %.1f MiB%n", mib(heap.getMax()));
        System.out.printf(
                "Non-heap used: %.1f MiB%n",
                mib(nonHeap.getUsed())
        );

        ThreadMXBean threadBean = ManagementFactory.getThreadMXBean();
        System.out.println("Live threads: " + threadBean.getThreadCount());

        for (BufferPoolMXBean pool :
                ManagementFactory.getPlatformMXBeans(
                        BufferPoolMXBean.class
                )) {
            System.out.printf(
                    "%s: used=%.1f MiB, capacity=%.1f MiB, count=%d%n",
                    pool.getName(),
                    mib(pool.getMemoryUsed()),
                    mib(pool.getTotalCapacity()),
                    pool.getCount()
            );
        }
    }
}
```

Compile and run:

```shell
javac --release 17 MemorySnapshot.java
java -Xms128m -Xmx512m MemorySnapshot
```

This example reads metrics exposed by the JVM. It does not measure total RSS/cgroup usage. In deployment environments, combine these figures with container or process metrics from your observability platform.

## 15. Operational checklist when changing heap limits

Before deployment:

- Confirm the container/VM memory limit.
- Confirm the Java 17 JVM detects the right cgroup limit.
- Verify final Xms/Xmx and percentage flags.
- Estimate metaspace, thread stacks, direct buffers, and native libraries.
- Confirm the heap dump path is writable and has sufficient disk space.
- Run representative and peak workloads.
- Check GC pauses, throughput, and peak RSS/cgroup usage.

After deployment:

- Monitor heap used/committed/max.
- Monitor process RSS and current/peak container memory.
- Monitor GC pauses and allocation rate.
- Monitor metaspace, direct buffers, and thread count.
- Alert before cgroup usage reaches the limit.
- Track OOMKilled and OutOfMemoryError separately.
- Re-evaluate when increasing concurrency, changing libraries, or upgrading the JDK.
