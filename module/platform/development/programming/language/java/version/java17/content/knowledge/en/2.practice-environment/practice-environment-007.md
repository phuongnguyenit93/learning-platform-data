# Organizing Source Code, Resources, and Replayable Examples in Java 17

A Java example is truly useful only when someone else can grab the source code, set up the right environment, run the same commands, and observe the expected output. To achieve that, you need to clearly organize **application source code**, **resources**, **test code**, **test data**, **build configuration**, and **run instructions**.

This lesson builds a complete **Java 17 + Maven + JUnit Jupiter** project. The APIs used—such as `InputStream.readAllBytes()`, `String.isBlank()`, `String.strip()`, and `String.formatted()`—are all included in Java 17. Tool versions are pinned so the example has a deterministic build baseline; do not assume they are the latest releases at all times.

## 1. What Makes an Example "Replayable"?

An example should answer five questions:

1. **Which JDK runs it?** Here it is **JDK 17**, including both `java` and `javac`.
2. **Which build tool is used?** The project uses Maven and provides the Maven Wrapper.
3. **Where are source code, resources, and tests?** They follow the standard directory layout.
4. **What are the build, test, and run commands?** Commands are documented clearly for Windows, Linux, and macOS.
5. **What output indicates the right result?** Automated tests and sample output are included.

It helps to distinguish:

| Goal | Meaning | How to Achieve It |
| --- | --- | --- |
| Replay same functionality | Same inputs produce meaningfully equivalent output | Document data, run commands, and expectations clearly |
| Build on another machine | Another machine can compile, test, and package | Pin target JDK, Maven, plugins, and dependencies |
| Byte-for-byte identical artifacts | Built files match identically across builds | Additionally control timestamps, environment, toolchains, and build steps |

This exercise provides the foundation for the first two goals. `project.build.outputTimestamp` helps stabilize timestamps inside the JAR, though it alone does not guarantee byte-for-byte identical artifacts across every environment.

## 2. Standard Source Directory Structure

~~~text
replay-demo/
├── .mvn/
│   └── wrapper/
│       └── maven-wrapper.properties   # Generated by Maven Wrapper
├── mvnw                              # Wrapper for Linux/macOS
├── mvnw.cmd                          # Wrapper for Windows
├── pom.xml                           # Maven configuration
├── README.md                         # Build, test, and run commands
├── .gitignore
└── src/
    ├── main/
    │   ├── java/
    │   │   └── vn/example/replay/
    │   │       ├── App.java
    │   │       └── GreetingService.java
    │   └── resources/
    │       └── messages/
    │           └── greeting.txt
    └── test/
        ├── java/
        │   └── vn/example/replay/
        │       └── GreetingServiceTest.java
        └── resources/
            └── fixtures/
                └── person.txt
~~~

| Path | Purpose | Packaged Inside Application JAR? |
| --- | --- | --- |
| `src/main/java` | Application Java source code | Yes, after compiling to `.class` |
| `src/main/resources` | Templates, static data, and runtime resources | Yes, on the classpath |
| `src/test/java` | Unit test code | No |
| `src/test/resources` | Fixtures used during tests | No |
| `pom.xml` | Build and dependency declarations | No |
| `target/` | Compiled output and packages generated by Maven | Should not be committed to Git |

The `vn/example/replay` folder mirrors the `vn.example.replay` package name. For multi-class code, use an explicit package instead of placing classes in the *default package*. You can add subpackages like `service`, `model`, and `repository` as the app grows; for small examples, splitting into too many nested folders makes it harder for learners to follow.

Java 17 also supports the **Java Platform Module System (JPMS)** via `module-info.java`. This sample project intentionally runs on the **classpath**, so `module-info.java` is unnecessary. If you adopt the module path for a larger project, configure and declare modules consistently with its dependencies.

## 3. Writing a Program with Packaged Resources

The example loads a greeting template from `src/main/resources`, takes a name from command-line arguments, and prints the formatted sentence.

### 3.1. Separating Logic from the `main` Class

Create **`src/main/java/vn/example/replay/GreetingService.java`**:

~~~java
package vn.example.replay;

public final class GreetingService {
    private GreetingService() {
        // Utility class; no instantiation needed.
    }

    public static String greet(String template, String name) {
        if (template == null || template.isBlank()) {
            throw new IllegalArgumentException("Greeting template must not be blank");
        }
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("Name must not be blank");
        }
        return template.formatted(name.strip());
    }
}
~~~

This class only handles string logic and does not depend on the console or filesystem, so it can be tested independently. `String.strip()` trims surrounding whitespace from the name; `String.formatted()` formats the greeting at the `%s` placeholder.

The example uses a project-controlled template containing one `%s` placeholder. If a template comes from an untrusted source, validate its format and handle formatting errors instead of assuming the content is always valid.

### 3.2. Reading a Resource from the Classpath

Create **`src/main/java/vn/example/replay/App.java`**:

~~~java
package vn.example.replay;

import java.io.IOException;
import java.io.InputStream;
import java.nio.charset.StandardCharsets;

public final class App {
    private App() {
    }

    public static void main(String[] args) throws IOException {
        String name = args.length == 0 ? "Java 17" : args[0];

        try (InputStream stream =
                     App.class.getResourceAsStream("/messages/greeting.txt")) {
            if (stream == null) {
                throw new IllegalStateException(
                        "Resource not found: /messages/greeting.txt");
            }

            String template = new String(
                    stream.readAllBytes(), StandardCharsets.UTF_8).strip();

            System.out.println(GreetingService.greet(template, name));
        }
    }
}
~~~

Create **`src/main/resources/messages/greeting.txt`**, saving the file in UTF-8:

~~~text
Hello, %s! This is a Java 17 example.
~~~

Three key points to understand:

- `App.class.getResourceAsStream("/messages/greeting.txt")` searches for the resource from the **classpath root**; the leading `/` is important when calling `Class.getResourceAsStream`.
- If the resource does not exist, the method returns `null`. Checking and throwing a clear error makes it easy to spot a misplaced folder or missing packaged file.
- `try-with-resources` closes the stream; `StandardCharsets.UTF_8` reads Vietnamese and non-ASCII text reliably across machines with different default charsets.

**Do not** read this file via the path `src/main/resources/messages/greeting.txt` in runtime code. That path belongs to the source tree, whereas when the application runs from a JAR, the resource lives inside the archive and is loaded via the classpath.

## 4. Writing Tests and Dedicated Fixtures

Create **`src/test/java/vn/example/replay/GreetingServiceTest.java`**:

~~~java
package vn.example.replay;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertThrows;

import java.io.IOException;
import java.io.InputStream;
import java.nio.charset.StandardCharsets;
import org.junit.jupiter.api.Test;

class GreetingServiceTest {

    @Test
    void formatsAndTrimsName() {
        String actual =
                GreetingService.greet("Hello, %s!", "  An  ");

        assertEquals("Hello, An!", actual);
    }

    @Test
    void rejectsBlankName() {
        assertThrows(
                IllegalArgumentException.class,
                () -> GreetingService.greet("Hello, %s!", "   "));
    }

    @Test
    void readsFixtureFromTestClasspath() throws IOException {
        try (InputStream stream =
                     getClass().getResourceAsStream("/fixtures/person.txt")) {
            assertNotNull(stream, "Missing fixture /fixtures/person.txt");

            String name = new String(
                    stream.readAllBytes(), StandardCharsets.UTF_8).strip();

            assertEquals(
                    "Hello, Bình!",
                    GreetingService.greet("Hello, %s!", name));
        }
    }
}
~~~

Create **`src/test/resources/fixtures/person.txt`**, encoded in UTF-8:

~~~text
Bình
~~~

During Maven's test lifecycle:

- `src/main/java` is compiled into `target/classes`; `src/main/resources` is copied into the same location so it is available on the classpath.
- `src/test/java` is compiled into `target/test-classes`; `src/test/resources` is copied there as well.
- Tests can access both application classes and test fixtures, while test fixtures do not appear in the regular application JAR.

Fixtures should be small, stable, and meaningful for the test's purpose. Outcomes must be verified with **assertions** so pass/fail is determined automatically; merely calling `System.out.println()` in a test and eyeballing output is difficult to replay reliably.

## 5. Configuring Maven for JDK 17 and JUnit

Create **`pom.xml`** in the root directory:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>vn.example</groupId>
    <artifactId>replay-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <project.reporting.outputEncoding>UTF-8</project.reporting.outputEncoding>
        <project.build.outputTimestamp>2026-01-01T00:00:00Z</project.build.outputTimestamp>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.11.4</version>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-clean-plugin</artifactId>
                <version>3.4.1</version>
            </plugin>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-resources-plugin</artifactId>
                <version>3.3.1</version>
            </plugin>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.14.0</version>
            </plugin>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
                <version>3.5.2</version>
            </plugin>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-jar-plugin</artifactId>
                <version>3.4.2</version>
                <configuration>
                    <archive>
                        <manifest>
                            <mainClass>vn.example.replay.App</mainClass>
                        </manifest>
                    </archive>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
~~~

Meaning of the configuration elements:

- `maven.compiler.release=17` enforces Java 17 source/API compatibility and emits matching bytecode.
- `project.build.sourceEncoding=UTF-8` sets the charset for source and resource processing across supporting plugins.
- The JUnit dependency has `scope=test`, serving tests only and staying out of the application's runtime classpath.
- `maven-surefire-plugin` runs tests matching standard naming conventions, such as `GreetingServiceTest`.
- `maven-jar-plugin` writes a manifest with `Main-Class` so you can run `java -jar`.
- Plugin versions are explicitly pinned so build behavior does not shift unexpectedly when an environment picks newer plugin versions.

This sample has no external runtime dependencies, so the standard JAR can launch directly. In applications with runtime libraries, **the default JAR does not automatically bundle all dependencies**. In those cases you must choose a suitable distribution approach: a classpath alongside dependency JARs, an application bundle, or a properly configured and tested packaging plugin.

## 6. Using Maven Wrapper to Avoid Depending on Preinstalled Maven

Maven Wrapper consists of the `mvnw`/`mvnw.cmd` scripts and metadata selecting the project's Maven version. Anyone cloning the repo still needs a suitable JDK, but does not have to guess which Maven version to install.

If initializing the project on a machine with Maven installed, generate the wrapper **once** at the root directory:

~~~bash
mvn -N org.apache.maven.plugins:maven-wrapper-plugin:3.3.4:wrapper -Dmaven=3.9.11
~~~

Commit the generated scripts and files in `.mvn/wrapper`. From then on, teammates invoke the project wrapper. Maven 3.9.11 here is the **pinned version for this example**, not a claim about the latest Maven release.

### 6.1. Windows PowerShell

Run from the directory containing `pom.xml` and `mvnw.cmd`:

~~~powershell
java -version
javac -version
.\mvnw.cmd --version
.\mvnw.cmd clean verify
java -jar .\target\replay-demo-1.0.0.jar
java -jar .\target\replay-demo-1.0.0.jar Lan
~~~

### 6.2. Linux and macOS

~~~bash
java -version
javac -version
./mvnw --version
./mvnw clean verify
java -jar target/replay-demo-1.0.0.jar
java -jar target/replay-demo-1.0.0.jar Lan
~~~

If `mvnw` lacks execute permission on Unix, run `chmod +x mvnw` and commit the file permission in Git.

`clean verify` removes old build outputs, processes sources and resources, runs tests, and packages the artifact. The first run when the wrapper or Maven downloads distributions/dependencies not yet cached may require network access.

Expected output from the two `java -jar` commands:

~~~text
Hello, Java 17! This is a Java 17 example.
Hello, Lan! This is a Java 17 example.
~~~

When tests pass, Maven reports a successful build. Log formatting, download paths, and run durations vary across machines; what needs to be verified is that all assertions pass and the program outputs the exact strings shown above.

Use JDK 17's `jar` tool to inspect the artifact contents:

~~~bash
jar --list --file target/replay-demo-1.0.0.jar
~~~

The listing should include `vn/example/replay/App.class`, `vn/example/replay/GreetingService.class`, and `messages/greeting.txt`. The `fixtures/person.txt` fixture is for testing only and must not be packaged into the application JAR.

## 7. Distinguishing JAR Resources from External Files

This distinction is a common reason an example works only inside an IDE.

**Packaged resource:** project-managed, read-only files shipped alongside code. Read them via the classpath.

~~~java
// Class.getResourceAsStream: leading "/" means classpath root.
InputStream a = App.class.getResourceAsStream("/messages/greeting.txt");

// ClassLoader.getResourceAsStream: no leading "/".
InputStream b = App.class.getClassLoader()
        .getResourceAsStream("messages/greeting.txt");
~~~

**External file:** data created or modified at runtime, such as user-provided CSVs, generated reports, or environment-specific config files. Read them via `Path`/`Files`:

~~~java
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

Path input = Path.of("data", "input.txt");
String content = Files.readString(input, StandardCharsets.UTF_8);
~~~

`Path.of("data", "input.txt")` is **relative to the process's working directory**, not automatically relative to the `.java` file or JAR location. If an example needs an external file, the README must explain where to place it or how to pass its path as an argument.

Do not bundle sensitive data such as API keys, passwords, or tokens into `src/main/resources`. Use environment variables or a secret manager appropriate to the runtime environment.

## 8. Factors Affecting Replayability

**Versions:** explicitly specify the target JDK, use a wrapper, and pin dependency/plugin versions. When upgrading, make deliberate changes and rerun tests. Avoid dynamic version ranges for examples meant to remain reproducible.

**Data:** store small fixtures in the repo when appropriate; supply sample inputs containing no private data. Tests should use self-contained data rather than relying on files sitting on the author's machine.

**Charset and line endings:** save text files as UTF-8 and pass `StandardCharsets.UTF_8` when reading and writing. When testing multiline strings across operating systems, account for `\n` vs. `\r\n` differences or normalize line endings before comparing if needed.

**Time, randomness, and locale:** tests relying on `Instant.now()`, `LocalDate.now()`, unseeded `Random`, the default timezone, locale-dependent number/date formatting, or live network calls may produce varying results. For logic requiring deterministic output, inject `Clock`, `ZoneId`, seeds, and `Locale` explicitly; use fakes/stubs for external dependencies in unit tests.

**Build outputs:** never edit files inside `target/` because they get overwritten. Edit files in `src` or `pom.xml` and rebuild. Do not commit caches, logs, or generated artifacts without a clear distribution reason.

Minimal `.gitignore`:

~~~gitignore
target/
*.log
.idea/
*.iml
.vscode/
~~~

Do not ignore `mvnw`, `mvnw.cmd`, or all of `.mvn/wrapper/`: those are what allow others to run the exact build tool you chose.

## 9. The README Is Part of the Example

Create a `README.md` with concise, self-contained instructions. For example:

~~~markdown
# replay-demo

Java 17 example reading resources from the classpath with JUnit tests.

## Requirements
- JDK 17.
- Network connection on first run so Maven Wrapper can download missing components.

## Build and test
Windows PowerShell: .\mvnw.cmd clean verify
Linux/macOS: ./mvnw clean verify

## Run
java -jar target/replay-demo-1.0.0.jar
java -jar target/replay-demo-1.0.0.jar Lan

## Output
Hello, Java 17! This is a Java 17 example.
Hello, Lan! This is a Java 17 example.

## File locations
- src/main/java: application code
- src/main/resources: resources bundled with the JAR
- src/test/java: test code
- src/test/resources: test fixtures
~~~

The README should specify **the directory where commands are run**, installation prerequisites, build steps, test steps, launch commands, arguments, and expected output. If commands differ across operating systems, list each OS variant separately rather than assuming every shell uses the same syntax.

In repositories with multiple examples, you can use `examples/` or separate modules per topic. Each example should have a clear entry point and run command; shared code should live in a module/library with explicit dependencies rather than being copy-pasted and drifting out of sync.

## 10. Common Errors and Resolutions

| Symptom | Typical Cause | Resolution |
| --- | --- | --- |
| Runs in IDE, `java -jar` reports file not found | Code reads `src/main/resources` directly as a filesystem path | Switch to `getResourceAsStream` and inspect JAR contents |
| `getResourceAsStream` returns `null` | Wrong path or resource is not on the classpath | Check leading `/` and placement under `src/main/resources` |
| Tests fail to recognize `org.junit.jupiter.api` | Missing JUnit dependency or tests placed in wrong directory | Declare `junit-jupiter` with `scope=test` and place tests under `src/test/java` |
| Fails on another machine with Java version error | Wrong JDK or compiler target | Check `java -version`, `javac -version`, and `release=17` |
| Vietnamese/non-ASCII text displays garbled characters | Mismatched charsets | Save and read as UTF-8, and configure encoding in Maven |
| Tests pass intermittently | Dependency on current time, timezone, randomness, or network | Control inputs and replace external dependencies in unit tests |
| JAR launches but fails with missing libraries | Standard JARs do not bundle runtime dependencies | Define a packaging/distribution strategy for dependencies |
| Git repo polluted with build artifacts and logs | Committed `target/` or IDE files | Add an appropriate `.gitignore` |

## 11. Extension Exercises

1. Create `src/main/resources/messages/farewell.txt`, load it via the classpath, and print a farewell message. Verify the built JAR still locates the file.
2. Add a test using a new fixture in `src/test/resources` and verify the output with `assertEquals`.
3. Add an option to accept a text file path from an argument, read it with `Files.readString`, and document how to pass the path in `README.md`.
4. Edit `greeting.txt`, rerun `clean verify`, and observe the updated text after packaging a new JAR.

**Expected outcome:** Anyone with only the repository, JDK 17, and the README instructions can install missing build components, run `clean verify`, launch the JAR, and observe the documented output—without needing the author's local paths or manual IDE steps.
