# Risks of Reading Untrusted Object Data in Java 17

> **Topic:** Java 17  
> **Chapter:** Deserialization Filters  
> **Scope:** Java Object Serialization and the object filtering mechanisms of the current JPMS/JDK. The content focuses on APIs still usable in Java 17, especially `ObjectInputFilter` (JEP 290) and the `ObjectInputFilter.Config` filter factory (JEP 415).

## 1. Why Can Reading an Object Stream Be Dangerous?

Java supports converting an object graph into a sequence of bytes via **serialization** and reconstructing the object graph from bytes via **deserialization**. Familiar APIs include:

- `ObjectOutputStream` for writing objects.
- `ObjectInputStream` for reading and reconstructing objects.
- `Serializable` for marking classes that can participate in the default serialization mechanism.
- `Externalizable` for classes to control how data is written and read themselves.

For data generated by the application itself, stored in a trusted zone, and appropriately protected, serialization can serve certain compatibility needs. However, when a program reads an object stream provided by a user, network, downloaded file, message queue, or external system, that data can be crafted intentionally to trigger dangerous behavior.

**Calling `readObject()` should not be treated as a passive data-parsing operation.** While reconstructing the object graph, Java can instantiate many classes and invoke serialization callbacks defined by those classes. If suitable classes are present on the classpath, a crafted object graph can trigger an unintended chain of behavior.

The most important security rule:

> Do not deserialize Java native serialization data from untrusted sources. If a legacy system must accept this type of data, apply a very narrow allowlist, limit the object graph size, validate the data, and control dependencies.

Object filters reduce risk, but they do not turn an arbitrary object stream into safe data.

## 2. Main Risk Categories

### 2.1. Behavior Execution via Gadget Chains

A class can define callbacks that are invoked during deserialization, such as:

- `readObject`: reads and restores the object's state.
- `readExternal`: reading logic implemented by an `Externalizable` class.
- `readResolve`: replaces the newly deserialized object with another object.
- Other methods/mechanisms triggered indirectly by the callbacks above or by operations using the object after deserialization.

A **gadget** is a class whose behavior is useful for an exploitation chain. A **gadget chain** combines multiple classes so that when the object graph is reconstructed or used, the callbacks lead to dangerous actions—for example, invoking a sink that can execute commands, access resources, or modify state.

Not every `readObject()` call automatically executes OS commands. The risk depends on which classes can be loaded, how they process data, and which gadgets/sinks are present in the application. However, even a single dependency library containing a suitable gadget can increase the attack surface.

### 2.2. Denial of Service

A malicious object stream can attempt to make the application consume excessive resources:

- **Overly deep object graph:** nested reference chains can put pressure on the stack or CPU.
- **Too many objects/references:** creating a huge number of objects, increasing allocation and garbage collection.
- **Huge arrays:** declaring a very large array length, causing memory pressure.
- **Overly large stream:** transmitting a byte volume exceeding what the application can handle.
- **Complex structures or reference cycles:** increasing the cost of graph reconstruction and callback execution.
- **Resource-intensive callbacks:** an allowed deserialized class might perform expensive computation or resource access inside its callback.

Therefore, checking allowed classes alone is not enough. You need to limit depth, reference count, byte count, and array length to match valid data.

### 2.3. Data Invariant Violations and Type Assumptions

After deserialization, the application may receive an object whose state does not satisfy the business rules that code normally expects. For example:

- Negative quantities or values exceeding limits.
- Enum/flag states inappropriate for the workflow.
- Inconsistent relationships between objects.
- Null references in places where the application assumed a value is always present.
- Objects containing stale data, the wrong version, or data intentionally modified by the sender.

Do not treat a deserialized object as valid merely because it has the expected class. Validate the root type, data fields, relationships between fields, and business permissions before using it.

### 2.4. Risk Grows with Dependencies

Exploitability does not come only from classes written by the application itself. Libraries on the classpath/module path can also provide callbacks or gadgets. Adding a new dependency can change which classes are able to participate in deserialization.

Therefore, controlling dependency versions, removing unnecessary libraries, and avoiding broad allowlists covering entire large packages are important measures.

## 3. Why Can Deserialization Execute Class Code?

Java serialization does not merely read a sequence of bytes into simple data fields. It reconstructs an object graph according to each class's rules.

### 3.1. Serialization Callbacks

Classes can participate in this process using special methods:

| Mechanism | Role |
|---|---|
| `private void readObject(ObjectInputStream in)` | The class reads and restores its own state; it can validate data and invoke other logic |
| `private void readObjectNoData()` | Handles the case where a class in the hierarchy has no corresponding data in the stream |
| `protected Object readResolve()` | Replaces the newly restored object with another object |
| `void readExternal(ObjectInput in)` | An `Externalizable` class reads its own data |
| `ObjectInputValidation` | Registers validation after the object graph is read, before returning the final result to the caller |

A callback can invoke additional methods, process collections, look up resources, or interact with dependencies. Thus, input data can influence the execution flow through the deserialized classes.

Example of a technically valid callback that must be reviewed carefully:

```java
private void readObject(ObjectInputStream in)
        throws IOException, ClassNotFoundException {
    in.defaultReadObject();

    if (quantity < 0) {
        throw new InvalidObjectException("quantity must be non-negative");
    }
}
```

This code illustrates validating state after reading. It is not a class filter and is not sufficient to protect the application if the object graph contains other dangerous classes.

### 3.2. Regular Constructors Are Not a Universal Safeguard

For classes implementing `Serializable` under the default mechanism, the constructor of that serializable class is not called the way it is when creating an object with `new`. Java restores state according to the serialization protocol; the first non-serializable superclass constructor in the hierarchy is invoked per serialization rules.

Therefore, do not place safety checks solely in a regular constructor and assume those checks always run during deserialization.

`Externalizable` has different rules: the class needs a public no-arg constructor for the runtime to instantiate it, after which `readExternal` is called. Records also have their own serialization rules; a record's canonical constructor is invoked when deserializing a record.

Regardless of the class kind used, the application still needs to validate the object after receiving it and before using it for sensitive operations.

### 3.3. Validating Data After Deserialization

Validate at the application boundary:

```java
static UserProfile validate(Object value) throws InvalidObjectException {
    if (value == null || value.getClass() != UserProfile.class) {
        throw new InvalidObjectException("Unexpected object type");
    }

    UserProfile profile = (UserProfile) value;
    if (profile.age() < 0 || profile.age() > 130) {
        throw new InvalidObjectException("Invalid age");
    }
    if (profile.username() == null || profile.username().isBlank()) {
        throw new InvalidObjectException("Username is required");
    }
    return profile;
}
```

This is only an example of checking type and business rules. In a real system, also check string lengths, element count limits, relationships between objects, user state, and caller permissions.

## 4. ObjectInputFilter: Filtering Classes and Limiting the Object Graph

Java 9 added object deserialization filtering via JEP 290. In Java 17, the primary API is `java.io.ObjectInputFilter`.

The filter is called while `ObjectInputStream` reads the object graph so the application can decide:

- Which classes are allowed to appear.
- How deep the object graph can be.
- How many references are processed.
- How many bytes the stream has consumed.
- What the maximum length of deserialized arrays can be.

This is an important defense layer when a legacy system cannot yet drop Java native serialization. Filters should be designed around an **allowlist of actually needed types**, combined with resource limits.

### 4.1. ObjectInputFilter.FilterInfo

A filter receives a `FilterInfo` object containing information about the reading process:

| Property | Meaning |
|---|---|
| `serialClass()` | The class currently being checked; may be `null` in some calls, e.g., when there is no new class to check |
| `arrayLength()` | The length of the array being checked; negative if not applicable |
| `depth()` | The current depth of the object graph |
| `references()` | The number of references processed so far in the stream |
| `streamBytes()` | The number of bytes consumed from the stream at the time of the check |

The filter returns one of three statuses:

| Status | Meaning |
|---|---|
| `ALLOWED` | This filter permits the object/condition under consideration |
| `REJECTED` | Reject; deserialization is aborted with an error |
| `UNDECIDED` | The filter does not make a decision; other filters or the default mechanism may continue |

When using a single filter for a stream, an easily controlled approach is to **allow classes in the allowlist and reject other classes**. Do not return `UNDECIDED` for all unknown classes and assume you have created an allowlist.

### 4.2. Example Filter by Class and Resource Limits

Suppose the application only accepts a simple DTO type:

```java
import java.io.Serial;
import java.io.Serializable;

public final class UserSnapshot implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;

    private final String username;
    private final int score;

    public UserSnapshot(String username, int score) {
        this.username = username;
        this.score = score;
    }

    public String username() {
        return username;
    }

    public int score() {
        return score;
    }
}
```

Reading method:

```java
import java.io.IOException;
import java.io.InvalidObjectException;
import java.io.ObjectInputFilter;
import java.io.ObjectInputStream;
import java.nio.file.Files;
import java.nio.file.Path;

static UserSnapshot readSnapshot(Path path)
        throws IOException, ClassNotFoundException {

    try (ObjectInputStream input =
                 new ObjectInputStream(Files.newInputStream(path))) {

        ObjectInputFilter filter = info -> {
            if (info.depth() > 10
                    || info.references() > 100
                    || info.streamBytes() > 1_000_000
                    || info.arrayLength() > 10_000) {
                return ObjectInputFilter.Status.REJECTED;
            }

            Class<?> type = info.serialClass();
            if (type == null) {
                return ObjectInputFilter.Status.UNDECIDED;
            }

            if (type == UserSnapshot.class || type == String.class) {
                return ObjectInputFilter.Status.ALLOWED;
            }

            return ObjectInputFilter.Status.REJECTED;
        };

        // Install the filter before reading any object.
        input.setObjectInputFilter(filter);

        Object value = input.readObject();
        if (value == null || value.getClass() != UserSnapshot.class) {
            throw new InvalidObjectException("Unexpected root object type");
        }

        UserSnapshot snapshot = (UserSnapshot) value;
        if (snapshot.username() == null || snapshot.username().isBlank()
                || snapshot.score() < 0) {
            throw new InvalidObjectException("Invalid user snapshot");
        }
        return snapshot;
    }
}
```

Key points to understand:

1. The filter is installed after creating `ObjectInputStream` but **before calling `readObject()`**.
2. Graph limits are checked before deciding on the class.
3. Only the expected DTO class is allowed; other classes are rejected.
4. `serialClass()` can be `null`, so never call methods on it without checking first.
5. After reading, the application still validates the root object and business data.

This example illustrates a very small allowlist. When an actual DTO contains collections, date/time types, or other serializable types, you must add the exact required classes after understanding the object graph. Do not widen it to all of `java.base` or entire library packages just to make errors disappear.

### 4.3. Filters Do Not Replace Data Validation

A filter can reject classes or graphs exceeding limits. It is not a validator for all field values:

- It does not check whether a username is valid under business rules.
- It does not check whether the sender has permission to modify a score.
- It does not verify the signature or origin of the byte stream.
- It does not prove that callbacks in an allowlisted class are harmless.

Therefore, filters and validation must be used together. If an object graph contains an allowed class that has a dangerous callback, an overly broad allowlist can still let unwanted behavior slip through.

## 5. Configuring Filters with Patterns

Java 17 supports a pattern syntax to describe limits and allowed/rejected classes without writing lambdas manually.

### 5.1. Graph Limits

The main limit properties:

| Pattern | Limit |
|---|---|
| `maxdepth=n` | Maximum graph depth |
| `maxrefs=n` | Maximum number of references |
| `maxbytes=n` | Maximum number of bytes read |
| `maxarray=n` | Maximum array length |

Example:

```text
maxdepth=12;maxrefs=5000;maxbytes=1048576;maxarray=10000
```

The values above are only examples. Proper limits must be measured from the application's valid object graphs, plus an appropriate safety margin. Setting them too low can cause valid data to be rejected; setting them too high reduces protection effectiveness.

### 5.2. Class Allowlist and Denylist Patterns

Class patterns support exact class names and package wildcards:

- `com.acme.dto.UserSnapshot`: a specific class.
- `com.acme.dto.*`: classes directly in that package.
- `com.acme.dto.**`: classes in that package and its subpackages.
- `!com.acme.internal.**`: rejects classes belonging to this internal package.
- `!*`: rejects classes not allowed by any preceding pattern.

You can specify the module name before the class name, separated by `/`, when you want to restrict by module.

Example pattern:

```text
maxdepth=12;maxrefs=5000;maxbytes=1048576;maxarray=10000;com.acme.dto.**;java.base/java.util.ArrayList;java.base/java.util.HashMap;!*
```

This is an allowlist example: it allows DTOs in the specified package and two specific collection classes, rejecting all remaining classes. Replace them with the types actually needed in your application; collections may contain additional element types or supporting types.

### 5.3. Using a Filter Pattern at JVM Startup

You can set the `jdk.serialFilter` system property when running the application:

```bash
java -Djdk.serialFilter="maxdepth=12;maxrefs=5000;maxbytes=1048576;maxarray=10000;com.acme.dto.**;java.base/java.util.ArrayList;!*" -jar app.jar
```

This filter has JVM-wide scope according to the serialization filter configuration. It is suitable when an organization wants to establish a centralized default policy for deserialization flows.

For deployment configurations, set the property in runtime/launcher configuration managed by the organization. Do not let a user request determine security system properties.

### 5.4. Setting a Global Filter via API

You can set a JVM-wide filter using `ObjectInputFilter.Config.setSerialFilter`:

```java
ObjectInputFilter.Config.setSerialFilter(globalFilter);
```

The global filter is process-wide and can only be set once per the API's rules. Set it early during application startup, before creating deserialization streams that require that policy. If a filter already exists from runtime configuration or other code, design a policy merge rather than trying to overwrite it arbitrarily.

### 5.5. Setting a Per-Stream Filter

When each reading flow has different needs, use:

```java
ObjectInputStream input = new ObjectInputStream(source);
input.setObjectInputFilter(streamFilter);
Object value = input.readObject();
```

The per-stream filter must be set before reading the first object. This API is useful for applying an allowlist per protocol or data type of that stream.

Do not wait until after reading the object to set the filter: by then, object graph reconstruction has already occurred.

### 5.6. Pattern Order and Allowlist Principles

Filter patterns are separated by semicolons. Graph limits are evaluated to reject graphs exceeding thresholds; for class patterns, the order of patterns matters because the first matching pattern determines the outcome for that class.

Example:

```text
maxdepth=10;maxrefs=1000;com.acme.dto.**;!com.acme.dto.internal.**;!*
```

To avoid accidentally broadening permissions:

- Prefer exact class names if the number of allowed classes is small.
- Only use package wildcards when every class within that scope genuinely needs to be deserialized.
- Place specific rejection rules before a broader allow rule that could match them.
- End with `!*` if you want to reject any class not in the allowlist.
- Test with valid object graphs and graphs intentionally containing classes outside the allowlist.

A pattern should not be considered a safe policy if it merely lists a few broad packages without knowing which classes inside them have serialization callbacks.

## 6. Filter Factory in Java 17 (JEP 415)

A large application may have multiple components deserializing data with different requirements: one stream reading internal DTOs, one stream reading messages from a partner system, and one stream supporting legacy data compatibility. A single global filter sometimes cannot express enough context.

Java 17 adds **serialization filter factories** under JEP 415. The filter factory decides which filter is applied when an `ObjectInputStream` is created or when a stream filter is requested to be set.

### 6.1. Role of the Factory

The factory receives the current filter and the requested filter, then returns the final filter to be used. This enables the application to:

- Combine the JVM-wide policy with a stream-specific policy.
- Choose a filter based on application context.
- Prevent a component from lowering protection by replacing an existing filter.
- Create different policies for data streams with different protocols.

The factory is a mechanism to **select and combine filters**, not a parser replacement for `ObjectInputFilter`.

### 6.2. Installing a Filter Factory

The API is in `ObjectInputFilter.Config`:

```java
ObjectInputFilter.Config.setSerialFilterFactory(
        (currentFilter, requestedFilter) -> {
            // The application decides the final filter.
            // Simple example: if the stream requests a specific filter,
            // combine it with the current policy per application rules.
            return requestedFilter != null
                    ? requestedFilter
                    : currentFilter;
        });
```

The snippet above only illustrates the signature and installation point; **it is not a complete safe factory**. In a real application, do not return a new filter in a way that discards the existing global filter. Filters must be combined so that if one filter rejects, the final result is still rejected, and mandatory resource limits always remain enforced.

The factory can be configured via the `jdk.serialFilterFactory` system property or set via the API. It must be configured during startup, before components create `ObjectInputStream` instances.

### 6.3. Separating Filters by Context

A practical design can categorize streams by function:

| Context | Example Policy |
|---|---|
| Reading internal DTOs | Specific DTO class allowlist, tight graph limits |
| Reading partner data | Allowlist per specific schema/protocol, low byte and array limits |
| Reading legacy compatibility archives | Run only in an isolated process, allowlist of known data versions |

Do not choose a filter based solely on untrusted self-declared data inside the stream. Context must be determined from trusted application execution flows, such as configured endpoints or adapters.

## 7. What Can ObjectInputFilter Protect Against and What Can It Not?

A filter is an important defense layer, but it has a clear scope.

### 7.1. What Can a Filter Do?

- Reject classes not in the allowlist.
- Reject classes/arrays conditionally.
- Reject object graphs exceeding depth, reference count, byte count, or array length limits.
- Apply a global policy or per-stream policies.
- Allow the system to monitor and control which object types are being deserialized.

### 7.2. What Does a Filter Not Do?

- It does not authenticate the sender's identity.
- It does not verify signatures, MACs, or byte stream integrity.
- It does not check all field values against business rules.
- It does not guarantee that allowlisted classes lack dangerous callbacks.
- It does not prevent all forms of CPU/memory consumption inside callbacks of allowed classes.
- It does not replace size limits at the network, HTTP, file upload, or message broker layers.
- It does not automatically protect data passing through JSON, XML, YAML, or other formats; those parsers need their own policies.

For example, if you allow a DTO class whose `readObject` performs an expensive query, the filter that allowed that class cannot tell whether the query is reasonable. Keep callbacks simple and avoid performing sensitive side effects during object restoration.

### 7.3. A Filter Is Not a Sandbox

Do not rely on filters to run arbitrary user object streams in the same process as sensitive application logic. If you must process untrusted legacy data, consider isolating the process with minimal OS permissions, resource limits, timeouts, and communication over a narrow data schema.

Legacy permission-management mechanisms are not a substitute for avoiding deserialization of untrusted data. Use process boundaries and OS privileges suited to the current deployment environment.

## 8. Safe Workflow When Forced to Keep Java Serialization

If a legacy protocol must accept Java object streams, build a clear processing boundary.

### 8.1. Limit Data Before Creating ObjectInputStream

Object filters have a `maxbytes` limit, but the data-receiving layer also needs size limits:

- HTTP endpoints set request body limits.
- Uploads enforce file size limits before saving or processing.
- Message brokers enforce message size limits and per-producer quotas.
- Socket protocols limit frame length before allocating buffers.

Do not read unbounded data from the network into a byte array and only then hope the filter rejects it in time.

### 8.2. Verify Source and Integrity When the Protocol Requires It

If the byte stream is stored or transmitted over an environment where it can be modified, digital signatures or MACs can be used per the protocol to authenticate origin/integrity. Whenever possible, verify on the size-bounded byte frame **before** creating `ObjectInputStream` and deserializing.

Signature/MAC verification does not replace a filter. An authenticated source can still send malformed data, oversized data, or data from an incompatible version; signing keys can also be leaked or a trusted source compromised.

### 8.3. Use a Small Allowlist and Graph Limits

Only allow:

- Specific DTOs required by the protocol.
- Specific collections if the format actually contains collections.
- Reviewed supporting types.

Set thresholds for:

- Graph depth.
- Reference count.
- Bytes read.
- Array length.

Thresholds must be determined from real valid data, not picked as an arbitrary large number.

### 8.4. Validate Objects After Reading

Even when the filter allows the classes, check:

- Exact root object type.
- Required values are non-null/non-empty.
- String and collection bounds.
- Numeric values fall within valid ranges.
- Relationships between fields and related objects.
- Sender's authorization for the action requested by the data.

Do not perform sensitive operations (database writes, fund transfers, command execution, notifications) merely because deserialization succeeded.

### 8.5. Keep Serialization Callbacks Simple

In serializable classes controlled by the application:

- Avoid network, file, database access, or external service calls in `readObject`/`readExternal`.
- Do not execute commands or spawn threads in object restoration callbacks.
- Only restore necessary data and check local invariants.
- Use an explicit validation step after the graph has been constructed.
- Minimize use of `Externalizable` because the class controls its own protocol and requires careful review.

### 8.6. Reduce the Gadget Surface

- Remove unnecessary dependencies.
- Update libraries to supported security-patched versions.
- Avoid having old unused libraries on the classpath.
- Do not allow classes via overly broad wildcards.
- Document and test allowlist changes when adding dependencies.

## 9. Should Java Native Serialization Be Replaced with Another Format?

For data arriving from outside or requiring long-term storage, it is usually better to use a data format with an explicit schema or DTO rather than deserializing arbitrary object graphs.

Common options:

| Format | Characteristics | What to Control |
|---|---|---|
| JSON with DTO/schema | Readable, widely supported across languages | Do not enable arbitrary polymorphic typing; limit depth/size; validate schema and fields |
| Protocol Buffers | Explicit schema, binary encoding, multi-language support | Control schema/versioning, message size, and business validation |
| Avro | Schema-driven, suited for data pipelines | Manage schema evolution and parser resource limits |
| CBOR | JSON-style data representation in binary form | Use safely configured parser, limit depth/size and data types |
| MessagePack | Compact binary encoding for data structures | Do not implicitly trust data; limit depth, element counts, and accepted types |

Switching to JSON does not automatically solve everything. A JSON library that allows specifying class names and instantiating arbitrary types (polymorphic deserialization/auto type) can still create a similar gadget surface. Map to concrete DTOs, disable automatic class instantiation from input data unless needed, and validate against a schema.

### 9.1. Example: DTO Thinking Instead of Object Graphs

Instead of accepting an arbitrary object graph:

```java
Object value = input.readObject();
```

The data protocol can define a narrow structure:

```json
{
  "username": "linh",
  "score": 42
}
```

After parsing, map into a known DTO:

```java
record UserSnapshot(String username, int score) { }
```

The application only accepts the defined fields and validates values before use. The JSON example only illustrates the data schema; the actual parser still needs configured limits and validation.

### 9.2. When to Keep Native Serialization?

There may still be internal systems needing compatibility with data already written with Java serialization. In that case:

- Clearly identify the data producer and trust boundary.
- Read only from protected storage with access control.
- Have a global or per-stream filter with an allowlist.
- Enforce resource limits and business validation after reading.
- Have a gradual replacement plan if the data needs external exchange or long-term storage.

Do not expose a public endpoint accepting arbitrary object streams just because the client is also written in Java.

## 10. Technical Limits to Remember When Using Filters

### 10.1. Filters Do Not Inspect Every Primitive Value and String

Object filters primarily inspect classes/arrays and object graph information at runtime filter invocation points. They are not a byte-by-byte or field-by-field validator. Primitive values and `String` instances are not filtered like ordinary object classes.

Therefore:

- Do not rely on a class allowlist to limit the length of a string.
- Limit total stream bytes with `maxbytes` and enforce business string length limits after reading.
- For data with many strings, account for both string count and total size.
- Do not treat `serialClass() == null` as proof that data is safe; it is simply a situation where the filter has no new class to decide on.

### 10.2. Filters Do Not Verify Business Structure of the Object Graph

A graph can contain only allowlisted classes and still be logically invalid. For instance, an allowed `ArrayList` might contain more elements than business rules permit, or a DTO might have an invalid status field. Graph limits and business validation solve two different problems.

### 10.3. Filters Are Not Execution Time Limits

`maxdepth`, `maxrefs`, `maxbytes`, and `maxarray` help control structural metrics. They do not guarantee that an allowed class's callback will finish quickly. If a callback performs expensive work, redesign the class, enforce timeouts at the processing layer, and isolate the process when necessary.

### 10.4. serialVersionUID Is Not a Security Mechanism

`serialVersionUID` supports class version compatibility checks in Java serialization. It does not authenticate the sender, sign data, or prevent gadget chains. Do not treat declaring a fixed UID as a deserialization security measure.

### 10.5. transient Is Not a Safety Barrier for the Whole Object

`transient` prevents a field from being written by the default serialization mechanism. It does not make a class safe to deserialize, does not block callbacks, and does not replace filters. Other fields or custom logic can still cause dangerous behavior.

## 11. Common Mistakes and How to Handle Them

| Misconception or Mistake | Reality | How to Handle |
|---|---|---|
| Data has a .ser extension so it must be trustworthy | File extension does not authenticate the source | Identify the source, verify integrity, and use a filter |
| Only checking the root object after readObject is enough | Callbacks on nested objects may have already executed | Filter the graph before constructing objects, then validate the root object |
| A class allowlist alone is enough | Graphs can still be too deep, too large, or have too many references | Combine class allowlists with graph limits |
| Allowing entire packages of popular libraries | Packages may contain unnecessary classes or gadgets | Allow specific classes and expand in a controlled manner |
| Returning UNDECIDED for unknown classes | The filter does not express a rejection policy | Reject classes not in the allowlist |
| Setting the filter after readObject | The object graph has already been constructed before the filter applies | Set the filter before the first object read |
| Filter will check the contents of every String | Strings and primitives are not filtered like ordinary object classes | Limit stream bytes and validate length/values after reading |
| readObject callback always runs the class constructor | Regular constructors of Serializable classes do not run as with `new` | Do not put all validation in constructors; check in appropriate callbacks and after deserialization |
| serialVersionUID makes a stream secure | UID is for version compatibility | Use filters, source authentication, and validation |
| transient eliminates deserialization risks | Callbacks and other fields can still be dangerous | Evaluate both classes and the object graph |
| Using JSON is automatically safe | Uncontrolled polymorphic typing or auto type is still dangerous | Bind to concrete DTOs/schemas, limit the parser, and validate |
| Filter allowing a class means the class callback is harmless | Allowlists only control classes, not callback safety | Review callbacks and dependencies; avoid side effects |

## 12. Example Setting a Filter via Pattern in Code

If you want to create a filter from a pattern string rather than writing a lambda:

```java
import java.io.ObjectInputFilter;

ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
        "maxdepth=10;maxrefs=1000;maxbytes=1048576;"
        + "maxarray=10000;com.acme.dto.UserSnapshot;!*");
```

Then attach it to the stream:

```java
try (ObjectInputStream input = new ObjectInputStream(source)) {
    input.setObjectInputFilter(filter);
    Object value = input.readObject();
    // Continue validating the type and contents of value.
}
```

This pattern allows only one specific DTO class and rejects other classes while enforcing graph limits. If the DTO contains other object types that need to be deserialized, each appropriate class must be added to the allowlist.

One point to remember: a pattern filter returns `UNDECIDED` if no pattern decides the class. Therefore, a trailing `!*` rule is useful to reject unlisted classes.

## 13. Design Checklist for Data-Receiving Flows

Before deploying an endpoint or worker that reads Java object streams, answer:

1. Who is the data source? Can it be controlled or modified by external parties?
2. Can Java native serialization be replaced with a DTO/schema format?
3. If deserialization is unavoidable, which classes actually need to exist in the graph?
4. Does the allowlist contain only necessary classes, and have their callbacks been reviewed?
5. What are the limits for bytes, depth, references, and array length?
6. At what level—global, stream, or factory—is the filter installed before the first read?
7. Is integrity/origin verified before deserialization when the protocol requires it?
8. Are the root type and business data validated after deserialization?
9. Are resource limits enforced at the network, file, message, and process layers?
10. When adding dependencies or upgrading versions, who reviews the allowlist and test results?

These are design decisions that should be documented in configuration and protocol specifications; each `readObject()` call site should not pick a different policy ad hoc.

### Exercise 2 — Design an Allowlist

A protocol only needs to read `com.acme.dto.UserSnapshot` containing a string field and an integer. Write a filter:

- Maximum depth of 5.
- Maximum 100 references.
- Maximum 64 KiB stream bytes.
- Only allow that DTO and reject all other classes.

**Hint:**

```java
ObjectInputFilter filter = info -> {
    if (info.depth() > 5
            || info.references() > 100
            || info.streamBytes() > 64 * 1024) {
        return ObjectInputFilter.Status.REJECTED;
    }

    Class<?> type = info.serialClass();
    if (type == null) {
        return ObjectInputFilter.Status.UNDECIDED;
    }
    return type == UserSnapshot.class
            ? ObjectInputFilter.Status.ALLOWED
            : ObjectInputFilter.Status.REJECTED;
};
```

If the actual object graph needs additional classes, determine why and add the specific classes. Strings are length-validated separately after reading.

**Key takeaway:** Reading an object stream reconstructs an object graph and can trigger class callbacks. Untrusted data can lead to gadget chains, DoS, or invalid business state. By default, avoid Java native deserialization from untrusted sources. If it must be retained, use `ObjectInputFilter` with a narrow allowlist and graph limits, install the filter before reading, verify origin/integrity when needed, and validate business data after deserialization. JEP 415 in Java 17 adds filter factories to apply context-specific policies; it does not make arbitrary deserialization safe.
