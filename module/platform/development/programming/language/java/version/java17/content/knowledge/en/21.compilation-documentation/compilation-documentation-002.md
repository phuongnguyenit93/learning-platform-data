# Class Files, Bytecode, and Inspection with javap

When compiling Java code, the `javac` compiler translates source code into **class files** containing bytecode for the Java Virtual Machine (JVM). A class file stores the class structure, methods, constant pool, bytecode, and metadata required by the JVM to link, verify, and execute the program.

In JDK 17, the **`javap`** command-line tool reads class file structures and disassembles bytecode so you can observe how the compiler represents source code. It is useful when learning how the compiler works, investigating class file version compatibility errors, checking method descriptors, inspecting annotations/attributes, or understanding why a snippet of Java produces certain instructions.

This lesson presents class files and bytecode from a Java 17 perspective, controlled compilation with `javac --release`, common `javap` options, how to read its output, and a practical inspection workflow. Bytecode is an intermediate format for the JVM; it is neither Java source code nor native machine code for a specific CPU.

## 1. From source code to class file

Basic process:

~~~text
Hello.java
    |
    | javac
    v
Hello.class
    |
    | JVM class loader
    v
Load -> Link -> Initialize
    |
    v
Bytecode execution
    |
    +--> Interpreter
    |
    +--> JIT compilation -> Native machine code
~~~

Example source:

~~~java
package demo;

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java 17!");
    }
}
~~~

Compile:

~~~bash
javac --release 17 -d out src/demo/Hello.java
~~~

The result is `out/demo/Hello.class`. Run:

~~~bash
java -cp out demo.Hello
~~~

Output:

~~~text
Hello, Java 17!
~~~

`javac` creates the class file; the JVM loads the class file and executes the bytecode. Depending on the JVM and how hot the code is, some methods may be compiled into native machine code by the JIT compiler at runtime.

### 1.1. Class files are platform-independent

A Java class file is not compiled specifically for x86-64, ARM64, or a particular operating system. It contains bytecode according to the JVM Specification. JVMs that support the class file version and features used can run that bytecode on their platform.

This independence comes with conditions:

- The runtime must support the corresponding class file version.
- The APIs called by the program must exist in the runtime.
- Dependent libraries must be compatible.
- If the code uses native libraries/JNI, the native portion remains platform-dependent.
- Some preview features require the runtime to enable preview accordingly.

Therefore, class files are more portable than native executables, though they do not guarantee every Java application behaves identically across all runtimes.

## 2. What does a class file contain?

A class file has a binary structure defined by the JVM Specification. Using `javap -v`, you can inspect many components:

1. Magic number.
2. Minor version and major version.
3. Constant pool.
4. Access flags.
5. Current class and superclass information.
6. Interfaces.
7. Fields.
8. Methods.
9. Attributes.

You can visualize the general structure:

~~~text
ClassFile
|
+-- magic
+-- minor_version
+-- major_version
+-- constant_pool
+-- access_flags
+-- this_class
+-- super_class
+-- interfaces
+-- fields
+-- methods
+-- attributes
~~~

### 2.1. Magic number

The first four bytes of a valid class file are:

~~~text
CA FE BA BE
~~~

This is the magic number `0xCAFEBABE`, used to identify the class file format. If a file is corrupted, is not a class file, or is read in the wrong format, tools can report an error immediately when checking the header.

### 2.2. Major version and minor version

A class file stores its format version using two fields:

- `major_version`: the major version of the class file.
- `minor_version`: the minor version, which includes a convention reserved for preview features.

A standard class file generated by Java 17 has:

| Field | Value |
| --- | ---: |
| `major_version` | 61 |
| `minor_version` | 0 |

Some common major versions:

| Java release | Class file major version |
| --- | ---: |
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

If a class file has a higher major version than the runtime supports, the JVM can throw `UnsupportedClassVersionError`.

For example, a class file with major version 61 requires a runtime supporting the Java 17 format or newer. Running a Java 17 class file on Java 11 cannot be solved simply by adding a JAR; you must recompile for the appropriate target version or upgrade the runtime.

### 2.3. Constant pool

The constant pool is a table holding constants and references used by the class file. Entries can represent:

- Integer, float, long, and double literals.
- String constants.
- Class and interface names.
- Field and method names.
- Field/method references.
- Method handles and method types.
- Dynamic constants and invokedynamic metadata.

Example source:

~~~java
public class Greeting {
    public static final String MESSAGE = "Hello";

    public static void print(String name) {
        System.out.println(MESSAGE + ", " + name);
    }
}
~~~

The constant pool may contain the strings `"Hello"`, `", "`, the class name `java/lang/System`, field name `out`, method name `println`, and related descriptors.

In `javap -v` output, entries are numbered `#1`, `#2`, ... These numbers are indices into the constant pool; bytecode can reference them using instructions such as `ldc`, `getstatic`, `invokevirtual`, or `invokedynamic`.

The constant pool is not just a simple list of literals. It also describes symbolic links among classes, fields, methods, data types, and bootstrap methods.

### 2.4. Fields and methods

The fields section describes the class's fields, including access flags, names, descriptors, and attributes if present.

The methods section describes constructors, regular methods, synthetic methods, or compiler-generated methods. Each method can have properties such as:

- Access flags (`public`, `private`, `static`, `final`, ...).
- Method descriptor.
- `Code` attribute if the method has bytecode.
- `Exceptions` attribute.
- `Signature` for generic signatures when needed.
- `RuntimeVisibleAnnotations` or other annotation attributes.
- `MethodParameters` if the compiler recorded parameter names/info.

An abstract or native method does not have a `Code` attribute containing bytecode like a regular method.

## 3. What is bytecode?

Bytecode is the instruction set of the JVM. The JVM is a stack-based virtual machine: many instructions pop operands from the **operand stack**, perform an operation, and push the result back onto the stack.

Example adding two integers:

~~~java
public static int add(int left, int right) {
    return left + right;
}
~~~

Illustrative bytecode:

~~~text
0: iload_0
1: iload_1
2: iadd
3: ireturn
~~~

Explanation:

1. `iload_0`: pushes the int value in local variable slot 0 onto the operand stack.
2. `iload_1`: pushes the int value in slot 1 onto the stack.
3. `iadd`: pops two ints from the stack, adds them, and pushes the result.
4. `ireturn`: returns the int.

For a static method, the two parameters `left` and `right` typically occupy slots 0 and 1. For an instance method, slot 0 holds `this`; parameters start at slot 1. `long` and `double` occupy two local variable slots in the JVM model.

### 3.1. Local variables and the operand stack

Each method execution has a frame. A frame contains:

- Local variable array.
- Operand stack.
- Reference to the runtime constant pool of the current class.

Some instructions operate on local variables, some on the operand stack, and others access fields or invoke methods.

~~~text
Method frame
+---------------------------+
| Local variables           |
|  slot 0: left             |
|  slot 1: right            |
+---------------------------+
| Operand stack             |
|  [left]                   |
|  [left, right]            |
|  [sum]                    |
+---------------------------+
~~~

This is a model for reading bytecode; a JVM implementation may optimize execution underneath, but it must preserve bytecode semantics.

### 3.2. Common instruction groups

| Group | Example instructions | Meaning |
| --- | --- | --- |
| Load/store | `iload`, `aload`, `istore`, `astore` | Read/write local variable |
| Constant | `iconst`, `bipush`, `sipush`, `ldc` | Push constant onto stack |
| Arithmetic | `iadd`, `isub`, `imul`, `idiv` | Arithmetic operations |
| Compare/branch | `if_icmpge`, `ifeq`, `goto` | Comparison and branching |
| Object | `new`, `checkcast`, `instanceof` | Create/check object |
| Field | `getfield`, `putfield`, `getstatic`, `putstatic` | Read/write field |
| Method call | `invokevirtual`, `invokestatic`, `invokespecial`, `invokeinterface` | Call method |
| Dynamic call | `invokedynamic` | Dynamic call linkage via bootstrap method |
| Array | `newarray`, `anewarray`, `iaload`, `aastore` | Create and access array |
| Return | `ireturn`, `areturn`, `return` | Return result or finish void method |
| Exception | `athrow` | Throw a throwable |

Instruction names often have a prefix indicating the data type. For example `iadd` for int, `ladd` for long, `fadd` for float, and `dadd` for double.

You do not need to memorize every opcode to use `javap`. Learn to recognize the major instructions and trace the operand stack, local variables, and constant pool references.

## 4. Descriptors and data types in class files

Class files use descriptors to represent field types and method signatures. Descriptors do not look like generic syntax in source code; they are JVM-level representations.

### 4.1. Descriptors for primitive and reference types

| Java type | Descriptor |
| --- | --- |
| `boolean` | `Z` |
| `byte` | `B` |
| `char` | `C` |
| `short` | `S` |
| `int` | `I` |
| `long` | `J` |
| `float` | `F` |
| `double` | `D` |
| `void` (return) | `V` |
| `String` | `Ljava/lang/String;` |
| `int[]` | `[I` |
| `String[]` | `[Ljava/lang/String;` |

A reference type has the form `L` + internal name + `;`. Internal names use `/` to separate packages.

### 4.2. Method descriptors

A method descriptor has the form:

~~~text
(parameter-descriptors)return-descriptor
~~~

Example:

~~~java
public boolean isValid(String name, int age) {
    return name != null && age >= 0;
}
~~~

Descriptor:

~~~text
(Ljava/lang/String;I)Z
~~~

It represents two parameters (`String`, `int`) and a `boolean` return value.

Another method:

~~~java
public static void log(long id, String[] tags) {
}
~~~

Descriptor:

~~~text
(J[Ljava/lang/String;)V
~~~

Method descriptors are useful when reading `javap -s`, low-level stack traces, reflection metadata, or method linkage errors.

### 4.3. Generic signatures and type erasure

Java generics undergo type erasure when represented in bytecode. For example:

~~~java
List<String> names;
~~~

The field's descriptor may simply be:

~~~text
Ljava/util/List;
~~~

A separate generic signature may store `List<String>` information in the `Signature` attribute. Thus descriptors and generic signatures serve two distinct purposes: the descriptor defines the JVM type used for linking; the signature preserves generic metadata for the compiler, reflection, and tooling.

## 5. Attributes in class files

Attributes attach metadata to a class, field, method, or code block. Commonly seen attributes include:

| Attribute | Content |
| --- | --- |
| `SourceFile` | Associated source file name |
| `LineNumberTable` | Mapping from bytecode offsets to source line numbers |
| `LocalVariableTable` | Names and types of local variables when debug metadata is recorded |
| `StackMapTable` | Stack map frame information for bytecode verification |
| `Exceptions` | Exceptions declared in `throws` |
| `Signature` | Generic signature |
| `RuntimeVisibleAnnotations` | Annotations retained at runtime |
| `BootstrapMethods` | Bootstrap methods for `invokedynamic` and dynamic constants |
| `NestHost`, `NestMembers` | Metadata for nest-based access |
| `Record` | Metadata for record classes |
| `PermittedSubclasses` | List of permitted subclasses of a sealed class |
| `Module` | Module descriptor in `module-info.class` |

Not every class file contains all attributes. Some metadata is only emitted if the source uses the corresponding construct or the compiler is instructed to record debug information.

### 5.1. Debug information

You can control debug information with `javac`:

~~~bash
javac --release 17 -g -d out src/demo/Hello.java
~~~

`-g` instructs the compiler to emit debug information. You can select specific components:

~~~bash
javac --release 17 -g:lines,source -d out src/demo/Hello.java
~~~

Or omit debug information:

~~~bash
javac --release 17 -g:none -d out src/demo/Hello.java
~~~

Debug metadata helps debuggers and observability tools map bytecode back to source code. It does not alter the program's business logic. Local variable names may be absent from the class file if the compiler did not write `LocalVariableTable`.

## 6. Compiling for the right version with javac --release

When releasing a library or application, determine the lowest Java version the artifact supports.

On JDK 17:

~~~bash
javac --release 17 -d out src/demo/Hello.java
~~~

`--release 17` simultaneously configures:

- The accepted Java language level.
- The generated class file version.
- The set of Java SE APIs permitted for the target release.

The last point is crucial. If you only use `-source 17 -target 17` on a newer JDK, the compiler can still see new APIs from the current JDK; the generated class file may call methods that do not exist on a Java 17 runtime. `--release` constrains the API surface to the target release as well.

### 6.1. Comparing options

| Option | Effect |
| --- | --- |
| `--release 17` | Source level, target class version, and Java 17 APIs |
| `-source 17` | Accepted syntax/language level |
| `-target 17` | Class file major version |
| `-g` | Emit debug information |
| `-parameters` | Record method parameter names for reflection |
| `-encoding UTF-8` | Specify source file encoding |

For projects targeting Java 17 compatibility, prefer `--release 17` instead of manually pairing `-source` and `-target`.

### 6.2. Preview features

Preview features are explicitly enabled at compile and run time. General syntax on JDK 17:

~~~bash
javac --release 17 --enable-preview -d out src/demo/PreviewDemo.java
java --enable-preview -cp out demo.PreviewDemo
~~~

Class files compiled with a release's preview features carry a special minor version (65535). The runtime must enable preview for that exact release to run the class file. Do not treat `--enable-preview` as a generic flag for running preview class files from a different release.

## 7. Using javap to read class files

`javap` is the disassembler included with the JDK. It reads class files and prints class structure, fields, methods, descriptors, bytecode, and attributes depending on the flags used.

Check version and help:

~~~bash
javap -version
javap --help
~~~

The tool normally resides in the same `bin` directory as `javac` and `java` in the JDK. If the terminal reports `javap` is not found, check that `JAVA_HOME` and `PATH` point to a JDK rather than a stripped-down JRE or runtime image.

### 7.1. Viewing class and method signatures

~~~bash
javap -classpath out demo.Hello
~~~

The default output focuses on class info and public/protected members. It does not show full bytecode.

To include private members as well:

~~~bash
javap -classpath out -p demo.Hello
~~~

`-p` (or `-private`) displays all class members that the tool can present, including private fields and methods.

### 7.2. Disassembling bytecode with -c

~~~bash
javap -classpath out -c demo.Hello
~~~

`-c` prints the bytecode of each method. This is the most important option when you want to inspect instructions generated by the compiler.

### 7.3. Viewing descriptors with -s

~~~bash
javap -classpath out -s demo.Hello
~~~

`-s` prints internal type signatures/descriptors. This is useful when matching overloads, method descriptors, or field types.

### 7.4. Viewing line numbers and local variables with -l

~~~bash
javap -classpath out -l demo.Hello
~~~

`-l` prints line number and local variable tables if that metadata is present in the class file. If the class was compiled without saving that information, those sections may be missing from the output.

### 7.5. Viewing full details with -v

~~~bash
javap -classpath out -v demo.Hello
~~~

`-v` (or `-verbose`) prints comprehensive details, typically including:

- Class file path.
- Minor/major version.
- Access flags.
- Constant pool.
- Field and method descriptors.
- Bytecode and stack/local limits.
- Exception tables.
- Class/method/code attributes.
- Annotations and bootstrap metadata if present.

This is the right choice when checking class file versions, the constant pool, annotations, or how a method is linked.

### 7.6. Common options

| Option | Meaning |
| --- | --- |
| `-c` | Show bytecode |
| `-p` / `-private` | Show all class members |
| `-s` | Show descriptors |
| `-l` | Show line number and local variable tables if present |
| `-v` / `-verbose` | Show detailed class file and attributes |
| `-constants` | Show `static final` constants |
| `-public` | Show only public members |
| `-protected` | Show public and protected members |
| `-package` | Show package, protected, and public members |
| `-classpath` / `-cp` | Specify where to find classes |
| `--module` | Specify module containing the class |
| `--multi-release` | Select entry version in a multi-release JAR |
| `-sysinfo` | Show system information about the class file |
| `-version` | Show `javap` version |

You can combine options, such as `-c -p -l`. When you need full details, `-v` already includes most of the information shown by individual options.

## 8. Step-by-step bytecode reading example

Create source:

~~~java
package demo;

public class Calculator {
    public static int add(int left, int right) {
        return left + right;
    }

    public static int absolute(int value) {
        if (value < 0) {
            return -value;
        }
        return value;
    }
}
~~~

Compile:

~~~bash
javac --release 17 -g -d out src/demo/Calculator.java
~~~

Inspect bytecode:

~~~bash
javap -classpath out -c -p demo.Calculator
~~~

The `add` section looks like:

~~~text
public static int add(int, int);
  Code:
     0: iload_0
     1: iload_1
     2: iadd
     3: ireturn
~~~

The `absolute` section may look like:

~~~text
public static int absolute(int);
  Code:
     0: iload_0
     1: ifge          7
     4: iload_0
     5: ineg
     6: ireturn
     7: iload_0
     8: ireturn
~~~

Bytecode offsets and instruction layout depend on the compiler, but the logical meaning corresponds to:

- `iload_0`: load the `value` parameter.
- `ifge`: if the value is greater than or equal to zero, jump to the branch returning the original value.
- `ineg`: negate the integer.
- `ireturn`: return the result.

When reading real output, use the offsets printed in the class file rather than assuming offsets always match the example.

## 9. Understanding javap -v output

With the command:

~~~bash
javap -classpath out -v demo.Calculator
~~~

Part of the output may look like this illustrative snippet:

~~~text
Classfile .../demo/Calculator.class
  Last modified ...; size ...
  SHA-256 checksum ...
  Compiled from "Calculator.java"
public class demo.Calculator
  minor version: 0
  major version: 61
  flags: (0x0021) ACC_PUBLIC, ACC_SUPER
Constant pool:
   #1 = Methodref          #2.#3
   #2 = Class              #4
   #3 = NameAndType        #5:#6
   ...
{
  public demo.Calculator();
    descriptor: ()V
    flags: (0x0001) ACC_PUBLIC
    Code:
      stack=1, locals=1, args_size=1
      ...

  public static int add(int, int);
    descriptor: (II)I
    flags: (0x0009) ACC_PUBLIC, ACC_STATIC
    Code:
      stack=2, locals=2, args_size=2
      ...
}
~~~

This is condensed output to explain the fields; actual constant pool indices and offsets depend on the compiled class.

Notable items:

- `major version: 61`: class file targeting Java 17.
- `flags`: JVM-level modifiers.
- `descriptor: (II)I`: two int parameters, returning int.
- `stack=2`: maximum operand stack depth for the method in this example.
- `locals=2`: two local variable slots used.
- `args_size=2`: two parameters of the static method.

For instance methods, `args_size` also counts the slot reserved for `this`. `long` and `double` occupy two local variable slots in the JVM model.

## 10. Method invocation and field access instructions

When viewing bytecode, method invocation instructions indicate how the compiler represents dispatch.

| Instruction | General meaning |
| --- | --- |
| `invokestatic` | Call a static method |
| `invokevirtual` | Call an instance method with virtual dispatch |
| `invokespecial` | Call a constructor, private method, or certain special calls such as superclass methods |
| `invokeinterface` | Call a method through an interface |
| `invokedynamic` | Call via dynamic linkage using a bootstrap method |

Field access:

- `getstatic`: read a static field.
- `putstatic`: write a static field.
- `getfield`: read an instance field.
- `putfield`: write an instance field.

Example:

~~~java
public class Counter {
    private int value;

    public int increment() {
        value++;
        return value;
    }
}
~~~

The bytecode may use `aload_0` to load `this`, `dup` to duplicate the reference on the operand stack, `getfield` to read the field, `iconst_1` and `iadd` to add, and `putfield` to write it back. `javap -c -p` lets you inspect the exact sequence of instructions.

## 11. Lambdas, string concatenation, and invokedynamic

Some modern Java constructs produce bytecode using `invokedynamic`.

Lambda example:

~~~java
Runnable task = () -> System.out.println("run");
~~~

The compiler may emit an `invokedynamic` instruction along with bootstrap metadata referencing `LambdaMetafactory`. The JVM links the dynamic call to produce the lambda behavior at runtime.

String concatenation:

~~~java
String message = "Hello, " + name;
~~~

With modern Java compilers, string concatenation may be represented using `invokedynamic` and a `StringConcatFactory` bootstrap method. How bytecode is emitted depends on the compiler and version; do not assume every string concatenation always produces the exact same instruction sequence.

To inspect:

~~~bash
javap -classpath out -c -v demo.LambdaDemo
~~~

Look for `InvokeDynamic`, `BootstrapMethods`, `LambdaMetafactory`, or `StringConcatFactory` in the output. This helps you understand dynamic linkage at the bytecode level without reading internal JVM implementation code.

## 12. Inspecting classes inside JARs and JDK modules

### 12.1. Reading classes in a JAR

If the class is inside a JAR, pass the JAR on the classpath:

~~~bash
javap -classpath app.jar -c -p com.example.App
~~~

With external dependencies:

~~~bash
javap -classpath "app.jar;lib/dependency.jar" -c com.example.App
~~~

The classpath separator depends on the operating system: Windows typically uses `;`, while Linux/macOS typically uses `:`. In cross-platform scripts, let the build tool or launcher construct the classpath instead of hard-coding the separator.

For multi-release JARs, you can specify which version entry to inspect:

~~~bash
javap --multi-release 17 -classpath library.jar -c com.example.Library
~~~

This is helpful when a JAR contains different class versions for different Java releases.

### 12.2. Viewing classes in JDK modules

`javap` can read classes belonging to JDK modules:

~~~bash
javap --module java.base -p java.lang.String
~~~

To view bytecode:

~~~bash
javap --module java.base -c -p java.lang.String
~~~

JDK classes can be very large; target specific classes/methods or filter output when investigating. Reading bytecode of a JDK class helps you understand a specific JDK implementation, but it does not turn those implementation details into guaranteed compatible APIs.

### 12.3. Viewing module descriptors

A module descriptor resides in the special class file `module-info.class`. You can inspect a module's descriptor with:

~~~bash
javap --module java.base module-info
~~~

Or view full details:

~~~bash
javap -v --module java.base module-info
~~~

The output displays directives such as `requires`, `exports`, `opens`, `uses`, and `provides`.

## 13. Bytecode verification and StackMapTable

Before executing bytecode, the JVM performs loading and linking steps. During verification, the JVM checks structural and type validity of the bytecode, such as:

- The operand stack is used with valid types.
- Local variables have valid types at control-flow points.
- Method calls and field accesses match expected types.
- Control-flow branches do not produce invalid stack states.
- Stack map frames satisfy the verification rules of the class file version.

`StackMapTable` stores stack map frame information at relevant points in a method. It assists the verifier in checking types and stack/local variable states across control-flow branches.

`javap -v` can display `StackMapTable`. This tool lets you observe the metadata, though reading the output does not replace the JVM verifier's full checks.

### 13.1. Loading, linking, and initialization

Three concepts commonly mentioned when the JVM processes a class:

1. **Loading:** locating and loading the binary representation of a class.
2. **Linking:** consisting of verification, preparation, and resolution as needed.
3. **Initialization:** running static initializers and initializing static fields in the specified order.

`javap` only inspects the class file representation. To confirm a class can load and run in a specific environment, execute it on the actual JVM with the real classpath/module path and dependencies.

## 14. Using javap to investigate compatibility errors

### 14.1. UnsupportedClassVersionError

If logs report:

~~~text
UnsupportedClassVersionError
~~~

Check the major version:

~~~bash
javap -verbose -classpath out demo.Hello
~~~

Compare the major version against the runtime. Java 17 produces class files with major version 61; older runtimes do not support this format.

Typical solutions are:

- Upgrade the runtime to a version supporting the class file.
- Or compile source with an appropriate JDK and `--release`.
- Also check dependencies, because a third-party JAR can contain newer class files.

### 14.2. NoSuchMethodError

`NoSuchMethodError` can occur when code was compiled against one version of a library, but the runtime loads a different version lacking the matching method descriptor.

Use `javap -s -p` on the actual library class to inspect methods and descriptors:

~~~bash
javap -classpath lib/dependency.jar -s -p com.example.Library
~~~

Compare compile-time and runtime classpaths. `javap` tells you which methods exist in the inspected class file; it does not automatically detect the entire class loader order or dependency conflicts in the application.

### 14.3. Checking annotations and generic metadata

When a framework does not recognize annotations or generic types as expected, use:

~~~bash
javap -v -p -classpath out demo.Model
~~~

Look for attributes such as `RuntimeVisibleAnnotations`, `RuntimeInvisibleAnnotations`, `Signature`, and `MethodParameters`.

Annotations with `SOURCE` retention are not kept in the class file. Annotations with `CLASS` retention may be stored in the class file, though not exposed via runtime reflection. Annotations with `RUNTIME` retention are preserved so reflection can read them.

## 15. javap is not a Java decompiler

`javap` disassembles class files and presents bytecode and metadata. It does not reconstruct the original Java source code.

Several reasons:

- Multiple distinct source constructs can produce equivalent bytecode.
- Local variable names may not be recorded.
- Source comments and formatting are not stored in the class file.
- Generics undergo type erasure in runtime descriptors.
- The compiler may generate synthetic methods, bridge methods, or bootstrap metadata.
- Optimizations and lowering make bytecode structure differ from source.

If you need an approximate reconstruction of Java source from a class file, you need a dedicated decompiler. Even then, decompiled source is only a reconstruction; it cannot restore original comments, formatting, or every authoring decision.

`javap` is better suited when the questions are: which version is this class file, what are the method descriptors, which instructions were generated, which fields/methods/attributes exist, and which classes does the bytecode reference.

## 16. Practical workflow from source to bytecode

You can use a repeatable workflow to understand a Java change:

1. Write a small example focusing on a specific construct.
2. Compile with JDK 17 and `--release 17`.
3. Use `javap -c -p` to inspect the bytecode.
4. Use `javap -v` when you need the constant pool, version, or attributes.
5. Change one source construct and recompile.
6. Compare the bytecode before and after.
7. Run on the target JVM to verify actual behavior.

Example command sequence:

~~~bash
javac --release 17 -g -d out src/demo/Calculator.java
javap -classpath out -c -p demo.Calculator
javap -classpath out -s demo.Calculator
javap -classpath out -v demo.Calculator
java -cp out demo.Calculator
~~~

When comparing outputs, keep the JDK/compiler version and compilation options identical. Changing compiler versions or flags can change bytecode even when source code is unchanged.

## 17. Common mistakes

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| `javap` cannot find the class | Classpath does not point to the directory/JAR containing the class, or class name is wrong | Use `-classpath` and the fully qualified package name |
| Class file has newer major version than runtime | Artifact was compiled with a newer JDK | Upgrade runtime or compile with appropriate `--release` |
| No bytecode shown in output | Did not pass `-c` or `-v` | Add `-c` |
| Private methods/fields missing | Default output does not show all members | Add `-p` |
| Local variable names missing | Class file does not store `LocalVariableTable` | Recompile with `-g` if you control the source |
| Generic types missing in descriptors | Descriptors use type erasure | Inspect `Signature` with `-v` |
| Unclear what `#12`, `#25` mean | These are constant pool indices | Cross-reference the Constant pool section in `-v` |
| Bytecode differs from example | Different compiler version/flags or source | Check JDK, `--release`, debug flags, and source |
| Unclear what `invokedynamic` does | Dynamic linkage uses bootstrap metadata | Inspect `BootstrapMethods` with `-v` |
| Assuming `javap` proves the class will run | Disassembly does not replace runtime linking/verification | Run tests on the target JVM |
| Assuming bytecode is CPU machine code | Confusing JVM instructions with native machine code | Distinguish bytecode from JIT-compiled code |

## 19. Key principles to remember

- `javac` compiles Java source into class files containing bytecode and metadata.
- Class files start with magic number `CAFEBABE`; standard Java 17 class files use major version 61.
- Bytecode consists of JVM instructions, typically described using the operand stack and local variable slots.
- The constant pool holds literals and symbolic references to classes, fields, methods, types, and bootstrap metadata.
- Descriptors represent field/method types at the JVM level; generic signatures may be stored separately.
- `javap -c` reads bytecode; `-p` shows private members; `-s` shows descriptors; `-l` shows debug tables; `-v` shows full class file details.
- Use `javac --release 17` to enforce Java 17 source level, class file version, and APIs.
- `invokedynamic` with bootstrap metadata is used for constructs such as lambdas and string concatenation.
- `javap` is a disassembler, not a decompiler, and does not replace running classes on the target JVM.
- When investigating compatibility errors, inspect class file version, descriptors, actual dependencies, and the runtime classpath/module path.

Understanding class files and bytecode clarifies the bridge between Java source and the JVM. With `javap`, developers can inspect compiled artifacts, determine class file versions, and read instructions and metadata—making it easier to troubleshoot compatibility errors or understand how the compiler represents programs in Java 17.
