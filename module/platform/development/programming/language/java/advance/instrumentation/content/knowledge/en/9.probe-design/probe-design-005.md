# Handling Exceptions Raised by Calls or Other Instructions Without a Direct athrow

When designing a probe at **method exit** using Java bytecode instrumentation, simply looking at the **ATHROW** instruction appearing in the method is **not enough** to record every time the method terminates due to an exception. For example, a method might only invoke **INVOKEVIRTUAL**, **INVOKESTATIC**, or execute **IDIV**, **GETFIELD**, **AALOAD** and then terminate abnormally because the underlying call throws an exception, divides by zero, dereferences **null**, or goes out of array bounds. **In the bytecode of the method being instrumented, there is not necessarily a direct ATHROW instruction on that execution path.**

If an agent only inserts logic at **RETURN** and **ATHROW** positions using **ASM AdviceAdapter.onMethodExit(opcode)**, the probe will easily miss **exceptional exits caused by other instructions**. A more general way to record *exceptions escaping the method scope* is to wrap **the entire body to be observed** with an **exception handler catching Throwable**, record the exception in the handler, and then **rethrow the exact original object**. Normal return paths are handled separately; direct **ATHROW** instructions in the body must not be logged a second time if a catch-all is already in place.

This lesson distinguishes bytecode with an **explicit ATHROW**, exceptions **propagating up from a call**, exceptions **generated by the VM when executing an instruction**, the **exception table** mechanism, and how to use Java 17 + ASM to instrument a method properly. The focus is on **preserving the original semantics of the application**, without swallowing or turning an exception into a normal result.

## 1. Learning Objectives

After this lesson, you will be able to:

1. Explain why a method can exit with an exception without **executing ATHROW directly in that method**.
2. Distinguish between the **ATHROW** instruction, **exception handler**, **exception table**, and JVM **unwinding**.
3. Know the limitations of hooking by opcode via **AdviceAdapter.onMethodExit(ATHROW)**.
4. Design a **catch-all handler** covering the method body, without **double-logging** or misreporting exceptions that are handled internally by the body.
5. Preserve the return type, operand stack, local variables, **StackMapTable**, handler order, and the original **Throwable** object.
6. Understand scenarios without standard method entry/exit probes: failures before entering the method, async failures, constructors, native methods, and callbacks on another thread.
7. Run a Java 17 example demonstrating **return**, **callee throwing an exception**, **null dereference**, **division by zero**, and **direct ATHROW**, and verify that the agent does not alter the exception type observed by the caller.

## 2. Why Can an Exception Occur Without ATHROW?

### 2.1. Exceptions from Method Calls

Consider the Java code:

~~~java
// Illustrative snippet; not a standalone file.
static int service() {
    return repository();
}

static int repository() {
    throw new IllegalStateException("database unavailable");
}
~~~

The bytecode of **service()** can be:

~~~text
invokestatic  #... // Method repository:()I
ireturn
~~~

**ATHROW resides in repository()**, while **service()** only executes **INVOKESTATIC**. When repository throws **IllegalStateException**, the call in service **does not return a value** to reach **IRETURN**. The JVM searches for a matching exception handler in service; if none exists, it continues unwinding to the caller of service. An instrumentation that only inspects **IRETURN/RETURN/ARETURN/.../ATHROW** opcodes of service **has no chance to run onMethodExit** on this exception path unless a separate handler is installed.

The same applies to **INVOKEVIRTUAL**, **INVOKEINTERFACE**, **INVOKESPECIAL**, **INVOKESTATIC**, and **INVOKEDYNAMIC**: the call itself or the target method can lead to an exception. Certain class linking/initialization errors can also occur when executing the relevant instruction.

### 2.2. Exceptions Generated by Instructions

| Instruction or group | Scenario | Common Throwable |
| --- | --- | --- |
| **IDIV/IREM/LDIV/LREM** | Division or remainder with divisor equal to 0 | **ArithmeticException** |
| **GETFIELD/PUTFIELD** | Accessing an instance field through a null reference | **NullPointerException** |
| **INVOKEVIRTUAL/INVOKEINTERFACE/INVOKESPECIAL** | Null receiver or callee throws an error | **NullPointerException** or Throwable from callee |
| **ARRAYLENGTH**, **AALOAD/IALOAD/...** | Null array, out-of-bounds index | **NullPointerException**, **ArrayIndexOutOfBoundsException** |
| **AASTORE** | Attempting to store an object incompatible with the array's component type | **ArrayStoreException** |
| **CHECKCAST** | Object does not belong to the target cast type | **ClassCastException** |
| **NEWARRAY/ANEWARRAY/MULTIANEWARRAY** | Negative size, out of memory | **NegativeArraySizeException**, possibly **OutOfMemoryError** |
| **NEW**, **GETSTATIC**, **INVOKESTATIC** and related instructions | Resolution, class initialization, or execution failure | **LinkageError**, **ExceptionInInitializerError**, etc. |

Not every instruction above always throws an error; the table lists **possible generation paths**. The key point is that **an exceptional method exit does not require the method to have an ATHROW instruction at that location**.

### 2.3. Three Scenarios to Distinguish

~~~text
(A) Method throws directly:
    NEW IllegalArgumentException
    ...
    ATHROW                       ← direct ATHROW in the method

(B) Method calls a callee:
    INVOKESTATIC callOther()
       └── callee throws
    IRETURN is not executed      ← caller does not need its own ATHROW

(C) Method executes an instruction that can throw:
    ILOAD dividend
    ILOAD divisor
    IDIV  (divisor == 0)          ← ArithmeticException at IDIV
    IRETURN is not executed
~~~

All three are **method terminations by exception** if the exception is not handled before leaving the method. However, a hook triggered **when the visitor sees the ATHROW opcode** only has a reliable signal in case A; one cannot infer B/C from the absence of a RETURN instruction in a static callback.

## 3. How Does the JVM Find an Exception Handler?

A **Code attribute** in a class file has an **exception table**. Each entry contains:

- **start_pc**: start offset of the protected range (inclusive).
- **end_pc**: end offset (exclusive).
- **handler_pc**: where the JVM transfers control when the exception is caught.
- **catch_type**: exception class to catch; if 0, it is a handler for any matching Throwable (commonly used to compile `finally`). For an agent, **java/lang/Throwable** can be used as `catch_type`.

When an instruction throws an exception, the JVM searches for the **first handler in the table** whose range contains the instruction offset and whose exception type is compatible. If found, the JVM jumps to the handler with the **exception object on the operand stack**; otherwise, the current frame is unwound and the exception is propagated to the calling method. A handler can:

- Handle the exception and continue normally.
- Translate it into another exception according to business logic.
- **Rethrow the same Throwable** to preserve the original exception result.
- Run **finally/cleanup** and then rethrow.

Specifically, the method:

~~~java
// Illustrative snippet: method with an internal catch.
static int parse(String input) {
    try {
        return Integer.parseInt(input);
    } catch (NumberFormatException ex) {
        return -1;
    }
}
~~~

**NumberFormatException** is handled completely inside the method, so **parse() returns normally**. An agent measuring **exceptional exits of parse()** should not report an error just because **Integer.parseInt()** once threw an exception. The synthetic catch-all handler needs to be added **after existing handlers** so that internal catch blocks continue to work; only exceptions **actually escaping the method** reach the agent's handler.

This distinguishes two KPIs:

- **Thrown events**: the number of times an exception occurs at an instruction/callee (even if caught internally).
- **Exceptional method exits**: the number of times the instrumented method **exits to its caller with an exception**.

This lesson primarily addresses **exceptional method exits**. If you want to measure every thrown event, you must instrument a different scope, such as throw sites, catch sites, or an appropriate JVM event mechanism; that is a different problem and cannot be fully inferred using a catch-all at the end of a method.

## 4. Limitations of AdviceAdapter.onMethodExit

ASM commons provides the **AdviceAdapter** class to help insert code at method entry and before return/ATHROW opcodes. Illustrative example:

~~~java
// Illustrative snippet inside an AdviceAdapter; not standalone Java yet.
@Override
protected void onMethodExit(int opcode) {
    if (opcode == ATHROW) {
        // Only knows that the visitor encountered a direct ATHROW instruction.
        logErrorExit();
    } else {
        logNormalExit();
    }
}
~~~

Drawbacks:

1. The visitor **sees the ATHROW instruction in the bytecode being visited**, not a JVM callback when a Throwable is thrown at runtime.
2. Exceptions from **INVOKESTATIC**, **INVOKEVIRTUAL**, **IDIV**, or **GETFIELD** do not automatically trigger an **onMethodExit(ATHROW)** call on the instrumented method.
3. An ATHROW opcode may appear **inside a try/catch of the method itself**; that exception can be caught and the method continues to return normally. If an error exit is recorded at **every ATHROW**, the exit KPI will **count inaccurately**.
4. If an error is logged both in **onMethodExit(ATHROW)** and in a catch-all handler that also logs errors, an exception actually escaping the method may be recorded **twice**.

Therefore, when the goal is to **count/trace every time a method exits with an exception**, the reliable approach is:

- Insert a **normal-exit hook** at return opcodes.
- **Do not** record an exceptional exit at the ATHROW opcode alone.
- Install a **catch-all exception handler** covering the original code to be measured.
- Inside the handler, record the exception, then **reload and ATHROW the same object**.
- Ensure the handler does not catch itself, is not placed before business handlers, and does not alter the original exception.

### 4.1. Comparison of the Two Approaches

| Criterion | Only onMethodExit(ATHROW) | Catch-all covering body |
| --- | --- | --- |
| Explicit ATHROW and exception escaping method | Observable | Observed |
| Callee throws, caller has no ATHROW | **Missed** | Observed |
| IDIV/GETFIELD throws exception | **Missed** | Observed |
| Internal ATHROW then caught inside method | May **falsely report exit** | Does not report exceptional exit if internal handler handles it |
| Works properly on normal method return | Requires handling return opcodes | Requires separate normal-exit hook |
| Risk of self-inflicted errors | Lower regarding CFG | Must build valid exception table and frames |
| Constructor/native/synchronized | Requires separate handling | Also requires separate handling |

## 5. Bytecode Structure Pattern for Exceptional Exit

Most **regular method** instrumentation designs will have the following shape:

~~~text
Method m(args):
    call TraceHooks.enter()             ← start of measurement

    L_start:
        ... original method body ...
        ... calls, field accesses, arithmetic ...
        ... method's own try/catch ...
        ...
        RETURN / IRETURN / ARETURN:
            call TraceHooks.normal()    ← right before normal return
            RETURN / IRETURN / ARETURN

    L_end:
    L_handler:                           ← outside the try range
        ASTORE localThrowable           ← save Throwable from operand stack
        ALOAD localThrowable
        call TraceHooks.exception(Throwable)
        ALOAD localThrowable
        ATHROW                           ← rethrow the same object

Exception table:
    [L_start, L_end) -> L_handler catch java/lang/Throwable
~~~

This is a **bytecode diagram**, not a Java source file. The handler must lie **outside the protected range itself** so that if the handler logic throws an exception, it does not create a loop catching itself. The application's exception table must have the chance to handle exceptions first; when using ASM, the synthetic catch-all is typically **added after existing handlers**.

### 5.1. Why Catch Throwable Instead of Exception?

**Throwable** includes both **Exception** and **Error**. An instruction can lead to **OutOfMemoryError**, **LinkageError**, **ExceptionInInitializerError**, or an error that is not a subclass of **Exception**. If you want to observe **every exceptional exit**, the handler needs to cover **Throwable**.

However, "catching Throwable to **record and rethrow**" is different from "catching Throwable to **swallow**". One should not swallow **ThreadDeath**, **VirtualMachineError**, or alter how the JVM reports serious errors. The probe must prioritize preserving original behavior; the logger in the handler should be minimal, non-blocking, and limit allocations.

### 5.2. Preserving the Exception Object and Stack

At handler entry, the JVM places the Throwable object on the stack. A safe pattern:

~~~text
ASTORE exceptionSlot
ALOAD  exceptionSlot
INVOKESTATIC TraceHooks.exception(Throwable)
ALOAD  exceptionSlot
ATHROW
~~~

Here **exceptionSlot** is a new local variable slot allocated by the instrumenter, and must not accidentally overwrite an application local. **The ATHROW at the end of the handler is inserted by the agent** to propagate the original exception. That does not mean every exception from the body had to go through a direct ATHROW in the body.

Do not do:

~~~text
POP
RETURN
~~~

because that turns an error into a normal return, breaking the method contract. Nor should you always create **new RuntimeException(original)** if the goal is to preserve the Throwable; doing so changes its type, identity, stack trace, and can break control flow in the caller.

### 5.3. Hooks Must Not Break Semantics When They Fail

If **TraceHooks.normal()** throws an exception, a method that normally returns a valid result can become a method throwing an error. If **TraceHooks.exception(t)** throws a new exception, the caller may no longer see the original Throwable. Therefore, production instrumentation should use **hooks that do not throw exceptions outward**, log in a controlled manner, avoid calling complex frameworks on class load / hot paths, and have an error-handling policy for the logger.

For the runnable example below, the hook simply prints a single line for ease of learning; it is **not a production telemetry stack**. In real-world usage, choose a non-blocking logging path and account for failures in the observability system itself.

## 6. Step One: Java 17 Program Without Instrumentation

We build a small program containing a **run(String)** method whose main error paths **have no direct ATHROW instruction in the caller**. A separate **directThrow()** method serves as a control.

**File src/main/java/demo/App.java**

~~~java
package demo;

public final class App {
    public static final class Worker {
        private Worker() { }

        public static int run(String mode) {
            return switch (mode) {
                case "ok" -> 7;
                case "call" -> downstream();
                case "null" -> ((String) null).length();
                case "divide" -> 10 / zero();
                default -> -1;
            };
        }

        public static int directThrow() {
            throw new IllegalArgumentException("direct");
        }

        private static int downstream() {
            throw new IllegalStateException("from callee");
        }

        private static int zero() {
            return 0;
        }
    }

    public static void main(String[] args) {
        for (String mode : new String[] {
                "ok", "call", "null", "divide", "explicit"
        }) {
            try {
                int answer = mode.equals("explicit")
                        ? Worker.directThrow()
                        : Worker.run(mode);
                System.out.println("RESULT " + mode + "=" + answer);
            } catch (Throwable error) {
                System.out.println("CAUGHT " + mode + " "
                        + error.getClass().getSimpleName());
            }
        }
    }
}
~~~

Explanation of each case:

- **ok**: the method returns **7**, taking a normal return.
- **call**: **run** calls **downstream()**; the downstream method uses ATHROW, while **run** only calls the method and propagates the exception upward.
- **null**: inside **run**, the instruction calling **String.length()** on a null reference throws **NullPointerException**.
- **divide**: the division **10 / zero()** executes IDIV with divisor 0, throwing **ArithmeticException**.
- **explicit**: **directThrow()** throws **IllegalArgumentException** itself; this method has an explicit ATHROW and serves as a control.

**run(String)** alone does not need a direct ATHROW to have three types of exception exits. With a Java 17 switch expression, **javac** may use `lookupswitch` or a chain of comparisons to dispatch, but that does not change exception semantics.

If you only want to run the Java version without an agent, after saving App.java, you can compile it standalone:

~~~bash
javac --release 17 -d out src/main/java/demo/App.java
java -cp out demo.App
~~~

Consistent output of the uninstrumented version:

~~~text
RESULT ok=7
CAUGHT call IllegalStateException
CAUGHT null NullPointerException
CAUGHT divide ArithmeticException
CAUGHT explicit IllegalArgumentException
~~~

### 6.1. Reading Disassembly with javap

~~~bash
javap -c -p -classpath out 'demo.App$Worker'
~~~

The command above uses single quotes for POSIX shells to preserve the **$** character. In Windows PowerShell, also use single quotes; if running Windows cmd.exe, apply appropriate quoting.

Observe the **run(java.lang.String)** method: the error branches will have instructions such as:

~~~text
invokestatic ... downstream:()I
...
invokevirtual ... java/lang/String.length:()I
...
idiv
...
ireturn
~~~

These are **abbreviated illustrative lines**, not a full transcript, because constant pool positions/indices are determined by the compiler. There is no need to write a direct ATHROW in **run** for those errors to escape. **directThrow()**, by contrast, will show the **athrow** opcode in the disassembly.

## 7. Step Two: Instrumenting the Method with ASM AdviceAdapter and Catch-All

The example agent uses **ASM 9.7.1** on Java 17. ASM is packaged into the JAR using **Maven Shade**, so when using **-javaagent** there is no need to pass the two ASM JARs on an external classpath. There are two Java source files (App.java and ExitAgent.java), along with a pom.xml. The example intentionally transforms only **demo/App$Worker**, specifically the **run(String)** and **directThrow()** methods; it does not touch constructors, native methods, or other classes.

### 7.2. ExitAgent.java

**File src/main/java/demo/ExitAgent.java**

~~~java
package demo;

import java.lang.instrument.ClassFileTransformer;
import java.lang.instrument.Instrumentation;
import java.security.ProtectionDomain;

import org.objectweb.asm.ClassReader;
import org.objectweb.asm.ClassVisitor;
import org.objectweb.asm.ClassWriter;
import org.objectweb.asm.Label;
import org.objectweb.asm.MethodVisitor;
import org.objectweb.asm.Opcodes;
import org.objectweb.asm.Type;
import org.objectweb.asm.commons.AdviceAdapter;
import org.objectweb.asm.commons.Method;

public final class ExitAgent {
    private ExitAgent() { }

    public static void premain(String options, Instrumentation inst) {
        inst.addTransformer(new ExitTransformer(), false);
    }
}

final class ExitTransformer implements ClassFileTransformer {
    @Override
    public byte[] transform(
            ClassLoader loader,
            String className,
            Class<?> classBeingRedefined,
            ProtectionDomain protectionDomain,
            byte[] classfileBuffer) {

        if (!"demo/App$Worker".equals(className)) {
            return null;
        }

        ClassReader reader = new ClassReader(classfileBuffer);
        ClassWriter writer = new ClassWriter(
                reader, ClassWriter.COMPUTE_FRAMES
                        | ClassWriter.COMPUTE_MAXS);

        ClassVisitor visitor = new ClassVisitor(Opcodes.ASM9, writer) {
            @Override
            public MethodVisitor visitMethod(
                    int access,
                    String name,
                    String descriptor,
                    String signature,
                    String[] exceptions) {

                MethodVisitor original = super.visitMethod(
                        access, name, descriptor, signature, exceptions);

                boolean selected =
                        ("run".equals(name)
                                && "(Ljava/lang/String;)I"
                                        .equals(descriptor))
                        || ("directThrow".equals(name)
                                && "()I".equals(descriptor));

                if (!selected) {
                    return original;
                }

                return new AdviceAdapter(
                        Opcodes.ASM9, original,
                        access, name, descriptor) {

                    private final Label bodyStart = new Label();
                    private final Label bodyEnd = new Label();
                    private final Label errorHandler = new Label();

                    @Override
                    protected void onMethodEnter() {
                        invokeStatic(
                                Type.getType(ExitHooks.class),
                                new Method("enter", "()V"));
                        mark(bodyStart);
                    }

                    @Override
                    protected void onMethodExit(int opcode) {
                        // Direct ATHROW will be handled by the handler if
                        // the exception actually escapes the method.
                        if (opcode != ATHROW) {
                            invokeStatic(
                                    Type.getType(ExitHooks.class),
                                    new Method("normal", "()V"));
                        }
                    }

                    @Override
                    public void visitMaxs(int maxStack, int maxLocals) {
                        // Add handler after existing handlers:
                        // the method's internal catch retains priority.
                        mark(bodyEnd);
                        visitTryCatchBlock(
                                bodyStart, bodyEnd, errorHandler,
                                "java/lang/Throwable");
                        mark(errorHandler);

                        int exceptionLocal =
                                newLocal(Type.getType(Throwable.class));
                        storeLocal(exceptionLocal);

                        loadLocal(exceptionLocal);
                        invokeStatic(
                                Type.getType(ExitHooks.class),
                                new Method(
                                        "exception",
                                        "(Ljava/lang/Throwable;)V"));

                        loadLocal(exceptionLocal);
                        throwException(); // rethrow the exact Throwable

                        super.visitMaxs(maxStack, maxLocals);
                    }
                };
            }
        };

        reader.accept(visitor, ClassReader.EXPAND_FRAMES);
        return writer.toByteArray();
    }
}

// Helper in the same runtime package/class loader as App$Worker in the demo.
final class ExitHooks {
    private ExitHooks() { }

    public static void enter() {
        System.out.println("TRACE_ENTER");
    }

    public static void normal() {
        System.out.println("TRACE_NORMAL");
    }

    public static void exception(Throwable error) {
        System.out.println("TRACE_EXCEPTION "
                + error.getClass().getSimpleName());
    }
}
~~~

**Key points in the code:**

1. **ExitTransformer** filters strictly for the internal class name **demo/App$Worker**. Other classes return **null**, so ASM does not have to process every class loaded by the JVM.
2. **visitMethod** filters both method name and descriptor. This avoids accidentally instrumenting overloads.
3. **onMethodEnter** inserts **ExitHooks.enter()** and then marks **bodyStart**. Because both target methods are **static, not constructors**, there is no **uninitialized this** issue.
4. **onMethodExit** only inserts **ExitHooks.normal()** for normal return opcodes. **ATHROW** is skipped to avoid double-reporting errors and to avoid misreporting an internally caught ATHROW.
5. **visitMaxs** adds a **catch-all handler** covering the range from **bodyStart** to **bodyEnd**. It is added after the original handlers have already been passed by the reader to the visitor, so existing business handlers are evaluated first.
6. In the handler, the JVM provides the **Throwable** on the stack; **storeLocal** saves the object into a new local, **ExitHooks.exception** records it, and then **throwException()** rethrows that exact object.
7. **bodyEnd** is placed before the handler, so **the handler does not catch itself**.
8. **ClassWriter.COMPUTE_MAXS | COMPUTE_FRAMES** recalculates stack/local limits and frames for the demo class; **ClassReader.EXPAND_FRAMES** reads frames in expanded form compatible with writing.
9. The class is defined after the transformer returns the new bytes; the application actually invoking the methods is the proof that the JVM accepted and used the instrumentation.

**Demo limitations:** The example does not register the transformer with **canRetransform=true**, does not instrument constructors/native/abstract methods, does not define rollback logic, and assumes all demo classes share the system/application class loader in the unnamed module. In production, **COMPUTE_FRAMES** may need a **ClassWriter.getCommonSuperClass** suited to the target class's class loader; resolving type hierarchies with the wrong loader can lead to verifier errors or nested class loading. An agent should not apply this sample transformation to arbitrary classes without checking access/module/classloader visibility and the class's handler order.

### 7.4. Why Doesn't the Handler Catch Exceptions Already Handled by the Method?

In ASM, the original method's exception table entries are passed into the visitor while reading the class. The **catch Throwable** handler of the example is added last. The JVM scans the exception table in order, so if the original method has a matching **try/catch** and the exception occurs within that region, the original handler is selected first.

If the original catch handles the error and the method returns normally, the **normal-exit hook** will log **TRACE_NORMAL**; the **exceptional-exit hook** does not run. If the original catch rethrows the exception or throws a different exception outward, the agent's catch-all can observe the actual method exit.

**However**, one should not assume every visitor configuration preserves handler order like the example. Another tool might insert a catch-all before application handlers, or the class writer might be used incorrectly. Always inspect the final exception table with **javap -v** and test methods that have internal catches.

## 8. An Alternative Way to Understand It via Standard Java try/finally

Because ASM handlers look somewhat abstract, you can imagine the instrumented method as equivalent to the following Java source code (describing semantics only; the agent does not modify source):

~~~java
// Illustrative Java source model, not directly transformed code.
static int observed(String mode) {
    ExitHooks.enter();
    try {
        int result = Worker.run(mode);
        ExitHooks.normal();
        return result;
    } catch (Throwable original) {
        ExitHooks.exception(original);
        throw original;
    }
}
~~~

If Worker.run("call") throws IllegalStateException from downstream, the **catch** block in the wrapper still runs. If Worker.run("divide") throws ArithmeticException at **IDIV**, the wrapper still catches it. This model shows that the probe must surround **the execution**, not just the method's **throw** statements.

However, the source code above **is not completely identical to a transform inserted into the body itself** when a method has internal catches, multiple returns, and exceptions arising from hooks: the wrapper could catch exceptions from **ExitHooks.normal()** as well, whereas in production hooks should be designed not to throw exceptions. Additionally, an external wrapper cannot see exceptions that were caught by the target method and turned into a normal return, which matches the concept of an exceptional *exit*.

### 8.1. Why Not Just Use finally?

**finally** can record a single "method finished" event for both returns and exceptions; however, if you need to distinguish **NORMAL** from **EXCEPTIONAL**, you have to design extra state or a catch to know the exit type. A flag variable set before return can work for simple code, but if cleanup/hook logic throws an exception afterward, the reported status may differ from what the caller actually receives. A catch-all with a rethrowing handler has clearer semantics for **exceptional exits**, while the normal hook is attached separately at returns.

If you only want a single unified event at every exit, you can design a finally-like hook with state and control-flow checks; you still have to update bytecode/frames, preserve the exception object, and avoid double-logging. Simply inserting code before return opcodes will not handle every exceptional exit.

## 9. Limitations That Cannot Be Solved by a Method-Body Catch-All Alone

### 9.1. Method Was Never Actually Entered

**NoClassDefFoundError**, **ExceptionInInitializerError**, or linking errors can occur when **a caller attempts to invoke a method** but the target class has not been fully initialized/resolved. In that situation, the **target method's** bytecode may **never have been executed**, so a handler inside the target method cannot record entry/exit. Instrument the **call site** or caller method if you want to observe failures at the call boundary.

Distinguish between:

~~~text
Caller -> prepare/resolve Callee's class -> failure
            (Callee body never starts)

Caller -> Callee body runs -> throws error
            (handler in Callee can catch exceptional exit)
~~~

### 9.2. Exception Handled Inside the Method

If a method catches an error itself and returns a fallback value, it **returns normally**. The catch-all handler at the end should not record an exceptional exit; if you want to count every exception ever thrown, you need to instrument thrown/catch events under a different KPI definition.

### 9.3. Exception Occurs Asynchronously

A method may return a **CompletableFuture**, **CompletionStage**, **Future**, **Publisher**, or spawn a thread and return before the actual work fails. For example:

~~~java
// Non-standalone illustrative snippet; future fails after method returns.
java.util.concurrent.CompletableFuture<String> loadAsync() {
    return java.util.concurrent.CompletableFuture.supplyAsync(() -> {
        throw new IllegalStateException("background");
    });
}
~~~

**loadAsync()** has already **returned normally** with a future; the exception occurs on a task thread and is represented via future completion. A handler around **loadAsync** cannot automatically catch this error. To measure **asynchronous business errors**, instrument the appropriate completion callback, async boundary, or task execution; propagate trace context across threads if needed.

### 9.4. Constructors and Uninitialized this

**AdviceAdapter.onMethodEnter** has special semantics for constructors: it is typically invoked only after the appropriate **super()/this()** call has completed. A catch-all covering the region before the object is validly initialized can cause verifier errors or violate uninitialized-this rules. The example only instruments **static methods**. For constructors, handlers and advice must be placed after the valid initialization point or use a specialized design tested against the JVM verifier.

### 9.5. Native, Abstract, and Synchronized Methods

- **Abstract/native methods** do not have a Java **Code attribute** to insert a try/catch body in the usual way. A different solution or caller/wrapper instrumentation is needed.
- For **synchronized methods**, the normal-exit hook is inserted before the body's returns, while the JVM-managed monitor may be released when the method actually finishes. Duration measured at the hook may not include the entire overhead outside the body/monitor release depending on the definition. Avoid blocking logging inside synchronized methods because it extends monitor hold time.
- For **JNI**, exceptions can be created/stored via native mechanisms and propagated when the native call finishes; a catch-all in the Java caller can see the Throwable as it propagates out, but cannot observe individual details inside the native body through Java bytecode alone.

### 9.6. Failures of the Instrumentation Mechanism Itself

If the JVM rejects the bytes returned by the agent (invalid exception table, invalid StackMapTable, invalid bytecode), the application may receive **VerifyError/ClassFormatError/LinkageError** when defining or using the class. That is a failure **of the instrumentation installation process**, not a normal exceptional exit of the instrumented method. Separate class load/retransform checks and behavioral tests are required.

## 10. Verifying Bytecode, Stack Frames, and Handler Order

After building, you can inspect the **original method on disk** using:

~~~bash
javap -c -v -p -classpath target/exception-exit-agent.jar 'demo.App$Worker'
~~~

The JAR contains class files **not yet transformed by the JVM at runtime**, so javap reading it directly **will not show the agent's synthetic handler**. To inspect the actual transform result, dump the `byte[]` returned by the agent to a file **in a controlled way**, or use an appropriate export tool/path and disassemble that output. Do not conclude "the transformer didn't run" just because javap on the original file does not show the handler.

When inspecting the transformed output, verify:

1. There is an added **exception table entry** with the exact range **[bodyStart, bodyEnd)** and catch type **java/lang/Throwable**.
2. The agent's catch-all entry is placed **after business handlers** that need priority.
3. The handler writes to a **new local slot**, without overwriting method locals.
4. The handler **is not inside its own protected range**.
5. All applicable return opcodes have the normal hook.
6. Explicit **ATHROW** opcodes are not handled twice; the exception is propagated properly.
7. **Max stack/max locals/StackMapTable** are written validly; the JVM verifier accepts the class.
8. Original instructions/call sites and try/catch logic are not inadvertently altered.

For classes with complex inheritance or custom defining class loaders, the default **ClassWriter.COMPUTE_FRAMES** may attempt to resolve common superclasses using the wrong class loader for the target. That is why this simple pattern should not be deployed to all production classes without a type-resolution policy, classloader visibility checks, and tests.

### 10.1. When Should Existing Exception Handlers Be Tested?

Create a method:

~~~java
// Illustrative snippet.
static int safeParse(String value) {
    try {
        return Integer.parseInt(value);
    } catch (NumberFormatException ignored) {
        return -1;
    }
}
~~~

If you test **safeParse("not-a-number")**, the correct result for **exceptional-exit instrumentation** is **NORMAL** because the method returns **-1**. If the agent handler records **EXCEPTION** before the application's catch runs, the exception table order or catch-all range was configured incorrectly.

If the application only catches **NumberFormatException** but the callee throws **OutOfMemoryError**, the agent's **Throwable**-catching handler can see the error escaping the method and must rethrow the same object. Do not use a catch-all to make the application appear "stable" by hiding dangerous errors.

## 11. Test Matrix for Method-Exit Probes

| Case | Has ATHROW in instrumented method? | Expected event |
| --- | --- | --- |
| Normal return | No | **NORMAL** exactly once |
| Method throws itself and does not catch | Yes | **EXCEPTIONAL** exactly once |
| Method calls callee that throws unchecked exception | Possibly no | **EXCEPTIONAL** exactly once |
| IDIV division by 0 | Not needed | **EXCEPTIONAL** exactly once |
| Null dereference | Not needed | **EXCEPTIONAL** exactly once |
| Array index out of bounds | Not needed | **EXCEPTIONAL** exactly once |
| Method catches internally and returns fallback | Possibly in callee | **NORMAL**, no false exceptional exit |
| Method catches and rethrows | Yes or no | **EXCEPTIONAL** exactly once |
| Observation hook itself fails | Not part of business method | Must not break application semantics by production design |
| Async task fails after method returns | Not part of this method return | **NORMAL** for method, measure async completion separately |
| Constructor fails before super init | Depends on situation | Do not infer from a catch-all placed in body after super |
| Class initialization error before entering method | Method did not run | Observe at caller/call site |

### 11.1. Important Assertions

When testing, in addition to logs, verify:

- **The caller receives the exact Throwable type** (**IllegalStateException**, **NullPointerException**, **ArithmeticException**, ...).
- **The exact same Throwable object** is rethrown if testing identity directly (no unintended wrapper).
- No change in return values/side effects of normal methods.
- **NORMAL** and **EXCEPTIONAL** events do not both appear for a single valid invocation.
- Exactly one exit event per invocation (barring intentional sampling/drop policies).
- Existing handlers take precedence, so exceptions handled by the method are not counted as exceptional exits.
- Under concurrent load, counters/logs do not race, deadlock, or leak class loaders.

If adding latency measurement, clearly define start/end clocks, hook overhead, and the difference between synchronous completion and async completion. **System.nanoTime()** is suitable for measuring relative duration within the same JVM, but should not be used to infer absolute wall-clock timestamps.

## 12. Common Design Mistakes and Fixes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Only hooking ATHROW | Misses callee/instruction exceptions | Add catch-all protecting the body |
| Both ATHROW hook and catch-all log | Double-counts explicit throws | Remove exceptional hook at ATHROW; handler logs once |
| Hooking every ATHROW even when method catches | Records false exceptional exits | Let application handlers process first |
| Catch-all placed before original catch | Alters application try/catch semantics | Add catch-all after original handlers |
| Handler does not rethrow | Turns error into return or swallows Error | Rethrow the exact Throwable object |
| Handler creates a new exception | Changes type/cause/stack/identity | Log and rethrow the original |
| Handler lies inside protected region | Catches its own errors | Place handler outside `[start, end)` |
| Inserting advice into constructor before super | Verifier/uninitialized-this error | Use dedicated probe strategy for constructors |
| Wrong local slot or frame | VerifyError/class load failure | Allocate local via ASM and compute frames properly |
| Instrumenting method where helper is not visible | NoClassDefFoundError/IllegalAccessError at runtime | Manage loader/module and package access |
| Blocking/throwing logger | Increases latency or corrupts original exception | Minimal, non-throwing hook with fallback |
| Treating future failure as sync method exit | Miscounts async errors | Instrument completion/callback |
| Using javap on original JAR to verify transformed bytes | Handler not visible even though agent works | Dump actual output `classfileBuffer` to inspect |
| Only checking TRANSFORMED log and assuming success | JVM may still reject bytes | Verify class definition + actual runtime behavior |

## 13. Self-Check Questions

1. **Service only calls repository(), but repository() throws an exception; does Service need an ATHROW?** No. The invocation instruction can terminate abnormally and the exception unwinds through Service.
2. **Through which opcode does IDIV with divisor 0 throw an exception?** **IDIV** causes **ArithmeticException**; no direct ATHROW is needed in the body.
3. **Does AdviceAdapter.onMethodExit(ATHROW) see an exception thrown by a callee via INVOKESTATIC?** No, if the caller method does not execute an ATHROW on that error path.
4. **Why can an ATHROW hook cause false positives?** ATHROW may lie inside an internally caught branch; the method subsequently returns normally.
5. **Where should a synthetic catch-all handler be placed?** Covering the body to be measured, placed outside its own catch range, and after business exception handlers when priority must be preserved.
6. **Why catch Throwable?** To observe both **Exception** and **Error** escaping the method, while rethrowing rather than swallowing.
7. **Can we return a default value after catching so the app continues?** Not if preserving semantics is required; doing so hides application errors.
8. **If a method returns a CompletionStage successfully and the task later fails, will a catch-all around the method see the error?** No. The error occurs at asynchronous completion and requires instrumenting a different boundary.
9. **Does javap on the original JAR class show the handler inserted at runtime?** No. You must inspect the actual bytes provided by the transformer or runtime behavior.
10. **What is the strongest proof for an exceptional-exit probe?** The caller still sees the exact Throwable, and the log receives **one exceptional-exit event** across direct throws, callee exceptions, and implicit instruction exceptions; normal returns and internal catches are not misreported.

## 14. Checklist for Applying to a Real Java Agent

- I have identified whether the KPI is **exception thrown event**, **exceptional method exit**, or **async task failure**; they are not mixed.
- I understand that **ATHROW does not cover every exceptional exit** from method calls/instructions.
- The instrumenter uses the exact method name/descriptor and class loader/module, without accidentally modifying other methods/classes.
- The normal-exit hook is present at valid return opcodes; exceptional exits use a catch-all rather than ATHROW alone.
- The catch-all covers the exact body region, **does not swallow exceptions**, and **rethrows the same object**.
- Application handlers take precedence, and the synthetic handler is outside its own protected range.
- Stack, local slots, exception table, and StackMapTable are valid after writing the class file.
- Telemetry hooks are designed not to alter application errors/returns; overhead and locking impact have been evaluated.
- Constructors, native/abstract methods, class initialization failures, and asynchronous operations have dedicated strategies.
- I have tested **normal, callee throw, NPE, arithmetic, explicit throw, internally caught exception**, and at least one concurrency test when needed.
- I verified that the JVM **accepted the class file** and the caller still observes the correct behavior, rather than relying only on transform logs.

**Conclusion:** to measure **every time a method terminates due to a Throwable**, one cannot rely solely on whether the method's bytecode contains an **ATHROW** instruction. Exceptions can **propagate up from a callee** or **be generated at many other instructions**. The standard solution is **a normal hook for returns + a catch-all handler covering the body**, preserving catch order and **rethrowing the same Throwable**; then verify with the actual bytecode and application behavior.
