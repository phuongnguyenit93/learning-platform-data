# Can-Set-Native-Method-Prefix and isNativeMethodPrefixSupported

> **Key Takeaway:** `Can-Set-Native-Method-Prefix` is an **optional capability** of Java instrumentation, requested in the agent's manifest. `Instrumentation.isNativeMethodPrefixSupported()` checks that capability in the current JVM configuration. When supported, `Instrumentation.setNativeMethodPrefix(transformer, prefix)` allows the JVM to **retry linking a `native` method to its JNI implementation according to a prefix rule**. This mechanism serves agents that want to create a **Java wrapper with bytecode** around a native method that originally **has no Java bytecode to instrument directly**. Declaring the flag or calling the API **does not automatically transform bytecode and does not automatically create a wrapper**.

## 1. Why does instrumentation need a "native method prefix"?

A regular Java method has a bytecode body, so a `ClassFileTransformer` can insert instrumentation paths: logging, timing, counting invocations, and forwarding to the original body. In contrast, a method declared `native` has no `Code` attribute containing Java bytecode; execution resides in a native library or runtime linked via JNI.

For example, the original application class has:

~~~java
package com.example;

public class NativeCounter {
    public native long read(long key);
}
~~~

This is an **illustrative code snippet**, not a complete program because it requires a JNI library to provide the implementation. If JNI uses automatic symbol name lookup, the corresponding native code might export a function like:

~~~c
/* JNI illustration for an instance method, not a standalone C program. */
JNIEXPORT jlong JNICALL
Java_com_example_NativeCounter_read(JNIEnv *env, jobject self, jlong key);
~~~

An agent cannot insert Java bytecode directly into the `native read` body. Instead, during **initial class definition**, the transformer can create an equivalent structure:

~~~java
package com.example;

public class NativeCounter {
    // Java wrapper generated by the transformer, with bytecode for instrumentation.
    public long read(long key) {
        long started = System.nanoTime();
        try {
            return $observe$read(key);
        } finally {
            System.out.println("elapsed-ns=" + (System.nanoTime() - started));
        }
    }

    // Renamed native entry, preserving the parameter/return signature.
    private native long $observe$read(long key);
}
~~~

This is also an **illustration of the class file transformation result**: a real transformer must also generate valid bytecode, handle the constant pool, stack frames, exception table, and method compatibility. Writing two `NativeCounter` classes with the same name in two Java files does not substitute for a transformer, and the example cannot run standalone without a JNI library.

A new problem arises: the native library already provides a symbol for `read`, and **does not have** a new symbol for `$observe$read`. If the JVM only looks up the new native name, the call may end with `UnsatisfiedLinkError`. The native method prefix solves this bridge: when normal lookup fails, the JVM is allowed to retry by **stripping the prefix** according to the transformer's rule, thereby finding the original JNI implementation again.

~~~text
Application calls NativeCounter.read(key)
         |
         v
Java wrapper read() with bytecode
  - starts timing
  - calls native $observe$read(key)
         |
         v
JVM looks up JNI implementation for $observe$read
         |
         +--> Normal lookup succeeds: use that implementation
         |
         +--> Not found: try registered prefix rule
                  |
                  v
             Find original JNI implementation of read
                  |
                  v
              Return result to wrapper
                  |
                  v
             Wrapper finishes instrumentation
~~~

**Role of each part:** the transformer creates the wrapper and renames the method; `setNativeMethodPrefix` configures how the JVM *retries resolution*; `isNativeMethodPrefixSupported` indicates whether this configuration is allowed to be used. The mechanism does not arbitrarily intercept every JNI call, does not modify machine code in native libraries, and does not replace a class that has valid bytecode.

## 2. Three layers of conditions: manifest, JVM, and transformer

There are two public API components and one manifest attribute to remember accurately:

| Component | Type/input | Meaning |
| --- | --- | --- |
| `Can-Set-Native-Method-Prefix` | **Main section** attribute of `META-INF/MANIFEST.MF`, typically taking `true` or `false` | Agent **requests** permission to use the native prefix feature |
| `Instrumentation.isNativeMethodPrefixSupported()` | No-argument method, returns `boolean` | Indicates whether the current JVM configuration actually allows setting prefixes |
| `Instrumentation.setNativeMethodPrefix(ClassFileTransformer, String)` | `void` method | Attaches a prefix rule to **a registered transformer** |

Example manifest for a **startup agent** using `-javaagent`:

~~~text
Manifest-Version: 1.0
Premain-Class: com.example.agent.NativeProbeAgent
Can-Set-Native-Method-Prefix: true
~~~

Save the manifest as text with valid line endings. `Premain-Class` is the class containing `premain` and is required when starting with `-javaagent`. If the agent is attached to a running JVM, the manifest also needs `Agent-Class` pointing to the class containing `agentmain`; the `Can-Set-Native-Method-Prefix` attribute still refers to the native prefix capability. Dynamic agent loading has its own rules and policies, which do not change the meaning of the three components above.

Important support rules:

1. The `Can-Set-Native-Method-Prefix` attribute is optional. **Missing attribute → defaults to `false`**.
2. The value `true` (case-insensitive) is how this capability is requested; any value other than `true` is treated as `false`.
3. **Manifest `true` is a necessary condition but not sufficient**: the JVM must also support that capability. Do not assume every JVM vendor enables it.
4. `isNativeMethodPrefixSupported()` must be the check point in agent code. For a single JVM invocation, consecutive calls to this method return the same answer per the API contract.
5. `Can-Set-Native-Method-Prefix` is **different from** `Can-Retransform-Classes` and `Can-Redefine-Classes`. The three capabilities are independent; declaring one flag does not automatically enable the other two.

Decision table:

| Manifest | Does the JVM have native prefix capability? | `isNativeMethodPrefixSupported()` | Handling approach |
| --- | --- | --- | --- |
| Missing attribute or `false` | Any | `false` in an agent configuration that does not request the capability | Do not call `setNativeMethodPrefix`; if a JNI wrapper is needed, the plan must change |
| `true` | No | `false` | Skip the optional feature or report a configuration error if the feature is required |
| `true` | Yes | `true` | Register the transformer, set the prefix, then implement the transformation properly |

A `true` value **does not mean** the JVM has linked a JNI library or that the agent has actually instrumented any native calls.

## 3. Call order for `setNativeMethodPrefix` and API errors

Typical initialization flow in `premain(String, Instrumentation)` or `agentmain(String, Instrumentation)`:

~~~text
Receive Instrumentation from JVM
    |
    v
isNativeMethodPrefixSupported()?
    |
    +-- false --> skip or stop with diagnostics
    |
    +-- true --> instantiate ClassFileTransformer
                      |
                      v
              addTransformer(transformer)
                      |
                      v
              setNativeMethodPrefix(transformer, prefix)
                      |
                      v
              JVM defines classes targeted by the transformer
                      |
                      v
              Transformer creates Java wrapper + prefixed native method
~~~

**`addTransformer` is required before `setNativeMethodPrefix`.** Calling `setNativeMethodPrefix` for an unregistered transformer is an error, even if the JVM reports the capability as `true`. The prefix name must match exactly how the transformer renames the method. You can use an example like `"$agent$"` or a string less likely to collide with application names, such as `"$$$TraceToolNative$$$_"`.

Specified exceptions:

| Situation | Exception | Meaning/remediation |
| --- | --- | --- |
| `transformer == null` | `NullPointerException` | Provide a real transformer object |
| Configuration does not support the feature | `UnsupportedOperationException` | Check the manifest, JVM, and `isNativeMethodPrefixSupported()` result |
| Transformer not yet registered | `IllegalArgumentException` | Call `addTransformer` with **that exact instance** first |
| `prefix == null` or `prefix.isEmpty()` | **Not an error due to the prefix itself** | Disables the native resolution retry rule for that transformer |

Note: if a single call simultaneously violates multiple conditions (for example, unsupported configuration **and** unregistered transformer), **do not rely on exception ordering** across JVMs. Check capability and registration order first. The `setNativeMethodPrefix` method returns `void`; to verify the actual effect of the native wrapper, you must test the transformed class together with the corresponding JNI library.

**A prefix does not automatically apply to all transformers in the JVM.** Each `ClassFileTransformer` has its own prefix; multiple agents can coexist, so choose a sufficiently distinctive name to reduce collisions, test the transformation order properly, and avoid accidentally recreating the transformer.

## 4. Runnable Java 17+ example: enabling/disabling capability and configuring prefix

This experiment **does not require JNI or libraries outside the JDK**. It clearly verifies: manifest with/without the flag; `isNativeMethodPrefixSupported()` result; error before registration; setting and then disabling the prefix. The transformer in the demo **does not modify bytecode**, so there is no actual native wrapper. This is an **API/capability** test, not a test of forwarding to JNI.

Create five files in the **same directory**, compiled with JDK 17+.

**File `PrefixNoopTransformer.java`**

~~~java
import java.lang.instrument.ClassFileTransformer;

public final class PrefixNoopTransformer implements ClassFileTransformer {
    // Demo: does not modify bytecode. Java 17 has default transform methods.
}
~~~

**File `PrefixProbeAgent.java`**

~~~java
import java.lang.instrument.Instrumentation;

public final class PrefixProbeAgent {
    public static void premain(String options, Instrumentation inst) {
        boolean supported = inst.isNativeMethodPrefixSupported();
        System.out.println("native-prefix-supported=" + supported);

        if (!supported) {
            System.out.println("set-prefix-skipped");
            return;
        }

        PrefixNoopTransformer transformer = new PrefixNoopTransformer();
        try {
            inst.setNativeMethodPrefix(transformer, "$probe$");
            System.out.println("unexpected-success");
        } catch (IllegalArgumentException expected) {
            System.out.println("unregistered-transformer=IllegalArgumentException");
        }

        inst.addTransformer(transformer);
        try {
            inst.setNativeMethodPrefix(transformer, "$probe$");
            System.out.println("prefix-configured");
            inst.setNativeMethodPrefix(transformer, "");
            System.out.println("prefix-disabled");
        } finally {
            System.out.println("transformer-removed=" + inst.removeTransformer(transformer));
        }
    }
}
~~~

In production code, you should not intentionally call `setNativeMethodPrefix` before registration. That snippet is only meant to demonstrate `IllegalArgumentException`. The `finally` block removes the transformer that the demo installed; for a real agent, you only remove it when the feature needs to stop.

**File `PrefixApp.java`**

~~~java
public final class PrefixApp {
    public static void main(String[] args) {
        System.out.println("application-main");
    }
}
~~~

**File `enabled.mf`**

~~~text
Manifest-Version: 1.0
Premain-Class: PrefixProbeAgent
Can-Set-Native-Method-Prefix: true
~~~

**File `disabled.mf`**

~~~text
Manifest-Version: 1.0
Premain-Class: PrefixProbeAgent
~~~

In the example, `disabled.mf` omits the flag, so it defaults to `false`. If you want to simulate an explicitly disabled configuration, replace it with `Can-Set-Native-Method-Prefix: false`.

### Compile, package, and run

~~~bash
javac --release 17 PrefixNoopTransformer.java PrefixProbeAgent.java PrefixApp.java

jar --create --file enabled-agent.jar --manifest enabled.mf PrefixProbeAgent.class PrefixNoopTransformer.class
jar --create --file disabled-agent.jar --manifest disabled.mf PrefixProbeAgent.class PrefixNoopTransformer.class

java -javaagent:enabled-agent.jar PrefixApp
java -javaagent:disabled-agent.jar PrefixApp
~~~

**Both `PrefixProbeAgent.class` and `PrefixNoopTransformer.class` must be packaged** in the agent JAR. To verify you are running the right file, use `jar --list --file enabled-agent.jar`. The `Premain-Class` name in the manifest must match the packaged class.

With **HotSpot/OpenJDK supporting the capability** and the `enabled-agent.jar` JAR, stdout:

~~~text
native-prefix-supported=true
unregistered-transformer=IllegalArgumentException
prefix-configured
prefix-disabled
transformer-removed=true
application-main
~~~

With `disabled-agent.jar`, stdout:

~~~text
native-prefix-supported=false
set-prefix-skipped
application-main
~~~

These results were verified by compiling with `--release 17` and running on OpenJDK 24. If another JVM does not support native prefix even when the manifest is `true`, the `supported=false` branch will be executed; **that is a valid result** according to the API, not a Java syntax error.

Explanation:

- `isNativeMethodPrefixSupported()` reflects both the JVM and the declared manifest.
- When supported, calling `setNativeMethodPrefix` before `addTransformer` throws `IllegalArgumentException` as expected.
- After `addTransformer`, the API accepts `"$probe$"`; the empty string in the subsequent call disables the retry mechanism for that transformer.
- `removeTransformer` returns `true` because the transformer was registered. It does not mean any native method was instrumented.
- `application-main` indicates that `premain` finished normally and then the JVM ran the application.

If you want to further test a controlled unsupported error, you can call `setNativeMethodPrefix` in an agent where `isNativeMethodPrefixSupported()` is `false` and catch `UnsupportedOperationException` specifically; **do not do that in production code** because it only produces a pre-reported error.

## 5. How does the JVM perform native method resolution with a prefix?

The two common JNI linking paths share the same goal but differ in how names are looked up. Both start from **normal lookup failing**, and then try the prefix rule, rather than always forcing every native call to switch to a different symbol.

### 5.1. JNI automatic name resolution

Suppose the transformer has created the method pair:

~~~java
public long read(long key) {
    return $observe$read(key);
}

private native long $observe$read(long key);
~~~

This code only illustrates two methods **in the same class** after transformation. If the library has already exported a JNI name corresponding to the original `read`, the JVM first tries normal resolution for `$observe$read`. When it cannot find it, it can strip `$observe$` using the registered prefix and retry as `read`. As a result, the program has a Java wrapper while still being able to call the original native implementation.

Do not infer that renaming in Java means having to edit `JNI_OnLoad`, rename `.dll`/`.so` libraries, or recompile every C symbol. The prefix mechanism is a **fallback for native method linking**, not a replacement for `System.loadLibrary`.

### 5.2. JNI `RegisterNatives`

A native library might not rely on automatic symbol lookup and instead register mappings using `RegisterNatives`, for example intending:

~~~text
method read(long)  ->  nativeFunctionRead
~~~

After the transformer turns the native method into `$observe$read`, the prefix rule allows the JVM to try the corresponding mapping with:

~~~text
method $observe$read(long)  ->  nativeFunctionRead
~~~

This is a mapping diagram, **not standalone compilable C code**. The registration mechanism must still match parameter types, return type, class, loading, and JNI rules. If the symbol or mapping differs in reality, `setNativeMethodPrefix` cannot synthesize a missing native implementation.

### 5.3. Multiple wrapper layers

A method `foo` can be wrapped sequentially by two or more transformers. Each transformer uses its own prefix, for example:

~~~text
foo
  -> $trace$foo                 (transformer A)
  -> $metrics$$trace$foo        (transformer B)
~~~

The JVM uses the sequence of transformer prefixes and considers the existence of intermediate wrappers so it can find the right native implementation. If transformer B skips a particular method, you should not assume that prefix B is still added for that method. This is why the API documentation requires **each transformer to have its own prefix**, and when multiple agents operate together you must test the actual chain.

Setting an overly generic prefix like `"wrapped_"` may collide with methods that already exist in the application; a long and distinctive prefix like `"$$$ExampleTraceAgentNative$$$_"` reduces that possibility. The retry rule only activates **when standard resolution fails**, so unwrapped methods can still use JNI normally.

## 6. Limitations when bringing the feature into a real agent

A working architecture needs **both parts**:

1. A `ClassFileTransformer` that generates valid bytecode and **wraps** the native method with a corresponding Java method. In practice, a class file manipulation library appropriate for the JVM version is usually used, rather than manual byte manipulation.
2. `setNativeMethodPrefix` helps the renamed native method re-link to the original JNI implementation via the retry mechanism.

From this arise several limitations:

- **Timing of class definition:** wrapping a native method by adding a wrapper, renaming, and modifying modifiers is a form of method structure change. Design the transformer to apply **before the class is first defined**. `retransformClasses`/`redefineClasses` on already-loaded classes have strict limitations (you cannot arbitrarily add/remove methods or change signatures/modifiers). Declaring `Can-Retransform-Classes: true` does not remove those limitations.
- **Not every agent needs a prefix:** if the job only logs at class load time, instruments normal Java methods, or uses another approach that does not create a Java wrapper around `native` methods, there is no need to request the capability.
- **The actual JNI must still exist:** a class can still encounter `UnsatisfiedLinkError` due to an unloaded library, wrong symbol, wrong native signature, mismatched CPU architecture, or `RegisterNatives` failure. Prefix does not cure these errors.
- **Preserving semantics:** the wrapper must preserve return values, exceptions, `static`/instance invocation, synchronization, and side-effect ordering. Pay attention to overloads, native methods with complex signatures, mangled JNI symbol names, and different class loaders.
- **Safe initialization:** with `-javaagent`, an unhandled error in `premain` can prevent the JVM from starting. If native prefix is a required feature, report a clear capability error; if optional, you can disable that feature specifically before registering the transformer and log an observable status.
- **Instrumentation overhead:** the wrapper introduces an extra Java call and instrumentation processing; you must measure overhead and avoid recursion when the agent touches APIs that it instruments itself.
- **Multi-agent ecosystem:** determine transformer order, duplicate prefixes, presence of intermediate wrappers, and compatibility between tools. Successfully setting a prefix does not prove the native call chain runs properly.
- **Cleanup:** `setNativeMethodPrefix(transformer, null)` or `""` disables the retry rule for the transformer; `removeTransformer` unregisters future callbacks, but does not automatically restore already-modified class definitions. Do not assume changing the prefix or removing the transformer can revert all previously transformed classes.

## 7. Debugging by symptom

| Observation | Likely cause | How to check |
| --- | --- | --- |
| `isNativeMethodPrefixSupported() == false` | Missing/incorrect `Can-Set-Native-Method-Prefix` in manifest or VM does not support it | Open the **deployed JAR**, read `META-INF/MANIFEST.MF`, compare JDK/JVM implementations |
| `UnsupportedOperationException` at `setNativeMethodPrefix` | Configuration does not allow setting native prefix | Check capability **before the call** and confirm the right agent JAR |
| `IllegalArgumentException` at `setNativeMethodPrefix` | Transformer instance not yet registered | Keep the same instance, call `addTransformer` first; avoid creating a new transformer when setting |
| `NullPointerException` when passing transformer | Passed `null` as the first argument | Check the transformer object; `null` in the **prefix parameter** has a different meaning |
| Wrapper not observed to be used | Transformer did not apply to the class, class was already loaded, or returned `null`/unchanged bytes | Log class name, loader, `transform` timing; inspect the transformed class |
| `UnsatisfiedLinkError` at native wrapper | Prefix does not match method name, missing JNI library/symbol, wrong signature, or resolution still cannot find it | Check method name after transform, registered prefix, native mapping/symbol, and library loading |
| With two or more agents, native linking differs from expected | Transformer/prefix chain changed order or name collision | Record registration order, class bytes after each transformation, and intermediate wrappers |
| `NoClassDefFoundError`/`ClassFormatError`/`VerifyError` on class load | Transformer generated invalid bytes or missing dependency | Test generated bytecode with the actual JDK; read the root cause and class file format |

**Short workflow to verify the feature:** open the actual manifest → call `isNativeMethodPrefixSupported()` → record the registered transformer instance → set a prefix matching the generated bytecode → verify method names and wrapper after transformation → load the right JNI library → run an actual native test. Do not use a `"prefix-configured"` log as proof that native instrumentation succeeded.

## 8. Common misconceptions

- **"Setting `Can-Set-Native-Method-Prefix: true` is enough to turn `native` into a Java method."** False. The manifest requests the capability; the transformer still has to generate the wrapper.
- **"`isNativeMethodPrefixSupported()` indicates the JVM has found the JNI library."** False. It only reflects the ability to configure native prefixes, not checking libraries or symbols.
- **"`setNativeMethodPrefix` renames the JNI symbol on disk."** False. It adjusts **the retry rule when resolution fails**; it does not compile or modify DLL/SO files.
- **"You can set a prefix for any unregistered transformer."** False. The transformer must be registered via `addTransformer` using that exact object.
- **"`prefix = null` will cause `NullPointerException`."** False: a **`null transformer`** causes that error; `null`/empty in **prefix** disables the transformer's retry rule.
- **"Every native method is wrapped automatically."** False. The agent only instruments classes/methods that the transformer actually transforms properly.
- **"You can add a native method wrapper after the class is loaded using only `retransformClasses`."** You cannot arbitrarily change class structure during retransformation; create the wrapper at initial class definition.
- **"`Can-Set-Native-Method-Prefix`, `Can-Retransform-Classes`, and `Can-Redefine-Classes` are the same flag."** False. These are independent capabilities.
- **"The API experiment reporting `prefix-configured` proves a native method was instrumented."** False. The demo above intentionally uses a transformer that does not modify bytecode; an end-to-end JNI test needs a native library and a transformer that generates a real wrapper.

**Remember by the chain of conditions:**

~~~text
Agent manifest requests Can-Set-Native-Method-Prefix: true
         +
Actual JVM supports it
         |
         v
isNativeMethodPrefixSupported() == true
         |
         v
addTransformer(transformer)
         |
         v
setNativeMethodPrefix(transformer, "$unique$")
         |
         v
Transformer generates Java wrapper and renames native method when class is defined
         |
         v
Standard native resolution fails -> JVM retries using prefix
         |
         v
If a valid JNI implementation exists, the Java wrapper can call the original native logic
~~~
