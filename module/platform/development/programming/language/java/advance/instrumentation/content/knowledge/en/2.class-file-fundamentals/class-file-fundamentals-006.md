# Jump Labels, Exception Table, and StackMapTable in a JVM Class File

When reading or modifying bytecode with instrumentation tools, three components must align: **control-flow jump targets**, **exception-catching ranges**, and **the type state expected by the bytecode verifier**. A single wrong offset or stack frame can cause a class to be rejected with `VerifyError` or `ClassFormatError`, even if the original Java source code is valid.

After this lesson, you will be able to read the `Code`, `Exception table`, and `StackMapTable` sections in `javap -v` output; explain the relationship between labels, PC offsets, handlers, and frames; and know how to keep bytecode valid when inserting instructions with ASM.

## 1. Where Are the Three Components Located?

A method with bytecode (other than `abstract` or `native` methods) carries a `Code` attribute inside its `method_info` structure. Simplified layout:

~~~text
method_info
└── Code
    ├── max_stack                 maximum operand stack depth
    ├── max_locals                number of local variable slots
    ├── code[]                    sequence of JVM instruction bytes
    ├── exception_table[]         protected regions and handlers
    └── attributes[]
        ├── StackMapTable         type state for the verifier
        ├── LineNumberTable?      source line mapping (if present)
        └── LocalVariableTable?   variable debug info (if present)
~~~

**Three distinct concepts:**

| Component | Question It Answers | Form |
|---|---|---|
| Jump label (*label*) | Where will a branch instruction go? | Name/symbol in an assembler or bytecode library; resolved to an offset when writing the class file |
| `exception_table` | If an exception occurs in a given region, which handler does it transfer to? | Table of `[start_pc, end_pc)` ranges with `handler_pc` and `catch_type` in `Code` |
| `StackMapTable` | At key control points, what types must locals and the operand stack have? | `stack_map_frame` entries inside `Code.attributes` |

**PC/bytecode offset** counts **bytes from the start of the `code[]` array**, not instruction ordinal numbers, Java source lines, or positions in the entire `.class` file. JVM instructions vary in length, so two adjacent instructions do not necessarily have offsets differing by 1.

## 2. Jump Labels and Control Flow

In Java code, `if`, `while`, `for`, `switch`, `break`, and `continue` create different execution paths. In bytecode, the JVM executes branch instructions to an offset:

- `ifeq`, `ifne`, `iflt`, `ifge`, `if_icmp*`, `if_acmp*`, `ifnull`, `ifnonnull`: conditional jumps; if the condition is false, execution continues with the next instruction.
- `goto` and `goto_w`: unconditional jumps. `goto` uses a 16-bit signed offset; `goto_w` uses 32 bits.
- `tableswitch` and `lookupswitch`: multiple jump targets, including a default branch; their format includes alignment padding bytes, so changing code length can shift offsets.
- `return`, `ireturn`, `areturn`, `athrow`: terminate the current path accordingly; they are not labels.

In the class file representation, the operand of jump instructions is usually a **signed offset relative to the first byte of the jump opcode itself**. `javap -c` displays the **absolute target offset** for readability. For example, an instruction at offset 1 printed as `1: ifge 6` has an encoded offset of `6 - 1 = +5`, not `6 - offset of the next instruction`.

A `Label` in ASM marks a **position**: `visitLabel(target)` defines where instructions referencing the label will point; by itself, it **does not emit an opcode**. Multiple labels can point to the same position. When emitting bytecode, the assembler recalculates offsets and adjusts branch widths if needed. A jump target must be **the start of a valid opcode**, never the middle of another instruction's operands.

A common point of confusion: `LineNumberTable` is for debugging and source line mapping; it does not define jump targets. Label names generated by a disassembler are also not stored verbatim in the class file.

## 3. Exception Table: Protected Ranges and Handler Entry Points

Each entry in `Code.exception_table` has four fields:

| Field | Meaning | Key Constraint |
|---|---|---|
| `start_pc` | First byte of the protected region | Offset of an opcode; inclusive |
| `end_pc` | End of the protected region | **Exclusive**; must be the start of an opcode or equal to `code_length` |
| `handler_pc` | Offset of the handler's first opcode | Must point to an opcode within `code[]` |
| `catch_type` | Index into `CONSTANT_Class_info` describing the exception type | Non-zero: catches that type and its subclasses; zero: catches all exceptions |

Core invariant: `0 <= start_pc < end_pc <= code_length`, and `handler_pc < code_length`. All fields are byte offsets, not labels or source line numbers.

Suppose an entry has the range `[6, 10)`. An exception thrown by an instruction at offset 6, 7, 8, or 9 can match; **offset 10 does not**, even if offset 10 is the handler itself.

When an instruction throws an exception, the JVM checks entries **in the exact order they appear in the table**. The first entry satisfying both conditions is selected: the throwing instruction's offset falls within the protected range and the exception type matches `catch_type` (or `catch_type = 0`). Therefore, handler order is critical when protected ranges or caught types overlap. If no entry matches, the exception propagates up to the caller method.

Upon entering a handler, the execution thread's operand stack is reset to contain only **a single reference to the exception being handled**. A handler typically starts with `astore` to save that reference into a local; the verifier must know the valid reference type at the handler entry point.

In bytecode, `try`/`catch` has no dedicated opcode: **the exception table + handler instructions** represent them. For `finally`, the compiler may generate a cleanup block used by both the normal path and a catch-all handler (`catch_type = 0`, followed by `athrow` to rethrow). `try-with-resources` also generates resource-closing logic and *suppressed exceptions*; you should not infer the full Java structure from a single entry alone.

**Do not confuse `exception_table` with the `Exceptions` attribute:** `Exceptions` lists the checked exceptions declared in the `throws` signature; `exception_table` is what governs catching and control transfer at runtime. The JVM also relies on this table to catch unchecked exceptions when a matching handler exists.

## 4. StackMapTable: Type Contracts at Control-Flow Merge Points

A **type frame** describes two states at a bytecode location:

1. **Locals:** the verifier type of each local variable/slot that is still meaningful at that point.
2. **Operand stack:** the types currently on the operand stack, in exact order and count.

Branches can converge at the same offset. The verifier must ensure that all paths reaching that point carry compatible states: for example, the same operand stack height, values on the stack matching the next instruction, and locals read afterward being initialized with valid types. If one path brings an `int` and another brings an object reference to an instruction expecting an `int`, the class will be rejected even if the code might only execute a specific branch.

`StackMapTable` stores **frames at the required offsets**, rather than snapshots at every instruction. Branch targets, `switch` targets, and handler entry points are the specific locations that must be considered. **The method's initial frame is implicit**, derived from its descriptor and method flags: instance methods have `this`; static methods have only parameters. In a constructor, `this` initially has the `uninitializedThis` state until a suitable initialization call completes. The operand stack is initially empty.

From class file version **50.0 onward** (Java 6+), if a `Code` attribute has no `StackMapTable`, the JVM treats it as an implicit frame table with **0 entries**. This does **not** mean you can delete all frames from a method with multiple branch targets: the bytecode must still satisfy the corresponding verification rules. A `Code` attribute can have at most one `StackMapTable` attribute.

### 4.1. Types Used by the Verifier

The `verification_type_info` variants include `Top`, `Integer`, `Float`, `Long`, `Double`, `Null`, `UninitializedThis`, `Object`, and `Uninitialized(offset)`.

- `Integer` represents the type-checking state of `int` as well as `boolean`, `byte`, `char`, and `short` values on the operand stack.
- `Object` references a type via the constant pool; `Null` represents the `null` reference.
- `Long` and `Double` occupy **two slots** in the JVM model; the frame format has specific rules when encoding two-slot values.
- `Uninitialized(offset)` tracks an object just created with `new` that has not yet been validly initialized via `<init>`; it cannot be treated as an initialized reference.

These types are used for **data-flow verification**, not as a list of variable names. `LocalVariableTable`, if present, is debug metadata distinct from `StackMapTable`.

### 4.2. Compressed Frame Formats

| Frame Format | Primary Meaning |
|---|---|
| `same_frame` | Same locals as previous frame, empty operand stack |
| `same_locals_1_stack_item_frame` | Locals unchanged, stack has exactly one type |
| `same_locals_1_stack_item_frame_extended` | Same as above, but uses an extended delta field |
| `chop_frame` | Drops a number of trailing locals compared to the previous frame |
| `append_frame` | Appends a number of trailing locals compared to the previous frame |
| `same_frame_extended` | Locals unchanged and empty stack, using an extended delta |
| `full_frame` | Explicitly records all locals and operand stack entries |

Instead of storing an absolute offset for each frame, `StackMapTable` encodes `offset_delta`:

- **First explicit entry:** `offset = offset_delta`.
- **Subsequent entries:** `offset = previous_offset + offset_delta + 1`.

For example, if there is a frame at offset 6 and then at offset 10, the second frame's delta is `10 - 6 - 1 = 3`. For short frame formats, the `frame_type` value itself encodes the delta; for instance, `same_frame` with delta 6 has `frame_type = 6`, while `same_locals_1_stack_item_frame` with delta 3 has `frame_type = 64 + 3 = 67`.

**A frame with the right offset but wrong types is still invalid.** Adding a `dup`, `astore`, `new`, or changing a branch can alter both stack height and types at a merge point. `max_stack` and `max_locals` must be accurate, but they **do not replace** updating `StackMapTable`.

## 5. Practice with Java 17+: Generating a Class File to Inspect the Three Components

Save the following standalone program as `BytecodeFlowDemo.java`:

~~~java
public final class BytecodeFlowDemo {
    static int safeDivide(int numerator, int denominator) {
        if (numerator < 0) {
            return -2;
        }
        try {
            return numerator / denominator;
        } catch (ArithmeticException ex) {
            return -1;
        }
    }

    public static void main(String[] args) {
        System.out.println(safeDivide(8, 2));
        System.out.println(safeDivide(8, 0));
        System.out.println(safeDivide(-3, 0));
    }
}
~~~

Compile with JDK 17 or newer and run:

~~~bash
javac --release 17 BytecodeFlowDemo.java
java BytecodeFlowDemo
javap -v -c -p BytecodeFlowDemo
~~~

The stdout of `java BytecodeFlowDemo` is:

~~~text
4
-1
-2
~~~

Explanation: `8 / 2` returns `4`; `8 / 0` throws `ArithmeticException` and the handler returns `-1`; with `numerator = -3`, the `if` branch returns `-2` **before** the division is executed, so no exception occurs.

In the `javap` output, locate the `safeDivide(int, int)` method and inspect:

- `Code:` shows bytecode offsets on the left margin. `ifge`/an equivalent branch instruction jumps into the computation branch; there are no named labels like in source code.
- `Exception table:` will have an entry protecting the division section and pointing to the handler catching `java/lang/ArithmeticException`; check `from`, `to`, and `target`.
- `StackMapTable:` shows the frames at the branch target and handler. At the handler, the stack holds the matching exception reference. Frame compression, constant pool indices, and exact offsets may vary across `javac` versions; **read the numbers just produced by the tool**, rather than copying an assumed offset.

`javap -v` also displays **major version 61** when compiled with `--release 17`. If local variable names or line numbers are missing, debug info may not have been emitted; the exception table and verifier rules still apply independently.

## 6. Reading a Bytecode Example with Explicitly Chosen Offsets

Consider a **hand-crafted illustrative bytecode** for a static method taking two `int`s: if the first argument is negative, return `-1`; otherwise divide the two numbers, returning `0` if dividing by 0. This is not a claim about the exact offsets `javac` emits.

~~~text
Offset  Instruction  Meaning
0       iload_0      push a onto stack
1       ifge 6       if a >= 0, jump to offset 6
4       iconst_m1    a < 0 branch: push -1 onto stack
5       ireturn      return -1
6       iload_0      start of try region
7       iload_1
8       idiv         may throw ArithmeticException
9       ireturn
10      astore_2     start of handler: pop exception from stack
11      iconst_0
12      ireturn

Exception table:
From  To  Target  Type
6     10  10      java/lang/ArithmeticException
~~~

**Verifying the links:**

1. `ifge` at offset 1 jumps to **6**; the encoded offset is `+5`. The fall-through branch proceeds to offset 4.
2. The protected range **`[6,10)`** includes `idiv` at 8 but excludes the handler at 10.
3. When `idiv` throws `ArithmeticException`, the JVM pushes the exception reference onto the operand stack and jumps to `10: astore_2`.
4. The two corresponding explicit frames can be encoded as follows (initial locals are `[int, int]`):
   - Frame at **6**: `same_frame`, `offset_delta = 6`, empty stack, `frame_type = 6`.
   - Frame at **10**: `same_locals_1_stack_item_frame`, `offset_delta = 3`, stack contains `Object(java/lang/ArithmeticException)`, `frame_type = 67`.
5. `max_stack = 2` is enough for the two operands before `idiv`; `max_locals = 3` is enough for the arguments in slots 0/1 and the exception in slot 2.

If a new instruction is inserted before offset 6, branch offsets, exception-catching ranges, and frames may all shift together. Updating only the `ifge` target while leaving the other two structures untouched is a common cause of broken class files.

## 7. Instrumenting with ASM

ASM provides `org.objectweb.asm.Label` to represent positions and visitors to build or modify methods. The following snippet is **part of an ASM bytecode generator**, not a standalone Java program: it assumes you already have a `ClassWriter cw`, have declared the class, and are generating the method `static int divideOrZero(int, int)` with descriptor `(II)I`.

~~~java
MethodVisitor mv = cw.visitMethod(
        Opcodes.ACC_PUBLIC | Opcodes.ACC_STATIC,
        "divideOrZero", "(II)I", null, null);

Label start = new Label();
Label end = new Label();
Label handler = new Label();

mv.visitCode();
// Declare the catch range before visiting the referenced labels.
mv.visitTryCatchBlock(
        start, end, handler, "java/lang/ArithmeticException");

mv.visitLabel(start);
mv.visitVarInsn(Opcodes.ILOAD, 0);
mv.visitVarInsn(Opcodes.ILOAD, 1);
mv.visitInsn(Opcodes.IDIV);

mv.visitLabel(end);                // end is exclusive
mv.visitInsn(Opcodes.IRETURN);     // success path

mv.visitLabel(handler);            // handler receives 1 exception on stack
mv.visitVarInsn(Opcodes.ASTORE, 2);
mv.visitInsn(Opcodes.ICONST_0);
mv.visitInsn(Opcodes.IRETURN);

mv.visitMaxs(0, 0);                // ASM computes these if COMPUTE_FRAMES is set
mv.visitEnd();
~~~

To recompute frames for generated/modified methods, configure the writer upfront, for example:

~~~java
ClassWriter cw = new ClassWriter(ClassWriter.COMPUTE_FRAMES);
~~~

`COMPUTE_FRAMES` recomputes `StackMapTable` and **also** implies `COMPUTE_MAXS`; if you only use `COMPUTE_MAXS`, ASM computes stack/locals limits but **does not fix wrong or missing frames**. Frame computation requires knowing inheritance relationships between object types; the default `getCommonSuperClass` implementation may load classes. For agents/custom class loaders or transforming classes not yet on the classpath, configure an appropriate hierarchy lookup strategy rather than guessing every type is `java/lang/Object`.

A controlled method modification workflow:

1. Read the existing **version**, descriptor, branches, exception handlers, and frames.
2. Place labels at **opcode boundaries**; determine clearly whether inserted instructions sit inside or outside a `try` region. ASM requires `visitTryCatchBlock` to be called before the referenced labels have been visited.
3. Preserve the precedence order of overlapping handlers; avoid letting a broad handler accidentally swallow exceptions or alter `finally` paths.
4. Recompute branches, `max_stack`, `max_locals`, and frames according to the final bytecode. If maintaining frames manually, update both offsets and type states at all control-flow target points.
5. Inspect the transformed class with `javap -v -c -p` and test loading/running it with the verifier. When using ASM, `CheckClassAdapter` can help catch structural/analysis errors before runtime.

When transforming constructors, avoid inserting operations that use `this` as a fully initialized object before a valid constructor invocation. When inserting code into `try`/`finally`, remember that **exceptions thrown by the inserted code itself** may be caught by an existing handler; that is a behavioral change worth considering even if the class passes the verifier.

## 8. Diagnosing Common Errors

| Symptom | Possible Cause | How to Check |
|---|---|---|
| `VerifyError: Expecting a stackmap frame at branch target ...` | Added/moved a branch target without a matching frame | Cross-check the target in `javap -c` against frame offsets in `javap -v` |
| `VerifyError: Bad type on operand stack` | Two converging paths have incompatible stack types; or a local is used without the right type | Trace the push/pop effect of each opcode and local states at the frame |
| `ClassFormatError` related to the exception table | `start_pc`, `end_pc`, or `handler_pc` has invalid boundaries or exceeds `code_length` | Re-check `[start_pc, end_pc)` and actual opcode start offsets |
| Exception caught by an unexpected `catch` branch | Entry order, caught type, or protected range was altered | Compare handlers in **order of appearance** |
| Runs successfully, but `finally` behaves incorrectly | Code inserted outside/inside the cleanup region, or `return`/`athrow` altered the path | Test both the normal path and the exception path |
| ASM frame computation fails due to class not found | Hierarchy resolution relies on an unsuitable class loader/classpath | Check `getCommonSuperClass` and the class loader used for transformation |

You can run checks with:

~~~bash
javap -v -c -p BytecodeFlowDemo
java -Xverify:all BytecodeFlowDemo
~~~

`-Xverify:all` instructs the JVM to verify bytecode on class load under the active verification policy; testing both exception and non-exception paths is still necessary to confirm **semantics**. A program that passes the verifier is not guaranteed to have the intended behavior.

## 9. Self-Check Exercises

1. Given an entry `[6,10)` and an exception thrown at offset `10`, does that entry catch it? **No**, because `end_pc` is exclusive.
2. Previous frame at offset `6`, next frame at `10`: what is the `offset_delta` of the second frame? **3**, because `10 = 6 + 3 + 1`.
3. Upon entering a `catch (ArithmeticException e)` handler, what is on the operand stack? **A single exception reference** compatible with the catch type, not whatever remained on the stack from the operation in progress.
4. Why can inserting an instruction before `goto` break a class? Because branch targets, handler ranges, frames, and stack states may need to be recalculated; labels are only how tools keep references consistent.
5. Is `COMPUTE_MAXS` enough to fix an invalid `StackMapTable`? **No**; you must supply valid frames or recompute them with `COMPUTE_FRAMES` with complete type information.

**Key takeaway:** labels determine **where to go**; `exception_table` specifies **which handler receives exceptions from where**; `StackMapTable` ensures **valid type states at destinations**. Together they describe a single control-flow graph, so instrumentation must treat and verify them as a unified whole.
