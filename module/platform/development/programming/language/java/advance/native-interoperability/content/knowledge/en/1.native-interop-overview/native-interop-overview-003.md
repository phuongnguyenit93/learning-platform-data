# Two Call Directions: Java to Native Functions and Native Functions Calling Back into Java

## 1. Nature of Two-Way Interoperability

Java runs inside the JVM; a native library is typically machine code compiled from C/C++. When integrating, control flow can go in **both directions**:

- **Java → native (downcall):** Java requests a C function to perform work, such as calling a device library, processing data, or using an operating system API.
- **Native → Java (callback/upcall):** During or after processing, C code reports a result, event, or error back to a Java method. A callback can be synchronous on the calling thread or asynchronous on another native thread.

Two common paths are **Java Native Interface (JNI)** and **Foreign Function & Memory API (FFM)**. JNI allows C/C++ code to interact directly with JVM objects, methods, and state via `JNIEnv`. FFM (an official API since JDK 22) allows Java to call C functions according to the ABI and create function pointers for C to call back into a Java `MethodHandle`.

Example of a synchronous flow:

```text
Java: multiplyAndNotify(6, 7)
    │
    ▼  native call
C: computes result 42
    │
    ▼  callback to Java
Java: onNativeResult(42)  → prints message
    │
    ▼  returns to C function
C: return 42
    │
    ▼
Java: receives 42 and continues processing
```

Key point: the **return value** of a C function and a **callback** are two different communication channels. A native function can perform a callback and only then return its result; a callback does not automatically become asynchronous.

## 2. JNI: Complete Java → C → Java Example

The following example runs with **JDK 17+ and GCC on Linux**. The `nativebridge` library multiplies two integers, calls back a Java method to report the result, and then returns the result of the native call itself. All code snippets in this section belong to a single runnable program.

### 2.1. Java Declares the Native Method and Callback

Create `NativeBridge.java`:

```java
public final class NativeBridge {
    static {
        System.loadLibrary("nativebridge");
    }

    // Java -> C: JVM looks up the JNI function exported from the library.
    private native int multiplyAndNotify(int a, int b);

    // C -> Java: the C function will find and invoke this method via JNI.
    private void onNativeResult(int result) {
        System.out.println("Native callback: " + result);
    }

    public static void main(String[] args) {
        NativeBridge bridge = new NativeBridge();
        int result = bridge.multiplyAndNotify(6, 7);
        System.out.println("Java result: " + result);
    }
}
```

`native` only declares the signature; the body resides in the C library. `System.loadLibrary("nativebridge")` instructs the JVM to load the library according to the operating system's naming convention: Linux is typically `libnativebridge.so`, macOS is `libnativebridge.dylib`, and Windows is `nativebridge.dll`. The `onNativeResult` method does not need to be `native`: it is a **normal Java method**, called by C via JNI.

### 2.2. C Performs the Calculation and Calls Back into Java

First use `javac -h .` (in the compilation step below) to generate the `NativeBridge.h` header. Then create `nativebridge.c`:

```c
#include <jni.h>
#include <stdint.h>
#include "NativeBridge.h"

JNIEXPORT jint JNICALL Java_NativeBridge_multiplyAndNotify(
        JNIEnv *env, jobject self, jint a, jint b) {

    // Avoid signed integer overflow in C multiplication.
    jlong wide = (jlong) a * (jlong) b;
    if (wide > INT32_MAX || wide < INT32_MIN) {
        jclass error = (*env)->FindClass(env, "java/lang/ArithmeticException");
        if (error != NULL) {
            (*env)->ThrowNew(env, error, "native result out of int range");
            (*env)->DeleteLocalRef(env, error);
        }
        return 0; // When an exception is pending, Java will receive the exception.
    }
    jint result = (jint) wide;

    jclass cls = (*env)->GetObjectClass(env, self);
    if (cls == NULL) {
        return 0; // The JVM has already set an exception if the operation failed.
    }

    // (I)V: takes an int, returns void.
    jmethodID callback = (*env)->GetMethodID(
            env, cls, "onNativeResult", "(I)V");
    if (callback == NULL) {
        (*env)->DeleteLocalRef(env, cls);
        return 0;
    }

    (*env)->CallVoidMethod(env, self, callback, result);
    (*env)->DeleteLocalRef(env, cls);

    if ((*env)->ExceptionCheck(env)) {
        return 0; // Preserve the Java exception and return to the JVM.
    }
    return result;
}
```

Explanation in execution order:

1. `JNIEXPORT` and `JNICALL` expose the entry point with the appropriate calling convention; `Java_NativeBridge_multiplyAndNotify` is the JNI name corresponding to the class/method in this packageless example. Use the header generated by `javac -h` to avoid writing an incorrect signature.
2. `JNIEnv *env` is the JNI interface **of the current thread**; `jobject self` is the `NativeBridge` object on which the instance method was called. If `native` is `static`, the corresponding parameter is `jclass`.
3. `jint` and `jlong` are JNI types with fixed sizes. The multiplication is promoted to `jlong` before checking the `jint` range to avoid undefined behavior from `int` overflow in C.
4. `GetObjectClass` returns a **local reference** to the class of `self`; `GetMethodID` looks up the instance method by **name and descriptor**. `jmethodID` is a method identifier, not a local reference.
5. `CallVoidMethod` transfers control back to Java. When `onNativeResult` finishes, C resumes execution right after that call. `DeleteLocalRef` frees the local reference created in the native frame.
6. If the callback throws an exception, `ExceptionCheck` detects the pending exception. C does not continue calling arbitrary JNI APIs; when the native method returns, that exception is thrown back to the Java side. `return 0` in the error path only satisfies the C signature, not a successful result.

### 2.3. Compiling and Running on Linux

Place `NativeBridge.java` and `nativebridge.c` in the same directory; configure `JAVA_HOME` to point to the JDK directory (containing `include/jni.h`). Run:

```bash
javac -encoding UTF-8 -h . NativeBridge.java
gcc -fPIC -shared -I"$JAVA_HOME/include" -I"$JAVA_HOME/include/linux" -o libnativebridge.so nativebridge.c
java -Xcheck:jni -Djava.library.path=. NativeBridge
```

`javac -h .` generates `NativeBridge.h` containing the JNI prototype. GCC compiles a shared library loadable by the JVM. `-Djava.library.path=.` tells the JVM to look for libraries in the current directory; `-Xcheck:jni` enables additional checks for certain JNI usage errors.

Standard output when running with `6` and `7`:

```text
Native callback: 42
Java result: 42
```

The print order proves that the callback runs **before** `multiplyAndNotify` returns to Java. On macOS, use the `$JAVA_HOME/include/darwin` include and the appropriate way to build a `.dylib`; on Windows, use the `win32` include, a `.dll` library, and a compatible compiler toolchain. The library name and path must match `System.loadLibrary`.

## 3. How Does JNI Look Up Java Methods?

JNI does not look up methods by a standalone Java name. `GetMethodID` requires the JVM descriptor of the parameters and return type.

| Java Type/Method | JNI Descriptor |
| --- | --- |
| `void callback(int x)` | `(I)V` |
| `void callback(String s)` | `(Ljava/lang/String;)V` |
| `int size(byte[] bytes)` | `([B)I` |
| `long getValue()` | `()J` |

Common rules: `V` = `void`, `I` = `int`, `J` = `long`, `Z` = `boolean`, `Lpackage/Class;` = object, `[` = array. The full descriptor includes the **parameter list in parentheses** and the **return type**. An incorrect descriptor can cause `GetMethodID` to return `NULL` with a pending `NoSuchMethodError`.

Choose the call matching the return type: `CallVoidMethod` for `void`, `CallIntMethod` for `int`, `CallObjectMethod` for objects. For static methods, use `GetStaticMethodID` and `CallStatic...Method`. JNI does not automatically check the validity of all arguments like the Java compiler; the ID, object, signature, and types must match.

## 4. Callbacks on Another Native Thread

The example in section 2 is a **synchronous callback on a Java thread that has entered JNI**, so the JVM has already provided a valid `JNIEnv *`. For callbacks emitted from a thread created by C/C++ itself (such as a thread receiving device events), **thread attachment, references, and lifecycle** must be handled:

1. While still inside a valid JNI call, obtain `JavaVM *` using `(*env)->GetJavaVM(env, &vm)`. You may store `JavaVM *` for thread attachment purposes; **do not store `JNIEnv *` for use on another thread**.
2. If the callback needs to access a Java object after the initial native method returns, create a `global reference` via `NewGlobalRef`. A `jobject` received from a parameter or `GetObjectClass` is typically a local reference: it must not be saved and used after the native frame ends.
3. On the C thread performing the callback, call `GetEnv` to determine whether the thread is already attached to the JVM. If it returns `JNI_EDETACHED`, call `AttachCurrentThread` (or `AttachCurrentThreadAsDaemon` by design) to obtain a `JNIEnv *` dedicated to **that thread**. If attaching fails, do not call JNI.
4. Use the current thread's `JNIEnv *`, a still-live global reference, and a valid `jmethodID` to invoke the callback. Define how raised exceptions are handled, especially when there is no synchronous Java caller to receive the exception.
5. If the C thread itself attached, call `DetachCurrentThread` before the thread exits (when no Java frames remain on the stack). Do not detach a Java thread using JNI just because a callback function has finished.
6. When unregistering the callback or closing the library, synchronize with any currently running callbacks, then call `DeleteGlobalRef` at a valid point. Do not free references or data while a C thread may still use them.

One note when looking up classes: `FindClass` from a self-attached native thread has a different class loader context than a call originating from Java; for application classes, keep a valid class reference or use a chosen class loader rather than assuming `FindClass` can always find it. Callbacks from a separate thread also require a clear shutdown mechanism to avoid calling into Java after the listener or VM has stopped.

**A global reference does not mean immutable or thread-safe**: it only keeps the Java object reachable. Data inside the object still needs appropriate synchronization; callbacks can still race with cancellation or state updates.

## 5. FFM (JDK 22+): Downcalls and Upcalls Without a JNI Function per Entry Point

When integrating **C functions via ABI**, FFM provides a different model:

- `downcallHandle` creates a `MethodHandle` for Java to call a **C function** at a resolved symbol address;
- `upcallStub` creates a **native function pointer** pointing back to a Java `MethodHandle`;
- `FunctionDescriptor` and `ValueLayout` describe the binary signature; `Arena` controls the lifecycle of native resources, including upcall stubs.

This is a standalone example separate from the JNI one above. It uses **JDK 22 or later** with the official `java.lang.foreign` API (no `--enable-preview` required) and GCC on Linux.

### 5.1. C Function Accepting a Callback Pointer

Create `ffmbridge.c`:

```c
typedef void (*callback_t)(int);

int compute_and_notify(int a, int b, callback_t callback) {
    // Example uses small inputs, within the int range.
    int result = a * b;
    if (callback != 0) {
        callback(result); // C calls the function pointer of the Java upcall stub.
    }
    return result;
}
```

The library accepts a function pointer with signature `void (*)(int)`. C knows nothing about Java classes, `JNIEnv`, or `jmethodID`; it simply calls the pointer according to the agreed ABI. In a real system, input ranges and error reporting must be defined rather than letting C `int` multiplication overflow.

### 5.2. Java Creates the Downcall Handle and Upcall Stub

Create `FfmBridge.java`:

```java
import java.lang.foreign.Arena;
import java.lang.foreign.FunctionDescriptor;
import java.lang.foreign.Linker;
import java.lang.foreign.MemorySegment;
import java.lang.foreign.SymbolLookup;
import java.lang.foreign.ValueLayout;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;

public final class FfmBridge {
    private static void onResult(int value) {
        System.out.println("Native callback: " + value);
    }

    public static void main(String[] args) throws Throwable {
        System.loadLibrary("ffmbridge");

        Linker linker = Linker.nativeLinker();
        SymbolLookup symbols = SymbolLookup.loaderLookup();
        MemorySegment function = symbols.find("compute_and_notify")
                .orElseThrow();

        // C callback: void (*)(int)
        FunctionDescriptor callbackType =
                FunctionDescriptor.ofVoid(ValueLayout.JAVA_INT);

        // C function: int (int, int, callback_t)
        FunctionDescriptor nativeType = FunctionDescriptor.of(
                ValueLayout.JAVA_INT,
                ValueLayout.JAVA_INT,
                ValueLayout.JAVA_INT,
                ValueLayout.ADDRESS);

        MethodHandle target = MethodHandles.lookup().findStatic(
                FfmBridge.class,
                "onResult",
                MethodType.methodType(void.class, int.class));
        MethodHandle downcall = linker.downcallHandle(function, nativeType);

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment callback =
                    linker.upcallStub(target, callbackType, arena);
            int result = (int) downcall.invokeExact(6, 7, callback);
            System.out.println("Java result: " + result);
        }
    }
}
```

`System.loadLibrary` loads the library before `SymbolLookup.loaderLookup()` looks up the C symbol name. `JAVA_INT` represents `int` in the ABI matching the example; `ADDRESS` is the callback pointer parameter. `findStatic` creates a handle to the Java method; `upcallStub` turns that handle into a C-callable address. `invokeExact` requires the Java types to match the handle signature exactly: two `int`s, one `MemorySegment`, and an `int` result.

Compile and run on Linux:

```bash
gcc -fPIC -shared -o libffmbridge.so ffmbridge.c
javac -encoding UTF-8 FfmBridge.java
java --enable-native-access=ALL-UNNAMED -Djava.library.path=. FfmBridge
```

Output:

```text
Native callback: 42
Java result: 42
```

Native access permission must be enabled for the module performing restricted calls (for example `ALL-UNNAMED` for a program running on the classpath). When running in a **named module**, grant permission to that exact module name. Do not confuse `--enable-native-access` with `--enable-preview`: FFM has been official since JDK 22.

### 5.3. Lifecycle and Error Boundaries in FFM

In this example, C calls the callback **synchronously** before `compute_and_notify` returns, so `Arena.ofConfined()` remains alive until the callback completes. If C **stores the callback pointer to call later**, the arena cannot be closed immediately after the downcall; an appropriate arena/lifecycle is needed, managing unregistration, in-flight callbacks, and cross-thread access. Calling the pointer after the stub has been freed can cause a severe crash.

**Do not let exceptions escape an FFM upcall target.** By the contract of `Linker.upcallStub`, an unhandled Java exception at the callback boundary can cause the JVM to terminate abruptly. Callbacks in real applications must catch and handle all errors before returning to C (for example, recording the error in safe state or returning an error code via a defined protocol), rather than relying on C to catch a Java exception.

FFM does not automatically turn an arbitrarily name-mangled C++ function into a C ABI. When calling a C++ library, an `extern "C"` wrapper with explicit types/ABI is usually needed. A `MemorySegment` and a native pointer are also not `jobject`; do not pass the address of an arbitrary Java object to C.

## 6. Choosing JNI or FFM for Two-Way Interoperability

| Criterion | JNI | FFM (JDK 22+) |
| --- | --- | --- |
| Java calls native code | Declare `native`, export JNI function with matching signature | `Linker.downcallHandle` for C ABI functions |
| Native calls back into Java | `GetMethodID` + `Call...Method` on a valid `JNIEnv` | C calls a function pointer from `Linker.upcallStub` |
| Java data | Access `jobject`, arrays, strings via JNI | Prefer C types, `MemorySegment`, and layouts |
| Callback lifecycle | Local/global/weak global references; attach thread when needed | Arena and upcall stub lifetime |
| Typical use cases | Deep JVM integration, SDKs already using JNI, calling Java methods/objects | Calling existing C libraries via ABI and registering function-pointer callbacks |
| Risks to manage | Wrong reference/signature, pending exception, wrong `JNIEnv`/thread | Wrong layout/ABI, expired pointer, exception escaping upcall |

Both APIs step outside pure Java's memory safety boundary. Either API requires defining **who owns resources**, **who is allowed to invoke callbacks**, and **when a callback is no longer valid**. With C++ and Java 17, JNI is the practical choice if native code needs to call Java objects; FFM in its finalized form requires JDK 22+.

## 7. Designing a Safe Callback Contract

Before implementing, settle the following points on both the Java and native sides:

1. **Signature and ABI:** `int/long/pointer` types, calling convention, data widths, string encoding, and return conventions. With JNI, the descriptor must match Java; with FFM, `FunctionDescriptor` must match the C definition.
2. **Synchronous or asynchronous:** Does the callback happen before return or can it arrive later? Can it arrive multiple times, concurrently, or after a cancel call? Is event ordering required?
3. **Calling thread:** Which thread does the callback arrive on; is it allowed to access the UI thread, transactions, or thread-local context? With JNI, native threads outside the JVM must attach properly; do not pass `JNIEnv` across threads.
4. **Ownership and release:** Who holds Java listeners, local/global references, `MemorySegment`s, buffers, and function pointers? On shutdown, stop emitting callbacks before freeing what they use.
5. **Errors and cancellation:** Are there status codes, error callbacks, or exceptions? With JNI there are pending Java exceptions; with FFM, exceptions must be prevented from escaping the upcall. Clearly specify the path when a callback rejects data, times out, or is cancelled.
6. **Reentrancy and locks:** While Java holds a lock and calls C, C may call back into Java or Java may call back into C. Avoid holding locks across uncontrolled callbacks because it easily causes deadlocks; update state according to the chosen synchronization contract.
7. **Data validation:** Check memory region lengths, nulls, buffer capacity, overflow, and encoding at the boundary; do not assume native code automatically guarantees Java type safety.

An often manageable design is to have native code emit **small, strongly typed events**, while Java receives the callback and schedules heavy work onto an appropriate executor if needed. Do not perform long-running I/O inside a callback if the native function is waiting synchronously to complete.

## 8. Common Errors and How to Diagnose Them

| Symptom | Common Cause | How to Check/Fix |
| --- | --- | --- |
| `UnsatisfiedLinkError` on load | Mismatched library name, path, architecture, or native dependencies | Check `System.loadLibrary`, `.so/.dll/.dylib` file, `java.library.path`, JVM architecture, and dependent libraries |
| `UnsatisfiedLinkError` when calling `native` | Missing matching JNI symbol or wrong C signature | Regenerate header with `javac -h`; check package, function name, overloads, and exported symbols |
| `NoSuchMethodError` on JNI callback | `GetMethodID` looks up wrong name, descriptor, or static/instance | Recheck signature `(I)V`; distinguish `GetMethodID` from `GetStaticMethodID` |
| Crash when using reference after return | Storing a local reference/`JNIEnv` past its lifetime or using it from another thread | Use a global reference with cleanup; obtain a separate `JNIEnv` per thread |
| JNI continues failing after callback | Java threw an exception but C keeps making invalid JNI calls | Check `ExceptionCheck`; return to let the exception propagate to Java, or handle and clear intentionally |
| FFM crash/random errors | Wrong `FunctionDescriptor`, ABI, address, or expired callback stub | Cross-check C signature and layout; keep the arena alive for the right lifetime |
| Program terminates when FFM callback fails | Java exception escapes `upcallStub` | Catch all exceptions inside the callback and translate them into a dedicated error-reporting mechanism |
| Hang/corrupted state | Reentrant callback, race on unregister, or holding a lock across a native call | Identify threads and lock ordering; synchronize shutdown; test concurrently |

`-Xcheck:jni` helps detect many JNI mistakes, but does not replace C memory checking or multithreaded testing. Beyond the happy path, test library load failures, callbacks throwing exceptions, listener cancellation, late-arriving callbacks, and data at numeric type boundaries.

## 9. Self-Check Questions

- In the JNI example, why is `NativeBridge.onNativeResult` called **before** the line `Java result: 42` even though both run in Java? Point out the exact JNI call that transfers control.
- If `onNativeResult(int)` is changed to `onNativeResult(long)`, which descriptor must change and what argument type/call must C change?
- If the C library sends a callback from a worker thread after `multiplyAndNotify` has returned, why must the initial `self` or `env` not be retained?
- If FFM C stores `callback` in a global variable and calls it after `try (Arena arena...)` ends, what is the lifecycle issue? How should callback registration/unregistration be redesigned to be safe?
- State the appropriate error propagation mechanism for a failing Java callback in JNI and a failing FFM upcall. Why cannot the same exception handling approach be used?

**Key takeaway:** Java → native and native → Java are two control directions with their own **signatures, threads, lifecycles, and error boundaries**. Synchronous examples explain the mechanism; asynchronous callback systems must add thread attachment, retaining references or stubs, and safe shutdown.
