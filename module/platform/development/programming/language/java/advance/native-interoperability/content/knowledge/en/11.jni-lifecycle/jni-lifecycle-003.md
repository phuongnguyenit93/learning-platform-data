# Registering Methods with RegisterNatives Instead of Name-Based Symbol Lookup

## 1. Goal: Two Mechanisms for Binding a Java Native Method to a C Function

In the **Java Native Interface (JNI)**, a `native` declaration in a Java class only indicates that the method body is implemented by native code. The JVM still needs to know **which native function** corresponds to each Java method. There are two important ways to bind them:

1. **Name-based lookup:** the library exports a function named according to the JNI convention, such as `Java_demo_jni_RegisteredOps_doubleValue`. When a native method needs to be resolved, the JVM searches for the corresponding symbol in the loaded native library.
2. **Explicit registration:** native code calls `RegisterNatives`, passing a table containing the **Java method name, JVM signature, and C function pointer**. The JVM records this mapping; the C implementation functions **do not necessarily have to be named `Java_...` or be publicly exported**.

This lesson focuses on **`RegisterNatives` in the JNI lifecycle**: the shape of `JNINativeMethod`, signatures, registering onto the right `jclass`, the timing of using `JNI_OnLoad`, class loaders, error checking, ABI risks, comparison with name-based lookup, and a Java 17 + C example that can be compiled/run on Linux, macOS, and Windows.

**Do not confuse the two things:** `RegisterNatives` replaces **how the C function for a native method is looked up**, and **does not replace `System.loadLibrary` or `System.load`**. Before code in a library can register methods, that library must still be properly loaded by the JVM.

## 2. Default Binding Mechanism: `Java_...` Symbols

Without explicit registration, a declaration like:

~~~java
package demo.jni;

public final class NamedExample {
    public static native int doubleValue(int value);
}
~~~

can be bound by JNI to a C symbol like:

~~~c
JNIEXPORT jint JNICALL Java_demo_jni_NamedExample_doubleValue(
    JNIEnv *env, jclass clazz, jint value
) {
    (void) env;
    (void) clazz;
    return value * 2;
}
~~~

These are **two illustrative snippets**, not a standalone runnable program (there is no library-loading step or `main` yet).

Because the Java method is `static`, the second hidden JNI argument is `jclass`. If it were an instance native method, that position would be `jobject`. `JNIEXPORT` helps export the symbol, while `JNICALL` selects the platform-appropriate JNI calling convention.

This automatic approach is convenient when learning JNI and is easy to match against headers generated by `javac -h`. However, symbol names become long or hard to read when a class has a package, methods contain underscores/Unicode, nested classes, or many overloads. A single package/name rename can cause the old symbol to no longer match, leading to `UnsatisfiedLinkError` when a call needs to resolve the native method.

**`RegisterNatives` directly solves the mapping problem** using a registration table instead of imposing C naming conventions on every implementation function.

## 3. The RegisterNatives API and JNINativeMethod Structure

Signature from the JNI C API:

~~~c
jint RegisterNatives(
    JNIEnv *env,
    jclass clazz,
    const JNINativeMethod *methods,
    jint nMethods
);
~~~

This is an **explanatory prototype**, not a function we define ourselves; in actual JNI C code it is called via:

~~~c
jint rc = (*env)->RegisterNatives(env, clazz, methods, count);
~~~

Parameters:

| Parameter | Meaning |
|---|---|
| `env` | `JNIEnv *` of the current thread, used on the right thread |
| `clazz` | `jclass` representing the **Java class whose native methods are to be registered** |
| `methods` | Pointer to the `JNINativeMethod` table, must not be `NULL` |
| `nMethods` | Number of elements in the table, must be greater than 0 |

On success, the API returns **`JNI_OK` (= 0)**. On failure, it returns a **negative code**. If an entry points to a method that does not exist or is not declared `native`, JNI may throw **`NoSuchMethodError`**. Never treat a non-zero return value as "partially registered enough to work". With a failing registration table, you should stop initialization and fix the declaration/signature instead of trying to keep running.

JNI structure:

~~~c
typedef struct {
    char *name;
    char *signature;
    void *fnPtr;
} JNINativeMethod;
~~~

This is the shape according to the specification; `jni.h` already declares the type, so **do not copy the typedef** into a real program.

- **`name`:** the **original Java method name**, for example `"addBias"`, **not** `"Java_demo_jni_RegisteredOps_addBias"`.
- **`signature`:** the **full JVM method descriptor**, such as `"(I)I"`: takes one `int`, returns `int`. In a method descriptor, the return type part is required.
- **`fnPtr`:** pointer to a native function with the **correct JNI ABI** for that method, including `JNIEnv *`, the `jobject`/`jclass` receiver, and all declared Java parameters.

According to the specification, the `name` and `signature` strings in the table are **modified UTF-8**. ASCII names and descriptors in the example use ASCII characters, so there are no special encoding issues.

Example with two entries:

~~~c
static JNINativeMethod methods[] = {
    {"addBias",     "(I)I", (void *) add_bias_impl},
    {"doubleValue", "(I)I", (void *) double_value_impl}
};
~~~

This is a snippet; `add_bias_impl` and `double_value_impl` will be fully defined in the hands-on section. Do not mistake the C name in `fnPtr` for the Java name: the mapping is determined by the two strings `name` + `signature` in the same entry.

A C compiler uses type `void *` for the `fnPtr` field per the JNI interface. Representing a function pointer as `void *` is the JNI ABI convention on supported platforms; avoid inventing your own typedefs or calling a function through a mismatched pointer type.

## 4. JVM Signatures: One Wrong Character Means a Different Method

A **method descriptor** has the form:

~~~text
(<parameter descriptors in order>)<return type descriptor>
~~~

Common table:

| Java Type | Descriptor |
|---|---|
| `boolean` | `Z` |
| `byte` | `B` |
| `char` | `C` |
| `short` | `S` |
| `int` | `I` |
| `long` | `J` |
| `float` | `F` |
| `double` | `D` |
| `void` (return) | `V` |
| `String` | `Ljava/lang/String;` |
| `int[]` | `[I` |
| `String[]` | `[Ljava/lang/String;` |

Examples:

| Java declaration | Registered method descriptor |
|---|---|
| `native int addBias(int x)` | `(I)I` |
| `static native int doubleValue(int x)` | `(I)I` |
| `static native void send(String message)` | `(Ljava/lang/String;)V` |
| `native long sum(int[] values)` | `([I)J` |
| `static native String format(int n, String prefix)` | `(ILjava/lang/String;)Ljava/lang/String;` |

The `/` in the descriptor's class name is the **JVM internal separator**, not a Linux or Windows file separator. `String` is written as `Ljava/lang/String;`, not `java.lang.String`. The descriptor `(I)I` **does not include** `JNIEnv *` or the receiver, because those two parameters belong to the JNI C signature, not the declared Java parameters.

**Instance/static cannot be distinguished by descriptor alone.** Both `addBias(int)` and `doubleValue(int)` have `(I)I`, but the instance C function must accept **`jobject self`**, whereas the static one must accept **`jclass clazz`**. `RegisterNatives` cannot fix a C function using the wrong calling convention/parameter types; the mapping only works properly when the function pointer matches the JNI ABI.

### 4.1. Overloading Without JNI Long-Name Mangling

Suppose a class has:

~~~java
public static native int transform(int x);
public static native long transform(long x);
~~~

This is a **standalone snippet**, not part of the hands-on class below. The registration table can describe:

~~~c
static JNINativeMethod overloaded[] = {
    {"transform", "(I)I", (void *) transform_int_impl},
    {"transform", "(J)J", (void *) transform_long_impl}
};
~~~

The two entries have the **same Java name but different descriptors**. There is no need to use long C names with escaped descriptor suffixes like `Java_..._transform__I` and `Java_..._transform__J`, as long as the table is registered properly. The two C functions must also have truly matching return types and parameters: `jint`/`jlong` respectively.

This is especially useful when a class has a complex name, but it does not mean you can register just any regular Java method: **the target must be a method declared `native`**. `RegisterNatives` looks up the method by the name + descriptor pair in the **passed-in class `clazz`**.

## 5. Choosing When to Register in the JNI Library Lifecycle

For a native method to be callable, it must be registered **before the first Java call that needs to execute it**. There are two basic designs.

### 5.1. Registering in `JNI_OnLoad` — Usually Convenient

A native library can export the hook:

~~~c
JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM *vm, void *reserved);
~~~

`JNI_OnLoad` is an **optional hook** that the JVM calls when loading a dynamic library with `System.loadLibrary`/`System.load`. You can use the hook to:

1. Receive `JavaVM *vm` from the JVM; use `GetEnv` to obtain a valid `JNIEnv *` for the loading thread.
2. Use `FindClass` to obtain the exact `jclass` of the class containing the native methods.
3. Prepare the `JNINativeMethod` table and call `RegisterNatives`.
4. Delete the local class reference if it does not need to be kept.
5. On success, return the constant `JNI_VERSION_1_6`; if initialization/registration fails, report failure per the `JNI_OnLoad` contract (for example, return `JNI_ERR`).

Example diagram:

~~~text
JVM initializes class RegisteredOps
  |
  | static { System.loadLibrary("registeredops"); }
  v
JVM loads library registeredops
  |
  v
JNI_OnLoad(JavaVM*, void*)
  |
  +--> GetEnv --> JNIEnv*
  +--> FindClass("demo/jni/RegisteredOps") --> jclass
  +--> RegisterNatives(clazz, methods, 2) --> JNI_OK
  +--> DeleteLocalRef(clazz)
  +--> return JNI_VERSION_1_6
  |
  v
Library loading succeeds
  |
  v
Java calls RegisteredOps.doubleValue(5)
  |
  v
JVM uses the registered function pointer
  |
  v
double_value_impl(env, clazz, 5) --> 10
~~~

`JNI_VERSION_1_6` is the **JNI interface version that the library requires**, **not "Java SE 6" that must be installed**. JDK 17 recognizes this JNI constant. You must include `<jni.h>` and use the proper platform macros.

**Do not confuse `JNI_OnLoad` with the Java static initializer:** the static initializer calls `System.loadLibrary`; during that load process, the JVM calls `JNI_OnLoad`. The hook is a C function exported by the library and is where registration happens; no separate Java native bootstrap method is needed in this model.

### 5.2. Registering from a Native Bootstrap Method

Another option: export one JNI function by name (or an entrypoint that already has a binding mechanism), and Java calls it to perform `RegisterNatives` for the remaining methods. This design can be useful if you need to select a set of functions based on runtime configuration.

However, **there must still be a callable entrypoint** to start registration. If all Java native methods lack symbols/registration and `JNI_OnLoad` does not register them either, calling a method cannot "magically" find a function pointer that was never declared.

Registering in `JNI_OnLoad` ensures that the needed methods are already mapped **before** the first call, and wrong names/signatures are usually caught **early during the load phase**, rather than waiting until a method call triggers `UnsatisfiedLinkError`.

## 6. Complete Example: Java 17 + C, Two Explicitly Registered Native Methods

The example will demonstrate three things:

- An **instance native method** that receives `jobject` and reads each object's own field.
- A **static native method** that receives `jclass`.
- Both C functions have **ordinary names**, are declared `static` in C, and **do not export `Java_...`**; the JVM can still call them thanks to the `RegisterNatives` table executed in `JNI_OnLoad`.

Structure:

~~~text
register-natives-demo/
├── src/
│   └── demo/jni/
│       └── RegisteredOps.java
├── registeredops.c
└── build/
    └── classes/                 (created by javac)
        └── demo/jni/
            └── RegisteredOps.class
~~~

The dynamic libraries `registeredops.dll`, `libregisteredops.so`, or `libregisteredops.dylib` are created in the root directory by the corresponding compiler. **There is no requirement to generate a `Java_...` header to implement the code below**, because the C functions are registered by pointer rather than looked up by exported name.

### 6.1. Java — `src/demo/jni/RegisteredOps.java`

~~~java
package demo.jni;

public final class RegisteredOps {
    static {
        System.loadLibrary("registeredops");
    }

    private final int bias;

    public RegisteredOps(int bias) {
        this.bias = bias;
    }

    public native int addBias(int value);

    public static native int doubleValue(int value);

    public static void main(String[] args) {
        RegisteredOps first = new RegisteredOps(7);
        RegisteredOps second = new RegisteredOps(-2);

        System.out.println("instance A = " + first.addBias(5));
        System.out.println("instance B = " + second.addBias(5));
        System.out.println("static = " + RegisteredOps.doubleValue(5));
    }
}
~~~

Explanation:

- `addBias` is an **instance** method; `first` and `second` have their own `bias` field, so with the same argument `5` they produce different results.
- `doubleValue` is a **static** method; called via the class name, with no implicit `this` instance receiver.
- The `static` block loads the logical library `registeredops` when the class is initialized. Before the first native call occurs, the JVM has already had the chance to call `JNI_OnLoad` and perform registration.
- If loading/registering the library fails, class initialization or the native call cannot succeed; the program must not pretend an implementation exists just because `javac` compiled it.

### 6.2. C — `registeredops.c`

~~~c
#include <jni.h>

/* Instance implementation: the second parameter is jobject self. */
static jint JNICALL add_bias_impl(
    JNIEnv *env, jobject self, jint value
) {
    jclass clazz = (*env)->GetObjectClass(env, self);
    if (clazz == NULL) {
        return 0; /* Pending Java exception if lookup fails. */
    }

    jfieldID field = (*env)->GetFieldID(
        env, clazz, "bias", "I"
    );

    /* clazz is a local reference, no need to keep after GetFieldID. */
    (*env)->DeleteLocalRef(env, clazz);

    if (field == NULL) {
        return 0; /* GetFieldID may leave a Java exception. */
    }

    jint bias = (*env)->GetIntField(env, self, field);
    return value + bias;
}

/* Static implementation: the second parameter is jclass clazz. */
static jint JNICALL double_value_impl(
    JNIEnv *env, jclass clazz, jint value
) {
    (void) env;
    (void) clazz;
    return value * 2;
}

/* Declare Java method -> JVM descriptor -> C function pointer. */
static JNINativeMethod methods[] = {
    {"addBias",     "(I)I", (void *) add_bias_impl},
    {"doubleValue", "(I)I", (void *) double_value_impl}
};

/* The only hook that needs to be exported to register the native implementations. */
JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM *vm, void *reserved) {
    (void) reserved;

    JNIEnv *env = NULL;

    if ((*vm)->GetEnv(
            vm, (void **) &env, JNI_VERSION_1_6
        ) != JNI_OK) {
        return JNI_ERR;
    }

    jclass clazz = (*env)->FindClass(
        env, "demo/jni/RegisteredOps"
    );
    if (clazz == NULL) {
        return JNI_ERR; /* Class lookup failed. */
    }

    jint count = (jint) (sizeof(methods) / sizeof(methods[0]));
    jint rc = (*env)->RegisterNatives(
        env, clazz, methods, count
    );

    (*env)->DeleteLocalRef(env, clazz);

    if (rc != JNI_OK) {
        /* Invalid registration: do not complete loading. */
        return JNI_ERR;
    }

    return JNI_VERSION_1_6;
}
~~~

This is the **complete C file** for the example. There is no function named `Java_demo_jni_RegisteredOps_addBias` or `Java_demo_jni_RegisteredOps_doubleValue`, and the two C implementation functions are declared `static` to keep linkage scope within the translation unit. The JVM still knows how to call them because the `methods` table holds the exact function pointers.

**Details that must match strictly:**

1. `FindClass(env, "demo/jni/RegisteredOps")` uses the **JVM internal name with slashes `/`**, not a dot-separated package name in the C string.
2. `"addBias"` and `"doubleValue"` are the **exact Java names**, with exact casing; do not add the `Java_` prefix.
3. Both Java methods are `int method(int)`, so both descriptors are `"(I)I"`. `static` does not appear in the descriptor.
4. `add_bias_impl(JNIEnv*, jobject, jint)` receives the receiver; `double_value_impl(JNIEnv*, jclass, jint)` receives the class. Registering the wrong receiver type can cause subtle ABI bugs or crashes.
5. `JNINativeMethod.fnPtr` points to the **actual function address**; a method does not automatically bind just because the name/signature strings are right.
6. `RegisterNatives` has its result checked; if it fails, `JNI_OnLoad` does not return a success version.
7. `DeleteLocalRef(clazz)` deletes the **local handle** used for registration. It **does not undo the registered mapping table** and does not remove the class from the JVM. Do not keep `clazz` as a C pointer for later use after the local reference goes out of scope.
8. `GetFieldID` retrieves the instance field `bias` with descriptor `I`. If the field is not found, it may leave a pending exception, and the instance function returns so the JVM can handle the exception.
9. The implementation functions add/multiply small numbers; in real problems you should consider overflow when crossing the C/Java boundary instead of implicitly assuming all `jint` values behave like Java if C has signed overflow.

**Why not include the header generated by `javac -h`?** That header typically declares C names following the `Java_...` convention for **name-based lookup**. With a registration table, implementations use their own names and must ensure JNI-compatible signatures; `jni.h` is the required header. You can generate the header **for cross-checking**, but it is not necessary to include it or export those `Java_...` names in this example.

### 6.3. Compile Java and Inspect Descriptors

From the root directory `register-natives-demo`:

**Linux/macOS (shell):**

~~~bash
mkdir -p build/classes
javac -d build/classes src/demo/jni/RegisteredOps.java
javap -s -p -classpath build/classes demo.jni.RegisteredOps
~~~

**Windows Command Prompt:**

~~~bat
if not exist build\classes mkdir build\classes
javac -d build\classes src\demo\jni\RegisteredOps.java
javap -s -p -classpath build\classes demo.jni.RegisteredOps
~~~

In the `javap` output, look for the two native methods and the descriptor line `(I)I`. The `javap` output also contains the constructor, field, `main`, and `static initializer`; do not copy the entire output into the `JNINativeMethod` table. Only the **name and descriptor of each native method** need to match.

If you want to use `javac -h` to check declarations, you **can** replace the Java compile command with:

~~~bash
javac -h build -d build/classes src/demo/jni/RegisteredOps.java
~~~

This command additionally generates a header based on the Java declarations; it does not change the binding mechanism of `registeredops.c`. In this hands-on exercise, that header is only a reference tool, **not a prerequisite** for registration to work.

### 6.4. Build the C Library and Run

The `JAVA_HOME` environment variable must point to a JDK 17+ that has an `include` directory. The compiler must produce a library matching the platform, CPU, bitness, and ABI of the **JVM process**. Use only the command set appropriate for your OS.

**Linux (GCC):**

~~~bash
gcc -fPIC -shared \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  registeredops.c -o libregisteredops.so

java -Djava.library.path=. -cp build/classes demo.jni.RegisteredOps
~~~

**macOS (Clang):**

~~~bash
cc -dynamiclib -fPIC \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/darwin" \
  registeredops.c -o libregisteredops.dylib

java -Djava.library.path=. -cp build/classes demo.jni.RegisteredOps
~~~

**Windows (MSVC in Developer Command Prompt, cmd.exe):**

~~~bat
cl /LD /I"%JAVA_HOME%\include" /I"%JAVA_HOME%\include\win32" registeredops.c /Fe:registeredops.dll

java -Djava.library.path=. -cp build\classes demo.jni.RegisteredOps
~~~

The `-Djava.library.path=.` flag must come before the class name so the JVM searches the current working directory for the library. `System.loadLibrary("registeredops")` uses the logical name `registeredops`, without adding `lib` or the `.dll`/`.so`/`.dylib` extension.

**Exact stdout when build, load, and registration succeed:**

~~~text
instance A = 12
instance B = 3
static = 10
~~~

Explanation:

- `first.addBias(5)` reads field `bias = 7` from the first receiver, returning `5 + 7 = 12`.
- `second.addBias(5)` reads `bias = -2` from the second receiver, returning `5 + (-2) = 3`.
- `RegisteredOps.doubleValue(5)` has no instance receiver, returning `5 * 2 = 10`.

The C code only exports the `JNI_OnLoad` hook and does not need to export the two `Java_...` names of the native implementations. That is practical proof that **registration replaces name-based symbol lookup** for the two methods, while **the library is still loaded normally by the JVM**.

## 7. Why Are JNI_OnLoad and Class Loaders Directly Related to RegisterNatives?

### 7.1. FindClass in JNI_OnLoad Uses the Loader of the Class Loading the Library

When calling `FindClass` **from `JNI_OnLoad`**, the JVM selects the **class loader of the class that is loading the native library**. In the example, `RegisteredOps` calls `System.loadLibrary` from its static initializer, so `FindClass("demo/jni/RegisteredOps")` finds the exact class in that loader's context.

This is an important difference compared to `FindClass` on a **newly attached native thread** without an appropriate Java frame: in another context, `FindClass` may search using the **system class loader** and fail to find a class that only exists in a custom loader.

To register properly, you must have the **`jclass` of the actual class**. The same name `demo.jni.RegisteredOps` loaded by two independent class loaders can be **two different Java class identities**. Matching the string name alone does not mean registering for every copy of the class in every loader.

### 7.2. Native Libraries Are Managed per Class Loader

In standard JNI, **a JNI library cannot be loaded into multiple different class loaders simultaneously**. The JVM may throw `UnsatisfiedLinkError` if a JNI library already associated with one loader is loaded again from another loader. This is a mechanism to preserve namespace boundaries and avoid mixing incompatible classes.

Therefore, plugin/hot-reload architectures using multiple loaders must design library loading/registration carefully. Never assume that a single `RegisterNatives` call by class name is a "JVM-wide registration" for every class loader.

### 7.3. When Does Registration Persist and When Is Cleanup Needed?

Registration connects the native methods **of class `clazz`** to the provided C functions. It is not an operation valid for only **a single call**; after registration succeeds, subsequent calls use that mapping for the lifetime of the class/native library.

`JNI_OnLoad` runs **when the library is loaded**, not on every native method call. Therefore, declaring the C table as `static JNINativeMethod methods[]` is appropriate for the example. The C functions that the pointers point to must remain alive and have the correct ABI **for as long as the JVM can still call them**.

If a class loader can be GC'd and the native library unloaded, `JNI_OnUnload(JavaVM*, void*)` is an optional hook to clean up native resources owned by the library. Do not assume GC/unloading happens at a deterministic time. `JNI_OnUnload` also runs in a context where you should not arbitrarily invoke Java callbacks.

### 7.4. UnregisterNatives Is Not a Mandatory Final Step

JNI provides:

~~~c
jint UnregisterNatives(JNIEnv *env, jclass clazz);
~~~

This API returns the class's native methods to the state before they were linked/registered. According to the specification, it **is not recommended for use in normal native code**; it mainly serves special programs that need relinking/reloading.

Do not automatically call `UnregisterNatives` after `RegisterNatives` succeeds or after each Java call: doing so can wipe out the mapping before other calls use it. If you truly implement a dynamic re-registration mechanism, you need **lifecycle synchronization** so function pointers are not altered while other threads are using them.

## 8. Comparing RegisterNatives and Name-Based Symbol Lookup

| Criterion | Name-based symbol lookup | RegisterNatives |
|---|---|---|
| Java declaration | Still declared `native` | Still declared `native` |
| C function name | Follows `Java_package_Class_method...` convention | C name chosen by the author |
| Exporting each implementation | Usually needs to export the exact JNI symbol | Implementations can be `static`/hidden; needs an entrypoint that can perform registration |
| How overloads match | Short/long mangled name with parameter suffix | Pair of `name` + **full method descriptor** |
| Where the mapping is created | JVM looks up the symbol when resolving the native method | Native code proactively calls `RegisterNatives` |
| When a wrong mapping is detected | Usually when the JVM needs to resolve the method | Usually at the registration step if called immediately in `JNI_OnLoad` |
| Class loader dependency | Yes, during load/lookup | Yes, because it registers onto a **specific `jclass`** |
| Ease of debugging | Can inspect the export table and `javac -h` | Must inspect entries, descriptor, function pointer, registration result |
| Main risks | Wrong name/escaping/overload suffix | Wrong descriptor, receiver ABI, non-`native` method, registering on the wrong class |
| Loading the native library | Still required | **Still required** |

Neither should be considered universally better than the other. For small examples with few methods, name-based lookup is simple and intuitive. For libraries with many native methods, stable APIs, or where mapping control is desired, `RegisterNatives` decouples C names from Java names, supports early checking at load time, and can reduce the need to export many symbols.

**Important limitation:** RegisterNatives is not a "sandbox API" or security mechanism. An improperly trusted native library can alter the execution of native methods. Do not register from untrusted sources, do not load binaries without verified provenance, and do not use registration to replace sensitive methods outside the application contract.

## 9. Common Errors

| Symptom | Cause | How to diagnose and fix |
|---|---|---|
| `NoSuchMethodError` during `RegisterNatives` | Wrong `name`, descriptor, class, or method not declared `native` | Cross-check Java source and `javap -s -p`; verify the right `jclass` |
| `UnsatisfiedLinkError` when calling method | Library not loaded, not registered, or name-based lookup also found no symbol | Ensure `JNI_OnLoad` is exported/called and registration returns `JNI_OK` |
| Library load fails right in static initializer | `JNI_OnLoad` returned an invalid version/`JNI_ERR` or dependency load failed | Check results of `GetEnv`, `FindClass`, `RegisterNatives`, and library name |
| `FindClass` cannot find class | Wrong `/` separator, package, loader, or binary not on classpath | Use internal name `demo/jni/RegisteredOps`; check `-cp build/classes` |
| `RegisterNatives` points to wrong C function | Wrong `fnPtr` entry, Java/C signature mismatch | Compare return type, receiver, parameter types, and order in full |
| C receives `jclass` instead of `jobject` for instance | Wrong JNI ABI signature used | Instance → `jobject`; static → `jclass` |
| C crashes/`hs_err_pid...log` | Wrong native pointer/ABI, expired JNI ref, memory error | Review C prototypes, JNI refs; use JNI checks, read native stack |
| OS cannot find `JNI_OnLoad` | Hook not exported or mangled by C++ | Use `JNIEXPORT`/`JNICALL`; for C++ ensure C linkage |
| `NoSuchMethodError` on overload | Descriptor missing `( ... )Return` or wrong parameters picked | Use `javap -s -p`, register each name + descriptor pair |
| Same library loaded from two class loaders | Library bound per class loader | Redesign library/class loader distribution instead of calling `System.loadLibrary` twice |
| Using `JNIEnv *` from another thread | JNI environment is thread-specific | Each native thread must attach properly and obtain its own environment |
| Holding local `jclass` long-term | Local ref does not have library-wide lifetime | If caching, create a global ref and clean up at the appropriate place |

### 9.1. Checking Exported Symbols

**Linux:**

~~~bash
nm -D libregisteredops.so | grep JNI_OnLoad
~~~

**macOS:**

~~~bash

~~~

**Windows (Visual Studio Developer Command Prompt):**

~~~bat

~~~

These commands are examples for inspecting the symbol table; symbol names/decorations may vary by platform/compiler. You need to verify that **`JNI_OnLoad` is the exported entrypoint**. It is not necessary to see `add_bias_impl` or `double_value_impl` in the export table because they are declared `static` and the JVM calls them through function pointers after registration.

HotSpot's `-Xcheck:jni` can help detect some incorrect JNI usages:

~~~bash

~~~

This is a diagnostic mode (not guaranteed to catch every C/ABI bug). If the program runs properly, application stdout still consists of the three lines `instance A = 12`, `instance B = 3`, `static = 10`.

### 9.2. Why Should JNI_OnLoad Failure Be Handled Strictly?

If `FindClass` does not find the target class or `RegisterNatives` returns a negative code, you should not return `JNI_VERSION_1_6` as if initialization succeeded. Doing so lets Java proceed without the proper mapping and only fail later when the method is called.

Returning `JNI_ERR` signals failure during loading. The exact exception/error description Java sees depends on the situation and the JVM; do not assume every error will have the same message. For production applications, log appropriate diagnostics and check for any pending exception before continuing to call more JNI APIs; do not silently clear errors and report false success.

If implementing retry/re-registration, you must distinguish recoverable errors from wrong signatures/configurations. Do not rely on assuming all entries in the table are automatically rolled back if one entry fails: design registration as a consistent set, check the result, and refuse to continue when the state is unsatisfactory.

## 10. When Using C++ Instead of C

JNI has two ways to call the API depending on the language:

~~~c
/* C: JNI functions are accessed through the function pointer table. */
jint rc = (*env)->RegisterNatives(env, clazz, methods, count);
~~~

~~~cpp
// C++: JNIEnv is a wrapper with member methods.
jint rc = env->RegisterNatives(clazz, methods, count);
~~~

These are only **two syntax snippets**, not two complete programs.

With C++, you must ensure `JNI_OnLoad` is exported with **C linkage**, for example:

~~~cpp
extern "C" JNIEXPORT jint JNICALL JNI_OnLoad(
    JavaVM *vm, void *reserved
) {
    // Implement GetEnv, FindClass, RegisterNatives accordingly.
    return JNI_VERSION_1_6;
}
~~~

This snippet **does not register methods yet**, it only illustrates linkage. If `JNI_OnLoad` gets C++ name-mangled into a different symbol name, the JVM may fail to call the expected hook, resulting in missing registration. Implementation functions can be static C++ functions as long as they have the appropriate calling type and are placed into `fnPtr` properly.

If using an instance method of a C++ object as a function pointer, remember that a non-static member function has a hidden C++ receiver and therefore **does not match** the standard JNI callback form. Use a static/free function as the JNI entrypoint, and dispatch to the inner C++ object according to your own design.

## 11. Advanced Design: Multiple Classes and Multiple Methods

### 11.1. Multiple Methods in One Class

You can use the same table for native methods **in the same class `clazz`**, with `nMethods` set to the exact number of elements. Each entry needs its own name, descriptor, and function pointer.

However, if the number of methods is large, you should split the preparation/registration functions for easier review and to avoid name/descriptor mistakes. Registration is part of **runtime linking**, so one wrong entry can cause loading to fail rather than just breaking a rare case.

### 11.2. Multiple Classes in the Same Library

If a library implements native methods for multiple Java classes, you can:

1. Find class A with `FindClass`, register table A onto `jclass A`.
2. Find class B with `FindClass`, register table B onto `jclass B`.
3. Delete local references when done.
4. Only report `JNI_OnLoad` success when **all required registrations** succeed.

Do not pass methods belonging to class B into `RegisterNatives(env, classA, ...)` and expect the JVM to "automatically look in another class". `clazz` is the specific registration scope.

Pay attention to loader visibility and **class initialization order**: inside `JNI_OnLoad`, do not spontaneously invoke Java methods that could lead to recursive class initialization or reloading the library. The example pattern only calls `FindClass` and `RegisterNatives` to avoid unnecessary side effects.

### 11.3. Caching JNI Information After OnLoad

You can cache `jmethodID`, `jfieldID`, or `jclass` to avoid repeated lookups, but you must obey their lifecycles:

- `jclass` returned from `FindClass` is a **local reference**; to keep it across native calls/threads you must create `NewGlobalRef` and release it with `DeleteGlobalRef` when appropriate.
- `jmethodID`/`jfieldID` are not local references; do not call `DeleteLocalRef` on them. Their validity is tied to the corresponding class, so do not use them after the class is unloaded.
- `JNIEnv *` belongs to the **current thread**; do not cache a `JNIEnv *` and share it across threads. `JavaVM *` can be used to attach/get the environment for a thread per the JNI contract.
- Do not let global references unintentionally prevent a class loader from being garbage-collected; if caching a global class, have a release plan.

The simple example in section 6 intentionally **does not cache `jclass`**. The hook finishes registering and deletes the local reference, creating no global resources that need cleanup.

**Conclusion:** `RegisterNatives` is an **active registration** mechanism that maps `name + JVM signature → native function pointer` for a **specific `jclass`**. Using `JNI_OnLoad` enables registration at **library load time**, catches wrong mappings early, and removes the requirement to export each `Java_...` name. However, you must maintain the exact JNI ABI, loader/lifecycle rules, version, reference cleanup, and error checking. Flexible custom C names **do not mean bypassing JNI rules or loading the native library**.
