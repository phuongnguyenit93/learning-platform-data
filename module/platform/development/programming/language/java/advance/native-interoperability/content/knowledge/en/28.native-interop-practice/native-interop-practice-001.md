# Practice Lab: Creating a C Computation Library and Calling the Same Function via JNI and then via FFM

## Objective

This practice lab builds **one** native library in C, containing the computation function `calc_multiply_add(a, b, c) = a × b + c`. That same C function is called from Java through **two paths**:

1. **JNI (Java Native Interface):** Java calls a `native` method; a JNI bridge written in C forwards to `calc_multiply_add`.
2. **FFM (Foreign Function & Memory API):** Java uses `SymbolLookup` to find the symbol `calc_multiply_add` and `Linker.downcallHandle` to call the function address directly, without going through the JNI bridge.

After this lesson, you will create the C and Java files yourself, use `javac -h` to generate the JNI header, compile a `.so`, run both calling methods on the **same input set**, explain each binding layer, and verify the results using an independent calculation. This is a practice lab on Java/native interoperability, not a benchmark claiming that JNI or FFM is always faster.

**Command execution environment:** Linux x86-64, JDK **25** and a C compiler (GCC or Clang), Bash shell. The FFM API has been final since JDK 22; JDK 25 is chosen to consistently present the `java.lang.foreign` classes and native access permissions. `int32_t` in C and `jint`/`JAVA_INT` are matched according to the Linux x86-64 ABI. When switching OS/CPU/ABI, the layout and build commands need to be re-checked.

## 1. Architecture: there is only one real computation function

Path diagram:

```text
NativeMathDemo.java
    |
    +-- computeViaJni(a,b,c) --------------------------+
    |       (Java native method)                       |
    |               |                                  |
    |          JNI bridge in calc.c                    |
    |        Java_NativeMathDemo_computeViaJni         |
    |               |                                  |
    |               v                                  |
    |       calc_multiply_add(a,b,c) <-----------------+
    |               ^                                  |
    |               |                                  |
    +-- FFM: SymbolLookup -> Linker.downcallHandle ----+
                   symbol "calc_multiply_add"

Same native library: libcalc.so
```

**Key point:** The JNI bridge is only an adapter; it **does not contain the computation formula a second time**. FFM resolves the exact C function name `calc_multiply_add` in the same `libcalc.so`. Therefore, when modifying the formula in the C function, both paths will receive the same implementation after recompiling the library.

Initial directory structure:

```text
jni-ffm-lab/
├── NativeMathDemo.java
└── calc.c
```

After building, the directory will additionally contain `NativeMathDemo.class`, `NativeMathDemo.h` (generated by `javac -h`), and `libcalc.so`. Do not write `NativeMathDemo.h` manually, because the JNI function name/signature should be obtained from the Java compiler.

## 2. Defining the C function contract

Choose a small signature with no pointers that is easy to observe:

```c
int32_t calc_multiply_add(int32_t a, int32_t b, int32_t c);
```

For example, `calc_multiply_add(6, 7, 5)` returns `47`.

Reasons for choosing three `int32_t`s:

- `jint` on the JNI side is a 32-bit signed integer; on the FFM side, `ValueLayout.JAVA_INT` represents a Java `int` value.
- On Linux x86-64, C `int32_t` is passed/returned matching a 32-bit integer according to the ABI in the example; this avoids guessing whether C `long` is 32 or 64 bits.
- There are no strings, arrays, memory allocations, pointers, arenas, or callbacks, so the focus stays on **calling the same function** without getting distracted by native memory management issues.

**Input domain:** the multiplication and addition operations must produce results within the signed 32-bit range (−2,147,483,648 to 2,147,483,647). **Signed integer overflow in C is undefined behavior**; therefore, the example does not use extreme values to "test overflow". The Java-side test uses `Math.multiplyExact` and `Math.addExact` to confirm safe inputs.

## 3. Writing the C library containing the shared function and JNI bridge

Create the file **`calc.c`** with the full content:

```c
#include <stdint.h>
#include <jni.h>
#include "NativeMathDemo.h"

/* Export C symbol so FFM can look it up by name. */
#if defined(_WIN32)
#define CALC_EXPORT __declspec(dllexport)
#else
#define CALC_EXPORT __attribute__((visibility("default")))
#endif

/*
 * SINGLE COMPUTATION FUNCTION.
 * Precondition: a * b + c does not overflow int32_t.
 */
CALC_EXPORT int32_t calc_multiply_add(
        int32_t a, int32_t b, int32_t c) {
    return a * b + c;
}

/*
 * Java native method -> JNI wrapper -> same C function above.
 * JNI function name/signature matches the header file generated by javac -h.
 */
JNIEXPORT jint JNICALL Java_NativeMathDemo_computeViaJni(
        JNIEnv *env, jclass clazz, jint a, jint b, jint c) {
    (void)env;   /* Demo does not need to call APIs via JNIEnv*. */
    (void)clazz; /* Java method is static native. */

    return (jint)calc_multiply_add(
        (int32_t)a, (int32_t)b, (int32_t)c);
}
```

Explanation:

- `CALC_EXPORT` makes the symbol `calc_multiply_add` present in the shared library's exported symbol table. Thanks to this, FFM can look up this exact name. The macro is written with a Windows branch to illustrate the meaning of export; the build command below is specifically for Linux.
- `JNIEXPORT` and `JNICALL` come from `jni.h`, providing the export/calling convention for JNI. `Java_NativeMathDemo_computeViaJni` is the entry point name prescribed by JNI name-mangling for a class without a package and a non-overloaded static native method in the lab.
- `JNIEnv *env` and `jclass clazz` are parameters supplied by the JNI runtime. The bridge does not need to call into the JVM, so the two unused variables are intentionally marked with `(void)`.
- `calc_multiply_add` is **defined only once**. The JNI bridge **calls this function** instead of computing `a * b + c` inside the wrapper.
- FFM **does not call** `Java_NativeMathDemo_computeViaJni`, but instead calls the symbol `calc_multiply_add`. The two paths share the C core, but have different entry points.

If you place the Java class in a package or rename the method, the JNI C entry point name will change. In that case, re-run `javac -h`, open the new header, and update the C code according to the header's declaration rather than guessing the name.

## 4. Writing the Java program: calling both JNI and FFM

Create the file **`NativeMathDemo.java`** in the same directory:

```java
import java.lang.foreign.FunctionDescriptor;
import java.lang.foreign.Linker;
import java.lang.foreign.MemorySegment;
import java.lang.foreign.SymbolLookup;
import java.lang.invoke.MethodHandle;

import static java.lang.foreign.ValueLayout.JAVA_INT;

public final class NativeMathDemo {

    // JNI requires wrapper Java_NativeMathDemo_computeViaJni in calc.c.
    private static native int computeViaJni(int a, int b, int c);

    public static void main(String[] args) throws Throwable {
        // Load EXACTLY ONE shared library for both JNI and FFM.
        System.loadLibrary("calc");

        // FFM: find the C core symbol in the loaded library.
        SymbolLookup lookup = SymbolLookup.loaderLookup();
        MemorySegment address =
                lookup.find("calc_multiply_add").orElseThrow();

        // C: int32_t calc_multiply_add(int32_t, int32_t, int32_t)
        // Java: int compute(int, int, int)
        Linker linker = Linker.nativeLinker();
        FunctionDescriptor signature = FunctionDescriptor.of(
                JAVA_INT,  // Return value
                JAVA_INT,  // a
                JAVA_INT,  // b
                JAVA_INT   // c
        );
        MethodHandle computeViaFfm =
                linker.downcallHandle(address, signature);

        int[][] samples = {
                {6, 7, 5},
                {-3, 4, 10},
                {0, 100, 5},
                {8, -2, -1}
        };

        for (int[] sample : samples) {
            int a = sample[0];
            int b = sample[1];
            int c = sample[2];

            // Oracle computed in Java: throws if input causes int overflow.
            int expected = Math.addExact(Math.multiplyExact(a, b), c);

            // Path 1: Java -> JNI bridge -> calc_multiply_add.
            int jni = computeViaJni(a, b, c);

            // Path 2: Java -> FFM downcall -> calc_multiply_add.
            // invokeExact requires int,int,int parameters and int result.
            int ffm = (int) computeViaFfm.invokeExact(a, b, c);

            if (jni != expected || ffm != expected) {
                throw new AssertionError(
                    "Mismatch: expected=" + expected
                        + ", JNI=" + jni + ", FFM=" + ffm);
            }

            System.out.printf(
                    "a=%d b=%d c=%d | JNI=%d | FFM=%d%n",
                    a, b, c, jni, ffm);
        }
        System.out.println("ALL MATCH");
    }
}
```

### Why does FFM code not need a JNI bridge?

`System.loadLibrary("calc")` loads `libcalc.so` and associates the library with the calling class loader. `SymbolLookup.loaderLookup()` searches for symbols in libraries loaded by `System.load` or `System.loadLibrary` with that class loader. Thus `lookup.find("calc_multiply_add")` returns the native address of the **C core**, while `Linker.nativeLinker().downcallHandle(address, signature)` turns the address and ABI description into a `MethodHandle` callable from Java.

On JDK 25, `FunctionDescriptor.of(JAVA_INT, JAVA_INT, JAVA_INT, JAVA_INT)` reads in the order **return type first, three argument types after**. The handle bound to `address` will accept three `int`s and return an `int`. `invokeExact` requires the Java call-site to match the handle signature exactly; the `(int)` cast explicitly states the result type, avoiding confusion from type adaptation.

The `System.loadLibrary` method is used here **only to load the same library file for both paths**. The FFM computation call still accesses `calc_multiply_add` **directly**, without going through the JNI wrapper. In a program that uses only FFM, you can replace the loading method with `SymbolLookup.libraryLookup(path, arena)` and manage the library's lifetime with `Arena`; this lesson chooses `loaderLookup` so that both paths use a single loaded file.

### Why must JNI code have a Java `native` method?

In Java, `private static native int computeViaJni(...)` is an entry point declaration resolved by the JVM. The JVM finds the corresponding JNI wrapper in the loaded library and passes `JNIEnv*`, `jclass`, and the `jint` arguments to the C code. The JNI wrapper in turn calls the C core. Java does not need to know about the C core in the JNI path, only the declared native method.

Conversely, FFM needs the **symbol address** and the **signature description**. The API does not automatically infer parameter types from the C binary; if the `FunctionDescriptor` or ABI is declared incorrectly, the JVM may crash or corrupt memory. Therefore, using the correct `JAVA_INT` and the correct parameter order is a safety requirement, not merely a compilation issue.

## 5. Compiling and running from scratch

Open a Bash terminal in the `jni-ffm-lab/` directory containing the two source files. Ensure `java` and `javac` on `PATH` belong to the **same JDK 25**.

### Step 1: check tools and determine JDK home

```bash
java -version
javac -version
cc --version
JAVA_HOME="$(dirname "$(dirname "$(readlink -f "$(command -v javac)")")")"
test -f "$JAVA_HOME/include/jni.h"
```

The command above to get `JAVA_HOME` uses Linux's `readlink -f` to find the JDK directory containing `javac`. If the machine has multiple JDKs, set `PATH` so that both `java` and `javac` point to version 25 before running. `test -f` succeeding means the JNI header exists; if not, a full JDK is required rather than just a Java runtime.

### Step 2: generate the JNI header and Java class

```bash
javac -h . NativeMathDemo.java
```

The important output is `NativeMathDemo.h`. Part of the header declaration must have a form equivalent to:

```c
JNIEXPORT jint JNICALL Java_NativeMathDemo_computeViaJni
  (JNIEnv *, jclass, jint, jint, jint);
```

This is an **excerpt**, not the full content of the header file; keep the file generated by `javac -h`, because it contains include guards and other necessary declarations. In the lab's C code, `#include "NativeMathDemo.h"` helps the compiler detect JNI naming or signature errors at build time.

### Step 3: compile `calc.c` into a shared library

```bash
cc -std=c11 -O0 -fPIC -shared \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  calc.c -o libcalc.so
```

Meaning of the flags:

- `-fPIC -shared` creates a shared library for Linux.
- `-I"$JAVA_HOME/include"` and `-I"$JAVA_HOME/include/linux"` let the C compiler find `jni.h` and the platform header files.
- `-O0` makes debugging easier and clearly shows the JNI bridge → C core call path when using a debugger; performance is not the goal of this lab. For real benchmarks, choose compiler settings that are appropriate and match the deployment environment.
- The result is **one** `libcalc.so` file containing both `Java_NativeMathDemo_computeViaJni` and `calc_multiply_add`.

You can check exports on Linux with the following command (optional):

```bash
nm -D --defined-only libcalc.so | grep -E 'calc_multiply_add|Java_NativeMathDemo_computeViaJni'
```

You should see **both symbol names**. The address/symbol type fields may vary by compiler, so do not hardcode the entire `nm` output.

### Step 4: run the JVM with native access enabled

```bash
java --enable-native-access=ALL-UNNAMED \
  -Djava.library.path=. \
  -cp . NativeMathDemo
```

`--enable-native-access=ALL-UNNAMED` grants native access permission to classpath code, appropriate for JDK 25 when calling restricted FFM APIs and using `System.loadLibrary`. `-Djava.library.path=.` tells the JVM where to look for `libcalc.so`. Place these flags **before the main class name**; if placed after `NativeMathDemo`, they become application `args`.

**Exact expected stdout** with JDK 25, Linux x86-64, and the library and inputs above:

```text
a=6 b=7 c=5 | JNI=47 | FFM=47
a=-3 b=4 c=10 | JNI=-2 | FFM=-2
a=0 b=100 c=5 | JNI=5 | FFM=5
a=8 b=-2 c=-1 | JNI=-17 | FFM=-17
ALL MATCH
```

Quick explanation:

- `6 × 7 + 5 = 47`.
- `-3 × 4 + 10 = -2`.
- `0 × 100 + 5 = 5`.
- `8 × -2 - 1 = -17`.

The program **does not only verify JNI against FFM**; each result is compared against an oracle computed using Java `Math.multiplyExact`/`Math.addExact`. Both paths use the same C core, so if the core is wrong, both could still be **wrong in the same way**; comparing against the oracle is important.

### Step 5: modify the core to confirm both paths share the same implementation

After running successfully, you can temporarily change this in `calc.c`:

```c
return a * b + c + 1;  /* Experiment only to prove shared core */
```

This is a **one-line replacement inside the `calc_multiply_add` function**, not a standalone C program. Recompile `libcalc.so` using the command in Step 3, then run the Java program in Step 4. With the current test program, an `AssertionError` will occur because **both JNI and FFM use the new result, which differs from the Java oracle**. This proves that both paths observe the same core and that the test suite catches contract changes. After the experiment, **restore `return a * b + c;`**, recompile, and run until you get `ALL MATCH`.

## 6. Comparing JNI and FFM mechanisms in this exact lab

| Criterion | JNI | FFM |
| --- | --- | --- |
| Java call site | `computeViaJni(a,b,c)` declared `native` | `computeViaFfm.invokeExact(a,b,c)` |
| Actual native entry point | `Java_NativeMathDemo_computeViaJni` | `calc_multiply_add` |
| C adapter code | **Requires** a JNI wrapper in the lab | No computation wrapper needed |
| Name resolution | JNI mangling rules; header generated with `javac -h` | C symbol name string and `SymbolLookup` |
| Boundary signature | Java `native` signature + `JNIEXPORT ... (JNIEnv*, jclass, ...)` | `FunctionDescriptor` + exact C ABI |
| Interop mechanism | JNI calls native via JVM native-method dispatch | FFM creates a `MethodHandle` for downcall |
| Library and core | `libcalc.so` / `calc_multiply_add` | **Same `libcalc.so` / `calc_multiply_add`** |
| Common configuration errors | Lib/JNI symbol not found, wrong header | C symbol not found, wrong descriptor, `WrongMethodTypeException` |
| Example data | Three 32-bit integers | Also three 32-bit integers |

**JNI is not inherently "bad" and FFM is not inherently "faster".** For a simple lab, FFM reduces the need to write extra JNI wrappers. For complex native APIs (structs, callbacks, strings, arrays, ownership), you must understand the ABI and memory lifetime; the `jextract` tool can help generate FFM bindings from C headers. Choosing a technology should be based on integration requirements, maintainability, and proper benchmarks, not on a single `System.nanoTime()` run.

## 7. What to understand about safety and type correctness

### 7.1. Java `int`, JNI `jint`, C `int32_t`, and FFM `JAVA_INT`

In the lab, all three arguments and the return value are 32-bit integers. The JNI wrapper signature has three `jint`s; the C core function has three `int32_t`s; the FFM descriptor has **four** `JAVA_INT` layouts: one for the return value and three for the arguments.

Do not assume that `JAVA_LONG` is always equivalent to C `long`. C `long` can vary in size across platforms, whereas Java `long` is fixed at 64 bits. With JNI use `jlong`, while with FFM you must choose the layout matching the ABI and the actual C type. If you change types, you must simultaneously update the core, Java native method, JNI wrapper, FFM descriptor, and tests.

### 7.2. FFM does not automatically protect native code from UB

A correct `FunctionDescriptor` helps the linker lay out parameters properly; it does not make C operations safe against overflow, invalid pointer access, races, or memory bugs in native code. A wrong ABI/signature can crash the JVM. Keep C computations within safe bounds and test the native part separately.

### 7.3. Lifetime and access permissions

This lab only passes integers, so it **does not need** to create an `Arena`, a `MemorySegment` data buffer, or allocate/free native memory. `MemorySegment address` in Java represents the **function address** found by `SymbolLookup`, which is different from a data buffer. `loaderLookup` is tied to libraries loaded by the class loader; keep code using the handle/symbol while the library remains loaded.

If expanding to `char*`, arrays, strings, structs, or callbacks, you need to study `Arena` allocation, lifetime, thread ownership, encoding, layout, alignment, and data conversion separately. Do not arbitrarily pass `byte[]` as `ADDRESS` assuming FFM has safely copied or pinned the array.

### 7.4. When packaging the application

The JVM must be able to find the library for the **correct architecture** and all dependent native libraries. `java.library.path` and `LD_LIBRARY_PATH` are not the same mechanism; configurations from shells/system services, containers, and IDEs may differ. When moving to the module path, replace `ALL-UNNAMED` with the appropriate module name. On macOS, you typically build `libcalc.dylib`, while on Windows you build `calc.dll` with the JNI include for `win32`; do not apply the Linux `cc -shared -fPIC ...` command verbatim.

## 8. Self-diagnosing common errors

| Symptom | Common cause | How to check/fix |
| --- | --- | --- |
| `javac` reports `java.lang.foreign` does not exist | Using an older JDK, or compiler differs from runtime | Run `javac -version`, use JDK 25 |
| C compiler reports `jni.h` not found | Wrong `JAVA_HOME`, missing JDK, or wrong `-I` | Check `"$JAVA_HOME/include/jni.h"`, `include/linux` |
| C compiler reports `NativeMathDemo.h` not found | `javac -h . NativeMathDemo.java` has not been run yet | Regenerate header before building C |
| `UnsatisfiedLinkError: no calc in java.library.path` | `libcalc.so` not found, wrong name/path | Check library location and `-Djava.library.path=.` |
| `UnsatisfiedLinkError` when calling `computeViaJni` | Wrong JNI entry point name or not exported | Use auto-generated header; check symbol with `nm -D` |
| `NoSuchElementException` at `lookup.find(...).orElseThrow()` | Missing export `calc_multiply_add` or lookup in wrong class loader | Check `CALC_EXPORT`, `nm -D`, `System.loadLibrary` runs before lookup |
| `WrongMethodTypeException` at `invokeExact` | Descriptor or call-site types do not match | Cross-check `(int,int,int)int`, `(int)` cast, and `JAVA_INT` |
| Warning/native access denied | Missing flag for module calling restricted method | Use `--enable-native-access=ALL-UNNAMED` for classpath on JDK 25 |
| Crash or abnormal numeric result | Wrong ABI, function pointer, pointer/lifetime, or C overflow | Re-check native signature, numeric bounds, debug/sanitizer build; do not treat crash as a Java exception |
| Both paths equal each other but differ from expected | Core logic changed/broken | Compare against Java oracle, test independent values |

If using JDK 25 and still encountering errors, collect the **complete** compile command, run command, `java -version`, `javac -version`, stderr, and `nm -D` output. Do not try to fix it by guessing and adding `-Xcheck:jni` for FFM: this flag checks certain JNI contracts, not FFM descriptors.

## 9. Extension exercises with guided answers

**Exercise 1 — Add a safe input.** Add `{12, 3, 7}` to `samples`. Expect both JNI and FFM to return `43`, and the Java oracle to also equal `43`.

**Exercise 2 — Detect a mismatch in the native core.** Change the addition `+ c` to `- c` in the **single** C function, rebuild, and run. Expect the program to throw `AssertionError` on the first input, because both JNI and FFM use the modified core while the oracle still checks `a * b + c`. Restore the original code after the experiment.

**Exercise 3 — Test a controlled FFM lookup failure.** Change the symbol lookup string to `"missing_symbol"` while keeping `calc.c` unchanged. Expect `NoSuchElementException` when `orElseThrow()` runs; no native downcall is created yet. Restore the name `"calc_multiply_add"`.

**Exercise 4 — Analyze the JNI bridge.** Why not write `return (jint)(a * b + c);` directly inside the JNI wrapper?  
**Hint:** That would create **two implementations** that can diverge after edits; the lab requires a single core called by both JNI and FFM.

**Exercise 5 — State the test limitation.** Why is `JNI == FFM` not enough to prove the result is correct?  
**Hint:** Both paths call the same C core; a shared bug will produce the same wrong result. An independent oracle or a precomputed test suite compared against the contract is needed.
