# Generating JNI Header Files with `javac -h` Instead of the Old `javah`

## 1. Why Do We Need to Generate JNI Headers?

In the Java Native Interface (JNI), Java declares a method with the `native` keyword, while **the body of the method resides in a native library**, usually written in C or C++. At runtime, the JVM must find a native function whose name, parameter types, return type, and calling convention match the Java declaration.

A `.h` header file generated by the JDK acts as a **contract between Java and C/C++**. It lets the native side know:

- The JNI function name to define or export, including the encoded package/class/method name.
- The JNI return type, such as `jint`, `jlong`, `jobject`.
- The two hidden JNI parameters: `JNIEnv *` and `jobject` (for instance methods), or `jclass` (for static methods).
- The list and types of Java parameters mapped to JNI types.
- The JNI method descriptor appearing in the comment, for example `(II)I`.

**Use `javac -h` to obtain the signature from real Java code; do not guess the JNI function name.** Whenever you change a `native` signature or a class name/package, you need to regenerate the header and recompile the corresponding C/C++ code.

### Where did `javah` go?

`javah` is an older tool that generated headers from **compiled** Java classes. Starting with **JDK 8**, `javac` has the `-h` option to both compile Java source and generate native headers. The `javah` tool was **removed from the JDK starting in JDK 10**. Therefore, when using Java 17, 21, or newer, the standard workflow is:

```text
.java file (native declaration)
      │
      ▼
javac -h <header-directory> -d <classes-directory> <source.java>
      ├──────────────► .class file (bytecode)
      └──────────────► .h file (JNI C declarations)
                               │
                               ▼
                       C/C++ includes header,
                       defines JNI function
                               │
                               ▼
                       native compiler/linker
                               │
                               ▼
                        .so / .dylib / .dll
                               │
                               ▼
                      JVM loads library and calls
```

A key distinction: **`javac -h` does not compile C/C++ and does not automatically generate `.so`/`.dll` libraries**. It only generates Java bytecode along with the JNI header. The native compiler performs the remaining steps.

## 2. Syntax and Meaning of the Options

Commonly used syntax:

```bash
javac -encoding UTF-8 -h build/headers -d build/classes src/demo/jni/NativeAdder.java
```

| Component | Role |
| --- | --- |
| `javac` | The Java compiler from the **JDK**, not the `java` launcher |
| `-h build/headers` | Directory to receive **native headers** generated from `native` declarations (or constants annotated with `@Native`) |
| `-d build/classes` | Directory to store `.class` files after compilation |
| `-encoding UTF-8` | Specifies source file encoding to handle accented comments/strings reliably |
| `src/demo/jni/NativeAdder.java` | Path to the **Java source file** being compiled |

`-h` expects a **directory path**, not a specific `.h` filename. The header name is generated by `javac` from the class identity. For the example below using classpath and package `demo.jni`, the expected header is `demo_jni_NativeAdder.h`.

It is generally good practice to separate `build/classes` and `build/headers`. Do not confuse `-h` with `-d`: `-h` determines the header location, while `-d` determines the bytecode location. Both can be used in the **same compilation**.

## 3. Hands-On from Scratch: A Java Method Calling C

This section provides a complete program using **Java 17+** and **GCC on Linux**. The goal is to demonstrate that the header is generated correctly, C uses that exact header, the library is loaded by the JVM, and the native call returns the result.

### 3.1. Directory Structure

Create the project directory as follows:

```text
jni-header-demo/
├── src/
│   └── demo/
│       └── jni/
│           └── NativeAdder.java
└── nativeadder.c
```

After building, `build/classes`, `build/headers`, and `build/lib` will also be created. The files inside `build/` are generated artifacts; in this example, there is no need to write the header by hand.

### 3.2. Declaring the `native` Method in Java

Contents of `src/demo/jni/NativeAdder.java`:

```java
package demo.jni;

public final class NativeAdder {
    static {
        // "nativeadder" is the logical name; the JVM adds the OS-specific prefix/suffix.
        System.loadLibrary("nativeadder");
    }

    // The actual implementation resides in the native library.
    public native int add(int left, int right);

    public static void main(String[] args) {
        NativeAdder adder = new NativeAdder();
        int result = adder.add(19, 23);
        System.out.println("Result: " + result);
    }
}
```

Here:

- `package demo.jni` is part of the class identity and affects the JNI symbol name.
- `public native int add(int, int)` **has no Java method body**. `native` is a concrete method implemented outside the JVM layer.
- `System.loadLibrary("nativeadder")` instructs the JVM to load the library by the logical name `nativeadder`: on Linux it is `libnativeadder.so`, on macOS `libnativeadder.dylib`, and on Windows `nativeadder.dll`.
- `main` calls `add(19, 23)` to verify the Java ↔ native connection.

**There is no need to create `NativeAdder.h` manually.** `javac -h` will generate it based on the declaration above.

### 3.3. Generating the Header and Bytecode in One Command

Open a **bash terminal on Linux**, navigate to the `jni-header-demo` directory, ensure `javac` belongs to JDK 17+, and run:

```bash
mkdir -p build/classes build/headers build/lib

javac -encoding UTF-8 \
  -h build/headers \
  -d build/classes \
  src/demo/jni/NativeAdder.java
```

The two key outputs are:

```text
build/
├── classes/
│   └── demo/
│       └── jni/
│           └── NativeAdder.class
└── headers/
    └── demo_jni_NativeAdder.h
```

In this classpath example, `NativeAdder.class` resides under the package structure; the header uses the class name encoded according to JNI rules. When using a **named Java module**, the header directory layout may also reflect the module name; check the actual output of the build command rather than guessing the path.

If `javac` succeeds but you only look inside `build/classes`, you will not find the header, because it is placed in `build/headers` per `-h`.

### 3.4. Reading the Generated Header

Open `build/headers/demo_jni_NativeAdder.h`. After the include guards and comments, the important part will look equivalent to:

```c
#include <jni.h>

/*
 * Class:     demo_jni_NativeAdder
 * Method:    add
 * Signature: (II)I
 */
JNIEXPORT jint JNICALL Java_demo_jni_NativeAdder_add
  (JNIEnv *, jobject, jint, jint);
```

This is an **illustrative excerpt**, not the entire header content. The actual file also contains include guards and an `extern "C"` block for compatibility when included from C++.

Breakdown of each part:

| Header Component | Meaning |
| --- | --- |
| `#include <jni.h>` | Loads JNI types and macros defined by the JDK |
| `JNIEXPORT` | Ensures the function symbol is exported properly on supported platforms |
| `jint` | JNI type corresponding to Java `int` |
| `JNICALL` | Calling convention matching the ABI/JNI |
| `Java_demo_jni_NativeAdder_add` | Mangled JNI export name from package, class, and method |
| `JNIEnv *` | JNI interface pointer for the **thread making the call** |
| `jobject` | The `NativeAdder` instance invoking the instance method |
| `jint, jint` | The two Java parameters `left` and `right` |
| `(II)I` | Descriptor: takes two `int`s and returns an `int` |

Count the C parameters to avoid confusion: in this example there are **four** parameters in the C function (two hidden JNI parameters and two Java parameters) even though the Java declaration only has **two** parameters.

JNI descriptors use JVM-level signatures, not Java's `(int, int) -> int` syntax. Some common symbols: `I` = `int`, `J` = `long`, `Z` = `boolean`, `V` = `void`, `[B` = `byte[]`, `Ljava/lang/String;` = `String`. Thus `(II)I` means `int add(int, int)`.

### 3.5. Implementing C According to the Header Prototype

Create `nativeadder.c` in the project root directory:

```c
#include "demo_jni_NativeAdder.h"

JNIEXPORT jint JNICALL Java_demo_jni_NativeAdder_add(
        JNIEnv *env, jobject receiver, jint left, jint right) {
    (void)env;       // This example does not need to call JNI functions yet.
    (void)receiver;  // This example does not use the Java object yet.

    // Illustrative inputs 19 and 23 do not cause jint overflow.
    return left + right;
}
```

The function name, return type, and parameter order must match the prototype. Including the **header generated by `javac`** allows the C compiler to catch declaration mismatches at compile time. Do not edit the generated header to legitimize a C function with the wrong signature; fix the Java or C source appropriately and regenerate the header.

This is a minimal arithmetic example; for arbitrary input values, signed integer overflow must be checked at the C layer before adding. Java and C do not share the same `int` overflow safety rules, so unchecked `jint` addition should not be used as a production API contract.

### 3.6. Compiling the Native Library and Running Java

`JAVA_HOME` must point to the **JDK in use**, containing `include/jni.h` and `include/linux/jni_md.h`. From the `jni-header-demo` directory, run:

```bash
gcc -fPIC -shared \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  -Ibuild/headers \
  -o build/lib/libnativeadder.so \
  nativeadder.c

java -Xcheck:jni \
  -Djava.library.path=build/lib \
  -cp build/classes \
  demo.jni.NativeAdder
```

Notable components:

- `-I"$JAVA_HOME/include"` and `-I"$JAVA_HOME/include/linux"`: so GCC can find the standard JNI headers.
- `-Ibuild/headers`: to find `demo_jni_NativeAdder.h` generated by `javac -h`.
- `-fPIC -shared` and the name `libnativeadder.so`: builds a shared library for Linux.
- `-Djava.library.path=build/lib`: adds the library search directory for the JVM. Place `-D` options **before** the Java class name.
- `-cp build/classes`: specifies the path containing `demo/jni/NativeAdder.class`.
- `-Xcheck:jni`: enables additional JNI checks in the JVM (useful for learning and diagnostics).

**Expected stdout:**

```text
Result: 42
```

The execution flow is: class `NativeAdder` is initialized → JVM loads `libnativeadder.so` → `main` calls `add` → JVM locates `Java_demo_jni_NativeAdder_add` → C returns `42` → Java prints `Result: 42`. Success at this step proves that the header, C implementation, library name, and load command are compatible.

### 3.7. What Changes on macOS and Windows

**On macOS**, use the platform header `$JAVA_HOME/include/darwin` and build `libnativeadder.dylib` with a compatible tool; with Clang from Command Line Tools, you can use:

```bash
cc -dynamiclib \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/darwin" \
  -Ibuild/headers \
  -o build/lib/libnativeadder.dylib \
  nativeadder.c
```

**On Windows**, use `%JAVA_HOME%\include\win32` when compiling with an appropriate toolchain to produce `nativeadder.dll`, adjusting path separators and environment variable syntax for CMD/PowerShell. The library's architecture (e.g., x64) must match the JVM. The Java code still uses the logical name `nativeadder` in `System.loadLibrary`.

The `gcc` and `cc` commands above use OS-specific libraries/toolchains; **the JNI header and Java declarations are the reusable contract**.

## 4. When Java Source Changes, How Must the Header and C Change?

Suppose we change Java from:

```java
public native int add(int left, int right);
```

to:

```java
public native long add(long left, int right);
```

This is a **signature change illustration**, not a complete program replacing the previous example. After modifying the source, run `javac -h` again. The new header will have the descriptor `(JI)J` because `J` represents `long`:

```c
/*
 * Signature: (JI)J
 */
JNIEXPORT jlong JNICALL Java_demo_jni_NativeAdder_add
  (JNIEnv *, jobject, jlong, jint);
```

The C code must change the **return type to `jlong`** and the corresponding parameter to `jlong`. If Java has changed its signature but the native library has not been rebuilt, the result may be a linking error or incorrect behavior due to ABI incompatibility; seeing the same function name **does not guarantee the C signature is still correct**.

After updating a native method, repeat the steps in order:

1. Recompile Java with `javac -h`.
2. Inspect the new prototype in the header.
3. Update and recompile C/C++ based on the new header.
4. Load the new library with a fresh JVM process and run tests.

For a `static native` method, the second parameter of the JNI function is **`jclass` instead of `jobject`**. For **overloaded** methods (multiple methods with the same name), the JNI symbol name may also include encoded parameter signatures. Class/package names with characters requiring escaping are also subject to JNI name mangling rules. Therefore, do not manually shorten export names after seeing a simple example; **always take the exact prototype from the newly generated `.h` file**.

## 5. At Which Step Do `javac -h` and `javah` Differ?

| Aspect | `javah` (old workflow) | `javac -h` (modern workflow) |
| --- | --- | --- |
| Input | Compiled Java class on the classpath | `.java` source code being compiled |
| Task | Generates JNI header in a separate step | Compiles Java and generates header in one pass |
| Status | Removed in JDK 10+ | Available since JDK 8; used on modern JDKs |
| Output | Native header | Java `.class` and native header |
| Suitable for Java 17+ | No | Yes |

A **historical** workflow used to require `javac` first and then `javah` on the compiled class. Do not put `javah` commands into scripts targeting JDK 17+, as standard JDK distributions no longer include this tool.

The essential change is not simply renaming the command from `javah` to `javac`; you must **fold the header generation step into the source compilation task itself** and point `-h`/`-d` appropriately. If an old script passed a compiled class name to `javah`, you cannot pass that same class name to `javac -h` and expect an equivalent result: `javac` requires source files and appropriate compiler options.

## 6. When Does `javac -h` Generate a Header?

According to the `javac` documentation, `-h` generates a native header for each class that:

- Has one or more `native` methods; **or**
- Has one or more constants marked with the `java.lang.annotation.Native` annotation.

Example of declaring a constant for native code (this snippet **only illustrates the annotation** and does not replace the full program in section 3):

```java
import java.lang.annotation.Native;

@Native
public static final int FLAG_ENABLED = 1;
```

When such a valid field is placed **inside a class**, the compiler can include the constant definition in the header so C uses the same value. Conversely, `final` alone is not equivalent to `@Native`; a class with no native methods and no `@Native` constants will normally not have a JNI header generated.

With **named modules**, classpath and module-path can affect where generated headers are placed depending on the version/build setup; check the actual path produced by the compiler. For the classpath example in section 3, the file is generated directly under `build/headers` with the name shown.

## 7. Checking Descriptors and Symbols When Diagnosing Errors

Besides the header, you can use `javap` to inspect the class descriptors after compilation:

```bash
javap -s -p -classpath build/classes demo.jni.NativeAdder
```

In the output, the lines related to `add` correspond to:

```text
public native int add(int, int);
  descriptor: (II)I
```

`javap -s` displays descriptors from bytecode; it is an **inspection tool**, not a replacement for `-h` header generation. Cross-check `(II)I` with the `Signature: (II)I` comment in the header to confirm that the Java source and bytecode are consistent.

If you need to inspect library symbols on Linux, you can use `nm -D build/lib/libnativeadder.so` (if your toolchain includes `nm`) and search for `Java_demo_jni_NativeAdder_add`. A wrong package/class name, an unloaded library, or an outdated `.so` version can cause runtime errors even though `javac -h` succeeded.

## 8. Common Errors and How to Fix Them

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `javah: command not found` | Using JDK 10+ | Migrate the pipeline to `javac -h`; do not attempt to use `javah` on newer JDKs |
| `javac: no source files` or file not found | Passing a class name or wrong `.java` path | Provide the actual source path, e.g., `src/demo/jni/NativeAdder.java` |
| No `.h` file appears | Looking under `-d` by mistake; class has no `native`/`@Native`; compile step skipped | Check `-h`, compilation errors, native declarations, and which task actually ran |
| `jni.h: No such file or directory` | GCC was not given the JDK include paths | Specify `JAVA_HOME/include` and the OS-specific include path |
| `demo_jni_NativeAdder.h: No such file or directory` | Wrong header directory or `javac -h` not run | Add `-Ibuild/headers` and regenerate headers before building C |
| `UnsatisfiedLinkError: no nativeadder in java.library.path` | Library not built, or JVM searching the wrong directory/filename | Check `build/lib`, OS filename conventions, and `-Djava.library.path` |
| `UnsatisfiedLinkError` when calling `native` method | Exported symbol name mismatch, wrong overload, stale library | Compare against the new header, verify symbol name, and rebuild the library |
| C compiler reports conflicting types | Prototype in `.h` does not match C definition | Update the C definition to match the header generated from the latest Java code |
| Wrong platform/architecture | Using `linux` includes on Windows or library architecture mismatches JVM | Use `linux/darwin/win32` includes and the matching platform toolchain |

**Never edit the generated `.h` file to "patch" a signature** while forgetting to fix `.java` or C. The header is derived from the Java source of truth; upon rebuild, any manual edits may be overwritten.

## 9. Integrating Header Generation into the Build Process

When a small example grows into a real project, treat headers as **artifacts generated from Java source** and establish the dependency order:

```text
compile Java + generate JNI headers (javac -h)
                     ↓
compile/link C or C++ (using the exact new header)
                     ↓
package the native library and configure the load path
                     ↓
run Java ↔ native integration tests
```

In Gradle/Maven or custom build scripts, native compilation must depend on the Java step that generates headers; do not assume compiling Java once means the headers will remain valid forever. If a `native` signature, package name, or class name changes, ensure both the Java compiler and C compilation step re-run. When investigating hard-to-reproduce bugs, cleaning old build artifacts and performing a clean build is a reasonable way to eliminate stale headers/libraries.

JNI headers only contain declarations for the bridge; they **do not automatically solve** native memory management, JNI reference lifecycles, exceptions, threading, or the ABI of other C/C++ APIs. This introductory lesson focuses on generating accurate JNI signatures.

## 10. Self-Check

1. For `native int add(int, int)` in package `demo.jni`, why is the C function named `Java_demo_jni_NativeAdder_add` instead of just `add`? What does `(II)I` in the header represent?
2. What **two types of files** does `javac -h build/headers -d build/classes src/demo/jni/NativeAdder.java` generate? Where are they located and which component uses each?
3. If the method is changed to `static native int add(int, int)`, which JNI parameter changes from `jobject` to `jclass`? Why does manually writing old prototypes become risky?
4. Why can't an old `javah` script be reused on JDK 21? Can a compiled class name previously passed to `javah` be passed directly to `javac -h`?
5. If Java changes from `int add(int, int)` to `long add(long, int)`, state the new descriptor, the new JNI types, and the **rebuild order** required.

**Key takeaway:** In modern Java, use **`javac -h <header-dir>`** during source compilation to generate JNI headers; use **`-d <class-dir>`** for bytecode; **include the generated header in C/C++ code and compile the native library separately**. Whenever Java signatures change, regenerate the header, update C, and rebuild the library.
