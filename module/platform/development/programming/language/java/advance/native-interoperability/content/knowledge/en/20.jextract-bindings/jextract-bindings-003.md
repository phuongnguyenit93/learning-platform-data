# Choosing the Right jextract Version for the FFM API and Target JDK

## 1. The Problem to Solve

**jextract** is a tool from the OpenJDK Code Tools project that reads **C headers (.h)** via Clang/libclang and generates **Java source bindings** using the **Foreign Function & Memory API (FFM)**. The bindings typically contain **MemorySegment**, **MemoryLayout**, **Arena**, **SymbolLookup**, **Linker**, **FunctionDescriptor**, **MethodHandle**, helpers to access C structs/unions, and wrappers for native functions. They are not ordinary JDK-version-independent Java code.

Because the FFM API went through the **incubator → preview → final** stages, and continues to evolve after becoming final, the jextract version used to generate the source **must be compatible with the JDK intended to compile and run that source**. You should not download the latest jextract without looking at the target JDK: a newer version may generate API calls that the target JDK does not yet have.

**Short rule:**

> Choose the **JDK the application will run on** first; choose a **jextract release or build targeting that JDK's FFM API**; generate bindings from the right header/ABI; then **compile and smoke-test on that exact target JDK**.

This lesson guides you through checking actual versions, choosing a branch/binary, running a C → jextract → Java example, isolating errors, managing versions in CI/CD, and making upgrade decisions. The default example uses **JDK 25** because it is an LTS JDK with a standard FFM API and has distributed jextract builds targeting JDK 25; however, the commands depend on the specific jextract package and you need to check **jextract --version**, rather than treating a single build number as a permanent standard.

**Scope:** jextract automates **C ABI** bindings, not a compiler that directly translates C++ classes/templates to Java. For C++, Rust, or other languages, use a properly exported C-compatible wrapper/API/header before running jextract.

## 2. Why Is There a Version Compatibility Problem?

Let's separate the four interacting layers:

~~~text
    C headers  ---------  ABI/native library
        |                         |
        v                         v
  Clang/libclang            .so / .dylib / .dll
        |
        v
     jextract (tool version)
        |
        v
    Java bindings (source using a specific FFM API)
        |
        +--> target javac/JDK  --- compiles into .class
                                       |
                                       v
                                 java/JDK runtime
                                       |
                                       v
                           native Linker + C library
~~~

The **jextract tool** can run using its own JDK or a runtime bundled with the toolset. **Bindings generated by jextract** must be compiled with a JDK version that provides all the FFM classes/methods referenced by the generated source. The **native library**, in turn, must be compatible with the operating system, CPU architecture, calling convention, and C ABI.

A C header file may be parsed successfully by jextract, yet the Java binding may fail to compile with the target JDK. Conversely, the Java binding may compile successfully, yet at runtime it may load the wrong native library or use an incompatible C ABI. Therefore, "jextract runs" is **not enough** to conclude "the Java application runs".

Four types of compatibility need to be checked separately:

| Layer | Decision question | Example errors |
| --- | --- | --- |
| **Tool → host JDK** | Can the jextract binary run on the build machine's JDK/OS? | Tool fails to start, missing Java runtime or libclang |
| **Generated source → JDK API** | Do the generated FFM classes/methods exist in the target JDK? | package/class/method does not exist during javac |
| **Generated bytecode → runtime JDK** | Are the classfile level and linked methods compatible with the runtime? | UnsupportedClassVersionError, NoSuchMethodError |
| **Binding → native ABI** | Do the header, compiler flags, and actual .so/.dll match? | UnsatisfiedLinkError, wrong sizeof/offset, crash |

These are four related decisions, but **you cannot use a single version number in place of all of them**.

## 3. FFM API History and Implications for Choosing jextract

| JDK group | FFM status | Impact on jextract |
| --- | --- | --- |
| **JDK 17** | Early Foreign API in incubator, e.g., package **jdk.incubator.foreign** | Must use tool/bindings matching the old API; source generated for modern java.lang.foreign cannot be used directly |
| **JDK 19–21** | FFM in preview stage; packages/signatures underwent changes | Need a jextract build tied to the **exact preview target JDK**; may need --enable-preview during compile/run |
| **JDK 22** | FFM became a **final API** (JEP 454) in **java.lang.foreign** | Can use jextract compatible with JDK 22; no longer requires preview just for using FFM |
| **JDK 23–24** | FFM continued to have changes/additions per JDK | Choose a matching jextract build; verify generated source on the exact runtime rather than assuming backward compatibility |
| **JDK 25 LTS** | FFM is already a standard API; jextract builds targeting JDK 25 exist | Suitable for a build pipeline example pinning JDK 25 + jextract 25 |
| **JDK 26–27** | Newer JDKs (JDK 27 released in September 2026) | Check the jextract binary/branch and FFM API of that exact target; **do not assume** a JDK 27 binary is always available or that a JDK 25 build runs unchanged |

**Distinction to make:** **FFM API becoming final in JDK 22** does not mean **jextract became a default command in every JDK**. jextract is a **separately released tool**; a standard JDK installation is not guaranteed to have **bin/jextract**. Nor is there an absolute rule that "jextract version N only runs on JDK N and cannot run on any other JDK": **the ability to run the tool** and **the API required by the source it generates** are two different contracts, both of which must be measured/checked.

**For Java 17/21 still in operation:** Do not upgrade jextract to master and hope the newly generated code will automatically be compatible with the old incubator/preview API. Choose a branch or release targeting the historical JDK, keep the tested generated source, or consider a plan to upgrade the application JDK first. The OpenJDK jextract README explains that the **master** branch follows the new FFM API, while versioned branches like **jdk21** are for older targets. Which branches actually exist and can be built must be checked from the repository at the time of use.

## 4. Version Selection Process in the Right Order

**Step 1: Lock in the target JDK.** Record the exact **major** version, update release if important, vendor, OS, and architecture. For example, "OpenJDK 25 LTS x64 Linux", not just "new Java". Check the JDK used for **compile** and **runtime**; if they differ, verify the cross-compilation strategy.

**Step 2: Look up the jextract release/branch supporting the target JDK.** Prefer official binary releases or builds from a trusted provider for the target JDK. The OpenJDK project posts instructions at **https://github.com/openjdk/jextract** and packaged builds are linked from **https://jdk.java.net/jextract/**. Prebuilt binaries are released in batches and may **not match** the latest GA JDK release.

**Step 3: Read the tool's actual metadata.** Run **jextract --version** and match the tool/JDK info, plus **jextract --help** to confirm the options of that version. Do not guess syntax from a blog written for an earlier generation of jextract.

**Step 4: Lock in the C header and compiler/ABI.** The C header version must match the native library used at runtime. Include locations, -D macros, target OS, and compiler flags can change declarations and layouts. **The same version of jextract** running on Windows and Linux can produce different source due to different C long/pointer/layout sizes.

**Step 5: Generate bindings into a clean directory with a fixed package.** Record the tool build, OS, JDK, libclang version, and CLI arguments. Compare the output after each tool/header upgrade.

**Step 6: Compile the generated source with the target JDK.** This is the most effective verification of the FFM API: an immediate error in javac is a sign that the target JDK does not provide the class/method the binding needs, or there is another source-generation mismatch.

**Step 7: Run a smoke test with the actual native library.** Successful compilation is not enough; you need to load the right .so/.dll/.dylib and call at least one function to detect loader, symbol, and ABI issues.

**Step 8: Pin versions and tests in CI.** When changing the target JDK or jextract, regenerate/test intentionally. Do not silently pull the "latest" binary on every CI run.

In summary, the priority order is:

~~~text
Lock in target JDK
      |
      v
Find jextract documented as compatible with target
      |
      v
jextract --version / --help
      |
      v
Generate Java bindings from right header/ABI
      |
      v
javac target JDK -> PASS?
      |
    NO: check API mismatch, tool version, source
      |
    YES
      v
java target JDK + native lib -> PASS?
      |
    NO: classfile, native access, linker/loader, ABI
      |
    YES
      v
Pin versions and save artifacts/CI test
~~~

## 5. Distinguishing Three Version Numbers That Must Not Be Mixed Up

### 5.1. Version of the jextract tool

**jextract --version** prints the tool's version information and may include the JDK version it was built for/targets along with **libclang**. The exact output varies across releases, platforms, and vendors. For example, a jextract package targeting JDK 25 might print a build string like **25-jextract+...** or **JDK version 25...**.

**Do not** use that number to automatically infer:

- the JDK version that production is running;
- the bytecode version of the generated classes;
- the machine's native libclang version;
- the C header or libfoo.so version on the system.

The tool version is one line of evidence, not a full end-to-end check.

### 5.2. Version of javac and Java runtime

**javac --version** checks which JDK the compiler is shipped with; **java --version** checks which JVM launches. It is possible for **javac** and **java** to resolve to two different JDKs due to **PATH**, **JAVA_HOME**, IDE/Gradle toolchains, or CI configuration.

Example of running explicitly using binaries in one JDK:

~~~bash
"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
"$JAVA_HOME/bin/javac" -d classes MyApp.java
"$JAVA_HOME/bin/java" -cp classes MyApp
~~~

**These are illustrative commands**; you must have the MyApp.java file and the classes directory in place. Do not assume **JAVA_HOME** will change the executable used by another build tool; Gradle/Maven IDEs may use their own toolchains.

### 5.3. Version/API called by the generated source

In the generated .java files, inspect the **imports** and API usages:

- **import java.lang.foreign...** indicates the modern FFM package (from preview and final stages).
- **import jdk.incubator.foreign...** indicates targeting the older incubator API.
- Methods like **Arena.allocate(...)**, **SymbolLookup.libraryLookup(...)**, **Linker.nativeLinker().downcallHandle(...)**, **MemorySegment.reinterpret(...)**, or layout factories have signatures that change across versions.
- Generated helper classes/fields/methods can change their organization when jextract changes, even with the same C header name.

**Do not just look for the package name.** Java 21 preview also has **java.lang.foreign**, but that does not mean code generated for JDK25/26 is compatible with the Java21 API.

## 6. Obtaining jextract Binaries and Verifying from Trusted Sources

Public references:

- OpenJDK jextract project: **https://github.com/openjdk/jextract**
- Official linked jextract builds page: **https://jdk.java.net/jextract/**
- Usage guide: **https://github.com/openjdk/jextract/blob/master/doc/GUIDE.md**
- Tutorial on dev.java: **https://dev.java/learn/ffm/jextract/**

How to choose a package:

1. Check which **JDK N** the release is described as targeting; avoid choosing just because of the newest upload date.
2. Verify OS/CPU: Linux x64/AArch64, macOS x64/AArch64, Windows x64... A build for macOS ARM64 will not run on Windows x64.
3. Check **SHA-256**, signatures/distribution source if provided. Do not grab a binary named **jextract** from a site of unknown provenance and use it to parse C headers in CI.
4. Extract separately (e.g., **/opt/tools/jextract25**); do not overwrite an old version and lose reproducibility.
5. Invoke the executable by absolute path or a pinned environment; avoid relying on an older jextract earlier in **PATH**.

Example check after installing on Linux:

~~~bash
/opt/tools/jextract25/bin/jextract --version
/opt/tools/jextract25/bin/jextract --help

"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
uname -m
~~~

All paths in the snippet above are **illustrative** and must be replaced with where you actually installed them. **The output of --version** depends on the package, so there is no fixed stdout string across all JDK/tool vendors. Use **--version** to record this exact detail in build logs.

**Key point to remember:** the **master** branch in the repo usually follows the FFM API of the newest JDK under development; if your target is JDK 25/22/21, do not just build master without checking the corresponding README/branch. Even if the master tool can launch with the JDK installed on the machine, newly generated bindings may still require an FFM API too new for the deployment target.

## 7. When No Suitable Binary Exists: Build from the Corresponding Branch

The OpenJDK jextract README describes how to build from source and gives an example of checking out the **jdk21** branch for use with an older JDK. Orientation workflow:

~~~bash
git clone https://github.com/openjdk/jextract.git
cd jextract

git branch -a
git tag -l

# Example *if the target is JDK 21* and the branch still exists:
git checkout jdk21
~~~

**Do not blindly apply one branch name to every JDK**. Check **git branch -a** and release notes; some versions may use different tags/binaries. If the tool for the target JDK is no longer supported, use a verified release archive or plan to upgrade the target JDK. Building an old branch on a too-new compiler/JDK can hit Gradle, Clang, or toolchain errors — not due to your application's C code.

The build command per the current OpenJDK README uses the Gradle wrapper and separate parameters for the JDK toolchain and libclang:

~~~bash
# Inside the jextract source directory checked out to the right branch.
sh ./gradlew \
  -Pjdk_home=/opt/jdks/jdk-target \
  -Pllvm_home=/opt/llvm \
  clean verify

build/jextract/bin/jextract --version
~~~

**Paths are examples**, and each branch may have its own build script/toolchain prerequisites: **you must read the README of that exact commit/branch** before running. The JDK used to **run Gradle** may differ from the JDK supplied via **-Pjdk_home**; the README explicitly notes to consult the **Gradle Java compatibility matrix**.

jextract uses the **libclang C API**, so besides the JDK you also need the LLVM/libclang version supported by the branch. If the tool fails to load **libclang** or fails to parse headers, check clang availability, ABI, and include paths; that error must not be immediately blamed on "wrong JDK FFM version".

For reproducibility: pin the **jextract Git commit/tag**, **JDK distribution/version**, **LLVM/libclang version**, and build flags. A build generated on master today may differ from master tomorrow.

## 8. End-to-End Linux Example with JDK 25 and Matching jextract

This example demonstrates the full version selection without needing complex C features. Assume you have:

- **JDK 25** as the Java compiler + runtime used in the demo;
- **jextract** with a release/commit targeting the JDK 25 FFM API, installed for the right OS/CPU;
- GCC or Clang C compiler on Linux x64, with the same ABI as the Java process;
- Native access enabled when running Java.

Example C function:

~~~c
int add_ints(int left, int right);
~~~

On standard Linux x64, C **int** is 4 bytes, matching Java **int**. In a real native project, confirm bit widths with the ABI/toolchain rather than generalizing to every C ABI.

### 8.1. Directory structure

~~~text
ffm-version-lab/
├── native/
│   ├── adder.h
│   ├── adder.c
│   └── libadder.so       (built)
├── generated/             (jextract output)
├── classes/               (javac output)
└── App.java
~~~

**All of the following are separate sample files.** The generated and classes directories are outputs, not handwritten source files.

### 8.2. File native/adder.h

~~~c
#ifndef DEMO_ADDER_H
#define DEMO_ADDER_H

#ifdef __cplusplus
extern "C" {
#endif

int add_ints(int left, int right);

#ifdef __cplusplus
}
#endif

#endif
~~~

This header declares exactly one exported C ABI function. The **extern "C"** block only takes effect when the header is included in C++ source; the example implementation is compiled as C11.

### 8.3. File native/adder.c

~~~c
#include "adder.h"

int add_ints(int left, int right) {
    return left + right;
}
~~~

This is complete C11 code for a library function, with no main. With inputs 20 and 22, no signed overflow occurs.

Build the Linux shared library:

~~~bash
mkdir -p generated classes

cc -std=c11 -Wall -Wextra -Wpedantic \
  -fPIC -shared native/adder.c \
  -o native/libadder.so
~~~

The command uses the machine's native compiler and creates the library file at **native/libadder.so**. Verify the **add_ints** symbol exists if needed using a tool such as **nm -D native/libadder.so**.

### 8.4. Checking the tools before generating

~~~bash
jextract --version
jextract --help

"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
~~~

Proceed only when:

- the jextract in use is the build **chosen to target JDK25**;
- JAVA_HOME points to JDK25 for the right CPU/OS;
- CLI options **--output**, **--target-package**, **--library** are present in that tool build's **--help**.

Do not treat **jextract --version** merely showing the number 25 as proof that all generated source will run right away. The real test begins in the next step.

### 8.5. Generating Java bindings

~~~bash
jextract \
  --output generated \
  --target-package demo.bindings \
  --library adder \
  native/adder.h
~~~

**Explanation:**

- **--output generated**: root of the generated source files.
- **--target-package demo.bindings**: Java package; jextract creates the corresponding directory.
- **--library adder**: the binding will look up the native library named **adder** via platform conventions; on Linux this is usually **libadder.so**.
- **native/adder.h**: main header containing the C declaration to generate.

Per current jextract guide conventions, the **adder.h** header creates the main class **adder_h** in package **demo.bindings**, with static method **add_ints(int,int)**. If your pinned jextract build generates different names/code, **inspect the output directly** and adjust the caller program to match the actual API. Do not copy a class generated by another jextract version and assume the name never changes; you can use the **--header-class-name** option when you need to fix the name.

### 8.6. File App.java

~~~java
import static demo.bindings.adder_h.add_ints;

public class App {
    public static void main(String[] args) {
        int result = add_ints(20, 22);
        System.out.println("native result = " + result);
    }
}
~~~

This is a standalone Java program using the wrapper jextract generated from the C header. It does **not** call JNI native methods, does not write FunctionDescriptor manually, and does not declare downcall handles itself; those parts belong to the generated binding.

### 8.7. Compiling with the exact target JDK

Run these commands from the **ffm-version-lab/** directory:

~~~bash
# Note: generated contains .java source, not a prebuilt JAR.
find generated -type f -name '*.java' -print0 \
  | xargs -0 "$JAVA_HOME/bin/javac" -d classes

"$JAVA_HOME/bin/javac" -cp classes -d classes App.java
~~~

Checkpoints:

- **javac** must be the binary of **target JDK 25**.
- If an error occurs on imports/methods in **java.lang.foreign**, suspect **jextract ↔ FFM API target** incompatibility.
- If the error says **demo.bindings.adder_h** is not found, check the actual generated class/package before blaming the JDK.
- If jextract did not generate the **add_ints** function, check the header path, Clang diagnostics, and symbol filters.
- If compilation passes, proceed to the runtime smoke test; compiler success does not prove the native symbol will load.

### 8.8. Running and verifying the result

~~~bash
LD_LIBRARY_PATH="$PWD/native" \
  "$JAVA_HOME/bin/java" --enable-native-access=ALL-UNNAMED \
  -cp classes App
~~~

**--enable-native-access=ALL-UNNAMED** permits native FFM operations from classpath code in the unnamed module. Mechanisms/diagnostics may vary by JDK; if using named modules, grant native access to the module name instead of ALL-UNNAMED.

**LD_LIBRARY_PATH** here helps the loader find **libadder.so** for the demo. Production packaging workflows should manage library locations explicitly and more safely than allowing any library of the same name to be loaded from a manipulable path.

With a toolchain/JDK verified as compatible, on Linux stdout prints:

~~~text
native result = 42
~~~

Logs or environment warnings may appear on stderr/stdout depending on the JVM, but the core check is that **the wrapper actually calls the C function and returns 42**. If the native library is not loaded, you will typically see **UnsatisfiedLinkError** or a related lookup error; that differs from an FFM API error during javac compilation.

**Do not consider successfully launching the jextract tool without compile/run as having tested compatibility.** This is why the example goes through all three steps: generate → compile → invoke.

## 9. Testing Without jextract to Determine Whether the Target JDK Has the Standard FFM API

Before using the tool, you can run a simple FFM smoke test on **JDK 22+**. This snippet only verifies that basic **java.lang.foreign** can compile/run; it does not verify jextract itself.

### File FfmApiCheck.java

~~~java
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;

public class FfmApiCheck {
    public static void main(String[] args) {
        byte[] data = {10, 20, 30};
        MemorySegment segment = MemorySegment.ofArray(data);

        byte middle = segment.get(ValueLayout.JAVA_BYTE, 1);
        System.out.println("FFM byte = " + middle);
        System.out.println("FFM package available");
    }
}
~~~

~~~bash
javac FfmApiCheck.java
java FfmApiCheck
~~~

Stdout on **JDK 22+**:

~~~text
FFM byte = 20
FFM package available
~~~

The example uses memory on the Java heap, so it does not require native access, libclang, or a .so file. If **JDK 17** reports that package **java.lang.foreign** is not found, the cause is that the JDK version does not yet have the standard FFM package, not that jextract is broken.

**Limitation of the test:** JDK22+ having the package does not prove that every symbol generated by jextract25/26 exists in that API. You must still compile the actual generated source.

## 10. Is a Newer jextract Guaranteed to Work with an Older JDK?

**There is no universal guarantee.** The FFM API changed from incubator/preview; even after becoming final in 22, overloads and native access restrictions continued to evolve. Newer generator code may reference APIs only present in newer JDKs.

Some cases:

| Scenario | Reasonable conclusion |
| --- | --- |
| jextract tied to JDK21 preview generates code, compiled on matching JDK21 | May be compatible if preview level and flags match; must run tests |
| jextract tied to JDK25 generates code, compiled on JDK21 | Not compatible by default; 21 is still preview, 25 uses standard API; usually need a build suited for 21 |
| jextract tied to JDK25 generates code, compiled on JDK22 | Depends on generated symbols/overloads; no promise that source is always backward compatible |
| jextract tied to JDK25 generates code, compiled on JDK25 | This is a sensible starting pair, still must check tool, Clang, native ABI |
| jextract tied to JDK25 generates code, compiled/run on JDK27 | May work if compatibility is preserved; do not claim without compile and runtime tests |
| jextract from master branch generates code, compiled on JDK25 | Risks newer APIs; use a JDK25-targeted release/branch or test in practice |

**Right mindset:** "Might still run" does not mean "verified". For production, pinning a tool/JDK pair with passing compile/test results is better than trusting version numbers or a "newer is always better" rule.

### Java classfile version differs from FFM source compatibility

A **.class** file compiled with a newer JDK can cause **UnsupportedClassVersionError** on an older Java runtime. For example, building default classfiles with JDK25 and deploying to JDK21 will be incompatible at the classfile level, regardless of whether the Java source uses FFM.

Using **javac --release N** controls the Java language/API/classfile target at compile time, but **cannot fix** cases where generated code requires an **FFM method not present in N**. If generated Java from jextract25 uses an API only in JDK25, **--release 22** will not make that method exist in JDK22. It is best to use **javac of the target JDK itself**, or control **--release** and compile/test on the runtime target.

## 11. Pin the Native ABI Together with the jextract Version

jextract parses headers via Clang. Results depend on the C preprocessor, platform, compiler flags, OS, and data model.

C example:

~~~c
struct NativePair {
    long first;
    void *second;
};
~~~

- On **Linux x64 LP64**, **long** is usually 8 bytes and a pointer is 8 bytes.
- On **Windows x64 LLP64**, **long** is usually 4 bytes while a pointer is 8 bytes; the struct may insert padding.
- On 32-bit ABIs, pointers and alignment differ again.

Therefore, the same jextract25 build running on two platforms can produce different **MemoryLayout**, Java carriers, and offsets. The jextract guide recommends generating per platform and comparing generated output before sharing a single set of bindings across multiple platforms.

Other factors include:

- **#ifdef _WIN32**, **#if defined(__linux__)** select different declarations;
- **-D** macro flags change struct/feature selection;
- **-I / --include-dir** determine which headers are parsed;
- clang target triple and compiler-specific attributes can affect layout;
- a **libfoo.so** version different from the **foo.h** version can change the ABI while keeping the same symbol names.

In the repository, pin at a minimum:

~~~text
TARGET_JDK       = 25 (vendor/build explicitly recorded)
JEXTRACT_RELEASE = build targeting JDK25, pinned build/commit
LLVM_LIBCLANG    = version supported by the jextract distribution
TARGET_OS_ARCH   = linux-x64 or matrix per platform
HEADER_VERSION   = revision/tag of the native SDK
NATIVE_LIBRARY   = version/ABI matching the header
JEXTRACT_FLAGS   = include dirs, macros, package, library
~~~

This is an *illustrative configuration template*, not the standard format of a specific tool. For reproducibility, versions and checksums must be recorded as real values in the project.

If any **C header, compiler flags, native library, jextract version, or target JDK** changes, evaluate regenerating bindings and running at least a smoke test.

## 12. CI/CD: How to Avoid "Works on My Machine"?

A practical pipeline should have separate steps:

~~~text
Setup target JDK (pin major/vendor/build)
        |
Install/pin jextract release + checksum
        |
Install/verify LLVM/libclang and C compiler
        |
Compile native library against pinned headers
        |
Run jextract to a clean generated/ directory
        |
Compile generated .java with target javac
        |
Compile smoke test against generated classes
        |
Run java with native access + correct library path
        |
Record versions, logs, generated diff, test result
~~~

An illustrative Linux script with strict checks (assuming the files in section 8 are already present):

~~~bash
#!/usr/bin/env bash
set -euo pipefail

: "$JAVA_HOME"
: "$JEXTRACT_HOME"

"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
"$JEXTRACT_HOME/bin/jextract" --version

rm -rf generated classes
mkdir -p generated classes native

cc -std=c11 -Wall -Wextra -Wpedantic -fPIC -shared \
  native/adder.c -o native/libadder.so

"$JEXTRACT_HOME/bin/jextract" \
  --output generated \
  --target-package demo.bindings \
  --library adder \
  native/adder.h

find generated -type f -name '*.java' -print0 \
  | xargs -0 "$JAVA_HOME/bin/javac" -d classes

"$JAVA_HOME/bin/javac" -cp classes -d classes App.java

LD_LIBRARY_PATH="$PWD/native" \
  "$JAVA_HOME/bin/java" --enable-native-access=ALL-UNNAMED \
  -cp classes App
~~~

**Condition for using the script:** Run only in a **verified lab/sandbox directory**, because **rm -rf generated classes** deletes those two output directories. This is **a sample script** for CI, not meant to be run on an important working tree; in a real project, use the build tool's own output directory and avoid unverified directory-cleanup commands.

When CI runs across multiple OSes/ABIs, **do not reuse generated bindings from Linux x64 for Windows x64 by default**. You can generate per target in the pipeline or verify that the declarations/ABI are truly portable before sharing output.

### Generate at build time or commit generated code?

Both strategies are valid:

- **Commit generated Java source:** the main build does not need libclang/jextract every time; reviewing diffs is easier and output is easy to pin. Requires a controlled regeneration process when upgrading headers/tool/JDK.
- **Generate in the build pipeline:** always stays in sync with pinned C headers; however, you must ensure the jextract binary, libclang, compiler environment, and flags are fixed so results are reproducible.

The OpenJDK jextract guide describes the common approach of generating from headers and checking the created sources into the project, regenerating only when the native library or jextract changes. There is no requirement to run jextract when starting the Java application.

## 13. Verifying Generated Bindings Instead of Trusting Class Names from Old Examples

Generated class names and helpers can change between jextract generations. With the current guide, an **adder.h** header typically produces **adder_h** and static method **add_ints**. But if you take tutorial code from an old blog or use a different JDK-target branch:

1. Open the generated source to confirm the **package** and main class name.
2. Check whether **--header-class-name** is supported by the tool if you need to fix the name.
3. Inspect the static wrapper signatures for C functions rather than assuming Java carrier types.
4. Compile all generated source before writing the client.
5. You can inspect the compiled class with **javap** to see the actual signatures.

Example with the compiled class:

~~~bash
"$JAVA_HOME/bin/javap" -classpath classes demo.bindings.adder_h
~~~

If another tool build generates different method names or carriers, follow the actual generated class. **Update the Java caller code** accordingly; do not alter the C ABI or fake wrapper signatures to force compilation.

Some generated code includes helpers such as **Point.layout()**, **Point.sizeof()**, **Point.x(segment)**, **foo$address()**, **foo$descriptor()**, **foo$handle()** depending on the version. These are utilities generated by jextract, **not standard MemorySegment methods**; when migrating between jextract versions, this part also needs source compatibility testing.

## 14. JDK17/JDK21: What to Do with Systems That Cannot Upgrade?

### JDK17 (incubator-era)

JDK17 has the Foreign Function & Memory API in an experimental stage, differing significantly from the standard **java.lang.foreign** in JDK22+. You cannot guarantee that source generated by jextract25 will run on JDK17 simply by adding **--add-modules jdk.incubator.foreign**. When forced to run JDK17:

- find a jextract binary/tag released for the exact incubator API of JDK17;
- keep the JDK17 toolchain + required flags consistent;
- check whether the old branch still actually builds;
- consider staying on JNI/JNA or updating the runtime if no suitable tool/binding exists.

Do not promise that a single compile flag will backport APIs from JDK25 to JDK17.

### JDK21 LTS (preview-era)

JDK21 has **java.lang.foreign** as a preview. To compile/run source that is actually compatible with JDK21 preview, you may need:

~~~bash
javac --enable-preview --release 21 MyApp.java
java --enable-preview MyApp
~~~

This is **a command template for source written against the JDK21 preview API**, not a way to "force" bindings generated by jextract25 onto JDK21. In a real project you need to add classpath/module path, generated sources, native access flags, and the main class name as appropriate.

The OpenJDK jextract README gives the **jdk21** branch as an example for a tool build targeting JDK21. If using that branch, check the build prerequisites of **that exact branch**, rather than copying Gradle commands verbatim from the evolving master branch.

### JDK22 and JDK25 (final-era)

JDK22 is the FFM final milestone; JDK25 is a newer LTS. When targeting JDK22, you can look for a jextract release/branch generating 22-compatible code. When targeting JDK25, prefer releases/binaries labeled **JDK25**; jextract master at any given time is not guaranteed to target 25.

**--enable-preview is not needed just to use final FFM on JDK22/25.** However, native access has its own restrictions: when performing downcalls/loading libraries, use **--enable-native-access** or the corresponding module configuration per the exact target JDK. The preview flag and native access flag solve **two different problems**.

## 15. When Upgrading Versions: Evaluating Source Compatibility, Binary Compatibility, and ABI

Suppose a project is currently using JDK25 + jextract25 and wants to upgrade to JDK27.

Do not change all three components at once without checkpoints. Safe workflow:

1. **Keep** the current generated bindings and native SDK/library in source control.
2. **Upgrade the JDK runtime/compiler** first on a test branch; compile the old generated code and run native integration tests.
3. If the compiler/runtime has issues or new features are needed, choose a **jextract documented as supporting target JDK27**; verify the binary actually exists and matches the OS/CPU.
4. Regenerate bindings into a **new** output directory without overwriting the old version immediately.
5. Diff the generated source: package/class names, field accessors, var handles, memory layouts, SymbolLookup, Linker callsites, C macro processing.
6. Compile, run smoke tests and the native regression suite on the target runtime; check native access permissions.
7. Update lockfiles/build instructions and caller code if the generated API changed.
8. After QA, intentionally replace the old output.

A transition checklist:

| Changed component | What to check |
| --- | --- |
| Only JDK patch 25.0.x | JDK compatibility/runtime/native access diagnostics, regressions |
| JDK25 → JDK27 | FFM methods, classfile, native access policy, generated bindings |
| Only jextract release | Generated helper names/schemas, layout code, wrapper implementation |
| Only native SDK/header | Function signatures, macros, struct offsets, enums, pointer ownership |
| Only architecture Linux x64 → ARM64 | Pointer width, C ABI, alignment, calling convention |
| OS change Linux → Windows | DLL loading, LLP64 vs LP64, C long, wchar_t, compiler headers |

Key point: **you can recompile generated source for use on a new JDK** without regenerating yet, but only accept this when proven by compile/runtime/integration tests. Conversely, **regenerating does not automatically guarantee** C library binary compatibility if the header/ABI is wrong.

## 16. Common Errors and How to Diagnose the Right Layer

| Symptom | Primary suspect | Action |
| --- | --- | --- |
| **jextract: command not found** | Not installed or wrong PATH | Invoke binary by absolute path; check --version |
| jextract tool fails to start due to Java version | Tool's host runtime mismatch | Check which JDK the release requires, pick the right tool/binary |
| **Unable to load libclang** | Missing/wrong LLVM libclang or architecture | Check libclang tool dependency, native library loader |
| **fatal error: 'foo.h' file not found** | Wrong include path or SDK header | Use --include-dir and verify exact header |
| Generated code calls **java.lang.foreign** but JDK17 cannot find it | API does not exist in JDK17 | Use target JDK22+ or the right incubator generator build |
| Preview error on JDK21 | Preview not enabled or source level mismatch | Use target21 preview flags and matching generator21 |
| **cannot find symbol / no suitable method** in javac | Binding generated different FFM API than target | Compare imports/methods with JDK docs and jextract --version |
| **class file has wrong version** | Newer compiler, older runtime | Align javac/java target; check --release |
| **NoSuchMethodError/NoClassDefFoundError** at runtime | Compile/runtime mismatch or wrong classpath | Align JDK, dependencies, rebuild generated classes |
| **IllegalCallerException** / native access warning | Appropriate native access not granted | --enable-native-access for the right module/classpath |
| **UnsatisfiedLinkError** when loading .so/.dll | Native library not found, missing symbol, wrong ABI/arch | Check library path, exported symbols, dependencies, bitness |
| Native call returns wrong value or crashes | C ABI differs from parsed header | Check sizeof/offsetof, calling convention, macros |
| Generated wrapper class name changed | Tool version or CLI changes | --header-class-name if supported; compile + review diff |
| Java source missing struct/bitfield/macro | jextract limitation or symbol filter | Check warnings, unsupported features, write a C wrapper |
| Java code runs on Linux but fails on Windows | Platform-dependent layout/data model | Generate and test per OS/ABI, do not share blindly |

**Do not treat everything by upgrading the JDK.** libclang errors happen before Java binding compilation; native loader errors can happen after Java compilation is completely correct. Diagnosing the right stage saves time and avoids unnecessary changes.

### Header errors and features not supported by jextract

The jextract guide notes limitations may include **function-like macros**, **C bitfields**, **opaque incomplete types**, certain C scalars not fully supported by the ABI, or special linker options. For example, to capture **errno** via **captureCallState**, you may need to write/adjust bindings manually or create a corresponding helper rather than expecting every jextract version to auto-generate that linker option.

If jextract prints a warning skipping a C declaration, that is **not necessarily due to choosing the wrong JDK**. Check the unsupported features of that exact tool version, understand the header, and design a C façade when needed.

## 17. Important Questions When Pinning jextract in Enterprise

### Is it mandatory to pin jextract to the exact major JDK?

**There is no universal one-to-one rule for every binary and release.** However, pairing **jextract targeting JDK N's FFM API ↔ target JDK N** is a safe starting point. The final decision rests on **release notes, --version, generated source compilation, and runtime tests**. Especially with preview/incubator, differences are often large, so mismatching versions carries high risk.

### Can I download the latest jextract and use it to generate bindings for JDK21?

Do not assume so. **Master** usually follows the new mainline JDK; JDK21 uses the preview FFM API. Find a historical build for 21, such as the jdk21 branch when available, or upgrade the runtime.

### Can I use jextract25 generated source on JDK27?

**Possibly**, if the generated code only uses APIs that remain compatible and the runtime/native ABI meets requirements, but you must verify with **javac/java on JDK27**. Never guarantee it from the version label alone.

### Is jextract needed on production servers?

**No, if you deploy compiled Java classes or a prebuilt JAR.** jextract is a **code-generation/build-time** tool. Production needs the matching Java runtime, native libraries and OS dependencies, and native access configuration; there is no need to run the generator at runtime unless your application has a very special workflow.

### Can I run jextract on C++ headers directly?

jextract primarily parses **C headers**. C++ source can provide an **extern "C" façade** containing a C ABI and then generate bindings from that façade header. C++ overloads/templates/name mangling are not solved simply by pointing jextract at a complex C++ header.

### Does jextract automatically fix ABI differences between LP64 and LLP64?

It parses headers and generates layouts per platform, but output depends on the **exact target ABI**. What you must ensure is that **the generating machine matches the target platform** or you have a cross-generation/testing approach proving the layout is correct. Do not take Linux-generated source with 8-byte C long and use it on Windows with 4-byte C long without testing.

### Should we delete generated sources and regenerate on every CI run?

You can, if the jextract binary, JDK, clang, headers, and flags are all pinned and the build is reproducible. However, the OpenJDK guide also accepts the workflow of generating once, checking generated sources into the codebase, and regenerating when version/header changes occur. Choose a clear policy rather than depending on a "latest" artifact that changes daily.

## 18. Decision Checklist and PASS Criteria

### Tool selection

- [ ] Clear **target JDK major, vendor/build, OS, and architecture**.
- [ ] jextract release/branch documented as supporting the **target FFM API**.
- [ ] **jextract --version** runs on the host; binary/platform verified.
- [ ] **jextract --help** confirms the CLI flags in use.
- [ ] Compatible libclang, header include paths, and macros match the native SDK.
- [ ] Tool binary/commit, JDK, LLVM, and native SDK pinned and download source verified.

### Generate/compile

- [ ] Source generated into a clean directory, package/header class name determined.
- [ ] No important Clang warnings ignored.
- [ ] Generated imports/methods match **java.lang.foreign** of the target JDK.
- [ ] **Target JDK javac** compiles all generated .java files.
- [ ] Java caller compiles cleanly against generated wrappers.
- [ ] Not using **--release** to mask missing APIs on the target JDK.

### Runtime/ABI

- [ ] Actual runtime java matches the target JDK.
- [ ] Native access granted for the right module/classpath.
- [ ] Native library found and matches CPU/OS/ABI.
- [ ] **A real downcall** executed, return value or side effects verified.
- [ ] If structs exist, **sizeof/offsetof/alignment** cross-checked with the C compiler.
- [ ] Smoke/integration tests run on every supported OS/arch.
- [ ] Generated bindings/version history reviewed and recorded.

Only when the **tool, generated source, javac, JVM runtime, and native library** all pass their respective checks is there a basis to call a jextract/JDK pair "suitable" for a specific project.

## 19. Exercises and Practical Scenarios

**Question 1.** Why is installing jextract25 on a JDK25 machine and successfully running **jextract --version** not enough?

**Answer:** The version command only proves the tool launches. The generated binding must still compile on JDK25 and call a real native function on the right ABI.

**Question 2.** The generated source imports **jdk.incubator.foreign**, but the project uses JDK25. Should we just change the import line to java.lang.foreign?

**Answer:** No. API classes/method signatures/semantics have changed; you need to regenerate from a jextract suited for target25 or migrate the code with testing.

**Question 3.** The generated source imports **java.lang.foreign** and the target is JDK21. Is compatibility guaranteed?

**Answer:** Not yet. JDK21 also used that package in its preview stage, but APIs between 21 and final JDK22+/JDK25 can differ. You need the matching generator/flags and actual compile/run on target21.

**Question 4.** Does JDK25 need **--enable-preview** just to use FFM?

**Answer:** No. FFM has been final since JDK22. However, native linker calls are restricted operations and may require **--enable-native-access** per runtime policy.

**Question 5.** The binding code compiles with JDK25, but at runtime it throws **UnsatisfiedLinkError**. Is it definitely a wrong jextract version?

**Answer:** No. Check .so/.dll loading, library path, symbol exports, OS/arch, and ABI; this error occurs at the runtime native link stage.

**Question 6.** Is it safe to use Linux x64 generated bindings on Windows x64 if both use JDK25?

**Answer:** Not necessarily. C long is usually 8 bytes on LP64 Linux x64 but 4 bytes on LLP64 Windows x64; macros, pointer handling, calling conventions, and library names also differ.

**Question 7.** Does using **javac --release 22** make a jextract25 binding automatically compatible with JDK22?

**Answer:** No. If the code uses FFM APIs absent in JDK22, the compiler will report an error when checking the target API, or the application will fail if bypassed.

**Question 8.** Why should we pin the Clang/libclang version even though the Java runtime is already pinned?

**Answer:** jextract parses C headers using Clang. Different parser/compiler/target flags can produce different output or warnings, independent of Java FFM directly.

**Question 9.** A project has a C++ template library, and jextract only sees C-compatible headers. What should be done?

**Answer:** Build an explicit C ABI wrapper, use extern "C" appropriately, and generate bindings from the exported C declarations. Do not treat jextract as a translator for all of C++ to Java.

**Question 10.** When upgrading from JDK25 to JDK27, must we regenerate all bindings immediately?

**Answer:** Not mandatory if the old generated bindings compile/run/integration-test on 27. However, if new features are needed or there is a tool/API mismatch, choose a matching jextract targeting 27 if available, regenerate on a test branch, review the diff, and retest native integration.

**Exercise A:** With the same **adder.h** header, save two sets of generated sources from two jextract releases (pick two builds that can run). Compare **imports**, class names, wrapper signatures, and linker calls. Record differences rather than just comparing source line counts.

**Exercise B:** Use an **older JDK's javac** to compile bindings generated for a newer JDK. Categorize errors into: missing package/class, missing signature, missing preview flag, or different carrier/overload.

**Exercise C:** Change **int** in the C header to **long**, generate on Linux x64 and Windows x64. Compare differences in Java carriers/layouts, then measure **sizeof(long)** with each OS's C compiler. Do not use one machine's result to represent both.

**Exercise D:** Create two CI profiles: **JDK25 + jextract target25** and **JDK27 + jextract proven compatible with 27**. Both must compile generated bindings and run to return **native result = 42**. If the second profile lacks a suitable tool build, mark a specific blocker rather than downloading an untargeted "latest" binary.
