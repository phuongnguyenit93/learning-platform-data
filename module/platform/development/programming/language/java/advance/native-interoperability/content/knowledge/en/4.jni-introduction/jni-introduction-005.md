# Compiling, Linking, and Exporting Symbols of a Shared Library for Your First JNI

Declaring a `native` method in Java only creates a **function call contract**; the JVM does not yet have the machine code to execute it. For a JNI call to run, you must compile the Java code, generate the JNI prototype, compile the C/C++ code with the correct headers and ABI, link it into a **shared library**, have the JVM locate and load the library, and ensure the library **exports the exact symbol** that the JVM looks for.

This lesson walks through that entire chain with Java 17+ and C11. The final result is running `demo.NativeMath.add(7, 35)` from Java and receiving `42` from native code; knowing how to inspect `.so`, `.dylib`, and `.dll` libraries and trace the root cause when encountering `UnsatisfiedLinkError`.

## 1. Distinguishing compilation, linking, library loading, and JNI method binding

~~~text
NativeMath.java
    |
    | javac -h ... -d ...
    +--> NativeMath.class ---------------------+
    |                                         |
    +--> demo_NativeMath.h                    |
                |                             |
nativemath.c ---+                             |
    |                                         |
    | C compiler: compile -c                  |
    v                                         |
nativemath.o / nativemath.obj                 |
    |                                         |
    | Native linker: -shared / -dynamiclib     |
    v                                         |
libnativemath.so / libnativemath.dylib         |
               / nativemath.dll              |
    |                                         |
    | System.loadLibrary("nativemath")         |
    v                                         v
       JVM loads library, looks up symbol Java_demo_NativeMath_add
                           |
                           v
                        JNI call
~~~

The steps have distinct meanings:

1. **Java compilation:** `javac` checks types, produces `.class` files, and (with `-h`) generates C headers for `native` declarations; it **does not** compile C and does not provide the native library.
2. **C/C++ compilation:** the compiler turns each source file into an object file `.o`/`.obj`; `jni.h`, the header generated by `javac -h`, and project headers must be in the include path.
3. **Native linking:** the linker combines object files with the required dependencies into a shared library in the operating system's format: ELF `.so` (Linux), Mach-O `.dylib` (macOS), PE `.dll` (Windows).
4. **Runtime loading:** `System.loadLibrary` asks the JVM/OS to find and load the library file along with its dependencies. Failing to find the file or failing to load it can both cause `UnsatisfiedLinkError`.
5. **JNI method binding:** when the `native` method is resolved, the JVM looks for an export with the matching JNI name and signature (or a registration via `RegisterNatives`). Successfully loading `.so/.dll` **does not prove** the method has been bound successfully.

A **static** library (`.a` or static `.lib`) is a collection of object files used by the linker when creating a binary; it does not directly replace a shared library that `System.loadLibrary` loads in the usual way. On Windows, a `.lib` file can also be an **import library** for a `.dll`: you must distinguish its role based on the linker output and toolchain.

| Stage | Primary input | Output / typical error |
| --- | --- | --- |
| `javac` | `.java` | `.class`, `.h`; Java type error or invalid declaration |
| C compiler (`-c`) | `.c` + `.h` | `.o`/`.obj`; missing header, mismatched prototype, syntax error |
| Native linker | object files + libraries | `.so/.dylib/.dll`; `undefined reference`, `unresolved external symbol` |
| OS/JVM loader | native binary + dependencies | loaded image or missing file, wrong architecture, missing dependency error |
| JNI method lookup | Java declaration + exported name/registration | native function called or `UnsatisfiedLinkError` due to missing symbol/signature |

## 2. Preparing the environment and directory structure

You need JDK 17 or later (containing `javac`, `java`, `jni.h`), a C compiler and linker matching the JVM's architecture (64-bit for 64-bit, ARM64 for ARM64, etc.), and the corresponding terminal. Use the **JDK that runs the program** to get the JNI headers at build time; verify that `JAVA_HOME` points to the actual JDK directory, not the `bin` directory or a JRE missing headers.

Check:

~~~sh
java -version
javac -version
echo "$JAVA_HOME"
~~~

On Windows Command Prompt:

~~~bat
java -version
javac -version
echo %JAVA_HOME%
~~~

In the JDK, two include directories are commonly used:

- `$JAVA_HOME/include`: contains `jni.h` and shared headers.
- `$JAVA_HOME/include/linux`, `darwin`, or `win32`: contains `jni_md.h` and platform-specific declarations.

Example project:

~~~text
native-demo/
├── src/
│   └── demo/
│       └── NativeMath.java
├── native/
│   └── nativemath.c
└── build/                   (created during the build process)
    ├── classes/
    ├── include/
    └── lib/
~~~

From here on, all commands are run from the `native-demo` directory. The source consists of **two files** `src/demo/NativeMath.java` and `native/nativemath.c`; the `build` directories are output. The paths in the example contain no spaces to keep commands short, but when a real project has spaces you must quote paths appropriately.

Do not hard-code the path to an arbitrary JDK from another machine: build on the target operating system using a compatible compiler/headers/architecture and then package the corresponding binary.

## 3. Step 1: declaring the native method on the Java side

Create `src/demo/NativeMath.java` with the complete content:

~~~java
package demo;

public final class NativeMath {
    private NativeMath() {
    }

    static {
        System.loadLibrary("nativemath");
    }

    public static native long add(int left, int right);

    public static void main(String[] args) {
        System.out.println("7 + 35 = " + add(7, 35));
    }
}
~~~

Explanation of each point:

- `package demo` is part of the class's **binary name**, and also affects the symbol name according to the JNI standard.
- `native` states that the method body resides outside Java bytecode; in Java source it ends with `;`, with no implementation block.
- `static` makes the second JNI parameter a `jclass`; if this were an instance method, the second parameter would have to be `jobject`.
- Java `int` corresponds to JNI `jint`, Java `long` corresponds to JNI `jlong`; the example returns `long` so that adding two `int` values does not cause 32-bit addition overflow.
- `System.loadLibrary("nativemath")` uses the **logical** name of the library, without passing the file extension, `lib` prefix, or file path. The JVM maps it to the operating system's naming convention.
- The `static` block runs when the class is initialized; loading errors typically appear at this point, before the `main` body calls the native method.

If you want to load a file by an absolute path, use `System.load(absolutePath)`, though in that case you must supply the full filename and absolute path. The choice of loader does not replace resolving the dependent libraries that the OS loader requires.

### 3.1. Generating the class and JNI header: `javac -h`

Linux/macOS:

~~~sh
mkdir -p build/classes build/include build/lib
javac -h build/include -d build/classes src/demo/NativeMath.java
~~~

Windows Command Prompt:

~~~bat
mkdir build\classes build\include build\lib
javac -h build\include -d build\classes src\demo\NativeMath.java
~~~

After the command, the important files include:

~~~text
build/classes/demo/NativeMath.class
build/include/demo_NativeMath.h
~~~

`-d` places class files into a directory with the package structure; `-h` places the JNI header into the specified directory. Do not replace `-h` by guessing and typing symbols manually. Whenever you change the package, class, `native` method, overloads, or parameter/return types, **regenerate the header** and rebuild the C/C++ code.

The header generated by `javac -h` will have a declaration equivalent to the following (this is an illustrative excerpt, **not a replacement for the entire generated header file**):

~~~c
#include <jni.h>

/*
 * Class:     demo_NativeMath
 * Method:    add
 * Signature: (II)J
 */
JNIEXPORT jlong JNICALL Java_demo_NativeMath_add
  (JNIEnv *, jclass, jint, jint);
~~~

`(II)J` is the JVM method descriptor: two arguments `I` = `int`, result `J` = `long`. A Java method descriptor and a C ABI name are two different concepts: the descriptor describes types, while the exported symbol is the name seen by the runtime/linker.

You can inspect the descriptor from the compiled class:

~~~sh
javap -s -classpath build/classes demo.NativeMath
~~~

In the output, the corresponding method has the descriptor `(II)J`. Do not infer this manually from `.java` filenames if the project has complex packages/overloads; the compiler and `javap` are the direct sources of verification.

## 4. Step 2: implementing the exact prototype and JNI export in C

Create `native/nativemath.c`:

~~~c
#include "demo_NativeMath.h"

JNIEXPORT jlong JNICALL
Java_demo_NativeMath_add(JNIEnv *env, jclass declaring_class,
                         jint left, jint right) {
    (void) env;
    (void) declaring_class;

    return (jlong) left + (jlong) right;
}
~~~

This is the **complete C code for the native part** of the example. It has no `main` because the entry point is the JNI function called by the JVM after loading the library. Do not run `nativemath.c` as a standalone C program.

The JNI signature has four parts that cannot be arbitrarily changed:

1. `JNIEXPORT`: platform-appropriate visibility/export declaration in the JNI headers; especially required on Windows so the DLL has exported symbols.
2. `jlong`: return type corresponding to Java `long`.
3. `JNICALL`: calling convention according to JNI/target ABI. On 32-bit Windows this is especially important; do not omit it just because commands work on a 64-bit machine.
4. `Java_demo_NativeMath_add(JNIEnv *, jclass, jint, jint)`: JNI-formatted name, interface pointer, class of the static method, and two arguments.

The `jni.h`/`jni_md.h` headers provide the macros and types. The declaration in `demo_NativeMath.h` helps the compiler catch signature mismatches instead of letting the error slip through to runtime.

The line `(jlong) left + (jlong) right` performs addition in the 64-bit domain. If you add `left + right` directly before casting, two 32-bit integers in C can overflow, leading to undefined behavior. Two 32-bit `jint` values added after widening to 64-bit `jlong` always stay within the `jlong` range.

The two parameters `env` and `declaring_class` are currently unused; `(void)` prevents the compiler from warning about unused parameters under warning flags. In examples that need to call the JNI API, `env` is the interface to the JVM, not an arbitrary pointer that can be used on another thread.

### 4.1. Exporting a symbol is different from making a method `public` in Java

Java `public` controls Java access rights; it does not export a native symbol. On the native side, the symbol name, visibility, and calling convention determine whether the runtime can find the JNI function.

For example on Linux, when exported properly, the dynamic symbol table contains `Java_demo_NativeMath_add`. If building with `-fvisibility=hidden` for a large C/C++ project, `JNIEXPORT` is still designed to mark JNI entry points that need to be visible to the linker/loader. If you define another wrapper API yourself, it may need its own export rules.

Do not rename the C function to `add` just because Java names it `add`: the JVM uses the JNI naming rules or `RegisterNatives`, and does not automatically map arbitrary C names.

## 5. Steps 3 and 4 on Linux: compiling the object then linking `.so`

Prerequisites: POSIX shell, a C compiler such as GCC/Clang, `JAVA_HOME` pointing to the JDK, run from `native-demo`.

~~~sh
cc -std=c11 -O2 -Wall -Wextra -Wpedantic -fPIC \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  -Ibuild/include \
  -c native/nativemath.c -o build/nativemath.o

cc -shared build/nativemath.o -o build/lib/libnativemath.so
~~~

The first command **compiles** into an object file; the second **links** that object into a shared object. You can also combine them into a single command so the compiler driver performs both steps automatically:

~~~sh
cc -std=c11 -O2 -Wall -Wextra -Wpedantic -fPIC -shared \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  -Ibuild/include \
  native/nativemath.c -o build/lib/libnativemath.so
~~~

Flag explanations:

- `-std=c11`: selects the C dialect; `-Wall -Wextra -Wpedantic`: catches many issues at compile time (does not guarantee all bugs are caught).
- `-O2`: optimizes in a normal build; for debugging you can replace it with `-O0 -g`.
- `-I...`: adds a search path for **headers** at compile time, not a library search path at runtime.
- `-fPIC`: generates position-independent code suitable for linking into a shared object on many ELF targets; omitting this flag can cause relocation errors during linking.
- `-c`: compile only, do not link; `-o build/nativemath.o` sets the object output name.
- `-shared`: creates a shared library; `-o build/lib/libnativemath.so` chooses the output name.
- Pass the object files into the link command; with external libraries, the order of objects and `-l...` can affect symbol resolution on some linkers.

Why is the name `libnativemath.so`? With Java `System.loadLibrary("nativemath")`, the logical name `nativemath` is normally mapped by the JVM to `libnativemath.so` on Linux. Do not write `System.loadLibrary("libnativemath.so")`.

### 5.1. Running from Java

~~~sh
java -Djava.library.path=build/lib -cp build/classes demo.NativeMath
~~~

When compiled and loaded correctly, the **exact stdout** is:

~~~text
7 + 35 = 42
~~~

`-cp build/classes` specifies the classpath for Java bytecode; `-Djava.library.path=build/lib` provides the location for the JVM to find JNI libraries. These two paths resolve **two different kinds of files**. Place `-Djava.library.path` before the main class name, because it is a JVM option.

The command does not require placing `libnativemath.so` in the same directory as `.class` files; the library only needs to be somewhere the loader can find it according to the specified mechanism.

## 6. Steps 3 and 4 on macOS: compiling then creating `.dylib`

Use a macOS JDK of the same architecture (Apple Silicon/Intel) and the Clang compiler. Keep the two Java/C source files unchanged:

~~~sh
mkdir -p build/classes build/include build/lib
javac -h build/include -d build/classes src/demo/NativeMath.java

cc -std=c11 -O2 -Wall -Wextra -Wpedantic -fPIC \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/darwin" \
  -Ibuild/include \
  -c native/nativemath.c -o build/nativemath.o

cc -dynamiclib build/nativemath.o -o build/lib/libnativemath.dylib
java -Djava.library.path=build/lib -cp build/classes demo.NativeMath
~~~

The output is still:

~~~text
7 + 35 = 42
~~~

On macOS, `-dynamiclib` is the standard Clang toolchain option to create a dynamic library; it differs from `-shared` in the Linux example. The corresponding filename is normally `libnativemath.dylib`. Some older JNI environments still mention `.jnilib`; for modern builds, use the name the JVM maps on the target JDK and verify directly with the example in section 9.

If the Java build runs on Apple Silicon while the `.dylib` file contains an Intel-only binary, or vice versa, the loader may report an architecture incompatibility error. Do not fix this error by renaming the file extension: you must build for the right target/architecture or create a universal binary using the appropriate workflow.

## 7. Steps 3 and 4 on Windows: MSVC, `.dll`, and exports

The Windows example uses **x64 Native Tools Command Prompt for VS** or Developer Command Prompt with `cl` and `link` in `PATH`. Set `JAVA_HOME` to the corresponding Windows x64 JDK. The commands below are for **Command Prompt**, not PowerShell environment variable syntax.

~~~bat
mkdir build\classes build\include build\lib
javac -h build\include -d build\classes src\demo\NativeMath.java

cl /nologo /W4 /O2 /LD ^
  /I"%JAVA_HOME%\include" ^
  /I"%JAVA_HOME%\include\win32" ^
  /I"build\include" ^
  native\nativemath.c ^
  /link /OUT:build\lib\nativemath.dll

java -Djava.library.path=build\lib -cp build\classes demo.NativeMath
~~~

The `^` character is the line continuation character in Windows Command Prompt; if you copy the command into another environment, turn it into a single line or use the corresponding shell syntax. If `JAVA_HOME` contains spaces, quote it as in the example.

Output:

~~~text
7 + 35 = 42
~~~

In MSVC, `/LD` requests building a DLL, and `/OUT:...dll` chooses the output file. `JNIEXPORT` in the Windows JDK expands to the appropriate DLL export mechanism, so a properly declared JNI function usually appears in the export table. Intermediate `.obj`, `.exp`, and `.lib` files may also be generated by the linker; Java loads **`nativemath.dll`**, not `nativemath.lib`.

If using MinGW-w64 instead of MSVC, you need a GCC compiler compatible with the Windows target/architecture/JDK, replace the platform include with `win32`, and create `nativemath.dll` with `-shared`. Do not blindly mix objects, runtime libraries, and import libraries from toolchains with different ABIs without verifying compatibility.

**A Windows difference to remember:** when Windows reports that it cannot load a DLL, the problem may be `nativemath.dll` itself, a bitness mismatch, or a missing **dependent** DLL. Merely checking that the target file exists is not enough to conclude the library can be loaded.

## 8. Checking whether the library exported the right symbol

After building, you should inspect the **native dynamic/export symbol table**. These commands are inspection commands and do not modify files:

| Operating System | Inspection command | What to look for |
| --- | --- | --- |
| Linux | `nm -D --defined-only build/lib/libnativemath.so` | `Java_demo_NativeMath_add` present in dynamic defined symbols |
| Linux | `readelf -Ws build/lib/libnativemath.so` | Symbol has appropriate binding/visibility and is defined |
| macOS | `nm -gU build/lib/libnativemath.dylib` | `_Java_demo_NativeMath_add` present (leading underscore is normally shown by Mach-O tools) |
| Windows/MSVC | `dumpbin /exports build\lib\nativemath.dll` | JNI export name present for the method |
| Linux/macOS | `file build/lib/libnativemath.so` / `file build/lib/libnativemath.dylib` | Binary format and architecture match target |

Linux example filtering for the exact symbol:

~~~sh
nm -D --defined-only build/lib/libnativemath.so | grep Java_demo_NativeMath_add
~~~

Illustrative output line (address values vary per build):

~~~text
0000000000001100 T Java_demo_NativeMath_add
~~~

`T` normally indicates the symbol is in the defined code/text section. On Linux, `nm` without `-D` may list the regular symbol table, whereas the loader needs symbols it can find in the **dynamic symbol table**; use `nm -D` or `readelf -Ws` for runtime export questions.

macOS:

~~~sh
nm -gU build/lib/libnativemath.dylib | grep Java_demo_NativeMath_add
otool -L build/lib/libnativemath.dylib
~~~

Windows (Developer Command Prompt):

~~~bat
dumpbin /exports build\lib\nativemath.dll
dumpbin /dependents build\lib\nativemath.dll
~~~

If the exported name is wrong, Java may load the library successfully and only throw `UnsatisfiedLinkError` **when calling the native method**. If the library has the symbol but the DLL/shared library is missing a dependency or has the wrong architecture, the error appears earlier during loading.

### 8.1. Meaning of `JNIEXPORT`, `JNICALL`, and C++ name mangling

In C++, function names are usually **name-mangled** to encode namespaces and parameter types. According to JNI rules, the JVM looks for `Java_demo_NativeMath_add`, and does not automatically understand a differently mangled C++ name. If you rename `native/nativemath.c` to `native/nativemath.cpp` and compile as C++, define the entry point with **C language linkage**:

~~~cpp
#include "demo_NativeMath.h"

extern "C" JNIEXPORT jlong JNICALL
Java_demo_NativeMath_add(JNIEnv *env, jclass declaring_class,
                         jint left, jint right) {
    (void) env;
    (void) declaring_class;
    return (jlong) left + (jlong) right;
}
~~~

`extern "C"` preserves C linkage for the symbol name; `JNIEXPORT` handles export/visibility; `JNICALL` specifies the calling convention. These are three distinct concepts and cannot be arbitrarily substituted for one another.

The header generated by `javac -h` usually already wraps the prototype in an `extern "C"` guard when compiling C++, but writing it explicitly on the implementation helps readers recognize the ABI contract. When switching to C++, use the `c++`/`g++`/`clang++` compiler driver or `cl` in C++ mode for both compiling and linking as appropriate, because the library may need the C++ runtime. Do not just change the source extension and continue assuming plain C linking.

### 8.2. JNI names for overloaded methods

For a method without native overloads, the short name in the example is:

~~~text
Java_demo_NativeMath_add
~~~

If there are **multiple native methods with the same name** in one class, JNI uses a long name containing encoded parameter types, for example `(int, int)` has the suffix `__II`. The JVM follows the rule of looking up the short name first and then the long name; overload cases should not be handled by manual guessing.

Characters in package/class/method names also have escaping rules (for instance, underscores in Java names are specially encoded), so **always** re-run `javac -h`. Renaming `demo.NativeMath` to another package name without rebuilding `nativemath.c` is a classic cause of the export existing while the JVM fails to find the right method.

`RegisterNatives` is another option: native code registers function pointers by name/descriptor, usually from `JNI_OnLoad`. In that case, each function's Java entry point **does not necessarily** have to be exported under a `Java_...` name, but the `JNI_OnLoad` symbol and the registration logic must be exported/implemented properly. For your **first JNI**, using the automatically exported names from `javac -h` is the easiest path to verify with the fewest moving parts.

## 9. Distinguishing three paths: include path, library link path, and runtime search path

Three kinds of paths are often confused:

| Path | When it is used | Examples |
| --- | --- | --- |
| Header include path | C compiler reads declarations | `-I"$JAVA_HOME/include"`, `-Ibuild/include` |
| Linker library search path | Native linker finds `-lfoo` or import library | `-Lvendor/lib -lfoo`, MSVC `/LIBPATH:...` |
| Runtime shared-library search path | JVM/OS loader loads `.so/.dylib/.dll` and dependencies | `-Djava.library.path=build/lib`, system loader paths, rpath/runpath, OS-specific mechanisms |

`-I` does not help the JVM find `libnativemath.so`. `-Djava.library.path` does not help the C compiler find `jni.h`. `-L` helps native code **link** to a dependency, but does not guarantee the OS can find that dependency **at runtime**.

### 9.1. When a JNI library calls another native library

Suppose `nativemath.c` calls a function from `libhelper.so` (assuming headers and library already exist); on Linux the link command might need a form like:

~~~sh
cc -shared build/nativemath.o \
  -Lvendor/lib -lhelper \
  -o build/lib/libnativemath.so
~~~

This is an **illustrative pattern** for an additional dependency and will not run standalone without `libhelper.so` and the required declarations/definitions. `-lhelper` tells the linker to find a library with a valid name according to toolchain rules, usually `libhelper.so` or `libhelper.a` in the search directories. You must distinguish dynamic linking from static linking: which file is chosen affects dependencies during deployment.

If linking succeeds but `libhelper.so` is not on the loader path at runtime, `System.loadLibrary("nativemath")` can still fail. Inspect:

~~~sh
readelf -d build/lib/libnativemath.so
ldd build/lib/libnativemath.so
~~~

`readelf -d` shows metadata such as `NEEDED`, `RPATH`/`RUNPATH` if present; `ldd` displays dependency resolution in the current environment and should only be run on trusted binaries. If the dependency sits next to `libnativemath.so` in a Linux package, the linker can embed a relative runtime search path using `$ORIGIN`; using rpath/runpath must be designed consistently with the release layout:

~~~sh
cc -shared build/nativemath.o \
  -Lbuild/lib -lhelper \
  -Wl,-rpath,'$ORIGIN' \
  -o build/lib/libnativemath.so
~~~

The pattern above assumes `libhelper.so` is already in `build/lib` at link time and deployed in the same directory as the JNI library. Single quotes preserve `$ORIGIN` so the **dynamic loader** expands it at runtime, rather than the shell expanding the variable prematurely. On macOS, `@loader_path` is commonly used, while Windows uses its own DLL/loader search rules; do not copy Linux flags to other systems.

**You do not need to link `libjvm.so` directly just to implement basic JNI functions** like in this example: JNI operations are called through the `JNIEnv` function table. If a C application uses the Invocation API to create a JVM itself or directly calls symbols outside that interface, the linking requirements will differ.

## 10. Distinguishing errors at build, load, and JNI call time

The following scenarios help diagnose the right layer:

| Symptom | Possible cause | Check / how to fix |
| --- | --- | --- |
| `jni.h: No such file or directory` | Missing JDK include path | Verify `JAVA_HOME` and `-I.../include` |
| `jni_md.h: No such file or directory` | Missing OS include directory | Add `-I.../linux`, `darwin`, or `win32` |
| `conflicting types for Java_...` | C source does not match generated header | Rebuild with `javac -h`; compare static/instance, return, and argument types |
| `relocation ... recompile with -fPIC` | Object not suitable for linking into `.so` | Recompile object with `-fPIC` before linking |
| `undefined reference` or `unresolved external symbol` | Missing object/library or wrong signature/link order | Identify unresolved symbol, add the exact object/`-l`/import library |
| `no nativemath in java.library.path` | JVM cannot find library by name/path | Check `-Djava.library.path` and standard OS filename |
| `Can't load ... / wrong ELF class`, `Bad CPU type`, or `not a valid Win32 application` | Binary has wrong architecture or format | Check 32/64-bit, x86_64/ARM64, OS, and toolchain |
| `libhelper.so: cannot open shared object file` / missing secondary DLL | Main library has an unresolved dependency | `readelf/ldd`, `otool -L`, `dumpbin /dependents`, package layout |
| `UnsatisfiedLinkError: 'long demo.NativeMath.add(int, int)'` (exact message depends on JVM) | Library loaded but method not resolved | `nm -D`/`dumpbin /exports`, header, method signature, native registration |
| JVM crash when entering native method | Wrong prototype/ABI or C memory bug | Recheck header and calling convention, enable debugger/sanitizer, `-Xcheck:jni` |

Work through them in order:

1. **Do you have the latest class and header?** Check `javap -s`, `demo_NativeMath.h`, and the right JDK.
2. **Did the C compiler produce the object successfully?** If not, this is a compile error (headers/syntax/types).
3. **Did the linker produce a valid shared library?** If not, resolve objects, flags, unresolved symbols, and dependencies.
4. **Is the library the right architecture and in the path the JVM searches?** Use `file`/`dumpbin`, paths, and loader diagnostics.
5. **Does the export have the right JNI name and linkage?** Use `nm`/`readelf`/`dumpbin` and compare with the generated header.
6. **If it can be called but produces wrong results/crashes**, inspect ABI, memory lifetime, pointers, exceptions, and native logic; stop changing paths when the bug is inside running code.

### 10.1. Two very different `UnsatisfiedLinkError` errors

**Scenario A — error during class initialization:**

~~~text
java.lang.UnsatisfiedLinkError: no nativemath in java.library.path: ...
~~~

The JVM could not find/load the logical library `nativemath`. Check the file location, platform naming, architecture, permissions, and dependencies. The exact message text may vary across JVM versions.

**Scenario B — error when calling the native method:**

~~~text
java.lang.UnsatisfiedLinkError: 'long demo.NativeMath.add(int, int)'
~~~

The library may have loaded, but the JVM could not find a matching implementation. Check the `Java_demo_NativeMath_add` symbol or `RegisterNatives` logic, make sure the C source was rebuilt after the Java signature changed, check C++ name mangling, and check symbol visibility. Do not try to fix error B merely by moving `.so` to the classpath directory.

### 10.2. Inspecting with JVM and native tools

You can add `-Xcheck:jni` when running to get additional JNI checks supported by the JVM:

~~~sh
java -Xcheck:jni -Djava.library.path=build/lib \
  -cp build/classes demo.NativeMath
~~~

This flag helps detect certain misuses of the JNI API, but **does not replace** checking all pointer, overflow, and ABI bugs in C/C++. When encountering a native crash, a debugger (gdb/lldb/Visual Studio) with debug symbols from `-g` or `/Zi` is more useful than only looking at the Java stack trace.

Asking yourself “did the error occur during `javac`, `cc/cl`, `System.loadLibrary`, or when calling `add`?” usually narrows down the cause faster than trying flags at random.

## 11. Exporting symbols in multi-file projects and release builds

As a project grows, split native helper functions into separate object files. The build flow remains: **each source -> one object -> one shared library**. For example, if you add `native/helper.c` and the code calls a function declared in `helper.h`, Linux needs to compile both:

~~~sh
cc -std=c11 -fPIC -Ibuild/include \
  -I"$JAVA_HOME/include" -I"$JAVA_HOME/include/linux" \
  -Inative -c native/nativemath.c -o build/nativemath.o

cc -std=c11 -fPIC -Inative \
  -c native/helper.c -o build/helper.o

cc -shared build/nativemath.o build/helper.o \
  -o build/lib/libnativemath.so
~~~

This extended example **is only valid after you actually add helper.c/helper.h and the corresponding call**. If you only build `nativemath.o` and forget `helper.o`, the linker may report an unresolved reference; with some linkers/build modes, the error may even surface at load/call time. Limiting exported symbols to the necessary entry points keeps the native API cleaner, especially when the library uses C++.

When building for release, note:

- **ABI and platform:** build for the compatible OS + CPU architecture + toolchain; a Linux `.so` cannot replace a Windows `.dll`; do not think renaming the extension is enough.
- **JDK headers:** take them from the target JDK; avoid using headers copied from another JDK/OS version without checking compatibility.
- **Library name:** Java calls the logical name consistently; each platform packages the file according to its convention.
- **Reproducibility:** build scripts should regenerate `.h` after every `native` change, clean old objects, and run a real JNI smoke test.
- **Visibility:** export JNI symbols and callbacks/hooks needed by the runtime, keeping internal functions private where appropriate; `JNI_OnLoad` needs the right signature and export if used.
- **Dependencies:** ship valid dependent native libraries as well, and configure the runtime loader consistently with the deployment layout, license, and target architecture.
- **Threads and initialization:** if using `JNI_OnLoad` for registration/hooks, handle the returned status and do not retain one thread's `JNIEnv *` for another thread.
- **Testing:** test both Debug/Release builds and runtime with the right Java version/architecture; inspect actual symbols after the link step.

### 11.1. About `JNI_OnLoad`

This is an **optional** entry point for a native library to perform JNI initialization when loaded. When declared, the pattern usually looks like:

~~~c
JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM *vm, void *reserved) {
    (void) vm;
    (void) reserved;
    return JNI_VERSION_1_8;
}
~~~

This is an **illustrative snippet**, without registration/initialization operations; to use it standalone you must include `jni.h` and link it into the shared library. `JNI_VERSION_1_8` indicates the JNI version level the library requires, **not that the program only runs on Java 8**. If `JNI_OnLoad` returns a JNI version not supported by the VM, loading will fail.

For this first lesson, you do not need to add `JNI_OnLoad`; the JVM looks up `Java_demo_NativeMath_add` by convention. When switching to `RegisterNatives`, you need to clearly understand the `(II)J` method descriptor and register the function pointer matching the Java declaration.

## 12. Self-check exercises to reinforce compile/link/export

1. **Rename the logical library.** Change `System.loadLibrary("nativemath")` to `"othermath"` without renaming the file. Predict which step fails; then restore the right name.
2. **Rename the Java method from `add` to `sum`.** Re-run `javac -h`. Observe the generated header change to `Java_demo_NativeMath_sum`, then update the C source; inspect the export after building.
3. **Change `static native` to instance `native`.** The generated header will change the second JNI parameter from `jclass` to `jobject`; update the Java caller accordingly and rebuild.
4. **Remove `JNIEXPORT` in a test build.** Inspect the export table, especially on Windows or when building with hidden visibility; restore the macro before finishing.
5. **Create load errors and lookup errors separately.** Move the library out of `build/lib` to test a loader error; put the library back but intentionally export the wrong method name to test a lookup error. Restore the source, build, and verify the output `7 + 35 = 42`.

When doing these exercises, change one factor at a time and always re-run the related compile + link steps. The important part is identifying the exact boundary between a **compiler** error, **linker** error, **dynamic loader** error, and **JNI lookup** error.

## 13. Checklist before calling this a working JNI library

- The latest Java `.class` and `javac -h` header are generated from the same declaration (package, method, `static`, argument/return types).
- The C/C++ function has `JNIEXPORT`, `JNICALL`, and the right JNI name/prototype; C++ has C linkage; `jclass` and `jobject` are not misused.
- The compiler finds `jni.h`/`jni_md.h`/generated header; objects are built for the right OS/CPU/toolchain.
- The linker produces the right `.so/.dylib/.dll` with no missing required objects/libraries; the entry point is in the export table.
- `System.loadLibrary` receives the **logical name**; the file is in a path the JVM/OS loader can find, and dependencies can also be loaded.
- `CLASSPATH`, `-I`, `-L`, and `java.library.path` are not confused; the timing of any error is identified accurately.
- Actually run Java and get **`7 + 35 = 42`**; verify the exported symbol on the packaged library, not only on intermediate objects.
- If releasing for multiple platforms, produce separate artifacts for each target and run a post-build JNI smoke test.

**Key takeaway:** “Build succeeded” only says the compiler/linker created a file; a successful JNI call requires **the right Java declaration, the right C ABI/prototype, the right exported symbol, the right shared library, and the right runtime loader path**. Every link in the chain can be verified with the corresponding tool.
