# Reading jextract-Generated Code for Functions, Constants, Structs, and Function Pointers

## Lesson Objectives

`jextract` is a tool in the OpenJDK Code Tools project: it reads **C headers** (`.h`) using a C parser and **generates Java bindings** based on the Foreign Function & Memory API (FFM). The goal is not only to replace manual `Linker.downcallHandle` or `Linker.upcallStub` calls, but also to help Java code use C declarations with a structured API: **functions**, **macro/enum constants**, **structs/unions**, **global variables**, **typedefs**, and **function pointers/callbacks**.

When reading a set of Java sources generated by jextract, the learner needs to answer:

1. Which declaration in the C header generates **which Java file/class**?
2. Which method is the **wrapper to call**, and which methods only provide the **address, `FunctionDescriptor`, or `MemoryLayout`**?
3. How are `C int`, `long`, `size_t`, pointer, `struct`, and function pointer represented in Java?
4. Who owns native memory, callback stubs, and native libraries, and when are they freed?
5. When a symbol or method does not appear, is it a code generation error, preprocessor/filter, unsupported macro, ABI mismatch, or jextract version difference?

This lesson teaches how to **read and use generated sources**, rather than treating generated code as business implementation that needs to be rewritten. A C header and a running example set help connect these concepts together.

**Version requirements:** FFM in the `java.lang.foreign` package became a standard API in **JDK 22** (JEP 454). `jextract` is a **separately released** tool and is not included by default in the `bin` directory of every JDK. Choose a jextract build compatible with your JDK and target platform; the helper names here follow the current **OpenJDK jextract Guide**, but **generated APIs may vary across versions, C headers, and platforms**. Always inspect the actual source in your own output directory.

## 1. From C Header to Java Source Tree: Overview Map

Suppose the native library has the header `demo.h`:

~~~c
#ifndef DEMO_H
#define DEMO_H

#define DEMO_LIMIT 64
#define DEMO_FLAG_A 1
#define DEMO_FLAG_B 2

enum demo_state { DEMO_OFF = 0, DEMO_ON = 1 };

struct Point {
    int x;
    int y;
};

typedef int (*binary_fn)(int a, int b);

int add_values(int a, int b);
int sum_point(const struct Point *p);
int call_callback(binary_fn fn, int a, int b);
binary_fn native_callback(void);

#endif
~~~

This is a **complete illustrative header**, not a pre-built native library. It introduces different C constructs:

| C declaration | Nature | Where do Java bindings usually live? |
| --- | --- | --- |
| `#define DEMO_LIMIT 64` | Numeric macro constant | Accessor method `DEMO_LIMIT()` in the header class |
| `enum demo_state { ... }` | C enum constants | `DEMO_OFF()`/`DEMO_ON()` in the header class, not necessarily a Java `enum` |
| `struct Point { int x; int y; }` | Struct layout and fields | Class `Point` with `layout`, `sizeof`, getters/setters |
| `typedef int (*binary_fn)(int,int)` | C function pointer type | Class `binary_fn` with `Function`, `allocate`, `invoke` |
| `int add_values(int,int)` | Native function | Static wrapper `add_values(...)` and metadata `$address/$descriptor/$handle` |
| `int sum_point(const struct Point *)` | Function taking pointer-to-struct | Static wrapper using `MemorySegment` for the argument |
| `binary_fn native_callback(void)` | Function returning function pointer | Wrapper returning `MemorySegment`, using `binary_fn.invoke` if calling is needed |
| `int call_callback(binary_fn,...)` | Function taking callback | Wrapper taking a `MemorySegment` upcall stub created by Java |

The jextract command according to the OpenJDK Guide (the content is a **procedure that can be executed once the tool is installed**):

~~~bash
jextract \
  --output gensrc \
  --target-package org.example.demo \
  --library demo_native \
  demo.h
~~~

On Windows, line continuation in PowerShell/CMD differs from POSIX shells; you can use a single line:

~~~text
jextract --output gensrc --target-package org.example.demo --library demo_native demo.h
~~~

The components:

- `demo.h`: input C header that clang will parse; the header itself **does not produce a .so/.dll file**.
- `--output gensrc`: root directory storing the generated Java code.
- `--target-package org.example.demo`: Java namespace for the classes.
- `--library demo_native`: instructs bindings to attach to a native library looked up by platform name; the actual file such as `libdemo_native.so` on Linux or `demo_native.dll` on Windows **must be present at runtime**, unless you use another library management mechanism.
- For multi-header libraries or complex `#include`s, add `--include-dir` (`-I`) and the necessary macro defines so clang understands headers the same way as the native library's compiler.
- You can use `--header-class-name` to choose the aggregate class name; otherwise, it is usually derived from the header name, e.g., `demo.h` becomes `demo_h`.

**Illustrative** example layout of the source output (not a listing from running jextract on this machine):

~~~text
gensrc/
└── org/
    └── example/
        └── demo/
            ├── demo_h.java
            ├── Point.java
            ├── binary_fn.java
            └── ...  (helper/internal files depending on version)
~~~

**Do not guess file names from examples and hardcode them in production:** with typedefs, anonymous structs/unions, nested structs, duplicate name handling, generated helper names, or new versions, names may differ. Read the actual generated files, check the package/imports/signatures, and then write the client.

## 2. How to Read the Header Class: `demo_h.java`

According to the OpenJDK jextract Guide, most bindings have **static methods** in a *header class* (for example `demo_h`). That is the first place to look when you need to call a C function or read macro/enum constants.

Import example:

~~~java
import static org.example.demo.demo_h.*;
import org.example.demo.Point;
import org.example.demo.binary_fn;
~~~

`import static` brings the static accessors/wrappers of the header class into Java scope; importing the generated classes provides access to struct and callback helpers. Wildcard imports are not required; in large products, explicit imports make name collision control easier.

Distinguish **generated Java files** from the **native library implementation**:

~~~text
demo.h                       demo.c / native library
   |                               |
   | jextract parses               | cc builds
   v                               v
demo_h.java, Point.java,     libdemo_native.so / .dll / .dylib
binary_fn.java, ...
   |                               |
   +-------- Java application -----+
              ↓ FFM linker/lookup
           native symbols
~~~

Jextract only parses headers and generates Java bindings; it **does not implement native functions itself**, does not guarantee the OS loader can find the library, and does not verify that the C source/library in use actually matches the header. To run, you need the **right native binary** with matching exported symbols and ABI.

### Reading the Three Layers of a Binding

When you see a C name like `foo`, look in order for:

1. **Public wrapper** `foo(...)`: convenient entry point for Java callers.
2. **Metadata** `foo$descriptor()`, `foo$address()`, `foo$handle()`: provides ABI type, symbol address, and method handle.
3. **Internal implementation/wiring**: symbol lookup, `Linker`, library loading, argument conversion.

Layer 2 is very useful for debugging signatures; layer 3 is machine-generated code and should not be hand-edited to "fix the ABI" when the real issue is header/build configuration.

## 3. Reading C Function Bindings

For the header:

~~~c
void foo(int x);
~~~

The OpenJDK Guide presents the **equivalent** generated Java API:

~~~java
// Shape excerpted from documentation, not a file with method bodies.
public static void foo(int x) { /* generated downcall */ }

public static MemorySegment foo$address() { /* address */ }
public static FunctionDescriptor foo$descriptor() { /* ABI */ }
public static MethodHandle foo$handle() { /* downcall handle */ }
~~~

The four parts serve different purposes:

| Component | Question answered | How to use |
| --- | --- | --- |
| `foo(int)` | "How do I call the C function directly?" | `foo(5)` |
| `foo$address()` | "What is the native symbol address?" | Check symbol lookup/lifetime; do not dereference as data |
| `foo$descriptor()` | "What are the return/argument types in FFM?" | Inspect `FunctionDescriptor` when debugging ABI |
| `foo$handle()` | "Where is the actual FFM MethodHandle?" | Use only if advanced MethodHandle manipulation is needed; wrapper is usually enough |

`$address` is not a Java object address; it is a pointer to a native symbol. `$descriptor` is derived from the C header parsed by the tool, **not** an independent check against the loaded binary. If the header and library versions diverge, the generated descriptor may still "look right" while the native call fails.

### C Functions with Pointer Arguments

Header:

~~~c
int sum_point(const struct Point *p);
~~~

The wrapper usually has the form:

~~~java
// Illustrative shape; take the exact signature from the generated source.
public static int sum_point(MemorySegment p) {
    /* generated FFM downcall */
}
~~~

`MemorySegment` represents a **C pointer**, not automatically a Java `Point` object on the heap. When calling, you must pass a segment that the native library is allowed to read; in the example, use `Point.allocate(arena)` and keep the arena alive throughout the call.

**Do not** mistake `const struct Point *` for a Java immutable type: `const` is a C contract, while mutability through aliases and how generated source represents read-only may differ. The caller must not mutate data when the C contract forbids it, even if the Java compiler does not prevent it.

### Return Types and Carriers

Layouts of C arguments/returns are converted into FFM carriers:

| C | Typical Java carrier | Additional checks |
| --- | --- | --- |
| `int` | `int` | `C_INT`/ABI: C int must match Java int size on the platform |
| `long` | `int` or `long` depending on ABI | Windows 64-bit usually has 32-bit C long; do not guess |
| `long long` | `long` on common ABIs | Check generated layout |
| `float` / `double` | `float` / `double` | Depends on C ABI/calling convention |
| `void *` / `T *` | `MemorySegment` | Address, bounds, null, ownership, and lifetime |
| `void` | Java `void` | No return value |
| `struct` by value | May require `MemorySegment`/allocator depending on FFM ABI | Read the exact generated signature; do not assume scalar |

If a generated method takes a `MemorySegment` at the beginning for a **struct return by value**, there may be a **`SegmentAllocator`** as a parameter inserted by FFM convention. That differs from a C function taking a pointer; you must read the **generated method signature and descriptor**, not infer from the name.

### When to Use `$handle`?

`$handle` is useful when you need to apply MethodHandle combinators, caching, or call site optimization. However, `invokeExact` requires **exact Java types at the call site**, so a mismatch like `int` vs `long`, or `MemorySegment` vs `Object` can cause `WrongMethodTypeException`. For normal applications, prefer the **generated wrapper** because it already expresses the signature and type conversions according to the generator's logic.

## 4. Reading Constants: Macros and C Enums

This is where it is easy to confuse them with Java `static final` or Java `enum`.

Header example:

~~~c
#define DEMO_LIMIT 64
#define DEMO_FLAG_A 1
#define DEMO_FLAG_B 2

enum demo_state { DEMO_OFF = 0, DEMO_ON = 1 };
~~~

According to the jextract Guide, numeric macro/enum constants usually become **static accessor methods** in the header class:

~~~java
// Sketch of the generated API, not complete source.
public static int DEMO_LIMIT() { /* returns 64 */ }
public static int DEMO_FLAG_A() { /* returns 1 */ }
public static int DEMO_FLAG_B() { /* returns 2 */ }

public static int DEMO_OFF() { /* returns 0 */ }
public static int DEMO_ON() { /* returns 1 */ }
~~~

Client:

~~~java
int limit = DEMO_LIMIT();
int flags = DEMO_FLAG_A() | DEMO_FLAG_B();
int state = DEMO_ON();
~~~

This is a snippet, assuming `import static org.example.demo.demo_h.*;` and that the generator produces those names. The corresponding values are `64`, `3`, `1`.

**C enums do not necessarily become Java `enum`s**: enum constants are placed in the top-level C namespace. A bit-mask enum value may need `|`, `&` operations; a Java `enum` by itself is not equivalent to C integers.

### Which Macros Cannot Generate Accessors?

Some C macros cannot be converted into simple Java constants:

~~~c
#define DEMO_LIMIT 64                /* constant-like: can be generated */
#define DEMO_VERSION "1.0"           /* string literal: can be generated */
#define DOUBLE_IT(x) ((x) * 2)       /* function-like: NOT directly supported */
~~~

The OpenJDK Guide states that jextract supports macros with **primitive numeric, string, or pointer** values, but **does not support function-like macros**. If `DOUBLE_IT()` is not found in the Java source, that is **not necessarily a bug**.

Macros using conditional compilation also depend on headers/defines and the target platform:

~~~c
#ifdef _WIN32
#define PLATFORM_CODE 1
#else
#define PLATFORM_CODE 2
#endif
~~~

The value seen by jextract is the result of **preprocessing in the environment running the tool**. Do not reuse bindings generated from headers/platform A on platform B without comparing the ABI and constant values.

**Note on `-D`:** macros defined only via the command-line option `-DNAME=VALUE` can be used to control preprocessing, but according to the guide will **not** automatically have accessors generated like a macro declared in the header.

## 5. Structs: Understanding `Point.java`, `layout`, and Field Helpers

C header:

~~~c
struct Point {
    int x;
    int y;
};
~~~

Jextract usually generates **a separate class** for `Point`. According to the Guide, the API shape is roughly:

~~~java
// ILLUSTRATIVE GENERATED API; bodies depend on version.
public class Point {
    public static GroupLayout layout() { /* ... */ }
    public static long sizeof() { /* ... */ }

    public static ValueLayout.OfInt x$layout() { /* ... */ }
    public static long x$offset() { /* ... */ }
    public static int x(MemorySegment struct) { /* ... */ }
    public static void x(MemorySegment struct, int value) { /* ... */ }

    public static ValueLayout.OfInt y$layout() { /* ... */ }
    public static long y$offset() { /* ... */ }
    public static int y(MemorySegment struct) { /* ... */ }
    public static void y(MemorySegment struct, int value) { /* ... */ }

    public static MemorySegment allocate(SegmentAllocator a) { /* ... */ }
    public static MemorySegment allocateArray(long count, SegmentAllocator a)
            { /* ... */ }
    public static MemorySegment asSlice(MemorySegment array, long index)
            { /* ... */ }
}
~~~

**The signatures here are illustrative only; do not copy this block verbatim to compile:** this is not complete generated source. Real functions may have overloads or other helpers. What matters is learning the **responsibility of each method name**:

| Generated method | Meaning | Review point |
| --- | --- | --- |
| `Point.layout()` | `GroupLayout` describing overall fields/padding/alignment | Compare against C header/ABI |
| `Point.sizeof()` | Size `sizeof(struct Point)` per generator | Do not replace by summing sizes manually if padding exists |
| `Point.x$layout()` | Memory layout of field `x` | What layout does C int have on this platform? |
| `Point.x$offset()` | Byte offset of field in struct | **Byte** offset, not index |
| `Point.x(point)` | Read field x from native segment | Requires valid segment with sufficient bounds |
| `Point.x(point, 3)` | Write field x | Writable, live segment |
| `Point.allocate(arena)` | Allocate one struct | Lifetime tied to `Arena` |
| `Point.allocateArray(n, arena)` | Allocate n contiguous structs | Check `n`, size, avoid overflow |
| `Point.asSlice(array,i)` | View of the i-th element | No extra allocation/copy, keeps parent lifetime |

A proper client typically looks like:

~~~java
try (Arena arena = Arena.ofConfined()) {
    MemorySegment p = Point.allocate(arena);
    Point.x(p, 3);
    Point.y(p, 4);

    int x = Point.x(p);
    int y = Point.y(p);
    System.out.println(x + y); // 7
}
~~~

This snippet **assumes jextract has been run and `Point` is imported**. It only manipulates memory allocated by the arena; no C function call is needed to see the generated getters/setters working.

### Padding and Alignment Cannot Be Ignored

Given:

~~~c
struct Packet {
    char kind;
    int count;
    void *payload;
};
~~~

Between fields there may be **padding** due to the ABI. If you manually assemble Java `MemoryLayout.structLayout(JAVA_BYTE, JAVA_INT, ADDRESS)` without adding padding and verifying alignment, the description may be wrong. Generated `Packet.layout()` can contain padding and ABI-specific member layouts, so `Packet.count$offset()` is the source to check.

Do not take `sizeof` on one operating system and hardcode it into the JVM on another. C `long` in particular differs between Windows x64 and many Unix x64 ABIs; native compilers may also use packing options that affect offsets.

### Struct Arrays and Slices

~~~java
try (Arena arena = Arena.ofConfined()) {
    MemorySegment points = Point.allocateArray(3, arena);

    for (long i = 0; i < 3; i++) {
        MemorySegment element = Point.asSlice(points, i);
        Point.x(element, (int) (i + 1));
        Point.y(element, 10);
    }

    int secondX = Point.x(Point.asSlice(points, 1)); // 2
}
~~~

This snippet relies on the generated `Point`. `asSlice(points,i)` is a view of a struct at **index i**, not to be confused with a byte offset. The slice still depends on the arena's lifetime. If native code retains a pointer to an element, the arena must remain alive until the native code no longer uses that pointer.

### Union

A C `union` allows multiple fields to **overlap the same memory region**, unlike a `struct` which lays fields out sequentially. The jextract Guide describes union helper classes as **having a similar shape to structs** (`layout`, field accessors, allocation), but with different aliasing semantics. Writing union field A can alter the bits of field B; the application must know which field is currently active according to the C protocol.

## 6. Function Pointers: Why Does jextract Generate a Separate Class?

C declaration:

~~~c
typedef int (*binary_fn)(int a, int b);
~~~

`binary_fn` is neither a scalar int nor a pointer to a struct; it is a **function pointer type** with signature `int(int,int)` under the C ABI.

According to the OpenJDK Guide, a class is generated for the function pointer type, with an **equivalent** shape:

~~~java
// ILLUSTRATIVE GENERATED SHAPE; not a standalone runnable file.
public class binary_fn {
    public interface Function {
        int apply(int a, int b);
    }

    public static FunctionDescriptor descriptor() { /* ... */ }

    public static MemorySegment allocate(Function impl, Arena arena)
            { /* ... upcall stub ... */ }

    public static int invoke(MemorySegment functionPointer, int a, int b)
            { /* ... downcall ... */ }
}
~~~

**Two directions that are easy to confuse**:

- `binary_fn.allocate((a,b) -> a + b, arena)`: turns a **Java lambda** into a **native function pointer** that C can call — **upcall**.
- `binary_fn.invoke(nativeFunctionPointer, 3, 4)`: Java calls a **function pointer received from C** — **downcall** to that pointer.

| Generated API | Input | Who calls whom? | Ownership |
| --- | --- | --- | --- |
| `binary_fn.descriptor()` | None | Reads ABI metadata only | Allocates no callback |
| `binary_fn.allocate(impl,arena)` | Java functional interface + arena | C calls into Java callback stub | Stub valid until arena closes |
| `binary_fn.invoke(ptr,a,b)` | Native function pointer + arguments | Java calls C function pointer | Pointer must remain valid per C library |
| `call_callback(ptr,a,b)` | Callback pointer from `allocate` | Java calls C, then C calls Java | Must keep stub alive while C calls it |

### Callback Lifecycle Truly Matters

For a C API that invokes the callback **synchronously** and returns immediately, you can create the stub inside `try (Arena arena = Arena.ofConfined())` and free it when the native call finishes. However, if C stores the pointer for **asynchronous** events, you must not close the arena after registration; you must unregister/acknowledge completion of in-flight callbacks before closing the arena.

A **Java upcall must not throw a Java exception across the native boundary**. Under the FFM Linker contract, throwing an exception across an upcall can cause the JVM to terminate abruptly. Catch errors **inside the callback**, return an appropriate C error code if the native protocol allows, and pass the error to the Java owner through a separate channel.

`binary_fn.invoke` also does not automatically validate that the native pointer is valid code; passing a NULL/dangling address or wrong ABI can crash. Do not call a function pointer whose library has been unloaded or whose callback stub has been freed.

### Typedef Function Pointers Appear in Many Places

Typical C cases:

~~~c
void register_callback(void (*cb)(void)); // parameter
void (*get_callback(void))(void);         // return type
typedef int (*binary_fn)(int, int);      // typedef
struct Holder {
    binary_fn on_event;                 // field in struct
};
~~~

Jextract can generate separate types/helpers to represent these function pointers. When a field has a function pointer type, the struct getter may return a `MemorySegment` (the address value). Do not try to read a function pointer field as `JAVA_INT` or treat it as a Java `Runnable`. To call it, use the `invoke` helper with the matching signature; to install a Java callback, use the `allocate` helper with a valid arena.

## 7. Running Example: Same Header, Multiple Kinds of Generated Bindings

Create the two files below in a **separate example directory**. The lesson presents them so learners can practice on a machine with a compatible native compiler and jextract installed. The C and Java code below form **an end-to-end demo**; the generated API parts are predicted from the OpenJDK Guide and **must be verified for exact names/signatures against actual output** when running on a different tool version.

### 7.1. Native Header: `demo.h`

~~~c
#ifndef DEMO_H
#define DEMO_H

#define DEMO_LIMIT 64
#define DEMO_FLAG_A 1
#define DEMO_FLAG_B 2

enum demo_state {
    DEMO_OFF = 0,
    DEMO_ON = 1
};

struct Point {
    int x;
    int y;
};

typedef int (*binary_fn)(int a, int b);

int add_values(int a, int b);
int sum_point(const struct Point *p);
int call_callback(binary_fn fn, int a, int b);
binary_fn native_callback(void);

#endif
~~~

The C declarations are kept simple: no function-like macros, anonymous structs, varargs, or C++ name mangling. `int` is assumed to be 32-bit under common ABIs compatible with FFM/jextract; when porting, verify the actual ABI.

### 7.2. Native Implementation: `demo.c`

~~~c
#include "demo.h"

static int multiply(int a, int b) {
    return a * b;
}

int add_values(int a, int b) {
    return a + b;
}

int sum_point(const struct Point *p) {
    if (p == 0) {
        return -1;
    }
    return p->x + p->y;
}

int call_callback(binary_fn fn, int a, int b) {
    if (fn == 0) {
        return -1;
    }
    return fn(a, b);
}

binary_fn native_callback(void) {
    return &multiply;
}
~~~

`multiply` here is a `static` C function: it does not need to be an exported symbol because `native_callback` returns a **function pointer** to it; the lifetime of the code depends on the native library remaining loaded. `add_values`, `sum_point`, `call_callback`, and `native_callback` are public functions matching the header; building the shared library must export symbols according to the compiler/linker in use.

### 7.3. Building the Shared Library and Running jextract (Linux/POSIX)

Example for Linux with a C11-capable C compiler:

~~~bash
cc -std=c11 -Wall -Wextra -Werror -fPIC -shared \
   demo.c -o libdemo_native.so

jextract \
  --output gensrc \
  --target-package org.example.demo \
  --library demo_native \
  demo.h
~~~

`jextract` runs at build time to generate **Java source**; `cc` compiles C to produce **native executable code**. These two steps are independent. On macOS/Windows, adjust compiler flags, library extensions, and search paths; do not use the exact Linux commands on other systems.

### 7.4. Java Client: `DemoMain.java`

~~~java
import java.lang.foreign.Arena;
import java.lang.foreign.MemorySegment;

import static org.example.demo.demo_h.*;
import org.example.demo.Point;
import org.example.demo.binary_fn;

public final class DemoMain {
    public static void main(String[] args) {
        System.out.println("limit=" + DEMO_LIMIT());
        System.out.println("flags=" + (DEMO_FLAG_A() | DEMO_FLAG_B()));
        System.out.println("state=" + DEMO_ON());

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment point = Point.allocate(arena);
            Point.x(point, 3);
            Point.y(point, 4);

            System.out.println("add=" + add_values(2, 5));
            System.out.println("point-sum=" + sum_point(point));

            MemorySegment javaCallback = binary_fn.allocate(
                    (a, b) -> a + b,
                    arena);

            System.out.println("c-to-java="
                    + call_callback(javaCallback, 6, 7));

            MemorySegment cCallback = native_callback();
            System.out.println("java-to-c="
                    + binary_fn.invoke(cCallback, 3, 4));
        }
    }
}
~~~

All four binding groups are clearly used:

1. `DEMO_LIMIT()`, `DEMO_FLAG_A()`, `DEMO_FLAG_B()`, `DEMO_ON()`: macro and C enum constants.
2. `Point.allocate`, `Point.x`, `Point.y`: generated struct layout/field helpers.
3. `add_values`, `sum_point`, `call_callback`, `native_callback`: C function wrappers in the header class.
4. `binary_fn.allocate` and `binary_fn.invoke`: Java → C callback pointer (upcall) and Java calling a C function pointer (downcall).

### 7.5. Compiling/Running the Client

On Linux/POSIX, if you are in the directory containing `DemoMain.java`, `gensrc`, and `libdemo_native.so`:

~~~bash
javac -encoding UTF-8 -d classes \
  $(find gensrc -name '*.java') \
  DemoMain.java

LD_LIBRARY_PATH=. java -cp classes \
  --enable-native-access=ALL-UNNAMED DemoMain
~~~

On Windows, adjust the compile/find commands and dynamic library search path. `--enable-native-access` is required because generated FFM bindings typically use restricted native operations (downcall/upcall/library loading). If the generated code belongs to a named module, grant native access to that module rather than only the unnamed module.

**Expected stdout** on a compatible Linux environment (header, C library, jextract, and JDK all share the same ABI and generated names match the guide):

~~~text
limit=64
flags=3
state=1
add=7
point-sum=7
c-to-java=13
java-to-c=12
~~~

This is **a result inferred from the provided C/Java implementation**, not a claim that every jextract version has been run on every OS. If the tool generates different method names, adjust imports/calls based on the actual source; if the library fails to load, fix the native library path before analyzing logic correctness.

### Why Is `Point.sizeof()` Not Printed in This Stdout?

The size of a C struct is determined by the **ABI**. For two contiguous 4-byte `int`s, many ABIs give a size of 8, but the lesson does not treat a fixed size as a cross-platform requirement. You can add lines:

~~~java
System.out.println(Point.sizeof());
System.out.println(Point.x$offset());
System.out.println(Point.y$offset());
~~~

These values must be compared with `sizeof(struct Point)` and `offsetof` from the **actual native compiler**, especially when the library uses packing flags or structs contain pointers/`long`/bit-fields.

## 8. Standalone Java Lab: Checking Layout and Descriptor Meaning (Without jextract)

To distinguish **actual FFM rules** from **the shape of jextract-generated APIs**, here is a **standalone Java 22+** lab requiring no C compiler, shared library, or jextract. It manually models two things that generated code typically exposes: a `FunctionDescriptor` for a function taking two C ints and a `GroupLayout` for a struct with two fields.

File `BindingReadingLab.java`:

~~~java
import java.lang.foreign.Arena;
import java.lang.foreign.FunctionDescriptor;
import java.lang.foreign.GroupLayout;
import java.lang.foreign.MemoryLayout;
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;

public final class BindingReadingLab {
    public static void main(String[] args) {
        FunctionDescriptor fn = FunctionDescriptor.of(
                ValueLayout.JAVA_INT,
                ValueLayout.JAVA_INT,
                ValueLayout.JAVA_INT);

        GroupLayout point = MemoryLayout.structLayout(
                ValueLayout.JAVA_INT.withName("x"),
                ValueLayout.JAVA_INT.withName("y"));

        long x = point.byteOffset(
                MemoryLayout.PathElement.groupElement("x"));
        long y = point.byteOffset(
                MemoryLayout.PathElement.groupElement("y"));

        System.out.println("method-type=" + fn.toMethodType());
        System.out.println("point-size=" + point.byteSize());
        System.out.println("x-offset=" + x);
        System.out.println("y-offset=" + y);

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment p = arena.allocate(point);
            p.set(ValueLayout.JAVA_INT, x, 3);
            p.set(ValueLayout.JAVA_INT, y, 4);

            int sum = p.get(ValueLayout.JAVA_INT, x)
                    + p.get(ValueLayout.JAVA_INT, y);
            System.out.println("point-sum=" + sum);
        }
    }
}
~~~

Run with JDK 22+ (standard FFM, **no native access needed** for this snippet):

~~~bash
javac -encoding UTF-8 BindingReadingLab.java
java BindingReadingLab
~~~

**Stdout verified on JDK 24**, with 4-byte `JAVA_INT`:

~~~text
method-type=(int,int)int
point-size=8
x-offset=0
y-offset=4
point-sum=7
~~~

This is **not** Java code generated by jextract. It illustrates the practical meaning of the metadata we read in `foo$descriptor()` and `Point.layout()/x$offset()/y$offset()`. If the native compiler uses a different layout, the ABI-matching generated source is what needs to be reviewed before calling C.

## 9. Global Variables: Distinguishing `bar()` from `bar$segment()`

Although the topic focuses on functions/constants/structs/function pointers, it is important to recognize **C global variables** because the generated code has naming similar to functions:

~~~c
int bar;
~~~

According to the Guide, the header class usually has:

~~~java
// Illustrative shape.
public static ValueLayout.OfInt bar$layout() { /* ... */ }
public static MemorySegment bar$segment() { /* ... */ }
public static int bar() { /* getter */ }
public static void bar(int value) { /* setter */ }
~~~

- `bar$layout()`: layout of the global variable.
- `bar$segment()`: address/region representing the global variable.
- `bar()`: reads the current contents of the C global.
- `bar(int)`: writes the global's contents if the native library allows it.

**Unlike macros:** `bar()` is not a constant accessor; its value can change. A C global has the lifetime of the native library/process and may need synchronization when multiple threads access it. Do not cache the getter output and treat it as an immutable macro constant.

With C `extern const int` or a library that only provides a getter, do not assume every generated setter is safe. You must respect the native declaration and library contract. If a global symbol is not exported, the binding may fail to find it at runtime load/call; being declared in a header does not mean the symbol is exported by the linker.

## 10. Typedefs and Names That Look Like Java Classes

C:

~~~c
typedef int MyInt;

struct Point {
    int x;
    int y;
};
typedef struct Point MyPoint;
~~~

According to the Guide:

- **Primitive typedefs** like `MyInt` usually become a **layout constant** in the main header class.
- **Struct/union typedefs** like `MyPoint` usually become a **separate Java class** related to the original struct class.

Do not assume that `typedef int MyInt` creates a new Java primitive type or class used in method signatures. It remains a C alias, and generated methods may use the Java `int` carrier with the corresponding layout metadata.

**Self-check:** if `MyInt.java` does not exist, do not jump to the conclusion that the binding is missing; search for `MyInt` in the main header class and inspect the actual declaration. For `Point`/`MyPoint`, check the generated classes and inherited/forwarded static methods to understand the alias.

## 11. Reading `MemorySegment` in Generated Code Does Not Mean "Safe Pointer"

Generated code usually performs FFM operations using the right APIs, but it cannot infer every native library contract:

| Value of type `MemorySegment` | Risk | What you need to verify yourself |
| --- | --- | --- |
| Pointer returned from C function | May be `NULL`, size 0, dangling | Check `address()==0L`, length, owner/free |
| Pointer-to-struct | May lack sufficient bounds to read fields | Use generated `reinterpret` when the right lifetime/size contract holds |
| Pointer returned by `Point.allocate(arena)` | Becomes invalid when arena closes | Native code must not retain it after close |
| Function pointer returned from native library | Code pointer may become invalid after unload | Only invoke while library exists and signature matches |
| Callback pointer from `binary_fn.allocate` | Stub has arena's lifetime | C must not call after close |
| C string pointer | Unclear encoding/NUL terminator/length | Do not read past buffer; API contract decides |
| C array pointer | No automatic count | Use explicit length, avoid index overflow |
| Global variable address | Mutable data or library unloaded | Proper synchronization and lifetime |

### Generated `reinterpret`: A Powerful Tool, Not Validation

Example following the OpenJDK Guide structure:

~~~java
// Illustrative snippet with a caller-owned native API:
// struct Point *new_point(void);
// void delete_point(struct Point *);
try (Arena arena = Arena.ofConfined()) {
    MemorySegment p = new_point();
    if (p.address() == 0L) {
        throw new IllegalStateException("native allocation failed");
    }

    MemorySegment sized =
            Point.reinterpret(p, arena, demo_h::delete_point);

    // Only use sized within the lifetime of the arena.
}
~~~

Here `Point.reinterpret` is a **generated helper** that can attach `sizeof(Point)` bounds and a cleanup function when the arena closes. **Only use it if the C API genuinely returns a caller-owned Point from an allocator that `delete_point` is allowed to free.** If the C library owns the pointer, this cleanup will cause a double-free/invalid free. If C returns an array with multiple elements, use the element-count overload and verify the count.

If the header does not declare `new_point` or `delete_point`, **the snippet above does not run with the demo header in section 7**: it describes a *different API* to explain the generated helper. Do not mistake this section for a verbatim runnable command of DemoMain.

## 12. Why Are Some Places Missing a Generated Java Method?

Not every C construct is represented directly by jextract. Common categories:

### Function-like Macros

~~~c
#define DOUBLE_IT(x) ((x) * 2)
~~~

No `DOUBLE_IT(...)` method is generated under the jextract Guide's constant-macro mechanism. If needed, write a real C wrapper with an exported function or implement the Java logic yourself after understanding macro side effects and types.

### C++ APIs

FFM/jextract currently focuses on the **C header ABI**. C++ classes, templates, overloads, exceptions, name mangling, and cross-compiler ABIs make direct linking complex. Design an **`extern "C"` C-compatible wrapper** for the C++ library and run jextract on the wrapper header; do not assume reading `.hpp` will produce a complete, portable generated Java API.

### Static Inline / No Exported Symbol

~~~c
static inline int triple(int x) { return x * 3; }
~~~

This function may be inlined by the compiler and have no external symbol in the shared library. Do not assume jextract can call it as an exported function. If a stable callable ABI is needed, write an exported C wrapper. To debug, inspect the output source and the native library's symbol table.

### Headers Preprocessed Differently

`#ifdef`, `#define`, `-I` include paths, ABI, compiler target, and feature macros affect the declarations jextract sees. If Linux source contains a method that Windows bindings lack, first compare the generated preprocess configuration and native headers.

### Filtering

To reduce output for large libraries, jextract provides `--include-function`, `--include-constant`, `--include-struct`, `--include-union`, `--include-typedef`, and `--include-var`. A run with filters will **not generate all symbols**. If a helper needs a dependency that was filtered out, the tool may report a missing dependency and stop.

## 13. Using Generated Metadata to Debug ABI

Read these accessors before deciding to cast or modify the generator:

~~~java
// Example of checking metadata in a generated project:
FunctionDescriptor d = foo$descriptor();
MemorySegment addr = foo$address();
MethodHandle h = foo$handle();
~~~

This is a **snippet** used on a real binding when `foo` exists; the demo header in section 7 has no `foo`, so do not copy this snippet into `DemoMain`.

A good debugging workflow:

1. Open the original C header declaration and verify the library was built from the **exact same header version**.
2. Locate the generated header class (usually `demo_h`) and the wrapper method.
3. Check `$descriptor()`: does it have the right number of arguments and return layout? Are pointers `ADDRESS`? What actual width do `long` and `size_t` have?
4. Check `$address()`: was the symbol found in the right native shared library? Do not dereference a function pointer as data.
5. Check `$handle()` and the wrapper: do the generated Java carriers match `toMethodType()`?
6. For `struct`, inspect `layout/sizeof/field$offset/field$layout`; compare with `sizeof`/`offsetof` of the C compiler used to build the binary.
7. For callbacks, check the C typedef and `descriptor/allocate/invoke` helpers, ABI, and arena lifetime.
8. Run on the target JDK/native compiler/OS/CPU; do not use results generated on another platform as sufficient proof.

### `C_LONG` and Platform Pitfalls

The OpenJDK Guide gives an example where generated `C_LONG` corresponds to `JAVA_INT` on 64-bit Windows, because C `long` is 32-bit in that ABI. On many Unix x64 systems, C `long` is 64-bit. Therefore:

- Do not assume C `long` equals Java `long`.
- Do not copy Java source generated on Windows and assume it runs on Linux without comparing headers/ABIs.
- Do not arbitrarily replace generated constants `C_INT`, `C_LONG`, `C_POINTER` with `JAVA_INT`/`JAVA_LONG`.
- When a portable ABI is needed, consider fixed-width C types (such as `int32_t`/`int64_t`) and a C API with a clearly defined ABI.

### Comparing Actual Struct Offsets

If a struct adds a pointer:

~~~c
struct WithPointer {
    char flag;
    void *data;
};
~~~

There is usually padding between `flag` and `data`. `sizeof(struct WithPointer)` may differ from `1 + sizeof(void*)`. Compare the generated layout with the native compiler using `offsetof(struct WithPointer, data)`; do not hardcode offsets from another machine.

## 14. Build, Runtime Loading, and Native Access

Editing generated Java source usually **does not** solve these fundamental problems:

| Symptom | Possible cause | How to handle |
| --- | --- | --- |
| `jextract: command not found` | Tool not installed or not in PATH | Install a jextract build compatible with JDK/OS; check `jextract --version` |
| Cannot parse `#include` | Missing include directories/defines | Configure `-I` and `-D` to match the C headers |
| Missing `foo(...)` | Insufficient C header/filter/macro or unsupported construct | Compare declaration and `--include-*` output |
| `ClassNotFoundException` for generated class | Build did not compile/include Java source properly | Check generated package, `javac -d`, and classpath/modulepath |
| `UnsatisfiedLinkError`/library not found | Native binary not on loader path/wrong name | Check `--library`, `.so/.dll/.dylib` file, OS loader paths |
| Symbol missing when calling wrapper | Header declares it but shared library does not export symbol | Check version/symbol table/linking |
| Native access warning/error | Permission not granted for restricted FFM operation | `--enable-native-access=ALL-UNNAMED` or corresponding named module |
| `WrongMethodTypeException` | MethodHandle invoked with wrong carrier type | Use generated wrapper or exact `MethodType` |
| JVM crash when calling C | Wrong ABI/layout/lifetime/null/function pointer | Compare native header, generated descriptors, and ownership |
| Field getter out-of-bounds | Pointer segment has size 0 or slice lacks bytes | Only reinterpret when size/lifetime is verified by native contract |
| Java callback not called/already freed | Stub arena closed early or not properly registered | Keep Arena alive, unregister/drain properly per lifecycle |

**Minimum deployment target:** pin the version set of **C headers + native library binary + jextract + JDK/FFM ABI + target platform** and regenerate source with the same configuration. When changing a component that may affect layout/signatures, regenerate bindings and re-verify instead of manually editing generated Java.

## 15. Learning to Read Source Whose Internal Names Change

Sometimes generated source has unfamiliar class/helper names, internal methods, or most logic inside static methods. Instead of memorizing every Java name of a specific generator version:

- Find the **C symbol name** in the header class.
- Find **`$descriptor()`** to understand the C function's signature.
- Find **`$layout()`** and **`$offset()`** to understand field data.
- Find **`sizeof()`** and **`layout()`** to know the struct aggregate.
- Find **`allocate(Arena/SegmentAllocator)`** for structs or callbacks; read the return type to distinguish data allocation vs upcall stub.
- Find **`invoke(MemorySegment, ...)`** in the function pointer helper.
- Find **`$segment()`** for C global variables.
- Find constant getters `NAME()`, remembering enums are not Java `enum`s.
- Read **generated comments** if present, but the final contract still resides in headers/native docs and the ABI.

Names like `$address()`, `$descriptor()`, `$handle()` are not the "real body" of the C function; they serve introspection/FFM linking. The Java client can call generated `add_values(2,5)` without rewriting downcall handles. That is the main benefit of jextract.

## 16. Self-Check Quiz

**Question 1.** Does `int add_values(int,int)` in C become a separate Java `class AddValues` or a wrapper in the header class?

According to the OpenJDK Guide, **ordinary functions** are generated as **static wrapper methods** in the header class, along with `$address/$descriptor/$handle` metadata accessors. No separate class is needed for each non-variadic C function.

**Question 2.** Does `#define DEMO_LIMIT 64` use `DEMO_LIMIT` as a Java constant field or `DEMO_LIMIT()`?

Following the documented pattern, jextract uses an **accessor method `DEMO_LIMIT()`** for numeric macros. However, check the specific output; do not assume a complex macro will also be generated.

**Question 3.** Does `enum demo_state { DEMO_OFF, DEMO_ON }` create a Java `enum DemoState`?

Usually **no**. C enum constants are represented as top-level accessor methods in the header class (`DEMO_OFF()`, `DEMO_ON()`). Bitwise operations must be done with integers when the ABI/API requires it.

**Question 4.** Is `Point.x$offset()` the 0-th field index or a byte offset?

It is the **byte offset** of field `x` according to the generated C struct layout. It avoids assuming packed memory without padding.

**Question 5.** Why is `Point.sizeof()` more reliable than summing field sizes manually?

It reflects the struct size from the layout generator according to the ABI, including padding/alignment; summing fields manually can be wrong.

**Question 6.** How do `binary_fn.allocate((a,b)->a*b,arena)` and `binary_fn.invoke(ptr,a,b)` differ?

`allocate` creates a **function pointer for C to call back into Java** (upcall stub) with the arena's lifetime; `invoke` lets Java call a **native function pointer** (downcall). Both relate to the pointer type but in opposite call directions.

**Question 7.** Does a C function returning `struct Point *` automatically carry sufficient byte bounds into Java?

Not necessarily. Returned native pointers often lack bounds/lifetime. The generated helper `Point.reinterpret` can attach bounds if the **caller verifies** allocation, count, owner, and cleanup. Do not blindly reinterpret pointers of unknown origin.

**Question 8.** `DOUBLE_IT(x)` from `#define DOUBLE_IT(x) ...` is missing from generated source: is that definitely a tool bug?

No. **Function-like macros are not supported by the jextract Guide** as ordinary constants; a C wrapper or Java implementation with matching semantics is needed.

**Question 9.** If you build generated source on Windows x64 and run it on Linux x64, is C `long` guaranteed to keep the same layout?

No. C `long` differs across many Windows and Unix x64 ABIs. You must inspect the generated `C_LONG` and the platform's native library ABI.

**Question 10.** If a C callback is stored asynchronously, can Java close the arena right after `register`?

No. The **upcall stub is only valid while the arena is alive**. C must unregister and complete in-flight callbacks before closing the arena.

**Question 11.** `foo$descriptor()` is correct, yet the native call still crashes: why?

The generated descriptor may be right for the **header jextract parsed**, but the header/library binary may mismatch, pointers may be invalid, thread/lifetime or allocator may be wrong, or the C ABI may differ. Metadata is not proof that all memory accesses are safe.

**Question 12.** Which places should you open first when reviewing generated source?

Header class `demo_h` (function wrappers, constants, and C layouts), struct class `Point` (layout/fields/allocate), function pointer class `binary_fn` (descriptor/allocate/invoke). Then re-verify the C header and library ABI.

## 17. Checklist for Reading and Using Bindings Safely

- [ ] Verified matching JDK 22+/jextract version, target OS/CPU, C compiler, and native library?
- [ ] Know the generated header class name (derived from header by default, or set via `--header-class-name`)?
- [ ] Located each C function's wrapper and `$descriptor/$address/$handle` metadata?
- [ ] Understood return/argument carrier types, especially C `long`/`size_t`/pointer/struct?
- [ ] Read constant accessors for numeric/string macros and C enums; not assuming function-like macros are generated?
- [ ] Know which class represents each struct/union, `layout/sizeof`, and `field$offset/$layout`?
- [ ] For struct arrays, distinguished `asSlice` element index from field byte offsets?
- [ ] For function pointers, distinguished `allocate` (Java callback upcall stub) from `invoke` (native function pointer downcall)?
- [ ] Callback stubs and native data have appropriate arena/lifetime covering all C work, including async?
- [ ] Verified null, buffer size, owner, and proper deallocator before `reinterpret`/dereference?
- [ ] Checked that generated code matches the native headers used to build the binary and exported symbols?
- [ ] Understood why C macros, static inline, typedefs, and platform conditionals may not generate as expected?
- [ ] On errors, checked exact generated source and C ABI before hand-editing generated files?
- [ ] Have tests running on the target platform, not relying on actual address stdout or accidental layout?
- [ ] Generated source is only regenerated when headers/tool intentionally change; no mixing ABI versions?
