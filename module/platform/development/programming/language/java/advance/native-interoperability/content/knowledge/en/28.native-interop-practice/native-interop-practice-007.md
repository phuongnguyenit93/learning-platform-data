# Generate Bindings with jextract and Add a Contract-Checking Wrapper

## Objectives and Practice Deliverables

This practice builds a very small C library, uses **jextract** to generate Java bindings from the `.h` header file, and then writes a **self-managed Java wrapper class** to check the contract before and after the native call. This approach applies when integrating a C library or a C++ C ABI via the Foreign Function & Memory API (FFM).

After completing it, you should have:

1. A native library `labmath` with an integer array sum function and an explicit error contract.
2. Bindings **automatically generated by jextract** from `labmath.h`, capable of calling the C function using `MemorySegment`.
3. A `LabMath` class that accepts a regular `int[]`, validates inputs/ABI, allocates and closes native memory, handles error codes, and returns `long`.
4. A `Main` program demonstrating the results and testing error boundaries, plus a raw call to verify the C contract.
5. A checklist to distinguish header/binary errors, loader errors, data errors, ownership errors, and differences between raw bindings and the public Java API.

**Why is a wrapper class needed?** jextract solves the mechanical part of the ABI: identifying functions, types, layouts, symbols, and building downcalls. It **does not know** the business policy: what the maximum array length is, whether `NULL` is allowed, who owns the buffer, whether it can be called after `close`, which return code is an error, and whether the Java API should throw an exception or return a result. That contract belongs to the **wrapper class**, based on the library's C documentation.

> **Version requirements:** use **JDK 22+** because FFM became a standard API starting in JDK 22. Choose a jextract build compatible with your JDK and verify with `jextract --version`. jextract is a separate tool from the OpenJDK project and is not included by default in every JDK distribution. The Linux examples use a C compiler (`cc`) and a POSIX shell; Windows/macOS adjustments are provided later.

## 1. Contract First: Start from a Clear C ABI

We choose a minimal API so it is easy to observe:

```c
int32_t labmath_abi_version(void);
int32_t labmath_sum(const int32_t *values,
                    int32_t count,
                    int64_t *out_sum);
```

`labmath_sum` contract:

- `count` is in the range **0..4096**, inclusive.
- If `count > 0`, `values` must point to at least `count` readable `int32_t` elements for the duration of the call.
- When `count == 0`, `values == NULL` is valid and the sum is 0.
- `out_sum` must not be `NULL` and must point to at least one writable `int64_t`.
- On success, the function returns `LABMATH_OK == 0` and writes `*out_sum`. On error, it returns a non-zero code and **leaves `*out_sum` unchanged**.
- C **does not retain** the pointers after the function returns; nor does it allocate/free the input data or output buffer itself.
- C does not spawn worker threads or callbacks; all native access completes synchronously before Java closes the `Arena`.
- `labmath_abi_version()` returns the ABI version that the binary actually provides; this value is compared against the constant in the header used to generate the bindings.

With at most 4096 signed 32-bit integers, the sum fits safely in `int64_t`. We intentionally return a 64-bit type to avoid `int32_t` sum overflow. This is a contract decision, not a feature that jextract infers automatically.

| What to protect | What the raw binding sees | What the wrapper must do |
| --- | --- | --- |
| `values` | `MemorySegment`, which may be NULL or a wrongly sized segment | Accept `int[]`, check null/length, create a segment with enough bytes |
| `count` | `int` passed verbatim to C | Prevent exceeding 4096 or mismatching element count |
| `out_sum` | `MemorySegment` pointing to the write target | Allocate 8 bytes with proper alignment, read only after success |
| Return code | `int` returned by C | Convert errors into exceptions preserving the code |
| Version | Function and macro generated from header | Compare header version with binary before use |
| Lifetime | Pointer is just an address | Use `try (Arena ...)` and ensure C does not retain pointers |
| Library | Symbol linked by jextract from binary | Package for the right OS/arch/ABI and check the loader |

## 3. Write the C Header Containing the Contract

Create `native/labmath.h`:

```c
#ifndef LABMATH_H
#define LABMATH_H

#include <stdint.h>

/* Windows: export when building DLL, import when application uses it. */
#if defined(_WIN32)
  #if defined(LABMATH_BUILD)
    #define LABMATH_API __declspec(dllexport)
  #else
    #define LABMATH_API __declspec(dllimport)
  #endif
#else
  #define LABMATH_API
#endif

#ifdef __cplusplus
extern "C" {
#endif

#define LABMATH_ABI_VERSION 1
#define LABMATH_MAX_COUNT   4096

#define LABMATH_OK          0
#define LABMATH_ERR_NULL    1
#define LABMATH_ERR_RANGE   2

/*
 * Returns the C ABI version of the loaded binary.
 */
LABMATH_API int32_t labmath_abi_version(void);

/*
 * values: borrowed, at least count int32_t if count > 0.
 * count: 0..4096; values may be NULL when count == 0.
 * out_sum: borrowed, writable int64_t, must not be NULL.
 *
 * Success: returns 0, writes out_sum.
 * Failure: returns LABMATH_ERR_*, does NOT modify out_sum.
 * Synchronous function; does not retain pointers after returning.
 */
LABMATH_API int32_t labmath_sum(
    const int32_t *values,
    int32_t count,
    int64_t *out_sum);

#ifdef __cplusplus
}
#endif

#endif
```

The `int32_t`/`int64_t` types avoid depending on the size of `long` in C (which varies by platform). When using jextract with a real header, also check struct packing, alignment, calling convention, typedefs, pointer ownership, and compile flags. C++ functions with name mangling need an `extern "C"` layer or a true C ABI; jextract does not automatically interpret the entire C++ object/method model.

The `LABMATH_ABI_VERSION` constant is a contract designed by us. jextract cannot automatically verify the ABI of a binary with a different header version. Therefore, a runtime function `labmath_abi_version` is needed.

## 4. Write the C Library Implementing the Contract

Create `native/labmath.c`:

```c
#include "labmath.h"
#include <stddef.h>

int32_t labmath_abi_version(void) {
    return LABMATH_ABI_VERSION;
}

int32_t labmath_sum(
        const int32_t *values,
        int32_t count,
        int64_t *out_sum) {

    if (out_sum == NULL) {
        return LABMATH_ERR_NULL;
    }
    if (count < 0 || count > LABMATH_MAX_COUNT) {
        return LABMATH_ERR_RANGE;
    }
    if (count > 0 && values == NULL) {
        return LABMATH_ERR_NULL;
    }

    int64_t total = 0;
    for (int32_t i = 0; i < count; ++i) {
        total += (int64_t) values[i];
    }

    *out_sum = total;     /* write only after passing all validation */
    return LABMATH_OK;
}
```

Explanation of intentional details:

1. Check `out_sum` before dereferencing.
2. Check negative/oversized count **before** accessing elements.
3. `values == NULL` is only valid if count equals 0.
4. Accumulate into `int64_t` and only update `out_sum` when there is no longer any reason to fail.
5. C does not retain pointers after the call, so Java's local arena is eligible to close immediately after the downcall.

C code **cannot prove on its own** that a non-NULL pointer actually points to at least `count` elements. Ensuring pointer bounds is the caller's responsibility. If raw pointers are passed directly from Java without a wrapper, C may read outside valid memory.

**Contract counterexample:** if C is later modified to store `values` in an asynchronous processing queue, the Java call below will become dangerous because the `Arena` might close before the queue finishes reading. The protocol must be changed to copy into long-lived native-owned memory or have explicit release/stop/drain functions. Do not keep the same wrapper just because the C signature has not changed.

## 5. Build the Native Library

Example on **Linux x86-64 or aarch64** with a C11 compiler supporting shared libraries:

```bash
mkdir -p build/native build/generated build/classes
cc -std=c11 -O2 -Wall -Wextra -Werror -fPIC -shared \
   -o build/native/liblabmath.so native/labmath.c
```

After building, `build/native/liblabmath.so` must exist. Check exported functions with an appropriate tool, for example `nm -D build/native/liblabmath.so` or `readelf -Ws build/native/liblabmath.so`. Expected symbol names are `labmath_sum` and `labmath_abi_version`.

For macOS, use dynamic library creation mode:

```bash
mkdir -p build/native
cc -std=c11 -O2 -Wall -Wextra -dynamiclib \
   -o build/native/liblabmath.dylib native/labmath.c
```

For Windows, build a DLL using MSVC/clang or a compatible toolchain, defining `LABMATH_BUILD` when compiling C to export functions. The expected file is `labmath.dll`. Specific commands and linker flags vary by toolchain; ensure the same architecture as the JVM and that symbols are actually exported. Do not use a `.so` file on Windows or mix up a 32-bit library with a 64-bit JVM.

## 6. Use jextract to Generate Bindings from the Header

Check tools and JDK:

```bash
java -version
jextract --version
```

Use the jextract release for your chosen JDK (from the [jextract page](https://jdk.java.net/jextract/) or [OpenJDK jextract source](https://github.com/openjdk/jextract)). Newer jextract builds target the current JDK, so compiling the bindings may require a JDK newer than 22.

Example on Linux, from the project root:

```bash
jextract \
  --output build/generated \
  --target-package demo.raw \
  --header-class-name labmath_h \
  --library ":$(pwd)/build/native/liblabmath.so" \
  native/labmath.h
```

Flag meanings:

| Option | Meaning |
| --- | --- |
| `--output build/generated` | Place generated Java sources in the build directory, separate from handwritten code |
| `--target-package demo.raw` | Package for low-level bindings |
| `--header-class-name labmath_h` | Lock the main class name so Java imports remain stable |
| `--library ":.../liblabmath.so"` | Load the exact binary by path; the `:` prefix tells jextract this is a *path* |
| `native/labmath.h` | C header providing signatures, constants, and layouts |

The example uses an absolute path produced by `$(pwd)`; if the project directory moves, you **must regenerate** the bindings or switch to a name-based loading strategy. To run a distributed application, you can use `--library labmath` with the OS library lookup mechanism, or `--use-system-load-library` and `java.library.path` per the jextract documentation. Do not hardcode developer build paths into production artifacts.

After running, inspect `build/generated/demo/raw`. A compatible jextract build will generate the `labmath_h` header class with corresponding accessors. In this practice, we use the standard signatures from the declarations above:

```java
// Expected API in the jextract-generated class, not handwritten code.
int labmath_abi_version();
int labmath_sum(MemorySegment values, int count, MemorySegment outSum);
int LABMATH_ABI_VERSION();
```

This is an **illustration of the signatures to check in the output**, not a complete Java class. For simple functions, jextract also generates `labmath_sum$address()`, `labmath_sum$descriptor()`, and `labmath_sum$handle()`. These help with diagnostics and low-level FFM operations; the public API in the next section should only call the generated wrapper functions.

**Do not be mistaken:** jextract generates `MemorySegment` based on C pointer types; it does not infer that `count` is the element count of `values`, nor does it add `Objects.requireNonNull`, the 4096 limit, or return code checks. Therefore, Java code calling `labmath_h.labmath_sum(...)` directly can still break the C contract.

## 7. Write the Contract-Checking Java Wrapper Class

Create `src/demo/LabMath.java`:

```java
package demo;

import demo.raw.labmath_h;
import java.lang.foreign.Arena;
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;
import java.util.Objects;

public final class LabMath {
    public static final int MAX_ELEMENTS = 4096;

    private LabMath() {}

    public static long sum(int[] values) {
        Objects.requireNonNull(values, "values");
        if (values.length > MAX_ELEMENTS) {
            throw new IllegalArgumentException("Maximum length is 4096");
        }
        int abiVersion = labmath_h.labmath_abi_version();
        if (abiVersion != labmath_h.LABMATH_ABI_VERSION()) {
            throw new LinkageError("Header/native ABI mismatch: " + abiVersion);
        }

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment nativeValues = values.length == 0
                ? MemorySegment.NULL
                : arena.allocate(
                    (long) values.length * ValueLayout.JAVA_INT.byteSize(),
                    ValueLayout.JAVA_INT.byteAlignment());

            for (int i = 0; i < values.length; i++) {
                nativeValues.setAtIndex(ValueLayout.JAVA_INT, i, values[i]);
            }

            MemorySegment out = arena.allocate(ValueLayout.JAVA_LONG);
            int status = labmath_h.labmath_sum(nativeValues, values.length, out);
            if (status != 0) {
                throw new NativeCallException("labmath_sum", status);
            }
            return out.get(ValueLayout.JAVA_LONG, 0);
        }
    }

    public static final class NativeCallException extends RuntimeException {
        private final int status;
        public NativeCallException(String operation, int status) {
            super(operation + " failed with native status " + status);
            this.status = status;
        }
        public int status() { return status; }
    }
}
```

### Walking Through Each Guardrail

**Guardrail 1: Java inputs.** `Objects.requireNonNull` rejects `null` upfront; `MAX_ELEMENTS` is checked right before allocation. Java array lengths are inherently non-negative. The 4096 rule is explicitly placed in the wrapper to avoid accidentally calling C with an oversized count. In production, synchronize this limit with the header via configuration/checking generated constants, and test version mismatches.

**Guardrail 2: header vs. binary.** `LABMATH_ABI_VERSION()` comes from the header; `labmath_abi_version()` comes from the native binary. Different values throw `LinkageError` before manipulating pointers. A version check helps detect conventional version skew, but **does not replace** actual ABI verification: the provider must bump the version when changing the ABI, test symbol/struct layouts, and package the right binary.

**Guardrail 3: size/alignment.** Each Java `int` is copied into a segment with `count * 4` bytes and alignment matching `ValueLayout.JAVA_INT`. Casting `(long) values.length` performs 64-bit multiplication; with the 4096 limit it cannot overflow. The output is allocated with `ValueLayout.JAVA_LONG` matching the 64-bit size in the example. `setAtIndex`/`get` perform bounds checking on the Java side, while C still requires the pointer and count to match.

**Guardrail 4: empty array case.** For a 0-element array, the wrapper passes `MemorySegment.NULL` with `count=0`; that is valid **because the header allows it**. If another C API requires a non-null pointer even when length=0, the wrapper must handle it differently. Do not assume every API allows null/empty.

**Guardrail 5: return code.** Do not read `out` before `status == 0`. When C reports an error, `NativeCallException` carries the operation and raw integer, avoiding information loss from guessing inappropriate exceptions. For a real library, *known error codes* can be mapped to specific exceptions, while unknown codes must still be preserved.

**Guardrail 6: lifetime.** `Arena.ofConfined()` belongs to the thread calling `sum`; `try-with-resources` closes both `nativeValues` and `out` on success or on exception. C only borrows pointers for **the duration of the synchronous downcall** and does not store them, so there is no use-after-free. If C retains pointers for callbacks/workers, a different lifecycle must be designed and the arena must not be closed immediately.

**Guardrail 7: API surface.** Callers see `long sum(int[])`, not `MemorySegment`, `Arena`, or raw error codes. Placing generated code in `demo.raw` and the public wrapper in `demo` prevents unsafe operations from spreading throughout the application. Importing the raw package can be restricted via module/package conventions and code review.

## 8. Write a Program Testing Both Java Behavior and the Raw Contract

Create `src/demo/Main.java`:

```java
package demo;

import demo.raw.labmath_h;
import java.lang.foreign.Arena;
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;

public final class Main {
    public static void main(String[] args) {
        System.out.println("sum=" + LabMath.sum(new int[] {1, 2, 3}));
        System.out.println("empty=" + LabMath.sum(new int[] {}));
        System.out.println("wide=" + LabMath.sum(
            new int[] {Integer.MAX_VALUE, Integer.MAX_VALUE}));

        try {
            LabMath.sum(null);
            throw new AssertionError("null was accepted");
        } catch (NullPointerException expected) {
            System.out.println("null rejected");
        }

        try {
            LabMath.sum(new int[4097]);
            throw new AssertionError("too many elements were accepted");
        } catch (IllegalArgumentException expected) {
            System.out.println("too many rejected");
        }

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment out = arena.allocate(ValueLayout.JAVA_LONG);
            out.set(ValueLayout.JAVA_LONG, 0, 123L);
            int code = labmath_h.labmath_sum(MemorySegment.NULL, -1, out);
            System.out.println("raw status=" + code
                + " out=" + out.get(ValueLayout.JAVA_LONG, 0));
        }
    }
}
```

**Why is there a raw call in `Main`?** This is a test of **the C contract itself**, not how a normal application calls the library. We allocate a valid output, pass `count=-1` and a NULL input pointer; C must detect the invalid range, return `LABMATH_ERR_RANGE == 2`, and not overwrite the sentinel output `123`. That tests the difference between the raw binding (which allows passing arbitrary values) and the wrapper (which rejects invalid data before calling C). This test is only safe because the C API **already** checks count before accessing `values`.

`wide` also verifies that two `Integer.MAX_VALUE` values sum to `4294967294L`, exceeding the `int` limit while fitting in `long`. If native code or the generated binding accidentally used a 32-bit type for output, the test would expose the discrepancy.

Once `build/generated` has been created by jextract, on Linux:

```bash
  -cp build/classes demo.Main
```

Use a JDK compatible with jextract's output. The `--enable-native-access=ALL-UNNAMED` flag grants native call permission to code running on the classpath in this case. When using named modules, configure native-access for the specific module and application packaging rules. Do not enable native access for untrusted code.

**Expected stdout from the sample program** (excluding loader logs or JVM configuration warnings, if any):

```text
sum=6
empty=0
wide=4294967294
null rejected
too many rejected
raw status=2 out=123
```

Meaning:

- `sum=6` proves the path Java `int[]` → native pointer → success code → Java `long`.
- `empty=0` confirms the combination of `count=0` and a valid NULL pointer.
- `wide=4294967294` confirms 64-bit output.
- `null rejected` and `too many rejected` confirm Java validation before allocating/calling C.
- `raw status=2 out=123` confirms C's error condition and the property of not writing output on failure.

If jextract/clang/toolchain is missing on your learning machine, you can **separately verify the syntax and wrapper logic using a test stand-in with the same `labmath_h` signatures**, but that is only a Java-side unit test. To consider the native interop practice complete, you must generate bindings and run the actual `liblabmath` using jextract on a suitable machine.

## 10. Extended Test Matrix to Catch Contract Bugs

| Test | Data / setup | Expected | Catching layer |
| --- | --- | --- | --- |
| Normal sum | `[1,2,3]` | `6` | End-to-end |
| Empty array | `[]` | `0` | Wrapper + C |
| Sum exceeding int32 | `[MAX_INT,MAX_INT]` | `4294967294L` | ABI/output layout |
| Null from Java | `null` | `NullPointerException` before downcall | Wrapper |
| Exceeding limit | `new int[4097]` | `IllegalArgumentException` before downcall | Wrapper |
| Maximum boundary | 4096 valid elements | Correct 64-bit sum | Wrapper + native |
| Negative length raw | `values=NULL,count=-1,out=valid` | `ERR_RANGE`, output unchanged | C |
| Output pointer NULL raw | `out=NULL` | `ERR_NULL`, no dereference | C |
| Positive count + input NULL raw | `count=1,values=NULL,out=valid` | `ERR_NULL` | C |
| Header/binary version mismatch | Header 1, binary returns 2 | `LinkageError` before calling sum | Wrapper |
| Native returns unknown error | Test shim returns mock code | Exception preserves exact code and function name | Wrapper |
| Library not found | Change path/delete file in test env | Linkage/loading error with clear cause | Loader |
| Missing `labmath_sum` symbol | Rename export in test binary | Load/link must fail in a controlled way | Binding + loader |
| Wrong pointer extent | Raw pointer shorter than count | Do not run in main JVM; separate test/sanitizer | Native ABI safety |
| Multi-thread | Multiple threads calling `LabMath.sum` | Each call has its own arena, independent output | Wrapper/thread safety |
| Regenerate header | Change C signature and re-run jextract | Signature diff reviewed; update tests | Build/contract drift |

For a third-party library without a version API, the wrapper can check symbol lookup capability, run a smoke test with small known inputs, verify layouts before opening a session, or maintain its own version-pinning mechanism. Do **not** assume a single version check validates all C layouts.

For undefined memory-safety cases, avoid intentionally passing freed pointers in the main JVM. C/C++ can cause `SIGSEGV` or access violations rather than Java exceptions; run tests in a separate process with AddressSanitizer/UndefinedBehaviorSanitizer when possible, set timeouts, and collect crash dumps.

## 11. What Did jextract Do and What Didn't It Do?

From the C declaration:

```c
int32_t labmath_sum(const int32_t *, int32_t, int64_t *);
```

jextract handles the **ABI-conforming part**: resolving the symbol name, C type descriptor, downcall handle, and Java method accepting the corresponding parameters. Typically, the generated header class provides methods to get the function's `$address`, `$descriptor`, and `$handle`.

Things jextract cannot infer from the prototype alone:

- Whether a pointer is *borrowed* or must be `free`d with a specific function.
- How many bytes/elements a length corresponds to; when a pointer can be NULL.
- Whether passing a memory segment is valid on this thread or after close.
- Whether two C symbols have the same ABI/runtime version as the header at generation time.
- Whether code `0` means success, or whether other codes are retryable.
- Whether the library retains callbacks or pointers after the downcall returns.
- Whether a call can block, spawn workers, or require synchronization.
- Which values must be forbidden by business rules (e.g., max count, input constraints).

The wrapper is where these rules are expressed and tested. For real libraries, **do not edit jextract-generated Java code** to patch null checks and error handling directly: regenerating will wipe out your edits. Keep generated code as a build artifact, and place validation, error mapping, and ownership in separate classes.

If a C API uses structs or opaque handles, the wrapper usually needs `AutoCloseable` and explicit state. For example, if `create_native_handle` returns an owned pointer, `close` must call the exact destructor **once**, after no downcalls/callbacks are still using the handle; not just close the arena holding the pointer. If native code retains a callback, the upcall stub's lifetime must extend past unregister + drain per the contract. Those decisions are outside the scope of this lab's synchronous `labmath_sum` function, but are mandatory when extending the exercise.

## 12. Common Errors and How to Diagnose Them

### 12.1. Cannot Run jextract

- `jextract: command not found`: install the appropriate tool and add the executable to PATH; the JDK does not always include jextract.
- `UnsupportedClassVersionError` when running jextract/generated code: the runtime JDK is too old for the tool or bytecode; check `java -version`, `javac -version`, `jextract --version`.
- Clang cannot parse the header: check `-I` include paths, `-D` macros, compiler flags, typedefs/attributes, and the actual SDK.
- Header contains C++ classes/templates: create a C ABI bridge with `extern "C"` first; jextract primarily processes C headers.
- Too many `--include-function` filters omitting dependent typedefs/structs: use full output first, then filter only once dependencies are known.

### 12.2. Cannot Link or Load the Binary

- `UnsatisfiedLinkError`/linkage failure: check the path in `--library`, file existence, library dependencies, architecture, OS, and exported symbol names.
- On Linux, if using `--library labmath`, the loader searches for `liblabmath.so` via the OS mechanism (`LD_LIBRARY_PATH` can be used). macOS uses `liblabmath.dylib`, Windows uses `labmath.dll`.
- If choosing `--use-system-load-library`, loading relies on `System.loadLibrary` and `java.library.path`; native dependencies still rely on the OS loader.
- “Symbol not found” errors are usually caused by wrong export names, C++ name mangling, wrong library version, or unexported functions. Do not fix bindings by guessing addresses.
- Native-access flag error: set `--enable-native-access=ALL-UNNAMED` for the classpath; for named modules, use the module list per JDK configuration.

**Debugging order:** check tool versions → binary matches OS/arch → symbol exports → generated header class and signatures → library lookup mode → native access → runtime contract.

### 12.3. Wrong Results Despite Successful Build

- Java receives `long` while C returns `int`: header/binary signatures do not match; do not cast as a “quick fix”.
- C `long` type differs on 64-bit Windows and 64-bit Linux: choose `int32_t/int64_t` or generate per platform, and verify layouts.
- Reading `out_sum` when `status != 0`: reading unguaranteed data; read only after success.
- Passing a pointer to a buffer that is too short: crash or corrupt data; wrapper must create segments with exact bounds and count.
- Closing the arena before native completes: use-after-free; async APIs need different stop/drain/ownership handling.
- Using a `MemorySegment` from a confined arena on another thread: may encounter `WrongThreadException`.
- Comparing the version macro against the generated code's own macro **without calling the native version function**: only checks the header, does not verify the binary.
- Editing files in `build/generated` directly: next generation loses edits; put policy in the wrapper.

## 13. How to Bring This Structure into a Real Module

A Java codebase can be divided into three layers:

```text
native C library / third-party C ABI
              ↓  jextract
demo.raw.labmath_h  (generated; ABI only)
              ↓  contract checks + ownership
demo.LabMath         (authored; public Java API)
              ↓
application/service/tests
```

For Gradle or Maven projects, add an appropriate generation/build step **only when truly needed**, keeping generated output outside human-edited sources. Pin a JDK-compatible jextract version; separate native builds by target platform and check header/binary changes in CI. A learning Java repository is not required to use the exact same package layout as the example: `demo.raw` and `demo` are just names for this standalone lab.

Acceptance checks when integrating:

1. `labmath.h` has a clear contract for every pointer, count, return code, ABI version, and ownership.
2. The native library compiles for the right platform; exported symbols match header names.
3. jextract generates bindings with stable package/class names; all output changes are reviewed after regeneration.
4. The Java wrapper blocks invalid inputs, creates proper bounds/alignment, and reads output only when native reports success.
5. The wrapper does not leak raw pointers outside the public API; the arena lives for the exact duration C borrows the pointers.
6. Running `Main` produces the exact six lines of stdout; negative count test confirms output is unchanged.
7. Separate tests for version mismatch, missing symbol, and non-zero native return codes; original error code is preserved in the exception.
8. Tested on each supported OS/arch and with the right JDK/jextract release; do not assume a Linux binary runs on Windows.

**Conclusion:** jextract significantly reduces the work of creating FFM bindings from C headers, but only provides *the native call gate*. A contract-checking wrapper turns that gate into a Java API with valid inputs, clear ownership, meaningful errors, and testability. Integration quality depends on **a clearly written C contract → generated bindings faithful to the ABI → a wrapper guarding conditions the header cannot express on its own → end-to-end tests with the real binary**.
