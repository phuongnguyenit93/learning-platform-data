# 5.7. Distinguishing Message Authentication from Anti-Replay Using Nonces or Sequence Numbers

In a message-exchange protocol, **authentication** answers the question "Was this message created by a party holding the right key/identity and kept intact?", whereas **anti-replay** answers a different question: "Has a valid message like this **already been accepted before** or has it expired?" A message with a completely **valid HMAC or signature can still be an old message being replayed**. This is why payment systems, state-mutating APIs, webhooks, and key-exchange protocols often require **nonces, sequence numbers, timestamps, and receiver-side state**.

## Lesson Objectives

After this lesson, you will be able to:

1. Distinguish origin/integrity checks using **MACs, digital signatures, or AEAD** from checks for **freshness**, ordering, and single use.
2. Describe a replay attack where the HMAC still verifies; explain why plain hashes and standalone timestamps cannot replace an anti-replay mechanism.
3. Choose between a **random nonce/challenge** and a **sequence number** based on communication requirements, ordering, state synchronization, and retry capability.
4. Design mandatory authenticated fields, replay caches/counters, time windows, and **atomic** state writes across multiple servers.
5. Write and run a **Java 21** example using `Mac`/HmacSHA256, `SecureRandom`, `MessageDigest.isEqual`, and an illustrative replay set; understand the exact limits of the example.

## 1. Two Independent Security Properties

Suppose a legitimate client sends a command:

```text
POST /transfers
{"to":"Bob","amount":100}
timestamp = 1700000000
nonce = N1
tag = HMAC(secret, method | path | body | timestamp | nonce)
```

The server verifies the HMAC successfully and transfers 100 units. An attacker captures the signed packet and sends the exact same packet a second time. Because **the data bytes and tag have not changed**, the second HMAC still verifies. If the server does not remember that `N1` was already used, the transfer command may execute again.

| Property / Mechanism | What Does It Prove or Protect? | Prevents Replay by Itself? |
| --- | --- | --- |
| Unkeyed hash, e.g. SHA-256 | Detects changes when a trusted reference hash is available; does not authenticate sender on its own | No |
| MAC/HMAC with shared secret key | Integrity and proof that the tag creator knows the MAC key | **No** |
| Digital signature verified with matching public key | Integrity and origin tied to the private key; outcome also depends on public-key authentication | **No** |
| AEAD, e.g. AES-GCM | Confidentiality + integrity/authenticity of ciphertext and chosen AAD | **Not automatically** at the application-message layer |
| Authenticated timestamp | Bounds message age / validity period | Does not prevent resending **within the window** |
| Authenticated nonce **and** single-use check | Detects that the same nonce was already accepted by the server | Yes, within the scope and state retention period |
| Authenticated sequence number **and** receiver state | Detects old or duplicate sequence numbers, depending on rules and window | Yes, with appropriate acceptance rules |

**Key point:** cryptographic validity is a condition for trusting that data came from a key-holding party; **freshness** is an additional constraint requiring protocol rules and receiver memory. Generating a nonce and ignoring it, or putting a nonce in a header without including it in the HMACed/signed data, provides no replay protection.

### What anti-replay does not promise

If an attacker intercepts a valid request **before** the server accepts it, the attacker can submit it ahead of the real client. An anti-replay system can ensure **only one request is accepted**, but cannot tell which copy was "original" on the network. TLS, key protection, channel authentication, session binding, and other protocol measures remain necessary. If an attacker **knows the HMAC key/private key** and crafts valid new messages, blocking duplicate nonces will not stop that forgery.

## 2. Nonce: A Unique Value per Request

A **nonce** (*number used once*) is a value that a protocol requires to be used at most once **within a defined scope**, such as per client identity + key + session. A nonce may be randomly generated by the client or issued by the server as a challenge.

### 2.1 Client-generated random nonce

Common workflow for an HTTP API:

1. The client uses a cryptographic random generator (`SecureRandom`) to create a sufficiently long nonce, e.g., **128 bits = 16 random bytes**.
2. The client sends `clientId/keyId`, operation, payload, timestamp, and nonce; **the MAC/signature must cover every field affecting the operation's meaning**, especially the nonce and timestamp.
3. The server resolves the key from controlled identity metadata, verifies the tag, checks the timestamp, and then checks the **replay store** for the nonce within that identity/key's scope.
4. The server **records the nonce atomically** before or together with committing the business operation. If the nonce already exists, the server rejects or returns the prior processed result per idempotency policy.
5. The server retains the record long enough so an old message cannot become valid again after the record expires.

A random nonce has negligible collision probability when generated properly, yet **randomness only reduces the chance that two legitimate requests pick the same nonce**. A replay attacker deliberately reuses **the exact old nonce**, so the server must store and check prior usage.

### 2.2 Server-issued nonce (challenge–response)

In some protocols, the server generates a short-lived challenge bound to the client/session, action, and expiration time; the client signs/MACs both the challenge and the request; the server **marks the challenge as used once** upon verification. This gives the server control over nonce lifecycles. In exchange, it requires an extra round trip and challenge state storage. A challenge is valid only within the scope for which it was issued; never use a challenge from one session/target to authorize another operation.

### 2.3 Nonce + timestamp: different roles

- **Nonce + replay store:** catches the exact same request being resent.
- **Authenticated timestamp:** bounds the inspection window and how long records must be retained.
- **Timestamp alone:** a validly signed packet can still be replayed repeatedly within the multi-minute window.
- **Nonce alone without state:** cannot detect reuse.
- **Nonce placed outside MAC/signature:** an attacker can change the nonce and replay another message's tag; this layout is a design flaw.

Policy example: accept `issuedAt` from **5 minutes in the past** to **30 seconds in the future** to allow for considered clock skew. That is an illustrative policy, not a parameter to copy blindly into every system. If the server accepts a message with a +30s future timestamp, the nonce record must survive at least until the message **is no longer valid** (e.g., `issuedAt + 300 seconds` plus safety margin), not merely deleted 300 seconds after receipt time. Synchronize clocks, monitor skew, and bound replay cache size.

### 2.4 Scoping replay lookup keys

With multiple tenants/keys, store replay keys with clear boundaries, for example:

```text
replayKey = protocolVersion | verifiedClientId | keyId | nonce
```

`verifiedClientId` must be an authenticated identity or key-bound identity, not an unverified client-claimed header string. If a nonce is only guaranteed unique **per session**, include session/epoch in the scope; if single-use is required **across all endpoints** under the same key, do not keep isolated per-endpoint replay caches. Define scope before implementing the system.

## 3. Sequence Number: Stateful Ordering Counters

A sequence number (counter) is a monotonically increasing value **per sender, key, or session**, and the counter itself must be inside the MACed/signed data. The server remembers the last accepted value or a window of seen values.

### 3.1 Strictly increasing acceptance

Suppose the server stores `lastAccepted = 40`:

- Receive **41** with a valid tag → accept and update `lastAccepted = 41`.
- Receive **41** again → reject duplicate.
- Receive **39** → reject stale.
- Receive **43** before **42** → 43 may be accepted if the rule is `seq > lastAccepted`; afterward 42 is treated as stale. If the rule is `seq = lastAccepted + 1`, wait for 42 or use a reordering mechanism.

Explicitly decide whether the protocol requires **strict sequential order**, **stale/duplicate rejection only**, or **bounded out-of-order tolerance**. A monotonic counter alone does not guarantee completion of lost commands.

For clients with multiple threads/devices, a single shared counter can become a bottleneck or cause out-of-order arrivals. Typically you need a separate counter per **security association/session**, or random nonces when operations are independent and order is not required. Counters must be durably persisted and must never reset to old values on restart, unless starting a newly authenticated **epoch/session**.

### 3.2 Sliding window for out-of-order messages

One option for out-of-order datagrams/streams is storing `highestSeen` alongside a bitmap of recently seen sequence numbers:

```text
highestSeen = 100; windowSize = 64
Active window: 37..100

seq = 98, bit 98 unset -> accept, mark 98
seq = 98 again         -> reject because bit is set
seq = 36               -> reject because outside window
seq = 101, valid tag   -> shift window and mark 101
```

This is an **algorithm description**, not production code. Shifting the bitmap must handle overflow, session start values, key reset/rotation, epoch transitions, sequence jumps larger than multiples of the window size, and concurrent access. For financial HTTP APIs, nonces + business records are often easier to audit than sliding-window bitmaps.

### 3.3 Comparing nonces and sequence numbers

| Criterion | Random Nonce + Cache | Counter / Sequence Number |
| --- | --- | --- |
| Fresh data generation | `SecureRandom` or server challenge | Counter incremented per message |
| Receiver state | Set of accepted nonces + TTL/scope | High-watermark, optionally plus window bitmap |
| Out-of-order packets | Acceptable if nonce is fresh and timestamp valid | Requires window design or reordering |
| Concurrent client sends | Natural when nonces are independent | Must allocate numbers without collision and coordinate order |
| Restart recovery | Persist/shared cache retained long enough | Persist counter, guard against resets/epochs |
| Best suited for | Independent API requests, webhooks, challenge–response | Ordered channels, packet/session protocols |
| Typical pitfalls | Per-node local cache; TTL too short; unsigned nonce | Counter reset; skipped numbers; update race; dropping valid packets |

Both approaches must guard against **concurrent race conditions**: if two requests with the same nonce/sequence hit two different workers, at most one worker may succeed. Separate "check-then-write" steps are unsafe.

## 4. Fields That Must Be Authenticated With the Message

At minimum, when using an HMAC or signature for a state-changing operation, signer and verifier must agree on **the exact signed bytes**:

- Protocol version and usage purpose (*domain separation*), e.g., `payment-v1`.
- Sender identity bound to the key, `keyId`/session if applicable; target service/tenant/recipient to avoid forwarding a signature across another trust domain (*cross-context replay*).
- HTTP method, resource/path, query parameters, or message components determining the operation.
- Payload in a deterministic encoding (body bytes, or a digest covered by the signature/MAC per protocol).
- Nonce or sequence number, timestamp, expiration, or window when used.

Never concatenate strings arbitrarily like `"AB" + "C"` and `"A" + "BC"` because they yield identical bytes. Use length-prefixing, structured binary encoding, or a canonicalization rule defined and tested at **both ends**. JSON varies in field order, whitespace, and number formatting; when signing JSON, require canonical JSON or sign the exact received raw body bytes. Account for proxies, URL normalization, and protocol-permitted header edits.

**Common bug:** signing body while omitting method/path lets a body signature be transplanted to another endpoint; signing body and timestamp while omitting nonce leaves the nonce unprotected; reusing one key/MAC format across message types without version/purpose fields increases context-confusion risk.

## 5. Java 21 Practice: Valid HMAC Rejected on Replay

The example below simulates **one client and one server sharing an HMAC key**, in a single process, with a fixed clock for deterministic stdout. It demonstrates three checks: **valid tag**, **timestamp within window**, and **unused nonce**. Real systems require mapping `clientId` to separate keys, a shared/persistent replay store, and transactional business processing; Section 7 covers those.

Create the exact file **`ReplayDemo.java`**:

```java
import java.io.ByteArrayOutputStream;
import java.io.DataOutputStream;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Base64;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import javax.crypto.KeyGenerator;
import javax.crypto.Mac;
import javax.crypto.SecretKey;

public class ReplayDemo {
    record Request(String method, String path, String body,
                   long issuedAt, String nonce, String tag) {}

    // Length-prefix each field to avoid concatenation ambiguity.
    static void field(DataOutputStream out, String value) throws IOException {
        byte[] bytes = value.getBytes(StandardCharsets.UTF_8);
        out.writeInt(bytes.length);
        out.write(bytes);
    }

    // The tag does not sign itself. Every meaningful field is signed.
    static byte[] signedBytes(Request request) throws IOException {
        ByteArrayOutputStream buffer = new ByteArrayOutputStream();
        DataOutputStream out = new DataOutputStream(buffer);
        field(out, "replay-demo-v1");
        field(out, request.method());
        field(out, request.path());
        field(out, request.body());
        out.writeLong(request.issuedAt());
        field(out, request.nonce());
        out.flush();
        return buffer.toByteArray();
    }

    static byte[] hmac(SecretKey key, Request request) throws Exception {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(key);
        return mac.doFinal(signedBytes(request));
    }

    static Request sign(SecretKey key, String body, long issuedAt)
            throws Exception {
        byte[] random = new byte[16];       // 128-bit nonce.
        new SecureRandom().nextBytes(random);
        String nonce = Base64.getUrlEncoder().withoutPadding()
                .encodeToString(random);
        Request unsigned = new Request(
                "POST", "/payments", body, issuedAt, nonce, "");
        String tag = Base64.getUrlEncoder().withoutPadding()
                .encodeToString(hmac(key, unsigned));
        return new Request(unsigned.method(), unsigned.path(),
                unsigned.body(), unsigned.issuedAt(), nonce, tag);
    }

    static boolean verify(SecretKey key, Request request,
                          long now, Set<String> usedNonces)
            throws Exception {
        // Illustrative window: at most 300 seconds old, 30 seconds in the future.
        if (request.issuedAt() < now - 300 || request.issuedAt() > now + 30) {
            return false;
        }
        byte[] suppliedTag;
        try {
            suppliedTag = Base64.getUrlDecoder().decode(request.tag());
        } catch (IllegalArgumentException ex) {
            return false;
        }
        // Verify MAC BEFORE claiming the nonce in the replay store.
        if (!MessageDigest.isEqual(hmac(key, request), suppliedTag)) {
            return false;
        }
        // Atomic within one JVM: only the first nonce insertion returns true.
        return usedNonces.add(request.nonce());
    }

    public static void main(String[] args) throws Exception {
        KeyGenerator generator = KeyGenerator.getInstance("HmacSHA256");
        generator.init(256);
        SecretKey sharedKey = generator.generateKey();
        Set<String> usedNonces = ConcurrentHashMap.newKeySet();
        long now = 1_700_000_000L; // Simulated time for deterministic test output.

        Request first = sign(sharedKey, "{\"amount\":100}", now);
        System.out.println("new request: " +
                verify(sharedKey, first, now, usedNonces));
        System.out.println("exact replay: " +
                verify(sharedKey, first, now, usedNonces));

        Request modified = new Request(first.method(), first.path(),
                "{\"amount\":900}", first.issuedAt(),
                first.nonce(), first.tag());
        System.out.println("tampered body: " +
                verify(sharedKey, modified, now, usedNonces));

        Request expired = sign(sharedKey, "{\"amount\":100}", now - 301);
        System.out.println("stale request: " +
                verify(sharedKey, expired, now, usedNonces));
    }
}
```

Compile and run with **JDK 21 or a newer compiler supporting `--release 21`**:

```text
javac -version
mkdir out
javac --release 21 -encoding UTF-8 -d out ReplayDemo.java
java -cp out ReplayDemo
```

Stdout from the program (random nonces and keys are **not** printed so output stays deterministic):

```text
new request: true
exact replay: false
tampered body: false
stale request: false
```

### Why does this output happen?

1. **New request = true:** valid tag, timestamp within window, and `usedNonces.add(nonce)` adds the nonce for the first time.
2. **Exact replay = false:** payload and HMAC are still valid, yet `add` on an already-present nonce returns `false`. This is the **anti-replay** layer that HMAC alone does not provide.
3. **Tampered body = false:** the object keeps the old tag while `body` changed; HMAC verification fails right before touching the replay set.
4. **Stale request = false:** the new request has a valid tag and fresh nonce, but its timestamp is 301 seconds old so it is rejected.
5. `MessageDigest.isEqual` is the standard API for comparing tag bytes rather than writing a loop that exits on the first differing byte; verification must still bound input length/format and avoid leaking sensitive error details.

### Intentional limitations of the program

- `ConcurrentHashMap.newKeySet()` makes `add` atomic **within a single JVM**; data is lost on process restart, not shared across server nodes, and has no TTL. This is a **demo**, not production anti-replay.
- Fixed `now` is only for reproducible lab output. Real systems use an injectable/controllable clock (e.g., UTC `Clock` for testing) and proper expiration/tolerance policies.
- The key is generated ephemerally with `KeyGenerator`. Real systems provision per-principal keys via a key management/KMS/keystore workflow, store secrets safely, support rotation, and never embed real keys in source code/logs.
- The demo uses `String body`. An HTTP service must sign the exact **received payload bytes** or defined canonical form, validate required method/path/headers, and bind the authenticated principal.
- The demo does not execute business logic, provide response idempotency, or resolve races between a replay store and a database. Do not use this standalone `verify` function to safeguard financial transactions.
- A new request with a **new nonce** and an identical body to an earlier request will be accepted: that may be a valid new operation. If business rules require "one order is charged at most once," add an **idempotency key / business ID**.

## 6. When Choosing Sequence Numbers: Updates Must Be Atomic

For a protocol accepting any `seq > lastAccepted` without replays, a single-process update concept can be written with `AtomicLong`. **Only run this step after verifying a tag covering `seq` and identifying the sender/session**:

```java
import java.util.concurrent.atomic.AtomicLong;

public class SequenceGate {
    private final AtomicLong lastAccepted = new AtomicLong(0);

    // Precondition: MAC/signature covering seq has already been verified.
    public boolean accept(long seq) {
        while (true) {
            long last = lastAccepted.get();
            if (seq <= last) {
                return false;
            }
            if (lastAccepted.compareAndSet(last, seq)) {
                return true;
            }
        }
    }

    public static void main(String[] args) {
        SequenceGate gate = new SequenceGate();
        System.out.println(gate.accept(41));
        System.out.println(gate.accept(41));
        System.out.println(gate.accept(40));
        System.out.println(gate.accept(42));
    }
}
```

```text
javac --release 21 SequenceGate.java
java SequenceGate
```

```text
true
false
false
true
```

This example is an **in-memory gate** for a single sender; since it does not verify a MAC here, never call it directly on unauthenticated data. It does not enforce contiguous order, rejects late packets arriving after a higher seq, and loses its watermark on restart. In production, persist **(verified principal, key/session epoch, lastAccepted)** with compare-and-swap in durable storage or a locked transaction; if out-of-order delivery is needed, use a tested sliding-window algorithm.

## 7. Real Server Design: Authentication, Anti-Replay, and Business Logic

A real-world pipeline can follow these steps:

```text
Receive request
   |
   v
Size-bounded parse, identify keyId and principal
   |
   v
Fetch key from trusted registry + check permissions and context
   |
   v
Reconstruct exact bytes to sign; verify HMAC/signature
   | invalid --> Reject
   v
Check timestamp/expiry, nonce/seq, session/audience
   | invalid --> Reject
   v
Atomic transaction: claim nonce/seq + execute one business action
   | duplicate --> Reject or return stored idempotent result
   v
Commit and return response
```

Here `claim` is an atomic **check-and-record** operation on the replay key/counter: only one request with the same replay identity can win processing rights, even across multiple concurrent servers.

### 7.1 Data design example for nonces

A replay guard table can use a unique key:

```sql
CREATE TABLE replay_guard (
    principal_id  VARCHAR(128) NOT NULL,
    key_id        VARCHAR(128) NOT NULL,
    nonce         VARCHAR(128) NOT NULL,
    expires_at    TIMESTAMP NOT NULL,
    PRIMARY KEY (principal_id, key_id, nonce)
);
```

Once the request is authenticated, open a transaction and attempt to `INSERT` a record; a unique-key conflict means the nonce was already used. Within the **same transaction boundary**, record state/outcome and the single-execution business changes. Only on commit is the request durably accepted. Other databases differ in UPSERT/transaction syntax while preserving equivalent semantics. The SQL above shows a **schema**, not a complete transaction workflow; production requires input limits, DB permissions, expiry cleanup, and concurrency error handling.

**Do not use this anti-pattern:**

```text
if (!replayStore.contains(key)) {
    businessAction();
    replayStore.put(key);
}
```

Two threads can both observe "not present" and both run `businessAction()`. A separate `SELECT` followed by `INSERT` unprotected by locks/transactions suffers the exact same race.

**Mid-step failure note:** if you claim a nonce in Redis with `SET NX` and the business transaction then fails, the client may be unable to retry even though no business effect happened. Conversely, if the business commits yet recording the nonce fails, re-execution becomes possible. Design `processing/succeeded/failed` states, unique operation IDs, response caching, or shared transactions to achieve the right semantics. "Accepted at most once" does not automatically mean "guaranteed to succeed exactly once."

### 7.2 Multi-server synchronization and TTL

- Every node handling the same principal/replay scope must share **one consistent source of truth**, such as a DB unique constraint or atomic operations in a shared store designed to survive node loss/failover.
- TTL must extend **at least until the request can no longer pass freshness checks**, with safety margin for clock skew, replication, and slow processing. Never allow a record to expire while the request itself is still inside its validity window.
- Cap requests/nonces per client, string lengths, and submission rates; otherwise, the replay store can be abused for resource exhaustion. Record nonces **only after authentication succeeds** so unsigned junk requests cannot fill memory.
- On key rotation or sequence resets, clearly specify `keyId`, epoch, authentication requirements, and legacy state retention; never accidentally reopen the door for old messages.
- Log by event type, principal, and request ID; avoid logging secret keys, raw tokens, sensitive plaintext, or full MACs.

## 8. Replay, Retry, and Idempotency Are Three Related Problems

**Malicious replay:** a third party resends a valid packet to trigger duplicate side effects. **Legitimate retry:** a client resends after a timeout because it does not know whether the server finished. **Idempotency:** multiple calls to the same *logical operation* produce at most one business effect according to defined rules.

For example, a payment client sends operation ID `order-123` with nonce `N1`. The server completes processing, yet the response is lost; the client resends **the exact same old request**. The replay guard rejects nonce `N1`, or to support clean retries, the server can return the **stored response** for `order-123` without executing the transfer a second time. If the client retries with a **new nonce N2**, protocol-level anti-replay sees a fresh message; an **idempotency key / unique business ID** must still prevent duplicate business execution. Idempotency keys must be bound to the principal and request contents: reusing a key with a different payload should report a conflict rather than silently returning the old result.

| Scenario | Valid Tag? | Nonce/Seq Check | What the Server Should Do |
| --- | --- | --- | --- |
| Fresh request matching policy | Yes | Unseen | Accept and record atomically, execute operation |
| Verbatim packet replay | Yes | Already seen | Do not re-execute |
| Altered `amount` with old tag | No | Not reached | Reject before writing replay state |
| Valid tag with expired timestamp | Yes | May be new nonce | Reject because no longer fresh |
| Same order, new nonce, new tag | Yes | Unseen | Check business idempotency to avoid double charging |
| Same request hits two nodes concurrently | Yes | Same nonce | Atomic claim ensures at most one node processes |
| Old counter after restart | Yes | Stale if state persisted | Reject; losing state is a vulnerability to fix |

### Boundaries with TLS and AES-GCM

TLS protects data in transit and has its own record/sequence mechanism. **Do not assume** an HTTP command replayed over a **new TLS connection** will be rejected by the TLS layer. Application-layer idempotency/anti-replay still depends on application design.

AES-GCM uses a **cryptographic IV/nonce** with strict requirements against reusing an IV with the same key. An AES-GCM IV is encryption material; an **application replay nonce** lets the receiver detect already-processed messages. Both concepts can appear in the same protocol, yet **they do not automatically replace each other**. A replayed valid AES-GCM ciphertext with a valid tag still needs replay state if the application must reject the second delivery.

## 9. Testing Checklist and Mistakes to Avoid

| Test | Expected Behavior |
| --- | --- |
| Send the same request/tag/nonce twice | Second delivery creates no business side effect |
| Alter body, method, path, timestamp, or nonce while keeping tag | Authentication fails |
| Timestamp just inside and just outside bounds | Handled strictly per clock skew/expiration rules |
| Two requests with same nonce hit two nodes concurrently | At most one request wins claim |
| Restart server while old request is still within window | Replay is still rejected if accepted before restart |
| Retry after lost response | No double charge/order; proper idempotent response |
| Out-of-order, missing, duplicate, or out-of-window sequence | Matches published strict or sliding-window policy |
| Key rotation, session/epoch change, multi-device client | Old state does not reopen and counters do not collide unexpectedly |
| Replay after TTL or near skew boundary | Old message has expired before its record is purged |
| Invalid tag with a fresh nonce | Does not consume the nonce in the replay cache |
| Overlong nonce / rapid flood | Resource bounds and rate limits hold |

**Common mistakes to remember:**

- "Valid HMAC means the request is fresh": **false**, tags remain valid on verbatim replay.
- "Adding a UUID/nonce header is enough": **false**, it must be authenticated and tracked statefully.
- "Signed timestamp eliminates replay": **false**, replays succeed anywhere inside the acceptance window.
- "Store nonces in a `HashSet` per server": only works for single-process demos; multi-node systems need shared atomic state.
- "Check nonce, process, then record": creates a race under concurrent requests and risks double effects.
- "Incrementing counter without signing it": an attacker can bump it to a higher number to bypass the gate.
- "One execution per nonce means one execution per transaction": **false**, the same transaction can be re-signed with a new nonce.
- "HMAC nonces and AES-GCM IVs are both called nonces so they are interchangeable": **false**, they protect different properties under different constraints.

1. **Explain a replay flow:** diagram 3 messages between client, attacker, and server; pinpoint the exact step where HMAC still passes and the step where the replay store rejects the used nonce.
2. **Java practice:** run `ReplayDemo.java`. Temporarily remove the `usedNonces.add(...)` line (in your lab copy only) to observe replays passing unchecked. Change `amount` while keeping the old tag and explain why it is rejected.
3. **Scenario design:** an API receives webhooks from multiple senders, runs on 4 nodes, and allows retries for 24 hours. Specify who issues nonces, the replay key scope, TTL, shared state storage, and duplicate response handling.
4. **Nonce vs. sequence choice:** a UDP message stream that can reorder, a parallel order-creation API, and a strictly ordered command channel. For each scenario, choose a mechanism, explain which fields must be signed, and how late messages are handled.
5. **Tricky calculation:** if a server checks `now-300 <= issuedAt <= now+30` and at time `now` accepts a message with `issuedAt=now+30`, until when must the nonce record remain alive to block replays? Explain why "TTL of exactly 300 seconds from receipt" is not always enough.
6. **Transaction analysis:** describe what happens if the cache marks a nonce yet the DB rolls back, or the DB commits yet the cache write fails; propose a unique operation ID + transaction/response cache to prevent double charges.

- [NIST SP 800-38D — GCM and GMAC](https://csrc.nist.gov/pubs/sp/800/38/d/final): AEAD properties and IV/nonce requirements for GCM.

**Self-assessment:** If a request with a valid MAC/signature arrives a second time, do you have a mechanism that is **stateful enough, atomic enough, properly scoped, and retained long enough** to decide whether it may run again? Answering that is what truly separates message authentication from anti-replay.
