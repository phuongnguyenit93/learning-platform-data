# 14.2 Distinguishing Path Building with CertPathBuilder from Path Checking with CertPathValidator

In Java PKI, a server's X.509 certificate may be issued by an intermediate CA, which in turn is issued by a root CA that the application trusts. To decide whether to **trust the target certificate's public key**, the application needs an appropriate **certification path** and must verify that path against PKIX policy. Java separates two tasks:

- **`CertPathBuilder` — building a path:** given a **target certificate**, a set of **trust anchors**, selection criteria, and a source of **candidate certificates**, the engine **discovers a valid path** leading to a trust anchor. It both **searches** and **validates** to return a path already verified against the supplied parameters.
- **`CertPathValidator` — checking a path:** takes **an already-supplied path** and a set of trust anchors/policies, then **evaluates that exact path**. It is not responsible for finding a replacement chain if the supplied chain is missing an intermediate, is out of order, or is invalid.

This is lesson **14.2** in section **14. Trust Paths** of Java Advanced Security & Cryptography. The focus is understanding the inputs and outputs of the two JCA engines, the roles of `CertStore`, `PKIXBuilderParameters`, `PKIXParameters`, and `TrustAnchor`; running a Java 17+ experiment with real root/intermediate/leaf certificates generated by `keytool`; and accurately recognizing the limits of PKIX compared to hostname/TLS/revocation verification in production systems.

## 1. One Table So You Never Confuse the Two Engines

| Aspect | `CertPathBuilder` | `CertPathValidator` |
| --- | --- | --- |
| Primary question | “**Can a valid certification path be found** from the target to a trust anchor?” | “**Is the given certification path** valid under the trust anchors and policy?” |
| Primary inputs | `CertSelector` selecting target, `TrustAnchor`, candidate source (`CertStore`), `PKIXBuilderParameters` | An **existing** `CertPath`, `TrustAnchor`, `PKIXParameters` |
| Is the full chain needed upfront? | **Not necessarily**; enough retrievable candidates/intermediates to link the chain are needed | **Yes**: the path must be supplied in order with all certificates except the trust anchor |
| Searches multiple options / cross-signs? | Can explore candidates/paths depending on implementation and policy | Does not search for alternative paths; processes only the passed-in path |
| Verifies signatures/validity/PKIX constraints? | **Yes**; the returned path has been verified against the builder parameters | **Yes**; this is its primary responsibility |
| Parameters | `PKIXBuilderParameters` (extends `PKIXParameters`) | `PKIXParameters` |
| PKIX result | `PKIXCertPathBuilderResult` with `CertPath`, `TrustAnchor`, public key, and policy tree | `PKIXCertPathValidatorResult` with `TrustAnchor`, public key, and policy tree; does **not** return a new `CertPath` |
| Common error | `CertPathBuilderException` when no accepted path can be found | `CertPathValidatorException` when the supplied path fails checks |
| When to use | Only the leaf and a pool of candidate intermediates/CAs are available; chain is incomplete or multiple linking options exist | A fixed chain has already been received/obtained and needs checking against trust policy |
| Critical security note | A candidate store is **not a truststore**; a plausible-looking candidate is not trustworthy on its own | A syntactically well-formed certificate path can still be rejected for trust/policy/date reasons |

**Common misconception:** `CertPathBuilder.build(...)` **does not merely “stitch certificates together”**. With the `"PKIX"` algorithm, the engine finds **a path that has already been validated** under PKIX policy; `PKIXCertPathBuilderResult.getCertPath()` holds an already-checked path. You may call `CertPathValidator` afterward to revalidate at a **different date/policy** or for demonstration, but a successful build does not require revalidating again with identical parameters.

## 2. Certification Path, Trust Anchor, and Candidate Certificates

Consider a simple topology:

```text
                         ROOT CA
             CN=Example Root CA
             [self-signed in lab]
             [TRUST ANCHOR configured by app]
                        |
                        | signs certificate
                        v
                     ISSUING CA
              CN=Example Issuing CA
              [intermediate certificate]
              [CA=true; keyCertSign]
                        |
                        | signs certificate
                        v
                   END ENTITY / LEAF
             CN=service.example.test
             [SAN: service.example.test]
             [CA=false; serverAuth]
```

The verifier starts from the **leaf certificate** and wants to trace a valid signature/issuer chain back to an **approved root CA**. Not every root CA existing on the Internet automatically becomes a trust anchor: the list of approved roots comes from **the application's truststore or policy**.

### 2.1 In Java, What Does CertPath Contain?

In the standard Java PKIX storage direction, the path's certificate list is represented from the **target upward**:

```text
CertPath.getCertificates():
    [0] leaf certificate                (target)
    [1] intermediate CA certificate
    [does not contain root trust anchor]

PKIXCertPathBuilderResult.getTrustAnchor():
    trusted root CA
```

That is why in the hands-on example, `getCertPath().getCertificates().size()` equals **2** even though the topology has **3 certificates**. **The trust anchor stays separate**, and is not appended to the certificate list of the `CertPath` returned by the PKIX builder.

`CertPath` is an **immutable object** holding an ordered list of certificates and path type; it can be created via `CertificateFactory.generateCertPath(...)`, returned from `CertPathBuilder`, or decoded from an appropriate encoding. Having a `CertPath` object **does not by itself assert validity**: a certificate list can be constructed even when signatures, dates, or trust anchors are wrong.

### 2.2 TrustAnchor Is an Independent Trust Decision

`java.security.cert.TrustAnchor` describes a CA approved as a trust starting point in PKIX. It can be created from a trusted `X509Certificate` or a CA name + public key (per API). In this lab we use:

```java
// Snippet inside a method that already has root as an X509Certificate.
TrustAnchor anchor = new TrustAnchor(root, null);
Set<TrustAnchor> anchors = Set.of(anchor);
```

The snippet above is a **non-standalone illustration**, not a full Java class. The root certificate in the lab is **explicitly trusted** by the application; simply being self-signed does not make `root` safe in production. Before adding a root CA/private CA to a truststore, verify **its source, fingerprint, trust scope, and administrative authority**.

The trust anchor sits outside the path validated in the usual way; do not assume every attribute of the root certificate is checked identically to leaf/intermediate certificates (for example, constraints on the anchor must be governed by **trust policy**). Changing the trust anchor can completely change the outcome for the same path.

### 2.3 CertStore Is a Candidate Source, Not a Trust Point

`java.security.cert.CertStore` is a source for looking up certificates and CRLs. It can back onto an in-memory collection, an LDAP directory, or another backend depending on the provider.

```text
Trusted CA / TrustAnchor
     |
     +-- from truststore/policy -> basis for approving a path
     |
CertStore (Collection/LDAP/...):
     +-- leaf certificates
     +-- intermediate CA certificates
     +-- candidate CRLs
     |
     +-- supplies data to builder/PKIX, does NOT grant trust
```

Putting an intermediate into `CertStore` only helps the builder **find the link**; it does not turn the intermediate into a trusted root. An attacker-supplied certificate can sit in the candidate pool; the builder/validator itself must verify the chain leading to a **pre-configured trust anchor** and security conditions.

**Do not blindly import a missing intermediate into the truststore as an anchor** just because the builder throws an error. Retrieve the intermediate from an appropriate source, verify its issuer/chain, and supply it as a **candidate**; trust anchors must be a policy decision.

## 3. CertPathBuilder: Select a Target, Then Find a Valid Path

Related classes:

```text
java.security.cert.CertPathBuilder
    getInstance("PKIX")
    build(CertPathParameters)
                |
                v
java.security.cert.PKIXBuilderParameters
    trustAnchors          (CAs the receiver actually trusts)
    targetCertConstraints (CertSelector picking the target)
    CertStores            (intermediate/CRL candidates)
    date, policies, revocation, checkers, constraints...
    maxPathLength          (limit on intermediates)
                |
                v
java.security.cert.PKIXCertPathBuilderResult
    getCertPath()     = path both built AND validated
    getTrustAnchor()  = anchor used
    getPublicKey()    = target's public key
    getPolicyTree()   = policy tree result (may be null)
```

### 3.1 Minimal Input

```java
// Illustrative snippet (not standalone):
// root and leaf are already-parsed X509Certificates;
Set<TrustAnchor> anchors =
        Set.of(new TrustAnchor(root, null));

X509CertSelector target = new X509CertSelector();
target.setCertificate(leaf);

CertStore source = CertStore.getInstance(
        "Collection",
        new CollectionCertStoreParameters(
                List.of(leaf, intermediate)));

PKIXBuilderParameters params =
        new PKIXBuilderParameters(anchors, target);
params.addCertStore(source);
params.setRevocationEnabled(false); // Lab-only setting.

PKIXCertPathBuilderResult result =
        (PKIXCertPathBuilderResult)
                CertPathBuilder.getInstance("PKIX").build(params);
```

**Key points to understand:**

1. **Target constraints** specify criteria for the target certificate. `target.setCertificate(leaf)` selects one specific certificate; in a system searching among multiple candidates you can use `setSubject`, `setKeyUsage`, `setExtendedKeyUsage`, and appropriate criteria.
2. **Trust anchors** define the final point of acceptance—never derived from filenames or arbitrary self-signed certificates.
3. **CertStore** supplies candidate intermediates/certificates/CRLs; **the builder is permitted to search** sources supported by the provider/policy. Do not expect every provider to automatically download AIA over the Internet; provide controlled sources and measure on a real JDK.
4. **PKIXBuilderParameters extends PKIXParameters**: in addition to validation parameters, it adds **target constraints and a path length limit**.
5. **Revocation** is disabled in the code **only so the demo runs offline**, with no real CRL- or OCSP-issuing CA. Production must have an **explicit revocation policy** rather than copying `false`.
6. The builder can inspect multiple candidates/chains; the resulting path is **validated**, not merely chained by `issuerDN == subjectDN`.

### 3.2 What Does setMaxPathLength Mean?

`PKIXBuilderParameters.setMaxPathLength(int)` limits the **number of non-self-issued intermediate certificates** in the path per the API contract. With the topology leaf → one intermediate → root anchor, `maxPathLength=1` suffices; `maxPathLength=0` allows only paths with no such intermediate.

- Value **`-1`**: no limit imposed by this setting.
- Value **`0`**: allows only a path with **one certificate** before the anchor.
- If unset, **the API default is 5** per the Java 21 documentation.
- This is **not** a limit on the total number of certificates including root anchor and leaf. Separate rules apply for CA-signed `BasicConstraints.pathLenConstraint`; actual policy may be stricter than the builder limit.

Example:

```java
// Illustrative only, inside a method with PKIXBuilderParameters params.
params.setMaxPathLength(1); // One intermediate in the lab.
```

The limit prevents overly deep search algorithms and out-of-policy paths, **but does not** replace signature validation, usage checks, algorithm constraints, or trust anchors.

## 4. CertPathValidator: Checking an Existing CertPath

The validator takes a **specific certification path**:

```text
     CertPath
  [leaf, intermediate]  --------+
                                |
          PKIXParameters -------+------> CertPathValidator("PKIX")
          - trust anchors                      |
          - date, policies                     v
          - revocation                    Validate signatures,
          - checkers                      basicConstraints,
          - cert constraints             validity, policies...
                                                |
                                       +--------+---------+
                                       |                  |
                                     PASS                 FAIL
                                       |                  |
                         PKIXCertPathValidatorResult  CertPathValidatorException
                           trustAnchor, publicKey,         index/reason/cause
                           policyTree
```

### 4.1 Creating a CertPath Manually

When you **already have the chain in the right order**, you can construct a `CertPath` via `CertificateFactory`:

```java
// Illustrative snippet inside a method with full imports/throws.
// root is not in the path list because it is the trust anchor.
CertificateFactory factory = CertificateFactory.getInstance("X.509");
CertPath givenPath =
        factory.generateCertPath(List.of(leaf, intermediate));

PKIXParameters params = new PKIXParameters(
        Set.of(new TrustAnchor(root, null)));
params.setRevocationEnabled(false); // Lab ONLY without CRL/OCSP.

PKIXCertPathValidatorResult checked =
        (PKIXCertPathValidatorResult)
                CertPathValidator.getInstance("PKIX")
                        .validate(givenPath, params);
```

Unlike the builder, the validator **does not use `CertStore` to fix ordering or supply missing intermediates**. It can use `CertStore` when **supporting validation data** is needed—especially CRLs/revocation—but that **does not turn** the validator into a path discovery engine.

**Ordering matters:** `CertificateFactory.generateCertPath(List)` for X.509 PKIX typically expects **leaf → intermediate CA(s)** per the Java API. Do not append the root trust anchor to the end of the list just to make “all three certificates”: the anchor is passed separately in parameters.

### 4.2 PKIXParameters Describes the Verification Policy

Important attributes of `PKIXParameters`:

| Component | Typical API | Effect |
| --- | --- | --- |
| Trust anchors | `new PKIXParameters(Set<TrustAnchor>)` or from trusted certificate entries of a `KeyStore` | Defines which CA/key serves as the accepted trust point |
| Validation date | `setDate(Date)` | Sets the point in time used to check validity; does not perform clock-stamping |
| Revocation | `setRevocationEnabled(boolean)` | Enables/disables revocation checking per capabilities/checker/policy |
| Certificate/CRL sources | `addCertStore(CertStore)` | Supplies sources for revocation and related checks |
| Policy OIDs | `setInitialPolicies(Set<String>)` | Constrains accepted certificate policies under the PKIX model |
| Custom checkers | `addCertPathChecker(PKIXCertPathChecker)` | Adds extension/policy-logic checks |
| Policy enforcement | `setExplicitPolicyRequired(...)`, `setPolicyMappingInhibited(...)`... | Controls policy tree processing |
| Trusted CA list | `getTrustAnchors()` | Enforces configured trust rules, never inferred from candidate pool |

In practice there are also **disabled algorithms**, JDK/provider constraints, certificate extensions, name constraints, basic constraints, and key usages; concrete policy definitions depend on the environment. Do not try to replace the PKIX validator by listing a few if-statements yourself.

**A successful `CertPathValidator.validate` does not mean every TLS rule is complete.** Hostname/SAN verification for HTTPS, server/client usage purpose, application identity, pinning, and state/replay belong to the certificate-consuming layer/JSSE and corresponding policy. That part must be verified separately, not assumed from PKIX API success alone.

## 5. Result and Exception Types: Differences in Contract

| API | Returned on success | Primary failures |
| --- | --- | --- |
| `CertPathBuilder.getInstance("PKIX")` | A builder engine | `NoSuchAlgorithmException` |
| `CertPathBuilder.build(PKIXBuilderParameters)` | `CertPathBuilderResult`, typically `PKIXCertPathBuilderResult` | `CertPathBuilderException`; bad configuration can cause parameter errors |
| `CertPathValidator.getInstance("PKIX")` | A validator engine | `NoSuchAlgorithmException` |
| `CertPathValidator.validate(certPath, PKIXParameters)` | `CertPathValidatorResult`, typically `PKIXCertPathValidatorResult` | `CertPathValidatorException`, `InvalidAlgorithmParameterException` |
| `CertificateFactory.generateCertPath(List)` | A `CertPath` object from the certificate list | `CertificateException` if input violates the contract |
| `CertStore.getCertificates(selector)` | A collection of candidates | `CertStoreException` when the lookup source fails |
| `PKIXBuilderParameters(trustAnchors, target)` | Parameters suitable for the builder | `InvalidAlgorithmParameterException` if trust anchors are missing/invalid per constructor |

**`CertPathBuilderException` does not strictly mean “intermediate not found”.** It can be caused by no valid path to an anchor, candidate source failure, certificate constraints, signature, validity dates, disabled algorithms, or revocation. Conversely, **`CertPathValidatorException` does not automatically mean a signature error**; inspect `getReason()`, `getIndex()`, `getCause()`, policy details, and appropriate logging.

With `CertPathValidatorException.getIndex()`, the index points to the failing certificate **if the provider has that information**; it can be **`-1`** when undetermined. Never interpret index -1 as “the root certificate failed” or “the whole chain is safe”.

## 6. Runnable Lab: root CA → intermediate CA → leaf

We create **three real X.509 certificates in a temporary test environment** so the builder and validator operate on genuine signatures/extensions rather than “pseudo certificates”. `keytool` ships with the JDK and requires no real CA service or Internet access.

**Run only in an empty lab directory** containing no real keystores. The `changeit` password and `service.example.test` name are strictly for experimentation; keytool creates private keys inside `.p12` files, so never place these files into Git, build artifacts, or production environments. Commands below are one line per operation and can be entered sequentially in a shell, including PowerShell with `keytool.exe`.

### 6.1 Create a Self-Signed Root CA for the Lab

```bash
keytool -genkeypair -alias root -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 3650 -dname "CN=Example Root CA,O=Lab,C=VN" -ext "BC:critical=ca:true,pathlen:1" -ext "KU:critical=keyCertSign,cRLSign" -keystore root.p12 -storetype PKCS12 -storepass changeit -keypass changeit -noprompt

keytool -exportcert -alias root -rfc -file root.pem -keystore root.p12 -storetype PKCS12 -storepass changeit
```

- The Root CA uses an RSA-2048 keypair for the **lab**; `BasicConstraints CA=true` and `keyCertSign` describe its CA role.
- `root.pem` holds the **public certificate**, while `root.p12` holds the root's private key. **Only `root.pem`** will be used by the Java application as a trust anchor.
- In production, never self-issue a root and accept it as a matter of course: manage trust distribution, fingerprints, private key protection, and lifecycle under CA policy.

### 6.2 Generate an Intermediate CA and Have the Root Sign It

```bash
keytool -genkeypair -alias intermediate -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 800 -dname "CN=Example Issuing CA,O=Lab,C=VN" -ext "BC:critical=ca:true,pathlen:0" -ext "KU:critical=keyCertSign,cRLSign" -keystore intermediate.p12 -storetype PKCS12 -storepass changeit -keypass changeit -noprompt

keytool -certreq -alias intermediate -file intermediate.csr -keystore intermediate.p12 -storetype PKCS12 -storepass changeit

keytool -gencert -alias root -infile intermediate.csr -outfile intermediate.pem -rfc -validity 730 -ext "BC:critical=ca:true,pathlen:0" -ext "KU:critical=keyCertSign,cRLSign" -keystore root.p12 -storetype PKCS12 -storepass changeit

keytool -importcert -alias root -file root.pem -keystore intermediate.p12 -storetype PKCS12 -storepass changeit -noprompt

keytool -importcert -alias intermediate -file intermediate.pem -keystore intermediate.p12 -storetype PKCS12 -storepass changeit -noprompt
```

These commands create a **CSR**, use the **private root CA** to sign the intermediate, and then import the root and issued certificate into the intermediate's identity keystore. `intermediate.pem` is the candidate certificate the builder will need. `pathlen:0` on the intermediate restricts subordinate CAs underneath (aside from self-issued cases per standard); it is still permitted to issue leaf end-entity certificates.

**Distinction:** running `keytool -importcert` into `intermediate.p12` to complete the intermediate's identity certificate chain **does not** mean the receiving application should set the intermediate as a trust anchor. In the Java lab we put only **root** in `Set<TrustAnchor>`.

### 6.3 Generate a Leaf Certificate Signed by the Intermediate

```bash
keytool -genkeypair -alias leaf -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 300 -dname "CN=service.example.test,O=Lab,C=VN" -ext "SAN=dns:service.example.test" -keystore leaf.p12 -storetype PKCS12 -storepass changeit -keypass changeit -noprompt

keytool -certreq -alias leaf -file leaf.csr -keystore leaf.p12 -storetype PKCS12 -storepass changeit

keytool -gencert -alias intermediate -infile leaf.csr -outfile leaf.pem -rfc -validity 200 -ext "BC=ca:false" -ext "KU:critical=digitalSignature,keyEncipherment" -ext "EKU=serverAuth" -ext "SAN=dns:service.example.test" -keystore intermediate.p12 -storetype PKCS12 -storepass changeit
```

The leaf has `CA=false`, `serverAuth`, and the lab domain's SAN. `leaf.pem` is the certificate to be verified. To test the `CertPathBuilder` API, the Java application only needs the **three PEM certificate files**; the program does not need access to the private keys in the `.p12` files just created.

**Before real use:** self-issued/self-signed certificates and demo passwords must never be used as production trust configuration. If you lose the lab files, you can regenerate and rerun them. Never copy this root certificate into the shared JDK `cacerts` or a production truststore.

## 7. Java 17+: Build, Validate, and Demonstrate Two Failure Modes

Save the following complete program as **`CertPathBuilderValidatorDemo.java`** in the **same directory** containing `root.pem`, `intermediate.pem`, and `leaf.pem`.

```java
import java.io.*;
import java.nio.file.*;
import java.security.*;
import java.security.cert.*;
import java.time.*;
import java.util.*;

public final class CertPathBuilderValidatorDemo {
    static X509Certificate cert(String path) throws Exception {
        CertificateFactory cf = CertificateFactory.getInstance("X.509");
        try (InputStream in = Files.newInputStream(Path.of(path))) {
            return (X509Certificate) cf.generateCertificate(in);
        }
    }

    public static void main(String[] args) throws Exception {
        X509Certificate root = cert("root.pem");
        X509Certificate intermediate = cert("intermediate.pem");
        X509Certificate leaf = cert("leaf.pem");

        // Trust anchor: explicit decision to trust the lab's root CA.
        Set<TrustAnchor> anchors =
                Set.of(new TrustAnchor(root, null));

        // Specify the target certificate for which to build a path.
        X509CertSelector target = new X509CertSelector();
        target.setCertificate(leaf);

        // Intermediate is only a candidate, not a trust anchor.
        CertStore repository = CertStore.getInstance(
                "Collection",
                new CollectionCertStoreParameters(
                        List.of(leaf, intermediate)));

        PKIXBuilderParameters bp =
                new PKIXBuilderParameters(anchors, target);
        bp.setRevocationEnabled(false); // Lab only, no CRL/OCSP.
        bp.addCertStore(repository);

        CertPathBuilder builder =
                CertPathBuilder.getInstance("PKIX");
        PKIXCertPathBuilderResult built =
                (PKIXCertPathBuilderResult) builder.build(bp);

        System.out.println("Builder path certificates: "
                + built.getCertPath().getCertificates().size());
        System.out.println("Builder trusted root: "
                + built.getTrustAnchor()
                        .getTrustedCert()
                        .getSubjectX500Principal()
                        .getName()
                        .contains("Example Root CA"));

        // Re-verify the same built path, illustrating the separate API.
        PKIXParameters vp = new PKIXParameters(anchors);
        vp.setRevocationEnabled(false); // Lab only.
        CertPathValidator validator =
                CertPathValidator.getInstance("PKIX");
        PKIXCertPathValidatorResult validated =
                (PKIXCertPathValidatorResult)
                        validator.validate(
                                built.getCertPath(), vp);

        System.out.println("Validator public key matches leaf: "
                + validated.getPublicKey()
                        .equals(leaf.getPublicKey()));

        // Builder sees only leaf; no intermediate in the store.
        PKIXBuilderParameters missing =
                new PKIXBuilderParameters(anchors, target);
        missing.setRevocationEnabled(false);
        missing.addCertStore(CertStore.getInstance(
                "Collection",
                new CollectionCertStoreParameters(
                        List.of(leaf))));
        boolean cannotBuild = false;
        try {
            builder.build(missing);
        } catch (CertPathBuilderException expected) {
            cannotBuild = true;
        }
        System.out.println("Build without intermediate fails: "
                + cannotBuild);

        // Validator receives complete path but checks at a date
        // far in the future, past leaf/intermediate expiration.
        PKIXParameters future = new PKIXParameters(anchors);
        future.setRevocationEnabled(false);
        future.setDate(Date.from(
                Instant.now().plus(
                        4000, java.time.temporal.ChronoUnit.DAYS)));

        boolean expired = false;
        try {
            validator.validate(built.getCertPath(), future);
        } catch (CertPathValidatorException expected) {
            expired = true;
        }
        System.out.println("Validate at future date fails: "
                + expired);
    }
}
```

Compile and run:

```bash
javac -encoding UTF-8 CertPathBuilderValidatorDemo.java
java CertPathBuilderValidatorDemo
```

Verified stdout on a JDK with a compatible PKIX algorithm, after creating the files from the **three keytool steps** above:

```text
Builder path certificates: 2
Builder trusted root: true
Validator public key matches leaf: true
Build without intermediate fails: true
Validate at future date fails: true
```

### 7.1 Explaining the Results

**Line 1 — Builder path certificates = 2**

The path contains **leaf, intermediate**, without the root. `PKIXCertPathBuilderResult.getTrustAnchor()` provides the selected root **separately**. If you count the path list and see the root is absent, that **is not a bug**.

**Line 2 — Builder trusted root = true**

The builder linked a path to a trust anchor we supplied in `anchors`. `contains("Example Root CA")` is just an **illustrative boolean print** based on the fixed name of the lab certificate; in production never decide trust by checking a substring in a DN.

**Line 3 — Validator public key matches leaf = true**

`CertPathValidator` checks the **same path** under the lab's `PKIXParameters` and returns a `PKIXCertPathValidatorResult` with the target's public key. Calling the validator again here is to learn the API difference; the builder **already validated the path** when `build` returned successfully.

**Line 4 — Build without intermediate fails = true**

When `CertStore` contains only the leaf, with no intermediate and no other configured source in the lab, the builder **cannot find** a path to the root. This is an error of **missing candidate certificate to build the path**. It does not mean the root is missing from the trust anchors set; the root is still present.

**Line 5 — Validate at future date fails = true**

The newly built path is valid **now**, but at a point 4,000 days ahead as in the example, it exceeds the leaf/intermediate validity period; `CertPathValidator` rejects that path. The exact same certificate list can yield different results if the **validation date, trust anchors, or policy** changes.

### 7.2 What the Lab Intentionally Does Not Check

- **Revocation:** the lab certificates have no CRL/OCSP service; `setRevocationEnabled(false)` is only for running offline. Production needs a real policy for revocation checking.
- **TLS Hostname/SAN:** `CertPathValidator.validate` does not automatically know which URL the application is calling. Even though the leaf has `SAN=dns:service.example.test`, the Java snippet **does not compare it against a requested endpoint**.
- **External trust level:** the program **explicitly** chooses the lab root as an anchor. It does not prove a production CA certificate is organizationally approved.
- **Full TLS algorithms/cipher suites:** a certificate with a valid PKIX path does not guarantee the TLS handshake protocol, host, ciphers, certificate usage, and identity policy are all sound.
- **Alternative paths:** the lab has exactly one intermediate. Production may have cross-signing/multiple CAs, requiring the builder to search/evaluate multiple options.
- **Business-specific key usage:** `serverAuth` and `digitalSignature` are present in the lab certificate, yet the application still needs to enforce proper certificate usage per protocol/JSSE.

## 8. The Builder Can Solve Problems the Validator Cannot Solve on Its Own

A real system may receive only the **leaf certificate** from a peer; the intermediate might reside in the application's store, in the accompanying certificate chain, or in a properly configured lookup source.

```text
Available data:
  leaf
  candidates = {intermediate A, intermediate B, cross-signed CA C, ...}
  anchors = {root X, root Y}

Builder:
  picks target leaf
  searches issuer candidates
  checks signatures/validity/constraints per config
  chains candidates that can lead to X or Y
  returns a validated CertPath + TrustAnchor

Validator:
  takes existing CertPath [leaf, intermediate A]
  checks THAT EXACT path under trust anchors/policy
  does not swap intermediate A for B if A fails
```

**Cross-signing case:** the same CA subject/public key can appear under multiple certificates signed by different issuers. There may be multiple paths to different roots; the builder can find a path given the provider's candidates and policy. If you already received a specific certificate path, the validator does not automatically “detour” through another cross-signed certificate. **Do not rely solely on subject DN** to treat two certificates as equivalent; signatures, keys, extensions, issuance, and policy all matter.

### 8.1 When Is Path Building Necessary?

- The application has the leaf certificate but **did not receive the complete intermediate chain** and has a trustworthy candidate source to search.
- A certificate may be issued through **multiple chains** to multiple roots, requiring discovery of a path matching trust policy.
- An internal PKI system stores certificates/CRLs in a directory/collection and needs to build paths from end-entities to roots.
- A document/signature verification tool must find the issuer path for a signer's certificate.

Even so, **the builder does not guarantee that intermediate download sources are always available or safe**. If using AIA or LDAP/network, constrain endpoints, timeouts, data count/size limits, handle SSRF and caching, and never treat fetched content as trusted merely because it was auto-downloaded. Depending on the JDK/provider, automatic AIA fetching may require specific options or be unsupported; **do not assume every build will auto-fetch from the Internet**.

### 8.2 When Is Only the Validator Needed?

- The application already has an appropriately ordered chain from a defined source and wants to evaluate it against a set of `PKIXParameters`.
- An application wants to **revalidate** a path at a **different date** (e.g., signing time and timestamping evidence under appropriate policy) or a different set of trust anchors.
- Testing a fixed path with an expired certificate, an unqualified CA, an unsatisfied policy, or a bad signature.
- Administrative/diagnostic tools needing to pinpoint the exact failure of a **given path**.

If an intermediate is missing, do not “fix” it by adding the root to `CertPath`. Supply the proper candidate to the builder or add the **actual intermediate** to the path from a verified source; the trust anchor stays independent.

## 9. What Does PKIX Path Checking Do?

PKIX validation is not merely `cert.verify(issuer.getPublicKey())` for each pair. An accepted path must satisfy checks covering **signatures and issuer linking**, **time validity**, **CA basic constraints**, **key usage**, **name constraints**, **certificate policies**, **algorithms/key sizes**, and other requirements per standards, APIs, and provider/policy.

A mental model:

```text
CertPath [leaf, intermediate, ...] + TrustAnchor root
                   |
            1. Chain order/issuer
                   |
            2. Verify signatures
                   |
            3. Check dates (validationDate)
                   |
            4. Check BasicConstraints + keyCertSign
                   |
            5. Process name constraints / policy constraints
                   |
            6. Algorithm policy / critical extensions
                   |
            7. Revocation checking per configuration
                   |
                PASS / FAIL
```

The actual PKIX algorithm order is more complex than the diagram (see RFC 5280, Section 6); **do not use this diagram as an implementation spec** to write your own validator. A provider may enforce additional policies such as `jdk.certpath.disabledAlgorithms` on supporting JDKs.

### 9.1 Do Not Confuse Trust Anchors with Candidate Certificates

| Property | TrustAnchor | CertStore candidate |
| --- | --- | --- |
| Approved by whom? | **Operator/application** per trust policy | May come from network/file/peer, untrusted by default |
| Used for what? | Serves as the **trusted starting point** when evaluating a chain | Source of certificates/CRLs to help find/check a chain |
| Added to which API? | `PKIXParameters`/`PKIXBuilderParameters` | `PKIXParameters.addCertStore` and builder parameters |
| Does adding an item widen trust? | **Potentially**, if adding an out-of-policy anchor | **Not directly**; candidates must still validate to an anchor |
| Impact if tampered with | Can allow a rogue CA to sign accepted forged certificates | Can cause DoS, wrong selection, or alternate path attempts; proper validation still requires trust anchors |

### 9.2 Path Building Is Not Hostname Verification

A chain with valid signatures from an approved root can terminate at a certificate for `service-a.example.test` while the client is connecting to `service-b.example.test`. **The PKIX builder/validator alone is not enough to verify the hostname identity of an HTTPS request**.

When doing TLS, use an HTTP client/JSSE configured with **endpoint identification** via the proper API and policy, checking SAN, EKU/usage, and endpoint name per protocol. Never write a custom trust manager that only calls `CertPathValidator.validate` and claim HTTPS is fully verified.

## 10. Revocation: Must Be Designed Intentionally, Never Left False in Production

In the lab, we called:

```java
params.setRevocationEnabled(false);
```

This **disables revocation checking** in parameters, which is necessary for an offline demo without CRL/OCSP. In a real product:

- Choose CRL, OCSP, or the corresponding checker based on certificate type/protocol/policy.
- Define data freshness, timing, caching, timeouts, and handling when revocation sources are unavailable.
- Check `PKIXRevocationChecker`/provider support if customization is needed.
- Ensure CRL/OCSP sources are authenticated (CRL has valid signature and matching issuer; OCSP response conforms to policy).
- Distinguish **no response** from **certificate not revoked**; never conflate the two when policy demands fail-closed behavior.
- Test revoked certificates, certificates lacking revocation info, expired CRLs, and network timeouts on a real JDK/provider.

**Adding a `CertStore` with CRLs does not automatically guarantee revocation is checked** if policy does not enable/configure it accordingly. Conversely, enabling revocation without providing working data/sources can cause paths to be rejected because status cannot be determined.

## 11. Common Errors and How to Read Them Correctly

| Symptom | Where it occurs | Primary diagnosis |
| --- | --- | --- |
| `CertPathBuilderException: unable to find valid certification path to requested target` | `builder.build` | No path satisfies the **current anchors, candidates, and policy**; check intermediate, truststore, algorithms, constraints, date, revocation |
| `CertPathValidatorException: validity check failed` | `validator.validate` | A certificate in the path is outside its validity period at `validationDate`; inspect index/reason |
| `CertPathValidatorException: Path does not chain with any of the trust anchors` | `validator.validate` | Supplied path cannot link to an anchor; check root/chain/order |
| `CertPathValidatorException: signature check failed` | `validator.validate` | Invalid issuer signature, wrong key, altered path, or mismatched chain |
| `CertPathValidatorException` with `INVALID_KEY_USAGE`/constraints | `validator.validate` | Intermediate lacks `keyCertSign`, is not a CA, or violates constraints or policy |
| `InvalidAlgorithmParameterException` | Parameter constructor or validate | No valid trust anchor, invalid parameters, or rejected by provider |
| `CertificateException` | `CertificateFactory.generateCertificate`/`generateCertPath` | Corrupted or improperly formatted certificate/encoding input |
| `NoSuchAlgorithmException` | `getInstance("PKIX")` | JDK/provider lacks the `PKIX` engine |
| `CertStoreException` | `CertStore` fetching certificates/CRLs | Corrupted candidate source, network/LDAP error, incompatible selector/backend |
| `SSLHandshakeException` with PKIX error | TLS/JSSE | May stem from the underlying builder/validator; inspect the actual effective truststore **and** hostname/chain/policy |

**Do not conclude “missing root” from every builder error.** In the lab, the root was still configured, yet a missing **intermediate** also caused the builder to fail. Conversely, having all intermediates while the root is untrusted still fails to approve the path.

When handling `CertPathValidatorException` in an application:

```java
// Illustrative snippet, not a full class.
// ex is a caught CertPathValidatorException.
int index = ex.getIndex(); // May be -1.
CertPathValidatorException.Reason reason = ex.getReason();
// Log reason/index on a protected internal channel, avoiding sensitive data leaks.
```

You can enable temporary debugging in a controlled environment, such as `-Djava.security.debug=certpath` on a supporting JDK/implementation. Path-building logs can expose hostnames, subjects/issuers, truststores, and internal details; do not leave them enabled long-term in production or return them in public API responses.

## 12. Major Misconceptions to Eliminate

1. **“Builder only finds the chain; validator actually verifies it.”** False: under PKIX, the builder **returns an already-validated path**, not an arbitrarily assembled list.
2. **“Validator will automatically find intermediates if the path lacks them.”** False: the validator checks the **supplied path**; it does not perform path discovery.
3. **“A result path with only 2 certificates means the root is missing.”** No: the PKIX builder **excludes the trust anchor from `CertPath`**; the anchor is retrieved separately from the result.
4. **“CertStore = truststore.”** No: `CertStore` holds **candidates**; trust anchors are an independent decision.
5. **“Adding an intermediate to the truststore fixes every PKIX error.”** Very dangerous: it can unintentionally broaden the set of trusted CAs; supply intermediates properly as candidates.
6. **“The issuer's subject DN just needs to match the previous cert's issuer DN.”** No: signatures, keys, constraints, validity dates, policy, and the full chain must be checked.
7. **“A trust anchor must always be a self-signed root.”** Not at the API level: a trust anchor is a trust decision and can point to another CA per policy; however, the trust scope must be understood and controlled.
8. **“Builder returning success means the hostname is right.”** No: PKIX path validation does not automatically know which hostname the client intends to connect to.
9. **“Toggling revocation doesn't matter.”** False: it is a critical part of the threat model; offline demo disablement must not be copied into production.
10. **“Setting `maxPathLength=1` means the whole path has just one cert.”** No: this parameter limits **intermediates**; the leaf and trust anchor have separate roles.
11. **“A path built successfully today will stay valid forever.”** No: time, revocation, trust policy, and disabled algorithms can change.
12. **“Any certificate from the network can be trusted.”** No: candidates have no authority; they must chain to a **pre-verified trust anchor**.
13. **“Having the right root CA is enough to stop all MITM attacks.”** No: endpoint identity (SAN/hostname), EKU/purpose, and TLS protocol protections are required.
14. **“A single `CertPathValidator.validate` call is the entire TLS handshake.”** No: TLS also includes key agreement, proof of possession, protocol negotiation, record protection, replay policies, and JSSE configuration.

## 13. Practice Scenarios

**Scenario A.** The client has the server's leaf and a truststore containing the root; the peer did not send the intermediate, but the application has `intermediate.pem` in a `CertStore`. What should be used?  
**Answer:** Use **`CertPathBuilder`** when you need to find a path from the leaf to a trust anchor through candidates; the builder can locate the intermediate and validate the chain. Do not add the intermediate as a trust anchor just to bypass the error.

**Scenario B.** The application already has the path `[leaf, intermediate]` and wants to verify whether it was valid at a specific point in time.  
**Answer:** Use **`CertPathValidator`** with `PKIXParameters` containing trust anchors and `setDate(...)` per policy; it checks the **given path**.

**Scenario C.** The builder returns `getCertPath().getCertificates().size() == 2` in a root/intermediate/leaf setup. Is the root missing?  
**Answer:** No. **The root is the trust anchor**, obtained from `getTrustAnchor()`, and is not in the path list.

**Scenario D.** A certificate chain has a leaf for `internal-a.example.test`, while the app connects to `internal-b.example.test`. Is PKIX builder/validator success safe enough for HTTPS?  
**Answer:** **No.** You must check hostname/endpoint identity and certificate purpose in the TLS client.

**Scenario E.** An intermediate present in `CertStore` has a valid signature but leads to an untrusted root. Will it be accepted?  
**Answer:** Not merely because the intermediate is in `CertStore`. There must be a path to an **approved trust anchor** with all constraints satisfied.

**Scenario F.** The builder with `setMaxPathLength(0)` fails because one intermediate is needed. Can it be increased to `1`?  
**Answer:** Yes, if trust policy approves one intermediate and CA constraints allow it; a security review is required. Never automatically allow unlimited depth just because of an error.

**Scenario G.** Both the chain and anchor are present, yet the validator reports `EXPIRED` at the current time. Should you call the builder to “find another chain” and ignore expiry?  
**Answer:** Validity requirements must not be bypassed. The builder must also respect the validation date; only if another genuinely valid path exists and policy allows it does that make sense.

**Scenario H.** `CertStore` contains many CRLs, yet `setRevocationEnabled(false)` is set. Are revoked certificates guaranteed to be rejected?  
**Answer:** No. Adding CRL candidates does not automatically enable revocation. Production must configure the right revocation checker/policy and test it.

**Scenario I.** An attacker's self-signed certificate gets added to the truststore by an automated import script. Can the builder return success for a leaf issued by the attacker?  
**Answer:** Potentially yes if the anchor was improperly added and the remaining parameters pass; a poorly managed truststore **alters the trust boundary**. Never import unverified certificates.

**Scenario J.** `PKIXCertPathBuilderResult` already returns a validated path. Why does the example still call `CertPathValidator`?  
**Answer:** To study both APIs and illustrate **revalidation** when changing the date/policy. Not because the builder “built without checking”.

## 14. Checklist When Designing PKIX in Java

- **Identify the exact task needed:** need to **find** a path from a target → builder; already have a path to **verify** → validator.
- **Select trust anchors from verified sources:** avoid indiscriminate certificate imports; never conflate candidates with trust.
- **Set precise target constraints:** appropriate `X509CertSelector`, identifying the certificate or required key/subject/usage.
- **Provide controlled candidate stores:** leaf, intermediates, and CRLs; bound network connections and oversized inputs.
- **Understand `CertPath` ordering:** Java PKIX paths typically go from leaf to intermediate, **without the trust anchor**.
- **Use the right parameter class:** `PKIXBuilderParameters` for `build`, `PKIXParameters` for `validate`; set appropriate date, revocation, policy, and algorithm constraints.
- **Do not disable revocation for convenience:** separate offline demos from production, with a CRL/OCSP/failure-handling strategy.
- **Do not treat PKIX as a hostname check:** TLS clients must enforce endpoint identification/SAN and certificate purpose/usage checks.
- **Report errors from the right API:** builder failures differ from validator failures; log reason/index/cause safely when possible.
- **Test diverse path cases:** missing intermediate, wrong anchor, expired, invalid signature, constrained CA, cross-signing, revocation, and hostname mismatch.
- **Stay grounded in real providers/runtimes:** `PKIX` is standard on the JDK, but certpath policies, AIA behavior, disabledAlgorithms, and revocation support can vary.
- **Do not hand-roll an X.509 validator:** RFC 5280 is complex; use JCA/JSSE and maintained libraries/protocols.
