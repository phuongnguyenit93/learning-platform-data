# 6.11 Limitations of `CipherInputStream` When AEAD Authentication Failures Must Be Detected

## Learning Objectives

After this lesson, you will be able to:

1. Explain what AEAD authenticates and why the authentication tag must be verified before using plaintext.
2. State the exact Java SE 17 warning for **`javax.crypto.CipherInputStream`** when decrypting with an AEAD mode such as AES-GCM: some authentication exceptions may be caught and **not propagated** to calling code.
3. Distinguish **reading an entire InputStream without an IOException** from **successfully authenticating the ciphertext**.
4. Use **`javax.crypto.Cipher.doFinal()`** directly to receive **`AEADBadTagException`**, handling tampered ciphertext, wrong AAD, wrong key, or truncated ciphertext.
5. Design a decryption workflow that keeps plaintext **untrusted** until authentication succeeds, even for large data; avoid consuming partial output, mishandling errors, or accepting data missing a valid tag.

**Key takeaway:** When an application must detect authentication failures, never treat reading cleanly from **`CipherInputStream`** as proof. Java 17 documentation warns that this class can swallow integrity-check exceptions during GCM decryption. The **direct Cipher API**, especially **`doFinal()`**, surfaces authentication results clearly.

## 1. How Does AEAD Protect Data?

**AEAD (Authenticated Encryption with Associated Data)** is authenticated encryption. With AES-GCM, beyond plaintext secrecy, the system verifies key-based integrity and authenticity of both the ciphertext and **AAD**.

Components to understand:

- **Key:** secret AES key, properly protected and access-controlled.
- **Nonce/IV:** per-encryption value, typically 12 bytes for GCM; **must never repeat under the same key**. The nonce can be stored alongside ciphertext, yet must match the original bytes exactly.
- **Plaintext:** data prior to encryption.
- **Ciphertext:** data after encryption.
- **Authentication tag:** MAC-like tag generated by GCM; typically 16 bytes (128 bits), computed over key, nonce, data, and AAD.
- **AAD (Additional Authenticated Data):** context that need not stay secret yet must be integrity-checked, such as tenant ID, record type, version, or resource identifier.

Diagram:

~~~text
ENCRYPTION:
plaintext + key + nonce + AAD
               |
        AES-GCM encrypt
               |
         ciphertext || tag
               |
      store/transmit with nonce

DECRYPTION:
ciphertext || tag + key + nonce + AAD
                   |
            AES-GCM decrypt
                   |
               Verify tag
                 /     \
               Valid  Invalid
                |       |
          plaintext   Reject
~~~

In Java JCA, **`Cipher.getInstance("AES/GCM/NoPadding")`** returns a `Cipher` usable for encryption or decryption. On encryption, **`Cipher.doFinal(plaintext)`** produces ciphertext with the tag appended per JCA/provider output format. On decryption, **`Cipher.doFinal(ciphertextWithTag)`** verifies the tag. On mismatch, the method may throw **`AEADBadTagException`**.

A record with a bad tag may result from tampered ciphertext, wrong key, wrong nonce, wrong AAD, missing/truncated bytes, or storage/transit corruption. **A bad tag means authentication failed; it does not prove the cause or who caused the fault.**

### 1.1 Why Verify the Tag Before Using Plaintext?

Suppose a service reads an AES-GCM encrypted account record from storage. An attacker modifies the ciphertext on disk without knowing the key. Proper service behavior:

1. Decrypt and authenticate with the matching key/nonce/AAD.
2. If the tag fails, do not return the profile or an empty record marked valid.
3. Never write unauthenticated plaintext into caches, DBs, responses, or downstream systems.
4. Detect the error, handle it per policy, and log safely without leaking keys/plaintext.

Using data before authentication completes defeats AEAD's integrity protection.

## 2. How Does `CipherInputStream` Work?

**`javax.crypto.CipherInputStream`** wraps an underlying **`InputStream`** and an initialized **`Cipher`**. Each time the caller invokes `read()`, the wrapper reads source bytes and feeds them through `Cipher` before returning data to the caller.

~~~text
encrypted.bin
     |
  InputStream
     |
CipherInputStream
  [Cipher]
     |
read()/readAllBytes()
     |
output byte[]
~~~

This API is convenient for processing byte streams through the `InputStream` interface. However, because it bridges two different abstraction layers, **its exception contract differs from using the Cipher API directly**.

### 2.1 Official Warning in Java SE 17

The Java 17 Javadoc for **`CipherInputStream`** states that the class adheres to the semantics—specifically the **failure semantics**—of **`FilterInputStream`** and **`InputStream`**. It catches exceptions outside those declared by the superclass interface. Specifically:

- It **may catch `BadPaddingException` and other exceptions** thrown when integrity checks fail during decryption.
- Those exceptions **are not rethrown**, so calling code **may remain unaware** that the integrity check failed.
- Therefore, `CipherInputStream` **may be unsuitable for decrypting authenticated encryption modes such as GCM**.
- Applications requiring authenticated encryption may use the **Cipher API directly** instead.

Technical sources:

- [Oracle Java SE 17 — CipherInputStream](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/crypto/CipherInputStream.html)
- [Oracle Java SE 17 — Cipher](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/crypto/Cipher.html)
- [Oracle Java SE 17 — AEADBadTagException](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/crypto/AEADBadTagException.html)

**Precision in interpretation:** the documentation says it **may** ignore authentication failures, not that every JVM/provider behaves identically. Observing one provider or one test catch the error **does not provide a portable guarantee across all environments**.

### 2.2 Why Can the Cryptographic Exception Disappear?

In the `Cipher` model:

~~~text
Cipher.doFinal(ciphertextAndTag)
          |
     Verify tag
       /     \
     OK       FAILED
      |          |
  plaintext   AEADBadTagException
~~~

In the `CipherInputStream` model:

~~~text
Stream.read()
    |
Cipher (may invoke doFinal at end of input)
    |
Tag verification fails
    |
BadPaddingException / AEADBadTagException
    |
CipherInputStream may catch and not propagate
    |
Stream reader may receive no signal of bad tag
~~~

**`AEADBadTagException`** is a subclass of **`BadPaddingException`**, which belongs to **`GeneralSecurityException`**. **`InputStream.read()`** primarily follows the **`IOException`** contract. Wrapping `Cipher` in an `InputStream` does not automatically translate every cryptographic error into a propagated `IOException`.

Never conclude "CipherInputStream protects the data because it uses a valid Cipher internally." The algorithm may detect a bad tag, yet **outside callers may never observe the failure**.

## 3. Anti-Pattern Example: Reading to EOF Does Not Mean Authentication Succeeded

The Java snippet below illustrates a misleading pattern; the `Cipher`/`InputStream` variables are initialized externally, so this is **not a standalone program**.

~~~java
// decryptCipher is an AES-GCM Cipher initialized in DECRYPT_MODE.
// encryptedInput had its nonce handled during init,
// and this stream contains ciphertext || authentication tag.
try (CipherInputStream stream =
         new CipherInputStream(encryptedInput, decryptCipher)) {

    byte[] received = stream.readAllBytes();

    // Never assume the tag is valid just because readAllBytes() did not throw.
    // Never use received as authenticated plaintext.
}
~~~

The flaw lies in the developer's implicit assumption:

~~~text
"readAllBytes did not throw IOException"
                  |
                  v
"The tag must have been verified successfully"   <- WRONG INFERENCE
                  |
                  v
"Safe to pass data into business logic"
~~~

When the tag is invalid, depending on the provider, you might see an exception, truncated/empty output, or other behavior; never rely on one observed test result as an API guarantee.

### 3.1 `readAllBytes()`, `close()`, and `catch (IOException)` Do Not Fix the Problem

| Approach | What It Actually Does | What Is Not Guaranteed |
| --- | --- | --- |
| **`readAllBytes()`** | Attempts to read all bytes until EOF unless an I/O error occurs | Does not force the wrapper to rethrow a caught tag exception |
| **`try-with-resources`/`close()`** | Releases resources per lifecycle contract | Does not prove the entire message was authenticated |
| **`catch (IOException)`** | Catches propagated `IOException`s | Does not catch an `AEADBadTagException` swallowed by the wrapper |
| **`available()`** | Reports estimated non-blocking readable bytes per `InputStream` | Not an integrity-check or tag status |
| **`skip()`** | Skips bytes per stream semantics | Does not authenticate in place of Cipher finalization |
| **Checking plaintext is non-empty** | Can check length or basic syntax | Does not verify cryptographic integrity |

Closing a stream cleanly **is not equivalent** to **`doFinal` returning plaintext after verifying the tag**.

### 3.2 Read Errors and Authentication Errors Are Two Distinct Failure Modes

An **`IOException`** may originate from the filesystem, network, or underlying `InputStream`. By contrast, **`AEADBadTagException`** indicates the authentication tag does not match the key, nonce, AAD, and ciphertext passed to `Cipher`.

Applications should distinguish:

- **Format errors** before decryption (version, structure, missing nonce, payload too short).
- **Source read errors** (disk/network).
- **Authentication errors** when calling `Cipher.doFinal`.
- **Business errors** after obtaining authenticated plaintext.

Do not collapse everything into "empty file" or "no data yet". However, when returning errors to untrusted clients, limit sensitive details and avoid creating an oracle revealing cryptographic internals.

## 4. Safe Design for Size-Bounded Payloads

For a record or file sized to fit in memory:

1. **Bound input size** before and while reading.
2. Parse **version, key ID (if any), nonce, and ciphertext/tag**, validating minimum structure.
3. Obtain the key from a proper key manager/KMS with restricted usage permissions.
4. Call **`Cipher.init(DECRYPT_MODE, key, new GCMParameterSpec(tagBits, nonce))`**.
5. Call **`Cipher.updateAAD(aad)`** before feeding ciphertext into `Cipher`.
6. Call **`Cipher.doFinal(ciphertextWithTag)`** directly. The method returns plaintext on success or throws a cryptographic exception on failure.
7. **Only after `doFinal` succeeds**, publish or process plaintext.
8. On failure, reject the record; discard intermediate bytes and never fall back to a weaker mode.

~~~text
Size-bounded ciphertext input
            |
Check header/nonce/version
            |
Cipher.init(DECRYPT_MODE)
Cipher.updateAAD(...)
            |
Cipher.doFinal(ciphertext || tag)
        /                 \
    success           AEADBadTagException
        |                 |
Use plaintext         Reject, do not publish
~~~

Why does this make a critical difference? The caller **directly receives the final Cipher result**, and authentication exceptions do not pass through an `InputStream` layer whose semantics allow swallowing them.

## 5. Complete Java 17+ Example: Detecting Bad Tags with `doFinal`

The program generates an ephemeral AES key for **a single demo run**, encrypts with AES-GCM, and tests decryption across four cases: valid packet, modified tag, wrong AAD, and missing trailing byte.

Illustrative binary format:

~~~text
+------------+----------------+---------------------------+
| version 1B | nonce 12 bytes | ciphertext || tag 16 B   |
+------------+----------------+---------------------------+
~~~

Real applications must add key IDs, nonce policies, storage/transport framing, size limits, and error/rotation handling. This example uses non-sensitive test data and **prints no keys to output**.

Create **`AeadDoFinalDemo.java`** saved as UTF-8:

~~~java
import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.security.GeneralSecurityException;
import java.security.SecureRandom;
import java.util.Arrays;

import javax.crypto.AEADBadTagException;
import javax.crypto.Cipher;
import javax.crypto.KeyGenerator;
import javax.crypto.SecretKey;
import javax.crypto.spec.GCMParameterSpec;

public class AeadDoFinalDemo {
    private static final byte VERSION = 1;
    private static final int NONCE_BYTES = 12;
    private static final int TAG_BITS = 128;
    private static final int TAG_BYTES = TAG_BITS / 8;
    private static final SecureRandom RANDOM = new SecureRandom();

    private static byte[] encrypt(byte[] plaintext,
                                  SecretKey key,
                                  byte[] aad)
            throws GeneralSecurityException {
        byte[] nonce = new byte[NONCE_BYTES];
        RANDOM.nextBytes(nonce);

        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        cipher.init(Cipher.ENCRYPT_MODE, key,
                new GCMParameterSpec(TAG_BITS, nonce));
        cipher.updateAAD(aad);
        byte[] ciphertextWithTag = cipher.doFinal(plaintext);

        return ByteBuffer.allocate(
                    1 + NONCE_BYTES + ciphertextWithTag.length)
                .put(VERSION)
                .put(nonce)
                .put(ciphertextWithTag)
                .array();
    }

    private static byte[] decrypt(byte[] packet,
                                  SecretKey key,
                                  byte[] aad)
            throws GeneralSecurityException {
        if (packet.length < 1 + NONCE_BYTES + TAG_BYTES) {
            throw new IllegalArgumentException("Payload too short");
        }

        ByteBuffer input = ByteBuffer.wrap(packet);
        if (input.get() != VERSION) {
            throw new IllegalArgumentException("Invalid version");
        }

        byte[] nonce = new byte[NONCE_BYTES];
        input.get(nonce);

        byte[] ciphertextWithTag = new byte[input.remaining()];
        input.get(ciphertextWithTag);

        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        cipher.init(Cipher.DECRYPT_MODE, key,
                new GCMParameterSpec(TAG_BITS, nonce));
        cipher.updateAAD(aad);

        // Returns plaintext after tag verification,
        // or throws AEADBadTagException if tag is invalid.
        return cipher.doFinal(ciphertextWithTag);
    }

    private static boolean tagRejected(byte[] packet,
                                       SecretKey key,
                                       byte[] aad)
            throws GeneralSecurityException {
        try {
            decrypt(packet, key, aad);
            return false;
        } catch (AEADBadTagException expected) {
            return true;
        }
    }

    public static void main(String[] args) throws Exception {
        KeyGenerator generator = KeyGenerator.getInstance("AES");
        generator.init(128);
        SecretKey key = generator.generateKey();

        byte[] plaintext = "Test record"
                .getBytes(StandardCharsets.UTF_8);
        byte[] aad = "record:42".getBytes(StandardCharsets.UTF_8);

        byte[] packet = encrypt(plaintext, key, aad);
        byte[] recovered = decrypt(packet, key, aad);

        System.out.println("Valid original: "
                + Arrays.equals(plaintext, recovered));

        byte[] tampered = packet.clone();
        tampered[tampered.length - 1] ^= 1;
        System.out.println("Tampered tag rejected: "
                + tagRejected(tampered, key, aad));

        byte[] wrongAad = "record:43"
                .getBytes(StandardCharsets.UTF_8);
        System.out.println("Wrong AAD rejected: "
                + tagRejected(packet, key, wrongAad));

        byte[] truncated = Arrays.copyOf(
                packet, packet.length - 1);
        System.out.println("Truncated trailing byte rejected: "
                + tagRejected(truncated, key, aad));

        Arrays.fill(plaintext, (byte) 0);
        Arrays.fill(recovered, (byte) 0);
    }
}
~~~

Compile and run with JDK 17+:

~~~bash
javac -encoding UTF-8 AeadDoFinalDemo.java
java AeadDoFinalDemo
~~~

Expected stdout on standard JDK 17 AES-GCM implementations:

~~~text
Valid original: true
Tampered tag rejected: true
Wrong AAD rejected: true
Truncated trailing byte rejected: true
~~~

Interpretation:

- **Valid original: true:** matching key, nonce, and AAD; valid tag; `doFinal` recovers the exact plaintext.
- **Tampered tag rejected: true:** flips one bit in the last byte of the tag; `doFinal` returns no plaintext and throws `AEADBadTagException`.
- **Wrong AAD rejected: true:** keeps ciphertext/tag identical while changing context from `record:42` to `record:43`. The tag mismatches the new AAD.
- **Truncated trailing byte rejected: true:** input still passes the minimum structural length check, yet the tag is missing one byte, causing authentication failure.

Nonce and key are random so ciphertext changes each run; the program prints no ciphertext/tag and prints only verifiable boolean conditions. Specific exception behavior depends on the JCA provider used, though `Cipher.doFinal` has the AEAD exception contract in Java SE 17.

**Note:** the example does not manage keys persistently and is not a production protocol. `Arrays.fill()` clears only `byte[]` arrays controlled by code and does not guarantee erasing all JVM copies.

### 5.1 Distinguishing `AEADBadTagException` from Other Data Errors

**`AEADBadTagException`** extends **`BadPaddingException`** and can be caught separately to distinguish it from structural errors caught before calling `Cipher`. However, an authentication failure does not determine whether the cause was an attack, file corruption, or wrong metadata.

Never use a fallback such as:

~~~text
GCM tag invalid
     |
Retry decryption without verifying tag
     |
Accept "readable" content
~~~

That bypasses AEAD's core integrity property. **Rejecting the entire record** is the safe outcome when the tag is invalid.

## 6. Another Warning: Plaintext from `Cipher.update` Is Also Unauthenticated

Suppose you avoid `CipherInputStream` and write your own loop reading ciphertext in chunks. Calling **`Cipher.update(...)`** can return intermediate `byte[]` chunks; the byte count returned depends on provider and mode.

~~~text
cipher.update(chunk1) -> candidatePlaintext1 (may be empty)
cipher.update(chunk2) -> candidatePlaintext2 (may be empty)
...
cipher.doFinal(lastChunkAndTag) -> final slice OR authentication error
~~~

**Never treat `candidatePlaintext` as "authenticated" before `doFinal` succeeds.** Some providers buffer all plaintext until the end; others emit bytes earlier. Applications must code to the security requirement rather than relying on how a specific provider buffers bytes.

If code already:

- Wrote `candidatePlaintext` to a real database;
- Passed bytes into a sensitive parser or decompressor;
- Streamed data out into an HTTP response;
- Emitted events, unlocked resources, or updated business state;

then a tag error at the end **cannot automatically undo** side effects that already happened.

Rule: **Keep unauthenticated data isolated until the final verification step succeeds.**

## 7. Decrypting Large Files Safely

### 7.1 Simple Approach for Size-Bounded Files

If the payload fits comfortably in RAM:

1. Cap file/request size realistically.
2. Read the full encrypted payload with tag (standard byte reading, not `CipherInputStream` for verification).
3. Call `Cipher.doFinal` directly.
4. Pass plaintext to business logic only if no exception occurred.

**`Files.readAllBytes`/`InputStream.readAllBytes`** can allocate huge amounts of memory; unsuitable for untrusted sources or unbounded files. Check sizes before and while reading, or use bounded reads.

### 7.2 Staging Approach for Large Files

If chunked decryption is needed to save RAM:

1. Parse metadata, check key/version/nonce/AAD policy and data limits.
2. Use **`Cipher.update()`** directly on ciphertext chunks, storing any output returned by the provider in an **isolated staging area**, inaccessible to clients or business logic.
3. Only after reading to the true end of ciphertext **including the tag**, call **`Cipher.doFinal()`**; write any remaining output into staging.
4. If **`doFinal` fails**, discard staging and abort all operations; never publish the record.
5. If **`doFinal` succeeds**, close staging and commit/move to the official destination atomically (e.g., atomic rename if supported by the filesystem, or a suitable transaction).
6. Protect staging with strict permissions, retention limits, and failure cleanup; remember staging may temporarily hold **sensitive unauthenticated plaintext**.

Important limitation: **a GCM tag authenticates the whole record**. If an app needs to stream plaintext chunks to a client **before receiving the trailing tag**, a single GCM ciphertext cannot prove each independent chunk is authentic.

For true online streaming, you must **design an authenticated chunked protocol**: each chunk is its own AEAD record with a unique nonce, AAD binding record number/stream ID, and checks against dropped, duplicated, reordered, or truncated final records. Slicing one GCM ciphertext into pieces pretending each piece has its own tag is **wrong**.

### 7.3 Why Closing the Stream at the End Is Not Enough

`close()` releases resources per `InputStream`/`FilterInputStream` contracts. It does not fix the fact that `CipherInputStream` may have swallowed authentication exceptions from `Cipher`. Therefore:

~~~text
try (CipherInputStream stream = ...) {
    byte[] bytes = stream.readAllBytes();
}
// Exits try normally.
~~~

**Does not mean:**

~~~text
Cipher.doFinal() verified the tag successfully
and returned valid plaintext for the exact message.
~~~

Any workflow relying on "read to EOF + close stream without error" to assert GCM integrity must be revisited.

## 8. Proper Checklist for AES-GCM

Changing APIs only fixes **authentication error detection**; it does not fix broken cryptographic design.

| Requirement | Why It Is Needed |
| --- | --- |
| Unique nonce under the same key | Reusing AES-GCM nonces can break both confidentiality and integrity |
| Separately managed keys with proper permissions | Anyone holding the key can forge valid ciphertexts/tags |
| Same AAD order and bytes on both sides | Mismatched AAD must cause tag verification to fail |
| Fixed/allowlisted format version and algorithm | Prevents attackers from forcing weak modes or alternate parsing |
| Full ciphertext and tag before `doFinal` | Missing tag cannot be verified |
| Input and output size bounds | Prevents RAM, disk, and CPU exhaustion on untrusted input |
| No output consumption before final success | Ensures unauthenticated plaintext is never acted upon |
| Discard staging on authentication failure | Prevents forged artifacts from being served as valid data |
| No logging keys, plaintext, or sensitive payloads | Prevents leakage through operational observability |
| Anti-replay if business logic needs it | Valid AEAD tag does not stop replaying old packets |
| Tests for bad tag, bad AAD, and truncation | Proves error paths actually reject invalid data |

### 8.1 Notes on Nonce and Key Rotation

AES-GCM requires never repeating nonces under the same key. Many examples generate random 12-byte nonces, yet high-volume systems must design traffic caps, nonce management, and key rotation to keep collision risk negligible. Nonces are not secret and can be stored alongside ciphertext. Keys must be protected by KMS/secret managers or equivalent mechanisms.

Never hardcode keys in Java source, or write keys to headers, logs, or URLs. When rotating keys, older records may need a key ID to select the old decryption key. Never disable authentication just because an old record fails after rotation.

### 8.2 AAD and Record Context

AAD can include tenant ID, record ID, version, or business context that must stay bound to the ciphertext. It is not encrypted confidentially, yet participates in authentication. The decryptor must supply exact AAD bytes before feeding ciphertext into `Cipher`.

If an application deserializes an object to JSON and re-serializes it, field order, whitespace, or Unicode normalization may alter the bytes. Define a canonical format and explicitly protected metadata to avoid "logically identical data" failing tag checks due to byte differences.

### 8.3 Rejecting Data with a Bad Tag Does Not Identify the Culprit

GCM does not distinguish among:

- an attacker actively altering ciphertext;
- a truncated backup copy;
- a storage bug dropping bytes;
- pulling the wrong key from a keystore;
- supplying the wrong nonce;
- mismatched AAD context.

In all cases, unauthenticated data must be rejected. To diagnose root causes, log non-sensitive metadata, inspect infrastructure, and follow controlled recovery workflows; never dump keys or plaintext for "quick debugging".

## 9. API Selection Decision Table

| Need | Approach |
| --- | --- |
| Decrypt a small GCM record and ensure tag validity | Direct `Cipher.doFinal`, catch `AEADBadTagException` |
| Read a large file encrypted as one GCM record | Direct `Cipher.update`/`doFinal` with staging unpublished before final success |
| Serve plaintext chunks before reaching end of file | Design a per-record AEAD protocol, authenticating each record and stream completeness |
| Using `CipherInputStream` and treating "no IOException" as success | Fix design: not reliable AEAD authentication evidence |
| Using `CipherInputStream` when AEAD integrity errors are not needed | Evaluate against specific mode and API contract; do not generalize beyond scope |
| Valid Base64 input yet invalid tag | Reject at `Cipher.doFinal`; Base64 is only a representation encoding |
| Valid tag yet record re-sent from yesterday | Add protocol freshness/anti-replay; tags do not check recency |

### 9.1 Common Misconceptions

1. **"CipherInputStream always throws AEADBadTagException on a bad tag."** No such guarantee exists in the Javadoc.
2. **"Just readAllBytes and catch IOException—that's safe."** Authentication errors may be masked by the wrapper layer.
3. **"close() will report a missing tag error."** Never treat that as an authentication contract.
4. **"Cipher.update always returns plaintext immediately."** Buffering behavior is provider-dependent.
5. **"My current provider buffers until the end, so all providers do."** Never substitute an empirical observation for a security contract.
6. **"Since doFinal is at the end, streaming plaintext to HTTP beforehand is fine."** No: unauthenticated data was already published.
7. **"The tag failed, yet the start of plaintext looks valid, so process it anyway."** No: the entire record failed authentication.
8. **"available() == 0 means authentication finished."** No: `available` does not report tag/EOF status.
9. **"A bad tag can only mean an attacker altered ciphertext."** No: wrong key, nonce, AAD, storage/transit faults, or truncation also cause it.
10. **"I use GCM, so I don't need a nonce policy."** No: reusing a nonce under the same key is a critical vulnerability.
11. **"I can split a GCM file into chunks and treat each chunk as authenticated."** No: you need per-record AEAD framing with separate tags and stream-completeness checks.
12. **"Base64 decoding succeeded, so ciphertext is trustworthy."** No: you must verify the GCM tag.

## 10. Real-World Scenarios

**Scenario A — Customer profile altered on disk.** A service reads via `CipherInputStream` and gets an empty or truncated byte array with no `IOException`; the app overwrites the profile with empty data. This is a **stream success-signal misinterpretation** bug. Switch to direct `Cipher.doFinal`, reject records on bad tags, and never commit unauthenticated data.

**Scenario B — Decompressing before tag verification.** A pipeline doing GCM decrypt → decompress → parse → DB insert can process unauthenticated bytes before `doFinal`. If the tag fails at the end, parser/DB side effects have already occurred. Fix: stage unauthenticated plaintext, verify completely before sensitive logic touches it, and enforce size bounds against resource exhaustion.

**Scenario C — Multi-GB file too large for `readAllBytes`.** No need to cram all plaintext into RAM. Use direct `Cipher.update`/`doFinal` with secure staging; mark the file "authenticated" only after `doFinal`, then expose it to users/apps. If pieces must be served before a final tag arrives, design separate AEAD records with sequence binding and an end-of-stream marker.

**Scenario D — Wrong AAD after tenant migration.** Ciphertext and tag are unchanged, yet the app uses AAD with the new tenant ID. `doFinal` throws `AEADBadTagException`. That is the intended protection: ciphertext cannot be transplanted across contexts. Never drop AAD just to "make decryption work".

**Scenario E — `InputStream` disconnects mid-stream.** You cannot take the partial decrypted bytes as a valid result. Reject incomplete records, handle I/O failures separately, and never publish artifacts until all data and the tag are verified.

### 10.1 Essential Test Matrix

| Test | Expected Result |
| --- | --- |
| Key + nonce + AAD + ciphertext/tag all valid | `doFinal` returns exact plaintext |
| Flip one bit of ciphertext | Rejected, plaintext not published |
| Flip one bit of tag | `AEADBadTagException` or appropriate authentication error |
| Modify AAD | Rejected, output unused |
| Change key or nonce | Rejected due to failed verification |
| Truncate part of tag | Rejected, never treated as a valid file |
| Input missing version/nonce | Rejected at format validation |
| Decrypt to staging then tag fails | Staging deleted, no official output created |
| Source read throws `IOException` | Fail closed, no partial bytes published |
| Test across multiple supported providers/JDKs | Error path via `Cipher` API still handled properly |

The most important test is not merely "an exception was thrown", but **zero side effects occurred from unauthenticated data**.

## 11. Self-Check Knowledge Questions

**Q1.** If `CipherInputStream.readAllBytes()` returns normally, is the AES-GCM tag guaranteed valid?

**A:** No. The Javadoc warns `CipherInputStream` may catch and swallow integrity-check errors.

**Q2.** What should be used to reliably catch GCM authentication errors in Java 17?

**A:** Use `Cipher` directly, call `doFinal` with the right key, nonce, AAD, and ciphertext/tag; catch `AEADBadTagException` and reject data on error.

**Q3.** Can bytes returned by `Cipher.update` be passed immediately to business logic?

**A:** Never treat them as authenticated plaintext before `doFinal` succeeds. Hold them in staging or an unpublished buffer.

**Q4.** Why is `close()` insufficient?

**A:** `close()` only ends resource lifecycle; it does not guarantee authentication errors swallowed by the wrapper will be surfaced to callers.

**Q5.** Does a bad tag prove an attack definitely happened?

**A:** No. Data corruption, missing bytes, wrong key, wrong nonce, or wrong AAD can also cause `doFinal` to fail.

**Q6.** If a file is too large to fit in RAM, must you go back to `CipherInputStream`?

**A:** No. Use `Cipher.update`/`doFinal` directly with safe staging; publish only after the tag is verified.

**Q7.** Can a large GCM ciphertext be split into chunks and each chunk authenticated using the final tag?

**A:** No. Authenticating chunks independently requires an AEAD record design with per-record nonces/tags and protected ordering and stream completeness.

**Q8.** Why does AES-GCM still require nonce management?

**A:** Reusing a nonce under the same key severely compromises confidentiality and integrity, even when the decryption API reports tag errors properly.

## Conclusion

**`CipherInputStream` is a convenient byte-reading API, yet not a reliable AEAD authentication signal in all cases.** When security depends on detecting bad tags, use **`Cipher.doFinal()` directly**, control key/nonce/AAD, and reject data on failure. For large streams, quarantine plaintext in an untrusted staging area and publish only after the final verification step succeeds.
