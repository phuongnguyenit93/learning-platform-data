# Capturing Bytecode via `JavaFileObject` and `ForwardingJavaFileManager`

**In-memory compilation** is a technique that takes Java source code as a string or in-memory object, invokes the Java compiler from within the program itself, and captures the resulting `.class` outputs directly as `byte[]` arrays. Applications can cache the bytecode, inspect the output, pass it to a class loader, or package it into another artifact without letting the compiler write individual `.class` files to a directory.

The core of this technique rests on two extension points in the Java Compiler API (JSR 199):

1. **`JavaFileObject`** represents a compiler input or output, which can be backed by in-memory data rather than a physical file.
2. **`ForwardingJavaFileManager`** wraps a standard file manager and intercepts requests to create **bytecode output files**, redirecting the `.class` write stream into a `ByteArrayOutputStream`.

This lesson uses **Java 17+** and provides a complete, compilable, and runnable program. The example deliberately causes the compiler to emit **two class files** from a single source file (the main class and a nested class) to demonstrate that you must capture **all outputs**, not just the file corresponding to the original source class.

## 1. Data Flow: From Source Text to Bytecode

With the familiar compilation flow:

```text
Hello.java --javac--> Hello.class on disk
```

With the Java Compiler API:

```text
Source code String
       |
       v
SimpleJavaFileObject (Kind.SOURCE)
       |
       v
JavaCompiler.getTask(...).call()
       |
       v
JavaFileManager.getJavaFileForOutput(...)
       |
       v
JavaFileObject (Kind.CLASS)
       |
       v
openOutputStream()
       |
       v
ByteArrayOutputStream
       |
       v
Map<binaryClassName, byte[]>
       |
       +--> cache / package / inspect
       |
       +--> ClassLoader.defineClass(...)
```

**There is no mandatory step writing `.class` files to disk** in the compilation pipeline designed here. However, that does not mean the entire process never touches disk: the compiler may still read dependencies, modules, or resources from the regular classpath/module path. "In-memory" in this lesson only asserts that **the source and output bytecode are managed in memory**.

Additionally, when you run `javac` to compile the demo program itself, the `.class` files of the **compilation driver program** may reside on disk; those are not the bytecode of the Java class dynamically generated by the demo.

## 2. Four Roles in the Java Compiler API

| Component | Role | Methods to understand |
|---|---|---|
| `JavaCompiler` | Launches a compilation task from inside the JVM | `getTask(...)`, `CompilationTask.call()` |
| `JavaFileObject` | Models a source unit or output bytecode unit | `getCharContent(...)`, `openOutputStream()` |
| `JavaFileManager` | Supplies inputs and handles where the compiler writes outputs | `getJavaFileForOutput(...)`, `close()` |
| `ForwardingJavaFileManager<M>` | Wraps an existing manager, customizing only the needed behavior | Override `getJavaFileForOutput(...)`, delegate the rest |

Several related APIs:

- `ToolProvider.getSystemJavaCompiler()` retrieves the Java compiler provided by the runtime environment, if present; a **suitable JDK** is required, as not every runtime image can be assumed to include a compiler.
- `StandardJavaFileManager` knows how to work with files, JARs, the classpath, and standard paths.
- `SimpleJavaFileObject` is a convenient base class when you do not need to implement the entire `JavaFileObject` interface manually.
- `DiagnosticCollector<JavaFileObject>` captures errors/warnings with source positions without having to parse stderr text.
- `JavaFileObject.Kind.SOURCE` represents source; `Kind.CLASS` represents a class file. **Source code is text; `.class` bytecode is binary data**.

The pragmatic approach is to **use the standard manager for most behavior** and intercept only the specific output that needs changing. You should not rewrite all dependency/JAR lookup logic from scratch when the goal is simply to capture `.class` outputs into memory.

## 3. Input: Source Text as a `JavaFileObject`

Suppose we need to compile the binary name `demo.DynamicHello` from a string containing `package demo;` and `public final class DynamicHello`.

We create a `SimpleJavaFileObject` of kind SOURCE:

```java
private static final class SourceFile extends SimpleJavaFileObject {
    private final String source;

    SourceFile(String className, String source) {
        super(URI.create("string:///" + className.replace('.', '/')
                + Kind.SOURCE.extension), Kind.SOURCE);
        this.source = source;
    }

    @Override
    public CharSequence getCharContent(boolean ignoreEncodingErrors) {
        return source;
    }
}
```

This is **a component inside the complete program in section 6**, not a standalone file. Key points:

1. `URI.create("string:///demo/DynamicHello.java")` is a **logical URI**, not a file path that must exist on disk.
2. The second argument to `SimpleJavaFileObject` is `Kind.SOURCE`, indicating this is a source input.
3. `getCharContent(...)` supplies the text to the compiler. With the source already in a `String`, no `FileInputStream` or file re-read is needed.
4. The class name used to build the URI must match the source and Java naming rules; this is no reason to skip validating user-supplied class/package names.

`SimpleJavaFileObject` has several default behaviors that do not provide content; therefore, source inputs need to override the appropriate read method. Conversely, **CLASS outputs** need to override the **binary write** method, not `getCharContent()`.

## 4. Output: `JavaFileObject` Storing `.class` into a Byte Array

When the compiler prepares to write a class file, it obtains an output `JavaFileObject` from the file manager and invokes the appropriate write method. For binary output of `Kind.CLASS`, we provide an `OutputStream`:

```java
private static final class BytecodeFile extends SimpleJavaFileObject {
    private final ByteArrayOutputStream bytes = new ByteArrayOutputStream();

    BytecodeFile(String className, Kind kind) {
        super(URI.create("mem:///" + className.replace('.', '/')
                + kind.extension), kind);
    }

    @Override
    public OutputStream openOutputStream() {
        return bytes;
    }

    byte[] content() {
        return bytes.toByteArray();
    }
}
```

Details to distinguish:

- `mem:///demo/DynamicHello.class` is an **output-identifying URI**; the `mem` scheme does not itself allocate memory or storage. The bytecode is actually written into the `ByteArrayOutputStream`.
- `Kind.CLASS.extension` corresponds to `.class`.
- `openOutputStream()` returns the output stream so the compiler can send the **class file byte sequence** into it. Holding only a `StringBuilder` will not properly capture `.class` output.
- `toByteArray()` returns **a copy of the byte data** after the compiler finishes writing.
- Each class file needs **its own output object**. If multiple classes write into one shared stream, the data will interleave and no longer form valid class files.
- Copies of bytecode should be retrieved **after `CompilationTask.call()` completes successfully**. Reading while the compiler is still writing can yield incomplete data.

In environments requiring memory optimization, you can design policies for buffer management and release timing. However, `ByteArrayOutputStream` must not be treated as shared storage safe for concurrent compilation tasks.

## 5. Intercepting Output Creation with `ForwardingJavaFileManager`

The compiler does not know we want to write to memory, so we must **redirect `getJavaFileForOutput(...)`**. Illustrative manager class:

```java
private static final class MemoryManager
        extends ForwardingJavaFileManager<StandardJavaFileManager> {
    private final Map<String, BytecodeFile> classes = new LinkedHashMap<>();

    MemoryManager(StandardJavaFileManager standard) {
        super(standard);
    }

    @Override
    public JavaFileObject getJavaFileForOutput(
            JavaFileManager.Location location, String className,
            JavaFileObject.Kind kind, FileObject sibling) throws IOException {
        BytecodeFile output = new BytecodeFile(className, kind);
        classes.put(className, output);
        return output;
    }

    Map<String, byte[]> bytecodes() {
        Map<String, byte[]> result = new LinkedHashMap<>();
        classes.forEach((name, file) -> result.put(name, file.content()));
        return result;
    }
}
```

Like the two classes above, this is an **excerpt** that appears in the full program. Signature explanation:

| Parameter | Meaning |
|---|---|
| `location` | The output location requested by the compiler, e.g., class output; in the simple example no routing by location is needed yet |
| `className` | **Binary name** of the generated class, e.g., `demo.DynamicHello$Punctuation` |
| `kind` | Kind of file to create; in the demo flow, primarily `CLASS` |
| `sibling` | Related file object, helping the manager know context if needed; must not be assumed always non-`null` |

**Why use `ForwardingJavaFileManager`?** It preserves input reading, classpath lookup, JAR lookup, location handling, and `close()` provided by `StandardJavaFileManager`. We override only the output part we need to control.

The demo stores a `Map<String, BytecodeFile>` keyed by class name. This design suits a single **simple-classpath** compilation where each binary name of an output class appears only once. In multi-module, multi-round, or multi-output-location build systems, keying solely by name may not suffice; in those cases you must also account for **module/location/round** to avoid overwriting results.

**Important:** overriding `getJavaFileForOutput` only controls outputs accessed through this method. A complex implementation might generate resources, generated sources, module-scoped outputs, or use additional file manager mechanisms. When the requirement is **never write any artifact to disk**, you must also audit methods like `getFileForOutput`, annotation processor handling, module-oriented outputs, and tool-dependent outputs.

## 6. Complete, Compilable, and Runnable Java 17 Program

Create a single file `InMemoryCompilerDemo.java` with the **entire contents** below. The code uses standard `javax.tools` classes and Java APIs, requiring no third-party libraries.

```java
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.OutputStream;
import java.net.URI;
import java.nio.charset.StandardCharsets;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.TreeSet;
import javax.tools.Diagnostic;
import javax.tools.DiagnosticCollector;
import javax.tools.FileObject;
import javax.tools.ForwardingJavaFileManager;
import javax.tools.JavaCompiler;
import javax.tools.JavaFileManager;
import javax.tools.JavaFileObject;
import javax.tools.SimpleJavaFileObject;
import javax.tools.StandardJavaFileManager;
import javax.tools.ToolProvider;

public final class InMemoryCompilerDemo {
    private static final class SourceFile extends SimpleJavaFileObject {
        private final String source;

        SourceFile(String className, String source) {
            super(URI.create("string:///" + className.replace('.', '/')
                    + Kind.SOURCE.extension), Kind.SOURCE);
            this.source = source;
        }

        @Override
        public CharSequence getCharContent(boolean ignoreEncodingErrors) {
            return source;
        }
    }

    private static final class BytecodeFile extends SimpleJavaFileObject {
        private final ByteArrayOutputStream bytes = new ByteArrayOutputStream();

        BytecodeFile(String className, Kind kind) {
            super(URI.create("mem:///" + className.replace('.', '/')
                    + kind.extension), kind);
        }

        @Override
        public OutputStream openOutputStream() {
            return bytes;
        }

        byte[] content() {
            return bytes.toByteArray();
        }
    }

    private static final class MemoryManager
            extends ForwardingJavaFileManager<StandardJavaFileManager> {
        private final Map<String, BytecodeFile> classes = new LinkedHashMap<>();

        MemoryManager(StandardJavaFileManager standard) {
            super(standard);
        }

        @Override
        public JavaFileObject getJavaFileForOutput(
                JavaFileManager.Location location, String className,
                JavaFileObject.Kind kind, FileObject sibling) throws IOException {
            BytecodeFile output = new BytecodeFile(className, kind);
            classes.put(className, output);
            return output;
        }

        Map<String, byte[]> bytecodes() {
            Map<String, byte[]> result = new LinkedHashMap<>();
            classes.forEach((name, file) -> result.put(name, file.content()));
            return result;
        }
    }

    private static final class MemoryLoader extends ClassLoader {
        private final Map<String, byte[]> code;

        MemoryLoader(Map<String, byte[]> code) {
            super(InMemoryCompilerDemo.class.getClassLoader());
            this.code = Map.copyOf(code);
        }

        @Override
        protected Class<?> findClass(String name) throws ClassNotFoundException {
            byte[] bytes = code.get(name);
            if (bytes == null) {
                throw new ClassNotFoundException(name);
            }
            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Exception {
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null) {
            throw new IllegalStateException("A JDK is required");
        }

        String binaryName = "demo.DynamicHello";
        String source = """
                package demo;
                public final class DynamicHello {
                    private static final class Punctuation {
                        static String ending() { return "!"; }
                    }
                    public static String message(String name) {
                        return "Hello, " + name + Punctuation.ending();
                    }
                }
                """;

        DiagnosticCollector<JavaFileObject> diagnostics =
                new DiagnosticCollector<>();
        Map<String, byte[]> bytecodes;

        try (MemoryManager manager = new MemoryManager(
                compiler.getStandardFileManager(
                        diagnostics, Locale.ROOT, StandardCharsets.UTF_8))) {
            JavaCompiler.CompilationTask task = compiler.getTask(
                    null,
                    manager,
                    diagnostics,
                    List.of("--release", "17"),
                    null,
                    List.of(new SourceFile(binaryName, source)));

            boolean ok = Boolean.TRUE.equals(task.call());
            if (!ok) {
                for (Diagnostic<? extends JavaFileObject> d
                        : diagnostics.getDiagnostics()) {
                    System.err.println(d.getKind() + " at line "
                            + d.getLineNumber() + ": "
                            + d.getMessage(Locale.ROOT));
                }
                throw new IllegalStateException("Compilation failed");
            }

            bytecodes = manager.bytecodes();
        }

        System.out.println("Compilation: success");
        System.out.println("Classes: " + new TreeSet<>(bytecodes.keySet()));

        ClassLoader loader = new MemoryLoader(bytecodes);
        Class<?> generated = loader.loadClass(binaryName);
        Object result = generated.getMethod("message", String.class)
                .invoke(null, "Java");

        System.out.println("Result: " + result);
    }
}
```

### 6.1. How to Run

Install JDK 17 or newer and navigate to the directory containing `InMemoryCompilerDemo.java`.

Linux/macOS:

```bash
javac --release 17 -encoding UTF-8 InMemoryCompilerDemo.java
java InMemoryCompilerDemo
```

Windows PowerShell uses the **same two commands**:

```powershell
javac --release 17 -encoding UTF-8 InMemoryCompilerDemo.java
java InMemoryCompilerDemo
```

There is no need to prepare a `demo/DynamicHello.java` file on disk; the dynamic class's source string is already embedded in the program.

### 6.2. Exact Stdout

Output of a successful run:

```text
Compilation: success
Classes: [demo.DynamicHello, demo.DynamicHello$Punctuation]
Result: Hello, Java!
```

**Why are there two names in `Classes`?** Even though only **one** `SourceFile` of kind SOURCE was supplied, the compiler produces one class file for `demo.DynamicHello` and one class file for the nested class `demo.DynamicHello$Punctuation`. The `$` is part of the nested class's binary name in the example; it does not mean the two names refer to the same class file.

The result is sorted using `TreeSet` for deterministic output; the order in which the compiler calls `getJavaFileForOutput()` is not something a consumer should rely on.

`MemoryLoader` uses the captured bytecode map directly. When `demo.DynamicHello.message(...)` invokes the nested class, the class loader also finds `demo.DynamicHello$Punctuation` in the map, thereby avoiding missing auxiliary class errors.

## 7. Execution Sequence Inside `main`

You can trace the flow through these milestones:

1. **Obtain the compiler:** `ToolProvider.getSystemJavaCompiler()` returns a compiler if the runtime has this tool; otherwise, it stops with a message requiring a JDK.
2. **Create input:** `new SourceFile(binaryName, source)` wraps the source text and a logical URI matching the class name.
3. **Create diagnostic collector:** receives warnings/errors as objects containing `Kind`, location, and message.
4. **Open manager:** the standard manager handles classpath/JARs; `MemoryManager` intercepts requests to create class outputs.
5. **Create task:** `compiler.getTask(writer, fileManager, diagnosticListener, options, classes, compilationUnits)` receives the manager, the `--release 17` option, and the in-memory source.
6. **Call `task.call()`:** the compiler parses, type-checks, and generates output via `getJavaFileForOutput()` → `BytecodeFile.openOutputStream()`.
7. **Check the result:** accept only `Boolean.TRUE`; on failure, use diagnostics to report errors and **do not treat incomplete bytecode as a valid result**.
8. **Snapshot bytecode:** `manager.bytecodes()` converts the buffers into a `Map<String, byte[]>`. Upon exiting `try`, the manager (and its delegate) is closed.
9. **Load from bytecode:** the class loader receives the map and calls `defineClass(...)` inside `findClass(...)`. Only when the JVM needs the corresponding class are the byte data defined into a `Class<?>`.
10. **Invoke method:** uses reflection with the known signature (`message(String)`), receives the result, and prints it.

Returning a task from `getTask()` **does not guarantee compilation has happened**. Compilation executes when `task.call()` is called. `JavaCompiler.CompilationTask` is not an object meant to be invoked repeatedly with the same state; each compilation pass should have a new task and possibly a new manager.

## 8. Why Capture All Class Outputs Instead of Just the Main Class?

A single source file can emit multiple class files:

- **Nested classes** (nested/static/inner classes).
- **Anonymous classes** or certain language constructs that generate synthetic/auxiliary classes.
- **Multiple top-level classes** valid in the same compilation unit (at most one public top-level class matching the source file name).
- **Multiple compilation units supplied together** in a single compilation run.

You should not design:

```java
// Illustrates an insufficient approach: guessing only one output for the main class.
byte[] compiled = outputs.get("demo.DynamicHello");
```

and discard the rest if you expect to load and execute the dynamic class. If `DynamicHello` references `Punctuation`, the loader needs both bytecodes when the auxiliary class is loaded.

A more reliable design is to **store all outputs by binary name** and only construct the loader after the task succeeds:

```java
Map<String, byte[]> allClasses = manager.bytecodes();
```

The statement above is a snippet used in a context where the `manager` variable exists. You only need to intercept additional resource/source kinds when the problem actually uses annotation processors or auxiliary outputs.

## 9. Diagnostics: Compilation Errors vs. Class Runtime Errors

`JavaCompiler.getTask(...).call()` typically returns:

- `true`: the compilation task succeeded (warnings may still be present).
- `false`: there are compilation errors, such as syntax or type errors.
- Certain other serious errors may be thrown as exceptions; not every failure case should be lumped into a `false` return value.

For example, if the dynamic source calls a non-existent method, the compiler reports an error in `DiagnosticCollector`, and the program in section 6 **does not proceed to the class-loading step**.

To print structured errors:

```java
for (Diagnostic<? extends JavaFileObject> d : diagnostics.getDiagnostics()) {
    System.err.printf("%s: line %d, column %d: %s%n",
            d.getKind(),
            d.getLineNumber(),
            d.getColumnNumber(),
            d.getMessage(Locale.ROOT));
}
```

This is a snippet within a scope containing the `diagnostics` variable. When line/column numbers are unknown, the API may supply sentinel values indicating "no position"; do not assume every diagnostic maps to a specific source line.

Two phases must be distinguished:

| Phase | Common errors | How to check |
|---|---|---|
| Compilation | Invalid syntax, missing type or method, invalid options | `task.call()`, `DiagnosticCollector`, compilation classpath |
| Class definition/loading | Missing auxiliary class bytecode, mismatched class name, missing dependency | Output map, `ClassLoader.findClass`, `ClassLoader.loadClass` |
| Linking/execution | `NoClassDefFoundError`, `NoSuchMethodError`, exceptions thrown by dynamic code | Runtime dependency versions, stack trace, loader boundaries |
| Reflection | Wrong method name/signature/access permissions | `getMethod(...)`, parameter types, accessibility |
 
A task can **compile successfully** yet still fail at runtime if the compilation classpath contains dependencies absent from the runtime class loader. Capturing all bytecode of classes *compiled in the current pass* does not mean capturing every dependency required for execution.

## 10. Practical Extensions of the File Manager

### 10.1. Multiple Source Units

`getTask()` has the parameter `Iterable<? extends JavaFileObject> compilationUnits`, so you can pass multiple `SourceFile` instances into the same compilation:

```java
List<JavaFileObject> units = List.of(
        new SourceFile("demo.First", firstSource),
        new SourceFile("demo.Second", secondSource));
```

This is an **illustrative syntax example**: `firstSource`/`secondSource` are variables holding source text that the application must supply. When both sources are visible to the compiler within the same task, they can reference each other under normal Java rules.

You should not launch a separate `getTask()` for each mutually dependent class without designing a way to feed previously compiled bytecode as classpath/in-memory input to the next task.

### 10.2. Multi-Pass Compilation and In-Memory Class Lookup

In the demo, `MemoryManager` only captures outputs; it **does not** feed those `byte[]` arrays as inputs to another compiler task. If you want to compile class B in a later pass while B depends on class A compiled in an earlier pass, you must solve how the compiler finds A's `.class`.

There are two main approaches:

1. Package/provide A on a classpath supported by the compiler (possibly via an intermediate JAR/file if I/O is acceptable).
2. Implement input-lookup methods in `JavaFileManager`, such as `getJavaFileForInput(...)`, `list(...)`, `inferBinaryName(...)`, and corresponding module/classpath semantics, so that in-memory bytecode is recognized by the compiler. **Overriding `getJavaFileForOutput()` alone is not enough for this case.**

Do not confuse the **compiler's** class lookup path with the `ClassLoader` used to **execute** classes after compilation: these are two mechanisms belonging to two different phases.

### 10.3. Annotation Processors and Generated Resources

Annotation processors can emit new sources, classes, or resources. The article's example does not enable custom processors; if applied in a larger project, the manager may need to handle:

- `getJavaFileForOutput(...)` for generated sources and classes.
- `getFileForOutput(...)` for non-Java-class resources.
- Module/location-related output methods if there are multiple modules.
- Appropriate binary class names and origins/siblings across multiple compilation rounds.
- Policies permitting or disabling annotation processing based on source trust levels.

You must not claim "never touches disk" based solely on capturing `Kind.CLASS` when other output paths have not been audited. If sources are untrusted, you should proactively consider processing configuration and isolation mechanisms.

### 10.4. Managing Multiple Modules or Multiple Class Versions

In a simple task, a `Map<String, byte[]>` keyed by `binaryName` suffices. When the same class name appears in multiple modules or compilation contexts, you must add **module identity / output location** information. At runtime, each class loader scope must also be designed to know which class names belong to it.

Putting two classes with the same name into one map under a single key causes one to overwrite the other; that is not version isolation. You need module layers or separate loaders according to design requirements, rather than merely changing the map type.

## 11. Interaction with Class Loaders: Capturing Bytecode Does Not Mean Loading Classes

The demo includes:

```java
ClassLoader loader = new MemoryLoader(bytecodes);
Class<?> generated = loader.loadClass("demo.DynamicHello");
```

`MemoryLoader.findClass()` uses `defineClass(name, bytes, 0, bytes.length)`. It **does not** touch the filesystem to find dynamic classes. However, the class loader in the demo still follows the **default parent-first** mechanism via `ClassLoader.loadClass()`; if the parent already has a class with the same name, the parent can win before `findClass()` is ever called.

That is why in the example we chose the name `demo.DynamicHello`, which is not already on the classpath. In real plugin environments, clear namespace, package, and delegation policies are needed to avoid collisions. Do not arbitrarily switch the entire loader to child-first, as that can duplicate shared contract types and cause `ClassCastException`.

In addition:

- `defineClass` validates class file integrity according to JVM rules; malformed bytecode can cause `ClassFormatError` or verification/linking errors.
- Loading a class does not mean every execution path in it has been validated for business logic.
- Recompiling the same class name **cannot replace an existing definition in the same loader** merely by swapping `byte[]` entries in a map. You usually have to create a new loader or use an appropriate specialized mechanism.
- Loaders/classes/instances that remain referenced retain their associated data and resources; if creating compilers and loaders per request, you must define lifecycles and cache limits.

## 12. Security, Resources, and Operations

Compiling dynamic source code is not a sandbox. Even during compilation alone, annotation processors or compiler plugins can execute code; once generated classes are loaded and executed, that code runs with the permissions of the current JVM.

For code supplied by external users, strict evaluation is required:

- **Trusted sources:** who is allowed to submit sources, which compiler options may be enabled, and who is allowed to enable annotation processors.
- **Resource limits:** source size, number of compilation units, number of generated classes, total bytecode size, CPU time, and memory. An unbounded build can exhaust the heap.
- **Dependencies:** the compilation classpath should not arbitrarily pull in unvetted libraries. Compiler artifacts and extensions must be audited and controlled.
- **Code execution:** running untrusted code requires strong enough isolation, such as a process/container with proper permission and resource policies; **a class loader is not a security boundary**.
- **Concurrent requests:** each task should own its own state/manager/buffers; do not share a `LinkedHashMap` or standard file manager across multiple threads without synchronization.
- **Cleanup:** use `try-with-resources` to close the file manager. After snapshotting bytecode, decide when to evict caches and drop loader/instance references.
- **Monitoring:** record metrics for duration, source count, class byte count, and warnings/errors; avoid logging full sensitive sources.

In particular, `DiagnosticCollector` may contain code snippets, file names, or errors related to the source; if the source contains sensitive information, handle logs and access permissions appropriately.

## 13. Common Mistakes and Fixes

| Mistake | Symptom | Fix |
|---|---|---|
| Overriding `getCharContent()` for `.class` outputs too | Bytecode is not captured properly | CLASS outputs require `openOutputStream()` |
| Reusing a single `ByteArrayOutputStream` for all classes | `.class` files get corrupted/mixed | Create a new output object per binary name/output location |
| Extracting only the top-level class bytecode | Auxiliary classes missing during loading | Collect every `getJavaFileForOutput()` call in the task |
| Using file path strings instead of binary class names | Map lookup/class loader name mismatch | Use the `className` provided by the compiler; maintain clear mappings |
| Using output even when `task.call()` returns false | May only contain incomplete bytes | Stop and inspect diagnostics |
| Generating bytecode without providing a class loader | Cannot directly call dynamic classes via static types absent from compile classpath | Use an appropriate loader and reflection or shared interfaces |
| Mixing up compilation classpath and runtime classpath | Compiles cleanly, fails at runtime with missing dependencies | Verify both environments |
| `ToolProvider.getSystemJavaCompiler()` returns null | Runtime lacks the compiler | Use a JDK/runtime containing the required compiler module |
| Overriding only output while expecting subsequent compilations to reuse bytecode | Compiler cannot find previously compiled classes | Implement input lookup or supply artifacts on the classpath |
| Running untrusted source code inside the host JVM | Resource and security risks | Isolate build/execution processes and restrict permissions |
| Sharing a manager/buffer arbitrarily across threads | Race conditions, corrupted results | Isolate state per task, synchronize when necessary |
| Retaining `byte[]` maps and loaders indefinitely | Growing heap and difficulty unloading classes | Manage caches, quotas, and lifecycles |

## 14. Testing Checklist for an In-Memory Compiler

Before deploying to production:

1. **Accurate input:** `JavaFileObject.Kind.SOURCE` has a valid URI and source content, with package/class names matching the source.
2. **Complete capture:** `getJavaFileForOutput` receives accurate binary names and creates a separate buffer for each class file.
3. **No unintended disk writes:** verify all output kinds that need capturing, including resources generated by processors if enabled.
4. **Reliable diagnostics:** compilation errors are reported via diagnostics with context; partial bytecode is never used.
5. **Multiple classes:** test nested/anonymous classes and verify all `byte[]` entries needed for loading are captured.
6. **Dependency boundaries:** both the compiler and the class loader see the correct dependencies and versions.
7. **Post-compilation results:** map is captured after `task.call()`, and binary data is not corrupted by encoding conversions.
8. **Lifecycle:** file manager is closed; bytecode caches and loaders do not grow without bound.
9. **Failure tests:** invalid syntax, missing types, missing runtime dependencies, compiler unavailable.
10. **Security:** policies exist for sources/processors and dynamic class execution.

2. **Add another nested class:** add one more nested static class to the `source` string. Predict the number of `Kind.CLASS` outputs and which new keys will appear in the map.
3. **Intentionally trigger an error:** change `Punctuation.ending()` to a non-existent method name. Observe `DiagnosticCollector` and explain why `bytecodes` must not be used when compilation fails.
4. **Compile two sources:** create two `SourceFile` instances with different classes and pass both simultaneously to `getTask()`. Have one class call a method on the other; verify the compiler resolves the dependency within the same task.
5. **Multi-pass compilation:** design a step that exposes previously stored bytecode as `JavaFileObject.Kind.CLASS` for a subsequent compiler pass, listing the file manager methods to consider. Why is `getJavaFileForOutput()` alone insufficient?
6. **Change runtime strategy:** create a new loader from the bytecode map and demonstrate that updating the bytecode map does not automatically replace classes already loaded in the old loader. Describe the loader-leak risk when running repeatedly.

**Conclusion:** in the Java Compiler API, `JavaFileObject` is **where the compiler reads sources or writes classes**, while `ForwardingJavaFileManager` is **the redirection point for outputs** from default file storage into memory. A sound design must store *every* generated class file, check compiler results and diagnostics, and cleanly separate **compilation**, **loading**, and **execution** of bytecode.
