# `ExecutionControlProvider` and the Boundary Between the Controlling JVM and Execution JVM

## 1. Why Does JShell Need an Execution Engine?

JShell is an interactive Java API and tool introduced in JDK 9. When a host application embeds `jdk.jshell.JShell` and calls `eval(...)`, JShell must compile snippets, manage declaration state, and **execute** the generated bytecode. The execution mechanism is abstracted through `jdk.jshell.spi.ExecutionControl`, while `jdk.jshell.spi.ExecutionControlProvider` is the extension point for choosing how to create the execution engine.

A key distinction: the **controlling JVM** runs the host, holds the `JShell` instance, analyzes snippets, and orchestrates the session. The **execution JVM** is where snippet bytecode runs; it may be a separate JVM process, or execute in the same process via an appropriate engine. The term "execution JVM" does not always imply a separate process: that depends on the chosen provider.

### Conceptual Diagram

```text
+----------------------------------------------+
| Controlling JVM                              |
| Host app -> JShell API -> compiler/state      |
|                  |                           |
|           ExecutionControl                   |
+------------------|---------------------------+
                   | invocation / class load
                   v
+----------------------------------------------+
| Execution environment                        |
| - Local engine: inside host JVM              |
| - Remote engine: separate JVM process        |
| - Custom provider: execution strategy        |
|   defined by provider author                 |
+----------------------------------------------+
```

The execution engine is not a JSR 223 script engine. JShell executes **Java snippets** via `jdk.jshell`, rather than looking up `javax.script.ScriptEngineFactory` or running JavaScript.

## 2. Related APIs

| API | Role |
|---|---|
| `jdk.jshell.JShell` | Interactive session holding snippet state, providing `eval`, `drop`, `variables`, `methods`, `close` |
| `JShell.Builder.executionEngine(...)` | Selects a provider or specifies an execution engine when building JShell |
| `jdk.jshell.spi.ExecutionControl` | Interface communicating with the execution runtime: loading classes, invoking code, stopping, querying variables, etc. |
| `jdk.jshell.spi.ExecutionControlProvider` | Service provider creating an `ExecutionControl` from `ExecutionEnv` and parameters |
| `jdk.jshell.spi.ExecutionEnv` | Bridge supplying I/O streams, configuration, and info from JShell to the execution provider |
| `jdk.jshell.execution.JdiExecutionControlProvider` | Provider supporting execution in another JVM via JDI |
| `jdk.jshell.execution.LocalExecutionControlProvider` | Provider executing locally inside the controlling JVM |
| `jdk.jshell.execution.FailOverExecutionControlProvider` | Mechanism trying multiple providers in configured order |

These provider classes belong to the `jdk.jshell` module and Java 17+ APIs. Specific provider names, parameters, and characteristics should be verified against the deployed JDK/runtime; do not assume all providers offer the same stopping, isolation, or recovery capabilities.

## 3. How Does `ExecutionControlProvider` Work?

By design, `ExecutionControlProvider` provides:

- `name()`: the provider name used in configuration.
- `defaultParameters()`: a map of default parameters advertised by the provider.
- `generate(ExecutionEnv env, Map<String,String> parameters)`: creates an `ExecutionControl` given the environment and parameters.

The JShell builder can select an execution engine by provider and parameters. `ExecutionEnv` lets the provider communicate with the controlling JShell, such as retrieving output/error streams and initializing/resetting the environment per the API contract. The provider is responsible for engine lifecycle and handling failures if the execution environment becomes unresponsive.

**Illustrative** example using a pre-configured provider:

```java
ExecutionControlProvider provider = ...; // appropriate provider
Map<String, String> options = provider.defaultParameters();
try (JShell js = JShell.builder()
        .executionEngine(provider, options)
        .build()) {
    js.eval("int answer = 42;");
}
```

Requires importing `jdk.jshell.JShell`, `jdk.jshell.spi.ExecutionControlProvider`, and `java.util.Map`. This snippet is **not standalone** because `provider` has no concrete value. In a real host, supply an instance of `LocalExecutionControlProvider` or a custom provider instead of `...`.

In plugin architectures, choose the provider **before creating the JShell instance**. Do not try to swap the execution provider mid-session on a shell containing snippet state and expect state to migrate automatically to another engine. State transfer workflows must be designed explicitly, or a new session created and code re-evaluated appropriately.

## 4. Java 17+ Example: Default JShell vs. Local Engine

This example requires no external plugins and demonstrates controlling snippet execution via the API. Create `InspectJShell.java`:

```java
import java.util.List;
import jdk.jshell.JShell;
import jdk.jshell.SnippetEvent;
import jdk.jshell.execution.LocalExecutionControlProvider;

public final class InspectJShell {
    static void run(JShell shell, String title) {
        List<SnippetEvent> events = shell.eval("int n = 6 * 7;");
        System.out.println(title + " events: " + events.size());
        for (SnippetEvent event : events) {
            System.out.println(event.status() + ": " + event.value());
        }
    }

    public static void main(String[] args) {
        try (JShell defaultShell = JShell.create()) {
            run(defaultShell, "default");
        }

        try (JShell localShell = JShell.builder()
                .executionEngine(new LocalExecutionControlProvider(), null)
                .build()) {
            run(localShell, "local");
        }
    }
}
```

Compile and run (JDK 17+):

```bash
javac --add-modules jdk.jshell InspectJShell.java
java --add-modules jdk.jshell InspectJShell
```

Expected output:

```text
default events: 1
VALID: 42
local events: 1
VALID: 42
```

This snippet creates **two separate JShell sessions**. One uses JShell's default execution engine, while the other explicitly selects the local provider. Identical `42` results do not mean the two sessions share the same process boundary or failure model.

**Important note:** Passing `null` as the second argument to `executionEngine(provider, parameters)` lets the builder use default parameters per the session configuration mechanism. In applications needing explicit policies, pass an adjusted copy of `provider.defaultParameters()` rather than assuming all providers accept the same map.

## 5. Remote Execution: Child JVM and Process Boundaries

A remote execution engine (such as a provider using JDI to launch a child JVM) can place snippets in a **separate process** with independent heap, static fields, and threads. This brings fault isolation and resource management benefits, yet does not create a secure sandbox on its own:

- Snippets in a child JVM cannot directly share heap object references with the controlling JVM. Passing data requires an intentionally designed protocol, serialization, or bridge.
- The child JVM's classpath, module path, system properties, OS environment, and Java version may differ from the controlling JVM; specify launch options explicitly.
- Snippet stdout/stderr can be forwarded back to the controlling process via `ExecutionEnv` configuration; do not assume they are always the same stream or thread.
- The child process can crash, hang, or be killed; the host must handle execution engine errors, timeouts, cleanup, and session recreation as needed.
- Process separation reduces some risks of corrupting the host heap, **but does not automatically restrict network, filesystem, CPU, or sensitive data access** if the process still runs with the same OS privileges.

### Specifying a Remote Provider

The snippet below illustrates selecting an existing JDI provider:

```java
import jdk.jshell.JShell;
import jdk.jshell.execution.JdiExecutionControlProvider;

JdiExecutionControlProvider jdi = new JdiExecutionControlProvider();
try (JShell shell = JShell.builder()
        .executionEngine(jdi, jdi.defaultParameters())
        .build()) {
    shell.eval("System.out.println(\"run in execution environment\");");
}
```

This is a **code fragment**, not a standalone file (statements must sit inside a method). Launching a child JVM can fail due to process-creation permissions, ports, JDI, system policies, or a JDK runtime image missing modules; catch and handle errors appropriately. Do not treat this snippet as proof that every environment can run the remote provider.

## 6. Local Execution: Shared JVM and Resource-Sharing Risks

`LocalExecutionControlProvider` lets JShell execute snippets inside the controlling JVM. This is convenient for applications that tightly control content and want to avoid spawning a child JVM, at the cost of isolation.

Consequences:

- Snippets can mutate process-wide state, such as system properties and JVM resources, if code has access.
- Threads, memory, native libraries, class loaders, and static state must be carefully managed; closing JShell does not guarantee arbitrary executed code has not left threads or resources behind.
- Severe errors in a snippet can impact the host itself.
- The ability to halt uncooperative snippets is limited; never promise hard timeouts solely through the JShell API.

In applications executing user-supplied or untrusted code, **never use the local engine as a security boundary**. Even with a remote engine, OS/container isolation, privilege restrictions, and resource limits remain necessary to meet security requirements.

## 7. `ExecutionControl` Is Not `ClassLoader`

Distinguish these two abstractions:

| Aspect | ClassLoader | ExecutionControl |
|---|---|---|
| Purpose | Locate and define classes | Orchestrate execution of snippets compiled by JShell |
| Primary subjects | `Class<?>`, packages, bytecode | Snippet state, invocation, class installation, stop, execution lifecycle |
| Scope | One JVM process | Can cross JVM/process boundaries |
| Provides a sandbox? | No | No |

JShell typically emits classes from snippets. The provider must deliver class bytes to the execution environment per the `ExecutionControl` contract. With a remote JVM, bytecode and commands are transmitted over an implementation-specific internal protocol. Do not equate the loader the host used to load `ExecutionControlProvider` with the loader that actually loads snippet classes in the execution environment.

For instance, a host discovering a provider from the classpath via `ServiceLoader<ExecutionControlProvider>` does not prove all providers run locally. A provider might launch another JVM or use a custom remote mechanism. Inspect the provider's contract and configuration and verify by observing process/lifecycle behavior rather than inferring from the class loader.

## 8. Writing a Custom `ExecutionControlProvider`: When Is It Needed?

Valid use cases can include:

- Dispatching snippet execution to a host-managed JVM worker.
- Using a custom transport/protocol to the execution environment.
- Customizing classpath, startup, logging, resource limits, and reconnection for a deployment environment.
- Explicitly tracking lifecycle and recovering when a worker fails.

Do not write a custom provider just to run a simple Java snippet: the compiler/class loader APIs or built-in providers usually suffice. If you implement `ExecutionControl` yourself, you must satisfy every method and exception contract of the SPI, including class byte management, invocation, variables, `stop`, and `close`. This is a high-complexity integration layer, not simply writing an `eval(String)` function.

### Illustrative Skeleton Pattern

```java
import java.util.Map;
import jdk.jshell.spi.ExecutionControl;
import jdk.jshell.spi.ExecutionControlProvider;
import jdk.jshell.spi.ExecutionEnv;

public final class MyProvider implements ExecutionControlProvider {
    @Override
    public String name() { return "my-engine"; }

    @Override
    public Map<String, String> defaultParameters() {
        return Map.of();
    }

    @Override
    public ExecutionControl generate(ExecutionEnv env,
                                     Map<String, String> parameters)
            throws Throwable {
        throw new UnsupportedOperationException(
                "A complete ExecutionControl must be provided");
    }
}
```

**Not a usable implementation**: `generate` intentionally does not create an engine. This snippet only illustrates the provider interface; do not register it as an active plugin because JShell creation will fail. When building a real provider, start from the SPI documentation and a reference implementation matching your target JDK.

## 9. Lifecycle, Errors, and Execution Interruption

The host must distinguish among error categories:

| Category | Symptom | Appropriate Response |
|---|---|---|
| Snippet rejected by compiler | `SnippetEvent.status()` is a rejected status | Display diagnostics; do not treat as an engine failure |
| Snippet throws an exception | `SnippetEvent.exception()` holds exception details | Report snippet runtime error; do not equate with JVM crash |
| Engine/provider failed to start | Error in `JShell.Builder.build()` or `ExecutionControlProvider.generate` | Log cause, cancel session, apply fallback per policy |
| Remote JVM died or disconnected | Execution control error, engine unresponsive or terminated | Clean up process/sockets, create a new session when appropriate |
| Snippet hangs / infinite loop | Does not finish within expected time | Enforce timeout/cancellation at the appropriate management layer with independent worker kill capability |

`JShell.stop()` is designed to request halting a running snippet, yet whether and when it succeeds depends on the provider and what the running code is doing. Do not use it as a hard time limit for untrusted code.

Use `try-with-resources` to call `JShell.close()` at session end. With a remote engine, ensure subprocesses, connections, and auxiliary resources are not orphaned. With a local engine, watch for threads/resources created by snippets; `close()` cannot automatically undo all side effects.

## 10. Checklist for Choosing an Execution Provider

1. Determine whether snippets are trusted internal code or untrusted code.
2. Verify the runtime includes `jdk.jshell`, the compiler, and required providers.
3. Explicitly choose local/remote/custom engine based on latency, isolation, and debugging needs.
4. For remote engines: configure the Java executable, JVM options, classpath/module path, and OS permissions properly.
5. Design handling for I/O, errors, timeouts, worker crashes, and cleanup.
6. Never pass live host Java objects directly across a JVM boundary; use a schema-backed data protocol.
7. Test restarts/failover and ensure dead engine JShell state is not blindly reused.
8. Evaluate security at the OS/process level rather than assuming a class loader or subprocess is a sandbox.

**Conclusion:** `ExecutionControlProvider` governs how JShell constructs its execution engine and therefore defines the execution boundary. The controlling JVM holds the JShell session and orchestration logic; the engine can run locally or in a separate JVM. Choosing a provider is an architectural decision about latency, resources, resilience, and security—not just a parameter on `JShell.Builder`.
