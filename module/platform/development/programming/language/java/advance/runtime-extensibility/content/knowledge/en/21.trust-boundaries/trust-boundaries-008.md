# Controlling Inputs, Dependencies, and Tools Executed During Compilation

In a Java platform with runtime extensibility, the host may accept plugin source code, resolve dependency libraries, invoke the Java compiler, and produce bytecode for subsequent loading. Every one of those steps sits on a **trust boundary**: content submitted by a user or plugin is not inherently trusted, downloaded libraries have different provenance and authority from host code, and compilers/annotation processors/build plugins can execute with the privileges of the process running the build.

A common mistake is assuming that **because `.class` files have not been executed yet, the compilation phase is automatically safe**. That is false. Having `javac` merely parse ordinary Java source does not automatically run static initializers of the source classes, yet **annotation processors, `javac` plugins, build scripts, build-tool plugins, code generators, and auxiliary tools** can execute code right during compilation. At the same time, even without extension tools, a large or malicious input can consume CPU, RAM, or disk, prolong compilation time, or trigger tool bugs.

The goal of this lesson is to distinguish **what is being compiled** from **what is executed during compilation**, and then design a control pipeline: **input → dependencies → toolchain → compilation task → artifact**. The hands-on section uses **Java 17+**, providing a standalone program that obtains `JavaCompiler`, applies fixed options, validates input, keeps annotation processing disabled, and only verifies the generated bytecode; never treat the in-process example as a sandbox for untrusted code.

## 1. Identifying Boundaries and Assets to Protect

In a plugin compilation service, the assets requiring protection go beyond host application code:

- **Build machine/process:** CPU, RAM, threads, file descriptors, disk, and processing time. A single compile request must not stall the entire host.
- **Secrets and configuration:** environment tokens, artifact repository credentials, signing keys, user data, or build agent metadata.
- **Filesystem:** source files, other tenants' artifacts, dependency caches, configuration files, and system working directories.
- **Network and external services:** repositories, internal databases, metadata endpoints, and plugin control services.
- **Supply chain:** JDK version, annotation processors, compiler plugins, dependencies, build plugins, and JAR download sources.
- **Output integrity:** bytecode must originate solely from the accepted inputs, dependencies, and toolchain; no stale artifacts may leak into a new build.
- **Tenant boundaries:** one tenant's code and libraries must never read or modify another tenant's sources, outputs, or secrets.

Ask **who is allowed to decide each part**. User-supplied source code should be treated strictly as **compilation data**; users must not arbitrarily decide the compiler executable, JDK options, processor path, network endpoints, or worker output location.

A diagram separating authority:

~~~text
[Untrusted plugin submitter]
   |
   | source + metadata declared under a restricted schema
   v
[Ingress validator] -- reject --> [Reasoned error response]
   |
   | normalized source; request ID; quota
   v
[Policy/dependency resolver] <-- approved repos/artifacts only
   |
   | version manifest + SHA-256 + permission list
   v
[Isolated compile worker]
   |  trusted version-pinned JDK/compiler
   |  classpath/module path built from allowlist
   |  processors disabled by default; no secrets
   |  OS-enforced CPU/RAM/time/disk/network limits
   v
[Output artifact quarantine]
   |
   | verify binary names, file count, metadata, hash
   v
[Approved artifact] -- separate activation step --> [Plugin runtime]
~~~

This diagram is an **operational model**, not a built-in feature of `javax.tools`. If you merely invoke `compiler.getTask()` inside the host JVM, isolation/quarantine steps must be guaranteed by other parts of the architecture.

### Roles and Trust Zones

| Component | Default trust | Decisions it should be allowed to make |
| --- | --- | --- |
| User-uploaded Java source | Untrusted | Define plugin logic within allowed APIs; never choose system privileges |
| User-submitted build metadata | Schema-constrained data | Only allowlisted fields: plugin name, version, permitted dependency IDs |
| Dependency artifacts from repository | Dependent on provenance verification | Accepted by resolver by exact coordinates/hash; never self-promoted to executable tools |
| Annotation processor | **Code executed at compile time** | Run only when trusted by the host, version-pinned, and explicitly permitted |
| `javac` / toolchain | Trusted administrative component | Version, binary path, flags, and module graph fixed by policy |
| Build script / plugin | **Code executed at build time** | Must be treated as a privileged program, not a pure config file |
| Output `.class` / `.jar` | Not automatically trusted | Moved to approved artifact storage only after verification; execution is a separate step |

## 2. Stage-by-Stage Threat Model

### 2.1. Inputs Are Treated as Data, Not Execution Commands

Inputs may contain valid Java code that is dangerous when **run**, or contain source structures/paths/filenames that corrupt the compiler workspace **right during processing**. Not every risk requires code execution.

Examples of problem categories:

- **Resource exhaustion:** oversized sources, too many classes, deeply nested expressions/generics, excessive files, or constructs causing high resource usage during analysis.
- **Path traversal and file storage:** filenames using absolute paths, `../`, Windows path equivalents, symlinks, or improperly normalized names causing writes outside the workspace.
- **Archive inputs:** JAR/ZIP archives or bundles with duplicate files, path traversal in ZIP entries, extreme decompression ratios, or excessive entry counts filling the disk.
- **Namespace collisions:** sources attempting to redefine host API packages, reserved package names, or class names colliding with others in the workspace.
- **Unintended compiler options:** users setting compiler options, output directories, classpaths, or processor paths instead of the host.
- **Information leaks via diagnostics:** host paths, classpaths, source excerpts, internal package names, or system environment details logged to the wrong audience.

**Pre-compiler protection** policies should clearly determine which files are allowed, accepted input types, maximum sizes, package structures, directory tree depth, source paths, and output destinations. However, syntax checks or regex filters on source **are not a sandbox** proving code is safe to run afterward.

### 2.2. Dependencies and Tools Are Separate Execution Gates

In Java 17, `javac` can discover and execute **annotation processors** during compilation. According to JDK 17's `javac` documentation, if no separate processor path is configured, processors may be searched on the **classpath**. A dependency added solely for type references that also ships a processor service declaration can therefore become an executed code path whenever annotation processing is enabled.

Build tools introduce additional boundaries: for instance, a Maven/Gradle plugin, task, or user-supplied script can run system commands directly during the build phase, regardless of `javac`. Compile classpath dependencies and **executed tools** must never be merged into a single trust bucket.

**Core lesson:** merely placing a JAR on the classpath does not mean its classes run automatically; however, tools configured to **load providers/processors/plugins** can turn a JAR into privileged build-time code. You must control both **discovery mechanisms** and **the list of executed tools**.

## 3. Input Control: Clear Limits and Proper Normalization

An upload contract should contain only controlled fields, for example:

~~~json
{
  "pluginId": "formatter-basic",
  "language": "java",
  "targetRelease": 17,
  "sources": [
    {
      "binaryName": "demo.generated.FormatterImpl",
      "content": "package demo.generated; public final class FormatterImpl {}"
    }
  ],
  "dependencyIds": ["public-plugin-api:1.2"]
}
~~~

**This is an example payload**, not a standard Java API. The host must **never** accept keys such as `compilerCommand`, `arbitraryFlags`, `shellScript`, `processorJarPath`, `uploadOutputPath`, or `absoluteClasspath` from untrusted callers. Where configuration choices exist, each choice must map to an explicitly authorized policy.

### 3.1. Size and Structural Limits

Minimum checks **before creating a workspace**:

1. Authenticate the submitter and verify compile permissions for that plugin/tenant.
2. Cap total request size, per-source UTF-8 byte size, source count, identifier lengths, package counts, and dependency artifact counts.
3. Accept only the specified encoding, typically UTF-8; never rely on the build host's default encoding.
4. Validate binary class names and package segments against Java grammar; dots or visually similar Unicode characters do not automatically make a name valid.
5. Allow only authorized packages/namespaces; reject `java.*`, internal host namespaces, and API packages plugins are forbidden from defining.
6. Prevent new sources from overwriting existing files belonging to other tenants or the toolchain itself.
7. Check file counts, total uncompressed bytes, and projected output bytes against quotas.
8. Do not treat a source that fails parsing as proof of an attack: return `VALIDATION_FAILED` or `COMPILE_FAILED` appropriately while logging signs of policy-bypass attempts.

Input limits prevent many simple DoS cases, yet cannot bound every compiler complexity corner case. Small inputs can still trigger heavy CPU usage or parser bugs; workers need out-of-process quotas.

### 3.2. Class Names and Paths Are Two Different Concepts

A valid binary name such as `demo.generated.FormatterImpl` can be mapped to:

~~~text
workspace/src/demo/generated/FormatterImpl.java
~~~

Never do this:

~~~java
// WRONG ILLUSTRATIVE CODE: rawFileName comes from an untrusted request.
Path output = workspace.resolve(rawFileName);
Files.writeString(output, source);
~~~

This snippet is not a standalone class and intentionally omits validation to highlight the risk. If `rawFileName` starts with an absolute path, contains traversal, points through a symlink, or is interpreted differently across OSes, output may land outside the intended spot.

The proper approach is for **the host to derive paths from a validated binary name**, enforce namespace restrictions, split the name into Java identifier segments, append a fixed `.java` suffix, and operate strictly inside a host-created workspace. Calling `Path.normalize` and checking `startsWith` on canonicalized absolute paths is a necessary step, yet **insufficient against symlinks/races** when another actor can modify directory trees. Real workers need proper filesystem/mount ownership, must never share writable workspaces with untrusted actors, and must enforce symlink policies.

### 3.3. When Receiving ZIP/JAR Archives Containing Source

An entry-scanning loop must:

- Reject absolute entries, traversal entries, invalid names, device/special files, and disallowed entry/link types.
- Extract into an isolated workspace without following symlinks created by the archive.
- Limit **entry count**, **nesting depth**, **compressed size**, **uncompressed size**, and **total output**, checking continuously while streaming to stop ZIP bombs.
- Detect duplicate names after normalization (including case differences on target filesystems) to avoid unintended overwrites.
- Never automatically execute scripts or build files uploaded alongside the archive.
- Never use archive-supplied filenames to construct shell commands or tool paths.

**Checking ZIP entries before extraction is insufficient** if the subsequent extraction follows symlinks or fails to enforce quotas while streaming. Maintain enforcement boundaries at both the API layer and the filesystem layer.

## 4. Controlling Dependencies: The Classpath Is Not an Arbitrary JAR Store

Dependencies let the compiler resolve types, methods, and annotations. Letting submitters fetch arbitrary Maven coordinates or URLs turns compilation into an uncontrolled network gateway or tool-execution vector.

### 4.1. Safer Resolver Policies

- **Allow via registered IDs/catalogs** instead of accepting raw URLs or absolute paths directly from requests.
- The resolver maps IDs to **pinned group/artifact/version and immutable hashes**, trusted repositories, licenses, and transitive dependency lists.
- Verify hashes/signatures per policy; TLS protects transport, not content pinning.
- Validate the full dependency graph: no floating versions, unintended cycles, or libraries altering host API identities.
- Use a local cache with proper access permissions, verifying integrity even on cache hits.
- If network downloads are unnecessary during compilation, block egress so sources cannot abuse resolution to reach internal services.
- Apply SBOMs, vulnerability scanning, provenance, and reviews per operational requirements; never treat an automated scanner as proof a library is completely safe.

**Pinning a version does not equal pinning content** when a repository allows overwriting artifacts under the same version tag. Locking by hash and publisher origin is essential for reproducible builds.

### 4.2. Separating the Three Dependency Path Groups

| Group | Purpose | Privilege boundary |
| --- | --- | --- |
| **Compile classpath / module path** | Provides APIs and classes for compiler type resolution | Permitted dependencies only, version/hash pinned |
| **Processor path / processor module path** | Holds annotation processors executed during compilation | **Executable code** group requiring separate approval; disable if unneeded |
| **Compiler/build tool runtime** | JDK, `javac`, build plugins, and executed tools/helpers | Managed by platform; never let plugins pick executables/flags arbitrarily |

Using one shared JAR folder for every group blurs trust boundaries. In Java 17, if annotation processing is enabled **without declaring a separate processor path**, `javac` may search for processors on the user classpath. The safe default is **`-proc:none`** for tasks that do not need annotation-based code generation.

### 4.3. Classpath/Module Path Must Be Explicit

If `-classpath`/`--class-path` is omitted, `javac` may pick up `CLASSPATH` from the environment or current directory. That exposes libraries outside the approved manifest to the compiler. Therefore, always pass a **host-constructed classpath**, never relying on the worker's ambient environment.

For explicit JPMS modules, use a controlled **`--module-path`**, checking module names, `requires`, `exports`, and avoiding split packages. Never wildcard-include every library on disk when policy permits only a specific artifact set; never rely on an accidental host class loader to define the dependencies source may reference.

When preparing to compile untrusted input, also check **source path**: if the compiler defaults to searching for additional `.java` files on the classpath, a compilation task can pull in sources outside the request list. Point **`-sourcepath`** to an approved source directory or an empty directory when compiling in-memory sources, and verify the actual output artifacts afterward.

## 5. Annotation Processors and Compiler Plugins: The Heart of Compile-Time Risk

Annotation processing is not merely metadata reading. An implementation of **`javax.annotation.processing.Processor`** is a Java class containing code that the compiler can load, instantiate, and invoke while processing annotations. It can generate sources or resources, access the filesystem, use the network, or run complex logic with the privileges of **the compiler process**.

### 5.1. How Can a Dependency JAR Become a Processor?

A JAR may contain the file:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

Its contents name a `Processor` implementation class. This is the Service Provider mechanism allowing `javac` to discover annotation processors whenever annotation processing is active and the processor search path allows it.

Suppose an app uploads a library solely because its source references an annotation. If the compiler scans the classpath as its default processor path, a library registering a processor can trigger **processor code execution at compile time**, even if the host never calls that library's methods post-build.

Do not equate every library containing annotations with executable code: **an annotation is only metadata**, whereas a **processor** is a program running inside the compile environment. Risk arises when the tool is configured to discover and invoke processors.

### 5.2. Configuration Choices

**No annotation processing needed:**

~~~text
-proc:none
~~~

On **Java 17 `javac`**, this option disables annotation processing for the compilation run. This should be the default for ordinary plugin sources when business logic does not require processors.

**When a trusted processor must run:**

~~~text
-processor com.example.approved.SafeProcessor
-processorpath /approved/processors
~~~

These two lines are **illustrative options**, not a standalone `javac` command. For modular projects, `--processor-module-path` may be needed instead of the classic processor path. The host must pin exact processor artifacts, dependencies, and allowed processor options. Specifying `-processor` selects which processor runs, yet **does not make an untrusted processor safe**.

**Never** accept arbitrary processor class names, processor paths, or `-Akey=value` options from unprivileged users. Some processors read files or configs based on options; `-A` values must also be validated against a schema if the host chooses to support them.

### 5.3. Compiler Plugins and Build Tools

Beyond annotation processors, there are `javac` plugins and other build-time code-execution mechanisms:

- **`-Xplugin`:** the compiler plugin mechanism in `javac` builds that support it. Permit plugins strictly from the approved toolchain, never from source requests.
- **Maven/Gradle plugins, tasks, and scripts:** letting users upload `pom.xml` or `build.gradle` and executing them fully allows a custom build program to run inside the worker. Validating Java source does not control this.
- **Code generators / native tools:** protobuf/thrift/codegen tools, shell/PowerShell scripts, and formatters/analyzers capable of executing code require an allowlist of executables and permitted arguments.
- **`javac` runtime flags:** JVM flags or internal module openings can alter the tool's runtime environment; never pass through a raw list of user-supplied compiler flags.
- **Custom file managers:** the `JavaCompiler` API allows applications to install custom `JavaFileManager` and `JavaFileObject` implementations. An untrusted implementation could read/write data when invoked by the compiler; it must stay inside the reviewed boundary as well.

Do not set `-proc:none` and assume other plugins/build scripts are disabled. **`-proc:none` only governs annotation processing**; it has no blanket effect on external toolchain activity.

### 5.4. Compile-Time Execution Assessment Table

| Input / tool | Can run code during compile? | Policy |
| --- | --- | --- |
| Ordinary Java source parsed by `javac` | **Does not automatically run source static initializers or `main`** | Validate and bound resources; output must not auto-run |
| Processor discovered by `javac` | **Yes** | Disable with `-proc:none` or allowlist approved processors |
| Enabled `javac` plugin | **Yes** | Forbid arbitrary options; pin plugins from trusted toolchain |
| Build script / task / plugin | **Yes** | Never run user-uploaded build files in a privileged host; use platform-defined pipelines |
| External code generator | **Yes** | Approved binaries/versions/args running inside isolated workers |
| Dependency JAR solely on compile path, not a processor/plugin | Normally read for type resolution; **does not auto-call business code** | Still verify provenance, hashes, class identity, and tool bugs |
| `.class` bytecode produced after compile | **Does not auto-run merely because files were created** | Inspect artifacts; load/execute in a separate trust-boundary phase |

This table does not promise parsers or compilers are bug-free; a compiler is still a complex program processing untrusted input, requiring patching and worker-level isolation.

## 6. Controlling the Compiler/Toolchain: Capabilities, Versions, and Options

### 6.1. Select Tools via Policy, Not via Source Requests

A trustworthy build definition should pin:

- JDK distribution and patch version, e.g., organization-supported JDK 17.x.
- Binary/compiler implementation path and checksum/container image digest.
- Bytecode target via **`--release 17`** or the target matching the supported runtime.
- **UTF-8** encoding; worker locale/timezone when reproducible builds are needed.
- Classpath, module path, source path, and processor path from an approved manifest.
- Dedicated output root, workspace file permissions, and temporary-file cleanup rules.
- Limits on CPU/RAM/disk/process count/time/network and secret access.
- Policies for compiler diagnostics, caches, and artifact publication.

With the Java Compiler API, obtain the compiler via:

~~~java
JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
if (compiler == null) {
    throw new IllegalStateException(
            "Runtime does not provide a system Java compiler");
}
~~~

This snippet goes inside a method importing `javax.tools.JavaCompiler` and `javax.tools.ToolProvider`. On Java 17, **`javax.tools`** resides in module **`java.compiler`**, while the system compiler implementation is provided by **`jdk.compiler`** when available. A custom runtime image may run Java yet omit the system compiler; the `null` branch must report **`TOOLCHAIN_UNAVAILABLE`** or a configuration failure, never masquerading as a source syntax error.

### 6.2. Proper Uses and Limits of Common Options

| Option | Intended purpose | What not to misread into it |
| --- | --- | --- |
| **`--release 17`** | Compile targeting API/language/bytecode of the supported release | Does not restrict code privileges once executed |
| **`-encoding UTF-8`** | Parse source with a stable encoding | Does not make source trustworthy |
| **`-proc:none`** | Disable annotation processing in `javac` | Does not disable all plugins/codegen or prevent compiler resource exhaustion |
| **`-classpath` / `--class-path`** | Specify library/class lookup for classpath compilation | Not an OS sandbox or automatic verified dependency list |
| **`--module-path`** | Specify module lookup when compiling modules | Does not verify provenance/trust of module JARs |
| **`-sourcepath`** | Restrict where other sources are found when needed by the compiler | Does not stop path traversal if tool inputs/outputs are arbitrary |
| **`-d`** | Place generated bytecode into the specified output directory | Does not guarantee output stays sandboxed if workspace is tampered with |
| **`-processorpath` / `-processor`** | Specify processors when intentionally enabling them | Not a defense against malicious processors |

When compiling user code, **never pass raw options straight through to the API**. A user must never supply flags altering processor paths, output paths, classpaths, plugin execution, or argfile reads.

### 6.3. Environment Variables You Must Not Overlook

When running `javac` as a **separate process**, environment variables can affect the launcher and tool. For instance, **`JDK_JAVAC_OPTIONS`** is read by `javac` to prepend command-line options; **`JAVA_TOOL_OPTIONS`** and related launcher options can also alter how a new JVM starts. If a worker inherits an environment from a process containing tokens, proxies, or unwanted flags, passing a clean `argv` alone is insufficient.

With `ProcessBuilder`, construct a **minimal OS-appropriate environment** for the tool, actively stripping disallowed variables—especially those affecting compilers/launchers and secrets. Never wipe the entire environment blindly assuming `javac` works identically everywhere; give the worker a fixed set of variables tested on the target OS/locale.

**`JDK_JAVAC_OPTIONS` does not directly affect in-JVM `getTask` calls the way `javac.exe`'s CLI parser reads it**, whereas when the host spawns an external `javac` process, that variable is an input that must be controlled. Separating these two execution modes is essential for accurate policy design.

## 7. Compile In-JVM or in a Separate Process?

### 7.1. `JavaCompiler` API in the Same JVM

Advantages: in-memory inputs, structured diagnostics, custom `JavaFileManager`, and no per-compile process spawn overhead. Example:

~~~java
// ILLUSTRATIVE CODE: requires valid sourceFile and options objects.
JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
if (compiler == null) {
    throw new IllegalStateException("Compiler unavailable");
}
try (StandardJavaFileManager manager =
             compiler.getStandardFileManager(
                     diagnostics, Locale.ROOT, StandardCharsets.UTF_8)) {
    boolean success = Boolean.TRUE.equals(
            compiler.getTask(
                    null, manager, diagnostics,
                    options, null, List.of(sourceFile)).call());
}
~~~

This snippet is **not a standalone program**, as `diagnostics`/`options`/`sourceFile` are caller-supplied. This path fits **trusted sources or already-isolated workers**, yet creates no new security boundary between sources/processors and the host.

If an annotation processor or plugin from an untrusted party runs, that code can inherit the privileges of the JVM/compiler. A memory-hungry compilation task can also affect the host JVM directly; the `JavaCompiler` API provides no per-`CompilationTask.call()` timeout or heap quota parameter.

### 7.2. Carefully Configured Separate Process

Use `ProcessBuilder` with an **argument list**, **never concatenating a command line into a shell string**, to avoid shell metacharacter interpretation from filenames or arguments.

~~~java
// STRUCTURAL ILLUSTRATION, NOT A STANDALONE PROGRAM.
// javacPath, approvedClasspath, sourceFile, outputDir, workDir
// are all created and verified by the HOST; never taken raw from users.
ProcessBuilder builder = new ProcessBuilder(
        javacPath.toString(),
        "--release", "17",
        "-proc:none",
        "-encoding", "UTF-8",
        "-classpath", approvedClasspath.toString(),
        "-d", outputDir.toString(),
        sourceFile.toString());
builder.directory(workDir.toFile());

// Before builder.start(): apply environment allowlist,
// handle stdout/stderr, filesystem permissions, network, quotas, and timeout.
~~~

**`ProcessBuilder` only solves passing `argv` without a shell; it is not a sandbox itself.** The compiler process still carries the OS privileges of the account running it. Do not grant the worker access to host directories, networks, or secrets unnecessarily; use dedicated users/processes/containers, restricted mounts, and egress controls.

Process management must:

1. Enforce wall-time, CPU, memory, process-count, and output-size limits **from the OS/container**.
2. Drain stdout/stderr concurrently or redirect them to bounded sinks. Calling `waitFor` without draining full pipes can deadlock the process and cause spurious timeouts.
3. On timeout, record **`TIMEOUT`**; terminate the process **and its child processes** per policy, rather than assuming a single `destroyForcibly` handles the entire process tree.
4. Protect cleanup if the parent crashes; use supervisor/worker leases and post-failure workspace reclamation.
5. Never publish artifacts if the compiler exit code is non-zero, the task was cancelled, or output validation fails.
6. For untrusted sources, consider workers with **no network**, no secrets, and write permissions limited strictly to the assigned output/workspace.

**Important:** even with `-proc:none` and file-based source input, merely moving into a subprocess running under an account with full host privileges is not a meaningful trust boundary. The true boundary lies in OS privileges, filesystem isolation, resource limits, and verified artifact publication paths.

## 8. Standalone Java 17 Example: Compiling Fixed Input Under Minimal Policy

This example shows **how to configure `JavaCompiler` properly** before building a full service. It compiles only **trusted hardcoded source**, executes no bytecode, loads no external dependencies, disables annotation processors, and deletes outputs after checking.

**Never use this in-process example to compile stranger-supplied source on a production host.** It only demonstrates API control points; real isolation and quotas belong in a worker as covered in section 7.

### 8.1. File `CompilationBoundaryDemo.java`

~~~java
import java.io.IOException;
import java.net.URI;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Comparator;
import java.util.List;
import java.util.Locale;
import java.util.stream.Stream;

import javax.lang.model.SourceVersion;
import javax.tools.Diagnostic;
import javax.tools.DiagnosticCollector;
import javax.tools.JavaCompiler;
import javax.tools.JavaFileObject;
import javax.tools.SimpleJavaFileObject;
import javax.tools.StandardJavaFileManager;
import javax.tools.ToolProvider;

public final class CompilationBoundaryDemo {
    private static final String BINARY_NAME =
            "demo.generated.SafeValue";

    private static final String SOURCE = """
            package demo.generated;

            public final class SafeValue {
                public static String value() {
                    return "OK";
                }
            }
            """;

    private CompilationBoundaryDemo() {
    }

    public static void main(String[] args) throws Exception {
        // Runtime capability, unrelated to source syntax.
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null) {
            System.out.println("compiler=unavailable");
            return;
        }
        System.out.println("compiler=available");

        validateInput(BINARY_NAME, SOURCE);
        System.out.println("source=accepted");

        // Workspace not shared with other compilation runs.
        Path workspace = Files.createTempDirectory(
                "compile-boundary-demo-");

        try {
            Path output = Files.createDirectories(
                    workspace.resolve("classes"));
            Path emptyDependencies = Files.createDirectories(
                    workspace.resolve("empty-dependencies"));

            DiagnosticCollector<JavaFileObject> diagnostics =
                    new DiagnosticCollector<>();

            JavaFileObject sourceFile =
                    new InMemorySource(BINARY_NAME, SOURCE);

            List<String> options = List.of(
                    "--release", "17",
                    "-encoding", "UTF-8",
                    "-proc:none",
                    "-classpath", emptyDependencies.toString(),
                    "-sourcepath", emptyDependencies.toString(),
                    "-d", output.toString()
            );

            boolean ok;
            try (StandardJavaFileManager manager =
                         compiler.getStandardFileManager(
                                 diagnostics,
                                 Locale.ROOT,
                                 StandardCharsets.UTF_8)) {

                JavaCompiler.CompilationTask task =
                        compiler.getTask(
                                null,
                                manager,
                                diagnostics,
                                options,
                                null,
                                List.of(sourceFile));

                ok = Boolean.TRUE.equals(task.call());
            }

            System.out.println("compile=" +
                    (ok ? "success" : "failure"));

            if (!ok) {
                for (Diagnostic<? extends JavaFileObject> d
                        : diagnostics.getDiagnostics()) {
                    System.err.println(
                            d.getKind() + "@line=" +
                            d.getLineNumber());
                }
                return;
            }

            Path classFile = output.resolve(
                    "demo/generated/SafeValue.class");
            System.out.println(
                    "artifact=" + Files.isRegularFile(classFile));
            // Intentionally DO NOT load or execute the generated bytecode.
        } finally {
            deleteRecursively(workspace);
        }
    }

    private static void validateInput(
            String binaryName, String source) {

        if (!binaryName.startsWith("demo.generated.")) {
            throw new IllegalArgumentException(
                    "Namespace is not permitted");
        }
        for (String part : binaryName.split("\\.", -1)) {
            if (!SourceVersion.isIdentifier(part)
                    || SourceVersion.isKeyword(part)) {
                throw new IllegalArgumentException(
                        "Invalid Java binary name");
            }
        }
        if (source.length() > 16_000) {
            throw new IllegalArgumentException(
                    "Source exceeds demo character limit");
        }
    }

    private static void deleteRecursively(Path root)
            throws IOException {
        try (Stream<Path> paths = Files.walk(root)) {
            for (Path path : paths
                    .sorted(Comparator.reverseOrder())
                    .toList()) {
                Files.deleteIfExists(path);
            }
        }
    }

    private static final class InMemorySource
            extends SimpleJavaFileObject {

        private final String code;

        InMemorySource(String binaryName, String source) {
            super(URI.create(
                    "string:///" +
                    binaryName.replace('.', '/') +
                    Kind.SOURCE.extension),
                    Kind.SOURCE);
            this.code = source;
        }

        @Override
        public CharSequence getCharContent(
                boolean ignoreEncodingErrors) {
            return code;
        }
    }
}
~~~

### 8.2. Run Command and Stdout

Save the file with the exact name **`CompilationBoundaryDemo.java`** in UTF-8. Open a terminal in the file's directory using a full JDK 17:

~~~bash
javac --release 17 -encoding UTF-8 CompilationBoundaryDemo.java
java CompilationBoundaryDemo
~~~

**Expected stdout on a full JDK 17 with permission to create/delete temp directories and a working compiler:**

~~~text
compiler=available
source=accepted
compile=success
artifact=true
~~~

If the example's class files were pre-built and run on a runtime **that includes the `java.compiler` API but provides no system compiler**, the expected branch is:

~~~text
compiler=unavailable
~~~

These are two different runtime environments, not outputs of the same run. If the system disallows writing temp directories or the compiler hits an infrastructure error, the program may throw an exception; such errors must be classified separately in production apps.

### 8.3. What Does Each Measure in the Example Achieve?

**`validateInput`** checks a simple namespace, binary name segments, and character length for a fixed source. It illustrates ingress validation, yet **remains incomplete for a real upload system**: UTF-8 byte limits, file count caps, path traversal, ZIP entries, request origin, and authorization still need to be implemented.

**`InMemorySource`** supplies compilation input as a host-constructed `JavaFileObject`, rather than an arbitrary request path. The file manager can still touch the filesystem with process privileges and the compiler can still consume resources, so **in-memory input does not turn compilation into a sandbox**.

**`--release 17`** fixes the Java 17 target, **`-encoding UTF-8`** avoids environment encoding drift, **`-proc:none`** disables annotation processing, and **`-classpath`** and **`-sourcepath`** point to empty host-created directories to avoid silently falling back to `CLASSPATH`/current directory. When compiling real projects with dependencies, replace the empty directory with **the verified artifact set**.

**`-d`** separates outputs from inputs. Each task gets a fresh output root, preventing stale `.class` files from earlier builds. Use **`Boolean.TRUE.equals(task.call())`** to read the result, while diagnostics capture error kinds and locations without assuming verbatim messages stay identical across JDKs/vendors/locales.

**Never load compiled classes automatically:** producing `.class` files and executing code are two distinct phases. The example only verifies that the class file exists. For untrusted plugins, the execution phase needs a dedicated process/container boundary rather than treating `URLClassLoader` as sufficient isolation.

**Cleanup** runs in `finally` after closing the manager. Production systems also need orphan workspace cleanup when a process crashes, handling deletion errors, and ensuring cleanup exceptions do not mask important build results.

## 9. Why Do Some Seemingly Safe Configurations Fall Short?

### 9.1. Using `-proc:none` Alone

This option indeed disables `javac` annotation processors for the compilation. However, it does not disable build scripts, `javac` plugins enabled by other flags, native code generators, or toolchain steps invoked before/after `javac`. Nor does it cap parser CPU/RAM or protect the post-compile class-loading stage.

Thus `-proc:none` is a **targeted protective layer**, not the entire security policy.

### 9.2. Filtering Source with Regex Alone

Filtering keywords like `Runtime`, `ProcessBuilder`, or `java.io` does not make code safe; Java offers reflection, libraries, language constructs, and countless alternative expressions. Before executing bytecode, the system must enforce isolation grounded in real privileges. Static analysis and API allowlists provide extra signals, not a replacement for OS sandboxes.

### 9.3. Using `ProcessBuilder` Without a Shell Alone

Argument arrays prevent many traditional shell-quoting and injection flaws, yet **`javac` still has its own argument semantics**, such as `@filename` argfiles and other compiler flags. Letting users control `argv` enables reading files or altering compilation behavior even without a shell.

The fix is for the host to construct **the entire option vector** from typed/validated parameters; never append raw `compilerArg` values to the command. Process and filesystem permissions must still be restricted alongside it.

### 9.4. Using `--release 17` Alone

`--release` controls API/language targeting; it does not forbid importing code from dependencies the host placed on the classpath, does not disable annotation processors, and does not restrict runtime privileges. Use it to guarantee bytecode compatibility, **not as a sandbox policy**.

### 9.5. Using Only a Separate Temp Directory per Request

Separate directories prevent builds from overwriting one another, yet offer no protection if the compiler process still has permission to read home directories, credentials, or other tenants' files. The file environment needs dedicated worker ownership, mounts, and permissions; the process must not inherit broad host privileges.

### 9.6. Checking Only Whether Compilation Succeeded

`CompilationTask.call()` returning `true` means the tool considers compilation successful; **it does not mean the artifact is safe, belongs to the right tenant, is authorized to load, or matches the host API**. Before publishing, verify output origin, structure, hashes, policies, and module/class metadata where possible. Never treat compilation success as approval for runtime execution.

## 10. Managing Output: From `.class` Files to Approved Artifacts

Outputs should be generated in an **isolated temporary area** and promoted to a registry only after a separate verification step:

1. Attach job ID, tenant ID, source digest, dependency manifest digest, compiler image digest, and the applied policy.
2. Create a fresh output directory; never share output directories across jobs or reuse stale files.
3. Bound total `.class`/`.jar` size, file counts, package names, and entry counts; never follow symlinks.
4. Verify all outputs reside inside the permitted workspace; never write sources or outputs across untrusted shared directories.
5. Check bytecode/JAR structure and main/provider metadata if required by the plugin contract. Never treat bytecode verification as malware detection.
6. Publish the artifact only when **compile succeeds, output validation succeeds, provenance is complete, and policy approves**.
7. Record checksums / content-addressed artifact IDs so later download and activation verify exact bytes.
8. Never mix outputs between jobs; roll back strictly using recorded artifacts rather than reusing tampered temp files.

Note: matching Java package names and binary names does not prove a provider implements the host's interface properly. That belongs to the next **API compatibility validation** step inside an isolated environment. Never load a provider into a production JVM "just to test it" while the code remains untrusted.

### Build Reproducibility and Artifact Recipes

An attestation record can describe:

~~~text
BuildIdentity =
  SHA-256(source manifest + normalized contents)
  + SHA-256(dependency lock manifest)
  + compiler image/version digest
  + normalized compiler options
  + build policy revision

PublishedArtifact =
  artifact SHA-256 + BuildIdentity + diagnostics/attestation
~~~

This is a **conceptual diagram**, not a standardized hash formula: real implementations must use canonical serialization, explicit signing/hashing algorithms, and avoid ambiguous string concatenation. Two compilations do not always yield byte-for-byte identical outputs when timestamps, non-deterministic processors, resource ordering, or non-reproducible tools are involved. Recording provenance aids auditing, while actual reproducibility must be tested.

## 11. Real-World System Scenarios: Extending the Minimal Example

### 11.1. Host Only Needs to Compile Simple Interface Implementations

For sources generated from trusted host-controlled templates, many setups can run the `JavaCompiler` API inside a managed worker process. Never let users pick compiler flags; dependencies are pinned API artifacts, processors default to off, and outputs stay isolated. Artifacts then flow into a separate plugin activation step.

If sources are genuinely written externally and untrusted, run the compiler inside a **low-privilege worker** even with processors disabled, because the compiler still processes complex inputs and can consume substantial resources.

### 11.2. Plugins Requiring Annotation Processors

You cannot simply re-enable annotation processing while keeping old assumptions. You need a policy:

1. Confirm the plugin's codegen need and the required processor.
2. Approve processor artifacts and dependencies separately from compile dependencies; pin versions/hashes and privileges.
3. Run the processor inside an isolated worker with quotas, no secrets, and restricted networking.
4. Specify exact `-processor`, processor path/module path, and allowed `-A` options.
5. Constrain processor-generated files, total output volume, and write locations.
6. Record processor identity in the build attestation.
7. Test failure modes and non-deterministic behavior; a processor can emit different sources across processing rounds.

If a processor requires special network or file-write access, treat that as **an explicit, approved capability**, never granted automatically merely because a dependency declared a processor.

### 11.3. Plugins Submitting Entire Maven/Gradle Projects

This differs completely from submitting individual Java files. A build project can contain scripts and executable plugins/tasks. The host must never shell out to **`mvn`** or **`gradle`** on user build files inside an account holding secrets merely because the Java source passed validation.

Architectural options:

- Accept **sources + a schema-restricted dependency manifest**, letting the platform generate fixed build scripts/tasks.
- Or, if arbitrary build projects must be supported, run them inside a **strongly isolated build worker** with restricted privileges and networking, no mounted host secrets or sensitive caches, quotas/timeouts, and artifact verification policies.
- Pin Maven/Gradle distributions, settings, plugin repositories, dependency repositories, and corresponding checksums.
- Never allow builds to reach Docker sockets, the host filesystem, cloud credentials, or internal networks.

Do not confuse dependency resolution with dependency execution: a Gradle plugin or Maven plugin has authority to execute code inside the worker, unlike `javac` merely reading a JAR for type resolution.

## 12. Logging, Diagnostics, and Typed Results

A system should classify failures rather than returning a generic boolean:

| Result code | Stage | Meaning |
| --- | --- | --- |
| **`INPUT_REJECTED`** | Ingress | Bad schema, quota exceeded, disallowed package/path |
| **`DEPENDENCY_REJECTED`** | Resolve | Artifact/version/hash or transitive graph violates policy |
| **`TOOLCHAIN_UNAVAILABLE`** | Prepare compiler | Missing compiler/JDK image or invalid binary |
| **`TOOL_POLICY_REJECTED`** | Prepare task | Unapproved processor/plugin/option or executable |
| **`COMPILATION_FAILED`** | Compile | Source failed to compile; diagnostics meant for the author |
| **`COMPILER_TIMEOUT`** | Compile worker | Resource/time budget exhausted; clean up process tree and outputs |
| **`INFRASTRUCTURE_ERROR`** | Worker/I/O | Failure in file manager, temp workspace, disk, permitted network, or cleanup |
| **`ARTIFACT_REJECTED`** | Post-build | Output exceeds limits or fails structure/hash/provenance checks |
| **`APPROVED`** | Publish | Artifact eligible for storage; **not automatically executed** |

When `ToolProvider.getSystemJavaCompiler()` returns `null`, report **`TOOLCHAIN_UNAVAILABLE`**, never confusing it with `COMPILATION_FAILED`. When `JavaCompiler.getTask(...).call()` returns `false`, report `COMPILATION_FAILED` and collect `DiagnosticCollector`. An `IOException` or `RuntimeException` in the worker may be `INFRASTRUCTURE_ERROR`, classified carefully by context without masking unexpected failures.

### Diagnostics Are Not Verbatim Public Logs

Diagnostics can contain **source paths, filenames, line/column numbers, code excerpts, and dependency details**. Cap message counts and sizes, strip server paths/secrets before returning, and avoid dumping raw command lines or full environments into client logs.

Log by job ID / tenant ID with appropriate access controls:

~~~text
job=build-42
tenant=tenant-a
stage=compile
toolchain=approved-jdk17-digest
processors=disabled
dependency-lock=sha256:...
source-count=2
outcome=COMPILATION_FAILED
diagnostics-count=3
artifact-published=false
~~~

The lines above are merely an **illustrative log example**, not stdout from section 8's program. Logs must retain enough detail to reproduce failures without leaking sources or tokens to other tenants.

## 13. Mandatory Pre-Deployment Test Cases

Separate tests into **unit validation**, **compiler integration**, and **isolation/system tests**.

### 13.1. Validation and Dependency Policy

- Empty sources, byte limits exceeded, too many files, class names with invalid segments, or forbidden namespaces.
- ZIP uploads with traversal entries, absolute paths, symlinks, duplicate names after normalization, and decompression ratios exceeding quotas.
- Unapproved dependency IDs, hash mismatches, floating dependency versions, or transitives absent from lockfiles.
- User attempts to pass raw flags, processor paths, output directories, or shell scripts in the request schema: **`INPUT_REJECTED`/`TOOL_POLICY_REJECTED`**.
- Two tenants using the same binary name concurrently: workspaces/outputs/caches never overwrite one another.
- User submits valid source whose package/class mismatches metadata: reject or report a clear compile error without silently renaming.

### 13.2. Toolchain and Compiler Behavior

- Full JDK 17 with system `JavaCompiler`: valid internal source compiles cleanly.
- Custom runtime image omitting `jdk.compiler`: `getSystemJavaCompiler()` returns `null`, reporting `TOOLCHAIN_UNAVAILABLE`.
- Source with syntax errors: `task.call()` returns `false`, diagnostics collected, no artifact published.
- Missing dependency: compiler reports missing type without scanning libraries outside the allowlist.
- JAR registering an annotation processor while configured with `-proc:none`: processor is never invoked.
- Processor allowlist mode: only approved processors run inside an isolated worker.
- User-supplied values never enter `argv` as options; weird filenames and shell metacharacters do not alter tool behavior.
- Compiler process receives a scrubbed environment unaffected by tenant-injected `JDK_JAVAC_OPTIONS`.
- Output artifact altered between compile and publish: hash/ownership check rejects it.

### 13.3. Resource Isolation and Failure Handling

- Long compiler loop or high RAM usage: worker is throttled/killed per policy; main host keeps serving other requests.
- Oversized output, full disk, or file manager failure: returns accurate code, cleans workspace, never publishes partial artifacts.
- Process timeout: reclaims the entire process tree, leaving no surviving subprocess consuming resources.
- Worker crash mid-compile: scheduler marks job failed; janitor cleans orphaned temps/artifacts.
- No network / no tokens: any tool/plugin probing unauthorized destinations is blocked by OS/network policies.
- Rollout of built artifacts: loaded/tested inside the proper plugin runtime zone, never treating compile security policies as a runtime sandbox.
- JDK minor upgrades, dependency updates, or processor updates: rerun reproducibility/test matrix prior to release.

**Distinguish validator-enforced tests from isolation-enforced tests.** A unit test showing a regex rejection is useful, yet does not prove a process container blocks filesystem/network access or cleans up child processes.

## 14. Common Configuration Mistakes and Fixes

| Symptom | Possible cause | Priority fix |
| --- | --- | --- |
| Annotation processor runs unexpectedly | `javac` scans user classpath as processor path | Use `-proc:none`; if processors are needed, dedicated path/allowlist |
| Build reads libraries outside allowlist | Falls back to default `CLASSPATH` / current directory | Explicitly set classpath/module path/source path from fixed manifest |
| Uploaded source writes outside build directory | Trusts raw filenames or extracts ZIP unchecked | Derive paths from validated binary names; check filesystem/symlinks/quotas |
| `JavaCompiler` returns `null` | Runtime lacks `jdk.compiler` | Use appropriate toolchain image and return `TOOLCHAIN_UNAVAILABLE` |
| Compile errors misreported as missing compiler | Conflates `false`/exceptions/`null` | Separate capability, diagnostics, and infrastructure status |
| Users can pass `-processor` or `-Xplugin` | Uncontrolled raw tool flags | Use host-owned schemas and option builders |
| Network-fetched dependency JAR trusted implicitly | No pinned checksum/provenance | Approved repositories + lock manifests + hashes |
| Compile process can read secrets | Worker uses host privileges and environment | Least privilege, sanitized env, no secrets, mount/net isolation |
| Output mixes classes from previous builds | Reuses output directories | Fresh output per job; verify and publish by job ID |
| Process times out yet child stays alive | Kills only top-level process | Supervisor/process-group/container cleanup |
| Compile passes yet artifact causes runtime failure | Confuses compile success with runtime validation | Separate artifact review, API compatibility, activation sandbox |
| Build cannot be reproduced | Toolchain/dependencies/options unpinned | Build identity, digests, manifests, normalized configs |
| Security checks done solely via source regex | Ignores compiler plugins/build scripts/isolation | Threat-model sources, tools, deps, and runtime together |

## 15. Plugin Compilation Control Checklist

**Before accepting input**

- Authenticate tenant/compile permissions; enforce rate limits and quotas.
- API accepts only schema-constrained metadata; reject raw shell commands / compiler `argv`.
- Validate source count, UTF-8 bytes, binary names, package allowlists, depth, and total size.
- If input is an archive, block traversal, symlinks, duplicate entries, and decompression bombs.

**Before resolving dependencies**

- Accept only permitted dependency IDs; pin transitive graphs, versions, and hashes.
- Verify repository/provenance and cache ownership; never expose internal networks.
- Separate compile classpath/module path from processor path and build-tool runtime.
- Ensure shared host APIs cannot be arbitrarily shadowed/redefined by plugins.

**Before running the compiler**

- Use an approved compiler/JDK image with pinned version/digest and controlled environment.
- Check `ToolProvider` is non-null or verify the worker's `javac` executable.
- Build explicit options: `--release`, encoding, classpath/module path, source path, output path.
- **`-proc:none` when annotation processors are unneeded**; if needed, pin and allowlist processors separately.
- Reject user-supplied `-Xplugin`, argfiles, JVM flags, or unapproved codegen tasks.
- Run inside a low-privilege process/container for untrusted sources; no secrets, restricted network.
- Enforce CPU/memory/disk/time/process limits and handle timeouts/process trees.

**After compilation**

- Distinguish `null` compiler, `false` source compilation, worker exceptions, and timeouts.
- Collect bounded `DiagnosticCollector`/outputs while protecting internal paths and sensitive data.
- Close `JavaFileManager`/streams, clean up workspaces, and handle crash recovery.
- Verify all outputs belong to the job, match size/name/schema bounds, hashes, and provenance.
- Publish only approved artifacts; plugin loading and execution are governed by a separate boundary.

**Conclusion:** The compilation trust boundary **does not stop at the contents of `.java` files**. You must control **structured inputs**, **dependency graphs and JAR origins**, **code-executing processors/plugins/build tools**, **`javac` versions and options**, **process privileges and resource quotas**, and **generated artifacts**. Disabling annotation processing, passing explicit classpaths, and validating sources are necessary layers, yet **do not replace isolation for untrusted sources**. Separating compilation from activation keeps a runtime extensibility system flexible without handing host privileges to plugins through the build pipeline.
