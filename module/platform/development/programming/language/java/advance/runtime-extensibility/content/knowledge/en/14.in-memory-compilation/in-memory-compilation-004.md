# Loading Bytecode with a New Loader Sharing a Contract in the Parent Loader

## 1. Context and Goal

A Java extensibility system can receive source code at runtime (for example, business expressions, processing rules, or plugins whose source is generated by the system), compile the source into **in-memory bytecode**, and load the new classes without writing `.class` files to disk. The JDK provides `javax.tools.JavaCompiler` for compilation, `JavaFileObject`/`JavaFileManager` for capturing results, and `ClassLoader#defineClass` for defining classes from byte arrays.

However, "being able to load a class" **is not enough**. The host and plugin need a **shared communication contract** (API/SPI) so the host can safely cast instances, invoke methods, or register providers:

- **The host owns the contract**: for example, `demo.host.MemoryPluginDemo.Greeting` is loaded and defined by the host's class loader.
- **Each plugin load gets its own loader**: a new `PluginLoader` holds the bytecode of `demo.plugin.Hello` and defines that implementation.
- **The plugin loader's parent is the host's loader**: when the implementation references `Greeting`, default delegation resolves the exact **same Java type** that the host uses.
- **The compiler sees the host's actual contract**: at compile time, `JavaCompiler` must search the classpath/module path containing the shared API. The compiler succeeding and the JVM loading via the right loader are **two separate conditions**.
- **Do not redefine the contract in the child loader**: if the plugin creates its own copy of an identically named interface, `ClassCastException` or linkage errors can occur even when the source looks valid.

Within the scope of this lesson, the example runs with **JDK 17+, the Java classpath, and a shared interface**, requiring no external libraries. JPMS systems, `ModuleLayer`, or untrusted services require additional dedicated controls.

### 1.1. Overview Diagram

```text
                       HOST (application class loader)
             +---------------------------------------+
             | API/SPI: Greeting                     |
             | Code calling compiler + registry      |
             +---------------------------------------+
                                ^
                                | parent delegation
                   +------------+-------------+
                   |                          |
            PluginLoader A              PluginLoader B
            (new instance)              (new instance)
                   |                          |
            defineClass(...)             defineClass(...)
                   |                          |
            demo.plugin.Hello            demo.plugin.Hello
            greet() -> "hello-A"          greet() -> "hello-B"
                   |                          |
                   +--> implements same Greeting <--+
                        (defined by parent loader)
```

The two `demo.plugin.Hello` classes have the **same binary name**, but because they are defined by **two different defining loaders**, they are **two distinct runtime classes**. Yet both can implement the **same** `Greeting` because that interface comes from the parent loader. This is very useful when swapping plugin versions across reloads without changing the host's contract.

## 2. Distinguishing Compilation, Loading, Linking, and Initialization

You must view the processing pipeline stage by stage to diagnose errors accurately.

| Stage | Component | Output | Common errors |
| --- | --- | --- | --- |
| Source generation/intake | Host | Java source string | Invalid code, wrong imports |
| Compilation | `JavaCompiler` | Bytecode for one or more binary class names | Compilation diagnostics, missing API on classpath |
| Bytecode capture | `JavaFileManager` | `Map<String, byte[]>` | Missing auxiliary/anonymous classes, improper output handling |
| Loader creation | `new PluginLoader(parent, bytes)` | New loader with determined parent | Wrong parent choice, reference leaks |
| Loading/defining | `loadClass` / `findClass` / `defineClass` | A `Class<?>` with a specific loader identity | `ClassNotFoundException`, `NoClassDefFoundError`, `ClassFormatError`, linkage |
| Instance creation | Reflection / constructor | Java instance | `InvocationTargetException`, static initializer error, missing constructor |
| Contract usage | Cast to host API/SPI | Host calls typed methods | `ClassCastException`, `NoSuchMethodError`, incompatibility |

A new `ClassLoader` instance **does not automatically define** every class present in the bytecode map. When the host calls `loader.loadClass(binaryName)`, the delegation mechanism checks the parent and calls `findClass` to define the corresponding bytecode if the parent does not have that class.

**`loadClass` does not automatically initialize the class the way instantiating it does.** Invoking the constructor afterwards triggers the steps needed to run the class's code. Therefore, errors can surface during compilation, loading, linking, or constructor execution; do not lump every failure under a single "compilation failed" label.

## 3. JavaCompiler Components for Fully In-Memory Compilation

### 3.1. Obtaining the Compiler from the JDK

`ToolProvider.getSystemJavaCompiler()` returns the default compiler when the Java environment includes the tool. On a runtime without a compiler, the result can be `null`:

```java
JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
if (compiler == null) {
    throw new IllegalStateException("A JDK is required");
}
```

This is an **illustrative snippet**, requiring imports for `javax.tools.JavaCompiler` and `javax.tools.ToolProvider`. The complete program in section 5 has all imports and usage.

JavaCompiler is a compilation API, not an API for running code in a sandbox. When the compiler uses the wrong classpath, the source may fail to find the host interface or accidentally compile against a different version. You must explicitly specify the target Java version (e.g., `--release 17`) and which API libraries the compiler is permitted to reference.

### 3.2. Source Residing in JavaFileObject

So the compiler does not have to read physical `.java` files, we create a `SimpleJavaFileObject` of kind `Kind.SOURCE`, providing its content via `getCharContent`.

A URI such as `string:///demo/plugin/Hello.java` tells the compiler the virtual filename and maps to the binary name `demo.plugin.Hello`. This URI is **not a path where the JVM will automatically look up classes**; it is only an identifier for the compiler's file object.

Multiple source objects can be passed into a single compiler invocation. If a source produces inner classes, local classes, or multiple auxiliary classes, outputs can include multiple names such as `ClassName$Inner.class`, `ClassName$1.class`, etc. Never assume the compiler emits only one `.class` per source file.

### 3.3. Output Bytecode Residing in ByteArrayOutputStream

`JavaCompiler` asks the file manager where to write output for each class. By overriding `ForwardingJavaFileManager#getJavaFileForOutput`, we can return a `JavaFileObject` whose `openOutputStream()` writes into a `ByteArrayOutputStream`.

```text
getJavaFileForOutput(location, "demo.plugin.Hello", CLASS, sibling)
    -> Bytecode("demo.plugin.Hello")
        -> openOutputStream()
            -> byte[] representing demo.plugin.Hello
```

The bytecode map should be keyed by the **full binary name**, not just the simple filename. For example, `demo.plugin.Hello` is the name `ClassLoader.findClass(String)` receives; a key of `Hello` will not match.

`ByteArrayOutputStream` can be converted to a `byte[]` copy via `toByteArray()`. Do not pass externally mutable buffers into a loader without verifying ownership/immutability. For large systems, limit bytecode size, class count, and memory usage.

### 3.4. Standard FileManager Still Plays an Important Role

`StandardJavaFileManager` helps the compiler locate precompiled classes and dependent libraries on the classpath/module path. `ForwardingJavaFileManager` wraps this file manager to **intercept outputs** into memory while **preserving dependency reading** according to the compiler configuration.

Important distinctions:

- "In-memory compilation" in the example means **plugin source is a string and plugin output is a byte array**, without creating physical `.java`/`.class` files for that plugin.
- The host's API class is already on the classpath when running the demo; it is the shared contract, not a plugin artifact.
- If the compiler needs to see a class compiled **in an earlier pass that was never saved to disk**, overriding `getJavaFileForOutput` alone is not enough for all cases; you may also need input/listing mechanisms, a virtual classpath, or a single compiler task with multiple sources together.
- Annotation processors and the resources they generate may require additional overrides/configuration. The sample code focuses on a single simple Java source and `.class` output.

## 4. Role of the Parent Loader and the API/SPI Boundary

### 4.1. Why Must the Shared Interface Be Defined by the Parent?

In Java, class identity is bound to **binary name + defining class loader**. Two interfaces with the same name `com.example.spi.Task` defined by two different loaders are two distinct runtime types. Casting a plugin instance to the host's `Task` can fail if the implementation uses a different copy of the interface.

Under the normal policy of `ClassLoader.loadClass`:

1. Check if the class has already been loaded by that loader (`findLoadedClass`).
2. Try delegating to the parent loader.
3. If the parent does not find it, call the child loader's `findClass` to define the class locally.
4. Optionally resolve as requested before returning.

In plugin systems, this is the **parent-first** policy, appropriate when the host owns interfaces, DTOs, enums, exceptions, and callbacks across the boundary. Parent-first also means that **if the host accidentally contains the implementation class `demo.plugin.Hello`**, the parent may return the host's class instead of the new bytecode. Therefore, you must ensure the host classpath does not shadow implementation names, or design a child-first rule with **parent-only** exceptions for the shared contract.

### 4.2. Do Not Share Only the Main Interface

A realistic contract might look like:

```java
package com.example.api;

public interface Transform {
    Result apply(Request request) throws TransformException;
}
```

The snippet above only describes the architecture; `Request`, `Result`, and `TransformException` are not built-in Java classes. If the host and plugin need to exchange these types directly, **all of them** must belong to the shared API with the same class identity:

- Interfaces/abstract classes and base classes.
- DTOs, records, enums, and annotations crossing the boundary.
- Exceptions in method signatures, callbacks/listeners, and event types.
- Generic bounds or types exposed in method signatures.
- Any part of the host framework that the plugin actually uses as a contract.

You should not place only `Transform` in the parent and let the plugin define its own copy of `Result`. Every type meaningful across the boundary must be governed for identity and API version.

### 4.3. Rules Restricting Local Class Lookup

The demo loader checks:

```java
if (binaryName.startsWith("java.") || binaryName.startsWith("demo.host.")) {
    throw new ClassNotFoundException("Shared classes are parent-owned: " + binaryName);
}
```

This is an **excerpt from the complete program**. It prevents the plugin loader's `findClass` itself from defining bytecode inside those namespaces. However, default `loadClass` already asks the parent first; when the parent finds `demo.host.*`, the `findClass` branch does not run. The check in `findClass` is an extra guardrail if the parent reports not found, not a mechanism for validating that an artifact contains no forbidden classes.

A production system should **inspect the list of binary names as soon as it receives the bytecode map**, reject plugins attempting to define API packages or protected namespaces, and ensure the required contract actually exists in the parent. Do not try to "rescue" a contract missing from the parent by defining a copy inside the plugin.

### 4.4. One Class Name, Multiple Loaders

Plugin A and B can both define `demo.plugin.Hello`:

```text
PluginLoader A  --defines--> demo.plugin.Hello [version A]
PluginLoader B  --defines--> demo.plugin.Hello [version B]
Host loader     --defines--> demo.host.MemoryPluginDemo$Greeting
```

Then:

- `first.getClass() != second.getClass()` is **true**.
- `first instanceof Greeting` and `second instanceof Greeting` can both be **true**.
- You cannot cast an instance of A to B's implementation class; they are two distinct class definitions.
- The parent must provide the right version of the API. Shared identity does not by itself guarantee method ABI or behavioral compatibility.
- If you need to upgrade an already-loaded implementation, you typically create a **new loader**, rather than trying to call `defineClass` again with the same binary name in the old loader.

## 5. Runnable Java 17+ Example: Compile Source in Memory and Load with a Child Loader

Only **one Java source file on the host side** is needed. The program constructs the plugin source string itself, compiles it into memory with `JavaCompiler`, creates a new loader for each version, and casts the instance to the `Greeting` interface already present on the host.

Place the file at **`src/demo/host/MemoryPluginDemo.java`**:

```java
package demo.host;

import java.io.ByteArrayOutputStream;
import java.io.OutputStream;
import java.net.URI;
import java.nio.charset.StandardCharsets;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import javax.tools.DiagnosticCollector;
import javax.tools.FileObject;
import javax.tools.ForwardingJavaFileManager;
import javax.tools.JavaCompiler;
import javax.tools.JavaFileManager;
import javax.tools.JavaFileObject;
import javax.tools.SimpleJavaFileObject;
import javax.tools.StandardJavaFileManager;
import javax.tools.ToolProvider;

public final class MemoryPluginDemo {
    public interface Greeting {
        String greet();
    }

    private static final class Source extends SimpleJavaFileObject {
        private final String code;

        Source(String binaryName, String code) {
            super(URI.create("string:///" + binaryName.replace('.', '/') + Kind.SOURCE.extension),
                    Kind.SOURCE);
            this.code = code;
        }

        @Override
        public CharSequence getCharContent(boolean ignoreEncodingErrors) {
            return code;
        }
    }

    private static final class Bytecode extends SimpleJavaFileObject {
        private final ByteArrayOutputStream bytes = new ByteArrayOutputStream();

        Bytecode(String binaryName, Kind kind) {
            super(URI.create("mem:///" + binaryName.replace('.', '/') + kind.extension), kind);
        }

        @Override
        public OutputStream openOutputStream() {
            return bytes;
        }

        byte[] content() {
            return bytes.toByteArray();
        }
    }

    private static final class MemoryManager
            extends ForwardingJavaFileManager<JavaFileManager> {
        private final Map<String, Bytecode> outputs = new HashMap<>();

        MemoryManager(JavaFileManager delegate) {
            super(delegate);
        }

        @Override
        public JavaFileObject getJavaFileForOutput(
                Location location, String className, JavaFileObject.Kind kind,
                FileObject sibling) {
            Bytecode output = new Bytecode(className, kind);
            outputs.put(className, output);
            return output;
        }

        Map<String, byte[]> snapshot() {
            Map<String, byte[]> result = new HashMap<>();
            outputs.forEach((name, output) -> result.put(name, output.content()));
            return Map.copyOf(result);
        }
    }

    private static final class PluginLoader extends ClassLoader {
        private final Map<String, byte[]> classes;

        PluginLoader(ClassLoader parent, Map<String, byte[]> classes) {
            super(parent);
            this.classes = Map.copyOf(classes);
        }

        @Override
        protected Class<?> findClass(String binaryName) throws ClassNotFoundException {
            if (binaryName.startsWith("java.") || binaryName.startsWith("demo.host.")) {
                throw new ClassNotFoundException("Shared classes are parent-owned: " + binaryName);
            }
            byte[] bytes = classes.get(binaryName);
            if (bytes == null) {
                throw new ClassNotFoundException(binaryName);
            }
            return defineClass(binaryName, bytes, 0, bytes.length);
        }
    }

    private static Map<String, byte[]> compile(String binaryName, String code)
            throws Exception {
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null) {
            throw new IllegalStateException("A JDK is required");
        }
        DiagnosticCollector<JavaFileObject> diagnostics = new DiagnosticCollector<>();
        try (StandardJavaFileManager standard =
                     compiler.getStandardFileManager(diagnostics, null, StandardCharsets.UTF_8)) {
            MemoryManager files = new MemoryManager(standard);
            List<String> options = List.of(
                    "--release", "17", "-classpath", System.getProperty("java.class.path"));
            boolean ok = Boolean.TRUE.equals(
                    compiler.getTask(null, files, diagnostics, options, null,
                            List.of(new Source(binaryName, code))).call());
            if (!ok) {
                throw new IllegalStateException("Compile errors: " + diagnostics.getDiagnostics());
            }
            return files.snapshot();
        }
    }

    private static Greeting create(String value) throws Exception {
        String binaryName = "demo.plugin.Hello";
        String code = """
                package demo.plugin;
                public final class Hello implements demo.host.MemoryPluginDemo.Greeting {
                    public Hello() {}
                    @Override public String greet() { return "%s"; }
                }
                """.formatted(value);
        Map<String, byte[]> bytes = compile(binaryName, code);
        ClassLoader loader = new PluginLoader(MemoryPluginDemo.class.getClassLoader(), bytes);
        Class<?> type = loader.loadClass(binaryName);
        return (Greeting) type.getDeclaredConstructor().newInstance();
    }

    public static void main(String[] args) throws Exception {
        Greeting first = create("hello-A");
        Greeting second = create("hello-B");
        System.out.println("first: " + first.greet());
        System.out.println("second: " + second.greet());
        System.out.println("shared contract: " +
                (first.getClass().getInterfaces()[0] == Greeting.class
                && second.getClass().getInterfaces()[0] == Greeting.class));
        System.out.println("different plugin loaders: " +
                (first.getClass().getClassLoader() != second.getClass().getClassLoader()));
        System.out.println("different implementation types: " +
                (first.getClass() != second.getClass()));
        try {
            Class.forName("demo.plugin.Hello", false, MemoryPluginDemo.class.getClassLoader());
            System.out.println("host sees implementation: true");
        } catch (ClassNotFoundException expected) {
            System.out.println("host sees implementation: false");
        }
    }
}
```

### 5.1. Compile and Run

From the working directory containing `src`, using JDK 17 or newer:

```bash
javac --release 17 -d out src/demo/host/MemoryPluginDemo.java
java -cp out demo.host.MemoryPluginDemo
```

The host program is compiled into `.class` files in `out`; **only the plugin's bytecode** is dynamically compiled and kept in memory. It requires a JDK at runtime for `ToolProvider.getSystemJavaCompiler()` to work.

**Exact stdout verified with `javac --release 17` and `java`:**

```text
first: hello-A
second: hello-B
shared contract: true
different plugin loaders: true
different implementation types: true
host sees implementation: false
```

Meaning of the output:

1. `first: hello-A` and `second: hello-B`: the compiler ran twice with different sources; each bytecode was defined in a new loader so it did not overwrite the old implementation.
2. `shared contract: true`: the `Hello` class of both versions **references the exact `Greeting.class` of the host**; the host can cast to `Greeting` and call `greet()`.
3. `different plugin loaders: true`: the two instances were defined by two different loaders.
4. `different implementation types: true`: even though both classes share the binary name `demo.plugin.Hello`, they are not the same `Class<?>`.
5. `host sees implementation: false`: querying the host's class loader for the plugin implementation fails as expected; the child loader knows its own classes, but the parent does not automatically "look downward" to find classes defined by a child.

### 5.2. Why Doesn't the Example Create a Second Copy of Greeting?

`Greeting` is a public nested interface inside `MemoryPluginDemo`, so its actual binary name is `demo.host.MemoryPluginDemo$Greeting`. The compiler can resolve this interface via the host's classpath (`-cp out`). When the child loader defines `demo.plugin.Hello`, the default class loader mechanism favors the parent; it finds `Greeting` in the loader that defined `MemoryPluginDemo`.

Consequently, `(Greeting) type.getDeclaredConstructor().newInstance()` does not cause a `ClassCastException`. If the plugin itself defined bytecode with the binary name `demo.host.MemoryPluginDemo$Greeting` in another loader and the runtime actually used that separate copy, compatibility would break.

### 5.3. Intentional Limitations of the Example

- The strings `"hello-A"` and `"hello-B"` are fixed and trusted; the demo uses `String.formatted(value)` to generate Java source, which is **not** a safe Java string escaper for arbitrary input. For external input, you must generate properly escaped literals or separate data from source code.
- The example host classpath contains only the compiled source and contract. A production system needs to supply an **explicit, minimal classpath/module path** to the compiler; do not blindly use the entire `java.class.path` if doing so exposes internal dependencies or causes version skew.
- `MemoryManager` captures simple class outputs. A complex compiler workflow with annotation processors, generated resources, incremental compilation, or multiple in-memory dependencies may require an advanced file manager.
- The loader only overrides `findClass` and inherits **parent-first**; if an implementation class with the same name already exists on the parent's classpath, the parent can win. The demo assumes the host does **not** contain `demo.plugin.Hello`.
- The example uses the host's loader as parent and does not attempt to enforce strong security policies or run untrusted code.

## 6. Upholding the Contract When Bytecode Is Generated Repeatedly

### 6.1. Keep the Interface Stable, Swap the Implementation

The practical model is typically:

```text
host:
  api.PluginTask       -> parent loader, defined once
  PluginRegistry       -> stores api.PluginTask

compile generation #1:
  impl.TaskV1          -> pluginLoader#1
  impl.Helper          -> pluginLoader#1

compile generation #2:
  impl.TaskV2          -> pluginLoader#2
  impl.Helper          -> pluginLoader#2

PluginRegistry swaps implementation, keeps api.PluginTask contract unchanged
```

If you replace the bytecode of the **same binary name** `impl.Task`, you can still load two versions concurrently using two different loaders. Within the same loader, once `impl.Task` has been defined, you cannot simply update the map contents and expect `loadClass("impl.Task")` to return the new version. A `ClassLoader` caches loaded classes; redefining a name in the same loader is not a valid update mechanism.

### 6.2. The Shared API Must Be on the Compile-Time Classpath *and* in the Runtime Parent Loader

You should independently verify both sides:

- **Compile-time visibility:** which version of the API is the compiler reading? Does `-classpath` or `--module-path` point to the version the host expects? Does the compiler report incompatible methods/constructors?
- **Runtime identity:** are `Greeting.class.getClassLoader()` and the interface the implementation actually implements the exact same `Class<?>`? Is `Greeting.class.isAssignableFrom(type)` true?
- **Version compatibility:** sharing class identity does not by itself prove the API version supports the behavior the plugin expects. There should be version/capability metadata or a handshake to reject incompatible plugins.
- **Contract closure:** every DTO, enum, exception, callback, and event type crossing the boundary must share the same loader policy, not just the primary interface.

A runtime might compile successfully against one version of an API, yet at runtime load against an older version and hit `NoSuchMethodError` or linkage errors. You must test against the exact classpath and JDK of the deployment environment, not just the IDE.

### 6.3. Blocking Bad-Namespace Bytecode Before Defining

If enforcing namespace rules, the host can inspect `Map<String, byte[]>`:

```java
for (String name : compiledBytecode.keySet()) {
    if (name.startsWith("java.") || name.startsWith("demo.host.")) {
        throw new IllegalArgumentException("Plugin cannot define: " + name);
    }
}
```

This is an **illustrative snippet** requiring a `compiledBytecode` variable of type `Map<String, byte[]>` defined from the compilation result, not a standalone runnable program. In a real system, checking binary names from the map is useful but **insufficient** to validate the origin of bytecode: you should restrict allowed packages and evaluate class format, dependencies, and size. Do not use `defineClass` as a code-safety validator.

### 6.4. Parent-First vs. Child-First

The loader in the example inherits the parent-first algorithm. This is the right choice when:

- The parent owns `Greeting` and cross-boundary APIs.
- The host does not bundle plugin implementation classes.
- Private dependencies do not collide in name with the parent or are placed in separate namespaces.

If a plugin has a private library with the same name as one in the host but a different version, parent-first may pick the host's version by mistake. In that case you need a controlled child-first policy for **implementations and private dependencies**, while keeping **strict parent-only/parent-first** for the shared SPI. Switching everything to child-first without exceptions for the API usually creates hard-to-diagnose type-identity errors.

## 7. Stage-by-Stage Error Diagnosis

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| `getSystemJavaCompiler() == null` | Runtime does not provide a system compiler | Use a suitable JDK or provide another compiler strategy |
| Compiler says `Greeting` not found | Host API is missing from compiler classpath/module path | Pass the right paths; do not create ad-hoc copies |
| Compiler reports syntax errors | Invalid source string or Java version mismatch | Read `DiagnosticCollector`, line/column positions |
| Bytecode map is missing class names | File manager failed to record all `getJavaFileForOutput` calls or dropped outputs | Log binary names; handle multiple output classes |
| `ClassNotFoundException` | Wrong binary name, missing bytecode, or parent cannot see dependency | Verify map keys and the loader used for lookup |
| `NoClassDefFoundError` | A class needed during linking/initialization is absent, or earlier initialization failed | Inspect dependencies/cause, not only the main class |
| `ClassFormatError` / `VerifyError` | Bytecode invalid for the JVM | Do not define bytecode not accepted by the compiler/JVM |
| `ClassCastException` | Plugin loaded a duplicate copy of the contract with different class identity | Compare `Class<?>` and defining loaders of the SPI |
| `NoSuchMethodError` / `AbstractMethodError` | Compile-time API differs from runtime ABI | Pin API versions; test runtime dependencies |
| `InvocationTargetException` | Constructor/method invoked via reflection threw an exception | Inspect `getCause()` on the reflection error |
| `ExceptionInInitializerError` | Static initializer of the class failed | Preserve root cause; fix initialization logic |
| Loading new version always yields old logic | Reusing same loader/class or shadowed by parent | Create a new loader and check whether parent holds implementation names |
| Metaspace/memory grows continuously | Retaining old classes, instances, loaders, threads, registries, or caches | Manage lifecycles and drop unused references |

At the class-loading boundary, log at least: binary class name, bytecode origin, compilation hash/version, defining loader name, contract name, Java version, and exception cause. For dynamic sources containing sensitive information, do not log verbatim full sources in production.

You can quickly check identity:

```java
Class<?> implementation = pluginLoader.loadClass("demo.plugin.Hello");
System.out.println(implementation.getClassLoader());
System.out.println(Greeting.class.getClassLoader());
System.out.println(Greeting.class.isAssignableFrom(implementation));
```

This is an **integration illustrative snippet**, requiring `pluginLoader` and `Greeting` provided by the host. In the correct case, the implementation's loader normally differs from the contract's loader, yet `isAssignableFrom` is still true.

## 8. Resources, ServiceLoader, TCCL, and the Module System

### 8.1. Bytecode in a Map Is Not Equivalent to a Full Plugin JAR

Overriding `findClass` only handles loading **classes by binary name**. It does not automatically provide:

- `ClassLoader.getResource("config.yml")`.
- `getResources("META-INF/services/<service>")` for `ServiceLoader` to discover provider descriptors.
- Manifests, JAR signatures, or auxiliary library files.
- The ability for a subsequent compiler pass to reuse all bytecode loaded in the memory map as a standard classpath.

If a plugin needs resources, you must additionally implement a mechanism returning `URL`/resource streams or package outputs into an appropriate artifact, depending on the architecture. Do not equate class lookup order with resource lookup order.

### 8.2. ServiceLoader and Class Identity

If the host uses the service contract `Greeting` and discovers plugins with `ServiceLoader`, the provider **must implement the same `Greeting.class`** that the host passes to the loader. If the plugin creates a duplicate copy of the SPI in its own loader, service configuration errors can appear even when the descriptor lists the exact provider name.

The demo intentionally calls `loader.loadClass` and casts to highlight the parent-child mechanism, and does **not** call `ServiceLoader`. To use `ServiceLoader` over an in-memory bytecode map, you must additionally implement provider discovery (the `META-INF/services` resource or appropriate module design), rather than merely copying the code and expecting the loader to infer service names automatically.

Some frameworks also rely on the **thread context class loader (TCCL)**. Setting the TCCL to a plugin loader and forgetting to restore it causes thread pools to use the wrong classes/resources in subsequent tasks and retain references to the old loader. Whenever you must switch the TCCL for a synchronous call, use `try/finally` to restore the previous state.

### 8.3. JPMS and ModuleLayer

The example uses **unnamed modules/classpath** so the Java APIs remain simple and runnable standalone. With **named modules**, classes defined via `defineClass` into a custom loader do not automatically become a module with a `module-info.class` descriptor. `ModuleLayer` and `Configuration.resolve` are a separate workflow: locating modules, resolving the graph, and defining the layer along with corresponding loaders. Do not deduce that "compile into `byte[]` + `new ClassLoader`" completes module resolution on its own.

When using a shared SPI belonging to a named module, you must add appropriate `requires`, `exports`/`opens`, and module readability. Conversely, an API in an unnamed module and a plugin in a named module have distinct JPMS constraints; choose the right deployment model rather than applying a classpath demo to every runtime.

## 9. Security, Performance, and Lifecycle

### 9.1. Dynamic Code Is Not Safe Code

Compiling source in memory and loading it with a separate loader **does not create a security sandbox**. A plugin can call APIs permitted by the host/runtime, access files/network, or use reflection depending on the environment. `JavaCompiler` can also execute **annotation processors** present on the compiler path if configured/discovered under the active settings; those are executable code during build/compile time, not passive data.

For untrusted code sources, you must isolate at the OS/process boundary, restrict privileges, filesystem/network access, and resources, and bound execution time. You can pass `-proc:none` when annotation processing is unneeded to avoid running processors discovered by the compiler; however, that **does not** make executing plugin bytecode safe. A better strategy for business rules is a restricted DSL/grammar or execution inside a worker process with explicit quotas.

If user input is allowed, never interpolate it directly into a Java source string like `String.formatted(userInput)` without literal escaping and validation. In the demo, `value` only takes two known constants to keep the example easy to follow.

### 9.2. Bytecode Size, Time, and Memory

- Limit source length, number of output classes, bytecode size, and concurrent compilation tasks.
- Collect categorized diagnostics; avoid storing every source/bytecode in caches permanently if unnecessary.
- Separate the cost of **compilation** (CPU/heap) from **class loading/linking** (heap/metaspace) and **plugin execution** (CPU, I/O, memory).
- Cache by source hash + compiler options + API version where appropriate; do not treat source hash alone as proof that bytecode is compatible with a new runtime.
- Do not repeatedly create new loaders without bound for the same small request if the workload demands high throughput.

### 9.3. Unloading Is a Reference Problem

`ClassLoader` does not provide an immediate "delete defined class" operation. When upgrading:

1. Create a new loader and a new plugin instance.
2. Register the new instance and switch routing/callbacks in a controlled way.
3. Unregister the old instance.
4. Clean up tasks, listeners, threads, TCCL, and caches still holding references to old `Class<?>`/instances/loaders.
5. Allow GC to reclaim the loader and its classes once no strong references remain.

An instance of an old plugin remains usable if the host still holds it and the class has not been collected. This is a useful property for versioned transitions, but also a source of memory leaks when registries fail to release old versions.

## 10. Testing Checklist for a Runtime Compilation System

1. **API exists upfront:** `Greeting.class` must be defined by the host and accessible to the plugin's parent loader.
2. **Compiler targets the right API:** depends on classpath/module path and Java baseline; avoid accidentally compiling against another version.
3. **No plugin `.class` written to disk:** `getJavaFileForOutput` accurately captures the bytecode map, including nested/anonymous classes if any.
4. **Accurate binary names:** `demo.plugin.Hello` in the source, output map, and `loadClass` must match.
5. **Parent does not shadow implementation:** when new bytecode is needed, the host classpath does not contain an implementation with the same name, or the loader policy is designed accordingly.
6. **Contract runtime identity:** `Greeting.class.isAssignableFrom(type)` is true, casting to `Greeting` succeeds, and methods work.
7. **Two independent generations:** same binary name with different loaders produces distinct class identities.
8. **Missing dependencies:** compilation, loading, and runtime errors are clearly distinguished in logs.
9. **No loader leaks:** test repeated reloads and verify threads/caches/instances are reclaimed after version swaps.
10. **Do not treat ClassLoader as a sandbox:** govern source trust, annotation processors, execution privileges, quotas, and input escaping.

**Conclusion:** the right architecture for **"loading bytecode with a new loader sharing a contract in the parent loader"** is: compile plugin sources with `JavaCompiler` having the valid host API on the compiler path; capture bytecode into a map via `JavaFileManager`; create a **new child loader** whose parent is the host loader; define only plugin-owned implementations and dependencies in the child loader; and cast instances through the **exact contract defined by the parent**. Plugins can swap versions via dedicated loaders while keeping type identity stable across the host–plugin boundary.
