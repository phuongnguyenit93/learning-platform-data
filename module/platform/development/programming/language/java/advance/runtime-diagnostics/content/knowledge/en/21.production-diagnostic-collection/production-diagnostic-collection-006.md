# 21.6. Naming Diagnostic Files With PID, Timestamp, Application Version, and Action Taken

## 1. Why Is a Filename Convention Part of Production Diagnostics?

When operating Java applications, a single incident can generate multiple *diagnostic artifacts*: thread dumps, heap dumps, Java Flight Recorder (JFR) recordings, `jcmd` outputs, GC logs, native memory reports, and configuration snapshots. They may be collected from **multiple JVMs, multiple pods, multiple deployed versions, and multiple timestamps**. If files are simply named `dump.txt`, `heap.hprof`, or `recording.jfr`, engineers easily compare the wrong processes, lose chronological ordering, overwrite files, or attach the wrong evidence to an incident.

The goal of this lesson is to design a **filename that is fast to scan by eye, machine-sortable, and context-preserving**, including at minimum:

- **PID** of the **target JVM** (without accidentally grabbing the collector script's PID).
- **Timestamp** of collection, with an explicit timezone, preferring UTC.
- **Application version** or build identifier running at capture time.
- **Action taken**, such as `thread-dump`, `heap-dump`, `jfr-dump`, or `vm-flags`.

To prevent collisions, the convention also includes **service**, **environment**, **instance**, and **capture ID**. This lesson also explains why a filename is only a *lookup label*, requiring a manifest/metadata record and safe write mechanics for trustworthy evidence.

After completing this lesson, you will be able to:

1. Read a filename and distinguish recordings across pods/JVMs, timestamps, releases, and action types.
2. Construct safe filenames across Windows/Linux/containers without overwriting files or embedding secrets into paths.
3. Bind filenames to the **exact timestamp and target PID**, whether invoked from an admin host, container, or target JVM.
4. Build a manifest linking file, command, collector, status, size, checksum, incident, and security policy.
5. Run Java 17+ code that generates standardized names, uses `CREATE_NEW`, and proves duplicate names are **not** overwritten.
6. Design an auditable artifact finalization/upload/cleanup workflow without mistaking naming for proof of successful collection.

Scope focuses on **identifying and managing diagnostic files in Java operations**. Never run heap dumps or debuggers in production solely to test naming conventions: several commands carry heavy impact and require separate approval.

## 2. Recommended Filename Convention

Consistent structure:

~~~text
<service>__<environment>__<instance>__pid-<pid>__<utc-time>__<version>__<action>__<capture-id>.<extension>
~~~

The separator between components is **a double underscore `__`**. Illustrative examples (not real production files):

~~~text
orders-api__prod__pod-7c2__pid-3142__20261029T095501.123Z__v2.8.1__thread-dump__f8c47de5d7c74ef7a59cc89c935e7d2b.txt
orders-api__prod__pod-7c2__pid-3142__20261029T095501.123Z__v2.8.1__jfr-dump__f8c47de5d7c74ef7a59cc89c935e7d2b.jfr
orders-api__prod__pod-7c2__pid-3142__20261029T095501.123Z__v2.8.1__heap-dump__f8c47de5d7c74ef7a59cc89c935e7d2b.hprof
~~~

These examples share **the same capture ID to illustrate a single collection batch producing multiple artifacts** with different `action` values. In production pipelines where each artifact needs its own ID, keep a shared `collectionId` in the manifest while assigning a unique `captureId` per file. Most importantly, **define clearly whether the ID represents one file or one session** and enforce it consistently; never allow two concurrent jobs to produce the same filename.

### 2.1. Meaning and Source of Truth for Each Field

| Component | Example | Preferred Source of Truth | What Never to Guess |
| --- | --- | --- | --- |
| `service` | `orders-api` | Service identifier in deployment/inventory | Main class name does not always match service name |
| `environment` | `prod` | Platform-managed environment metadata | Never guess from hostname or port |
| `instance` | `pod-7c2` | Pod/instance ID or short code with stable mapping | A single service can run multiple JVMs on one instance |
| `pid` | `pid-3142` | **Target JVM** PID in an explicitly recorded namespace | Operator workstation PID or host PID need not equal container PID |
| `utc-time` | `20261029T095501.123Z` | UTC clock at a **well-defined instant** | Local time without offset fails cross-cluster comparison |
| `version` | `v2.8.1` | Build/release metadata of the **running binary** | Never take app version from `java -version` |
| `action` | `thread-dump` | Controlled action vocabulary (*enum/registry*) | Never embed raw command lines with flags and secrets |
| `capture-id` | 32 hex chars | UUID/random ID generated by the collector | PID + millisecond does not guarantee uniqueness |
| `extension` | `txt`, `jfr`, `hprof` | Actual format produced | Never rename extensions to fake another format |

A readable convention needs **stable semantics**, not cramming in as many fields as possible. Long fields like full paths, namespace names, 40-char commit SHAs, incident IDs, or command options belong in the **manifest** if they bloat the filename. The filename gives quick orientation; the manifest is the authoritative collection record.

### 2.2. When Should Cluster/Region/Node Be Added?

Across multiple clusters or regions, `cluster`/`region` can be placed in the **directory hierarchy** rather than every filename:

~~~text
diagnostics/
  prod/
    ap-southeast/
      cluster-blue/
        orders-api/
          2026/10/29/
            orders-api__prod__pod-7c2__pid-3142__20261029T095501.123Z__v2.8.1__thread-dump__f8c47de5d7c74ef7a59cc89c935e7d2b.txt
~~~

This is an illustrative directory tree only. If files may be downloaded or moved out of this tree, **do not store vital identity solely in folder names**. Keep `cluster` and `region` in the manifest and managed storage object keys. Avoid overly deep paths that exceed OS/tooling limits, and keep sensitive internal hostnames out of public locations.

## 3. PID: Process Identifier, Not Permanent Identity

### 3.1. Always Record the PID of the Target JVM

Three PIDs are easily confused:

1. **Target JVM PID:** the Java process from which the thread dump, heap dump, or JFR is captured.
2. **Collector PID:** the `jcmd` process, Python/Bash/PowerShell script, or Java collector executing the capture.
3. **Host PID vs. container PID:** the exact same JVM can appear under different PIDs in the host and container namespaces.

For example, a worker runs `jcmd 3142 Thread.print`, while `ProcessHandle.current().pid()` inside the **collector program** might be `8921`. Naming the file `pid-8921` sends the investigation to the wrong process. When collecting externally, read the target PID from the **selected target object** or verified parameter—never call `current()` and attribute it to another JVM.

Java 17+ offers `ProcessHandle.current().pid()` to get the PID **of the Java process running that code**. That is accurate when a JVM generates its own artifact, yet is **not** an API for reading a remote JVM's PID. If using `ProcessHandle.of(targetPid)`, remember the OS can reuse PIDs and process state can change between inspection and execution.

### 3.2. PIDs Collide Across Time and Hosts

A PID is not a global identifier:

- The OS can reuse a PID after a process exits.
- Multiple hosts or containers can all run PID `1`, `3142`, and so on.
- In Kubernetes, the JVM PID seen inside a pod can differ from the host PID.
- A process can restart between metadata lookup and actual dump execution.

**Therefore include `instance`, UTC timestamp, capture ID, and `processStartTime` in the manifest.** A restarted service in the same pod with the same PID can still be distinguished by process start time, build/run identity, and capture ID.

When sending `jcmd`, verify the exact PID/VM under authorized scope; on HotSpot you can use `jcmd <pid> VM.version` and `VM.command_line` per policy. Never dump full `VM.system_properties` indiscriminately, as it may contain sensitive data. If attach fails, never substitute a "similar-looking" PID guessed from a Java process name.

## 4. Time: UTC, Resolution, and Timestamp Semantics

Recommended filename format:

~~~text
uuuuMMdd'T'HHmmss.SSS'Z'
20261029T095501.123Z
~~~

Its advantages: no `:` or `/` characters that are awkward in filenames on some OSes, chronological sorting from year down to milliseconds, and the `Z` suffix denoting UTC. Under consistent formatting, **sorting filenames for the same service/instance** naturally sorts chronologically.

- In Java: `Instant.now()` yields a UTC instant, formatted via `DateTimeFormatter` with `ZoneOffset.UTC`.
- `Z` is truthful only when **actually formatting UTC**; never append `Z` to local time.
- Use the **same timestamp** captured at collection start across all related artifacts if your rule defines `utc-time` as `captureStartedAt`; record `captureCompletedAt` separately in the manifest.
- If your filename represents **write completion time** instead of start time, rename/document the standard and ensure every collector agrees.

**Recommended standard:** `utc-time` in the filename is **when collection started**. Completion time, command-to-JVM turnaround time, the event window inside a JFR file, and upload time **are not the same timestamp**.

### 4.1. For JFR: The Event Window Can Differ From Dump Time

Suppose a JFR recording runs 14:00–14:30 UTC and an operator invokes `JFR.dump` at 14:25. The file can contain events before 14:25 depending on retention and dump flags. A filename `...T142500Z...jfr-dump...` marks only **when the snapshot was exported**, not the exact span of data inside. The manifest should record `recordingStartedAt`, `recordingEndedAt`, or verified min/max event timestamps.

### 4.2. Millisecond Resolution Is Not Deduplication

Two collectors can start within the same millisecond, or job retries can emit the same timestamped name. Never rely on `yyyyMMddHHmmssSSS` alone to prevent collisions. Add a **capture ID** and use **non-overwriting writes**. UUIDs make collisions vanishingly rare, yet code must still handle `FileAlreadyExistsException` or storage conflicts.

### 4.3. Clock Skew and Event Ordering

Clocks can drift across nodes even when all print UTC. To prove strict ordering in a distributed incident, combine NTP/clock health, time sync, tracing correlation, build/deploy timelines, and internal artifact event timestamps. A filename **never proves** happens-before ordering between two JVMs.

## 5. Application Version: Do Not Confuse With JDK or Image Tag

At least four versions exist:

| Label | Example | Meaning |
| --- | --- | --- |
| `appVersion` | `v2.8.1` | Logical application release version |
| `buildId` | `build-483` | Pipeline/build identifier |
| `commitSha` | `6a2f...` | Source commit tied to the binary |
| `jvmVersion` | `21.0.5` | Executing JDK, independent of app version |

For container deployments, `imageDigest` and `imageTag` also exist; **tags can be reassigned**, whereas a digest identifies immutable content. When diagnosing a bad release, `buildId`/`commitSha`/`imageDigest` in the manifest matter more than a short app-version label.

Application version should be **embedded in the build artifact** or verified deployment metadata, such as:

- JAR manifest `Implementation-Version` or a build-generated version file.
- Pipeline-injected environment variables, **cross-checked** against image digest/build metadata.
- Workload release metadata/annotations paired with instance identity and time.
- A build-info endpoint, if present, with appropriate access and data restrictions.

Never report `System.getProperty("java.version")` as the app version. Never trust an operator-typed version without verification. If version cannot be retrieved, use a standard placeholder like `unknown` in the filename and set `metadataStatus=missing` in the manifest with a reason. **Never invent a version** just to make filenames look complete.

Standardize normalization when source versions contain filename-unsafe characters. For example, SemVer `2.8.1+build.483` has a `+`: the filename might use `v2.8.1-build.483`, while the manifest preserves the **exact raw value** `2.8.1+build.483` and documents the mapping rule. Avoid silent sanitizers that collapse two distinct values into one label.

## 6. Action Taken: Use a Controlled Vocabulary

`action` answers: "**What was the JVM or collector asked to do to produce this file?**" It is not the incident name, root-cause conclusion, or operator name.

| Recommended Action | Artifact Form | Example Source |
| --- | --- | --- |
| `thread-dump` | `.txt` | `jcmd <pid> Thread.print`, stdout saved by collector |
| `heap-dump` | `.hprof` | `jcmd <pid> GC.heap_dump`, written by target JVM |
| `jfr-dump` | `.jfr` | `jcmd <pid> JFR.dump`, snapshot of a recording |
| `jfr-stop` | `.jfr` | `JFR.stop filename=...`, stops and exports recording |
| `class-histogram` | `.txt` | `GC.class_histogram` |
| `vm-flags` | `.txt` | `VM.flags` |
| `vm-version` | `.txt` | `VM.version` |
| `nmt-summary` | `.txt` | `VM.native_memory summary` if NMT enabled and authorized |
| `gc-log-export` | `.log` or `.log.gz` | Copy of existing GC logs; **do not confuse with a freshly run JVM command** |

Keep action names stable, lowercase, and hyphen-separated (`-`). Version your schema when changing the action registry; never casually rename `heap-dump` to `memory-dump` without mapping. Never embed full command lines into filenames: arguments can expose internal paths, tokens, secret-bearing URLs, and produce overly long names.

**Name the action after what was done, not a hypothesis:** a `heap-dump` file should not be named `leak-confirmed.hprof` because taking a dump does not prove a leak yet. Record `suspectedCause` in incident notes marked as a "hypothesis."

### 6.1. Match Extension to Actual Content

`.jfr` holds JFR data; `.hprof` is an HPROF heap dump; `.txt` suits text dumps; `.gz` indicates compression. If `GC.heap_dump -gz` writes a gzipped HPROF, the extension should clearly reflect `.hprof.gz` when accurate, and the manifest should record compression. Changing an extension does not convert a text file into an HPROF. Never declare a file valid solely from its suffix.

## 7. Preventing Collisions and Overwrites

A name containing PID, timestamp, and action **can still collide** on retries or concurrent collectors. A safe pattern relies on three elements:

1. **Unique per-capture ID:** a 128-bit UUID or equivalent managed ID; filenames are not the sole primary key.
2. **Non-overwriting creation:** when creating files in Java, use `StandardOpenOption.CREATE_NEW`; fail if the file exists rather than destroying prior evidence.
3. **Finalization state:** a file mid-write must never be analyzed as complete. Publish/index only after command success, file close, format/size checks, and manifest creation.

**Do not do this:**

~~~java
// WRONG example: subject to race conditions and overwrites.
if (!java.nio.file.Files.exists(destination)) {
    java.nio.file.Files.writeString(destination, report); // Can overwrite by default.
}
~~~

Between `exists` and `writeString`, another collector may have created the file. You need protection at **atomic filesystem-provider creation**, such as `CREATE_NEW`. With object storage, use conditional puts (`if-none-match`) or immutable object keys; never assume a default `upload()` API refuses overwrites.

### 7.1. Staging Files and Atomic Publishing

Recommended lifecycle:

~~~text
COLLECT_REQUESTED
       |
       v
assign captureId + metadata + final filename
       |
       v
write to secure staging path with unique name
       |
       v
collector/JVM succeeded cleanly? ----- no ----> FAILED / PARTIAL; keep error log,
       |                                        never publish as complete file
      yes
       |
       v
verify artifact: exists, format, size, checksum,
captured time window, exit status, read permissions
       |
       v
publish to final path/key WITHOUT overwrite + write manifest
       |
       v
READY_FOR_ANALYSIS -> RETAIN/DELETE per policy
~~~

To use filesystem atomic rename, staging and final paths must reside on the **same filesystem**, and you must verify `ATOMIC_MOVE` support. Semantics when a destination exists can vary by provider; **never rely on `Files.move(..., ATOMIC_MOVE)` alone as overwrite protection**—enforce no-overwrite/uniqueness at the destination. Cross-volume moves or network uploads are generally not atomic. For multi-node collectors, use storage APIs with **no-overwrite preconditions** and lifecycle metadata.

Do not pre-create an empty `.hprof` file and point `GC.heap_dump` at it when the tool refuses existing files by default. For commands where **the JVM itself writes the file**, pick a unique filename inside a secured directory and rely on the command's no-overwrite behavior or staging paths rather than mechanically applying collector file-open flags.

### 7.2. Failures After File Creation

If `jcmd` times out, the JVM is killed, or disk fills up, a partial file or incomplete manifest may remain. **Do not silently delete it** and lose failure evidence, yet never list a partial file as "successfully collected." Mark it `FAILED`/`PARTIAL`, save the exit code, filtered stderr, and failure time, and allow policy-driven cleanup. On retry, issue a **new capture ID** and link `retryOf` to the previous attempt.

A SHA-256 checksum detects corruption or tampering during copying, yet **does not prove authenticity** if an attacker modifying the file can also edit the checksum. Tamper resistance requires tightly controlled storage ACLs, audit logs, object lock/signatures, or organizational integrity controls.

## 8. Java 17+: Standard Naming and Overwrite Prevention Demo

This lab **creates only a synthetic text file**—it never generates a heap dump, attaches to another JVM, or touches production. Inputs are fixed for deterministic stdout verification; in real collectors, feed the target JVM's PID and real timestamp **from verified sources**.

Create **`DiagnosticArtifactNameDemo.java`**:

~~~java
import java.nio.charset.StandardCharsets;
import java.nio.file.FileAlreadyExistsException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
import java.time.Instant;
import java.time.ZoneOffset;
import java.time.format.DateTimeFormatter;
import java.util.Locale;
import java.util.UUID;

public final class DiagnosticArtifactNameDemo {
    enum Action {
        THREAD_DUMP("thread-dump", "txt"),
        JFR_DUMP("jfr-dump", "jfr"),
        HEAP_DUMP("heap-dump", "hprof");

        final String slug;
        final String extension;

        Action(String slug, String extension) {
            this.slug = slug;
            this.extension = extension;
        }
    }

    private static final DateTimeFormatter UTC =
            DateTimeFormatter.ofPattern("uuuuMMdd'T'HHmmss.SSS'Z'", Locale.ROOT)
                    .withZone(ZoneOffset.UTC);

    private static String component(String label, String value) {
        if (value == null || !value.matches("[a-z0-9][a-z0-9.-]{0,62}")
                || value.endsWith(".") || value.contains("..")) {
            throw new IllegalArgumentException("Invalid " + label);
        }
        return value;
    }

    static String name(String service, String environment, String instance,
                       long targetPid, Instant capturedAt, String version,
                       Action action, UUID captureId) {
        if (targetPid <= 0 || capturedAt == null || action == null
                || captureId == null) {
            throw new IllegalArgumentException("Missing or invalid metadata");
        }
        String stem = String.join("__",
                component("service", service),
                component("environment", environment),
                component("instance", instance),
                "pid-" + targetPid,
                UTC.format(capturedAt),
                component("version", version),
                action.slug,
                captureId.toString().replace("-", ""));
        return stem + "." + action.extension;
    }

    public static void main(String[] args) throws Exception {
        Instant capturedAt = Instant.parse("2026-10-29T09:55:01.123Z");
        UUID id = UUID.fromString("f8c47de5-d7c7-4ef7-a59c-c89c935e7d2b");
        String filename = name("orders-api", "prod", "pod-7c2",
                3142L, capturedAt, "v2.8.1", Action.THREAD_DUMP, id);
        Path directory = Files.createTempDirectory("artifact-name-demo-");
        Path artifact = directory.resolve(filename);

        try {
            Files.writeString(artifact, "demo-only\n",
                    StandardCharsets.UTF_8, StandardOpenOption.CREATE_NEW,
                    StandardOpenOption.WRITE);

            boolean duplicateRejected = false;
            try {
                Files.writeString(artifact, "do-not-overwrite",
                        StandardCharsets.UTF_8, StandardOpenOption.CREATE_NEW);
            } catch (FileAlreadyExistsException expected) {
                duplicateRejected = true;
            }

            System.out.println("file=" + filename);
            System.out.println("created=" + Files.isRegularFile(artifact));
            System.out.println("duplicateRejected=" + duplicateRejected);
            System.out.println("content=" +
                    Files.readString(artifact, StandardCharsets.UTF_8).strip());
        } finally {
            Files.deleteIfExists(artifact);
            Files.deleteIfExists(directory);
        }
    }
}
~~~

Compile and run with JDK 17+:

~~~bash
javac DiagnosticArtifactNameDemo.java
java DiagnosticArtifactNameDemo
~~~

Stdout verified on JDK 24:

~~~text
file=orders-api__prod__pod-7c2__pid-3142__20261029T095501.123Z__v2.8.1__thread-dump__f8c47de5d7c74ef7a59cc89c935e7d2b.txt
created=true
duplicateRejected=true
content=demo-only
~~~

### 8.1. Code Walkthrough

- `DateTimeFormatter` uses `uuuuMMdd'T'HHmmss.SSS'Z'` and `ZoneOffset.UTC` for consistent timestamps; `Instant` does not depend on the host's default timezone.
- `component(...)` rejects spaces, slashes, backslashes, the `__` delimiter, and malformed names. It does **not** replace comprehensive path/permission validation; still enforce a fixed base directory, distrust unverified inputs, and guard against symlinks in untrusted environments.
- `targetPid=3142` in the lab is an illustrative value, not the PID of the running demo JVM. In a real collector, **never substitute `ProcessHandle.current().pid()`** when writing files for another process.
- `UUID.fromString(...)` uses a fixed capture ID for repeatable test output. In operations, generate `UUID.randomUUID()` per capture and record it in the manifest.
- `Action` is an enum constraining vocabulary and extensions. Selecting the extension from the enum is safe only when actual output format is verified after capture; this lab writes a dummy `.txt` file.
- `CREATE_NEW` creates a new file and rejects existing names; the second write throws `FileAlreadyExistsException`, yielding `duplicateRejected=true`.
- `Files.readString(...).strip()` confirms the original content was untouched by the attempted overwrite.
- `try/finally` cleans up the temp file and directory; this is for the test only—**never auto-delete production evidence right after creation**.
- The lab writes into the OS temp directory and contains only `demo-only`. For real data, avoid shared unvetted temp directories because heap/thread dumps can hold sensitive data.

**Known limitations:** the example omits atomic publishing, checksum/manifest generation, and ACL management. It demonstrates **standardized naming and no-overwrite creation** specifically; production pipelines require the remaining steps.

### 8.2. Scaling to a Real Collector

In production collection code, abstract out:

~~~text
ArtifactIdentity:
  serviceId
  environment
  instanceId
  targetPid
  processStartTime
  appVersion
  buildId
  captureStartedAt
  action
  captureId

ArtifactWriter:
  reserveUniqueDestination()
  executeCollectorWithTimeout()
  validateOutput()
  calculateSha256()
  publishWithoutOverwrite()
  writeManifest()
~~~

This is a **design outline, not Java code**. Collectors should pull trusted metadata from deployment/orchestrator sources rather than arbitrary user-supplied environment variables. Ensure high-impact I/O/GC tasks run only through authorized, quota-checked workflows.

## 9. Key Difference Between Collector-Written and JVM-Written Outputs

The two command styles have **different file writers**, directly affecting paths, permissions, and verification locations.

### 9.1. Capturing Thread Dumps via `jcmd` Stdout

POSIX shell example for **authorized** hosts and JVMs only:

~~~bash
# PID=3142 and output filename are illustrative only.
PID=3142
OUT_DIR=/srv/diag/private
FILE_NAME='orders-api__prod__pod-7c2__pid-3142__20261029T095501.123Z__v2.8.1__thread-dump__f8c47de5d7c74ef7a59cc89c935e7d2b.txt'

# An administrator must pre-create OUT_DIR securely with right owner/quota.
# Noclobber prevents the shell from overwriting an existing path.
if ( umask 077; set -C; jcmd "$PID" Thread.print > "$OUT_DIR/$FILE_NAME" ); then
    echo 'collector finished'
else
    echo 'collector failed: review partial file and stderr' >&2
fi
~~~

This is a **stdout capture example**. The collector's shell opens `OUT_DIR/FILE_NAME`; the path resolves **where the collector runs**, not necessarily in the JVM's container namespace. `set -C` (noclobber) blocks redirect overwrites in many POSIX shells, yet does not replace directory/symlink protections or provide atomic publication, and partial files can still remain if `jcmd` fails. Verify your target shell and empty/error-file handling policy before use. Never treat shell file creation alone as proof of a valid dump.

For `Thread.print`, if the JVM has many threads or is busy, the call still carries cost; never poll tightly in production without measuring.

### 9.2. Capturing HPROF or JFR: Files Written by the Target JVM

~~~bash
# Example on a machine/namespace with jcmd and matching permissions.
jcmd 3142 help GC.heap_dump
jcmd 3142 GC.heap_dump /srv/diag/private/heap-capture.hprof

jcmd 3142 JFR.check
jcmd 3142 JFR.dump name=diag filename=/srv/diag/private/jfr-capture.jfr
~~~

Here `/srv/diag/private/...` for `GC.heap_dump`/`JFR.dump` is resolved by the **target JVM**. If the JVM runs inside a container, the file resides **inside the container** or a mount distinct from the collector's filesystem. Verify the target JVM has write permission, the volume has space, and the retriever has read access. Replace short sample names (`heap-capture.hprof`/`jfr-capture.jfr`) with the full standard convention from Section 2 in real operations.

**Never add `-overwrite` to `GC.heap_dump` for convenience.** On HotSpot JDK 21, `-overwrite` defaults to false; enabling overwrites can destroy evidence. Heap dumps carry **high impact**, may trigger Full GC, write huge files, pause the app, and contain sensitive data. `JFR.dump` exports a snapshot while the recording may continue running; it does not stop the recording, and internal event times can differ from filename timestamps. Always check `jcmd <pid> help <command>` on the target JDK.

If two commands emit files simultaneously, **never reuse the same capture ID and action** expecting no collision; assign distinct artifact IDs or a manifest with `collectionId` and `artifactId`.

### 9.3. Recording Metadata After Command Success

For text dumps, verify headers/data are present, the command exited zero, and the file is closed. For JFR, use `jfr summary file.jfr`; for HPROF, validate format and size with MAT or an appropriate reader. On Linux, after completion:

~~~bash
# Inspect only metadata/integrity of a valid captured file, never print sensitive content.
stat -c '%n %s bytes' /srv/diag/private/heap-capture.hprof
sha256sum /srv/diag/private/heap-capture.hprof
~~~

Byte counts and SHA-256 must be recorded in the manifest **after the file is completely closed**. Hashing while the JVM is still writing yields a digest that does not match the final artifact. After transferring to another node, recompute the checksum and compare against signed/managed metadata. Hashing does not block unauthorized reads, so transport, files, and manifests still require access protection.

## 10. Manifest: Turning Filenames Into Auditable Evidence

Filenames are **compact indexes**, whereas incident investigations need more: who requested it, what command ran, on which JVM, why, where it lives, whether it succeeded, and whether sharing is permitted.

Illustrative JSON manifest for a **hypothetical** capture, stored alongside or inside a managed metadata store. This is sample data, not the output of the Section 8 program:

~~~json
{
  "schemaVersion": 1,
  "artifactId": "f8c47de5-d7c7-4ef7-a59c-c89c935e7d2b",
  "incidentId": "inc-20261029-42",
  "service": "orders-api",
  "environment": "prod",
  "cluster": "cluster-blue",
  "instance": "pod-7c2",
  "targetPid": 3142,
  "pidNamespace": "container",
  "targetProcessStartedAt": "2026-10-29T08:40:00Z",
  "appVersion": "2.8.1+build.483",
  "buildId": "build-483",
  "commitSha": "6a2fc8b",
  "jvmVersion": "21.0.5",
  "action": "thread-dump",
  "captureStartedAt": "2026-10-29T09:55:01.123Z",
  "captureFinishedAt": "2026-10-29T09:55:01.823Z",
  "commandTemplate": "jcmd TARGET_PID Thread.print",
  "collectorLocation": "approved-bastion",
  "status": "SUCCEEDED",
  "fileName": "orders-api__prod__pod-7c2__pid-3142__20261029T095501.123Z__v2.8.1__thread-dump__f8c47de5d7c74ef7a59cc89c935e7d2b.txt",
~~~

**Warning:** `sizeBytes`, `sha256`, and timestamps in this sample are **illustrative values**—never feed them into real systems as measurements. In real workflows, `sha256` must hold the real digest computed from the finalized file; the manifest must explicitly record status if hashing is pending or the file failed. Never store raw commands containing passwords/tokens; record only a secret-scrubbed **command template** and non-sensitive flags.

### 10.1. Critical Fields That Do Not Belong in the Filename

- `targetProcessStartedAt`: distinguishes reused PIDs when retrieved from a trusted source.
- `pidNamespace`, `cluster`, `node`, `podUid`, or deployment instance: resolves host vs. container PID ambiguity.
- `captureStartedAt` and `captureFinishedAt`: lets analysts compute command duration and align with the incident.
- `recordingWindow` (for JFR): actual event timespan inside the file once verified.
- `commandTemplate`, `exitCode`, `stderrSummary`: distinguishes success, error, timeout, and executed action.
- `fileName`, `objectKey`, `sizeBytes`, `sha256`, `format`: locates the file and verifies integrity.
- `sensitivity`, `retentionUntil`, `authorizedBy`, `collectedBy`: enforces access control, expiration, and audit.
- `retryOf`/`collectionId`: links retries and multiple artifacts belonging to one incident.

Avoid cramming all these fields into a single filename; overly long names truncate in UIs, exceed path limits, or leak sensitive context. If you run an artifact management service, manifests can live in a database, object-storage metadata, or sidecars—ensure an **immutable binding** between artifact and record.

### 10.2. Filenames and Manifests Serve Different Roles

- **Filename:** quick human scan, initial filtering, approximate sorting, avoids generic names like "dump."
- **Manifest:** schema-backed record with status and full metadata for automation.
- **Checksum:** detects post-capture file modification.
- **Audit log:** records user/system actions; never trust a client-submitted `collectedBy` field on its own.
- **Object store ACL/retention:** enforces who actually reads and when files expire.

For multi-person investigations, readable filenames are essential, yet **never replace** session governance and security controls.

## 11. OS and Data Safety Conventions

### 11.1. Characters, Length, and Delimiters

Use **validated or deterministically normalized** components. In the Java example, each component allows lowercase `a–z`, digits `0–9`, hyphens, and dots, rejecting spaces, `/`, `\`, `:`, and `__`. This works smoothly across OSes, though filesystems can still impose differing limits.

Avoid:

- Overly long names (per-component and total-path limits vary).
- Shell-special characters like `&`, `;`, `$`, spaces, or inconsistently handled Unicode.
- Mixed upper/lowercase collisions on case-insensitive filesystems.
- Truncating versions/hashes without keeping originals and mapping rules.
- Treating filename regexes as complete protection against symlinks or path traversal. You still need a trusted base directory, permissions/ownership, and safe file-creation APIs.

It is almost always better to **reject invalid metadata** with a clear error than to silently "sanitize" user strings into colliding filenames.

### 11.2. Filenames Themselves Can Leak Information

A filename like `user-123456__token-abcdef__customer-a.hprof` easily leaks PII/secrets into tickets, emails, storage logs, or shared URLs. Never put tokens, credentials, payloads, usernames, emails, query strings, or sensitive customer IDs directly in filenames. Use incident IDs or authorized internal aliases instead, keeping mappings in a separate restricted manifest system.

Even with a clean filename, **artifact contents can be highly sensitive**:

- Heap dumps can hold passwords/tokens, sessions, PII, and payloads.
- Thread dumps can expose stack traces, class names, paths, or data depending on logging/frames.
- JFR can contain method names, file paths, IPs/hosts, and custom event fields.
- JVM command lines and system properties can contain secrets.

Enforce strict filesystem permissions, encryption in transit and at rest per policy, TTL/retention, download auditing, and restricted access lists. Never attach raw artifacts to public tickets just because the filename contains no secrets.

### 11.3. Never Let File Creation Fill Disk

Good naming does not stop a directory from filling up. Collectors need artifact count caps, quotas, reserved free space, size estimates, per-incident rate limits, and retention limits. Heap dumps can be huge and high-impact; never repeat them blindly on job retries. If a file already exists and a command reports collision, never slap on `-overwrite` just to force the job to "succeed."

## 12. Common Operational Mistakes

| Observation / Error | Why It Is Dangerous | Verification and Fix |
| --- | --- | --- |
| Two files both named `dump.txt` | Overwrites and lost provenance | Apply schema with service + PID + UTC + version + action + capture ID |
| Filename carries the `jcmd` script's PID | Blames the wrong JVM | Verify target PID, manifest PID namespace, and process start time |
| App version taken from `java -version` | Confuses Java runtime release with app release | Pull build/release metadata from the running binary |
| Local timestamps without offset | Breaks cross-node, timezone, and DST alignment | Format UTC with `Z`; store start/finish in manifest |
| Timestamped names still overwrite | Retries or concurrent jobs hit the same millisecond | UUID + `CREATE_NEW` / conditional publish |
| `File.exists()` then `writeString()` | TOCTOU race condition, overwrites after check | Create via atomic create APIs; never check-then-write |
| `jcmd Thread.print > output` exits nonzero | File may contain only errors or truncated output | Record exit code, validate output, mark PARTIAL/FAILED |
| `GC.heap_dump` invoked from a bastion | JVM cannot see bastion paths | Check target JVM filesystem/container mounts and JVM permissions |
| JFR dumped at 10:00, filename says 10:00 | Does not describe the internal event time span | Record recording/event window separately |
| `.hprof.gz` renamed to `.hprof` | Parsers fail on wrong format | Keep extension aligned with actual format and compression |
| Reusing one capture ID for a retry with the same action | Name collision or replacing prior artifact | Fresh ID plus `retryOf` in manifest |
| File exists on disk before closing | Analysts pick up partial files | Staging → validation → publish workflow |
| Right filename, mismatched hash post-upload | Incomplete transfer or tampering | Recompute SHA-256; never mark ready on mismatch |
| Unprotected manifest | Unauthorized metadata edits, broken audit | ACL-protected store, logs, restricted writes, integrity checks |
| Putting customer IDs in filenames | Leaks info through paths and logs | Use aliases/incident IDs and restricted mappings |
| Overly long names truncated by scripts | Parsing breaks, collisions occur | Bound component length; move details to manifest |
| Deleting local files early because GC logs "went to cloud" | Evidence lost if upload failed | Verify checksum and durability before cleanup |
| Splitting filenames on single `_` | Breaks whenever a component uses underscores | Enforce `__` delimiter and component validation, or read manifest |

A key QA rule: **fail loudly rather than silently patching missing metadata**. If PID, version, or timestamp cannot be verified, mark metadata missing instead of fabricating values or inserting misleading defaults.

## 13. Practice Exercises

**Exercise 1 — reading a filename.** Given:

~~~text
billing-api__staging__pod-9f1__pid-87__20261029T101500.000Z__v3.2.0__jfr-dump__0123456789abcdef0123456789abcdef.jfr
~~~

Identify service, environment, instance, PID, UTC time, version, action, and format. Answers in order: `billing-api`, `staging`, `pod-9f1`, `87`, **2026-10-29 10:15:00.000 UTC**, `v3.2.0`, `jfr-dump`, `.jfr`. You cannot tell when the JFR events begin until you inspect the manifest or file.

**Exercise 2 — wrong PID.** A collector with PID 9000 takes a thread dump of JVM PID 313 inside a container, and the filename uses `pid-9000`. How do you fix it? Record **target JVM PID 313**, add namespace/`processStartTime` and collector identity to the manifest, and never auto-bind the collector's PID to the JVM filename.

**Exercise 3 — timeout.** An `.hprof` file appears after `GC.heap_dump` times out. Can you analyze it as complete? **Never assume so.** Mark `PARTIAL`, inspect exit status, file size, and format. For a retry, issue a new ID and obtain impact approval.

**Exercise 4 — same millisecond.** Two operators capture `thread-dump` from the same JVM within the same millisecond. Why can a name with only PID and timestamp collide? Because timestamp resolution does not guarantee uniqueness. Use capture IDs and non-overwriting writes.

**Exercise 5 — normalized version.** Raw version is `2.8.1+build.483`, and the filename uses `v2.8.1-build.483`. What must the manifest preserve? The exact raw version, build ID, commit/image digest, and normalization rule so distinguishability is never lost.

**Exercise 6 — wrong format.** A file ends in `.jfr`, yet `jfr summary` cannot read it. Should you rename it to `.txt` and declare success? **No.** Investigate partial/corrupt/wrong-format issues, paths, and exit codes; changing an extension does not fix data.

**Exercise 7 — write permissions.** `Thread.print > /collector/data/x.txt` succeeds, while `GC.heap_dump /collector/data/x.hprof` fails with permission denied. Where is the difference? The thread dump is redirected by the **collector's shell**; the HPROF is written by the **target JVM** along the path it sees. Check namespaces and each process's permissions.

**Exercise 8 — checksum timing.** You compute SHA-256 before the JVM closes the file, upload it, and the receiver sees a different hash. Did the network definitely corrupt the file? **No.** The file may still have been written after the first hash; compute hashes only after completion and closed state are confirmed.

**Exercise 9 — multi-artifact incident.** One capture gathers 2 thread dumps and 1 JFR. How should IDs be structured? Assign one shared `collectionId` for the incident/window and **unique `artifactId` values** per file; link them in the manifest and never reuse identical action+name across two dumps.

**Exercise 10 — sensitive file.** The filename has valid PID and version, yet the heap dump contains session tokens. Can it be attached freely to any ticket? **No.** Classify and enforce permissions, retention, and encryption per policy. A clean filename does not make file contents benign.

## 14. Pre- and Post-Collection Checklist

**Before collecting:**

- [ ] Target JVM, PID in the right namespace, and process start/instance identity are verified.
- [ ] Accurate service/environment/app version obtained from trusted build/deployment sources.
- [ ] UTC timestamp anchored as **captureStartedAt**; clock sync verified sufficiently for investigation.
- [ ] `action` chosen from the approved vocabulary; extension matches real format.
- [ ] Unique capture ID generated and final filename stays within path limits.
- [ ] Output directory/volume verified for permissions, free space, quotas, and sensitivity.
- [ ] High-impact diagnostic commands approved with duration bounds and owner.
- [ ] No-overwrite policy, staging/partial-state handling, and retry path defined.

**After collecting:**

- [ ] Command actually succeeded; exit code and start/finish timestamps recorded.
- [ ] File closed, valid size, and verified readable by the proper tool.
- [ ] Exact SHA-256, format, compression, size, and location recorded in manifest.
- [ ] Manifest binds capture ID, PID, app version, action, and incident accurately.
- [ ] File/manifest permissions, reader list, and retention limits verified.
- [ ] Copy/upload verified before cleaning up staging files.
- [ ] Zero overwrites or clobbering of earlier collection evidence.
- [ ] Partial/`FAILED` files flagged accurately, never mixed with verified artifacts.

**Conclusion:** good filenames connect **which JVM – when – which version – what action**, while capture IDs prevent collisions, manifests preserve full context, and safe write/verification mechanics ensure artifacts hold up in investigation. Treat naming as part of **controlled collection**, not merely string concatenation.
