# 13.2 Non-Heap Memory Sources: Thread Stacks, Metaspace, Code Cache, Direct Buffers, and Native Libraries

## 1. Objectives and Memory Boundaries

A Java process **does not only use the Java heap**. `-Xmx` limits the heap managed by the JVM for Java objects; the process also needs memory for threads, class metadata, machine code generated by JIT, I/O buffers, the garbage collector, the runtime, and native libraries. Consequently, situations where **the heap still has free space while RSS climbs, a container gets OOMKilled, or the JVM reports a native allocation error** can readily occur.

This lesson helps you:

1. Identify the allocation site, lifecycle, and limits of five major sources: **platform-thread stacks, metaspace, code cache, direct buffers, and native libraries**.
2. Distinguish Java heap, the non-heap regions reported by MXBeans, native/off-heap memory, and total process footprint.
3. Correctly interpret **reserved, committed, used, RSS**, and JVM/container limits.
4. Use `jcmd`, Native Memory Tracking (NMT), `BufferPoolMXBean`, and OS metrics to pinpoint the source of memory growth.
5. Choose the right fix instead of merely increasing `-Xmx` or forcing GC.

**Terminology:**

- **Java heap:** the region the JVM uses to allocate most Java objects and arrays; managed by GC, typically observed via heap metrics and `-Xmx`.
- **JVM non-heap (per `MemoryMXBean`):** memory pools serving the JVM such as metaspace and code cache. This is **not** all native memory in the process.
- **Native/off-heap memory:** a general term for regions outside the Java heap, including parts managed by HotSpot, Java libraries, or native code. Each source has its own tracking mechanisms and limits.
- **Process footprint:** memory as seen by the OS/container, which may include Java heap, native allocations, runtime structures, memory mappings, and shared regions.

There is no exact equation like `RSS = heap used + metaspace used + direct buffer used`. Measurement tools cover different scopes, and some regions are shared, mapped, merely reserved, or not yet resident in RAM.

## 2. Map of the Five Memory Sources

| Source | Primary Contents | Lifecycle / Growth Drivers | Observation Tools | Relevant Limits |
| --- | --- | --- | --- | --- |
| **Thread stack** | Call frames of **platform/OS threads**, stack guard pages, and thread structures | Platform thread count, call depth, stack size | NMT `Thread`, OS thread count, `jcmd Thread.print`, OS | `-Xss`, `-XX:ThreadStackSize`; plus OS/container limits |
| **Metaspace** | Metadata for classes, methods, class loaders; may include compressed class space | Number of loaded classes, live class loaders, dynamic proxies/codegen | NMT `Class`, `jcmd VM.metaspace`, class-loading metrics | `-XX:MaxMetaspaceSize`, `-XX:CompressedClassSpaceSize` when applicable |
| **Code cache** | Native machine code generated by JIT and runtime code components | Warm-up, number of methods/optimized versions, tiered compilation | NMT `Code`, `jcmd Compiler.codecache`, JIT logs | `-XX:ReservedCodeCacheSize` |
| **Direct buffers** | Backing data of `ByteBuffer.allocateDirect`, typically outside the heap | Buffer count, capacity, objects/views holding references, release rate | `BufferPoolMXBean` (`direct`), JFR/library metrics, OS | `-XX:MaxDirectMemorySize` for applicable NIO direct allocations |
| **Native libraries** | `malloc`/`mmap`, C/C++ structures, JNI/FFM, native handles, `.so`/`.dll` code/data | Native caches, native leaks, library lifecycle, memory mappings | OS memory maps, native profilers, library metrics | Library-specific limits, OS/cgroup; the JVM flags above do **not** cap this source |

Beyond these five main sources, there are **GC structures, compiler working data, symbols, internal JVM structures, arenas, JFR buffers, memory-mapped files, page tables**, etc. Do not force those items into metaspace or direct buffers just because they live off-heap.

### 2.1. Differences Between Reserved, Committed, Used, and RSS

- **Reserved**: virtual address range set aside for a purpose. A large reserved value **does not by itself prove** the process is holding that much RAM. For example, compressed class space can reserve a large address range while committed remains small.
- **Committed**: memory committed/allocated for a JVM region as backed by the OS. This still **does not strictly equal** the number of pages resident in RAM.
- **Used**: amount counted as actively in use by the allocator or subsystem within committed memory. NMT and MXBeans may measure this differently.
- **RSS (Resident Set Size)**: total resident memory pages of the process as measured by the OS. Shared pages, file mappings, and OS page accounting prevent RSS from being added directly from NMT categories.

Illustrative example: `Class reserved=1050 MB, committed=38 MB` does **not** mean 1,050 MB of metaspace has consumed RAM. When investigating actual memory pressure, check **how committed/used change over time** and cross-check RSS/container memory.

## 3. Thread Stacks: Each OS Thread Has Its Own Cost

### 3.1. Platform Threads and Native Stacks

`new Thread(...).start()` creates a **platform thread** on common JDKs. It maps to an OS thread and has a native stack for call frames, arguments, local variables, runtime info, and guard pages. Stack size can be tuned with `-Xss`:

```bash
java -Xss1m -Xmx512m -jar app.jar
```

`-Xss1m` sets the thread stack size according to the implementation/OS; it does **not** mean each thread immediately increases RSS by 1 MiB upon creation. The OS typically reserves address space and commits/touches pages as needed; HotSpot may report the stack portion in NMT under its accounting conventions. Threads also have native data structures outside the stack, so `threadCount × Xss` is only a **reserved address estimate**, not an RSS formula.

If you have 500 platform threads with a stack configured near 1 MiB, address space reserved for stacks alone is in the hundreds of MiB. Actual physical usage still depends on stack depth, the OS, and related regions.

**Two errors to distinguish:**

- `java.lang.StackOverflowError`: a single thread exceeds its stack capacity, e.g., due to unbounded recursion; this can happen even when the process has plenty of RAM left.
- `java.lang.OutOfMemoryError: unable to create native thread` or similar message: the OS/JVM cannot create another native thread due to resource exhaustion, process/thread limits, PID limits, or native memory pressure; **the heap does not have to be full**.

Remediation: bound concurrent platform threads, avoid spawning an unbounded platform thread per request, analyze thread leaks/blocked threads, and consider thread pools or virtual threads if the workload fits. Lowering `-Xss` too far risks `StackOverflowError`; raising `-Xss` does not fix creating too many threads.

### 3.2. Virtual Threads Do Not Have Dedicated Native Stacks in That Way

Since JDK 21, virtual threads are a standard feature. They use **stack chunks** on the Java heap when unmounted and are mounted onto **carrier platform threads** by the scheduler to run. Therefore, **do not multiply the number of virtual threads by `-Xss` to compute total native stack**: one million VTs do not correspond to one million OS stacks. However, carrier/platform threads still have native stacks, and VTs still consume heap and other resources used by their work (buffers, connections, objects).

When thread counts or the `Thread` category grow, first confirm whether they are **platform/OS threads** or application VTs. Do not assume "many VTs → many native stacks".

### 3.3. Practical Signals

```bash
jcmd <PID> Thread.print
jcmd <PID> VM.native_memory summary scale=MB
```

Read the NMT `Thread` category, thread count, and `stack: reserved/committed`. Combine with OS thread count from `/proc/<PID>/status` (Linux: `Threads` field) or equivalent tools. For processes with very many threads, `Thread.print` can produce large output; use it purposefully when diagnosing.

## 4. Metaspace: Metadata for Classes and Class Loaders

### 4.1. What Does Metaspace Hold?

HotSpot uses **metaspace** to store metadata needed for loaded classes: class info, methods, constant-pool metadata, and supporting structures. **Application Java objects still live on the Java heap**; `Class<?>` is a Java object on the heap, while many class-describing structures reside in the separate metadata area.

Metaspace depends on **the number of loaded classes and class loader lifetimes**. Applications using dynamic proxies, bytecode enhancement, scripting, plugin systems, hot reload, or runtime class generation can grow metadata. GC only reclaims metadata when classes/class loaders become **eligible for unloading**, so increasing heap GC frequency does not guarantee metaspace reclamation.

With compressed class pointers, HotSpot may use a **compressed class space** for certain class metadata. This region is reserved separately and can have a `reserved` value much larger than `committed`.

### 4.2. Limits and Errors

```bash
java -XX:MaxMetaspaceSize=256m -XX:CompressedClassSpaceSize=128m -jar app.jar
```

- `-XX:MaxMetaspaceSize` caps class metadata usage per VM mechanisms. Leaving it unset does not mean infinite memory; it is still constrained by the OS/container.
- `-XX:CompressedClassSpaceSize` governs the class metadata space for compressed class pointers **when that mechanism is enabled and applies**. It is not a general cap on all of metaspace or all native allocations.
- Running out of space can trigger `OutOfMemoryError: Metaspace` or `OutOfMemoryError: Compressed class space`, two signals that should be distinguished.

Raising the limit may be appropriate if the workload genuinely needs many classes. However, **class loaders retained after redeploy**, static caches, registries, or thread context class loaders holding old plugins can also cause metaspace to grow continuously. In that case, raising the limit only delays the failure.

### 4.3. Monitoring

```bash
jcmd <PID> VM.metaspace basic
jcmd <PID> VM.metaspace show-loaders
jcmd <PID> VM.native_memory summary scale=MB
```

The NMT `Class` group typically displays `Metadata`, `Class space`, class count, and `reserved/committed` amounts. `VM.metaspace show-loaders` shows which class loaders retain metadata; add `show-classes` only when higher detail is truly needed. JMX memory pools like `Metaspace` and `Compressed Class Space`, along with class-loading metrics, help track trends over time.

**Diagnostic tip:** total loaded classes/loaders growing without shrinking even after the workload returns to baseline, or creating duplicate copies of classes on every redeploy, signals class-loader retention to investigate. Do not diagnose a class-loader leak solely because JVM warm-up caused metaspace to grow once and then stabilize.

## 5. Code Cache: Machine Code Compiled by JIT

### 5.1. Code Cache Differs from Metaspace

As a program runs, the HotSpot Just-In-Time compiler translates frequently executed Java methods into **native machine code**. That code, along with certain runtime code/stubs, is placed in the **code cache**. This is an executable memory region, distinct from the Java heap (objects) and metaspace (class metadata).

As an application warms up or optimizes more methods/code paths, the code cache grows. HotSpot has mechanisms to sweep obsolete code and manage code heaps; several versions use a **segmented code cache** (profiled nmethods, non-profiled nmethods, non-nmethods). The NMT `Code` group reflects various code cache components; the `Compiler` group reflects **compiler working memory**—do not conflate the two groups.

### 5.2. Limits and Symptoms

```bash
java -XX:ReservedCodeCacheSize=256m -jar app.jar
```

`-XX:ReservedCodeCacheSize` controls the maximum reserved size for the HotSpot code cache. If the code cache runs out of suitable space, the JVM may log a message such as **code cache is full** and JIT compilation may be restricted or halted; application speed can degrade even while the heap has free space. This typically does not look like `OutOfMemoryError: Java heap space`.

Observation:

```bash
jcmd <PID> Compiler.codecache
jcmd <PID> Compiler.queue
jcmd <PID> VM.native_memory summary scale=MB
```

`Compiler.codecache` shows the active code heaps, size/used/max, and status; `Compiler.queue` checks pending compilation tasks. Combine with compilation logs when needed. Do not increase code cache size reflexively: check whether it is genuinely full, compilation rates, number of compiled methods, and overall process footprint.

## 6. Direct Buffers: I/O Memory Outside the Java Heap

### 6.1. `allocate` vs. `allocateDirect`

```java
ByteBuffer heapBuffer = ByteBuffer.allocate(1024);
ByteBuffer directBuffer = ByteBuffer.allocateDirect(1024);
```

- `allocate`: creates a Java-heap-backed buffer (e.g., a Java byte array).
- `allocateDirect`: creates a direct byte buffer whose data typically lives outside the Java heap, allowing the JVM to avoid intermediate copying during native I/O. The **Java wrapper object** and managing references still live on the heap.
- `isDirect()` indicates the buffer type; direct buffers generally have higher allocation/deallocation cost, so they are not automatically faster for all sizes and usage patterns.

In HotSpot, the native backing of many direct buffers is freed when the wrapper or objects retaining that resource become unreachable and the cleanup mechanism gets a chance to run. **`buffer = null` does not guarantee immediate deallocation**; `slice()`, `duplicate()`, caches, and retained views can extend the memory's lifetime. Do not call internal/Unsafe APIs to force cleanup of a buffer still in use.

### 6.2. NIO Direct Memory Limit

```bash
java -Xmx512m -XX:MaxDirectMemorySize=128m -jar app.jar
```

`-XX:MaxDirectMemorySize` applies to **JDK/VM-managed NIO direct-buffer allocations**, not a quota for **every kind of native memory**. When left unspecified, the VM/JDK picks a default limit based on implementation policy; do not assume every version uses one fixed number. Exceeding the quota can raise an `OutOfMemoryError` mentioning inability to reserve direct buffer memory (exact wording varies by JDK version).

A direct buffer with 1 MiB capacity may occupy slightly more native memory due to allocator behavior, alignment, or metadata; the capacity metric does not necessarily equal actual memory used. `-XX:MaxDirectMemorySize` also **does not cap all JNI `malloc`, native library caches, memory-mapped pages, or FFM allocations**.

### 6.3. Observing via `BufferPoolMXBean`

Java provides `java.lang.management.BufferPoolMXBean` for pools such as `direct` and `mapped`:

- `getCount()`: estimated number of buffers.
- `getTotalCapacity()`: estimated total capacity (bytes).
- `getMemoryUsed()`: estimated bytes consumed; may return `-1` if undetermined.
- `getName()`: pool name; the list and scope of pools depend on the JVM/provider.

**Why do you need count, capacity, and used together?** A pool might have few buffers that are each huge, or many tiny buffers with high overhead. Looking only at `count` misses memory usage patterns. Also, the sum of `memoryUsed` across buffer pools is **not** all off-heap memory in the process.

**Memory-mapped files:** `FileChannel.map` creates a `MappedByteBuffer` backed by file pages and OS paging. It should not be treated identically to `allocateDirect` using anonymous native memory; observe the `mapped` pool, memory mappings, RSS/page cache in context, and manage file/mapping lifecycles appropriately.

## 7. Native Libraries: JNI, FFM, Allocators, and Mappings

A Java program can use native code via **JNI**, libraries with `.so`/`.dll`/`.dylib`, graphics/crypto/compression libraries, or the **Foreign Function & Memory API (FFM)** on supported JDKs. They can:

- Allocate via `malloc`, `calloc`, native arenas, or `mmap`.
- Create OS threads, thread-local storage, native caches, TLS buffers, handles, and unmanaged structures.
- Map executable code, data, and shared-library pages into the process address space.
- Retain memory even when Java wrappers are small or absent from a heap dump.

Native code must pair acquire/release according to each library's contract; e.g., JNI must free its native allocations, and FFM arenas must be closed following an appropriate lifecycle. Holding a pointer to freed memory or closing an arena too early can cause crashes/use-after-free; failing to free causes native leaks.

**Key limitation of NMT:** HotSpot Native Memory Tracking tracks **memory tracked by HotSpot/JVM itself**, and does not cover every allocation made by JNI, native libraries, or parts of the class library. Thus, **stable NMT does not mean process-wide native memory is stable**. When native code is suspected, use platform-appropriate profilers/allocator instrumentation or library-exposed metrics together with OS tools.

`System.gc()` is not a fix for native leaks. Garbage collection can allow some wrappers to be cleaned up once unreachable, but it cannot free regions that native code forgot to release or regions still referenced.

## 8. Relationships Between Limit Flags and Errors

| Flag / Limit | Primary Scope | What It Does Not Limit |
| --- | --- | --- |
| `-Xmx` | Maximum Java heap | Native stacks, metaspace, code cache, direct/native libraries |
| `-Xss` | Stack size per platform thread per VM/OS | Total thread count, all native memory |
| `-XX:MaxMetaspaceSize` | Class metadata in metaspace | Direct buffers, stacks, JNI allocations |
| `-XX:CompressedClassSpaceSize` | Compressed class metadata space when used | Entire metaspace and native libraries |
| `-XX:ReservedCodeCacheSize` | JIT code cache | Metaspace, heap, or all compilation working data |
| `-XX:MaxDirectMemorySize` | Applicable NIO direct-buffer allocations | JNI `malloc`, memory mappings, all off-heap |
| cgroup `memory.max`, OS memory limit | Resources charged to container/process by the OS | Does not classify JVM subsystems and does not alter internal JVM bookkeeping |

A common mistake: a container has a 2 GiB limit and someone sets `-Xmx2g`, assuming zero native overhead. **Even before the heap reaches Xmx**, the process still needs thread stacks, class metadata, JIT code, GC data, and buffers. Design native memory headroom using **observed data under high load**, rather than summing `reserved` values as real RAM.

### Common Errors Have Different Meanings

| Symptom | Most Likely Cause | What to Confirm |
| --- | --- | --- |
| `OutOfMemoryError: Java heap space` | Java heap has no room for objects | Heap dump, retained objects, allocation rate, `-Xmx` |
| `OutOfMemoryError: Metaspace` | Metadata out of space against limit | Class/loader count, `VM.metaspace`, Class NMT |
| `OutOfMemoryError: Compressed class space` | Dedicated class space limit reached | Compressed class space used/committed/limit |
| `OutOfMemoryError: unable to create native thread` | Unable to create an OS thread | OS thread count, PID limits, stacks, native memory |
| `OutOfMemoryError` mentioning `direct buffer memory` | NIO direct-buffer quota/allocation failure | `BufferPoolMXBean`, capacity/used, retention |
| `CodeCache is full` in JVM logs | Code cache full/JIT compilation restricted | `Compiler.codecache`, warm-up performance and logs |
| Container `OOMKilled` with no Java stack trace | OS/cgroup killed process due to memory pressure | `memory.events`, RSS/cgroup usage, NMT and mappings |

Exact messages vary by JDK/OS; a single error can have multiple causes, so gather evidence rather than guessing from phrasing alone.

## 9. Native Memory Tracking (NMT) from Numbers to Diagnosis

### 9.1. Enabling NMT at Startup

```bash
java -XX:NativeMemoryTracking=summary -Xmx512m -jar app.jar
```

NMT is **disabled by default** on many HotSpot builds. It has two levels:

- `summary`: statistics by JVM subsystem/category, usually the best starting point.
- `detail`: adds call-site and address-region map details, used when summary is not enough. NMT adds memory/CPU overhead; Oracle docs note overhead can be around **5–10%**, so enable it purposefully.

You cannot enable or raise NMT from `off` to `summary`/`detail` on an already running JVM using `jcmd` alone; configure it **at startup** and rerun a diagnostic session when appropriate. `jcmd` is mainly used to **read** metrics, create a baseline, diff, or shut down NMT.

```bash
jcmd -l
jcmd <PID> VM.native_memory summary scale=MB
jcmd <PID> VM.native_memory baseline
```

After real load has run for a period of time, inspect changes since the baseline:

```bash
jcmd <PID> VM.native_memory summary.diff scale=MB
```

If `-XX:NativeMemoryTracking=detail` was enabled from startup:

```bash
jcmd <PID> VM.native_memory detail scale=MB
jcmd <PID> VM.native_memory detail.diff scale=MB
```

`summary.diff` and `detail.diff` require a **prior baseline**. Take the baseline after warm-up (if looking for steady-state leaks), run the **same kind of workload** long enough, and compare across multiple snapshots. Observing a growing delta matters more than a single large snapshot.

### 9.2. Reading NMT Categories

Example **illustrating how to read**, not fixed output of a program:

```text
Total: reserved=2600MB, committed=920MB
- Java Heap (reserved=1536MB, committed=480MB)
- Class     (reserved=1040MB, committed=36MB)
- Thread    (reserved=160MB,  committed=24MB)
- Code      (reserved=240MB,  committed=90MB)
```

The lines in this example are abbreviated and **are not meant to sum to the actual total** (many other categories exist). Points to keep in mind:

- `Java Heap`: still appears in NMT. NMT is **not** a table of off-heap-only memory; when analyzing native memory, separate out the heap category.
- `Class`: metadata and class space. A large `reserved` field does not prove a class leak.
- `Thread`: thread structures and stacks; also read `stack: reserved/committed` alongside OS thread counts.
- `Code`: runtime/JIT code. Do not confuse with `Compiler`, which is JIT compiler working data.
- `GC`, `Internal`, `Symbol`, `Arena Chunk`, `Native Memory Tracking`, and other groups: can all consume substantial native memory depending on workload/JDK.

**NMT committed is not RSS.** NMT tracks a HotSpot scope; RSS reflects process resident pages and includes allocations/mappings outside NMT's scope. Therefore, do not subtract `RSS - NMT committed` and claim the exact difference is a "JNI leak": shared pages, allocator fragmentation, class library allocations, or paging behavior may explain it.

### 9.3. Combining the Right Tools

| When You Need to Know | Tool | How to Use the Result |
| --- | --- | --- |
| Which group HotSpot native memory is growing in | `jcmd VM.native_memory summary.diff` | Pinpoint `Thread`, `Class`, `Code`, `GC`, ... |
| Which loaders drive metaspace growth | `jcmd VM.metaspace show-loaders` | Trace back to frameworks, plugins, redeploys, or codegen |
| Whether code cache is full or growing | `jcmd Compiler.codecache` | Assess used/free and JIT compilation status |
| Direct-buffer pool growth | `BufferPoolMXBean` / JMX | Inspect count, capacity, used, retention |
| High OS thread count | OS `/proc/<PID>/status`, `Thread.print` | Compare platform-thread count and stack pressure |
| Total footprint growth on Linux | `/proc/<PID>/status`, `/proc/<PID>/smaps_rollup`, `pmap` | Check RSS, mappings, anonymous/file-backed regions |
| Container near OOM | cgroup `memory.current`, `memory.max`, `memory.events` | Check usage and OOM-kill events |
| NMT flat while RSS grows | OS profilers/native allocator tools | Find JNI/library allocators, mappings, fragmentation, page residency |

Direct Linux inspection example (fill in the appropriate PID):

```bash
grep -E 'VmRSS|VmSize|Threads' /proc/<PID>/status
cat /proc/<PID>/smaps_rollup
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.events
```

On cgroup v2, `memory.current` and `memory.events` reside in the **cgroup containing the process**, not necessarily at the root path shown above. `memory.current` also uses cgroup-level accounting, which is **not identical** to a single PID's RSS. On Windows/macOS, use the corresponding process/memory-map tools. Distinguish metrics by **PID, process tree, container/cgroup, and host** before comparing.

## 10. Java 17+ Lab: Comparing Heap Buffer and Direct Buffer

Create **`OffHeapSourcesDemo.java`** in your working directory. The example uses ~1 MiB of direct memory, small enough to run locally; the optional `hold` argument keeps the process alive for 60 seconds so you can attach `jcmd`.

```java
import java.lang.management.BufferPoolMXBean;
import java.lang.management.ManagementFactory;
import java.nio.ByteBuffer;

public class OffHeapSourcesDemo {
    private static ByteBuffer retained;

    public static void main(String[] args) throws InterruptedException {
        ByteBuffer heap = ByteBuffer.allocate(32);
        retained = ByteBuffer.allocateDirect(1024 * 1024);
        retained.putInt(0, 42);

        System.out.println("heap.isDirect=" + heap.isDirect());
        System.out.println("direct.isDirect=" + retained.isDirect());
        System.out.println("direct.value=" + retained.getInt(0));

        for (BufferPoolMXBean pool : ManagementFactory.getPlatformMXBeans(BufferPoolMXBean.class)) {
            if ("direct".equals(pool.getName())) {
                System.out.println("pool.name=" + pool.getName());
                System.out.println("pool.count=" + pool.getCount());
                System.out.println("pool.capacityBytes=" + pool.getTotalCapacity());
                System.out.println("pool.usedBytes=" + pool.getMemoryUsed());
            }
        }

        if (args.length == 1 && "hold".equals(args[0])) {
            System.out.println("pid=" + ProcessHandle.current().pid());
            Thread.sleep(60_000);
        }
    }
}
```

Compile and run with JDK 17+:

```bash
javac OffHeapSourcesDemo.java
java -XX:NativeMemoryTracking=summary -XX:MaxDirectMemorySize=128m OffHeapSourcesDemo
```

**First three lines of stdout** (stable for this example):

```text
heap.isDirect=false
direct.isDirect=true
direct.value=42
```

The remaining lines print the `direct` pool name and `pool.count`, `pool.capacityBytes`, and `pool.usedBytes`; exact values depend on the JVM and any other buffers in the same process. A run on a clean JDK might show `pool.capacityBytes=1048576`, but **do not treat this as fixed output across all environments**.

To capture snapshots while the program is running, launch again with `hold`:

```bash
java -XX:NativeMemoryTracking=summary -XX:MaxDirectMemorySize=128m OffHeapSourcesDemo hold
```

The program additionally prints `pid=<a PID number>` and keeps the process alive for about a minute. Open a second terminal, replacing PID with the printed number:

```bash
jcmd <PID> VM.native_memory summary scale=MB
jcmd <PID> VM.metaspace basic
jcmd <PID> Compiler.codecache
```

**Key takeaway from the lab:** the `retained` object lives on the Java heap while the direct buffer's data typically lives off-heap; `isDirect()` classifies them, `BufferPoolMXBean` tracks NIO buffer pools, and NMT tracks HotSpot categories. Do not expect NMT `Other` to increase by exactly 1 MiB for `allocateDirect`, because NMT **does not guarantee** coverage of all Java class library allocations.

You can try running with a direct memory limit smaller than the buffer size to observe quota behavior, but do not treat one specific error message as standard output across all JDKs; padding/alignment and allocator behavior also apply.

## 11. Diagnostic Workflow for the Five Memory Sources

**Scenario A — heap stable, RSS climbs alongside OS thread count.** Measure platform-thread count and `Thread` NMT; check for unbounded pools or threads that never terminate. Fix lifecycle/thread pools, check native thread count and headroom; treat `-Xss` as a limited tuning knob, not a substitute for bounding concurrency.

**Scenario B — class count and `Class` NMT grow with each deploy.** Use `VM.metaspace show-loaders`, class load/unload logs, or class-loader analysis; find retained old loaders/plugins, static caches, or thread-context references. Fix retention and observe metaspace drop or stabilize; adjust `MaxMetaspaceSize` only based on real demand.

**Scenario C — JVM logs code cache full, throughput drops after warm-up.** Read `Compiler.codecache`, JIT logs, and `ReservedCodeCacheSize`. If code cache exhaustion is proven and native headroom is sufficient, adjust its size and verify performance; do not treat code cache exhaustion by increasing Java heap.

**Scenario D — NIO networking grows direct memory under load, triggering `direct buffer memory` OOME.** Monitor `BufferPoolMXBean` over time; check pooling, caches, `slice`/`duplicate` retaining the parent buffer, I/O lifecycle, and backpressure. Rebalance buffer pool sizing or bound concurrency. Increase `MaxDirectMemorySize` only when necessary and within the container budget.

**Scenario E — RSS/container memory grows while NMT categories remain mostly flat.** Confirm timestamps align; inspect native library allocations, memory mappings, fragmentation, cgroup page cache, and shared pages; use a native allocator profiler or OS tools. Do not use flat NMT results to conclude there is no native leak.

**Scenario F — container is OOMKilled without a heap OOME.** Collect cgroup `memory.events`, memory limit, RSS/mappings, heap committed, NMT committed, direct pool metrics, and JVM flags. Note whether other services share the cgroup alongside the JVM. A heap dump alone will not explain all native allocations; capture data early before the process is killed.

### Template for Recording a Diagnostic Pass

Record at minimum: **JDK/VM version; OS/container/cgroup limit; `-Xmx`, `-Xss`, metaspace/code-cache/direct limits; NMT mode; baseline timestamp; throughput/load; heap used/committed; `Class/Thread/Code` NMT; direct pool count/capacity/used; RSS/container memory; errors/logs around the time of growth**.

From there, conclude from **trends**, not a single snapshot: which category grew first, whether it correlates with workload or thread/class/buffer counts, whether NMT can observe the suspected source, and whether any fix has been verified under equivalent run conditions.

## 12. Misconceptions to Avoid

1. **"Heap usage is low so the process cannot OOM."** False: native memory and OS/container accounting can still hit limits.
2. **"Metaspace/class space reserved = RAM in use."** False: distinguish reserved, committed, used, and RSS.
3. **"`MemoryMXBean.getNonHeapMemoryUsage()` is the sum of all off-heap memory."** False: those are JVM-defined memory pools, typically excluding thread stacks, JNI allocations, and all direct memory.
4. **"Every virtual thread needs a `-Xss` native stack."** False: virtual thread stacks are primarily heap-backed stack chunks; carrier platform threads still have native stacks.
5. **"Raising `-XX:MaxDirectMemorySize` eliminates native OOM."** False: it neither limits nor fixes allocations from JNI/FFM, thread stacks, code cache, and libraries.
6. **"NMT `Other` always equals direct buffer usage."** False: NMT does not account for all memory allocated by Java/native libraries; use `BufferPoolMXBean` as well.
7. **"Seeing a large code cache means a leak."** False: legitimate warm-up/JIT compilation can grow it up to a plateau; check full state and trends.
8. **"Metaspace shrinks on every GC."** False: class unloading depends on class loader reachability, references, and runtime policy.
9. **"The smallest `-Xss` always saves the most RAM."** False: risks stack overflow, guard/alignment, OS limits, and RSS does not equal reserved.
10. **"A heap dump contains all native memory."** False: a heap dump mainly shows Java objects/wrappers and retention paths; native bytes usually require NMT, JMX, and OS/native tools.
11. **"RSS − NMT committed = exact JNI allocations."** False: measurement scopes, mappings, resident pages, fragmentation, and shared memory differ.
12. **"Container limit equals `-Xmx`."** False: `-Xmx` is only maximum heap; you need native headroom and cgroup monitoring.

## 13. Practical Checklist

- [ ] Confirm **JDK/OS/container**, total footprint, and actual JVM flags in effect.
- [ ] Separate heap used/committed from native sources; prioritize observing **changes over time**.
- [ ] Use NMT `summary`/`summary.diff` for `Thread`, `Class`, `Code`, and other JVM categories; choose `detail` at startup if call-site evidence is needed.
- [ ] Use `VM.metaspace`, `Compiler.codecache`, thread metrics, `BufferPoolMXBean`, OS memory maps, and cgroup memory according to each hypothesis.
- [ ] Recognize the **JNI/native library** portion not fully covered by NMT; measure with native tools when needed.
- [ ] Verify root cause via lifecycles, counters, and workload; fix retention/bounds before raising quotas.
- [ ] Re-evaluate throughput, latency, peak RSS/container usage, and memory metrics after changes.

**Core takeaway:** the five memory sources differ in **allocator, lifecycle, measurement tools, and limits**. A Java process can run out of native memory while the Java heap is not full. Proper diagnosis requires linking **JVM + JMX + OS/container** metrics while respecting the units and boundaries of each source.
