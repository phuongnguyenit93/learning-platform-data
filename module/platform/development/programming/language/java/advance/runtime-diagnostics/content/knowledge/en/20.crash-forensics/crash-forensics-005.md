# 20.5. Distinguishing Signs of Faults in Native Libraries, the JVM, or JIT-Compiled Code

## Objectives

When a Java application crashes, you may see `SIGSEGV`, `SIGBUS`, `SIGILL`, `EXCEPTION_ACCESS_VIOLATION`, or a HotSpot **`Internal Error`** message. These signs differ from an ordinary Java exception. The **`hs_err_pid...log`** file shows where the instruction was executing when the fault was detected; however, **where the crash happens is not necessarily where the bug began**.

This lesson focuses on three scenarios you need to tell apart:

- **Native library**: C/C++/JNI/JNA code, `.so`/`.dll` libraries belonging to the application, a vendor, the JDK, or the OS.
- **JVM/HotSpot**: code inside the VM itself, such as GC, VM runtime, interpreter, compiler implementation, or stubs.
- **JIT-compiled Java code**: machine code generated by the JIT compiler from Java bytecode, being executed by a thread.

Additionally, you must clearly distinguish **a crash while a compiler thread is compiling a method** from **a crash while an application thread is executing an already-compiled method**. Both can involve the JIT, yet their traces differ.

Objectives after this lesson:

1. Classify the frame markers **`C`, `V`, `v`, `J`, `j`** in a HotSpot fatal error log.
2. Read `Problematic frame`, `Current thread`, thread state, `Native frames`, `Java frames`, `Current CompileTask`, and `VM_Operation` together.
3. Understand the limits of inferences like “C = native bug”, “V = JVM bug”, and “J = JIT bug”.
4. Use corroborating evidence such as native core dumps, loaded libraries, JVM flags, JDK build, and controlled tests.
5. Collect, store, and report crash artifacts safely; never intentionally crash production.

The examples target **HotSpot/OpenJDK 17+**, with Linux as the primary illustrative environment. Field names, thread names, stack layouts, and signals may vary by OS, architecture, JVM vendor, or JDK update.

## 1. Distinguishing a JVM Crash from a Java Exception and an OS Kill

| Observed symptom | Possible meaning | Priority evidence |
| --- | --- | --- |
| `java.lang.NullPointerException`, `ArrayIndexOutOfBoundsException`, `IllegalStateException` | Java exception thrown via language mechanism | Application stack trace and exception handling |
| `java.lang.OutOfMemoryError: Java heap space` | JVM could not allocate in the Java heap; **not automatically a native fatal crash** | Heap/GC logs, heap size, live objects |
| HotSpot reports `A fatal error has been detected by the Java Runtime Environment`, `Problematic frame` | JVM detected a fatal condition, usually tries to write `hs_err` then stops the process | Fatal error log, native core/minidump |
| Linux `SIGSEGV` / Windows `EXCEPTION_ACCESS_VIOLATION` | Executed instruction caused a memory access violation | `pc`/`rip`, `siginfo`, frame, native stack, core |
| `Internal Error`, `guarantee(...) failed`, `assert` | HotSpot detected a violated internal invariant | Exact message, JDK version, current thread, VM state |
| Kubernetes `OOMKilled`, kernel `SIGKILL` | Process terminated from outside the JVM; may have no fatal error log | Container/kernel events, cgroup memory counters |
| Process exited on its own via shutdown / `System.exit` | May be a normal/application exit path, not a VM crash | Exit status, lifecycle logs, signal/health events |

**Simply seeing the process vanish does not prove a VM bug.** `SIGKILL` does not let the JVM run its error handler, so no fatal log may be produced. Conversely, native memory corruption can cause the JVM itself to detect an error and write `hs_err`—which does not mean the JDK implementation caused the corruption.

A Java `StackOverflowError` from Java recursion is generally different from a **native stack overflow** that can cause a fatal crash. Inspect the signal, frame, and native stack instead of lumping the two together.

## 2. The `hs_err_pid...log` File: Where to Find It and How to Preserve Evidence

With HotSpot, unless reconfigured, the fatal error log is typically named **`hs_err_pid12345.log`** (`12345` is the PID). The JVM first tries to write in the **process working directory**; if that fails, it may try an OS temporary directory such as `/tmp` on Linux. Startup flags can specify an explicit location:

```bash
java -XX:ErrorFile=/var/log/java/hs_err_pid%p.log -jar app.jar
```

`%p` is a placeholder replaced by the PID. Verify that the directory exists, has write permissions, disk capacity, and an artifact-collection mechanism inside containers. Do not use a single fixed filename for multiple JVMs if there is a risk of overwriting data.

**A sound investigation preserves verbatim** the fatal error log, core/minidump if available, stdout/stderr, Java build and native libraries, timestamps, PID/TID/namespace, JVM flags, container image, OS/kernel version, active workload, and recent deployments. Do not screenshot just the top 10 header lines and discard the stack/process/system sections.

The file may be partially written if the crash is severe, the stack is corrupted, the disk is full, or the error reporter itself faults. If `hs_err` does not exist, check OS events and other log locations **within authorized boundaries** before concluding there was no JVM crash.

**Security:** `hs_err`/core files can contain JVM arguments, file paths, environment variables, memory addresses, and sensitive data. Core dumps can contain application memory contents. Restrict access and sanitize contents when sharing bug reports.

## 3. Reading the Header: Signal, PC, PID/TID, and Problematic Frame

**Hypothetical** sample:

```text
#
# A fatal error has been detected by the Java Runtime Environment:
#
# SIGSEGV (0xb) at pc=0x00007f5ab0001240, pid=3015, tid=3020
#
# JRE version: OpenJDK Runtime Environment (17.x)
# Java VM: OpenJDK 64-Bit Server VM (17.x, mixed mode, ...)
# Problematic frame:
# C  [libfastcodec.so+0x1240]
#
```

Here:

- `SIGSEGV` is the segmentation violation signal on Linux. Windows typically uses exception codes such as `EXCEPTION_ACCESS_VIOLATION`.
- `pc=...` (*program counter*) is the instruction address when the fault occurred, **not a Java line number**.
- `pid` identifies the process; `tid` identifies the faulting native thread. In containers, the PID namespace may differ from the host.
- `Problematic frame: C [libfastcodec.so+0x1240]` says the instruction belongs to a **native frame** in a library named `libfastcodec.so`, at an offset relative to the loaded image.
- This line suggests investigating the library/ABI/JNI, but **does not by itself prove that library caused the corruption**. A pointer may have been corrupted elsewhere earlier.

Another clue in Linux fatal logs:

```text
siginfo: si_signo: 11 (SIGSEGV), si_code: 1 (SEGV_MAPERR), si_addr: 0x0000000000000000
```

`si_addr` is the address associated with the fault. `0x0` may suggest a null pointer dereference in native code. `SEGV_MAPERR` generally indicates an unmapped address; `SEGV_ACCERR` relates to access permissions. Still, never conclude the root cause from `si_addr` alone: you need registers, the instruction at `pc`, and memory mappings.

`SIGBUS`, `SIGILL`, `SIGFPE`, or `Internal Error` also have many possible sources, ranging from native libraries, codegen, and VM runtime to OS/hardware. The signal name is only the **detected failure type**, not the responsible module.

## 4. HotSpot Frame Markers: Uppercase vs. Lowercase Matters Greatly

| Marker | Execution region | Accurate interpretation | What not to conclude |
| --- | --- | --- | --- |
| **`C`** | Native C/C++/library code | Crash PC is in a native library, e.g. `.so`/`.dll` | Not automatically a third-party library bug; could be JDK native code or prior corruption |
| **`V`** | HotSpot VM code | Crash PC is in VM code, such as GC, runtime, or compiler implementation | Not automatically a JVM bug |
| **`v`** | VM-generated stub/adapter | Could be a runtime transition or generated stub | Not automatically the source of the bug |
| **`J`** | Compiled Java code | Java bytecode already compiled to machine code, currently executing | Does not automatically prove the compiler generated bad code |
| **`j`** | Interpreted Java code | Java bytecode currently being executed by the interpreter | Lowercase `j` is **not** equivalent to `J` (JIT-compiled) |

Some fatal logs include a legend like `Native frames: (J=compiled Java code, j=interpreted, Vv=VM code, C=native code)`. Read the **exact markers** in the target log; do not mix display conventions from one JDK with another.

### The most important distinction regarding JIT

**Scenario 1 — compiled code running:** `Problematic frame: J demo.Algorithm.compute`, current thread is `request-worker`. The CPU is executing **already-compiled** machine code.

**Scenario 2 — JIT compiler generating code:** `Problematic frame: V [libjvm.so+...]`, `Current thread: C2 CompilerThread0`, with `Current CompileTask`. The CPU is running HotSpot's **compiler implementation**.

Although both mention JIT, the crash site and reproduction approach differ. Always read **frame + current thread + compile task** instead of seeing the word `JIT` and assigning blame.

## 5. Branch A: Native Library / JNI / Third-Party Code

**Hypothetical** sample:

```text
# Problematic frame:
# C  [libimagecodec.so+0x23d]

---------------  T H R E A D  ---------------
Current thread: JavaThread "image-worker" [_thread_in_native, id=4220]

Native frames:
C  [libimagecodec.so+0x23d]
C  [libimagecodec.so+0x117]
j  demo.ImageService.decode([B)[I+0
v  ~StubRoutines::call_stub
```

Multiple clues point together toward native code:

1. The `C` frame indicates **the instruction is in native code**, not Java bytecode.
2. `_thread_in_native` shows the thread was running native/JNI code at crash time.
3. The stack has multiple `C` frames inside the codec library and a related Java caller.
4. When checking `Dynamic libraries` in `hs_err`, verify the **exact path and actual binary build loaded**, not merely the dependency name in a build file.
5. Suspects to inspect: bounds violations, use-after-free, double-free, invalid pointers, JNI reference lifetimes, JNI thread attachment, data races, allocator mismatches, or ABI/architecture incompatibilities.

A `C [libnet.so]` or `C [zip.dll]` is also a native frame, yet may belong to the **JDK distribution**. If the fault lies in a JDK native library, investigate the JDK build, OS, agents, and JNI/native callers together; do not lump it with “HotSpot VM core” or automatically blame an application library.

### A bug in JNI can surface as a VM frame

Classic illustrative sample:

```text
# Problematic frame:
# V  [jvm.dll+0x83d77]

Current thread: JavaThread "main" [_thread_in_vm, id=2896]
Native frames:
V  [jvm.dll+0x83d77]
C  [App.dll+0x1047]
j  demo.NativeService.invoke()V+0
```

Even though **`Problematic frame` is `V`**, the stack shows native `App.dll` calling into the VM. A JNI routine passing an invalid pointer or reference can make HotSpot crash while processing the request. Therefore, always inspect the **caller chain and JNI contract**, not only the first line.

### Checking JNI in a controlled environment

```bash
java -Xcheck:jni -jar app.jar
```

`-Xcheck:jni` tells HotSpot to perform extra checks on JNI calls. It can catch many forms of JNI misuse, but **does not guarantee** finding every native/C++ bug (especially pointer bugs, data races, or stack corruption). It adds overhead and a severe violation can stop the VM. Enable it only in staging/test environments with authorization and prepared logs, not as a “bug-fixing flag.”

If native source is available, use compiler sanitizers, native debuggers, and matching debug symbols in an appropriate environment; correlate the fault with inputs, versions, and threading rather than guessing from the library name.

## 6. Branch B: JVM/HotSpot VM Code, GC, Safepoints, and Internal Errors

Example:

```text
# Problematic frame:
# V  [libjvm.so+0x4f20]

Current thread: VMThread [id=5100]
VM_Operation: ... (operation name depends on version)
```

The `V` marker shows the crashing instruction is in core HotSpot VM code. However, the **root cause** can include:

- A VM/GC/runtime bug or an issue in a specific JDK update.
- A JNI/native library or JVMTI agent corrupting the heap or object references earlier; the VM detects it later during GC or a safepoint.
- Abnormal metadata/code cache/`ClassLoader` state or native memory corruption.
- Hardware/OS/driver issues or other low-level memory corruption.

If the current thread is **`VMThread`**, inspect `VM_Operation`. When the operation involves GC, you need GC logs, native agent/JNI history, the exact GC collector, and flags. “The crash happened during GC” **does not prove the GC implementation is the culprit**.

If the header shows `Internal Error`, `guarantee(...) failed`, `ShouldNotReachHere`, or `assert`, the VM itself reported a violated invariant. The internal source file/line (if shown) and exact JDK build are critical. The same internal error string across two JDK builds **does not guarantee** the same cause; conversely, the same underlying bug can report differently.

### Current thread state is a clue, not a verdict

- `_thread_in_native`: in native code at the time of reporting.
- `_thread_in_vm`: inside VM code.
- `_thread_in_Java`: executing interpreted or compiled Java code.
- `VMThread`, `GC Thread`, `CompilerThread` are thread roles. Exact names vary by collector and JDK.

Thread state is only a **snapshot** at crash time. A native bug could corrupt data seconds or minutes earlier, and the JVM crashes later when GC scans the object. Correlate the corrupted region and event sequence rather than stopping at one state label.

## 7. Branch C: Fault While Executing **JIT-Compiled** Java Code

Sample example:

```text
# SIGSEGV (0xb) at pc=0x00007f0000009000, pid=6100, tid=6111
# Problematic frame:
# J 1342 c2 demo.FastHash.mix([B)I

Current thread: JavaThread "request-9" [_thread_in_Java, id=6111]
```

Meaning:

- `J` is a **compiled Java frame**, meaning the Java method was compiled into native machine code and **is currently executing**.
- `request-9` is an application thread, **not** a compiler thread generating machine code.
- `c2` in the example indicates the optimization tier in some HotSpot outputs; formatting, IDs, and tiers may vary.
- Method `demo.FastHash.mix` is associated with the crash PC. It is the **method executing when the fault was detected**, not necessarily the method containing a bug.

Hypotheses include JIT wrong-code generation, intrinsic/runtime stub bugs, native/JNI/JVMTI corruption, unsafe native access, or hardware/OS faults. Ordinary Java logic errors throw exceptions or return wrong results rather than **automatically producing `SIGSEGV`**; therefore, also inspect any native/VM transition paths.

### A/B test with interpreter mode `-Xint`

```bash
java -Xint -jar app.jar
```

`-Xint` runs bytecode in interpreted-only mode without JIT compilation for hot Java methods. If the crash reproduces reliably in mixed mode but disappears under `-Xint`, that is a **signal supporting a JIT hypothesis**—still not proof, because interpretation changes timing, performance, and concurrency interactions, which can mask a native race.

**Never enable `-Xint` in production as a default “fix”:** throughput and latency can drop sharply. Test only in an isolated environment, measure crash rates across many runs, and hold inputs and other configuration constant.

### A/B test excluding only a single method from JIT

If the log points to a specific method `demo.FastHash.mix`:

```bash
java -XX:CompileCommand=exclude,demo/FastHash.mix -jar app.jar
```

This HotSpot JDK 17 flag prevents the compiler from compiling the specified method, narrowing the experiment compared to `-Xint`. Use the exact package/class/method from the real build; overloaded method names may require matching signatures. Seeing crashes drop with this flag **does not necessarily** prove a JIT bug because it also alters timing, inlining, and workload behavior. It is a diagnostic experiment that must be paired with a reproducer and core evidence.

## 8. Branch D: HotSpot **CompilerThread Actively Compiling**, Not Compiled Java Code Running

Hypothetical sample:

```text
# Problematic frame:
# V  [libjvm.so+0xa321]

Current thread: JavaThread "C2 CompilerThread0" daemon [_thread_in_vm, id=7201]

Current CompileTask:
... demo.MathKernel.fold(I)J ...
```

What this tells us:

1. Current thread is `C2 CompilerThread0`: HotSpot's compiler implementation is running to **generate machine code**.
2. `Problematic frame: V` says the faulting instruction is in VM code, which makes complete sense because the JIT compiler is implemented inside the VM runtime.
3. `Current CompileTask` shows the method being compiled when the fault occurred. The Java source of that method is the *input* to the JIT; **do not immediately blame the author of that method**.
4. Suspects include a bug in the compiler IR/optimizer/code generation or native memory corruption affecting the compiler.
5. You need the exact JDK patch level, compiler tier, compilation logs (if enabled), method bytecode, flags, and a reproducer.

**This is the core distinction:**

| Label | Thread | Typical frame | Phase |
| --- | --- | --- | --- |
| Crash in **compiled Java method** | `request-worker` / application thread | `J demo.Class.method` | Executing **generated machine code** |
| Crash in **JIT compiler implementation** | `C1 CompilerThread` / `C2 CompilerThread` | Typically `V [libjvm]` | **Compiling/optimizing** a method |
| Interpreted Java bytecode | Application thread | `j demo.Class.method` | Interpreter, **not** JIT execution |

Compiler thread names and `Current CompileTask` formats vary by VM and JDK. Historical docs show examples like `CompilerThread0`/`AdapterCompiler` and `-client`; do not blindly copy workarounds from very old JVMs to JDK 17. Check the options and implementation of the JVM you actually run.

## 9. Crash Site Does Not Equal Root Cause: Two Layers of Evidence

Every triage note should separate into two distinct statements:

- **Observation:** “Crash PC is in `C [libx.so]`”, “VM thread was executing GC”, or “thread `request-7` was running `J Class.method`”.
- **Hypothesis:** “Suspect invalid JNI pointer”, “suspect heap corruption / GC interaction”, or “suspect JIT codegen fault / agent corruption”.

Never turn a hypothesis into a conclusion without corroboration.

### Example 1: crash in VM, yet native code is the source

A native library holds onto a JNI global reference after releasing it, leaving an invalid object reference. The VM crashes while scanning that reference during GC. The header may show `V [libjvm.so]` and a GC-related `VM_Operation`. Concluding “HotSpot GC bug” from the `V` frame alone sends the investigation down the wrong path.

### Example 2: crash in compiled method, yet root cause is JNI

Native code overflows a buffer and corrupts an object or address. An hour later, a request thread runs a JIT-compiled method and hits `SIGSEGV` at `J demo.Index.lookup`. The `J` frame accurately marks **where it was detected**, while the original fault was earlier native corruption.

### Example 3: crash while compiler runs, Java code is input

`Current thread: C2 CompilerThread0` and `Current CompileTask: demo.Algo.compute` may indicate a compiler crash while processing bytecode. It does not mean the Java code has a bad pointer; for valid Java bytecode, the JIT compiler/JVM is responsible for handling it safely. You need a reproducer and JDK/vendor evidence.

### Signals stronger than a single frame

- A small reproducer repeating the same crash **on the exact build**.
- A native core dump and build-matched debug symbols confirming the instruction and memory state.
- Controlled A/B testing changing only the library/agent version or JDK patch level.
- The fault disappears consistently after a targeted fix, verified under equivalent load.
- Whether the crash occurs across multiple machines or only on one hardware/kernel/image.
- Cross-checking loaded libraries, GC/JIT flags, and deployment history.

Even when a workaround stops the crash, keep **“stopped reproducing in tests”** distinct from **“root cause confirmed.”**

## 10. Three-Way Crash Triage Table

| Combined clues | Initial investigation direction | What to rule out / cross-check |
| --- | --- | --- |
| `C [libthirdparty.so]` + `_thread_in_native` + multiple `C` frames | Native library / JNI / ABI / ownership | Core, source, actual loaded binary, other races/corruption |
| `C [libnet.so]` / `C [awt.dll]` from the JDK | JDK native library and OS interactions | Native agents, VM/JDK bug, ABI, system dependencies |
| `V [libjvm.so]` + `VMThread` + GC-related `VM_Operation` | GC/VM runtime crash site | JNI/agent corruption, collector config, VM bug, hardware |
| `V [jvm.dll]` + `C [App.dll]` immediately below on stack | VM crash while called by native caller | JNI contract/reference misuse; do not rush to blame JVM bug |
| `J demo.Method` + `request-worker` | Compiled Java code executing | JIT wrong-code generation, native memory corruption, agents, intrinsics |
| `V [libjvm]` + `C2 CompilerThread` + `Current CompileTask` | HotSpot compiler executing | Compiler bug vs. corrupted compiler state, method input / JDK build |
| `j demo.Method` | Interpreted frame | Check full stack / top PC; do not call this a JIT-compiled frame |
| `v ~StubRoutines` | VM-generated stub/adapter | Adjacent native/Java/VM frames and registers |
| `Internal Error` / `guarantee failed` | VM detected invalid internal state | Exact JDK build, file/line, inputs, flags, memory corruption |
| No `hs_err`, yet `OOMKilled` | OS/container killed the process | cgroup/host logs, memory limits, exit events; do not infer native/JIT bug |

**Reminder:** Markers only classify **the execution region where the fault occurred**. In memory-corruption bugs, the first bad write and the final crash can be far apart in both time and stack frames.

## 11. Post-Incident Fatal Error Log Handling Workflow

### Step 1 — Identify the exact crash

Verify timestamp, PID, process/container, Java command, JDK vendor/build, OS kernel/CPU architecture, app release, loaded libraries/agents, JVM flags, load, and recent changes. Do not confuse an old fatal log with a new deployment.

### Step 2 — Start from the header

Read the signal/internal error, `pc`, `pid`/`tid`, and `Problematic frame`. Identify `C/V/v/J/j` and the module/method; record using observational language instead of labeling the bug prematurely.

### Step 3 — Read the thread and stack

In the `THREAD` section, examine `Current thread`, state, native frames, and Java frames. If it is a compiler thread → find `Current CompileTask`; if `VMThread` → find `VM_Operation`; if `C`/native → check the Java/native transition and library source.

Do not assume every Java stack trace in `hs_err` is an exact method-by-method call stack: inlining, stack corruption, and faults during error reporting can leave logs incomplete. If you see `error occurred during error reporting`, explicitly record the data limitation.

### Step 4 — Identify the actual module and configuration

Cross-check `Dynamic libraries` / memory maps against library versions on disk and inside the container image. Check `VM Arguments`, `java_command`, JDK build, GC/JIT flags, JVMTI agents, and JNI dependencies. Offsets in `libfoo.so+0x...` require the **exact matching binary and debug symbols** to obtain reliable function/source lines; Address Space Layout Randomization (ASLR) also affects addresses.

### Step 5 — Collect corroborating evidence

- **Native core/minidump** (if configured and authorized): native backtrace, registers, memory map, disassembly.
- **GC/JVM logs** when GC/`VMThread` is suspected.
- **JFR/compilation logs** if enabled and persisted prior to crash; recordings may not be fully flushed when a process dies abruptly.
- **OS/Kubernetes/kernel events** to rule out OOM kills, hardware issues, or native memory/resource exhaustion.
- **Heap dump**: useful for object graphs/OOME, but **does not replace a native core** when investigating corrupted C/C++ pointers or JIT machine code.

### Step 6 — Controlled testing in staging

- If native is suspected: swap only the native library version or disable an agent in a controlled test; use `-Xcheck:jni` and native sanitizers where appropriate.
- If compiled JIT code is suspected: compare mixed mode against `-Xint` or targeted `-XX:CompileCommand=exclude`; keep inputs, workload, and other flags identical.
- If VM/GC is suspected: correlate crashes with GC logs, vendor issues, agents/JNI, changing collector or JDK update **one variable at a time** when permitted.
- Measure frequency across repeated runs. A single non-reproducing run may simply reflect changed race/timing behavior.

### Step 7 — Report to the right owner

Application library → native code team. Third-party library → vendor with symbolicated trace/reproducer. Suspected HotSpot/JDK → report to JDK vendor/bug tracker with exact version, reproducer, flags, test results, and redacted logs/core per policy. **Workarounds** must be documented separately from a **confirmed root cause**.

## 12. Commands to Extract Key Lines from a Fatal Log (Linux)

Assuming the file is confirmed to be a copy from the exact crash:

```bash
grep -n -E 'SIGSEGV|SIGBUS|SIGILL|Internal Error|Problematic frame|Current thread|VM_Operation|Current CompileTask|Native frames|Java frames|Dynamic libraries' hs_err_pid3015.log
```

Read the header and start of the thread section:

```bash
sed -n '1,140p' hs_err_pid3015.log
```

Both commands are read-only. If `grep` finds no `Current CompileTask`, the log may simply lack that section; it does not mean no compilation was happening. If the log is truncated, avoid filling in unobserved details.

If you **already have a native core** with the matching executable and symbols, you can use a debugger in an authorized environment:

```bash
gdb -q /path/to/java /path/to/core
```

Core analysis must verify the exact executable/JDK/library build; mismatched symbols produce wrong stack and function names. On Windows, use WinDbg or equivalent Visual Studio dump tools. Never attach a debugger to a production process without authorization.

## 13. Standalone Java 17 Example: Reading Frame Markers **Without Causing a Crash**

The small program below only parses **three simulated log strings**. It does not touch native memory, does not raise `SIGSEGV`, and does not modify JVM flags. Its purpose is to show the frame marker corresponding to each execution region; it **does not automatically find root causes**.

Create **`CrashFrameClues.java`**:

```java
public final class CrashFrameClues {
    static String frameKind(String log) {
        boolean afterHeader = false;

        for (String raw : log.split("\\R")) {
            String line = raw.trim();
            if (line.startsWith("#")) {
                line = line.substring(1).trim();
            }

            if (!afterHeader) {
                if (line.equals("Problematic frame:")) {
                    afterHeader = true;
                }
                continue;
            }

            if (line.isEmpty()) {
                continue;
            }

            if (line.length() < 2 || !Character.isWhitespace(line.charAt(1))) {
                return "UNKNOWN";
            }

            return switch (line.charAt(0)) {
                case 'C' -> "NATIVE_FRAME";
                case 'V' -> "VM_FRAME";
                case 'v' -> "VM_STUB_FRAME";
                case 'J' -> "COMPILED_JAVA_FRAME";
                case 'j' -> "INTERPRETED_JAVA_FRAME";
                default -> "UNKNOWN";
            };
        }

        return "UNKNOWN";
    }

    public static void main(String[] args) {
        String[] sampleLogs = {
            "# Problematic frame:\n# C  [libdemo.so+0x20]\n",
            "# Problematic frame:\n# V  [libjvm.so+0x44]\n",
            "# Problematic frame:\n# J 301 c2 demo.Hash.mix([B)I\n"
        };

        for (int i = 0; i < sampleLogs.length; i++) {
            System.out.println("case" + (i + 1) + "="
                    + frameKind(sampleLogs[i]));
        }
    }
}
```

Compile and run:

```bash
javac --release 17 CrashFrameClues.java
java CrashFrameClues
```

**Exact output when the program runs successfully:**

```text
case1=NATIVE_FRAME
case2=VM_FRAME
case3=COMPILED_JAVA_FRAME
```

Interpretation:

- `case1`: crash instruction is in native code; inspect library name, stack, and JNI.
- `case2`: crash instruction is in the HotSpot VM; still inspect current thread, VM operation, and native callers.
- `case3`: compiled Java code was running; inspect thread, JIT, and potential native corruption.

**Intentional limitation:** this code only reads the marker right under `Problematic frame` in **simple samples**; it is not a production parser for every `hs_err` across OSes and JDKs. It does not validate symbols, registers, corrupted stacks, or compile tasks. Real files must be read with a forensic eye across multiple evidence sections.

## 14. Scenario Analysis

### Scenario A — Crashes start after upgrading a native image codec

A JVM shows `C [libcodec.so+...]`, `_thread_in_native`, and the same stack in `decode`; testing the same input in staging reproduces the crash consistently, and rolling back the native codec makes the failure disappear.

**Right approach:** this is strong evidence involving the native codec or its ABI/OS interaction. Capture core dumps and symbols, and inspect pointers, buffers, and lifetimes. Still distinguish **the library where it crashed** from **an actual bug inside that library**, as a third party could be corrupting memory.

### Scenario B — `V [libjvm]` crash in GC after upgrading a JVMTI agent

`VM_Operation` shows GC, current thread is `VMThread`; the agent loaded into the JVM was just updated. Concluding “JVM GC bug” would skip checking whether JVMTI/JNI corrupted the object graph.

**Right approach:** preserve core/GC/JVM logs, run an A/B test of the agent version in staging, use a supported JDK patch, and check for memory corruption.

### Scenario C — `J demo.Transform.hash` on a request thread

The crash reproduces repeatedly when running compiled code, while `-Xint` does not reproduce across a batch of tests. This is a **JIT-suspect signal**, though altered scheduling could also hide a native race. If targeted method exclusion also eliminates the crash, the JIT hypothesis becomes stronger. Still provide a reproducer and core dump, and check JNI/agents.

### Scenario D — `V [libjvm]` on `C2 CompilerThread`

`Current CompileTask` lists `demo.Transform.hash`. The fault occurred while the compiler **was generating code**, not on a request thread executing `J` code. Investigate the compiler implementation, method bytecode, tiered flags, exact JDK build, and possible memory corruption; avoid blaming Java business logic merely because the method name appears.

## 15. Common Mistakes

1. **“`C` is always a third-party library bug.”** No: `C` marks a native frame location, including JDK-native or OS-native code.
2. **“`V` means HotSpot is definitely the root cause.”** A native caller may have corrupted memory earlier.
3. **“`J` means Java source code caused a segfault.”** It indicates JIT-compiled machine code executing, which does not by itself prove a Java source error or a JIT compiler bug.
4. **“`j` means JIT.”** Lowercase `j` is an interpreted frame; uppercase `J` is a compiled Java frame.
5. **“CompilerThread crashes always show `J`.”** The compiler implementation generally runs in `V`; `J` is already-compiled code executing.
6. **“`SIGSEGV` is a Java `NullPointerException`.”** They are two different mechanisms; a Java NPE normally does not crash the VM.
7. **“Crash during GC means just raise `-Xmx`.”** Groundless; it could be heap corruption, JNI, or a VM bug.
8. **“`-Xint` stops the crash ⇒ proves a JIT bug.”** The interpreter changes performance and timing, which easily masks races.
9. **“`-XX:CompileCommand=exclude` is a side-effect-free fix.”** It can hurt performance or alter codegen; use only for controlled testing.
10. **“No `hs_err` means no crash.”** The OS may have killed the process or the file could not be written.
11. **“A heap dump is enough to investigate a native crash.”** It does not replace a native core, registers, or symbols.
12. **“`libfoo.so+0x10` immediately reveals the source line.”** You need the exact binary, debug symbols, and relocation/load map.
13. **“`Current CompileTask` means a developer wrote a broken Java method.”** The compiler is processing input bytecode; root cause is not yet established.
14. **“One non-reproducing run means it's fixed.”** Race/timing-sensitive crashes require repeated A/B runs.
15. **“Raw core/fatal logs can be posted publicly.”** They may contain secrets and must be handled securely.
16. **“Every JVM fatal crash is a JDK bug.”** Native libraries, agents, OS, hardware, and resource limits can all cause crashes.

## 16. Self-Check Questions

**Q1.** `Problematic frame: C [libvendor.so+0x3d]`, current thread `_thread_in_native`. What should you do?  
**Answer:** Investigate native code/JNI, the exact binary, stack/core/symbols, and inputs. Do not assert the bug belongs to the vendor solely from the frame.

**Q2.** `Problematic frame: V [jvm.dll]`, next stack frame is `C [App.dll]`. Can you conclude a JVM bug?  
**Answer:** No; the VM is the crash site, and the JNI caller may have passed an invalid reference or caused memory corruption.

**Q3.** Is `Problematic frame: J demo.FastPath.run` on a request worker a crash while the JIT compiler is generating code?  
**Answer:** No. This indicates **executing already-compiled Java code**.

**Q4.** `Problematic frame: V`, current thread `C2 CompilerThread0`, with `Current CompileTask`. Why does this differ from Q3?  
**Answer:** The compiler thread is **actively compiling** the method, not an application thread executing compiled Java machine code.

**Q5.** Testing with `-Xint` no longer crashes. Have you proved a JIT bug?  
**Answer:** Not yet. It could be the compiler, or timing changes could be masking a native race.

**Q6.** `VMThread` hit a fatal error during a GC `VM_Operation`. What other sources must be checked?  
**Answer:** JNI/JVMTI agents, heap corruption, GC logs, collector flags, core dump, exact JDK build, and OS/hardware.

**Q7.** A pod was `OOMKilled` with no `hs_err`. Should you look for compiled code `J` first?  
**Answer:** No; prioritize cgroup/kernel memory events because the kernel can kill the JVM from outside.

**Q8.** Why can't you use `libfoo.so+offset` alone to pinpoint a source line?  
**Answer:** You need the exact binary, symbols, build, relocation/ASLR info, and load addresses. The module name is only a clue.
