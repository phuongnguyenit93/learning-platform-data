# Heap, Metaspace, and JIT-Compiled Machine Code

In the JVM, a Java application can use multiple memory regions for different purposes. Three regions that are frequently confused are **Java Heap**, **Metaspace**, and **Code Cache**. The Heap holds object data; Metaspace holds metadata describing loaded classes; Code Cache holds machine code generated by the JIT compiler so the JVM can execute faster.

This distinction is especially useful when working with **CRaC (Coordinated Restore at Checkpoint)**. CRaC creates a checkpoint of a running process and then restores that process on a subsequent startup. Therefore, object state, class-loading state, and JVM compilation state can affect startup time, checkpoint size, and memory consumption after restore.

## 1. Overview of Memory Regions

The JVM specification describes runtime data areas such as the heap, method area, runtime constant pool, Java stack, and native method stack. **Metaspace** and **Code Cache** are how HotSpot implements parts of that model; they are not mandatory memory region names that every JVM implementation must use.

In modern HotSpot, the relevant regions can be visualized as follows:

```text
Java Process
│
├── Java Heap
│   ├── Objects
│   ├── Arrays
│   └── GC regions (e.g., Eden, Survivor, Old)
│
├── Metaspace (native memory)
│   ├── Class metadata
│   ├── Method metadata
│   └── Class-related runtime structures
│
├── Code Cache (native memory)
│   ├── JIT-compiled machine code
│   ├── Runtime stubs
│   └── JVM-generated code snippets
│
└── Other regions
    ├── Per-thread Java stack
    ├── Direct buffers / native allocations
    ├── Native libraries and JVM internal structures
    └── Memory for GC, compiler, and threads
```

Heap, Metaspace, and Code Cache can all grow together in an application, but they do not store the same kind of data and are not tuned using the same JVM flags. Setting a larger `-Xmx` only increases the heap limit; it does not automatically grant more Metaspace or Code Cache.

## 2. Java Heap: Where Objects and Arrays Live

### 2.1. Role of the Heap

The Java Heap is the runtime memory area used to allocate objects and arrays. The heap is shared among threads within the same JVM. When the program executes:

```java
Customer customer = new Customer("An");
int[] scores = new int[100];
```

the `Customer` and `int[]` objects are allocated on the heap under the standard execution model. The local variables `customer` and `scores` are references; when they are local variables inside a method, the storage location for the reference variable is typically tied to the thread's stack frame, while the referenced object resides on the heap.

The JIT can optimize some allocations via escape analysis and scalar replacement. Therefore, you should not conclude that every `new` expression in source code necessarily produces a physical object existing on the heap after optimization.

### 2.2. Heap and Garbage Collection

The heap is managed by the Garbage Collector (GC). The GC identifies objects still reachable from GC roots, then reclaims or reuses the memory of objects that are no longer reachable.

Some common concepts in HotSpot:

- **Young Generation**: the area for newly allocated objects. In generational configurations, this area typically contains Eden and Survivor spaces.
- **Old Generation**: where longer-lived objects may be promoted.
- **Eden**: where most new objects are allocated in generational collectors.
- **Survivor**: the area holding objects that survive one or more Young Generation collections.

This is a common organization, though layout details depend on the chosen GC. G1 organizes the heap into regions; ZGC has its own mechanism and structure. Do not mechanically apply the Eden/Survivor/Old diagram to every collector.

### 2.3. Sizing the Heap

Two basic flags:

```bash
java -Xms512m -Xmx2g -jar application.jar
```

- `-Xms`: initial heap size and the minimum level the JVM targets.
- `-Xmx`: maximum heap size.

The values above are syntax examples only, not allocation recommendations for every application. When choosing heap size, consider the machine or container memory limit, concurrent request count, size of long-lived data, GC pauses, and the native memory the process still needs.

If the heap is too small, GC may run frequently and the application may encounter `OutOfMemoryError: Java heap space`. If the heap is too large relative to the container limit, the process can still be terminated by the OS for exceeding the memory limit even before Java Heap reaches `-Xmx`.

### 2.4. What Does Not Live in the Heap

Not all data used by a Java application resides on the heap. For example:

- HotSpot class metadata resides in Metaspace.
- Machine code generated by the JIT resides in Code Cache.
- Thread stacks are separate memory areas per thread.
- Direct `ByteBuffer` instances can use native memory.
- JNI libraries and native libraries can allocate memory off-heap.

This is why RSS or total container memory can be significantly higher than used heap.

## 3. Metaspace: Metadata of Loaded Classes

### 3.1. What Does Metaspace Store?

When the JVM loads a class, it must store information to understand and execute that class: class structure, field and method descriptors, bytecode, the runtime constant pool, and related metadata structures. In HotSpot, most of this class metadata is allocated in **Metaspace**, using native memory rather than Java Heap.

Metaspace was introduced in Java 8 to replace PermGen from older HotSpot versions. Consequently, legacy Java documentation or configurations may mention `PermGen`, `-XX:PermSize`, or `-XX:MaxPermSize`; those are not how Metaspace is tuned on modern JVMs.

Several distinctions to keep in mind:

- An instance such as `new Customer()` belongs to the Heap.
- Metadata describing class `Customer` belongs to JVM-managed metadata memory, which in HotSpot is typically Metaspace.
- The `java.lang.Class` object representing the class is a Java object on the Heap.
- Static field values are associated with the class mirror and how the JVM represents data; do not conclude that all static fields are stored directly inside Metaspace.
- String literals/interned strings are managed as objects on the Heap, even though the class constant pool metadata may reference them.

### 3.2. ClassLoader and Metaspace Lifecycle

A class is tied to the ClassLoader that defined it. In HotSpot, class metadata can be reclaimed when a class is unloaded; unloading usually happens only when the ClassLoader defining that class is no longer reachable and the JVM performs a GC cycle capable of class unloading.

This explains why an application can experience continuous Metaspace growth even when the number of objects on the Heap does not grow proportionally. Common causes include:

- The application continuously generates dynamic classes or proxies.
- A framework creates many classes across configurations or deployments.
- An old ClassLoader remains retained by static references, threads, ThreadLocals, callbacks, or caches.
- The application hot-reloads, yet the old version's ClassLoader is not released.
- Classes are loaded in large numbers and remain needed throughout the application's lifetime.

A ClassLoader leak can retain both metadata in Metaspace and objects on the Heap. Therefore, when investigating, inspect class loading/unloading, reference chains, and ClassLoader lifecycles rather than looking at a single heap metric.

### 3.3. Metaspace Flags

Example:

```bash
java -XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=512m -jar application.jar
```

- `-XX:MetaspaceSize` is an initial threshold related to when the JVM considers triggering GC based on Metaspace usage; it is not a simple hard limit equivalent to `-Xmx`.
- `-XX:MaxMetaspaceSize` sets the maximum limit for Metaspace.
- `-XX:CompressedClassSpaceSize` adjusts the space reserved for compressed class pointers when the corresponding feature is enabled.

Do not set `MaxMetaspaceSize` too low merely to save memory. As Metaspace approaches its limit, the JVM may need GC and class unloading to reclaim metadata. If not enough can be reclaimed, the application can encounter `OutOfMemoryError: Metaspace` or compressed class space errors.

## 4. JIT and Code Cache: Machine Code Generated at Runtime

### 4.1. From Bytecode to Machine Code

The Java compiler normally compiles source code into bytecode in `.class` files. At runtime, the JVM can execute bytecode via the interpreter. HotSpot also profiles execution behavior, such as which methods are called frequently and which branches are commonly taken. When a method or code segment becomes hot enough, the JIT compiler can compile it into machine code tailored to the running CPU architecture.

Conceptual flow:

```text
.java
  │ javac
  ▼
.class (bytecode)
  │
  ▼
JVM interpreter + runtime profiling
  │
  ├── Infrequently called code: continue interpreting
  │
  └── Hot enough code
        │
        ▼
      JIT compiler
        │
        ▼
      Native machine code
        │
        ▼
      Code Cache
        │
        ▼
      CPU executes machine code
```

HotSpot typically uses multiple compilation tiers. C1 can generate code quickly with lower compilation cost; C2 performs deeper optimizations at higher compilation cost. When tiered compilation is enabled, the JVM may progress through multiple tiers before a method reaches higher optimization levels. Details depend on the JVM version and runtime options.

The JIT can also perform **On-Stack Replacement (OSR)** to transition a running loop from the interpreter into compiled code. Some optimizations rely on assumptions about data types or runtime behavior. When an assumption no longer holds, the JVM can deoptimize and fall back to a less optimized execution level to continue profiling or recompile.

### 4.2. What Does Code Cache Contain?

In HotSpot, **Code Cache** is the native memory area used to store JVM-generated machine code, including compiled methods (often called nmethods) and certain stubs/runtime code. The CPU can execute these code segments directly.

Code Cache is not Java Heap:

- GC manages objects on the Heap.
- The JIT compiler generates and manages machine code in Code Cache.
- A compiled method is not a regular Java object that the application holds via a reference.
- Removing objects from the Heap does not mean corresponding machine code immediately disappears from Code Cache; the JVM manages compiled code lifetimes separately.

In some HotSpot versions with segmented code cache, code segments are partitioned into areas such as non-method, profiled, and non-profiled code. This is an implementation detail that can change across JVM versions and configurations.

### 4.3. When Code Cache Becomes Full

If Code Cache runs low on space, the JVM may struggle to compile new methods. Depending on the JVM version and code cache state, the JVM may sweep unused compiled code, yet if insufficient space is freed, JIT compilation may be restricted or halted. The application can still run using the interpreter and existing valid compiled code, though performance may degrade.

Commonly used flags:

```bash
java -XX:InitialCodeCacheSize=32m -XX:ReservedCodeCacheSize=240m -jar application.jar
```

- `-XX:InitialCodeCacheSize` sets the initial capacity.
- `-XX:ReservedCodeCacheSize` sets the maximum reserved Code Cache capacity.

Numbers should be chosen based on JDK version, workload, and the number of genuinely hot methods. Increasing Code Cache does not fix the root cause of excessive class/method generation and does not replace measurement.

## 5. Comparing the Three Memory Regions

| Criterion | Java Heap | Metaspace | Code Cache |
|---|---|---|---|
| Primary data | Objects and arrays | Class metadata | JVM/JIT-generated machine code |
| Location in HotSpot | Java heap | Native memory | Native memory |
| Primary manager | Garbage Collector | Class loading/unloading and metadata management | JIT compiler and compiled code management |
| Grows when | Number/size of live objects grows | More classes are loaded or metadata grows | More methods are compiled or code is generated |
| Related errors/symptoms | `OutOfMemoryError: Java heap space` | `OutOfMemoryError: Metaspace` | Full Code Cache, JIT compilation restricted |
| Common flags | `-Xms`, `-Xmx` | `-XX:MetaspaceSize`, `-XX:MaxMetaspaceSize` | `-XX:InitialCodeCacheSize`, `-XX:ReservedCodeCacheSize` |

These three regions interact within the same process but must be monitored separately. An application may have ample free heap space yet run out of Metaspace; likewise, Heap and Metaspace may be stable while Code Cache nears full capacity.

## 6. How Does CRaC Affect These Memory Regions?

### 6.1. A Checkpoint Saves Process State

CRaC coordinates between the JVM and OS checkpoint/restore mechanisms to save the state of a running process. Upon restore, the process is recovered from the checkpoint instead of executing the entire application startup from the beginning.

The key point is that a CRaC checkpoint is not like serializing individual objects into a portable data format. It saves process state subject to runtime/platform mechanisms and constraints. Therefore, a checkpoint depends tightly on a compatible environment: JVM build, architecture, native libraries, configuration, and supported OS conditions.

Regarding the three memory regions:

- **Heap**: objects, arrays, caches, and application state existing at checkpoint time are part of the process's memory state. Objects already created and still reachable can be ready immediately after restore.
- **Metaspace**: loaded class state and JVM-managed metadata are part of the process's runtime state. The application can avoid reloading and relinking classes already prepared before checkpoint.
- **Code Cache**: JIT-generated machine code is stored in the process's native memory. When checkpoint/restore preserves the corresponding memory pages, compiled code can be restored along with the process. Whether a specific compiled method continues to be used, gets invalidated/deoptimized, or is recompiled depends on the JVM build, platform, and runtime conditions; verify using logs and performance measurements in the actual deployment environment.

Accordingly, an application can be prepared before checkpoint to reduce post-restore startup work, but you should not assume every class or every piece of JIT code will always remain intact and used across every environment.

### 6.2. Pre-Checkpoint Warm-Up

If a checkpoint is taken immediately after the JVM has just started, many classes may not yet be loaded, application caches remain empty, and critical methods are not hot enough for JIT compilation. After restore, the application still has to perform part of the initialization and warm-up work.

A preparation workflow may include:

1. Start the application with the exact JVM and configuration intended for deployment.
2. Execute safe initialization steps: load configuration, prepare dependencies, initialize needed caches.
3. Send representative workloads through critical processing paths so classes are loaded and hot methods have a chance to be JIT-compiled.
4. Observe Heap, Metaspace, Code Cache, GC, and processing times to confirm the state has stabilized.
5. Bring the application into a checkpointable state: no in-flight requests or tasks that the application cannot safely recover.
6. Perform the checkpoint and verify post-restore behavior under the exact expected deployment conditions.

The warm-up workload should represent real traffic. Calling only a simple endpoint may warm part of the code while missing critical processing paths. Conversely, overly broad warm-up can bloat the heap with unnecessary caches, load too many classes, or enlarge Code Cache, making the checkpoint larger and increasing post-restore memory usage.

### 6.3. Memory State and External Resources

Not everything the application sees is preserved in the same way as memory pages. Network connections, sockets, file descriptors, threads interacting with the OS, leases, expiring tokens, and database connections may need to be closed before checkpoint or recreated after restore.

CRaC provides a resource callback registration mechanism, typically via `org.crac.Resource`, so the application can prepare before checkpoint and recover after restore. Skeleton example:

```java
import org.crac.Context;
import org.crac.Core;
import org.crac.Resource;

public final class AppResource implements Resource {

    public AppResource() {
        Core.getGlobalContext().register(this);
    }

    @Override
    public void beforeCheckpoint(Context<? extends Resource> context)
            throws Exception {
        // Stop accepting new work, close or release resources requiring handling.
    }

    @Override
    public void afterRestore(Context<? extends Resource> context)
            throws Exception {
        // Recreate connections and refresh time-dependent resources.
    }
}
```

This is an illustrative skeleton. Concrete behavior must match the library in use and the CRaC version. Callbacks help the application manage resources; they do not replace understanding the state of Heap, Metaspace, and Code Cache at checkpoint time.

## 7. Monitoring and Diagnostics

When an application runs for a long time or after restore, identify which memory region is growing. Do not look only at total RAM or heap usage and immediately conclude it is a memory leak.

### 7.1. Inspecting Heap

```bash
jcmd <pid> GC.heap_info
```

This command provides current heap and GC information. It can be combined with GC logs:

```bash
java -Xlog:gc*,safepoint=info -jar application.jar
```

GC logs help observe collection frequency, heap sizes before/after GC, and pause times. If you need to investigate objects retaining memory, capture a heap dump with an appropriate tool and analyze the dominator tree, retained sizes, and reference chains.

### 7.2. Inspecting Metaspace and Native Memory

Native Memory Tracking (NMT) can be enabled at startup:

```bash
java -XX:NativeMemoryTracking=summary -jar application.jar
```

Then query:

```bash
jcmd <pid> VM.native_memory summary
```

NMT helps categorize a portion of JVM-managed native memory. NMT must be enabled from JVM startup and has overhead; its metrics do not always cover all native allocations performed by third-party libraries.

To monitor class loading and unloading:

```bash
java -Xlog:class+load=info,class+unload=info -jar application.jar
```

If Metaspace grows continuously, correlate loaded class count, unloaded class count, ClassLoader count, and references retaining ClassLoaders. Increasing `MaxMetaspaceSize` can delay the error but does not fix a ClassLoader leak.

### 7.3. Inspecting Code Cache and JIT

On HotSpot builds supporting the corresponding diagnostic command, you can view Code Cache statistics:

```bash
jcmd <pid> Compiler.codecache
```

To log compilation activity:

```bash
java -Xlog:jit+compilation=debug -jar application.jar
```

Check used capacity, remaining capacity, number of compiled methods, and Code Cache full messages. When evaluating CRaC, compare metrics before checkpoint and after restore, while also measuring latency of representative endpoints. A restored Code Cache size by itself does not prove that every critical method executes in compiled machine code after restore.

### 7.4. Interpreting Different Error Types

| Symptom | Area to check first | Investigation direction |
|---|---|---|
| `OutOfMemoryError: Java heap space` | Heap | Long-lived retained objects, unbounded caches, heap too small, or increased workload |
| `OutOfMemoryError: Metaspace` | Metaspace | Continuous class growth, ClassLoader leak, Metaspace limit too low |
| Errors related to `Compressed class space` | Compressed class space | Class count and compressed class pointer configuration |
| Logs indicating Code Cache full or compiler disabled | Code Cache | Code Cache capacity, compiled method count, and JIT activity |
| Container OOM killed even though heap is not full | Total process/container memory | Metaspace, Code Cache, thread stacks, direct buffers, native libraries, and other memory |

A heap dump is useful for object graphs, but insufficient to explain all native memory. Conversely, NMT helps inspect JVM native memory categories but does not replace a heap dump when locating reference-retaining objects.

## 8. Common Mistakes When Optimizing for CRaC

### Increasing only `-Xmx` when total RAM rises

`-Xmx` sets only the Java Heap limit. If Metaspace, Code Cache, direct buffers, or thread stacks are growing, increasing the heap can make total process memory even larger and cause the container to hit its limit sooner.

### Assuming Metaspace stores all static objects

Static fields are associated with a class, but that does not mean all static values live directly in Metaspace. Objects referenced by static fields remain objects on the Heap. A static cache can grow the Heap even when class count and Metaspace remain unchanged.

### Assuming Code Cache stores bytecode

Bytecode resides in class representations and is managed by the JVM alongside class state. Code Cache primarily stores machine code generated during execution, along with certain JVM-generated runtime code.

### Checkpointing as late as possible

Checkpointing after warm-up can reduce post-restore work, but waiting too long can bloat caches, retain unnecessary temporary data, increase loaded classes, or enlarge the checkpoint. Choose the timing based on measurements and business state.

### Assuming every connection remains valid after restore

A Java object representing a connection may still exist in the restored Heap, while the OS/server socket or session has expired. Resource callbacks must close, recreate, or revalidate environment-dependent resources.

### Raising limits without finding the root cause

Increasing `MaxMetaspaceSize` or `ReservedCodeCacheSize` may give the application more headroom, but if classes are generated without bound or the workload causes the JIT to emit excessive code, the underlying issue remains. Identify the growing region, growth rate, and root cause before tuning.

## 9. Practical Verification Workflow

When optimizing a Java application with CRaC, you can follow this workflow:

1. **Record a pre-checkpoint baseline**: heap used/committed, GC activity, Metaspace, Code Cache, loaded class count, RSS, and request processing times.
2. **Run controlled warm-up**: use a representative workload, avoiding unnecessary test data generation or altering business state.
3. **Inspect memory regions**: determine whether heap grows from live objects, Metaspace grows from classes, or Code Cache grows from JIT compilation.
4. **Check checkpoint conditions**: handle in-flight requests, threads, and off-memory resources per CRaC and application library requirements.
5. **Create checkpoint and restore**: verify the application starts up and serves requests successfully in a compatible environment.
6. **Re-measure after restore**: compare time-to-readiness, representative workload latency, GC, class loading, and JIT compilation.
7. **Iterate with different configurations**: change only one group of parameters at a time to see which change produces the effect.

A good checkpoint does not just have a short restore time. The application must also have valid business state, functioning external resources, memory within deployment limits, and stable performance under real traffic.

## 10. Things to Remember When Reading JVM Metrics

When reading a memory report, distinguish three concepts:

- **Used**: amount of data currently in use.
- **Committed**: amount of memory the JVM has committed for potential use under the memory region's management mechanism.
- **Reserved**: address space reserved in advance; reserved does not mean the entire region occupies physical RAM.

Therefore, do not add up all reserved values to infer actual RAM usage. RSS reflects resident memory pages of the process, whereas Heap, Metaspace, Code Cache, and NMT metrics each have their own measurement methods and scopes.

When reading logs or dashboards, always clarify whether metrics refer to Heap, native memory, Code Cache, committed, or reserved memory. This is the first step to distinguishing a heap leak, a ClassLoader leak, Code Cache pressure, and high native memory usage after CRaC restore.
