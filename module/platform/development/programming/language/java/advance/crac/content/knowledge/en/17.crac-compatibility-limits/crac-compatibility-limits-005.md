# Limits on Changing Heap, GC, and JVM Flags by Build

A CRaC checkpoint saves the state of a running Java process. That state includes not only objects in the heap, but also memory management structures, garbage collector (GC) state, the JIT code region, threads, native memory, and many internal JVM components. Therefore, a checkpoint is tightly coupled to the JDK build and JVM configuration used when creating the image.

A checkpoint created with a specific heap and GC configuration should not be treated as data that can be arbitrarily restored with a different JDK, a different collector, or a different set of JVM flags. Changing parameters such as `-Xms`, `-Xmx`, `-XX:+UseG1GC`, compressed object pointers, object alignment, or options affecting runtime structures can cause the restore environment to no longer match the saved state.

The safe operational principle is to **pin the JDK vendor/build and the set of JVM flags that created the checkpoint; if you need to change the heap, GC, or flags affecting the runtime, create a new checkpoint from the new configuration**. Only make changes when the documentation of the exact JDK distribution confirms that the option is allowed to change during restore and the exact deployment combination has been tested.

## 1. Why Are Heap and GC Configurations Coupled to the Checkpoint?

The JVM manages memory using many structures beyond the application's object graph. When the process is checkpointed, these memory regions and runtime structures are part of the state that needs to be restored.

Related components include:

- **Java heap:** the region containing objects, arrays, and application data.
- **Heap reservation and commit:** the address range reserved by the JVM and the memory committed for the heap.
- **Object layout:** how the JVM represents object headers, references, and alignment.
- **GC metadata:** regions, card tables, remembered sets, marking state, free lists, or equivalent collector structures.
- **Native memory:** off-heap memory used by the JVM, GC, native libraries, and application.
- **Code cache:** the region storing machine code generated by the JIT compiler.
- **Thread stacks:** stack regions of existing threads.
- **Runtime metadata:** class metadata, classloaders, synchronization structures, and other internal state.

These structures are created and managed according to the specific JVM configuration. If restored with a different configuration, you cannot assume the JVM will automatically convert all saved state to the new layout or policy.

## 2. Heap Sizing: `-Xms` and `-Xmx`

Two commonly used heap sizing options:

- `-Xms`: initial heap size requested by the JVM.
- `-Xmx`: maximum heap limit.

For example:

```bash
java -Xms512m -Xmx2g -jar app.jar
```

These values affect how the JVM reserves, commits, and manages the heap. A process checkpointed with `-Xms512m -Xmx2g` has formed its memory state under that configuration. Upon restore, changing to `-Xms1g -Xmx4g` is not merely changing a configuration number: the heap and runtime structures already present in the image must continue under the corresponding assumptions.

Therefore, keep heap sizing unchanged at restore, unless the JDK vendor clearly documents changeability and confirms the new configuration is compatible.

### 2.1. Impact of Changing `-Xmx`

Changing `-Xmx` can alter:

- the heap limit the JVM is allowed to use;
- GC sizing and ergonomics decisions;
- the number of regions or region size in region-based collectors;
- GC trigger thresholds and allocation behavior;
- the amount of memory the container must provide.

If a checkpoint was created with a large maximum heap but the restore container has a lower memory limit, the process may fail to restore, be constrained by the OS/container runtime, or hit OOM after receiving load. Conversely, increasing `-Xmx` at restore does not guarantee the JVM can safely expand the saved heap state.

### 2.2. Impact of Changing `-Xms`

`-Xms` affects the initial heap amount the JVM commits or manages according to runtime policy. Changing this value can alter the memory footprint and heap expansion behavior. At restore, the heap state is already present in the checkpoint; `-Xms` should not be treated as an independent parameter that can be changed arbitrarily.

### 2.3. Choosing Heap Sizing Before Creating a Checkpoint

Heap sizing should be chosen based on the workload and checkpoint environment limits:

1. Measure heap usage under a representative workload.
2. Determine allocation rate and GC behavior.
3. Measure native memory, thread stacks, code cache, and off-heap memory.
4. Leave headroom for restore, callbacks, and load after the instance becomes ready.
5. Cross-check against the container memory limit and node capacity.
6. Run a test restore under the exact projected resource limits.

Do not set `-Xmx` equal to the entire container memory limit. The JVM also needs native memory, thread stacks, direct buffers, metaspace, code cache, and other memory regions. The container also needs room for agents, native libraries, and auxiliary processes if present.

## 3. Object Layout and Flags Affecting Memory Representation

Certain JVM flags affect how the JVM represents objects and references. They can impact object size, how the heap is accessed, and internal runtime assumptions.

Examples of common options in HotSpot:

- `-XX:+UseCompressedOops`: uses compressed ordinary object pointers under conditions supported by the JVM.
- `-XX:+UseCompressedClassPointers`: compresses class pointers in object metadata.
- `-XX:ObjectAlignmentInBytes=<n>`: adjusts object alignment in supporting JVM builds.
- Options related to heap base, pointer compression, or other internal layout details.

These options depend on architecture, heap size, and JVM build. Some may be automatically chosen by JVM ergonomics rather than specified by the operator.

When a checkpoint is created, the object graph already exists with the layout chosen by the JVM. Do not change layout-affecting flags at restore without explicit documentation confirming compatibility. Record the effective values as well, not just the flags typed on the command line.

### 3.1. Default Values Are Also Part of the Configuration

If `UseCompressedOops` is not specified, the JVM may automatically enable or disable it depending on architecture and heap sizing. Two environments using the same command line but different memory limits or JDK builds can end up with different effective values.

Therefore, saving only the launch script is not enough. You must record effective flags and runtime information from the checkpoint-creating process itself.

## 4. GC Collectors and Internal State

The garbage collector manages the heap using its own structures and algorithms. A checkpoint saves the process state, including the collector's runtime structures. Therefore, the collector chosen at checkpoint creation is a critical part of the configuration set that must remain stable.

Common HotSpot collectors have different designs, for example:

| Collector | General Characteristics | What Must Be Pinned When Creating a Checkpoint |
| --- | --- | --- |
| Serial GC | Collects in a simple manner, typically used for small heaps or specific environments | Collector configuration and related heap parameters |
| Parallel GC | Prioritizes throughput, uses parallel workers during GC | Collector, worker count, and key sizing parameters |
| G1 GC | Divides heap into regions and balances pause time/throughput | Collector, region/heap ergonomics, and G1 flags |
| ZGC | Low-latency collector with its own heap management structures | Collector, operating mode, and JDK-specific ZGC flags |
| Shenandoah | Concurrent collector with its own heap management mechanism | Collector and options supported in the exact build |

You cannot take a checkpoint created with one collector and arbitrarily restore it with another collector. For example, `-XX:+UseG1GC` and `-XX:+UseZGC` are not interchangeable options that can be swapped at the restore step like changing an application configuration variable.

### 4.1. G1 GC

G1 divides the heap into many regions and maintains metadata for marking, remembered sets, evacuation, and collection set selection. Heap size, region size, worker count, and G1 options affect how the collector organizes and operates.

If you change `-XX:+UseG1GC`, heap sizing, or G1 flags between checkpoint creation and restore, the saved runtime state may no longer be compatible with the new configuration. Keep the collector and key flags unchanged; to change G1 policy, restart the application with the new configuration, warm up, and create a new checkpoint.

### 4.2. ZGC and Other Collectors

ZGC and concurrent collectors have their own memory management structures. Collector options can change how the heap is mapped, how references are handled, and how native memory is used. Modes and flag names can also change between JDK releases.

Do not assume that the same collector name means the same implementation across all JDKs. Record the exact JDK build and check that release's documentation. If upgrading the JDK or changing the collector, create a new checkpoint rather than reusing the old image.

### 4.3. GC State Is Not Only Heap Contents

A heap with the same object contents can still be managed by different GC structures. The GC also tracks memory regions, metadata, phases, reference processing, and internal state. Therefore, compatibility cannot be evaluated merely by comparing object counts or heap used.

Restore must maintain consistency among the heap, the collector's metadata, and the runtime that created them.

## 5. Groups of JVM Flags to Distinguish

Not every JVM flag has the same degree of impact. When packaging a checkpoint, categorize flags to know which parts must be strictly pinned and which parts may be changed according to JDK documentation.

| Group | Examples | Management Approach |
| --- | --- | --- |
| Heap sizing | `-Xms`, `-Xmx`, `-Xmn` if used | Keep unchanged between checkpoint and restore |
| GC selection | `-XX:+UseG1GC`, `-XX:+UseZGC`, `-XX:+UseParallelGC` | Do not change collector for an already-created image |
| GC tuning | G1 pause target, GC worker count, region-related flags | Keep unchanged and version together with the runtime |
| Object layout | CompressedOops, compressed class pointers, object alignment | Pin by effective value |
| Runtime memory | Metaspace, code cache, direct memory limits | Record and keep compatible |
| Thread/runtime | Stack size, compiler threads, runtime thread options | Do not change arbitrarily; test per build |
| Module/access | `--add-opens`, `--add-exports`, module path | Keep identical configuration to avoid class access differences |
| Agent/native | `-javaagent`, `-agentlib`, `-agentpath` | Pin agent binary, version, and configuration |
| Diagnostics | JFR, logging, GC log | Manage separately; evaluate impact and how to enable at restore |
| System properties | `-Dkey=value`, locale, timezone, encoding | Keep consistent with config already used by initialized objects |
| CRaC options | Checkpoint/restore path and JDK-specific options | Follow documentation of the exact JDK distribution |

Some flags can be changed dynamically via diagnostic commands or MXBeans in certain JVM builds; that does not mean every change is suitable during restore. With checkpoints, the most controllable approach is to use the same flag set and only change it after creating a new checkpoint.

## 6. Dynamically Changeable Flags and Startup Flags

The JVM has different types of options:

- **Startup-only flags:** read only when the JVM starts; cannot be changed by editing the command line after the process is already running.
- **Manageable flags:** certain values can be changed via JMX or diagnostic commands if supported by the JVM.
- **Ergonomic values:** automatically selected by the JVM based on JDK, hardware, container limits, and other flags.
- **Restore-specific options:** options controlling the restore mechanism as defined by the JDK distribution.

Do not infer mutability from the flag name alone. Check the flag metadata and documentation of the specific JDK. Even if a flag is manageable, verify whether changing it before checkpoint produces a state supported at restore.

### 6.1. Viewing Effective Flag Values

You can record flags when running the JVM with:

```bash
java -XX:+PrintFlagsFinal -version
```

The command prints the list of flags and final values after applying defaults and command-line options. The output can be very long; the pipeline should save the full output as a release artifact.

For a running process, use `jcmd` from the corresponding JDK:

```bash
jcmd <pid> VM.flags -all
jcmd <pid> VM.command_line
jcmd <pid> VM.version
```

These commands help inspect the actual flags, command line, and JVM version. Some commands or output fields depend on the JDK build; check `jcmd <pid> help` if a command is unsupported.

### 6.2. Comparing Configuration Before Restore

The release manifest should contain the digest of the flags file and a list of critical effective flags. Before restore, the deployment system can verify:

- JDK vendor/version/build matches.
- Heap sizing matches.
- GC collector and critical options match.
- Object layout flags match.
- Native agent and module options match.
- Container memory limit and architecture fall within the tested range.

Not every diagnostic flag needs to be treated as a blocker if documentation confirms it can be changed. However, every exception must be clearly defined in the compatibility policy rather than handled by guesswork during deployment.

## 7. Container Configuration and Memory Limits

The JVM can use container-aware ergonomics to determine heap size and visible CPU count. A container's memory limit or CPU quota can therefore affect effective flag values.

For example, the same command:

```bash
java -XX:+UseContainerSupport -jar app.jar
```

can result in different heap sizing if containers have different memory limits. If a checkpoint is created in a 4 GiB container but restored in a 1 GiB container, the JVM may lack sufficient resources to recover and operate the saved state.

Factors to record:

- Container memory limit and CPU limit.
- Cgroup version and how the JVM detects the container.
- Effective max heap and initial heap.
- Number of processors seen by the JVM.
- Native memory and direct memory limits.
- Thread count and stack size.
- Node capacity and memory pressure at restore time.

Do not inspect `-Xmx` alone. An application with a 1 GiB heap can still exceed the memory limit if native memory, thread stacks, direct buffers, code cache, and other processes consume the remainder.

### 7.1. Setting Memory Headroom

For example, a container with a 3 GiB limit should not default to `-Xmx3g`. Part of the memory must be reserved for:

- Metaspace and class metadata.
- Code cache.
- Thread stacks.
- Direct byte buffers.
- Native libraries and GC structures.
- JVM internal allocations.
- Agents, profilers, or telemetry.
- Headroom for workload fluctuations.

Measure the actual memory footprint after restore and under representative load. The goal is for the instance to restore, reach readiness, and handle load without being OOM-killed.

## 8. Code Cache and JIT-Related Flags

CRaC can preserve the state of JIT-compiled code in the process. Therefore, the code cache and compiler options are also part of the runtime state that must be managed.

Some related flags:

- `-XX:ReservedCodeCacheSize`.
- `-XX:InitialCodeCacheSize`.
- `-XX:+TieredCompilation`.
- Compiler thread or compilation threshold options per JDK.

If you change the code cache size or compiler configuration at restore, do not assume compiled code and compiler state will automatically adapt properly. Keep the configuration that created the checkpoint or create a new image after changing it.

Warm-up also affects how much code cache is used. If the workload warms up too many rare code paths, the checkpoint may contain more JIT code than necessary. Weigh latency benefits against image size and memory footprint rather than trying to warm up as many methods as possible.

## 9. Metaspace, Direct Memory, and Thread Stacks

The heap is not the only memory region affected by flags.

### 9.1. Metaspace

Metaspace stores class metadata. Flags such as `-XX:MetaspaceSize` and `-XX:MaxMetaspaceSize` can affect metadata management behavior. Applications using many classloaders, proxies, or dynamic class generation need to monitor metaspace and class unloading.

A checkpoint preserves the process's class metadata state. Do not arbitrarily change metaspace configuration or the classpath at restore.

### 9.2. Direct Memory

NIO direct buffers and some native libraries use off-heap memory. `-XX:MaxDirectMemorySize` can limit the amount of direct buffer memory the application uses. If the restore container has a lower memory limit, direct memory and native allocations can push the instance over its limit even when the heap still has free space.

### 9.3. Thread Stacks

`-Xss` affects the stack size of new Java threads. Threads already existing at checkpoint have their own stack state inside the process. Changing the stack size at restore does not alter the saved stacks of existing threads; it may only affect how new threads are created according to the runtime and must be tested with the specific JDK.

Keep thread configuration stable, drain tasks that do not need to survive across the checkpoint, and verify the thread count after restore.

## 10. Java Agents, Native Agents, and Instrumentation

Agents can modify bytecode, instrument classes, create threads, or allocate native memory. They can affect class loading and runtime state before checkpoint.

For example:

- APM agents.
- Profilers.
- Coverage agents.
- Bytecode instrumentation agents.
- Native agents using `-agentlib` or `-agentpath`.

If a checkpoint is created with one agent but restored using a different agent binary or configuration, the instrumentation and runtime state may not match. Pin the agent version, checksum, and flags. If an agent does not support CRaC or lacks restore guidance, verify compatibility before including it in the image.

Some agents may require dedicated callbacks or hooks to close sockets, flush telemetry, and restart exporters. Do not assume the JVM automatically handles every agent resource merely because the process is checkpointed.

## 11. System Properties and Launch Environment

System properties such as timezone, locale, encoding, profiles, or framework configuration may already have been read and copied into objects in the heap. If restored with different values, the application may end up in a hybrid state: initialized objects retain old values while lazy components read new values.

For example:

```bash
java \
  -Duser.timezone=UTC \
  -Dfile.encoding=UTF-8 \
  -Dspring.profiles.active=production \
  -Xms512m \
  -Xmx2g \
  -XX:+UseG1GC \
  -jar app.jar
```

The values above are illustrative only. If the timezone or Spring profile is changed after restore, beans already created before checkpoint may not automatically update. If dynamic configuration is needed, design an explicit refresh lifecycle instead of relying on changing environment variables.

Not every system property affects JVM layout, but they can affect application behavior. Therefore, record the launch configuration and keep it consistent per release.

## 12. Creating a Compatibility Manifest for Heap, GC, and JVM Flags

Each checkpoint release should store enough configuration information to accurately identify the runtime that created the image.

For example:

```yaml
runtime:
  vendor: "<jdk-vendor>"
  version: "<java-runtime-version>"
  build: "<jdk-build-number>"
  vmName: "<jvm-name>"
  architecture: amd64

heap:
  initial: 512m
  maximum: 2g
  compressedOops: true
  compressedClassPointers: true
  objectAlignment: "<effective-value>"

gc:
  collector: G1
  flagsFile: jvm-flags.txt
  flagsSha256: "<flags-file-sha256>"

memory:
  maxMetaspace: "<effective-value>"
  maxDirectMemory: "<effective-value>"
  reservedCodeCache: "<effective-value>"
  threadStackSize: "<effective-value>"

container:
  memoryLimit: 3Gi
  cpuLimit: "2"
  imageDigest: "sha256:<image-digest>"

checkpoint:
  createdWithRuntime: "<same-runtime-identifier>"
  path: /var/lib/app/checkpoint
```

The values in angle brackets are placeholders. The pipeline needs to obtain actual values from the JVM and environment that created the checkpoint. Do not guess effective values from configuration files.

### 12.1. Recording Effective Flags

You can save the output of:

```bash
java -XX:+PrintFlagsFinal -version > effective-flags.txt 2>&1
```

And for an already-running process:

```bash
jcmd <pid> VM.flags -all > process-flags.txt
jcmd <pid> VM.command_line > process-command-line.txt
jcmd <pid> VM.version > process-version.txt
```

Generate checksums for these files and store them with the manifest. Some flags may have different values between startup and checkpoint time if changed dynamically; if so, clearly record the timestamp and final value.

## 13. Safe Procedure for Changing Heap or GC

If you need to increase the heap, change the collector, or adjust flags, treat it as a new runtime configuration.

Recommended procedure:

1. Create a new release configuration with the chosen JDK build and JVM flags.
2. Start a new application instance from scratch using that configuration.
3. Inspect effective flags, heap, GC, and container memory.
4. Run a representative warm-up workload.
5. Measure latency, throughput, allocation, GC pauses, and memory footprint.
6. Verify that the application meets warm-up criteria and resources can drain.
7. Create a new checkpoint.
8. Test restoring using the exact new JDK, flags, and container image.
9. Measure restore-to-ready time and test under load.
10. Promote the new release only after testing succeeds.

Do not edit `-Xmx` in a deployment manifest and continue using an old checkpoint without testing. Changing startup flags does not alter the heap state already saved in the image.

### 13.1. Configuration Change Example

Suppose the old release uses:

```bash
-Xms512m -Xmx2g -XX:+UseG1GC
```

After load testing, the operations team wants to use:

```bash
-Xms1g -Xmx3g -XX:+UseZGC
```

This changes both heap sizing and the collector. The deployment approach should be to start a new application instance with the new configuration, warm up again, create a new checkpoint, and release a new bundle. Do not pair an old image with a new restore command just because the JAR has not changed.

## 14. Which Flag Changes May Be Acceptable?

There is no single universal rule across all JDK distributions. Some options are used to control restore, some only affect logging/diagnostics, some are startup-only, and some alter critical runtime state.

| Type of Change | How to Handle |
| --- | --- |
| Changing `-Xms` or `-Xmx` | Keep unchanged; if a change is needed, create a new checkpoint unless JDK documentation explicitly confirms a supported case |
| Changing GC collector | Do not reuse the old image; create a new checkpoint with the new collector |
| Changing object layout/compressed pointers | Keep effective values unchanged; create a new image when changed |
| Changing code cache/compiler flags | Keep unchanged unless specific guidance and testing exist |
| Changing module access or classpath | Treat as a runtime/application bundle change; create a new checkpoint |
| Changing agent/native library | Pin the exact binary and configuration; if changed, create and test a new image |
| Enabling/disabling logging or JFR | Check which flags are supported at restore and the impact of agents/runtime; do not infer |
| Changing application system properties | Evaluate initialized objects; perform controlled refresh or create a new image |
| Changing checkpoint/restore path | Follow the syntax and limits of the specific CRaC JDK |

If the JDK vendor publishes an option that is permitted to differ between checkpoint and restore, record that exception in the manifest and test using the exact build. Do not use documentation from a different JDK as evidence for the runtime being deployed.

## 15. Diagnosing Errors Related to Heap, GC, and Flags

When restore fails, classify the error by layer rather than changing multiple flags at once.

| Symptom | Possible Cause | What to Check |
| --- | --- | --- |
| JVM reports unrecognized or unsupported option | Restore JDK does not support the flag or the flag was renamed | Runtime vendor, version, build, and documentation |
| Restore fails when using different heap sizing | Heap configuration is incompatible with image state or environment lacks memory | Compare `-Xms`, `-Xmx`, container limits, and effective flags |
| GC- or memory-mapping-related error | Collector/build or memory state is incompatible | Collector, GC flags, JDK build, and kernel |
| Process restores but later hits OOM | Low memory limit, native memory, or workload exceeds projection | Heap, metaspace, direct memory, thread stacks, code cache, and cgroups |
| GC pauses spike after restore | Heap/GC sizing is unsuitable for the workload or new environment | GC logs/JFR, allocation rate, and collector configuration |
| Abnormal code cache or compilation behavior | Compiler flags, JDK build, or warm-up differs | Effective compiler flags, code cache usage, and JFR |
| Native agent fails after restore | Agent does not support checkpoint/restore or binary differs | Agent version, checksum, native dependencies, and lifecycle hooks |
| Application behavior differs even though process restore succeeded | System properties or initialized object configs do not match | Launch config, Spring profile, timezone, and config refresh |

Retain logs from the JVM, CRIU, and the application. Do not ignore resource errors or continue serving just because the process appeared after restore.

## 16. Configuration Matrix Compatibility Testing

When supporting multiple deployment profiles, create a matrix for permitted configurations. Each profile must be checkpointed and restored with its exact runtime tuple.

| Component | Value to Pin | Check |
| --- | --- | --- |
| JDK | Vendor, version, build | Restore using the exact build |
| Heap | `-Xms`, `-Xmx`, heap limits | Compare effective flags and memory footprint |
| GC | Collector and GC tuning flags | Checkpoint/restore and run representative workload |
| Object layout | Compressed pointers, alignment | Compare effective flags |
| Native memory | Metaspace, direct memory, code cache | Measure memory after restore and under load |
| Threads | Stack size, worker count, compiler threads | Check thread state and resource usage |
| Agents | Binary version and arguments | Restore and check agent lifecycle |
| Container | Image digest, memory/CPU limits | Restore within the exact container constraints |
| OS | Kernel, architecture, CRIU | `criu check` and real smoke test |

### 16.1. Minimal Smoke Test

For each profile:

1. Start with the pinned JDK and flags.
2. Save effective flags and runtime version.
3. Run the warm-up workload.
4. Create the checkpoint.
5. Restore with the exact JDK build and container configuration.
6. Verify resource callbacks and health/readiness.
7. Run a representative workload after restore.
8. Measure heap, GC, CPU, native memory, and latency.

### 16.2. Negative Testing

Controlled testing with a mismatched JDK or flags can help confirm that release validation rejects invalid combinations before invoking restore. There is no need to intentionally run an unsupported combination in production.

## 17. Release Management Rules

Each checkpoint release should be immutable. Do not overwrite an old image when changing heap or GC configuration. Associate the checkpoint with:

- JDK vendor/version/build.
- Application version and checksum.
- Dependency/classpath digest.
- Effective JVM flags.
- Heap and GC configuration.
- Container image digest.
- OS/kernel/architecture and CRIU version.
- Resource configuration required for restore.

When releasing a new configuration, keep the previous bundle for rollback. Rollback must restore the exact runtime and checkpoint pair, rather than only changing JVM flags or the container tag.

## 18. Conclusion

Heap, GC, and many JVM flags directly affect the runtime state saved in a checkpoint. `-Xms`, `-Xmx`, collector, object layout, code cache, metaspace, direct memory, thread stacks, and agent configuration must be managed alongside the JDK build that created the image.

Record effective flags, pin the JDK vendor/version/build, and keep the configuration unchanged at restore. If you need to change heap, collector, or flags affecting runtime structures, start a new application instance, warm up again, and create a new checkpoint. Apply exceptions only when documentation for the exact JDK distribution explicitly confirms compatibility and the combination has been tested. Managing via release bundles avoids pairing saved JVM state with a mismatched configuration and keeps the restore process reproducible.
