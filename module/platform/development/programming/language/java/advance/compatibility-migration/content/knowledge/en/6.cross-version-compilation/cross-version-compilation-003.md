# `-source` and `-target`: control scope and risks of using new APIs

When a Java project must continue running on an older JDK while the development team wants to use a newer JDK for compilation, the two options `-source` and `-target` are often used to set compatibility levels. However, they control only two aspects of compilation: the accepted Java language rules and the generated bytecode format.

**`-source` and `-target` do not restrict the set of JDK APIs visible to the compiler.** Consequently, code can compile successfully and emit class files bearing an older version, yet still call a method that appeared only in a newer JDK. When running on the older target JDK, the application can fail with `NoSuchMethodError` or `NoClassDefFoundError`.

This is a significant risk in Java Compatibility Migration: a class file that looks compatible does not mean the application actually works on the older runtime. With JDK 9 or newer, prefer `--release` to combine language level, bytecode level, and platform APIs of the target release.

## 1. Three concepts that must be separated

To understand `-source` and `-target` properly, distinguish three layers:

| Layer | Question | Control mechanism |
|---|---|---|
| Source language | Which version's syntax and Java rules does the compiler accept? | `-source` or `--source` |
| Bytecode format | Which JVM version can read the generated class files? | `-target` or `--target` |
| Platform APIs | Which JDK classes, methods, and fields is code allowed to reference? | `--release`; or equivalent platform API config such as boot class path in legacy environments |

These three concepts are related yet cannot substitute for one another.

### 1.1. `-source`: restricting the Java language

`-source` specifies the language version the compiler uses to parse source code. It determines which syntax, language rules, and certain compile-time checks are accepted.

For example, `var` for local variables exists only since Java 10:

```java
public class SourceLevelExample {
    public static void main(String[] args) {
        var message = "Hello";
        System.out.println(message);
    }
}
```

If compiled with source level 8, the compiler rejects the `var` syntax. When using source level 10 or higher, this syntax is accepted if the compiler supports the corresponding release.

`-source` does not mean the compiler is running on that version's JDK. For example, a `javac` command from JDK 17 can still be asked to parse source according to Java 8 rules. The compiler is still JDK 17's compiler; only the selected language level is Java 8.

### 1.2. `-target`: choosing the class file version

`-target` specifies the class file format version generated by the compiler. The JVM checks the class file version when loading a class. If the class file is newer than the JVM supports, the JVM can throw `UnsupportedClassVersionError`.

Some common class file major versions:

| Java release | Class file major version |
|---:|---:|
| Java 8 | 52 |
| Java 9 | 53 |
| Java 10 | 54 |
| Java 11 | 55 |
| Java 17 | 61 |

For example, `-target 8` instructs the compiler to emit major version 52 class files. That enables a Java 8 JVM to read the class file format, yet does not prove every API the class calls exists in Java 8.

### 1.3. Platform APIs are a separate layer

The compiler must look up classes and methods to type-check during compilation. If the compiler runs on JDK 17, the platform classes it sees by default belong to JDK 17. Setting `-source 8 -target 8` does not automatically replace that platform class set with Java 8's APIs.

Therefore, the compiler can accept a method call added in Java 9, even though the emitted class file has major version 52. This is the source of the “compiles fine yet fails to run on target Java” error.

## 2. Example: Java 8 bytecode calling a Java 9 API

Suppose a project wants to build an artifact running on Java 8, yet the build server upgraded to JDK 17. Source contains a call to `List.of`, an API added in Java 9:

```java
import java.util.List;

public class ApiLeak {
    public static void main(String[] args) {
        System.out.println(List.of("Java", "Compatibility"));
    }
}
```

If compiled with JDK 17 as follows:

```bash
javac -source 8 -target 8 ApiLeak.java
```

the compiler can succeed and emit a warning that bootstrap class path is not set together with `-source 8`. The compiler sees JDK 17's `java.util.List` and therefore finds `List.of`.

You can check the class file version:

```bash
javap -verbose ApiLeak | findstr "major version"
```

On Windows, output shows major version 52. On Linux/macOS, `grep` can be used instead of `findstr`:

```bash
javap -verbose ApiLeak | grep "major version"
```

The class file carries the Java 8 version yet holds a symbolic reference to `java.util.List.of`. When run on Java 8, the `List` class lacks that method; method linkage fails with `NoSuchMethodError`.

<text color="secondary" size="sm">Error flow</text>

```text
JDK 17 javac
   |
   | -source 8 -target 8
   v
Source uses List.of() from Java 9
   |
   v
Class file major version 52
   |
   | Java 8 JVM can read the class file
   v
Link java.util.List.of()
   |
   v
NoSuchMethodError: Java 8 lacks List.of()
```

The key point is that `UnsupportedClassVersionError` and `NoSuchMethodError` manifest two different issues:

- `UnsupportedClassVersionError`: the JVM cannot read the class file format.
- `NoSuchMethodError`: the JVM can read the class file, yet the referenced method does not exist in the class loaded at runtime.

A similar error can happen with a new class, new field, or new constructor in the platform API, producing `NoClassDefFoundError`, `NoSuchFieldError`, or other linkage errors.

## 3. Why `-source` and `-target` are not enough

### 3.1. The compiler uses the running JDK's platform APIs

These two options do not swap out the boot/platform classes used by the compiler. When running `javac` from JDK 17, the compiler sees JDK 17 APIs by default. If only old source and target levels are set, code can still call new APIs.

Setting a low `-target` changes only the class file format. The JVM does not read class file metadata to deduce that the author intended Java 8 and reject every post-Java-8 API. The JVM simply resolves classes, fields, and methods on demand.

### 3.2. Third-party dependencies can also cause errors

Even if source uses only Java 8 APIs, a dependency library may be compiled with a newer JDK and reference APIs present only in Java 11 or 17. The consumer may compile because the compiler reads the library's public signature, yet the library fails when running on Java 8.

Additionally, if a dependency is compiled with class file major version 61, a Java 8 JVM cannot load it. Setting `-target 8` on the application's source does not automatically downgrade dependency bytecode.

Therefore, compatibility targets must apply across the entire dependency graph, including internal libraries and independently released artifacts.

### 3.3. Behavioral compatibility is not guaranteed

An API may exist in both versions while behavior differs. A newer JDK may alter algorithms, default values, providers, TLS handling, charsets, locales, or when exceptions are thrown.

`-source`, `-target`, and `--release` none of them prove application behavior is identical. Run tests on the target runtime and verify real business flows.

### 3.4. Proper dependency resolution is not guaranteed

A build may resolve dependencies differently by JDK, Gradle/Maven profile, repository, or variant metadata. If a pipeline logs only declared versions without logging actually resolved versions, migration results are hard to reproduce.

Save compile/runtime/test dependency graphs and verify the version of each key artifact.

## 4. `--release`: controlling source, target, and APIs together

Since JDK 9, `javac` provides `--release`. This option is designed to compile source for a specific Java release while also restricting platform APIs to that release.

For example, using JDK 17 to compile for Java 8:

```bash
javac --release 8 ApiLeak.java
```

With source calling `List.of`, the compiler reports an error because this API does not exist in Java 8. If code is changed to an API available since Java 8, for example:

```java
import java.util.Arrays;
import java.util.List;

public class ApiCompatible {
    public static void main(String[] args) {
        List<String> values = Arrays.asList("Java", "Compatibility");
        System.out.println(values);
    }
}
```

then `javac --release 8 ApiCompatible.java` can compile with JDK 17 and emit class files for Java 8.

### 4.1. What does `--release` do?

In purpose, `--release N` combines three constraints:

1. Accept syntax and language rules of Java release N.
2. Emit bytecode matching release N.
3. Permit access only to public platform APIs belonging to release N.

The JDK stores historical API information in platform data used by the compiler, often referenced via `ct.sym`. Because of this, a newer JDK compiler can check source against an older release's APIs without needing a full older JDK for every release.

### 4.2. What are the limits of `--release`?

`--release` controls Java SE platform APIs and JDK APIs included in the corresponding release's API set. It does not automatically check all third-party dependencies. If a Maven/Gradle library calls a new API inside its implementation, the application's compiler cannot necessarily detect that from public signatures alone.

Nor does it replace testing on the target runtime, prove behavioral compatibility, or automatically govern native libraries.

Do not use `--release` simultaneously with `-source`, `-target`, or incompatible options that modify the platform system image. Once `--release` is chosen, let it be the sole release configuration source for the compile task.

### 4.3. JDK 8 and limits of `--release`

`--release` exists only from JDK 9 onward. If building with JDK 8, the compiler does not accept this option. In that case, the simplest and most reliable way to build for Java 8 is using the JDK 8 compiler and corresponding platform classes.

In legacy cross-compile environments, `-bootclasspath` can be used to point to the target's platform classes. Ensure the boot class path truly belongs to the right target JDK/APIs; setting only `-source` and `-target` still does not restrict APIs.

## 5. Maven configuration

### 5.1. Legacy approach: source and target

A Maven project may declare:

```xml
<properties>
    <maven.compiler.source>8</maven.compiler.source>
    <maven.compiler.target>8</maven.compiler.target>
</properties>
```

This configuration sets language and bytecode targets. If Maven runs on JDK 17, it does not automatically restrict JDK APIs to Java 8.

### 5.2. Recommended approach: release

With a Maven Compiler Plugin supporting the `release` property (plugin line 3.6 and newer), you can declare:

```xml
<properties>
    <maven.compiler.release>8</maven.compiler.release>
</properties>
```

Or configure the plugin explicitly:

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.13.0</version>
            <configuration>
                <release>8</release>
            </configuration>
        </plugin>
    </plugins>
</build>
```

Choose a plugin version matching the Maven/JDK in use and inspect the effective POM configuration. Parent POMs, profiles, or plugin management can override values in child modules.

If you need to build/test with JDK 17 while still supporting a Java 11 runtime, you can set `<maven.compiler.release>11</maven.compiler.release>` while Maven runs on JDK 17, provided plugins and dependencies support that environment.

## 6. Gradle configuration

### 6.1. Distinguishing sourceCompatibility/targetCompatibility from options.release

The Gradle Java plugin has properties:

- `sourceCompatibility`: Java language level for source.
- `targetCompatibility`: bytecode target version.
- `options.release`: instructs the compiler to conform to a specific Java release, including platform APIs.

Example setting source/target:

```groovy
java {
    sourceCompatibility = JavaVersion.VERSION_1_8
    targetCompatibility = JavaVersion.VERSION_1_8
}
```

The configuration above is equivalent to setting source/target levels in the compiler. It does not replace the API restriction of `--release`.

### 6.2. Using a new toolchain with an old release

With Gradle, you can run the compiler on JDK 17 while compiling source for Java 8:

```groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 8
}
```

In this example, the toolchain picks JDK 17 to run the compiler; `options.release` restricts source language, bytecode, and platform APIs to Java 8. If the project wants to run on Java 11, change `options.release` to `11`.

Do not inspect only `targetCompatibility` to conclude APIs were restricted. At the same time, Gradle variant metadata may use target compatibility to select matching artifacts across projects; this is a different function from restricting the compiler's platform APIs.

### 6.3. Multiple modules with different releases

A multi-module build might have a library module supporting Java 8 and an application running only Java 17. In that case, set release explicitly on each module and verify dependency direction.

Example:

```groovy
project(":shared-library") {
    tasks.withType(JavaCompile).configureEach {
        options.release = 8
    }
}

project(":modern-service") {
    tasks.withType(JavaCompile).configureEach {
        options.release = 17
    }
}
```

A Java 17 module can use a Java 8 library. The reverse does not hold if the Java 8 library depends on APIs or bytecode of a Java 17 module. Let the dependency graph reflect this relationship clearly.

If the project contains Kotlin or Scala, `JavaCompile.options.release` applies only to JavaCompile tasks. Configure appropriate JVM target/API settings separately for those compiler plugins and verify the final artifact.

## 7. How to choose compiler JDK and runtime JDK?

The following concepts should be recorded separately in configurations and migration reports:

| Concept | Meaning |
|---|---|
| Build JDK | JDK running Gradle/Maven and build plugins |
| Compiler toolchain | JDK performing compilation of Java sources |
| Release/source target | Language, bytecode, and API level targeted by a module |
| Runtime JDK | Actual JDK/JRE image running the application |
| Dependency bytecode target | Class file version of each library in the graph |

For example, a team can run Gradle on JDK 17, use toolchain JDK 17, compile libraries with `--release 11`, and then run the application on JDK 11. This is a valid configuration if all dependencies and runtime plugins are compatible with Java 11.

However, if a dependency was compiled for Java 17, a Java 11 runtime still cannot load that dependency. The application compiling itself to bytecode 11 does not downgrade the library's bytecode.

When migrating the entire runtime from 11 to 17, also check:

- Which release each module is compiled with.
- Which class file major version dependencies have.
- Whether new JDK APIs are used in modules declared to support an older runtime.
- Whether native libraries have artifacts for the target OS/architecture.
- Whether build/test plugins are compatible with the JDK running the build.

## 8. How to verify the artifact is genuinely compatible

Do not conclude solely from `release`, `sourceCompatibility`, or `targetCompatibility` config lines. Inspect the generated artifact and run it with the target runtime.

### 8.1. Inspect class file version

Use `javap`:

```bash
javap -verbose -classpath build/classes/java/main \
  com.example.Application | grep "major version"
```

Major version helps catch class files newer than the target runtime. For dependency JARs, you can extract or use bytecode analysis tools to inspect key classes.

### 8.2. Inspect target JDK APIs

With a JDK 9 or newer compiler, building with `--release` or `options.release` is the primary check layer for platform APIs. When additional checks on compiled dependencies are needed, use `jdeps`, `jdeprscan`, and tests on the target runtime.

Example:

```bash
jdeps --jdk-internals --recursive --class-path "lib/*" app.jar
jdeprscan --release 11 --class-path "lib/*" app.jar
```

Select the release corresponding to the runtime the artifact must support. Static analysis tools have limitations with reflection, service loading, and native code.

### 8.3. Run tests with the exact runtime

If the artifact must support Java 11, run integration tests on JDK 11 or a real Java 11 runtime image. If the artifact only needs Java 17, run tests on JDK 17 and its corresponding deployment environment.

Check:

- Startup and shutdown.
- Reflection, proxies, bytecode generation, and instrumentation.
- Serialization/deserialization and data persisted by older versions.
- TLS, certificates, HTTP clients, and database/message broker connections.
- Charsets, locales, timezones, and file paths.
- JNI/JNA, native libraries, and operating system dependencies.
- Error-handling flows, timeouts, retries, and scheduled batches.

## 9. Common misconceptions

### “Setting target 11 guarantees running on Java 11”

Incorrect. `target` selects only the class file format. Source can still call Java 17 APIs if the compiler runs on JDK 17 without restricting platform APIs.

### “Source 11 means using the Java 11 compiler”

Incorrect. That is the source language level. The actual compiler is determined by the JDK running `javac` or the toolchain chosen by the build tool.

### “Compilation succeeding means every dependency is compatible”

Incorrect. The compiler can check public signatures yet cannot prove library implementations call only APIs present in the target runtime. Inspect dependency graphs, bytecode, and run on the target runtime.

### “`--release` solves all compatibility”

Incorrect. `--release` controls platform APIs when compiling source. It does not govern third-party APIs, native code, runtime behavior, production configuration, or communication schemas.

### “We can build with JDK 17 and run on Java 11 without testing Java 11”

Do not draw that conclusion. If Java 11 remains a supported runtime, have a test job running on JDK/runtime 11 or an equivalent image to confirm dependencies and behavior.

## 10. Checklist for choosing source/target/release levels

- [ ] Identified the lowest runtime needing support.
- [ ] Identified the actual JDK running the build and compiler toolchain.
- [ ] On JDK 9+, used `--release` or `options.release` instead of only setting source/target when API restriction is required.
- [ ] If using the JDK 8 compiler, compiled against matching Java 8 platform APIs.
- [ ] Checked class file versions of modules and key dependencies.
- [ ] Checked that direct and transitive dependencies are compatible with the target runtime.
- [ ] Separately configured Kotlin/Scala compilers if modules contain those languages.
- [ ] Ran tests on the lowest supported runtime.
- [ ] Explicitly recorded release targets and rationale per module.

## 11. Conclusion

`-source` controls the language accepted by the compiler; `-target` controls the generated bytecode format. Neither automatically restricts the JDK APIs source can call. Therefore, compiling with a newer JDK using older source/target can emit older class files containing references to newer APIs, leading to linkage errors on older runtimes.

With JDK 9 or newer, prefer `--release` or equivalent configurations such as Gradle `options.release` and Maven Compiler Plugin `release`. Simultaneously inspect third-party dependencies, bytecode across the entire graph, and run tests on the target runtime. By explicitly separating build JDK, compiler toolchain, release target, and runtime JDK, the development team avoids many migration failures that otherwise surface only after deployment.
