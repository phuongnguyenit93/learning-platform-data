# Checking generated code and annotation processors by Java version

In a Java project, part of the code included in the application is not necessarily written directly by developers. Code may be generated from annotations, schemas, API description files, protobuf, WSDL, or build tools. Some tools generate source files before compilation; some annotation processors run inside the compiler and generate additional Java source during annotation processing rounds. When upgrading the JDK or changing the target Java version, both the generated code and the code generation tools need to be verified.

A project may compile successfully on an older JDK yet fail on a newer JDK because an annotation processor does not yet support the new compiler, depends on internal `javac` APIs, is no longer automatically discovered, or generates source/APIs incompatible with the target release. Conversely, the processor may run successfully, yet the generated code is incompatible with the lowest runtime that the application must support.

The goal of the verification step is to determine what code is generated, which tool creates it, which compiler/JDK runs the tool, which source/API baseline applies to the output, and which versions need to be tested.

## 1. Distinguishing types of generated code in Java projects

Not every automatically generated file comes from annotation processing. Proper classification is needed because execution timing, configuration, and compatibility mechanisms differ.

### 1.1. Code generated before the compilation step

Some tools read a schema or service description and generate `.java` source before `javac` runs. Examples:

- OpenAPI Generator creates models, API interfaces, and client/server stubs from an OpenAPI document.
- Protocol Buffers compiler (`protoc`) together with the Java plugin generates classes from `.proto` files.
- SOAP client generators create Java stubs from WSDL/XSD.
- Code generators that produce code from database schemas, DSLs, or configuration files.
- Build plugins that generate sources, resources, or metadata from templates.

These tools usually run as separate Gradle/Maven tasks. You need to verify the generator version, plugin, input schema, accompanying runtime library, and the JDK used to run the tool itself. Once generated, the source still has to compile under the application's source/API baseline.

### 1.2. Code generated by annotation processors

Annotation processing is a standard mechanism of the Java compiler, specified by JSR 269. Processors read annotations and type information during compilation, and can then generate source files, class files, or resources through `Filer`.

Some common examples:

- MapStruct generates implementations for mapper interfaces.
- Dagger generates code for dependency injection.
- AutoValue and Immutables generate implementations for immutable data types.
- QueryDSL can generate metamodels or query types from entities.
- Hibernate/JPA metamodel processor generates static metamodels.
- Some processors generate metadata, registries, or adapters based on custom annotations.

Lombok also participates in compilation to add members to the compiler's syntax model. How Lombok works has details that depend on `javac` implementation internals, so you must specifically verify the JDK support matrix for the exact Lombok version.

### 1.3. Distinguishing processors from runtime annotations

An annotation may serve only runtime reflection without generating code. For example, a framework reads annotations to configure beans or routes at application startup. In that case, you need to check the runtime library and how the framework handles annotations on the new JDK, even though there is not necessarily an annotation processor.

Conversely, a library may provide both compile-time annotations and a runtime API. For example, the processor generates an implementation while the application needs a runtime dependency to invoke that implementation. Clearly separate the components:

- Annotations/APIs referenced by source code.
- The processor running inside the compiler.
- The runtime library used by the application at runtime.
- Generated sources/classes/resources packaged into the final artifact.

Do not put the processor on the runtime classpath simply because the application uses its annotations. Use the proper compile-time and runtime configurations according to the library's instructions.

## 2. Understanding the annotation processing lifecycle

`javac` executes annotation processing in rounds. A processor is invoked with the relevant set of annotations and elements in the current round. Processors can generate new sources; those sources are fed into subsequent rounds for the compiler and processors to handle. The process finishes when there are no more new sources to process or no further rounds remain.

A processor typically implements `javax.annotation.processing.Processor`, or extends `AbstractProcessor`. It declares supported annotations, source version, and configuration options. Example of a simple structure:

~~~java
@SupportedAnnotationTypes("com.example.GenerateMapper")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class MapperProcessor extends AbstractProcessor {
    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {
        // Read annotated elements and generate source via Filer.
        return false;
    }
}
~~~

This is an example illustrating processor structure; source generation and error handling are omitted. In a real implementation, a processor must handle multiple annotations, multiple rounds, generic types, nested types, duplicate name errors, and cases where compilation has no matching elements.

### 2.1. How are processors discovered?

A processor can be specified directly with `-processor`, discovered via service provider metadata, or placed on the processor module path. The traditional service discovery mechanism uses the file:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

This file lists the fully qualified names of the processor implementations. For a modular JAR, a processor can also declare the service provider in `module-info.java` and be discovered via the corresponding module path.

Having a processor on the compile classpath does not mean it is always executed in every compiler version. Clearly determine where the processor is declared, how the compiler is instructed to run it, and which options the build tool actually passes to `javac`.

### 2.2. Processing rounds and file generation

Processors typically use `Filer` to generate sources or resources. File names must be deterministic and must not be created twice within the same compilation. If a processor attempts to rewrite an already generated file, the compiler may report `FilerException`.

Important principles:

- Only create files when there are valid elements and data to generate.
- Generate deterministic package/class names, avoiding dependence on element traversal order.
- Do not write files into the user-managed source tree if the build tool already provides a generated-source directory.
- Include appropriate comments or metadata so readers recognize the file as generated output.
- Handle multiple rounds and the `processingOver()` state properly.
- Report errors via `Messager` with the element location so developers know which annotation is invalid.
- Avoid generating the same type across multiple processors or multiple modules.

A common bug is a processor working properly only on a clean build while failing on an incremental build, or vice versa. Both modes must be tested because the build tool may re-run the processor only when inputs it tracks change.

## 3. Distinguishing the JDK running the processor from the Java release of the compiled code

This is the most critical point when checking generated code by Java version. There are at least three versions to distinguish:

1. **JDK running build/compiler:** the JVM executing Gradle/Maven and the `javac` process.
2. **Target source/API release:** the language version and Java SE APIs that application code is permitted to use.
3. **Minimum runtime:** the lowest Java version on which the final artifact needs to run.

For example, the build may run on JDK 21, compile the application with `--release 17`, and deploy the artifact on JRE/JDK 17. The annotation processor runs inside the compiler process on JDK 21. However, the source generated by the processor still has to be compiled targeting release 17.

`--release 17` constrains the source language, bytecode, and Java platform APIs that the compilation target is allowed to reference. It does not turn the JVM running the processor into JDK 17, nor does it prevent the processor itself from calling JDK 21 APIs during execution. Therefore, a processor might work on JDK 21 yet fail to run on JDK 17 if you downgrade the build toolchain to JDK 17.

Conversely, a processor running on JDK 21 might generate code calling an API introduced only in JDK 21. If the output is compiled with `--release 17`, the compiler typically detects that API reference and reports an error. However, if the processor creates resources or code compiled in a separate task that does not share the same release constraint, additional checks are needed to prevent newer APIs from leaking into the artifact.

Record an explicit matrix instead of using a generic phrase like “Java version”:

| Component | Example | Question |
|---|---|---|
| JDK running Gradle/Maven | JDK 21 | Do the build tool and plugins run on this JDK? |
| JDK running `javac` | Toolchain JDK 21 | Do the compiler and processors support this JDK? |
| Source/API release | `--release 17` | Which sources and APIs are permitted? |
| Bytecode target | Java 17 class file | Which runtimes can read the bytecode? |
| Minimum runtime | JDK 17 | Do the application and generated code run on this runtime? |
| Processor version | Specific MapStruct/Lombok/... version | Does the processor support this compiler and source model? |

If the build tool runs on one JDK while using a different toolchain to compile, verify the exact process running the processor. Usually the processor is loaded and executed inside the compiler process, so the compile task's toolchain is the decisive factor.

## 4. Checking annotation processor compatibility with a new JDK

A processor is a dependency executing in the build environment. It may depend on the Java compiler API, JDK APIs, bytecode libraries, reflection, or internal implementations of `javac`.

### 4.1. Checking the vendor's support matrix

For each processor, check the official support documentation and release notes for the exact version. Verify:

- Minimum JDK required to run the processor.
- JDKs officially tested or supported by the vendor.
- Maximum source version that the processor understands properly.
- Supported Gradle/Maven and compiler plugin versions.
- Required accompanying framework, annotation API, and runtime library versions.
- Fixes related to newer JDKs, the module system, or incremental compilation.
- Known limitations and workarounds published by the vendor.

Do not infer support solely from a higher version number or the fact that the dependency can be downloaded. If the documentation does not clearly state the target JDK, mark it as “unverified” and check with a trial build alongside a representative test suite.

### 4.2. Checking usage of internal compiler APIs

The public Java annotation processing APIs include packages such as `javax.annotation.processing`, `javax.lang.model.*`, and specified compiler APIs. Some processors, especially tools that deeply manipulate the AST or compiler internals, may use implementation classes in `com.sun.tools.javac.*`.

Internal packages are not a stable Java SE contract. Newer JDKs may change class structures, methods, or module access permissions. Older processors may encounter errors such as:

- `IllegalAccessError` or `InaccessibleObjectException` when accessing encapsulated members.
- `NoSuchFieldError` or `NoSuchMethodError` when compiler internals change.
- `ClassCastException` or tree/element processing errors because assumptions about AST structure no longer hold.
- Processor initialization failures or reflection errors occurring before compilation completes.

When encountering an error, capture the full stack trace to determine whether the fault lies in the processor, compiler plugin, or source code. Look for an official processor update before adding `--add-exports` or `--add-opens`. If an internal package must be opened temporarily, restrict it to the exact package/module, document the reason, and set a removal deadline. Do not use a set of JVM options exposing all compiler internals as a default solution.

### 4.3. Checking SourceVersion and new syntax

A processor may declare the source version it supports via `@SupportedSourceVersion` or `getSupportedSourceVersion()`. Check whether that declaration matches the source release being compiled.

A processor returning `SourceVersion.latestSupported()` does not automatically prove it understands all new syntax properly. If the processor parses source itself, uses the `Tree API`, or processes annotations on records, sealed types, patterns, or new constructs, confirm that its implementation has been updated to understand those constructs.

For processors that only read `Element` and `TypeMirror` through standard APIs, the risk may be lower, yet you must still verify how they handle new element and type kinds. Pay special attention to:

- Record components, record constructors, and accessors.
- Sealed classes/interfaces and permitted subclasses.
- Generic types, intersection types, and type-use annotations.
- Module elements, package elements, and service providers.
- Repeatable annotations, parameter/type-use annotations, and inherited annotations.
- New types or representation changes in `javax.lang.model` and `com.sun.source`.

Not every new JDK introduces changes across all of the categories above. Cross-check against the exact language/source release and compiler APIs of the target version.

### 4.4. Checking processor discovery and configuration

JDK 23 changes the default policy of `javac`: annotation processing no longer runs automatically simply because a processor happens to be found on the compile classpath. Running processors must be requested explicitly, for example via `-processor`, `--processor-path`, `--processor-module-path`, or the appropriate `-proc:only`/`-proc:full` modes.

This change can cause an older build to suddenly stop producing generated sources after moving to JDK 23+, even though the processor JAR is still present in dependencies. Therefore, check whether the build tool explicitly configures the processor path or processor selection.

In `javac`, common options include:

~~~bash
javac \
  --release 17 \
  --processor-path path/to/processor.jar \
  -processor com.example.MapperProcessor \
  -s build/generated/sources/annotations \
  -d build/classes \
  @sources.txt
~~~

- `--processor-path` specifies where to locate processors.
- `-processor` specifies the processor class to run.
- `-s` specifies the output directory for generated sources.
- `-d` specifies the output directory for class files.
- `--release` selects the source/API/bytecode baseline for the compiled code.

Specific options may vary by compiler version; check `javac --help` of the active JDK before adding them to the build. `-proc:none` disables annotation processing; `-proc:only` runs only processing without compiling sources like a normal compilation; `-proc:full` enables both processing and compilation. Do not add `-proc:full` mechanically if the build tool already configures an appropriate processor path and processing policy.

With Gradle, processors should be declared in dedicated configurations rather than mixed into `implementation`:

~~~groovy
dependencies {
    compileOnly 'org.projectlombok:lombok:<version>'
    annotationProcessor 'org.projectlombok:lombok:<version>'

    testCompileOnly 'org.projectlombok:lombok:<version>'
    testAnnotationProcessor 'org.projectlombok:lombok:<version>'
}
~~~

The example above illustrates Lombok configuration; substitute the supported version in your project. Other processors may require a separate runtime dependency and different configuration. With Maven, use `annotationProcessorPaths` or `annotationProcessors` of the compiler plugin where appropriate, and check how the plugin passes options to the target JDK.

## 5. Checking generated code

A processor running successfully is not sufficient to conclude that the output is compatible. You must verify the generated sources/classes/resources and the final artifact.

### 5.1. Generated source level and APIs

Generated source must conform to the target source release. If the application needs to run on Java 17, the processor must not generate syntax available only in Java 21 or reference APIs introduced only in Java 21.

Check:

- Source syntax produced by the generator.
- Referenced Java SE APIs.
- Annotations and runtime dependencies used by generated code.
- Generic signatures, checked exceptions, visibility, and packages.
- Reflection metadata, service registrations, and module descriptors if present.
- New warnings or errors from the target compiler.

Compiling generated source with `--release` is an important way to detect syntax/APIs exceeding the baseline. However, not every generator produces source in the same compilation. If codegen runs as a separate task, ensure the output's compile task also uses the right toolchain and release.

### 5.2. Checking runtime dependencies

Generated classes may reference the processor's runtime library. For example, a generated mapper may call a runtime helper; Protobuf-generated classes depend on the protobuf runtime; clients generated from OpenAPI may require an HTTP client and JSON library.

Identify:

- Which dependencies are needed only at compile time to run the processor.
- Which dependencies must be present on the runtime classpath.
- Which runtime library version is compatible with the generated code.
- Whether there are version conflicts with other dependencies in the application.
- Whether generated code uses APIs existing only in a newer runtime version.

Do not assume the processor and runtime library must always share the same version number, but follow the compatibility matrix published by the vendor.

### 5.3. Checking stability and reproducibility

Generated output should remain stable when inputs and tool versions do not change. If results depend on file traversal order, timestamps, locale, timezone, or nondeterministic collection ordering, builds can produce unnecessary diffs and make real changes harder to verify.

Check:

- Whether two clean builds with identical inputs produce equivalent outputs.
- Whether output contains timestamps or absolute paths from the build machine.
- Whether generated files are written into the proper build output directory.
- Whether a clean build removes old outputs before regenerating them.
- Whether incremental builds update/delete corresponding files when annotations or schemas change.
- Whether stale generated files remain even after the original source has been deleted.

Normally, generated files should not be edited manually. Modify the annotations, schema, template, or generator configuration and rerun the task. If the project intentionally commits generated code to the repository, clearly document the source, tool version, and regeneration procedure to avoid modifying output without updating inputs.

### 5.4. Incremental annotation processing

Build tools can classify processors by how inputs affect outputs. In Gradle, a processor can declare an incremental type such as `isolating`, `aggregating`, or `dynamic` via the corresponding metadata.

- **Isolating:** the output of one input element does not depend on other unrelated elements. When an input changes, the build tool can process only the corresponding slice.
- **Aggregating:** aggregated output depends on multiple inputs, such as a registry or a list of implementations. Changing one input may require updating the combined output.
- **Dynamic:** the processor declares incremental behavior through a dynamic mechanism supported by the build tool.

Only declare an incremental kind when the processor genuinely adheres to that contract. Incorrect declarations can cause incremental builds to miss required outputs or fail to delete stale outputs. When upgrading the JDK, compiler plugin, or processor, run both clean and incremental builds to compare results.

## 6. Checking code generation tools outside annotation processing

For OpenAPI Generator, Protobuf, WSDL generators, or similar tools, evaluate both the generator and its output:

1. Does the generator version run on the JDK used for the build?
2. Does the Gradle/Maven plugin support the current build tool and JDK versions?
3. Does the schema/input change between builds?
4. Does the generator use custom templates or custom plugins?
5. Which source level and Java APIs does the generated source use?
6. Which version of the runtime library does the generated code require?
7. Is the output stable and reproducible?
8. Are there stale generated files no longer referenced yet still remaining in the source set?

For example, upgrading OpenAPI Generator can change packages, method names, date/time types, client implementations, or JSON annotations. Even if the OpenAPI document stays unchanged, the new output may still differ. Inspect diffs of the generated source and test consumers before accepting the change.

For Protobuf, verify `protoc`, the Java plugin, generated code, and the protobuf runtime. The schema may stay the same while a newer generator version emits code depending on different runtime APIs. For SOAP, WSDL/XSD and generated stubs need to be tested with the exact JAX-WS/JAXB implementation version the application actually uses; do not assume all modules remain bundled in the JDK as in older Java versions.

## 7. Building a build and runtime matrix for generated code

For projects supporting multiple Java releases, build a matrix to clearly confirm which combinations are supported.

Illustrative example:

| Case | JDK running compiler/processor | Release/API target | Test runtime | Goal |
|---|---:|---:|---:|---|
| A | 17 | 17 | 17 | Current baseline |
| B | 21 | 17 | 17 | Newer build while keeping older runtime baseline |
| C | 21 | 21 | 21 | Raise both compile target and runtime |
| D | 25 | 21 | 21 | Test newer compiler/processor while keeping Java 21 baseline |

The actual matrix should reflect the JDKs the project commits to supporting. You do not need to run every mathematically possible combination; prioritize combinations that can occur in CI, release, deployment, and rollback.

For each combination, record:

- Gradle/Maven version and the JDK running the build tool.
- JDK toolchain executing `javac`.
- Processor/generator versions and runtime dependencies.
- Source/API release and bytecode target.
- Minimum Java version used to run the artifact.
- Clean build, incremental build, test, and runtime verification results.

## 8. Configuration and verification example in Gradle

The example below illustrates separating the toolchain, release target, and processor dependency in a Gradle project using the Java plugin:

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}

dependencies {
    compileOnly 'org.mapstruct:mapstruct:<version>'
    annotationProcessor 'org.mapstruct:mapstruct-processor:<version>'
}
~~~

In the example, JDK 21 is used as the compilation toolchain, while the source/API/bytecode baseline is set to Java 17. The MapStruct processor is placed in `annotationProcessor`, separated from runtime dependencies. Verify that the Gradle version, JDK toolchain, MapStruct, and other plugins support this combination.

If test sources also use annotation processing, configure the processor for the corresponding test source set. If there is a separate processor for integrationTest or custom source sets, configure it separately rather than assuming it automatically inherits `main`'s configuration.

After building, inspect the compile task's generated source directory and confirm that the source was included in compilation. Inspect the final JAR with `jar tf`, then run tests on the minimum runtime committed by the project.

## 9. Configuration and verification example in Maven

With the Maven Compiler Plugin, processors can be declared in `annotationProcessorPaths` to separate the processor path from the compile classpath. Structural example:

~~~xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <release>17</release>
        <annotationProcessorPaths>
            <path>
                <groupId>org.mapstruct</groupId>
                <artifactId>mapstruct-processor</artifactId>
                <version>${mapstruct.version}</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
~~~

This is an illustrative structure; use a Maven Compiler Plugin version that supports the corresponding settings and declare the annotation API/runtime library as required by the processor. If using multiple processors, declare each processor and verify ordering/interactions if they jointly generate or read generated types.

For JDK 23 and later, declaring processors explicitly is especially important due to the default discovery change in `javac`. Check the effective POM and compiler command line to confirm that the processor path is actually passed to the compiler.

## 10. Checking in CI and verifying output

A suitable pipeline can perform:

~~~text
Resolve JDK/toolchain and build plugins
              |
              v
Resolve annotation processors / generators
              |
              v
Generate source from schema/template (if any)
              |
              v
Compile + annotation processing according to --release
              |
              v
Inspect generated output and compiler warnings
              |
              v
Unit + integration + runtime tests
              |
              v
Clean/incremental build consistency
              |
              v
Publish build artifact and save build metadata
~~~

Record in build metadata:

- JDK vendor/version/build used for the build.
- Gradle/Maven and compiler plugin versions.
- Processors/generators along with their versions.
- Source/API release and bytecode target.
- Key annotation processing options.
- Schema/template revisions and generated source artifacts if auditing is required.

It is not necessary to commit all generated source into Git. However, CI needs a way to store or deterministically reproduce the output so that when an issue occurs, you can identify which generator or processor produced it.

## 11. Common errors when upgrading the JDK

### Processor does not run

Possible causes include the processor being only on the compile classpath, invalid service metadata, a missing processor path, or the changed discovery policy in the newer JDK. Inspect compiler arguments and build tool configuration, not just dependency presence.

### Processor fails during initialization or when accessing compiler internals

A common cause is an older processor using internal `javac` APIs, reflection, or AST assumptions. Upgrade the processor to a version supporting the target JDK and check release notes. Only use `--add-exports`/`--add-opens` when instructed by the vendor and with a limited scope.

### Generated source fails to compile

Possible causes include the processor not understanding the new source version, the generator producing syntax/APIs exceeding `--release`, or an incompatible runtime dependency. Read the generated source, inspect compiler errors in the generated file, and identify the file's generation source before fixing.

### Generated output differs between clean and incremental builds

Possible causes include inaccurate incremental metadata, processor dependence on nondeterministic ordering, stale outputs not being deleted, or insufficiently declared task dependencies. Compare outputs from both modes, check input/output declarations, and upgrade the processor/build plugin if necessary.

### Build succeeds but runtime fails

Generated code may call APIs absent on the lowest runtime, require an unpackaged runtime dependency, or produce metadata that a newer framework reads differently. Run tests on the target runtime, check the dependency tree and final artifact instead of checking only the compile task.

## 12. Checklist for evaluating generated code and processors by Java version

- [ ] Listed every generator running before the compiler and every annotation processor.
- [ ] Distinguished compile-time annotations, generated outputs, and runtime dependencies.
- [ ] Identified the JDK running the build tool and the JDK toolchain running the compiler/processors.
- [ ] Identified the source/API release, bytecode target, and minimum runtime.
- [ ] Checked the JDK support matrix for the exact processor/generator version.
- [ ] Verified processor discovery, processor path/module path, and service metadata.
- [ ] Reviewed dependencies on `com.sun.tools.javac.*`, reflection, and compiler internals.
- [ ] Checked `SourceVersion` and how the processor handles new language constructs.
- [ ] Checked whether generated source uses syntax/APIs compatible with the release target.
- [ ] Confirmed runtime dependencies and generated classes are packaged properly.
- [ ] Verified clean builds, incremental builds, and output reproducibility.
- [ ] Ran tests on the target JDK and the lowest supported runtime.
- [ ] Saved processor/generator versions, compiler options, and test results in CI.

## 13. Conclusion

Evaluating generated code and annotation processors must examine the tools, the environment running the tools, and the final output. The JDK running the compiler determines the environment in which processors execute; `--release` determines the source/API/bytecode baseline of the compiled code; the minimum runtime determines where the output can run. These three factors can differ and should be documented separately.

When upgrading Java, verify processors/generators against the support documentation for their exact versions, configure discovery explicitly, review compiler internals usage, inspect generated source, and run both clean and incremental builds. Only when generated outputs compile, package, and run properly on the target JDKs does the team have sufficient evidence to accept the change on the migration roadmap.
