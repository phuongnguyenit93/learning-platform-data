# Prerequisite Knowledge and Learning Sequence

In the **Java Advance Compatibility Migration** module, this lesson identifies the knowledge required before starting to migrate a Java application to a newer JDK version, and recommends a learning and practice sequence so that the migration process can be controlled.

Migrating a Java version is not just replacing the JDK and recompiling. An application also depends on platform APIs, third-party libraries, build tools, frameworks, application servers, JVM configurations, and the deployment environment. Therefore, learners need to understand both the source code and the runtime environment of the application. The steps below do not assume a specific pair of Java versions; replace the target version with the version that the project is targeting.

## 1. Learning Objectives

After the lesson, learners can:

- Identify the Java, JVM, build, and testing knowledge needed in a migration project.
- Distinguish source compatibility, binary compatibility, behavioral compatibility, and operational compatibility.
- Gather information about the current Java version, target version, libraries, and runtime environment.
- Read release notes and migration documentation to find changes that may affect the application.
- Use JDK tools to identify deprecated APIs, dependencies on internal APIs, and module-related issues.
- Build a migration sequence that can be verified through builds, tests, and trials in an environment close to production.

## 2. Prerequisite Knowledge

You do not need to become an expert on every component of the JVM before starting. However, you need to understand the following fundamentals to understand the causes of errors and choose an appropriate resolution.

### 2.1. Java Language and Standard Library

Learners should be proficient in the following:

- Program structure, packages, classes, interfaces, inheritance, polymorphism, and access levels.
- Generics, collections, exception handling, and how APIs are organized across modules.
- Annotations, reflection, and dynamic proxies at a level sufficient to read and understand how frameworks use them.
- Lambdas, functional interfaces, and the Stream API if the application uses these features.
- I/O, NIO, networking, serialization, and resource handling.
- Basic concurrency: threads, executors, synchronization, concurrent collections, and visibility issues.

This knowledge helps recognize changes in the standard library, reflection behavior, data stream handling, concurrency, and serialization. When reading a migration error, you need to distinguish errors caused by Java syntax or APIs from errors caused by frameworks or external libraries.

### 2.2. JDK, JVM, and Bytecode

Understand the roles of the main components:

- **JDK (Java Development Kit):** the development toolkit, including the compiler and tools for building, analyzing, packaging, and diagnostics.
- **JVM (Java Virtual Machine):** the bytecode execution environment, managing class loading, memory, garbage collection, and code execution.
- **Bytecode:** intermediate code generated by the compiler and loaded by the JVM to run. The class file version must be supported by the target JVM.
- **Class loader:** the mechanism for loading and linking classes; class loader order and scope can affect server applications or frameworks.
- **Classpath and module path:** two mechanisms for locating and organizing classes/libraries. The Module System needs to be understood if the project uses modules or encounters module access issues.
- **JVM options:** heap parameters, garbage collector, logging, system properties, opening packages, and other runtime options.

Distinguish the JDK version used for compiling from the JDK version used for running. An application can be compiled with one JDK but deployed on another JDK; build and runtime configurations must be recorded separately. The fact that class files can be read by the JVM does not guarantee that all APIs, libraries, and behaviors of the application are compatible.

### 2.3. Build and Dependency Management

Understand the tool the project is using, typically Maven or Gradle:

- How to declare direct dependencies and transitive dependencies.
- Dependency scopes, versions, repositories, and conflict resolution mechanisms.
- Plugins for compilation, packaging, testing, code generation, and static analysis.
- How to run reproducible builds on a local machine and in CI.
- How to create JAR/WAR files, manage resources, and configure profiles or build variants.

Migration can fail before compiling application code if the Maven/Gradle wrapper, plugins, compiler plugin, or CI tools do not yet support the new JDK. Therefore, both application dependencies and build-process dependencies need to be checked.

### 2.4. Frameworks and Deployment Environment

List the components that run alongside the application, for example:

- Frameworks and foundational libraries such as web frameworks, dependency injection, ORM, and logging.
- Application servers, servlet containers, message broker clients, and database drivers.
- Libraries with native code, JNI, monitoring agents, security agents, and profiling tools.
- Operating system, container images, environment variables, certificates, truststores, and network configuration.
- External services that the application communicates with over HTTP, JDBC, messaging, or other protocols.

A library may be compatible with the source code, yet not compatible with the target JDK version. Similarly, an application that runs on a development machine is not guaranteed to run in an actual container or application server.

### 2.5. Testing and Diagnostics

Learners need to know how to run and read the results of:

- Unit tests to verify the behavior of individual components.
- Integration tests to verify connections to databases, filesystems, message brokers, and external services.
- Contract or end-to-end tests to verify communication between systems.
- Performance testing to compare latency, throughput, CPU usage, and memory usage.
- Logs, stack traces, thread dumps, heap dumps, and JVM startup information.

Before migration, you need a baseline test suite that runs on the current version. Without baseline results, it is very difficult to determine whether an error or performance change was introduced by the migration or already existed beforehand.

## 3. Types of Compatibility to Distinguish

A change may pass one type of compatibility and still fail another. Classify the issue before deciding whether to modify source code, upgrade dependencies, or change configuration.

| Compatibility Type | Question to Answer | Example Issues |
| --- | --- | --- |
| Source compatibility | Does the source code compile with the compiler and APIs of the target version? | Removed APIs, changed method signatures, compiler rejecting older usage. |
| Binary compatibility | Can already-compiled classes link and load with classes/libraries in the new environment? | Missing classes or methods, changed data types, `NoSuchMethodError`, `NoClassDefFoundError`. |
| Behavioral compatibility | Does the program continue to produce the expected results and behavior? | Default changes in charset, locale, timezone, TLS, serialization, or error handling. |
| Operational compatibility | Can the application start up, be monitored, and operate stably in the target environment? | Unsupported JVM options, incompatible agents, containers missing tools, or inappropriate memory configuration. |
| Ecosystem compatibility | Do the frameworks, plugins, drivers, and accompanying tools support the new version combination? | Old build plugins, frameworks not yet supporting the target JDK, drivers or native libraries not working. |

For example: a project may compile successfully after upgrading the JDK, but encounter an `IllegalAccessError` at runtime because a library relies on internal APIs or reflective access is restricted. This is a sign that a successful compilation result is not enough to conclude that the migration succeeded.

## 4. Recommended Learning and Practice Sequence

You should learn in order from understanding the current system to analyzing changes, and only then perform the migration and verify the results. Each phase needs to produce a concrete output to serve as the basis for the next phase.

### Step 1: Define Scope and Baseline

First, record:

- The current JDK used to build and the JDK running the application.
- The target Java version and the reason for upgrading.
- How it is built, run, and deployed, and the environments that need to be supported.
- Main modules, related services, and key dependencies.
- The existing test suite along with build/test results on the current version.

Practice by running version-check commands in the exact project environment:

```bash
java -version
javac -version
mvn -version
./gradlew --version
```

Only run the command corresponding to the tool the project is using. On Windows, the Gradle wrapper is typically invoked with `gradlew.bat --version`. Note that the output of `java -version` and `javac -version` may come from different JDKs if `PATH` or toolchain configuration is not aligned.

**Required output:** a record of current/target versions, a high-level component diagram, and baseline build/test results.

### Step 2: Review Java Architecture Relevant to the Application

Focus on the parts the application actually uses: class loading, reflection, module access, concurrency, serialization, networking, security providers, and JVM options. There is no need to read the entire JVM specification if the project does not have a corresponding need.

Practice by selecting a critical business flow and tracing its path from source code through frameworks and libraries to runtime. Record the points that depend on reflection, internal APIs, native libraries, or JVM configuration.

**Required output:** a list of Java/JVM mechanisms the application depends on and locations that may be affected when upgrading versions.

### Step 3: Learn About Changes Between the Current Version and the Target Version

Read the official documentation for each version along the upgrade path, especially release notes, migration guides, API documentation, and notes on security or runtime changes. For a multi-version jump, you should not read only the target version's documentation; a change may have already appeared in an intermediate version.

When reading the documentation, categorize each change by group:

- APIs added, deprecated, marked for removal, or removed.
- Changes to the compiler, bytecode, module system, and access rules.
- Changes to default behavior of the standard library or the JVM.
- Changes related to security, TLS, cryptographic algorithms, and certificates.
- Changes to the garbage collector, logging, monitoring, or JVM options.
- Changes to version requirements of frameworks, plugins, and libraries.

Not every change in the release notes impacts the project. Link each item to actual source code, dependencies, or configuration to determine relevance.

**Required output:** a list of relevant changes, impact levels, how to verify them, and the person/work item responsible for handling them.

### Step 4: Inventory and Analyze Dependencies

Inspect direct dependencies, transitive dependencies, build plugins, frameworks, application servers, drivers, agents, and native libraries. For each component, record the current version, the version supporting the target JDK according to vendor documentation, the planned upgrade version, and accompanying constraints.

You can use tools bundled with the JDK to assist analysis:

```bash
# Find dependencies on JDK internal APIs in a JAR
jdeps --recursive --jdk-internals path/to/application.jar

# Find deprecated APIs in a JAR for the specified release
jdeprscan --release <target-release> path/to/application.jar

# View the module description of a JAR, if the JAR has appropriate module information
jar --describe-module --file path/to/application.jar
```

Replace `path/to/application.jar` with the actual artifact path and `<target-release>` with the release to check that is supported by the tool in use. Depending on the JDK version, syntax and supported release range may vary; check `--help` or that JDK's own documentation before putting the command into CI.

The tools above only help detect certain categories of issues. They do not prove that all dependencies are compatible, do not fully detect all behavioral changes, and do not replace reading vendor documentation.

**Required output:** a dependency matrix and a list of warnings to resolve or verify.

### Step 5: Upgrade Build Tools and Dependencies in a Controlled Order

Check target JDK support for the Maven/Gradle wrapper, compiler plugin, test plugin, packaging plugin, analysis tools, and CI runners. Then determine appropriate versions of frameworks and main dependencies.

When configuring the compilation target, prefer mechanisms that explicitly declare the API release and bytecode to support. With `javac`, the `--release` option compiles against the platform API set and class file format of the selected release within the range supported by the current JDK:

```bash
javac --release <target-release> -d out src/example/App.java
```

In a Maven or Gradle project, the corresponding configuration is usually in the compiler plugin or Java toolchain. Check the documentation for the plugin version in use rather than copying configuration from another project.

Make changes in small batches and rebuild after each meaningful change. When multiple dependencies change together, record the reasons and dependency relationships so you can trace the origin if an error occurs.

**Required output:** updated build scripts and dependencies, along with reproducible build logs.

### Step 6: Address Source Code and Runtime Configuration

Rely on compiler errors, analysis warnings, and migration documentation to address each issue. Common categories include:

- Replace deprecated or removed APIs with supported APIs.
- Remove dependencies on JDK internal packages by using public APIs or library-supported solutions.
- Adjust reflection and module access according to the application's packaging, module descriptors, and access policies.
- Upgrade frameworks/drivers instead of directly modifying third-party library code.
- Update JVM options, system properties, security configurations, and environment settings.
- Verify charset, locale, timezone, TLS, serialization, and defaults that may affect business outcomes.

Adding options to open module access or disabling a security control should not be treated as the default fix. If a temporary compatibility option is needed, clearly document the reason, scope, risk, and removal plan.

**Required output:** explained source code/configuration changes, along with a list of resolved issues and remaining issues.

### Step 7: Test on the Target JDK

Run a clean build and the full applicable test suite. At minimum, verify:

- The application starts up, loads configuration, and connects to dependent services.
- Critical business flows produce the same results as the baseline.
- Error handling, logging, serialization, and network communication work properly.
- Authentication, authorization, TLS, and security settings still meet requirements.
- No class-linking errors, module access errors, or unexplained runtime warnings occur.
- Performance and resource usage remain within acceptable thresholds.

Example general verification commands:

```bash
# Maven
mvn clean verify

# Gradle
./gradlew clean check
```

Run the command appropriate for the project structure and ensure the process actually uses the target JDK. If tests depend on a database, broker, or external service, the test environment must be prepared to match the conditions the tests require.

**Required output:** build/test results, a report of remaining errors, and a performance comparison against the baseline when needed.

### Step 8: Trial Deployment and Release Preparation

Deploy to a test environment close to production, including the JDK distribution, container image, environment variables, JVM options, certificates, agents, and monitoring setup. Monitor startup logs, runtime errors, latency, throughput, CPU, heap, and garbage collection.

Before release, you need to define:

- Migration acceptance criteria and the metrics to monitor.
- How to roll out in stages or limit user scope if the system supports it.
- How to roll back to the previous artifact, image, and runtime configuration.
- Who is responsible for incident handling and what data needs to be collected during a rollback.

**Required output:** trial report, release criteria, rollback plan, and sign-off from responsible parties.

## 5. Learning and Migration Tracking Table

You can use the following table to track progress. Each row should be linked to concrete evidence such as logs, test results, vendor documentation, or repository changes.

| Phase | What to Understand | Completion Evidence |
| --- | --- | --- |
| Baseline | Current/target JDK, build and run setup, existing tests | Environment record and baseline build/test results |
| Java/JVM | Relevant bytecode, class loading, modules, reflection, memory, and JVM options | Description of mechanisms used by the application |
| Release changes | API, runtime, security, and behavioral changes between versions | List of changes relevant to the project |
| Dependency | Libraries, plugins, frameworks, drivers, agents, and native libraries | Version matrix and support status |
| Build/code | Toolchain, compiler, dependencies, and source code | Clean build on the target JDK |
| Verification | Unit, integration, end-to-end, security, and performance | Test report and explained discrepancies |
| Rollout | Deployment environment, monitoring, and rollback | Trial results along with the release plan |

A minimal dependency matrix can include the columns: component name, role, current version, planned version, target JDK support evidence, known issues, action, and status. Do not mark a library as compatible just because it downloads or the build reports no errors.

## 6. How to Learn Effectively

### Learn on a Small Application First

Create or pick a small Java application that has a build, tests, a few dependencies, and runtime configuration. Perform the inventory, analysis, and JDK upgrade steps on this application to understand the process before applying it to a large system. If the project has multiple modules, pick a representative module while still checking shared dependencies.

### Keep Before-and-After Migration Results

Save the baseline JDK version, build logs, test reports, configuration, and performance metrics. After migration, rerun the same scenarios under equivalent conditions. Comparing results helps uncover behavioral or performance changes that the compiler cannot point out.

### Classify Errors Before Fixing

When encountering an error, identify whether it belongs to the compiler, dependency resolution, class loading/linking, module access, runtime behavior, security, or deployment. Then consult the documentation for the exact component and version involved. This classification avoids modifying source code when the actual cause lies in a plugin, driver, or runtime configuration.

### Prioritize Verifiable Evidence

Record the commands run, the actual JDK used, dependency versions, logs, and test results. For any conclusion about supportability, prioritize official documentation from the project or vendor. If evidence is not yet available, mark it as unverified instead of assuming compatibility.

## 7. Common Mistakes

- **Only checking compilation:** a successful build does not confirm binary, behavioral, or operational compatibility.
- **Ignoring transitive dependencies:** indirect libraries may use internal APIs or require an older runtime.
- **Forgetting plugins and CI tools:** a local build succeeds, but the pipeline fails to run because the wrapper, plugins, or runner lack support.
- **Reading only the target version's documentation:** upgrading across multiple releases can accumulate many changes.
- **Upgrading everything at once:** when the JDK, frameworks, drivers, and build plugins change simultaneously, finding the root cause of errors becomes harder.
- **Relying on a single scanning tool:** `jdeps` and `jdeprscan` are useful, but cannot detect all behavioral changes or guarantee that every library works properly.
- **Skipping operational testing:** an application that starts up can still encounter issues with TLS, memory configuration, performance, agents, or containers.
- **Having no rollback plan:** if only new artifacts are kept without preserving old artifacts and configurations, recovery will be slower and riskier.

## 8. Readiness Criteria to Start Migration

Before moving into actual migration work, confirm the following conditions:

- [ ] Current JDK, target JDK, and deployment environments to support have been identified.
- [ ] Baseline build and tests run, or baseline failures have been clearly documented.
- [ ] Relevant modules, frameworks, dependencies, plugins, drivers, agents, and native libraries have been listed.
- [ ] Change documentation across the versions in the upgrade scope has been read.
- [ ] Usages of deprecated APIs, internal APIs, reflection, or sensitive JVM configurations have been identified.
- [ ] A plan exists to upgrade the toolchain and dependencies in verifiable batches.
- [ ] The test suite and metrics used for post-migration comparison have been defined.
- [ ] Test environment, release criteria, and rollback plan have been prepared.

If a condition is not yet met, clearly record what is missing and how to gather evidence. Once the conditions above are met, learners have sufficient foundation to move into analyzing and executing Java compatibility migration systematically.
