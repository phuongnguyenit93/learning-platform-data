# Inventorying actual JDKs across developer machines, CI, and runtime environments

## 1. Why inventory the JDKs actually in use?

In a Java system, the answer to the question “which JDK is the project using?” is usually not a single version. A developer workstation may have multiple JDKs installed; the terminal selects one via PATH; the IDE uses its own Project SDK or Gradle JVM; the Gradle daemon runs on one JVM while the Java toolchain compiles with another JDK; CI runs inside a separate runner or container; and the production application may run in an image containing a different runtime from the build machine.

If you only read the JAVA_HOME configuration or run java -version in one terminal, you only know part of the system. That information is not enough to conclude which JDK the compiler, test process, or application is using.

Inventorying actual JDKs is the practice of gathering evidence for every environment and every process involved in the application lifecycle:

~~~text
Developer workstation
  ├─ Terminal / shell
  ├─ IDE and application run configuration
  └─ Gradle or Maven launched by IDE

CI
  ├─ Runner / agent
  ├─ Job container or build container
  └─ Compiler, test process, and packaging tools

Runtime environment
  ├─ Local / development
  ├─ Test / staging
  └─ Production and each replica / instance
~~~

The goal is to identify the version, vendor, installation path, architecture, and role of each JDK/JRE; then cross-check them against the version declared in the build and the version required by the application.

## 2. Distinguishing JDKs/JVMs within the same workflow

Before collecting information, distinguish the following roles. They may share the same version number, but are not automatically the same entity.

| Role | Meaning | Where to check |
|---|---|---|
| Terminal JDK | The JDK found when running java or javac in the current shell. | PATH, JAVA_HOME, and the actual executable. |
| IDE JDK | The SDK used by the IDE to analyze source code, compile, or run application configurations. | Project SDK, module SDK, run configuration, and IDE runtime. |
| Build tool JVM | The JVM launching Gradle or Maven. With Gradle, pay attention to the daemon JVM as well. | gradlew --version, mvn -version, IDE configuration, and build properties. |
| Java toolchain | The JDK chosen by the build tool for compile, test, javadoc, or specific tasks. | Gradle toolchain, Maven Toolchains, and compiler/test plugin configurations. |
| Test process JVM | The JVM executing tests when a plugin spawns a separate forked process. | Test task configuration, Surefire/Failsafe, and test process logs. |
| Application JVM | The JVM executing the actual application process. | Process on host, inside container, or on application server. |
| Bytecode target | The class file version generated by the compiler. | --release, compiler configuration, or class file inspection. |

For example, a machine may have JDK 21 in the terminal, Gradle daemon running on JDK 21, compiler toolchain using JDK 17, and production running a Java 17 runtime. That can be an intentional configuration if the project sets an appropriate bytecode target. Simply seeing JDK 21 in the terminal is not enough to conclude the application was compiled or is running on Java 21.

### 2.1. JDK and runtime are not always the same

The JDK provides the compiler and development tools such as javac, javadoc, and jcmd. The runtime used to execute the application needs the JVM and required runtime modules, yet may omit the compiler. Some deployment images install only a minimal runtime or a custom runtime built with jlink.

Therefore:

- java -version shows the runtime invoked by the java command in the current environment.
- javac -version shows the compiler invoked by the javac command; this command may not exist on a minimal runtime image.
- The JAVA_HOME path is a configuration value; you must inspect the actual executable used by the shell or process.
- java.home in system properties helps identify the Java home of the JVM running that process.

The absence of javac in production should not be treated as an error if production only needs to run artifacts. Identify the role of the environment properly before evaluating.

### 2.2. Versions to record

Do not record only a major version number like Java 17 or Java 21. Whenever possible, save:

- Full Java and runtime version, including update/build number.
- JDK vendor, e.g., Oracle, Eclipse Temurin, Amazon Corretto, Microsoft Build of OpenJDK, or another distribution.
- JVM name and VM type if available.
- java.home path and actual executable path.
- Operating system and JVM architecture, e.g., x86_64 or aarch64.
- Operating system, image/container, and environment identifier.
- Collection timestamp and commit/artifact version under inspection.

Two machines both showing Java 21 can still differ in vendor, update level, architecture, or runtime path. These differences can matter when investigating native library, TLS, performance, or JVM behavior issues.

## 3. Inventorying on developer workstations

Developer machines often have multiple JDKs installed side by side to serve different projects. The inventory should be performed in the terminal actually used by developers, and then repeated in the IDE if building or running the application from the IDE.

### 3.1. Checking on Windows PowerShell

Run the following commands in PowerShell:

~~~powershell
Write-Output "JAVA_HOME=$env:JAVA_HOME"
Get-Command java -All | Select-Object CommandType, Source
Get-Command javac -All | Select-Object CommandType, Source
where.exe java
where.exe javac
java -version
javac -version
java -XshowSettings:properties -version 2>&1 |
    Select-String 'java.home|java.version|java.vendor|java.runtime.version|java.vm.name|os.arch'
~~~

The commands above answer different questions:

- JAVA_HOME shows the environment variable configured in the PowerShell session.
- Get-Command and where.exe show the executables discoverable through command resolution/PATH.
- java -version and javac -version show the version of the first selected executable.
- java -XshowSettings:properties additionally provides java.home, java.vendor, java.runtime.version, VM name, and architecture.

If JAVA_HOME points to one directory while where.exe java returns an executable in another directory, inspect PATH ordering. Do not modify environment variables immediately during the inventory step; first record both the declared value and the actual result.

### 3.2. Checking on Linux and macOS

In a Bash or Zsh shell:

~~~bash
printf 'JAVA_HOME=%s\n' "$JAVA_HOME"
command -v java
type -a java
command -v javac
type -a javac
java -version
javac -version
java -XshowSettings:properties -version 2>&1 |
  grep -E 'java.home|java.version|java.vendor|java.runtime.version|java.vm.name|os.arch'
~~~

On Linux, you can determine the path after resolving symbolic links:

~~~bash
readlink -f "$(command -v java)"
readlink -f "$(command -v javac)"
~~~

On macOS, you can list the JDKs recognized by the operating system:

~~~bash
/usr/libexec/java_home -V
/usr/libexec/java_home
~~~

The command java_home -V lists the JDKs recognized by macOS; the command without -V returns the Java home selected under current configuration. This result still needs cross-checking against command -v java and java.home of the actual process.

### 3.3. Checking multi-version management tools

Some machines use SDKMAN!, asdf, or jenv to switch Java versions per project directory or shell session. When these tools are used, record the selected version and its scope:

~~~bash
sdk current java
asdf current java
jenv version
~~~

Run only the command corresponding to the installed tool. Output from a version manager helps explain why two terminals on the same machine may pick different JDKs. It does not replace checking the actual executable via java -version and path.

### 3.4. Checking the JDK used by the IDE

An IDE can launch the compiler, Gradle/Maven, or the application with a different JDK than the terminal. Therefore, check each relevant setting:

| IDE / tool | Location or setting to inspect |
|---|---|
| IntelliJ IDEA | Project SDK, module SDK, Gradle JVM, Maven runner JRE, and JRE in each Run/Debug Configuration. |
| Eclipse | Installed JREs, Execution Environments, project JRE, and Maven/Gradle settings if present. |
| Visual Studio Code | Java runtime configured for the extension, project runtime, and integrated terminal. |
| NetBeans | Project Java Platform and the JDK used by the IDE to run tasks. |

Specifically with IntelliJ IDEA, Project SDK and Gradle JVM are two distinct settings. Project SDK can be used to analyze/compile source code inside the IDE, while Gradle JVM is used to launch Gradle. If the developer clicks the Run button, the IDE may also use a separate JRE specified in the run configuration.

You should record the results of both scenarios: running the build from the terminal and running the build from the IDE. If results differ, check the JDK configured in the IDE and the environment variables inherited by the IDE at startup.

## 4. Inventorying Gradle/Maven JVMs and toolchains

Running java -version in the terminal does not fully reveal the build tool's JDK. Check using the project's own wrapper, because the wrapper is the tool version required by the repository.

### 4.1. Gradle

From the project directory, run:

~~~bash
./gradlew --version
~~~

On Windows:

~~~powershell
.\gradlew.bat --version
~~~

Gradle output may display both the launcher JVM and daemon JVM versions. Record both if the Gradle version in use prints them. The launcher JVM is the JVM launching the wrapper/Gradle; the daemon JVM is the JVM executing most build operations.

If the project's Gradle version supports the task listing Java toolchains, you can run:

~~~bash
./gradlew -q javaToolchains
~~~

This task helps inspect the toolchains Gradle detects, including path, vendor, and version when information is available. If the task does not exist in the Gradle version in use, note that a toolchain report was not obtained; do not infer from the daemon's JDK.

During inventory, read the relevant settings:

- JAVA_HOME and PATH in the shell/runner.
- org.gradle.java.home in gradle.properties in user home or project.
- Gradle JVM configured in the IDE.
- Gradle daemon JVM criteria if configured in the repository and supported by the wrapper in use.
- Java toolchain in build scripts or convention plugins.
- Specific configuration of test tasks, javadoc tasks, or tasks that fork Java processes.

org.gradle.java.home controls the JVM used for the Gradle daemon; it does not mean every compilation task uses the same JDK. A Java toolchain can select a separate compiler. A test task can also specify a separate launcher to run tests on a different JVM.

For example, a project might configure its toolchain as follows:

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

In this example, the compiler is selected from the Java 21 toolchain, while bytecode/target APIs are restricted to Java 17. A project's specific configuration may differ; the purpose of the example is to show that toolchain version and bytecode target level are two separate pieces of information to inventory.

### 4.2. Maven

Use the Maven Wrapper if provided by the repository:

~~~bash
./mvnw -version
~~~

On Windows:

~~~powershell
.\mvnw.cmd -version
~~~

The output shows Maven version, Java version, vendor, and Java home used by the Maven process. Running only java -version does not confirm that the Maven Wrapper uses the same runtime.

Next, inspect:

- JAVA_HOME and PATH of the Maven process.
- Maven Wrapper and JVM configuration in .mvn/jvm.config if present.
- maven.compiler.release, source, and target in compiler plugin configuration.
- Maven Toolchains Plugin and toolchains.xml file if used by the project.
- Forked compiler configuration, Surefire/Failsafe, and plugins that spawn separate Java processes.
- JDK used by the IDE Maven runner when running goals from the IDE.

Maven Toolchains allows a plugin to select a JDK different from the JDK running Maven. Therefore, mvn -version confirms Maven's JVM but does not prove which JDK the compiler or test fork runs on. Cross-check toolchain configuration and the corresponding plugin logs.

### 4.3. Do not confuse the build JVM with the bytecode target

The following three values must be recorded as separate fields:

1. JVM running Gradle/Maven.
2. Compiler/toolchain JDK selected for compilation.
3. Target bytecode/API level of the application.

For example, the build tool may run on JDK 21, the compiler toolchain may use JDK 17, and the bytecode target is Java 17. The application can then run on a Java 17 runtime. Conversely, if an artifact requires Java 21 APIs while production only has a Java 17 runtime, the application can fail even though the CI build step succeeded.

## 5. Inventorying JDKs in CI

CI often has multiple execution layers. A workflow may declare a runner image, install a JDK via an action, run a job inside a container, invoke Docker build, and then run tests inside another container. Each layer may use a different JDK.

### 5.1. Identify the execution environment of each job

For each job, record:

- Runner type: hosted runner or self-hosted agent.
- Operating system, image version, and architecture.
- Whether the job runs in a container; if so, record the actual image and digest when provided by the system.
- Step installing/selecting the JDK, including requested vendor and version.
- Whether steps switch into another container or machine to build/test.
- Effective JAVA_HOME, PATH, and Gradle/Maven configurations inside the job.

A workflow configuration line declaring Java 21 only states configuration intent. You must inspect actual commands after the JDK setup step to confirm the runner or container selected the right version.

### 5.2. Print targeted JDK info in the pipeline

You can add a temporary diagnostic step or retain a secret-free environment info step. Example on a Linux runner:

~~~yaml
- name: Inspect Java environment
  shell: bash
  run: |
    printf 'JAVA_HOME=%s\n' "$JAVA_HOME"
    command -v java
    java -version
    command -v javac || true
    javac -version || true
    ./gradlew --version
~~~

If the project uses Maven, replace with or add:

~~~bash
./mvnw -version
~~~

On a Windows runner, use PowerShell:

~~~powershell
Write-Output "JAVA_HOME=$env:JAVA_HOME"
Get-Command java -All | Select-Object Source
java -version
javac -version
.\gradlew.bat --version
~~~

If the build uses Java toolchains, gather additional toolchain information using the mechanism appropriate for the Gradle/Maven version in use. If tests run in a forked JVM or Docker build, inspect the JDK inside that process/container; outer runner info does not represent those layers.

Do not print all environment variables or all system properties into CI logs. Those values can contain tokens, passwords, connection info, or internal data. Print only the needed Java fields and mask sensitive identifiers before sharing logs.

### 5.3. Self-hosted runners and caches

With self-hosted runners, JDKs may be installed manually or managed by an image/agent. Record the actual path and distribution, because the same runner name may be upgraded or reconfigured over time.

Gradle/Maven caches do not prove which JDK was used. A cache is only reused data; the JDK must be confirmed from the current process. If a runner is shared across multiple workflows, check whether each job explicitly installs/re-selects its JDK or depends on leftover state from a previous job.

### 5.4. Record by job and matrix

If CI has a matrix of Java versions, operating systems, or modules, each combination is a separate test environment. Do not collapse all job results into a single row. Record job name, matrix parameters, runner/container, actual JDK, and corresponding verification status.

## 6. Inventorying the JVM of the running application

For runtime environments, what matters is identifying the JVM of the active application process. Configuration in a Dockerfile, manifest, or JAVA_HOME variable is only an input; the process may be launched with a different executable, a different image, or an overriding parameter.

### 6.1. Checking on a Linux machine

First, find the PID of the Java process via the process management tool or process supervisor. Then, if you have access permissions:

~~~bash
ps -p <PID> -o pid,args
readlink -f /proc/<PID>/exe
jcmd <PID> VM.version
jcmd <PID> VM.system_properties |
  grep -E '^(java.home|java.version|java.vendor|java.runtime.version|java.vm.name|os.arch)='
~~~

/proc/<PID>/exe reveals the executable the process is running on Linux. jcmd can query VM version and system properties of the target process if the tool is compatible and the user/permissions and attach mechanism allow it. Some minimal production environments do not install jcmd; in those cases, use evidence from the executable, image, and runtime metadata provided by the platform.

### 6.2. Checking on Windows

With appropriate permissions, you can query the executable path and command line of the process:

~~~powershell
$javaPid = 1234
Get-CimInstance Win32_Process -Filter "ProcessId = $javaPid" |
    Select-Object ProcessId, ExecutablePath, CommandLine
~~~

Replace 1234 with the actual PID. If the machine runs multiple Java processes, you must identify the exact PID of the application being inventoried; do not infer from an arbitrary Java process.

If a compatible JDK and attach permissions are available, you can use jcmd with that PID to view the VM version and needed properties. Output from jcmd reflects the queried process better than running java -version in another PowerShell window.

### 6.3. Checking inside Docker

If the container has a shell and Java tools:

~~~bash
docker exec <container> java -version
docker exec <container> sh -lc 'command -v java; printf "JAVA_HOME=%s\n" "$JAVA_HOME"'
~~~

If the application has its own PID, check the executable or VM properties of the exact PID inside the container. Do not assume the application PID is always PID 1.

Also record:

- Actual image name/tag and image digest.
- Base JDK/JRE image declared in the Dockerfile.
- Entrypoint, command, and Java environment variables.
- Container ID, creation timestamp, and running artifact version.

An image tag can be updated to point to another image. The digest helps identify the actual image deployed at inventory time. The Dockerfile shows how the image was intended to be built; the digest and running process help confirm the actual artifact/runtime.

### 6.4. Checking on Kubernetes

In Kubernetes, a workload can have multiple pods, multiple containers, and multiple replicas. Inspect each container type running Java: application containers, sidecars, or task-processing containers. For the pod being inventoried, record the declared image and the imageID/digest pulled by the node.

For example, you can check pod and container info with kubectl describe pod or query required fields from the Pod specification/status. If the container permits command execution:

~~~bash
kubectl exec <pod> -c <container> -- java -version
~~~

If a specific process needs inspection, use the PID inside the container and an appropriate observation mechanism. A pod can be replaced during inventory; record namespace, pod name, container name, node, timestamp, and imageID so results can be correlated.

Some distroless or minimal images lack a shell, java on PATH, or jcmd. In that case, do not conclude Java is absent. Use the image digest, command/args, process executable if the platform exposes it, or a diagnostic mechanism supported by your organization. Do not alter production images solely to install inspection tools.

### 6.5. Checking across each environment and replica

Do not inspect only one machine to represent all of production. The system may be mid-rolling deployment, with some instances still running an old image or a worker group using a different runtime from the web application.

At a minimum, distinguish environments that actually exist such as local, development, test, staging, and production. In production, identify workload/replica groups sharing the same configuration and check enough instances to detect version drift. If certain processes are managed by a scheduler or job runner, include them in the inventory when they execute system Java code.

## 7. Reconciling declarations against actual results

After collecting data, clearly distinguish three categories of information:

1. **Declared:** the version written in build files, toolchains, workflows, Dockerfiles, or manifests.
2. **Selected environment:** the JDK found via PATH, JAVA_HOME, IDE settings, runner setup, or container image.
3. **Actual process:** the JVM/compiler that executed the build, tests, or application at inventory time.

These categories can differ without always being an error. For example, a project deliberately builds with JDK 21 yet produces Java 17 bytecode and deploys on a Java 17 runtime. What must be done is confirming that combination falls within the accepted compatibility matrix.

### 7.1. Common discrepancies

| Observation | Possible cause | What to verify |
|---|---|---|
| JAVA_HOME points to one JDK, yet java -version shows another. | PATH prioritizes another executable; shell/IDE has not picked up updated variables; a version manager selects another version. | Executable path, PATH ordering, and process environment. |
| Terminal and IDE builds yield different results. | IDE has its own Project SDK, Gradle JVM, or Maven runner JRE. | Compare configuration and logs of each execution path. |
| gradlew --version shows a daemon JDK different from terminal. | org.gradle.java.home, daemon JVM criteria, or IDE setting selects another JVM. | Effective Gradle configuration and daemon JVM. |
| Gradle daemon uses JDK A, yet compile uses JDK B. | Java toolchain specifies a separate compiler. | Toolchain report and compiler tasks. |
| Maven runs on JDK A, yet compiler uses JDK B. | Maven Toolchains or compiler fork. | toolchains.xml, plugin configuration, and compiler logs. |
| CI runner uses a newer JDK, yet application in container uses an older JDK. | Docker build/runtime image has its own JDK. | Image digest and JVM inside the container. |
| Some pods run a different version from remaining pods. | Rolling deployment, node/image cache, or incomplete rollout. | ImageID and runtime of each replica. |
| javac is absent in production. | Runtime image contains only JRE or minimal runtime. | Confirm application process and runtime; do not require compiler if on-box compilation is unneeded. |

### 7.2. Do not infer runtime version from bytecode target

The bytecode target indicates the class file level emitted by the compiler, not which JVM is running the application. Similarly, a Java 21 runtime can execute bytecode compiled for Java 17. Therefore, reports must have separate fields for:

- JDK running the compiler.
- Release/bytecode target.
- Application runtime JVM.

If you need to verify a class file, you can run javap -verbose on a compiled class and check its major version. However, the class-file version number is evidence of the inspected class's bytecode; it does not determine the JDK of the build process or running runtime.

## 8. JDK inventory table template

Use one row per meaningful role/environment. Do not merge developer workstations, CI, and production into one row because they can have different configurations.

| Environment / host | Role / process | JDK/JVM version and vendor | Executable / java.home | Architecture | How JDK is selected | Evidence / timestamp |
|---|---|---|---|---|---|---|
| Developer workstation | Terminal |  |  |  | JAVA_HOME / PATH / version manager |  |
| Developer workstation | IDE build/run |  |  |  | Project SDK / IDE runner |  |
| Developer workstation | Gradle daemon or Maven |  |  |  | Wrapper / IDE / gradle.properties |  |
| Developer workstation | Compiler toolchain |  |  |  | Gradle toolchain / Maven Toolchains |  |
| CI job | Runner / agent |  |  |  | Runner image / setup step |  |
| CI job | Build container / test JVM |  |  |  | Container image / task configuration |  |
| Runtime environment | Application process |  |  |  | Image / startup command / process |  |
| Runtime environment | Worker / scheduled job |  |  |  | Image / service configuration |  |

Depending on system scale, additional fields may be added:

- Project/module name, job, service, pod, or container.
- OS and OS version; runner label or node.
- JDK distribution, full build number, and image digest.
- PID/process name, artifact version, and commit SHA.
- JAVA_HOME, selected PATH entry, and toolchain configuration.
- Bytecode target, framework version, and support status.
- Responsible person/team and next inventory timestamp.

Example of recording one row, with illustrative values:

| Environment / host | Role / process | JDK/JVM version and vendor | Executable / java.home | Architecture | How JDK is selected | Evidence / timestamp |
|---|---|---|---|---|---|---|
| CI job compile | Gradle daemon | Java 21, vendor per actual output | Path taken from java.home | Per os.arch | Runner setup and Gradle configuration | Log gradlew --version, execution time |

Do not fill in values based on guesswork. If an environment cannot yet be accessed, mark it “unverified”, note the reason, and specify what evidence is missing.

## 9. Repeatable inventory workflow

A standardized workflow makes it possible to compare results across teams and across migrations:

1. **Define environment scope:** list workstations/IDEs, CI jobs, build containers, test environments, runtime services, workers, and relevant replicas.
2. **Record declared configurations:** JDK version, vendor, toolchain, workflow setup, image, startup command, and bytecode target.
3. **Collect from actual environments:** run inspection commands in the exact terminal/runner/container or query the exact running process.
4. **Separate by role:** record build-tool JVM, compiler toolchain, test JVM, and application JVM separately.
5. **Reconcile:** compare declarations, selected environment, and actual processes; explain every intentional difference.
6. **Record evidence:** save selective outputs, paths, image digests, job/pod/PID, and check timestamp.
7. **Mark unverified parts:** clearly record environments that could not be accessed or tools that could not attach.
8. **Establish baseline:** use the verified table as a baseline to compare against the target JDK in the migration plan.

When repeating the inventory after changes, use the same commands and the same environment identification method. If runner images, container digests, or replica counts change, record them so comparisons target the right subjects.

## 10. Protecting information while collecting evidence

JDK details are usually less sensitive than application configs, yet system logs can still contain usernames, hostnames, internal paths, command lines, JVM arguments, or system properties holding secret data.

When sharing inventory results:

- Collect only necessary Java properties; do not dump all environment variables or all system properties.
- Review command lines and logs before putting them in tickets, repositories, or shared documents.
- Redact tokens, passwords, URLs with credentials, connection strings, and personal identifiers.
- Retain technical fields needed for reconciliation such as Java version, vendor, java.home, architecture, and image digest.
- Respect environment access permissions; do not attempt to attach to processes or containers without authorization.

## 11. Expected outputs after inventorying

A complete inventory pass should allow the team to answer:

- Which JDKs are installed on developer machines, and which version do terminal/IDE pick?
- Which JVM launches Gradle or Maven?
- Which toolchain do the compiler and test processes use?
- Which JDKs exist in CI runners, job containers, and Docker build/runtime images?
- Which JVM is the application actually running on across each environment and replica?
- What is the artifact's bytecode target?
- Which differences are intentional, and which differences are drifts needing remediation?
- Which environments lack confirming evidence?

The results should be stored as a baseline with inventory date, evidence sources, and owner. This baseline serves as input for selecting the target JDK, determining compatible build tools/frameworks, planning the upgrade, and verifying after migration. Without knowing the exact JDK used at each layer, teams can easily fix the wrong setting or judge success based on an environment that does not represent the real system.
