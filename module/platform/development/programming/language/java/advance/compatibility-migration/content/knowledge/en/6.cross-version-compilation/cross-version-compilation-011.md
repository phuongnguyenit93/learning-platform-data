
# Verifying an Artifact on the Minimum Supported JDK

When a library or application declares support starting from a minimum Java version, the development team must prove the released artifact actually runs on that version. Compiling successfully with a new JDK or setting an older bytecode target is not enough to prove compatibility.

For example, a team might build with JDK 21 while committing to support a Java 17 runtime. The compiler can generate Java 17 bytecode and restrict permitted Java SE API references, yet a dependency compiled for Java 21, a dynamically loaded class, a Java agent, or a native library can still cause the application to fail on Java 17.

Verification must be executed on the **final packaged artifact**, using the **exact minimum supported JDK**, in an environment matching deployment configuration. Results must tie to the exact artifact file, JDK version, dependencies, OS, and architecture tested.

## 1. Define Exactly What Must Be Proven

Before running tests, clearly define the product's compatibility claim.

For instance, a library declares:

> Supports Java 17 runtime and newer.

This means consumers can use the artifact on Java 17 if published conditions and dependencies are met. It does not automatically mean:

- Every JDK 17 release from every vendor has been tested.
- Build tools and plugins can all run on JDK 17.
- Every operating system and CPU architecture is supported.
- Every optional dependency or external plugin is compatible.
- The application can use APIs introduced in Java 21 and still run on Java 17.
- An artifact built with JDK 21 naturally runs on Java 17.

Separate the following concepts:

| Concept | Question to Answer |
|---|---|
| Build JDK | Which JDK runs Gradle/Maven, the compiler, and plugins? |
| Compiler target | Which Java syntax and APIs may the source code use? |
| Bytecode target | Which Java version are the output class files compatible with? |
| Runtime baseline | What is the lowest JDK version the product commits to supporting? |
| Dependency baseline | Do all runtime dependencies support that same baseline? |
| Environment baseline | Which OS, CPU, native libraries, and configurations fall within support scope? |
| Artifact identity | Which file was tested, and is it identical to the file being released? |

An example matrix:

| Component | Value |
|---|---|
| JDK used to build | 21 |
| Compiler/API release | 17 |
| Declared minimum runtime | 17 |
| Runtime dependencies | All must support Java 17 |
| Verification runtime | JDK 17 |
| Additional verification runtime | JDK 21 |
| Artifact | The exact JAR/WAR/ZIP entering release |

If the product supports multiple platforms, expand the matrix by OS and CPU. Do not collapse "Java 17" into a single generic result when native libraries or system behavior are platform-dependent.

## 2. Why Target Bytecode Is Not Enough

### 2.1. Bytecode Is Only Part of the Contract

Every class file carries a major version. A JVM can only load class files within the version range it supports. Key milestones:

| Java | Class file major version |
|---|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

If a class compiled for Java 21 is loaded on JVM 17, the application can throw:

~~~
java.lang.UnsupportedClassVersionError
~~~

Setting a Java 17 target for your application source only governs the classes generated by that compiler. It does not downgrade bytecode inside external dependencies to Java 17.

An application can contain:

- Main classes compiled at major version 61.
- Dependency A compiled at major version 61.
- Dependency B compiled at major version 65.
- A plugin loaded from an extension directory also at major version 65.

JVM 17 can still fail when loading Dependency B or the plugin, even though the remaining classes are all major version 61.

### 2.2. Java SE APIs Must Also Match the Version

A class with a valid major version can still reference APIs that exist only on a newer JDK. For example, a newer compiler may compile a new API call if you restrict only bytecode target without restricting the API surface.

On modern JDKs, use `--release` to constrain simultaneously:

1. Java language rules.
2. The permitted set of Java SE APIs.
3. The output bytecode version.

Example:

~~~
javac --release 17 -d out src/com/example/App.java
~~~

However, `--release 17` controls only the compilation step where it is applied. It does not verify every dependency, reflection target, dynamically generated class, Java agent, or native library inside the final artifact.

### 2.3. Dependencies Can Require a Higher Baseline Than the Application

Suppose an application is compiled with `--release 17`, yet a runtime library requires Java 21. The application may still build successfully if the compiler needs only the library's compile-time signatures without checking minimum Java versions across all bytecode.

When running on Java 17, the library's classes may fail to load. Thus, the product baseline is constrained by the runtime component with the highest Java requirement along actual execution paths.

Check direct dependencies, transitive dependencies, plugins, and dynamically loaded modules.

## 3. Configuring the Build to Target the Minimum JDK

### 3.1. Gradle: Separating Build Toolchain and Target Release

A project can use JDK 21 to execute the build while producing Java 17-compatible bytecode:

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

In this configuration:

- Gradle selects JDK 21 as the compilation toolchain.
- The compiler enforces Java 17 limits for source, Java SE APIs, and bytecode.
- Java compilation tasks inherit this configuration, including test sources if they are also `JavaCompile` tasks.

The JDK version running Gradle itself remains a separate concern. The Gradle Wrapper, plugins, and convention plugins may require a newer JDK than the application's runtime baseline. Record the build JDK and the product runtime JDK separately.

### 3.2. Running Tests on the Exact Minimum JDK

If tests are only compiled and executed on JDK 21, you have not proven the Java 17 runtime works.

You can configure the Gradle test launcher to run tests on JDK 17:

~~~groovy
tasks.withType(Test).configureEach {
    javaLauncher = javaToolchains.launcherFor {
        languageVersion = JavaLanguageVersion.of(17)
    }
}
~~~

This configuration requires JDK 17 to be installed or supplied via toolchain provisioning. Check logs to verify which JVM actually runs the test process.

For integration tests, ensure the test process executes against the packaged artifact. Tests calling classes directly from source sets or output directories can miss packaging errors, missing resources, or missing runtime dependencies.

### 3.3. Maven: Compiler Release and Test Runtime

With the Maven Compiler Plugin, declare the target release:

~~~xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
~~~

This instructs the compiler to apply Java 17 language level, Java SE APIs, and bytecode when running on a suitable JDK.

To test on JDK 17, configure the environment or Maven Toolchains/Surefire appropriately so the test process uses JDK 17. Setting compiler release does not automatically switch the JVM running Maven or forked tests to JDK 17.

### 3.4. Controlling Every Compiler in the Project

Multi-language or multi-module projects must inspect each compiler individually:

- Java compiler: `options.release` or compiler release.
- Kotlin compiler: JVM target and referenced JDK/API set.
- Groovy compiler: target bytecode and runtime dependencies.
- Scala compiler: target bytecode and JDK-compatible Scala version.
- Code generators and annotation processors: the JDK running the processor and the generated class files.

Do not assume a `JavaCompile` setting automatically applies to other compilers. Inspect outputs of every module and test on the minimum JDK.

## 4. Identifying the Exact Artifact to Verify

A common mistake is testing classes in the build directory while shipping a different JAR/WAR. Artifacts can differ because:

- Dependencies were packaged or excluded differently.
- Resources were not copied.
- Manifests or module descriptors differ.
- Classes were relocated, shaded, or transformed.
- Plugins were placed in a separate directory.
- Native libraries were packaged by classifier or platform.
- Executable JARs embed nested dependencies.
- Packaging generated extra metadata or code.

Therefore, the workflow must pinpoint the exact output artifact, e.g.:

~~~
build/libs/application-1.2.0.jar
~~~

Generate a checksum before testing and store it alongside the report:

~~~
sha256sum build/libs/application-1.2.0.jar
~~~

On Windows you can use:

~~~
Get-FileHash .\build\libs\application-1.2.0.jar -Algorithm SHA256
~~~

After testing, compare the tested file's checksum with the file prepared for release. If the artifact changes after testing, prior test results no longer validate the new file.

### 4.1. Inspecting JAR/WAR Contents

List contents:

~~~
jar tf application.jar
~~~

Verify:

- Application classes.
- Config resources and metadata files.
- Packaged dependencies.
- Service providers under `META-INF/services`.
- Module descriptor `module-info.class`.
- Manifest.
- Native files such as `.dll`, `.so`, `.dylib`.
- Classes or resources generated during the build.

For executable JARs using nested JAR structures, examine the framework's packaging layout. Some bytecode analysis tools do not recursively scan all nested JARs automatically.

### 4.2. Checking Class File Versions

Use `javap` to check a class's major version:

~~~
javap -verbose -classpath application.jar com.example.Application
~~~

In the output, locate:

~~~
major version: 61
~~~

Major version 61 corresponds to Java 17. Inspect key classes across dependencies, plugins, and internal modules. One representative class having major version 61 does not prove the entire JAR complies.

If an artifact bundles many dependencies, extract each JAR to check class files or run an appropriate bytecode analysis tool to report across the full archive.

## 5. Checking Dependencies Against the Baseline

### 5.1. Inspecting the Runtime Dependency Graph

With Gradle:

~~~
./gradlew dependencies --configuration runtimeClasspath
~~~

To find why a dependency version was selected:

~~~
./gradlew dependencyInsight --dependency artifact-name --configuration runtimeClasspath
~~~

With Maven:

~~~
mvn dependency:tree -Dscope=runtime
~~~

Record direct and transitive dependencies, including:

- Group, artifact, and version.
- Scope/configuration.
- Actual resolved version.
- Excluded or substituted dependencies.
- Modules or plugins loaded only in a specific environment.
- Dependencies provided externally outside the artifact.

### 5.2. Verifying Each Dependency's Minimum Java Version

Not every dependency declares its Java baseline clearly in metadata. Check:

- Vendor's Java requirement documentation.
- Release notes and migration guides.
- Class file major versions.
- Referenced Java SE APIs.
- Native binaries and platform classifiers.
- Transitive dependencies of that library itself.

A library may have Java 17 class files while a runtime branch invoked only in a rare feature references a newer API. Therefore, static analysis must accompany testing.

### 5.3. Using jdeps to Analyze Dependencies

Example:

~~~
jdeps --recursive --class-path "lib/*" application.jar
~~~

To check dependencies on JDK internal APIs:

~~~
jdeps --jdk-internals --recursive application.jar
~~~

For a multi-release JAR, specify the runtime view:

~~~
jdeps --multi-release 17 --recursive application.jar
~~~

Depending on packaging structure, classpath and module path must be supplied accurately. The tool does not automatically guarantee analysis of dynamically loaded classes or nested JARs.

### 5.4. Deprecated or Removed APIs

Run the deprecation scanner against the target release:

~~~
jdeprscan --release 17 application.jar
~~~

Focus on APIs marked for removal:

~~~
jdeprscan --release 17 --for-removal application.jar
~~~

These results supplement baseline verification. Deprecated APIs do not necessarily prevent running on Java 17, but warn of migrations needed in future releases.

## 6. Verifying Multi-Release JARs

A Multi-Release JAR allows a library to package different class versions per Java version. Base classes sit at the JAR root; version-specific replacements sit under:

~~~
META-INF/versions/<N>/
~~~

The manifest must declare:

~~~
Multi-Release: true
~~~

Example structure:

~~~
library.jar
├── META-INF/
│   ├── MANIFEST.MF
│   └── versions/
│       ├── 17/
│       │   └── com/example/Feature.class
│       └── 21/
│           └── com/example/Feature.class
└── com/
    └── example/
        └── Feature.class
~~~

When running on Java 17, the JVM picks the base class or the class in version directory 17 according to multi-release rules. Classes in directory 21 are ignored by a Java 17 runtime.

Therefore, verify:

1. Base classes are compatible with the minimum JDK.
2. Classes inside versioned directories are compiled for their matching Java level.
3. The manifest correctly declares `Multi-Release`.
4. APIs across class versions preserve the required compatibility contract.
5. Testing on the minimum JDK actually selects the intended base/17 implementation.
6. Testing on newer JDKs confirms version-specific implementations work.

Do not inspect only classes in `META-INF/versions/21` and conclude the JAR supports Java 17. Verify the exact execution path chosen by JVM 17.

## 7. Running the Artifact on the Minimum JDK

This is the most important direct verification step. Take the exact artifact file identified earlier and run it with the minimum supported JDK.

First, confirm the runtime:

~~~
java -version
~~~

If multiple JDKs exist on the machine, invoke the explicit executable path to avoid accidentally picking up a newer Java version:

~~~
/opt/jdk-17/bin/java -version
/opt/jdk-17/bin/java -jar application.jar
~~~

On Windows, use the path to `java.exe` belonging to the installed JDK 17.

### 7.1. Startup Verification

Confirm:

- The JVM starts cleanly.
- The main class is located.
- Dependencies and resources load.
- The application context or container initializes cleanly.
- No class version, missing class, or missing method errors occur.
- Agents and native libraries load if configured.
- Health checks reach ready state.

A clean startup proves only the components exercised during the startup phase.

### 7.2. Functional Verification

Exercise representative application flows:

- Primary APIs or commands.
- Database and message broker access.
- Serialization/deserialization.
- Reflection, proxies, and dependency injection.
- Plugins or dynamically loaded modules.
- Scheduled jobs and background workers.
- Logging, metrics, and tracing.
- Native integrations or external process calls.

For a library, create an independent sample consumer using the published artifact. The consumer should be compiled and run on the minimum JDK to verify exactly how library users integrate it.

### 7.3. Shutdown and Operational Error Checks

Do not stop at startup checks. Verify:

- Graceful shutdown.
- Resource cleanup hooks.
- Threads and executors terminate.
- Connection pools release properly.
- Files, sockets, and native resources do not leak.
- The application can restart.
- Logging and diagnostics work on the minimum runtime.

An application can start smoothly yet fail during shutdown or under realistic load.

## 8. Testing in the Exact Deployment Environment

The minimum JDK is one axis of the matrix. OS, CPU, and container images can also affect execution.

| Axis | Examples to Check |
|---|---|
| Java runtime | JDK 17, JDK 21 |
| Vendor | Announced supported JDK distribution |
| OS | Linux, Windows, macOS if supported by the product |
| CPU | x86-64, ARM64 |
| Container | Base image, libc, and system libraries |
| Runtime config | JVM flags, environment variables, truststore |
| Dependencies | Runtime classpath, plugins, and native libraries |

Every combination does not necessarily need testing if the product supports only specific environments. However, the support matrix must be published clearly and CI must verify critical representative combinations.

### 8.1. Container Testing

Run the artifact inside an image containing the exact minimum JDK:

~~~
docker run --rm \
  -v "$PWD/build/libs/application.jar:/app/application.jar:ro" \
  -w /app \
  eclipse-temurin:17-jre \
  java -jar application.jar
~~~

This example illustrates a Linux shell and Java 17 image. Adapt image, volume mount, and command for your project's OS, architecture, and deployment process.

If production uses a minimal image, test that exact image. A full JDK image may contain tools or system libraries missing from a JRE/minimal image.

### 8.2. Encoding, Timezone, and Locale

Test Vietnamese text data, dates/times, timezones, and filesystem operations on the target environment. If the application relies on OS defaults, results may differ between developer workstations and production.

Prefer declaring encodings and timezones explicitly in code or configuration. Record runtime defaults if the application must rely on them.

### 8.3. TLS and Certificates

The minimum JDK may have a different truststore, security algorithms, or TLS policies from a newer JDK. Test connections to databases, external APIs, brokers, and internal services.

Do not test only unencrypted HTTP or mock servers if production uses TLS. Test with certificates and truststores matching the deployment environment.

## 9. Checking Easily Overlooked Components

### 9.1. Reflection and Module Access

Test flows using `setAccessible`, `trySetAccessible`, `MethodHandles`, ORMs, serializers, and framework proxies. Run on the minimum JDK to catch errors such as:

~~~
java.lang.reflect.InaccessibleObjectException
~~~

Document packages/modules needing to be opened if any. Do not add broad access permissions indiscriminately just to make tests pass.

### 9.2. Java Agents

If the application uses `-javaagent`, run that exact agent on the minimum JDK and verify:

- The agent loads cleanly.
- Transformers work.
- Transformed bytecode remains valid.
- Other agents do not conflict in ordering.
- The Attach API works if the product requires dynamic attach.

### 9.3. Native Libraries

Verify the exact packaged binary and environment architecture. For JNI/JNA/FFM, execute at least one real path confirming the library loads, symbols resolve, and data passes accurately across the native boundary.

If separate binaries exist per OS/CPU, test every platform included in the support commitment.

### 9.4. Class Loading and Service Providers

Test `ServiceLoader`, plugin directories, module paths, classpaths, and custom class loaders. A class may load only when a specific feature is invoked, escaping startup tests.

## 10. Designing CI to Protect the Minimum JDK

A basic CI matrix can build once and then test the artifact across supported runtimes:

~~~mermaid
flowchart TD
    A["Checkout source"] --> B["Build with build toolchain JDK"]
    B --> C["Package artifact"]
    C --> D["Generate checksum and store artifact"]
    D --> E["Test artifact on minimum JDK"]
    D --> F["Test artifact on newer JDK"]
    E --> G["Aggregate results"]
    F --> G
    G --> H{"All supported runtimes pass?"}
    H -->|Yes| I["Allow release"]
    H -->|No| J["Block release and investigate"]
~~~

Crucially, runtime jobs must download or reuse the exact single built artifact rather than rebuilding from source on each JDK and testing different outputs. If each job builds its own artifact, you are testing different products and may miss discrepancies between build and release.

Example steps:

1. Build the artifact on the designated build JDK.
2. Generate SHA-256 and store the artifact as an immutable CI output.
3. The minimum JDK job downloads that exact artifact.
4. Verify the checksum before running.
5. Run smoke tests, integration tests, and platform checks.
6. The newer JDK job also downloads the same artifact.
7. Aggregate reports by Java version and environment.
8. Release only the artifact that passed required gates.

### 10.1. Runtime Matrix in GitHub Actions

Runtime versions can be expressed via a matrix:

~~~yaml
strategy:
  fail-fast: false
  matrix:
    java: [17, 21]

steps:
  - uses: actions/setup-java@v4
    with:
      distribution: temurin
      java-version: ${{ matrix.java }}
  - name: Verify runtime
    run: java -version
  - name: Run artifact smoke tests
    run: ./scripts/test-artifact.sh build/libs/application.jar
~~~

This is only an illustrative skeleton. If build and test workflows reside in separate jobs, upload/download the artifact and verify its checksum. Never let the test step accidentally rebuild the JAR using the matrix JDK.

### 10.2. Storing Verification Evidence

Every CI run should store:

- Artifact SHA-256.
- Full JDK version and vendor.
- Runner OS and architecture.
- Dependency graph or SBOM if available.
- Compiler lint, `jdeprscan`, and `jdeps` results.
- Startup and test logs.
- Critical JVM flags.
- Container image version or digest.
- Execution timestamp and source commit.

This information helps the team identify which artifact was verified and reproduce issues after release.

## 11. Pass and Fail Criteria

### Pass

You can conclude an artifact meets the baseline when:

- The artifact with the matching checksum was used during testing.
- The runtime is the exact declared minimum JDK.
- The JVM loaded all required classes across tested execution paths.
- Runtime dependencies support the baseline.
- No linkage errors occur due to missing APIs/classes/modules.
- Reflection, agents, plugins, and native integrations function within support scope.
- Critical features and regression tests pass.
- OS/CPU/image are within the published support matrix.
- Logs and evidence are tied to the artifact.

### Fail

Block release or log a blocker when situations occur such as:

- `UnsupportedClassVersionError` from application or dependency classes.
- `NoSuchMethodError` or `NoClassDefFoundError` on the baseline.
- A required API or module was removed.
- Blocked reflection causes a mandatory feature to fail.
- An agent fails to load or produces invalid transformed bytecode.
- A native library has the wrong architecture or missing symbols.
- Critical business tests fail.
- The tested artifact checksum does not match the artifact prepared for release.

If an optional feature is outside support scope, clearly document the condition and how to disable it. Do not claim the entire product "supports Java 17" if a mandatory feature requires Java 21 or higher.

## 12. Sample Verification Report

Use the following template to record results:

| Field | Value |
|---|---|
| Product/version | application 1.2.0 |
| Artifact | application-1.2.0.jar |
| SHA-256 | checksum of tested file |
| Build JDK | JDK 21, vendor and update |
| Compiler release | 17 |
| Runtime tested | JDK 17, vendor and update |
| OS/CPU | Linux x86-64 |
| Container image | Tag name and digest |
| Dependency status | Checked runtime graph |
| Startup | PASS/FAIL |
| Integration tests | PASS/FAIL |
| Agent/reflection/native | PASS/FAIL/NOT USED |
| Known limitations | Unsupported conditions |
| Evidence | Links to logs, test reports, and artifact metadata |
| Decision | PASS/FAIL/BLOCKED |

Do not record PASS if baseline testing has not been performed. If a section has not been tested, record NOT TESTED or UNKNOWN and state the impact clearly.

## 13. Execution Checklist

### Build and Artifact

- [ ] Identified the build JDK and compiler target.
- [ ] Applied `--release` or equivalent baseline configuration.
- [ ] Checked compilers for every language/module.
- [ ] Packaged the final artifact.
- [ ] Generated checksum and stored the exact tested artifact.
- [ ] Inspected manifest, resources, service providers, module descriptors, and packaged dependencies.
- [ ] Checked class file versions of both application and dependencies.

### Minimum Runtime

- [ ] Confirmed `java -version` matches the minimum supported JDK.
- [ ] Executed the exact packaged artifact.
- [ ] Verified startup and health checks.
- [ ] Ran core functional and integration tests.
- [ ] Tested shutdown, restart, and resource release.
- [ ] Tested reflection, agents, plugins, and native integrations if present.
- [ ] Tested on OS/CPU/containers included in the support commitment.

### CI and Evidence

- [ ] Runtime matrix uses the exact same artifact and checksum.
- [ ] Did not rebuild separate artifacts in each runtime job when verifying the same release.
- [ ] Stored logs, test reports, and JDK versions.
- [ ] Documented known limitations and untested portions.
- [ ] Marked PASS only after mandatory gates passed.

## Conclusion

Verifying an artifact on the minimum JDK directly confirms the runtime compatibility commitment. Compiler target and bytecode version form the foundation, yet dependencies, Java SE APIs, reflection, agents, native libraries, packaged resources, and deployment environments can still cause an artifact to fail.

Build the artifact per specified configuration, identify it by checksum, and run that exact file on the minimum JDK in a representative environment. Combine static analysis with startup, integration, and real behavioral checks; store evidence keyed by artifact and runtime. Only when all declared support conditions have been verified is there sound basis to conclude the product meets its baseline.
