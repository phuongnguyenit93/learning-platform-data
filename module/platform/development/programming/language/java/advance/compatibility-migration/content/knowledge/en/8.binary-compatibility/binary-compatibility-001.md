# Binary names, symbolic references, and the class linking process

A Java application does not call classes and methods by looking up source code every time it runs. After compilation, bytecode stores references to types, fields, and methods by name along with descriptors. When an application is loaded and run with different library versions, the JVM must find the right class, identify the right member, and verify that those references are still valid. This is the foundation of **binary compatibility** and is also why a small change in a library may only cause errors when the application runs.

To understand linking errors during migration, it is necessary to distinguish three concepts: **binary name** is the class identifier name at the binary level; **symbolic reference** is a reference recorded in a class file to a class or member; **linking** is the process by which the JVM verifies and resolves those references so that bytecode can be executed.

## 1. Class names at different layers

A Java type can be represented by multiple name forms depending on the context. Names used in source code should not be confused with names used by class files or the JVM.

### 1.1. Names in source code

Source names are usually simple names or names written with a package. For example:

~~~java
package com.example.billing;

public class Invoice {
    public static class LineItem {
    }
}
~~~

In source code, the outer class is referenced by `Invoice`, while the member class can be written as `Invoice.LineItem` in the appropriate scope or `com.example.billing.Invoice.LineItem` when the fully qualified name is needed.

### 1.2. Binary name

According to Java's binary naming rules, a binary name is the class name used in binary structures and many reflection/class loading APIs. For a top-level class in a package, the binary name is usually the same as the fully qualified name in source:

~~~text
com.example.billing.Invoice
~~~

For a member class, the dot separating the outer class and the member class is represented by `$` in the binary name:

~~~text
com.example.billing.Invoice$LineItem
~~~

The names of local classes and anonymous classes also have an encoded form based on the enclosing class and may contain numbers generated by the compiler. These internal names should not be treated as a stable API for other applications to construct via string concatenation or store long-term.

A binary name does not include the `.class` extension and is not a file path. It is a logical name used to identify a type within a class loader space.

### 1.3. Internal name in class files

In a class file's constant pool, class names are typically represented in internal name form, using `/` to separate packages:

~~~text
com/example/billing/Invoice
com/example/billing/Invoice$LineItem
~~~

You can visualize the difference:

| Form | Example |
|---|---|
| Fully qualified source name | `com.example.billing.Invoice.LineItem` |
| Binary name | `com.example.billing.Invoice$LineItem` |
| Internal name | `com/example/billing/Invoice$LineItem` |
| Common class file | `com/example/billing/Invoice$LineItem.class` |

A JAR file path usually corresponds to the internal name plus `.class`, but that is just how artifacts are stored. A class loader can obtain bytecode from a JAR, directory, network, or custom source; not every class has to exist as a file on the filesystem.

### 1.4. Field and method descriptors

A descriptor describes a data type in JVM form. It differs from a binary name because it represents the type of a field or a method signature.

Some basic descriptors:

| Java type | JVM descriptor |
|---|---|
| `boolean` | `Z` |
| `byte` | `B` |
| `char` | `C` |
| `short` | `S` |
| `int` | `I` |
| `long` | `J` |
| `float` | `F` |
| `double` | `D` |
| `void` | `V` |
| `String` | `Ljava/lang/String;` |
| `Invoice` | `Lcom/example/billing/Invoice;` |
| `String[]` | `[Ljava/lang/String;` |
| `int[][]` | `[[I` |

A method descriptor places the parameter types inside parentheses, followed by the return type. For example:

~~~text
(Ljava/lang/String;I)Ljava/math/BigDecimal;
~~~

The descriptor above describes a method that takes `String` and `int` and returns `BigDecimal`. The return type is also part of the JVM descriptor, even though Java source does not allow overloading that differs only by return type.

Descriptors have direct significance during method/field resolution. If a library changes a return type, parameter type, or field type, the reference compiled into the consumer may no longer match the member in the new version.

## 2. How do class files store symbolic references?

After compilation, a class file has a structure consisting of a header, version, access flags, class/interface information, fields, methods, and a **constant pool**. The constant pool contains the constants and references used by bytecode.

A symbolic reference is not necessarily a memory address of a class or method. It describes the target object to locate using a name and descriptor. The JVM resolves that reference in the runtime environment, where class loaders, modules, and already loaded classes determine the result.

### 2.1. Related constant pool entry types

Some important entry types in a class file include:

- `CONSTANT_Class`: reference to a class/interface or array type.
- `CONSTANT_Fieldref`: reference to a field of a class.
- `CONSTANT_Methodref`: reference to a method of a class.
- `CONSTANT_InterfaceMethodref`: reference to a method of an interface.
- `CONSTANT_NameAndType`: pairs a member name with a descriptor.
- `CONSTANT_MethodHandle`: represents a method handle pointing to a field or method reference.
- `CONSTANT_MethodType`: stores a method descriptor for method handles/dynamic invocation.
- `CONSTANT_InvokeDynamic`: links a dynamic call through a bootstrap method.
- `CONSTANT_Dynamic`: represents a dynamically linked constant through a bootstrap method.

These entries link to one another. For example, a `CONSTANT_Methodref` identifies the class owning the method and a `NameAndType` containing the name and descriptor of that method.

### 2.2. Symbolic reference example

Suppose a library provides:

~~~java
package com.example.payment;

public class PaymentClient {
    public String status(String paymentId) {
        return "PENDING";
    }
}
~~~

A consumer calls the method:

~~~java
PaymentClient client = new PaymentClient();
String value = client.status("P-100");
~~~

The consumer bytecode needs to reference the class `com.example.payment.PaymentClient` and the method `status` with a descriptor taking one `String` and returning `String`:

~~~text
com/example/payment/PaymentClient
status
(Ljava/lang/String;)Ljava/lang/String;
~~~

When the consumer runs with a new JAR, the JVM needs to find the class with the matching name and the method with the matching descriptor in the appropriate class hierarchy. If the new JAR only has a `status(String)` method returning `Optional<String>`, the descriptor has changed and the old reference is no longer satisfied. The old consumer may encounter `NoSuchMethodError` when the JVM resolves or executes that call.

### 2.3. A symbolic reference is not just a standalone method name

The name `status` is not enough to identify a method. The same class can have multiple overloads:

~~~java
public String status(String id) { ... }
public String status(long id) { ... }
~~~

The two methods have the same name but different descriptors. Similarly, a field reference requires the owning class, the field name, and the field type descriptor. Therefore, simply searching for a method name in source code or `javap` is not sufficient; you need to inspect the descriptor and owner class.

## 3. Where does bytecode use symbolic references?

Bytecode contains instructions that reference the constant pool. Common instruction groups include:

| Instruction group | Example | Reference used |
|---|---|---|
| Object creation | `new` | Class reference |
| Instance method invocation | `invokevirtual` | Method reference |
| Interface method invocation | `invokeinterface` | Interface method reference |
| Static method invocation | `invokestatic` | Method reference |
| Constructor/private/super method invocation | `invokespecial` | Method reference |
| Read/write static field | `getstatic`, `putstatic` | Field reference |
| Read/write instance field | `getfield`, `putfield` | Field reference |
| Dynamic invocation | `invokedynamic` | InvokeDynamic entry and bootstrap method |

With `invokedynamic`, the JVM uses a bootstrap method to link the call site. Lambda expressions and certain language/library mechanisms can use this instruction. Consequently, modern class file analysis cannot just search for `invokevirtual` and `invokestatic`.

References to classes/interfaces also appear in superclass declarations, interfaces, field types, method descriptors, exception tables, annotations, and other attributes. A type change can affect many places rather than just explicit method calls in source code.

## 4. The loading, linking, and initialization process

The JVM does not simply read a `.class` file and run it immediately. The class lifecycle consists of interrelated phases: loading, linking, and initialization. Linking is typically divided into verification, preparation, and resolution.

~~~text
             Class bytes / binary representation
                         |
                         v
                      Loading
                         |
                         v
                       Linking
             +-----------+-----------+
             |           |           |
             v           v           v
         Verification Preparation Resolution
             |           |           |
             +-----------+-----------+
                         |
                         v
                  Initialization
                         |
                         v
                    Execution
~~~

The diagram illustrates conceptual relationships. In practice, the JVM may defer some resolution steps until a reference is used; not every symbolic reference is necessarily resolved as soon as the class is loaded.

### 4.1. Loading

Loading is the process of finding the binary representation of a class/interface by binary name and creating the corresponding `Class` object in the JVM.

A class loader can obtain bytecode from:

- Class output directory.
- JAR or module.
- Classpath/module path.
- Network or custom source.
- Byte array defined through a custom class loader.

Common platform loaders are the bootstrap class loader, platform class loader, and application class loader. Applications may also have custom class loaders, plugin loaders, or framework-created loaders.

The delegation model typically allows a loader to ask its parent before searching for a class itself, though not every loader follows the same policy. When investigating errors, it is necessary to know which loader actually defines the class.

### 4.2. Class identity and class loaders

A very important point: **the identity of a class at runtime is determined by its binary name and defining class loader**. Two classes with the same binary name defined by two different loaders can be two incompatible types.

For example, two plugins both package `com.example.api.Message` in separate class loaders. Even though the class name is identical, an object from plugin A may fail to cast to the `Message` type defined by plugin B. The error may appear as a `ClassCastException` with a message stating that two classes have the same name but belong to different loaders.

A runtime package is also tied to the defining loader. Therefore, having the same package name does not automatically guarantee that two classes belong to the same runtime package or have package-private access to each other.

When surveying a migration, check custom class loaders, plugin isolation, application servers, OSGi, or hot reload frameworks if the system uses those mechanisms.

### 4.3. Verification

Verification checks whether the class file has a valid structure and whether bytecode complies with the JVM's safety constraints. This process helps detect corrupted class files, invalid operand stack/local variables, mismatched data types, or bytecode control flow that violates rules.

A related error can be `VerifyError`. This error can appear when a class is generated by a bytecode generator, enhancer, agent, or compiler that does not produce bytecode compliant with the new JVM's verifier.

If the application uses ASM, Byte Buddy, Javassist, CGLIB, or instrumentation tools, check their versions and JDK support matrices. These tools can generate or transform class files, so they need to keep up with new class file versions and verifier rules.

### 4.4. Preparation

Preparation creates `static` fields and initializes them to default values according to their data types. Constant variables with a `ConstantValue` attribute are handled according to JVM rules during this phase.

Do not confuse preparation with running static initialization statements in source code. Normal expressions and static initializers are executed during the initialization phase via the special `<clinit>` method if the class has content that requires initialization.

### 4.5. Resolution

Resolution converts symbolic references in the constant pool into runtime references to the corresponding class/interface, field, method, or method handle. This is the phase directly associated with many binary compatibility errors.

For example, when bytecode requests `PaymentClient.status(String):String`, the JVM needs to:

1. Find the class/interface specified in the reference.
2. Find the member with the matching name and descriptor according to JVM lookup rules.
3. Check access permissions and related conditions.
4. Confirm that the usage matches the member kind and instruction.

If the member is not found, is inaccessible, or the class structure does not match the instruction, the JVM can throw a linkage error. Resolution can be performed eagerly or lazily; therefore, an application may start up successfully and only fail when a rare code path is executed.

### 4.6. Initialization

Initialization executes static field initializers and static initializers in `<clinit>`. It occurs when a class is used under initialization-triggering conditions defined by the JVM, such as creating an instance, calling a static method, or accessing a static field that is not a constant variable.

If initialization fails, the first attempt may receive `ExceptionInInitializerError` when the cause is an exception in the initializer; subsequent uses may receive `NoClassDefFoundError` because the class is already in an initialization error state. Therefore, `NoClassDefFoundError` does not always mean a JAR file is missing; you need to check the first cause in the stack trace.

## 5. Class, field, and method resolution

Different symbolic references have their own resolution rules. Understanding the general idea helps read errors and compare binaries between two releases.

### 5.1. Class/interface resolution

The JVM searches for a class/interface by binary name in the loader context determined by the class containing the symbolic reference and loading rules. The result must satisfy constraints on kind, access permissions, and related modules.

If a class cannot be found during loading required by a symbolic reference, `NoClassDefFoundError` can be thrown. If the application calls reflection APIs such as `Class.forName` or `ClassLoader.loadClass` and the requested name is not found, that API can throw `ClassNotFoundException`. The two errors are related but occur in different mechanisms and contexts.

### 5.2. Field resolution

A field reference specifies the owning class/interface, field name, and descriptor. The JVM searches for the field according to lookup rules in the class and related superclasses/interfaces.

Common errors:

- `NoSuchFieldError`: the referenced field no longer exists with the required name/descriptor.
- `IllegalAccessError`: the field exists, but bytecode lacks access permission under runtime rules.
- `IncompatibleClassChangeError`: the field usage is no longer compatible with the class structure, for example expecting static when the actual member is no longer static.

Changing a field from `public` to `private`, changing its type, or changing static/instance can break compiled consumers.

### 5.3. Method resolution

A method reference contains the owner type, method name, and descriptor. The JVM applies lookup rules corresponding to a class method or interface method. After resolution succeeds, the method invocation instruction may also select an implementation based on the receiver or invocation kind.

Common errors:

- `NoSuchMethodError`: no method is found with the referenced name and descriptor.
- `IllegalAccessError`: the method exists but is inaccessible.
- `AbstractMethodError`: the call requires an implementation, but the runtime object does not provide a suitable implementation.
- `IncompatibleClassChangeError`: class/interface or static/instance assumptions no longer match the bytecode.
- `BootstrapMethodError`: the bootstrap method of `invokedynamic` or a dynamic constant fails during linking.

For example, if a library changes a method from instance to static while the old consumer still contains `invokevirtual`, the runtime structure no longer matches the compiled instruction. Similarly, changing an interface hierarchy can affect method dispatch even when the method name still exists.

## 6. Connection to binary compatibility when upgrading dependencies

Binary compatibility answers whether bytecode compiled against an old version can link with a new version without recompilation. Because a symbolic reference contains owner, name, and descriptor, changing these components can break linking.

Suppose version 1 of a library has:

~~~java
package com.example.customer;

public class CustomerClient {
    public Customer find(String id) {
        return null;
    }
}
~~~

The consumer is compiled with the method descriptor:

~~~text
find(Ljava/lang/String;)Lcom/example/customer/Customer;
~~~

Version 2 changes the return type:

~~~java
public Optional<Customer> find(String id) {
    return Optional.empty();
}
~~~

In Java source, two methods differing only by return type cannot be declared simultaneously. In bytecode, the return type is part of the method descriptor, so the descriptor of the new version differs from the descriptor referenced by the old consumer. When the old consumer runs with the new JAR, the JVM may fail to find the old method and throw `NoSuchMethodError`.

One migration approach is to keep the old method and add a new method with a different name, such as `findOptional`, or keep the old API during a deprecation period. Which option to choose depends on the contract and semantics; you should not simply change the return type and expect the JVM to convert it automatically.

Other changes also need to be considered:

- Changing package/class names changes the binary name.
- Renaming a nested class can change the binary name containing `$`.
- Removing a constructor leaves the `<init>` reference unsatisfied.
- Changing a field type causes a descriptor mismatch.
- Replacing a class with an interface or vice versa changes resolution/invocation behavior.
- Changing access modifiers can cause consumers to lose access rights.
- Changing the hierarchy can alter lookup and dispatch.

## 7. Inspecting binary names and symbolic references with tools

`javap` is the basic tool for viewing class files and bytecode. Commonly used options:

~~~bash
javap -classpath path/to/library.jar -p com.example.payment.PaymentClient
javap -classpath path/to/library.jar -v -c -s com.example.payment.PaymentClient
~~~

- `-p` displays members including non-public access levels.
- `-v` displays detailed information such as the constant pool and attributes.
- `-c` displays bytecode instructions.
- `-s` displays internal type signatures/descriptors.

In verbose output, you can see `CONSTANT_Class`, `CONSTANT_Methodref`, `CONSTANT_Fieldref`, `NameAndType`, and descriptors. This is direct evidence for comparing which API a compiled consumer references.

You can inspect the contents of a JAR using:

~~~bash
jar tf path/to/library.jar
~~~

This command lists entries in the JAR. Comparing the class list between two releases helps find added/removed classes, but does not detect signature changes inside a class. Therefore, it must be combined with `javap` or an API comparison tool such as japicmp/Revapi.

To find class-level dependencies of an application, you can use:

~~~bash
jdeps -verbose:class path/to/application.jar
~~~

The output helps identify which packages/classes the application's classes depend on. This is not a complete report of all dynamic calls or reflection; it should be combined with source search, runtime traces, and tests.

## 8. Investigating runtime linking errors

When an application encounters a linkage error after replacing a JAR or JDK, look for the root cause first instead of only handling the last logged exception.

Investigation process:

1. Record the full exception/error, and the first class and method where the error occurred.
2. Identify which dependency version the consumer class was compiled against.
3. Identify which JAR/class is actually loaded by the JVM at runtime.
4. Use `javap -v -c -s` to inspect symbolic references in the consumer.
5. Use `javap` on the runtime provider to inspect existing classes/members and descriptors.
6. Check class loaders, module path, dependency conflicts, and classpath order.
7. Reproduce with the exact old/new artifacts and a minimal test.
8. Choose a fix: maintain a compatible API, upgrade the consumer, adjust dependency resolution, or split contract versions.

On JDKs supporting unified logging, you can enable class loading logs to identify class sources:

~~~bash
java -Xlog:class+load=info -jar application.jar
~~~

For older JDKs that do not support unified logging, you can use `-verbose:class` according to that runtime's documentation. Class loading logs can be quite large; filter by relevant classes and avoid leaving them enabled for long periods in production without evaluating log volume.

A diagnostic snippet in code can also print the class loader and code source:

~~~java
Class<?> type = PaymentClient.class;

System.out.println("name=" + type.getName());
System.out.println("loader=" + type.getClassLoader());
System.out.println("module=" + type.getModule());
System.out.println("source=" + type.getProtectionDomain()
        .getCodeSource());
~~~

This is an example for diagnostics in an appropriate environment. Code source may be `null` depending on how the class is defined; do not treat it as information that is always available.

## 9. Class loaders and errors that appear to be duplicate names

Class identity at runtime is tied to the binary name and defining class loader. If two plugins or two sub-applications both load a class named `com.example.api.Message` from two different loaders, the JVM may treat them as two separate types.

This commonly appears in:

- Application servers with separate class loaders per deployment.
- Plugin architectures and extension systems.
- OSGi or module containers.
- Hot reload/devtools frameworks.
- Applications packaging duplicate dependencies across multiple modules/plugins.

A typical scenario is a method expecting a `Message` defined by loader A while the caller passes a `Message` object defined by loader B. A `ClassCastException`, loader constraint violation, or other linkage error can occur. Checking only the class name in the JAR is not enough; you need to inspect the defining loader and actual class source.

When designing modules/plugins, clearly determine which classes are shared through a parent loader, which classes are isolated, and which dependencies are packaged only once. Conflicts should not be resolved by randomly removing JARs from the classpath without understanding API ownership.

## 10. Checklist for checking binary names and linking during migration

- [ ] Identified the binary name and internal name of the relevant classes.
- [ ] Distinguished binary names from method/field descriptors.
- [ ] Identified symbolic references in the consumer's constant pool.
- [ ] Checked classes, fields, methods, constructors, and hierarchy in the new provider.
- [ ] Reviewed the corresponding invocation/read/write instructions.
- [ ] Distinguished loading, verification, preparation, resolution, and initialization.
- [ ] Checked class loaders, modules, and actual JAR sources.
- [ ] Reviewed `NoClassDefFoundError`, `NoSuchMethodError`, `NoSuchFieldError`, `IllegalAccessError`, `AbstractMethodError`, and related linkage errors.
- [ ] Tested old binaries running against new dependencies when required.
- [ ] Tested recompiling consumer source against the new API.
- [ ] Combined API diffs with integration tests and behavioral testing.
- [ ] Recorded baseline artifacts, runtime classpath, and investigation evidence.

## 11. Conclusion

A binary name identifies a class at the binary level; a descriptor specifies the type of a field or a method signature; a symbolic reference in the constant pool connects bytecode with the classes and members it needs. The JVM loads classes via class loaders, performs linking consisting of verification, preparation, and resolution, and then performs initialization before the class is used under the corresponding conditions.

During a library or JDK migration, changing a binary name, descriptor, access level, class hierarchy, or class loader can prevent compiled references from linking. Using `javap`, `jar`, `jdeps`, class loading logs, and testing old consumers helps pinpoint the source of errors. Combining this evidence with API comparison and runtime tests helps evaluate binary compatibility on a solid basis instead of relying solely on whether source code still compiles.
