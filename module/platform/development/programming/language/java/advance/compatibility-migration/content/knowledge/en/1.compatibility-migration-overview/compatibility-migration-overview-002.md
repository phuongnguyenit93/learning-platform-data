# Why Upgrading the JDK Can Affect a Running Application

Upgrading the JDK can change how an application is compiled, started, and executed, even when the application's source code does not change. The JDK is not only a tool used to run the `javac` command; it also provides the Java Virtual Machine (JVM), the standard library, bundled tools, and many default configurations that directly affect the runtime environment.

Therefore, an application that previously worked stably on an older JDK may not behave identically when moved to a newer JDK. The application may fail to start, be missing classes or libraries, encounter security errors, process data differently than before, or experience changes in performance. To upgrade safely, it is necessary to understand which parts of the Java platform can change and test them layer by layer.

## 1. The JDK Is Part of the Application Execution Environment

A Java application is typically developed from source code, compiled into bytecode, and then run on the JVM. When deployed, a JAR or WAR file usually does not include the JVM; the server, container, or operating environment provides an appropriate JDK/JRE to run the application.

```text
Java source code
     |
     v
javac compiler
     |
     v
Bytecode (.class) + application libraries
     |
     v
JVM + JDK standard library
     |
     v
Operating system / container / hardware
```

The JDK (Java Development Kit) is the development toolkit. It includes the compiler, the JVM, and the standard libraries needed to develop, test, and run programs. Depending on the packaging and Java version, the deployment environment may be called a JRE or use a JDK distribution directly. Regardless of the name, the application still depends on the JVM and the libraries present in the execution environment.

This creates two points in time to distinguish:

- **Build time:** source code is compiled using a JDK. The compiler version, the APIs visible to the compiler, and the build configuration determine the generated bytecode.
- **Runtime:** bytecode is loaded and executed by the JVM along with the libraries of the JDK installed on the machine running the application. The runtime version determines much of the actual behavior.

These two points in time may use different JDKs. For example, the development team compiles the application on a newer JDK while the server still runs an older JDK; or an application was built long ago but is now redeployed on a newer runtime. In both cases, compatibility issues can arise.

## 2. Compatibility Does Not Only Mean Compiling Successfully

When evaluating a JDK upgrade, multiple types of compatibility must be considered. An application that passes one type of check may not pass the remaining ones.

| Compatibility type | Question to answer | Example of incompatibility |
|---|---|---|
| Source compatibility | Can the current source code be compiled with the new compiler? | An API is no longer provided, causing the compiler to report that the package or class cannot be found. |
| Binary compatibility | Can the compiled `.class` files or JARs be successfully loaded and linked by the JVM? | An older JVM cannot read bytecode with a newer class file version; or a class/method needed by the application is missing. |
| Behavioral compatibility | At runtime, does the program preserve the expected results and processing rules? | Text encoding, security algorithm selection, or time zone data changes. |
| Operational compatibility | Does the application start up, support monitoring, open connections, and handle load as before? | The JVM rejects an old startup option, or memory usage or latency changes. |

For example, the source code may compile successfully because the required libraries have been added to the classpath. However, when running on the server, a different version of a library may be loaded first, leading to a `NoSuchMethodError`. Similarly, an application may start normally and only fail when handling a certain type of TLS certificate, reading a file with non-ASCII characters, or loading a class via reflection.

Therefore, the right question is not only “Can the application compile on the new JDK?”, but also “Can the application start up, execute all business flows completely, and operate stably in the new environment?”.

## 3. Changes in the JDK That Can Impact Applications

### 3.1. The Standard Library and APIs Can Change

The JDK provides many packages that applications can use directly. Across versions, APIs can be added, marked deprecated, changed, or removed. Some modules that used to be bundled with the JDK can also be separated out from the standard JDK.

A notable example is the Java EE and CORBA modules, which were removed from the JDK starting in Java 11. Older applications that used to rely on APIs such as JAXB without declaring separate dependencies may encounter compilation errors such as `package javax.xml.bind does not exist`, or runtime errors such as `ClassNotFoundException` when changing environments.

The reason is that previously the application inadvertently relied on a library provided out of the box by the JDK. When that library is no longer included in the JDK, the dependency must be explicitly declared in the build system and packaged with the application.

Another change is the class file version. A newer compiler can generate bytecode for a newer Java version. An older JVM does not understand that class file format and may report `UnsupportedClassVersionError`.

```text
Newer compiler
     |
     v
Newer version bytecode
     |
     v
Older JVM does not support the class file version
     |
     v
UnsupportedClassVersionError
```

Normally, bytecode generated for an older Java version can run on a newer JVM, provided that the APIs and dependencies used by the program still exist and remain compatible. The reverse direction is not guaranteed: an older JVM cannot run bytecode that requires a newer class file format.

### 3.2. The Module System and Reflection Access Can Be Stricter

Some older libraries and frameworks use reflection to access non-public fields, methods, or constructors. In some cases, they also access internal JDK classes, such as packages whose names begin with `sun.` or `com.sun.`.

These internal APIs are not a stable public contract. As the Java platform strengthens its module mechanism and internal encapsulation, deep access to those classes may trigger warnings or be blocked. Applications may encounter `IllegalAccessException`, `InaccessibleObjectException`, or related errors when a library attempts to open access via reflection.

For example, an older framework might attempt to access a private field inside a JDK class. In the old environment, that operation might succeed because the encapsulation rules still permitted it. In the new environment, the same code may be rejected because the module owning the class does not open that package to the calling module.

The resolution approach should follow this order:

1. Identify which library or code is performing internal access.
2. Upgrade the library to a version that supports the target JDK.
3. If the code is owned by the application, replace the internal API with a supported public API.
4. Only use a module-opening option like `--add-opens` when the scope is clearly understood and treat it as a controlled transitional measure.

Adding `--add-opens` can help an older application continue running in some situations, but it does not turn an internal API into an API guaranteed to be stable. If this dependency remains, the next JDK upgrade may still run into issues.

### 3.3. The JVM, Garbage Collector, and JIT Compiler Can Change Operational Behavior

The JVM is responsible for loading classes, managing memory, performing garbage collection, compiling hot code with the JIT, and executing bytecode. These components are improved across JDK versions.

These changes can bring better performance, but can also alter:

- The timing and duration of garbage collection cycles.
- The usage of heap, native memory, metaspace, or the number of threads.
- Startup time and JIT warm-up time.
- Latency at the average or at high percentiles such as p95 and p99.
- How the JVM reacts when memory is nearly exhausted or when the application is under heavy load.

For example, an application might run stably with heap and garbage collector settings tuned for an older JDK. After upgrading, the default GC algorithm or its implementation has changed; the same old configuration may produce a different garbage collection cadence and increase latency during peak hours.

That does not mean a newer JDK is always slower. Performance depends on the application, data, load, hardware, and configuration. Therefore, one should not draw conclusions based solely on small benchmark results or startup time. Measurements should be taken under representative load while observing throughput, latency, memory, and GC activity.

### 3.4. JVM Options and Logging May No Longer Be the Same as Before

Applications are often started with options such as `-Xms`, `-Xmx`, garbage collector configurations, system properties, or feature toggle flags. Across versions, some options may be deprecated, replaced, or removed.

If a deployment script still passes a flag that is no longer supported by the JVM, the application may terminate immediately on startup with a message like `Unrecognized VM option`. Some options that previously took effect may now have a different meaning or no longer be the recommended way to configure.

The JVM logging mechanism also changes over time. For instance, newer Java versions introduced the unified logging system with the `-Xlog` syntax. Log collection scripts based on old GC logging flags need to be checked and adjusted when switching versions.

Therefore, upgrading the JDK requires reviewing the actual startup command, container configuration files, environment variables, and process management scripts, not just inspecting the JAR file.

### 3.5. Security Configuration and Network Connections Can Be Stricter

The JDK provides security components such as JSSE, JCA, cryptographic algorithm lists, trusted certificate stores, and providers. These components are updated to remove weak algorithms, fix vulnerabilities, and comply with new security requirements.

A connection that previously succeeded may fail after a JDK upgrade if the peer server only supports a protocol or cipher suite that has been disabled, the certificate is no longer accepted, the certificate chain lacks a trusted CA, or the new security configuration rejects an old algorithm.

For example, an application connects to a legacy internal service that only supports a weak TLS configuration. The new runtime refuses to negotiate the connection; the error appears as an `SSLHandshakeException`. Looking at the business code, the HTTP call has not changed, but the runtime's security policy has changed.

When investigating, both sides of the connection must be checked: the JDK version, truststore, certificates, protocols, and cipher suites supported by the client, along with the TLS configuration of the target service. You should not resolve this by re-enabling a weak algorithm in production without assessing the risk and having a replacement plan.

### 3.6. Charset, Locale, and Time Zone Data Can Affect Processing Results

Applications may depend on environment defaults such as charset, locale, or timezone. When these defaults or the data bundled with the JDK change, the same piece of code can produce different results.

A concrete example is the default charset. Starting in Java 18, UTF-8 became the default charset under JEP 400 in standard environments, whereas earlier versions typically obtained the default charset from the environment. Legacy applications that rely on the default charset to read or write files may produce different data when switching JDKs, especially if the files were created with an encoding other than UTF-8.

Source code prone to depending on defaults:

```java
// Depends on the environment's default charset
String content = new String(bytes);
```

If the file format is specified as UTF-8, the encoding should be explicitly stated:

```java
import java.nio.charset.StandardCharsets;

String content = new String(bytes, StandardCharsets.UTF_8);
```

Similarly, if business logic needs to handle time in a specific time zone, use an explicit `ZoneId` instead of relying on the default timezone of the host machine. Timezone and locale data are also updated to reflect world changes; this can affect how dates and times are parsed, as well as the formatting of numbers, currencies, or month names.

### 3.7. Dependencies, Frameworks, Agents, and Native Libraries May Not Yet Support the New JDK

Applications rarely use only the standard library. Frameworks, ORMs, JSON libraries, bytecode libraries, testing tools, Java agents, and native libraries can all depend on JDK details.

Some libraries generate or transform bytecode and therefore need to be updated to understand newer class file versions. Some frameworks use reflection or access internal APIs. Java agents can intervene in the class loading process. JNI/JNA libraries also depend on the ABI, CPU architecture, and operating system libraries.

Therefore, an application may compile yet still fail at startup because a framework does not support the new runtime, or fail only in a specific execution flow because an agent cannot handle the new class files. Indirect dependencies must also be examined; not every library appears directly in the application's build file.

Before upgrading, check the supported versions of critical frameworks and libraries against the target JDK. If a dependency is no longer maintained or only supports older JDKs, an upgrade or replacement plan must be identified before deployment.

### 3.8. Operating System, Container, and Hardware Architecture Are Also Part of Compatibility

The JDK runs on a specific environment. The JDK distribution, operating system, CPU architecture, native libraries, container image, and resource settings can all affect the outcome.

A JDK upgrade is often accompanied by changing the container base image or upgrading the operating system. If the application uses native libraries, changes in libc, CPU architecture, or system library versions can prevent those libraries from loading. Container CPU and memory limits can also cause the JVM to detect resources differently from the previous virtual machine or server.

When comparing two environments, it is necessary to record in full the JDK version as well as the vendor/distribution, operating system, architecture, container image, and resource limits. Simply noting “Java 21” is not enough to describe the entire runtime environment.

## 4. Some Illustrative Scenarios

### Scenario A: The Application Loses an API Previously Available in the JDK

A legacy application uses JAXB to convert XML without declaring a separate JAXB dependency because the previous JDK environment provided the relevant modules out of the box. When moving to JDK 11 or later, the build may report that the package cannot be found, or the runtime may report missing classes.

Key point: the source code is not necessarily wrong. The application was relying on a component provided indirectly by the older JDK. The way to handle this is to declare the corresponding dependency, choose a compatible version, and package it with the application.

### Scenario B: An Older Framework Can No Longer Access Internal Classes

The application started with an older JDK. A framework uses reflection to open a private field inside a JDK class. After upgrading, the application encounters `InaccessibleObjectException` when the framework performs that operation.

Key point: module encapsulation rules have become stricter. You need to identify the framework performing the access, check for a version supporting the target JDK, and upgrade it. The `--add-opens` option should only be used when there is a clear reason and a plan to remove the dependency.

### Scenario C: File Content Changes After Upgrading

The application reads a CSV file using `new String(bytes)` and then parses the data. The file was created by a system using an encoding other than UTF-8. When the runtime environment changes the default charset, accented characters may become incorrect or the data may no longer be parsed as expected.

Key point: the program relied on a default that was not explicitly specified in the data contract. The file encoding must be defined and the charset explicitly specified in the source code.

### Scenario D: The Application Fails to Start Because of an Old JVM Flag

The deployment pipeline still passes a GC option previously used on the older JDK. The newer JDK no longer recognizes that option, and the JVM exits before loading the application classes.

Key point: operational configuration is part of the application. The startup command must be inspected and the old flag replaced with a configuration supported on the target JDK, followed by re-verifying GC behavior and logging.

## 5. Why Can an Application Running Stably Still Be Affected?

A running application has usually been validated in a specific combination: JDK version, dependencies, JVM configuration, operating system, certificates, data, and actual load. When one component in that combination changes, the assumptions the application relies on may no longer hold.

Some common causes:

1. **The runtime changes while the bytecode stays the same.** The old JAR file is run on a new JVM, so the behavior of the standard library, security, GC, or JIT may differ.
2. **The application is rebuilt with a new compiler.** The bytecode, APIs used, or resolved dependencies may differ from the previous build.
3. **The deployment environment changes at the same time.** The container image, operating system, environment variables, timezone, truststore, or resource limits are updated.
4. **Errors only appear in a rarely used branch.** A reflection operation, a TLS connection to an uncommon partner, or a file with a special encoding might not show up during startup checks.
5. **Performance differences only surface under load.** An application that runs well in small tests can still experience latency, GC pauses, or memory pressure when request volume increases.

For continuously running systems, the impact often appears when processes are restarted with the new runtime, when a new instance is added to the cluster, or when a rolling update leaves instances temporarily running on different JDK versions. If behavior differs across instances, the same request may succeed on one instance but fail on another.

## 6. How to Assess Impact Before Upgrading

You should not start by replacing the JDK in production and waiting to see whether errors occur. Identify the current environment, select the target JDK, and inspect each layer of dependencies.

### Step 1: Record the Currently Running Environment

Collect at least the following information:

- JDK/JVM version, vendor, and distribution used at build time and runtime.
- Actual startup command, JVM arguments, system properties, and environment variables.
- Operating system, CPU architecture, container image, and CPU/memory limits.
- Framework versions, direct dependencies, and transitive dependencies.
- Native libraries, Java agents, monitoring tools, and profiling tools.
- External connections, truststores, certificates, and security protocols.
- File formats, encodings, locales, and timezones used by the business logic.

Information should be gathered from the actual running environment, because the configuration on a developer machine may differ from the production configuration.

### Step 2: Determine the Scope of Changes in the Target JDK

Read the release notes and migration guides for the versions between the current JDK and the target JDK. Focus on:

- APIs or modules that were removed, replaced, or changed.
- Changes to the module system, reflection, and internal API access.
- Changes to JVM flags, garbage collectors, logging, and memory management.
- Changes to TLS, cryptographic algorithms, certificates, and providers.
- Changes to default charset, locale, timezone, and the standard library.
- Minimum JDK requirements of frameworks, plugins, agents, and dependencies.

If upgrading across multiple major versions, you must review the cumulative changes across each intermediate version, not only the release notes of the target version.

### Step 3: Check Dependencies and Internal APIs

Review both direct and transitive dependencies, then upgrade any libraries that do not yet support the target JDK. Tools such as `jdeps` can help detect dependencies and references to internal JDK APIs; `jdeprscan` can help locate usage of deprecated APIs. Tool output is input for investigation and does not replace runtime testing: dynamic reflection, classes loaded by configuration, and interactions with external systems may not be fully detected through static analysis.

If a project builds with a newer JDK but needs to maintain the ability to run on a lower Java version, the `--release` option can be used to constrain the language level, bytecode, and standard API to the target version supported by the compiler:

```bash
javac --release 17 -d out src/com/example/App.java
```

The example above instructs the compiler to produce output compatible with Java 17. It does not guarantee that all external dependencies, runtime configuration, or application behavior are compatible; those parts still need to be tested separately.

### Step 4: Test on the Exact Target JDK and Environment

Create a test environment as close to production as possible, including the same image type, JVM configuration, dependencies, and resource limits. Run at least the following test groups:

| Test group | What to verify |
|---|---|
| Build | Source code compiles; dependencies are resolved and packaged properly. |
| Startup | The JVM accepts all flags; the application loads classes, configurations, and beans successfully. |
| Integration | Databases, message brokers, HTTP clients, TLS, and external services connect properly. |
| Business logic | Main flows and edge cases produce correct results. |
| Data | Files, encodings, dates and times, locales, and serialization are handled properly. |
| Security | Certificates, TLS, algorithms, and authentication operate according to the new policy. |
| Performance | Throughput, latency, memory, threads, and GC meet targets. |
| Operations | Logs, metrics, tracing, health checks, shutdown, and restart work normally. |

Do not only test success paths. Error cases, timeouts, high load, large data, and rarely used yet critical connections must also be tested.

### Step 5: Deploy in a Controlled Manner and Observe

After testing meets requirements, perform a trial deployment on staging or a small group of instances. Monitor startup logs, exceptions, connection errors, failed request rate, p95/p99 latency, heap/native memory usage, and GC activity.

If using rolling deployment, know which JDK versions are serving requests concurrently during the transition window. Verify protocol and data compatibility between instances during this phase.

Prepare the previous version's image or artifact, corresponding configuration, and rollback procedure in advance. If errors exceed the threshold, you can revert to an environment known to be stable while continuing investigation. Only conclude the migration when all instances are running the target version and operational metrics remain stable over an appropriate observation window.

## 7. Distinguishing Between Patch Updates and Major Version Upgrades

Not every JDK upgrade carries the same level of change.

- **Patch update:** usually focuses on bug fixes and security fixes within the same release line. Although the scope of change is usually narrower, a patch can still update the list of disabled algorithms, trusted certificates, or fix behavior relevant to the application.
- **Major release:** can add APIs, change the JVM, update defaults, remove old APIs/modules, and change requirements for tools or dependencies. It requires broader evaluation and thorough migration testing.
- **Changing vendor or distribution:** even when carrying the same Java version number, distributions may differ in packaging, bundled components, patches, and platform support. You need to test the exact distribution that will be used in production.

Therefore, “only upgrading a patch” does not mean there is no risk. The level of testing can be adjusted to match the scope of changes, but critical functionalities and security requirements must still be verified.

## 8. Assumptions That Easily Lead to an Unsafe Migration

| Assumption | Why it is insufficient | Appropriate way to evaluate |
|---|---|---|
| “The source code compiles, so the application is compatible.” | Compilation does not fully verify runtime, reflection, TLS, data, and performance. | Verify build, startup, integration, business logic, and operations. |
| “A new JDK can always run all old applications.” | APIs/modules may be removed; internal access may be blocked; defaults may change. | Cross-check migration guides, dependencies, and test on the target JDK. |
| “If source code is not modified, behavior will stay the same.” | The runtime, standard library, security, data, and environment have changed. | Compare results and metrics of the same application across both environments. |
| “The application starting successfully is enough.” | Errors may only appear in a specific business branch, connection, or load. | Test representative flows, edge cases, and realistic load. |
| “If the Java version number is the same, all JDKs are identical.” | Vendor, distribution, operating system, and packaged components may differ. | Record and test the exact JDK to be deployed. |

## 9. Conclusion

Upgrading the JDK means changing the application's execution platform. Impacts can come from the compiler, bytecode, JVM, standard library, module system, security, default values, dependencies, or the operating system environment. Because these layers are interconnected, an application can still encounter errors or behavioral changes after upgrading without any changes to its source code.

A safe migration begins by accurately recording the current environment, identifying changes from the target JDK, checking dependencies and configuration, and then running tests in a production-like environment. Finally, roll out in stages, observe operational metrics, and keep a rollback plan ready. This approach helps turn a JDK upgrade from a change based on many assumptions into a change with clear scope, evidence, and controllability.
