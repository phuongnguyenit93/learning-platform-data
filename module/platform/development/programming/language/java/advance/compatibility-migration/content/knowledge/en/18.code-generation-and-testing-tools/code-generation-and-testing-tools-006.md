# JaCoCo, static analysis tools, and supported class-file versions

In **Java Advance Compatibility Migration**, upgrading the JDK often leads development teams to focus on compilation errors and application runtime errors. However, another critical layer of compatibility lies in **tools that read, analyze, or transform class files**. An application may compile successfully with the new JDK, yet JaCoCo fails to instrument bytecode, a static analysis tool cannot read class files, a plugin throws unexplained errors, or quality reports lose data. When that happens, test quality can no longer be measured reliably.

**JaCoCo** is a code coverage tool for the JVM. It can instrument bytecode when classes are loaded or process class files in offline mode, then generate line/branch/instruction coverage reports. Some static analysis tools such as SpotBugs read bytecode; others like PMD, Checkstyle, or Error Prone analyze source code, ASTs, or compiler models. Because they operate at **different layers of the Java toolchain**, one tool may be compatible with the target JDK while another is not.

This lesson explains how to read class-file versions, the relationship between the JDK, JVM, and the ASM library, how JaCoCo instruments and generates reports, how to classify static analyzers, inspect Gradle/Maven configurations, recognize common errors, and design a verification matrix when upgrading Java. The goal is not merely turning CI green, but **preserving meaningful testing evidence and quality analysis** on the new runtime.

## 1. Class files are an important compatibility boundary

A `.java` file is processed by the compiler into bytecode stored in a `.class` file. Each class file has a header and structures describing the constant pool, methods, attributes, annotations, and information needed by the JVM.

Diagram:

~~~text
Java source (.java)
       |
       | javac / compiler
       v
Class file (.class)
       |
       +----> Java Virtual Machine reads and executes
       |
       +----> JaCoCo / bytecode agent reads or transforms
       |
       +----> SpotBugs / bytecode analyzer reads
       |
       +----> Shading / obfuscation / weaving tools
       |
       +----> Framework proxy / instrumentation
~~~

These components do not necessarily support the same class-file format version. For instance, a Java 21 JVM can run Java 21 class files, while an older bytecode analyzer version may not yet understand the corresponding structure.

It is also necessary to distinguish:

- **Java source level:** the syntax accepted by the compiler.
- **Class-file version:** major/minor version recorded in `.class`.
- **Platform API target:** the Java SE API set permitted during compilation.
- **Runtime JVM version:** the JVM's ability to load and execute bytecode.
- **Tool parser version:** an external tool's ability to read and transform class files.

A tool claiming "supports Java 21" must be read in the right context: does it support **running the tool itself on JDK 21**, **analyzing class files generated by JDK 21**, or **analyzing source using Java 21 syntax**? Those three commitments are different.

## 2. Major/minor version of a class file

A class file header begins with the `CAFEBABE` magic number, followed by the minor and major versions. The major version generally identifies the Java release corresponding to the bytecode format.

| Java release | Class-file major version |
|---|---:|
| Java 8 | 52 |
| Java 9 | 53 |
| Java 10 | 54 |
| Java 11 | 55 |
| Java 12 | 56 |
| Java 13 | 57 |
| Java 14 | 58 |
| Java 15 | 59 |
| Java 16 | 60 |
| Java 17 | 61 |
| Java 18 | 62 |
| Java 19 | 63 |
| Java 20 | 64 |
| Java 21 | 65 |
| Java 22 | 66 |
| Java 23 | 67 |
| Java 24 | 68 |
| Java 25 | 69 |

For example, a class file with major version **65** corresponds to the Java 21 class-file format. A typical Java 17 JVM cannot load a class file with major 65; the result may be `UnsupportedClassVersionError`. However, a static analysis tool can still throw a similar error such as `IllegalArgumentException: Unsupported class file major version 65`, even when the JVM running the tool is Java 21. That case indicates **the tool's bytecode parser does not support it yet**, not necessarily that the JVM cannot run the application.

### 2.1. Minor version and preview features

For class files generated when using preview language features on Java releases applying the preview class-file version mechanism, the minor version may be `65535`. Loading/running such class files is subject to conditions tied to the release and `--enable-preview`.

Example:

~~~bash
javac --enable-preview --release 21 Example.java
java --enable-preview Example
~~~

The syntax above illustrates running a project **that uses valid Java 21 preview features**. Not every class generated by the compiler from source code in a preview compilation necessarily carries the preview marker; inspect the specific file.

Analysis tools must support both the **class-file major version** and the **constructs/attributes** appearing in the code, especially when using preview or new JVM features. Looking at the major version alone does not prove the tool understands all semantics.

### 2.2. Checking class files with javap

~~~bash
javap -verbose -classpath build/classes/java/main \
  com.example.orders.OrderService
~~~

Look in the output for:

~~~text
minor version: 0
major version: 65
~~~

Here major 65 means the class-file format corresponds to Java 21. Check the **exact class files the tool is reading**. In a multi-module repository, one module may be compiled with `--release 17` while another uses Java 21.

### 2.3. Do not infer bytecode version from JAR age

A JAR can contain classes compiled at different releases, especially when using a **multi-release JAR** with `META-INF/versions/...`. Therefore, do not look at a JAR's release or one representative class and conclude every class file shares the same major version.

Many bytecode tools can handle multi-release JARs, yet how variants are selected may depend on the tool version and configuration. When a report fails only on one JDK, determine which actual variant the runtime or analyzer used.

## 3. Three easily confused "unsupported version" errors

With the same "unsupported version" phrase, the root cause can be completely different.

| Error | Component usually throwing it | Meaning |
|---|---|---|
| `UnsupportedClassVersionError` at application start | JVM | Running JVM cannot load the class-file version |
| `Unsupported class file major version N` in JaCoCo/ASM/SpotBugs | Tool parser/transformer | Tool or bytecode library does not yet understand the bytecode format |
| `release version N not supported` at compile | javac | Compiler is too old or `--release` setting is unsuitable |
| `Invalid source release: N` | Compiler or build plugin | Toolchain/source level mismatch |
| `Preview features are not enabled` | Compiler/JVM or tool | Preview setting does not match source/class |
| Coverage report empty even though tests pass | Plugin/agent/report pipeline | Not instrumented, missing exec data, wrong class mapping, or task skipped |

**Diagnostic rule:** identify the *process* and *class* throwing the exception. A `java.lang.IllegalArgumentException` from the ASM library is not treated like a JVM major-version error, even though the message looks very similar.

## 4. How does JaCoCo measure code coverage?

JaCoCo (Java Code Coverage) collects bytecode execution data while running tests or an application, then generates reports from that data and the corresponding class/source files.

Common flow:

~~~text
Source code                         Test source
    |                                   |
    | compile                           | compile
    v                                   v
.class files                      Test .class files
    |                                   |
    | JVM loads classes as tests run    |
    v                                   |
JaCoCo Java agent <----------------------+
    |
    | Instrument bytecode (probes)
    | Write execution data
    v
jacoco.exec or equivalent execution data
    |
    | + Original class files
    | + Source files
    v
JaCoCo report task
    |
    +--> HTML report
    +--> XML report (CI/Sonar integration)
    +--> CSV report (when needed)
~~~

JaCoCo does not measure coverage merely by reading source code; it needs data indicating which probes executed. Displaying line/branch coverage also depends on line-number metadata, bytecode structures, and source mapping capabilities.

### 4.1. Coverage is not simply "lines of source executed"

JaCoCo uses probes in bytecode to derive coverage units such as:

- **Instructions:** bytecode instructions executed or not executed.
- **Branches:** conditional branches identifiable under the tool's bytecode analysis model.
- **Lines:** mapping bytecode to source lines when appropriate debug information is present.
- **Methods/classes:** presence and execution extent of components.

A single source line can map to multiple bytecode instructions; a complex expression can contain multiple branches. Thus, "80% line coverage" does not mean 80% of business logic has been thoroughly tested.

### 4.2. JaCoCo needs to understand bytecode

To insert probes and analyze class files, JaCoCo uses bytecode reading/transformation technology, including the **ASM** library. If the JaCoCo or ASM version used by the tool does not yet support the new class-file major version, instrumentation or report generation can fail.

When upgrading the JDK, verify the **actual JaCoCo version** used by your plugin/test runner and compare it against the release compatibility notes. Do not assume a newer Gradle/Maven plugin automatically implies a newer JaCoCo agent; plugin version, agent runtime, and report tooling can be separate components.

## 5. Online instrumentation and offline instrumentation

### 5.1. Online instrumentation

The common mode is running JaCoCo as a **Java agent** via `-javaagent`. The agent intercepts class loading and instruments bytecode before the class is defined in the JVM.

Illustrative example of JVM argument syntax:

~~~bash
java -javaagent:/opt/tools/jacocoagent.jar=destfile=build/jacoco/test.exec \
     -cp "build/classes:lib/*" \
     com.example.orders.Main
~~~

This illustrates the agent mechanism, not a recommendation to run production applications with a coverage agent. Argument passing, port selection, and execution data paths must follow the actual JaCoCo release.

### 5.2. Offline instrumentation

In offline mode, class files are instrumented **before** the JVM runs. This mode is sometimes used when class loading is special or an agent cannot be attached normally.

Risks to note:

- Instrumented classes differ from original classes.
- Some setups require matching runtime support to execute probes.
- Reports require class files appropriate to the instrumentation mechanism used; depending on the workflow, using original classes is a critical requirement.
- Never accidentally instrument the same class **twice**.
- Build caches/shading can confuse original artifacts with instrumented artifacts.

Unless the project has a specific reason for offline instrumentation, keep a consistent coverage approach and avoid enabling online and offline simultaneously on the same classes.

### 5.3. Differences from static analysis

JaCoCo requires code to be executed to obtain execution data; a tool like SpotBugs can analyze bytecode without executing business methods. Therefore:

- **Coverage** answers how much code was executed by tests.
- **Static analysis** detects patterns or potential issues in code without executing the entire program.
- **Tests** verify assertions and behavior.
- **Runtime instrumentation** can alter timing/performance and be affected by class loaders and agent ordering.

Do not treat a high coverage score as proof of zero bugs or substitute static analysis for tests.

## 6. Why does older JaCoCo fail after upgrading the JDK?

Typical scenarios:

1. The JaCoCo agent does not recognize the new class-file major version.
2. The ASM version inside JaCoCo or another pipeline component is too old.
3. The test launcher runs on a different JVM than the JVM used to compile classes.
4. Frameworks/test libraries dynamically generate bytecode at a newer version unhandled by the agent.
5. The project enables preview features, yet the agent/report tool does not support those constructs.
6. Classes are transformed by multiple Java agents in a conflicting order.
7. The report task reads classes that mismatch the execution data.
8. The test task is skipped, JVM forking fails to launch, or the JaCoCo agent argument is not passed.
9. Some classes are loaded via custom class loaders or mechanisms incompatible with instrumentation settings.
10. The agent report destination lacks write permissions, is deleted before merging, or writes to another path.

An example log may look like:

~~~text
java.lang.instrument.IllegalClassFormatException:
Error while instrumenting com/example/OrderService
Caused by: java.lang.IllegalArgumentException:
Unsupported class file major version 65
~~~

For major 65 (Java 21), inspect the **actual JaCoCo/ASM version** before adding JVM flags. Opening JPMS packages with `--add-opens` will not make an old bytecode parser understand a new format.

### 6.1. Failures occurring only during report generation

Sometimes the test JVM runs and writes execution data, yet the report task fails when reading the new class files. This can happen if the agent and report generator differ in version, or if the report task reads a class-file variant unsupported by its parser.

Separate:

- Test/agent execution failures.
- Class instrumentation failures.
- Execution data generation failures.
- Class-file analysis failures during reporting.
- XML upload/import failures into analysis platforms.

Do not treat every "jacocoTestReport FAILED" error as a test behavior failure.

## 7. Updating JaCoCo for the target JDK

When upgrading the JDK, check the release notes and compatibility matrix **of the exact JaCoCo version used by the project**. Do not hardcode a rule like "JaCoCo version X onward supports all future Java versions"; the class-file format can change in future releases.

Technical process:

1. Record the JDK running tests and the compiler bytecode target.
2. Record the class-file major versions of main, test, and generated classes.
3. Record the JaCoCo plugin version, agent version, and report generator version.
4. Read JaCoCo documentation regarding support for the corresponding Java/class-file releases.
5. Update JaCoCo to an appropriate version.
6. If necessary, update Gradle/Maven plugins so configuration and report tasks are compatible.
7. Clean old outputs and run the new instrumentation/report pipeline.
8. Verify coverage reports and quality gates with real data.

Do not assume from **Gradle's version number** that the JaCoCo agent is already new enough. Gradle provides plugin integration, while JaCoCo `toolVersion` determines the JaCoCo implementation used in a Gradle pipeline when configured accordingly.

## 8. Example JaCoCo configuration in Gradle

With the Gradle Java plugin:

~~~groovy
plugins {
    id 'java'
    id 'jacoco'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 21
}

jacoco {
    // Choose a JaCoCo version confirmed by release notes to support the target JDK.
    toolVersion = 'REPLACE_WITH_VERIFIED_JACOCO_VERSION'
}

tasks.named('test') {
    useJUnitPlatform()
    finalizedBy(tasks.named('jacocoTestReport'))
}

tasks.named('jacocoTestReport') {
    dependsOn(tasks.named('test'))

    reports {
        html.required = true
        xml.required = true
        csv.required = false
    }
}
~~~

`REPLACE_WITH_VERIFIED_JACOCO_VERSION` is a **placeholder**, not a version to use verbatim. Choose a real version based on release notes, artifact repositories, and dependency management policies. The example also assumes the test suite uses JUnit Platform; if not using JUnit 5, adjust `useJUnitPlatform()`.

Some older Gradle versions have different report configuration syntax. Do not copy config from an arbitrary Gradle release without checking the project's wrapper.

### 8.1. Role of toolchain and options.release

- `java.toolchain` specifies the compiler/test tools JDK via Gradle's supported mechanism.
- `options.release` controls source syntax, class-file target, and target platform API set when supported by the compiler.
- The test JVM may be configured differently by Gradle from the compiler JVM; check the actual execution environment.
- The JaCoCo agent runs in the same test JVM process, so **the agent must be compatible with the runtime and actual bytecode loaded**.

If the JDK 21 compiler outputs class files targeting `--release 17`, many application classes have major 61, yet other libraries/test tools or generated code may still contain class files with higher major versions. Do not check just one class and conclude the entire process only needs major 61 support.

### 8.2. Running the corresponding tasks

Example command for team use in the build process:

~~~bash
./gradlew clean test jacocoTestReport
~~~

This command illustrates the workflow; it does not imply tests for a specific project have run or passed. When upgrading Java, verify how many tests the `test` task actually ran, whether XML/HTML reports were generated, and whether report paths match CI configuration.

### 8.3. Coverage verification gates

The JaCoCo Gradle plugin provides a `jacocoTestCoverageVerification` task with configurable rules. Example:

~~~groovy
tasks.named('jacocoTestCoverageVerification') {
    violationRules {
        rule {
            element = 'BUNDLE'
            limit {
                counter = 'LINE'
                value = 'COVEREDRATIO'
                minimum = 0.80
            }
        }
    }
}

tasks.named('check') {
    dependsOn(tasks.named('jacocoTestCoverageVerification'))
}
~~~

The 0.80 threshold is a **project policy example**, not a universal recommendation for all systems. Ensure tasks receive execution data accurately and do not turn a JDK change into a silent coverage-threshold change without an explicit decision.

A build can pass a coverage gate because the test task was skipped or the report is empty if rules do not trigger as expected; observe both executed tasks and actual coverage data.

## 9. Example JaCoCo configuration in Maven

In Maven, the JaCoCo Maven Plugin typically provides goals to:

- `prepare-agent`: prepare JVM agent properties for the test runner.
- `report`: generate coverage reports after tests run.
- `check`: enforce coverage rules.
- `report-aggregate`: support aggregated reporting in certain multi-module projects.

Example configuration snippet, not a complete POM:

~~~xml
<build>
  <plugins>
    <plugin>
      <groupId>org.jacoco</groupId>
      <artifactId>jacoco-maven-plugin</artifactId>
      <version>REPLACE_WITH_VERIFIED_JACOCO_VERSION</version>
      <executions>
        <execution>
          <id>prepare-coverage-agent</id>
          <goals>
            <goal>prepare-agent</goal>
          </goals>
        </execution>
        <execution>
          <id>generate-coverage-report</id>
          <phase>verify</phase>
          <goals>
            <goal>report</goal>
          </goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>
~~~

The version remains a placeholder that must be replaced with one confirmed to support your runtime/bytecode target. For reliable coverage results, coordinate with Maven Surefire/Failsafe configuration and test JVM forking.

### 9.1. The argLine issue

When JaCoCo prepares a Java agent for Maven tests, the test plugin configuration must **preserve the JVM arguments added by JaCoCo**. If a build overwrites `argLine` in Surefire/Failsafe without combining them properly, tests may still pass yet the agent never runs.

A configuration illustrating late property evaluation:

~~~xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <argLine>@{argLine} -Xmx1g</argLine>
  </configuration>
</plugin>
~~~

The `@{argLine}` syntax and mechanism must be used appropriately for the project's Surefire/Failsafe and JaCoCo versions. If the property is undefined in certain build profiles/branches, handle it per plugin documentation. Do not blindly edit every POM without understanding existing test JVM settings.

### 9.2. Do not disable JVM forking arbitrarily

If the test runner executes tests in the same JVM as the Maven process or the JVM agent fails to attach properly, JaCoCo may collect no data. Ensure test processes launch in a way compatible with JaCoCo. Passing tests do not guarantee the agent ran.

### 9.3. Running sample build phases

~~~bash
mvn clean verify
~~~

If unit and integration tests run in separate phases, examine whether goals bind to the right phases and execution data files connect to the right reports. Do not assume the `verify` lifecycle goal automatically measures all integration flows, especially if integration tests are run by another plugin or separate JVM/process.

## 10. Coverage reports in multi-module projects

A Java monorepo typically contains multiple subprojects:

~~~text
project/
├── api/
├── domain/
├── persistence/
├── web/
└── integration-tests/
~~~

If integration tests live in a separate module yet execute `domain` and `persistence` code, per-module coverage reports may lack data or calculate coverage differently than expected.

Common issues:

- Execution data resides in `integration-tests`, yet the `domain` report task is unaware of it.
- Reports point to compiled classes different from those executed by the test JVM.
- A module has generated code and separate source mappings.
- Multiple JVM forks overwrite the same `jacoco.exec` file.
- Tests run in parallel and data is written to multiple destinations.
- One module uses a different Java release, preventing the report parser from supporting all classes.
- Aggregate reports combine the same class name across multiple variants/versions.
- CI only imports XML from one submodule.

Before building aggregated reports, define the **coverage scope to measure**: production business source line coverage, all modules, or changed code only. Then design how execution data and class/source files are collected.

### 10.1. Execution data must match class files

JaCoCo identifies classes to link probes with class files. If reporting reads bytecode different from the actual bytecode instrumented during testing, coverage may vanish or report class mismatch errors.

A common cause is compilation/shading/generation rewriting class files right after tests run and before the report task reads them. Therefore, pipelines need consistent ordering for class creation, instrumentation, test execution, and reporting.

### 10.2. Do not arbitrarily merge data across versions

`.exec` data uses JaCoCo's internal format; when combining reports from multiple processes or JaCoCo versions, use compatible tools and versions. Do not simply concatenate binary files or treat XML reports as mergeable execution data.

If CI upgrades JaCoCo during migration, check whether upload/merge/aggregate reporting steps expect the same protocol/format.

## 11. Coverage when Java adds new language constructs

Modern Java features records, sealed classes, switch expressions, pattern matching, lambdas, text blocks, and more. Compilers may emit bytecode different from what developers see in source code.

Record example:

~~~java
public record OrderId(String value) {
    public OrderId {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("Order id must not be blank");
        }
    }
}
~~~

The compiler generates methods and bytecode required for records by specification. A sufficiently recent coverage tool may contain **filtering logic** excluding certain compiler-generated bytecode not directly controlled by source authors. Filtering and reporting logic can vary across JaCoCo releases.

### 11.1. Coverage percentages can shift even without test changes

When upgrading the compiler or JaCoCo, identical source and tests can yield different coverage percentages because:

- The compiler emits different bytecode.
- The tool adds filters for synthetic/generated constructs.
- Branch counting varies with bytecode structure.
- Debug metadata or source line mapping differs.
- New Java language features alter branch layouts.
- Exclusions/report scopes are configured differently.

This does not necessarily mean test quality improved or degraded. Cross-check executed test counts, input data, generated bytecode, and report scope.

### 11.2. Text blocks and constant folding

A text block or compile-time constant expression may produce less bytecode than a reader of source code imagines. Coverage on a source line is not a count of visible tokens or statements on that line.

### 11.3. Branch coverage of switches and patterns

A switch expression can produce more complex bytecode than a legacy switch statement. JaCoCo derives branches from bytecode under its model, not necessarily counting every `case` in source as an equal unit. When noticing branch coverage shifts from baseline, inspect the report and understand what the tool is measuring.

## 12. Generated code, Lombok, and coverage filters

In a project using annotation processors or generators:

~~~text
src/main/java/            handwritten source
build/generated/sources/  generated source
build/classes/            compiled output
~~~

Some generated classes can inflate the coverage denominator. If reports measure business-code test effectiveness, the team must decide whether generated sources should be included.

Some tools recognize/filter generated code based on bytecode patterns or corresponding annotations, though behavior changes by tool version. Do not assume every annotation named `Generated` causes every tool to skip code identically.

### 12.1. Clearly scoped exclusions

Options can include:

- Measuring only packages representing production business code.
- Excluding generated classes from reports using documented patterns.
- Maintaining separate reports for critical generated code if needed.
- Focusing test coverage on code the organization truly owns.

If a generated client or mapper is critical to product quality, excluding it entirely from the test strategy may be inappropriate. **Coverage exclusions only change reports; they do not verify correctness**.

### 12.2. Lombok and AST transformations

Tools like Lombok can affect compiler-generated code. When upgrading the JDK, check both the Lombok/processor version and JaCoCo version. An error in a compiler plugin/AST transformation can appear before coverage instrumentation even starts.

Do not blame JaCoCo for every unusual line-coverage metric on Lombok-generated methods; it may be a change in bytecode emitted by the compiler or processor.

## 13. Static analysis tools: not all read class files

**Static analysis** checks a program without running every business code path. Yet how tools accomplish this varies widely.

| Tool/group | Primary input | Analysis type | Java upgrade risk |
|---|---|---|---|
| JaCoCo | Bytecode + execution data | Runtime coverage instrumentation/reporting | Unsupported class-file version, report mapping |
| SpotBugs | Compiled Java bytecode | Bytecode static analysis | Parser fails to read class files, outdated detector versions |
| PMD Java | Java source/AST | Source rules and syntax | Parser does not yet support new language level |
| Checkstyle | Java source/AST grammar | Style and structural checks | Unrecognized new grammar/tokens |
| Error Prone | javac compilation/type model | Compiler-integrated bug checking | Plugin version incompatible with JDK/javac APIs |
| SonarJava / quality analyzer | Source, semantic model, and pipeline-dependent bytecode | Rules/semantic analysis | Analyzer version and JDK support mismatch |
| Semgrep and source-based analyzers | Source/AST/patterns per language | Pattern/semantic checks | Grammar, rule engine, language version |
| Custom Java agent/ASM tool | Loaded class files/bytecode | Instrumentation or transformation | Bytecode parser does not support new major version |

This table is a generalized model; a product may combine source and bytecode or change architectures across releases. When evaluating a tool, consult documentation for the **exact version** rather than assuming all versions behave identically.

### 13.1. Source parser failure

If PMD or Checkstyle does not yet understand switch pattern or record syntax, the tool may throw parse errors even when the new javac compiles sources cleanly. In that case, swapping ASM is unlikely to help; upgrade the analyzer's **language parser**.

### 13.2. Bytecode parser failure

If SpotBugs or JaCoCo throws `Unsupported class file major version N`, inspect the bytecode-reading library and analyzer version. Upgrading another source-grammar tool will not resolve this error.

### 13.3. Compiler-integrated failure

Error Prone or a javac plugin can depend on compiler internals/lifecycle. A newer JDK can prevent the plugin from loading or trigger `IllegalAccessError`, `NoSuchMethodError`, or `NoSuchFieldError`. The issue is not necessarily the source parser or ASM, but **compatibility between the plugin and javac version**.

## 14. SpotBugs: checking bytecode with a compatible parser

SpotBugs operates primarily on class files and needs to understand the bytecode structures of scanned modules.

A typical workflow:

~~~text
Compile source
    |
    v
Compiled .class / JAR
    |
    v
SpotBugs analyzer + detectors
    |
    v
Bug reports XML/HTML/other
    |
    v
CI quality gate / triage
~~~

Scenarios to investigate:

- Old tool does not understand the new major version.
- Missing dependency classpath causes incomplete type resolution.
- Analyzer or Gradle/Maven wrapper plugin is incompatible with the new JDK.
- Custom detector plugin compiled for a different API version.
- New compiler output alters detection patterns, increasing/decreasing findings.
- Generated classes, test classes, or exclusions fall into a different scope than before.

Reference Gradle command when the project already has the corresponding plugin configured:

~~~bash
./gradlew spotbugsMain
~~~

`spotbugsMain` is not a default task in every Gradle Java project; it exists only when the corresponding SpotBugs plugin is applied and configured properly. Avoid writing CI docs requiring tasks a project lacks.

### 14.1. Do not treat zero findings as sufficient proof

If an analyzer skips modules due to a broken classpath, scans an empty source set, or downgrades errors to warnings, the report may show fewer findings without any actual improvement in code quality. When upgrading the JDK, confirm the number of classes analyzed, enabled rules/plugins, and exit status.

## 15. Checkstyle, PMD, and Java syntax parsers

Source-based tools do not necessarily need to read class-file versions, yet must still understand the **Java syntax used in source code**.

Example:

~~~java
public record Account(String id) {
}

public sealed interface PaymentState
        permits Pending, Completed {
}

public record Pending(String key) implements PaymentState {
}

public record Completed(long transactionId)
        implements PaymentState {
}
~~~

If an old parser only supports Java 11, it may fail to recognize `record` or `sealed interface`. Having the application compile on Java 21 will not automatically allow an old Checkstyle/PMD version to parse it.

Signs include:

- ParseException / unexpected token.
- AST node kind unsupported by a rule/plugin.
- Custom rules casting nodes incorrectly when new constructs appear.
- Default language-level configuration differs from source target.
- Analyzer upgrade alters rule defaults or severity levels.

### 15.1. Upgrading an analyzer can change finding counts

A new PMD/Checkstyle release may:

- Add new rules or rename rule identifiers.
- Support new AST nodes.
- Alter behavior of certain AST visitors.
- Change default severities or file scopes.
- Remove deprecated rules.

Therefore, compare baseline findings against the **rule set, analyzer version, source scope**, and Java language level, not merely total issue counts.

### 15.2. Project-specific rules

Custom checks/PMD rules are also dependencies. If they rely on AST internals or old plugin APIs, a newer analyzer can break custom rules even when the core engine supports the new Java version. Verify plugin/rule compatibility separately.

## 16. Error Prone and javac plugins

Tools running inside javac behave differently from standalone source scanners. They may use compiler trees, type models, or APIs tied to a specific javac version.

When upgrading the JDK:

- The plugin must be compatible with that JDK's javac API/lifecycle.
- Build plugins integrating with javac must also be compatible.
- Rule providers may need recompilation against matching API/plugin versions.
- JVM module boundaries may affect access to compiler internals.
- Gradle/Maven toolchains may use a different JDK than the daemon/build process.

Do not spray `--add-exports` broadly to hide a compiler plugin's `NoSuchFieldError`. If an internal field changed, opening access will not bring it back. Find an Error Prone/plugin release built for the target JDK or change the integration method.

## 17. Sonar and coverage import pipelines

A quality analysis pipeline typically has two separate steps:

~~~text
Run tests + JaCoCo agent
       |
       v
Generate JaCoCo XML report
       |
       v
Quality analyzer / Sonar scanner
       |
       v
Dashboard and quality gate
~~~

When upgrading the JDK, multiple points can fail independently:

- The JaCoCo agent fails to instrument new Java bytecode.
- The JaCoCo report task fails to read class files.
- The XML report is missing because tests were skipped.
- The scanner cannot locate XML reports at new paths.
- The analyzer server or plugin does not support the new source language level.
- The scanner JVM requires a different version than the build/test JVM.
- Source paths in XML mismatch the scanner's module/directory structure.
- Quality gates import incomplete module data or duplicate entries.

**A "SUCCESS" scanner run does not guarantee coverage was imported.** Inspect reported paths and the actual dashboard. If coverage drops to 0 or "not available" after migration, determine whether the failure is instrumentation, reporting, or import.

### 17.1. JaCoCo XML and execution data are different

`jacoco.exec` is typically execution data in JaCoCo's internal format; the XML report is generated from execution data + classes + sources. Quality reporting systems usually import XML reports; an exec file cannot be used as XML simply because both are coverage artifacts.

When migrating pipelines, check file types, matching schemas/versions, and explicitly configured paths.

## 18. ASM compatibility and other bytecode tools

JaCoCo is not the only component using ASM or bytecode-reading technology. Many libraries embed their own ASM or a shaded version.

Ecosystem examples:

- Byte Buddy.
- ASM used directly or through plugins.
- Mocking frameworks and inline mock makers.
- AOP/weaving tools.
- Spring proxy/instrumentation components.
- Coverage agents and Java profilers.
- Bytecode optimizers, obfuscators, and shaders.
- Testing utilities generating dynamic classes.

A tool may throw errors when reading classes generated by a new compiler, or when reading dynamically generated classes containing unsupported constructs. Upgrading only JaCoCo may not be enough if another mocking/agent library still bundles an old parser.

### 18.1. Multiple agents running together

A JVM can accept multiple `-javaagent` flags. Agent order, retransformation mechanisms, and interactions between transformers can affect final bytecode.

Example:

~~~text
JVM startup
   |
   +-- JaCoCo agent
   +-- APM / tracing agent
   +-- Mocking or test instrumentation
   |
   v
Class loading and transformation chain
   |
   v
Application / tests
~~~

If errors happen only with coverage enabled, isolate agents in a test environment to pinpoint the conflicting component. Do not experiment arbitrarily in production, as doing so can impact monitoring and security.

### 18.2. Do not force ASM versions via dependency overrides

A library may shade ASM internally; adding a newer `org.ow2.asm:asm` onto the application classpath will not necessarily replace the ASM inside an agent. Forcing a transitive version can also break the parent library's ABI.

A better approach is upgrading the **component owning the parser** to an officially supported release and verifying the resolved dependency graph.

## 19. Gradle daemon, compiler toolchain, and test JVM

During a Java migration, multiple distinct JVMs may exist:

~~~text
Gradle daemon JVM
       |
       +--> JavaCompile toolchain (javac)
       |
       +--> Test JVM (JaCoCo agent)
       |
       +--> Static analyzer worker JVM
       |
       +--> Packaging / codegen plugin
~~~

A Gradle version may require a minimum JDK to run the daemon, while compiler toolchains can be chosen independently. Test tasks can also configure a different Java launcher or forked JVM.

Example:

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.named('test', Test) {
    javaLauncher = javaToolchains.launcherFor {
        languageVersion = JavaLanguageVersion.of(21)
    }
}
~~~

This configuration illustrates the intent to run tests on Java 21. API/syntax must match the installed Gradle wrapper and plugins. In practice, some toolchain configs apply automatically to tests, yet during diagnosis **verify the JVM actually used by tests** rather than inferring it from the compile task.

### 19.1. Why do tests run old Java while bytecode is new Java?

If the compile target exceeds the test JVM, test startup can throw `UnsupportedClassVersionError` before JaCoCo instruments anything. This is a runtime mismatch, not a lack of class-file reading support in JaCoCo.

If the test JVM is new while the JaCoCo agent is old, the error likely comes from the agent. Distinguish the two cases using stack traces and JVM logs.

## 20. Maven compiler, Surefire/Failsafe, and Java agents

In Maven, check three areas:

1. The Maven JVM running plugins.
2. Maven Compiler Plugin using the target compiler/release.
3. Surefire/Failsafe launching or reusing the test JVM and receiving JaCoCo agent arguments.

Example compiler release configuration:

~~~xml
<properties>
  <maven.compiler.release>21</maven.compiler.release>
</properties>
~~~

This is a POM fragment, not a complete Maven file. If running Maven on an old JDK, the new compiler release is not supported merely because the property is declared. An appropriate compiler JDK is required.

If tests run yet coverage is absent, inspect logs for JVM arguments added by `jacoco:prepare-agent`, `argLine` configs, fork settings, and the report phase. Do not lower coverage gates to mask an unattached agent.

## 21. Preview features and toolchain support

Some teams experiment with Java preview features. Watch two separate concerns:

- Compiler and runtime must enable preview for the matching release.
- Parsers/transformers/analyzers must support the emitted bytecode and source constructs.

Conceptual Java 21 example:

~~~bash
javac --enable-preview --release 21 Example.java
java --enable-preview Example
~~~

If the application uses preview features in a given release, a static analysis tool may fail to recognize new AST nodes even if the JDK compiles them. JaCoCo/ASM must also support the class-file version and related structures.

Do not conclude "the tool supports Java 21" guarantees support for all Java 21 preview features. Read release notes and test specific classes using preview features.

### 21.1. Preview features and production releases

Preview features have distinct lifecycles and compatibility conditions. Shipping production software dependent on preview features raises the cost of the next JDK upgrade; document that decision clearly and ensure tests/agents/analyzers stay compatible.

## 22. Multi-release JARs and class-file variants

A multi-release JAR can contain:

~~~text
META-INF/MANIFEST.MF
com/example/Util.class
META-INF/versions/11/com/example/Util.class
META-INF/versions/17/com/example/Util.class
META-INF/versions/21/com/example/Util.class
~~~

The JVM selects the appropriate runtime variant under the multi-release JAR mechanism. Static analyzers or report generators may select variants differently; incomplete support can cause coverage or findings to diverge from runtime execution.

Questions to answer:

- Is the tool reading the base class or a version-specific class?
- Which major version was the variant compiled to?
- Which variant does the test JVM actually load?
- Where does source mapping for that variant live?
- Is reporting collapsing multiple variants into one logical class?

When upgrading from JDK 17 to JDK 21, a JAR may start loading its Java 21 variant, exposing agents to a new class-file major version even without changing application source code.

## 23. Checking source paths and debug information

Line coverage requires mapping bytecode back to source files. If compilation lacks or changes debug info, reports may display class/method coverage yet omit line mappings or show "no source".

Other causes:

- Source files are missing where the report task looks.
- Class names/packages differ from the source layout.
- Generated source directories are not declared.
- Compilers/code generators alter line-number tables.
- Reporting reads original classes different from executed classes.
- Build artifacts are obfuscated/shaded after tests collect data.

Source directory settings must match the project build. Do not inflate coverage metrics by mis-mapping sources or excluding unexpected classes without a deliberate report-scope decision.

## 24. Separating instrumentation failures from test behavior failures

When `test` fails, a build log may contain both JaCoCo messages and assertion failures. Pinpoint the root cause.

| Symptom | Possible phase | Resolution |
|---|---|---|
| `Error while instrumenting ...` | Java agent/class transform | Check JaCoCo/ASM versions, class major, and agents |
| `Unsupported class file major version N` in analyzer | Bytecode parser | Upgrade tool owning the parser; check bytecode |
| `UnsupportedClassVersionError` | Test JVM cannot load class | Align runtime and target |
| `ClassFormatError` | Invalid bytecode or broken transform | Check agent ordering and compilers/transformers |
| Test assertion failed | Business or test logic | Investigate behavior change; do not blame coverage first |
| Report file missing | Task/report pipeline | Check test execution, destination, report task, paths |
| Coverage = 0 | Missing/mismatched data or import | Check agent args, exec files, class mapping, scanner |
| Static analyzer parse error | Source grammar/tool | Upgrade parser and rule plugins |
| Compiler plugin `IllegalAccessError` | Javac internals/module boundary | Upgrade JDK-compatible plugin |
| Findings spike sharply | Analyzer/rules/scope changed | Compare baseline, rule sets, parser version |

A valuable diagnostic technique is running tests with and without coverage inside a **test environment** to separate instrumentation failures from application failures; keep test inputs, runtime, dependency graph, and environment identical for a meaningful comparison.

## 25. Do not equate coverage with test quality

Coverage measures whether bytecode instructions were triggered, not correctness guarantees. Example:

~~~java
public int divide(int total, int count) {
    return total / count;
}
~~~

A test calling `divide(10, 2)` yields high line coverage without testing `count == 0`, overflow, signs, or business expectations.

During migration, one risk is teams focusing on getting coverage percentages "back to normal" without confirming assertions remain valid. If the JDK or a library changes semantics, tests must verify correct behavior, not merely execution counts.

### 25.1. Combining quality layers

- Unit tests verify logic.
- Integration tests verify dependencies/frameworks/runtime.
- JaCoCo measures execution coverage during executed tests.
- Static analysis detects bug patterns, style issues, or code smells.
- Dependency/security analysis surfaces library risks.
- Performance tests catch regressions.
- Runtime smoke tests validate real deployment.

No layer fully replaces another. Safe Java upgrades require combined evidence.

## 26. Determining whether a tool supports a new class-file major version

For JaCoCo or bytecode analyzers, follow this sequence:

1. Identify the target JDK and actual compiler-emitted bytecode.
2. Read the class-file major version from a representative set of classes.
3. Identify tool versions and related dependencies.
4. Read the tool's release notes/compatibility matrix, including preview support when applicable.
5. Confirm the tool supports reading the **class-file format**, not just running on the JVM.
6. Test analyzing/instrumenting actual project classes.
7. Verify output artifacts/reports, not only exit codes.
8. Record version pins and evidence in the migration report.

Do not guess "ASM version N definitely supports Java M" by version arithmetic. Support is added release by release and may differ between experimental and official support.

If a tool shades its own ASM copy, upgrading `org.ow2.asm` on the application classpath will not necessarily change the implementation the tool executes.

## 29. Hypothetical real-world failure example

Suppose a system previously used Java 17 and an older JaCoCo release. After building on Java 21, the pipeline reports:

~~~text
> Task :orders-service:test FAILED
java.lang.instrument.IllegalClassFormatException:
Error while instrumenting com/example/orders/OrderService
Caused by: java.lang.IllegalArgumentException:
Unsupported class file major version 65
~~~

An investigation path:

1. Confirm `OrderService.class` has major 65 via `javap -verbose`.
2. Check which JaCoCo agent version is attached to the Test JVM.
3. Confirm the test JVM runs Java 21 or an appropriate runtime.
4. Read JaCoCo release notes to pick a version supporting major 65.
5. Update JaCoCo and necessary plugins, pinning versions.
6. Re-run tests with instrumentation.
7. Generate XML/HTML reports and verify line/branch coverage.
8. Confirm the quality analyzer imports full data.

Do not add `--add-opens java.base/...` to fix a major 65 error. The error involves class-file format, not reflective access into encapsulated packages.

### 29.1. Next failure scenario: coverage drops to 0

After upgrading the JaCoCo agent, tests pass yet dashboard coverage drops to 0.

Possibilities:

- Test runner did not receive `-javaagent`.
- JaCoCo exec data file was not written.
- Report task did not run or read the wrong path.
- XML report failed to import into the scanner.
- Report class files mismatched executed classes.
- Exclusions are overly broad.
- Multi-module aggregation missed a module.

This is a **different pipeline error**; do not keep bumping JaCoCo versions blindly if instrumentation already succeeded.

## 30. Managing quality gates when the compiler shifts coverage

When upgrading the JDK, JaCoCo, and analyzers, percentages or finding counts may shift despite unchanged tests.

To distinguish causes:

- Save baseline reports from the old JDK and JaCoCo.
- Record compiler target, tool versions, excludes, rules, and source scope.
- Compare executed test counts.
- Compare classes/instructions/branches included in the denominator.
- Inspect synthetic/generated code filters.
- Check source mappings and original class files.
- Separately evaluate rule or severity changes in static analyzers.
- If thresholds need adjustment, make an explicit quality decision rather than silently loosening the gate.

A small coverage shift after compiler bytecode changes does not automatically prove test regression; however, **never assume** every difference comes from tooling. Tests may genuinely have been skipped or code paths changed.

## 31. Generated classes, instrumented artifacts, and reproducibility

During a Java migration, code generation output also changes. An updated annotation processor may emit different methods, getters, builders, or models than before.

Accordingly, a trustworthy coverage report needs:

1. Build inputs and code generator versions.
2. Compiler JDK and `--release`.
3. Actual class files loaded during tests.
4. JaCoCo agent/report versions.
5. Execution data alongside corresponding JVM forks.
6. Consistent source mappings and original classes.
7. Reviewed exclusions.
8. Importing quality analyzer version.

Do not generate reports from class files of a different build or artifacts transformed after execution data collection. If shading or obfuscation is present, clarify when instrumentation occurs and which classes reporting maps to.

## 32. Phased troubleshooting workflow

When a Java-upgrade pipeline fails, avoid fixing multiple tools at once. A layered approach:

### Phase A: Run Java without instrumentation

Confirm compiler, runtime, and basic tests are compatible. If the test JVM fails to load classes, resolve the runtime/bytecode mismatch before investigating JaCoCo.

### Phase B: Enable the JaCoCo agent

Verify the test JVM loads the agent, classes instrument cleanly, and tests still run. Read exact errors for which class, major version, and transformer failed.

### Phase C: Generate JaCoCo reports

Confirm execution data is written and XML/HTML reports cover the right modules. Compare metrics against baseline.

### Phase D: Run static analyzers

Separate bytecode analyzers like SpotBugs from source parsers like PMD/Checkstyle and compiler-integrated tools. Each category needs its own compatible versions.

### Phase E: Integrate with the quality dashboard

Confirm the scanner imports the right XML, rules/scopes did not change unexpectedly, and quality gates reflect the new data.

### Phase F: Cross-JDK and deployment tests

If supporting multiple JDKs, re-run the matrix. Verify agents, native libraries, and instrumentation in a production-like environment, not just on a laptop.

Separating phases pinpoints exactly which dependency/tool requires upgrading, preventing migrations from turning into unproven version overrides.

## 33. Investigation checklist for coverage/static analysis failures

- [ ] Identified the exact JDKs running the build, javac, tests, and analyzers.
- [ ] Read class-file major/minor versions of failing classes.
- [ ] Verified `--release`, source level, and preview flags.
- [ ] Identified JaCoCo agent version and report plugin version.
- [ ] Verified class-file support via tool release notes.
- [ ] Checked ASM/other bytecode tools, including shaded copies.
- [ ] Distinguished JVM errors from analyzer parser errors.
- [ ] Confirmed the test JVM actually attached the JaCoCo agent.
- [ ] Verified execution data exists and the report task consumes it correctly.
- [ ] Confirmed XML/HTML generation and successful dashboard import.
- [ ] Checked multi-module aggregation and report class/source mappings.
- [ ] Verified source parsers support new Java syntax.
- [ ] Checked custom analyzer rules and compiler plugin compatibility.
- [ ] Checked preview/MR-JAR/generated classes if applicable.
- [ ] Compared test counts, coverage scope, and rule sets against baseline.
- [ ] Obtained test results without coverage to separate behavior failures from instrumentation failures.
- [ ] Recorded version pins, artifacts, logs, and fix owners.

This list serves as lesson guidance, not confirmation that steps were run on a specific repository.

## 34. Mistakes to avoid

### 34.1. Confusing "JVM supports Java 21" with "JaCoCo supports Java 21 bytecode"

A JVM able to load major 65 classes does not prove an old JaCoCo/ASM version can parse/instrument that format. Consult a separate support matrix.

### 34.2. Upgrading only JaCoCo while ignoring mocking/agent tools

Another Java agent may also bundle an old ASM or bytecode parser. Failures occurring only with coverage enabled may stem from transformer interactions rather than the coverage agent alone.

### 34.3. Adding `--add-opens` for unsupported class-file major errors

Module exports/opens govern access, not missing class-file version support in a parser.

### 34.4. Seeing passing tests and assuming JaCoCo ran

Tests may run without the agent attached; coverage data stays empty. Inspect JVM args, exec data, and report outputs.

### 34.5. Seeing an XML report file and trusting every metric

The report may be leftover from a previous build, missing modules in scope, or mismatched with classes. Clean outputs when investigating and verify timestamps, source mappings, and artifacts.

### 34.6. Substituting high coverage for assertions

Executed code does not mean correct code. Unit, integration, and behavioral tests remain necessary.

### 34.7. Turning off all static analysis to turn CI green

Doing so hides source/bytecode compatibility failures and breaks quality control. Upgrade tools and document owned exceptions if a brief deferral is unavoidable.

### 34.8. Immediately lowering coverage gates upon upgrading the JDK

Coverage percentage shifts can stem from compiler filters, yet can also indicate skipped tests. Investigate root causes before deciding to alter thresholds.

### 34.9. Forcing one external ASM version across every dependency

Many tools shade their parser or require specific API versions; overriding without compatibility evidence can introduce new errors.

### 34.10. Testing only a single class file

A project contains generated classes, multi-release JARs, or dependencies at different major versions. Scan the actual class-file set read by analyzers.

## 36. Summary principles

- **Class-file version is a compatibility contract across compiler, JVM, and bytecode tools.** Not only must the JDK runtime read bytecode; JaCoCo and analyzers must understand that format as well.
- **A tool running on a new JDK does not guarantee it can analyze class files created by that JDK.** Distinguish runtime compatibility from input-format compatibility.
- **JaCoCo instruments bytecode and collects execution data**, then combines them with classes/sources to produce reports. Passing tests do not guarantee coverage data exists.
- **JaCoCo/ASM must support the actual bytecode target.** Consult release notes/version matrices and test on project classes rather than guessing.
- **Source analyzers, bytecode analyzers, and javac-integrated tools carry different risks.** PMD/Checkstyle need grammars; SpotBugs needs bytecode parsers; Error Prone needs matching compiler integration.
- **Coverage percentages can shift when compiler/tool filters change.** Compare scope, tests, class files, and report rules before lowering gates.
- **Generated code, records, patterns, preview features, and multi-release JARs** can affect bytecode, instrumentation, and source mappings.
- **Gradle/Maven plugins, the JaCoCo agent, test JVM, and report generator must each be verified separately.** Do not assume upgrading the wrapper upgraded every analyzer.
- **Agent conflicts and shaded ASM versions** must be investigated at the owning component rather than forcing blanket dependency overrides.
- **XML coverage import is a separate step** from generating exec data and reports. A successful dashboard run does not guarantee full data import.
- **Static analysis does not replace behavioral testing; coverage does not replace assertions.** Migration must combine quality layers.
- **Compatibility conclusions must be backed by evidence:** tool versions, JDK runtime, class-file major versions, executed tests, report artifacts, and CI quality gates.

A reliable Java Advance Compatibility Migration plan does not just make sources compile and services start. It must also ensure **JaCoCo can measure the code actually running, static analysis tools understand the syntax and bytecode of the new Java version, and the quality pipeline continues producing meaningful reports**. When preserving this observability and verification capability, the team can evaluate JDK changes based on evidence rather than accepting a "CI-green" upgrade that silently lost defect-detection capability.
