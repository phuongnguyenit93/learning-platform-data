# Reproducing Reflection Errors and Eliminating the Need for --add-opens

## 1. Exercise Context

A legacy Java project might use reflection to read/write `private` fields, invoke internal constructors, or access unpublished JDK APIs. That approach sometimes ran on Java 8 or certain Java 9–15 configurations, yet fails when upgrading to JDK 17, JDK 21, or newer releases with **strong encapsulation**.

A typical error:

~~~text
java.lang.reflect.InaccessibleObjectException:
  Unable to make field private final byte[] java.lang.String.value accessible:
  module java.base does not "opens java.lang" to unnamed module ...
~~~

A common "quick-fix" workaround:

~~~bash
java --add-opens=java.base/java.lang=ALL-UNNAMED \
     -cp out LegacyStringProbe
~~~

This flag can help reproduce and isolate the issue, but it **does not turn code relying on internal fields into a compatible API**, nor is it a default option for long-term production releases.

This exercise belongs to **Java Advance Compatibility Migration — Practice Exercises**, with the goal: **reproduce the reflection error, identify the root cause at the module boundary, and replace the code/configuration so the application runs without the command-line `--add-opens`**.

We will perform two independent labs:

1. **Lab A:** A classpath application reads the JDK's `String.value` field and fails because `java.base` does not open `java.lang`. Migrate to public Java APIs.
2. **Lab B:** Two named modules where one module attempts to access a `private` field of the other module. Fix primarily with a public API; if a framework genuinely needs reflective access, use scoped `opens ... to ...` in the module descriptor instead of a broad JVM flag.

Later sections expand to third-party libraries, frameworks, annotations/serialization, agents, CI, compatibility testing, and removing leftover flags.

## 2. Objectives and Completion Criteria

After completing this lesson, the reader can:

- Recognize `InaccessibleObjectException` arising from `AccessibleObject.setAccessible(true)`.
- Distinguish `exports` from `opens`, as well as reflective access from normal Java bytecode access.
- Use a temporary JVM flag strictly for **control verification**, without turning it into a permanent dependency.
- Replace access to JDK private internals with Java public APIs while preserving behavior.
- Design APIs or module descriptors so frameworks can handle private members within permitted boundaries.
- Detect `--add-opens` injected from the CLI, Gradle/Maven, test runners, `JAVA_TOOL_OPTIONS`, containers, or agents.
- Write regression tests proving the application runs on the target JDK **without unauthorized package-opening flags**.
- Distinguish module encapsulation errors from `NoSuchMethodError`, `VerifyError`, `UnsatisfiedLinkError`, or missing JAR errors.

**Final outcome:** The same business functionality runs on the target JDK without needing `--add-opens=java.base/java.lang=ALL-UNNAMED`; legitimate access changes on project-owned modules are clearly documented and tested.

## 5. Lab A — Legacy Code Accessing a Private JDK Field

Create `src/LegacyStringProbe.java`:

~~~java
import java.lang.reflect.Field;

public final class LegacyStringProbe {
    public static void main(String[] args) throws Exception {
        String text = "Hello Java";

        Field field = String.class.getDeclaredField("value");
        System.out.println("Declared field type: "
                + field.getType().getTypeName());

        // Line causing error when java.base/java.lang is not opened:
        field.setAccessible(true);

        Object rawValue = field.get(text);
        System.out.println("Internal value runtime type: "
                + rawValue.getClass().getTypeName());
    }
}
~~~

This is an **intentional anti-pattern to reproduce the error**. Do not copy `String.value` access into business code.

### 5.1. Statement-by-Statement Analysis

`String.class.getDeclaredField("value")` looks up a field declared directly in class `String`, even when it is `private`. **Retrieving Field metadata** does not necessarily require permission to read its contents.

`field.setAccessible(true)` requests suppressing Java access checks within the bounds permitted by module rules. On JDKs with strong encapsulation, the `java.base` module does not open the `java.lang` package to classpath code in the unnamed module, so the request is denied.

`field.get(text)` runs only if the preceding access-suppression step succeeds. The raw internal representation of `String` is not a stable API and must not be used to infer string encoding logic.

## 6. Compiling and Running to Reproduce

From the `reflection-lab` directory:

~~~bash
javac --release 17 -d out src/LegacyStringProbe.java
java -cp out LegacyStringProbe
~~~

If using JDK 21, `--release 17` can still be appropriate because this code only requires Java 17 or earlier APIs. If using a JDK older than 17, adjust the target per compiler support, though module access results may differ across releases.

On common JDK 17/21 HotSpot builds, the output before failure looks like:

~~~text
Declared field type: byte[]
Exception in thread "main"
  java.lang.reflect.InaccessibleObjectException:
  Unable to make field private final byte[] java.lang.String.value accessible:
  module java.base does not "opens java.lang" to unnamed module ...
    at java.base/java.lang.reflect.AccessibleObject...
    at java.base/java.lang.reflect.Field...
    at LegacyStringProbe.main(LegacyStringProbe.java:...)
~~~

Wording, line numbers, and stack trace details may vary by JDK build.

### 6.1. What Has Been Proven

1. The application class compiled and the JVM can load it.
2. `String.value` may exist, yet access from the caller is denied.
3. The error stems from a **deep reflection** request into `java.base/java.lang`, not from uncompilable Java source.
4. The message explicitly identifies the **owning module**, **package**, and **caller's module**.

### 6.2. What Has Not Been Proven

- It has not proven that a package-opening flag is a sustainable solution.
- It has not proven that the field type is always `byte[]` in every JDK.
- It has not proven that reading the private value satisfies the string's business semantics.
- It has not proven that other application errors will disappear if the flag is added.

## 7. Decoding the `InaccessibleObjectException` Message

Example:

~~~text
module java.base does not "opens java.lang" to unnamed module
~~~

| Component | Meaning |
| --- | --- |
| `java.base` | Module containing the class the caller is trying to reflect on |
| `java.lang` | Package containing the field/method requiring deep access |
| `opens` | Deep reflection permission for the package |
| `unnamed module` | Code running on the classpath, not belonging to a named module |
| `setAccessible(true)` | Request to suppress access checks was rejected |

An error in another package might look like:

~~~text
module java.base does not "opens java.util" to unnamed module
~~~

or:

~~~text
module com.example.model does not
  "opens com.example.model.internal"
  to module com.example.consumer
~~~

Analyze the **source module, source package, and caller module** before choosing a fix. Do not just look at the exception name and blindly add a common set of flags.

## 8. Trying `--add-opens` Once as a Control Check

Re-run the legacy class:

~~~bash
java --add-opens=java.base/java.lang=ALL-UNNAMED \
     -cp out LegacyStringProbe
~~~

On HotSpot JDKs that currently hold the `String.value` field, the program can pass `setAccessible(true)` and print:

~~~text
Declared field type: byte[]
Internal value runtime type: byte[]
~~~

This confirms the failure is tied to **module openness**, rather than the field not existing at all. However, this is strictly an **isolation experiment**.

### 8.1. What Does `ALL-UNNAMED` Mean?

Classpath code resides in unnamed modules corresponding to class loaders. `ALL-UNNAMED` is a special target covering all unnamed modules in launcher flag syntax. Opening `java.base/java.lang` to all unnamed modules is **broader** than what a specific call site needs.

### 8.2. The Flag Does Not Change the Public API

`String.value` remains `private` and remains an implementation detail. `--add-opens` permits reflective access within the specified scope, yet does not promise the field will not be renamed or change its type, layout, or behavior in the next JDK update.

### 8.3. Recording the Control Evidence

~~~text
Without --add-opens: InaccessibleObjectException
With --add-opens: reflective access proceeds
Likely cause: deep reflection into strongly encapsulated JDK package
Preferred fix: remove dependency on JDK-private representation
~~~

**Do not add the flag to production Dockerfiles or startup scripts just because the lab ran with it.**

## 9. Why Is Reflection into `String.value` a Risky Design?

Prior to Java 9, many JDKs used an internal representation different from releases with **Compact Strings**. On JDKs implementing Compact Strings, data may be held in a `byte[]` accompanied by representation metadata. This is a **JVM implementation detail**, not a public contract of `java.lang.String`.

Code accessing the internal field might:

- Wrongly assume `char[]` while the runtime uses `byte[]`.
- Confuse Java UTF-16 code units with bytes of internal storage.
- Ignore internal coder/encoding metadata.
- Depend on an unguaranteed private field layout.
- Expose sensitive data if raw contents are logged.
- Break due to strong encapsulation even though it still compiles cleanly.

An application wanting to **count characters**, **encode to bytes**, **read code points**, or **compare strings** should use the matching Java public API instead of reading raw fields.

## 10. Lab A — Fixing with Java Public APIs

Create `src/PublicStringProbe.java`:

~~~java
import java.nio.charset.StandardCharsets;
import java.util.Arrays;

public final class PublicStringProbe {
    public static void main(String[] args) {
        String text = "A\uD83D\uDE00"; // A and an emoji.

        int utf16Units = text.length();
        int codePoints =
                text.codePointCount(0, text.length());
        byte[] utf8 = text.getBytes(StandardCharsets.UTF_8);

        System.out.println("UTF-16 code units: " + utf16Units);
        System.out.println("Unicode code points: " + codePoints);
        System.out.println("UTF-8 bytes: " + utf8.length);

        // Assertions independent of the -ea flag.
        if (utf16Units != 3 || codePoints != 2
                || utf8.length != 5) {
            throw new AssertionError("Unexpected String semantics");
        }

        String roundTrip =
                new String(utf8, StandardCharsets.UTF_8);
        if (!text.equals(roundTrip)) {
            throw new AssertionError("UTF-8 round-trip failed");
        }

        System.out.println("PASS");
    }
}
~~~

APIs used:

- `String.length()`: number of **UTF-16 code units**, not necessarily the number of Unicode code points.
- `String.codePointCount(...)`: number of Unicode code points in a range.
- `String.getBytes(StandardCharsets.UTF_8)`: converts a string into bytes using an **explicitly declared** encoding.
- `new String(bytes, StandardCharsets.UTF_8)`: decodes UTF-8 bytes into a string.
- `String.equals(...)`: compares string content per contract.

No private field lookup is needed at all.

## 11. Compiling and Running the Fixed Version

~~~bash
javac --release 17 -d out src/PublicStringProbe.java
java -cp out PublicStringProbe
~~~

Expected output:

~~~text
UTF-16 code units: 3
Unicode code points: 2
UTF-8 bytes: 5
PASS
~~~

**Without `--add-opens`.** The code only calls public APIs supported by Java SE.

### 11.1. Why 3, 2, and 5?

The string consists of `A` and an emoji represented by a surrogate pair in UTF-16:

- `A` takes one UTF-16 code unit.
- The emoji takes two UTF-16 code units.
- Total `length()` = 3.
- In code points, the string has 2.
- In UTF-8, `A` is 1 byte and the emoji is 4 bytes, totaling 5.

This demonstrates that a public API must be chosen **by semantic requirement**, not by access to an internal byte array.

### 11.2. Code Points Are Not User-Perceived Characters

A grapheme cluster can contain multiple code points (e.g., a base character and combining marks). If the requirement is to count "visible characters," `codePointCount` is not sufficient in every language. In that case, an appropriate grapheme-boundary solution is needed, such as Java text APIs/Unicode libraries with verified support scope.

**There is no single one-to-one replacement for every misuse of `String.value`**; you must understand the original intent.

## 12. Before-and-After Comparison

| Criterion | Legacy reflection | Public API |
| --- | --- | --- |
| Accesses private JDK field | Yes | No |
| `setAccessible(true)` | Yes | No |
| Needs `--add-opens` on JDK 17/21 | May be needed for legacy code to run | No |
| Depends on `String` layout | Yes | No |
| Unicode/encoding semantics | Easy to misinfer | Explicit via APIs |
| JDK update compatibility | High risk | Follows Java SE API contract |
| Test/triage | Behavior hard to explain | Testable via input/output |
| Security and least privilege | Opens JDK package | No opening needed |

### 12.1. The Goal Is Reducing Privilege

Success is not merely "the exception disappeared." Success is **no longer having a reason to grant access to private internals**. A public API with clear business meaning prevents both encapsulation errors and coupling to implementation layouts.

## 13. Distinguishing `exports` and `opens`

In the Java Platform Module System (JPMS), these two mechanisms solve different problems:

| Mechanism | What does it allow? | Does it open private members for deep reflection? |
| --- | --- | --- |
| `exports p` | Lets other modules access public types/members of package `p` per access rules | Not automatically |
| `exports p to m` | Qualified public API export to module `m` | Not automatically |
| `opens p` | Allows runtime deep reflection into package `p` | Yes, per reflective access rules |
| `opens p to m` | Opens `p` only to module `m` | Yes, scoped only to target |
| `open module m` | Opens all packages of the module for deep reflection | Yes, very broad |
| `--add-opens=m/p=t` | Opens package `p` in module `m` to target `t` via launcher | Yes, scope depends on target |

**`exports` is not equivalent to `opens`.** Exporting a `public` class does not mean another class is free to read its `private` fields.

### 13.1. Deep Reflection Does Not Mean Calling a Public Method

Calling `customer.id()` is normal API access when the public type and method are properly exported. Calling `Customer.class.getDeclaredField("id")` followed by `setAccessible(true)` is a deep reflection request bypassing Java access checks.

In a stable design, prefer intentional public APIs. `opens` is meant for runtime frameworks that genuinely need reflective binding.

## 14. Lab B — Two Named Modules in One Application

In Lab A, the caller ran on the **classpath** and was therefore described as the `unnamed module`. In Lab B, we create **two named modules** to observe the error more clearly.

Goal:

- Module `com.example.model` owns the `Customer` object.
- Module `com.example.reader` uses `Customer`'s API.
- The package containing `Customer` is `exports`ed, but not `opens`ed.
- Reader code attempts to use reflection to read the `private id` field and receives `InaccessibleObjectException`.

Structure:

~~~text
reflection-lab/
└── modsrc/
    ├── com.example.model/
    │   ├── module-info.java
    │   └── com/example/model/api/Customer.java
    └── com.example.reader/
        ├── module-info.java
        └── com/example/reader/Main.java
~~~

Module/package names and paths are examples. This lab does not need Maven/Gradle; the modules are compiled with `javac --module-source-path`.

## 15. Declaring the Model-Providing Module

File `modsrc/com.example.model/module-info.java`:

~~~java
module com.example.model {
    exports com.example.model.api;
}
~~~

File `modsrc/com.example.model/com/example/model/api/Customer.java`:

~~~java
package com.example.model.api;

import java.util.Objects;

public final class Customer {
    private final String id;

    public Customer(String id) {
        this.id = Objects.requireNonNull(id);
    }

    public String id() {
        return id;
    }
}
~~~

In this module:

- `Customer` is a public class in an exported package.
- The constructor and `id()` are public APIs.
- Field `id` remains private and is not part of a reflective contract exposed to other modules.

There is no business reason forcing the consumer to read the field directly; `id()` is explicitly provided.

## 16. Creating a Consumer That Intentionally Violates Encapsulation

File `modsrc/com.example.reader/module-info.java`:

~~~java
module com.example.reader {
    requires com.example.model;
}
~~~

File `modsrc/com.example.reader/com/example/reader/Main.java`:

~~~java
package com.example.reader;

import com.example.model.api.Customer;
import java.lang.reflect.Field;

public final class Main {
    public static void main(String[] args) throws Exception {
        Customer customer = new Customer("C-100");

        Field field =
                Customer.class.getDeclaredField("id");
        field.setAccessible(true); // Deep reflection: rejected.

        System.out.println(field.get(customer));
    }
}
~~~

The consumer has `requires com.example.model`, so it can see the public class `Customer` in the exported package. However, `requires` and `exports` **do not make private fields accessible via `setAccessible(true)`**.

From the `reflection-lab` directory, with the `modsrc` structure created:

~~~bash
javac --release 17 \
  --module-source-path modsrc \
  -d mods \
  -m com.example.model,com.example.reader

java --module-path mods \
~~~

~~~text

  Unable to make field private final java.lang.String
  com.example.model.api.Customer.id accessible:
  module com.example.model does not
  "opens com.example.model.api"
~~~

This is an error **between two project-owned modules**, not an error caused by a private JDK field.

### 17.1. Why Is `exports` Not Enough?

`exports com.example.model.api` allows the consumer to call:

~~~java
new Customer("C-100").id()
~~~

It does not grant permission to bypass `private` access checks. To let external code use a value, the package owner must design an appropriate public API or decide on a scoped reflective openness policy.

## 18. Lab B — Primary Fix: Using Getter/Public API

Replace `modsrc/com.example.reader/com/example/reader/Main.java`:

~~~java
package com.example.reader;

import com.example.model.api.Customer;

public final class Main {
    public static void main(String[] args) {
        Customer customer = new Customer("C-100");
        System.out.println(customer.id());
    }
}
~~~

Keep both `module-info.java` files unchanged: the model still only `exports` the API package and **does not need `opens`**.

Recompile and run:

~~~bash
javac --release 17 \
  --module-source-path modsrc \
  -d mods \
  -m com.example.model,com.example.reader

java --module-path mods \
  --module com.example.reader/com.example.reader.Main
~~~

Expected output:

~~~text
C-100
~~~

No `--add-opens` and no new deep-reflection permission needed.

### 18.1. Why Is This Solution More Sustainable?

The module owning the type defines precisely what data is permitted to be exposed. Consumers do not depend on private field names, memory layouts, setters, constructor internals, or annotation metadata outside the API contract.

If validation, access control, or data masking needs to be added, the model module can implement it behind the method without forcing consumers to change reflection rules.

## 19. Lab B — When a Framework Truly Needs Reflection

Not every use case can be turned into a getter call. JSON serializers, ORM frameworks, dependency injection, test frameworks, or some component scanners may need to inspect/construct objects via reflection per framework contracts.

If **you control the model module** and **the framework genuinely requires deep reflection**, you can write a module descriptor that opens the package to the trusted module:

~~~java
module com.example.model {
    exports com.example.model.api;
    opens com.example.model.api to com.example.reader;
}
~~~

If the consumer still has the original reflection code from Lab B, re-running with the updated module descriptor can pass `setAccessible(true)` **without adding the JVM `--add-opens` flag**.

**However, note the distinction:** This approach **does not eliminate reflection**; it replaces a launcher override with a **permission declared at the module owner** and scoped to the target module.

### 19.1. Qualified `opens` Differs from `ALL-UNNAMED`

`opens com.example.model.api to com.example.reader` only opens the package to the specified module. It is not equivalent to opening all of `java.base/java.lang` to all unnamed modules.

Still, `opens` applies at the **package level**, not just to the single `id` field. You must therefore evaluate what data in the package becomes accessible via deep reflection.

### 19.2. Do Not Guess a Framework's Module Name

A framework might span multiple modules, run on the classpath/unnamed module, or have different package/module names across versions. Consult the **JPMS documentation of the exact framework in use** before adding qualified `opens`.

In particular, the syntax:

~~~text
opens com.example.model.api to ALL-UNNAMED;
~~~

is **not valid `module-info.java` syntax** just because `ALL-UNNAMED` has meaning in launcher flags. For unnamed modules, choose an appropriate packaging/opens model per policy, or avoid deep reflection.

## 20. Criteria for Choosing Between Public API and `opens`

| Scenario | Preferred option | Reason |
| --- | --- | --- |
| Business code wants to read object data | Public method/DTO/API | Deep access unnecessary |
| Code wants to serialize public data | Public serializer/record/API if framework supports | Explicit contract |
| Framework genuinely needs private field binding | Qualified `opens` on package-owning module where appropriate | Intentional permission scope |
| Framework demands private JDK internals | Upgrade framework or change technology | You do not own JDK packages |
| Unit test reads private field just to assert | Test via behavior/public contract | Avoid coupling to implementation |
| Need atomic update on class's own private state | Internal `Atomic*` or `VarHandle` | Keeps access where state is owned |
| Third-party agent opens JDK package to instrument | Find version/vendor-supported mode | Do not blindly broaden JVM policy |
| Plugin lacks public extension point | Design valid SPI/adapter | Do not depend on private implementation |

**Decision principle:** prioritize **eliminating the need** for deep reflection; if impossible, bound and explicitly own the access policy. Do not treat `opens` as a universal API design strategy replacing public contracts.

## 21. `setAccessible` and `trySetAccessible`

Java reflection provides:

~~~java
field.setAccessible(true);
~~~

and on supporting JDKs:

~~~java
boolean allowed = field.trySetAccessible();
~~~

`trySetAccessible()` can return `false` when access cannot be enabled, instead of throwing `InaccessibleObjectException` in corresponding situations. However:

- It **does not bypass module encapsulation**.
- It **does not supply data** or an alternative API on its own.
- A test merely seeing `false` does not solve the business requirement.
- Failures caused by other security controls may manifest differently across JDKs.

It can be useful when an optional feature is legitimately designed to fall back, yet it is **not a migration fix** if the code still depends on private JDK state.

### 21.1. Should You Catch `InaccessibleObjectException`?

Catching the exception intentionally to show a compatibility message or choose a fallback **preserving the semantic contract** can be valid. Catching and ignoring it:

~~~java
try {
    field.setAccessible(true);
} catch (RuntimeException ignored) {
    // Continues with unknown state.
}
~~~

is an anti-pattern. It hides the root cause and can cause subsequent logic to behave incorrectly.

## 22. `MethodHandles` Is Not a Default Backdoor

Java provides `java.lang.invoke.MethodHandles` for method/field access governed by access control. However:

~~~java
MethodHandles.privateLookupIn(Target.class, lookup);
~~~

is **not a way to bypass module boundaries**. It requires appropriate access/opens permissions between the caller and target module. Switching `setAccessible(true)` to `privateLookupIn` without changing the design may simply produce a different exception.

### 22.1. Using a Public Method via MethodHandle When Dynamic Access Is Needed

Example of a public Java API:

~~~java
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;

public final class PublicHandleDemo {
    public static void main(String[] args) throws Throwable {
        MethodHandle length = MethodHandles.publicLookup()
                .findVirtual(
                        String.class,
                        "length",
                        MethodType.methodType(int.class));

        int result = (int) length.invokeExact("Java");
        System.out.println(result);
    }
}
~~~

Output:

~~~text
4
~~~

This example requires dynamic invocation of a **public** member supported by the JDK; it does not access `String.value` and needs no `--add-opens`.

### 22.2. When to Use `VarHandle`?

`VarHandle` is appropriate when the code that owns the state needs typed variable access or atomic/memory-order operations per the Java API. It is not a license to modify private fields of the JDK or another module.

For an ordinary counter, `AtomicInteger` is usually simpler:

~~~java
import java.util.concurrent.atomic.AtomicInteger;

public final class Counter {
    private final AtomicInteger count = new AtomicInteger();

    public int incrementAndGet() {
        return count.incrementAndGet();
    }

    public int value() {
        return count.get();
    }
}
~~~

This code does not need to reflect into `AtomicInteger` internals or access private fields of another class.

## 23. When Errors Do Not Appear on Java 8 but Appear on Java 17

Before the module system, many JDK classes could be accessed via reflection and `setAccessible(true)` under certain security conditions. Starting in Java 9, JPMS introduced boundaries. After a transitional period permitting some illegal reflective access to ease migration, JDK 17 strongly encapsulated JDK internals per JEP 403.

That does not mean:

- All reflection is banned.
- Reflection on legitimate public APIs is banned.
- Reflection on your own code always fails.
- `--add-opens` is the only choice.
- JDK 17 introduced bugs that "broke" class `String`.

Instead, old code relied on **an unguaranteed access permission**, and the runtime change exposed that dependency.

### 23.1. `--illegal-access=permit` Is No Longer a Solution

Some old migration guides recommend:

~~~text
--illegal-access=permit
~~~

Since JDK 17, this option has become obsolete/no longer permits relaxed strong encapsulation as before. Its exact status in newer releases must be checked in launcher documentation, yet **never use it as a fix** for JDK 17/21.

### 23.2. Do Not Draw Conclusions from a Single JVM

To reproduce reliably, record the Java feature release, full patch/build, vendor, module/classpath mode, and JVM flags. If libraries use native agents or multiple class loaders, they can also affect behavior.

## 24. Inventorying Reflection Before Refactoring

A large application can have many deep reflection sites, from internal code to third-party libraries.

Common sources:

- `Field.setAccessible(true)`, `Method.setAccessible(true)`, `Constructor.setAccessible(true)`.
- `AccessibleObject.trySetAccessible()`.
- `Class.getDeclaredFields()/getDeclaredMethods()`.
- `MethodHandles.privateLookupIn(...)`.
- Framework utility methods such as `ReflectionUtils`.
- ORM/serialization/deserialization targeting private fields.
- Dependency injection and test/mocking tools.
- Java agents or bytecode instrumentation.
- Libraries using `sun.*`, `com.sun.*`, or JDK internals.
- JVM startup flags set in containers/CI.

### 24.1. Scanning Source Code with ripgrep

If the project has `rg`:

~~~bash
rg -n -- \
  'setAccessible\(|trySetAccessible\(|getDeclaredField|privateLookupIn|--add-opens|--illegal-access|sun\.|com\.sun\.' \
  .
~~~

The output is only a **candidate list**. Not every `getDeclaredField` is wrong; nor does every reflection call appear directly in source text. Embedded libraries or dynamically generated bytecode may not show up in text search.

### 24.2. Windows PowerShell

An example searching common text files:

~~~powershell
Get-ChildItem -Recurse -File -Include *.java,*.xml,*.gradle,*.properties,*.yaml,*.yml |
    Select-String -Pattern 'setAccessible\(', 'trySetAccessible\(', '--add-opens'
~~~

This is an illustrative command for authorized internal project inventory. For large repositories, restrict directories to avoid scanning build outputs/dependency caches unnecessarily.

## 25. Does `jdeps --jdk-internals` Help Detect Reflection?

`jdeps` can find **static references** to JDK internal APIs:

~~~bash
jdeps --jdk-internals path/to/application.jar
~~~

If the JAR is a multi-release JAR, pass the matching release view:

~~~bash
jdeps --multi-release 17 \
  --jdk-internals path/to/application.jar
~~~

However, code like:

~~~java
Class.forName("java.lang.SomeInternalType");
~~~

or:

~~~java
String name = "value";
String.class.getDeclaredField(name);
~~~

may not show up fully in static dependency analysis. Therefore, combine:

1. Source search.
2. Dependency/agent inventory.
3. Runtime logs with original stack traces.
4. Real tests on the new JDK **without additional package-opening permissions**.

Do not treat an empty `jdeps` report as proof of "zero illegal reflection."

## 26. Tracing the Failing Third-Party Library

In practice, the stack trace might show:

~~~text
java.lang.reflect.InaccessibleObjectException: ...
    at java.base/java.lang.reflect.AccessibleObject...
    at third.party.reflect.ReflectionHelper...
    at third.party.serializer.Serializer...
    at com.example.app.Main...
~~~

In that case, editing `Main` may not suffice. Identify:

- Which library triggers the `setAccessible` call.
- The actual version running, including transitive dependencies.
- Whether the artifact is shaded inside another JAR.
- Whether the library vendor offers a version supporting Java 17/21.
- Whether the framework has a mode using public getters, constructors, records, or explicit adapters.
- Whether the library requires `opens` on **application-owned packages** rather than opening JDK internals.
- Whether multiple agents/bytecode transformers touch the same class.

### 26.1. Priority Workflow

1. **Upgrade the library** to a version officially supporting the target JDK.
2. Use official public extension points/configuration.
3. Refactor DTOs/models/serializers so they do not require reading private JDK internals.
4. If reflection is still needed in a **self-owned module**, consider qualified `opens`.
5. Use a clearly scoped flag only temporarily during an approved migration; set a removal date.

Do not arbitrarily override ASM/Byte Buddy on the application classpath when an agent already shades those dependencies; doing so may fail to fix the library actually executing.

## 27. Reflection, Serialization, and DTOs: Designing Replacement APIs

An old serialization layer might scan all fields and write values directly. For classes you own, there are multiple alternatives:

- Public getters/constructors per framework convention.
- Immutable DTOs with canonical constructors.
- Records on appropriate Java releases.
- Explicit mapping functions.
- Custom serializers/deserializers using public APIs.
- Framework-supported annotations on permitted fields/methods.
- Qualified `opens` if the framework genuinely requires deep field binding in a named module.

### 27.1. Mapping Example Without Private Reflection

~~~java
public final class CustomerDto {
    private final String id;
    private final String displayName;

    public CustomerDto(String id, String displayName) {
        this.id = id;
        this.displayName = displayName;
    }

    public String getId() {
        return id;
    }

    public String getDisplayName() {
        return displayName;
    }
}
~~~

A mapper invoking `getId()` and `getDisplayName()` has an explicit public API. Depending on the framework, configuring getter/constructor-based serialization instead of private-field reflection can remove the need for `opens`.

### 27.2. Caution with Semantic Compatibility

If the serializer previously read all private fields (including secrets, caches, or internal flags), switching to public getters can alter the JSON/schema. Cross-check **golden fixtures**, versioned API contracts, and stored data. Removing `--add-opens` must not accidentally leak data or break the wire protocol.

## 28. Reflection in Unit Tests: Fix Test Design Instead of Opening the JDK

A unit test might use reflection to read a private field solely to inspect implementation:

~~~java
Field field =
        SomeService.class.getDeclaredField("cache");
field.setAccessible(true);
Object cache = field.get(service);
~~~

If private state is an implementation detail, a better approach is usually **testing observable behavior**:

- Cache hits reduce calls to the dependency.
- Validation handles boundary inputs properly.
- The service returns expected results when state changes via public APIs.
- Atomicity/concurrency is verified via contract and synchronization tests.

If tests need injection or observability to inspect a complex class, consider constructor injection, a test fixture/seam with proper package/module visibility, or a clearly designed test-specific interface.

### 28.1. Mockito/Byte Buddy Must Also Be JDK-Compatible

Some test tools use Java instrumentation and dynamic attach. On JDK 21, there is the dynamic agent loading warning context from JEP 451; that is **not the same** as `InaccessibleObjectException` caused by `String.value`.

If errors originate from mocking/bytecode parsing, inspect agent modes, library versions, class-file support, and vendor guidance. Do not make adding `--add-opens` the blanket answer to every test failure.

## 29. `--add-opens`, `--add-exports`, and `--add-reads` Are Different

| Flag | Role | Does not automatically fix |
| --- | --- | --- |
| `--add-opens=M/P=T` | Grants target `T` deep reflection into package `P` of module `M` | Missing class/method, malformed bytecode |
| `--add-exports=M/P=T` | Grants target access to public types in an unexported package | Deep reflection to private members |
| `--add-reads=M=T` | Adds a module readability edge for module `M` to read module `T` | Does not open private fields |
| `--enable-native-access=...` | Mechanism controlling native access on supporting JDKs | Does not open Java packages for deep reflection |

Examples:

~~~text
--add-opens=java.base/java.lang=ALL-UNNAMED
--add-exports=java.base/jdk.internal.misc=ALL-UNNAMED
~~~

Both options have different permission scopes and both carry risk when exposing JDK internals to code not designed to depend on them. **Adding these lines in production is not recommended** without a specific justification and approval.

### 29.1. Using Syntactically Valid Flags for the Wrong Target

If a stack trace reports:

~~~text
java.lang.NoSuchMethodError: ...
~~~

then `--add-opens` cannot recreate the missing method. If `VerifyError` reports invalid stack map frames, `--add-exports` will not fix the bytecode either. Select a flag only when **the error is genuinely module access** and a removal roadmap exists.

## 30. Finding Hidden Flags in the Launch Process

An application may appear to "not need `--add-opens` locally" while the JVM is actually receiving it from somewhere else.

Places to inspect:

| Configuration location | Example flag sources |
| --- | --- |
| Java launcher | Command-line options |
| Environment | `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS` |
| Gradle | `org.gradle.jvmargs`, `Test.jvmArgs`, run task |
| Maven | Surefire/Failsafe `argLine`, `.mvn/jvm.config` |
| IDE | Run/Debug configuration, test runner |
| Docker | Entrypoint, command, environment |
| Kubernetes | Pod spec, Helm chart, mutating admission/injection |
| App server | Server-specific JVM options |
| Platform agent | JVM args injected by observability/security |

### 30.1. The Local vs. CI Discrepancy Problem

~~~text
Developer JVM: --add-opens present via IDE
CI JVM:        --add-opens present via Test.jvmArgs
Production:    no --add-opens
~~~

Local and CI both pass while production still hits `InaccessibleObjectException`. Therefore, migration testing must include **at least one execution path without the legacy package-opening flags**, on a production-equivalent artifact/runtime.

## 31. Example: Removing Flags from Gradle Tests

Suppose the old configuration:

~~~groovy
tasks.withType(Test).configureEach {
    jvmArgs '--add-opens=java.base/java.lang=ALL-UNNAMED'
}
~~~

After fixing code/frameworks:

~~~groovy
tasks.withType(Test).configureEach {
    // Do not add access permissions to private JDK internals.
    // Keep other JVM options only if there is a specific reason.
}
~~~

This illustrates the difference rather than a complete Gradle configuration. When changing it, check `org.gradle.jvmargs`, test forks, IDE runners, and other plugins to see if they inject flags.

### 31.1. The Gradle Daemon and Test JVM Can Be Two Different Processes

A flag in `org.gradle.jvmargs` can affect the Gradle daemon; a flag in `Test.jvmArgs` affects the forked test JVM. Do not remove it from one place and conclude no process still carries the flag.

### 31.2. Engineering Guidance Is Verification, Not Just Text Editing

After deleting the flag, run the suite on the target JDK and check for reflection errors. If CI remains green because a plugin injects the flag automatically, the report must identify the exact injection source before declaring the migration complete.

## 32. Example: Removing Flags from Maven Tests

An old configuration might use:

~~~xml
<configuration>
  <argLine>--add-opens=java.base/java.lang=ALL-UNNAMED</argLine>
</configuration>
~~~

Once code/frameworks no longer need this access, remove the option from `argLine` while **preserving other necessary test options** such as coverage agents, memory settings, or intentional JVM properties.

### 32.1. Caution with JaCoCo

JaCoCo or another plugin may set/append the `argLine` property. Replacing the entire property without understanding lifecycle bindings can break coverage collection. Edit configuration according to the exact versions of Maven Surefire/Failsafe/JaCoCo in use.

### 32.2. Maven Runtime Is Not Necessarily the Test Runtime

`mvn -version` reports the JVM running Maven, whereas Surefire may fork a different JDK via toolchains. Capture runtime fingerprints directly **inside the test JVM** to prove results on the exact release/vendor.

## 33. Removing Flags in Containers and Kubernetes

A JVM running in a container can receive flags from:

~~~text
Dockerfile ENTRYPOINT
startup.sh
JAVA_TOOL_OPTIONS
JDK_JAVA_OPTIONS
Kubernetes container args
Helm values
platform-injected javaagent startup config
~~~

After refactoring reflection:

1. Identify the authoritative flag declaration site.
2. Remove the exact options no longer needed.
3. Build a new immutable runtime image/deployment manifest.
4. Inspect the full redacted JVM command line and environment.
5. Run smoke/integration tests on the final image.
6. Compare logs/metrics/traces before and after.
7. Canary first, then ramp up rollout.

### 33.1. Do Not Only Edit the Shell Script in the Repository

If the platform automatically injects `--add-opens` via an agent injector, an edited script does not prove the production process no longer receives the flag. Verify **effective runtime arguments** from a live deployment or an equivalent staging replica.

## 34. Regression Testing: Same Behavior, No Internal Opening Permissions

Define **two test groups**:

**Group 1 — Contract tests**

- String processing/encoding handles Unicode accurately.
- Serializer/mapper output is unchanged outside approved changes.
- Object construction, validation, and error handling behave properly.
- Reflective frameworks continue functioning on legitimately declared modules/packages.
- Key workflows do not fail when classes are loaded lazily.

**Group 2 — Runtime configuration tests**

- Full target JDK build has been identified.
- Test JVM does not carry old `--add-opens` workarounds.
- Classpath/module path matches deployment.
- No illegal reflective access warnings/errors appear from supported dependencies.
- Agents/native libraries do not silently demand other broad flags.
- No functional/performance regressions from changing serializers/frameworks.

### 34.1. A Test Checking Only Exit Code Is Not Enough

`PublicStringProbe` printing `PASS` is a small smoke test. Real applications must test every call path likely to touch reflection: startup, first request, batch scheduling, serializer edge cases, proxy initialization, and long-running workloads.

### 34.2. Negative Tests Must Prove the Flag Is Absent

To avoid a "false pass," create a CI job launching a **new process** with a controlled JVM argument list, enforcing a policy that forbids `--add-opens` for the target JDK packages scheduled for removal. Do not merely delete the flag from a script while leaving `JAVA_TOOL_OPTIONS` injecting it.

If the product still supports Java 8, design a separate matrix and compile sources with the corresponding compatibility level. The JPMS lab does not run on Java 8 because Java 8 lacks the Java 9+ module system. Do not use the fact that legacy Lab A could access a private field on Java 8 as a valid excuse to keep that code on JDK 17+.

## 36. The Pitfall of Trying to Fix Errors with `open module`

Changing:

~~~java
module com.example.model {
    exports com.example.model.api;
}
~~~

to:

~~~java
open module com.example.model {
    exports com.example.model.api;
}
~~~

can make many reflective accesses succeed. Yet this is a **decision to open every package in the module for deep reflection**, far broader than qualified `opens`.

If only one serializer module needs to read one DTO package, prefer a narrower approach. If the DTO has a suitable public API, avoid `opens` altogether.

**Do not use `open module` solely to silence a stack trace** without evaluating all other private members in the module.

## 37. Notes When Moving from Classpath to Module Path

A library that ran on the classpath could perform deep reflection into application classes without hitting the same JPMS barriers as named modules. Moving to the module path with explicit `module-info.java` alters access checks.

Scenarios:

- Both consumer and target are unnamed modules.
- Target is in a named module, consumer is in an unnamed module.
- Both are named modules.
- Target is a JDK module, consumer is an app/framework module.
- Application uses custom class loaders, agents, or nested JAR launchers.

An error appearing only on the module path is not necessarily caused by a JDK update; it can stem from changing the **packaging mode**. Record the exact command line, module graph, and class sources.

### 37.1. `module-info.java` Is a Runtime Contract

Adding `exports`/`opens` must be reviewed as an access-boundary change, not just "adding a dependency to quiet the compiler." If the module is a public library, changing the descriptor impacts consumers and framework behavior.

## 38. Errors Easily Confused with `InaccessibleObjectException`

| Error | Characteristics | First resolution direction |
| --- | --- | --- |
| `InaccessibleObjectException` | Deep reflection rejected by module access checks | Public API or scoped opens if package is owned |
| `IllegalAccessException` | Reflection caller lacks access per API/checks | Check public/member access and module contract |
| `IllegalAccessError` | Bytecode linkage access violation | ABI/module exports and runtime class versions |
| `NoSuchFieldException` | Field does not exist under looked-up name | Remove private layout coupling, check source |
| `NoSuchMethodError` | Runtime method descriptor mismatch | Dependency graph/binary compatibility |
| `NoClassDefFoundError` | Class could not be defined or initialization already failed | First error, classpath/module path |
| `VerifyError` | JVM verifier rejects bytecode | Transformer/generator/frames |
| `UnsupportedClassVersionError` | JVM does not support class-file major version | Compiler `--release` and runtime |
| `UnsatisfiedLinkError` | JNI/native library or symbol binding | OS/ABI/native dependency |

When an exception occurs inside a framework stack, inspect the **first cause** and exact class/module before fixing. A library can hit `NoClassDefFoundError` after a static initializer threw `InaccessibleObjectException` or another error; preserve the initial startup logs.

## 39. Triaging from an Actual Stack Trace

An analysis workflow:

1. **Select the first error** along with its `Caused by` chain; not just the final startup exception.
2. **Identify the member** being accessed: field, method, or constructor; which class/package it belongs to.
3. **Identify the caller** in the stack trace: application code, framework, test tool, or Java agent.
4. **Identify the owner and target modules** from the message.
5. **Inspect flag sources** for effective JVM options (CLI, IDE, CI, env, container).
6. **Create a minimal reproduction** in a class/test without needing full application state.
7. **Run a control check** with `--add-opens` only in an authorized test environment.
8. **Find public APIs or vendor-supported library upgrades**.
9. **Fix the code or scoped module descriptor**, then remove the flag workaround.
10. **Re-run regression tests** on the final runtime image and check observability.

### 39.1. Do Not Batch-"Swap a Flag and Hope"

If the error states:

~~~text
module java.base does not "opens java.util" to module xyz
~~~

then adding:

~~~text
--add-opens=java.base/java.lang=ALL-UNNAMED
~~~

will not necessarily affect that error because **both the package and target differ**. Yet the right solution is still not automatically opening both packages; determine why the library accesses internals.

## 41. Anti-Patterns to Avoid

**"Opening `java.base/java.lang` to all unnamed modules is harmless."** False: it grants deep reflection permissions into a core JDK package to all code within the target scope; it weakens encapsulation and offers no guarantee of future compatibility.

**"Replacing `setAccessible` with `privateLookupIn` bypasses JPMS."** False: MethodHandles are also subject to module access restrictions.

**"Using `trySetAccessible` returning false is a complete fix."** False if the business path still needs that data and lacks an accurate fallback.

**"`exports` is enough to access private fields."** False: `exports` governs access to public members, not granting deep reflection.

**"`opens ... to ALL-UNNAMED` can be written in `module-info.java`."** Not valid module descriptor syntax.

**"Add `open module` for speed."** Can over-expose the permission surface.

**"A class without module-info is exempt from JPMS."** Incorrect: classpath code still sits in an unnamed module; JDK named modules still enforce their openness.

**"A test passing with `--add-opens` proves the code is compatible with the new JDK."** Insufficient; the code still depends on JDK internals.

**"Reflection into `String.value` is faster than public APIs so it's worth keeping."** Unsubstantiated without benchmarks/semantic checks, and carries high correctness/compatibility risk.

**"JDK 17 bans all reflection."** False: public reflection is allowed per access rules, and module owners themselves can open packages where justified.

**"Deleting the flag from Gradle finishes the job."** Not if Maven/IDE/container/`JAVA_TOOL_OPTIONS` still injects it.

**"Every `IllegalAccessError` is caused by missing `--add-opens`."** Incorrect; linkage access and deep reflection are two distinct checks.

**"We can disable agents/coverage to stop the error without impacting release quality."** Not if they are mandatory gates; upgrade or properly configure those tools.

**"Using public getters always keeps JSON identical to before."** Not guaranteed; test serialization/schema contracts.

**"Switching to qualified `opens` means reflection is gone."** Incorrect: it only changes where the permission is declared.

## 43. Self-Check Questions

**1. Why can `getDeclaredField("value")` succeed while `setAccessible(true)` fails?**

Because querying metadata about a field does not automatically grant the caller deep reflection rights to bypass access checks. JPMS can deny opening access to a JDK package.

**2. Does `--add-opens=java.base/java.lang=ALL-UNNAMED` make `String.value` a guaranteed API?**

No. It only opens reflection permission within the target scope; the private field's name/type/layout still has no compatibility contract.

**3. If a module exports a package, can you reflect on private fields of a public class?**

Not by default. Valid openness for deep reflection is required—or better yet, an appropriate public API.

**4. Does switching from the flag to `opens package to module` eliminate reflection?**

No. It removes the need for a launcher override in a well-structured modular architecture, yet still performs deep reflection with a declared permission.

**5. Does `MethodHandles.privateLookupIn` bypass module boundaries?**

No. It requires valid access permissions, including inter-module `opens` where API rules demand it.

**6. Why does a green CI test run not prove production needs no flag?**

Because flags can be injected by IDEs/test runners/build plugins/environments/container platforms. Effective JVM arguments must be verified and production-equivalent artifacts tested.

**7. When should business code be fixed versus upgrading a library?**

If reflection is in your own code, prefer public APIs/redesign. If it originates in a dependency, identify the version, find a vendor-supported release or official configuration; do not reach into private JDK fields externally.

**8. Why must Unicode/serialization be tested after removing reflection?**

Because public APIs have different semantic contracts than private layouts. A fix that "eliminates the exception" can still change encoding, data shape, or business behavior.

## 46. Conclusion

`InaccessibleObjectException` in Java Advance Compatibility Migration typically signals that code is requesting **deep reflection beyond allowed module access boundaries**. In Lab A, accessing `String.value` failed because `java.base` does not open `java.lang` to the caller; enabling `--add-opens` isolated the cause but did not turn private JDK internals into a stable API. The sustainable fix is migrating to `String.length()`, `codePointCount()`, `getBytes(StandardCharsets.UTF_8)`, or the public API matching the requirement.

In Lab B, the consumer attempted to reflect on `Customer.id` across two named modules. The preferred fix is calling the **public method `Customer.id()`**, keeping the module descriptor exporting only the required contract. When a framework genuinely requires deep reflection into a package you own, qualified `opens` can replace broad launcher overrides, yet it remains a **scoped permission**, not the elimination of reflection.

Completing the migration means **removing dependencies on private internals, removing obsolete `--add-opens` workarounds, verifying effective JVM arguments in a real environment, and running regression tests that preserve semantics**. That way, the application does not merely "get past an exception," but becomes more resilient to JDK updates, module boundaries, and system security requirements.
