# Migration Scope: JDK, Build Tools, Dependencies, and Frameworks

## 1. Properly Understanding the Scope of a Java Compatibility Migration

Java compatibility migration is the process of moving an application or a module system from the current Java platform to a target platform while keeping the source code, build process, libraries, frameworks, and runtime environment continuing to work properly.

The migration scope therefore does not stop at changing the JDK version. An application may compile with the new JDK yet still fail to build because a Gradle or Maven plugin is not yet compatible; build successfully yet fail to start because the framework requires a different library version; or start normally yet change behavior when handling HTTP, transactions, JSON, dates and times, or configuration.

When determining the scope, you need to look at the system in terms of interrelated layers:

```text
Java source code and bytecode
          │
          ▼
JDK, compiler, and JVM
          │
          ▼
Build tools, plugins, and packaging process
          │
          ▼
Direct dependencies and transitive dependencies
          │
          ▼
Frameworks, adapters, and integration libraries
          │
          ▼
Deployment and operations environment
```

These layers are not independent. The framework version often constrains the minimum JDK version; the framework in turn manages the versions of many dependencies; a build plugin may require a different JDK than the one the application uses at runtime. Therefore, the scope must include both directly affected components and components that depend on that change.

## 2. JDK: Java Version, Compiler, and JVM

The JDK is a central part of the migration scope, but it is necessary to distinguish three concepts that are often conflated:

- **JDK used to run the build tool:** The JVM that launches Gradle, Maven, compiler plugins, and other build tools.
- **Java toolchain used for compilation:** The JDK that provides `javac`, `javadoc`, and corresponding tools to generate bytecode.
- **JRE/JVM used to run the application:** the actual environment that executes the packaged bytecode.

These three roles can use the same version, but they do not have to be identical in every configuration. A build can run with a new JDK while the compilation toolchain targets a lower Java version. Conversely, building successfully with a new JDK does not prove that the production server already has an appropriate runtime.

### 2.1. Source Code and Bytecode Compatibility Levels

When changing the JDK, you need to clearly determine whether the application is changing the Java language or only changing the compilation and runtime environment.

| Component | Questions to Determine |
|---|---|
| Source compatibility | Is the current source code still valid for the target compiler? Are there syntax, annotations, or APIs that need to be changed? |
| Language level | Is the project intentionally using features of the new Java version? |
| Bytecode target | Can the generated bytecode run on the committed minimum JVM version? |
| JDK API | Do the APIs currently in use still exist, remain supported, and preserve the desired behavior? |
| Runtime behavior | Does the new JVM change behavior related to encoding, reflection, class loading, garbage collection, threads, or security? |

For example, `javac`'s `--release` helps restrict both the bytecode level and the set of Java APIs allowed to be used according to the target version. Setting only `sourceCompatibility` and `targetCompatibility` does not always fully replace the meaning of `--release`. With Gradle, you should configure the Java toolchain and the release level consistently; with Maven, you need to check the compiler plugin configuration and the actual JDK on which Maven is running.

Gradle configuration example:

```groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 21
}
```

Maven Compiler Plugin configuration example:

```xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
</properties>
```

The numbers in the examples only illustrate how to declare them. Actual versions must be taken from the baseline and target chosen by the project.

### 2.2. APIs, Module System, and JVM Behavior

Beyond language syntax, the JDK scope needs to review removed APIs, internal APIs that were previously accessed directly, access permission changes caused by the Java Platform Module System, reflection mechanisms, and legacy JVM options.

Some signs that need investigation include:

- Source code or libraries accessing classes in internal packages such as `sun.*` or `com.sun.*`.
- The application relying on reflection to access non-public members.
- Legacy JVM arguments that are no longer recognized or have different meanings.
- Libraries using class loading, instrumentation, proxy, or serialization mechanisms that are sensitive to the runtime version.
- Changes in TLS, certificates, cryptographic algorithms, or security policies affecting outbound connections.

You should not automatically add options to open modules or lower security levels just to make errors disappear. Each temporary compatibility option needs a reason, an applicability scope, and a removal plan.

### 2.3. Runtime Environment

The JDK scope also includes how the runtime is distributed and installed: the JDK/JRE distribution used, vendor, operating system, CPU architecture, container image, heap configuration, memory limits, and JVM flags. If production runs in containers, both the base image and how the container allocates resources to the JVM must be checked. A local machine having a new JDK does not prove that the production image has been updated.

## 3. Build Tools: Gradle, Maven, and the Entire Build Chain

Build tools are responsible for turning source code into testable and deployable artifacts. A JDK migration can expose compatibility limits in wrappers, plugins, custom tasks, or auxiliary tools.

The build tool scope needs to inspect at least the following components:

| Component | What to Check |
|---|---|
| Gradle Wrapper / Maven Wrapper | The wrapper version locked in the repository, its ability to run on the target JDK, and how the distribution is downloaded. |
| Build tool runtime | The JDK version used to launch Gradle or Maven. |
| Compiler plugin | The ability to invoke the target compiler and configure source/release/target. |
| External plugins | Spring Boot, Kotlin, Checkstyle, SpotBugs, JaCoCo, code coverage, packaging, publishing, and other plugins. |
| Annotation processors | The ability to run on the target JDK and compatibility with the new compiler. |
| Custom tasks | The Gradle/Maven APIs used, and how files, processes, configuration, and the task graph are accessed. |
| Test engine | JUnit Platform, test frameworks, mocking frameworks, and test runner plugins. |
| Code generation | OpenAPI, protobuf, QueryDSL, MapStruct, or other code generation tools. |
| Packaging and publishing | JAR/WAR, executable archives, metadata, manifests, signing, and publication. |

### 3.1. Distinguishing the JDK Running Gradle from the Project Toolchain

The Gradle Wrapper locks the project's Gradle version, but it does not automatically mean every task compiles with the same JDK. The Gradle daemon needs a compatible JVM to run; the Java toolchain can select a separate JDK for compile, test, or javadoc.

Therefore, during migration, both sides need to be checked:

1. Whether the Gradle version can launch on the JDK selected for the build.
2. Whether the compile/test tasks use the right toolchain and the right target bytecode level.

With Maven, you need to check the JDK running Maven, Maven Wrapper, Maven Compiler Plugin, Surefire/Failsafe, and the plugins involved in packaging. `maven.compiler.release` only controls the compilation level; it does not by itself change the JDK launching Maven.

### 3.2. Plugins and Tasks Are Part of the Scope

A build can fail before compiling source code if a plugin is incompatible with the new Gradle, Maven, or JDK version. Less-noticed plugins such as quality check, report generation, code generation, image packaging, and artifact publishing plugins can also block the pipeline.

You should not check only the main build file. You need to trace plugins declared in `plugins`, `buildscript`, parent POMs, Maven profiles, convention plugins, shared build logic, and indirectly applied scripts. If the repository has multiple modules, identify which modules use separate plugins or toolchains.

### 3.3. Builds Must Be Reproducible

A migration is only reliable when build results are reproducible in CI environments and supported development environments. Therefore, the scope should record the wrapper, toolchain, dependency repositories, required environment variables, and standard build commands. Avoid relying on an implicitly installed JDK on a personal machine or plugin versions that are not explicitly locked.

## 4. Dependencies: Direct and Transitive Libraries, and Version Management

Dependencies are the libraries and artifacts that a project needs to compile, test, run, or package. The migration scope must include direct dependencies declared by the project and transitive dependencies pulled in through other libraries.

For example, an application declaring a framework starter might not directly declare an HTTP client, JSON mapper, logging implementation, or validation library. However, those libraries are still on the runtime classpath and can be affected by JDK or framework changes.

### 4.1. Categorizing Dependencies

Dependencies should be categorized by intended use to avoid missing components:

- **Compile/API:** libraries appearing in data types, public signatures, or compiled source code.
- **Runtime:** libraries needed when the application starts up or processes business logic.
- **Test:** JUnit, Mockito, AssertJ, test containers, and testing support libraries.
- **Build-time:** annotation processors, plugins, generators, and tools invoked during the build process.
- **Provided/Container:** libraries provided by the deployment environment, such as the Servlet API in some WAR models.
- **Optional/Feature-specific:** libraries used only when a specific feature or module is enabled.

This categorization helps identify whether an error occurs at the compile, test, startup, or runtime stage; it also helps avoid mistakenly packaging libraries that the container already provides.

### 4.2. Transitive Dependencies and Version Conflicts

A library can pull in many other dependencies. Two dependency branches may request different versions of the same artifact. The build tool will apply version resolution rules, but successful resolution does not guarantee that the libraries are binary- or behavior-compatible.

During migration, you need to:

1. Export the dependency tree or dependency insight for important configurations.
2. Identify legacy libraries, libraries with overlapping functionality, superseded dependencies, and dependencies that are now only pulled in indirectly.
3. Check which dependencies have JDK, framework, or platform API constraints.
4. Cross-check the actual versions after applying BOMs, constraints, dependency management, exclusions, and version catalogs.
5. Check all of the compile classpath, runtime classpath, and test classpath.

You should not resolve every conflict by forcing the latest version. A new version might require different APIs, change behavior, or not be in the version set supported by the framework.

### 4.3. BOM and Version Management Sources

A Bill of Materials (BOM) defines a set of dependency versions designed to work together. Frameworks often provide their own BOM or dependency management. When upgrading a framework, review the set of versions managed by the framework before overriding individual dependencies.

If the project explicitly declares a version for a library managed by a BOM, clearly identify the reason. An inappropriate override can create an untested version combination. For a multi-module repository, standardize where versions are managed to avoid each module picking a different version unintentionally.

### 4.4. API, License, and Security

The dependency scope also includes changes to packages, classes, methods, generic signatures, annotations, serialization formats, licenses, and security vulnerabilities. A dependency version change can alter the APIs that the project's source code calls, or alter data written/read between application versions.

For libraries affecting protocols or persistent data, you need to determine backward and forward compatibility: whether the new version can read old data, whether other services continue to understand the new payload, and whether rollback remains feasible.

## 5. Frameworks: Application Platform and Related Integrations

Frameworks provide the structure and execution mechanisms for an application. A framework migration usually has a broader scope than changing a single dependency because frameworks define many shared contracts: configuration, lifecycle, dependency injection, transactions, web stack, persistence, security, and system observability.

In a Java application, groups of frameworks and foundational libraries may include:

- Application frameworks such as Spring Framework and Spring Boot.
- Web stacks such as Servlet API, Spring MVC, WebFlux, or other HTTP frameworks.
- Persistence such as Jakarta Persistence/JPA, Hibernate, and JDBC.
- Serialization such as Jackson, JSON-B, or XML libraries.
- Security such as Spring Security, OAuth/OIDC clients, and cryptography libraries.
- Validation such as Jakarta Bean Validation and corresponding implementations.
- Messaging and integration such as Kafka, AMQP, JMS, or HTTP clients.
- Logging, metrics, tracing, and health checks.
- Testing frameworks and integration testing.

Not every project uses all of these groups. The actual scope must be based on the components present in the project's dependency graph, configuration, and source code.

### 5.1. Compatibility Between Frameworks and the JDK

Each framework version typically specifies a minimum Java version, supported foundational library versions, and versions of integration modules. When choosing a target JDK, you must cross-check it against the intended framework version.

If the target JDK is newer than the framework's minimum requirement, that only shows the framework can accept that Java level according to its support policy; you still need to check specific integration libraries, plugins, and features. Conversely, upgrading a framework may force upgrading the JDK beforehand or simultaneously.

### 5.2. Namespace and Platform API Changes

An important example is the transition from the Java EE namespace `javax.*` to the Jakarta EE namespace `jakarta.*` across the corresponding platform generations. This is a change in package names and the API ecosystem, not merely changing a dependency version.

When a target framework requires the Jakarta namespace, you need to check consistently:

- Imports and annotations in source code.
- Servlet, Persistence, Validation, and other Jakarta APIs.
- Corresponding runtime implementations.
- Transitive dependencies and integration libraries still using the old namespace.
- Configuration, XML descriptors, generated sources, and test fixtures.

You cannot mechanically replace all `javax` strings with `jakarta`, because not every package starting with `javax` belongs to the API group moving to Jakarta. You must base this on the specific APIs and the target framework version.

### 5.3. Default and Behavioral Changes

A new framework version may keep the same API names while changing default behavior. Areas that commonly need attention include:

- How beans are registered, component scanning, auto-configuration, and configuration ordering.
- Conditions for activating configuration based on classpath or properties.
- Transaction boundaries, propagation, rollback, and exception handling.
- HTTP mapping rules, content negotiation, validation, and error responses.
- Authentication, authorization, CSRF, CORS, and filter chain mechanisms.
- Entity mapping, lazy loading, query generation, and schema handling.
- JSON naming, date/time formats, null handling, and polymorphic serialization.
- Logging levels, metric names, tracing propagation, and health endpoints.

Therefore, checking compilation only confirms partial compatibility. There need to be tests focused on the contracts that the application provides and consumes.

### 5.4. Configuration and Integrations Outside the Framework

Frameworks typically read configuration from YAML, properties, environment variables, command-line arguments, or secret stores. When upgrading versions, property names, data types, default values, and configuration locations can change. You need to review configuration by environment, profiles, environment variables in CI/CD, container configuration, and configuration provided by the deployment platform.

Integration modules must also be treated as part of the framework: database drivers, migration tools, cache providers, message broker clients, observability agents, application servers, and cloud libraries. A compatible framework core does not guarantee that every external adapter is also compatible.

## 6. Deployment Environment and Software Supply Chain

The migration scope should follow the application to where it actually runs. If only source code and build scripts are updated while the old deployment environment is kept unchanged, the application may continue running on an unsupported runtime.

Points to include in scope when relevant:

- Dockerfiles, base images, JRE/JDK images, and CPU architectures.
- Application servers or servlet containers if the application does not package its own runtime.
- Kubernetes manifests, startup commands, readiness/liveness probes, and resource limits.
- CI workflows, runner images, Gradle/Maven caches, and JDK configuration.
- Shell/PowerShell scripts, database migration tools, and operations tools.
- Environment certificate stores, TLS, proxies, timezones, locales, and encodings.
- Processes for building, scanning, signing, publishing, deploying, rolling back, and storing artifacts.

Not every environmental change belongs to every migration. Only include in scope the components that need to change or need verification to ensure compatibility goals. However, clearly record which components are kept unchanged and the evidence showing they still support the target platform.

## 7. Defining Boundaries: What Is and Is Not Part of the Migration?

A good scope must be broad enough to cover technical impacts, while clear enough to avoid turning the migration into a full application rewrite project.

**Typically in scope:**

- Upgrading or replacing the JDK, compiler, JVM runtime, and toolchain configuration.
- Upgrading wrappers, build tools, plugins, and tasks necessary to build/test on the target platform.
- Adjusting direct and transitive dependencies, BOMs, constraints, and version alignment.
- Upgrading frameworks or adapters required to support the target JDK/dependencies.
- Fixing source code, configuration, and tests affected by changed APIs or behavior.
- Updating images, CI, and deployment configuration needed to run the new artifacts.
- Adding compatibility verification and documenting version decisions.

**Only in scope with a separate requirement or evidence:**

- Redesigning the architecture or changing how modules are partitioned.
- Rewriting business logic unrelated to compatibility.
- Replacing databases, message brokers, or cloud providers merely for modernization.
- Changing protocols or public contracts not required by the target platform.
- Broad performance optimizations unrelated to JDK/framework changes.
- Changing the user interface or product workflows unrelated to the migration.

If another valuable improvement is discovered during the migration, record it as a separate item and clearly state the relationship. Do not bundle business logic changes into the migration if they make it harder to determine root causes of errors or assess rollback feasibility.

## 8. Mapping Compatibility Before Making Changes

Before updating versions, you need to map the current state and the target state. This map helps uncover constraints before making bulk changes.

A minimal matrix may take the form:

| Layer | Current Baseline | Target | Constraints to Verify |
|---|---|---|---|
| JDK running build | Version currently used in CI/local | Target JDK | Can Gradle/Maven and plugins run? |
| Java toolchain | Current compiler | Target compiler | Are source level, release, and APIs suitable? |
| Runtime | Production JDK/JRE | Target runtime | Are images, servers, and JVM options supported? |
| Build tool | Current wrapper | Target wrapper | Are build logic and plugins compatible? |
| Dependencies | Current BOM and dependency tree | Target dependency set | Are there conflicts, removed APIs, or unsupported libraries? |
| Framework | Current framework and adapters | Target framework | Are there any breaking changes, namespace changes, or default changes? |
| Deployment | Current CI, containers, servers | Post-migration environment | Can the new artifacts be built, deployed, and rolled back? |

It is not necessary for every version to be upgraded at the same time. An intermediate phase can exist to upgrade build tools, address warnings, or transition dependencies before upgrading the framework. However, each intermediate state must be a buildable and verifiable combination, rather than an arbitrarily chosen set of versions.

### 8.1. Gathering the Current State

Current-state information should be gathered from the effective configuration and execution environment, not just from project notes. Sources that commonly need to be inspected include:

- `java -version` and `javac -version` in the relevant environments.
- `./gradlew --version` or `mvn -version` to identify the JVM running the build.
- Wrappers, build scripts, parent POMs, plugins, and convention build logic.
- Dependency reports for compile, runtime, and test.
- BOMs, version catalogs, dependency constraints, and exclusions.
- Framework configuration, application properties/YAML, and profiles.
- Dockerfiles, CI workflows, startup scripts, and deployment manifests.

For multi-module projects, record which modules share a common platform and which modules have custom configurations. One module may use a different Java toolchain, different plugins, or separate runtime dependencies; you should not infer the configuration of the entire repository from a single representative module.

### 8.2. Risk Categorization and Handling Order

Each difference between the baseline and the target should be categorized by impact level:

- **Direct incompatibility:** components that cannot run, build, or compile with the target version.
- **Requires source code/configuration changes:** APIs or properties have changed, packages have moved, or old configurations are no longer valid.
- **Risk of behavioral change:** builds successfully, but runtime semantics or external contracts may differ.
- **Requires environment verification:** no evidence yet regarding containers, servers, CI, or the operating system.
- **Unaffected:** components kept unchanged with grounds confirming they remain compatible.

The handling order should be based on dependency relationships. For example, lock in the target JDK version before choosing a wrapper; lock in the target framework before freezing the dependency set managed by the framework; and determine the final runtime before updating production images.

## 9. Verifying Scope After Migration

Verification must cover every layer included in scope. A successful build command is a necessary signal, but not sufficient.

| Layer | Appropriate Verification Evidence |
|---|---|
| JDK/compiler | Build with the target toolchain; confirm release/bytecode; check related APIs and JVM options. |
| Build tool | Run the standard wrapper in the CI environment; execute necessary compile, test, package, and publish tasks. |
| Dependencies | Resolve the dependency graph; check for conflicts; run tests with the actual runtime classpath. |
| Framework | Test context startup, web endpoints, transactions, persistence, security, serialization, and integrations currently in use. |
| Runtime environment | Run the artifact in the target image/server; check startup, health, outbound connections, and resource limits. |
| Application contracts | Compare requests/responses, events, stored data, and public behavior before/after. |

Maintain a representative test suite for the application's critical flows. If the migration affects schemas, serialization, or message formats, check the ability to read old data and interact with services that have not yet been upgraded. If deploying incrementally, clearly determine which versions can coexist during the transition period.

## 10. Example of a Migration's Scope

Suppose an application is currently running on an older JDK, using Gradle, a web framework, an ORM, a JSON mapper, and a database driver. The goal is to move to a new JDK and a framework version supported on that JDK.

The scope can be expressed as the following work groups:

1. **JDK:** choose the target runtime, configure the toolchain/compiler, handle removed APIs, and check JVM options.
2. **Build:** choose a compatible Gradle Wrapper, update plugins and annotation processors, and confirm build/tests run in CI.
3. **Dependencies:** update the BOM or dependency management, check transitive dependencies, handle unsupported libraries, and verify the classpath.
4. **Framework:** upgrade the web framework and related adapters, update affected APIs/namespaces/configuration, and check default behavior.
5. **Operations:** update the JDK base image, pipeline, and startup configuration; run a trial of the artifact in the target environment.
6. **Data and communication compatibility:** check JSON, HTTP contracts, schemas, and message formats if these components are affected.

Tasks such as changing business logic, splitting services, switching databases, or redesigning APIs are not automatically brought into scope. They are only added when there is an independent requirement or when a specific compatibility constraint proves that the change is necessary.

## 11. Required Outputs When Finalizing Scope

Once the migration scope is agreed upon, the implementation team should have outputs clear enough for others to continue the work and verify results:

- **Baseline:** a list of current versions and configurations of the JDK, build tools, dependencies, frameworks, and runtime environment.
- **Target:** target versions along with selection rationale and support constraints.
- **Compatibility matrix:** accepted version combinations, intermediate combinations, and unsupported combinations.
- **Dependency inventory:** direct/transitive dependencies, BOMs, plugins, and libraries that need changing.
- **Migration items:** source code, configuration, build, and deployment changes tied to specific causes.
- **Verification evidence:** build/test commands, test results, and evidence of running on the target runtime.
- **Known limitations:** unresolved issues, remaining workarounds, and conditions to monitor.
- **Rollback considerations:** artifacts, configuration, and data compatibility required to revert to the previous version.

The clearer the scope, the safer it is to break down the migration. Each change should trace back to a compatibility constraint or an agreed-upon goal; each important constraint needs a corresponding verification method. As a result, the team can distinguish errors caused by the JDK, build tools, dependencies, frameworks, or deployment environment, while knowing exactly which parts have been migrated and which parts still need to be addressed.
