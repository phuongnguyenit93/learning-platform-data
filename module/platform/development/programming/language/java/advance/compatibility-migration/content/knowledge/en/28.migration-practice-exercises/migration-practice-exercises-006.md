# Finding and Replacing an Internal API With `jdeps`

A Java application may run fine on an older JDK yet emit warnings, class-loading failures, or access errors when moved to Java 17, 21, or a newer JDK. In many cases, the cause is application code or a library depending on **JDK internal APIs** such as `sun.misc.Unsafe`, `sun.security.x509.*`, or classes under `jdk.internal.*`.

Those APIs may have been in use for years and some are still present in modern JDKs. However, they **do not carry the same compatibility commitment as public Java SE APIs**. The fact that an internal class still exists at runtime does not guarantee its signature, accessibility, or behavior will remain intact in future JDK releases.

**`jdeps`** is a tool bundled with the JDK that reads class files/JARs to detect bytecode-level dependencies. The `--jdk-internals` option finds static references to internal APIs. It does not edit source code, does not prove complete runtime behavior, and cannot automatically choose the right replacement for every use case.

This hands-on exercise walks through a complete end-to-end migration cycle:

```text
Source using sun.misc.Unsafe
               |
               v
       Compile into JAR
               |
               v
     jdeps --jdk-internals
               |
               v
     Find offending class
               |
               v
   Understand behavior to keep
               |
               v
Replace with AtomicIntegerFieldUpdater
               |
               v
     Compile --release 8
               |
               v
  Run concurrency contract test
               |
               v
    Re-scan JAR with jdeps
               |
               v
Save evidence and handle the rest
```

The central example uses `sun.misc.Unsafe.compareAndSwapInt` to increment a counter atomically. The fix uses `java.util.concurrent.atomic.AtomicIntegerFieldUpdater`, a public Java SE API present since Java 8 (and earlier). The advanced section introduces `VarHandle` for Java 9+ and explains how to handle cases where third-party libraries, reflection, or native code depend on internal APIs.

> **Environment:** Illustrative commands assume a full HotSpot/OpenJDK-style JDK, preferring JDK 17 or 21 to execute. When using a different JDK vendor/version, consult `jdeps --help`, `javac --help`, and corresponding release documentation. Never modify a production JVM or bypass security policies just to run this lab.

## 1. Objectives and Completion Criteria

Upon completion, learners should be able to:

1. Distinguish Java SE public APIs from JDK internal APIs and JDK-specific APIs.
2. Locate usages of internal classes inside a compiled JAR using `jdeps`.
3. Understand `jdeps --jdk-internals` reports at the module and class levels.
4. Use `javap` to verify which classes/methods bytecode actually references.
5. Determine the behavior of legacy code before picking a replacement.
6. Write an implementation that no longer uses `Unsafe`.
7. Compile the new source using `javac --release 8`.
8. Run the same concurrency test on both the old and new code.
9. Re-scan the JAR to confirm the finding in the fixed module is gone.
10. Understand limits of static analysis, inventory dependency graphs, and integrate checks into CI.

**Reasonable completion condition:** the new JAR produced from this lab's source no longer references `sun.misc.Unsafe`, uses standard APIs, still increments to the expected total under concurrency, and compiles at Java 8 level. This condition verifies only this exercise's scope, not that an arbitrary full application is compatible with every JDK.

## 3. What Are Internal APIs?

### 3.1. Public APIs With Support Commitments

Examples of Java SE APIs:

```java
java.util.concurrent.atomic.AtomicInteger
java.util.concurrent.atomic.AtomicIntegerFieldUpdater
java.lang.invoke.VarHandle
java.util.Base64
java.nio.ByteBuffer
java.security.cert.CertificateFactory
```

Public APIs appeared in different releases: `VarHandle` requires Java 9+, while `Base64` exists in Java 8. "Public" does not mean present in all JDK releases. Determine the product's **minimum Java** baseline before choosing.

### 3.2. Internal APIs Carry Different Risks

Some examples:

```text
sun.misc.Unsafe
jdk.internal.misc.Unsafe
sun.security.x509.*
sun.reflect.* (depending on class and JDK version)
```

These classes can be implementation details without stability guarantees from the Java SE specification. Under the module system, some sit inside packages sealed by strong encapsulation; a few critical compatibility ones remain exposed via `jdk.unsupported`.

Do not infer blindly from name prefixes. Certain `com.sun.*` APIs are provided by the JDK with explicit documentation. Use tools, specifications, and your vendor's support policy to classify them.

### 3.3. Why Did Legacy Applications Use Them?

- No equivalent public API existed when the code was written.
- Libraries needed CAS operations, memory ordering, or native memory.
- Serialization/ORM frameworks instantiated objects via special mechanisms.
- Frameworks/agents instrumented bytecode or read JVM internals.
- Code was copied from a JVM-specific optimization example.
- Legacy libraries had a fast path using internal APIs and a fallback path.

Do not delete an `Unsafe` line without first identifying **why** it exists. A replacement is valid only when it preserves functional semantics and concurrency contracts.

## 4. The `jdeps` Tool: Capabilities and Limits

### 4.1. Key Options

| Option | Purpose |
|---|---|
| `--jdk-internals` | Find static references to JDK internal APIs |
| `--class-path` or `-cp` | Supply dependent JARs/classes |
| `--recursive` or `-R` | Traverse dependencies as supported by the tool |
| `--verbose:class` | Display class-level dependencies |
| `--print-module-deps` | Print a list of module dependencies |
| `--list-deps` | List module dependencies |
| `--multi-release` | Analyze the appropriate MR-JAR class variant for a target version |
| `--ignore-missing-deps` | Continue analysis when dependencies are missing |

Not all options can be combined arbitrarily; consult `jdeps --help` for your running JDK to confirm invocation syntax.

### 4.2. `jdeps` Sees Only Part of the Picture

Direct example:

```java
import sun.misc.Unsafe;

Class<?> type = Unsafe.class;
```

Bytecode has an explicit class reference that `jdeps` can analyze.

Dynamic example:

```java
Class<?> type = Class.forName("sun.misc.Unsafe");
```

The class name in the second example sits inside a string literal. `jdeps` cannot reliably know every string represents a class loaded at runtime; reflection, generated bytecode, and plugin loading may go undetected.

### 4.3. Tool Comparison

| Tool | Question answered |
|---|---|
| `javac` | Does code compile for the target release/API? |
| `jdeps` | Which classes/modules/internal APIs does the artifact depend on? |
| `javap` | What exact method/class references appear in bytecode? |
| `java` | Does behavior work on the target runtime? |
| Maven/Gradle reports | Which runtime dependency versions were actually selected? |
| JFR/GC/runtime diagnostics | How do performance and JVM behavior look in practice? |

A `jdeps` report does not replace compiler checks, contract tests, or running the application on the target JDK.

## 5. Defining the Atomic Counter Problem

We need a counter that multiple threads can update concurrently:

```text
Counter
  incrementAndGet():
    - increment by exactly 1
    - return the value after incrementing
  get():
    - read the current value
```

Suppose 4 threads, each incrementing 10,000 times:

```text
4 x 10,000 = 40,000 increments
Final value must be 40,000.
```

If code uses plain `value++`, threads can read the same value before writing and lose increments.

### 5.1. Why Is `volatile` Not Enough?

```java
private volatile int value;

public int incrementAndGet() {
    return ++value;
}
```

`volatile` provides certain visibility/ordering guarantees, yet `++` still comprises a read, addition, and write; the full read-modify-write sequence does not become atomic automatically.

### 5.2. CAS Protects the Update

```text
value = 7

Thread A: reads 7
Thread B: reads 7
Thread A: CAS(expected=7, update=8) -> succeeds
Thread B: CAS(expected=7, update=8) -> fails
Thread B: reads 8 and retries
Thread B: CAS(expected=8, update=9) -> succeeds

Correct result: 9
```

Legacy code uses an internal API for the CAS operation. New code must preserve the exact same behavior without relying on JVM implementation details.

## 6. Creating a Shared API for Both Implementations

File:

```text
src/api/demo/Counter.java
```

Contents:

```java
package demo;

public interface Counter {
    int incrementAndGet();

    int get();
}
```

The interface exposes neither `sun.misc.Unsafe`, field offsets, `AtomicIntegerFieldUpdater`, nor `VarHandle`. Thus callers can share the same contract across multiple implementations.

## 7. Creating the Legacy Implementation Using `Unsafe`

File:

```text
src/legacy/demo/LegacyCounter.java
```

Full contents:

```java
package demo;

import java.lang.reflect.Field;
import sun.misc.Unsafe;

public final class LegacyCounter implements Counter {
    private static final Unsafe UNSAFE;
    private static final long VALUE_OFFSET;

    static {
        try {
            Field field =
                Unsafe.class.getDeclaredField("theUnsafe");
            field.setAccessible(true);

            UNSAFE = (Unsafe) field.get(null);
            VALUE_OFFSET = UNSAFE.objectFieldOffset(
                LegacyCounter.class.getDeclaredField("value")
            );
        } catch (ReflectiveOperationException ex) {
            throw new ExceptionInInitializerError(ex);
        }
    }

    private volatile int value;

    @Override
    public int incrementAndGet() {
        for (;;) {
            int before = value;
            int after = before + 1;

            if (UNSAFE.compareAndSwapInt(
                    this, VALUE_OFFSET, before, after)) {
                return after;
            }
        }
    }

    @Override
    public int get() {
        return value;
    }
}
```

This is **code intentionally using an internal API for illustration**; never copy it verbatim into a new project.

### 7.1. Key Points

- `import sun.misc.Unsafe`: direct internal dependency.
- `Unsafe.class`: class reference visible to bytecode analysis.
- `theUnsafe`: private field accessed via reflection.
- `objectFieldOffset`: retrieves the field's offset within the object.
- `compareAndSwapInt`: atomic update via CAS.
- `volatile`: field concurrently accessed by multiple threads.

Some HotSpot JDKs still provide `sun.misc.Unsafe` in the `jdk.unsupported` module for compatibility reasons. However, its presence **does not make it a long-term guaranteed Java SE API**.

### 7.2. Why Fetch the Instance via Reflection?

`Unsafe.getUnsafe()` is normally restricted from ordinary application classes. Some historical libraries use reflection to access the singleton instance.

This example exists solely to illustrate a dependency that must be eliminated. If the JDK or security environment forbids access, that is a meaningful migration finding; do not break policies at all costs just to keep an old example running.

### 7.3. Expected Compile Warning

When compiling, the compiler may print a warning along the lines of:

```text
Unsafe is internal proprietary API and may be removed
in a future release
```

Exact wording and warning severity vary by toolchain. This is a real issue requiring attention, not mere warning noise to suppress.

### 9.2. How to Read the Output

| Element | Meaning |
|---|---|
| `legacy-counter.jar` | Artifact being scanned |
| `demo.LegacyCounter` | Class in the application/JAR creating the dependency |

### 10.1. Inspection Command

```shell
javap -classpath build/legacy-counter.jar \
  -c -p -v demo.LegacyCounter
```

Strings visible in the constant pool/bytecode include:

```text

```

Actual output syntax includes method descriptors, flags, and constant-pool indexes. The items above list only the symbols to look for.

### 10.2. Why Not Read Source Code Alone?

- A production JAR may have been built from a different commit.
- Generated classes from annotation processors may exist.
- Dependencies may be shaded and relocated.
- An older JAR may linger inside a container layer.
- A library may ship only binaries without source.
- IDE and CI may resolve different dependency versions.

Running `javap` on the exact scanned artifact confirms bytecode **truly** references the internal API.

### 10.3. What `javap` Does Not Do

`javap` does not prove a code path executes under real workloads. Nor does it verify equivalent replacement semantics. Doing that requires understanding requirements and writing tests.

## 11. Finding a Replacement API for CAS Needs

### 11.1. Questions to Ask Before Fixing

- Does code need atomic increments or just simple reads/writes?
- Is the field `int`, `long`, or an object reference?
- Must it return the old value or new value?
- Which volatile/acquire/release memory ordering is needed?
- Is object layout part of a public binary contract?
- Is Java 8 supported, or has the baseline moved to Java 17/21?
- Is hot-path performance a measurable requirement?
- Do external callers depend on the field or implementation?

### 11.2. Replacement Table by Use Case

| Internal API usage | Public API to consider | Limitations |
|---|---|---|
| Atomic integer counter | `AtomicInteger` | Replaces representation with an object |
| Atomic update on `volatile int` field | `AtomicIntegerFieldUpdater` | Field and access permissions must satisfy rules |
| Atomic update on reference field | `AtomicReferenceFieldUpdater` | Field type and visibility rules |
| Diverse CAS/access modes | `VarHandle` (Java 9+) | Minimum Java version and access semantics |
| Direct buffers | `ByteBuffer.allocateDirect` | Not an arbitrary substitute for raw addresses |
| Off-heap memory | JDK-appropriate memory API, native abstraction | Must consider ownership and lifecycle |
| Object instantiation skipping constructors | Suitable factory/constructor/serialization framework | Often no one-to-one replacement |
| Internal security/certificate APIs | JCA/JCE/`java.security.cert`/supported libraries | Must evaluate validation and standards |

A sprawling internal API like `Unsafe` cannot be replaced wholesale by any single class.

### 11.3. Primary Choice: `AtomicIntegerFieldUpdater`

`AtomicIntegerFieldUpdater` has existed since Java 5 in the Java SE public API, allowing atomic updates on a `volatile int` field. It fits this lab's scope, eliminates reliance on JVM internals, and avoids raising the minimum JDK requirement.

## 12. Writing the New Implementation

Create file:

```text
src/modern/demo/ModernCounter.java
```

Contents:

```java
package demo;

import java.util.concurrent.atomic.AtomicIntegerFieldUpdater;

public final class ModernCounter implements Counter {
    private static final AtomicIntegerFieldUpdater<ModernCounter>
        VALUE_UPDATER =
            AtomicIntegerFieldUpdater.newUpdater(
                ModernCounter.class,
                "value"
            );

    private volatile int value;

    @Override
    public int incrementAndGet() {
        return VALUE_UPDATER.incrementAndGet(this);
    }

    @Override
    public int get() {
        return value;
    }
}
```

### 12.1. What Was Removed

The new version no longer has:

```text
import sun.misc.Unsafe
Field("theUnsafe")
setAccessible(true) on the Unsafe class
objectFieldOffset(...)
compareAndSwapInt(...)
```

Instead, it uses a public atomic updater. Callers continue invoking `Counter.incrementAndGet()` and `Counter.get()` just as before.

### 12.2. `volatile` Remains Mandatory

`AtomicIntegerFieldUpdater` requires a field conforming to its contract; for this updater type, the target field must be `volatile int`. You cannot arbitrarily change it to `Integer` or remove `volatile`.

### 12.3. Where the Updater Is Created and Access Rules

The `newUpdater` factory verifies field access permissions. In this example, the updater is created in the static initializer of the same class owning the `private` field, avoiding access errors from unauthorized modules/classes.

If moving factory logic to a helper class or another named module, check accessibility and adjust design if needed. Never open an entire module solely to preserve an unclear implementation layout.

### 12.4. Why Are Results Equivalent?

The old implementation used a CAS loop to ensure each increment applied atomically. The updater's `incrementAndGet` provides atomic updates per API contract, returning the exact new value.

What is **not equivalent**:

```java
public int incrementAndGet() {
    return ++value;
}
```

An increment expression on a `volatile int` can still lose updates under multithreading.

## 13. A Simpler Alternative: `AtomicInteger`

If preserving a primitive field is unnecessary, you can use:

```java
package demo;

import java.util.concurrent.atomic.AtomicInteger;

public final class SimpleCounter implements Counter {
    private final AtomicInteger value = new AtomicInteger();

    @Override
    public int incrementAndGet() {
        return value.incrementAndGet();
    }

    @Override
    public int get() {
        return value.get();
    }
}
```

This option is often simpler to read with fewer field-access constraints. The trade-off is a different representation/instance memory layout. Never assume an updater is always faster than `AtomicInteger`; if performance matters, measure under equivalent workloads.

## 16. Writing a Multithreaded Contract Test

Create file:

```text
src/test/demo/CounterContractTest.java
```

Contents:

```java
package demo;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public final class CounterContractTest {
    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException(
                "Usage: CounterContractTest <provider-class>"
            );
        }

        Class<?> type = Class.forName(args[0]);
        final Counter counter =
            (Counter) type.getDeclaredConstructor().newInstance();

        final int workers = 4;
        final int incrementsPerWorker = 10000;

        ExecutorService pool =
            Executors.newFixedThreadPool(workers);

        try {
            List<Future<?>> tasks =
                new ArrayList<Future<?>>();

            for (int i = 0; i < workers; i++) {
                tasks.add(pool.submit(new Runnable() {
                    @Override
                    public void run() {
                        for (int n = 0;
                                n < incrementsPerWorker; n++) {
                            counter.incrementAndGet();
                        }
                    }
                }));
            }

            for (Future<?> task : tasks) {
                task.get();
            }
        } finally {
            pool.shutdownNow();
        }

        int expected = workers * incrementsPerWorker;
        int actual = counter.get();

        if (actual != expected) {
            throw new AssertionError(
                "Expected " + expected + ", got " + actual
            );
        }

        System.out.println("PASS: counter=" + actual);
    }
}
```

### 16.1. Why Use `Class.forName`?

We want to run the same test binary against both implementations without compiling direct references to both `LegacyCounter` and `ModernCounter` into the test.

The provider class name is passed as an argument; the test illustrates an intentional use of dynamic class loading. This also demonstrates `jdeps`'s limitation: from the test's bytecode alone, it cannot know which class name an operator will pass.

### 16.2. What Does the Test Verify?

- Starts with counter 0.
- Spawns four workers.
- Each worker increments 10,000 times.
- Awaits completion of all `Future.get()` calls.
- Compares final result against 40,000.
- Fails if any increments are lost.

This test does not prove the entire Java Memory Model, yet directly checks the property the migration must preserve.

```text
PASS: counter=40000
```

If the old version fails to launch because internal APIs are restricted or altered, record the exception and environment. Do not bypass policies just to force the desired output.

### 17.3. Running the Modern Version

Unix-like:

```shell
java -cp "build/modern-counter.jar:build/test" \
  demo.CounterContractTest demo.ModernCounter
```

Windows PowerShell:

```powershell
java -cp "build/modern-counter.jar;build/test" demo.CounterContractTest demo.ModernCounter
```

Expected output:

```text
PASS: counter=40000
```

### 17.4. Do Not Put Both JARs on the Same Test Classpath

In this demo, both the legacy JAR and the modern JAR contain `demo.Counter`. To avoid unnecessary duplicate classes, include **only one** JAR alongside the test classes per run.

In production projects, extract `Counter` into a shared API JAR and package only the chosen implementation for each release.

### 17.5. Additional Tests Needed Before Production

- Initial value and sequential increments.
- Multiple independent counter instances.
- Varying worker counts and iteration counts.
- Overflow behavior if specified by contract.
- Performance under real contention.
- Error handling/resource lifecycle if embedded in a service.
- Minimum JDK committed for the product.
- Integration tests on the final application artifact.

One successful run of 40,000 increments does not prove all concurrent execution conditions have been tested.

## 18. `VarHandle`: An Option for JDK 9+

If the application's minimum JDK is Java 9+, `java.lang.invoke.VarHandle` is a public API worth considering when code requires atomic access and specific memory ordering modes.

### 18.1. Complete Example

```java
package demo;

import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;

public final class VarHandleCounter implements Counter {
    private static final VarHandle VALUE_HANDLE;

    static {
        try {
            VALUE_HANDLE = MethodHandles.lookup()
                .findVarHandle(
                    VarHandleCounter.class,
                    "value",
                    int.class
                );
        } catch (ReflectiveOperationException ex) {
            throw new ExceptionInInitializerError(ex);
        }
    }

    private volatile int value;

    @Override
    public int incrementAndGet() {
        int before = (int) VALUE_HANDLE.getAndAdd(this, 1);
        return before + 1;
    }

    @Override
    public int get() {
        return value;
    }
}
```

### 18.2. Return Values Differ

`AtomicIntegerFieldUpdater.incrementAndGet(this)` returns the value **after incrementing**.

`VarHandle.getAndAdd(this, 1)` returns the value **before incrementing**. Thus the example adds 1 to satisfy `Counter.incrementAndGet()`.

Replacing a low-level API without checking return-value semantics can introduce bugs even with zero compiler warnings.

### 18.3. Important Baseline

| API | Minimum JDK level |
|---|---|
| `AtomicInteger` | Java 5 |
| `AtomicIntegerFieldUpdater` | Java 5 |
| `VarHandle` | Java 9 |
| `sun.misc.Unsafe` | Not a stable Java SE public API |

If Java 8 consumers still exist, do not put `VarHandle` directly in a shared implementation targeting 8. Adapters or multi-release JARs can be created when multiple implementations are genuinely required, provided each JVM is tested.

## 19. Cases Where `Unsafe` Cannot Be Replaced Simply

### 19.1. Atomic Operations Differ From Direct Memory

`Unsafe` spans many capabilities: CAS, object offsets, native memory, unaligned access, object allocation, and JVM-specific operations.

If legacy code uses only CAS on an `int`, `AtomicIntegerFieldUpdater` is a natural fit. If code uses `Unsafe.allocateMemory`, replacing it with an updater is functionally completely wrong.

### 19.2. Off-Heap Memory

Modern approaches may include:

- `ByteBuffer.allocateDirect` if suited to the data model.
- Foreign Function & Memory API on JDKs with a supported version.
- Managed native library abstractions.
- Refactoring data back on-heap when off-heap is unnecessary.

The FFM API became final in JDK 22 after passing through incubator/preview phases where APIs changed. Do not copy JDK 22 examples into Java 17 or Java 21 assuming compatibility.

### 19.3. Object Instantiation Bypassing Constructors

Certain historical serialization frameworks used internal methods to allocate objects. Switching to `new` can alter invariants, constructor side effects, and compatibility with old data.

Examine actively maintained frameworks and Java Serialization/JSON/JPA contracts rather than trying to swap method names alone.

### 19.4. Memory Ordering

Some code uses release/acquire, volatile, opaque, or ordered memory accesses. Moving to public APIs requires understanding the **Java Memory Model** and the exact ordering required.

Do not equate all CAS, set, or lazy-set methods. If the existing code's semantics are unclear, write concurrency-level contract tests and conduct thorough reviews.

## 20. Side Exercise: Base64 Internal API

Some legacy Java applications use:

```java
sun.misc.BASE64Encoder
sun.misc.BASE64Decoder
```

Java 8 provides the public API `java.util.Base64`:

```java
import java.nio.charset.StandardCharsets;
import java.util.Base64;

byte[] input = "Xin chào Java".getBytes(
    StandardCharsets.UTF_8
);

String encoded = Base64.getEncoder()
    .encodeToString(input);

byte[] decoded = Base64.getDecoder()
    .decode(encoded);
```

### 20.1. Do Not Check Only Round Trips

Compare behavior across:

- Standard vs URL-safe Base64 alphabet.
- Padding.
- MIME line wrapping.
- Whitespace handling.
- Character encoding of original data.
- Error behavior on invalid inputs.

`Base64.getEncoder()`, `getUrlEncoder()`, and `getMimeEncoder()` serve different purposes.

### 20.2. Note When Scanning Very Old Artifacts

An internal class present on JDK 8 yet removed from modern runtimes may be flagged by a newer `jdeps` as a missing dependency rather than clearly labeled as a JDK internal API on that target JDK.

Do not conclude code is safe merely because `--jdk-internals` did not print the removed class name. Combine scans across baseline JDKs, source/binary inspection, and runtime tests.

## 21. Real-World Application: Internal APIs Inside Transitive Dependencies

Example:

```text
order-service.jar
   |
   +-- web-framework.jar
   |
   +-- messaging-client.jar
   |       |
   |       +-- buffer-helper.jar
   |                 |
   |                 +-- sun.misc.Unsafe
   |
   +-- jdbc-driver.jar
```

Scanning only `order-service.jar` can miss internal APIs inside `buffer-helper.jar`. Proper scanning must cover the runtime dependency closure.

### 21.1. Using Classpath and Recursive Analysis

Unix-like:

```shell
jdeps --recursive --jdk-internals \
  --class-path "lib/*" \
  application.jar
```

PowerShell:

```powershell
jdeps --recursive --jdk-internals --class-path "lib/*" application.jar
```

Analysis is complete only within **the scope of JARs/modules provided to the tool and resolvable**. Dynamically loaded plugin JARs, JARs nested inside executable archives, or server-shared libraries may need separate collection.

### 21.2. Scanning Each Dependency Directly

In a directory containing many runtime JARs, inventory and scan each artifact individually to uncover internal APIs outside static reference paths from the main JAR.

When automating, store artifact paths, versions, and checksums. Do not merely output "3 findings" without specifying which JAR contains them.

### 21.3. `--ignore-missing-deps` Is Not a Clean Bill of Health

If forced to continue analysis despite missing libraries:

```shell
jdeps --ignore-missing-deps --recursive \
  --jdk-internals \
  --class-path "lib/*" \
  application.jar
```

Simultaneously record all missing dependencies. A scan that finishes while missing the JAR containing an internal API yields an incomplete report.

## 24. Creating a CI Gate and Managing Exceptions

### 24.1. Do Not Check Exit Code Alone

Running `jdeps --jdk-internals` may print internal API findings while returning an exit status that does not indicate "quality gate failed due to findings".

To make CI fail when internal APIs are detected:

1. Pin JDK/tool version.
2. Save full stdout/stderr and exit status.
3. Distinguish tool errors from scan findings.
4. Parse reports with tested logic.
5. Run a positive fixture intentionally using `Unsafe`.
6. Run a negative fixture using only public APIs.
7. Fail if new findings are outside the allowlist.
8. Never declare PASS while missing dependencies remain unresolved.

### 24.2. Allowlists Must Have Deadlines

Example metadata:

```yaml
artifact: legacy-buffer-helper
owner: platform-runtime
finding: sun.misc.Unsafe
status: temporary-exception
reason: upstream migration in progress
target_jdk: "21"
remediation: upgrade dependency
review_by: "YYYY-MM-DD"
```

This is a declaration template, not a standard `jdeps` format. Never grant indefinite exceptions; each exception requires an owner, risk assessment, and review date.

### 24.3. Avoid False Assurance

A gate scanning only the main source module can turn "green" even while the production fat JAR still embeds an old library.

Verify:

- Resolved runtime dependencies.
- Final JAR/WAR/OCI image layout.
- Nested or server-provided JARs.
- MR-JAR variants.
- Plugin/agent artifacts if present.
- Production minimum runtime/JDK.

## 25. When Third-Party Libraries Use `Unsafe`

If `jdeps` reports a JAR you do not own referencing `sun.misc.Unsafe`, do not directly patch binaries in your local repository while ignoring provenance.

Approaches:

1. Find a newer vendor version supporting the target JDK.
2. Read release notes to see if internal API fast paths were replaced.
3. Select a compatible framework/BOM version rather than forcing individual JARs.
4. Check whether the library has a vendor-supported fallback.
5. If the library is EOL, plan a replacement.
6. Controlled fork when your organization can maintain and test it.
7. Record a time-boxed exception if immediate remediation is impossible.

A library might keep `Unsafe` on one code path while using public APIs on another. The `jdeps` finding stays relevant, while prioritization considers runtime support and actual usage frequency.

## 26. Distinguishing `jdeps` Findings From JPMS Errors

### 26.1. What Is `jdk.unsupported`?

Certain critical internal APIs like `sun.misc.Unsafe` live in the `jdk.unsupported` module on modern JDKs. This supports historical compatibility cases without turning those APIs into Java SE.

### 26.2. `InaccessibleObjectException`

This error typically arises when reflection tries to access a member not opened under JPMS strong encapsulation. It can occur with code whose dependency `jdeps` cannot see via string names.

### 26.3. `IllegalAccessError`

Can appear when bytecode references a class/member inaccessible under access/module rules. Not every internal API finding produces this error.

### 26.4. Why Not Just Add `--add-opens`?

`--add-opens` grants reflective access in certain cases; `--add-exports` affects exports for other access. However, they:

- Do not restore removed classes/methods.
- Do not fix internal API semantics.
- Do not eliminate the dependency from bytecode.
- Can increase risk and flag maintenance overhead.

Use scoped temporary workarounds with owners and deadlines if necessary. The long-term path is migrating to public APIs or properly supported libraries.

## 27. Static Analysis Limitations to Remember

### 27.1. Reflection Strings

`Class.forName("sun.misc.Unsafe")` may not be recognized by `jdeps` as a direct class dependency. Source searches and runtime integration tests are needed.

### 27.2. Generated Bytecode

Byte Buddy, ASM, Mockito, ORMs, agents, and proxies can generate classes at runtime. Check framework support matrices and test on the target JDK.

### 27.3. Native Code

JNI/JVMTI libraries can depend on JVM implementations, OS/architecture, or ABI. `jdeps` does not analyze full native shared library semantics.

### 27.4. Multi-Release JARs

A JAR may contain:

```text
com/example/Feature.class
META-INF/versions/17/com/example/Feature.class
META-INF/versions/21/com/example/Feature.class
```

When scanning, pass the appropriate `--multi-release` flag and check which versioned class the runtime actually loads. Scanning one release does not prove all variants are clean.

### 27.5. Internal APIs That Vanished on Newer JDKs

An internal class present in JDK 8 may have been removed in newer JDKs. Running `jdeps` on a newer JDK may report a missing dependency instead of labeling it a JDK internal API as expected.

Therefore, "zero JDK internal API lines" does not equal "no missing classes". Check missing-deps warnings and runtime tests.

### 27.6. Custom Runtime Images

An image built with `jlink` may exclude `jdk.unsupported` or other modules. When deploying on custom runtimes, check the module list and test the actual image; scanning on a full JDK does not substitute for real deployment testing.

## 28. Performance After Replacing Internal APIs

### 28.1. Correctness Comes First

Replacing a CAS loop with a public atomic updater succeeds only if behavior is preserved. Evaluate performance next if the use case requires it.

### 28.2. Benchmarks Require Control

Never draw conclusions from a single `System.nanoTime()` loop over a few hundred iterations. Measurements are affected by:

- JIT warm-up.
- Dead-code elimination.
- CPU frequency/throttling.
- Cache effects.
- Contention.
- Allocation/GC.
- JDK version and flags.
- OS scheduling.

If performance is critical, use JMH or a controlled harness with proper warm-up/repetitions, recording the exact JDK and hardware.

### 28.3. Post-Deploy Monitoring

If the code sits on a hot path, compare:

- Error rate and exception types.
- p95/p99 latency.
- Throughput.
- CPU and allocation.
- Heap/native memory.
- Lock contention.
- GC pauses.
- Resource saturation.

Never retain `Unsafe` merely because an uncontrolled microbenchmark appeared a few percent faster.

## 29. Troubleshooting

### 29.1. `jdeps` Not Found

Usually caused by PATH/JDK installation issues or running inside a JRE/custom runtime image.

Check whether `java`, `javac`, and `jdeps` belong to the same toolchain/version. If needed, invoke `jdeps` using the full JDK path.

### 29.2. Compiler Warns About Proprietary APIs

This is the expected finding on legacy code. Never silence the warning and call migration complete.

### 29.3. `--release 8` Cannot Find `Unsafe`

Internal APIs are excluded from `--release 8`'s public Java SE API view on modern compilers. Do not attempt to bypass it to package old code; migrate to public APIs as shown in this exercise.

### 29.4. Legacy Example Fails to Run on Newer JDKs

May result from reflective access policies, changed APIs, or missing modules. Record the error and verify target JDK. The intended path is using the modern implementation.

### 29.5. Updater Initialization Fails

Check that the `value` field has the exact name, type `volatile int`, owning class, and access visibility required by the updater factory.

### 29.6. Test Returns Less Than 40,000

Check whether the implementation actually performs atomic updates, whether the test awaits `Future.get()`, and whether the wrong class was loaded.

### 29.7. `jdeps` Still Reports `Unsafe` After Fixing

Another dependency JAR may still reference `Unsafe`, or the old artifact was not rebuilt/republished. Inspect the exact source class and JAR in the report and verify checksums.

### 29.8. `jdeps` Is Clean Yet Runtime Still Fails

Possible causes include missing dependencies, reflection strings, native code, dynamic plugins, MR-JAR variants, or errors unrelated to internal APIs. Inspect the full stack trace and final artifact.

### 29.9. Output Differs Across JDKs

Internal module APIs, class availability, and `jdeps` output formats can change. Pin the exact JDK vendor/version, record commands, and do not diff stdout byte-for-byte across releases.

### 29.10. Fixed Build Works Properly Yet Runs Slower

Do not revert to `Unsafe` immediately. Profile workload, contention, allocation, and JIT behavior; run controlled comparative benchmarks before selecting an appropriate public API.

## 30. Process for Rolling Out Into a Real Repository

### Step 1: Select Target JDK

Record the Java baseline, JDK vendor/full version, deployment format, OS/arch, and support contract.

### Step 2: Inventory Binary Artifacts

Gather application JARs, runtime dependencies, plugin/agent JARs, and server-shared libraries requiring analysis.

### Step 3: Run `jdeps --jdk-internals`

Save reports per artifact and JDK version. Do not ignore unresolved dependencies.

### Step 4: Classify Findings

Assign each finding an owner, impact level, code path, replacement viability, and remediation deadline.

### Step 5: Understand Behavior

Read source, `javap`, tests, and workloads. Never edit before understanding what job the internal API performs.

### Step 6: Pick Replacement Public APIs

Prefer Java SE APIs meeting the baseline or well-supported libraries. Separate adapters if supporting multiple JDKs.

### Step 7: Refactor With Tests

Preserve functionality, concurrency semantics, and data contracts. Compile with the appropriate `--release`.

### Step 8: Re-Scan the Final Artifact

Compare before/after rather than scanning just one source class. Check transitive dependencies.

### Step 9: Runtime and Performance Tests

Run on the actual minimum/target JDKs; test integration, errors, latency, and memory where relevant.

### Step 10: Record Migration Evidence

Save reports, toolchain metadata, artifact checksums, remaining risks, and the rollback plan.

## Conclusion

**Finding and replacing an internal API with `jdeps`** is a workflow combining bytecode analysis with Java API knowledge and behavioral testing. In this lesson, `sun.misc.Unsafe` was used to increment a field atomically; `jdeps --jdk-internals` pinpointed the dependency, and then `AtomicIntegerFieldUpdater` satisfied the CAS requirement without accessing low-level JVM internals.

Migrating properly means more than making a warning disappear. You must **understand the internal API's purpose, preserve semantics, compile for the right baseline, test on the real runtime, and confirm the final artifact is free of the remediated dependency**. Paired with dependency inventories, transitive JAR checks, CI gates, and release provenance, `jdeps` becomes a practical tool to reduce compatibility risk in Java Advance Compatibility Migration.
