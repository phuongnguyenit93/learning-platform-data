# 7.1 Signature polymorphism and the descriptor recorded by the compiler at the call site

**Module:** Java Advance - dynamic-runtime  
**Knowledge group:** 7. Method handle invocation

## Objectives

When invoking a `MethodHandle`, Java does not simply look up an overload with the matching number of parameters like a regular method call. The two methods `MethodHandle.invokeExact` and `MethodHandle.invoke` have a **signature polymorphism** mechanism, causing **the static types of the argument expressions** and **the return type context** to directly affect the *method descriptor* recorded by the compiler in bytecode at each call site.

After this lesson, you will be able to:

1. Explain what a signature polymorphic method is, why `invokeExact`/`invoke` differ from regular varargs methods, and distinguish them from overloading, generics, and `invokedynamic`.
2. Distinguish **`MethodHandle.type()`** (the type that the handle currently has) from **the call-site descriptor** (determined by `javac` from the source code of a specific call).
3. Read descriptors such as `(Ljava/lang/String;)Ljava/lang/String;`, `(Ljava/lang/Object;)Ljava/lang/String;`, `(Ljava/lang/String;)V` and relate them to the source code.
4. Predict whether `invokeExact` succeeds or throws `WrongMethodTypeException`; explain why a change in a cast, variable declaration, or how the result is used can change the descriptor.
5. Understand that `invoke` uses `asType`-like type conversions when appropriate; know the limits of this conversion and when an explicit `asType` is needed.
6. Compile Java 17+, run the example, and use `javap` to verify `invokevirtual` calls yourself.

## 1. Three things that must be kept separate

Before talking about descriptors, let us separate three concepts that are often mixed up.

| Concept | What does it describe? | Example |
| --- | --- | --- |
| **Target method** | The method/constructor/field operation that a handle is created to represent | `static String decorate(String text)` |
| **Handle type** (`MethodHandle.type()`) | The order, argument types, and return type accepted by the *current handle* | `(String)String` |
| **Call descriptor** | The symbolic signature recorded by `javac` at a specific `invokeExact`/`invoke` call instruction | `(Ljava/lang/String;)Ljava/lang/Object;` |

A handle can have type `(String)String`, yet the following two lines of source code request **two different descriptors**:

~~~java
String text = (String) handle.invokeExact("java");
Object value = handle.invokeExact("java");
~~~

The first line requests `(String)String`; the second line requests `(String)Object`. If `handle.type()` is indeed `(String)String`, the first line can run, whereas the second throws `WrongMethodTypeException`. This happens **even though the String object returned if the call succeeded would still be a String at runtime**. In `invokeExact`, the type *declared in the descriptor* must match, not merely whether the returned value is assignable to `Object`.

The two lines above **are only an illustration when the `handle` variable has already been declared/created**; the complete runnable program is in section 5.

## 2. What is a signature polymorphic method really?

### 2.1. Why does a method that looks like `Object...` accept many signatures?

In Java SE 17, `MethodHandle` provides public native varargs methods with declarations similar to:

~~~java
public final native Object invokeExact(Object... args) throws Throwable;
public final native Object invoke(Object... args) throws Throwable;
~~~

This is an **illustrative declaration shape** of the API, not code to implement yourself. According to Java language rules, native varargs methods belonging to `MethodHandle` (and the corresponding access mode methods on `VarHandle`) have a *signature polymorphic* mechanism. The compiler allows calling them with argument lists of different types; at the call site, it generates a **specialized descriptor**.

Therefore:

~~~java
(String) handle.invokeExact("java")
~~~

must not be understood as “Java packs `"java"` into an `Object[]` and then calls a method taking an array”. Normally, there is no `Object[]` packing step as in regular Java varargs. Instead, the bytecode can contain `invokevirtual` referencing:

~~~text
java/lang/invoke/MethodHandle.invokeExact:(Ljava/lang/String;)Ljava/lang/String;
~~~

The JVM has special resolution and execution rules for signature polymorphic calls. It does not require `MethodHandle` to actually declare a separate Java overload for each descriptor generated by the compiler.

**Distinction:** not just any method with `Object...` receives this special treatment. A method you write yourself named `invokeExact` with `Object...` is still a regular varargs method. You cannot create your own signature polymorphic method simply by adding `native` or using unsupported internal annotations.

### 2.2. How does it differ from overloading, generics, and `invokedynamic`?

- **Overloading:** the compiler chooses one of several actual declarations with the same name but different parameter types, according to overload resolution rules.
- **Generics:** the compiler checks type parameters, inference, and erasure; runtime method descriptors usually relate to the erased signatures.
- **Signature polymorphism:** a special declaration can appear with **many different descriptors at call sites**; the JVM knows how to resolve it even without corresponding overloads.
- **`invokedynamic`:** a separate bytecode instruction that uses a bootstrap method to link a dynamic call site. A regular `handle.invokeExact(...)` call is compiled using **`invokevirtual`**, not `invokedynamic`. A bootstrap of `invokedynamic` *can* create/use a method handle, but that is a different linking mechanism.

Saying “method handles are dynamic” does not mean every method handle call site emits `invokedynamic`.

## 3. How does `javac` determine the descriptor?

According to JLS `15.12.3`, for a signature polymorphic method invocation, the compiler determines **compile-time parameter types** directly from the types of **the argument expressions**, without performing normal method invocation conversions to coerce them to `Object[]`.

For a method returning `Object` such as `invokeExact`/`invoke`, **the compile-time return type of the call** is determined by context:

1. If the call is the **direct operand of a cast**, the compiler takes the **erasure of the cast type** as the return type of the call.
2. If the call is used as an **expression statement** (the result is discarded), the return type is `void`.
3. In all other cases, the return type is `Object`.

That is why **the cast outside the call** is so important:

| Java expression | Parameter type at call site | Return type at call site | JVM descriptor |
| --- | --- | --- | --- |
| `(String) h.invokeExact("java")` | `String` | `String` | `(Ljava/lang/String;)Ljava/lang/String;` |
| `Object x = h.invokeExact("java")` | `String` | `Object` | `(Ljava/lang/String;)Ljava/lang/Object;` |
| `(String) h.invokeExact((Object) "java")` | `Object` | `String` | `(Ljava/lang/Object;)Ljava/lang/String;` |
| `h.invokeExact("java");` | `String` | `void` | `(Ljava/lang/String;)V` |
| `Object x = h.invoke("java")` | `String` | `Object` | `(Ljava/lang/String;)Ljava/lang/Object;` |

The rows in the table are **illustrative expressions** assuming an existing handle variable `h`. There are three important observations:

- `"java"` has **expression type `String`**. Casting `(Object) "java"` changes the expression type to `Object` even though the runtime object is still the exact same string.
- Assigning the value to an `Object` variable **does not automatically make** `invokeExact` convert a `String` result to `Object`; the compiler already recorded the return descriptor according to the rules above.
- `h.invokeExact("java");` discards the result, making the return descriptor `V` (void). A handle with return type `String` will not match that descriptor if `invokeExact` is used.

**A common trap:** writing `String s = h.invokeExact("java");` is not the same as `String s = (String) h.invokeExact("java");`. For a call without a direct cast, the static type of the expression is `Object`, so direct assignment to `String` is invalid. A cast is needed to select the intended return type.

### 3.1. How to read a JVM method descriptor

A *method descriptor* has the structure:

~~~text
(parameter_type_1 parameter_type_2 ...)return_type
~~~

Some common notations:

| Notation | Java type |
| --- | --- |
| `I` | `int` |
| `J` | `long` |
| `Z` | `boolean` |
| `V` | `void` (only in the return position of a method descriptor) |
| `Ljava/lang/String;` | `java.lang.String` |
| `Ljava/lang/Object;` | `java.lang.Object` |
| `[I` | `int[]` |
| `[Ljava/lang/String;` | `String[]` |

Examples:

~~~text
(Ljava/lang/String;)Ljava/lang/String;    // String -> String
(Ljava/lang/Object;)Ljava/lang/String;    // Object -> String
(II)I                                    // (int, int) -> int
()V                                      // () -> void
~~~

The descriptor in `invokevirtual` **does not list the `MethodHandle` receiver inside the parentheses**; the receiver sits separately on the instruction's operand stack. For `MethodHandle.findVirtual` pointing to an *instance method*, `MethodHandle.type()` may in turn have the receiver object **of the target method** as its first parameter. Those are two different receiver concepts: the receiver of the instruction calling the handle and the receiver of the target method.

### 3.2. Static type matters more than the runtime object's type

Consider:

~~~java
Object input = "java";
String output = (String) handle.invokeExact(input);
~~~

Even though `input` currently holds a `String`, the expression `input` has type **`Object`** at compile time. Therefore the descriptor is `(Object)String`, not `(String)String`. Only reassigning to a String variable or casting the argument to String when the contract allows it changes the descriptor:

~~~java
String typed = (String) input;
String output = (String) handle.invokeExact(typed);
~~~

Both snippets are **separate illustrations**, not placed side by side in the same Java block because of the duplicate variable name. The first case does not match a `(String)String` handle and throws `WrongMethodTypeException`. The second case has a matching descriptor; casting `input` to String beforehand can still throw `ClassCastException` if the object is not actually a String.

## 4. How does the runtime check the descriptor?

### 4.1. `MethodHandle.type()` is the handle's runtime contract

A handle with `type() == MethodType.methodType(String.class, String.class)` takes one `String` argument and returns a `String` result. The human-readable printout of `type()` is:

~~~text
(String)String
~~~

The JVM has special symbol resolution rules for `MethodHandle.invokeExact` and `invoke`. At the time the instruction runs, it examines **the method type derived from the symbolic descriptor at the call site** and compares it with the current handle's type.

**For `invokeExact`:**

- The type at the call site must **be exactly equal to** `MethodHandle.type()` after resolving symbolic types.
- It compares **parameter order, each parameter type, and the return type**.
- It does not automatically box/unbox, widen primitives, or cast reference types to compensate for a mismatch in the signature.
- When there is a mismatch, it throws `WrongMethodTypeException`. When they match, the handle proceeds to invoke the target; errors thrown inside the target can still propagate out.

**For `invoke`:**

- If the descriptor matches the handle's type, the call behaves similarly to `invokeExact`.
- If they do not match, the JVM attempts a conversion equivalent to `handle.asType(callSiteType)`; if the type conversion is supported, it applies the appropriate adapter before/after calling the target.
- Conversions can include **reference casts**, **boxing/unboxing**, and certain **primitive widenings** according to `asType` rules. This is **not** an arbitrary coercion mechanism: conversions that cannot be formed may throw `WrongMethodTypeException`; actual casts that fail may throw `ClassCastException`.
- `invoke` **does not permanently mutate** the type of the original handle variable. One should not assume it is always as cheap as `invokeExact` or always slower: measure in the actual context.

### 4.2. Choosing an invocation approach from the available contract

| Need | Approach |
| --- | --- |
| Know the exact `MethodType` and want to call with that signature | Use `invokeExact` with matching argument types **and result type** |
| Want the JVM to adapt between two types with a valid `asType` conversion | Use `invoke` and verify conversion semantics |
| Want to create a handle with a new, explicit `type()`, then call exact | `MethodHandle.asType(...)`, then `invokeExact` with the new descriptor |
| Want to call with a list of `Object`s collected dynamically from metadata | Consider `invokeWithArguments` or an appropriate adapter, understanding the added overhead and conversion rules |
| Want to pass an array as **a single** parameter | Check the array-typed descriptor, `asFixedArity()`, or related adapters when needed; do not implicitly treat an array as varargs |
| Want to go from a receiver instance to a handle calling a method | `findVirtual` creates a handle with the target receiver as part of `MethodType` |

`invokeWithArguments` is a different API from `invoke`/`invokeExact`; it accepts a list of Objects in a more conventional way, convenient when the number/types of arguments are only known dynamically, but it should not be confused with signature polymorphic syntax.

## 5. Java 17+ Practice: same handle, multiple call-site descriptors

The program uses **one base handle** for the static method `decorate(String)`, with type `(String)String`. The first calls succeed; the next three `invokeExact` cases intentionally produce mismatched descriptors to observe `WrongMethodTypeException`; finally `asType` creates another handle matching the signature `(Object)Object`.

**File:** `SignaturePolymorphicDemo.java`

~~~java
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;
import java.lang.invoke.WrongMethodTypeException;
import java.util.Locale;

public class SignaturePolymorphicDemo {
    public static String decorate(String text) {
        return "[" + text.toUpperCase(Locale.ROOT) + "]";
    }

    public static void main(String[] args) throws Throwable {
        MethodHandle handle = MethodHandles.lookup().findStatic(
                SignaturePolymorphicDemo.class,
                "decorate",
                MethodType.methodType(String.class, String.class));

        System.out.println("handleType=" + handle.type());

        String exact = (String) handle.invokeExact("java");
        System.out.println("exact=" + exact);

        Object flexibleResult = handle.invoke("jvm");
        System.out.println("invokeResult=" + flexibleResult);

        String flexibleArgument = (String) handle.invoke((Object) "api");
        System.out.println("invokeArgument=" + flexibleArgument);

        try {
            Object ignored = handle.invokeExact("java");
            System.out.println("unexpected=" + ignored);
        } catch (WrongMethodTypeException expected) {
            System.out.println("exactReturnMismatch");
        }

        try {
            String ignored = (String) handle.invokeExact((Object) "java");
            System.out.println("unexpected=" + ignored);
        } catch (WrongMethodTypeException expected) {
            System.out.println("exactParameterMismatch");
        }

        try {
            handle.invokeExact("java");
            System.out.println("unexpected");
        } catch (WrongMethodTypeException expected) {
            System.out.println("exactVoidMismatch");
        }

        MethodHandle generic = handle.asType(
                MethodType.methodType(Object.class, Object.class));
        Object exactAfterAdapt = (Object) generic.invokeExact((Object) "module");
        System.out.println("adaptedExact=" + exactAfterAdapt);
    }
}
~~~

Save the source code with the exact filename `SignaturePolymorphicDemo.java`. From the directory containing the file, using JDK 17 or later:

~~~bash
javac --release 17 -d out SignaturePolymorphicDemo.java
java -cp out SignaturePolymorphicDemo
~~~

**Verified exact stdout of the program:**

~~~text
handleType=(String)String
exact=[JAVA]
invokeResult=[JVM]
invokeArgument=[API]
exactReturnMismatch
exactParameterMismatch
exactVoidMismatch
adaptedExact=[MODULE]
~~~

### 5.1. Interpreting each call

| Key line | Descriptor at call site | Effect |
| --- | --- | --- |
| `(String) handle.invokeExact("java")` | `(String)String` | Matches `handle.type()`; call succeeds |
| `handle.invoke("jvm")` assigned to `Object` | `(String)Object` | `invoke` can adapt return `String` to `Object` |
| `(String) handle.invoke((Object) "api")` | `(Object)String` | `invoke` can cast an Object reference containing a String to String |
| `Object ignored = handle.invokeExact("java")` | `(String)Object` | `invokeExact` fails on **return type** |
| `(String) handle.invokeExact((Object) "java")` | `(Object)String` | `invokeExact` fails on **parameter type** |
| `handle.invokeExact("java");` | `(String)void` | `invokeExact` fails due to **void return** |
| `(Object) generic.invokeExact((Object) "module")` | `(Object)Object` | Matches **`generic.type()`** after `asType`; call succeeds |

Point to remember: both handles `handle` and `generic` delegate to the `decorate` behavior, but have **different `MethodType`s**. `asType` builds an adapter with the new type; it does not change the type of the original handle. When code calls exact on `generic`, the static types of both the argument and the result are `Object` as required by the adapter.

### 5.2. Inspecting bytecode with `javap`

After compiling the program above:

~~~

In `main`, look for the `invokevirtual` instructions related to `MethodHandle.invokeExact` and `MethodHandle.invoke`. ~~~text

Method java/lang/invoke/MethodHandle.invoke:(Ljava/lang/String;)Ljava/lang/Object;
Method java/lang/invoke/MethodHandle.invoke:(Ljava/lang/Object;)Ljava/lang/String;
Method java/lang/invoke/MethodHandle.invokeExact:(Ljava/lang/String;)Ljava/lang/Object;

These descriptors have been verified with `javap -c -p` for the example's source. `invokevirtual` precedes each actual comment; the set of descriptors corresponds to the rows in the table. **Each instruction** references the exact descriptor inferred by `javac` from the source expression, rather than retrieving that descriptor via Reflection at runtime.

## 6. Why can the JVM resolve a descriptor that does not match the declaration?

In `MethodHandle`, the Java declaration looks like `Object invokeExact(Object... args)`. A call `invokeExact:(Ljava/lang/String;)Ljava/lang/String;` has no corresponding normally declared overload. If you applied regular Java method resolution rules while ignoring the signature polymorphic exception, it would look like “the method does not exist”.

The JVM Specification (`5.4.3.3` and `6.5 invokevirtual`) handles signature polymorphic methods specially:

1. The **symbolic reference** in the constant pool holds the class, method name, and descriptor emitted by the compiler.
2. During JVM resolution/verification, it knows that `MethodHandle`'s `invokeExact`/`invoke` methods are signature polymorphic; it does not require a method declaration bearing that exact varied descriptor.
3. The JVM resolves the types mentioned in the descriptor, checks structural validity, and then at invocation **obtains the `MethodType` corresponding to the descriptor**.
4. For `invokeExact`, the JVM requires that `MethodType` to equal `handle.type()`; for `invoke`, it checks type adaptation according to `asType`.
5. A valid handle transfers control to the target or adapter; target exceptions are still propagated according to method handle mechanics.

Therefore, the `WrongMethodTypeException` error in the example **does not mean** the `MethodHandle` class is missing a method named `invokeExact` or that the JVM cannot resolve the symbol. The call site has already been linked via the special mechanism; the error occurs when **the handle's actual signature does not satisfy the call site's requirement**.

Clearly distinguish two forms of “linking”:

- **Linking the symbolic method reference**: the JVM recognizes a signature polymorphic call and that its descriptor is valid.
- **Checking handle compatibility at invocation**: the JVM enforces the exact or adaptable requirement on the `MethodHandle` received at runtime.

The JVM may optimize these call paths, but a fixed cost should not be assumed across all versions/runtimes.

## 7. Practical consequences when writing dynamic APIs

### 7.1. A change in source can change the descriptor without changing the runtime value

Example:

~~~java
String s = "java";
Object o = s;
String a = (String) handle.invokeExact(s); // (String)String
String b = (String) handle.invokeExact(o); // (Object)String
~~~

This snippet is **an illustration in a scope with a handle of type `(String)String`**, so line `a` can run while line `b` throws `WrongMethodTypeException`. The fact that `o` still points to the same String does not make the two descriptors identical. To make an exact call through an `Object` variable, check/cast the type according to the contract first, or use an adapted handle.

### 7.2. Interaction with generics and erasure

When a generic wrapper method contains an `invokeExact` call, the static type can be **erased** in bytecode. The value at runtime may appear to have the right type, yet the descriptor does not match the specific handle. For example, an argument variable declared with type `T` where `T` is erased to `Object` can result in a descriptor using `Object`. Do not only look at the value in the debugger; always examine the static type/cast of the expression and check the bytecode.

You should check `handle.type()`, use an adapter at the API boundary, or design a call point with a statically known signature. Trying to “force a random cast” outside the expression without knowing the return/argument contract can lead to earlier or harder-to-understand errors.

### 7.3. Signature polymorphism **does not** bypass access rules when creating a handle

Creating a `MethodHandle` using `Lookup.findStatic`, `findVirtual`, `findConstructor`, etc. must still obey Java/module access permissions. `invokeExact` does not allow bypassing private method access; it only describes how to invoke a handle **that has already been validly granted and created**. Errors related to `IllegalAccessException` when `Lookup` creates a handle are fundamentally different from `WrongMethodTypeException` when calling with the wrong descriptor.

### 7.4. Wrong value type and wrong signature are two different errors

- `WrongMethodTypeException`: the call-site descriptor is wrong for `invokeExact`, or `invoke` cannot create an adapter via `asType`.
- `ClassCastException`: the reference cast/adaptation is valid in terms of signature, but the runtime value does not fit, such as casting an `Integer` held in `Object` to `String` for the target to receive.
- `NullPointerException`: can occur if the `MethodHandle` receiver is `null` or the target itself dereferences null.
- **Target** exceptions: a handle with a matching type can still invoke business logic that throws an exception. Since `invokeExact`/`invoke` declare `throws Throwable`, calling source code must handle/declare exceptions appropriately; the demo chose `main throws Throwable` to keep the illustration focused.

## 8. Common errors and how to debug

| Symptom | Possible cause | How to verify |
| --- | --- | --- |
| `invokeExact` reports `WrongMethodTypeException` even though the argument is “right” | The static type/name of the argument variable differs from what the handle accepts | Print `handle.type()`; check casts and the descriptor in `javap` |
| `invokeExact` reports wrong return type | Did not cast the call directly, cast to the wrong type, or discarded the result | Check the return type in the descriptor: `Ljava/lang/Object;`, `Ljava/lang/String;`, or `V` |
| `invoke` works while `invokeExact` fails | `invoke` adapted the type via the `asType` mechanism | Compare the original `MethodType` and the call site; try an explicit `asType` |
| `invoke` reports `ClassCastException` | The runtime object does not match the adapter's cast | Observe the actual type of the argument, check boundary conversions |
| `invoke` reports `WrongMethodTypeException` | `asType` does not support the desired conversion | Check the `asType` API regarding primitive/reference/boxing |
| Trying `String x = mh.invokeExact(...)` causes a compile error | Without a direct cast, the return expression is `Object` | Write `(String) mh.invokeExact(...)` after verifying the handle's return type |
| `javap` shows `invokevirtual` instead of `invokedynamic` | This is the correct bytecode for `MethodHandle.invokeExact`/`invoke` | Distinguish signature-polymorphic invokevirtual from bootstrap-based invokedynamic |
| Viewing Reflection shows `invokeExact(Object[])` | Reflection represents the placeholder declaration, not every call-site descriptor | Use `javap` or `MethodHandle.type()` to inspect the right layer |
| Seeing `NoSuchMethodException` when creating a handle | `findStatic`/`findVirtual` could not find the exact method/signature | Check class, name, `MethodType`, and access permissions independently of the call site |

**Short diagnostic procedure:**

1. Print `handle.type()` right before the failing call; distinguish the original handle from an adapter handle.
2. Determine the **static type** of each argument in source, including `(Object)`, primitive boxing, and generic erasure.
3. See which return type the call is **directly** cast to, or whether the result is discarded, or used in another context.
4. Run `javap -c -p` on **the class file actually being executed**, and locate the exact `invokevirtual MethodHandle.invokeExact/invoke:...` instruction.
5. Compare the descriptor with `handle.type()`: exact requires equality; inexact requires a valid `asType` conversion.
6. If the descriptor matches yet it still fails, check runtime values, access/target exceptions, class loader/modules, and build sources.

**Note on optimization:** avoid turning APIs into `Object...` everywhere just to dodge type mismatches; instead, establish clear type contracts at dynamic boundaries, create purposeful adapters, and cache when justified. Performance decisions must be backed by reliable measurements.

## 9. Self-check exercises

**Question 1 — Predict the descriptor.** Suppose `h.type() == (int)long` (one int argument, returns long). Predict the descriptor for:

~~~java
long a = (long) h.invokeExact(5);
Object b = h.invokeExact(5);
h.invokeExact(5);
~~~

Answer: `(I)J`, `(I)Ljava/lang/Object;`, and `(I)V` respectively. For a `(int)long` handle, only the first expression has an exact matching type. These are **three illustrative expressions**, not a standalone program.

**Question 2 — Change variable declaration.** Replace `"java"` in the main program with `Object input = "java"` and call `(String) handle.invokeExact(input)`. Predict the error and explain why the runtime object type cannot save the descriptor.

**Question 3 — Inspect bytecode.** Find the line `invokeExact:(Ljava/lang/String;)V` in the `javap` output. Point out the corresponding Java statement and explain why discarding the return value changes the call-site type.

**Question 4 — Try an adapter.** Compare `(String) handle.invoke((Object) "api")` with `(Object) generic.invokeExact((Object) "api")`: what converts at the call site, and what is changed beforehand in the handle adapter?

**Question 5 — Distinguish from `invokedynamic`.** Explain why a call `handle.invokeExact("java")` is recorded with `invokevirtual` even though the method has a “dynamic” name/behavior. If you encounter `invokedynamic` in a class using lambdas, can you conclude that it is an `invokeExact` call?

**Question 6 — Nature of the return cast.** Why is:

~~~java
String s = (String) h.invokeExact("java");
~~~

different from:

~~~java
Object o = h.invokeExact("java");
String s = (String) o;
~~~

In the latter snippet, the cast happens **after the call**, so it does not alter the return descriptor of the `invokeExact` call site. If the handle returns `String`, the latter snippet throws `WrongMethodTypeException` before a value for `o` even exists. The two snippets are independent examples.

## 10. Takeaways

- **Signature polymorphism** for `MethodHandle.invokeExact`/`invoke` makes the call emit a descriptor from **the argument expression types and result context**, not from a fixed `Object[]` signature.
- `javac` records method references to `MethodHandle.invokeExact`/`invoke` with a **specific descriptor**; this Java call uses **`invokevirtual`**.
- **`handle.type()`** is the runtime type of the handle; the **descriptor** is the type requirement carried by the call site.
- **`invokeExact`** requires the two types to be equal, including the return type; a mismatch produces `WrongMethodTypeException`.
- **`invoke`** can perform `asType` adaptation, but does not accept every kind of conversion.
- A cast on an **argument** changes the descriptor's parameter type; a cast **directly on the call** determines the return type; using the call as a statement makes the return descriptor `V`.
- When confused, predict from the source first and then **verify with `javap`**, avoiding inferences from the argument's runtime class.
