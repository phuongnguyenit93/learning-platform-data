# 4.2 Identifying bridge methods and avoiding duplicate processing of generic methods

## 1. The problem: why does a Java method appear twice?

When using Reflection to scan `Class.getDeclaredMethods()` or `Class.getMethods()`, a class using generics can show **two `Method` objects related to the same behavior**, even though in the source code we only wrote one overriding method. One element is the method declared by the developer; the other element is a **bridge method** generated by the compiler to preserve proper overriding and polymorphism after compiling generics.

If a framework scans all methods to register endpoints, execute hooks, generate schemas, build action menus, or process annotations, it may register or invoke the same behavior twice. Conversely, if it deduplicates by **method name** or **name + parameter count**, the framework may mistakenly delete valid overloads.

Objectives of this lesson:

1. Explain the relationship between **type erasure**, **override**, **bridge method**, and **covariant return type**.
2. Identify bridge methods using `Method.isBridge()` and distinguish them from `Method.isSynthetic()`.
3. Correctly read metadata from `getDeclaredMethods()`, `getMethods()`, `getParameterTypes()`, `getReturnType()`, and `getDeclaringClass()`.
4. Build a method discovery workflow that **does not process bridges as separate business logic**, while preserving true overloads.
5. Know when filtering out bridges is sufficient and when it is necessary to **resolve a bridge back to its source method** to look up annotations/generic signatures.

> **Key point:** A bridge method is a real method in bytecode and can be invoked by the JVM. It “duplicates” in **business meaning** the target method it forwards to, not necessarily in JVM signature or `Method` object identity.

## 2. Why does the compiler generate bridge methods?

### 2.1. Generics undergo type erasure when compiled into bytecode

Java applies **type erasure**: an unbounded type variable, such as `T`, is replaced with `Object`; a bounded type variable is typically replaced with the appropriate bound (for example, `T extends Number` is erased to `Number`). The compiler also inserts the necessary casts.

Consider the contract:

```java
interface Transformer<T> {
    T transform(T value);
}

final class TrimTransformer implements Transformer<String> {
    @Override
    public String transform(String value) {
        return value.trim();
    }
}
```

In **source code**, `TrimTransformer.transform(String)` overrides `Transformer<String>.transform(String)`. However, after type erasure, the interface method takes the equivalent form `Object transform(Object)`, while the method written in the subclass remains `String transform(String)`. If only these two methods were kept, a call compiled against the `Transformer` type might not dispatch to the intended implementation.

To preserve polymorphism, `javac` can generate an intermediate method. Describing the mechanism in **pseudocode** (do not copy this snippet into the Java class above):

```java
// Bridge generated by the compiler in bytecode, NOT a Java declaration to write.
public Object transform(Object value) {
    return transform((String) value);
}
```

The bridge receives the parameter with the erased type, casts it, and forwards to `transform(String)`. Therefore:

- `transform(String)` is the **business method** written by the author.
- `transform(Object)` is the **bridge** so that calls through the erased contract still reach the implementation.
- If an attempt is made to pass a non-`String` value through the erased call path, the bridge's cast can throw `ClassCastException`. This is not “Reflection adding an error on its own”; it is part of the runtime type-safety mechanism.

How signatures are represented at the JVM level also helps explain this phenomenon: a descriptor contains **parameter types and return type**. In this example, the two corresponding descriptors can be:

```text
(Ljava/lang/String;)Ljava/lang/String;   // implementation
(Ljava/lang/Object;)Ljava/lang/Object;   // compiler bridge
```

In the **Java language**, overloads are not distinguished solely by return type. In the **class file/JVM**, two methods can differ in descriptor by return type or parameters; the compiler uses this capability to generate bridges that the developer cannot/does not need to declare manually.

### 2.2. Bridges also appear with covariant return types

Generics are not the only cause. Java allows a subclass to override a method returning `Number` with a method returning `Integer`:

```java
class ValueBase {
    public Number value() { return 10; }
}

class IntValue extends ValueBase {
    @Override
    public Integer value() { return 20; }
}
```

The source code has one method `IntValue.value(): Integer`. In the bytecode generated by `javac`, the subclass can also have a bridge `value(): Number` forwarding to `value(): Integer`. Here **the name and parameter list are identical**, but the return type differs: this is why `getDeclaredMethods()` can return both `Method` objects.

With covariant return types, deduplicating based solely on name and parameters can cause a framework to pick the bridge by mistake or lose information about the most specific return type.

### 2.3. Bridge and overload are two different concepts

- **Override:** Provides a concrete implementation for a parent class/interface contract. Bridges help preserve proper overriding after compilation.
- **Overload:** Multiple methods with **the same name but different parameter type lists** declared by the developer, for example `transform(String)` and `transform(CharSequence)`. They are distinct APIs and must not be discarded just because they share a name.
- **Bridge:** A compiler-generated method, typically delegating to an implementation. It may have a different parameter type list from the implementation (generic erasure) or differ only in return type (covariant override).

Do not infer that “same name” = “same method” or “same parameter count” = “same meaning”.

## 3. Reflection APIs for accurate identification

| API / attribute | Role | Things to remember |
| --- | --- | --- |
| `Class.getDeclaredMethods()` | Lists all methods **declared on that exact type**, including compiler-generated bridge/synthetic methods | Does not list purely inherited methods; order is not guaranteed |
| `Class.getMethods()` | Lists public methods of the type and eligible inherited ones | May include both public bridges and target methods; also includes methods from `Object` |
| `Method.isBridge()` | `true` if the method is a bridge | The most accurate and direct signal to identify a bridge via core Reflection |
| `Method.isSynthetic()` | `true` if the member is synthetic (compiler/tool-generated) | Bridges are usually synthetic; **synthetic does not mean bridge** |
| `Method.getParameterTypes()` | **Erased** parameter types as `Class<?>[]` | In the generic example, the bridge takes `Object`, the implementation takes `String` |
| `Method.getReturnType()` | Runtime JVM return type | A covariant bridge may return `Number`, while the implementation returns `Integer` |
| `Method.getGenericParameterTypes()` / `getGenericReturnType()` | `Type`, `TypeVariable`, `ParameterizedType` information if metadata is retained | Does not automatically resolve all generic substitutions across every inheritance level |
| `Method.getDeclaringClass()` | Class/interface that **declares** this method | Important when processing results from `getMethods()` which include inherited methods |
| `Method.getModifiers()` | Access flags, `static`, `abstract`... | `public` does not indicate whether a method is a bridge or not |

`getDeclaredMethods()` reflects the **class file**, not just the Java source code written by the author; therefore, the compiler may add methods with no corresponding source lines. And appearing in Reflection results does not mean the method can be invoked from every module or every access context.

Another easily misunderstood API: `getMethod("value")` and `getDeclaredMethod("value")` return **a single** method according to Reflection's selection rules. If there are methods with the same name/parameters but different return types, the API may prefer the more specific return type. Therefore, **do not use a single-method lookup to conclude a class has no bridge**: for complete analysis, enumerate and check `Method.isBridge()` on each one.

## 4. Standalone runnable example on Java 17+

The code below simultaneously demonstrates three phenomena: bridge due to erasure, bridge due to covariant return, and valid overloads that must be preserved.

Create **`BridgeMethodDemo.java`** with the following complete content:

```java
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.Comparator;
import java.util.Locale;
import java.util.stream.Collectors;

interface Transformer<T> {
    T transform(T value);
}

final class TrimTransformer implements Transformer<String> {
    @Override
    public String transform(String value) {
        return value.trim().toUpperCase(Locale.ROOT);
    }

    // Valid overload: same name and one parameter, different parameter type.
    public String transform(CharSequence value) {
        return value.toString();
    }

    // Second valid overload: two parameters.
    public String transform(String value, int repeat) {
        return value.repeat(repeat);
    }
}

class ValueBase {
    public Number value() {
        return 10;
    }
}

final class IntValue extends ValueBase {
    @Override
    public Integer value() {
        return 20;
    }
}

public class BridgeMethodDemo {
    private static String params(Method method) {
        return Arrays.stream(method.getParameterTypes())
                .map(Class::getSimpleName)
                .collect(Collectors.joining(","));
    }

    private static void printDeclared(Class<?> type) {
        Method[] methods = type.getDeclaredMethods();

        // Reflection does not guarantee order: sort for stable stdout.
        Arrays.sort(methods, Comparator.comparing(Method::getName)
                .thenComparing(BridgeMethodDemo::params)
                .thenComparing(m -> m.getReturnType().getSimpleName()));

        for (Method method : methods) {
            System.out.printf(
                    "%s(%s):%s bridge=%s synthetic=%s%n",
                    method.getName(),
                    params(method),
                    method.getReturnType().getSimpleName(),
                    method.isBridge(),
                    method.isSynthetic());
        }

        long userMethods = Arrays.stream(methods)
                .filter(method -> !method.isBridge())
                .count();
        System.out.println("user methods=" + userMethods);
    }

    public static void main(String[] args)
            throws ReflectiveOperationException {
        System.out.println("TrimTransformer");
        printDeclared(TrimTransformer.class);

        Method viaErasure = TrimTransformer.class
                .getMethod("transform", Object.class);
        Method source = TrimTransformer.class
                .getMethod("transform", String.class);

        System.out.println("lookup Object is bridge="
                + viaErasure.isBridge());
        System.out.println("lookup String is bridge="
                + source.isBridge());
        System.out.println("invoke bridge="
                + viaErasure.invoke(new TrimTransformer(), "  java  "));

        System.out.println("IntValue");
        printDeclared(IntValue.class);

        Method valueBridge = Arrays.stream(
                        IntValue.class.getDeclaredMethods())
                .filter(Method::isBridge)
                .findFirst()
                .orElseThrow();

        System.out.println("return bridge="
                + valueBridge.getReturnType().getSimpleName());
    }
}
```

Compile and run from the directory containing the file:

```bash
javac BridgeMethodDemo.java
java BridgeMethodDemo
```

**Stdout when compiled with `javac` on JDK 17+:**

```text
TrimTransformer
transform(CharSequence):String bridge=false synthetic=false
transform(Object):Object bridge=true synthetic=true
transform(String):String bridge=false synthetic=false
transform(String,int):String bridge=false synthetic=false
user methods=3
lookup Object is bridge=true
lookup String is bridge=false
invoke bridge=JAVA
IntValue
value():Integer bridge=false synthetic=false
value():Number bridge=true synthetic=true
user methods=1
return bridge=Number
```

**Reading the output:**

1. `TrimTransformer` has three author-written methods plus one bridge `transform(Object):Object`. If a framework treats all `getDeclaredMethods()` results as independent business operations, `transform(String)` risks being processed **twice**: once directly and once through the bridge.
2. `transform(CharSequence)` and `transform(String)` both take **one parameter**, but they are two real overloads. A rule like “once per name + parameter count” would mistakenly remove one of them.
3. `getMethod("transform", Object.class)` finds the bridge; `getMethod("transform", String.class)` finds the implementation. Invoking the bridge with `"  java  "` forwards to the implementation, so it returns `"JAVA"`.
4. `IntValue.value()` has an implementation returning `Integer` and a bridge returning `Number`. Both methods have the same name and **no parameters**, but different return types. `getDeclaredMethods()` lists both.
5. `isBridge()` accurately identifies both bridge methods; in this example `isSynthetic()` is also true for them. Do not infer in reverse that **every synthetic method is a bridge**.

In this example, `printDeclared` intentionally iterates only over methods of **the class itself**. If changed to `getMethods()`, the results will also contain inherited public methods, such as from `Object`; the counts or stdout above cannot remain the same.

## 5. How to avoid duplicate processing during method discovery

### 5.1. First determine the unit to collect

A tool that only wants **business methods declared directly by the developer** collects differently from a tool that wants **the entire inherited public API** or a **bytecode** analyzer.

- **Source-level API doc generation / handler registration:** typically starts from `getDeclaredMethods()`, filters out bridges, and then applies other business conditions (modifiers, annotations, access permissions).
- **Discovering public API including inheritance:** starts from `getMethods()`, filters out bridges when the bridge is not a separate API, and uses `getDeclaringClass()` and signatures to distinguish declaring sources.
- **Debugger / bytecode analyzer / JVM tooling:** may **need to keep bridges** because they genuinely exist in the class file and affect dispatch, stack traces, and invocation behavior. In this category, label bridges instead of removing them.
- **A framework that receives a `Method` that is itself a bridge:** do not merely skip it; it may be necessary to find **the target method the bridge forwards to** before reading annotations or generic types for business logic.

### 5.2. Safe filtering pattern for methods declared by a class

When the goal is simply to list business methods on **a specific class**, a minimal example is:

```java
// Snippet: requires importing java.lang.reflect.Method, java.util.Arrays,
// java.util.Comparator, and java.util.List.
List<Method> methods = Arrays.stream(type.getDeclaredMethods())
        .filter(method -> !method.isBridge())
        .sorted(Comparator.comparing(Method::getName)
                .thenComparing(m -> Arrays.toString(m.getParameterTypes()))
                .thenComparing(m -> m.getReturnType().getName()))
        .toList();
```

For `type = TrimTransformer.class`, this list keeps **all three author-written overloads** and drops the `transform(Object)` bridge. `toList()` is available since Java 16. This code is only a **snippet**, not a standalone file with `main`; it assumes the `type` variable already exists.

Depending on the product, if all compiler-generated methods must be excluded from user-facing screens, adding `!method.isSynthetic()` can be considered. However, **do not replace the bridge filter with a synthetic filter and assume the two concepts are identical**. Other synthetic methods (for example, compiler-generated helper methods) have their own roles and may need to be kept in runtime analysis tools.

**Important:** `filter(!isBridge())` is a sound way to avoid **counting a bridge as a separate business operation** during method discovery. It **is not a solver for all overriding, inheritance, proxy, or annotation scenarios**.

### 5.3. Why deduplicating by name or name + parameter count is wrong

Consider two error-prone approaches:

```java
// BUSINESS-LOGIC BUG: drops overloads with the same name.
Set<String> seen = new HashSet<>();
for (Method method : type.getDeclaredMethods()) {
    if (seen.add(method.getName())) {
        register(method);
    }
}

// STILL WRONG: transform(String) and transform(CharSequence)
// both have name="transform", parameterCount=1.
String key = method.getName() + "/" + method.getParameterCount();
```

This is **counterexample code**, not a complete program: `type`, `method`, and `register` are just illustrative symbols. Such deduplication may pick a bridge, drop the implementation, or delete a valid overload. Because Reflection does not guarantee array order, results can also vary between runs.

Better practices:

1. **Filter bridges by metadata flag** (`isBridge()`) if the goal is discovering business methods.
2. **Preserve full parameter types**, not just `parameterCount`. For bytecode analysis, the identifying key can include **declaring class, method name, parameter type list, and return type** (JVM descriptor). For Java-level APIs, handle overriding/hiding by their own rules and keep valid overloads intact.
3. **Sort explicitly** if stable output is needed. `getDeclaredMethods()` and `getMethods()` do not promise ordering.
4. **Count after filtering** if the metric represents the number of business actions/handlers; do not use `getDeclaredMethods().length` as the number of author-written methods.
5. **Do not call `Method.invoke` during the scan phase just to identify methods**. Doing so can cause side effects, consume resources, or mutate state. Reading metadata is sufficient to identify bridges.

Even `Set<Method>` is not an automatic solution: a bridge and its implementation can differ in parameter types or return type, so they are not necessarily treated as the same metadata object.

## 6. When must we resolve a bridge's target method?

Some frameworks receive a `Method` provided by a proxy, interceptor, reflection scan, or callback. If `method.isBridge() == true`, the framework may want to know the **original business method** in order to:

- Accurately look up annotations used for routing, validation, or serialization.
- Determine parameters and return type at the concrete implementation level.
- Build cache keys by business method, avoiding two keys representing the same behavior.
- Display the author-written method rather than the post-erasure signature.

In the runnable example above, the specific pair is clearly known:

```java
// Illustrative snippet, assuming the classes from the example above already exist.
Method bridge = TrimTransformer.class
        .getDeclaredMethod("transform", Object.class);
Method target = TrimTransformer.class
        .getDeclaredMethod("transform", String.class);

System.out.println(bridge.isBridge()); // true
System.out.println(target.isBridge()); // false
```

However, **JDK core Reflection does not have a general API like `getBridgedMethod()` to automatically return the target method**. You should not write a general algorithm using only “same name + same parameter count + not a bridge”, because `TrimTransformer` has both `transform(CharSequence)` and `transform(String)`; both of these methods have one parameter and neither is a bridge.

Resolving bridge-to-target reliably may require combining:

- Declaring type and generic hierarchy (`getGenericInterfaces()`, `getGenericSuperclass()`).
- Substituting type variables with the subclass's actual types, handling bounds and erasure.
- Method signatures, return types, and override compatibility.
- Forwarding bytecode analysis when JVM-level precision is truly needed, especially across different compilers/languages.

If the application already uses a framework that provides **bridge resolution**, use that framework's battle-tested solution, and test it against real generic/overload/covariant cases. Do not blindly pair a bridge with “the first candidate” from `getDeclaredMethods()`.

### 6.1. Annotations do not automatically “follow” every override

The annotation lookup policy must be clearly defined:

- `Method.getAnnotation(...)` inspects metadata on the `Method` passed in; it does not guarantee finding annotations on another overridden method or ancestor interface.
- `@Inherited` in Java applies to annotations on **classes**; it does not create an automatic inheritance mechanism for annotations on overridden methods.
- Compilers may copy certain annotations onto bridges in specific situations, but one compiler's behavior should not be turned into a universal contract for all compilers and all annotations.
- Therefore, a framework needs a consistent policy: read annotations on the implementation method, or actively search interfaces/superclasses if business logic requires it; when the input is a bridge, first resolve to the target method when appropriate.

**Do not** filter out bridges and then claim all annotation information “has been inherited properly”: those are two separate problems.

## 7. Edge cases and common misconceptions

### 7.1. `isBridge()` and `isSynthetic()` are not equivalent

Bridges from `javac` usually carry both `ACC_BRIDGE` and `ACC_SYNTHETIC` flags in the class file. However, synthetic can be used for other compiler-generated details. When the question is “is this a bridge?”, use **`isBridge()`**. Use `isSynthetic()` when the goal is broader filtering/recording of compiler-generated members.

### 7.2. Not every use of generics produces a bridge

`List<String>`, generic methods, generic classes, or using `T` do not automatically force bridge generation. A bridge appears when the compiler needs to reconcile source-level overriding semantics with bytecode/JVM-level method descriptors. **Observe the flags on the compiled class**, rather than guessing solely from the presence of `<...>` in source code.

### 7.3. Erasure does not always become `Object`

For example, `T extends Number` typically erases to `Number`; bounds can directly affect the bridge signature. Do not hard-code rules like “bridges always have `Object` parameters” or “bridges always return `Object`”. The covariant-return bridge in `IntValue` takes **0 parameters** and returns `Number`.

### 7.4. `getMethods()` includes inheritance; `getDeclaredMethods()` does not

`getDeclaredMethods()` on a subclass only considers methods **declared by that class**, including bridges declared by the compiler on that class. If methods from parent classes/interfaces are needed, `getMethods()` only provides **public** ones; to scan non-public methods of each superclass, you must traverse the hierarchy yourself. Do not merge results across multiple classes and deduplicate by name, because overrides, overloads, default methods, and bridges require distinct rules.

### 7.5. Not every pair of same-named methods involves a bridge

`static` methods are hidden according to hiding rules, not dynamically overridden like instance methods. Private methods do not override in the usual way. Overloads are different APIs. `isBridge()` avoids relying on guesses from names, access modifiers, or argument counts.

### 7.6. Generic reflection can show both source types and erased types

On the `Transformer<T>` interface, `getGenericParameterTypes()` may show `T` (`TypeVariable`); on the implementation it may be `String`, while on the bridge it is `Object`. To deduce `T -> String` across a chain of types/interfaces, type variables must be resolved in the **actual class context**. Calling `getGenericParameterTypes()` once does not automatically do all of that.

### 7.7. Watch out for compiler, build, and access control

The examples are based on Java 17+ and bridges generated by `javac`. Other compilers or transformed bytecode may add different synthetic methods. In addition, obtaining a `Method` via Reflection is not a license to bypass `private`/module boundaries; invocation may be subject to access checks. Verify framework assumptions against the actual bytecode of the built artifact.

## 8. Inspecting bridges directly in the class file

After compiling the example, you can inspect the bytecode with:

```bash
javap -p -c -v TrimTransformer
javap -p -c -v IntValue
```

In the `javap` output, look for methods with the same name as the implementation, the **`ACC_BRIDGE`** and **`ACC_SYNTHETIC`** flags, and forwarding bytecode such as `checkcast` and `invokevirtual` when present. Cross-check with the methods declared by the author. Do not rely on method position/order: `javap` and Reflection present methods according to different rules.

A meaningful verification workflow is:

1. Identify the business method in source code.
2. Confirm which bridge the compiler generates and where the bridge forwards.
3. Run Reflection to compare `isBridge()`, `isSynthetic()`, parameters, and return type.
4. Confirm the application's scan logic creates **one business handler** per target method, while still keeping distinct overloads.

These steps are especially helpful when a framework suddenly reports **“duplicate handler”** after adding a generic interface or changing an override's return type.

## 9. Practical application scenarios

| Context | Risk | Approach |
| --- | --- | --- |
| Writing a custom dispatcher/registry from `getDeclaredMethods()` | Registering a generic handler twice | Filter `isBridge()` when building the handler list; keep real overloads |
| Generating API docs from Reflection | Showing `Object -> Object` signature next to `String -> String` | Display the target method; note the bridge only if readers need bytecode details |
| Scanning annotations on methods | Missing annotations due to receiving a bridge, or wrongly merging parent annotations | Resolve the target method and apply an explicit annotation lookup policy at declaration/interface |
| Framework receiving a `Method` from an interceptor | Business cache stores both bridge and implementation | Normalize to the business method before building cache keys if context requires |
| Bytecode analysis, dispatch/stack trace measurement | Losing a real JVM method if bridges are filtered out | Keep bridges and attach `ACC_BRIDGE`/`isBridge()` metadata |
| Scanning inherited public methods via `getMethods()` | Mixing bridges, overloads, overrides, and `Object` methods | Filter by scope/`getDeclaringClass()`; resolve method inheritance before converting to actions |

## 10. Self-check exercises

**Exercise 1.** `interface Repository<T> { T save(T x); }` and `class StringRepository implements Repository<String>` with `public String save(String x)`. Why might `save(Object)` appear when calling `getDeclaredMethods()`?  
**Answer:** `Repository<T>.save(T)` erases to `save(Object)`; the compiler generates a bridge so calls through the erased contract dispatch to `save(String)`. Check with `isBridge()`.

**Exercise 2.** `getDeclaredMethods()` returns `run(String)` and `run(Integer)`, both with `isBridge() == false`. Should one method be removed using the key `"run/1"`?  
**Answer:** No. These are two valid overloads with the same parameter count but different parameter **types**.

**Exercise 3.** A subclass overrides `Number value()` with `Integer value()`. Why do two `Method` objects have the same name and zero parameters but different return types?  
**Answer:** The bridge for covariant return can have a signature returning `Number`; the source method returns `Integer`. The JVM descriptor includes the return type.

**Exercise 4.** A `Method` has `isSynthetic() == true`. Can we conclude for certain that `isBridge() == true`?  
**Answer:** No. Synthetic is a broader category. Use `isBridge()` to identify bridges.

**Exercise 5.** A framework receives the bridge from `getMethod("transform", Object.class)` and needs the annotations of `transform(String)`. Should it take the first non-bridge method with the same name?  
**Answer:** No. There may be an overload `transform(CharSequence)` with the same name/parameter count. Bridge-to-target mapping must be resolved using generic types/hierarchy and override rules, then the annotation lookup policy applied.

**Exercise 6.** When building a bytecode analysis tool, should all bridges be discarded from the start?  
**Answer:** No. Bridges are real JVM methods and must be kept to understand dispatch and bytecode; only filter them from **business** lists if that is the requirement.

## 11. Checklist when building a method scanner

- Precisely define the target: methods of **one class**, public methods **with inheritance**, or all methods **in bytecode**.
- For business lists, check `isBridge()` before registering/invoking a method.
- Preserve overloads by **actual parameter types**, not merging by name/parameter count.
- Do not trust Reflection ordering; sort results when stable output is needed.
- If a received `Method` is a bridge and source annotations/signatures are needed, perform verified **bridge-to-target** resolution; do not pick candidates using naive heuristics.
- Distinguish `isSynthetic` from `isBridge`, generic source types from erased types, and source methods from JVM method descriptors.
- Test at least the cases of **generic interface, covariant return, same-arity overloads, inheritance**, and bytecode produced by the compiler actually used in the project.

**Remember:** Bridges are generated to preserve Java's correctness after type erasure/covariant override. For business-oriented Reflection, choose the **target method** and exclude bridges from independent registration; for bytecode-reading tools, keep bridges as real members. **Never “dedup” by method name.**
