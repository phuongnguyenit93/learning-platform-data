# 11.7 Bootstrap May Be Executed Concurrently: Designing Safe Side Effects

`invokedynamic` moves the selection of a method call target from compile time to **runtime linking time**. When an `invokedynamic` instruction is not yet linked, the JVM invokes a *bootstrap method* (BSM) to produce a `CallSite` with a suitable call target. The tricky and easily overlooked point is: if multiple threads reach an unlinked call site at the same time, the JVM **is permitted to invoke the same bootstrap concurrently**. The JVM will choose **one linking result** as the `CallSite` for that instruction and discard the remaining results, but **it does not roll back side effects** performed by the bootstrap invocations that were not chosen.

Therefore, **"an instruction is only linked successfully once" does not mean "the bootstrap only runs once"**. If a BSM writes to a registry, registers a listener, creates an external resource, increments a business counter, starts a thread, or emits an event, relying on the "runs only once" assumption can cause duplicates, data races, resource leaks, or inconsistent state.

This article focuses directly on **bootstrap concurrency**, the difference between **the result chosen by the JVM** and **side effects that have already occurred**, along with safe designs: pure-computation bootstraps, immutable configuration, thread-safe caches, *idempotency keys*, durable transactions, lifecycle control, and testing. The examples use **Java 17+**, including a program that invokes the BSM directly from multiple threads to test concurrent behavior **in a controlled way**, and a program containing a real `invokedynamic` generated by `javac` to inspect the class file.

## 1. Under What Model Is an invokedynamic Instruction Linked?

In bytecode, `invokedynamic` does not reference a fixed target method like `invokestatic`. The class file has `CONSTANT_InvokeDynamic` and `BootstrapMethods` entries describing:

- **Bootstrap method handle**: the code the JVM invokes to decide the target.
- **Call name** (name) and **call type** (`MethodType`) requested by the call site.
- **Optional static bootstrap arguments**: metadata embedded in the class file to configure the bootstrap.
- **Instruction location**: each `invokedynamic` instruction is a specific linking point; it is not identical across all call sites using the same name or the same bootstrap.

A BSM typically has the signature:

```java
public static CallSite bootstrap(
        MethodHandles.Lookup caller,
        String name,
        MethodType type,
        /* static arguments if any */)
        throws Throwable
```

This is an **illustrative signature**, not a standalone program. The first three parameters usually have the following meanings:

| Argument | Purpose |
| --- | --- |
| `caller` | Permissions and the class containing the instruction being linked; `caller.lookupClass()` often helps identify the caller |
| `name` | Symbolic name at the call site, for example `apply` or `dispatch` |
| `type` | Required runtime signature, for example `(String)String` |
| Static args | Logical ID, target handle, configuration flags, policy, or immutable data provided by the class file |

The BSM **must return a non-null `CallSite`**, and `callSite.type()` must match the type requested by the `invokedynamic` instruction. A `ConstantCallSite` keeps a fixed target; `MutableCallSite` or `VolatileCallSite` can change the target after linking, with different visibility rules. The choice of CallSite type is a **different** issue from the fact that the BSM can run concurrently during linking.

General path:

```text
unlinked invokedynamic
          |
          v
JVM resolves BSM, name, MethodType, static args
          |
          v
calls BSM in the thread attempting to execute the instruction
          |
          v
BSM creates a CallSite with a matching type
          |
          v
JVM selects / installs the instruction's linking result
          |
          v
subsequent executions invoke the target through the linked CallSite
```

An instruction that has been successfully linked does not automatically re-link just because the caller continues running. If `MutableCallSite` is used to change the target afterward, **changing the target is not re-running the BSM**. Nor should you call `bootstrap(...)` manually and think that is an operation asking the JVM to re-link the instruction.

## 2. What Happens When Multiple Threads Hit a Call Site for the First Time?

Java Virtual Machine Specification 17, `5.4.3.6, allows threads that are simultaneously resolving a symbolic reference to execute the bootstrap **concurrently**. If multiple BSM invocations occur, the JVM selects the result of **one invocation** and installs it so that threads see it; the other BSMs may continue running to completion, but their results are discarded.

Imagine:

```text
                  instruction X: unlinked invokedynamic
Thread T1:   BSM(X) ---------> CallSite A ----                                               Thread T2:     BSM(X) -------> CallSite B -------+--> JVM selects one result
                                               /       installs for X
Thread T3:   BSM(X) ---------> CallSite C ----/         other results discarded
                                                             |
                       side effects of A, B, C can still occur
```

This is **one possible interleaving**, not the number of BSM calls that every JVM is required to perform. A JVM may also serialize linking and invoke the bootstrap only once. **Do not verify correctness by "on my machine I only saw it once"**.

### 2.1. What Does the JVM Guarantee — and What Does It Not Guarantee?

| What can be relied upon | What must not be inferred |
| --- | --- |
| An `invokedynamic` instruction that is successfully linked will have one `CallSite` chosen by the JVM | The BSM is executed exactly once across the entire process |
| Threads use the linking result published by the JVM | The side-effect sections of all BSMs have been serialized or rolled back |
| A valid BSM result must have a type matching the instruction | If a BSM fails, the JVM will "keep retrying until there is a good result" for future calls |
| Subsequent executions of the linked instruction use the same linkage | Other instructions using the same name/type/bootstrap will automatically share one CallSite |
| Concurrent BSMs may create different `CallSite` instances | The JVM always picks the CallSite created first, fastest, or by thread ID |

**"One CallSite is chosen" does not mean "one CallSite object is created".** If T1, T2, and T3 all execute `new ConstantCallSite(...)`, they can create three objects; one object is chosen to link X, while the others can become garbage for GC if no references retain them. However, if each BSM also opens a socket, registers a callback in a global registry, or writes to a database, those side effects **do not automatically disappear** when the CallSite object is discarded.

### 2.2. Why Doesn't the JVM Simply Guarantee the BSM Runs Exactly Once?

The dynamic linking model allows multiple threads to attempt executing the same unresolved instruction. The specification prioritizes the rule of **selecting one observable linking result**, rather than granting the BSM an automatic "execute-once" lock that wraps all application changes. A BSM is Java code that can access shared state and throw exceptions, so BSM authors must apply synchronization, immutability, and side-effect policies just as with ordinary multithreaded code.

**Connection to `CONSTANT_Dynamic`:** dynamic constants also use a bootstrap upon resolution; specification `5.4.3.6` describes similar concurrency possibilities. However, the focus of this article is **`invokedynamic` CallSites**, so do not confuse a dynamic constant with a method-invocation instruction.

## 3. Distinguishing Three "Counts" That Are Easily Conflated

For an instruction X, you should separate:

1. **Bootstrap attempts**: how many times the BSM is actually invoked while threads race.
2. **Logical initialization/registration**: how many times the system performs a business action that should only happen once per logical key.
3. **JVM-installed linkage**: the CallSite result selected by the JVM for instruction X.

For example, T1 and T2 run the BSM simultaneously, each incrementing `attempts`. A safe design can have `attempts==2` (accurate for the *attempts* metric) while only performing **one** setup of `registry` for the same key. The JVM still selects only one result for X. You should not compute the number of installed CallSites by counting how many times the BSM executed — the BSM **has no standard callback reporting "I am the winner"**.

If you want a "linked call sites" metric, you must name and define the measurement convention honestly; do not attach that label to a counter incremented inside the BSM. Even if you observe `attempts==1` on a specific JVM, that does not establish a contract applicable to other platforms.

## 4. Which Side Effects Are Most Dangerous?

| Side effect in BSM | Risk when BSM runs concurrently | Recommended design |
| --- | --- | --- |
| `counter++` on a regular field | Lost updates, races, and measuring the wrong kind of metric | `AtomicInteger`/`LongAdder` if counting attempts is needed |
| `new Thread(...).start()` | Launches multiple workers while only one CallSite is used | Move lifecycle outside the BSM or register via an idempotent gate |
| Sending email, writing an invoice, debiting an account | External action is duplicated, irreversible consequences | Do not perform in BSM; if mandatory, require an idempotency key + external system transaction |
| Registering a listener/route in a global map | Duplicate callbacks, listener leaks, or overwriting state | `ConcurrentHashMap.computeIfAbsent` with immutable values, or a lifecycle-managed registry |
| Opening a connection/file/socket | Loser may still hold the resource, increasing cost and leaking | Avoid opening in BSM; use a resource pool with clear ownership and close policy |
| Building a cache key from `name + type` | Different sites accidentally share state | Key includes caller identity and static site ID if required by the contract |
| Emitting a `BOOTSTRAP_DONE` event | Event may be emitted multiple times even though only one linkage is chosen | Distinguish attempt events from once-only business events |
| Updating a shared `MutableCallSite` | Unrelated sites accidentally change behavior together | Create a separate CallSite if independent targets are wanted; handle visibility separately |

The following **unsafe** pattern has a race:

```java
// Illustrative anti-pattern: not a standalone program.
static boolean registered;
static void onBootstrap() {
    if (!registered) {
        registerListener();    // May be executed twice.
        registered = true;
    }
}
```

Two threads can both see `registered == false` and both call `registerListener()`. A `volatile boolean registered` variable helps visibility, but **does not turn check-then-act into an atomic operation**: both can still pass the condition before either thread writes `true`.

An `AtomicBoolean.compareAndSet(false,true)` can establish an at-most-once gate for a simple internal action, but failure must be considered: if the thread sets the gate to true and then the action fails, other threads think initialization is already complete. For complex resources, use a `NEW → INITIALIZING → READY/FAILED` state machine, a shared future, or a lifecycle manager. For external side effects, in-process CAS **does not guarantee exactly-once** if the process crashes/restarts.

## 5. Design Principle: Keep the BSM as Purely Computational as Possible

The easiest design to review:

```text
BSM receives Lookup + name + MethodType + static args
  -> validate type/metadata
  -> select an already-authorized MethodHandle
  -> combine/adapt handle (asType, insertArguments, filter...)
  -> create ConstantCallSite
  -> return CallSite
```

These steps mainly create local metadata/handles and produce results independent of the order in which threads run. If the BSM can run twice and each time returns a **semantically equivalent** CallSite, which result the JVM chooses makes no business difference.

A well-designed BSM should:

- **Be deterministic with respect to contract inputs**: the same metadata and valid configuration yield an equivalent target; if the system is intentionally dynamic, the state being read must follow consistent rules.
- **Have no non-idempotent side effects**: do not charge money, send emails, or register listeners multiple times.
- **Not publish partially initialized objects**: shared structures must be immutable or safely published.
- **Handle errors in a controlled manner**: verify the handle can be invoked with the requested `MethodType` before returning the CallSite, avoiding mutating external systems and only then throwing an exception due to a type mismatch.
- **Not hold broad locks during complex resolution**: a BSM can trigger class loading, handle lookup, initialization, or nested bootstraps. Global locks increase the risk of contention/reentrancy/deadlock.

This does **not** mean a BSM must be strictly pure; many runtime linkers have practical needs for caches/registries. However, side effects must have explicitly defined idempotency, thread-safety, error, and lifetime contracts.

### 5.1. Local Allocation Differs from Global Side Effects

Creating a separate `ConstantCallSite`, a `MethodHandle`, or an immutable configuration object per BSM attempt is generally safe: only objects that are actually still referenced survive long-term. Conversely, registering every object in a static list/map turns losers into long-lived objects and can leak memory.

Do not put `registry.add(site)` logic inside a BSM and assume that "the JVM will automatically unregister the loser". The JVM provides no such rollback mechanism.

## 6. Java 17+ Program: Forcing Two Concurrent Bootstrap Calls

The following example demonstrates how to write a BSM that **tolerates being called multiple times**. It performs a *manual bootstrap invocation* test: two Java threads **directly call** the same `bootstrap` method with the same metadata. This tests the thread safety/idempotency of the BSM code, but **is not** `invokedynamic` bytecode for the JVM to pick a winner. We are not simulating the JVM's CallSite installation algorithm.

Create the file **`IndyBootstrapSafetyDemo.java`**:

```java
import java.lang.invoke.CallSite;
import java.lang.invoke.ConstantCallSite;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;
import java.util.concurrent.Callable;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class IndyBootstrapSafetyDemo {
    record SiteKey(Class<?> caller, String logicalId) {}

    private static final ConcurrentHashMap<SiteKey, String> CONFIG = new ConcurrentHashMap<>();
    private static final AtomicInteger attempts = new AtomicInteger();
    private static final AtomicInteger registrations = new AtomicInteger();

    public static String dispatch(String configuration, String input) {
        return configuration + ":" + input;
    }

    public static CallSite bootstrap(MethodHandles.Lookup caller, String name,
                                     MethodType type, String logicalId)
            throws ReflectiveOperationException {
        attempts.incrementAndGet(); // Count attempts, not installed JVM call sites.
        SiteKey key = new SiteKey(caller.lookupClass(), logicalId);
        String configuration = CONFIG.computeIfAbsent(key, ignored -> {
            registrations.incrementAndGet();
            return "policy-" + logicalId;
        });

        MethodHandle raw = MethodHandles.lookup().findStatic(
                IndyBootstrapSafetyDemo.class, "dispatch",
                MethodType.methodType(String.class, String.class, String.class));
        MethodHandle bound = MethodHandles.insertArguments(raw, 0, configuration);
        return new ConstantCallSite(bound.asType(type));
    }

    public static void main(String[] args) throws Throwable {
        MethodType type = MethodType.methodType(String.class, String.class);
        CountDownLatch ready = new CountDownLatch(2);
        CountDownLatch start = new CountDownLatch(1);
        ExecutorService workers = Executors.newFixedThreadPool(2);
        try {
            Callable<CallSite> job = () -> {
                ready.countDown();
                start.await();
                return bootstrap(MethodHandles.lookup(), "run", type, "demo-site");
            };
            Future<CallSite> firstTask = workers.submit(job);
            Future<CallSite> secondTask = workers.submit(job);
            if (!ready.await(5, TimeUnit.SECONDS)) {
                throw new IllegalStateException("workers did not start");
            }
            start.countDown();
            CallSite first = firstTask.get();
            CallSite second = secondTask.get();

            System.out.println("attempts=" + attempts.get());
            System.out.println("registrations=" + registrations.get());
            System.out.println("cachedKeys=" + CONFIG.size());
            System.out.println("siteTypesEqual=" + first.type().equals(second.type()));
            System.out.println("first=" + (String) first.dynamicInvoker().invokeExact("A"));
            System.out.println("second=" + (String) second.dynamicInvoker().invokeExact("B"));
        } finally {
            start.countDown();
            workers.shutdownNow();
        }
    }
}
```

Compile and run:

```bash
javac --release 17 IndyBootstrapSafetyDemo.java
java IndyBootstrapSafetyDemo
```

Program `stdout` when both tasks complete properly:

```text
attempts=2
registrations=1
cachedKeys=1
siteTypesEqual=true
first=policy-demo-site:A
second=policy-demo-site:B
```

**Explanation:**

1. `CountDownLatch` ensures both tasks are ready before opening the `start` gate. The experiment always **calls bootstrap twice**; it does not depend on whether the JVM itself creates `invokedynamic` linking contention.
2. `attempts` counts the two actual invocations using `AtomicInteger`. It is **not** the number of CallSites installed by the JVM.
3. `CONFIG.computeIfAbsent(key, ...)` ensures that setting the cache value for the **same key** is coordinated atomically. In this test with no errors/removals of this entry, the initialization lambda runs once, so `registrations=1` and `cachedKeys=1`.
4. Each `bootstrap` call creates **its own `ConstantCallSite`**; both have a valid `type` and equivalent targets. In real `invokedynamic` linking, the JVM can pick one of the equivalent results, whereas this demo program **does not declare a winner itself**.
5. `MethodHandles.insertArguments(raw,0,configuration)` pre-binds the configuration to the `dispatch(String,String)` target so the final target has type `(String)String`; `bound.asType(type)` adapts the target type to match the BSM request. Not every type can be validly adapted, so a production BSM must still validate `type`.

**Important limitation of `computeIfAbsent`:** in `ConcurrentHashMap`, the mapping function is coordinated on the same key when computing an absent value; it should be short and avoid recursively modifying the same map. If the mapping function throws an exception, the entry may not be stored and a subsequent call may retry. Therefore, **do not put a non-repeatable external transaction inside the mapping function and call that exactly-once**. `registrations` in the code only measures one successful in-memory initialization in the example, and does not represent a transaction durable across crashes.

## 7. Observing a Real invokedynamic Generated by javac

Standard Java source has no keyword to directly write arbitrary `invokedynamic` bytecode. In a Java 17 program, a lambda expression or method reference is typically compiled by `javac` into an `invokedynamic` linked by `LambdaMetafactory`. This is a way to inspect a **real instruction** without needing ASM, external libraries, or a bytecode generator.

Create the file **`IndyLambdaInspection.java`**:

```java
import java.util.function.IntUnaryOperator;

public class IndyLambdaInspection {
    static IntUnaryOperator add(int delta) {
        return value -> value + delta;
    }

    public static void main(String[] args) {
        IntUnaryOperator op = add(3);
        System.out.println("lambda=" + op.applyAsInt(4));
    }
}
```

```bash
javac --release 17 IndyLambdaInspection.java
java IndyLambdaInspection
javap -c -p IndyLambdaInspection
javap -v -p IndyLambdaInspection
```

The **`stdout` of the `java` command**:

```text
lambda=7
```

When inspecting the `javap` output, look for two signs (constant pool index formatting may vary across compilers/builds):

- In the bytecode of `add(int)`, there is an `invokedynamic` instruction corresponding to creating the `IntUnaryOperator` for the lambda.
- In `BootstrapMethods`, there is a method handle pointing to `java.lang.invoke.LambdaMetafactory.metafactory`. The class may also contain another `invokedynamic` for string concatenation in `println`; that is a different bootstrap mechanism, not an extra BSM run for the same lambda instruction.

**Important:** `javap` proves that the class file contains `invokedynamic` and bootstrap references; it **does not** count how many times the BSM is executed by the JVM at runtime. Nor can you use an uncontended run to conclude that the JVM will always call the BSM once. The purposes of the two programs are clearly separated: the `IndyBootstrapSafetyDemo` example tests the concurrency/idempotency of **a BSM you wrote**; the `IndyLambdaInspection` example illustrates a **real invokedynamic instruction**.

## 8. Choosing an Idempotency Key with the Right Scope

This is one of the hardest decisions in a BSM with side effects. You must not assume the key `(name,type)` is unique for an instruction:

- Two different instructions in the **same class** can share the same `name` and `MethodType`, and even the same bootstrap method handle.
- Two different classes can have the same name and descriptor at their call sites. In plugin applications, classes with the same binary name loaded by **different class loaders** are different `Class<?>` instances.
- Static arguments can carry different configurations. If the key does not include the configuration attributes that need to be distinguished, the cache will mix state.
- There are cases where **intentionally sharing** a logical configuration across multiple sites is desired; in that case, keying by *logical feature* is reasonable, but that must be a deliberate decision, not a default optimization.

A key selection table:

| Kind of data to cache | Principled key | Notes |
| --- | --- | --- |
| Immutable configuration shared for a feature | `(tenant, featureId, version)` if defined by the contract | Does not depend on which BSM wins; ensure loader/tenant isolation |
| Metadata specific to the caller class | `(caller.lookupClass(), configId)` | `Class<?>` reflects identity together with loader; a strong cache can keep the class loader alive |
| Data specific to each instruction | An ID **uniquely assigned** to the instruction from static args or external metadata | `(caller,name,type)` alone does not guarantee distinguishing two instructions |
| Attempts metric | Keyed according to observability needs (caller/site/feature) | Name it attempts, do not name it installed |
| An external transaction requiring once-only | Business idempotency key with a durable unique constraint | Do not rely on the identity of an arbitrary CallSite object |

In the example, `SiteKey(Class<?> caller,String logicalId)` is used to illustrate caching a **logical registration** by caller class and explicit ID. It is **not** claimed to be a unique key for every instruction if two instructions intentionally use the same `logicalId`. To distinguish them, the bytecode generator needs to pass a static argument identifying the specific site or use an architecture with a registry managing specific instructions.

### 8.1. Avoiding Class Loader Leaks

A long-lived static cache holding `Class<?>`, `Lookup`, `MethodHandle`, `CallSite`, or plugin instances can keep the entire class loader alive, causing hot reload/unload to fail. If you need to cache by caller class, consider `ClassValue`, a cache with an explicit lifecycle, weak keys, and an appropriate cleanup policy. **Do not** use an unbounded static `ConcurrentHashMap` just because it is thread-safe: thread safety is different from memory-lifecycle safety.

## 9. If Side Effects Are Unavoidable: Define the Guarantee Level

### 9.1. At-Most-Once Within a Single JVM Process

An `AtomicBoolean` gate or a map/future can ensure multiple BSM attempts coordinate so that **one thread performs the initialization** for a key. However:

```java
// Illustrative idea; lacks recovery if registerService() fails.
if (installed.compareAndSet(false, true)) {
    registerService();
}
```

This snippet assumes `installed` is an `AtomicBoolean`, and is not a standalone program. If `registerService()` fails after the CAS, the flag remains true and other threads may skip the failed initialization. If the registration operation itself takes a long time, other threads need to **wait for the READY state**, not just see that "someone else has started".

A more complete in-memory design uses a `CompletableFuture<Registration>` cache per key, creating the future with a thread-safe primitive, having one worker run the initializer and complete the future, while waiters wait together for success/failure. You must define retry, cancellation, timeout, reentrancy, and removal of the future on error to avoid a dead state.

### 9.2. Exactly-Once in External Systems Does Not Happen Automatically

A BSM should not directly charge a payment, issue an invoice, or send a notification as an action that must happen exactly once. CAS and `computeIfAbsent` only protect **the memory of the current process**. When the process crashes after the remote system receives the request but before recording success, a retry can create a duplicate.

If the side effect cannot be avoided, you need:

- A durable business idempotency key, independent of threads and CallSite instances.
- A unique constraint/transaction or a remote API that supports idempotent requests.
- Recording `PENDING / COMPLETED / FAILED` state and checking the result before retrying.
- An outbox/inbox or an event-processing mechanism capable of deduplication.
- A dedicated lifecycle manager for the bootstrap/linker if resources need to be rolled back or unused temporary resources need to be closed.

The safest approach is usually to **move business side effects out of the BSM** to the target execution point or an application service step that already has explicit transactions/idempotency. Even so, a side effect moved to the target can still run multiple times when the target is called multiple times; if once-only is required, a separate gate must exist at the appropriate layer.

### 9.3. Do Not Unintentionally Share a Mutable CallSite

If a BSM returns a `MutableCallSite` from a shared cache for multiple instructions, those instructions may end up using the same object. Calling `setTarget` will affect **every instruction sharing that object**, not just one site.

If the application needs **each site to retarget independently**, the BSM should create a separate `MutableCallSite` for each requested result, rather than handing out the same singleton object from a cache. Conversely, sharing the object can be a valid design when you want the same routing policy to be updated all at once; in that case, you must document the semantics and visibility policy clearly.

Also distinguish:

- `ConstantCallSite`: target is fixed after creation.
- `MutableCallSite`: target can change; visibility across threads is not automatically volatile-like; `MutableCallSite.syncAll(...)` is the specific synchronization mechanism when updating targets.
- `VolatileCallSite`: target has volatile semantics for reading/writing the target; suitable if updated frequently and visibility under that contract is needed.

These choices address **changing the target after linking**, and do not replace the rule that the BSM can be called concurrently during initial linking.

## 10. BSM Failure: Do Not Rely on the JVM Retrying Automatically

If a BSM throws an exception, the JVM applies linking error rules:

- If the error is `Error` or a subclass, per the specification it may propagate that error according to the resolution mechanism.
- If the BSM throws a non-`Error` exception, the linking failure is represented by `BootstrapMethodError` with the corresponding cause.
- If the BSM returns `null`, an object that is not a `CallSite`, or a `CallSite` with the wrong type, resolution is invalid and raises `BootstrapMethodError`.
- For an instruction that has failed resolution, **there is no contract that "each call invokes the bootstrap again to try once more"**. The linking failure result is recorded for subsequent resolutions according to JVM rules.

Do not write a BSM like:

```java
// Anti-pattern: side effect may succeed and then the type check fails.
chargeCustomer();
return new ConstantCallSite(wrongTypeHandle);
```

The snippet above is only an illustrative anti-pattern. If `wrongTypeHandle` does not match the required `MethodType`, linkage fails **after** the customer has already been charged. Another competing thread could also charge. The fact that "the call site cannot be used" does not undo the transaction that already occurred.

**A better sequence:**

1. Validate the name, `MethodType`, metadata, and lookup permissions.
2. Find/adapt the handle, verify `target.type().equals(type)` or perform a controlled adaptation.
3. Prepare a valid local `CallSite` with no dangerous side effects.
4. Only register thread-safe configuration/caching if this is genuinely a required part of the contract; prefer immutable and idempotent caches.
5. Return the `CallSite`. If it fails, log the cause clearly, do not swallow the error, and do not rely on automatic retries.

**Race limitation when both success and failure occur:** the specification allows concurrent bootstrap attempts; do not infer that the runtime will definitely pick the result of the successful attempt or retry on the next request. Design so that every valid attempt under the same metadata yields an equivalent result and does not need "winner/loser" side effects.

## 11. Reentrancy, Class Initialization, and Deadlock

A BSM does not only run application logic; it can also trigger resolution of other classes, method handles, static arguments, or dynamic constants. A BSM can also indirectly trigger another call site or the related linking logic itself.

Situations to watch out for:

- Holding `synchronized(globalRegistry)`, then calling `Class.forName` or performing complex reflection/class loading; another thread holds the class-initialization lock and is waiting on the registry lock.
- Inside `computeIfAbsent`, the mapping function calls code that comes back to update the same map/key — this is not guaranteed to be safe; it can fail or cause blocking/unexpected behavior.
- The BSM accesses a static field whose class initializer in turn calls into the very dynamic site currently being resolved.
- Initializing dependencies inside the BSM and then waiting on another thread that is blocked by class initialization or a lock held by the BSM.
- The BSM creates a target that depends on a mutable global configuration that has not been properly published.

According to the JVM spec, certain bootstrap resolution cycles can lead to `StackOverflowError` due to nested calls. You should not use recursion inside a BSM as a "retry until success" mechanism. Keep the BSM **fast, with minimal locking, minimal I/O, and minimal auxiliary initialization**, and avoid re-entering the same site while it is not yet linked.

## 12. Testing Properly: Do Not Rely on a Single invokedynamic Run

**Functional testing** confirms the target accepts the right arguments and returns the right type. **Concurrency testing** confirms the BSM tolerates multiple attempts and shared state has idempotency. **JVM linkage testing** confirms the real class file has the expected `invokedynamic` and bootstrap metadata. These three types complement each other; they do not replace one another.

| Test | Goal | What must not be inferred |
| --- | --- | --- |
| Call BSM manually from 2–100 threads with latch/barrier | Tolerance of concurrent invocation and cache/key logic | The real JVM is guaranteed to run the BSM that many times |
| Use `javap -v` | Inspect `CONSTANT_InvokeDynamic` and `BootstrapMethods` of the class file | How many times the bootstrap method executes at runtime |
| Run stress tests across multiple JDKs/CPUs | Find data races, deadlocks, duplicates, timing issues | Passing stress tests proves every interleaving is correct |
| Inject failures into initializer/cache | Check retry, cleanup, and not leaving `INITIALIZING` state forever | The JVM will automatically retry a failed linkage |
| Two call sites with the same `name/type` but different static args | Ensure keys do not collide across logical sites | The triple caller/name/type always identifies an instruction |
| Repeated plugin load/unload | Detect classloader leaks caused by static caches | `ConcurrentHashMap` automatically cleans up the cache when a plugin unloads |

### 12.1. Designing a Meaningful Stress Test

For a custom BSM that can be called directly, tests should:

1. Use the **same request key** for all tasks to test real contention on a single logical registration.
2. Synchronize the starting point with `CountDownLatch` or `CyclicBarrier`, not just `Thread.sleep`.
3. Retrieve the result of each `Future` and verify **every returned CallSite has the right type** and equivalent behavior.
4. Verify the number of *attempts* with a thread-safe counter; know in advance the number of deliberate calls in the harness.
5. Verify once-only side effects as far as possible: cache size, registration count, final state, and error policy.
6. Test a mapping function that throws an exception or times out; ensure no half-initialized configuration is left behind.
7. Separate the "BSM attempted" metric from "logical registration", "linkage success", and "target invocation".
8. Independently test cases with two different logical IDs, two different caller classes, or two different class loaders.
9. Do not add `synchronized` logging on the hot path and then assume test results still represent normal interleavings; instrumentation can inadvertently mask races.
10. If the system has durable side effects, test crash/restart and retry with the same idempotency key, not just runs within the same JVM.

### 12.2. Criteria for a Safe BSM

A good code review should be able to answer:

```text
BSM input:
  Lookup lookup, String name, MethodType type, staticArgs ...
Semantic site identity:
  explicitly defines caller + logicalId (or similar), does not guess uniqueness
Local target construction:
  pure / equivalent across competing attempts
Shared registry:
  thread-safe, immutable values, defined cleanup
External side effect:
  absent (preferred) or durable idempotency + error recovery
CallSite:
  non-null; type exactly expected; mutable-sharing intentional?
Failure:
  BootstrapMethodError? invalid metadata? who owns cleanup?
Observability:
  attempts != installed CallSites != invocation count
Testing:
  manual concurrency + real classfile inspection + failure injection
```

If a BSM has no answer for **"what did the losing attempt do?"**, **"is retrying after an error safe?"**, and **"how does the cache key distinguish two sites?"**, that design should not yet be considered safe for production.

## 13. Common Misconceptions

| Statement or observation | True/false and explanation |
| --- | --- |
| "Since it is the same instruction, bootstrap is called only once" | **False.** The JVM can run multiple concurrent bootstrap attempts for an unlinked instruction |
| "Only one CallSite is chosen, so side effects happen only once too" | **False.** Losing BSMs may complete their side effects; only their CallSite results are discarded |
| "Using `AtomicInteger` makes side effects once-only" | **False.** An atomic counter counts attempts accurately, but does not prevent a business operation from running multiple times |
| "`volatile boolean done` + check-then-act is enough" | **False.** The check and the action are not atomic as a single transaction |
| "With `ConcurrentHashMap.computeIfAbsent`, an external charge is exactly-once" | **False.** Errors, retries, crashes, and multiple processes can happen; durable idempotency is required |
| "`name + MethodType` distinguishes each invokedynamic instruction" | **Not guaranteed.** Multiple instructions can match; a contract ID is needed to distinguish them |
| "If BSM fails, the call site retries automatically when another thread calls it" | **No such contract.** Linkage errors are recorded according to JVM rules |
| "`MutableCallSite.setTarget` calls bootstrap again" | **False.** Retargeting happens after linkage and does not re-run bootstrap |
| "The BSM log count on this JVM is always 1, so the code is fine" | **Insufficient.** The spec allows concurrency; testing one execution schedule does not prove safety |
| "You should just share CallSites to save memory" | **Depends.** A shared mutable target can couple sites that ought to be independent |
| "Creating a ConstantCallSite every time is a duplicate side effect" | **Not necessarily.** Local allocation/GC is different from registration or non-idempotent I/O |
| "The JVM picks the BSM that finishes fastest" | **Not promised.** Do not rely on any specific winner-selection policy |

## 14. Self-Check Exercises

**Exercise 1.** Two threads simultaneously run a BSM for an unlinked instruction; each BSM calls `mailService.sendWelcomeEmail()` and then returns a `ConstantCallSite`. The JVM picks only one CallSite. Can two emails be sent?

**Answer:** Yes. The JVM picks one *linking result*; it does not roll back the loser's side effects. Do not send the welcome email directly from the BSM; route the task through an idempotent workflow.

**Exercise 2.** A BSM uses `static int registrations; registrations++;` to measure the number of linked sites. What two bugs are there?

**Answer:** `registrations++` is not atomic so it has a data race; at the same time, it counts bootstrap attempts (not even accurately due to the race), **not** the number of sites installed by the JVM.

**Exercise 3.** Two BSM attempts simultaneously call `ConcurrentHashMap.computeIfAbsent` with the same key, and the mapping function returns a normal value without removing the key. Can this be used as an in-memory configuration cache?

**Answer:** Yes, if the key and data are properly scoped and the value is safely published. It does not mean external exactly-once across exceptions or process restarts; the mapping function must be short and avoid reentrancy.

**Exercise 4.** Two instructions in the same class use `name="route"`, `type=(String)String`, but their static argument `siteId` is `"A"` and `"B"`, respectively. Should you cache by `(callerClass,name,type)` to create separate state?

**Answer:** No, because that key collides for both. If state must be separate, add `siteId` or an ID guaranteed to distinguish them to the key.

**Exercise 5.** A BSM returns `new ConstantCallSite(handle)`, but `handle.type()` differs from the type requested by the instruction. What is the consequence?

**Answer:** Linkage is rejected with `BootstrapMethodError` according to the JVM's validation rules. You should validate/adapt the type before performing side effects.

**Exercise 6.** In a manual test, `attempts=2` and `registrations=1`. Can you conclude that the JVM installed one of those two CallSites into the bytecode?

**Answer:** No. The test **calls the BSM directly from Java code**; it does not execute a custom `invokedynamic` instruction. It tests the concurrency of the BSM, not the JVM's result-selection/installation step.

**Exercise 7.** A BSM caches and shares a single `MutableCallSite` for two different instructions. Later, `setTarget` is called. What needs to be reviewed?

**Answer:** Both instructions can share the target change of the same object. If independence is required, each site must have its own CallSite; if sharing is intentional, a visibility policy (`syncAll` or considering `VolatileCallSite`) must be specified.

**Exercise 8.** Thread T1 marks `initialized=true` with CAS before writing the config; T2 sees true and uses the config. Is this safe?

**Answer:** Not yet. CAS only wins the right to execute; it does not prove the config is ready. You must publish the `READY` state **after** initialization succeeds and provide an appropriate mechanism to wait or receive errors.

**Remember:** do not write a bootstrap based on the assumption "the JVM only calls me once". Build the BSM so that **every attempt is safe**, including attempts that do not win: prefer *pure/local work*, use a thread-safe cache with an intentional key, keep state fully published, separate attempt metrics from linkage, and push external side effects to a controlled idempotent protocol. **One installed linkage does not mean one execution of side effects.**
