# 16.7 Receiving Bytecode in Memory and Defining a Class in the Appropriate Context

## 1. The Problem: From Source Code/Bytecode to an Executable `Class<?>`

In a dynamic Java runtime, **compilation** and **class definition** are two separate stages:

1. **Compiling/generating:** takes Java code or a DSL structure and produces standard **class file** bytecode. You can use `javax.tools.JavaCompiler` to compile Java source code right inside the JVM, or use a valid bytecode generator.
2. **Receiving and holding bytes:** collects the `byte[]` of the `.class` file in memory instead of necessarily writing it to an output directory.
3. **Defining:** converts the exact `byte[]` into a `Class<?>` inside the chosen **class loader, module, package, and permission context**.
4. **Linking and using:** obtains a `MethodHandle`, the Reflection API, or a common interface to invoke the newly created logic; manages dependencies and lifecycle.

This lesson focuses on the question: **once bytecode is in memory, how should the class be defined so that it is in the right context?**

Three main options on Java 17+:

| Definition Method | Class Kind | Where It Is Defined | Special Requirements | Best Suited For |
| --- | --- | --- | --- | --- |
| `ClassLoader.defineClass(name, bytes, 0, length)` | **Named class** | A loader that you actively manage (often a child loader) | Subclass of `ClassLoader`, valid binary name/bytes, valid delegation/package/security | Plugins, rules, or named implementations with their own loader/lifecycle |
| `MethodHandles.Lookup.defineClass(bytes)` | **Named class** | **Same loader/module/runtime package** as the lookup class | Lookup must have `PACKAGE` access; package name in bytes must match | Adding a class into the already-trusted context itself |
| `MethodHandles.Lookup.defineHiddenClass(bytes, initialize, options...)` | **Hidden class** | **Same loader/module/runtime package** as the lookup class; not discoverable by binary name | Lookup with **full privilege** (`PRIVATE` + `MODULE`), bytes in the same package | Dynamically generated lambdas/adapters/internal implementations, no `Class.forName` needed |

**Clear distinction:** `JavaCompiler` **does not automatically load** the new class, and `ClassLoader.defineClass`/**`Lookup.defineClass`** **do not automatically compile** source code. `getTask(...).call()` returning `true` only confirms that the compilation task completed successfully; you still need the appropriate bytes and the exact definition mechanism.

### Objectives After This Lesson

You will know how to:

- Use `SimpleJavaFileObject`, `ForwardingJavaFileManager`, and `JavaCompiler.CompilationTask` to receive `.class` outputs as a `Map<String,byte[]>`.
- Distinguish **binary name**, **class identity**, **defining loader**, **runtime package**, **module**, **Lookup capability**, and **class initialization**.
- Run three Java 17 demos: loading a named class from memory with a child ClassLoader; defining a named class via `Lookup.defineClass`; and creating a hidden class via `Lookup.defineHiddenClass`.
- Understand why `Class.forName(name)` only succeeds when using the **appropriate loader** and when the named class can be found; hidden classes cannot be found with `Class.forName`.
- Analyze compilation diagnostics errors, package mismatch, duplicate definition, `ClassFormatError`, `LinkageError`, permission/module failures, and untrusted code risks.

## 2. Processing Flow Diagram

```text
Java source / DSL / bytecode generator
                 |
                 v
JavaCompiler or bytecode producer
                 |
                 v
byte[] of each class file (Map<binaryName,byte[]>)
                 |
        +--------+------------------------+
        |                                 |
        v                                 v
Custom ClassLoader                   MethodHandles.Lookup
  findClass -> defineClass              |             |
        |                            defineClass  defineHiddenClass
        v                                 |             |
 named class in                       named class     hidden class
 child loader                         same context    same context
        |                                 |             |
        +---------------------------------+-------------+
                                          |
                                 Class<?> / MethodHandle
                                          |
                                     invoke/use
```

**A single class file is not enough for every program.** One source can generate multiple class files, such as top-level classes, nested classes (`Outer$Inner`), and auxiliary structures. Compiler output must be collected **per binary name**. If generated bytecode references other classes, the JVM needs to find them through the **defining loader** and appropriate resolution rules.

**Definition is not synonymous with initialization.** A named class defined with `defineClass` is usually only defined/linked, while the static initializer runs when active use is required. `Class.forName(name, true, loader)` can proactively initialize it. A hidden class lets you choose `initialize=true/false` directly in `defineHiddenClass`.

## 3. First Step: Receiving Bytecode Without Writing the Target Class File to Disk

The Java Compiler API resides in the `java.compiler` module, package `javax.tools`. A **JDK with a compiler** provides `ToolProvider.getSystemJavaCompiler()`. In a runtime image without a compiler or in a stripped-down JRE environment, this method may return `null`.

To use the API completely in memory for **the target class's source and output**, you need:

1. A source `JavaFileObject` with `Kind.SOURCE`; its content is read from a `String` via `getCharContent()`.
2. An output `JavaFileObject` with `Kind.CLASS`, writing to a `ByteArrayOutputStream` via `openOutputStream()`.
3. A `ForwardingJavaFileManager` that intercepts the compiler's `getJavaFileForOutput(...)`; the rest delegates to the standard file manager.
4. A `DiagnosticCollector<JavaFileObject>` to read compilation errors/warnings.
5. Call `compiler.getTask(...).call()`, check for `Boolean.TRUE`, and retrieve the `byte[]` **after the task finishes**.

**Limitation of the example:** although the source and the new `.class` file are kept in memory, the standard file manager can still read JDK modules, the classpath, JARs, and metadata from the file system. It does **not** mean the compiler never touches disk for any internal operation, nor is it a sandbox.

### 3.1. Shared File: `demo/runtime/MemoryCompiler.java`

The example below is a **runnable Java 17** utility shared across the next three programs. Each demo program is run in a separate JVM and uses this same helper. Place the file in the right package location.

```java
package demo.runtime;

import javax.tools.*;
import java.io.*;
import java.net.URI;
import java.nio.charset.StandardCharsets;
import java.util.*;

public final class MemoryCompiler {
    private MemoryCompiler() { }

    static final class Source extends SimpleJavaFileObject {
        private final String source;

        Source(String binaryName, String source) {
            super(URI.create("string:///"
                    + binaryName.replace('.', '/')
                    + Kind.SOURCE.extension), Kind.SOURCE);
            this.source = source;
        }

        @Override
        public CharSequence getCharContent(boolean ignoreEncodingErrors) {
            return source;
        }
    }

    static final class Bytecode extends SimpleJavaFileObject {
        final ByteArrayOutputStream buffer = new ByteArrayOutputStream();

        Bytecode(String binaryName, Kind kind) {
            super(URI.create("mem:///"
                    + binaryName.replace('.', '/')
                    + kind.extension), kind);
        }

        @Override
        public OutputStream openOutputStream() {
            return buffer;
        }

        byte[] bytes() {
            return buffer.toByteArray();
        }
    }

    static final class CapturingFileManager
            extends ForwardingJavaFileManager<StandardJavaFileManager> {
        private final Map<String, Bytecode> outputs = new HashMap<>();

        CapturingFileManager(StandardJavaFileManager delegate) {
            super(delegate);
        }

        @Override
        public JavaFileObject getJavaFileForOutput(
                Location location, String className, JavaFileObject.Kind kind,
                FileObject sibling) {
            Bytecode output = new Bytecode(className, kind);
            outputs.put(className, output);
            return output;
        }

        Map<String, byte[]> copyBytes() {
            Map<String, byte[]> result = new HashMap<>();
            outputs.forEach((name, output) ->
                    result.put(name, output.bytes()));
            return Map.copyOf(result);
        }
    }

    public static Map<String, byte[]> compile(
            String binaryName, String javaSource) throws IOException {
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null) {
            throw new IllegalStateException(
                    "A JDK with java.compiler is required");
        }

        DiagnosticCollector<JavaFileObject> diagnostics =
                new DiagnosticCollector<>();

        try (StandardJavaFileManager standard =
                     compiler.getStandardFileManager(
                             diagnostics, Locale.ROOT,
                             StandardCharsets.UTF_8)) {
            CapturingFileManager memory =
                    new CapturingFileManager(standard);

            Boolean success = compiler.getTask(
                    null, memory, diagnostics,
                    List.of("--release", "17", "-proc:none"),
                    null, List.of(new Source(binaryName, javaSource))
            ).call();

            if (!Boolean.TRUE.equals(success)) {
                StringBuilder message =
                        new StringBuilder("Compilation failed");
                for (Diagnostic<? extends JavaFileObject> diagnostic
                        : diagnostics.getDiagnostics()) {
                    message.append("\n")
                           .append(diagnostic.getKind())
                           .append(" line ")
                           .append(diagnostic.getLineNumber())
                           .append(": ")
                           .append(diagnostic.getMessage(Locale.ROOT));
                }
                throw new IllegalArgumentException(message.toString());
            }
            return memory.copyBytes();
        }
    }
}
```

### 3.2. Why Is Each Part Necessary?

- `Source` is treated by the compiler as a **source file**, even though the Java source bytes are already in a `String`. The URI `string:///demo/runtime/Foo.java` describes a logical path, **not** an instruction to create a real file.
- `Bytecode` collects all requested output into a `ByteArrayOutputStream`. Call `bytes()` after the compilation task finishes to receive the complete `byte[]`.
- `CapturingFileManager.getJavaFileForOutput(...)` receives the **className reported by the compiler**, rather than guessing the output from the main class name. As a result, secondary outputs such as `Outer$Inner` are also kept in the map when the compiler generates them.
- `ForwardingJavaFileManager` still uses the standard manager for locating JDK APIs/classpath; it only replaces how the compilation task writes outputs.
- `DiagnosticCollector` holds `kind`, `lineNumber`, and message information. If compilation failed, the helper **does not** return the output map to avoid using potentially incomplete bytes.
- `--release 17` selects the appropriate Java 17 source/bytecode/API level; `-proc:none` disables annotation processing in **this compilation task** so the example stays controllable. These options **do not** turn the compiler or bytecode into a sandbox.
- `Map.copyOf(...)` creates an unmodifiable map in terms of key/value mappings, but the **`byte[]` inside are still mutable**. The helper copies each buffer into an array; callers should avoid mutating the array after inspection/definition or make another copy when strong immutability is needed.

### 3.3. What This Utility Does Not Implement Yet

This is a **one source unit per compile** example, sufficient for the three demos. If you want the compiler to reference **previously compiled classes that exist only in memory**, you need a fuller file manager: providing those class files via `getJavaFileForInput`, `list`, `inferBinaryName`, and an appropriate classpath, or compiling multiple source units in **a single compilation task**. Modifying only `getJavaFileForOutput` does not automatically make the compiler see bytecode dependencies in a map from a previous compilation.

In production, you also need to handle locale/version-level diagnostics, allowlisted compiler options, maximum sizes, file manager concurrency/lifecycle, and dependencies. Do not reuse the same `CapturingFileManager` concurrently across multiple compilation tasks without a synchronized design.

## 4. Option 1 — ClassLoader.defineClass: Named Class in Its Own Loader

When a plugin/rule needs a **binary name that can be looked up again with the right loader**, a `ClassLoader` subclass is usually the easiest approach to control:

1. Override `findClass(String binaryName)` to look up the output map.
2. Call `defineClass(binaryName, byte[], 0, bytes.length)`.
3. Let the default `loadClass` handle **parent delegation** (parent-first), unless there is a good reason to change the policy and design special synchronization.
4. Use `Class.forName(name, initialize, customLoader)` or `customLoader.loadClass(name)` to obtain the exact named class.

**Important:** `defineClass` is a `protected final` method on `ClassLoader`; it cannot be called directly on an arbitrary class loader from anywhere. You invoke it **inside the subclass**. The name passed in must match the binary name recorded in the bytes; a mismatch can throw `NoClassDefFoundError`, and forbidden package names or invalid signers/sealing can cause a `SecurityException`.

### 4.1. File `demo/runtime/MemoryLoaderDemo.java`

```java
package demo.runtime;

import java.lang.invoke.*;
import java.util.Map;

public class MemoryLoaderDemo {
    static final class BytecodeLoader extends ClassLoader {
        private final Map<String, byte[]> definitions;

        BytecodeLoader(ClassLoader parent, Map<String, byte[]> definitions) {
            super(parent);
            this.definitions = definitions;
        }

        @Override
        protected Class<?> findClass(String name)
                throws ClassNotFoundException {
            byte[] bytes = definitions.get(name);
            if (bytes == null) {
                throw new ClassNotFoundException(name);
            }
            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Throwable {
        String name = "generated.memory.Greeter";
        String code = """
                package generated.memory;
                public class Greeter {
                    public static String hello(String who) {
                        return "Hello " + who;
                    }
                }
                """;

        Map<String, byte[]> classes = MemoryCompiler.compile(name, code);
        BytecodeLoader loader = new BytecodeLoader(
                MemoryLoaderDemo.class.getClassLoader(), classes);

        Class<?> greeter = Class.forName(name, true, loader);
        MethodHandle hello = MethodHandles.publicLookup().findStatic(
                greeter, "hello",
                MethodType.methodType(String.class, String.class));

        System.out.println("bytes captured: "
                + classes.containsKey(name));
        System.out.println("loaded name: " + greeter.getName());
        System.out.println("same loader: "
                + (greeter.getClassLoader() == loader));
        System.out.println("call: "
                + (String) hello.invokeExact("runtime"));

        try {
            Class.forName(name);
            System.out.println("unexpected parent found class");
        } catch (ClassNotFoundException expected) {
            System.out.println("parent forName: not found");
        }

        Class<?> another = Class.forName(name, true,
                new BytecodeLoader(
                        MemoryLoaderDemo.class.getClassLoader(), classes));
        System.out.println("separate loader distinct: "
                + (greeter != another));
    }
}
```

### 4.2. Run Commands

Create the two files `MemoryCompiler.java` and `MemoryLoaderDemo.java` in `demo/runtime/`; from the root directory containing `demo/`:

```bash
javac -encoding UTF-8 --release 17 -d out demo/runtime/MemoryCompiler.java demo/runtime/MemoryLoaderDemo.java
java -cp out demo.runtime.MemoryLoaderDemo
```

Verified stdout with an equivalent demo:

```text

loaded name: generated.memory.Greeter
same loader: true
call: Hello runtime
parent forName: not found
separate loader distinct: true
```

### 4.3. Explaining the Output

- The source `generated.memory.Greeter` appears **only in a String**; `MemoryCompiler` creates a map entry with the binary name key `generated.memory.Greeter` and the class file bytes as the value.
- `BytecodeLoader.findClass` creates the class from bytes **when the loader is asked to find that binary name**. `Class.forName(name,true,loader)` uses the right loader and can also initialize the class.
- `MethodHandles.publicLookup().findStatic(...)` creates a handle for a public method on a public class in an unnamed module/accessible package in the classpath example. In a named-module deployment, you must account for `exports`/readability in the proper context.
- `Class.forName(name)` **without passing a loader** uses the caller's loader. Because `Greeter` is not on the application loader's classpath in this demo, it throws `ClassNotFoundException`.
- Two different `BytecodeLoader` instances both define `generated.memory.Greeter` from **the same bytes** yet produce **two distinct `Class` objects**. Class identity depends on **binary name + defining loader**; two instances of two different `Class` objects are not type-compatible just because their names are the same.
- The example chooses the package name `generated.memory` to avoid colliding with a class in the parent loader. If the parent can already load the same name, parent-first delegation may pick **the class from the parent** instead of the new bytes in the map.

### 4.4. Boundaries When Extending the Loader

A plugin with multiple classes needs a map containing **all related class outputs**. When one class references another, the JVM asks its defining loader to resolve the dependency; `findClass` must be able to look up the appropriate bytes or the parent must provide the dependency.

Even though the Java package name string may be identical, two classes belonging to **two different defining loaders** are not by default in the same **runtime package** according to the JVM; package-private access can be blocked. Do not try to define a new class in a child loader and expect it to automatically have package-private access to a class of the same package name defined by the application loader.

A named class in a child loader typically belongs to **that loader's own unnamed module** when using this demo's mechanism. It does not automatically become a member of a named module or gain permission to access another module's package-private internals.

## 5. Option 2 — Lookup.defineClass: Adding a Named Class to the Caller's Package

If the goal is to define **a named class in the same runtime package, module, class loader, and protection domain** as an existing class, `MethodHandles.Lookup.defineClass(byte[])` is a better fit than creating a child loader.

Key characteristics:

- The API directly returns the **`Class<?>`** of the new named class.
- The Lookup must have **`PACKAGE` access**; it does not require **full privilege** like `defineHiddenClass`. A lookup from `MethodHandles.lookup()` in a valid caller class has the required modes.
- The binary name recorded in the bytes must be in the **same package as the lookup class**, and the JVM determines the runtime package/module/class loader from the lookup class.
- The class is **named**: it can be found by binary name through the appropriate loader after definition.
- You cannot define **two classes with the same binary name in the same defining loader**: the second attempt normally throws a `LinkageError` (e.g., duplicate definition).
- `defineClass` has no `initialize` parameter; the static initializer will run at the point required by Java class initialization rules.

### 5.1. File `demo/runtime/MemoryLookupDemo.java`

```java
package demo.runtime;

import java.lang.invoke.*;

public class MemoryLookupDemo {
    public static void main(String[] args) throws Throwable {
        String name = "demo.runtime.InlineGenerated";
        String code = """
                package demo.runtime;
                public class InlineGenerated {
                    public static String ping() {
                        return "LOOKUP";
                    }
                }
                """;

        byte[] bytes = MemoryCompiler.compile(name, code).get(name);
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        Class<?> defined = lookup.defineClass(bytes);

        MethodHandle ping = lookup.findStatic(
                defined, "ping", MethodType.methodType(String.class));
        System.out.println("named hidden? " + defined.isHidden());
        System.out.println("same loader? "
                + (defined.getClassLoader()
                        == MemoryLookupDemo.class.getClassLoader()));
        System.out.println("forName finds named? "
                + (Class.forName(name) == defined));
        System.out.println("named invoke: "
                + (String) ping.invokeExact());

        try {
            lookup.defineClass(bytes);
        } catch (LinkageError expected) {
            System.out.println("duplicate definition: rejected");
        }

        try {
            MethodHandles.publicLookup().defineClass(bytes);
        } catch (IllegalAccessException expected) {
            System.out.println("publicLookup defineClass: denied");
        }

        String wrongName = "generated.other.Outsider";
        byte[] wrong = MemoryCompiler.compile(wrongName, """
                package generated.other;
                public class Outsider { }
                """).get(wrongName);
        try {
            lookup.defineClass(wrong);
        } catch (IllegalArgumentException expected) {
            System.out.println("wrong package: denied");
        }
    }
}
```

Compile together with the `MemoryCompiler.java` helper:

```bash
javac -encoding UTF-8 --release 17 -d out demo/runtime/MemoryCompiler.java demo/runtime/MemoryLookupDemo.java
java -cp out demo.runtime.MemoryLookupDemo
```

Verified stdout:

```text
named hidden? false
same loader? true
forName finds named? true
named invoke: LOOKUP
duplicate definition: rejected
publicLookup defineClass: denied
wrong package: denied
```

**Explanation:**

1. The helper produces bytes from `demo.runtime.InlineGenerated` **in memory**. That class file is **not** a file on the application's classpath, so it does not automatically appear just because the compiler finished.
2. `lookup.defineClass(bytes)` defines the class **in the loader/module/package of `MemoryLookupDemo`**. Unlike a child loader, no separate loader needs to be created and it can share the appropriate runtime package.
3. `Class.forName(name) == defined` is true: the new class is a **named class** and the caller's defining loader knows about it after `defineClass`.
4. `lookup.findStatic(defined, "ping", ...)` links to the defined method, returning `LOOKUP`.
5. A second `defineClass(bytes)` call on the **same loader and same binary name** is rejected. Do not use `Lookup.defineClass` as a **hot-swap** mechanism or to automatically overwrite an existing class.
6. `publicLookup()` lacks `PACKAGE` access, so it is rejected with `IllegalAccessException`.
7. Bytes named `generated.other.Outsider` are not in the same `demo.runtime` package as the lookup class, so `defineClass` throws `IllegalArgumentException`.

### 5.2. Why Not Just Use ClassLoader for Everything?

A class in a child loader can have the same **package name string** as the host yet still not share the same **runtime package** or module, so it is not granted package-private/protected access like host code under many JVM rules. `Lookup.defineClass` is advantageous when a framework **has the appropriate privileges** and wants the generated class to join the **same trusted context** as the lookup class.

In return, because the new class is defined in the host's loader, it generally lives for that loader's lifecycle; you must ensure unique binary names and avoid unbounded growth in class count/metaspace. Do not use the host's Lookup privileges to bring untrusted bytecode into the same module/package.

## 6. Option 3 — Lookup.defineHiddenClass: Internal Implementations Without Name Lookup

If the runtime only needs a class linked via `Class<?>`, `MethodHandle`, or an interface, and does not need `Class.forName(binaryName)`, then `Lookup.defineHiddenClass` may be appropriate.

Syntax:

```java
MethodHandles.Lookup hiddenLookup =
        MethodHandles.lookup().defineHiddenClass(bytes, false);
Class<?> hidden = hiddenLookup.lookupClass();
```

**Differences from `Lookup.defineClass`:**

- `defineHiddenClass` returns a **`Lookup`**, not `Class<?>` directly. The returned Lookup has the appropriate access to the hidden class.
- Requires the caller Lookup to have **full privilege access**, including `PRIVATE` and `MODULE`. `publicLookup()` is definitely not sufficient.
- The bytes must still describe a class in the **same package** as the lookup class.
- A hidden class has `Class.isHidden() == true` and a diagnostic name with a suffix, but **has no binary name that can be looked up by name**. `Class.forName(hidden.getName())` cannot locate a hidden class.
- You can define **multiple hidden classes from the same bytes** without binary name collisions in the way named classes have; each call gets a distinct identity.
- `initialize=false` allows deferring class initialization until active use. `initialize=true` initializes during definition.
- `ClassOption.NESTMATE` lets the hidden class become a nestmate of the lookup class under JVM rules; `ClassOption.STRONG` strongly ties the hidden class's lifecycle to the defining loader. Neither option **turns** a hidden class into a named class.
- By default, a hidden class can be unloaded independently when no live references remain; **exact GC/unloading timing cannot be guaranteed**.

### 6.1. File `demo/runtime/MemoryHiddenDemo.java`

```java
package demo.runtime;

import java.lang.invoke.*;

public class MemoryHiddenDemo {
    public static void main(String[] args) throws Throwable {
        String name = "demo.runtime.HiddenGenerated";
        String code = """
                package demo.runtime;
                public class HiddenGenerated {
                    static {
                        System.out.println("<clinit> HiddenGenerated");
                    }
                    public static String run() {
                        return "HIDDEN";
                    }
                }
                """;

        byte[] bytes = MemoryCompiler.compile(name, code).get(name);
        MethodHandles.Lookup base = MethodHandles.lookup();
        MethodHandles.Lookup lazy =
                base.defineHiddenClass(bytes, false);
        Class<?> hidden = lazy.lookupClass();

        System.out.println("hidden? " + hidden.isHidden());
        System.out.println("same package? "
                + hidden.getPackageName().equals(
                        MemoryHiddenDemo.class.getPackageName()));
        System.out.println("canonical name null? "
                + (hidden.getCanonicalName() == null));

        try {
            Class.forName(hidden.getName());
        } catch (ClassNotFoundException expected) {
            System.out.println("forName hidden: not found");
        }

        MethodHandle run = lazy.findStatic(
                hidden, "run", MethodType.methodType(String.class));
        System.out.println("before first invoke");
        System.out.println("invoke: "
                + (String) run.invokeExact());

        System.out.println("before eager define");
        Class<?> eager =
                base.defineHiddenClass(bytes, true).lookupClass();
        System.out.println("distinct classes? "
                + (hidden != eager));

        Class<?> nestmate = base.defineHiddenClass(
                bytes, false,
                MethodHandles.Lookup.ClassOption.NESTMATE,
                MethodHandles.Lookup.ClassOption.STRONG
        ).lookupClass();
        System.out.println("nestmate host? "
                + (nestmate.getNestHost() == MemoryHiddenDemo.class));
        System.out.println("strong still hidden? "
                + nestmate.isHidden());

        try {
            MethodHandles.publicLookup().defineHiddenClass(
                    bytes, false);
        } catch (IllegalAccessException expected) {
            System.out.println("publicLookup defineHiddenClass: denied");
        }
    }
}
```

Run commands:

```bash
javac -encoding UTF-8 --release 17 -d out demo/runtime/MemoryCompiler.java demo/runtime/MemoryHiddenDemo.java
java -cp out demo.runtime.MemoryHiddenDemo
```

Verified stdout:

```text
hidden? true
same package? true
canonical name null? true
forName hidden: not found
before first invoke
<clinit> HiddenGenerated
invoke: HIDDEN
before eager define
<clinit> HiddenGenerated
distinct classes? true
nestmate host? true
strong still hidden? true
publicLookup defineHiddenClass: denied
```

**Reading the output:**

1. The hidden class indeed has `isHidden() == true` and is in the same package as the host. Although `getName()` returns a string of the form `demo.runtime.HiddenGenerated/...`, that is **not a class name to pass to `Class.forName`**. The demo does not print the suffix because the suffix is JVM-generated and unstable.
2. `defineHiddenClass(bytes,false)` defines the hidden class without running the static initializer yet. `findStatic` can create a `MethodHandle` to the method, and then on the **first invocation** the JVM initializes the class and prints `<clinit> HiddenGenerated`.
3. `defineHiddenClass(bytes,true)` creates **another hidden class** and initializes it immediately, so the initializer runs a second time. The two classes have two separate identities, not the same class being re-initialized.
4. `NESTMATE` makes the hidden class join the lookup class's nest; `STRONG` changes unloading lifecycle, but the hidden class still cannot be found by name. Do not draw conclusions about GC behavior from this output alone.
5. `publicLookup()` lacks full privilege, so `defineHiddenClass` throws `IllegalAccessException`.

### 6.2. A Hidden Class Is Not a Class "Nobody Can Call"

A hidden class can still implement a **named interface** known to the host, return an instance via a factory, or provide method handles. It simply cannot be **nominally referenced/resolved by binary name** in the usual way. This is useful when generating interpreter adapters, lambda implementations, or DSL specializations.

Conversely, if you need to store a class name in a database and later use `Class.forName` on a subsequent startup to restore it, a hidden class **does not meet that goal**. Store the input/bytecode template and create a new implementation when needed, or choose a named class.

## 7. Decision Rules by Context, Not by Habit

| Design Question | Answer and Appropriate API |
| --- | --- |
| Need a class **with a binary name**, looked up via its own class loader, with version lifecycle isolation? | Create a child loader + `ClassLoader.defineClass`; query with `Class.forName(name, true, loader)`. |
| Need a **named** class in the **same module/package/loader** as the host to share valid privileges/package access? | Use `Lookup.defineClass` with a Lookup having `PACKAGE` access and bytes in the right package. |
| Need a dynamically generated implementation, held only via `Class<?>`/handle, no name lookup needed, wanting multiple classes from the same template? | Use `Lookup.defineHiddenClass` with full privilege and the appropriate package. |
| Need a class that can be looked up by name via an existing loader? | Use a **named class**; hidden classes cannot be used with `Class.forName`. |
| Want to define a class into a package of another module that the host does not own? | No API is a "free privilege bypass". You need a valid API/Lookup/module boundary design first. |
| Want to replace the bytecode of an already-loaded class without changing its identity? | `defineClass` is not hot-swap; consider Java Instrumentation/agents under supported contracts, or create a new version in another loader and switch dispatch. |
| Want to execute untrusted code safely? | Do not use defineClass/hidden as a sandbox; you need real isolation and a different security policy. |

### 7.1. Class Identity Is `(binary name, defining loader)` for Named Classes

Two classes with the same binary name defined by **two different loaders** are two **different runtime types**. This affects:

- `instanceof`, casts, and method parameter types;
- package-private access (the runtime package depends on the loader/module, not just the name string);
- static state (each class has its own copy of state);
- registries, DI containers, and caches;
- unloadability (references to the loader/class/method handles can keep the loader alive).

A **shared interface defined by the parent loader** is usually a good bridge between the host and plugin classes in a child loader. If each plugin loader defines its own copy of an interface with the same name, casting to the host-loaded interface can **fail** despite identical names.

## 8. From Compiler Output to Definition: Safe Implementation Order

A serious pipeline should go through clear steps:

1. **Choose name and namespace:** decide allowed binary names/packages, target class loader/module, and whether the class needs to be discoverable by name.
2. **Validate the source:** do not accept arbitrary source code if the user lacks execution privileges. Enforce size limits, version, expected class count, compiler options, dependencies, and timeouts at the system layer.
3. **Compile in memory:** pass the `SOURCE` `JavaFileObject`, collect `CLASS` outputs, and handle diagnostics. If compilation fails, do not define incomplete outputs.
4. **Verify bytes:** map by binary name; ensure the class file version matches the target runtime; check package/name and dependencies. You can apply additional scanning/allowlisting, but scanning does not replace a sandbox.
5. **Choose definition:** child loader or Lookup named/hidden depending on context, rather than using one strategy for every situation.
6. **Avoid races:** if multiple threads concurrently request the same binary name, ensure only one definition operation occurs in the same loader; cache `Class<?>`/handles under an appropriate key.
7. **Link and invoke:** use `MethodHandle`/Reflection/typed interfaces with exact signatures. A created `MethodHandle` carries capability; manage sharing permissions.
8. **Manage lifecycle:** have policies for caching, versioning, and unloading; do not redefine infinitely. Close file manager resources; do not close or clear a loader while its objects/classes are still in use.

### 8.1. Checking Whether Compiler Output Is Complete

A single Java unit can generate multiple class files, including nested types `Outer$Inner`. The lesson's helper uses `getJavaFileForOutput` to collect **every output reported by the compiler**, not just the main `binaryName`. In real applications, if class `A` references class `B`:

- Ensure `B` is in the map or can be **resolved by the loader from a parent/dependency path**.
- If compiling across **multiple independent rounds**, the standard file manager does not automatically know about outputs residing in memory from a previous round; you must implement input classfile lookup (`getJavaFileForInput`/`list`/`inferBinaryName`) or compile them together.
- If they are in the same package across two loaders, package-private access is not automatically shared. Choose the right loader and module from the start.

### 8.2. Compiler Errors Are Not Class Loader Errors

An example of syntactically invalid source:

```java
// Illustrative snippet that DOES NOT compile:
public class Broken {
    public int value( { return 1; }
}
```

With this input, `JavaCompiler.CompilationTask.call()` returns `false` and `DiagnosticCollector` contains the compilation error. In the helper, it throws `IllegalArgumentException` with kind/line/message; **never call `defineClass`** when compilation has not succeeded.

Conversely, compilation may succeed while definition or linking fails: bytecode/classpath that is valid at compile time **does not** guarantee every dependency will be present in a different runtime loader.

## 9. Distinguishing Errors by Stage

| Stage | Typical Error | Why It Happens and What to Check |
| --- | --- | --- |
| Preparing compiler | `getSystemJavaCompiler() == null` | Runtime has no system compiler; use a JDK image with `java.compiler` and a compiler implementation. |
| Compilation | `call() == false` + `DiagnosticCollector` | Invalid source, missing classpath/module path, invalid option, compiler diagnostic. |
| Reading bytecode map | `bytes == null` | Did not capture the right className or the class was not generated; never pass null to `defineClass`. |
| `ClassLoader.defineClass` | `ClassFormatError` / `VerifyError` | Malformed bytes or invalid according to the JVM verifier. |
| `ClassLoader.defineClass` | `NoClassDefFoundError` | Binary name passed in does not match the name in the class file (or dependency error during resolution). |
| `ClassLoader.defineClass` | `SecurityException` | Blocked `java.*` package, signer/package sealing, or related security policy. |
| `Lookup.defineClass` | `IllegalAccessException` | Lookup does not have `PACKAGE` access. |
| `Lookup.defineClass`/`defineHiddenClass` | `IllegalArgumentException` | Bytes specify a class in a package that does not match the lookup class, or invalid input per contract. |
| `Lookup.defineHiddenClass` | `IllegalAccessException` | Lookup does not have full privilege (`PRIVATE` + `MODULE`). |
| Duplicate named class | `LinkageError` | Same binary name already defined in the defining loader; cannot "overwrite" load. |
| Class file version | `UnsupportedClassVersionError` | Target bytes exceed the current JVM version; use an appropriate `--release` or upgrade the runtime. |
| Resolution on use | `NoClassDefFoundError` / `ClassNotFoundException` | Dependency not provided by the loader, wrong classpath, or module boundary. |
| Looking up hidden name | `ClassNotFoundException` | **Expected result**: a hidden class is not discoverable via `Class.forName`. |
| Linking method handle | `NoSuchMethodException`/`IllegalAccessException` | Name, type, or member access does not match. |
| Invoking method handle | `WrongMethodTypeException` | Call-site descriptor does not match `MethodHandle.type()` when using `invokeExact`. |

**Do not catch generic `Throwable` and treat every failure as a "compile error".** Separate compilation diagnostics, class definition, dependency linking, class initialization, and invocation to report accurate errors. JVM errors related to class format, linkage, or verification can be subclasses of `Error`, not checked exceptions.

## 10. Security and Trust Boundaries

**Bytecode in memory is no safer than bytecode on disk.** If the source or bytes are untrusted, defining and **executing** the class will run code with the capabilities of the JVM process, within the runtime's permissions and boundaries. A hidden class is not a sandbox; a child class loader does not create an OS security boundary either.

Risks and requirements:

- **Resource abuse:** code creating infinite loops, spawning too many threads, class definitions, heap/metaspace objects, or accessing local resources. Restrict via process/container isolation and quotas if input is untrusted; do not rely on Java thread interrupt timeouts to stop arbitrary code.
- **Class initialization:** `Class.forName(name,true,loader)` or `defineHiddenClass(bytes,true)` can trigger static initializers with side effects. Defining without invoking does not always mean no execution.
- **Compiler processors:** `-proc:none` prevents annotation processing in the demo task, but does not eliminate all risks from untrusted compilers/plugins/providers or open commands/toolchains.
- **Lookup authority:** `Lookup.defineClass`/`defineHiddenClass` uses the lookup class's privileges. Do not hand a full-privilege Lookup or a MethodHandle pointing to private logic to an untrusted plugin.
- **Package/module:** do not try to inject new classes into `java.*` or another module's private packages by bypassing class loaders. If deep access is needed, use valid APIs and explicit JPMS `exports`/`opens` configuration; do not enable `--add-opens` indiscriminately.
- **ProtectionDomain and sealing:** `ClassLoader.defineClass` has an overload accepting a `ProtectionDomain`; signer/package sealing must be consistent. The minimal helper example uses the default overload, which does not replace a security policy for multi-tenant environments.
- **Class identity and caching:** older version class loaders may fail to unload due to caches, thread context class loaders, static references, MethodHandles, or retained tasks. Hidden classes using `STRONG` can live as long as the loader.

If you must execute code submitted by untrusted customers or agents, a more appropriate approach is to **isolate into a separate process/container** with low OS privileges, bounded resources, and a controlled communication protocol. Class definition APIs are not designed to replace a sandbox.

## 11. Comparison With Other Mechanisms

| Mechanism | Is It a Tool to Define a Class From Bytes? | Characteristics |
| --- | --- | --- |
| `JavaCompiler` | No, only **compiles** | Produces `byte[]`/class files if the file manager captures outputs properly. |
| `ClassLoader.defineClass` | Yes | Named class in a custom loader; parent delegation and runtime package identity must be designed. |
| `Lookup.defineClass` | Yes | Named class in the lookup class's loader/module/package; requires `PACKAGE`. |
| `Lookup.defineHiddenClass` | Yes | Hidden class in the same lookup context; requires full privilege, cannot be found via binary name. |
| `Class.forName` | **Does not** define arbitrary bytes | Asks a loader to find/initialize a **named class** by name; does not find hidden classes. |
| `LambdaMetafactory` | Not a direct user `byte[]` reader | Bootstrap factory for lambdas/SAMs; the runtime may use internally generated classes. |
| `java.lang.instrument.Instrumentation` | Has redefine/retransform mechanisms within supported scope | Intended for agents/hot instrumentation, not a direct replacement for `defineClass` in normal applications. |
| Bytecode generators (ASM, Byte Buddy, etc.) | Typically **generate/transform bytes** | Still must define the output with an appropriate loader/Lookup; do not bypass JVM constraints. |

Do not equate `Class.forName` with `defineClass`. `Class.forName` is a **lookup/loading path by binary name**, whereas `defineClass` turns bytes into **an actual class definition** in the chosen context.

## 12. Choices When Modules and Class Loaders Are Complex

### 12.1. Unnamed Module and Named Module

In the demos, the host class runs from the **classpath** and therefore resides in the unnamed module. A child class loader defining a generated named class typically places it in that loader's unnamed module, rather than **automatically joining** the host's module. This changes module membership, loader identity, and package-private accessibility.

When the host runs in a **named module**, `Lookup.defineClass` and `Lookup.defineHiddenClass` can define a class in the **same module** as the lookup class, provided privilege/package conditions are met. However, obtaining a privileged lookup in another module must follow JPMS checks; `publicLookup()` has neither `PACKAGE` nor full privilege.

Simply having a package name like `com.app.internal` in the generated source is **not enough on its own** to define a class in module `com.app`. Context is determined by the defining loader/Lookup, not just the package string.

### 12.2. Same Package String but Different Runtime Package

A runtime package is based on **package name and defining loader** (and associated module context). Two classes named `com.app.A` and `com.app.B` defined by different loaders **do not automatically have** valid package-private access to each other. This is a common cause of `IllegalAccessError` after both compilation and definition succeed.

If the bytecode needs package-private access to the host, **`Lookup.defineClass`** with valid privileges is usually the right choice over a child loader. If that access is not needed, a cleaner approach is to use a **public interface/contract** rather than relying on package-private internals.

### 12.3. When Using Hidden Classes

A hidden class is the choice for implementations that do not need discovery by name. If the bytes have the class name `demo.runtime.HiddenGenerated` and the lookup class is in `demo.runtime`, the API accepts them; the result still carries a hidden name with a JVM-generated suffix. Do not register the hidden name to reload after a restart: store the template/source/bytes and redefine a new class, then hold the `Class<?>`/MethodHandle.

## 13. Self-Practice Exercises

**Exercise 1 — Is the compiler result really in memory?**

From `MemoryCompiler.compile("generated.memory.Greeter", code)`, check the key in the map and the byte count (greater than 0). Run the loader demo in a directory containing only the host's classes, **without** `generated/memory/Greeter.class`. Why does `Class.forName(name,true,customLoader)` succeed while `Class.forName(name)` fails?

**Answer:** the custom loader looks up the map and calls `defineClass`; the application loader does not know about the map and cannot find the generated class on its classpath.

**Exercise 2 — Two loaders, same name.**

Create two `BytecodeLoader` instances from the same map, and call `Class.forName(name,true,loader1)` and `Class.forName(name,true,loader2)`. Why are the two `Class<?>` objects different even though the bytes and binary name are identical?

**Answer:** a named class's class identity depends on its defining loader; each loader creates an independent type.

**Exercise 3 — Same loader, same name.**

With `Lookup.defineClass(bytes)`, call it a second time on the same bytes. What happens?

**Answer:** a named class cannot be redefined with the same binary name in the same loader. The second attempt is rejected with `LinkageError`; if you want a different version, you need a different name/loader strategy or an appropriate instrumentation mechanism.

**Exercise 4 — Why is a wrong package rejected?**

Use the lookup created in `demo.runtime.MemoryLookupDemo` to define bytes with the class name `generated.other.Outsider`. How does the API respond?

**Answer:** `Lookup.defineClass` requires the bytes to be in the same package as the lookup class; it throws `IllegalArgumentException`. `Lookup.defineHiddenClass` also has the same-package constraint.

**Exercise 5 — Can a hidden class be invoked?**

After `defineHiddenClass(bytes,false)`, get `hiddenLookup.lookupClass()`, call `findStatic(...)`, and invoke `invokeExact()`. Why can the method be called yet `Class.forName(hidden.getName())` cannot find it?

**Answer:** a hidden class is still a `Class` object that can be linked and executed via capability. However, it has no binary name discoverable by name.

**Exercise 6 — Class initialization order.**

In `MemoryHiddenDemo`, why does `<clinit> HiddenGenerated` appear twice?

**Answer:** the two `defineHiddenClass` calls create **two distinct hidden classes** from the same bytes. One is initialized on the first static method call (`initialize=false`), and the other is initialized immediately upon definition (`initialize=true`).

**Exercise 7 — Source depending on multiple classes.**

Extend the program to compile source `A` that depends on `B`. Why is merely keeping the `Map<String,byte[]>` from the previous compile round not enough for the compiler in the next round to recognize `B`?

**Answer:** the standard file manager looks up dependencies via the module path/classpath; for the compiler to see bytes that exist only in memory, you need to additionally provide `JavaFileManager` `getJavaFileForInput`/`list`/`inferBinaryName` or compile both A and B in the same task. At runtime, the defining loader must also be able to resolve both.

## 14. Implementation Checklist

Before taking the pipeline to production, check yourself:

- [ ] Determined whether a **named** or **hidden** class is needed.
- [ ] Binary name/source URI and output `className` are consistent; package matches the context.
- [ ] Compiler is present; `JavaCompiler.getTask(...).call()` succeeds; diagnostics are preserved on failure.
- [ ] Secondary bytes (nested/anonymous/generated classes) and dependencies are fully collected and resolved.
- [ ] If using a custom loader, parent delegation, class identity, module membership, and lifecycle are understood.
- [ ] If using `Lookup.defineClass`, the lookup has `PACKAGE` access and bytes are in the same package.
- [ ] If using `Lookup.defineHiddenClass`, the lookup has **full privilege**; `initialize`/`NESTMATE`/`STRONG` are chosen intentionally.
- [ ] Untrusted code is not executed based solely on the belief that "hidden/in-memory is safe".
- [ ] No unbounded redefinition under the same name/loader; appropriate versioning/caching/cleanup is in place.
- [ ] Tests cover compile failure, package mismatch, loader visibility, duplicate definition, method lookup, and class initialization.
- [ ] Run commands verified with JDK 17+ and the actual runtime/classpath/module configuration.

## 15. Takeaways

- **Receiving bytecode** via `JavaCompiler + ForwardingJavaFileManager` is a **data-producing** step, not a class-loading step.
- **`ClassLoader.defineClass`** defines a **named class** in the chosen loader; you must understand parent delegation and type independence across loaders.
- **`Lookup.defineClass`** defines a **named class** in the same loader/module/runtime package as the lookup class; requires `PACKAGE` access.
- **`Lookup.defineHiddenClass`** defines a **hidden class** in the same lookup context; requires full privilege, cannot be found via `Class.forName`; offers `initialize`, `NESTMATE`, and `STRONG` options.
- **Class identity and access rights** are tied to the loader/module/runtime package, not just the class name string.
- **Bytecode in memory is not a sandbox.** Only generate/define/execute classes in trusted contexts with a clear lifecycle management mechanism.
