# 3.2 Do not rely on the member order returned by reflection; sort explicitly by signature

## 1. Why should we care about order?

Java Reflection lets you retrieve the list of methods, fields, and constructors of a class. For example:

```java
Method[] methods = SomeType.class.getDeclaredMethods();
Field[] fields = SomeType.class.getDeclaredFields();
Constructor<?>[] constructors = SomeType.class.getDeclaredConstructors();
```

**Do not infer the order of these elements from their declaration order in the source code.** According to the `java.lang.Class` API contract, the arrays returned by `getDeclaredMethods()`, `getMethods()`, `getDeclaredFields()`, `getFields()`, `getDeclaredConstructors()`, and `getConstructors()` **are not sorted in any deterministic order**. An order observed by chance on one JDK, compiler, or run does not constitute a guarantee for another run.

For example, if a class declares:

```java
void finish() {}
void start() {}
void pause() {}
```

then `getDeclaredMethods()[0]` **does not mean** the `finish` method or "the first declared method". You cannot rely on an order that "looks right" in logs or tests to conclude that an ordering contract exists.

Consequences when a program uses Reflection to generate documentation, map data, register handlers, create CLI commands, check snapshots, or compute fingerprints: the output may be reordered, tests may become flaky, unnecessary diffs may appear, or worse, logic may accidentally invoke the wrong member selected by index.

**Rule:** If order affects the result, **choose an explicit rule and sort before using**. If you are looking for one specific member, look it up by name/signature instead of picking an array index.

## 2. Understanding the API and member scope

| API | Members listed | Order guaranteed? |
| --- | --- | --- |
| `getDeclaredMethods()` | Methods declared in the class/interface itself, including private ones, but excluding inherited methods; may include bridge/synthetic methods generated by the compiler. | No |
| `getMethods()` | Public methods visible from the class/interface, including inherited methods according to API rules. | No |
| `getDeclaredFields()` / `getFields()` | Fields declared in the class / accessible public fields, including inherited ones according to API rules. | No |
| `getDeclaredConstructors()` / `getConstructors()` | Constructors declared in the class / public constructors of the class; constructors are not inherited. | No |

Note the difference between **the order of the member list** and **the order of parameters within a signature**. `Method.getParameterTypes()` and `Constructor.getParameterTypes()` return parameter types **in the declaration order of that executable itself**. Therefore, `run(String, int)` and `run(int, String)` are two different signatures, and you must preserve this order when building the key.

Do not overgeneralize this rule to "every Reflection API is unordered": some APIs reflect structures that inherently have a deterministic order (for example, record components). Always read the contract of the exact API being used.

## 3. What does "sorting by signature" actually sort by?

### 3.1. Method: name and ordered list of parameter types

At the Java language level, two overloads are distinguished primarily by name and parameter types. For example:

```java
void save(String key) {}
void save(int id) {}
void save(String key, boolean overwrite) {}
```

Sorting only by `Method::getName` is **not enough**: all three share the name `save`. The comparator treats them as equal on the name key; a stable sort will preserve the input order, which is not guaranteed.

A useful sort key:

1. Method name: `getName()`.
2. List of **parameter types in exact positional order**: `getParameterTypes()`.
3. Return type: `getReturnType()`.
4. Declaring class: `getDeclaringClass()`, especially important when combining members from multiple classes or using `getMethods()`.

**Why include the return type in the key even though Java does not allow overloading by return type alone?** JVM bytecode can contain methods with the same name and parameter types but different return types, such as bridge methods generated by the compiler to implement generics or covariant returns. The Javadoc for `getDeclaredMethods()` explicitly states that in this case it may return **multiple `Method` objects**. If you use a key consisting only of name and parameters, they will be treated as equal.

For display, the string might look like:

```text
save(int):void
save(java.lang.String):void
save(java.lang.String,boolean):void
```

This is an **application-defined display key**, not a promise that Java Reflection returns that exact format. When matching members across multiple classes, add the declaring class name to the key. When identifying members across class loaders that may have classes with the same name, you also need an application-managed stable provider/loader ID; the class's binary name alone is not enough.

### 3.2. Fields and constructors have their own keys

- **Field:** field name `getName()`, type `getType()`; add the declaring class if combining multiple classes.
- **Constructor:** declaring class name and ordered list of parameter types `getParameterTypes()`; there is no return type.
- **Modifiers, annotations, generic types:** can be added if the **specific problem** requires them, but do not automatically turn them into a business priority order.

Use `Class.getName()` or `Class.getTypeName()` to build type strings; avoid relying on parameter variable names (often not retained without the `-parameters` compiler option), source code order, `hashCode()`, or JVM identity hash. `getParameterTypes()` reflects erased types: `List<String>` and `List<Integer>` both have the raw class `java.util.List`; when you need to represent generics for documentation, inspect `getGenericParameterTypes()` as well and define a separate policy.

## 4. Runnable example: sorting methods, constructors, and fields

The following example intentionally declares members in non-alphabetical order. The program **sorts the arrays** before printing, so the output does not depend on how `getDeclared...()` initially lists them.

Create the file **`ReflectionOrderDemo.java`**:

```java
import java.lang.reflect.Constructor;
import java.lang.reflect.Field;
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.Comparator;
import java.util.stream.Collectors;

public class ReflectionOrderDemo {
    public static final class Endpoint {
        public String label;
        private int code;

        public Endpoint(int code) {
            this.code = code;
        }

        public Endpoint() {
        }

        public void send(String message) {
        }

        public int status() {
            return code;
        }

        public void send(int retries) {
        }
    }

    // Parameter order and types used for the key and display.
    private static String parameters(Class<?>[] types) {
        return Arrays.stream(types)
                .map(Class::getTypeName)
                .collect(Collectors.joining(","));
    }

    private static String methodKey(Method method) {
        return method.getName()
                + "(" + parameters(method.getParameterTypes()) + "):"
                + method.getReturnType().getTypeName()
                + "@" + method.getDeclaringClass().getName();
    }

    private static String constructorKey(Constructor<?> constructor) {
        return constructor.getDeclaringClass().getName()
                + "(" + parameters(constructor.getParameterTypes()) + ")";
    }

    private static String fieldKey(Field field) {
        return field.getDeclaringClass().getName()
                + "#" + field.getName()
                + ":" + field.getType().getTypeName();
    }

    public static void main(String[] args) {
        Method[] methods = Endpoint.class.getDeclaredMethods();
        Arrays.sort(methods,
                Comparator.comparing(ReflectionOrderDemo::methodKey));

        System.out.println("METHODS");
        for (Method method : methods) {
            System.out.println(method.getName()
                    + "(" + parameters(method.getParameterTypes()) + "):"
                    + method.getReturnType().getTypeName());
        }

        Constructor<?>[] constructors =
                Endpoint.class.getDeclaredConstructors();
        Arrays.sort(constructors,
                Comparator.comparing(ReflectionOrderDemo::constructorKey));

        System.out.println("CONSTRUCTORS");
        for (Constructor<?> constructor : constructors) {
            System.out.println("Endpoint("
                    + parameters(constructor.getParameterTypes()) + ")");
        }

        Field[] fields = Endpoint.class.getDeclaredFields();
        Arrays.sort(fields,
                Comparator.comparing(ReflectionOrderDemo::fieldKey));

        System.out.println("FIELDS");
        for (Field field : fields) {
            System.out.println(field.getName()
                    + ":" + field.getType().getTypeName());
        }
    }
}
```

Run with JDK 17 or later:

```bash
javac -encoding UTF-8 --release 17 ReflectionOrderDemo.java
java ReflectionOrderDemo
```

Stdout:

```text
METHODS
send(int):void
send(java.lang.String):void
status():int
CONSTRUCTORS
Endpoint()
Endpoint(int)
FIELDS
code:int
label:java.lang.String
```

Explanation:

- `Method[]`, `Constructor<?>[]`, and `Field[]` are separate arrays. `Arrays.sort(array, comparator)` only reorders elements in the array; **it does not modify the methods or the class definition**.
- `methodKey` uses the method name, **parameter type order**, return type, and declaring class. Thus the two overloads `send(int)` and `send(String)` have different keys, regardless of the order `getDeclaredMethods()` initially returns.
- `constructorKey` does not use a return type; `Endpoint()` comes before `Endpoint(int)` under the chosen string rule.
- `fieldKey` places `code` before `label` in lexicographical order.
- Type names use `getTypeName()` for readability; array types look like `java.lang.String[]`. The key string is **a policy we define ourselves**. If you want to prioritize methods with no parameters or fewer parameters first, use an explicit multi-level comparator instead of implicitly treating lexicographical order as a business rule.

You do not always need to build a key string. For a large set of members, you can compare each component directly to reduce temporary string allocations. For documentation generators or startup configuration, a readable key like the one above is usually clear enough and easy to test.

## 5. Why `Method::getName` is not enough: bridge methods

When using generics, the compiler may generate an additional **bridge method** to ensure compatibility after type erasure. Two reflected methods can have the same name and the same parameter list, yet **different return types**.

Standalone example, saved as **`BridgeSortDemo.java`**:

```java
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.Comparator;

public class BridgeSortDemo {
    interface Value<T> {
        T read();
    }

    static final class TextValue implements Value<String> {
        @Override
        public String read() {
            return "ok";
        }
    }

    public static void main(String[] args) {
        Method[] methods = TextValue.class.getDeclaredMethods();

        // For this demo class, every method is named "read" with no parameters.
        // The return type distinguishes the bridge method from the source-code method.
        Arrays.sort(methods, Comparator
                .comparing(Method::getName)
                .thenComparing(method -> method.getReturnType().getName()));

        for (Method method : methods) {
            System.out.println(method.getName() + "():"
                    + method.getReturnType().getTypeName()
                    + " bridge=" + method.isBridge()
                    + " synthetic=" + method.isSynthetic());
        }
    }
}
```

```bash
javac -encoding UTF-8 --release 17 BridgeSortDemo.java
java BridgeSortDemo
```

Stdout when compiled with standard `javac` on JDK 17:

```text
read():java.lang.Object bridge=true synthetic=true
read():java.lang.String bridge=false synthetic=false
```

Reason: `Value<T>.read()` returns `Object` after erasure; the compiler generates the bridge `Object read()` to forward calls to the `String read()` implementation. Both have the name `read` and **no parameters**; if you sort only by name or only by name + parameters, the comparator returns 0 between them. Java's stable sort then still preserves the unguaranteed input order.

The example uses a shortened comparator because the class only has two parameterless methods. In a library handling **multiple classes and multiple overloads**, use a full key as in section 4 or a multi-level comparator that includes parameter types, return type, and declaring class.

If the goal is **the list of APIs written in source code**, you can apply a filtering policy:

```java
Method[] sourceLikeMethods = Arrays.stream(
        TextValue.class.getDeclaredMethods())
        .filter(method -> !method.isBridge() && !method.isSynthetic())
        .sorted(Comparator.comparing(Method::getName)
                .thenComparing(method -> method.getReturnType().getName()))
        .toArray(Method[]::new);
```

This is a **code snippet illustrating a filtering policy**, not a standalone runnable program. Do not filter out bridge/synthetic members unconditionally: bytecode analysis tools, dispatch frameworks, or debuggers may **need** those members. What structures the compiler generates also depends on the compiler version and specific source code; applications should not hardcode the number of bridge methods for every class.

## 6. Designing a clear comparator for your needs

### 6.1. Consistent lexicographical order

For API documentation or snapshots, you can choose:

```java
Comparator<Method> bySignature = Comparator
        .comparing(Method::getName)
        .thenComparingInt(Method::getParameterCount)
        .thenComparing(m -> Arrays.stream(m.getParameterTypes())
                .map(Class::getName)
                .collect(Collectors.joining(",")))
        .thenComparing(m -> m.getReturnType().getName())
        .thenComparing(m -> m.getDeclaringClass().getName());
```

**This snippet is an excerpt inside a class or method that imports `java.lang.reflect.Method`, `java.util.Arrays`, `java.util.Comparator`, and `java.util.stream.Collectors`; it is not a standalone Java file.**

The rule is: **name → parameter count → parameter types by position → return type → declaring class**. Compared to section 4, this approach puts methods with fewer parameters first within the same name group. Both are valid; what matters is publishing and consistently applying **one** policy.

If you need backward-compatible ordering for a released tool, **do not silently change the comparator**; a new order can alter generated content or artifact checksums even when the set of members has not changed.

### 6.2. The comparison key must be sufficiently distinguishing

A comparator that returns 0 when comparing two different members can cause the final order to depend on the initial Reflection order. The stability of the sorting algorithm only preserves the relative order of elements **considered equal by the comparator**; it does not fix an under-specified comparator.

For methods within a normal class loader scope, a key based on **declaring class + name + parameter types + return type** distinguishes reflected methods with different descriptors. When combining members from multiple class loaders where classes may share binary names, you must provide a **stable plugin/provider identity** from application configuration. Do not use `System.identityHashCode(...)` or loader discovery order if deterministic results across runs are required.

### 6.3. Sorting content, not deciding business semantics

There are two kinds of order that need to be kept separate:

- **Presentation order:** method tables, documentation lines, snapshots, manifests. Signature sorting is well suited here.
- **Execution or priority order:** migrations must run by version; handlers must run by priority; interceptors have explicit before/after semantics. **Do not infer this order from signatures or from the position returned by Reflection.** Use explicit ordering configuration, a dependency graph, a priority annotation with a clear contract, or a controlled registration structure. Only use signature sorting as a tie-breaker if the policy specifies doing so.

Wrong example:

```java
// Wrong: "the first method" is arbitrary according to the API contract.
Method handler = Handler.class.getDeclaredMethods()[0];
```

If you know the exact name and parameter types, look it up directly:

```java
Method handler = Handler.class.getDeclaredMethod(
        "handle", String.class);
```

Both snippets above **are illustrative excerpts**, assuming `Handler` has a `handle(String)` method and the code handles `NoSuchMethodException`. The second approach selects by signature without needing to sort the entire list. If you need to select by **return type** when bytecode has methods with the same name/parameters but different return types, list them and filter as required rather than picking by position.

## 7. Common mistakes and how to avoid them

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Relying on `getDeclaredMethods()[0]` or iterating in returned order | Different member selected when changing JDK/compiler, flaky results | Look up by signature or sort before using. |
| Sorting only by method name | Overloads tie on the key, still dependent on initial order | Add parameter types; for full reflection add return type and declaring class. |
| Sorting by **parameter** names | Names may be absent and may change during refactoring | Use `getParameterTypes()`, preserving parameter order. |
| Ignoring bridge/synthetic methods | Duplicate name/parameters, unstable snapshots or duplicated APIs | Define a keep/filter policy; if keeping, include return type in the key. |
| Assuming `getFields()` order is declaration order | Inherited members are mixed according to API rules, order is non-deterministic | Sort and include declaring class in the key when there are multiple sources. |
| Using `Method.toString()`/`toGenericString()` as a durable data identifier | Human-readable descriptive string that may not match application schema/version | Build a dedicated key schema from chosen attributes; manage format changes. |
| Using `HashSet` / `HashMap` after sorting and expecting iteration to keep the order | Order is lost due to the collection structure | Keep the sorted `List` or use an order-preserving structure when needed. |
| Using signatures to decide execution order of migrations, validators, or interceptors | Wrong business order even though output is "stable" | Model priority/dependencies with explicit data. |
| Defaulting to the machine's locale when comparing names | Results may vary by locale | For technical keys use deterministic string ordering (e.g. `String.compareTo`), or configure locale if actually sorting for users. |

Sorting operations only require metadata; there is **no need** for `setAccessible(true)` or invoking methods. In a modular environment, metadata reading and accessibility have their own rules; trying to bypass encapsulation just to obtain a sorted list is unnecessary.

## 8. Testing determinism

A useful test should compare the **sorted result** against an expected set of signatures, rather than checking the raw order returned by Reflection. For `Endpoint` in section 4, a test can assert the string order is:

```text
send(int):void
send(java.lang.String):void
status():int
```

To verify that the comparator does not miss important attributes, include in the test fixture at least:

1. Two overloads with the same name but different parameter counts/types.
2. Methods with different return types via bridge mechanisms or covariant overrides.
3. A class with both public/private fields and two constructors.
4. If inherited members are included, some methods from a superclass/interface.

**Do not assert that the raw array must have a specific order.** You can randomly shuffle the input list in the test and then sort it again, then compare against the same expected result. If the output still changes, the comparator has key ties without a tie-breaker, or a subsequent transformation step does not preserve order.

For documentation/metadata generators, maintain a golden file of the normalized signature strings and version the sorting policy when it is part of a public format. This ensures diffs reflect actual API changes rather than unintended runtime variations.

## 9. Self-check questions

**1. Why can `Arrays.sort(methods, Comparator.comparing(Method::getName))` still produce different outputs?**

Because overloads with the same name are considered equal by the comparator; a stable sort still preserves the initial order returned by Reflection, which is not guaranteed.

**2. When is the return type needed in a method sort key?**

When you want to fully distinguish reflected `Method` objects, especially with bridge/synthetic methods or bytecode that has the same name and parameter types but different return types. Return type is not a normal overloading criterion at the Java source code level.

**3. If you only want to invoke the `handle(String)` method, should you sort `getDeclaredMethods()` and take the corresponding index?**

No. Use `getDeclaredMethod("handle", String.class)` and handle the lookup error if it does not exist. Sorting is only needed when you actually have to output a list or process members in a deterministic order.

**4. Does sorting by signature guarantee the correct execution sequence for migrations?**

No. Signatures produce a repeatable technical order, whereas migrations require a business order based on version, dependencies, or dedicated configuration.

**5. Does `getParameterTypes()` return parameter types in a random order like `getDeclaredMethods()`?**

No. `getParameterTypes()` represents the list of parameter types **in the executable's declaration order**. That is precisely why this order must be preserved when building the key.

## 10. Takeaways

- **Reflection lists members without guaranteeing order** for the method/field/constructor arrays mentioned above.
- When deterministic results are needed, **sort with an explicit comparator**: for methods, at minimum you need the name and parameter list; when handling full reflected members, you must also consider return type and declaring class to avoid key ties from bridge methods/inheritance.
- **Sorting output and selecting behavior are two different problems.** Use signatures for presentation, fingerprints, and snapshots; use dedicated priority/dependency contracts for execution order.
- **Test the normalized result**, do not rely on the raw order of the JDK.
