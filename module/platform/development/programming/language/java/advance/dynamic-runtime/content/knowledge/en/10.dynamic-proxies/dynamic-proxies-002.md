# 10.2 Creating a proxy with `Proxy.newProxyInstance` and choosing a class loader

Java's **dynamic proxy** allows creating an object that implements one or more **interfaces** at runtime. When a client calls a method on this object, the JVM dispatches the call to an `InvocationHandler` that we provide. This is a commonly used mechanism for creating logging wrappers, timing, permission checks, RPC calls, plugin adapters, or facades for an interface-based service.

Key point of this lesson: **the `ClassLoader` passed to `Proxy.newProxyInstance` must see the exact `Class<?>` objects of the interfaces to be implemented**, not merely find a class with the same name. In a single-class-loader application, choosing a loader is usually simple. With plugins, containers, multi-module applications, or multiple class loaders, a wrong choice can prevent the proxy from being created or prevent the object from being cast to the interface the caller is using.

The following examples use **Java 17+**, standard APIs in `java.lang.reflect`.

## 1. The three parameters of `Proxy.newProxyInstance`

Signature:

~~~java
public static Object newProxyInstance(
    ClassLoader loader,
    Class<?>[] interfaces,
    InvocationHandler h)
~~~

| Parameter | Role | Things to remember |
| --- | --- | --- |
| `loader` | Class loader chosen to **define the generated proxy class** | Must resolve each interface to the **exact `Class` object**. The value `null` denotes the bootstrap class loader, not a mechanism to automatically find a suitable loader |
| `interfaces` | List of interfaces that the proxy class will implement, **in exact order** | Must be valid interfaces, without duplicates, non-hidden, non-sealed; certain combinations of methods and access are not allowed |
| `h` | `InvocationHandler` that handles method calls on the proxy | Must not be `null`. Returns an object compatible with the return type, handling `Object` methods and default methods as well if needed |

Sample example when there is only one contract visible to the application:

~~~java
ClassLoader loader = Service.class.getClassLoader();
Service proxy = (Service) Proxy.newProxyInstance(
        loader,
        new Class<?>[] { Service.class },
        handler);
~~~

This snippet is an **illustrative pattern**, assuming `Service` and `handler` are already declared; a complete runnable program is in section 6.

The result of `newProxyInstance` has a static return type of `Object`, but the runtime object implements the listed interfaces, so it can be cast to the corresponding interface. The generated proxy class is a **`final` class**, extending `java.lang.reflect.Proxy`. It is not a subclass of an arbitrary business class.

## 2. The path of a call

~~~text
Client code
   │  Greeting greeting = (Greeting) proxy
   │  greeting.greet("Java")
   ▼
Proxy class generated by the JVM
   │  implements Greeting
   │  packages Method + Object[] args
   ▼
InvocationHandler.invoke(proxy, method, args)
   │  look up / log / check / call real object
   │  return "Hello, Java"
   ▼
Proxy class checks/casts the result
   │
   ▼
Client receives "Hello, Java"
~~~

The handler has the signature:

~~~java
Object invoke(Object proxy, java.lang.reflect.Method method, Object[] args)
        throws Throwable;
~~~

- `proxy` is the proxy object currently being invoked; **do not** call `method.invoke(proxy,args)` unconditionally inside the handler, as that can call back into the handler and cause infinite recursion.
- `method` describes the method called through the interface (or one of the three special `Object` methods).
- `args` can be **`null` if the method has no parameters**; primitive parameters such as `int` are boxed into wrappers (`Integer`, etc.).
- The return value must be compatible with the interface's return type. For a primitive return such as `int`, the handler needs to return the corresponding wrapper; returning `null` leads to a `NullPointerException` when the proxy attempts to unbox. Returning an incompatible value can lead to a `ClassCastException`.
- The handler can throw an exception. A checked exception incompatible with the interface method's `throws` clause will be wrapped by the proxy in an `UndeclaredThrowableException`.

**Separation of roles:** `ClassLoader` determines **whether the proxy class can be created and linked**; `InvocationHandler` determines **what work each call performs**. A correct loader does not guarantee a correct handler.

## 3. Choosing a class loader: core principle

For each interface `intf` in the `interfaces` array, the JVM requires:

~~~java
Class.forName(intf.getName(), false, loader) == intf
~~~

This is a **same type identity condition**, not just a name comparison. Two classes with the same binary name but defined by two different loaders can be two different Java types. In Java, type identity is tied to the **class name and defining class loader**.

- `Class.forName(name, false, loader)` finds/retrieves the class using the specified loader, without actively initializing the class because `initialize=false`. The loader may still perform the necessary loading/linking.
- The `==` comparison checks for the exact `Class<?>` object.
- A **child loader** can see an interface defined by a **parent loader** through the delegation mechanism. Therefore, the proxy's loader **does not have to** be the exact loader that defined the interface; it only needs to resolve to the exact `Class`.
- If the loader returns a copy of the interface with the same name but a different identity, the condition above **fails**.
- In addition to the interfaces, the types referenced in the **public method** signatures of the interfaces and superinterfaces must also be properly visible to the loader.

For a single interface, a sensible default is **the loader associated with the interface itself**:

~~~java
ClassLoader chosen = MyApi.class.getClassLoader();
Object proxy = Proxy.newProxyInstance(
        chosen, new Class<?>[] { MyApi.class }, handler);
~~~

`MyApi.class.getClassLoader()` **can return `null`**, for example for classes defined by the bootstrap loader. In that case `null` is valid for interfaces that the bootstrap loader actually sees; it does **not** mean "choose the system loader" or "choose by thread".

## 4. Comparing common sources for choosing a loader

| How to get the loader | When useful | What must be checked |
| --- | --- | --- |
| `SomeInterface.class.getClassLoader()` | One interface or multiple interfaces in the same visibility scope | Are other interfaces, types in public signatures, and module access compatible? |
| `Thread.currentThread().getContextClassLoader()` (TCCL) | A framework/plugin container actively sets the loader per thread context | TCCL can be `null`, vary across threads, and not see the real interface; **must check** before using |
| `SomeImplementation.class.getClassLoader()` | The implementation loader is already determined and also sees all contracts | It may see the implementation but not resolve the caller's exact `Class<?>` contract |
| `ClassLoader.getSystemClassLoader()` | Simple applications running entirely under the system/application loader | Does not by default see types in child/isolated loaders or plugin classes |
| `new ClassLoader(parent) { ... }` | Creating a separate, intentional namespace for proxies with appropriate delegation | Proxy creation is allowed when the child sees the contract; a proxy class defined by a child changes lifecycle and retention |
| `null` | Interfaces and signature types are all visible to the bootstrap loader | Cannot proxy application interfaces simply by passing `null`; usually fails on visibility |

**There is no single choice that is always right for every application.** When there are multiple interfaces, **a single loader that resolves all of them** to their exact corresponding `Class`, while also seeing the related types in public signatures, is required. It is not necessarily the loader of the first interface.

For plugin systems, a common structure is:

~~~text
Application / shared API loader
    └── defines PluginService and shared DTOs
         ├── Plugin A loader (delegates to API loader)
         └── Plugin B loader (delegates to API loader)

Proxy uses:
  - shared API loader if only shared contracts are needed;
  - a specific compatible loader if it must also proxy
    a private interface that this loader actually sees.
~~~

If two interfaces are defined only in **two independent loaders** and no loader sees both with the exact identity, redesign the module/plugin boundaries or provide a suitable loader; blindly switching to TCCL does not solve the identity condition.

## 5. Checking a loader before creating a proxy

You can check early and provide a clear message:

~~~java
static boolean sees(ClassLoader loader, Class<?> type) {
    try {
        return Class.forName(type.getName(), false, loader) == type;
    } catch (ClassNotFoundException ex) {
        return false;
    }
}
~~~

This is an **illustrative helper**, not a standalone runnable program. This check answers whether the loader sees the **exact interface class**; other restrictions such as non-public interfaces, sealed interfaces, method signatures, or module boundaries can still cause proxy creation to fail.

If the loader does not see the class, diagnose from actual observations:

~~~java
System.out.println(type.getName());
System.out.println(type.getClassLoader());
System.out.println(Thread.currentThread().getContextClassLoader());
System.out.println(type.getModule().getName());
~~~

This snippet assumes the variable `type` already has a value. `ClassLoader.toString()` only helps identify loaders during debugging; **do not** compare loaders by that string to determine same identity. Use `==` for loaders or `Class<?>` when object comparison is needed.

## 6. Complete Java 17 example: creating a proxy and verifying the loader

Save **all** of the code below into a file **`ProxyLoaderDemo.java`** in an empty directory. Every interface is declared `public` inside the `ProxyLoaderDemo` class so it can also be used outside the class when needed.

~~~java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;

public final class ProxyLoaderDemo {
    public interface Greeting {
        String greet(String name);
        default String farewell() { return "See you"; }
    }

    public interface Counter {
        int count();
    }

    public static void main(String[] args) {
        ClassLoader contractLoader = Greeting.class.getClassLoader();
        InvocationHandler handler = (proxy, method, callArgs) -> {
            if (method.getDeclaringClass() == Object.class) {
                return switch (method.getName()) {
                    case "toString" -> "GreetingProxy";
                    case "hashCode" -> System.identityHashCode(proxy);
                    case "equals" -> proxy == callArgs[0];
                    default -> throw new UnsupportedOperationException(method.toString());
                };
            }
            if (method.isDefault()) {
                return InvocationHandler.invokeDefault(proxy, method, callArgs);
            }
            return switch (method.getName()) {
                case "greet" -> "Hello, " + callArgs[0];
                case "count" -> 3;
                default -> throw new UnsupportedOperationException(method.toString());
            };
        };

        Object object = Proxy.newProxyInstance(
                contractLoader, new Class<?>[] {Greeting.class, Counter.class}, handler);
        Greeting greeting = (Greeting) object;
        Counter counter = (Counter) object;

        System.out.println("greet: " + greeting.greet("Java"));
        System.out.println("default: " + greeting.farewell());
        System.out.println("count: " + counter.count());
        System.out.println("proxy class: " + Proxy.isProxyClass(object.getClass()));
        System.out.println("same loader: " + (object.getClass().getClassLoader() == contractLoader));
        System.out.println("same handler: " + (Proxy.getInvocationHandler(object) == handler));
        System.out.println("interfaces: " + object.getClass().getInterfaces().length);
        System.out.println("toString: " + object);
        System.out.println("equals self: " + object.equals(object));
        System.out.println("equals other: " + object.equals(new Object()));

        ClassLoader child = new ClassLoader(contractLoader) {};
        Object childObject = Proxy.newProxyInstance(
                child, new Class<?>[] {Greeting.class}, handler);
        System.out.println("child sees interface: " +
                (loadSameClass(child, Greeting.class)));
        System.out.println("child is proxy loader: " +
                (childObject.getClass().getClassLoader() == child));

        ClassLoader isolated = new ClassLoader(null) {};
        System.out.println("isolated sees interface: " +
                loadSameClass(isolated, Greeting.class));
        try {
            Proxy.newProxyInstance(isolated, new Class<?>[] {Greeting.class}, handler);
            throw new AssertionError("Expected visibility error");
        } catch (IllegalArgumentException expected) {
            System.out.println("isolated proxy: " + expected.getClass().getSimpleName());
        }

        try {
            Proxy.newProxyInstance(contractLoader,
                    new Class<?>[] {Greeting.class, Greeting.class}, handler);
            throw new AssertionError("Expected duplicate-interface error");
        } catch (IllegalArgumentException expected) {
            System.out.println("duplicate interface: " + expected.getClass().getSimpleName());
        }
    }

    private static boolean loadSameClass(ClassLoader loader, Class<?> type) {
        try {
            return Class.forName(type.getName(), false, loader) == type;
        } catch (ClassNotFoundException ex) {
            return false;
        }
    }
}
~~~

Compile at Java 17 language level, then run:

~~~bash
javac --release 17 ProxyLoaderDemo.java
java ProxyLoaderDemo
~~~

**Stdout:**

~~~text
greet: Hello, Java
default: See you
count: 3
proxy class: true
same loader: true
same handler: true
interfaces: 2
toString: GreetingProxy
equals self: true
equals other: false
child sees interface: true
child is proxy loader: true
isolated sees interface: false
isolated proxy: IllegalArgumentException
duplicate interface: IllegalArgumentException
~~~

The lines directly related to choosing a loader:

1. `same loader: true`: the first proxy was defined by the requested `contractLoader`.
2. `child sees interface: true`: the child class loader **delegates to the parent**, so it still resolves `Greeting.class` to the same `Class` object.
3. `child is proxy loader: true`: the second proxy was defined by the **child loader**, even though the interface was loaded by the parent.
4. `isolated sees interface: false`: a loader with parent `null` can only find types visible to the bootstrap loader, and does not see the application nested interface `Greeting`.
5. `isolated proxy: IllegalArgumentException`: the visibility/identity condition is violated **at proxy creation time**.
6. `duplicate interface: IllegalArgumentException`: the interface list must not repeat the same `Class<?>`.

The handler also shows: the `greet` method returns a `String`, `count` returns an `Integer` auto-boxed for the primitive `int` return, the default method `farewell` is forwarded to the default implementation via `InvocationHandler.invokeDefault`, and `toString`/`equals` calls are decided by the handler. The presence of `default` does not cause the proxy to bypass the handler automatically.

**Why doesn't stdout print the proxy class name?** The exact package/class name of a proxy is a JVM detail that can vary across runs and environments. `Proxy.isProxyClass`, `getInterfaces()`, and `getClassLoader()` are more reliable ways to inspect than assuming the class is always named like `$Proxy0`.

## 7. When there are multiple interfaces: additional constraints

`Proxy.newProxyInstance(loader, interfaces, handler)` does not check only the first interface. Under Java 17 rules, the important restrictions include:

- Every element must be a **true interface**, **non-hidden**, and **non-sealed**; do not pass regular classes, primitives, `null`, or sealed interfaces in the list.
- No two `Class<?>` elements may be duplicates in the array, even at different positions.
- The chosen loader must see **every interface** and **every type in the relevant public method signatures** (including inherited methods) with the exact identity.
- If there are **non-`public`** interfaces, all non-public interfaces must be in the same **package and module**, defined by the chosen loader, and other access conditions must be satisfied. You cannot arbitrarily combine two package-private interfaces from two different packages.
- When multiple interfaces declare methods with the **same name and parameter types**, the return types must be compatible according to Proxy's rules: the exact same primitive/`void`, or there is one reference return type assignable to all the others. Otherwise, proxy creation fails.
- **Interface order matters.** When multiple interfaces have the same signature, the `Method` passed to the handler corresponds to the interface appearing earlier in the list, not necessarily the interface whose reference type the caller used to make the call.

Example (**deliberately invalid snippet**, not meant to be run standalone):

~~~java
Proxy.newProxyInstance(
        contractLoader,
        new Class<?>[] { Greeting.class, Greeting.class },
        handler);
// IllegalArgumentException: same interface repeated in the array
~~~

Even when the binary names of two classes are identical but their class loaders differ, putting a `Class<?>` from loader A into the list and creating a proxy with loader B can still violate identity. Do not fix this by comparing `getName()`; choose the right loader or unify the contract in a shared API layer.

If an interface method returns a domain type defined in a plugin loader that the proxy's loader does not see, checking only each interface `Class` is not enough. You must check parameter/return/exception types in **public method signatures** and how they are loaded.

## 8. JPMS modules and where the proxy class is placed

Since Java 9, a class belongs not only to a **class loader** but also to a **module**. These two pieces of information do not replace each other. Call:

~~~java
Class<?> generated = proxy.getClass();
System.out.println(generated.getClassLoader());
System.out.println(generated.getModule());
~~~

Here `proxy` is an already-created object; this snippet is only for diagnostics.

Java 17 determines the **module and package containing the proxy class** based on the accessibility of the interfaces:

| Interface situation | Location/accessibility of the proxy class |
| --- | --- |
| All interfaces are `public`, and their packages are exported or opened **unconditionally** | `public` proxy class in a package that is exported unconditionally but **not open**; package/module names are decided by the JDK |
| At least one non-`public` interface (same package and module constraints are satisfied) | **Non-public** proxy class, placed in the exact same package and module as the group of non-public interfaces |
| All interfaces are `public`, but at least one interface is in a package that is **not exported and not opened unconditionally** | `public` proxy class placed in a **non-exported, non-open** package of a **dynamic named module** created by the runtime |

A **dynamic module** here is a named module created at runtime to encapsulate the proxy class, not a new module that the developer needs to add to `module-info.java`. Certain read/export permissions required for this module are set up by the runtime. Even if the proxy class is `public`, a class in a non-exported package may still be **inaccessible from outside the module**. Therefore, you should not assume `proxy.getClass().getConstructor(...).newInstance(...)` is always valid; use `Proxy.newProxyInstance` to create objects.

Practical points:

- `module-info.java` with `exports` or `opens` changes **access boundaries between modules**; the class loader determines **identity and visibility**. Both layers must be checked.
- A public interface in a non-exported package can still have a proxy created by the JDK in appropriate cases; this does **not** mean an arbitrary caller can import that interface or has reflective access to the generated proxy class.
- The **unnamed module** (code on the class path) exports and opens its packages by default; however, the class loader must still see the exact interface.
- In a module-path environment, public method signatures, read/export relationships, and the modules containing the interfaces must be consistent. Do not try to fix a loader identity error by adding `--add-opens`: that flag does not create the same `Class<?>` across independent loaders.
- **The module/package name of the proxy class is not guaranteed to be fixed.** Do not hardcode `jdk.proxy1` or `$Proxy0` in application logic.

## 9. `InvocationHandler`: details to handle properly

### 9.1. `Object.toString`, `equals`, and `hashCode`

These three familiar `public` methods are forwarded by the proxy to the handler, with `method.getDeclaringClass() == Object.class`. If the handler only knows business methods, even calling `toString()` during logging can lead to unexpected errors.

The program in section 6 handles the three methods with **identity semantics**: `equals` compares `proxy == other`, `hashCode` uses `System.identityHashCode(proxy)`, and `toString` returns a fixed string. This is a suitable choice for an illustrative proxy; in production, if business-key equality is used, `equals` and `hashCode` must be designed consistently.

### 9.2. Interface default methods

Even though an interface has `default String farewell()`, the proxy still forwards the call to the handler. On Java 17, you can explicitly invoke the default logic:

~~~java
if (method.isDefault()) {
    return InvocationHandler.invokeDefault(proxy, method, callArgs);
}
~~~

This snippet is an **excerpt from the complete program**. `InvocationHandler.invokeDefault` has been available since Java 16 and executes the invocation of the selected default method on the proxy, subject to valid-method constraints. Do not default to calling `method.invoke(proxy, args)` to "reach the default", because that can loop back into the handler.

### 9.3. Delegating to a real object

A forwarding handler can use `Method.invoke(realTarget, args)` **if `realTarget` actually implements the interface containing the method**. With reflection delegation, `InvocationTargetException` wraps the exception thrown by the target:

~~~java
try {
    return method.invoke(realTarget, args);
} catch (java.lang.reflect.InvocationTargetException ex) {
    throw ex.getCause();
}
~~~

This is an **illustrative snippet inside `InvocationHandler.invoke`**, assuming `realTarget` is type-compatible. Unwrapping `getCause()` prevents needlessly leaking the reflection wrapper; however, checked exceptions must still obey the interface's `throws` clause. For an object that does not implement the relevant interface, `Method.invoke` can throw `IllegalArgumentException`.

### 9.4. Primitive results and checked exceptions

The handler is a method returning `Object`. If the interface has `int count()`, returning `Integer` is valid; `return null` causes the proxy to encounter a `NullPointerException` at the unboxing step. If the interface has `String name()` and the handler returns `Integer`, a `ClassCastException` will occur when the proxy casts the result.

If the handler throws a checked exception that the interface method does not declare and does not allow, the proxy converts it into an `UndeclaredThrowableException`. Keep the exception contract clear rather than throwing arbitrary checked exceptions from the handler.

## 10. Common loader-selection errors and how to diagnose them

| Symptom | Possible cause | How to fix |
| --- | --- | --- |
| `IllegalArgumentException` immediately at `newProxyInstance` | The loader does not see the exact interface or a signature type, duplicate interface, sealed interface, or invalid method constraint | Check each `Class`, `Class.forName(...,loader) == type`, the interface list, and signatures |
| `ClassCastException` when casting the result to the interface | The caller and the proxy are using two copies of the interface with **different identities**, or that interface was not included in the list | Print the loader/`Class` identity of the caller and the passed-in interfaces; share the contract via a common loader |
| Works normally on the main thread but fails on a worker thread | TCCL varies by thread or is `null` | Use the loader tied to the contract or pass a loader explicitly; verify TCCL before choosing it |
| Plugin A works, Plugin B does not | The two plugin loaders have different visibility | Place shared contracts/DTOs in a shared API loader or provide a compatible loader |
| Proxy creation succeeds, but reflective construction of the proxy class fails | The proxy class is in an encapsulated module/package | Use `Proxy.newProxyInstance`; inspect module/package when diagnosing |
| Calling `toString`/`equals` fails or recurses | The handler does not handle `Object` methods, or calls a method on the proxy itself | Add a separate branch for `Object`; avoid delegating to the intercepting proxy |
| Default method does not run | The handler did not call `InvocationHandler.invokeDefault` | Call it explicitly according to the interface contract |
| Method returning a primitive causes `NullPointerException` | The handler returned `null`, causing the proxy to unbox | Return a valid wrapper, with data validation |
| Checked exception wrapped in `UndeclaredThrowableException` | The handler threw a checked exception outside the interface's `throws` contract | Handle or declare exceptions matching the contract |
| Loader sees the interface, but proxy still fails | Public method signatures, non-public accessibility, or JPMS restrictions are not satisfied | Check all method types, module/package, duplicate signatures, and loader |

### Investigation checklist in order

1. Identify the **actual set of interfaces** to proxy, taken from the `Class<?>` objects used in the application; do not reconstruct `Class` from name strings alone.
2. Choose a loader and check `Class.forName(i.getName(), false, loader) == i` **for each interface**, not just the first element.
3. Check that types in public method signatures and inherited interfaces are properly visible to that loader.
4. Check `public`/package-private, sealed/hidden, and overlapping signatures; confirm that packages/modules can be combined.
5. Print `interfaceClass.getClassLoader()`, `interfaceClass.getModule()`, and `Thread.currentThread().getContextClassLoader()` to identify differences between execution environments.
6. If the proxy class was created, check `Proxy.isProxyClass(proxy.getClass())`, `proxy.getClass().getClassLoader()`, `proxy.getClass().getInterfaces()`, and `Proxy.getInvocationHandler(proxy)`.
7. Separate **proxy creation** errors from **handler invocation** errors and **result casting** errors. These three failure points require different fixes.

`Proxy.getProxyClass(loader, interfaces...)` exists to obtain the proxy class, but it is **deprecated** in Java 17; when you need an actual runtime object, prefer `Proxy.newProxyInstance`. Holding strong references to class loaders, generated classes, or proxies in long-lived caches can prevent loaders/plugins from being garbage-collected; manage cache lifecycles intentionally.

## 11. Self-check exercises

**Scenario 1.** `Api.class` is defined in a shared parent loader. A child plugin loader delegates to the parent; the system loader does not see plugin-specific classes. You need to proxy both `Api` and `PluginOnly`. Can you immediately use `Api.class.getClassLoader()`?  
**Answer:** Only if that loader also sees `PluginOnly.class` and all public signature types. Typically, you will need the plugin loader **that is able to see both**; verify each identity first.

**Scenario 2.** Two independent loaders both load a class named `com.example.Api`; by name they are completely identical. Can a proxy created from loader A's `Api` be cast to loader B's `Api`?  
**Answer:** There is no guarantee. The two `Class<?>` objects have different identities; casting can throw `ClassCastException`. The durable solution is to unify the contract's loading scope.

**Scenario 3.** A thread pool sets TCCL to a loader that only sees JDK classes; `MyApi` is defined by the application loader. Why does `Proxy.newProxyInstance(TCCL, ...)` fail?  
**Answer:** TCCL does not see the exact `MyApi.class`. Choosing by thread fails the `Class.forName(...) == MyApi.class` condition.

**Scenario 4.** An interface has a default method, but the handler does not call the default logic. Does the JVM run the default method automatically?  
**Answer:** No. The invocation goes through the handler; on Java 17 you must call `InvocationHandler.invokeDefault` if you want the default behavior.

**Scenario 5.** Why does seeing `proxy.getClass().getModule().isNamed()` return `true` not prove that the input interface is in a named module?  
**Answer:** The runtime may place the generated proxy class into a separate **dynamic named module**. You must check `interfaceClass.getModule()` and `proxy.getClass().getModule()` separately.
