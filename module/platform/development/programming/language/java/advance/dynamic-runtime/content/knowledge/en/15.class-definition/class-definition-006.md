# 15.6 defineHiddenClassWithClassData and Accessing Class Data via MethodHandles

Java can define a **hidden class** directly from bytecode and attach a dedicated data object to that class's identity. The key API pair is `MethodHandles.Lookup.defineHiddenClassWithClassData` to **create the class and attach data**, and `MethodHandles.classData` / `MethodHandles.classDataAt` to **read the data** from a `Lookup` with appropriate access.

This mechanism is useful for runtime compilers, lambda-like implementations, serializer-generating frameworks, DSL interpreters, or libraries that need to generate many classes from the same template with different configurations. It is not an API meant to replace all static fields or constructors in ordinary Java.

Key points to grasp:

- `defineHiddenClassWithClassData(bytes, classData, initialize, options...)` takes a **valid class file `byte[]`** and **a data object**; it **does not compile Java source**.
- The result is a `MethodHandles.Lookup` pointing to the **new hidden class**, not a `Class<?>` directly. Retrieve `Class<?>` via `hiddenLookup.lookupClass()`.
- `MethodHandles.classData(hiddenLookup, "_", List.class)` reads the **entire object**. If the object is a `List`, `classDataAt(hiddenLookup, "_", String.class, 0)` reads a single element.
- The constant/data name is always `"_"` (`ConstantDescs.DEFAULT_NAME`); you cannot arbitrarily use `"config"` or a field name.
- The Lookup used for reading requires **`Lookup.ORIGINAL` access**, which is higher than merely having a `Class<?>` reference or ordinary reflection permissions.
- Class data can be read by calling the API directly or through a **`CONSTANT_Dynamic` bootstrap** in dynamically generated bytecode.
- It is necessary to distinguish between **defining/linking** a class, **initializing** a class, **reading data**, **invoking a method handle**, and **lifecycle/unloading**.

## 1. Map of Participating Objects

| Object | Function | Not equivalent to |
| --- | --- | --- |
| `byte[] bytes` | Class file bytes describing a valid JVM template | A `.java` file or a class name |
| `Lookup host` | Permission to define a class in the right runtime package/module | An arbitrary class loader |
| `classData` | An object attached to the hidden class; can be `List.of(...)` or a custom configuration | A named Java static field |
| `Lookup hiddenLookup` | Returned Lookup, pointing to the new class, with `ORIGINAL` and full privilege | The host's Lookup |
| `Class<?> hidden` | Identity of the hidden class, `isHidden() == true` | An ordinary template class |
| `MethodHandles.classData` | Retrieves the whole data object, per the lookup class | `Class.getDeclaredField` |
| `MethodHandles.classDataAt` | Retrieves an element by index in List data | An indexed accessor for any Map/array |
| `MethodHandle` | Handle invoking a method/constructor of the hidden class or another method | Class data itself |
| `CONSTANT_Dynamic` | Constant-pool entry whose value is computed by a bootstrap | `invokedynamic` using `CallSite` to link a call |

Flow diagram:

~~~text
Framework (host, trusted)
  |
  +-- class file bytes of Template
  +-- data = List.of("prefix:", 2)
  |
  v
hostLookup.defineHiddenClassWithClassData(bytes, data, false, NESTMATE)
  |
  +----> hiddenLookup (ORIGINAL + full privilege)
            |
            +----> lookupClass() ----> Class<?> hidden; hidden.isHidden() == true
            |
            +----> MethodHandles.classData(hiddenLookup, "_", List.class)
            |                                 -> ["prefix:", 2]
            |
            +----> classDataAt(hiddenLookup, "_", String.class, 0)
            |                                 -> "prefix:"
            |
            +----> findStatic(hidden, "render", (String)String)
                                        |
                                        v
                                invokeExact("Go")
                                        |
                              code of the hidden class uses
                              its MethodHandles.lookup()
                                        |
                           classData + classDataAt via ORIGINAL
                                        |
                                        v
                           "prefix:GoGo / entries=2"
~~~

**Note on separating two things:** the hidden class is new JVM code, while `classData` is the **data object** that the JVM attaches to that class. A class can receive data containing a `MethodHandle`; however, that does not turn the data itself into a method invocation. You need to build an execution handle separately when you want to run logic.

## 2. API Signature: Defining a Class with Data

~~~java
MethodHandles.Lookup defineHiddenClassWithClassData(
        byte[] bytes,
        Object classData,
        boolean initialize,
        MethodHandles.Lookup.ClassOption... options)
        throws IllegalAccessException
~~~

The method is called **on a `Lookup`**, for example `MethodHandles.lookup()` created in trusted host code. It requires the lookup to have **full privilege access** (`PRIVATE` and `MODULE` access); `publicLookup()` usually does not have sufficient privileges.

| Parameter | Role | Conditions/notes |
| --- | --- | --- |
| `bytes` | Byte array of a valid `ClassFile` | Supported class file version, valid for verifier, **same package** as the lookup class |
| `classData` | Object prepared before definition | Multiple values can be wrapped in `List.of(...)`; should be immutable |
| `initialize` | `true` to request immediate initialization; `false` to defer | `classData`/`classDataAt` can actively trigger `<clinit>` later |
| `options` | `NESTMATE`, `STRONG`, or no options | Affects nest access and hidden class lifecycle |
| Result | `Lookup` on the newly defined hidden class | Has `ORIGINAL` and **full privilege** on the new class |

Compared to `Lookup.defineHiddenClass(bytes, initialize, options...)`, the `WithClassData` variant also attaches a **data object**. `defineHiddenClass` normally does not attach data; when reading with `MethodHandles.classData` on a hidden class without data, the result is `null`.

### Why does the API return a `Lookup`, not a `Class<?>` directly?

The framework needs a capability to continue looking up methods/constructors of the new class and, if valid, reading class data. The returned `Lookup` has `lookupClass()` returning `Class<?>`; it also carries initial privileges for the new class itself. You can call `hiddenLookup.findStatic(hiddenClass,...)` or `hiddenLookup.findConstructor(...)` by signature, without needing to look up the class by name via `Class.forName`.

However, **do not expose the entire original Lookup** to untrusted components. This capability can do much more than a specialized method handle; only pass consumers what they actually need.

## 3. `MethodHandles.classData`: Reading the Whole Object, Not Fields

Standard signature:

~~~java
public static <T> T classData(
        MethodHandles.Lookup caller,
        String name,
        Class<T> type) throws IllegalAccessException
~~~

| Parameter | Meaning |
| --- | --- |
| `caller` | `Lookup` with `ORIGINAL`; `caller.lookupClass()` is the class from which the JVM reads class data |
| `name` | Must be `"_"` (the constant `ConstantDescs.DEFAULT_NAME`), not an optional key |
| `type` | Requested type when retrieving data, such as `List.class`, `String.class`, `MethodHandle.class` |

For example, with data `List.of("prefix:", 2)`:

~~~java
List<?> all = MethodHandles.classData(hiddenLookup, "_", List.class);
~~~

This is a **non-standalone** snippet, assuming `hiddenLookup` already points to a hidden class with List data. `List<?>` reflects erasure at Java runtime: there is no `List<String>.class`. If the requested type is incompatible with the actual object, the API throws `ClassCastException`. If the class has no data, it returns `null`.

If you call:

~~~java
MethodHandles.classData(hostLookup, "_", List.class);
~~~

then the API reads the data of **`hostLookup.lookupClass()`**, not automatically any hidden class created by the host. For a normal host class with no data, the result is `null`. This is a fairly common mental mistake: `Lookup` identifies the **target**, not whichever `Class<?>` object you are thinking of in scope.

**Access condition:** `ORIGINAL` is a special mode. A `Lookup` may be able to access private methods under access rules yet still **lack `ORIGINAL`**, and therefore cannot read class data. `MethodHandles.lookup()` called directly inside the hidden class's code creates its own original lookup; the returned hidden Lookup from the factory also has original access.

## 4. `MethodHandles.classDataAt`: List-Shaped Data

Signature:

~~~java
public static <T> T classDataAt(
        MethodHandles.Lookup caller,
        String name,
        Class<T> type,
        int index) throws IllegalAccessException
~~~

This method is for **List class data**, reading each element by `index`. The `type` parameter is **the type of the element**, not the type of the List.

Example:

~~~java
String prefix = MethodHandles.classDataAt(
        hiddenLookup, "_", String.class, 0);
Integer repeat = MethodHandles.classDataAt(
        hiddenLookup, "_", Integer.class, 1);
~~~

If the class data is `List.of("prefix:", 2)`, the corresponding results are `"prefix:"` and `Integer.valueOf(2)`.

| Issue | Behavior |
| --- | --- |
| `name` other than `"_"` | `IllegalArgumentException` |
| Lookup lacks `ORIGINAL` | `IllegalAccessException` |
| Class data is not a `List` | `ClassCastException` when reading as a List |
| Element has a type incompatible with `Class<T>` | `ClassCastException` |
| Negative index or index greater than or equal to List size | `IndexOutOfBoundsException` |
| Class data does not exist | Returns `null` per API contract |
| A `null` element in a situation requiring primitive unboxing | May encounter `NullPointerException` |

`List.of(...)` does not accept null elements and does not allow modifying the List structure; this is a suitable choice when data is used as fixed information for a hidden class. If you want to pass a single object, **there is no need to create a List**: `classData` reads that object directly, while `classDataAt` is only for when there is a List.

### `classData` is not an API for “multiple named variables”

A hidden class attaches **one data object**. You cannot call `classData(hiddenLookup,"name1",...)` and `classData(hiddenLookup,"name2",...)` to read two separate fields. The solution is to create a **record/config object** or a **List** and then access it by element/schema. The character `"_"` is the standardized name of the constant-dynamic bootstrap, not a user-defined storage key.

## 5. Access Permissions: `full privilege` to Define, `ORIGINAL` to Read

The two operations require different permissions:

1. **Define:** `hostLookup.defineHiddenClassWithClassData(...)` requires `hostLookup.hasFullPrivilegeAccess()` to be true. Bytes must describe a class or interface in the same package.
2. **Read:** `MethodHandles.classData(hiddenLookup,"_",...)` requires `hiddenLookup.lookupModes()` to contain `Lookup.ORIGINAL`. `PRIVATE`/`MODULE` permissions on a context-switched lookup do not automatically substitute for `ORIGINAL`.

Table:

| `Lookup` | What can it do? |
| --- | --- |
| `MethodHandles.lookup()` in trusted host | Can define a hidden class in the same package when it has full privilege |
| Lookup returned from `defineHiddenClassWithClassData` | Points to the new hidden class, has `ORIGINAL` and full privilege |
| `MethodHandles.lookup()` called inside a method of the hidden class | Original Lookup of the hidden class itself; used to read class data |
| `MethodHandles.publicLookup()` | Lacks full privilege to define a hidden class, lacks `ORIGINAL` to read class data |
| `lookup.in(otherClass)` | Can lose modes; not a way to grant `ORIGINAL` |
| `MethodHandles.privateLookupIn(...)` | Subject to access/JPMS checks, not an instruction to arbitrarily create `ORIGINAL` access |
| `hiddenLookup.dropLookupMode(PRIVATE)` | In the example, removes required access, causing `classData` to throw `IllegalAccessException` |

In the following program, checking:

~~~java
(hiddenLookup.lookupModes() & MethodHandles.Lookup.ORIGINAL) != 0
~~~

returns `true`. This proves the lookup provided by the factory carries the necessary mode; a mere `Class<?>` has no equivalent capability information.

**Do not call `Class.forName(hidden.getName())` to recover access.** A hidden class cannot be looked up by its ordinary name, and even if you have a class reference, you do not automatically obtain its original Lookup.

## 6. Class Bytes, Same Package, and Identity

`defineHiddenClassWithClassData` takes **class file bytes**. You can obtain them from:

- A precompiled template class, reading the `.class` resource via `Class.getResourceAsStream`.
- A suitable bytecode generator/library producing a verified class file.
- The code generator of a DSL/runtime compiler, then passing `byte[]` to Lookup.

Do not pass a `.java` file path, source string, or binary name. When using a template class yourself, **the bytecode must be in the same runtime package** as the lookup class. The resource path is just a way to obtain the bytes of the compiled template; the actual hidden class is created separately by the JVM.

Example:

~~~java
String resource =
        "/" + Template.class.getName().replace('.', '/') + ".class";
byte[] bytes;
try (InputStream input = Template.class.getResourceAsStream(resource)) {
    if (input == null) throw new IOException("Missing: " + resource);
    bytes = input.readAllBytes();
}
~~~

The snippet requires `InputStream`, `IOException`, and a nested class `Template` in a real program. If the source is placed in package `example.runtime`, ensure both host and Template are in the same package, and the resource path is constructed from the binary name as above.

**The result is a new class identity.** Even though the bytes are taken from `Template.class`, the created hidden class is **distinct** from the ordinary template. `Class.isHidden()` returns `true`, its runtime name has a JVM-managed suffix form, and it cannot be found with `Class.forName(...)` via ordinary name lookup. Each call to the factory with the same bytes normally creates **a new hidden class**, with its own class data.

## 7. Complete Java 17+ Example: Creating a Hidden Class with List Data, Invoking a Method, and Checking Errors

Create the file **`HiddenClassDataDemo.java`**. The program requires no external libraries, as it reuses the bytes of a nested template class. The method `Template.render` executes **in the hidden class**, so `MethodHandles.lookup()` inside it points to the hidden class, not the host.

~~~java
import java.io.IOException;
import java.io.InputStream;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;
import java.util.List;

public final class HiddenClassDataDemo {
    public static class Template {
        static {
            System.out.println("hidden template initialized");
        }
        public static String render(String input) throws IllegalAccessException {
            MethodHandles.Lookup self = MethodHandles.lookup();
            List<?> all = MethodHandles.classData(self, "_", List.class);
            String prefix = MethodHandles.classDataAt(self, "_", String.class, 0);
            Integer repeat = MethodHandles.classDataAt(self, "_", Integer.class, 1);
            return prefix + input.repeat(repeat) + " / entries=" + all.size();
        }
    }
    public static void main(String[] args) throws Throwable {
        String resource = "/" + Template.class.getName().replace('.', '/') + ".class";
        byte[] bytes;
        try (InputStream input = Template.class.getResourceAsStream(resource)) {
            if (input == null) throw new IOException("Missing class resource: " + resource);
            bytes = input.readAllBytes();
        }

        List<Object> data = List.of("prefix:", 2);
        MethodHandles.Lookup host = MethodHandles.lookup();
        MethodHandles.Lookup hiddenLookup = host.defineHiddenClassWithClassData(
                bytes, data, false, MethodHandles.Lookup.ClassOption.NESTMATE);
        Class<?> hidden = hiddenLookup.lookupClass();

        System.out.println("hidden = " + hidden.isHidden());
        System.out.println("hidden name has slash = " + hidden.getName().contains("/"));
        System.out.println("original access = " +
                ((hiddenLookup.lookupModes() & MethodHandles.Lookup.ORIGINAL) != 0));
        System.out.println("class data not ordinary field = " +
                (hidden.getDeclaredFields().length == 0));
        System.out.println("before reading class data");
        List<?> received = MethodHandles.classData(hiddenLookup, "_", List.class);
        System.out.println("class data = " + received);
        System.out.println("element 0 = " +
                MethodHandles.classDataAt(hiddenLookup, "_", String.class, 0));
        MethodHandle call = hiddenLookup.findStatic(hidden, "render",
                MethodType.methodType(String.class, String.class));
        System.out.println("handle type = " + call.type());
        System.out.println("render = " + (String) call.invokeExact("Go"));

        try {
            MethodHandles.classData(hiddenLookup, "wrongName", List.class);
        } catch (IllegalArgumentException ex) {
            System.out.println("wrong name = " + ex.getClass().getSimpleName());
        }
        try {
            MethodHandles.classData(hiddenLookup, "_", String.class);
        } catch (ClassCastException ex) {
            System.out.println("wrong type = " + ex.getClass().getSimpleName());
        }
        try {
            MethodHandles.classDataAt(hiddenLookup, "_", String.class, 9);
        } catch (IndexOutOfBoundsException ex) {
            System.out.println("wrong index = " + ex.getClass().getSimpleName());
        }
        MethodHandles.Lookup reduced = hiddenLookup.dropLookupMode(
                MethodHandles.Lookup.PRIVATE);
        try {
            MethodHandles.classData(reduced, "_", List.class);
        } catch (IllegalAccessException ex) {
            System.out.println("reduced lookup = " + ex.getClass().getSimpleName());
        }
        System.out.println("host data absent = " +
                (MethodHandles.classData(MethodHandles.lookup(), "_", Object.class) == null));

        try {
            Class.forName(hidden.getName());
        } catch (ClassNotFoundException ex) {
            System.out.println("Class.forName hidden = " + ex.getClass().getSimpleName());
        }
    }
}
~~~

Run from the directory containing the file with **JDK 17 or later**:

~~~bash
javac --release 17 HiddenClassDataDemo.java
java HiddenClassDataDemo
~~~

This is not a claim that the program was run separately on a JDK 17 machine; however, the APIs used have existed since Java 16 and all the output above was verified from a real run.

### 7.1. Why is `hidden.isHidden()` `true`?

`host.defineHiddenClassWithClassData` does not look up or modify `Template.class`, but creates a new hidden class identity from bytes. On the JVM used for testing, this class's name contains `/` and a special suffix, and `Class.forName(hidden.getName())` throws `ClassNotFoundException`. This illustrates that **a hidden class cannot be treated as a public class discoverable by name**; keep the `hiddenLookup`/`Class<?>`/`MethodHandle` provided by the factory when further use is needed.

### 7.2. Why does class data not appear as an ordinary field?

Template in the demo declares no data fields. The result `hidden.getDeclaredFields().length == 0` was `true` in the test run, while `MethodHandles.classData(hiddenLookup,"_",List.class)` still retrieved `[prefix:,2]`. The class data API has its own JVM model; you do not need to and should not assume a public/private static field named `"classData"` exists to be read.

### 7.3. Why does the static initializer run in the middle of the output?

`defineHiddenClassWithClassData(..., false, ...)` **defines and links** the class without forcing initialization itself. After printing `before reading class data`, the call `MethodHandles.classData(...)` **ensures class initialization** if not yet initialized. Thus the order:

~~~text
before reading class data
hidden template initialized
class data = [prefix:, 2]
~~~

is not accidental. If `initialize=true` is passed, initialization is requested during class definition, so the static initializer can run earlier.

### 7.4. Why can `render` read data from the hidden class itself?

`Template.render`, when executed on the **hidden class**, calls `MethodHandles.lookup()` in the context of the hidden class. This lookup has `ORIGINAL`, so `classData` reads the List and `classDataAt` reads prefix/repeat. `"Go".repeat(2)` is `"GoGo"`; the result is `prefix:GoGo / entries=2`. `hiddenLookup.findStatic` creates a handle of type `(String)String`, and `invokeExact` is called with exact matching argument/return types.

### 7.5. Why do name/type/index/access errors differ?

- `wrongName` other than `"_"` → `IllegalArgumentException`.
- Requesting `String.class` for the whole `List` data → `ClassCastException`.
- Retrieving index `9` of a two-element List → `IndexOutOfBoundsException`.
- `dropLookupMode(PRIVATE)` removes `ORIGINAL` from this lookup → `IllegalAccessException`.
- Calling `classData` with the lookup of an **ordinary host class** returns `null`, not the class data of the newly created hidden class.

These exceptions occur at the **read step**, not as Java compiler errors from using a generic List type or `MethodHandle.invokeExact` errors.

## 8. `CONSTANT_Dynamic` (condy): Reading Class Data in Bytecode as a Dynamic Constant

`MethodHandles.classData` and `classDataAt` are designed to be usable as **bootstrap methods** for a **dynamically computed constant** in the JVM constant pool. A runtime framework can generate a hidden class with bytecode containing `CONSTANT_Dynamic_info` pointing to these bootstraps. When the constant is resolved, the JVM provides the lookup of the class containing the resolution site along with the constant's name/type, and receives the result from class data.

Example **bytecode/constant-pool diagram**, not standalone Java source:

~~~text
Hidden class data = List.of("PREFIX:", methodHandle, schemaObject)
                                  |
                                  v
Constant-pool entry CONSTANT_Dynamic
  name               = "_"
  descriptor          = Ljava/lang/invoke/MethodHandle;
  bootstrap reference = MethodHandles.classDataAt
  static argument     = index 1
                                  |
                         JVM resolves constant
                                  |
             classDataAt(originalLookup, "_", MethodHandle.class, 1)
                                  |
                                  v
                     MethodHandle from List data
                                  |
                 resolved constant-dynamic entry
~~~

Distinguishing `classData` and `classDataAt` as bootstraps:

| Bootstrap | Value received |
| --- | --- |
| `MethodHandles.classData(caller, "_", DesiredType.class)` | The entire data object, cast/converted to the requested type |
| `MethodHandles.classDataAt(caller, "_", ItemType.class, index)` | An item of the List; `index` is a **static bootstrap argument** |

**Condy is not invokedynamic.** `CONSTANT_Dynamic` binds a **constant value** and has a descriptor of that value's type; `invokedynamic` binds a **call site** via a `CallSite` and has a method descriptor. Both can use a bootstrap Lookup, but their semantics/result kinds differ.

Plain Java source generally has no syntax to arbitrarily declare a `CONSTANT_Dynamic` with a custom bootstrap. To implement this diagram, a framework needs to **generate a valid class file** (perhaps using a bytecode library or a suitable class-file API), then define the hidden class from the generated bytes. The program in section 7 illustrates **reading class data directly**, without pretending that an ordinary Java call generated a custom condy.

### Why is condy mentioned in the class data documentation?

Class data is designed so that the data is only available to a **Lookup with `ORIGINAL`**. When hidden class code needs a `MethodHandle` or class metadata attached to the class, a constant-dynamic bootstrap can help load the needed value directly without placing the data in a named static field. This supports frameworks that need to restrict access scope. However, if code actively publishes the data or the original Lookup externally, the hidden mechanism does not prevent leaks on its own.

## 9. `NESTMATE` and `STRONG` Are Two Different Options

| `Lookup.ClassOption` | Meaning | When to use |
| --- | --- | --- |
| Without `NESTMATE` | Does not require the hidden class to be a nestmate of the lookup class | When private access between classes in the nest is not needed |
| `NESTMATE` | The hidden class is added to the corresponding nest per JVM rules | When generated code needs valid nest access |
| Without `STRONG` | The hidden class can be unloaded when no references keep the class alive | When you want the hidden class to have a temporary lifecycle |
| `STRONG` | The hidden class is strongly held by the class loader, close to an ordinary class | When you need the class to remain stable until the class loader is gone |

**Point to remember:** `NESTMATE` **does not allow every nestmate to read class data**. Reading data still requires `ORIGINAL` of the exact target lookup class. Similarly, `STRONG` does not affect the data type or data access permissions; it relates to **class lifecycle**.

If you create many hidden classes while holding all `Class<?>`, `Lookup`, and `MethodHandle` references in a global cache, you can cause them to stay alive longer than expected even without using `STRONG`. Design cache/class loader lifecycles clearly, measure metaspace, and drop unused references.

## 10. Class Initialization: `initialize=false` Does Not Mean “Never Run `<clinit>`”

Process:

~~~text
defineHiddenClassWithClassData(bytes, data, false, options)
  -> class is defined + linked
  -> initialization not yet forced at the factory itself
  -> hiddenLookup.lookupClass() can retrieve the Class object

Afterward:
MethodHandles.classData(hiddenLookup, "_", Type.class)
  -> ensures hidden class initialization if not yet initialized
  -> returns data after valid checks

Or:
defineHiddenClassWithClassData(bytes, data, true, options)
  -> defines + links + actively requests initialization
~~~

When reading class data, the JVM may execute the static initializer, and the initializer may perform I/O, allocate, or throw an error. Keep `<clinit>` lean, avoid class initialization dependency cycles, and understand that `ExceptionInInitializerError` is an initialization error, not an error from an out-of-bounds `classDataAt` index.

The Javadoc describes class data as prepared as if there were a private static final unnamed field set at the start of initialization. That is a **semantic model**; do not write code assuming there is a field named `CONFIG` or `classData` that reflection can find.

## 11. Data Design: Immutability and Clear Schema

A hidden class has **one class data object**, so if multiple values are needed, wrap them in a List/record:

~~~java
List<Object> data = List.of(
        "prefix:",
        Integer.valueOf(2),
        methodHandle);
~~~

This snippet assumes `methodHandle` has been safely created. `List.of(...)` is structurally immutable and does not allow `null` elements. However, this **does not make each item immutable**: a mutable object placed inside the List can still change.

The Javadoc warns that mutating an object used as class data after the class is linked can lead to unpredictable behavior, especially if the data is treated as constant or optimized by the JIT. Therefore:

1. Choose immutable/effectively immutable data whenever possible.
2. Standardize item order and types: `0 = String prefix`, `1 = Integer count`, etc.
3. Protect the original Lookup; avoid exposing it in public APIs arbitrarily.
4. Do not use class data as a shared mutable map in place of properly synchronized state.
5. For data needing runtime updates, consider a dedicated state object and concurrency contract, or `MutableCallSite`/`VolatileCallSite` when the goal is changing behavior.
6. Do not log tokens or secrets attached to class data. “Hidden” does not mean the data is an absolute secret.

## 12. When to Use Class Data Instead of Static/Instance Fields?

| Aspect | Class data | Static field | Instance field |
| --- | --- | --- | --- |
| Attached to | Hidden class identity | Class | Each instance |
| Multiple values | One composite object, e.g., `List` | Multiple fields | Multiple fields |
| Reading | Original Lookup + `classData`/`classDataAt` | Valid field access/VarHandle/reflection | Receiver + field access |
| Has Java field name? | Not like a normally declared field | Yes | Yes |
| Nestmate access | Does not automatically open class data to all nestmates | Private field can be accessed by nestmates | Private field can be accessed by nestmates |
| Initialization | Attached when defining hidden class | Usually via `<clinit>` | Via constructor/initializer |
| Used for condy | Yes, `classData`/`classDataAt` bootstrap | Not a direct replacement | Not a direct replacement |

If an application only has a few objects with simple configuration, **constructor injection + instance fields** are usually easier to read, easier to test, and have fewer JVM constraints. Hidden class class data is valuable when **executable code itself is dynamically generated** and you want data bound to that class.

## 13. Error Table by Stage

| Stage | Error/phenomenon | Typical cause |
| --- | --- | --- |
| Defining bytes | `IllegalAccessException` | Host lookup lacks full privilege |
| Defining bytes | `IllegalArgumentException` | Template bytes are in a different package or class file type is unsuitable |
| Defining bytes | `ClassFormatError` | Byte array is not a valid ClassFile |
| Defining bytes | `UnsupportedClassVersionError` | Bytecode version is not supported by the running JVM |
| Defining/linking | `VerifyError` / `LinkageError` | Invalid bytecode/stack map or resolution error |
| Defining | `NullPointerException` | Bytes or required argument is `null` |
| Reading data | `IllegalArgumentException` | `name` is not equal to `"_"` |
| Reading data | `IllegalAccessException` | Lookup lacks `ORIGINAL` |
| Reading data | `ClassCastException` | Whole data or List item does not match requested type |
| Reading data | `IndexOutOfBoundsException` | `classDataAt` has `index` out of range |
| Reading data | `NullPointerException` | `caller`/`type` is null or primitive unboxing requires a non-null item |
| Reading data | Returns `null` | Lookup class has no class data |
| Invoking handle | `NoSuchMethodException` | `findStatic` has wrong method name/descriptor |
| Invoking handle | `WrongMethodTypeException` | `invokeExact` call-site type does not equal `MethodHandle.type()` |
| Looking up hidden by name | `ClassNotFoundException` | Hidden class has no ordinary lookup mechanism via `Class.forName` |
| Class initialization | `ExceptionInInitializerError` | `<clinit>` logic throws an error |
| Lifecycle | Does not unload as expected | Strong references held via cache/loader or `STRONG` is used |

Separate **bytecode errors**, **access errors**, **data schema errors**, **method handle errors**, and **initialization errors**. If you catch every `Throwable` and return `null`, you will hide the reason why the class could not be defined or why runtime logic failed.

## 14. Common Misconceptions

### “Having `Class<?>` lets you read class data?”

No. `MethodHandles.classData` takes a `Lookup`, not an arbitrary `Class<?>`. The Lookup must have `ORIGINAL` and must point to the **exact hidden class**. `publicLookup().in(hidden)` does not create this permission.

### “Having `PRIVATE` is enough?”

No. `Lookup.ORIGINAL` is a distinct mode required for `classData` and `classDataAt`. For example, `dropLookupMode(PRIVATE)` causes the lookup to lose its reading eligibility. Mechanisms like `in(...)`/`privateLookupIn(...)` are not ways to arbitrarily grant original access.

### “`classDataAt` can retrieve an item from an array or Map?”

Not per the API contract. It is defined for class data that is a **`List`**. For an array/Map, call `classData` to retrieve the object and then access it via that object's API (if application policy allows).

### “`initialize=false` prevents the static initializer forever?”

No. Operations requiring initialization such as `classData`/`classDataAt` or appropriate invocations can still trigger `<clinit>`. The demo output clearly shows this timing.

### “`NESTMATE` makes class data readable from the host?”

No. `NESTMATE` changes nest membership/the ability to access private members; it **does not replace an original lookup**. The trusted host can read it because it keeps the returned `hiddenLookup`, not merely because it happens to be a nestmate.

### “Can you call `Class.forName(hidden.getName())` and then invoke?”

Not like with an ordinary Java class. Keep the `Class<?>`/`Lookup`/`MethodHandle` reference returned when creating the hidden class.

### “Want a `classData` object per request, just mutate the List each time?”

Do not do this. Use class data for fixed configuration information attached to the class identity. For per-request mutable state, pass arguments through handles or design an instance/state object instead of mutating data meant to be constant.

## 15. Implementation and Testing Checklist

- Bytecode is compiled/generated for the right Java version, in the same package as the lookup class.
- Host lookup has full privilege, not obtained from `publicLookup()`.
- Data is standardized, preferably immutable, with a consistent item type/index schema.
- Class options `NESTMATE`/`STRONG` are chosen based on actual requirements, not habit.
- `initialize` is designed to avoid unexpected `<clinit>` side effects.
- Returned original Lookup is kept secure; avoid returning the raw capability to untrusted code.
- Inside the hidden class, use its own `MethodHandles.lookup()` if data needs to be read.
- Call `classData(...,"_",Type.class)` with the right class/type; use `classDataAt` only for Lists.
- Invoke methods of the hidden class using `findStatic`/`findVirtual`/... with the exact `MethodType`.
- Test wrong name, wrong type, wrong index, reduced lookup, absent data, and deferred initialization.
- Check memory/class unloading if generating many hidden classes; do not hold an unbounded cache.
- When generating real condy, inspect the constant pool, bootstrap descriptor, and resolved type instead of assuming a Java call to `classData` automatically generated condy.

## 16. Self-Check

**1.** What does `defineHiddenClassWithClassData` return?  
**Answer:** An original/full-privilege `MethodHandles.Lookup` on the new hidden class; retrieve `Class<?>` via `lookupClass()`.

**2.** Is `classData(hiddenLookup, "settings", List.class)` valid?  
**Answer:** No; `name` must be `"_"` (the constant `ConstantDescs.DEFAULT_NAME`). A wrong name causes `IllegalArgumentException`.

**3.** Given `List.of("A", 3)`, how do you retrieve the `Integer` at index 1?  
**Answer:** `MethodHandles.classDataAt(hiddenLookup, "_", Integer.class, 1)`.

**4.** Does `initialize=false` guarantee that reading class data will not run `<clinit>`?  
**Answer:** No. `classData`/`classDataAt` ensures initialization of the lookup class if needed.

**5.** Once you have `Class<?> hidden` and private reflection, can you arbitrarily read class data?  
**Answer:** No. The API requires `Lookup.ORIGINAL` for the exact hidden class, not just reflection permissions.

**6.** How do `CONSTANT_Dynamic` and `invokedynamic` differ?  
**Answer:** Condy binds a constant value; invokedynamic binds a call site via a CallSite. Both can use bootstraps and MethodHandles.

**7.** If a hidden class is created with `NESTMATE`, is every nestmate allowed to read its class data?  
**Answer:** No. `ORIGINAL` access is a separate constraint.

**8.** Why should you not mutate ArrayList-shaped class data after linkage?  
**Answer:** The Javadoc warns of unpredictable behavior if data intended as constant is mutated; use immutable/effectively immutable data or design separate state instead.

**9.** Class data is a List, but what does `classData(hiddenLookup,"_",String.class)` do?  
**Answer:** Throws `ClassCastException` because the whole object is a List, not a String.

**10.** Does defining the same template bytes twice yield a single class?  
**Answer:** No. Each successful definition creates a separate hidden class identity with its own attached data.
