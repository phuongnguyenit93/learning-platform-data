# 13.5 altMetafactory with bridges, marker interfaces, and serialization requirements

A lambda expression in Java is typically compiled into an `invokedynamic` call site linked by `java.lang.invoke.LambdaMetafactory`. The basic `metafactory` method creates an object implementing a *functional interface* (an interface with one abstract method functionally). When **multiple method signatures**, **additional marker interfaces**, or **serialization support** are needed, the JVM and compiler can use the extended variant `LambdaMetafactory.altMetafactory`.

Three names to master:

- **`FLAG_BRIDGES`:** requests adding methods with the **same name** but different JVM signatures, all delegating to the implementation. They help connect the views of an abstract method with the signature forms that need adaptation.
- **`FLAG_MARKERS`:** adds one or more interfaces to the interface list of the generated lambda class; the common case is marker interfaces that have no abstract methods of their own.
- **`FLAG_SERIALIZABLE`:** requests the lambda object to support Java serialization via the `SerializedLambda` mechanism, while also imposing an important requirement on the *capturing* class during deserialization.

The lesson moves from the linkage–capture–invocation model, the `Object... args` protocol, and how to verify method signatures/markers via Reflection, to the **practical limits of serializable lambdas**. There are three Java 17+ verification programs: calling `altMetafactory` manually to create bridges and markers; an intersection-type lambda generated by `javac` that serializes/deserializes successfully; and a scenario of **manual `altMetafactory` with `FLAG_SERIALIZABLE` that lacks the conditions to deserialize**. The source code and `stdout` in the lesson can be used to run on your own.

## 1. What does LambdaMetafactory link?

`LambdaMetafactory` is not simply a "new lambda" function. The Javadoc describes three phases:

1. **Linkage:** the bootstrap receives `Lookup`, the abstract method name, the factory `MethodType`, and the implementation handle; the result is a `CallSite`.
2. **Capture:** the `CallSite` target is invoked with *captured* variables (if any) to create or obtain a *function object* implementing the interface.
3. **Invocation:** a method on the function object is called; the stored captured arguments and invocation arguments are forwarded to the implementation.

Conceptual flow:

```text
class file / linker
  LambdaMetafactory.altMetafactory(lookup, "apply", factoryType, args...)
           |
           v
      CallSite  --getTarget()-->  factory MethodHandle
                                      |
                                capture arguments
                                      |
                                      v
                            object implements Mapper
                                + marker(s)
                                + optional bridge(s)
                                + optional serialization protocol
                                      |
                            mapper.apply(...)
                                      |
                                      v
                           implementation MethodHandle
```

A `CallSite` can be used to create multiple function objects; the number of object creations does not equal the number of linkages. The JVM may optimize stateless captures to reuse objects; **do not rely on `==` identity, lambda class names, default hashCode, or allocation counts** in business logic design.

### 1.1. `factoryType` is not the abstract method's signature

Example interface:

```java
@FunctionalInterface
interface Mapper {
    Object apply(Object value);
}
```

This illustrative declaration snippet is not a standalone program.

- `factoryType = ()Mapper`: the CallSite target takes no captures and **returns Mapper**.
- `interfaceMethodType = (Object)Object`: the bytecode type of the abstract method `apply` on Mapper.
- `implementation = (String)String`: the actual method, which could be `normalize(String)`.
- `dynamicMethodType = (String)String`: the concrete type used to constrain/check calls at runtime.

These four elements **do not share the same role**, even though their signatures are sometimes identical. For a lambda capturing a `prefix` variable, `factoryType` might be `(String)Mapper` instead of `()Mapper`, because the caller must supply the prefix when creating the object. The object's `apply` method still only takes the business parameter `value`.

## 2. `altMetafactory` signature and the position of each argument

Java 17 API:

```java
public static CallSite altMetafactory(
        MethodHandles.Lookup caller,
        String interfaceMethodName,
        MethodType factoryType,
        Object... args) throws LambdaConversionException
```

This is an API signature, not a standalone Java file. Although `args` is `Object...`, the Javadoc defines **a strict protocol regarding position and type**, interpreted as follows:

```text
args[0] = interfaceMethodType       // MethodType: SAM erased
args[1] = implementation            // MethodHandle: direct
args[2] = dynamicMethodType         // MethodType: instantiated SAM
args[3] = flags                     // int (boxed Integer)

if flags has FLAG_MARKERS:
    int altInterfaceCount
    Class<?> altInterfaces[altInterfaceCount]

if flags has FLAG_BRIDGES:
    int altMethodCount
    MethodType altMethods[altMethodCount]
```

**Fixed order:** four mandatory parameters → **marker count + interfaces** if the marker flag is set → **bridge count + MethodTypes** if the bridge flag is set. `FLAG_SERIALIZABLE` has no count and does not introduce an extra args group.

| Input | Type | Meaning |
| --- | --- | --- |
| `caller` | `MethodHandles.Lookup` | Lookup of the class containing the site, must have appropriate privileges (*full privilege access*) |
| `interfaceMethodName` | `String` | Name of the abstract method being implemented, e.g., `"apply"` |
| `factoryType` | `MethodType` | Input at capture and the interface type returned from the factory CallSite |
| `interfaceMethodType` | `MethodType` | Primary functional signature of the functional interface, usually erased |
| `implementation` | `MethodHandle` | **Direct method handle** pointing to the actual method or constructor |
| `dynamicMethodType` | `MethodType` | Instantiated signature that may be narrower in reference types |
| `flags` | `int` | Bitwise OR of `FLAG_BRIDGES`, `FLAG_MARKERS`, `FLAG_SERIALIZABLE` |
| `altInterfaceCount` + interfaces | `int` + `Class<?>` | List of additional interfaces, present only if `FLAG_MARKERS` is enabled |
| `altMethodCount` + method types | `int` + `MethodType` | List of additional method signatures, present only if `FLAG_BRIDGES` is enabled |

Example call syntax, once the appropriate variables are prepared:

```java
int flags = LambdaMetafactory.FLAG_MARKERS
          | LambdaMetafactory.FLAG_BRIDGES;

CallSite site = LambdaMetafactory.altMetafactory(
        lookup, "apply", factoryType,
        samType, directImpl, instantiatedType, flags,
        1, Tagged.class,
        1, MethodType.methodType(String.class, String.class));
```

This is an **illustrative snippet with undeclared variables**, not a standalone program; the full program is in section 6.

**Do not add `markerCount` if `FLAG_MARKERS` is not enabled; do not add `bridgeCount` if `FLAG_BRIDGES` is not enabled.** Conversely, if enabled, you must provide the count (even if 0) and the exact number of elements. Misreading a `Class` as a `MethodType` or placing the bridge group before the marker group is a protocol structure error, not a generic cast issue that can fix itself.

### 2.1. Combining flags

There is no precedence order for the three flags; combine them with OR:

```java
int flags = LambdaMetafactory.FLAG_MARKERS
          | LambdaMetafactory.FLAG_BRIDGES
          | LambdaMetafactory.FLAG_SERIALIZABLE;
```

Table for preparing `args`:

| `flags` | Args portion after `samType, impl, instantiatedType, flags` |
| --- | --- |
| `0` | None |
| `FLAG_MARKERS` | `markerCount, Marker1.class, ...` |
| `FLAG_BRIDGES` | `bridgeCount, bridgeType1, ...` |
| `FLAG_SERIALIZABLE` | No count added |
| `FLAG_MARKERS \| FLAG_BRIDGES` | Marker group **first**, bridge group **after** |
| All three flags | Marker group before bridge group; no serialization group |

The number of elements must be calculated **according to the flags**, not fixed for every call. Mistakenly wrapping an array of `MethodType` into a nested `Object[]` element also breaks the protocol. Because `Object...` supports varargs, when passing the args sequence directly in Java as in the example above, each element goes in the exact order.

## 3. FLAG_BRIDGES: multiple JVM signatures, one implementation logic

### 3.1. Why are bridges needed?

A generic interface after *type erasure* may have the method `apply(Object):Object`, while the concrete business logic works with `String`. In the JVM, method identity is distinguished by name and descriptor; the signatures:

```text
apply(Ljava/lang/Object;)Ljava/lang/Object;
apply(Ljava/lang/String;)Ljava/lang/String;
```

are **two different method descriptors**. The functional interface has an erased abstract method, but the linker may need the function object class to declare an additional version with a specialized signature. `FLAG_BRIDGES` allows requesting additional method versions that all invoke the implementation.

The Javadoc states this is a mechanism to support cases where multiple distinct JVM signatures are considered functionally the same at the language level, with parameter/return type adaptation. `altMetafactory` adds methods **with the same name `interfaceMethodName`**, and does not create arbitrary `foo`, `bar` methods with different names.

### 3.2. Distinguishing the three signatures

In the example:

```text
Mapper.apply:              (Object)Object       <-- interfaceMethodType
implementation.normalize:  (String)String       <-- direct impl MethodHandle
instantiated SAM:          (String)String       <-- dynamicMethodType
additional bridge:         (String)String       <-- altMethods[0]
factory:                   ()Mapper             <-- factoryType
```

`Mapper.apply(Object)` can still be called through a variable of type `Mapper`. The lambda generation mechanism uses the instantiated type to check/cast actual arguments, then calls `normalize(String)`. Enabling `FLAG_BRIDGES` causes the function class to also declare the `apply(String)String` version. No additional Java source method with that signature is needed.

When `mapper.apply(123)` goes through the erased SAM `apply(Object)` and the implementation requires `String`, the runtime may throw `ClassCastException` along the adaptation path. That is **not** a sign that "the bridge is broken": the type mismatch at invocation is already determined by the instantiated method type.

**Bridge conditions:** each additional `MethodType` must have a parameter count matching the SAM, and comply with the metafactory's type adaptation rules (not just any method type is accepted). You cannot request a new method taking two arguments if the SAM only has one; nor does it automatically duplicate implementations under new names.

### 3.3. Do not infer from `Method.isBridge()`

In regular Java source, the compiler generates a *synthetic bridge method* to satisfy erasure/overriding and Reflection has `Method.isBridge()`. However, the list of **additional bridge signatures** from `FLAG_BRIDGES` is a protocol request; **there is no contract that all additional methods must report `isBridge()==true`**. For instance, OpenJDK may generate those methods without attaching the JVM `ACC_BRIDGE` flag like a classic compiler-generated bridge.

When inspecting `FLAG_BRIDGES`, prioritize:

- Comparing the **name, parameters, and return type** of the methods that the function class actually declares.
- Verifying call behavior against the implementation.
- When detailed bytecode is needed, inspect appropriate metadata, but do not rely on lambda class names or the ability to dump hidden classes across every JDK.

## 4. FLAG_MARKERS: extending interfaces without adding other implementation methods

`FLAG_MARKERS` allows adding a list of interfaces that the function object implements. Typically these are **marker interfaces without their own abstract methods**, used to attach semantics or classify objects:

```java
public interface Tagged {}
public interface FastPath {}
```

These are illustrative declarations. If `factoryType` returns `Mapper` and `altInterfaces` contains `Tagged.class`, `FastPath.class`, the object can be used via a `Mapper` variable while both `mapper instanceof Tagged` and `mapper instanceof FastPath` are true.

**Caution:** an "empty" marker interface does not change the `Mapper.apply` logic; it only expands the object's set of interfaces. If an added interface has an abstract method **with a different name or signature** for which the metafactory does not generate an implementation, you may encounter interface contract issues, linkage errors, or `AbstractMethodError` when called. Do not use `FLAG_MARKERS` as a way to implement all methods of an arbitrary interface.

Additional interfaces must obey `altMetafactory` constraints: valid interface, type visibility, linkability, and compatible loader/module. `Class<?>` in the marker list is not a `Class.forName` string and must not be replaced by a text name.

### 4.1. Marker and primary interface are not the same

`factoryType.returnType()` determines the **primary interface** returned upon capture. If it returns `Mapper`, we still cast the result of `factory.getTarget().invokeExact()` to `Mapper`. `Tagged`/`FastPath` do not change `factoryType` into a tuple or another interface.

For plugin systems, markers can be used for routing/annotation-like capability detection via `instanceof`, but remember **markers do not themselves enforce security or access control checks**. The class generated by the factory is an implementation detail; do not design logic based on generated class names like `$$Lambda`.

## 5. FLAG_SERIALIZABLE: what does serialization actually require?

`FLAG_SERIALIZABLE` requires the function object to implement `java.io.Serializable` and have a `writeReplace` method returning a representation of type `java.lang.invoke.SerializedLambda`. This is a mechanism for serializing **metadata about the lambda factory and captured arguments**, not serializing the entire bytecode/class of the lambda into a long-lived format.

`SerializedLambda` contains these groups of facts:

| Property | Meaning |
| --- | --- |
| `capturingClass` | The class where the lambda was captured (according to `caller` and the corresponding site) |
| `functionalInterfaceClass` | Primary interface represented in slash-separated binary name form |
| `functionalInterfaceMethodName/Signature` | SAM name and descriptor |
| `implClass/implMethodName/implMethodSignature` | Linked implementation method |
| `implMethodKind` | Kind of direct `MethodHandle` pointing to the method/constructor |
| `instantiatedMethodType` | Instantiated type of the SAM |
| `capturedArgs[]` | Values captured when the function object was created |

Path during *serialization*:

```text
lambda object implements Serializable
          |
   ObjectOutputStream.writeObject
          |
   writeReplace()
          |
   SerializedLambda(metadata + capturedArgs)
          |
        bytes
```

Path during *deserialization*:

```text
ObjectInputStream.readObject
          |
   SerializedLambda.readResolve()
          |
   lookup in capturing class:
   private/static $deserializeLambda$(SerializedLambda)
          |
   validate valid metadata + reconstruct lambda
          |
       function object
```

According to the Javadoc, **the capturing class must provide a matching `$deserializeLambda$(SerializedLambda)`**. When `javac` generates bytecode for a serializable lambda expression, the compiler typically generates that helper along with identity checks for the lambda site, allowing the roundtrip to work. However, if you call `altMetafactory(..., FLAG_SERIALIZABLE)` **manually** and the capturing class lacks a suitable hook, Java may serialize to bytes but **deserialization will fail**.

### 5.1. "`instanceof Serializable`" is not enough

Three layers must be kept separate:

1. The function object is marked `Serializable`.
2. **Captured state** is actually serializable (all captured values must be handleable by Java serialization).
3. The capturing class has a proper **deserialization and SerializedLambda validation** mechanism.

Enabling a flag only solves the first layer and supports the structure of the second/third layers. If a captured object is not serializable, serialization may throw `NotSerializableException`. If the hook is missing, incompatible, or metadata has changed, deserialization may fail. If the package/module/class loader differs from when the bytes were created, class lookup and lambda verification may also run into issues.

**No long-term compatibility guarantee:** a serializable lambda is not a durable schema format for long-term storage or sending between two application versions. The compiler may change implementation method names, descriptors, capture layouts, and class identity when code is modified or rebuilt. Avoid using lambda bytes as a public data contract or message protocol.

### 5.2. Deserialization security

`SerializedLambda.readResolve` calls back into the capturing class. The `$deserializeLambda$` helper needs to **validate metadata** rather than accepting arbitrary method/class names from the stream to construct privileged MethodHandles. If you want a custom serializer, use versioned DTOs, an allowlist of permitted behaviors, and clear trust boundaries.

Do not deserialize objects from untrusted sources just because it is a "standard Java lambda". Java deserialization in general carries risks of processing unsafe object graphs/elements; consider object input filters or replacing it with a transparent data format when needed.

### 5.3. Serializable marker vs. FLAG_SERIALIZABLE

`java.io.Serializable` is itself a marker interface, but in the `altMetafactory` protocol **serialization has its own mechanism `FLAG_SERIALIZABLE`**. You should not just add `Serializable.class` to `altInterfaces` and assume the roundtrip is complete. If serializability is a requirement, you must check the flag, captured args, the capturing class's helper, and the versioning model.

## 6. Complete Java 17+ example: bridge + multiple marker interfaces

Create the file **`AltMetafactoryDemo.java`** with the following complete code:

```java
import java.lang.invoke.CallSite;
import java.lang.invoke.LambdaMetafactory;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;
import java.util.Arrays;
import java.util.Locale;

public class AltMetafactoryDemo {
    @FunctionalInterface
    public interface Mapper {
        Object apply(Object value);
    }

    public interface Tagged {}
    public interface FastPath {}

    public static String normalize(String value) {
        return value.trim().toUpperCase(Locale.ROOT);
    }

    public static void main(String[] args) throws Throwable {
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        MethodHandle implementation = lookup.findStatic(
                AltMetafactoryDemo.class, "normalize",
                MethodType.methodType(String.class, String.class));

        MethodType sam = MethodType.methodType(Object.class, Object.class);
        MethodType instantiated = MethodType.methodType(String.class, String.class);
        MethodType bridge = MethodType.methodType(String.class, String.class);

        int flags = LambdaMetafactory.FLAG_MARKERS
                  | LambdaMetafactory.FLAG_BRIDGES;

        CallSite factory = LambdaMetafactory.altMetafactory(
                lookup, "apply", MethodType.methodType(Mapper.class),
                sam, implementation, instantiated, flags,
                2, Tagged.class, FastPath.class,
                1, bridge);

        Mapper mapper = (Mapper) factory.getTarget().invokeExact();
        System.out.println("factory=" + factory.type());
        System.out.println("mapper=" + mapper.apply("  java  "));
        System.out.println("tagged=" + (mapper instanceof Tagged));
        System.out.println("fast=" + (mapper instanceof FastPath));
        System.out.println("serializable="
                + (mapper instanceof java.io.Serializable));

        System.out.println("methods=" +
                Arrays.stream(mapper.getClass().getDeclaredMethods())
                    .filter(m -> m.getName().equals("apply"))
                    .map(m -> m.getName() + "("
                            + m.getParameterTypes()[0].getSimpleName()
                            + ")->" + m.getReturnType().getSimpleName())
                    .sorted()
                    .toList());

        try {
            mapper.apply(123);
        } catch (ClassCastException error) {
            System.out.println("badInput="
                    + error.getClass().getSimpleName());
        }
    }
}
```

Compile/run with JDK 17+:

```bash
javac --release 17 AltMetafactoryDemo.java
java AltMetafactoryDemo
```

`stdout` on OpenJDK 17+ (the lines in the program intentionally avoid printing lambda class names that may vary):

```text
factory=()Mapper
mapper=JAVA
tagged=true
fast=true
serializable=false
methods=[apply(Object)->Object, apply(String)->String]
badInput=ClassCastException
```

### 6.1. Line-by-line analysis

- `factory=()Mapper` shows that the linkage result is a factory **requiring no captured arguments**; upon capture, the target returns `Mapper`.
- `mapper=JAVA` proves that a call through the erased abstract method `apply(Object)` is adapted to the implementation `normalize(String)`, then returns `String` as `Object`.
- `tagged=true` and `fast=true` confirm that both marker interfaces are structurally implemented. They provide no additional business methods.
- `serializable=false` because the example does not enable `FLAG_SERIALIZABLE`, and neither `Mapper` nor the markers `Tagged/FastPath` extend `Serializable`.
- `methods=[apply(Object)->Object, apply(String)->String]` proves the resulting class has **two signatures with the same name `apply`**, corresponding to the erased SAM and the extra method type from `FLAG_BRIDGES`.
- `badInput=ClassCastException` because the instantiated type is narrowed to `String`. `mapper.apply(123)` goes through the erased SAM but cannot convert `Integer` to `String`.

In the example, `implementation` created via `lookup.findStatic` is a **direct MethodHandle**. It is not transformed by `bindTo`, `asType`, or other combinators into a non-direct handle before being passed to the metafactory. The direct method handle rule is a condition of `LambdaMetafactory`; you cannot arbitrarily replace `implementation` with a composite method handle and expect every JVM to accept it.

**Do not use `mapper.getClass().getName()` as fixed output.** The JDK may use hidden lambda classes whose names are not part of a stable API. Internal naming and metadata results should not be a public contract.

## 7. Complete Java 17+ example: intersection-type lambda with serialization

When writing Java source code instead of calling `altMetafactory` manually, the compiler can prepare the exact bootstrap arguments, additional interfaces, `writeReplace`, and deserialize helper. An *intersection cast* simultaneously requires `Function` and adds `Tagged` and `Serializable`:

Create the file **`SerializableLambdaDemo.java`**:

```java
import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.lang.invoke.SerializedLambda;
import java.util.function.Function;

public class SerializableLambdaDemo {
    interface Tagged {}

    static Function<String, String> create(String prefix) {
        return (Function<String, String> & Tagged & Serializable)
                (value -> prefix + value.trim());
    }

    public static void main(String[] args) throws Exception {
        Function<String, String> original = create("id=");
        System.out.println("original=" + original.apply("  A7  "));
        System.out.println("serializable="
                + (original instanceof Serializable));
        System.out.println("tagged=" + (original instanceof Tagged));

        System.out.println("hook="
                + (SerializableLambdaDemo.class.getDeclaredMethod(
                        "$deserializeLambda$", SerializedLambda.class) != null));

        ByteArrayOutputStream buffer = new ByteArrayOutputStream();
        try (ObjectOutputStream output = new ObjectOutputStream(buffer)) {
            output.writeObject(original);
        }

        Object restored;
        try (ObjectInputStream input = new ObjectInputStream(
                new ByteArrayInputStream(buffer.toByteArray()))) {
            restored = input.readObject();
        }

        @SuppressWarnings("unchecked")
        Function<String, String> copy = (Function<String, String>) restored;
        System.out.println("restored=" + copy.apply("  B8 "));
        System.out.println("restoredTagged=" + (restored instanceof Tagged));
    }
}
```

```bash
javac --release 17 SerializableLambdaDemo.java
java SerializableLambdaDemo
```

`stdout`:

```text
original=id=A7
serializable=true
tagged=true
hook=true
restored=id=B8
restoredTagged=true
```

**What is being verified?**

1. The lambda captures the value `prefix="id="`, which is a serializable `String`. The result after deserialization still uses the same prefix.
2. The function object implements both `Serializable` and `Tagged`, even though the Java variable type is `Function<String,String>`.
3. The compiler generates the `$deserializeLambda$(SerializedLambda)` helper on the capturing class; Reflection in the example **only checks for its existence**, without calling the helper with arbitrary input.
4. `ObjectOutputStream` writes the lambda representation; `ObjectInputStream` invokes the resolve logic and reconstructs the function object, which may be a different instance. Comparing `apply` behavior is what matters.
5. This case can roundtrip because the program does not change code/compiler metadata between serialization and deserialization and the captured argument is serializable. **Do not infer that every serializable lambda can be stored long-term across application upgrades**.

### 7.1. Inspecting the real `altMetafactory` in the class file

Run:

```bash
javap -v -p SerializableLambdaDemo
```

Look in the output for:

- The bootstrap method handle pointing to `java/lang/invoke/LambdaMetafactory.altMetafactory`.
- The `invokedynamic` instruction used for the lambda in the `create` method.
- `BootstrapMethods` with static arguments including method types, implementation handle, and flags/marker data.
- The method `private static java.lang.Object $deserializeLambda$(java.lang.invoke.SerializedLambda)` (the displayed signature may include additional details).

`javap` only inspects the class file and bootstrap metadata; it **does not count how many times the JVM has executed the bootstrap** and does not prove serialization compatibility across different builds.

There may be other `invokedynamic` instructions for string concatenation via `StringConcatFactory`. Do not confuse them with the bootstrap for lambdas.

## 8. Control example: manually enabling FLAG_SERIALIZABLE can still fail deserialization

Here we **call `altMetafactory` manually** (with no serializable lambda expression in the capturing class's source), then serialize the function object. Enabling the flag makes the object implement `Serializable` and `writeReplace` can write out `SerializedLambda`; however, the capturing class **does not automatically receive the `$deserializeLambda$` helper**.

Create the file **`ManualSerializablePitfall.java`**:

```java
import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.lang.invoke.CallSite;
import java.lang.invoke.LambdaMetafactory;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;
import java.util.Arrays;

public class ManualSerializablePitfall {
    interface Mapper { String map(String value); }

    public static String normalize(String value) {
        return value.trim();
    }

    public static void main(String[] args) throws Throwable {
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        MethodType signature =
                MethodType.methodType(String.class, String.class);
        MethodHandle direct = lookup.findStatic(
                ManualSerializablePitfall.class, "normalize", signature);

        CallSite factory = LambdaMetafactory.altMetafactory(
                lookup, "map", MethodType.methodType(Mapper.class),
                signature, direct, signature,
                LambdaMetafactory.FLAG_SERIALIZABLE);

        Mapper mapper = (Mapper) factory.getTarget().invokeExact();
        System.out.println("serializable=" + (mapper instanceof Serializable));
        System.out.println("call=" + mapper.map("  hi  "));

        boolean hasHook =
                Arrays.stream(ManualSerializablePitfall.class.getDeclaredMethods())
                    .anyMatch(m -> m.getName().equals("$deserializeLambda$"));
        System.out.println("hasHook=" + hasHook);

        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
            out.writeObject(mapper);
        }
        System.out.println("wroteBytes=" + (bytes.size() > 0));

        boolean restored = false;
        try (ObjectInputStream in = new ObjectInputStream(
                new ByteArrayInputStream(bytes.toByteArray()))) {
            in.readObject();
            restored = true;
        } catch (Exception expected) {
            // Only testing expected failure: missing deserialization hook.
        }
        System.out.println("roundtripSucceeded=" + restored);
    }
}
```

```bash
javac --release 17 ManualSerializablePitfall.java
java ManualSerializablePitfall
```

`stdout` in the test environment:

```text
serializable=true
call=hi
hasHook=false
wroteBytes=true
roundtripSucceeded=false
```

**Key takeaway:** the serialization file/stream can be written successfully yet the roundtrip fails, because `SerializedLambda.readResolve` cannot find a suitable deserialization hook in the capturing class. The example intentionally catches `Exception` and prints a boolean **only to demonstrate the expected failure**; production code should not swallow serialization exceptions. If logging is needed, log the exception class and cause with context, and do not trust data from an arbitrary stream.

If building a runtime framework that truly needs serializable callbacks, a safer common approach is **not to rely on serializing Java lambdas directly**: store the handler identifier, schema version, and allowed capture DTO data; on load, select the handler from a trusted registry and reconstruct the callback at the application level.

## 9. Linkage invariants: why does altMetafactory sometimes reject?

The `LambdaMetafactory` Javadoc describes conditions on the four type lists:

- `factoryType` has **K** capture parameters `(D1,...,Dk)` and interface return type `Rd`.
- `interfaceMethodType` has **N** functional parameters `(U1,...,Un)` and return `Ru`.
- `implementation.type()` has **M** actual parameters `(A1,...,Am)` and return `Ra`. For an instance method, the handle includes the receiver in the parameter list.
- `dynamicMethodType` has **N** instantiated parameters `(T1,...,Tn)` and return `Rt`.

Important invariants:

```text
K + N = M

factoryType.parameterType(i) == implementation.type().parameterType(i)
    for i in captured inputs (exact type comparison)

dynamicMethodType.parameterCount() == interfaceMethodType.parameterCount()

instantiated reference arguments must not be wider in a way that breaks
the contract of the erased SAM; adaptation also follows JVM/Javadoc rules.
```

Regarding interface call inputs, when `Ti` and `Ui` differ they must be reference types and `Ti` must be a subtype of `Ui`. The return type has a similar rule: the instantiated return must be compatible with the SAM's return (or identical). The instantiated SAM parameters must be adaptable to the implementation; primitive widening and boxing/unboxing are evaluated under specific metafactory rules and are **not** equivalent to arbitrary `MethodHandle.asType` conversions.

Valid example from section 6:

```text
K = 0                       // factory ()Mapper
N = 1                       // Mapper.apply(Object)
M = 1                       // normalize(String)
K + N = M = 1

SAM (Object)Object
instantiated (String)String  // String subtype Object
impl (String)String          // direct static method
```

If the implementation method needs two parameters while the factory captures nothing and the SAM has only one, `K+N != M`, so linkage is invalid. If `factoryType` returns a regular class that is not a functional interface, that is also an invalid configuration. If the direct `MethodHandle` was turned into a non-direct adapter before being passed in, the metafactory may reject it.

### 9.1. Is a captured receiver counted in K?

Yes. For an instance implementation `StringBuilder.append(String)`, the handle after `findVirtual` carries the receiver first, e.g., type `(StringBuilder,String)StringBuilder`. If the factory captures the `StringBuilder` receiver and the SAM has one `String` parameter, then `K=1`, `N=1`, `M=2`. The factory type must describe the receiver as an input of the capture phase; in the function object, the method invocation only has the SAM parameter left.

**Do not confuse receiver capture with a bridge or marker.** Those are independent of the number of captured arguments.

### 9.2. How do erased type, instantiated type, and bridge type differ?

| Item | When/where used | Example |
| --- | --- | --- |
| SAM erased `interfaceMethodType` | Method descriptor of the functional interface | `(Object)Object` |
| Instantiated `dynamicMethodType` | Checking/casting at invocation by specialization | `(String)String` |
| Direct implementation `MethodHandle` | Actual code being delegated to | `normalize(String):String` |
| Extra bridge `MethodType` | Additional same-named entry method for the function object | `(String)String` |
| Factory `MethodType` | When capturing to create the function object | `()Mapper` or `(Prefix)Mapper` |

Someone might use the word "bridge" to refer to the erased→instantiated adaptation or the **additional method** created by `FLAG_BRIDGES`; to avoid ambiguity, state clearly when referring to an *additional method signature*.

## 10. Choosing markers, bridges, and serialization based on real needs

**Only need a normal functional method**: `metafactory` is usually sufficient; do not add flags "for looks" or out of thinking `altMetafactory` is always faster.

**Need one or more additional same-named method versions with different descriptors**: use `FLAG_BRIDGES`, ensure all signatures adapt to the SAM and implementation, and avoid the notion of "adding arbitrary API methods".

**Need marker interfaces**: use `FLAG_MARKERS` with a valid interface list. If you actually need additional methods with different logic, design an appropriate class/interface/adapter instead of attaching interfaces with abstract methods to the marker list.

**Need Java serialization**: `FLAG_SERIALIZABLE` is what requests a serializable lambda object, but there must be a capturing-class deserializer and serializable captured values, plus clear versioning, class loading, and security policies. For long-lived stored data or network exchange, prefer a custom schema instead of serializing lambdas.

**Need all three**: bitwise OR the flags, pass the marker count/group and then the bridge count/group in the exact order. Before creating the CallSite, validate all types and the direct implementation. If code uses the serializable flag but the caller class lacks the corresponding hook, do not advertise "safe roundtrip" just because `instanceof Serializable` is true.

## 11. Access rules, class loaders, and safety when using the runtime linker

### 11.1. Lookup and implementation handle

`caller` must be a `Lookup` with full privilege access per the Javadoc. The JVM supplies an appropriate lookup when executing `invokedynamic`; when testing manually in `main`, `MethodHandles.lookup()` from the calling class can satisfy this. `publicLookup()` usually **cannot be substituted directly** in these cases.

`implementation` must be a **direct method handle**, such as one obtained via `Lookup.findStatic`, `Lookup.findVirtual`, `Lookup.findConstructor`, or unreflecting a direct member per the rules. A handle that has gone through `insertArguments`, `asType`, or `filterArguments` is typically no longer a direct handle, even though it is still callable. `LambdaMetafactory` does not promise to accept every callable handle.

### 11.2. Marker interfaces in module/plugin environments

Markers must be valid interfaces visible/applicable in the context of the generated lambda class. When there are multiple class loaders, two interfaces with the **same binary name** created by different loaders **are not the same `Class<?>`**. Do not use class name text as identity. Plugin loaders can cause `ClassCastException` or linkage errors when caller/implementation/marker belong to incompatible access realms.

Caching a `CallSite` or function object in a long-lived static map can also retain the plugin's class loader, `MethodHandle`, and captured objects. This is a **lifetime issue**, not automatically solved by markers or bridges.

### 11.3. Prefer Java source solutions when possible

If you just want an object implementing `Function<String,String>` plus a marker/`Serializable`, an intersection cast in Java source is easier to understand and lets the compiler prepare the helper more reliably than manually assembling an `Object...` payload:

```java
Function<String, String> action =
        (Function<String, String> & Tagged & java.io.Serializable)
        (text -> text.trim());
```

This illustrative snippet assumes `Tagged` is valid and `Function` is imported. It cannot execute on its own without those declarations; use `SerializableLambdaDemo` to run a complete file.

## 12. Common errors and how to diagnose them

| Symptom | Possible cause | Verification method |
| --- | --- | --- |
| `LambdaConversionException` when creating CallSite | Wrong `factoryType`, invalid SAM/instantiated/impl type, non-direct handle, Lookup lacks privileges, or linkage invariant violated | Print `factoryType`, `samType`, `impl.type()`, `instantiatedType`, and lookup context |
| `ClassCastException` when calling via SAM | Erased SAM accepts `Object`, instantiated type requires `String`, and value cannot be converted | Check the actual value type and `dynamicMethodType` |
| `WrongMethodTypeException` when calling factory target | `invokeExact` at the call site has a different result/argument type than `factoryType` | Compare `factory.getTarget().type()` with the static type of the call |
| Marker `instanceof` is wrong | Missing `FLAG_MARKERS` or wrong marker list, or received object from another factory | Check flags/count/interfaces; test class identity by loader |
| Extra method does not appear | Missing `FLAG_BRIDGES`/`altMethodCount`, wrong order of `Object...` args | Inspect declared methods list and descriptors |
| `Method.isBridge()==false` | Additional method does not necessarily carry bytecode flag `ACC_BRIDGE` | Check signature and method behavior instead of requiring `isBridge` |
| `Serializable==true` but cannot be read back | Missing `$deserializeLambda$` or hook rejects metadata | Inspect capturing class and root exception during deserialization |
| `NotSerializableException` in `writeObject` | A captured argument or related object is not serializable | Inspect captured values; design an immutable/serializable DTO |
| Deserialization fails after version upgrade | Change in implementation method, captured state, class name/descriptor/loader | Do not use serialized lambdas as a durable schema |
| Lambda class name changes | JVM uses generated/hidden classes, unstable naming | Do not store lambda class names as business identifiers |
| Mismatch `K+N!=M` | Number of captured parameters and SAM arguments does not match implementation | Explicitly write out `factoryType`, `samType`, `implementation.type()` |
| Adding an interface with different methods to markers | Markers are not a place to implement arbitrary extra API methods | Use a marker interface or a real adapter class |
| `javap` shows multiple `invokedynamic` | String concatenation and lambdas have different bootstraps | Read `BootstrapMethods` per instruction |
| Serialization behavior differs from security intent | Java deserialization can trigger reconstruction based on metadata | Only accept trusted data; use versioned schema/allowlist |

**Suggested debugging order:**

1. Log input metadata in a controlled manner: `name`, `factoryType`, `samType`, `impl.type()`, `instantiatedType`, `flags`, `markerCount`, `bridgeCount`.
2. Verify the order of `Object... args` elements. Do not confuse `MethodType` with `Class` objects or counts with flags.
3. Verify the implementation is **direct** and the caller has privileges.
4. Create the `CallSite`; if rejected, handle `LambdaConversionException` at linkage rather than masking it with a cast at capture.
5. Check `site.type()` then call `site.getTarget().invokeExact(...)` with the **exact** types.
6. Check `instanceof` markers, declared methods, and invocation behavior.
7. For serialization, test both **write** and **read**, without stopping at `instanceof Serializable` or a non-empty byte array; also test failure/rebuild/version change.
8. If analyzing compiler output, use `javap -v -p` to match each `invokedynamic` instruction to its exact bootstrap entry.

## 13. Practice exercises

**Exercise 1 — arguments protocol.** You want to add a marker interface `Audited` and a bridge type `(String)String`. What flags are needed and what is the order of args after the mandatory trio?

**Answer:** `FLAG_MARKERS | FLAG_BRIDGES`. After `samType,impl,dynamicType` come `flags, 1, Audited.class, 1, MethodType.methodType(String.class,String.class)`. The marker group always precedes the bridge group.

**Exercise 2 — factory and SAM.** A lambda captures nothing and implements `Consumer.accept(String)`. How many arguments does `factoryType` take? How many does the SAM take?

**Answer:** The factory captures nothing so it has `0` parameters and returns the `Consumer` interface; the SAM `accept` has `1` parameter, usually with erased descriptor `(Object)void`. `factoryType` and `interfaceMethodType` are not the same thing.

**Exercise 3 — bridge and erased method.** With `Mapper.apply(Object):Object` and implementation `normalize(String):String`, why is there an additional `apply(String):String` when using `FLAG_BRIDGES`?

**Answer:** That is the requested additional method signature; the function object has two entry methods with the same name, both delegating to the implementation after adaptation. The erased SAM still exists to satisfy the interface.

**Exercise 4 — marker.** Why can `instanceof Tagged` be true even though `Mapper` does not declare `extends Tagged`?

**Answer:** Because the function object class generated by `altMetafactory` directly implements the interfaces listed when `FLAG_MARKERS` is enabled.

**Exercise 5 — serialization.** `FLAG_SERIALIZABLE` is enabled and `writeObject` finishes running. Does that prove `readObject` is guaranteed to succeed?

**Answer:** No. Valid captured values, the `$deserializeLambda$(SerializedLambda)` helper on the capturing class, identity checks, and a compatible class loader/version environment are required. Manual `altMetafactory` does not automatically add the helper to the source class.

**Exercise 6 — invariant.** `factoryType` has K=2 captured arguments, SAM N=1, but the implementation handle only has M=2 parameters. Can it link?

**Answer:** No, because `K + N = 3 != M = 2`. You must choose the right direct implementation or redesign the capture/functional method arity.

**Exercise 7 — method bridge flag.** If Reflection sees two declared methods `apply(Object)Object` and `apply(String)String` but `isBridge()` on the added method is `false`, can we conclude `FLAG_BRIDGES` was ignored?

**Answer:** No. `FLAG_BRIDGES` specifies extra method signatures; it does not require every implementation to set the `ACC_BRIDGE` flag recognized by `Method.isBridge`. Check the signatures and behavior.

**Exercise 8 — captured state.** A serializable lambda captures `new Object()` into a closure. Even though the lambda implements `Serializable`, why can serialization fail?

**Answer:** `Object` does not implement `Serializable`, so when the stream writes the captured argument it may throw `NotSerializableException`. A serializable DTO is needed, or do not serialize this closure.

**Exercise 9 — architecture.** A system wants to persist the callback "normalize, upper, trim" long-term in a database. Should it store the lambda's bytes or store an identifier + capture data?

**Answer:** Prefer a handler identifier/version, an approved capture data schema, and a factory to reconstruct the callback. Serialized lambdas depend on compiler metadata, implementation methods, capturing classes, and class loaders, so they are not a stable long-term schema.

- Oracle JDK 17 — [`MethodHandle`](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/invoke/MethodHandle.html): typed handles, direct handles, and `invokeExact` at the call site.
- Oracle JDK 17 — [`MethodHandles.Lookup`](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/invoke/MethodHandles.Lookup.html): `findStatic`, `findVirtual`, caller privileges, and access rights.
- Oracle JDK 17 — [`MethodType`](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/invoke/MethodType.html): factory type, SAM erased/instantiated type, and signature checks.
- Oracle JDK 17 — [`ObjectInputStream`](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/io/ObjectInputStream.html): requirements and risks when deserializing Java objects.
- Oracle JDK 17 — [`javap`](https://docs.oracle.com/en/java/javase/17/docs/specs/man/javap.html): inspecting `invokedynamic`, constant pool, and `BootstrapMethods`.

**Remember:** `altMetafactory` does not "guess" extended interfaces/methods. You must supply the exact **SAM erased type**, **direct implementation handle**, **instantiated type**, **flags**, and count/argument groups in the exact order. `FLAG_BRIDGES` adds same-named method signatures; `FLAG_MARKERS` adds marker interfaces; `FLAG_SERIALIZABLE` activates the serialization protocol but **does not waive the requirement for `$deserializeLambda$` and serializable captured state**. Verify linkage, capture, invocation, and deserialization before trusting a function object to have all required capabilities.
