# 10.7 Unwrapping InvocationTargetException and Handling UndeclaredThrowableException

In Java Dynamic Proxy, an error from a business method can be **wrapped in two layers** if the `InvocationHandler` uses Reflection to invoke the real object (*target*). The two important exception classes are:

- **`java.lang.reflect.InvocationTargetException`**: the wrapper class generated by `Method.invoke(...)` when the **target method body** throws an exception.
- **`java.lang.reflect.UndeclaredThrowableException`**: the wrapper class that the **dynamic proxy** can generate when `InvocationHandler.invoke(...)` throws a **checked exception** that the proxied interface method **is not allowed to declare** in `throws`.

These two classes address two different boundaries: **Reflection → target** and **InvocationHandler → proxy caller**. Removing `InvocationTargetException` is a necessary step when you want to propagate the root cause outward, but **unwrapping alone does not guarantee avoiding `UndeclaredThrowableException`**: the original exception must still conform to the `throws` contract of the method in the interface.

Lesson objectives: accurately understand both wrapping mechanisms, write an `InvocationHandler` that preserves exception semantics, identify the cause chain in a stack trace, and establish a clear policy when a checked exception is not in the API signature. Examples use **Java 17+**.

## 1. Context: a call passes through two layers

JDK Dynamic Proxy is based on interfaces and `InvocationHandler`:

~~~text
Caller
  |
  | proxy.load("42")
  v
JDK Proxy: method load(...)
  |
  | InvocationHandler.invoke(proxy, method, args)
  v
Handler
  |
  | Method.invoke(target, args)
  v
Target.load(...) ------------------> throws FileNotFoundException
  |
  | Reflection wraps target's exception
  v
InvocationTargetException
  |
  | handler unwraps via getCause()
  v
FileNotFoundException
  |
  | Proxy checks if exception thrown by handler is valid
  v
Caller receives FileNotFoundException if interface declares IOException
~~~

If the handler **does not unwrap** `InvocationTargetException`, the proxy may see the checked exception class `InvocationTargetException` itself — not the `FileNotFoundException` inside. For an interface that only declares `throws IOException`, `InvocationTargetException` is not a subtype of `IOException`, so the proxy will wrap it further:

~~~text
UndeclaredThrowableException
  -> InvocationTargetException
       -> FileNotFoundException
~~~

Even when the handler has properly unwrapped `InvocationTargetException`, if the interface **does not have** `throws IOException`, an `IOException` is still an undeclared checked exception and the proxy may create:

~~~text
UndeclaredThrowableException
  -> IOException
~~~

The difference between these two cause trees is central when debugging dynamic proxies.

## 2. InvocationTargetException: the mechanism of Method.invoke

`java.lang.reflect.Method.invoke(Object receiver, Object... args)` invokes a method via Reflection. If **code inside the target method** throws a `Throwable`, the reflective call throws an `InvocationTargetException` containing that exception.

Conceptual code example:

~~~java
public static class Reader {
    public String read(String id) throws java.io.IOException {
        throw new java.io.IOException("not found: " + id);
    }
}
~~~

Reflective call:

~~~java
Method method = Reader.class.getMethod("read", String.class);
try {
    method.invoke(new Reader(), "A1");
} catch (InvocationTargetException wrapper) {
    Throwable original = wrapper.getCause();
    // original is IOException with message "not found: A1".
}
~~~

The two snippets above are **illustrative**, not a standalone runnable program: an enclosing class/method and imports from `java.lang.reflect` are needed. `Method.invoke` does not change the nature of the business error, it only wraps it to distinguish “the invoked method threw an error” from “the Reflection operation itself could not be executed”.

APIs to read the cause:

- `wrapper.getCause()`: returns the target exception, following `Throwable.getCause()`.
- `wrapper.getTargetException()`: specialized API of `InvocationTargetException`, which for this purpose also returns the target exception.
- `wrapper.getClass().getSimpleName()`: returns the name of the **wrapper class**, not the real business error.

**Important distinction:** not every exception when calling `Method.invoke` is wrapped into `InvocationTargetException`. For example, `IllegalAccessException` when the caller lacks permission is an error of the **Reflection layer**, while `IllegalArgumentException` can occur when passing a wrong receiver/arguments. Lookup error `NoSuchMethodException` originates from `getMethod`/`getDeclaredMethod`, not from the target method body.

Even when the target throws a `RuntimeException` or `Error`, `Method.invoke` still uses `InvocationTargetException` to wrap the **target's** exception. Therefore a reflective handler should not only unwrap checked exceptions and handle unchecked exceptions differently; unwrap the target exception properly before applying API policy.

## 3. Why unwrap right inside InvocationHandler?

The method of `InvocationHandler` has the signature:

~~~java
Object invoke(Object proxy, Method method, Object[] args) throws Throwable;
~~~

It is called by the JDK Proxy whenever a caller invokes a proxied method. The `method` parameter represents the interface method (or some `Object` methods); `args` is the array of arguments, which can be `null` for methods with no parameters.

A forwarding handler using Reflection typically looks like:

~~~java
InvocationHandler handler = (proxy, method, args) -> {
    Method targetMethod = target.getClass().getMethod(
            method.getName(), method.getParameterTypes());
    try {
        return targetMethod.invoke(target, args);
    } catch (InvocationTargetException wrapper) {
        throw wrapper.getCause();
    }
};
~~~

This is an **illustrative snippet**, requiring a valid `target` variable, `java.lang.reflect.*` imports, and a proxy creation context. `target.getClass().getMethod(...)` looks up a public method matching the name and erased parameter types from the interface. The target's method **is not required** to be the same `Method` passed from the interface; method selection and signature compatibility are the handler's responsibility.

`catch (InvocationTargetException wrapper) { throw wrapper.getCause(); }` has three meanings:

1. Avoids exposing the Reflection wrapper class as a checked exception from the handler, if the root cause is not of that type.
2. Preserves the **concrete type**, **message**, **cause chain**, and **stack trace** of the business exception.
3. Brings the original exception back to the JDK Proxy boundary so the proxy can properly enforce the interface's checked exception contract.

**Do not use `throw wrapper` to “preserve the original error”.** That is the Reflection wrapper error, not the business `Throwable` object. Also avoid `throw new RuntimeException(wrapper)` if the contract expects the caller to catch `IOException` or another checked exception directly: this changes the API and leaves an unnecessary wrapping layer.

However, unwrapping **does not automatically grant permission** for a checked exception to escape from every interface method; that is decided by the `throws` rule in the next step.

## 4. UndeclaredThrowableException: checked exceptions rules of JDK Proxy

When `InvocationHandler.invoke` completes abruptly with an exception, the dynamic proxy method handles it according to the exception type:

| Exception thrown by handler | Does the interface declare and allow it? | Proxy caller receives |
| --- | --- | --- |
| `RuntimeException` (unchecked) | No need to declare `throws` | The `RuntimeException` itself |
| `Error` (unchecked) | No need to declare `throws` | The `Error` itself |
| `FileNotFoundException` | `throws IOException` or a suitable supertype | The `FileNotFoundException` itself |
| `IOException` | Method does not declare checked exception | `UndeclaredThrowableException` with `IOException` as cause |
| `InvocationTargetException` | Only `throws IOException` | Typically `UndeclaredThrowableException`, because the wrapper is not `IOException` |
| Other checked exception | Only when compatible with `throws` of the proxied method | Passed through directly if valid, otherwise wrapped in `UndeclaredThrowableException` |

**`UndeclaredThrowableException` is a `RuntimeException`**, so the caller is not required to declare or catch it at compile time. It does not mean the JVM “secretly converts all exceptions into RuntimeException”; this is behavior to protect the checked exceptions contract of the **proxy method**.

`UndeclaredThrowableException` has two ways to retrieve the undeclared exception:

- `e.getUndeclaredThrowable()`: directly accesses the wrapped checked exception.
- `e.getCause()`: the same standard cause chain of `Throwable`.

Example:

~~~java
catch (UndeclaredThrowableException e) {
    Throwable rootAtProxyBoundary = e.getUndeclaredThrowable();
    System.out.println(rootAtProxyBoundary.getClass().getName());
}
~~~

This is an **illustrative catch branch**, not a standalone program. If the handler has not unwrapped `InvocationTargetException`, the `rootAtProxyBoundary` variable here may still be **`InvocationTargetException`**, requiring one more step to find the target error. If the handler unwrapped properly but the checked exception is not in `throws`, it may be `IOException` itself.

### The “validity” rule depends on the interface, not the target

Suppose the interface specifies:

~~~java
interface Api {
    String load(String id) throws java.io.IOException;
    void audit();
}
~~~

The handler invokes the target reflectively:

- `load` throws `FileNotFoundException`: `FileNotFoundException extends IOException`, so after the handler unwraps `InvocationTargetException`, the proxy allows it to pass straight through.
- `audit` throws `IOException`: `audit()` declares no checked exception, so the proxy wraps `IOException` into `UndeclaredThrowableException` if the handler lets it escape directly.

Even if the target's implementation declares `throws IOException` for `audit()`, that **does not change** the `Api.audit()` signature that the caller sees.

## 5. Complete Java 17+ example: three outcomes in the same proxy

Create the file **ProxyExceptionsDemo.java**:

~~~java
import java.io.FileNotFoundException;
import java.io.IOException;
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.lang.reflect.UndeclaredThrowableException;

public class ProxyExceptionsDemo {
    public interface Service {
        String load(String id) throws IOException;
        void audit();
        String status();
    }

    public static class Target {
        public String load(String id) throws IOException {
            throw new FileNotFoundException("not found: " + id);
        }

        public void audit() throws IOException {
            throw new IOException("audit offline");
        }

        public String status() {
            return "up";
        }
    }

    static Service create(InvocationHandler handler) {
        return (Service) Proxy.newProxyInstance(
                ProxyExceptionsDemo.class.getClassLoader(),
                new Class<?>[] { Service.class },
                handler);
    }

    public static void main(String[] args) {
        Target target = new Target();

        // Correct way: unwrap target exception from Method.invoke.
        InvocationHandler correct = (proxy, method, actualArgs) -> {
            Method implementation = Target.class.getMethod(
                    method.getName(), method.getParameterTypes());
            try {
                return implementation.invoke(target, actualArgs);
            } catch (InvocationTargetException wrapper) {
                throw wrapper.getCause();
            }
        };

        Service safe = create(correct);
        System.out.println("status: " + safe.status());

        try {
            safe.load("a");
        } catch (IOException ex) {
            System.out.println("declared: " +
                    ex.getClass().getSimpleName() + " | " + ex.getMessage());
        }

        try {
            safe.audit();
        } catch (UndeclaredThrowableException ex) {
            Throwable cause = ex.getUndeclaredThrowable();
            System.out.println("undeclared wrapper: " +
                    ex.getClass().getSimpleName());
            System.out.println("undeclared cause: " +
                    cause.getClass().getSimpleName());
        }

        // Intentional wrong way: expose InvocationTargetException.
        InvocationHandler raw = (proxy, method, actualArgs) -> {
            Method implementation = Target.class.getMethod(
                    method.getName(), method.getParameterTypes());
            return implementation.invoke(target, actualArgs);
        };

        Service wrong = create(raw);
        try {
            wrong.load("b");
        } catch (UndeclaredThrowableException ex) {
            Throwable inner = ex.getUndeclaredThrowable();
            System.out.println("bad inner: " +
                    inner.getClass().getSimpleName());
            System.out.println("bad root: " +
                    ((InvocationTargetException) inner)
                            .getCause().getClass().getSimpleName());
        }
    }
}
~~~

Compile and run with JDK 17+:

~~~bash
javac ProxyExceptionsDemo.java
java ProxyExceptionsDemo
~~~

Expected stdout:

~~~text
status: up
declared: FileNotFoundException | not found: a
undeclared wrapper: UndeclaredThrowableException
undeclared cause: IOException
bad inner: InvocationTargetException
bad root: FileNotFoundException
~~~

### Why does each line appear?

**`status`:** target returns a normal string; `Method.invoke` returns the result, the handler returns it, and the proxy converts it to `String` per the interface signature.

**`load("a")` with the correct handler:** target throws `FileNotFoundException`, Reflection wraps it in `InvocationTargetException`, the handler rethrows `getCause()`. The interface `Service.load` declares `throws IOException` so the proxy passes `FileNotFoundException` through intact; the `IOException` catch in the caller catches it. The error does not become `UndeclaredThrowableException`.

**`audit()` with the correct handler:** target throws `IOException`, the handler properly unwrapped it to `IOException`, but `Service.audit()` **does not** have `throws IOException`. The proxy must preserve the interface contract so it wraps it in `UndeclaredThrowableException`; `getUndeclaredThrowable()` returns `IOException`.

**`load("b")` with the wrong handler:** the handler just returns the result of `Method.invoke`, without catching `InvocationTargetException`. The proxy receives `InvocationTargetException` as a checked exception escaping from the handler. `Service.load` only declares `IOException` and does not allow `InvocationTargetException`, so the proxy wraps it in `UndeclaredThrowableException`. Thus the direct cause of `UTE` is `InvocationTargetException`, while `FileNotFoundException` is one layer deeper.

The program intentionally does not call `equals`, `hashCode`, or `toString` on the proxy. These `Object` calls can also be forwarded by `InvocationHandler` and require their own policy if building a reusable handler in a framework.

## 6. Unwrapping one layer properly and walking the cause chain

Once `InvocationTargetException` is caught, normal handling code is:

~~~java
try {
    return method.invoke(target, args);
} catch (InvocationTargetException e) {
    throw e.getCause();
}
~~~

This snippet is **illustrative code** placed inside `InvocationHandler.invoke` or a lambda handler that can throw `Throwable`. Do not cast `getCause()` to `Exception`: the target can throw an `Error` as well, and `InvocationHandler.invoke` declares `throws Throwable`.

If you are on the **caller** side and catch `UndeclaredThrowableException`, you should not assume there is only one wrapping layer. With the chain:

~~~text
UTE
 ├── directly: IOException
 └── or: InvocationTargetException
               └── IOException / RuntimeException / other Error
~~~

Unwrapping the cause for **diagnostics** can use a small helper method:

~~~java
static Throwable unwrapOne(Throwable error) {
    if (error instanceof InvocationTargetException e
            && e.getCause() != null) {
        return e.getCause();
    }
    if (error instanceof UndeclaredThrowableException e
            && e.getUndeclaredThrowable() != null) {
        return e.getUndeclaredThrowable();
    }
    return error;
}
~~~

The method above is **an illustrative method**, requiring imports for both exception types and placement inside a class. If you want to trace across multiple layers, you can call it repeatedly while the new result differs from the previous object; however, production code must guard the loop and preserve layer traces for logging.

**Do not blindly strip all wrappers.** Sometimes `UndeclaredThrowableException` is important information that the interface and implementation have a **mismatched exception contract**. `InvocationTargetException` may come from a Reflection API that the caller actually needs to know about. An “unwrap one” helper is suitable for observation or for unwrapping at a designed boundary, not a reason to erase all exception semantics across every layer of the system.

### When should getCause be used?

- **In a handler calling `Method.invoke`:** catch **specifically `InvocationTargetException`**, rethrow `getCause()` so the proxy evaluates the checked exception contract itself.
- **In a caller catching `UndeclaredThrowableException`:** use `getUndeclaredThrowable()` or `getCause()` to see which exception actually escaped the handler; check further whether it is `InvocationTargetException`.
- **When reporting system errors:** preserve the cause chain to observe all Reflection/Proxy boundaries, avoiding logging only `e.toString()` and losing context.

## 7. Three strategies when a checked exception is not declared by the interface

Once the handler has the original exception, the next decision is **what the API contract should do**.

### A. Declare the checked exception on the interface (when you control the design)

~~~java
public interface FileApi {
    String read(String path) throws java.io.IOException;
}
~~~

If this is a business API that genuinely produces I/O errors, declaring `throws IOException` is usually natural. The handler removes the Reflection wrapper and rethrows `IOException`; the caller is required to handle or declare it further. The advantage is minimal information loss and a clear contract.

However, **changing `throws` on a public interface is not always feasible** when the API is already published or implemented in many places. Adding a checked exception can break calling code. Consider compatibility, and do not add `throws Throwable` everywhere just to “suppress” `UndeclaredThrowableException`.

### B. Convert intentionally into an unchecked exception

If the interface is an API that does not allow checked exceptions, you can translate the original exception into a meaningful unchecked exception:

~~~java
catch (InvocationTargetException wrapper) {
    Throwable cause = wrapper.getCause();
    if (cause instanceof java.io.IOException io) {
        throw new java.io.UncheckedIOException("read failed", io);
    }
    if (cause instanceof RuntimeException runtime) {
        throw runtime;
    }
    if (cause instanceof Error error) {
        throw error;
    }
    throw new IllegalStateException("unexpected checked failure", cause);
}
~~~

This is an **illustrative snippet**, not a standalone program. `UncheckedIOException` is a specialized `RuntimeException` for wrapping `IOException` while still keeping `IOException` in `getCause()`. For other business exceptions, you can use a custom unchecked exception with a domain-appropriate name, rather than turning everything into `IllegalStateException`.

Points to follow:

- Convert **intentionally and consistently** between interface and target.
- Keep unchecked exceptions or `Error` unchanged when there is no special reason to transform them.
- Keep the original `cause` for diagnostics.
- Do not promise an API “never fails” just because checked exceptions were converted to unchecked.

### C. Let the proxy wrap with UndeclaredThrowableException and handle at the boundary

A framework that does not control all interfaces may choose to rethrow the original checked exception and let the proxy create `UndeclaredThrowableException`. Callers can catch UTE and read `getUndeclaredThrowable()`. This accurately expresses JDK behavior but is often **awkward to use** when callers do not expect UTE; therefore it requires clear documentation, logging, and tests. Do not treat UTE as an arbitrary business conversion mechanism if a more transparent API can be designed.

## 8. Complete Java 17+ example: translating IOException to UncheckedIOException

Create the file **ProxyPolicyDemo.java**:

~~~java
import java.io.IOException;
import java.io.UncheckedIOException;
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;

public class ProxyPolicyDemo {
    public interface Port {
        String read(String key);
    }

    public static class LegacyStore {
        public String read(String key) throws IOException {
            if ("ok".equals(key)) {
                return "data:ok";
            }
            throw new IOException("storage unavailable");
        }
    }

    public static void main(String[] args) {
        LegacyStore legacy = new LegacyStore();

        InvocationHandler handler = (proxy, method, actualArgs) -> {
            Method targetMethod = LegacyStore.class.getMethod(
                    method.getName(), method.getParameterTypes());
            try {
                return targetMethod.invoke(legacy, actualArgs);
            } catch (InvocationTargetException wrapper) {
                Throwable cause = wrapper.getCause();

                if (cause instanceof IOException io) {
                    throw new UncheckedIOException("read failed", io);
                }
                if (cause instanceof RuntimeException re) {
                    throw re;
                }
                if (cause instanceof Error err) {
                    throw err;
                }
                throw new IllegalStateException(
                        "unexpected checked failure", cause);
            }
        };

        Port port = (Port) Proxy.newProxyInstance(
                ProxyPolicyDemo.class.getClassLoader(),
                new Class<?>[] { Port.class },
                handler);

        System.out.println("success: " + port.read("ok"));

        try {
            port.read("bad");
        } catch (UncheckedIOException ex) {
            System.out.println("mapped: " +
                    ex.getClass().getSimpleName());
            System.out.println("cause: " +
                    ex.getCause().getClass().getSimpleName());
            System.out.println("detail: " +
                    ex.getCause().getMessage());
        }
    }
}
~~~

Compile/run:

~~~bash
javac ProxyPolicyDemo.java
java ProxyPolicyDemo
~~~

Expected stdout:

~~~text
success: data:ok
mapped: UncheckedIOException
cause: IOException
detail: storage unavailable
~~~

**What changed:** `Port.read` declares no checked exception, but target `LegacyStore.read` can throw `IOException`. The handler catches `InvocationTargetException`, extracts the original `IOException`, and converts it to `UncheckedIOException` (a subtype of `RuntimeException`). The proxy passes the unchecked exception directly to the caller, **without needing to create `UndeclaredThrowableException`**. The caller can still read the I/O cause and error message.

This approach does not make `IOException` disappear from the system; it makes the proxy's **error contract** explicit in unchecked form. When other business needs arise, use a domain-named exception instead of `UncheckedIOException`, while always keeping the original cause.

## 9. When unwrapping fails: distinguishing target errors and Reflection errors

The related APIs sit at two different stages:

| Where it occurs | Error types that may occur | Correct interpretation |
| --- | --- | --- |
| `Target.class.getMethod(...)` | `NoSuchMethodException` | No public method found matching name and erased parameter types |
| `targetMethod.invoke(...)` before running target | `IllegalAccessException`, `IllegalArgumentException` | Insufficient access, wrong receiver or argument, Reflection issue |
| Inside target code | Any business error | `Method.invoke` wraps into `InvocationTargetException` |
| Handler throws checked exception outside interface `throws` | `UndeclaredThrowableException` | Proxy protects the checked exceptions contract |
| Handler throws RuntimeException/Error | Exception passes straight through | Proxy is not required to wrap unchecked |
| Caller invokes proxy but handler returns wrong return type | `ClassCastException` or unboxing error | Handler finished executing but result does not match proxy signature |

Do not write:

~~~java
try {
    return targetMethod.invoke(target, args);
} catch (Exception e) {
    throw new RuntimeException(e);
}
~~~

This snippet is an **example of a design flaw**: if the target throws an `IOException` allowed by the interface, the code wraps it in a `RuntimeException` containing `InvocationTargetException`, preventing the caller from catching `IOException` per the contract. It also easily mixes business errors with `IllegalAccessException` or `NoSuchMethodException` from the Reflection infrastructure itself.

The sensible approach is to catch `InvocationTargetException` separately to handle the target cause, while lookup/access errors are handled according to system policy, potentially converted into clear configuration errors when they are truly unrecoverable anomalies.

### Interfaces, method overloads, and mapping to target

`InvocationHandler.invoke` provides a `Method` belonging to the proxy declaration (usually from an interface), which does not guarantee `method.invoke(target, args)` is valid if `target` **does not implement that interface**. In both demos, the target has methods with the same name and parameters but does not implement the interface, so the handler proactively looks up the corresponding `Method` on the target class.

If the target actually implements the interface, calling `method.invoke(target, args)` is a common choice. But if you are invoking a proxy as the target or accidentally pass `proxy` itself into `Method.invoke`, it can cause **infinite recursion** through the handler. Always identify the real target object and avoid re-invoking the proxy on the forwarding path itself.

When mapping by name and parameter types, you also need to check return type, overloads, generic erasure, and the possibility of multiple interfaces declaring methods with identical signatures. A handler in a framework should have mapping rules clearer than “matching name is enough”.

## 10. Cases with multiple methods / multiple interfaces

Java allows a proxy to implement multiple interfaces at once. Two interfaces can have methods with the same name and parameter list but different `throws` lists. When handling the same merged signature in the proxy, an escaping checked exception must be valid under the rules of **all relevant declarations** — intuitively, the **intersection** of allowed checked exceptions rather than the union of all `throws`.

Conceptual example:

~~~java
interface A {
    void process() throws java.io.IOException;
}
interface B {
    void process();
}
~~~

A proxy implementing both `A` and `B` cannot allow `IOException` just because `A` declares it, while `B.process()` declares no checked exceptions. If the handler throws `IOException` for that shared signature, the proxy class may use `UndeclaredThrowableException`. Which interface the `Method` parameter passed to the handler belongs to is also subject to JDK Proxy's method selection rules when declarations collide; do not use `method.getDeclaringClass()` to infer that the caller “came through one interface” and is entitled to receive checked exceptions per that interface alone.

Situations with `throws Exception`, `throws IOException`, or intersecting checked exceptions need careful review when designing proxies that combine multiple interfaces. It is best to unify exception contracts at the interface level.

## 11. Common misconceptions about exceptions and dynamic proxies

### “Handler declares throws Throwable so it can throw anything to the caller”

`InvocationHandler.invoke` **is allowed to throw `Throwable` at the handler layer**, but the interface method implemented by JDK Proxy still has a **checked exceptions contract**. The proxy must decide which types pass straight through and which are wrapped into UTE. These two signatures are at different layers and cannot substitute for each other.

### “Once you throw e.getCause(), there will be no more UTE”

Incorrect. `throw e.getCause()` only unwraps the **Reflection exception**. If the cause is a checked exception outside the interface method's `throws`, the proxy can still create UTE. That is the **correct behavior** of JDK Proxy, not a bug in `getCause()`.

### “UTE definitely contains InvocationTargetException”

Incorrect. UTE can directly contain `IOException` or another checked exception if the handler already unwrapped or threw it directly. Only rely on `e.getUndeclaredThrowable()` to inspect what is actually there, then decide whether you need to read `InvocationTargetException.getCause()` further.

### “Method.invoke only wraps checked exceptions”

Incorrect. It wraps **the exception thrown by the target method**, including unchecked exceptions or `Error`. Errors occurring before the target method executes belong to other Reflection exception categories.

### “Catching UTE and casting cause to IOException is always safe”

Incorrect. `getUndeclaredThrowable()` may be `InvocationTargetException` or any incompatible checked `Throwable`. Check `instanceof` before casting and log thoroughly. Avoid relying on a single assumed chain structure.

### “Just adding throws Exception to the interface is a good fix”

Declaring `throws Exception` can broaden the set of valid checked exceptions and change the API meaning/how callers handle it. But that is an interface design decision, not an arbitrary bug fix. For stable APIs, only declare exceptions that truly belong to the business contract.

## 12. Handling table by practical scenario

| Scenario | Action at handler | Action at caller |
| --- | --- | --- |
| Target throws subtype of declared checked exception | Catch ITE, `throw getCause()` | Catch checked exception per interface |
| Target throws `RuntimeException` | Catch ITE, rethrow cause | Handle unchecked per business logic |
| Target throws `Error` | Catch ITE, forward Error; do not swallow | Do not use a catch-all to hide system errors |
| Target throws checked exception not in interface | Unwrap ITE then choose: map to unchecked, change interface validly, or let proxy create UTE | Catch error per documented policy |
| Caller receives UTE containing ITE | Investigate handler still forwarding Reflection wrapper | Caller reads UTE → ITE → cause, fix handler to proper design |
| Caller receives UTE containing IOException directly | Handler unwrapped ITE but interface does not allow IOException | Review `throws` contract or convert error intentionally |
| NoSuchMethod/IllegalAccess error in Reflection | Do not treat as business exception | Log stage, class, method signature, and cause |
| Proxy handler called for `equals`/`hashCode`/`toString` | Define separate handling policy or forward properly | Avoid assuming these are normal business methods |

**Important limitation:** Handlers written like the demos above are intentionally simple to illustrate exceptions. A complete proxy framework usually also needs policies for `Object` methods, default methods on interfaces, annotations, transactions, logging, and classloader/module boundaries. Those features do not change the two core wrapping mechanisms learned here.

## 13. Logging, diagnostics, and testing the exception chain

When production logs only show `UndeclaredThrowableException`, the bug is easily misattributed to “JDK Proxy is broken”. A good observation workflow is:

1. Record the **interface method** called and its declared checked exceptions (`Method.getExceptionTypes()`).
2. If UTE is seen, read `getUndeclaredThrowable()` and check its type.
3. If that cause is ITE, read `getCause()` further to find the target exception.
4. Determine whether the handler uses `Method.invoke` and whether it catches `InvocationTargetException` separately.
5. Compare the original checked exception with the valid `throws` of the proxied method (especially if the proxy implements multiple interfaces with colliding methods).
6. Only then choose whether to fix the handler, fix the interface contract, or translate the exception per domain; do not just catch UTE in the UI and silently ignore it.

When logging, preserve the **full throwable/cause chain** instead of printing only the message. An empty message does not mean the exception is harmless. At the same time, do not accidentally log passwords, tokens, or sensitive data in method arguments; log class/method with an appropriate trace and apply data protection rules.

### Recommended test cases

| Case | Handler receives from target | Interface contract | Expected outcome |
| --- | --- | --- | --- |
| Normal return | No exception | Any | Caller receives exact result |
| Valid checked | `FileNotFoundException` after unwrap | `throws IOException` | Caller catches `IOException` directly |
| Invalid checked | `IOException` after unwrap | No checked declared | Caller receives UTE, cause is IOException |
| Forgot unwrap | `InvocationTargetException` | `throws IOException` | Caller receives UTE, cause is ITE |
| Runtime exception | `IllegalStateException` after unwrap | Not declared | Caller receives IllegalStateException itself |
| Target throws Error | `AssertionError` after unwrap | Not declared | Caller receives Error if handler passes through |
| Handler maps itself | `IOException` to `UncheckedIOException` | No checked declared | Caller receives UncheckedIOException |
| Wrong Reflection mapping | `NoSuchMethodException` | Any | Infrastructure error clearly classified, not mislabeled as business exception |

A good test should assert using **`instanceof`** and the **cause chain** rather than only comparing error message strings. For the two sample programs, the fixed stdout line count can be used as a smoke test in a Java 17+ environment.

## 14. Self-check questions (with answers)

**Question 1.** `Method.invoke` calls a target that throws `IOException`. What does the Reflection call directly throw?  
**Answer:** `InvocationTargetException`; `getCause()` is `IOException`.

**Question 2.** An interface has `read() throws IOException`. The handler unwraps ITE and throws `FileNotFoundException`. What does the caller receive?  
**Answer:** `FileNotFoundException` itself because it extends `IOException`, which is a checked exception allowed by the interface contract.

**Question 3.** Interface `void audit()` declares no checked exceptions. The handler throws `IOException`. What does the caller receive?  
**Answer:** Typically `UndeclaredThrowableException`; `getUndeclaredThrowable()` is `IOException`.

**Question 4.** Why can a handler that does not unwrap ITE produce UTE even when the interface declares `throws IOException`?  
**Answer:** Because the proxy sees `InvocationTargetException` (checked) rather than the `IOException` cause. `InvocationTargetException` is not a subtype of `IOException`.

**Question 5.** Can `UndeclaredThrowableException` directly contain `IOException`?  
**Answer:** Yes. That happens when the handler has unwrapped ITE or thrown `IOException` itself, but the interface does not declare and allow it.

**Question 6.** Should you catch `Exception` around all Reflection and `throw new RuntimeException(e)`?  
**Answer:** No, not if you want to preserve checked exception contracts. You should separate target errors (ITE) from Reflection infrastructure errors, and handle each group accordingly.

**Question 7.** Are `RuntimeException` or `Error` passing through a handler automatically wrapped into UTE by the proxy?  
**Answer:** No, per JDK Proxy rules they are forwarded directly. If they originate from `Method.invoke`, the handler still has to unwrap ITE first.

**Question 8.** When is `UncheckedIOException` appropriate?  
**Answer:** When the API does not declare checked `IOException` and the design intentionally wants to convert I/O errors into unchecked, while keeping the original `IOException` in `getCause()`.

**Question 9.** If the target method declares `throws IOException` but the proxy interface does not, does the target declaration automatically grant the proxy permission to throw IOException?  
**Answer:** No. The proxy enforces the **interface's** contract, not the `throws` list from the target's implementation method.

**Question 10.** If a proxy implements two interfaces with colliding method signatures, one with `throws IOException` and the other without, is it guaranteed to pass IOException through directly?  
**Answer:** No. Checked exception rules for colliding signatures must be compatible with all relevant declarations; you should unify the throws policy or convert errors intentionally.

**Question 11.** How do `getCause()` and `getUndeclaredThrowable()` differ on UTE?  
**Answer:** Both provide access to the undeclared cause; `getUndeclaredThrowable()` explicitly expresses the specialized purpose of UTE.

**Question 12.** If a caller catches UTE and only prints `e.getMessage()`, what might be missed?  
**Answer:** The type of the original checked exception, a possible `InvocationTargetException` Reflection layer, the stack trace, and the context of the violated throws contract.

## 15. Conclusion and implementation checklist

- **`InvocationTargetException` belongs to the Reflection layer:** `Method.invoke` wraps exceptions thrown by the target. In a reflective handler, catch ITE separately and use **`throw wrapper.getCause()`** when you want to forward the exact target exception.
- **`UndeclaredThrowableException` belongs to the Proxy layer:** occurs when the handler throws a checked exception not allowed by the interface method. **Unwrapping ITE properly does not mean UTE will definitely disappear**.
- **Check the interface contract:** checked exceptions passed straight through must be types allowed by `throws`; unchecked `RuntimeException` and `Error` are passed directly.
- **Choose a consistent policy:** declare the appropriate checked exception when you can design the API; if the API does not allow it, you can map to a meaningful unchecked exception and preserve the cause; or document the UTE behavior.
- **Distinguish business errors from Reflection infrastructure errors:** `NoSuchMethodException`, `IllegalAccessException`, and wrong receiver/args are not errors from the target itself.
- **Unwrap the right number of layers:** UTE can contain ITE or contain IOException directly. Read `getUndeclaredThrowable()`, `getCause()`, and inspect the entire exception chain.
- **Test systematically:** target returns normally, valid checked, invalid checked, missing unwrap, unchecked, Error, and mapping policy; verify exception type, cause, and message rather than checking only a single log line.

Understanding **who creates the wrapper, at which boundary, and why** helps design Dynamic Proxies that keep the right contract, preserve error causes, and avoid situations where code only sees `UndeclaredThrowableException` without knowing where the real business exception is.
