# 16.7 Nhận bytecode trong bộ nhớ rồi định nghĩa lớp theo ngữ cảnh thích hợp

## 1. Bài toán: từ mã nguồn/bytecode đến một Class<?> có thể thực thi

Trong một Java runtime động, việc **biên dịch** và **định nghĩa lớp** là hai giai đoạn riêng biệt:

1. **Biên dịch/generating:** nhận mã Java hoặc cấu trúc DSL và tạo bytecode chuẩn **class file**. Có thể dùng `javax.tools.JavaCompiler` để biên dịch mã nguồn Java ngay trong JVM, hoặc dùng một bytecode generator hợp lệ.
2. **Nhận và giữ bytes:** thu các `byte[]` của file `.class` trong bộ nhớ thay vì nhất thiết ghi ra thư mục output.
3. **Định nghĩa:** chuyển đúng `byte[]` thành một `Class<?>` bên trong **class loader, module, package và bối cảnh quyền** đã chọn.
4. **Liên kết và sử dụng:** lấy `MethodHandle`, Reflection API hoặc một interface chung để gọi logic mới tạo; quản lý dependencies và vòng đời.

Bài này tập trung vào câu hỏi: **sau khi đã có bytecode trong bộ nhớ, nên định nghĩa lớp bằng cách nào để đúng ngữ cảnh?**

Ba lựa chọn chính trên Java 17+:

| Cách định nghĩa | Loại lớp | Nơi được định nghĩa | Yêu cầu đặc biệt | Phù hợp |
| --- | --- | --- | --- | --- |
| `ClassLoader.defineClass(name, bytes, 0, length)` | **Named class** | Loader mà bạn chủ động quản lý (thường một child loader) | Subclass của `ClassLoader`, binary name/bytes hợp lệ, delegation/package/security hợp lệ | Plugin, rule hoặc implementation có tên và có loader/lifecycle riêng |
| `MethodHandles.Lookup.defineClass(bytes)` | **Named class** | **Cùng loader/module/runtime package** của lookup class | Lookup phải có `PACKAGE` access; tên package trong bytes phải phù hợp | Bổ sung một class vào chính ngữ cảnh đã tin cậy |
| `MethodHandles.Lookup.defineHiddenClass(bytes, initialize, options...)` | **Hidden class** | **Cùng loader/module/runtime package** của lookup class; không tra cứu theo binary name | Lookup có **full privilege** (`PRIVATE` + `MODULE`), bytes cùng package | Lambda/adapter/internal implementation sinh động, không cần Class.forName |

**Phân biệt rõ:** `JavaCompiler` **không tự nạp** class mới, và `ClassLoader.defineClass`/**`Lookup.defineClass`** **không tự biên dịch** mã nguồn. Việc `getTask(...).call()` trả `true` mới chỉ xác nhận compilation task hoàn thành thành công; bạn còn cần bytes phù hợp và cơ chế định nghĩa chính xác.

### Mục tiêu sau bài

Bạn sẽ biết cách:

- Dùng `SimpleJavaFileObject`, `ForwardingJavaFileManager` và `JavaCompiler.CompilationTask` để nhận các output `.class` dưới dạng `Map<String,byte[]>`.
- Phân biệt **binary name**, **class identity**, **defining loader**, **runtime package**, **module**, **Lookup capability**, và **class initialization**.
- Chạy ba demo Java 17: nạp named class từ memory bằng child ClassLoader; định nghĩa named class qua `Lookup.defineClass`; và tạo hidden class qua `Lookup.defineHiddenClass`.
- Hiểu tại sao `Class.forName(name)` chỉ thành công khi dùng **loader phù hợp** và khi lớp có tên có thể tìm; hidden class không thể tìm bằng `Class.forName`.
- Phân tích lỗi compilation diagnostics, package mismatch, duplicate definition, `ClassFormatError`, `LinkageError`, permission/module failures và rủi ro mã không tin cậy.

## 2. Sơ đồ luồng xử lý

```text
Java source / DSL / bytecode generator
                 |
                 v
JavaCompiler hoặc bytecode producer
                 |
                 v
byte[] của từng class file (Map<binaryName,byte[]>)
                 |
        +--------+------------------------+
        |                                 |
        v                                 v
ClassLoader tùy chỉnh                MethodHandles.Lookup
  findClass -> defineClass              |             |
        |                            defineClass  defineHiddenClass
        v                                 |             |
 named class trong                    named class     hidden class
 child loader                         cùng context    cùng context
        |                                 |             |
        +---------------------------------+-------------+
                                          |
                                 Class<?> / MethodHandle
                                          |
                                     invoke/use
```

**Một class file riêng không đủ cho mọi chương trình.** Một source có thể sinh nhiều file class, ví dụ top-level class, nested class (`Outer$Inner`) và các cấu trúc phụ. Compiler output phải được thu theo **từng binary name**. Nếu generated bytecode tham chiếu các class khác, JVM cần tìm được chúng qua **defining loader** và quy tắc resolution thích hợp.

**Định nghĩa không đồng nghĩa với khởi tạo.** Named class được `defineClass` thường mới định nghĩa/liên kết, còn static initializer chạy khi cần active use. `Class.forName(name, true, loader)` có thể chủ động khởi tạo. Hidden class cho phép chọn `initialize=true/false` ngay trong `defineHiddenClass`.

## 3. Bước đầu: nhận bytecode mà không ghi class file của target ra đĩa

API Java Compiler nằm trong module `java.compiler`, package `javax.tools`. Một **JDK có compiler** cung cấp `ToolProvider.getSystemJavaCompiler()`. Trong runtime image không có compiler hoặc chỉ có môi trường JRE cắt giảm, phương thức này có thể trả `null`.

Để dùng API hoàn toàn trong bộ nhớ đối với **source và output của class đích**, cần:

1. Một `JavaFileObject` nguồn có `Kind.SOURCE`; nội dung đọc từ `String` qua `getCharContent()`.
2. Một `JavaFileObject` đầu ra có `Kind.CLASS`, ghi xuống `ByteArrayOutputStream` qua `openOutputStream()`.
3. Một `ForwardingJavaFileManager` chặn `getJavaFileForOutput(...)` của compiler; phần còn lại ủy quyền cho standard file manager.
4. Một `DiagnosticCollector<JavaFileObject>` để đọc lỗi/warnings compilation.
5. Gọi `compiler.getTask(...).call()`, kiểm tra `Boolean.TRUE` và lấy byte[] **sau khi task kết thúc**.

**Giới hạn của ví dụ:** tuy source và file `.class` mới được giữ trong memory, standard file manager vẫn có thể đọc JDK modules, classpath, JAR và metadata từ file system. Nó **không** có nghĩa là compiler hoàn toàn không chạm đến đĩa cho mọi hoạt động nội bộ, cũng không phải sandbox.

### 3.1. File dùng chung: `demo/runtime/MemoryCompiler.java`

Ví dụ dưới đây là một utility **runnable Java 17** dùng chung cho ba chương trình tiếp theo. Mỗi chương trình demo được chạy trong một JVM riêng và sử dụng chính helper này. Đặt file đúng vị trí package.

```java
package demo.runtime;

import javax.tools.*;
import java.io.*;
import java.net.URI;
import java.nio.charset.StandardCharsets;
import java.util.*;

public final class MemoryCompiler {
    private MemoryCompiler() { }

    static final class Source extends SimpleJavaFileObject {
        private final String source;

        Source(String binaryName, String source) {
            super(URI.create("string:///"
                    + binaryName.replace('.', '/')
                    + Kind.SOURCE.extension), Kind.SOURCE);
            this.source = source;
        }

        @Override
        public CharSequence getCharContent(boolean ignoreEncodingErrors) {
            return source;
        }
    }

    static final class Bytecode extends SimpleJavaFileObject {
        final ByteArrayOutputStream buffer = new ByteArrayOutputStream();

        Bytecode(String binaryName, Kind kind) {
            super(URI.create("mem:///"
                    + binaryName.replace('.', '/')
                    + kind.extension), kind);
        }

        @Override
        public OutputStream openOutputStream() {
            return buffer;
        }

        byte[] bytes() {
            return buffer.toByteArray();
        }
    }

    static final class CapturingFileManager
            extends ForwardingJavaFileManager<StandardJavaFileManager> {
        private final Map<String, Bytecode> outputs = new HashMap<>();

        CapturingFileManager(StandardJavaFileManager delegate) {
            super(delegate);
        }

        @Override
        public JavaFileObject getJavaFileForOutput(
                Location location, String className, JavaFileObject.Kind kind,
                FileObject sibling) {
            Bytecode output = new Bytecode(className, kind);
            outputs.put(className, output);
            return output;
        }

        Map<String, byte[]> copyBytes() {
            Map<String, byte[]> result = new HashMap<>();
            outputs.forEach((name, output) ->
                    result.put(name, output.bytes()));
            return Map.copyOf(result);
        }
    }

    public static Map<String, byte[]> compile(
            String binaryName, String javaSource) throws IOException {
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null) {
            throw new IllegalStateException(
                    "A JDK with java.compiler is required");
        }

        DiagnosticCollector<JavaFileObject> diagnostics =
                new DiagnosticCollector<>();

        try (StandardJavaFileManager standard =
                     compiler.getStandardFileManager(
                             diagnostics, Locale.ROOT,
                             StandardCharsets.UTF_8)) {
            CapturingFileManager memory =
                    new CapturingFileManager(standard);

            Boolean success = compiler.getTask(
                    null, memory, diagnostics,
                    List.of("--release", "17", "-proc:none"),
                    null, List.of(new Source(binaryName, javaSource))
            ).call();

            if (!Boolean.TRUE.equals(success)) {
                StringBuilder message =
                        new StringBuilder("Compilation failed");
                for (Diagnostic<? extends JavaFileObject> diagnostic
                        : diagnostics.getDiagnostics()) {
                    message.append("\n")
                           .append(diagnostic.getKind())
                           .append(" line ")
                           .append(diagnostic.getLineNumber())
                           .append(": ")
                           .append(diagnostic.getMessage(Locale.ROOT));
                }
                throw new IllegalArgumentException(message.toString());
            }
            return memory.copyBytes();
        }
    }
}
```

### 3.2. Vì sao từng phần lại cần thiết?

- `Source` được compiler xem là một **source file**, dù bytes Java source nằm sẵn trong `String`. URI `string:///demo/runtime/Foo.java` mô tả đường dẫn logic, **không phải** lệnh tạo file thật.
- `Bytecode` thu toàn bộ output được yêu cầu vào `ByteArrayOutputStream`. Gọi `bytes()` sau khi compilation task xong để nhận `byte[]` hoàn chỉnh.
- `CapturingFileManager.getJavaFileForOutput(...)` nhận **className compiler báo về**, không tự suy đoán output bằng tên class chính. Nhờ vậy các output phụ như `Outer$Inner` cũng được giữ trong map khi compiler sinh chúng.
- `ForwardingJavaFileManager` vẫn dùng standard manager cho việc tìm JDK APIs/classpath; chỉ thay cách xuất output của compilation task.
- `DiagnosticCollector` giữ thông tin `kind`, `lineNumber` và message. Nếu compilation failed, helper **không** trả output map để tránh dùng các bytes có thể chưa đầy đủ.
- `--release 17` chọn mức source/bytecode/API Java 17 phù hợp; `-proc:none` tắt annotation processing trong **compilation task này** để ví dụ dễ kiểm soát. Các option **không** biến compiler hoặc bytecode thành sandbox.
- `Map.copyOf(...)` tạo map không sửa được về mặt key/value mapping, nhưng các **byte[] bên trong vẫn là mutable**. Helper sao chép mỗi buffer thành một array; caller cần tránh tự sửa array sau khi kiểm tra/định nghĩa hoặc sao chép thêm khi cần bất biến mạnh.

### 3.3. Những thứ utility này chưa triển khai

Đây là ví dụ **một source unit mỗi lần compile**, đủ cho ba demo. Muốn compiler tham chiếu đến các **class đã compile trước nhưng chỉ nằm trong bộ nhớ**, cần một file manager đầy đủ hơn: cung cấp các class files đó qua `getJavaFileForInput`, `list`, `inferBinaryName` và classpath phù hợp, hoặc compile nhiều source units trong **một compilation task**. Chỉ sửa `getJavaFileForOutput` không tự làm compiler nhìn thấy các dependencies bytecode trong một map của lần compile trước.

Trong production cũng cần xử lý diagnostics cấp độ locale/version, compiler options được allowlist, tối đa dung lượng, concurrency/lifecycle file manager và dependencies. Không tái sử dụng cùng `CapturingFileManager` đồng thời giữa nhiều compilation tasks nếu chưa có thiết kế đồng bộ.

## 4. Lựa chọn 1 — ClassLoader.defineClass: named class trong loader riêng

Khi plugin/rule cần một **binary name có thể tìm lại bằng đúng loader**, một subclass `ClassLoader` thường là cách dễ kiểm soát:

1. Override `findClass(String binaryName)` để tra map output.
2. Gọi `defineClass(binaryName, byte[], 0, bytes.length)`.
3. Để `loadClass` mặc định xử lý **parent delegation** (parent-first), trừ khi có lý do chính đáng để thay chính sách và thiết kế đồng bộ đặc biệt.
4. Dùng `Class.forName(name, initialize, customLoader)` hoặc `customLoader.loadClass(name)` để lấy đúng named class.

**Quan trọng:** `defineClass` là phương thức `protected final` của `ClassLoader`, không thể gọi trực tiếp trên một class loader tùy ý từ mọi chỗ. Bạn thực hiện nó **bên trong subclass**. Tên truyền vào phải phù hợp binary name được ghi trong bytes; mismatch có thể ném `NoClassDefFoundError`, tên package bị cấm hoặc signer/sealing không hợp lệ có thể gây `SecurityException`.

### 4.1. Tệp `demo/runtime/MemoryLoaderDemo.java`

```java
package demo.runtime;

import java.lang.invoke.*;
import java.util.Map;

public class MemoryLoaderDemo {
    static final class BytecodeLoader extends ClassLoader {
        private final Map<String, byte[]> definitions;

        BytecodeLoader(ClassLoader parent, Map<String, byte[]> definitions) {
            super(parent);
            this.definitions = definitions;
        }

        @Override
        protected Class<?> findClass(String name)
                throws ClassNotFoundException {
            byte[] bytes = definitions.get(name);
            if (bytes == null) {
                throw new ClassNotFoundException(name);
            }
            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Throwable {
        String name = "generated.memory.Greeter";
        String code = """
                package generated.memory;
                public class Greeter {
                    public static String hello(String who) {
                        return "Hello " + who;
                    }
                }
                """;

        Map<String, byte[]> classes = MemoryCompiler.compile(name, code);
        BytecodeLoader loader = new BytecodeLoader(
                MemoryLoaderDemo.class.getClassLoader(), classes);

        Class<?> greeter = Class.forName(name, true, loader);
        MethodHandle hello = MethodHandles.publicLookup().findStatic(
                greeter, "hello",
                MethodType.methodType(String.class, String.class));

        System.out.println("bytes captured: "
                + classes.containsKey(name));
        System.out.println("loaded name: " + greeter.getName());
        System.out.println("same loader: "
                + (greeter.getClassLoader() == loader));
        System.out.println("call: "
                + (String) hello.invokeExact("runtime"));

        try {
            Class.forName(name);
            System.out.println("unexpected parent found class");
        } catch (ClassNotFoundException expected) {
            System.out.println("parent forName: not found");
        }

        Class<?> another = Class.forName(name, true,
                new BytecodeLoader(
                        MemoryLoaderDemo.class.getClassLoader(), classes));
        System.out.println("separate loader distinct: "
                + (greeter != another));
    }
}
```

### 4.3. Giải thích kết quả

- Source `generated.memory.Greeter` xuất hiện **chỉ trong String**; `MemoryCompiler` tạo một phần tử map có key binary name `generated.memory.Greeter` và value là bytes của class file.
- `BytecodeLoader.findClass` tạo class từ bytes **khi loader được yêu cầu tìm binary name đó**. `Class.forName(name,true,loader)` lấy đúng loader, đồng thời có thể khởi tạo class.
- `MethodHandles.publicLookup().findStatic(...)` tạo handle cho public method trên public class nằm trong unnamed module/package accessible trong ví dụ classpath. Trong named-module deployment, phải xét `exports`/readability đúng ngữ cảnh.
- `Class.forName(name)` **không truyền loader** dùng loader của caller. Vì `Greeter` không nằm trên classpath của application loader trong demo này, nó ném `ClassNotFoundException`.
- Hai `BytecodeLoader` khác nhau cùng định nghĩa `generated.memory.Greeter` từ **cùng bytes** nhưng tạo **hai Class objects khác nhau**. Class identity phụ thuộc **binary name + defining loader**; hai instance thuộc hai Class khác nhau không tương đương về kiểu chỉ vì tên giống nhau.
- Ví dụ chọn tên package `generated.memory` để tránh trùng class trong parent loader. Nếu parent đã nạp được cùng tên, parent-first delegation có thể chọn **class từ parent** thay vì bytes mới trong map.

### 4.4. Ranh giới khi mở rộng loader

Một plugin với nhiều class cần map chứa **toàn bộ class outputs** có liên hệ. Khi một class tham chiếu class khác, JVM hỏi defining loader của nó để resolve dependency; `findClass` phải tra được các bytes thích hợp hoặc parent phải cung cấp dependency.

Mặc dù tên package Java có thể giống nhau, hai class thuộc **hai defining loaders khác nhau** không mặc nhiên cùng **runtime package** theo JVM; package-private access có thể bị chặn. Đừng cố định nghĩa một class mới ở child loader rồi kỳ vọng nó tự có quyền package-private đối với class cùng tên package do application loader định nghĩa.

Named class trong child loader thường thuộc **unnamed module của chính loader đó** khi dùng cơ chế demo này. Nó không tự trở thành member của một named module hoặc có quyền can thiệp vào package private của module khác.

## 5. Lựa chọn 2 — Lookup.defineClass: bổ sung named class vào package của caller

Nếu mục tiêu là định nghĩa **một named class cùng runtime package, module, class loader và protection domain** với một class đã tồn tại, `MethodHandles.Lookup.defineClass(byte[])` phù hợp hơn việc tạo child loader.

Đặc điểm quan trọng:

- API trả trực tiếp **`Class<?>`** của named class mới.
- Lookup phải có **`PACKAGE` access**; không yêu cầu **full privilege** như `defineHiddenClass`. Một lookup từ `MethodHandles.lookup()` trong class caller hợp lệ có các mode cần thiết.
- Binary name ghi trong bytes phải nằm trong **cùng package với lookup class**, và JVM xác định runtime package/module/class loader theo lookup class.
- Lớp là **named**: có thể được tìm bằng binary name qua loader phù hợp sau khi định nghĩa.
- Không thể định nghĩa **hai lớp cùng binary name trong cùng defining loader**: lần thứ hai thường ném một `LinkageError` (ví dụ duplicate definition).
- `defineClass` không có tham số `initialize`; static initializer sẽ chạy vào thời điểm được Java class initialization rules yêu cầu.

### 5.1. Tệp `demo/runtime/MemoryLookupDemo.java`

```java
package demo.runtime;

import java.lang.invoke.*;

public class MemoryLookupDemo {
    public static void main(String[] args) throws Throwable {
        String name = "demo.runtime.InlineGenerated";
        String code = """
                package demo.runtime;
                public class InlineGenerated {
                    public static String ping() {
                        return "LOOKUP";
                    }
                }
                """;

        byte[] bytes = MemoryCompiler.compile(name, code).get(name);
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        Class<?> defined = lookup.defineClass(bytes);

        MethodHandle ping = lookup.findStatic(
                defined, "ping", MethodType.methodType(String.class));
        System.out.println("named hidden? " + defined.isHidden());
        System.out.println("same loader? "
                + (defined.getClassLoader()
                        == MemoryLookupDemo.class.getClassLoader()));
        System.out.println("forName finds named? "
                + (Class.forName(name) == defined));
        System.out.println("named invoke: "
                + (String) ping.invokeExact());

        try {
            lookup.defineClass(bytes);
        } catch (LinkageError expected) {
            System.out.println("duplicate definition: rejected");
        }

        try {
            MethodHandles.publicLookup().defineClass(bytes);
        } catch (IllegalAccessException expected) {
            System.out.println("publicLookup defineClass: denied");
        }

        String wrongName = "generated.other.Outsider";
        byte[] wrong = MemoryCompiler.compile(wrongName, """
                package generated.other;
                public class Outsider { }
                """).get(wrongName);
        try {
            lookup.defineClass(wrong);
        } catch (IllegalArgumentException expected) {
            System.out.println("wrong package: denied");
        }
    }
}
```

Biên dịch cùng helper `MemoryCompiler.java`:

```bash

java -cp out demo.runtime.MemoryLookupDemo
```

Stdout đã kiểm chứng:

```text
named hidden? false
same loader? true
forName finds named? true
named invoke: LOOKUP
duplicate definition: rejected
publicLookup defineClass: denied
wrong package: denied
```

**Giải thích:**

1. Helper tạo bytes từ `demo.runtime.InlineGenerated` **trong memory**. Class file đó **không phải** file nằm trên classpath của ứng dụng, nên không tự xuất hiện khi compiler vừa hoàn thành.
2. `lookup.defineClass(bytes)` định nghĩa class **trong loader/module/package của `MemoryLookupDemo`**. Khác với child loader, không cần tạo loader riêng và có thể chia sẻ runtime package phù hợp.
3. `Class.forName(name) == defined` là true: class mới là **named class** và defining loader của caller biết về nó sau khi `defineClass`.
4. `lookup.findStatic(defined, "ping", ...)` liên kết đến method đã được định nghĩa, trả `LOOKUP`.
5. Lần `defineClass(bytes)` thứ hai trên **cùng loader và cùng binary name** bị từ chối. Không sử dụng `Lookup.defineClass` như cơ chế **hot-swap** hoặc tự động ghi đè class hiện hữu.
6. `publicLookup()` không có `PACKAGE` access, nên bị từ chối với `IllegalAccessException`.
7. Bytes có tên `generated.other.Outsider` không cùng package `demo.runtime` với lookup class, nên `defineClass` ném `IllegalArgumentException`.

### 5.2. Vì sao không chỉ dùng ClassLoader cho mọi trường hợp?

Một class trong child loader có thể nằm cùng **chuỗi tên package** với host nhưng vẫn không cùng **runtime package** hoặc module, nên không được truy cập package-private/protected như code host theo nhiều quy tắc JVM. `Lookup.defineClass` có lợi khi framework **có quyền thích hợp** và muốn generated class gia nhập **cùng ngữ cảnh tin cậy** của lookup class.

Đổi lại, vì class mới được định nghĩa trong loader của host, nó thường sống theo lifecycle của loader ấy; cần bảo đảm binary name duy nhất và tránh tăng số class/metaspace vô hạn. Không dùng quyền Lookup của host để đưa bytecode không đáng tin vào cùng module/package.

## 6. Lựa chọn 3 — Lookup.defineHiddenClass: implementation nội bộ không tra theo tên

Nếu runtime chỉ cần một class được liên kết qua `Class<?>`, `MethodHandle` hoặc một interface, không cần `Class.forName(binaryName)`, thì `Lookup.defineHiddenClass` có thể phù hợp.

Cú pháp:

```java
MethodHandles.Lookup hiddenLookup =
        MethodHandles.lookup().defineHiddenClass(bytes, false);
Class<?> hidden = hiddenLookup.lookupClass();
```

**Phân biệt với `Lookup.defineClass`:**

- `defineHiddenClass` trả **`Lookup`**, không trả trực tiếp `Class<?>`. Lookup trả về có quyền thích hợp để truy cập hidden class.
- Yêu cầu caller Lookup có **full privilege access**, bao gồm `PRIVATE` và `MODULE`. `publicLookup()` chắc chắn không đủ.
- Bytes vẫn phải mô tả class thuộc **cùng package** với lookup class.
- Hidden class có `Class.isHidden() == true` và một tên diagnostic có suffix, nhưng **không có binary name có thể tìm theo tên**. `Class.forName(hidden.getName())` không thể định vị hidden class.
- Có thể định nghĩa **nhiều hidden classes từ cùng bytes** mà không trùng binary name theo cách của named class; mỗi lần được một identity riêng.
- `initialize=false` cho phép trì hoãn class initialization đến active use. `initialize=true` khởi tạo trong quá trình define.
- `ClassOption.NESTMATE` cho phép hidden class trở thành nestmate của lookup class theo quy tắc JVM; `ClassOption.STRONG` gắn mạnh vòng đời hidden class với defining loader. Hai option **không** biến hidden thành named class.
- Hidden class mặc định có thể unload độc lập khi không còn các tham chiếu giữ sống; **không thể bảo đảm thời điểm GC/unload**.

### 6.1. Tệp `demo/runtime/MemoryHiddenDemo.java`

```java
package demo.runtime;

import java.lang.invoke.*;

public class MemoryHiddenDemo {
    public static void main(String[] args) throws Throwable {
        String name = "demo.runtime.HiddenGenerated";
        String code = """
                package demo.runtime;
                public class HiddenGenerated {
                    static {
                        System.out.println("<clinit> HiddenGenerated");
                    }
                    public static String run() {
                        return "HIDDEN";
                    }
                }
                """;

        byte[] bytes = MemoryCompiler.compile(name, code).get(name);
        MethodHandles.Lookup base = MethodHandles.lookup();
        MethodHandles.Lookup lazy =
                base.defineHiddenClass(bytes, false);
        Class<?> hidden = lazy.lookupClass();

        System.out.println("hidden? " + hidden.isHidden());
        System.out.println("same package? "
                + hidden.getPackageName().equals(
                        MemoryHiddenDemo.class.getPackageName()));
        System.out.println("canonical name null? "
                + (hidden.getCanonicalName() == null));

        try {
            Class.forName(hidden.getName());
        } catch (ClassNotFoundException expected) {
            System.out.println("forName hidden: not found");
        }

        MethodHandle run = lazy.findStatic(
                hidden, "run", MethodType.methodType(String.class));
        System.out.println("before first invoke");
        System.out.println("invoke: "
                + (String) run.invokeExact());

        System.out.println("before eager define");
        Class<?> eager =
                base.defineHiddenClass(bytes, true).lookupClass();
        System.out.println("distinct classes? "
                + (hidden != eager));

        Class<?> nestmate = base.defineHiddenClass(
                bytes, false,
                MethodHandles.Lookup.ClassOption.NESTMATE,
                MethodHandles.Lookup.ClassOption.STRONG
        ).lookupClass();
        System.out.println("nestmate host? "
                + (nestmate.getNestHost() == MemoryHiddenDemo.class));
        System.out.println("strong still hidden? "
                + nestmate.isHidden());

        try {
            MethodHandles.publicLookup().defineHiddenClass(
                    bytes, false);
        } catch (IllegalAccessException expected) {
            System.out.println("publicLookup defineHiddenClass: denied");
        }
    }
}
```

Lệnh chạy:

```bash
javac -encoding UTF-8 --release 17 -d out demo/runtime/MemoryCompiler.java demo/runtime/MemoryHiddenDemo.java
java -cp out demo.runtime.MemoryHiddenDemo
```

Stdout đã kiểm chứng:

```text
hidden? true
same package? true
canonical name null? true
forName hidden: not found
before first invoke
<clinit> HiddenGenerated
invoke: HIDDEN
before eager define
<clinit> HiddenGenerated
distinct classes? true
nestmate host? true
strong still hidden? true
publicLookup defineHiddenClass: denied
```

**Đọc output:**

1. Hidden class đúng là `isHidden() == true`, cùng package với host. Dù `getName()` trả chuỗi hình dạng `demo.runtime.HiddenGenerated/...`, đó **không phải tên class để truyền cho Class.forName**. Demo không in suffix vì suffix được JVM tự sinh và không ổn định.
2. `defineHiddenClass(bytes,false)` định nghĩa hidden class nhưng chưa chạy static initializer. `findStatic` có thể tạo MethodHandle tới method, rồi ở **lượt invoke đầu tiên** JVM khởi tạo class và in `<clinit> HiddenGenerated`.
3. `defineHiddenClass(bytes,true)` tạo **một hidden class khác** và khởi tạo ngay, nên initializer chạy lần thứ hai. Hai class là hai identity, không phải cùng class bị khởi tạo lại.
4. `NESTMATE` làm hidden class gia nhập nest của lookup class; `STRONG` thay lifecycle unloading nhưng hidden class vẫn không thể tìm theo tên. Không kết luận GC behavior chỉ từ kết quả này.
5. `publicLookup()` không có full privilege nên `defineHiddenClass` ném `IllegalAccessException`.

### 6.2. Hidden class không phải lớp “không ai gọi được”

Một hidden class vẫn có thể implement **interface có tên** do host biết đến, nhận instance qua factory hoặc cung cấp các method handles. Nó chỉ không thể **nominally reference/resolve bằng binary name** theo cách thông thường. Điều đó hữu ích khi sinh interpreter adapter, lambda implementation hoặc DSL specialization.

Ngược lại, nếu bạn cần lưu tên class vào database rồi dùng `Class.forName` trong lần khởi động sau để khôi phục, hidden class **không đáp ứng mục tiêu đó**. Hãy lưu input/bytecode template và tạo implementation mới khi cần, hoặc chọn named class.

## 7. Quy tắc quyết định theo context, không theo thói quen

| Câu hỏi thiết kế | Đáp án và API phù hợp |
| --- | --- |
| Cần class **có binary name**, tìm bằng class loader riêng, cô lập vòng đời phiên bản? | Tạo child loader + `ClassLoader.defineClass`; truy vấn `Class.forName(name, true, loader)`. |
| Cần class **có tên** trong **cùng module/package/loader** với host để chia sẻ các quyền/package hợp lệ? | Dùng `Lookup.defineClass` với Lookup có `PACKAGE` access và bytes đúng package. |
| Cần implementation sinh động, chỉ giữ bằng `Class<?>`/handle, không cần lookup tên, muốn nhiều class từ cùng template? | Dùng `Lookup.defineHiddenClass` với full privilege và package phù hợp. |
| Cần class được tìm lại bằng tên qua loader hiện có? | Dùng **named class**; hidden không thể dùng `Class.forName`. |
| Muốn định nghĩa class sang package của module khác mà host không sở hữu? | Không API nào là “tự do vượt quyền”. Cần thiết kế API/Lookup/module boundary hợp lệ trước. |
| Muốn thay bytecode của class đã được nạp mà không đổi identity? | `defineClass` không phải hotswap; cân nhắc Java Instrumentation/agent theo hợp đồng hỗ trợ, hoặc tạo phiên bản mới trong loader khác và chuyển dispatch. |
| Muốn thực thi code untrusted an toàn? | Không dùng defineClass/hidden như sandbox; cần cô lập thực sự và chính sách an ninh khác. |

### 7.1. Class identity là `(binary name, defining loader)` đối với named class

Hai class có cùng binary name nhưng do **hai loaders khác nhau** định nghĩa là hai **runtime types khác nhau**. Điều này tác động đến:

- `instanceof`, cast và method parameter types;
- package-private access (runtime package phụ thuộc loader/module, không chỉ string tên);
- static state (mỗi class có một bản state riêng);
- registry, DI container và cache;
- unloadability (các tham chiếu tới loader/class/method handles có thể giữ loader sống).

Một interface **chung do parent loader định nghĩa** thường là điểm nối tốt giữa host và plugin classes trong child loader. Nếu mỗi plugin loader tự định nghĩa một bản interface có cùng tên, việc cast sang interface do host nạp có thể **thất bại** dù tên giống nhau.

## 8. Từ compiler output đến định nghĩa: thứ tự triển khai an toàn

Một pipeline nghiêm túc nên đi qua các bước rõ ràng:

1. **Chọn tên và namespace:** quyết định binary name/package được phép, class loader/module mục tiêu, liệu class có cần discover qua tên hay không.
2. **Kiểm tra nguồn:** không nhận source code tùy ý nếu user không có quyền thực thi. Giới hạn kích thước, phiên bản, số class dự kiến, compiler options, dependencies và timeout ở tầng hệ thống.
3. **Biên dịch trong memory:** truyền `SOURCE` JavaFileObject, thu `CLASS` outputs, xử lý diagnostics. Nếu compilation failed, không định nghĩa phần output chưa đầy đủ.
4. **Xác minh bytes:** map theo binary name; đảm bảo class file version phù hợp target runtime; kiểm tra package/name và dependencies. Có thể áp thêm scan/allowlist, nhưng scan không thay thế sandbox.
5. **Chọn định nghĩa:** child loader hoặc Lookup named/hidden theo context, không dùng một chiến lược cho mọi tình huống.
6. **Tránh race:** nếu nhiều thread đồng thời yêu cầu cùng binary name, bảo đảm chỉ một hoạt động định nghĩa trong cùng loader; cache `Class<?>`/handle theo bộ khóa thích hợp.
7. **Liên kết và invoke:** dùng `MethodHandle`/Reflection/typed interface với chữ ký đúng. MethodHandle đã được tạo có capability; quản lý quyền chia sẻ.
8. **Quản lý vòng đời:** có chính sách cache, version và unloading; đừng định nghĩa lại vô hạn. Close resources của file manager; không đóng hoặc clear loader khi object/class của nó còn đang dùng.

### 8.1. Kiểm tra đầu ra compiler có đầy đủ không?

Một unit Java có thể sinh nhiều class files, kể cả nested types `Outer$Inner`. Helper của bài dùng `getJavaFileForOutput` để thu **mọi output được compiler báo**, không chỉ main binaryName. Trong ứng dụng thực tế, nếu class `A` tham chiếu class `B`:

- Cần đảm bảo `B` có trong map hoặc có thể được loader **resolve từ parent/đường phụ thuộc**.
- Nếu compile qua **nhiều vòng** độc lập, standard file manager không tự biết outputs đã ở trong memory của vòng trước; phải triển khai thêm input classfile lookup hoặc compile đồng thời.
- Nếu cùng package trong hai loaders, quyền package-private không tự chia sẻ. Cần chọn đúng loader và module từ đầu.

### 8.2. Lỗi compiler không phải lỗi class loader

Một ví dụ source sai cú pháp:

```java
// Đoạn minh họa KHÔNG biên dịch:
public class Broken {
    public int value( { return 1; }
}
```

Với input này, `JavaCompiler.CompilationTask.call()` trả `false` và `DiagnosticCollector` chứa lỗi biên dịch. Trong helper, nó ném `IllegalArgumentException` với kind/line/message; **không gọi defineClass** khi compile chưa thành công.

Ngược lại, compilation có thể thành công nhưng quá trình định nghĩa hoặc liên kết thất bại: bytecode/classpath phù hợp lúc compile **không** bảo đảm mọi dependency sẽ hiện diện ở runtime loader khác.

| Giai đoạn | Lỗi điển hình | Vì sao xảy ra và cần kiểm tra |

Các lỗi JVM liên quan đến class format, linkage hoặc verifier có thể là những subclass của `Error`, không phải checked exception.

## 10. Bảo mật và ranh giới tin cậy

**Bytecode trong bộ nhớ không an toàn hơn bytecode trên đĩa.** Nếu source hoặc bytes không đáng tin, việc định nghĩa và **thực thi** class sẽ chạy mã với khả năng của tiến trình JVM, theo những quyền và ranh giới của runtime. Hidden class không phải sandbox; child class loader cũng không tạo một OS security boundary.

Các nguy cơ và yêu cầu:

- **Resource abuse:** code tạo vòng lặp vô hạn, tạo quá nhiều threads, class definitions, heap/metaspace objects, hoặc truy cập tài nguyên cục bộ. Hạn chế bằng process/container isolation và quota nếu input không tin cậy; không dựa vào timeout Java thread interrupt để dừng mã tùy ý.
- **Class initialization:** `Class.forName(name,true,loader)` hoặc `defineHiddenClass(bytes,true)` có thể kích hoạt static initializer với side effects. Chỉ define chưa invoke không luôn có nghĩa không có execution.
- **Compiler processors:** `-proc:none` ngăn annotation processing trong task demo, nhưng không loại bỏ mọi rủi ro từ compiler/plugin/provider không đáng tin hoặc lệnh/toolchain được phép mở.
- **Lookup authority:** `Lookup.defineClass`/`defineHiddenClass` dùng quyền của lookup class. Không trao full-privilege Lookup hoặc MethodHandle trỏ private logic cho untrusted plugin.
- **Package/module:** không cố nhồi class mới vào `java.*` hay package riêng của module khác bằng cách qua mặt class loader. Nếu cần deep access, dùng API hợp lệ và cấu hình JPMS `exports`/`opens` rõ ràng; đừng bật `--add-opens` tràn lan.
- **ProtectionDomain và sealing:** `ClassLoader.defineClass` có overload nhận `ProtectionDomain`; signer/package sealing cần nhất quán. Ví dụ helper tối giản dùng overload mặc định, không thay thế chính sách bảo mật cho môi trường multi-tenant.
- **Class identity và caching:** các class loader phiên bản cũ có thể không unload vì cache, thread context class loader, static references, MethodHandle hoặc task còn giữ. Hidden class dùng `STRONG` có thể sống cùng loader lâu hơn.

Nếu phải thực thi code do khách hàng hoặc agent không tin cậy gửi, cách tiếp cận phù hợp hơn là **isolate thành process/container khác** với quyền OS thấp, tài nguyên giới hạn và giao thức giao tiếp có kiểm soát. API định nghĩa class không được thiết kế để thay thế sandbox.

## 11. So sánh với các cơ chế khác

| Cơ chế | Có phải công cụ định nghĩa lớp từ bytes? | Đặc điểm |
| --- | --- | --- |
| `JavaCompiler` | Không, chỉ **biên dịch** | Tạo byte[]/class files nếu file manager thu output đúng cách. |
| `ClassLoader.defineClass` | Có | Named class trong loader tùy chỉnh; parent delegation và runtime package identity cần được thiết kế. |
| `Lookup.defineClass` | Có | Named class trong loader/module/package của lookup class; cần `PACKAGE`. |
| `Lookup.defineHiddenClass` | Có | Hidden class cùng ngữ cảnh lookup; cần full privilege, không thể tìm qua binary name. |
| `Class.forName` | **Không** định nghĩa bytes tùy ý | Yêu cầu loader tìm/khởi tạo **named class** theo tên; không tìm hidden class. |
| `LambdaMetafactory` | Không phải bộ đọc byte[] trực tiếp từ user | Bootstrap factory cho lambda/SAM; runtime có thể dùng lớp sinh động nội bộ. |
| `java.lang.instrument.Instrumentation` | Có cơ chế redefine/retransform trong phạm vi hỗ trợ | Dành cho agent/hot instrumentation, không phải thay thế trực tiếp `defineClass` trong ứng dụng thường. |
| Bytecode generator (ASM, Byte Buddy, v.v.) | Thường **sinh/biến đổi bytes** | Vẫn phải định nghĩa output với loader/Lookup phù hợp; không tự loại bỏ ràng buộc JVM. |

Đừng đồng nhất `Class.forName` với `defineClass`. `Class.forName` là một **đường truy vấn/nạp theo binary name**, trong khi `defineClass` chuyển bytes thành **một class definition thực sự** trong ngữ cảnh đã chọn.

## 12. Lựa chọn khi module và class loader phức tạp

### 12.1. Unnamed module và named module

Trong các demo, class host chạy từ **classpath** nên nằm trong unnamed module. Một child class loader định nghĩa generated named class thường đặt nó trong unnamed module của loader đó, chứ **không tự gia nhập** module của host. Điều này làm khác nhau cả module membership, loader identity và khả năng truy cập package-private.

Khi host chạy trong **named module**, `Lookup.defineClass` và `Lookup.defineHiddenClass` có thể định nghĩa class cùng **module** với lookup class, nếu thỏa điều kiện quyền/package. Nhưng việc tạo lookup có quyền ở module khác phải tuân theo kiểm tra của JPMS; `publicLookup()` không có `PACKAGE` hoặc full privilege.

Nếu bạn chỉ có tên package như `com.app.internal` trong source generated, điều đó **không tự đủ** để định nghĩa class trong module `com.app`. Context xác định bởi defining loader/Lookup, không phải chỉ bởi chuỗi package.

### 12.2. Cùng package string nhưng khác runtime package

Runtime package dựa vào **package name và defining loader** (và ngữ cảnh module liên quan). Hai class tên `com.app.A` và `com.app.B` do loaders khác nhau định nghĩa **không tự có** quan hệ truy cập package-private hợp lệ. Đây là một nguyên nhân hay gặp của `IllegalAccessError` sau khi compile và define đều thành công.

Nếu bytecode cần package-private access đến host, thường **Lookup.defineClass** với quyền hợp lệ là lựa chọn đúng hơn child loader. Nếu không cần quyền đó, cách sạch hơn là dùng một **public interface/contract** thay vì dựa vào package-private internals.

### 12.3. Khi dùng hidden class

Hidden class là lựa chọn cho implementation không cần discover theo tên. Nếu bytes có class name `demo.runtime.HiddenGenerated` nhưng lookup class ở `demo.runtime`, API chấp nhận; kết quả vẫn mang tên hidden có suffix do JVM tạo. Không đăng ký hidden name để nạp lại sau restart: lưu template/source/bytes và tái định nghĩa một class mới, sau đó giữ `Class<?>`/MethodHandle.

## 13. Bài tập tự luyện

**Bài tập 1 — kết quả compiler có thực sự nằm trong memory?**

Từ `MemoryCompiler.compile("generated.memory.Greeter", code)`, kiểm tra key trong map và số byte (lớn hơn 0). Chạy loader demo trong một thư mục chỉ chứa các class của host, **không** chứa `generated/memory/Greeter.class`. Vì sao `Class.forName(name,true,customLoader)` thành công trong khi `Class.forName(name)` thất bại?

**Đáp án:** custom loader tra map rồi gọi `defineClass`; application loader không biết map và không tìm được generated class theo classpath của nó.

**Bài tập 2 — hai loaders, cùng tên.**

Tạo hai `BytecodeLoader` từ cùng map, gọi `Class.forName(name,true,loader1)` và `Class.forName(name,true,loader2)`. Vì sao hai `Class<?>` khác nhau dù bytes và binary name giống nhau?

**Đáp án:** class identity của named class phụ thuộc defining loader; mỗi loader tạo một type độc lập.

**Bài tập 3 — cùng loader, cùng tên.**

Với `Lookup.defineClass(bytes)`, gọi lần thứ hai trên cùng bytes. Điều gì xảy ra?

**Đáp án:** named class không thể được định nghĩa lại cùng binary name trong cùng loader. Lần hai bị từ chối bằng `LinkageError`; nếu muốn một phiên bản khác, cần chiến lược tên/loader khác hoặc cơ chế instrumentation phù hợp.

**Bài tập 4 — vì sao sai package bị từ chối?**

Dùng lookup được tạo trong `demo.runtime.MemoryLookupDemo` để định nghĩa bytes có class name `generated.other.Outsider`. API phản ứng thế nào?

**Đáp án:** `Lookup.defineClass` yêu cầu bytes cùng package với lookup class; ném `IllegalArgumentException`. `Lookup.defineHiddenClass` cũng có ràng buộc cùng package.

**Bài tập 5 — hidden có thể được gọi không?**

Sau `defineHiddenClass(bytes,false)`, lấy `hiddenLookup.lookupClass()`, `findStatic(...)` và gọi `invokeExact()`. Vì sao có thể gọi method nhưng `Class.forName(hidden.getName())` không tìm được?

**Đáp án:** hidden class vẫn là Class object có thể liên kết và thực thi qua capability. Nhưng nó không có binary name discoverable theo tên.

**Bài tập 6 — thứ tự class initialization.**

Trong `MemoryHiddenDemo`, vì sao `<clinit> HiddenGenerated` xuất hiện hai lần?

**Đáp án:** hai lần `defineHiddenClass` tạo **hai hidden classes khác nhau** từ cùng bytes. Một được khởi tạo ở lần gọi static method đầu tiên (initialize=false), một được khởi tạo ngay khi define (initialize=true).

**Bài tập 7 — source phụ thuộc nhiều class.**

Mở rộng chương trình để compile source `A` phụ thuộc `B`. Tại sao chỉ giữ `Map<String,byte[]>` của vòng compile trước chưa đủ để compiler ở vòng sau nhận biết `B`?

**Đáp án:** standard file manager tìm dependency theo module path/classpath; để compiler nhìn thấy bytes chỉ nằm trong memory cần cung cấp thêm JavaFileManager input/list/inferBinaryName hoặc compile cả A/B cùng task. Lúc chạy, defining loader cũng phải resolve được cả hai.

## 14. Checklist triển khai

Trước khi đưa pipeline vào production, hãy tự kiểm tra:

- [ ] Đã xác định liệu cần **named** hay **hidden** class.
- [ ] Tên binary/source URI và output className nhất quán; package khớp context.
- [ ] Compiler tồn tại; `JavaCompiler.getTask(...).call()` thành công; diagnostics được giữ khi thất bại.
- [ ] Các bytes phụ (nested/anonymous/generated class) và dependencies được thu, resolve đầy đủ.
- [ ] Nếu dùng custom loader, đã hiểu parent delegation, class identity, module membership và lifecycle.
- [ ] Nếu dùng `Lookup.defineClass`, lookup có `PACKAGE` access và bytes cùng package.
- [ ] Nếu dùng `Lookup.defineHiddenClass`, lookup có **full privilege**; `initialize`/`NESTMATE`/`STRONG` được chọn có chủ đích.
- [ ] Mã không tin cậy không được thực thi chỉ dựa vào niềm tin “hidden/in-memory là an toàn”.
- [ ] Không định nghĩa lại vô hạn cùng tên/loader; có version/cache/cleanup phù hợp.
- [ ] Test đã bao gồm compile failure, package mismatch, loader visibility, duplicate definition, method lookup và class initialization.
- [ ] Đã xác minh lệnh chạy với JDK 17+ và cấu hình runtime/classpath/module thực tế.

## 15. Ghi nhớ

- **Nhận bytecode** qua `JavaCompiler + ForwardingJavaFileManager` là bước **tạo dữ liệu**, không phải bước nạp lớp.
- **`ClassLoader.defineClass`** định nghĩa **named class** trong loader được chọn; cần hiểu parent delegation và tính độc lập của types giữa loaders.
- **`Lookup.defineClass`** định nghĩa **named class** cùng loader/module/runtime package với lookup class; cần `PACKAGE` access.
- **`Lookup.defineHiddenClass`** định nghĩa **hidden class** cùng ngữ cảnh lookup; cần full privilege, không thể tìm qua `Class.forName`; có tùy chọn `initialize`, `NESTMATE` và `STRONG`.
- **Class identity và quyền truy cập** gắn với loader/module/runtime package, không chỉ dựa vào chuỗi tên class.
- **Bytecode trong memory không phải sandbox**. Chỉ sinh/định nghĩa/thực thi class trong những context được tin cậy và có cơ chế quản lý lifecycle rõ ràng.
