# 16.8 Managing Multiple Generated Classes, File Manager Resources, and Compiled Code Versions

A **runtime** Java compilation system does not merely convert a source code string into a single `.class` file. In real-world applications, a single compilation pass may receive **multiple source units**, generate **multiple class files** (including nested, anonymous, synthetic, and types generated by annotation processors), read multiple dependencies, and simultaneously create auxiliary resources. Afterward, the runtime must also decide **which set of bytecode belongs to the same version**, load them with **which class loader**, and when to close `JavaFileManager`, release file handles/caches, or discard failed compilation artifacts.

This topic belongs to **16. Runtime Compilation**. The focus is not on the syntax of calling `javac` in isolation, but on three closely related responsibilities:

1. **Managing the full output of a compilation task**: not dropping `Outer$Inner.class`, not overwriting files between two passes, not using the wrong dependency, or returning only the bytecode of a single main class.
2. **Managing the resource lifecycle of the file manager**: determining who owns `StandardJavaFileManager`/`ForwardingJavaFileManager`, read–write locations, streams, diagnostics, caching, and concurrency policies.
3. **Managing versions of compiled code**: separating compilation results by version/release, not mixing two generations that share the same binary name, verifying compatibility on the target JVM, and proactively managing class loader/lifecycle.

The examples use **Java 17+**, based on the Java Compiler API (JSR 199, `java.compiler` module). There are two standalone programs: compiling multiple classes into memory and loading two revisions side by side; and batch compiling to a temporary directory, reusing the file manager sequentially, and **not publishing** a failed compilation pass. The code and `stdout` were verified using `javac --release 17`.

## 1. Components of a Runtime Compilation Pipeline

| Component | API | Responsibility |
| --- | --- | --- |
| Obtain compiler | `ToolProvider.getSystemJavaCompiler()` | Provides the compiler when the runtime has `jdk.compiler`; may return `null` if unavailable |
| Create compilation task | `JavaCompiler.getTask(...)` | Accepts options, units, diagnostics, and file manager; returns a task with `call()` |
| Abstract source/bytecode | `JavaFileObject`, `SimpleJavaFileObject` | Represents `.java`, `.class` in the file system, memory, or other sources |
| Input/output routing | `JavaFileManager` | Locates source/class/resource files across `Location`s and receives output for each generated class |
| Standard file manager | `StandardJavaFileManager` | Reads/writes files, jars, paths; configures output/classpath/module-path |
| Custom file manager | `ForwardingJavaFileManager` | Delegates most of the API; overrides operations needed to redirect into memory or audit |
| Error reporting | `DiagnosticCollector<JavaFileObject>` | Collects `ERROR`, `WARNING`, line/column, source, and message |
| Load results | `ClassLoader` or `URLClassLoader` | Defines each class from the **entire** output bundle, preserving version boundaries |

Key point: **`JavaCompiler` is not a class loader**. Successful compilation does not mean the runtime has loaded or initialized the class. `JavaFileManager` serves the compiler; a `ClassLoader` (or appropriate class-defining mechanism) handles the step of loading the generated code. Both have different lifecycles and responsibilities.

### 1.1. What inputs does `getTask` take?

```java
JavaCompiler.CompilationTask task = compiler.getTask(
        null,            // Writer for non-standard diagnostic output
        fileManager,     // JavaFileManager: input/output routing
        diagnostics,     // DiagnosticListener
        options,         // e.g. ["--release", "17", "-proc:none"]
        null,            // classes: class names for annotation processing
        compilationUnits // Iterable<? extends JavaFileObject>
);
boolean success = Boolean.TRUE.equals(task.call());
```

This is an **illustrative snippet** that requires variables to already be declared/imported. `call()` executes the task; a `CompilationTask` **cannot be called again** to compile another version. To perform a new build, obtain a **new task**, and depending on the strategy, reuse or create a new file manager.

Do not assume that `getTask` returning success means all bytecode is already **safely published** for other requests. The compiler may generate partial output before detecting an error in another unit; the orchestrating layer must check the result before deciding to publish the **entire bundle**. Even when `call()` returns true, the verification/packaging process and dependency validation remain the application's responsibility.

## 2. A Single Compilation Pass Can Generate More Classes Than .java Files

For example, given two units:

```java
// Helper.java
package demo.generated;
public class Helper {
    public static String prefix() { return "Hello, "; }
}

// Greeter.java
package demo.generated;
public class Greeter {
    public String greet(String name) {
        return Helper.prefix() + name + "@" + new Info().tag();
    }
    static class Info {
        String tag() { return "v1"; }
    }
}
```

These are two separate files written consecutively for illustration; **do not** save both `public class` declarations in one file. When compiled together, the compiler produces at least:

```text
demo/generated/Helper.class
demo/generated/Greeter.class
demo/generated/Greeter$Info.class
```

Do not try to predict the complete list of outputs from the number of units. With local classes, anonymous classes, lambdas/bridges, annotation processing, or compiler bytecode variations, the actual count and names of outputs may differ.

- Every `getJavaFileForOutput(location, className, kind, sibling)` with `kind == CLASS` is **an output artifact to retain**.
- For nested classes, `className` may be `demo.generated.Greeter$Info`; use the **binary name provided by the compiler**, do not construct it yourself from the source name.
- The same unit may define additional package-private top-level classes, so `Greeter.java` does not necessarily yield only `Greeter.class`.
- If letting the compiler write to a directory, inventory all actual `.class` files in the task's dedicated output.
- If storing in-memory, map **binary name → full byte[]**, including nested/secondary classes. Do not take only the bytecode of the public class.

**One batch for interdependent units** is usually simplest. For example, `Greeter` calls `Helper`, so pass both `JavaFileObject`s into the same `getTask` so the compiler resolves internal dependencies automatically. Compiling `Greeter` in a separate task when `Helper` only resides in a separate `byte[]` map may fail: the compiler needs a `CLASS_PATH`/`MODULE_PATH` or an input file manager that knows how to find `Helper.class`. **The application's class loader does not automatically become the compiler's classpath**.

### 2.1. Do Not Confuse File Names with Binary Names

`demo.generated.Greeter` is a binary name, whereas `demo/generated/Greeter.class` is a common path mapping. `Greeter$Info` is the binary name of the nested type, **not `Greeter.Info`** when calling `ClassLoader.loadClass`. In Java source code, we write `Greeter.Info`; in the file manager/class loader, that class usually has the binary name `demo.generated.Greeter$Info`.

A `JavaFileObject` for in-memory source should have an absolute URI, for example:

```java
URI.create("string:///demo/generated/Greeter.java");
```

`SimpleJavaFileObject` uses this URI as the identity describing the source. Do not create a relative URI like `Greeter.java`; some compilers/file managers rely on the URI for diagnostics and source checking. If code or class names come from users, **validate the binary name and escape/encode paths properly**, avoiding unconditional concatenation into a filesystem path.

## 3. Lifecycle and Ownership of JavaFileManager

`StandardJavaFileManager` is a **resource owner**. It may hold streams, zip/jar file handles, caches, and other file system structures; therefore, always determine where `close()` is called. The `JavaCompiler` Javadoc even suggests **reusing one standard file manager across multiple sequential compilation tasks** to reduce jar/file system scanning overhead, then closing it at the end.

An easy-to-manage model:

```text
create compiler
  |
  +--> open StandardJavaFileManager
         |
         +--> task revision A (sources + options + output A)
         +--> task revision B (sources + options + output B)
         |
         +--> close file manager (end of scope)
  |
  +--> publish validated bundle(s)
  |
  +--> separate runtime ClassLoader generation(s)
```

**Principles:**

1. Use `try-with-resources` for `StandardJavaFileManager` or a `ForwardingJavaFileManager` wrapper. `close()` releases the manager's resources (and for a standard forwarding manager, calls close on the delegate).
2. `flush()` only flushes/completes buffered output; **it does not mean `close()`**. Do not rely on `flush()` as a way to close all jar handles or resources.
3. **One manager can be used for multiple sequential tasks**; however, `JavaFileManager` **is not required to be synchronized for all methods**. Do not concurrently run multiple `CompilationTask`s sharing a mutable manager and assume thread-safety.
4. `JavaFileManager` is obligated to support concurrent access to **different file objects** it creates, but this **does not** guarantee thread-safety for the entire manager or the state of a custom map.
5. If the application processes multiple jobs in parallel, prefer a **separate manager/compilation context per job**; if a shared cache is needed, design explicit synchronization and do not share mutable output.
6. Closing the manager does not unload `Class<?>` objects already defined by a class loader; the compilation lifecycle and execution lifecycle are two separate things.
7. Do not reuse the same output directory for different versions if atomic publish or rollback is required. A failed task can leave partial files; overwriting a class file currently used by a loader can also lead to unpredictable behavior.

### 3.1. Standard Manager and Forwarding Manager

`StandardJavaFileManager` works with `Path` and `File`, supporting configuration of `StandardLocation.CLASS_OUTPUT`, `CLASS_PATH`, `SOURCE_PATH`, `ANNOTATION_PROCESSOR_PATH`, `SOURCE_OUTPUT`, or JPMS-related locations. For example:

```java
try (StandardJavaFileManager fm =
         compiler.getStandardFileManager(diagnostics, Locale.ROOT, StandardCharsets.UTF_8)) {
    fm.setLocationFromPaths(StandardLocation.CLASS_OUTPUT, List.of(outputDir));
    Iterable<? extends JavaFileObject> units =
        fm.getJavaFileObjectsFromPaths(List.of(sourceA, sourceB));
    boolean success = Boolean.TRUE.equals(
        compiler.getTask(null, fm, diagnostics,
            List.of("--release", "17", "-proc:none"),
            null, units).call());
}
```

The snippet above is an **illustrative skeleton** with variables `compiler`, `diagnostics`, `outputDir`, `sourceA`, and `sourceB`. The full program is in section 6.

`ForwardingJavaFileManager<StandardJavaFileManager>` can override only `getJavaFileForOutput` to capture bytecode into a `ByteArrayOutputStream`, while forwarding other operations (reading standard modules, classpath, jars) to the standard manager. This is a practical approach for an **in-memory compiler**.

**Warning:** a forwarding manager that only overrides `CLASS` output is not guaranteed to **fully** support in-memory mode when annotation processors or resource generators are present. `Filer.createSourceFile` and `Filer.createResource` may use `SOURCE_OUTPUT`/`CLASS_OUTPUT` through other methods such as `getFileForOutput`. Routing for sources/resources, corresponding input paths, and processing rounds must be added if annotation processing is enabled.

## 4. Full Example 1: Compile Multiple Classes into Memory, Load v1/v2 Separately

This program runs in **a single Java source file**:

- Creates **two compilation units** `demo.generated.Helper` and `demo.generated.Greeter`.
- Captures **all `CLASS` outputs** into a map in `MemoryManager`, including `Greeter$Info`.
- Compiles version `v1` with `--release 11` and `v2` with `--release 17`.
- Inspects the **major version** of the class file, using two separate `ClassLoader`s to load the same binary name of the two revisions.
- Does not publish the map if the task fails; the manager is closed via try-with-resources.
- Intentionally uses `-proc:none` so the example only works with source/class files without running annotation processors.

Save with the exact name **`InMemoryVersionsDemo.java`**:

```java
import javax.tools.*;
import java.io.*;
import java.lang.reflect.Method;
import java.net.URI;
import java.util.*;

public class InMemoryVersionsDemo {
    static final class Source extends SimpleJavaFileObject {
        private final String code;
        Source(String binaryName, String code) {
            super(URI.create("string:///" + binaryName.replace('.', '/')
                    + Kind.SOURCE.extension), Kind.SOURCE);
            this.code = code;
        }
        @Override public CharSequence getCharContent(boolean ignoreEncodingErrors) {
            return code;
        }
    }

    static final class Bytecode extends SimpleJavaFileObject {
        private final ByteArrayOutputStream data = new ByteArrayOutputStream();
        Bytecode(String binaryName) {
            super(URI.create("mem:///" + binaryName.replace('.', '/')
                    + Kind.CLASS.extension), Kind.CLASS);
        }
        @Override public OutputStream openOutputStream() { return data; }
        byte[] bytes() { return data.toByteArray(); }
    }

    static final class MemoryManager
            extends ForwardingJavaFileManager<StandardJavaFileManager> {
        private final Map<String, Bytecode> compiled = new TreeMap<>();
        MemoryManager(StandardJavaFileManager standard) { super(standard); }

        @Override public JavaFileObject getJavaFileForOutput(
                Location location, String className, JavaFileObject.Kind kind,
                FileObject sibling) throws IOException {
            if (location == StandardLocation.CLASS_OUTPUT
                    && kind == JavaFileObject.Kind.CLASS) {
                Bytecode file = new Bytecode(className);
                if (compiled.putIfAbsent(className, file) != null)
                    throw new IOException("Duplicate class output: " + className);
                return file;
            }
            return super.getJavaFileForOutput(location, className, kind, sibling);
        }

        Map<String, byte[]> snapshot() {
            Map<String, byte[]> result = new TreeMap<>();
            compiled.forEach((name, file) -> result.put(name, file.bytes()));
            return Collections.unmodifiableMap(result);
        }
    }

    static Map<String, byte[]> compile(String revision, int release)
            throws IOException {
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null)
            throw new IllegalStateException("Run on a JDK with jdk.compiler");

        String prefix = switch (revision) {
            case "v1" -> "Hello, ";
            case "v2" -> "Hi, ";
            default -> throw new IllegalArgumentException("Unknown revision");
        };

        String helper = "package demo.generated;\n"
                + "public class Helper { public static String prefix() { "
                + "return \"" + prefix + "\"; } }\n";
        String greeter = "package demo.generated;\n"
                + "public class Greeter {\n"
                + "  public String greet(String name) { "
                + "return Helper.prefix() + name + \"@\" "
                + "+ new Info().tag(); }\n"
                + "  static class Info { String tag() { "
                + "return \"" + revision + "\"; } }\n"
                + "}\n";
        List<JavaFileObject> units = List.of(
                new Source("demo.generated.Helper", helper),
                new Source("demo.generated.Greeter", greeter));

        DiagnosticCollector<JavaFileObject> diagnostics = new DiagnosticCollector<>();
        try (MemoryManager manager = new MemoryManager(
                compiler.getStandardFileManager(
                        diagnostics, Locale.ROOT,
                        java.nio.charset.StandardCharsets.UTF_8))) {

            List<String> options = List.of("--release", String.valueOf(release),
                    "-proc:none", "-encoding", "UTF-8");
            boolean ok = Boolean.TRUE.equals(compiler.getTask(
                    null, manager, diagnostics, options, null, units).call());
            if (!ok) {
                for (Diagnostic<? extends JavaFileObject> d
                        : diagnostics.getDiagnostics()) {
                    System.err.println(d.getKind() + " line "
                            + d.getLineNumber() + " "
                            + d.getMessage(Locale.ROOT));
                }
                throw new IllegalStateException(
                        "Compilation failed for " + revision);
            }
            return manager.snapshot();
        }
    }

    static final class VersionLoader extends ClassLoader {
        private final Map<String, byte[]> bytecode;
        VersionLoader(Map<String, byte[]> bytecode) {
            super(InMemoryVersionsDemo.class.getClassLoader());
            this.bytecode = bytecode;
        }

        @Override protected Class<?> findClass(String name)
                throws ClassNotFoundException {
            byte[] bytes = bytecode.get(name);
            if (bytes == null) throw new ClassNotFoundException(name);
            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    static int classMajor(byte[] b) {
        return ((b[6] & 0xff) << 8) | (b[7] & 0xff);
    }

    public static void main(String[] args) throws Exception {
        Map<String, byte[]> v1 = compile("v1", 11);
        Map<String, byte[]> v2 = compile("v2", 17);
        System.out.println("classes=" + v1.keySet());
        System.out.println("v1 major="
                + classMajor(v1.get("demo.generated.Greeter")));
        System.out.println("v2 major="
                + classMajor(v2.get("demo.generated.Greeter")));

        VersionLoader loader1 = new VersionLoader(v1);
        VersionLoader loader2 = new VersionLoader(v2);
        Class<?> first = loader1.loadClass("demo.generated.Greeter");
        Class<?> second = loader2.loadClass("demo.generated.Greeter");
        Method greet1 = first.getMethod("greet", String.class);
        Method greet2 = second.getMethod("greet", String.class);
        System.out.println("v1=" + greet1.invoke(
                first.getConstructor().newInstance(), "Ada"));
        System.out.println("v2=" + greet2.invoke(
                second.getConstructor().newInstance(), "Ada"));
        System.out.println("sameClass=" + (first == second));
        System.out.println("sameName="
                + first.getName().equals(second.getName()));
    }
}
```

Compile/run with JDK 17 or higher (the `javac` command is for the **host class**, not the two sources generated in strings):

```bash
javac --release 17 InMemoryVersionsDemo.java
java InMemoryVersionsDemo
```

Verified full `stdout`:

```text
classes=[demo.generated.Greeter, demo.generated.Greeter$Info, demo.generated.Helper]
v1 major=55
v2 major=61
v1=Hello, Ada@v1
v2=Hi, Ada@v2
sameClass=false
sameName=true
```

### 4.1. Why must all three class files be kept?

When calling `Greeter.greet`, the method needs `Helper.prefix()` **and** `Greeter$Info.tag()`. If the cache only keeps `demo.generated.Greeter.class`, the call may throw `NoClassDefFoundError` when the JVM needs to load a missing auxiliary class. Therefore `MemoryManager` stores **every `className`** that the compiler passes to `getJavaFileForOutput`, without hardcoding a single Greeter name.

`TreeMap` only makes the output list order deterministic for the demo; production can use another map. `Collections.unmodifiableMap` prevents modifying the map structure, **not** the contents of each `byte[]` from modification. If the bundle crosses an untrusted boundary, arrays must be cloned when storing/returning or a sufficiently strong immutable structure must be used.

### 4.2. Why do v1 and v2 have the same name but are different Classes?

`Class<?>` identity on the JVM depends on **binary name + defining class loader** (along with other class-loading rules). `v1` and `v2` both define `demo.generated.Greeter`, but `loader1 != loader2`, so:

- `first.getName().equals(second.getName())` is true;
- `first == second` is false;
- the static fields of the two versions are separate states, unless they point to other shared state from the parent loader;
- a v1 object **is not an instance of Class v2** and must not be blindly cast across generations.

`VersionLoader` only overrides `findClass`. It still uses the default **parent-first** mechanism of `ClassLoader.loadClass`. The example works because the parent loader **does not have** `demo.generated.Greeter` or `Helper`. If the parent has already loaded a class with the same binary name, the class loader may return **the parent's version** instead of the new bytes; production must intentionally manage namespace naming, parent policy, and loader architecture.

### 4.3. Why does a Java 17 host source produce Java 11 bytecode?

`InMemoryVersionsDemo` is a Java 17 host program (using switch expressions and modern APIs). However, the source **generated as a string** only uses syntax compatible with release 11. The compiler task `compile("v1",11)` passes `--release 11`, so `Greeter.class` has **major version 55**. Version v2 uses `--release 17`, producing major **61**. **The release of the compiler output is not determined by the release of the host application**; it is determined by each task's options within the limits supported by the compiler.

Version v1 can run on Java 11 if **all** code and dependencies are compatible, not just because the class header says 55. This is a necessary condition, not sufficient proof for every dependency, module, native library, or runtime environment.

### 4.4. Some limitations kept intentionally in the example

- Annotation processing is not used (`-proc:none`). To support generated sources/resources, the file manager must be extended beyond overriding `CLASS_OUTPUT`.
- A new `MemoryManager` is created for each revision. This prevents v1 output from lingering when building v2. The compiler object can be created anew; this example chooses isolation over maximizing caching.
- `VersionLoader` receives the entire bytes map. It is only responsible for `findClass` and does not scan the file system itself. For untrusted code, a regular loader **is not a sandbox**.
- `classMajor` only illustrates reading the two major bytes at offset 6–7 per the JVMS; production must check the `CAFEBABE` header, length, minor/preview version, checksum/signature, and format before trusting the bytes.
- The source `String` in the demo is assembled from a **revision controlled by the program itself**, without directly inserting arbitrary input. For user-supplied source, validation, authorization, and isolation must be applied.

## 5. Compiled Code Version Has at Least Three Meanings

An application that "compiles v2" should clarify **what v2 is**:

1. **Bytecode target release**: `--release 8/11/17/...` determines the target standard Java language/API and classfile format; chosen according to the JVM to run on.
2. **Source/logic revision**: `v1`, `v2`, commit hash, schema version, or generation number. Two revisions can both use `--release 17` yet exhibit different behavior.
3. **Loaded runtime generation**: a `ClassLoader`/module layer and specific Class objects. Two bundles with identical bytes can still be defined in two different loaders, creating different class identities.

One concept should not be conflated with the other two. An example manifest might look like:

```text
bundleId=orders-eval-v2
sourceDigest=SHA256(source files + normalized config)
compilerJdk=21.x
options=--release 17 -proc:none -encoding UTF-8
targetClassMajor=61
dependencies=exact artifact IDs / checksums
outputClasses=demo.generated.Helper,demo.generated.Greeter,demo.generated.Greeter$Info
loaderGeneration=17
buildStatus=VALIDATED
```

This is an **illustrative metadata template**, not program output. Do not assign a fabricated hash to `sourceDigest`. When build reproducibility is required, the hash must cover all inputs that affect the output; not just the contents of a single Java file.

### 5.1. `--release`, `-source`, and `-target`

| Option | Effect | Note |
| --- | --- | --- |
| `--release N` | Compiles against the syntax and public platform API of release N, generating the corresponding class version | Recommended when needing to run on an older Java version supported by the compiler |
| `-source N` | Restricts source syntax features | Does not automatically forbid calling newer platform APIs if using a newer JDK |
| `-target N` | Selects the class file format | Does not automatically verify that the platform API actually exists on JDK N |
| `-encoding UTF-8` | Specifies the encoding of source read from files | Maintains consistency when compiling across multiple machines |
| `-proc:none` | Disables annotation processing | Useful for demos with controlled sources; do not use if the project needs code generated from processors |

According to the Java 17 `javac` documentation, `--release` should be used instead of manually combining `-source`/`-target` when API compatibility with an older release is needed. However, it **does not guarantee** compatibility with a third-party library at runtime, module versions, service configurations, or native dependencies. Each JDK's compiler only supports a certain set of target releases; verify options and the actual environment.

### 5.2. Classfile Major and UnsupportedClassVersionError

Common milestones:

| Java release | Classfile major |
| --- | --- |
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

If compiled to major 65 and deployed on Java 17 (which typically supports up to major 61), the JVM will refuse to load it with `UnsupportedClassVersionError`, rather than automatically running the newer version. Yet merely reading the major version does not guarantee safety either: the bytes could be corrupted, depend on unavailable APIs, or have a specific minor version for preview features.

**Do not treat `--release N` as a "runs properly on N on every server" switch**. It primarily controls syntax, classfile, and platform API. Test the bundle and dependencies on the target JVM, and control compiler flags, annotation processors, and module path.

## 6. Full Example 2: StandardJavaFileManager, Separate Output Directory, and Build Errors

This example demonstrates the approach of **writing class files to disk** instead of memory:

- Creates a temporary workspace using `Files.createTempDirectory`.
- Batch-compiles two dependent source files, writing to the `good` directory.
- Loads the output with a `URLClassLoader` and then **closes the loader**.
- Reuses the **same StandardJavaFileManager sequentially** for a task with broken source, but switches the output to `rejected`.
- Does not overwrite or publish the `good` output because the second compilation fails.
- Cleans up only the temporary directory created by the program, without touching other project resources.

Save the file **`BatchFileManagerDemo.java`**:

```java
import javax.tools.*;
import java.io.IOException;
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.util.*;
import java.util.stream.Stream;

public class BatchFileManagerDemo {
    static List<String> names(Path root) throws IOException {
        try (Stream<Path> paths = Files.walk(root)) {
            return paths.filter(p -> p.toString().endsWith(".class"))
                    .map(p -> root.relativize(p).toString().replace('\\', '/'))
                    .sorted().toList();
        }
    }

    public static void main(String[] args) throws Exception {
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null)
            throw new IllegalStateException("Requires a JDK compiler");

        Path root = Files.createTempDirectory("batch-compile-");
        try {
            Path src = root.resolve("src/demo/job");
            Path good = root.resolve("good");
            Path rejected = root.resolve("rejected");
            Files.createDirectories(src);
            Files.createDirectories(good);
            Files.createDirectories(rejected);

            Path helper = src.resolve("Helper.java");
            Path worker = src.resolve("Worker.java");
            Path broken = src.resolve("Broken.java");

            Files.writeString(helper,
                    "package demo.job; public class Helper { "
                    + "public static int value() { return 6; } }",
                    StandardCharsets.UTF_8);
            Files.writeString(worker,
                    "package demo.job; public class Worker { "
                    + "public int total() { return Helper.value() * 7; } }",
                    StandardCharsets.UTF_8);
            Files.writeString(broken,
                    "package demo.job; public class Broken { int value = ; }",
                    StandardCharsets.UTF_8);

            try (StandardJavaFileManager fm =
                     compiler.getStandardFileManager(
                        null, Locale.ROOT, StandardCharsets.UTF_8)) {

                fm.setLocationFromPaths(StandardLocation.CLASS_OUTPUT,
                        List.of(good));
                DiagnosticCollector<JavaFileObject> goodDiagnostics =
                        new DiagnosticCollector<>();
                boolean success = Boolean.TRUE.equals(compiler.getTask(
                        null, fm, goodDiagnostics,
                        List.of("--release", "17", "-proc:none"),
                        null, fm.getJavaFileObjectsFromPaths(
                                List.of(helper, worker))).call());

                System.out.println("valid=" + success);
                System.out.println("classes=" + names(good));
                try (URLClassLoader loader = new URLClassLoader(
                        new URL[] { good.toUri().toURL() },
                        BatchFileManagerDemo.class.getClassLoader())) {
                    Class<?> cls = loader.loadClass("demo.job.Worker");
                    Object instance = cls.getConstructor().newInstance();
                    System.out.println("result="
                            + cls.getMethod("total").invoke(instance));
                }

                fm.setLocationFromPaths(StandardLocation.CLASS_OUTPUT,
                        List.of(rejected));
                DiagnosticCollector<JavaFileObject> badDiagnostics =
                        new DiagnosticCollector<>();
                boolean bad = Boolean.TRUE.equals(compiler.getTask(
                        null, fm, badDiagnostics,
                        List.of("--release", "17", "-proc:none"),
                        null, fm.getJavaFileObjectsFromPaths(
                                List.of(broken))).call());
                boolean error = badDiagnostics.getDiagnostics().stream()
                        .anyMatch(d -> d.getKind() == Diagnostic.Kind.ERROR);

                System.out.println("invalid=" + bad);
                System.out.println("hasError=" + error);
                System.out.println("publishedClasses=" + names(good).size());
            }
        } finally {
            try (Stream<Path> paths = Files.walk(root)) {
                for (Path p : paths.sorted(
                        Comparator.reverseOrder()).toList())
                    Files.deleteIfExists(p);
            }
        }
    }
}
```

Compile and run with JDK 17+:

```bash
javac --release 17 BatchFileManagerDemo.java
java BatchFileManagerDemo
```

Exact `stdout`:

```text
valid=true
classes=[demo/job/Helper.class, demo/job/Worker.class]
result=42
invalid=false
hasError=true
publishedClasses=2
```

### 6.1. Operational Meaning of the Disk Example

1. `setLocationFromPaths(CLASS_OUTPUT,List.of(good))` directs the output of the successful task into a separate directory. Do not use the source directory or a shared output directory when isolation is required.
2. `getJavaFileObjectsFromPaths(List.of(helper,worker))` passes **two files** into the same task; `Worker` can resolve `Helper` within that compilation.
3. `success=true` is the compiler status. The code still loads the class only **after** verifying success.
4. `URLClassLoader` needs to be closed to release the resource/URL handles it holds. `close()` **does not mean** the JVM automatically unloads already loaded Class objects; they can stay alive as long as references remain.
5. Switching `CLASS_OUTPUT` to `rejected` demonstrates that we can **reuse StandardJavaFileManager sequentially** for another task. `invalid=false` and `hasError=true` are read from `DiagnosticCollector`.
6. `publishedClasses=2` proves the old build remains intact. The program **never takes output from a failed build** to mix into the running version, regardless of whatever artifacts the compiler might have created in the `rejected` directory before reporting an error.
7. Cleanup in `finally` only deletes the path newly created by `Files.createTempDirectory`. In a real product, workspace cleanup must respect ownership/retention and avoid deleting an output folder currently in use by another loader/process.

**Important:** `DiagnosticCollector` may contain multiple diagnostics; do not write tests that depend on the count or exact English wording of diagnostic messages across `javac` versions. The example only checks for `ERROR`. For a real API, log `getKind`, `getCode`, `getSource().toUri()` if non-null, `getLineNumber`, `getColumnNumber`, and the locale-based message — redacting if the source is sensitive.

## 7. What If Annotation Processing Generates Additional Sources and Resources?

Enabling annotation processing (not using `-proc:none`) significantly changes the shape of the pipeline. Processors run in *rounds* and via `Filer` can create:

- `.java` into `StandardLocation.SOURCE_OUTPUT`;
- `.class` into `CLASS_OUTPUT`;
- auxiliary files such as `META-INF/services/...` or JSON/properties metadata via `Filer.createResource` and `JavaFileManager.getFileForOutput`.

Distinction table:

| Need | API/file manager | What to manage |
| --- | --- | --- |
| Receive generated class | `getJavaFileForOutput(...,Kind.CLASS,...)` | All binary names, including nested |
| Source created by processor | `getJavaFileForOutput(...,Kind.SOURCE,...)` | `SOURCE_OUTPUT` location, next round, identity URI |
| Resource created by processor | `getFileForOutput(location,packageName,relativeName,sibling)` | Package-based path, resource kind, duplicate/collision |
| Look up generated class/source | `getJavaFileForInput`, `list`, `inferBinaryName` (compiler-dependent) | Compiler must see the right output/generation |
| Load resource at runtime | `ClassLoader.getResource(...)` or a valid resource store | Bundling resources with classpath and loader generation |

A custom file manager that **only** captures `Kind.CLASS` like `MemoryManager` in section 4 is suitable for demos with processors disabled, but must not be advertised as a complete in-memory Java build system with annotation processors. To run annotation processors reliably, one must manage **SOURCE_OUTPUT, CLASS_OUTPUT, resources, re-read passes for sources/classes, and collision policies**, along with testing against real processors.

### 7.1. Caution with Processors

Annotation processors are **code executed during compilation**, not just metadata. If accepting user-submitted sources, enabling processors from the classpath/modulepath can cause untrusted plugins to be loaded right at **compile time**, before even the result-loading step. The demo uses `-proc:none` to avoid that variable; in production, one must whitelist processors, pin versions, isolate environments, and apply appropriate sandbox/process boundaries.

To support processors in an official build, do not silently disable them and assume the output is complete — a framework using MapStruct, Dagger, Lombok, or another processor may need the generated sources to compile successfully. You can control `-processor`, `-processorpath`, `--processor-module-path`, and processor options, and record them in the bundle's manifest.

## 8. Multiple Compilation Tasks and Dependencies Between Versions

### 8.1. One Batch vs. Different Batches

**If multiple units share dependencies of the same version**, compile them in a single task when possible. If split into multiple batches, outputs from batch A must be visible to the compiler of B:

- With the file system, place A's output directory onto **B's appropriate input classpath or module path**.
- With in-memory output, the file manager must implement **read/list/inferBinaryName** paths so the compiler can find A's `.class` files, or use an intermediate layer that actually serves bytes via classpath/memory filesystem.
- Do not just "let `ClassLoader` remember A". The Compiler API uses its own file manager and search locations; it does not automatically query the application loader for every type.
- If using JPMS, distinguish **CLASS_PATH**, **MODULE_PATH**, **MODULE_SOURCE_PATH**, and the module's output location; do not dump everything into the package-oriented classpath when a dependency is a named module.

Outputs should be tied to a **revision/dependency graph**. Do not let revision v2 compile against v1 classfiles simply because an old output dir still contains `Helper.class`, unless that is an **intentionally pinned** dependency version.

### 8.2. Do Not "Overwrite-Add" a Class in the Same Loader

A class loader generally cannot redefine the same binary name with new bytes using `defineClass` as if creating a second class in that same loader. Calling `defineClass` repeatedly with the same name in one loader throws `LinkageError`. If a class is already loaded, modifying the `.class` file on disk **does not** make the JVM automatically replace the bytecode of the old `Class<?>`.

Common update strategy:

1. Compile a **complete bundle** of revision v2 into a new output.
2. Validate/package.
3. Create a **new loader generation** for v2 and load the exact set of classes.
4. Switch a reference point at the application layer (routing/registry/service handle) to the new generation according to a synchronization policy.
5. Let requests that started on v1 finish with v1; only release the old loader when no instances/threads/handles/caches retain it.

**Do not force casts between generations** just because `Class.getName()` is the same. If a common API is desired, define a stable interface/DTO **in the parent loader** and have the generated versions implement it. The boundary should use interfaces or schema-defined data, not pass v1's `demo.generated.Greeter` directly to code expecting Greeter v2.

### 8.3. Class Loader and Resource Isolation

- Default parent-first prioritizes classes already in the parent. Ensure generated namespaces do not collide, or have a tested loader policy (avoid indiscriminate broad child-first for `java.*`).
- `URLClassLoader.close()` releases open resources, but **does not** guarantee immediate class unloading.
- Memory loaders do not have file handles like URL loaders, but `Class<?>`, `MethodHandle`, static caches, thread context class loaders, threads, or plugin objects can still keep the loader alive.
- A global static `Map<String,Class<?>>` can break hot reload: keying solely by binary name does not distinguish loader generations, and values retain old loaders.
- Resource files and class files must belong to the **same bundle version**; do not load `META-INF/services` from an old revision into a new loader when the API expects a different version.
- If safe unloading is required, manage in-flight calls, cleanup hooks, references, and timeouts. GC is not the tool for deciding business rollback ordering.

## 9. Building Durable Compilation Artifacts/Bundles

A production build artifact should include:

```text
CompilationBundle {
  id: logicalName + revision + contentHash
  sourceUnitNames: [binary names...]
  classFiles: Map<binaryName, byte[]>
  resources: Map<relativePath, byte[]>  // if generated
  compiler: JDK build and implementation
  options: --release, classpath, modulepath, processors...
  dependencyDigests: exact resolved dependencies
  diagnostics: captured errors/warnings
  status: BUILDING | VALIDATED | REJECTED | PUBLISHED
}
```

This is an **illustrative design**, not a standalone declared Java type. In the memory example, the `Map<String,byte[]>` output is only the **classFiles portion** of a larger structure.

### 9.1. Build–validate–publish Instead of Direct Overwrite

**A simpler and safer strategy:**

```text
sources + pinned dependencies + compiler options
         |
         v
  isolated task / output staging
         |
      call()
         |
    +----+----+
    |         |
  ERROR       OK
    |         |
 discard     check complete bundle + diagnostics
    |         |
 no publish   verify outputs / source-dependency versions
              |
              v
         publish immutable artifact
              |
              v
         loader generation / atomic route switch
```

If writing output to the filesystem, one can use a UUID/hash-based directory per build and **only publish a manifest/pointer** after all verification steps succeed. An atomic rename operation is only meaningful if the filesystem/path actually supports same-volume atomic move; with `Files.move(...,ATOMIC_MOVE)` one may encounter `AtomicMoveNotSupportedException`. Design a fallback, fsync/durability if required, and do not promise "atomic deploy" solely by moving a directory.

If storing in a database/object storage, upload the immutable bundle first, then update a version pointer conditionally/transactionally. **Do not** scatter half a set of `.class` files and expect the runtime to wait for the rest to appear.

### 9.2. When to Cache Compilation Results?

A proper cache key must represent the inputs that can affect the class output, for example:

- hash of **all source units** after normalizing encoding and paths;
- `--release`, compiler flags affecting semantics, and processor options;
- compiler implementation/version (if deterministic builds are required);
- resolved classpath/modulepath libraries and checksums;
- annotation processor names/versions/config;
- generated resources or feature flag configs embedded into source;
- target platform and code generator policy.

Hashing only the source string of the main class while ignoring helpers, dependencies, or processors can cache bytecode of the **wrong generation**. Do not rely solely on timestamps/mtime, because two different contents can have the same timestamp or remote caches may use different clocks.

**Do not confuse caching compiled bytes with caching loaded Classes:** a bytes bundle can be reused to create different loader generations; whereas `Class<?>` is tied to a specific defining loader, so caching purely by binary name easily mixes versions.

## 10. Managing Concurrent Compilation Jobs

JavaFileManager is not required to be thread-safe across its entire API. If multiple requests ask for builds simultaneously:

- Each job has its **own file manager, diagnostic collector, output store, and task**; output directories/maps must not be shared mutable state.
- If deduplicating the same source hash is needed, a build coordinator can use `ConcurrentHashMap<Key,CompletableFuture<Bundle>>` or a keyed job queue, but must design retry/cancel/timeout policies and cleanup on failure. Do not have multiple compilation tasks write into one map concurrently.
- Pin dependency versions at **build start time**: do not let a task read jar v1 at the beginning and jar v2 at a later stage because an output directory was updated.
- Publish only **completed bundles** via an immutable reference/transactional pointer; requests running v1 hold the v1 reference until they finish.
- If there are memory or metaspace quotas, control output byte counts, compiler task counts, and live loader counts; consider TTL/LRU and GC/lifecycle constraints.

**A small but important note:** `ConcurrentHashMap` makes the map safe per operation, but does not automatically turn a multi-file build into an atomic transaction. You still need a separate build status and publish point.

## 11. Common Errors: Reading Symptoms and Fixing the Right Layer

| Symptom | Common Cause | Resolution |
| --- | --- | --- |
| `ToolProvider.getSystemJavaCompiler()==null` | Runtime lacks `jdk.compiler` or uses a stripped-down image | Use an appropriate JDK; check modules of the runtime image |
| `CompilationTask.call()==false` | Source/option/dependency error | Read `DiagnosticCollector`; do not publish partial artifacts |
| `IllegalArgumentException` when creating `getTask` | Invalid options/arguments | Validate options and unit list; do not build flags from raw user strings |
| `NoClassDefFoundError` at runtime | Missing secondary/nested class, wrong dependency, or class loader | Store **all generated binary names**; check bundle/classpath |
| `ClassNotFoundException` | Loader cannot find binary name | Use `package.Outer$Inner` for nested; check resource/output map |
| `LinkageError: duplicate class definition` | Attempting to define the same FQN twice in one loader | Create a new loader generation for a different revision |
| `ClassCastException` between two versions with same name | Different class identities due to different loaders | Use an API interface in the parent loader or neutral DTO |
| `UnsupportedClassVersionError` | Output major higher than target JVM | Choose the right `--release`; test on the target JDK |
| `NoSuchMethodError` at runtime | Class compiled against a different dependency version than runtime | Pin dependency graph/bundle, check binary compatibility |
| `ClassFormatError` or `VerifyError` | Invalid or corrupted/mismatched bytecode | Check bytes and compiler source; do not mutate `byte[]` after publish |
| Intermittent errors during parallel builds | Unsynchronized sharing of FileManager/output/cache | Separate manager/outputs per job, coordinator for duplicate requests |
| Jar files locked for a long time | `StandardJavaFileManager` or `URLClassLoader` not closed | Use try-with-resources, track ownership |
| Generated code runs old version | Parent loader already has FQN, or loader/cache unchanged | Resolve parent-first collision, create new loader and update route |
| Resources/metadata disappear | File manager only captures Kind.CLASS, skips `getFileForOutput` | Add SOURCE_OUTPUT/resources and loader resource lookup |
| Build reports error but old `.class` remains | Shared output dir, compiler leaves stale files | Compile in clean staging, publish bundle only on success |
| Class loader/metaspace not freed | Remaining Class/MethodHandle/threads/context loader caches | Track references, close resources, lifecycle-aware caching |
| Different builds hit the same cache | Cache key missing dependencies/options/processor/version | Hash all inputs, pin compiler metadata |
| Compilation exceeds CPU/memory budget | Unbounded resources, dangerous processor/cycle input | Limit jobs, timeouts, isolate process/container by policy |

### 11.1. Diagnostics: Source Line, Source URI, Warning

`DiagnosticCollector<JavaFileObject>` stores `Diagnostic` with kind, position, code, and message. An error may have `getSource()==null` or a line number of `Diagnostic.NOPOS`; therefore, do not hardcode that a path/line is always present. For certain compiler options or failures, some information may also be written to the `Writer` passed to `getTask` or default output per the Javadoc. Applications should capture both the diagnostic listener and I/O errors/task exceptions.

**Do not put confidential source into uncontrolled exceptions/logs.** Compiler messages may contain class names, source paths, and code snippets. Attach a build ID and categorize errors, warnings, and notes so users can fix issues without leaking another tenant's source code.

## 12. Security and Trust Boundaries

Compiling Java from a string **does not** make the code safe. Risks to evaluate:

- **Code execution:** loaders and reflection when instantiating or invoking methods can run static initializers, I/O, thread spawning, and network/process access under the process's privileges.
- **Compiler plugins/processors:** annotation processors can execute right at compile time; `-proc:none` in this article only mitigates this risk, it does not make compiled source harmless.
- **Resources:** source intentionally generating vast numbers of classes, annotation processing loops, or nested types can exhaust heap/disk/metaspace.
- **Namespace/dependency confusion:** classes with the same binary name across tenants or versions, parent-first loaders, or wrong module paths can lead to invoking unintended code.
- **Filesystem path injection:** source binary names, package paths, manifest/resource paths, and output dirs must be canonicalized/validated; do not let users directly control the process's write directories.
- **Deserialization/classpath:** do not load jars/processors/bytecode from untrusted sources merely because `CompilationTask.call()==true`.

If you must support running **untrusted external Java code**, consider **OS-level process/container isolation**, least privilege, CPU/memory/network/filesystem limits, monitoring, and process termination. A custom `ClassLoader` within the same JVM is not a complete security sandbox.

## 13. Implementation Checklist

Before considering a runtime compilation pipeline stable enough, answer these questions:

1. **Input units:** have all dependent sources been collected, with valid and non-duplicate package/binary names?
2. **Options:** are `--release`, encoding, classpath/modulepath, and annotation processing explicitly pinned?
3. **Compiler availability:** does the actual runtime have `jdk.compiler` and does the JDK support the target release?
4. **Manager ownership:** who creates and who closes; is the manager reused sequentially or isolated for concurrent tasks?
5. **Output completeness:** does `getJavaFileForOutput` or the output directory record every generated `.class`, including nested/secondary?
6. **Resources:** do processors create sources/resources; are `getFileForOutput` and `SOURCE_OUTPUT` handled?
7. **Diagnostics:** is `call()==true`; do errors/warnings have accurate source locations without leaking tenant data?
8. **Publish:** is the artifact published **only after success + validation** under an immutable version ID?
9. **Version compatibility:** can the target classfile major and all dependencies run on the target JVM?
10. **Classloader:** does each generation have its own loader/resource policy; are parent-first collisions and interface boundaries clear?
11. **Hot reload:** are route switching, in-flight tasks, and old generation cleanup planned?
12. **Cache:** does the key include sources, options, compiler, library digests, and processors?
13. **Concurrency:** is there a build coordinator or output isolation to prevent two tasks from overwriting each other?
14. **Security:** are source code, processors, bytecode, file paths, and runtime execution controlled by trust boundaries?
15. **Resource limits:** are compile timeouts, bytecode size, file handles, threads, and metaspace observed?

If you cannot yet answer questions such as **"can v2 accidentally load v1's `Helper`?"**, **"what output can a failed task leave behind?"**, **"who closes the file manager?"**, or **"if a processor generates additional classes, where does the manager find them?"**, the pipeline does not yet have a clear lifecycle model.

## 14. Self-Check Exercises

**Exercise A — multiple outputs.** A unit `Outer.java` contains a nested class `Outer.Inner` and an anonymous class. The in-memory manager only stores `Outer.class`. What can happen?

**Answer:** When code needs the nested/anonymous class, the loader cannot find `Outer$Inner` or `Outer$1` and may throw `NoClassDefFoundError`. Every class output reported by the compiler must be retained without hardcoding counts or names.

**Exercise B — class identity.** Two bundles v1/v2 both contain `pkg.Service`, loaded by two different `ClassLoader`s. What values can `v1.getName().equals(v2.getName())` and `v1==v2` have?

**Answer:** The names can be equal (true), but the `Class<?>` objects have different identities (false) if actually defined by two different loaders. Use a stable interface in the parent loader to bridge them if needed.

**Exercise C — bytecode target.** A Java 17 host invokes the compiler with `--release 11` for a valid Java 11 source. What is the major version of the `.class` file?

**Answer:** 55, not 61. The host source and the compiled source are two programs with different options.

**Exercise D — task failure.** A task compiling three units returns `false`, yet the output directory contains two `.class` files. Should they be published?

**Answer:** No. That is partial/stale output; discard the failed task's staging and keep the already published bundle intact.

**Exercise E — resource lifetime.** When using the same `StandardJavaFileManager` for two **sequential** tasks, does it need to be closed at the end? Is `flush()` enough?

**Answer:** It must be closed at the end of its lifecycle. Sequential reuse is recommended by the Javadoc, but flush does not replace close; jar/filesystem resources may still remain open.

**Exercise F — annotation processor.** A custom file manager only overrides `getJavaFileForOutput(...,Kind.CLASS,...)`. A processor creates `META-INF/services/example.Service`. Will that resource definitely be stored in the class map?

**Answer:** No. Resources use `getFileForOutput` and a resource location, and do not automatically become `JavaFileObject.Kind.CLASS`. A corresponding output/resource store is required.

**Exercise G — caching.** Source code is unchanged, but a jar dependency changed its implementation. Is a cache key based solely on source hash still valid?

**Answer:** Insufficient. Dependency graph/digest, options, and compiler/processor versions can affect output and runtime compatibility.

**Exercise H — parent-first.** A bytecode loader contains `pkg.Widget` v2, but the parent has already loaded `pkg.Widget` v1. Does overriding only `findClass` guarantee loading v2?

**Answer:** No. Normal `loadClass` checks the parent first; a namespace/parent policy must be designed to avoid collisions, alongside separating loader generations.

**Exercise I — release vs source.** Why is `-source 11 -target 11` on JDK 17 not fully equivalent to `--release 11`?

**Answer:** The first two options mainly restrict syntax and class format, without automatically forbidding references to Java platform APIs introduced in newer releases. `--release` restricts the public platform API available in the target release.

**Exercise J — memory map.** Does `Collections.unmodifiableMap(Map<String,byte[]>)` make all bytecode in the map immutable?

**Answer:** Not yet. The map cannot change structure, but the `byte[]` values can still be modified if someone holds a reference. A snapshot/defensive copy or immutable binary container is needed at trust boundaries.
