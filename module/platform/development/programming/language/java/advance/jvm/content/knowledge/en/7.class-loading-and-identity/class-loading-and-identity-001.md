# What Is Class Loading and Why Doesn't the JVM Load the Entire Program from the Start?

## 1. Short Answer: The JVM Builds the Running Program from the Required Types

A Java program can contain thousands of `.class` files on the classpath/module path, along with many classes in the JDK libraries. **There is no rule stating "at startup, load and initialize all of those classes."** The JVM starts from the initial class (typically the class containing `main`), then loads, links, and initializes other classes/interfaces according to execution needs and related requirements.

For a **non-array class or interface**, *class loading* is the process of finding the **binary representation** of a type by name (typically `.class` bytes in a directory, JAR, module, or source provided by a class loader), and then creating a **runtime representation of the type** so that the JVM can manage it. This is a different task from **running a `static {}` block** or creating an **instance** with `new`.

For example: an application's JAR has a `ReportExporter` class, but the user never clicks the Export button. There is no obligation to **initialize** `ReportExporter` right at startup. However, this observation must not be turned into a rigid claim that `ReportExporter` was definitely never **loaded**: the JVM may resolve or verify early, or frameworks may proactively find/load that type.

A more accurate way to put it:

> The JVM supports **dynamic loading** and can defer much of the work until needed; the exact timing of loading/linking is partly determined by the JVM implementation, while the events that trigger **initialization** must follow language/JVM rules.

### Questions to Distinguish

- **Is the class in the JAR?** That only says the binary code is available on the search path; it does not say the class has been loaded by the JVM.
- **Is the class loaded?** The JVM has a representation of that type; the class is not necessarily initialized.
- **Is the class linked?** Verification/preparation has completed and symbolic references are resolved as needed; `<clinit>` has not necessarily run.
- **Is the class initialized?** Static initializers / initializers of static fields that are not constant variables have been executed according to class initialization rules.
- **Does an object exist?** An instance has been created; a class can be initialized without having any instances.
- **Has a method run?** It could be a static method that needs no instance, an instance method called through an object, or another method leading to a type loading request.

## 2. The Three Phases: Loading, Linking, Initialization

In JVM architecture, the three major phases have an ordering relationship at the semantic level:

~~~text
Class is requested/referenced by an appropriate operation
             |
             v
        LOADING
   find bytes / define Class
             |
             v
        LINKING
  verification -> preparation -> resolution (*)
             |
             v
      INITIALIZATION
  run class/interface initialization logic
             |
             v
       Use the type according to Java semantics

(*) Resolution can occur early or be deferred; not every
    symbolic reference is required to be resolved at the same time.
~~~

### 2.1. Loading — Finding/Defining a Type

For an ordinary type, a class loader can:

1. Receive a request for a **binary name** such as `com.example.service.ReportExporter`.
2. Find an appropriate definition from the loader's source (JAR, directory, module, dynamically generated bytes, ...).
3. Supply the class bytes to the JVM to **define** the type; the JVM builds internal structures for the class/interface and a `java.lang.Class` object representing that type.
4. Record the **defining class loader** relationship, because class identity at runtime is not based on name alone.

`ClassLoader.loadClass(...)` is a Java-level API commonly used to request loading a class, though loader delegation details and byte sources depend on the implementation.

**Do not confuse:** finding a `.class` file on disk does not mean that type's static initializer method has run. Conversely, a runtime type does not always come from an individual `.class` file read directly from disk: the runtime can generate bytecode or define a class from another source.

### 2.2. Linking — Preparing the Class for Correct and Safe Use

*Linking* has three main groups of activities:

| Step | Purpose |
| --- | --- |
| **Verification** | Checks class file/bytecode constraints, stack type validity, control flow, access permissions, and related verification rules |
| **Preparation** | Allocates/prepares memory and structures for static fields; sets default initial values according to rules, handles constants declared via `ConstantValue` |
| **Resolution** | Turns symbolic references to classes, fields, methods, etc. into appropriate runtime references, checking linkability and accessibility |

**Preparation does not mean initialization.** For example, `static int count = 5;` receives the default value `0` during the preparation phase, and then the static field initialization logic assigns `5` during initialization. For `static final int LIMIT = 10;`, which is a compile-time constant variable, the class file may have `ConstantValue`; the rules for assigning constants during preparation differ from executing a runtime expression.

An implementation may **resolve early** many symbolic references, or defer them until actual use. The specification requires preserving conditions such as a class being loaded before linking, verified/prepared before initialization, and linkage errors being thrown at the point where the program performs an action that may require the corresponding linking process. Therefore, **lazy loading does not mean "every class is always loaded at the exact first Java line that mentions its name."**

### 2.3. Initialization — Executing `<clinit>` if Needed

Initialization processes static field initializers and `static {}` in the exact source order of the relevant members, typically combined by the compiler into a class/interface initialization method named **`<clinit>`** in the JVM when needed.

~~~java
class Settings {
    static int port = loadPort();
    static {
        System.out.println("SETTINGS_INITIALIZED");
    }
    static int loadPort() {
        return 8080;
    }
}
~~~

This is an **illustrative code snippet**, not a standalone runnable program since it has no `main`. When `Settings` is initialized, `loadPort()` is called and the static block prints the message; however, merely having `Settings.class` appear in an expression **does not automatically trigger** the static block.

Initialization typically occurs **once per runtime class defined by its corresponding loader**, with synchronization across threads. If one thread is initializing a class and another thread needs that class, the JVM applies initialization coordination rules; it does not arbitrarily run `<clinit>` concurrently multiple times for the same class.

A class may not need its own `<clinit>` if there is no dynamic initialization logic; the type still has an "initialized" state. Also, do not use the phrase "`new` is what loads": a class can already be loaded and initialized from a static call, without any instance at all.

## 3. Why Not Load Every Class at Startup?

### 3.1. Avoiding Work That May Never Be Needed

Suppose a system supports four features:

~~~text
app.jar
├── Main.class                 application startup
├── core/RequestHandler.class frequently used
├── export/PdfExporter.class  only when exporting PDF
├── billing/InvoiceJob.class  only when billing schedule runs
└── admin/MigrationTool.class only when running migration
~~~

If the current request only uses `RequestHandler`, forcing all classes for export, billing, and admin to be loaded and linked immediately could cause unnecessary I/O, verification, metadata allocation, and dependencies. The dynamic loading model allows the JVM **not to do all of that work up front**.

The tree example above is an illustration of **artifacts containing classes**, not a record showing exactly which classes have been loaded in a specific JVM. Class loaders, frameworks, and the JVM may proactively load additional classes due to annotation scanning, discovery, proxies, verification, resolution, or warm-up.

### 3.2. Balancing Startup, Memory, and First-Use Latency

Common benefits and costs:

| Choice | What It Can Improve | Cost to Consider |
| --- | --- | --- |
| Load/link on demand | Less work at startup, avoids processing many unused classes, can reduce resident metadata | First use of a feature may incur latency for loading, verification, resolution, and initialization |
| Controlled eager initialization/preloading | Moves work off the first request, detects errors earlier, warms up | Longer startup, retains extra metadata/objects, and may initialize unneeded parts |
| Classpath/module path scanning by frameworks | Auto-registering components, dependency injection, plugin discovery | A lot of class-loading or reflective access activity before real requests arrive |

Do not infer that **loading accounts for the entire startup cost**. A Java application also has JVM startup, GC/JIT runtime setup, framework initialization, I/O, network connections, config, database migrations, etc. And class loading does not have a simple linear relationship of "fewer classes means the program is always faster" across all workloads.

### 3.3. Supporting Plugins and Dynamic Class Definition

When a system only learns about plugins after startup—for example, plugins placed into a directory/module layer or loaded from a custom source—the class loader mechanism allows loading new definitions on demand. However, simply dropping another JAR into a directory while the JVM is running does not make the application **automatically** recognize the plugin; the system needs discovery logic, loaders/module layers, versioning, and lifecycle management.

Many bytecode generation frameworks create proxies or helper classes at runtime. These types may not exist as corresponding Java source files in the source tree.

### 3.4. Not a Mechanism for "Skipping Broken Dependencies"

Dynamic loading can cause a rarely used feature to only reveal a missing class/method error when that code path is executed. This is a **deferred-error risk**, not a guarantee that the JVM "will permanently ignore" all broken dependencies.

A JVM has the right to link/resolve early within the bounds of the specification; libraries/frameworks may also load/initialize early. You should implement smoke tests for critical plugin/feature paths, rather than treating "main ran successfully" as proof that all classpath dependencies are healthy.

## 4. How Does the JVM Learn About Other Classes?

A class file typically contains a **constant pool** with many **symbolic references**, such as type names `java/lang/String`, `com/example/Feature`, or method descriptors containing parameter types. Those names help the JVM locate classes when resolution/linking is needed.

~~~text
Main.class
  constant_pool:
    class Main
    class com/example/Feature
    Methodref com/example/Feature.run:()V
    class java/lang/String
    ...
~~~

This is a conceptual diagram, not exact `javap -v` output for a real file.

**Having a name in the constant pool does NOT mean:** the JVM has read all class bytes of every mentioned class, initialized all related superclasses/interfaces, or executed the static initializer of any class. Some types may be loaded/resolved for verification or linking; the choice of timing has flexible bounds according to the specification.

Operations that commonly lead to needing to know a class at runtime include:

- `new SomeClass()` when creating an object.
- Accessing a static field that is not a compile-time constant or calling a static method.
- Calling an instance method, checking a cast/`instanceof`, or accessing a field on an object (with the required class/reference).
- Reflection via `Class.forName`, querying methods/fields, `ClassLoader.loadClass`, or framework scanning.
- Method handles, `invokedynamic`, generated proxies, serialization, and service loading when features use them.
- Linking/verifying/resolving other classes that the JVM decides need processing.

**Not every operation above immediately runs the static initializer of every related type.** You must distinguish between *a class being loaded/resolved to understand the type* and *a class having to be initialized due to active use*.

## 5. Cases That Typically Trigger Initialization

According to the JLS/JVMS (in the context of Java 17), notable cases include:

1. **Creating an instance** of a class with `new` (before the constructor executes, the class must be initialized according to rules).
2. **Calling a static method** declared by the corresponding class/interface, e.g. `Feature.run()`.
3. **Reading a static field that is not a constant variable**, e.g. `Settings.port`.
4. **Assigning a static field**, e.g. `Settings.port = 9090`.
5. Certain requests from **reflection** and corresponding runtime APIs, such as `Class.forName(String)`, can also directly require initialization.
6. **JVM startup:** the initial class needs to be loaded/linked/initialized before running `main`.
7. When a class is initialized, its **superclasses** are initialized first, along with **superinterfaces that declare default methods** according to modern rules if not already initialized.

These rules refer to the class/interface **that actually declares the resolved field or method**, not merely the superficial static name in an expression.

### 5.1. Class Literals Do Not Cause `<clinit>` to Run by Themselves

~~~java
Class<?> type = Feature.class;
~~~

This expression creates or obtains a `Class` object representing the `Feature` type for the program, and the JVM may load/link enough required information. However, it **does not trigger initialization of Feature merely because of the class literal**. This is a classic example of why observing "static block hasn't printed" **does not prove the class hasn't been loaded**.

### 5.2. Compile-Time Constants Can Be Inlined

~~~java
class Constants {
    static {
        System.out.println("INIT_CONSTANTS");
    }
    static final int LIMIT = 10;
    static int computed = Integer.parseInt("10");
}
~~~

If a caller references `Constants.LIMIT`, the Java compiler can embed the literal `10` into the caller's bytecode; merely reading this compile-time constant variable does not trigger initialization of `Constants`. In contrast, accessing `Constants.computed` typically leads to `getstatic` and initialization if it has not yet occurred.

This also has ABI consequences: changing a compile-time constant value and only replacing the JAR may not make previously compiled callers pick up the new value; callers need to be rebuilt when appropriate.

### 5.3. Creating an Array Does Not Initialize the Element Class

~~~java
Feature[] slots = new Feature[3];
~~~

Creating an array object may cause the runtime to need the array/element type, but it **does not invoke `Feature.<clinit>`** merely because the elements have type `Feature`. Reference elements default to `null`. If you later actually write `new Feature()`, the class will need to be initialized.

Array types are created by the JVM according to its own rules; **there is no ordinary `[LFeature;.class` file** for each array type. For `int[]`, primitive component types and how the JVM provides `Class` objects for primitives also differ from the mechanism of reading bytes for user-defined classes.

### 5.4. `Class.forName` Has an Initialization Mode

| API / expression | Usually requires load/resolve? | Requires initialization? |
| --- | --- | --- |
| `SomeType.class` | May cause the runtime to need type representation info | **No, not merely for a class literal** |
| `Class.forName("pkg.SomeType")` | Finds/resolves the type via API | **Yes**, with the single-parameter overload for an ordinary class |
| `Class.forName(name, false, loader)` | Loads/links per API contract | **Does not require initialization** |
| `loader.loadClass(name)` | Asks the loader to find the class | **Usually does not** initialize, though another class may have its own side effects from a custom loader |
| `new SomeType()` | Must have the class to create an instance | **Yes**, before the constructor runs |
| `SomeType.nonConstantStatic` | Must resolve the appropriate field | **Yes**, if accessing a static field that is not a constant variable |
| `SomeType.COMPILE_TIME_CONSTANT` | Caller may use an inlined literal | **No, not merely from reading a constant variable** |

In particular, `Class.forName(name, false, loader)` can still load and link, causing class loading/linking errors even without initializing; **`initialize=false` does not mean "do not load the class."**

Do not treat this table as a hard promise about class-loading logs: the JVM can load types early due to linking/verification, and custom loaders can have side effects.

## 6. Complete Java 17 Program: Demonstrating "Having Class Without Being Initialized"

Create a single file **`LazyLoadingDemo.java`**:

~~~java
public final class LazyLoadingDemo {
    static final class OnlyMentioned {
        static {
            System.out.println("INIT_ONLY_MENTIONED");
        }
    }

    static final class Feature {
        static {
            System.out.println("INIT_FEATURE");
        }

        static String run() {
            return "READY";
        }
    }

    static final class Config {
        static {
            System.out.println("INIT_CONFIG");
        }

        static final int LIMIT = 10;
        static int dynamic = compute();

        static int compute() {
            return 99;
        }
    }

    static final class Untouched {
        static {
            System.out.println("INIT_UNTOUCHED");
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("MAIN");

        Class<?> description = OnlyMentioned.class;
        System.out.println("CLASS=" + description.getSimpleName());

        Class.forName(Feature.class.getName(), false,
                LazyLoadingDemo.class.getClassLoader());
        System.out.println("FOUND_FEATURE");

        System.out.println("CONST=" + Config.LIMIT);
        System.out.println("BEFORE_RUN");
        System.out.println("RESULT=" + Feature.run());

        System.out.println("BEFORE_CONFIG");
        System.out.println("DYNAMIC=" + Config.dynamic);

        Class.forName(OnlyMentioned.class.getName());
        System.out.println("FOR_NAME_DONE");
        System.out.println("END");
    }
}
~~~

Compile and run from the directory containing the file:

~~~bash
javac --release 17 LazyLoadingDemo.java
java LazyLoadingDemo
~~~

**Expected stdout that can be verified programmatically:**

~~~text
MAIN
CLASS=OnlyMentioned
FOUND_FEATURE
CONST=10
BEFORE_RUN
INIT_FEATURE
RESULT=READY
BEFORE_CONFIG
INIT_CONFIG
DYNAMIC=99
INIT_ONLY_MENTIONED
FOR_NAME_DONE
END
~~~

### Reading the Output Step by Step

1. `MAIN`: the `LazyLoadingDemo` class is ready to execute the `main` method.
2. `OnlyMentioned.class` yields a `Class` object. `getSimpleName()` is called, yet **`INIT_ONLY_MENTIONED` is not seen**; this illustrates that **a class literal does not require initialization**, and **does not** prove the class is not loaded.
3. `Class.forName(..., false, ...)` requests knowing the `Feature` class **without initializing** it; `FOUND_FEATURE` appears before `INIT_FEATURE`.
4. `Config.LIMIT` is a compile-time constant `10`; the line `CONST=10` does not cause `INIT_CONFIG` to print. This is not a sign that the `Config.class` file has never been loaded.
5. On the first call to `Feature.run()`, the JVM ensures `Feature` is initialized before executing the method: `INIT_FEATURE` appears before `RESULT=READY`.
6. Reading `Config.dynamic` triggers initialization of `Config`: `INIT_CONFIG` appears before `DYNAMIC=99`.
7. Calling `Class.forName(OnlyMentioned.class.getName())` using the single-parameter overload requires initialization: `INIT_ONLY_MENTIONED` appears before `FOR_NAME_DONE`.
8. `Untouched` is never actively used in the program. Not seeing `INIT_UNTOUCHED` means **class initialization was not observed**, but it is **not sufficient to prove the runtime has not loaded/verified that class**.

The most important point of the example is not guessing how many classes were loaded from stdout, but **using static initializers to separately observe initialization events**. To observe loading, use the tooling logs in Section 7.

### What If `false` Is Changed to `true`?

The snippet:

~~~java
Class.forName(Feature.class.getName(), true,
        LazyLoadingDemo.class.getClassLoader());
~~~

is a **variant for separate experimentation, not the original code of the exercise**. When `initialize=true`, `INIT_FEATURE` will appear right at that `Class.forName` call, before `FOUND_FEATURE`. At the subsequent `Feature.run()` call, the static initializer will **not run again** for the same runtime class. Similarly, only initializing another class with the same binary name under a different defining loader constitutes a different class identity to consider separately.

## 7. Observing Actually Loaded Classes with JDK Tools

### 7.1. `-Xlog:class+load=info` on HotSpot / JDK 17

With OpenJDK/HotSpot supporting Unified Logging:

~~~bash
java -Xlog:class+load=info LazyLoadingDemo
~~~

You will see many class-loading log events in addition to the example's stdout. The number of log lines, module/JAR/loader names, and order can vary by JDK, classpath, configuration, or how the implementation performs resolution; therefore, **an "exact stdout" is not provided for logging-enabled mode**.

Write the class-load log separately to a file:

~~~bash
java -Xlog:class+load=info:file=class-load.log:uptime,level,tags LazyLoadingDemo
~~~

Then filter for lines containing the app name:

~~~bash
# Bash on Linux/macOS
grep 'LazyLoadingDemo' class-load.log

# PowerShell on Windows
Select-String -Path class-load.log -Pattern 'LazyLoadingDemo'
~~~

Note: JDK classes such as `java.lang.Object`, `java.lang.String`, class loaders, I/O, and many runtime components can be loaded before `main` prints its first line. Saying that a JVM startup literally loads only the `Main` class is an **inaccurate** description.

The older form `-verbose:class` can also be used with many Java launchers to view class-loading information. For production systems, enabling high-volume class-load logging can increase log volume and I/O cost; try it in a test environment.

### 7.2. `javap` Is Not a Class-Load Log

~~~bash
javap -v LazyLoadingDemo
javap -c -p LazyLoadingDemo
~~~

`javap -v` shows **class file structure** and constant-pool references, while `javap -c` displays bytecode. This is **static analysis of the class file**; it does not tell you the runtime order in which other classes were loaded.

For example, `javap` can show references to `Feature.run()` and `Config.dynamic`. However, **a `// Method ...` comment appearing in the disassembly does not prove that the method or `<clinit>` has executed**.

### 7.3. A JAR Containing a Class Does Not Mean the JVM Loaded All of Them

~~~bash
jar tf app.jar
~~~

The command above (if `app.jar` exists) only lists files inside the archive. It does not launch the application and is not a statistic of classes loaded by the JVM. This is the difference between **being on the classpath**, **being loaded**, **being linked**, and **being initialized**.

## 8. ClassLoader: Who Defines the Class Also Matters

A Java class is identified at runtime by its **binary name combined with its defining class loader** (for non-hidden types and the standard model). Two different loaders can define two types with the **same binary name**, yet the JVM still treats them as **two different runtime classes**.

A conceptual example:

~~~text
Loader A defines com.acme.Plugin  ---> Class A
Loader B defines com.acme.Plugin  ---> Class B

Same binary name; different defining loader;
therefore Class A != Class B at runtime.
~~~

Consequences:

- Casting between two incompatible types can cause `ClassCastException`, even though both are called `com.acme.Plugin` in logs.
- `static` fields and the initialization process belong to **each runtime class** separately, not shared based on name alone.
- In application server, plugin, and test runner environments, `ClassCastException: Foo cannot be cast to Foo` can involve multiple class loaders, not necessarily wrong class source code.

### 8.1. Bootstrap, Platform, Application Loaders

In modern JDKs, you commonly see:

- **Bootstrap class loader:** the VM's foundational mechanism, loading many core platform classes such as `java.lang.Object`; in the `Class.getClassLoader()` API, bootstrap classes typically return **`null`** by contract.
- **Platform class loader:** loads many module/platform classes according to the JDK implementation mechanism.
- **Application/system class loader:** typically loads the application from the classpath/module path defined by the launcher.

Actual loader relationships can be complex, especially with module layers, application servers, and plugin frameworks. **Parent-first delegation** is the common default model of `ClassLoader.loadClass`: ask the parent loader first before searching for the class itself; **it is not a law forbidding custom loaders from doing child-first** where permitted.

Distinguish:

- **Initiating loader:** the loader that receives/initiates the class-loading request.
- **Defining loader:** the loader that actually defines that class. These two concepts can differ due to delegation.
- **Runtime package** is also affected by the defining loader; two classes with the same package name string but different loaders are not automatically in the same runtime package for access checks.

### 8.2. ClassLoader Context and the Module System

Many frameworks read the **thread context class loader** when discovering plugins/resources so they are not restricted to the library code's loader. With the Java Platform Module System (JPMS), the module graph and readability/export rules also affect resolution/access capabilities.

However, a class loader **does not by itself handle** complete dependency injection, discovery, or module lifecycle management. It is the class loading/identity layer; much of the application-level work is performed by frameworks.

## 9. Loading, Initialization, and `new` Are Not Synonymous

| Situation | What Actually Happens |
| --- | --- |
| `obj = new Service()` | Requires class `Service` to be initialized; creates an instance, calls constructor per rules |
| `Service.runStatic()` | May initialize `Service` but **does not create a Service instance** |
| `Service.class` | May create/obtain `Class<Service>`; does not require running the static initializer |
| `new Service[5]` | Creates a **Service reference array** with null elements; does not create 5 Service instances |
| `Class.forName("Service", false, loader)` | Can load/link Service but does not require initialization |
| `Object o = new Object()` | Does not prove the JVM has loaded every class extending Object across the entire classpath |
| `main()` starts | The class running main has been initialized, along with required dependencies; **not all classes in the entire program** |

This is also why the phrase "the JVM reads Java files when running" is inaccurate for the standard mechanism: the launcher works with class/module artifacts; class loaders supply appropriate binary representations to the JVM. `.java` source files are not the default input for every bytecode load, even though the Java launcher supports a source-file execution mode at the development tool level.

## 10. Errors Revealed at Different Times Due to Dynamic Loading/Linking

### 10.1. `ClassNotFoundException` Differs from `NoClassDefFoundError`

| Symptom | Typical Context | What to Check |
| --- | --- | --- |
| `ClassNotFoundException` | Reflective/loader API was asked to find a class by name but could not find it, e.g. `Class.forName("missing.Plugin")` | Binary name, module/classpath, JAR, case-sensitive path, passed loader |
| `NoClassDefFoundError` | The JVM needed a class at runtime but its definition is unavailable/unusable, or a class previously failed initialization | Root cause (often in `Caused by`), classpath/version, prior class initialization |
| `ExceptionInInitializerError` | An exception escaped abnormally from class initialization code (according to Throwable wrapping rules) | Static fields/blocks, configuration, I/O, recursive initialization |
| `UnsupportedClassVersionError` | The class file was compiled for a higher JVM version than the runtime supports | Bytecode major version, actual running JDK, and `--release` |
| `ClassFormatError` / `VerifyError` | Invalid binary class file or bytecode/verification rules | Class file build/transform/obfuscation, dependencies and versions |
| `NoSuchMethodError` / `NoSuchFieldError` | Caller references a member with a name/descriptor that no longer matches the runtime binary | Jar hell, API/ABI changes, transitive dependencies |

**Important:** `NoClassDefFoundError` does not always mean **the `.class` file does not exist**. For example, `<clinit>` of a class fails on the first initialization attempt; a subsequent use may receive `NoClassDefFoundError: Could not initialize class ...`. The JVM does not arbitrarily "re-run the static initializer" to fix the error state of the same class.

### 10.2. Errors Can Appear Late

For example, a `PdfExporter` class depends on a library used only during export. If startup does not need to resolve or initialize the export path, the application may run normally until the user clicks Export. At that point, the JVM or framework needs the related class and the dependency error appears.

However, do not promise that "the error will definitely only occur when Export is clicked": the JVM is allowed to perform some early linking; frameworks may also preload/scan. The **exact error timing** must be based on the stack trace and runtime configuration.

### 10.3. Practical Diagnostic Workflow

1. Identify **which class** failed and **which operation** triggered it: load by name, method call, field access, instance creation, reflection, or plugin discovery.
2. Check the artifact containing the class, classpath/module path, and JDK version: `java -version`, build target, actual JAR present at runtime.
3. Find the **first caused by** in the stack trace; do not just read the `NoClassDefFoundError` message at the end.
4. Enable selective class-load logging in a test environment, then verify **which source the class was loaded from**.
5. Check loader identity when an app server/plugin has multiple loaders. Use `someObject.getClass().getClassLoader()` to inspect an object's loader when appropriate (bootstrap may be null).
6. If the error is in static initialization, check initialization order, side effects, recursive dependencies, and required configuration **before the first active use**.
7. Test rarely used feature paths with smoke tests instead of testing only startup.

## 11. Class Unloading: Not Every Loaded Class Exists Forever

The JVM has a **class unloading** mechanism under appropriate conditions. For classes defined by a user-defined loader, the ability to reclaim class metadata is typically tied to the **defining loader** and related structures no longer being reachable, along with GC/implementation rules.

There is no promise that `System.gc()` will immediately unload a class. Loading a class multiple times by the **same loader** in the normal way does not mean creating a new class definition each time; the loader must follow identity/definition constraints, and the JVM manages the loaded/linked/initialized state of the runtime class.

A **class loader leak** can prevent class metadata and related objects from being reclaimed: for example, holding a reference to a plugin loader in a static cache, thread, or thread context class loader after the plugin has been shut down. When designing hot-reload, you must manage resources, threads, caches, and static references, not just delete the JAR file.

HotSpot typically has a **Metaspace** region to store various kinds of class metadata, but the region name, allocation policy, and GC are implementation details, not a requirement that every JVM must use an identical layout.

## 12. Key Misconceptions to Drop

1. **"If an app has 10,000 classes, the JVM loads all 10,000 before main."** There is no such rule.
2. **"Having a name in the constant pool means the class is loaded."** No; a symbolic reference may still be awaiting resolution.
3. **"Lazy load means a class is loaded at the exact first statement that uses it."** No; verification/resolution can cause early loading, and loaders/frameworks can also preload.
4. **"A loaded class means its static block has run."** False; initialization is a separate phase.
5. **"`Class.forName(..., false, ...)` does not load the class."** False; `false` controls initialization, not disabling loading.
6. **"`SomeType.class` definitely runs `<clinit>`."** False; a class literal does not initialize by itself.
7. **"Reading a `static final int` always initializes the class."** False if it is a compile-time constant variable used according to Java rules.
8. **"`new Widget[10]` creates 10 Widget objects."** False; it is one array object containing null reference elements.
9. **"`ClassNotFoundException` and `NoClassDefFoundError` are the same."** False; the APIs/contexts and causes differ.
10. **"If the app reaches main, all dependencies are error-free."** False; unused code paths can fail later.
11. **"Two classes with the same full name are always the same class."** False; the defining class loader is part of identity.
12. **"The lazier class loading is, the faster it always is."** False; there are trade-offs between startup vs. first-use latency and dynamic overhead.
13. **"Each class is initialized only once across the entire operating system."** False; the state belongs to each runtime class/loader within its respective JVM process.
14. **"When class initialization fails, the next access automatically re-runs the initializer."** There is no such arbitrary retry mechanism for the same class that has entered an error state.
15. **"`javap` proves a class is loaded in the process."** False; `javap` reads a static class file, whereas class-load logs observe runtime.

## 13. Self-Check Questions

1. What does class loading include? **Finding an appropriate binary representation and creating a runtime type**, not automatically running `static {}`.
2. What parts does linking have? **Verification, preparation, and resolution**, with resolution timing being flexible within specification bounds.
3. What is the precondition before initialization? **The class has completed loading, verification, and preparation**, and initialization dependency rules are respected.
4. Why can't "didn't see INIT" be used to prove "not loaded"? Because **static initializers only reflect initialization**; the class may have been loaded/linked earlier.
5. Does reading `Config.LIMIT`, a compile-time constant, cause `INIT_CONFIG` to run? **Not merely because of this read**.
6. What is the main difference between `Class.forName(name)` and `Class.forName(name,false,loader)`? **The single-parameter overload requests initialization; the overload with `false` does not request initialization**.
7. Does `new Feature[3]` call the constructor of three Features? **No**.
8. Why might a class in a JAR not be loaded yet? Because a JAR is an **available source of bytes**, which does not mean every class is used/linked at startup.
9. Do two loaders defining the same binary name create the same runtime class? **No**.
10. Why might a dependency error only occur on the 100th request? Because that code path may only start **loading/linking/initializing** the dependency when that request uses the feature; though it can also be detected earlier.
11. What does `-Xlog:class+load=info` observe? **Class-loading events recorded by a JVM that supports that logging mechanism**; not a list of static initializers that have run.
12. Should all classes be preloaded to avoid every error? **Not by default**; choose a startup/warmup/smoke test strategy based on latency, memory, and reliability.
13. Is class unloading guaranteed immediately when setting a reference to null? **No**; GC, class loader reachability, and the implementation determine this.
14. Can `NoClassDefFoundError` come from a previous initialization error? **Yes**, not only from a missing class file.

**Conclusion:** class loading is the process by which the JVM receives and defines a **runtime type**, not reading every file of the program into RAM immediately and not running `static {}`. The JVM supports dynamic loading and linking to reduce unnecessary work and serve flexible plugin/runtime systems, though it is permitted to perform some resolution early. Clearly distinguishing **loading → linking → initialization**, **class in JAR → class loaded → class initialized**, and **class identity = binary name + defining loader** is the foundation for understanding startup, first-use latency, and classpath errors in Java applications.
