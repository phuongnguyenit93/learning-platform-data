# The Path from a Cold Method to Hot Code in the HotSpot JVM

## 1. The Core Question: Why Doesn't Java Compile and Optimize Every Method Immediately?

When running a Java program on the **HotSpot JVM**, class files carry **bytecode**. HotSpot typically starts executing new code with an **interpreter**, observes runtime behavior, and can then use **Just-In-Time (JIT) compilation** to turn frequently used methods/loops into **machine code**.

A rarely run method (*cold method*) may never need to be JIT-compiled. A method called many times or containing a long-running loop can become **hot code** and is worth paying the compilation cost so that subsequent runs are faster.

```text
.class / bytecode
       |
       v
Class loading + verification + linking when needed
       |
       v
Interpreted execution (tier 0)
       |
       +--- rarely called, rarely run ---> keep interpreted or another strategy
       |
       +--- many invocations / loop backedges
       |             |
       |             v
       |       profiling + compilation policy
       |             |
       |             v
       |       compilation queue / compiler threads
       |             |
       |             v
       |          C1 compiled code
       |             |
       |         more runtime profiles,
       |         compiler finds it worth optimizing
       |             |
       |             v
       |          C2 compiled code
       |             |
       |       guard/assumption fails?
       |             |
       |             v
       +------ deoptimization / interpreter / recompile
```

This is an **intuitive diagram**, not a mandatory sequence for every method. There are tier-skipping paths, methods that only go through C1, methods that are never compiled, compilation occurring mid-loop via **OSR**, and cases where the JIT invalidates or replaces an old machine code version.

### Three Concepts to Distinguish

1. **Warm-up:** the initial period when the program runs as classes are loaded, runtime information is accumulated, and the JIT can begin optimizing.
2. **Hotness:** the VM's internal assessment that a method/loop is important enough to compile or recompile.
3. **Tiered compilation:** the policy HotSpot uses across different execution/compilation levels to balance **startup time**, **profiling overhead**, **peak performance**, and **compilation cost**.

**There is no contract in the Java Language Specification** stating that "on the 10,000th call, the method is guaranteed to transition to C2." Hotness thresholds and tier transition paths belong to the **HotSpot implementation**, depending on the JDK build, JVM flags, runtime load, and workload.

## 2. Java Source, Bytecode, and Machine Code Are Three Different Things

For example:

```java
static int square(int x) {
    return x * x;
}
```

After using `javac`, the class file contains bytecode representing loading the parameter, multiplying integers, and returning the result. At runtime, HotSpot has several options to execute the exact semantics of those instructions:

- The **Interpreter** reads/executes bytecode in the runtime engine.
- The **C1 compiler** produces machine code quickly and can collect additional profiling depending on the tier.
- The **C2 compiler** uses more complex analyses/optimizations to produce optimized machine code.
- The JIT may **inline** `square` into its caller, so you will not always see a separate native call to compiled code for `square`.

```text
Java source: square(x)
        |
      javac
        |
        v
Bytecode in square.class
        |
   HotSpot runtime
        |
        +--> Interpreter executes bytecode
        +--> C1 creates compiled machine code
        +--> C2 creates aggressively optimized machine code
                  |
                  +--> may inline square into the caller
```

**The JIT does not modify `.class` files on disk when optimizing in-process.** Machine code generated by the JIT is stored in runtime structures (such as the **code cache/nmethods**), used when appropriate, and can be replaced/invalidated.

### 2.1. What Does "Compiled" Mean Here?

`javac` already compiled **source → bytecode** before execution. The JIT is a different step: **bytecode/runtime IR → machine code for a specific CPU**, performed at runtime.

Therefore, both of the following statements can be true:

- "Java is compiled before running" — true at the stage where `javac` produces bytecode.
- "HotSpot can interpret bytecode and then JIT-compile it while running" — true regarding runtime execution.

### 2.2. Not Every JVM Requires C1/C2

The JVMS specifies **bytecode behavior**; it does not require an interpreter named HotSpot, C1/C2, tiered compilation, or counting invocations in a specific way.

This article focuses on **HotSpot with tiered compilation supported**, especially easy to practice with **JDK 17+**. Other JVMs like OpenJ9/GraalVM or other HotSpot configurations may have their own compiler pipelines.

## 3. Why Do Cold Methods Usually Start in the Interpreter?

The **Interpreter** has the advantage of **not needing to pay the full cost of optimizing native code before the first use**. If a method only runs once during startup, an expensive C2 compile can waste more CPU/memory than the time it saves.

For example:

```java
static void printHelp() {
    System.out.println("Usage: ...");
}
```

If `printHelp()` only runs once when the user passes `--help`, the interpreter can execute it fast enough; a multi-pass JIT compilation is unlikely to yield net value.

Conversely:

```java
static int decode(int x) {
    return (x * 31) ^ (x >>> 3);
}
```

If `decode` is called millions of times in a data-processing path, the JIT cost can be amortized by repeated gains.

### 3.1. Startup Time vs Steady-State Performance

- **Startup:** getting the application running and returning the first result quickly.
- **Warm-up:** the JIT collects profiles and compiles/recompiles; speed may vary.
- **Steady state:** hot paths can run more optimized compiled code.

However, **there is no promise that steady state arrives after exactly N seconds**. A web service may continuously encounter new methods called for the first time upon each new request, new plugin, or new class loader.

### 3.2. Interpreted Does Not Mean "Unsafe"

Whether interpreted or compiled, Java code must still obey the appropriate semantics (types, exceptions, concurrency rules, access checks). The JIT is not allowed to validate incorrect Java behavior just because it runs faster.

### 3.3. The Interpreter Is Not a Permanent Lower Tier

When a method/loop becomes hot, the compilation policy can request creating a compiled entry; subsequent calls can enter native code, or for a long loop the JVM can transition mid-execution via OSR.

## 4. Hotness: Invocation Counters and Loop Backedges

HotSpot tracks **method invocation counts** and **loop backedge counts** (how many times execution loops back) along with other profiling information to decide whether to compile/recompile.

Two very different signal sources:

| Signal | Example | Meaning |
| --- | --- | --- |
| **Method invocation count** | `process()` is called repeatedly from a request handler | Method is hot due to **many method entries** |
| **Loop backedge count** | `process()` is called only once, but the loop has millions of iterations | A method/loop is hot even with **few invocations** |

### 4.1. Many Calls, Little Work Each Time

```java
static int addOne(int x) {
    return x + 1;
}

static int callManyTimes() {
    int result = 0;
    for (int i = 0; i < 100_000; i++) {
        result += addOne(i);
    }
    return result;
}
```

This is **illustrative code** inside a class, not a standalone `main` program. `addOne` is called many times, but the JIT may **inline** it into the caller; therefore, profiling logs will not necessarily show a standalone compiled native method in all circumstances.

### 4.2. One Call, Very Long Loop

```java
static long bigLoop(int n) {
    long sum = 0;
    for (int i = 0; i < n; i++) {
        sum += i;
    }
    return sum;
}
```

If `bigLoop(1_000_000)` is called once, the **invocation count is only one**, but the **backedge count** can be very large. That can trigger **on-stack replacement (OSR)**.

### 4.3. "Hot Method" and "Hot Loop" Are Not Necessarily the Same

A method can stand out because of call count; a loop in another method stands out because of iteration count. HotSpot may compile a method entry separately, compile an OSR entry separately, or either one depending on policy/runtime state.

**Do not treat the number of source-code loop lines or method length as a direct measure of hotness.** Runtime execution frequency and compiler heuristics matter more.

## 5. Tiered Compilation: The Five Execution Levels of Traditional HotSpot

The tiered compilation model in HotSpot C1/C2 is commonly described as **levels 0–4**:

| Level | Engine | Key Point |
| --- | --- | --- |
| **0** | **Interpreter** | Executes bytecode; can collect runtime information |
| **1** | **C1, simple compilation** | C1 native code, **does not collect full profiling** |
| **2** | **C1, limited profiling** | C1 with basic counters, lower overhead than full profiling |
| **3** | **C1, full profiling** | C1 with richer instrumentation/profiling to support decisions and C2 |
| **4** | **C2 optimization** | Heavily optimized native code, using profiles/assumptions when appropriate |

Names you may encounter in OpenJDK:

```text
CompLevel_none                  (0)
CompLevel_simple                (1)
CompLevel_limited_profile       (2)
CompLevel_full_profile          (3)
CompLevel_full_optimization     (4)
```

These names are **HotSpot implementation details**. **Do not infer that execution must always go sequentially 0 → 1 → 2 → 3 → 4.** In practice, a very common path is:

```text
Interpreter (0) ---> C1 with profiling (3) ---> C2 (4)
```

And it can also be:

```text
Interpreter (0) ---> C1 limited profiling (2)
                        |
                        v
                     C1 full profiling (3)
                        |
                        v
                        C2 (4)
```

All of the models above are **only possible paths**, not a rigid timeline for every method.

### 5.1. Why Are There Multiple C1 Tiers?

C1 generally compiles faster than C2, so it can provide native code earlier. Level 3 collects more detailed profiles so C2 has data for speculative optimizations, but collecting profiles also has overhead.

Level 2 can be used when compilation queues/load situations make running C1 full profiling too long not worthwhile yet, and it can transition later. Level 1 can suit methods that do not need profiling or under special policies.

### 5.2. Is C2 Always Faster Than C1?

There is no guarantee that **every individual method** running C2 will be faster than C1 in every microbenchmark. C2 generally aims for peak optimization, but code size, profile quality, JIT decisions, CPU microarchitecture, warm-up, and compiler overhead all have an impact.

Performance claims must be measured end-to-end under the target workload, rather than just seeing "level 4" and declaring an exact percentage speedup.

### 5.3. Tier Names May Not Appear the Same on Other JVMs

Tools may show level numbers in HotSpot logs; other JVMs or HotSpot builds without C2 may have their own mapping/compilation policies. When reading logs, check `java -version` first.

## 6. From Invocation/Backedge Counters to the Compile Decision

A compilation policy must balance two types of cost:

1. **The cost of running interpreted or C1 profiling** on each execution.
2. **The cost of compilation, code cache, compile threads, profile storage**, and the risk that compiled code is no longer used much.

Trigger thresholds can be influenced by:

- Invocation/backedge counts.
- The rate of increase of those counts and method activity.
- C1/C2 queues, number of compiler threads, and CPU load.
- The current execution tier and the quality of available profiles.
- Compile directives, excluded methods, and JVM flags.
- Code cache availability.
- Deoptimization/uncommon traps or the state of compiled versions.

**Do not write "`CompileThreshold=10000` means on the exact 10,000th call every method becomes C2."** Tiered policy has multiple thresholds and rules combining counts/counters, plus queue/load heuristics.

### 6.1. Thresholds Are Not an API Contract

There are HotSpot flags such as:

```text
-XX:CompileThreshold=...
-XX:TieredStopAtLevel=...
-XX:+TieredCompilation
-XX:-TieredCompilation
```

However, flag interactions vary across JDK/VM versions. With **tiered compilation** enabled, **`CompileThreshold` alone** should not be treated as an exact way to control every tier transition path.

### 6.2. Compilation Thresholds Are Not Measured Simply by Wall Time

A method that runs for 10 seconds because it is waiting on I/O may have very few invocations and no hot loop backedges. Conversely, a compute method running for a few hundred milliseconds may have already exceeded multiple counters.

"Hot" does not mean "the method appearing longest in a thread dump" or "the method spending the most wall-clock time blocked."

### 6.3. Compilation Queues

When the policy decides a method is worth compiling, the request can enter a **compiler queue**. A compiler thread works independently of mutator threads, producing an nmethod in the **code cache**. While waiting, the application can continue running in interpreted/C1 code.

```text
Application thread:
  interpreted / C1 execution --- continues work --->
                    |
                    +-- enqueue method for C2 compilation
                                      |
Compiler thread:                  compile, optimize
                                      |
                                      v
                                publish nmethod
                                      |
Application later:                    use compiled entry
```

Because compilation can happen asynchronously, **the moment a method transitions tiers is not determined by a single source line**.

## 7. Method Data and Profiling: How Does the JIT Learn from Runtime?

In HotSpot, **MethodData** and runtime profiling structures can record signals such as:

- Invocation/backedge counts where needed.
- Branch frequencies of commonly taken paths.
- Runtime types observed at call sites.
- Exception types or control-flow shapes where instrumentation is present.
- Information supporting inlining, virtual-call optimization, and loop optimization.

For example:

```java
interface Handler {
    int apply(int x);
}

static int dispatch(Handler h, int x) {
    return h.apply(x);
}
```

This is **illustrative code without `main`**. If in every actual run `h` is a single implementation, the profile can help the JIT optimize the call site. If another implementation appears later, the optimization assumption may no longer hold, leading to deoptimization/recompilation when needed.

### 7.1. Monomorphic, Bimorphic, Megamorphic — Understood by Call Site

A call site can observe:

- **Monomorphic:** one receiver type is dominant/unique in the profile.
- **Bimorphic:** two prominent receiver types.
- **Megamorphic:** many receiver types, making type-specialized optimization strategies less effective.

These are **runtime profile descriptions**, not fixed properties of the `interface` syntax. There is no single implementation-count formula that guarantees every JIT decision.

### 7.2. Profile-Guided Optimization Can Be Speculative

HotSpot can optimize based on observed information accompanied by **guards**. If runtime takes a rarely seen path or a new receiver type appears, the VM must preserve correct behavior — via a slow path, guard failure, deoptimization, or recompilation.

**Speculation does not allow the JIT to violate Java semantics.**

### 7.3. Profiling Does Not Mean Every Branch Has Been Executed

If a rare exception branch never appeared during warm-up, C2 can optimize for the common path, but it must still have a correct mechanism to handle the exception when it occurs. A benchmark that only warms up the "happy path" does not prove production code will always stay in that condition.

## 8. C1 vs C2: Compilation Cost and Code Quality

### 8.1. C1 — Early Native Code, Can Attach Instrumentation

C1 is often described as the **client compiler**, designed to be relatively fast and used in lower tiers to improve startup/warm-up without paying the full cost of C2. When in a profiling tier, C1 can insert instrumentation to collect type/branch/counter data.

### 8.2. C2 — Deeper Optimization

C2 is often described as the **server/optimizing compiler**. Techniques may include:

- Inlining across method boundaries when profile/size allow.
- Devirtualization/speculative type-check optimization.
- Common subexpression elimination and constant propagation.
- Loop optimizations (unrolling, range-check elimination, etc., when safe).
- Escape analysis and scalar replacement under suitable conditions.
- Dead-code elimination and other IR/low-level optimizations.

Not every technique is applied to every method; the optimization pipeline depends on compiler IR, flags, method shape, CPU capabilities, and runtime assumptions.

### 8.3. A Method Can Have Multiple Compiled Versions

A method can have:

- A compiled C1 entry (tier 3).
- A compiled C2 entry (tier 4).
- An OSR nmethod for a loop backedge.
- Older compiled versions in a state no longer used for method entry.
- Code inlined into other callers.

**Do not conflate "one Java method" with "a single immutable piece of machine code."**

### 8.4. "The JIT Turns Interpreter Into C2 and Stops" Is an Incomplete Diagram

The JIT does not just run once. The runtime can continue profiling, raising tiers, deoptimizing and recompiling if the environment changes, or managing the code cache.

## 9. OSR — Switching to Compiled Code Mid-Loop

**On-Stack Replacement (OSR)** is especially important for the topic "from a cold method to a hot path."

Suppose a method is called just once but runs a long loop:

```java
static long aggregate(int n) {
    long result = 0;
    for (int i = 0; i < n; i++) {
        result += (i & 255);
    }
    return result;
}
```

If the interpreter/lower level detects hot **loop backedges**, HotSpot can compile an **OSR version** of the method for a specific **bytecode index (BCI)**, and then swap the execution state while the loop is still running.

```text
Thread runs aggregate(n)
     |
     v
Interpreter enters loop
     |
     +-- very many iterations --> backedge counter exceeds appropriate threshold
     |
     +-- requests OSR compilation at loop-entry/backedge BCI
                         |
                         v
                  OSR compiled nmethod
                         |
             thread in the loop transitions into new code
                         |
                         v
                  continues with exact local/stack state
```

### 9.1. OSR Differs from Method-Entry Compilation

- **Normal compiled entry:** subsequent calls to the method can enter machine code from the start.
- **OSR compiled entry:** a frame currently executing a loop can be switched to compiled execution **without returning and calling the method again**.

**A compiled OSR version does not automatically mean the normal method entry is already at level 4.** Logs usually have a distinct marker for OSR, such as the **`%`** character and `@ bytecodeIndex`.

### 9.2. Sample Log, Not Fixed Output

```text
27   15 %     3       HotMethodDemo::loop @ 4 (25 bytes)
```

This is an **example pattern similar to events observed in a HotSpot test**, not a guarantee of timestamps/compile IDs/tiers in every run. The `%` marker indicates OSR compilation; `@ 4` indicates the relevant bytecode index.

### 9.3. When Does OSR Not Appear?

- The loop has not run enough for the policy to consider it worth compiling.
- The method was already compiled at a suitable level from the start.
- The JIT is disabled or compilation is restricted by flags.
- The workload/JIT optimizer changes the loop shape or code path.
- The VM chooses another strategy or compilation does not finish before the loop ends.

**Do not write a test asserting "every loop over 10,000 iterations must have OSR."**

## 10. Deoptimization — When an Optimization Was Once Valid but Assumptions No Longer Hold

The JIT often optimizes for **the most frequently observed path**. However, new situations can arise at runtime.

For example:

```java
interface Worker {
    int work(int x);
}

final class FastWorker implements Worker {
    public int work(int x) { return x + 1; }
}

final class AlternateWorker implements Worker {
    public int work(int x) { return x * 2; }
}
```

If a call site usually only sees `FastWorker`, the JIT can optimize/inline based on the profile. When `AlternateWorker` appears, a guard/class-hierarchy assumption may need to be checked, and the runtime can **deoptimize** an nmethod if the assumptions of the optimized version are invalidated.

### 10.1. What Does Deoptimization Do?

Intuitively:

1. The runtime detects that compiled code no longer matches the conditions it assumed.
2. The JVM creates/restores an **interpreter-compatible execution state** when needed.
3. The thread can continue via the interpreter/other code without losing Java semantics.
4. The policy can recompile with a more suitable profile/assumptions.

Not every new receiver type triggers deoptimization. Optimized code may already contain checks/slow paths; specific deoptimization behavior depends on the version and compiler strategy.

### 10.2. Uncommon Traps

HotSpot has an **uncommon traps** mechanism for paths assumed to be rare, such as a branch/type not previously profiled or a situation requiring a fallback to the runtime.

In diagnostic logs, you may see the term `uncommon_trap`; that by itself does not prove the application has an exception or bug.

### 10.3. "Made Not Entrant" and "Made Zombie"

A compiled code version can be marked **not entrant**: the runtime no longer uses it for new method entries, for example because a better-optimized version exists or old code needs to be invalidated. Code cache lifecycle management can later transition old code to the **zombie** state when no frames are using it appropriately.

These states **are not Java objects being reclaimed by GC** in the application heap sense, and that log line is not necessarily an error.

### 10.4. Deopt Must Not Change the Correct Result of the Program

If the compiler optimizes with assumptions, the JVM must still preserve Java semantics, including return values, exceptions, memory visibility, and side effects per the specification.

## 11. Code Cache — Where Does JIT Machine Code Live?

HotSpot stores compiled methods in the **code cache**, a set of runtime memory regions for code generated by the JVM/JIT. It is separate from the Java heap that holds application objects.

```text
Java heap:
   Object instances, arrays, class mirrors

Native/runtime memory:
   Code cache:
     - compiled C1 methods
     - compiled C2 methods
     - runtime/adapters/stubs per VM
   Metaspace:
     - class metadata, method metadata per HotSpot
```

This diagram is only a conceptual classification; specific code cache segments and the scope of each group vary by JDK/build.

### 11.1. Compilation Is Not Free

JIT costs include:

- CPU for compiler threads.
- Memory for compiler data structures and profiling.
- Code cache space for compiled code.
- Instruction-cache pressure from machine code.
- Deoptimization/recompilation if profiles change.

It does not make sense to force compilation of every method at startup just because compiled code can run faster than interpreted code.

### 11.2. What Happens When the Code Cache Is Full?

If the code cache reaches its available limit, the JVM may restrict or disable further JIT compilation; the app can continue running, but throughput/latency may degrade. Exact semantics depend on HotSpot version/options.

Check logs and metrics before arbitrarily increasing the code cache.

### 11.3. Runtime Parameters

Some flags to recognize:

```text
-XX:ReservedCodeCacheSize=...
-XX:+SegmentedCodeCache
```

These are HotSpot-specific options, not mandatory parts of the Java Specification. When investigating, check `java -XX:+PrintFlagsFinal -version` to see actual values on the target JVM.

## 12. Standalone Java 17+ Demo: Verifying Correctness, Observing Hot Paths via JIT Logs

Create the file **`HotMethodDemo.java`**:

```java
public final class HotMethodDemo {
    private static volatile long blackhole;

    static int transform(int x) {
        return (x * 31 ^ (x >>> 3)) & 1023;
    }

    static long loop(int count) {
        long sum = 0;
        for (int i = 0; i < count; i++) {
            sum += transform(i);
        }
        return sum;
    }

    public static void main(String[] args) {
        long calls = 0;
        for (int i = 0; i < 20_000; i++) {
            calls += transform(i & 255);
        }
        long loops = loop(1_000_000);
        blackhole = calls + loops;
        System.out.println("method calls=20000");
        System.out.println("call checksum=" + calls);
        System.out.println("loop checksum=" + loops);
        System.out.println("combined checksum=" + blackhole);
    }
}
```

### 12.1. Compiling/Running in Default Mode

```bash
javac --release 17 HotMethodDemo.java
java HotMethodDemo
```

**Exact stdout of the program when run successfully:**

```text
method calls=20000
call checksum=10169104
loop checksum=511499680
combined checksum=521668784
```

The file above was tested with `javac --release 17` and run on OpenJDK/HotSpot; the results above also match when run with `-Xint` and `-XX:-TieredCompilation`.

### 12.2. Explaining the Demo's Intent

- `transform(int)` is a small method called many times.
- The outer loop in `main` calls `transform` **20,000 times**, passing data in the range `0..255`.
- `loop(1_000_000)` is called only **once** but has a long loop with many backedges.
- `volatile blackhole` receives the result to create an observable side effect, reducing the chance the compiler eliminates the computation altogether as unnecessary.
- `checksum` and `loop checksum` use deterministic integer arithmetic; the program does not use clocks/timing as output.

**Important point:** `volatile` does not by itself guarantee that **all calls remain independent machine-level calls** or that the JIT will definitely compile at level 4. The JIT can still inline/optimize as long as it preserves observable behavior.

### 12.3. Why Does the Demo Intentionally Not Print "JIT Count"?

The number of compilations, compile IDs, tiers, OSR events, and order of appearance depend on HotSpot/JDK, platform, CPU, and scheduling. The Java Specification does not fix them.

The program only prints stable logical results. To observe the JIT, use separate **runtime diagnostics** — do not hardcode "will see 3 compiles" into stdout.

## 13. Practicing `-XX:+PrintCompilation`

Run:

```bash
java -XX:+PrintCompilation HotMethodDemo
```

In HotSpot JDK 17+, this option typically logs compilation events over time, including JDK methods. The output is **non-deterministic** and may interleave with application stdout.

To study it, look for lines containing:

```text
HotMethodDemo::transform
HotMethodDemo::loop
HotMethodDemo::main
```

### 13.1. How to Understand Common Fields

A log entry may look like:

```text
23   13       3       HotMethodDemo::transform (13 bytes)
26   15       4       HotMethodDemo::transform (13 bytes)
26   14 %     3       HotMethodDemo::loop @ 4 (25 bytes)
```

**These are format examples observed on a HotSpot test run, NOT standard output for every machine.** Common fields include:

- **Timestamp** since VM startup (unit/format per output).
- **Compile ID** of the nmethod/task.
- **Markers** such as `%` for OSR.
- **Compilation level** (for example, 3 for C1 profiling, 4 for C2).
- **Class::method** and bytecode size.
- **`@ bci`** in the case of OSR.

Do not interpret `(13 bytes)` as **13 bytes of machine code**: that is usually the method's bytecode size, not the compiled machine code footprint.

### 13.2. Seeing Both C1 and C2 for the Same Method

If the log has:

```text
... 3 ... HotMethodDemo::transform ...
... 4 ... HotMethodDemo::transform ...
```

then this is evidence that the runtime requested/completed compilation at the corresponding tiers in this run. However, **there is no guarantee that every run will show both versions or in the exact same order in stdout**.

### 13.3. OSR Is Marked with `%`

An example:

```text
... % 3 HotMethodDemo::loop @ 4 ...
```

shows that the method had an **OSR compilation** for the loop at the recorded BCI, not that "`loop` was called for the third time."

### 13.4. `made not entrant` Lines

You may see:

```text
... HotMethodDemo::transform ... made not entrant
```

This can be an older nmethod being removed from compiled method entry when more optimized code is available, not a fatal error. Check the timeline and runtime state before judging.

### 13.5. Lots of Logs Does Not Mean the Program Is Wrong

The JVM also JIT-compiles a number of runtime/JDK methods in the same process. If the log has hundreds of lines not containing `HotMethodDemo`, that is normal.

## 14. Isolating Interpreter, Tiered JIT, and Non-Tiered Modes for Comparison

### 14.1. Interpreter-Only with `-Xint`

```bash
java -Xint HotMethodDemo
```

On HotSpot, `-Xint` requests executing Java bytecode in interpreted mode, useful as a control when studying JIT effects. It **does not mean every native runtime stub or library call turns into interpreted Java bytecode**.

**Application stdout must still be:**

```text
method calls=20000
call checksum=10169104
loop checksum=511499680
combined checksum=521668784
```

Running `-Xint` is typically slower for compute-intensive workloads, though there is no fixed ratio rule.

### 14.2. Disabling Tiered Compilation

```bash
java -XX:-TieredCompilation HotMethodDemo
```

This flag stops HotSpot from using the default C1→C2 tiered policy. **Do not interpret disabling tiered as disabling all JIT**: compiler configurations can still compile methods using another mode, depending on the VM build.

### 14.3. Limiting Tiers with `TieredStopAtLevel`

```bash
java -XX:+TieredCompilation -XX:TieredStopAtLevel=1 HotMethodDemo
```

In a suitably configured HotSpot C1/C2, setting level 1 can help study the C1 path without reaching C2 level 4. However, **what "level 1" means is a HotSpot detail**, not a portable option across all Java VMs.

### 14.4. Comparison Table

| How to Run | Intent | What Must Not Be Inferred |
| --- | --- | --- |
| `java HotMethodDemo` | Current HotSpot/JDK default | Every hot method must reach level 4 |
| `java -Xint HotMethodDemo` | Control for interpreted execution | All runtime/native code is disabled |
| `java -XX:-TieredCompilation HotMethodDemo` | Do not use default tiered policy | JIT is completely disabled |
| `java -XX:TieredStopAtLevel=1 HotMethodDemo` | Limit tier on supported builds | All methods are compiled at C1 level 1 |
| `java -XX:+PrintCompilation HotMethodDemo` | Log compilation events | Event counts/timestamps are fixed |

**When verifying a flag, read `java -version` and the documentation of the JVM in use.**

## 15. `PrintInlining`, `LogCompilation`, and Diagnostic Tools

### 15.1. PrintInlining

On supported HotSpot builds, you can enable inlining info during compilation:

```bash
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining HotMethodDemo
```

Output may mention details like `inline (hot)`, `callee is too large`, or reasons from compiler heuristics. Printing format varies by JDK; **do not use a fixed log string as an API**.

If you want to combine them:

```bash
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintCompilation \
     -XX:+PrintInlining HotMethodDemo
```

The trailing `\` is **Bash-style shell line-continuation syntax**, not used verbatim in Windows PowerShell. On Windows, write the command **on one line** or use PowerShell-appropriate line continuation.

### 15.2. PrintAssembly Requires Additional Support

Depending on the HotSpot build, flags like `-XX:+PrintAssembly` or compiler commands to print machine code may require a supporting tool/disassembler, such as the corresponding `hsdis` library. Do not assume every JDK bundle displays annotated assembly out of the box.

**Do not use a binary assembly dump as an example of "standard stdout"** because it varies by CPU architecture, compiler/code layout, and runtime.

### 15.3. `-XX:+LogCompilation`

HotSpot supports logging detailed compilation metadata to a file with appropriate diagnostic options. Reading the log often involves separate analysis tools.

Suggested example:

```bash
java -XX:+UnlockDiagnosticVMOptions -XX:+LogCompilation HotMethodDemo
```

The log may create a file depending on VM options/current directory; check `java -XX:+PrintFlagsFinal -version`, write permissions, and where output is created. Do not use this log without considering its size/impact on production workloads.

### 15.4. Java Flight Recorder (JFR)

JFR can record events related to JIT compilation/code cache, CPU usage, and execution samples on supported configurations. Check event settings in the target build; not all compilation events are enabled in every recording profile.

JFR helps connect runtime behavior to application performance; `PrintCompilation` is often more convenient for simple exercises because it logs directly by method.

### 15.5. `jcmd`

If you need to inspect a running JVM:

```bash
jcmd -l
jcmd <pid> Compiler.codecache
jcmd <pid> Compiler.queue
jcmd <pid> Compiler.codelist
```

Command availability varies by JDK; replace `<pid>` with the actual PID. You can check:

```bash
jcmd <pid> help
```

These commands help observe the compilation queue, code cache, and compiled methods in HotSpot; they are not APIs to run in every Java application.

## 16. On Thresholds and Compilation Policy: Avoid Writing "One Magic Number"

Some older resources say "HotSpot compiles after 10,000 calls." That is an **oversimplified** statement, especially with tiered compilation.

### 16.1. Actual Thresholds Can Be More Complex

OpenJDK's tiered policy has thresholds controlling:

- Frequency of updating and checking counters.
- Per-tier invocation thresholds.
- Per-tier backedge thresholds for OSR.
- Minimum invocation thresholds.
- Combined invocation + backedge activity.
- Queue-length factors that adjust the compilation policy.

Option names like `Tier3InvocationThreshold` or `Tier4BackEdgeThreshold` belong to HotSpot versions/configurations and should not be treated as a public stable API.

### 16.2. Is Lowering Thresholds to "Force JIT" Right?

In test environments, you can adjust compilation policy flags to study behavior. However, **do not assume lower thresholds always make an application faster**:

- Compiler threads consume additional CPU.
- Methods may lack good enough profiles, leading to poor speculation.
- The code cache can experience pressure.
- Compilation/recompilation consumes startup resources.
- Benchmarks can easily become noisy.

### 16.3. Why Does Queue Pressure Affect Compilation Tiers?

If the C2 queue is too long, pushing too many methods to C1 full profiling and then waiting for C2 can cause unnecessary profiling overhead. The tiered policy may choose more suitable C1 paths based on compiler load.

In other words, "hotness" is not just an isolated counter; it is combined with **compilation resource cost**.

## 17. Inlining Makes "Hot" Methods Hard to See in Stack Traces

A hot call site can be optimized via **inlining**: the callee's body is integrated into the caller, reducing call overhead and unlocking constant propagation, bounds-check elimination, or optimizations across method boundaries.

```java
static int twice(int x) {
    return x + x;
}

static int runMany(int n) {
    int sum = 0;
    for (int i = 0; i < n; i++) {
        sum += twice(i);
    }
    return sum;
}
```

This code is only a **snippet**. The JIT may inline `twice` into `runMany`. The result is not required to have a separate call instruction to `twice` in compiled machine code.

### 17.1. Why Can Runtime Profiles Look Different from Source Shape?

- A Java method's logic may appear inside the caller's machine code.
- A long method may be split into compiled hot/cold paths.
- Speculative guards and uncommon-trap edges may not resemble source `if` statements.
- An OSR entry into the middle of a loop differs from a normal method entry.

Adding/removing a Java method does not by itself determine the final method-call cost after JIT.

### 17.2. Do Not Say "Abstracting Into Many Small Methods Is Always Slow"

Java method boundaries can be inlined. Source design should prioritize clarity/correctness; micro-optimizations require real benchmarking and profiling, not counting calls visible in source.

## 18. How Does Warm-Up Affect Performance Measurements?

A microbenchmark measuring right on the first call:

```java
long start = System.nanoTime();
someMethod();
long elapsed = System.nanoTime() - start;
```

does not only measure "the speed of `someMethod` at steady state." It can also include:

- Class loading/linking/initialization.
- Interpreter execution and runtime resolution.
- Ongoing JIT compilation/warm-up.
- GC and safepoints.
- Thread scheduling, CPU scaling/JIT code cache activity.
- Dead-code elimination or constant folding if the measurement does not properly prevent optimization.

### 18.1. A Hand-Rolled Timing Loop Is Easy to Get Wrong

```java
for (int i = 0; i < 1_000_000; i++) {
    compute(42);
}
```

This snippet is not standalone; `compute` must be declared. The JIT may inline `compute`, hoist invariant computations, or eliminate unused results. This is why "one million iterations" is not by itself a reliable benchmark.

### 18.2. JMH Is the Preferred Choice for Microbenchmarks

OpenJDK's **JMH (Java Microbenchmark Harness)** provides warm-up iterations, measurement iterations, forks, blackholes, and mechanisms to reduce benchmark pitfalls. If the goal is to measure speedup from JIT/C1/C2, use JMH instead of writing an arbitrary `nanoTime` loop.

Project page: https://openjdk.org/projects/code-tools/jmh/

### 18.3. Benchmarks Need a Stable Environment

Keep the following consistent:

- JDK vendor/build and VM flags.
- CPU quota/affinity, host load, and power policies.
- Heap sizing and GC.
- Input data/branch ratios/object shapes.
- Warm-up, forks, and sample counts.

A difference appearing in a single run is not enough to prove C2 always improves performance.

## 19. A Learning Timeline from Cold Method to Hot Path

Suppose a service has `parse(int)` in a request handler:

```text
t0: JVM starts
    parse() has never been called

t1: first request
    parse() is executed interpreted
    JVM collects appropriate profiling/counter data

t2: requests increase
    invocation count grows
    policy considers parse() hot enough
    enqueues C1 compile

t3: C1 version is published
    later requests can use C1
    profiling tier continues collecting branch/type data

t4: requests continue
    policy has enough profile, enqueues C2
    while waiting, application continues

t5: C2 version available
    new requests can use optimized code
    parse() may be inlined into handler

t6: new input type/call path appears
    guards/assumptions may be invalidated
    deoptimization/recompilation may occur
```

This is an **illustrative timeline**; it does not say every service necessarily goes through t2–t6 or that each step takes exactly one request. A rarely run method may never reach t2. A long loop may OSR without a large method invocation count.

## 20. Comparing Java 17 HotSpot with Edge Cases

### 20.1. Native Methods

`native` methods typically execute via native implementation/ABI/JNI, not regular Java bytecode for HotSpot C1/C2 to compile identically to a Java method body.

### 20.2. Abstract Methods

An abstract method has no bytecode body for the JIT to compile standalone. Concrete implementations/call sites can be compiled and optimized.

### 20.3. Large or Complex Methods

Some methods that are too large or unsuitable for a compiler tier may not be compiled at that level; the VM may choose another tier, fall back, or leave them interpreted depending on policy. Not every hot method is guaranteed C2 level 4.

### 20.4. Synchronized Methods

The JIT can optimize synchronization under valid conditions, but it must preserve the Java Memory Model. Just because a method is hot does not mean the JIT can remove synchronization in a way that alters correctness.

### 20.5. Exceptions

Rare exception paths can affect profiling/uncommon traps. You should not artificially increase exception rates to "warm up" a method without considering business correctness and GC/allocation overhead.

### 20.6. Multiple Class Loaders

Two classes with the same binary name defined by two different defining class loaders form two distinct runtime classes. Compilation metadata/code and profiling can be organized separately by method identity; do not infer that because a method is hot in loader A, loader B is compiled the same way.

## 21. Common Misconceptions

| Misconception | Correct Understanding |
| --- | --- |
| "Java is always interpreted, with no machine code." | HotSpot has C1/C2 JIT and runs compiled native code when appropriate. |
| "`javac` produces C2 code." | `javac` produces bytecode; HotSpot JIT is a separate runtime step. |
| "Every method is compiled immediately on its first run." | The interpreter can be the starting point; compilation is based on policy/hotness. |
| "Hot = the method with the longest wall-clock time." | Invocation/backedge activity, profiles, queues, and heuristics matter. |
| "A method called 10,000 times is guaranteed level 4." | There is no portable absolute threshold; tiered policy is more complex. |
| "Tiers always go sequentially 0→1→2→3→4." | A common path is 0→3→4; levels can be skipped or paths changed. |
| "C1 is the interpreter." | C1 is a JIT compiler producing native code; level 0 is the interpreter. |
| "C2 must be faster than C1 by an exact ratio." | It depends on the method/profile/CPU and benchmark. |
| "Only methods called many times get hot." | A method called once with a long loop may need OSR. |
| "OSR is a request calling a new method." | OSR can replace execution of a currently running frame at a loop BCI. |
| "`%` in PrintCompilation means an error." | `%` is typically the OSR compilation marker. |
| "`@ 4` in OSR logs means the fourth invocation." | It indicates a bytecode index (BCI), not an invocation count. |
| "`13 bytes` in the log is the machine code size." | It is usually the method's bytecode size. |
| "`made not entrant` means the app is broken." | It is usually a state where compiled code is not used for new entries. |
| "Deoptimization makes Java return different results." | The JVM must preserve semantics when switching execution/recompiling. |
| "`-Xint` is the same as `-XX:-TieredCompilation`." | `-Xint` requests the interpreter; disabling tiered does not mean disabling JIT. |
| "Adding a volatile field forces every call not to inline." | Volatile side effects must be preserved, but inlining can still occur. |
| "PrintCompilation always has the same number of lines." | Compilation events depend on JVM/load/timing, not deterministic. |
| "Inlining makes every API abstraction always free." | Only when the JIT actually inlines/optimizes under the right conditions. |
| "The code cache is the Java heap." | The code cache is runtime memory separate from Java objects in the heap. |
| "The JIT compiler only runs before `main()`." | The JIT can run at any time during runtime when a method is hot. |
| "A single cold-run benchmark can conclude steady-state performance." | Warm-up/forks/JMH and multiple runs are needed. |

## 22. Self-Check with Answers

**Q1.** What does `javac` compile Java into, and what do C1/C2 compile?

**Answer:** `javac` produces bytecode in `.class` files; C1/C2 are HotSpot runtime JIT compilers that produce machine code suited to the CPU/runtime.

**Q2.** Why might a method run only once never be JIT-compiled?

**Answer:** The compile/profiling cost may exceed the benefit of a single run; the policy keeping it interpreted is a reasonable choice.

**Q3.** Can code become hot even if called only once?

**Answer:** Yes. A very long loop increases backedge activity and can trigger OSR.

**Q4.** What does Tier 0 correspond to?

**Answer:** Interpreter execution in the HotSpot tiered compilation model.

**Q5.** How do Level 3 and Level 4 differ?

**Answer:** Level 3 is C1 with full profiling; Level 4 is C2 optimized compiled code in the typical HotSpot model.

**Q6.** Does every method always go through C1 level 1 before levels 2/3/4?

**Answer:** No. It can go 0→3→4 or other paths depending on policy.

**Q7.** Do invocation count and backedge count mean the same thing?

**Answer:** No. Invocation counts method entries; backedge relates to loop iterations and can heat up a loop within a single invocation.

**Q8.** What is OSR?

**Answer:** On-Stack Replacement: the runtime can switch a frame currently running a loop from interpreted/lower-tier compiled execution to OSR compiled code at an appropriate bytecode location.

**Q9.** What does C2 use runtime profiles for?

**Answer:** Selecting/optimizing frequently taken paths, such as inlining or devirtualization, with guards and deoptimization when needed to preserve semantics.

**Q10.** Does deoptimization mean "GC reclaims compiled code"?

**Answer:** No. It relates to invalidating/leaving optimized compiled execution and restoring appropriate runtime state; code cache management is a separate matter.

**Q11.** Why can performance improve after warm-up?

**Answer:** Hot methods/loops can be JIT-compiled and optimized based on profiling, though the gain depends on the workload.

**Q12.** Does `-Xint` disable JIT compilation for application bytecode on HotSpot?

**Answer:** Yes, it requests interpreted mode for Java bytecode; however, it does not make all native runtime components disappear.

**Q13.** Does `-XX:-TieredCompilation` mean the same as `-Xint`?

**Answer:** No. It disables the tiered policy, not necessarily every JIT compiler.

**Q14.** Does `PrintCompilation` help prove that compilation events were logged in that run?

**Answer:** Yes, for the events/log format reported by the JVM; however, it does not guarantee all compiler decisions will always have the same line count/timing.

**Q15.** In the log `HotMethodDemo::loop @ 4`, what is the number 4 usually?

**Answer:** The bytecode index (BCI) used for OSR compilation in that log format.

**Q16.** Why might a very small method not appear as a separate machine-level call in a hot path?

**Answer:** The JIT may inline it into the caller.

**Q17.** Why is simply taking `System.nanoTime` around a single cold call not a steady-state benchmark?

**Answer:** It can include class initialization/interpreter/warm-up/JIT/GC/OS noise and be misled by compiler optimizations.

**Q18.** Which tool is more suitable for building Java microbenchmarks with warm-up and forks?

**Answer:** OpenJDK **JMH**.

**Q19.** When the code cache is full, is Java's result allowed to change?

**Answer:** No. The JVM must preserve semantics; it may restrict compilation/impact performance depending on the runtime.

**Q20.** Can you force every hot method to level 4 within a fixed time window?

**Answer:** There is no such portable API guarantee; policy, compiler queues, profile quality, and other constraints apply.

## 23. Practical Checklist

1. Check **`java -version`** to know the JVM vendor/build and tiered compiler availability.
2. Read class bytecode with `javap -c` when you need to understand method shape/loop backedges.
3. Distinguish **method-entry compilation** from **OSR compilation**.
4. Use `-XX:+PrintCompilation` to view compilation events, recognizing levels 3/4, `%`, and `@ BCI`.
5. Do not compare timestamps/log counts between two runs as a contract.
6. Use `-Xint` as a control for interpreted behavior, understanding how it differs from `-XX:-TieredCompilation`.
7. Observe inlining when tools are available rather than guessing from source.
8. Avoid optimizing microbenchmarks around computed results that the compiler eliminates.
9. Use JMH if the goal is performance comparison.
10. Measure compilation CPU, code cache, and application latency when tuning policy flags.
11. Record warm-up/forks/heap/CPU/GC for reproducible results.
12. Avoid setting compilation thresholds in production without measured evidence.
13. If throughput drops after a long uptime, check code cache, deoptimizations, and profile shifts.
14. If an application has continuous class loaders/redeploys, remember compilation state and runtime class identity have their own lifecycles.
15. Distinguish **optimized machine code** from Java language guarantees; correctness must be the same across interpreter/C1/C2.

### Final Summary

```text
Cold method
     |
     v
HotSpot interpreter (tier 0)
     |
     +-- low call count and short loops --> may remain interpreted
     |
     +-- many calls / loop backedges --> hotness / profiling
                                             |
                                             v
                                      JIT compilation policy
                                             |
                     +-----------------------+------------------+
                     |                                          |
                   C1 tiers                                 OSR entry
                  (1,2,3)                                for hot loop
                     |
                collect profile
                     |
                     v
               C2 (tier 4)
                     |
            guards / assumptions
                     |
                  deopt?
                     |
                     +--> interpreter / reprofile / recompile

GC, JIT, and the Java app remain one process;
every execution path must preserve the same Java semantics.
```

**Conclusion:** HotSpot does not optimize all bytecode immediately. It **executes**, **observes**, **identifies hot code**, and then **selectively compiles** to balance startup and throughput. A frequently called method may be compiled by C1 and then C2; a long-running loop may transition to compiled code mid-execution via OSR; speculative optimizations may be invalidated when assumptions change. **These steps are HotSpot policies, not a fixed schedule of the Java language.**
