# LineNumberTable, LocalVariableTable, and Limitations When Recovering Source Code

## 1. What Can a `.class` File Reveal About Source Code?

The Java compiler converts source code into a **class file** containing bytecode and binary structures according to the JVM specification. A class file has enough information for the JVM to load, verify, link, and execute a class; it is **not a verbatim copy** of the `.java` file.

In a class file, **optional attributes** can provide data for debugging tools, such as:

- **`LineNumberTable`**: maps certain bytecode positions of a method to **source code line numbers**.
- **`LocalVariableTable`**: describes **local variable names**, types as descriptors, slot positions, and the bytecode range in which the variable is valid.
- **`LocalVariableTypeTable`**: may additionally store a **generic signature** for some local variables with generic types; it does not replace `LocalVariableTable`.
- **`SourceFile`**: the source file name used to describe where the class was compiled, commonly serving debugging/stack traces; this is only a name, not the file contents.
- **`SourceDebugExtension`** (when present): may carry extended source mapping information generated by tools/languages, useful for multi-layered code generation scenarios.

The first two tables are the focus of this lesson. Their presence helps debuggers, IDEs, and `javap` display more understandable information; they **do not make the JVM require the original source code to execute**. A class file without these tables can still be a completely valid class file and run properly.

It is also necessary to distinguish three activities:

1. **Disassembly**: displaying JVM instructions, for example `iload`, `iadd`, `invokevirtual`, from bytecode. This is what `javap -c` does.
2. **Debugging**: correlating execution positions with source lines/variables when metadata and runtime state permit. Debuggers can inspect data maintained by the JIT/runtime, but they do not recreate source information that was never stored.
3. **Decompilation**: inferring a high-level source snippet with corresponding behavior from bytecode. Source reconstructed by a decompiler **is not automatically the original source**.

## 2. Where Are These Attributes Located in the Class File Structure?

According to the JVM class-file format, a class has a constant pool, field/method declarations, and attributes. Each method can have a **`Code`** attribute if that method has bytecode. Inside `Code` are the bytecode, stack/locals information, exception handler table, and a list of attributes **attached specifically to that code**.

~~~text
ClassFile
├── constant_pool
├── fields[]
├── methods[]
│   └── method_info
│       └── attributes[]
│           └── Code (if the method has bytecode)
│               ├── max_stack
│               ├── max_locals
│               ├── code[]                  ← instruction bytes
│               ├── exception_table[]
│               └── attributes[]
│                   ├── LineNumberTable    ← optional
│                   ├── LocalVariableTable ← optional
│                   ├── LocalVariableTypeTable (if present)
│                   └── StackMapTable/...  ← serves other purposes
└── attributes[]
    └── SourceFile (if present)
~~~

`LineNumberTable` and `LocalVariableTable` are **nested attributes of `Code`**, so they are attached to **a specific method**, not a single table applying to the entire class. `SourceFile` is a class attribute, not inside `Code`.

Although this data resides in `.class`, it is **not instructions that affect the Java algorithm**. The JVM can use or provide this data to debugging tools; having or not having metadata does not turn `if`, `for`, or `return` into a different algorithm.

In addition:

- **`StackMapTable`** supports type verification at relevant bytecode points. This is not a list of source variable names and does not replace LocalVariableTable.
- **`Exceptions`** describes exceptions declared at the method level; it does not contain the verbatim `throws` syntax from the source.
- **`Signature`** may record the generic signature of a class/field/method; generic source is not fully reconstructed because of this.
- **`MethodParameters`** may contain the names and flags of **method parameters**, depending on compiler options such as `javac -parameters`; it is **different from** `LocalVariableTable`.

## 3. LineNumberTable: Mapping Bytecode Positions to Source Lines

An entry of `LineNumberTable` consists of two meaningful values:

| Field | Meaning |
| --- | --- |
| `start_pc` | Bytecode offset measured from the beginning of the `code[]` array of the **current method** |
| `line_number` | Source line number that the compiler associates with the bytecode starting from that position |

**Illustrative** example (offsets/lines are determined by the compiler, not a `javap` output guaranteed across all versions):

~~~text
LineNumberTable:
  line 10: 0
  line 11: 4
  line 12: 9
~~~

How to read: the instruction starting at offset 0 is associated with line 10; offset 4 is associated with line 11; offset 9 is associated with line 12. Instructions between markers can be correlated by the debugger to the appropriate line marker according to the table and execution position.

**LineNumberTable is not a one-to-one map between source lines and instructions:**

- One Java line can generate **multiple instructions**.
- One statement or expression can span **multiple lines**.
- Multiple instructions can be associated with the **same line**.
- The compiler may choose or omit line markers depending on how bytecode is generated.
- Synthetically generated code or code transformed by the compiler may have line mappings that differ from source intuition.
- The table contains **line numbers**, not text on the line, indentation, comments, variable names, or character columns.

### Effect on Stack Traces

When an exception is formatted as a stack trace, the JVM/runtime can use the class name, method name, `SourceFile`, and `LineNumberTable` to report, for example:

~~~text
at demo.DebugInfoDemo.compute(DebugInfoDemo.java:7)
~~~

This is only a **formatting example**, not a stack trace line claimed to appear in the hands-on program below. The number `7` is simply the source line number when metadata allows determining it. If line information is absent, the stack trace may display `Unknown Source`, or keep the file name without a line number, depending on metadata and representation.

Having `LineNumberTable` **does not guarantee** always identifying an exact source statement for every PC. With compiler-generated code, lambdas, `switch`, runtime inlining, instrumentation, or code from other languages, line markers may not match the debugger user's expectations.

## 4. LocalVariableTable: Name, Type, Slot, and Scope of Existence

Each `LocalVariableTable` entry is described by the following fields:

| Field | Meaning |
| --- | --- |
| `start_pc` | Bytecode offset where the variable's validity range begins |
| `length` | Number of bytes in the described validity range |
| `name_index` | Constant pool index pointing to the variable name |
| `descriptor_index` | Constant pool index pointing to the descriptor of the variable's type |
| `index` | Index of the **local-variable slot** in the method's frame |

The validity range is described by `[start_pc, start_pc + length)`, measured in bytecode offsets. Do not read `length` as the number of characters, the number of Java lines, the number of times the variable is used, or the number of bytes the object occupies on the heap.

An illustrative example similar to `javap -l` (lines/offsets are illustrative, not fixed results):

~~~text
LocalVariableTable:
  Start  Length  Slot  Name      Signature
      0      14     0  input     I
      4      10     1  doubled   I
      9       5     2  result    I
~~~

- `input`, `doubled`, `result` are **source names stored by the compiler**, not their actual numeric values when the program runs.
- `Signature` in the `javap` output of the table above displays **descriptors** such as `I`, `Ljava/lang/String;`; this does not mean `LocalVariableTable` itself stores full generic types.
- `Slot` identifies a logical cell in the local-variable array of a **method frame**; it is **not a stack address in RAM**.
- On an instance method, slot 0 usually holds `this`; on a `static` method there is no `this`.
- `long` and `double` use **two consecutive local-variable slots** according to JVM frame rules; many other types, including references, use one slot.

### Source Scope and Bytecode Range

Two variables with the same name in separate scopes can use the **same local slot in two non-overlapping live ranges**. A compiler can reuse a slot even when names and types differ; reading `index = 2` in two different entries does not allow concluding that it is **one source variable**.

Conversely, source code may declare a variable, yet the compiler allocates, reorders, or eliminates its physical representation during optimization. LocalVariableTable reflects the metadata of the **emitted class file**, not a snapshot of JIT register/stack state at time T.

### LocalVariableTypeTable and Generics

Java example:

~~~java
java.util.List<String> words = java.util.List.of("JVM");
~~~

With a class file having sufficient debug metadata, `LocalVariableTable` may describe the descriptor of `words` as `Ljava/util/List;`. `LocalVariableTypeTable` may additionally store a generic signature such as `Ljava/util/List<Ljava/lang/String;>;` so the debugger understands the generic type. That information is **optional** and does not fully reconstruct all generic expressions or source type inference.

Do not confuse `LocalVariableTypeTable` with the **`Signature` attribute** of a field/method/class, or `StackMapTable` supporting verification; their names are similar, but their purposes and locations differ.

## 5. Java 17+ Hands-On: With and Without Debug Metadata

Create the file **`src/demo/DebugInfoDemo.java`** with the full content:

~~~java
package demo;

public final class DebugInfoDemo {
    static int compute(int input) {
        int doubled = input * 2;
        int result = doubled + 3;
        return result;
    }

    public static void main(String[] args) {
        int answer = compute(4);
        System.out.println("Result=" + answer);
    }
}
~~~

Compile with JDK 17+; create two separate output directories first:

~~~bash
mkdir out-debug
mkdir out-minimal
javac --release 17 -g:lines,vars,source -d out-debug src/demo/DebugInfoDemo.java
javac --release 17 -g:none -d out-minimal src/demo/DebugInfoDemo.java
~~~

Run both class files with the same logic:

~~~bash
java -cp out-debug demo.DebugInfoDemo
java -cp out-minimal demo.DebugInfoDemo
~~~

**Each command prints exactly one line to stdout**:

~~~text
Result=11
~~~

Both builds run with the same semantics because `-g` changes the amount of **debug metadata** the compiler embeds into the class, without changing the algorithm needed to compute `4 * 2 + 3`.

### 5.1. Using javap to Read the Version with Debug Info

~~~bash
javap -classpath out-debug -c -l -p demo.DebugInfoDemo
javap -classpath out-debug -v -p demo.DebugInfoDemo
~~~

Observe:

1. `-c` displays the bytecode of `compute` and `main` (such as multiplication, addition, calling `println`, returning).
2. `-l` requests printing **line number** and **local variable tables** if present.
3. `-p` requests displaying non-public members as well; `compute` in the example is package-private.
4. `-v` prints additional detailed information such as class-file version, constant pool, and `Code` attributes.
5. With `--release 17`, the class file generated for Java 17 has **major version 61**.

The `out-debug` build was requested to emit line numbers, local variable names, and source information. Therefore, in the `compute` section, you can find variables such as `input`, `doubled`, `result` in `LocalVariableTable`. At the same time, `LineNumberTable` maps bytecode offsets to the line numbers of the file you just created. **The exact offsets and full printed table are determined by the compiler**: read the actual output instead of copying an example table and treating it as standard.

### 5.2. Comparing with the Version Stripped of Debug Metadata

~~~bash
javap -classpath out-minimal -c -l -p demo.DebugInfoDemo
javap -classpath out-minimal -v -p demo.DebugInfoDemo
~~~

With `javac`'s `-g:none`, the class file does not carry the `LineNumberTable` and `LocalVariableTable` debug attributes generated by `-g` options. The `SourceFile` debug attribute is also not requested in this build. Even so, the bytecode needed to execute `compute(4)` and call `println` still exists; `javap -c` still displays instructions and methods, and `java` still runs.

Do not conclude that **all metadata has disappeared**: the class file must still have class/method names, descriptors, constant pool, and structures serving the runtime; some other attributes are still needed for verification or language features.

### 5.3. Distinguishing Common Switches

| javac Option | Information to Observe |
| --- | --- |
| `-g` | Generates all supported debug information, including line, source, vars |
| `-g:lines,vars,source` | Explicitly requests the three groups of information above |
| `-g:lines,source` | Includes line/source but does not request local variable names |
| `-g:none` | Generates no debug information |
| `-parameters` | May store **method parameter names** in `MethodParameters`; different from LocalVariableTable |
| `--release 17` | Targets Java 17 API/platform semantics and class-file target; not a debug switch |

`javac` in default mode usually generates **lines and source** but does not generate **vars**. When you need to be sure to see local variable names in exercises, use `-g:vars` or `-g` depending on the specific compiler.

## 6. Reading `javap -v` Without Confusing Metadata with Program Code

When opening the `Code` section, you will commonly see the related structure:

~~~text
Code:
  stack=..., locals=..., args_size=...
     0: ...
     1: ...
     ...
  LineNumberTable:
    line ...: ...
  LocalVariableTable:
    Start Length Slot Name Signature
    ...
~~~

This is a **presentation template**, not the actual output of a specific `javac` version.

- `stack=...` and `locals=...` indicate the operand stack limit and number of local slots **per bytecode frame**, not the native call stack size or total program memory.
- Instructions at addresses 0, 1, ... are **offsets in the method's `code[]`**, not RAM addresses.
- An abstract or native method has no corresponding `Code` section, so do not expect it to contain `LineNumberTable`/`LocalVariableTable` like a Java method with bytecode.
- Compiler-generated methods (default constructors, bridge, lambda helpers, synthetic members...) may not have a mapping structure corresponding to an intact method in the source.

If source variable names are absent from `LocalVariableTable`, a debugger/decompiler may synthesize names such as `var1`, `local2`, or `arg0`. Those names **are products of tool inference or display** when reliable metadata is absent, not proof that the original Java file had the same names.

## 7. Limitations When Recovering Source Code from a Class File

### 7.1. Compilation Is a Many-to-Fewer-Information Transformation

Many different source snippets can produce **equivalent, or even identical, bytecode** after compile-time optimizations. For example:

~~~java
int result = 4 + 5;
~~~

and:

~~~java
int result = 9;
~~~

A Java compiler can constant-fold the expression `4 + 5` into the constant `9`. When viewing bytecode, there is no guarantee to distinguish whether the author typed the addition or the literal constant directly. If the source had `final int n = 9` or shortened imports, the verbatim form may also be normalized or eliminated by the compiler.

Even when keeping `LineNumberTable`, the two ways of writing above can be on the **same line**, so knowing only the line marker is not enough to distinguish how it was written. Having `LocalVariableTable` can preserve the name `result`, but does not preserve the expression `4 + 5` as text.

### 7.2. Information Commonly Lost or Transformed

| Information in Source | Can It Be Accurately Recovered from the Class File? |
| --- | --- |
| Compiled bytecode instructions and descriptors | **Yes**, when the class file is valid and readable, `javap` can inspect the actual structure |
| Class/method/field names present in the ABI | Usually **yes**, but may have been obfuscated/renamed before receiving the file |
| Source lines associated with bytecode | **Partially** if LineNumberTable and corresponding information exist |
| Local variable names | **Partially** if LocalVariableTable exists and the compiler stored the names |
| Generic types of some local variables | **Partially** if LocalVariableTypeTable exists and the information is valid |
| Method parameter names | Possible via LocalVariableTable or MethodParameters, depending on compiler flags |
| Comments, whitespace, indentation, line breaks | **No**, normally not stored |
| Verbatim import statements, import aliases, qualifier placement | **No**; class files normally store type references already resolved by the compiler |
| Original expressions before constant folding or desugaring | **Not guaranteed** |
| Whether `for`, `while`, or `switch` was written in source | Can only be **inferred**; many constructs lower to similar bytecode |
| Exact names/boundaries of all variables in source | **Not guaranteed**; scopes/slots may be altered or metadata missing |
| Original file name, full `.java` file contents | SourceFile is only a name when present; **does not contain the full file text** |

A decompiler usually reconstructs code that is **readable and looks like Java**, but that is **one solution** for the known bytecode, not proof that this is the source the author wrote.

### 7.3. Compiler Transformations of High-Level Semantics Down to the JVM

Source-level features can undergo **lowering/desugaring** during compilation:

- Lambdas or method references may be bound to `invokedynamic` and bootstrap methods instead of existing as verbatim lambda expressions.
- Try-with-resources is transformed into resource-closing and exception/suppressed-exception handling structures, often significantly longer than the `try (...)` syntax.
- Enhanced `for` may become an iterator loop or index-based access depending on the data type.
- String switch, enum switch, generic erasure, autoboxing, bridge methods, and synthetic methods/classes can all cause bytecode to no longer match the original statement structure.
- Kotlin, Scala, or other JVM languages can generate state machines, helper classes, metadata, and method names that have no one-to-one equivalent Java source syntax. **Being able to decompile to Java-like output** does not mean the original Kotlin/Scala source has been recovered.

Even when a decompiler recovers a **recompilable** Java representation that runs equivalently, comments, variable names absent from metadata, business intent, source file/package structure, and stylistic choices can still differ from the original.

### 7.4. Obfuscation and Stripping Metadata

Packaging/obfuscation tools can rename classes, methods, or fields that are not required to keep their names, remove debug attributes, alter bytecode structure, or optimize. Therefore, a downloaded file may differ from the class file originally emitted by the compiler. `LocalVariableTable` may be completely removed or retained with names that no longer hold their original meaning.

Losing LineNumberTable makes reading stack traces and setting line breakpoints harder; losing LocalVariableTable makes it harder for debuggers to present local variable names. **Neither table prevents the JVM from running** if the transformed class file still complies with execution constraints.

### 7.5. JIT Is Not a Reverse-Recovery Process from Source

The JVM can JIT-compile and optimize instructions at runtime: inlining methods, eliminating allocations, changing data locations in registers/stack. This is **runtime** optimization, separate from the class-file debug attributes the compiler generated earlier.

A decompiler typically reads the class file on disk or existing bytecode; it **cannot read the full original source text from JIT-optimized machine code**. When debugging in optimized mode, a source variable may temporarily have no directly observable value at the selected PC, even though LocalVariableTable still describes the name/slot at the bytecode level. Debugging tools may use additional runtime metadata to display information, but there is no guarantee every local is always readable.

## 8. Practical Applications of the Two Tables

### 8.1. Stack Traces and Production Investigation

When errors appear in logs, `LineNumberTable` helps associate stack frames with source line numbers. This is useful **only when the source being viewed matches the exact version of the class that ran**. If the production build was built from a different commit or went through instrumentation/obfuscation, line 52 in the stack trace does not necessarily point to the same statement in the current checkout.

Diagnostic workflow:

1. Identify the exact running artifact/version, JDK, classpath/module path, and build identifier.
2. Read the stack trace, separating **stderr** from stdout/logs by timestamp if possible.
3. Check whether the runtime class contains LineNumberTable using `javap -v` on the **actual artifact**.
4. Open the source at the exact commit/build; do not match line numbers of binary A with source B.
5. If the artifact is obfuscated, use the corresponding mapping provided by the build, if preserved.

### 8.2. Debuggers and IDEs

When clicking "Step Over/Into" or setting a breakpoint on a line, the debugger uses the mapping from **source line ↔ bytecode execution position** according to compiler/runtime data. Because LineNumberTable is not a one-to-one mapping, a line breakpoint may stop at an unintuitive position, or fail to be set when there is no corresponding code.

LocalVariableTable helps display local names within a code range. Without this table, a debugger can still inspect fields, parameters with separate metadata, stack/frame, and other values depending on its capabilities, but it cannot promise to recover original local names. Messages like "variable not available" can be caused by **scope having ended, missing metadata, or runtime optimization**, not just a single cause.

### 8.3. Decompiling to Understand Bytecode, Not Replacing Source Control

Decompiling can help:

- Understand the public API and control flow of a library lacking source.
- Recognize synthetic/bridge methods or compiler-generated code.
- Cross-check bytecode behavior against assumptions made during code review.
- Investigate differences between source and binary caused by build, bytecode instrumentation, or obfuscation.

Limitation: decompiled results **must be verified with bytecode and testing** before being treated as reliable behavior. Accurately recovering source files still requires the corresponding source code stored in Git/source archives or original artifacts if available.

## 9. Checklist for Reading an Unfamiliar Class File

With `some-library.jar`, you can work as follows:

~~~bash
jar tf some-library.jar
javap -classpath some-library.jar -public -s example.pkg.LibraryClass
javap -classpath some-library.jar -c -l -p example.pkg.LibraryClass
javap -classpath some-library.jar -v -p example.pkg.LibraryClass
~~~

`jar tf` lists the archive contents; `javap -public -s` gives API/descriptors; `-c` views instructions, `-l` views line/local tables if present; `-v` checks version, constant pool, and attributes. Replace `example.pkg.LibraryClass` with an actual class name in the JAR.

If the tables are present, ask yourself:

- Does `LineNumberTable` cover the code region under investigation? What is the `SourceFile` source name?
- What local names and PC ranges does `LocalVariableTable` have? Is a slot reused in another range?
- Are `LocalVariableTypeTable` or `MethodParameters` present? They answer **different questions** than LNT/LVT.
- Are there signs of synthetic/bridge methods, lambdas, or compiler transformations?
- Has the artifact been obfuscated/stripped, and which commit/build does it correspond to?

Do not take `javap` offset numbers and treat them as **physical addresses**, and do not take local names from a decompiler and conclude with certainty that they are source names.

## 10. Misconceptions to Avoid

1. **"LineNumberTable stores code line by line."** No: it stores **bytecode offsets and line numbers**, not characters on the line.
2. **"LocalVariableTable contains the current value of each variable."** No: it describes name/descriptor/slot/range metadata; values are runtime state.
3. **"With LVT, the compiler must preserve variable names after all optimizations."** No: the compiler, obfuscator, or build pipeline can remove/change metadata, and the JIT runtime can optimize state.
4. **"Slot index is a RAM address."** No: it is a logical index of the local-variable array in a JVM frame.
5. **"SourceFile is enough to recover the source."** No: it usually only stores the file name, without the `.java` text.
6. **"`javap -c` is a decompiler to Java."** No: `javap -c` **disassembles JVM instructions**; a decompiler must infer high-level structures.
7. **"Without debug tables, the class won't run."** No: debug metadata is optional; the JVM still executes valid classes.
8. **"A class file corresponds to only one exact Java source."** No: many sources can produce equivalent bytecode, especially after constant folding/desugaring.
9. **"Generic parameters, lambdas, and try-with-resources always remain intact as written."** No: the compiler can change representations while preserving required semantics.
10. **"Having a stack trace at line N means the bug is definitely on line N of the latest source."** No: you must match the build/version and class transformations.

## 11. Self-Check Exercises

1. A `LineNumberTable` records `line 18: 6`. What is the number 6? **Bytecode offset in the method's code[] array**, not a character column or RAM address.
2. `LocalVariableTable` records `Start=3, Length=8, Slot=1, Name=total, Signature=I`. Does that data tell you the value of total when PC=5? **No**; it only tells you the variable is described in the range `[3,11)`, slot 1, type int.
3. Must two entries with the same slot 1 but different live ranges necessarily be one source variable? **No**; the compiler can reuse slots.
4. Does using `javac -g:none` cause `java Demo` to stop running? **No**, if the class file is still valid and has sufficient dependencies.
5. Why can't a decompiler be sure whether the author typed `4 + 5` or `9`? Because the compiler can constant-fold both into the same bytecode.
6. Do `MethodParameters` and `LocalVariableTable` completely replace each other? **No**; one describes parameter metadata, the other describes local variables by code region.
7. Why can a variable name be present in LVT yet the debugger still say "optimized out"? Because **bytecode metadata does not guarantee that value remains in a readable location after JIT optimization**.
8. To match a production stack trace, do you need the latest source or **the source matching the build that ran**? You need the **exact build**.

**Technical Conclusion:** `LineNumberTable` connects **bytecode positions to source lines**; `LocalVariableTable` connects **bytecode scopes/slots to local variable names and types**. Both tables aid debugging, but **do not store source code verbatim**. A decompiler can reconstruct equivalent code for reference, rather than guaranteeing from such metadata to recover the exact comments, structure, and wording of the original Java source.
