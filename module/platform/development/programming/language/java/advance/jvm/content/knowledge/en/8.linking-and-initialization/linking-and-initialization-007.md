# Operations That Trigger Initialization and Class-Loading-Only Cases in the JVM

A Java class can **already be loaded by the JVM and have a `Class<?>` object**, yet **not have executed its static initializer**. Only when the program performs an operation that requires initialization does the JVM execute the initialization procedure for that class/interface. Confusing these two points causes hard-to-find bugs: static logs appearing unexpectedly, plugins auto-starting too early, reading a field returning an unexpected value, or a class failing in `<clinit>` and then being unable to initialize again.

This article focuses on the question: **which operations obligatorily trigger initialization, and which operations may only perform loading/linking without running `<clinit>`?** The explanation is based on **JLS Java SE 17 `12.4** and **JVMS Java SE 17 `5.5**, with standalone runnable Java 17 examples, bytecode comparisons, and a troubleshooting checklist.

**Opening rule:** "A class being mentioned" is not enough to conclude "the class has been initialized". You need to know the **type of operation**, the **class/interface that actually declares the member**, the previous initialization state, and dependencies such as superclasses or superinterfaces with default methods.

## 1. Three phases that must not be conflated

The JVM distinguishes the following concepts:

| Phase | What the JVM performs | Does it necessarily run the target class's static initializer? |
| --- | --- | --- |
| **Loading** | Finds/defines the runtime representation of a class/interface from its name and binary data; creates the corresponding `Class` object | **No** |
| **Linking: verification** | Checks format, bytecode, types, and validity constraints | **No** |
| **Linking: preparation** | Allocates storage for static fields and sets initial values according to VM rules; special handling for `ConstantValue` attributes | **Does not run `<clinit>`** |
| **Linking: resolution** | Resolves symbolic references (class, field, method...) when the JVM decides to perform it according to the specification | **Not necessarily** |
| **Initialization** | Executes the class/interface initialization procedure, including static field initializers and static blocks generated by the compiler | **Yes**, if there is initialization work |

For a normal class, the compiler usually groups static initialization statements into a **class initialization method `<clinit>`**. If a class has no code to run, there is not necessarily a `<clinit>` method in the class file, but the JVM still has an **initialization state** for the class.

Conceptual diagram:

```text
not yet loaded
     |
     | ClassLoader / JVM requests class
     v
LOADING --------> Class<?> and runtime identity exist
     |
     v
LINKING --------> verification / preparation / resolution
     |             (part of resolution may occur as needed)
     |
     | active use operation requires initialization
     v
INITIALIZATION --> initialize superclass / some superinterfaces if required
     |             --> execute static initializers / <clinit>
     v
initialized successfully; active uses continue
```

Do not view the diagram as a strict timeline where all resolution steps complete at a single point: JLS/JVMS allow the JVM to resolve symbolic references at appropriate times within the constraints of the specification.

### Initialization is different from construction

- **Class initialization** is a type-level procedure, usually occurring **once** for each runtime class defined by a defining class loader.
- **Instance construction** is creating and initializing **each individual object**, which can happen many times; the constructor `<init>` is different from the `<clinit>` method.
- Calling `new Example()` usually leads to class initialization if the class is not yet initialized, and only then proceeds to create and construct the object according to Java rules.
- Calling `Class.forName("Example")` can initialize the class without **creating any `Example` instance**.

## 2. Four typical active use operations in JLS `12.4.1

For a class `T`, the JLS specifies that initialization occurs **immediately before the first** occurrence of certain operations, among which the most important cases are:

1. **Creating an instance of `T`**, such as `new T()`; this can also be done via reflection.
2. **Invoking a static method declared by `T`**, such as `T.perform()`.
3. **Assigning a value to a static field declared by `T`**, such as `T.count = 3`.
4. **Reading a static field declared by `T` that is not a constant variable**, such as `System.out.println(T.dynamicValue)`.

Other specific operations, such as certain reflection methods or the first invocation of appropriate method handles, can also force initialization. The initialization of a class's superclass and certain superinterfaces is also triggered **indirectly** by the initialization of that class.

### Quick decision table

| Operation | Actively requests initialization of the related class? | Conditions to remember |
| --- | --- | --- |
| `new T()` | **Yes** | Before creating and constructing the object of `T` if not yet initialized |
| `T.staticMethod()` | **Yes** | Initializes the **class/interface declaring the called method**, not necessarily the class written to the left of the dot |
| `T.nonConstantStaticField` | **Yes** | Reading a field that is not a constant variable |
| `T.staticField = value` | **Yes** | Assigning a static field of the declaring class/interface |
| `T.COMPILE_TIME_CONSTANT` | **No from this read alone** | If it is a **constant variable** properly declared and accessed under constant rules |
| `T.class` | **No** | Obtaining a class literal does not by itself initialize `T` |
| `new T[10]` | **No for component `T`** | Creates an array class/object; does not create a `T` instance |
| `obj instanceof T` | **No from this check alone** | May require type resolution, but does not actively run `T.<clinit>` |
| `(T) obj` | **No from this cast alone** | Checkcast may fail to cast; not an initialization trigger |
| `ClassLoader.loadClass("p.T")` | **No under default contract** | Loads the class, does not require initializing `T` |
| `Class.forName("p.T", false, loader)` | **No** | Requests loading/linking without actively initializing |
| `Class.forName("p.T")` | **Yes** | Single-parameter overload defaults to requesting initialization |
| `Class.forName("p.T", true, loader)` | **Yes** | Can choose loader and actively requests initialization |
| `Class.forName(module, "p.T")` | **No** | `Module`-based overload has a different contract and can return `null` |
| `T[].class` | **No for `T`** | Obtains the class literal of the array type |
| Reflection: invoking static method via `Method.invoke` | **Yes** | If needed, initializes declaring class before invocation |
| Reflection: creating instance via `Constructor.newInstance` | **Yes** | If needed, initializes declaring class before creation |
| Reflection: reading/writing static field via `Field.get`/`set` | **Yes** | Access checks and field state can throw errors |
| `Class.getDeclaredMethods()` | **No from metadata lookup alone** | May load/resolve dependent types; not equivalent to invoking a method |

This table is for **direct causes**. If a passive operation calls into a library with side effects, or another thread concurrently performs an active use on the same class, you may still observe that the class has been initialized; do not conclude that a passive API is a trigger just because logs appear nearby.

## 3. Java 17 program: load, get `Class<?>`, and then initialize

Create the file **`ActiveUseMatrix.java`**:

```java
public class ActiveUseMatrix {
    public static class Target {
        public static final int CONSTANT = 7;

        static {
            System.out.println("Target.<clinit>");
        }

        public static int dynamic = compute();

        private static int compute() {
            System.out.println("Target.compute");
            return 42;
        }

        public static void ping() {
            System.out.println("Target.ping");
        }
    }

    public static void main(String[] args) throws Exception {
        ClassLoader loader = ActiveUseMatrix.class.getClassLoader();
        String name = ActiveUseMatrix.class.getName() + "$Target";

        System.out.println("01 constant=" + Target.CONSTANT);

        Class<?> literal = Target.class;
        System.out.println("02 literal=" + literal.getSimpleName());

        Class<?> viaLoader = loader.loadClass(name);
        System.out.println("03 loadClass same=" + (viaLoader == literal));

        Class<?> viaForName = Class.forName(name, false, loader);
        System.out.println("04 forName(false) same=" + (viaForName == literal));

        Class<?> arrayType = Class.forName("[L" + name + ";", false, loader);
        System.out.println("05 array=" + arrayType.isArray());

        Class.forName(name, true, loader);
        System.out.println("06 after forName(true)");

        Target.ping();
        System.out.println("07 done");
    }
}
```

Run with a JDK whose `javac` supports Java 17:

```bash
javac --release 17 ActiveUseMatrix.java
java ActiveUseMatrix
```

**Exact stdout**:

```text
01 constant=7
02 literal=Target
03 loadClass same=true
04 forName(false) same=true
05 array=true
Target.<clinit>
Target.compute
06 after forName(true)
Target.ping
07 done
```

Step-by-step explanation:

- `Target.CONSTANT` is a **constant variable** because `static final int` is assigned a constant expression. Using the value 7 can be inlined into the caller by the compiler; line 01 does not cause `Target` to initialize.
- `Target.class` obtains a `Class<Target>` but **does not** actively run the static block; line 02 comes before `Target.<clinit>`.
- `loader.loadClass(name)` and `Class.forName(name, false, loader)` identify the same runtime class because of the same defining loader; both identity comparisons with the class literal are `true`, yet `Target` is still not initialized.
- `Class.forName("[L" + name + ";", false, loader)` obtains the **array class** with component `Target`; it neither creates a `Target` instance nor initializes the component class. Line 05 still comes before the static block.
- `forName(name, true, loader)` requests initialization. The static block runs first, and then the static field `dynamic` calls `compute()`. This order comes from the **textual order of static initializers** in `Target`.
- `Target.ping()` runs after the class is already initialized, so `<clinit>` is not re-executed. The line `Target.ping` appears once from the `ping` method.

**Subtle point:** The JVM may have already **loaded** `Target` earlier, including because the verifier needed that type, but what is observed here is that **there was no initialization request** before calling `forName(true)`. Do not use the first log line `Target.<clinit>` to deduce the exact moment the class file was first read from disk.

## 4. Static fields: why `static final` is not necessarily "non-triggering"

It is necessary to distinguish a **constant variable** in the JLS from a field that merely carries `static final` modifiers.

According to JLS `4.12.4, a constant variable must be `final`, have a **primitive or `String`** type, and be initialized with a **constant expression** per JLS `15.29. For example:

```java
static final int LIMIT = 100;            // constant variable
static final String TITLE = "JVM";       // constant variable
static final int SUM = 2 + 3;            // constant variable

static final int RUNTIME = calculate();  // NOT a constant variable
static final Integer WRAPPED = 100;      // NOT a constant variable
static final Object OBJECT = new Object(); // NOT a constant variable
```

This is a **fragment inside a class**, not a standalone program. Note the distinctions:

- `LIMIT`, `TITLE`, and `SUM` satisfy the constant variable conditions.
- `RUNTIME` uses a method call, so it is not a constant expression.
- `WRAPPED` has reference type `Integer`, not primitive or `String`.
- `OBJECT` is a reference to an object created at runtime.
- When code **reads** one of these nonconstant static fields, the normal active use case causes the **declaring class** to be initialized.
- The `ConstantValue` attribute in the class file is part of the mechanism that assigns a value to a constant variable at preparation time; do not infer that reading that constant forces the JVM to run `<clinit>`.

### A program to observe constant and nonconstant fields

Create **`ConstantVsRuntime.java`**:

```java
public class ConstantVsRuntime {
    static class Holder {
        static final String LABEL = "ready";
        static final int FIXED = 5;
        static final Integer BOXED = Integer.valueOf(8);

        static {
            System.out.println("Holder.<clinit>");
        }

        static final int COMPUTED = 10 + runtimeValue();

        private static int runtimeValue() {
            System.out.println("Holder.runtimeValue");
            return 2;
        }
    }

    public static void main(String[] args) {
        System.out.println("label=" + Holder.LABEL);
        System.out.println("fixed=" + Holder.FIXED);

        System.out.println("boxed=" + Holder.BOXED);
        System.out.println("computed=" + Holder.COMPUTED);
    }
}
```

```bash
javac --release 17 ConstantVsRuntime.java
java ConstantVsRuntime
```

**Stdout**:

```text
label=ready
fixed=5
Holder.<clinit>
Holder.runtimeValue
boxed=8
computed=12
```

When `Holder.BOXED` is read, the JVM must initialize `Holder`. During `<clinit>`, field initializers and static blocks run in source order: `BOXED` receives 8, then `Holder.<clinit>` is printed, then `COMPUTED` is initialized via `runtimeValue()` and prints `Holder.runtimeValue`. Afterward, reading `Holder.COMPUTED` does not re-execute initialization.

### Is there any way to read a field without initializing the class?

Getting the **metadata** of a field with `Holder.class.getDeclaredField("BOXED")` is not the same as **reading the field's value**. However, `Field.get(null)` on a static field will require initialization when needed. Do not treat metadata lookup and value access as identical behaviors.

## 5. The class that declares the static member is what matters

A particularly common source of confusion: the expression `Subclass.staticField` **does not necessarily** initialize `Subclass` if that field is actually declared in `Superclass`.

Create **`DeclaringClassRules.java`**:

```java
public class DeclaringClassRules {
    static class Parent {
        static {
            System.out.println("Parent.<clinit>");
        }

        static int value = 10;

        static void show() {
            System.out.println("Parent.show");
        }
    }

    static class Child extends Parent {
        static {
            System.out.println("Child.<clinit>");
        }
    }

    public static void main(String[] args) {
        System.out.println("field=" + Child.value);
        Child.show();
        System.out.println("after inherited members");

        new Child();
        System.out.println("after instance");
    }
}
```

```bash
javac --release 17 DeclaringClassRules.java
java DeclaringClassRules
```

**Stdout**:

```text
Parent.<clinit>
field=10
Parent.show
after inherited members
Child.<clinit>
after instance
```

Explanation:

1. `Child.value` syntactically mentions `Child`, but the field `value` is declared by **Parent**. The read requests initialization of **Parent**, and does not directly force `Child` to initialize.
2. `Child.show()` also points to the static method declared by `Parent`, so it invokes `Parent.show`. `Parent` is already initialized; `Child` is still not.
3. `new Child()` is an active use of `Child`. Superclass `Parent` is already initialized, so this time only `Child.<clinit>` is logged.

Do not confuse **static hiding** with **instance overriding**. The class name to the left of the dot in source code may differ from the final **declaring class** that the compiler/VM links to. When unsure, use `javap -c -v` to see which field/method `getstatic` or `invokestatic` references.

## 6. Operations that do not by themselves initialize the component class

### Class literals and type checks

- `SomeType.class` is a **class literal**; evaluating this expression does not by itself trigger initialization of `SomeType`.
- `obj instanceof SomeType` and the cast `(SomeType) obj` may require the VM to check/resolve the type; they are **not** active-use triggers to run `SomeType.<clinit>`.
- `someClass.getName()`, `getSimpleName()`, or equivalent metadata-reading operations do not imply running the target class's static initializer.
- Metadata APIs **may** involve resolving and loading other types. Do not equate "does not initialize target" with "zero VM work at all".

### Arrays `new T[n]`

`new T[3]` **creates an array object**, not three `T` objects, and does not force `T` to initialize. The reference elements are initially `null`. Conversely, `new T[] {new T()}` **does** create a `T` instance inside the array initializer, so it will trigger initialization when needed.

### Java 17 example

Create **`PassiveOperations.java`**:

```java
public class PassiveOperations {
    static class Element {
        static {
            System.out.println("Element.<clinit>");
        }

        static int DATA = 5;
    }

    public static void main(String[] args) {
        System.out.println("class=" + Element.class.getSimpleName());

        Element[] elements = new Element[2];
        System.out.println("arrayLength=" + elements.length);
        System.out.println("firstIsNull=" + (elements[0] == null));

        Object item = "not an Element";
        System.out.println("instanceof=" + (item instanceof Element));

        System.out.println("before active read");
        System.out.println("data=" + Element.DATA);
    }
}
```

```bash
javac --release 17 PassiveOperations.java
java PassiveOperations
```

**Stdout**:

```text
class=Element
arrayLength=2
firstIsNull=true
instanceof=false
before active read
Element.<clinit>
data=5
```

No operation before `Element.DATA` actively requests initialization of `Element`. Reading the non-constant static field is what causes `Element.<clinit>` to execute.

### Why `Class.forName("[Lpkg.Type;")` needs to be distinguished

With an **array descriptor-like name**, `Class.forName` recognizes an **array class**. Even with the overload that requests initialization, **the component class is still not initialized just by loading the array class**. If the program later executes `new pkg.Type()`, that is a separate active use and must be considered separately.

Do not arbitrarily substitute `pkg.Type[]` (source syntax) for the class-loading string; for reference arrays, the name format uses `[Lpkg.Type;`; for primitive `int[]` arrays, it uses `[I`. The primitive name `int` itself is not a binary class name to load like a regular class.

## 7. `Class.forName` and `ClassLoader.loadClass`: choosing the right overload

| Call | Chosen loader | Actively requests initialization? |
| --- | --- | --- |
| `Class.forName(name)` | Loader of the **class calling** `Class.forName` (caller-sensitive) | **Yes** |
| `Class.forName(name, true, loader)` | Passed-in loader, `null` is bootstrap loader | **Yes** |
| `Class.forName(name, false, loader)` | Passed-in loader | **No** |
| `loader.loadClass(name)` | The loader object being called | **No** under default implementation/contract |
| `Class.forName(module, name)` | Searches within the specified module | **No**, may return `null` if not found |

Several important points:

- `ClassLoader.loadClass(String name)` normally delegates to `loadClass(name, false)`; the `resolve` parameter of the protected overload relates to **linking/resolution**, **not** the initialize flag.
- `Class.forName(name, false, loader)` requests loading and linking without actively initializing. Another thread can concurrently initialize the same class, so `initialize=false` **is not a guarantee that the class remains "uninitialized" forever**.
- `Class.forName(name)` **does not automatically use the Thread Context ClassLoader**. A framework may obtain `Thread.currentThread().getContextClassLoader()` and pass that loader into the three-parameter overload if it needs to find a provider by context.
- For the same **runtime class** and defining loader, the initializer runs according to initialization-state rules, not again on every `forName(true)` call. The same class name **defined by two different defining loaders** produces two distinct runtime types, each with its own initialization state.
- `Class.forName(module, name)` is a different API and is not a mechanical replacement for `forName(name, true, loader)` when you need to run the static initializer.

### Plugin pattern: inspect metadata first, actively initialize later

```java
ClassLoader loader = Thread.currentThread().getContextClassLoader();
Class<?> candidate = Class.forName("com.example.Plugin", false, loader);

// Check metadata/type relationships according to the application's contract...
// When deciding to start using the class:
Class.forName("com.example.Plugin", true, loader);
```

This is an **illustrative snippet**; `com.example.Plugin` and the loader must exist in a real application, and you need to check whether `loader` can be null. Actively separating class discovery from initialization helps reduce side effects when scanning many plugins, though it does not eliminate all loading/linking of metadata dependencies.

## 8. Reflection: reading metadata is not the same as invoking a method / creating an instance

Reflection uses `Class<?>` as a "type descriptor object", but each operation has a different level of active use.

- `type.getDeclaredMethods()`, `getDeclaredFields()`, and `getDeclaredConstructor(...)` are normally **metadata lookups**, and do not by themselves request running the target class's `<clinit>`.
- `method.invoke(null, ...)` on a **static method** requires the JVM to initialize the declaring class before invocation if needed.
- `constructor.newInstance(...)` requires the class to be initialized before creating the instance.
- `field.get(null)` or `field.set(null, value)` on a **static field** requires initialization per the reflection contract before reading/writing the value, unlike merely obtaining `Field` metadata.
- Reflection also checks **accessibility** and module boundaries. A located method may still be uncallable due to `IllegalAccessException` or module policy; those errors cannot be fixed by trying to call `Class.forName(true)`.

### Example: metadata first, active use later

Create **`ReflectionInitialization.java`**:

```java
import java.lang.reflect.Method;

public class ReflectionInitialization {
    public static class Service {
        static {
            System.out.println("Service.<clinit>");
        }

        public static void hello() {
            System.out.println("Service.hello");
        }
    }

    public static void main(String[] args) throws Exception {
        ClassLoader loader = ReflectionInitialization.class.getClassLoader();
        String name = ReflectionInitialization.class.getName() + "$Service";

        Class<?> type = Class.forName(name, false, loader);
        Method hello = type.getDeclaredMethod("hello");
        System.out.println("metadata acquired");

        hello.invoke(null);
        System.out.println("invocation completed");
    }
}
```

```bash
javac --release 17 ReflectionInitialization.java
java ReflectionInitialization
```

**Stdout**:

```text
metadata acquired
Service.<clinit>
Service.hello
invocation completed
```

`Class.forName(false)` and `getDeclaredMethod` allow acquiring metadata first; `Method.invoke` on the static method causes `Service` to initialize if not yet initialized. `Method.invoke` can wrap an error **inside the method body** into an `InvocationTargetException`, whereas an **initialization failure** can manifest as an `ExceptionInInitializerError`; read the actual cause/stack trace rather than lumping all reflection errors into one category.

## 9. Subclass initialization pulls in the superclass and some superinterfaces

Not only operations targeting `T` directly cause other classes/interfaces to be initialized. When the JVM initializes a **class**:

1. It executes the procedure ensuring the required superclass is already initialized.
2. It also initializes **superinterfaces that declare default methods** according to the rules in JVMS `5.5, including certain indirect superinterfaces in a defined order.
3. Only then does the target class complete its own initialization.

Do not interpret this as "initializing a class always initializes every implemented interface": an interface **without default methods** is not necessarily initialized just because a class implements it. Interface rules also differ from class superclass ordering.

### Illustrative example with a default method

Create **`DefaultInterfaceInitialization.java`**:

```java
public class DefaultInterfaceInitialization {

    static int announce(String message) {
        System.out.println(message);
        return 1;
    }

    static class Base {
        static {
            System.out.println("Base.<clinit>");
        }
    }

    interface WithDefault {
        int FLAG = announce("WithDefault.<clinit>");

        default void action() {
            // Does not need to be called for WithDefault to initialize when Derived initializes.
        }
    }

    static class Derived extends Base implements WithDefault {
        static {
            System.out.println("Derived.<clinit>");
        }
    }

    public static void main(String[] args) {
        System.out.println("before new");
        new Derived();
        System.out.println("after new");
    }
}
```

```bash
javac --release 17 DefaultInterfaceInitialization.java
java DefaultInterfaceInitialization
```

**Stdout**:

```text
before new
Base.<clinit>
WithDefault.<clinit>
Derived.<clinit>
after new
```

Explanation: `new Derived()` requires initialization of `Derived`. `Base` is the superclass and must be initialized first; `WithDefault` declares a default method, so initializing `Derived` also pulls in the appropriate interface; finally `Derived.<clinit>` is printed.

An interface can still be initialized **directly** by reading a static field **that is not a constant variable** of the interface or by calling a static method of the interface. An interface's initialization state should **not** be inferred solely from code declaring `implements`.

### Calling a default method and interface loading

Although an interface default method has a body, calling `interfaceRef.action()` dispatches based on the receiver and JVMS method selection rules. It does not mean every interface loaded at startup runs its initializer. The presence of a default method in the superinterface chain **relates to** initialization rules when an implementing class is initialized; the first call to `action()` is not always the trigger.

## 10. Method handles can also be active use

An advanced point from JVMS `5.5: the **first invocation** of a `MethodHandle` resolved from certain **symbolic method handle kinds** can trigger initialization of the class/interface declaring the corresponding member. The reference kinds to remember:

- `REF_getStatic`
- `REF_putStatic`
- `REF_invokeStatic`
- `REF_newInvokeSpecial`

Do not conclude that "obtaining a `MethodHandle`" always runs the static initializer. You must look at the **symbolic reference kind, resolution and invocation timing**, and the contract of the relevant API. Obtaining/looking up a `MethodHandle` and **executing the handle** are two events that must be distinguished.

Conversely, merely creating a `MethodType` or getting `Class` metadata is not "calling a static method" just because a method name appears in a lookup string.

### Why shouldn't you learn this mechanism with a normal `staticMethod()` example?

The compiler can directly emit `invokestatic` and `getstatic` for ordinary calls. Method handles are a different call representation layer with their own lookup and adaptation mechanisms. If you are analyzing a class file with `invokedynamic`, the bootstrap method may indirectly access method handles; always inspect the bootstrap owner, constant pool, and specific semantics rather than assuming every `invokedynamic` has the same initialization conditions.

## 11. Bytecode shows which trigger is used, but does not require initialization at resolution time

A source–bytecode correspondence table:

| Java source | Typical opcode/representation | Why it relates to initialization |
| --- | --- | --- |
| `new Target()` | `new` + `dup` + `invokespecial <init>` | `new` creates an instance, requiring initialization of `Target` when needed |
| `Target.staticMethod()` | `invokestatic` | `Target` **declaring class** must be initialized per the rules |
| `Target.dynamicField` | `getstatic` | Non-constant static field requires active use |
| `Target.dynamicField = x` | `putstatic` | Writing a static field requires active use |
| `Target.class` | `ldc` class constant or valid representation | Class literal does not by itself initialize `Target` |
| `Target.CONSTANT` | May become a direct literal constant, `bipush`/`ldc`... | Constant variable can be inlined, no `getstatic` needed |
| `new Target[3]` | `anewarray` (usually) | Creates an array, **does not** create a `Target` instance |
| `obj instanceof Target` | `instanceof` | Type check, not an active use of `Target` |
| `(Target) obj` | `checkcast` | Type check, not an initialization trigger |
| `loader.loadClass(name)` | Library API call via `invokevirtual` | Loader API does not directly require target init |
| `Class.forName(name)` | `invokestatic Class.forName` | Init behavior is requested by the `Class.forName` API on the target |

**Especially:** an `ldc` opcode for a class constant and an `invokestatic` opcode calling a static method of a class **differ semantically**. Do not infer "if a class is present in the constant pool, its static block has already run".

`javap` commands to inspect the examples:

```bash
javap -c -v -p ActiveUseMatrix
javap -c -v -p ConstantVsRuntime
javap -c -v -p DeclaringClassRules
```

In the output, look for `ldc ... class`, `getstatic`, `invokestatic`, `new`, `anewarray` along with their constant-pool references. BCI and constant-pool indices are compiler-generated and are not fixed in sequence by the JLS.

### Illustrative bytecode pattern, not verbatim output

```text
ldc #ClassTarget     // get Class<Target>, does not by itself request <clinit>
anewarray #Target    // create array of Target references, does not initialize component
getstatic #Target.x  // read nonconstant static field, may trigger <clinit>
invokestatic #Target.m // call static method, may trigger <clinit>
new #Target          // create instance, may trigger <clinit>
```

Labels like `#ClassTarget` and `#Target` are **placeholders for constant-pool indices**, not exact `javap` output syntax. The phrasing "may trigger" is because if the class was **already initialized successfully** earlier, the same active use **does not run the initializer again**.

## 12. Failed class initialization: erroneous state and error path

Initialization can fail, for example if a static field initializer calls code that throws an exception. Once the JVM marks the class as **erroneous** in that loader, subsequent initialization requests do not re-run `<clinit>` as if the class were brand new.

Create **`InitializationFailure.java`**:

```java
public class InitializationFailure {
    static class Broken {
        static final int VALUE = compute();

        private static int compute() {
            throw new IllegalStateException("boom");
        }
    }

    public static void main(String[] args) throws Exception {
        String name = InitializationFailure.class.getName() + "$Broken";

        try {
            Class.forName(name);
        } catch (ExceptionInInitializerError error) {
            System.out.println("first=ExceptionInInitializerError");
        }

        try {
            Class.forName(name);
        } catch (NoClassDefFoundError error) {
            System.out.println("second=NoClassDefFoundError");
        }
    }
}
```

```bash
javac --release 17 InitializationFailure.java
java InitializationFailure
```

**Stdout**:

```text
first=ExceptionInInitializerError
second=NoClassDefFoundError
```

- The first time, `Class.forName(name)` requests initialization. `compute()` throws `IllegalStateException`, preventing initialization from completing; the runtime reports `ExceptionInInitializerError` for the wrapped exception per the rules.
- The next time, the same class in the same defining loader is erroneous, so the re-initialization attempt typically receives `NoClassDefFoundError` ("Could not initialize class ...").
- `ClassNotFoundException` is a checked exception for **not finding a class by name**; it is not the same as `NoClassDefFoundError` caused by a **prior failed class initialization** or linking/dependency errors.

**Do not use "try calling `forName` again" as a default recovery mechanism**. If startup logic risks failing, design retries at the service or application resource layer instead of hiding too many side effects in static initializers.

## 13. Initialization in multithreaded environments and custom class loaders

JVMS `5.5 specifies a synchronization procedure so that only one thread executes initialization of each class/interface at a time. If thread A is initializing `T`:

- Thread B requesting an active use of `T` may have to **wait** for `T`'s initialization to complete.
- If `<clinit>` code holds locks, performs I/O, or waits mutually, startup can **block or deadlock**. Stack traces / `jcmd Thread.print` can help investigate, but do not replace reading the logic.
- If initialization succeeds, other threads can use `T` with the corresponding synchronization and memory model guarantees.
- If initialization fails, other threads may receive appropriate initialization/linking errors rather than re-running the static initializer themselves.

Class identity consists of **binary name + defining class loader**. Two defining loaders can create two runtime classes with the same name, with **separate** initialization states. A plugin reloaded with a new loader can run the new class's own static initializers, but this is **not** "resetting the class" in the old loader.

Especially in plugin architectures, `Thread.currentThread().getContextClassLoader()` is the **thread-contextual** loader, and does not automatically replace the defining loader of an already-loaded class. `Class.forName(name)` does not use TCCL by default; if you want a plugin loader, pass it explicitly to `Class.forName(name, initialize, pluginLoader)`.

## 14. Common reasoning errors

| Misconception | Correct explanation |
| --- | --- |
| "Getting `Class<?>` means the static block has run" | Loading/metadata and initialization are separate |
| "`SomeClass.class` is an active use like `new SomeClass()`" | A class literal does not force initializing the component class |
| "`new SomeClass[10]` creates 10 `SomeClass` instances" | Only creates an array; each reference element starts as `null` |
| "`instanceof` or cast triggers the target's `<clinit>`" | These are type checks, not initialization triggers |
| "`ClassLoader.loadClass` always invokes the static initializer" | The default contract does not require initialization |
| "`Class.forName(name)` and `Class.forName(name,false,loader)` are the same" | The single-argument overload requests init; the `false` overload does not |
| "`Class.forName(...,false,...)` guarantees the class stays uninitialized when the method returns" | Another thread or active use may initialize it concurrently |
| "Every `static final` is a compile-time constant" | Only primitive/`String` final fields with a constant expression |
| "`Child.staticField` always initializes `Child`" | The JVM considers the **declaring class** of the resolved member |
| "A class implementing an interface means the interface is initialized" | Depends on default methods and active uses; not true in general |
| "Getting a reflection `Method` is equivalent to calling that method" | Metadata lookup is not invocation |
| "`getstatic` and `ldc` of a class constant are equivalent" | One accesses a static field; the other loads constant/class metadata |
| "A class runs `<clinit>` only once JVM-wide even with multiple loaders" | State is per runtime class and defining loader |
| "If init fails, the next time `<clinit>` runs again" | The class can be erroneous and throw a different error next time |
| "Not seeing the static block log means the class is not loaded" | Loading may have occurred earlier without init |
| "`Class.forName(module,name)` also initializes" | The `Module`-based overload does not have that same contract |

## 15. Checklist when designing or debugging

1. **Has the target class already been initialized?** Has there been an active use or indirect initialization via a superclass/default superinterface?
2. **What is the direct operation?** `new`, `invokestatic`, `getstatic`, `putstatic`, reflection invocation, or just `ldc` class literal, `loadClass`, `instanceof`, `anewarray`?
3. **Is the static field a true constant variable or merely `static final`?** Check its type and constant expression; do not rely on a `FINAL` naming convention.
4. **Which class actually declares the member?** `Child.value` may link to `Parent.value`.
5. **Are the class name and loader right?** Binary name, `$` for nested classes, module/classpath, defining loader, and TCCL can differ.
6. **Are you scanning metadata or starting to run a plugin?** Do you need `Class.forName(name,false,loader)` first and only explicitly instantiate/initialize afterward?
7. **Are you reading a static field via reflection or invoking a static method handle?** These operations have different semantics from merely fetching metadata.
8. **Does the class have a slow static initializer or side effects?** Avoid network calls / blocking locks / uncontrolled resource registration in `<clinit>`.
9. **If an error occurs on the second attempt, what was the first error?** Preserve the cause of `ExceptionInInitializerError`; do not see `NoClassDefFoundError` and immediately conclude a missing JAR.
10. **Are you reading the contract or compiler details?** Use JLS/JVMS as the source of truth; `javap` helps illustrate, not decide initialization policy.

## 16. Self-assessment exercises

**Q1.** Does `Class<?> c = Widget.class;` cause `Widget.<clinit>` to run?  
**No**, not from the class literal alone.

**Q2.** Does `Widget[] xs = new Widget[100];` cause `Widget` to initialize?  
**No**, if only creating an array of references; when code actually creates `new Widget()`, it is different.

**Q3.** `Class.forName("p.Widget", false, loader)` returns `Class<?>`. Is the class guaranteed to be initialized?  
**No**. This call does not request init; the actual state still depends on other active uses.

**Q4.** Given `static final int X = 5;` and `static final int Y = compute();`, reading which field can trigger initialization?  
**Y** is a nonconstant static field; reading Y requires init if not yet done. X is a constant variable; normal reading does not.

**Q5.** Given `Sub extends Base`, `Sub.counter` references a static field declared in `Base`. Which class is directly initialized by the read?  
**Base**, not necessarily `Sub`.

**Q6.** `Constructor.newInstance` creates an object via reflection when the class is not yet initialized. Does the initializer run first?  
**Yes**, the class must be initialized per the JVM procedure before instance construction.

**Q7.** Do `getDeclaredMethod` and `Method.invoke` have the same initialization conditions?  
**No**. Acquiring metadata is not the same as executing a static method via reflection.

**Q8.** If a class just failed in `<clinit>`, will the next `Class.forName(name)` call in the same loader initialize it from scratch again?  
**No**; the class is erroneous and may report `NoClassDefFoundError`.

**Q9.** Can you obtain `Class<?>` of an interface without initializing that interface?  
**Yes**. Loading/metadata are separate from initialization; however, reading a nonconstant static field or other active uses can trigger it.
