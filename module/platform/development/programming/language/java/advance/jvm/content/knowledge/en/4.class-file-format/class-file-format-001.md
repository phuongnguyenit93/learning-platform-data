# ClassFile Structure: magic number, major version, and minor version

A Java `.class` file is a **binary file following the ClassFile format defined by the JVM Specification**. It is typically generated by the `javac` compiler from source code, but can also be produced by bytecode generation or transformation tools. A ClassFile contains the format identifier, class file version, constant pool, class description, fields, methods, and attributes. The JVM uses this information to identify, read, verify, link, and execute the class.

The first three fields of the ClassFile structure are the focus of this lesson:

- **`magic`**: the first four bytes with value **`0xCAFEBABE`**, which identify that the data is expected to follow the ClassFile format.
- **`minor_version`**: a **16-bit** unsigned integer indicating the minor version according to the rules of the class file format.
- **`major_version`**: a **16-bit** unsigned integer indicating the major version and serving as an important basis for the JVM to decide whether it supports the class file.

A class file with the right magic number is **not necessarily valid or executable**. The JVM still has to read and check the remaining structure, data types, bytecode, version compatibility, classpath/module path, and referenced dependencies.

## 1. ClassFile is a binary structure, not Java source code

A simple diagram of the first bytes in a typical `.class` compiled for Java 17:

```text
Offset (hex)   00 01 02 03 | 04 05 | 06 07 | 08 09 | ...
Value          CA FE BA BE | 00 00 | 00 3D | ...   | ...
                  magic       minor    major   constant_pool_count ...

magic         = 0xCAFEBABE
minor_version = 0
major_version = 0x003D = 61
```

Each **`u1`** field is 1 byte, **`u2`** is 2 bytes, and **`u4`** is 4 bytes. According to the ClassFile format, multi-byte values are stored in **big-endian** order (most significant byte first). Therefore:

- The byte sequence `CA FE BA BE` represents the 32-bit number `0xCAFEBABE`.
- The sequence `00 00` represents `minor_version = 0`.
- The sequence `00 3D` represents `major_version = 0x003D = 61`, corresponding to the standard class-file version of Java 17.

**This is a header example, not the entire file.** The bytes at offset 8–9 are `constant_pool_count`; the actual value depends on the number of entries in the constant pool generated by the compiler. Do not guess it from the example without reading the file.

### Why can't `.class` be opened as text?

A `.java` file contains source code characters; a `.class` contains a structured sequence of bytes, integers, indices, encoded strings, and bytecode. A text editor may display gibberish characters when trying to interpret binary bytes as Unicode. Use `javap -verbose`, a hex viewer, or a binary-reading program to inspect it. The instructions in a `.class` file are **JVM bytecode**, not directly x86-64 or ARM machine code.

## 2. General structure of `ClassFile`

The beginning and component groups described in the JVM Specification have the form:

```text
ClassFile {
    u4             magic;
    u2             minor_version;
    u2             major_version;
    u2             constant_pool_count;
    cp_info        constant_pool[constant_pool_count - 1];
    u2             access_flags;
    u2             this_class;
    u2             super_class;
    u2             interfaces_count;
    u2             interfaces[interfaces_count];
    u2             fields_count;
    field_info     fields[fields_count];
    u2             methods_count;
    method_info    methods[methods_count];
    u2             attributes_count;
    attribute_info attributes[attributes_count];
}
```

This is a **data structure description of the file format**, not Java syntax to put into `ClassFile.java`. The notation `u1/u2/u4` denotes fixed-width unsigned integers, not standalone Java primitive variable types.

| Component | Main function |
| --- | --- |
| `magic` | Identifier for the ClassFile format |
| `minor_version`, `major_version` | Version pair for the JVM to determine reading and support rules |
| `constant_pool_count`, `constant_pool` | Table of constants and symbolic references for class names, fields, methods, strings, literals, descriptors, etc. |
| `access_flags` | Flags describing properties of the class/interface/module such as `public`, `final`, `abstract` at the format level |
| `this_class`, `super_class` | Indices referencing the representations of the current class and superclass respectively in the constant pool |
| `interfaces_count`, `interfaces` | List of interfaces declared as extended/implemented by this class or interface |
| `fields_count`, `fields` | Descriptions of fields, types, flags, and related attributes |
| `methods_count`, `methods` | Descriptions of methods, descriptors, flags, and attributes; a method with code may contain a `Code` attribute |
| `attributes_count`, `attributes` | Metadata such as `SourceFile`, `Signature`, `BootstrapMethods`, `InnerClasses`, etc. when applicable |

The three fields `magic`, `minor_version`, and `major_version` **are at fixed positions**. From `constant_pool` onward, the sizes of blocks can vary. You cannot find `methods_count` using a fixed offset like major version; you must decode the preceding components sequentially.

**Note on `constant_pool_count`:** the constant pool table is indexed starting from **1** and normally has `constant_pool_count - 1` indexed slots. `CONSTANT_Long` and `CONSTANT_Double` constants occupy two **index slots** according to the format rules even though the content is one entry; the next slot is reserved. Therefore, the actual number of entries does not necessarily equal the number of index slots used.

## 3. Magic number: four bytes `CA FE BA BE`

### 3.1. Definition

The beginning of a class file must have exactly:

```text
CA FE BA BE
```

Written as a 32-bit hex integer: **`0xCAFEBABE`**. In Java documentation, the bytes are sometimes written together as `CAFEBABE`, but this is **a `u4` field**, not the four ASCII characters `C`, `A`, `F`, `E`.

Comparison example:

```text
ClassFile bytes:    CA FE BA BE
ASCII "CAFE" bytes: 43 41 46 45
```

The two byte sequences are completely different. When viewing a hex dump, you must check the **actual bytes**, not the rendered text content.

### 3.2. What does Magic do and what can't it do?

The magic number helps tools/the JVM detect early when an input does not have a properly formatted header. If a file starts with `50 4B ...`, for example, it is most likely a ZIP/JAR container rather than a raw class file: a JAR can **contain multiple `.class` files**, but the JAR itself does not start with the ClassFile magic.

Magic is **not a cryptographic signature**; it does not verify the origin or integrity of the file. Anyone can create a file consisting of the four bytes `CA FE BA BE` without the rest of the structure; that file is still not a valid class file. The JVM must proceed to check the version, constant pool structure, attributes, and bytecode.

## 4. `major_version`: the ClassFile version supported by the JVM

**`major_version`** is located at byte offset 6–7 (0-indexed). It typically increments with Java releases, indicating the class-file format level of the file. An older JVM **is not required** to understand every class file format compiled with a newer JDK.

Some common milestones:

| Target Java SE for compilation | `major_version` | Hex of `u2` field |
| --- | ---: | --- |
| Java 8 | 52 | `00 34` |
| Java 11 | 55 | `00 37` |
| Java 17 | 61 | `00 3D` |
| Java 21 | 65 | `00 41` |
| Java 25 | 69 | `00 45` |

The milestones above apply to standard class files of each release, typically with **`minor_version = 0`**. For historical Java versions, minor/major rules may differ; one should not mechanically apply a linear formula to all of Java's history.

Examples:

- Compiling for Java 17 typically produces a class file of version **61.0**.
- Compiling for Java 21 typically produces a class file of version **65.0**.
- A runtime that understands class files up to version **61** will reject a class file requiring **65**, typically with **`UnsupportedClassVersionError`** when attempting to load the class.
- A newer JVM can support older class file versions, but **class format compatibility alone is not enough**: dependencies, APIs, access/module permissions, runtime behavior, or native libraries can still cause errors.

### 4.1. The JDK running the compiler differs from the target release

If you use JDK 21 to run:

```bash
javac --release 17 Hello.java
```

then the compiler is instructed to generate output suitable for **Java 17**, including class-file version 61 and restricting platform APIs to those supported by the target release. That means the **JDK of the compiler tool** can be newer than the **release that the class file targets**.

Conversely, just because a development machine has JDK 21 does not mean every generated class **must** be major 65. You must check the compiler flags and the resulting file.

If you want to guarantee bytecode/runtime APIs for a specific release, prefer `--release N` when the JDK in use supports that target. `-source N` only controls the language level; `-target N` controls the output format, but combining those two flags **does not automatically guarantee** against accidentally using standard APIs from a newer JDK, whereas `--release` controls this part.

### 4.2. File version differs from runtime/API version

It is necessary to distinguish:

```text
JDK used to run javac    → toolchain version
--release or -target     → target bytecode / class-file major version
java --version           → Java runtime being launched
javap -verbose           → version recorded in the specific .class file
```

You cannot conclude the target solely from the name of the source directory or the JAR name. In some cases, the same JAR can even contain **multiple class file variants by release** (multi-release JAR); therefore, you must check the **exact class file entry** being selected.

## 5. `minor_version`: minor version and preview class files

**`minor_version`** is located at byte offset 4–5. It is an unsigned integer from 0 to 65535. For ordinary class files generated by modern Java compilers, minor is typically **0**.

### 5.1. Minor equal to 0

This is the most common case when compiling stable Java applications:

```text
CA FE BA BE 00 00 00 3D ...
             └─┘   └─┘
            minor  major
              0     61 (Java 17)
```

Read `61.0` as **major 61, minor 0**; do not misread 61.0 as Java language version “61”.

### 5.2. Special value `65535` (`0xFFFF`) and preview features

Since the preview mechanism specified for modern Java releases, the class-file version of **preview features** can be marked with `minor_version = 65535` (`0xFFFF`). For example, a class compiled using a Java 17 preview feature may have version **61.65535** recorded.

Points to remember:

- A class file with minor **65535** is intended for the preview mechanism of the corresponding release, **not equivalent to a stable class file** with minor 0.
- A JVM supporting preview requires **`--enable-preview`** when launching a class that uses preview according to that release's rules.
- A class file carrying the preview marker is tied to the **corresponding release**; one should not expect a preview class from an older version to automatically run on a JVM of a newer Java release just because the newer JVM supports a higher major.
- `--enable-preview` in `javac` only supports preview features of **the exact release the compiler is using**, and cannot be used arbitrarily to enable preview of an older release when running a newer compiler.

Having `--enable-preview` does not mean every generated class file necessarily has minor 65535; this also depends on whether the compiled code actually uses features requiring the preview marker and the corresponding compiler/version rules. Reading **the value recorded in the class file itself** is always more accurate than guessing.

### 5.3. Checking the full major/minor pair

A JVM needs to look at the **version pair** rather than just major, according to the set of supported versions and preview rules. For modern class file versions, minor normally only has standard meaning when equal to 0, or 65535 in the case of supported preview. Other combinations may be rejected even if the magic is right.

Version errors typically appear **when the class is loaded/verified**, before bytecode in `main` starts running. A program may have already started and only encounter an error later when another class is loaded for the first time.

## 6. Hands-on with JDK 17+: creating and viewing the header of a class file

To get reproducible results on JDK 17 and above, use **`--release 17`** instead of relying on the default target of the current JDK.

### 6.1. Create the sample class `Hello.java`

Create the file **`Hello.java`** with the content:

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, JVM!");
    }
}
```

From the directory containing the file:

```bash
javac --release 17 -encoding UTF-8 Hello.java
java Hello
```

**Standard output of `java Hello`:**

```text
Hello, JVM!
```

After `javac`, you have the file **`Hello.class`**, which is the input for viewing the ClassFile header. If you get an error `invalid flag: --release` or `release version 17 not supported`, check `javac --version`: you need a JDK that supports target 17.

### 6.2. Using the standard tool `javap -verbose`

```bash
javap -verbose Hello
```

In the long output of `javap`, find the following lines:

```text
minor version: 0
major version: 61
```

These are the lines about the **class-file version**. `javap` can also display the constant pool, class name, descriptors, flags, metadata, methods, and bytecode. Do not confuse the `major version` line with the running JVM version: `javap` is **reading a class file**.

To know the actual JDK/runtime:

```bash
javac --version
java --version
```

The output of these two commands depends on the machine; do not take the JDK version from book examples and assume it for the actual environment.

### 6.3. Reading the exact first 8 bytes with Java

Create the file **`ClassHeaderReader.java`** in the same directory as `Hello.java`:

```java
import java.io.DataInputStream;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class ClassHeaderReader {
    public static void main(String[] args) throws IOException {
        if (args.length != 1) {
            System.err.println("Usage: java ClassHeaderReader <file.class>");
            return;
        }

        Path file = Path.of(args[0]);
        try (DataInputStream input =
                     new DataInputStream(Files.newInputStream(file))) {
            long magic = Integer.toUnsignedLong(input.readInt());
            int minor = input.readUnsignedShort();
            int major = input.readUnsignedShort();

            System.out.printf("magic: 0x%08X%n", magic);
            System.out.println("minor_version: " + minor);
            System.out.println("major_version: " + major);
            System.out.println("magic_valid: " + (magic == 0xCAFEBABEL));
        }
    }
}
```

Compile and run:

```bash
javac --release 17 -encoding UTF-8 ClassHeaderReader.java
java ClassHeaderReader Hello.class
```

**Exact standard output when `Hello.class` is compiled with the command in section 6.1:**

```text
magic: 0xCAFEBABE
minor_version: 0
major_version: 61
magic_valid: true
```

How the program works:

1. `Files.newInputStream(file)` opens the file as a **binary byte stream**.
2. `DataInputStream.readInt()` reads **4 big-endian bytes**; `Integer.toUnsignedLong` is used to represent the value as `u4` without being misinterpreted due to the sign of Java `int`.
3. `readUnsignedShort()` reads **2 big-endian bytes** and returns an `int` in the range `0..65535`, matching the `u2` type of ClassFile.
4. `System.out.printf("0x%08X", magic)` prints the 8 hex digits of magic.
5. Comparing with `0xCAFEBABEL` verifies only the **magic field**, without checking the entire ClassFile or bytecode.

This program reads **exactly the first 8 bytes** and does not parse the subsequent parts. If the file is too short, the read methods may throw `EOFException` (a type of `IOException`); if it does not exist or lacks access permissions, opening the file may throw `IOException`. This is a **learning tool**, not a full ClassFile validator.

### 6.4. Inspecting directly with a hex viewer

If you have a suitable hex viewer for your platform, open `Hello.class` and check the first eight bytes:

```text
CA FE BA BE 00 00 00 3D
```

Spaces are only for readability, not bytes in the file. A hex tool may display offset, byte, and corresponding ASCII character columns; the **hex bytes** column is the reliable source for reading the header. Do not directly edit the version bytes to “upgrade/downgrade” the file: the format, constant pool, and bytecode that follow must actually be compatible.

## 7. `ClassFile` and the JVM class loading process

The class file reading process sits within the JVM runtime lifecycle:

```text
.class file / bytes provided by class loader
                │
                ▼
    Check magic and supported version
                │
                ▼
    Parse ClassFile structure
    constant pool, field, method, attribute...
                │
                ▼
    Validation and bytecode verification
                │
                ▼
    Linking / initialization when needed
                │
                ▼
    Execute method bytecode by JVM
```

The diagram is intended to clarify **responsibilities**, without guaranteeing the exact detailed order of every operation is identical across all JVMs or that every class is verified/resolved/initialized completely all at once.

- **Class loader** provides the class definition as bytes; the source can be a `.class` file, an entry in a JAR, a module, or another loader mechanism.
- **Format identification**: the magic number and class-file version help the runtime determine whether the format can be read and is permitted to be processed.
- **Structure parsing**: the JVM checks the organization of blocks and constraints on information such as the constant pool, class names, descriptors, and attributes.
- **Bytecode verification**: the JVM checks type/stack-state safety conditions and instruction validity according to the corresponding class file rules.
- **Linking, initialization, and execution**: the runtime prepares and initializes the class at the appropriate time, then executes the required methods.

Classes can be loaded **lazily** when used by the program. Therefore, class format or incompatibility errors in a dependency may appear **after** the main class has already run partially. It must not be assumed that the magic number replaces the role of the verifier.

### Errors related to ClassFile

| Error/symptom | Meaning to check |
| --- | --- |
| `ClassFormatError` | The ClassFile data has an invalid structure; inspect the class bytes and class generation/transformation tools |
| `UnsupportedClassVersionError` | The JVM does not support the requested class file version, or the version/preview combination is invalid |
| `VerifyError` | The bytecode does not satisfy the verifier's check requirements |
| `NoClassDefFoundError` | The runtime needs a class but cannot obtain an appropriate definition; may be due to dependencies, classpath, or an earlier initialization error |
| `ClassNotFoundException` | The class-loading-by-name mechanism could not find the class in the search context; depends on how it is called |
| `IOException` from `ClassHeaderReader` | The demo file-reading tool could not open/read enough bytes; not a JVM error when running a program |

`UnsupportedClassVersionError` is a related form of `ClassFormatError`, and `VerifyError` belongs to the `LinkageError` group. In real applications, keep the stack trace intact and check the **specific class name** causing the error; do not assume the error lies in the class specified in the `java` command.

## 8. Why might a new class file not run on an older JVM?

Suppose the source code is syntactically compatible, but you compile with JDK 21 `javac` without setting a target release and get output major **65**. A Java 17 JVM that only understands up to major **61** will reject that class file.

```text
Default javac JDK 21
       │
       └── class file 65.0
                │
                └── Java 17 JVM (max major 61) → not supported

javac JDK 21 --release 17
       │
       └── class file 61.0
                │
                └── Java 17 JVM → matching class-file version
```

The last line only says **the file version is supported**; it does not guarantee the application will run successfully if external libraries, configuration, data, or runtime behavior have issues.

### Distinguishing four cases

1. **Compilation error**: `javac` does not produce a valid class for faulty source code, e.g., syntax error or using an API not in the target `--release`.
2. **Class file has too new a major**: the JVM rejects it at the class loading stage, possibly reporting `UnsupportedClassVersionError`.
3. **Matching major but malformed bytes**: the class file can still be rejected with `ClassFormatError` or `VerifyError`.
4. **Valid major and bytes but missing dependency**: errors loading/linking other classes can still occur.

To diagnose, use:

```bash
java --version
javac --version
javap -verbose Hello
```

Then read the `major version`/`minor version` lines in the `javap` output and compare against the releases supported by the actual runtime.

## 9. What should not be inferred from the 8-byte header alone

**You cannot conclude the program is safe.** The header does not check digital signatures, download source, packages, malicious bytecode, or business logic.

**You cannot know all the APIs the program uses.** The major version can tell about the class file format level, but to determine specific methods/fields/dependencies you must inspect the constant pool, method bytecode, descriptors, and dependent classes. `--release` restricts standard Java APIs at compile time but does not check every external library.

**You cannot know what optimizations the JIT will perform.** The header belongs to the storage format; the JIT is a runtime mechanism processing already-loaded bytecode. A `.class` does not directly contain JIT-generated machine code for the current CPU.

**You cannot assume the file has only one kind of metadata.** `attributes` can contain compiler/debugger/framework data; the JVM has rules for recognizing attributes, ignoring unrecognized ones when appropriate, and validating attributes with standard meanings.

**You cannot check the integrity of a JAR using ClassFile magic.** A JAR is a ZIP container; you must open the exact `.class` entry inside and read each header. The same application can have multiple class files with different majors due to the build process or multi-release JAR design.

## 10. Practice exercises and self-check questions

### Exercise A — Calculating version from bytes

You read the first eight bytes:

```text
CA FE BA BE 00 00 00 41
```

- Magic is **`0xCAFEBABE`**.
- Minor = **0**.
- Major = **`0x0041 = 65`**, corresponding to the standard Java 21 class-file version.

If you try to open it with a Java 17 JVM, the version check step will fail because Java 17 does not support major 65.

### Exercise B — Inferring the preview marker

Header:

```text
CA FE BA BE FF FF 00 3D
```

- Magic is still `0xCAFEBABE`.
- Minor = `0xFFFF = 65535`.
- Major = `0x003D = 61`.

This is the value pair associated with **Java 17 preview version class** according to the format rules. It requires appropriate preview support conditions and cannot be treated like a stable 61.0 class.

### Exercise C — Why is the right magic not enough?

Create a file yourself containing only four bytes:

```text
CA FE BA BE
```

It has the right magic but **does not have enough bytes for `minor_version` and `major_version`**, not to mention the other required components. The file does not form a valid ClassFile; the `ClassHeaderReader` program above will encounter an error reading insufficient data.

### Review questions

**1. Is `major_version` the version of the JDK running `java` or of `.class`?**  
It is the **format version field of the class file**. It is recorded at file creation/transformation time; the JDK runtime is a separate piece of information.

**2. Why does `00 3D` give the result 61?**  
Because ClassFile stores integers in **big-endian**, `0x003D` in base 16 equals **61** in base 10.

**3. Is `minor_version = 0` always true for every historical ClassFile?**  
**No.** For modern stable Java class files, minor is typically 0; older versions had their own historical rules, and modern preview can use 65535.

**4. Will a file with the right magic but invalid bytecode be run by the JVM?**  
It cannot be guaranteed. The JVM still has to check **structure, types, verifier, version, and linking rules**.

**5. Why not change `00 41` to `00 3D` to run Java 21 bytecode on Java 17?**  
Changing two bytes only changes the **version label**, not downgrading the structures/opcodes/APIs encoded for a higher release. The file may no longer be valid or still fail to run.

**6. What does `javap -verbose` help check?**  
It reads the **actual information of the class file**: major/minor version, constant pool, class/method structure, descriptors, and attributes that the tool supports displaying.

When investigating a `.class` file, check in order: **4 magic bytes `CAFEBABE` → 2 minor bytes → 2 major bytes → entire structure and bytecode → runtime/dependency compatibility**. The first three fields help detect format errors or version incompatibility early; it is the subsequent reading and checking steps that determine whether the ClassFile can be loaded and executed by the JVM.
