# `tableswitch` and `lookupswitch`: how the JVM represents `switch` instructions

When you see a `switch` statement or expression in Java, you are reading **language syntax**. When you open the `.class` file with `javap -c`, you may see two dedicated JVM opcodes: **`tableswitch`** and **`lookupswitch`**. Both select a branch based on an `int` value, but they store the branches in two different structures.

- **`tableswitch`** stores a jump table for **every integer value in a contiguous range** from `low` to `high`.
- **`lookupswitch`** stores a **list of `match → target` pairs** sorted in ascending order by key.

This difference explains why a switch with close cases usually uses `tableswitch` while sparse cases usually use `lookupswitch`. This is a **compiler optimization tendency**, not a guarantee that the Java Language Specification requires a specific opcode to be chosen for a given piece of source code.

This lesson focuses on the bytecode mechanism, how to read the data with `javap`, handling `default`, missing values, class file representation, and the limits when inferring from Java code. The examples run on **Java 17+**.

## 1. Going from Java `switch` to JVM instruction

Java code:

```java
static int level(int code) {
    return switch (code) {
        case 1 -> 10;
        case 2 -> 20;
        case 3 -> 30;
        default -> -1;
    };
}
```

This is an **illustrative method snippet**, not a standalone program. In the `.class` file generated by `javac`, the JVM no longer processes the `case` or `->` keywords of Java source. It executes the bytecode generated by the compiler, typically following this sequence:

```text
load variable/parameter containing key
        │
        ▼
  operand stack: [int key]
        │
        ▼
  tableswitch OR lookupswitch
        │
        ├─ matching case → instruction at corresponding target
        └─ no match → instruction at default target
                │
                ▼
     execute branch code then continue/return
```

**Both opcodes consume one `int`-type value at the top of the operand stack.** They do not directly accept `String`, `enum`, `long`, or an arbitrary object as a key. If a Java switch has another type, the compiler must apply a conversion/mapping step or generate a different control structure.

### 1.1. Quick comparison

| Criterion | `tableswitch` | `lookupswitch` |
| --- | --- | --- |
| Opcode | **170**, hexadecimal `0xaa` | **171**, hexadecimal `0xab` |
| Key on operand stack | One `int` | One `int` |
| Main data | `low`, `high`, then `high-low+1` offsets | `npairs`, then `npairs` pairs of `match, offset` |
| Described values | Every integer in the range `[low, high]` | Only the listed `match` keys |
| Undeclared case | Table entry can point to the default branch | No match pair, uses the default branch |
| Table access by design | Bounds check then index by `key-low` | Search for a key in the match list |
| Data length | By **width of the key range** | By **number of listed keys** |
| Situation compiler usually chooses | Relatively dense cases | Cases far apart |

The two instructions **do not store the result of each case directly**; they store **relative jump addresses** to the bytecodes that execute the branch body. Multiple different keys can jump to the same target.

## 2. `tableswitch`: jump table over a contiguous key range

With cases `3, 4, 5, 6`:

```java
static String classify(int code) {
    return switch (code) {
        case 3 -> "THREE";
        case 4 -> "FOUR";
        case 5 -> "FIVE";
        case 6 -> "SIX";
        default -> "UNKNOWN";
    };
}
```

The compiler can organize a table:

```text
index value   jump-table index   bytecode target
3             0                  case 3
4             1                  case 4
5             2                  case 5
6             3                  case 6
other         —                  default
```

Typical bytecode description when using `tableswitch`:

```text
iload_0
tableswitch { // 3 to 6
    3: <target case 3>
    4: <target case 4>
    5: <target case 5>
    6: <target case 6>
    default: <target default>
}
```

**The labels `<target ...>` are explanatory notation**, not actual bytecode offsets; `javap` will display the offset numbers of the compiled program.

### 2.1. Algorithm at the instruction semantics level

When `tableswitch` executes:

1. Pop and remove an `int index` from the operand stack.
2. If `index < low` or `index > high`, select the `default` offset.
3. Otherwise, compute **`position = index - low`** and retrieve the offset at that position in the jump table.
4. Add the selected offset to the **`tableswitch` opcode address** to determine the target instruction address.
5. Continue execution at the target instruction address.

Pseudocode:

```text
key = pop_int()
if (key < low || key > high) {
    relativeOffset = defaultOffset
} else {
    relativeOffset = jumpOffsets[key - low]
}
nextPc = switchOpcodePc + relativeOffset
```

This is a **semantic** description, not a requirement that the JVM/JIT must implement it using that exact sequence of machine operations.

### 2.2. Missing cases still must have a table entry

Suppose the source only has `1, 3, 5`:

```java
static String oddLabel(int x) {
    return switch (x) {
        case 1 -> "ONE";
        case 3 -> "THREE";
        case 5 -> "FIVE";
        default -> "OTHER";
    };
}
```

If the compiler chooses `tableswitch` with `low = 1`, `high = 5`, it must have **5 entries**, even though the source only has 3 cases:

```text
key:         1        2         3         4         5
entry:   case 1    default   case 3    default   case 5
```

Missing cases **do not have a separate Java branch**; the corresponding entries can point to the same `default` target. This is an important detail when estimating table size: `high-low+1` can be much larger than the number of cases.

**Extreme example:** if there are only cases `1` and `1_000_000`, `tableswitch` would have to cover about **1 million entries** if choosing that same range. Because of the waste, the compiler usually leans toward `lookupswitch` or another approach.

### 2.3. Data section size of `tableswitch`

Instruction format:

```text
tableswitch (1 byte opcode: 0xaa)
  0..3 byte padding
  default (4 byte signed offset)
  low     (4 byte signed int)
  high    (4 byte signed int)
  jump offsets[high - low + 1]   (4 bytes per offset)
```

With `N = high-low+1`:

```text
total bytes = 1 + padding + 12 + 4*N
```

This is the **instruction length in bytecode**, not counting the code of the cases after the table and other class file metadata. For example, `low=3, high=6` has `N=4`, so it uses **29 to 32 bytes** for the instruction itself, depending on 0–3 bytes of padding.

`low` and `high` must satisfy `low <= high`. Every jump target in the table and `default` must point to **the opcode of a valid instruction within the same method**.

## 3. `lookupswitch`: sparse key list and match–offset pairs

Example:

```java
static String sparse(int code) {
    return switch (code) {
        case -100 -> "NEGATIVE";
        case 7 -> "SEVEN";
        case 10_000 -> "BIG";
        default -> "OTHER";
    };
}
```

If `lookupswitch` is used, the bytecode stores only **the three keys that appear**:

```text
match        relative jump target
-100         case -100
7            case 7
10000        case 10000
(default)    default
```

The corresponding presentation in `javap -c` usually looks like:

```text
iload_0
lookupswitch { // 3
    -100: <target NEGATIVE>
       7: <target SEVEN>
   10000: <target BIG>
 default: <target OTHER>
}
```

Unlike `tableswitch`, there are no entries for the numbers between `7` and `10000`. Therefore, this structure usually saves space when the key range is wide but the number of cases is small.

### 3.1. Semantics of `lookupswitch`

When the JVM executes:

1. Pop an `int` key from the operand stack.
2. Search for a `match` value equal to the key in the stored list of pairs.
3. If a match is found, take the accompanying offset; otherwise, take `default`.
4. The jump target equals **the `lookupswitch` opcode address + the selected offset**.
5. Continue from the opcode at the target.

```text
key = pop_int()
pair = lookup_match(key)
relativeOffset = pair.found ? pair.offset : defaultOffset
nextPc = switchOpcodePc + relativeOffset
```

**The `match` values must be sorted in ascending order by signed integer value.** This is a **constraint of the class-file format**, not just a display choice of `javap`. A JVM or implementation may exploit the sorted order to search efficiently, but **the JVMS does not mandate** a specific search algorithm such as binary search.

### 3.2. Data size of `lookupswitch`

```text
lookupswitch (1 byte opcode: 0xab)
  0..3 byte padding
  default (4 byte signed offset)
  npairs  (4 byte signed int, non-negative)
  match_0 (4 byte signed int), offset_0 (4 byte signed int)
  match_1 (4 byte signed int), offset_1 (4 byte signed int)
  ...
```

With `P = npairs`:

```text
total bytes = 1 + padding + 8 + 8*P
```

With 3 cases, the instruction occupies **33–36 bytes**, depending on padding. A `tableswitch` covering around one million values is clearly not an economical storage choice in this situation.

`npairs` can be 0 in a valid instruction format according to the JVMS. In that case there are no match pairs; every key takes the `default` branch. However, a normal Java compiler does not necessarily generate such a `lookupswitch` for an empty source switch.

## 4. Why do the instructions need 0–3 bytes of padding?

Bytecode is a stream of variable-length opcodes and operands. The two instructions `tableswitch` and `lookupswitch` are special because **the 32-bit fields inside them must start at an address divisible by 4, measured from the start of the method's code**.

- After the **1-byte opcode**, there can be **0, 1, 2, or 3 padding bytes**.
- The first byte of the `default` field must be at an offset divisible by 4 in the `Code.code[]` array.
- Padding aligns **the internal operands**; it does not require the switch opcode's address to be divisible by 4.
- The 32-bit numbers of the two instructions are encoded in big-endian according to the JVM format.
- Padding bytes are not new cases or targets; when reading the binary file, the exact number of padding bytes must be skipped.

If the opcode starts at index `p` in the code array, the number of padding bytes is:

```text
padding = (4 - ((p + 1) % 4)) % 4
```

Example:

| Opcode starts at `p` | Offset right after opcode | Padding | `default` starts |
| ---: | ---: | ---: | ---: |
| 0 | 1 | 3 | 4 |
| 1 | 2 | 2 | 4 |
| 2 | 3 | 1 | 4 |
| 3 | 4 | 0 | 4 |
| 4 | 5 | 3 | 8 |

All offsets in the table are calculated **from the start of the method's bytecode**, not from the start of the entire `.class` file. Do not use the absolute file address to calculate padding.

### 4.1. Jump target is a relative offset from the switch OPCODE

This is a common mistake when writing your own disassembler:

```text
If the tableswitch/lookupswitch opcode starts at code offset 12
and a jump offset has value +40
→ the target is code offset 52

NOT:
  12 + 1 + padding count + 40
  or the position right after the entire instruction + 40
```

Even when `default` is a negative value, the target address is still calculated as **switchOpcodePc + signedOffset**. Every computed target must be **the start of a valid opcode belonging to that method**, and must not point into the middle of an operand, padding, or another instruction.

This is especially important when instrumentation modifies bytecode: adding or removing an instruction before the switch can change the padding; changing the switch structure also requires updating offsets, other branches, and related frame verification metadata.

## 5. How does the compiler choose `tableswitch` or `lookupswitch`?

For integer `case`s, a natural criterion is the **density of the key set**:

```text
rangeSize = maxCase - minCase + 1
caseCount = number of distinct case values
density = caseCount / rangeSize
```

If `rangeSize` is close to `caseCount`, the jump table has few gaps. If `rangeSize` is very large while `caseCount` is small, storing offsets for every value in the range wastes class file space.

Regarding the cost **of the instruction itself alone** and ignoring padding:

```text
tableswitch: 1 + 12 + 4 * rangeSize
lookupswitch: 1 + 8 + 8 * caseCount
```

This comparison is useful for understanding the trade-off in **bytecode size**, but it is **not a mandatory formula** that decides which instruction the compiler will use. The compiler may consider many factors or use its own heuristics; the choice varies between versions/toolchains or when other optimizations are present.

For example, with cases `1, 2, 3, 4`:

- `rangeSize = 4`, `caseCount = 4`.
- `tableswitch` has dense data and few gaps.
- The `javac` compiler usually chooses `tableswitch`.

With cases `-100, 7, 10000`:

- `rangeSize = 10101`, `caseCount = 3`.
- `tableswitch` would need over ten thousand offsets.
- The `javac` compiler usually chooses `lookupswitch`.

**There is no “50% threshold” or “more than 5 cases always uses tableswitch” guaranteed by the Java Language Specification.** Any certain conclusion for a running class must come from **the actual bytecode**.

### 5.1. Is `tableswitch` necessarily faster?

One cannot claim “every `tableswitch` is always faster than every `lookupswitch`” in real programs:

- `tableswitch` supports indexed lookup, but can make the instruction large if the key range is wide.
- `lookupswitch` saves data for sparse keys, but needs to search for a match.
- The JVM interpreter may execute the two instructions directly in its own implementation-specific way.
- **The JIT compiler** may turn them into machine-code jump tables, branched comparisons, decision trees, or other forms.
- Actual performance depends on key distribution, cache, branch prediction, code size, runtime profile, and the code in each branch.

Therefore, when optimizing an application, use an appropriate profiler/benchmark; do not write convoluted code to force an opcode without proving a benefit. In source code, prioritize an understandable and correct `switch` first.

## 6. Java 17+ example: two representations in the same program

Create the file **`SwitchOpcodesDemo.java`**:

```java
public class SwitchOpcodesDemo {

    static String dense(int value) {
        return switch (value) {
            case 1 -> "ONE";
            case 2 -> "TWO";
            case 3 -> "THREE";
            case 4 -> "FOUR";
            default -> "OTHER";
        };
    }

    static String sparse(int value) {
        return switch (value) {
            case -100 -> "NEGATIVE";
            case 7 -> "SEVEN";
            case 10_000 -> "BIG";
            default -> "OTHER";
        };
    }

    public static void main(String[] args) {
        System.out.println("dense(3) = " + dense(3));
        System.out.println("dense(8) = " + dense(8));
        System.out.println("sparse(7) = " + sparse(7));
        System.out.println("sparse(5) = " + sparse(5));
    }
}
```

Compile/run with JDK 17 or later:

```bash
javac --release 17 SwitchOpcodesDemo.java
java SwitchOpcodesDemo
```

**Deterministic stdout:**

```text
dense(3) = THREE
dense(8) = OTHER
sparse(7) = SEVEN
sparse(5) = OTHER
```

Both methods return results according to Java semantics; there is no mandatory difference in external behavior. The notable difference lies in how the compiler chooses to store the jump table in bytecode.

### 6.1. Using `javap` to inspect accurately

```bash
javap -c -p SwitchOpcodesDemo
```

With JDK 17 `javac` and this case shape, typically:

- The `dense` method has a `tableswitch` covering **1 to 4**.
- The `sparse` method has a `lookupswitch` with **3 match pairs** carrying keys **-100, 7, 10000**.
- The body of each case has operations pushing a `String` literal and `areturn`; depending on the compiler, there may be additional branches/metadata.
- `javap` will print the specific opcode/target addresses. Do not assume offset numbers before viewing the output from the compiler used.

An excerpt **illustrating the key fields, not the full dump with fixed offsets**:

```text
dense(int):
  iload_0
  tableswitch { // 1 to 4
       1: <ONE>
       2: <TWO>
       3: <THREE>
       4: <FOUR>
  default: <OTHER>
  }

sparse(int):
  iload_0
  lookupswitch { // 3
      -100: <NEGATIVE>
         7: <SEVEN>
     10000: <BIG>
   default: <OTHER>
  }
```

Read the dump as follows:

1. **`iload_0`:** pushes the `int value` parameter onto the operand stack.
2. **`tableswitch` / `lookupswitch`:** pops the key, selects a target.
3. **`case` target:** loads the corresponding string and returns.
4. **`default` target:** loads `"OTHER"` and returns.
5. Check the printed offsets to see that the actual targets lie **after the switch instruction**, even though that instruction is longer than one byte.

### 6.2. Observing class-file version separately from opcodes

`--release 17` generates bytecode targeting Java 17. Check with:

```bash
javap -v -p SwitchOpcodesDemo
```

Expected version lines:

```text
minor version: 0
major version: 61
```

`tableswitch` and `lookupswitch` themselves **are not preview features**. They are opcodes that have existed since earlier JVM generations. Therefore, `--enable-preview` is not needed to run the valid Java 17 switch expression in the example.

## 7. What about gap cases, `default`, and multiple cases sharing a body?

### 7.1. No explicit `default` in a switch statement

A `switch statement` can be valid without declaring a `default` branch:

```java
static void printIfKnown(int value) {
    switch (value) {
        case 1:
            System.out.println("ONE");
            break;
        case 2:
            System.out.println("TWO");
            break;
    }
}
```

This snippet is an illustrative method. In the class file, **both `tableswitch` and `lookupswitch` always have a `default offset` field** according to the instruction format. When the source has no `default`, the compiler can point default to the code **after the switch**, to skip all branches.

**No `default` in Java source** does not mean **the bytecode switch instruction lacks a default operand**.

### 7.2. Multiple case labels using the same target

```java
static String category(int x) {
    return switch (x) {
        case 1, 2, 3 -> "SMALL";
        case 100 -> "LARGE";
        default -> "OTHER";
    };
}
```

The compiler can have keys 1/2/3 all jump to the code that produces the string `SMALL`. The table data has **multiple keys** but duplicate targets; the JVMS does not require each case to have a new code block.

In `tableswitch`, multiple entries can carry the same offset; in `lookupswitch`, multiple different `match` pairs can have the same offset.

### 7.3. `fall-through` in a classic switch statement

```java
static int countFlags(int x) {
    int result = 0;
    switch (x) {
        case 1:
            result += 1;
        case 2:
            result += 2;
            break;
        default:
            result = -1;
    }
    return result;
}
```

- `countFlags(1)` returns **3**, because after case 1 control flow **continues** into case 2.
- `countFlags(2)` returns **2**.
- `countFlags(3)` returns **-1**.

`tableswitch`/`lookupswitch` only decide **the initial jump target**, while **fall-through** is determined by the sequential instructions after the target. The compiler itself manages branch body layout and `goto`/`break`; the switch opcode does not have a separate “fall-through flag”.

### 7.4. Switch expression and `yield`

A switch expression (Java 14+) requires producing a **value**. With arrow cases, the compiler usually places the branch value on the operand stack and goes to the convergence point or return. If a `{ ... yield value; }` block is used, `yield` is source syntax, not a bytecode opcode named `yield`.

```java
static int points(int n) {
    return switch (n) {
        case 1 -> 10;
        case 2 -> {
            int value = 20;
            yield value;
        }
        default -> -1;
    };
}
```

`tableswitch` or `lookupswitch` still only jump by integer key; they **do not directly decide the return value**. The value is produced by the bytecode at the branch target.

## 8. Which types can be switched on? Why is there not always a switch opcode?

The two opcodes accept **`int`**. However, Java supports richer forms of switch.

| Source switch | Common representation/limitation |
| --- | --- |
| `int` / `byte` / `short` / `char` | Can directly use `tableswitch` or `lookupswitch` on a JVM `int` key |
| `Integer`, `Byte`, `Short`, `Character` | Usually unboxed (and converted appropriately) to use an `int` key; `null` can cause `NullPointerException` in a traditional switch |
| `enum` | The compiler converts enum values into integer keys (possibly via synthetic mapping or ordinal) and then selects the branch |
| `String` | The compiler usually uses `hashCode()`, `equals()`, and one or more switches on integer values; there is no `stringswitch` opcode |
| Pattern switch (standard in Java 21+) | May use `invokedynamic`/bootstrap runtime matching followed by integer branches; a fixed opcode cannot be inferred from the `switch` keyword alone |
| Regular `long`, `float`, `double` in Java 17 | Not allowed as selector types for switch in Java 17 |

Do not confuse **the Java type of the switch expression** with **the input data type of the JVM instruction**. String and enum can be valid Java switches, but that does not mean `tableswitch` compares strings or enum objects by itself.

### 8.1. Switching on `String` usually needs another lookup step

Java 17 example:

```java
static int stringCode(String text) {
    return switch (text) {
        case "ON" -> 1;
        case "OFF" -> 0;
        default -> -1;
    };
}
```

`javac` can generate code based on the string's hash, then check `equals` to handle **hash collisions** semantically correctly. One or more switch opcodes on an `int` key may appear in the resulting code, but **do not directly infer the branch position from the hash value** as if hashes were unique.

If `text == null` in a regular Java 17 `String` switch, operating on the selector can throw `NullPointerException`. With newer-version pattern switches, `case null` rules may differ. You must check **the specific version and switch form** before drawing conclusions about `null`.

### 8.2. Switching on enum does not need an opcode for object types

Java enums have named constants, but JVM switch instructions still take `int`. The compiler can generate code mapping ordinal → case number; codegen details are the compiler's choice, and binary compatibility when an enum changes also depends on how the code was compiled.

You should not reorder an enum to “force tableswitch” without checking business impact and binary compatibility.

## 9. Does JIT machine code keep the jump table style?

`javap` shows **bytecode before JVM runtime optimizations**, not necessarily the actual CPU machine instructions executed.

After the JVM gathers profiles, the JIT compiler may:

- Use a machine jump table for a dense group of cases.
- Generate a sequence of comparisons/branches for sparse keys.
- Reorder branches based on profile, inline case bodies, or simplify code.
- Eliminate the switch when the compiler infers the key is a constant at the call site.
- Execute via the interpreter first and then use compiled machine code later.

There is no 1–1 guarantee that `tableswitch` becomes “a single CPU instruction” or that `lookupswitch` always uses binary search at runtime. **Bytecode is the semantic contract with the JVM**; the actual execution strategy depends on the JVM/JIT/CPU.

If you want to measure, the benchmark must have sufficient warm-up, varied inputs, and avoid constant folding/dead-code elimination. For Java, a framework like JMH is usually more appropriate than writing a short `System.nanoTime()` loop and concluding which opcode is faster.

## 10. Bytecode verifier and jump table validity

When generating or modifying class files manually (ASM, Byte Buddy, instrumentation), you cannot arbitrarily put data into a switch opcode.

### 10.1. Important invariants

For **`tableswitch`**:

- The operand stack must have a suitable `int` key.
- `low <= high`.
- There must be exactly **`high - low + 1`** jump offsets.
- Offsets, including `default`, must lead to **the start of a valid instruction opcode belonging to the current method**.
- The padding region must be placed properly so that the `default` field is four-byte aligned relative to the code array offset.

For **`lookupswitch`**:

- The operand stack must have a suitable `int` key.
- `npairs >= 0`; the number of data pairs matches `npairs`.
- `match` values must be **strictly increasing as signed integers**, not sorted lexicographically as text.
- Each offset must point to a valid opcode in the method, not into the middle of an instruction or padding.
- Padding must be placed properly before `default`.

In addition to format, branches after merging must also have consistent operand stack state, local variables, and `StackMapTable` according to the verification rules of the corresponding class file.

### 10.2. An offset bug when inserting logging

Suppose an agent adds logging bytecode right before `tableswitch`:

```text
Before:
  ... bytecode
  tableswitch (opcode at offset p; padding based on p)

After inserting 1–3 bytes:
  ... new bytecode
  tableswitch (opcode at offset p + delta; padding may change)
```

If you only copy the old operands as-is, the switch structure can become misaligned; jump offsets and other structures depending on code layout must also be recalculated.

In practice, you should use a bytecode library that understands switch structures and computes frames/offsets appropriately. When encountering `VerifyError` or `ClassFormatError` after instrumentation, check alignment, targets, and type state instead of blaming the Java source `switch` logic.

## 11. Observations for debugging and optimization

Useful commands:

```bash
# Compile the example targeting Java 17
javac --release 17 SwitchOpcodesDemo.java

# View instructions and target labels
javap -c -p SwitchOpcodesDemo

# Also view max_stack, max_locals, StackMapTable, version...
javap -v -p SwitchOpcodesDemo

# Execute to verify observable behavior
java SwitchOpcodesDemo
```

Reading workflow:

1. Find the right `dense`/`sparse` method and its corresponding bytecode; do not confuse `main` with the method to be analyzed.
2. Verify the switch opcode appears after the instruction pushing the selector (for example `iload_0`).
3. For `tableswitch`, note `low`, `high`, missing cases, and the `default` target.
4. For `lookupswitch`, note `npairs`, the sorted key list, and the `default` target.
5. Follow the targets to the instructions producing values/running side effects/`goto`/`return`, do not stop at the jump table section.
6. If the goal is performance, use profiling/benchmarking; if the goal is a bug, cross-check the actual bytecode and the JVM/spec.

### 11.1. Symptom analysis table

| Symptom | What to check |
| --- | --- |
| `javap` does not have `tableswitch` even though cases are contiguous | Compiler heuristics, switch optimized into an `if`/`goto` chain or another form |
| `tableswitch` is present but some cases are missing in source | The missing entries may all point to `default` |
| Switch on String but `lookupswitch` on integers appears | That may be a hash-based lookup; must check `equals` and collision-handling branches |
| Cases are in a different order from source | `lookupswitch` stores matches in ascending order; body layout may differ from declaration order |
| Branch target looks like a confusing byte offset number | `javap` displays addresses relative to the start of the method; in the class file, switch offsets are measured from the opcode |
| Class is rejected after bytecode instrumentation | Check entry count, offsets, padding, `StackMapTable`, and verification rules |
| Switch is slow despite having `tableswitch` | Profile to confirm whether time is spent in lookup, case body, boxing, I/O, or cache/branch effects |
| Benchmarks across Java versions give different results | JIT, compiler, layout, profile, options, and hardware environment may differ |

## 12. Common misconceptions

1. **“`switch` in Java always compiles to a switch opcode.”** False. The compiler may use `tableswitch`, `lookupswitch`, or a combination of other instructions, especially with `String`, enum, and pattern switches.
2. **“`tableswitch` contains the exact number of cases written in source.”** False. It must have an entry for **every value in `low..high`**, including gaps.
3. **“`lookupswitch` can store match pairs in any arbitrary order.”** False. The JVMS requires `match` values to be sorted in ascending order.
4. **“The bytecode `default` can be omitted if the source does not declare one.”** False. Both instructions always contain a `default` offset.
5. **“Switch jump offsets are measured from the end of the instruction.”** False. The offset is added to **the switch opcode address**.
6. **“Padding bytes are part of the case table.”** False. They only serve to align the 32-bit data of the instruction.
7. **“`tableswitch` can only be used when every case in the range is declared.”** False. Missing entries can point to `default`.
8. **“`lookupswitch` always uses binary search.”** False. The JVMS describes semantics; the lookup algorithm is up to the implementation.
9. **“`tableswitch` is definitely faster than `lookupswitch`.”** False when generalizing to the JVM/JIT and specific workloads; it must be measured.
10. **“`long` or `double` can be keys for the two instructions.”** False. They pop an **`int`** from the operand stack; Java 17 switches do not allow these types as regular selectors.
11. **“Case order in source must match machine code order.”** False. The compiler/JIT is allowed to lay them out differently while preserving behavior.
12. **“`fall-through` is enabled by a flag in `tableswitch`.”** False. Fall-through comes from the instruction flow after the target, not opcode metadata.

## 13. Self-check (with answers)

**Question 1.** With `tableswitch low=-2, high=2`, how many entries does the jump offsets table have, even if the source only has cases `-2, 0, 2`?

**Answer:** `2 - (-2) + 1 = 5` entries for `-2,-1,0,1,2`. The two undeclared values can point to `default`.

**Question 2.** `lookupswitch` has keys `9, -10, 100`. In what order must they be stored?

**Answer:** `-10, 9, 100` (ascending as signed `int`); source order does not determine the order of match pairs in bytecode.

**Question 3.** If the `tableswitch` opcode is at code offset 10, how many padding bytes are needed so that `default` starts at an offset divisible by 4?

**Answer:** After the opcode is 11; **1 byte** is needed so that `default` starts at offset 12.

**Question 4.** A `lookupswitch` at offset 12 has a relative jump offset `-8`. What is the target address?

**Answer:** `12 + (-8) = 4`, provided offset 4 is indeed the start of a valid opcode in the same method.

**Question 5.** Why can a `switch` on String in bytecode show `lookupswitch` even though the JVM has no string keys?

**Answer:** The compiler turned string matching into a step using integer keys (for example, hash), combined with `equals` comparisons to preserve semantics even with collisions. `lookupswitch` only works with `int`.

**Question 6.** With three keys `1, 2, 3`, is `javac` required to generate `tableswitch`?

**Answer:** No. High density makes `tableswitch` usually suitable, but the JVMS/JLS does not force the compiler to use a specific opcode.

**Question 7.** Can a switch statement missing `default` in source produce `tableswitch` bytecode missing the `default` field?

**Answer:** No. The `default` field is mandatory in the instruction format; the compiler points it to the appropriate control path, such as the code after the switch.

**Question 8.** Why is looking at `javap -c` alone not enough to conclude switch performance on a specific HotSpot build?

**Answer:** `javap` shows bytecode; HotSpot/JIT can compile/transform it into different machine code. Workload/profiler/benchmark data is needed.

## 14. Connecting knowledge: source, class file, and runtime

```text
Java source switch
        │
        ▼
javac chooses lowering strategy
        │
        ├─ dense table    → tableswitch (low..high + offsets)
        ├─ sparse keys    → lookupswitch (sorted match-offset pairs)
        └─ complex type   → conversion/comparison/other dispatch
        │
        ▼
.class — bytecode with valid jump offsets, proper padding
        │
        ▼
JVM verifier / interpreter / JIT
        │
        ▼
Observable behavior according to Java semantics
```

**Remember:** `tableswitch` indexes into a range of integer keys; `lookupswitch` searches for a match in a sorted list of integer keys. Both pop an `int`, have a mandatory `default` target, encode jump offsets relative to **the switch opcode address**, and need padding for 32-bit operands. How a `switch` in source is represented depends on the compiler; how it actually runs can be further optimized by the JIT.
