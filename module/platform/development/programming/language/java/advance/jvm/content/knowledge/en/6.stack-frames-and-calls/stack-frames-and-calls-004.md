# Method Resolution and Method Selection by Actual Object Type in the JVM

When a Java variable is declared with a parent type but points to a subclass object, an instance method call can execute the subclass's implementation. For example, `Animal animal = new Dog(); animal.sound();` can invoke `Dog.sound()`, even though the method name in the bytecode of the call site is referenced through `Animal`. To explain this behavior accurately, we must separate **method resolution (resolving the method reference)** and **method selection/dispatch (choosing the method to execute)**.

In the JVM, those two tasks are not a single operation: **resolution** finds a method matching the symbolic reference in the constant pool; whereas **selection** in `invokevirtual`/`invokeinterface` examines the **runtime type of the receiver object** and the resolved method to choose the appropriate implementation. That is the foundation for overriding and dynamic polymorphism. This article focuses on the Java SE 17 JVM mechanism, relating it to how `javac` selects overloads, invocation opcodes, JVM frames, interface default methods, bridge methods, and cases that do not dispatch dynamically.

## 1. Three Concepts to Distinguish

| Phase | Question to answer | Data used |
| --- | --- | --- |
| **Compile-time method lookup / overload resolution** (JLS `15.12`) | Among same-named methods, which **signature** does the source call choose? | Static type of the expression, argument types, overload applicability, generic inference, and most-specific selection rules |
| **JVM symbolic reference resolution** (JVMS `5.4.3`) | Which method is the constant-pool method reference being called bound to, and is it valid regarding class/interface, name, descriptor, and access permissions? | Methodref/InterfaceMethodref, class loader, class/interface hierarchy, name + descriptor, and linkage checks |
| **Run-time method selection** (JVMS `5.4.6`) | With `invokevirtual` or `invokeinterface`, which implementation does the actual object need to run? | **Run-time class of the receiver**, the resolved method, and overriding/inheritance rules |

Example of an expression `animal.sound()`:

1. The compiler knows `animal` has static type `Animal`, determines that the `sound()` call is valid, and determines the matching return descriptor.
2. In the class file, the invocation contains a symbolic reference such as `Animal.sound:()Ljava/lang/String;`.
3. The JVM resolves that method reference according to linkage rules.
4. When executing the `invokevirtual` instruction on an actual `Dog` object, the JVM selects the `Dog.sound()` implementation if it is a valid override.
5. The JVM creates the corresponding frame/invocation mechanism and transfers control to the selected code.

**Key takeaway:** the static type determines **which calls are valid and which overload is encoded**; the runtime type determines **which override is executed** for an applicable virtual call. Not every method invocation opcode uses this selection step.

## 2. What Information Does a Method Reference in a Class File Contain?

A `.class` file has a **constant pool** containing symbolic references. A reference to a class method normally uses `CONSTANT_Methodref_info`; a reference to an interface method normally uses `CONSTANT_InterfaceMethodref_info`. Each reference carries:

- A class/interface referenced by binary name.
- **Method name**, for example `sound` or `get`.
- **Method descriptor** recording the parameter types and return type at the JVM level.
- Combining these components into a reference that requires resolution, **not yet a machine address** or a fixed pointer to an instruction.

Illustrative descriptors:

| Java method | JVM descriptor |
| --- | --- |
| `String sound()` | `()Ljava/lang/String;` |
| `int add(int a, int b)` | `(II)I` |
| `void accept(Object o)` | `(Ljava/lang/Object;)V` |
| `long calculate(int x, long y)` | `(IJ)J` |
| `String[] split(String text)` | `(Ljava/lang/String;)[Ljava/lang/String;` |

Notation rules: `I` = `int`, `J` = `long`, `V` = `void`, `L...;` is a class/interface reference, and `[` is an array. **A JVM descriptor includes the return type**, whereas Java source **does not** allow overloading differing only by return type. That is why it is necessary to distinguish a “source method signature” from a “JVM method descriptor”, especially when reading bridge methods generated by the compiler.

Example in `javap -c -v` disassembly:

```text
invokevirtual #N  // Method DispatchWalkthrough$Animal.sound:()Ljava/lang/String;
```

Here `#N` is a placeholder notation for the **actual index** in the constant pool; do not treat `N` as a fixed number or part of the actual output. In `javap`, the target of the symbolic reference can be `Animal.sound` even though runtime selects `Dog.sound`. Seeing the parent class name in the constant pool **does not refute** dynamic dispatch.

### Method resolution is not the same as class initialization

- Loading prepares the type representation; linking consists of verification, preparation, and resolution; initialization runs `<clinit>` when trigger conditions occur.
- Method resolution finds the referenced method and checks linkage validity; class initialization is a separate process. `invokestatic` can cause a class/interface to be initialized according to its own rules.
- The JVMS allows implementations to perform resolution with an appropriate strategy (for example, eagerly or on demand); do not claim that every method reference is “only resolved on the exact first call” or “must all be resolved at startup”.
- The JVM may cache resolution results or optimize call sites; that is an implementation detail. The specified guarantee lies in **observable behavior**.

## 3. Java Chooses the Overload at Compile Time, Then the JVM Chooses the Override

Two terms that are often confused:

- **Overloading:** multiple methods with the same name but different parameter lists; the compiler selects the applicable and most specific method based on **static types** at the call site. This is not runtime dispatch based on the actual types of arguments.
- **Overriding:** a subclass provides a replacement implementation for an inherited **instance method**, subject to compatibility of signature, access permissions, return type, and related Java rules. When a virtual call arrives at a receiver belonging to the subclass, the overriding implementation can be selected.

Example:

```java
class Animal { }
class Dog extends Animal { }

static String describe(Animal a) { return "Animal"; }
static String describe(Dog d) { return "Dog"; }

Animal value = new Dog();
System.out.println(describe(value)); // Animal
```

This is an **illustrative snippet**, placed inside an appropriate class to compile. `describe(value)` selects the `describe(Animal)` overload because in the source `value` has type **Animal**. The JVM does not “switch the overload” to `describe(Dog)` when it discovers the runtime object is a Dog. To use the other overload, you must write a call with the corresponding static type (for example, a valid cast), or use an explicit object-based dispatch mechanism.

Conversely:

```java
Animal value = new Dog();
System.out.println(value.sound()); // Assume Dog overrides sound()
```

The compiler selects the method with descriptor `sound()` on static type `Animal`; after resolution, `invokevirtual` can select the overriding body in `Dog`. The two steps involve **different kinds of selection**.

### Caveat about casts

`((Dog) value).sound()` gives the expression static type `Dog` and performs a runtime cast check. Yet even **without a cast**, `value.sound()` can already call `Dog.sound()` if the override is valid. A cast is not a prerequisite for dynamic dispatch; it mainly changes which methods are accessible at compile time, which overload is chosen, or performs a cast check.

## 4. Selection Rules of `invokevirtual` and `invokeinterface`

After resolving the method reference, when executing `invokevirtual`/`invokeinterface`, the JVM examines the **runtime class of the receiver** and the resolved method. A learning model for ordinary instance method cases:

1. If the receiver is `null`, the corresponding instance call throws `NullPointerException`; there is no object from which to select an implementation.
2. If the resolved method belongs to the special `ACC_PRIVATE` case, selection does not proceed as for an overridable method.
3. For an overridable method, examine the receiver's runtime class: if it has a matching overriding method declaration, select it.
4. If that class does not declare an override, walk up to the nearest superclass that has a matching overriding implementation.
5. If none is found in the class chain, examine the **maximally-specific superinterface methods** according to JVMS rules; a matching default method may be selected.
6. If there is no suitable concrete implementation, or there is a special default conflict due to binary changes, the call may cause a linkage/runtime error such as `AbstractMethodError` or `IncompatibleClassChangeError`.

Full details such as method access, override rules, interface/Object methods, abstract/default methods, and linkage errors are specified by JVMS `5.4.3.3–`5.4.6 and each `invoke*` instruction. Do not oversimplify selection as “always find the first method with the same name on the object”: **descriptor and valid overriding capability** also matter.

Hierarchy example:

```text
Animal
  ├─ sound()       [Animal body]
  └─ eat()         [Animal body]
      ^
      |
     Dog
      └─ sound()   [Dog override]

Animal a = new Dog();
a.sound()  → Dog.sound()
a.eat()    → Animal.eat() (Dog does not override)
```

The crucial point is that “the actual method called depends on the runtime type” **does not mean** every method belonging to the runtime class is allowed to be called. A call like `a.bark()` is still rejected by the compiler if `Animal` does not declare/inherit a `bark()` method, even though the runtime object is a Dog.

## 5. The Invocation Opcode Group: Which Instructions Dispatch Dynamically?

| JVM Opcode | Primary use | Relationship to receiver runtime type |
| --- | --- | --- |
| `invokevirtual` | Ordinary class instance methods; most overridable calls | **Has selection** based on receiver class and resolved method |
| `invokeinterface` | Instance calls through an interface method reference | **Has selection** based on receiver, class hierarchy/default interface methods |
| `invokespecial` | Constructors `<init>`, `super.m()` calls, certain special/private instance calls | Has its own target lookup rules; **does not** use the ordinary virtual dispatch mechanism |
| `invokestatic` | `static` methods of a class or interface | No receiver to dispatch on at runtime; finds the resolved static method |
| `invokedynamic` | Dynamic call site linked via a bootstrap method, such as many compiler-generated lambdas/string concats | Separate call site linking mechanism, **not** equivalent to “invokevirtual selects an override” |

### `invokevirtual`

Takes an **object reference** along with arguments on the operand stack, uses the method reference from the constant pool, and then selects the target based on the runtime receiver. If the target is not `native`, the JVM normally creates a **frame** for the called method; the frame receives the receiver in local slot 0 and the parameters in subsequent slots. The frame model in a later section will illustrate this.

### `invokeinterface`

Uses an interface method reference in the constant pool, but the executing object has a concrete runtime class. Example:

```java
Runnable task = new SomeRunnable();
task.run();
```

This is only an **illustrative snippet**; `SomeRunnable` is assumed to implement `Runnable` and have a `run` method. The compiler can emit `invokeinterface Runnable.run:()V`. The actual target is selected according to the class of `task` (or an inherited implementation), not by running bytecode “inside the interface” if the interface method is abstract.

### `invokespecial`

Used for calls with special semantic relationships, such as `new Dog()` needing to invoke constructor `<init>`, or `super.sound()` intentionally starting according to superclass rules. For class files with `ACC_SUPER`, the JVM has additional lookup rules for `super`; saying `invokespecial` “simply executes the exact method named in the constant pool with no lookup” is an oversimplification. However, it **does not select an override from the receiver's runtime class like `invokevirtual`**.

### `invokestatic`

Static methods belong to the class/interface used at compile time/link time, not to an instance. A `static` method in a subclass can **hide** a superclass static method, but does not override it. Calling `Animal.category()` and `Dog.category()` selects two different methods according to the class name in the source. Calling through a variable `Animal ref = new Dog(); ref.category();` is valid in Java, but should not be written that way because it easily misleads readers into thinking dynamic dispatch occurs; the target still belongs to `Animal`.

### `invokedynamic`

`invokedynamic` links a **call site** via bootstrap information in the constant pool. It commonly appears in bytecode generated by the compiler for lambdas or string concatenation in modern Java. Specific behavior depends on the bootstrap and the call site's target; do not assume `invokevirtual`'s override selection table applies to the `invokedynamic` opcode itself, even though a deeper linked method may perform another virtual call.

## 6. Java 17 Program: Clearly Seeing Override, Overload, Static Hiding, Super, and Private

Create the file **`DispatchWalkthrough.java`**:

```java
public class DispatchWalkthrough {

    static class Animal {
        public String sound() {
            return "Animal";
        }

        public String eat() {
            return "Animal.eat";
        }

        public static String category() {
            return "Animal.category";
        }

        private String secret() {
            return "Animal.secret";
        }

        public String reveal() {
            return secret();
        }
    }

    static class Dog extends Animal {
        @Override
        public String sound() {
            return "Dog";
        }

        public String bark() {
            return "woof";
        }

        public static String category() {
            return "Dog.category";
        }

        private String secret() {
            return "Dog.secret";
        }

        public String revealDog() {
            return secret();
        }

        public String callSuper() {
            return super.sound();
        }
    }

    static String describe(Animal value) {
        return "describe(Animal)";
    }

    static String describe(Dog value) {
        return "describe(Dog)";
    }

    public static void main(String[] args) {
        Animal ref = new Dog();
        Dog dog = new Dog();

        System.out.println("virtual=" + ref.sound());
        System.out.println("inherited=" + ref.eat());
        System.out.println("overload=" + describe(ref));
        System.out.println("overloadDog=" + describe(dog));

        // Intentionally demonstrates a static call via a reference;
        // real-world code should use Animal.category() directly.
        System.out.println("static=" + ref.category());
        System.out.println("super=" + dog.callSuper());
        System.out.println("private=" + ref.reveal());
        System.out.println("dogPrivate=" + dog.revealDog());

        try {
            Animal missing = null;
            missing.sound();
        } catch (NullPointerException ex) {
            System.out.println("null=NPE");
        }
    }
}
```

Compile/run on a JDK whose `javac` supports Java 17:

```bash
javac --release 17 DispatchWalkthrough.java
java DispatchWalkthrough
```

**Stdout**:

```text
virtual=Dog
inherited=Animal.eat
overload=describe(Animal)
overloadDog=describe(Dog)
static=Animal.category
super=Animal
private=Animal.secret
dogPrivate=Dog.secret
null=NPE
```

Line-by-line explanation:

- `virtual=Dog`: `ref` has static type `Animal` but the runtime object is `Dog`; `Dog.sound()` overrides it, so it is selected.
- `inherited=Animal.eat`: `Dog` does not override `eat`, so the body inherited from `Animal` executes.
- `overload=describe(Animal)`: `describe(ref)` selects the overload according to the **Animal** type known at compile time.
- `overloadDog=describe(Dog)`: `dog` has static type `Dog`, selecting the overload for Dog.
- `static=Animal.category`: the static method is determined by the static type `Animal` even though `ref` points to a Dog. That is **method hiding**, not polymorphic override.
- `super=Animal`: inside `Dog.callSuper()`, `super.sound()` intentionally invokes the superclass implementation using `invokespecial` semantics.
- `private=Animal.secret`: `Animal.reveal()` calls `Animal`'s own **private** method. `Dog.secret()` has the same name but does not override that private method.
- `dogPrivate=Dog.secret`: the body of `Dog.revealDog()` calls `Dog`'s private method.
- `null=NPE`: a `null` instance receiver cannot be dispatched to an implementation.

`Dog.bark()` exists on the actual object, but adding `ref.bark();` will **not compile**, because the static type `Animal` does not have that method. Dynamic polymorphism does not replace compiler type checking.

### Reading bytecode in the right place

Run the disassembler:

```bash
javap -c -p DispatchWalkthrough
javap -c -p 'DispatchWalkthrough$Dog'
javap -v -p 'DispatchWalkthrough$Animal'
```

Points to observe in the classes generated by `javac`:

- In `DispatchWalkthrough.main`, the `ref.sound()` call normally appears with the **`invokevirtual`** opcode, referencing a method like `DispatchWalkthrough$Animal.sound:()Ljava/lang/String;`. The object running at that moment is `Dog`, so the result is `Dog`.
- In `Dog.callSuper()`, the `super.sound()` call uses **`invokespecial`** to the parent class's method.
- For `describe(...)` and `category()`, because the methods are static, the bytecode uses **`invokestatic`** to the method selected by the compiler based on type.
- Constructor `Dog.<init>` calls constructor `Animal.<init>` with **`invokespecial`**.
- The related private calls may have bytecode representations depending on the Java release/compiler and private method rules; fundamentally, they remain methods that **cannot be overridden**. Do not turn one disassembly sample into the claim that “every private call always has the single opcode X”.

In `javap` output, constant pool indices `#7`, `#15`, etc. and bytecode offsets depend on the build/compiler, so **do not hardcode** those numbers for every environment. Furthermore, string concatenation expressions like `"virtual=" + ref.sound()` on JDK 17 may show `invokedynamic` for string concatenation; it **does not remove** the fact that `ref.sound()` is executed according to its own instance call rules.

## 7. Tracing the Operand Stack and Frame When Calling an Instance Method

Consider specifically:

```java
Animal receiver = new Dog();
String result = receiver.sound();
```

This is an **illustrative snippet placed inside a method**. A typical bytecode sequence for the call part might be:

```text
aload_1                 // load the receiver reference onto the operand stack
invokevirtual #N        // Method Animal.sound:()Ljava/lang/String;
astore_2                // store the String result into the corresponding local slot
```

The locals and constant pool index numbers are **illustrative**, depending on how the compiler lays out the frame. Flow of meaning:

1. The caller frame already exists; a local variable holds the reference to the `Dog` object.
2. `aload` copies the reference onto the caller's **operand stack**. It does not copy the entire Dog object.
3. `invokevirtual` reads the symbolic reference and performs the appropriate checks/selection. The resolved method serves as the starting point, and the runtime class `Dog` leads to the method `Dog.sound`.
4. Arguments (if any) and the receiver reference are popped from the caller's operand stack; for a normal Java method, a callee frame is created and receives the receiver in **local slot 0** (`this`), with parameters in subsequent slots.
5. The code of `Dog.sound` executes in the callee frame and returns a `String` reference via `areturn`; the result returns to the caller's operand stack.
6. The caller uses `astore` or another operation on the result.

For a `static` method, `invokestatic` does not need a receiver in slot 0; the first parameter starts at local 0. For an instance method, a `long`/`double` parameter occupies two local slots. **The object type selected for dispatch does not change the position of `this` at slot 0** of the called method's frame.

### Resolved once or on every invocation?

The specification distinguishes symbolic reference resolution from invocation selection; the JVM may cache resolution/dispatch results, use method tables, or apply JIT optimizations. In the example, calling `receiver.sound()` many times does not force the JVM to re-run every lookup with a slow algorithm in a loop. Regardless of how an implementation optimizes, **the observable result must match the standard semantics**.

## 8. Interface Methods and Default Methods: The Receiver Still Determines the Implementation

Interfaces can declare abstract methods or provide a **default method**. `invokeinterface` relies on a reference to an interface method, and then selection depends on the receiver's runtime class and implementation structure.

Create a standalone file **`InterfaceDispatch.java`**:

```java
public class InterfaceDispatch {

    interface Speaker {
        default String text() {
            return "Speaker";
        }
    }

    static class Basic implements Speaker {
        // Inherits the default method Speaker.text()
    }

    static class Premium extends Basic {
        @Override
        public String text() {
            return "Premium";
        }
    }

    static class Decorated implements Speaker {
        @Override
        public String text() {
            return "Decorated(" + Speaker.super.text() + ")";
        }
    }

    public static void main(String[] args) {
        Speaker first = new Basic();
        Speaker second = new Premium();
        Speaker third = new Decorated();

        System.out.println("first=" + first.text());
        System.out.println("second=" + second.text());
        System.out.println("third=" + third.text());
    }
}
```

```bash
javac --release 17 InterfaceDispatch.java
java InterfaceDispatch
javap -c -p InterfaceDispatch
javap -c -p 'InterfaceDispatch$Decorated'
```

**Stdout of `java InterfaceDispatch`**:

```text
first=Speaker
second=Premium
third=Decorated(Speaker)
```

- `first.text()` has receiver `Basic`; no class override is found, so the applicable default method `Speaker.text()` is used.
- `second.text()` has receiver `Premium`; this class overrides `text`, so the `Premium.text()` body is selected.
- `third.text()` selects `Decorated.text()`; inside this method, `Speaker.super.text()` is an explicit call to the specified default implementation, typically represented by **`invokespecial`** to the matching interface method.
- In `InterfaceDispatch.main`, the calls through the `Speaker` variable typically have the **`invokeinterface`** opcode.

### When a class method and an interface default have the same name

A matching concrete instance method in a class/superclass takes precedence over a corresponding interface default method. If multiple default methods from independent interfaces conflict when writing Java source, the compiler usually requires the implementing class to provide an override to resolve it. Do not assume the JVM will randomly pick one default method when two conflicting choices exist.

With class files generated from **incompatible** library versions after binary evolution, situations where no valid single target remains can lead to linkage errors such as `IncompatibleClassChangeError` or `AbstractMethodError`; that is why interface API changes require checking binary compatibility.

## 9. Overriding Depends on Signature and Inheritability: Not Just Name Matching

The conditions that determine whether a method overrides a resolved method include:

- **Matching name and signature**, with rules on erasure/subsignature, return-type substitutability, and visibility according to the JLS.
- **Instance vs static:** a static method can only hide, not override, an instance method. Java forbids “overriding static with instance” or vice versa when two methods have the same compatible signature.
- **`private`:** private methods are not inherited to be overridden in the usual way. A subclass can have an independent method with the same name.
- **`final`:** a final instance method does not allow subclasses to validly override it; the JVM can optimize because the target cannot be replaced by a subclass under Java rules.
- **Package-private:** the override relationship depends on inheritability/accessibility across packages and the class hierarchy; you cannot just compare names and conclude.
- **`abstract`:** a method declared without a body; a concrete object must have a valid implementation before that call can succeed.
- **Interface defaults:** there are precedence, maximally-specific, and conflict-resolution rules.

### A counterexample with fields

`Field access` normally resolves the field according to the static type (and symbolic reference) of the expression, not using the same override dispatch as instance methods.

```java
class Base {
    String name = "Base-field";
    String who() { return "Base-method"; }
}
class Child extends Base {
    String name = "Child-field";
    @Override String who() { return "Child-method"; }
}
```

If `Base x = new Child();`, then `x.name` reads the field selected from type `Base` and returns `"Base-field"`, whereas `x.who()` runs the override `Child.who()`. This is an **illustrative snippet** to distinguish field hiding from method overriding; it is not a standalone program.

## 10. Generics, Erasure, and Bridge Methods Can Make Bytecode Differ from Source

Java generics are implemented with **type erasure**. When the return type in source is covariant or when erasure causes bytecode signatures to differ, the compiler may generate a **bridge method** with flags `ACC_BRIDGE` and `ACC_SYNTHETIC` to preserve proper polymorphism behavior and binary linkage.

Create **`BridgeDispatch.java`**:

```java
public class BridgeDispatch {

    static class Box<T> {
        T value() {
            return null;
        }
    }

    static class TextBox extends Box<String> {
        @Override
        String value() {
            return "hello";
        }
    }

    public static void main(String[] args) {
        Box<String> box = new TextBox();
        System.out.println("value=" + box.value());
    }
}
```

```bash
javac --release 17 BridgeDispatch.java
java BridgeDispatch
javap -c -v -p 'BridgeDispatch$TextBox'
```

**Stdout**:

```text
value=hello
```

In the bytecode of `Box<T>`, the method after erasure has descriptor `value:()Ljava/lang/Object;`. `TextBox` declares a method returning `String` with descriptor `value:()Ljava/lang/String;`. `javac` normally generates an additional **bridge** in `TextBox` with a descriptor returning `Object`; the bridge calls the actual `String`-returning method.

Therefore, a call with a symbolic reference to `Box.value:()Ljava/lang/Object;` can still dispatch to **bridge `TextBox.value:()Ljava/lang/Object;`**, and then the bridge delegates to the body of `TextBox.value:()Ljava/lang/String;`. From this, you can understand why `javap -p` sometimes shows two methods with the same name even though the source only declares one method.

Do not remove a bridge method from bytecode just because it is `synthetic`: already-compiled callers may need that method to maintain compatible call behavior.

## 11. Runtime Errors Related to Resolution/Selection

The JVM is not allowed to pick an arbitrary method if a reference is invalid. Distinguish several error groups:

| Common error | Typical situation | Meaning when debugging |
| --- | --- | --- |
| `NoSuchMethodError` | Caller was compiled against an existing descriptor/method, but the runtime library no longer has a matching method | Check **binary version**, descriptor, classpath/module path |
| `IllegalAccessError` | Method/reference is no longer accessible under linkage rules | Check visibility, package/module, and binary compatibility |
| `IncompatibleClassChangeError` | Caller expects static/instance/interface/class that does not match, or interface defaults conflict | Check API shape changes between compile and runtime |
| `AbstractMethodError` | A target is selected but is abstract, with no corresponding concrete implementation | Check interface/class library changes and class files |
| `NullPointerException` | Instance call uses a `null` receiver | Check the reference's data flow, do not attribute to a missing method |
| `VerifyError` | Bytecode violates typing/stack/control-flow constraints | Check generator/instrumentation and verification metadata |
| `ExceptionInInitializerError` | Class initialization running `<clinit>` fails under standard conditions | Distinguish class initialization failure from method lookup failure |

These are **typical** examples, not “one error only has single cause X”. Inspect the stack trace, cause, Java version, class loader, and running JAR set. A test on a newer JDK/IDE may pass while production uses a class of the same name from an older version, leading to a linkage error.

### When changing a library, keeping the right descriptor matters more than the method name

For example, library version 1 has `String lookup(int id)`, and a compiled caller contains a method reference with descriptor `(I)Ljava/lang/String;`. If at runtime it is replaced by library version 2 that **only** has `String lookup(long id)`, the two methods have different descriptors: the old caller can hit `NoSuchMethodError`. If only the overriding implementation changes while keeping a compatible contract, dispatch can continue to work normally. Binary compatibility must consider **class files and method descriptors**, not just names in source.

## 12. Performance: Dynamic Dispatch Does Not Mean “Always Linear Search on Every Call”

JVM implementations can use method tables, interface lookup caches, profiling, or JIT compilation to reduce invocation overhead. The HotSpot JIT can **devirtualize** or inline a call if there is sufficient evidence about the target; when the assumption no longer holds, the VM has appropriate guard/deoptimization mechanisms to preserve semantics.

Statements that should be layered:

- **JVMS specification guarantees:** selecting the appropriate implementation via resolution/selection, throwing the corresponding errors, and preserving observable results.
- **Implementation details:** how HotSpot looks up targets in memory, cache lookup counts, monomorphic/polymorphic call sites, when inlining happens, and machine code shape.
- **Actual measurements:** benchmark on the exact JDK build, compiler, flags, workload, and warm-up state.

Do not conclude “virtual is always slower than static by a fixed amount”, “the JVM walks every superclass on every call”, or “the JIT eliminated dynamic dispatch so type checks no longer exist” from a `javap` snippet alone. `javap` shows **bytecode invocation**, not the full optimized machine code at runtime.

## 13. Workflow for Reading and Analyzing a Method Call

When you see `receiver.m(args)` or an `invoke*` opcode, apply in order:

1. **Pin down the Java version and running class files**: `java -version`, `javac -version`, library versions, runtime classpath/module path.
2. **In Java source, determine the static types** of the receiver/arguments and the chosen overload per JLS `15.12`. Note casts/generics/autoboxing/varargs if present.
3. **Use `javap -c -v -p`**, find the class method containing the call site and the `invokevirtual`/`invokeinterface`/`invokestatic`/`invokespecial`/`invokedynamic` instruction.
4. **Read the constant-pool entry** of the instruction: target owner, method name, and JVM descriptor. Remember the return type is also in the descriptor.
5. **Identify the invocation kind**: virtual/interface needs selection by receiver; static/special/dynamic have different mechanisms.
6. **Determine the actual runtime class** of the receiver at the call site, rather than inferring from variable names. You can validly observe it via `obj.getClass()` when the reference is non-null or via a debugger.
7. **Follow the override chain**: runtime class, superclasses, interface defaults per JVMS and access permissions. With generics, also check bridge methods.
8. **Read the frame/operand stack if needed**: how receiver/args are passed, whether the method is instance/static, and which return opcode brings the result back to the caller.
9. **If there is a linkage error**, check mismatched binary versions/loaders before concluding JVM dispatch is wrong.
10. **If performance is in question**, separate the contract from JIT optimizations; use profiling/benchmarking, do not infer from `javap`.

### Self-check

**Question 1:** `Parent p = new Child(); p.run();`, `Child` validly overrides `run`. Which method executes when using virtual invocation?  
**Answer:** `Child.run()`, because the runtime receiver is `Child`.

**Question 2:** Two overloads `f(Parent)` and `f(Child)`; calling `f(p)` with `p` declared as `Parent` but holding a Child object. Which overload is selected?  
**Answer:** `f(Parent)`, because the compiler examines static types.

**Question 3:** `Parent p = new Child(); p.staticMethod();` if both classes declare the same static method?  
**Answer:** The static version belonging to `Parent` is selected according to the static type; calling via an instance syntax should be avoided in real code.

**Question 4:** `Child.callSuper()` executes `super.run()`; does it select `Child.run()` because the object is still a Child?  
**Answer:** No; `super` requires a special call to the appropriate superclass implementation.

**Question 5:** An interface default method is overridden in a concrete class, and the receiver variable is declared with the interface type. Which method runs?  
**Answer:** The overriding implementation in the runtime class, according to the appropriate selection rules.

**Question 6:** Why can `javap` show a bridge method that the source did not declare?  
**Answer:** The compiler generates a synthetic/bridge method to maintain the polymorphism contract after erasure/covariant return.

**Question 7:** The constant pool shows `Animal.sound`, yet the output for a Dog object is `Dog`; is that a bug?  
**Answer:** No. The symbolic reference is resolved separately; `invokevirtual` selects the implementation based on the runtime receiver.

## 14. Common Misconceptions

| Misconception | Correct understanding |
| --- | --- |
| “Resolution always selects the final executed method” | For `invokevirtual`/`invokeinterface` there is also **selection** based on the runtime object |
| “Overloads are decided when the JVM sees the object” | Source overloads are chosen by the compiler based on static types and method invocation rules |
| “The variable's static type forces the call to always run on the parent class” | Static type constrains valid calls; overrides can run according to the runtime type |
| “A Dog object has `bark()` so an Animal variable can call `bark()`” | The compiler still requires a valid member on the static type or a valid cast |
| “Static methods are overridden like instance methods” | Static methods have **hiding**, not virtual dispatch |
| “A same-named private method in a subclass overrides the parent's private method” | Private superclass methods are not overridden that way |
| “`super.m()` still selects the override on the subclass receiver” | `super` uses `invokespecial` with special lookup rules |
| “Interfaces always run the method body defined on the interface” | A class override can be selected; default methods are only one possibility |
| “One Java call equals one `invokevirtual` opcode in all cases” | There are `invokeinterface`, `invokestatic`, `invokespecial`, `invokedynamic`, and compiler transformations |
| “Bridge methods are dead code that can be deleted” | Bridges preserve correct invocation compatibility after erasure/covariant return |
| “`javap` says `Animal.sound` so the JVM cannot call Dog” | The constant pool holds the **referenced** method; selection can find `Dog.sound` |
| “The JVM always walks every superclass on every call” | The spec defines the result; implementations/JITs can optimize lookup and inline |

**Remember:** **JLS overload** selects the call based on static types; **JVM resolution** resolves the method reference in the constant pool; **method selection** of `invokevirtual`/`invokeinterface` chooses the implementation based on the receiver's runtime type and valid override relationships. These three layers explain why the same object can produce different results when calling overloads, overrides, static methods, or `super`.
