# Off-Heap Memory: Direct Buffers, Native Libraries, and JVM Internal Structures

## 1. The Java heap is not the entire memory of a Java process

In the JVM, the **Java heap** is the region that the garbage collector typically manages to hold ordinary Java objects and arrays. However, a Java process also needs many other types of memory: **direct buffers** content, data allocated by **native libraries**, class metadata, machine code generated by the JIT compiler, native thread stacks, internal GC structures, mapped file regions, and memory used by the OS/runtime.

**Off-heap memory** usually refers to capacity located outside the Java heap directly managed by GC. In practice, the term has two scopes that need to be clearly distinguished:

- **Application off-heap:** byte storage for NIO direct buffers, memory from JNI/JNA/FFI, or other native libraries; the application needs to understand the owner, scope, and cleanup of each source.
- **Native/non-heap process memory:** a broader scope, including JVM internal regions such as HotSpot Metaspace, code cache, native thread stacks, GC work areas, shared libraries, and memory mappings.

Do not conflate the two scopes above. **A direct buffer is not the entirety of native memory**, and native allocations do not necessarily fall under the same quota.

~~~text
Java process (conceptual diagram, not actual address layout)

  Java heap (GC manages objects)
  ├── Business objects, arrays, String...
  ├── HeapByteBuffer wrapper ────> byte[] in Java heap
  └── DirectByteBuffer wrapper ──┐
                                 │
  Memory outside Java heap       │
  ├── Direct buffer content <────┘
  ├── Native C/C++ allocations from JNI/JNA
  ├── Memory-mapped file regions
  ├── Class metadata / Metaspace (HotSpot)
  ├── JIT code cache
  ├── Native thread stacks
  └── GC/runtime/internal structures
~~~

**Key takeaway:** `ByteBuffer.allocateDirect(n)` returns a **`ByteBuffer` Java object** managed like other objects; the **byte content** it represents is typically stored outside the ordinary GC heap. Do not say “the entire DirectByteBuffer object is outside the heap”.

### Outside the heap does not mean outside RAM

Native allocations typically reside in the process's **virtual address space**. The OS maps the corresponding pages to physical RAM or file backing when needed. `virtual reserved`, `committed`, and `resident (RSS)` are different quantities. A typical JNI pointer is a virtual address, **not a physical RAM address**, and Java has no portable API to read the physical address of an object.

## 2. Why is off-heap needed and when should it not be used?

Main reasons:

1. **Native I/O:** direct buffers allow the JVM to attempt to use byte data directly for certain OS I/O operations, reducing copies through intermediate buffers.
2. **Native integration:** encryption, compression, database, image processing, networking, or device libraries may allocate memory in C/C++.
3. **File mapping:** reading/writing large files by page via the memory-mapped file mechanism, sometimes beneficial for random access.
4. **Needs of the VM itself:** class metadata, compiled code, thread stacks, and GC bookkeeping always consume resources outside the Java heap depending on the corresponding implementation.
5. **Data lifecycle control:** some systems need buffer pools with clear capacity limits/ownership, reducing churn of heap arrays.

However, **direct does not automatically mean faster**, **off-heap does not automatically mean zero-copy**, and **replacing arrays with direct buffers does not eliminate GC**. The Java SE 17 API states that allocating/deallocating direct buffers is typically more expensive than heap buffers; they should only be used when the workload has measurable benefits.

| Characteristic | Heap ByteBuffer | Direct ByteBuffer |
| --- | --- | --- |
| Created via | `ByteBuffer.allocate(n)`, `wrap(byte[])` | `ByteBuffer.allocateDirect(n)` |
| `isDirect()` | `false` | `true` |
| Java wrapper | Yes | Yes |
| Where byte content resides | Usually in a Java `byte[]` | Can reside outside the ordinary GC heap |
| Use backing array via `array()` | Has backing array with `allocate` | Not supported by default; check `hasArray()` |
| Native I/O | May require an intermediate copy | JVM best effort to reduce intermediate copies |
| When memory is reclaimed | GC of the heap backing array when unreachable | GC/reference processing/native cleanup depending on implementation |
| Ownership specification | Typically by Java object reachability | Also requires attention to pool/view/native user lifetime |

## 3. How to use `ByteBuffer` and the meaning of views

Important operations in Java NIO:

- `capacity()`: total **byte** capacity of the buffer.
- `position()`: next relative read/write position.
- `limit()`: valid boundary for relative operations.
- `remaining()`: number of elements from position to limit.
- `put`, `get`, `putInt`, `getInt`: read/write content by logical offset.
- `order(ByteOrder.BIG_ENDIAN)` and `LITTLE_ENDIAN`: choose byte order when reading/writing multi-byte primitives.
- `duplicate()`: creates a new wrapper with its own position/limit/mark state, but **shares content**.
- `slice()` or `slice(int, int)`: creates a view of a sub-region without **copying** content.
- `asReadOnlyBuffer()`: creates a read-only view; does not make the physical storage immutable to other views that have write access.

### Buffer state is not allocation lifetime

~~~text
0 ----- position ----- limit ----- capacity

clear():  position=0, limit=capacity
flip():   limit=position, position=0
rewind(): position=0
~~~

`clear()` **does not zero-fill**, **does not free native allocation**, **does not erase sensitive data**. `flip()` mainly changes logical pointers so that written data can be read; it does not flush files and does not call `free`. When a pool reuses a buffer, sensitive data and ownership must be handled separately.

### `duplicate()`/`slice()` can keep memory alive longer

A 100-byte view from a 64 MiB direct allocation can continue to keep the large backing region **reachable**. This can cause high direct-memory usage even though the application “only holds a small slice”. When needing to keep a few bytes for a long time, an independent copy is sometimes easier to manage than aliasing into a large buffer.

## 4. Complete Java 17 example: direct, heap, and aliasing

Create file **`DirectMemoryDemo.java`**:

~~~java
import java.nio.ByteBuffer;
import java.nio.ByteOrder;

public final class DirectMemoryDemo {
    public static void main(String[] args) {
        ByteBuffer heap = ByteBuffer.allocate(8);
        ByteBuffer direct = ByteBuffer.allocateDirect(8);

        heap.order(ByteOrder.BIG_ENDIAN);
        direct.order(ByteOrder.BIG_ENDIAN);
        heap.putInt(0, 0x01020304);
        direct.putInt(0, 0x01020304);

        System.out.println("heap.isDirect=" + heap.isDirect());
        System.out.println("direct.isDirect=" + direct.isDirect());
        System.out.println("sameInt=" +
                (heap.getInt(0) == direct.getInt(0)));

        ByteBuffer alias = direct.duplicate();
        alias.putInt(0, 0x0A0B0C0D);
        System.out.println("duplicateSharesBytes=" +
                (direct.getInt(0) == 0x0A0B0C0D));
        System.out.println("heapUnaffected=" +
                (heap.getInt(0) == 0x01020304));

        ByteBuffer firstFour = direct.slice(0, 4);
        System.out.println("slice.isDirect=" + firstFour.isDirect());
        System.out.println("slice.capacity=" + firstFour.capacity());
        System.out.println("sliceSharesBytes=" +
                (firstFour.getInt(0) == direct.getInt(0)));
    }
}
~~~

Run with JDK 17+:

~~~bash
javac --release 17 DirectMemoryDemo.java
java DirectMemoryDemo
~~~

**Exact stdout compiled/run and verified with JDK 21 targeting Java 17:**

~~~text
heap.isDirect=false
direct.isDirect=true
sameInt=true
duplicateSharesBytes=true
heapUnaffected=true
slice.isDirect=true
slice.capacity=4
sliceSharesBytes=true
~~~

Analysis:

1. Both the heap buffer and the direct buffer are allocated 8 bytes, but `isDirect()` differs.
2. `putInt(0, ...)` writes four bytes at byte index 0; `sameInt=true` only proves the **values** are equal, not that the two buffers point to the same address.
3. `duplicate()` creates another view wrapper but shares the byte region. Writing through `alias` causes `direct` to see `0x0A0B0C0D`.
4. The `heap` buffer is independent and unchanged.
5. `slice(0, 4)` holds a 4-byte view and remains direct, containing the four bytes shared with `direct`.

Do not infer that direct buffers have an official API returning a **physical address**. When `hasArray() == false`, calling `array()` is not allowed. Do not use reflection/Unsafe to read private fields to guess layout or stable native addresses.

## 5. When is direct memory reclaimed?

For `ByteBuffer.allocateDirect`, **Java 17 does not provide a public `ByteBuffer.close()` or `ByteBuffer.free()`**. In HotSpot and common JVMs, there are cleaner/reference processing mechanisms to manage the corresponding native storage when the Java wrapper and links holding the storage are no longer needed. However, **the timing of GC cleanup is not guaranteed**.

Claims to avoid:

- **`direct = null`** does not mean the memory is already freed; there may still be other views, queued I/O operations, or references from other objects.
- **`System.gc()`** is only a GC request; the JVM is not required to reclaim a specific direct allocation at a deterministic time.
- **`clear()`** only resets position/limit, it does not deallocate memory.
- **Manually invoking internal cleaners** via reflection/`sun.misc.Unsafe` is not a portable API; it risks use-after-free while a buffer/view/native code is still accessing the memory.
- **Direct memory provided by JNI** does not by itself prove the JVM is responsible for calling native `free`.

Distinguish between **managed direct allocation** controlled by the Java runtime and **application-owned native allocation**. If native code allocates memory itself and passes a pointer to Java, ownership/lifetime must be clearly defined. The memory must remain valid until all users have finished; then the proper owner frees it.

### When deterministic lifetime is needed

An API/library with `AutoCloseable` or an appropriate lifetime scope can help proactively reclaim resources. Java 17 has foreign-memory APIs that were in an incubating state, whereas FFM syntax/contracts in newer JDKs changed significantly. **Do not copy FFM examples from newer JDK versions into a Java 17 project and assume they will compile.**

If implementing an `AutoCloseable` native handle wrapper, ensure:

1. `close()` does not double-free.
2. No async operation is holding the pointer when closing.
3. Native callbacks/workers are stopped before deallocation.
4. Do not pass a freed pointer to another Java wrapper or thread.
5. Exceptions in Java code still go through `try-with-resources`/`finally` cleanup.
6. The library has synchronization rules when two threads access the same byte region.

## 6. `-Xmx` and `-XX:MaxDirectMemorySize` are two different limits

Common HotSpot/JDK 17 options:

~~~bash
java -Xmx512m -XX:MaxDirectMemorySize=256m DirectMemoryDemo
~~~

- `-Xmx` is the max **Java heap** limit under the JVM/HotSpot mechanism.
- `-XX:MaxDirectMemorySize` sets the total limit for **NIO direct-buffer allocations** accounted for under the HotSpot mechanism.
- Do not add the two flags together and call that sum **all memory of the process**.
- JNI/JNA native `malloc`, thread stacks, Metaspace, JIT code cache, GC structures, and memory mappings have different allocation/quota mechanisms.
- Native allocator overhead and alignment mean logical buffer capacity does not necessarily equal the exact native bytes reserved/committed.
- `-XX:` flags belong to the VM implementation, **there is no guarantee every Java runtime supports/interprets them identically**.

### OOME due to direct memory is not the same as OOME due to Java heap

HotSpot may throw `OutOfMemoryError` with a message like `Cannot reserve ... bytes of direct buffer memory` when it cannot reserve within the native buffer limit/budget. The exact message depends on version/implementation and **is not an API contract to parse**.

`OutOfMemoryError: Java heap space` is a different situation. If the heap still has spare room while native memory is exhausted or the container exceeds its limit, increasing `-Xmx` can even make total memory pressure worse.

### Container memory limit

If a container is limited to 1 GiB, do not set `-Xmx` close to 1 GiB and forget direct buffers, thread stacks, class metadata, code cache, and native libraries. The OS/cgroup OOM killer can terminate the process **without a Java stack trace**, unlike an `OutOfMemoryError` exception thrown by the JVM.

There is no universal heap/native ratio applicable to every service. A memory budget must be based on workload: concurrent requests, payload sizes, connection buffers, number of threads, number of class loaders, library allocations, and GC/JIT runtime footprint.

## 7. Memory-mapped files: `MappedByteBuffer`

`FileChannel.map(...)` creates a `MappedByteBuffer`, a type of direct buffer using file memory mapping. The OS manages the mapped pages; **a 10 GiB file is not guaranteed to be 10 GiB resident in RAM immediately after mapping**.

An **illustrative snippet, not a complete Java file**:

~~~java
try (FileChannel channel = FileChannel.open(
        Path.of("data.bin"),
        StandardOpenOption.READ,
        StandardOpenOption.WRITE)) {
    MappedByteBuffer mapped = channel.map(
            FileChannel.MapMode.READ_WRITE, 0, 4096L);
    mapped.putInt(0, 123);
    mapped.force();
}
~~~

To run this snippet, you need imports `java.nio.*`, `java.nio.channels.*`, `java.nio.file.*`, a valid file, and appropriate permissions. Mapping a file region beyond the file size/corresponding limits must follow the `FileChannel.map` contract and the OS.

Required distinctions:

- `mapped.isDirect()` is `true`, but a mapping differs from a direct buffer allocating bytes via `allocateDirect`.
- `mapped.force()` means **requesting that changes be pushed to the file/storage** per the API; it does not mean free or unmap.
- `FileChannel.close()` closing the channel **does not mean the mapping disappears immediately** if the mapped buffer is still alive.
- The OS may page-fault on access; file mapping memory accounting differs from native heap allocations.
- Modifying/truncating the file from elsewhere while a mapping is in use can make some regions invalid to access; file ownership must be managed.
- Deleting/renaming a file while a mapped region still exists can behave differently across operating systems, notably on Windows.
- Buffer pools typically distinguish between `direct` and `mapped`; do not mix them when measuring.

Mapping a file is useful for some random/large workloads; it is not guaranteed to be faster than `FileChannel.read()` for every file, cache level, or I/O pattern.

## 8. Native libraries: JNI/JNA, native allocators, and pointers

Java code can interact with C/C++ or external systems using JNI, JNA, or a foreign-function mechanism appropriate for the JDK version. These libraries can themselves use:

- `malloc`, `calloc`, `realloc`, `free` in the C runtime.
- `mmap`/OS virtual memory allocations.
- Native sockets, file descriptors, GPU/device buffers, crypto/compression contexts.
- Native-created threads, native stacks.
- JNI global references keeping Java objects/classes alive.
- Direct buffers representing native memory regions.

Therefore, a Java heap dump may look normal while a C/C++ heap leak causes process RSS to grow sharply.

### 8.1. A JNI method does not automatically establish memory ownership

~~~java
public final class NativeCodec {
    static {
        System.loadLibrary("codec");
    }

    public static native int compress(
            byte[] input, int inputLength);
}
~~~

This is a **non-standalone illustrative snippet**: it requires a real native library, a JNI implementation with the matching signature, a compatible ABI build, and library path configuration. It is not sufficient to produce stdout.

If the implementation allocates a temporary output buffer in native memory, there must be a place to free it properly. A JNI global reference must be deleted per the API when no longer used. A forgotten global ref can keep a Java object or class loader alive unexpectedly.

### 8.2. Native direct buffers are not owned by the JVM by default

JNI has APIs like `NewDirectByteBuffer` for Java to view a native memory region. **Do not infer** that the JVM will automatically `free` a region allocated by an application library just because a `ByteBuffer` wrapper was created.

Two serious bugs:

1. **Use-after-free:** native code frees the byte region while the Java buffer is still using it.
2. **Double-free:** two owners both free the same allocation.

The result can be a crash, wrong data, memory corruption, or a vulnerability, not necessarily a clean Java exception. In multithreading, memory visibility/atomicity rules must be present alongside lifetime.

### 8.3. A direct buffer does not prove zero-copy

The JVM can avoid **some** intermediate copies when passing a direct buffer to native I/O. However, between the application, TLS, compression, network kernel, device drivers, and file systems, copies can still occur. **Zero-copy is a property of the entire data path**, not a guarantee based solely on `isDirect()`. Measure syscalls, throughput, and CPU before/after.

## 9. JVM internal native/non-heap structures

From the HotSpot perspective, many memory regions exist outside the Java heap:

| Region or mechanism | Role | Signals/points to measure |
| --- | --- | --- |
| **Metaspace / class metadata** | Class/interface/loader-related VM structures | Class loading count, unloading, metaspace stats, NMT |
| **JIT code cache** | Native code generated by the compiler | Code cache usage, compiler/code metrics, NMT |
| **Native thread stacks** | Stack/resources of platform threads | Thread count, `-Xss`, OS/native tracking |
| **GC internal structures** | Card tables, remembered sets, bitmaps, runtime bookkeeping | GC logs, NMT categories |
| **JNI/JVMTI/native code** | Native library allocations, global refs, C/C++ data | Native profilers, heap retaining paths, OS metrics |
| **Direct NIO buffers** | Off-heap byte content, I/O | `BufferPoolMXBean`, direct memory quota |
| **Memory-mapped files** | OS mappings of files | Mapped pool, page-faults, process mappings |
| **Shared libraries/mappings** | Native executable/library code/data | OS mapping tools, process metrics |

**Metaspace is a HotSpot mechanism**, not a mandatory name in the JVM Specification. The JVM specification defines the abstract **method area**, thread stacks, and heap; another JVM implementation may organize actual structures differently.

### Metaspace and class loader leaks

If each hot-reload creates a new loader while the host retains plugin objects, thread context class loaders, listeners, or reflection caches, the old loader may not become eligible for GC/class unloading. Per-session class metadata accumulates and can cause a Metaspace OOME. This is a **lifecycle issue of loaders/classes**, not a `ByteBuffer.allocateDirect` issue.

### Code cache

The JIT compiler needs native memory to store machine code of compiled methods and related structures. Size/cache policy depends on VM flags and workload. The JIT can deoptimize or reclaim/reuse code. Do not lump code cache into Java heap used when budgeting.

### Thread stacks

A process with thousands of platform threads can reserve/commit significant native stack memory. `-Xss` relates to stack size on HotSpot, but reducing it too low can cause more `StackOverflowError`s; it is no substitute for fixing thread leaks and bounded concurrency. Errors like `unable to create native thread` can be caused by native memory, thread/process count limits, or OS resources, not necessarily because the Java heap is full.

## 10. Monitoring direct/mapped buffers with BufferPoolMXBean

Java SE 17 has the `java.lang.management.BufferPoolMXBean` interface, typically providing pools named `direct`, `mapped`, and other pools depending on the runtime.

Create file **`BufferStatsDemo.java`**:

~~~java
import java.lang.management.BufferPoolMXBean;
import java.lang.management.ManagementFactory;

public final class BufferStatsDemo {
    public static void main(String[] args) {
        for (BufferPoolMXBean pool :
                ManagementFactory.getPlatformMXBeans(BufferPoolMXBean.class)) {
            System.out.printf(
                    "pool=%s count=%d capacity=%d used=%d%n",
                    pool.getName(),
                    pool.getCount(),
                    pool.getTotalCapacity(),
                    pool.getMemoryUsed());
        }
    }
}
~~~

Run:

~~~bash
javac --release 17 BufferStatsDemo.java
java BufferStatsDemo
~~~

**There is no fixed numeric stdout** for this program: the number of pools, buffer count, and bytes vary by JVM/workload/timing. The example above was compiled with `javac --release 17` and run with JDK 21; one run showed `direct` and `mapped` pools, but **do not turn that single run's observation into a general contract**.

| API | Meaning |
| --- | --- |
| `getName()` | Pool name |
| `getCount()` | **Estimate** of the number of buffers in the pool |
| `getTotalCapacity()` | **Estimate** of cumulative logical capacity, in bytes |
| `getMemoryUsed()` | **Estimate** of memory the VM uses for the pool; may differ from capacity due to alignment/allocator |
| `getMemoryUsed() == -1` | The JVM has no available estimate |

Buffer pool stats are **not statistics for all JNI native malloc**, Metaspace, code cache, or thread stacks. Some views like `slice()`/`duplicate()` share backing bytes; do not infer resident bytes as `count * size` without knowing the implementation's accounting method.

## 11. HotSpot Native Memory Tracking (NMT)

NMT is a tool for observing many **HotSpot VM internal allocations** by category such as Thread, Class, Code, GC, Compiler, and Internal. It has `summary` and `detail` modes along with noticeable overhead.

Example enabling NMT **at startup** of a real application:

~~~bash
java -XX:NativeMemoryTracking=summary -cp app.jar com.example.Main
~~~

Here `app.jar` and `com.example.Main` are **illustrative names only**, to be replaced with the application's artifact and main class.

When the process has a real PID:

~~~text
jcmd PID VM.native_memory summary
jcmd PID VM.native_memory baseline
jcmd PID VM.native_memory summary.diff
~~~

`PID` here indicates where to substitute the **PID number**, do not type the literal word `PID` if the shell/application does not have a variable of that name.

Workflow:

1. Start the JVM with `-XX:NativeMemoryTracking=summary` or `detail`.
2. Record a baseline when the app is stable.
3. Run the workload with direct buffers/native code/class loading/threads.
4. Use `summary.diff` to see which category grew.
5. Cross-reference with `BufferPoolMXBean`, heap/GC logs, thread count, and OS/process metrics.
6. When suspecting a third-party native leak, use a **native allocator profiler** or the corresponding library's tools.

**Decisive limitation:** According to Oracle JDK 17 documentation, NMT observes **JVM/HotSpot internal native memory**, but **does not cover all memory from third-party native code and many class-library allocations**. Therefore, NMT not increasing is **not sufficient** to conclude that a C++ library is not leaking.

Do not assume NMT can be enabled at any time on an already-running process. For NMT to collect meaningful data, it needs to be enabled at JVM startup; there are `jcmd` commands to view/baseline and perform some NMT management operations, but one should not promise re-enabling NMT if it was not configured at startup.

## 12. Why can process RSS be much larger than heap used?

One way to build an approximate **memory budget**:

~~~text
Process memory footprint (approximate model)
  Java heap resident pages
+ direct/native application buffers
+ Metaspace / class metadata
+ JIT compiled code / code cache
+ thread stacks
+ GC runtime structures
+ native libraries / device allocations
+ file mappings and OS-related pages
~~~

This is **not** an exact sum of different memory reports: metrics can double-count shared mappings or measure reservation/commit/residency in different units.

Distinguish:

- **Heap used:** capacity visible to GC inside the Java heap.
- **Heap committed:** capacity the VM has committed to serve the heap, not necessarily all pages physically resident.
- **Virtual reserved:** reserved virtual address range; not equivalent to physical memory.
- **Process RSS:** resident pages according to OS accounting, which may include shared pages.
- **Cgroup/container usage:** memory counted by container accounting, which may include items different from process RSS.
- **NMT reserved/committed:** information on VM allocations by category, not including all external native code.

Which metric is appropriate depends on the question you are asking: Java object leak, direct buffer quota, native malloc leak, cgroup OOM, Metaspace growth, or thread stack pressure.

## 13. Diagnosis by symptom

### A. `OutOfMemoryError: Java heap space`

Inspect Java heap allocations, live objects, and GC. Do not blindly increase `MaxDirectMemorySize` to fix a heap OOME. However, also consider the total memory budget when adjusting `-Xmx`.

### B. Direct buffer memory OOME

Can be caused by:

- Unbounded pool; too many live buffers.
- Views (`slice`, `duplicate`) or async requests retaining backing allocations.
- Allocating too frequently so reference cleanup cannot keep up.
- Direct-buffer quota too small for the actual workload.
- Native/OS memory pressure preventing allocation.

Remediation approach: measure `BufferPoolMXBean`, total capacity, active requests, buffer lifecycle, quota, and memory limits. **Do not just increase the limit and ignore the source holding references**.

### C. RSS grows while Java heap used is stable

Suspect native allocations, mapped pages, direct buffers, Metaspace, JIT code, or many native thread stacks. Enable NMT in a controlled manner, compare `BufferPoolMXBean` and OS metrics; if NMT does not cover C/C++ memory, use native tools.

### D. Container OOMKilled, JVM did not throw `OutOfMemoryError`

The OS/cgroup can kill the process before the JVM has a chance to log OOME/run shutdown hooks. Check container events, exit code, and total resident/working set, rather than only looking at heap GC.

### E. `unable to create native thread`

Check thread count, executor leaks, OS process/thread limits, `-Xss`, and native memory. Do not rush to increase `-Xmx` when the Java heap is not the cause.

### F. Metaspace OOME after multiple hot reloads

Check class-loader retention, ThreadLocal/TCCL, static caches, reflection metadata, and class unloading. Direct buffer tuning does not fix loader metadata leaks.

### G. Native library crash

When there is a use-after-free, double-free, out-of-bounds, or ABI mismatch, the JVM can crash the entire process. A Java heap dump does not necessarily point to a native allocation. Crash logs, native debug/sanitizers in a safe environment, and checking the ownership contract are needed.

## 14. Designing applications that use off-heap safely

### 14.1. Bounded capacity and backpressure

For example, if each request uses a 1 MiB direct buffer and there are 500 concurrent requests, the buffer content alone can reach **around 500 MiB**, before allocator overhead, async retention, and other regions.

Should limit:

- Total number of buffers.
- Total bytes of direct capacity.
- Number of requests/operations holding buffers simultaneously.
- Maximum size for a single buffer.
- Time a buffer is held in the pool and timeout for operations that have not returned the buffer.
- Behavior when the pool is exhausted: backpressure, bounded queue, or returning an appropriate error instead of unbounded allocation.

### 14.2. Ownership and cleanup

~~~text
acquire / allocate
       |
       v
write bytes, pass to I/O/native operation
       |
       v
wait until operation REALLY completes
       |
       v
release back to bounded pool / close native owner
~~~

Do not return a buffer to the pool while TLS/socket/async channel still references it. Do not keep a small `slice` that keeps an entire large region alive when unnecessary. Do not use `clear()` to erase processed secret data. If using a native region owned by a library, only close/free when **all parties** have finished using it.

### 14.3. Benchmark instead of relying on API names

Compare heap/direct/mapped on throughput, tail latency, CPU, GC pause, page faults, and total process memory under real workload. A large `ByteBuffer.allocateDirect` may suit long-lived native I/O, but millions of short-lived small direct allocations can increase allocator overhead, cleanup cost, and memory pressure.

### 14.4. Restrict native access privileges

Native pointers or foreign memory APIs have different power than Java memory-safe object access. Check bounds, alignment, thread-safety, ownership, and privileges/module access. Avoid calling unsupported internal APIs to obtain memory addresses or force cleanup of a direct buffer that is not certain to have no remaining users.

## 15. Common mistakes

1. **“Off-heap means not using RAM.”** False: it is the scope of memory outside the Java heap, not whether pages are resident or not.
2. **“The DirectByteBuffer object is outside the Java heap.”** False: the wrapper is a Java object; the byte storage is what is typically off-heap.
3. **“Direct buffers are always zero-copy.”** False: the JVM commits to best effort for suitable native I/O.
4. **“`clear()` frees native memory or erases data.”** False.
5. **“`slice()` and `duplicate()` copy the entire byte content.”** False: they share content.
6. **“Once the original reference is gone, the buffer is already freed.”** False: there may still be views or I/O users.
7. **“`System.gc()` guarantees immediate native cleanup.”** False.
8. **“Every Java 17 direct buffer has `close()`.”** False: the basic ByteBuffer API does not have it.
9. **“`-Xmx` limits total process memory.”** False.
10. **“`MaxDirectMemorySize` limits all JNI `malloc`.”** False.
11. **“A mapped file is guaranteed to be loaded entirely into RAM upon mapping.”** False.
12. **“`MappedByteBuffer.force()` is unmap.”** False.
13. **“Closing FileChannel means the mapped buffer is unmapped.”** False.
14. **“Metaspace is a mandatory region name in every JVM.”** False: it is a HotSpot implementation detail.
15. **“BufferPoolMXBean tracks all native allocations.”** False.
16. **“NMT tracks all third-party native code.”** False.
17. **“RSS not decreasing means there is definitely a leak.”** False: the allocator/OS may retain resident/committed capacity.
18. **“A native pointer is a physical RAM address.”** False: it is typically a virtual address.
19. **“GC automatically fixes all native lifetime bugs.”** False: use-after-free can crash the process.
20. **“Direct buffers are faster than heap in every workload.”** False: actual measurement decides.

## 16. Self-check questions

1. What is `ByteBuffer.allocate(16).isDirect()`? **`false`**.
2. What is `ByteBuffer.allocateDirect(16).isDirect()`? **`true`**.
3. If `duplicate()` writes bytes, can the original buffer see them? **Yes**, because of shared content.
4. Does `clear()` zero-fill or free memory? **No**.
5. Is heap GC still used when there are direct buffers? **Yes**, because Java wrappers are still objects.
6. Does `-Xmx1g` prevent process RSS from exceeding 1 GiB? **No**.
7. Does `-XX:MaxDirectMemorySize` put a quota on all JNI malloc? **No**.
8. Why does `getMemoryUsed()` differ from `getTotalCapacity()`? **Overhead/alignment/measurement method**, both are estimates.
9. Can `getMemoryUsed()` be `-1`? **Yes**, when no estimate is available.
10. Does NMT prove there is no C++ memory leak? **No**.
11. Does `MappedByteBuffer.force()` reclaim the mapping? **No**.
12. Why can holding a 100-byte slice retain a 64 MiB region? **The slice shares the backing region**.
13. When thread count increases sharply, what causes native memory to grow? **Thread stacks** and runtime/thread resources.
14. Which region does a class-loader leak typically impact? **Class metadata/Metaspace**.
15. Why is `System.gc()` not a cleanup deadline? **The collector is not forced to execute right then**.
16. When OOMKilled by a container without a Java OOME, what should be checked? **OS/cgroup memory limit and process footprint**.
17. If native frees a direct memory region while Java still holds a buffer wrapper, what happens? **Use-after-free can crash/corrupt data**.
18. What does a safe off-heap solution need? **Bounded allocations, ownership, cleanup, backpressure, and multi-layer monitoring**.

**Technical conclusion:** **The Java heap is not the entire JVM memory footprint.** `ByteBuffer.allocateDirect` creates a Java wrapper with byte storage that may be off-heap, native libraries can own their own allocations, and the JVM itself must manage class metadata, compiled-code cache, stacks, and GC structures. Do not treat `-Xmx`, `MaxDirectMemorySize`, BufferPoolMXBean, or NMT as the complete picture on its own. Design bounded buffers and clear lifetimes, monitor heap/native/thread/class loading/OS metrics simultaneously, and distinguish GC of Java objects from the reclamation of native resources.
