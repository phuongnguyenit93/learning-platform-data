# KeyManager, TrustManager, keystore và truststore có trách nhiệm khác nhau

Trong TLS của Java (JSSE), **`KeyManager` quản lý credential cục bộ để chứng minh danh tính của bên mình**, còn **`TrustManager` xác minh chứng chỉ của đối tác**. **Keystore** và **truststore** là các kho chứa dữ liệu mà manager dùng; chúng **không phải hai định dạng tệp bắt buộc khác nhau**. Cả hai có thể được nạp qua `java.security.KeyStore` và cùng dùng định dạng `PKCS12`.

Hiểu sai bốn khái niệm này dễ dẫn đến cấu hình thiếu private key, client không xác minh được certificate chain, mTLS không thực sự yêu cầu chứng chỉ client hoặc lỗi nguy hiểm nhất: viết manager “trust all” để bỏ qua xác thực. Bài học thuộc phần **TLS** trong Java Advance - networking, dùng Java 17+ và giải thích cả vai trò, cách cấu hình, lỗi, kiểm thử và quản trị vận hành.

## 1. Bảng phân công trách nhiệm

| Thành phần | Loại đối tượng | Chức năng | Không chịu trách nhiệm chính |
| --- | --- | --- | --- |
| `KeyManager` | Runtime JSSE manager | Chọn **private key và certificate chain của local endpoint** khi TLS cần trình chứng chỉ | Không quyết định peer có được tin không |
| `TrustManager` | Runtime JSSE manager | **Xác minh certificate chain của remote peer** theo trust material/chính sách | Không cung cấp private key của bên mình |
| *Keystore* (identity store) | Nguồn dữ liệu, thường là file | Chứa **private key** và certificate chain tương ứng của bên mình | Không tự xác thực đối tác |
| *Truststore* | Nguồn dữ liệu, thường là file | Chứa **trusted certificate/CA** làm trust anchors phù hợp | Không chứng minh bên mình sở hữu private key |

Cụ thể hơn, `KeyManagerFactory` đọc key material trong `KeyStore` và tạo `KeyManager[]`; `TrustManagerFactory` đọc trust material và tạo `TrustManager[]`. Hai mảng được cấu hình vào `SSLContext` để tạo `SSLSocket`, `SSLServerSocket` hoặc `SSLEngine`.

```text
  LOCAL IDENTITY                            VERIFY REMOTE PEER
  identity.p12                              trust.p12
      |                                        |
      v                                        v
  KeyStore.load()                         KeyStore.load()
      |                                        |
  KeyManagerFactory                       TrustManagerFactory
      |                                        |
  getKeyManagers()                         getTrustManagers()
      \                                        /
       \                                      /
                SSLContext.init(...)
                       |
             SSLSocket / SSLEngine
                       |
                  TLS handshake
```

**Store** giữ dữ liệu. **Manager** dùng dữ liệu theo chính sách trong handshake. **Context** ghép các manager và làm nơi tạo các đối tượng TLS. Không thay thế tên gọi hoặc vai trò của chúng cho nhau.

## 2. Ai chứng minh danh tính, ai kiểm tra?

Xét một TLS client `A` kết nối tới TLS server `B`:

- `B` phải **trình chứng chỉ server** và chứng minh có private key tương ứng theo TLS handshake. JSSE server dùng local **`KeyManager`**, thường đọc từ **server identity keystore**.
- `A` phải **kiểm tra chứng chỉ server**: chain có đáng tin theo trust anchor được chấp nhận, còn hiệu lực, dùng đúng mục đích/chính sách và đúng **hostname/IP** của dịch vụ không? JSSE client dùng **`TrustManager`** cùng cấu hình endpoint identification phù hợp.
- Để xác thực server theo TLS thông thường, `A` **không cần sở hữu client certificate**. Việc không có local client identity không đồng nghĩa `A` không thể xác thực `B`.

```text
                       A: CLIENT                       B: SERVER
                  client-truststore                server-keystore
                  [CA / server cert]               [server private key]
                           |                               |
                 TrustManager kiểm tra               KeyManager lựa chọn
                           |                               |
  TLS client <-------------+------- certificate chain -----+-- TLS server
             Verify chain + endpoint identity
             Verify server proof-of-possession
```

Chia sẻ **public certificate** đúng mục đích không đồng nghĩa chia sẻ **private key**. Private key server phải ở server/secret storage được phép quản lý; không chép cả `server.p12` chứa private key cho phía client chỉ để client “tin server”.

## 3. TLS một chiều và mutual TLS (mTLS)

| Trường hợp | KeyManager server | TrustManager server kiểm tra client | KeyManager client | TrustManager client kiểm tra server |
| --- | --- | --- | --- | --- |
| Server-authenticated TLS phổ biến | Cần identity server | Không cần kiểm tra client certificate nếu server không yêu cầu | Không bắt buộc | Cần trust server |
| mTLS dùng certificate hai chiều | Cần identity server | **Cần** trust client | **Cần** identity client | Cần trust server |

Với mTLS, **cả client lẫn server đồng thời có vai trò “present” và “verify”**:

```text
Server                                               Client
======                                               ======
server-keystore.p12                                  client-keystore.p12
  server private key                                   client private key
  server certificate chain                             client certificate chain
         |                                                      |
   KeyManager                                        KeyManager
       trình cert server                               trình cert client

server-trust.p12                                     client-trust.p12
  trusted client CA/cert                               trusted server CA/cert
         |                                                      |
   TrustManager                                     TrustManager
       kiểm tra client                                kiểm tra server
```

Đặc biệt:

1. `KeyManager` **không chỉ dành cho server**. Khi mTLS client trình chứng chỉ, client cũng dùng nó.
2. `TrustManager` **không chỉ dành cho client**. Khi server muốn kiểm tra cert của client, server cũng dùng nó.
3. Chỉ cấp client keystore không khiến server tự đòi cert: server phải thiết lập yêu cầu client authentication. Với `SSLServerSocket` hoặc `SSLEngine`, dùng `setNeedClientAuth(true)` khi **bắt buộc** phải có chứng chỉ client. `setWantClientAuth(true)` là **tùy chọn**, không tương đương.
4. Ngay cả khi client certificate đã được trust manager chấp thuận, server còn cần quyết định **authorization**: client identity nào được phép dùng endpoint/dữ liệu nào?

## 4. Keystore và truststore: định dạng giống, entry khác

Java không định nghĩa một class riêng `TrustStore` để thay `KeyStore`. Trong thực tế, cả hai là `KeyStore` được tổ chức cho mục đích khác nhau.

Ví dụ:

```text
server.p12
  alias server
  Entry type: PrivateKeyEntry
    private key: server giữ bí mật
    certificate chain: server leaf + intermediate nếu có

client-trust.p12
  alias server-cert
  Entry type: TrustedCertificateEntry
    public certificate: bản self-signed server của lab
    private key: KHÔNG CÓ
```

- **`PrivateKeyEntry`** chứa key bí mật/riêng và chain; `KeyManager` cần nó khi bên mình phải chứng minh sở hữu key.
- **`TrustedCertificateEntry`** chứa certificate được xem là trust material; `TrustManager` dùng các entry theo thuật toán của provider để quyết định chain có đáng tin không.
- **Alias** chỉ là tên gọi trong store. Alias `server` không phải DNS hostname mà TLS xác thực. Tên địa chỉ được xác nhận qua thông tin certificate như **Subject Alternative Name (SAN)**.
- **`PKCS12`, `JKS`** là các kiểu store; `.p12`/`.jks` chỉ là cách đặt tên tệp, không đủ để xác định vai trò. Trong JDK mới, PKCS#12 thường là lựa chọn mặc định, nhưng dùng `KeyStore.getInstance("PKCS12")` cho code rõ ràng.
- Truststore có thể chứa các CA được tin hoặc một leaf certificate được pin theo chính sách. **Phạm vi trust khác nhau**: tin root CA có thể chấp nhận nhiều leaf do CA ấy cấp, trong khi tin một leaf self-signed cụ thể chỉ phù hợp khi có thiết kế trust cụ thể.

## 5. Private key và certificate chain làm được gì?

Certificate X.509 chứa **public key**, subject/SAN, validity period, issuer và các extensions như key usage/EKU. Private key tương ứng ở local identity store cho phép thực hiện bước chứng minh sở hữu key trong TLS handshake. Nó **không cần và không được chia sẻ** cho peer.

```text
        ROOT CA (trust anchor)
             |
             | ký
             v
        Intermediate CA
             |
             | ký
             v
       Leaf certificate (server)
             |
             | public key tương ứng
             v
       Server PRIVATE KEY  <--- chỉ bên server kiểm soát
```

Server thường trình **leaf + intermediate cần thiết**. Client xây dựng/đánh giá chain tới trust anchor theo PKIX/thuật toán đã cấu hình. Root CA mà client đã tin thường không cần gửi trong chain. Việc validate có thể tính tới chữ ký, thời hạn, constraints, key usage, algorithm restrictions và chính sách revocation.

Lưu ý hai cấp độ độc lập:

- **Certificate path trust**: chain có thể được xây dựng tới trust anchor được phép không?
- **Endpoint identity**: certificate được tin đó có đúng cho tên máy/IP mà application dự định kết nối không?

Nếu chỉ giải quyết “chain được CA tin cậy ký” mà bỏ qua hostname verification, certificate của `alpha.example` có thể bị sử dụng sai khi kết nối tới `beta.example` trong một client tự viết không kiểm tra tên. **Trust hợp lệ không tự chứng minh đúng đích**.

## 6. KeyManager và KeyManagerFactory

`KeyManagerFactory` tạo `KeyManager` từ nguồn key material đã load. Với X.509, `X509KeyManager` hoặc `X509ExtendedKeyManager` chọn alias/private key/chain phù hợp với loại chứng chỉ, issuer, thuật toán và TLS context.

Snippet **minh họa, không phải class độc lập**:

```java
KeyStore identity = KeyStore.getInstance("PKCS12");
// ... identity.load(input, storePassword) ...
KeyManagerFactory kmf = KeyManagerFactory.getInstance(
        KeyManagerFactory.getDefaultAlgorithm());
kmf.init(identity, keyPassword);
KeyManager[] keyManagers = kmf.getKeyManagers();
```

**Ý nghĩa của từng bước:**

1. `KeyStore.load` mở dữ liệu của store; nếu file sai/không đọc được hoặc mật khẩu không phù hợp, sẽ lỗi ngay từ bước load.
2. `kmf.init(identity, keyPassword)` chuẩn bị cách truy xuất **private key** ở alias phù hợp.
3. `getKeyManagers()` trả runtime managers. Họ có trách nhiệm chọn credential cục bộ khi handshake cần trình certificate.
4. Server có thể có nhiều alias/certificate để phục vụ các hostname hoặc key algorithms khác nhau; phải có alias/cert/chain thật sự tương thích.
5. `X509ExtendedKeyManager` có hỗ trợ chọn credential trong ngữ cảnh `SSLEngine` cho ứng dụng NIO/TLS.

Một `KeyManager` được cấu hình thành công **không có quyền quyết định peer có tin cert đó hay không**. Client vẫn có thể từ chối vì thiếu CA, SAN sai, expiry hoặc policy. Hơn nữa, nếu certificate và private key không khớp, handshake có thể thất bại dù store mở được.

## 7. TrustManager và TrustManagerFactory

`TrustManagerFactory` tạo `TrustManager` từ nguồn trust anchors/policy phù hợp. Với X.509, `X509TrustManager` và `X509ExtendedTrustManager` kiểm tra certificate chain được peer trình.

Snippet **minh họa, không phải class độc lập**:

```java
KeyStore trustedPeers = KeyStore.getInstance("PKCS12");
// ... trustedPeers.load(input, storePassword) ...
TrustManagerFactory tmf = TrustManagerFactory.getInstance(
        TrustManagerFactory.getDefaultAlgorithm());
tmf.init(trustedPeers);
TrustManager[] trustManagers = tmf.getTrustManagers();
```

`checkServerTrusted(...)` thường phục vụ đánh giá cert của server phía client; `checkClientTrusted(...)` phục vụ đánh giá cert của client phía server mTLS. Những biến thể `X509ExtendedTrustManager` có tham số `Socket` hoặc `SSLEngine` cho phép kết hợp ngữ cảnh kết nối.

**Quan trọng:** trust manager **không phát private key**, và việc chỉ đặt certificate vào truststore không có nghĩa application có identity tương ứng. Truststore phải có tính toàn vẹn, vì nếu người tấn công có thể thêm root CA vào truststore thì có thể mở rộng tập peer được tin.

Khi cần chính sách custom, nên cân nhắc **delegate tới trust manager PKIX hợp lệ rồi siết thêm điều kiện**. Không tự viết `checkServerTrusted` rỗng để mọi certificate đều được chấp nhận. Thay trust manager mặc định bằng implementation tự chế sai sẽ phá vỡ phần thiết yếu của TLS.

## 8. Tạo demo identity và truststore bằng keytool (JDK 17+)

Hai ví dụ chạy được dưới đây sử dụng **self-signed certificate chỉ dành cho loopback lab**. Máy phải có `java`, `javac` và `keytool` từ JDK 17+ trong PATH. Các lệnh chạy trong **một thư mục lab** riêng, không dùng file/credential của production.

### Bước 1: tạo server identity PKCS#12

```sh
keytool -genkeypair -alias server -keyalg RSA -keysize 2048 -validity 30 -dname "CN=localhost, OU=Learning, O=Example, C=US" -ext "SAN=dns:localhost,ip:127.0.0.1" -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -noprompt
```

Tệp `server.p12` chứa **private key + self-signed server certificate**. `-alias server` chỉ đặt alias nội bộ. `SAN=dns:localhost,ip:127.0.0.1` gán danh tính đích để client raw `SSLSocket` trong demo có thể kiểm tra địa chỉ `127.0.0.1` bằng thuật toán endpoint identification `HTTPS`. Không trông cậy vào Common Name `CN=localhost` thay cho SAN.

### Bước 2: xuất public certificate, không xuất private key

```sh
keytool -exportcert -alias server -keystore server.p12 -storepass changeit -rfc -file server.crt
```

Tệp `server.crt` chứa certificate dạng PEM; không có private key. Có thể cung cấp public certificate này cho bên cần cấu hình trust material của lab.

### Bước 3: import vào truststore của client

```sh
keytool -importcert -alias server-cert -file server.crt -keystore client-trust.p12 -storetype PKCS12 -storepass changeit -noprompt
```

Truststore `client-trust.p12` giữ public certificate dưới `TrustedCertificateEntry`, **không giữ server private key**. Import leaf self-signed như trust anchor là cách thiết lập tin cậy cụ thể trong lab, không phải một mô hình CA/PKI production.

### Bước 4: kiểm tra loại entry

```sh
keytool -list -keystore server.p12 -storetype PKCS12 -storepass changeit
keytool -list -keystore client-trust.p12 -storetype PKCS12 -storepass changeit
```

Kỳ vọng alias `server` là `PrivateKeyEntry`, alias `server-cert` là `trustedCertEntry` (cách viết hoa trong output có thể khác). Đừng gửi `server.p12` cho client; file đó có private key.

Mật khẩu `changeit` là **mật khẩu cố định dùng làm ví dụ học tập**, tuyệt đối không dùng cho hệ thống thật. Command-line arguments và lịch sử shell có thể làm lộ mật khẩu; trong production hãy dùng secret management, quyền file và cơ chế nhập credential phù hợp. Private key lab cũng cần được dọn dẹp sau khi sử dụng.

## 9. Java 17+ demo số 1: phân biệt entry type và khởi tạo SSLContext

Lưu tệp **`TlsRolesInspect.java`** dưới đây vào đúng thư mục lab vừa tạo. Chương trình đọc hai PKCS#12 stores, kiểm tra alias/entry, sau đó init `KeyManagerFactory`, `TrustManagerFactory` và một `SSLContext` riêng.

```java
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.Arrays;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.TrustManagerFactory;

public class TlsRolesInspect {
    static KeyStore load(Path file, char[] pass) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(file)) {
            store.load(in, pass);
        }
        return store;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Usage: TlsRolesInspect server.p12 client-trust.p12");
        }
        char[] pass = "changeit".toCharArray(); // LAB ONLY!
        try {
            KeyStore identity = load(Path.of(args[0]), pass);
            KeyStore trusted = load(Path.of(args[1]), pass);

            System.out.println("Server identity has private key: "
                    + identity.isKeyEntry("server"));
            System.out.println("Client trusts certificate: "
                    + trusted.isCertificateEntry("server-cert"));
            System.out.println("Truststore holds private key: "
                    + trusted.isKeyEntry("server-cert"));

            KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                    KeyManagerFactory.getDefaultAlgorithm());
            kmf.init(identity, pass);
            TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                    TrustManagerFactory.getDefaultAlgorithm());
            tmf.init(trusted);

            SSLContext context = SSLContext.getInstance("TLS");
            context.init(kmf.getKeyManagers(),
                    tmf.getTrustManagers(), new SecureRandom());
            System.out.println("Custom TLS context ready: "
                    + (context.getSocketFactory() != null));
        } finally {
            Arrays.fill(pass, '\0');
        }
    }
}
```

Biên dịch và chạy:

```sh
javac -encoding UTF-8 TlsRolesInspect.java
java TlsRolesInspect server.p12 client-trust.p12
```

Stdout khi tạo stores theo bước 8:

```text
Server identity has private key: true
Client trusts certificate: true
Truststore holds private key: false
Custom TLS context ready: true
```

Vì sao đúng?

- Cả hai file có định dạng PKCS12, nhưng `identity.isKeyEntry("server")` trả `true` vì entry chứa private key.
- `trusted.isCertificateEntry("server-cert")` trả `true`, còn `trusted.isKeyEntry("server-cert")` là `false`. Store bên client chỉ giữ certificate để tin peer.
- `kmf.init(identity, pass)` cấp local key material cho manager; `tmf.init(trusted)` cấp trust material cho manager. `SSLContext.init(kms,tms,random)` ghép cả hai trách nhiệm.
- `Custom TLS context ready: true` **chỉ chứng nhận context đã khởi tạo được**, không chứng nhận handshake thực với peer đã thành công hay hostname đúng. Đó là bài kiểm tra riêng.

`Arrays.fill(pass, '\0')` giảm thời gian giữ mảng password sau khi dùng, nhưng code demo chứa literal `"changeit"`, không phải cách bảo mật credential production.

## 10. Java 17+ demo số 2: TLS loopback, server identity và client trust

Chương trình **`TlsLoopback.java`** tạo server context với `KeyManager` đọc `server.p12`; client context với `TrustManager` đọc `client-trust.p12`. Client **không có local certificate** vì đây là TLS xác thực server một chiều, không phải mTLS.

Trong mã, raw `SSLSocket` client bật `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` trước handshake, để xác minh `127.0.0.1` khớp **IP SAN** của server certificate. Hai phía trao đổi request `PING` và response `ACK:PING` qua TLS loopback.

```java
import java.io.BufferedReader;
import java.io.BufferedWriter;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.net.InetAddress;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.Arrays;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.TrustManagerFactory;

public class TlsLoopback {
    static KeyStore load(Path file, char[] pass) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(file)) {
            store.load(in, pass);
        }
        return store;
    }

    static SSLContext forServer(Path identityPath, char[] pass)
            throws Exception {
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(load(identityPath, pass), pass);
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(kmf.getKeyManagers(), null, new SecureRandom());
        return context;
    }

    static SSLContext forClient(Path trustPath, char[] pass)
            throws Exception {
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(load(trustPath, pass));
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(null, tmf.getTrustManagers(), new SecureRandom());
        return context;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Usage: TlsLoopback server.p12 client-trust.p12");
        }
        char[] pass = "changeit".toCharArray();
        try {
            SSLContext serverTls = forServer(Path.of(args[0]), pass);
            SSLContext clientTls = forClient(Path.of(args[1]), pass);
            InetAddress local = InetAddress.getByAddress(
                    new byte[] {127, 0, 0, 1});

            try (SSLServerSocket listener = (SSLServerSocket)
                    serverTls.getServerSocketFactory()
                            .createServerSocket(0, 10, local)) {
                listener.setSoTimeout(10_000);
                int port = listener.getLocalPort();
                ExecutorService workers = Executors.newSingleThreadExecutor();
                try {
                    Future<String> future = workers.submit(() -> {
                        try (SSLSocket peer = (SSLSocket) listener.accept()) {
                            peer.setSoTimeout(10_000);
                            peer.startHandshake();
                            BufferedReader in = new BufferedReader(
                                    new InputStreamReader(
                                            peer.getInputStream(),
                                            StandardCharsets.UTF_8));
                            BufferedWriter out = new BufferedWriter(
                                    new OutputStreamWriter(
                                            peer.getOutputStream(),
                                            StandardCharsets.UTF_8));
                            String request = in.readLine();
                            out.write("ACK:" + request);
                            out.newLine();
                            out.flush();
                            return request;
                        }
                    });

                    try (SSLSocket client = (SSLSocket)
                            clientTls.getSocketFactory()
                                    .createSocket("127.0.0.1", port)) {
                        client.setSoTimeout(10_000);
                        SSLParameters parameters = client.getSSLParameters();
                        parameters.setEndpointIdentificationAlgorithm("HTTPS");
                        client.setSSLParameters(parameters);
                        client.startHandshake();

                        BufferedWriter out = new BufferedWriter(
                                new OutputStreamWriter(
                                        client.getOutputStream(),
                                        StandardCharsets.UTF_8));
                        BufferedReader in = new BufferedReader(
                                new InputStreamReader(
                                        client.getInputStream(),
                                        StandardCharsets.UTF_8));
                        out.write("PING");
                        out.newLine();
                        out.flush();

                        String reply = in.readLine();
                        System.out.println("TLS handshake success: true");
                        System.out.println("Peer certificate available: "
                                + (client.getSession()
                                        .getPeerCertificates().length > 0));
                        System.out.println("Client reply: " + reply);
                    }
                    System.out.println("Server request: "
                            + future.get(15, TimeUnit.SECONDS));
                } finally {
                    workers.shutdownNow();
                }
            }
        } finally {
            Arrays.fill(pass, '\0');
        }
    }
}
```

Biên dịch và chạy:

```sh
javac -encoding UTF-8 TlsLoopback.java
java TlsLoopback server.p12 client-trust.p12
```

Stdout của kết nối hợp lệ:

```text
TLS handshake success: true
Peer certificate available: true
Client reply: ACK:PING
Server request: PING
```

Các điểm học tập:

1. Server `KeyManagerFactory` có private key/cert chain ở store identity. Client `TrustManagerFactory` tin đúng public certificate đã import.
2. Client `context.init(null, tmf.getTrustManagers(),...)` không đưa local key material, **không biến quá trình thành mTLS**.
3. `setEndpointIdentificationAlgorithm("HTTPS")` khiến client kiểm tra tên/IP của endpoint trong chứng chỉ qua provider hỗ trợ. IP `127.0.0.1` cần **IP SAN**, không chỉ DNS SAN `localhost`.
4. `client.startHandshake()` thực hiện handshake; nếu client không tin certificate hoặc endpoint identity không khớp, kết nối bị từ chối thay vì tiếp tục trao đổi ứng dụng.
5. `getPeerCertificates()` trả peer certificates sau handshake. Nó **không thay thế** trust manager và hostname checking; việc app gọi method rồi đếm cert không phải quy trình xác thực.
6. Server worker thread và client thread chạy đồng thời nhằm tránh chờ vòng tròn khi handshake, đọc và ghi. Listener bind **chỉ vào 127.0.0.1**, không lắng nghe Internet.
7. TLS `ACK:PING` trong demo là **phản hồi ứng dụng**, không chứng minh dữ liệu đã được lưu vào DB hoặc được cấp quyền truy cập.

Để thử nghiệm thực, certificate cần được cấp bởi PKI phù hợp, không dùng self-signed và mật khẩu hardcode như lab.

## 11. SSLContext: nơi ghép identity và trust, không phải store

`SSLContext` cung cấp factory cho `SSLSocket`, `SSLServerSocket` và `SSLEngine`, cùng state TLS cần thiết. Bạn cấu hình **runtime managers**:

```java
// Snippet: kmf và tmf đã được init trước đó.
SSLContext context = SSLContext.getInstance("TLS");
context.init(
        kmf.getKeyManagers(),     // local identity
        tmf.getTrustManagers(),   // peer verification
        new SecureRandom()
);
```

Một `SSLContext` đã init không tự tạo keystore, không tự ký certificate và không chứng minh chain/hostname. Các phép xác minh danh tính thực tế diễn ra khi handshake cho từng connection.

**Semantics `null` quan trọng:** với SunJSSE, `KeyManager[] = null` thông thường nghĩa không cung cấp local key credentials, còn `TrustManager[] = null` khiến provider dùng mặc định theo cơ chế của nó. Điều đó **không phải “trust all”**. Nếu chính sách yêu cầu một truststore riêng, cung cấp rõ managers do `TrustManagerFactory` init bằng store đó, không dựa vào implicit fallback.

Không mặc định `SSLContext.getInstance("TLS")` dùng TLS 1.0: `TLS` là tên context hỗ trợ đàm phán các phiên bản TLS theo JDK/provider/policy; tránh bật lại protocol/cipher lỗi thời chỉ vì peer cũ không kết nối được.

## 12. Truststore mặc định và truststore được cấu hình riêng

Java có cơ chế default trust material thông qua provider/JDK settings; ở SunJSSE, cấu hình có thể xem xét `javax.net.ssl.trustStore` và các file truststore được cài như `jssecacerts`, `cacerts` theo quy tắc của phiên bản/provider.

| Cách tạo trust managers | Điều cần nhớ |
| --- | --- |
| `tmf.init((KeyStore) null)` | Yêu cầu provider lấy trust material mặc định theo quy tắc của nó |
| `tmf.init(customTrust)` | Dùng trust material từ **store được truyền tường minh**, không mặc nhiên cộng với default CA set |
| `tmf.init(emptyKeyStore)` | Không có trust anchors mong muốn; có thể khiến mọi chain validation theo cơ chế này thất bại |
| `SSLContext.init(km, null, rng)` | Provider quyết định trust managers mặc định; không được hiểu là vô hiệu hóa kiểm tra |

Một truststore chỉ có private CA nội bộ có thể làm client kết nối được API nội bộ nhưng **không còn tin public HTTPS endpoints** nếu application chỉ dùng custom truststore ấy. Nếu cần hai nhóm trust khác nhau, cân nhắc **SSLContext riêng theo service** hoặc chính sách kết hợp đã được thiết kế, thay vì thêm “CA nào cũng được” vào một truststore global.

Các JVM properties thường gặp:

```text
-Djavax.net.ssl.keyStore=/path/identity.p12
-Djavax.net.ssl.keyStoreType=PKCS12
-Djavax.net.ssl.trustStore=/path/trust.p12
-Djavax.net.ssl.trustStoreType=PKCS12
```

Chúng tác động tới cách lấy **default managers/context** phù hợp, không tự ghi đè một `SSLContext` tự init bằng managers riêng. Password JVM properties/arguments cũng có rủi ro lộ secret qua process configuration hoặc logs. Với ứng dụng đa tenant/service, ưu tiên scope trust/identity rõ hơn là một thay đổi toàn JVM.

## 13. Hostname verification là lớp kiểm tra riêng

Ví dụ client muốn gọi `service-a.example`. Certificate có chain hợp lệ đến một CA được tin, nhưng SAN chỉ chứa `service-b.example`. Nếu application chỉ kiểm tra chain mà **không xác minh tên đích**, nó có thể tin sai dịch vụ.

Trong raw JSSE dùng `SSLSocket`:

```java
// Snippet minh họa: socket đã tạo từ SSLSocketFactory.
SSLParameters parameters = socket.getSSLParameters();
parameters.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(parameters);
socket.startHandshake();
```

`HTTPS` ở đây là tên thuật toán nhận diện endpoint được JSSE hỗ trợ, không đồng nghĩa bạn đang bắt buộc dùng HTTP trên socket. Với HTTP client có lớp xác minh hostname tích hợp, sử dụng chính sách của client thay vì tự chồng một verifier không hiểu ngữ cảnh.

**SAN vs CN:** đối với hostname hoặc IP, thiết kế certificate phải có SAN tương ứng. Đừng dựa vào `CN` như một cách “chữa” certificate thiếu SAN. Khi connect bằng IP, cần một **IP SAN** matching; DNS SAN chứa `localhost` không tự động xác minh `127.0.0.1`.

Nói cách khác: **truststore quyết định CA/cert nào được tin**; **endpoint identification quyết định cert ấy có đúng với host/IP dự kiến không**. Cả hai đều quan trọng.

## 14. Xử lý mTLS đúng với cả hai chiều

Trong mTLS, server trình `server.p12`, client trình `client-identity.p12`; đồng thời client tin server CA/cert và server tin client CA/cert.

Một đoạn **minh họa API, không độc lập**, các factory đã khởi tạo từ nguồn đúng:

```java
SSLContext serverContext = SSLContext.getInstance("TLS");
serverContext.init(
        serverKeyManagerFactory.getKeyManagers(),
        serverClientTrustFactory.getTrustManagers(),
        new SecureRandom()
);

SSLServerSocket listener = (SSLServerSocket)
        serverContext.getServerSocketFactory().createServerSocket(port);
listener.setNeedClientAuth(true);

SSLContext clientContext = SSLContext.getInstance("TLS");
clientContext.init(
        clientKeyManagerFactory.getKeyManagers(),
        clientServerTrustFactory.getTrustManagers(),
        new SecureRandom()
);
```

Nếu server cấu hình `setWantClientAuth(true)`, client có thể không trình certificate và handshake vẫn được chấp nhận tùy chính sách. Nếu nghiệp vụ thực sự cần xác thực client, dùng `setNeedClientAuth(true)`. Phải chú ý certificate dùng đúng **Extended Key Usage** (ví dụ serverAuth/clientAuth khi policy yêu cầu), issuer/trust anchor, thời hạn và danh tính được map tới quyền nghiệp vụ.

Không lẫn client certificate authentication với đăng nhập/authorization. Một certificate client được CA nội bộ ký không tự chứng minh nó có quyền sửa dữ liệu của tất cả tenant.

## 15. Không được dùng trust-all để sửa lỗi handshake

Một anti-pattern nguy hiểm là tự cài `X509TrustManager` có `checkServerTrusted` và `checkClientTrusted` rỗng:

```java
// Chỉ để nhận diện lỗi bảo mật: KHÔNG SỬ DỤNG.
X509TrustManager unsafe = new X509TrustManager() {
    public void checkServerTrusted(X509Certificate[] c, String a) {}
    public void checkClientTrusted(X509Certificate[] c, String a) {}
    public X509Certificate[] getAcceptedIssuers() {
        return new X509Certificate[0];
    }
};
```

Đây là snippet thiếu imports, chỉ để **nhận diện anti-pattern**, không phải một chương trình hướng dẫn chạy. Việc bỏ trống kiểm tra xóa bỏ lớp xác thực chứng chỉ. Nếu đồng thời dùng hostname verifier luôn trả true, app dễ trở thành mục tiêu của man-in-the-middle.

Cách xử lý đúng: tìm nguyên nhân của lỗi `SSLHandshakeException`/`CertPathValidatorException`, cung cấp đúng trust anchors, chain và SAN, đảm bảo server có private key và certificate hợp lệ, rồi kiểm thử lại **trường hợp bị từ chối**. Nếu cần custom trust policy, xem xét delegate tới trust manager PKIX chuẩn và chỉ thêm ràng buộc chặt hơn; không bỏ qua kiểm tra.

Đặc biệt không import mọi certificate tự gặp vào truststore một cách tự động trong môi trường không tin cậy. Làm vậy tương đương cho peer mới quyền tự chỉ định ai được tin.

## 16. Khoanh lỗi theo chiều xác thực

| Triệu chứng | Cần điều tra | Không nên phản ứng bằng cách |
| --- | --- | --- |
| `PKIX path building failed` ở client | Client truststore, CA root/intermediate, chain server gửi | Trust-all |
| `No subject alternative names matching IP address` | SAN IP trong server cert, IP đã kết nối, endpoint ID | Tắt hostname checking |
| `No name matching ...` | DNS SAN và tên host thật của request | Chỉ đổi alias trong store |
| `no suitable certificate` | Local identity store, `PrivateKeyEntry`, chain, key type, password | Chép private key sang peer |
| `unknown_ca` / `bad_certificate` ở mTLS | Server trust client certificate/CA, client đã trình cert hay chưa | Tắt needClientAuth nếu vẫn cần mTLS |
| `UnrecoverableKeyException` | Key entry password và provider/type | Bỏ password/security |
| `certificate_expired` | Clock, validity period và chain/policy | Nới trust manager cho cert hết hạn |
| HTTP 403 sau TLS thành công | App authorization, principal mapping | Đổ lỗi cho truststore |

Chuỗi thông báo khác nhau theo provider/TLS version, và phía nhận alert có thể chỉ thấy thông báo chung. Đọc log **hai đầu** mới biết bên nào từ chối chứng chỉ.

Trong môi trường lab, có thể bật debug:

```text
-Djavax.net.debug=ssl,handshake,trustmanager,keymanager
```

Tùy provider/JDK, log có thể chứa certificate chain, hostname hoặc metadata nhạy cảm. Chỉ bật tạm khi phù hợp với chính sách log nội bộ, rồi tắt. Đừng đưa log đầy đủ chứa thông tin nội bộ/secret lên diễn đàn công khai.

## 17. Quản lý mật khẩu, private key, rotation và integrity

Đừng nhầm hai loại mật khẩu:

- **Store password:** bảo vệ/kiểm tra quyền mở toàn kho, phụ thuộc provider/store type.
- **Key password:** dùng để khôi phục private key của key entry; `KeyManagerFactory.init(identity, keyPassword)` sử dụng nguồn key material với password phù hợp.

Nhiều triển khai PKCS12 trên JDK dùng mật khẩu store và key giống nhau, nhưng hai khái niệm không hoàn toàn đồng nghĩa cho mọi provider. Một store có thể load được nhưng không lấy được key nếu mật khẩu key sai.

Các biện pháp quan trọng:

1. **Private key là bí mật:** không commit vào Git, không gửi vào client truststore, không gắn kèm ảnh build/container công khai, không đưa vào logs.
2. **Bảo vệ tính toàn vẹn truststore:** dù certificate là public, người có quyền thêm CA vào truststore có thể thay đổi phạm vi tin của ứng dụng.
3. **Không hardcode secrets production:** `changeit` ở demo chỉ để học API. Secrets thực cần vault/KMS/HSM hoặc cơ chế triển khai bảo vệ tương đương.
4. **Phân quyền file:** process TLS service chỉ được đọc đúng identity/trust material cần thiết; tránh cả write không cần thiết.
5. **Chuẩn bị rotation:** thay cert/key trước ngày hết hạn, kiểm tra chain/SAN/EKU, giai đoạn overlap trust khi cần, rollback policy rõ.
6. **Reload có chủ đích:** việc thay `.p12` trên disk **không đảm bảo** `SSLContext` đã khởi tạo tự phát hiện. Cần tạo lại managers/context/factories theo lifecycle và kiểm soát kết nối/phiên cũ.
7. **Thu hồi/certificate revocation:** tùy policy và provider cần cấu hình CRL/OCSP, giám sát certificate status; không giả định mọi ứng dụng Java tự luôn kiểm tra revocation online.
8. **HSM/PKCS#11:** key material có thể được quản lý bởi token/provider thay vì một file PKCS12; vai trò `KeyManager` vẫn là local identity.

## 18. Những nhầm lẫn phổ biến

1. **“KeyManager kiểm tra chứng chỉ server.”** Không theo trách nhiệm chính: KeyManager chọn local credential; TrustManager kiểm tra peer.
2. **“TrustManager cung cấp private key để server ký handshake.”** Sai: đó là identity/key manager.
3. **“Chỉ cần public certificate trong server keystore là server chạy TLS.”** Server certificate authentication thường cần private key khớp.
4. **“Client phải có bản sao server private key để tin server.”** Tuyệt đối sai về bảo mật.
5. **“Keystore phải là JKS còn truststore phải là P12.”** Hai store có thể cùng PKCS12 hoặc type phù hợp khác.
6. **“Alias của keystore phải bằng hostname.”** Alias là tên entry; SAN/endpoint identification mới quyết định host match.
7. **“Truststore có root CA hợp lệ là không cần hostname verification.”** Chain trust không chứng minh đúng hostname.
8. **“mTLS chỉ yêu cầu server có truststore.”** mTLS cần cả client identity, server identity và trust ở cả hai phía.
9. **“Dùng wantClientAuth là buộc mọi client có cert.”** Muốn bắt buộc phải dùng needClientAuth.
10. **“Có thể sửa mọi lỗi PKIX bằng checkServerTrusted rỗng.”** Làm vậy vô hiệu hóa authentication.
11. **“SSLContext.init chạy thành công là handshake đã xong.”** Init cấu hình; handshake xảy ra khi connection hoạt động.
12. **“Đã có TLS thì mọi client được phép truy cập API.”** TLS authentication không thay authorization nghiệp vụ.
13. **“File truststore là public nên ai sửa cũng được.”** Integrity trust anchor rất quan trọng.
14. **“Thay file keystore sẽ tự đổi cert cho mọi connection.”** Reload và session lifecycle phải được thiết kế.
15. **“Một custom truststore tự cộng với default CA.”** Không mặc định; phụ thuộc chính sách/tmfactory được init.
16. **“Bật JVM properties sẽ ghi đè mọi SSLContext explicit.”** Không; context quản lý managers riêng có scope riêng.
17. **“Dùng trust-all chỉ trong production ngắn ngày không nguy hiểm.”** Đây là lỗ hổng xác thực, cần sửa đúng nguyên nhân.
18. **“Chứng chỉ client do CA hợp lệ cấp thì tự có quyền mọi tenant.”** Phải map identity/authorization riêng.

## 19. Câu hỏi tự kiểm tra

**1.** Server có cert `server.crt` nhưng không có private key. Có đủ cho TLS server authentication không? **Không.** KeyManager cần credential cục bộ có private key tương ứng.

**2.** Client muốn tin server self-signed trong lab. Nên chép file `server.p12` hay import public `server.crt` vào truststore? **Chỉ import public cert** (hoặc CA theo trust policy), không chép private key.

**3.** Server cần xác thực client bằng mTLS. Server còn cần TrustManager không? **Có.** Server phải validate client certificate chain, đồng thời đòi client cert bằng `setNeedClientAuth(true)`.

**4.** Client dùng `TrustManagerFactory.init(customTrustStore)`; có chắc public CA mặc định vẫn được tin không? **Không.** Custom trust material có thể thay thế tập CA trong context.

**5.** Đã trust CA ký certificate, nhưng host kết nối khác SAN. Kết nối có hợp lệ không? **Không** theo chính sách endpoint identification đúng: tên/IP phải khớp.

**6.** Hai file đều là `.p12`, file nào là keystore và file nào là truststore? **Tùy nội dung entry và cách manager dùng**, không theo extension.

**7.** `setWantClientAuth(true)` có bắt buộc client gửi chứng chỉ không? **Không**, khác `setNeedClientAuth(true)`.

**8.** Đã nhận alert `unknown_ca`, nên tắt trust manager để chạy tiếp? **Không.** Kiểm tra CA, chain, store và mapping trust đúng.

## 20. Checklist cấu hình trước khi triển khai

1. **Xác định ai là TLS server/client và có mTLS hay không.** Đừng nhầm role theo tên class HTTP.
2. **Xác định local identity store:** bên cần trình cert phải có private key và chain đúng; alias, SAN, EKU và algorithm phù hợp.
3. **Xác định peer truststore:** ai được tin theo CA/cert/policy; phạm vi trust phải tối thiểu đáp ứng nghiệp vụ.
4. **Khởi tạo manager factory theo trách nhiệm:** `KeyManagerFactory.init(identity, password)` và `TrustManagerFactory.init(trust)`.
5. **Ghép SSLContext đúng scope:** tránh một global context vô tình tin CA quá rộng cho mọi service.
6. **Kiểm tra endpoint identity:** raw TLS client bật hostname/IP check khi cần; SAN đúng với địa chỉ gọi.
7. **Nếu mTLS:** server yêu cầu client cert, client có identity, cả hai có trust anchors cho phía kia.
8. **Kiểm thử cả thành công và thất bại:** CA sai, SAN sai, cert hết hạn, thiếu private key, client thiếu certificate, sai password.
9. **Bảo vệ secret và truststore integrity:** permission, vault/KMS/HSM, không lộ key/pass qua source và logs.
10. **Lập kế hoạch rotation/reload:** theo dõi expiry, overlap CA khi cần, thiết lập SSLContext/engine/socket mới và rollback.
11. **Giữ authorization sau authentication:** cert hợp lệ không đương nhiên có quyền thao tác mọi resource.
12. **Không bao giờ vô hiệu hóa certificate validation để “fix nhanh”:** khắc phục nguyên nhân PKIX/endpoint thực tế.

**Tóm tắt:** `KeyManager` trả lời **“Tôi dùng private key/certificate nào để chứng minh tôi là ai?”**. `TrustManager` trả lời **“Tôi có tin certificate của peer này không?”**. *Keystore* thường giữ local private key + chain; *truststore* giữ public trust anchors/certificates. Hai store có thể cùng là PKCS#12; điều quan trọng là **dữ liệu, factory, vai trò TLS và chính sách endpoint identity**.
