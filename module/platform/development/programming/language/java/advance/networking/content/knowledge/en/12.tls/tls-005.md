# Hostname verification using endpoint identification with direct TLS sockets

## 1. The problem: TLS encryption alone is not enough to know you are talking to the right server

In Java, `SSLSocket` provides TLS connections for applications using direct sockets. TLS can encrypt data and verify the peer's certificate, but **certificate path validation does not equate to hostname/endpoint verification**.

For example, a client wants to connect to `api.example.com`. An attacker redirects traffic to a machine holding **a valid certificate issued by a trusted CA for `other.example.com`**. That certificate may be valid in signature, expiration, and chain, yet **it does not belong to the service name the client intends to access**. If the application only trusts that "the TLS handshake did not throw an exception" and skips endpoint verification, it could send tokens or sensitive data to the wrong server.

**Security rule for Java clients using `SSLSocket` directly: before the TLS handshake, enable endpoint identification with `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")`**, while keeping certificate chain validation through a trusted trust manager. The `"HTTPS"` choice is JSSE's endpoint identity verification algorithm name; it does not turn a custom socket application into HTTP.

This lesson focuses on the **Java client → TLS server** path. Having the server require a client certificate (mutual TLS, mTLS) is the reverse-direction authentication problem and does not replace **server hostname** verification on the client.

## 2. Three mechanisms to distinguish: trust, endpoint name, SNI

```text
Client wants to access: api.example.com
                 |
                 v
        TCP connect to an IP address
                 |
                 v
        TLS handshake + server certificate
                 |
          +------+------+------------------------+
          |             |                        |
          v             v                        v
   Chain/trust       Endpoint ID                 SNI
   validation        verification             (ClientHello)
          |             |                        |
   Does the cert   Is the cert authorized   Hostname hint so the
   chain to a CA/  to represent the exact   server selects the right
   trust anchor?   name api.example.com?    cert / virtual host config
          |             |                        |
          +------ AND --+                        |
                 |                               |
                 v                               |
        Accept only if both pass <---------------+
        (SNI helps the server pick a cert, NOT verify it)
```

| Mechanism | What question does it answer? | What it does **not** guarantee |
| --- | --- | --- |
| **Trust chain / PKIX** via `X509TrustManager` | Are the certificate chain, signature, trust anchor, and applicable certificate validation policies trustworthy? | That the certificate belongs to the **exact hostname** requested by the application |
| **Endpoint identification** | Does the identity **expected** by the client match an identity in the certificate (typically Subject Alternative Name, SAN)? | That the certificate is signed by a trusted CA if the trust manager was replaced with a trust-all implementation |
| **SNI** (Server Name Indication) | Tells the server the logical hostname during TLS setup so it can select the appropriate certificate/virtual host | Does not replace chain or hostname verification; the server can still send the wrong certificate |

When you do not actively configure endpoint identification on a directly created `SSLSocket`, **do not assume JSSE will automatically verify the hostname like a high-level HTTPS client**. Use `SSLParameters` to set it explicitly before the handshake. Client APIs such as `HttpsURLConnection` or `java.net.http.HttpClient` have their own HTTPS verification rules; do not extrapolate their default behavior to all code using `SSLSocket`.

**A distinguishing test:** a certificate issued by a trusted CA for `payments.example.com` when the socket is created with expected name `profile.example.com` **must be rejected by endpoint identification**, even though the trust chain is valid. Conversely, a certificate with a matching SAN name that is signed by a CA not in the trust store **must also be rejected by trust validation**.

## 3. Safe direct `SSLSocket` client pattern on Java 17+

In a normal application with a real server and a properly configured public/private PKI, you can use the **default `SSLSocketFactory`** to keep the JVM's default trust managers, and then configure hostname verification:

```java
import java.io.IOException;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSocketFactory;

public final class DirectTlsClient {
    public static void main(String[] args) throws IOException {
        String expectedHost = "api.example.com";
        int port = 443;

        SSLSocketFactory factory =
                (SSLSocketFactory) SSLSocketFactory.getDefault();
        try (SSLSocket ssl = (SSLSocket)
                factory.createSocket(expectedHost, port)) {
            SSLParameters params = ssl.getSSLParameters();
            params.setEndpointIdentificationAlgorithm("HTTPS");
            ssl.setSSLParameters(params);    // BEFORE handshake.

            ssl.setSoTimeout(5000);          // Read timeout, not a total deadline.
            ssl.startHandshake();            // Fail-closed if certificate is wrong.

            // Only exchange application data after TLS handshake succeeds.
            System.out.println("TLS server identity verified");
        }
    }
}
```

This is a **standalone file** `DirectTlsClient.java`, compilable with Java 17:

```bash
javac --release 17 DirectTlsClient.java
java DirectTlsClient
```

**Note:** `api.example.com` in the code is an illustrative name, not a service configured for running a test. No guaranteed success stdout is promised for this example because it depends on DNS, the server listening on the port, the certificate, and the actual trust store. The empirical example that creates its own server and trust store on loopback in section 7 will have deterministic test stdout.

Security-significant steps:

1. `expectedHost` must be **the logical name the application actually intends to connect to**, taken from an allowed configuration/target address, not from the contents of the certificate sent by the peer.
2. `createSocket(expectedHost, port)` lets JSSE know the **logical peer host**. If connecting via IP, proxy, or an existing transport, you must preserve the expected hostname when creating a layered socket (section 5).
3. Obtain `SSLParameters params = ssl.getSSLParameters()` and modify that one property, avoiding creating `new SSLParameters()` which could inadvertently omit other settings.
4. `setEndpointIdentificationAlgorithm("HTTPS")` enables the endpoint identity algorithm. Do not use `null` or an empty string to disable verification.
5. `ssl.setSSLParameters(params)` must run **before** `ssl.startHandshake()` and before any I/O operation that implicitly starts the TLS handshake.
6. Only send tokens/requests/secrets after `startHandshake()` completes successfully; when the handshake fails, **close the socket and abort the transaction**.

`SSLSocket.setSoTimeout(...)` affects socket read operations; it does not by itself create an **end-to-end deadline** covering DNS, TCP connect, the entire handshake, and business logic. To bound TCP connection time explicitly, use a TCP socket with `connect(address, timeout)` and then create a layered TLS socket as shown next.

## 4. Identity must be matched against SAN, not just the CA or destination IP

Hostname verification is based on the **expected hostname** and the identity advertised by the certificate. According to the HTTPS algorithm rules:

- If the client uses a DNS hostname `service.example.com`, the server certificate needs a corresponding DNS identity, typically in **`subjectAltName: dNSName`**.
- If the client genuinely expects an IP literal address such as `192.0.2.10`, the certificate needs a matching **`iPAddress`** SAN entry; having only a `dNSName` containing an IP-like string is not an equivalent substitute.
- `CN=service.example.com` in the Subject **should not be used instead of SAN** for modern certificates. Some older algorithms/implementations have a CN fallback mechanism in certain situations, but **do not design for or rely on that fallback**.
- Wildcard certificates have specific hostname matching rules; do not assume `*.example.com` matches arbitrary subdomain levels or the apex domain `example.com`.
- Hostname checking is separate from checking certificate expiration, signature, trust anchor, or key usage policies. A matching name with an untrusted chain must still fail.

**Examples:**

| Application-expected host | Certificate SAN | Identity result (assuming valid trust chain) |
| --- | --- | --- |
| `api.example.com` | `DNS:api.example.com` | Match |
| `api.example.com` | `DNS:other.example.com` | Mismatch |
| `192.0.2.10` | `IP:192.0.2.10` | Match |
| `192.0.2.10` | Only `DNS:api.example.com` | Does not match IP literal |
| `example.com` | Only `DNS:*.example.com` | Should not be considered a match for the apex domain |
| `a.b.example.com` | Only `DNS:*.example.com` | Single-label wildcard should not match multiple levels |

When an application connects directly to an IP returned by service discovery, **do not change `expectedHost` to the IP** just to make the socket connect succeed. If the service's trusted identity is `api.example.com`, keep that name for TLS verification; the IP is only the TCP transport destination. If the system truly uses an IP literal as its identity, issue a certificate with an appropriate `iPAddress` SAN.

## 5. Connecting TCP to an IP while verifying a DNS name: layered TLS socket

Sometimes a client must open a TCP connection to an address provided by DNS/cache/proxy/service discovery, yet still verify the certificate against the **original service name**. With JSSE, use the overload:

```java
SSLSocketFactory.createSocket(
        Socket existingTcp, String expectedHost, int port, boolean autoClose)
```

Illustrative snippet (within a method that already has `InetAddress ip`, `String expectedHost`, `int port`, and `IOException` handling):

```java
Socket transport = new Socket();
transport.connect(new InetSocketAddress(ip, port), 3000);

try (SSLSocket tls = (SSLSocket) factory.createSocket(
        transport, expectedHost, port, true)) {
    SSLParameters p = tls.getSSLParameters();
    p.setEndpointIdentificationAlgorithm("HTTPS");
    tls.setSSLParameters(p);
    tls.setSoTimeout(5000);
    tls.startHandshake();

    // Application data only after TLS handshake and endpoint check pass.
}
```

**Resource note:** in this shortened snippet, if creating the layered TLS socket throws an exception **before try-with-resources takes ownership**, you must close `transport` in a corresponding catch/finally block. In production code, wrap `transport` in an outer `try-with-resources` or manage closing reliably. Passing `autoClose=true` causes the layered TLS socket to close `transport` when it closes.

Meaning of the arguments:

- `transport`: the open TCP connection to the actual IP destination.
- `expectedHost`: **the logical hostname the client requires and the certificate must match**; it does not have to be the transport's IP string.
- `port`: the service port.
- `autoClose`: whether closing the TLS socket automatically closes the underlying socket.

Do not pick `expectedHost` by looking back at the server certificate and "matching" it against itself. That lets the peer decide the expected identity and defeats endpoint spoofing protection.

A layered socket with the right logical host also gives JSSE hostname context for other mechanisms such as SNI when the provider can use it; however, **SNI is still not a hostname verification step**. Keep the logical host intact and do not arbitrarily disable SNI to work around certificate errors.

## 6. What do TLS handshake success and failure mean?

For a client configured with an appropriate trust manager **and** endpoint identification before the handshake:

```text
TCP connected
     |
     v
Set SSLParameters endpoint algorithm = "HTTPS"
     |
     v
Start TLS handshake
     |
     +--> Check trust chain / certificate constraints
     |
     +--> Check expected hostname against certificate identity
     |
     +--> Negotiate TLS version, cipher suite, keys
     |
     +--> ANY FAILURE? -- yes --> SSLException / SSLHandshakeException
     |                            close connection; no sensitive data
     |
     v
Handshake successful
     |
     v
Application can send private data to verified TLS endpoint
```

A successful `startHandshake()` is only meaningful **within the scope of the security policy actually configured**. If the code replaces `TrustManager` with an "accept all certificates" implementation, or sets endpoint identification to empty, you cannot conclude that the server was properly authenticated from handshake success alone.

Conversely, if the handshake fails with a hostname mismatch error, the program **must not automatically retry with endpoint identification disabled**; doing so turns a MITM detection mechanism into a backdoor. Instead, verify the DNS/service name, certificate SAN, trust store, and server/SNI configuration, then fix the configuration or issue the correct certificate.

## 7. Java 17 empirical example: same certificate, valid name accepted and wrong name rejected

We create a **local TLS server on loopback** with a self-signed certificate solely for learning purposes. The certificate's SAN contains `DNS:localhost` and `IP:127.0.0.1`. The client has a dedicated trust store containing **the test server's public certificate**, so chain validation can pass in the test environment. We then make **two connections to the same IP/port**:

1. Connection A passes `expectedHost="localhost"` → the certificate has a matching DNS SAN → handshake passes.
2. Connection B passes `expectedHost="wrong.example"` → still trusts the same certificate, but **the DNS SAN does not match** → endpoint identification rejects it during the handshake.

This test isolates the two security conditions: **the trust store remains identical across both connections**, and the only variable changed is **the hostname expected by the client**. No trust-all manager is used, and hostname verification is not disabled.

### 7.1. Create the test certificate and trust store

In a **separate test directory** with JDK `keytool` available on `PATH`, run in order:

```bash
keytool -genkeypair -alias server -keyalg RSA -keysize 2048 -validity 2 -dname "CN=localhost" -ext "SAN=dns:localhost,ip:127.0.0.1" -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -noprompt
keytool -exportcert -alias server -keystore server.p12 -storepass changeit -rfc -file server.cer
keytool -importcert -alias local-test -file server.cer -keystore client-trust.p12 -storetype PKCS12 -storepass changeit -noprompt
```

Generated files:

- `server.p12`: key store **containing the server's private key** and certificate. Protect this file; do not commit it to Git or send it to clients.
- `server.cer`: public certificate exported from the server, used when creating the trust store.
- `client-trust.p12`: trust store for the **test client**, containing the public certificate accepted for this test. It does not need the server's private key.

**`changeit` here is only a hardcoded password for the localhost example; do not use it in production.** The test certificate has a short validity (`-validity 2` days) and must not be treated as a certificate issued by a public CA. In real systems, use a managed trust store, appropriate file permissions, non-hardcoded secrets, and certificate/key rotation.

### 7.2. Complete Java code

**File name:** `TlsEndpointIdentificationDemo.java`.

```java
import java.io.IOException;
import java.io.InputStream;
import java.net.InetAddress;
import java.net.Socket;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLHandshakeException;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSocketFactory;
import javax.net.ssl.TrustManagerFactory;

public final class TlsEndpointIdentificationDemo {
    private static final char[] PASSWORD = "changeit".toCharArray();

    static KeyStore loadStore(Path path) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(path)) {
            store.load(in, PASSWORD);
        }
        return store;
    }

    static SSLContext serverContext(Path keyStore) throws Exception {
        KeyManagerFactory keys = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        keys.init(loadStore(keyStore), PASSWORD);
        SSLContext ctx = SSLContext.getInstance("TLS");
        ctx.init(keys.getKeyManagers(), null, null);
        return ctx;
    }

    static SSLContext clientContext(Path trustStore) throws Exception {
        TrustManagerFactory trust = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        trust.init(loadStore(trustStore));
        SSLContext ctx = SSLContext.getInstance("TLS");
        ctx.init(null, trust.getTrustManagers(), null);
        return ctx;
    }

    static void connectAndVerify(SSLSocketFactory factory, InetAddress ip,
            int port, String expectedHost) throws Exception {
        Socket tcp = new Socket(ip, port);
        try (SSLSocket tls = (SSLSocket) factory.createSocket(
                tcp, expectedHost, port, true)) {
            tls.setSoTimeout(5000);
            SSLParameters params = tls.getSSLParameters();
            params.setEndpointIdentificationAlgorithm("HTTPS");
            tls.setSSLParameters(params);  // Before handshake.
            tls.startHandshake();
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Pass server.p12 and client-trust.p12");
        }
        SSLContext serverCtx = serverContext(Path.of(args[0]));
        SSLContext clientCtx = clientContext(Path.of(args[1]));
        InetAddress loopback = InetAddress.getLoopbackAddress();
        try (SSLServerSocket listener = (SSLServerSocket) serverCtx
                .getServerSocketFactory().createServerSocket(0, 50, loopback)) {
            listener.setSoTimeout(5000);
            ExecutorService worker = Executors.newSingleThreadExecutor();
            try {
                Future<?> server = worker.submit(() -> {
                    for (int i = 0; i < 2; i++) {
                        try (SSLSocket peer = (SSLSocket) listener.accept()) {
                            peer.setSoTimeout(5000);
                            peer.startHandshake();
                        } catch (IOException duringClientAbort) {
                            // The mismatch case can abort the server handshake.
                        }
                    }
                    return null;
                });
                int port = listener.getLocalPort();
                SSLSocketFactory factory = clientCtx.getSocketFactory();

                connectAndVerify(factory, loopback, port, "localhost");
                System.out.println("localhost: verified");

                try {
                    connectAndVerify(factory, loopback, port, "wrong.example");
                    throw new AssertionError("Expected hostname mismatch");
                } catch (SSLHandshakeException expected) {
                    System.out.println("wrong.example: rejected");
                }
                server.get(8, TimeUnit.SECONDS);
            } finally {
                worker.shutdownNow();
            }
        }
    }
}
```

**Run after generating the three test certificate/store files:**

```bash
javac --release 17 TlsEndpointIdentificationDemo.java
java TlsEndpointIdentificationDemo server.p12 client-trust.p12
```

Stdout on the tested Java 17 environment:

```text
localhost: verified
wrong.example: rejected
```

**Exact analysis:**

- The first connection has `expectedHost="localhost"` and SAN `DNS:localhost`; the client trusts the test certificate and has `"HTTPS"` enabled, so the TLS handshake succeeds.
- The second connection also goes to **the same loopback IP/port**, using the same `SSLContext` and trust store; `expectedHost="wrong.example"` is not in the SAN. `startHandshake()` throws `SSLHandshakeException`, which the program catches and prints `rejected`.
- These stdout lines only prove **the TLS check result in the test**, not that the server processed an application payload or a business API successfully.
- The demo server **ignores `IOException` when the client aborts the handshake** to keep stdout simple and allow both `accept` calls to finish. In a production server, log/handle exceptions by type, enforce timeouts, and do not silently ignore TLS errors arbitrarily.
- The demo uses a layered socket for both attempts. This clearly demonstrates that **the transport IP** does not determine the hostname check result when the client supplies **the logical peer hostname** to the factory.

### 7.3. Why not use the Internet/public CAs for this test?

If you test against a public website, the result depends on DNS, proxy policies, public CAs, system time, the remote server, and the network. A loopback test lets you control every input: a certificate you generated, a known SAN, a dedicated trust store, and two expected hostnames. This is a more reliable way to distinguish **a matching name** from **a mismatched name**, without needing a dangerous "trust-all `SSLContext`".

## 8. SNI helps select a certificate, not replace hostname verification

A TLS server can serve multiple hostnames on the same IP/port. The TLS `ClientHello` can include **Server Name Indication (SNI)** to help the server choose the corresponding certificate:

```text
TCP -> 203.0.113.10:443

Client expectedHost = api.example.com
ClientHello SNI     = api.example.com
Server chooses cert = DNS:api.example.com
Client verifies cert chain AND endpoint ID api.example.com
```

If SNI is omitted, the server may return a default certificate for a different hostname. When endpoint identification is enabled, the client must reject it if the default certificate's SAN does not match.

**Do not assume that "correct SNI means the hostname is verified."** SNI is only information **sent by the client to the server**; endpoint identification is the check comparing **the certificate returned by the server against the expected name**.

In special cases using an IP or a layered socket, the JSSE provider may decide how to send SNI based on a valid hostname. When custom SNI configuration is needed, the relevant API is `SSLParameters.setServerNames(...)` with `SNIHostName`, but that configuration should not be used to mask certificate/SAN errors. Also remember that **the endpoint check name and SNI have different roles**: do not change the expected identity just to match an invalid certificate.

## 9. Trust store and hostname verification must both be enabled

A common mistake when seeing a self-signed certificate rejected in a development environment is writing:

```java
// INSECURE: trust-all manager with an empty checkServerTrusted.
TrustManager[] trustAll = new TrustManager[] {
    new X509TrustManager() {
        public void checkClientTrusted(X509Certificate[] c, String a) {}
        public void checkServerTrusted(X509Certificate[] c, String a) {}
        public X509Certificate[] getAcceptedIssuers() {
            return new X509Certificate[0];
        }
    }
};
```

*The snippet above is intentionally an **insecure anti-pattern**, is incomplete, and must not be run or used in production.* If you replace the trust manager with an implementation that passes every chain, a forged certificate can be accepted. **Enabling `setEndpointIdentificationAlgorithm("HTTPS")` does not make trust-all safe**, because an attacker can issue their own certificate with a SAN matching the expected name.

The valid approach for internal systems is to **add the approved CA or specific certificate to the trust store**, using `TrustManagerFactory` or the default JVM trust configuration with a managed CA. The local test above uses a client trust store that trusts only one public certificate; production systems typically trust a policy-approved set of CAs, with rotation/revocation processes and expiration limits.

**Bad choices to avoid:**

- Do not use a `TrustManager` with an empty `checkServerTrusted(...)`.
- Do not set the endpoint identification algorithm to `""` or `null` to "fix" hostname errors.
- Do not skip `startHandshake()` and send credentials before the server identity has been verified.
- Do not use `HttpsURLConnection.setDefaultHostnameVerifier((h,s)->true)` to fix HTTPS client errors, and **do not mistake `HttpsURLConnection`'s `HostnameVerifier` for a global setting for all `SSLSocket`s**.
- Do not rely on `SSLSession.getPeerCertificates()` and only check that "a certificate exists" while skipping SAN/hostname checks.
- Do not arbitrarily pin a certificate/leaf key and skip hostname verification; if pinning is required, it must be designed together with identity verification and a key rotation process.

## 10. Common mistakes when using `SSLSocket` directly

| Situation | Why is it dangerous or wrong? | How to handle it |
| --- | --- | --- |
| Calling `factory.createSocket(host, port)` and only `startHandshake()` | You should not assume a direct socket has hostname verification like an HTTPS client | Enable `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` before the handshake |
| Trust store accepts the CA, but the cert belongs to a different hostname | Chain validation does not equate to endpoint identity | Verify SAN against the expected host |
| Connecting to an IP and passing the IP as `expectedHost` while the cert only has a DNS SAN | The logical name and transport IP are different | Use a layered socket with the verified logical DNS hostname |
| Sending the right SNI and assuming that is enough security | SNI is a hint to the server, not a verification step | Enable endpoint identification |
| Calling `getSession()` / doing I/O before configuring `SSLParameters` | The handshake can start before hostname rules are applied | Set `SSLParameters` before any operation that triggers the handshake |
| Certificate hostname mismatch, retrying with verification disabled | Opens the door to MITM | Fail-closed; fix the SAN or target name |
| Certificate not trusted, using trust-all | Loses PKIX trust validation | Configure a valid trust store/CA |
| Checking only `CN` and ignoring SAN | Does not follow modern certificate identification standards | Require an appropriate DNS/IP SAN |
| Using `getInetAddress().getHostAddress()` as the default identity | The connected IP is not necessarily the service name | Keep the logical host from an allowed configuration |
| Using a self-signed localhost certificate in production | Unsuitable for real service lifecycle and trust | Use managed certificates/CAs |
| Logging only "SSL handshake failed" without classification | Hard to distinguish chain errors, hostname mismatches, and TLS versions | Log the cause in a controlled way; do not log secrets |
| Disabling hostname verification in test environments and forgetting to re-enable it | Insecure configuration reaches production | Test both valid-host and wrong-host cases in CI |
| Treating `setSoTimeout(5000)` as a full-transaction deadline | It is only a socket read wait policy | Design overall connect/handshake/deadline/cancellation timeouts |
| Equating an mTLS client certificate with server hostname checking | They are two different directions of authentication | Perform both if the application needs mutual identity |

## 11. Failure outcomes and fail-closed behavior

Common cases:

| Error | Observable symptom | How to respond |
| --- | --- | --- |
| Certificate has a SAN mismatching the hostname | Usually `SSLHandshakeException` with a certificate name mismatch cause | Reject; verify the configured name and SAN |
| Certificate expired / untrusted chain | `SSLHandshakeException` or a certificate exception nested inside | Check the certificate chain, CA, and system clock |
| Incompatible TLS protocol/cipher | `SSLException`/`SSLHandshakeException`, message varies by JDK/provider | Update TLS configuration; do not blindly weaken security |
| TCP connect failure | `ConnectException`, `SocketTimeoutException`, or `IOException` depending on the case | Check host, route, firewall, and timeout |
| Server closes mid-handshake | EOF/`SSLException`/socket I/O exception | Close the socket; do not send application payload |
| TLS handshake succeeds, but app response fails | Application protocol error after the handshake | Handle at the application layer; do not confuse with hostname checking |

**Do not do exact string matching on error messages** across JDK versions, providers, and operating systems. For automated tests, verify that the handshake **is rejected**, classify the exception/cause chain appropriately, and ensure valid connections still succeed.

Distinguish **trust validation**, **endpoint identification**, **TLS handshake**, and **application authorization**: a client verifying the TLS server's name does not mean the server is authorized to perform every business operation; the application still needs user authentication, authorization, and data controls.

## 12. Notes for `SSLEngine` and high-level clients

When implementing TLS over an NIO `SocketChannel` using `SSLEngine`, the same principle applies: create the engine in **client mode** with the appropriate logical peer hostname, obtain `SSLParameters`, and configure endpoint identification before driving handshake steps via `wrap/unwrap`. API example:

```java
// Illustrative snippet, assuming SSLContext ctx,
// expectedHost, and port already exist; wrap/unwrap loop is not implemented.
SSLEngine engine = ctx.createSSLEngine(expectedHost, port);
engine.setUseClientMode(true);
SSLParameters parameters = engine.getSSLParameters();
parameters.setEndpointIdentificationAlgorithm("HTTPS");
engine.setSSLParameters(parameters);
```

*This `SSLEngine` snippet is not a runnable application*: the NIO handshake loop, TLS buffers, delegated tasks, and `NEED_WRAP/NEED_UNWRAP/NEED_TASK` states require a dedicated implementation. When using `SSLEngine` in client mode, do not omit the peer host if you want endpoint identity matching. SNI configuration and trust managers remain separate concerns.

For high-level HTTP clients, prefer APIs with standard HTTPS policies and hostname verification instead of writing your own TLS stack. The focus of this lesson is **direct TLS socket applications**, where the developer must ensure verification parameters are configured.

## 13. Pre-release security verification checklist

You can apply the following checklist to any code that creates an `SSLSocket` directly:

1. **Determine the expected host:** take it from trusted configuration/allowed target URL; do not take it from the server certificate, arbitrary reverse DNS, or attacker-controlled data.
2. **Verify the certificate SAN:** the certificate must have a DNS SAN or IP SAN matching the exact identity the application uses; reissue the certificate if missing.
3. **Verify trust:** the client uses a PKIX trust manager and the right trust store for the environment. No trust-all or always-true hostname verifier.
4. **Configure TLS before the handshake:** `getSSLParameters()` → `setEndpointIdentificationAlgorithm("HTTPS")` → `setSSLParameters(...)` → `startHandshake()`.
5. **Preserve `peerHost` with an existing transport:** use a layered socket with the logical hostname so the hostname is not replaced by an IP.
6. **Fail-closed:** if handshake/hostname validation fails, close the socket, do not send credentials, and do not retry with verification disabled.
7. **Test two mandatory cases:** matching SAN and mismatched SAN with a still-trusted chain. Also test expired/untrusted certificates for trust validation.
8. **Test SNI:** virtual hosting selects the right cert when SNI is right; if the default cert has the wrong name, the client must reject it.
9. **Timeouts and operations:** add TCP connect timeouts, handshake/transaction deadlines, controlled logging, and error monitoring.
10. **Do not confuse mTLS with server verification:** if using a client cert, you still need to validate the server hostname on the client side.

For real-world certificates, revocation checking policies (CRL/OCSP), certificate transparency, rotation lifecycle, pinning, or private CAs depend on the environment and JSSE configuration. **Do not claim that enabling endpoint identification automatically solves all certificate/revocation policies.** It solves one critical layer: whether the peer's certificate matches the expected hostname.

## 14. Self-check exercises

**Exercise 1.** A client trusts public CAs and connects to `billing.example.com`, but the peer presents a valid certificate for `cdn.example.com`. If only chain validation is performed, what can go wrong? Which API should be configured on `SSLSocket` to reject it?

**Exercise 2.** A client connects via a service discovery IP, but the expected identity is `api.example.com`. The certificate has `DNS:api.example.com` and no IP SAN. Which host should be passed to `SSLSocketFactory.createSocket(existingTcp, host, port, true)`?

**Exercise 3.** The server returns a certificate with the right SAN, but signed by an untrusted CA. Can passing endpoint identification alone be considered secure?

**Exercise 4.** If the client has the exact expected host and sends the exact SNI, why must it still perform hostname verification?

**Exercise 5.** A developer calls `ssl.getSession()` first and then `ssl.setSSLParameters(...)`. What is the ordering issue?

**Exercise 6.** In the demo, using the same trust store containing the localhost public certificate, why is `localhost` verified while `wrong.example` is rejected even though both use the same IP?

**Exercise 7.** When a certificate hostname mismatches, a developer proposes installing a trust-all manager and disabling endpoint identification in production. Is this a valid fix?

**Suggested answers:**

1. The client may accept a server with the wrong identity. Use `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` before the handshake along with a trusted trust manager.
2. Pass `"api.example.com"` — the logical hostname used to verify the certificate — instead of the transport IP.
3. No. Both **a trusted chain** and **a matching expected hostname** must be satisfied.
4. SNI only hints to the server which certificate to select. The peer can still return a different cert; the client must verify the identity on the returned cert.
5. `getSession()` can start the handshake; setting endpoint ID afterward is too late. Configure `SSLParameters` before any action that triggers the handshake.
6. The cert has a `localhost` DNS SAN, not `wrong.example`; trust stays the same, and endpoint ID makes the difference.
7. No. That is a dangerous security downgrade. Fix the service name, SAN/certificate, and valid trust configuration while keeping fail-closed behavior.
