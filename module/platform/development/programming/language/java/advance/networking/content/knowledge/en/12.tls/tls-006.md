# Configuring SSLParameters: TLS Versions, Cipher Suites, SNI, and ALPN in Java

When connecting over HTTPS or building a custom protocol over TLS, a Java program needs more than just "enabling SSL". A TLS connection must agree on the **protocol version**, **cipher suite**, and, when applicable, the **target hostname via SNI** and **application protocol via ALPN**. These decisions occur during the **TLS handshake** before application data is protected and exchanged.

`javax.net.ssl.SSLParameters` is the class that groups the options affecting the handshake. It can be applied to `SSLSocket`, `SSLServerSocket`, and `SSLEngine`. This article covers all four main components, the configuration order, how to check runtime support, how to read the actual results after the handshake, common security mistakes, and Java 17+ examples.

Things to remember from the start:

- **Allowed/proposed configuration** ≠ **negotiated result**. `setProtocols(...)` selects the allowed versions, whereas `SSLSession.getProtocol()` tells you the version of the connection that completed the handshake.
- **SNI is not hostname verification**. SNI lets the server know which domain name the client is requesting; you must still have certificate chain verification and server identity matching.
- **ALPN is not the TLS version**. ALPN selects an application protocol such as `h2` or `http/1.1`, independent of version names like `TLSv1.3` or `TLSv1.2`.
- **`SSLParameters` does not open network connections or own a truststore**. It must be attached to the socket/engine before the handshake; `SSLContext`, key/trust managers, and the JDK security policy still determine the security foundation.

## 1. The Big Picture: What Does a TLS Connection Negotiate?

~~~text
       CLIENT (SSLSocket/SSLEngine)              SERVER (SSLSocket/SSLEngine)
                    |                                         |
                    |     ClientHello                         |
                    |   - proposed TLS versions               |
                    |   - proposed cipher suites              |
                    |   - SNI: api.example.test               |
                    |   - ALPN: h2, http/1.1                  |
                    |---------------------------------------->|
                    |                                         |
                    |    ServerHello + rest of handshake      |
                    |   - selected TLS version                |
                    |   - selected cipher suite               |
                    |   - certificate / authentication        |
                    |   - selected ALPN (if any)              |
                    |<----------------------------------------|
                    |                                         |
                    |  TLS handshake complete, verify cert    |
                    |<=======================================>|
                    |  application data protected by TLS      |
~~~

The diagram only describes the logic at a high level, **not the exact message order in every TLS version**. TLS 1.3 uses different handshake extensions/flows than TLS 1.2; specifically, TLS 1.3 determines the version through `supported_versions`, so you should not naively decode the legacy version field in ClientHello and conclude it is TLS 1.2.

| Component | Configuration API | Value observed after handshake | Notes |
| --- | --- | --- | --- |
| **TLS version** | `SSLParameters.setProtocols(String[])` | `SSLSession.getProtocol()` | For example `TLSv1.3` or `TLSv1.2` |
| **Cipher suite** | `SSLParameters.setCipherSuites(String[])` | `SSLSession.getCipherSuite()` | Must match the version, key/certificate, and policy |
| **SNI (Server Name Indication)** | Client: `setServerNames(List<SNIServerName>)` | Not identical to the negotiated hostname | Client hints the virtual host name in ClientHello |
| **ALPN (Application-Layer Protocol Negotiation)** | `setApplicationProtocols(String[])` | `SSLSocket.getApplicationProtocol()` or `SSLEngine.getApplicationProtocol()` | For example `h2` or `http/1.1`, may be unnegotiated |
| **Endpoint identity verification** | `setEndpointIdentificationAlgorithm("HTTPS")` | Handshake succeeds after identity check per policy | Cannot be replaced by SNI |
| **Trust and key material** | `SSLContext`/key-trust managers or application config | Handshake authentication succeeds/fails | Not the responsibility of `SSLParameters` itself |

**Do not confuse "supported" with "enabled".** A JDK may know about many versions/cipher suites while only enabling a safe default set; the `jdk.tls.disabledAlgorithms` security property and provider configuration may forbid weak algorithms. Even when a suite is "supported", the peer might not support it or the certificate/key might be incompatible.

## 2. `SSLParameters` Is a Configuration Object, Not a Connection

`SSLParameters` holds components such as:

~~~java
SSLParameters params = sslSocket.getSSLParameters();

params.setProtocols(new String[] {"TLSv1.3", "TLSv1.2"});
params.setCipherSuites(new String[] {
        "TLS_AES_128_GCM_SHA256",
        "TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256"
});
params.setServerNames(
        java.util.List.of(new SNIHostName("api.example.test")));
params.setApplicationProtocols(
        new String[] {"h2", "http/1.1"});
params.setEndpointIdentificationAlgorithm("HTTPS");

sslSocket.setSSLParameters(params);
~~~

This is an **illustrative snippet** inside a Java method with an `sslSocket` of type `SSLSocket`, `javax.net.ssl.*` imports, and appropriate exception handling. Hardcoding suites/versions as above is **only valid when the runtime allows them**; the full example below checks the enabled set before setting them. The important order is **get current parameters → modify → apply to socket/engine → start handshake**.

### 2.1. Sources of `SSLParameters`

- `new SSLParameters()` creates a new object; the protocol/cipher arrays may be `null` if not yet set.
- `SSLContext.getDefaultSSLParameters()` gets the default parameters from the context.
- `SSLContext.getSupportedSSLParameters()` indicates parameters that can be supported by the context, **not** all of which are always enabled.
- `sslSocket.getSSLParameters()` / `sslEngine.getSSLParameters()` gets the current parameters of the object itself. For `SSLSocket`, the protocol and cipher arrays returned by this method are non-null per the Javadoc.

You should start from `getSSLParameters()` on the object you intend to use in order to **preserve existing settings**, rather than creating `new SSLParameters()` and accidentally forgetting a security setting already applied by a library/provider layer.

### 2.2. Modifying the Object Does Not Mean Modifying the Socket

After:

~~~java
SSLParameters params = socket.getSSLParameters();
params.setApplicationProtocols(new String[] {"h2"});
~~~

`socket` **has not received the configuration yet**. You must call:

~~~java
socket.setSSLParameters(params);
~~~

Call `getSSLParameters()` to **read back the applied configuration**; do not just look at the `params` variable and assume the handshake used them. Once the handshake has started, do not expect late changes to alter the current negotiation. With TLS 1.3, renegotiation mechanisms like in TLS 1.2 cannot be arbitrarily used to modify an already-established session.

### 2.3. What `SSLParameters` Does *Not* Do

- Does not create a TCP connection by itself. `SSLSocket` runs TLS transport over a socket, while `SSLEngine` requires the application to perform network I/O.
- Does not load private keys, certificate chains, or trust anchors by itself. `SSLContext`/`KeyManager`/`TrustManager` are responsible for that.
- Does not guarantee a cipher/version will be negotiated. There must be an **intersection** with the peer and compliance with the active policy.
- Does not change HTTP request contents, nor automatically translate HTTP/1.1 into HTTP/2 just because ALPN selected `h2`.
- Does not verify server identity just because `setServerNames` was called.

## 3. Selecting the TLS Protocol Version

API:

~~~java
params.setProtocols(new String[] {"TLSv1.3", "TLSv1.2"});
~~~

Meaning: the socket/engine is only allowed to use versions in this set, provided the implementation and policy support them. TLS 1.3 and 1.2 are appropriate targets for many modern Java 17+ systems; final requirements must follow your product security policy and target system, and you must **not** assume every JDK vendor or device supports them identically.

Check on the socket itself:

~~~java
System.out.println(
        java.util.Arrays.toString(socket.getSupportedProtocols()));
System.out.println(
        java.util.Arrays.toString(socket.getEnabledProtocols()));
~~~

This is an **illustrative snippet**; actual output depends on the JDK/provider. `getSupportedProtocols()` lists versions the provider can configure; `getEnabledProtocols()` lists the versions currently enabled. You may see `TLSv1` or `TLSv1.1` in the supported set even though they are disabled by security policy; **do not re-enable them** just to connect to a legacy server unless an approved security decision is in place.

### 3.1. Do Not Set Values Unsupported by the Runtime

Java 17+ code example checking the intersection:

~~~java
Set<String> enabled = new HashSet<>(
        Arrays.asList(socket.getEnabledProtocols()));
String[] versions = Stream.of("TLSv1.3", "TLSv1.2")
        .filter(enabled::contains)
        .toArray(String[]::new);
if (versions.length == 0) {
    throw new IllegalStateException("No acceptable TLS version enabled");
}
params.setProtocols(versions);
~~~

This is an **illustrative snippet** inside a method, with imports for `Set`, `HashSet`, `Arrays`, and `Stream`, and a valid socket. It filters against **enabled defaults**, rather than taking every version in supported and enabling them all. Checking the intersection is a necessary technical step; whether to accept a given version is a **security policy** decision.

If the product **only** accepts TLS 1.3, do not silently add TLS 1.2 when a peer rejects TLS 1.3. The configured set must accurately reflect the requirement. Conversely, if policy allows TLS 1.2 and 1.3, the client can offer both for compatibility.

### 3.2. The Actual Selected TLS Version Is Only Known After the Handshake

After `socket.startHandshake()` succeeds:

~~~java
SSLSession session = socket.getSession();
String chosenVersion = session.getProtocol();
System.out.println(chosenVersion);
~~~

This may print `TLSv1.3` or `TLSv1.2`; **there is no single fixed stdout** across all servers. If there is no common version (or algorithms/certificates/trust policy do not match), the handshake can fail with `SSLHandshakeException` or a related exception.

**Do not check "was TLS 1.3 used" with `Arrays.asList(params.getProtocols()).contains("TLSv1.3")`.** That only tells you the version was **allowed/proposed**.

## 4. Selecting Cipher Suites: Names, Versions, and Policy Limits

A **cipher suite** describes the set of cryptographic algorithms used to protect a TLS connection. Naming differs significantly between TLS 1.3 and TLS 1.2:

| Version | Example suite | What to understand |
| --- | --- | --- |
| TLS 1.3 | `TLS_AES_128_GCM_SHA256` | Name describes the AEAD cipher and HKDF hash; key exchange/certificate authentication are negotiated by other mechanisms |
| TLS 1.3 | `TLS_AES_256_GCM_SHA384` | A common TLS 1.3 suite if supported by the provider |
| TLS 1.2 | `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` | Name includes the key exchange/authentication mechanism and record cipher |
| TLS 1.2 | `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256` | Example of an ECDSA certificate/key path; depends on the peer |

**Do not mix lists arbitrarily**: TLS 1.3 suites do not become TLS 1.2 suites; TLS 1.2 suites have requirements on the certificate and key exchange. If you enable TLS 1.2 but only allow TLS 1.3 suites, a TLS 1.2 handshake will not be able to select a matching suite.

### 4.1. Supported, Enabled, Negotiated

- `socket.getSupportedCipherSuites()`: names the implementation knows how to configure.
- `socket.getEnabledCipherSuites()`: the set currently enabled on the object.
- `params.setCipherSuites(...)` + `socket.setSSLParameters(params)`: the configured accepted/offered set, not the negotiated value.
- `socket.getSession().getCipherSuite()` **after the handshake**: the single suite actually used.

A modern whitelist should be based on the application's security policy. The lesson example uses four AES-GCM names for TLS 1.2/1.3 to demonstrate filtering against enabled defaults, but **does not claim those four suites are the entire optimal list**. A product may have different requirements regarding ECDSA/RSA certificates, hardware, FIPS, compliance, or ChaCha20.

Do not "fix" handshake errors by enabling `TLS_RSA_WITH_...`, 3DES, CBC, TLS 1.0/1.1, or suites disabled by policy. If no valid suite exists, report a clear error and change the configuration/certificate according to an approved decision.

### 4.2. Checking a Usable Safe Cipher Set

~~~java
Set<String> enabledSuites = new HashSet<>(
        Arrays.asList(socket.getEnabledCipherSuites()));
String[] chosen = Stream.of(
        "TLS_AES_128_GCM_SHA256",
        "TLS_AES_256_GCM_SHA384",
        "TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256",
        "TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256")
        .filter(enabledSuites::contains)
        .toArray(String[]::new);

if (chosen.length == 0) {
    throw new IllegalStateException("No acceptable enabled TLS suites");
}
params.setCipherSuites(chosen);
~~~

This is an **illustrative snippet**; the logic is similar to the version list. A suite being in enabled **still does not guarantee** that the peer's certificate matches, key exchange works, and all algorithms pass runtime barriers. `jdk.tls.disabledAlgorithms` restrictions, `AlgorithmConstraints`, and the provider's cryptography policy continue to be evaluated during the handshake.

### 4.3. Server-Side Cipher Suite Order Preference

`params.setUseCipherSuitesOrder(true)` requests prioritizing the local suite order when possible; this is most appropriate for a **TLS server** selecting a suite from the common list. The degree of effect also depends on the provider, TLS version, and valid algorithms. Setting it on the client does not mean the client forces the server to pick the first suite.

With TLS 1.3, key exchange/authentication is not expressed directly in the cipher suite name; therefore, do not assess security solely from a single suite string after the handshake. You must also consider the version, certificate chain/hostname, key policy, and trust.

## 5. SNI — Server Name in ClientHello, Not Identity Verification

**Server Name Indication** (SNI, RFC 6066) allows the client to propose the DNS name of the server it wants to reach, especially when one IP:port serves multiple virtual hosts/certificates.

~~~text
Client wants https://api.example.test
    |
    | TLS ClientHello: SNI host_name=api.example.test
    v
Reverse proxy / TLS server receives SNI
    |
    +--> selects matching virtual host/certificate (if configured)
    |
    +--> TLS handshake and client-side certificate verification
~~~

On the Java client side:

~~~java
params.setServerNames(
        List.of(new SNIHostName("api.example.test")));
~~~

`SNIHostName` represents a **DNS hostname**, not a full URL: do not pass `https://api.example.test/path`. Do not use an IP literal as the SNI `host_name` value; when connecting to an IP address, hostname/certificate policy must handle IP SANs separately and may omit sending DNS SNI. `new SNIHostName(...)` validates the name and normalizes IDNs to an ASCII A-label representation when needed.

The Javadoc allows one server name of each SNI type in the list; adding two `SNIHostName` entries of the same type throws `IllegalArgumentException`. You need to import `java.util.List` and `javax.net.ssl.SNIHostName`.

### 5.1. When Do You Need to Set SNI Explicitly?

If you create `SSLSocketFactory.createSocket("api.example.test", 443)` or `SSLContext.createSSLEngine("api.example.test", 443)`, the provider usually has enough hostname information to suggest a default SNI automatically. However, do not assume this always happens across every provider/flow (for example, a socket wrapping an existing IP connection). Set `SSLParameters.setServerNames(...)` explicitly when the application needs DNS-based virtual hosting and predictable behavior.

It is important to use the **same intended hostname** for the connection, SNI, and endpoint verification in the typical case; if they intentionally differ (custom routing/proxy), you must design the corresponding trust and identity policy rather than disabling certificate checks.

### 5.2. SNI Does Not Replace `HTTPS` Endpoint Identification

An attacker can see the SNI the client requested and still present a certificate with the wrong name. **Merely sending SNI** does not prove the remote peer is actually `api.example.test`.

For a **client-side raw `SSLSocket` or `SSLEngine`**, you should enable:

~~~java
params.setEndpointIdentificationAlgorithm("HTTPS");
~~~

At the same time, you must use a **trust manager that genuinely verifies the certificate chain**. The examples use `SSLContext.getDefault()` to inherit the runtime's trust configuration; do not use a "trust-all" `X509TrustManager`, and do not skip hostname verification just to make the handshake succeed. For high-level HTTP clients like `java.net.http.HttpClient` or `HttpsURLConnection`, the framework already has its own default TLS/hostname verification policy; do not override it with a weaker configuration unnecessarily.

SNI can also appear in observable form in a standard TLS ClientHello; do not treat the hostname sent via SNI as an absolute secret. Encrypted ClientHello (ECH) is a separate topic/deployment capability and cannot be assumed just because `SSLParameters` is used.

### 5.3. Server Side: `SNIMatcher` and Certificate Selection

On the TLS server side, `SSLParameters.setSNIMatchers(...)` can set a filter accepting SNI names. This is **different** from the client's `setServerNames(...)`. Having an SNI matcher does not guarantee the application is configured to **select the right certificate per hostname**: the key manager, server TLS provider, certificate store, and application routing must be configured and tested.

For mTLS, `params.setNeedClientAuth(true)` requires **client certificate authentication** on the server; this is not an SNI feature. You must have trust anchors/TrustManager to verify the client certificate and authorization logic after authentication.

## 6. ALPN — Selecting the Application-Layer Protocol During the TLS Handshake

**Application-Layer Protocol Negotiation** (ALPN, RFC 7301) allows both sides to agree on an application protocol alongside the TLS handshake, such as `h2` (HTTP/2) or `http/1.1`. This is **not** TLS version selection and does not replace application-layer HTTP negotiation.

On Java 17:

~~~java
params.setApplicationProtocols(
        new String[] {"h2", "http/1.1"});
~~~

The array values are **protocol identifiers** ordered by preference; `protocols[0]` is typically the highest preference of the configuring side. Common identifiers `h2` and `http/1.1` are ASCII strings defined in the ALPN registry.

- **Client** sends the list of protocols it can speak over TLS.
- **Server** picks a common value according to its mechanism/provider and preference; there is no guarantee the server always picks the first element the client offers.
- If there is **no common protocol**, policy/JSSE may cause a handshake failure with `no_application_protocol` or yield an unnegotiated result, depending on configuration/peer.
- If the provider does not support ALPN, the related APIs may not perform the expected operation; you must read the JDK/provider contract and handle `UnsupportedOperationException` as appropriate.

### 6.1. How to Read the Negotiated Value

After the handshake:

~~~java
String app = sslSocket.getApplicationProtocol();
if ("h2".equals(app)) {
    // Only send/receive proper HTTP/2 framing.
} else if ("http/1.1".equals(app)) {
    // Use HTTP/1.1 framing.
} else if (app != null && app.isEmpty()) {
    // No ALPN was negotiated.
}
~~~

This is an **illustrative snippet**; the application must have a proper implementation—you cannot send HTTP/1.1 bytes over a connection that selected `h2`.

Per the `SSLSocket.getApplicationProtocol()` Javadoc:
- `null`: it has not yet been determined whether ALPN is used (typically before the handshake).
- `""`: no application protocol value was used/agreed upon.
- Non-empty string: the protocol that was negotiated.
- The provider may not implement this and throw `UnsupportedOperationException`.

`getHandshakeApplicationProtocol()` is for observing **while the handshake is in progress**, not a replacement for `getApplicationProtocol()` after the handshake. On the server side, `SSLSocket.setHandshakeApplicationProtocolSelector(...)` / `SSLEngine.setHandshakeApplicationProtocolSelector(...)` can register a callback to select the protocol. This callback **overrides** the default selection list in `SSLParameters.setApplicationProtocols`; do not configure both mechanisms casually and rely on guesswork.

### 6.2. ALPN Does Not Automatically Create an HTTP/2 Client

Suppose you connect to a server and get `getApplicationProtocol()=="h2"`. That only means TLS selected HTTP/2 at the application layer. Someone writing a raw socket still has to:
- Implement the HTTP/2 connection preface, SETTINGS frame, stream IDs, HPACK, flow control, and lifecycle handling according to HTTP/2.
- Not send `GET / HTTP/1.1\r\n...` directly and expect compatibility.
- Or choose an HTTP client library with an HTTP/2 implementation (such as `java.net.http.HttpClient`) instead of handling the protocol manually.

If writing a standard HTTP client, prefer a high-level library that provides hostname verification, ALPN, and compliant HTTP framing; only manipulate raw `SSLParameters` when learning, building a custom protocol, or meeting specific integration constraints.

## 7. Correct Configuration Sequence Before the Handshake

~~~text
Choose SSLContext (key/trust managers, default security policy)
       |
Create SSLSocket/SSLEngine before handshake
       |
getSupported... / getEnabled... / validate policy
       |
SSLParameters p = getSSLParameters()
       |
setProtocols + setCipherSuites
       |
setServerNames (client SNI) + setApplicationProtocols (ALPN)
       |
setEndpointIdentificationAlgorithm("HTTPS") for TLS client
       |
setSSLParameters(p)  <<< actually apply to socket/engine
       |
TCP connect / begin TLS handshake
       |
Handshaking + trust + hostname verification
       |
SSLSession.getProtocol(), getCipherSuite()
SSLSocket.getApplicationProtocol()
       |
Communicate using the selected application protocol
~~~

`setSSLParameters` must be executed **before the handshake starts**. With `SSLSocket`, the handshake can be triggered by `startHandshake()`, reading/writing application data, or certain session calls; **do not wait until the handshake is already running to configure it**.

With `SSLEngine`, after `beginHandshake`, the application must drive `wrap`, `unwrap`, `NEED_TASK`, `NEED_WRAP`, `NEED_UNWRAP`, and send/receive TLS records over its own transport. There is no `SSLEngine.connect()` like on a TCP socket. An example client engine before the handshake:

~~~java
// Illustrative, not standalone-runnable: assumes SSLContext context already exists.
SSLEngine engine = context.createSSLEngine("api.example.test", 443);
engine.setUseClientMode(true);

SSLParameters p = engine.getSSLParameters();
p.setEndpointIdentificationAlgorithm("HTTPS");
p.setServerNames(List.of(new SNIHostName("api.example.test")));
p.setApplicationProtocols(new String[] {"h2", "http/1.1"});
engine.setSSLParameters(p);
// Next: set up transport, beginHandshake(), wrap/unwrap + delegated tasks.
~~~

Similarly, `SSLServerSocket` has `setSSLParameters(...)`, so the server can set versions, suites, ALPN, and mTLS policy before `accept`. An `SSLServerSocket` needs an appropriate certificate/private key in `SSLContext`; configuring `SSLParameters` alone does not provide a server identity.

## 8. Java 17+ Program #1: Previewing TLS Configuration Without Connecting to the Network

Goal: get the **currently enabled** ciphers/versions, filter against a modern whitelist, configure SNI/ALPN/endpoint verification, and read them back via `getSSLParameters()`. No DNS query, TCP connect, or TLS handshake occurs. This example helps distinguish **configuration** from **negotiated results**.

Create the file **`TlsParametersPreview.java`**:

~~~java
import javax.net.ssl.*;
import java.util.*;

public final class TlsParametersPreview {
    private static String[] enabledOnly(
            String[] wanted, String[] enabled) {
        Set<String> available =
                new HashSet<>(Arrays.asList(enabled));
        return Arrays.stream(wanted)
                .filter(available::contains)
                .toArray(String[]::new);
    }

    public static void main(String[] args) throws Exception {
        try (SSLSocket socket = (SSLSocket)
                SSLContext.getDefault().getSocketFactory()
                        .createSocket()) {

            String[] versions = enabledOnly(
                    new String[] {"TLSv1.3", "TLSv1.2"},
                    socket.getEnabledProtocols());

            String[] suites = enabledOnly(
                    new String[] {
                        "TLS_AES_128_GCM_SHA256",
                        "TLS_AES_256_GCM_SHA384",
                        "TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256",
                        "TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256"
                    },
                    socket.getEnabledCipherSuites());

            if (versions.length == 0 || suites.length == 0) {
                throw new IllegalStateException(
                        "No acceptable enabled TLS settings");
            }

            SSLParameters params = socket.getSSLParameters();
            params.setProtocols(versions);
            params.setCipherSuites(suites);
            params.setServerNames(
                    List.of(new SNIHostName("api.example.test")));
            params.setApplicationProtocols(
                    new String[] {"h2", "http/1.1"});
            params.setEndpointIdentificationAlgorithm("HTTPS");
            socket.setSSLParameters(params);

            SSLParameters actual = socket.getSSLParameters();
            System.out.println("versions: " +
                    Arrays.toString(actual.getProtocols()));
            System.out.println("cipher count: " +
                    actual.getCipherSuites().length);
            System.out.println("SNI: " +
                    ((SNIHostName) actual.getServerNames().get(0))
                            .getAsciiName());
            System.out.println("ALPN offered: " +
                    Arrays.toString(actual.getApplicationProtocols()));
            System.out.println("endpoint identification: " +
                    actual.getEndpointIdentificationAlgorithm());
            System.out.println("connected: " + socket.isConnected());
        }
    }
}
~~~

Run commands:

~~~bash
javac --release 17 TlsParametersPreview.java
java TlsParametersPreview
~~~

On a JDK where the example options are enabled, **one observed output** is:

~~~text
versions: [TLSv1.3, TLSv1.2]
cipher count: 4
SNI: api.example.test
ALPN offered: [h2, http/1.1]
endpoint identification: HTTPS
connected: false
~~~

The `versions` and `cipher count` lines **depend on the runtime/policy**; if the runtime disables an option, the list or count will differ. If no version/suite from the whitelist remains enabled, the program intentionally fails fast. The remaining lines reflect the applied configuration. `connected: false` proves that `setSSLParameters` and `getSSLParameters` do not create a TCP connection or perform a TLS handshake.

Technically, this is a **configuration readback**, not proof that a peer supports them, what cipher would actually be selected, or that a certificate is valid. The program never calls `getSession().getProtocol()` because no session has been negotiated yet.

## 9. Java 17+ Program #2: Probing a Real Handshake with SNI and ALPN

This example takes a **DNS hostname** and port from the command line. It opens a TCP connection with a connect timeout, wraps it in an `SSLSocket` with the logical peer hostname attached, sets `SSLParameters` **before the handshake**, enables hostname verification, and uses the default trust manager. Only after `startHandshake()` succeeds does it read the **TLS version, cipher suite, and negotiated ALPN**.

Do not use random hosts or systems you are not authorized to access; only connect to endpoints you have permission to test. The program does not send an HTTP request or download application content; it only performs the handshake.

Create the file **`TlsHandshakeProbe.java`**:

~~~java
import javax.net.ssl.*;
import java.net.*;
import java.util.*;

public final class TlsHandshakeProbe {
    private static String[] enabledOnly(
            String[] wanted, String[] enabled) {
        Set<String> available =
                new HashSet<>(Arrays.asList(enabled));
        return Arrays.stream(wanted)
                .filter(available::contains)
                .toArray(String[]::new);
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            System.out.println(
                    "Usage: java TlsHandshakeProbe <dns-host> <port>");
            return;
        }

        String host = args[0];          // DNS hostname, not an IP literal
        int port = Integer.parseInt(args[1]);

        SSLSocketFactory factory =
                SSLContext.getDefault().getSocketFactory();

        try (Socket tcp = new Socket()) {
            tcp.connect(new InetSocketAddress(host, port), 5000);

            try (SSLSocket tls = (SSLSocket)
                    factory.createSocket(tcp, host, port, true)) {

                String[] versions = enabledOnly(
                        new String[] {"TLSv1.3", "TLSv1.2"},
                        tls.getEnabledProtocols());

                String[] suites = enabledOnly(
                        new String[] {
                            "TLS_AES_128_GCM_SHA256",
                            "TLS_AES_256_GCM_SHA384",
                            "TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256",
                            "TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256"
                        },
                        tls.getEnabledCipherSuites());

                if (versions.length == 0 || suites.length == 0) {
                    throw new IllegalStateException(
                            "No acceptable enabled TLS settings");
                }

                SSLParameters params = tls.getSSLParameters();
                params.setProtocols(versions);
                params.setCipherSuites(suites);
                params.setServerNames(
                        List.of(new SNIHostName(host)));
                params.setApplicationProtocols(
                        new String[] {"h2", "http/1.1"});
                params.setEndpointIdentificationAlgorithm("HTTPS");
                tls.setSSLParameters(params);

                tls.setSoTimeout(5000);
                tls.startHandshake();

                SSLSession session = tls.getSession();
                System.out.println(
                        "TLS version: " + session.getProtocol());
                System.out.println(
                        "cipher suite: " + session.getCipherSuite());

                String app = tls.getApplicationProtocol();
                System.out.println("ALPN: " +
                        (app == null ? "undetermined"
                                : app.isEmpty() ? "none" : app));
            }
        }
    }
}
~~~

Run with insufficient arguments to check the usage branch, **fixed stdout**:

~~~bash
javac --release 17 TlsHandshakeProbe.java
java TlsHandshakeProbe
~~~

~~~text
Usage: java TlsHandshakeProbe <dns-host> <port>
~~~

When testing an authorized TLS endpoint, for example:

~~~bash
java TlsHandshakeProbe www.example.com 443
~~~

**There is no fixed negotiated stdout**. You might see something like:

~~~text
TLS version: TLSv1.3
cipher suite: TLS_AES_128_GCM_SHA256
ALPN: h2
~~~

However, this is an **illustrative example of one possible outcome**, not a guarantee that the server will pick TLS 1.3, that cipher, or ALPN `h2`. If the environment lacks DNS/network, the truststore does not trust the chain, the hostname does not match the certificate, the peer has no common cipher, SNI is invalid, or a timeout expires, the program may throw an exception before printing those lines.

Additional notes:
- `tcp.connect(..., 5000)` bounds the TCP connection setup time; `tls.setSoTimeout(5000)` is a read timeout, **not** an absolute total 5-second deadline for all TLS handshake steps.
- `factory.createSocket(tcp, host, port, true)` preserves the logical hostname for TLS and endpoint identification. Do not use a socket to an IP and omit the hostname assuming SNI was already sent.
- The suite and version arrays are only filtered by enabled defaults, which does not guarantee both sides match. Handshake errors should be diagnosed based on server policy/certificate, not "quick-fixed" with trust-all.
- Because `h2` may be negotiated, **do not write raw HTTP/1.1 bytes** after the handshake. To make an HTTP request, use an appropriate protocol library.

## 10. How Does Server Configuration Differ from Client Configuration?

### 10.1. The Server Needs Key Material/Certificates

A TLS server must have an appropriate private key and certificate chain, usually configured via `SSLContext` with a `KeyManager`. A conceptual example:

~~~java
// Illustrative, not standalone-runnable: context must be initialized with
// appropriate key material/certificate and trust policy.
SSLServerSocketFactory factory =
        context.getServerSocketFactory();
try (SSLServerSocket listener = (SSLServerSocket)
        factory.createServerSocket(9443)) {

    SSLParameters p = listener.getSSLParameters();
    p.setProtocols(new String[] {"TLSv1.3", "TLSv1.2"});
    p.setApplicationProtocols(
            new String[] {"h2", "http/1.1"});
    p.setUseCipherSuitesOrder(true);
    listener.setSSLParameters(p);

    try (SSLSocket peer = (SSLSocket) listener.accept()) {
        peer.startHandshake();
        System.out.println(peer.getApplicationProtocol());
    }
}
~~~

This is an **illustrative snippet** assuming an initialized `context`, a test port, and `javax.net.ssl.*` imports; it still lacks certificate setup, an accept loop, shutdown, and error handling to be a real server. Do not use `SSLContext.getDefault()` and assume the server has a suitable certificate: the default context usually does not contain a pre-provisioned application server private key.

### 10.2. Client `setServerNames`, Server `setSNIMatchers`

| Side | Common configuration | Purpose |
| --- | --- | --- |
| Client | `setServerNames(List.of(new SNIHostName(host)))` | Tells the server which DNS name needs to be served |
| Client | `setEndpointIdentificationAlgorithm("HTTPS")` | Verifies the hostname against the certificate via an appropriate trust manager |
| Server | `setSNIMatchers(...)` | Inspects/accepts client-side SNI names if designed to do so |
| Server | `setUseCipherSuitesOrder(true)` | Requests local suite order preference during negotiation, provider-dependent |
| Server | `setNeedClientAuth(true)` | mTLS: requires client cert and trust validation |
| Both | `setApplicationProtocols(...)` | ALPN offer/selection of application protocol |

When a server application serves multiple hostnames, "reading SNI" or setting an `SNIMatcher` still does not automatically pick the right certificate. A multi-domain server must integrate an appropriate key/certificate selector in `X509ExtendedKeyManager`/the TLS provider or a properly configured reverse proxy layer.

### 10.3. Server-Side ALPN Pitfalls

With `setApplicationProtocols(new String[] {"h2", "http/1.1"})`, the server must actually support both HTTP/2 and HTTP/1.1 framing. Do not offer `h2` if you only have HTTP/1.1 code. `SSLParameters` selects the protocol string during the handshake; the application layer must dispatch the connection based on `getApplicationProtocol()`.

If using `setHandshakeApplicationProtocolSelector`, the callback must pick a protocol advertised by the peer and implemented by the server; returning an invalid choice can cause the handshake to fail. Complex callbacks should be tested with various ALPN sets rather than blindly prioritizing the client's first entry.

## 11. `SSLParameters` with `SSLEngine` and Non-Blocking Event Loops

In NIO `Selector` applications, `SSLSocket` is a blocking socket abstraction. When TLS is needed over a non-blocking `SocketChannel`, the typical model is:

~~~text
SocketChannel (network bytes)
       │
       ▼
SSLEngine.unwrap()  -> plaintext / handshake status
       │
       └── application data
       │
application produces plaintext -> SSLEngine.wrap()
                               │
                               ▼
                         encrypted net bytes
                               │
                               ▼
                        SocketChannel.write()
~~~

`SSLEngine` takes `SSLParameters` similarly, but the application must provide the transport and handle handshake tasks/readiness; do **not** just call `setSSLParameters` and assume the socket is using TLS.

Distinguish TLS backpressure from TCP backpressure: `SSLEngine.wrap()` can produce ciphertext longer than the plaintext, emit handshake/control records, and require retaining buffers to flush completely when `SocketChannel.write` returns `0` or a partial write. Adjust `SSLParameters` before `beginHandshake()`; changing certain settings mid-handshake does not immediately apply to the current handshake per the contract.

If a reliable modern TLS/HTTP stack is already available (server/framework/HTTP client), you should usually configure it through that stack's official API rather than implementing an `SSLEngine` state machine yourself.

## 12. Diagnosing Errors at the Right Layer

| Symptom | Possible cause | How to check |
| --- | --- | --- |
| `IllegalArgumentException` in `setSSLParameters` | Version/cipher unsupported by runtime, invalid SNI, malformed ALPN name | Print supported/enabled arrays, validate hostname and policy |
| `SSLHandshakeException: protocol_version` or `handshake_failure` | No common TLS version/cipher, or rejected by provider/server policy | Compare enabled versions/suites on both sides and check valid handshake logs |
| `SSLHandshakeException: No subject alternative DNS name...` | Hostname verification failed | Check actual DNS name, certificate SANs, SNI, and truststore; do not disable verification |
| `PKIX path building failed` | Untrusted cert chain/missing issuer or mismatched trust anchors | Verify chain, truststore, cert expiration, and CA configuration |
| Same IP but wrong virtual host certificate | Missing/wrong SNI, wrong server key selection | Set matching DNS SNI, check virtual host/cert mapping |
| Empty ALPN after handshake | Peer does not support/did not negotiate, or no common protocol per policy | Print `getApplicationProtocols()` before, `getApplicationProtocol()` after |
| ALPN is `h2` but HTTP requests fail | Application still speaks HTTP/1.1 | Choose parser/framing matching the negotiated ALPN |
| Works on one machine, fails on another | Different JDK build, `jdk.tls.disabledAlgorithms`, provider, truststore, or OS/security policy | Log Java runtime/vendor, enabled settings, and controlled certificate/trust info |
| TLS 1.3 fails but TLS 1.2 works | Peer does not support TLS 1.3 or incompatible suite/extension/policy | Test matching policy/version/suite; do not downgrade if policy forbids it |
| Handshake hangs/times out | DNS/TCP/firewall, peer unresponsive, insufficient read timeout and deadline | Distinguish connect timeout, read timeout, and total handshake duration |

**Do not disable certificate verification or use a trust-all manager to "fix" PKIX/SAN errors**. That removes peer identity authentication and can open the door to man-in-the-middle attacks. Instead, fix the chain, CA/truststore, DNS name, certificate configuration, or route properly.

### 12.1. Controlled TLS Debugging

A test JVM can enable:

~~~bash
java -Djavax.net.debug=ssl,handshake TlsHandshakeProbe www.example.com 443
~~~

`javax.net.debug` can output detailed information about the handshake, certificates/extensions, algorithm constraints, and errors; **do not enable this verbose logging permanently in production** and protect logs from sensitive information. Do not log private keys or session secret contents for diagnosis.

Use `java -version` and `System.getProperty("java.vendor")` when recording differences, adding security properties and TLS providers when authorized and compliant with policy. The same Java 17 source code does not mean every runtime will have the exact same enabled ciphers.

## 13. Self-Check Exercises

**Q1.** Does `params.setProtocols(new String[] {"TLSv1.3", "TLSv1.2"})` prove the handshake uses TLS 1.3?  
**Answer:** No. It only sets the allowed set; check `SSLSession.getProtocol()` after a successful handshake.

**Q2.** Does `getSupportedCipherSuites()` mean the same thing as `getEnabledCipherSuites()`?  
**Answer:** No. Supported includes suites the provider can offer, while enabled is the currently active set; policy may disable weak algorithms.

**Q3.** The client sets SNI `api.example.test`, but the server certificate only has SAN `other.example.test`. Should the client accept it?  
**Answer:** No. SNI is only a virtual host hint; HTTPS endpoint identification and trust policy must verify the exact hostname.

**Q4.** When using the IP literal `203.0.113.10` to connect, should you use `new SNIHostName("203.0.113.10")`?  
**Answer:** You should not send an IP literal as the SNI `host_name`. Use an appropriate DNS hostname if available, or design separate IP SAN verification/trust policy.

**Q5.** ALPN returns `h2`; does the socket automatically know how to send HTTP/2 frames?  
**Answer:** No. A raw `SSLSocket` only encrypts TLS; the application must implement the `h2` protocol properly or use an HTTP client/server library.

**Q6.** What does `getApplicationProtocol()` returning `""` after the handshake mean?  
**Answer:** No application protocol value was negotiated; handle it according to policy rather than assuming it means `http/1.1` in every protocol.

**Q7.** If you set `SSLParameters` and then only modify the object afterward, does the socket update automatically?  
**Answer:** No. You need `socket.setSSLParameters(params)` to apply the configuration before the handshake.

**Q8.** A server wants to prioritize its own cipher order; which API should it use?  
**Answer:** `params.setUseCipherSuitesOrder(true)` on the server side, though the result still depends on the provider, common ciphers, and TLS version.

**Q9.** Why can a handshake fail even when both sides support TLS 1.3?  
**Answer:** It also depends on common suites, signature algorithms, certificate/key, truststore, hostname, algorithm constraints, ALPN/extensions, and server policy.

**Q10.** Does setting `setNeedClientAuth(true)` on the server replace `setSNIMatchers`?  
**Answer:** No. mTLS authenticates the client; SNI is an indication of the DNS hostname the client wants the server to serve.

**Q11.** With `SSLEngine`, does calling `setSSLParameters(...)` set up a complete TLS transport?  
**Answer:** Not yet. You must perform the handshake `wrap/unwrap`, delegated tasks, and application network I/O.

**Q12.** When TLS 1.3 only is required, should you automatically fall back to TLS 1.2 to reduce handshake errors?  
**Answer:** No, if policy mandates TLS 1.3. Fail with clear diagnostics; only relax the policy after a security decision.

## 14. Checklist Before Putting TLS Configuration into Production

1. Use `SSLContext` with **proper key/trust managers**, never trust-all.
2. Choose TLS versions/cipher suites per approved policy; check **enabled**, not just supported.
3. Obtain `SSLParameters` from the target socket/engine, modify them, and **re-apply with `setSSLParameters` before the handshake**.
4. A TLS client with a DNS hostname must use appropriate SNI and **HTTPS endpoint verification**, without confusing the two functions.
5. Enable ALPN only for application protocols that are actually implemented.
6. The server must have an appropriate certificate/key; if serving multiple domains, configure key selection by SNI rather than relying solely on a matcher.
7. After the handshake, log the **negotiated** TLS version, cipher suite, and ALPN rather than inferring from the configuration arrays.
8. Clearly separate connect timeout, read timeout, handshake deadline, and retry policy.
9. Test the server/client with the actual JDKs/providers, OSes, truststores, and hostnames/certificates your product supports.
10. Do not disable identity verification algorithms, and do not re-enable weak protocols/ciphers to bypass handshake failures.
11. With `SSLEngine` in NIO, thoroughly verify `wrap/unwrap`/handshake tasks and ciphertext buffers; do not equate parameter setup with TLS transport.
12. If you only need HTTP(S), consider a maintained `HttpClient`/framework instead of writing raw TLS framing/ALPN.
