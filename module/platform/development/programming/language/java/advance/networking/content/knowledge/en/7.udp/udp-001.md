# DatagramSocket and DatagramPacket in Connectionless Communication (UDP)

With TCP, both endpoints must establish a connection and then transmit a byte stream. With **UDP (User Datagram Protocol)**, a program can send each independent message as a **datagram** to a destination IP address and port. Java provides two fundamental classes in `java.net` to do this:

- **`DatagramSocket`**: the process's UDP endpoint. The socket is bound to a local IP address/port, using `send(...)` to send and `receive(...)` to receive.
- **`DatagramPacket`**: a data packet containing a byte buffer, offset, length, and sender or receiver IP/port information.

This lesson explains the **connectionless** model, socket lifecycle, how to pack and read bytes, the blocking behavior of `receive`, timeouts, capacity limits, and two **standalone runnable Java 17+ examples** on `127.0.0.1`. The examples run on the same machine, perform no DNS queries, and do not depend on Internet services.

## 1. What does “connectionless” actually mean?

UDP sends **datagrams** over an IP network without a three-way handshake like TCP. Before sending, the sender only needs to know the **destination address and destination UDP port**, then hands the data to the operating system through the socket. The receiver binds a local address/port to read datagrams arriving there.

~~~text
Machine A / UDP client                       Machine B / UDP service
┌──────────────────────┐                     ┌──────────────────────┐
│ DatagramSocket       │                     │ DatagramSocket       │
│ source port: 54321   │                     │ bind UDP port: 9000  │
│ send(packet)         │ ── datagram #1 ──>  │ receive(packet)      │
│                      │ ── datagram #2 ──>  │ receive(packet)      │
│ receive(reply)       │ <─ datagram reply ─ │ send(reply)          │
└──────────────────────┘                     └──────────────────────┘
    Source IP:port                             Destination IP:port
~~~

Core characteristics:

1. **No handshake at the UDP layer.** A successful `send` call only indicates that Java/the operating system accepted the send operation within the API's scope; it does **not** prove that the receiver processed the packet.
2. **Preserves message boundaries.** One send produces one datagram; each `receive` returns **one** datagram (or the portion of data received if the buffer is too small). Unlike a TCP byte stream, the program does not merge all datagrams into an unbounded stream of bytes.
3. **No delivery guarantee.** Datagrams can be lost, arrive out of order, be duplicated, or be dropped in transit. UDP itself does not acknowledge, retransmit, or guarantee ordering.
4. **No TCP-like flow control/congestion control.** When rate limiting is needed, the application must design an appropriate mechanism or use a protocol/library that already solves the problem.
5. **One socket can send to multiple destinations.** Without calling `DatagramSocket.connect(...)`, each sent `DatagramPacket` can specify a different destination; datagrams can be received from different sources if the network/operating system allows it.

“Connectionless” **does not mean** the data is encrypted, error-free, or portless. UDP still uses the IP address/port pair to route to the application. UDP also has a checksum mechanism to detect transmission errors, but it does not replace application-layer authenticity/integrity checks.

## 2. DatagramSocket and DatagramPacket have different roles

| Component | Holds / performs | API examples |
| --- | --- | --- |
| `DatagramSocket` | UDP socket, local address/port binding, sending/receiving packets, socket options | `new DatagramSocket(0)`, `send(p)`, `receive(p)`, `setSoTimeout(ms)`, `close()` |
| `DatagramPacket` | Byte buffer and metadata of **one** datagram | `new DatagramPacket(bytes, bytes.length, host, port)`, `getData()`, `getLength()` |
| `InetAddress` | An IPv4/IPv6 IP address | `InetAddress.getByName("127.0.0.1")` |
| `InetSocketAddress` | IP address/hostname + port, used when binding or describing an endpoint | `new InetSocketAddress(ip, 0)` |
| `StandardCharsets.UTF_8` | Rules for converting text to bytes and vice versa | `text.getBytes(UTF_8)`, `new String(bytes, offset, len, UTF_8)` |

**A packet used for sending** needs data, length, and destination, for example:

~~~java
byte[] bytes = "ping".getBytes(StandardCharsets.UTF_8);
DatagramPacket outgoing =
        new DatagramPacket(bytes, bytes.length, destinationIp, 9000);
socket.send(outgoing);
~~~

This is a **snippet**: it assumes `socket`, `destinationIp`, and imports for `java.net.*` and `java.nio.charset.StandardCharsets` are already present. On an “unconnected” UDP socket, if the destination is missing when sending, it will not know where to send the datagram.

**A packet used for receiving** needs a sufficiently large buffer:

~~~java
byte[] receiveBuffer = new byte[1024];
DatagramPacket incoming =
        new DatagramPacket(receiveBuffer, receiveBuffer.length);
socket.receive(incoming);
~~~

After `receive` returns:
- `incoming.getAddress()` and `incoming.getPort()` are the **source** that sent the received datagram.
- `incoming.getLength()` is the **actual number of bytes received** in the buffer, which may be smaller than `receiveBuffer.length`.
- `incoming.getOffset()` is the starting position of the data in the buffer.
- `incoming.getData()` returns **the byte array used as the buffer**, not always a new array sized to the received length.

Therefore, to decode text accurately, use **offset + length** instead of the entire buffer.

## 3. Port binding, ephemeral ports, and the loopback address

A UDP socket is bound to a local endpoint so the operating system knows which application should receive datagrams sent to a given port.

Common ways to instantiate it:

~~~java
// The operating system chooses an available local UDP port.
DatagramSocket client = new DatagramSocket();

// Bind a fixed UDP port on appropriate local addresses.
// May fail if the port is already in use or due to insufficient permissions.
DatagramSocket server = new DatagramSocket(9000);

// Bind the IPv4 loopback address, requesting an ephemeral port.
InetAddress loopback = InetAddress.getByName("127.0.0.1");
DatagramSocket localOnly =
        new DatagramSocket(new InetSocketAddress(loopback, 0));
~~~

The snippets above are conceptually standalone but lack class/method declarations, imports, or lifecycle management. In real code, use `try-with-resources` because `DatagramSocket` implements `AutoCloseable` and `close()` releases the socket.

Meaning of ports and addresses:

- **Port 0 when binding**: asks the operating system to allocate an ephemeral UDP port. After creating the socket, call `getLocalPort()` to find out **the actual allocated port**; do not send datagrams to “port 0” as if it were an application service.
- **Fixed port**: services typically choose a configured port so clients know where to send. The port may already be used by another process, throwing `BindException` / `SocketException`.
- **`127.0.0.1`**: IPv4 loopback, communicating only within the same machine; useful for exercises because it avoids external firewall/router dependencies.
- **`0.0.0.0` when binding**: the IPv4 wildcard address typically means listening on appropriate IPv4 interfaces. It is not a destination address that a remote client should use to reach the service.
- **Source port** bound by the client is used by the server to send the reply datagram. The server does **not** automatically know the reply port without reading `incoming.getPort()`.

In IPv6 environments, the corresponding IPv6 address can be used, and both endpoints must agree on the address family/capabilities. The runnable examples below intentionally use IPv4 `127.0.0.1` for consistent output.

## 4. Lifecycle of sending and receiving a datagram

Assume the receiving socket is already bound to the **destination** UDP port; the sequence is:

1. The client converts the string to a byte array using UTF-8.
2. The client creates a `DatagramPacket` containing the bytes, byte count, and destination address/port, and calls `client.send(packet)`.
3. The operating system and network transport the datagram on a best-effort basis; there is no automatic UDP acknowledgment.
4. The server has prepared a buffer and calls `server.receive(incoming)`. By default, this is a **blocking** operation: it waits for a datagram or an error.
5. Upon receiving, the server reads exactly `getOffset()` and `getLength()`, and extracts the sender's IP/port from `incoming`.
6. If a reply is needed, the server creates a **new datagram** sent to this source IP/port.
7. The client reads the reply on its own UDP socket, and should usually set a timeout to avoid waiting indefinitely.

~~~text
client.send("ping")           server.receive()
      │                             │
      ├──── UDP datagram ──────────>│
      │                             ├─ decode (offset, length)
      │                             ├─ getAddress(), getPort()
client.receive()              server.send("pong")
      │<──── UDP datagram ──────────┤
      └─ decode reply               │
~~~

The diagram only describes the exchange **when datagrams arrive**. On a real network, one or both messages can be lost. Therefore, interactive programs usually add **timeouts, retries, request IDs, and reply source verification** at the application layer.

## 5. Java 17+ example: send “ping”, receive, and reply “pong”

The example runs in **a single process** so there is no need to synchronize two terminals. Two `DatagramSocket` instances have two different ephemeral ports, both bound on loopback. The client sends to the server's port; the server reads the packet and replies to the exact source address/port. Because it runs sequentially on loopback, the program does not need threads.

Create the file **`UdpRoundTrip.java`**:

~~~java
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class UdpRoundTrip {
    public static void main(String[] args) throws Exception {
        InetAddress loopback = InetAddress.getByName("127.0.0.1");

        try (DatagramSocket server =
                     new DatagramSocket(new InetSocketAddress(loopback, 0));
             DatagramSocket client =
                     new DatagramSocket(new InetSocketAddress(loopback, 0))) {

            // Prevent blocking indefinitely on network/OS issues.
            server.setSoTimeout(2000);
            client.setSoTimeout(2000);

            byte[] request = "ping".getBytes(StandardCharsets.UTF_8);
            DatagramPacket outgoing = new DatagramPacket(
                    request, request.length, loopback, server.getLocalPort());
            client.send(outgoing);

            byte[] serverBuffer = new byte[1024];
            DatagramPacket incoming =
                    new DatagramPacket(serverBuffer, serverBuffer.length);
            server.receive(incoming);

            String received = new String(
                    incoming.getData(),
                    incoming.getOffset(),
                    incoming.getLength(),
                    StandardCharsets.UTF_8);
            System.out.println("Server received: " + received);

            // Reply to the source address and port read from the packet.
            byte[] reply = "pong".getBytes(StandardCharsets.UTF_8);
            DatagramPacket response = new DatagramPacket(
                    reply, reply.length,
                    incoming.getAddress(), incoming.getPort());
            server.send(response);

            byte[] clientBuffer = new byte[1024];
            DatagramPacket answer =
                    new DatagramPacket(clientBuffer, clientBuffer.length);
            client.receive(answer);

            String answerText = new String(
                    answer.getData(),
                    answer.getOffset(),
                    answer.getLength(),
                    StandardCharsets.UTF_8);
            System.out.println("Client received: " + answerText);
            System.out.println("Receive length: " + answer.getLength());
            System.out.println("Client connected: " + client.isConnected());
        }
    }
}
~~~

Compile and run from the directory containing the file:

~~~bash
javac -encoding UTF-8 UdpRoundTrip.java
java UdpRoundTrip
~~~

**Expected output in a normally functioning loopback environment:**

~~~text
Server received: ping
Client received: pong
Receive length: 4
Client connected: false
~~~

Analysis:

- Both sockets bind `127.0.0.1` but have **separate local ports** because port 0 is used. There is no need to preselect ports 9000/9001.
- `client.send(outgoing)` specifies the destination using `loopback` + `server.getLocalPort()`.
- `server.receive(incoming)` populates the bytes, length, and source information into the server packet. `incoming.getAddress()` and `incoming.getPort()` are where the server sends the reply.
- The `pong` response has four UTF-8 bytes, so `getLength()` returns 4.
- `client.isConnected()` is `false`: the program never called `DatagramSocket.connect(...)`. Nevertheless, the client **can still send and receive** UDP datagrams.
- `setSoTimeout(2000)` sets the `receive` wait limit in milliseconds; when exceeded, it can throw `SocketTimeoutException`. The output above is not a promise that UDP always delivers; if the loopback environment drops packets, the program may time out.
- The `try-with-resources` block automatically closes both sockets even if an exception occurs; running it again will allocate new ports.

Sending/receiving across the two sockets is done sequentially: client send → server receive → server send → client receive. Because datagrams can be queued by the operating system for receiving, `receive` does not need to be called concurrently. This is a local demo; a real server application must loop on receive and have a concurrency handling policy.

## 6. Data is bytes: do not confuse packet length with string length

UDP carries **bytes**, not `String` directly, Java objects, or self-describing charset strings.

~~~java
String message = "Xin chào";
byte[] payload = message.getBytes(StandardCharsets.UTF_8);
DatagramPacket packet = new DatagramPacket(
        payload, payload.length, destinationIp, destinationPort);
~~~

This is a snippet; `destinationIp` and `destinationPort` are determined by the application. Do not use `message.length()` for the packet length: `String.length()` counts UTF-16 code units, whereas the UDP payload length must be the **actual number of bytes** after encoding. Vietnamese characters and other Unicode characters can use multiple UTF-8 bytes.

To decode a received packet, use:

~~~java
String text = new String(
        packet.getData(),
        packet.getOffset(),
        packet.getLength(),
        StandardCharsets.UTF_8);
~~~

Do not write `new String(packet.getData(), UTF_8)` if the buffer is larger than the received data: you may include zero bytes or stale data from the remainder into the string. If the API requires a binary payload (images, protocol data), **do not force every byte into UTF-8**; process it according to the protocol format.

### Offset and length

A `DatagramPacket` can reference **a slice** of a byte array:

~~~java
byte[] frame = {99, 99, 72, 105, 99};
DatagramPacket payloadPart = new DatagramPacket(
        frame, 2, 2, destinationIp, destinationPort);
// Only send bytes at offset 2, length 2: 72, 105 = "Hi" (ASCII).
~~~

This is a snippet to illustrate the constructor with offset; it is not a complete program. The exact data region of the packet is:

~~~text
byte[]:    [99, 99, 72, 105, 99]
index:       0   1   2    3    4
                     |----|
offset = 2, length = 2
~~~

In real code, validate `offset ≥ 0`, `length ≥ 0`, and `offset + length ≤ buffer.length`; the constructor will reject invalid values.

**Note on buffer ownership:** `DatagramPacket` holds a reference to the byte array. Avoid mutating the shared byte array from another thread while sending/receiving; if you need to keep an immutable copy of received data for asynchronous processing, **copy** the exact slice of received bytes.

## 7. Receive buffer, truncated datagrams, and reusing DatagramPacket

The receive buffer length is the **maximum capacity** allowed to be stored in the receiving packet. If a datagram is longer than the allocated capacity, the excess may be **truncated**: `receive` does not automatically grow the buffer and does not let you read the “remaining part” in a subsequent `receive`. UDP preserves packet boundaries; a truncated packet does not become a leftover byte stream to read.

Example with a 4-byte buffer but an 8-byte datagram:

~~~text
Sent datagram:    [a b c d e f g h]   (8 bytes)
Receive buffer:   [a b c d]           (4 bytes)
Result:           4 bytes received; the rest of the datagram is lost
~~~

Besides insufficient capacity, there is a common bug when **reusing a DatagramPacket for multiple receives**: after the first receive, `packet.getLength()` is the length of the datagram just received, **no longer the full buffer capacity by default**. Before the next `receive`, reset it with `packet.setLength(buffer.length)` (or use a new packet) to advertise the capacity.

Complete example **`UdpBufferReuse.java`**:

~~~java
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class UdpBufferReuse {
    public static void main(String[] args) throws Exception {
        InetAddress host = InetAddress.getByName("127.0.0.1");

        try (DatagramSocket receiver =
                     new DatagramSocket(new InetSocketAddress(host, 0));
             DatagramSocket sender =
                     new DatagramSocket(new InetSocketAddress(host, 0))) {

            receiver.setSoTimeout(2000);
            byte[] buffer = new byte[8];
            DatagramPacket packet = new DatagramPacket(buffer, buffer.length);

            byte[] first = "hi".getBytes(StandardCharsets.UTF_8);
            sender.send(new DatagramPacket(
                    first, first.length, host, receiver.getLocalPort()));
            receiver.receive(packet);

            String firstText = new String(
                    packet.getData(), packet.getOffset(),
                    packet.getLength(), StandardCharsets.UTF_8);
            System.out.println("First: " + firstText);
            System.out.println("First bytes: " + packet.getLength());

            // The next receive must reset the allowed capacity.
            packet.setLength(buffer.length);
            byte[] next = "long".getBytes(StandardCharsets.UTF_8);
            sender.send(new DatagramPacket(
                    next, next.length, host, receiver.getLocalPort()));
            receiver.receive(packet);

            String secondText = new String(
                    packet.getData(), packet.getOffset(),
                    packet.getLength(), StandardCharsets.UTF_8);
            System.out.println("Second: " + secondText);
            System.out.println("Second bytes: " + packet.getLength());
        }
    }
}
~~~

~~~bash
javac -encoding UTF-8 UdpBufferReuse.java
java UdpBufferReuse
~~~

Output on a normal loopback:

~~~text
First: hi
First bytes: 2
Second: long
Second bytes: 4
~~~

If you omit `packet.setLength(buffer.length)`, the second receive packet still has **length limit = 2** from the previous call, so the four-byte datagram risks receiving only two bytes. Therefore, this is an important test for UDP servers that reuse buffers/packets to reduce allocations. If you need to keep the old message across the next receive, copy the data before the buffer is overwritten.

## 8. setSoTimeout, blocking, and error handling

By default, `DatagramSocket.receive(packet)` **blocks** until a matching datagram arrives or an error occurs. Set a timeout so the program does not wait indefinitely:

~~~java
socket.setSoTimeout(1500); // in milliseconds
try {
    socket.receive(packet);
    // Process the received datagram.
} catch (java.net.SocketTimeoutException e) {
    // Wait timed out; the socket can still be used for another receive.
}
~~~

This is a snippet that belongs inside a method where `socket` and `packet` have been properly created. `setSoTimeout(0)` disables the receive timeout, not an immediate timeout. The timeout only limits how long `receive` waits; it is **not** a notification from the remote side that “the packet was lost”. Network congestion, NAT, firewall, an unstarted server, or delayed packets can all cause a timeout.

Error scenarios to distinguish:

| Symptom / exception | Common cause | Appropriate action |
| --- | --- | --- |
| `BindException` (subclass of `SocketException`) | Local UDP port is already in use or cannot be bound | Check configuration/binding; in tests use port 0 |
| `SocketTimeoutException` | No matching datagram arrived before `SO_TIMEOUT` | Bounded retry or report timeout per protocol |
| `PortUnreachableException` | May have received ICMP reporting destination/port unreachable | Do not rely on the presence of this exception as a guaranteed confirmation mechanism |
| `SocketException` / `IOException` | Socket closed, OS/network error, invalid option | Log with context, close socket when needed, classify error |
| Truncated datagram | Receive buffer too small | Design payload limits, allocate adequate buffer, check protocol |

In the Java API, `receive` can throw `IOException`; `SocketTimeoutException` extends `InterruptedIOException`, which extends `IOException`. When a socket is blocked in `receive` and closed from another thread, the operation may fail with `SocketException`. Interrupt behavior depends on how the socket was created and the runtime environment; applications should not rely on a universal thread-interruption rule across all configurations.

## 9. DatagramSocket.connect() does not turn UDP into TCP

Java allows:

~~~java
socket.connect(remoteAddress, remotePort);
boolean connected = socket.isConnected();
~~~

**This is not a TCP connection.** `DatagramSocket.connect(...)` only associates the socket with a remote UDP endpoint so that sending/receiving is restricted to that endpoint and can use a default destination. There is no handshake, no guarantee that the remote server exists, no automatic reliability, and no byte stream.

Comparison of the two cases:

| State | Sending | Receiving |
| --- | --- | --- |
| **Unconnected UDP socket** | Outgoing packet must specify destination IP/port | Can receive from different senders |
| **Connected UDP socket** | Sends to the connected endpoint; packet must not target a different remote | Only receives datagrams from the configured remote endpoint |

`disconnect()` clears the configured remote endpoint, allowing the socket to return to the unconnected state if still open. A socket connected to an address/port with no listening application **can still report `isConnected() == true`**: that is purely local socket state. `PortUnreachableException` sometimes appears after ICMP unreachable, but is not a reliable liveness check.

For request/reply with a fixed service, connected UDP can be useful for source filtering. For a server handling multiple clients, using an unconnected socket and reading metadata from each `DatagramPacket` is usually more convenient.

## 10. Packet size, fragmentation, and performance

A UDP datagram is transmitted as **an independent message** with an 8-byte UDP header, plus an IP header and application payload. The theoretical maximum size differs from a safe operational payload:

- The standard UDP length field is 16 bits. With IPv4 and no options, the theoretical maximum UDP payload is about **65,507 bytes** (65,535 − 20-byte IPv4 header − 8-byte UDP header); practical limits may be lower.
- The **path MTU** is usually smaller than the maximum datagram. A large datagram may be IP-fragmented (or rejected/dropped when fragmentation is not possible); if any fragment is missing, the application does not receive the complete datagram.
- For Internet applications, design payloads small enough or use application-layer packetization/segmentation. Specific thresholds depend on IPv4/IPv6, network path, the protocol over UDP, and Path MTU.
- Sending many large datagrams frequently does not solve reliability; you must consider socket buffers, MTU, pacing, rate limiting, and congestion control.
- `setReceiveBufferSize(...)` and `setSendBufferSize(...)` adjust/hint the size of **OS socket buffers**, do **not** automatically increase `DatagramPacket`'s `byte[]` size, and do not guarantee a large datagram will arrive.
- Application-level timing and retransmit mechanisms can increase traffic; avoid unbounded or synchronized retries.

A payload carrying multiple records may need a clear format, byte limits, version, and application-level checksum/sequence number. If the data strictly requires integrity, complete delivery, and ordering, consider TCP or a protocol built on UDP with its own reliability.

## 11. Designing a more reliable UDP protocol at the application layer

UDP only provides datagrams. If the application needs richer semantics, define the payload protocol clearly:

~~~text
version | requestId | messageType | payloadLength | payload
   1    |     42    |    REQ      |       4       | ping
~~~

The diagram above is a **conceptual format**, not runnable serializer code. For a real protocol, you must specify byte order, field sizes, encoding, and payload limits, and validate them before allocating or processing.

Measures when reliability is needed:
1. **Request ID / correlation:** send a request ID and verify that the reply matches that ID; since multiple clients and retries may share the same socket.
2. **Bounded timeout + retry:** if no reply with the matching ID arrives within the configured time, retry with appropriate backoff/jitter; do not assume the first datagram was lost (the reply may arrive late).
3. **Idempotency/deduplication:** retries may cause the server to process the same request multiple times. For state-changing operations, use an idempotency key or store processed IDs.
4. **Sequence numbers and ordering:** only needed if the application truly requires ordering. Do not enforce by default because many UDP workloads tolerate out-of-order delivery.
5. **Authentication / anti-replay:** the IP/port in a packet is not user authentication; UDP sources can be spoofed under certain network conditions.
6. **Rate limiting and response caps:** a UDP server returning large responses to unauthenticated sources can create a reflection/amplification risk; do not build unbounded response sizes.

Every mechanism has tradeoffs. If you are building a channel for large documents, critical transactions, or a fully guaranteed stream, using TCP/HTTP or a transport with built-in reliability is usually simpler than implementing a reliable protocol from scratch.

## 12. API choices and use cases

UDP is often useful in DNS, short telemetry, local network discovery, gaming, voice/media, and custom-reliability protocols over UDP. That does not mean every UDP application sends insecurely or accepts data loss: higher layers can add encryption, flow control, and retransmission.

| Need | Recommendation |
| --- | --- |
| Send a simple datagram, receive a blocking response | `DatagramSocket` + `DatagramPacket` |
| Run a UDP server with socket options/selector, nonblocking I/O | Explore `java.nio.channels.DatagramChannel` |
| UDP multicast | Explore `MulticastSocket` / multicast channel, interface, and TTL/hop limit |
| Need an ordered byte stream with retransmission | `Socket`/TCP or a protocol supporting reliability |
| Need DNS lookup | `InetAddress`/resolver; do not confuse with binding a UDP socket |
| Stable local testing | Bind `127.0.0.1` and port 0, avoiding fixed port dependencies |

Do not confuse a **UDP server** with `ServerSocket`: `ServerSocket` is only for accepting TCP connections. A UDP server also uses `DatagramSocket`, may bind a fixed port, calls `receive` in a loop, and replies via `send`.

## 13. Common mistakes and how to fix them

| Mistake | Symptom / consequence | Fix |
| --- | --- | --- |
| Using `String.length()` as payload length | Packet is short of bytes when string contains Unicode | Encode to UTF-8 first, use `bytes.length` |
| Reading all of `packet.getData()` | String has trailing zero/garbage bytes or stale data | Read exact `getOffset()` and `getLength()` |
| Reusing receive packet without resetting length | Subsequent longer receives get truncated | Call `packet.setLength(buffer.length)` before receiving |
| Receive buffer too small | Datagram is truncated, remainder cannot be read | Limit payload/protocol and allocate adequate buffer |
| Forgetting `setSoTimeout` | Waits indefinitely when no packet arrives | Set timeout, retry, and error policy |
| Treating successful `send` as delivered | Packet loss goes undetected | Design acknowledgments or choose a reliable transport |
| Hardcoding test port, e.g., 9000 | Port already in use → bind failure | Use port 0, get `getLocalPort()` |
| Replying to server port instead of client source port | Client does not receive reply | Use `incoming.getAddress()` and `incoming.getPort()` |
| Thinking `connect()` does a TCP handshake | False assumption about connection state | Understand UDP connect is a local remote-endpoint setting |
| Trusting `getAddress()/getPort()` as authentication | Vulnerable to spoofing and reflection | Authentication, validation, rate limiting |
| Sending overly large datagrams | Fragmentation, drops, timeouts | Design appropriate datagram sizes |
| Sharing `DatagramPacket` across threads and mutating buffer | Races, data overwritten | Use a separate buffer per task or synchronize and copy data |

## 14. Self-check questions

**Q1.** Does UDP perform a TCP handshake before `send`?  
**Answer:** No. UDP is connectionless, transmits individual datagrams, and does not guarantee delivery to the destination application.

**Q2.** How does `DatagramSocket` differ from `DatagramPacket`?  
**Answer:** The socket is an endpoint with a local port for sending/receiving. The packet is a message with a buffer, offset, length, IP, and port.

**Q3.** The buffer is 1024 bytes, but the received packet is 4 bytes long. How many bytes should be decoded?  
**Answer:** Exactly 4 bytes per `getLength()`, starting from `getOffset()`.

**Q4.** Why can a receive packet be truncated when reused?  
**Answer:** After each `receive`, `getLength()` is the length of the data just received. When reusing it, you must reset capacity with `setLength(buffer.length)`.

**Q5.** Can a server reply to a client over UDP without knowing the client's port in advance?  
**Answer:** Yes. After receiving a packet, the server has the source's `getAddress()` and `getPort()` to create the reply packet.

**Q6.** Does calling `socket.connect(ip, port)` with UDP confirm the server is alive?  
**Answer:** No. UDP connect only configures the remote endpoint/datagram filtering; it does not perform a TCP handshake.

**Q7.** Does a `receive` timeout prove the datagram was lost?  
**Answer:** No. It could be due to slow network, routing/firewall, an unresponsive server, or a lost packet; a separate handling policy is needed.

**Q8.** Does port 0 in `new DatagramSocket(0)` mean sending to destination port 0?  
**Answer:** No. When binding, port 0 asks the OS to pick an ephemeral local port; use `getLocalPort()` to find that port.

**Q9.** Why can retrying a state-changing UDP request be dangerous?  
**Answer:** The original request may already have been processed even if the reply was lost. A retry could process it a second time without idempotency/deduplication.
