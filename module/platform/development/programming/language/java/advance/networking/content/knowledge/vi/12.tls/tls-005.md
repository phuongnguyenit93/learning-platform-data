# Xác thực tên máy bằng endpoint identification khi dùng socket TLS trực tiếp

## 1. Bài toán: TLS mã hóa chưa đủ để biết đang nói chuyện với đúng máy chủ

Trong Java, `SSLSocket` cung cấp kết nối TLS cho ứng dụng dùng socket trực tiếp. TLS có thể mã hóa dữ liệu và kiểm tra chứng chỉ của peer, nhưng **xác thực chuỗi chứng chỉ (certificate path validation) không đồng nghĩa với kiểm tra tên máy chủ (hostname/endpoint verification)**.

Ví dụ client muốn kết nối đến `api.example.com`. Kẻ tấn công điều hướng traffic đến một máy sở hữu **chứng chỉ hợp lệ, được CA đáng tin cậy cấp cho `other.example.com`**. Chứng chỉ đó có thể hợp lệ về chữ ký, thời hạn và chain, nhưng **không thuộc tên dịch vụ mà client định truy cập**. Nếu ứng dụng chỉ tin rằng "TLS handshake không ném lỗi" mà bỏ qua bước xác thực endpoint, nó có thể gửi token hoặc dữ liệu nhạy cảm tới sai server.

**Quy tắc an toàn cho Java client dùng `SSLSocket` trực tiếp: trước TLS handshake phải bật endpoint identification bằng `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")`**, đồng thời giữ cơ chế kiểm tra chuỗi chứng chỉ bằng trust manager đáng tin cậy. Lựa chọn `"HTTPS"` là tên thuật toán kiểm tra danh tính endpoint của JSSE; nó không biến ứng dụng socket tùy chỉnh thành HTTP.

Bài học này tập trung vào đường đi **client Java → server TLS**. Việc server yêu cầu client certificate (mutual TLS, mTLS) là bài toán xác thực chiều ngược lại, không thay cho xác thực **server hostname** ở client.

## 2. Ba cơ chế phải phân biệt: trust, endpoint name, SNI

```text
Client muốn truy cập: api.example.com
                 |
                 v
        TCP connect tới một địa chỉ IP
                 |
                 v
        TLS handshake + server certificate
                 |
          +------+------+------------------------+
          |             |                        |
          v             v                        v
   Chain/trust       Endpoint ID                 SNI
   validation        verification             (ClientHello)
          |             |                        |
   Chứng chỉ có    Chứng chỉ có quyền      Gợi ý tên máy để server
   nối đến CA/     đại diện đúng tên       chọn đúng chứng chỉ/
   trust anchor?   api.example.com?        cấu hình virtual host
          |             |                        |
          +------ AND --+                        |
                 |                               |
                 v                               |
        Chỉ chấp nhận nếu cả hai pass <-----------+
        (SNI giúp server chọn cert nhưng KHÔNG xác thực)
```

| Cơ chế | Nó giải quyết câu hỏi gì? | Nó **không** bảo đảm |
| --- | --- | --- |
| **Trust chain / PKIX** qua `X509TrustManager` | Certificate chain, chữ ký, trust anchor, các chính sách kiểm tra chứng chỉ áp dụng có đáng tin? | Chứng chỉ thuộc **đúng hostname** mà ứng dụng yêu cầu |
| **Endpoint identification** | Danh tính mà client **mong đợi** có khớp danh tính trong certificate (thường là Subject Alternative Name, SAN) không? | Chứng chỉ được ký bởi CA đáng tin nếu trust manager bị thay bằng trust-all |
| **SNI** (Server Name Indication) | Cho server biết hostname logic khi thiết lập TLS để chọn certificate/virtual host phù hợp | Không thay thế kiểm tra chain hoặc hostname; server có thể gửi sai certificate |

Khi không chủ động cấu hình endpoint identification trên một `SSLSocket` tạo trực tiếp, **đừng giả định JSSE sẽ tự kiểm tra hostname giống một HTTPS client cấp cao**. Sử dụng `SSLParameters` để thiết lập điều đó một cách tường minh trước handshake. Các API client như `HttpsURLConnection` hoặc `java.net.http.HttpClient` có quy tắc xác thực HTTPS riêng; không lấy hành vi mặc định của chúng suy ra cho mọi mã dùng `SSLSocket`.

**Một phép thử phân biệt:** chứng chỉ được CA tin cậy cấp cho `payments.example.com` nhưng socket được tạo với tên kỳ vọng `profile.example.com` thì **endpoint identification phải từ chối**, dù trust chain hợp lệ. Ngược lại, certificate có SAN đúng tên nhưng ký bởi một CA không nằm trong trust store thì **trust validation cũng phải từ chối**.

## 3. Mẫu client `SSLSocket` trực tiếp an toàn trên Java 17+

Trong ứng dụng bình thường có máy chủ thật và public/private PKI được cấu hình đúng, có thể dùng **default `SSLSocketFactory`** để giữ các trust manager mặc định của JVM, sau đó thiết lập hostname verification:

```java
import java.io.IOException;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSocketFactory;

public final class DirectTlsClient {
    public static void main(String[] args) throws IOException {
        String expectedHost = "api.example.com";
        int port = 443;

        SSLSocketFactory factory =
                (SSLSocketFactory) SSLSocketFactory.getDefault();
        try (SSLSocket ssl = (SSLSocket)
                factory.createSocket(expectedHost, port)) {
            SSLParameters params = ssl.getSSLParameters();
            params.setEndpointIdentificationAlgorithm("HTTPS");
            ssl.setSSLParameters(params);    // TRƯỚC handshake.

            ssl.setSoTimeout(5000);          // Read timeout, không phải total deadline.
            ssl.startHandshake();            // Fail-closed nếu certificate sai.

            // Chỉ trao đổi application data sau khi TLS handshake thành công.
            System.out.println("TLS server identity verified");
        }
    }
}
```

Đây là **tệp độc lập** `DirectTlsClient.java`, biên dịch được bằng Java 17:

```bash
javac --release 17 DirectTlsClient.java
java DirectTlsClient
```

**Chú ý:** `api.example.com` trong mã là tên minh họa, không phải dịch vụ được cấu hình để chạy bài kiểm thử. Không có stdout thành công được cam kết cho ví dụ này vì còn phụ thuộc DNS, server đang phục vụ cổng, chứng chỉ và trust store thực tế. Ví dụ thực nghiệm tự tạo server và trust store trên loopback ở mục 7 sẽ có stdout kiểm thử xác định.

Các bước có ý nghĩa bảo mật:

1. `expectedHost` phải là **tên logic mà ứng dụng thực sự định kết nối**, lấy từ cấu hình/địa chỉ đích đã được cho phép, không lấy từ nội dung chứng chỉ do peer tự gửi.
2. `createSocket(expectedHost, port)` giúp JSSE biết **peer host logic**. Nếu đi bằng IP, proxy hoặc một transport có sẵn, cần bảo toàn expected hostname khi tạo layered socket (mục 5).
3. Lấy `SSLParameters params = ssl.getSSLParameters()` rồi chỉnh một thuộc tính, tránh tạo `new SSLParameters()` thiếu các cấu hình khác một cách vô ý.
4. `setEndpointIdentificationAlgorithm("HTTPS")` bật thuật toán endpoint identity. Không dùng `null` hoặc chuỗi rỗng để tắt kiểm tra.
5. `ssl.setSSLParameters(params)` phải chạy **trước** `ssl.startHandshake()` và trước bất kỳ hoạt động I/O nào vô tình khởi động TLS handshake.
6. Chỉ chuyển token/request/secret sau khi `startHandshake()` hoàn tất thành công; khi handshake thất bại, **đóng socket và dừng giao dịch**.

`SSLSocket.setSoTimeout(...)` ảnh hưởng các thao tác đọc của socket; nó không tự tạo một **deadline end-to-end** bao trùm DNS, TCP connect, toàn handshake và nghiệp vụ. Muốn giới hạn thời gian kết nối TCP rõ ràng, dùng socket TCP với `connect(address, timeout)` rồi tạo layered TLS socket như phần sau.

## 4. Danh tính phải so với SAN, không phải chỉ với CA hoặc IP đích

Hostname verification dựa trên **hostname expected** và danh tính được certificate công bố. Theo quy tắc của thuật toán HTTPS:

- Nếu client dùng DNS hostname `service.example.com`, certificate server cần danh tính DNS tương ứng, thông thường trong **`subjectAltName: dNSName`**.
- Nếu client thực sự kỳ vọng một địa chỉ IP literal như `192.0.2.10`, certificate cần SAN loại **`iPAddress`** phù hợp; chỉ có `dNSName` chứa chuỗi trông giống địa chỉ IP không phải lựa chọn tương đương.
- `CN=service.example.com` trong Subject **không nên dùng thay SAN** cho chứng chỉ hiện đại. Một số thuật toán/triển khai cũ có cơ chế fallback CN trong vài tình huống, nhưng **không thiết kế hay dựa vào fallback đó**.
- Chứng chỉ wildcard có quy tắc khớp hostname cụ thể, không nên giả định `*.example.com` khớp mọi cấp tên miền hay tên gốc `example.com`.
- Kiểm tra tên máy khác với kiểm tra chứng chỉ hết hạn, chữ ký, trust anchor hay chính sách key usage. Tên đúng nhưng chain không được trust vẫn phải thất bại.

**Ví dụ:**

| Host ứng dụng mong đợi | SAN certificate | Kết quả danh tính (giả sử trust chain hợp lệ) |
| --- | --- | --- |
| `api.example.com` | `DNS:api.example.com` | Khớp |
| `api.example.com` | `DNS:other.example.com` | Không khớp |
| `192.0.2.10` | `IP:192.0.2.10` | Khớp |
| `192.0.2.10` | Chỉ `DNS:api.example.com` | Không khớp với IP literal |
| `example.com` | Chỉ `DNS:*.example.com` | Không nên coi là khớp với tên miền gốc |
| `a.b.example.com` | Chỉ `DNS:*.example.com` | Không nên coi wildcard một nhãn là khớp nhiều cấp |

Khi ứng dụng cố kết nối trực tiếp tới IP do service discovery trả về, **đừng sửa `expectedHost` thành IP** chỉ để socket kết nối thành công. Nếu danh tính tin cậy của dịch vụ là `api.example.com`, hãy giữ tên đó để TLS kiểm tra; IP chỉ là đích vận chuyển TCP. Nếu hệ thống thật sự dùng IP literal làm danh tính, phát hành certificate có SAN loại iPAddress phù hợp.

## 5. Kết nối TCP tới IP nhưng xác thực tên DNS: layered TLS socket

Có lúc một client phải mở kết nối TCP theo một địa chỉ do DNS/cache/proxy/service discovery cung cấp, nhưng vẫn phải kiểm tra certificate theo **tên dịch vụ ban đầu**. Với JSSE, dùng overload:

```java
SSLSocketFactory.createSocket(
        Socket existingTcp, String expectedHost, int port, boolean autoClose)
```

Đoạn minh họa (trong phương thức đã có `InetAddress ip`, `String expectedHost`, `int port`, `IOException` handling):

```java
Socket transport = new Socket();
transport.connect(new InetSocketAddress(ip, port), 3000);

try (SSLSocket tls = (SSLSocket) factory.createSocket(
        transport, expectedHost, port, true)) {
    SSLParameters p = tls.getSSLParameters();
    p.setEndpointIdentificationAlgorithm("HTTPS");
    tls.setSSLParameters(p);
    tls.setSoTimeout(5000);
    tls.startHandshake();

    // Application data chỉ sau khi TLS handshake và endpoint check pass.
}
```

**Lưu ý tài nguyên:** ở đoạn rút gọn này nếu tạo layered TLS socket ném exception **trước khi try-with-resources nhận quyền sở hữu**, cần đóng `transport` ở catch/finally tương ứng. Trong chương trình production, dùng `try-with-resources` bao ngoài cho transport hoặc quản lý đóng chắc chắn. Tham số `autoClose=true` làm layered TLS socket đóng transport khi nó đóng.

Ý nghĩa các đối số:

- `transport`: kết nối TCP đang mở tới đích IP thực tế.
- `expectedHost`: **hostname logic client yêu cầu và certificate phải khớp**; không nhất thiết là chuỗi IP của transport.
- `port`: cổng dịch vụ.
- `autoClose`: có tự đóng socket bên dưới khi TLS socket đóng hay không.

Đừng chọn `expectedHost` bằng cách nhìn ngược từ certificate server rồi "so khớp" với chính nó. Đó là tự cho peer quyết định danh tính được kỳ vọng và phá bỏ mục đích chống giả mạo endpoint.

Một layered socket có host logic đúng còn giúp JSSE có ngữ cảnh tên máy cho các cơ chế khác như SNI khi provider có thể sử dụng; tuy nhiên **SNI vẫn không phải bước kiểm tra hostname**. Nên giữ nguyên host logic và không tùy tiện vô hiệu hóa SNI để giải quyết lỗi certificate.

## 6. TLS handshake thành công và thất bại có ý nghĩa gì?

Với client thiết lập trust manager phù hợp **và** endpoint identification trước handshake:

```text
TCP connected
     |
     v
Set SSLParameters endpoint algorithm = "HTTPS"
     |
     v
Start TLS handshake
     |
     +--> Check trust chain / certificate constraints
     |
     +--> Check expected hostname against certificate identity
     |
     +--> Negotiate TLS version, cipher suite, keys
     |
     +--> ANY FAILURE? -- yes --> SSLException / SSLHandshakeException
     |                            close connection; no sensitive data
     |
     v
Handshake successful
     |
     v
Application can send private data to verified TLS endpoint
```

Kết quả `startHandshake()` thành công chỉ có ý nghĩa **trong phạm vi chính sách bảo mật đã thực sự cấu hình**. Nếu code thay `TrustManager` bằng "chấp nhận mọi chứng chỉ", hoặc đặt endpoint identification rỗng, không được kết luận server đã được xác thực đúng chỉ từ handshake success.

Ngược lại, nếu handshake thất bại với lỗi hostname mismatch, chương trình **không được tự động retry mà tắt endpoint identification**; việc làm đó biến cơ chế phát hiện nguy cơ MITM thành một cửa hậu. Đúng hơn là xác minh DNS/service name, SAN của cert, trust store và cấu hình server/SNI, sau đó sửa cấu hình hoặc phát hành chứng chỉ đúng.

## 7. Ví dụ thực nghiệm Java 17: cùng một certificate, tên đúng được nhận và tên sai bị từ chối

Ta tạo một server TLS **cục bộ trên loopback** với certificate tự ký chỉ nhằm mục đích học. SAN của certificate chứa `DNS:localhost` và `IP:127.0.0.1`. Client có một trust store riêng chứa **certificate công khai của server thử nghiệm**, vì vậy kiểm tra chain có thể pass trong môi trường test. Sau đó tạo **hai kết nối đến cùng IP/cổng**:

1. Kết nối A truyền `expectedHost="localhost"` → certificate có DNS SAN tương ứng → handshake pass.
2. Kết nối B truyền `expectedHost="wrong.example"` → vẫn trust đúng certificate nhưng **DNS SAN không khớp** → endpoint identification từ chối trong handshake.

Bài test này tách hai điều kiện bảo mật: **trust store giữ nguyên ở cả hai kết nối**, biến duy nhất thay đổi là **tên máy mà client kỳ vọng**. Không dùng trust-all manager, không vô hiệu hóa hostname verification.

### 7.1. Tạo test certificate và trust store

Trong một **thư mục thử nghiệm riêng** với JDK `keytool` sẵn trên PATH, chạy lần lượt:

```bash
keytool -genkeypair -alias server -keyalg RSA -keysize 2048 -validity 2 -dname "CN=localhost" -ext "SAN=dns:localhost,ip:127.0.0.1" -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -noprompt
keytool -exportcert -alias server -keystore server.p12 -storepass changeit -rfc -file server.cer
keytool -importcert -alias local-test -file server.cer -keystore client-trust.p12 -storetype PKCS12 -storepass changeit -noprompt
```

Các file được tạo:

- `server.p12`: key store **có private key** và certificate của server. Phải bảo vệ file này; không chia sẻ lên Git hay gửi tới client.
- `server.cer`: certificate công khai xuất ra từ server, dùng trong bước tạo trust store.
- `client-trust.p12`: trust store của **client thử nghiệm**, chứa certificate công khai được chấp nhận cho test này. Nó không cần private key server.

**`changeit` ở đây chỉ là password cố định cho ví dụ localhost, không dùng trong production.** Certificate test có thời hạn ngắn (`-validity 2` ngày), không được xem là certificate cấp bởi public CA. Trong hệ thống thực, dùng trust store được quản trị, quyền hạn file phù hợp, secret không hard-code và luân chuyển certificate/key.

### 7.2. Mã Java đầy đủ

**Tên tệp:** `TlsEndpointIdentificationDemo.java`.

```java
import java.io.IOException;
import java.io.InputStream;
import java.net.InetAddress;
import java.net.Socket;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLHandshakeException;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSocketFactory;
import javax.net.ssl.TrustManagerFactory;

public final class TlsEndpointIdentificationDemo {
    private static final char[] PASSWORD = "changeit".toCharArray();

    static KeyStore loadStore(Path path) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(path)) {
            store.load(in, PASSWORD);
        }
        return store;
    }

    static SSLContext serverContext(Path keyStore) throws Exception {
        KeyManagerFactory keys = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        keys.init(loadStore(keyStore), PASSWORD);
        SSLContext ctx = SSLContext.getInstance("TLS");
        ctx.init(keys.getKeyManagers(), null, null);
        return ctx;
    }

    static SSLContext clientContext(Path trustStore) throws Exception {
        TrustManagerFactory trust = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        trust.init(loadStore(trustStore));
        SSLContext ctx = SSLContext.getInstance("TLS");
        ctx.init(null, trust.getTrustManagers(), null);
        return ctx;
    }

    static void connectAndVerify(SSLSocketFactory factory, InetAddress ip,
            int port, String expectedHost) throws Exception {
        Socket tcp = new Socket(ip, port);
        try (SSLSocket tls = (SSLSocket) factory.createSocket(
                tcp, expectedHost, port, true)) {
            tls.setSoTimeout(5000);
            SSLParameters params = tls.getSSLParameters();
            params.setEndpointIdentificationAlgorithm("HTTPS");
            tls.setSSLParameters(params);  // Before handshake.
            tls.startHandshake();
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Pass server.p12 and client-trust.p12");
        }
        SSLContext serverCtx = serverContext(Path.of(args[0]));
        SSLContext clientCtx = clientContext(Path.of(args[1]));
        InetAddress loopback = InetAddress.getLoopbackAddress();
        try (SSLServerSocket listener = (SSLServerSocket) serverCtx
                .getServerSocketFactory().createServerSocket(0, 50, loopback)) {
            listener.setSoTimeout(5000);
            ExecutorService worker = Executors.newSingleThreadExecutor();
            try {
                Future<?> server = worker.submit(() -> {
                    for (int i = 0; i < 2; i++) {
                        try (SSLSocket peer = (SSLSocket) listener.accept()) {
                            peer.setSoTimeout(5000);
                            peer.startHandshake();
                        } catch (IOException duringClientAbort) {
                            // The mismatch case can abort the server handshake.
                        }
                    }
                    return null;
                });
                int port = listener.getLocalPort();
                SSLSocketFactory factory = clientCtx.getSocketFactory();

                connectAndVerify(factory, loopback, port, "localhost");
                System.out.println("localhost: verified");

                try {
                    connectAndVerify(factory, loopback, port, "wrong.example");
                    throw new AssertionError("Expected hostname mismatch");
                } catch (SSLHandshakeException expected) {
                    System.out.println("wrong.example: rejected");
                }
                server.get(8, TimeUnit.SECONDS);
            } finally {
                worker.shutdownNow();
            }
        }
    }
}
```

**Chạy sau khi đã tạo ba file test certificate/store:**

```bash
javac --release 17 TlsEndpointIdentificationDemo.java
java TlsEndpointIdentificationDemo server.p12 client-trust.p12
```

Stdout trên môi trường Java 17 đã kiểm thử:

```text
localhost: verified
wrong.example: rejected
```

**Phân tích chính xác:**

- Kết nối đầu tiên có `expectedHost="localhost"` và SAN `DNS:localhost`; client đã trust certificate test và bật `"HTTPS"` nên TLS handshake thành công.
- Kết nối thứ hai cũng tới **cùng IP/cổng loopback**, cùng SSLContext và trust store; `expectedHost="wrong.example"` không có trong SAN. `startHandshake()` ném `SSLHandshakeException`, được chương trình bắt và in `rejected`.
- Các dòng stdout chỉ chứng minh **kết quả kiểm tra TLS trong bài thử**, không chứng minh server đã xử lý ứng dụng hay một API kinh doanh thành công.
- Phần server demo **bỏ qua IOException khi client chủ động abort handshake** để stdout đơn giản và hai lần accept kết thúc. Trong server sản xuất phải log/xử lý ngoại lệ theo loại, xác định thời hạn và không âm thầm bỏ qua lỗi TLS tùy ý.
- Đường đi của demo dùng socket layer cho cả hai lần thử. Điều này giúp chỉ rõ rằng **IP vận chuyển** không quyết định kết quả hostname check nếu client cung cấp **peer hostname logic** vào factory.

### 7.3. Vì sao không dùng Internet/public CA cho bài test?

Nếu thử trên một website công khai, kết quả phụ thuộc DNS, chính sách proxy, public CA, thời gian hệ thống, server và network. Test loopback có thể kiểm soát tất cả đầu vào: certificate do ta tạo, SAN biết trước, trust store riêng và hai expected hostname. Đây là cách tin cậy hơn để phân biệt **đúng tên** và **sai tên**, không cần thiết lập một "trust-all SSLContext" nguy hiểm.

## 8. SNI giúp chọn certificate, không thay hostname verification

Một server TLS có thể phục vụ nhiều hostname trên cùng IP/cổng. ClientHello TLS có thể chứa **Server Name Indication (SNI)** để giúp server chọn certificate tương ứng:

```text
TCP -> 203.0.113.10:443

Client expectedHost = api.example.com
ClientHello SNI     = api.example.com
Server chooses cert = DNS:api.example.com
Client verifies cert chain AND endpoint ID api.example.com
```

Nếu SNI bị bỏ, server có thể trả certificate mặc định cho một hostname khác. Khi bật endpoint identification, client phải từ chối nếu SAN của certificate mặc định không khớp.

**Đừng hiểu rằng "SNI đúng thì đã verify hostname".** SNI chỉ là thông tin do client **gửi tới server**; kiểm tra endpoint identification là phép kiểm tra **certificate server trả về so với tên kỳ vọng**.

Trong các trường hợp đặc biệt dùng IP hoặc layered socket, JSSE provider có thể quyết định cách gửi SNI dựa trên tên host hợp lệ. Khi cần cấu hình SNI riêng, API liên quan là `SSLParameters.setServerNames(...)` cùng `SNIHostName`, nhưng không nên dùng cấu hình đó để che lỗi certificate/SAN. Cũng cần nhớ **tên kiểm tra endpoint và SNI có vai trò khác nhau**: không đổi expected identity chỉ để khớp một certificate không hợp lệ.

## 9. Trust store và hostname verification phải cùng bật

Một lỗi thường gặp là thấy certificate tự ký trong môi trường phát triển bị từ chối rồi viết:

```java
// SAI về bảo mật: trust-all manager kiểu checkServerTrusted rỗng.
TrustManager[] trustAll = new TrustManager[] {
    new X509TrustManager() {
        public void checkClientTrusted(X509Certificate[] c, String a) {}
        public void checkServerTrusted(X509Certificate[] c, String a) {}
        public X509Certificate[] getAcceptedIssuers() {
            return new X509Certificate[0];
        }
    }
};
```

*Đoạn trên cố ý là **phản ví dụ không an toàn**, không hoàn chỉnh và không được chạy/dùng trong sản phẩm.* Nếu thay trust manager bằng implementation "cho qua" mọi chain, một certificate giả mạo có thể được chấp nhận. **Bật `setEndpointIdentificationAlgorithm("HTTPS")` không biến trust-all thành an toàn**, bởi attacker có thể tự phát hành certificate có SAN trùng tên mong đợi.

Cách hợp lệ cho hệ thống nội bộ là **thêm CA hoặc certificate cụ thể được phê duyệt vào trust store**, dùng `TrustManagerFactory` hoặc default JVM trust configuration với CA quản trị. Local test ở trên dùng client trust store chỉ tin một certificate công khai; còn production thường tin một tập CA phù hợp chính sách, có quy trình rotation/revocation và thời hạn.

**Các lựa chọn sai phải tránh:**

- Không sử dụng `TrustManager` với `checkServerTrusted(...)` rỗng.
- Không đặt endpoint identification algorithm thành `""` hoặc `null` để "sửa" lỗi hostname.
- Không bỏ `startHandshake()` rồi gửi credential trước khi server identity được kiểm tra.
- Không dùng `HttpsURLConnection.setDefaultHostnameVerifier((h,s)->true)` để chữa lỗi cho client HTTPS, và **cũng không nhầm HostnameVerifier của HttpsURLConnection là cấu hình chung cho mọi SSLSocket**.
- Không dựa vào `SSLSession.getPeerCertificates()` rồi chỉ kiểm tra "có chứng chỉ" mà bỏ SAN/hostname.
- Không pin một certificate/leaf key một cách tùy tiện rồi bỏ kiểm tra hostname; nếu pinning cần thiết, phải thiết kế kết hợp với xác thực danh tính và quy trình xoay khóa.

## 10. Những lỗi thường gặp khi dùng `SSLSocket` trực tiếp

| Tình huống | Vì sao nguy hiểm hoặc sai? | Hướng xử lý |
| --- | --- | --- |
| Dùng `factory.createSocket(host, port)` rồi chỉ `startHandshake()` | Không nên mặc định direct socket có hostname verification như HTTPS client | Bật `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` trước handshake |
| Trust store chấp nhận CA nhưng cert thuộc hostname khác | Xác thực chain không đồng nghĩa endpoint identity | Kiểm tra SAN theo expected host |
| Kết nối tới IP, truyền IP làm expectedHost trong khi cert chỉ có DNS SAN | Tên logic và IP transport khác nhau | Dùng layered socket với DNS hostname logic được xác thực |
| Gửi đúng SNI và cho rằng đủ bảo mật | SNI là hint cho server, không phải phép xác thực | Bật endpoint identification |
| Đọc `getSession()`/I/O trước khi cấu hình SSLParameters | Handshake có thể bắt đầu trước khi áp quy tắc hostname | Đặt SSLParameters trước mọi thao tác khởi động handshake |
| Certificate hostname sai, retry bằng cách tắt verification | Mở đường cho MITM | Fail-closed, sửa SAN/tên đích |
| Chứng chỉ chưa được trust, dùng trust-all | Mất PKIX trust validation | Cấu hình trust store/CA hợp lệ |
| Chỉ nhìn `CN` rồi bỏ SAN | Không theo quy ước định danh certificate hiện đại | Yêu cầu SAN DNS/IP phù hợp |
| Dùng `getInetAddress().getHostAddress()` làm identity mặc định | IP nhận kết nối không nhất thiết là tên dịch vụ | Giữ host logic từ cấu hình được cho phép |
| Dùng certificate tự ký localhost trong production | Không phù hợp vòng đời và độ tin cậy của dịch vụ thật | Dùng certificate/CA được quản trị |
| Chỉ log "SSL handshake failed" mà không phân loại | Khó phân biệt chain lỗi, hostname mismatch, TLS version | Log nguyên nhân có kiểm soát, không log secret |
| Tắt hostname verification trong môi trường test rồi quên bật lại | Cấu hình không an toàn đi vào production | Test cả trường hợp host đúng và host sai trong CI |
| Xem `setSoTimeout(5000)` là deadline toàn giao dịch | Chỉ là chính sách chờ read trên socket | Thiết kế timeout/connect/deadline/cancellation tổng thể |
| Đồng nhất mTLS client certificate với server hostname check | Hai chiều xác thực khác nhau | Thực hiện cả hai nếu ứng dụng cần mutual identity |

## 11. Kết quả lỗi và hành vi fail-closed

Các trường hợp thường gặp:

| Lỗi | Dấu hiệu có thể thấy | Cách phản ứng |
| --- | --- | --- |
| Certificate có SAN sai hostname | Thường `SSLHandshakeException` với nguyên nhân certificate name mismatch | Từ chối, xác minh tên cấu hình và SAN |
| Certificate hết hạn/chain không trusted | `SSLHandshakeException` hoặc lỗi chứng chỉ lồng trong exception | Kiểm tra certificate chain, CA, thời gian hệ thống |
| TLS protocol/cipher không tương thích | `SSLException`/`SSLHandshakeException`, thông báo tùy JDK/provider | Cập nhật cấu hình TLS, không hạ an ninh bừa bãi |
| TCP connect thất bại | `ConnectException`, `SocketTimeoutException` hoặc `IOException` tùy tình huống | Kiểm tra host, route, firewall, timeout |
| Server đóng giữa handshake | EOF/`SSLException`/socket I/O exception | Đóng socket, không gửi application payload |
| TLS handshake đúng nhưng app response lỗi | Lỗi giao thức ứng dụng sau handshake | Xử lý ở tầng application, không nhầm với hostname check |

**Đừng so khớp tuyệt đối chuỗi thông báo lỗi** giữa các phiên bản JDK, provider và hệ điều hành. Với test tự động, nên xác nhận handshake **bị từ chối**, phân loại exception/chuỗi nguyên nhân phù hợp, và bảo đảm kết nối hợp lệ vẫn thành công.

Cần phân biệt **trust validation**, **endpoint identification**, **TLS handshake** và **authorization của ứng dụng**: client xác thực server TLS đúng tên không đồng nghĩa server có quyền thực hiện mọi thao tác nghiệp vụ; ứng dụng vẫn cần xác thực người dùng, phân quyền và kiểm soát dữ liệu.

## 12. Lưu ý cho `SSLEngine` và các client cấp cao

Khi triển khai TLS trên NIO `SocketChannel` bằng `SSLEngine`, nguyên tắc tương tự: tạo engine ở **client mode** với peer hostname logic phù hợp, lấy `SSLParameters` và cấu hình endpoint identification trước khi thực hiện các bước handshake qua `wrap/unwrap`. Ví dụ về mặt API:

```java
// Mảnh minh họa, giả định đã có SSLContext ctx,
// expectedHost và port, chưa triển khai vòng wrap/unwrap.
SSLEngine engine = ctx.createSSLEngine(expectedHost, port);
engine.setUseClientMode(true);
SSLParameters parameters = engine.getSSLParameters();
parameters.setEndpointIdentificationAlgorithm("HTTPS");
engine.setSSLParameters(parameters);
```

*Phần `SSLEngine` này không phải ứng dụng runnable*: vòng handshake NIO, bộ đệm TLS, delegated tasks và trạng thái `NEED_WRAP/NEED_UNWRAP/NEED_TASK` cần một triển khai riêng. Khi dùng `SSLEngine` client mode, đừng tự bỏ peer host nếu muốn endpoint identity matching. Cấu hình SNI và trust managers vẫn là các vấn đề riêng.

Với các client HTTP cấp cao, ưu tiên API có chính sách HTTPS và hostname verification chuẩn thay vì tự viết TLS stack. Trọng tâm của bài là **ứng dụng socket TLS trực tiếp**, nơi người lập trình phải tự đảm bảo các tham số xác thực được thiết lập.

## 13. Quy trình kiểm tra bảo mật trước khi phát hành

Có thể áp dụng checklist sau cho mọi đoạn code tạo `SSLSocket` trực tiếp:

1. **Xác định expected host:** lấy từ cấu hình tin cậy/URL đích được cho phép; không lấy từ server certificate, reverse DNS tùy ý hoặc dữ liệu attacker kiểm soát.
2. **Kiểm tra certificate SAN:** certificate phải có DNS SAN hoặc IP SAN khớp đúng danh tính mà ứng dụng dùng; phát hành lại certificate nếu thiếu.
3. **Kiểm tra trust:** client dùng PKIX trust manager và trust store đúng môi trường. Không có trust-all hoặc hostname verifier luôn true.
4. **Cấu hình TLS trước handshake:** `getSSLParameters()` → `setEndpointIdentificationAlgorithm("HTTPS")` → `setSSLParameters(...)` → `startHandshake()`.
5. **Giữ peerHost khi dùng transport có sẵn:** dùng layered socket với hostname logic để không đổi hostname thành IP.
6. **Fail-closed:** handshake/hostname validation lỗi thì đóng socket, không gửi credential và không retry ở chế độ bỏ kiểm tra.
7. **Test hai trường hợp bắt buộc:** SAN đúng và SAN sai nhưng chain vẫn trust. Test thêm cert hết hạn/untrusted cho trust validation.
8. **Test SNI:** virtual hosting đúng cert khi SNI đúng; nếu cert mặc định sai tên, client phải từ chối.
9. **Timeout và quản trị:** thêm TCP connect timeout, deadline handshake/giao dịch, logging có kiểm soát và giám sát lỗi.
10. **Không nhầm mTLS với kiểm tra server:** nếu dùng client cert, vẫn cần validate server hostname ở chiều client.

Với chứng chỉ thực tế, policy kiểm tra thu hồi (CRL/OCSP), certificate transparency, vòng đời rotation, pinning hoặc private CA phụ thuộc môi trường và cấu hình JSSE. **Không khẳng định bật endpoint identification tự động giải quyết mọi chính sách certificate/revocation**. Nó chỉ giải quyết một lớp rất quan trọng: chứng chỉ của đối tác có phù hợp với hostname expected hay không.

## 14. Bài tập tự kiểm tra

**Bài 1.** Client tin cậy public CA và kết nối `billing.example.com`, nhưng peer trình certificate hợp lệ cho `cdn.example.com`. Nếu chỉ kiểm tra chain, có thể xảy ra vấn đề gì? Cần cấu hình API nào trên `SSLSocket` để reject?

**Bài 2.** Client kết nối qua một IP service discovery nhưng danh tính mong đợi là `api.example.com`. Certificate có `DNS:api.example.com`, không có IP SAN. Nên truyền host nào cho `SSLSocketFactory.createSocket(existingTcp, host, port, true)`?

**Bài 3.** Server trả certificate đúng SAN nhưng ký bằng CA không tin cậy. Có thể coi endpoint identification pass là đủ an toàn không?

**Bài 4.** Nếu client có expected host chính xác và gửi SNI chính xác, tại sao vẫn phải thực hiện hostname verification?

**Bài 5.** Developer gọi `ssl.getSession()` trước rồi mới `ssl.setSSLParameters(...)`. Vấn đề thứ tự là gì?

**Bài 6.** Trong demo, cùng một trust store chứa public certificate localhost, vì sao `localhost` được xác thực còn `wrong.example` bị từ chối dù cùng IP?

**Bài 7.** Khi cert hostname không khớp, developer đề xuất cài trust-all manager và tắt endpoint identification trong môi trường production. Đây có phải cách giải quyết lỗi hợp lệ không?

**Đáp án gợi ý:**

1. Client có thể chấp nhận server sai danh tính. Dùng `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` trước handshake và trust manager đáng tin.
2. Truyền `"api.example.com"` — hostname logic được dùng để kiểm tra certificate — thay vì IP transport.
3. Không. Phải thỏa cả **trusted chain** lẫn **matching expected hostname**.
4. SNI chỉ gợi ý server chọn certificate. Peer vẫn có thể trả cert khác; client phải xác thực danh tính trên cert trả về.
5. `getSession()` có thể khởi động handshake; thiết lập endpoint ID sau đó là quá muộn. Cấu hình SSLParameters trước bất kỳ hành vi kích hoạt handshake.
6. Cert có SAN DNS localhost nhưng không có wrong.example; trust vẫn như nhau, endpoint ID tạo khác biệt.
7. Không. Đó là giảm bảo mật nguy hiểm. Phải sửa tên dịch vụ, SAN/certificate và cấu hình trust hợp lệ, giữ fail-closed.
