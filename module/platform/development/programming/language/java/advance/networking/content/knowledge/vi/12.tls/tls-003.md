# SSLContext, SSLSocketFactory, SSLSocket và SSLServerSocket trong Java TLS

## 1. Mục tiêu của bài học

Trong Java Advanced Networking, **TLS** (Transport Layer Security) bảo vệ dữ liệu chạy trên kết nối TCP bằng cơ chế xác thực peer, thương lượng thuật toán mật mã, mã hóa và bảo vệ tính toàn vẹn. Bộ API **JSSE** (Java Secure Socket Extension, trong `javax.net.ssl`) cho phép ứng dụng Java thiết lập TLS mà không tự hiện thực thuật toán TLS.

Bốn đối tượng cần phân biệt là:

- **`SSLContext`:** cấu hình/bối cảnh TLS gồm những `KeyManager`, `TrustManager` và nguồn số ngẫu nhiên dùng để tạo các đầu cuối TLS.
- **`SSLSocketFactory`:** factory tạo **socket client TLS** dựa trên `SSLContext` đã chọn.
- **`SSLSocket`:** một socket TLS cụ thể, thường dùng để kết nối TCP, thực hiện handshake, đọc/ghi dữ liệu ứng dụng đã được TLS bảo vệ.
- **`SSLServerSocket`:** một **listening socket TLS** phía server; `accept()` tạo một `SSLSocket` riêng để xử lý client đã được chấp nhận.

Cần hiểu thêm **`SSLServerSocketFactory`**, vì `SSLContext.getServerSocketFactory()` trả đối tượng này để tạo `SSLServerSocket`; bộ bốn trong tiêu đề không tự mô tả đủ bước tạo listener server.

Sau bài, bạn sẽ biết:
1. Vẽ đúng quan hệ `SSLContext → factory → socket → TLS handshake` và phân biệt socket lắng nghe với socket đã chấp nhận.
2. Cấu hình server identity bằng **keystore/private key** và cấu hình client trust bằng **truststore/CA**, không dùng “trust-all”.
3. Tạo kết nối HTTPS-style **có xác minh tên host** khi dùng `SSLSocket` trực tiếp, thay vì chỉ tin chứng chỉ theo chuỗi.
4. Chạy ví dụ Java 17+ **TLSv1.3 loopback** dùng cả `SSLContext`, `SSLSocketFactory`, `SSLSocket` và `SSLServerSocket`.
5. Hiểu handshake, TLS session, cipher suite, client authentication (mTLS), timeout, đóng socket và các lỗi thường gặp.

> **Định hướng:** tên class vẫn mang tiền tố “SSL” vì lịch sử JSSE; cấu hình ví dụ sử dụng **TLSv1.3**, không sử dụng giao thức SSLv2/SSLv3 lỗi thời.

## 2. Bản đồ kiến trúc JSSE

```text
                        Java application
                        ┌────────────────────────────┐
                        │ Protocol code / streams    │
                        └─────────────┬──────────────┘
                                      │
             CLIENT                   │                        SERVER
                                      │
   ┌───────────────────────┐          │         ┌────────────────────────┐
   │ Trusted certificates  │          │         │ Identity certificate   │
   │ / CA truststore       │          │         │ + server private key   │
   └──────────┬────────────┘          │         └────────────┬───────────┘
              ▼                       │                      ▼
      TrustManagerFactory             │              KeyManagerFactory
              │                       │                      │
              ▼                       │                      ▼
     SSLContext (client)              │             SSLContext (server)
              │                       │                      │
              ▼                       │                      ▼
       SSLSocketFactory               │             SSLServerSocketFactory
              │                       │                      │
              ▼                       │                      ▼
         SSLSocket  ───── TCP + TLS handshake ────── SSLServerSocket
              │                                               │
              │                                               ▼ accept()
              └────────── encrypted TLS records ──────── SSLSocket
                              │                                 │
                      Application I/O                    Application I/O
```

Luồng tư duy:

1. **`SSLContext`** là nguồn cấu hình mật mã và quản lý session dùng để sản sinh socket/engine; nó **không phải** kết nối TCP.
2. **Factory** lấy cấu hình từ context và tạo socket phù hợp. Một factory có thể được tái sử dụng để tạo **nhiều** socket.
3. **`SSLServerSocket`** chỉ **bind, listen, accept**. Nó không là luồng trao đổi dữ liệu ứng dụng với mọi client; mỗi `accept()` trả về một socket TLS riêng.
4. **`SSLSocket`** đại diện cho **một kết nối**, có trạng thái handshake/session và `InputStream`, `OutputStream`.
5. Sau khi handshake hoàn tất, byte viết vào stream ứng dụng được JSSE đóng gói trong **TLS records** trước khi đi qua TCP; byte đọc ra là plaintext **sau khi TLS xử lý**.

TLS bổ sung bảo mật truyền thông. **Nó không thay thế** protocol framing: `SSLSocket.getInputStream()` vẫn là byte stream; nếu ứng dụng gửi nhiều thông điệp, phải định nghĩa length-prefix, delimiter hoặc protocol như HTTP.

## 3. Các class, vai trò và vòng đời

| Thành phần | Loại/đặc tính | Được tạo bằng | Vòng đời thường gặp |
| --- | --- | --- | --- |
| `SSLContext` | Bối cảnh TLS; quản lý cấu hình `KeyManager`, `TrustManager` và state TLS | `SSLContext.getInstance("TLS")` + `init(...)`; hoặc `getDefault()` | Khởi tạo khi ứng dụng/module bắt đầu, dùng lại nếu cùng policy |
| `SSLSocketFactory` | Factory cho client socket TLS | `context.getSocketFactory()` | Có thể tái sử dụng để mở nhiều kết nối |
| `SSLSocket` client | Socket TCP được TLS bảo vệ | `factory.createSocket(host, port)` | Một kết nối; handshake, I/O, close |
| `SSLServerSocketFactory` | Factory cho TLS server listener | `context.getServerSocketFactory()` | Có thể tạo một/nhiều listener |
| `SSLServerSocket` | Listening socket TLS; các cấu hình TLS thường áp dụng cho socket accept sau đó | `serverFactory.createServerSocket(port, backlog, bindAddress)` | Bind/listen/accept tới khi server dừng |
| `SSLSocket` server side | Socket TLS của **một client đã được accept** | `(SSLSocket) listener.accept()` | Một client; handshake, I/O, close |
| `SSLSession` | Thông tin của TLS session đã thương lượng | `socket.getSession()` sau handshake | Được TLS quản lý; có thể phục vụ session reuse/resumption |

`SSLSocket` **extends `java.net.Socket`**, còn `SSLServerSocket` **extends `java.net.ServerSocket`**. JSSE triển khai socket dựa trên TCP cho TLS; hai class này không phải một `DatagramSocket` UDP và không đại diện cho nonblocking NIO `SocketChannel`.

**Sai lầm hay gặp:** gọi `SSLContext.getInstance("TLS")` rồi nghĩ mình đã có kết nối được bảo vệ. Context cần được khởi tạo, sau đó tạo factory/socket, kết nối tới peer và hoàn thành TLS handshake với xác thực phù hợp.

## 4. SSLContext: nền tảng cấu hình TLS

`javax.net.ssl.SSLContext` được tạo theo tên giao thức/provider:

```java
SSLContext context = SSLContext.getInstance("TLS");
context.init(keyManagers, trustManagers, new SecureRandom());
```

Đây là **mảnh code**; `keyManagers` có kiểu `KeyManager[]`, `trustManagers` kiểu `TrustManager[]`. Trong ứng dụng cụ thể, các mảng này được tạo bằng `KeyManagerFactory` và `TrustManagerFactory`; ví dụ hoàn chỉnh ở mục 12.

Ba đối số của `init(...)`:

1. **`KeyManager[]`:** chọn khóa riêng và chuỗi chứng chỉ **của chính endpoint** để đưa ra khi cần. Server TLS xác thực bằng chứng chỉ thường **phải có** private key tương ứng. Client mTLS cũng cần key manager để gửi chứng chỉ client.
2. **`TrustManager[]`:** xác định có tin chứng chỉ của **peer** không. Client TLS thường cần trust manager để xác minh chứng chỉ server; server mTLS cần trust manager để xác minh client.
3. **`SecureRandom`:** nguồn ngẫu nhiên an toàn phục vụ hoạt động mật mã. Có thể truyền `null` để provider dùng mặc định; trong demo truyền `new SecureRandom()` cho minh bạch.

`SSLContext.getDefault()` lấy context mặc định đang được cấu hình cho JVM. `SSLContext.getInstance("TLS")` tạo context theo provider rồi cần `init(...)` trước khi gọi factory. Không nhầm `getDefault()` (đã được khởi tạo mặc định) với một context vừa `getInstance` chưa init.

### Vì sao dùng `"TLS"` thay vì `"SSL"`?

Trong JSSE, `"TLS"` là tên thuật toán context thông dụng để chọn họ TLS; những phiên bản giao thức thực sự được phép sử dụng còn chịu ảnh hưởng của provider/JDK và `SSLSocket.setEnabledProtocols(...)` hoặc `SSLParameters`. Trong Java 17 tiêu chuẩn, TLSv1.2 được yêu cầu hỗ trợ; TLSv1.3 được hỗ trợ bởi JDK Oracle/OpenJDK phổ biến nhưng phải kiểm tra provider và security policy khi dùng môi trường tùy biến.

Ví dụ sau đặt `TLSv1.3` **trên socket/listener** để minh họa rõ một phiên bản hiện đại; không nên bật lại SSLv3/TLSv1.0/TLSv1.1 để chạy với hệ thống cũ. Khi hệ thống yêu cầu tương thích, xét TLSv1.2 với policy ciphers hiện đại và kế hoạch nâng cấp.

### Một context hay nhiều context?

Có thể tái sử dụng một `SSLContext` cho nhiều kết nối có **chung nguồn identity/trust và policy**. Nhưng khi các dịch vụ cần truststore hay client certificate khác nhau, việc tạo **context riêng theo endpoint/policy** giúp tránh vô tình mở rộng trust: ví dụ client service A chỉ tin CA A, service B chỉ tin CA B.

Không nên thay đổi global `SSLContext.setDefault(...)` để điều chỉnh TLS của một kết nối riêng, vì nó có thể ảnh hưởng các component khác trong cùng JVM. Ưu tiên tạo context rõ ràng rồi truyền factory đến component sử dụng nó.

## 5. KeyStore, TrustStore và Certificate khác nhau thế nào?

**Keystore** và **truststore** thường đều là file Java `KeyStore` như `PKCS12`; khác biệt chính là **mục đích dữ liệu và cách sử dụng**:

| Khái niệm | Chứa gì? | Ai sử dụng? | Dùng làm gì? |
| --- | --- | --- | --- |
| Server keystore | Private key server + chuỗi certificate tương ứng | `KeyManagerFactory` phía server | Chứng minh server sở hữu private key của public cert |
| Client truststore | Trusted CA/root hoặc trusted certificate (trong demo là cert self-signed cụ thể) | `TrustManagerFactory` phía client | Đánh giá trust chain của chứng chỉ server |
| Client keystore (mTLS) | Private key client + client cert chain | `KeyManagerFactory` phía client | Client chứng minh danh tính cho server |
| Server truststore (mTLS) | Những CA/chứng chỉ client được server tin | `TrustManagerFactory` phía server | Kiểm tra client cert khi bật client auth |

**Private key** tuyệt đối không được chuyển vào client truststore của bên khác. Truststore của demo chỉ chứa **public certificate**, không chứa private key server. Certificate chứa public key/identity và thông tin ký, khác với private key.

`KeyManagerFactory` đọc identity:

```java
KeyStore identityStore = KeyStore.getInstance("PKCS12");
try (InputStream in = Files.newInputStream(Path.of("server.p12"))) {
    identityStore.load(in, storePassword);
}
KeyManagerFactory kmf = KeyManagerFactory.getInstance(
        KeyManagerFactory.getDefaultAlgorithm());
kmf.init(identityStore, keyPassword);
KeyManager[] keyManagers = kmf.getKeyManagers();
```

`TrustManagerFactory` đọc trust anchors:

```java
KeyStore trustedStore = KeyStore.getInstance("PKCS12");
try (InputStream in = Files.newInputStream(Path.of("client-trust.p12"))) {
    trustedStore.load(in, storePassword);
}
TrustManagerFactory tmf = TrustManagerFactory.getInstance(
        TrustManagerFactory.getDefaultAlgorithm());
tmf.init(trustedStore);
TrustManager[] trustManagers = tmf.getTrustManagers();
```

Hai đoạn trên là **mảnh code**; cần imports từ `java.security`, `java.nio.file`, `java.io` và `javax.net.ssl` và biến password `char[]`. Đừng đọc password nguồn production dưới dạng literal trong source. Dùng secrets manager, permission file và cơ chế secret rotation được vận hành an toàn.

Một client dùng root CA trong truststore **vẫn phải xác minh hostname**. Tin chuỗi chứng chỉ của CA chứng minh cert do CA tin cậy ký; nó **chưa chứng minh** cert thuộc đúng hostname mà client định kết nối. Phần này đặc biệt quan trọng khi dùng `SSLSocket` trực tiếp.

## 6. SSLSocketFactory: tạo TLS client socket

Lấy factory từ context đã khởi tạo:

```java
SSLSocketFactory factory = clientContext.getSocketFactory();
try (SSLSocket socket = (SSLSocket)
        factory.createSocket("api.example.com", 443)) {
    // cấu hình SSLParameters, timeout, rồi handshake và I/O
}
```

Đây là mảnh code. `createSocket(host, port)` tạo socket TCP gắn với peer, dùng JSSE để thực hiện TLS. Kết nối TCP có thể được mở trong quá trình tạo socket, còn TLS handshake thường bắt đầu khi gọi `startHandshake()` hoặc thao tác I/O đầu tiên; vì vậy muốn fail-fast và tách rõ lỗi TLS, hãy cấu hình các tham số trước rồi **gọi `startHandshake()` tường minh**.

Factory cũng có overload cho `Socket` đã kết nối:

```java
SSLSocket tls = (SSLSocket) factory.createSocket(
        plainConnectedSocket, "api.example.com", 443, true);
```

Đây là mảnh code cho tình huống **layer TLS trên một socket TCP đã kết nối**. Tham số hostname phải là **đích dự kiến được xác thực**; không thay bằng địa chỉ giả hoặc host không đáng tin chỉ để vượt qua tên chứng chỉ. `autoClose=true` giúp đóng socket nền khi socket TLS đóng theo semantics overload đó. Cần đặt endpoint identification và các TLS parameters **trước handshake**.

`SSLSocketFactory.getDefault()` cũng có thể tạo TLS socket dựa trên **context mặc định của JVM**. Cách này tiện khi truststore/policy toàn ứng dụng đã được vận hành đúng, nhưng không cho phép client chỉ tin một tập CA chuyên biệt theo dịch vụ nếu không có cấu hình tương ứng.

### Không nhầm factory với connection

Một `SSLSocketFactory` không gắn duy nhất với một connection. Với 1.000 request độc lập, có thể dùng **cùng factory/context** để tạo 1.000 `SSLSocket` khác nhau, mỗi socket có trạng thái, handshake và vòng đời riêng. Mỗi `SSLSocket` phải được close theo chính connection đó.

## 7. SSLSocket: kết nối TLS và các API quan trọng

`SSLSocket` cung cấp API socket stream và tùy chỉnh TLS:

| Phương thức | Vai trò | Thời điểm dùng |
| --- | --- | --- |
| `setSSLParameters(SSLParameters)` | Thiết lập tập tham số TLS, endpoint identification, ALPN, SNI hoặc policy khác | **Trước handshake** |
| `setEnabledProtocols(String[])` | Hạn chế phiên bản TLS được bật | Trước handshake |
| `setEnabledCipherSuites(String[])` | Hạn chế cipher suites | Chỉ khi có policy rõ; tránh chọn suite cũ/yếu |
| `setSoTimeout(int millis)` | Timeout trên thao tác đọc blocking | Trước read/handshake theo nhu cầu |
| `startHandshake()` | Bắt đầu TLS handshake một cách tường minh | Sau khi cấu hình, trước application data |
| `getSession()` | Truy cập protocol/cipher/session đã thương lượng | Sau handshake thành công |
| `getInputStream()` | Nhận plaintext application bytes đã TLS bảo vệ trên wire | Sau/đồng thời handshake theo contract |
| `getOutputStream()` | Gửi plaintext app bytes cho JSSE mã hóa trên wire | Sau/đồng thời handshake |
| `close()` | Đóng socket và tài nguyên liên quan | Cuối vòng đời |

**TLS là stream có bảo vệ mật mã, không phải message queue.** Nếu gửi một lần `write("HELLO")`, receiver có thể đọc byte theo nhiều lần `read` khác nhau. Phải dùng framing ở tầng ứng dụng (newline, length-prefix, HTTP...) giống TCP.

**`setSoTimeout` không phải timeout kết nối TCP tổng thể**: nó chủ yếu chi phối read blocking; cần thiết kế thêm connect timeout, handshake deadline tổng thể và timeout xử lý nghiệp vụ. Trong server lớn, đừng để một peer chiếm thread vô hạn trong handshake hay read.

### Client/server mode

`SSLSocket` có chế độ client hoặc server, được điều khiển bởi `setUseClientMode(...)` trước handshake. Socket tạo từ `SSLSocketFactory` thường ở client mode; socket accept từ `SSLServerSocket` thường ở server mode. TLS handshake cần hai bên ở vai trò phù hợp. Không đổi mode sau khi handshake đã bắt đầu.

`SSLSocket` cũng hỗ trợ `setNeedClientAuth(...)`/`setWantClientAuth(...)` ở **server mode** khi yêu cầu client certificate. Các tùy chọn này không tự cấp private key/truststore; phải chuẩn bị tương ứng trong `SSLContext`.

## 8. SSLServerSocket: listener chờ kết nối TLS

Phía server lấy factory từ **server SSLContext** đã được cấu hình với private key:

```java
SSLServerSocketFactory serverFactory =
        serverContext.getServerSocketFactory();
try (SSLServerSocket listener = (SSLServerSocket)
        serverFactory.createServerSocket(8443)) {
    listener.setEnabledProtocols(new String[]{"TLSv1.3"});

    try (SSLSocket peer = (SSLSocket) listener.accept()) {
        peer.startHandshake();
        // đọc/ghi ứng dụng trên peer, không trên listener
    }
}
```

Đây là mảnh code, giả định `serverContext` tồn tại. `listener` là listener lắng nghe trên port 8443; `peer` là socket được tạo **riêng cho một client**. Không viết dữ liệu request vào `SSLServerSocket`; lớp này không có ứng dụng stream cho một client cụ thể.

`SSLServerSocket` giống `ServerSocket` về bind/backlog/accept:
- Có thể tạo với port `0` để OS cấp ephemeral port trong test, rồi đọc `getLocalPort()`.
- Có thể bind tới địa chỉ loopback để không cho máy khác truy cập.
- `setSoTimeout(...)` trên **listener** giới hạn chờ `accept()`; `setSoTimeout(...)` trên accepted `SSLSocket` giới hạn read của peer, là hai đối tượng/tác dụng khác nhau.
- Server cần vòng accept và quản lý concurrency/connection limit trong hệ thống thực tế.

Các thiết lập `SSLServerSocket` như enabled protocols, cipher suites và client auth thường được kế thừa khi tạo accepted TLS sockets. Đặt chúng **trước khi accept** để kết nối mới dùng policy đúng. Kết nối đã được accept có thể có các tham số riêng cần thiết lập trước handshake.

**Cần key server thật:** tạo `SSLServerSocket` từ context không có private key thích hợp có thể bind/accept được nhưng **TLS handshake sẽ thất bại** vì server không xuất trình được chứng chỉ/credentials đáp ứng cipher suite.

## 9. TLS handshake làm gì và bắt đầu khi nào?

TLS handshake thiết lập thông số chung và xác thực trước khi application data được trao đổi có ý nghĩa. Mô tả đơn giản cho server-authenticated TLS 1.3:

```text
Client                                         Server
  │                                              │
  ├── ClientHello (versions, cipher suites, …) ──►│
  │◄─ ServerHello (chọn thông số, key share, …) ──┤
  │◄─ Các thông điệp TLS 1.3 được bảo vệ và       │
  │   chứng chỉ server / bằng chứng sở hữu key ──┤
  │                                              │
  │  Client xác minh trust chain + danh tính đích│
  │  nếu cấu hình endpoint identification đúng  │
  │                                              │
  ├── Finished và hoàn tất handshake ───────────►│
  │                                              │
  ◄──────── TLS-protected application data ──────►
```

Sơ đồ cố tình lược bỏ nhiều thông điệp và tùy chọn. Chi tiết khác nhau giữa TLSv1.2 và TLSv1.3 và giữa full/resumed handshake. **Không** suy từ sơ đồ rằng ứng dụng có quyền tự bỏ qua bước xác minh chứng chỉ hoặc đổi algorithm.

Trong JSSE, gọi `socket.startHandshake()` làm rõ ranh giới:
- Nếu handshake **thành công**, socket đã thương lượng protocol/cipher suite và thỏa những kiểm tra trust/endpoint theo cấu hình.
- Nếu handshake **thất bại**, thường nhận `SSLHandshakeException`, `SSLProtocolException`, `SSLException` hoặc lỗi I/O liên quan. Không tiếp tục application protocol như thể kết nối an toàn.
- Nếu không gọi tường minh, handshake có thể tự bắt đầu khi read/write đầu tiên; khi đó lỗi xuất hiện trong đường xử lý dữ liệu, dễ gây nhầm.

`getSession().getProtocol()` và `getSession().getCipherSuite()` hữu ích cho quan sát TLS thực sự đã thương lượng, nhưng **không tự chứng minh hostname đúng** nếu ứng dụng đã bỏ qua endpoint identification.

## 10. Xác minh danh tính server: trust chain khác hostname

Client TLS phải xác minh **hai lớp**:

1. **Certificate trust:** chuỗi certificate được `TrustManager` tin theo trust anchors và security policy.
2. **Endpoint identity:** certificate được cấp cho **hostname/IP thực sự dự kiến kết nối**; thường kiểm tra SAN (Subject Alternative Name). Đối với TLS kết nối HTTP/HTTPS, thuật toán endpoint identification `"HTTPS"` áp dụng quy tắc xác minh danh tính HTTP server.

Trong `SSLSocket` trực tiếp, **đừng mặc định** rằng hostname verification luôn được bật chỉ vì đã dùng TLS. Hãy cấu hình rõ ràng trước handshake:

```java
SSLParameters params = socket.getSSLParameters();
params.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(params);
socket.startHandshake();
```

Mảnh code trên giả định `socket` là client `SSLSocket` đã được tạo. Theo Java Security Standard Algorithm Names, `"HTTPS"` là tên thuật toán endpoint identification tiêu chuẩn. Trong ví dụ hoàn chỉnh, client kết nối địa chỉ **`127.0.0.1`** và certificate server chứa **SAN kiểu IP:127.0.0.1**, nên bước kiểm tra có thể thành công.

Những sai sót thường gặp:
- Server certificate do CA được tin cậy ký **nhưng thuộc domain khác**. Chuỗi tin cậy vẫn có thể hợp lệ, song endpoint identity phải từ chối.
- Chứng chỉ cho DNS `localhost` **không tự động** thay thế IP SAN `127.0.0.1` khi client thực sự dùng địa chỉ IP. Cần SAN theo kiểu danh tính đang kết nối.
- Dùng `SSLSocketFactory.createSocket(ip, port)` cho IP nhưng cố dùng hostname khác để bypass kiểm tra chứng chỉ là sai về an toàn; nếu cần kết nối tới IP định tuyến cố định nhưng vẫn xác thực hostname, thiết kế transport/layered socket và TLS peer host/SNI cho chính danh tính được phép.
- Tự tạo `X509TrustManager` chấp nhận tất cả certificate hoặc tắt hostname verification để “sửa” lỗi handshake **làm mất bảo vệ chống giả mạo server**.

Nếu chương trình dùng API HTTP cấp cao như `java.net.http.HttpClient` hoặc `HttpsURLConnection`, các lớp đó có cơ chế kiểm tra endpoint cho HTTPS. Không tự thay chúng bằng cấu hình bypass hostname verification. Khi cần custom TLS truststore cho HTTP client, có thể cấu hình `HttpClient.newBuilder().sslContext(context)` thay vì tự implement toàn bộ HTTP qua socket thô.

## 11. Chuẩn bị certificate và truststore cho bài thực hành localhost

Ta sẽ tạo một **server keypair tự ký, chỉ để học trên máy cục bộ**, xuất **public certificate** rồi import vào truststore phía client. Không dùng trust manager “tin tất cả”, không kết nối Internet và không yêu cầu chứng chỉ từ CA công khai.

Điều kiện:
- Cài **JDK 17 trở lên**, có lệnh `javac`, `java` và `keytool` trong PATH.
- Thư mục demo có thể ghi file.
- Loopback `127.0.0.1` cho phép bind TCP local.
- JSSE provider hỗ trợ `TLSv1.3` (môi trường JDK 17 thông thường).

Tạo thư mục trống riêng rồi chạy từng **lệnh một dòng** (đều là CLI `keytool`):

```bash
keytool -genkeypair -alias local-server -keyalg RSA -keysize 2048 -validity 7 -dname "CN=localhost" -ext "SAN=IP:127.0.0.1,DNS:localhost" -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -noprompt

keytool -exportcert -alias local-server -keystore server.p12 -storepass changeit -rfc -file server-cert.pem

keytool -importcert -noprompt -alias local-server -file server-cert.pem -keystore client-trust.p12 -storetype PKCS12 -storepass changeit
```

Sau đó, thư mục có:

```text
server.p12          server private key + server certificate
server-cert.pem     chỉ public certificate được export
client-trust.p12    trusted public certificate; KHÔNG có server private key
```

Giải thích:
- `-alias local-server` định danh entry.
- `-keyalg RSA -keysize 2048` tạo keypair RSA cho ví dụ; production phải theo tiêu chuẩn mật mã và policy tổ chức.
- `-validity 7` cấp thời hạn 7 ngày cho cert demo, tránh nhầm đây là chứng chỉ vận hành lâu dài.
- `-ext SAN=IP:127.0.0.1,DNS:localhost` khai báo **hai danh tính**; client demo kết nối IP nên dùng IP SAN.
- `-storetype PKCS12` dùng định dạng chuẩn chứa entry khóa/chứng chỉ.
- `-storepass changeit -keypass changeit` là **mật khẩu demo công khai, không có tính bảo mật**, tuyệt đối không dùng trong production hay đưa vào source code thật.
- `-exportcert` chỉ xuất certificate, không xuất private key.
- `-importcert` làm client tin **certificate demo này** theo truststore được cấu hình; không làm mọi server trở nên đáng tin.

Có thể kiểm tra SAN:

```bash
keytool -list -v -keystore server.p12 -storepass changeit -alias local-server
```

Tìm phần `SubjectAlternativeName` có `IPAddress: 127.0.0.1` và `DNSName: localhost`. Nếu keytool yêu cầu xác nhận vì file đã có hoặc alias bị trùng, hãy dùng một thư mục demo sạch; **không xóa hoặc ghi đè keystore production** để chạy bài.

### Vì sao không dùng default truststore?

Certificate tự ký mới tạo **không nằm trong danh sách CA hệ thống/JVM tin tưởng**. Nếu client dùng default `TrustManager`, handshake sẽ thất bại đúng thiết kế. Ta import public cert vào **truststore riêng cho bài demo** và đưa nó vào `clientContext`. Trong production, dùng CA/chứng chỉ được tổ chức quản lý, rotation và revocation theo policy; việc tin leaf certificate tự ký chỉ là phương án học tập trên loopback.

## 12. Chương trình Java 17+ chạy được: SSLContext → factories → sockets

Lưu đúng tên file **`LocalTlsEchoDemo.java`** vào **cùng thư mục** với `server.p12` và `client-trust.p12` đã tạo ở mục 11.

```java
import java.io.BufferedReader;
import java.io.BufferedWriter;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.net.InetAddress;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.concurrent.atomic.AtomicReference;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLServerSocketFactory;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSocketFactory;
import javax.net.ssl.TrustManagerFactory;

public class LocalTlsEchoDemo {
    private static final char[] PASSWORD = "changeit".toCharArray();

    private static KeyStore loadStore(String filename) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(Path.of(filename))) {
            store.load(in, PASSWORD);
        }
        return store;
    }

    private static SSLContext serverContext() throws Exception {
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(loadStore("server.p12"), PASSWORD);
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(kmf.getKeyManagers(), null, new SecureRandom());
        return context;
    }

    private static SSLContext clientContext() throws Exception {
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(loadStore("client-trust.p12"));
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(null, tmf.getTrustManagers(), new SecureRandom());
        return context;
    }

    public static void main(String[] args) throws Exception {
        SSLServerSocketFactory serverFactory =
                serverContext().getServerSocketFactory();
        InetAddress address = InetAddress.getByName("127.0.0.1");
        try (SSLServerSocket listener = (SSLServerSocket)
                serverFactory.createServerSocket(0, 10, address)) {
            listener.setEnabledProtocols(new String[]{"TLSv1.3"});
            listener.setSoTimeout(5000);

            AtomicReference<Throwable> serverFailure = new AtomicReference<>();
            Thread server = new Thread(() -> {
                try (SSLSocket socket = (SSLSocket) listener.accept()) {
                    socket.setSoTimeout(5000);
                    socket.startHandshake();
                    BufferedReader reader = new BufferedReader(
                            new InputStreamReader(socket.getInputStream(),
                                    StandardCharsets.UTF_8));
                    BufferedWriter writer = new BufferedWriter(
                            new OutputStreamWriter(socket.getOutputStream(),
                                    StandardCharsets.UTF_8));
                    String request = reader.readLine();
                    writer.write("ACK:" + request);
                    writer.newLine();
                    writer.flush();
                } catch (Throwable ex) {
                    serverFailure.set(ex);
                }
            });
            server.start();

            SSLSocketFactory clientFactory = clientContext().getSocketFactory();
            try (SSLSocket socket = (SSLSocket)
                    clientFactory.createSocket("127.0.0.1",
                            listener.getLocalPort())) {
                socket.setSoTimeout(5000);
                SSLParameters params = socket.getSSLParameters();
                params.setProtocols(new String[]{"TLSv1.3"});
                params.setEndpointIdentificationAlgorithm("HTTPS");
                socket.setSSLParameters(params);
                socket.startHandshake();

                BufferedWriter writer = new BufferedWriter(
                        new OutputStreamWriter(socket.getOutputStream(),
                                StandardCharsets.UTF_8));
                BufferedReader reader = new BufferedReader(
                        new InputStreamReader(socket.getInputStream(),
                                StandardCharsets.UTF_8));
                writer.write("ping");
                writer.newLine();
                writer.flush();
                String reply = reader.readLine();
                System.out.println("TLS=" + socket.getSession().getProtocol());
                System.out.println("reply=" + reply);
            }

            server.join(6000);
            if (server.isAlive()) {
                throw new IllegalStateException("Server did not finish");
            }
            if (serverFailure.get() != null) {
                throw new IllegalStateException("Server failed",
                        serverFailure.get());
            }
        }
    }
}
```

Đây là **file Java độc lập hoàn chỉnh**. Chạy trong thư mục có hai `.p12`:

```bash
javac LocalTlsEchoDemo.java
java LocalTlsEchoDemo
```

Trong môi trường Java 17 hỗ trợ TLSv1.3, keytool files hợp lệ và kết nối loopback thành công, stdout:

```text
TLS=TLSv1.3
reply=ACK:ping
```

Đã kiểm chứng chương trình với `javac --release 17` và chạy thực tế trên JDK hỗ trợ TLSv1.3; output đúng như trên.

### Đọc code từ server sang client

**Server:**
1. `loadStore("server.p12")` load private key + certificate server.
2. `KeyManagerFactory.init(...)` tạo `KeyManager[]` để chọn identity khi TLS handshake.
3. `serverContext()` tạo context TLS với các `KeyManager`; server chưa yêu cầu client certificate nên context không cần custom truststore cho mTLS.
4. `getServerSocketFactory()` tạo server factory từ context.
5. `createServerSocket(0, 10, address)` bind listener vào loopback, port OS cấp động; backlog được đặt 10 cho demo.
6. `listener.setEnabledProtocols({"TLSv1.3"})` hạn chế handshake của accepted sockets theo ví dụ.
7. `accept()` trả một `SSLSocket` server side; `startHandshake()` cho server tham gia handshake.
8. Server đọc **một dòng** `ping` và gửi `ACK:ping`; dấu newline là **framing ở tầng ứng dụng**, không do TLS tự tạo.

**Client:**
1. `loadStore("client-trust.p12")` load **trusted public certificate** của server.
2. `TrustManagerFactory.init(...)` tạo các trust managers để kiểm tra certificate peer.
3. `clientContext()` khởi tạo context TLS với trust manager vừa chọn; client không có certificate riêng trong demo.
4. `getSocketFactory()` tạo client factory.
5. `createSocket("127.0.0.1", listener.getLocalPort())` kết nối TCP tới listener.
6. `params.setProtocols({"TLSv1.3"})` và `setEndpointIdentificationAlgorithm("HTTPS")` đặt chính sách **trước handshake**.
7. `startHandshake()` kiểm tra trust + IP SAN tương ứng, rồi mới gửi application data.
8. `getSession().getProtocol()` cho biết phiên bản TLS thực sự được thương lượng; phần trả lời được đọc qua `InputStream` đã TLS xử lý.

### Vì sao demo có hai context khác nhau?

Server **sở hữu private key** và cần `KeyManagerFactory`. Client **tin public certificate của server** và cần `TrustManagerFactory`. Mỗi bên có vai trò bảo mật riêng, không nên “đưa hết keystore vào cả hai bên” chỉ để handshake qua được.

### Vì sao dùng hai luồng Java?

`SSLServerSocket.accept()` là thao tác blocking chờ client. Nếu chạy accept rồi mới gọi client connect trong **cùng** main thread, chương trình sẽ chờ mãi. Demo dùng một thread server cho đúng một kết nối, main thread đóng vai client. Đây là **cách tổ chức test**, không phải kiến trúc tối ưu cho production server nhiều client.

`serverFailure` giữ lỗi phía server, còn `server.join(6000)` bảo đảm main quan sát kết quả server trước khi kết thúc. Timeout 5–6 giây chỉ là ngưỡng của demo và có thể phải điều chỉnh ở môi trường tải nặng.

## 13. Phân biệt TCP socket, TLS socket và dữ liệu ứng dụng

Với `SSLSocket`, code application vẫn dùng `InputStream` và `OutputStream` giống `Socket`, nhưng JSSE đứng giữa ứng dụng và TCP:

```text
Client application                Server application
      │                                  ▲
      ▼ write("ping\n")                  │ readLine() => "ping"
   SSLSocket                              SSLSocket
      │ encrypt + tag                       ▲ decrypt + verify
      ▼                                     │
   TLS records  ─────── TCP stream ────────┘
```

Một `writer.write("ping")` không tương ứng bắt buộc một TCP segment hoặc TLS record. Một `reader.readLine()` đọc tới newline theo framing ứng dụng; nó có thể cần nhiều lượt đọc byte từ TLS socket. TLS đảm bảo tính bí mật và toàn vẹn dữ liệu trong kênh đã xác thực theo policy, nhưng **không** phân biệt “message số 1” và “message số 2” nếu ứng dụng không tự khai báo ranh giới.

Ở ví dụ dùng newline để framing, nếu payload nghiệp vụ có newline tùy ý thì protocol phải escape hoặc chuyển sang length-prefix. Không giải mã UTF-8 theo các chunk byte ngẫu nhiên nếu có khả năng cắt giữa code point; hãy dùng decoder/reader đúng loại hoặc đọc trọn frame.

Một ghi chú về `TLSv1.3`: dữ liệu truyền trên wire không phải `ping` ở dạng plaintext; TLS record chứa ciphertext. Nếu dùng Wireshark trên loopback không có key logging hợp lệ, sẽ không đọc được payload từ capture chỉ vì đã biết port.

## 14. SSLSession: kiểm tra phiên đã thương lượng

Sau handshake thành công:

```java
SSLSession session = socket.getSession();
String protocol = session.getProtocol();
String cipherSuite = session.getCipherSuite();
Principal peer = session.getPeerPrincipal();
```

Đây là mảnh code; imports `javax.net.ssl.SSLSession` và `java.security.Principal`, biến `socket` là `SSLSocket`. `getPeerPrincipal()` yêu cầu peer đã được xác thực thích hợp; nếu không có authenticated peer, có thể ném `SSLPeerUnverifiedException`. Không giả định server luôn xác thực client trong TLS một chiều.

`getSession().getProtocol()` ví dụ trả `"TLSv1.3"`. Cipher suite cụ thể phụ thuộc provider, danh sách thuật toán và chính sách máy, nên **không ghi một stdout cipher suite cố định** nếu chưa cố định môi trường.

TLS có thể hỗ trợ session resumption để giảm chi phí handshake. `SSLContext`/session context có thể duy trì cache theo provider. Không tự kết luận mỗi `SSLSocket` mới sẽ phải thực hiện một full handshake; ngược lại, không dựa vào resumption để bỏ kiểm tra endpoint/authorization cần thiết.

### Vì sao không chỉ nhìn `getCipherSuite()` rồi cho rằng an toàn?

Một cipher suite mạnh **không chứng minh** đã kết nối đúng máy nếu trust/hostname được cấu hình sai. Các lớp bảo mật cần đồng thời: protocol version, cipher suites được phép, certificate chain, endpoint identity, routing/hostname chính xác và ứng dụng xử lý dữ liệu theo chính sách.

## 15. mTLS: khi server cũng xác thực certificate của client

TLS server-authenticated (demo) thường chỉ bắt client kiểm tra danh tính server. **Mutual TLS (mTLS)** yêu cầu server cũng xác thực client certificate. Cần **đủ bốn loại dữ liệu**:

```text
Server:
  KeyManager  -> server private key + server cert chain
  TrustManager -> tin CA/certificate của client

Client:
  KeyManager  -> client private key + client cert chain
  TrustManager -> tin CA/certificate của server
```

Phía server bật yêu cầu client cert **trước handshake/accept**:

```java
SSLServerSocket listener = ...; // tạo từ server SSLContext
listener.setNeedClientAuth(true);
```

Đây là mảnh code. `setNeedClientAuth(true)` yêu cầu client xuất trình credential phù hợp; nếu client không có certificate được server tin cậy, handshake thất bại. `setWantClientAuth(true)` chỉ **yêu cầu nhưng không bắt buộc** client authentication trong nhiều tình huống. Chọn `need` hay `want` theo policy rõ, không dùng want rồi tự coi như mọi client đều đã xác thực.

Để mTLS thật sự hoạt động:
- Server `SSLContext.init(serverKeyManagers, serverTrustManagers, ...)`.
- Client `SSLContext.init(clientKeyManagers, clientTrustManagers, ...)`.
- Server phải kiểm tra/ủy quyền **client identity** tương ứng với chứng chỉ, không chỉ chấp nhận “một chứng chỉ bất kỳ do CA được tin ký”.
- Client vẫn phải kiểm tra server hostname, chain và TLS policy.

**Không bật `setNeedClientAuth(true)` trong `LocalTlsEchoDemo` rồi kỳ vọng nó vẫn chạy:** client của demo không có keypair/cert client, và server không cấu hình truststore xác thực client. Muốn mở rộng demo thành mTLS phải chủ động tạo thêm client keystore, server truststore và context hai chiều.

mTLS giải quyết một lớp xác thực peer, **không tự phân quyền API**. Sau handshake, service vẫn cần policy theo danh tính, vai trò, resource và request.

## 16. SSLParameters: protocol, cipher suite, SNI, ALPN và hostname

`SSLParameters` là tập thông số có thể áp lên socket trước handshake:

```java
SSLParameters params = socket.getSSLParameters();
params.setProtocols(new String[]{"TLSv1.3"});
params.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(params);
```

Mảnh code trên bảo đảm hai chính sách được đặt trước handshake. Cũng có thể dùng `socket.setEnabledProtocols(...)`, nhưng khi dùng cả hai cách, hãy tránh cấu hình chồng chéo khó bảo trì.

### TLS versions và cipher suites

- `getSupportedProtocols()` cho biết provider hỗ trợ những phiên bản nào; `getEnabledProtocols()` cho biết phiên bản đang bật trên socket.
- `getSupportedCipherSuites()` và `getEnabledCipherSuites()` tương tự đối với cipher suites. **Supported không đồng nghĩa enabled** hoặc được phép bởi security policy.
- Các thuật toán/phiên bản không an toàn có thể bị chặn bởi `jdk.tls.disabledAlgorithms` trong cấu hình JDK. Không xóa/chỉnh policy này chỉ để handshake với peer lỗi thời.
- Thông thường để JDK/provider chọn cipher suites an toàn theo policy, chỉ override khi có yêu cầu tuân thủ cụ thể và đã test tương thích.

### SNI (Server Name Indication)

Khi kết nối qua DNS hostname, client TLS có thể gửi **SNI** để server có nhiều virtual host chọn đúng certificate. Trường hợp demo kết nối **IP literal** trên loopback, không cần SNI. Trong production, hãy truyền hostname thật cần xác thực thay vì chỉ IP rồi phàn nàn server chọn sai cert.

`SSLParameters.setServerNames(...)` dùng để cấu hình server names tường minh khi có lý do phù hợp; đừng coi SNI là kiểm tra bảo mật thay thế trust/hostname. SNI thông báo tên mong muốn cho server, trong khi certificate validation chứng minh peer được tin và danh tính phù hợp.

### ALPN (Application-Layer Protocol Negotiation)

ALPN cho phép hai bên thương lượng protocol ứng dụng (ví dụ `h2` hoặc `http/1.1`) trong TLS handshake:

```java
SSLParameters params = socket.getSSLParameters();
params.setApplicationProtocols(new String[]{"h2", "http/1.1"});
socket.setSSLParameters(params);
// Sau handshake: socket.getApplicationProtocol()
```

Đây là mảnh code; ALPN chỉ có kết quả có ý nghĩa khi **cả hai bên** hỗ trợ/đồng ý và có application protocol được triển khai phù hợp. Chỉ khai báo `"h2"` **không** biến stream bất kỳ thành HTTP/2; ứng dụng phải implement HTTP/2 framing hoặc dùng HTTP client/server chuyên dụng.

## 17. SSLContext mặc định và system properties

Trong một số chương trình, JSSE lấy cấu hình từ system properties/keystore/truststore mặc định:

```text
javax.net.ssl.keyStore
javax.net.ssl.keyStorePassword
javax.net.ssl.keyStoreType

javax.net.ssl.trustStore
javax.net.ssl.trustStorePassword
javax.net.ssl.trustStoreType
```

Cách cấu hình qua JVM properties tiện cho tiến trình mà chính sách TLS áp dụng toàn ứng dụng, nhưng cũng có rủi ro nếu nhiều thư viện trong cùng JVM cần **trust policy khác nhau**. Đặt global truststore sai có thể làm hàng loạt outbound connection bị lỗi hoặc quá rộng trust.

`SSLSocketFactory.getDefault()` và `SSLServerSocketFactory.getDefault()` dựa vào default SSL context/provider configuration. Nếu server không có keystore chứa private key/certificate thích hợp, default factory **không tự tạo certificate server an toàn**. Trong ví dụ local, ta tạo **serverContext riêng** từ `server.p12` để tránh phụ thuộc cấu hình JVM.

Cũng không nên gọi:

```java
SSLContext.setDefault(customContext);
```

chỉ để chỉnh một kết nối đơn lẻ. Đây là thay đổi trạng thái mặc định ở cấp JVM có thể ảnh hưởng thành phần khác. Thay vào đó dùng `customContext.getSocketFactory()` hoặc truyền context vào client framework hỗ trợ injection.

**Production:** đặt mật khẩu qua secret manager và cơ chế runtime an toàn. Mật khẩu trên command line hoặc trong source dễ bị đọc từ history, process list/log. Lệnh chứa `changeit` ở đây chỉ dùng trong thư mục demo cục bộ có dữ liệu tạm.

## 18. Timeout, close và quản lý tài nguyên

Một kết nối TLS có nhiều giai đoạn riêng:

```text
TCP connect
   ▼
TLS handshake
   ▼
Application request/response
   ▼
TLS close / TCP close
```

Không nên dùng một timeout duy nhất rồi coi đã bao phủ mọi thứ:
- **TCP connect timeout:** thời gian kết nối socket tới địa chỉ/port.
- **Handshake timeout:** thời gian TLS handshake chờ peer, certificate validation hoặc dữ liệu cần thiết. Với blocking socket, `setSoTimeout` giới hạn một số thao tác đọc, nhưng deadline tổng thể nên được quản lý theo kiến trúc.
- **Application read timeout:** không để peer gửi 1 byte rồi giữ connection mãi.
- **Write/overall deadline:** chặn gửi hoặc xử lý kéo dài ngoài policy.

Demo cấu hình `listener.setSoTimeout(5000)` cho `accept`, `socket.setSoTimeout(5000)` cho read của hai peer và `server.join(6000)` để test không treo lâu. **Các con số là minh họa**, không phải default phù hợp mọi môi trường.

### Đóng đúng loại tài nguyên

`try-with-resources` trên `SSLServerSocket` đóng listener khi server dừng; mỗi `SSLSocket` được đóng khi kết nối hoàn tất. Đóng listener **không phải** thay thế đóng mọi accepted socket. Trong server nhiều client, cần quản lý danh sách connection và shutdown/timeout riêng.

TLS có cơ chế thông báo đóng an toàn `close_notify`; việc socket kết thúc đột ngột hoặc peer không gửi close_notify có thể gây tình huống truncation. Ứng dụng vẫn phải dựa vào **framing/application length** để biết một message có đầy đủ không, chứ không coi mọi socket close là một message hoàn chỉnh.

Đừng log plaintext nhạy cảm, private key, password hoặc toàn bộ TLS debug trong production. Nếu tạm bật debug như `-Djavax.net.debug=ssl:handshake`, chỉ dùng trong môi trường được kiểm soát và bảo vệ log.

## 19. SSLSocket so với SSLEngine khi cần nonblocking NIO

`SSLSocket` là API socket TLS theo mô hình `Socket`/`InputStream`/`OutputStream`, thuận tiện cho chương trình blocking hoặc một thread-per-connection. Nó **không phải `SelectableChannel`** để đăng ký trực tiếp với `Selector` bằng `OP_READ/OP_WRITE`.

Nếu ứng dụng cần hàng nghìn kết nối TLS trong một `Selector`/`SocketChannel` nonblocking, dùng **`SSLEngine`** (từ `SSLContext.createSSLEngine(...)`) và tự tích hợp:

```text
SocketChannel TCP bytes
    │
    ▼
ByteBuffer network input
    │     SSLEngine.unwrap(...)
    ▼
ByteBuffer plaintext input  -> application parser

Application plaintext output
    │     SSLEngine.wrap(...)
    ▼
ByteBuffer encrypted output -> SocketChannel.write(...)
```

Ngoài TLS record encryption/decryption, `SSLEngine` còn báo handshake status, delegated tasks, buffer underflow/overflow và close workflow. Đây là tầng phức tạp hơn rõ rệt, không thể chỉ thay `SocketChannel` bằng `SSLSocket` trong selector code.

Vì đề bài tập trung vào **`SSLContext`, `SSLSocketFactory`, `SSLSocket` và `SSLServerSocket`**, ví dụ chính dùng blocking socket. Khi cần nonblocking TLS thật, hãy chọn framework đã triển khai `SSLEngine` đúng cách hoặc thiết kế state machine và buffer ownership chuyên biệt.

## 20. Lỗi thường gặp và cách khắc phục

| Triệu chứng hoặc ngộ nhận | Nguyên nhân khả dĩ | Hướng xử lý |
| --- | --- | --- |
| `SSLHandshakeException: PKIX path building failed` | Client không tin certificate chain server | Cấu hình truststore đúng CA/cert; kiểm tra chain và expiry, không dùng trust-all |
| `No name matching ... found` hoặc `No subject alternative names ...` | Certificate không khớp host/IP kết nối | Sửa SAN/certificate hoặc dùng đúng hostname được cấp; giữ hostname verification |
| `handshake_failure` / `no cipher suites in common` | Không có suite/protocol/cert/key tương thích | Kiểm tra enabled protocols, provider, certificate key type, thuật toán bị disabled |
| `No available authentication scheme` | Server thiếu private key/certificate phù hợp cho TLS mode/cipher | Tạo/init KeyManagerFactory với keystore đúng |
| `UnrecoverableKeyException` | Mật khẩu private key không đúng hoặc entry không đọc được | Kiểm tra store/key password, alias, file permissions |
| `SocketTimeoutException` | Accept/read/handshake không hoàn thành trong timeout | Kiểm tra server listening, network, provider, timeout và peer state |
| `Connection refused` | Không có listener TCP ở địa chỉ/port | Kiểm tra bind address, firewall, port và service |
| Client tin cert nhưng vẫn kết nối sai máy | Thiếu endpoint identity verification | Thiết lập `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` trước handshake |
| `getSession().getProtocol()` là TLS cũ | Bật phiên bản cũ hoặc khác kỳ vọng | Kiểm tra enabled protocols, JDK policy, server config; không ép bật protocol yếu |
| Server yêu cầu client cert, client handshake fail | Client không có identity/key hoặc server không trust client CA | Cấu hình hai chiều key/trust đúng cho mTLS |
| Data bị dính/cắt theo ứng dụng | Nhầm TLS socket với message-oriented API | Thêm framing ứng dụng, xử lý partial read |
| CPU/threads tăng đột biến | Thread-per-connection + client chậm/handshake treo | Connection limits, deadline, backpressure; cân nhắc SSLEngine/framework |

Không bắt lỗi TLS rồi “retry bằng plain TCP” một cách tự động; đó là **downgrade không an toàn**. Nếu protocol yêu cầu TLS, handshake thất bại phải khiến kết nối bị từ chối hoặc báo lỗi rõ ràng.

### Phân biệt ba nguyên nhân chứng chỉ

1. **Untrusted:** certificate chain không dẫn đến trust anchor mà client tin.
2. **Expired/not yet valid:** certificate thời gian hiệu lực không phù hợp.
3. **Wrong hostname/IP:** chain có thể hợp lệ nhưng SAN không khớp endpoint dự kiến.

Khắc phục phải đúng loại lỗi. Không vì muốn client chạy “cho nhanh” mà tắt cả trust lẫn endpoint identification.

## 21. Checklist cấu hình TLS cho production

**Client:**
- Chỉ định hostname/IP và port đúng policy; ưu tiên hostname khi service dùng chứng chỉ DNS/SNI.
- Dùng `SSLContext` có truststore/CA được quản lý hoặc default trust phù hợp, tránh trust-all.
- Bật endpoint identification cho raw `SSLSocket`; với HTTP nên ưu tiên HTTP client cấp cao có HTTPS validation.
- Dùng TLS version/cipher suites được cho phép; không bật protocol bị disabled.
- Đặt connect, handshake/read và overall deadlines; giới hạn payload và số kết nối.
- Đóng socket sau khi hoàn tất; không log password, cert private key hoặc dữ liệu nhạy cảm.
- Nếu cần client cert (mTLS), cấu hình key manager riêng và chuỗi cert đầy đủ.

**Server:**
- Có private key + certificate chain đúng hostname từ keystore được bảo vệ.
- Đặt enabled TLS protocols/cipher policy trước accept; không dùng SSLv3.
- Dùng listener bind phù hợp, giới hạn backlog/đồng thời và timeout.
- Mỗi `accept()` tạo một `SSLSocket` riêng; không dùng cùng socket/stream cho nhiều client.
- Nếu yêu cầu mTLS, có server truststore cho client identities và `setNeedClientAuth(true)`.
- Xác thực/ủy quyền payload ứng dụng sau TLS theo danh tính đã xác minh; TLS không tự phân quyền endpoint.
- Dọn accepted sockets, listener, threads, queue/timeout khi close hoặc shutdown.

**Vận hành:**
- Xoay vòng certificate/private key và CA truststore an toàn; giám sát ngày hết hạn.
- Kiểm tra chênh lệch môi trường JDK/provider và `jdk.tls.disabledAlgorithms`.
- Test hostname mismatch, untrusted cert, expired cert, protocol mismatch và mTLS missing-client-cert trong môi trường kiểm soát.
- Không coi “socket connect thành công” đồng nghĩa “TLS handshake thành công”.
- Quan sát protocol/cipher sau handshake nhưng không suy ra thành công bảo mật chỉ từ một trường log.

## 22. Bài tập thực hành

**Bài 1 — Phân biệt object.** Tại sao server cần `SSLServerSocketFactory` và `SSLServerSocket`, nhưng dữ liệu của client được đọc từ `SSLSocket` nhận qua `accept()`?  
**Gợi ý đáp án:** listener chỉ bind/listen/accept; mỗi accepted socket là một kết nối TLS riêng, có handshake/session/stream riêng.

**Bài 2 — Private key và public cert.** Có được copy `server.p12` (chứa private key server) sang phía client rồi dùng làm truststore không?  
**Đáp án:** Không nên và nguy hiểm: client chỉ cần public certificate/CA trust anchors. Gửi private key làm mất tính bí mật identity server.

**Bài 3 — Vì sao client demo cần `client-trust.p12`?**  
**Đáp án:** Server certificate tự ký mới tạo chưa có trong default trust anchors. Import **public certificate** demo giúp client tin chain, đồng thời endpoint identification xác minh IP SAN.

**Bài 4 — Đổi client sang `createSocket("127.0.0.1", port)` nhưng cert chỉ có SAN `DNS:localhost`, không có `IP:127.0.0.1`. Với HTTPS endpoint identification bật thì điều gì có thể xảy ra?  
**Đáp án:** Hostname/IP verification phải thất bại vì identity được kết nối là IP literal không khớp DNS SAN. Hãy cấp đúng IP SAN hoặc kết nối bằng hostname phù hợp; không tắt verification.

**Bài 5 — `SSLContext.getInstance("TLS")` đã mở mạng chưa?**  
**Đáp án:** Chưa. Nó tạo context TLS. Cần `init(...)`, factory/socket, kết nối TCP và handshake.

**Bài 6 — Gọi `startHandshake()` dùng để làm gì?**  
**Đáp án:** Bắt đầu TLS handshake rõ ràng để thương lượng protocol/cipher và thực hiện xác thực theo key/trust/endpoint policy trước application data.

**Bài 7 — Bật `listener.setNeedClientAuth(true)` mà không cấu hình key/trust cho client có hợp lệ không?**  
**Đáp án:** Không đủ. Client phải có certificate + private key được server chấp nhận, server phải có trust managers tin certificate/CA của client.

**Bài 8 — `SSLSocket` có thể đăng ký trực tiếp với `Selector` không?**  
**Đáp án:** Không như `SocketChannel` vì nó không là `SelectableChannel`. Với nonblocking TLS qua NIO, cần `SSLEngine` hoặc framework quản lý wrap/unwrap/handshake.

**Bài 9 — Nếu `reader.readLine()` trả đủ một dòng, ranh giới thông điệp đến từ TLS không?**  
**Đáp án:** Không. Ranh giới đến từ **newline framing** của protocol ứng dụng và `BufferedReader`; TLS chỉ bảo vệ luồng byte vận chuyển.

**Bài 10 — Tại sao không tự động retry HTTP plaintext sau một `SSLHandshakeException`?**  
**Đáp án:** Việc hạ xuống plaintext làm mất xác thực/bí mật khi TLS thất bại và có thể mở đường cho downgrade attack; xử lý lỗi TLS đúng nguyên nhân.
