# Binding, Sending, and Receiving UDP Datagrams with Source or Destination Addresses in Java

UDP (User Datagram Protocol) transmits **datagrams**: individual messages with distinct boundaries, carrying source/destination IP addresses and source/destination ports. There is no TCP connection session, no `accept()`, and no guarantee of delivery, exactly-once delivery, or in-order arrival. In Java, the two core API groups for building UDP applications are:

- `DatagramSocket` + `DatagramPacket` in `java.net`: operates on byte arrays and packets, suitable for basic synchronous UDP clients/servers.
- `DatagramChannel` in `java.nio.channels`: operates on `ByteBuffer`, returns the source address upon receiving, supports blocking/non-blocking modes, and works with `Selector`.

Lesson objectives: **bind the correct local address/port; construct outbound packets with a destination address; receive data and accurately read the source address; send replies back to the right source; distinguish between local and remote addresses; handle timeouts, packet lengths, and common pitfalls.**

## 1. The Datagram Model: Four Address/Port Values

~~~text
  UDP Client                                        UDP Server
  local: 127.0.0.1:portA                            local: 127.0.0.1:portB
       │                                                   │
       │ source=127.0.0.1:portA                           │
       ├──────────────── datagram "ping" ──────────────────>│
       │                            destination=127.0.0.1:portB
       │                                                   │
       │                            source=127.0.0.1:portB │
       │<──────────────── datagram "pong" ──────────────────┤
       │ destination=127.0.0.1:portA                      │
~~~

In the diagram, `portA` and `portB` are actual ports assigned by the operating system; they are not fixed values. `127.0.0.1` is only an IPv4 example for illustration. Java may use the IPv6 loopback address (`::1`), so portable programs should use `InetAddress.getLoopbackAddress()`.

| Concept | Where in Java | Meaning |
| --- | --- | --- |
| **Local bind address** | `socket.getLocalSocketAddress()` or `channel.getLocalAddress()` | The IP/port that the socket is bound to on this machine |
| **Destination of outbound datagram** | `new DatagramPacket(bytes, len, dest)` or `channel.send(buffer, dest)` | The IP/port to which this packet is requested to be sent |
| **Source of received datagram** | `receivedPacket.getSocketAddress()` or the return value of `channel.receive(buffer)` | The sender's IP/port according to the received information |
| **Remote peer fixed via `connect`** | `socket.getRemoteSocketAddress()` or `channel.getRemoteAddress()` | Default/filtered peer after calling `connect`; does **not** create a reliable transport connection like TCP |

Key distinctions:

- **Bind** selects the *receiving/sending endpoint on this machine* (local endpoint).
- **Send** provides the *destination* (remote endpoint) for a packet; the same unconnected socket can send to many different destinations.
- **Receive** provides the *source* of the arriving packet; a server uses this information to send a reply.
- **UDP Connect** only restricts the peer allowed to communicate through the socket; there is no handshake, ACK, or delivery guarantee.

Note: the observed source address information may be an address/port behind NAT; IP address/port alone does not authenticate the sender. For applications requiring identity or anti-spoofing, an application-layer authentication mechanism must be used.

## 2. Binding a UDP Socket: Which IP/Port to Listen On?

### 2.1. `DatagramSocket`: Choosing the Local Port and Address

Several ways to instantiate:

~~~java
// Illustrative snippet; import java.net.*; and handle SocketException.
DatagramSocket auto = new DatagramSocket();       // OS assigns ephemeral port
DatagramSocket fixed = new DatagramSocket(9000);  // bind port 9000, wildcard
DatagramSocket local = new DatagramSocket(
        new InetSocketAddress(InetAddress.getLoopbackAddress(), 0));
~~~

The lines above are **independent examples of constructor syntax**; in real programs, place them in `try-with-resources` and avoid unintentionally opening multiple sockets. Not every machine allows binding port `9000`; the port may be occupied by another program or blocked by system policy.

For `new DatagramSocket(0)` or binding to `new InetSocketAddress(loopback, 0)`, the number `0` means **asking the operating system to choose an available local port**. After binding, read the chosen port with `getLocalPort()`; do not send datagrams to **port 0** as if it were a listening service port.

To control when binding happens, use the unbound constructor:

~~~java
try (DatagramSocket socket = new DatagramSocket(null)) {
    // Options that must be set before bind can be placed here.
    socket.bind(new InetSocketAddress(
            InetAddress.getLoopbackAddress(), 0));
    System.out.println(socket.isBound());
}
~~~

This is an illustrative Java snippet placed inside a method with `throws SocketException` (or handling the exception). `new DatagramSocket(null)` invokes the overload accepting `SocketAddress` with `null`, creating an **unbound** socket; the subsequent `bind(...)` call selects the local endpoint. In production code, this step is usually unnecessary unless options must be configured before binding or binding needs to be managed explicitly.

### 2.2. Loopback, Wildcard, and Interface Addresses

| Bind | Meaning |
| --- | --- |
| `new InetSocketAddress(InetAddress.getLoopbackAddress(), 0)` | Binds to the loopback address for communication on the same machine; good for tests |
| `new InetSocketAddress(0)` | Binds to the wildcard address and an ephemeral port; can receive on interfaces matching the protocol family |
| `new InetSocketAddress("192.0.2.10", 9000)` | **Syntax example only**; binds successfully only if it is a valid local address and permitted by the OS |
| `new InetSocketAddress("example.test", 9000)` | Do not use a remote machine's hostname to "listen on a remote machine"; binding is always an operation on the current machine |

Wildcard (`0.0.0.0` or `::` depending on configuration) represents matching local addresses; it is **not** a destination address to be used arbitrarily by clients. If a server binds to wildcard, the client must connect/send to a **specific reachable address** of the server.

`DatagramSocket.getLocalAddress()` may return the wildcard when bound to wildcard. It does not necessarily tell you **which local interface received a specific datagram**. `DatagramPacket` receives the peer's source information, whereas the exact local destination address of each packet on a wildcard socket is not provided via a dedicated field on `DatagramPacket`.

IPv4/IPv6 addresses and IPv6 link-local scopes can affect binding and sending capabilities. Choose the same IP family between sender and receiver in tests; `InetAddress.getLoopbackAddress()` helps avoid hardcoding IPv4.

### 2.3. Bind vs. Connect

~~~java
DatagramSocket socket = new DatagramSocket(
        new InetSocketAddress(InetAddress.getLoopbackAddress(), 0));
~~~

This constructor has bound the **local endpoint**, but the socket has not fixed a remote peer. Checking `socket.isBound()` and `socket.isConnected()` will show two different states. When unconnected, each outbound `DatagramPacket` can carry its own destination. When UDP-connected to a peer, the socket only sends to and receives from that peer (per the API), but `connect()` does not prove the peer exists or that a process is listening.

## 3. Sending Packets with `DatagramSocket.send(DatagramPacket)`

### 3.1. Converting Messages to Bytes

UDP transmits bytes, not Java `String` objects directly. Always choose a specific encoding for text:

~~~java
byte[] payload = "ping-udp".getBytes(StandardCharsets.UTF_8);
~~~

This is an illustrative snippet; `import java.nio.charset.StandardCharsets;` is required. With UTF-8, packet length is measured **in bytes**, not `String.length()` (the number of UTF-16 code units). When content contains Vietnamese diacritics, use `payload.length` to determine the exact number of bytes to send.

### 3.2. Destination Address Lives in the Outbound Packet

Two equivalent ways for unicast:

~~~java
// Illustrative snippet; byte[] payload, InetAddress host, int port are already defined.
DatagramPacket outbound1 = new DatagramPacket(
        payload, payload.length, host, port);

DatagramPacket outbound2 = new DatagramPacket(
        payload, payload.length, new InetSocketAddress(host, port));
~~~

Then:

~~~java
socket.send(outbound1); // socket is already bound or can auto-bind if needed
~~~

For an **outbound packet before sending**, `outbound1.getAddress()` / `getPort()` / `getSocketAddress()` describe the **packet's destination**. They do **not** reflect the local source port, which is determined by the sending socket. To observe the local source port, call `socket.getLocalPort()` after the socket is bound.

If a packet leaves from a socket bound to an ephemeral port, the remote server can reply to the observed source address/port. In a NAT environment, the source value seen by the server may differ from the client's internal endpoint.

### 3.3. Sending Only Hands the Packet to the OS

`socket.send(packet)` returning successfully only means the send call was accepted according to the API/OS; it does **not** confirm that the peer received it, read it, finished processing it, or will reply. IP packets can be lost, blocked, duplicated, reordered, or dropped at an unlistened port. Do not conclude "the server received it" just because `send` did not throw an exception.

## 4. Receiving Packets with `DatagramSocket.receive(DatagramPacket)`

### 4.1. Allocating a Buffer and Calling Blocking Receive

~~~java
// Illustrative snippet inside a method with throws IOException.
byte[] buffer = new byte[2048];
DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
socket.receive(packet);
~~~

By default, `receive` **blocks until a datagram arrives** or an error occurs; add `socket.setSoTimeout(2000)` before calling it to limit the wait time to about 2 seconds and detect `SocketTimeoutException`. This timeout does not mean the socket is closed; the Javadoc allows the socket to continue being used after a timeout.

When `receive` returns successfully:

| Method on packet | What does it mean after receive? |
| --- | --- |
| `getData()` | The backing byte array buffer, usually **larger** than the actual received data |
| `getOffset()` | The starting position of the actual data in the array |
| `getLength()` | **The number of actual data bytes** received into the packet |
| `getAddress()` | **The source IP address** of the received datagram |
| `getPort()` | **The source port** of the received datagram |
| `getSocketAddress()` | Source address + port as a `SocketAddress` |

Decoding the string properly:

~~~java
String text = new String(
        packet.getData(),
        packet.getOffset(),
        packet.getLength(),
        StandardCharsets.UTF_8);
~~~

This is an illustrative snippet (requires importing `StandardCharsets`). Do **not** use `new String(buffer)`, because the array may contain trailing or stale bytes; do **not** use `getData().length` instead of `getLength()`, because capacity is not payload length.

### 4.2. Replying to the Right Source

In a connectionless UDP server, the destination address for the reply is `packet.getSocketAddress()` **after receiving**:

~~~java
byte[] reply = "pong-udp".getBytes(StandardCharsets.UTF_8);
DatagramPacket response = new DatagramPacket(
        reply, reply.length, packet.getSocketAddress());
socket.send(response);
~~~

Do not use `serverSocket.getLocalSocketAddress()` as the reply destination: that is the **server's local address**, not the client's address. Nor should you store only the source IP and guess a default client port; the source port may be chosen by the OS and differ from the port the server application listens on.

Each datagram is routed independently. A server serving multiple clients on the same socket may receive packets from different sources one after another; to reply correctly, use the **source of the specific packet being processed**, or store context associated with the packet/request ID.

### 4.3. Packet Length Mutates After Receive; Reset When Reusing

Suppose a receiver uses a `DatagramPacket` with a 2048-byte buffer and receives a 5-byte message. `packet.getLength()` then becomes 5. If you pass **that same packet object** into the next `receive` call without resetting its length, the receiver may only allow 5 bytes and truncate the rest.

Correct reuse pattern:

~~~java
byte[] buffer = new byte[2048];
DatagramPacket packet = new DatagramPacket(buffer, buffer.length);

while (running) {
    packet.setLength(buffer.length); // reset capacity before receive
    socket.receive(packet);

    String text = new String(
            packet.getData(), packet.getOffset(),
            packet.getLength(), StandardCharsets.UTF_8);
    handle(text, packet.getSocketAddress());
}
~~~

This is **illustrative pseudocode inside a Java method**: `running` and `handle` represent hypothetical application logic, not a standalone program. For constructors with a non-zero offset, only reset the length within the remaining buffer from the offset, not exceeding `data.length - offset`. A receive buffer that is too small will **truncate** the excess; it will not produce additional `receive` calls to "read the rest" like a TCP stream.

## 5. Complete Java 17+ Program: Two Sockets, Request and Response on Loopback

The example below needs no external server: it creates a server socket and a client socket on the same machine, binding **each socket to the loopback address and a different ephemeral port**. The client sends `ping-udp`, and the server receives it and replies to the source address/port taken from the packet. No extra thread is needed because the kernel buffers a datagram sent before the process calls `receive`.

Create the file **`UdpSocketRoundTrip.java`**:

~~~java
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class UdpSocketRoundTrip {
    public static void main(String[] args) throws Exception {
        InetAddress loopback = InetAddress.getLoopbackAddress();

        try (DatagramSocket server = new DatagramSocket(
                     new InetSocketAddress(loopback, 0));
             DatagramSocket client = new DatagramSocket(
                     new InetSocketAddress(loopback, 0))) {

            server.setSoTimeout(2000);
            client.setSoTimeout(2000);

            byte[] ping = "ping-udp".getBytes(StandardCharsets.UTF_8);
            client.send(new DatagramPacket(
                    ping, ping.length,
                    new InetSocketAddress(loopback, server.getLocalPort())));

            DatagramPacket request =
                    new DatagramPacket(new byte[256], 256);
            server.receive(request);

            System.out.println("server received: " + new String(
                    request.getData(),
                    request.getOffset(),
                    request.getLength(),
                    StandardCharsets.UTF_8));
            System.out.println("source port matches: "
                    + (request.getPort() == client.getLocalPort()));
            System.out.println("source is loopback: "
                    + request.getAddress().isLoopbackAddress());

            byte[] pong = "pong-udp".getBytes(StandardCharsets.UTF_8);
            server.send(new DatagramPacket(
                    pong, pong.length, request.getSocketAddress()));

            DatagramPacket response =
                    new DatagramPacket(new byte[256], 256);
            client.receive(response);

            System.out.println("client received: " + new String(
                    response.getData(),
                    response.getOffset(),
                    response.getLength(),
                    StandardCharsets.UTF_8));
            System.out.println("reply port matches: "
                    + (response.getPort() == server.getLocalPort()));
        }
    }
}
~~~

Compile and run from the directory containing the file:

~~~bash
javac --release 17 UdpSocketRoundTrip.java
java UdpSocketRoundTrip
~~~

**If the OS permits creating loopback sockets and both datagrams are delivered within the timeout**, the exact stdout is:

~~~text
server received: ping-udp
source port matches: true
source is loopback: true
client received: pong-udp
reply port matches: true
~~~

Things to observe:

1. Neither the server's nor the client's local port needs to be known in advance; `getLocalPort()` is used after binding.
2. The client sends using the **destination** `loopback + server.getLocalPort()`; the server receives the **source** via `request.getPort()` and `request.getAddress()`.
3. The server replies to `request.getSocketAddress()`, without hardcoding the client port.
4. The client receives the response and verifies that the source port matches the server. The boolean comparison values are stable in a successful loopback test environment; **actual port numbers** are intentionally not printed because they change between runs.
5. `DatagramPacket` uses a 256-byte buffer, but decodes exactly `getLength()`; the wait time is bounded; `try-with-resources` closes both sockets.

If the program throws `SocketException` during bind, `SocketTimeoutException` during receive, or another `IOException`, treat it as an environmental error/condition to diagnose. UDP does not guarantee 100% delivery even on loopback; the program should not promise that stdout in a restricted sandbox/firewall.

## 6. NIO `DatagramChannel`: `send` Takes Destination Address, `receive` Returns Source Address

With NIO, endpoint information does not have to reside inside a packet object:

~~~java
int sent = channel.send(byteBuffer, destinationSocketAddress);
SocketAddress sender = channel.receive(receiveBuffer);
~~~

This makes the data flow explicit:

- `send(ByteBuffer src, SocketAddress target)`: takes bytes from `src` between the current `position` and `limit`; uses `target` as the **destination**; returns the number of bytes sent (in non-blocking mode this may be **0** if it could not be sent yet).
- `receive(ByteBuffer dst)`: puts up to `dst.remaining()` bytes into the buffer, advances `position`, and returns the **source SocketAddress** of the received datagram.
- If the channel is in **blocking mode**, `receive` waits for a datagram; in **non-blocking mode**, it may return `null` when no packet is available yet. Do not cast or dereference `null`.
- If the datagram is longer than `dst.remaining()`, **the excess is discarded**, rather than waiting for a second `receive`.
- After `receive`, call `buffer.flip()` before reading the contents; before the next receive, call `buffer.clear()` or `compact()` depending on your processing strategy.

An unconnected NIO channel can still call `send` and `receive`. Unlike `read`/`write` on `DatagramChannel`, the `read` and `write` methods require the channel to have called `connect(remote)` because they do not take or return an address per datagram.

### 6.1. Binding a Channel Is Also Local Binding

~~~java
DatagramChannel server = DatagramChannel.open();
server.bind(new InetSocketAddress(
        InetAddress.getLoopbackAddress(), 0));
SocketAddress local = server.getLocalAddress();
~~~

This is an illustrative snippet: place it in `try-with-resources` and handle `IOException`. `DatagramChannel.open()` starts unbound/unconnected; by default the protocol family is determined by the environment. If you need to control the family for IPv4/IPv6 or multicast, look at `DatagramChannel.open(StandardProtocolFamily.INET)` or `INET6`; check OS support.

### 6.2. Complete Java 17+ NIO Program

Create the file **`UdpChannelSourceDemo.java`**:

~~~java
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.net.SocketAddress;
import java.nio.ByteBuffer;
import java.nio.channels.DatagramChannel;
import java.nio.charset.StandardCharsets;

public class UdpChannelSourceDemo {
    public static void main(String[] args) throws Exception {
        InetAddress loopback = InetAddress.getLoopbackAddress();

        try (DatagramChannel server = DatagramChannel.open();
             DatagramChannel client = DatagramChannel.open()) {

            server.bind(new InetSocketAddress(loopback, 0));
            client.bind(new InetSocketAddress(loopback, 0));

            ByteBuffer outgoing =
                    StandardCharsets.UTF_8.encode("nio-ping");
            int sent = client.send(outgoing, server.getLocalAddress());

            ByteBuffer incoming = ByteBuffer.allocate(128);
            SocketAddress source = server.receive(incoming);
            incoming.flip();

            String text = StandardCharsets.UTF_8
                    .decode(incoming).toString();

            System.out.println("bytes sent: " + sent);
            System.out.println("server received: " + text);
            System.out.println("source matches client: "
                    + source.equals(client.getLocalAddress()));
        }
    }
}
~~~

~~~bash
javac --release 17 UdpChannelSourceDemo.java
java UdpChannelSourceDemo
~~~

When binding/delivering the datagram on loopback succeeds, the exact stdout is:

~~~text
bytes sent: 8
server received: nio-ping
source matches client: true
~~~

Explanation: `"nio-ping"` is 8 ASCII bytes in UTF-8; a blocking `send` sends the entire payload as a single datagram per the API; `receive` provides the source address/port to compare against `client.getLocalAddress()`. After `receive`, `incoming.position()` is at the end of the data, so `flip()` is needed for `decode` to read from the beginning.

The example uses the default **blocking mode** and sets no separate deadline on the channel. If no datagram arrives, the `receive` call can block. In service code, use `Selector`/`OP_READ` in non-blocking NIO with an explicit deadline, or manage deadlines with an appropriate concurrency model; do not write a busy loop `while (receive(...) == null) { }` that wastes CPU.

## 7. What `connect` on UDP Is and Is Not

`DatagramSocket.connect(remote)` and `DatagramChannel.connect(remote)` restrict communication to a single peer, often making sending and receiving more convenient when an application only talks to one remote endpoint. This helps the API handle several cases:

| State | Where can it send? | Where does it receive datagrams from? |
| --- | --- | --- |
| Unconnected | Each packet/`send` can choose a different destination | Can receive from any source matching the bound address |
| Connected to peer P | Sends to P per contract; other destinations are invalid | Socket/channel only receives packets purportedly from P |
| Disconnected | Returns to unconnected capability per API | Can send/receive with multiple peers |

**There is no TCP handshake** in UDP `connect`. It does not create a reliable stream, does not guarantee the peer has a listening socket, and does not require the peer to call `accept`. A successful `connect` call is a local socket configuration, not confirmation of successful communication.

On a connected `DatagramChannel`, `read(ByteBuffer)` / `write(ByteBuffer)` can be used because the remote endpoint is established; on an unconnected channel, calling them can throw `NotYetConnectedException`. For `send(buffer, target)` on a connected channel, a target other than the chosen remote can throw `AlreadyConnectedException`.

`PortUnreachableException` may occur when the OS detects that the destination is unreachable, especially in connected UDP state; the Javadoc **does not guarantee** that the exception will always be thrown when the remote is not listening. Therefore, "no exception" still does not mean the peer received it.

Connected UDP is not authentication either: IP addresses can be spoofed in certain network environments, and NAT can change the observed endpoint. Critical protocols still need tokens/nonces/challenges or appropriate cryptographic mechanisms at the application layer.

## 8. Common Errors When Sending/Receiving Datagrams

| Error or Symptom | Common Cause | How to Handle |
| --- | --- | --- |
| `BindException: Address already in use` | Fixed port already bound by another socket; invalid reuse configuration | Use ephemeral ports for tests, or manage ports for services |
| `SocketTimeoutException` | `receive` saw no packet within `SO_TIMEOUT` | Distinguish packet loss, wrong destination, firewall, server not running, IP family mismatch |
| No timeout but program "hangs" | `DatagramSocket.receive` / NIO blocking `receive` waiting indefinitely | Set `setSoTimeout` or a deadline via Selector/concurrency logic |
| Send succeeds but receiver gets no data | UDP may be lost, wrong address/port, NAT/firewall, bound to wrong interface | Log exact destination, check local bind, capture packets when appropriate |
| Received packet is empty/truncated | Buffer too small, confusing `getData().length`/`getLength()`, reusing packet without resetting length | Allocate sufficient buffer, read offset/length, `setLength` before next iteration |
| NIO `receive` returns `null` | Non-blocking channel has no datagram ready yet | Use `Selector` or wait for read readiness, avoid busy spin |
| NIO decoded payload is empty | Forgot `ByteBuffer.flip()` before decoding | `flip` before reading; `clear` before next receive |
| `IllegalBlockingModeException` | Mixing a channel's `DatagramSocket` view with a non-blocking channel and calling blocking API | Choose either NIO or classic model appropriately, do not mix incompatible states |
| Sending to `0.0.0.0` or port 0 | Confusing **wildcard bind** or ephemeral port request with an actual remote destination | Use a specific unicast address and the actual bound port |
| Responses go to the wrong client | Replying to a fixed configured port or to the server's local address | Obtain source `getSocketAddress()` from the **received request** |
| Fails only when changing machines | Different IPv4/IPv6, firewall, interface, container, port policy, or provider | Log OS/JDK, local/remote address + port, check family and permissions |

Do not catch every `Exception` and always print "UDP disconnected": UDP has no mandatory connection. Log the exception type, operation (`bind/send/receive`), local/remote endpoints, payload size, and timeout for easier diagnosis.

## 9. Datagram Boundaries, Payload Size, and Truncation Risks

UDP differs from TCP in how data is represented:

- One `send` produces **one datagram message** (if the send call succeeds). The receiver processes individual datagrams; it does not read "N bytes from a stream" like TCP.
- One `receive` consumes one available datagram; if the buffer is not large enough, the remainder may be **discarded**. It will not appear on the next receive.
- `DatagramPacket.getLength()` and `ByteBuffer.position()` (after receive) determine the actual number of bytes received.
- Networks have an **MTU**; large datagrams may undergo IP fragmentation, be blocked, or lose efficiency. Do not take the theoretical maximum size as your default packet size.
- `DatagramSocket.getReceiveBufferSize()` reflects the OS socket receive buffer, not the payload buffer of each `DatagramPacket`. The two buffers serve different roles.
- UDP can lose, duplicate, or reorder packets. A request-response protocol needs **request IDs**, timeouts, retry control, and idempotency handling if higher reliability is desired.

If a protocol accepts messages up to `MAX_PACKET_BYTES`, the server must define a clear policy for actual length. Allocating only MAX bytes causes longer datagrams to be truncated, and it may be hard to tell it was cut off if the received size equals the buffer size. One design approach is to use a **length header** and verify completeness, leave headroom to detect oversized packets, or choose a protocol with framing/size enforced at the source. Check `payload.length` on the sender before sending and reject data exceeding business limits.

Text data should have an encoding such as UTF-8. For binary protocols, use `ByteBuffer.order(...)` when endianness matters, and do not guess the format from arbitrary content. An empty packet (0-byte payload) can also be a valid datagram; do not assume `getLength()==0` means "socket closed".

## 10. Source/Destination Addresses in Multi-Client Applications

Suppose a server receives two packets close together:

~~~text
request #41 from 198.51.100.8:41234 -> server:9000
request #42 from 198.51.100.8:49876 -> server:9000
~~~

Both have the same IP but **different ports**; they could be two client sockets, two NAT mappings, or two different processes. If the server saves `lastClientIp` and drops the port, it will send responses to the wrong destination. Conversely, IP+port is not a durable identity either: NAT rebinding or client restarts change the port; application-layer request IDs/tokens help correlate properly.

A single-threaded server can handle this as follows (Java pseudocode with application-defined business logic):

~~~java
DatagramPacket packet = new DatagramPacket(buffer, buffer.length);

while (running) {
    packet.setLength(buffer.length);
    socket.receive(packet);

    SocketAddress source = packet.getSocketAddress();
    byte[] requestBytes = java.util.Arrays.copyOfRange(
            packet.getData(),
            packet.getOffset(),
            packet.getOffset() + packet.getLength());

    byte[] replyBytes = processRequest(requestBytes);
    socket.send(new DatagramPacket(
            replyBytes, replyBytes.length, source));
}
~~~

This is a **non-standalone illustrative snippet** because `buffer`, `running`, `socket`, `processRequest`, and exception handling belong to a specific service. The key point: **snapshot the source and payload of each request** before reusing `DatagramPacket` and the buffer. If you pass `getData()` directly to an asynchronous worker/thread, the next `receive` may overwrite the array and corrupt the data being processed. When concurrency is needed, copy the data or manage buffer ownership explicitly.

For distributed systems, payloads should carry a message type, version, request ID, and defined encoding. Do not assume that "received from address X" is sufficient to grant access or identify a user.

## 11. Comprehension Check Exercises

**Question 1.** What destination address should a client use for a server created with `new DatagramSocket(new InetSocketAddress(loopback, 0))`?  
**Answer:** Call `server.getLocalPort()` after binding and use a matching loopback address; port `0` in the constructor only asks the OS to pick an ephemeral port.

**Question 2.** Before sending, what port does `packet.getPort()` represent? After `receive(packet)`, what port does it represent?  
**Answer:** Before send, the packet holds the **destination port**; after receive, it holds the **source port** of the received packet. These are two different roles depending on the operation.

**Question 3.** A receiver uses a 4096-byte buffer and receives the two-byte data `"OK"`. Should it create `new String(packet.getData(), UTF_8)`?  
**Answer:** No. You must use `getOffset()` and `getLength()` to decode only the exact two bytes received.

**Question 4.** Why can reusing a `DatagramPacket` that previously received 3 bytes to then receive 100 bytes truncate the data?  
**Answer:** After receive, the length field reflects 3 bytes; before the next call, you must `setLength` back to the appropriate capacity.

**Question 5.** A server binds to `0.0.0.0:9000`; should a client on another machine send to `0.0.0.0:9000`?  
**Answer:** No. `0.0.0.0` is a wildcard bind, not a specific destination host address used for remote communication.

**Question 6.** What does NIO `DatagramChannel.receive(buffer)` return if the channel is not connected?  
**Answer:** When a datagram arrives, it returns the source `SocketAddress`; a channel **does not need to be connected** to use `receive`. If non-blocking and no packet is available, it may return `null`.

**Question 7.** Calling `DatagramChannel.receive(buffer)` and immediately decoding yields an empty string, even though non-empty content was sent. What is the common mistake?  
**Answer:** Forgetting `buffer.flip()` after data has been written into the buffer; `position` is at the end of the payload.

**Question 8.** Does a successful `DatagramSocket.connect(serverAddress)` prove the server is running?  
**Answer:** No. UDP connect has no TCP handshake or end-to-end confirmation; you must send a request and receive/check a response if you want to know the service is actually processing.

**Question 9.** A client sends two UDP datagrams consecutively. Is the server guaranteed to receive them in order?  
**Answer:** No. UDP does not guarantee delivery, ordering, or exactly-once semantics; the protocol itself must implement reliability if needed.

**Question 10.** A server socket receives a packet from client A, then B; is it reasonable to reply to all of them at `socket.getLocalSocketAddress()`?  
**Answer:** No. That is the server's local address. Each reply must be sent to `packet.getSocketAddress()` of the corresponding request (or the remote address properly saved for that request).

## 12. Checklist When Writing UDP Functionality in Java

1. **Bind the local endpoint** to match your goal: loopback for same-machine tests, wildcard or a specific interface per actual network requirements.
2. **Do not use port 0 as a destination.** Port 0 on local bind only requests automatic port selection; retrieve `getLocalPort()` after binding.
3. **Every outbound datagram has a valid destination.** For unconnected sockets, set destination IP+port in `DatagramPacket` or the parameter to `DatagramChannel.send`.
4. **Capture the source immediately upon receiving.** With classic: `getAddress()`, `getPort()`, `getSocketAddress()`; with NIO: the return value of `receive`.
5. **Decode only the received bytes.** `getOffset()/getLength()` or `ByteBuffer.flip()`; UTF-8 for text.
6. **Reset packet length** if reusing a `DatagramPacket` object; allocate a sufficient buffer and guard against truncation.
7. **Bound wait times.** `DatagramSocket.setSoTimeout` or NIO/`Selector` with a deadline; do not busy-spin indefinitely.
8. **Close resources.** Use `try-with-resources` for sockets/channels and do not retain references to reused buffers across requests without clear ownership.
9. **Do not infer reliability or identity from UDP.** Use request IDs, controlled retries, idempotent application logic, and authentication where needed.
10. **Test in the target environment.** IPv4/IPv6, firewalls, NAT, bind addresses, network namespaces/containers, and OS differences can alter behavior; log local/remote endpoints clearly.

**Key takeaway:** bind defines the *local address/port*; send chooses the *destination*; receive returns the *source*. Correct payload handling lies in **offset + length** for `DatagramPacket` or **position/limit** for `ByteBuffer`. UDP is a datagram protocol with no delivery guarantees, so any requirements for acknowledgment, ordering, retries, and identity must be designed at the application layer.
