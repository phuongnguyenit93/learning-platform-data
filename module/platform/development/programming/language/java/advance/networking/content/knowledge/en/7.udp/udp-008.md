# Application-Designed Receive Timeouts, Sequence Numbers, and Retries over UDP

**UDP (User Datagram Protocol) only transports datagrams on a best-effort basis.** It preserves individual datagram boundaries, but does not automatically guarantee that packets will arrive, arrive in order, arrive only once, or carry an acknowledgment from the receiving application. A successful **DatagramSocket.send(...)** call only proves that the local system accepted the send request; it does **not** prove that the peer received or processed the data.

Therefore, when your protocol needs to know whether a request has been processed, you must design three coordinated mechanisms at the **application layer**: **receive timeout/deadline**, **sequence numbers or request IDs**, and **controlled retries (retry/retransmission)**. Beyond that, you still need **ACKs, duplicate detection, idempotency, load limiting, and security**; simply adding a timeout and resending is not enough to build a reliable system.

This lesson in the **UDP** section progresses from mechanisms to a Java 17 example running on loopback that intentionally drops the first ACK. This makes it clear why the client must resend the **same request ID**, while the server must recognize duplicates and **not process the business logic twice**.

## 1. What UDP Provides and Does Not Provide

With TCP, the transport layer automatically manages a reliable, ordered byte stream (as long as the connection remains active). With UDP, each send produces a separate datagram message; the application must decide how to handle packet loss, errors, ordering, duplicates, and expiration.

| Property | Provided directly by UDP? | What should the application do if needed? |
|---|---|---|
| Preserve individual datagram boundaries | Yes, per received datagram | Read the exact **DatagramPacket.getLength()**; check for truncated payloads |
| Reliable delivery to the peer | No | Need acknowledgment, timeout, retry, and failure-handling mechanisms |
| In-order delivery | No | Sequence numbers and a reorder buffer or a policy to drop stale packets |
| No duplicate datagrams | No | Request IDs, duplicate detection window, idempotency |
| Delivery within a fixed deadline | No | Application deadline, latency budget, drop expired data |
| Avoid network congestion | No | Rate limiting, congestion control, backoff, pacing |
| Sender knows the business operation completed | No | ACK/response with clearly defined semantics |
| Datagrams automatically authenticate the sender | No | Session authentication, MAC/AEAD, DTLS/QUIC, or an appropriate security protocol |

States to distinguish:

- **Lost datagram:** the server never sees the request, and there is no response.
- **Lost ACK:** the server *already processed* the request, but the client assumes the request never arrived and retries.
- **Delayed response:** the client times out before a valid response arrives; a retry can create a duplicate request.
- **Out-of-order datagram:** request 12 arrives before request 11; the business meaning of applying them depends on the protocol.
- **Duplicate datagram:** caused by the network or by the client's own retransmission; the server must detect duplicates by ID, not merely by identical payload.

**A timeout does not prove that a packet was lost.** It only indicates that at that moment, the application has not received a valid expected message within the configured wait period.

## 2. Receive Timeout in Java: DatagramSocket.setSoTimeout

In Java 17, a normal **DatagramSocket.receive(DatagramPacket)** call **blocks** until a datagram is received or an error occurs. If you call **setSoTimeout(milliseconds)** with a positive value **before** calling receive:

- If a datagram arrives within the wait period, **receive** returns and populates the buffer, length, source address, and source port into **DatagramPacket**.
- If no datagram is received within the wait period, Java throws **SocketTimeoutException** (which is an IOException).
- After a **SocketTimeoutException**, the socket **remains valid**; you can continue receiving or sending, change the timeout, or close the socket.
- **setSoTimeout(0)** means **wait indefinitely** for each receive call; a negative value throws **IllegalArgumentException**.
- This timeout bounds **a single receive call**; it is not a timeout for the entire workflow spanning multiple sends, reads, and retries.

The following API snippet only illustrates the usage with pre-prepared variables and is **not a standalone program**:

~~~java
socket.setSoTimeout(500);
try {
    socket.receive(packet);
    // Validate sender source, header, request ID, and length.
} catch (SocketTimeoutException timeout) {
    // Expected valid datagram has not been seen yet.
    // Check retry/deadline policy; do not jump to concluding the server is dead.
}
~~~

If you repeatedly call receive after every unrelated datagram and wait a full 500 ms each time, the total time can stretch indefinitely. Therefore, when waiting for **the ACK of a request**, in addition to the per-receive timeout, you also need an **ACK wait deadline**.

### Per-Receive Timeout, Per-Attempt Timeout, Overall Transaction Deadline

Suppose the client is only allowed to spend at most **2 seconds** for the entire transaction:

1. **Per-receive timeout:** limits the duration of one blocking receive call, for example 150 ms.
2. **Per-attempt ACK window:** after each send, multiple datagrams may be received, but a valid ACK is only accepted within a time window.
3. **Overall deadline:** all sending, receiving, retrying, and backoff waiting must stop once the 2-second budget is exceeded.

**Do not add up timeouts by guesswork.** If one wait takes 200 ms, then backoff takes 400 ms, then another wait takes 400 ms, you are consuming from a shared budget. Each loop iteration should compute the remaining time:

~~~text
remaining = overallDeadline - monotonicNow
if remaining <= 0: stop
receiveTimeout = min(remaining, ackWaitWindowRemaining, systemLimit)
~~~

In Java, use **System.nanoTime()** to measure elapsed intervals and relative deadlines; do not use **System.currentTimeMillis()** for wait timers because the system clock can be adjusted. Any conversion from nanoseconds to milliseconds before **setSoTimeout** must ensure a minimum timeout of **1 ms**, never accidentally passing 0 (since 0 means infinite). Depending on the scheduler/OS, the actual timeout may drift slightly; **a deadline is an application stopping rule**, not a hard real-time guarantee.

## 3. Sequence Numbers, Request IDs, and Session IDs

UDP does not automatically attach business sequence numbers. You must clearly define each field in your wire protocol and what it is used for.

### 3.1. Three Fields with Distinct Roles

- **sessionId / connectionEpoch:** distinguishes logical sessions. UDP does not require a handshake like TCP, but an application can use sessions to avoid mistakenly accepting delayed packets from an old session.
- **sequenceNumber:** indicates the order of a *message, chunk, or packet* **within a session**, helping detect missing/out-of-order packets and reorder them if needed.
- **requestId / operationId:** identifies **a single business action**. When retrying because no ACK was seen, the requestId **must remain the same** so the server recognizes duplicates as the same request.

Example of sending three independent requests:

~~~text
session=74, seq=1, requestId=401, payload="set mode=A"
session=74, seq=2, requestId=402, payload="set mode=B"
session=74, seq=3, requestId=403, payload="read mode"
~~~

When the ACK for request 402 is lost, the client retransmits **requestId 402**, rather than generating 404. Conversely, if a new ID were generated for each send, the server could not tell that this is a retry of a previous operation and might execute it twice.

**Sequence numbers and request IDs are not necessarily the same.** When an operation is split across multiple datagrams, the datagrams can have their own **sequence numbers** while still belonging to the **same request ID**; an ACK can acknowledge individual chunks or the entire operation. If only one outstanding request is allowed in a stop-and-wait style, some systems use a single ID for both, but the contract must be clearly documented.

### 3.2. Packet Format Must Be Versioned and Bounded

A simple proposed header:

~~~text
+---------+------+-----------+-----------+----------+---------+
| version | type | sessionId | requestId | sequence | payload |
+---------+------+-----------+-----------+----------+---------+
    1 B     1 B     8 B          8 B        4 B       ... B
~~~

The wire format definition must also specify **byte order**, lengths, payload charset, magic/version, type values, checksum/authentication, error reporting, maximum size, and handling of unknown fields. Do not pass received bytes straight to business logic without first validating length and validity.

An ACK must clearly indicate **what it is acknowledging**:

~~~text
ACK(sessionId=74, requestId=402, status=ACCEPTED)
~~~

**ACCEPTED** is different from **APPLIED** or **DURABLY_COMMITTED**. If an ACK only means "datagram received," the client must not treat it as "money transfer completed." Statuses must be clearly defined according to business semantics; if the application writes to a database, the timing of sending the ACK and crash recovery behavior are especially important.

### 3.3. Duplicates, Stale Packets, and Sequence Wrap-Around

If a client uses a 32-bit integer sequence, after enough messages it will wrap around (*wrap-around*). Comparing **new seq > old seq** using plain signed or unsigned integer comparison is not always correct across the wrap point. Design appropriate serial number/window rules or use a sufficiently wide sequence combined with session/epoch, ensuring IDs are not reused while old packets can still be in flight.

A late-arriving ACK from a previous session must not mistakenly acknowledge a current request even if the sequence number matches. Therefore, **requestId + sessionId + peer identity + expiry** is usually a more important tuple than a lone sequence number.

## 4. Retry Flow with ACK: Stop-and-Wait

**Stop-and-wait** is a minimal protocol: at any point in time, the client keeps only **one request waiting for an ACK**. Until acknowledged, the client can retry the same datagram under a bounded policy.

~~~text
CLIENT                                     SERVER
 send REQ(id=42) -----------------------> receive id=42
                                          apply operation once
                    X--- ACK(id=42) ---- ACK lost
 (timeout)
 resend REQ(id=42) ---------------------> receive duplicate id=42
                                          do not execute again
                  <--------------------- ACK(id=42) again
 handle ACK matching id and peer
 complete request
~~~

The client typically needs these steps:

1. Assign a new requestId to a **new business request**, encode header and payload, and keep the exact bytes/metadata for retransmission.
2. Send the datagram to the right endpoint; keep only one outstanding request in this example.
3. Start the **per-attempt deadline** and wait for an ACK. While waiting, **ignore** datagrams with a mismatched source/session/requestId/type, while keeping the original deadline.
4. If a valid ACK with the expected status is received, complete. If a valid NACK is received, decide whether to retry or fail based on the error type.
5. If the window expires without an ACK, check the overall deadline, retry quota, and rate limiter; if allowed, wait for backoff and **resend the same requestId**.
6. When the budget is exhausted, return a **timeout/unknown outcome** status if the request may have been applied while the ACK was lost; do not assert with certainty that it was a business failure.

The server typically needs to:

1. Authenticate source and session, and validate header and payload.
2. Look up the **idempotency key** (e.g., sessionId + requestId) in an appropriate cache/durable store.
3. If not yet processed, execute once within the system's guarantees, persist the result/response, and then send the ACK.
4. If it is a valid duplicate, **do not re-apply side-effecting work**; return the stored ACK/result if still retained.
5. Enforce a state expiration policy, cap the number of entries, and define how to handle old requests arriving after state has been evicted.

**The server should not unconditionally ACK every datagram.** It may need to reject packets with failed authentication, wrong version, oversized payload, expired request, or quota violations. For potentially large responses, avoid UDP amplification reflection toward spoofed source addresses.

## 5. Complete Java 17 Example: Single Lost ACK, Retry Same ID, and Duplicate Suppression

The example below runs a **UDP client and server in the same JVM on loopback**, without hardcoded ports. To make the outcome clear, the server **intentionally omits sending the ACK the first time it receives the valid request**, simulating a lost ACK. The client times out and retransmits the same ID; the server detects the duplicate, does not apply the business logic a second time, and sends back the ACK.

Illustrative wire protocol:

- First byte: **1 = DATA**, **2 = ACK**.
- Next eight bytes: **requestId** as a Java long in ByteBuffer's default byte order (big-endian).
- DATA has a UTF-8 payload; the example ACK has a length of **exactly 9 bytes** and no payload.
- There is only one client, one request, and one local server. The demo does **not** include sessions, authentication, durable caching, or full congestion control; do not reuse it directly as a production server.

File **UdpStopAndWaitDemo.java**:

~~~java
import java.io.IOException;
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.SocketTimeoutException;
import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;

public class UdpStopAndWaitDemo {
    private static final byte DATA = 1;
    private static final byte ACK = 2;
    private static final int HEADER_SIZE = 9;
    private static final long REQUEST_ID = 7001L;
    private static final int MAX_ATTEMPTS = 5;

    private record ServerResult(int applied, boolean duplicate) {}
    private record ClientResult(boolean acknowledged, int attempts) {}

    private static byte[] frame(
            byte type, long id, byte[] payload) {
        return ByteBuffer.allocate(HEADER_SIZE + payload.length)
                .put(type).putLong(id).put(payload).array();
    }

    private static ServerResult serve(DatagramSocket server)
            throws IOException {
        server.setSoTimeout(4_000);
        int applied = 0;
        boolean duplicate = false;

        while (!duplicate) {
            byte[] buffer = new byte[128];
            DatagramPacket incoming =
                    new DatagramPacket(buffer, buffer.length);
            server.receive(incoming);

            ByteBuffer data = ByteBuffer.wrap(
                    incoming.getData(),
                    incoming.getOffset(),
                    incoming.getLength());

            if (data.remaining() < HEADER_SIZE) {
                continue;
            }

            byte type = data.get();
            long id = data.getLong();
            if (type != DATA || id != REQUEST_ID) {
                continue;
            }

            if (applied == 0) {
                applied++;
                // Intentionally "drop" the first ACK after processing.
                // The client will timeout and retransmit the same request ID.
                continue;
            }

            // Same ID => duplicate, do not apply business logic a second time.
            duplicate = true;
            byte[] reply = frame(ACK, id, new byte[0]);
            DatagramPacket outgoing = new DatagramPacket(
                    reply, reply.length,
                    incoming.getAddress(), incoming.getPort());
            server.send(outgoing);
        }

        return new ServerResult(applied, duplicate);
    }

    private static ClientResult request(
            DatagramSocket client, InetAddress serverIp, int serverPort)
            throws IOException {
        byte[] body = "HELLO".getBytes(StandardCharsets.UTF_8);
        byte[] data = frame(DATA, REQUEST_ID, body);

        for (int attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
            client.send(new DatagramPacket(
                    data, data.length, serverIp, serverPort));

            // Fixed deadline for the attempt; unrelated packets do not reset the clock.
            long until = System.nanoTime()
                    + TimeUnit.MILLISECONDS.toNanos(300);

            while (true) {
                long leftNanos = until - System.nanoTime();
                if (leftNanos <= 0) {
                    break;
                }

                // Never use 0 ms: setSoTimeout(0) = infinite.
                long leftMillis =
                        TimeUnit.NANOSECONDS.toMillis(leftNanos) + 1;
                client.setSoTimeout((int) Math.min(
                        Integer.MAX_VALUE, Math.max(1L, leftMillis)));

                byte[] buffer = new byte[128];
                DatagramPacket reply =
                        new DatagramPacket(buffer, buffer.length);

                try {
                    client.receive(reply);
                } catch (SocketTimeoutException timeout) {
                    break; // Current attempt's ACK window expired.
                }

                if (!reply.getAddress().equals(serverIp)
                        || reply.getPort() != serverPort
                        || reply.getLength() != HEADER_SIZE) {
                    continue;
                }

                ByteBuffer ack = ByteBuffer.wrap(
                        reply.getData(),
                        reply.getOffset(),
                        reply.getLength());

                if (ack.get() == ACK && ack.getLong() == REQUEST_ID) {
                    return new ClientResult(true, attempt);
                }
                // Mismatched ACK => ignore, keep waiting within the same deadline.
            }
        }

        throw new IOException(
                "No matching ACK after " + MAX_ATTEMPTS + " attempts");
    }

    public static void main(String[] args) throws Exception {
        InetAddress loopback = InetAddress.getLoopbackAddress();

        try (DatagramSocket server = new DatagramSocket(0, loopback);
             DatagramSocket client = new DatagramSocket(0, loopback)) {

            ExecutorService executor =
                    Executors.newSingleThreadExecutor();
            try {
                Future<ServerResult> serverTask =
                        executor.submit(() -> serve(server));

                ClientResult clientResult = request(
                        client, loopback, server.getLocalPort());
                ServerResult serverResult =
                        serverTask.get(5, TimeUnit.SECONDS);

                System.out.println("Matching ACK received: "
                        + clientResult.acknowledged());
                System.out.println("Client retried: "
                        + (clientResult.attempts() > 1));
                System.out.println("Server applied requests: "
                        + serverResult.applied());
                System.out.println("Duplicate detected: "
                        + serverResult.duplicate());
            } finally {
                executor.shutdownNow();
            }
        }
    }
}
~~~

Compile and run in the directory containing the file (Java 17+):

~~~bash
javac -encoding UTF-8 UdpStopAndWaitDemo.java
java UdpStopAndWaitDemo
~~~

Output when the experiment succeeds on loopback:

~~~text
Matching ACK received: true
Client retried: true
Server applied requests: 1
Duplicate detected: true
~~~

**Why is this output meaningful?**

- The server **receives and processes the request the first time** but intentionally drops the ACK, so the client gets no confirmation. When the first attempt's wait expires, **DatagramSocket.receive** throws **SocketTimeoutException** and the socket remains usable.
- The client resends the **exact same bytes with the same requestId 7001**, without creating a new request. This is the prerequisite for the server to detect a duplicate.
- The server increments **applied** only the first time it sees the ID. When it sees the duplicate, the server returns the ACK without incrementing the applied operation count. The ACK only contains type and ID, and the client verifies **source IP, source port, length, type, and ID**.
- Main waits for the **Future** to return before printing, so the order of the four lines is deterministic. No dynamic UDP port is printed, and it does not depend on log ordering between two threads.
- The example has **MAX_ATTEMPTS** and a server timeout; if the network/OS fails, it may terminate with an exception instead of the four lines above. On normal loopback, the first message is received and the first ACK is intentionally dropped; consequently, the conditions display exactly as in the sample output.

**Important limitations:** the example uses a single **applied** variable instead of a real dedup cache, serving only **one fixed request ID** and one client. A production server must use reliable session/request identity, authentication, store processed results, bound state, validate payload/data types, support multiple requests, protect against spoofing, and implement congestion control. **The 300 ms timeout** is just a small number for the loopback demo, **not a suitable Internet default**.

## 6. Why Source Address and ACK Matching Matter, Yet Are Not Enough

When using an **unconnected** DatagramSocket, a receive call can accept datagrams sent to the local port from multiple peers. If you only check the **ACK** string without requestId and endpoint, a stale ACK or one from another client can falsely complete a new transaction.

Minimum checklist for an ACK:

1. Check **type, version, packet size, source address/port**, and request ID.
2. Check **session ID** if multiple sessions exist, then verify which outstanding request the ACK corresponds to.
3. Check **status code and result** against protocol semantics; do not treat an ACK for "received" as "durably persisted."
4. Do not reset the deadline just because an unrelated datagram arrives. Continuously receiving invalid packets must not extend a request indefinitely.
5. If there are multiple outstanding requests, do not use a single unlocked global **lastAckId** variable; you need an outstanding requests table, thread safety, and ACK routing to the corresponding request.

**DatagramSocket.connect(remoteAddress, remotePort)** on UDP **does not create a TCP-like connection and does not automatically add ACKs/retries**. It binds the remote address for send/receive operations and may filter datagrams from other peers per API/OS behavior, but **provides no cryptographic authentication**: IP/port can be spoofed in some environments. Even when using a connected UDP socket, you must still manage IDs, timeouts, business state, and security.

The example shows an address check so learners see the trust boundary; in real systems, use authentication/MAC or a secure session such as DTLS when security is required over untrusted networks.

## 7. Retry Policy: Attempt Limits, Backoff, Jitter, and Overall Deadline

A loop like the following is unsafe:

~~~text
while no ACK:
    send request again immediately
~~~

It can cause a **retransmission storm** during network congestion, worsening packet loss. RFC 8085 emphasizes that UDP applications need congestion control, including **retransmission traffic**. For small stop-and-wait requests, a common starting point is a conservative timeout, finite attempts, **exponential backoff**, **jitter**, and an **overall deadline**.

Conceptual formula:

~~~text
base = baseline wait time, should be calibrated to RTT/service characteristics
delay_n = min(cap, base * 2^(n-1))
actual_delay_n = jitter(delay_n)
stop if attempts reach the limit or totalDeadline has expired
~~~

**Do not take demo numbers and apply them directly to the Internet.** RFC 8085 advises that applications unable to estimate RTT should start conservatively, typically around **1 second** for retransmission; protocols with specific characteristics may use other values. Choose timeouts by measuring RTT, variance, service behavior, and latency requirements. If you keep resending too early, even a valid slow response can trigger unnecessary duplicates.

### Runnable Java 17 Example: Illustrative Backoff Schedule

File **RetryScheduleDemo.java** (computes the schedule only, **does not send UDP**):

~~~java
public class RetryScheduleDemo {
    static long delayMillis(int failedAttempts) {
        long delay = 200;
        for (int i = 1; i < failedAttempts; i++) {
            delay = Math.min(1_600, delay * 2);
        }
        return delay;
    }

    public static void main(String[] args) {
        for (int failures = 1; failures <= 5; failures++) {
            System.out.println(
                    failures + " timeout(s) => "
                    + delayMillis(failures) + " ms");
        }
    }
}
~~~

~~~bash
javac RetryScheduleDemo.java
java RetryScheduleDemo
~~~

~~~text
1 timeout(s) => 200 ms
2 timeout(s) => 400 ms
3 timeout(s) => 800 ms
4 timeout(s) => 1600 ms
5 timeout(s) => 1600 ms
~~~

This is a **deterministic schedule to understand the formula**, without jitter yet. In production, bounded random jitter can be added to prevent many clients from waking up and retrying simultaneously (*thundering herd*). For high traffic, you also need **pacing**, limits on in-flight requests, per-peer rate limiting, circuit breakers, and proper congestion control; exponential backoff alone is not a complete solution.

### An Overall Deadline Must Not Be "Extended" After Each Retry

Suppose the total budget is 2,000 ms:

~~~text
t=0      send request, wait for ACK
t=300    1st timeout
t=500    backoff ends, resend
t=900    2nd ACK wait window expires
t=1300   resend after backoff
t=2000   total budget exhausted => stop, do not open a new window
~~~

These numbers are only an illustrative timeline, not a mandatory calculation for every environment. When 200 ms remain in the budget while the suggested per-attempt timeout is 500 ms, wait **at most 200 ms**. You must also account for **sending, processing, scheduler, retry queue, and network time**.

**When stopping due to deadline**: return an "unknown whether processed" result if the operation has side effects. If the client UI must display an error, the message should preserve accurate semantics: "confirmation not received in time" is more accurate than "the server definitely did not process it."

## 8. At-Most-Once, At-Least-Once, and Exactly-Once

**Retries are a trade-off decision, not a magic spell that turns UDP into TCP.**

| Design | Typical capability | Risks |
|---|---|---|
| Send once, no retry | May lose messages; avoids duplicates caused by client retries | No guarantee the message arrives |
| Retry until ACK or limit reached | Increases delivery chance, but may repeat requests | Without dedup, side effects may execute multiple times |
| Retry + request ID + dedup cache | Within the state retention window, server can avoid duplicate application | State expiration, crashes, multiple instances, and replay remain issues |
| Durable dedup + atomic transaction with side effect + response cache | Can achieve very strong business-effect semantics within a defined scope | Complex; cannot simply claim unconditional exactly-once over an unreliable network |

### Lost ACKs and the "Did It Happen or Not?" Problem

Consider a command to **debit 100 from an account**:

1. The server receives request 901, debits the amount, and sends an ACK.
2. The ACK is lost.
3. The client times out and resends request 901.

If the server does not deduplicate, the account is debited twice. If the server **stores requestId + result** and checks before executing, the duplicate request can simply return the stored result.

However, there is still the **crash window** problem: the server debits the account but crashes before recording that requestId was processed. After restart, a duplicate is executed a second time. To achieve business guarantees, **recording the side effect and the idempotency record must be synchronized/atomic** using an appropriate database mechanism; multiple instances must share a consistent state store, not just an in-JVM HashSet.

Therefore, **exactly-once delivery** is not an inherent feature of UDP + ACK + retry. State the scope precisely: **at-most-once effect within the idempotency retention window**, or **effectively-once** with durable transactions and business constraints; do not sell a demo protocol as a global mathematical promise.

### What Should a Dedup Key Include?

A common choice: **(authenticated principal, sessionId, requestId)**. Using only IP:port can break when NAT changes ports, the client restarts, or multiple users share the same NAT. Using only a short global requestId risks collisions; sufficient length and clear scoping are required.

The cache should store **in-progress / completed / terminal-error status**, a payload hash to detect the same ID with different content, a resendable response, expiration time, and quotas. When a duplicate request arrives while the original is still in flight, there must be a coordination strategy: wait for the result, report in-progress, or record to reply later; do not run two executions concurrently.

## 9. Sequence Numbers for Detecting Packet Loss and Out-of-Order Delivery

If an application needs to transmit multiple consecutive datagrams, requestId is not enough for ordering. For example:

~~~text
Sent:      seq=10   seq=11   seq=12
Received:  seq=12   seq=10   seq=12   (seq=11 not yet seen)
~~~

The receiver should distinguish:

- **seq=12 arrives early:** hold in a bounded reorder buffer if the application requires in-order data, or use the latest version if it is a real-time state update.
- **seq=10 is old:** can be processed if the data is still relevant, or discarded if expired.
- **seq=12 is repeated:** duplicate; do not apply the same event twice.
- **seq=11 is missing:** after a wait period or gap detection, request a targeted resend (**NACK**) or use selective/cumulative ACKs depending on the protocol.

**There is no single algorithm right for every application.** A real-time game updating positions can drop an old seq=10 once a newer seq=12 has arrived; a transaction-logging system needs to preserve order and accuracy. When packet loss occurs, consider **forward error correction** or timely packet dropping instead of infinite retries.

**Avoid reorder buffer overflow.** Bound the buffer by datagram count, bytes, time, and session. When seq jumps abnormally far, validate the payload and bound the gap before allocating memory; an attacker must not be able to force the system to hold millions of pending slots.

**Wrap-around:** for an n-bit sequence, after 2^n values you must define comparison within a valid window and epoch. Do not use the **>** operator on signed integers to conclude a packet is "newer" across the wrap point; consider standard serial number arithmetic if the protocol requires it.

## 10. Packet Boundaries and Common Java Pitfalls

**DatagramPacket is a buffer plus metadata, not a complete String.**

### 10.1. Do Not Read the Entire Buffer Array

After receive, you must use **getOffset()** and **getLength()**:

~~~java
String body = new String(
        packet.getData(),
        packet.getOffset(),
        packet.getLength(),
        StandardCharsets.UTF_8);
~~~

This is an illustrative API snippet assuming packet has already been received and StandardCharsets is imported. If you use **new String(packet.getData())**, you may include trailing garbage/zero bytes in the buffer and break header/ACK parsing. In the runnable example above, ByteBuffer is wrapped with **getData(), getOffset(), getLength()** for this exact reason.

### 10.2. Oversized Datagrams Truncate Silently in Small Buffers

If a datagram is larger than the length provided to DatagramPacket, Java **may only receive what fits in the buffer and truncate the rest**, rather than queuing the remainder like a TCP stream. For example, if you use a 32-byte buffer and the peer sends 100 bytes, you **cannot expect the next receive call to read the remaining 68 bytes**.

Protocol design must specify maximum datagram size, header length/payload length, a policy to reject oversized payloads, and MTU limits. If an application message exceeds safe datagram capacity, application-level fragmentation/reassembly and careful management of fragment counts/ACKs/chunks are required; usually a standardized protocol should be considered.

If **reusing a DatagramPacket** across multiple receives, remember to reset **packet.setLength(buffer.length)** before the next receive. After receiving a short datagram, getLength reflects that short length; if not reset, the available buffer for the next call may remain at the old length and truncate larger datagrams.

### 10.3. send Does Not Confirm Remote Receipt

~~~java
socket.send(new DatagramPacket(bytes, bytes.length, host, port));
~~~

This is a non-standalone snippet. There is no return value meaning "ACK from server"; Java has no automatic UDP retransmission. Sending over a connected socket only binds/filters the endpoint, **it does not create a TCP stream**. Some ICMP errors may trigger **PortUnreachableException** on a connected UDP socket, but this behavior is not guaranteed for every packet/OS; **do not rely on this exception as a substitute for an ACK**.

### 10.4. One Socket Across Multiple Threads Needs Clear Ownership

When multiple requests share a DatagramSocket, there should be **a single receiver that dispatches ACKs** (or an equivalent synchronization strategy) by requestId. If two threads both call receive directly on the same socket, one thread can consume an ACK meant for the other thread and discard it; spurious retries will follow. Outstanding request records, timers, and session state must use thread-safe structures and a clear cleanup lifecycle.

## 11. Security, Replay Protection, and Amplification Prevention

UDP is vulnerable to source address spoofing on unprotected networks. An ACK datagram containing the right requestId and matching address/port is **not cryptographic proof** that the legitimate peer processed it. Over the Internet, consider:

1. **Authenticated sessions** and cryptographic MAC/AEAD or **DTLS**/**QUIC** as required by the protocol; do not trust simple sequential IDs as secrets.
2. **Replay windows**, session epochs, non-repeating requestIds, and reasonable acceptance windows. Reject stale packets or identical IDs with different payloads; do not let replays break idempotency.
3. **Rate limits and amplification limits** for responses. Do not reply to a small spoofed UDP request with a huge payload sent to an unverified source IP.
4. **Bound inputs before allocation**: datagram size, payload length, field count, session count, and duplicate cache size.
5. **Encryption/integrity checks** if sensitive data is present. The UDP checksum is not authentication or integrity against an attacker.
6. **Never send indefinitely because an ACK never arrives**; retries need pacing/congestion control so they do not worsen network congestion.
7. **Never pass external data directly into String/JSON/SQL or system actions** without validating schema, charset, authorization, and idempotency.

A strong production solution usually uses a proven protocol if delivery, ordering, congestion control, and security are genuinely needed. **QUIC** runs over UDP yet provides its own mechanisms for connections, loss recovery, streams, and congestion control; this does not mean an application using DatagramSocket directly inherits QUIC's guarantees. **TCP** may be a better fit for transactions that need a reliable, ordered byte stream.

## 12. Testing Loss, Duplication, Reordering, and Retries

Do not only test "the client receives an ACK when the server is healthy." A UDP protocol must pass controlled scenarios:

| Scenario | What should the client do? | What should the server do? |
|---|---|---|
| Request lost | ACK window expires, retry same ID if budget remains | No state yet, wait for datagram arrival |
| ACK lost after server processed | Retry same ID, do not assume business failure | Detect duplicate, return stored ACK/result, do not re-apply |
| Response arrives late after retry | Accept matching ID if still outstanding and valid; drop extra after completion | Produce no side effect for the retry |
| ACK with wrong requestId | Ignore, keep existing deadline | Do not treat wrong ACK as proof of success |
| ACK from another source/session | Ignore or record suspicious metric | Authentication/session isolation |
| Two packets arrive out of order | Reorder or pick latest per business semantics | Manage sequence window and TTL |
| Duplicate arrives after cache expiry | Cannot be solved by short-lived cache alone | Require protocol expiry, ID scoping, durable dedup, or reject overly old requests |
| Client stops due to overall deadline | Return unknown outcome for unconfirmed side effects | May have processed; state requires query/reconciliation |
| Payload larger than receive buffer | Do not mistakenly reassemble truncated fragments | Check size, reject non-conforming packets |
| Application/host restart | Define resume/session epoch and dedup durability | Restore idempotency state when needed |

**Simulating a lost ACK in the Java example** is a repeatable form of fault injection. For more realistic testing, network control tools can be used **in authorized environments** to introduce packet loss, latency, jitter, reordering, and duplication, alongside clear metrics. Do not run network-flooding tests against other people's systems.

### Operational Metrics to Measure

- **ACK success rate** by peer and request type.
- **Retries per request**, total datagrams sent, retransmission rate.
- **RTT/response latency** (be careful measuring RTT on retried requests because it is hard to know which send an ACK corresponds to).
- **Timeout rate**, deadline exceeded rate, unknown-outcome rate.
- **Duplicate requests** at the server, cache hit/miss, state expiry, ID collisions.
- **Out-of-order and stale packets**, packet parse failures, invalid ACKs.
- **Congestion/rate limit drops**, bytes sent/received, amplification ratio.
- **Actual application effects** (DB commits, business operations applied), not just ACK counts.

Include correlation IDs in logs, but avoid logging sensitive information or full payloads. When analyzing failures, correlate monotonic timestamps for latency and timezone-aware timestamps for system events; do not use wall-clock time to compute internal timeout loops.

### Self-Check Questions

**1. Why is DatagramSocket.send() not enough to confirm a request succeeded?** Because it carries no ACK from the remote peer or business processing status.

**2. Does SocketTimeoutException in receive mean the request was definitely lost?** No. The request may have arrived while the ACK/response was lost or delayed.

**3. When retrying an operation with side effects, should you generate a new request ID or keep the old one?** Keep the **same request ID** for retries of the **same operation**; generate a new ID for a new business operation.

**4. Should the server re-process a request if it detects a valid duplicate ID?** Do not apply the side effect a second time within the idempotency policy; it may return the stored result.

**5. Does UDP preserve datagram ordering?** No. If ordered delivery is needed, the application must use a sequence/reorder protocol or choose an appropriate transport.

**6. Does setSoTimeout(0) mean 0 ms or wait indefinitely?** It means wait indefinitely for a blocking receive; positive values bound each receive duration.

**7. Can exactly-once be achieved solely with ACKs, sequences, and retries?** No. Crashes, ACK loss, durable dedup, atomicity of side effects, and multiple instances also matter.

**8. Why must retries have backoff/congestion control?** Because sending more datagrams when the network is already congested can make matters worse and impact other network flows.

**9. Should a client accept an ACK with a matching requestId but wrong session/source?** No. ACKs must be bound to the right session and peer; over untrusted networks, authentication is also required.

**10. If a request times out while the server may have executed it, what should the UI report?** "Confirmation not received in time" or a status requiring reconciliation, not a default "definitely not executed."

**Takeaway:** **UDP does not automatically provide application-level receive timers, numbering, acknowledgments, or retries.** To add reliability, you must design **receive timeouts + overall deadlines**, **session/sequence/request IDs**, **ACKs verified by content and source**, **bounded retries with backoff/jitter**, **duplicate suppression/idempotency**, **congestion control**, and **security**. When the deadline expires without an ACK, the accurate conclusion is usually **unknown outcome**, not "the request was definitely not processed."
