# Chẩn đoán chứng chỉ, tên máy và thuật toán mà vẫn giữ bước xác minh

## 1. Mục tiêu của bài

Khi ứng dụng Java kết nối HTTPS/TLS, lỗi handshake có thể bắt nguồn từ **đường chứng chỉ (certificate chain)**, **truststore**, **tên máy không khớp**, **thời gian hiệu lực**, **giao thức TLS**, **cipher suite**, **chữ ký/khóa**, hoặc **mTLS**. Việc chẩn đoán phải chỉ ra nguyên nhân cụ thể nhưng vẫn giữ hai điều kiện bắt buộc: **chứng chỉ phải được xác minh theo nguồn tin cậy phù hợp** và **danh tính máy chủ phải khớp endpoint đang truy cập**.

Nếu chỉ cần làm cho request đi qua, lập trình viên rất dễ vô tình bỏ một trong hai bước kiểm tra. Kết nối như vậy không còn bảo đảm đang trao đổi dữ liệu với đúng máy chủ. Hướng giải quyết của bài là **sửa chain, SAN, server, truststore hoặc cấu hình thuật toán**, không thay bộ xác minh chứng chỉ bằng cơ chế chấp nhận mọi peer và không tắt kiểm tra hostname.

### Ba nhóm điều kiện khác nhau

| Nhóm | Câu hỏi | Ví dụ lỗi |
| --- | --- | --- |
| **Path/PKIX** | Certificate có nối được tới trust anchor được JVM tin cậy và đáp ứng điều kiện sử dụng không? | Không tìm được intermediate hoặc CA nội bộ chưa được cấu hình |
| **Endpoint identity** | Certificate có đại diện cho đúng DNS name/IP ứng dụng dùng để kết nối không? | URL gọi api.example.com, SAN chỉ chứa www.example.com |
| **TLS/cryptography policy** | Protocol, cipher, signature, key size và thuật toán có còn được JDK cho phép không? | Server chỉ hỗ trợ giao thức hoặc chữ ký cũ |

Một chain được CA tin cậy ký **không tự chứng minh hostname đúng**. Ngược lại, một certificate chứa tên đúng nhưng không có đường tin cậy vẫn bị từ chối. Một certificate thỏa cả hai điều kiện vẫn có thể vi phạm thuật toán hoặc thời gian hiệu lực.

## 2. Mô hình quá trình xác thực TLS

~~~text
Ứng dụng gọi api.example.com:443
            |
     DNS / proxy / route
            |
         ClientHello
   phiên bản TLS, cipher,
   SNI và extensions khác
            |
          Server
    certificate chain
            |
    +-------+--------------------------+
    |                                  |
PKIX/path validation          Endpoint identification
CA/chain, hiệu lực,          SAN của DNS/IP so với
key usage, thuật toán        tên được yêu cầu
    |                                  |
    +---------------+------------------+
                    |
        Nếu mọi kiểm tra bắt buộc PASS
                    |
       Handshake kết thúc thành công
                    |
         Dữ liệu ứng dụng đi qua TLS
~~~

Sơ đồ là mô hình logic, không phải toàn bộ thứ tự bản tin của TLS 1.2 hay TLS 1.3. Trước khi gửi dữ liệu ứng dụng nhạy cảm, chương trình phải bảo đảm handshake của **đúng peer** được xác thực thành công.

Trong Java, **JSSE** cung cấp SSLContext, TrustManager, KeyManager, SSLSocket, SSLEngine và SSLParameters. **HttpsURLConnection** là client HTTPS có cơ chế xác minh hostname mặc định. Với **SSLSocket hoặc SSLEngine trực tiếp**, cần chủ động bật endpoint identification phù hợp, ví dụ:

~~~java
SSLParameters p = tlsSocket.getSSLParameters();
p.setEndpointIdentificationAlgorithm("HTTPS");
tlsSocket.setSSLParameters(p);
tlsSocket.startHandshake();
~~~

Đoạn mã trên là snippet đặt trong nơi đã có **SSLSocket tlsSocket**. Nó không phải một file Java độc lập. Cấu hình endpoint identification **trước handshake** rất quan trọng; chỉ nhìn SSLSession.getCipherSuite() không phải bằng chứng tên máy đã được kiểm tra.

## 3. Quy trình chẩn đoán từng bước

### Bước 1 — Chốt đúng endpoint và môi trường

Cần ghi lại **hostname từ cấu hình ứng dụng**, port, JDK vendor/version, container/VM đang chạy, proxy, DNS và điểm TLS termination. Địa chỉ IP DNS trả về không nhất thiết là tên cần dùng để xác minh certificate: nếu request hướng tới api.example.com, endpoint identity cần phù hợp api.example.com.

Trên gateway có nhiều virtual hosts, certificate nhận được còn phụ thuộc **SNI** trong ClientHello. Việc truy cập theo IP hoặc đặt tên SNI sai có thể khiến gateway trả **default certificate**, dù certificate của virtual host mong muốn thực tế vẫn hợp lệ.

Với proxy, service mesh, reverse proxy hoặc load balancer, Java có thể bắt tay TLS với một lớp trung gian thay vì origin. Hãy chẩn đoán certificate của **đúng điểm kết thúc TLS** mà chương trình thực sự nhìn thấy.

### Bước 2 — Lấy exception và cause chain

Không chỉ đọc lớp ngoài cùng **SSLHandshakeException**. Xem cause lồng nhau và log handshake/PKIX:

| Thông báo hoặc ngoại lệ | Hướng kiểm tra |
| --- | --- |
| **PKIX path building failed** / **unable to find valid certification path** | CA/trust anchor, thiếu intermediate, truststore được JVM nạp |
| **CertificateExpiredException** | NotAfter, giờ hệ thống, certificate đã hết hạn |
| **CertificateNotYetValidException** | NotBefore hoặc máy chạy sai giờ |
| **No subject alternative DNS name matching** | Hostname từ URL/socket so với DNS SAN |
| **No subject alternative names present** | Certificate thiếu SAN cần cho endpoint |
| **Algorithm constraints check failed** | Signature algorithm, kích thước khóa, certpath/TLS policy |
| **protocol_version** | Phiên bản TLS hai bên cho phép |
| **handshake_failure** | Giao thức/cipher/signature không tương thích, hoặc lỗi xác thực khác |
| **certificate_required** / **bad_certificate** | Có thể là yêu cầu/chính sách mTLS của server |

**Một SSLHandshakeException có thể có nhiều nguyên nhân**, nên đừng kết luận từ tên exception ngoài cùng. Nếu root cause liên quan đến CertPathValidatorException, cần đọc đúng thông tin path validation. Nếu có fatal alert, xem log cả client và server khi có quyền.

### Bước 3 — Bật log có chọn lọc trên Java

~~~bash
java -Djavax.net.debug=ssl:handshake:trustmanager -Djava.security.debug=certpath TlsVerifiedProbe api.example.com 443
~~~

- **javax.net.debug=ssl:handshake:trustmanager**: xem giai đoạn TLS, cert được trình bày và việc lựa chọn trust manager.
- **java.security.debug=certpath**: thêm thông tin kiểm tra đường chứng chỉ và algorithm constraints.
- Log có thể thay đổi theo vendor/JDK/provider; không dùng một chuỗi log duy nhất làm giả định cứng cho mọi Java 17 patch.

**Chỉ bật log tạm thời trong môi trường phù hợp.** Metadata của endpoint và certificate có thể nhạy cảm. Tránh ghi private key, keystore password, dữ liệu ứng dụng hoặc bản dump plaintext vào logs dùng chung.

### Bước 4 — Quan sát chứng chỉ server trả

~~~bash
# In certificate do endpoint cung cấp; chưa phải kiểm tra PKIX/SAN của app.
keytool -printcert -sslserver api.example.com:443 -rfc
~~~

Nếu cần quan sát theo đúng DNS SNI bằng OpenSSL:

~~~bash
openssl s_client -connect api.example.com:443 -servername api.example.com -verify_hostname api.example.com -verify_return_error -showcerts
~~~

OpenSSL có **trust store và security policy riêng**, không nhất thiết khớp với Java. Kết quả OpenSSL thành công **không tự chứng minh** JVM dùng đúng CA hoặc endpoint identification. Phép xác nhận cuối cùng vẫn là chạy client Java giữ verification bật.

### Bước 5 — Kiểm tra truststore thật

Xem tiến trình chạy bằng **JDK nào**, giá trị **JAVA_HOME**, cấu hình **javax.net.ssl.trustStore**, kiểu store, và trust anchors bên trong. Đừng giả định browser, OS và JVM dùng chung root CA.

Nếu app chỉ định truststore riêng, nó có thể **thay tập CA mặc định** mà JVM sử dụng. Một file chỉ chứa CA nội bộ có thể khiến các endpoint public từng hoạt động trước đó bị PKIX lỗi. Kiểm tra chính xác truststore được nạp, không chỉ kiểm tra file có tồn tại.

### Bước 6 — Kiểm tra certificate, hostname và thuật toán

Đối chiếu leaf, intermediates và trust anchor; kiểm tra thời gian hiệu lực, SAN DNS/IP, issuer, signature, key strength, Extended Key Usage và đường certification path. Xem security policy đang áp dụng từ bản JDK thực tế. Không ngắt phần kiểm tra nào để tạm có kết nối thành công.

### Bước 7 — Sửa ở nguồn và thử cả trường hợp xấu

Sau khi sửa certificate/server/truststore, chạy lại cùng Java client với hostname đúng. Ngoài một ca PASS hợp lệ, cần một ca certificate không được tin cậy hoặc hostname không khớp **vẫn FAIL**. Đây là bằng chứng kiểm tra danh tính chưa bị vô hiệu hóa.

## 4. Chẩn đoán certificate chain và PKIX

### Leaf, intermediate, root/trust anchor

~~~text
Leaf: SAN api.example.com, public key dùng cho TLS server
  |
Intermediate CA: xác nhận leaf, có điều kiện CA phù hợp
  |
Root CA/trust anchor: được JVM hoặc truststore scoped tin cậy
~~~

Server thường phải gửi đủ **leaf + các intermediate cần thiết**; root vốn được client tin cậy thường không cần gửi. Java phải xây được một đường đi hợp lệ tới **trust anchor** đã cho phép, áp dụng chữ ký/độ dài khóa/BasicConstraints/KeyUsage, thời hạn và các constraint khác.

**Thiếu intermediate** có thể làm PKIX path building failed dù root CA đã nằm trong truststore. Cách sửa bền vững là triển khai server/gateway với **certificate chain chính xác**. Không dựa vào việc client may mắn có intermediate từ một nguồn khác.

**Private CA chưa được tin cậy:** cần CA public certificate của tổ chức đã được xác minh bằng **nguồn tin cậy độc lập**, rồi thêm CA đó vào **truststore đúng phạm vi**. Không tự động lấy certificate từ một kết nối đang lỗi để biến thành CA đáng tin.

**Thời hạn và đồng hồ:** CertificateExpiredException liên quan NotAfter; CertificateNotYetValidException liên quan NotBefore. Container lệch giờ có thể làm một certificate hợp lệ bị từ chối. Hãy chỉnh thời gian hoặc gia hạn/cấp certificate, không tắt bước kiểm tra thời gian.

**KeyUsage/EKU:** leaf certificate của TLS server phải phù hợp mục đích xác thực server theo đường validation của Java. Một client certificate có EKU phục vụ mTLS không thể mặc định dùng thay server certificate. Chứng chỉ CA cũng cần có những constraint CA hợp lệ.

**Thu hồi (revocation):** chính sách OCSP/CRL tùy môi trường, có thể không được bật mặc định trong mọi cấu hình JSSE. Nếu quy định bảo mật yêu cầu kiểm tra revocation, cấu hình và kiểm thử nó riêng; đừng tự khẳng định tất cả handshake Java luôn kiểm tra thu hồi trực tuyến.

### Truststore riêng, không bỏ path validation

Khi CA nội bộ đã được quản trị viên xác minh trước, có thể tạo truststore riêng cho ứng dụng:

~~~bash
# Ví dụ với file public CA certificate đã được xác nhận ngoài băng.
keytool -importcert -alias approved-corp-root -file corp-root-ca.pem -keystore app-trust.p12 -storetype PKCS12

# Kiểm tra alias, fingerprint và issuer; keytool yêu cầu mật khẩu.
keytool -list -v -keystore app-trust.p12 -storetype PKCS12
~~~

Chạy client với truststore được tổ chức quản lý:

~~~bash
java -Djavax.net.ssl.trustStore=app-trust.p12 -Djavax.net.ssl.trustStoreType=PKCS12 TlsVerifiedProbe service.corp.example 443
~~~

Các tên file và hostname trên chỉ minh họa; để chạy bạn phải có public CA certificate thật đã được kiểm tra fingerprint. Không đưa password vào source/command line hay logs. **Import CA không thay kiểm tra SAN/hostname**. Nếu cần tin cậy cả CA công cộng và CA nội bộ, hãy thiết kế tập trust anchors có quản trị thay vì nghĩ rằng Java tự ghép custom store với tất cả nguồn mặc định.

## 5. Chẩn đoán hostname, SAN và SNI

### 5.1. Hostname cần khớp SAN

Ví dụ ứng dụng gọi **https://api.example.com** nhưng leaf certificate chỉ có:

~~~text
Subject Alternative Name:
  DNS:www.example.com
  DNS:static.example.com
~~~

thì **api.example.com** không xuất hiện trong SAN và một client có hostname verification đúng phải từ chối. Certificate còn hạn và do CA uy tín ký **không sửa được sai tên**.

**Cách sửa:** triển khai cert có **dNSName SAN** phù hợp api.example.com, sửa virtual host/SNI chọn certificate đúng, hoặc sửa URL nếu ứng dụng đang dùng sai endpoint. Không dùng HostnameVerifier chấp nhận vô điều kiện.

**CN (Common Name)** không nên được coi là phương án thay thế cho SAN thiếu; certificate hiện đại nên khai báo SAN cho DNS/IP cần sử dụng. Wildcard có quy tắc giới hạn: **\*.example.com** không mặc nhiên bao phủ **v2.api.example.com** hay mọi mức subdomain. Không tự nới lỏng quy tắc wildcard.

### 5.2. Tên DNS và IP là hai dạng định danh

| Client thực sự yêu cầu | Certificate nên có |
| --- | --- |
| api.example.com | SAN loại **dNSName** khớp api.example.com |
| 192.0.2.10 | SAN loại **iPAddress** khớp địa chỉ IP |
| IPv6 literal | SAN loại **iPAddress** cho địa chỉ IPv6 đó |

Nếu client yêu cầu **api.example.com**, việc DNS phân giải thành 192.0.2.10 không bắt buộc certificate có IP SAN. Ngược lại, đổi URL sang IP chỉ để tránh một hostname mismatch thường gây mismatch mới vì chứng chỉ chỉ bảo vệ DNS name.

### 5.3. SNI chọn cert; endpoint identification kiểm tra cert

**SNI (Server Name Indication)** được gửi trong ClientHello của client để endpoint TLS nhiều virtual host có thể chọn certificate tương ứng:

~~~text
ClientHello SNI = api.example.com
       |
    TLS gateway chọn cert SAN api.example.com
       |
    Java kiểm tra chain + hostname
       |
    PASS nếu đủ điều kiện

Nếu SNI sai hoặc bị bỏ qua:
    gateway có thể gửi default cert SAN khác
    Java kiểm tra hostname -> FAIL
~~~

Một số lỗi nhìn như “certificate không khớp” thật ra do client truyền host sai cho SSLSocket, cấu hình gateway sai, hoặc corporate proxy trả certificate khác. Phải đo certificate trên **đúng đường kết nối** của ứng dụng, không chỉ trên origin.

## 6. Chẩn đoán TLS protocol, cipher và thuật toán

### 6.1. Những thuật toán thuộc các lớp khác nhau

- **TLS version**: ví dụ TLS 1.2, TLS 1.3; hai bên phải có phiên bản chung được policy cho phép.
- **Cipher suite**: mô tả bộ thuật toán bảo vệ dữ liệu và cơ chế liên quan; cách đàm phán khác giữa TLS 1.2 và TLS 1.3.
- **Certificate signature algorithm**: chữ ký trên certificate, ví dụ SHA256withRSA hay ECDSA; phải hợp lệ theo chính sách CertPath.
- **Public key size và loại key**: RSA/EC và độ dài/nhóm tương ứng; khóa quá yếu có thể bị từ chối.
- **Signature schemes/named groups**: khả năng xác thực/trao đổi khóa trong handshake, cũng có thể gây không tương thích.

Thông báo **handshake_failure** không tự nói rõ mục nào sai. Cần đối chiếu ClientHello/ServerHello và certificate chain, cùng cấu hình mTLS và trust của hai bên.

### 6.2. Hai security properties Java quan trọng

- **jdk.certpath.disabledAlgorithms**: ràng buộc thuật toán chữ ký, public key và điều kiện kiểm tra chain.
- **jdk.tls.disabledAlgorithms**: ràng buộc TLS protocol versions, cipher suites, key agreement hoặc cơ chế thuật toán TLS theo implementation.

Mặc định thay đổi theo **JDK vendor, patch level và policy**. Kiểm tra file **JAVA_HOME/conf/security/java.security** và log trong đúng JVM đang chạy, không sao chép danh sách từ một phiên bản Java khác.

Nếu có **Algorithm constraints check failed**, hãy nâng cấp server, cấp lại certificate/key phù hợp hoặc cấu hình đúng những thuật toán hiện đại được tổ chức cho phép. **Không xóa các security constraints** để “sửa” lỗi vì có thể mở lại những giao thức hay chữ ký yếu cho nhiều kết nối.

### 6.3. mTLS

Khi server yêu cầu **mutual TLS**, client phải có **client certificate và private key** phù hợp từ KeyManager/keystore, đồng thời server phải tin cậy client CA. Thêm server CA vào **client truststore** không thay thế việc cung cấp client identity. Ngược lại, cung cấp client certificate không làm mất nghĩa vụ xác minh server chain và hostname.

## 7. Ví dụ Java 17+ chạy độc lập và không bỏ xác minh

**TlsVerifiedProbe.java** tạo một TCP connection rồi bọc thành SSLSocket bằng **SSLSocketFactory mặc định** của JVM. Nó cài **HTTPS endpoint identification trước startHandshake()**, dùng CA/trust policy đang được JVM cấu hình, và **chỉ in session/certificate sau handshake thành công**. Lỗi được in cùng cause chain và **ném lại**, để bước kiểm thử không vô tình chuyển FAIL thành PASS.

Chế độ **--self-test** không kết nối ra mạng: nó kiểm tra SSLParameters đã đặt "HTTPS" và có enabled protocols. Đó là kiểm tra cấu hình cục bộ, **không thay thế một handshake thực với hostname thật**.

### Tệp TlsVerifiedProbe.java

~~~java
import java.net.InetSocketAddress;
import java.net.Socket;
import java.security.cert.X509Certificate;
import java.util.Collection;
import java.util.List;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLSession;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSocketFactory;

public class TlsVerifiedProbe {
    static final int CONNECT_TIMEOUT_MS = 5000;
    static final int READ_TIMEOUT_MS = 8000;

    static void selfTest() throws Exception {
        try (SSLSocket socket =
                (SSLSocket) SSLSocketFactory.getDefault().createSocket()) {
            SSLParameters settings = socket.getSSLParameters();
            settings.setEndpointIdentificationAlgorithm("HTTPS");
            socket.setSSLParameters(settings);
            check("HTTPS".equals(socket.getSSLParameters()
                    .getEndpointIdentificationAlgorithm()),
                    "HTTPS endpoint identification missing");
            check(socket.getEnabledProtocols().length > 0,
                    "No enabled TLS protocols");
            System.out.println("PASS: HTTPS endpoint identification configured");
            System.out.println("PASS: TLS protocols enabled");
            System.out.println("PASS: self-test made no network connection");
        }
    }

    static void check(boolean valid, String message) {
        if (!valid) throw new IllegalStateException(message);
    }

    static void probe(String host, int port) throws Exception {
        try (Socket transport = new Socket()) {
            transport.connect(new InetSocketAddress(host, port),
                    CONNECT_TIMEOUT_MS);
            transport.setSoTimeout(READ_TIMEOUT_MS);

            SSLSocketFactory factory =
                    (SSLSocketFactory) SSLSocketFactory.getDefault();
            try (SSLSocket tls = (SSLSocket) factory.createSocket(
                    transport, host, port, false)) {
                tls.setUseClientMode(true);
                tls.setSoTimeout(READ_TIMEOUT_MS);

                SSLParameters settings = tls.getSSLParameters();
                settings.setEndpointIdentificationAlgorithm("HTTPS");
                tls.setSSLParameters(settings);
                tls.startHandshake();

                SSLSession session = tls.getSession();
                X509Certificate leaf =
                        (X509Certificate) session.getPeerCertificates()[0];
                leaf.checkValidity();

                System.out.println("VERIFIED: " + host + ":" + port);
                System.out.println("Protocol: " + session.getProtocol());
                System.out.println("Cipher suite: " + session.getCipherSuite());
                System.out.println("Subject: " +
                        leaf.getSubjectX500Principal().getName());
                System.out.println("Issuer: " +
                        leaf.getIssuerX500Principal().getName());
                System.out.println("Not before: " +
                        leaf.getNotBefore().toInstant());
                System.out.println("Not after: " +
                        leaf.getNotAfter().toInstant());

                Collection<List<?>> names =
                        leaf.getSubjectAlternativeNames();
                if (names != null) {
                    for (List<?> san : names) {
                        int type = (Integer) san.get(0);
                        if (type == 2 || type == 7) {
                            System.out.println("SAN " +
                                    (type == 2 ? "DNS" : "IP") + ": " +
                                    san.get(1));
                        }
                    }
                }
            }
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length == 1 && "--self-test".equals(args[0])) {
            selfTest();
            return;
        }
        if (args.length < 1 || args.length > 2 || args[0].isBlank()
                || args[0].contains("/") || args[0].contains(":")) {
            throw new IllegalArgumentException(
                    "Usage: java TlsVerifiedProbe dns-host [port]");
        }
        int port = args.length == 2 ? Integer.parseInt(args[1]) : 443;
        if (port < 1 || port > 65535) {
            throw new IllegalArgumentException("Port out of range");
        }

        try {
            probe(args[0], port);
        } catch (Exception ex) {
            System.err.println("NOT VERIFIED: " +
                    ex.getClass().getSimpleName() + ": " + ex.getMessage());
            for (Throwable cause = ex.getCause(); cause != null;
                    cause = cause.getCause()) {
                System.err.println("Caused by " +
                        cause.getClass().getSimpleName() + ": " +
                        cause.getMessage());
            }
            throw ex;
        }
    }
}
~~~

### Biên dịch và chạy

Lưu mã vào tệp **TlsVerifiedProbe.java** và sử dụng **JDK 17 trở lên**:

~~~bash
javac --release 17 -encoding UTF-8 TlsVerifiedProbe.java
java TlsVerifiedProbe --self-test
~~~

**Stdout chính xác của chế độ tự kiểm tra (đã thử bằng Java runtime):**

~~~text
PASS: HTTPS endpoint identification configured
PASS: TLS protocols enabled
PASS: self-test made no network connection
~~~

Chạy với DNS hostname thật do bạn được phép kiểm thử:

~~~bash
java TlsVerifiedProbe api.example.com 443
~~~

**api.example.com chỉ là hostname minh họa**, hãy dùng endpoint thật trong bài tập. Khi TLS được xác minh, chương trình in **VERIFIED: host:port**, protocol, cipher suite, certificate subject/issuer, thời hạn và các DNS/IP SAN. Khi thất bại, chương trình in **NOT VERIFIED**, liệt kê nguyên nhân và vẫn ném exception; không tự động fallback hay bật trust-all.

Đầu vào của ví dụ được tối giản cho DNS hostname hoặc IPv4 và port; không chấp nhận URL đầy đủ hay IPv6 literal chứa dấu hai chấm. API thực tế cần parse URI/host đúng chuẩn nếu hỗ trợ nhiều dạng địa chỉ.

**Vì sao giữ được verification?** Code không thay TrustManager, truyền hostname mong đợi vào layered socket, đặt endpoint identification **HTTPS** và bắt buộc startHandshake hoàn tất trước khi đọc session/cert. Transport và SSLSocket đều được đóng qua try-with-resources. **Tuy nhiên**, nếu môi trường JVM đã được người vận hành cấu hình một truststore rộng hơn policy mong muốn, app vẫn phải kiểm soát cấu hình CA đó; không có self-test nào thay việc rà soát trust policy thực tế.

## 8. Ba tình huống sửa lỗi đúng

### A. Browser được nhưng Java báo PKIX

**Nguyên nhân khả dĩ:** Java và browser dùng trust anchors khác nhau; Java trustStore override sai; server không gửi intermediate; private CA chưa được cho phép.

**Cách sửa:** kiểm tra chain/truststore đang dùng, đối chiếu fingerprint CA ngoài băng, triển khai full chain, cấu hình CA được phép vào truststore đúng phạm vi. Thử lại Java với verification bật.

**Không nên:** cho client tin mọi certificate hoặc tự import một leaf certificate chưa được xác thực chỉ vì lỗi tạm thời biến mất.

### B. Java báo No subject alternative DNS name matching

**Nguyên nhân khả dĩ:** URL sai hostname, SAN không bao phủ tên đó, SNI không được gửi đúng, TLS gateway trả cert của virtual host khác, proxy can thiệp.

**Cách sửa:** cấp cert đúng SAN, sửa URL/SNI/gateway. Dùng tên DNS có chủ đích; đừng đổi thành IP rồi bỏ kiểm tra hostname.

**Không nên:** dùng HostnameVerifier vô điều kiện.

### C. Java báo Algorithm constraints check failed hoặc handshake_failure

**Nguyên nhân khả dĩ:** certificate signature/key quá cũ, server thiếu cipher/protocol chung, signature schemes không tương thích, hoặc mTLS thiếu client key/cert.

**Cách sửa:** nhìn handshake logs và security properties trong đúng JVM, nâng cấp TLS server, certificate/key, JDK hoặc cấu hình mTLS cho tương thích policy. Giữ các giới hạn thuật toán không an toàn ở trạng thái bị vô hiệu hóa.

**Không nên:** nới jdk.tls.disabledAlgorithms hay jdk.certpath.disabledAlgorithms chỉ để request qua.

## 9. Kiểm thử sau khi sửa để chứng minh verification vẫn có tác dụng

| Test | Kết quả đúng |
| --- | --- |
| Certificate hợp lệ, chain được tin cậy, hostname đúng | Handshake thành công |
| CA không nằm trong truststore | Handshake bị từ chối |
| Hostname không khớp SAN | Handshake bị từ chối |
| Leaf certificate hết hạn/chưa có hiệu lực | Handshake bị từ chối |
| Certificate/key vi phạm policy | Handshake bị từ chối |
| Không có TLS version chung | Handshake thất bại cho tới khi hai bên dùng cấu hình cho phép |
| mTLS bắt buộc nhưng client thiếu cert phù hợp | Không được xác thực thành công |
| Sửa lại cấu hình hợp lệ của từng trường hợp | Chỉ những endpoint đủ điều kiện mới được chấp nhận |

Một ca **thiếu intermediate** có thể không luôn FAIL nếu JVM có sẵn đường trust khác phù hợp; cần log PKIX path thực tế khi dựng test fixture. Một lần HTTP 200 **không đủ** chứng minh kết nối đã xác minh đúng peer nếu code đã can thiệp vào TLS validation.

Trong CI hoặc staging, nên giữ bài test âm tính với certificate không được tin hoặc hostname cố tình sai. Nếu chúng bắt đầu PASS sau khi đổi cấu hình, đó là dấu hiệu đáng nghi về xác minh danh tính.

### Checklist trước khi chốt sự cố

1. Đã xác định hostname, port và điểm TLS termination thực tế.
2. Đã lưu exception/cause chain, JDK version và thời gian xảy ra lỗi.
3. Đã kiểm tra chain, SAN, thời hạn, key usage, algorithm constraints và mTLS nếu có.
4. Đã biết truststore nào được Java nạp; fingerprint CA được xác minh độc lập.
5. Đã kiểm tra SNI, DNS và proxy khi certificate trả về không như mong đợi.
6. Đã chạy lại client **có verification** với endpoint thật.
7. Đã chứng minh endpoint sai SAN hoặc chain không đáng tin vẫn bị từ chối.
8. Đã tắt debug nhạy cảm sau khi chẩn đoán, không để bí mật trong log.

## 10. Câu hỏi tự kiểm tra

**Câu 1.** Vì sao certificate còn hạn và do CA đáng tin ký vẫn có thể bị từ chối?  
**Đáp án:** SAN sai hostname, EKU/KeyUsage hoặc thuật toán/khóa không thỏa policy, hoặc constraint PKIX khác không hợp lệ.

**Câu 2.** PKIX path building failed có chứng minh URL sai hostname?  
**Đáp án:** Không. Nó thường liên quan đến đường chain/trust anchor. Hostname là bước xác minh danh tính riêng.

**Câu 3.** Tại sao SSLSocket raw nên đặt endpoint identification algorithm HTTPS?  
**Đáp án:** Để kiểm tra chứng chỉ theo **tên peer mong muốn** trong handshake chứ không chỉ tin một chain do CA ký.

**Câu 4.** Có nên xử lý hostname mismatch bằng cách luôn cho HostnameVerifier trả true?  
**Đáp án:** Không. Cách đó bỏ điều kiện xác thực peer; phải sửa SAN, URL, SNI hoặc gateway.

**Câu 5.** Tại sao OpenSSL probe thành công mà Java vẫn báo lỗi?  
**Đáp án:** Java có truststore/provider/security policy khác, cần chạy client Java xác minh trực tiếp.

**Câu 6.** Khi kết nối bằng IP, SAN kiểu dNSName giống chuỗi IP có đủ không?  
**Đáp án:** Không nên dựa vào đó. IP literal cần iPAddress SAN thích hợp, còn DNS name cần dNSName SAN.

**Câu 7.** Lỗi algorithm constraints nên xử lý bằng cách bỏ policy cấm thuật toán?  
**Đáp án:** Không. Cập nhật certificate, server, TLS configuration hoặc runtime để dùng thuật toán được cho phép.

**Câu 8.** Mã TlsVerifiedProbe --self-test PASS có chứng minh remote certificate hợp lệ?  
**Đáp án:** Không. Nó chỉ kiểm tra cấu hình cục bộ; cần live handshake với hostname và truststore thực.

**Câu 9.** Nếu server yêu cầu mTLS, thêm root CA của server vào client truststore đã đủ chưa?  
**Đáp án:** Chưa. Client cần chứng chỉ và private key phù hợp; phía server còn phải xác minh client.

**Câu 10.** Điều kiện nào chứng minh sửa lỗi TLS là an toàn?  
**Đáp án:** Endpoint hợp lệ PASS, endpoint sai chain/SAN/algorithm vẫn FAIL, và không có bước verification nào bị tắt.

## Kết luận

**Không sửa lỗi TLS bằng cách làm yếu xác minh.** Hãy xác định đúng endpoint, đọc cause chain và JSSE/CertPath logs, kiểm tra chain/truststore, SAN/SNI, thuật toán và mTLS. Sau khi cập nhật cấu hình, chạy lại Java client với hostname đúng, giữ cơ chế PKIX và HTTPS endpoint identification, đồng thời kiểm thử các kết nối không hợp lệ vẫn bị từ chối.
