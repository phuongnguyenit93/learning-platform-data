# Receive Buffer Too Small, Truncated Data, and Actual Received Packet Length in UDP

## 1. When a Datagram Is Larger Than the Receive Region

UDP transmits data in individual **datagrams** with their own message boundaries. One `DatagramSocket.send(DatagramPacket)` call sends one datagram; one `DatagramSocket.receive(DatagramPacket)` call receives one datagram. Unlike a TCP byte stream, UDP **does not allow the application to read the remaining part of the same datagram with another receive call**.

For example, the sender sends exactly 12 ASCII bytes `ABCDEFGHIJKL`, but the receiver allocates a receive region of at most 5 bytes:

```text
Sender:    A B C D E F G H I J K L   (12 bytes)
Receiver: [A B C D E]                 (5 bytes)
           ^^^^^^^^^
           bytes copied into the array

packet.getLength() = 5
F G H I J K L    = trailing part of the datagram discarded
```

**This is truncation—meaning data is cut off.** The `receive()` call can complete normally when the payload is truncated; it does not throw an exception by default to warn about missing bytes. Receiving the next packet only retrieves a **new datagram**, not the truncated trailing part.

Three fundamental rules:

1. **`packet.getLength()` after receiving** returns the number of bytes received into the `DatagramPacket`'s region. When the buffer is too small, this number **does not reflect the full length of the original datagram on the network**.
2. **`packet.getData().length`** is the capacity of the backing array, not the number of valid bytes in the receive operation.
3. If the number of bytes received equals the **receive region limit**, you cannot conclude with certainty from that comparison alone whether the datagram was truncated: a packet that fits exactly and an oversized packet can produce the same result.

This differs from a packet lost on the network: truncation occurs when **a datagram has arrived, but the container allocated for the application is insufficient**; packet loss is when the datagram is not delivered to the application at all. In production, both can occur and must be analyzed separately.

## 2. Four Types of Length to Distinguish

| Concept | Meaning | What Must Not Be Inferred |
| --- | --- | --- |
| `byte[] buffer.length` | Total number of elements in the Java array | Not the length of the received datagram |
| `DatagramPacket(buffer, offset, length)` | Allocated receive region, starting at `offset`, up to `length` bytes | A large array is useless if the `length` parameter is too small |
| `packet.getLength()` **after** `receive()` | Actual number of bytes placed into the packet in the most recent receive | Does not prove the sender only sent that many bytes |
| Payload length **declared by the application protocol** | Expected size taken from the header or message specification | Not inherently trustworthy if the sender is buggy or input data is unauthenticated |

APIs in Java 17+:

- `new DatagramPacket(buf, length)`: uses the region starting at offset 0, up to `length` bytes, as the receive target.
- `new DatagramPacket(buf, offset, length)`: receives into the region `buf[offset ... offset+length)`. Parameters must be within array bounds.
- `socket.receive(packet)`: waits for a datagram, writes bytes into the provided region, and updates metadata including source IP/port and received length.
- `packet.getData()`: returns the backing array, including regions **not** belonging to the payload just received.
- `packet.getOffset()`: indicates the starting position of the payload inside the array.
- `packet.getLength()`: after `receive()` finishes, returns the number of bytes received into the packet.
- `packet.setLength(n)`: sets the number of bytes used when sending or the receive region limit when receiving. If offset is non-zero, you must ensure `offset+n <= buf.length`.
- `packet.getAddress()`/`getPort()`: source address/port after receiving, useful for replying and logging, **not proof of identity authentication**.

**Correct:** convert the payload into a string using the actual offset and length:

```java
// Code snippet inside a method that already has DatagramSocket socket.
// The enclosing method handles IOException.
byte[] data = new byte[2048];
DatagramPacket packet = new DatagramPacket(data, data.length);
socket.receive(packet);

String text = new String(
        packet.getData(),
        packet.getOffset(),
        packet.getLength(),
        StandardCharsets.UTF_8);
```

Import `java.net.DatagramPacket` and `java.nio.charset.StandardCharsets` when using the snippet above. If you call `new String(packet.getData())`, the program will also decode bytes outside the payload, including zeros or stale data from previous receives.

## 3. Java 17 Experiment: Truncation, New Packets, and Receive Limits

The program uses UDP loopback and does not require internet access. It actively sends ASCII datagrams and compares receive regions of 5, 16, and 32 bytes. `setSoTimeout(2000)` prevents hanging indefinitely if the test environment encounters a receive failure; it is a read timeout, **not a truncation detection tool**.

**`UdpTruncationDemo.java`**

```java
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public final class UdpTruncationDemo {
    private static void send(DatagramSocket sender,
            InetSocketAddress target, String text) throws Exception {
        byte[] data = text.getBytes(StandardCharsets.UTF_8);
        sender.send(new DatagramPacket(data, data.length, target));
    }

    private static void show(String label, DatagramPacket packet) {
        String text = new String(packet.getData(), packet.getOffset(),
                packet.getLength(), StandardCharsets.UTF_8);
        System.out.println(label + ": length=" + packet.getLength()
                + ", text=" + text);
    }

    public static void main(String[] args) throws Exception {
        InetAddress loopback = InetAddress.getLoopbackAddress();
        try (DatagramSocket receiver = new DatagramSocket(0, loopback);
             DatagramSocket sender = new DatagramSocket(0, loopback)) {
            receiver.setSoTimeout(2000);
            InetSocketAddress target =
                    new InetSocketAddress(loopback, receiver.getLocalPort());

            byte[] small = new byte[5];
            DatagramPacket packet = new DatagramPacket(small, small.length);
            send(sender, target, "ABCDEFGHIJKL");
            receiver.receive(packet);
            show("small", packet);

            // The next receive gets a NEW datagram, not the trailing part.
            packet.setLength(small.length);
            send(sender, target, "Z");
            receiver.receive(packet);
            show("next", packet);

            byte[] large = new byte[32];
            DatagramPacket big = new DatagramPacket(large, large.length);
            send(sender, target, "ABCDEFGHIJKL");
            receiver.receive(big);
            show("large", big);

            byte[] storage = new byte[16];
            DatagramPacket reusable =
                    new DatagramPacket(storage, storage.length);
            send(sender, target, "PING");
            receiver.receive(reusable);
            show("reuse-first", reusable);

            // Set a 4-byte receive limit on an array that is actually 16 bytes long.
            reusable.setLength(4);
            send(sender, target, "LONGER-DATA");
            receiver.receive(reusable);
            show("explicit-limit4", reusable);

            // Restore the limit to the desired receive region.
            reusable.setLength(storage.length);
            send(sender, target, "LONGER-DATA");
            receiver.receive(reusable);
            show("reset-limit16", reusable);
        }
    }
}
```

Compile/run:

```bash
javac --release 17 UdpTruncationDemo.java
java UdpTruncationDemo
```

Output in the loopback test environment:

```text
small: length=5, text=ABCDE
next: length=1, text=Z
large: length=12, text=ABCDEFGHIJKL
reuse-first: length=4, text=PING
explicit-limit4: length=4, text=LONG
reset-limit16: length=11, text=LONGER-DATA
```

Explanation of each milestone:

1. **`small`:** 12 bytes were created and sent by the sender, but the receiver's packet only holds 5 bytes. `getLength()==5` is the length **received into the packet**, and cannot be used as proof that the sender only sent 5 bytes.
2. **`next`:** the new datagram containing `Z` is read separately, without the missing `FGHIJKL` sequence from the previous packet. An oversized datagram does not turn into multiple `receive()` calls.
3. **`large`:** when the receiver prepares a 32-byte region **before receiving**, the 12 bytes of the sample datagram fit completely into the packet.
4. **`reuse-first`:** after receiving `PING`, the length of the content just received is 4 bytes; do not equate this number with the capacity of the entire 16-byte array.
5. **`explicit-limit4`:** `setLength(4)` explicitly allows only 4 bytes to be used for the next receive, so `LONGER-DATA` is truncated to `LONG`. **`reset-limit16`** reopens the receive region and receives all 11 bytes.

**Commonly misinterpreted point:** from `getLength()` being 4 after receiving `PING`, you must not assert that **every** subsequent receive is necessarily limited to 4 bytes. In experiments on the JDK, a packet whose initial receive region is wide can still receive longer messages on subsequent turns. Actually narrowing a receive turn is clearly demonstrated by an **explicit `setLength(4)` call**. To keep code predictable, you can set the desired receive region limit with `setLength(...)` before each reuse turn.

UDP can drop or reorder packets on a real network; the ordering in the loopback program only illustrates behavior under test conditions, not a transport guarantee of UDP.

## 4. Why `getLength() == capacity` Is Not Proof of Truncation

Two different inputs can produce the same result on the receiver side:

```text
Receiver configuration: length = 8

A. Sender sends 8 bytes   -> receives 8 bytes, complete
B. Sender sends 30 bytes  -> receives 8 bytes, 22 bytes truncated

Common observation: packet.getLength() == 8
```

Therefore, both of the following statements are inaccurate:

- "Received 8 bytes ⇒ the original datagram was 8 bytes long".
- "8-byte buffer is full ⇒ the datagram was definitely truncated".

A better design approach is to agree on a **protocol-level frame size limit** and validate frame integrity. If the maximum valid limit is `MAX_FRAME=1200` bytes, you can allocate a **1201-byte** receive region to distinguish an allowed frame (up to 1200) from a frame that clearly violates the limit:

```java
// Code snippet inside a method that has socket and handles IOException.
int maxFrame = 1200;
byte[] buf = new byte[maxFrame + 1];
DatagramPacket p = new DatagramPacket(buf, buf.length);
socket.receive(p);

if (p.getLength() > maxFrame) {
    throw new IOException("Oversized UDP frame");
}
```

If 1201 bytes are received, we know the datagram **exceeds the 1200-byte policy**, though we still do not know its exact original size if it was truncated at 1201. The "add one byte" technique helps enforce a **protocol limit**, not obtain the true length of an arbitrary datagram.

If the content format must contain certain required fields, you can use a length header and appropriate payload/CRC/MAC checks. A system should not merely check `getLength()==buf.length` and then assign a "truncated" or "valid" status by default.

## 5. Length-Prefix Design to Detect Incomplete Payloads

A common way to detect an incomplete payload is to place the **expected length directly inside the datagram content**:

```text
UDP application payload = [4 bytes: N][N bytes UTF-8 body]
                            big endian

Receiver knows:
  actualDatagramBytes = packet.getLength()
  actualBodyBytes     = actualDatagramBytes - 4
  announcedBodyBytes  = N
  valid in size ⇔ actualBodyBytes == N
```

Validation conditions:

- First receive all 4 header bytes; if insufficient, reject.
- Do not trust `N` from the sender: check `N >= 0`, `N <= MAX_PAYLOAD`, avoiding oversized allocations.
- Compare the actual remaining bytes in the datagram with `N`. Reject both missing and extra bytes if the protocol specifies an exact match.
- Do not append trailing bytes from the next datagram to "fill in" an incomplete frame. UDP only preserves individual datagram boundaries; if the application wants to split and reassemble across multiple datagrams, it must have its own protocol with ID/index/part count.
- A length-prefix helps detect **size inconsistency**. If the sender intentionally declares an incorrect length or the payload is tampered with, additional integrity/source checks are required.

**`UdpFrameValidationDemo.java`** illustrates encoding and decoding (pure in-memory test, no socket sends):

```java
import java.io.IOException;
import java.nio.ByteBuffer;
import java.nio.ByteOrder;
import java.nio.charset.StandardCharsets;

public final class UdpFrameValidationDemo {
    private static final int MAX_PAYLOAD = 1024;

    static byte[] encode(String value) {
        byte[] body = value.getBytes(StandardCharsets.UTF_8);
        if (body.length > MAX_PAYLOAD) {
            throw new IllegalArgumentException("Payload too large");
        }
        ByteBuffer frame = ByteBuffer.allocate(4 + body.length)
                .order(ByteOrder.BIG_ENDIAN);
        frame.putInt(body.length);
        frame.put(body);
        return frame.array();
    }

    static String decode(byte[] data, int offset, int receivedLength)
            throws IOException {
        if (receivedLength < 4) {
            throw new IOException("Missing length header");
        }
        ByteBuffer frame = ByteBuffer.wrap(
                data, offset, receivedLength).order(ByteOrder.BIG_ENDIAN);
        int announced = frame.getInt();
        if (announced < 0 || announced > MAX_PAYLOAD) {
            throw new IOException("Invalid declared length");
        }
        if (frame.remaining() != announced) {
            throw new IOException("Incomplete or extra payload");
        }
        byte[] body = new byte[announced];
        frame.get(body);
        return new String(body, StandardCharsets.UTF_8);
    }

    public static void main(String[] args) throws Exception {
        byte[] encoded = encode("ABCDEF");
        System.out.println("full: " + decode(encoded, 0, encoded.length));

        // Simulate a receive that only retains a frame missing the last 2 bytes.
        try {
            decode(encoded, 0, encoded.length - 2);
            throw new AssertionError("Expected truncation rejection");
        } catch (IOException e) {
            System.out.println("truncated: rejected");
        }

        byte[] withOffset = new byte[encoded.length + 4];
        System.arraycopy(encoded, 0, withOffset, 2, encoded.length);
        System.out.println("offset: "
                + decode(withOffset, 2, encoded.length));
    }
}
```

```bash
javac --release 17 UdpFrameValidationDemo.java
java UdpFrameValidationDemo
```

```text
full: ABCDEF
truncated: rejected
offset: ABCDEF
```

When receiving real UDP data, use:

```java
String decoded = UdpFrameValidationDemo.decode(
        packet.getData(), packet.getOffset(), packet.getLength());
```

*This is an API integration snippet inside a method that already has the `packet` variable and handles `IOException`.* The length `getLength()` is the number of received bytes for the decoder to inspect. If the sender declares a 6-byte body but the receiver only has the header + 4 body bytes, the decoder reports an error. It does not inherently know what values the two missing bytes had and does not automatically request retransmission. For a datagram truncated to the point of losing even the header, the decoder rejects it immediately at the four-byte check step.

Note: checking `announced == frame.remaining()` only checks length consistency. For untrusted data or when security is required, you must still validate the format, checksum/MAC, or use a security protocol such as DTLS depending on requirements.

## 6. Reading the Correct Offset and Avoiding Stale Data

The receive region can start at a non-zero offset:

```java
byte[] storage = new byte[256];
DatagramPacket p = new DatagramPacket(storage, 10, 100);
socket.receive(p);

int begin = p.getOffset();
int endExclusive = begin + p.getLength();
byte[] payload = java.util.Arrays.copyOfRange(
        p.getData(), begin, endExclusive);
```

*Illustration snippet using an existing `socket` variable with `IOException` handled externally.*

If `p.getOffset()==10` and `p.getLength()==6`, then the valid bytes are in `storage[10]..storage[15]`. Taking `storage[0]..storage[5]` or the entire `storage.length==256` will read the wrong position/content.

A reused array is not automatically cleared in full after a short datagram. For example, if the previous turn received 90 bytes and the next turn receives 3 bytes, the bytes located after the 3-byte region may still contain data from the old packet. **Do not truncate at zero bytes, and do not use `trim()` to "fix" the payload**: UDP can carry valid binary data containing byte 0.

Byte length also does not equal character count. UTF-8 has multi-byte characters; if truncation cuts in the middle of a character, calling `new String(..., UTF_8)` may insert replacement characters (``). However, if it cuts cleanly on a character boundary, the string may still look valid despite missing the end. Therefore, do not use UTF-8 validity as the sole way to detect a truncated payload. When you need to reject malformed UTF-8, use `CharsetDecoder` with `CodingErrorAction.REPORT` after length/frame validation has been performed.

## 7. Reusing `DatagramPacket` and `setLength`

`DatagramPacket` holds the buffer, offset, length, and metadata. If the application explicitly narrows the receive region via `setLength(4)`, then a datagram longer than four bytes is truncated upon receipt at that limit, even if the backing array still has space. If you want to receive up to the entire array, you must set the appropriate limit before the receive turn:

```java
// Code snippet in a receive loop that already has socket and running variable.
byte[] storage = new byte[2048];
DatagramPacket packet = new DatagramPacket(storage, storage.length);

while (running) {
    packet.setLength(storage.length - packet.getOffset());
    socket.receive(packet);
    handleDatagram(packet.getData(),
            packet.getOffset(), packet.getLength());
}
```

In a real program, you must add `IOException` handling, a shutdown mechanism, and message limits; `handleDatagram(...)` is an application-provided function.

Setting `setLength` explicitly before a receive turn prevents accidentally keeping a narrow limit configured earlier in the code. However, **you must not make the one-way assumption that a small `getLength()` from a previous datagram automatically narrows the receive region of every subsequent turn**. Tests with the JDK show that after receiving `PING` with `getLength()==4`, a packet initially allocated with a 16-byte region can still receive 11 bytes on the next turn if `setLength(4)` is not intentionally called. That is why you should clearly distinguish **the length metadata of the packet just received** from **the container region policy allocated for the receive turn**.

If you swap the array via `setData(...)`, you must update/recheck the offset and length. You should not share a single mutable `DatagramPacket` for concurrent `receive()` calls from multiple threads and expect each packet's data and metadata to be preserved.

## 8. Two Buffer Layers: `DatagramPacket` and `SO_RCVBUF`

`DatagramSocket.setReceiveBufferSize(...)` sets a hint for the **operating system-level socket receive buffer**, which serves the queue of datagrams not yet dequeued by the application. This is distinct from `new byte[1024]`, which Java uses to hold **one** datagram already dequeued from the queue.

```text
Network packet
     |
     v
+-------------------------------+
| OS socket receive queue       |  <--- SO_RCVBUF
| multiple waiting datagrams    |
+---------------+---------------+
                |
                | DatagramSocket.receive(packet)
                v
+-------------------------------+
| Java DatagramPacket region    |  <--- byte[] + offset + length
| one datagram at that moment   |
+---------------+---------------+
                |
                v
packet.getLength() = bytes actually delivered into the packet
```

| Symptom | Appropriate Measure | Limitation of Measure |
| --- | --- | --- |
| Datagram payload truncated because Java receive region is small | Increase `DatagramPacket` region according to protocol max size | Does not recover packets that were already truncated |
| Burst of many datagrams, process cannot dequeue fast enough | Improve receive loop performance, consider increasing `SO_RCVBUF` | OS may cap/treat as a hint; does not guarantee zero drops |
| No datagram arrives before deadline | `setSoTimeout` and retry/heartbeat policy | Does not reveal whether any datagram was truncated |
| Large packet lost due to fragmentation/MTU | Use smaller datagrams, chunking/reassembly if needed | A large Java buffer does not fix packet loss in transit |
| Protocol length overflow | Validate header length, max size, and reject | Cannot retrieve original datagram size from truncated API |

Example of configuring the socket receive queue:

```java
socket.setReceiveBufferSize(256 * 1024);
int reported = socket.getReceiveBufferSize();
// reported is the socket-side buffer size reported by the OS.
// It does not change the application's byte[]/DatagramPacket.
```

The requested value is a **hint**; the actual size and when it can be adjusted depend on the OS/JDK. Do not replace `DatagramPacket(..., 5)` with a `setReceiveBufferSize(256*1024)` call and expect to receive a full 100-byte payload; those are two separate layers.

## 9. MTU, Large Datagrams, and Reliable Protocols

Even when allocating a very large array, UDP does not guarantee that large datagrams will always arrive:

- UDP payload size is constrained by IPv4/IPv6 and headers; the practical limit also depends on **Path MTU**, tunnels, VPNs, NATs, and firewalls.
- Large IP datagrams may be fragmented when the protocol/path allows. If one fragment is lost, the entire datagram may not be delivered to the application.
- UDP does not inherently guarantee delivery, ordering, deduplication, or application-level ACKs. A successful `DatagramSocket.send()` does not prove the remote application received the payload.
- A large receiver array reduces the risk of truncation **after** the datagram arrives, but it does not prevent packet loss on the network.
- If large messages must be sent, the application protocol needs `messageId`, `chunkIndex`, total part count, total byte limit, reassembly timeout, integrity checks, deduplication, and a retransmission request policy. Do not treat a second datagram as the "continuation" of a truncated first datagram unless **the application protocol itself** designs ordered/ID-based chunking.

For most custom-designed protocols, choosing **small datagrams and clear size constraints** is more reliable than relying on very large payloads or IP fragmentation.

## 10. When Using `DatagramChannel` and `ByteBuffer`

In NIO, `DatagramChannel.receive(ByteBuffer)` places the payload into the `remaining()` portion of the `ByteBuffer`. If the datagram is longer than the remaining space, the excess may be discarded, similar to the small-buffer issue.

Code snippet for a bound **blocking** channel, with exception handling outside:

```java
ByteBuffer buffer = ByteBuffer.allocate(2048);
buffer.clear();                 // position=0, limit=capacity
SocketAddress sender = channel.receive(buffer);
int received = buffer.position();
buffer.flip();                  // limit reading to the exact number of bytes just written

// Parse 'received' bytes from buffer, do not use buffer.capacity()
// as the actual datagram length.
```

If the channel is non-blocking, `receive(buffer)` can return `null` when no datagram is available; that is not a zero-length datagram. If `ByteBuffer.position()` before receive is non-zero, the actual received length must be calculated as **position after − position before**. `flip()` adjusts the read region for what was written; it does not help recover any truncated trailing data.

## 11. Boundary Tests and Diagnostic Signs

When testing a receiver, include at least the following cases:

1. **Shorter than capacity:** send 3 bytes into a 1024-byte buffer; `getLength()==3`; parser does not read stale trailing bytes.
2. **Equal to capacity:** send exactly 1024 bytes into a 1024-byte buffer; result is 1024, cannot yet infer truncation.
3. **Larger than capacity:** send 1200 bytes into a 1024-byte region; receives at most the allocated region; check protocol header or sentinel to reject.
4. **Missing header:** receive fewer than 4 bytes in a four-byte length-prefix protocol; reject before calling `getInt()`.
5. **Missing body:** header declares N=100, region has 4 header + 40 body bytes; reject, do not concatenate the next datagram.
6. **Non-zero offset:** use `new DatagramPacket(buf, 8, 200)`, parser must start from offset 8.
7. **Reused array:** receive a long packet then a short packet; prevent old bytes from leaking into the new frame.
8. **Explicit limit:** use `setLength(4)` then reset; result depends on the **configured receive region**.
9. **Multi-byte UTF-8:** cut in the middle of a character; reject malformed input per protocol, while also verifying length.
10. **Empty datagram, timeout, drop:** a zero-byte datagram can have `getLength()==0`; `SocketTimeoutException` means no datagram was received within the wait period, not a truncation error.

To troubleshoot, log the **sender-side size before send**, receive region size, `getLength()` after receive, address/port, and request/message ID. Avoid logging entire sensitive payloads. Packet capture can help compare the actual datagram length on the network with the number of bytes received by the application, though traffic can be dropped before reaching the process, so only draw conclusions within the observed scope.

## 12. Common Mistakes

| Mistake | Why Is It Wrong? | Fix |
| --- | --- | --- |
| Using `byte[256]` for a protocol allowing 1 KB | Large datagrams have their tails truncated | Allocate region according to protocol limit |
| Calling `new String(packet.getData())` | Decodes the whole array, including garbage/stale bytes | Use `getOffset()` and `getLength()` |
| Treating `getLength()` as the sender's original size | Truncation reduces the number of received bytes | Application header, tests, and framing checks |
| Seeing `getLength()==capacity` and definitely reporting "truncated" | The datagram might fit exactly | Check contract length and sentinel |
| Calling `receive()` again to get the missing part | UDP does not split a datagram across multiple reads | Only retry/resend per protocol |
| Increasing `SO_RCVBUF` while still using packet length=5 | Socket queue is separate from Java packet region | Increase receive region at the right layer |
| Forgetting to reset limit after `setLength(4)` | Subsequent receives are restricted by the narrow config | Set `setLength(capacity-offset)` when needed |
| Assuming a small `getLength()` after receive definitely narrows all future receives | Confuses data size with receive configuration | Configure receive region explicitly |
| Using UTF-8 replacement character as the sole detector | Payload can be cut on a character boundary | Framing + validation |
| Trusting sender-provided length to allocate arbitrarily | Can cause OOM or data attacks | Check bounds before allocating |
| Expecting a large buffer to guarantee reliable UDP | Network can drop, reorder, or lose fragments | Reduce size, ACK/retry when needed |

## 13. Self-Check Exercises

**Question 1.** Sender sends 900 bytes; receiver uses `new DatagramPacket(new byte[512], 512)`. After `receive()`, `getLength()==512`. Can we be sure the sender only sent 512 bytes? Can we call `receive()` again to get the remaining 388 bytes?

**Question 2.** Receiver has `byte[2048]` but creates `new DatagramPacket(buffer, 100)`. Can a 300-byte datagram be truncated? Why?

**Question 3.** A protocol has a 4-byte length-prefix, the header announces a 100-byte body, but the entire received datagram is only 44 bytes. What should the decoder do?

**Question 4.** Packet has `offset=10` and `getLength()==6`. Where are the bytes read from? Why is reading `data[0..5]` wrong?

**Question 5.** Packet initially has a 16-byte array and just received `PING`, `getLength()==4`. Can we conclude with certainty that the next receive will only accept at most 4 bytes? What if the code explicitly called `setLength(4)`?

**Question 6.** Does `setReceiveBufferSize(262144)` automatically expand `DatagramPacket`'s `byte[128]` array?

**Suggested Answers:** (1) cannot know original length from getLength alone, truncated part cannot be read further; (2) yes, the packet limit is set by the `100` parameter; (3) reject the incomplete frame (4+100 differs from 44), do not append a new datagram; (4) valid data is at indices 10–15; (5) cannot conclude from previous getLength, but `setLength(4)` explicitly enforces a four-byte limit; (6) no, `SO_RCVBUF` adjusts the OS-level socket receive queue, not the Java array.
