# SSLContext, SSLSocketFactory, SSLSocket, and SSLServerSocket in Java TLS

## 1. Lesson Objectives

In Java Advanced Networking, **TLS** (Transport Layer Security) protects data running over a TCP connection using peer authentication, cryptographic algorithm negotiation, encryption, and integrity protection. The **JSSE** (Java Secure Socket Extension, in `javax.net.ssl`) API allows Java applications to establish TLS without implementing TLS algorithms themselves.

The four objects to distinguish are:

- **`SSLContext`:** a TLS configuration/context containing `KeyManager`s, `TrustManager`s, and a random number source used to create TLS endpoints.
- **`SSLSocketFactory`:** a factory that creates **TLS client sockets** based on the selected `SSLContext`.
- **`SSLSocket`:** a specific TLS socket, typically used to establish a TCP connection, perform the handshake, and read/write TLS-protected application data.
- **`SSLServerSocket`:** a server-side **TLS listening socket**; `accept()` creates a separate `SSLSocket` to handle the accepted client.

You also need to understand **`SSLServerSocketFactory`**, because `SSLContext.getServerSocketFactory()` returns this object to create an `SSLServerSocket`; the four classes in the title alone do not fully describe the server listener creation step.

After this lesson, you will know how to:
1. Correctly map the `SSLContext → factory → socket → TLS handshake` relationship and distinguish a listening socket from an accepted socket.
2. Configure server identity using a **keystore/private key** and configure client trust using a **truststore/CA**, without using "trust-all".
3. Create an HTTPS-style connection **with hostname verification** when using `SSLSocket` directly, rather than only trusting certificates by chain.
4. Run a Java 17+ **TLSv1.3 loopback** example using all of `SSLContext`, `SSLSocketFactory`, `SSLSocket`, and `SSLServerSocket`.
5. Understand the handshake, TLS session, cipher suite, client authentication (mTLS), timeouts, socket closing, and common errors.

> **Orientation:** class names still carry the "SSL" prefix due to JSSE history; the example configuration uses **TLSv1.3**, not the obsolete SSLv2/SSLv3 protocols.

## 2. JSSE Architecture Map

```text
                        Java application
                        ┌────────────────────────────┐
                        │ Protocol code / streams    │
                        └─────────────┬──────────────┘
                                      │
             CLIENT                   │                        SERVER
                                      │
   ┌───────────────────────┐          │         ┌────────────────────────┐
   │ Trusted certificates  │          │         │ Identity certificate   │
   │ / CA truststore       │          │         │ + server private key   │
   └──────────┬────────────┘          │         └────────────┬───────────┘
              ▼                       │                      ▼
      TrustManagerFactory             │              KeyManagerFactory
              │                       │                      │
              ▼                       │                      ▼
     SSLContext (client)              │             SSLContext (server)
              │                       │                      │
              ▼                       │                      ▼
       SSLSocketFactory               │             SSLServerSocketFactory
              │                       │                      │
              ▼                       │                      ▼
         SSLSocket  ───── TCP + TLS handshake ────── SSLServerSocket
              │                                               │
              │                                               ▼ accept()
              └────────── encrypted TLS records ──────── SSLSocket
                              │                                 │
                      Application I/O                    Application I/O
```

Mental flow:

1. **`SSLContext`** is the source of cryptographic configuration and session management used to produce sockets/engines; it is **not** a TCP connection.
2. A **Factory** takes configuration from the context and creates the appropriate socket. A single factory can be reused to create **multiple** sockets.
3. **`SSLServerSocket`** only **binds, listens, and accepts**. It is not the stream for exchanging application data with all clients; each `accept()` returns a separate TLS socket.
4. **`SSLSocket`** represents **a single connection**, holding handshake/session state and `InputStream`, `OutputStream`.
5. After the handshake completes, bytes written to the application stream are encapsulated by JSSE into **TLS records** before going over TCP; bytes read out are plaintext **after TLS processing**.

TLS adds communication security. **It does not replace** protocol framing: `SSLSocket.getInputStream()` is still a byte stream; if the application sends multiple messages, it must define a length-prefix, delimiter, or protocol such as HTTP.

## 3. Classes, Roles, and Lifecycles

| Component | Type/Characteristics | Created By | Typical Lifecycle |
| --- | --- | --- | --- |
| `SSLContext` | TLS context; manages `KeyManager`, `TrustManager` configuration and TLS state | `SSLContext.getInstance("TLS")` + `init(...)`; or `getDefault()` | Initialized when the application/module starts, reused if sharing the same policy |
| `SSLSocketFactory` | Factory for TLS client sockets | `context.getSocketFactory()` | Reusable to open multiple connections |
| `SSLSocket` client | TLS-protected TCP socket | `factory.createSocket(host, port)` | Single connection; handshake, I/O, close |
| `SSLServerSocketFactory` | Factory for TLS server listeners | `context.getServerSocketFactory()` | Can create one/multiple listeners |
| `SSLServerSocket` | TLS listening socket; TLS settings typically apply to subsequently accepted sockets | `serverFactory.createServerSocket(port, backlog, bindAddress)` | Bind/listen/accept until the server stops |
| `SSLSocket` server side | TLS socket for **a single accepted client** | `(SSLSocket) listener.accept()` | Single client; handshake, I/O, close |
| `SSLSession` | Information about the negotiated TLS session | `socket.getSession()` after handshake | Managed by TLS; can support session reuse/resumption |

`SSLSocket` **extends `java.net.Socket`**, and `SSLServerSocket` **extends `java.net.ServerSocket`**. JSSE implements TCP-based sockets for TLS; these two classes are not a UDP `DatagramSocket` and do not represent a nonblocking NIO `SocketChannel`.

**Common mistake:** calling `SSLContext.getInstance("TLS")` and thinking you already have a protected connection. The context must be initialized, then a factory/socket created, connected to the peer, and a TLS handshake completed with proper verification.

## 4. SSLContext: The Foundation of TLS Configuration

`javax.net.ssl.SSLContext` is created by protocol/provider name:

```java
SSLContext context = SSLContext.getInstance("TLS");
context.init(keyManagers, trustManagers, new SecureRandom());
```

This is a **code snippet**; `keyManagers` has type `KeyManager[]`, `trustManagers` has type `TrustManager[]`. In a concrete application, these arrays are created using `KeyManagerFactory` and `TrustManagerFactory`; a complete example is in section 12.

The three arguments of `init(...)`:

1. **`KeyManager[]`:** selects the private key and certificate chain **of the endpoint itself** to present when needed. A TLS server authenticating with a certificate normally **must have** the corresponding private key. An mTLS client also needs a key manager to send the client certificate.
2. **`TrustManager[]`:** determines whether to trust the **peer's** certificate. A TLS client normally needs a trust manager to verify the server certificate; an mTLS server needs a trust manager to verify the client.
3. **`SecureRandom`:** a secure random source for cryptographic operations. `null` can be passed to let the provider use the default; in the demo, `new SecureRandom()` is passed for clarity.

`SSLContext.getDefault()` retrieves the default context currently configured for the JVM. `SSLContext.getInstance("TLS")` creates a context from a provider and then requires `init(...)` before calling a factory. Do not confuse `getDefault()` (already initialized by default) with a newly `getInstance` context that has not been initialized yet.

### Why use `"TLS"` instead of `"SSL"`?

In JSSE, `"TLS"` is the standard context algorithm name for selecting the TLS family; the protocol versions actually permitted are also affected by the provider/JDK and `SSLSocket.setEnabledProtocols(...)` or `SSLParameters`. In standard Java 17, TLSv1.2 is required to be supported; TLSv1.3 is supported by common Oracle/OpenJDK JDKs, though you should verify the provider and security policy when using custom environments.

The following example sets `TLSv1.3` **on the socket/listener** to clearly illustrate a modern version; you should not re-enable SSLv3/TLSv1.0/TLSv1.1 to work with legacy systems. When a system requires compatibility, consider TLSv1.2 with a modern cipher policy and an upgrade plan.

### One context or multiple contexts?

You can reuse a single `SSLContext` for multiple connections that **share the same identity/trust source and policy**. However, when services require different truststores or client certificates, creating **separate contexts per endpoint/policy** helps avoid accidentally broadening trust: for example, client service A only trusts CA A, while service B only trusts CA B.

You should not modify the global `SSLContext.setDefault(...)` to adjust TLS for an individual connection, because it can affect other components in the same JVM. Prefer creating an explicit context and passing its factory to the component that uses it.

## 5. How Do KeyStore, TrustStore, and Certificate Differ?

A **keystore** and a **truststore** are both typically Java `KeyStore` files such as `PKCS12`; the main difference is **the purpose of the data and how it is used**:

| Concept | What does it contain? | Who uses it? | What is it used for? |
| --- | --- | --- | --- |
| Server keystore | Server private key + corresponding certificate chain | `KeyManagerFactory` on the server side | Proves the server possesses the private key for the public cert |
| Client truststore | Trusted CA/root or trusted certificate (in the demo, a specific self-signed cert) | `TrustManagerFactory` on the client side | Evaluates the trust chain of the server certificate |
| Client keystore (mTLS) | Client private key + client cert chain | `KeyManagerFactory` on the client side | Client proves its identity to the server |
| Server truststore (mTLS) | CAs/client certificates trusted by the server | `TrustManagerFactory` on the server side | Verifies the client cert when client auth is enabled |

The **private key** must never be placed into another party's client truststore. The demo's truststore contains only the **public certificate**, not the server private key. A certificate contains the public key/identity and signature information, which is distinct from the private key.

`KeyManagerFactory` reads the identity:

```java
KeyStore identityStore = KeyStore.getInstance("PKCS12");
try (InputStream in = Files.newInputStream(Path.of("server.p12"))) {
    identityStore.load(in, storePassword);
}
KeyManagerFactory kmf = KeyManagerFactory.getInstance(
        KeyManagerFactory.getDefaultAlgorithm());
kmf.init(identityStore, keyPassword);
KeyManager[] keyManagers = kmf.getKeyManagers();
```

`TrustManagerFactory` reads trust anchors:

```java
KeyStore trustedStore = KeyStore.getInstance("PKCS12");
try (InputStream in = Files.newInputStream(Path.of("client-trust.p12"))) {
    trustedStore.load(in, storePassword);
}
TrustManagerFactory tmf = TrustManagerFactory.getInstance(
        TrustManagerFactory.getDefaultAlgorithm());
tmf.init(trustedStore);
TrustManager[] trustManagers = tmf.getTrustManagers();
```

The two snippets above are **code fragments**; they require imports from `java.security`, `java.nio.file`, `java.io`, and `javax.net.ssl`, as well as `char[]` password variables. Do not hardcode production passwords as literals in source code. Use a secrets manager, file permissions, and a securely operated secret rotation mechanism.

A client using a root CA in its truststore **still must verify the hostname**. Trusting the CA's certificate chain proves the cert was signed by a trusted CA; it **does not prove** the cert belongs to the exact hostname the client intends to connect to. This part is especially important when using `SSLSocket` directly.

## 6. SSLSocketFactory: Creating TLS Client Sockets

Obtain a factory from an initialized context:

```java
SSLSocketFactory factory = clientContext.getSocketFactory();
try (SSLSocket socket = (SSLSocket)
        factory.createSocket("api.example.com", 443)) {
    // configure SSLParameters, timeout, then handshake and I/O
}
```

This is a code snippet. `createSocket(host, port)` creates a TCP socket bound to the peer, using JSSE to perform TLS. The TCP connection may be opened during socket creation, while the TLS handshake typically starts when `startHandshake()` or the first I/O operation is called; therefore, to fail fast and clearly separate TLS errors, configure parameters first and then **call `startHandshake()` explicitly**.

The factory also has an overload for an already connected `Socket`:

```java
SSLSocket tls = (SSLSocket) factory.createSocket(
        plainConnectedSocket, "api.example.com", 443, true);
```

This is a code snippet for the scenario of **layering TLS over an already connected TCP socket**. The hostname parameter must be the **intended destination to be verified**; do not substitute a fake address or untrusted host just to bypass the certificate name. `autoClose=true` ensures the underlying socket is closed when the TLS socket closes according to that overload's semantics. Endpoint identification and TLS parameters must be set **before the handshake**.

`SSLSocketFactory.getDefault()` can also create TLS sockets based on the **JVM's default context**. This is convenient when an application-wide truststore/policy is properly managed, but it does not allow a client to trust only a service-specific set of CAs without corresponding configuration.

### Do not confuse factory with connection

An `SSLSocketFactory` is not tied to a single connection. For 1,000 independent requests, you can use **the same factory/context** to create 1,000 different `SSLSocket`s, each with its own state, handshake, and lifecycle. Each `SSLSocket` must be closed according to that connection's lifecycle.

## 7. SSLSocket: TLS Connection and Key APIs

`SSLSocket` provides a stream socket API and TLS customization:

| Method | Role | When to Use |
| --- | --- | --- |
| `setSSLParameters(SSLParameters)` | Sets TLS parameters, endpoint identification, ALPN, SNI, or other policies | **Before handshake** |
| `setEnabledProtocols(String[])` | Restricts enabled TLS versions | Before handshake |
| `setEnabledCipherSuites(String[])` | Restricts cipher suites | Only when there is a clear policy; avoid weak/legacy suites |
| `setSoTimeout(int millis)` | Timeout on blocking read operations | Before read/handshake as needed |
| `startHandshake()` | Explicitly initiates the TLS handshake | After configuration, before application data |
| `getSession()` | Accesses the negotiated protocol/cipher/session | After a successful handshake |
| `getInputStream()` | Receives plaintext application bytes protected by TLS on the wire | After/concurrent with handshake per contract |
| `getOutputStream()` | Sends plaintext app bytes for JSSE to encrypt on the wire | After/concurrent with handshake |
| `close()` | Closes the socket and related resources | End of lifecycle |

**TLS is a cryptographically protected stream, not a message queue.** If you send a single `write("HELLO")`, the receiver may read the bytes across multiple `read` calls. You must use application-layer framing (newline, length-prefix, HTTP, etc.) just like TCP.

**`setSoTimeout` is not an overall TCP connection timeout**: it primarily governs blocking reads; you should also design a connect timeout, an overall handshake deadline, and a business-processing timeout. In a large server, do not let a peer tie up a thread indefinitely during handshake or read.

### Client/server mode

`SSLSocket` has a client or server mode, controlled by `setUseClientMode(...)` before the handshake. Sockets created from `SSLSocketFactory` are normally in client mode; sockets accepted from `SSLServerSocket` are normally in server mode. A TLS handshake requires the two sides to be in matching roles. Do not change the mode after the handshake has started.

`SSLSocket` also supports `setNeedClientAuth(...)`/`setWantClientAuth(...)` in **server mode** when requesting a client certificate. These options do not provision private keys/truststores by themselves; they must be prepared accordingly in `SSLContext`.

## 8. SSLServerSocket: Listener Waiting for TLS Connections

On the server side, obtain the factory from the **server SSLContext** configured with a private key:

```java
SSLServerSocketFactory serverFactory =
        serverContext.getServerSocketFactory();
try (SSLServerSocket listener = (SSLServerSocket)
        serverFactory.createServerSocket(8443)) {
    listener.setEnabledProtocols(new String[]{"TLSv1.3"});

    try (SSLSocket peer = (SSLSocket) listener.accept()) {
        peer.startHandshake();
        // read/write application data on peer, not on listener
    }
}
```

This is a code snippet, assuming `serverContext` exists. `listener` is the listener listening on port 8443; `peer` is the socket created **specifically for a single client**. Do not write request data to `SSLServerSocket`; that class has no application stream for a specific client.

`SSLServerSocket` is similar to `ServerSocket` regarding bind/backlog/accept:
- Can be created with port `0` so the OS assigns an ephemeral port in tests, then read via `getLocalPort()`.
- Can bind to the loopback address to prevent other machines from accessing it.
- `setSoTimeout(...)` on the **listener** limits waiting in `accept()`; `setSoTimeout(...)` on the accepted `SSLSocket` limits the peer's read—they are two different objects with different effects.
- A server needs an accept loop and concurrency/connection-limit management in real-world systems.

`SSLServerSocket` settings such as enabled protocols, cipher suites, and client auth are normally inherited when creating accepted TLS sockets. Set them **before accept** so new connections use the right policy. An already accepted connection may have its own parameters that need to be set before the handshake.

**A real server key is required:** creating an `SSLServerSocket` from a context without an appropriate private key may bind/accept, but **the TLS handshake will fail** because the server cannot present a certificate/credentials satisfying the cipher suite.

## 9. What Does the TLS Handshake Do and When Does It Start?

The TLS handshake establishes shared parameters and authentication before meaningful application data is exchanged. A simplified description for server-authenticated TLS 1.3:

```text
Client                                         Server
  │                                              │
  ├── ClientHello (versions, cipher suites, …) ──►│
  │◄─ ServerHello (selected params, key share, …) ─┤
  │◄─ Protected TLS 1.3 messages and             │
  │   server cert / proof of key possession    ──┤
  │                                              │
  │  Client verifies trust chain + target identity│
  │  if endpoint identification is set properly  │
  │                                              │
  ├── Finished and handshake completion ────────►│
  │                                              │
  ◄──────── TLS-protected application data ──────►
```

The diagram intentionally omits many messages and options. Details differ between TLSv1.2 and TLSv1.3 and between full/resumed handshakes. **Do not** infer from the diagram that the application has the right to skip certificate verification or swap algorithms on its own.

In JSSE, calling `socket.startHandshake()` makes the boundary explicit:
- If the handshake **succeeds**, the socket has negotiated the protocol/cipher suite and satisfied the configured trust/endpoint checks.
- If the handshake **fails**, you typically receive `SSLHandshakeException`, `SSLProtocolException`, `SSLException`, or a related I/O error. Do not proceed with the application protocol as if the connection were secure.
- If not called explicitly, the handshake may start automatically on the first read/write; in that case, errors surface in the data-processing path, which is easily confusing.

`getSession().getProtocol()` and `getSession().getCipherSuite()` are useful for observing what TLS actually negotiated, but **do not by themselves prove the hostname is correct** if the application omitted endpoint identification.

## 10. Verifying Server Identity: Trust Chain vs. Hostname

A TLS client must verify **two layers**:

1. **Certificate trust:** the certificate chain is trusted by the `TrustManager` according to trust anchors and security policy.
2. **Endpoint identity:** the certificate was issued for the **actual hostname/IP intended for connection**; typically checked via SAN (Subject Alternative Name). For TLS over HTTP/HTTPS connections, the `"HTTPS"` endpoint identification algorithm applies HTTP server identity verification rules.

With `SSLSocket` directly, **do not assume** hostname verification is always enabled just because TLS is used. Configure it explicitly before the handshake:

```java
SSLParameters params = socket.getSSLParameters();
params.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(params);
socket.startHandshake();
```

The snippet above assumes `socket` is a created client `SSLSocket`. According to Java Security Standard Algorithm Names, `"HTTPS"` is the standard endpoint identification algorithm name. In the complete example, the client connects to **`127.0.0.1`** and the server certificate contains a **SAN of type IP:127.0.0.1**, so the check can succeed.

Common pitfalls:
- A server certificate signed by a trusted CA **but belonging to a different domain**. The trust chain may still be valid, yet endpoint identity must reject it.
- A certificate for DNS `localhost` **does not automatically** substitute for IP SAN `127.0.0.1` when the client actually uses the IP address. A SAN matching the identity type being connected to is required.
- Using `SSLSocketFactory.createSocket(ip, port)` for an IP while trying to pass a different hostname to bypass certificate checks is insecure; if you need to connect to a fixed routed IP while still verifying a hostname, design a transport/layered socket and TLS peer host/SNI for the exact authorized identity.
- Writing a custom `X509TrustManager` that accepts all certificates or disabling hostname verification to "fix" handshake errors **destroys protection against server spoofing**.

If a program uses a high-level HTTP API such as `java.net.http.HttpClient` or `HttpsURLConnection`, those classes have built-in endpoint verification for HTTPS. Do not replace them with configurations that bypass hostname verification. When a custom TLS truststore is needed for an HTTP client, you can configure `HttpClient.newBuilder().sslContext(context)` instead of re-implementing all of HTTP over raw sockets.

## 11. Preparing the Certificate and Truststore for the Localhost Lab

We will generate a **self-signed server keypair, strictly for local learning**, export the **public certificate**, and import it into a client-side truststore. We will not use a "trust-all" trust manager, connect to the Internet, or require a certificate from a public CA.

Prerequisites:
- **JDK 17 or later** installed, with `javac`, `java`, and `keytool` available in PATH.
- A writable demo directory.
- Loopback `127.0.0.1` allows local TCP binding.
- JSSE provider supports `TLSv1.3` (standard JDK 17 environment).

Create a separate empty directory and run each **single-line command** (all are `keytool` CLI commands):

```bash
keytool -genkeypair -alias local-server -keyalg RSA -keysize 2048 -validity 7 -dname "CN=localhost" -ext "SAN=IP:127.0.0.1,DNS:localhost" -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -noprompt

keytool -exportcert -alias local-server -keystore server.p12 -storepass changeit -rfc -file server-cert.pem

keytool -importcert -noprompt -alias local-server -file server-cert.pem -keystore client-trust.p12 -storetype PKCS12 -storepass changeit
```

Afterward, the directory contains:

```text
server.p12          server private key + server certificate
server-cert.pem     exported public certificate only
client-trust.p12    trusted public certificate; NO server private key
```

Explanation:
- `-alias local-server` identifies the entry.
- `-keyalg RSA -keysize 2048` generates an RSA keypair for the example; production must follow cryptographic standards and organizational policy.
- `-validity 7` grants a 7-day validity for the demo cert, avoiding confusion with a long-lived operational certificate.
- `-ext SAN=IP:127.0.0.1,DNS:localhost` declares **two identities**; the demo client connects by IP, so it uses the IP SAN.
- `-storetype PKCS12` uses the standard format for storing key/certificate entries.
- `-storepass changeit -keypass changeit` is a **public demo password with no security**; never use it in production or put it in real source code.
- `-exportcert` exports only the certificate, not the private key.
- `-importcert` makes the client trust **this demo certificate** via the configured truststore; it does not make every server trusted.

You can inspect the SAN:

```bash
keytool -list -v -keystore server.p12 -storepass changeit -alias local-server
```

Look for the `SubjectAlternativeName` section containing `IPAddress: 127.0.0.1` and `DNSName: localhost`. If `keytool` asks for confirmation because the file already exists or the alias conflicts, use a clean demo directory; **do not delete or overwrite production keystores** to run the lab.

### Why not use the default truststore?

The newly generated self-signed certificate **is not in the system/JVM's trusted CA list**. If the client uses the default `TrustManager`, the handshake will fail as designed. We import the public cert into a **dedicated truststore for the demo** and pass it to `clientContext`. In production, use CAs/certificates managed by your organization with rotation and revocation per policy; trusting a self-signed leaf certificate is strictly a learning approach on loopback.

## 12. Runnable Java 17+ Program: SSLContext → factories → sockets

Save the exact filename **`LocalTlsEchoDemo.java`** in the **same directory** as `server.p12` and `client-trust.p12` created in section 11.

```java
import java.io.BufferedReader;
import java.io.BufferedWriter;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.net.InetAddress;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.concurrent.atomic.AtomicReference;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLServerSocketFactory;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSocketFactory;
import javax.net.ssl.TrustManagerFactory;

public class LocalTlsEchoDemo {
    private static final char[] PASSWORD = "changeit".toCharArray();

    private static KeyStore loadStore(String filename) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(Path.of(filename))) {
            store.load(in, PASSWORD);
        }
        return store;
    }

    private static SSLContext serverContext() throws Exception {
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(loadStore("server.p12"), PASSWORD);
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(kmf.getKeyManagers(), null, new SecureRandom());
        return context;
    }

    private static SSLContext clientContext() throws Exception {
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(loadStore("client-trust.p12"));
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(null, tmf.getTrustManagers(), new SecureRandom());
        return context;
    }

    public static void main(String[] args) throws Exception {
        SSLServerSocketFactory serverFactory =
                serverContext().getServerSocketFactory();
        InetAddress address = InetAddress.getByName("127.0.0.1");
        try (SSLServerSocket listener = (SSLServerSocket)
                serverFactory.createServerSocket(0, 10, address)) {
            listener.setEnabledProtocols(new String[]{"TLSv1.3"});
            listener.setSoTimeout(5000);

            AtomicReference<Throwable> serverFailure = new AtomicReference<>();
            Thread server = new Thread(() -> {
                try (SSLSocket socket = (SSLSocket) listener.accept()) {
                    socket.setSoTimeout(5000);
                    socket.startHandshake();
                    BufferedReader reader = new BufferedReader(
                            new InputStreamReader(socket.getInputStream(),
                                    StandardCharsets.UTF_8));
                    BufferedWriter writer = new BufferedWriter(
                            new OutputStreamWriter(socket.getOutputStream(),
                                    StandardCharsets.UTF_8));
                    String request = reader.readLine();
                    writer.write("ACK:" + request);
                    writer.newLine();
                    writer.flush();
                } catch (Throwable ex) {
                    serverFailure.set(ex);
                }
            });
            server.start();

            SSLSocketFactory clientFactory = clientContext().getSocketFactory();
            try (SSLSocket socket = (SSLSocket)
                    clientFactory.createSocket("127.0.0.1",
                            listener.getLocalPort())) {
                socket.setSoTimeout(5000);
                SSLParameters params = socket.getSSLParameters();
                params.setProtocols(new String[]{"TLSv1.3"});
                params.setEndpointIdentificationAlgorithm("HTTPS");
                socket.setSSLParameters(params);
                socket.startHandshake();

                BufferedWriter writer = new BufferedWriter(
                        new OutputStreamWriter(socket.getOutputStream(),
                                StandardCharsets.UTF_8));
                BufferedReader reader = new BufferedReader(
                        new InputStreamReader(socket.getInputStream(),
                                StandardCharsets.UTF_8));
                writer.write("ping");
                writer.newLine();
                writer.flush();
                String reply = reader.readLine();
                System.out.println("TLS=" + socket.getSession().getProtocol());
                System.out.println("reply=" + reply);
            }

            server.join(6000);
            if (server.isAlive()) {
                throw new IllegalStateException("Server did not finish");
            }
            if (serverFailure.get() != null) {
                throw new IllegalStateException("Server failed",
                        serverFailure.get());
            }
        }
    }
}
```

This is a **complete standalone Java file**. Run it in the directory containing the two `.p12` files:

```bash
javac LocalTlsEchoDemo.java
java LocalTlsEchoDemo
```

In a Java 17 environment supporting TLSv1.3, with valid keytool files and a successful loopback connection, stdout is:

```text
TLS=TLSv1.3
reply=ACK:ping
```

Verified the program with `javac --release 17` and ran it on a JDK supporting TLSv1.3; the output matches the above.

### Reading the code from server to client

**Server:**
1. `loadStore("server.p12")` loads the server private key + certificate.
2. `KeyManagerFactory.init(...)` creates `KeyManager[]` to select the identity during the TLS handshake.
3. `serverContext()` creates a TLS context with the `KeyManager`s; the server does not require a client certificate yet, so the context does not need a custom truststore for mTLS.
4. `getServerSocketFactory()` creates a server factory from the context.
5. `createServerSocket(0, 10, address)` binds the listener to loopback with an OS-assigned port; backlog is set to 10 for the demo.
6. `listener.setEnabledProtocols({"TLSv1.3"})` restricts the handshake of accepted sockets for the example.
7. `accept()` returns a server-side `SSLSocket`; `startHandshake()` has the server participate in the handshake.
8. The server reads **one line** `ping` and sends `ACK:ping`; the newline is **application-layer framing**, not automatically created by TLS.

**Client:**
1. `loadStore("client-trust.p12")` loads the server's **trusted public certificate**.
2. `TrustManagerFactory.init(...)` creates trust managers to verify the peer certificate.
3. `clientContext()` initializes a TLS context with the selected trust manager; the client has no certificate of its own in the demo.
4. `getSocketFactory()` creates a client factory.
5. `createSocket("127.0.0.1", listener.getLocalPort())` establishes a TCP connection to the listener.
6. `params.setProtocols({"TLSv1.3"})` and `setEndpointIdentificationAlgorithm("HTTPS")` set the policy **before the handshake**.
7. `startHandshake()` verifies trust + the matching IP SAN before sending application data.
8. `getSession().getProtocol()` reports the TLS version actually negotiated; the reply is read through the TLS-processed `InputStream`.

### Why does the demo have two separate contexts?

The server **possesses a private key** and needs `KeyManagerFactory`. The client **trusts the server's public certificate** and needs `TrustManagerFactory`. Each side has a distinct security role; you should not "put the entire keystore on both sides" just to get the handshake to pass.

### Why use two Java threads?

`SSLServerSocket.accept()` is a blocking operation waiting for a client. If you ran accept and then called client connect in the **same** main thread, the program would wait forever. The demo uses one server thread for a single connection, while the main thread acts as the client. This is a **test-organization pattern**, not an optimal architecture for a multi-client production server.

`serverFailure` captures server-side errors, and `server.join(6000)` ensures main observes the server outcome before exiting. The 5–6 second timeouts are demo thresholds and may need adjustment in heavily loaded environments.

## 13. Distinguishing TCP Socket, TLS Socket, and Application Data

With `SSLSocket`, application code still uses `InputStream` and `OutputStream` like `Socket`, but JSSE sits between the application and TCP:

```text
Client application                Server application
      │                                  ▲
      ▼ write("ping\n")                  │ readLine() => "ping"
   SSLSocket                              SSLSocket
      │ encrypt + tag                       ▲ decrypt + verify
      ▼                                     │
   TLS records  ─────── TCP stream ────────┘
```

A single `writer.write("ping")` does not necessarily correspond to one TCP segment or TLS record. A single `reader.readLine()` reads until a newline according to application framing; it may require multiple byte reads from the TLS socket. TLS guarantees data confidentiality and integrity within a policy-verified channel, but **does not** distinguish "message 1" from "message 2" if the application does not declare boundaries itself.

In the example, newlines are used for framing; if business payloads can contain arbitrary newlines, the protocol must escape them or switch to length-prefixing. Do not decode UTF-8 across arbitrary byte chunks if there is a risk of splitting mid-code-point; use the proper decoder/reader or read complete frames.

A note on `TLSv1.3`: data transmitted on the wire is not plaintext `ping`; TLS records contain ciphertext. If you use Wireshark on loopback without valid key logging, you will not be able to read the payload from the capture simply because you know the port.

## 14. SSLSession: Inspecting the Negotiated Session

After a successful handshake:

```java
SSLSession session = socket.getSession();
String protocol = session.getProtocol();
String cipherSuite = session.getCipherSuite();
Principal peer = session.getPeerPrincipal();
```

This is a code snippet; imports are `javax.net.ssl.SSLSession` and `java.security.Principal`, and `socket` is an `SSLSocket`. `getPeerPrincipal()` requires that the peer was properly authenticated; if there is no authenticated peer, it may throw `SSLPeerUnverifiedException`. Do not assume the server always authenticates the client in one-way TLS.

`getSession().getProtocol()` in the example returns `"TLSv1.3"`. The specific cipher suite depends on the provider, algorithm list, and machine policy, so **do not hardcode a fixed cipher suite stdout** without a fixed environment.

TLS can support session resumption to reduce handshake overhead. `SSLContext`/session context may maintain a cache per provider. Do not assume every new `SSLSocket` will perform a full handshake; conversely, do not rely on resumption to skip necessary endpoint/authorization checks.

### Why shouldn't you look only at `getCipherSuite()` and assume it is secure?

A strong cipher suite **does not prove** you connected to the right machine if trust/hostname is misconfigured. Security layers must work together: protocol version, allowed cipher suites, certificate chain, endpoint identity, accurate routing/hostname, and application data handling per policy.

## 15. mTLS: When the Server Also Authenticates the Client's Certificate

Server-authenticated TLS (the demo) normally only requires the client to verify the server's identity. **Mutual TLS (mTLS)** requires the server to also authenticate the client certificate. **All four pieces of data** are needed:

```text
Server:
  KeyManager   -> server private key + server cert chain
  TrustManager -> trusts client CA/certificate

Client:
  KeyManager   -> client private key + client cert chain
  TrustManager -> trusts server CA/certificate
```

The server enables the client cert requirement **before handshake/accept**:

```java
SSLServerSocket listener = ...; // created from server SSLContext
listener.setNeedClientAuth(true);
```

This is a code snippet. `setNeedClientAuth(true)` requires the client to present matching credentials; if the client lacks a certificate trusted by the server, the handshake fails. `setWantClientAuth(true)` only **requests but does not require** client authentication in many situations. Choose `need` or `want` according to a clear policy; do not use `want` and assume every client has been authenticated.

For mTLS to truly work:
- Server `SSLContext.init(serverKeyManagers, serverTrustManagers, ...)`.
- Client `SSLContext.init(clientKeyManagers, clientTrustManagers, ...)`.
- The server must verify/authorize the **client identity** corresponding to the certificate, rather than accepting "any certificate signed by a trusted CA".
- The client must still verify the server hostname, chain, and TLS policy.

**Do not enable `setNeedClientAuth(true)` in `LocalTlsEchoDemo` and expect it to still run:** the demo's client has no client keypair/cert, and the server has no truststore configured for client verification. Expanding the demo into mTLS requires actively creating a client keystore, a server truststore, and two-way contexts.

mTLS solves one layer of peer authentication; **it does not automatically authorize APIs**. After the handshake, the service still needs policies based on identity, roles, resources, and requests.

## 16. SSLParameters: Protocol, Cipher Suite, SNI, ALPN, and Hostname

`SSLParameters` is a set of parameters that can be applied to a socket before the handshake:

```java
SSLParameters params = socket.getSSLParameters();
params.setProtocols(new String[]{"TLSv1.3"});
params.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(params);
```

The snippet above ensures both policies are set before the handshake. You can also use `socket.setEnabledProtocols(...)`, but when using both approaches, avoid overlapping configurations that are hard to maintain.

### TLS versions and cipher suites

- `getSupportedProtocols()` shows which versions the provider supports; `getEnabledProtocols()` shows the versions currently enabled on the socket.
- `getSupportedCipherSuites()` and `getEnabledCipherSuites()` work similarly for cipher suites. **Supported does not mean enabled** or permitted by security policy.
- Insecure algorithms/versions may be blocked by `jdk.tls.disabledAlgorithms` in the JDK configuration. Do not remove/edit this policy just to handshake with an obsolete peer.
- Normally let the JDK/provider choose secure cipher suites per policy; only override when there is a specific compliance requirement and compatibility has been tested.

### SNI (Server Name Indication)

When connecting via a DNS hostname, a TLS client can send **SNI** so a server hosting multiple virtual hosts selects the right certificate. In the demo connecting to a loopback **IP literal**, SNI is not needed. In production, pass the real hostname to be verified rather than just an IP and then complaining the server picked the wrong cert.

`SSLParameters.setServerNames(...)` is used to explicitly configure server names when there is a valid reason; do not treat SNI as a security check replacing trust/hostname verification. SNI informs the server of the desired name, whereas certificate validation proves the peer is trusted and the identity matches.

### ALPN (Application-Layer Protocol Negotiation)

ALPN allows both sides to negotiate an application protocol (e.g., `h2` or `http/1.1`) during the TLS handshake:

```java
SSLParameters params = socket.getSSLParameters();
params.setApplicationProtocols(new String[]{"h2", "http/1.1"});
socket.setSSLParameters(params);
// After handshake: socket.getApplicationProtocol()
```

This is a code snippet; ALPN only produces a meaningful result when **both sides** support/agree on it and a matching application protocol is implemented. Merely declaring `"h2"` **does not** turn an arbitrary stream into HTTP/2; the application must implement HTTP/2 framing or use a dedicated HTTP client/server.

## 17. Default SSLContext and System Properties

In some programs, JSSE reads configuration from default system properties/keystore/truststore:

```text
javax.net.ssl.keyStore
javax.net.ssl.keyStorePassword
javax.net.ssl.keyStoreType

javax.net.ssl.trustStore
javax.net.ssl.trustStorePassword
javax.net.ssl.trustStoreType
```

Configuring via JVM properties is convenient for processes where a TLS policy applies application-wide, but it also carries risks if multiple libraries in the same JVM need **different trust policies**. Setting a global truststore incorrectly can break many outbound connections or overly broaden trust.

`SSLSocketFactory.getDefault()` and `SSLServerSocketFactory.getDefault()` rely on the default SSL context/provider configuration. If the server does not have a keystore containing an appropriate private key/certificate, the default factory **does not automatically generate a secure server certificate**. In the local example, we create a **dedicated `serverContext`** from `server.p12` to avoid depending on JVM-wide configuration.

You should also avoid calling:

```java
SSLContext.setDefault(customContext);
```

just to configure a single connection. This mutates JVM-wide default state and can affect other components. Instead, use `customContext.getSocketFactory()` or pass the context into a client framework that supports injection.

**Production:** provide passwords via a secret manager and secure runtime mechanisms. Passwords on the command line or in source code can be read from shell history or process lists/logs. Commands containing `changeit` here are strictly for use in a local demo directory with temporary data.

## 18. Timeouts, Closing, and Resource Management

A TLS connection has multiple distinct phases:

```text
TCP connect
   ▼
TLS handshake
   ▼
Application request/response
   ▼
TLS close / TCP close
```

Do not use a single timeout and assume it covers everything:
- **TCP connect timeout:** time to connect the socket to the address/port.
- **Handshake timeout:** time the TLS handshake waits for the peer, certificate validation, or required data. With blocking sockets, `setSoTimeout` bounds certain read operations, but an overall deadline should be managed by the architecture.
- **Application read timeout:** prevents a peer from sending 1 byte and holding the connection open forever.
- **Write/overall deadline:** prevents sending or processing from dragging on beyond policy.

The demo configures `listener.setSoTimeout(5000)` for `accept`, `socket.setSoTimeout(5000)` for reads on both peers, and `server.join(6000)` so the test does not hang for long. **These numbers are illustrative**, not suitable defaults for every environment.

### Closing the right resources

`try-with-resources` on `SSLServerSocket` closes the listener when the server stops; each `SSLSocket` is closed when its connection finishes. Closing the listener **does not** substitute for closing every accepted socket. In a multi-client server, you must manage the connection list and separate shutdown/timeout handling.

TLS has a secure closure notification mechanism called `close_notify`; an abrupt socket termination or a peer failing to send `close_notify` can cause a truncation condition. The application must still rely on **framing/application length** to know whether a message is complete, rather than treating any socket close as a complete message.

Do not log sensitive plaintext, private keys, passwords, or full TLS debug output in production. If temporarily enabling debug flags like `-Djavax.net.debug=ssl:handshake`, use them only in a controlled environment and protect the logs.

## 19. SSLSocket vs. SSLEngine When Nonblocking NIO Is Needed

`SSLSocket` is a TLS socket API following the `Socket`/`InputStream`/`OutputStream` model, convenient for blocking programs or a thread-per-connection model. It is **not a `SelectableChannel`** that can be registered directly with a `Selector` using `OP_READ/OP_WRITE`.

If an application needs thousands of TLS connections in a nonblocking `Selector`/`SocketChannel` loop, use **`SSLEngine`** (from `SSLContext.createSSLEngine(...)`) and integrate it yourself:

```text
SocketChannel TCP bytes
    │
    ▼
ByteBuffer network input
    │     SSLEngine.unwrap(...)
    ▼
ByteBuffer plaintext input  -> application parser

Application plaintext output
    │     SSLEngine.wrap(...)
    ▼
ByteBuffer encrypted output -> SocketChannel.write(...)
```

Beyond TLS record encryption/decryption, `SSLEngine` also reports handshake status, delegated tasks, buffer underflow/overflow, and the close workflow. This is a significantly more complex layer; you cannot simply swap `SocketChannel` for `SSLSocket` in selector code.

Because this lesson focuses on **`SSLContext`, `SSLSocketFactory`, `SSLSocket`, and `SSLServerSocket`**, the main example uses blocking sockets. When true nonblocking TLS is needed, choose a framework that properly implements `SSLEngine` or design a dedicated state machine and buffer ownership model.

## 20. Common Errors and Troubleshooting

| Symptom or Misconception | Possible Cause | Resolution |
| --- | --- | --- |
| `SSLHandshakeException: PKIX path building failed` | Client does not trust the server certificate chain | Configure truststore with the right CA/cert; check chain and expiry, do not use trust-all |
| `No name matching ... found` or `No subject alternative names ...` | Certificate does not match the connected host/IP | Fix SAN/certificate or use the issued hostname; keep hostname verification enabled |
| `handshake_failure` / `no cipher suites in common` | No compatible suite/protocol/cert/key | Check enabled protocols, provider, certificate key type, disabled algorithms |
| `No available authentication scheme` | Server lacks a private key/certificate suitable for the TLS mode/cipher | Create/init `KeyManagerFactory` with the proper keystore |
| `UnrecoverableKeyException` | Incorrect private key password or unreadable entry | Check store/key password, alias, file permissions |
| `SocketTimeoutException` | Accept/read/handshake did not complete within timeout | Check server listening state, network, provider, timeout, and peer state |
| `Connection refused` | No TCP listener at the address/port | Check bind address, firewall, port, and service |
| Client trusts cert yet still connects to wrong machine | Missing endpoint identity verification | Set `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` before handshake |
| `getSession().getProtocol()` is an old TLS version | Legacy version enabled or unexpected policy | Check enabled protocols, JDK policy, server config; do not force weak protocols |
| Server requires client cert, client handshake fails | Client lacks identity/key or server does not trust client CA | Configure two-way key/trust properly for mTLS |
| Data is merged/split at the application level | Confusing TLS socket with a message-oriented API | Add application framing, handle partial reads |
| Sudden CPU/thread spike | Thread-per-connection + slow clients/hanging handshakes | Connection limits, deadlines, backpressure; consider `SSLEngine`/framework |

Do not catch a TLS error and automatically "retry with plain TCP"; that is an **insecure downgrade**. If the protocol requires TLS, a handshake failure must reject the connection or report a clear error.

### Distinguishing three certificate failure causes

1. **Untrusted:** the certificate chain does not lead to a trust anchor trusted by the client.
2. **Expired/not yet valid:** the certificate's validity period is out of range.
3. **Wrong hostname/IP:** the chain may be valid, but the SAN does not match the expected endpoint.

The fix must match the error type. Do not disable both trust and endpoint identification just to make the client "work quickly".

## 21. Production TLS Configuration Checklist

**Client:**
- Specify hostname/IP and port per policy; prefer hostname when the service uses DNS/SNI certificates.
- Use an `SSLContext` with a managed truststore/CA or appropriate default trust; avoid trust-all.
- Enable endpoint identification for raw `SSLSocket`; for HTTP, prefer high-level HTTP clients with built-in HTTPS validation.
- Use permitted TLS versions/cipher suites; do not enable disabled protocols.
- Set connect, handshake/read, and overall deadlines; bound payload sizes and connection counts.
- Close sockets when done; do not log passwords, cert private keys, or sensitive data.
- If a client cert (mTLS) is required, configure a dedicated key manager and full cert chain.

**Server:**
- Have a private key + certificate chain matching the hostname from a protected keystore.
- Set enabled TLS protocols/cipher policy before accept; do not use SSLv3.
- Use an appropriate listener bind, limit backlog/concurrency, and set timeouts.
- Each `accept()` creates a separate `SSLSocket`; do not share a single socket/stream across multiple clients.
- If mTLS is required, have a server truststore for client identities and set `setNeedClientAuth(true)`.
- Authenticate/authorize application payloads after TLS based on the verified identity; TLS does not authorize endpoints by itself.
- Clean up accepted sockets, listener, threads, and queues/timeouts on close or shutdown.

**Operations:**
- Rotate certificates/private keys and CA truststores safely; monitor expiration dates.
- Check for differences across JDK/provider environments and `jdk.tls.disabledAlgorithms`.
- Test hostname mismatch, untrusted cert, expired cert, protocol mismatch, and mTLS missing-client-cert in a controlled environment.
- Do not equate "socket connect succeeded" with "TLS handshake succeeded".
- Observe protocol/cipher after handshake, but do not infer overall security success from a single log field.

## 22. Practice Exercises

**Exercise 1 — Distinguishing objects.** Why does the server need `SSLServerSocketFactory` and `SSLServerSocket`, while client data is read from the `SSLSocket` returned by `accept()`?  
**Answer hint:** the listener only binds/listens/accepts; each accepted socket is a separate TLS connection with its own handshake, session, and streams.

**Exercise 2 — Private key and public cert.** Can you copy `server.p12` (containing the server private key) to the client side and use it as a truststore?  
**Answer:** No, and it is dangerous: the client only needs the public certificate/CA trust anchors. Distributing the private key compromises the confidentiality of the server's identity.

**Exercise 3 — Why does the demo client need `client-trust.p12`?**  
**Answer:** The newly created self-signed server certificate is not in the default trust anchors. Importing the demo **public certificate** lets the client trust the chain, while endpoint identification verifies the IP SAN.

**Exercise 4 — Change the client to `createSocket("127.0.0.1", port)` when the cert only has SAN `DNS:localhost` and no `IP:127.0.0.1`. With HTTPS endpoint identification enabled, what happens?**  
**Answer:** Hostname/IP verification must fail because the connected identity is an IP literal that does not match the DNS SAN. Provision the proper IP SAN or connect using the matching hostname; do not disable verification.

**Exercise 5 — Has `SSLContext.getInstance("TLS")` opened the network yet?**  
**Answer:** No. It creates a TLS context. You still need `init(...)`, factory/socket creation, TCP connection, and handshake.

**Exercise 6 — What is `startHandshake()` used for?**  
**Answer:** Explicitly starting the TLS handshake to negotiate the protocol/cipher and perform authentication according to key/trust/endpoint policy before application data.

**Exercise 7 — Is enabling `listener.setNeedClientAuth(true)` without configuring client key/trust valid?**  
**Answer:** Not sufficient. The client must have a certificate + private key accepted by the server, and the server must have trust managers that trust the client's certificate/CA.

**Exercise 8 — Can `SSLSocket` be registered directly with a `Selector`?**  
**Answer:** Not like `SocketChannel`, because it is not a `SelectableChannel`. For nonblocking TLS over NIO, you need `SSLEngine` or a framework that manages wrap/unwrap/handshake.

**Exercise 9 — If `reader.readLine()` returns a full line, did the message boundary come from TLS?**  
**Answer:** No. The boundary came from the application protocol's **newline framing** and `BufferedReader`; TLS only protects the transported byte stream.

**Exercise 10 — Why should you not automatically retry plaintext HTTP after an `SSLHandshakeException`?**  
**Answer:** Falling back to plaintext loses authentication and confidentiality when TLS fails and can open the door to downgrade attacks; handle the TLS error according to its root cause.
