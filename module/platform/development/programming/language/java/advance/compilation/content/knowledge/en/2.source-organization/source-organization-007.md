# Separating Main, Test, and Generated Sources in a Java Project

## 1. Why Separate Types of Source Code?

A Java project can contain three types of code that superficially all appear to be `.java` files, but have different roles and lifecycles:

- **Main (main/production) sources**: maintained by developers, forming the distributed application or library.
- **Test sources**: used to verify the behavior of main code; needed only during testing and development, and usually do not go into the production JAR.
- **Generated sources**: created by an annotation processor, API client generator, schema code generator, or a build tool from defined inputs. Do not manually edit the generated output because the next generation run may overwrite it.

Proper separation is not simply a matter of placing files into three directories. The build tool must know the **input sources, generation/compilation order, classpath, and output directory** of each type. As a result, builds can be reproduced, only the necessary parts are run when code changes, test libraries are prevented from leaking into the application, and stale generated code is prevented from hiding errors.

A general model:

```text
Input sources / generator configuration
             │
             ▼
       Run generator
             │
             ▼
   generated sources (.java) ─────┐
                                  │
src/main/java ────────────────────┼──► compile main ──► classes/main ──► JAR
                                  │
src/main/resources ───────────────┘                   (resources are copied)
                                         │
src/test/java ───────────────────────────┼──► compile test ──► classes/test ──► run tests
src/test/resources ──────────────────────┘
```

In this diagram, test code **depends on the compilation output of main**. The reverse direction must not exist: a class in `src/main/java` should not import a class that exists only in `src/test/java`.

## 2. Directory Layout Conventions

For a Java project following Gradle/Maven conventions:

```text
project/
├── src/
│   ├── main/
│   │   ├── java/example/             # human-written Java, used in production
│   │   └── resources/                # configuration, templates, production resources
│   └── test/
│       ├── java/example/             # test code, simple test fixtures
│       └── resources/                # test data
├── tools/                             # code generator tool source, if the project has one
├── build/                             # output generated by Gradle, not original source code
│   ├── generated/sources/.../         # tool-generated Java
│   ├── classes/java/main/
│   ├── classes/java/test/
│   ├── resources/main/
│   └── resources/test/
└── build.gradle
```

This is an example **Gradle** layout. In Maven, the corresponding output directory is usually under `target/`, for example `target/classes`, `target/test-classes`, `target/generated-sources`. Do not hardcode output paths by guesswork when the project or a plugin has configured them differently.

| Source | Who owns it? | Where is it usually located? | Included in product? |
| --- | --- | --- | --- |
| Production Java | Developers | `src/main/java` | Yes, as `.class` |
| Production resources | Developers | `src/main/resources` | Usually yes |
| Test Java | Developers | `src/test/java` | Usually no |
| Test resources | Developers | `src/test/resources` | No |
| Generated Java for main | Generator/build | `build/generated/sources/.../java` | Compiled classes may be included |
| Generated Java for test | Generator/build | Separate generated area for tests | Only for testing |
| Compiled output | Compiler | `build/classes/...` | Main classes used for packaging |

**Source root differs from package.** The file `src/main/java/example/App.java` can declare `package example;`. When placing a generated source at `build/generated/sources/buildInfo/java/example/BuildInfo.java`, both classes are in the same package `example` but in **two different source roots**. The package name determines the Java namespace; the source root tells the build tool where to find source files. The directory `build/classes/java/main/example` is **binary output**, and must not be used as a source root.

## 3. Dependency and Classpath Boundaries

Basic rules:

1. **Main compile classpath** includes libraries needed to compile production code. It must not depend on test-only libraries.
2. **Test compile classpath** needs the compiled main classes, the required main libraries, and test libraries such as JUnit/Mockito when used.
3. **Test runtime classpath** needs test classes, main classes, resources, and dependencies at test execution time.
4. **Generator** needs to run before any compilation task that uses its output. Libraries that run the generator can belong to a separate configuration; do not automatically turn them into runtime dependencies of the product.
5. **Generated sources** must be declared for the right source set (`main` or `test`), whereas `generated .class` is compiler output, not source files for the next compilation.

A typical mistake is adding `src/test/java` to the `main` source set to "make compilation easier". When doing so, test helpers and testing dependencies can leak into the production build path, while also creating circular dependencies. The right approach is to fix the **test** classpath or extract truly shared logic into main or an appropriate shared module.

## 4. Runnable Example with JDK 17+: Main, Test, and Generator

The following example requires no external libraries. Main code calls a `BuildInfo` class generated before compilation; a smoke test program checks `App.greet`. Create the exact three *human-written* files below.

### 4.1. Code Generator Tool: `tools/BuildInfoGenerator.java`

```java
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

public class BuildInfoGenerator {
    public static void main(String[] args) throws Exception {
        Path output = Path.of(
            "build/generated/sources/buildInfo/java/example/BuildInfo.java"
        );
        Files.createDirectories(output.getParent());

        String source = """
            package example;

            public final class BuildInfo {
                public static final String VERSION = "1.0-demo";

                private BuildInfo() {}
            }
            """;

        Files.writeString(output, source, StandardCharsets.UTF_8);
    }
}
```

`Path.of` and `Files.writeString` have existed since Java 11; text blocks are available in Java 17. The generator writes a file with a deterministic path and deterministic content, and creates parent directories automatically. In this article, the generator is placed under `tools/` so the boundary with application code is clear. In a real project, the generator can be a plugin, an annotation processor, or a build task.

### 4.2. Main Code: `src/main/java/example/App.java`

```java
package example;

public class App {
    public static String greet(String name) {
        return "Xin chào, " + name + "!";
    }

    public static void main(String[] args) {
        System.out.println(greet("Java"));
        System.out.println(BuildInfo.VERSION);
    }
}
```

`App` references `BuildInfo` even though that file is not stored in `src/main/java`. It will be seen by the compiler when we pass **both the main source root and the generated file** as compilation inputs.

### 4.3. Test Code: `src/test/java/example/AppSmokeTest.java`

```java
package example;

public class AppSmokeTest {
    public static void main(String[] args) {
        String actual = App.greet("Java");
        if (!"Xin chào, Java!".equals(actual)) {
            throw new AssertionError("Unexpected greeting: " + actual);
        }
        System.out.println("TEST OK");
    }
}
```

This is a **self-running smoke test using `main`**, not a JUnit test, and it will not be automatically discovered by Gradle `test`. It uses an explicit `AssertionError`, so the `-ea` option is not needed. In a normal testing setup, place JUnit `@Test` methods in `src/test/java` and let the test runner execute them.

### 4.4. Phase-by-Phase Compilation

From the `project/` directory, run in a Bash-style shell on Linux/macOS or Git Bash:

```bash
mkdir -p build/tools build/classes/java/main build/classes/java/test

# (1) Compile and run the code generator tool.
javac -d build/tools tools/BuildInfoGenerator.java
java -cp build/tools BuildInfoGenerator

# (2) Compile main together with the generated Java file.
javac -d build/classes/java/main \
  src/main/java/example/App.java \
  build/generated/sources/buildInfo/java/example/BuildInfo.java

# (3) Compile test: main classes are on the test compile classpath.
javac -cp build/classes/java/main \
  -d build/classes/java/test src/test/java/example/AppSmokeTest.java

# (4) Run the application; test classes are not on this classpath.
java -cp build/classes/java/main example.App

# (5) Run the smoke test with both main classes and test classes.
java -cp build/classes/java/main:build/classes/java/test example.AppSmokeTest
```

Exact output of the last two `java` commands:

```text
Xin chào, Java!
1.0-demo
TEST OK
```

On PowerShell/Windows, you can use `New-Item -ItemType Directory -Force` to create directories or let `javac` create the destination directory automatically when parent directories already exist. Most importantly, **the classpath separator on Windows is `;`**, instead of `:` on Unix. Example smoke test command:

```powershell
java -cp 'build/classes/java/main;build/classes/java/test' example.AppSmokeTest
```

Note that the `javac -d` command writes `.class` files into a different directory tree from the input sources; do not use `-d src/main/java`. For large projects, the build tool manages source roots, dependencies, and tasks, without needing to manually list each `.java` file as in this demonstration.

### 4.5. Trying Out-of-Order Scenarios

If you skip the `BuildInfo.java` generation step and try to compile `App.java` alone in a clean build tree, `javac` will not find the symbol `BuildInfo`. If you compile `AppSmokeTest.java` without putting `build/classes/java/main` on `-cp`, the compiler will not find `App`. These are **two different errors**: missing generated input before main compilation and missing main output on the test compile classpath. The fact that tests compiled successfully earlier does not prove the current dependency graph is correct if `build/` still retains old files.

## 5. Expressing the Same Principles with Gradle

With the Java plugin, Gradle provides built-in `main` and `test` source sets, which by default read `src/main/java`, `src/main/resources`, `src/test/java`, and `src/test/resources`. Familiar tasks are `compileJava`, `processResources`, `classes`, `compileTestJava`, `processTestResources`, `testClasses`, and `test`.

Example `build.gradle` using Groovy DSL: the task creating `BuildInfo.java` is declared as the **producer of an output directory**, and then that directory is registered as a Java input of `main`.

```groovy
plugins {
    id 'java'
}

def generatedJavaDir =
    layout.buildDirectory.dir('generated/sources/buildInfo/java')

def generateBuildInfo = tasks.register('generateBuildInfo') {
    outputs.dir(generatedJavaDir)

    doLast {
        def output = generatedJavaDir.get()
            .file('example/BuildInfo.java').asFile
        output.parentFile.mkdirs()
        output.setText('''package example;

public final class BuildInfo {
    public static final String VERSION = "1.0-demo";
    private BuildInfo() {}
}
''', 'UTF-8')
    }
}

sourceSets {
    main {
        java.srcDir(generateBuildInfo)
    }
}
```

In the Gradle example, the `generateBuildInfo` task itself generates the class, so **there is no need to additionally run `tools/BuildInfoGenerator.java`** from the manual compilation section. `sourceSets.main.java.srcDir(generateBuildInfo)` uses the task provider's output as a source directory and passes the task dependency relationship to Gradle. `compileJava` receives the output of the code generation task; `compileTestJava` receives the main output and test sources. `outputs.dir` lets Gradle know the generator's output and is part of the basis for tracking up-to-date status/cache.

You can verify this using `./gradlew classes` on Linux/macOS or `gradlew.bat classes` on Windows, when the project has a Gradle Wrapper. If you want to run `gradle test` in the standard way, write JUnit tests and declare the corresponding dependencies/test framework; `AppSmokeTest.main` above only runs via a separate `java` command.

**Avoid two Gradle configuration mistakes:**

- Do not place generated output under `src/main/java` so that "Gradle sees it automatically". That mixes tool-managed files into Git and prevents `clean` from keeping them cleanly separated.
- Do not add a build-generated path into a source root as a hardcoded string while forgetting to declare the code generation dependency. A build may accidentally pass thanks to old files, but fail after `clean` or when CI runs in parallel.

If a real-world generator requires annotation processing, use the appropriate processor configuration (for example, `annotationProcessor` for the main Java source set). Processor code is not by default a runtime dependency of the application. If test code is also generated, that output must belong to the `test` source set, not `main`. Different generator plugins have their own ways of registering tasks and source roots; always check the plugin documentation instead of just adding a directory in the IDE.

## 6. Generated Source, Resources, and Compiled Output Are Not the Same

Three output types need to be distinguished:

- **Generated source**: files with source language syntax, such as `BuildInfo.java`. The compiler still has to read them to produce `.class` files.
- **Generated resource**: JSON, YAML, XML, metadata, localization files, or other resources generated from inputs. They need to be wired into `processResources` or the appropriate resource task, and are usually copied rather than compiled like Java.
- **Compiled output**: `.class` files from a compiler or bytecode producer. A `.class` directory should not be treated as a Java source directory. They are consumed via the classpath or packaging output.

An annotation processor can generate code during `compileJava`; the generated source then belongs to a generated directory managed by the compiler/build task. Do not assume every generator must have a separate task running **before** `compileJava`: the exact relationship depends on the generation mechanism. What is mandatory is that the build knows who produces the output and who consumes the output.

**Marking a "generated sources root" in an IDE is a navigation convenience**, not a substitute for build configuration. Verifying after `clean` and running the build from the command line/CI is what reveals missing source set configuration or task dependencies.

## 7. Tests Have Their Own Source Types

For tests, separation also includes data, dependencies, and execution scope:

- Test code can import public APIs and package-level APIs of main when in the same package; do not force application code to depend back on test utilities.
- Mock data, test fixtures, and test configuration should reside in `src/test/resources` or a dedicated test-fixtures source set/module if broader sharing is needed.
- Generated files solely for testing (such as test stubs) must reside in the test generator output and go onto the **test compile classpath**.
- Unit tests should be independent of files generated from a previous build; integration tests may need a separate source set/task, but do not merge everything into main.
- A test file in `src/test/java` **is not guaranteed to be discovered by the test runner**: it also depends on naming, framework, annotations, and task configuration. The manually run `AppSmokeTest` example illustrates this exact point.

In a released library, main classes and main resources can be packaged into the JAR; test classes and test resources are usually excluded. Verify the actual packaged artifact when configuring custom packaging, rather than relying entirely on directory names.

## 8. Reproducibility, Git Management, and Safety During Code Generation

A robust code generation pipeline needs to satisfy the following principles.

**Explicit inputs:** the generator receives the schema, interface, configuration, tool version, and all necessary inputs. If the version/schema changes, the output needs to be regenerated. Do not depend on personal machine state, the system clock, or undeclared temporary directories if you want reproducible output.

**Separated outputs:** the generator writes only to a directory it owns, for example `build/generated/sources/<tool>/java`; do not overwrite human-written files. Two different generators need separate output directories to avoid write contention and to keep cleanup scoped.

**Clean build verification:** run `clean` and then `build` in a clean environment to prove there is no reliance on leftover generated files. With Gradle, declare inputs/outputs and task relationships properly so that up-to-date checking, the build cache, and parallel execution work reliably. If a generator does not have fully declared inputs or has unstable results, caching/up-to-date checks can be wrong even with `outputs.dir`.

**Git conventions:** usually only commit main code, tests, schemas, and generator configuration; ignore `build/` or `target/`. There are cases where generated sources are intentionally committed (for example, to distribute an SDK or support tools that do not run the generator), but that is a project decision: you must document the source of truth, how to regenerate, and the diff verification process. Do not edit a generated file directly while ignoring the input that generated it.

**Avoid boundary leaks:** do not put secrets, personal machine paths, sensitive data, or random timestamps into generated artifacts if they will be packaged or published. Do not allow test dependencies to appear in the production runtime just because the generator or tests need them.

## 9. Common Symptoms and How to Handle Them

| Symptom | Possible Cause | Check/Fix |
| --- | --- | --- |
| `cannot find symbol BuildInfo` when compiling main | File not yet generated or generated source root not declared | Check generator output and the dependency from `compileJava` to the producer |
| Test compilation reports `App` not found | Missing main classes on the test compile classpath | Check the `test` source set, `main` output, and classpath |
| Build passes in IDE but fails on CI | IDE picks up an old generated directory; build task missing dependency | Run `clean` and build from the command line; declare producer/consumer in the build |
| Build only passes when not running `clean` | Using stale artifacts | Delete outputs using the clean task; regenerate everything from original sources |
| Generated code is edited and then changes are lost | Output edited manually | Fix the schema/template/generator and regenerate |
| Test library appears in the JAR | Main mixed with test or wrong dependency scope | Check source sets and dependency configurations, then inspect the JAR |
| Same class defined twice | Generated code copied into main sources or two generators generate the same class | Choose one owning source for the class; remove the duplicate in source roots |
| Tests do not run even though compilation succeeds | Test runner does not recognize the tests | Check framework/annotation/naming and `test` task configuration |

## 10. Checklist for Self-Assessing a Project

A good configuration can answer these questions:

1. Do human-written files and generator-produced files have separate **owners** and directories?
2. Are `main` and `test` distinguished in terms of source roots, resources, classpath, and packaged artifacts?
3. Which task creates each generated directory and which task consumes it? Is that relationship described in build configuration rather than manual steps in an IDE?
4. Does running from a clean checkout (without `build/`/`target/`) generate all generated sources and compile/test successfully?
5. Does modifying generator inputs update the output appropriately, while leaving inputs unchanged avoids unnecessary regeneration/recompilation?
6. Can you inspect the final JAR and confirm it **does not contain** unintended test classes, test fixtures, or test libraries?

**Practice exercise:** try deleting just the `build/generated/sources/buildInfo/java` directory in the example, then rerun the command sequence starting from the generator; next, try skipping the generator step on a clean build to observe the `javac` error. Finally, configure `generateBuildInfo` in Gradle and verify that `classes` generates the code automatically. These three tests respectively verify regenerability, dependency ordering, and that the build tool truly owns the generated source.
