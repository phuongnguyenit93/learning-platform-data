# The Generated Source Directory `-s` and Its Relationship with the Class Directory in Java

In a Java compilation pipeline with **annotation processing**, a processor can generate additional `.java` source files. The `javac` compiler has two different output destinations: **`-s <dir>` to store generated Java sources**, and **`-d <dir>` to store compiled `.class` files**. The two directories may relate to the same Java type, yet hold **two different artifact types at two different stages**, and do not replace each other.

This lesson is about *annotation processing*, not merely a directory-creation command. You need to understand when processors generate code, how `javac` feeds that code through processing rounds, why you sometimes see `Generated.java` without `Generated.class`, and how to configure builds to avoid mixing source/generated code with class output.

## 1. Overall Map of Annotation Processing

~~~text
Original source (*.java) + annotations
                |
                v
             javac
      analyzes source, types
                |
                v
       Annotation processor(s)
                |     javax.annotation.processing.Processor
                |     Filer.createSourceFile(...)
                v
   Generated Java source (*.java)
                |
                +-------> -s build/generated-sources/
                |
                v
   Next processing round (when new source exists)
                |
                v
     Compiler analyzes + generates bytecode
                |
                +-------> -d build/classes/
                            *.class, including classes from generated source
~~~

Conceptual workflow:

1. `javac` reads initial sources and identifies matching annotations/processors.
2. A processor runs in *processing rounds*. The processor can use `javax.annotation.processing.Filer` to create new sources.
3. Source files are created in **`SOURCE_OUTPUT`**, which is the location specified by `-s` when this option is present.
4. New source files are fed into subsequent rounds and, in normal compilation mode, can be compiled by `javac` into bytecode.
5. Class files are written to **`CLASS_OUTPUT`**, i.e., the directory specified by `-d`.

Key point: **`-s` does not mean forcing the compiler to generate sources at all costs.** It merely sets the *destination* for source files that an annotation processor might create. If there is no matching processor, no processed annotation, or the processor generates no source, `-s` may contain no new files.

Similarly, `-d` does not automatically enable annotation processing; it specifies where to place the compiler's output class files.

## 2. Exact Meaning of `-s` and `-d`

| Criterion | `javac -s DIR` | `javac -d DIR` |
| --- | --- | --- |
| Purpose | Destination for **generated source files** | Destination for **compiled class files** |
| Common file types | `.java` generated by annotation processors | `.class` from original sources and generated sources |
| Corresponding API in processor | `StandardLocation.SOURCE_OUTPUT` | `StandardLocation.CLASS_OUTPUT` |
| Who creates the contents? | Processor using `Filer.createSourceFile` | `javac` generates bytecode, or processor using `Filer.createClassFile` in specialized cases |
| Must sources be generated? | No: the directory may be empty | No: normal source code still generates `.class` when compilation succeeds |
| Package-based path layout | `demo.GeneratedGreeting` → `DIR/demo/GeneratedGreeting.java` | `demo.GeneratedGreeting` → `DIR/demo/GeneratedGreeting.class` |
| Input for `java -cp` | Do not use source directory as runtime classpath | Use directory containing class files |
| Common usage | Inspect/debug generated code; IDE support; check processor output | Run/test/package application |

The two directories **should be distinct** and also distinct from the original sources:

~~~text
project/
├── processor-src/             # Source code of annotations and processors
├── app-src/                   # Hand-written source code
├── build/
│   ├── processor-classes/     # Compiled processor and annotation
│   ├── generated-sources/     # Destination of -s
│   └── classes/               # Destination of -d
~~~

For example, `build/generated-sources/demo/GeneratedGreeting.java` and `build/classes/demo/GeneratedGreeting.class` correspond to **the same type `demo.GeneratedGreeting`**, yet the first file is human-readable source, while the second is an executable JVM binary artifact.

**Do not confuse `javac`'s `-s` with `-source` or `--source`**: `-s` specifies the processor-generated source directory; `--source 17` specifies the Java syntax level. Similarly, `--release 17` is a language/API/bytecode compatibility option, not an output directory setting.

## 3. Complete Example: Processor Generating `GeneratedGreeting.java`

The example runs with **JDK 17+**, using only standard APIs, without Maven/Gradle or third-party libraries. We create an annotation `@AutoInfo`, an annotation processor, and an application program using the newly generated class.

### 3.1. File Tree Before Compilation

~~~text
sample/
├── processor-src/
│   └── demo/
│       ├── AutoInfo.java
│       └── GreetingProcessor.java
└── app-src/
    └── demo/
        ├── Request.java
        └── App.java
~~~

Place the files below accurately, then run the commands from the `sample/` directory.

### 3.2. Defining the Annotation

**`processor-src/demo/AutoInfo.java`**

~~~java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface AutoInfo {
}
~~~

`RetentionPolicy.SOURCE` is sufficient for an annotation processor to read the annotation during compilation; there is no need to retain the annotation in the class file/runtime for this example's code-generation functionality.

### 3.3. Writing the Annotation Processor

**`processor-src/demo/GreetingProcessor.java`**

~~~java
package demo;

import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.TypeElement;

@SupportedAnnotationTypes("demo.AutoInfo")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class GreetingProcessor extends AbstractProcessor {
    private boolean generated;

    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment roundEnv) {
        if (generated || roundEnv.processingOver() ||
            roundEnv.getElementsAnnotatedWith(AutoInfo.class).isEmpty()) {
            return true;
        }

        generated = true;
        try {
            var file = processingEnv.getFiler()
                    .createSourceFile("demo.GeneratedGreeting");
            try (Writer writer = file.openWriter()) {
                writer.write("package demo;\n"
                    + "public final class GeneratedGreeting {\n"
                    + "  private GeneratedGreeting() {}\n"
                    + "  public static String message() { return \"generated-ok\"; }\n"
                    + "}\n");
            }
        } catch (IOException ex) {
            throw new IllegalStateException("Cannot generate source", ex);
        }
        return true;
    }
}
~~~

Explanation of key points:

- `AbstractProcessor` implements the standard processor interface.
- `@SupportedAnnotationTypes("demo.AutoInfo")` declares the annotation name that the processor supports. That name is **not** the generated source file name.
- `@SupportedSourceVersion(SourceVersion.RELEASE_17)` declares the ability to process Java 17 sources; this differs from `javac --release 17`, which sets the compilation target.
- `roundEnv.getElementsAnnotatedWith(AutoInfo.class)` finds declarations carrying the annotation. If there are none, the processor generates no file.
- `processingEnv.getFiler().createSourceFile("demo.GeneratedGreeting")` creates a `JavaFileObject` belonging to location `SOURCE_OUTPUT`; the name supplied is the **fully qualified type name including package**, not a filesystem path.
- `openWriter()` writes the entire new Java source, including `package demo;`.
- The `generated` flag prevents attempting to create the same source file again in a subsequent round; `roundEnv.processingOver()` avoids generating files in the final round. In real projects, multi-file/multi-source writing and error handling must also be designed carefully.

**Do not write `new File("build/generated-sources/...")` directly inside a processor to bypass `Filer`**: `Filer` provides a compiler-managed mechanism to place output by package, register new sources for processing rounds, and detect many duplicate-creation cases.

### 3.4. Application Sources Triggering the Processor

**`app-src/demo/Request.java`**

~~~java
package demo;

@AutoInfo
public final class Request {
}
~~~

**`app-src/demo/App.java`**

~~~java
package demo;

public final class App {
    public static void main(String[] args) {
        System.out.println(GeneratedGreeting.message());
    }
}
~~~

When the project is first created, **neither** `GeneratedGreeting.java` nor `GeneratedGreeting.class` exists. App references a type that will be generated by the processor during compilation. Therefore, accurate processor configuration is required.

### 3.5. First Compilation: Creating the Compiled Processor

Create the three output directories using Bash/Linux/macOS:

~~~bash
mkdir -p build/processor-classes build/generated-sources build/classes
~~~

PowerShell can create them equivalently with:

~~~powershell
New-Item -ItemType Directory -Force -Path build/processor-classes,build/generated-sources,build/classes
~~~

Compile the annotation and processor (do not compile the app yet):

~~~bash
javac --release 17 -d build/processor-classes processor-src/demo/AutoInfo.java processor-src/demo/GreetingProcessor.java
~~~

After this command:

~~~text
build/processor-classes/
└── demo/
    ├── AutoInfo.class
    └── GreetingProcessor.class
~~~

**`GeneratedGreeting.java` does not exist yet** because in this compilation we only built the processor, without running the processor on `Request`'s `@AutoInfo`. This is a common separation between a processor library module and a processor-consuming application module.

### 3.6. Second Compilation: Running the Processor, Writing `-s` and `-d`

~~~bash
javac --release 17 -cp build/processor-classes -processorpath build/processor-classes -processor demo.GreetingProcessor -s build/generated-sources -d build/classes app-src/demo/Request.java app-src/demo/App.java
~~~

Meaning of each option:

1. `--release 17`: Java 17 syntax/API/bytecode target.
2. `-cp build/processor-classes`: lets the compiler see the declaration of the `demo.AutoInfo` annotation used by `Request.java`.
3. `-processorpath build/processor-classes`: lets the annotation processing mechanism locate/read the processor and its needed dependencies.
4. `-processor demo.GreetingProcessor`: **explicitly specifies the processor to execute**, instead of relying on auto-discovery. This also avoids differences in default processor-execution behavior across JDK versions.
5. `-s build/generated-sources`: directs new Java sources created by the processor into this directory.
6. `-d build/classes`: directs class files of both original sources **and generated sources** into this directory.
7. `app-src/demo/Request.java app-src/demo/App.java`: input files for the current compilation.

**When compilation succeeds, `javac` normally prints no stdout.** In the example, the generated source directory:

~~~text
build/generated-sources/
└── demo/
    └── GeneratedGreeting.java
~~~

File `GeneratedGreeting.java` contains:

~~~java
package demo;
public final class GeneratedGreeting {
  private GeneratedGreeting() {}
  public static String message() { return "generated-ok"; }
}
~~~

Class files directory:

~~~text
build/classes/
└── demo/
    ├── App.class
    ├── Request.class
    └── GeneratedGreeting.class
~~~

An easily overlooked point: **there is no need to invoke `javac` a third time to compile `GeneratedGreeting.java`** in this normal build workflow. `javac` picks up the source generated via `Filer`, feeds it into processing/compilation according to the annotation processing mechanism, and finally generates `GeneratedGreeting.class`.

### 3.7. Running the Application After Compilation

~~~bash
java -cp build/classes demo.App
~~~

**Exact stdout:**

~~~text
generated-ok
~~~

The `GeneratedGreeting.class` class is on the runtime classpath, so the JVM can load and run it. Since the example uses an annotation with `SOURCE` retention and the application does not reference `AutoInfo` at runtime, the runtime classpath only needs `build/classes` for this simple program.

**Do not run**:

~~~bash
java -cp build/generated-sources demo.App
~~~

because `build/generated-sources` contains Java sources rather than the application's class files. That is not the right runtime classpath for the example.

## 4. Why Are There Multiple Processing Rounds?

Annotation processing is not necessarily a single step. Each round sees a set of Java elements provided by the compiler. When a processor generates additional source or class files, the compiler can perform another round so that other processors can observe the new elements.

In the example:

~~~text
First round:
  Request.java has @AutoInfo
  GreetingProcessor creates GeneratedGreeting.java

Next round:
  Compiler recognizes new source
  Processor can see elements originating from that source
  GreetingProcessor does not recreate file (generated = true)

Final round:
  roundEnv.processingOver() = true
  No new source created

Normal compilation phase:
  Generates App.class, Request.class, GeneratedGreeting.class
~~~

This is a model to explain behavior; exact ordering between compiler passes is not a public contract forcing every `javac` implementation to have identical logs. Diagnostic options of `javac` can be enabled to observe processing rounds (see section 8).

Notable rules:

- A processor **should not create the same type/resource file multiple times within the same compilation**. `Filer` may throw `FilerException` when a path/name has already been created or already exists as a corresponding input.
- Sources generated in an earlier round can affect type resolution in later rounds.
- A processor may **generate no Java source** and instead only check annotations, report errors via `Messager`, generate configuration resources, or generate binary class files under the `Filer` contract.
- If a processor generates syntactically invalid source or type errors, final compilation can still fail, even though the `.java` file already appeared in `-s`.

## 5. When You Only Want to Generate Sources: `-proc:only`

Sometimes you want to inspect the sources a processor will generate, yet **do not want to compile the application into class files yet**. Use:

~~~bash
mkdir -p build/only-sources build/only-classes
javac --release 17 -cp build/processor-classes -processorpath build/processor-classes -processor demo.GreetingProcessor -proc:only -s build/only-sources -d build/only-classes app-src/demo/Request.java app-src/demo/App.java
~~~

With PowerShell, create both directories using:

~~~powershell
New-Item -ItemType Directory -Force -Path build/only-sources,build/only-classes
~~~

Result in the example:

~~~text
build/only-sources/
└── demo/
    └── GeneratedGreeting.java

build/only-classes/
    (no App.class, Request.class, GeneratedGreeting.class)
~~~

`-proc:only` requests performing **annotation processing without compiling regular Java classes**. It is very useful for inspecting codegen and splitting the pipeline. `-d` does not change its meaning: the compiler simply does not proceed to the step of generating application class files because of the selected mode.

After generated source already exists, if you want to compile **in a separate next step**, you can do the following:

~~~bash
mkdir -p build/manual-classes
javac --release 17 -proc:none -cp build/processor-classes -d build/manual-classes app-src/demo/Request.java app-src/demo/App.java build/only-sources/demo/GeneratedGreeting.java
java -cp build/manual-classes demo.App
~~~

Stdout is still:

~~~text
generated-ok
~~~

Here `-proc:none` **disables annotation processing**, while the generated source is explicitly specified as an input file to the second `javac` invocation. This is a **manually orchestrated** two-step pipeline, differing from the normal single-pass compilation in section 3.6. If you do not pass the generated source to the second compilation (and the corresponding class is not on the classpath either), `App.java` will fail to resolve `GeneratedGreeting`.

**Do not mistakenly believe `-proc:only` produces sufficient runtime artifacts:** running `java -cp build/only-sources ...` will fail to run the example because there are no compiled classes.

## 6. When Processing Is Disabled: `-proc:none`

With the same `Request.java` and `App.java` sources, if compiled as follows on empty output:

~~~bash
javac --release 17 -proc:none -cp build/processor-classes -d build/classes app-src/demo/Request.java app-src/demo/App.java
~~~

The compiler does not run `GreetingProcessor`, so there is no new `GeneratedGreeting`. Because `App.java` references a type not yet existing on the classpath, the command **fails** with a diagnostic like `cannot find symbol: GeneratedGreeting`.

This is an **intentionally failing example** to distinguish:

- `-proc:none` = do not run annotation processors.
- `-proc:only` = run processing, do not proceed to normal class compilation.
- Normal compile command with `-processor ...` = processing + compilation, able to produce both `.java` and `.class`.

If a previous build left `GeneratedGreeting.class` where the compiler searches, disabling processors can be masked by stale bytecode; when verifying, use **new/clean output directories** and explicit input search paths.

## 7. What If `-s` Is Not Specified?

According to how `javac` works, when a processor generates `.java` files **without `-s`**, generated source files are placed **in the same area as class output** (the directory specified by `-d`) instead of a separate generated-sources directory.

Example:

~~~bash
javac --release 17 -cp build/processor-classes -processorpath build/processor-classes -processor demo.GreetingProcessor -d build/mixed-output app-src/demo/Request.java app-src/demo/App.java
~~~

Assuming `build/mixed-output` was created, the following may appear:

~~~text
build/mixed-output/
└── demo/
    ├── App.class
    ├── Request.class
    ├── GeneratedGreeting.java
    └── GeneratedGreeting.class
~~~

This is **not a syntax error**, yet it mixes generated sources and binary output. For easier inspection, packaging, and clean builds, configure both locations separately:

~~~bash
javac ... -s build/generated-sources -d build/classes ...
~~~

The benefit is clarity of ownership and output kind; separating the directories **does not by itself change the meaning of generated classes**.

### Do the Directories Need to Exist Beforehand?

When using `-d` and `-s`, **create the root directories beforehand** for stable builds, especially when using the CLI directly or on machines with differing path checks. The compiler/processor can create package subdirectories beneath the root when writing files.

If the path lacks write permissions, accidentally points to a file instead of a directory, or is held by another tool, the build can report IO/Filer errors. Do not treat a non-existent directory as proof that the processor did not run: inspect compiler logs and output configuration.

## 8. Processor-Related Options

| Option | Meaning |
| --- | --- |
| `-processor demo.GreetingProcessor` | Explicitly specifies the processor class to run |
| `-processorpath PATH` or `--processor-path PATH` | Specifies the search path for processors and processor dependencies |
| `--processor-module-path PATH` | Specifies the search path for processors packaged as modules, under module-aware rules |
| `-proc:only` | Process annotations only; do not compile normal classes |
| `-proc:none` | Do not run annotation processing |
| `-s DIR` | Source output location |
| `-d DIR` | Class output location |
| `-Akey=value` | Passes a custom option to processors if declared/supported by the processor |
| `-XprintRounds` | Prints processing round information for debugging |
| `-XprintProcessorInfo` | Prints information on invoked processors and the annotations they handle |

The `-X...` options are diagnostic observation flags of `javac`; do not write tests relying on fixed log messages/formats. For an annotation processor in package `demo`, **`processorpath`** must provide both the processor class and the types the processor needs to load. In the example, `AutoInfo.class` and `GreetingProcessor.class` are both in `build/processor-classes`.

### Diagnosing Rounds of the Example

~~~bash
javac --release 17 -cp build/processor-classes -processorpath build/processor-classes -processor demo.GreetingProcessor -XprintRounds -XprintProcessorInfo -s build/generated-sources -d build/classes app-src/demo/Request.java app-src/demo/App.java
~~~

This is an actual compile command with **diagnostic output**, not a new program. `javac` may print lines about `Round 1`, `Round 2`, annotation/processor names, and the final round. Log output may appear on stderr and **should not be treated as stdout of `demo.App`**.

When debugging, check three things: whether the processor was invoked, whether `Request` along with `@AutoInfo` was visible, and whether the generated file was placed in `SOURCE_OUTPUT`. If the processor did not run, an empty `-s` is an entirely expected outcome.

## 9. `Filer` Categorizes Sources, Classes, and Resources

In an annotation processor, common APIs:

| API | Artifact Form | Typical Location |
| --- | --- | --- |
| `Filer.createSourceFile("demo.NewType")` | `demo/NewType.java` | `SOURCE_OUTPUT` → `-s` |
| `Filer.createClassFile("demo.NewType")` | `demo/NewType.class` | `CLASS_OUTPUT` → `-d` |
| `Filer.createResource(StandardLocation.CLASS_OUTPUT, "demo", "info.txt")` | `demo/info.txt` | `CLASS_OUTPUT` → `-d` |
| `Filer.createResource(StandardLocation.SOURCE_OUTPUT, "demo", "info.txt")` | `demo/info.txt` | `SOURCE_OUTPUT` → `-s` |

A processor can generate **resources** in addition to Java sources; therefore, `-s` does not necessarily hold only `.java` files, and `-d` does not necessarily hold only `.class` files. When a processor creates binaries directly with `createClassFile`, there is no "generated `.java` then compiler compiles it automatically" cycle, because the processor itself is supplying the class file.

`Filer` also tracks **the relationship to originating elements** when provided in `createSourceFile(name, originatingElements...)`. This information can help incremental build/tooling understand which declarations generated files relate to. The simple example above does not need an originating element, yet real processors should pass appropriate originating elements when possible.

**Do not manually edit generated sources and treat them as a long-term source of truth.** The next build may regenerate the file, overwrite it, or report duplicate creation depending on workflow. Edit the annotation/processor/template or generation mechanism, then perform a clean rebuild.

## 10. Distinguishing Processor, Annotation, and Application When Arranging Classpaths

Annotation processing involves at least three artifact groups:

1. **Annotations:** application sources need to know `@AutoInfo` is a valid annotation type. For example, place `AutoInfo.class` on the **compile classpath**.
2. **Processor implementation:** the compiler needs to load `GreetingProcessor.class` and its dependencies. For example, use the **processor path**.
3. **Application and generated classes:** runtime needs `App.class`, `GeneratedGreeting.class`, and all dependencies used at runtime. For example, take from the **class output**.

You can declare a single JAR containing both annotations and processor in a demo, yet in practice the **annotation API** and **processor implementation** are usually separated to avoid bringing codegen libraries into runtime unnecessarily.

An annotation with `RetentionPolicy.SOURCE` does not by itself make the processor a runtime dependency. Conversely, a processor may **generate code that depends on a runtime library**, for example a generated serializer calling into runtime APIs; in that case, that runtime library must be declared outside the processor path. Do not infer "compilation succeeded so deployment dependencies are sufficient".

### Classpath, Module Path, and Processor Module Path

For JPMS projects, how processors and annotations are loaded also depends on whether they are packaged as classpath JARs or named modules. `--processor-module-path` is the option for processors on the module path; it differs from the application's `--module-path` and from `--module-source-path`, which specifies module source roots. Do not conflate path types merely because they all contain the word "module".

## 11. Generated Sources and Incremental Build Modes

When a build tool like Maven or Gradle orchestrates Java compilation, it typically sets up separate generated-source directories and class directories, managing task dependencies and caching. Actual directory names depend on the plugin/config and do not necessarily match `build/generated-sources` or `build/classes` in the CLI demo.

For **incremental builds**, distinguish:

- **Hand-written sources**: managed in the project's source tree, reviewed and version-controlled like normal source code.
- **Generated sources**: originate from processors, annotations, and input models; typically regenerated, potentially losing manual edits.
- **Compiled classes**: products of compilation, used for running and packaging. Deleting class output does not mean deleting generated-source output, and vice versa.
- **Stale artifacts**: leftover generated files or old classes when an annotation is removed, a processor changes output, or a build is not clean. They can cause IDEs, tests, and production builds to see different versions.

### Common Scenario: Old Source Still Exists

In run 1, `@AutoInfo` makes the processor generate `GeneratedGreeting.java` and `GeneratedGreeting.class`. In run 2, the developer removes the annotation from `Request` without cleaning the generated-sources/classes directories. Then the old file may still sit on disk, creating the false impression that the processor is still generating it.

**How to diagnose:** use fresh empty output directories, recompile, and inspect the result; or use the build system's official clean task. Do not automatically delete other project directories without confirming ownership and output locations.

### Should the Generated Source Directory Be Added as a Source Root to Recompile?

In **a single normal compilation**, when a processor generates via `Filer`, `javac` already knows the new source and can compile it. Adding `build/generated-sources` back as an input root inside the same compilation or running the processor a second time can:

- Compile the same class twice, causing `duplicate class`.
- Cause the processor to try creating an already-existing file, hitting `FilerException`.
- Mix generated sources from an old build with new sources, causing hard-to-detect discrepancies.

In a **two-step separated pipeline**, such as `-proc:only` followed by `-proc:none`, feeding generated sources into the next compilation is **intentional**. Decisions vary by task graph; do not apply one pattern to every build.

## 12. Common Errors and Root Causes

| Symptom | Possible Cause | How to Check/Fix |
| --- | --- | --- |
| `-s` empty even after compiling | Processor was not invoked; no annotation found; processor generated no source | `-processor`, `-processorpath`, annotations, `-XprintRounds` |
| `package demo does not exist` or `@AutoInfo` unrecognized | Annotation API missing on compile classpath/module path | Add `AutoInfo.class` where the compiler reads sources |
| `Annotation processor '...' not found` | Processor class/dependency missing from processor path or wrong class name | Compile processor first, check FQCN and path |
| `cannot find symbol: GeneratedGreeting` | Generated type not yet created, processed into wrong package, or processing disabled | Check `-s`, compiler diagnostics, `-proc:none` |
| `FilerException: Attempt to recreate a file for type ...` | Processor tried creating the same source/class multiple times or name collided with input | Check rounds, guard/idempotence, clean output |
| `GeneratedGreeting.java` exists yet `.class` is missing | Using `-proc:only`; or generated source failed to compile | Check `-proc` mode, compiler errors, and `-d` |
| `GeneratedGreeting.class` exists yet `.java` is not in expected `-s` | `-s` not specified, mixed output, or class created directly | Check location, processor API, and javac command |
| Source generation fails with `IOException`/permission denied | Cannot write to output directory, invalid path | Check permissions, root directories, filesystem |
| Generated source placed in wrong package directory | Processor passed wrong canonical/package name or wrote filesystem directly | Use `Filer.createSourceFile` and matching `package` source |
| Class exists locally yet missing when deploying | Packaging omitted generated class or runtime dependency | Check `build/classes`, JAR contents, and classpath/module path |
| After editing annotation, still runs old version | Stale source/class artifacts | Clean build, check task graph and inputs |
| Generated source written into hand-written source directory | Wrong `-s` configuration | Separate generated sources from version-controlled sources |

### An Effective Debugging Principle

Do not only ask "does the `.java` file exist yet?", ask sequentially:

1. Did the compiler **locate and run the processor**?
2. Did the processor see the right annotation/element and **call `Filer.createSourceFile`**?
3. Is the source file at **`-s` + package path**?
4. Did the compiler process the new source and succeed?
5. Is the class file at **`-d` + package path**?
6. Are the class file and runtime dependencies on the application's classpath/module path?

Answering these six questions usually pinpoints the exact fault location in the pipeline instead of trial-and-error "adding paths".

## 13. Scenario Table: `-s`, `-d`, and `-proc`

| Command/Condition | Generated `.java` | Compiled `.class` |
| --- | --- | --- |
| `-processor ... -s GEN -d CLASSES` with processor generating valid source | In `GEN` | In `CLASSES` (regular sources + generated sources) |
| `-processor ... -proc:only -s GEN -d CLASSES` | In `GEN` | Does not compile regular app classes |
| `-proc:none -s GEN -d CLASSES` | Not generated via annotation processing | Compiler may still generate classes from provided input sources if error-free |
| Processor present without `-s` specified, with `-d CLASSES` | Normally in class output location `CLASSES` | In `CLASSES` |
| No processor or processor creates no source | No generated source | Can still generate classes for original sources |
| Processor creates only resources at `CLASS_OUTPUT` | Possibly no generated `.java` | Resources in class output; normal classes generated by compiler if compilation succeeds |

`-s` and `-d` are **output locations**, not file-creation switches and not guarantees that compilation succeeded. Read full compiler diagnostics and the exit code.

## 15. Self-Check Questions

**1. Does `javac -s gen -d classes` always create Java files in `gen`?**  
No. `-s` only specifies the location; a processor must generate new sources for files to appear.

**2. Why does the same type have `gen/demo/T.java` and `classes/demo/T.class`?**  
`.java` is source created by the processor; `.class` is bytecode generated by the compiler after compiling that source.

**3. Is a second `javac` run needed after the processor creates source?**  
No in normal compile mode when source is created via `Filer` and the compiler handles it automatically. Yes in a pipeline intentionally separating `-proc:only` then `-proc:none`.

**4. What does `-proc:only` produce?**  
Runs annotation processing and can write generated sources/resources; does not generate application class files via normal compilation.

**5. What does `-proc:none` mean?**  
Does not execute annotation processors; the compiler can still compile provided source files if they have sufficient dependencies.

**6. Can `-processorpath` replace `-cp`?**  
Not in all cases. Processor path lets the compiler load processors; compile classpath lets sources see annotation APIs and source dependencies. Paths may coincide in demos, yet they are two different responsibilities.

**7. Why is `Generated.java` located under `gen/demo/`?**  
Canonical name `demo.Generated` has package `demo`, so `Filer` uses the matching package path under the source output root.

**8. Is running `java -cp build/generated-sources demo.App` correct?**  
Not in the example. The JVM needs class files and runtime dependencies, not using the source output directory as a compiled classpath.

**9. What happens if a processor generates syntactically invalid source?**  
You may see the file in `-s`, yet compilation will report errors and class output will be incomplete.

**10. Why can generated files still appear from a previous build even when the annotation is gone?**  
Output was not cleaned or incremental build did not track inputs accurately; verify using a new output directory and a clean build.

**Conclusion:** `-s` decides **where processor-generated sources go**, while `-d` decides **where class files are placed**. A generated Java source can continue to be processed by the compiler within the same compilation to produce a class file; only when intentionally choosing `-proc:only` are code generation and class compilation separated.
