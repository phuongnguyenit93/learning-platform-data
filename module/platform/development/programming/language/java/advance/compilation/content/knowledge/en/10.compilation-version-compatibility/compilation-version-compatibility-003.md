# Using `javac --release` to Constrain Syntax, Platform APIs, and Output

## Learning Objectives

After this lesson, you can:

- Distinguish the three compatibility layers that the Java compiler needs to control: **language syntax/semantics**, **Java platform APIs**, and **class-file format**.
- Use `javac --release N` to compile on a newer JDK while targeting an older Java version supported by the compiler.
- Explain why using only `-source N -target N` can still generate class files that use APIs that do not exist on the target runtime.
- Inspect class-file major version with `javap -verbose`, identify `UnsupportedClassVersionError`, `NoSuchMethodError`, and the limitations outside the scope of `--release`.
- Configure Gradle/Maven consistently and verify compatibility by running tests on the exact supported runtime.

This lesson focuses on **the meaning and usage of `--release` in Java compilation**; it does not address the entire cross-platform deployment problem.

## 1. Java Compatibility Has at Least Three Layers

Suppose you develop with **JDK 21**, but the application must run on **Java 17**. Saying “the code is written in Java 17” is not clear enough: you also need to ask what syntax the source uses, which APIs it calls, and which class-file version the compiler produces.

| Constraint layer | Question to answer | Risk example |
| --- | --- | --- |
| **Language (source level)** | Does it use syntax/semantic features that only appear in newer versions? | Using `record` while requesting compilation under Java 11 |
| **Platform API** | Do the Java SE classes, methods, and fields called exist in the target release? | Using `List.getFirst()` (Java 21) while having to run on Java 17 |
| **Class-file target** | Can the target JVM read the `.class` format generated by the compiler? | A Java 21 class file with major version 65 given to a JVM 17 supporting only level 61 |

**`javac --release 17` constrains all three layers for the source code compiled by `javac`**, based on the releases supported by the JDK version in use.

Basic flow:

~~~text
JDK 21 runs javac
         |
         | javac --release 17 -d out17 src/App.java
         v
Check language at Java 17 level
         |
         v
Allow only supported Java 17 platform APIs
         |
         v
Generate Java 17 target class file (major version 61)
         |
         v
Can run on Java 17+ if other runtime conditions are satisfied
~~~

The word “Can” in the last line is very important: the application may still depend on external libraries, native libraries, module configuration, files, network, OS, or runtime behavior that `--release` is not responsible for.

### 1.1 `--release` is a compiler option, not a launcher option

These two commands do different things:

~~~bash
javac --release 17 -d out17 src/App.java
java -cp out17 App
~~~

- `javac` checks the source and generates bytecode.
- `java` starts the JVM, loads, and executes bytecode.
- `--release 17` applies **at compile-time**. It does not install Java 17 on the machine, does not automatically switch `java` to JVM 17, and does not create a JVM 17 runtime in the output directory.
- If the `java` command in the terminal points to Java 21, the example above will still run on Java 21. To verify the ability to run on Java 17, you must actually test on a **Java 17 runtime**.

Do not use `java --release 17 App` as a way to “select the Java level” for bytecode; that is not the purpose of this compiler option.

## 2. How Does `--release` Differ from `-source` and `-target`?

The three options have separate responsibilities:

| `javac` option | What it controls | Limitation |
| --- | --- | --- |
| `-source 17` or `--source 17` | Language level that source is allowed to use | **Does not automatically restrict** standard APIs of the compiler JDK |
| `-target 17` or `--target 17` | Generated class-file version | **Does not automatically restrict** platform APIs called |
| `--release 17` | Language level, release 17 platform APIs, and class-file target 17 | Does not guarantee all non-JDK dependencies, runtime features, or deployment environments are compatible |

`-source` and `-target` are not completely useless: compilers/build tools may still need them in specific configuration scenarios. However, when the goal is to **target an older Java release on a newer JDK**, `--release` usually expresses the right contract.

### 2.1 Why can setting only the target class file be dangerous?

A class file with major version 61 is recognized by JVM 17 in terms of format. However, inside that bytecode there can still be a call to a method **not yet defined in the Java 17 API** if you compiled it against Java 21 libraries.

In that case, reading the class file has no major version problem, but when linking or executing the call, the JVM may encounter `NoSuchMethodError`. This error is in **API/linkage compatibility**, not class format.

`--release 17` prevents using Java 21 platform APIs right at compile time by showing the compiler the platform APIs appropriate for Java 17.

### 2.2 Language level does not equal API level

A piece of source code with very old syntax can still call a method introduced much later. For example:

~~~java
String first = java.util.List.of("Lan", "Minh").getFirst();
~~~

The method call here uses no special Java 21 syntax; however, `List.getFirst()` was introduced in Java 21. On JDK 21, `-source 17 -target 17` can accept that expression if the compiler uses the current platform APIs. `--release 17` will reject APIs that do not exist at the target level.

Conversely, an API that already existed in Java 17 does not allow you to use syntax present only in Java 21 when compiling with `--release 17`.

## 3. Lab Preparation

In the examples comparing Java 17 and Java 21 below, use **JDK 21 to run the compiler**. To run separate tests on Java 17, you also need an installed Java 17 runtime/JDK and be able to invoke its exact path.

Check the compiler and launcher currently used by the terminal:

~~~bash
javac -version
java -version
javac --help
~~~

`javac --help` lists the releases supported by **the installed compiler version**. Do not assume any arbitrary JDK can target every Java version in history or a future version.

Create a new project directory:

~~~text
release-demo/
└── src/
    ├── Report.java
    ├── ApiBoundary.java
    └── ApiOnly.java
~~~

The files can be created with a text editor, saved as **UTF-8**. All `javac` commands below are run from the root directory `release-demo`.

Prepare output directories in PowerShell:

~~~powershell
New-Item -ItemType Directory -Force out17, out21, out11, out8, out-bad | Out-Null
~~~

Or in Bash/Zsh:

~~~bash
mkdir -p out17 out21 out11 out8 out-bad
~~~

Use separate output directories to avoid mixing up class files across compilation runs. In each command, `-d` specifies where to write output; the class name and package determine the class path inside.

## 4. Practice A: Creating a Java 17 Class with JDK 21

Create the file **`src/Report.java`**:

~~~java
import java.util.List;
import java.util.stream.Collectors;

public record Report(String language, int count) {
    public static void main(String[] args) {
        List<String> words = List.of("JDK", "javac", "JVM");
        String keywords = words.stream()
                .map(String::toLowerCase)
                .collect(Collectors.joining(","));

        Report report = new Report("Java", words.size());
        System.out.println(report);
        System.out.println("Keywords = " + keywords);
    }
}
~~~

This is **standalone source code that compiles on Java 17+**. `record` is a language feature finalized in Java 16; `List.of` has been available since Java 9; `Collectors.joining` since Java 8.

### 4.1 Compile on JDK 21 with release 17

~~~bash
javac --release 17 -encoding UTF-8 -d out17 src/Report.java
java -cp out17 Report
~~~

Exact stdout of the example:

~~~text
Report[language=Java, count=3]
Keywords = jdk,javac,jvm
~~~

We used **JDK 21 to compile**, yet source, platform APIs, and class-file format are constrained to **Java 17**.

The first line shows the record's `toString()`. The second line is produced by a stream joining the three words converted to lowercase, in list order.

### 4.2 Check the major version

~~~bash
javap -verbose -classpath out17 Report
~~~

In the output, find:

~~~text
major version: 61
~~~

For Java 17, major version 61 is the corresponding class-file version. `javap -verbose` also displays various other metadata; you do not need to memorize the order or constant-pool indexes.

If compiling the same source with JDK 21 **without setting a lower target**, the class file usually carries major version **65** (Java 21):

~~~bash
javac -encoding UTF-8 -d out21 src/Report.java
javap -verbose -classpath out21 Report
~~~

With the default JDK 21 compiler, you will see `major version: 65`.

Do not drop the default `out21/Report.class` into a JVM 17 and expect it to run: JVM 17 does not support class-file level 65 and may throw `UnsupportedClassVersionError`.

### 4.3 Lowering the requirement to Java 11: the compiler rejects new syntax

~~~bash
javac --release 11 -encoding UTF-8 -d out11 src/Report.java
~~~

The command must fail because **record** is not yet a supported language syntax in Java 11. The compiler may emit a diagnostic equivalent to “records are not supported in -source 11”; diagnostic wording and line numbers vary by JDK version.

This proves one branch of `--release`: it controls the language level, rather than merely producing a class file with a lower version number.

Do not fix the warning/error by simply adding `-target 11`: record syntax does not belong to Java 11. If Java 11 compatibility is required, you must replace the language construct with a form valid for Java 11, such as a regular class.

## 5. Practice B: Preventing Java 21 API Usage in an Artifact Targeting Java 17

This example shows that **a valid language level can still be accompanied by a wrong-version API**.

Create the file **`src/ApiBoundary.java`**:

~~~java
import java.util.List;

public class ApiBoundary {
    public static void main(String[] args) {
        List<String> names = List.of("Lan", "Minh");
        System.out.println(names.getFirst());
    }
}
~~~

`List.of` has existed since Java 9. However, `getFirst()` on `java.util.List` only appeared with the sequenced collection APIs of **Java 21**.

### 5.1 Default compilation with JDK 21

~~~bash
javac -encoding UTF-8 -d out21 src/ApiBoundary.java
java -cp out21 ApiBoundary
~~~

With JDK 21, stdout:

~~~text
Lan
~~~

That is a valid result **on Java 21**. It does not prove the application can run on Java 17.

### 5.2 Using `--release 17`: detecting errors before deployment

~~~bash
javac --release 17 -encoding UTF-8 -d out17 src/ApiBoundary.java
~~~

The command **fails at compile-time** because the `List.getFirst()` API does not belong to the Java 17 API surface. The diagnostic typically includes `cannot find symbol` and the location of the `getFirst()` call. This is the exact expected error: the compiler is preventing you from publishing a class whose format is Java 17-compatible but which calls an API missing in the target runtime.

### 5.3 Using only `-source 17 -target 17`: compatibility trap

On the JDK 21 compiler, try:

~~~bash
javac -source 17 -target 17 -encoding UTF-8 -d out-bad src/ApiBoundary.java
javap -verbose -classpath out-bad ApiBoundary
~~~

In a typical JDK 21 environment, this source can **compile successfully**, because the syntax matches Java 17 and the compiler still sees Java 21 APIs. The generated class file has:

~~~text
major version: 61
~~~

There may be a warning about the system modules path of the older target; that further reminds us that `-source/-target` alone does not constrain platform APIs.

If running `out-bad` **with an actual JVM 17**, the call `List.getFirst()` does not exist on Java 17's `java.util.List` class and may lead to `NoSuchMethodError` when invoked. Do not assume an exact full stack trace because message strings vary across JVMs.

Key takeaway:

~~~text
JDK 21 + -source 17 -target 17
    |
    +--> Java 17 syntax: passes
    +--> Class file major 61: passes
    +--> Java 21 List.getFirst(): can still slip in
    |
    v
JVM 17: error when needing to resolve/call the missing method

JDK 21 + --release 17
    |
    +--> Java 17 syntax: checked
    +--> Java 17 APIs: checked
    +--> Class file major 61: generated if valid
    |
    v
API error caught right at compile time
~~~

**This is the core benefit of `--release` over `-source/-target` alone when cross-compiling Java platform APIs.**

## 6. Practice C: Old Source Syntax, New API

The previous example used `List.of` (Java 9), making it hard to observe API restriction at Java 8 separately. Let us use source code with older Java syntax that calls a method introduced in Java 11.

Create the file **`src/ApiOnly.java`**:

~~~java
public class ApiOnly {
    public static void main(String[] args) {
        System.out.println("ab".repeat(3));
    }
}
~~~

The syntax `"ab".repeat(3)` does not use records, text blocks, or pattern matching. The issue is that **`String.repeat(int)` was added in Java 11**.

### 6.1 Targeting Java 8

On a JDK 21 supporting release 8:

~~~bash
javac --release 8 -encoding UTF-8 -d out8 src/ApiOnly.java
~~~

The compiler cannot resolve `String.repeat(int)` against Java 8 APIs, so it reports `cannot find symbol` (method `repeat(int)`).

### 6.2 Targeting Java 11

~~~bash
javac --release 11 -encoding UTF-8 -d out11 src/ApiOnly.java
java -cp out11 ApiOnly
~~~

Stdout:

~~~text
ababab
~~~

`javap -verbose -classpath out11 ApiOnly` will show `major version: 55`, corresponding to Java 11.

Thus, the same syntax can be valid at two source levels, whereas an **API call** is only valid when the target release's platform API already includes it.

### 6.3 Class-file milestone reference table

| Java release | Class-file major version |
| --- | ---: |
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

The table speaks only of the class-file format; it does not tell which platform APIs a class calls and does not replace compiling with `--release`.

## 7. How Does the Compiler Implement `--release`?

Conceptually, when running `javac --release N`, the compiler needs to know **the platform API shape of Java release N**, rather than simply compiling against the classes of the current JDK. Some modern JDKs use data representing historical signatures of platform APIs, such as OpenJDK's `ct.sym` information system, to check which symbols are permitted at the target release.

You **do not need to manually edit `ct.sym` or copy Java libraries from an older JDK**. The right configuration is to pass `--release N` to a compiler that supports level N. The technical storage path for API signatures is a JDK distribution implementation detail; you should not write scripts that depend on internal file structures.

### 7.1 Not every historical release is supported by a given compiler

`javac --help` or the current compiler documentation tells you which `--release` values are valid. JDK 21, for instance, can compile for many prior releases, but a future newer compiler is not obligated to retain support for every very old release.

If the compiler reports `release version ... not supported`, it does not mean the command syntax is wrong; it may be that **that `javac` version does not support the requested target**. In that case, you need a JDK/toolchain suitable for the target release or to revise the project's version support policy.

### 7.2 `--release` cannot be used to target a future release

JDK 17 cannot fully know the syntax, platform APIs, and class-file target of Java 21. Running a JDK 17 compiler with `--release 21` will not work. To target Java 21, you need a compiler that supports Java 21.

### 7.3 Java preview features have separate constraints

**Preview** features are features not yet fully finalized at the time of their release. The `--enable-preview` flag (when supported) is not a way to use preview features from an arbitrary older release on a newer compiler. Usually, preview source is compiled and run against the **current release** of the corresponding JDK/compiler, with dedicated compatibility rules.

Do not treat `--release 17` as permission to use every syntax that ever appeared in preview form in earlier Java versions or in Java 17. The `record` example above is valid because record became a standard feature in Java 16.

### 7.4 JDK internal APIs are not public platform APIs

A program using internal JDK APIs such as `sun.*` packages or non-exported packages may fail to compile under `--release`. This is usually a sign that the code relies on implementation details rather than Java SE APIs supported in the target release.

`--add-exports` is not a way to arbitrarily bypass `--release` platform API checks; combining compiler flags with internal modules has specific restrictions. For learning code and ordinary applications, prefer public and supported APIs.

## 8. What Does `--release` Not Guarantee?

A class file successfully compiled with `--release 17` **is not yet a certificate that the application will definitely run on every machine with Java 17 installed**. There are many other boundaries to check.

### 8.1 Third-party libraries

Suppose your app compiles with `--release 17` but uses a JAR built for Java 21. The compiler may be unable to read the library's newer class files, or the Java 17 runtime environment may encounter `UnsupportedClassVersionError` when loading those classes. `--release` only controls the source being compiled by the compiler and the platform APIs the compiler permits; it does not rewrite dependency bytecode.

A library with major 61 class files can still use other dependencies/APIs unsuitable for Java 17. You must choose **a library version declared to support the target runtime** and check transitive dependencies.

### 8.2 Reflection and string-constructed names

The compiler can only check calls it sees via normal syntax and types. If code calls `Class.forName("some.NewClass")` or reads API names from a config file, the compiler may not detect that the target class only exists in newer Java. The outcome depends on runtime and classpath.

Similarly, runtime-generated code, plugins, bytecode instrumentation, and JNI can introduce additional requirements not covered by `--release`. For reflection and dynamic plugins, test on the actual runtime.

### 8.3 Operating system, CPU architecture, and native libraries

`--release 17` does not cross-compile native `.dll`, `.so`, `.dylib` libraries, does not guarantee file paths are valid on Windows/Linux, and does not guarantee permissions or network connectivity. Java bytecode is portable across compatible JVMs, yet applications can still depend on the environment.

### 8.4 Behavioral compatibility

Even when an API exists on both runtimes, different updates or environments can cause differences in behavior dependent on locale, charset, time zone, TLS/providers, file handling, or system configuration. `--release` does not replace integration tests.

### 8.5 Compile-time vs. runtime dependencies

If the compiler sees a JAR at compile time but that JAR is not packaged/specified at runtime, the application can still encounter `NoClassDefFoundError`, `ClassNotFoundException`, or other linkage errors. `--release` does not automatically add libraries to the runtime classpath.

In particular, `UnsupportedClassVersionError` is about class-file version; `NoSuchMethodError` is about a method failing to resolve at runtime. Both errors may stem from compatibility issues, but fixing them must be based on the exact root cause.

### 8.6 Multi-release JAR

A JAR can contain multiple class variants via the **multi-release JAR** mechanism so the runtime picks the matching one. `--release` for a single compiler task only generates output for the specified level; it **does not automatically create, arrange, or validate** multi-release variants.

When using a multi-release JAR, you must configure compilation, packaging, manifest, and testing for each appropriate release. Do not infer that “the JAR runs on Java 21” means every class selected when running Java 17 is compatible.

## 9. `--release` in Gradle and Maven

When a project has many source files and modules, put the constraint into the **build configuration** so others/CI do not have to remember to type individual commands.

### 9.1 Gradle — Java toolchain and release are two separate axes

In `build.gradle` (Groovy DSL), for example a project using the Java plugin that wants a JDK 21 compiler to produce classes targeting Java 17:

~~~groovy
plugins {
    id 'java'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

Here:

- Toolchain selects the **JDK 21 compiler** (if Gradle can locate or provision a suitable JDK according to configuration).
- `options.release = 17` requires **classes to be compiled for Java 17**, covering syntax, platform APIs, and class files.
- This **does not automatically make test tasks run with JVM 17**. The test toolchain/launcher may need separate configuration if project policy requires testing on Java 17.
- In multi-module builds, check the configuration of every module whose source is distributed for Java 17.

In `build.gradle.kts` (Gradle Kotlin DSL), the equivalent setup:

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

The snippets above are build configurations for a Java project with a suitable Gradle plugin. The Gradle version must support the selected Java toolchain/JDK; this example is not meant to prescribe a specific Gradle version.

Do not confuse `sourceCompatibility` and `targetCompatibility` with `options.release`. In projects targeting a runtime lower than the compiler JDK, the release option is what tightens the constraint on platform APIs.

### 9.2 Maven — configuring compiler release

In `pom.xml`, with a Maven Compiler Plugin version supporting release, you can configure:

~~~xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
~~~

Or in the plugin configuration:

~~~xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <configuration>
                <release>17</release>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

These are **XML configuration snippets** inside a valid POM, not an entire POM. The plugin version and the JDK running the compiler must support configuring the corresponding release. In real projects, you should pin/manage plugin versions through a verified build configuration.

Do not assume `<source>17</source><target>17</target>` gives the same API guarantee as `<release>17</release>` when building with a newer JDK. Inspect the effective configuration and compiler invocation.

### 9.3 Does `--release` in CI still need the target JDK?

You can compile with JDK 21 using `--release 17`, but to test **actual execution** on Java 17, CI should include a step that runs tests/the application on Java 17. Verification flow:

~~~text
JDK 21 compiler + --release 17
             |
             v
     Build class/JAR
             |
             v
    Test with runtime 17
             |
             v
(By policy) Also test runtime 21
~~~

If tests are run only on JDK 21, many API/behavior issues from third-party code or runtime reflection will not appear. A test matrix across supported runtimes is far more valuable than merely checking target class-file labels.

## 10. Error Diagnosis and Output Verification

### 10.1 Checking which release the compiler uses

Run:

~~~bash
javac -version
javac --help
~~~

Then inspect the build tool's compiler arguments. Do not assume `JAVA_HOME`, terminal, IDE, Gradle daemon, and Maven toolchain all use the same JDK.

### 10.2 Inspecting class files

~~~bash
javap -verbose -classpath out17 Report
~~~

Look for `major version: 61`. For a built JAR, you can use `javap` with the classpath pointing to the JAR:

~~~bash
javap -verbose -classpath path/to/app.jar com.example.Main
~~~

The second command is an **illustrative template**: replace `path/to/app.jar` and `com.example.Main` with the real artifact and class. It is not a runnable command for the `Report` project above unless a corresponding JAR has been built.

**Class-file version only verifies the output layer**; it does not prove all platform APIs are valid. The `ApiBoundary` experiment demonstrated that a major 61 class can still call Java 21 APIs if built with the wrong configuration.

### 10.3 Verifying on the target runtime

On a machine with Java 17, invoke the `java` executable of version 17, then run the Java 17-targeted artifact. General command example:

~~~bash
/path/to/jdk17/bin/java -cp out17 Report
~~~

This is a **sample path** and must be replaced with the real path. On Windows, the executable path is `java.exe` inside JDK 17's `bin`, with invocation syntax matching the shell.

Before drawing conclusions, verify the version of that exact launcher with `-version`; this is especially important if multiple JDKs are installed on the machine.

### 10.4 Common errors

| Message or symptom | Typical cause | How to resolve |
| --- | --- | --- |
| `release version 17 not supported` | Compiler is too old / does not support release 17 | Choose a compiler/toolchain supporting Java 17 |
| `records are not supported in -source 11` | Source uses language features newer than release 11 | Rewrite using Java 11 syntax or raise the release level |
| `cannot find symbol` with `List.getFirst()` under `--release 17` | API exists only in Java 21 | Use an API existing in Java 17 (e.g., `get(0)` when the list is non-empty) |
| `UnsupportedClassVersionError` on JVM 17 | Runtime reads a class file with a major version higher than supported | Build with a compatible target and check all dependencies |
| `NoSuchMethodError` on Java 17 | Binary calls an API missing from the loaded library/runtime | Use `--release`, align dependencies, and test on the real runtime |
| Build succeeds but runtime cannot find class | Missing runtime dependency/classpath/module path | Verify packaging and runtime classpath |
| Compiler sees API but `--release` rejects it | API is outside the supported platform API surface at the target release | Change the API or intentionally raise the release level |
| `invalid flag` or `--release` not recognized | Using a compiler version that is too old or passing wrong flags | Check `javac -version`, `javac --help`, build tool arguments |
| Tests pass on JDK 21 but artifact fails on JDK 17 | Did not test on the actual target runtime or incompatible dependency | Test on Java 17 and inspect the final artifact |

### 10.5 A proper fix for the `ApiBoundary` example

To make `ApiBoundary` run on Java 17, you can replace the code using the Java 21 API by checking that the list is non-empty and then calling `get(0)`.

File **`src/ApiBoundary.java`** after fixing:

~~~java
import java.util.List;

public class ApiBoundary {
    public static void main(String[] args) {
        List<String> names = List.of("Lan", "Minh");
        if (!names.isEmpty()) {
            System.out.println(names.get(0));
        }
    }
}
~~~

Compile and run:

~~~bash
javac --release 17 -encoding UTF-8 -d out17 src/ApiBoundary.java
java -cp out17 ApiBoundary
~~~

Stdout:

~~~text
Lan
~~~

Two points emerge from this example: `--release` detects wrong-version APIs; fixing requires choosing **an API with the same intent that actually exists in the target release**. Using `get(0)` also requires the list to be non-empty, which is why the code checks before accessing.

## 11. Versioning Strategy for Real Projects

### 11.1 Choose the minimum runtime first

If the team declares support for Java 17 and above, explicitly define **Java 17 as the minimum runtime**, then choose a suitable compiler JDK and configure release 17. Do not leave it to default to whatever JDK each developer machine has.

If supporting only Java 21, using `--release 21` on JDK 21 is still helpful for consistent configuration, even though by default the compiler already targets the running version. Avoid accidentally changing the target simply because the toolchain on a machine/CI gets upgraded.

### 11.2 Use a single build configuration as the source of control

For Gradle/Maven, put the release setting into the build file. Verify in build logs/compiler invocations that this setting is applied to **all source sets and modules to be verified**. Generated sources, annotation processors, code in other modules, or custom tasks might use different settings.

In a multi-module app, a library module targeting Java 21 can prevent an app module targeting Java 17 from compiling or running properly. Modules distributed together must share an explicit compatibility policy.

### 11.3 Rebuild and remove stale outputs

When switching from `--release 21` to `--release 17`, you must rebuild the class/JAR that is actually released. If old classes remain in the output or packaging, checking a single new class with major 61 does not guarantee the final artifact contains no major 65 classes.

When in doubt, use a clean output directory or the tool's clean build, inspect the JAR contents, and test loading all critical code paths on Java 17. Mixing multiple bytecode levels in one artifact is only appropriate when intentionally designed, such as a multi-release JAR.

### 11.4 Test behavior alongside bytecode

A good verification policy includes:

1. Compile with `--release` matching the minimum runtime.
2. Inspect the final artifact and dependency graph.
3. Run unit/integration tests on the minimum runtime.
4. Run additional checks on newer runtimes if the project supports them.
5. Monitor API/behavior changes when upgrading JDK, frameworks, or libraries.

The goal of `--release` is to **catch syntax/platform API errors and class format issues right at compile time**. The remaining checks address the limitations that the compiler cannot guarantee on its own.

## 12. Practice Exercises with Answers

### Exercise 1 — Distinguishing each compatibility layer

You use JDK 21, while the application must run on Java 17. Evaluate the configurations:

| Configuration | Java 17 syntax | Java 17 platform APIs | Java 17 class-file target |
| --- | --- | --- | --- |
| `javac --release 17` | Yes | Yes | Yes |
| `javac -source 17 -target 17` on JDK 21 | Yes | Not guaranteed | Yes |
| Default `javac` of JDK 21 | Java 21 | Java 21 | Java 21 |

**Answer:** the first configuration is best suited when using JDK 21 to target Java 17, because it adds API constraints. The second configuration easily lets calls present only in newer platform APIs slip through, while the third defaults to targeting Java 21.

### Exercise 2 — Predicting the outcome for `Report.java`

On JDK 21, try:

~~~bash
javac --release 17 -d out17 src/Report.java
javac --release 11 -d out11 src/Report.java
~~~

**Answer:** the first command succeeds because records are supported in Java 17; the second fails because records are not supported at source level 11. The default output of the first example is the two lines `Report[language=Java, count=3]` and `Keywords = jdk,javac,jvm`.

### Exercise 3 — Why is major version 61 not enough?

Compile `ApiBoundary.java` with `-source 17 -target 17` on JDK 21, then analyze its ability to run on Java 17.

**Answer:** the major 61 class has a format understood by Java 17, but the `List.getFirst()` call does not exist in the Java 17 API. When the method is executed, the runtime may throw `NoSuchMethodError`. `--release 17` prevents this error right at compile time.

### Exercise 4 — Fixing the API to match the release

Replace `names.getFirst()` with logic calling `names.get(0)` when the list is non-empty, then compile:

~~~bash
javac --release 17 -d out17 src/ApiBoundary.java
java -cp out17 ApiBoundary
~~~

**Answer:** after updating the source per section 10.5, the compiler accepts it and stdout is `Lan`. Checking that the list is non-empty avoids an index-access error on an empty list.

### Exercise 5 — Java 11 API on Java 8 target

With `ApiOnly.java`, why does `--release 8` reject `String.repeat` while `--release 11` accepts it?

**Answer:** `String.repeat(int)` was introduced in Java 11. The call syntax itself is ordinary syntax, but the **platform API** differs between release 8 and release 11.

### Exercise 6 — Reading class files without misinterpreting conclusions

`javap -verbose` shows `major version: 61`. What may you conclude?

**Answer:** the class file has the Java 17 target format. You cannot yet conclude that all runtime libraries are compatible or that the code uses no newer APIs, because a major 61 class can still be miscompiled with `-source/-target` and call JDK 21 APIs.

### Exercise 7 — Gradle/Maven setup

In a project with a JDK 21 toolchain and minimum runtime Java 17, what needs to be declared?

**Answer:** Gradle uses `options.release = 17` or `options.release.set(17)` depending on the DSL; Maven uses `maven.compiler.release=17` or `<release>17</release>` in a supporting compiler plugin. Afterward, rebuild, inspect class files, and test on a Java 17 runtime.

## 13. Pre-Release Checklist

- [ ] Clearly identified the **minimum Java runtime** supported by the product.
- [ ] Selected compiler supports the required `--release` value.
- [ ] Compile configuration constrains **language + platform APIs + class file**, preferring `--release` where appropriate.
- [ ] Verified no preview/internal APIs are used outside project policy.
- [ ] Rebuilt classes/JARs and avoided mixing stale artifacts.
- [ ] Verified the major class-file version of important artifacts.
- [ ] Dependencies and external libraries are compatible with the target runtime.
- [ ] Runtime classpath/module path contains the right artifacts when running.
- [ ] Tested on the **actual minimum JVM**, not just a newer JDK on a developer machine.
- [ ] Required OS environments, native libraries, permissions, and runtime configurations are verified.

## Takeaway

**`javac --release N` establishes a compile-time contract on Java syntax, platform APIs, and the class-file target of release N.** This is an important difference from setting only `-source N -target N`, because code can carry an older class format while calling newer Java APIs. To ensure the application is deployable, combine `--release` with compatible dependencies, clean builds, and direct testing on the minimum runtime you declare support for.
