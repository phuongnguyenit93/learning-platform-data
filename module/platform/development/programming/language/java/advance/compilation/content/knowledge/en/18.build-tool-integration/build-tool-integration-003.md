# Separating Compilation of Main Code, Test Code, and Generated Sources

A Java project can contain three code groups with **different roles, different lifecycles, and different classpaths**: main/production code (*main/production sources*), test code (*test sources*), and code generated by tools (*generated sources*). If you put everything into a single directory and invoke `javac` once without distinction, the project will struggle to determine what gets packaged, which libraries serve only tests, which task owns generated code, why incremental builds fail to update, and how to reproduce artifacts on CI.

The right goal is not merely producing `.class` files. The goal is designing **an ordered compilation graph with explicit inputs and outputs**:

1. Code generation tools or annotation processors must be built/ready **before** the task that needs to run them.
2. Main code is compiled together with generated sources **belonging to main**, using the proper production dependencies.
3. Test code is compiled **after main output exists**, with separate test dependencies.
4. Running tests may need both main and test outputs; however, normal production artifacts **do not package test code, test frameworks, or build-time processors**.
5. Generated files reside under a **build/generated...** directory, owned by a task, deletable and regenerable, and not mixed with handwritten code in `src/main/java`.

This lesson applies Java 17+, explaining direct `javac` usage and how it maps to Gradle source sets/tasks, the Maven lifecycle, annotation processing, incremental builds, CI, and real-world classpath errors. The `javac` demo was **actually compiled/run with JDK 24 and `--release 17`**; the Gradle/Maven configuration sections are architectural guidance based on tool documentation and need to be adjusted for your actual project/plugins.

## 1. Distinguishing the Three Source Kinds by Contract

| Kind | Conventional location | Who creates it? | When is it compiled? | Usually in production JAR? |
| --- | --- | --- | --- | --- |
| Main code (main) | `src/main/java` | Programmer | Main compile stage | **Yes**: main class outputs |
| Test code (test) | `src/test/java` | Programmer/test tool | After main, at test-compile stage | **No** |
| Generated source for main | `build/generated/.../main` or `target/generated-sources/...` | Annotation processor/codegen | During or before main compilation | **Generated classes usually yes**, not necessarily packaging `.java` files |
| Generated source for test | `build/generated/.../test` or `target/generated-test-sources/...` | Test processor/codegen | During or before test compilation | **No** in production JAR |
| Processor source | A separate module, e.g., `processor/src/main/java` | Programmer | Before running the processor | Does not go into app runtime if build-only |

The phrase “generated source is in the JAR” easily causes misunderstanding. Normal Java JARs **contain built class files/resources**, not necessarily `.java` files. Generated Java acts as **input to the compiler**; its `.class` files, if belonging to main, are what get placed into production output/packaging.

### Classpaths Are Different Contracts

- **Main compile classpath:** contains libraries that main sources need for type-checking; for example, `SOURCE`-retention annotation APIs if main uses them.
- **Main runtime classpath:** contains main class files and dependencies the application actually needs at runtime.
- **Test compile classpath:** typically contains main class outputs/APIs and test dependencies (JUnit, assertion libraries, test fixtures...).
- **Test runtime classpath:** consists of test classes, main classes, test runtime dependencies, and production runtime dependencies.
- **Annotation processor path:** contains *code running inside the compiler* to generate sources or diagnostics; **not identical** to the main runtime classpath.

It is possible for the same JAR to appear on two classpaths, yet its **role** still differs. In particular, a processor may need libraries used solely for code generation, which should not be pulled into runtime simply because the compiler loaded the processor.

## 2. Compilation Dependency Graph

```text
                 (1) BUILD / FETCH PROCESSOR
                     annotation API
                           |
                           v
                   annotation processor
                           |
                           v
                (2) COMPILE MAIN SOURCES
            src/main/java + processor path
                           |
                           +---- generate .java -> generated/main
                           |
                           +---- javac compiles main + generated
                           |
                           v
                    build/classes/main
                           |
               +-----------+-----------+
               |                       |
          (3) PACKAGE                (4) COMPILE TEST
          app.jar                     src/test/java
               |                       + main classpath
               |                       + test dependencies
               |                       |
               |                       v
               |                 build/classes/test
               |                       |
               |                       v
               +                 (5) RUN TEST
                                      |
                                      v
                                 test result
```

**This is a dependency relationship graph**, not a claim that every build tool produces every class in an exact physical task order. Annotation processing can **generate and compile sources in a single `javac` invocation** across multiple processing rounds, or an independent generator can run as a separate task before `compileJava`. What must be preserved are correct dependencies and clearly owned outputs.

### Three Questions to Audit the Design

1. **Who owns the generated file?** A processor, a schema generator, an OpenAPI compiler, or a codegen task? Avoid two tasks writing to the same path.
2. **Does the generated file belong to main or test?** If the real application needs the class, it is production output; if it only serves tests, it must be isolated from the artifact.
3. **When an input changes, what must re-run?** Changing an annotation, schema, or dependency version must trigger the appropriate generation and compilation tasks; do not rely on files generated from an old build.

## 3. Example Layered Project Structure

Let us run a demo without Maven/Gradle/JUnit so we can observe the principles clearly with `javac`.

```text
build-stages-lab/
├── src/
│   ├── processor/
│   │   └── java/
│   │       └── demo/
│   │           ├── generate/
│   │           │   └── GenerateGreeting.java
│   │           └── processor/
│   │               └── GreetingProcessor.java
│   ├── main/
│   │   └── java/
│   │       └── demo/app/Main.java
│   └── test/
│       └── java/
│           └── demo/app/MainTest.java
└── build/
    ├── processor/
    ├── classes/
    │   ├── main/
    │   └── test/
    └── generated/
        └── sources/main/
```

In the demo, the processor group contains both the **annotation API** and the **processor implementation** in `src/processor/java` so the learner only needs to compile once. In large systems, the annotation API and processor implementation are usually **two artifacts**: main code needs the annotation API at compile time, while the processor implementation sits on the annotation processor path.

The `src/processor/java` location is a **custom manual structure for this lab**, not a source set that Gradle or Maven automatically recognizes in any arbitrary project. When moving to a build tool, place the processor into a separate subproject/module and declare dependencies explicitly.

## 4. Step 1: Build the Annotation API and Processor

Create file `src/processor/java/demo/generate/GenerateGreeting.java`:

```java
package demo.generate;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.SOURCE)
public @interface GenerateGreeting {}
```

This is the annotation that main sources will use to request generating a class. `RetentionPolicy.SOURCE` is appropriate: the annotation is only needed during compilation and is not required when the application runs.

Create file `src/processor/java/demo/processor/GreetingProcessor.java`:

```java
package demo.processor;

import demo.generate.GenerateGreeting;
import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;
import javax.tools.JavaFileObject;

@SupportedAnnotationTypes("demo.generate.GenerateGreeting")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class GreetingProcessor extends AbstractProcessor {
    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment round) {
        if (round.processingOver()
                || round.getElementsAnnotatedWith(GenerateGreeting.class).isEmpty()) {
            return true;
        }

        try {
            JavaFileObject output = processingEnv.getFiler()
                    .createSourceFile("demo.generated.Greeting");

            try (Writer writer = output.openWriter()) {
                writer.write("""
                        package demo.generated;
                        public final class Greeting {
                            private Greeting() {}
                            public static String text() {
                                return "Hello from generated source";
                            }
                        }
                        """);
            }
        } catch (IOException ex) {
            processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.ERROR,
                    "Generation failed: " + ex.getMessage());
        }
        return true;
    }
}
```

**Role:** the processor runs inside the JVM/compiler when processing `@GenerateGreeting`. It creates the logical source `demo.generated.Greeting` via `Filer.createSourceFile(...)`, rather than directly creating bytecode `Greeting.class`.

Why is `Filer` needed instead of opening a file yourself with `Files.writeString`?

- `Filer` is part of the annotation processing contract and knows the compilation's output location.
- `javac` manages generated compilation units and associated processing rounds.
- Generated files can be fed by the compiler into the next round and compiled in the same compilation.
- Build tools can track generated files better when processors adhere to the Filer API.

**Demo limitation:** this processor generates **one fixed-name class** when it finds the annotation; it assumes only one source triggers the generator in the compilation. If multiple elements are annotated, the processor would still try to create a single class; making it production-ready requires naming and managing unique outputs, duplicate detection, and originating elements so incremental builds track dependencies properly. Do not use the demo as-is to generate multiple classes in a large system.

### Compile the Processor First

Standing inside directory `build-stages-lab`:

```bash
javac --release 17 -d build/processor src/processor/java/demo/generate/GenerateGreeting.java src/processor/java/demo/processor/GreetingProcessor.java
```

After succeeding, the key classes include:

```text
build/processor/demo/generate/GenerateGreeting.class
build/processor/demo/processor/GreetingProcessor.class
```

**These are outputs of the processor-building stage**, not production outputs of the application. Keeping them in `build/processor` clearly distinguishes them from `build/classes/main` and `build/classes/test`.

## 5. Step 2: Main Source Calls the Generated Class

Create file `src/main/java/demo/app/Main.java`:

```java
package demo.app;

import demo.generate.GenerateGreeting;
import demo.generated.Greeting;

@GenerateGreeting
public final class Main {
    public static String message() {
        return Greeting.text();
    }

    public static void main(String[] args) {
        System.out.println(message());
    }
}
```

At the time the learner has not yet run the compiler, **there is no `demo/generated/Greeting.java` file in `src/main/java`**. That is intentional! The main source is written to use a type created by the processor during compilation.

### Compile Main and Generate Source in the Same Invocation

```bash
javac --release 17 -cp build/processor -processorpath build/processor -processor demo.processor.GreetingProcessor -s build/generated/sources/main -d build/classes/main src/main/java/demo/app/Main.java
```

Analyzing each option:

| Option | Role |
| --- | --- |
| `--release 17` | Compiles according to Java 17 language/API/class target |
| `-cp build/processor` | Lets main code find `demo.generate.GenerateGreeting` |
| `-processorpath build/processor` | Where the compiler finds `GreetingProcessor` code |
| `-processor demo.processor.GreetingProcessor` | Explicitly specifies the processor to run, avoiding reliance on auto-discovery |
| `-s build/generated/sources/main` | Destination to save **`.java` sources generated by the processor** |
| `-d build/classes/main` | Destination to save **`.class` files of main and generated classes** |
| `src/main/java/demo/app/Main.java` | Handwritten input source for main |

Extremely important points:

- `-s` **does not mean “class output”**; it is for generated sources.
- `-d` is for compiled classes.
- `-processorpath` does not automatically add annotation types to the compile classpath; the demo must include `-cp` because main `import`s the annotation.
- `-processor` is explicitly set so behavior is consistent across different JDKs/toolchains; do not assume processors are always automatically discovered and executed.
- The command **does not list the generated file in source arguments**, because `Filer` and `javac` already manage it within the same pass.

After the compiler runs successfully, inspect the results:

```text
build/generated/sources/main/demo/generated/Greeting.java
build/classes/main/demo/generated/Greeting.class
build/classes/main/demo/app/Main.class
```

The generated file is in directory `build/generated`, **not inside `src/main/java`**. That is a good practice for repository hygiene and clean builds.

### Running Main with Only Class Output

```bash
java -cp build/classes/main demo.app.Main
```

Stdout:

```text
Hello from generated source
```

This run command **does not need `build/processor` on the runtime classpath**, because `@GenerateGreeting` has `RetentionPolicy.SOURCE` and the `Greeting` class was already generated/compiled into main output. If generated code in another project needs a runtime library, then that library must be declared on the runtime classpath; not every annotation processor has zero runtime footprint.

The experiment was actually run with JDK 24 and `--release 17`: both processor compilation and main compilation returned exit code `0`, generated `.java` and `.class` files exist, and main printed the exact single line above.

## 6. Step 3: Compiling Test Code Separate from Main

JUnit is not used in this small example to reduce external dependencies, yet the compile/test classpath principles are identical.

Create file `src/test/java/demo/app/MainTest.java`:

```java
package demo.app;

public final class MainTest {
    public static void main(String[] args) {
        String actual = Main.message();
        if (!"Hello from generated source".equals(actual)) {
            throw new AssertionError("Unexpected: " + actual);
        }
        System.out.println("TEST PASSED");
    }
}
```

Test code **directly references `Main.message()`**, so test compilation must see main classes, including generated classes inside main output.

### Compiling Tests to a Separate Output

Linux/macOS:

```bash
javac --release 17 -cp build/classes/main -d build/classes/test src/test/java/demo/app/MainTest.java
java -cp "build/classes/test:build/classes/main" demo.app.MainTest
```

Windows PowerShell/cmd:

```powershell
javac --release 17 -cp build/classes/main -d build/classes/test src/test/java/demo/app/MainTest.java
java -cp "build/classes/test;build/classes/main" demo.app.MainTest
```

Stdout of the test execution command:

```text
TEST PASSED
```

The experiment also ran successfully on JDK 24 with a runtime classpath **containing only main/test outputs**, without needing processor classes. Class `MainTest` was not emitted into `build/classes/main` because `-d build/classes/test` was used separately.

**No-inverted-dependency rule:** tests read main, whereas main **should not** read test classes or test frameworks. If `Main.java` only compiles when adding `build/classes/test` to the main classpath, that is usually a sign of bad architecture or misplaced test utilities.

### When Real Testing Libraries Exist

For example with JUnit Jupiter, test compilation needs the JUnit API on the **test compile classpath** and running tests needs the corresponding test engine/launcher. These libraries do not automatically need to be packaged into the production JAR. Maven/Gradle manage those classpaths; this lesson does not attempt to fully emulate JUnit's test runner with plain `java` commands.

**Avoid false inferences:** a file named `MainTest.java` with `main` as in the demo is still a manual Java application test. The command `java demo.app.MainTest` simply runs the check; it is not JUnit test discovery. When using JUnit, the build tool runs a different test task/plugin.

## 7. Why Shouldn't Everything Be Compiled in One Pass?

A boundary-violating approach:

```bash
javac -d all-classes src/main/java/demo/app/Main.java src/test/java/demo/app/MainTest.java
```

This command **illustrates an anti-pattern**, and is not even a valid command for the demo with generated classes if proper processor/config is omitted. Architectural problems when throwing both main/test into one output:

- Test code can **accidentally appear in the production JAR** if packaging all of `all-classes`.
- Main might inadvertently depend on a class existing only in tests.
- Test libraries get pulled into main's compile graph, masking missing dependency errors.
- Changing a test file can unnecessarily re-trigger main compilation/packaging steps.
- Generated code can lack a clear owner and get rebuilt at the wrong time.
- Security/license/dependency scope verification rules are no longer easy to enforce.

Separating outputs is not just for “clean structure”. It helps **guarantee the production artifact contains the exact intended class scope** and reduces rebuild costs.

### Do Not Turn Generated Files into Handwritten Code

Do not copy `build/generated/sources/main/demo/generated/Greeting.java` into `src/main/java` and commit it, unless the project has an explicit policy that generator output is checked in/frozen to be managed as handwritten code. If both locations have class `demo.generated.Greeting`, the compiler may report duplicate class errors or pick up the wrong version.

A generated file should be treated as **output reproducible from inputs**. For an annotation processor, inputs may be annotations/sources, compiler options, and the processor implementation; for a schema generator, inputs may be schema files, generator version, and config.

## 8. Are Generated Sources Emitted in the Same Pass or by a Separate Task?

Two common forms:

### 8.1. Annotation Processing in the Same javac Pass

```text
javac input Main.java
  -> processor detects @GenerateGreeting
  -> Filer creates Greeting.java
  -> javac processes next round
  -> javac produces Main.class + Greeting.class
```

The example in section 5 uses this form. Generated sources **do not need** to be manually listed as a second source root in that compilation task.

Note carefully:

- When a processor emits sources across multiple rounds, create new files only when actually necessary.
- `Filer` normally prevents writing the same output name twice in one pass; `FilerException` may be thrown if a processor attempts duplicate creation.
- Do not pass `-proc:only` when expecting the compiler to produce `Main.class` and `Greeting.class` in the same pass; `-proc:only` only processes annotations without emitting class files from sources.
- Specifying the processor explicitly helps avoid auto-discovery behavior changes across JDKs.

### 8.2. Code Generator Running as a Separate Task

```text
schema.yaml / API definition
         |
         v
  generateJavaSources
         |
         v
 build/generated/schema/java/*.java
         |
         v
     compileJava
         |
         v
 build/classes/java/main/*.class
```

For example when using OpenAPI generator, Protocol Buffers, or an API generation tool with its own executable, the `generateJavaSources` task must be wired as a dependency of `compileJava`, and the **source output directory** must be an input of the compile task. Do not run the code generator manually once and hope `compileJava` magically knows there are new inputs.

**Avoid creating cycles:** a generator often needs its own API/tool first; avoid making a generator task depend on the output of code that the generator itself will produce if doing so creates a build cycle.

## 9. Distinguishing -s, -d, -cp, -processorpath, and -proc

| javac flag | Data kind | Example | Question to ask |
| --- | --- | --- | --- |
| `-s` | Generated Java source destination | `-s build/generated/sources/main` | “Where does the processor write `.java` files?” |
| `-d` | Class file destination | `-d build/classes/main` | “Where does the compiler put `.class` files?” |
| `-cp` / `--class-path` | Input libraries/classes for compilation | `-cp build/processor` | “Which types do the sources being compiled need to see?” |
| `-processorpath` | Where to find annotation processors | `-processorpath build/processor` | “Which processor implementation does the compiler run?” |
| `-processor` | Explicit processor selection | `-processor demo.processor.GreetingProcessor` | “Which processor is executed?” |
| `-proc:only` | Only perform annotation processing | `-proc:only` | “Only generate sources/check diagnostics without emitting class files?” |
| `-proc:none` | Disable annotation processing | `-proc:none` | “Need to exclude processors when isolating an issue?” |
| `--release` | Target Java platform | `--release 17` | “Which target bytecode/API version is expected?” |

A very common mistake is “putting generated sources into `-d`”: `-d` is not the generated Java directory name. Another mistake is running `-proc:only` for main and then wondering why `Main.class` is missing. They are two different output kinds, hence two distinct paths are needed.

### Quick Command to Inspect Generated Classes

After building:

```bash
javap -classpath build/classes/main demo.generated.Greeting
javap -classpath build/classes/main demo.app.Main
javap -classpath build/classes/test demo.app.MainTest
```

These commands use `javap` to confirm the classes exist in the proper outputs. `javap` prints class/method signatures depending on the JDK; we only care whether the class is found, without requiring identical output formatting to a specific version.

## 10. How Gradle Organizes Main, Test, and Generated Sources

With the **Gradle Java plugin**, the two default source sets are **`main`** and **`test`**.

Conventional structure:

```text
src/main/java                -> main sources
src/main/resources           -> main resources
src/test/java                -> test sources
src/test/resources           -> test resources
build/classes/java/main      -> main Java classes
build/classes/java/test      -> test Java classes
build/generated/sources/annotationProcessor/java/main
build/generated/sources/annotationProcessor/java/test
```

The generated path above is the **default convention of Gradle JavaCompile for the Java source set** in the corresponding documented versions, and can be reconfigured via `CompileOptions.generatedSourceOutputDirectory`. Do not hardcode that path into every script and assume it applies to custom plugins.

### Default Tasks

| Gradle task | Role |
| --- | --- |
| `compileJava` | Compiles `main`, including annotation processing configured for main |
| `processResources` | Processes main resources |
| `classes` | Aggregates preparation of main classes/resources |
| `compileTestJava` | Compiles test sources based on main output and test dependencies |
| `processTestResources` | Prepares test resources |
| `testClasses` | Aggregates test class/resource outputs |
| `test` | Runs tests via the configured test framework |
| `jar` | Packages main output into a JAR |
| `build` | Combines assemble/check according to the Gradle lifecycle |

`compileTestJava` depends on `main` output; it does not run beforehand. `jar` by default relies on the main source set output, **without pulling test classes into the production JAR**. Only when you customize artifact configuration yourself (e.g., fat/uber jar or custom packaging) do you need to verify different contents.

### Simple Gradle Kotlin DSL

A minimal `build.gradle.kts` (with Gradle/JDK supporting Java toolchains):

```kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
    options.encoding = "UTF-8"
}
```

This snippet mainly shows **toolchain and target release** applied to `JavaCompile` tasks. It **does not automatically add processors, test frameworks, or generators** since those dependencies depend on the project. If using `java-library`, `application`, or another codegen plugin, check the source set/task configuration contributed by that plugin.

Use `./gradlew compileJava`, `./gradlew compileTestJava`, `./gradlew test`, or `./gradlew build` depending on your environment; on Windows there is also the `gradlew.bat` wrapper. Do not invoke `javac` manually on top of a properly configured Gradle build if that causes two output systems to compete with each other.

### Configuring Dependencies for Processors Distinct from Main Runtime

Suppose a multi-project Gradle build has two separate subprojects providing the annotation API and processor implementation, such as `:annotation-api` and `:greeting-processor`. In the application project, the `dependencies` block can be written as:

```kotlin
dependencies {
    compileOnly(project(":annotation-api"))
    annotationProcessor(project(":greeting-processor"))

    testCompileOnly(project(":annotation-api"))
    testAnnotationProcessor(project(":greeting-processor"))
}
```

This is an **illustration for a multi-project build that already has two valid subprojects**, not a complete runnable build without defining `settings.gradle.kts`, processor code, and proper dependencies. The two path groups are distinct:

- `compileOnly` lets main sources import the annotation API without automatically placing the dependency on the production runtime.
- `annotationProcessor` supplies the processor for the **main compile task**.
- `testCompileOnly` and `testAnnotationProcessor` serve test sources when tests also use separate annotations/generators; they are unnecessary if tests only call generated main classes.

In the `javac` demo, `GenerateGreeting` resided in the same artifact as the processor for convenience. In a multi-module Gradle build, separating the annotation API from the processor implementation is better for dependency isolation.

### Do Not Add Generated Annotation Sources to Main sourceDirs a Second Time

If an annotation processor has already generated sources **inside `compileJava` itself**, Gradle/`javac` handles it as annotation processing output. Manually adding the directory `build/generated/sources/annotationProcessor/java/main` as a source root of `main` can cause the generated file to be ingested by the compiler a second time, causing duplicate source errors, incremental tracking difficulties, or unclear task dependencies.

**Rule:** only declare the source directory of an **independent** codegen task when it is input produced **before compileJava**; do not “re-register” a processor's output within the same task as a handwritten source.

### Independent Codegen Tasks and Generated Roots

If there is a dedicated task generating sources from a schema, the right approach is connecting the **producer task** to the **consumer source set** via task output/provider, so Gradle knows the dependency and does not rely on hardcoded locations. Conceptually:

```text
generateApiCode (output: build/generated/api/java)
       |
       v
compileJava (input: src/main/java + output of generateApiCode)
```

Codegen plugins usually provide ways to register generated sources and task dependencies. Do not merely write `java.srcDir("build/generated/api/java")` without creating a dependency on the task producing that directory: Gradle might compile before the generator runs, use stale sources, or emit ambiguous input warnings.

The same applies to generated test sources: wire the output to the **test source set** and `compileTestJava`, rather than accidentally adding it to main.

## 11. Maven Lifecycle: compile, test-compile, and generated-sources

Maven follows the convention:

```text
src/main/java                 -> target/classes
src/test/java                 -> target/test-classes
target/generated-sources/annotations
target/generated-test-sources/test-annotations
```

The Maven Compiler Plugin has two key goals:

- `compiler:compile`: compiles main sources into `target/classes`, bound by default to the `compile` lifecycle phase.
- `compiler:testCompile`: compiles test sources into `target/test-classes`, bound by default to the `test-compile` lifecycle phase.

In the `mvn test` lifecycle, Maven walks through the preceding required phases: preparing/generating main sources, compiling main, processing/generating test sources, compiling tests, and then running tests via an appropriate plugin (e.g., Surefire). **`test-compile` differs from `test`**: one phase produces test classes, the other executes tests.

### Configuring release for Maven

Plugin snippet in `pom.xml`:

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <version>3.16.0</version>
  <configuration>
    <release>17</release>
  </configuration>
</plugin>
```

This is **a snippet inside a POM's `<build><plugins>...`**, not a standalone POM file. It configures the Java 17 target for the compiler plugin; processor and test framework dependencies must be declared separately depending on the project. The plugin version range must fit the Maven/JDK in use; check the corresponding plugin documentation rather than blindly copying version numbers.

The Maven Compiler Plugin has `generatedSourcesDirectory` and `generatedTestSourcesDirectory` options to manage the locations of sources created by annotation processing in the two stages. Default values typically reside at `target/generated-sources/annotations` and `target/generated-test-sources/test-annotations`, respectively.

### Annotation Processors in Maven

The Maven compiler plugin has configurations for processors, processor paths, and annotation processing, yet **exact syntax depends on plugin version** (especially changes in the 4.x plugin line/newer Maven). If the processor is packaged as a separate artifact, ensure:

1. The annotation API is in compile dependencies when main code imports the annotation.
2. The compiler knows which processor is selected and can find its implementation along with its dependencies.
3. Generated source outputs for main and test do not overlap.
4. During a clean build, the processor module is built/resolved before the consuming module.
5. Generated sources are tracked by the compiler plugin itself or generator plugin, without adding duplicate source roots.

Do not confuse `maven-compiler-plugin` with `maven-surefire-plugin`: the compiler plugin produces test class files, while the test plugin executes tests discovered according to configuration.

### Common Commands and Their Meaning

```bash
mvn clean compile
mvn test-compile
mvn test
mvn package
```

- `clean compile`: deletes previous Maven outputs and then compiles main.
- `test-compile`: runs the phases needed to produce test classes, which **does not mean tests have been executed**.
- `test`: executes the test lifecycle.
- `package`: builds the JAR or artifact per packaging, after the relevant test phases.

**Do not guess that Maven and Gradle put generated sources at the same path**. They have different layouts; inspect actual outputs and plugin configuration to know precisely.

## 12. Is an Annotation Processor Only for Main or Also Needed for Test?

If tests only call production APIs already generated in main, such as `MainTest` calling `Main.message()`, you normally do not need to run `GreetingProcessor` again on test sources. `compileTestJava` only needs main output on the classpath.

If **test sources themselves contain annotations requiring codegen**, then test compilation must also have a separate processor path and source output:

```text
main compile:
  src/main/java + processor(main)
    -> generated/main
    -> classes/main

test compile:
  src/test/java + classes/main + processor(test)
    -> generated/test
    -> classes/test
```

Use the proper test annotation processor dependency type (`testAnnotationProcessor` in Gradle or the corresponding testCompile plugin configuration in Maven). Do not stuff generated test classes into main output “so tests can see them”, because test-only code could then enter the production JAR.

### Test Fixtures and Integration Tests

Large projects also have `testFixtures`, `integrationTest`, `functionalTest`, or similar source sets; they are **not** all main sources. Clearly define which direction dependencies point:

```text
main
  |
  +----> unitTest
  |
  +----> integrationTest
             |
             +----> test fixtures (if any)
```

This is an output visibility relationship, not a requirement that every build defines the source sets above. Gradle allows creating custom source sets; Maven can use plugins/frameworks for integration tests. Each set should have clear compile/runtime classpaths and outputs.

## 13. Generated Sources in the JAR: Which Bytecode Belongs to Production?

After building main and test, there are typically:

```text
build/classes/main/demo/app/Main.class
build/classes/main/demo/generated/Greeting.class
build/classes/test/demo/app/MainTest.class
```

Create the production JAR by packaging only `build/classes/main`. Example in the lab directory:

```bash
jar --create --file build/app.jar -C build/classes/main .
```

Run the command:

```bash
jar --list --file build/app.jar
```

to check that the JAR contains `demo/app/Main.class` and `demo/generated/Greeting.class`, yet **does not contain** `demo/app/MainTest.class` or the processor implementation. The `jar` command above requires the **JDK jar tool** and a real `build/classes/main` path; there is no module source probing here.

You can run:

```bash
java -cp build/app.jar demo.app.Main
```

Stdout remains:

```text
Hello from generated source
```

**This is packaging verification**, not a test runner. If the application depends on external runtime JARs, they must additionally be provided on the runtime classpath. The lab example needs no runtime libraries beyond the Java standard library and generated code.

A generated `.java` file may be kept as an artifact for debugging, though normally it is not inside the production runtime JAR unless you intentionally package a source archive or separate classifier.

## 14. Build Order and Incremental Correctness

Build systems optimize via incremental compilation and build caches. They only reproduce reliable results when **every meaningful input is declared**:

- Source files and annotations.
- Dependency graph, compile classpath, and processor path.
- Generator implementation/version and options.
- Schemas/configs/resources read by the generator.
- JDK/toolchain/release/compiler options.
- Output directories and task ownership.
- Environment variables that actually affect generated output, if the build system has a way to declare them.

If a processor reads external files itself without declaring them as inputs, Gradle/Maven or the cache might **not know to re-run** when those files change. Do not fix this by always running `clean` on every build: clean helps isolate issues, yet does not replace proper task input/output design.

### Incremental Annotation Processing

Gradle distinguishes **isolating** and **aggregating** annotation processors:

- **Isolating:** each generated file depends on one or a group of originating elements determined per supported rules; typically enables small-scope rebuilds.
- **Aggregating:** output combines data from multiple annotated elements, so the impact scope can be broader.
- A processor not supporting incremental mechanisms may force the compile task to reprocess/recompile more files.

With `Filer.createSourceFile(...)`, the API allows passing **originating elements** to support tracking. The demo processor used a fixed name and passed no origins to keep the example easy to read; **do not treat it as an optimal processor for Gradle incremental builds**. When releasing a real processor, design how origins are collected, declare the processor kind, and avoid reading untracked external data.

According to Gradle documentation, some processors not complying with the incremental contract trigger full recompilation. Any claim of “incremental compilation succeeded” must be verified through actual logs and build behavior, not just by noting that a source file did not change.

### Stale Generated Code Bugs

Suppose a generator previously produced `OldApi.java`, and after a schema change it only generates `NewApi.java`. If the task does not **clean up old outputs**, `OldApi.java` may remain in the generated directory and get compiled into the artifact. This is why generated directories must belong clearly to a task; do not share a single output directory across multiple producers without a safe deletion/writing strategy.

If a source file's package changes, **old class outputs** can also linger when not cleaned properly; a deployment picking up a stale class is an artifact hygiene bug, not proof that the compiler ignored new code.

## 15. Reproducible Clean Build Checklist

To prove a workflow is valid from a fresh checkout:

1. Delete **only the build output directory of the project being tested** or run `gradlew clean`/`mvn clean` depending on the tool; do not indiscriminately delete other directories.
2. Restore dependencies via the build tool or prepare processor artifacts at the exact versions.
3. Run processor/codegen tasks (if separate); verify generated files are created from real inputs.
4. Compile main. Check that generated sources are picked up by the compiler and classes are emitted in main output.
5. Compile tests with main output/classpath; test output must be separate.
6. Run tests; check exit codes and test reports, rather than looking only at “compilation successful”.
7. Package the production artifact; verify test classes and processor implementations **are not mixed in** unless there is a special requirement.
8. Run the production artifact with real runtime dependencies.
9. Modify a source annotation or schema, rebuild, and verify generated outputs update.
10. Verify incremental behavior: changing a test-only source does not needlessly recompile main; changing main ABI must recompile dependent tests when needed.

### Diagnostic javac Commands

```bash
javac --help
javac -X
java -version
javac -version
```

Several “fails only on another machine” root causes stem from **a different JDK version**, an annotation processor not being activated, a different classpath, or a different build cache. You must record the compiler/toolchain and the full arguments of the actual task.

## 16. Common Errors and How to Resolve Them

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| `package demo.generated does not exist` when compiling main | Processor did not run, wrong processor path, generated wrong package, or invocation omitted `-processor` | Check processor stage and `-s`/`-d` |
| Generated `.java` exists but no `.class` | `-proc:only` was run, generated source failed to compile, or subsequent compile step is missing | Check javac mode and diagnostics |
| Tests cannot see `Main` | Test compile classpath is missing main output | Add `build/classes/main` or appropriate task dependency |
| Main compiles only when JUnit is present | Main accidentally imports test framework | Move code/test utility to test sources, check dependency scope |
| Test classes appear in app.jar | Wrongly packaged entire build directory or test output | Take only main output when packaging |
| Processor implementation is in runtime | Processor unnecessarily declared as `implementation` dependency | Use annotation processor path and appropriate API dependency |
| `FilerException` during code generation | Processor tried to recreate the same file in one compilation or colliding producers | Design unique output names and rounds |
| Generated code does not update when schema changes | Task inputs/outputs under-declared, faulty cache/up-to-date | Declare schema as input and use task output providers |
| Deleting generated file still passes build then fails at runtime | Stale class output remains on classpath | Controlled clean build, inspect actual JAR |
| `NoClassDefFoundError` at runtime | Generated class not packaged or missing runtime dependency | Check class files/JAR and runtime classpath |
| Tests run in IDE but fail to compile in CI | IDE auto-added generated sources/processor, CI not configured | Sync build tool config and test clean CI |
| Two sources share the same fully-qualified class name | Generated source copied into handwritten sources or two generators share output | One owner, one output path |
| Java 17 target not respected | Different toolchain, `--release` not configured | Check compile options for main/test/codegen |
| Annotation processor does not auto-run on newer JDK | Relied on default auto-discovery that changed | Explicitly configure processor path/processor in build |

**Classifying the right phase is the first step when debugging.** A “generated class not found” error during main compilation requires inspecting processor/source output; during test compilation requires inspecting main output/classpath; at runtime requires inspecting the packaged artifact and runtime dependencies.

## 17. Exercises with Answers

### Exercise 1: Ordering Tasks

Given: `compileTestJava`, `compileJava`, `generateApi`, `test`. If `compileJava` needs generated sources from `generateApi`, what is the right logical order?

**Answer:** `generateApi` before `compileJava`; `compileTestJava` depends on main output; `test` runs after test compilation. A build tool may organize the task graph differently for parallelism, yet must preserve those true dependency edges.

### Exercise 2: -s and -d

A processor generates `demo.generated.Greeting.java`; you want to keep sources in `build/generated/sources/main` and classes in `build/classes/main`. Which two options do you use?

**Answer:** `-s build/generated/sources/main` and `-d build/classes/main`. Do not swap the two options.

### Exercise 3: Test Classpath

`MainTest` calls `Main.message()`, yet the compiler reports it cannot find `Main`. Test compilation tried running without main output. What needs fixing?

**Answer:** Compile main first and add main output to the **test compile classpath**, while keeping test `-d` separate.

### Exercise 4: Processor Path and Compile Classpath

Main code imports `@GenerateGreeting`, while the processor implementation is only used during build. Can you omit the annotation API from the compile classpath and only pass `-processorpath`?

**Answer:** Not in this demo. Main code still must see `GenerateGreeting` as a type in order to compile; the processor path serves the compiler when loading the processor and does not replace the compile classpath.

### Exercise 5: Generated Java in the Production JAR

A generated source `Greeting.java` is compiled into `Greeting.class` belonging to main. Does the production JAR necessarily contain `Greeting.java`?

**Answer:** No. Application JARs usually package main's compiled classes/resources; the generated class can go into the JAR, whereas the Java source usually does not.

### Exercise 6: -proc:only

A task using `-proc:only` created `Greeting.java` yet `Main.class` is missing. Is the generator broken?

**Answer:** Not necessarily. `-proc:only` actively prevents emitting class files; if you want classes compiled, remove the option or create a separate compile step for generated sources.

### Exercise 7: Editing Only Test Code

Modify `MainTest.java` while leaving main/codegen inputs unchanged. Ideally, which tasks must re-run?

**Answer:** Primarily `compileTestJava` and `test`; main codegen/main compile do not need to re-run if the input/output graph and caching are accurate. This is not a guarantee for every custom plugin.

### Exercise 8: Stale Retained Generated File

After renaming an annotation from one type to another, the old generated file remains and keeps getting packaged. Is editing only Java source in `src/main` enough?

**Answer:** No. Check the generator task, directory ownership, deletion policy, build cache/incremental inputs, and actual packaging; use a clean build to pinpoint the cause, then fix the long-term configuration.

### Exercise 9: JUnit Library Present in the JAR

If `jar --list` unexpectedly shows all test classes and test libraries inside the production artifact, which parts need inspection?

**Answer:** Packaging/fat JAR configuration and source set outputs, along with dependency scopes. Do not manually “delete classes after packaging” as the primary fix.

## 18. Conclusion and References

**Separating main code, test code, and generated sources means separating three build contracts**, not just separating three directories:

- **Main** produces code that actually runs; classpaths and artifacts match production needs.
- **Test** consumes main output and testing dependencies, compiled/executed in a separate stage.
- **Generated** is the output of a producer; it must have clear task ownership, output directory, dependency graph, and regeneration mechanism. Main generated classes may belong to production, yet generated sources do not automatically become test or main unless properly wired into a compile task.

The `javac` example proves a single build can have **processor compilation → main compile/code generation → test compile → test run → production packaging**, each stage verifiable without mixing outputs.
