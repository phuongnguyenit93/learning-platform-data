# Isolating Untrusted Sources, File Permissions, and Process Resources During Java Compilation

## 1. Why Is This a Compilation System Problem?

Java grading services, online editors, code analysis systems, or tools accepting user-submitted repositories all have to handle **untrusted source code**. Work may include extracting sources, running `javac`, executing annotation processors, loading classes, and running programs for testing. These steps carry different risk levels yet all require permission and resource controls.

A submitted program can intentionally or accidentally:

- Consume CPU via loops, complex generic/type graphs, or spawning large numbers of threads.
- Allocate excessive RAM, native memory, and buffers, causing the JVM or host to run out of memory.
- Write gigabytes of logs or create countless temporary files, exhausting inodes or disk space.
- Read internal files, credentials, or other submissions' source; connect over the network to exfiltrate data.
- Spawn child processes that survive after the parent process is terminated.
- Inject `../` paths, symlinks, or malformed ZIP entries to escape the submission directory.
- Supply annotation processors, plugins, or build scripts capable of **running code during compilation**.

**Successful compilation does not prove code is safe.** The compiler checks validity according to language and configuration, not as a certifier of runtime behavior. Conversely, simply not having called `main()` yet does not mean compilation operations execute no code.

The goal of this lesson is to design the **security boundary of a compile/run worker**, with least-privilege file permissions, resource quotas, process management, and accurate failure statuses.

## 2. Trust Boundary Model

```text
 Client / Upload source / ZIP (UNTRUSTED)
                     |
                     v
       Trusted control plane
       - admission limits, validation
       - create isolated workspace
       - select JDK, classpath, compiler flags
       - manage time and resources
                     |
                     v
         Isolated compile worker
           javac / compiler API
                     |
                     v
          Isolated run worker
              java / tests
                     |
                     v
          Bounded result collector
                     |
                     v
        Cleanup worker + workspace
```

The **control plane** decides policies, allocates quotas, and monitors jobs. The **execution plane** consists of processes directly handling submitted sources and bytecode. The execution plane needs fewer privileges and only sees data required for the job.

| Subject | Trust level | Appropriate policy |
|---|---|---|
| Source, filenames, ZIP entries | Untrusted | Limit sizes and counts, validate paths |
| Compiler/JDK and flags | System-selected | Do not accept arbitrary user strings |
| User-uploaded dependencies/JARs | Untrusted | Allowlist or strongly isolated worker |
| Annotation processors/plugins | Can execute code during compile | Disable if unneeded; do not load in server JVM |
| Generated bytecode | Untrusted | Run only inside a sandbox |
| Test harness and expected output | More trusted than submission code | Read-only and isolated from user code |
| Server secrets, tokens, home dir | Sensitive | Do not grant to workers |
| Stdout/stderr, output artifacts | Untrusted | Cap sizes and escape when displaying |

An architecture with two separate compile and run workers is useful when granting distinct permissions: the compiler needs to read source and write classes; the runner only needs to read classes/test inputs and write results in scratch space. You can implement either one sandbox with controlled phases or two separate sandboxes depending on the threat model. For adversarial workloads, prefer a **fresh environment per job**, avoiding shared memory or filesystems across tenants.

## 3. Why Not Use the Server's Own JVM as a Sandbox?

Suppose a Spring Boot API invokes `ToolProvider.getSystemJavaCompiler()` directly inside the same JVM. Even before running the submitted class, several dangerous situations can happen:

1. The compiler consumes the server's CPU/RAM and can destabilize the service.
2. The compiler holds the filesystem/network privileges of the server process.
3. Configured annotation processors or compiler plugins can execute code during compilation.
4. If classes are later loaded via reflection, `URLClassLoader`, or JShell, submitted code runs in a JVM with server privileges.

`ClassLoader` manages namespaces/class loading and does **not** enforce CPU quotas, RAM limits, OS permissions, or network boundaries. `ThreadGroup` does not create a sandbox either. `try/catch` cannot stop every resource-exhaustion failure.

### 3.1. The Security Manager Has Been Disabled

`SecurityManager` was deprecated for removal in Java 17 (JEP 411), and **permanently disabled in JDK 24** (JEP 486). On JDK 24+, it cannot be enabled to restrict submitted code. Even on older JDKs, this mechanism never provided absolute protection against runtime bugs, native code, or all attack channels.

The modern model places isolation **outside the JVM** using OS process identities, container namespaces/cgroups, policies, and VMs/microVMs when needed. The Oracle Java Security Guide also directs toward mechanisms outside the JDK for such scenarios.

**A separate process alone is not enough:** If the child still runs under the same OS account, same home directory, same network, and can read server secrets, the child retains equivalent access to those resources. Separate processes must be combined with **least privilege** and hard quotas at the OS/container/VM level.

## 4. Separating Compile and Run

| Control item | Compile phase | Run phase |
|---|---|---|
| Allowed executable to launch | Trusted `javac` / compiler | Trusted `java` / test runner |
| Input | Checked `.java` files, permitted dependencies | Built classes and test inputs |
| Output | `.class`, generated sources, diagnostics | Stdout, stderr, test results |
| Annotation processors | Disabled if unneeded or explicitly allowlisted | Not triggered unless running another compilation |
| Write permissions | Only the compile job's output/scratch | Only the runtime job's scratch/logs |
| Read permissions | Permitted sources and dependencies | Permitted classes and test cases |
| Network | None by default | None by default |
| Quota | Dedicated CPU, RAM, disk, timeout | Dedicated CPU, RAM, PIDs, timeout, output |

The compile worker can also be attacked via complex inputs, compiler bugs, build scripts, or annotation processors; therefore it still needs isolation. The runtime worker must additionally handle infinite loops, sockets, forks, file reads, and native access.

Do not execute submitted code when the requirement only asks to check compiler errors. Even when execution is requested, admission checks and a privilege-restricted worker are mandatory.

## 5. Restricting Annotation Processors and Build Scripts

An annotation processor is Java code running **during compilation**, not a passive syntax check. If a user's JAR is placed on the processor path, the processor can read/write with the `javac` process privileges. Processor discovery depends on JDK version and configuration; never rely on implicit defaults to protect the system.

For exercises that do not require code generation, on JDK 17 you can use:

```bash
javac -proc:none -d classes src/Main.java
```

`-proc:none` disables `javac` annotation processing. However:

- This flag **does not create a sandbox**; `javac` must still run inside a quota-enforced worker.
- Some code genuinely needs Lombok, MapStruct, or another processor to compile; if permitted by the assignment, enforce an approved-processor policy and an isolated worker.
- If users supply Gradle/Maven scripts or compiler plugins, the build can execute arbitrary logic. Treat **running build scripts as executing untrusted code**.
- Flags such as `-processorpath`, `-Xplugin`, `-d`, `-s`, `-J...`, and classpath/module-path must be controlled by the server; do not let users freely configure them.

A service grading only `.java` files is generally safer and easier to reproduce when the server itself generates the compile command with pre-installed JDK and allowlisted libraries. A service building entire repositories from the internet requires a stricter threat model.

## 6. Workspace Design and Least-Privilege File Permissions

Example **logical** structure of a job:

```text
sandbox/jobs/<random-job-id>/
├── input/        # validated files, read-only inside worker
├── deps/         # allowlisted dependencies, read-only
├── classes/      # class output with quota
├── scratch/      # temporary files with quota
├── logs/         # bounded stdout/stderr
└── result.json   # result validated before returning
```

The name `<random-job-id>` illustrates a server-generated identifier; never concatenate usernames or user-supplied names directly into host directory paths.

Principles:

1. **Each job has its own filesystem**; avoid letting two tenants write to the same directory.
2. **Read-only input**; output/scratch are the only writable locations granted to the worker.
3. Do not mount host `/home`, backend source code, SSH keys, cloud credentials, metadata endpoints, or container runtime sockets into the worker.
4. Run the worker under an **unprivileged OS identity**; do not use root/administrator unless strictly necessary.
5. Enforce **disk quotas and inode/file-count limits**, not just upload byte limits.
6. Control read access to downloadable artifacts by job/tenant identity; never let users supply an arbitrary absolute path.
7. Clean up even on timeout, crash, cancellation, or node disconnection.

On POSIX, a private directory with permissions equivalent to `0700` and sensitive files equivalent to `0600` are a starting point. On Windows, use appropriate NTFS ACLs and process tokens; `PosixFilePermissions` does not work on all filesystems.

`Files.createTempDirectory` helps generate a unique name, yet **does not by itself guarantee** OS permissions, ACLs, symlink safety, quotas, and isolation. These requirements must be verified in the actual environment.

## 7. Paths from Uploads: Traversal, ZIP Bombs, and Symbolic Links

A ZIP archive may contain:

```text
src/Main.java
../../config/secrets.yml
/absolute/path.txt
link-to-outside/escape.java
```

Never apply entry names directly to filesystem paths:

```java
// Anti-pattern: illustrative fragment, do not use for extraction.
Path destination = workspace.resolve(userSuppliedEntryName);
Files.copy(uploadStream, destination);
```

Sequences like `../` can escape root. Absolute paths can point elsewhere. Symlinks can reside **inside** the workspace while pointing outside.

### 7.1. Java 17: Example of Lexical Path Validation

**Standalone file `PathBoundaryDemo.java`:**

```java
import java.nio.file.Path;

public class PathBoundaryDemo {
    static Path lexicalDestination(Path root, String input) {
        Path candidate = root.resolve(input).normalize();
        if (!candidate.startsWith(root) || candidate.equals(root)) {
            throw new IllegalArgumentException("Outside workspace");
        }
        return candidate;
    }

    public static void main(String[] args) {
        Path root = Path.of("job-space").toAbsolutePath().normalize();

        System.out.println(
                lexicalDestination(root, "src/Main.java").startsWith(root));

        try {
            lexicalDestination(root, "../secret.txt");
            System.out.println("unexpected");
        } catch (IllegalArgumentException expected) {
            System.out.println("traversal rejected");
        }
    }
}
```

Run:

```bash
javac PathBoundaryDemo.java
java PathBoundaryDemo
```

**Stdout:**

```text
true
traversal rejected
```

The example only **computes paths and writes no files**. `normalize()` and `startsWith()` only check paths lexically; they are **insufficient against symlinks or TOCTOU**. For example, `root/link/file.java` can escape root if `link` is a symlink pointing outside. In an environment where another actor concurrently modifies the filesystem, checking a path before opening a file later also has a race condition.

### 7.2. Rules for Handling Archives

- Limit uploaded file size, total **uncompressed** size, entry count, directory depth, name length, and total file count to mitigate ZIP bombs.
- Reject absolute entries, `..`, invalid files, unneeded symlinks/hardlinks, duplicate names after normalization, and overly long paths.
- Allow only file types required by the task; do not trust client-declared extensions or MIME types.
- Do not follow symlinks during file creation or cleanup; if operating in a directory with concurrent adversaries, use suitable safe primitives such as handle-relative/no-follow or `SecureDirectoryStream` when supported by the filesystem.
- Separate the worker filesystem from host secrets and allow writes only within a dedicated mount; this acts as a second line of defense if validation has a bug.
- Never overwrite existing files created by another job. Create a clean, separate workspace and verify ownership before writing.

`Path.normalize().startsWith(root)` is a first step to eliminate common traversals, not the **sole security boundary**.

## 8. Essential Quotas: CPU, RAM, Time, PIDs, Disk, and Output

| Resource | Exhaustion example | Measure |
|---|---|---|
| CPU | Busy loop; complex generic compilation | cgroup/VM/OS CPU quota |
| Wall-clock | `sleep()`, deadlock, waiting for input | Deadline enforced by an external supervisor |
| RAM | Object allocation, compiler heap, native memory | Container/VM memory limit |
| Threads/PIDs | Spawning many threads, forking child processes | Group-wide PID/task quota |
| Disk | Writing files indefinitely or huge class outputs | Scratch volume quota / size cap |
| File count/inodes | Creating millions of small files | Inode/file-count limits |
| Stdout/stderr | Printing endlessly | Byte cap and cancel/discard policy |
| File descriptors | Opening many files/sockets | OS resource limit |
| Network | Exfiltration, internal scanning | Disabled or deny-by-default policy |
| Concurrency | Thousands of jobs running simultaneously | Admission control, per-tenant quotas |

**`-Xmx256m` is not a hard RAM limit for the whole job**. It only bounds the Java heap of one JVM; native allocations, threads, metaspace, direct buffers, child processes, and the compiler can consume extra RAM. Likewise, `-XX:ActiveProcessorCount=1` is not a hard CPU quota. JVM flags can supplement, but do not replace, OS/container limits.

**Wall-clock timeout differs from CPU quota:** a task sleeping for an hour uses little CPU yet must be terminated past its deadline; a task spawning many threads can saturate CPU well before the deadline. **Both** are needed, along with system concurrency limits.

## 9. ProcessBuilder: Lifecycle Management, Not a Sandbox

`ProcessBuilder` lets you launch a child process with an **argv list**. This avoids shell expansion when not going through `sh -c`/`cmd /c`, yet the new process still inherits the launching OS user's privileges unless sandboxed externally.

### 9.1. Complete Java 17 Example with a Trusted Child

The following example runs only a **fixed** child class that we define. It demonstrates timeouts, exit codes, log redirection, and cleanup. **Do not replace Child with code submitted from the internet on the host.**

**File `ProcessLifecycleDemo.java`:**

```java
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.concurrent.TimeUnit;

public class ProcessLifecycleDemo {
    public static final class Child {
        public static void main(String[] args) {
            System.out.println("child-ok");
        }
    }

    public static void main(String[] args) throws Exception {
        boolean windows = System.getProperty("os.name")
                .toLowerCase().contains("win");
        Path javaBin = Path.of(
                System.getProperty("java.home"),
                "bin",
                windows ? "java.exe" : "java");

        Path log = Files.createTempFile("child-log-", ".txt");
        try {
            ProcessBuilder pb = new ProcessBuilder(
                    javaBin.toString(),
                    "-cp",
                    System.getProperty("java.class.path"),
                    Child.class.getName());
            pb.redirectErrorStream(true);
            pb.redirectOutput(log.toFile());

            Process child = pb.start();
            boolean finished = child.waitFor(3, TimeUnit.SECONDS);
            if (!finished) {
                child.destroyForcibly();
                child.waitFor();
                throw new IllegalStateException("Timed out");
            }
            if (child.exitValue() != 0) {
                throw new IllegalStateException(
                        "Failed with exit " + child.exitValue());
            }
            System.out.println("finished: " + finished);
            System.out.println("output: " + Files.readString(log).strip());
        } finally {
            Files.deleteIfExists(log);
        }
    }
}
```

Run with JDK 17+:

```bash
javac ProcessLifecycleDemo.java
java ProcessLifecycleDemo
```

**Expected stdout:**

```text
finished: true
output: child-ok
```

Explanation:

- `java.home/bin/java` selects the executable from the active JVM rather than relying on PATH.
- `ProcessBuilder` does not invoke a shell; each argument is passed separately.
- `redirectErrorStream(true)` merges stderr into stdout, and `redirectOutput(log.toFile())` avoids blocking due to an unread pipe in this small example.
- `waitFor(timeout, TimeUnit.SECONDS)` applies a wall-clock deadline to the child process.
- `destroyForcibly()` requests termination of the child when timed out, then `waitFor()` waits for completion before cleaning up the log.
- The exit code is only accessed after the child has stopped.
- `finally` cleans up the log file if the parent reaches this block.

**Limitations to understand:** The log in this example has no size cap; if the child prints continuously, the file can grow huge before timeout. `destroyForcibly()` also **does not guarantee** that all descendant processes of the child are terminated. This example is suitable for learning Java process lifecycles on **trusted code**, not yet a safe runner for untrusted code.

### 9.2. What Must Be Added in Production?

1. Spawn children inside a worker with restricted OS identity, filesystem, network, and quotas.
2. Manage the entire **process group/cgroup/container/Windows Job Object**, terminating all descendants on timeout.
3. Cap output bytes at the collector or filesystem quota, not just by truncating an HTTP response string.
4. Collect logs under limits, distinguishing compiler stderr from child output when needed.
5. Associate each process with an internal job ID; never trust user-supplied process names or PIDs.
6. Clean up when the parent disconnects/crashes; you cannot rely solely on `finally` inside a killed process.

`ProcessHandle.descendants()` lets you inspect descendants, yet the process tree changes continuously; merely scanning and killing one by one has race conditions. A supervisor owning the entire process group is far more reliable.

## 10. Deadlocks and Memory Overflow from stdout/stderr

With `ProcessBuilder`, stdout and stderr default to **pipes**. If the child prints heavily while the parent calls `waitFor()` without draining them, the pipe can fill up. The child blocks on write while the parent waits for the child: deadlock.

Strategies include:

- **Redirect logs to a quota-limited file:** easy to inspect, but requires byte caps and ACLs.
- **Concurrently drain both streams:** the reader/collector must apply a byte cap, either continuing to read and discarding the excess or terminating the worker. Simply stopping reads when the buffer is full can block the child.
- **Merge stderr/stdout:** simpler single-stream collection, though it loses separation between the two channels; use when separation is unnecessary.
- **Bounded streaming:** forward chunks through a bounded queue; requires backpressure and cancellation.

Never buffer all output into an unbounded `ByteArrayOutputStream` or `StringBuilder`. Also never just return the first 16 KiB in the response while letting the child write to disk unboundedly.

**Stdout/stderr is untrusted data**: it may contain HTML/JS, terminal control characters, forged result JSON, or huge strings. The UI must escape contextually, the server must limit sizes, and a `PASS` string printed by submitted code must never be treated as the test verdict.

## 11. Container/VM Isolation: Defense Layers

The container runtime or VM must be configured to enforce the job's security policy:

| Layer | What to enforce |
|---|---|
| User identity | Unprivileged, dedicated UID/GID or appropriate user namespace |
| Root filesystem | Read-only if possible, mount only required input/deps |
| Scratch/output | Dedicated writable volume, byte/inode quotas |
| Network | Disabled or strictly necessary allowlist |
| CPU/RAM/PIDs | Hard limits, not just JVM flags |
| Capabilities | Drop unnecessary capabilities, no-new-privileges |
| Syscalls | Platform-appropriate Seccomp/AppArmor/SELinux |
| Lifecycle | Fresh job environment, teardown entire worker/process group |
| Tenant separation | No shared workspace/secrets/sockets |

**Containers do not automatically mean total safety.** Privileged containers, mounting the Docker socket, host networking, host paths holding secrets, or broad kernel capabilities drastically weaken isolation. For strongly adversarial code, consider VMs/microVMs to reduce reliance on a shared kernel.

### 11.1. Logical-Level Policy Example

```yaml
# This is an illustrative policy, NOT a complete Kubernetes/Docker manifest.
submission:
  maxFiles: 20
  maxSourceBytes: 100000
  maxUncompressedBytes: 500000

compile:
  wallClockSeconds: 15
  memoryMiB: 512
  cpuCoresQuota: 1
  maxLogBytes: 65536

run:
  wallClockSeconds: 3
  memoryMiB: 256
  maxProcesses: 32
  maxLogBytes: 16384
  network: disabled
```

The numbers are illustrative only, not universal recommendations for every product. Complex tasks, large source counts, or allowed annotation processing may require different quotas. What matters is that the worker/supervisor **enforces** those limits and reports a status when they are exceeded.

A policy written only in YAML without the runtime configuring corresponding cgroups/network namespaces/volume quotas provides no real security.

## 12. Avoiding Command Injection and Dangerous Compiler Options

**Never concatenate user input directly into a shell command:**

```java
// Anti-pattern, illustrative only: the shell will parse the input syntax.
new ProcessBuilder(
        "sh", "-c", "javac " + userFlags + " " + submittedFile
).start();
```

Spaces, shell metacharacters, command substitution, and unexpected paths can alter command meaning. Instead, use `ProcessBuilder(List<String>)` or the varargs constructor, with **server-decided flags** and validated filenames.

However, passing separate arguments **does not automatically make user-supplied compiler flags safe**: a valid compiler flag can request loading a plugin or annotation processor, changing the output folder, altering JVM options, or reading unintended files. Therefore:

- Select a fixed set of `javac` options; `--release` and classpath must come from policy.
- Do not let users directly control `-processorpath`, `-Xplugin`, `-J...`, `-d`, and `-s`.
- Do not allow arbitrary submitted filenames to cause option injection; use controlled paths and ensure arguments are treated as paths.
- Do not let users control `CLASSPATH`, `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS`, or environment variables that can affect the compiler/runtime.
- If running a user's Gradle/Maven project is mandatory, treat build scripts and plugins as untrusted code; the compile worker requires isolation equivalent to the runtime worker.

A shared read-only dependency cache is usually preferable to letting workers download arbitrary libraries from the internet. If network access must be opened to fetch dependencies, use a controlled proxy rather than granting internal network access.

## 13. Classifying Outcomes: Avoid Mistaking Environment Errors for Source Errors

A non-zero exit code from `javac` does **not automatically** mean the Java source is wrong. The JDK might not be installed, the executable might be blocked, the worker might have been OOM-killed, timed out, missed a dependency, or hit an I/O error.

Return meaningful statuses:

| Status | Meaning |
|---|---|
| `COMPILE_OK` | Compiler ran and accepted the source |
| `COMPILE_ERROR` | Compiler ran properly and rejected the source with error diagnostics |
| `RUNTIME_FAILED` | Program/tests ran, yet results or exit code failed |
| `TIMEOUT` | Worker exceeded the allowed time |
| `RESOURCE_LIMIT` | CPU/RAM/PIDs/disk/output quota was exceeded |
| `INPUT_REJECTED` | Source/archive/path violated admission policy |
| `INFRA_ERROR` | Compiler not found, container failure, wrong mount/config |
| `CANCELLED` | User or administrator cancelled the job |

Example **illustrative application schema**, not JSON printed by `javac`:

```json
{
  "jobId": "opaque-job-id",
  "phase": "COMPILE",
  "status": "COMPILE_ERROR",
  "exitCode": 1,
  "timedOut": false,
  "quota": null,
  "diagnostics": [
    { "kind": "ERROR", "file": "Main.java", "line": 3 }
  ],
  "stdoutTruncated": false,
  "stderrTruncated": false
}
```

If using the `JavaCompiler` API to collect `Diagnostic.Kind.ERROR`, still run the compiler in an isolated worker for untrusted sources. `Diagnostic.getMessage()` and stdout/stderr should only serve as diagnostic info; do not depend on exact wording or trust self-reported results from submitted code.

For negative compilation tests, verify that the compiler **actually launched and received the right fixture**. A "command not found" error must not count as a pass for a test expecting the compiler to reject source code.

## 14. Durable Cleanup and Full Lifecycle Management

```text
ACCEPTED
  |
  v
VALIDATING --------> INPUT_REJECTED ------> CLEANUP
  |
  v
PROVISIONING ------> INFRA_ERROR ---------> CLEANUP
  |
  v
COMPILING
  |-- bad source ---> COMPILE_ERROR ------> CLEANUP
  |-- timeout/limit -> TERMINATE_GROUP ---> CLEANUP
  v
RUNNING (if requested)
  |-- test failure -> RUNTIME_FAILED -----> CLEANUP
  |-- timeout/limit -> TERMINATE_GROUP ---> CLEANUP
  v
COLLECTING (bounded)
  |
  v
FINISHED ------------> CLEANUP
```

`try/finally` inside a worker only runs while the JVM/flow still has a chance to execute; if the process receives SIGKILL, loses power, or the node dies, `finally` is not guaranteed to clean up. Therefore, an **external control plane outside the worker** must own the lifecycle: job lease/TTL, orphan detection, and cleanup/reaper.

Sound management sequence:

1. Record job identity and quota configuration before provisioning a worker.
2. Initialize the worker with mounts, user, network, and resource policy.
3. Execute compile/run; monitor deadlines/quotas and terminate the **entire group** when needed.
4. Collect bounded results, exit status, kill/OOM reasons, logs, and metrics.
5. Validate the result schema; prevent a worker from altering another job's results.
6. Delete the worker, scratch space, mounts, and temporary grants; if cleanup fails, mark for controlled retry.

Keep secrets/test harnesses outside the submission's writable area. When serving downloadable artifacts, identify them by job and tenant permissions, never exposing an API accepting arbitrary absolute filesystem paths.

## 15. Testing Sandbox Safety

Fixtures with resource-exhausting behavior should be tested **inside an already isolated, quota-enforced environment**, not on a developer machine or production server.

| Scenario | What must be proven |
|---|---|
| ZIP containing `../escape.java` | Does not write outside workspace |
| ZIP with an external symlink | Does not follow link to host files |
| Very large upload / many entries | Blocked by admission limits or quotas |
| Infinite-loop program | Timeout/CPU budget enforced, job terminated |
| Program printing stdout nonstop | Byte cap and disk quota hold |
| Spawning many child processes | PID quota applies to descendants; group torn down |
| Attempt to read host config files | Denied by OS permissions/mount isolation |
| Attempt to reach internal network | Denied by network policy |
| Disallowed processor | Not discovered/executed inside compiler |
| Worker crashes during compile | Supervisor reaps orphans and reports INFRA_ERROR |
| Two tenants running concurrently | Cannot read/write each other's workspace or results |

Metrics to observe include queue/compile/run times, CPU and peak RAM, PID counts, disk bytes, file counts, log bytes, timeout/quota counts, orphan cleanup counts, and infrastructure error rates. Metrics/logs also require access control and should avoid unnecessarily recording source code containing secrets.

## 16. Common Mistakes and How to Fix Them

**"Only compiling, not running `main()`, so it is safe."** The compiler still consumes resources and can load processors/plugins; run compilation in an isolated worker with explicit policies.

**"`URLClassLoader` or JShell is a sandbox."** They create no OS permission boundaries; use worker processes and isolate filesystem/network/resources.

**"Just enable `SecurityManager`."** Permanently disabled in JDK 24; new designs must use mechanisms outside the JVM.

**"`-Xmx` already sets a RAM limit."** Only the Java heap; hard memory quotas at the OS/container layer are required.

**"A timeout is enough."** CPU, PIDs, disk, and memory quotas must still be enforced before the job runs.

**"`destroyForcibly()` kills all children."** Not guaranteed; a process group/container supervisor is needed.

**"Using `normalize().startsWith(root)` makes traversal impossible."** It does not address symlinks/TOCTOU; use filesystem isolation and safe no-follow operations.

**"Truncating logs on HTTP return is enough."** The child can still write indefinitely; enforce an output byte cap.

**"Docker is completely safe by default."** Check identity, privileged mode, mounts, network, resource limits, and security profile; consider VMs when needed.

**"A non-zero exit code means the source is wrong."** Infrastructure errors, quota breaches, and compiler errors must be classified separately.

**"A user-supplied file is just data."** Build scripts, processors, compiler plugins, and bytecode can execute code; evaluate phases and permissions properly.

## 17. Practical Exercises

**Scenario A — Compiler inside Spring Boot.** An API calls `ToolProvider.getSystemJavaCompiler()` directly inside the server JVM to grade uploaded code. A user's annotation processor plugin activates and writes files outside the workspace. What architectural change is needed?

*Hint:* Use a dedicated compile worker with OS identity and filesystem isolation; if the assignment needs no processing, use `-proc:none`; if needed, allowlist only trusted processors. Do not load compilers/user plugins inside the server JVM.

**Scenario B — Path validator.** An application uses `Path.normalize().startsWith(root)` and concludes every path is safe. A submission creates a symbolic link inside root pointing to a secret file. Why is that check insufficient?

*Hint:* Lexical validation does not resolve symlinks or races; use no-follow/handle-relative operations and a worker filesystem containing no secret files.

**Scenario C — Surviving child process.** The parent times out and calls `destroyForcibly()`; afterwards a child process remains alive. What control layer is needed?

*Hint:* An OS process group/cgroup/Job Object/container supervisor owning all descendants, PID quotas, and group-wide teardown.

**Scenario D — Multi-GB output.** The API only returns 16 KiB of stdout, yet the host disk still fills up. Where is the issue?

*Hint:* API truncation is not a log/file quota. Enforce a byte cap at the output collector or filesystem and apply policy when the cap is exceeded.

**Scenario E — False compile error.** `javac` is not found, and the system returns `COMPILE_ERROR`. How should the status be fixed?

*Hint:* This is `INFRA_ERROR`, because the compiler never evaluated the source. A negative compile result is only valid when the compiler runs properly and emits appropriate diagnostics.

**Scenario F — Two tenants.** Jobs A and B share a writable scratch directory. B has a class file altered before testing. Which guarantee was violated?

*Hint:* Cross-tenant artifact integrity. Each job needs an isolated workspace, outputs unwritable by other jobs, and ideally an immutable handoff from compile to run.

## 18. Pre-Deployment Checklist

- [ ] Threat model covers sources, archives, annotation processors, build scripts, compiler, and runtime.
- [ ] Compile untrusted sources inside a worker with OS-level isolation; never use the server JVM.
- [ ] Enforce upload/extraction sizes, file counts, path depth, and filenames.
- [ ] Defend against traversal, symlinks, TOCTOU, and keep host secrets out of the worker filesystem.
- [ ] Read-only input/dependencies; dedicated output/scratch with quotas and least-privilege access.
- [ ] Compiler JDK/flags/classpath are system-controlled; processors are disabled or allowlisted.
- [ ] Unprivileged worker, with network denied by default.
- [ ] CPU, RAM, PIDs, disk/inodes, file descriptors, and log byte caps are enforced.
- [ ] Wall-clock timeout, cancellation, and cleanup cover the entire process tree.
- [ ] Logs are bounded during collection, escaped on display, and never treated as trusted results.
- [ ] Statuses `COMPILE_ERROR`, `TIMEOUT`, `RESOURCE_LIMIT`, and `INFRA_ERROR` are distinguished.
- [ ] Real isolation tests and orphan worker/workspace cleanup workflows exist.
- [ ] Tenant quotas/concurrency limits and metrics help detect overload.
