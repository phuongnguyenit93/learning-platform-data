# Distinguishing Compilation, Packaging, Class Loading, and Execution in Java

These four concepts describe **four different tasks** along the journey from Java source code to program behavior. When encountering an error, you need to determine which task it occurred in: the compiler failed to produce bytecode, the packaging tool missed a file, the JVM could not find/load/link/initialize a class, or the code started running and then failed.

## 1. The Big Picture

~~~text
.java source code
    │
    │ javac: syntax parsing, type checking, bytecode generation
    ▼
.class file
    │
    │ jar: bundles files, resources, and metadata (optional step)
    ▼
classes directory / JAR / module / other class source
    │
    │ ClassLoader + JVM: class loading, linking, initialization when needed
    ▼
Class ready for use
    │
    │ JVM executes bytecode: interpretation and possible JIT optimization
    ▼
Runtime behavior: output, I/O, threads, exceptions, ...
~~~

| Phase | Primary Input | Responsible Component | Output | Example Errors |
| --- | --- | --- | --- | --- |
| **Compilation** | `.java`, classpath/module path for type lookup | `javac` or equivalent compiler | `.class` bytecode | `cannot find symbol`, `incompatible types` |
| **Packaging** | `.class`, resources, manifest, metadata | `jar`, Gradle, Maven, etc. | `.jar` or other artifact type | Missing `Main-Class`, omitted dependency |
| **Class loading** | Class name and available bytecode source | Class loader combined with JVM linking/initialization mechanisms | `Class<?>` definition and class ready for use when needed | `ClassNotFoundException`, `NoClassDefFoundError` |
| **Execution** | Usable class, bytecode, input data | JVM, interpreter, JIT, libraries/runtime | Results and runtime side effects | `NullPointerException`, wrong output, I/O error |

The diagram is a **conceptual flow**, not a mandatory rule that always runs step by step completely. Java can run `.class` files directly in a directory **without creating a JAR**; class loaders can continue loading classes dynamically after `main` has started running; and `java File.java` (source-file mode) performs compilation during startup, which does not mean skipping compilation.

## 2. Compilation: From Source Code to Bytecode

### What Does `javac` Do?

For a typical Java program, the compiler:

1. Reads the source code, parses syntax, declared names, access scope, and type relationships.
2. Checks language rules such as argument types, return types, checked exceptions, availability of methods/fields, and part of generic constraints.
3. Generates `.class` files carrying JVM bytecode, the constant pool, type/method information, and necessary metadata; a single source file can produce multiple `.class` files (for example, nested classes, anonymous classes).

Example:

~~~java
// src/demo/Greeter.java
package demo;

public final class Greeter {
    public static String greet(String name) {
        return "Xin chào, " + name;
    }
}
~~~

~~~bash
mkdir out
javac -encoding UTF-8 -d out src/demo/Greeter.java
javap -classpath out -c demo.Greeter
~~~

After the compilation command, the file `out/demo/Greeter.class` exists. `javap -c` lets you observe the generated bytecode instructions; this is **inspecting the compilation output**, not running the `greet` method yet. The `mkdir out` command only needs to be done once; the target directory of `-d` must exist. All illustrated commands use JDK 17+ tool syntax.

### What Is Decided at Compile Time?

- Whether a variable/method name is recognized, types are compatible, and access is valid according to the information the compiler sees.
- References to classes/methods/fields can be recorded **by symbolic name** in the `.class` constant pool; the compiler does not turn every reference into a final memory address.
- `import` assists name resolution at the source-code level; it **does not instruct the JVM to load a class** and does not automatically put dependencies into a JAR.
- Java generics are largely checked and then undergo **type erasure** during compilation; this differs from the class loader mechanism.

Successful compilation **does not guarantee** that required classes will be present at runtime, does not guarantee that network connections/file reads will succeed, and does not guarantee that the program will not encounter exceptions. The compiler checks information available at build time; runtime also depends on bytecode version, environment, data, and actual dependencies.

### Compile-Time Dependencies vs. Runtime Dependencies

If code calls `lib.Api.run()`, `javac` needs to find a suitable definition of `lib.Api` to check types. At runtime, the JVM must also find the compatible class and method in the runtime environment. Thus, an application can **compile** thanks to library A yet **fail at runtime** if library A is not carried along, is missing transitive dependencies, or is replaced by an incompatible version.

`classpath` is used to find types/class files in a classpath environment; `module path` serves JPMS's module model. These two paths are **different** configurations. The same library can also be configured differently for the compiler and the Java launcher.

## 3. Packaging: Bundling Artifacts, Not Equivalent to Compiling

A JAR is a ZIP format with a conventional structure to hold `.class` files, resources (for example `.properties`), a `META-INF/` directory, and a manifest. The `jar` tool **does not automatically convert `.java` into `.class`**: normally you compile first and then bundle artifacts, even though Gradle/Maven can automatically invoke compilation tasks as dependencies of packaging tasks.

There are three distribution approaches to distinguish:

- **Class directory:** `java -cp out demo.Main`. No JAR, yet the JVM is still needed to load classes and execute.
- **Library JAR:** provides classes/resources for other programs; may not have an entry point. A library does not necessarily run with `java -jar`.
- **Executable JAR:** has entry point information such as `Main-Class: demo.Main` in `META-INF/MANIFEST.MF`; `java -jar app.jar` uses that information to locate the `main` method. The word "executable" does not turn a JAR into a machine file that runs independently of the JVM.

**A JAR does not automatically include dependencies**: a "thin" JAR usually contains only the application's own code/resources. To carry dependencies, an appropriate packaging approach is required (fat/uber JAR, a custom layout like Spring Boot executable JAR, or distributing multiple JARs with a proper classpath). Some packaging tools also transform or merge class contents; one cannot conclude that every packaging process is simply archiving as-is.

Note: when using `java -jar app.jar`, the Java launcher's `-cp` / `-classpath` option is not used as the user classpath for that run. Libraries need to be included in the packaging layout, in a custom loader mechanism, or in an appropriately configured manifest `Class-Path`. Conversely, `java -cp "app.jar;lib/*" demo.Main` on Windows (`:` on Linux/macOS) uses an explicit classpath and main class name, without relying on `Main-Class`.

## 4. Class Loading: Bringing Class Definitions into the JVM When Needed

**Class loading** is not simply "opening a JAR file". The JVM can read bytecode from a class directory, JAR, runtime module, or source supported by a class loader. The JAR is storage; the class loader is responsible for finding/defining classes according to its mechanism.

The lifecycle according to the JVM specification consists of three groups of behaviors, where exact timing may differ across JVMs:

1. **Loading:** finds the binary representation of a class and creates the corresponding `Class` representation in the JVM. The JVM has a bootstrap loader for foundational classes; modern Java JVMs also have platform and application class loaders. Custom class loaders can provide other bytecode sources.
2. **Linking:** includes **verification** (checking bytecode and structural validity), **preparation** (allocating and setting initial default values for static fields), and **resolution** (converting symbolic references into direct references when appropriate). Resolution can be performed lazily on first use, so not every dependency is fully resolved right when the class is loaded.
3. **Initialization:** runs the class's static initialization logic (typically synthesized by the compiler into `<clinit>`) when initialization is required. Common examples: `new` an instance of the class, invoking a static method of the class, accessing/writing a static field that is not a compile-time inlined constant, or the default form `Class.forName(name)`.

**Loading a class ≠ initializing a class**. For instance, `Class.forName(name, false, loader)` requests loading and linking the class without requesting initialization. `Class.forName(name, true, loader)` requests initialization. The JVM may load/link eagerly within implementation permissions, yet must preserve observable initialization behavior according to the specification.

A class is identified by **its binary name together with the class loader that defines it**. Two different loaders can define two classes with the same name that are not the same type inside the JVM; casting between them can fail. The parent-delegation mechanism helps reuse foundational classes and reduce duplication, though custom loaders can have their own rules.

### Separating Class-Loading Errors from Initialization Errors

| Symptom | Typical Timing/Meaning | What to Check |
| --- | --- | --- |
| `ClassNotFoundException` | An API looking up a class by name (such as `Class.forName`) could not find the definition | Fully qualified name, classpath/module path, chosen class loader |
| `NoClassDefFoundError` | The JVM needed a class definition yet could not obtain an available definition at that time; can also relate to a class whose prior initialization failed | Runtime dependencies, JAR name/version, earlier `Caused by` error |
| `UnsupportedClassVersionError` | Bytecode has a higher version than the runtime supports | Compare the JDK used to compile and the actual Java runtime |
| `VerifyError` / `LinkageError` | Invalid bytecode or linking/binary compatibility issue | Corrupted artifact, incompatible library, duplicate classes |
| `ExceptionInInitializerError` | Static initialization threw an unhandled exception | `static` blocks, static field initializers, and root cause |

Do not equate `ClassNotFoundException` (a checked exception from some class-lookup APIs) with `NoClassDefFoundError` (a JVM `Error`). A runtime error can arise **before the expected line of code executes**, because the JVM also has to link/initialize required classes.

## 5. Execution: Running Bytecode and Performing Business Logic

The Java launcher creates the JVM environment, chooses the initial class/program, and invokes the appropriate entry point. For traditional classpath programs, that is usually `public static void main(String[] args)`. During operation, the JVM executes bytecode; a JVM like HotSpot can **interpret** and then **JIT compile** sufficiently "hot" code segments into machine code to improve performance.

**JIT compilation is not `javac`**:

- `javac` runs during the build step, converting **Java source code → bytecode** and creating `.class` files.
- JIT runs inside the JVM while the program is running, potentially converting **bytecode → optimized machine code** based on runtime information; there is no guarantee that a specific method will be JIT-compiled during a short run.
- A program can still execute correctly even without being JIT-compiled. Business results must not depend on whether JIT occurs.

At runtime, I/O, thread creation, object allocation, library calls, database access, exceptions, or logic errors can occur. These phenomena generally cannot be inferred merely from successful compilation/packaging.

## 6. Full-Pipeline Experiment (JDK 17+)

The following example distinguishes **loading/getting class metadata** from **static initialization**, then shows that the same bytecode can run from the `out` directory or from a JAR. Create exactly two source files:

**File `src/demo/Main.java`**

~~~java
package demo;

public final class Main {
    public static void main(String[] args) throws ClassNotFoundException {
        System.out.println("1. main()");

        ClassLoader loader = Main.class.getClassLoader();
        Class<?> type = Class.forName("demo.Marker", false, loader);
        System.out.println("2. loaded: " + type.getSimpleName());

        Class.forName("demo.Marker", true, loader);
        System.out.println("4. initialized");

        Marker.run();
    }
}
~~~

**File `src/demo/Marker.java`**

~~~java
package demo;

public final class Marker {
    static {
        System.out.println("3. Marker.<clinit>");
    }

    public static void run() {
        System.out.println("5. Marker.run()");
    }
}
~~~

### Step A — Compile

~~~bash
mkdir out
javac -encoding UTF-8 -d out src/demo/Main.java src/demo/Marker.java
~~~

The result is `out/demo/Main.class` and `out/demo/Marker.class`. **The program has not been run yet**, so the five `System.out.println` lines have not been printed. If `javac` reports an error, fix the source error before thinking about JARs or class loaders.

### Step B — Run Directly from the Class Directory

~~~bash
java -cp out demo.Main
~~~

**Expected stdout, in exact order:**

~~~text
1. main()
2. loaded: Marker
3. Marker.<clinit>
4. initialized
5. Marker.run()
~~~

Line-by-line explanation:

1. The JVM was able to launch `demo.Main.main`; this is code **executing**.
2. `Class.forName("demo.Marker", false, loader)` returns the `Class` object without requiring `Marker`'s static initializer to run. The word "loaded" is an illustrative label: the class was requested to be loaded and linked, not proof that the entire system only starts loading at this line.
3. Calling `Class.forName(..., true, ...)` requests initializing `Marker`, so the `static` block prints `3. Marker.<clinit>` **before** the call returns.
4. After initialization finishes, `Main` prints `4. initialized`.
5. Calling `Marker.run()` prints the last line. Calling a static method is also a form of active use that can trigger initialization if the class has not been initialized previously.

### Step C — Package and Run Again

~~~bash
jar --create --file app.jar --main-class demo.Main -C out .
jar --list --file app.jar
java -jar app.jar
~~~

The `jar --create` command takes compiled files from `out` and creates `app.jar` with entry point `demo.Main` in the manifest. `jar --list` lets you inspect entries such as `demo/Main.class`, `demo/Marker.class`, and `META-INF/MANIFEST.MF`. The `java -jar app.jar` command produces **the same five stdout lines** as in Step B. The identical output illustrates: **packaging changes how the artifact is distributed/launched, without itself changing Java functionality** in this example.

**Artifact comparison:**

| After Command | Observation to Verify | What Has Not Been Proven |
| --- | --- | --- |
| `javac ...` | `Main.class` and `Marker.class` exist | Has not proven the application runs correctly |
| `jar --create ...` | `app.jar`, classes, and manifest exist | Has not proven all runtime dependencies are sufficient |
| `java -cp out demo.Main` | All five lines are printed | No JAR is required |
| `java -jar app.jar` | All five lines are printed | The JAR still requires a Java runtime to execute |

**Terminal note:** `mkdir out` and the `javac`/`jar`/`java` commands can all be used in PowerShell or Unix shells when run from the root directory containing `src/demo/`. If `out` already exists, skip the `mkdir` step. The OS-specific classpath list separator only matters when using **multiple** directories/JARs; this example uses a single `out`.

## 7. How to Identify Which Phase an Error Belongs To

When investigating, read **the failing command and the actual stack trace**, rather than guessing from the phrase "Java error".

| Symptom | First Check | Nearest Phase |
| --- | --- | --- |
| `javac`: `';' expected`, `cannot find symbol`, `incompatible types` | Syntax, names, types, compiler `-cp` | Compilation |
| Build creates JAR yet `java -jar` reports `no main manifest attribute` | Whether the proper `Main-Class` entry is present | Packaging/entry point configuration |
| `java -jar` cannot find a dependency at runtime | Whether dependencies are bundled/distributed and loader/classpath is configured properly | Class loading/linking |
| `UnsupportedClassVersionError` | Which class-file version the compiler JDK emitted, which version the running JVM supports | Loading/linking |
| `ExceptionInInitializerError` | Static initializer logic and `Caused by` | Class initialization |
| `NullPointerException` inside `main`, wrong computed value, timeout | Call stack, data, code branch, runtime resources | Execution |

**Short diagnostic workflow:**

1. Record the command being run (`javac`, `jar`, `java`, or build task) along with the **first meaningful** error.
2. If it is a compilation error, address `javac`'s message and the compiler's classpath/module path.
3. If a JAR already exists, inspect its contents/manifest with `jar --list --file app.jar`; you can view the manifest with a ZIP tool if needed.
4. If the error occurs when launching or calling a class, check the actual Java runtime with `java -version`, the classpath/module path, and the `Caused by` chain.
5. If the program has already entered business logic, debug the call stack, state, and data; do not blindly change packaging configuration to "fix" every runtime error.

Some errors **do not stay strictly inside an absolute boundary**: for example, a missing library might be detected right at startup or only when an execution path uses that class for the first time; many linking errors only surface at the moment the JVM resolves references.

## 8. Misconceptions to Avoid

- **"Once compilation finishes, it can run."** False: a compatible runtime, appropriate classes/resources, and valid data are required.
- **"Having a JAR means having all dependencies."** False: you need to check the packaging approach and deployment environment.
- **"Loading a class means the static block has already run."** False: loading, linking, and initialization are distinct steps; the `Class.forName` example with `initialize=false` clearly illustrates this.
- **"A JAR is machine code."** False: a typical Java JAR contains bytecode and resources; the JVM executes bytecode, possibly using JIT. A native image is a different kind of artifact, with a different build process.
- **"JIT is the same as javac."** False: they differ in input, timing, purpose, and where they operate.
- **"Without `import`, the JVM cannot find the class."** False: `import` is only a naming rule in source code; runtime relies on class loaders, classpath/module path, binary names, and actual dependencies.
- **"The JVM loads all classes in the JAR before calling main."** False: classes can be loaded, linked, and initialized on demand; exact timing depends on valid requirements and implementation.

## 9. Self-Check

1. **Can you run a Java program without packaging a JAR?** Yes. If `out` contains the appropriate classes and dependencies are available, use `java -cp out demo.Main`.
2. **Does creating a JAR automatically fix `cannot find symbol`?** No. That is a compilation error; you need to fix the source/dependency configuration for the compiler.
3. **Why does `Class.forName(name, false, loader)` not print the line inside the `static` block?** Because requesting load/link does not mean requesting initialization.
4. **If an application compiles successfully yet fails at runtime with `NoClassDefFoundError`, where do you look?** Check the class/dependencies at runtime, class loader, artifact version, and root cause; do not conclude the source code has a syntax error.
5. **Can the same JAR behave differently between two environments?** Yes: different JVM, dependency configuration, system properties, environment variables, resources, data, OS, permissions, and runtime conditions.
6. **When does JIT run?** Decided by the JVM based on optimization policy and operates at runtime; not a mandatory condition for code to run correctly.

**One-sentence takeaway:** `javac` **creates bytecode**; `jar` **packages artifacts**; the class loader together with the JVM **defines, links, and initializes classes when needed**; the JVM **executes bytecode** to produce observable behavior.
