# Selecting Processors with -processor and Configuring Processor Lookup Paths in javac

Annotation processing in Java is the mechanism for **processing annotations at compile time** under the `javax.annotation.processing` API (JSR 269). Processors can inspect declarations, emit diagnostics, and generate source files or resources. Notably, **having an annotation in source does not mean a corresponding processor runs automatically**. The `javac` compiler must be configured to **locate the processor implementation**, **select which processor to use**, and **enable processing** appropriately for the JDK.

This lesson focuses on two frequently confused decisions: **`-processor` chooses *which processor***, whereas **`-processorpath` / `--processor-path` or `--processor-module-path` specifies *where to find and load processors***. We will set up a Java 17+ example with a processor that generates a class, run it end to end from scratch, and compare service discovery, classpath, module path, multiple processors, and common errors. The module's Special Note has no additional requirements.

## 1. Mechanism Map: Source, Processor, and Output Are Three Different Roles

~~~text
Application: @GenerateInfo on Model.java
           │
           │ annotation API present on compile classpath
           ▼
        javac
           │
           ├── Configure -processor proc.InfoProcessor
           │         → select processor class by name
           │
           ├── Configure -processorpath ...
           │         → load implementation and dependencies
           │
           └── Annotation processing rounds
                        │
                        ├── Processor reads Element/Type model
                        ├── Generates GeneratedInfo.java via Filer
                        └── New generated source enters next round
                                      │
                                      ▼
                         Compile original + generated sources
                                      │
                           App.class, GeneratedInfo.class
~~~

Three path categories must be distinguished:

| Component | Role | Example |
| --- | --- | --- |
| **Compile classpath** `-cp`/`--class-path` | Gives Java sources being compiled access to annotation APIs and application dependencies | `build/annotations` |
| **Processor path** `-processorpath`/`--processor-path` | Lets `javac` find/load processors **and libraries the processors need to execute** | `build/processor:build/annotations` |
| **Source output** `-s` | Where `Filer` writes `.java` sources generated by processors | `build/generated` |
| **Class output** `-d` | Where the compiler writes `.class` files of the application and generated sources | `build/classes` |
| **Processor module path** `--processor-module-path` | Where to find *modular processors*, instead of the processor-classpath loader | `mods/processors` |
| **Module path** `--module-path` | Where to find module dependencies of **sources being compiled** | `mods/libraries` |

**A processor is a program executed by `javac` in the build environment**. It is not a class automatically invoked by the application JVM at runtime simply because an annotation is present. Annotations with `SOURCE` retention can disappear from class files yet still have been processed at compile time.

An important principle: compile classpath and processor path **should not be accidentally conflated**. If a processor is on the processor path yet the annotation API is missing from the compile classpath, code with `@GenerateInfo` may still fail with `cannot find symbol`. Conversely, if source can import the annotation yet the processor implementation cannot be found, code generation will not occur.

## 2. Syntax and Meanings of Key Options

| `javac` option | Meaning |
| --- | --- |
| `-processor p.First,p.Second` | Specifies exact processor classes to use, **bypassing default provider discovery** |
| `-processorpath path` | Sets processor lookup path using traditional classpath |
| `--processor-path path` | Long form equivalent to `-processorpath` |
| `--processor-module-path path` | Lookup path for processors packaged as named modules |
| `-proc:none` | Disables annotation processing, continues normal source compilation |
| `-proc:only` | Runs annotation processing yet **does not continue to normal class-file compilation** |
| `-proc:full` | Requests both annotation processing and compilation (on JDKs supporting this option) |
| `-s directory` | Sets target directory for generated sources |
| `-d directory` | Sets target directory for class files |
| `-Akey=value` | Passes custom option to processors, accessible via `ProcessingEnvironment.getOptions()` |
| `-XprintRounds` | Prints annotation processing round information |
| `-XprintProcessorInfo` | Prints which processors are asked to handle which annotations |

The list after `-processor` uses **commas**, not spaces, to separate processor names. Each entry is a **fully-qualified class name** having a valid public no-arg constructor or Java-provided default public constructor, implementing `javax.annotation.processing.Processor`. The class must be present on the appropriate lookup path for `javac` to load it.

**Distinguishing `-processor` from `-processorpath`:**

~~~bash
# Select a specific processor class. -processor itself is not a path.
javac -processor proc.InfoProcessor ...

# Tell the compiler where to locate processors. Can be combined with discovery.
javac -processorpath build/processor ...

# Use both: explicit about which processor runs and where to load it.
javac -processorpath build/processor -processor proc.InfoProcessor ...
~~~

The `...` in the three lines above represents other options/sources to fill in, **not standalone runnable syntax**. The complete example below provides step-by-step executable commands.

## 3. Important Change from JDK 23: Do Not Rely on Implicit Processor Discovery

Prior to JDK 23, many builds accidentally ran processors because a JAR containing a service provider sat on the **classpath**. Starting with **JDK 23**, `javac` **does not activate annotation processing merely because a processor happens to be discovered on the classpath**. Explicit configuration is needed, such as:

- Specifying classes with `-processor`.
- Specifying processor lookup paths with `-processorpath` or `--processor-module-path`, when the artifact supplies matching discovery info.
- Requesting processing via `-proc:only` or `-proc:full`, on supporting JDKs.

This does not mean you must **always pass all three options**. A command `-processor proc.InfoProcessor -processorpath ...` already clearly specifies both the class and where to load it. A processor JAR with a service descriptor can be found via `-processorpath ...` when processing is properly configured.

JDK 21/22 emitted warnings/notes about implicit processing in certain commands; JDK 23 changed the default to reduce builds silently executing processors from the classpath. Because processors execute code during the build, explicitly listing processors and processor dependencies also **reduces the supply-chain attack surface** and improves reproducibility.

**Inspect the exact compiler in use:**

~~~bash
javac -version
javac -help
javac -X
~~~

`-proc:full` is not present in all older JDK 17 patch builds; the Java 17+ example below uses **`-processor` and `-processorpath`** so it does not depend on `-proc:full` for demonstration. Do not assume every JDK 17.x release supports the exact same set of newer flags.

## 4. When to Use -processor vs. Discovery?

**Use `-processor` if:**

- You need to select **the exact** one or few controlled processors, even if multiple providers exist on the processor path.
- You want reproducible builds: adding a stray JAR must not introduce a new processor.
- You want to isolate a single processor when debugging, checking versions, or troubleshooting conflicts.
- Implementing a security pipeline requiring an explicitly approved processor list.

**Use service discovery if:**

- The processor JAR already packages a proper service provider descriptor.
- Build tools/plugins manage annotation processor dependency lists.
- You want new processors recognized via SPI without editing `-processor` for each class.

Both approaches must still ensure the processor can **load** and matching annotations actually appear in the processed roots. Specifying a processor class does not create annotations in source, nor does it force every `process` method to run on a fixed schedule for every file.

**Example list of multiple processors:**

~~~bash
javac -processor proc.InfoProcessor,proc.CheckerProcessor \
  -processorpath build/processors:build/annotations \
  -cp build/annotations \
  -d build/classes src/app/demo/Model.java
~~~

This is a **syntax template** and runs only if `proc.CheckerProcessor` is already compiled and all paths exist. The `-processor` list is not a list of annotation types received by processors; processors declare supported annotation types themselves via `@SupportedAnnotationTypes` or the corresponding API.

### Selecting a Class Does Not Guarantee Running process()

There are two logical phases:

1. `javac` **creates and initializes** processor candidates from configuration.
2. During rounds, the compiler checks present annotation types against types each processor supports, along with whether another processor already “claimed” the annotation, before deciding to invoke it.

Therefore, adding a class to `-processor` does not mean `process()` runs in every round if no matching annotations exist, except in cases specified by the API contract (such as a processor supporting `"*"`). To verify with evidence, use `-XprintRounds` and `-XprintProcessorInfo` rather than guessing from the list alone.

## 5. Complete Java 17+ Example: Processor Generating GeneratedInfo.java

We write one annotation API, one processor, and two application files. The processor will generate class `demo.GeneratedInfo` from the `@GenerateInfo` annotation, and `App` uses that class within **the same `javac` invocation**. This is a strong test: if the processor does not run, the application cannot compile because `GeneratedInfo` does not exist yet.

### 5.1. Directory Structure

~~~text
processor-demo/
├── src/
│   ├── api/
│   │   └── demo/GenerateInfo.java
│   ├── processor/
│   │   └── proc/InfoProcessor.java
│   └── app/
│       └── demo/
│           ├── Model.java
│           └── App.java
└── build/                    # Created in the commands below
    ├── annotations/          # Compiled annotation API
    ├── processor/            # Compiled processor implementation
    ├── generated/            # Generated .java sources
    └── classes/              # App + generated classes
~~~

All Bash commands assume you are in the `processor-demo` directory with JDK 17+ providing `javac`, `java`, and `jar`. Examples use `:` as path separator (Linux/macOS); on Windows use `;` and corresponding directory-creation commands.

### 5.2. Annotation File: src/api/demo/GenerateInfo.java

~~~java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.SOURCE)
public @interface GenerateInfo {
}
~~~

`@Target(TYPE)` restricts the annotation to type declarations such as classes. `@Retention(SOURCE)` fits the example: the annotation is needed at compile time and need not be placed in runtime metadata. This annotation does not generate a class by itself; the processor performs that work.

### 5.3. Processor: src/processor/proc/InfoProcessor.java

~~~java
package proc;

import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;
import javax.tools.JavaFileObject;

@SupportedAnnotationTypes("demo.GenerateInfo")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class InfoProcessor extends AbstractProcessor {
    private boolean generated;

    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {

        if (roundEnv.processingOver() || generated || annotations.isEmpty()) {
            return false;
        }

        try {
            JavaFileObject file = processingEnv.getFiler()
                    .createSourceFile("demo.GeneratedInfo");

            try (Writer out = file.openWriter()) {
                out.write("package demo;\n");
                out.write("public final class GeneratedInfo {\n");
                out.write("    private GeneratedInfo() {}\n");
                out.write("    public static String value() {\n");
                out.write("        return \"generated: ok\";\n");
                out.write("    }\n");
                out.write("}\n");
            }

            generated = true;
        } catch (IOException ex) {
            processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.ERROR, "Cannot generate source: " + ex);
        }
        return true;
    }
}
~~~

**Explanation:**

- `AbstractProcessor` provides a convenient implementation of `Processor`.
- `@SupportedAnnotationTypes("demo.GenerateInfo")` informs the compiler that the processor handles the package-qualified annotation name; do not write `"GenerateInfo"` without the package.
- `@SupportedSourceVersion(RELEASE_17)` declares the source level supported by the processor. It is not a mechanism that automatically turns an annotation processor into a Java 17 runtime library; the processor's class files still depend on the JDK and options used to compile it.
- `process(...)` receives the annotation types assigned by the framework for the current round and a `RoundEnvironment`; `annotations.isEmpty()` guards against generating source when no matching annotation is present.
- `generated` prevents recreating the same file in subsequent rounds. Processors are instantiated **once per run**, not as a new instance in every round.
- `Filer.createSourceFile` creates Java source; the compiler can feed the new source into the next round and compile it alongside original sources.
- `return true` indicates the processor **claims** the assigned annotations; processors considered later will not be passed that same annotation type in that round.
- When file creation fails, `Messager` emits a build diagnostic; exceptions are not silently swallowed.

The code here uses a fixed output name `demo.GeneratedInfo` for easy observation. In a real processor, derive names per annotated element, check for collisions, and avoid creating the same path across rounds. If two processors attempt to write that file, `FilerException`/diagnostics may appear.

### 5.4. Application: Model.java and App.java

**`src/app/demo/Model.java`**

~~~java
package demo;

@GenerateInfo
public final class Model {
}
~~~

**`src/app/demo/App.java`**

~~~java
package demo;

public final class App {
    private App() {
    }

    public static void main(String[] args) {
        System.out.println(GeneratedInfo.value());
    }
}
~~~

`GeneratedInfo` has no initial Java file and appears only when processing creates the source. `App` directly references the generated class to verify that **annotation discovery**, **processor loading**, **rounds**, and **compilation** all succeed.

### 5.5. Compile the Annotation API and Processor First

~~~bash
mkdir -p build/annotations build/processor build/generated build/classes

javac --release 17 \
  -d build/annotations \
  src/api/demo/GenerateInfo.java

javac --release 17 \
  -cp build/annotations \
  -d build/processor \
  src/processor/proc/InfoProcessor.java
~~~

After these two steps you have:

~~~text
build/annotations/demo/GenerateInfo.class
build/processor/proc/InfoProcessor.class
~~~

Reason for **separating the bootstrap phase**: `javac` needs to **load an already-compiled processor** before the processor handles application sources. You cannot just put uncompiled `InfoProcessor.java` on `-processorpath` and expect the compiler to compile the processor from source in the same pass.

### 5.6. Invoke javac with Both -processor and -processorpath

~~~bash
javac --release 17 \
  -cp build/annotations \
  -processorpath build/processor:build/annotations \
  -processor proc.InfoProcessor \
  -s build/generated \
  -d build/classes \
  src/app/demo/Model.java src/app/demo/App.java
~~~

In this command:

- `-cp build/annotations` lets `Model` source see `demo.GenerateInfo`.
- `-processorpath build/processor:build/annotations` gives the loader `proc.InfoProcessor`'s implementation and any annotation APIs/dependencies the processor might need. The demo processor uses the annotation name as a string, yet configuring the path cleanly remains helpful for real examples.
- `-processor proc.InfoProcessor` specifies **the exact** processor to run; no service descriptor is needed for this mode.
- `-s build/generated` writes generated sources into `build/generated/demo/GeneratedInfo.java`.
- `-d build/classes` writes `App.class`, `Model.class`, and `GeneratedInfo.class` into their respective packages.

The compiler creates new code during annotation processing and compiles it. There is no need to run `javac` a second time to compile `build/generated/demo/GeneratedInfo.java` in this example.

Run the program:

~~~bash
java -cp build/classes demo.App
~~~

**Exact stdout from App:**

~~~text
generated: ok
~~~

There is no need to place the processor implementation on the runtime classpath when merely running `demo.App`. The processor serves the build process; the generated class is what the application uses at runtime. Annotation `@GenerateInfo` has `RetentionPolicy.SOURCE`, so it is not a runtime dependency for this example either.

### 5.7. Evidence That the Processor Generated Code

Outputs to verify:

~~~text
build/generated/demo/GeneratedInfo.java
build/classes/demo/GeneratedInfo.class
build/classes/demo/Model.class
build/classes/demo/App.class
~~~

If compilation fails because `GeneratedInfo` does not exist, immediately inspect processor selection, processor lookup path, service registration, and diagnostics. Do not hastily edit `App.java` to mask the fact that the processor did not run.

## 6. Trying Service Discovery: Omitting -processor

`-processor` is not mandatory when the processor is **advertised as a service provider** via the classpath SPI mechanism. The service file must sit at the exact path inside the processor output directory or JAR:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

**Sole content of the service file in the demo:**

~~~text
proc.InfoProcessor
~~~

From inside `processor-demo`, create the service metadata:

~~~bash
mkdir -p build/processor/META-INF/services
printf '%s\n' 'proc.InfoProcessor' \
  > build/processor/META-INF/services/javax.annotation.processing.Processor
~~~

Then isolate outputs for this test build by deleting/moving outputs **only inside your demo directory** and recreating them:

~~~bash
rm -rf build/classes build/generated
mkdir -p build/classes build/generated

javac --release 17 \
  -cp build/annotations \
  -processorpath build/processor:build/annotations \
  -s build/generated \
  -d build/classes \
  src/app/demo/Model.java src/app/demo/App.java

java -cp build/classes demo.App
~~~

The final run command continues printing:

~~~text
generated: ok
~~~

In this compile pass, **there is no `-processor`**. `javac` locates the service file on the processor path, discovers `proc.InfoProcessor`, and invokes it per matching annotations. This is **discovery**. It differs from explicit selection because a processor artifact can advertise one or multiple providers via service metadata.

Note: `rm -rf` is a recursive deletion command. Use this example only when certain you are in `processor-demo` and `build/classes`, `build/generated` are **your demo's own outputs**; never copy deletion commands into another project directory without checking. Do not delete `build/processor` because it contains the implementation and service file.

### When Is a Service File Not Recognized?

- Wrong filename, such as `META-INF/service` (missing `s`) or service name other than `javax.annotation.processing.Processor`.
- Placing the file next to the JAR instead of **inside the JAR** or at the root of a processor-path directory entry.
- Incomplete class name; non-`public` class or missing public no-arg constructor; class does not implement `Processor`.
- Missing processor class/dependencies causing the loader to throw an exception.
- Declaring service metadata without validly enabling processing on JDK 23+.
- Using `-proc:none` and expecting processors to run.

Processor implementations and service files can be packaged in a JAR via `jar --create --file ...`; entry paths inside the JAR must be exact. A single JAR holding both processor and annotation API can be designed intentionally, though forcing all processor dependencies onto the app's compile classpath unnecessarily should be avoided.

## 7. Why Is -cp Different from -processorpath?

This is the single largest source of confusion when configuring Lombok, MapStruct, Dagger, AutoService, or custom processors.

**Case A:** annotation is on `-cp`, implementation is missing from `-processorpath`.

~~~text
javac ... -cp build/annotations -processorpath empty_processors \
  -processor proc.InfoProcessor ...
~~~

This command **cannot run** if `empty_processors` lacks the processor: the compiler typically reports `Annotation processor 'proc.InfoProcessor' not found`. This is an **error pattern**, not a complete runnable command.

**Case B:** implementation sits on processor path, yet annotation API is missing from compile classpath.

When compiling `Model.java` containing `@GenerateInfo`, the compiler may fail to find `demo.GenerateInfo`. Adding the processor implementation **does not automatically** make the annotation API a dependency for application source imports.

**Case C:** configuring only `-cp` and expecting JDK 23+ to auto-discover providers.

From JDK 23 onward, do not rely on this implicit processing. Select processors explicitly via `-processor` or configure processor path/discovery or `-proc:full` explicitly. With build tools, use the dependency configuration dedicated to processors.

**Case D:** placing processor runtime dependencies on the application classpath while forgetting the processor path.

Once `-processorpath` is specified, it is the lookup area for the processor loader; do not assume a JAR on `-cp` is automatically present on the processor path. Add required JARs where the processor loader sees them.

### Realistic Example with Multiple Dependency JARs

On Linux/macOS:

~~~bash
javac \
  -cp libs/annotations.jar:libs/application-api.jar \
  -processorpath libs/my-processor.jar:libs/processor-helper.jar:libs/annotations.jar \
  -processor com.example.build.MyProcessor \
  -d out \
  src/main/java/com/example/App.java
~~~

This is an **usage template**, not a standalone runnable project: replace class/JAR/source names with real artifacts. On Windows, change `:` in path lists to `;`.

Do not dump all application JARs onto the processor path needlessly, because every processor dependency is code that can be loaded during the build; good practice restricts the processor path to processors and dependencies needed by the processors themselves to execute.

## 8. Modular Annotation Processors: --processor-module-path

In the Java module system, processors can be packaged as **named modules** providing services via `provides ... with ...`. In that case, use:

~~~text
--processor-module-path path
~~~

instead of the traditional processor classpath. Example descriptor of a **dedicated processor module**:

~~~java
module com.example.codegen {
    requires java.compiler;
    provides javax.annotation.processing.Processor
            with com.example.codegen.MyProcessor;
}
~~~

This is an **illustrative module-info.java**, not a direct addition to the classpath demo in section 5; an actual `com.example.codegen.MyProcessor` class must exist, implement `Processor`, and be built as a module. `java.compiler` provides the `javax.annotation.processing`, `javax.lang.model`, and `javax.tools` packages.

Template example for a project with packaged modular processors:

~~~bash
javac \
  --processor-module-path mods/processors \
  --module-path mods/application-libraries \
  -d out \
  src/app/module-info.java src/app/com/example/app/Main.java
~~~

The syntax above is **only a configuration skeleton**: fill in real modules, sources, and dependencies. The compiler searches for service providers in modules on the processor module path. When using module paths, note:

- Providers must be **properly published** via module service declarations.
- Processor modules and dependencies must load with appropriate module access.
- Do not equate `--processor-module-path` with `--module-path` intended for **application modules**.
- Avoid configuring both processor path and processor module path mechanisms ambiguously; choose the right artifact packaging model.

A processor can run on a newer build JDK than the release of the generated code. However, final source/generated code must still adhere to the application's `--release`. To support multiple build JDKs, verify both **the processor's runtime requirements** and **target requirements of the emitted code**.

## 9. Multiple Processors in One Compile: Annotation Claiming and Rounds

Annotation processing typically spans **multiple rounds**. Each round, processors receive elements with matching annotations; when a processor emits new source via `Filer`, the compiler can process those sources in the next round.

~~~text
Round 1: Model.java has @GenerateInfo
    └── InfoProcessor → generates GeneratedInfo.java
                    │
                    ▼
Round 2: generated source enters next round input
                    │
                    ▼
Final round: processingOver() == true
                    │
                    ▼
Compilation: App, Model, and GeneratedInfo → .class
~~~

This diagram is conceptual; round counts, present annotations, and invocation order can vary by processor set and generated sources. A processor already invoked in one round will continue to be invoked by the framework in subsequent rounds per contract, including the final round; hence check `roundEnv.processingOver()` and avoid recreating files.

### Claiming: What Do true and false Mean?

`process(Set<? extends TypeElement>, RoundEnvironment)` returns:

- `true`: the processor **claims** the annotation types in the `annotations` set passed to it; they are not passed further to processors evaluated later in the round.
- `false`: unclaimed, allowing other processors to also process those annotations per discovery/matching rules.

Do not use `return true` to “ensure a certain processor runs first”; discovery order, claiming, and annotation sets delivered to processors have their own rules. Multiple processors editing the same file/source can conflict. If a processor depends on source created by another processor, design around **rounds and Filer outputs** rather than assuming invocation order.

### Why Should a Processor Not Compile Outputs Itself?

The `Filer` API is responsible for creating sources/classes/resources per contract. As the compiler proceeds with processing and compilation, generated sources enter the workflow. Invoking a nested `javac` inside `process` usually complicates class loaders, dependencies, duplicate outputs, and diagnostics; do it only when a dedicated workflow is genuinely needed.

## 10. Reading -XprintRounds and -XprintProcessorInfo Logs

To watch the demo operate, run the command from section 5.6 with both diagnostic options added:

~~~bash
javac --release 17 \
  -cp build/annotations \
  -processorpath build/processor:build/annotations \
  -processor proc.InfoProcessor \
  -XprintRounds -XprintProcessorInfo \
  -s build/generated -d build/classes \
  src/app/demo/Model.java src/app/demo/App.java
~~~

Before re-running from scratch with a processor generating fixed filenames, ensure `build/generated` and `build/classes` are clean outputs of **the demo**; old generated files can make recreation or compilation confusing. Both flags only print diagnostics and do not enable processors if core configuration is wrong.

You may see output like:

~~~text
Round 1:
    input files: {...}
    annotations: [...]
    last round: false
Processor proc.InfoProcessor matches [...] and returns true.
...
~~~

This is **an illustration of log format**, not exact guaranteed output across every JDK. Round counts and exact formatting depend on compiler, annotations, and generated sources. For the demo, **the most reliable proof** remains the created class running and printing `generated: ok`.

When logs omit a processor you expected, check sequentially:

1. Are `-processor` or discovery/processing flags configured properly for the JDK?
2. Is the fully-qualified processor class name accurate?
3. Can the processor and its dependencies load from the processor path/module path?
4. Does `@SupportedAnnotationTypes` match annotations appearing in the sources under compilation?
5. Did another processor claim the annotation earlier?
6. Was the source listed/read in the current compilation pass, or is it only an old dependency?

## 11. -proc:none, -proc:only, and -proc:full

These three modes are not the same:

| Mode | Annotation processing | Normal `.class` compilation |
| --- | --- | --- |
| `-proc:none` | No | Yes |
| `-proc:only` | Yes, when matching processor is configured | **Does not** perform normal class compilation phase |
| `-proc:full` | Yes, when configured/discovered | Yes |

`-proc:only` fits when you want to run annotation validation or **only generate sources** to inspect results before deciding to proceed with building. Yet do not expect `App.class` to be generated merely because `-d` is present. A pipeline using `-proc:only` can produce generated sources without application bytecode yet.

On very old JDK 17 releases, `-proc:full` may not have been backported. Explicit processor selection such as `-processor proc.InfoProcessor` on `-processorpath` works cleanly for demos without relying on that newer option. On JDK 23+, specifying processing explicitly is especially critical.

### Running a Negative Test

If you process the demo on **clean outputs** using `-proc:none`:

~~~bash
javac --release 17 \
  -proc:none \
  -cp build/annotations \
  -d build/classes \
  src/app/demo/Model.java src/app/demo/App.java
~~~

The command will **have no generated class `GeneratedInfo`** because the processor is disabled. Since `App` references that class, on clean outputs compilation fails with a symbol-lookup error. If stale classes remain in output/classpath, results can differ; that is why outputs must be cleaned for testing processing logic. Never claim every annotated source fails compilation under `-proc:none`: sources still compile if they do not depend on generated code.

## 12. Passing Custom Options with -A and Checking Configuration

Annotation processors sometimes need custom settings such as target package, strict mode, or filename. Use:

~~~text
-Acodegen.mode=debug
-Acodegen.outputPackage=com.example.generated
~~~

The processor reads them via:

~~~java
String mode = processingEnv.getOptions().getOrDefault(
        "codegen.mode", "default");
~~~

This is a **snippet inside the processor**, not a standalone Java program. A processor should declare supported options via `@SupportedOptions({"codegen.mode", "codegen.outputPackage"})` or `getSupportedOptions()` so the compiler recognizes them. Values are text; the processor must validate them itself. `javac` does not automatically turn `-Acodegen.mode=debug` into any behavior if the processor does not read it.

Note `-A` uses the syntax `-Akey[=value]`, with no space between `-A` and key. Values containing whitespace require shell and option-syntax quoting. Do not confuse `-A` with application arguments passed to `main(String[] args)`.

### Processor Output Must Be Reproducible

In production code generation:

- Avoid depending on element order when the API does not guarantee it; if needed, sort by fully-qualified name.
- Do not write build timestamps or absolute paths into generated files unless required.
- Emit clear diagnostics when misconfigured; never swallow exceptions.
- Do not read files from arbitrary paths or access networks unnecessarily, since processors execute inside the build environment.
- Restrict privileges and dependencies of processors as you would for any build tool capable of executing code.

## 13. Processor Path, Module Path, and Java Version

Processor lookup paths are configured for **the compiler's execution environment**, whereas sources being compiled have their own **type/API context**. That leads to several scenarios:

- A processor class compiled for Java 21 cannot load when running `javac` on JDK 17 (may trigger `UnsupportedClassVersionError` or a processor load failure message), **even** when source target is only `--release 8`.
- A processor running on JDK 21 yet generating Java source using Java 21 APIs while the app compiles with `--release 17` will be rejected by the compiler. Processors must emit code compatible with the application's target.
- With processor module path, provider modules `requires java.compiler` and may need `requires`/`opens`/`exports` for processor dependency modules; these are constraints at **processor execution time**, not the application's module descriptor.
- `--module-path` locates dependencies of modular applications; `--processor-module-path` locates processor modules; the paths cannot substitute for each other.
- `-J-Xmx1g` adjusts the JVM running the compiler when invoking the `javac` launcher; it is not a `-A` parameter and not the heap size of the deployed application.

Practice: record `javac -version`, processor artifact version, target release, plus both compile classpath and processor path. Especially in CI, build tools may select a different JDK from `java` on the shell; do not infer the source target purely from a Docker image tag or job label.

## 14. Processors in Maven and Gradle

Build tools usually provide **separate configurations for processor dependencies** and app compile dependencies.

### Maven

With Maven Compiler Plugin versions supporting `annotationProcessorPaths`, an illustrative example in `pom.xml`:

~~~xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.14.0</version>
            <configuration>
                <release>17</release>
                <annotationProcessorPaths>
                    <path>
                        <groupId>com.example</groupId>
                        <artifactId>my-processor</artifactId>
                        <version>1.0.0</version>
                    </path>
                </annotationProcessorPaths>
                <annotationProcessors>
                    <annotationProcessor>com.example.ProcessorImpl</annotationProcessor>
                </annotationProcessors>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

This is a **configuration example**, not a self-running project: Maven coordinates and processor classes must be replaced with real artifacts. `annotationProcessorPaths` controls where to locate processors, `annotationProcessors` corresponds to selecting processor names; `release` sets source/API target. When a project uses annotation APIs in source, declare the annotation API dependency in the project's dependencies section as needed.

Plugin versions, processor module path configuration, and Maven/JDK compatibility can change; consult the documentation for **the exact plugin version in use**. Do not copy templates as a “single standard version” across every repository.

### Gradle (Groovy DSL)

~~~groovy
plugins {
    id 'java'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    compileOnly 'com.example:my-annotations:1.0.0'
    annotationProcessor 'com.example:my-processor:1.0.0'
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
    options.compilerArgs += [
        '-processor', 'com.example.ProcessorImpl'
    ]
}
~~~

`annotationProcessor` declares dependencies Gradle places on the processor path; `compileOnly` makes annotation APIs visible to sources without necessarily bundling them at runtime. In real projects, annotations with `RUNTIME` retention or runtime usage may require different dependency scopes. `options.compilerArgs` is an example when wanting to **specify processors explicitly**; if the JAR provides service discovery and the build has a valid processor path, forcing this list may not be necessary.

Do not simply put a processor JAR into `implementation` and expect Gradle/JDK 23+ to run codegen. Separating `annotationProcessor` from runtime/application dependencies keeps pipelines clean and avoids accidentally shipping build tools in distributions.

## 15. Common Errors and Resolutions

| Error/symptom | Common cause | Resolution |
| --- | --- | --- |
| `Annotation processor 'x.Y' not found` | Typo in class name, processor uncompiled, processor path lacks output/JAR | Check FQCN, `jar tf`, root path, compiler JVM/JDK |
| `Bad service configuration file` | Service descriptor misnamed or faulty provider class | Check `META-INF/services/javax.annotation.processing.Processor` and public class |
| `NoClassDefFoundError` when loading processor | Processor's own library missing on processor path | Add processor dependencies to processor path, not only app `-cp` |
| Annotation API not found in source | Missing annotation artifact on compile classpath/module path | Add dependency used to compile the app |
| Annotation recognized yet no code generated | Processor not selected; `-proc:none`; annotation didn't match; processor emitted no file | Use `-XprintRounds`, check `@SupportedAnnotationTypes`, logging/diagnostics |
| `FilerException: Attempt to recreate a file` | Processor wrote same output across multiple rounds or multiple processors | Guard by round/element, unique filenames, clean outputs |
| Using JDK 23+ yet missing generated code | Relied on implicit processor discovery from classpath | Use processor path/explicit `-processor`/build tool configuration |
| Processor `UnsupportedClassVersionError` | Processor compiled with newer Java than build JDK | Use processor supporting build JDK or upgrade build JDK |
| Generated source uses too-new APIs/syntax | Processor violates app `--release` | Fix generator or target, inspect outputs |
| Source generated yet `.class` missing | `-proc:only` or compilation failed | Use processing + compile when `.class` is desired |
| Two processors “compete” over same annotation | Claiming and discovery order, overly greedy processor | Check supported annotations and `return true/false` |
| `-processorpath` on Windows fails to find JAR | Used `:` instead of `;` between path entries | Use OS-appropriate path separator |
| Processor runs repeatedly unexpectedly in CI | Old generated sources, incremental cache, uncleaned outputs | Reproduce on clean outputs and check build tool |

**Note:** some errors occur only once entering code generation, not necessarily when the processor loads. Do not assume every `cannot find symbol` error is a processor bug: it could be source/package/classpath. Read full diagnostics, and inspect generated sources before blindly altering configuration.

## 16. Checklist for Reliable Processor Configuration

1. **Identify processor FQCN**, supported annotation types, and Java version needed to run the implementation.
2. **Place annotation APIs** on the compile classpath/module path appropriate for project sources.
3. **Place processor implementation and its runtime dependencies** on `--processor-path` or `--processor-module-path` matching artifact type.
4. **Decide between explicit vs. discovery:** `-processor p.X` for a fixed list; service file or `provides` when wanting SPI.
5. **Enable processing explicitly**, especially on JDK 23+; do not rely on JARs falling onto the classpath.
6. **Set `-s`, `-d`** to manage source and bytecode outputs cleanly.
7. **Inspect rounds and generated outputs:** `-XprintRounds`, `-XprintProcessorInfo`, actual `.java`/`.class` files.
8. **Distinguish `-proc:none`/`-proc:only`/full compilation**, avoiding confusing source-only generation with compiling the application.
9. **Pin processor dependency versions** and test on supported build JDKs.
10. **Keep processor path free of unnecessary app dependencies**; audit processors as part of code-executing toolchains.
11. **Test on clean builds and CI**, especially when switching JDKs, Maven/Gradle, or upgrading dependencies.
12. **Check real runtime:** generated classes exist in artifacts, while the processor itself usually need not ship with the application.

## 17. Self-Check Questions

**Question 1.** Does `-processor proc.InfoProcessor` specify where to find the `InfoProcessor.class` file?  
**Answer:** No. It selects the processor class; a processor path/module path or appropriate loading configuration is needed to locate the class.

**Question 2.** Does `-processorpath libs/tool.jar` force running specifically `com.acme.MyProcessor`?  
**Answer:** Not necessarily. When using discovery, service metadata determines provider candidates. To pin one specific processor, use `-processor com.acme.MyProcessor`.

**Question 3.** Why can the app import the annotation yet the generated class still be missing?  
**Answer:** A valid compile classpath does not guarantee the processor loader found the implementation or processing is enabled. Check processor path, processor selection, rounds, and `-proc:none`.

**Question 4.** Using JDK 23, a processor JAR sits on `-cp` with valid service metadata. Should we assume the processor runs automatically?  
**Answer:** No. From JDK 23 onward, implicit processing from the classpath is disabled by default; configure processors explicitly.

**Question 5.** Does `-proc:only` generate `App.class` after processing?  
**Answer:** Normal compilation is skipped. To get both source generation and bytecode, use processing + compilation mode.

**Question 6.** How do `--processor-module-path` and `--module-path` differ?  
**Answer:** One locates **processor modules** for the compiler to execute them; the other locates **application modules** for sources being compiled.

**Question 7.** Why can a processor be called multiple times?  
**Answer:** Annotation processing spans multiple rounds; newly generated sources are processed in the next round; processors must watch `processingOver()` and avoid writing the same file twice.

**Question 8.** If `return true` is used in a processor, does that mean the class compiled successfully?  
**Answer:** No. It claims the assigned annotation types, not a build result; compilation can still fail.

**Question 9.** Is it necessary to put `build/processor` onto `demo.App`'s runtime classpath?  
**Answer:** No for this demo; `App` only uses the compiled `GeneratedInfo`, without calling the processor at runtime.

## 18. Takeaways and References

**`-processor` answers “which implementation to select?”**; **`-processorpath`/`--processor-path` answers “where to find and load the implementation and its dependencies?”**; **`--processor-module-path` is for modular processor providers**. Source compile classpath, `-s`/`-d` outputs, and application runtime classpath are **separate** components. Processing configuration must be explicit on JDK 23+; declare processor dependencies and choose processors explicitly or via SPI rather than relying on accidental discovery.
