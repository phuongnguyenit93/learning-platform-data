# Identifying build cache inputs and avoiding using results from wrong configurations

## 1. What problem does the build cache solve?

In a Java build, compilation, code generation, testing, packaging, or documentation generation steps can take a long time. The build cache allows Gradle to reuse **existing outputs** of a task when the relevant inputs have not changed. However, the cache is only correct when we fully describe the relationship:

> **Same input data, same tools, and same affecting configuration must produce the same output content.**

Imagine `output = f(source, dependencies, toolchain, options, task configuration, external inputs)`. The cache key is built from the inputs Gradle knows about. If a factor **affects the output** yet is **not declared**, the cache can return a result generated by a different configuration. That is a *false cache hit*. If you also declare factors that **do not affect the output**, the cache will miss unnecessarily, wasting time.

For example, a task generates a product configuration file from `-Pedition=community` or `-Pedition=enterprise`. If the action reads this value directly from the project without the task declaring it as an input, changing the edition may not change the cache key. An enterprise build could accidentally receive a community artifact. This is a correctness bug, not merely an optimization issue.

The goal of this lesson is to identify real inputs, declare standard Gradle metadata, compare results when changing configuration, and design tasks deterministic enough to use the build cache safely.

## 2. Distinguishing up-to-date, build cache, and configuration cache

| Mechanism | What question does it answer? | Typical status |
|---|---|---|
| **Up-to-date check** | Has the task already run in this workspace and do inputs/outputs still match? | `UP-TO-DATE` |
| **Build cache** | Is there an artifact from an equivalent run to restore without executing the action? | `FROM-CACHE` |
| **Configuration cache** | Can the *build configuration* state be reused to skip the configuration phase? | Configuration cache reuse log |

The three mechanisms are related yet not identical. The build cache stores **task outputs**, whereas the configuration cache stores **build configuration state**. A task re-running and producing new output does not mean the configuration cache was ineffective. A `FROM-CACHE` line only proves Gradle found an entry matching the **declared** fingerprint; it does not prove the fingerprint included *every* affecting factor.

In Gradle, you can use `--build-cache` when running a command or set `org.gradle.caching=true` in `gradle.properties` to enable build cache usage. A task must qualify to be cached: built-in tasks are supported by Gradle under their contract; custom tasks must declare inputs and outputs properly and are typically marked `@CacheableTask` after ensuring determinism.

## 3. Identifying complete inputs of a task

The starting point should be **everything the action and the tools it invokes actually read**, including indirect data. Then determine the declaration type:

| Source | Real-world example | How to represent |
|---|---|---|
| Source and resources | `.java`, schema, config, template, processor descriptor | `@InputFile`, `@InputFiles`, and path policy |
| Classpath | Library JARs, code generators, annotation processors | `@Classpath`, in some cases `@CompileClasspath` |
| Parameters | debug, edition, target release, feature flag, package name | `@Input` / typed properties |
| Toolchain and tool version | JDK, Java compiler, compiler plugin, generator | Gradle toolchain/task API or explicit version input |
| System | environment variables, system properties, locale, timezone, encoding | Convert used values into inputs or normalize |
| External data | git SHA, API schema from server, network response, clock | Stable snapshot/version/hash or do not cache |
| Output | class files, JAR, generated source, report | `@OutputFile` / `@OutputDirectory` |

**Direct inputs** are data accessed by the action. **Indirect inputs** are data affecting tools invoked by the action: for example, a file read by a shell script, the JDK running the compiler, or an environment variable passed into a code generator. Inputs with **default values** also matter. For instance, a default value `targetRelease=17` must participate in the input contract if it changes bytecode.

An effective audit technique: trace every data read path from source to output. If changing that source can change any output byte, the source must appear in the fingerprint or the task must not be reused via cache.

With Gradle `JavaCompile`, configure via `java.toolchain`, `options.release`, compiler arguments, and standard dependency declarations. Gradle already tracks many inputs for this task; do not replace it with an `Exec` invoking `javac` while only declaring the source directory. Distinguish the **JDK version executing the compiler** from the **bytecode target**: both can affect the result.

## 4. Sample cacheable task in Gradle Groovy DSL

This example can be placed directly in `build.gradle` of a test Gradle project. It generates a metadata file from exactly two properties. The class containing the input/output contract is separated from the action; the action does not read hidden sources.

~~~groovy
import org.gradle.api.DefaultTask
import org.gradle.api.file.RegularFileProperty
import org.gradle.api.provider.Property
import org.gradle.api.tasks.CacheableTask
import org.gradle.api.tasks.Input
import org.gradle.api.tasks.OutputFile
import org.gradle.api.tasks.TaskAction

@CacheableTask
abstract class GenerateBuildDescriptor extends DefaultTask {
    @Input
    abstract Property<String> getEdition()

    @Input
    abstract Property<String> getSchemaVersion()

    @OutputFile
    abstract RegularFileProperty getDestination()

    @TaskAction
    void generate() {
        File target = destination.get().asFile
        target.parentFile.mkdirs()

        String content = "edition=" + edition.get() + "\n" +
                         "schemaVersion=" + schemaVersion.get() + "\n"
        target.setText(content, "UTF-8")
    }
}

tasks.register("generateBuildDescriptor", GenerateBuildDescriptor) {
    edition.set(providers.gradleProperty("edition").orElse("community"))
    schemaVersion.set(providers.gradleProperty("schemaVersion").orElse("1"))
    destination.set(layout.buildDirectory.file("generated/build-descriptor.properties"))
}
~~~

Run at the project root containing Gradle Wrapper:

~~~bash
./gradlew generateBuildDescriptor --build-cache --info
./gradlew generateBuildDescriptor -Pedition=enterprise --build-cache --info
~~~

On Windows use `gradlew.bat` instead of `./gradlew`. When run with defaults, `build/generated/build-descriptor.properties` contains:

~~~properties
edition=community
schemaVersion=1
~~~

When passing `-Pedition=enterprise`, the first value becomes `edition=enterprise`, producing a different result, and the cache key must reflect the difference. When running a second time with the same inputs while the output still exists, you may see `UP-TO-DATE`. To verify **cache restoration**, delete the test output and re-run with the same parameters using `--build-cache --info`; Gradle can report `FROM-CACHE` if the cache contains a valid entry. Do not infer that the first run must hit the cache.

Because the output file is determined completely by `edition` and `schemaVersion`, the task is suitable for caching. `@CacheableTask` is a commitment regarding **output reproducibility**; this annotation does not make a task with hidden reads correct.

## 5. Configuration mistakes causing incorrect cache hits

### 5.1. Reading environment variables or project properties outside the input contract

**Wrong:** the action calls `System.getenv("BUILD_PROFILE")` and embeds the result into the file without declaring this value as an input. Two runs with different profiles can share the same key.

**Fix:** add a property and wire the corresponding provider. The following snippet is an **additional code fragment** for the class and `tasks.register` block in section 4; inside the action you must also switch to reading `profile.get()` instead of `System.getenv(...)`:

~~~groovy
// Inside class GenerateBuildDescriptor:
@Input
abstract Property<String> getProfile()

// Inside tasks.register("generateBuildDescriptor", ...):
profile.set(providers.environmentVariable("BUILD_PROFILE").orElse("dev"))
~~~

If `profile` does not actually affect the output, there is no need to add it as an input. Avoid dumping all environment variables into the cache key because unrelated variables will cause excessive cache misses and may leak sensitive metadata.

### 5.2. Declaring the file name while forgetting the file contents

**Wrong:** the task has `@Input String getTemplatePath()`, then opens the file at that path and uses its contents to generate code. The template contents change while the path string stays the same: Gradle can permit invalid reuse.

**Fix:** declare a file input and path normalization. This snippet goes **inside the custom task class**, requiring the corresponding imports from `org.gradle.api.tasks`:

~~~groovy
@InputFile
@PathSensitive(PathSensitivity.RELATIVE)
abstract RegularFileProperty getTemplateFile()
~~~

`@InputFile` specifies that file contents are tracked, while `PathSensitivity.RELATIVE` makes the **relative** location a meaningful part of the path. For multiple files, use `@InputFiles` and an appropriate file collection. Do not arbitrarily choose `PathSensitivity.NONE` just to increase hits: if directory names or relative paths affect how output is assembled, they must participate in the key.

### 5.3. Applying the wrong classpath normalization

`@Classpath` is intended for data interpreted as a classpath, such as JARs containing implementations needed by a code generator. `@CompileClasspath` can ignore implementation changes that do not affect the **ABI** of dependencies when the output depends only on the API used for compilation. Do not use `@CompileClasspath` for a task that must read method bodies, resources, or execute dependency code. Wrong normalization can cause Gradle to treat two behaviorally different inputs as equivalent.

For ordinary compilation, prefer built-in Gradle tasks and their dependency/toolchain APIs to avoid incomplete manual classpath descriptions.

### 5.4. Nondeterministic outputs and data

A task writing `report.json` and `manifest.txt` while only declaring `report.json` as output risks incomplete restoration. A task inserting `Instant.now()`, random UUIDs, hostnames, or absolute paths into artifacts means two runs with the same fingerprint can produce different bytes. The fix is to publish all outputs; remove or normalize nondeterministic data; or declare genuinely needed values as inputs. If determinism cannot be guaranteed, do not mark the task cacheable.

### 5.5. External tools and services

An `Exec` task running a compiler/generator can depend on executable version, command-line flags, config files the tool opens on its own, environment variables, locale, and external resources. A task downloading a schema from a server depends on responses at each point in time. Use a built-in task with proper metadata, or supply a versioned/hashed schema snapshot as a file input. If external sources cannot be pinned, avoid caching that task. Do not use the endpoint URL string as a proxy for **response content** that may change at the same URL.

## 6. Rules for choosing annotations and normalization

| Annotation / property | Meaning | Pitfalls |
|---|---|---|
| `@Input` | Strings, numbers, booleans, options, versions, or plain properties | A path string does not represent file contents |
| `@InputFile`, `@InputFiles` | Contents of files read by the task | Must choose appropriate path sensitivity |
| `@Classpath` | Input classpath under classpath semantics | Do not treat all resources as source files |
| `@CompileClasspath` | Dependencies affecting only the ABI used by the task | Unsuitable when depending on implementation |
| `@Nested` | Object containing other input/output properties | Child properties still require complete metadata |
| `@OutputFile`, `@OutputDirectory` | File or directory produced by the task | Avoid multiple tasks writing to the same output |
| `@Internal` | Internal property that genuinely does not affect results | Misuse can hide important inputs |

Using relative paths enables cache reuse across checkouts in different directories, **only when absolute paths do not affect output**. If file names matter, the policy must preserve file names; if relative positions matter, use `RELATIVE`. For inputs genuinely insensitive to CRLF/LF, `@NormalizeLineEndings` can be combined with suitable metadata. Also normalize encoding so output files do not vary across OSes.

Ordering can also be part of the input: for example, classpath or command-line arguments. If a task traverses the filesystem itself and order has no meaning, sort inputs or process deterministically; do not let arbitrary ordering affect outputs.

## 7. Procedure for verifying configuration-correct caching

Run experiments on a project where outputs can be safely deleted, recording Gradle, JDK, plugin, and dependency versions when comparing:

1. **List real inputs/outputs:** identify every file, option, toolchain, environment variable, and output. Choose files or SHA-256 to prove results match.
2. **Create baseline A:** build with profile A, open the artifact, and verify contents match A. Record full inputs, not merely task status logs.
3. **Change one meaningful input:** e.g., edition A→B, template, classpath API, or release target. Output must be generated/supplied properly for B, carrying no data from A.
4. **Change one irrelevant factor:** e.g., move checkout to another directory when the task does not depend on absolute paths. Cache can be reused if path normalization metadata is right; output must still remain identical.
5. **Restore clean output:** delete output in the test workspace and re-run with the same inputs using `--build-cache --info`; when a valid entry exists, check for `FROM-CACHE` and compare restored file contents against baseline.
6. **Test A→B→A:** ensure artifacts of the two configurations do not mix, even when the cache already holds results for both.
7. **Control comparison:** generate output with `--no-build-cache` and compare contents with the restored version. You can use `--rerun-tasks` to force re-execution for diagnostics; forcing re-execution itself does not prove the cache key is correct.
8. **Test another environment:** on CI/another agent, inspect toolchain, OS, checkout path, locale, filesystem, and dependency resolution when they can affect output.

Commonly used inspection command: `./gradlew generateBuildDescriptor --build-cache --info`. Logs can display `UP-TO-DATE`, `FROM-CACHE`, or task execution; interpret based on actual state without assuming a machine already holds a cache entry.

## 8. Diagnosing symptoms

**Changed flag yet output unchanged or carries old configuration:** search for code reading `System.getenv`, `project.findProperty`, system properties, config files, and command line directly inside the action. Turn the true source into a Gradle property/file input; test the A→B→A case. For artifacts previously cached incorrectly, purge bad entries in the test environment or change the key after fixing the input contract.

**Continuous cache misses:** check for overly broad inputs, absolute paths, files updated by timestamp, unnecessarily changing generated versions, changing classpath/toolchain, or tasks not yet eligible for caching. Inspect `--info` to distinguish uncacheable, missing entry, and changed input.

**Cache hit on another machine yet faulty artifact:** check whether binaries depend on OS, JDK path, hostname, file encoding, or undeclared external environment. Cross-machine caching is only safe if output is compatible across environments treated as equivalent.

**Bytecode changes after upgrading JDK/compiler plugin:** inspect Java toolchain, `options.release`, compiler args, annotation processors, and dependency versions. Do not describe the compiler as having “identical sources” when compilation is additionally affected by toolchains and processors.

**Remote cache returns suspicious artifacts:** control write permissions. Only allow trusted build sources to push artifacts into shared remote caches; do not cache secrets, credentials, or outputs derived from data that should not be shared. Both cache integrity and input declaration correctness are necessary.

## 9. Checklist before marking a task cacheable

- [ ] All sources affecting output, including tools/processors, env, and indirect config, are declared with the proper type.
- [ ] Every output is declared; tasks do not overwrite a shared output directory.
- [ ] Action does not depend on time, randomness, hostname, filesystem order, or unpinned network responses without stable snapshots/versions.
- [ ] Path sensitivity, classpath normalization, line endings, and encoding accurately reflect output semantics.
- [ ] Changing meaningful inputs accurately produces new output; changing irrelevant inputs does not cause unnecessary cache misses.
- [ ] Tested with cache, without cache, restoration after deleting output, and toggling back and forth between configurations A/B.
- [ ] Remote cache has an appropriate trust policy, publishing no artifacts containing secrets or machine-specific dependencies.

**Key takeaway:** the build cache is only safe when its key fully represents the **artifact generation contract**. Missing inputs cause false cache hits; excessive inputs cause unnecessary cache misses. Prove correctness by changing each configuration and comparing actual output contents, rather than relying solely on the `FROM-CACHE` status.
