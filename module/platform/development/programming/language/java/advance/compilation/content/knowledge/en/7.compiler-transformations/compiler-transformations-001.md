# Type erasure and the difference between source types and JVM descriptors

## 1. The big picture: three ways of viewing a declaration

Java allows writing parameterized types, such as `List<String>`, `Box<Integer>`, and `<T extends Number> T get(T value)`. In **source code**, these types help the compiler check type safety, infer types, select methods, control conversions, and detect errors before running. When `javac` compiles, most generic constructs undergo **erasure** (removing type parameters) to produce types that the Java Virtual Machine can operate on via field/method **descriptors**.

Three concepts need to be clearly distinguished:

| Layer | What does it describe? | Example |
| --- | --- | --- |
| **Source-level type** | Types in the Java Language Specification (JLS), including type parameters, wildcards, bounds, and type variables | `List<String>`, `T extends Number` |
| **Descriptor in the class file** | The field/parameter/return type representation that the JVM uses to identify members and link invocations | `Ljava/util/List;`, `()Ljava/lang/Number;` |
| **Generic signature (`Signature` attribute)** | Separate metadata that can preserve generic declarations for the compiler, reflection, and tools | `Ljava/util/List<Ljava/lang/String;>;`, `()TT;` |

**Core point:** *descriptor* and *generic signature* are two different structures. A descriptor uses the JVM grammar and does not encode `List<String>` as a separate runtime type. A `Signature` attribute can record generic parameters at the declaration level, even though the descriptor has been erased. A generic signature does **not** turn into automatic type parameter checks for individual objects at runtime.

This lesson focuses on the difference between source types and descriptors generated by `javac`, along with methods for inspecting them using `javap` on JDK 17+.

## 2. Type erasure rules according to JLS `4.6

Erasure is a mapping from a type (possibly containing type parameters or type variables) to a type **without** type parameters/type variables. For basic cases:

1. **Parameterized type:** the erasure of `G<A, B>` is the erasure of `G`. For example, `List<String>`, `List<Integer>`, and `List<? extends Number>` all become `List` in terms of erasure.
2. **Unbounded type variable:** `T` implicitly has bound `Object`, so its erasure is `Object`.
3. **Bounded type variable:** `T extends Number` becomes `Number`. For `T extends Number & Comparable<T>`, erasure is based on the **first bound**, namely `Number`.
4. **Type variable with an interface as its first bound:** `T extends Comparable<T> & java.io.Serializable` becomes `Comparable`; it does not automatically become `Object` or an intersection type in the JVM.
5. **Array:** erasure is applied to the element type: `T[]` becomes `Object[]` if `T` has no bound; `List<String>[]` becomes `List[]` at the type-representation level (though creating generic arrays has its own restrictive rules).
6. **Types without type parameters/type variables:** remain unchanged, such as `int`, `String`, and `Number`.

Comparison examples:

| Source type | Type after erasure | Corresponding field descriptor |
| --- | --- | --- |
| `String` | `String` | `Ljava/lang/String;` |
| `List<String>` | `List` | `Ljava/util/List;` |
| `Map<String, Integer>` | `Map` | `Ljava/util/Map;` |
| `T` (unbounded) | `Object` | `Ljava/lang/Object;` |
| `T extends Number` | `Number` | `Ljava/lang/Number;` |
| `T extends Number & Runnable` | `Number` | `Ljava/lang/Number;` |
| `List<String>[]` | `List[]` | `[Ljava/util/List;` |
| `T[]` with `T extends Number` | `Number[]` | `[Ljava/lang/Number;` |
| `int[]` | `int[]` | `[I` |

**Distinguish erasure from "removing all type checks."** Checking whether `List<String>` accepts an `Integer` occurs at compile time, according to the language's generic rules. After compilation, the bytecode may need to insert `checkcast` to preserve the type that the source code relied upon. Erasure does not cause Java to ignore generic errors right in valid source code.

## 3. JVM descriptors: grammar and how to read them

The JVM defines field descriptors in JVMS `4.3.2 and method descriptors in `4.3.3. A descriptor is a compact notation string, **completely different from Java source syntax**.

| Java type | JVM descriptor | Meaning |
| --- | --- | --- |
| `byte` | `B` | 8-bit primitive |
| `char` | `C` | character primitive |
| `double` | `D` | double primitive |
| `float` | `F` | float primitive |
| `int` | `I` | int primitive |
| `long` | `J` | long primitive |
| `short` | `S` | short primitive |
| `boolean` | `Z` | boolean primitive |
| `void` (return position of method descriptor only) | `V` | returns no value |
| `java.lang.String` | `Ljava/lang/String;` | object/class, internal name uses `/` |
| `java.util.List` | `Ljava/util/List;` | interface/class |
| `int[]` | `[I` | one-dimensional array |
| `String[][]` | `[[Ljava/lang/String;` | two-dimensional array |

For example, a method descriptor definition has the form:

```text
(DescriptorOfParameter1 DescriptorOfParameter2 ...) ReturnDescriptor
```

There are no commas between parameters. The `(...)` part contains the **actual parameters at the JVM level**, and after `)` is the return type; the method name is stored separately in the class file.

| Java declaration | Descriptor |
| --- | --- |
| `void ping()` | `()V` |
| `int sum(int left, int right)` | `(II)I` |
| `String get(String[] values, int i)` | `([Ljava/lang/String;I)Ljava/lang/String;` |
| `List<String> parse(String input)` | `(Ljava/lang/String;)Ljava/util/List;` |
| `T id(T value)` with unbounded `T` | `(Ljava/lang/Object;)Ljava/lang/Object;` |
| `T id(T value)` with `T extends Number` | `(Ljava/lang/Number;)Ljava/lang/Number;` |

A descriptor **contains the return type**. This differs from how the JLS defines a *method signature* at the source level (name, type parameters, and parameter types after the corresponding rules; it does **not** use the return type to distinguish two overloads in Java). The JVM can contain methods with the same name and parameters whose descriptors differ in the return type; `javac` sometimes needs this capability to generate *bridge methods*. Do not confuse the terms *method signature in the JLS*, *method descriptor in the JVMS*, and *generic `Signature` attribute* just because they all contain the word "signature".

In JVM internal names, `/` separates package components: `java.lang.String` is written `java/lang/String` inside a descriptor. For nested classes, the binary name usually has `$`, for example `LErasureLab$Box;`, instead of the source syntax `ErasureLab.Box`.

## 4. Runnable example: a single file demonstrating erasure, casts, and bridges

Create a file named **`ErasureLab.java`** under the current working directory:

```java
import java.lang.reflect.Method;
import java.util.List;

public class ErasureLab {
    static class Box<T extends Number> {
        private T value;

        Box(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

    static class Parent<T> {
        T get() {
            return null;
        }
    }

    static class Child extends Parent<String> {
        @Override
        String get() {
            return "child";
        }
    }

    static <T> T same(T value) {
        return value;
    }

    static void accept(List<String> values) {
        System.out.println(values.get(0));
    }

    public static void main(String[] args) throws NoSuchMethodException {
        Box<Integer> box = new Box<>(7);
        Integer number = box.get();
        String text = same("hello");
        Parent<String> parent = new Child();

        accept(List.of("java"));
        System.out.println(number);
        System.out.println(text);
        System.out.println(parent.get());

        long bridges = 0;
        for (Method method : Child.class.getDeclaredMethods()) {
            if (method.isBridge()) {
                bridges++;
            }
        }
        System.out.println("bridge=" + bridges);

        Method method = ErasureLab.class.getDeclaredMethod(
                "accept", List.class);
        System.out.println(
                "descriptorParam=" + method.getParameterTypes()[0].getTypeName());
        System.out.println(
                "genericParam=" + method.getGenericParameterTypes()[0].getTypeName());
    }
}
```

Use JDK 17+ and compile targeting release 17:

```bash
javac --release 17 -d out ErasureLab.java
java -cp out ErasureLab
```

**Exact stdout:**

```text
java
7
hello
child
bridge=1
descriptorParam=java.util.List
genericParam=java.util.List<java.lang.String>
```

This example was tested with JDK 21 `javac`. Points to note:

- `Box<T extends Number>` has a field with source type `T`, but the field descriptor uses `Number`.
- `Box<Integer>` returns `Integer` at the call site in source code; when bytecode calls `Box.get()` and receives a JVM-level result of `Number`, the compiler may insert `checkcast java/lang/Integer` to satisfy the source type `Integer`.
- `same(T)` has an unbounded type variable, so the parameter and result descriptors are `Object`; a call assigned to `String` also requires a cast check when needed.
- `Parent<T>.get()` returns `Object` after erasure; `Child.get()` returns `String` in source. The compiler generates an additional **bridge method** returning `Object` so that calls through the type `Parent<String>` continue to dispatch properly.
- `accept(List<String>)` has parameter descriptor `List`, yet generic metadata can still describe `List<String>` for reflection to read via `getGenericParameterTypes()`.

The next section will inspect the generated class file and explain each point.

## 5. Using javap to verify descriptors and the generic Signature

`javap` is a JDK tool for analyzing class files. It does **not** modify source code or recompile; it reads the generated artifacts.

After compiling the `ErasureLab.java` example, run:

```bash
javap -s -p -classpath out ErasureLab
javap -s -p -classpath out 'ErasureLab$Box'
javap -s -p -classpath out 'ErasureLab$Child'
```

Single quotes around `ErasureLab$Box` and `ErasureLab$Child` prevent some shells from interpreting the `$` character as a variable name. The example commands work in POSIX shells and PowerShell; on Windows CMD, double quotes can be used. The actual class files are `ErasureLab$Box.class` and `ErasureLab$Child.class`.

### 5.1. Fields and methods of Box

Relevant portion from `javap -s -p -classpath out 'ErasureLab$Box'`:

```text
private T value;
  descriptor: Ljava/lang/Number;
ErasureLab$Box(T);
  descriptor: (Ljava/lang/Number;)V
T get();
  descriptor: ()Ljava/lang/Number;
```

The line displaying type `T` is `javap`'s presentation format, whereas the **`descriptor`** line is the type used by the JVM. One must not infer that there is a "JVM object of type T" just because `javap` can display the type variable name.

When using verbose mode:

```bash
javap -v -p -classpath out 'ErasureLab$Box'
```

You can find the declaration sections corresponding to the `Signature` attribute, structurally:

```text
field value:
  descriptor: Ljava/lang/Number;
  Signature: TT;

method get:
  descriptor: ()Ljava/lang/Number;
  Signature: ()TT;
```

This is a **summary of the relevant values**, not a verbatim copy of the full `javap -v` output. In the actual output, `javap` also includes constant pool indices, flags, instructions, and attribute locations.

### 5.2. Method with parameterized List

With the declaration:

```java
static void accept(List<String> values) { ... }
```

Relevant portion:

```text
descriptor: (Ljava/util/List;)V
Signature: (Ljava/util/List<Ljava/lang/String;>;)V
```

This is a direct example of the lesson's topic:

- **Source:** `List<String>`, helping the compiler prevent passing incompatible element types.
- **Descriptor:** `Ljava/util/List;`, which does not contain `String`.
- **Signature attribute:** additionally encodes the type argument `String` for reflection and generic-aware tools.

You do not need to know the constant pool index numbers; you only need to compare the two values. If you only view `javap -s`, you may see the descriptor without seeing the detailed generic signature. Use `-v` to read attributes and `-c` to inspect instructions.

### 5.3. Invocations and casts in bytecode

```bash
javap -c -p -classpath out ErasureLab
```

Locate the code section of `main`. For the assignment statements:

```java
Integer number = box.get();
String text = same("hello");
```

The compiler needs to ensure that the results of erased calls match the type expectations in the source. You will typically see instructions corresponding to `checkcast java/lang/Integer` and `checkcast java/lang/String` after invoking methods whose descriptors return `Number` or `Object`. The exact offset positions and instruction ordering are outputs of a specific compiler, not a mandatory rule requiring every Java compiler to emit the exact same bytecode sequence.

**Compiler-generated casts are not meaningless casts.** If the bytecode actually receives an incompatible object at a site where the source relies on `Integer` or `String`, the cast can throw `ClassCastException`.

## 6. Generic Signature attribute: storing metadata, not reifying each instance

JVMS `4.7.9 defines an attribute named **`Signature`**, and `4.7.9.1` defines the generic signature grammar. The Java compiler writes generic signatures for applicable declarations according to JVMS rules: generic classes, generic methods, members with type variables/parameterized types, etc.

For `Box<T extends Number>`, the generic signature of the **class** expresses that type variable `T` has bound `Number` and the class inherits from `Object`, in the form:

```text
<T:Ljava/lang/Number;>Ljava/lang/Object;
```

Different notations:

| Notation | Meaning |
| --- | --- |
| `Ljava/lang/Number;` in a **descriptor** | Reference type named `java.lang.Number` at runtime |
| `T` in source | Type variable named `T`, checked by the compiler against its bound |
| `TT;` in the **generic signature grammar** | Reference to the type variable named `T` |
| `Ljava/util/List<Ljava/lang/String;>;` in a **generic signature** | A parameterized type `List<String>` at the metadata level |

**Do not read Signature attribute grammar as a descriptor.** `TT;` is a TypeVariableSignature, **not** a valid field descriptor. Conversely, `Ljava/util/List;` is the descriptor of the reference type `List`, but cannot record the `<String>` part.

The generic signature helps a compiler later read type information when compiling code that depends on a class file, and enables Java reflection to return generic declarations such as `Method.getGenericParameterTypes()`, `Field.getGenericType()`, or `Class.getGenericSuperclass()`. Reflection **cannot** infer from an arbitrary `new Box<Integer>(7)` object that this instance was declared as `Box<Integer>` in source: an object generally only knows its runtime class `Box`, while the type arguments of variables/expressions are not stored separately per instance.

There are cases where generic information is still known at runtime because the **declaration** has recorded metadata, such as `Child extends Parent<String>`. This is information belonging to the class `Child`, not evidence that the JVM retains the parameterized type of every `Parent<String>` object.

## 7. Bridge methods: why is an extra method added after erasure?

This is an example of the mechanism that preserves polymorphism between source types and JVM descriptors.

Source:

```java
static class Parent<T> {
    T get() {
        return null;
    }
}

static class Child extends Parent<String> {
    @Override
    String get() {
        return "child";
    }
}
```

At the source level, `Child.get()` overrides `Parent<String>.get()`, and its result is treated as `String`. However, after erasure:

- `Parent<T>.get()` has descriptor `()Ljava/lang/Object;`.
- The method declared by the author in `Child` has descriptor `()Ljava/lang/String;`.
- For calls to `Parent`'s method to continue dispatching properly to `Child`, `javac` generates an additional method in `Child` with descriptor `()Ljava/lang/Object;`. This method calls `Child.get()` returning `String` and returns it as `Object`.

With `javap -s -p -classpath out 'ErasureLab$Child'`, the relevant portion is:

```text
java.lang.String get();
  descriptor: ()Ljava/lang/String;

java.lang.Object get();
  descriptor: ()Ljava/lang/Object;
```

Inspect flag information using:

```bash
javap -v -p -classpath out 'ErasureLab$Child'
```

The extra method is marked with **`ACC_BRIDGE`** and **`ACC_SYNTHETIC`**. In the example, reflection calls `isBridge()` and counts one bridge, so stdout outputs `bridge=1`. The order of methods returned by reflection is not an order to rely on; the example only counts them to avoid depending on that order.

**Understand this accurately:** a bridge is a real method in the class file generated by the compiler to preserve the override relationship after erasure (and in other situations such as covariant return). This is not a "valid overload where the author could declare both methods" at the Java source level. The JLS forbids multiple declarations that cause a name clash under erasure rules, even though bytecode can contain different descriptors.

## 8. Name clash: two overloads can collide after erasure

The following snippet **intentionally does not compile**, because the two overloads differ only by type argument:

```java
import java.util.List;

class InvalidOverloads {
    void process(List<String> names) {
    }

    void process(List<Integer> ids) {
    }
}
```

After erasure both have parameter descriptor `(Ljava/util/List;)`; both return `void`, so the method descriptor of both is `(Ljava/util/List;)V`. Java will report a name clash error because they cannot be distinguished by parameter types after erasure.

One way to fix this is to choose two method names reflecting different functionalities:

```java
import java.util.List;

class DistinctMethods {
    void processNames(List<String> names) {
    }

    void processIds(List<Integer> ids) {
    }
}
```

You can also design a generic API `process(List<T>)` if the two operations truly share the same semantics. But do not think that using two different type arguments for the same `List` will create two separate runtime methods.

**Distinguish from two overloads that remain valid after erasure:** `process(String)` and `process(Integer)` have different parameter descriptors, so they can coexist. When complex generics are involved, Java also applies *subsignature* and *override-equivalent* rules; merely "looking different to the eye in source" is not enough to guarantee a valid overload.

## 9. Casts, heap pollution, and runtime checking limitations

### 9.1. Cannot fully check type arguments with instanceof

`List<String>` is not a reifiable type. Therefore the following **intentionally invalid** snippet:

```java
import java.util.List;

class InvalidCheck {
    boolean check(Object value) {
        return value instanceof List<String>;
    }
}
```

will be rejected at compile time. You can check `value instanceof List<?>` (a parameterization using only unbounded wildcards is reifiable), or check `value instanceof List` at the raw type level. However, these checks do not prove that all elements in the list are `String`.

### 9.2. Unchecked conversion can cause errors to appear late

This example is a runnable Java program written **intentionally unsafe** to demonstrate the limitation:

```java
import java.util.ArrayList;
import java.util.List;

public class HeapPollutionDemo {
    public static void main(String[] args) {
        List raw = new ArrayList<String>();
        raw.add(42);
        List<String> strings = raw;

        try {
            String first = strings.get(0);
            System.out.println(first);
        } catch (ClassCastException ex) {
            System.out.println("ClassCastException");
        }
    }
}
```

```bash
javac --release 17 -Xlint:unchecked HeapPollutionDemo.java
java HeapPollutionDemo
```

Program stdout:

```text
ClassCastException
```

`javac -Xlint:unchecked` may print warning diagnostics (stderr; exact wording depends on the JDK), because `raw.add(42)` and the assignment from raw to `List<String>` are not fully checked. When `strings.get(0)` is used as a `String`, the compiler-inserted cast can fail because the actual element is an `Integer`.

**Type erasure does not make `List<String>` "completely safe at runtime."** Type safety is designed around compile-time checks and necessary casts. Raw types, unchecked operations, reflection, native/unsafe code, or incompatible binaries can violate source type assumptions.

### 9.3. Related limitations

- You cannot directly create `new List<String>[10]` because generic array creation is restricted.
- You cannot write `new T()` with a type variable `T` just because its bound is known; erasure does not turn a type parameter into a usable constructor.
- You cannot write `List<String>.class`; `List.class` exists, but there is no separate `Class` object for each type argument of `List`.
- Some declarations using wildcards or array types remain reifiable according to JLS `4.7; one should not overgeneralize that "no generic type can be checked at runtime."
- Java reflection can see the **generic type of a declaration** from the `Signature` attribute; that capability is different from checking the type argument of each individual instance.

## 10. Relationship to overload resolution, binary APIs, and linkage

### 10.1. Overloads are selected at compile time

With source code `List<String> names`, `javac` uses the full parameterized type to detect unsafe operations. When multiple overloads exist, the compiler applies candidate checking and most-specific method rules according to the JLS; it does not simply "select based on the JVM descriptor string."

Once compiled, an invocation holds a symbolic reference to a method with the corresponding name and descriptor in the class file. If the binary API is later changed without recompiling the client, the program may encounter linkage errors, such as `NoSuchMethodError`, when the method with the descriptor expected by the client no longer exists.

### 10.2. Changing type arguments does not necessarily change the descriptor

For example, changing the declaration `void read(List<String> values)` to `void read(List<Integer> values)` leaves the **parameter descriptor as `Ljava/util/List;`**, but the source type rules and generic `Signature` attribute may differ. Therefore, comparing descriptors alone is not enough to confirm that a library's generic API has remained unchanged.

Conversely, changing the bound of a type variable can change the erasure and descriptor. For example:

```java
class Before<T> {
    T get() {
        return null;
    }
}

class After<T extends Number> {
    T get() {
        return null;
    }
}
```

`Before.get()` returns `Object` in its descriptor; `After.get()` returns `Number`. These are **two different illustrative classes**; if the bound of an already-released API is changed, the runtime signature may change, so binary compatibility must be checked. Do not conclude that modifying a generic bound always has only a compile-time impact.

### 10.3. JVM descriptors and generic Signatures do not play equal roles

- The JVM uses **descriptors** to describe member parameter/return types, perform verification, link symbolic references, and execute invocations.
- The generic **`Signature` attribute** contains metadata supporting generic declarations. The compiler/reflection can use that information, but it does not create distinct runtime class sets for `List<String>` and `List<Integer>`.
- Bridge methods have separate descriptors to maintain dispatch when source types and erased types would cause methods to be mapped differently.

Therefore, when debugging `NoSuchMethodError` or ABI differences, check the **descriptor** first; when debugging a library with incorrect generic declarations, check the **Signature** and source API as well.

## 11. Investigation workflow using javap

When encountering a case where "the type in source does not match what appears in bytecode," proceed in order:

1. **Record the source declaration:** type parameters, bounds, wildcards, return type, and parameter types; identify overloads/overrides.
2. **Apply JLS `4.6:** replace each type variable with the erasure of its first bound, erase parameterized types, and apply erasure to arrays.
3. **Convert to descriptor grammar:** primitives become single characters, objects become `L...;`, arrays are prefixed with `[`, and methods have `(...)return`.
4. **Compile with a fixed toolchain:** for example `javac --release 17 -d out ErasureLab.java`.
5. **Inspect `javap -s -p`:** read descriptors of fields/constructors/methods, including non-public members.
6. **Inspect `javap -v -p`:** read the `Signature` attribute, and `ACC_BRIDGE`/`ACC_SYNTHETIC` flags if present.
7. **Inspect `javap -c -p`:** look for compiler-generated casts and invocations; do not assume another compiler must generate identical instruction offsets.
8. **Cross-check behavior and API:** run the program, check reflection, and try compiling a client; clearly note what is guaranteed by the JLS/JVMS and what is the code generation form of a specific `javac` version.

Quick reference table:

| Observation | Tool/source |
| --- | --- |
| Is Java source `List<String>` valid? | JLS: generic types, assignment, method invocation |
| What type does type variable `T` erase to? | JLS `4.6, check the first bound |
| What are the JVM method parameters/return type? | `javap -s -p`, JVMS `4.3.3` |
| What generic metadata remains? | `javap -v -p`, `Signature` attribute in JVMS `4.7.9` |
| Is there a compiler-generated bridge? | `javap -v -p` flags; reflection `Method.isBridge()` |
| Why does `checkcast` appear? | `javap -c -p` and JLS conversion/typing rules |
| Does runtime know `List<String>` for each object? | Reifiable types (JLS `4.7) and erasure limits |

## 12. Common misconceptions

| Misconception | Accurate understanding |
| --- | --- |
| "Generics completely disappear from class files." | Descriptors are erased, but the `Signature` attribute can store generic declarations. |
| "`List<String>` and `List<Integer>` will have different JVM classes." | They share the same runtime class `List`/implementation; type arguments do not create separate classes. |
| "`TT;` is the field descriptor for type variable `T`." | `TT;` belongs to the generic signature grammar; the descriptor uses the erasure of the bound. |
| "Erasure always replaces `T` with `Object`." | Only true for type variables without an explicit bound; `T extends Number` becomes `Number`. |
| "Java method signatures always include the return type because JVM descriptors have a return type." | The two terms are at different layers; Java overloads are not distinguished solely by return type. |
| "A bridge is a method that programmers must write manually." | `javac` generates bridges when needed to preserve override/dispatch after applicable transformations. |
| "Reflection cannot read any generics." | Reflection can read the `Signature` of declarations; it cannot reconstruct erased type arguments of every instance. |
| "A cast in bytecode means the source contains an explicit cast." | The compiler can insert `checkcast` due to erasure to satisfy the expression's type. |
| "Generic types allow `instanceof List<String>`." | This parameterized type is not reifiable, so such a check is invalid. |
| "Two source APIs with the same descriptor have identical generic APIs." | Type arguments/bounds in `Signature` and source type rules can still differ. |

## 13. Self-check exercises

**Exercise 1.** For the declaration `class Store<T extends CharSequence> { T read(); }`, what is the descriptor of `read()`?

**Answer:** `()Ljava/lang/CharSequence;`. The erasure of `T` is its first bound `CharSequence`, not `Object`.

**Exercise 2.** Can two methods `save(List<String>)` and `save(List<Integer>)` overload in the same class?

**Answer:** No. Both parameter types erase to `List`; the two methods have the same name and erased signature, so a name clash occurs.

**Exercise 3.** What is the return descriptor of source `Map<String, List<Integer>> lookup()`?

**Answer:** `()Ljava/util/Map;`. The generic signature can retain the `String` and `List<Integer>` declaration; the descriptor only keeps raw `Map`.

**Exercise 4.** What does `T extends Runnable & AutoCloseable` erase to?

**Answer:** `Runnable` because that is its first bound; the corresponding field descriptor is `Ljava/lang/Runnable;`. Both bounds still exist at the source level.

**Exercise 5.** Why can `Child extends Parent<String>` have two `get()` methods in the class file, one returning `String` and one returning `Object`?

**Answer:** The compiler can generate a bridge `get():Object` (marked `ACC_BRIDGE`, `ACC_SYNTHETIC`) to maintain polymorphic dispatch to the `get():String` method after erasure.

**Exercise 6.** `javap -s` only shows `List`. Does that prove the `.class` file does not record `String` from `List<String>` at all?

**Answer:** No. You need to read the `Signature` attribute with `javap -v`; the descriptor and generic signature store two different kinds of information.

**Exercise 7.** Why can `List<String> strings = rawList; String s = strings.get(0);` throw `ClassCastException`?

**Answer:** An unchecked conversion from a raw list can put an element of the wrong type into the collection; reading the result as `String` causes the compiler-inserted cast to fail if the object is not a `String`.

- **JLS Java SE 21 `4.7 — Reifiable Types:** https://docs.oracle.com/javase/specs/jls/se21/html/jls-4.html#jls-4.7 — types that can be fully recognized at runtime.
- **JVMS Java SE 21 `4.3.2, `4.3.3:** https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.3 — field and method descriptors.
- **JVMS Java SE 21 `4.7.9 — The Signature Attribute:** https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.7.9 — generic signatures stored in class files.
- **JDK 21 javap tool reference:** https://docs.oracle.com/en/java/javase/21/docs/specs/man/javap.html — using `-s`, `-p`, `-v`, and `-c` to inspect artifacts.

**Key takeaway:** reading a generic Java method requires separating **the source type checked by the JLS**, **the erased type represented by the JVM via descriptors**, and **the additional generic metadata in the Signature attribute**. When these three layers are clearly distinguished, you will understand why the compiler inserts casts, why it generates bridge methods, and why the same descriptor can still correspond to different generic declarations.
