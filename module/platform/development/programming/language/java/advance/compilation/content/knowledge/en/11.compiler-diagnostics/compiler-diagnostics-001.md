# Reading Locations, Error Codes, and Context of Java Compilation Messages

When **javac** fails to compile a Java file, the error message is not simply an English sentence. A diagnostic usually contains multiple clues: **source file**, **line/column**, **message kind**, **code snippet of concern**, **position marker**, **reason for the compiler check**, and sometimes **details about the symbol, type, or method signature**.

Learning how to read these parts in order helps fix the right issue instead of guessing and changing multiple code segments at once. This topic belongs to the **compilation error diagnosis** phase: the focus is on understanding compiler messages, tracing back to the source code context, and distinguishing root errors from cascading errors. This lesson uses tools available from **JDK 17+**.

## 1. What Is a Diagnostic?

A **diagnostic** is a message generated by the compiler when analyzing source code or performing a compilation-related step. A diagnostic can be:

- **Error**: an issue that causes the compilation step to fail, such as invalid syntax, a symbol not found, or incompatible types.
- **Warning**: code can still be compiled, but the compiler warns about a risk or issue needing attention, such as a raw type or an unchecked operation.
- **Note / additional information**: an explanation about context, the possibility of using another option, annotation processing, or related issues.

When reading the output, always ask **what is the compiler trying to do at that location?** For example, a variable declaration may be syntactically valid but have the wrong type. In another case, the name of a class is correct, but the compiler cannot find the JAR or module containing that class. They may produce similar English sentences, yet the ways to handle them are different.

**A diagnostic message does not necessarily have every field.** An error directly related to source code usually has a specific location. A general warning about compiler options, classpath, or annotation processors might not be attached to any line/column in a file.

## 2. Structure of a Typical javac Message

Create the file **Broken.java** with the following content:

~~~java
public class Broken {
    public static void main(String[] args) {
        int total = 10;
        System.out.println(totla);
    }
}
~~~

The declared variable name is **total**, but the print statement uses **totla**. Run:

~~~bash
javac Broken.java
~~~

A JDK build displaying English diagnostics may produce equivalent output:

~~~text
Broken.java:4: error: cannot find symbol
        System.out.println(totla);
                           ^
  symbol:   variable totla
  location: class Broken
1 error
~~~

The example above illustrates a **common message shape**, without guaranteeing every space, displayed column, or line break remains identical across JDK versions, locales, and terminal formatting.

Analyzing each part:

| Part | Illustrative Value | Meaning |
| --- | --- | --- |
| **File** | Broken.java | Source file related to the diagnostic |
| **Line** | 4 | Location associated with the error by the compiler |
| **Severity** | error | This is a compilation error, not just a warning |
| **Main message** | cannot find symbol | Could not resolve a name in this context |
| **Source line** | System.out.println(totla); | The code snippet that caused the compiler to report the issue |
| **Caret** | ^ under totla | Points to the token/location the compiler is marking |
| **symbol** | variable totla | The symbol being searched for is a variable named totla |
| **location** | class Broken | The scope or location where the name search occurred, mentioned by the compiler |
| **Summary** | 1 error | Number of error diagnostics reported by the tool in the run |

**Do not mechanically conclude "line 4 is always the root cause".** The compiler marks where it detects a conflict; the declaration causing the error may lie earlier, in another file, or in a dependency. For this example, comparing **total** and **totla** is enough to spot the typo.

### 2.1. Line Numbers and Column Numbers

In the text-based diagnostic pattern **Broken.java:4: error...**, the number **4** is the line. For many standard javac diagnostics, the column position is represented by a caret under the source snippet, without necessarily having an explicit column number written in the header. IDEs and the Java Compiler API may provide separate column numbers.

When using the Java Compiler API:

- **getLineNumber()** and **getColumnNumber()** return positions following the API's line/column convention, starting from **1** for valid positions.
- **getPosition()** returns the character offset from the start of the source object, starting from **0**.
- If the compiler has no suitable position, the API returns **Diagnostic.NOPOS** for those position details.
- **getStartPosition()**, **getPosition()**, **getEndPosition()** allow tools to highlight source ranges; you should not infer an exact range from a single caret character alone.

Do not confuse a compiler column with pixel position in an IDE. **Tabs**, Unicode characters, variable-width fonts, CRLF, and terminal rendering can make the visual position differ from the tool's character/offset position. If the caret looks misaligned, open the file in whitespace-visible mode or view the position via an IDE.

### 2.2. Relative and Absolute Paths

Depending on how it is invoked, a diagnostic may use a filename like **Broken.java**, a relative path like **src/main/java/app/Broken.java**, or a longer path. If compiling multiple sources with the same name, pay attention to the **full path in the message** rather than just the final name.

When running in Gradle/Maven or CI, the working directory may differ from your terminal. Check the actual compilation command used by the build tool; do not assume the diagnostic path is always calculated from the current directory open in the IDE.

## 3. The Caret Points to Where It Was Detected, Not Always Where to Fix

The compiler performs multiple steps: reading characters, tokenizing, building the syntax tree, resolving names, type checking, flow analysis, and several related checks. At each step, it chooses a **meaningful source position** to attach the diagnostic.

Example of a missing separator error:

~~~java
public class MissingSemicolon {
    public static void main(String[] args) {
        int a = 10
        System.out.println(a);
    }
}
~~~

The compiler may mark the **System** token on the next line, because that is where it realizes the previous declaration line did not end with **;**. The right fix is adding a semicolon after **10**, not deleting System.

Another case:

~~~java
class WrongType {
    public static void main(String[] args) {
        int count = "five";
    }
}
~~~

This is a **type error**, not a character or brace error. The compiler may highlight the expression **"five"**, but the cause is that the **int** declaration is incompatible with a **String** value.

**Procedure when the caret does not seem to point directly to the cause:** read a few lines before and after, check parentheses/semicolons, inspect the declaration of the related symbol, and examine the expression's type. The diagnostic location is the **starting point of an investigation**, not an order to edit the exact character being pointed to.

## 4. Distinguishing "Error Codes" from Message Sentences and Warning Labels

In javac, there are usually at least three concepts that should be kept separate:

1. **The human-readable message**: such as **cannot find symbol**, **incompatible types**, **';' expected**. The text may vary by version and display language.
2. **The diagnostic code**: a string provided by the compiler, retrieved via **javax.tools.Diagnostic.getCode()** or a mechanism for tools. This value is **implementation-dependent**, not a universal standard set of error numbers for every Java compiler.
3. **The warning group (lint category)**: for example **[unchecked]**, **[rawtypes]**, **[deprecation]** when the appropriate lint option is enabled. This is a warning classification label, not synonymous with a full diagnostic code.

For example, when javac cannot resolve a variable, the visible message may be **cannot find symbol**; for tools using javac, the diagnostic code may take a form prefixed with **compiler.err.**. You should not hardcode a specific code and assume every javac build, IDE, Eclipse compiler, and build system must return the same string.

**Messages are not stable error codes for programs to parse.** If automation is needed, prefer structured APIs with **Diagnostic.Kind**, position, source, and diagnostic code if supported. If storing codes to analyze error trends across multiple JDKs, also record **vendor, javac version, options, and language** to avoid misinterpretation.

### 4.1. Errors, Warnings, and Notes

| Group | Meaning | Forces Compilation to Fail? |
| --- | --- | --- |
| **ERROR** | A compilation rule was violated | Yes |
| **WARNING** | An issue the compiler warns about; class files may still be generated | Normally no; **-Werror** can turn warnings into a compile step failure |
| **MANDATORY_WARNING** in the API | A mandatory type of warning according to tool/language rules | Not automatically synonymous with a compile error |
| **NOTE** | Additional information | No |
| **OTHER** | A message type not belonging to the specific groups above | Must inspect the actual message |

**Having class files does not mean there are no warnings.** Conversely, when using **-Werror**, the compiler may terminate compilation unsuccessfully due to warnings even if the source has no normal syntax errors.

## 5. Common Error Groups and How to Read Context

### 5.1. "cannot find symbol"

Example:

~~~java
class NameError {
    void show() {
        System.out.println(userNmae);
    }
}
~~~

In the context above, the compiler cannot find the variable **userNmae**. You need to check:

- Whether the variable is declared; whether there is a typo or a difference in uppercase/lowercase?
- Whether the variable is in scope at the point of use?
- For a method or class, whether the name, import, receiver type, and classpath/module path are correct?
- Whether a member is being called on the wrong object or on a type that does not provide that method?

**Do not automatically add an import** when the diagnostic is talking about a **local variable**. The **symbol: variable ...** field differs from **symbol: class ...** or **symbol: method ...**, so read the symbol/location section before fixing.

### 5.2. "incompatible types"

Example:

~~~java
class TypeError {
    String name = 42;
}
~~~

The compiler sees an integer value where a **String** is needed. You must read both sides: **required** (expected type) and **found/provided** (actual type), or equivalent phrasing in the diagnostic. The issue may lie in:

- The type of the variable receiving the result;
- The return value of a method;
- The generic type in a collection;
- The overload being selected;
- An automatic type conversion not allowed by Java.

Do not fix this with an arbitrary cast. Determine the contract first: should the variable be a String, or must the data actually be converted into a String?

### 5.3. "';' expected", "')' expected", "reached end of file while parsing"

These are usually syntax errors. Check:

- Semicolons after statements;
- Pairs of parentheses, square brackets, and curly braces;
- String quotes or char literals;
- Structure of if, for, method, class;
- A token on a previous line causing the parser to misinterpret the subsequent part.

Example:

~~~java
class UnclosedBlock {
    void run() {
        System.out.println("Hello");
    // Missing curly braces to close method and class.
~~~

Depending on the exact structure, the compiler may report at the end of the file because the parser has not received the necessary closing parts. Fix at the **origin of the brace imbalance**, not by adding arbitrary characters at the end of the file just to silence a message.

### 5.4. "package ... does not exist" or Package Not Visible

If the source contains:

~~~java
import example.library.Widget;
~~~

and javac cannot find the library, check **dependencies and compile classpath/module path**. When running under JPMS, errors about a package **not visible** may relate to **requires** or **exports**, not just a missing JAR.

**Imports do not download libraries.** A properly spelled import line still does not make the class appear on the classpath. When classifying the error, separate the question "is the type found?" from "is the type accessible?".

### 5.5. Overload and Method Parameter Errors

Messages such as **method ... cannot be applied to given types** are often accompanied by **required**, **found**, **reason** sections, or a list of **candidate methods**. Compare:

- Number of arguments;
- Order and type of each argument;
- Generic type arguments;
- Whether the constructor/method is public and accessible;
- Static/instance context;
- Whether any overload is applicable under Java's type conversion rules?

If the diagnostic is long, use **-Xdiags:verbose** (section 7) to expand the context. Be careful when using an IDE's automatic code fix if it changes the method contract just to match an incorrect call.

## 6. One Root Error Can Trigger Many Cascading Messages

A syntax error early in a file can cause the parser to misread subsequent lines. A missing type can cause many expressions using that type to continue failing type checks. Therefore, the output may contain dozens of diagnostics without meaning there are dozens of independent causes.

Illustrative example:

~~~java
class CascadingErrors {
    void run() {
        UnknownType item = new UnknownType();
        System.out.println(item.value());
    }
}
~~~

If **UnknownType** has no declaration or dependency, the compiler cannot reliably determine the type and the **value()** method. Fix or add the proper type before evaluating subsequent messages; the diagnostic list in the next compilation run may change.

A useful approach:

1. Read the **first sufficiently specific diagnostic**, including file, position, and message.
2. Inspect a few surrounding lines and related declarations.
3. Fix one evidence-backed cause.
4. Recompile, and see what messages remain.
5. Only address warnings after understanding the errors that block analysis.

**Do not rigidly apply "always fix line 1 in the list".** When the compiler processes multiple files or annotation processors, the order of diagnostics may not match the causal dependency order. A foundational dependency error may be more important than the first few error lines reported in downstream source.

## 7. javac Options That Help Read Diagnostics in More Detail

### 7.1. Showing More Details with -Xdiags

Try:

~~~bash
javac -Xdiags:verbose Broken.java
~~~

**-Xdiags:verbose** selects a more detailed diagnostic mode, useful when a method call or generic type inference has many candidates. It can be compared with:

~~~bash
javac -Xdiags:compact Broken.java
~~~

The two options control **how diagnostics are presented**, do not modify code, and do not themselves change Java's type rules. It is not guaranteed that every simple error like a typo will have a significantly different message between the two modes.

### 7.2. Enabling Warning Groups with -Xlint

Create **WarningSample.java**:

~~~java
import java.util.List;

public class WarningSample {
    List values;
}
~~~

Compile:

~~~bash
javac -Xlint:rawtypes WarningSample.java
~~~

The compiler may report a **[rawtypes]** warning at the **List values** declaration because the generic type List was used without type arguments. To see more warning groups:

~~~bash
javac -Xlint:all WarningSample.java
~~~

**-Xlint:rawtypes** and **-Xlint:unchecked** are two different groups; a raw declaration can appear without a specific unchecked invocation. When receiving a warning, read both the **lint label**, the source line, and the explanation.

You can view the lint groups supported by the JDK version with:

~~~bash
javac --help-lint
~~~

Do not assume every JDK has the same set of warning categories or enables the same groups by default. Lint parameters help ask clearer diagnostic questions, rather than automatically turning a validly compiled logic error into a type error.

### 7.3. Turning Warnings into Build Failures with -Werror

~~~bash
javac -Xlint:rawtypes -Werror WarningSample.java
~~~

**-Werror** instructs javac to treat warnings as a condition that causes the compilation task to fail. In the example with raw List, the compile step will not be considered successful when the warning is detected. This usage suits CI when a project needs to keep new warnings under control.

Distinguish:

- **Detected error**: a language rule was violated.
- **Warning causing failure due to -Werror**: the source is permitted by the core rules, but the build policy does not accept warnings.

Do not say a warning has "turned into a syntax error" just because -Werror causes a non-zero exit code.

### 7.4. Limiting the Number of Displayed Messages

For projects producing many errors, you can adjust:

~~~bash
javac -Xmaxerrs 20 -Xmaxwarns 20 Broken.java
~~~

These two options limit **the number of printed errors/warnings**, without removing causes in the source and without fixing compilation. When only a few messages appear, do not conclude that the rest do not exist.

When handling a heavily broken codebase, you can limit output for readability, fix root errors, and then rerun with full output before concluding success.

### 7.5. Internal Diagnostic Codes and Stability Limits

Some javac builds have internal modes like **-XDrawDiagnostics** to display message keys intended for diagnostics/compiler testing. This is **not a stable message interface for production applications to depend on**; if researching, inspect the specific JDK build and do not claim keys like **compiler.err...** are a universal standard of the Java language.

If you want to collect diagnostics in an official Java tool, the better choice is the **Java Compiler API** and **DiagnosticCollector**, as in section 9.

## 8. Reading Compilation Logs in IDEs, Maven, Gradle, and CI

Each tool may wrap javac messages with its own logs. For instance, a build tool may prepend task paths, timestamps, severity indicators, or error count summaries. You must **separate the tool's log layer from the original diagnostic**.

Illustrative format example, not an exact log of every version:

~~~text
> Task :compileJava FAILED
.../src/main/java/app/Broken.java:4: error: cannot find symbol
        System.out.println(totla);
                           ^
...
~~~

Here **compileJava FAILED** indicates that Gradle's task failed; meanwhile, **Broken.java:4: error: cannot find symbol** is the information that helps identify the source error. If Maven/Gradle uses a different compiler or a custom formatter, messages and locations may be phrased differently.

Diagnostic steps:

1. **Confirm the task/module being compiled**: many projects have identical filenames in main/test or multiple subprojects.
2. **Record the actual JDK and compiler used**: a terminal using a different JDK from the IDE/CI will have differences in APIs and messages.
3. **Find the original diagnostic** before reading a long build tool stack trace summary.
4. **Open the right source revision**: CI logs may correspond to a different commit from the file currently on your machine.
5. **Check dependency root causes** if many classes are not found.
6. **Recompile after fixing** and record the exit status to confirm.

**Runtime exceptions are not compile diagnostics.** Stack traces like **NullPointerException** or **ClassNotFoundException** during execution indicate runtime errors, differing from javac messages during compilation. However, a build tool can also throw an exception during the build process itself, so look at the task and when it occurred.

## 9. Reading Structured Diagnostics via the Java Compiler API

When writing IDE plugins, source inspection tools, or grading systems, you may need structured information instead of parsing stderr strings. Java provides **javax.tools.JavaCompiler**, **javax.tools.Diagnostic**, **DiagnosticListener**, and **DiagnosticCollector**.

Useful fields of **Diagnostic**:

| API | Meaning |
| --- | --- |
| **getKind()** | ERROR, WARNING, MANDATORY_WARNING, NOTE, or OTHER |
| **getSource()** | Related source object; may be null if not attached to a source |
| **getLineNumber()** | Line number when a position is available |
| **getColumnNumber()** | Column number when a position is available |
| **getPosition()** | Offset of the diagnostic position in the source |
| **getStartPosition(), getEndPosition()** | Position range for highlighting |
| **getCode()** | Implementation-provided code; may be null |
| **getMessage(Locale)** | Message that may be localized; content is compiler-dependent |

Use **getKind**, position, and source to build an error viewer; store **getCode** if useful, but do not use it as the sole key determining behavior across all compilers.

### 9.1. Standalone Example: Collecting Errors Without Parsing stderr

Create the file **CompileReport.java**:

~~~java
import java.net.URI;
import java.util.List;
import javax.tools.Diagnostic;
import javax.tools.DiagnosticCollector;
import javax.tools.JavaCompiler;
import javax.tools.JavaFileObject;
import javax.tools.SimpleJavaFileObject;
import javax.tools.ToolProvider;

public class CompileReport {
    static final class MemorySource extends SimpleJavaFileObject {
        private final String content;

        MemorySource(String name, String content) {
            super(
                URI.create("string:///" + name),
                JavaFileObject.Kind.SOURCE
            );
            this.content = content;
        }

        @Override
        public CharSequence getCharContent(boolean ignoreEncodingErrors) {
            return content;
        }
    }

    public static void main(String[] args) {
        String source = String.join("\n",
            "public class Broken {",
            "    public static void main(String[] args) {",
            "        int total = 10;",
            "        System.out.println(totla);",
            "    }",
            "}"
        );

        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null) {
            System.out.println("Cần chạy bằng JDK đầy đủ");
            return;
        }

        DiagnosticCollector<JavaFileObject> collector =
                new DiagnosticCollector<>();

        JavaCompiler.CompilationTask task = compiler.getTask(
            null,
            null,
            collector,
            List.of("--release", "17", "-proc:none"),
            null,
            List.of(new MemorySource("Broken.java", source))
        );

        Boolean successful = task.call();
        System.out.println("success=" + successful);

        for (Diagnostic<? extends JavaFileObject> d
                : collector.getDiagnostics()) {
            System.out.println(
                d.getKind() + " line " + d.getLineNumber()
            );
        }
    }
}
~~~

Compile and run on a JDK that supports **--release 17** (for example JDK 17 or JDK 21):

~~~bash
javac CompileReport.java
java CompileReport
~~~

Expected output for the example with a standard javac compiler:

~~~text
success=false
ERROR line 4
~~~

**Why is the result predictable?** The in-memory source has the Broken class and exactly one reference to the undeclared variable **totla** on line 4. The compiler is instructed not to run annotation processors via **-proc:none**, so no generated code alters the situation. The API collector receives the diagnostic instead of just relying on the compiler's stderr.

**Example scope:** The CompileReport program is standalone runnable code. It intentionally **compiles an invalid Broken.java snippet in memory**, so the success result is false; **CompileReport.java** itself must still compile successfully. If using a Java runtime image that omits **jdk.compiler**, ToolProvider may not provide the system JavaCompiler. Use a full JDK.

You can extend the loop to read more data:

~~~java
// Illustrates loop body: not a standalone program.
System.out.println("column=" + d.getColumnNumber());
System.out.println("code=" + d.getCode());
System.out.println("message=" + d.getMessage(java.util.Locale.ENGLISH));
~~~

With the code version above, add these three statements **inside the for loop** when needed. The contents of **code** and **message** are compiler-dependent information; you should not hardcode a fixed stdout for them.

### 9.2. A Diagnostic May Have No Position

Not every message comes with a source location. When integrating the API, check:

~~~java
// Illustrates when variable d has type Diagnostic<? extends JavaFileObject>.
if (d.getPosition() == Diagnostic.NOPOS) {
    System.out.println("Không có vị trí nguồn cụ thể");
}
~~~

If there are no sources, **getSource()** may return null. Therefore, a diagnostic storage system should allow **source, line, column** to be absent, instead of assuming every warning belongs to a line in a .java file.

### 9.3. Notes on Diagnostic Codes

**Diagnostic.getCode()** returns an implementation-defined code. It can be used to group messages within one javac version, but when upgrading the JDK or switching compilers, verify the mapping again. Localization can change the language of **getMessage(Locale)** while the diagnostic code stays in the same form within one implementation; do not use the English message text as a mandatory machine protocol.

## 10. Practical Scenario: Read, Verify, Fix, Recompile

Consider the code snippet:

~~~java
import java.util.List;

public class OrderReport {
    public static void main(String[] args) {
        List<String> names = List.of("An", "Binh");
        System.out.println(names.get(2));
    }
}
~~~

**This example compiles successfully.** The latent error here is **IndexOutOfBoundsException at runtime**, because the list only has two elements at indices 0 and 1. Do not expect javac to report an error about get(2): the compiler cannot infer all runtime state from this general call. The goal is to distinguish errors not reported by the compiler from compile diagnostics.

Conversely, change it to:

~~~java
// Code snippet illustrating a type error, not a standalone program.
List<String> names = List.of("An", "Binh");
names.add(42);
~~~

The compiler has sufficient static information to report a parameter type error: **add(String)** does not accept int/Integer. The right diagnostic conclusion is to fix the element type or the data being added, not trying to add imports or classpath entries.

### 10.1. Five-Question Process Template

When encountering a diagnostic, answer in order:

1. **Where?** The exact file, line, column, or token being pointed to; is it the right code revision?
2. **What severity?** ERROR, WARNING, or NOTE; is there a **-Werror** policy?
3. **What is the compiler saying?** Read the main message, symbol, required/found, location, method candidates, and note lines.
4. **Why in this context?** Check scope, declarations, types, package/module, dependencies, or preceding syntax.
5. **Proof that the fix is done?** Recompile with the same JDK/options, check whether any diagnostics remain, and run tests if the program can compile.

You should not look only at the **1 error** line at the end of the log; that is an **aggregate summary**, which does not state which class the error belongs to.

## 11. Common Diagnostic Mistakes

**Mistake 1 — Fixing right at the caret position without reading the previous line.** A missing semicolon on line 3 can cause an error at a token on line 4. You must read the entire open statement.

**Mistake 2 — Seeing cannot find symbol and immediately adding an import.** If the symbol is a misspelled local variable, an import does nothing. If the symbol is a class from a dependency, besides the name, you also need to check the classpath/module path.

**Mistake 3 — Reading only the first line of a multi-line diagnostic.** The **symbol, location, required, found, reason** parts may be the decisive facts needed for a proper fix.

**Mistake 4 — Treating all warnings as errors.** Warnings usually do not block compilation unless the build policy sets **-Werror** or another tool handles them. Yet do not ignore warnings because of that.

**Mistake 5 — Treating javac error codes as standardized Java ID numbers.** Diagnostic codes are implementation-dependent; different compilers may use different codes.

**Mistake 6 — Copying a diagnostic verbatim from CI and comparing it against a file from a different commit.** The error output corresponds to the revision at compile time. Check the branch/commit before relying on line numbers.

**Mistake 7 — Fixing one diagnostic at a time out of 100 errors without checking the root error.** When an important type is missing, many subsequent messages can be consequences. Fix the common cause first.

**Mistake 8 — Confusing a runtime stack trace with a javac error.** You must distinguish whether the compiler is analyzing source code or the JVM is executing the application.

**Mistake 9 — Reading the caret as an absolute column number across all tools.** Terminals, IDEs, and the compiler API have different position display rules. When positions are needed for an editor, use a structured API.

**Mistake 10 — Suppressing warnings without understanding them.** Annotations or build options may suppress a warning category; that does not prove the source is safe.
