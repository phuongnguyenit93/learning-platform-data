# Ensuring Idempotency When Tasks May Be Re-executed

In a concurrent system, a task may be submitted twice, retried after a timeout, re-executed on process startup, or picked up by two workers almost simultaneously. Proper design must ensure that **a repeated business request does not produce unintended side effects**, even when we cannot control how many times the code executes. This applies to Java in general (threads, executors, queues, databases, external APIs), without depending on Spring.

## 1. What Does Idempotency Really Mean?

An operation `f` is idempotent with respect to business state if applying it multiple times with the same intent produces an observable result equivalent to applying it once: `f(f(s)) = f(s)`. "Same intent" must be identified by a stable **idempotency key**, not by the number of method invocations. For example:

| Operation | On re-execution | Remarks |
|---|---|---|
| `order.status = SHIPPED` with the same valid version/condition | Status remains `SHIPPED` | Can be idempotent |
| `balance += 100` | Balance continues to increase | Not idempotent |
| `sendEmail()` | Sends another email | Not idempotent without deduplication at the sender |
| `INSERT event` with a unique `event_id` and ignoring duplicate records | Creates no extra records | Idempotent within that table's boundary |
| `UPSERT` that updates `updated_at` or emits an event every time | Produces new side effects | Not yet idempotent in overall behavior |

Distinguish the concepts:

- **Idempotency:** retrying the same request causes no additional business side effects.
- **Deduplication:** identifying and discarding duplicate requests; often a mechanism to achieve idempotency.
- **Thread safety:** preventing races/data races when threads access shared data; a thread-safe method can still increment a balance twice.
- **At-most-once execution:** attempts to avoid repeated execution, risking lost work if a failure occurs before the work is done.
- **At-least-once delivery:** keeps resending until acknowledged; may result in duplicate execution.
- **Exactly-once effect:** an effect is recorded exactly once within a **protected boundary**, such as a database transaction. It does not mean "the code runs only once" across all machines and services.

In practice, "completed but response lost" cannot be distinguished from "not yet completed" by a timeout alone. Therefore, retries are normal; the consequences of retries must be controlled.

## 2. Choosing an Idempotency Key and Result Contract

The key represents the **business intent**, such as `charge:order-842`, `import:file-sha256:row-17`, or a request UUID generated by the caller and **reused across all retries** of the same request. An attempt ID (`attemptId`), the current timestamp, or a newly generated UUID on each run does not help detect retries.

A practical contract includes:

1. **Key scope:** specify whether the key is unique globally, per tenant, per user, or per operation type. If scoped, the unique key can be `(tenant_id, operation_type, idempotency_key)`.
2. **Payload binding:** store a canonical hash of the business-meaningful fields. If the same key is sent with a different payload, fail with `KEY_REUSED_WITH_DIFFERENT_PAYLOAD`; do not silently treat it as the original request. Canonicalization must be deterministic (field ordering, encoding, currency, numeric precision).
3. **Stable result:** if already completed, return the stored result or equivalent state without re-executing the side effect. You may need to preserve the HTTP status/operation ID alongside the result payload.
4. **In-flight tasks:** respond with `IN_PROGRESS`, return an operation ID for polling, or wait with a bounded timeout; do not arbitrarily start a second task.
5. **Retention period:** keep receipts/keys long enough for late retries, queue replays, and auditing requirements. Expiring TTL too early can cause an old message to trigger a new side effect.

Keys must be access-controlled: do not let a client from one tenant use a key to read another tenant's confidential result. A payload hash only identifies content; it does not replace authentication/authorization.

## 3. Race Condition: Check-Then-Act Is Not Enough

The following design has a race condition:

```java
if (!processedIds.contains(taskId)) {
    performEffect();
    processedIds.add(taskId);
}
```

Two threads can both see "not yet processed" and both call `performEffect()`. Switching `HashSet` to a thread-safe set only makes individual operations safe; it does not turn the **check + effect pair** into an atomic step. A `synchronized` lock can serialize execution within a single JVM if all callers use the same lock, but it does not protect against workers in other JVMs, restarts, or data loss after a crash.

A correct design must define a **linearization point**: an atomic operation that decides who owns the key. Within a single process, you can use `ConcurrentHashMap.putIfAbsent` or `computeIfAbsent` under suitable conditions. Across multiple processes, use a unique constraint, conditional update/compare-and-set, or an equivalent primitive at a durable data store. Claiming the key **is not enough** if the side effect happens outside the atomic boundary.

## 4. Java 17+ Example: Coalescing Concurrent Calls in One JVM

The following complete example uses `FutureTask` so callers with the same key receive **the same shared result**. `putIfAbsent` publishes exactly one task; only the winning thread calls `run()`. Even when four callers arrive concurrently, the simulated processing runs only once.

File `IdempotentTaskDemo.java`:

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.Callable;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.FutureTask;
import java.util.concurrent.atomic.AtomicInteger;

public class IdempotentTaskDemo {
    private static final ConcurrentMap<String, FutureTask<String>> tasks =
            new ConcurrentHashMap<>();

    static String executeOnce(String key, Callable<String> action)
            throws InterruptedException, ExecutionException {
        FutureTask<String> candidate = new FutureTask<>(action);
        FutureTask<String> existing = tasks.putIfAbsent(key, candidate);
        FutureTask<String> selected = existing == null ? candidate : existing;

        if (existing == null) {
            selected.run(); // Only the caller that wins putIfAbsent executes the action.
        }
        return selected.get(); // Other callers wait on the same FutureTask.
    }

    public static void main(String[] args) throws Exception {
        AtomicInteger effects = new AtomicInteger();
        ExecutorService pool = Executors.newFixedThreadPool(4);
        try {
            List<Future<String>> replies = new ArrayList<>();
            for (int i = 0; i < 4; i++) {
                replies.add(pool.submit(() ->
                        executeOnce("job:42", () -> {
                            effects.incrementAndGet();
                            return "DONE";
                        })));
            }
            for (Future<String> reply : replies) {
                System.out.println(reply.get());
            }
            System.out.println("Số lần xử lý: " + effects.get());
        } finally {
            pool.shutdown();
        }
    }
}
```

Run in the directory containing the file:

```bash
javac IdempotentTaskDemo.java
java IdempotentTaskDemo
```

Output:

```text
DONE
DONE
DONE
DONE
Số lần xử lý: 1
```

**Limitations to understand before using in production:**

- The map lives in the memory of **a single JVM**. A restart or two separate instances will not share receipts. This is in-process single-flight/memoization, not durable idempotency.
- The same key with a different payload will still receive the old result: production code must also validate the payload hash and scope before returning a result.
- If `Callable` fails, `FutureTask` caches the failure and all callers receive `ExecutionException`; the current demo does not retry that key. To support retries, you need an explicit failure policy and removal by object identity, such as `tasks.remove(key, selected)`, **only after confirming a retry is safe**. Unconditional removal could delete a newer task.
- Do not perform long-running network I/O directly inside a `ConcurrentHashMap.computeIfAbsent` callback as a distributed mechanism. The mapping function must not recursively modify the map itself, and a slow action can block other updates.
- `selected.get()` blocks until completion; production systems need timeouts, cancellation, and thread interruption strategies. Canceling one caller should not arbitrarily cancel shared work that other callers are still waiting on.
- The map retains results indefinitely without eviction/TTL. Eviction allows a key to be reprocessed, so the side effect must have its own durability layer.

## 5. Durable Idempotency: Receipts and Transactions

When restarts, multiple JVMs, or queue replays are involved, use a shared **receipt store** with a unique constraint where the business side effect occurs. A basic structure:

| Field | Purpose |
|---|---|
| `scope + idempotency_key` (unique/primary key) | Identifies the same request |
| `payload_hash` | Rejects key reuse with different content |
| `status`: `PENDING`, `IN_PROGRESS`, `SUCCEEDED`, `FAILED` | Tracks lifecycle |
| `result` or `resource_id` | Returns the result on retry |
| `attempt`, `lease_until`, `fencing_token` | Manages takeover when a worker is lost |
| `created_at`, `completed_at` | Monitoring and retention |

**Short transaction pattern (effect and receipt in the same database):**

```text
Receive (scope, key, payload):
  BEGIN TRANSACTION
    Attempt to claim the key using INSERT with a UNIQUE constraint.
    If duplicate key:
      read the corresponding receipt using an appropriate locking/isolation strategy;
      if payload_hash differs -> reject;
      if SUCCEEDED -> return the stored result;
      if in progress -> return IN_PROGRESS / wait with a bound;
      if FAILED -> apply the retry policy;
    If claim succeeds:
      update business data;
      update receipt = SUCCEEDED and store result;
  COMMIT
  Return result
```

This is an **illustrative algorithm**, not standalone runnable Java/SQL code. For fast tasks, wrapping claim + business update + receipt success in **the same transaction** guarantees atomic rollback on failure. All competing transactions must rely on the database's unique constraint; a "SELECT to check existence then INSERT" without a unique constraint still has a race condition.

Minimal DDL example, PostgreSQL syntax (adjust for other databases):

```sql
CREATE TABLE job_receipt (
    scope          VARCHAR(100) NOT NULL,
    idempotency_key VARCHAR(200) NOT NULL,
    payload_hash   CHAR(64) NOT NULL,
    status         VARCHAR(20) NOT NULL,
    result_ref     VARCHAR(200),
    created_at     TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at   TIMESTAMPTZ,
    PRIMARY KEY (scope, idempotency_key)
);
```

To claim a key, PostgreSQL supports `INSERT ... ON CONFLICT DO NOTHING RETURNING ...`. If the statement returns a row, the caller just claimed the key successfully; if not, it must read the existing state, compare the payload hash, and handle the appropriate branch. The unique index resolves concurrent claim contention; it does **not** automatically protect side effects outside the transaction.

Avoid a subtle bug: if you commit an `IN_PROGRESS` receipt first, then perform the business work and crash before writing `SUCCEEDED`, the key gets stuck. The design must have lease/recovery, or keep the business update and receipt in a single transaction so that retries after a rollback can start fresh. Do not hold a transaction open for minutes or hours just to lock a long-running task: long locks cause contention and tie up connections.

### Long-running tasks: leases, tokens, and fencing off stale workers

When a task takes a long time, a worker can claim it with a `lease_until` timestamp and renew it periodically. After the lease expires, another worker may reclaim it. However, **lease expiration does not stop the old worker from running**. If two workers operate concurrently, you need a monotonically increasing **fencing token** on each claim and must include that token in the write condition of the protected resource:

```text
Worker A receives token 7 -> lease expires
Worker B receives token 8 -> starts processing
Worker A wakes up, tries to write with token 7 -> target system rejects stale token
Worker B writes with token 8 -> accepted
```

Example conditional update logic: only accept the effect if the worker's token is still valid against the resource's current version/token. This check must be placed **at the exact point where the mutation happens**, in the same atomic operation as the mutation. Checking in Java and then writing afterward creates a new race window. Internal tokens also cannot stop an email or external API call that has already been sent; external boundaries require their own mechanisms.

## 6. Side Effects Outside the Database: Outbox, Inbox, and Downstream Keys

A database transaction cannot roll back a sent email or an HTTP request already accepted by a partner. The dangerous window:

```text
Worker -> partner accepts request -> response is lost
Worker does not know whether partner processed it -> retries -> partner receives it again
```

If the partner API supports an idempotency key, send the **same business key** on every retry, and verify the scope, TTL, and behavior on payload mismatch according to the partner's documentation. If the partner does not deduplicate, you cannot guarantee an exactly-once effect using locks or maps in Java alone. Consider reconciliation (querying status by external reference) or designing compensating business actions, depending on the risk level.

For events/messages, two layers are commonly used:

1. **Transactional outbox (producer side):** write the business change **and** an outbox record with a stable `event_id` in the same transaction. The dispatcher may send the event multiple times; marking it as sent after publishing does not completely eliminate duplicate sends.
2. **Idempotent inbox/consumer (consumer side):** insert `event_id` into a table with a unique constraint **in the same transaction as the business processing**. If duplicate, ignore it or return the previous result. If the consumer calls an external system, it still needs keys/controls at that external system.

Example of transitioning an order from `READY` to `SHIPPED`: use `WHERE status = 'READY'` when updating, create an outbox event with a stable `event_id` in the same transaction; redelivered messages will not cause the consumer to apply the effect a second time if the consumer's inbox and update share a transaction. If event ordering matters, also check version/sequence; deduplication **does not** automatically guarantee ordering.

## 7. Retries, Errors, and Observable Outcomes

Design your retry policy based on **the error and side-effect state**, not just the failure count.

| Scenario | Handling |
|---|---|
| Error definitely occurred before the side effect, transaction rolled back | Safe to retry with the same key |
| Side effect and transaction committed, but response was lost | Read the receipt and return the result; do not re-execute |
| Transient error, unclear whether the partner processed it | Query status by key/reference or retry using a partner-supported idempotency key |
| New payload reuses an old key | Reject and return an explicit error |
| A worker is currently processing | Wait with a timeout, return pending, or let the client poll; do not spawn a second worker |
| Permanent business error (missing permissions, invalid data) | Do not retry indefinitely; record the appropriate error state/details |
| Lease expired | Perform a fenced takeover and safely recover intermediate state |

Backoff with jitter reduces synchronized retry storms; max attempts and a dead-letter queue (if using queues) prevent infinite loops. **Retries must keep the same key** and logical payload. Be careful when canceling tasks: `Future.cancel(true)` only requests interruption; it cannot undo an already committed side effect. Design operation IDs so you can verify the actual outcome before confirming a failure.

Do not delete receipts immediately upon task success to "save memory" while a replay window still exists. Retention policies should be based on maximum retry duration, message retention time, data recovery capabilities, API contracts, and reconciliation needs.

## 8. Common Design Mistakes

- **Relying only on `synchronized`, `ReentrantLock`, or a static map:** does not protect across multiple JVMs or restarts.
- **Check-then-act:** checking "already processed?" and writing in a separate step without a unique constraint/transaction.
- **Generating a new key on retry:** makes every attempt look like a brand-new request.
- **Same key, changed payload:** mistakenly returning the old result or applying the new payload's side effect.
- **Writing `SUCCEEDED` before the side effect:** a crash causes the task to be skipped. Writing the side effect before the receipt in two separate transactions allows duplicate execution.
- **Marking `IN_PROGRESS` without recovery:** tasks stay stuck forever when a worker dies.
- **Assuming TTL/lease is an absolute lock:** an old worker may still be running after its lease expires.
- **Assuming a queue/Future/HTTP timeout tells you for sure whether a side effect happened:** the state may be indeterminate.
- **Using `putIfAbsent` but running the side effect before inserting:** both callers still execute.
- **Treating a database commit as sufficient for external APIs:** downstream idempotency/reconciliation is still required.

## 9. Design and Testing Checklist

Before implementing, clearly answer: which fields identify the "same request"? Are the receipt and business data in the same transaction? If two instances receive the same key concurrently, which one wins? If a worker dies at any point between claim, side effect, commit, and ack, what does the new worker observe? If a partner accepted the request but timed out on the response, how do you query it? When is a key allowed to expire? Is there a mechanism to block an old worker after a takeover?

Testing should include **realistic interleavings**, not just calling twice sequentially:

| Test case | Expected result |
|---|---|
| Call with the same key sequentially 2–10 times | One side effect, equivalent results every time |
| 50–100 concurrent callers with the same key | One claim succeeds; remaining callers cause no extra effect |
| Same key with a different payload | Error returned, no stale result leaked |
| Two competing JVMs/workers | Unique/conditional claim still protects |
| Crash before transaction commit | Rollback; retry can process it |
| Commit succeeds but response/ack is lost | Retry retrieves receipt/result, does not reprocess |
| Crash after claiming `IN_PROGRESS` | Lease/recovery reclaims the task without leaving it stuck |
| Lease expires while old worker is still running | Stale token is rejected at the write site |
| Duplicate events, out-of-order events | Inbox blocks duplicates; version/sequence blocks backward updates |
| TTL expires, very late retry | Behavior is deterministic and causes no out-of-contract side effects |

In production, monitor metrics such as `claim_success`, `duplicate_seen`, `key_payload_conflict`, `in_progress_age`, `retry_count`, `stale_fence_rejected`, and end-to-end latency. Log using safely sanitized key/operation IDs, avoiding sensitive data. A sudden spike in duplicate rates may indicate lost acks, timeouts, or a broken retry loop.

## 10. Choosing a Mechanism by Guarantee Scope

| Scope | Appropriate tools | Limitations |
|---|---|---|
| Multiple threads in **one JVM** | `ConcurrentHashMap` + `FutureTask`, atomic CAS, locks | Not durable across restarts/other JVMs |
| Multiple processes, side effect within **one DB** | Unique key, transaction, receipt/result | Must handle long transactions and pending states |
| Long-running workers with takeover | Lease + fencing token + conditional write | Token must be enforced at the target resource |
| Replayable messages/events | Transactional outbox + idempotent inbox | Duplicates can still occur when crossing to external systems |
| External APIs/emails/payments | Downstream idempotency key, external reference, reconciliation | Depends on the partner's guarantees |

**Core principle:** allow tasks to be re-executed, but place atomic and durable guards **at the exact place where the side effect is recorded**. Single-flight in Java optimizes duplicate work; transactions/unique keys protect effects in the database; outbox/inbox and external system contracts extend guarantees across boundaries. Always design for the case where the outcome succeeded but the confirmation signal was lost.
