# HttpClient.sendAsync(): Combining HTTP Responses, Network Errors, and CompletableFuture

## 1. Problem and Scope

Java 11+ provides an HTTP client API in the `java.net.http` package. The `HttpClient.sendAsync()` method sends an HTTP request and returns a `CompletableFuture<HttpResponse<T>>`, allowing the future result to be expressed through processing, composition, error recovery, and deadline control stages. This lesson uses plain Java 17+ in the context of **Java concurrency**; it does not depend on Spring, annotations, or framework-specific asynchronous mechanisms.

After this lesson, you should be able to distinguish between:

- **Received HTTP response**: has `statusCode()`, headers, and body; status codes `404`, `429`, `500` are still normal HTTP responses at the API level.
- **Exchange failure**: the request/response exchange could not be completed due to DNS, connection, TLS, timeout, body read error, or task cancellation; the `CompletableFuture` completes *exceptionally*.
- **Application-converted error**: after reading the status, the program explicitly throws an exception to turn an unacceptable HTTP status into the error branch of the pipeline.

These are three distinct cases; lumping them together as a single "failed HTTP" will make retries, user notifications, and system observability inaccurate.

## 2. Components and Execution Flow

`HttpClient` manages configuration and connection reuse; `HttpRequest` describes the URI, method, headers, body, and timeout; `HttpResponse.BodyHandler<T>` determines how the body is received; `HttpResponse<T>` holds the status, headers, and body; `CompletableFuture` provides stages to handle the result or exception.

```java
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(3))
        .build();

HttpRequest request = HttpRequest.newBuilder(URI.create("https://example.org/data"))
        .timeout(Duration.ofSeconds(5))
        .GET()
        .build();

CompletableFuture<HttpResponse<String>> pending =
        client.sendAsync(request, HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8));
```

The snippet above is an **illustrative code fragment** placed inside a method with appropriate imports, not a standalone runnable program. `sendAsync` returns a future so that stages can be attached; you should not call `get()` or `join()` immediately. The HTTP exchange happens asynchronously, and dependent stages run when the data is ready or when an error occurs. The execution order and thread of callbacks depend on the stage, executor, and completion timing; do not assume callbacks always run on the original calling thread or a fixed "HTTP thread".

Conceptual diagram:

```text
HttpRequest --sendAsync--> CompletableFuture<HttpResponse<T>>
                               |
                      HTTP exchange completed?
                      /                    \
                  succeeded               failed
                    |                         |
         HttpResponse(status, body)      CompletionException/cause
                    |                         |
            check statusCode()          handle / exceptionally
                    |
           2xx? use body; other? decide by business logic
                    |
            thenApply / thenCompose / handle ...
```

**Important:** `sendAsync` does not throw an exception by default just because the server returns `400` or `500`. If you call `thenApply(HttpResponse::body)` directly, you may accidentally process an error page's content as valid data.

## 3. Status and Body Handling Pattern

Choose a clear application convention. For an operation requiring a `2xx` success:

```java
CompletableFuture<String> result = client
        .sendAsync(request, HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8))
        .thenApply(response -> {
            int status = response.statusCode();
            if (status < 200 || status >= 300) {
                throw new HttpStatusException(status);
            }
            return response.body();
        });
```

`HttpStatusException` in the example is an **application-defined class**, not a standard exception automatically generated by `HttpClient`. If the contract requires `200` specifically, check for `200` explicitly; if the operation accepts `201`, `202`, `204`, the rule must match accordingly. `204 No Content` has no useful body; `304 Not Modified` should only be handled in a cache/conditional request context—not all non-`2xx` statuses can be treated the same.

If you need to keep metadata, do not rush to convert `HttpResponse<T>` into `T`: keep the response or map it to a result type containing `status`, `headers`, and `body`. For large/binary/streaming bodies, choose `BodyHandlers.ofFile(...)`, `ofByteArray()`, `ofInputStream()`, or an appropriate specialized handler instead of always loading the entire body into a `String`. When receiving an `InputStream`, you must properly manage closing the stream and consuming the data.

## 4. Standalone Java 17 Program Without Internet Dependency

The following example starts an HTTP server on loopback with an OS-chosen port. It executes two asynchronous requests: one that succeeds and one that returns `404`. Both are handled via `CompletableFuture`; the HTTP status is **explicitly** converted into an exception.

Save the entire code in the file `AsyncHttpDemo.java`:

```java
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.time.Duration;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionException;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class AsyncHttpDemo {
    static final class HttpStatusException extends RuntimeException {
        final int status;

        HttpStatusException(int status) {
            super("HTTP status " + status);
            this.status = status;
        }
    }

    static CompletableFuture<String> fetch(HttpClient client, URI uri) {
        HttpRequest request = HttpRequest.newBuilder(uri)
                .timeout(Duration.ofSeconds(2))
                .GET()
                .build();

        return client.sendAsync(
                    request,
                    HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8))
                .thenApply(response -> {
                    int status = response.statusCode();
                    if (status < 200 || status >= 300) {
                        throw new HttpStatusException(status);
                    }
                    return response.body();
                });
    }

    static Throwable unwrap(Throwable error) {
        Throwable current = error;
        while ((current instanceof CompletionException
                || current instanceof ExecutionException)
                && current.getCause() != null) {
            current = current.getCause();
        }
        return current;
    }

    static String describe(CompletableFuture<String> future) {
        return future.handle((body, error) -> {
            if (error == null) {
                return "OK: " + body;
            }
            Throwable root = unwrap(error);
            if (root instanceof HttpStatusException httpError) {
                return "HTTP: " + httpError.status;
            }
            return "NETWORK/EXCHANGE: " + root.getClass().getSimpleName();
        }).join();
    }

    static void reply(HttpExchange exchange, int code, String text)
            throws IOException {
        byte[] bytes = text.getBytes(StandardCharsets.UTF_8);
        exchange.getResponseHeaders().set(
                "Content-Type", "text/plain; charset=utf-8");
        exchange.sendResponseHeaders(code, bytes.length);
        try (var body = exchange.getResponseBody()) {
            body.write(bytes);
        }
    }

    public static void main(String[] args) throws IOException {
        HttpServer server = HttpServer.create(
                new InetSocketAddress("127.0.0.1", 0), 0);
        ExecutorService serverExecutor = Executors.newFixedThreadPool(2);
        server.setExecutor(serverExecutor);
        server.createContext("/ok", ex -> reply(ex, 200, "ready"));
        server.createContext("/missing", ex -> reply(ex, 404, "not found"));
        server.start();

        try {
            HttpClient client = HttpClient.newBuilder()
                    .connectTimeout(Duration.ofSeconds(2))
                    .build();
            String base = "http://127.0.0.1:" + server.getAddress().getPort();

            CompletableFuture<String> ok =
                    fetch(client, URI.create(base + "/ok"));
            CompletableFuture<String> missing =
                    fetch(client, URI.create(base + "/missing"));

            System.out.println(describe(ok));
            System.out.println(describe(missing));
        } finally {
            server.stop(0);
            serverExecutor.shutdownNow();
        }
    }
}
```

Commands on JDK 17+ (`jdk.httpserver` is a JDK module used for the test example):

```bash
javac --add-modules jdk.httpserver AsyncHttpDemo.java
java --add-modules jdk.httpserver AsyncHttpDemo
```

Expected output:

```text
OK: ready
HTTP: 404
```

Step-by-step explanation:

1. The two `fetch(...)` calls start the HTTP exchanges without blocking the calling thread at `sendAsync`. The server receives the two separate paths and sends responses.
2. `/ok` returns `200`, so `thenApply` extracts the body `ready`; `handle` returns the string `OK: ready`.
3. `/missing` returns a complete `404` response; `thenApply` explicitly throws `HttpStatusException`. The future after `thenApply` completes exceptionally, then `handle` reads the cause and formats `HTTP: 404`.
4. `join()` in `describe` is only used at the console program boundary to wait for and print results. In a server/event loop, calling `join()` right after `sendAsync()` can defeat the benefits of asynchrony or cause thread starvation.

The **network completion** order of the two requests is not guaranteed; the order of the **two printed lines** here is determined by the two sequential `println` calls.

## 5. Error Categories and Branching

| Situation | What `sendAsync` returns | Appropriate handling |
| --- | --- | --- |
| HTTP `200`, `201`, `204` | Future completes normally with `HttpResponse<T>` | Check contract, use body if present |
| HTTP `400`, `404`, `409` | Future **still completes normally** with response | Read error status/body; decide business outcome, do not retry blindly |
| HTTP `429`, `502`, `503`, `504` | Normal future if response was received | Consider retry based on method, system load, `Retry-After`, and rate-limit policy |
| DNS, connection refused, TLS handshake, connection closed, I/O error | Future may complete exceptionally | Inspect cause; record technical error type and consider retrying |
| No response received within request deadline | Future completes exceptionally, usually containing `HttpTimeoutException` | Configure timeouts, classify retry separately |
| HTTP status rejected by application | Error occurs in stage because **you explicitly threw** it | Use a dedicated exception/result type for HTTP status |
| `CompletableFuture` cancelled | Future is cancelled/exceptionally completed | Identify who cancelled, clean up, and do not treat as HTTP status |

Exceptions from stages may be wrapped in `CompletionException` when using `join()`; `get()` throws `ExecutionException` and requires handling `InterruptedException`. Therefore, log and classify by `getCause()` (taking care to unwrap only appropriate wrappers), rather than directly comparing the class name of the outer exception.

Some real-world cause types include `java.net.ConnectException`, `java.net.UnknownHostException`, `javax.net.ssl.SSLException`, `java.net.http.HttpTimeoutException`, and `java.net.http.HttpConnectTimeoutException`. Do not rely on one specific exception type across all OS, DNS, or proxy variations; runtime context can affect the cause chain.

Do not include `Authorization` tokens, cookies, or full bodies containing sensitive data in logs. For HTTP statuses, you can log the method, safe route, status, duration, and correlation ID when available in the system.

## 6. Choosing the Right Stage: Transform, Depend, Combine, Recover

### `thenApply`: transform an available result

```java
CompletableFuture<Integer> length =
        fetch(client, uri).thenApply(String::length);
```

When `fetch` succeeds, the stage yields the length; if `fetch` fails, the transform stage is skipped and the error propagates downstream. `thenApply` is suitable for short, non-blocking operations. The callback may run on the thread that completed the previous stage, so avoid `sleep`, blocking I/O, and heavy computation directly inside the callback.

### `thenCompose`: request B needs the result of request A

```java
CompletableFuture<String> detail = fetch(client, indexUri)
        .thenCompose(relativePath -> {
            URI resolved = indexUri.resolve(relativePath);
            return fetch(client, resolved);
        });
```

This is an **illustrative code fragment** assuming the content of `indexUri` is a trusted path. When data comes from external sources, you must validate scheme, host, path, and allowlist policies before sending the second request, to avoid arbitrary URI access. `thenCompose` flattens `CompletableFuture<CompletableFuture<String>>` into a single future; do not use `thenApply` to nest futures if you need the final result. The second request only starts after the first request succeeds.

### `thenCombine` and `allOf`: multiple independent requests

```java
CompletableFuture<String> combined =
        fetch(client, firstUri)
          .thenCombine(fetch(client, secondUri),
                  (first, second) -> first + " | " + second);
```

Both `fetch` calls are initiated independently, allowing the requests to overlap their network wait times. `thenCombine` receives the values of both when both succeed. `CompletableFuture.allOf(f1, f2, ...)` is suitable for waiting on a set of futures, but the future returned by `allOf` has type `CompletableFuture<Void>`; it **does not** contain a list of results. Only after `allOf` succeeds should you retrieve each result in the desired order. If one future fails, the standard combination also fails; there is no built-in mechanism to automatically collect all errors or cancel remaining requests.

### `handle`, `exceptionally`, `whenComplete`, and `exceptionallyCompose`

- `handle((value, error) -> ...)` runs for both success and error, returning a **new value** to recover or transform. The `describe` example uses `handle` to produce a consistent message.
- `exceptionally(error -> fallback)` runs only on error and produces a replacement value of the same type `T`. If you arbitrarily recover with an empty string, the caller can no longer distinguish real data from an error.
- `whenComplete((value, error) -> ...)` is suitable for lightweight observation/metrics/logging. It normally forwards the original result or error; it is not a recovery operator. If the callback also throws an exception, the additional error can affect the outcome according to the API rules.
- `exceptionallyCompose(error -> otherFuture)` (available in Java 17) is used when the recovery branch is also **asynchronous**, such as calling a fallback source after an allowed error type.

Example fallback policy for `404` (snippet uses `fetch`, `unwrap`, and `HttpStatusException` defined in the program above):

```java
CompletableFuture<String> withFallback = fetch(client, primaryUri)
        .exceptionallyCompose(error -> {
            Throwable cause = unwrap(error);
            if (cause instanceof HttpStatusException httpError
                    && httpError.status == 404) {
                return fetch(client, secondaryUri);
            }
            return CompletableFuture.failedFuture(cause);
        });
```

The fallback applies only to `404` per business requirements; timeouts, TLS errors, or other statuses remain errors. `CompletableFuture.failedFuture` has been available since Java 9. Do not use a single `exceptionally` function to swallow every case and return dummy data without recording the cause.

## 7. Timeouts, Cancellation, and Resource Control

There are three mechanisms with different meanings:

```java
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(2)) // connection setup
        .build();

HttpRequest request = HttpRequest.newBuilder(uri)
        .timeout(Duration.ofSeconds(4))        // HTTP request deadline
        .GET()
        .build();

CompletableFuture<HttpResponse<String>> pending =
        client.sendAsync(request, HttpResponse.BodyHandlers.ofString());

pending.orTimeout(5, java.util.concurrent.TimeUnit.SECONDS);
```

- `connectTimeout` applies to establishing a new connection; reusing an existing connection does not necessarily go through the connect step. Do not use it as a replacement for a request timeout.
- `HttpRequest.timeout` sets a deadline at the HTTP exchange level; when expired, you may receive `HttpTimeoutException`. This is the primary choice for bounding a request.
- `orTimeout` sets a deadline on the **CompletableFuture** and completes that future exceptionally with `TimeoutException` if the deadline is reached. The future timing out does not guarantee that the underlying I/O stops immediately; do not treat this as a complete replacement for request timeouts and resource management.
- `completeOnTimeout(fallback, ...)` completes the future with a fallback value if the deadline is reached. Only use it when the fallback genuinely has business meaning; do not let a timeout masquerade as a server response.

Cancelling the root `CompletableFuture` returned by `HttpClient.sendAsync` with `cancel(true)` may request stopping the HTTP exchange and releasing resources, but it does not guarantee that the request has not already been sent or that cancellation takes effect immediately. Cancelling a **dependent** future after `thenApply` does not automatically cancel the root future. Cancellation is not a server "rollback" mechanism: write operations already performed by the server may still persist.

When catching `InterruptedException` from `get()`, remember to restore the interrupt flag with `Thread.currentThread().interrupt()` if in an appropriate handling layer, while also performing cleanup. For long-running applications, reuse `HttpClient` instead of creating a new client per request, set appropriate limits on concurrent requests, and avoid holding large bodies in memory.

## 8. Retries, Backpressure, and Correctness

Asynchrony **does not mean** you are allowed to fire thousands of unbounded requests. Sending too many futures at once can exhaust the connection pool, saturate resources, put pressure on the server, and increase timeouts. Limit concurrency by regulating the number of in-flight tasks (e.g., a `Semaphore` or a bounded queue); do not hold a semaphore by calling `acquire()` and blocking a thread inside an HTTP callback. You can manage permits around issuing the request and release them in `whenComplete`, while ensuring cleanup even if request initialization fails.

Only retry when there is a valid reason:

1. **Operation type:** `GET` and `HEAD` are generally safer to retry than `POST` with side effects. If retrying write operations, you need an idempotency mechanism or contract guarantee.
2. **Failure type:** timeout/connection reset can occur after the server has already processed the request; you cannot infer "the server never received it." HTTP `429` and `503` often require `Retry-After` or a dedicated policy; HTTP `400` typically gains nothing from being resent as-is.
3. **Budget:** cap the number of attempts, total deadline, exponential backoff with jitter, and monitor retry counts. Avoid infinite retry loops or synchronized retries that create traffic storms.
4. **Overall cancellation/timeout:** propagate cancellation/deadline policies down to child branches and clean up resources as practically as possible.

If a delay is needed before retrying in an asynchronous chain, you can use `CompletableFuture.delayedExecutor(...)` to schedule the next step; avoid `Thread.sleep()` in callbacks on a shared executor. A retry with backoff must actually re-execute the request in a new future, not "re-run" an already completed `CompletableFuture`.

## 9. Common Mistakes and How to Fix Them

| Pitfall | Consequence | Fix |
| --- | --- | --- |
| Calling `sendAsync(...).join()` immediately everywhere | Blocks the calling thread, reducing concurrency benefits | Pass futures through layers, only wait at the boundary where synchronization is needed |
| Treating `404`/`500` as network errors thrown automatically by `sendAsync` | Misclassification, ignoring body/status | Check `statusCode()` and map the response explicitly |
| Using `thenApply` for a second request that returns a future | Nested `CompletableFuture<CompletableFuture<T>>` | Use `thenCompose` |
| Using `exceptionally(e -> null)` for all errors | Hides real errors, prone to `NullPointerException` later | Recover conditionally or propagate the error |
| Using `whenComplete` to replace a failed result | Does not recover the result as intended | Use `handle` or `exceptionally` |
| Configuring only `connectTimeout` | Response read duration may still exceed expectations | Add a timeout on `HttpRequest` / overall deadline |
| Cancelling the final stage and assuming HTTP has definitely stopped | Root exchange may still be running | Manage the future returned by `sendAsync` and understand cancellation limits |
| Retrying every `POST` after a timeout | Can cause repeated side effects | Use idempotency keys/contracts and bounded retries |
| Processing JSON or large streams on short stages in an uncontrolled executor | Holds threads for a long time, increasing latency for other completions | Choose an appropriate body handler and offload heavy processing to a bounded executor |

## 10. Self-Check Knowledge Questions

1. The server returns `503` with body `"maintenance"`. Does `sendAsync(..., ofString())` automatically complete exceptionally due to status `503`? **No.** The response has a normal status/body; application code decides how to handle it.
2. DNS resolution fails before any response arrives. Does `thenApply(HttpResponse::body)` run? **No** on the success path; the exception flows through the chain and can be handled in `handle`/`exceptionally`.
3. To fetch data A and then make HTTP call B based on A, which stage should you use? **`thenCompose`**. If A and B are independent, initiate both and consider `thenCombine`.
4. If `orTimeout` completes a future with `TimeoutException`, does that guarantee the server has not processed the request? **No**; it controls the state of the future, not a transaction rollback.
5. Why is using `join()` in the local example still valid? It is at the result-printing boundary of a **console program**; both requests are initiated before waiting for their results.

### Key Takeaway

`HttpClient.sendAsync` returns a **future of an HTTP response**, not a future that automatically classifies every HTTP status as an exception. Keep the three layers separate: whether the HTTP exchange completed, whether the status is valid per the contract, and whether the data satisfies business logic. From there, use `thenApply` to transform, `thenCompose` for dependent tasks, `thenCombine` for independent tasks, and `handle`/`exceptionally` for intentional recovery, while managing timeouts, cancellation, concurrency limits, and idempotent retries.
