# ClassLoadingMXBean: Total Loaded, Currently Loaded, and Unloaded Classes in the JVM

`java.lang.management.ClassLoadingMXBean` is an **MXBean in the Java Management API** for observing **the class-loading state of the entire JVM**. It does not load, unload, or free classes itself: its job is to **provide aggregate metrics** and an option to toggle verbose output for class-loading/unloading activity.

The basic metrics:

1. `getTotalLoadedClassCount()` — **the total number of classes loaded by the JVM since startup** (cumulative counter).
2. `getLoadedClassCount()` — **the number of classes currently considered loaded by the JVM** at the time of sampling.
3. `getUnloadedClassCount()` — **the total number of classes unloaded by the JVM since startup** (cumulative counter).
4. `isVerbose()`/`setVerbose(boolean)` — status and control of verbose class-loading output (JVM-wide scope, not specific to a single loader).

Especially important for plugin systems: **these three metrics are JVM-wide in scope**, not pre-categorized by plugin name, JAR, ClassLoader instance, or module. To find out which class or loader is retaining memory, you need to combine other tools (JFR, JVM logging, thread dumps, JMX, classloader statistics, and heap analysis).

This article explains the exact API, the differences among the three counters, how to read them inside an application and via JMX, how to calculate deltas/evaluate classloader leaks, the limitations of what cannot be inferred from a single snapshot, and a Java 17+ example that **loads a class using two independent loaders** to observe the metrics increase.

## 1. Why Observe Class Loading?

The JVM loads classes when the program needs them, through the class loader system and JVMS rules. In addition to application code, the JVM may also load:

- Core Java/platform/library classes.
- Application classes and dependency JARs.
- Dynamic proxies, lambda-related implementations, generated adapters, or framework-generated bytecode.
- Separate classes from plugin loaders, OSGi/container classloader hierarchies, or modular environments.
- Classes loaded via reflection, `ServiceLoader`, and on-demand dependency resolution.

If a service continuously deploys/redeploys plugins, creates new classloaders, or dynamically generates classes, **the total number of loaded classes** can grow rapidly. If old loaders cannot be garbage-collected, **the number of currently loaded classes** can also accumulate, driving up native metadata/metaspace usage and other resources.

`ClassLoadingMXBean` helps answer the initial questions:

~~~text
How much has the total number of ever-loaded classes grown?
                            |
     How many classes are currently still loaded?
                            |
     How many classes have actually been unloaded?
                            |
What is the trend over multiple minutes/hours/deployments?
~~~

However, it **does not return a list of classes** or the reason why a loader has not been garbage-collected. Diagnosing leaks requires more layers of evidence than a class-count chart.

## 2. Location of ClassLoadingMXBean in Java Management

Since Java 5, JMX platform management has provided a bean for class loading. On Java 17, the API belongs to the standard `java.management` module:

~~~text
Module java.management
   |
   +-- java.lang.management.ManagementFactory
   |
   +-- java.lang.management.ClassLoadingMXBean
   |
   +-- java.lang.management.MemoryMXBean
   +-- java.lang.management.MemoryPoolMXBean
   +-- java.lang.management.ThreadMXBean
   ...
~~~

Obtaining a JVM-wide bean:

~~~java
import java.lang.management.ClassLoadingMXBean;
import java.lang.management.ManagementFactory;

ClassLoadingMXBean bean =
        ManagementFactory.getClassLoadingMXBean();
~~~

This is an **illustrative API snippet** that can be placed inside `main` or a method to use. A JVM has **one class-loading management bean instance by contract**, and this bean is also registered in the **platform MBeanServer**.

Standard ObjectName:

~~~text
java.lang:type=ClassLoading
~~~

It can be obtained from:

~~~java
System.out.println(bean.getObjectName());
~~~

`ClassLoadingMXBean` extends `PlatformManagedObject`, so the `getObjectName()` method returns the corresponding JMX `ObjectName` object.

### Three Core Counters

| Method | Return Type | Meaning |
|---|---|---|
| `getLoadedClassCount()` | `int` | How many classes are currently loaded in the JVM |
| `getTotalLoadedClassCount()` | `long` | Total classes loaded since the JVM started |
| `getUnloadedClassCount()` | `long` | Total classes unloaded since the JVM started |

Do not confuse `getLoadedClassCount()` with `getTotalLoadedClassCount()`: **currently loaded** can decrease after some classes are unloaded, whereas **total loaded** is a cumulative total across the JVM's lifetime and does not decrease.

## 3. Relationship Between Total Loaded, Currently Loaded, and Unloaded

In terms of interpretation, the metrics describe:

~~~text
            Classes ever loaded
                     |
          +----------+-----------+
          |                      |
    Still loaded              Unloaded
          |                      |
getLoadedClassCount()  getUnloadedClassCount()
          \                      /
           \                    /
        getTotalLoadedClassCount()
               (cumulative)
~~~

In an ideal point-in-time snapshot:

~~~text
Total loaded ≈ Currently loaded + Total unloaded
~~~

Why use **`≈` instead of requiring `==` for three consecutive calls**?

- The three methods are called **sequentially**, not as a single atomic snapshot API for all three counters.
- The JVM can load or unload classes between reads.
- Class loading can occur in the background due to the compiler/JIT, reflection, instrumentation, or other threads.
- Different implementations may have different measurement details; applications should not depend on an **exactly measurable** invariant under every race.

Therefore, do not take a single sample and throw an exception simply because the arithmetic sum **is not strictly equal**. When trend analysis is needed, sample periodically, record timestamps, and distinguish cumulative metrics from instantaneous metrics.

### Illustration with Hypothetical Numbers

Suppose a JVM at time T1:

| Metric | T1 |
|---|---:|
| Total loaded | 12,000 |
| Currently loaded | 11,850 |
| Total unloaded | 150 |

These are **example numbers**, not the fixed output of any program.

After a batch of plugin loads, at T2:

| Metric | T2 |
|---|---:|
| Total loaded | 12,500 |
| Currently loaded | 12,300 |
| Total unloaded | 200 |

We have:

- `Δtotal = 500`: the JVM loaded 500 additional classes during the observation window.
- `Δunloaded = 50`: 50 additional classes were unloaded.
- `Δcurrent = 450`: the current class count is higher by 450.
- It cannot yet be concluded which specific plugin those 450 classes belong to or whether there is a leak, because the system may be warming up and caching classes legitimately.

Do not use `getTotalLoadedClassCount()` as the "number of classes currently occupying metaspace"; it is a **cumulative counter**.

## 4. Simple Code to Read Metrics

Java snippet:

~~~java
ClassLoadingMXBean bean =
        ManagementFactory.getClassLoadingMXBean();

long total = bean.getTotalLoadedClassCount();
int current = bean.getLoadedClassCount();
long unloaded = bean.getUnloadedClassCount();

System.out.println("total=" + total);
System.out.println("current=" + current);
System.out.println("unloaded=" + unloaded);
~~~

This is an illustrative snippet that requires the two imports `ClassLoadingMXBean` and `ManagementFactory`. The output consists of **actual JVM numbers**, depending on the JDK, command-line flags, classpath, warmed-up classes, and whether the JVM unloads classes.

**There is no fixed set of numbers like “total=1234/current=...”** across all machines. When writing lessons or tests, verify **relationships, deltas, or formats**, rather than hard-coding counter values.

### Reading the Correct Numeric Types

- `getTotalLoadedClassCount()` returns `long`.
- `getUnloadedClassCount()` returns `long`.
- `getLoadedClassCount()` returns `int`.

Do not cast all three to `int` or parse log strings for metrics when you can call the API directly. Over long periods of time, cumulative counters can become large.

### Observing Across Time Points

~~~java
record Sample(
        long nanoTime,
        long totalLoaded,
        int currentlyLoaded,
        long unloaded) {
}

static Sample sample(ClassLoadingMXBean bean) {
    return new Sample(
            System.nanoTime(),
            bean.getTotalLoadedClassCount(),
            bean.getLoadedClassCount(),
            bean.getUnloadedClassCount());
}
~~~

This is an **illustrative snippet**, suitable when `ClassLoadingMXBean` has already been imported. `System.nanoTime()` is intended for **elapsed time within the same process**, not a wall-clock timestamp or Unix time. If you need to log events by calendar time, record `Instant.now()` as well.

## 5. Complete Java 17+ Example: Loading One Class from Two Loaders

The experiment uses:

- A class `experiment.Marker` compiled into a separate plugin directory.
- A host class `ClassLoadingLab` present only on the application classpath.
- Two independent `URLClassLoader` instances, both rooted at `out/plugin`.
- Two runtime `Class<?>` objects with the same binary name but different defining loaders.
- `ClassLoadingMXBean` sampled before and after both classes are loaded.

The goal is to verify **predictable events and relationships** rather than printing absolute counter values that cannot be predicted across JDKs.

### 5.1. Project Structure

~~~text
project/
  src/
    plugin/
      experiment/
        Marker.java
    host/
      ClassLoadingLab.java
  out/
    plugin/
    host/
~~~

### 5.2. File `src/plugin/experiment/Marker.java`

~~~java
package experiment;

public final class Marker {
    public String id() {
        return "marker";
    }
}
~~~

The class uses only core `java.base` types and has no host dependencies. Thus, choosing `ClassLoader.getPlatformClassLoader()` as the parent for the two plugin loaders in this experiment does not cause any missing shared host APIs.

### 5.3. File `src/host/ClassLoadingLab.java`

~~~java
import java.lang.management.ClassLoadingMXBean;
import java.lang.management.ManagementFactory;
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Path;

public final class ClassLoadingLab {
    private static final String PLUGIN_CLASS = "experiment.Marker";

    record Sample(long total, int current, long unloaded) {
    }

    static Sample read(ClassLoadingMXBean bean) {
        return new Sample(
                bean.getTotalLoadedClassCount(),
                bean.getLoadedClassCount(),
                bean.getUnloadedClassCount());
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException(
                    "Usage: ClassLoadingLab <plugin-dir>");
        }

        ClassLoadingMXBean bean =
                ManagementFactory.getClassLoadingMXBean();

        URL url = Path.of(args[0]).toAbsolutePath()
                .toUri().toURL();

        Sample before = read(bean);

        try (URLClassLoader loaderA = new URLClassLoader(
                    "plugin-A", new URL[] {url},
                    ClassLoader.getPlatformClassLoader());
             URLClassLoader loaderB = new URLClassLoader(
                    "plugin-B", new URL[] {url},
                    ClassLoader.getPlatformClassLoader())) {

            Class<?> first = loaderA.loadClass(PLUGIN_CLASS);
            Class<?> second = loaderB.loadClass(PLUGIN_CLASS);

            Sample after = read(bean);

            System.out.println("mxbean name correct: "
                    + bean.getObjectName().getCanonicalName()
                        .equals("java.lang:type=ClassLoading"));

            System.out.println("same binary name: "
                    + first.getName().equals(second.getName()));
            System.out.println("same runtime class: "
                    + (first == second));

            System.out.println("A defines its class: "
                    + (first.getClassLoader() == loaderA));
            System.out.println("B defines its class: "
                    + (second.getClassLoader() == loaderB));

            System.out.println("total loaded grew by at least two: "
                    + (after.total() >= before.total() + 2));

            System.out.println("unloaded count nondecreasing: "
                    + (after.unloaded() >= before.unloaded()));

            System.out.println("current loaded count positive: "
                    + (after.current() > 0));
        }
    }
}
~~~

**Important details:**

1. `getClassLoadingMXBean()` provides a bean that observes **the entire JVM**, not specifically loader A or B.
2. `Sample before` is taken **before** creating and using the two URLClassLoaders.
3. The parent is the platform loader, and `experiment.Marker` is not on the application classpath; both A and B must find `experiment/Marker.class` themselves under the URL root.
4. `loaderA.loadClass` and `loaderB.loadClass` define two runtime classes with the **same binary name** but different defining loaders. Therefore, `first == second` is `false`.
5. The two new class definitions contribute to **total loaded**; other classes may also be loaded by the JVM during the experiment, so check `>= 2` and **do not** check for exactly 2.
6. `getUnloadedClassCount()` is a cumulative counter and does not decrease within a JVM; while `first`/`second`/loaders are still retained inside the block, **do not** assert that they have been unloaded.
7. `getLoadedClassCount()` in a running JVM state is a positive value; do not check `after.current() - before.current() == 2` because concurrency or unloading may change the current count.

### 5.4. Compiling and Running with JDK 17+

From the `project` directory, run with Bash on Linux/macOS or a compatible Bash environment:

~~~bash
mkdir -p out/plugin out/host

javac -d out/plugin src/plugin/experiment/Marker.java

javac -d out/host src/host/ClassLoadingLab.java

java -cp out/host ClassLoadingLab out/plugin
~~~

**Do not add `out/plugin` to the application classpath**; otherwise, the parent/caller may see the class first and it is no longer guaranteed that the two child loaders define it themselves.

On Windows PowerShell, create the output directories with `New-Item -ItemType Directory -Force` and then run `javac`/`java` accordingly. Because the host classpath has only **one** element, no `:` or `;` separator is needed.

### 5.5. Expected Stdout

~~~text
mxbean name correct: true
same binary name: true
same runtime class: false
A defines its class: true
B defines its class: true
total loaded grew by at least two: true
unloaded count nondecreasing: true
current loaded count positive: true
~~~

The output above relies on valid class files, no copy of `experiment.Marker` in the parent, two different URLClassLoaders, and a JVM conforming to `ClassLoadingMXBean` counters. **Actual counts are not printed**, because they can vary by JDK/OS/classpath/GC.

### 5.6. Why Does Closing Loaders Not Mean Class Unloading?

Upon exiting the `try-with-resources` block, the `URLClassLoader` instances close the opened file/JAR resources. This **does not force** the VM to unload `experiment.Marker` immediately when the block ends.

For class unloading to have a chance to occur, there must be no remaining strong references to:

- Loader instances, `Class<?>`, or objects created by that class.
- Threads, scheduled tasks, TCCL, or `ThreadLocal` pointing to the loader.
- Reflection `Method`/`Constructor`, `MethodHandle`, service providers, or framework caches.
- JNI global references, listeners, callbacks, or registries holding the plugin generation.

Even when all references have been released, the JVM may choose different timing for GC/unloading. **`System.gc()` is not a guarantee of class unloading**, and the fact that `getUnloadedClassCount()` does not increase immediately **does not prove there is a leak**.

## 6. Collecting Metrics Periodically in a Real Service

In production, a single snapshot is not enough. You should sample at a defined interval (for example, 10–60 seconds depending on your needs) and include a timestamp:

~~~java
import java.lang.management.ClassLoadingMXBean;
import java.lang.management.ManagementFactory;
import java.time.Instant;

public final class ClassLoadingSnapshot {
    public static void main(String[] args) {
        ClassLoadingMXBean bean =
                ManagementFactory.getClassLoadingMXBean();

        System.out.println("timestamp=" + Instant.now());
        System.out.println("loaded_current="
                + bean.getLoadedClassCount());
        System.out.println("loaded_total="
                + bean.getTotalLoadedClassCount());
        System.out.println("unloaded_total="
                + bean.getUnloadedClassCount());
    }
}
~~~

This is a **standalone program** for taking a current snapshot. Run:

~~~bash
javac ClassLoadingSnapshot.java
java ClassLoadingSnapshot
~~~

The output consists of **a timestamp and dynamic metrics**; illustrative example:

~~~text
timestamp=2026-10-24T12:00:00Z
loaded_current=1200
loaded_total=1200
unloaded_total=0
~~~

The numbers and timestamp are **for illustration only**, not a fixed stdout. What matters are the API/field names and the point-in-time nature.

**Note:** running `java ClassLoadingSnapshot` multiple times spawns **different JVMs**, so it does not produce a time series for **the same process**. To measure trends of a running application, collect metrics from **inside that JVM** or use a JMX/metrics exporter attached to the same process.

### Storing Deltas Instead of Only Absolute Values

If there are two samples T1/T2:

~~~text
total_loads_per_interval  = totalLoaded(T2) - totalLoaded(T1)
unloads_per_interval      = unloaded(T2) - unloaded(T1)
current_loaded_change     = currentlyLoaded(T2) - currentlyLoaded(T1)
rate_total_loads_per_sec  = deltaTotal / elapsedSeconds
~~~

Calculate the rate using the **actual elapsed time between the two samples**. Do not use the “total classes ever loaded” to infer the class-loading rate directly without a prior sample.

**Counter reset:** all cumulative metrics reset when the JVM restarts. When building time series, attach **process identity / start time** and handle resets; do not interpret a negative delta across two JVMs as “the JVM unloaded thousands of classes”.

### Dashboard Diagram

~~~text
JVM process (PID + startTime)
         |
         +-- loaded_class_count (gauge)
         |
         +-- total_loaded_class_count (cumulative counter)
         |
         +-- total_unloaded_class_count (cumulative counter)
         |
         +-- load_rate = delta(total) / delta(time)
         |
         +-- unload_rate = delta(unloaded) / delta(time)
         |
         +-- metaspace_used / committed (other memory MXBean source)
         |
         +-- loader count / GC / deployment events (additional sources)
~~~

`getLoadedClassCount()` fits as a **gauge**; `getTotalLoadedClassCount()` and `getUnloadedClassCount()` fit as **counters**. Do not publish all three metrics as counters or equate class count with byte-size memory.

## 7. Reading ClassLoadingMXBean via JMX

`ClassLoadingMXBean` has a fixed ObjectName:

~~~text
java.lang:type=ClassLoading
~~~

In `MBeanServer`, the corresponding attributes are typically:

| JMX Attribute | Java Method |
|---|---|
| `LoadedClassCount` | `getLoadedClassCount()` |
| `TotalLoadedClassCount` | `getTotalLoadedClassCount()` |
| `UnloadedClassCount` | `getUnloadedClassCount()` |
| `Verbose` | `isVerbose()`, `setVerbose(boolean)` |

### 7.1. Example of Reading MBeanServer Directly Inside the JVM

~~~java
import java.lang.management.ManagementFactory;
import javax.management.MBeanServer;
import javax.management.ObjectName;

public final class JmxClassLoadingSample {
    public static void main(String[] args) throws Exception {
        MBeanServer server =
                ManagementFactory.getPlatformMBeanServer();
        ObjectName key =
                new ObjectName("java.lang:type=ClassLoading");

        Object loaded =
                server.getAttribute(key, "LoadedClassCount");
        Object total =
                server.getAttribute(key, "TotalLoadedClassCount");
        Object unloaded =
                server.getAttribute(key, "UnloadedClassCount");

        System.out.println("loaded numeric: "
                + (loaded instanceof Number));
        System.out.println("total numeric: "
                + (total instanceof Number));
        System.out.println("unloaded numeric: "
                + (unloaded instanceof Number));
    }
}
~~~

Compile and run:

~~~bash
javac JmxClassLoadingSample.java
java JmxClassLoadingSample
~~~

Expected stdout:

~~~text
loaded numeric: true
total numeric: true
unloaded numeric: true
~~~

This demonstrates **JMX attribute access** without having to write a custom MXBean implementation. Do not expect JMX to return a list of currently loaded classes; these attributes remain JVM-wide aggregate counters.

### 7.2. Viewing via JConsole/JMX Client

For a running Java process where attach/JMX is permitted by the environment:

1. Launch **JConsole** from the JDK or an appropriately configured JMX client.
2. Connect to the target process/JVM.
3. Open the **MBeans** section and find `java.lang:type=ClassLoading`.
4. Read `LoadedClassCount`, `TotalLoadedClassCount`, `UnloadedClassCount`, and `Verbose`.
5. Record baselines before and after deploying or unloading a plugin, then compare against memory, GC, and logs.

**Remote JMX** connections must be properly secured with authentication, authorization, and network policies; do not expose a public JMX port just to read counters. In some container/production environments, attach may be disabled or require dedicated configuration.

## 8. `isVerbose()` and `setVerbose(boolean)`

Alongside the counters, the bean provides:

~~~java
boolean enabled = bean.isVerbose();
bean.setVerbose(true);
~~~

This is an API snippet requiring `bean` to be a `ClassLoadingMXBean`. `setVerbose(true)` asks the VM to enable additional output on class loading/unloading; `setVerbose(false)` disables it **JVM-wide**.

**Points to remember:**

- This is **not** a setting for just one classloader or plugin.
- Changes affect other threads and code within the same process.
- Output format and destination are **implementation-dependent**; there is no guarantee that every JDK prints the same format.
- It can generate substantial output/log volume, impacting performance and log observability.
- Per the Java 17 API contract, a `SecurityException` may be thrown if a security manager is present and `ManagementPermission("control")` is lacking.
- Multiple threads may call `setVerbose`, but they mutate **a single global setting**, not a separate setting per caller.

You should not put:

~~~java
bean.setVerbose(true);
~~~

inside every request handler just to debug a single plugin; doing so creates a JVM-wide side effect. In production environments, prefer JVM logging or JFR with clear configuration, time bounds, and observability policies.

### Enabling Class-Loading Logs on HotSpot Java 17

Example:

~~~bash
java -Xlog:class+load=info,class+unload=info \
     -cp out/host ClassLoadingLab out/plugin
~~~

This is a **diagnostic command for compatible HotSpot/JDK builds**. The output will include many additional log lines and will no longer resemble the concise stdout in the earlier example. Logging at the `info` level often reveals many loaded classes and their sources, though it may not fully explain **why** each class is kept alive.

Other JDKs have different logging flags and formats; always verify support on the actual runtime.

## 9. Using Metrics to Identify Classloader Leaks

A typical scenario:

~~~text
Plugin generation 1 -> loader A -> 100 classes
Plugin generation 2 -> loader B -> 100 classes
Plugin generation 3 -> loader C -> 100 classes
...
Host still retains references to A, B, C
       |
       v
getLoadedClassCount() grows long-term
getTotalLoadedClassCount() grows long-term
getUnloadedClassCount() grows little or not at all
Metaspace may grow
~~~

However, **this is only a warning signal, not conclusive proof**.

### 9.1. Pre/Post-Deployment Analysis Model

| Time Point | Total | Current | Unloaded | Notes |
|---|---:|---:|---:|---|
| Before deploy | 10,000 | 9,900 | 100 | Baseline |
| After plugin deploy | 10,300 | 10,200 | 100 | Plugin classes loaded |
| After undeploy, wait, and observed GC | 10,350 | 10,050 | 300 | Partially unloaded |
| After multiple redeploys | 12,500 | 11,900 | 600 | Trend needs investigation |

All **values in the table are hypothetical data for learning how to read the metrics**, not empirical results.

In particular, from this example alone it is impossible to determine exactly which classes are retained or whether GC triggers class unloading immediately. You need to observe **within the same JVM** and correlate with deployment events, memory pools, classloader statistics, heap dumps, and the plugin lifecycle.

### 9.2. Why an Always-Increasing Total Does Not Mean a Leak

`TotalLoadedClassCount` is a cumulative counter and therefore **will not decrease**, even if the JVM unloads every class belonging to old plugins. A healthy system can still see total increase for hours because:

- The framework initializes new features.
- Dynamic proxies, lambdas, or generated classes appear as new workloads arrive.
- Plugins are legitimately updated.
- New application code paths are hit for the first time.
- JVM/application warm-up has not finished yet.

A more concerning signal is when the **currently loaded class count** continues to climb across multiple steady-state cycles and fails to drop when lifecycle/GC conditions allow unloading, especially when metaspace and the loader count also increase.

### 9.3. Why No Increase in Unloaded Does Not Confirm a Leak

Class unloading is typically tied to **garbage collection and the reachability of the defining loader**. There is no guarantee that `close()` or `System.gc()` will cause the count to increase immediately. JVM flags, the collector, memory pressure, and references still holding the class or loader all play a role.

Do not write a test like:

~~~java
System.gc();
assert bean.getUnloadedClassCount() > before;
~~~

as a **mandatory pass condition** across all JDKs; this is an anti-pattern because GC and class unloading are non-deterministic.

## 10. When the Class Count Grows, Where Should You Look for the Holder?

`ClassLoadingMXBean` only provides JVM-wide aggregate metrics; it does not point out which cache, thread, or plugin loader is retaining classes. If `LoadedClassCount`, metaspace, and the loader count grow across multiple redeploy cycles, investigate common retention sources: host static registries, listeners/callbacks, queued tasks, thread pool TCCLs, `ThreadLocal`, provider caches, JNI references, and plugin-owned executors.

To distinguish among them, combine `jcmd VM.classloader_stats`/JFR with a heap dump and **Path to GC Roots**; confirm that the holder is still unnecessary after the plugin stops before concluding it is a leak. The article on JFR, heap dumps, and GC roots walks through proving retention, whereas this article focuses on **counting classes and building metric time series**.

## 11. Combining with Metaspace and Memory Metrics

A loaded class consumes metadata/memory in the JVM, but **there is no fixed conversion formula like “1 class = X bytes of metaspace”**. Its size depends on methods, the constant pool, annotations, class structure, runtime implementation, and many other factors.

`ClassLoadingMXBean` **does not have** a method like:

~~~java
bean.getMetaspaceBytes();
~~~

This is a **non-existent API**, shown only to warn against misconceptions. To measure memory, use `MemoryPoolMXBean`, `MemoryMXBean`, JVM tools, or JFR.

Example reading memory pools whose names contain Metaspace (suitable for HotSpot, **not portable across pool names**):

~~~java
import java.lang.management.ManagementFactory;
import java.lang.management.MemoryPoolMXBean;
import java.lang.management.MemoryUsage;

for (MemoryPoolMXBean pool
        : ManagementFactory.getMemoryPoolMXBeans()) {
    if (pool.getName().contains("Metaspace")) {
        MemoryUsage usage = pool.getUsage();
        if (usage != null) {
            System.out.println(usage.getUsed());
        }
    }
}
~~~

This is an illustrative snippet; pool names may vary across JVMs, and the byte output depends on the runtime. Do not use `Metaspace used` to infer the number of leaked classes on a one-to-one basis.

### When Are Additional Tools Needed?

| Question | Tool / Signal |
|---|---|
| How many classes have been loaded in total? | `ClassLoadingMXBean.getTotalLoadedClassCount()` |
| How many classes are currently loaded? | `getLoadedClassCount()` |
| How many have been unloaded? | `getUnloadedClassCount()` |
| Which class was loaded from which JAR? | Unified JVM class-loading logs, JFR/JVM-specific tools |
| How many classloaders are currently alive? | JFR, `jcmd`/VM-specific classloader stats, or heap analysis |
| Is Metaspace growing? | `MemoryPoolMXBean`/JVM memory metrics |
| Why is the plugin loader not unloading? | Heap dump reference paths, thread/TCCL inspection, native references |
| Is the classloader still holding JAR handles? | Lifecycle log, URLClassLoader close, OS file handle tools |

## 12. Differences Between Class Loading, Linking, and Initialization

Compiling a Java source file into `.class` **does not mean the JVM has loaded it**. A loader must locate the appropriate definition, the JVM must link/verify/resolve it according to the rules, and the class may be initialized upon active use.

~~~text
Source .java
     |
   javac
     |
 .class file / JAR entry
     |
 ClassLoader.loadClass(...)
     |
 JVM class loading
     |
 Linking (verify/prepare/resolve as needed)
     |
 Initialization (static init if required)
     |
 Instance/method execution
~~~

`ClassLoadingMXBean` observes **class loading/unloading counts**, and does not provide a separate counter for every verification, linking, or initialization step. Do not use “totalLoaded increased by 1” to conclude that a class's constructor has executed.

Example:

~~~java
Class<?> type =
        Class.forName("experiment.Marker", false, pluginLoader);
~~~

This is an illustrative snippet with an appropriate `pluginLoader`. The call can load/link the class without **requiring class initialization** because `initialize=false`. TotalLoaded may increase, even though the static initializer has not run yet.

### Class Identity Across Multiple Loaders

Two loaders can load the same class name yet produce **two separate runtime types**:

~~~text
("experiment.Marker", LoaderA) !=
("experiment.Marker", LoaderB)
~~~

`ClassLoadingMXBean` **does not merge two types just because they share the same name** into a single logical entry by name. It measures the runtime classes loaded in the JVM. This is why the loaded class count increases when creating plugin loaders that define their own copies of the same dependency.

Do not create a new loader for every request either: multiple duplicate class definitions can cause increased memory usage and classloading overhead.

## 13. Common Mistakes When Using ClassLoadingMXBean

1. **“Total loaded is the number of classes still in memory.”** False: it is the cumulative count since the JVM started.
2. **“Unloaded is the number of classes deleted from a JAR.”** False: this is the runtime class unloading count and has nothing to do with deleting JAR files.
3. **“Currently loaded never decreases.”** False: the JVM can unload classes when GC and reachability conditions are met.
4. **“`ClassLoadingMXBean` returns class names.”** False: it provides counts, not a list of classes, JARs, or loaders.
5. **“`ClassLoadingMXBean` belongs to each ClassLoader.”** False: the metrics have **JVM-wide** scope.
6. **“A class name is counted only once across the entire JVM.”** False: the same binary name defined by different loaders produces distinct runtime types.
7. **“Three calls reading the counters form an atomic snapshot.”** False: class loading/unloading can happen between them.
8. **“`getTotalLoadedClassCount()` must decrease on GC.”** False: it is a cumulative counter.
9. **“If the unloaded count has not increased after `System.gc()`, it is definitely a leak.”** False: synchronous immediate GC/unloading is not guaranteed.
10. **“An increase in loaded count once after startup proves a leak.”** False: normal warm-up and feature loading also increase it.
11. **“Metaspace bytes can be computed as loaded classes × a constant.”** False: metadata footprint varies.
12. **“`setVerbose(true)` only enables logging for the current thread.”** False: it is a global JVM setting.
13. **“`setVerbose(true)` always prints to stdout in the same format.”** False: the output format and stream are determined by the JVM implementation.
14. **“Reading the bean via JMX requires opening a remote server.”** False: it can be obtained within the same JVM via `ManagementFactory` or the platform MBeanServer.
15. **“The bean can force the JVM to unload one specific class.”** False: there is no API to unload individual classes by name.
16. **“Closing a plugin loader is equivalent to class unloading.”** False: closing handles and class unloading are two different mechanisms.
17. **“Counting classes is sufficient to diagnose every memory leak.”** False: there are also threads, heap objects, native memory, metaspace, and classloader reachability.
18. **“Counters from multiple processes can be summed without process identity.”** False: you need to attach PID/JVM start time to handle counter resets and avoid mixing up processes.
19. **“A `Class<?>` from loader A can be reused as a class from loader B.”** False: runtime class identity depends on the defining loader.
20. **“`getLoadedClassCount()` reflects the number of `.class` files in a package or JAR.”** False: it counts currently loaded runtime classes, not by scanning the filesystem.

## 14. Observability Checklist Before Concluding a Classloader Leak

- [ ] Obtain the bean properly via `ManagementFactory.getClassLoadingMXBean()`.
- [ ] Record all three metrics explicitly: total loaded, current loaded, and total unloaded.
- [ ] Distinguish **cumulative counters** from **instantaneous gauges**.
- [ ] Attach a sample timestamp, PID/process identity, and JVM start time.
- [ ] Collect multiple samples from the same JVM, not across separate `java` invocations.
- [ ] Compute deltas and rates over the exact time interval.
- [ ] Compare before/after deployment, redeploy, and shutdown under the same workload.
- [ ] Allow the JVM enough time for GC/unloading when evaluating trends; do not require a single GC to pass a test.
- [ ] Monitor Metaspace and loader counts from appropriate sources if a leak is suspected.
- [ ] Log class sources and loader IDs when you need to pinpoint a specific plugin.
- [ ] Inspect caches, TCCL, threads, scheduled tasks, callbacks, registries, and JNI refs.
- [ ] Have a mechanism to drain and then close URLClassLoader when using plugin JARs.
- [ ] Do not leave `setVerbose(true)` enabled indefinitely on high-traffic JVMs.
- [ ] Restrict JMX access permissions; avoid unprotected remote exposure.
- [ ] Do not hard-code expected counters for any specific JVM.
- [ ] If the application is modular, distinguish class-loading stats from module readability/opens/exports.

## 15. Self-Check Questions

**Question 1.** How do `getTotalLoadedClassCount()` and `getLoadedClassCount()` differ?

**Answer:** Total is the cumulative number of classes ever loaded since JVM startup; current is the number of classes currently loaded at the time of reading. Total does not decrease due to class unloading.

**Question 2.** What does it mean when `getUnloadedClassCount()` increases after a period of time?

**Answer:** The JVM unloaded additional classes during that period. You cannot yet identify which specific classes or loaders were unloaded without additional diagnostic sources.

**Question 3.** Can you conclude there is a classloader leak solely because TotalLoaded keeps increasing?

**Answer:** No. Total is cumulative and increases with legitimate activity. You need to look at current, unloaded, metaspace, loader count, and retention/lifecycle over time.

**Question 4.** Is `LoadedClassCount` broken down by plugin JAR?

**Answer:** No. It is a JVM-wide metric. To trace specific classes or loaders, you need logs, JFR, jcmd, or heap analysis.

**Question 5.** Two URLClassLoaders define the same `experiment.Marker`. Are there two runtime class types?

**Answer:** Yes. The same binary name with different defining loaders produces two `Class<?>` objects with distinct identities; both contribute to classloading counters.

**Question 6.** Does `URLClassLoader.close()` guarantee that `UnloadedClassCount` increases immediately?

**Answer:** No. It closes file/JAR handles, whereas class unloading depends on references and GC.

**Question 7.** Does `setVerbose(true)` change settings for a single plugin only?

**Answer:** No. It changes verbose class-loading output for the entire JVM; multiple threads can be affected.

**Question 8.** Which ObjectName is needed when reading via JMX?

**Answer:** `java.lang:type=ClassLoading`, with attributes such as `LoadedClassCount`, `TotalLoadedClassCount`, and `UnloadedClassCount`.

**Question 9.** Why do three consecutively read counters sometimes fail to match `total == current + unloaded` exactly?

**Answer:** Because the calls do not form an atomic snapshot; the JVM can load or unload classes between reads.

**Question 10.** After one week, currently loaded classes and metaspace increase after every redeploy, while unloaded barely increases. What is the next step?

**Answer:** Investigate retention: heap dump, loader statistics, threads/TCCL, static caches, service providers, JNI refs, and the plugin lifecycle. Counters are a signal, not enough for a final conclusion.

## 16. Diagnostic Decision Flowchart

~~~text
                 Observe class loading in the JVM
                              |
                  ManagementFactory.get...
                              |
                     ClassLoadingMXBean
                      /       |       \
                     /        |        \
            total loaded    current    unloaded
             (counter)       (gauge)   (counter)
                    \         |        /
                     \        |       /
                       Samples + time
                              |
                    Compute deltas/rates
                              |
                      Abnormal growth?
                        /           \
                      No            Yes
                       |             |
                 Save baseline    Check Metaspace,
                                  loader count,
                                  deployment events
                                      |
                              Suspected retention?
                                   /        \
                                 No         Yes
                                  |          |
                             Continue       Heap dump,
                             observing      TCCL/threads/
                                            callbacks
                                                  |
                                          Fix lifecycle,
                                          re-measure after deploy
~~~

**Conclusion:** `ClassLoadingMXBean` is a tool for **measuring three aspects of class loading**: **total loaded**, **currently loaded**, and **unloaded**. Cumulative counters help measure overall activity volume, and the current gauge helps observe retention; however, identifying a classloader leak must rely on **multi-sample trends within the same JVM** and specialized loader/memory diagnostic tools. Do not draw a one-sided conclusion from an increasing total or from GC not unloading classes immediately.
