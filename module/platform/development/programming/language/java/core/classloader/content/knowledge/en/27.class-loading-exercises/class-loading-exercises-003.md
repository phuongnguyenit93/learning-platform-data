# Building a ClassLoader That Loads Bytecode Directly from Memory

## 1. Exercise Objectives

A `ClassLoader` is not required to obtain class definitions from `.class` files on disk, from a JAR, or over a URL. The JVM needs a **byte array representing a valid class file**, an appropriate class name, and a defining loader with permission to define the class. The source of the bytes can be:

- The result of compiling Java source directly inside the program using `JavaCompiler`.
- Bytecode generated by a bytecode generator.
- An artifact read, checked, and kept in a memory cache.
- Bytes transferred over IPC/network or read from a data store (if the application trusts that source and has an appropriate verification policy).

The focus is on building a **binary name → byte[] map**-style loader so that classes are defined from memory using protected `ClassLoader.defineClass`. We then combine this loader with `javax.tools.JavaCompiler` to create an example that **compiles and loads completely in RAM**, without needing to write a `Hello.class` file to disk.

This exercise belongs to the **Practice** group of the *Java core – classloader* module. After this exercise, you will be able to:

1. Write a `MemoryLoader extends ClassLoader` subclass and override `findClass(String)` properly.
2. Compile Java source into `byte[]` using `JavaCompiler` and a custom `JavaFileManager`.
3. Put the bytes into a map and call `loadClass` to create a runtime `Class<?>`.
4. Use reflection or a shared contract to create an object and invoke a method.
5. Verify that **loading the same name on the same loader** returns the same class, while **two different loaders** can produce two different runtime types.
6. Distinguish **loading from memory** from **exposing a `.class` resource via `getResource`**.
7. Properly handle `ClassNotFoundException`, `LinkageError`, classfile version, parent delegation, initialization, and memory leak risks.
8. Know the limitations of the demo compared to production, where bytecode must be verified and the classloader lifecycle must be managed.

**Version:** Java 17 or later. The example requires no Maven/Gradle, Internet, external JARs, or non-public JDK APIs. The complete program has been compiled with `javac --release 17` and run in practice.

## 2. Understanding “Loading Bytecode from Memory” Correctly

### 2.1. Source → byte[] → runtime Class

A typical flow:

~~~text
Hello.java
  |
  | javac
  v
Hello.class on disk
  |
  | ClassLoader reads file/JAR
  v
byte[] classfile
  |
  | defineClass
  v
Class<?> in the JVM
~~~

In this exercise, we replace it with:

~~~text
Java source in a String
  |
  | JavaCompiler (JSR 199)
  v
JavaFileObject containing ByteArrayOutputStream
  |
  | snapshot()
  v
Map<String,byte[]> in RAM
  |
  | MemoryLoader.findClass(name)
  | -> defineClass(name, bytes, 0, bytes.length)
  v
Class<?> in the JVM
  |
  | Reflection
  v
Instance + method invocation
~~~

The difference is that **the input bytes are kept in a map and passed directly to `defineClass`**. There is no step that creates a `memory/generated/Hello.class` file on disk. However, the Java VM still creates class information at runtime, including metadata/linking structures, and may generate native/JIT code during normal operation.

**“From memory” does not mean “no metadata, no memory footprint, or no JVM safety checks”.**

### 2.2. Binary Name Differs from Resource Path

If the source declares:

~~~java
package memory.generated;

public final class Hello {
    public String greet(String person) {
        return "MEMORY:" + person;
    }
}
~~~

then:

- **Binary name:** `memory.generated.Hello`.
- **Typical resource path:** `memory/generated/Hello.class`.
- **Source path representation in the compiler tool:** `memory/generated/Hello.java`.
- **Runtime class identity:** depends on **binary name + defining ClassLoader**, not just the name string.

The loader's map should use binary names as keys:

~~~java
Map<String, byte[]> compiled = Map.of(
    "memory.generated.Hello", classfileBytes);
~~~

This is an illustrative snippet requiring a `classfileBytes` variable that holds actual classfile bytecode. If you accidentally use the key `memory/generated/Hello.class` and then call `loadClass("memory.generated.Hello")`, the map lookup will not match.

### 2.3. `ClassLoader.loadClass` and `findClass` Are Not the Same

- `loadClass(String)` is the public entry point typically used by callers.
- The default implementation handles the loaded-class cache, parent delegation, and only calls `findClass` when needed.
- `findClass(String)` is the hook that subclasses override to **locate bytes and define classes managed by their own loader**.
- `defineClass(...)` is the operation that actually turns classfile bytes into a class defined by the JVM for this loader.

Therefore, this exercise only needs to override **`findClass`**, without rewriting `loadClass` yourself. Keeping the default implementation allows you to take advantage of synchronization, `findLoadedClass`, and parent delegation to avoid many hard-to-reproduce bugs.

## 3. Minimal MemoryLoader: The Core Part to Remember

Once you have a trusted `Map<String, byte[]>` that is immutable after construction, the main loader only needs:

~~~java
import java.util.Map;

final class MemoryLoader extends ClassLoader {
    private final Map<String, byte[]> bytecodes;

    MemoryLoader(Map<String, byte[]> bytecodes, ClassLoader parent) {
        super(parent);
        this.bytecodes = Map.copyOf(bytecodes);
    }

    @Override
    protected Class<?> findClass(String name)
            throws ClassNotFoundException {
        byte[] bytes = bytecodes.get(name);
        if (bytes == null) {
            throw new ClassNotFoundException(name);
        }
        return defineClass(name, bytes, 0, bytes.length);
    }
}
~~~

This is **a complete class snippet for the loading mechanism**, though it does not yet have a `main` method or generate bytecode. Key steps:

1. `MemoryLoader` extends `ClassLoader` with a specified parent.
2. The map maps binary name → Java classfile bytes.
3. `findClass(name)` looks up the byte array.
4. If there is no entry, **throw `ClassNotFoundException(name)`** — do not return `null`.
5. If found, call `defineClass(name, bytes, 0, bytes.length)`.
6. The JVM checks the classfile, name, and verification/linking constraints per the contract, and creates a `Class<?>` when valid.

**Note on immutability:** `Map.copyOf` only copies the map structure; **it does not clone the byte[] arrays**. If the caller modifies the arrays after supplying them to the loader, it will create races and unpredictable behavior. In production, create **defensive copies** of each byte array at the boundary, and do not pass a mutable map into untrusted code. In the full demo, the compiler creates dedicated arrays and no other thread modifies them.

### 3.1. Why Not Call `defineClass` Directly from Application Code?

`defineClass` is a protected API. Placing the call inside a `ClassLoader` subclass is the supported approach. It is not a public static method like:

~~~java
Class<?> clazz = ClassLoader.defineClass(...);
~~~

The line above is **intentionally incorrect code**. The full example calls `defineClass` from `MemoryLoader.findClass`, and then application code calls `loader.loadClass(binaryName)`.

### 3.2. Why Not Override `loadClass` Right from the Start?

Overriding `loadClass` yourself and always calling `defineClass` easily causes a race condition or a duplicate-definition error:

~~~text
Thread A: findClass("X") -> defineClass X -> succeeds
Thread B: findClass("X") -> defineClass X -> LinkageError
~~~

The standard `loadClass` implementation properly synchronizes the critical section and checks `findLoadedClass` before using the `findClass` hook. If you need a child-first plugin policy, that is an advanced design requiring locking with `getClassLoadingLock(name)` and thorough cache/delegation checks. You should not change the policy just to solve loading bytecode in RAM.

### 3.3. Parent-First Can “Beat” MemoryLoader's Map

Suppose the application loader already has the `memory.generated.Hello` class on `-cp`. When the child calls `loadClass("memory.generated.Hello")`, the parent may return the parent's class **before `findClass` is called**. As a result, you might think the memory map is being ignored, when in fact this is parent-first delegation working as designed.

To reproduce this exercise:

- Compile only **`MemoryLoaderDemo.java`** as the launcher.
- Keep the `Hello` source in a **String**, with no `Hello.class` on the app classpath.
- Call `MemoryLoader.loadClass(NAME)` with the parent being the loader that defines the host.
- Do not accidentally add another JAR that also contains `memory.generated.Hello` to the application classpath.

## 4. Generating Bytecode in RAM with JavaCompiler

### 4.1. What Is `javax.tools.JavaCompiler`?

`ToolProvider.getSystemJavaCompiler()` retrieves the Java compiler provided by the currently running JDK:

~~~java
JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
if (compiler == null) {
    throw new IllegalStateException("Run with a JDK, not a JRE");
}
~~~

On JDK 17+, the compiler tool is located in the `java.compiler` module (API) and the JDK's implementation/compiler support (typically the `jdk.compiler` module). If running with a custom runtime image that does not contain the system compiler, `getSystemJavaCompiler()` may return `null`. In that case, you cannot use the “compile source at runtime” approach without adding a compiler; **MemoryLoader can still load precompiled bytes**.

### 4.2. `JavaFileObject` for Java Source from a String

Instead of pointing the compiler to a `.java` file, we create a `SimpleJavaFileObject` carrying a synthetic URI and returning the source string via `getCharContent`:

~~~java
static final class SourceFile extends SimpleJavaFileObject {
    final String code;

    SourceFile(String name, String code) {
        super(URI.create("string:///" +
              name.replace('.', '/') + Kind.SOURCE.extension),
              Kind.SOURCE);
        this.code = code;
    }

    @Override
    public CharSequence getCharContent(boolean ignoreEncodingErrors) {
        return code;
    }
}
~~~

This is a **snippet inside a class**, requiring `URI` and `javax.tools.SimpleJavaFileObject` imports. `string:///...` is a **URI naming the JavaFileObject**, not a file that must exist or an actual network protocol.

### 4.3. `JavaFileObject` Writing `.class` into a `ByteArrayOutputStream`

Normally, the compiler's output is a `.class` file. We replace the destination with an object that writes into RAM:

~~~java
static final class ClassFile extends SimpleJavaFileObject {
    final ByteArrayOutputStream out = new ByteArrayOutputStream();

    ClassFile(String name, Kind kind) {
        super(URI.create("bytes:///" +
              name.replace('.', '/') + kind.extension), kind);
    }

    @Override
    public OutputStream openOutputStream() {
        return out;
    }

    byte[] bytes() {
        return out.toByteArray();
    }
}
~~~

This snippet requires `ByteArrayOutputStream`, `OutputStream`, `URI`, and `SimpleJavaFileObject` imports. The `bytes:///...` URI is only an identifier for the compiler output object; the actual byte array resides in the `out` buffer.

### 4.4. Custom JavaFileManager Receiving Each Compiled Class

A single compilation run can emit **multiple `.class` outputs** from one source (inner/nested classes, auxiliary classes). Therefore, you should not have just one `byte[] compiledOutput` variable for all names. We create a file manager:

~~~java
static final class MemoryFileManager
        extends ForwardingJavaFileManager<StandardJavaFileManager> {
    final Map<String, ClassFile> outputs = new HashMap<>();

    MemoryFileManager(StandardJavaFileManager delegate) {
        super(delegate);
    }

    @Override
    public JavaFileObject getJavaFileForOutput(
            Location location, String className,
            JavaFileObject.Kind kind, FileObject sibling) {
        ClassFile file = new ClassFile(className, kind);
        outputs.put(className, file);
        return file;
    }

    Map<String, byte[]> snapshot() {
        Map<String, byte[]> all = new HashMap<>();
        outputs.forEach((name, file) -> all.put(name, file.bytes()));
        return Map.copyOf(all);
    }
}
~~~

This is a snippet inside an enclosing class with imports for JavaCompiler/JavaFileManager, HashMap/Map, FileObject, and JavaFileObject. `getJavaFileForOutput` is called by the compiler when it wants to write class bytes. We store each output by the **binary class name** provided by the compiler.

**Actual effect:** the compiler writes the classfile into RAM, and then `snapshot()` retrieves the byte arrays. In the single-class `Hello` example, there will be one entry `memory.generated.Hello`; with inner classes, there can also be `Outer$Inner`.

## 5. Complete, Runnable Java 17+ Program

The complete example below compiles the `memory.generated.Hello` source stored in a String, uses `MemoryLoader` to define the bytes, invokes a method via reflection, and then loads the same bytes in a second loader.

### 5.1. Project Tree

~~~text
memory-loader-demo/
├── MemoryLoaderDemo.java
└── out/
    └── MemoryLoaderDemo*.class  (created when compiling the launcher with javac)
~~~

No `Hello.java` file is needed and **there is no `Hello.class` file on disk**. Use JDK 17+ to run the program from a directory where you have permission to create the launcher's files; the entire compilation output of **the dynamically generated `Hello` class** remains in memory.

### 5.2. The `MemoryLoaderDemo.java` File

~~~java
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.OutputStream;
import java.net.URI;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import javax.tools.DiagnosticCollector;
import javax.tools.FileObject;
import javax.tools.ForwardingJavaFileManager;
import javax.tools.JavaCompiler;
import javax.tools.JavaFileObject;
import javax.tools.SimpleJavaFileObject;
import javax.tools.StandardJavaFileManager;
import javax.tools.ToolProvider;

public final class MemoryLoaderDemo {
    static final String NAME = "memory.generated.Hello";
    static final String CODE = """
            package memory.generated;
            public final class Hello {
                public String greet(String person) {
                    return "MEMORY:" + person;
                }
            }
            """;

    static final class SourceFile extends SimpleJavaFileObject {
        final String code;
        SourceFile(String name, String code) {
            super(URI.create("string:///" +
                  name.replace('.', '/') + Kind.SOURCE.extension),
                  Kind.SOURCE);
            this.code = code;
        }
        @Override
        public CharSequence getCharContent(boolean ignoreEncodingErrors) {
            return code;
        }
    }

    static final class ClassFile extends SimpleJavaFileObject {
        final ByteArrayOutputStream out = new ByteArrayOutputStream();
        ClassFile(String name, Kind kind) {
            super(URI.create("bytes:///" +
                  name.replace('.', '/') + kind.extension), kind);
        }
        @Override
        public OutputStream openOutputStream() {
            return out;
        }
        byte[] bytes() { return out.toByteArray(); }
    }

    static final class MemoryFileManager
            extends ForwardingJavaFileManager<StandardJavaFileManager> {
        final Map<String, ClassFile> outputs = new HashMap<>();

        MemoryFileManager(StandardJavaFileManager delegate) {
            super(delegate);
        }

        @Override
        public JavaFileObject getJavaFileForOutput(
                Location location, String className,
                JavaFileObject.Kind kind, FileObject sibling) {
            ClassFile file = new ClassFile(className, kind);
            outputs.put(className, file);
            return file;
        }

        Map<String, byte[]> snapshot() {
            Map<String, byte[]> all = new HashMap<>();
            outputs.forEach((name, file) -> all.put(name, file.bytes()));
            return Map.copyOf(all);
        }
    }

    static final class MemoryLoader extends ClassLoader {
        final Map<String, byte[]> bytecodes;

        MemoryLoader(Map<String, byte[]> bytecodes) {
            super(MemoryLoaderDemo.class.getClassLoader());
            this.bytecodes = bytecodes;
        }

        @Override
        protected Class<?> findClass(String name)
                throws ClassNotFoundException {
            byte[] bytes = bytecodes.get(name);
            if (bytes == null) {
                throw new ClassNotFoundException(name);
            }
            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Exception {
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null) {
            throw new IllegalStateException("Run with a JDK, not a JRE");
        }

        DiagnosticCollector<JavaFileObject> diagnostics =
                new DiagnosticCollector<>();
        Map<String, byte[]> compiled;

        try (StandardJavaFileManager standard =
                     compiler.getStandardFileManager(
                             diagnostics, null, null);
             MemoryFileManager files = new MemoryFileManager(standard)) {
            boolean ok = compiler.getTask(
                    null, files, diagnostics,
                    List.of("--release", "17", "-proc:none"),
                    null, List.of(new SourceFile(NAME, CODE))).call();
            if (!ok) {
                throw new IllegalStateException(
                        "Compilation failed: " + diagnostics.getDiagnostics());
            }
            compiled = files.snapshot();
        }

        System.out.println("compiledNames=" + compiled.keySet());
        System.out.println("validClassBytes="
                + (compiled.get(NAME).length > 4));

        MemoryLoader first = new MemoryLoader(compiled);
        Class<?> c1 = first.loadClass(NAME);
        System.out.println("definedByMemoryLoader="
                + (c1.getClassLoader() == first));
        System.out.println("repeatedLoadSameClass="
                + (first.loadClass(NAME) == c1));

        Object obj = c1.getDeclaredConstructor().newInstance();
        Object reply = c1.getMethod("greet", String.class)
                         .invoke(obj, "Java");
        System.out.println("result=" + reply);

        MemoryLoader second = new MemoryLoader(compiled);
        Class<?> c2 = second.loadClass(NAME);
        System.out.println("differentLoaderDifferentClass=" + (c1 != c2));
        System.out.println("parentStringShared="
                + (first.loadClass("java.lang.String") == String.class));
        System.out.println("resourceNotAutoPublished="
                + (first.getResource("memory/generated/Hello.class") == null));

        try {
            MemoryLoaderDemo.class.getClassLoader().loadClass(NAME);
            System.out.println("appLoaderFindsGenerated=true");
        } catch (ClassNotFoundException expected) {
            System.out.println("appLoaderFindsGenerated=false");
        }

        try {
            first.loadClass("memory.generated.Absent");
            System.out.println("missingClassRejected=false");
        } catch (ClassNotFoundException expected) {
            System.out.println("missingClassRejected=true");
        }
    }
}
~~~

**Key takeaway:** `ClassFile` is written out by the compiler in RAM; `MemoryFileManager.snapshot()` provides the byte map; `MemoryLoader.findClass` is the only place that calls `defineClass`. The host does not import `memory.generated.Hello` and has no runtime dependency on a `Hello.class` file.

| Output | What It Verifies |

| `definedByMemoryLoader=true` | The JVM assigned the defining loader of the generated class to the `first` instance |

## 6. Why Doesn't `getResource("...Hello.class")` Find the Bytes?

A common mistake when building a MemoryLoader is assuming:

~~~java
loader.getResource("memory/generated/Hello.class");
~~~

will automatically return a URL because the loader already holds the bytecode map. **Incorrect.** `findClass` is the hook for finding/defining classes, whereas `findResource`/`findResources` are **separate** hooks for resource lookup.

In the demo:

~~~text
Map entry:
  memory.generated.Hello -> byte[]

loadClass("memory.generated.Hello"):
  -> findClass -> defineClass -> Class<?>

getResource("memory/generated/Hello.class"):
  -> parent resource search
  -> child findResource (not overridden)
  -> null
~~~

This is normal. If a framework needs to expose `.class` files or JSON/config/resources from RAM, you must add a **resource store** and an appropriate `URL`/`URLConnection`/stream solution, or provide an API that accepts bytes directly. Do not silently write files to disk just to make `getResource` work if the original requirement is RAM-only.

### 6.1. Two Namespaces Should Be Clearly Designed

- **Class map:** `Map<String,byte[]>`, keyed by binary class name.
- **Resource map:** `Map<String,byte[]>`, keyed by slash-separated resource path.

These two maps can point to the same classfile bytes for the path `memory/generated/Hello.class`, but they are **not automatically linked** to each other. You need to define how parent/resource lookups work and the URL exposure permissions if the application requires them.

### 6.2. CodeSource Location May Not Exist

When calling `ClassLoader.defineClass(name, bytes, ...)` without passing an explicit `ProtectionDomain`, the JDK provides a default protection domain. You **should not assume CodeSource has a location URL pointing to a JAR file**.

A class loaded solely from RAM may have a `CodeSource` with `getLocation()==null`. This is not a sign that there is no defining loader or that the bytecode is corrupted. If provenance is needed, you must **store separate metadata when receiving the bytecode** (artifact ID/hash, verified origin, version) rather than inferring it from `getResource`.

## 7. Two Loaders Using the Same byte[] Create Two Different Class<?> Objects

The runtime identity of an ordinary class consists of:

~~~text
(binary class name, defining ClassLoader)
~~~

In the demo, both have the name `memory.generated.Hello`:

~~~java
Class<?> c1 = first.loadClass(NAME);
Class<?> c2 = second.loadClass(NAME);
System.out.println(c1 == c2); // false
~~~

This snippet uses the demo variables already created. The two `Class<?>` objects are different because **the defining loaders are different**, even though the bytes are identical.

Consequences:

- You cannot cast a `Hello` instance from loader A to loader B's `Hello` type merely because their binary names are the same.
- Reflection using each loader's `Class<?>` can still operate on the corresponding instances properly.
- If you want type-safe host/plugin communication, place a **shared interface/DTO** in the parent loader and have the generated class implement that contract.
- Do not let the generated library contain a copy of the shared API and accidentally child-first define a separate API; this easily causes `ClassCastException`, `LinkageError`, or `ServiceConfigurationError`.

### 7.1. You Cannot “Redefine” the Same Class in the Same Loader by Modifying the Map

After `first.loadClass(NAME)` succeeds, changing the bytes in the map does not cause the JVM to automatically replace `c1`. Subsequent calls to `loadClass(NAME)` normally return the already loaded class.

If you attempt to call `defineClass` again with the same binary name in the same loader, you may encounter a `LinkageError` due to duplicate definition. To create a new version, you typically must use a **new MemoryLoader instance** and manage references/lifecycle appropriately; this also creates a **new runtime type identity**.

### 7.2. When Is a Class Initialized?

Calling `MemoryLoader.loadClass(NAME)` creates/loads the class; it does not automatically imply running static initialization. In the demo, `Hello` has no static initializer.

If you add:

~~~java
static {
    System.out.println("HELLO_INITIALIZED");
}
~~~

to the compiled class source, this line will be printed when the class is **initialized** (for example, when creating a new instance), not merely because we obtained a `Class<?>` from `loadClass`.

Distinguish:

~~~text
load/define -> verify/link/resolution (when needed) -> initialize (active use)
~~~

With `Class.forName(NAME, true, first)`, the `true` flag requests initialization, whereas `Class.forName(NAME, false, first)` does not require immediate initialization. Do not confuse this with `Class.forName(Module, String)`, which has a different contract.

## 8. Errors and Edge Cases to Handle

### 8.1. Class Not Found in the Map

~~~java
byte[] bytes = bytecodes.get(name);
if (bytes == null) {
    throw new ClassNotFoundException(name);
}
~~~

This is the proper behavior in `findClass`. `ClassNotFoundException` is the checked exception for the active class-lookup path; do not return `null` and let external code fail with a `NullPointerException`.

If the generated class references a helper class that is neither in the map nor found by the parent, you may get a `NoClassDefFoundError` when the VM tries to link or use the helper. You must store **all output classes**, not only the entry-point class.

### 8.2. Malformed Class Bytes

`defineClass` may throw:

- `ClassFormatError`: the classfile structure is invalid.
- `UnsupportedClassVersionError`: the classfile target version exceeds what the JVM supports.
- `VerifyError`: the bytecode violates verification rules.
- `NoClassDefFoundError` or other linkage errors when dependencies or binary names do not match.

Do not convert every `LinkageError` into a `ClassNotFoundException`; they have different causes and fixes. Preserve the stack trace/cause when debugging.

### 8.3. Binary Name Does Not Match Class File Contents

If the map has the key `memory.generated.Hello` while the bytecode declares `another.pkg.Hello`, `defineClass(name, bytes, ...)` may throw `NoClassDefFoundError` or a linkage error reporting a wrong name.

The key invariant to guarantee:

~~~text
requested name == map key == binary name in the classfile
~~~

In the example, the compiler passes the canonical `className` to `MemoryFileManager.getJavaFileForOutput`, so the map key is formed consistently with the class output.

### 8.4. Protected `java.*` Packages

Do not try to use a custom loader to define classes in `java.lang` or packages that the JVM does not allow application loaders to define. You may encounter a `SecurityException` due to protected package rules. You must also respect sealing and package metadata when loading from signed/sealed libraries.

This is a core namespace-protection rule, **not a general-purpose sandbox** against untrusted code.

### 8.5. Compiler Unavailable at Runtime

`ToolProvider.getSystemJavaCompiler()==null` occurs on runtimes without a compiler module (for example, some custom jlink images). Two options:

1. **Compile during the build/deploy phase** and pass the checked classfile bytes into the program.
2. Run on a JDK/runtime configured with a compiler.

`MemoryLoader` only needs bytes and does not depend on having a compiler. **Only the runtime compilation part requires `JavaCompiler`**.

### 8.6. Compiler Emits Multiple Classes

A single source containing inner classes, anonymous classes, or auxiliary top-level classes can produce multiple outputs:

~~~text
memory.generated.Outer
memory.generated.Outer$Inner
memory.generated.Helper
~~~

If the file manager only stores `Outer.class`, code paths using `Outer$Inner` may later throw `NoClassDefFoundError`. For that reason, the demo's `MemoryFileManager` **stores every name emitted by the compiler** instead of a single buffer.

### 8.7. Compile-Time and Runtime Dependencies Differ

`JavaCompiler` must resolve dependencies when compiling the source. `MemoryLoader`, in turn, must load the required classes at runtime. The two phases have **separate classpath/loader graphs**:

~~~text
JavaCompiler classpath/modulepath -> compile source
MemoryLoader parent + bytecode map -> runtime resolution
~~~

If the source references a library that was available at compile time, yet that library is neither in the parent nor in the map at runtime, the program can still throw `NoClassDefFoundError`. Do not assume that compilation success implies sufficient runtime visibility.

### 8.8. Concurrency and Race Conditions

Because the demo overrides **`findClass`, not `loadClass`**, the default implementation of `ClassLoader.loadClass` checks whether the class is already loaded and holds the corresponding lock. This is the maintainable path.

When building a compiler/file manager for concurrent requests:

- Do not share a single `ByteArrayOutputStream` across multiple class names or compilation tasks.
- Snapshot the map only after the compiler finishes.
- Create an immutable catalog per generation and do not modify byte arrays while the loader is reading them.
- If a custom child-first `loadClass` is required, you must protect `findLoadedClass + findClass/defineClass` inside the same synchronized block on `getClassLoadingLock(name)`.
- Separate caches/versions per tenant/plugin and manage cleanup.

Races in the producer map are a separate issue; ClassLoader synchronization itself does not automatically make every application map thread-safe.

## 9. Memory, Unloading, and Loader Lifecycle

### 9.1. The Byte Map Differs from JVM Class Metadata

After `defineClass` succeeds, the JVM maintains its own class information; this does not mean the byte arrays in the map are the only copy the JVM needs to keep. There are at least two categories of memory to consider:

- **Java heap:** `Map`, `byte[]` buffers, source strings, instances, and metadata held by the application.
- **VM/native/metaspace & code caches:** metadata/linking/JIT structures corresponding to the loaded classes.

Keeping all generations in a static registry will keep both the byte maps and the ClassLoader/classes/instances alive for a long time. If an in-server build tool compiles thousands of classes per minute, there must be a retention/eviction policy.

### 9.2. When Can a Loader Be Unloaded?

For an ordinary class, unloading depends on **its defining ClassLoader no longer being reachable** under the JVM's conditions. There is no API like:

~~~java
loader.unloadClass("memory.generated.Hello");
~~~

The line above is **nonexistent code**. You cannot remove an entry from the map and ask the JVM to “forget” an already defined `Class<?>`.

A sensible plugin reload workflow:

1. Stop accepting requests for the old generation.
2. Wait for or cancel still-running tasks under a clear policy.
3. Clean up instances, callbacks, listeners, thread locals, reflection caches, and TCCL references.
4. Drop references to the old generation's `MemoryLoader` and `Class<?>` objects.
5. Create a **new MemoryLoader instance** for the new generation's bytes.
6. Let the garbage collector reclaim class metadata when eligible; do not rely on an exact timing.

`System.gc()` does not guarantee immediate unloading. You should monitor appropriate memory/metrics if the application continuously generates classes.

### 9.3. MemoryLoader Is Not a Security Sandbox

Valid bytecode defined by a custom loader still runs in **the same JVM process as the host** and generally has the process's permissions for files/network/threads/resources. Using a separate ClassLoader provides **namespace isolation**, not automatic OS-level permission isolation.

Allowing users to input untrusted Java source and then compiling/loading it inside a JVM serving sensitive data poses a major risk. The compiler can also consume excessive CPU/RAM or trigger annotation processors if left uncontrolled. In the demo, `-proc:none` was used to disable annotation processing, but **that does not create a sandbox**.

For untrusted code, you need process/container/VM isolation with least-privilege OS permissions, quotas, network policy, artifact provenance, and IPC authorization. On JDK 24+, SecurityManager can no longer be enabled (JEP 486); do not rely on `SecurityManager` or `ProtectionDomain` to design a modern permission sandbox.

## 10. Deploying MemoryLoader in a Real-World Application

### 10.1. Designing the Input Contract

An API that creates a loader should accept **a trusted snapshot**:

~~~java
Map<String, byte[]> snapshot = new HashMap<>();
input.forEach((name, bytes) -> snapshot.put(name, bytes.clone()));

MemoryLoader loader =
        new MemoryLoader(Map.copyOf(snapshot), sharedApiLoader);
~~~

This is an illustrative snippet. `input` is the caller's map; `sharedApiLoader` is the parent ClassLoader containing the agreed contract. Cloning the byte arrays avoids depending on a mutable source. You should validate that `name` is non-null/non-empty and enforce limits on total bytes/class count according to policy.

### 10.2. Setting a Policy for Namespaces

Do not accept arbitrary binary names from an untrusted source and try to define them. You should specify:

- Which package prefix belongs to generated implementations, for example `memory.generated.*`.
- Which API packages must delegate to the parent.
- Do not create classes in packages reserved for the JDK.
- Avoid colliding with runtime packages that have unsatisfied sealing/certificate constraints.
- If the compiled source contains public classes, the package path and binary name must match.

Map keys/names from the compiler are more reliable than arbitrary map keys, yet input code must still have a clear origin/validation when deployed.

### 10.3. Sharing the API with the Host

If the host needs to invoke a generated implementation through an interface, for example:

~~~java
package shared.api;

public interface Operation {
    String execute(String argument);
}
~~~

then `Operation` should be defined by the **shared API loader/parent**. The dynamically generated source class can `implements shared.api.Operation`, while the implementation's bytes reside in the child MemoryLoader.

Then the host can do:

~~~java
Class<?> implementation = loader.loadClass("memory.generated.OpImpl");
Operation operation = (Operation)
        implementation.getDeclaredConstructor().newInstance();
System.out.println(operation.execute("hello"));
~~~

This is an architectural snippet, **not part of the runnable demo program in Section 5**, because the main example uses only reflection. When applying this pattern, ensure the compiler can locate `shared.api.Operation` and runtime child delegation sees **the same `Operation.class`** used by the host. If the parent and child define two versions of the API, a `ClassCastException` will still occur.

### 10.4. Logging and Diagnostics

On compilation failure, `DiagnosticCollector` contains line/column/error code details. You can handle it as:

~~~java
for (var diagnostic : diagnostics.getDiagnostics()) {
    System.err.println(
            diagnostic.getKind() + " line " + diagnostic.getLineNumber()
            + ": " + diagnostic.getMessage(null));
}
~~~

This is a snippet inside a method that has `diagnostics`. Do not log user source code/paths/secrets if they contain sensitive data. For runtime errors, log:

- The requested binary class name.
- The loader identity (and a host-assigned version/generation ID, not just `toString()`).
- Available class names in the snapshot (mindful of log privacy).
- Source/compiler diagnostics and target classfile major version.
- The full `ClassNotFoundException`/`LinkageError` stack trace and cause.
- The artifact bytes hash computed from the accepted data (if provenance is needed).

### 10.5. Size and Time Limits

Dynamic compilation is a pipeline that can consume memory. Production should have:

- Max source size, number of source files, number of output classes, and max classfile bytes.
- Timeouts for compilation/execution at an **enforced process boundary** if the code is untrusted.
- A mechanism so compiled byte arrays are not retained indefinitely.
- Compiler options controlling the classpath, module path, and annotation processors.
- Metrics for the number of generated classes and still-reachable ClassLoader generations.
- Cache keys based on source/options/dependency versions, not just the binary name.

Do not treat `Map.copyOf` or `try-with-resources` as sufficient to solve memory leaks of loaded classes.

## 11. Comparing Dynamic Bytecode Loading Approaches

| Approach | When to Use | Key Things to Remember |
|---|---|---|
| `ClassLoader.findClass` + `defineClass` from `byte[]` | The loader owns the generated classes' namespace, with multiple binary names | Parent delegation, runtime identity, lifecycle |
| `Lookup.defineClass(byte[])` | Defining an ordinary class in the lookup class's package/loader, with access constraints | Does not create a new loader automatically; package/nest/module rules |
| `Lookup.defineHiddenClass(...)` | A framework generating internal implementations that do not need to be looked up by name | Hidden classes are not discoverable via `Class.forName`/`loadClass` |
| `URLClassLoader` | Loading classes/resources from packaged URLs/JARs | Involves a filesystem/JAR path, not a pure in-memory byte map |
| `JavaCompiler` + custom file manager | Compiling Java source text into in-RAM bytecode | Requires a compiler module; separate output files/map |
| Bytecode library/generator | Generating classfile bytes without going through a Java source compiler | Must ensure the classfile is valid and compatible with the JVM target |
| ModuleLayer | Defining named modules and mapping loader(s) | JPMS module graph/access is not automatically created by a byte map |

This exercise intentionally builds **an ordinary class loaded from bytecode in memory**, not a hidden class, not a JPMS named module, and not JAR resource loading with URLClassLoader.

## 12. Common Errors and How to Handle Them

| Symptom | Possible Cause | How to Investigate |
|---|---|---|
| `getSystemJavaCompiler() == null` | Runtime is missing the compiler | Use a JDK with a compiler or precompile during the build |
| `compilation failed` | Source syntax/dependency/options | Print `DiagnosticCollector`, check `--release`/classpath |
| `ClassNotFoundException` for the entry-point class | Wrong map key/binary name; parent cannot find it | Print the compiled key set, check the package |
| `NoClassDefFoundError` when invoking a method | Missing generated nested/helper class or runtime dependency | Store all outputs, compare the loader graph |
| `NoClassDefFoundError: wrong name` | Key/name does not match the classfile contents | Build keys from the compiler output |
| `UnsupportedClassVersionError` | Bytecode target is higher than the JVM | Use a `--release` matching the runtime |
| `ClassFormatError`/`VerifyError` | Corrupted/invalidly generated bytes | Inspect the generator/JavaFileObject and origin |
| `LinkageError` on repeated definition | Defining the same name twice in one loader | Use the default `loadClass`, create a new loader per generation |
| `ClassCastException` between two classes with the same name | Different defining loaders | Use parent-shared API types |
| `getResource("Hello.class") == null` | A byte map is not automatically a resource store | Add `findResource` or a separate bytes API |
| Parent returns a different class than the memory map | Parent-first loader has the same binary name | Isolate the app classpath; enforce a namespace policy |
| Static initializer does not run right after `loadClass` | Loading/linking differs from initialization | Trigger active use or use `Class.forName(...,true,...)` |
| Memory grows after many compilations | Old maps/caches/handles/loaders remain reachable | Limit generations, clear references, profile |
| Multiple threads using the same map cause errors | Mutable bytes or publishing before compilation finishes | Immutable snapshot, defensive copy |
| Code compiles successfully but fails at runtime | Compiler classpath differs from memory loader graph | Check both compile-time and runtime dependencies |
| Plugin can read host files/secrets | A separate loader is not a security sandbox | Process isolation/OS permissions |
| New code is not used after updating the map | Class already defined once in the loader | Create a new MemoryLoader generation |

### Checklist Before Production Use

1. Is the source/bytecode origin trusted and validated against policy?
2. Are packages/binary names clearly specified for generated classes?
3. Has the byte map been **deep-copied** and frozen before publishing to the loader?
4. Are all compiler outputs stored, including nested/helper classes?
5. Are the compiler runtime and target JVM version compatible?
6. Does the compiler classpath match the dependencies provided by MemoryLoader/parent at runtime?
7. Do APIs across the boundary have a single defining loader?
8. Are metrics, diagnostics, and memory/classloader generation lifecycle management in place?
9. Are there limits on source/output byte size and compilation time?
10. If the source is untrusted, is there a **process-level sandbox** and appropriate OS permissions?

**Conclusion:** MemoryClassLoader is a very practical way to use ClassLoader: the JVM does not care whether bytes come from a JAR file or RAM as long as the classfile is valid and the loader defines it properly. By combining `JavaCompiler` with `JavaFileManager`, you can compile, capture all classfile outputs, and load them directly in memory. What is harder than the code itself is **maintaining runtime type identity, parent delegation, dependency visibility, resource policy, memory lifecycle, and permission boundaries** as the system scales.
