# Risks of Loading Classes from Network Sources or Mutable Directories

## 1. The Problem: Finding a Class Does Not Mean Trusting It

`ClassLoader` allows a Java application to locate and define classes from a classpath, JAR, plugin directory, module, in-memory generated data, or network-downloaded source. That extensibility carries a security boundary: **who has the authority to decide which bytes the JVM will define and execute?**

Suppose the host needs `plugin.SafeTask`. If the file `plugins/current/plugin/SafeTask.class` resides in a directory that can be modified by another user, a compromised process, an unprotected deployment job, or an unauthenticated download step, the class content may differ from the approved version.

The risk is not limited to loading the wrong version or encountering a `ClassNotFoundException`. A class with a valid name and structure can still perform unintended behavior in a static initializer, constructor, or method. The Java bytecode verifier checks bytecode format/type constraints, and **does not prove the author's origin or intent**.

**Principle:** do not treat a class name, classpath, HTTPS URL, self-computed hash from the same directory, or a successful `loadClass` call as proof of safety. Establish an **independent trust anchor**, verify the artifact, keep the verified snapshot, and load only from that data.

## 2. Threat Model: Dangerous Sources of Modification

| Class Source | Risk | Mitigations to Consider |
|---|---|---|
| Network-downloaded JAR | Compromised endpoint/CDN, dependency confusion, substituted artifact | TLS validation, signer/digest from an independent approval source |
| Shared plugin directory | Another user/process overwrites `.class` or JAR | ACL/ownership, immutable staging, integrity verification |
| Network filesystem | Content changes between check and file open, inconsistent cache | Protected snapshot, verification of the bytes actually used |
| Artifact repository/cache | Poisoned cache, mutable `latest` tag, wrong version | Digest pinning, immutable release coordinates |
| Parent classpath | Parent-first unintentionally selects a class with a colliding binary name | Check parent policy/defining loader, keep private classes outside the parent |
| Plugin metadata | `META-INF/services/...` altered to load a different provider | Verify both service metadata and provider artifacts |
| Resources/scripts | Altered config, XML, template, script, or native library | Whole-artifact verification and resource policy |
| Generated bytecode | Untrusted generator/input produces wrong behavior | Input source control, build provenance, output approval |

Two independent questions: **is the artifact truly the approved version?** and **is the approved version permitted to execute at the current privilege level?** Integrity does not prove that the logic is completely safe.

### Classpath Injection and Shadowing

A common mistake is having a child loader whose `findClass` reads the verified plugin file, while the default `loadClass` performs **parent-first** delegation:

```text
child.loadClass("plugin.SafeTask")
    -> findLoadedClass(name)
    -> parent.loadClass(name)  // if parent has the same name
    -> calls child.findClass only when parent cannot find it
```

If the parent has already defined a different `plugin.SafeTask`, the hash check inside the child's `findClass` may **not be executed**. Therefore, an integrity check placed only in `findClass` is insufficient to protect a namespace that the parent can provide.

How to handle this: place private plugin implementations **outside** the parent classpath, or override `loadClass` **selectively** for the private namespace and verify the hash before `defineClass`. Do not switch to child-first for all packages: `java.*` and shared `api.*` must preserve proper type sharing/identity mechanisms.

## 3. ClassLoader, Verifier, and Execution Privileges: Three Separate Layers

Per Java 17:

1. `ClassLoader.loadClass`/`findClass` locates the class or bytes. `defineClass` defines a runtime class from bytecode.
2. The JVM checks the class-file format, verification, linking, and type-system constraints. An invalid class file can cause `ClassFormatError`, `VerifyError`, or `LinkageError`.
3. Accepted Java code can execute side effects within the permissions of the **process** and runtime policy. Valid bytecode does not guarantee benign intent.

`Class.forName(name, true, loader)` also requests class initialization, which can run `<clinit>`. Performing an integrity check only **after** calling `Class.forName(..., true, ...)` is too late: the code has already had a chance to execute.

`ClassLoader.getName()` is a debug label; `clazz.getClassLoader()` indicates the defining loader for a regular class; `clazz.getProtectionDomain()` provides metadata related to the security-domain model. None of them **by themselves** guarantee that the artifact is approved.

**Java 17 SecurityManager has been deprecated for removal** per JEP 411. Do not design a new sandbox for untrusted Java bytecode using only a custom ClassLoader or SecurityManager. Running untrusted code generally requires process/container isolation and minimal OS privileges.

## 4. TOCTOU: Checking at T1, Reading Bytes at T2

TOCTOU (*time of check to time of use*) occurs when a program checks an object and then reopens a source that can be modified.

```text
T1: hash plugins/current/plugin.jar -> correct SHA-256
T2: untrusted actor replaces plugin.jar
T3: create URLClassLoader from the same path
T4: URLClassLoader opens the file and gets the replaced class bytes
T5: JVM defines/initializes the new class
```

It is not enough to check `Files.exists`, `size`, `lastModifiedTime`, `Path.normalize()`, or `toRealPath()` and assume the file will remain unchanged. Symlinks and file contents can change between **check** and **open**, especially in a directory where an attacker has write permission or on a shared filesystem.

A more reliable pattern:

```java
byte[] bytes = Files.readAllBytes(classFile);
byte[] digest = MessageDigest.getInstance("SHA-256").digest(bytes);
if (!MessageDigest.isEqual(digest, approvedDigest)) {
    throw new SecurityException("Integrity failure");
}
Class<?> type = defineClass(binaryName, bytes, 0, bytes.length);
```

This is an **illustrative snippet inside a `ClassLoader` subclass**, requiring imports, variables, and checked exception handling. The key point: **the exact same byte array is hashed and passed to `defineClass`**. If the file changes after being read, the data captured in the byte array does not change with it. If it changes during the read, the resulting bytes still have to pass the digest check.

For a plugin consisting of multiple classes and resources, hashing a single class is **not enough**. You should create an immutable snapshot of the entire artifact, verify its manifest/signature/digest first, and then allow the loader to read only from that snapshot.

## 5. SHA-256 Pinning and the Crucial Question: Which Digest Do You Trust?

Comparing `SHA256(bytes)` against an expected value only has security meaning if **the expected value comes from an independent trust root**. For example, use an approved/signed release manifest and verify the proper signer; or pin it in deployment configuration that only a trusted party has permission to update. Do not take a checksum placed next to the JAR/class file in the same mutable directory as a trusted source: an attacker can modify both the file and the checksum.

The specific issue with a **mutable class source** in this lesson is that the hash result must be bound to **the exact byte array about to be passed into `defineClass`**. If you hash the file at T1 but `URLClassLoader` reads the same pathname again at T2, TOCTOU still exists. The example in Section 6 demonstrates how to verify `readAllBytes → digest → defineClass` for a single class.

Digest pinning does not yet guarantee that the code is harmless, that the dependency graph is clean, or that runtime privileges are appropriate. Full-JAR verification, signers, provenance, transitive dependencies, and revocation policies are practiced in the lesson **Controlling JAR Sources, Integrity, and Allowed Dependencies**.

## 6. Complete Java 17 Example: Checking the Hash Before defineClass

The example has **one** class `plugin.SafeTask` in a separate directory and a host that does not include the plugin directory on the application classpath. The host receives the approved SHA-256 from the build/release environment, reads the bytes once, verifies them, and only then calls `defineClass`.

**Limitations of the example:** it illustrates the integrity of **a single class**; it does not automatically verify transitive dependencies, resources, network transport, or JAR signatures; it is not a security sandbox.

### 6.1. Structure

```text
src/
  plugin/
    plugin/
      SafeTask.java
  host/
    PinnedLoaderDemo.java
out/
  plugin/
  host/
```

File `src/plugin/plugin/SafeTask.java`:

```java
package plugin;

public final class SafeTask {
    public static String run() {
        return "safe-v1";
    }
}
```

File `src/host/PinnedLoaderDemo.java`:

```java
import java.io.IOException;
import java.lang.reflect.Method;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;

public final class PinnedLoaderDemo {
    private static final String TARGET = "plugin.SafeTask";

    static final class PinnedLoader extends ClassLoader {
        private final Path classFile;
        private final byte[] expectedHash;

        PinnedLoader(Path classFile, byte[] expectedHash, ClassLoader parent) {
            super("pinned-plugin", parent);
            this.classFile = classFile;
            this.expectedHash = expectedHash.clone();
        }

        @Override
        protected Class<?> loadClass(String name, boolean resolve)
                throws ClassNotFoundException {
            if (!TARGET.equals(name)) {
                return super.loadClass(name, resolve);
            }

            synchronized (getClassLoadingLock(name)) {
                Class<?> found = findLoadedClass(name);
                if (found == null) {
                    found = findClass(name);
                }
                if (resolve) {
                    resolveClass(found);
                }
                return found;
            }
        }

        @Override
        protected Class<?> findClass(String name)
                throws ClassNotFoundException {
            if (!TARGET.equals(name)) {
                throw new ClassNotFoundException(name);
            }

            byte[] bytes;
            try {
                bytes = Files.readAllBytes(classFile);
            } catch (IOException ex) {
                throw new ClassNotFoundException(name, ex);
            }

            byte[] actual;
            try {
                actual = MessageDigest.getInstance("SHA-256").digest(bytes);
            } catch (NoSuchAlgorithmException impossible) {
                throw new AssertionError(impossible);
            }

            if (!MessageDigest.isEqual(actual, expectedHash)) {
                throw new SecurityException(
                        "SHA-256 mismatch for " + name);
            }

            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Usage: PinnedLoaderDemo <plugin-root> <trusted-sha256-hex>");
        }

        byte[] trustedDigest = HexFormat.of().parseHex(args[1]);
        if (trustedDigest.length != 32) {
            throw new IllegalArgumentException(
                    "Expected 32 SHA-256 bytes");
        }

        Path classFile = Path.of(args[0], "plugin", "SafeTask.class");
        PinnedLoader loader = new PinnedLoader(
                classFile,
                trustedDigest,
                PinnedLoaderDemo.class.getClassLoader());

        Class<?> type = Class.forName(TARGET, true, loader);
        Method run = type.getMethod("run");

        System.out.println("SHA-256 accepted: true");
        System.out.println("Defined by pinned loader: "
                + (type.getClassLoader() == loader));
        System.out.println("Task result: " + run.invoke(null));
    }
}
```

### 6.2. Why Override loadClass for Exactly One Name?

- For `plugin.SafeTask`, the code calls `findLoadedClass`; if not yet loaded, it must go through `findClass`, which is protected by SHA-256. The parent cannot return a different `plugin.SafeTask` and bypass the check.
- For all other class names, the code keeps `super.loadClass` so as not to arbitrarily apply child-first loading to shared APIs and JVM classes.
- `synchronized (getClassLoadingLock(name))` protects the check → define sequence for the same name against multi-threaded races.
- `MessageDigest.isEqual` compares the digest bytes; on a mismatch, `SecurityException` is thrown **before** `defineClass`.
- `Class.forName(..., true, loader)` performs initialization only after the loader has returned a valid class.

For multi-class plugins, the policy must be extended to verify **all private classes and dependencies**. Do not use a loader that checks only `SafeTask` and assume the rest is already trusted.

### 6.3. Compiling

Bash on Linux/macOS:

```bash
mkdir -p out/plugin out/host
javac -d out/plugin src/plugin/plugin/SafeTask.java
javac -d out/host src/host/PinnedLoaderDemo.java
```

PowerShell on Windows:

```powershell
New-Item -ItemType Directory -Force out/plugin,out/host
javac -d out/plugin src/plugin/plugin/SafeTask.java
javac -d out/host src/host/PinnedLoaderDemo.java
```

### 6.4. Pinning the Digest from a Trusted Release Environment

At build/release time, once the source and builder have been approved, compute the digest:

```bash
sha256sum out/plugin/plugin/SafeTask.class
```

Or PowerShell:

```powershell
(Get-FileHash out/plugin/plugin/SafeTask.class -Algorithm SHA256).Hash
```

Store the **64 hex characters** in a signed manifest or a separately protected configuration. **Do not** re-hash the file in the mutable directory on every load and treat the new hash as a trusted expected value.

### 6.5. Running

Replace `TRUSTED_SHA256_HEX` with the exact approved digest:

```bash
java -cp out/host PinnedLoaderDemo out/plugin TRUSTED_SHA256_HEX
```

With the original bytes and the correct digest, stdout:

```text
SHA-256 accepted: true
Defined by pinned loader: true
Task result: safe-v1
```

The command runs with **`-cp out/host`**, without `out/plugin`. This keeps the plugin off the application classpath and clearly illustrates where the class is defined.

### 6.6. Testing File Replacement While Keeping the Old Digest

Change the literal `"safe-v1"` in `SafeTask.java` to `"safe-v2"`, recompile the plugin class, and still run with the digest of the previously approved version:

```bash
javac -d out/plugin src/plugin/plugin/SafeTask.java
java -cp out/host PinnedLoaderDemo out/plugin TRUSTED_SHA256_HEX
```

The program rejects it before `defineClass`. Key error line:

```text
java.lang.SecurityException: SHA-256 mismatch for plugin.SafeTask
```

That is the **identifying error line**, not the entire fixed stderr; the stack trace contains build-dependent method/file/line numbers. Do not change the expected digest to the new one just to "fix the error" unless the new version has genuinely been approved.

**Actual verification:** this demo code was compiled/run in an isolated test environment using JDK 21 with Java 17-compatible APIs. The matching-digest case prints the exact three success lines; the case with modified/recompiled source while keeping the old digest throws `SecurityException` before executing the method.

### 6.7. What the Demo Does Not Protect Against

- Whoever controls the **CLI digest** also decides which bytes are accepted; in practice, a trusted channel for the digest is required.
- The checksum applies only to the target class, not to every dependency/JAR/resource.
- If the file changes during `readAllBytes`, the captured content still must match the hash; avoid reading from a filesystem that allows untrusted parties to interfere continuously, and enforce strict permissions on staging.
- If the class has already been defined in the loader, subsequent `loadClass` calls return the existing class; replacing the file afterward does not cause the loader to redefine it automatically. For a new release, use a new loader/snapshot.
- Integrity is not static code analysis or a behavioral sandbox.
- `SecurityException` is a security failure; do **not** catch it and fall back to unverified bytes.

## 7. Signed JARs, jarsigner, and CodeSource

A JAR containing `META-INF/*.SF` or passing `jarsigner -verify` does not by itself prove **that the signer is authorized to release it**: you must also verify the chain/key pin, trust policy, signed entries, and artifact version. When a custom loader reads a class file from a mutable directory and calls `defineClass` directly, there is no automatic signer verification step for that file.

`CodeSource`/`ProtectionDomain` is useful metadata for diagnosing the source/loader, but **not** proof that the URL was verified or that the bytecode is trustworthy. In JDK 24+, SecurityManager is permanently disabled, so this metadata cannot be used as a file/network permission sandbox.

For real-world JARs, verify the signer/trust **before letting the loader load from an immutable snapshot**, along with checking all dependencies and resources. The lesson on **controlling JAR sources** explains the detailed JAR vetting, SHA-256, signature, and allowlist process.

## 8. Loading Over the Network: Protecting Transport and Provenance

A download pipeline should:

1. Select the artifact ID/version from an allowed catalog; do not execute plugins from an arbitrary request URL.
2. Use HTTPS/TLS properly: validate hostnames/certificates, and do not disable TLS verification to handle errors.
3. Restrict hosts, redirects, DNS/egress, size, and timeouts. An attacker-chosen URL can also introduce SSRF risk in some architectures.
4. Download data to a staging location where untrusted actors cannot write.
5. Verify the release manifest/signature or pinned digest from an independent source.
6. Check the dependency closure and resource/service metadata under the same release policy.
7. Transition the artifact into a protected snapshot before creating the class loader.
8. Record audit entries for artifact/version/digest/signing identity/loader where appropriate, without logging secrets.
9. Have a rollback and revocation procedure in case a compromised artifact or signing key is discovered.

**TLS does not replace artifact authorization.** A repository operating over HTTPS can still distribute the wrong version or an artifact not approved by the organization.

Content-digest paths such as `store/sha256/<digest>/plugin.jar` are useful for immutable storage, but the directory name **does not by itself prove** the content is valid. You still must verify the bytes against a trust root.

## 9. Loading from a Mutable Directory: Staging and Snapshots

A clear layout:

```text
incoming/            <- newly received artifact, untrusted
quarantine/          <- check format/size/manifest
verified/            <- verified snapshot, restricted write ACL
active/              <- points to the currently active version
```

This is an illustrative architecture, not directories that must be created immediately in the workspace.

Key points:

- **Do not use the active directory as a target for incremental copying** of the new version's `.class` files while a loader is reading.
- Build a complete new version directory, verify **all** files/the whole artifact, and only then activate it.
- If using `Files.move(..., ATOMIC_MOVE)`, check filesystem support and handle `AtomicMoveNotSupportedException`; atomic rename is not universal across volumes/network shares.
- Keep old versions immutable for running loaders; do not modify JARs underneath them.
- For hot reload, use a new loader for the new version; stop tasks, unregister listeners, and close the old loader's resources properly according to its lifecycle.

### Path Traversal and Symlinks

`Path.normalize()` resolves `.`/`..` in the path string; it **does not prove** that the final path lies within the trusted root if symlinks/junctions are present. `toRealPath()` resolves the path at a single point in time, yet an attacker can still replace a symlink right after the check if they have permission.

Do not concatenate any arbitrary user-supplied class/resource name directly into a filesystem path. You must validate namespaces, root containment, archive entry names, symlink handling, filesystem permissions, and time of use. Under a strict threat model, use protected snapshots/file handles instead of checking and then reopening a mutable path.

When extracting JAR/ZIP archives, validate entry paths before writing to prevent **Zip Slip** and prevent files from landing outside the staging root; limit extracted size and entry count to mitigate DoS.

## 10. Resources, Dependencies, and SPI Must Also Be Trusted

A plugin consists of more than just `Entry.class`:

- Private classes and transitive dependencies.
- `META-INF/services/...` specifying service providers.
- Resource/config files, XML, templates, embedded scripts.
- JNI/native libraries.
- Module descriptors, manifest/classpath metadata.

Example:

```java
ClassLoader pluginLoader = pluginInstance.getClass().getClassLoader();
java.net.URL config = pluginLoader.getResource("plugin/config.properties");
```

This snippet requires an actual `pluginInstance`. If the config is read from a mutable filesystem or an unexpected parent resource, the plugin can change behavior even if the class has been pinned. Therefore, you must also snapshot resources and enforce lookup policy.

With `ServiceLoader.load(Service.class)`, provider discovery normally uses the thread's TCCL; a container worker whose TCCL differs from the target plugin may discover the wrong provider. When the provider loader is known, use the `ServiceLoader.load(Service.class, pluginLoader)` overload and verify the provider artifact/descriptor, while ensuring the service interface type is defined consistently by the parent/shared loader.

**Parent-first and resource lookup also have visibility rules**: do not assume that simply choosing the plugin loader guarantees the class/resource comes from the plugin URL rather than the parent.

## 11. Safety Boundaries: A ClassLoader Is Not a Sandbox

A custom loader can help:

- Isolate the runtime class identities of plugin A and plugin B.
- Load from verified artifacts.
- Select a specific source/namespace.
- Provide a consistent lookup policy for the application.

However, it **does not by itself** restrict CPU/memory, network/file permissions, subprocesses, native code, process-wide system properties, or threads. If a plugin is truly untrusted, consider running it in a **separate process/JVM**, with minimal user/permissions, an appropriate OS sandbox/container, resource quotas, and an input-validated communication protocol.

Especially on Java 17, avoid designing a new "plugin sandbox" based solely on SecurityManager, since JEP 411 has deprecated that feature for removal. Signatures/hashes answer "are the bytes the approved version?", **not** "are they allowed to run inside the same trust boundary as the host?".

## 12. Common Mistakes

| Mistake | Why It Is Dangerous | How to Fix |
|---|---|---|
| Hashing a file and then reopening the mutable path | TOCTOU | Verify the exact bytes used for definition or use an immutable snapshot |
| Computing the expected hash at runtime from the same file | Attacker modifies both content and digest | Independent trusted manifest/pin |
| Pinning only one entry class | Helpers/resources/providers can still be replaced | Whole-artifact + dependency verification |
| Checking only the class name | The same name can carry different bytes | Digest/signature + defining loader audit |
| Checking only in `findClass` | Parent-first can bypass the check | Namespace/loader policy and parent preflight |
| Using child-first for every package | Creates duplicate copies of shared APIs | Selective policy, preserving shared API identity |
| Trusting the bytecode verifier like an antivirus | Valid code can still be malicious | Trust/approval + least privilege |
| Seeing a `META-INF` signature file and trusting the JAR | Signature/signer may not be verified | jarsigner/trusted verification path |
| Using TLS and skipping version approval | TLS does not select an authorized artifact | Pin artifact ID/version/digest |
| Copying multiple `.class` files into the active directory | Loader may get half v1 and half v2 | Stage a complete snapshot and use atomic activation |
| Catching `SecurityException` and falling back | Bypasses fail-closed control | Reject and investigate |
| Granting arbitrary system privileges to plugins | ClassLoader does not isolate permissions | Separate process/OS least privilege |
| Calling `System.gc()` to "remove loaded code" | Class unloading is not immediate and is not security revocation | Stop process/teardown plugin by design |

## 13. Diagnostics and Security Testing

**Do not test only the happy path where a valid plugin loads successfully.** You should test failure scenarios:

| Test | Expectation |
|---|---|
| Valid class bytes, digest from trusted release | Load/initialize/invoke succeeds |
| One byte changed in class, keeping trusted digest | Rejected before `defineClass` |
| Attacker modifies both file and checksum in the same directory | Rejects checksum from untrusted source |
| Parent has a class with a colliding name | Does not bypass pin policy for the protected target |
| Private dependency modified | Whole-artifact verification rejects it |
| SPI descriptor or resource altered | Manifest/verification policy detects it |
| Symlink escaping trusted root | Prevents crossing the source boundary |
| Source modified during copy | Only activates a snapshot matching the digest |
| Concurrent requests for the same binary name | No duplicate class definition, proper locking |
| A loader has loaded a class, then the file changes | Loaded class does not automatically hot-reload |
| Release v2 approved | Creates a new snapshot/loader and manages old lifecycle |

In logs, you can print:

```java
System.out.println(type.getName());
System.out.println(type.getClassLoader());
System.out.println(type.getModule());
```

This snippet requires the `type` variable. Such metadata is helpful when investigating shadowing, but **does not replace integrity validation**.

Distinct JVM errors:

- `ClassNotFoundException`: lookup did not find the name.
- `ClassFormatError` or `VerifyError`: invalid class data or verification failure.
- `LinkageError`: for example, inconsistent identity/constraints/APIs.
- `NoClassDefFoundError`: dependency/runtime resolution failure or a prior initialization failure.
- `SecurityException` in the demo: **explicit digest verification failure**.

Do not mask all root causes behind a generic "plugin load fail" message and automatically fall back to another artifact.

## 14. Self-Check Exercises

**Question 1.** The JAR's SHA-256 matches a checksum file placed next to the JAR in a directory where an attacker has write permission. Does that guarantee safety?

**Answer:** No. An attacker can modify both the JAR and the checksum. You need an expected digest/signature from an independent trust root.

**Question 2.** The bytecode verifier accepts a class; does that mean the class will not do anything dangerous?

**Answer:** No. The verifier enforces class/bytecode rules, not trustworthy behavior.

**Question 3.** Why is checking the SHA at T1 and then letting `URLClassLoader` read the file again at T2 still risky?

**Answer:** TOCTOU: the file can be replaced between the two points in time. Use a verified immutable snapshot or verify the exact byte[] that will be passed to `defineClass`.

**Question 4.** If an attacker replaces the class file after `readAllBytes` returns, but before `defineClass` uses the exact array that was hashed, can they modify the in-memory array's contents from disk?

**Answer:** No. The in-memory array is the snapshot that was hashed. However, other files/resources could be read later; a whole-artifact policy is needed.

**Question 5.** Why might overriding only `findClass` to check the hash be insufficient?

**Answer:** Parent-first `loadClass` can return a class from the parent first without calling `findClass`. You must coordinate namespace/lookup handling so protected classes cannot be bypassed.

**Question 6.** The plugin class is securely pinned, yet `META-INF/services` points to a malicious provider. What went wrong?

**Answer:** Service metadata/provider artifacts were left outside the integrity scope. You must verify the entire artifact and provider discovery.

**Question 7.** Does a valid JAR signature mean the plugin has no vulnerabilities?

**Answer:** No. A signature proves that the artifact was signed under a key and its contents have not changed relative to the signature, not that its behavior is bug-free. You must also check the trusted signer/approval and code security.

**Question 8.** Does a dedicated `ClassLoader` prevent a plugin from reading system files or opening network connections?

**Answer:** Not by class-name isolation alone. Appropriate OS/process permissions and sandboxing are what control behavior when a plugin is untrusted.

**Question 9.** During deployment, why should you not sequentially copy new classes over an active directory currently in use?

**Answer:** Loads can observe a mix of versions, leading to wrong behavior or `NoSuchMethodError`/`LinkageError`. Use a complete versioned snapshot and controlled activation.

**Question 10.** In the example, why is a mismatch detected **before** `SafeTask.run()` executes?

**Answer:** The loader hashes and compares the byte array before `defineClass`. On mismatch, it throws `SecurityException` immediately in `findClass`; `Class.forName` never receives a class to initialize.

## 15. Implementation Checklist

- [ ] Defined the threat model and who is authorized to publish/modify artifacts.
- [ ] Selected artifacts via an explicit ID/version/allowlist.
- [ ] Network transport uses proper TLS validation and restricts origins/redirects/size.
- [ ] Hashes/signatures are verified against a trust root independent of the mutable source.
- [ ] All relevant classes, resources, provider metadata, and dependencies are within verification scope.
- [ ] Verified immutable snapshot/staging is in place with appropriate permissions/ownership.
- [ ] No TOCTOU gap exists between verification and the bytes actually defined.
- [ ] Parent delegation does not bypass integrity checks for protected namespaces.
- [ ] Shared API types are not duplicated when applying selective child-first loading.
- [ ] Fail-closed error handling and logging/auditing are implemented without exposing secrets.
- [ ] Atomic/transactional activation and rollback logic are in place.
- [ ] Loader/resource/task cleanup is performed when updating plugins.
- [ ] For untrusted plugins, process isolation and least privilege are used instead of treating the classloader as a sandbox.
- [ ] Tests cover tampering, partial updates, symlink/path attacks, service injection, and lifecycle.

## 16. Summary and Authoritative References

**Six key points to remember:**

1. **Syntactically valid bytecode does not mean trustworthy.** Class loading only establishes a definition; it does not approve the author or behavior.
2. **Mutable sources lead to TOCTOU.** Never verify a file and then let a loader reopen a modifiable path without a new snapshot/integrity check.
3. **Hashes must be bound to a trusted expected digest.** Recomputing a digest over an untrusted source provides no trust.
4. **Verify the entire artifact and dependencies**, not just the entry class; SPI/resources can alter behavior.
5. **Control parent delegation** to prevent bypasses, but do not break shared API identities with indiscriminate child-first loading.
6. **A ClassLoader is not a sandbox.** For untrusted code, permissions must be restricted at the process/OS level.

**Official Java 17 references:**

- [ClassLoader API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/ClassLoader.html): `loadClass`, `findClass`, `defineClass`, `getClassLoadingLock`.
