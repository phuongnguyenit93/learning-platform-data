# URLClassLoader Nested JAR Lookup Limitations and Differences from Specialized Launchers

## 1. The Problem: A JAR "Contains Libraries" but Cannot Load Classes

A Java Archive (JAR) file is essentially a ZIP archive in the JAR format. A JAR can contain files, directories, classes, and **another JAR file as a data entry**. For example:

~~~text
outer.jar
├── META-INF/
│   └── MANIFEST.MF
├── app/Main.class
└── lib/
    └── helper.jar
        └── (inside helper.jar)
            demo/lib/Helper.class
~~~

Looking at this structure, one might assume that:

~~~java
new URLClassLoader(new URL[] { outerJarUrl })
        .loadClass("demo.lib.Helper");
~~~

will automatically open `outer.jar`, discover `lib/helper.jar`, and traverse into the nested archive. **This is a false assumption for the standard JDK `URLClassLoader`.** It searches for classes from **the URLs in its search path and standard JAR lookup rules**, and does not automatically traverse every `*.jar` entry inside an open JAR as new classpath roots.

**Key takeaways:**

- The `outer.jar` file can exist and contain `helper.jar`.
- A standard `URLClassLoader` **can see the `lib/helper.jar` entry as a resource** in the outer JAR.
- However, `demo.lib.Helper` resides *inside the byte stream of the `helper.jar` entry*, not at the `demo/lib/Helper.class` path of the **outer JAR**.
- To load classes directly from a nested archive **without extracting it**, you need a mechanism that understands nested archives, such as a framework's **specialized launcher/ClassLoader**. Another solution is to **extract the nested JAR into a real JAR file and place that file on the runtime classpath/URLClassLoader**.
- Not every file called an "executable/fat JAR" uses the same mechanism. A **shaded/uber JAR** can put classes directly into the same archive, whereas a **nested JAR** keeps libraries as separate JARs inside it.

This lesson explains the limitations of **`java.net.URLClassLoader`**, distinguishes it from Spring Boot executable JARs, and provides a standalone Java 17+ experiment with verified stdout.

## 2. First, Distinguish Three Packaging Formats

### 2.1. Plain JAR + External Dependencies

~~~text
dist/
├── app.jar
└── lib/
    ├── a.jar
    └── b.jar
~~~

`app.jar` is the application JAR, and `a.jar` and `b.jar` are **actual files** on the filesystem. The launcher can:

- Use `java -cp "app.jar:lib/a.jar:lib/b.jar" app.Main` on Linux/macOS.
- Use `java -cp "app.jar;lib/a.jar;lib/b.jar" app.Main` on Windows.
- Use an appropriate manifest `Class-Path` or a launcher script generated by a build tool, depending on deployment.

Each listed JAR is an independent **classpath entry**; a standard `URLClassLoader` can use URLs pointing to such JAR files.

### 2.2. Shaded/Uber JAR: Merging Classes into One Archive

~~~text
app-all.jar
├── META-INF/MANIFEST.MF
├── app/Main.class
├── demo/lib/Helper.class
└── another/lib/Codec.class
~~~

There is no `helper.jar` that needs to be opened recursively to find `Helper.class`: the dependency's classes have been placed **directly** into the outer JAR under their package paths. When there are no special conflicts or relocations, a standard class loader can find `demo/lib/Helper.class` just like an entry in a regular JAR.

Tools such as the Maven Shade Plugin, Gradle Shadow, and similar build tasks can produce archives in this format depending on configuration. Do not confuse the term "fat JAR" with "nested JAR": the actual packaging layout determines the loading mechanism.

**Specific risks of shaded JARs:** duplicate class/resource paths, JAR signatures, `META-INF/services`, package relocation, licenses/metadata, and multi-release entries may require careful handling during merging.

### 2.3. Nested JAR: Keeping Inner JARs Intact Inside the Outer JAR

~~~text
app-nested.jar
├── META-INF/MANIFEST.MF
├── app/Main.class
└── lib/helper.jar       <-- nested JAR file is an entry in the outer archive
    └── demo/lib/Helper.class  (located inside the nested archive)
~~~

`jar --list --file app-nested.jar` lists `lib/helper.jar`, but **does not automatically list** `demo/lib/Helper.class` as a direct entry of the outer archive.

If you add `app-nested.jar` to a `URLClassLoader`, the loader can find `app/Main.class` (if the class sits directly at the root), but **it does not automatically turn `lib/helper.jar` into a new classpath entry**. This is the exact limitation analyzed in this lesson.

## 3. Where Does `URLClassLoader` Actually Search?

According to the [Java SE 17 `URLClassLoader` API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/net/URLClassLoader.html), this loader uses URLs referring to **JAR files and directories**:

- A `file:` URL ending with `/` represents a directory classpath root.
- A `file:` URL pointing to a JAR file represents a JAR that can be opened to search for classes/resources.
- URLs of the form `jar:...!/` are handled according to JAR URL/`JarURLConnection` rules.
- URLs are searched following the delegation model and search path order; the `parent` may return a class before the child loader's `findClass`.
- `getURLs()` returns the URLs in the `URLClassLoader`'s own search path; this list **does not automatically expose any JARs embedded as entries inside an outer archive**.

### 3.1. How a Class Name Maps to a Resource Name

A binary name:

~~~text
demo.lib.Helper
~~~

typically corresponds to the class resource:

~~~text
demo/lib/Helper.class
~~~

To load from a standard JAR URL, this entry must be found according to JAR classpath root logic. However, when the outer archive contains:

~~~text
BOOT-INF/lib/helper.jar
~~~

the loader only sees **an entry containing the bytes of an inner JAR**; the path `demo/lib/Helper.class` is not a direct entry in the outer archive.

Therefore, two questions must be separated:

| Question | Answer when only `outer.jar` is added to URLClassLoader |
|---|---|
| Can it find the resource `BOOT-INF/lib/helper.jar`? | **Yes**, because it is a real entry of the outer JAR |
| Can it automatically load `demo.lib.Helper` from inside that resource? | **No, under standard JDK URLClassLoader nested JAR lookup behavior** |
| Can it load `app.Main` if `app/Main.class` is directly inside the outer JAR? | Yes, given the right loader/classpath path and no other constraints |
| Can it load `demo.lib.Helper` from a **standalone `helper.jar` file** added to URLClassLoader? | Yes, given a valid JAR and no other class/dependency issues |

Finding the `helper.jar` resource does not mean the JVM knows how to look up individual `.class` files inside that resource.

### 3.2. Do Not Confuse an Entry URL with a Classpath Root URL

A standard Java `jar:` URL roughly has the syntax:

~~~text
jar:<JAR-url>!/<entry>
~~~

For example, a class resource in a **non-nested** JAR:

~~~text
jar:file:/some/dir/helper.jar!/demo/lib/Helper.class
~~~

However, a concatenated string like:

~~~text
jar:file:/some/dir/outer.jar!/BOOT-INF/lib/helper.jar!/demo/lib/Helper.class
~~~

**does not automatically become a standard way for `JarURLConnection` to open a "JAR inside a JAR"**. The standard JDK/JAR URL protocol does not guarantee handling multiple `!/` levels as an independent classpath root. You should not manually construct such URLs and assume `URLClassLoader` will understand nested archives.

A framework may install a **specialized protocol handler/JAR abstraction**, producing URLs that look similar, but their semantics are provided by the framework. In that case, the behavior is no longer plain JDK default behavior.

### 3.3. A Resource Is Data, Not an Automatically Mounted JAR

A program can still read the bytes of a nested entry:

~~~java
try (java.util.jar.JarFile outer =
        new java.util.jar.JarFile("build/outer.jar")) {
    java.util.jar.JarEntry nested =
            outer.getJarEntry("BOOT-INF/lib/helper.jar");
    try (java.io.InputStream in = outer.getInputStream(nested)) {
        // You can read the bytes of helper.jar as regular data.
    }
}
~~~

The code above is an **illustrative snippet** and cannot compile standalone without being placed in an appropriate method with imports and exception handling. It demonstrates that **reading an entry of the outer JAR** is completely possible, but there is no step where the JVM automatically parses the inner class/JAR format. To use classes from those bytes, you need an appropriate strategy: extract the archive and pass its path to a loader, build a custom loader, or use a specialized launcher.

## 4. Why Doesn't `java -jar outer.jar` Automatically Resolve Nested JARs?

The command:

~~~sh
java -jar outer.jar
~~~

instructs the Java launcher to run the main class declared by the **`Main-Class` manifest attribute** in the outer JAR. According to the [Java launcher documentation](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html), when `-jar` is used, user-specified classpath options are not combined the way they are with `java -cp ... Main`.

Critically: `java -jar` **does not mean** "Java automatically finds every inner JAR inside the outer JAR."

For example, suppose a JAR has:

~~~text
META-INF/MANIFEST.MF:
  Main-Class: app.Main

outer.jar:
  app/Main.class
  BOOT-INF/lib/helper.jar
~~~

The `app.Main` application can start if its class is in a location the standard launcher can find. However, classes inside `BOOT-INF/lib/helper.jar` are still **not automatically present** on the classpath just because the `helper.jar` entry exists.

In particular, the standard manifest `Class-Path` attribute **is not syntax for loading inner JARs as entries inside an outer JAR**. It describes relative classpath paths according to the manifest contract, typically used for external dependencies. Running nested libraries inside a single archive requires an appropriate reading mechanism.

### Distinguishing "Starts Successfully" from "Loads All Dependencies"

It is possible for `java -jar app.jar` to start `main()` successfully and then throw:

~~~text
java.lang.NoClassDefFoundError: demo/lib/Helper
~~~

when a class in the nested JAR is actually needed. This is often a sign that the layout contains nested libraries, but the launch process **did not install a loader that understands that layout**. However, not every `NoClassDefFoundError` is caused by nested JARs: initialization errors, version mismatches, and other linkage issues can also lead to it. Always inspect the cause and the launch command.

## 5. How Do Specialized Launchers Solve This Problem?

A **specialized launcher** can perform the tasks that the standard JDK launcher does not do automatically:

1. Read the framework's archive format.
2. Distinguish **application classes** from **libraries**.
3. Access nested archives via a custom JAR API/abstraction or, in another approach, extract them to temporary files.
4. Create/configure a ClassLoader that recognizes those locations.
5. Set up the required environment (such as TCCL according to the framework's design).
6. Invoke the application's real `main()` after the loader has been prepared.

**There is no single technique used by all frameworks.** Direct nested JAR access and temporary extraction are two different implementation choices. You should not claim that every launcher always extracts inner JARs.

### 5.1. Spring Boot Executable JAR Example

The official Spring Boot documentation describes a typical structure:

~~~text
myapp.jar
├── META-INF/
│   └── MANIFEST.MF
├── org/springframework/boot/loader/...  (Boot bootstrap classes)
└── BOOT-INF/
    ├── classes/
    │   └── com/example/MyApplication.class
    └── lib/
        ├── dependency-1.jar
        └── dependency-2.jar
~~~

This layout itself shows that **`BOOT-INF/classes/` is not a standard classpath root** for `java -cp myapp.jar com.example.MyApplication`, and `BOOT-INF/lib/*.jar` are **nested** library JARs.

When the artifact is packaged properly by the Spring Boot plugin and run in the supported way:

~~~sh
java -jar myapp.jar
~~~

the manifest typically uses Spring Boot's launcher as the main entry point:

~~~text
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.MyApplication
~~~

- `Main-Class` is the **launcher** located where the standard Java launcher can load it.
- `Start-Class` specifies the **actual application main class**.
- The Spring Boot launcher sets up the loading environment for `BOOT-INF/classes` and `BOOT-INF/lib` before calling the application's main method.

The class name `org.springframework.boot.loader.launch.JarLauncher` applies to the **modern Spring Boot layout** (e.g., Boot 3.2+). Launcher package names differ across some Spring Boot generations; do not copy a manifest from another version without checking the Boot version in use.

**Source:** [Spring Boot — Launching Executable Jars](https://docs.spring.io/spring-boot/specification/executable-jar/launching.html).

### 5.2. Why Can Spring Boot Read Nested JARs?

The Spring Boot documentation describes the `NestedJarFile` abstraction: it maps nested JAR entries to offsets within the outer JAR so that class/resource bytes inside can be accessed **without necessarily extracting every library to disk**.

Spring Boot provides compatible URL/JAR connection mechanisms for internal URL forms such as:

~~~text
jar:nested:/path/myapp.jar/!BOOT-INF/lib/dependency-1.jar!/pkg/Type.class
~~~

This is an **example of syntax supported by Spring Boot through its own mechanism**, **not** syntax guaranteed to be understood by a standalone JDK `URLClassLoader` simply by calling `new URL(...)`. Do not infer from the `jar:...!/`-like appearance that multi-level JAR URLs have become a standard JDK protocol.

**Source:** [Spring Boot — NestedJarFile](https://docs.spring.io/spring-boot/specification/executable-jar/jarfile-class.html).

### 5.3. What Happens If You Bypass the Spring Boot Launcher?

Suppose you try to run:

~~~sh
java -cp myapp.jar com.example.MyApplication
~~~

with a properly laid out Spring Boot archive. The standard JVM may fail to find `com.example.MyApplication` because the class is under `BOOT-INF/classes/com/example/...` rather than at the root package path. Even if an entry can be found via JAR-reading APIs, the libraries under `BOOT-INF/lib/` are not automatically loaded onto the standard classpath.

Therefore, a **Spring Boot `bootJar` is not equivalent to a plain JAR** from Gradle/Maven. Use the proper launcher or the documented unpack/exploded mechanism for that version. Do not treat `java -jar` as the sole reason nested JARs work; **it is the Spring Boot bootstrap classes and loader inside the artifact** that provide this capability.

## 6. Standalone Java 17+ Practice: Standard URLClassLoader Sees the Nested Entry but Not the Class

This practice **does not require Spring Boot, Maven, or Gradle**. We create a JAR containing a nested JAR, try to find the inner class via a standard `URLClassLoader`, and then **extract the inner JAR to a real file** and load it again using a standard `URLClassLoader`.

### 6.1. Source and Output Structure

~~~text
demo/
├── src/
│   ├── app/
│   │   └── NestedJarDemo.java
│   └── lib/
│       └── demo/lib/Helper.java
└── build/
    ├── app/
    ├── lib/
    ├── pack/
    │   └── BOOT-INF/lib/helper.jar
    ├── helper.jar
    ├── outer.jar
    └── helper-extracted.jar   (created at runtime)
~~~

The `BOOT-INF/lib/` path in this practice is chosen solely to simulate **the location of a nested JAR**; this lesson's `outer.jar` is **not** a Spring Boot executable JAR, because it does not contain Boot's loader. This isolates the pure Java/JDK limitation.

### 6.2. File `src/lib/demo/lib/Helper.java`

~~~java
package demo.lib;

public class Helper {
    public static String message() {
        return "from-library";
    }
}
~~~

`Helper.class` will appear **only in the inner JAR**; do not accidentally put `build/lib` or `build/helper.jar` on the launcher's runtime classpath during the failure test step.

### 6.3. File `src/app/NestedJarDemo.java`

~~~java
import java.io.InputStream;
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardCopyOption;
import java.util.jar.JarEntry;
import java.util.jar.JarFile;

public class NestedJarDemo {
    public static void main(String[] args) throws Exception {
        Path outer = Path.of("build/outer.jar");

        try (URLClassLoader flat = new URLClassLoader(
                new URL[] { outer.toUri().toURL() },
                NestedJarDemo.class.getClassLoader())) {

            System.out.println("nestedEntryVisible="
                    + (flat.getResource("BOOT-INF/lib/helper.jar") != null));

            try {
                flat.loadClass("demo.lib.Helper");
                System.out.println("ordinaryLoaderFound=true");
            } catch (ClassNotFoundException expected) {
                System.out.println("ordinaryLoaderFound=false");
            }
        }

        Path extracted = Path.of("build/helper-extracted.jar");
        try (JarFile archive = new JarFile(outer.toFile())) {
            JarEntry nested =
                    archive.getJarEntry("BOOT-INF/lib/helper.jar");
            try (InputStream stream = archive.getInputStream(nested)) {
                Files.copy(stream, extracted,
                        StandardCopyOption.REPLACE_EXISTING);
            }
        }

        try (URLClassLoader unpacked = new URLClassLoader(
                new URL[] { extracted.toUri().toURL() },
                NestedJarDemo.class.getClassLoader())) {

            Class<?> helper = unpacked.loadClass("demo.lib.Helper");
            System.out.println("extractedLoaderFound="
                    + (helper.getClassLoader() == unpacked));
            System.out.println("message="
                    + helper.getMethod("message").invoke(null));
        }
    }
}
~~~

**Pre-run analysis:**

- `outer.toUri().toURL()` points to a **regular JAR file on disk**. `URLClassLoader flat` searches inside the outer archive.
- `flat.getResource("BOOT-INF/lib/helper.jar")` looks up **the entry containing the inner JAR's data bytes**, so it can return a resource URL.
- `flat.loadClass("demo.lib.Helper")` searches for the class at the corresponding `demo/lib/Helper.class` path, which **does not exist at the root of the outer archive**, resulting in a caught `ClassNotFoundException`.
- `JarFile` reads the `BOOT-INF/lib/helper.jar` entry and `Files.copy` saves those bytes as **the file `build/helper-extracted.jar`**.
- `URLClassLoader unpacked` uses the URL of the **extracted JAR**; now `demo/lib/Helper.class` sits directly inside the searched JAR, so loading succeeds.
- The program uses `try-with-resources` to close the `URLClassLoader`/`JarFile` instances that may hold file handles. Closing a loader does not guarantee immediate unloading of all classes.

### 6.4. Compiling and Packaging on Linux/macOS

From the `demo` directory, using JDK 17 or later:

~~~sh
mkdir -p build/app build/lib build/pack/BOOT-INF/lib
javac --release 17 -d build/lib src/lib/demo/lib/Helper.java
jar --create --file build/helper.jar -C build/lib .
cp build/helper.jar build/pack/BOOT-INF/lib/helper.jar
javac --release 17 -d build/app src/app/NestedJarDemo.java
jar --create --file build/outer.jar --main-class NestedJarDemo \
    -C build/app . \
    -C build/pack BOOT-INF/lib/helper.jar
java -jar build/outer.jar
~~~

The trailing `\` is only POSIX shell line-continuation syntax. You can write the `jar --create ...` command on **one line** if you are not using Bash/POSIX shell.

### 6.5. Equivalent Commands on Windows PowerShell

~~~powershell
New-Item -ItemType Directory -Force build/app, build/lib, build/pack/BOOT-INF/lib | Out-Null
javac --release 17 -d build/lib src/lib/demo/lib/Helper.java
jar --create --file build/helper.jar -C build/lib .
Copy-Item build/helper.jar build/pack/BOOT-INF/lib/helper.jar
javac --release 17 -d build/app src/app/NestedJarDemo.java
jar --create --file build/outer.jar --main-class NestedJarDemo -C build/app . -C build/pack BOOT-INF/lib/helper.jar
java -jar build/outer.jar
~~~

On both operating systems, run from the `demo` directory because `Path.of("build/outer.jar")` is a relative path. Do not add `build/helper.jar` or `build/lib` to the runtime classpath when running the example.

### 6.6. Verified Exact Stdout

~~~text
nestedEntryVisible=true
ordinaryLoaderFound=false
extractedLoaderFound=true
message=from-library
~~~

These four lines demonstrate **three distinct states**:

1. `nestedEntryVisible=true`: the outer JAR genuinely contains an entry named `BOOT-INF/lib/helper.jar`; the standard loader can find the entry as a resource.
2. `ordinaryLoaderFound=false`: the standard loader **does not automatically descend into the inner JAR** to load classes.
3. `extractedLoaderFound=true`: once the library is saved as a separate JAR file, the loader can define the class.
4. `message=from-library`: the class has been loaded and its public method can be invoked.

**Scope of the experiment:** extracting the archive here is only to clarify the mechanism. In production applications, extracting libraries requires attention to input security, temporary directories, write permissions, cleanup, synchronization/concurrency, and checksums/build reproducibility. Never extract untrusted archive contents indiscriminately.

### 6.7. How to Verify "Inner File" vs. "Direct Class" in a JAR

~~~sh
jar --list --file build/outer.jar
jar --list --file build/helper.jar
~~~

For `outer.jar`, you see `NestedJarDemo.class` and `BOOT-INF/lib/helper.jar`. For `helper.jar`, you see `demo/lib/Helper.class`. This check helps separate **a nested JAR resource** from **the actual class root that `URLClassLoader` searches**.

## 7. Comparison Table of Execution and Dependency Loading Mechanisms

| Mechanism | Library Layout | Who Provides Reading Capability? | Nested-JAR-Aware Loader Needed? |
|---|---|---|---|
| `java -cp "app.jar:lib/helper.jar" app.Main` | External JAR files | Java launcher + built-in loader | **No** |
| `new URLClassLoader(new URL[]{helperFileUrl})` | External JAR file URL | Standard `URLClassLoader` | **No** |
| `new URLClassLoader(new URL[]{outerFileUrl})`, helper inside outer | Nested JAR entry | Standard URLClassLoader **does not automatically read entries as classpath JARs** | **Yes**, if loading directly from nested |
| Shaded/uber JAR | Dependency classes merged into root JAR | Built-in loader/URLClassLoader is usually sufficient | **No** if packages are valid |
| Spring Boot executable JAR `java -jar` | `BOOT-INF/classes` + `BOOT-INF/lib/*.jar` | Boot launcher + nested-archive loader/handler | **Yes, provided by Boot** |
| Extract helper.jar then load with URLClassLoader | Inner JAR as standalone file | Extraction code + standard URLClassLoader | **No** after extraction |
| Container/script running JAR distribution | App directory + `lib/*.jar` | Script building `-cp` or framework launcher | Depends on packaging |

This table describes **typical mechanisms**, not a guarantee that every framework packages artifacts in a single way. "Executable JAR" only indicates that the artifact has an executable entry path; you must determine the actual launcher type and class layout.

## 8. Important Misconceptions

### "Using `java -jar` makes the JVM automatically load all nested JARs"

False. `java -jar` only selects the JAR/main entry point according to the launcher contract. A Spring Boot executable JAR works with `java -jar` **because its manifest points to the Boot launcher**, which knows how to read nested libraries.

### "If `URLClassLoader` can load the `helper.jar` resource, it can load classes inside it"

False. A resource of the outer archive is different from an archive inside that resource. `getResource("BOOT-INF/lib/helper.jar") != null` does not prove `loadClass("demo.lib.Helper")` will succeed.

### "Writing a URL like `jar:file:/outer.jar!/lib/helper.jar!/` is enough"

False in standard JDK behavior. A specialized archive/URL handling layer must understand multi-level semantics; syntax containing `!/` does not automatically grant nested JAR loading capability.

### "Adding `BOOT-INF/lib` to `-cp` will make the libraries usable"

Incorrect if it is only **an entry path inside an outer JAR** and not a real directory on disk. When an archive is extracted to a directory, the classpath can point to the extracted JAR files; however, **that mechanism differs from directly looking up unextracted nested JARs**.

### "Plain JAR, shaded JAR, and Boot JAR only differ in name"

False: they differ in how dependencies and classpath roots are recorded. A plain JAR may use external libs, a shaded JAR merges class files, and a Boot JAR typically uses nested libs and a bootstrap loader.

### "Spring Boot always extracts all inner JARs to a temporary directory"

Inaccurate. Spring Boot supports accessing nested JARs through abstractions such as `NestedJarFile` and does not need to unpack all dependencies to files during normal operation.

### "Any missing package/class error is caused by the nested-JAR limitation"

Inaccurate. `ClassNotFoundException`, `NoClassDefFoundError`, `NoSuchMethodError`, `UnsupportedClassVersionError`, and `IllegalAccessError` have different root causes; inspect the stack trace, versions, loaders, and archive layout before drawing conclusions.

## 9. Real-Project Diagnostic Workflow

If a project has been built into a JAR with nested dependencies, but classes cannot be found:

1. **Inspect the actual archive structure:** use `jar --list --file app.jar` or a ZIP tool. Are libraries external files, nested JARs under `BOOT-INF/lib`, or directly merged classes?
2. **Read the manifest:** is `Main-Class` the application class, the Boot launcher, or a custom launcher? Is there a `Start-Class` when using Spring Boot's format? Does the manifest have an appropriate external `Class-Path`?
3. **Check the actual launch command:** `java -jar`, `java -cp`, IDE, `gradlew run`, `bootRun`, and container scripts can create different loaders/classpaths.
4. **Identify the loader searching for the class:** is `ClassLoader.getSystemClassLoader()` the loader that contains the nested dependencies? Does the framework have a child/special loader? Print `getClassLoader()` of loaded classes if possible.
5. **Compare the class name and entries:** is `demo/lib/Helper.class` at the root of a JAR supported by the loader, or only inside `helper.jar` as an entry?
6. **If using Spring Boot:** run the proper Boot launcher/package format for your version, avoiding bypassing bootstrapping by running `Start-Class` directly from the outer JAR root.
7. **If using plain JDK URLClassLoader:** pass URLs of **real JAR files/real directories**; do not assume the loader automatically expands nested JARs.
8. **If packaging needs fixing:** choose external libs + launch script, a shaded JAR, or a framework-compatible nested JAR with a launcher; test from the released artifact, not only inside the IDE.
9. **If errors persist after the class is found:** check transitive dependencies, versions, JPMS exports, loader identity, and linkage/initialization errors, not just JAR placement.

### Commonly Used Tools

~~~sh
jar --list --file app.jar
jar --describe-module --file app.jar
java -Xlog:class+load=info -jar app.jar
~~~

`jar --describe-module` is useful when JPMS is involved; not every executable archive is required to be a named module. `-Xlog:class+load` on modern HotSpot JDKs helps observe the source from which classes are loaded, though its output is verbose and JDK-dependent; do not rely on it as fixed demo stdout.

### Questions to Ask When Seeing a Stack Trace

| Symptom | Check First |
|---|---|
| `ClassNotFoundException: demo.lib.Helper` from `URLClassLoader` | URL search path; is the class at the JAR root or only inside a nested JAR? |
| `NoClassDefFoundError: demo/lib/Helper` when running a plain outer JAR | Runtime loader missing dependency, archive layout, and root cause |
| `ClassNotFoundException` when running Boot `Start-Class` with `-cp` | Was the Boot launcher bypassed or is the `BOOT-INF/classes` layout incompatible? |
| `bootRun` works, `java -jar` fails | Was the artifact properly packaged with `bootJar`? Are version/manifest/loader correct? |
| `NoSuchMethodError` even though the class is found | Compile/runtime dependency versions, ABI mismatch |
| `ClassCastException` with the same binary class name | Was the class defined by two loaders into two distinct runtime types? |
