# The `<clinit>` method, static field initializers, and static blocks

> **Context:** Java Core → ClassLoader → Class Initialization. This lesson focuses on the code that runs during the **class/interface initialization phase** (class initialization), the execution order of `static` declarations, and how the compiler represents them with the JVM `<clinit>` method. The complete examples below use Java 17+ and run standalone using their exact file names.

## 1. Three concepts you must distinguish before reading code

- A **static field initializer** is the initial assignment expression attached to a class variable declaration, such as `static int count = initialize();`. The expression can have side effects, throw exceptions, or read other fields.
- A **static initializer block** is a `static { ... }` block in the `class` body. The block contains statements to run during class initialization. A class can have multiple `static` blocks interleaved with field initializers.
- **`<clinit>` (class/interface initialization method)** is a special method at the **class file/JVM level**, typically generated by the compiler to combine the static initialization instructions to be executed. It is not a method you declare yourself, call directly, or override in Java code.

Conceptual diagram:

~~~text
Java source code               Class file                    JVM runtime
static int a = compute(); ─┐
static { audit(a); } ───────┼──> <clinit>:()V ─────────────> runs when the class is initialized
static int b = more(); ────┘       in source order

static final int SIZE = 64  ────> ConstantValue = 64 ─────> assigned before running <clinit>
                                            (if the compiler emits the attribute)
~~~

**Note:** `static` belongs to the class, but it **does not mean** "runs immediately when the program starts". A class may already be **loaded / verified / prepared** while its static initialization has still not run. A class with no static initialization work to execute may **have no `<clinit>`** in its bytecode.

## 2. Quick distinction from the `<init>` constructor

`<clinit>:()V` is the JVM method for the static initialization code of a class or interface; a class file may omit this method if there is no static work to execute. `<init>(...)V` is a constructor, which can have multiple overloads and runs for each instance. Java source code does not call `<clinit>` directly; instead, the JVM orchestrates it automatically when the class is initialized. On the first `new Demo()`, class initialization completes before the constructor runs; subsequent `new` invocations still call the constructor without re-running static initializers.

The lesson **Distinguishing `<clinit>` from the `<init>` constructor** provides an example running `new` multiple times and explains instance field initializers, instance blocks, and `super(...)`. The remainder of this lesson focuses on bytecode, ordering, and limitations of **static initialization**.

## 3. What has the JVM done before `<clinit>`?

Phases specified by the JVM Specification:

~~~text
Loading                 Linking                                         Initialization
read / define class     ├─ Verification: check bytecode                 ├─ assign ConstantValue if present
                        ├─ Preparation: create static fields, defaults  └─ run <clinit> if the class has one
                        └─ Resolution: resolve symbolic references
                            (timing may be eager or lazy)
~~~

During **preparation**, static fields are created and given **default values**: `int` is `0`, `boolean` is `false`, and references are `null`. Do not say that `static int x = 10` ran "during preparation": the assignment expression produced from the source code belongs to initialization.

A common point of confusion: constant fields with `ConstantValue`. According to the JVMS, the value from that attribute is assigned **during initialization, before invoking `<clinit>`**; the JVM does not run an ordinary Java bytecode instruction for that constant at its declaration site. That is why the JLS algorithm prioritizes assigning **constant variables** before other initializers.

Consider two cases:

~~~java
static final int PORT = 8080;                 // constant variable: int + constant expression
static final int RUNTIME_PORT = readPort();   // final, but NOT a constant variable
~~~

`PORT` can be represented by `ConstantValue`, and direct references from other classes may be **inlined** by the compiler. `RUNTIME_PORT` requires running the `readPort()` expression during initialization, even though it is `final`.

**There is no guarantee that all symbolic references are resolved at the same time.** The JVM may link/resolve eagerly or lazily within the bounds of the specification; the condition that triggers initialization is what you should rely on, not a log message reporting that a class was just loaded.

## 4. In what order do static field initializers and static blocks run?

For ordinary static initialization code, Java executes **field initializers and static blocks in the order they appear in the class body**, after mandatory steps such as assigning compile-time constants and initializing required superclasses. Each initializer can read state assigned earlier; a field declared later that has not yet been assigned still holds its **default** value.

Runnable example, file **`InitOrder.java`**:

~~~java
public class InitOrder {
    static class Demo {
        static int first = mark("field first", 10);

        static {
            System.out.println(
                "block: first=" + first + ", second=" + readSecond());
        }

        static int second = mark("field second", 20);

        static int readSecond() {
            return second;
        }

        static int mark(String name, int value) {
            System.out.println(name);
            return value;
        }
    }

    public static void main(String[] args) {
        System.out.println("before");
        System.out.println("result=" + Demo.second);
        System.out.println("again=" + Demo.first);
    }
}
~~~

~~~bash
javac --release 17 InitOrder.java
java InitOrder
~~~

Actual output on OpenJDK 21 when compiled with `--release 17`:

~~~text
before
field first
block: first=10, second=0
field second
result=20
again=10
~~~

Step-by-step explanation:

1. The JVM begins initializing `Demo` when `Demo.second` needs to be read, as it is a static field that is **not a constant variable**.
2. Initially `first=0` and `second=0` due to preparation.
3. `first = mark(...)` prints `field first`, then sets `first=10`.
4. The `static` block runs; `readSecond()` observes `second=0` because the initializer of `second` appears **after** this block.
5. `second = mark(...)` prints `field second`, then sets `second=20`.
6. `main` receives the result `20`; the subsequent read of `Demo.first` does not re-run the initializers.

### 4.1. Inspecting bytecode combined into `<clinit>`

After compiling the example:

~~~bash
javap -c -p 'InitOrder$Demo'
~~~

Look for the `static {};` section near the end of the `javap` output. The key bytecode pattern has the following meaning:

~~~text
invokestatic mark(...)         // compute first
putstatic first                // first = 10
... invokevirtual println ...  // run static block
invokestatic mark(...)         // compute second
putstatic second               // second = 20
return
~~~

Code tested on OpenJDK 21 shows that the `static {};` section contains both `putstatic` instructions and the print call from the middle block, in that exact order. The **behavioral** order is specified by the language; specific constant pool indices, offsets, and optimized opcodes may differ across compilers/JDKs.

### 4.2. Forward references: compile-time rules and runtime values

The snippet below **fails to compile** because it reads a field declared later by *simple name* inside an initializer:

~~~java
class IllegalForward {
    static int first = later; // illegal forward reference
    static int later = 7;
}
~~~

However, the forward-reference restriction does not prohibit a method like `readSecond()` from reading the field once the JVM allows that method to be called. Therefore, `InitOrder.Demo` above **compiles**, yet still observes `second=0` while initialization is incomplete. Qualified field access or indirect method calls can bypass the compile-time prohibition, but doing so **does not cause the field to be assigned any earlier**.

**Rule of thumb:** If static fields depend on one another, write a straightforward initialization flow in the proper order and avoid callbacks in between. Do not design correctness logic around another field happening to still hold its default value.

## 5. Compile-time constants and static initialization code

`static final int RETRIES = 3` and `static final String LABEL = "ready"` are **constant variables**: `final`, of primitive or `String` type, whose value is a *constant expression*. They can use the `ConstantValue` attribute and be inlined into caller code. `static final Integer BOXED = 3` or `static final int SIZE = Integer.parseInt("3")` are not constant variables and require a runtime initializer. `ConstantValue` is assigned **during initialization before `<clinit>`**, after preparation sets default values.

Merely seeing `static final` is not enough to conclude whether `<clinit>` code exists or whether a read triggers initialization. The lesson **Operations that do not trigger initialization** presents dedicated examples on compile-time constants, `Integer`, inlining, and binary compatibility.

## 6. When does the JVM enter `<clinit>`?

A class may already be loaded/linked, yet its static code is executed only when **initialization** is requested. Common trigger points include: `new`, `getstatic` reading a nonconstant field, `putstatic` writing a field, `invokestatic` calling a static method of the **declaring type**, or APIs such as `Class.forName(name, true, loader)`. Conversely, merely performing `T.class`, `new T[5]`, or `Class.forName(name, false, loader)` does not by itself require initializing `T`.

The lessons **Operations that actively trigger initialization** and **Operations that do not trigger initialization** provide detailed guidance on triggers, reflection, MethodHandle, and constant inlining. Here, the key point is distinguishing **when the class file is available** from **when `<clinit>` code executes**.

## 7. Superclasses and interfaces in the initialization process

Before running the normal static initializers of a class, the JVM must initialize its superclass and any superinterfaces **that declare default methods** according to the specified algorithm. However, initializing an interface on its own does not automatically trigger initialization of all its superinterfaces; merely having an `implements` relationship also does not cause all interfaces to execute their static code.

The lessons **Superclass initialization and static initializer execution order** and **Interface initialization and the impact of default methods** provide dedicated examples with output to verify the ordering across types.

## 8. Initialization synchronization and reading incomplete values

The JVM coordinates initialization by **runtime class identity** (binary name and defining loader); a thread currently initializing a class forces other threads needing the same class to wait. When **that same thread** requests initialization of the same class again along a call cycle, the JVM does not re-run `<clinit>` from the beginning. Unassigned fields may still be `0` or `null`. Successful synchronization publishes the initial state, but it does not automatically make subsequent writes to mutable static fields thread-safe.

The two lessons **Multi-threaded class initialization synchronization** and **Recursive initialization, circular dependencies, and incomplete values** focus on happens-before guarantees, A → B → A cycles, and deadlocks.

## 9. If `<clinit>` fails

An unhandled exception thrown by a static initializer can leave the class in an **erroneous** state. The first time, the JVM wraps any throwable that is not an `Error` in `ExceptionInInitializerError`; if the throwable is an `Error`, it may propagate that error directly. Subsequent initialization requests for the **same runtime class** encounter `NoClassDefFoundError` instead of re-running `<clinit>`.

Therefore, look for the initial cause in the stack trace, and avoid placing I/O work or retryable operations inside a static initializer. The lesson **ExceptionInInitializerError and the failed initialization state** provides an in-depth debugging workflow.

## 10. Syntax and limitations of `static` blocks

A `static` block:

~~~java
class StaticRules {
    private static final java.util.Map<String, Integer> CODES;

    static {
        java.util.Map<String, Integer> values = new java.util.HashMap<>();
        values.put("ok", 200);
        values.put("missing", 404);
        CODES = java.util.Map.copyOf(values);
    }

    static int codeOf(String key) {
        return CODES.getOrDefault(key, -1);
    }
}
~~~

This is an **illustrative class** snippet that compiles on Java 17+ without declaring `main`. This approach is useful when multiple statements are needed to construct the final static state; `Map.copyOf` prevents callers from directly modifying that state after initialization. To test it from another program, call `StaticRules.codeOf("ok")` and it will return `200`.

Important limitations:

- A `static` block cannot use `return`; there is no instance `this`/`super`, and it cannot directly access instance fields or methods as if an object already existed.
- A static block must **be able to complete normally** under compile-time analysis; writing an infinite loop or an unconditional `throw` with no exit path violates the JLS restriction. A method called from an initializer can still throw at runtime, such as `FailureCase`.
- Checked exceptions in a static initializer must be handled inside the block or wrapped into an unchecked exception; a static initializer has no `throws` clause to declare.
- Interfaces **do not allow declaring `static { ... }` in Java syntax**, but they can have field initializers with method-call expressions, and the compiler can generate `<clinit>` for that interface.
- Enums, records, and compiler/framework-generated classes are still subject to class initialization rules; the generated code may contain more detail than the source lines suggest. Use `javap -c -p` to inspect the exact artifact that actually runs.
- Although the JVM typically combines static initializers into a single `<clinit>`, compiler optimizations for constants and other transformations may cause the resulting bytecode not to match each Java source line one-for-one. Focus on the **behavior mandated by the specification**, rather than assuming every compiler must emit identical bytecode.

## 11. Choosing between a static field initializer and a static block

| Need | Usually clearest approach | Considerations |
| --- | --- | --- |
| Standalone, concise value | `static final int LIMIT = 100;` | Compile-time constants may be inlined into clients |
| Need to call a method to compute the value | `static final Config DEFAULT = createDefault();` | The factory runs during class initialization; it may throw an exception |
| Need multiple steps or ordering constraints | `static { ... }` | Keep the block short with clear exceptions and dependencies |
| Configuration that may fail or depends on the environment | Explicit bootstrap / dependency injection | Avoid making the entire class unusable due to a one-time init failure |
| High resource creation cost that is rarely needed | Lazy holder or controlled lazy initialization | Handle closing/lifetime, concurrency, failures, and cleanup separately |

### 11.1. Initialization-on-demand holder: built directly on the `<clinit>` mechanism

~~~java
public final class LazyService {
    private LazyService() { }

    private static final class Holder {
        static final LazyService INSTANCE = new LazyService();
    }

    public static LazyService instance() {
        return Holder.INSTANCE;
    }
}
~~~

Because `LazyService.instance()` is a static method, it initializes `LazyService` if needed. However, `Holder` is a **separate class**: `Holder.INSTANCE` is initialized upon the first active use of `Holder`. The JVM guarantees cross-thread initialization coordination for `Holder`; this example demonstrates a simple lazy singleton without manually writing double-checked locking.

Limitations: the instance lives for the lifetime of the class/loader with no automatic resource-closing mechanism; if the constructor throws an exception, `Holder` becomes erroneous and there is no retry within the same loader. Avoid applying this pattern to resources that require a flexible stop/reopen lifecycle unless additional management mechanisms are added.

## 12. Checklist for debugging errors or analyzing `<clinit>`

When encountering a static initialization bug, follow this order:

1. **Identify the exact runtime class:** fully qualified name, defining loader, module, JDK/runtime, and launcher conditions. Classes with the same name in different loaders can have separate state.
2. **Find the first trigger:** `new`, `getstatic/putstatic`, `invokestatic`, `Class.forName(..., true, ...)`, framework reflection, or a subclass triggering its superclass or default-method interfaces.
3. **Read the source order:** all static field initializers and `static{}` blocks in order; mark dependencies on other classes. Distinguish constant variables from nonconstant static fields.
4. **Inspect bytecode when needed:** `javap -c -p ClassName`; examine the `static {};` section corresponding to `<clinit>`, `getstatic`/`putstatic` instructions, and `ConstantValue` in `javap -v`. Do not infer from a field's name that it necessarily has a `ConstantValue`.
5. **Read the first cause:** `ExceptionInInitializerError.getCause()` or `getException()` (legacy API), and the earliest logs; if you only see `NoClassDefFoundError`, look for the earlier failure in the same loader.
6. **Check for dependency cycles and blocking:** class A calling B while A is initializing and B reading back from A; locks, threads, external connections, and I/O inside `static{}`.
7. **Redesign if needed:** reduce side effects, move operations that can fail into explicitly managed startup logic, avoid unsynchronized shared mutable static state, and recompile consumers when changing compile-time constants.

Useful commands when JDK tools are available:

~~~bash
javac --release 17 InitOrder.java
javap -c -p 'InitOrder$Demo'
javap -v 'ConstantCase$Config'
java -Xlog:class+init=info InitOrder
~~~

`-Xlog:class+init=info` is logging for **HotSpot/OpenJDK supporting unified logging** and can print a large amount of output; the tag name and output format are not standard JLS syntax across all JVMs. Depending on your environment, check `java -Xlog:help`. `javap` is a JDK tool for reading class files; it can detect `ConstantValue` and `static {};` even without running the program.

## 13. Checkpoints when reading `<clinit>`

Read static field initializers and `static {}` blocks **in source order**, check for `ConstantValue`, use `javap -c -p` to see the bytecode typically printed under the `static {};` section, and distinguish **loading** activity from when the code actually runs. The number of `static` blocks in source code is not the number of `<clinit>` methods in the class file.

## 14. Self-check questions

1. Given `static int a = 1; static { a++; } static int b = a * 2;`, after initialization `a=2` and `b=4`. Explain this in terms of source order.
2. Why does `static final String LABEL = "ready";` not force its owning class to initialize when a client prints the constant, whereas `static final Integer BOXED = 42;` can? Answer using the **constant variable** criteria.
3. Why may `new ClassName[5]` and `ClassName.class` not trigger `<clinit>`?
4. After a static block throws `IllegalStateException` on the first initialization attempt, why may a subsequent attempt in the same loader see `NoClassDefFoundError`?
5. A plugin reload creates a new defining loader for the same class name: can static initializers run again? **Yes**, because that is a new runtime class identity, while the old class, if still referenced, remains a separate entity.
6. If a nonconstant field is declared after a block, why can the block read `0` through an indirect method call even though the field ends up as `20`?
7. Why does running `javap -c -p` and locating the `static {};` section help explain the ordering of field initializers and static blocks?

- [JVMS 5.4.2 — Preparation](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-5.html#jvms-5.4.2) and [JVMS `5.5 — Initialization](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-5.html#jvms-5.5): default values, `ConstantValue`, triggering initialization.
- [JVMS 2.9.2 — Class and Interface Initialization Methods](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-2.html#jvms-2.9.2): name/descriptor of the `<clinit>` method.
- [ClassLoader API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ClassLoader.html) and [Class.forName API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Class.html#forName(java.lang.String,boolean,java.lang.ClassLoader)): distinguishing loading from requesting initialization.

**Key takeaway:** Static field initializers and static blocks define a class's **initialization actions** in the order specified by the JLS; the compiler typically synthesizes them into `<clinit>` for the JVM to execute **when the class is initialized**, under the synchronization and error-handling mechanisms of the JVMS. Understanding *when*, *in what order*, and *for which class identity* matters more than memorizing the special method name.
