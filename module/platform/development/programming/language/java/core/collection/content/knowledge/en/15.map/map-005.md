# keySet, values, entrySet, and Map.Entry

## 1. One Map, Three Views of the Same Mappings

`Map<K, V>` stores a mapping from keys to values. When you need to process data using Collection operations, Java provides three views:

- `keySet()`: view of the keys.
- `values()`: view of the values.
- `entrySet()`: view of each key–value pair.

“View” is an important concept: the returned objects are backed by the original map rather than copying all the data into an independent structure. If the map changes, the view reflects the current data. Some operations performed through a view also modify the map directly. [Map Views Contract, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Map.html).

Example of item quantities:

~~~text
Map:
a -> 10
b -> 20
c -> 20
z -> null

keySet:  [a, b, c, z]
values:  [10, 20, 20, null]
entrySet:[a=10, b=20, c=20, z=null]
~~~

Each mapping contributes one key, one value occurrence, and one entry. Therefore, all three views have a number of elements equal to `map.size()`, even though some values are duplicated.

The lesson uses `LinkedHashMap` by default in the program so that printed output order is easy to compare. That is a choice for the examples; the `Set` and `Collection` return types do not automatically guarantee insertion order for every map.

After this lesson, you should be able to choose the right view for the task, predict the effect of a removal or update, and distinguish between a view, a copy containing references, a detached entry, and a deep copy.

## 2. What Do the Return Types Say About the Data?

The primary signatures:

~~~java
Set<K> keySet();
Collection<V> values();
Set<Map.Entry<K, V>> entrySet();
~~~

| View | One element represents | Can contain duplicates in the usual sense? | Use when |
| --- | --- | --- | --- |
| `Set<K>` from `keySet` | One key | No duplicate keys per the map contract | Only keys are needed |
| `Collection<V>` from `values` | The value of one mapping | Yes, multiple keys can have the same value | Only values are needed |
| `Set<Map.Entry<K,V>>` from `entrySet` | One key–value pair | No two mappings for the same key | Both keys and values are needed |

`values()` does not return `Set<V>` because a map allows `b -> 20` and `c -> 20` to coexist. Turning the values collection into a `Set` would deduplicate them and lose information about the number of mappings.

For example:

~~~java
Collection<Integer> values = map.values();
~~~

is not equivalent to:

~~~java
Set<Integer> distinctValues = new HashSet<>(map.values());
~~~

The first line creates a variable holding a view. The second creates an independent structure containing the distinct values at the time of copying; if there are two mappings with the value 20, the new set only contains one element equal to 20.

Similarly, `Set<Map.Entry<K,V>>` is not a `Map<K,V>`. It is a set of objects representing pairs. To read the key side and value side of an element, use `getKey()` and `getValue()`.

## 3. Choosing How to Iterate Based on What You Actually Need

### Only Keys Needed

~~~java
for (String key : map.keySet()) {
    System.out.println(key);
}
~~~

This is the natural approach when you need to list configuration names, product codes, or accounts present in the map.

### Only Values Needed

~~~java
for (Integer value : map.values()) {
    if (value != null) {
        System.out.println(value);
    }
}
~~~

Each mapping is visited once, so duplicate values can appear multiple times. In the opening example, the number 20 is visited twice.

### Both Keys and Values Needed

~~~java
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    String key = entry.getKey();
    Integer value = entry.getValue();
    System.out.println(key + " -> " + value);
}
~~~

`entrySet` provides both pieces of data from the same mapping. Iterating over keys and then calling `map.get(key)` can work in simple situations, but it adds extra lookups when you could already read the entry directly.

Do not assume the two approaches have the same cost on every map. Furthermore, on a `LinkedHashMap` configured in access-order mode, certain `get` calls also affect the order; the program in this lesson uses the default insertion-order constructor to avoid mixing the two mechanisms.

When you need to read pairs without needing the Entry object, you can use:

~~~java
map.forEach((key, value) ->
        System.out.println(key + " -> " + value));
~~~

Whichever approach you use, adding or removing mappings during iteration must still follow the rules of that iteration mechanism. Lambda syntax does not automatically make updates safe.

## 4. Views Stay Linked to the Original Map

Hold a view variable and then modify the map:

~~~java
Set<String> keys = map.keySet();
map.put("d", 40);
~~~

`keys` sees key `d`. There is no need to call `keySet()` again to see the new mapping.

Similarly:

~~~java
Collection<Integer> values = map.values();
map.put("a", 11);
~~~

the `values` view reflects the new value of `a`. It is not a list of quantities captured at the time the variable was declared.

Relationship diagram:

~~~text
              +--> keySet: view of the keys
Source Map ---+--> values: view of each value
              +--> entrySet: view of the pairs

All three views are backed by the state of the source Map.
A valid removal through a view removes the mapping in the Map.
A change to the Map is reflected in the views.
~~~

When `map.clear()` is called, any held views become empty. If a new mapping is added afterward, those same old view variables see the new mapping again. “Currently empty” does not mean “an empty collection detached from the source”.

Do not check `map.keySet() == map.keySet()` and use the result to infer whether the view is linked. Whether repeated calls return the same object instance is an implementation detail; what you should rely on is the view contract.

## 5. Removing Through Views: Real Impact on Mappings

The examples in this section apply to modifiable maps such as `LinkedHashMap` in the program. Read-only maps may reject the operations.

### keySet.remove Removes by Key

~~~java
boolean changed = map.keySet().remove("c");
~~~

If key `c` exists, its mapping is removed and `changed` is `true`. The mapping's value is removed along with it, because a Map does not keep an “orphaned” value that belongs to no key.

This operation can still succeed when the value is `null`. The `boolean` flag indicates whether the key was removed, without depending on the old value.

### values.remove Removes One Occurrence

Suppose there are two mappings with the value 40. The call:

~~~java
boolean changed = map.values().remove(40);
~~~

removes one mapping whose value is 40, if present. It does not replace the value 40 with a blank slot, and by default it does not remove every mapping with the value 40.

After one removal, the number of occurrences of 40 drops from two to one, and the map size decreases by one. If choosing the exact key matters, do not rely on `values.remove`; remove by key or by key–value pair instead.

The iteration order of a specific Map type may cause you to observe a particular key being removed first. That is not a “always pick this key” contract that applies across all Maps.

### entrySet.remove Removes by the Whole Pair

~~~java
boolean changed = map.entrySet().remove(Map.entry("b", 20));
~~~

This call removes the mapping for `b` only if it currently has the value 20. If `b` has the value 999, then the pair `b=20` does not match.

Comparison:

~~~text
Map has b -> 20.

entrySet.remove(entry b=999) -> false, mapping b remains.
entrySet.remove(entry b=20)  -> true, mapping b is removed.
~~~

An entry used for probing does not need to come from that map itself; it only needs to be a `Map.Entry` object representing the pair to match. For pairs containing `null`, choose a way to create an entry that supports `null`, such as `new AbstractMap.SimpleImmutableEntry<>(key, value)`. `Map.entry` does not accept `null` keys or values.

### clear, removeIf, removeAll, and retainAll

Calling `clear()` through any view of a modifiable map removes all mappings. It is not an operation that merely clears the view's “display object”.

Bulk removal operations should also be read from the perspective of the chosen side:

~~~java
map.keySet().removeIf(key -> key.startsWith("temp-"));
map.values().removeIf(value -> value == null);
map.entrySet().removeIf(entry ->
        entry.getValue() != null && entry.getValue() < 0);
~~~

These three snippets are independent examples of filtering: by key, by value, and by pair. `values().removeIf` can remove all mappings matching the condition, unlike a single `values().remove(value)` call which removes only one occurrence.

`retainAll` keeps the elements that belong to the target collection; any mapping whose corresponding element is not retained is removed. Choose the view based on the intended filtering semantics, and avoid modifying the Map itself from inside the filter predicate.

## 6. Why Can't You Add via add and addAll?

The three standard views of a Map do not support `add` or `addAll`. To add or update mappings, use Map operations such as `put`.

~~~java
map.keySet().add("new");
map.values().add(99);
map.entrySet().add(Map.entry("new", 99));
~~~

For the views in the example, all three calls throw `UnsupportedOperationException`.

Intuitively, adding a key alone does not specify a value; adding a value alone does not specify a key. Even for an Entry, which contains the full pair, the `entrySet` contract does not define `add` as an alternative to `put`. Do not infer add capability merely from the `Set` return type.

The key point is that “backed by the Map” does not mean “supports every update operation in both directions”. Views allow reading and, on suitable maps, removal paths; adding mappings still goes through the Map API.

## 7. How Does Map.Entry Represent a Pair?

Core methods:

~~~java
K getKey();
V getValue();
V setValue(V value);
~~~

`getKey` reads the key, and `getValue` reads the value. `setValue` is an optional operation: if supported on a live entry used within its valid scope, it replaces the mapping's value and returns the previous value.

~~~java
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    Integer old = entry.getValue();
    if (old != null) {
        Integer previous = entry.setValue(old + 1);
    }
}
~~~

The `previous` variable holds the value before the update. The key remains unchanged. `Map.Entry` has no `setKey` method; changing a key means changing the identity of the mapping, which requires a map-level operation with a policy for handling an already-existing target key.

Do not assume every object of type `Map.Entry` can write back to a Map. Entries from a read-only view, entries created by `Map.entry`, or `SimpleImmutableEntry` may disallow `setValue`. Conversely, a standalone `SimpleEntry` may allow changing its own value while not being linked to any Map.

### Lifetime of a Linked Entry

An entry object obtained while iterating `entrySet` has its backing link guaranteed during that iteration. Java 17 does not provide a general guarantee that you can hold onto it and continue using it arbitrarily outside the iteration, or after the map is modified in an unsupported way. In particular, do not retain a removed entry and call `setValue` expecting it to re-add the mapping. [Map.Entry Contract, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Map.Entry.html).

Therefore, read the key/value and update via `setValue` during the iteration itself. If you need to pass pairs elsewhere or keep them longer, create a detached entry while it is still valid.

### Equality Checks Both Sides

Under the standard Entry contract, two entries are equal when their keys are equal and their values are equal, with comparisons handling `null`. Therefore `b=20` is different from `b=999`, and also different from `c=20`.

This explains why `entrySet.contains` or `entrySet.remove` must check both parts of the pair. Equal values alone do not make two mappings the same entry.

Do not use `==` to compare a newly created probe entry against an entry in the map when you want to check for the same data pair. Two distinct objects can still represent the same pair.

## 8. Complete Java 17+ Program

Save as `MapViewsDemo.java`. The program uses `LinkedHashMap` by default in insertion order, so stdout has a stable order for comparison. Insertion-order preservation comes from this Map implementation, not from the `Set` or `Collection` view types themselves. [LinkedHashMap Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashMap.html).

The section with linked entries only reads and updates entries while the iteration is still active; after modifying the source structure, the program does not reuse the held linked entries. Newly created detached entries are used afterward.

~~~java
import java.util.AbstractMap;
import java.util.ArrayList;
import java.util.Collection;
import java.util.Collections;
import java.util.Iterator;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Set;

public class MapViewsDemo {
    static void expectUnsupported(String label, Runnable action) {
        try {
            action.run();
            throw new AssertionError("Expected UnsupportedOperationException: " + label);
        } catch (UnsupportedOperationException exception) {
            System.out.println(label + "=UnsupportedOperationException");
        }
    }

    static int countValue(Collection<Integer> values, Integer target) {
        int count = 0;
        for (Integer value : values) {
            if (Objects.equals(value, target)) {
                count++;
            }
        }
        return count;
    }

    public static void main(String[] args) {
        Map<String, Integer> map = new LinkedHashMap<>();
        map.put("a", 10);
        map.put("b", 20);
        map.put("c", 20);
        map.put("z", null);

        Set<String> keys = map.keySet();
        Collection<Integer> values = map.values();
        Set<Map.Entry<String, Integer>> entries = map.entrySet();

        System.out.println("initial keys=" + keys);
        System.out.println("initial values=" + values);
        System.out.println("initial entries=" + entries);
        System.out.println("view sizes=" + keys.size() + ","
                + values.size() + "," + entries.size());

        map.put("d", 40);
        System.out.println("keys after put=" + keys);
        map.put("a", 11);
        System.out.println("values after replace=" + values);

        System.out.println("remove c through keys=" + keys.remove("c"));
        System.out.println("map after key removal=" + map);
        System.out.println("remove mismatched pair="
                + entries.remove(Map.entry("b", 999)));
        System.out.println("remove matching pair="
                + entries.remove(Map.entry("b", 20)));
        System.out.println("contains z-null entry="
                + entries.contains(new AbstractMap.SimpleImmutableEntry<>("z", null)));
        System.out.println("remove null through values=" + values.remove(null));
        System.out.println("map after pair and null removal=" + map);

        expectUnsupported("keys add", () -> keys.add("new"));
        expectUnsupported("values add", () -> values.add(99));
        expectUnsupported("entries add", () -> entries.add(Map.entry("new", 99)));

        map.put("e", 40);
        System.out.println("count 40 before=" + countValue(values, 40));
        System.out.println("remove one 40=" + values.remove(40));
        System.out.println("count 40 after=" + countValue(values, 40));
        System.out.println("size after one value removal=" + map.size());

        Iterator<Map.Entry<String, Integer>> iterator = entries.iterator();
        while (iterator.hasNext()) {
            Map.Entry<String, Integer> entry = iterator.next();
            Integer value = entry.getValue();
            if (value != null && value < 20) {
                iterator.remove();
            }
        }
        System.out.println("keys after iterator removal=" + keys);
        for (Map.Entry<String, Integer> entry : entries) {
            entry.setValue(entry.getValue() + 1);
        }
        System.out.println("map after setValue=" + map);

        Map<String, Integer> source = new LinkedHashMap<>();
        source.put("p", 1);
        source.put("q", 2);
        Set<String> sourceKeys = source.keySet();
        List<String> keyCopy = new ArrayList<>(sourceKeys);
        List<Map.Entry<String, Integer>> entryReferences = new ArrayList<>();
        List<Map.Entry<String, Integer>> detachedEntries = new ArrayList<>();
        for (Map.Entry<String, Integer> entry : source.entrySet()) {
            detachedEntries.add(new AbstractMap.SimpleImmutableEntry<>(entry));
        }

        Iterator<Map.Entry<String, Integer>> sourceIterator =
                source.entrySet().iterator();
        Map.Entry<String, Integer> first = sourceIterator.next();
        entryReferences.add(first);
        Integer old = first.setValue(100);
        System.out.println("setValue old=" + old);
        System.out.println("source p=" + source.get("p"));
        System.out.println("entry reference value=" + entryReferences.get(0).getValue());
        System.out.println("detached entry value=" + detachedEntries.get(0).getValue());

        source.put("r", 3);
        System.out.println("live keys contain r=" + sourceKeys.contains("r"));
        System.out.println("copied keys contain r=" + keyCopy.contains("r"));
        source.values().clear();
        System.out.println("source size after view clear=" + source.size());
        System.out.println("live key size after clear=" + sourceKeys.size());
        System.out.println("copied keys after clear=" + keyCopy);
        System.out.println("detached entries after clear=" + detachedEntries);
        expectUnsupported("detached setValue",
                () -> detachedEntries.get(0).setValue(9));

        Map<String, Integer> base = new LinkedHashMap<>();
        base.put("u", 7);
        Map<String, Integer> readOnly = Collections.unmodifiableMap(base);
        Set<String> readOnlyKeys = readOnly.keySet();
        base.put("v", 8);
        System.out.println("read-only live keys=" + readOnlyKeys);
        expectUnsupported("read-only key removal",
                () -> readOnlyKeys.remove("u"));
        expectUnsupported("read-only entry setValue",
                () -> readOnly.entrySet().iterator().next().setValue(99));

        Map<String, Integer> fixedMappings = Map.copyOf(base);
        base.put("w", 9);
        System.out.println("read-only sees w=" + readOnly.containsKey("w"));
        System.out.println("copyOf sees w=" + fixedMappings.containsKey("w"));

        keys.clear();
        System.out.println("map size after keys clear=" + map.size());
        System.out.println("all original views empty="
                + (keys.isEmpty() && values.isEmpty() && entries.isEmpty()));
        map.put("f", 50);
        System.out.println("old keys after new mapping=" + keys);
    }
}
~~~

### Comparing the Key Changes

Initially, all three views have four elements, even though the value 20 appears twice. Adding `d` through the Map makes the existing `keys` variable see `d`; replacing `a` makes the existing `values` variable see 11.

Removing `c` through keys removes mapping `c`. Probing the pair `b=999` fails, whereas `b=20` succeeds in removing the mapping. Removing `null` through the values collection removes mapping `z`. The `add` calls are rejected in accordance with the view contract.

When `d` and `e` both have the value 40, a single `values.remove(40)` call only reduces the occurrence count from two to one. Because the example uses `LinkedHashMap`, `d` is encountered first, and the remaining element is `e`. Do not turn that observation into a promise about which key is chosen across all Map types.

Removing `a` through the iterator itself and then incrementing values with `setValue` leaves the map as `{e=41}`. The `p, q` source section contrasts entry references with detached entries. The read-only section shows that “cannot modify through this path” does not mean “the source data never changes”. Finally, clearing through `keys.clear` empties all views, and then adding `f` makes the old `keys` variable see `f` again.


## 9. Modifying Data Properly During Iteration

### Removing Using the Active Iterator Itself

When you need to remove mappings based on a condition combining key and value:

~~~java
Iterator<Map.Entry<String, Integer>> iterator =
        map.entrySet().iterator();

while (iterator.hasNext()) {
    Map.Entry<String, Integer> entry = iterator.next();
    Integer value = entry.getValue();
    if (value != null && value < 20) {
        iterator.remove();
    }
}
~~~

`iterator.remove()` removes the element most recently returned by `next()`. Do not call it before `next`, and do not call it twice for the same `next` call. After removal, do not continue using the removed entry as an existing mapping.

This is the removal path coordinated with the iterator's state. By contrast, the following snippet is not a generally safe way to remove from views of `HashMap` or `LinkedHashMap`:

~~~java
for (String key : map.keySet()) {
    if (key.startsWith("temp-")) {
        map.remove(key);
    }
}
~~~

This is code demonstrating a bug. It removes directly through the Map while the implicit iterator of the `for-each` loop is active. Iterators that detect structural modification can throw `ConcurrentModificationException`, and the iteration contract does not let you rely on the outcome of modifying outside the supported path.

Do not write code that intentionally breaks the rules and then relies on exceptions to drive the algorithm. Change-detection mechanisms are only a best-effort bug-catching aid, not a synchronization guarantee, and not every bug is guaranteed to be caught.

To filter concisely in suitable situations:

~~~java
map.entrySet().removeIf(entry ->
        entry.getKey().startsWith("temp-"));
~~~

The predicate should only read the information needed to decide. Do not call `map.put` or `map.remove` from inside the predicate to introduce another structural modification path.

### Changing Values Using the Current Entry

On maps that support updates, calling `entry.setValue` while iterating the entry set is a value-update path permitted by the contract. It preserves the number of mappings and the key of the current mapping.

Do not conclude from this that any `map.put` call inside any loop is safe. The Map type, access-order mode, and specific operation affect iteration rules. The simple rule is to use the exact API designed for the job: the iterator to remove the current element, the entry to replace the current value, or a separate update phase after the read pass finishes.

### Views Do Not Create Snapshots for Multiple Threads

Calling `keySet` or `entrySet` does not lock the source and does not freeze the data. If a Map is shared across threads, you must apply the access mechanism appropriate for that Map type.

Similarly, a copy loop does not automatically become an atomic snapshot of a source that is being modified concurrently. To get a consistent snapshot, you must read the data under a coordination mechanism respected by all parties involved, or use a source that is already stable. These rules apply regardless of whether the result variable has type `List` or `Set`.

## 10. Views, Collection Copies, and Detached Entries

This is where many design bugs occur because a variable name includes the word “copy” while the underlying data still remains linked or shares objects.

### Copying Keys or Values

~~~java
List<String> keyCopy = new ArrayList<>(map.keySet());
List<Integer> valueCopy = new ArrayList<>(map.values());
~~~

These two lists have their own separate structure. Adding or removing mappings in the Map afterward does not automatically add or remove elements in the copied lists. `valueCopy` still preserves duplicate occurrences.

If you need a set of keys:

~~~java
Set<String> keyCopy = new HashSet<>(map.keySet());
~~~

The new set holds the keys at the time of copying, but does not promise insertion order. If you need to preserve the source order when taking a snapshot, you can choose `ArrayList` or `LinkedHashSet` depending on your requirements.

This copying still copies references to the key or value objects. If a value is a mutable `ArrayList`, modifying that list object itself can be visible from both places. A new result list does not automatically deep-copy each value object.

### Copying an Entry Collection Without Detaching Each Entry

The following snippet creates a separate list, but does not require creating new entry objects for each element:

~~~java
List<Map.Entry<String, Integer>> entries =
        new ArrayList<>(map.entrySet());
~~~

Therefore, do not treat it as a stable snapshot of pairs for long-term storage. It collects the references provided by the source; the entries may still be tied to the Map, and using linked entries outside the iteration scope is not guaranteed by the general contract.

In the program, the `entryReferences` list holds the same `first` object being used during an active iteration. `first.setValue(100)` causes `entryReferences.get(0).getValue()` to also see 100, because both variables point to the same entry. The program does not use that list after modifying the source structure.

The point of the example is that copying references does not turn the referenced object into a different object. Do not infer a guarantee that every Map type allows retaining linked entries and observing arbitrary updates later.

### Creating New Entries to Detach from the Map

For data that may contain null keys or values, one way to snapshot the pairs is:

~~~java
List<Map.Entry<String, Integer>> snapshot = new ArrayList<>();
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    snapshot.add(new AbstractMap.SimpleImmutableEntry<>(entry));
}
~~~

Each new `SimpleImmutableEntry` holds the key and value references that were read, and does not belong to the Map's entry-set view. It does not allow `setValue` on that entry object itself. [SimpleImmutableEntry Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/AbstractMap.SimpleImmutableEntry.html).

In the program, the detached entry `p=1` does not change to `p=100` when the iterated entry is updated. After the source Map is completely cleared, the detached entries still represent `p=1`, `q=2`.

If both sides are guaranteed non-null, Java 17 also provides `Map.Entry.copyOf(entry)` to create an entry that is not linked to the Map and does not allow changing its value. `Map.entry(key, value)` for creating a pair directly also requires non-null arguments.

If you want an independent entry that allows changing its internal value, `AbstractMap.SimpleEntry` is an option. Calling `setValue` on such a standalone entry only modifies that entry, not a Map it was never linked to.

### “Disallowing setValue” Is Still Not a Deep Copy

For example, suppose a detached entry has a value of type `List<String>`. The entry does not allow replacing the value reference via `setValue`, but the held list object may still allow `add` or `remove`.

To decide how deeply the result should be detached, evaluate each layer:

| Created structure | Are later mapping additions/removals reflected? | Can keys/values still share objects? |
| --- | --- | --- |
| Map view | Yes | Yes |
| `new ArrayList<>(map.values())` | Does not automatically reflect Map structure | Yes |
| List of new `SimpleImmutableEntry` instances | Does not automatically reflect new pairs or values replaced by reference in the Map | Yes |
| Deep copy per domain model | According to the designed copy contract | Can be separated, depending on how copying is implemented |

In the runnable program, keys are `String` and values are `Integer`, so sharing immutable objects does not cause unexpected content changes. With mutable data, an extra step is needed to convert to immutable objects or perform appropriate copying; there is no single generic “copy” operation that handles all of that automatically.

## 11. Unmodifiable and Unchanging with the Source Are Two Different Properties

### Wrapping a Map with unmodifiableMap

~~~java
Map<String, Integer> readOnly =
        Collections.unmodifiableMap(base);
~~~

`readOnly` is a view that disallows modification through its own API. Changes to `base` can still be seen through `readOnly`. Modifications through the wrapper's collection views are also rejected. [Collections.unmodifiableMap Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Collections.html#unmodifiableMap(java.util.Map)).

In the program:

~~~text
base initially has u=7.
Create readOnly and readOnlyKeys.
base adds v=8.
readOnlyKeys sees [u, v].
~~~

Attempting `readOnlyKeys.remove("u")` is blocked. Attempting to get an entry through `readOnly.entrySet()` and call `setValue(99)` is also blocked. You cannot bypass read-only protection by going through an entry.

Do not confuse this with wrapping only a collection:

~~~java
Set<Map.Entry<String, Integer>> onlySetProtected =
        Collections.unmodifiableSet(map.entrySet());
~~~

The set wrapper prevents adding/removing through the set itself, but it does not automatically turn each entry inside into an entry that disallows `setValue`. If the underlying Map supports entry updates and the entry is still within its valid scope, returning such a collection can still expose a path to modify values. When you want a read-only Map interface, use the appropriate Map wrapper; when you want a detached result, create detached data.

Similarly, wrapping `map.values()` into an unmodifiable collection does not make the value objects inside immutable.

### Copying Mappings with Map.copyOf

`Map.copyOf(base)` returns a Map that does not allow updates and does not continue to reflect additions, removals, or replacements in the source. It does not accept null keys or values. The iteration order of the result does not guarantee preserving the insertion order of `LinkedHashMap`.

In the program, after capturing `fixedMappings` and then adding `w` to `base`, the `readOnly` view sees `w`, but `fixedMappings` does not see `w`. The program only prints existence flags, avoiding assumptions about the iteration order of a Map created by `copyOf`.

Once again, key and value objects may still be shared. If values are mutable, a resulting Map that disallows `put` still does not mean the deep contents of the values are frozen.

### Returning Results from a Class

Suppose a data-managing class has a method:

~~~java
Set<String> names() {
    return internalMap.keySet();
}
~~~

If the internal map is modifiable, the caller can delete internal data using `names().clear()` or `names().remove(...)`. The `Set` return signature does not prevent that.

Decide on the contract to provide:

- Live and modifiable view: return the view if that is the documented intent.
- Live read-only view: wrap at the right level to block the modification paths that need to be blocked.
- Structurally independent snapshot: copy into an appropriate collection or Map.
- Deeply immutable result: requires an appropriate key/value model as well, not just an outer wrapper.

This decision affects data ownership, not just how loops are written.

## 12. Order, Sorting Entries, and Costs to Understand Properly

### Views Follow the Map Type

`HashMap` does not promise insertion order. `LinkedHashMap` by default in this lesson iterates in insertion order. `TreeMap` has an order defined by its keys. Assigning a `keySet` to a `Set` variable does not introduce a new ordering.

Do not combine two lists captured from `keySet` and `values` at different times and assume elements at the same index are guaranteed to form a pair. The source may have changed between the two reads, and the two copies do not carry linking information. If you need pairs, iterate `entrySet` in one pass and capture each pair while the source is stable.

### Sorting the Represented Result, Not Assuming the Original Map Is Reordered

To get a list of pairs sorted by value then key, you can create detached entries and sort that list. Example with `String` keys, `Integer` values, and possible null values:

~~~java
List<Map.Entry<String, Integer>> snapshot = new ArrayList<>();
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    snapshot.add(new AbstractMap.SimpleImmutableEntry<>(entry));
}

Comparator<Integer> valueOrder =
        Comparator.nullsLast(Comparator.naturalOrder());

snapshot.sort(
        Map.Entry.<String, Integer>comparingByValue(valueOrder)
                .thenComparing(Map.Entry.comparingByKey()));
~~~

This snippet is placed in a context where `map` and the necessary imports are already present. It assumes keys are non-null so natural key comparison is valid. `null` on the value side is placed last by the chosen comparator.

`Map.Entry.comparingByKey` and `comparingByValue` create comparators for pairs. Sorting the `snapshot` list does not change the Map type and does not turn the original Map into a map sorted by value. If you want to keep the result in a specific order, keep that list or build a result structure with a clear contract.

### Cost of Obtaining a View vs. Cost of Iterating or Copying

Do not treat a `keySet` call as an operation that copies N keys just because the return type is a collection. Standard views are linked to the source and are not a new full dataset. However, when iterating or copying, the program still has to visit the source elements according to the cost of the Map type.

A copy containing N elements requires memory proportional to N for the reference container, in addition to any deep-copying cost if applicable. Sorting a list of pairs also incurs sorting work proportional to the number of pairs and comparator cost. Do not conflate the cost of “obtaining a view” with the cost of “snapshotting everything and sorting”.

Removing by key can leverage the Map's key lookup structure; removing by value typically requires searching for a matching mapping. Therefore, choosing the right view also helps avoid extra search passes when you already have the key or entry.

## 13. Mistakes to Recognize Yourself

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Treating `keySet` as a copy | Map changes cause previously held result to change too | Make a copy if a snapshot is needed |
| Treating `values` as a Set | Losing or misunderstanding duplicate occurrences | Preserve Collection semantics |
| Calling `clear` on a view to “clean a temporary variable” | Deletes data in the Map | Only clear an independent collection when that is the goal |
| Adding with `keySet.add` or `entrySet.add` | Unsupported operation exception | Add mappings through the Map |
| Removing by value and assuming a specific key was removed | Removes the wrong entry for the requirement | Remove by key or by pair |
| Modifying the Map directly inside a for-each loop | Breaks iterator rules, may throw an exception | Use `Iterator.remove` or an appropriate filter operation |
| Holding a linked entry for a long time and updating after source changes | Outside Entry's guarantee scope | Read/update during iteration or snapshot new entries |
| Copying an entry collection and calling it a stable snapshot | Entries inside are not yet detached | Create detached entries individually |
| Assuming every `Map.Entry` supports `setValue` | Exception or misunderstood effect | Check entry type and contract |
| Wrapping only `Set<Entry>` and assuming data is read-only | Entries inside may still have a modification path | Wrap the Map at the right level or create detached data |
| Treating `unmodifiableMap` as a fixed copy | Source changes are still visible | Choose a copy if mapping independence is needed |
| Treating a shallow copy as a deep copy | Value objects are still shared | Copy or make values immutable according to the domain model |

## 14. Exercises and Solutions

### Exercise 1 — Types and Element Counts

A Map has `a -> 1`, `b -> 1`, `c -> 2`. What are the types of the three views and how many elements does each view have?

**Solution:** `keySet` is `Set<String>`, `values` is `Collection<Integer>`, and `entrySet` is `Set<Map.Entry<String,Integer>>`. Each view has three elements. The value 1 appears twice in `values`, so it must not be counted as only one distinct value.

### Exercise 2 — Does an Old View See New Mappings?

Create `Set<String> keys = map.keySet()` when the Map is empty. Then run `map.put("x", 10)`, `map.clear()`, and `map.put("y", 20)`. What does the `keys` variable see now?

**Solution:** It sees key `y` and does not see `x`. It is linked to the current Map, not fixed at the empty state when it was created, and does not stop being linked after `clear`.

### Exercise 3 — Removing a Duplicate Value

A Map has three keys all mapped to 7. After one successful call to `map.values().remove(7)`, how many mappings with value 7 remain? Can you know for certain which key name was removed just from the `Map` type?

**Solution:** Two mappings with value 7 remain. There is no basis to pick a specific key name from the `Map` type alone. If you need to remove a specific key, use an operation by key or by pair.

### Exercise 4 — Matching the Whole Pair

A Map has `a -> 1`. Does `entrySet.remove(Map.entry("a", 2))` remove `a`? What about `entrySet.remove(Map.entry("a", 1))`?

**Solution:** The first call returns `false` and does not remove anything; the second call returns `true` and removes the mapping if the source has not changed. Entry matching checks both key and value, not just the existence of key `a`.

### Exercise 5 — Why Not Use add?

An entry has both key and value. Why can't you still use `map.entrySet().add(entry)` as a way to add a mapping?

**Solution:** The `entrySet` contract does not support `add`/`addAll`. Having complete data does not create an operation outside the contract. Use `map.put(entry.getKey(), entry.getValue())` if that is the desired add/replace policy.

### Exercise 6 — Removing While Iterating

You need to remove mappings whose value is `null`. Fix a `for-each` loop that currently calls `map.remove(entry.getKey())`.

**Solution:** Use `Iterator<Map.Entry<K,V>>`; after `next`, if `entry.getValue() == null`, call `iterator.remove()`. Or, on a modifiable map that supports the operation, use `map.entrySet().removeIf(e -> e.getValue() == null)`. Do not reuse a removed entry to modify mappings.

### Exercise 7 — Effect of setValue

During an `entrySet` iteration over a modifiable `LinkedHashMap`, entry `a=10` receives `setValue(15)`. What does the method return, does the key change, and does the Map add a new mapping?

**Solution:** It returns 10, the key remains `a`, mapping `a`'s value changes to 15, and the number of mappings stays the same. There is no corresponding `setKey` to change the key of the same entry object.

### Exercise 8 — Entry Copies and Usage Scope

Is `new ArrayList<>(map.entrySet())` sufficient to return pairs as a long-lived snapshot? How should it be fixed?

**Solution:** Not sufficient; the list only copies the entry references provided by the source. During a valid and stable iteration of the source, create `new AbstractMap.SimpleImmutableEntry<>(entry)` for each pair. For data without nulls, `Map.Entry.copyOf` can be used. If values are mutable, you must also decide whether deep copying is needed.

### Exercise 9 — Read-Only Yet Live with the Source

Given `readOnly = Collections.unmodifiableMap(base)`. Afterward, `base` adds a new key. Does `readOnly` see it? Can you update through `readOnly.entrySet()`?

**Solution:** It sees the new mapping because it is a read-only view of the source. You cannot modify through entries of this Map wrapper; `setValue` is rejected. Do not confuse a Map wrapper with wrapping only a `Set` containing entries that are still modifiable.

### Exercise 10 — Designing Return Methods

A class returns `internalMap.values()` directly in a `quantities()` method. The caller wants to remove all `null` values using `removeIf`. Could this affect internal data? How should the contract be changed if the goal is only to return a report?

**Solution:** Yes; on a modifiable source, filtering through the view can remove internal mappings. If the goal is a structurally independent report, return a copy of the values; if pairs are needed, create detached pairs. If the report must also disallow modification or deep changes, apply the corresponding restrictions to the value data.

## 15. Pre-Use Decision Checklist

When choosing a collection from a Map, clearly identify whether you need keys, values, or pairs. Then decide whether the object being held is a live view or a snapshot, whether the caller has permission to modify the data, and whether the data needs to remain independent after the iteration.

Before a removal operation, state clearly which side is being matched: key, a single value occurrence, or the whole pair. Before an Entry update, verify that it supports `setValue` and is still within its valid usage scope. Before returning a “copy”, check both the outer structure and the inner object references.

The three views are not three separate maps. They are three ways of accessing the same mappings; understanding that relationship lets you use the Collection API conveniently while still keeping proper control over what data is modified.
