# Union, Intersection, Difference, and Subset Using Collection Operations

## 1. From Business Questions to Set Operations

When you have two groups of codes, permissions, tags, or identifiers, you often need to answer four questions:

- Which values appear in at least one of the two groups?
- Which values are present in both groups?
- Which values are in the first group but not in the second group?
- Is every value in the first group also in the second group?

These are **union, intersection, difference, and the subset relation**, respectively.

Suppose:

```text
A = {A, B, C}
B = {B, D}

Union A ∪ B:         {A, B, C, D}
Intersection A ∩ B:  {B}
Difference A − B:    {A, C}
Difference B − A:    {D}
```
The curly braces here represent a set mathematically and say nothing about iteration order.

In Java, `Set` inherits operations from `Collection` and gives them set semantics. A common source of confusion is that mutating operations **do not return a new result set**: they modify the receiver object and return a `boolean` indicating whether that object changed.

Therefore, each operation requires deciding two separate things:

1. Which mathematical result do you want?
2. Is it acceptable to mutate the input set, or do you need an independent result set?

This article uses Java 17 or later. The examples use `String`, with compatible `equals`/`hashCode` semantics, non-null data, and no concurrent modification. Requirements on element types and implementations will be explained later.

## 2. Mapping Table Between Mathematics and the API

| Goal | Meaning for each value x | How to perform on a copy of A |
| --- | --- | --- |
| Union A ∪ B | x is in A or in B | result.addAll(B) |
| Intersection A ∩ B | x is in A and in B | result.retainAll(B) |
| Difference A − B | x is in A and not in B | result.removeAll(B) |
| A is a subset of B | Every x in A is in B | B.containsAll(A), no copy needed |

The first three rows start from `result` containing the members of A. The subset row is a query and does not create a result set.

The formal contract is described in [Java 17 Set](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html) and the corresponding methods of [Java 17 Collection](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Collection.html).

You can verify the three set-building operations using a membership table:

| x in A? | x in B? | x in A ∪ B? | x in A ∩ B? | x in A − B? |
| --- | --- | --- | --- | --- |
| No | No | No | No | No |
| No | Yes | Yes | No | No |
| Yes | No | Yes | No | Yes |
| Yes | Yes | Yes | Yes | No |

This table helps you reason directly without memorizing method names mechanically. For example, `retainAll` means keeping the members that satisfy the condition of belonging to B; `removeAll` does the opposite to those members.

## 3. Union with addAll: Keeping What Exists on at Least One Side

### 3.1. Preserving the Inputs

```java
// Illustrative snippet: a and b are two compatible Set<String> instances.
Set<String> union = new LinkedHashSet<>(a);
union.addAll(b);
```
After the constructor runs, `union` contains the values of `a`. `addAll` inserts the values of `b` that are not already present.

Shared values are not duplicated. If A contains `B` and set B also contains `B`, the union still has only one `B`.

If the argument is a `List` with duplicate elements, the resulting `Set` still keeps only distinct values. That does not turn a union into list concatenation.

### 3.2. Commutativity Applies to Set Contents

In terms of contents, A ∪ B equals B ∪ A. However, if you use `LinkedHashSet`, starting from A versus starting from B can produce different iteration orders.

For example, starting with A and then adding new elements from B differs in order from starting with B and then adding new elements from A. Both results are still equal under `Set.equals`.

Do not compare `toString` strings with different orders to conclude that a union is wrong. Compare contents according to the `Set` contract when order is not part of the requirement.

### 3.3. addAll Returns a boolean, Not a Set

```java
// Illustrative snippet.
boolean changed = union.addAll(b);
```
If `union` already contains all values of `b`, `changed` is `false` even though `union` may be very large and non-empty.

You cannot write `Set<String> union = a.addAll(b)`: the return type is `boolean`. Nor should you use that `boolean` as the answer to "is the union empty?".

If you only need to know whether the union is empty and both inputs are stable, you can infer it from whether both sets are empty, rather than necessarily building the entire union. Choose work that matches the question you need to answer.

## 4. Intersection with retainAll: Keeping What Exists on Both Sides

### 4.1. Starting from a Copy and Filtering Against the Other Set

```java
// Illustrative snippet.
Set<String> intersection = new LinkedHashSet<>(a);
intersection.retainAll(b);
```
`retainAll` removes from `intersection` every element that is not in `b`. Because `intersection` starts as a copy of `a`'s members, what remains is A ∩ B.

In the example A = {A, B, C}, B = {B, D}, only `B` remains.

### 4.2. "Retain All of B" Does Not Mean Copying B

`retainAll` does not add missing elements. If `D` is in `b` but not in `a`, `D` does not appear in the intersection.

Read the method name as "retain the existing elements that belong to the reference collection", not "put the entire reference collection in here".

### 4.3. false Does Not Mean No Common Elements

If A = {A, B} and B = {A, B, C}, calling `retainAll` on a copy of A does not remove anything, so it returns `false`. Yet the intersection is {A, B}, which is not empty.

To check whether the intersection is empty after computing it:

```java
// Illustrative snippet.
boolean noCommonElements = intersection.isEmpty();
```
If you only need to know whether there are any common elements, see the `Collections.disjoint` section to avoid building an unnecessary result set.

## 5. Difference with removeAll: Direction Is Part of the Meaning

### 5.1. A − B Starts from A

```java
// Illustrative snippet.
Set<String> difference = new LinkedHashSet<>(a);
difference.removeAll(b);
```
The result keeps the values that are in `a` but not in `b`.

If you need B − A, you must start from `b`:

```java
// Illustrative snippet.
Set<String> reverseDifference = new LinkedHashSet<>(b);
reverseDifference.removeAll(a);
```
Difference is not commutative. In the example, {A, C} differs from {D}. Swapping the two operands changes the question.

### 5.2. Difference Removes a Group of Values, Not Quantities

A `Set` does not track occurrence counts. If the reference collection lists `B` three times, removing `B` from a `Set` does not have three occurrences to subtract one by one.

With a `List` as the receiver, `removeAll` also has different collection behavior regarding occurrences: it removes all elements of the `List` that belong to the reference collection. Do not call that multiset subtraction by per-value count.

This article builds set algebra on `Set`. If your problem requires "have three of product A, remove one product A", you need a separate quantity model.

### 5.3. Difference Is Not Automatically an Absolute Complement

A − B is a relative difference: it is bounded by the existing members of A.

To express "every value not in B", you must define a universe set U. Then the complement of B within U is U − B.

In business code, make the scope explicit: for example, configured codes that have not yet been selected, rather than vaguely saying "all remaining elements" without a bounding source.

## 6. Runnable Example: Independent Calculations Preserving Both Sources

Save the program as `SetAlgebraDemo.java`:

```java
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

public class SetAlgebraDemo {
    public static void main(String[] args) {
        Set<String> a = new LinkedHashSet<>(List.of("A", "B", "C"));
        Set<String> b = new LinkedHashSet<>(List.of("B", "D"));

        Set<String> union = new LinkedHashSet<>(a);
        union.addAll(b);

        Set<String> intersection = new LinkedHashSet<>(a);
        intersection.retainAll(b);

        Set<String> aMinusB = new LinkedHashSet<>(a);
        aMinusB.removeAll(b);

        Set<String> bMinusA = new LinkedHashSet<>(b);
        bMinusA.removeAll(a);

        System.out.println("A union B = " + union);
        System.out.println("A intersection B = " + intersection);
        System.out.println("A minus B = " + aMinusB);
        System.out.println("B minus A = " + bMinusA);
        System.out.println("A after calculations = " + a);
        System.out.println("B after calculations = " + b);
    }
}
```
Compile and run:

```shell
javac --release 17 SetAlgebraDemo.java
java SetAlgebraDemo
```
Output:

```text
A union B = [A, B, C, D]
A intersection B = [B]
A minus B = [A, C]
B minus A = [D]
A after calculations = [A, B, C]
B after calculations = [B, D]
```
Each result starts from its own copy. Therefore, computing the intersection does not destroy data needed later for the difference or union.

If you used a single variable and called `addAll`, `retainAll`, and `removeAll` in sequence, later steps would receive data already mutated by earlier steps. That would no longer be four independent operations on the same original A and B.

The example uses `LinkedHashSet` because it has an insertion-order contract, making the output predictable for the given data. The [Java 17 LinkedHashSet documentation](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashSet.html) describes this guarantee.

The mathematical contents of a `Set` do not depend on that order. With `HashSet` or sources without a guaranteed iteration order, you must not assume a fixed printed order.

## 7. Subset with containsAll: Reading the Direction Correctly

### 7.1. A Is a Subset of B When B Contains All of A

```text
A ⊆ B
corresponds to
B.containsAll(A)
```
The receiver object is the set acting as the container. The argument is the set being checked to see whether it lies entirely inside.

Two expressions:

- `a.containsAll(b)`: asks whether B is a subset of A.
- `b.containsAll(a)`: asks whether A is a subset of B.

Swapping the receiver and the argument reverses the relation. Naming variables `candidate` and `container` can make the call easier to read—think of them as "the set to check" and "the containing set".

### 7.2. Equal Sets Are Still Subsets

In the non-strict sense, every set is a subset of itself. Two sets with the same members are subsets of each other.

If you want a **proper subset** for finite sets within the range where `size()` accurately represents the count, the candidate must both be contained and have fewer elements:

```java
// Illustrative snippet: a and b are both Sets with compatible membership rules.
boolean properSubset = a.size() < b.size() && b.containsAll(a);
```
The `size` condition alone is not enough: A can have fewer elements than B and still contain a value that is not in B.

### 7.3. The Empty Set Is a Subset of Every Set

A set contains all elements of the empty set because there is no element in the empty set that violates the condition.

Therefore:

- The empty set is a subset of a non-empty set.
- The empty set is a subset of itself.
- The empty set is not a proper subset of itself.
- The empty set is a proper subset of a non-empty set within the finite sets in use.

Include this case in your reasoning and tests; do not treat `containsAll(empty)` returning `true` as a bug.

### 7.4. containsAll Does Not Check Occurrence Counts

A `Set` containing only `A` still returns `true` for `containsAll` with a `List` `[A, A]`. Every queried value is present, even though the `Set` does not have "two copies of A".

Therefore, do not use `containsAll` on a `List` as a check for sufficient inventory, sufficient character counts, or sufficient occurrences.

The `size`-based formula for distinguishing a proper subset only applies as shown when both sides are **sets**; do not plug in the `size` of a `List` with duplicates as if it were the count of distinct elements.

## 8. Disjointness with Collections.disjoint

According to [Java 17 Collections.disjoint](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Collections.html#disjoint(java.util.Collection,java.util.Collection)), returning `true` means the two collections have no elements in common.

For inputs using the same membership rules:

```text
Collections.disjoint(A, B) == true
corresponds to
A ∩ B is empty.
```
To ask "is there at least one common element?", negate that result.

`disjoint` is a `boolean` query. It does not create an intersection set and does not remove data from either side.

When you only need a yes/no answer, you do not have to copy A and call `retainAll(B)` just to call `isEmpty`. `disjoint` expresses intent clearly and can stop as soon as a common element is found, depending on the implementation.

Do not confuse `disjoint` with "two different sets". Two sets can be different and still intersect. A = {A, B} and B = {B, C} are not equal, yet they are not disjoint because both contain `B`.

## 9. Runnable Example: Subsets, Empty Sets, and Repeated Data

Save to `SetSubsetDemo.java`:

```java
import java.util.Collections;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

public class SetSubsetDemo {
    static boolean isSubset(Set<?> candidate, Set<?> container) {
        return container.containsAll(candidate);
    }

    static boolean isProperSubset(Set<?> candidate, Set<?> container) {
        return candidate.size() < container.size()
                && container.containsAll(candidate);
    }

    public static void main(String[] args) {
        Set<String> small = new LinkedHashSet<>(List.of("A"));
        Set<String> large = new LinkedHashSet<>(List.of("A", "B"));
        Set<String> sameMembers = new LinkedHashSet<>(List.of("B", "A"));
        Set<String> empty = Set.of();

        System.out.println("small subset of large = " + isSubset(small, large));
        System.out.println("large subset of small = " + isSubset(large, small));
        System.out.println("small proper subset of large = "
                + isProperSubset(small, large));
        System.out.println("large subset of sameMembers = "
                + isSubset(large, sameMembers));
        System.out.println("large proper subset of sameMembers = "
                + isProperSubset(large, sameMembers));
        System.out.println("empty subset of large = " + isSubset(empty, large));
        System.out.println("empty proper subset of empty = "
                + isProperSubset(empty, empty));

        List<String> repeatedRequest = List.of("A", "A");
        System.out.println("request occurrence count = " + repeatedRequest.size());
        System.out.println("small contains repeated request = "
                + small.containsAll(repeatedRequest));

        System.out.println("small and only B are disjoint = "
                + Collections.disjoint(small, Set.of("B")));
        System.out.println("small and large are disjoint = "
                + Collections.disjoint(small, large));
    }
}
```
Compile and run:

```shell
javac --release 17 SetSubsetDemo.java
java SetSubsetDemo
```
Output:

```text
small subset of large = true
large subset of small = false
small proper subset of large = true
large subset of sameMembers = true
large proper subset of sameMembers = false
empty subset of large = true
empty proper subset of empty = false
request occurrence count = 2
small contains repeated request = true
small and only B are disjoint = true
small and large are disjoint = false
```
What is verified:

1. {A} is contained in {A, B}, while the reverse direction is `false`.
2. The two sets {A, B} and {B, A} have the same members, so the subset relation is `true` but proper subset is `false`.
3. The empty set is contained in a non-empty set.
4. The empty set is not smaller than itself, so it is not a proper subset of itself.
5. A `List` requesting `A` twice is still satisfied by `containsAll` on a `Set` with only one `A`.
6. {A} and {B} are disjoint; {A} and {A, B} share a common element.

The two helper methods in the program accept `Set<?>` because membership checks do not need to insert new elements into the sets. They assume the sets are non-null and that elements can be queried against each other according to the implementation's contract.

The `Set<?>` parameter type does not automatically turn incompatible element types into valid queries. The type and null restrictions of the concrete collection still apply.

## 10. The Change-Reporting Boolean Is Not the Algebraic Result

Given a mutable receiver set and valid data, the return value can be understood as follows:

| Call on initial A | When does it return true? | What does false mean? |
| --- | --- | --- |
| A.addAll(B) | At least one new value was added from B | A already contained the values of B |
| A.retainAll(B) | At least one value of A was removed because it was not in B | A did not need any elements removed |
| A.removeAll(B) | At least one common value was removed from A | No matching elements were removed |
| A.containsAll(B) | Every value of B is contained in A | At least one value of B is not contained |

The first three rows report the effect of a mutating operation. The last row reports the truth value of a query. All four return `boolean`, but they do not answer the same kind of question.

For example, `retainAll` returning `true` can leave either an empty or a non-empty set, depending on which elements were removed and which were kept. `retainAll` returning `false` can also leave a large set if all elements already belonged to B.

Do not use `changed` as if it were:

- The result set.
- A signal that "the two sets intersect".
- A signal that "the result is non-empty".
- The count of added or removed elements.

If you want the change count in a single stable thread, you can record `size` before and after the mutation completes; you must still interpret the operation correctly. If other modifications interleave, the `size` difference is no longer a reliable count for that call alone.

## 11. Copying a Reference Does Not Create an Independent Set Copy

### 11.1. Two Variables Can Point to the Same Set

```java
// Illustrative snippet.
Set<String> result = a;
result.removeAll(b);
```
The assignment only creates another variable referencing the same object. `a` is also modified because `result` is `a`.

The pattern that preserves the source is:

```java
// Illustrative snippet.
Set<String> result = new LinkedHashSet<>(a);
result.removeAll(b);
```
The resulting `Set` object has its own structure. Adding or removing its members does not directly add or remove members in `a`.

### 11.2. Separate Structure Is Not a Deep Copy of Elements

The collection constructor does not clone each element object. If an element is a mutable object, `a` and `result` can still point to that same object.

Do not mutate fields used by `equals`/`hashCode` or comparison rules while elements are inside sets. A correct set operation also requires stable membership semantics during the operation.

In the examples using `String`, the elements are immutable values, so we can focus on structural additions and removals.

### 11.3. The Receiver Set Might Not Support Mutation

`Set.of` and `Set.copyOf` create structurally unmodifiable sets. Calling `retainAll` or `removeAll` directly on these sets can throw `UnsupportedOperationException`; they do not return a new result set in place of mutating.

You can read a `Set.of` as a source or as a reference collection with valid data. What matters is that the **receiver of the mutating operation** must support that operation.

If you want to return an unmodifiable result, compute it on a mutable copy first and then apply the appropriate output policy. If you use `Set.copyOf`, also account for its no-null policy and the fact that you cannot rely on the result's iteration order.

### 11.4. Runnable Example on Aliasing, Copies, and Return Values

Save to `SetMutationResultDemo.java`:

```java
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

public class SetMutationResultDemo {
    public static void main(String[] args) {
        Set<String> unchanged = new LinkedHashSet<>(List.of("A", "B"));
        System.out.println("addAll changed = "
                + unchanged.addAll(List.of("A", "B")));
        System.out.println("retainAll changed = "
                + unchanged.retainAll(List.of("A", "B", "C")));
        System.out.println("removeAll changed = "
                + unchanged.removeAll(List.of("Z")));
        System.out.println("unchanged result = " + unchanged);

        Set<String> original = new LinkedHashSet<>(List.of("A", "B"));
        Set<String> alias = original;
        alias.addAll(List.of("C"));
        System.out.println("alias is original = " + (alias == original));
        System.out.println("original after alias.addAll = " + original);

        Set<String> independent = new LinkedHashSet<>(original);
        independent.removeAll(List.of("A"));
        System.out.println("copy is original = " + (independent == original));
        System.out.println("independent result = " + independent);
        System.out.println("original after copy.removeAll = " + original);

        Set<String> fixed = Set.of("A", "B");
        try {
            fixed.retainAll(Set.of("B"));
        } catch (UnsupportedOperationException ex) {
            System.out.println("retainAll on Set.of = "
                    + ex.getClass().getSimpleName());
        }
    }
}
```
Compile and run:

```shell
javac --release 17 SetMutationResultDemo.java
java SetMutationResultDemo
```
Output:

```text
addAll changed = false
retainAll changed = false
removeAll changed = false
unchanged result = [A, B]
alias is original = true
original after alias.addAll = [A, B, C]
copy is original = false
independent result = [B, C]
original after copy.removeAll = [A, B, C]
retainAll on Set.of = UnsupportedOperationException
```
The first three calls all return `false`, yet the resulting set is still `[A, B]`. This refutes interpreting `false` as "no result".

`alias` and `original` are the same object, so adding through `alias` mutates `original`. `independent` is a different `Set`, so removing `A` from `independent` does not remove `A` from `original`.

Finally, `retainAll` is unsupported on `Set.of` in the example. This is a mutability error, not because the intersection expression {A, B} ∩ {B} lacks mathematical meaning.

## 12. Conditions for Both Sides to Share the Same Semantics

### 12.1. Same Membership Criterion

The set expressions above assume the involved sets use compatible equality semantics.

For custom classes, `equals`/`hashCode` must be consistent. For `TreeSet`, the comparator must be consistent with `equals` if you want to use the full general `Set` contract.

If one side treats strings case-insensitively as the same value while the other uses case-sensitive `String.equals`, calling operations across them may not reflect the same mathematical operation.

A clearer approach is to normalize to a key type with the chosen semantics before computing. Do not expect `addAll`/`retainAll`/`removeAll` to reconcile two different definitions of "equal".

`Collections.disjoint` also requires attention to the membership semantics of the inputs; the implementation may choose which side to iterate and which side to query with `contains`. Do not build correctness on guessing a specific internal iteration direction.

### 12.2. Null Policy and Query Types Still Apply

One `Set` may allow `null` while another rejects `null` even during membership checks. Operations like `retainAll` may check membership on the reference side, so do not assume "copying into `LinkedHashSet` makes all nulls safe".

Similarly, a sorted set may require elements to be comparable or supported by its comparator. `Set<?>` does not remove these runtime requirements.

The examples intentionally use non-null `String` on all sides so the contract can be read consistently.

### 12.3. Result Order Is a Separate Decision

Using `LinkedHashSet` preserves the iteration order encountered while building the result and the insertion order of new values. However, if the source does not guarantee order, copying does not restore an "original insertion order" that the source never provided.

If the result must be sorted by a specific comparator, choose a sorted `Set` and keep that exact comparator. Do not blindly copy into a different type and assume all prior guarantees remain.

Set contents and presentation order are two distinct requirements. Choose how you construct the result to satisfy both if needed.

### 12.4. No Transaction or Shared Snapshot Guarantees

Bulk mutating operations are not all-or-nothing by default. If an element is invalid or an internal operation throws an exception, do not assume all earlier changes are rolled back.

Also do not mutate the source collection while `addAll` is reading it; the contract places limits on modifying the source during an operation. With receivers, sources, and views that share underlying data, understand the reference relationships before mutating.

In a multithreaded environment, you need an appropriate strategy to maintain the required consistency. A `Set` implementation that is thread-safe per operation does not automatically make a "copy then compute then apply" sequence an atomic transaction.

## 13. Cost: Fewer Calls Does Not Mean O(1)

A single `addAll` or `retainAll` call can traverse many elements. Separate out:

1. The cost of copying A to preserve the source.
2. The cost of iterating over the elements to inspect.
3. The cost of membership checks or structural updates.
4. Memory for the result set.

For example, with typical hash-based sets, well-distributed hashes, and reasonable `equals`/`hashCode` costs:

- Building a copy of A takes work proportional to the number of elements in A.
- Computing a union by copying A and then adding B typically has expected cost O(n + m), where n = |A| and m = |B|.
- One way to compute an intersection is to inspect each element of A and check whether it is in B; if each membership query has expected constant cost, the inspection grows linearly with the number of elements traversed.
- A subset query can stop early when a missing element is encountered, but the worst case must inspect every element of the candidate set.

That analysis assumes particular implementation characteristics, not a guarantee of every `Set`.

If the reference collection is a `List` of length m where `contains` performs a linear search, checking n elements can produce O(n * m) work. Some methods or implementations have other optimizations, so look at the actual algorithm rather than attaching a fixed complexity to a method name.

Building a lookup structure beforehand can help when querying repeatedly, but you must include its construction cost, memory, and preservation of the equality criterion. Do not switch to `HashSet` if doing so loses a different membership relation that the business logic relies on.

If you only need to know whether the intersection is empty or whether a subset relation holds, using the corresponding query can avoid creating the full result set. If you genuinely need the resulting members, you must allocate the work and memory to collect them.

## 14. Application: Comparing Current State with Desired State

Suppose:

```text
Current A = {A, B, C}
Desired B = {B, D}
```
You can partition this clearly:

| Group | Formula | Result |
| --- | --- | --- |
| To add | B − A | {D} |
| To remove | A − B | {A, C} |
| Already present and still needed | A ∩ B | {B} |

This is a structured way to reason when reconciling groups of codes or configurations.

Keep both input states intact so the calculations are independent. If you remove elements from A first and then use the modified A to compute the other parts, you can lose information about the initial state.

The resulting groups only describe differences by the chosen key or element. They do not automatically apply changes to an external system, nor do they resolve errors when executing each change. The application step needs its own contract based on the program's context.

If elements are full records but the question is only "which codes were added or removed?", compute on an appropriate set of stable keys. Two records with the same code but different attributes may need a separate update-comparison step, rather than treating every difference as an add or remove.

## 15. Rules for Self-Checking Results

For sets using the same membership relation:

| Rule | Meaning |
| --- | --- |
| A ∪ ∅ = A | Union with empty adds no values |
| A ∩ ∅ = ∅ | No values in common with empty |
| A − ∅ = A | Nothing to remove |
| ∅ − A = ∅ | No elements on the left to keep |
| A ∩ A = A | Every element of A belongs to A |
| A − A = ∅ | All elements are removed by the same set |
| A ∩ B is a subset of A and of B | Intersection creates no elements outside both sides |
| A − B is a subset of A | Difference adds no new members |
| A − B is disjoint from B | Does not keep values still in B |

When testing a function that produces an independent result, you can keep copies of both sources and assert they were not mutated after the call. Do not check only the output while ignoring side effects on the inputs.

For finite sets:

```text
|A ∪ B| = |A| + |B| − |A ∩ B|
|A − B| = |A| − |A ∩ B|
```
In the example, the union has 3 + 2 − 1 = 4 elements; the difference A − B has 3 − 1 = 2 elements.

If you need to compute very large sizes in code, choose an appropriate numeric type and mind the limits of `size` under the collection contract. Do not turn a correct mathematical formula into an `int` addition that could overflow without checking the data range.

## 16. Common Pitfalls and Practice

### 16.1. Pitfalls to Recognize

| Pitfall | How to correct the reasoning |
| --- | --- |
| Using A.containsAll(B) to check whether A is a subset of B | Read "B contains all of A": B.containsAll(A) |
| Using the boolean from retainAll as the intersection result | Read the elements in the receiver set after the operation |
| Seeing retainAll return false and concluding the sets are disjoint | Check isEmpty on the intersection or use disjoint |
| Computing multiple results sequentially on the same mutated variable | Start each independent result from the appropriate original data |
| Assigning result = A and assuming A is preserved | Create an independent copy Set object |
| Swapping A − B into B − A | Identify the side to keep first and the side to remove second |
| Calling retainAll on Set.of and expecting a new set back | Compute on a mutable copy |
| Using a List with duplicates as a multiset with containsAll | containsAll checks presence, not sufficient occurrence count |
| Comparing two toString strings to check set equality | Use the Set.equals contract when order is not a requirement |
| Mixing different comparison criteria | Normalize or choose a compatible key type and relation |
| Assuming a collection call is constant time | Account for elements traversed and membership check cost |
| Thinking a Set copy is a deep copy of elements | Determine mutability of element objects separately |

### Exercise 1: Compute Four Groups

Given A = {1, 2, 3, 4}, B = {3, 4, 5}.

- Union: {1, 2, 3, 4, 5}.
- Intersection: {3, 4}.
- A − B: {1, 2}.
- B − A: {5}.

Neither initial set is a subset of the other. The intersection is a subset of both.

### Exercise 2: RetainAll Returning false

A = {1, 2}, B = {1, 2, 3}. A copy of A calls `retainAll(B)`.

No elements are removed, so it returns `false`. The result is still {1, 2}; do not conclude the intersection is empty.

### Exercise 3: Checking Proper Subset

A has two elements, B has three elements. Is that enough to conclude A is a proper subset of B?

No. You also need `B.containsAll(A)`. A smaller size does not guarantee membership.

### Exercise 4: List with Repeated Requests

The `Set` has {A}; the queried `List` is `[A, A]`. Does `containsAll` returning `true` prove there are two occurrences of `A`?

No. It only checks that every queried value is present. To compare quantities, you need a counting model.

### Exercise 5: Reversing Difference Direction in Reconciliation

A is the current group of codes, B is the desired group of codes. To find codes to add, use B − A; to find codes to remove, use A − B. Reversing the direction changes the meaning of the result.

### Exercise 6: Ordered Result Set

A function returns a `LinkedHashSet` copied from a `HashSet` that has no source order guarantee. Can you claim it preserves the original insertion order of the data?

No. It only preserves the order encountered when iterating the source and inserting into the result. A guarantee absent from the source does not appear after a copy.

### Exercise 7: Only Needing to Know About Common Elements

If the question is only "do A and B intersect?", you can use `!Collections.disjoint(a, b)` with compatible data. There is no need to build an intersection `Set` if you do not use its members.

Before each operation, identify **the starting side, the reference side, whether the set may be mutated, and whether the result should be a set or a boolean**. These four questions help you use collection operations accurately to express set operations.
