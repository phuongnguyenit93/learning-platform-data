# getOrDefault and the Case of a Key Mapped to null

## 1. Default for "No Key", Not for Every null Result

Suppose a map holds usage limits for each account:

```text
known → 7
unset → null
zero  → 0
```

The account `missing` is not yet in the map. The application wants to use 99 when there is no configuration:

```java
Integer limit = limits.getOrDefault(account, 99);
```

This is an illustrative snippet inside a method, where `limits` has type `Map<String, Integer>` and `account` is a `String`.

The deciding factor is **whether the key exists**:

- `known` has a key, so it returns 7.
- `unset` has a key, so it returns the stored value `null`.
- `zero` has a key, so it returns 0.
- `missing` does not have a key, so it returns 99.

A common mistake is reading the method name as "if get returns null, return the default". That interpretation loses the distinction between **having no mapping** and **having a mapping to null**.

This lesson explains that distinction, its impact on numeric types and collections, when the default value is evaluated, and how to write the code properly when business logic wants to treat `null` as missing.

## 2. Signature and the Three States to Distinguish

### 2.1. Return Value Has Type V

Signature in `Map`:

```java
default V getOrDefault(Object key, V defaultValue)
```

This is an abbreviated API signature, not a standalone program declaration. `key` is the key to look up; `defaultValue` is the value returned when there is no mapping for the key.

With `Map<String, Integer>`, the result is `Integer`. Arguments `0` or `99` are boxed into `Integer` in this context. The word "default" does not guarantee the result is always non-null or automatically converted to a primitive type.

The method has existed since Java 8, so it is available in Java 17+.

### 2.2. Decision Table

Suppose the map allows storing `null` values and the default value is 99:

| Key state | get(key) | containsKey(key) | getOrDefault(key, 99) |
| --- | --- | --- | --- |
| Key absent | `null` | `false` | `99` |
| Key present, value is null | `null` | `true` | `null` |
| Key present, value is 7 | `7` | `true` | `7` |
| Key present, value is 0 | `0` | `true` | `0` |

The first two rows have the same `get` result but different `getOrDefault` results.

If the default is also `null`, both the absent-key case and the mapped-to-null case return `null`. A return value like that by itself does not carry enough information to distinguish the two states.

This contract is described in [Map.getOrDefault Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Map.html#getOrDefault(java.lang.Object,V)).

### 2.3. 0, false, and Empty Strings Are Still Values

There is no rule treating `0`, `false`, empty strings, or empty lists as "missing" in `getOrDefault`. If a key is already mapped to those values, they are returned as the existing value.

If business logic wants "an empty string is also treated as unconfigured", that is a separate check after reading. Do not attach that extra meaning to the API.

## 3. Mental Model: Key Presence Must Be Preserved

An equivalent model in terms of results, assuming the map is not modified elsewhere:

```java
// Illustrative method placed in a class; requires importing Map.
static <K, V> V readAbsentOnly(Map<K, V> map, K key, V fallback) {
    V value = map.get(key);
    if (value != null || map.containsKey(key)) {
        return value;
    }
    return fallback;
}
```

If reading yields a non-null value, you already have the result. If reading yields `null`, you need to know whether the map holds the key:

```text
get(key)
   ├─ non-null → return that value
   └─ null
       ├─ key present → return the stored null
       └─ key absent  → return the default
```

This is a way to explain the semantics, not a claim that every `Map` class must call `get` and then `containsKey` the exact number of times shown in the snippet. An implementation class may optimize lookup directly according to its internal structure.

Do not replace the model above with:

```java
// Different policy: treat absent key and null value the same.
V value = map.get(key);
return value != null ? value : fallback;
```

This snippet is a method body using the existing variables. It may be right for business logic that wants to replace `null` as well, but it does not have the same semantics as `getOrDefault`.

## 4. The Method Does Not Store the Default Value in the Map

Given a map that does not yet have the key `"missing"`:

```java
// Illustrative snippet:
Integer first = limits.getOrDefault("missing", 99);
Integer second = limits.getOrDefault("missing", 88);
```

The results can be 99 and 88 respectively because each call has its own default. There is no automatic step that saves 99 for the next read.

After those calls:

```text
limits.containsKey("missing") remains false
the number of mappings does not increase
```

Similarly, `getOrDefault` does not automatically replace the mapping `unset → null` with `unset → 99`.

Distinguish between two goals:

| Goal | Required effect |
| --- | --- |
| Read with a fallback value when the key is missing | Return the value without storing the fallback |
| Initialize or update data in the map | Requires an appropriate write operation and its own policy |

Initialization APIs such as `computeIfAbsent` have a different contract, including the ability to write and how they handle `null` mappings. Do not switch to them merely to avoid writing a conditional without deciding whether mutating the map is allowed.

Also do not state too broadly that the call "cannot cause any changes at all". The argument expression supplied by the caller may have side effects. With a `LinkedHashMap` configured in access-order mode, `getOrDefault` can also update the access order; see [LinkedHashMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashMap.html). The point here is that the method does not insert a mapping or replace a mapped value with the default.

## 5. Runnable Program: All Three States and the Unboxing Error

Save as **GetOrDefaultStatesDemo.java**:

```java
import java.util.HashMap;
import java.util.Map;

public class GetOrDefaultStatesDemo {
    public static void main(String[] args) {
        Map<String, Integer> limits = new HashMap<>();
        limits.put("known", 7);
        limits.put("unset", null);
        limits.put("zero", 0);

        System.out.println("get known: " + limits.get("known"));
        System.out.println("get unset: " + limits.get("unset"));
        System.out.println("get missing: " + limits.get("missing"));
        System.out.println("default known: " + limits.getOrDefault("known", 99));
        System.out.println("default unset: " + limits.getOrDefault("unset", 99));
        System.out.println("default zero: " + limits.getOrDefault("zero", 99));
        System.out.println("default missing: " + limits.getOrDefault("missing", 99));
        System.out.println("contains unset: " + limits.containsKey("unset"));
        System.out.println("contains missing: " + limits.containsKey("missing"));

        System.out.println("size after reads: " + limits.size());
        System.out.println("another missing default: "
                + limits.getOrDefault("missing", 88));
        System.out.println("missing with null default: "
                + limits.getOrDefault("missing", null));

        int missingLimit = limits.getOrDefault("missing", 0);
        System.out.println("missing primitive limit: " + missingLimit);
        try {
            int unsetLimit = limits.getOrDefault("unset", 0);
            System.out.println("unset primitive limit: " + unsetLimit);
        } catch (NullPointerException ex) {
            System.out.println("unset primitive limit: " + ex.getClass().getSimpleName());
        }

        System.out.println("still contains unset: " + limits.containsKey("unset"));
        System.out.println("still missing: " + !limits.containsKey("missing"));
        System.out.println("final size: " + limits.size());
    }
}
```

Compile and run:

```shell
javac --release 17 -encoding UTF-8 GetOrDefaultStatesDemo.java
java GetOrDefaultStatesDemo
```

Exact stdout:

```text
get known: 7
get unset: null
get missing: null
default known: 7
default unset: null
default zero: 0
default missing: 99
contains unset: true
contains missing: false
size after reads: 3
another missing default: 88
missing with null default: null
missing primitive limit: 0
unset primitive limit: NullPointerException
still contains unset: true
still missing: true
final size: 3
```

Results to note:

- `get` does not distinguish `unset` from `missing` via the `null` result alone.
- `getOrDefault` returns `null` for `unset` but 99 for `missing`.
- The `0` of `zero` is preserved.
- Reading multiple times does not create the `missing` key.
- A default of 0 does not prevent an error when the actual stored value is `null`.
- The `unset` mapping still exists after the unboxing exception is caught.

The programs in this lesson were compiled with `--release 17` and run on OpenJDK 24.0.2. That flag checks against the Java 17 target language/API and emits corresponding bytecode; the JVM running the examples is still the version noted.

### Why Can `int` Still Receive a NullPointerException?

In the statement:

```java
int value = limits.getOrDefault("unset", 0);
```

the method returns a `null` `Integer` because the key `unset` exists with value `null`. Java then tries to unbox `Integer` to `int`. It is that unboxing step that throws `NullPointerException`.

There is no rule saying "passing an integer default guarantees a non-null result". You must first choose a policy for stored `null` values.

## 6. If You Want to Replace null Too, Write a Different Policy Explicitly

### 6.1. Treating Both Absent Keys and null Values as Missing

An illustrative method:

```java
static <K, V> V readMissingOrNull(Map<K, V> map, K key, V fallback) {
    V value = map.get(key);
    return value != null ? value : fallback;
}
```

With fallback 99:

| State | getOrDefault | readMissingOrNull |
| --- | --- | --- |
| Key absent | `99` | `99` |
| Key mapped to null | `null` | `99` |
| Key mapped to 7 | `7` | `7` |

A dedicated method name shows the reader that this is an application-level decision. It only returns a value according to the new policy; it does not overwrite `null` in the map.

If `fallback` itself is `null`, the result can still be `null`. To guarantee a non-null result, you need appropriate data or checks, not just a safe-sounding method name.

### 6.2. null May Carry Real Meaning

In a configuration, you might define the convention:

```text
key absent → inherit the general configuration
key null   → explicitly clear/unset the value at this scope
has value  → use the specific value
```

In that case, replacing `null` with the default erases a meaningful domain distinction. Conversely, if `null` only represents incomplete data and the application chooses to treat it as missing, a policy that replaces `null` as well can make sense.

Do not pick a handling approach just to make an exception disappear. First determine whether `null` is valid, intentional, and distinct from an absent key.

### 6.3. Do Not Guess with a Sentinel Value

If you use `-1`, an empty string, or a sentinel object to mark "no key", make sure that value can never be valid data. Otherwise, the application introduces another ambiguity.

When you need to know existence, use key-presence information or a result type that clearly describes the state. `getOrDefault` is suitable when you only need a fallback value for the case where there is no mapping.

## 7. The Default Value Is Evaluated Before the Method Runs

### 7.1. getOrDefault Takes a Value, Not a Promise to Compute Later

Consider:

```java
String value = settings.getOrDefault("theme", buildDefault());
```

Even though `theme` currently has the value `dark`, `buildDefault()` still has to be evaluated to produce the argument before `getOrDefault` is called. Afterward, the method may return `dark` and discard the computed argument value.

Evaluation order:

```text
evaluate the key argument
    ↓
evaluate the defaultValue expression
    ↓
call getOrDefault with the evaluated arguments
    ↓
choose the stored value or the default value
```

Java's argument evaluation rules are described in [JLS 17, section 15.7.4](https://docs.oracle.com/javase/specs/jls/se17/html/jls-15.html#jls-15.7.4).

If `buildDefault` is expensive, writes logs, increments a counter, or throws an exception, those things can still happen even when the configuration map already has the value being read. Do not put an operation with side effects into the argument assuming "it only runs when missing".

### 7.2. An Exception in the Default Expression Happens Before the Lookup

If the default expression throws an exception, the method call never proceeds normally with a completed default value. Having the key present does not make Java skip an error in the argument.

Do not use `getOrDefault` as a mechanism to avoid calling an expensive fallback service. The check must happen before calling that service.

### 7.3. Compute on Demand While Still Preserving Stored null

A helper can accept a `Supplier`:

```java
static <K, V> V readAbsentOnlyLazy(
        Map<K, V> map, K key, Supplier<? extends V> fallback) {
    Objects.requireNonNull(fallback);
    V value = map.get(key);
    return value != null || map.containsKey(key) ? value : fallback.get();
}
```

This is an illustrative method placed in a class; it requires importing `Map`, `Objects`, and `java.util.function.Supplier`.

The call:

```java
String value = readAbsentOnlyLazy(
        settings, "theme", () -> buildDefault());
```

creates a behavior object to invoke later. The lambda body `() -> buildDefault()` is only executed when the helper calls `fallback.get()`.

The helper still preserves `null` if the key exists. `Supplier` does not by itself change the missing-data policy; the condition inside the helper decides when to use it.

This read-only example assumes the map is not modified elsewhere between steps. Two lookups are not presented as an atomic transaction or a guarantee for multiple threads.

## 8. Runnable Program: Eager Default, Lazy Default, and Mutable Payload

Save as **DefaultEvaluationDemo.java**:

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.function.Supplier;

public class DefaultEvaluationDemo {
    private static int builds;

    private static String buildDefault() {
        builds++;
        System.out.println("build-default #" + builds);
        return "fallback-" + builds;
    }

    private static <K, V> V readAbsentOnlyLazy(
            Map<K, V> map, K key, Supplier<? extends V> fallback) {
        Objects.requireNonNull(fallback);
        V value = map.get(key);
        return value != null || map.containsKey(key) ? value : fallback.get();
    }

    private static <K, V> V readMissingOrNull(Map<K, V> map, K key, V fallback) {
        V value = map.get(key);
        return value != null ? value : fallback;
    }

    public static void main(String[] args) {
        Map<String, String> settings = new HashMap<>();
        settings.put("theme", "dark");
        settings.put("note", null);

        System.out.println("eager present: "
                + settings.getOrDefault("theme", buildDefault()));
        System.out.println("eager mapped null: "
                + settings.getOrDefault("note", buildDefault()));
        System.out.println("eager missing: "
                + settings.getOrDefault("language", buildDefault()));
        System.out.println("builds after getOrDefault: " + builds);

        System.out.println("lazy present: "
                + readAbsentOnlyLazy(settings, "theme", () -> buildDefault()));
        System.out.println("lazy mapped null: "
                + readAbsentOnlyLazy(settings, "note", () -> buildDefault()));
        System.out.println("lazy missing: "
                + readAbsentOnlyLazy(settings, "language", () -> buildDefault()));
        System.out.println("builds after lazy reads: " + builds);
        System.out.println("null-as-missing policy: "
                + readMissingOrNull(settings, "note", "untitled"));
        System.out.println("settings size: " + settings.size());
        System.out.println("language stored: " + settings.containsKey("language"));

        Map<String, List<String>> groups = new HashMap<>();
        List<String> fallback = groups.getOrDefault("guest", new ArrayList<>());
        fallback.add("blue");
        System.out.println("modified fallback: " + fallback);
        System.out.println("guest stored: " + groups.containsKey("guest"));

        groups.put("member", new ArrayList<>(List.of("green")));
        List<String> existing = groups.getOrDefault("member", new ArrayList<>());
        existing.add("gold");
        System.out.println("existing stored list: " + groups.get("member"));
    }
}
```

Run commands:

```shell
javac --release 17 -encoding UTF-8 DefaultEvaluationDemo.java
java DefaultEvaluationDemo
```

Exact stdout:

```text
build-default #1
eager present: dark
build-default #2
eager mapped null: null
build-default #3
eager missing: fallback-3
builds after getOrDefault: 3
lazy present: dark
lazy mapped null: null
build-default #4
lazy missing: fallback-4
builds after lazy reads: 4
null-as-missing policy: untitled
settings size: 2
language stored: false
modified fallback: [blue]
guest stored: false
existing stored list: [green, gold]
```

In the first three `getOrDefault` calls:

- `theme` has `dark`, yet default build #1 still occurs.
- `note` has `null`, yet build #2 still occurs; the result is still `null`.
- `language` is missing, so build #3 is used as the result.

In the helper taking `Supplier`:

- `theme` returns `dark` without an extra build.
- `note` returns `null` without an extra build.
- `language` is missing, so only then is default #4 built.

After both groups, `settings` still has two mappings and does not contain `language`. Creating on demand does not mean storing the result in the map.

`readMissingOrNull` for `note` returns `untitled`, because that function intentionally treats `null` the same as a missing key. It is a different policy called deliberately.

## 9. When the Default Value Is a Collection: Two Easy-to-Hide Mistakes

### 9.1. Adding to the Default Does Not Create a Mapping

A misleading way to write this:

```java
// Illustrative snippet; groups does not yet contain the key guest:
groups.getOrDefault("guest", new ArrayList<>()).add("blue");
```

The new list receives `blue`, but no statement attaches that list to `guest` in the map. Unless you keep the reference or write it elsewhere, `guest` is still missing on the next read.

The program keeps the default list in a variable so we can observe this:

```text
modified fallback: [blue]
guest stored: false
```

If the goal is to create a group when missing and then add a member, you must choose an intentional initialization/update operation. `getOrDefault` only resolves the return value of a read.

### 9.2. A Key That Already Has a List Returns That Same Reference

In the program, `member` has an `ArrayList` holding `green`. `getOrDefault` returns the stored list itself; adding `gold` through the returned reference changes the contents in the map to `[green, gold]`.

The method does not deep-copy values. Therefore, it is both true that `getOrDefault` does not insert a new mapping and true that calling code can mutate the returned payload.

If the value is an unmodifiable list, calling `add` can throw `UnsupportedOperationException`. If the value is `null`, calling `add` throws `NullPointerException`; a newly created default list does not replace `null` for an existing key.

### 9.3. A Shared Default Does Not Create Independent Groups

If you pass the same `ArrayList` as the default for two missing keys, both calls may return that same object, without creating either key in the map.

If business logic wants each group to have its own list, you need an appropriate data-creation flow. Do not pass a shared default and assume each key now owns a separate copy.

## 10. Null Depends on the Map Type, While the Default Remains a Return Argument

`HashMap` allows `null` values, so all three states in the first table can occur. See [HashMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashMap.html).

`ConcurrentHashMap` does not allow storing `null` keys or `null` values. For a valid key, the "key mapped to null" case is not a valid data state of that class; see [ConcurrentHashMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html).

Do not infer from that that `defaultValue` on a read must be stored or must satisfy all constraints of an inserted value. For example, a `null` default can be used for a missing valid key without inserting `null` into a `ConcurrentHashMap`.

Similarly, an unmodifiable map such as `Map.of` can still be read with a fallback value when a valid key is missing. `getOrDefault` does not require write permission just to return a default.

An invalid key according to the map class can still fail. The method is not a wrapper that catches every `NullPointerException` or `ClassCastException` and turns it into `defaultValue`. When writing code intended to work with multiple map types, check the key and `null` policy of the actual type.

## 11. Using It in an Update: Look at the Whole Expression

A counting example in a map that does not store `null` values:

```java
// Single-threaded illustrative snippet:
int next = counts.getOrDefault(word, 0) + 1;
counts.put(word, next);
```

If `word` is absent, `getOrDefault` returns 0. Addition produces 1. Only the subsequent `put` stores 1 in the map.

If `word` is currently mapped to `null`, addition requires unboxing `null` and can fail before `put`. Having a default of 0 does not automatically make a counter containing `null` valid.

In addition, read–add–write consists of multiple steps. Two concurrent threads do not automatically get an atomic increment just because the read step uses `getOrDefault`. An appropriate update design is needed under concurrent access.

When reading a long line of code, separate the three effects:

```text
lookup with missing-key policy
    → compute new result
    → write only if there is an explicit write operation
```

This avoids mistakenly attributing the effects of `put`, unboxing, or the default-building method to `getOrDefault`.

## 12. Common Errors and Fixes

| Symptom | Cause | Inferred fix |
| --- | --- | --- |
| Passed default 99 but received null | Key already exists with value null | Decide explicitly whether to replace null or keep it |
| Assigning to int throws an error | Returned null Integer is unboxed | Handle the null policy before the unboxing step |
| Read missing key, yet map still lacks the key | getOrDefault does not store the default | Add an initialization operation if business logic needs a write |
| Default-building service still runs when value exists | Argument is evaluated before the call | Check beforehand or use a lazy-creation helper |
| Default throws an error even though key exists | Exception occurs while evaluating argument | Do not put a calculation you want to skip into an eager argument |
| Added to default list, then data disappears | List was never attached to the map | Use an explicit group creation/write flow |
| Adding to returned list changes map contents | Received the same payload reference | Copy when separate data is needed |
| Used null default, still don't know if key exists | Null result remains ambiguous | Check containsKey or return an explicit state |
| Treated 0/false/empty as missing | Projected business rule onto the API | Check that condition separately |
| Concurrent counting still loses updates | Read–add–write is not atomic | Choose an appropriate concurrent update mechanism |

## 13. Self-Check Exercises with Solutions

### Exercise 1: Three Reads

A map contains `A → 5` and `B → null`; `C` is absent. What does calling `getOrDefault` with default 10 return for each key? What is the size afterward?

**Solution:** `A` returns 5, `B` returns `null`, `C` returns 10. The size remains 2; `C` is not added and `B` is not replaced.

### Exercise 2: Default Is Also null

With the same map above, call `getOrDefault(B, null)` and `getOrDefault(C, null)`. Do the two results distinguish `B` from `C`?

**Solution:** No, both are `null`. `containsKey(B)` is `true`, and `containsKey(C)` is `false` in the state under consideration.

### Exercise 3: Unboxing

With a `Map<String,Integer>` containing `B → null`, does `int value = map.getOrDefault("B", 0)` guarantee `value` equals 0?

**Solution:** No. The method returns `B`'s `null`; unboxing to `int` throws `NullPointerException`. You need to decide the policy for stored `null` values.

### Exercise 4: When Does the Builder Run?

`A` already has a value. Does `map.getOrDefault("A", createDefault())` run `createDefault`?

**Solution:** Yes, because Java must evaluate arguments before the call. `A` having a value only affects which value the method returns, not whether the argument becomes lazily evaluated.

### Exercise 5: Keep null but Build When Missing

You want to avoid creating a default if `A` has a value, while keeping `null` when `A` exists with `null`. Is checking only `map.get("A") == null` enough?

**Solution:** No. A `null` result can also be an existing valid mapping. You need to check key presence, like the `readAbsentOnlyLazy` helper, under single-threaded use or a controlled read state.

### Exercise 6: Default List

`groups` is missing key `G`. You call `getOrDefault("G", new ArrayList<>())`, add `X` to the result, and discard the variable. Does the map contain `G`?

**Solution:** No. Adding modifies the created list; it does not create the mapping `G → list`. An appropriate write or initialization operation is needed if you want to store it.

### Exercise 7: null as a Configuration Decision

In an application, an absent key means inherit; a `null` key means explicitly unset. Should `getOrDefault` be replaced with "if `get` is null, use the default"?

**Solution:** No, if you want to preserve those two meanings. That replacement merges the explicitly `null` state with the absent-key state and breaks the configuration policy.

### Exercise 8: Two Consecutive Defaults

The map is empty. Call `getOrDefault("A", 1)` and then `getOrDefault("A", 2)`. Are the results 1 and then 1 because the default was remembered?

**Solution:** No. The results are 1 and then 2, and the map remains empty. The fallback value belongs to each individual call and is not automatically remembered.
