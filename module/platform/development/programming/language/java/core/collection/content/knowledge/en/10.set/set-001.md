# Uniqueness Semantics and the Contract of Set

## 1. Set models a "presence or absence" relationship, not occurrence counts

`Set<E>` is a collection that models a mathematical set: each distinct value has at most one presence in the set according to the equality relation required by its contract.

For example, a user either has the `read` permission or does not. Having the input data mention `read` three times does not usually give that user "three `read` permissions." A Set can be a good fit for representing a set of permission codes.

Conversely, if the data represents three scans of a product, the number of occurrences may be meaningful. Converting directly to a Set discards the scan count information. You must clarify the requirements before deduplicating.

```text
Input data: read, write, read

Viewed as occurrences: 3 occurrences.
Viewed as a set of values: read and write, i.e., 2 distinct values.
```
What matters is not just that "a Set has no duplicates." You must be able to answer:

1. By what criteria are two elements considered duplicates?
2. When adding an element that is already present, what does the set do and what does it return?
3. Does the set allow modification, accept `null`, or preserve order?
4. If an element changes after being added, what happens?
5. How are two Set objects compared for equality?

The authoritative contract is described in [Java 17 Set](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html). This lesson uses Java 17 or later, and the examples operate sequentially in a single thread.

## 2. "Duplicate" is an equality relation, not an arbitrary visual similarity

### 2.1. The general contract is based on equals

For two non-null elements, a Set must not simultaneously hold two elements that are equal according to `equals` if it fully adheres to the Set contract.

At the specification level with `null` considered, methods such as `add` and `contains` are defined in terms of `Objects.equals`:

```text
Objects.equals(a, b)
- true if both are null;
- for non-null a, based on a.equals(b);
- false if only one side is null.
```
This is a semantic specification. An implementation is not required to call `equals` against every element in a loop. `HashSet` can use `hashCode` for routing; `TreeSet` has a comparison rule that will be explained separately.

### 2.2. Different references can still be equal

```java
// Illustrative snippet.
String first = new String("read");
String second = new String("read");

System.out.println(first == second);      // false: two different objects.
System.out.println(first.equals(second)); // true: same string content.
```
These two Strings must not be kept as two distinct values in a Set that follows `String`'s `equals` relation.

The `==` operator on references asks "are these the same object?" `equals` asks "are these two objects equal according to this type's rules?" The two questions can have different answers.

Conversely, two objects that print the same string via `toString` are not necessarily equal. A Set does not use printed representation as its identity rule.

### 2.3. Set does not automatically discover a "business key"

If a class has `id`, `name`, and `status`, a Set does not automatically know to use `id` to distinguish elements. It uses the equality relation defined by the element type and the relevant implementation.

A class that does not override `equals` typically retains object-identity equality inherited from `Object`. Two objects whose fields look identical can still be stored separately.

By default, the compiler generates `equals` for a `record` based on all of its record components. For example, a record with `id` and `displayName` treats two records with the same `id` but different `displayName` values as two different values. That may be right for a data snapshot, but it does not satisfy a "unique by `id`" requirement.

You must design the distinction criteria before choosing Set as a deduplication mechanism.

### 2.4. Textual differences are not normalized automatically

For `String`, `"read"` and `"READ"` are not equal according to `equals`. Whitespace and other content differences are not stripped automatically either.

If the domain treats certain forms as equivalent, you need an explicit normalization rule before adding, or a key type with appropriate semantics. Do not apply case conversion or trimming to every kind of identifier without first confirming the requirements.

A Set only enforces the relation it is given; it does not decide on behalf of the business logic which spellings should be merged.

## 3. Contracts of add, contains, remove, and size

### 3.1. add returns whether the set changed

For a Set that supports addition and a valid element:

| State before calling add(e) | State after | Return value |
| --- | --- | --- |
| No element equal to e | e is added | true |
| Already has an element equal to e | Set remains unchanged | false |

When `add` returns `false` because an equal element is already present, the contract requires the set to remain unchanged. It is not a "replace the old instance with the new one" or "update with all the latest fields" operation.

A new object created with `new` can be rejected as a duplicate. Having a different object identity does not grant a second presence if `equals` considers the two objects equal.

If the Set does not support modification or the element is invalid, `add` may throw an exception. Do not interpret `false` as a generic signal for all insertion errors.

### 3.2. contains checks presence by equality

`contains(query)` means: is there an element in the set that is equal to `query`? `query` does not need to be the exact reference that was previously added.

For example, after adding `new String("read")`, querying with another `String` that has the same content must still reflect the same presence if the contracts are properly upheld.

Do not infer from the `Set` interface name that `contains` always searches linearly or is always O(1). The lookup mechanism and cost depend on the implementation.

### 3.3. remove deletes presence

For a Set that supports removal:

- `remove(query)` returns `true` if an element equal to `query` was removed and the set changed.
- It returns `false` when there is no matching element to remove.
- It does not require `query` to be the same reference as the stored element.

After a successful removal, that value is no longer in the set. This differs from removing a single occurrence in a `List` that contains multiple equal elements.

### 3.4. size counts distinct elements currently present

`size` does not count how many times `add` was attempted. If `A` is added three times and `B` once under normal equality rules, the set has two distinct elements.

From a constructed Set, you cannot reliably recover how many times `A` appeared in the source. If counts are needed, use a counting model or retain the appropriate source data.

### 3.5. Things Set does not define

The `Set` interface does not provide positional indexing like `List.get(i)`. Nor does it inherently imply:

- The first element by insertion time.
- Elements sorted by value.
- Automatically updating an existing object when adding an equal one.
- That all modification operations are supported.
- That every element type, `null`, or wrong-type query is accepted.
- Thread safety for multiple threads.
- A fixed time complexity for `add`/`contains`/`remove`.

These properties must be obtained from the contract of the concrete implementation.

## 4. Runnable example: adding duplicates, checking presence, and removing

Save the program as `SetContractDemo.java`:

```java
import java.util.ArrayList;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

public class SetContractDemo {
    public static void main(String[] args) {
        Set<String> permissions = new LinkedHashSet<>();

        System.out.println("add read = " + permissions.add("read"));
        System.out.println("add write = " + permissions.add("write"));
        System.out.println("add equal read = "
                + permissions.add(new String("read")));
        System.out.println("values = " + permissions);
        System.out.println("size = " + permissions.size());
        System.out.println("contains equal read = "
                + permissions.contains(new String("read")));

        Set<String> other = new LinkedHashSet<>(List.of("write", "read"));
        System.out.println("equal sets in different orders = "
                + permissions.equals(other));
        System.out.println("equal set hash codes = "
                + (permissions.hashCode() == other.hashCode()));

        List<String> list = new ArrayList<>(List.of("read", "write"));
        System.out.println("set equals list = " + permissions.equals(list));

        System.out.println("addAll changed = "
                + permissions.addAll(List.of("write", "admin", "admin")));
        System.out.println("after addAll = " + permissions);
        System.out.println("remove missing = " + permissions.remove("missing"));
        System.out.println("remove read = " + permissions.remove("read"));
        System.out.println("final = " + permissions);
    }
}
```
Compile and run:

```shell
javac --release 17 SetContractDemo.java
java SetContractDemo
```
Output:

```text
add read = true
add write = true
add equal read = false
values = [read, write]
size = 2
contains equal read = true
equal sets in different orders = true
equal set hash codes = true
set equals list = false
addAll changed = true
after addAll = [read, write, admin]
remove missing = false
remove read = true
final = [write, admin]
```
Explanation:

1. `read` is added for the first time, so `true`.
2. `write` is a different value, so `true`.
3. A new `String` with content `read` is still equal to the existing value, so `add` returns `false`.
4. `size` is 2 even though three `add` attempts were made.
5. `contains` with a new `String` still recognizes the `read` value.
6. Batch-adding `write`, `admin`, `admin` only adds the new distinct value `admin`.
7. Removing `missing` does not change the set; removing `read` changes the set.

The example uses `LinkedHashSet` so that the printed order deterministically follows insertion order. Do not take the `[read, write]` output as a guarantee that every Set iterates in that order.

The lines about `equals` and `hashCode` of the two sets are explained next. They are the contract of the **set object itself**, which is distinct from the `equals`/`hashCode` of each element inside.

## 5. Two Sets are equal by membership, not iteration order

### 5.1. The Set.equals contract

Two Sets that adhere to the relevant contracts are equal when:

1. The other object is also a Set.
2. Both sets have the same size.
3. They contain the same elements under the presence relation consistent with the general contract.

Therefore, a set containing `read` and `write` equals a set containing `write` and `read`. Insertion or iteration order does not participate in this definition.

A `List` with the same values is not equal to a Set. A List also carries ordering and occurrence-count semantics; a Set does not represent the same kind of collection value.

This contract allows different Set implementations to compare values with one another when they use consistent equality rules.

### 5.2. The Set.hashCode contract

The hash code of a Set is defined as the sum of the hash codes of its elements, where `null` contributes 0. The addition uses Java integer arithmetic.

The order of addition does not change the result. Therefore, changing iteration order must not cause two equal sets to have different hash codes.

The required relationship is:

```text
setA.equals(setB) == true
=> setA.hashCode() == setB.hashCode()
```
The converse is not true. Two different sets can have the same hash code. A hash code is not a unique fingerprint of a set's contents and is not proof that two sets are equal.

This definition also serves as a reminder that modifying the contents of a Set can change the `hashCode` of that Set itself. If you place a mutable Set into an external hash structure as an element or key, you must account for the risk of mutating the value used for identity.

A Set also must not contain itself as an element, as noted in the Set contract. Do not use self-referential structures to try to "trick" `equals` or `hashCode` and treat the result as valid usage.

## 6. Element equals and hashCode must cooperate properly

### 6.1. equals must satisfy the properties of an equivalence relation

When defining `equals` yourself, you must uphold the requirements in [Java 17 Object.equals and Object.hashCode](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/Object.html):

- Reflexive: an object is equal to itself.
- Symmetric: if `a` equals `b`, then `b` must equal `a`.
- Transitive: if `a` equals `b` and `b` equals `c`, then `a` equals `c`.
- Consistent as long as the relevant data does not change.
- A non-null object is not equal to `null`.

If you violate these properties, adding the same data in different orders can lead to behavior that no longer forms a reliable set model.

### 6.2. Equal objects must have the same hashCode

For hash-based structures like `HashSet` or `LinkedHashSet`:

```text
a.equals(b) == true
=> a.hashCode() == b.hashCode()
```
Having the same hash code does not require `equals` to be `true`. Two different elements can land in the same lookup bucket and still be distinguished by the equality relation.

If you override `equals` while keeping an incompatible `hashCode`, a hash structure may route two equal elements to different locations. Do not blame that symptom on "`HashSet` failing to deduplicate"; the element type broke the precondition the structure relies on.

Conversely, overriding only `hashCode` without a proper `equals` does not establish business uniqueness either. A hash code does not replace the equality relation.

### 6.3. Do not bake the wrong uniqueness criteria into the entire data type

One business flow might require uniqueness by `id`, while another needs to distinguish each `id` + `name` + `timestamp` snapshot. You should not arbitrarily change the `equals` of a type used across the entire program just to solve one local filtering step.

One option is to separate the key used for identification: a `Set<String>` of IDs or an immutable key type. If you need to associate an `id` with the latest record, a `Map` from `id` to record usually expresses that goal much more clearly than a Set, which only tracks presence.

Equality is a modeling decision, not a trick to make an example's `size` smaller.

## 7. Runnable example: same id may or may not be a duplicate, depending on the model

Save to `SetBusinessEqualityDemo.java`:

```java
import java.util.LinkedHashSet;
import java.util.Objects;
import java.util.Set;

public class SetBusinessEqualityDemo {
    record UserSnapshot(String id, String displayName) {}

    static final class Member {
        private final String id;
        private String displayName;

        Member(String id, String displayName) {
            this.id = Objects.requireNonNull(id, "id");
            this.displayName = Objects.requireNonNull(displayName, "displayName");
        }

        @Override
        public boolean equals(Object other) {
            return other instanceof Member member && id.equals(member.id);
        }

        @Override
        public int hashCode() {
            return id.hashCode();
        }
    }

    public static void main(String[] args) {
        Set<UserSnapshot> snapshots = new LinkedHashSet<>();
        snapshots.add(new UserSnapshot("U1", "Lan"));
        snapshots.add(new UserSnapshot("U1", "Linh"));
        System.out.println("record values with same id = " + snapshots.size());

        Member first = new Member("U1", "Lan");
        Member incoming = new Member("U1", "Linh");
        Set<Member> members = new LinkedHashSet<>();

        System.out.println("add first member = " + members.add(first));
        System.out.println("add equal incoming = " + members.add(incoming));
        System.out.println("member count = " + members.size());

        Member retained = members.iterator().next();
        System.out.println("retained the first reference = " + (retained == first));
        System.out.println("retained display name = " + retained.displayName);

        first.displayName = "Lan updated";
        System.out.println("contains same id after rename = "
                + members.contains(new Member("U1", "ignored")));
        System.out.println("display name after rename = "
                + members.iterator().next().displayName);
    }
}
```
Compile and run:

```shell
javac --release 17 SetBusinessEqualityDemo.java
java SetBusinessEqualityDemo
```
Output:

```text
record values with same id = 2
add first member = true
add equal incoming = false
member count = 1
retained the first reference = true
retained display name = Lan
contains same id after rename = true
display name after rename = Lan updated
```
There are two distinct models here:

- `UserSnapshot` is a record with `id` and `displayName`. Two snapshots with the same `id` but different names are two different record values in this example, so both are kept.
- `Member` has `equals`/`hashCode` based on `id`. Two `Member`s with the same `U1` are equal, so adding `incoming` returns `false`.

An easily missed detail: `incoming` with the name `Linh` does not replace the first `Member` named `Lan`. After the duplicate add, the retained reference is still `first`.

If the goal is to keep the latest record by `id`, you need an explicit update policy. `Set.add` does not perform that data replacement.

In the `Member` class:

- `id` is a non-null `String`, kept stable, and is the component used in `equals`/`hashCode`.
- `displayName` does not participate in identity.
- Changing `displayName` in the example does not alter `Member`'s presence rule.

This is an intentional example showing that "mutable element" does not mean every change breaks a Set. What matters is **whether the change affects `equals`, `hashCode`, or the ordering rule the structure depends on**.

Do not apply this `Member` design blindly to every entity type. Choose equality criteria that fit the lifecycle and usage scenarios of the actual data type.

## 8. Do not mutate identifying data while an element is in the set

### 8.1. Why can an object still exist in the set yet become hard to find?

A `HashSet` places an element based on its hash information at insertion time. If the data used to compute `hashCode` changes, a later lookup may follow a different path from where the element was placed.

With `TreeSet`, changing a field used for comparison can make the element's current position in the tree violate the ordering.

The Set contract warns that behavior is undefined if an element's value is changed in a way that affects `equals` while it is in the set. Specific implementations also depend on `hashCode` or the comparator accordingly.

Do not write code relying on a fixed outcome like "if you mutate the key, `contains` will definitely return `false`" or "`remove` will definitely still clean it up." Behavior after violating a precondition is not a guarantee to build upon.

### 8.2. final does not automatically make all contents immutable

A `final` field prevents its reference from being reassigned, but the referenced object itself may still be mutable. If `hashCode` or `equals` reads that mutable content, the identifying data can still change.

You must look at the values that actually participate in identity, not just the `final` keyword on a variable.

### 8.3. Safer ways to structure it

- Prefer stable or immutable value keys.
- If an identifying value must change, treat it as a presence change: remove the old value while it is still valid, then add the new value according to an explicit policy.
- Check the result of adding the new value because it might already exist in the set.
- If mutating a mutable object directly, remove it from the structure before modifying the identifying part; do not mutate first and assume `remove` will restore everything.
- If data has already been corrupted, fix the model and recover from trustworthy source data; do not treat a `contains`/`remove` trick as a guaranteed safeguard.

A Set does not deep-copy elements to protect them from external changes. Another variable holding the same reference can mutate the object, so ownership and mutability are also part of the design.

## 9. TreeSet and the requirement for comparator consistency with equals

### 9.1. Comparing as 0 is decisive in TreeSet

`TreeSet` uses natural ordering or a `Comparator` to identify elements at their positions in the tree. Two values that compare as `0` are treated by `TreeSet` as the same element.

To properly implement the general `equals`-based Set contract, the comparison rule must be consistent with `equals`:

```text
compare(a, b) == 0
must correspond to
a.equals(b) == true
over the element domain in use.
```
If you compare `String`s only by length, `cat` and `dog` have the same length so the comparator returns `0`, yet `String.equals` returns `false`. `TreeSet` still has well-defined behavior under that comparator, but it no longer fully adheres to the general Set contract.

This is a pitfall when designing comparison rules, not a new license saying "a Set arbitrarily decides what equality means" without regard for the contract.

The [Java 17 TreeSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/TreeSet.html) documentation clearly states the consistency requirement and the consequences when an ordering is inconsistent with `equals`.

### 9.2. Runnable example of inconsistency

Save to `TreeSetEqualityPitfallDemo.java`:

```java
import java.util.Comparator;
import java.util.HashSet;
import java.util.Set;
import java.util.TreeSet;

public class TreeSetEqualityPitfallDemo {
    public static void main(String[] args) {
        TreeSet<String> byLength = new TreeSet<>(
                Comparator.comparingInt(String::length));

        System.out.println("add cat = " + byLength.add("cat"));
        System.out.println("add dog = " + byLength.add("dog"));
        System.out.println("values by length = " + byLength);
        System.out.println("contains owl = " + byLength.contains("owl"));
        System.out.println("cat equals dog = " + "cat".equals("dog"));

        Set<String> ordinary = new HashSet<>(Set.of("dog"));
        System.out.println("byLength equals ordinary = " + byLength.equals(ordinary));
        System.out.println("ordinary equals byLength = " + ordinary.equals(byLength));

        Comparator<String> lengthThenText = Comparator
                .comparingInt(String::length)
                .thenComparing(Comparator.naturalOrder());
        TreeSet<String> consistent = new TreeSet<>(lengthThenText);
        consistent.add("cat");
        consistent.add("dog");
        System.out.println("consistent values = " + consistent);
        System.out.println("consistent contains owl = " + consistent.contains("owl"));
    }
}
```
Compile and run:

```shell
javac --release 17 TreeSetEqualityPitfallDemo.java
java TreeSetEqualityPitfallDemo
```
Output:

```text
add cat = true
add dog = false
values by length = [cat]
contains owl = true
cat equals dog = false
byLength equals ordinary = true
ordinary equals byLength = false
consistent values = [cat, dog]
consistent contains owl = false
```
In the `byLength` section:

- `dog` is not added after `cat` because the comparator returns `0`.
- `contains("owl")` returns `true` because `owl` is also three characters long, even though the stored element is `cat`.
- Compared against a `HashSet` containing `dog`, `equals` can return different results in the two directions as shown.

This asymmetry violates the standard `equals` contract. It illustrates the risk of letting a `TreeSet` with an inconsistent comparator interact as a general `Set`.

In the `consistent` section, the comparison rule is length followed by string content. For `String`, comparing as `0` under this rule corresponds to identical content; `cat` and `dog` are kept separately, and `owl` is not reported as present merely for having the same length.

If the actual goal is only a set of distinct lengths, using a `Set<Integer>` of lengths may express the requirement more clearly. If the goal is to keep distinct strings sorted by length, you also need a tie-breaker when lengths are equal.

Do not add an arbitrary tie-breaker that makes two `equals` values compare non-zero. Consistency must be verified against both the equality model and the ordering model.

## 10. Uniqueness, ordering, mutability, and null are separate properties

### 10.1. Unique does not mean unordered

The general Set interface does not mandate a single iteration order. A concrete implementation may provide additional guarantees.

| Creation or implementation | Iteration order to expect | Mutability and null |
| --- | --- | --- |
| HashSet | No guaranteed iteration order | Normally mutable; allows one null |
| LinkedHashSet | Insertion order guaranteed by class contract | Normally mutable; allows one null |
| TreeSet | Natural order or comparator order | Mutable; natural order rejects null, custom comparator must support it if null is used |
| Set.of / Set.copyOf | Do not rely on any guaranteed iteration order | Structurally unmodifiable; rejects null |

[Java 17 LinkedHashSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashSet.html) guarantees insertion order. That does not make order a component of `Set.equals`.

Do not rely on a single iteration of `HashSet` or `Set.of` to determine an output format that needs to be stable. If ordering is required, choose a representation with the corresponding contract.

### 10.2. Unique does not mean every operation is O(1)

`Set` is a behavioral interface. `HashSet` has hash-based characteristics; `TreeSet` has ordered-structure characteristics.

Even for hash-based structures, actual cost depends on `hashCode`, `equals`, and hash distribution. Do not turn the slogan "Set lookup is fast" into a complexity guarantee for every Set.

This lesson focuses on contracts. Choosing an implementation for performance requires checking the class documentation and actual access patterns.

### 10.3. Structurally unmodifiable differs from deeply immutable

A Set that disallows `add`/`remove` can still contain mutable objects. Changing a field on an element can alter the data read from it; if that field participates in identity, it can also break the structure's assumptions.

Therefore, "unmodifiable Set" does not mean everything reachable through its elements is immutable.

Similarly, a collection copy is not automatically a deep copy of its elements. You must be clear about which layer is being protected.

## 11. Set.of differs from Set.copyOf when the input has duplicates

### 11.1. Set.of from arguments

`Set.of` creates an unmodifiable set and rejects duplicate elements at creation time with `IllegalArgumentException`. It also rejects `null`.

This differs from calling `add` on a mutable `HashSet`: a normal duplicate add returns `false` instead of throwing an error.

Do not assume a universal rule that "duplicates are always silently ignored" for every way of creating a Set.

### 11.2. Set.copyOf from a Collection

`Set.copyOf` takes a source collection and creates an unmodifiable Set of distinct values. If the source contains equal elements, an arbitrary representative from the duplicate group is retained by contract; do not rely on always keeping the first or the last one.

If the source is structurally modified later, the returned Set does not reflect those changes. However, this does not create a deep copy of the elements.

`Set.copyOf` may reuse a suitable unmodifiable Set. Do not use new vs. old object identity as the meaning of `copyOf`.

### 11.3. Runnable example

Save to `SetFactoriesDemo.java`:

```java
import java.util.ArrayList;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

public class SetFactoriesDemo {
    public static void main(String[] args) {
        try {
            Set.of("A", "A");
        } catch (IllegalArgumentException ex) {
            System.out.println("Set.of duplicate = "
                    + ex.getClass().getSimpleName());
        }

        List<String> source = new ArrayList<>(List.of("A", "A", "B"));
        Set<String> snapshot = Set.copyOf(source);
        System.out.println("Set.copyOf distinct size = " + snapshot.size());

        source.add("C");
        System.out.println("copy contains later C = " + snapshot.contains("C"));

        try {
            snapshot.add("C");
        } catch (UnsupportedOperationException ex) {
            System.out.println("copy add = " + ex.getClass().getSimpleName());
        }

        try {
            Set.of("A", null);
        } catch (NullPointerException ex) {
            System.out.println("Set.of null = " + ex.getClass().getSimpleName());
        }

        Set<String> nullable = new LinkedHashSet<>();
        System.out.println("add first null = " + nullable.add(null));
        System.out.println("add second null = " + nullable.add(null));
        System.out.println("nullable size = " + nullable.size());
    }
}
```
Compile and run:

```shell
javac --release 17 SetFactoriesDemo.java
java SetFactoriesDemo
```
Output:

```text
Set.of duplicate = IllegalArgumentException
Set.copyOf distinct size = 2
copy contains later C = false
copy add = UnsupportedOperationException
Set.of null = NullPointerException
add first null = true
add second null = false
nullable size = 1
```
Explanation:

- `Set.of` receives `A` twice, so it throws `IllegalArgumentException`.
- `Set.copyOf` from the List `A, A, B` creates a set with two distinct values.
- Adding `C` to the source List afterward does not make `C` appear in the returned Set.
- Attempting `add` on the unmodifiable Set throws `UnsupportedOperationException`.
- `Set.of` rejects `null`.
- `LinkedHashSet` allows adding `null` the first time and does not create a second presence.

The program does not print the order of `Set.copyOf` because there is no ordering guarantee you are allowed to depend on. Nor does it test "first vs. last representative" among equal elements, because the contract does not guarantee that choice.

## 12. What do set operations modify?

Bulk operations often correspond to mathematical ideas, but they are method calls with mutating contracts.

Assuming `A` and `B` use consistent presence rules:

| Method on A | Resulting meaning for A |
| --- | --- |
| A.addAll(B) | Union: adds values from B not already in A |
| A.retainAll(B) | Intersection: keeps values present in both A and B |
| A.removeAll(B) | Difference: removes from A values that are in B |
| A.containsAll(B) | Only asks whether B is a subset of A, without modifying A |

`addAll`, `retainAll`, and `removeAll` modify the receiver set if supported. They do not by default create a new result set.

If you want to keep `A` intact, create a mutable copy and operate on that copy. Choose a copy approach that preserves ordering or comparator requirements if those are part of your goal.

`containsAll` does not count occurrences in the source. A set containing `A` still satisfies `containsAll` for a `List` containing `A, A`; it only checks presence of the queried values.

Bulk modification operations are not universal transactions across every Set either. If an element is invalid or an internal call fails, do not assume all prior modifications are rolled back. If the domain requires all-or-nothing, design an appropriate mechanism.

Do not confuse set union with sequence concatenation: union eliminates repetition under the presence relation, whereas concatenating two Lists can preserve all occurrences.

## 13. Applying Set properly in processing flows

### 13.1. Use the result of add to detect first occurrence

In a sequential pass, you can use:

```java
// Illustrative snippet: seen is a mutable Set<String>,
// and id has already been normalized according to the program's requirements.
if (seen.add(id)) {
    processFirstOccurrence(id);
}
```
This expresses "only process when `id` appears for the first time in the active set." It avoids splitting into two calls (`contains` then `add`) in a single thread.

However, a Set does not automatically turn `processFirstOccurrence` into a transaction. If the handler fails after `id` has been added, retries will need an explicit policy. Nor should you infer from a single `add` call that a regular `HashSet` is safe for concurrent access from multiple threads.

An in-memory presence set in a single process is not by itself a database uniqueness constraint or a cross-system deduplication mechanism.

### 13.2. Decide whether to ignore duplicates or report invalid data

If the source is not allowed to contain duplicate codes, building a Set and ignoring `false` return values can hide data errors.

You can check the return value of `add` to report duplicates as required. That is a different business policy from "deduplicate and continue."

If you want frequency statistics, do not discard duplicates before counting. If you want to keep the latest entry by key, do not expect a `false` from `add` to update the old element.

### 13.3. Test element classes with a newly created equivalent object

A meaningful test suite should include:

- Two objects with different references that are equal according to the model.
- Two objects that must be distinct even if they share some fields.
- Symmetric `equals` and consistent `hashCode` for equal values.
- Duplicate `add` returning `false` and leaving the retained object unchanged when that is the requirement.
- `contains`/`remove` using a newly created equivalent object.
- `null` policy and unsupported operations.
- Comparator/`equals` consistency if `TreeSet` is used.

Testing only `add` followed by `contains` on the exact same reference can miss `equals`/`hashCode` bugs. Merely checking `size` after a single example does not prove the uniqueness criteria match the business domain either.

## 14. Common misconceptions

| Misconception | Correct understanding |
| --- | --- |
| "Set removes objects with the same memory address" | The general contract is based on equality; two different references can still be duplicates |
| "Having the same id means Set removes it automatically" | You must choose an appropriate `equals`/`hashCode` model or key |
| "Same hashCode means duplicate" | Hash codes can collide; they do not replace `equals` |
| "Overriding equals is enough for HashSet" | You must also uphold the `hashCode` contract |
| "A duplicate add overwrites old data with new data" | Under the normal `add` contract, the set is unchanged and returns `false` |
| "Set has no order, so LinkedHashSet isn't a real Set" | Uniqueness and ordering are two independent properties |
| "Two sets that iterate in different orders are not equal" | `Set.equals` checks membership, not order |
| "If a Set is unmodifiable, its elements cannot be modified" | Structural unmodifiability does not create deep immutability |
| "Set.of and Set.copyOf handle duplicate inputs the same way" | `Set.of` rejects duplicate arguments; `Set.copyOf` takes distinct values from a collection |
| "TreeSet only changes sorting, not identity" | `compare` returning 0 determines presence; it must be consistent with `equals` to keep the general contract |
| "Mutating a key after adding and then calling remove will always clean it up" | Once identity assumptions are broken, there is no such guarantee |
| "Set automatically solves all duplication issues across threads or systems" | You need appropriate concurrency, data scope, and transaction mechanisms |

## 15. Practice identifying the right contract

### Exercise 1: Two Strings with different references

Add two `new String("A")` instances to a regular `HashSet`. Why is there only one distinct value?

Because `String.equals` compares content, the two objects are equal and have consistent `hashCode` values. Different object identities do not make them two different set values.

### Exercise 2: Two records with the same id but different names

A record has two components: `id` and `name`. Add two values with the same `id` but different names. Is `size` guaranteed to be 1?

No. A record's generated equality examines all record components. To enforce uniqueness by `id`, you need an appropriate key model or equality relation; it is not inferred from a field being named `id`.

### Exercise 3: Does a false add update?

The set already contains `Member` `U1` named `Lan`. Add `Member` `U1` named `Linh` under an `id`-based equality model.

`add` returns `false` and the set does not replace the old element. If the new name is needed, a separate update policy must be implemented. Checking which object is actually retained matters more than just seeing `size` remain 1.

### Exercise 4: Order and equality

One `LinkedHashSet` adds `A` then `B`; another adds `B` then `A`. Assuming element relations are valid, are the two sets equal?

Yes. They have the same members. Iteration order may differ, but `Set.equals` and `Set.hashCode` must still match.

### Exercise 5: Matching hash codes

If two Sets have the same `hashCode`, are they guaranteed to be equal?

No. The contract only requires equal sets to have the same `hashCode`; collisions are not forbidden. Use `equals` to compare set values.

### Exercise 6: Length rule in TreeSet

A `TreeSet<String>` comparing only by length already contains `cat`. Why might adding `dog` fail to increase `size`, and what issue does this raise?

The comparator treats two strings of the same length as equivalent in the tree. However, `String.equals` does not consider them equal, so that rule does not fully satisfy the general Set contract. You need to adjust how the requirement is modeled or fix the comparison rule.

### Exercise 7: An unmodifiable set containing a Member whose name can change

Does being unable to call `add`/`remove` guarantee that the `Member`'s name stays unchanged?

No. If another reference holds the same `Member` and mutates its name, the data read from the set can change. If a field participating in identity is mutated, it also risks breaking the structure's assumptions.

### Exercise 8: How do deduplicating and duplicate checking differ?

Silently dropping all duplicate elements is one way to process data. Reporting an error when a duplicate is seen is a different requirement. Decide the policy first, then use the return value of `add` or an appropriate structure to implement it.

A clear Set design must specify **the equality criteria, presence semantics, duplicate-handling policy, mutability, ordering, and lifecycle of identifying data**. Only when these parts are right does the "no duplicates" property accurately reflect what the program intends to model.
