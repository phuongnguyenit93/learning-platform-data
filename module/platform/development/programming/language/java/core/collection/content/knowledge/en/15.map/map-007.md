# Conditional putIfAbsent, replace, and remove

## 1. Writing data only when a condition still holds

A map holds the current state of work. A program wants to:

- Set an initial value if no usable value exists yet.
- Replace the value if the key already exists.
- Replace the value if it still matches what was read.
- Remove the mapping if the current value still belongs to the expected processing attempt.

Calling `put` or `remove(key)` directly does not express these conditions. The methods in this lesson build the condition into the update operation itself.

Two questions must be separated:

1. **What is the logical condition?** Is the key missing, is the key present, or does the current value equal the expected value?
2. **Are the check and the change atomic?** This depends on the contract of the map type, not on the method name alone.

This lesson uses `HashMap` to study states involving `null`, then uses `ConcurrentHashMap` to explain updates based on an expected value. The Java 17+ examples run standalone, without external libraries.

## 2. Four signatures and two return types

Condensed API signatures:

```java
V putIfAbsent(K key, V value);
V replace(K key, V value);
boolean replace(K key, V oldValue, V newValue);
boolean remove(Object key, Object value);
```

These are signatures for reference, not declarations of a standalone program.

| Method | Condition applied | Result |
| --- | --- | --- |
| `putIfAbsent(k, v)` | Key is absent or currently mapped to null | Previous value; may be null |
| `replace(k, v)` | Key exists | Previous value; may be null |
| `replace(k, expected, next)` | Key exists and current value equals expected | Boolean |
| `remove(k, expected)` | Key exists and current value equals expected | Boolean |

The most common point of confusion is that the first two rows return `V`, not `boolean`. The last two rows return whether the condition was met to perform the operation.

The foundational contract is in [Map Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Map.html). The null tables in the next section examine a modifiable map that supports null, such as `HashMap`.

## 3. putIfAbsent: keep the existing value if it is non-null

### 3.1. "Absent" here includes a null mapping

With a new candidate `"NEW"`:

| Prior state | Return value | New state |
| --- | --- | --- |
| No key k | `null` | `k → "NEW"` |
| Has `k → null` | `null` | `k → "NEW"` |
| Has `k → "OLD"` | `"OLD"` | Still `k → "OLD"` |

Therefore, `putIfAbsent` is not equivalent to "add only if `containsKey` is false" on a map that allows null.

If an existing value is non-null, the new candidate does not replace it. If the existing value is null, the candidate can fill that slot.

### 3.2. The result is the value before the operation, not always the current value

Illustrative snippet:

```java
// map is a modifiable Map<String, String> initially missing "task".
String previous = map.putIfAbsent("task", "NEW");
```

After a successful insertion, `previous` is `null`, while `map.get("task")` is `NEW`. Do not read `previous` as "the current value after initialization".

A common pattern when null is not stored is to use the old value if present, or use the newly accepted candidate. However, if the map allows null, a `null` result does not distinguish between a previously missing key and an existing null mapping.

### 3.3. A null candidate also has its own meaning

`HashMap` allows:

```java
// Illustrative snippet:
map.putIfAbsent("task", null);
```

If `task` did not exist, a mapping `task → null` can appear. If `task` already had a non-null value, that value is kept. If `task` was already null, the logical state may remain null.

Thus, `putIfAbsent` returning `null` does not by itself prove that a useful value was created or that the logical content changed.

The null policy of `HashMap` can be checked in [HashMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashMap.html).

## 4. Two-argument replace: replace only when the key exists

With `replace(k, "NEW")`:

| Prior state | Return value | New state |
| --- | --- | --- |
| No key k | `null` | Still no k |
| Has `k → null` | `null` | `k → "NEW"` |
| Has `k → "OLD"` | `"OLD"` | `k → "NEW"` |

The second row is an important difference from the assumption that "replace only replaces a non-null value". The condition here is the existence of the key.

Compared to `put`:

```text
put(k, v)      may create a new key or replace an existing key
replace(k, v)  only replaces the mapping of an existing key
```

Because both a missing key and replacing a null value can return `null`, do not use a `null` result from two-argument `replace` alone to conclude "replacement failed".

If you want to confirm that a replacement happened from a specific value, the three-argument variant provides a clearer condition and boolean result.

## 5. Three-argument replace: replace if the current value still matches

### 5.1. The condition includes both key presence and value equality

```java
boolean changed = map.replace("task", "NEW", "RUNNING");
```

This is an illustrative snippet inside a method. It does not mean "find the value NEW somewhere and replace it". It targets the exact key `task`.

| Prior state | `replace(k, "NEW", "RUNNING")` | New state |
| --- | --- | --- |
| No k | `false` | No k |
| Has `k → "NEW"` | `true` | `k → "RUNNING"` |
| Has `k → "DONE"` | `false` | Still `k → "DONE"` |
| Has `k → null` | `false` | Still `k → null` |

The `expected` value is a guard condition based on what the program expects. If another place has already changed `NEW` to `DONE`, an operation expecting `NEW` should not overwrite `DONE`.

### 5.2. Comparison uses equals, not necessarily reference identity

In the standard maps used in this lesson, the condition uses value equality according to the `Map` contract. Two records with different references but equal components can still match.

If the value class lacks a business-meaningful `equals`, a newly created object with identical-looking fields may fail to match. Conversely, if `equals` ignores a field that business logic needs to check, the operation may accept a broader state than intended.

Do not assume "conditional" means comparing whichever fields the caller happens to have in mind. The actual condition depends on the value's definition of equality.

### 5.3. Boolean true does not always mean the data changed

If the current mapping is `k → "A"`, the call:

```java
map.replace(k, "A", "A");
```

can return `true` because the condition matched and the replacement was accepted. The logical value before and after remains `A`.

Therefore, the accurate phrasing is "the conditional replace operation succeeded", not always "the content changed" or "the size changed". `replace` does not add a second key.

## 6. Two-argument remove: remove only the expected mapping

Compare the two variants:

```java
V old = map.remove(key);                    // remove by key, return previous value
boolean removed = map.remove(key, expected); // remove if value still matches
```

These are illustrative lines in a context where types `K`, `V` and the variables are already defined.

With `remove(k, "A")`:

| Prior state | Result | New state |
| --- | --- | --- |
| No k | `false` | No k |
| Has `k → "A"` | `true` | No longer has k |
| Has `k → "B"` | `false` | Keeps B |
| Has `k → null` | `false` | Keeps null mapping |

For example, a cache may want to remove data only if it is still the version that was observed. Removing by key does not check the version; `remove` with `expected` expresses that condition.

### Expected null does not make an absent key match

With `HashMap` supporting null:

```text
no k        → remove(k, null) is false
has k → null → remove(k, null) is true and removes k
```

A common mistake when writing this manually is:

```java
// Check missing an existence condition:
if (Objects.equals(map.get(key), expected)) {
    map.remove(key);
}
```

If `expected` is `null` and `key` is absent, `Objects.equals` can still return `true`. The code conflates two different states. In addition, checking then removing is a multi-step sequence, with no concurrency guarantee from that form alone.

Using the method with the right contract is clearer than hand-rolling an incomplete check.

## 7. Runnable program: conditions, null, and return values

Save as **ConditionalMapMethodsDemo.java**:

```java
import java.util.HashMap;
import java.util.Map;

public class ConditionalMapMethodsDemo {
    public static void main(String[] args) {
        Map<String, String> map = new HashMap<>();
        map.put("fixed", "A");
        map.put("null-slot", null);

        System.out.println("putIfAbsent new old: " + map.putIfAbsent("new", "N"));
        System.out.println("new current: " + map.get("new"));
        System.out.println("putIfAbsent fixed old: " + map.putIfAbsent("fixed", "B"));
        System.out.println("fixed after putIfAbsent: " + map.get("fixed"));
        System.out.println("putIfAbsent null-slot old: "
                + map.putIfAbsent("null-slot", "filled"));
        System.out.println("null-slot current: " + map.get("null-slot"));
        System.out.println("putIfAbsent null candidate old: "
                + map.putIfAbsent("still-null", null));
        System.out.println("still-null exists: " + map.containsKey("still-null"));

        System.out.println("replace missing old: " + map.replace("missing", "M"));
        System.out.println("missing exists: " + map.containsKey("missing"));
        map.put("null-replace", null);
        System.out.println("replace mapped-null old: " + map.replace("null-replace", "R"));
        System.out.println("null-replace current: " + map.get("null-replace"));
        System.out.println("replace fixed old: " + map.replace("fixed", "B"));

        System.out.println("replace stale A: " + map.replace("fixed", "A", "C"));
        System.out.println("replace expected B: " + map.replace("fixed", "B", "C"));
        System.out.println("replace same C: " + map.replace("fixed", "C", "C"));
        map.put("null-expected", null);
        System.out.println("replace expected null: "
                + map.replace("null-expected", null, "V"));
        System.out.println("replace absent expected null: "
                + map.replace("absent", null, "V"));

        map.put("null-remove", null);
        System.out.println("remove absent expected null: " + map.remove("absent", null));
        System.out.println("remove mapped null: " + map.remove("null-remove", null));
        System.out.println("null-remove exists: " + map.containsKey("null-remove"));
        System.out.println("remove fixed wrong value: " + map.remove("fixed", "X"));
        System.out.println("fixed still current: " + map.get("fixed"));
        System.out.println("remove fixed expected C: " + map.remove("fixed", "C"));
        System.out.println("fixed exists at end: " + map.containsKey("fixed"));
    }
}
```

Compile and run:

```shell
javac --release 17 -encoding UTF-8 ConditionalMapMethodsDemo.java
java ConditionalMapMethodsDemo
```

Exact stdout:

```text
putIfAbsent new old: null
new current: N
putIfAbsent fixed old: A
fixed after putIfAbsent: A
putIfAbsent null-slot old: null
null-slot current: filled
putIfAbsent null candidate old: null
still-null exists: true
replace missing old: null
missing exists: false
replace mapped-null old: null
null-replace current: R
replace fixed old: A
replace stale A: false
replace expected B: true
replace same C: true
replace expected null: true
replace absent expected null: false
remove absent expected null: false
remove mapped null: true
null-remove exists: false
remove fixed wrong value: false
fixed still current: C
remove fixed expected C: true
fixed exists at end: false
```

The states are set up clearly to read each case's result:

- `fixed` initially has `A`, so `putIfAbsent` does not replace it with `B`.
- `null-slot` is filled with `filled` even though the key already existed.
- `missing` is not created by two-argument `replace`.
- `null-replace` has the key, so `replace` replaces `null` with `R`, even though the returned previous value is still `null`.
- `fixed` then becomes `B`; expected `A` is rejected, while expected `B` is accepted to transition to `C`.
- Replacing `C` with `C` still returns `true`.
- Expected `null` only matches an existing null mapping, not an absent key.
- Removing with the wrong value keeps the data; removing with the correct value `C` deletes `fixed`.

The programs in this lesson were compiled with `--release 17` and run on OpenJDK 24.0.2. That flag targets the Java 17 language/API level and emits corresponding bytecode; the JVM running the examples is still the version noted.

## 8. Conditional does not automatically mean atomic on every Map

### 8.1. Logical conditions and synchronization are two separate contracts

Writing:

```java
// Illustrates multiple separate steps:
if (!map.containsKey(key)) {
    map.put(key, candidate);
}
```

leaves a gap between the check and the write. If another place writes during that gap, the earlier decision may already be stale.

Calling a method named `putIfAbsent` expresses intent better, but you cannot conclude that every `Map` object provides atomic operations. Default implementations on `Map` do not guarantee synchronization or atomicity for these methods.

`HashMap` does not become thread-safe simply because you call a default method. The `HashMap` examples in this lesson run single-threaded.

### 8.2. ConcurrentMap has a stronger contract

`ConcurrentMap` specifies that operations such as `putIfAbsent`, `replace`, and expected-value `remove` have corresponding atomic check-and-update behavior. `ConcurrentHashMap` is a suitable implementation class for using those contracts.

For example, with `ConcurrentHashMap`, three-argument `replace` does not allow another update to interleave between its match check and its replacement in a way that violates the condition.

See [ConcurrentMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ConcurrentMap.html) and [ConcurrentHashMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html).

A variable's declared type might be `Map` while the actual object is still a `ConcurrentHashMap`. Rely on the contract of the implementation being used, and choose a sufficiently clear declared type when the code requires concurrency capabilities.

### 8.3. One atomic operation does not make an entire workflow transactional

Two `replace` calls on two keys do not automatically become one atomic change across both. Changing state in a map and then sending a network request also do not automatically belong to the same transaction.

A `true` result only confirms that the specific operation was accepted under its condition. Immediately afterward, another valid operation can continue modifying the data.

If constraints across multiple keys or multiple systems are needed, an appropriate workflow-level mechanism must be designed. Do not stretch the guarantee of a single map operation into a global guarantee.

## 9. Runnable program: avoiding updates from stale reads

Save as **ExpectedValueUpdatesDemo.java**:

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;

public class ExpectedValueUpdatesDemo {
    record TaskState(String phase, long version) {}

    public static void main(String[] args) {
        ConcurrentMap<String, TaskState> states = new ConcurrentHashMap<>();
        states.putIfAbsent("job-7", new TaskState("NEW", 1));

        TaskState seenByA = states.get("job-7");
        TaskState seenByB = new TaskState("NEW", 1);
        System.out.println("same expected reference: " + (seenByA == seenByB));
        System.out.println("equal expected state: " + seenByA.equals(seenByB));

        TaskState running = new TaskState("RUNNING", 2);
        System.out.println("A starts job: "
                + states.replace("job-7", seenByA, running));
        System.out.println("B cancels stale state: "
                + states.replace("job-7", seenByB, new TaskState("CANCELLED", 2)));
        System.out.println("B removes stale state: " + states.remove("job-7", seenByB));
        System.out.println("state after stale attempts: " + states.get("job-7"));

        TaskState newAgain = new TaskState("NEW", 3);
        System.out.println("return to NEW with new version: "
                + states.replace("job-7", running, newAgain));
        System.out.println("old NEW version updates: "
                + states.replace("job-7", seenByA, new TaskState("FAILED", 4)));
        System.out.println("current versioned state: " + states.get("job-7"));
        System.out.println("remove current version: " + states.remove("job-7", newAgain));
        System.out.println("job remains: " + states.containsKey("job-7"));

        ConcurrentMap<String, String> plain = new ConcurrentHashMap<>();
        plain.put("job", "READY");
        String oldRead = plain.get("job");
        plain.replace("job", "READY", "BUSY");
        plain.replace("job", "BUSY", "READY");
        System.out.println("old plain value accepted again: "
                + plain.replace("job", oldRead, "CANCELLED"));
        System.out.println("plain final state: " + plain.get("job"));
    }
}
```

Run commands:

```shell
javac --release 17 -encoding UTF-8 ExpectedValueUpdatesDemo.java
java ExpectedValueUpdatesDemo
```

Exact stdout:

```text
same expected reference: false
equal expected state: true
A starts job: true
B cancels stale state: false
B removes stale state: false
state after stale attempts: TaskState[phase=RUNNING, version=2]
return to NEW with new version: true
old NEW version updates: false
current versioned state: TaskState[phase=NEW, version=3]
remove current version: true
job remains: false
old plain value accepted again: true
plain final state: CANCELLED
```

The program runs sequentially so the steps produce deterministic output. It simulates two places holding expected views of the same state; it does not present this print order as the execution schedule of two concurrently running threads.

`seenByA` and `seenByB` have different references but are equal as records. A transitions `NEW` version 1 to `RUNNING` version 2. Afterward, B cannot cancel or remove based on the stale `NEW` version 1 state.

When the state returns to `NEW` but with version 3, the `NEW` version 1 snapshot still does not match. The `version` field participates in the record's `equals`, distinguishing two occurrences of a state with the same name.

The `plain` string example at the end has no version. The value goes from `READY` to `BUSY` and back to `READY`. An old read of `READY` matches the current value again, so the transition to `CANCELLED` succeeds. The operation only checks the current value; it does not track the history of having passed through `BUSY`.

## 10. Current equality does not automatically detect every change that occurred

### 10.1. Returning to the same value can still match

The situation where a value goes from A to B and back to A is often described as **ABA**. It shows that comparing only the current value is not enough to know that "nobody has changed it since the read".

Not every program needs to detect intermediate history. If the requirement is simply "cancel if it is currently READY", accepting `READY` after a cycle of transitions may be fine.

If the requirement is "update only the exact version I read", a suitable version identifier is needed in the condition.

### 10.2. Versions must be managed by the application

A `version` field does not increment automatically just because it is placed in a record or `ConcurrentHashMap`. Application code must issue new versions according to its policy.

Versions should also not be reused during a window when stale reads might still be used as conditions. If a key is deleted and recreated with the same version, an old snapshot can appear equal to the new one again.

The example uses versions 1, 2, 3 for illustration; it is not a complete versioning system for an entire data lifecycle.

### 10.3. Mutable values can prevent the expected value from being a snapshot

If a map holds a mutable object and the `expected` variable points to that same object, mutating the object in place also changes the content seen through `expected`. Subsequent comparisons are no longer like comparing against an immutable snapshot read earlier.

Prefer immutable values or a meaningful snapshot for versioned checks. The record in the example contains `String` and `long` to keep the compared state stable.

Even in `ConcurrentHashMap`, the atomicity of a map update does not automatically lock every field inside a payload object that multiple places mutate concurrently.

## 11. The new argument is still evaluated before the call

Example:

```java
Value old = map.putIfAbsent(key, createValue());
```

is an illustrative snippet with types and variables already defined. Java evaluates `createValue` before the method receives its arguments. An existing non-null value may be kept, yet the new candidate object has already been created.

The same applies to the expression producing `newValue` in `replace`. The condition may fail after the candidate has already been computed.

If creating the candidate is expensive and should only happen when absent, choose an appropriate computation API such as `computeIfAbsent` after reading its contract carefully. That is a different contract: null handling, write permissions, and concurrency behavior must be considered separately.

Do not put sending notifications or creating external resources inside a candidate expression and assume a `false` condition means that side effect never happened.

## 12. Nulls and mutability still depend on the map type

The null tables and first program use `HashMap`. They do not mean every `Map` accepts null keys, null new values, or null `expected` arguments in the same way.

`ConcurrentHashMap` does not store null keys or null values. For a valid key, calls like `putIfAbsent(k, null)`, `replace(k, null)`, `replace(k, null, v)`, and `replace(k, v, null)` throw `NullPointerException`. Do not carry the `HashMap` table directly over to this class.

Meanwhile, `remove(k, null)` with a valid key returns `false` because there is no null mapping to match. Read each method's contract carefully and distinguish an expected argument from a value to be written; do not infer a uniform parameter policy solely from the fact that the class does not store null.

An unmodifiable map can also throw `UnsupportedOperationException` when update operations are called. Do not rely on a condition that looks certain to be `false` as a safety mechanism for calling write methods on a read-only object.

A good preparation step before choosing an API is to determine: is it modifiable, are nulls allowed, what is the value's equality semantics, and what atomicity is required.

## 13. Choosing a method by intent

| Intent | Suitable method | What to read from the result |
| --- | --- | --- |
| Fill only when no non-null value exists | `putIfAbsent` | Previous value, not a boolean flag |
| Replace the value of an existing key | Two-argument `replace` | Previous value; null can be ambiguous |
| Replace the exact expected current value | Three-argument `replace` | `true`/`false` of the condition |
| Remove only while the expected value still matches | Two-argument `remove` | `true` when the matching mapping was removed |
| Write regardless of whether the key exists | `put` | May create or replace the mapping |
| Remove regardless of the current value | One-argument `remove` | Returns previous value, may be null |

Do not pick a method just because it is shorter than an `if` statement. Choose based on the business condition to preserve, then verify that the map type meets concurrency requirements.

For a map that allows null, if the business logic requires "add only when the key is completely absent, including preserving an existing null", `putIfAbsent` does not express that exact condition. In a single-threaded example you can check `containsKey` and `put`; with multiple threads, a synchronization design tailored to that specific condition is needed.

## 14. Common mistakes and how to check

| Mistake | Cause | Fix |
| --- | --- | --- |
| `putIfAbsent` overwrites a stored null | Assuming "absent" only means no key | Remember the condition includes a null mapping |
| Two-argument `replace` does not create data | Key does not exist | Use `put` if creating new keys is desired |
| Concluding failure because `replace` returned null | Previous value may have been null | Read the return type and state properly |
| Assigning `putIfAbsent` to a boolean | Confusing a method returning `V` | Keep the old value type or pick a boolean variant |
| `replace` returns true yet value looks unchanged | `old` and `new` are equal | `true` means the replacement condition was accepted |
| Thinking `remove(k, null)` removes absent keys too | Ignoring the existence condition | Distinguish a missing key from a null mapping |
| A new value with identical data fails to match `expected` | `equals` does not match the intended model | Check the value class's `equals` implementation |
| Calling on `HashMap` and expecting race protection | Inferring atomicity from method name alone | Choose a `ConcurrentMap` contract or proper synchronization |
| Stale read matches after value returns | Only comparing current value | Add a version if history must be distinguished |
| Expensive candidate created even when condition fails | Arguments are evaluated beforehand | Choose a lazy computation mechanism if appropriate |

## 15. Self-check exercises with solutions

### Exercise 1: Two kinds of "absent"

A `HashMap` has `A → null` and does not have `B`. Call `putIfAbsent(A, 1)` then `putIfAbsent(B, 2)`. What are the results and the data afterward?

**Solution:** both return `null`. Afterward `A → 1` and `B → 2`. A `null` result does not distinguish `A`, which already had a key, from `B`, which did not.

### Exercise 2: Two-argument replace

A `HashMap` has `A → null` and does not have `B`. Call `replace(A, 1)` and `replace(B, 2)`. Both return `null`; do they have the same effect?

**Solution:** no. `A` is replaced with `1` because the key exists. `B` remains absent. Because the return type is the previous value, both cases can return `null`.

### Exercise 3: Null condition

A `HashMap` has `A → null` and does not have `B`. What do `remove(A, null)` and `remove(B, null)` return?

**Solution:** the first returns `true` and removes `A`; the second returns `false`. Both key presence and value match are required.

### Exercise 4: Replacing with the same old value

A `Map` has `A → 5`. Does `replace(A, 5, 5)` returning `true` contradict the fact that size and value did not change?

**Solution:** no. The condition matched and the operation was accepted. `true` does not mean the logical value must differ from before.

### Exercise 5: Stale read

A reads state `NEW`, then B changes it to `DONE`. A calls `replace(key, NEW, RUNNING)`. What is the expected result of a valid conditional operation?

**Solution:** `false`, keeping `DONE`. If `put` were used directly, A could overwrite it without checking the state B updated.

### Exercise 6: Map or ConcurrentMap?

Is changing a `containsKey`/`put` sequence to `putIfAbsent` on a `HashMap` enough for multiple threads to update safely together?

**Solution:** no. `Map`/`HashMap` does not automatically provide atomic guarantees just by calling a conditional method. You must choose a map type or synchronization mechanism with the appropriate contract.

### Exercise 7: Value returning to a prior state

A value goes `READY → BUSY → READY`. Can an old read of `READY` match `replace` with expected `READY`?

**Solution:** yes. The check compares the current value and does not automatically detect history. If you need to distinguish the exact version, include a meaningful version in the compared value and manage it properly.

### Exercise 8: When is the candidate created?

The key already has a non-null value. Does `putIfAbsent(key, build())` guarantee that `build` will not run?

**Solution:** no. `build` is evaluated before the call. The method may keep the old value after the candidate has already been created.
