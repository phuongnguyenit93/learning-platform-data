# Traversing with entrySet, forEach, or Views

## 1. What Does Traversing a Map Mean?

A `Map<K, V>` organizes data into mappings: each key identifies at most one current value. For example, an inventory map might contain:

```text
"pen"      → 3
"notebook" → 2
"marker"   → 3
```

Depending on the task, we need to look at the same data in three ways:

- Only need item codes: traverse the keys.
- Only need the total quantity: traverse the values.
- Need to print “item code = quantity” or filter by both: traverse each key–value pair.

Java provides three corresponding **views** via `keySet()`, `values()`, and `entrySet()`. In addition, `Map.forEach` accepts an action that processes each key together with its value directly.

A view is not a snapshot copied at the time of the call. It is backed by the original map. This allows processing data directly on the existing structure, but it also means a removal through a view can remove data in the map. Understanding this relationship is just as important as being able to write the loop.

### Learning Objectives

You should be able to choose a traversal approach based on the information you actually need, read the right element type in each view, and explain:

1. Why `entrySet` is convenient when both keys and values are needed.
2. How `map.forEach((key, value) -> ...)` differs from `map.entrySet().forEach(entry -> ...)`.
3. Why `values()` returns `Collection<V>` rather than `Set<V>`.
4. When values can be replaced or entries removed during traversal.
5. Why holding a view differs from holding a copy, and why holding a `Map.Entry` differs from capturing an independent pair of data.

## 2. Overview of Traversal Approaches

| How data is obtained | Returned type | What does each element represent? | When to choose |
|---|---|---|---|
| `map.entrySet()` | `Set<Map.Entry<K, V>>` | A mapping consisting of a key and a value | Both are needed, or you need to operate on each mapping |
| `map.keySet()` | `Set<K>` | A key | Only keys are needed |
| `map.values()` | `Collection<V>` | A value corresponding to a mapping | Only values are needed; duplicate values are expected |
| `map.forEach(action)` | Method returning `void` | Action receiving `K` and `V` separately | Concise action, without needing `break` or a direct iterator |

The view types extend `Collection`, so you can use a `for-each` loop, an iterator, or `Iterable.forEach` on them.

`Map` itself does not extend `Iterable`. Therefore, the following snippet is **illustrative syntax that does not compile**, even though it looks like a loop over a list:

```java
// Invalid: stock is a Map, not an Iterable.
for (Object item : stock) {
    System.out.println(item);
}
```

To use an enhanced `for` loop, choose a view, such as `stock.entrySet()`. Having a method named `forEach` on `Map` does not make `Map` an `Iterable`: it is a method provided by the `Map` interface itself.

### One Data Source, Three Kinds of Elements

With the initial example map:

```text
keySet():    "pen", "notebook", "marker"
values():     3,     2,          3
entrySet():  ("pen",3), ("notebook",2), ("marker",3)
```

This illustrates the insertion order of a default `LinkedHashMap`. Do not assume every `Map` has that order.

Two different keys can share the same value `3`. Therefore:

- `keySet` is a `Set`: there are no duplicate keys in a map.
- `entrySet` is a `Set` of mappings.
- `values` must retain both occurrences of `3`, so it is declared as `Collection`, without promising to eliminate duplicates.

In this example, the size of each view equals the size of the map, which is `3`. The number of **distinct values** is only `2`, which is a different quantity.

## 3. entrySet: Keeping Key and Value in the Same Element

A `Map.Entry<K, V>` element represents a key–value pair. The basic reading and updating methods are:

| Method | Result |
|---|---|
| `entry.getKey()` | Key of type `K` |
| `entry.getValue()` | Value of type `V` |
| `entry.setValue(newValue)` | Replaces the value if supported; returns the old value |

Illustrative loop, placed inside a method that already has `Map<String, Integer> stock`:

```java
for (Map.Entry<String, Integer> entry : stock.entrySet()) {
    String product = entry.getKey();
    Integer count = entry.getValue();
    System.out.println(product + "=" + count);
}
```

The element being traversed is an entry, not just a key and not a sub-map. `getValue()` here reads the value belonging to the mapping currently being examined.

If using `var`, an equivalent illustrative snippet can be written as:

```java
for (var entry : stock.entrySet()) {
    System.out.println(entry.getKey() + "=" + entry.getValue());
}
```

`var` only infers the local variable type. It does not change the actual element type or the traversal rules.

### Why Usually Avoid Traversing keySet and Calling get When Both Are Needed?

The following illustrative snippet can produce the right output for a suitable stable map:

```java
for (String key : stock.keySet()) {
    Integer value = stock.get(key);
    System.out.println(key + "=" + value);
}
```

However, if both the key and the value of every mapping are needed, `entrySet` expresses the intent more directly and avoids an extra key lookup for each element.

This observation should not be turned into an absolute speed claim for every map or every program. Cost depends on the implementation, size, work inside the loop, and runtime environment. The clearest benefit at the source-code level is that when both parts of the pair are already available, there is no need to look up the value again by key.

Beyond cost, there is also a behavioral issue: with a `LinkedHashMap` created in access-order mode, `get` can change the access order. Putting `get` inside a key traversal loop in that case can affect the very ordering structure being traversed. `entrySet` avoids unnecessary extra access calls.

If only keys are needed, `keySet` remains the right choice. There is no need to choose `entrySet` and discard all the values just because someone considers it the “best” traversal in every situation.

## 4. map.forEach: An Action Receiving Two Arguments

The method signature is:

```java
// API signature, not a standalone program.
void forEach(BiConsumer<? super K, ? super V> action);
```

`BiConsumer` is a functional interface for an action that takes two inputs and returns no result. With `Map<String, Integer>`, the lambda usually has two parameters:

```java
// Illustrative snippet with stock already initialized.
stock.forEach((key, value) -> {
    System.out.println(key + "=" + value);
});
```

Here `key` is the key and `value` is the value, not two consecutive elements of a collection.

Distinguish this from `forEach` called on a view:

```java
// Receives one Map.Entry per call.
stock.entrySet().forEach(entry -> {
    System.out.println(entry.getKey() + "=" + entry.getValue());
});

// Receives one key per call.
stock.keySet().forEach(key -> {
    System.out.println(key);
});

// Receives one value per call.
stock.values().forEach(value -> {
    System.out.println(value);
});
```

The examples above are illustrative snippets that require an existing `stock` variable. The difference lies in the element type where the method is called:

| Expression | Typical lambda parameter count | Data per invocation |
|---|---:|---|
| `stock.forEach((k, v) -> ...)` | 2 | Key and value |
| `stock.entrySet().forEach(e -> ...)` | 1 | One entry |
| `stock.keySet().forEach(k -> ...)` | 1 | One key |
| `stock.values().forEach(v -> ...)` | 1 | One value |

Writing a two-parameter lambda for `entrySet().forEach` mismatches the signature: the view provides a single entry object and does not split it into two parameters.

`forEach` fits actions such as printing data, forwarding each pair to another method, or recording into another result structure controlled by the program. If the task needs to find the first matching element and stop, a loop is usually clearer to express. Section 10 verifies the difference between `return` in a lambda and `break` in a loop.

## 5. Complete Program: Observing All Reading Forms

The following standalone program uses a default `LinkedHashMap`. Thanks to insertion order, the output lines have a deterministic order, making verification convenient.

```java
import java.util.LinkedHashMap;
import java.util.Map;

public class MapTraversalFormsDemo {
    public static void main(String[] args) {
        Map<String, Integer> stock = new LinkedHashMap<>();
        stock.put("pen", 3);
        stock.put("notebook", 2);
        stock.put("marker", 3);

        System.out.println("entrySet:");
        for (Map.Entry<String, Integer> entry : stock.entrySet()) {
            System.out.println(entry.getKey() + "=" + entry.getValue());
        }

        System.out.println("map.forEach:");
        stock.forEach((key, value) ->
                System.out.println(key + "=" + value));

        System.out.println("entrySet.forEach:");
        stock.entrySet().forEach(entry ->
                System.out.println(entry.getKey() + "=" + entry.getValue()));

        System.out.println("keys:");
        for (String key : stock.keySet()) {
            System.out.println(key);
        }

        System.out.println("values:");
        int total = 0;
        for (Integer count : stock.values()) {
            System.out.println(count);
            total += count;
        }
        System.out.println("total=" + total);
        System.out.println("map=" + stock);
    }
}
```

```shell

java MapTraversalFormsDemo
```

Exact output:

```text

notebook=2
marker=3
map.forEach:

notebook=2
marker=3
entrySet.forEach:
pen=3
notebook=2

keys:
pen
notebook
marker
```

### What to Observe from the Output

The three groups `entrySet`, `map.forEach`, and `entrySet.forEach` all traverse the same mappings in the example. The difference lies in the code form and the input data passed to the action:

- The `entrySet` loop places step-by-step control in the loop body.
- `map.forEach` passes key and value as two parameters.
- `entrySet.forEach` passes one entry as one parameter.

The `keys` group prints only item codes. The `values` group prints both occurrences of `3`; the final sum computes `3 + 2 + 3 = 8`. If you put the values into a `Set` before summing, the two `3`s would be collapsed and that would be a different calculation.

The program assumes quantities are all non-`null`. The expression `total += count` unboxes `Integer`; if the data allows `null`, you must decide how to handle it before adding, such as skipping, reporting invalid data, or applying a clear business rule.

No reading step in the program removes or adds mappings, so the final `map=` line still represents the three original items.

## 6. A View Is a Window into the Backing Map

When you store:

```java
// Illustrative snippet with stock already initialized.
Set<String> keys = stock.keySet();
Collection<Integer> values = stock.values();
Set<Map.Entry<String, Integer>> entries = stock.entrySet();
```

you do not have three independently copied data stores. These variables hold three views backed by the map underneath.

The two important directions of this relationship are:

```text
Add/remove/replace mappings in the map
        ↓
Contents observed through the view reflect the map

Remove an element through a view that supports removal
        ↓
The corresponding mapping in the map is removed
```

This describes the data relationship; it **does not guarantee thread safety**, and it does not allow keeping an old iterator and arbitrarily modifying the map outside the iterator.

For example, store `keys = stock.keySet()`, finish another operation, and then add a new key to `stock`; when you traverse `keys` in a new traversal pass, you will observe that new key. There is no need to call `keySet()` again to “refresh the copy”, because it was never a copy in the first place.

### What Do Removal Operations Mean?

| Operation on a modifiable view | Effect on the map |
|---|---|
| `keySet().remove(k)` | Removes the mapping with key `k` |
| `values().remove(v)` | Removes one mapping with a matching value if present |
| `entrySet().remove(entry)` | Removes the mapping matching both key and value of the entry |
| `clear()` on any of the three views | Removes the mappings in the map |
| `iterator.remove()` on a view | Removes the mapping corresponding to the element just returned by the iterator |

Mutating operations are optional and depend on whether the map/view supports them. With an unmodifiable map, removing through a view is not a workaround to modify the map.

`values().remove(v)` removes only **one** matching occurrence per the `Collection.remove` contract. If multiple keys carry that value, do not assume all of them are removed, and do not rely on a specific key being chosen unless the implementation guarantees it.

For `entrySet().remove`, providing the right key with the wrong value is not enough to remove the mapping. You can create a standalone entry to represent the pair to compare, as shown in a later program.

### Why Can't You Add Through a View?

The three `Map` views do not support `add` or `addAll`. For keys or values alone, the other half of the mapping is missing. Even for `entrySet`, which has a full pair, the view contract still does not support adding via `add`.

To add a mapping, use a map API such as `put`. Do not assume that because `Set` or `Collection` has an `add` method, every object of those types supports that operation.

## 7. Live Views, Copies, and Removing Through a View

A view obtained before adding a new mapping still reflects the map after the update. A copied list retains the structure from the time it was created. The illustrative snippet is placed in a method with the required types imported; `LinkedHashMap` preserves insertion order for easy comparison:

~~~java
Map<String, Integer> stock = new LinkedHashMap<>();
stock.put("pen", 3);
Set<String> liveKeys = stock.keySet();
List<String> copiedKeys = new ArrayList<>(liveKeys);
stock.put("marker", 3);
System.out.println(liveKeys);   // [pen, marker]
System.out.println(copiedKeys); // [pen]
~~~

If `liveKeys.remove("pen")` is called outside a traversal loop, the `"pen"` mapping also disappears from `stock`. Similarly, `stock.values().remove(3)` removes **one occurrence** of the value `3`, not all keys that have `3`. Here `values()` has type `Collection<Integer>`, so `remove(3)` removes by value (`remove(Object)`), not by list index.

That is the effect of a view; **removing during a traversal pass** requires using an iterator or `removeIf` properly. Sections 8–9 focus on verifying these two mechanisms. The lesson on `keySet, values, entrySet and Map.Entry` already explained removal operations across each view in detail.
## 8. Replacing Values and Removing During Traversal

Distinguish three different actions:

1. Replacing the value of the current mapping.
2. Removing the current mapping.
3. Adding/removing another mapping via a call outside the traversal mechanism.

Not every approach has the same contract.

### 8.1. Replacing a Value via entry.setValue

For an entry returned by the `entrySet` iterator, `setValue` can be used during traversal if the implementation supports it. That change is reflected in the backing map.

Illustrative snippet with a modifiable `Map<String, Integer> stock` and non-`null` values:

```java
for (Map.Entry<String, Integer> entry : stock.entrySet()) {
    Integer old = entry.setValue(entry.getValue() + 1);
    System.out.println("old=" + old);
}
```

`setValue` returns the old value. It cannot change the key. `Map.Entry` does not provide `setKey`; if a key needs to change, you must design the removal of the old mapping and creation of the new mapping using an appropriate mechanism, rather than mutating the key object itself inside the map.

Do not assume `setValue` always works. An entry from an unmodifiable map or an entry type that does not support value replacement can throw `UnsupportedOperationException`.

### 8.2. Removing with the Active Iterator Itself

The enhanced `for` loop hides the iterator underneath, so when you need to remove the current element, using an explicit iterator is usually easier to control:

```java
// Illustrative snippet with a modifiable stock and no null values.
Iterator<Map.Entry<String, Integer>> iterator =
        stock.entrySet().iterator();

while (iterator.hasNext()) {
    Map.Entry<String, Integer> entry = iterator.next();
    if (entry.getValue() == 0) {
        iterator.remove();
    }
}
```

Important rules:

- `remove()` removes the element just returned by `next()`.
- Do not call `remove()` before the first `next()`.
- Do not call `remove()` twice in a row for the same `next()` call.
- An iterator may not support removal; in that case it can throw `UnsupportedOperationException`.
- If you need to record the key/value of the removed element, read or copy the needed information **before removing**.

After a mapping has been removed, do not continue relying on the old entry's behavior as if it were still a valid mapping in the map. Section 13 clarifies the scope of entry usage.

### 8.3. Removing with removeIf on a View

If you only need to filter out mappings by a condition, you can call:

```java
// Illustrative snippet with a modifiable stock and non-null values.
boolean changed = stock.entrySet()
        .removeIf(entry -> entry.getValue() <= 0);
```

The call returns `true` if any elements were removed, not the count of removed elements. With `entrySet`, the condition can use both the key and the value; with `keySet` or `values`, only the corresponding data is available.

To express “remove every value equal to 3, even if the map may contain null”, an illustrative snippet is:

```java
stock.values().removeIf(value -> java.util.Objects.equals(value, 3));
```

`removeIf` requires removal to be supported. The predicate itself should not add or remove mappings in the map currently being filtered. Let the filtering operation manage the removal.

## 9. Complete Program: Controlled Value Updates and Removals

```java
import java.util.Iterator;
import java.util.LinkedHashMap;
import java.util.Map;

public class MapTraversalEditDemo {
    public static void main(String[] args) {
        Map<String, Integer> stock = new LinkedHashMap<>();
        stock.put("pen", 3);
        stock.put("notebook", 0);
        stock.put("marker", 2);
        stock.put("expired", 0);

        for (Map.Entry<String, Integer> entry : stock.entrySet()) {
            if (entry.getValue() > 0) {
                Integer old = entry.setValue(entry.getValue() + 1);
                System.out.println("updated=" + entry.getKey()
                        + ", old=" + old + ", now=" + entry.getValue());
            }
        }

        Iterator<Map.Entry<String, Integer>> iterator =
                stock.entrySet().iterator();
        while (iterator.hasNext()) {
            Map.Entry<String, Integer> entry = iterator.next();
            if (entry.getValue() == 0) {
                String removedKey = entry.getKey();
                iterator.remove();
                System.out.println("removed=" + removedKey);
            }
        }
        System.out.println("afterIterator=" + stock);

        stock.put("discarded", -1);
        boolean changed = stock.entrySet().removeIf(
                entry -> entry.getValue() <= 0);
        System.out.println("removeIfChanged=" + changed);
        System.out.println("finalMap=" + stock);
    }
}
```

Save as `MapTraversalEditDemo.java`, compile, and run:

```shell
javac --release 17 -encoding UTF-8 MapTraversalEditDemo.java
java MapTraversalEditDemo
```

Exact output:

```text
updated=pen, old=3, now=4
updated=marker, old=2, now=3
removed=notebook
removed=expired
afterIterator={pen=4, marker=3}
removeIfChanged=true
finalMap={pen=4, marker=3}
```

### Execution Flow Explanation

The first `entrySet` pass updates only positive values: `"pen"` from `3` to `4`, `"marker"` from `2` to `3`. The `old=` outputs are the old values returned by `setValue`.

The next iterator pass removes the two mappings with value `0`. The key is saved in `removedKey` before `iterator.remove()` is called, so printing the info does not need to use the removed entry.

Only after the iterator pass finishes does the program add `"discarded" → -1`. Next, an independent `entrySet().removeIf` call removes the non-positive mapping. The final structure retains `"pen" → 4` and `"marker" → 3`.

There are no additions or removals outside the iterator while that iterator is traversing. This is important for how steps are structured; you should not collapse them into one loop and insert arbitrary structural modification calls.

## 10. Control Flow in forEach Differs from Loops

### 10.1. return Is Not break

Inside a lambda passed to `Map.forEach`, `return;` ends **the current lambda invocation**. It does not tell `forEach` to skip the remaining mappings, and it does not return from the enclosing method.

Loop `break` and `continue` cannot be used to jump from inside a lambda to a loop outside the lambda. If you need to stop immediately upon encountering a mapping, use an explicit loop with `break`, or write an appropriate search method.

`Map.forEach` returns `void`; it is not a transformation that produces a new map. To transform values, consider dedicated operations such as `replaceAll` or `entry.setValue` when compatible with the implementation's contract. To build another result, create a separate target structure and write the collection logic explicitly.

### 10.2. Reassigning a Lambda Parameter Does Not Change the Mapping

Illustrative snippet:

```java
// Illustrative snippet with scores already containing non-null Integer values.
scores.forEach((key, value) -> {
    value = value + 10;
});
```

Only the local parameter variable `value` is reassigned. No call writes the new value back into the map, so the mappings do not update themselves.

Distinguish reassigning a parameter from mutating a referenced mutable object. If `value` is a list, `value.add(...)` can mutate the list currently referenced by the map. That is not the same as changing the key's mapping to a different value object.

### 10.3. Exceptions Stop the Process but Do Not Undo Prior Effects

If the action throws an exception, `forEach` propagates that exception to the caller and does not continue as if no error occurred. Effects the action already performed earlier, such as appending to a result list, are not automatically undone by `forEach`.

Do not use exceptions as a routine `break` just to find the first element. Exceptions are appropriate for representing real errors; a loop with direct stopping control is usually clearer for searching.

### Complete Program

```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class MapForEachControlDemo {
    public static void main(String[] args) {
        Map<String, Integer> scores = new LinkedHashMap<>();
        scores.put("A", 1);
        scores.put("B", 2);
        scores.put("C", 3);

        System.out.println("lambdaReturn:");
        scores.forEach((key, value) -> {
            if (value == 2) {
                return;
            }
            System.out.println("processed=" + key);
        });
        System.out.println("afterForEach");

        System.out.println("loopBreak:");
        for (Map.Entry<String, Integer> entry : scores.entrySet()) {
            if (entry.getValue() == 2) {
                System.out.println("stoppedAt=" + entry.getKey());
                break;
            }
            System.out.println("visited=" + entry.getKey());
        }

        System.out.println("localParameterAssignment:");
        scores.forEach((key, value) -> {
            value = value + 10;
            System.out.println(key + " local=" + value);
        });
        System.out.println("mapAfterLocalAssignment=" + scores);

        List<String> visited = new ArrayList<>();
        try {
            scores.forEach((key, value) -> {
                visited.add(key);
                if (value == 2) {
                    throw new IllegalStateException("stop");
                }
            });
        } catch (IllegalStateException expected) {
            System.out.println("callbackFailure=" + expected.getMessage());
        }
        System.out.println("visitedBeforeFailure=" + visited);
        System.out.println("mapAfterFailure=" + scores);
    }
}
```

Save as `MapForEachControlDemo.java`, compile, and run:

```shell
javac --release 17 -encoding UTF-8 MapForEachControlDemo.java
java MapForEachControlDemo
```

Exact output:

```text
lambdaReturn:
processed=A
processed=C
afterForEach
loopBreak:
visited=A
stoppedAt=B
localParameterAssignment:
A local=11
B local=12
C local=13
mapAfterLocalAssignment={A=1, B=2, C=3}
callbackFailure=stop
visitedBeforeFailure=[A, B]
mapAfterFailure={A=1, B=2, C=3}
```

### Reading the Output by Mechanism

- The `lambdaReturn` group skips processing key `B` but still processes `C`. This proves `return` only ends the lambda invocation for `B`.
- The `loopBreak` group stops at `B`, so it does not reach `C`.
- The `localParameterAssignment` group prints `11`, `12`, `13` in the local variable, while the map still contains `1`, `2`, `3`.
- When the action throws `IllegalStateException` at `B`, the `visited` list already contains `A` and `B`, and `C` has not been processed.

The `visited` list is a separate result object, distinct from the map being traversed. The lambda can mutate the contents of the list without reassigning the `visited` variable.

By contrast, local variables captured by a lambda must be `final` or effectively final. Therefore you cannot freely increment a local total variable outside the lambda:

```java
// Illustrative snippet that does not compile: total is modified inside the lambda.
int total = 0;
scores.forEach((key, value) -> {
    total += value;
});
```

If you only need a sequential sum, a loop over `values()` as in the first program is both clearer and avoids creating a mutable wrapper just to work around the syntax constraint. Choosing a lambda does not by itself make an operation faster or thread-safe.

## 11. Do Not Arbitrarily Modify Structure During Traversal

The following snippet is **an anti-pattern for analysis, not a recommended way to remove**:

```java
// stock is an ordinary map with a fail-fast iterator.
for (Map.Entry<String, Integer> entry : stock.entrySet()) {
    if (entry.getValue() == 0) {
        stock.remove(entry.getKey());
    }
}
```

The loop uses an iterator, yet the removal goes through `stock.remove`. With implementations like `HashMap` or `LinkedHashMap`, modifying the structure that way while an iterator is active can be detected and lead to `ConcurrentModificationException`.

Key points to understand accurately:

- A single thread can cause this error; the exception name does not mean two threads are necessarily involved.
- Do not rely on a short test run not throwing an exception to conclude the approach is valid.
- The fail-fast error detection mechanism makes a best-effort attempt to detect misuse, not a guarantee that every invalid modification will definitely be caught.
- Catching the exception and continuing to reuse the iterator does not fix a broken design.
- Switching the code to `map.forEach` or `entrySet().forEach` does not automatically make arbitrary additions/removals valid.

To remove the current element, use `iterator.remove` if supported. For bulk filtering, use `removeIf` on the appropriate view if supported. For a complex set of changes, you can collect the intended changes in a separate structure and apply them after the traversal pass finishes.

Illustrative snippet collecting keys to remove, assuming `stock` is not modified elsewhere during the process:

```java
List<String> toRemove = new ArrayList<>();

for (Map.Entry<String, Integer> entry : stock.entrySet()) {
    if (entry.getValue() != null && entry.getValue() == 0) {
        toRemove.add(entry.getKey());
    }
}

for (String key : toRemove) {
    stock.remove(key);
}
```

These are two separate passes and require memory for the key list. It does not by itself become a transaction or a concurrent-access solution; the goal here is to avoid modifying the map structure via calls outside the iterator while a map traversal pass is open.

### Replacing a Value Does Not Mean Every Way of Replacing Is Interchangeable

With `HashMap`, simply replacing the value of an existing key is not considered a structural modification. However, do not generalize this into a rule for every implementation or for the lifetime of every entry.

The direct mechanism permitted by the `entrySet` contract during traversal is `setValue` on the entry returned by the iterator, when supported. Using that mechanism expresses intent more clearly than calling arbitrary other methods on the map inside the loop body.

With an access-ordered `LinkedHashMap`, even a `get` can affect traversal order. So when diagnosing traversal bugs, do not look only for `put` or `remove`; you also need to understand the map type and how it was constructed.

### When Multiple Threads Access the Map

Views and `forEach` do not by themselves provide a consistent snapshot or a lock protecting the entire process. A loop over an ordinary `HashMap` does not become safe just because it reads via `entrySet` instead of `keySet`.

If data is shared, you must choose an appropriate coordination mechanism or an implementation with a suitable concurrent-access contract. Some specialized implementations have iterator rules different from fail-fast; do not apply the same conclusion to every class just because they all implement `Map`. The examples in this lesson use a single owning thread to separate traversal concerns from synchronization.

## 12. Ordering and Cost Belong to the Implementation's Contract

### 12.1. Changing Syntax Does Not Create a New Order

`entrySet`, `keySet`, `values`, and `forEach` do not automatically sort data alphabetically or by value.

- `HashMap` guarantees no traversal order.
- `LinkedHashMap` in default mode traverses in insertion order.
- `LinkedHashMap` in access-order mode follows a different rule.
- Maps created by `Map.of` do not commit to a fixed traversal order to rely on.

For `Map.forEach`, unless specified otherwise by the implementation, the action runs in the entry set's iteration order when that order is defined. Thus choosing a lambda over a loop does not turn a `HashMap` into an insertion-ordered map.

If report output requires a specific order, choose a structure with the appropriate ordering contract or build and sort the output data explicitly. Do not treat the order observed in one `HashMap` run as a stable program requirement.

Do not copy keys and values separately at two different times and then pair them up by position to reconstruct pairs. Data may have changed between the two copies. When the key–value association must be preserved, process or capture each pair via `entrySet`.

### 12.2. Traversing an Entire Map Is Not O(1)

Obtaining a view does not mean all the data has been processed. Traversing `n` mappings and performing an action for each mapping requires cost proportional to the number of elements plus the work of the action.

For commonly used implementations:

| Implementation and operation | View traversal cost |
|---|---|
| `HashMap` | Proportional to `capacity + size` |
| `LinkedHashMap` | Proportional to `size`, not dependent on hash table capacity in the same way |

`capacity` here is the hash table capacity, while `size` is the number of mappings. A `HashMap` with a large capacity but few elements can still spend work scanning buckets. Do not call all `Map` traversals identical in cost based solely on the interface name.

The bounds above do not include the cost of printing, network calls, string processing, or other work inside the loop body. If each mapping triggers a slow task, the difference between loop syntax and lambda syntax is unlikely to be the main optimization concern.

Using `entrySet` when both parts of the pair are needed avoids looking up each value by key again. Choosing the data structure itself should also consider ordering, update, access, and actual data requirements.

## 13. Holding a View, Copying a Collection, and Holding an Entry Are Three Different Things

Before retaining data after a traversal pass, be clear whether what you need to keep is a **live view**, a **structural copy**, or **detached key–value pairs**:

- `stock.keySet()` reflects mapping changes in the source; a `new ArrayList<>(stock.keySet())` has its own structure, though it may still share the key objects.
- `new ArrayList<>(stock.entrySet())` only copies entry references. Do not rely on entries still tied to the map as a durable snapshot after the map changes.
- To keep independent pairs, create `new AbstractMap.SimpleImmutableEntry<>(entry)` **while the entry is still valid**. The new entry does not follow mapping changes in the source, though the key and value objects inside may still be shared.
- `Collections.unmodifiableMap(stock)` blocks mapping changes through the wrapper, yet it remains a live view; it does not create an independent snapshot or turn mutable values into immutable ones.

For traversal and reporting problems, choosing a snapshot also depends on consistency requirements when multiple threads modify data. The program in Section 14 verifies a subtler point: **a copy containing list values still shares the old lists**, even when the source map has rebound the mapping.
## 14. Complete Program: Copies, Detached Entries, and Wrappers

```java
import java.util.AbstractMap;
import java.util.ArrayList;
import java.util.Collections;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class MapViewCopiesDemo {
    private static void expectUnsupported(String label, Runnable action) {
        try {
            action.run();
            throw new AssertionError("Expected UnsupportedOperationException");
        } catch (UnsupportedOperationException expected) {
            System.out.println(label + "=UnsupportedOperationException");
        }
    }

    public static void main(String[] args) {
        Map<String, List<String>> source = new LinkedHashMap<>();
        source.put("item", new ArrayList<>(List.of("A")));

        Map<String, List<String>> readOnly =
                Collections.unmodifiableMap(source);
        List<String> copiedKeys = new ArrayList<>(source.keySet());
        Map<String, List<String>> copiedMap = new LinkedHashMap<>(source);

        List<Map.Entry<String, List<String>>> detachedEntries =
                new ArrayList<>();
        for (Map.Entry<String, List<String>> entry : source.entrySet()) {
            detachedEntries.add(new AbstractMap.SimpleImmutableEntry<>(entry));
        }

        source.put("extra", new ArrayList<>(List.of("X")));
        source.get("item").add("B");

        System.out.println("readOnlyKeys=" + readOnly.keySet());
        System.out.println("copiedKeys=" + copiedKeys);
        System.out.println("copiedMapKeys=" + copiedMap.keySet());
        System.out.println("copiedMapItem=" + copiedMap.get("item"));
        System.out.println("detachedEntryKey="
                + detachedEntries.get(0).getKey());
        System.out.println("detachedEntryValue="
                + detachedEntries.get(0).getValue());

        source.put("item", new ArrayList<>(List.of("Z")));
        System.out.println("readOnlyItemAfterRebind=" + readOnly.get("item"));
        System.out.println("copiedMapItemAfterRebind=" + copiedMap.get("item"));
        System.out.println("detachedEntryValueAfterRebind="
                + detachedEntries.get(0).getValue());

        expectUnsupported("keySetAdd", () -> source.keySet().add("newKey"));
        expectUnsupported("valuesAdd",
                () -> source.values().add(new ArrayList<>()));
        expectUnsupported("entrySetAdd", () -> source.entrySet().add(
                new AbstractMap.SimpleImmutableEntry<>(
                        "newKey", new ArrayList<>())));
        expectUnsupported("readOnlyKeyRemove",
                () -> readOnly.keySet().remove("item"));
        expectUnsupported("readOnlyEntrySetValue",
                () -> readOnly.entrySet().iterator().next()
                        .setValue(new ArrayList<>()));
    }
}
```

Save as `MapViewCopiesDemo.java`, compile, and run:

```shell
javac --release 17 -encoding UTF-8 MapViewCopiesDemo.java
java MapViewCopiesDemo
```

Exact output:

```text
readOnlyKeys=[item, extra]
copiedKeys=[item]
copiedMapKeys=[item]
copiedMapItem=[A, B]
detachedEntryKey=item
detachedEntryValue=[A, B]
readOnlyItemAfterRebind=[Z]
copiedMapItemAfterRebind=[A, B]
detachedEntryValueAfterRebind=[A, B]
keySetAdd=UnsupportedOperationException
valuesAdd=UnsupportedOperationException
entrySetAdd=UnsupportedOperationException
readOnlyKeyRemove=UnsupportedOperationException
readOnlyEntrySetValue=UnsupportedOperationException
```

### 14.1. New Keys Appear Only in the Live Wrapper

`readOnlyKeys=[item, extra]` because `readOnly` reads the underlying `source` map. `copiedKeys` and `copiedMapKeys` only have `item` because they copied the structure before the `"extra"` key was added.

The name `readOnly` in the program means mappings cannot be modified through that reference; it does not promise that all underlying data is frozen.

### 14.2. The Old List Is Still Shared After Copying

Initially, `source`, `copiedMap`, and the detached entry all hold references to the same list containing `A`. After `B` is added to the list, both `copiedMapItem` and `detachedEntryValue` see `[A, B]`.

Later, `source.put("item", ...)` binds the source to a new list `[Z]`:

```text
source["item"] and readOnly["item"] → new list [Z]

copiedMap["item"] ─┐
                   ├→ old list [A, B]
detached entry ────┘
```

The detached entry does not automatically follow the source's new mapping. However, the contents of the old list can still change if anything else modifies it, because this is still only reference copying.

### 14.3. Unsupported Operations Are Rejected

All three `add` operations on the views of the modifiable source map are rejected. This is a limitation of the view contract, not evidence that the source map is completely unmodifiable.

The last two operations act through the unmodifiable wrapper: removing a key via `readOnly.keySet` and changing the value of an entry obtained from `readOnly.entrySet`. They throw `UnsupportedOperationException`, showing that views are not a workaround to mutate the wrapper's mappings.

The `expectUnsupported` helper throws `AssertionError` if the tested operation succeeds normally. Thus the output lines represent conditions that were actually verified, not just pre-printed messages.

## 15. Choosing the Right Tool for the Job

| Task | Usually suitable approach | Reason |
|---|---|---|
| Print each key and value | `entrySet` or `Map.forEach` | Both parts of the pair are available |
| Check only key names | `keySet` | No need to retrieve values |
| Sum quantities | Loop over `values` | Keeps duplicate values and updates a sum variable directly |
| Find one mapping and stop | Loop over `entrySet` | Allows `break` or returning from the enclosing method |
| Replace the current entry's value | `entry.setValue` when supported | Operation is tied to the entry being traversed |
| Remove mappings in a multi-step process | Explicit iterator and `iterator.remove` | Controls the current element alongside removal |
| Filter out mappings by condition | `entrySet().removeIf` when supported | Condition can use both key and value |
| Expose live data while restricting mapping edits | Appropriate unmodifiable wrapper | Still must account for live source and mutable values |
| Save data for later use | Create structural copies and independent pairs as needed | Avoids mistaking live views or entries for snapshots |

There is no single traversal syntax that is optimal for every task. Writing it properly usually starts with identifying the data needed, how long the data must be kept, and what changes are allowed during that process.

## 16. Self-Check: Predict Before Running

### Question 1: Duplicate Values

A map has `"a" → 5`, `"b" → 5`, `"c" → 8`. What is `values().size()`? When traversing `values()`, will you necessarily see only two numbers?

**Answer:** The size is `3`. There are three values corresponding to the three mappings, in which `5` appears twice. If you want distinct values, you must perform a separate set-creation step and accept losing occurrence counts.

### Question 2: View Obtained Earlier

You obtain `Set<String> keys = map.keySet();`, then add a new key to the map and start a new traversal pass on `keys`. Does the view reflect the new key?

**Answer:** Yes. The view is backed by the map. This does not mean an active iterator is allowed to tolerate arbitrary external changes, nor does it mean there is any thread-safety guarantee.

### Question 3: Removing a Key Through a View

With a modifiable map, `keys.remove("a")` returns `true`. Does the mapping for `"a"` still remain in the map?

**Answer:** No. Removing through the view removes the corresponding mapping in the backing map.

### Question 4: Removing a Duplicate Value

Two keys share the value `5`. You call `map.values().remove(5)` once. Are both mappings guaranteed to be removed?

**Answer:** No. `Collection.remove` removes one matching occurrence if present. To filter out all mappings with that value, use an explicit bulk removal condition on a supporting structure.

### Question 5: Right Key, Wrong Value

A map has `"a" → 5`. You try removing via `entrySet().remove(new AbstractMap.SimpleImmutableEntry<>("a", 9))`. Is the mapping removed?

**Answer:** No, under the mapping semantics of the ordinary maps discussed here. An entry requires both the key and the value to match; the pair `"a" → 9` is not the pair currently present.

### Question 6: return Inside a Lambda

A default `LinkedHashMap` has keys in order `A`, `B`, `C`. The lambda skips `B` with `return;`. Is `C` still processed?

**Answer:** Yes, assuming no error or other condition stops the operation. `return` only ends the lambda invocation for `B`. To stop the whole traversal at `B`, use a mechanism capable of stopping, such as a loop with `break`.

### Question 7: Reassigning value

With `Map<String, Integer>`, a lambda executes `value = value + 1;`. Does the map automatically increment each value?

**Answer:** No. The local parameter changes its reference, while the mapping is not written back. If the value is a mutable object and you call a method that mutates the object, that is a different action.

### Question 8: Calling iterator.remove Twice

An iterator supports removal. After one `next()`, you call `remove()` twice in a row without calling `next()` again. What is wrong?

**Answer:** `remove` may only be called once per `next` call. The second call violates the iterator's state and leads to `IllegalStateException`.

### Question 9: Not Seeing ConcurrentModificationException

Code that removes via `map.remove` directly inside a `for-each` loop over `entrySet` happens to finish without an exception. Does that prove the removal approach is valid?

**Answer:** No. Fail-fast is not a guarantee that every misuse will be detected. Your removal approach must follow the contract, not whether a particular run happened to report an error.

### Question 10: Copied Entry List

Does `new ArrayList<>(map.entrySet())` automatically create an independent snapshot for each key–value pair?

**Answer:** No. It creates a list containing entry references. To keep independent data for later use, actively construct separate data pairs while the entries are still valid; if values are mutable, you must also decide whether to deep-copy them.

### Question 11: Unmodifiable Wrapper

`readOnly = Collections.unmodifiableMap(source)`. Then you modify the map through `source`. Can reads through `readOnly` see the changes?

**Answer:** Yes. This is a wrapper that reads through the source, not a separate copy. Restricting mutations through `readOnly` also does not freeze mutable value objects.

### Question 12: Traversal Cost

A `HashMap` has a very large table capacity but only a few mappings. Can you conclude from the small `size` alone that every traversal cost is correspondingly small?

**Answer:** No. Traversing `HashMap` views has cost proportional to both capacity and the number of mappings. Do not ignore the underlying implementation structure when analyzing performance.

## 17. Practice: Inventory Reporting and Filtering

Create a separate program with `LinkedHashMap<String, Integer>`:

```text
pen      → 3
notebook → 0
marker   → 3
eraser   → 1
```

Perform in order:

1. Print each item code and quantity using `entrySet`.
2. Print again using `Map.forEach`, confirming the mappings are the same.
3. Sum the total using `values`, keeping both `3`s.
4. Create a separate list of the current keys.
5. Remove mappings with quantity `0` using an iterator or `removeIf`, according to the supported contract.
6. Increment each remaining quantity by `1` using `entry.setValue`.
7. Explain why the key list copied in step 4 still contains `"notebook"`, whereas the live key view does not.

Conditions to satisfy:

```text
Initial total quantity = 7.
After filtering, the key notebook is not in the map.
After incrementing, pen = 4, marker = 4, eraser = 2.
Final map size = 3.
The key list copied before filtering still has notebook.
```

Extend by adding a key with a `null` value, then choose and clearly document your policy:

- Skip `null` values when summing, or report invalid data.
- When filtering, decide whether `null` should be removed or kept.
- Do not accidentally unbox `null` with `<=`, `==` against an integer, or addition.

When checking results, use the set of mappings and data conditions as criteria. Only check print order when the implementation or a sorting step has a clear ordering contract.
