# put, putAll, get, remove, and the Returned Old Value

## 1. Viewing Map Through an Existing Mapping

A `Map<K, V>` stores mappings from keys of type `K` to values of type `V`. For example, the key `"pen"` might identify the current quantity of pens as `10`:

```text
"pen"      → 10
"notebook" → 7
```

The key point is that **each key has at most one current value**. Calling `put("pen", 15)` changes the mapping of `"pen"` from `10` to `15`; this operation does not create a second `"pen"` entry. If a key needs to be associated with multiple elements, the value type must express that, such as `Map<String, List<String>>`. `put` itself still associates a key with only one value object.

`Map` belongs to Java's collections framework, but it does not extend `Collection<E>`. Its operations revolve around keys and values, not index positions like `List`. There is no "insert at index 2" operation among the four methods in this lesson.

This lesson focuses on four questions:

- What should you use to associate or replace a key's value?
- What should you use to retrieve the current value?
- What should you use to remove a mapping?
- Does a method's return value reflect the state **before** or **after** the operation?

The last question is especially error-prone. With `put` and the single-argument `remove`, the return value usually helps identify the value that was just replaced or removed from the map. It is not a success flag.

### Why is the old value needed?

Suppose an inventory edit screen submits a new quantity of `15`. After calling `put("pen", 15)`, the program may need to record that the previous quantity was `10`. Reading `get("pen")` after the operation only yields `15`; the `10` has already been replaced. The return value of `put` provides that old information.

Similarly, `remove("pen")` both deletes the mapping and returns the value that was previously associated with the key. If you only need the removed value, you usually do not need to call `get` separately before `remove`. However, a `null` result may not be enough to determine whether the key existed beforehand; you need to understand the `null` policy of the map implementation you are using.

## 2. Contract Table of the Four Methods

Given a variable `Map<K, V> map`, the relevant signatures are:

| Method | Effect if the operation is supported | Return value |
|---|---|---|
| `V put(K key, V value)` | Associates `key` with `value`; replaces the value if the key already has a mapping | The key's value **before the call**, or `null` |
| `void putAll(Map<? extends K, ? extends V> source)` | Copies mappings from `source` into the target map; source wins on duplicate keys | No return value |
| `V get(Object key)` | Looks up the current value of the key | The current value, or `null` if there is no mapping |
| `V remove(Object key)` | Removes the mapping for the key if present | The key's value **before removal**, or `null` |

For `put` and `remove`, `null` has two possibilities if the map allows `null` values: there was no prior mapping, or there was a prior mapping with a `null` value. Section 5 separates these two states.

`get` and `remove` accept `Object` in the key parameter position in the API signature. That does not turn a map into a store for arbitrary keys: key types on writes are still constrained by `K`, and looking up with an incompatible object is not a technique to rely on. Some implementations may reject incompatible keys with an exception.

The table above describes mapping semantics. Operations that modify a map are optional operations in the `Map` interface; an unmodifiable map can throw `UnsupportedOperationException`. Support for `null` keys or values also depends on the implementation. You cannot conclude that an object is modifiable or accepts `null` solely because its declared type is `Map`.

### Reading a put line along two timelines

Consider the following illustrative statement, assuming the map currently contains `"pen" → 10`:

```java
Integer oldValue = stock.put("pen", 15);
```

There are two distinct pieces of information:

```text
Before the call: stock["pen"] = 10
New argument:                   15
Return value:                   10
After the call:  stock["pen"] = 15
```

`oldValue` is `10`, while `stock.get("pen")` afterward is `15`. Variable names should reflect this: `oldValue`, `previousStock`, or `removedValue` are clearer than `result` when distinguishing the two points in time.

## 3. Full Experiment: Adding, Replacing, Reading, and Removing

The standalone program below uses `LinkedHashMap` in its default mode so that the map's display order is predictable by insertion order. In this mode, replacing the value of an existing key does not move that key to the end. Choosing this implementation only helps observe the results; the return-value semantics of the four methods come from the `Map` contract.

```java
import java.util.LinkedHashMap;
import java.util.Map;

public class MapBasicReturnDemo {
    public static void main(String[] args) {
        Map<String, Integer> stock = new LinkedHashMap<>();

        Integer firstOld = stock.put("pen", 10);
        System.out.println("firstOld=" + firstOld);
        System.out.println("penNow=" + stock.get("pen"));
        System.out.println("size=" + stock.size());

        Integer replacedOld = stock.put("pen", 15);
        System.out.println("replacedOld=" + replacedOld);
        System.out.println("penNow=" + stock.get("pen"));
        System.out.println("size=" + stock.size());

        Integer notebookOld = stock.put("notebook", 7);
        System.out.println("notebookOld=" + notebookOld);
        System.out.println("stock=" + stock);

        System.out.println("missing=" + stock.get("missing"));
        System.out.println("sizeAfterMissingGet=" + stock.size());

        Integer removedOld = stock.remove("pen");
        System.out.println("removedOld=" + removedOld);
        System.out.println("stockAfterRemove=" + stock);
        System.out.println("removedAgain=" + stock.remove("pen"));

        Integer sameValueOld = stock.put("notebook", 7);
        System.out.println("sameValueOld=" + sameValueOld);
        System.out.println("finalSize=" + stock.size());
    }
}
```

Save the code to `MapBasicReturnDemo.java`, then compile and run it:

```shell
javac --release 17 -encoding UTF-8 MapBasicReturnDemo.java
java MapBasicReturnDemo
```

Expected output:

```text
firstOld=null
penNow=10
size=1
replacedOld=10
penNow=15
size=1
notebookOld=null
stock={pen=15, notebook=7}
missing=null
sizeAfterMissingGet=2
removedOld=15
stockAfterRemove={notebook=7}
removedAgain=null
sameValueOld=7
finalSize=1
```

### Explaining each state transition

1. `put("pen", 10)` encounters an absent key: creates a new mapping, returns `null`, size becomes `1`.
2. `put("pen", 15)` encounters an existing key: replaces `10` with `15`, returns `10`, size remains `1`.
3. `put("notebook", 7)` adds another key: returns `null`, size becomes `2`.
4. `get("missing")` returns `null` because there is no mapping. It does not create a key or insert a default value; size remains `2`.
5. `remove("pen")` returns `15`, leaving only `"notebook" → 7` in the map.
6. `remove("pen")` again finds no mapping and therefore returns `null`.
7. `put("notebook", 7)` returns `7`, even though the new value and old value are equal.

The last line is especially noteworthy: **the return value is the old data, not an answer to "did the data change?"**. Writing the same value still returns the old value. Conversely, adding a new entry has a real effect yet can return `null`.

If you switch to `HashMap`, the lookup values in the example still obey the contract, but you should not rely on the print order of the entire map as a pass/fail condition. `HashMap` does not guarantee iteration order.

### Size changes based on key presence

| State before the call | Successful call | Size change |
|---|---|---|
| Key `k` not present | `put(k, value)` | Increases by 1 |
| Key `k` already present | `put(k, value)` | Unchanged |
| Mapping exists for `k` | `remove(k)` | Decreases by 1 |
| No mapping exists for `k` | `remove(k)` | Unchanged |
| Any | `get(k)` | Neither creates nor removes mappings |

The size rules still hold when a mapping's value is `null`, as long as the implementation allows `null` values. Size counts the number of mappings, not the number of non-`null` values.

Do not overgeneralize the last row into the statement "`get` never has any side effect in any map." For example, `LinkedHashMap` has a special access-order mode in which `get` can change the access order. What is relied on here is that `get` does not create or remove mappings.

## 4. Correctly Interpreting the Results of put and remove

### 4.1. The old value is not a success code

With `Map<String, Boolean>`, `put` can return `false` because the old value really was `Boolean.FALSE`. That does not mean the write failed. With `Map<String, Integer>`, a result of `0` is likewise just the old integer.

The following snippet is **illustrative code**, assuming `flags` is a modifiable `Map<String, Boolean>`:

```java
flags.put("enabled", false);
Boolean previous = flags.put("enabled", true);
// previous is Boolean.FALSE; flags.get("enabled") is Boolean.TRUE.
```

Similarly, `remove` returning `false` from a `Map<String, Boolean>` can mean it removed a mapping whose value was `false`. Read the data types and method signature before interpreting a result as a success flag.

When a method completes normally, its effect is defined by its contract. Invalid situations are signaled by exceptions; do not invent a convention that `null`, `0`, or `false` means "failure" if the API does not define it that way.

### 4.2. Equal keys can be the same logical key

In the examples using `HashMap` or `LinkedHashMap`, matching keys is based on the `equals` and `hashCode` contract, not on requiring two references to be the exact same object.

Illustrative snippet:

```java
Map<String, Integer> counts = new HashMap<>();
counts.put("pen", 10);
Integer old = counts.put(new String("pen"), 15);
// old = 10, counts.size() = 1, counts.get("pen") = 15.
```

`new String("pen")` creates a different string object, yet it is still equal to `"pen"` according to `equals`. Therefore, the second `put` replaces the value of the existing logical key. The purpose of this example is to distinguish "a newly allocated key object" from "a logical key not yet in the map"; in normal code there is no need to construct strings with `new String` like this.

This lesson uses immutable `String` keys to focus on the operations. For custom key types, the correctness of `equals` and `hashCode`, and not mutating key-identifying fields while a key is inside the map, are separate prerequisites to maintain. Do not diagnose every case where `get` fails to find data as a bug in the return value of `put`.

### 4.3. The return value is the old reference when V is a reference type

If `V` is a mutable object, `put` or `remove` does not automatically create a deep snapshot of that object. They return the reference to the old value. Replacing a mapping in the map also does not destroy the old object if it is still referenced elsewhere.

For example, if the old value is an `ArrayList<String>`, the variable receiving the result from `put` can still point to that list after the map has associated the key with a new list. The old list is no longer the value for that key in the map, but it remains a normal live object as long as references to it exist.

Therefore, "saving the old value" and "saving an immutable snapshot of the old data" are two different requirements. The second requirement may need copying the data according to the application's structure and rules.

## 5. Null: Distinguishing an Absent Key from a Key Mapped to null

`HashMap` and `LinkedHashMap` allow `null` values. With these maps, there are at least three states to distinguish:

| State of key `k` | `get(k)` | `containsKey(k)` |
|---|---|---|
| No mapping | `null` | `false` |
| Mapping `k → null` | `null` | `true` |
| Mapping `k → "ready"` | `"ready"` | `true` |

Consequently, the question "is the retrieved value non-`null`?" is different from the question "does the map contain this key?".

### 5.1. put(k, null) is not remove(k)

If a map allows `null` values:

- `put(k, null)` keeps or creates a mapping for `k`; afterward `containsKey(k)` is `true`.
- `remove(k)` removes the mapping; afterward `containsKey(k)` is `false`.

An application may intentionally forbid `null` values to reduce the number of states it must handle, but that is an application policy. You must not infer from `get(k)` returning `null` that a removal occurred.

### 5.2. getOrDefault does not replace every null with the default value

`getOrDefault(k, fallback)` uses `fallback` when **there is no mapping** for `k`. If a mapping exists with the value `null`, the result can still be `null`.

This method also does not insert `fallback` into the map. If you need an operation that computes and stores a value when missing, that is a different requirement from reading a default value; you should not expect `get` or `getOrDefault` to perform it silently.

## 6. Full Experiment: Two Meanings of a null Result

The standalone program below uses `HashMap<String, String>`. It only prints lookup values and sizes, so the output does not depend on `HashMap` iteration order.

```java
import java.util.HashMap;
import java.util.Map;

public class MapNullAmbiguityDemo {
    public static void main(String[] args) {
        Map<String, String> states = new HashMap<>();

        System.out.println("firstPutOld=" + states.put("draft", null));
        System.out.println("draftValue=" + states.get("draft"));
        System.out.println("missingValue=" + states.get("missing"));
        System.out.println("hasDraft=" + states.containsKey("draft"));
        System.out.println("hasMissing=" + states.containsKey("missing"));
        System.out.println("draftOrDefault="
                + states.getOrDefault("draft", "fallback"));
        System.out.println("missingOrDefault="
                + states.getOrDefault("missing", "fallback"));

        boolean existedBeforePut = states.containsKey("draft");
        String oldOnReplace = states.put("draft", "ready");
        System.out.println("existedBeforePut=" + existedBeforePut);
        System.out.println("oldOnReplace=" + oldOnReplace);
        System.out.println("current=" + states.get("draft"));

        System.out.println("oldBeforeNull=" + states.put("draft", null));
        System.out.println("sizeWithNull=" + states.size());

        boolean existedBeforeRemove = states.containsKey("draft");
        String removedOld = states.remove("draft");
        System.out.println("existedBeforeRemove=" + existedBeforeRemove);
        System.out.println("removedOld=" + removedOld);
        System.out.println("hasDraftAfterRemove=" + states.containsKey("draft"));
        System.out.println("sizeAfterRemove=" + states.size());
        System.out.println("removeMissing=" + states.remove("draft"));
    }
}
```

Save the code to `MapNullAmbiguityDemo.java`, then compile and run it:

```shell
javac --release 17 -encoding UTF-8 MapNullAmbiguityDemo.java
java MapNullAmbiguityDemo
```

Expected output:

```text
firstPutOld=null
draftValue=null
missingValue=null
hasDraft=true
hasMissing=false
draftOrDefault=null
missingOrDefault=fallback
existedBeforePut=true
oldOnReplace=null
current=ready
oldBeforeNull=ready
sizeWithNull=1
existedBeforeRemove=true
removedOld=null
hasDraftAfterRemove=false
sizeAfterRemove=0
removeMissing=null
```

### Why is oldOnReplace still null?

Right before `put("draft", "ready")`, the map already had the mapping `"draft" → null`. Therefore:

- `existedBeforePut` is `true`: the key existed.
- `oldOnReplace` is `null`: that was the actual old value.
- `current` is `"ready"`: that is the new value.

If you only look at `oldOnReplace == null` and conclude "this was a new key insertion," the program will reach the wrong conclusion.

### Why is removedOld null even though it was removed?

Before removing, the program called `put("draft", null)`. The mapping still existed, with size `1`. Calling `remove("draft")` retrieved the old value `null` and removed the mapping. Result:

- `existedBeforeRemove = true`.
- `removedOld = null`.
- `hasDraftAfterRemove = false`.
- `sizeAfterRemove = 0`.

The next call to `remove("draft")` also returns `null`, but because no mapping remains. Returning the same value twice does not mean both calls produced the same change.

### When you check existence matters

If you want to know whether a key existed **before writing or removing**, capture that information from the state prior to the operation, as the example does with `existedBeforePut` and `existedBeforeRemove`.

Checking `containsKey(k)` after `put(k, value)` cannot recover whether the key was present beforehand: after a successful `put`, both cases have the key. Similarly, after `remove(k)`, both a successful removal and an initially absent key can yield `containsKey(k) == false`.

The examples run in a single thread. A sequence like "`containsKey` then `put`" or "`containsKey` then `remove`" consists of multiple separate calls; between them, another thread can modify the map if there is no proper coordination mechanism. Do not treat such a pair of calls as an atomic operation merely because the lines are adjacent. `HashMap` also does not provide synchronization for concurrent mutating access from multiple threads.

## 7. putAll: Copying Mappings and Handling Duplicate Keys

`target.putAll(source)` puts the mappings of `source` into `target`. You can understand the per-key effect by this rule:

```text
Key present in source:
    target receives the value from source.

Key present only in target:
    target keeps that mapping.
```

Example:

| Key | In target before operation | In source | In target after operation |
|---|---|---|---|
| `"pen"` | `10` | `20` | `20` |
| `"notebook"` | `5` | Not present | `5` |
| `"marker"` | Not present | `3` | `3` |

Key consequences to keep clear:

- `putAll` does not clear the target before copying the source.
- On duplicate keys, the source value overwrites the value in the target.
- It does not add quantities together: `10` and `20` do not become `30`.
- It does not deep-merge fields of two value objects.
- It does not return a map containing the old values; its return type is `void`.
- Only the mappings copied at the time of the operation are involved; this does not establish an automatic live sync between the two maps.

If the source contains a `null` value and the target allows it, `null` is also written into the target during the copy. It does not mean "skip this key" or "remove this key from the target." If the target forbids `null`, you must follow the target implementation's policy rather than assuming based on what the source accepts.

### Why do the parameters have ? extends K and ? extends V?

The signature `putAll(Map<? extends K, ? extends V> source)` allows copying from a map whose key and value types are narrower but still assignable to the target's types.

The following illustrative snippet requires importing `java.util.Map` and `java.util.LinkedHashMap`:

```java
Map<String, Integer> source = Map.of("pen", 20);
Map<CharSequence, Number> target = new LinkedHashMap<>();
target.putAll(source);
```

`String` is a subtype of `CharSequence`, and `Integer` is a subtype of `Number`. Because `putAll` reads keys and values from the source and writes them into the target, this type relationship is sound. No raw casts or suppressed generic checks are needed.

The source in this snippet is created by `Map.of` and is unmodifiable, yet it can still be **read** to copy into a modifiable target. Modifiability of the source and modifiability of the target are two separate concerns: the call mutates `target`, not `source`.

## 8. Full Experiment: Mapping Copies and Shared Objects

The standalone program below demonstrates two things that are easily confused:

1. Changing a mapping in the source map after `putAll` does not automatically change the corresponding mapping in the target map.
2. If both mappings point to the same mutable object, mutating that object can be observed through both maps.

```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class MapPutAllSemanticsDemo {
    public static void main(String[] args) {
        Map<String, Integer> target = new LinkedHashMap<>();
        target.put("pen", 10);
        target.put("notebook", 5);

        Map<String, Integer> source = new LinkedHashMap<>();
        source.put("pen", 20);
        source.put("marker", 3);

        Map<String, Integer> before = new LinkedHashMap<>(target);
        target.putAll(source);

        System.out.println("before=" + before);
        System.out.println("target=" + target);
        System.out.println("source=" + source);

        source.put("pen", 99);
        System.out.println("sourcePenAfterChange=" + source.get("pen"));
        System.out.println("targetPenAfterSourceChange=" + target.get("pen"));

        List<String> shared = new ArrayList<>();
        shared.add("A");

        Map<String, List<String>> listSource = new LinkedHashMap<>();
        listSource.put("item", shared);
        Map<String, List<String>> listTarget = new LinkedHashMap<>();
        listTarget.putAll(listSource);

        listSource.get("item").add("B");
        System.out.println("targetAfterSharedListChange="
                + listTarget.get("item"));

        listSource.put("item", new ArrayList<>(List.of("X")));
        System.out.println("sourceAfterRebind=" + listSource.get("item"));
        System.out.println("targetAfterSourceRebind=" + listTarget.get("item"));
        System.out.println("stillSharesOriginal="
                + (listTarget.get("item") == shared));
    }
}
```

Save the code to `MapPutAllSemanticsDemo.java`, then compile and run it:

```shell
javac --release 17 -encoding UTF-8 MapPutAllSemanticsDemo.java
java MapPutAllSemanticsDemo
```

Expected output:

```text
before={pen=10, notebook=5}
target={pen=20, notebook=5, marker=3}
source={pen=20, marker=3}
sourcePenAfterChange=99
targetPenAfterSourceChange=20
targetAfterSharedListChange=[A, B]
sourceAfterRebind=[X]
targetAfterSourceRebind=[A, B]
stillSharesOriginal=true
```

### 8.1. Why does target keep pen at 20?

Right after `target.putAll(source)`, both maps have the mapping `"pen" → 20`. Then `source.put("pen", 99)` replaces only the mapping in `source`.

`target` is not a live view of `source`. It still has its own mapping `"pen" → 20`; hence `targetPenAfterSourceChange=20`.

`Integer` objects are immutable. "Changing the quantity" in the example replaces the value reference of the mapping, rather than mutating the contents of an existing integer object.

### 8.2. Why is adding B visible through listTarget?

In the later part, `listSource` and `listTarget` are two different maps, but the value for key `"item"` in both points to the same `shared` list:

```text
listSource["item"] ─┐
                    ├──→ shared: [A]
listTarget["item"] ─┘
```

Calling `listSource.get("item").add("B")` mutates the **list object** being shared. It does not change the mapping for the key `"item"`. Therefore, reading the list through `listTarget` also sees `[A, B]`.

Next, `listSource.put("item", new ArrayList<>(List.of("X")))` replaces only the mapping in the source:

```text
listSource["item"] ───→ new list: [X]
listTarget["item"] ───→ shared: [A, B]
```

The target map still points to the old list. The line `stillSharesOriginal=true` confirms this using reference comparison `==`.

There are three levels to distinguish:

| Level | Question to ask |
|---|---|
| Map object | Do two variables point to the same map? |
| Mapping | Which value does a key in each map point to? |
| Value object | Do the mappings point to the same mutable object? |

`putAll` copies mappings; it does not automatically deep-copy the object graph of keys and values. If an application needs two maps with completely independent data, you must define an appropriate copying strategy for each data type. Merely changing syntax from `putAll` to a map copy constructor does not automatically resolve all shared internal references.

### 8.3. What level of snapshot is before?

In the first part, `new LinkedHashMap<>(target)` creates another map to store the mappings before `putAll`. Because the keys are `String` and the values are `Integer`, both immutable in the example, `before` is useful for observing the old numbers.

If the values were mutable lists, such a map copy could still share the lists. It does not guarantee that the deep contents of the old data will remain unchanged. When you need accurate logging or undo capability, design state capture around the actual data rather than assuming every map copy is a deep copy.

## 9. When You Need to Collect Old Values for Multiple Keys

`putAll` returns `void`. The following statement is **type-invalid**:

```java
// Illustrates a statement that does not compile:
Map<String, Integer> oldValues = target.putAll(source);
```

The right-hand side does not produce a value to assign. If you need to know the old data during a bulk write, you can choose one of two approaches depending on your requirements:

- Snapshot the necessary mappings before calling `putAll`.
- Iterate over the source yourself and call `put` for each key, collecting both the return values and prior existence information.

The following example is an **illustrative snippet inside a method**, where `target` and `source` are two distinct `Map<String, Integer>` instances, the source is stable, the target is modifiable, and access is owned by a single thread:

```java
Map<String, Integer> oldValues = new LinkedHashMap<>();
Map<String, Boolean> existedBefore = new LinkedHashMap<>();

for (Map.Entry<String, Integer> entry : source.entrySet()) {
    String key = entry.getKey();
    boolean existed = target.containsKey(key);
    Integer old = target.put(key, entry.getValue());

    existedBefore.put(key, existed);
    oldValues.put(key, old);
}
```

The snippet uses `LinkedHashMap`, so the corresponding import is needed if placed in a program. The two maps record two kinds of information:

- `oldValues` records the old value returned by `put`.
- `existedBefore` distinguishes an absent key from a key that already had a `null` value.

If the application forbids all `null` values, the recorded data can be simplified under that policy. If the application allows `null`, keeping only `oldValues` may not be enough to restore the old state: "no mapping" and "mapping with value `null`" require different restoration steps.

This is an example of collecting information during an update, not a general-purpose transaction or safe rollback mechanism. If an exception occurs mid-loop, part of the data may already have been written. If multiple threads modify the map concurrently, individual calls do not automatically form an atomic operation for the entire loop. If the value objects themselves are mutable, the collected old values may still be shared references.

### putAll does not promise all-or-nothing updates

The `Map.putAll` contract does not provide transactional guarantees for the entire set of mappings. For example, the target might reject a particular key or value. You should not assume that when an exception is thrown, all mappings from before the call remain untouched.

The extent of partial modification on failure depends on the implementation and execution order. You do not need to prove this using an assumed iteration order to apply the rule: the key point is that **there is no general guarantee to rely on**.

If business logic requires validating all data before publishing the new state, you must design appropriate validation steps, staging data structures, and state-swapping mechanisms. If the map is shared across threads, proper coordination is also needed. A single `putAll` call does not replace those requirements.

You should not structurally modify the source map while copying from it without understanding the specific implementation's guarantees. All examples in this lesson keep the source stable throughout the operation.

## 10. Unboxing Trap: The Write Succeeded, but the Assignment Still Fails

`Map<String, Integer>` has value type `Integer`, not `int`. When a key is absent, `put` can return `null`. The statement below includes an extra conversion from `Integer` to `int`:

```java
// Illustrates a statement that can cause a NullPointerException:
int old = counters.put("hits", 1);
```

The sequence of events is:

1. Call `put("hits", 1)`.
2. The map creates the mapping `"hits" → 1` and returns `null` because there was no previous value.
3. The assignment needs to unbox the `Integer` result to `int`.
4. Unboxing `null` throws a `NullPointerException`.

Therefore, an exception on this statement **does not prove the write did not happen**. If you catch the exception and blindly retry the write, the program may be operating on a different state than you think.

The proper way to receive the result when `null` is possible is to use the wrapper type:

```java
// Illustration with counters already initialized:
Integer old = counters.put("hits", 1);
if (old != null) {
    int previousCount = old;
    System.out.println(previousCount);
}
```

If you also need to distinguish "key absent" from "key has value `null`", add existence tracking as shown in Section 6; merely changing `int` to `Integer` solves the unboxing error, not all state ambiguities.

The same situation occurs with `int removed = map.remove("absent")` when the return value is `null`. It can also happen with `boolean previous = flags.put(...)` if the `Boolean` result is `null`.

## 11. Unmodifiable Maps and the boolean-Returning remove Overload

The same name `remove` with different parameter lists can have different return types and meanings:

| Call | Return type | Meaning |
|---|---|---|
| `remove(key)` | `V` | Removes by key and returns the old value |
| `remove(key, expectedValue)` | `boolean` | Removes only if the key is currently mapped to a matching value; returns whether the conditional removal succeeded |

If `remove("k", 99)` returns `false`, do not interpret it as "the old value was false." That is the conditional flag-returning overload. Conversely, `remove("k")` on a `Map<String, Boolean>` can return the old value `Boolean.FALSE`. The number of arguments and the return type determine how to read it.

Do not infer from the existence of the conditional overload that every `Map` implementation provides atomic guarantees for concurrent access. That is a contract you must check on the specific implementation or specialized interface being used.

Another issue is map modifiability. Maps created by `Map.of` do not allow adding, removing, or replacing mappings. They are still `Map` instances and can still be read with `get`, but mutating operations are unsupported.

### Full experiment

The standalone program below verifies the unboxing error, unmodifiable maps, and the two conditional `remove` calls together:

```java
import java.util.HashMap;
import java.util.Map;

public class MapReturnPitfallsDemo {
    private static void expectUnsupported(String label, Runnable action) {
        try {
            action.run();
            throw new AssertionError("Expected UnsupportedOperationException");
        } catch (UnsupportedOperationException expected) {
            System.out.println(label + "=UnsupportedOperationException");
        }
    }

    public static void main(String[] args) {
        Map<String, Integer> counters = new HashMap<>();

        try {
            int old = counters.put("hits", 1);
            System.out.println("unexpectedOld=" + old);
        } catch (NullPointerException expected) {
            System.out.println("firstPutAssignment=NullPointerException");
        }
        System.out.println("hitsExistsAfterException="
                + counters.containsKey("hits"));
        System.out.println("hitsValueAfterException=" + counters.get("hits"));

        try {
            int removed = counters.remove("absent");
            System.out.println("unexpectedRemoved=" + removed);
        } catch (NullPointerException expected) {
            System.out.println("missingRemoveAssignment=NullPointerException");
        }

        Map<String, Integer> readOnly = Map.of("fixed", 1);
        expectUnsupported("readOnlyPut", () -> readOnly.put("fixed", 2));
        expectUnsupported("readOnlyRemove", () -> readOnly.remove("fixed"));
        expectUnsupported("readOnlyPutAll",
                () -> readOnly.putAll(Map.of("extra", 3)));

        Map<String, Integer> values = new HashMap<>();
        values.put("k", 10);
        System.out.println("removeWrongValue=" + values.remove("k", 99));
        System.out.println("valueAfterWrongRemove=" + values.get("k"));
        System.out.println("removeMatchingValue=" + values.remove("k", 10));
        System.out.println("hasKAfterMatchingRemove=" + values.containsKey("k"));
    }
}
```

Save the code to `MapReturnPitfallsDemo.java`, then compile and run it:

```shell

```

Expected output:

```text

hitsExistsAfterException=true
hitsValueAfterException=1
missingRemoveAssignment=NullPointerException
readOnlyPut=UnsupportedOperationException

readOnlyPutAll=UnsupportedOperationException

```

### Reading the output to find the real cause

- `firstPutAssignment=NullPointerException` alongside `hitsExistsAfterException=true` and value `1`: the error occurred during unboxing of the `null` old result after the write.
- `missingRemoveAssignment=NullPointerException`: there was no old value to unbox into `int`.
- The three `readOnly...` lines show that modifying mappings in `Map.of` is rejected with `UnsupportedOperationException`.
- `removeWrongValue=false` because the current value is `10`, not `99`; the mapping remains.
- `removeMatchingValue=true` because the condition matched; afterward the key `"k"` is no longer in the map.

The `expectUnsupported` helper does not swallow errors silently: it throws `AssertionError` if an operation expected to be unsupported completes normally. The examples therefore clearly demonstrate the conditions they verify.

Do not use a no-op mutation, such as `putAll` with an empty source, as a general test for whether a map is modifiable. The contract allows implementations to differ on whether an unsupported operation throws an exception when it would make no changes. Know how the map was created and its implementation's contract, rather than probing modifiability with an ambiguous test.

## 12. Choosing an Approach Based on the Information You Actually Need

| Need | Approach | What to check |
|---|---|---|
| Read the current value | `get(key)` | `null` can represent multiple states |
| Read with a fallback when the key is absent | `getOrDefault(key, fallback)` | A key mapped to `null` does not automatically receive the fallback |
| Determine whether a mapping exists | `containsKey(key)` | If combined with other operations, consider ownership and concurrent access |
| Write a key and get the old value | Capture the result of `put` in an appropriate type `V` | Do not unbox `null`; do not confuse the old value with the new value |
| Remove by key and get the old value | `remove(key)` | An old value of `null` does not prove nothing was removed |
| Remove only when the current value matches | `remove(key, expectedValue)` | This is the `boolean`-returning overload; check implementation guarantees |
| Copy mappings and allow source to overwrite | `putAll(source)` | Return type is `void`; does not deep copy; no transactional guarantee |
| Keep history before multiple writes | Snapshot state or collect each `put` result | Record existence if `null` is allowed; account for mutable objects |

Choose based on business requirements first. For example, updating inventory with a **newly computed value** fits `put`; adding an amount to the current value is a different problem. Calling `put` multiple times does not automatically perform addition or protect a read–compute–write sequence from concurrent modifications.

Similarly, the requirement "populate default values for missing keys" is different from "let the source overwrite all duplicate keys." If you need to preserve existing values, do not pick `putAll` and hope it skips duplicate keys.

## 13. Common Mistakes and How to Re-read the Contract

### Confusing put as returning the new value

Symptom: you write `15`, see `10` in the result variable, and assume the map did not update.

How to check: inspect the return value and a subsequent `get` separately. `10` is the old data; `get` returning `15` is the new state.

### Mistaking null for a failed operation

Symptom: the first insertion returns `null`, and the program reports an error or retries.

How to check: check whether the key was previously absent or had a `null` value. A successful write can return `null` completely in accordance with the contract.

### Using get to check existence in a map that allows null

Symptom: `get(k) == null` is treated as proof that the key is definitely absent.

How to check: if the policy allows `null` values, use `containsKey` when you need to distinguish the cases. If the application policy forbids `null`, enforce that policy on every write path rather than just assuming it at a read site.

### Mistaking putAll as preserving old data on duplicate keys

Symptom: after copying configuration, existing values are unexpectedly overwritten.

How to check: `source` wins on duplicate keys. To keep target values, you must choose and explicitly write a different rule; the name `putAll` does not imply "put only if absent."

### Mistaking map copying for deep copying

Symptom: two maps are separate, yet modifying a list through one map shows up through the other.

How to check: check the value object references. Two independent mappings can still point to the same list.

### Catching an exception and assuming no effect occurred

Symptom: encountering a `NullPointerException` when assigning the result of `put` to an `int`, or encountering an exception during a bulk update, and continuing on the assumption that the old state is intact.

How to check: separate the method call from result handling; verify the actual state against the contract. For transactional requirements, design appropriate guarantees upfront.

### Forgetting that a map may be unmodifiable

Symptom: a variable is declared as `Map`, `get` works, but `put` throws `UnsupportedOperationException`.

How to check: trace how the object was created, such as `Map.of`. The interface type provides the method signatures; it does not require every instance to support all mutating operations.

## 14. Self-Check with Short Operation Sequences

The questions below assume a single thread using the map. Each question is an independent scenario.

### Question 1: Old values and size

Initially `Map<String, Integer> map = new HashMap<>();`. Execute:

```java
Integer a = map.put("x", 4);
Integer b = map.put("x", 9);
Integer c = map.put("x", 9);
```

What are `a`, `b`, `c`, `map.get("x")`, and `map.size()` respectively?

**Answer:** `null`, `4`, `9`, `9`, `1`. The third call writes the same number `9` yet still returns the old value `9`.

### Question 2: Mapping null then removing

A `HashMap<String, String>` is empty. After `put("x", null)`, `remove("x")` is called and returns `null`. Can you conclude the removal had no effect?

**Answer:** No. Before the removal, the mapping `"x" → null` existed, so removing it reduces the size from `1` to `0`. The old value removed was `null`.

### Question 3: Reading with default

A map has `"x" → null` and does not have `"y"`. What are the results of `getOrDefault("x", "N/A")` and `getOrDefault("y", "N/A")`? After these two reads, is key `"y"` added?

**Answer:** `null` and `"N/A"`, respectively. Key `"y"` is not added; a fallback read is not a write.

### Question 4: putAll on duplicate keys

Target has `"a" → 1`, `"b" → 2`; source has `"b" → 8`, `"c" → 3`. After `target.putAll(source)`, what mappings does target have? Which map does the method return?

**Answer:** Target has `"a" → 1`, `"b" → 8`, `"c" → 3`. The method does not return any map because its return type is `void`. This answer describes the set of mappings, not an assertion about iteration order for an arbitrary `Map`.

### Question 5: A false value

A `Map<String, Boolean>` has `"enabled" → false`. Call `Boolean old = map.put("enabled", true);`. If `old` is `false`, did the write fail?

**Answer:** No. `false` is the old value. The key's current value is `true` if the call completed normally. This is not a success-flag-returning overload.

### Question 6: Exception after a write

An empty `HashMap<String, Integer>` executes `int old = map.put("x", 1);` and throws `NullPointerException`. After catching the exception, what is `map.containsKey("x")`?

**Answer:** `true`, with current value `1`. `put` completed, and then the `null` result was unboxed to `int`, causing the exception. Fix the receiving variable's type to `Integer` and handle the state as needed.

### Question 7: Two maps sharing a list

Source has `"x"` pointing to list `["A"]`. Target copies using `putAll`. Afterward, the old list is mutated with `add("B")`, and then the source's mapping is replaced with a new list `["X"]`. Which list does target see?

**Answer:** Target still points to the old list `["A", "B"]`. Mutating a shared object is different from replacing a mapping in one map.

### Question 8: Two remove overloads

A modifiable map has `"k" → 10`. Call `remove("k", 99)`, then `remove("k")`. What are the types and values of the two results?

**Answer:** The first call returns `boolean false`, keeping the mapping because the value does not match. The second call returns `Integer 10` and removes the mapping. Do not read both results with the same meaning.

### Question 9: Unmodifiable source

`source = Map.of("x", 1)`, and `target = new HashMap<>()`. Will `target.putAll(source)` be rejected just because the source is unmodifiable?

**Answer:** No. The operation reads the source and modifies the target; this source is valid for reading. Conversely, calling `source.put("x", 2)` mutates the unmodifiable map and is rejected.

### Question 10: Keeping track before a removal

A map allows `null` values. Is saving only `V removed = map.remove(k)` enough to distinguish "key was absent" from "key was present with value `null`" before the removal?

**Answer:** No. In a single-threaded ownership scenario, you can also record `containsKey(k)` before removing. If there is concurrent access, an appropriate coordination mechanism is required; two separate calls do not automatically form an atomic operation.

## 15. Practice: Recording an Inventory Change

Write a program using `Map<String, Integer>` with item-code keys:

1. Create a modifiable map and associate `"pen" → 10`.
2. Write the new quantity `15`, storing the old value in an `Integer`.
3. Print both the old value and the current value.
4. Write `"notebook" → 7`, then remove `"pen"` and print the removed value.
5. Copy a source containing `"notebook" → 9` and `"marker" → 3` into the target.
6. Verify the final mappings using `get`, `containsKey`, and `size`, without relying on `HashMap` print order.

Required conditions to meet:

```text
Old value when replacing pen: 10
Value of pen immediately after replacing: 15
Removed value when deleting pen: 15
Finally, pen is no longer present.
Finally, notebook = 9.
Finally, marker = 3.
Final size = 2.
```

Then extend it under two separate policies:

- **Forbid null values:** validate input before writing; explain why a `null` return value can then be used to detect that no prior mapping existed, within the bounds of the enforced policy.
- **Allow null values:** add a case where a key has a `null` value; record existence information before writing or removing, and distinguish it from an absent key.

Do not mix the two policies in the same line of reasoning. A conclusion that holds when every write path forbids `null` can break as soon as any write path allows `null`.

## 16. Questions to Answer Before Using

Before performing a map operation, clarify:

1. Do you need to read the current value, replace a mapping, remove a mapping, or copy multiple mappings?
2. If there is a return value, is it the current value, the old value, or a conditional flag?
3. Do the map and application policy allow `null`?
4. Can the receiving variable hold `null`, or is it forcing unboxing to a primitive type?
5. Does the target map support modification?
6. When copying data, is it acceptable for the source to overwrite duplicate keys and share mutable objects?
7. If you need to preserve prior state or coordinate multiple threads, where do the necessary guarantees come from?

Answering these questions helps you read a line of `put`, `putAll`, `get`, or `remove` according to the actual data state, rather than guessing from variable names or a single `null` value.
