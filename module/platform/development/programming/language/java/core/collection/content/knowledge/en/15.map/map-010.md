# equals, hashCode, and the Map Key Contract

## 1. A Map Needs to Know When Two Keys Are the Same

Suppose a program stores inventory by item code and warehouse:

```text
(itemCode = "PEN", warehouse = 1) → 10
```

The first time, the data comes from the receiving screen. Later, another request creates a new key object that also carries the code `"PEN"` and warehouse `1`. Should two different objects in memory point to the same mapping?

If the business meaning is "same item code, same warehouse," the answer is yes. This is **equality by value or logical identity**, as opposed to two variables pointing to the exact same object.

For standard maps such as `HashMap` and `LinkedHashMap`, the key class must describe that equality using `equals`, while also providing a consistent `hashCode` so the hash-based map can locate equivalent keys.

If designed incorrectly, the program can exhibit confusing symptoms:

- You just called `put`, yet `get` with a supposedly equivalent key finds nothing.
- Two keys are `equals` to each other, yet the map observes two separate mappings.
- You modify a field of a key, and lookups can no longer find the existing data.
- You switch from a hash-based map to an ordered map, and the number of mappings changes because the key comparison rules differ.

This lesson moves from the meaning of a key to the Java contract, then verifies a correct design alongside counterexamples. The goal is not to memorize a hash formula, but to maintain a stable correspondence between **business key → equality relation → map lookup mechanism**.

## 2. Distinguishing ==, equals, and hashCode

| Mechanism | Primary Question |
|---|---|
| `a == b` for reference types | Do the two variables point to the same object? |
| `a.equals(b)` | Does their class consider the two objects equal? |
| `a.hashCode()` | What is the object's integer code used for hashing? |

By default, `Object.equals` uses reference identity: two distinct objects are not equal merely because their fields look alike. A class that wants data-based equality semantics must define or be given an appropriate implementation.

`String` already implements `equals` and `hashCode` based on content. Therefore, two strings that are different objects but have the same content can be used to look up the same key in a `HashMap`.

Illustrative snippet, placed inside a method:

```java
String first = new String("PEN");
String second = new String("PEN");

System.out.println(first == second);      // false
System.out.println(first.equals(second)); // true
```

`new String` is used here solely to create two distinct objects for observation. Normal application code does not need to construct strings this way.

Do not use the result of `==` with string literals or boxed integers to infer key comparison rules: object-sharing mechanisms can cause certain cases to coincidentally point to the same reference. The logical relation of keys must be defined independently of those storage optimizations.

### hashCode Is Not a Unique Identifier

`hashCode` returns an `int`. The number of `int` values is finite, whereas the number of distinguishable objects or states can be huge. Therefore, two different objects can completely legitimately have the same hash code.

Do not use `hashCode` alone as a customer ID, a unique database key, a security signature, or proof that two objects are equal. It is one component of the lookup mechanism, not a replacement for logical comparison.

## 3. The equals Contract: An Equivalence Relation

For non-`null` references, `equals` must satisfy the following properties:

| Property | Condition |
|---|---|
| Reflexive | `x.equals(x)` is `true` |
| Symmetric | `x.equals(y)` and `y.equals(x)` return the same result |
| Transitive | If `x.equals(y)` and `y.equals(z)` are both true, then `x.equals(z)` is also true |
| Consistent | Repeated calls for the same relevant data must return the same result |
| Comparison with null | For non-`null` `x`, `x.equals(null)` is `false` |

Consistency is conditional: the information used for comparison must not be modified. It does not mean every mutable object must forever equal another object after its data has changed. Precisely because of this mutability, using mutable objects as keys must be tightly controlled.

### Why Do These Properties Matter to a Map?

If the relation is not symmetric, the answer to "do two keys share the same mapping?" could depend on the comparison direction. If it is not transitive, three keys could form a self-contradictory "equal" group. A data structure cannot turn a contradictory key definition into a consistent business definition.

Start with the business question: **which fields identify the same key?** Then implement a proper equivalence relation for that answer.

For example, if a key is an item-code–warehouse pair, two keys with the same item code but different warehouses must be unequal. If you only compare the item code, warehouses are unintentionally merged. If you include the display name in equality, renaming an item could cause it to be treated as a new key even when the business logic does not want that.

### Only the Exact Signature Is an Override

The method to override is:

```java
// API signature.
public boolean equals(Object other)
```

If you accidentally write `equals(StockKey other)`, you create an overload rather than overriding `Object.equals(Object)`. A direct call with the concrete type may give the impression that it works, while calls through the interface used by collections will not behave as intended.

Use `@Override` so the compiler verifies the exact signature. Similarly, `hashCode` must be `public int hashCode()`, not a method taking extra parameters.

## 4. The hashCode Contract: Equal Objects Must Have Equal Hashes

The three main requirements are:

1. Calling `hashCode` multiple times on the same object during a single execution must return the same integer, provided no information used in `equals` has changed.
2. If `a.equals(b)` is `true`, then `a.hashCode() == b.hashCode()` must be `true`.
3. If `a.equals(b)` is `false`, the two hash codes may be either different or the same.

The crucial direction of implication:

```text
a.equals(b) == true
        ⇒ a.hashCode() == b.hashCode()

a.hashCode() == b.hashCode()
        ⇏ a.equals(b) == true
```

Two unequal objects with the same hash code produce a **hash collision**. Collisions are handled by hash-based maps through further differentiation; they do not automatically merge two keys into one.

If two equal objects have different hash codes, that is a contract violation by the key class. It is not a valid collision.

### The Hash Code Must Use Information Consistent with equals

Suppose `equals` only uses `id`, while `hashCode` also uses a display name that can differ between two objects with the same `id`. Two equal objects could then receive different hash codes, violating the contract.

An easy-to-verify design approach is to use the same identifying components in both methods. It is not mandatory that every field contribute to the hash code in one specific way: even a constant hash function preserves the "equal objects have equal hashes" requirement, though it usually distributes poorly. That is the difference between **being contract-compliant** and **having good distribution quality**.

Do not include the current time, random numbers, call counters, or external state in `equals`/`hashCode` if they cause results to change while the key identity remains unchanged.

### Do Not Rely on a Fixed Hash Number Outside the Contract

The `Object.hashCode` contract does not require keeping the same integer across different runs of an application. Some classes have their own documented formulas, but that does not turn every `hashCode` into a durable identifier.

For a `record`, the hash code is derived from its components, but you should not guess a specific numeric formula or store that number as the record's identifier. Test the required relationship between equal keys rather than forcing every implementation to produce a specific number according to a guessed formula.

## 5. How Does HashMap Coordinate hashCode and equals?

At a conceptual level, the lookup process can be pictured as:

```text
Key used for lookup
      ↓
Obtain hash code and locate search region
      ↓
Inspect matching candidates
      ↓
Distinguish keys via equality relation
      ↓
Return value of the found mapping
```

This is an explanatory model, not the full source code or bucket-index formula for every Java version. Implementations may further process the hash code, cache hash information, or organize candidates using different structures.

What matters is that a hash-based map **does not necessarily call equals on every key**. It is allowed to skip candidates based on hash information. Therefore, the question "these two keys are `equals`, so why didn't `get` find it?" must be checked together with their hash codes.

From a valid contract:

- Equivalent keys have the same hash code, so they can be found via the same locating mechanism.
- Different keys may collide; `equals` distinguishes them to preserve two separate mappings.
- If a key changes the information determining equality or hashing while stored, the previously organized structure may no longer match.

`LinkedHashMap` adds order management, but still relies on the hash-based map mechanism for keys. Switching from `HashMap` to `LinkedHashMap` does not fix a key class with broken `equals`/`hashCode`.

## 6. Proper Key Design: Immutable Identity and Two Consistent Methods

The standalone program below has two key types:

- `StockKey`: a key class that manually implements `equals` and `hashCode` based on both `sku` and `warehouse`.
- `CollidingKey`: a record key that intentionally returns a constant hash code to demonstrate that a collision does not mean keys are equal.

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public class MapKeyContractDemo {
    static final class StockKey {
        private final String sku;
        private final int warehouse;

        StockKey(String sku, int warehouse) {
            this.sku = Objects.requireNonNull(sku, "sku");
            this.warehouse = warehouse;
        }

        @Override
        public boolean equals(Object other) {
            if (this == other) {
                return true;
            }
            if (!(other instanceof StockKey key)) {
                return false;
            }
            return warehouse == key.warehouse && sku.equals(key.sku);
        }

        @Override
        public int hashCode() {
            return Objects.hash(sku, warehouse);
        }
    }

    record CollidingKey(int id) {
        @Override
        public int hashCode() {
            return 0;
        }
    }

    public static void main(String[] args) {
        StockKey first = new StockKey("PEN", 1);
        StockKey same = new StockKey("PEN", 1);
        StockKey otherWarehouse = new StockKey("PEN", 2);

        System.out.println("sameReference=" + (first == same));
        System.out.println("equalKeys=" + first.equals(same));
        System.out.println("equalHashes="
                + (first.hashCode() == same.hashCode()));
        System.out.println("otherWarehouseEqual="
                + first.equals(otherWarehouse));

        Map<StockKey, Integer> stock = new HashMap<>();
        System.out.println("firstOld=" + stock.put(first, 10));
        System.out.println("replacementOld=" + stock.put(same, 15));
        System.out.println("sizeAfterEqualKey=" + stock.size());
        System.out.println("lookupWithNewKey="
                + stock.get(new StockKey("PEN", 1)));
        stock.put(otherWarehouse, 7);
        System.out.println("sizeAfterDifferentKey=" + stock.size());

        CollidingKey left = new CollidingKey(1);
        CollidingKey right = new CollidingKey(2);
        Map<CollidingKey, String> collisionMap = new HashMap<>();
        collisionMap.put(left, "left");
        collisionMap.put(right, "right");
        System.out.println("collisionEquals=" + left.equals(right));
        System.out.println("collisionSameHash="
                + (left.hashCode() == right.hashCode()));
        System.out.println("collisionSize=" + collisionMap.size());
        System.out.println("lookupLeft="
                + collisionMap.get(new CollidingKey(1)));
        System.out.println("lookupRight="
                + collisionMap.get(new CollidingKey(2)));
    }
}
```

```shell

java MapKeyContractDemo
```

Verified output:

```text

equalKeys=true
equalHashes=true
otherWarehouseEqual=false
firstOld=null
replacementOld=10
sizeAfterEqualKey=1
lookupWithNewKey=15
sizeAfterDifferentKey=2
collisionEquals=false
collisionSameHash=true
collisionSize=2
lookupLeft=left
lookupRight=right
```

### 6.1. Why Are first and same the Same Logical Key?

`first == same` is `false`: they are two distinct objects. However, `equals` compares both item code and warehouse, so they are equal and must have the same hash code.

When `stock.put(same, 15)` is called, the map replaces the value of the existing logical mapping, returns the old value `10`, and keeps size `1`. A brand-new key object `new StockKey("PEN", 1)` also looks up the value `15`.

This allows constructing a lookup key from a new request without needing to retain the exact key object that was previously inserted into the map.

Do not infer from the value replacement a general guarantee that the key object stored internally must be replaced with the newly passed reference. What the contract cares about here is the mapping of the logical key and its corresponding value.

### 6.2. What Is the Purpose of the Choices in StockKey?

- Making the class `final` keeps the scope of the equality relation within one concrete key type, avoiding subclasses adding inconsistent identity.
- Two `final` fields cannot be reassigned after object construction.
- `String` is immutable; `int` is a primitive value. There are no mutable sub-objects to alter identity.
- `Objects.requireNonNull` enforces the policy that the item code cannot be `null`.
- `equals` accepts `Object`, has `@Override`, checks for the same type, and compares the identifying fields.
- `Objects.hash(sku, warehouse)` computes a consistent hash code from those two components.

`Objects.hash` is a convenience utility, not a mandatory requirement for every key. Using it also does not fix a bad choice of fields: if you include an inappropriate field or miss array semantics, you still have to revisit the design.

### 6.3. Why Do the Two CollidingKey Instances Still Coexist?

`CollidingKey(1)` and `CollidingKey(2)` share the same hash code `0` but are unequal because their `id` values differ. The map preserves two separate mappings and looks up each value accurately.

The constant hash function in the program is an experimental tool. It does not violate the requirement that equal keys have equal hashes, though it can pile many keys into the same processing region and degrade efficiency. You do not need to design a unique hash code for every key; prioritize correctness first and appropriate distribution second.

## 7. Counterexample: Conceptually Right equals, Inconsistent hashCode

The following program **intentionally defines a broken key class**. `BadKey.equals` only compares `id`, whereas `hashCode` returns a separately passed `wrongHash` field. Two keys with the same `id` can thus receive different hash codes.

The map observation lines below are empirical results on JDK 24.0.2. Because the key class violates the contract, those results must not be treated as a valid rule that every map or implementation is required to uphold.

```java
import java.util.HashMap;
import java.util.Map;

public class MapBrokenHashDemo {
    static final class BadKey {
        private final int id;
        private final int wrongHash;

        BadKey(int id, int wrongHash) {
            this.id = id;
            this.wrongHash = wrongHash;
        }

        @Override
        public boolean equals(Object other) {
            return other instanceof BadKey key && id == key.id;
        }

        @Override
        public int hashCode() {
            return wrongHash;
        }
    }

    public static void main(String[] args) {
        BadKey first = new BadKey(7, 7);
        BadKey second = new BadKey(7, 8);

        System.out.println("equalKeys=" + first.equals(second));
        System.out.println("equalHashes="
                + (first.hashCode() == second.hashCode()));

        Map<BadKey, String> map = new HashMap<>();
        map.put(first, "first");
        map.put(second, "second");
        System.out.println("observedSize=" + map.size());
        System.out.println("probeHash7=" + map.get(new BadKey(7, 7)));
        System.out.println("probeHash8=" + map.get(new BadKey(7, 8)));
    }
}
```

Save to `MapBrokenHashDemo.java`, then compile and run:

```shell
javac --release 17 -encoding UTF-8 MapBrokenHashDemo.java
java MapBrokenHashDemo
```

Verified output:

```text

equalHashes=false
observedSize=2
probeHash7=first
probeHash8=second
```

### Reading the Output to Pinpoint the Bug

The first two lines alone prove the violation:

```text
equalKeys=true
equalHashes=false
```

`observedSize=2` along with two different lookup results shows how confusing the consequences can be: two objects that the key class itself declares equal still lead to different search paths in the running hash map.

This is not a bug that requires `HashMap` to "scan everything to fix the key for you." The contract permits the implementation to leverage hash information to avoid unnecessary comparisons. It is the key class's responsibility to supply consistent information.

A similar real-world bug is overriding `equals` while leaving `Object.hashCode` untouched. If two objects are considered equal by data yet receive inappropriate default hash codes, a hash map may not behave as the business logic intends. Do not rely on one test dataset coincidentally producing the same hash code to assume the class is correct.

### Fixing by Root Cause

1. Identify the exact identifying components, such as `id`.
2. Have `equals` compare those components according to an equivalence relation.
3. Have `hashCode` derive a consistent hash code from the identity.
4. Keep the identity stable for the entire time the key is used in the map.
5. Test with two or more distinct objects that share the same identity, rather than retesting only the exact same reference.

Do not "fix" this by forcing every lookup call to use the original object if the business logic requires value-based equality. That only masks a key design that fails to meet the requirement.

## 8. Mutable Keys: Do Not Change Identity While Inside a Map

A map does not deep-copy keys on `put`. If you insert a mutable object as a key, the program may still hold another reference to that object and mutate it.

Danger arises when the modified information participates in `equals`, `hashCode`, or the ordering rule of the map in use:

```text
When inserted into the map:
    key has identity 20
    map organizes the mapping based on that info

After direct mutation:
    same key object now has identity 21
    map does not automatically perform a valid key-change operation
```

`Map` does not guarantee behavior if a key object is mutated in a way that affects `equals` comparisons while acting as a key. For hash-based maps, changing the hash code can also cause the new search path to no longer match the information used when storing it.

This does not mean every field of a key object must be immutable in every design. What must stay stable is the information that defines the key under the structure's contract. However, separating a small immutable key type from mutable descriptive data is usually easier to control than using a large object that many parts of the code mutate.

### Full Program: Observing the Failure and Using a New Key

The `unsafe` section below **intentionally violates the key-usage condition**. Lines prefixed with `observed` are observed results on JDK 24.0.2, not a promise of behavior once the contract has been violated.

The `safe` section uses an immutable record key. When an identity needs to move, it removes the old mapping and creates a mapping with a new key, rather than mutating an object currently used by the map.

```java
import java.util.HashMap;
import java.util.Map;

public class MapMutableKeyDemo {
    static final class MutableKey {
        private int id;

        MutableKey(int id) {
            this.id = id;
        }

        @Override
        public boolean equals(Object other) {
            return other instanceof MutableKey key && id == key.id;
        }

        @Override
        public int hashCode() {
            return Integer.hashCode(id);
        }
    }

    record StableKey(int id) {
    }

    public static void main(String[] args) {
        MutableKey key = new MutableKey(20);
        Map<MutableKey, String> unsafe = new HashMap<>();
        unsafe.put(key, "payload");
        System.out.println("beforeMutation=" + unsafe.get(key));
        System.out.println("hashBefore=" + key.hashCode());

        key.id = 21;
        System.out.println("hashAfter=" + key.hashCode());
        System.out.println("observedSize=" + unsafe.size());
        System.out.println("observedSameReferenceLookup=" + unsafe.get(key));
        System.out.println("observedOldIdLookup="
                + unsafe.get(new MutableKey(20)));

        boolean referenceStillSeen = false;
        for (Map.Entry<MutableKey, String> entry : unsafe.entrySet()) {
            if (entry.getKey() == key) {
                referenceStillSeen = true;
            }
        }
        System.out.println("observedReferenceInEntries=" + referenceStillSeen);

        Map<StableKey, String> safe = new HashMap<>();
        StableKey oldKey = new StableKey(20);
        StableKey newKey = new StableKey(21);
        safe.put(oldKey, "payload");

        if (safe.containsKey(newKey)) {
            throw new IllegalStateException("Target key already exists");
        }
        String moved = safe.remove(oldKey);
        safe.put(newKey, moved);

        System.out.println("safeHasOldKey=" + safe.containsKey(oldKey));
        System.out.println("safeNewKeyValue=" + safe.get(new StableKey(21)));
        System.out.println("safeSize=" + safe.size());
    }
}
```

```shell
javac --release 17 -encoding UTF-8 MapMutableKeyDemo.java
java MapMutableKeyDemo
```

Verified output:

```text

hashBefore=20
hashAfter=21
observedSize=1
observedSameReferenceLookup=null
observedOldIdLookup=null
observedReferenceInEntries=true
safeHasOldKey=false
safeNewKeyValue=payload
safeSize=1
```

### 8.1. Why Is size Still 1 Yet get Returns null?

In the verified run, the key object is still observable when iterating over entries, yet looking it up with the same reference after changing `id` fails to find it. Holding the exact reference does not make the map skip the entire hash-locating step.

Do not explain this `null` result as "the map must have deleted the data." The observed lines show otherwise: the data may still sit inside the structure, just no longer reachable via the lookup being called.

Nor should you write logic assuming that every mutated key will definitely fail to be found. Depending on the mutation, hash code, internal organization, and data, some cases might coincidentally still be found. Once the contract condition is broken, a lucky lookup does not restore the correctness of the design.

### 8.2. Changing a Key Must Be a Controlled Operation

The `safe` section leaves `StableKey(20)` intact, removes the value from the old mapping, and inserts it into a new mapping with `StableKey(21)`. The old key is not mutated into another key while stored.

The program checks whether the target key already exists because "renaming a key" can collide with an existing mapping. The application must explicitly decide whether to reject, overwrite, or merge according to business rules; do not let an accidental `put` decide silently.

This example has only a single thread owning the map, and all values are known and valid. A `remove` followed by `put` is not automatically an atomic transaction. If multiple threads are involved or rollback on error is required, an appropriate coordination mechanism must be designed.

### 8.3. Do Not Expect Automatic Self-Healing

The following are not fixes for a broken key contract:

- Switching to `LinkedHashMap`: the hash key mechanism still needs consistency.
- Switching to a concurrent map: thread-safe access does not turn a mutable key into a stable key.
- Increasing capacity or adding elements hoping the map will "rearrange itself right": there is no guarantee of restoring business identity that way.
- Caching the old hash code in the key while letting `equals` change freely: this can continue to produce an invalid identity relation.
- Wrapping the map as unmodifiable: the wrapper does not automatically freeze the key objects inside it.

If data has already been inserted with invalid keys, you must re-evaluate the data and the policy for handling duplicate identities before building a proper structure. Do not silently copy it into another map and assume all information has been recovered.

## 9. Records Help Write Keys, but Do Not Make All Data Deeply Immutable

For a key composed of stable components like `String` and `int`, a `record` is often a concise representation:

```java
// Illustrates a key type based on both item code and warehouse.
record StockKey(String sku, int warehouse) {
}
```

If not overridden, a record generates `equals` and `hashCode` based on its components. Equality requires the same record class and corresponding components being equal according to record rules.

However, a component field holding a `final` reference does not mean the referenced object cannot be modified. A `List<String>` component can point to an `ArrayList` that elsewhere still has permission to mutate. An array component also has its own equality rules that must be understood.

### Full Program: Defensive List Copy and Reference-Based Array Equality

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class MapRecordKeyDemo {
    record MutableTags(List<String> tags) {
    }

    record StableTags(List<String> tags) {
        StableTags {
            tags = List.copyOf(tags);
        }
    }

    record ArrayKey(int[] codes) {
    }

    public static void main(String[] args) {
        List<String> mutableInput = new ArrayList<>(List.of("java"));
        MutableTags unstable = new MutableTags(mutableInput);
        mutableInput.add("map");
        System.out.println("unstableTags=" + unstable.tags());
        System.out.println("unstableEqualsOneTag="
                + unstable.equals(new MutableTags(List.of("java"))));

        List<String> input = new ArrayList<>(List.of("java"));
        StableTags stable = new StableTags(input);
        Map<StableTags, String> map = new HashMap<>();
        map.put(stable, "saved");
        int initialHash = stable.hashCode();

        input.add("map");
        System.out.println("stableTags=" + stable.tags());
        System.out.println("stableHashUnchanged="
                + (initialHash == stable.hashCode()));
        System.out.println("stableLookup="
                + map.get(new StableTags(List.of("java"))));

        try {
            stable.tags().add("blocked");
            throw new AssertionError("Expected UnsupportedOperationException");
        } catch (UnsupportedOperationException expected) {
            System.out.println("stableListMutation=UnsupportedOperationException");
        }

        ArrayKey first = new ArrayKey(new int[] {1, 2});
        ArrayKey second = new ArrayKey(new int[] {1, 2});
        System.out.println("sameArrayContents="
                + Arrays.equals(first.codes(), second.codes()));
        System.out.println("arrayRecordsEqual=" + first.equals(second));

        Map<ArrayKey, String> arrayMap = new HashMap<>();
        arrayMap.put(first, "first");
        arrayMap.put(second, "second");
        System.out.println("arrayMapSize=" + arrayMap.size());
    }
}
```

### 9.1. Why Does MutableTags Still Change?

`MutableTags` holds the input list directly. After `mutableInput.add("map")`, calling the accessor sees `[java, map]`. The record's equality relation can also change because the list contents participate in the comparison.

In the program, this object is used only to observe the data and equality, without being inserted into a map. If you use it as a key and continue mutating the list like that, you risk violating the key stability condition.

The flaw is not in a record's ability to generate `equals`/`hashCode` from components. The design point to get right is whether the components have the right semantics and are stable enough to serve as identity.

### 9.2. What Does StableTags Protect?

The constructor of `StableTags` uses `List.copyOf(tags)` to retain an unmodifiable list isolated from structural changes to the input list. With immutable `String` elements, the example's identity remains stable.

After mutating `input` externally:

- `stable.tags()` is still `[java]`.
- The hash code of the same key does not change.
- A new key `StableTags(List.of("java"))` successfully looks up `"saved"`.
- Attempting to add directly through the accessor is rejected.

This approach enforces a clear policy: the list and its elements must not be `null`, per `List.copyOf` requirements. If the application has different requirements, appropriate validation and copying must be chosen.

If the list elements are mutable objects, `List.copyOf` alone does not deep-copy the elements. In that case, you must also examine which state of each element participates in `equals`/`hashCode`.

### 9.3. Why Does ArrayKey Have Two Keys Even Though the Numbers Match?

Java arrays do not define element-by-element `equals`. Two distinct `new int[] {1, 2}` arrays are not equal simply because they have the same contents.

A record uses the equality rule of its component references; it does not automatically convert arrays to deep comparisons. Therefore:

```text
sameArrayContents=true
arrayRecordsEqual=false
arrayMapSize=2
```

This is not inherently a Java contract violation. The two keys are being distinguished by array reference, and the hash code matches that equality. However, if the business rule wants "same numbers means same key," that design fails to express the requirement.

If you manually implement a key that compares arrays by content, you must pair `Arrays.equals` with an appropriate content-based hash such as `Arrays.hashCode`, while defensively copying the input and not exposing the internal array for external mutation. Fixing only `equals` while forgetting `hashCode`, or copying at construction time but returning the internal array directly for others to mutate, can still break the key.

For nested structures, determine the shallow or deep comparison level according to business rules. Do not assume an arbitrary "deep" utility will automatically choose the right identity for your data.

## 10. The Key Contract Also Depends on the Chosen Map Type

Most of this lesson uses `HashMap` and data-based equality. Do not conclude that every `Map` implementation uses `hashCode` to locate keys.

| Map Type | Key Identification Mechanism to Understand |
|---|---|
| `HashMap`, `LinkedHashMap` | Hashing combined with the key's equality relation |
| `TreeMap` | Comparison result of natural ordering or comparator |
| `IdentityHashMap` | Reference identity `==` instead of data-based equality |

### 10.1. TreeMap Uses compareTo or Comparator

In `TreeMap`, two keys whose comparison returns `0` are treated as the same key position in the tree structure. `hashCode` is not its key-locating mechanism.

To properly fulfill the general `Map` contract, the ordering relation should be consistent with `equals`: for valid keys, a comparison result of `0` should correspond to equality under `equals`.

If a comparator only compares names while `equals` compares both name and ID, two objects with different IDs but the same name can be merged by a tree map. Adding another field to the hash formula will not fix this; you must review the ordering rule.

A notable case to observe is `BigDecimal`:

- `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` is `false`, because `equals` considers both value and scale.
- `compareTo` between those two values returns `0`, because numerical ordering treats them as numerically equal.

Consequently, a hash map and a `TreeMap` using natural ordering can hold different numbers of keys. `BigDecimal` does not have a broken `equals`/`hashCode` in this case. This is a difference between equality semantics and ordering semantics that the designer must choose deliberately.

`TreeMap` still has well-defined behavior in terms of its ordering when that ordering is inconsistent with `equals`, but in that case it fails to satisfy the general `Map` contract. Do not use that case to claim the general contract no longer matters.

### 10.2. IdentityHashMap Is a Specialized Choice

`IdentityHashMap` intentionally uses `==` when comparing keys and values. Two distinct string objects with identical contents can be kept as two separate keys.

This implementation is meant for needs that require identifying **exact object instances**, such as tracking distinct nodes in an object graph. It is not a drop-in replacement for `HashMap` using business identity.

The class documentation explicitly states its intentional departure from the general `Map` equality contract. Therefore, do not pass it into an algorithm that assumes standard equality semantics without reviewing those assumptions.

### 10.3. Null Is an Implementation Policy, Not a Method Call on null

`HashMap` permits one `null` key; the map handles this case specially. It does not require the program to call `null.hashCode()` or `null.equals(...)`.

This is distinct from the contract `x.equals(null) == false` when `x` is non-`null`. Do not confuse "the map allows a null key" with being able to invoke methods on a null reference.

Some maps forbid `null` keys or values; ordered maps also depend on whether the comparator can handle keys. From the declared type `Map` alone, you cannot deduce all data-acceptance policies.

## 11. Distinguishing equals/hashCode of Keys, Entries, and the Whole Map

There are three layers with three questions:

| Layer | Question Asked by equals |
|---|---|
| Key object | Do the two objects have the same logical identity for the key type? |
| `Map.Entry` | Do the two pairs have the same key and the same value? |
| `Map` | Do the two maps have the same set of mappings? |

Confusing these layers easily leads to incomplete checks.

### 11.1. Map.Entry Checks Both Key and Value

For entries following the standard contract, equality can be expressed as:

```java
// Illustrative formula, not a standalone program.
Objects.equals(firstEntry.getKey(), secondEntry.getKey())
        && Objects.equals(firstEntry.getValue(), secondEntry.getValue())
```

An entry's hash code is defined as the XOR of the hash codes of its key and value, using `0` for a `null` component:

```java
// Map.Entry contract formula.
Objects.hashCode(entry.getKey()) ^ Objects.hashCode(entry.getValue())
```

Here `^` is Java's bitwise XOR operator, not exponentiation. `Objects.hashCode(null)` returns `0`, allowing the formula to handle null components without calling a method on null.

Equal keys with different values produce unequal entries. Two entries having the same hash code is also insufficient to conclude the entries are equal.

### 11.2. Map.equals Checks Mappings, Not Insertion Order

Under the general contract, two maps are equal if they represent the same mappings. Formally, this is defined in terms of `entrySet` equality.

Therefore, two `LinkedHashMap` instances with the same keys and values inserted in reverse order can still be equal. The order observed through an iterator is not an extra component in the definition of `Map.equals`.

Different standard implementations can also be equal if they share the same mappings. This assumes the keys, values, and implementations involved obey the general equality contract; specialized cases like `IdentityHashMap` or inconsistent orderings must be evaluated under their own stated contracts.

A map containing `"a" → null` is not equal to an empty map. Nor is it equal to a map containing only `"b" → null`. Comparing only `get` results while ignoring key presence and identity can miss this difference.

### 11.3. Map.hashCode Is the Sum of Entry Hash Codes

Under the general contract, a map's hash code is the sum of the hash codes of each entry. Addition does not depend on iteration order, matching the fact that `Map.equals` does not treat insertion order as a difference.

The result preserves the requirement:

```text
Two equal maps ⇒ same hash code.
Same hash code  ⇏ two maps are equal.
```

The sum is computed using Java `int` arithmetic. Do not replace it with an order-dependent string formula and still claim it conforms to the `Map.hashCode` contract.

### Why Is a Mutable Map Usually Unsuitable as a Key in Another Map?

A map's hash code can change when its mappings or data participating in hashing change. If you use that map as a key in an outer `HashMap` and then mutate it, you run right back into the unstable-key problem.

Similarly, mutating a mutable value inside a map might not change that map's lookup keys, but it can affect `Map.equals` or `Map.hashCode` for the whole map. You must know which layer you are talking about before concluding whether a mutation is safe for a key role.

## 12. Full Program: Equality at Each Layer and Key Policies

The following program combines three related observations:

1. Two maps with the same mappings despite different insertion orders.
2. `HashMap` and `TreeMap` identifying two `BigDecimal` keys differently according to their own mechanisms.
3. `IdentityHashMap` distinguishing two string objects that `HashMap` treats as the same logical key.

```java
import java.math.BigDecimal;
import java.util.AbstractMap;
import java.util.HashMap;
import java.util.IdentityHashMap;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Objects;
import java.util.TreeMap;

public class MapEqualityPoliciesDemo {
    public static void main(String[] args) {
        Map<String, Integer> first = new LinkedHashMap<>();
        first.put("a", 1);
        first.put("b", 2);

        Map<String, Integer> reversed = new LinkedHashMap<>();
        reversed.put("b", 2);
        reversed.put("a", 1);

        System.out.println("firstKeys=" + first.keySet());
        System.out.println("reversedKeys=" + reversed.keySet());
        System.out.println("mapsEqual=" + first.equals(reversed));
        System.out.println("mapHashesEqual="
                + (first.hashCode() == reversed.hashCode()));

        int entryHashSum = 0;
        for (Map.Entry<String, Integer> entry : first.entrySet()) {
            entryHashSum += entry.hashCode();
        }
        System.out.println("mapHashMatchesEntrySum="
                + (first.hashCode() == entryHashSum));

        Map.Entry<String, Integer> pair =
                new AbstractMap.SimpleImmutableEntry<>("a", 1);
        System.out.println("entryEquals="
                + pair.equals(Map.entry("a", 1)));
        System.out.println("entryHashMatchesXor="
                + (pair.hashCode()
                == (Objects.hashCode(pair.getKey())
                ^ Objects.hashCode(pair.getValue()))));

        BigDecimal scaleOne = new BigDecimal("1.0");
        BigDecimal scaleTwo = new BigDecimal("1.00");
        Map<BigDecimal, String> hashMap = new HashMap<>();
        Map<BigDecimal, String> treeMap = new TreeMap<>();
        hashMap.put(scaleOne, "first");
        hashMap.put(scaleTwo, "second");
        treeMap.put(scaleOne, "first");
        treeMap.put(scaleTwo, "second");

        System.out.println("decimalEquals=" + scaleOne.equals(scaleTwo));
        System.out.println("decimalCompare=" + scaleOne.compareTo(scaleTwo));
        System.out.println("decimalHashMapSize=" + hashMap.size());
        System.out.println("decimalTreeMapSize=" + treeMap.size());
        System.out.println("treeLookup=" + treeMap.get(scaleOne));

        String left = new String("id");
        String right = new String("id");
        Map<String, Integer> normal = new HashMap<>();
        Map<String, Integer> identity = new IdentityHashMap<>();
        normal.put(left, 1);
        normal.put(right, 2);
        identity.put(left, 1);
        identity.put(right, 2);

        System.out.println("stringEquals=" + left.equals(right));
        System.out.println("stringSameReference=" + (left == right));
        System.out.println("normalSize=" + normal.size());
        System.out.println("identitySize=" + identity.size());
    }
}
```

Save to `MapEqualityPoliciesDemo.java`, then compile and run:

```shell
javac --release 17 -encoding UTF-8 MapEqualityPoliciesDemo.java
java MapEqualityPoliciesDemo
```

Verified output:

```text
firstKeys=[a, b]
reversedKeys=[b, a]
mapsEqual=true
mapHashesEqual=true
mapHashMatchesEntrySum=true
entryEquals=true
entryHashMatchesXor=true
decimalEquals=false
decimalCompare=0
decimalHashMapSize=2
decimalTreeMapSize=1
treeLookup=second
stringEquals=true
stringSameReference=false
normalSize=1
identitySize=2
```

### 12.1. Map and Entry Group

`firstKeys=[a, b]` differs in order from `reversedKeys=[b, a]`, yet `mapsEqual=true` and `mapHashesEqual=true`. The line `mapHashMatchesEntrySum=true` verifies the sum of entry hash codes.

An entry constructed with `SimpleImmutableEntry` equals an entry with the same data pair from `Map.entry`. The line `entryHashMatchesXor=true` verifies the contract formula, independent of whether the two entries share the same concrete class.

### 12.2. BigDecimal Group

`decimalEquals=false`, yet `decimalCompare=0`. Therefore:

- `HashMap` keeps two keys according to `equals`, with size `2`.
- `TreeMap` using natural ordering treats a comparison result of `0` as the same key, with size `1`.
- The final value at that key position in `TreeMap` is `"second"`.

If business logic needs to distinguish scale, choose an appropriate rule and structure. If you want to normalize away a representation difference, normalization must be a deliberate business decision applied consistently to both writes and lookups. Do not erase data differences just to make different maps report the same size.

### 12.3. Reference Identity Group

The two strings `left` and `right` have the same content but are different objects:

```text
stringEquals=true
stringSameReference=false
normalSize=1
identitySize=2
```

There is no contradiction: the two maps are applying two different key-identification policies. Choosing the right policy is part of the design, not just picking a class name.

## 13. Design Decisions to Make Before Writing a Hash Formula

### Choose the Right Identifying Components

In multi-tenant data, the same account code in two organizations may be two distinct keys; the key needs to represent the organization as well if that is the business rule. The same applies to inventory with the same item code across two warehouses.

Conversely, descriptive information that changes frequently, such as a display name or notes, probably belongs in the value rather than accidentally changing a key's identity.

Not every attribute of a data object needs to participate in `equals`. However, the chosen attributes must accurately describe equality for **that type**. If the same object must be compared by different criteria in different contexts, separate specialized key types or comparators rather than letting `equals` vary by external context.

### Inheritance Must Preserve Symmetry and Transitivity

A superclass considering two objects equal by an ID while a subclass demands an additional attribute can cause a situation where parent equals child but child does not equal parent.

There is no single "always use instanceof" or "always use getClass" rule that solves every model. You must determine whether the classes belong to the same equality domain and preserve the contract for all related pairs.

For small value-key types, designing them as `final`, `record`, or using composition usually avoids this difficulty. If subclassing a key type is allowed, you must actively verify the relationship between superclass and subclass.

### Normalization Must Belong to the Data Rules

If a key code is meant to be case-insensitive, whitespace-insensitive, or normalized from a special representation, decide on the canonical representation before storing and looking it up. Do not normalize only inside `hashCode` while keeping a different rule in `equals`.

Nor should you automatically trim whitespace or change case for every code when business rules do not allow it: seemingly cosmetic differences may be a meaningful part of the identity.

### Approximate Comparisons Are Usually Not Valid equals

A rule like "two numbers within a threshold are equal" may fail transitivity. For instance, with threshold `1`, `0` is close to `0.75`, `0.75` is close to `1.5`, yet `0` is not close to `1.5`.

That can be a useful proximity check, but it should not be placed directly into a map key's `equals` as an equivalence relation. If you need to group data by buckets or ranges, design an explicit bucket identifier and verify the grouping semantics.

## 14. Verifying a Key Class

Testing once with the exact object just inserted into the map is far too weak. At a minimum, verify the following scenario groups:

| Group | What to Verify |
|---|---|
| Two distinct objects with the same identity | Two-way `equals` is true, hash codes are equal |
| Three objects with the same identity | Transitivity |
| Differing in one identifying component | Not equal according to business requirements |
| Null and unrelated types | Do not cause false equality interpretations |
| Valid hash collision | Two different keys still keep two mappings and look up accurately |
| Write with one key, read with a new equivalent key | Looks up the exact mapping |
| Overwrite with an equivalent key | Replaces value; does not increase logical key count |
| Defensive copy of input data | Mutating input does not alter stored identity |
| Superclass/subclass if any | Symmetry and transitivity still hold |
| Comparator if using an ordered map | Comparison result of 0 matches chosen semantics |

Verify correctness before measuring performance. A well-distributed hash function cannot save a broken `equals`; a correct `equals` is also insufficient for a hash map if the hash code is inconsistent.

If you need to measure performance, use appropriate data and benchmarking methods. Do not take a few `println` lines or a tiny timing run as proof that one hash formula is superior to all other choices.

### When get Unexpectedly Returns null, What Order Should You Check?

1. Are you sure you are using the right map and key type, and nothing removed or modified the data elsewhere?
2. Are the two keys you expect to be the same truly `equals` in both directions?
3. Do they have the same hash code while in use?
4. Has any field or sub-object participating in identity been mutated?
5. Did you accidentally write an overload `equals(MyKey)` instead of overriding `equals(Object)`?
6. Is the map using a comparator or reference identity instead of the mechanism you assumed?
7. If the map permits `null` values, have you distinguished a mapping with a null value from a missing key using `containsKey` where needed?

This checklist helps separate identity bugs from operational bugs or wrong assumptions about the map type. It does not turn multiple consecutive method reads into an atomic operation; if data is shared across threads, you must also consider timing and coordination mechanisms.

## 15. Self-Check and Explanations

### Question 1: Does Equal Hash Mean Equal Keys?

Two keys have `hashCode() == 0`, yet `equals` returns `false`. Is that a contract violation? Must a hash map keep only one key?

**Answer:** It is not a violation on that basis alone. This is a valid hash collision; the map can keep both mappings and must distinguish them by equality when all other contract conditions are met.

### Question 2: Equal by equals, Different Hash Codes

Two objects share the same business code, `equals` returns `true`, yet their hash codes differ. Can you require `HashMap` to scan every element so it still finds the right one?

**Answer:** No. The key class violates the requirement that equal objects have equal hash codes. The map is allowed to use hashes to skip candidates; the key class must be fixed.

### Question 3: Only equals, No hashCode

A class overrides `equals` by `id` while keeping `Object.hashCode`. Is using two separate objects with the same `id` in a hash map guaranteed to match business intent?

**Answer:** There is no basis to guarantee the hash contract is upheld. Normally, you must override `hashCode` consistently with `equals`; test with two separate objects, not just the same reference.

### Question 4: Mutating a Key but Using the Exact Old Reference

A key object changes a field participating in hashing after being stored. Is `get(key)` guaranteed to find it because `key` is still the exact old object?

**Answer:** No. Lookup still relies on the locating mechanism. More importantly, the key stability condition has been violated; expected behavior is no longer generally guaranteed.

### Question 5: A Record with a List

Does `record Key(List<String> parts)` automatically protect against the caller mutating the input list?

**Answer:** No. A record holds the component reference; if you need stable content-based identity, you must control or defensively copy the list and also consider the elements inside it.

### Question 6: A Record with an Array

Two `record Key(int[] parts)` instances are constructed with two different arrays that have the same contents. Are they automatically equal element-by-element?

**Answer:** No. Arrays use reference-based `equals`; a record does not automatically turn that into content comparison. If content semantics are desired, you must design appropriate equality, hash code, and data protection.

### Question 7: Changing Insertion Order

Two maps obeying the general contract contain the same mappings but were inserted in different orders. Does that force `Map.equals` to return `false`?

**Answer:** No. `Map.equals` checks the set of mappings; it does not include insertion order in its definition of equality.

### Question 8: Comparing Only Keys When Comparing Entries

Two entries have the same key but different values. Are they equal merely because they have the "same key"?

**Answer:** No. `Map.Entry.equals` checks both key and value. This is a different layer from key-only equality.

### Question 9: Does TreeMap Need hashCode to Locate Keys?

Two keys compare to `0` under a comparator but are not `equals`. Will adding a different hash formula make `TreeMap` keep them in two separate positions?

**Answer:** No. `TreeMap` identifies key positions via ordering comparison. You must review the comparator and the requirement for consistency with `equals`, not fix the wrong place with hash codes.

### Question 10: IdentityHashMap and Strings

Two strings with the same content but different object instances are put into an `IdentityHashMap`. Why can it retain two mappings?

**Answer:** The class uses reference identity `==`, rather than merging two objects simply because `String.equals` returns `true`. This is a specialized choice with a documented difference from the general contract.

### Question 11: Does Changing a Map's Value Change Its Lookup Key?

`Map<StockKey, List<String>>` has stable keys. Does mutating a value list automatically change `StockKey.hashCode`?

**Answer:** No, if `StockKey` is designed independently of that list. However, the content and hash code of the overall map can be affected because `Map.hashCode` considers entries. If the map itself is used as a key elsewhere, that is a separate risk.

### Question 12: Hash Codes Differing Across Runs

Should you persist the `hashCode` of a custom key and use that number as a durable identifier across future restarts?

**Answer:** You should not. The general contract provides no such guarantee, and collisions can still occur. Persist the actual data identifier in an appropriate format.

## 16. Practice: Inventory Key by Item Code and Warehouse

Design an immutable key type consisting of `sku` and `warehouse`, then write a verification program:

1. Create two distinct objects with the same `sku="PEN"`, `warehouse=1`.
2. Verify they are equal in both directions, have the same hash code, but do not share the same reference.
3. Store quantity `10` with the first key, then store `15` with the second key.
4. Verify the old value returned on the overwrite is `10`, and the size remains `1`.
5. Look up using a new equivalent key and receive `15`.
6. Add a key with the same `sku` but `warehouse=2`, and verify the size becomes `2`.
7. Verify there is no way to mutate the key-defining data through any references exposed by the class.
8. If using a collection component, add a test verifying that mutating the input does not affect the created key.

Afterward, write a counterexample solely for learning: have `equals` ignore `warehouse` while `hashCode` uses it. Before even testing a map, immediately find a pair of keys proving "equal yet different hash codes." Identifying the violation at the class level helps avoid the misconception that the bug only appears after choosing a specific map.

When finished, revert to the correct key version; do not leave the broken counterexample as application key code. All lookup expectations must rest on an upheld contract rather than a coincidental run that happened to yield a favorable result.
