# Measuring Java Collections Performance with JMH: Data, Warmup, and Fair Comparisons

## 1. Measurement Goals and Questions

The `Java Microbenchmark Harness` (JMH) is an OpenJDK tool for measuring Java operations that are small enough for JIT compilation, code optimizations, GC, JVM startup, and system noise to skew manual measurements. In the `Java core - collection` module, we use JMH to answer a specific question: **given a fixed dataset and query pattern, how does the element lookup time of `ArrayList.contains` differ from that of `HashSet.contains`?**

This lesson distinguishes three aspects:

- **Functional correctness:** both data structures must return the same result for the same key; all probe keys either exist (hit) or do not exist (miss) according to the scenario.
- **Measurement scope:** the benchmark below measures only `contains` along with the cost of retrieving the query key; creating the collection, populating data, and generating probe keys are performed in `@Setup`, outside the measured region.
- **Engineering decision:** the result of a single lookup operation is not enough to choose between `List` and `Set`. You must also consider ordering, duplicate elements, construction/update costs, memory footprint, cache locality, and the read/write ratio in the application.

From an algorithmic perspective, a single `ArrayList.contains` call performs a linear scan with O(n) worst-case complexity; `HashSet.contains` typically achieves an average cost close to O(1) with a good hash function and key distribution, though O(1) is not guaranteed in every case. JMH tests performance **under the measured conditions**; it does not prove that every input or every machine will exhibit the same relative speedup or slowdown.

## 2. Designing the Comparison Before Running

Formulate a hypothesis: as collection size grows, hash-based lookup may become more advantageous than a linear scan; for small collections, the fixed overhead of hashing and memory layout may affect the difference. Keep the following variables transparent:

| Variable | Example Design | Why It Must Be Controlled |
| --- | --- | --- |
| Element count (`size`) | 128, 8,192, 65,536 | Shows how performance scales with size and avoids drawing conclusions from a single size. |
| Lookup case (`scenario`) | `hit` and `miss` | `ArrayList` can terminate early upon finding a match; a miss typically requires scanning the entire list. |
| Stored data | Unique `Integer` values from 0 to `size - 1` in both collections | Ensures identical logical content and eliminates differences caused by input data. |
| Probe keys | 1,024 keys generated by `Random` with a fixed seed; hits are inside the collection, misses are outside | Varies keys across calls while keeping the experiment reproducible. |
| Environment | Same JDK, JVM options, CPU, thread count, forks, and machine load conditions | Minimizes noise from external factors. |
| Work per invocation | Retrieving one key and calling `contains` once | Compares the exact same task without mixing in data generation overhead. |

Do not directly compare `ArrayList.get(index)` with `HashSet.contains(value)`: those represent two different operations. Similarly, do not compare `new HashSet<>(list).contains(x)` with `list.contains(x)` and call the result **lookup** speed; the first approach includes the cost of building the hash structure. If your real business logic genuinely creates a set for a one-off lookup, measure **that entire workflow** in a separate benchmark.

## 3. Creating a Properly Configured JMH Project

Requirements: JDK 17 or later, Maven, and access to download dependencies from Maven Central. Use the official JMH Maven archetype so that the annotation processor and standalone uber-JAR are configured properly; this example pins JMH version 1.37 for reproducibility.

~~~bash
mvn archetype:generate -B -DarchetypeGroupId=org.openjdk.jmh -DarchetypeArtifactId=jmh-java-benchmark-archetype -DarchetypeVersion=1.37 -DgroupId=org.sample -DartifactId=collection-jmh -Dversion=1.0-SNAPSHOT
cd collection-jmh
~~~

Create the file `src/main/java/org/sample/CollectionLookupBenchmark.java` with the complete contents below. The sample class generated by the archetype can be left as is: when running, we will filter specifically for this benchmark.

## 4. Complete Java Benchmark

~~~java
package org.sample;

import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Random;
import java.util.Set;
import java.util.concurrent.TimeUnit;

import org.openjdk.jmh.annotations.Benchmark;
import org.openjdk.jmh.annotations.BenchmarkMode;
import org.openjdk.jmh.annotations.Fork;
import org.openjdk.jmh.annotations.Level;
import org.openjdk.jmh.annotations.Measurement;
import org.openjdk.jmh.annotations.Mode;
import org.openjdk.jmh.annotations.OutputTimeUnit;
import org.openjdk.jmh.annotations.Param;
import org.openjdk.jmh.annotations.Scope;
import org.openjdk.jmh.annotations.Setup;
import org.openjdk.jmh.annotations.State;
import org.openjdk.jmh.annotations.Warmup;

@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1, timeUnit = TimeUnit.SECONDS)
@Measurement(iterations = 5, time = 1, timeUnit = TimeUnit.SECONDS)
@Fork(2)
public class CollectionLookupBenchmark {

    @State(Scope.Thread)
    public static class LookupData {
        @Param({"128", "8192", "65536"})
        public int size;

        @Param({"hit", "miss"})
        public String scenario;

        List<Integer> list;
        Set<Integer> set;
        Integer[] probes;
        int position;

        @Setup(Level.Trial)
        public void prepare() {
            list = new ArrayList<>(size);
            set = new HashSet<>();

            for (int i = 0; i < size; i++) {
                Integer value = Integer.valueOf(i);
                list.add(value);
                set.add(value);
            }

            Random random = new Random(2026L + size);
            probes = new Integer[1024];

            for (int i = 0; i < probes.length; i++) {
                int selected = random.nextInt(size);
                int key = scenario.equals("hit") ? selected : size + selected;
                probes[i] = Integer.valueOf(key);
            }
        }

        Integer nextProbe() {
            return probes[position++ & (probes.length - 1)];
        }
    }

    @Benchmark
    public boolean arrayListContains(LookupData data) {
        return data.list.contains(data.nextProbe());
    }

    @Benchmark
    public boolean hashSetContains(LookupData data) {
        return data.set.contains(data.nextProbe());
    }

    @Benchmark
    public Integer probeOnly(LookupData data) {
        return data.nextProbe();
    }
}
~~~

**Why is it written this way?**

1. `@State(Scope.Thread)` instructs JMH to allocate a separate state instance for each benchmark thread. The collections are read-only, while `position` is mutated within the same thread; no cross-thread write contention occurs. The collections are re-initialized for each trial.
2. `@Param` creates a matrix of **3 sizes × 2 scenarios** for each benchmark. We examine each pair with matching parameters before comparing the two data structures.
3. `@Setup(Level.Trial)` populates the data **before measurement begins**. Therefore, the results do not include the time to construct the `HashSet` or `ArrayList`. If the question is construction cost, a dedicated construction benchmark is required.
4. A fixed seed keeps the input data consistent across runs and between the two alternatives. Because `probes` is pre-populated as an `Integer[]`, boxing and random number generation are excluded from the `contains` timing; both alternatives query the exact same key instances.
5. Each `nextProbe()` call cycles through 1,024 positions using a bitwise AND because 1,024 is a power of two. The key varies across invocations, avoiding the pitfall of measuring a single constant value. The benchmark still includes fetching the key and incrementing `position`; this is a shared baseline overhead, which is especially notable when the lookup operation itself is very fast.
6. `hit` uses keys in the range from 0 to `size - 1`; `miss` uses keys from `size` to `2 × size - 1`. Consequently, every call within each scenario returns a deterministic logical outcome: `true` or `false`, identical for both `List` and `Set`.
7. Each `@Benchmark` method **returns its result** so that JMH consumes it, reducing the risk that the JIT compiler eliminates the computation because its result is unused (*dead-code elimination*). If multiple results need to be consumed within a single benchmark invocation, you can inject a `Blackhole` and call `consume`.
8. `probeOnly` serves as a reference measurement for the key selection work. You must not simply subtract its score directly from the `contains` score and treat the difference as the exact lookup latency: JIT compilation, inlining optimizations, and invocation overhead can differ across benchmarks.

### Annotations That Affect Measurement

- `@BenchmarkMode(Mode.AverageTime)`: reports the **average time per operation** (lower is better when semantics are equivalent). For throughput, use `Mode.Throughput` and read the unit in operations per time unit (where higher is better).
- `@OutputTimeUnit(TimeUnit.NANOSECONDS)`: formats results as `ns/op`; it does not guarantee that the underlying hardware timers have absolute single-nanosecond precision.
- `@Warmup(iterations = 5, time = 1)`: runs 5 warmup iterations of 1 second each; warmup data is excluded from the final score. This gives the JVM time to load classes and lets the JIT compiler compile and optimize hot execution paths.
- `@Measurement(iterations = 5, time = 1)`: follows up with 5 measurement iterations of 1 second each per parameter combination and fork.
- `@Fork(2)`: executes the benchmark in 2 separate child JVM processes, reducing sensitivity to the state of any single JVM run. Use more forks/iterations when higher confidence is needed, trading off longer execution time.

Warmup is **not equivalent** to running a single trial loop with `System.nanoTime()`. The JIT compiler may recompile code as execution profiles evolve; allocation and GC can also affect behavior. JMH controls warmup iterations, measurement iterations, forking, and sampling mechanics, but the benchmark author is still responsible for choosing a realistic workload.

## 5. Building and Running the Benchmark

From the `collection-jmh` directory:

~~~bash
mvn clean verify
java -jar target/benchmarks.jar "CollectionLookupBenchmark.*" -t 1 -wi 5 -i 5 -w 1s -r 1s -f 2 -rf json -rff target/jmh-results.json
~~~

Meaning of key CLI arguments:

- `"CollectionLookupBenchmark.*"` selects only the three benchmarks in this class, skipping the default sample benchmark generated by the archetype.
- `-t 1` runs a single benchmark thread, reducing noise from CPU contention. To evaluate concurrent access, you must design a dedicated benchmark with appropriate state scope and contention levels.
- `-wi 5 -w 1s` configures 5 warmup iterations of 1 second each; `-i 5 -r 1s` configures 5 measurement iterations of 1 second each. CLI options override the defaults specified in annotations.
- `-f 2` uses 2 JVM forks; `-rf json -rff ...` writes machine-readable results to `target/jmh-results.json`.
- To test a single parameter combination, you can append `-p size=8192 -p scenario=hit` to the command above. Use the `-h` flag on the JAR to view all available flags for the JMH version in use.

Before the main experiment, run a short smoke test with fewer iterations to catch configuration errors; never draw performance conclusions from smoke-test scores. For official measurements, run on a relatively quiet machine, avoid heavy background builds or tasks, and document the hardware configuration and Java environment. Monitor CPU thermal throttling, power-saving modes, clock frequency, available RAM, and GC activity when datasets are large.

You can also re-run with JMH's built-in GC profiler:

~~~bash
java -jar target/benchmarks.jar "CollectionLookupBenchmark.*" -t 1 -f 2 -prof gc
~~~

The `gc.alloc.rate.norm` metric shows the number of bytes allocated per operation under the measured conditions. It does not directly measure the total memory footprint occupied by the collection built during `@Setup`; to evaluate actual memory footprint, combine this with a dedicated, controlled memory measurement tool.

## 6. Reading Results and Drawing Sound Conclusions

JMH outputs a summary table with columns such as `Benchmark`, parameters `size`/`scenario`, `Mode`, `Cnt`, `Score`, `Error`, and `Units`. With `avgt` and `ns/op`, compare `arrayListContains` against `hashSetContains` **under the exact same size, hit/miss scenario, JDK, configuration, and execution conditions**. Two sets of measurements taken under different conditions do not constitute a controlled comparison.

You can compute the ratio `Score(list) / Score(set)` when both measure the same operation and have positive, sufficiently stable scores; a ratio greater than 1 indicates that `HashSet` has a lower average time (is faster) **in that specific measured case**. Always report the raw scores, variance/error estimates, and iteration count—do not merely report "X times faster". If the difference is on the same order of magnitude as the measurement noise, increase the iteration/fork count, inspect the variance across forks, and re-run in a cleaner environment before drawing conclusions. `Error` should not be interpreted as a guarantee that the exact same numbers will be reproduced on different hardware.

When interpreting the output, answer these questions in order:

1. **How does `size` affect the results?** For linear scans, a miss typically requires proportionally more comparisons as `n` grows. Hash lookup tends to stay more stable, though it still depends on hash quality, CPU cache behavior, collisions, and memory traffic.
2. **How does `hit` differ from `miss`?** A list hit can terminate at any index; a list miss must scan to the end. Set hits and misses exhibit different characteristics in terms of hash probing, key equality checks, and branch prediction.
3. **Is `probeOnly` significant?** If key retrieval takes up a large fraction of the total lookup time, very fast operations become hard to distinguish from baseline overhead. When necessary, you can design a benchmark that performs multiple operations per invocation and normalize with `@OperationsPerInvocation`, taking care not to trigger loop optimizations that distort the measurement.
4. **Which data structure fits the application?** If you frequently test membership against a stable dataset and can accept the extra memory overhead, `HashSet` is a strong candidate. If you need to preserve insertion order, allow duplicates, or work with very small collections, `ArrayList` may be more appropriate. Never equate `contains` performance with the overall performance of every operation on a collection.

**Distinguishing microbenchmarks from end-to-end benchmarks:** JMH answers only the narrowly defined task you code into it. Production deployment decisions also require representative production data, end-to-end latency, real-world throughput, memory footprint, GC behavior, insertion/removal costs, correctness, and concurrency characteristics.

## 7. Common Pitfalls and How to Fix Them

| Pitfall | Consequence | Proper Approach |
| --- | --- | --- |
| Running `System.nanoTime()` once and drawing a conclusion | Skewed by JVM startup, JIT compilation, GC, and OS scheduling noise | Use JMH with controlled warmup iterations, measurements, and forks. |
| Passing a single constant value and ignoring the return value | JIT may constant-fold or eliminate the dead computation | Use an array of pre-generated probe keys and return the result or pass it to a `Blackhole`. |
| Calling `Random`, loading data, logging, or printing to the console inside `@Benchmark` | Measures unrelated work; I/O dominates the target operation | Move fixture preparation into `@Setup(Level.Trial)` when measuring lookup only. |
| Giving each candidate different datasets or different hit ratios | Different workloads make the comparison invalid | Use the exact same generation rules, seed, sizes, and scenarios. |
| Measuring a single tiny `size` and generalizing to all scales | Misses complexity scaling with `n` and CPU cache effects | Test multiple sizes representative of real data. |
| Comparing `List.get` against `Set.contains`, or ignoring set construction cost | Compares different operations and leads to false conclusions | Keep the measured operation identical; add a separate end-to-end benchmark if needed. |
| Mechanically resetting state with `@Setup(Level.Invocation)` | Per-invocation setup overhead and measurement pitfalls can heavily distort short operations | Choose the appropriate setup level; read JMH's documentation on `@Setup(Level.Invocation)` caveats for very short operations. |
| Running alongside a heavy IDE, high CPU load, or switching JDKs mid-experiment | System noise and different JIT compilers skew comparisons | Run from the standalone executable JAR, record configuration details, and control the environment. |
| Looking only at the mean score while ignoring forks and error margins | Easy to pick a winner based on an unstable measurement | Inspect variance across forks, repeat runs, and re-verify when differences are small. |
| Assuming the lowest `ns/op` is optimal for the entire system | Ignores RAM footprint, construction cost, writes, concurrency, and GC pressure | Combine JMH microbenchmarks with profiling and realistic application-level benchmarks. |

## 8. Process for Comparing Other Collections

When switching to `HashMap`/`TreeMap`, `ArrayList`/`LinkedList`, or `HashSet`/`TreeSet`, start with **a shared behavior that has identical semantics** (for example, looking up the same key or iterating over the exact same dataset), and then clearly define the dataset, sizes, hit/miss distribution, initialization method, operation count, execution order, thread count, and target metric. Generate representative test fixtures outside the measured window; write separate functional tests to verify correctness before benchmarking; configure adequate JMH warmup, measurement, and fork settings; and finally interpret the scores in the context of your workload and engineering trade-offs.

When multiple cost dimensions matter, create **multiple benchmarks with explicit scopes**: one benchmark for lookup on a pre-built structure, one for building the structure, one for updates/mutations, and a mixed-workload benchmark reflecting your application's actual operation ratios. Never lump them into a single number and declare a universal "fastest collection".
