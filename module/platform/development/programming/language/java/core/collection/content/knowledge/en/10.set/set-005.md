# Deduplicating While Preserving the Desired Order

"Deduplication" only answers how many representatives to keep for an equivalence group. It does not answer what order those representatives must appear in.

Given the input:

~~~text
B, A, B, C, A
~~~

there are at least three reasonable results depending on the requirement:

| Rule | Result |
|---|---|
| Keep the first occurrence, in first-seen order | B, A, C |
| Keep by last-occurrence position | B, C, A |
| Unique values in alphabetical order | A, B, C |

All three have no duplicate elements, yet they are not interchangeable. Picking an arbitrary `Set` and seeing the right members does not prove that the order is right.

This lesson explains how to combine duplicate criteria, representative selection, and output order; the examples run on Java 17 and later.

## 1. Separate three decisions before choosing a structure

### 1.1. What counts as a duplicate?

Two strings may be considered duplicates by exact content. Two records may be considered duplicates by a business key, even when the remaining fields differ.

A normalization rule may also be applied before comparison, such as handling whitespace or letter-casing conventions. In that case, you must specify what the normalized key is and whether the original display data is preserved.

`LinkedHashSet` and `HashSet` use the `equals/hashCode` contract to manage membership. `TreeSet` relies on ordering comparison. Do not switch structures without checking whether the definition of a duplicate changes along with it.

### 1.2. Which representative in a duplicate group should be kept?

If two records share the same key but have different names, you might need to keep:

- The first record.
- The last record.
- The record with the latest version.
- A result aggregated from the entire group.

This is a data-selection rule, not just an ordering rule. A set that deduplicates whole objects does not automatically know how to select by key or version.

### 1.3. In what order should the representatives be arranged?

You might need first-seen order, last-seen order, ascending order by key, or a display criterion.

For example, "keep the last record while preserving the order in which keys were first seen" is completely different from "keep the last record and order by last-seen position".

It helps to state the contract with all three parts:

~~~text
deduplicate by key
keep data from the last occurrence
order keys by first appearance
~~~

A requirement stated like that makes choosing the algorithm much clearer than a vague "put it into a set to deduplicate".

## 2. Preserving first-occurrence order with LinkedHashSet

`LinkedHashSet` both tracks uniqueness and maintains insertion order for iteration.

An illustrative method body:

~~~java
List<String> input = List.of("B", "A", "B", "C", "A");
Set<String> unique = new LinkedHashSet<>(input);
List<String> result = new ArrayList<>(unique);
~~~

The result is `[B, A, C]`.

### 2.1. Mechanism while iterating the input

| Element being read | Already present? | Order in LinkedHashSet after this step |
|---|---|---|
| B | No | B |
| A | No | B, A |
| B | Yes | B, A |
| C | No | B, A, C |
| A | Yes | B, A, C |

A new element is placed at the end of the insertion order. Re-adding an equivalent element that is already present does not create a new member and does not move it to the end.

That is the guarantee of [LinkedHashSet Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashSet.html): re-inserting an existing member does not affect insertion order.

### 2.2. Re-adding is not "most recently used"

After having `[B, A, C]`, calling `add("A")` returns `false` and the order remains B, A, C.

Do not use `LinkedHashSet.add` as an automatic command to mark "the element just appeared, so move it to the end". If you need that behavior, you must use a different algorithm, such as removing and then re-adding.

### 2.3. Why not use HashSet and then convert to List?

`HashSet` has no contract to preserve insertion order. According to [HashSet Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashSet.html), iteration order is not guaranteed and may change.

If you use:

~~~java
List<String> result = new ArrayList<>(new HashSet<>(input));
~~~

the result has unique members, but you must not rely on it to preserve input order.

One run happening to print B, A, C does not make it a guarantee. Do not write tests or business logic that depend on the observed order of a `HashSet`.

### 2.4. LinkedHashSet only preserves the order it actually receives

If the original source is a structure without an ordering contract, the `LinkedHashSet` constructor records the source's iteration order at the time of copying. It cannot recover prior insertion history that is no longer provided.

An ordered input is a precondition for the "preserve occurrence order" problem. If you need repeatable, deterministic results across runs, you need a source with a defined order or a sorting step using a complete criterion.

## 3. Preserving last-occurrence order

If you need results ordered by last-occurrence position, you can iterate from left to right, removing the old member and re-adding it each time:

~~~java
Set<String> lastOrder = new LinkedHashSet<>();
for (String value : input) {
    lastOrder.remove(value);
    lastOrder.add(value);
}
~~~

With the input B, A, B, C, A:

| Read up to | Order after removing old and re-adding |
|---|---|
| B | B |
| A | B, A |
| B | A, B |
| C | A, B, C |
| A | B, C, A |

Each retained element sits at the position corresponding to its most recent encounter in the portion of input processed so far. At the end of the loop, the order is the order of last occurrences.

### 3.1. Choosing the last representative and changing position are two effects

For equal values that are distinct objects, removing the old one and re-adding also replaces the representative object with the object from the current occurrence.

If you only call `add` without removing, the equivalent element is rejected and the retained representative is not automatically updated with the new data.

Therefore, check whether the intent is:

- Only replace the representative data while keeping the old position.
- Or replace the representative data and move its position to the last occurrence.

For business data deduplicated by key, a `Map` usually expresses these two choices more clearly; a later section illustrates this.

### 3.2. Do not perform this operation while iterating over the same set

The loop above iterates over a separate input source and mutates the result set. It does not iterate over `lastOrder` while removing from and adding to itself through separate calls.

Keeping the source and result separate avoids losing iteration position and avoids invalid structural modifications to the iterator. This lesson focuses on a single thread; do not treat the `remove` then `add` pair as atomic across multiple threads.

## 4. When you want sorted order: TreeSet or deduplicate then sort a List

### 4.1. TreeSet does not preserve input order

With the sequence B, A, B, C, A:

~~~java
Set<String> sorted = new TreeSet<>(input);
~~~

the iteration result is A, B, C in the natural order of strings.

This is appropriate when the requirement is members in sorted order, not preserving encounter order. The [TreeSet Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/TreeSet.html) documentation describes using natural order or a `Comparator` to organize the tree.

For strings, Java's natural order is not automatically synonymous with dictionary order in every language. If an application needs locale-specific rules, you must design an appropriate comparator rather than assuming Unicode order meets the requirement.

### 4.2. TreeSet's comparator also determines which elements are kept

A common pitfall is using a comparator that only compares one attribute, such as string length:

~~~java
Set<String> byLength = new TreeSet<>(Comparator.comparingInt(String::length));
~~~

If you add pear and plum, both have length 4 so the comparator returns 0. The tree treats them as equivalent and keeps only one element, even though `"pear".equals("plum")` is false.

If the requirement is "words with distinct content, sorted by length", the approach above has changed the deduplication criterion and dropped a word that needed to be kept.

`TreeSet`'s ordering must be consistent with `equals` to fully satisfy the general `Set` contract. The length-only comparator in the example illustrates a design that does not satisfy that requirement for strings.

### 4.3. Separate deduplication from display order when the two criteria differ

You can deduplicate by `equals/hashCode` first, and then sort the resulting list:

~~~java
List<String> result = new ArrayList<>(new LinkedHashSet<>(words));
result.sort(Comparator.comparingInt(String::length)
        .thenComparing(Comparator.naturalOrder()));
~~~

With `[pear, fig, plum, fig]`, the result is `[fig, pear, plum]`.

Both pear and plum are kept because having equal length is no longer a reason to deduplicate. Comparing by name in the second step also clearly defines the order of words with the same length.

If you only use a length comparator when sorting a `List`, elements that are equal according to the comparator are not removed. This is the difference between **sorting a list** and **using ordering to determine TreeSet membership**.

If you do not want to specify a secondary order yourself, a stable sort can preserve the previous order of elements that tie on the criterion. However, when the source does not have a stable order and the result must be repeatable, a complete secondary criterion is usually necessary.

## 5. Deduplicating by business key while keeping the right representative and order

Suppose the input consists of records:

~~~text
B:b1, A:a1, B:b2, C:c1, A:a2
~~~

The part before the colon is the key, and the part after is the data. For key B there are two different records.

If a record has two components `key` and `detail`, the record's default `equals` compares both components. Creating a `LinkedHashSet<Row>` does not automatically make it "unique by key"; both B:b1 and B:b2 remain distinct.

### 5.1. Keep the first record by key

Use a set only to check keys, while the result is a list:

~~~java
Set<String> seenKeys = new HashSet<>();
List<Row> result = new ArrayList<>();

for (Row row : rows) {
    if (seenKeys.add(row.key())) {
        result.add(row);
    }
}
~~~

Result: `[B:b1, A:a1, C:c1]`.

The membership-checking set does not need to be ordered, because we do not use it as the output iteration source. The result list receives elements directly from the ordered iteration loop.

This is an important example: you can use `HashSet` in an algorithm that still preserves order, as long as the order lives in the result structure and is not taken from iterating over the `HashSet`.

### 5.2. Keep the last record, in first-seen key order

Use a default `LinkedHashMap` and overwrite the value by key:

~~~java
Map<String, Row> byKey = new LinkedHashMap<>();
for (Row row : rows) {
    byKey.put(row.key(), row);
}
List<Row> result = new ArrayList<>(byKey.values());
~~~

Result: `[B:b2, A:a2, C:c1]`.

B and A receive the new data, but the key positions still follow first key insertion: B, A, C. Replacing the value of an existing key does not automatically move that key to the end in a default `LinkedHashMap`.

This is the insertion-order policy, as opposed to the access-order mode that can be configured on `LinkedHashMap`. This lesson uses the default constructor, per [LinkedHashMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashMap.html).

### 5.3. Keep the last record, in last-seen key order

If on each read you remove the old key and put it again:

~~~java
Map<String, Row> byKey = new LinkedHashMap<>();
for (Row row : rows) {
    byKey.remove(row.key());
    byKey.put(row.key(), row);
}
List<Row> result = new ArrayList<>(byKey.values());
~~~

the result is `[B:b2, C:c1, A:a2]`.

The representative data is still the last record. The difference is that the key is moved to the end each time it reappears.

### 5.4. Policy table for the same source

| Policy | Output data |
|---|---|
| First record, first-seen key order | B:b1, A:a1, C:c1 |
| Last record, first-seen key order | B:b2, A:a2, C:c1 |
| Last record, last-seen key order | B:b2, C:c1, A:a2 |

Do not name a helper "deduplicate" and leave callers guessing which row in the table is its contract. The name and documentation should clearly state the representative-selection rule and the ordering rule.

If you need the "latest version", the last occurrence only corresponds to the latest version when the source already satisfies an appropriate ordering precondition. If data arrives out of version order, you must compare versions using a dedicated rule.

## 6. Streams: distinct preserves order when the source is ordered

### 6.1. distinct on an ordered stream

With an ordered `List` source:

~~~java
List<String> result = input.stream().distinct().toList();
~~~

`distinct` uses `equals` to identify duplicate elements. For an ordered stream, it preserves the first-occurring representative in **encounter order**, as described in [Stream.distinct Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/stream/Stream.html#distinct()).

The result for the source B, A, B, C, A is `[B, A, C]`.

"Ordered" here does not mean the values are sorted in ascending order. It means the source and preceding operations define an encounter order that the pipeline must respect.

### 6.2. The collect target must also have an ordering contract

If you want a set in encounter order:

~~~java
Set<String> result = input.stream()
        .collect(Collectors.toCollection(LinkedHashSet::new));
~~~

The specified collector creates a `LinkedHashSet` and accumulates elements in encounter order. By contrast, `Collectors.toSet()` is an unordered collector with no contract to return a `LinkedHashSet`.

Per [Collectors Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/stream/Collectors.html#toCollection(java.util.function.Supplier)), `toCollection` lets you specify the collection type to use. If ordering is required, do not just check the `distinct` step and overlook the final result type.

### 6.3. Parallel does not automatically lose order, but unordered has its own meaning

An ordered stream running in parallel must still satisfy the stability contract of `distinct` if the ordering constraint is not dropped. The complete example verifies the parallel pipeline result against the sequential pipeline.

However, preserving stability during a parallel distinct can require significant coordination and buffering. Do not assume calling `parallelStream` will be faster for deduplication.

If the source has no encounter order, or if `unordered()` is called, there is no longer a guarantee of keeping the first representative in a previously desired order. `unordered()` allows dropping the ordering constraint; it is not a request to produce a specific random order.

### 6.4. Do not use shared state to simulate distinct by key while ignoring stream rules

A predicate like "put the key into an external set and return the result of add" has mutable state. If used with a parallel pipeline, synchronization issues arise along with which thread retains the representative first.

Even if you replace the set with a concurrent set, "which thread adds the key first" does not automatically equal "which record appears first in the source". For a requirement to keep the representative by encounter order, an explicit sequential loop or a collector with an appropriate contract is usually easier to reason about.

The examples in this lesson do not mutate a shared collection from multiple parallel `forEach` branches.

## 7. Preserving order across the result handoff

### 7.1. List is the clear choice when callers need a sequence

If the result needs sequential display or positional access, you can convert it:

~~~java
List<String> result = new ArrayList<>(uniqueInOrder);
~~~

The constructor reads the source's iteration order and preserves it in the new list. If the source is a properly constructed `LinkedHashSet`, the list preserves that order.

The new list is structurally mutable; adding or removing elements in the list does not mutate the source set's structure. However, the element objects themselves may still be the same references; this is not a deep copy.

### 7.2. Unmodifiable results must also preserve the ordering contract

For a result containing no `null` values, you can create:

~~~java
List<String> result = List.copyOf(uniqueInOrder);
~~~

`List.copyOf` preserves the iteration order of the source collection and does not allow modifying the resulting list, per [List.copyOf Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/List.html#copyOf(java.util.Collection)).

Conversely, do not use `Set.copyOf` as a promise to preserve insertion order. Sets created by this factory have no iteration-order guarantee like `LinkedHashSet`, per the [unmodifiable sets contract](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html#unmodifiable).

If you must return an unmodifiable set that still preserves the iteration order of a copy, you can wrap a newly created `LinkedHashSet`:

~~~java
Set<String> result =
        Collections.unmodifiableSet(new LinkedHashSet<>(input));
~~~

The wrapper is a read-only view over the backing set. In this pattern, the backing set is a fresh copy and is not handed out elsewhere to be mutated. If you directly wrap a shared set and that source is later modified, the view will reflect the source. See [Collections.unmodifiableSet Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Collections.html#unmodifiableSet(java.util.Set)).

### 7.3. Null policy must be compatible across the entire chain

`LinkedHashSet` allows a single `null` element and preserves its insertion position as a member. For example, `[B, null, A, null, B]` deduplicated keeping first occurrences becomes `[B, null, A]`.

However, `List.copyOf` does not accept `null` elements. A pipeline that gets ordering right in the first step can still be rejected at the result-conversion step.

Choose one of these approaches explicitly: disallow `null` in the input, handle/filter it deliberately according to business rules, or use a result type with a compatible policy. Do not silently drop `null` just to make a conversion method succeed.

### 7.4. Set.equals does not check order

Two `LinkedHashSet` instances that iterate as A, B and B, A can still be equal according to `Set.equals`, because the two sets have the same members.

If you need to verify order as well, you can compare lists collected from the iteration order:

~~~java
new ArrayList<>(actualSet).equals(expectedList)
~~~

This is a way to verify order without changing the `equals` contract of sets. Do not use a set equality check to assert a sequence requirement.

## 8. Complete program: multiple policies on the same data

This program tests first-seen order, last-seen order, sorted order, streams, business keys, and result conversion.

### 8.1. Source code

Save as `OrderedDedupDemo.java`:

~~~java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.Comparator;
import java.util.HashSet;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Set;
import java.util.TreeSet;
import java.util.stream.Collectors;

public class OrderedDedupDemo {
    record Row(String key, String detail) {
        Row {
            Objects.requireNonNull(key, "key");
            Objects.requireNonNull(detail, "detail");
        }

        @Override
        public String toString() {
            return key + ":" + detail;
        }
    }

    static <E> List<E> firstOccurrences(List<? extends E> input) {
        Set<E> unique = new LinkedHashSet<>(input);
        return new ArrayList<>(unique);
    }

    static <E> List<E> lastOccurrences(List<? extends E> input) {
        Set<E> unique = new LinkedHashSet<>();
        for (E element : input) {
            unique.remove(element);
            unique.add(element);
        }
        return new ArrayList<>(unique);
    }

    static List<Row> firstRowsByKey(List<Row> input) {
        Set<String> seenKeys = new HashSet<>();
        List<Row> result = new ArrayList<>();
        for (Row row : input) {
            if (seenKeys.add(row.key())) {
                result.add(row);
            }
        }
        return result;
    }

    public static void main(String[] args) {
        List<String> input = List.of("B", "A", "B", "C", "A");
        System.out.println("input: " + input);
        System.out.println("first occurrences: " + firstOccurrences(input));
        System.out.println("last occurrences: " + lastOccurrences(input));
        System.out.println("natural sorted: " + new TreeSet<>(input));

        Set<String> insertionOrder = new LinkedHashSet<>(input);
        boolean added = insertionOrder.add("A");
        System.out.printf("add existing A: returned=%s, values=%s%n",
                added, insertionOrder);
        insertionOrder.remove("A");
        insertionOrder.add("A");
        System.out.println("remove then add A: " + insertionOrder);

        List<String> streamDistinct = input.stream().distinct().toList();
        Set<String> collected = input.stream()
                .collect(Collectors.toCollection(LinkedHashSet::new));
        List<String> parallelDistinct = input.parallelStream().distinct().toList();
        System.out.println("ordered stream distinct: " + streamDistinct);
        System.out.println("collected LinkedHashSet: " + collected);
        System.out.println("ordered parallel matches: "
                + streamDistinct.equals(parallelDistinct));

        List<String> words = List.of("pear", "fig", "plum", "fig");
        List<String> uniqueWords = firstOccurrences(words);
        uniqueWords.sort(Comparator.comparingInt(String::length)
                .thenComparing(Comparator.naturalOrder()));
        Set<String> lengthOnly = new TreeSet<>(Comparator.comparingInt(String::length));
        lengthOnly.addAll(words);
        System.out.println("unique then length/name sort: " + uniqueWords);
        System.out.println("TreeSet length-only: " + lengthOnly);

        List<Row> rows = List.of(
                new Row("B", "b1"),
                new Row("A", "a1"),
                new Row("B", "b2"),
                new Row("C", "c1"),
                new Row("A", "a2"));
        System.out.println("record-equality unique count: "
                + new LinkedHashSet<>(rows).size());
        System.out.println("first row per key: " + firstRowsByKey(rows));

        Map<String, Row> lastValueFirstKeyOrder = new LinkedHashMap<>();
        Map<String, Row> lastValueLastKeyOrder = new LinkedHashMap<>();
        for (Row row : rows) {
            lastValueFirstKeyOrder.put(row.key(), row);
            lastValueLastKeyOrder.remove(row.key());
            lastValueLastKeyOrder.put(row.key(), row);
        }
        System.out.println("last row, first key order: "
                + new ArrayList<>(lastValueFirstKeyOrder.values()));
        System.out.println("last row, last key order: "
                + new ArrayList<>(lastValueLastKeyOrder.values()));

        Set<String> orderAB = new LinkedHashSet<>(List.of("A", "B"));
        Set<String> orderBA = new LinkedHashSet<>(List.of("B", "A"));
        System.out.println("set equality ignores order: " + orderAB.equals(orderBA));
        System.out.println("list equality sees order: "
                + new ArrayList<>(orderAB).equals(new ArrayList<>(orderBA)));

        List<String> nullableInput = Arrays.asList("B", null, "A", null, "B");
        List<String> nullableResult = firstOccurrences(nullableInput);
        System.out.println("nullable first occurrences: " + nullableResult);
        try {
            List.copyOf(nullableResult);
        } catch (NullPointerException exception) {
            System.out.println("List.copyOf nullable: NullPointerException");
        }
        List<String> snapshot = List.copyOf(firstOccurrences(input));
        try {
            snapshot.add("D");
        } catch (UnsupportedOperationException exception) {
            System.out.println("snapshot.add: UnsupportedOperationException");
        }
        System.out.println("input unchanged: " + input);
    }
}
~~~

Compile and run with JDK 17 or later:

~~~shell
javac --release 17 -encoding UTF-8 OrderedDedupDemo.java
java OrderedDedupDemo
~~~

### 8.3. Comparing the output groups

The first three output lines for first, last, and sorted have the same three members but different orders. They verify three different contracts, not three equivalent ways of writing the same thing.

`add existing A` returns false and does not change the order. Only when A is removed and then added does A's position move to the end.

Both stream approaches produce results in first-seen order. The parallel pipeline with an ordered source still produces the same sequence; this checks contract correctness, not fast/slow performance.

The words group keeps both pear and plum when deduplicating by content and then sorting the list. `TreeSet` comparing only by length keeps a single representative for length 4, losing plum for that requirement.

Record `Row` uses the default `equals/hashCode` across both key and detail. Because the five records differ in their pair of fields, the whole-record set still has size 5. The key-based helper and the two maps afterward accurately express the three record-selection policies.

The two equality checks demonstrate why checking set membership alone is insufficient for checking order. The null and snapshot group further verifies data and mutability contracts at the result-return step.

The result structures are created separately; the input list remains `[B, A, B, C, A]`. The example does not mutate the source to deduplicate.

## 9. Cost and stability of the algorithms

Let n be the number of input elements, and u be the number of unique members or unique keys.

| Approach | Expected work | Main auxiliary memory |
|---|---|---|
| LinkedHashSet keeping first | O(n) with well-distributed hashes and appropriate hash/equals cost | O(u) |
| Remove then add to keep last | O(n) under the same hashing assumption | O(u) |
| Key set + first-occurrence List | O(n), plus key-extraction/hash/equals cost | O(u) |
| LinkedHashMap by key | O(n) under appropriate hashing assumptions | O(u) |
| TreeSet | O(n log(u+1)) in general analysis, plus comparison cost | O(u) |
| Deduplicate then sort List | Expected O(n) for deduplication, plus O(u log u) comparisons for general sorting | O(u) and sorting workspace |

The bounds above do not mean every hash computation, string comparison, or key extraction is free. If keys are long or normalization is expensive, that work must be accounted for.

### 9.1. Avoid contains on a List per element for large inputs

A simple approach is to maintain a result list and call `result.contains(value)` before each addition. It can preserve first-occurrence order, but each check may scan many already-retained elements; the total can become O(n²).

A set separates membership checking from output ordering with a more efficient model when the data fits. You do not need to switch every small list to a complex algorithm, but you must recognize the repeated work at large scale.

### 9.2. Correctness of equals/hashCode remains a requirement

If the duplicate criterion uses fields that can change while an element is held in a hash-based set, the result may no longer be managed as intended. Using stable keys or immutable data makes the contract clearer.

A hash collision does not mean two elements are duplicates; `equals` must still be checked. Never discard data solely because comparing hash codes alone shows them to be equal.

### 9.3. Preserving order does not mean thread safety

Standard `LinkedHashSet` and `LinkedHashMap` are not synchronized. The remove/add or remove/put pair in the keep-last algorithm is not atomic.

If the source is modified concurrently, the concepts of "first" or "last" must also be defined according to a clear business ordering. The examples use a finite, stable source and a single thread building the result, except for the parallel pipeline whose collection mechanism is managed by the library.

## 10. Common mistakes

| Claim | What to reconsider |
|---|---|
| Every Set preserves input order | Only specific implementations/contracts provide that guarantee |
| HashSet printed the right order once so it can be relied on | Observed output does not replace a contract |
| LinkedHashSet recovers the history of a HashSet | It only records the order the source currently provides |
| Adding an existing element to LinkedHashSet moves it to the end | Re-adding does not change position; remove then add is a different operation |
| Keeping the last record always means last-seen order | Representative data and key order are two separate decisions |
| TreeSet only deduplicates and sorts by equals | The Comparator also determines which elements are considered equivalent |
| A length comparator keeps all distinct words | Words of the same length may be collapsed into a single tree member |
| distinct always keeps a deterministic "first" | It requires encounter order; an unordered stream has no such guarantee |
| toSet preserves the order of the preceding pipeline | This collector has no ordering contract |
| Switching to Set.copyOf still preserves insertion order | There is no such guarantee |
| Set.equals returning true proves the order is right | It checks membership, not sequence |
| A record has a key so it automatically deduplicates by key | Default equals also checks the other components |
| A record that arrives later is definitely newer | Only true if the source order reflects that |
| Deduplication does not need a representative decision | Records with the same key can carry different data |

## 11. Practice exercises

### Exercise 1: keep first

Input `[C, A, C, B, A, D]`. What sequence does using `LinkedHashSet` in source order produce?

**Explanation:** `[C, A, B, D]`. Each element is placed when it is first accepted into the set; duplicates do not change position.

### Exercise 2: keep by last

With the same input above, remove the old element and re-add it at each step. What is the result?

**Explanation:** `[C, B, A, D]`. The last occurrences have positions C at 2, B at 3, A at 4, and D at 5 using 0-based indexing.

### Exercise 3: independent record selection and order

Data `A:a1, B:b1, A:a2, C:c1`. A default `LinkedHashMap` putting by key at each step gives values in what order?

**Explanation:** `[A:a2, B:b1, C:c1]`. A gets the last record's data but remains at the position where the key was first seen. If you remove the key and put it again at each step, the result is `[B:b1, A:a2, C:c1]`.

### Exercise 4: insufficient comparator

You need to keep words with distinct content and sort by length. Does using a `TreeSet` with only a length comparator satisfy this?

**Explanation:** No, if multiple words of the same length must be kept. You can deduplicate by content first and then sort a `List`, or design a complete ordering that is appropriate and consistent with the membership definition.

### Exercise 5: verifying an ordered result

Two sets both contain A and B, but one iterates A, B and the other iterates B, A. Does `Set.equals` detect the order difference?

**Explanation:** No. To verify an ordering requirement, compare the sequence obtained from iteration against an expected list.

### Exercise 6: a source that has already lost order

Data is put into a `HashSet` first, and only later converted to a `LinkedHashSet`. Is there a guarantee of recovering the original order?

**Explanation:** No. You must preserve order at the source from the start, or retain other information sufficient to reconstruct it, such as a defined ordering key.

A proper deduplication approach must clarify the **equivalence criterion**, the **retained representative**, and the **output order**. Once those three are defined, `LinkedHashSet`, `List`, `TreeSet`, or `Map` become concrete tools to implement the contract rather than substitutes for defining the requirement.
