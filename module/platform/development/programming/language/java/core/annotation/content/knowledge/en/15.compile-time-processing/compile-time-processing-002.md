# Processor, AbstractProcessor, and ProcessingEnvironment — Annotation Processing in Java

## 1. Why do annotations need a processor at compile time?

In Java, an annotation like `@GenerateGreeting` is merely **metadata** written in source code. Declaring it does not mean the JVM automatically generates classes, validates business rules, or executes other methods.

~~~java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
@interface GenerateGreeting {
}
~~~

To perform work based on annotations **at compile time**, Java provides the **JSR 269 / Pluggable Annotation Processing API** standard. A compiler such as `javac` can load an **annotation processor** to read the program model, emit diagnostics, and generate additional source code or resources.

Three interrelated core components:

- **`javax.annotation.processing.Processor`**: the interface defining the *contract and lifecycle* of a processor.
- **`javax.annotation.processing.AbstractProcessor`**: an abstract class implementing `Processor` that provides default implementations and a context field; we extend it to reduce boilerplate.
- **`javax.annotation.processing.ProcessingEnvironment`**: the compiler context provided at initialization, supplying `Filer`, `Messager`, `Elements`, `Types`, options, and compilation session information.

A related component that is **not synonymous** with `ProcessingEnvironment` is **`RoundEnvironment`**: the data and state of *each annotation processing round*.

~~~text
@GenerateGreeting source code
             |
             v
javac finds and loads Processor
             |
             v
init(ProcessingEnvironment)  — prepare services
             |
             v
process(..., RoundEnvironment)  — read elements of a round
             |
             +-- Elements / Types: analyze source model
             +-- Messager: error / warning / note
             +-- Filer: create new Java source / class / resource
             |
             v
javac processes generated source in the next round
             |
             v
Application .class bytecode and resources
~~~

All of these APIs belong to the standard JDK, typically in the **`java.compiler`** module. In Java 17, the package is still named **`javax.annotation.processing`**, not `jakarta.annotation.processing`.

## 2. `Processor`: the contract of a compiler plugin

`Processor` is the public interface defining the methods an annotation processor must provide.

| Method | Purpose |
| --- | --- |
| `init(ProcessingEnvironment env)` | Called by the compiler to initialize and provide the environment |
| `getSupportedAnnotationTypes()` | Lists the annotation types the processor is interested in |
| `getSupportedSourceVersion()` | The Java source language level the processor declares support for |
| `getSupportedOptions()` | The `-Akey=value` option names the processor recognizes |
| `process(Set<? extends TypeElement> annotations, RoundEnvironment roundEnv)` | Processes the annotation types/elements in a round |
| `getCompletions(Element, AnnotationMirror, ExecutableElement, String)` | Can provide completion suggestions for annotation values in supporting tools |

When implementing `Processor` directly, you must implement the entire contract. Most typical processors **extend `AbstractProcessor`** instead of implementing the interface directly.

### `getSupportedAnnotationTypes()`

A processor needs to specify the annotation types it will receive:

~~~java
@SupportedAnnotationTypes("demo.GenerateGreeting")
~~~

This is a meta-annotation on the **processor class**. The value is the fully qualified name of the annotation type to process; in this example, it is `demo.GenerateGreeting`.

Multiple names can be supported, or even the `"*"` pattern to accept all annotation types. However, `"*"` should be used with caution because claiming too broadly can affect how other processors are coordinated by the compiler. You should not use `"*"` merely to avoid writing out the annotation name.

**Important:** `@SupportedAnnotationTypes` is not a way to *register* a processor. It only provides information after the processor has been loaded; you must specify the processor via `-processor` or register it appropriately as a service.

### `getSupportedSourceVersion()`

A processor written and tested against Java 17 syntax can declare:

~~~java
@SupportedSourceVersion(SourceVersion.RELEASE_17)
~~~

With imports `javax.annotation.processing.SupportedSourceVersion` and `javax.lang.model.SourceVersion`. This is the **source language level**, not the bytecode version generated by the processor or the JRE version used to run the application.

Besides the annotation above, a subclass can override `getSupportedSourceVersion()`; ensure that the declared value reflects tested capabilities.

### `getSupportedOptions()`

The compiler allows passing custom options to a processor:

~~~bash
javac -Agreeting.strict=true ...
~~~

The processor can declare `@SupportedOptions("greeting.strict")` and read it:

~~~java
String raw = processingEnv.getOptions()
        .getOrDefault("greeting.strict", "false");
boolean strict = Boolean.parseBoolean(raw);
~~~

This is a fragment belonging to a processor class. `getOptions()` returns a `Map<String, String>`; the processor decides how to parse and validate it. Note that `Boolean.parseBoolean("garbage")` returns `false` and does not automatically emit an error diagnostic; if strict validation is needed, you must check the string manually.

## 3. `AbstractProcessor`: the common implementation approach

`AbstractProcessor` is a base class implementing much of `Processor`. Notably, it holds the field:

~~~java
protected ProcessingEnvironment processingEnv;
~~~

The compiler invokes `init(ProcessingEnvironment)` and the base class initializes this field. Subclasses typically only need to define the main processing logic:

~~~java
@Override
public boolean process(
        Set<? extends TypeElement> annotations,
        RoundEnvironment roundEnv) {
    // Read annotated elements; validate; generate source if needed.
    return true;
}
~~~

**This is only a method fragment**; the full runnable example below provides the class, imports, annotation, and build commands.

`AbstractProcessor` reads `@SupportedAnnotationTypes`, `@SupportedOptions`, and `@SupportedSourceVersion` to provide default implementations for the corresponding query methods. It **does not inherently understand the business logic** of a custom annotation, does not automatically write source files, and does not automatically create runtime interception.

If you need to override `init` to initialize additional resources, you must call the superclass method:

~~~java
@Override
public synchronized void init(ProcessingEnvironment env) {
    super.init(env);
    // Prepare additional state.
}
~~~

Do not attempt to instantiate it with `new ProcessingEnvironment()`: it is an interface provided by the compiler. Nor should you retain this object in a global variable to reuse arbitrarily across compilation sessions.

### What does the `boolean` returned by `process` mean?

- `true`: the processor **claims** the set of annotation types passed in the round's `annotations` parameter, so subsequent processors do not continue receiving them as unclaimed types.
- `false`: the processor **does not claim** them; other processors still have the opportunity to receive and process them.

`true` does not mean "compilation succeeded", `false` does not mean "compilation failed", and claiming does not mean the compiler stops all processing rounds.

To actually report an error, you must use:

~~~java
processingEnv.getMessager().printMessage(
        Diagnostic.Kind.ERROR,
        "Invalid use of @GenerateGreeting",
        element);
~~~

This snippet is a fragment; `element` is the element being checked and `Diagnostic` belongs to `javax.tools`. The compiler can attach the diagnostic to the element's source location. Do not use `return false` as a substitute for emitting an error.

## 4. `ProcessingEnvironment`: compiler services provided to the processor

`ProcessingEnvironment` is passed into `init` **once when the processor is initialized**, holding the shared context for an annotation-processing run. Essential methods:

| Method | Return Type | Purpose |
| --- | --- | --- |
| `getFiler()` | `Filer` | Creates source, class, or resource files |
| `getMessager()` | `Messager` | Prints `ERROR`, `WARNING`, `NOTE`, etc. diagnostics |
| `getElementUtils()` | `Elements` | Queries declaration elements, packages, names, and declared types |
| `getTypeUtils()` | `Types` | Works with `TypeMirror`, subtype/assignability relationships |
| `getOptions()` | `Map<String,String>` | Receives options passed by the tool via `-A` |
| `getSourceVersion()` | `SourceVersion` | Determines the source language level used by the environment |
| `getLocale()` | `Locale` | The environment locale (may be `null`) |

You must distinguish `ProcessingEnvironment` from `RoundEnvironment`: **one provides infrastructure and services**, while the other holds the state and elements of the **current round**. Do not treat them as two names for the same object.

### `Filer` — generating files under compiler rules

Example:

~~~java
JavaFileObject file = processingEnv.getFiler()
        .createSourceFile("demo.SampleGreeting", element);
~~~

This snippet is a fragment using `javax.tools.JavaFileObject`. `Filer` manages generated files during the compilation session:

- The passed name is the fully qualified name of the source type.
- The `element` parameter is the **originating element**, helping build tools know which declaration the generated file originates from.
- `-s build/generated` specifies the generated source output directory for `javac`.
- The compiler can examine new sources in subsequent processing rounds.
- You must not recreate a name/path that was already created within the same processing run. Doing so may throw `FilerException` (an `IOException`).

Use **try-with-resources** to close the `Writer` after writing the complete source, preventing the compiler from receiving an incomplete file.

### `Messager` — diagnostics with severity levels

`Messager.printMessage` has several overloads that can attach a message to the appropriate `Element`, `AnnotationMirror`, or annotation value. Common levels:

- `Diagnostic.Kind.ERROR`: compile-time error.
- `Diagnostic.Kind.WARNING`: warning.
- `Diagnostic.Kind.MANDATORY_WARNING`: mandatory warning.
- `Diagnostic.Kind.NOTE`: informational note.

To give the message a clear source location, pass the annotated element whenever possible. `System.out.println` does not replace diagnostics: it does not carry compiler error semantics and typically does not point to the appropriate source location.

### How `Elements` differs from `Types`

An annotation processor does not necessarily have the runtime `Class<?>` objects of the classes being compiled. Instead, it typically operates on the model:

- `TypeElement`: a class/interface/annotation type declaration.
- `ExecutableElement`: methods, constructors, and callable members of the source model.
- `VariableElement`: fields, parameters, enum constants, etc., depending on kind.
- `TypeMirror`: the Java type represented by a declaration or expression.

`processingEnv.getElementUtils()` works with **declaration elements**. `processingEnv.getTypeUtils()` works with **types**.

For example, for a class with a type parameter `T`: `TypeElement` describes the **class declaration**, whereas `TypeMirror` describes the **type of the class or the types appearing inside it**. If you want to compare the return type of a method, you typically use `Types.isSameType`, not `Class.forName`.

## 5. `RoundEnvironment`: the model of each processing round

In `process(..., RoundEnvironment roundEnv)`, commonly used APIs include:

~~~java
roundEnv.getElementsAnnotatedWith(GenerateGreeting.class);
roundEnv.getRootElements();
roundEnv.processingOver();
roundEnv.errorRaised();
~~~

- `getElementsAnnotatedWith(...)` helps find elements annotated with the annotation type in the current round, according to the API rules.
- `getRootElements()` returns the **root elements of the round**, not all classes across every library on the classpath.
- `processingOver()` signals the **final processing round**; you should not expect source files generated in that round to be compiled in a subsequent round.
- `errorRaised()` reports whether an error diagnostic was raised in a previous round under the annotation processing model; it is not a general exception catcher.

A processor can be invoked **multiple times**. If it generates new source files, `javac` may run additional rounds to examine the new sources. Do not assume `process` is called only once per compilation or that all source elements always appear on the first invocation.

**A standard processor is not an arbitrary AST-transformation API.** JSR 269 is primarily intended for reading the source model, reporting errors/warnings, and generating additional files. Tools that modify the AST directly use other mechanisms outside the public contract of `Processor`.

## 6. Standalone Java 17 Demo: a processor generates source and the program uses the generated class

The example below requires only **JDK 17+**, with no frameworks or external dependencies. Use the initial directory structure:

~~~text
src/
  demo/
    GenerateGreeting.java
    GreetingProcessor.java
    Sample.java
~~~

The `Sample` program will reference `SampleGreeting`, a class generated by the processor **during the compile step**, so its source file does not exist beforehand.

### 6.1. File `src/demo/GenerateGreeting.java`

~~~java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateGreeting {
}
~~~

`SOURCE` is sufficient because the processor runs at compile time. Runtime reflection is not needed to read this annotation.

### 6.2. File `src/demo/GreetingProcessor.java`

~~~java
package demo;

import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.Element;
import javax.lang.model.element.ElementKind;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;
import javax.tools.JavaFileObject;

@SupportedAnnotationTypes("demo.GenerateGreeting")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class GreetingProcessor extends AbstractProcessor {

    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {

        if (roundEnv.processingOver()) {
            return true;
        }

        for (Element element :
                roundEnv.getElementsAnnotatedWith(GenerateGreeting.class)) {

            if (element.getKind() != ElementKind.CLASS) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "@GenerateGreeting requires a class",
                        element);
                continue;
            }

            String simpleName = element.getSimpleName().toString();
            String generatedName = simpleName + "Greeting";
            String qualifiedName = "demo." + generatedName;

            try {
                JavaFileObject file = processingEnv.getFiler()
                        .createSourceFile(qualifiedName, element);

                try (Writer writer = file.openWriter()) {
                    writer.write("package demo;\n");
                    writer.write("public final class " + generatedName + " {\n");
                    writer.write("    private " + generatedName + "() {}\n");
                    writer.write("    public static String message() {\n");
                    writer.write("        return \"Generated for " + simpleName + "\";\n");
                    writer.write("    }\n");
                    writer.write("}\n");
                }
            } catch (IOException ex) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "Failed to generate " + qualifiedName
                                + ": " + ex.getMessage(),
                        element);
            }
        }

        return true;
    }
}
~~~

**Explanation:**

1. `extends AbstractProcessor` uses the base implementation of the `Processor` interface; the compiler automatically calls `init` and supplies `ProcessingEnvironment`.
2. `@SupportedAnnotationTypes` declares the annotation of interest; `@SupportedSourceVersion` declares Java 17.
3. `RoundEnvironment.getElementsAnnotatedWith` finds declarations carrying the annotation.
4. The annotation's `@Target(TYPE)` allows multiple type kinds, but the processor **explicitly requires** `ElementKind.CLASS`. This is a custom check beyond the target.
5. `Filer.createSourceFile` creates `demo.SampleGreeting`. Write and close the `Writer` so the compiler processes the source.
6. `Messager` reports an error if the annotation is placed on the wrong element kind or if the file cannot be generated.
7. `return true` claims the annotation type; it does not mean "no errors".

The example intentionally uses the fixed `demo` package to keep the code easy to follow. A general-purpose processor should retrieve the element's package via `processingEnv.getElementUtils().getPackageOf(element)`, handle name collisions, and avoid assuming every class is in the `demo` package.

### 6.3. File `src/demo/Sample.java`

~~~java
package demo;

@GenerateGreeting
public class Sample {
    public static void main(String[] args) {
        System.out.println(SampleGreeting.message());
    }
}
~~~

When the compiler runs with the processor, it generates the `SampleGreeting.java` source file before finishing compilation of this program.

### 6.4. Compile/run commands in the exact order

From the parent directory of `src`, in PowerShell:

~~~powershell
New-Item -ItemType Directory -Force build/processor, build/classes, build/generated | Out-Null
~~~

**Step 1 — compile the processor and annotation type:**

~~~bash
javac -encoding UTF-8 -d build/processor src/demo/GenerateGreeting.java src/demo/GreetingProcessor.java
~~~

**Step 2 — compile the application and explicitly enable the processor:**

~~~bash
javac -encoding UTF-8 -cp build/processor -processorpath build/processor -processor demo.GreetingProcessor -s build/generated -d build/classes src/demo/Sample.java
~~~

Options:

- `-cp build/processor`: so `javac` can resolve `demo.GenerateGreeting` when compiling `Sample`.
- `-processorpath build/processor`: so the compiler loads `GreetingProcessor`.
- `-processor demo.GreetingProcessor`: specifies the processor by its fully qualified name.
- `-s build/generated`: where generated Java **source** files are placed.
- `-d build/classes`: where the application's class files are placed.

After step 2, you can observe:

~~~text
build/generated/demo/SampleGreeting.java
build/classes/demo/Sample.class
build/classes/demo/SampleGreeting.class
~~~

The paths above are the **expected output of a successful build**, not files that already exist right after writing only the three initial source files.

**Step 3 — run the program:**

~~~bash
java -cp build/classes demo.Sample
~~~

**Exact stdout:**

~~~text
Generated for Sample
~~~

The `java` command runs only the compiled `Sample` and `SampleGreeting` classes. The processor does not need to run again at runtime. Any `javac` diagnostics, if present, belong to the **compile phase**, not the program's stdout.

### 6.5. Role of rounds in the example

1. The compiler loads `demo.GreetingProcessor` from the processor path.
2. The processor is initialized and receives `ProcessingEnvironment`.
3. In the round containing the `Sample` declaration, `process` encounters `@GenerateGreeting`.
4. The processor creates the Java source `SampleGreeting.java` via `Filer`.
5. The compiler examines the new source in the next round and compiles the generated class.
6. At runtime, the program calls `SampleGreeting.message()` and prints `Generated for Sample`.

This is how a **compiler plugin generates code at build time**, rather than a method interception or runtime reflection mechanism.

## 7. How to register a processor with the compiler

The example used `-processor demo.GreetingProcessor`, so auto-discovery was not needed. In reusable libraries, processors are typically packaged into a JAR with service provider metadata:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

File contents:

~~~text
demo.GreetingProcessor
~~~

When the compiler is configured to allow discovering annotation processors from the processor path, it can load the implementation declared in the service file. With Java modules, there is also a mechanism for declaring the service appropriately via a module descriptor; different toolchains/JDK versions have different discovery policies. For reliable builds, explicitly declare the **processor path and processor activation** according to your tool's documentation.

Be sure to distinguish:

- `@SupportedAnnotationTypes`: indicates which annotations the **loaded processor** supports.
- Service registration or `-processor`: tells the **compiler which implementation to load**.
- `@Retention(SOURCE)`: indicates **whether the metadata persists after compilation**, not how to register a processor.

A processor JAR is typically a **compile-time** dependency; the application's runtime only needs the generated classes/resources and the dependencies actually required at runtime.

## 8. Distinguishing `ProcessingEnvironment` and `RoundEnvironment` in code

An illustrative method-processing snippet (not a standalone program):

~~~java
for (Element element : roundEnv.getElementsAnnotatedWith(MyMarker.class)) {
    if (element.getKind() == ElementKind.METHOD) {
        ExecutableElement method = (ExecutableElement) element;
        TypeMirror resultType = method.getReturnType();

        boolean returnsVoid = processingEnv.getTypeUtils()
                .isSameType(
                        resultType,
                        processingEnv.getTypeUtils()
                                .getNoType(TypeKind.VOID));

        if (returnsVoid) {
            processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.WARNING,
                    "Annotated method returns void",
                    method);
        }
    }
}
~~~

This snippet assumes the processor has declared `MyMarker`, has the `roundEnv` variable, along with imports `ExecutableElement`, `TypeMirror`, `TypeKind`, `ElementKind`, and `Diagnostic`.

- `roundEnv` **provides the elements of the current round**.
- `ElementKind` helps determine that the element is a method.
- `ExecutableElement` provides the method declaration model.
- `TypeMirror` describes the return type.
- `processingEnv.getTypeUtils()` assists with type comparison, while `getMessager()` emits the compiler warning.

You should not replace this entire model with `Class.forName("demo.SomeClass")`. Source code being compiled may not yet have a class file to load, and runtime reflection does not fully represent source models at the time the compiler runs.

## 9. Managing processing rounds and safe source generation

### Do not recreate the same file

`Filer` can throw `FilerException` when a processor attempts to recreate the same type/path within the same annotation processing run. Real-world processors must manage generated names, element kinds, and scenarios where multiple source requests resolve to the same name.

### Do not expect `getRootElements()` to contain every source in the project

Each round has a different set of roots. Sources generated by a processor can become roots in a later round; the compiler does not necessarily place the entire classpath into `getRootElements()` or re-pass the exact same set.

### Do not generate new sources in the final round expecting another compilation round

`processingOver()` marks the final round. Processors should create files in the appropriate earlier rounds; diagnostics can be emitted at the end, but do not expect the compiler to process late-generated sources as a normal round.

### Do not use `return false` as an error-reporting mechanism

If an element violates a constraint, use `Messager.printMessage(ERROR, ..., element)`. The return value from `process` primarily concerns **claiming annotations**, not controlling the success status of the entire compilation.

### Do not modify the AST directly using non-contract APIs

JSR 269 is the standard for **inspecting declarations, querying type models, emitting diagnostics, and generating files**. Rewriting existing code, mutating internal compiler ASTs, or automatically replacing method bodies is not promised by `Processor`.

## 10. Comparing compile-time processors with runtime reflection

| Aspect | Annotation Processing (JSR 269) | Runtime Reflection |
| --- | --- | --- |
| Execution phase | Build / compile with `javac` | JVM running the application |
| API | `Processor`, `AbstractProcessor`, `ProcessingEnvironment`, `RoundEnvironment` | `Class`, `Method`, `Field`, `AnnotatedElement` |
| Elements/types | `Element`, `TypeElement`, `TypeMirror` | `Class<?>`, reflection objects |
| `@Retention` | `SOURCE` is usually sufficient | Usually requires `RUNTIME` |
| Typical outcomes | Compile-time errors/warnings, new sources/resources | Metadata inspection, routing, runtime validation |
| File-writing tool | `Filer` | Not a responsibility of reflection |
| Error-reporting tool | `Messager` / compiler diagnostics | Application exceptions/logging |

For example, `@GenerateGreeting` has `SOURCE` retention, yet the processor can still handle it because it runs **before source annotations are stripped from class files**. At runtime, `Sample.class.getAnnotation(GenerateGreeting.class)` will not return that annotation just because the processor successfully generated `SampleGreeting`.

## 11. Common mistakes

**Mistake 1 — writing only `@interface` and assuming a processor exists.** An annotation is metadata; you must write and activate an implementation of `Processor`.

**Mistake 2 — confusing `@SupportedAnnotationTypes` with service registration.** One declares supported annotations; the other causes the compiler to load the processor.

**Mistake 3 — failing to compile the processor before using `-processor`.** The processor class must be loadable from the processor path.

**Mistake 4 — confusing `processingEnv` with `roundEnv`.** The former holds services for the compilation session; the latter holds per-round data.

**Mistake 5 — using reflection to query uncompiled sources.** Using `Element`, `TypeElement`, `TypeMirror`, `Elements`, and `Types` is the appropriate approach.

**Mistake 6 — using `System.out.println` to report compile errors.** It is not a compiler diagnostic. Use `Messager`.

**Mistake 7 — generating duplicate filenames across multiple rounds.** `Filer` may reject it. Design unique filenames and guard creation conditions.

**Mistake 8 — failing to close the stream/writer used to create a file.** The compiler may not see the complete source file; use try-with-resources.

**Mistake 9 — treating `process() == true` as meaning compilation succeeded.** That reflects claiming semantics; error diagnostics are what affect the compilation outcome.

**Mistake 10 — assuming `@Retention(RUNTIME)` is always required for a processor to read an annotation.** A compile-time processor can read `SOURCE` annotations.

**Mistake 11 — assuming `AbstractProcessor` automatically generates code.** It only provides default implementations; the actual logic resides in `process`.

**Mistake 12 — mixing up the processor path with the application runtime classpath.** Separate compile-time and runtime dependencies according to their purpose.

## 12. Exercises and review questions

**Question 1.** How do `Processor`, `AbstractProcessor`, and `ProcessingEnvironment` differ?

**Answer:** `Processor` is the contract interface; `AbstractProcessor` is a base class providing a partial implementation; `ProcessingEnvironment` is the context supplied by the compiler at initialization.

**Question 2.** If `process` returns `false`, does the compiler necessarily stop with an error?

**Answer:** No. `false` means the processor has not claimed the round's annotation types; to report an error, use `Messager` with `Diagnostic.Kind.ERROR`.

**Question 3.** Why is `@Retention(SOURCE)` sufficient for `@GenerateGreeting` in the example?

**Answer:** The processor only needs to inspect the metadata during compilation, while the application runs the generated file and does not need to access the original annotation at runtime.

**Question 4.** Why must `GreetingProcessor.java` be compiled before `Sample.java`?

**Answer:** `javac -processor demo.GreetingProcessor` needs to load a processor whose class file already exists. The processor can then generate `SampleGreeting.java` so `Sample` can reference it.

**Question 5.** How do `Filer` and `Messager` differ?

**Answer:** `Filer` creates source/class/resource files; `Messager` emits compiler diagnostics.

**Question 6.** Why should `getRootElements()` not be used as a list of every class across the entire project?

**Answer:** It only describes the root elements belonging to a single processing round; subsequent rounds may contain newly generated sources.

**Hands-on exercise:** After running the example, add `src/demo/Report.java` with `@GenerateGreeting`, then pass both `Sample.java` and `Report.java` to the `javac` command in step 2. Observe `SampleGreeting.java` and `ReportGreeting.java` being produced. Next, place `@GenerateGreeting` on an interface and observe the `@GenerateGreeting requires a class` diagnostic emitted by the processor. Finally, try omitting `-processor demo.GreetingProcessor` in a **clean build without service registration** and explain why `SampleGreeting` is not generated.

## 13. Java SE 17 API documentation

- [`Processor`](https://docs.oracle.com/en/java/javase/17/docs/api/java.compiler/javax/annotation/processing/Processor.html): lifecycle, annotation support, claiming, and options.
- [`AbstractProcessor`](https://docs.oracle.com/en/java/javase/17/docs/api/java.compiler/javax/annotation/processing/AbstractProcessor.html): base class and `processingEnv`.
- [`ProcessingEnvironment`](https://docs.oracle.com/en/java/javase/17/docs/api/java.compiler/javax/annotation/processing/ProcessingEnvironment.html): `Filer`, `Messager`, `Elements`, `Types`, and options.
- [`RoundEnvironment`](https://docs.oracle.com/en/java/javase/17/docs/api/java.compiler/javax/annotation/processing/RoundEnvironment.html): root elements, processing round state, and annotation queries.
- [`Filer`](https://docs.oracle.com/en/java/javase/17/docs/api/java.compiler/javax/annotation/processing/Filer.html): standard generation of source/class/resource files.
- [`Messager`](https://docs.oracle.com/en/java/javase/17/docs/api/java.compiler/javax/annotation/processing/Messager.html): compiler diagnostics.

**Key takeaway:** `Processor` defines the contract, `AbstractProcessor` aids implementation, `ProcessingEnvironment` provides services, and `RoundEnvironment` carries per-round data. Understanding those roles clearly will help you write processors to validate and generate code at compile time without confusing them with runtime mechanisms.
