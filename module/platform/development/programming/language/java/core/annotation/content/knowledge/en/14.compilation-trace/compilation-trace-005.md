# How the Compiler Represents Repeated Annotations Using a Container Type

A regular Java annotation can appear only once at a single declaration site. Since Java 8, `@Repeatable` allows the same annotation type to appear **multiple times on the same declaration or valid location**. However, the key question for the **compilation trace** is: how does the compiler store those multiple uses in the `.class` file?

**Core answer:** when an annotation type `T` is repeated, Java uses **a container annotation** `TC` declared by the programmer. Inside the container, the required element `T[] value()` holds the `@T` uses in order. When compiling multiple `@T` instances at the same location, the compiler represents them **indirectly through a single `@TC` use**, rather than writing multiple independent `@T` annotations onto the same declaration-annotation structure of the class file. Therefore, to see the actual representation, you must inspect the bytecode with `javap -v` or a class file reader; when using Reflection, you need to distinguish APIs that return the container from APIs that unwrap the container automatically.

This article follows the flow **type declaration → repeated use in source → compiler checks and generates the container representation → class file attributes → Reflection/bytecode reader**, while also clarifying the difference between a single use, multiple uses, and an explicitly written container.

## 1. Two Annotation Types, One Special Relationship

A simple example:

```java
import java.lang.annotation.Repeatable;

@Repeatable(Tags.class)
@interface Tag {
    String value();
}

@interface Tags {
    Tag[] value();
}
```

Where:

- `Tag` is the **repeatable annotation type**. The element `Tag.value()` is `String`, representing one value of **a single** `@Tag`.
- `Tags` is the **containing annotation type** (container). The `Tags.value()` element is **`Tag[]`**, meaning an array containing `Tag` annotations.
- `@Repeatable(Tags.class)` on **the `Tag` definition** declares the relationship between the repeated annotation and the container.
- `Tags` **is not automatically generated by the compiler**: the author must define this type beforehand. The compiler only uses that definition to represent repeated uses.

You can visualize the two levels as follows:

```text
@Tag("java")                   -> one Tag, Tag.value() is String

@Tags({
    @Tag("java"),
    @Tag("core")
})                             -> one Tags, Tags.value() is Tag[2]
```

`String value()` of `Tag` and `Tag[] value()` of `Tags` share the name `value` but belong to **two different annotation types**. Confusing these two types is a common reason the compiler rejects `@Repeatable`.

The container name `Tags` is nothing special: `TagContainer` is equally valid if used consistently in `@Repeatable(TagContainer.class)`. However, **the element name `value()` in the container is mandatory** and cannot be renamed to `items()`.

## 2. From Two Annotations in Source to One Container in the Class File

Consider the source:

```java
@Tag("red")
@Tag("blue")
class Multi {
}
```

When the compiler analyzes this, it verifies that `Tag` is indeed repeatable, that `Tags` is a valid container, that the uses are all at allowed locations, and that the values `"red"` and `"blue"` match the `String` element type.

In terms of representation semantics, these two occurrences are equivalent to:

```java
@Tags({
    @Tag("red"),
    @Tag("blue")
})
class Multi {
}
```

However, this **does not mean the compiler modifies your source file**, creates a new Java file, or generates a `Tags` class for you. It is a **compilation/metadata-representation rule**: in the class file for that declaration location, the container represents the repeated annotations.

Diagram:

```text
Multi.java:
    @Tag("red")
    @Tag("blue")
    class Multi {}

        | javac checks @Repeatable, @Target, @Retention
        v

Multi.class:
    annotation type Tags
        value: annotation array
            [0] Tag(value="red")
            [1] Tag(value="blue")

        | if Tags and Tag have RUNTIME retention
        v

Multi.class.getDeclaredAnnotations():
    [Tags]

Multi.class.getDeclaredAnnotationsByType(Tag.class):
    [Tag("red"), Tag("blue")]
```

**The order** of repeated `Tag` annotations is meaningful in the array representation: they are preserved in the order they appear at the source location. If business-logic code requires priority between tags, you should still document the priority contract explicitly rather than treating order as an automatic processing mechanism.

### The Representation Is a Container, Not Multiple Container Types

If there are three `@Tag` annotations, the compiler still uses the container with **`Tag[3]`**. There is no need for `Tags2`, `Tags3`, or one container per occurrence. Each element in the array is an **annotation value**, not a plain string.

A single annotation can contain multiple elements:

```java
@Repeatable(Rules.class)
@interface Rule {
    String field();
    int order();
}

@interface Rules {
    Rule[] value();
}
```

With:

```java
@Rule(field = "name", order = 1)
@Rule(field = "email", order = 2)
class Form {
}
```

the `Rules` container holds an array of two `Rule` annotations, with each element preserving its `field` and `order` elements. The compiler **does not split them into two separate arrays** such as `String[] fields()` and `int[] orders()`.

## 3. Container Signatures That javac Enforces

For `@Repeatable(Container.class)` to be valid for type `T`, `Container` must be an **annotation type** with an element:

```java
T[] value();
```

Key requirements:

| Condition | Meaning |
| --- | --- |
| Element name is `value` | Cannot be changed to `entries`, `items`, or `tags` |
| Return type is strictly `T[]` | Cannot use `String[]`, `Object[]`, `T`, or `T[][]` |
| **One-dimensional** array | Annotation elements do not support multidimensional array types |
| No parameters | `value()`, not `value(int i)` |
| Additional elements must have a `default` | The compiler must construct the container from repeated `@T` uses without supplying additional elements |
| Container has compatible retention/target/meta-annotations | Prevents losing information or using the container at invalid locations |

Valid example with an extra element that has a default:

```java
@Repeatable(Labels.class)
@interface Label {
    String value();
}

@interface Labels {
    Label[] value();
    String source() default "manual";
}
```

**Invalid** example if `WrongTags` is treated as the container for `Tag`:

```java
@Repeatable(WrongTags.class)
@interface Tag {
    String value();
}

@interface WrongTags {
    String[] value(); // Wrong: compiler requires Tag[].
}
```

This snippet is intentionally invalid and not meant to be run. The fact that `Tag.value()` returns `String` does **not** mean the container is allowed to return `String[]`.

Other invalid forms:

```java
// Illustrates errors in separate container declarations only.
// Wrong element name:
Tag[] items();

// Not an array:
Tag value();

// Multidimensional array:
Tag[][] value();

// Required extra element without a default:
String source();
```

These lines are **illustrative signatures**, not standalone declarations placed outside an `@interface` to be compiled. With `T[][]`, the annotation element type itself is already invalid.

## 4. @Retention: Which Class File Attribute Is the Container Written To?

A pair of declarations with `@Retention(RetentionPolicy.RUNTIME)` on both the primary annotation and the container:

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@Repeatable(Tags.class)
@interface Tag {
    String value();
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface Tags {
    Tag[] value();
}
```

When multiple `@Tag` annotations appear on a **class declaration**, the container metadata is stored in the **`RuntimeVisibleAnnotations`** class file attribute. With `CLASS` retention, it is recorded in **`RuntimeInvisibleAnnotations`**. With `SOURCE` retention, the annotation uses are not stored as annotation metadata in `.class`.

| Retention of repeated annotation and container | Declaration annotation trace in `.class` | Standard Reflection |
| --- | --- | --- |
| `SOURCE` / `SOURCE` | Annotation is not retained in the class file | Not readable |
| `CLASS` / `CLASS` | Container in `RuntimeInvisibleAnnotations` | Not readable |
| `RUNTIME` / `RUNTIME` | Container in `RuntimeVisibleAnnotations` | Readable with the appropriate API |

These rows assume the annotations are applied to a **class declaration**, not a type-use or parameter. The class file has dedicated attributes such as `RuntimeVisibleParameterAnnotations`, `RuntimeInvisibleParameterAnnotations`, `RuntimeVisibleTypeAnnotations`, and `RuntimeInvisibleTypeAnnotations` for those corresponding locations.

**Retentions must be compatible.** The container must not have a **shorter** retention than the repeated annotation: if `Tag` uses `RUNTIME`, `Tags` must also use `RUNTIME`. If `Tag` uses `CLASS`, `Tags` may use `CLASS` or `RUNTIME` under language rules; you should not rely on different retention policies unless there is a clear need.

If `@Retention` is not declared, the default is `CLASS`, not `RUNTIME`.

### Why Does RuntimeInvisibleAnnotations Still Contain Annotations?

The attribute name can be misleading:

- `RuntimeVisibleAnnotations` means the metadata in the class file is intended for **runtime-visible** annotations, such as those with `RUNTIME` retention.
- `RuntimeInvisibleAnnotations` means the metadata is present in the class file but **is not exposed by standard Java Reflection**.
- “Invisible” does not mean absent from the class file; tools such as `javap` or a bytecode reader can still observe it.

`@Repeatable` does not change a default annotation from `CLASS` to `RUNTIME`, nor does it automatically allow Reflection to read annotations with `CLASS` retention.

## 5. Complete Java 17+ Example to Inspect Source, Bytecode, and Reflection

Create a single file **`CompilerContainerDemo.java`**:

```java
import java.lang.annotation.*;
import java.util.Arrays;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@Repeatable(Tags.class)
@interface Tag {
    String value();
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface Tags {
    Tag[] value();
}

@Tag("red")
@Tag("blue")
class Multi {
}

@Tag("solo")
class Single {
}

@Tags({@Tag("manual-one"), @Tag("manual-two")})
class Explicit {
}

@Tags({})
class Empty {
}

@Retention(RetentionPolicy.CLASS)
@Target(ElementType.TYPE)
@Repeatable(BuildMarks.class)
@interface BuildMark {
    String value();
}

@Retention(RetentionPolicy.CLASS)
@Target(ElementType.TYPE)
@interface BuildMarks {
    BuildMark[] value();
}

@BuildMark("first")
@BuildMark("second")
class BuildOnly {
}

public class CompilerContainerDemo {
    static void show(Class<?> type) {
        String[] declared = Arrays.stream(type.getDeclaredAnnotations())
                .map(a -> a.annotationType().getSimpleName())
                .toArray(String[]::new);

        String[] tags = Arrays.stream(type.getDeclaredAnnotationsByType(Tag.class))
                .map(Tag::value)
                .toArray(String[]::new);

        System.out.println(type.getSimpleName()
                + " | direct=" + Arrays.toString(declared)
                + " | Tag=" + Arrays.toString(tags));
    }

    public static void main(String[] args) {
        show(Multi.class);
        show(Single.class);
        show(Explicit.class);
        show(Empty.class);

        System.out.println("BuildOnly visible="
                + BuildOnly.class.getDeclaredAnnotations().length);
    }
}
```

Compile in the directory containing the file using JDK 17 or later:

```bash
javac --release 17 CompilerContainerDemo.java
java CompilerContainerDemo
```

Stdout:

```text
Multi | direct=[Tags] | Tag=[red, blue]
Single | direct=[Tag] | Tag=[solo]
Explicit | direct=[Tags] | Tag=[manual-one, manual-two]
Empty | direct=[Tags] | Tag=[]
BuildOnly visible=0
```

**The output above has been verified:** the entire file was compiled with `javac --release 17` and executed, and stdout matches identically. The program requires no libraries outside the JDK.

### 5.1. Analyzing Multi

`Multi` has two `@Tag` annotations of the same type. The compiler represents them via the `Tags` container.

- `getDeclaredAnnotations()` sees **one `Tags`** at runtime.
- `getDeclaredAnnotationsByType(Tag.class)` **unwraps the container** and returns **two `Tag`** instances whose `value()` values are `"red"` and `"blue"`, respectively.
- `getDeclaredAnnotation(Tag.class)` **does not unwrap the container automatically** and returns `null` in the `Multi` example.
- `getDeclaredAnnotation(Tags.class)` returns the container so you can read `value()` directly if needed.

### 5.2. Analyzing Single

`Single` uses only one `@Tag("solo")`. A single use does not require a container.

- `getDeclaredAnnotations()` returns `Tag`, not `Tags`.
- `getDeclaredAnnotationsByType(Tag.class)` still returns one `Tag`.
- `getDeclaredAnnotation(Tags.class)` returns `null` in this case.

**Never assume every use of a repeatable annotation is wrapped in a container.** Single-use and multi-use cases have different physical representations.

### 5.3. Analyzing Explicit

`Explicit` explicitly writes:

```java
@Tags({@Tag("manual-one"), @Tag("manual-two")})
class Explicit {
}
```

Even though the repeated syntax is not used directly, the class still has a `Tags` container. Reflection can unwrap the container and retrieve the two `Tag` instances.

### 5.4. Analyzing Empty

`@Tags({})` places a **valid container with an empty array**. `getDeclaredAnnotations()` sees `Tags`, while `getDeclaredAnnotationsByType(Tag.class)` returns a `Tag[0]` array. Having a container does not mean it contains at least one repeated annotation.

### 5.5. Analyzing BuildOnly

`BuildMark` and `BuildMarks` have `CLASS` retention. The compiler still writes the container into the class file for `BuildOnly`, but standard Java Reflection does not return `CLASS` metadata, so `BuildOnly.class.getDeclaredAnnotations().length` is `0`.

**Do not infer “BuildOnly has no BuildMark in the class file” from the `0` line.** Use `javap` in the next section to inspect the compilation trace.

## 6. Using javap -v to Inspect the Container Trace in .class

After compiling `CompilerContainerDemo.java`, run:

```bash
javap -v -p Multi
javap -v -p Single
javap -v -p Explicit
javap -v -p Empty
javap -v -p BuildOnly
```

Run this in the directory containing the `.class` files. If you compile into a separate directory, for example `javac --release 17 -d out CompilerContainerDemo.java`, add `-classpath out` to `javap` and use `java -cp out CompilerContainerDemo`.

### 6.1. Multi.class: Only One Container Annotation at the Declaration Level

Look in the `javap -v -p Multi` output for the section:

```text
RuntimeVisibleAnnotations:
    ... Tags(
        value=[...Tag(value="red"), ...Tag(value="blue")]
    )
```

The block above is an **abbreviated illustration**, not a character-for-character copy of `javap` output. `javap` normally prints constant pool indices, descriptor forms, and array positions. The things to identify are:

1. There is a `RuntimeVisibleAnnotations` attribute on `Multi.class`.
2. The annotation encoded on this declaration is **`Tags`**.
3. The `value` element contains **two annotation values of type `Tag`**, along with the strings `"red"` and `"blue"`.

You should not expect to find two independent, parallel `Tag` entries in the top-level `RuntimeVisibleAnnotations` list of the `Multi` class.

### 6.2. Single.class: One Direct Tag Annotation

With `javap -v -p Single`, you will see the `Tag` annotation in `RuntimeVisibleAnnotations`, not a `Tags` container generated by the compiler merely because `Tag` has `@Repeatable`.

This is an important distinction between **an annotation type that supports repetition** and **an actual use that is repeated**.

### 6.3. Explicit.class and Empty.class

- `Explicit.class` contains `Tags` with two `Tag` instances in the `value` array because the source wrote the container explicitly.
- `Empty.class` contains `Tags` with an empty `value` array.

A bytecode analysis tool should not treat “encountering a container” as proof that multiple child annotations exist: it must read the **`value` array** and its length.

### 6.4. BuildOnly.class: RuntimeInvisibleAnnotations

`javap -v -p BuildOnly` shows the `BuildMarks` container in:

```text
RuntimeInvisibleAnnotations:
    ... BuildMarks(
        value=[...BuildMark(value="first"), ...BuildMark(value="second")]
    )
```

This is also an abbreviated diagram rather than verbatim output. This trace confirms that **CLASS retention preserves metadata in .class** without making it readable through standard Reflection.

### 6.5. Do Not Confuse the Annotation Type File with the Annotated Class File

If you run `javap -v Tag`, you are viewing **the `Tag` annotation type definition**, where the `@Repeatable(Tags.class)` meta-annotation lives. This is not the same metadata as **the two `@Tag` uses on `Multi`**.

Distinguish between:

| File being inspected | What to look for |
| --- | --- |
| `Tag.class` | Meta-annotation declaring the `@Repeatable(Tags.class)` relationship |
| `Tags.class` | Container annotation definition with `Tag[] value()` |
| `Multi.class` | One use of the `Tags` container holding an array of two `Tag` annotations |
| `Single.class` | One direct use of `Tag` |
| `BuildOnly.class` | The `BuildMarks` container in the runtime-invisible attribute |

Across different compilers/JDKs, constant pool indices and display order may differ, but **the meaning of the container structure** still follows Java's rules.

## 7. Which Reflection APIs Recover the List of Repeated Annotations?

When the retention is `RUNTIME`, Java Reflection has two groups of APIs that need to be distinguished:

| API | Meaning in the `Multi` example |
| --- | --- |
| `getDeclaredAnnotations()` | Sees `Tags` as a direct annotation of the class |
| `getDeclaredAnnotation(Tag.class)` | Does not unwrap the container automatically; returns `null` |
| `getDeclaredAnnotation(Tags.class)` | Returns `Tags`; calling `value()` yields an array of two `Tag` instances |
| `getDeclaredAnnotationsByType(Tag.class)` | Automatically reads direct/indirect annotations; returns `Tag[2]` |
| `getAnnotationsByType(Tag.class)` | Also returns `Tag[2]` in this example; additionally applies `@Inherited` rules when applicable |
| `getAnnotation(Tag.class)` | Not “the first element in the container”; not the right API for reading multiple `Tag` instances |

Choose the API based on your question:

- Need **all `Tag` annotations** on the annotated class, regardless of whether it is a single use, multiple uses, or an explicit container? Use `getDeclaredAnnotationsByType(Tag.class)` if inspecting only that declaration itself.
- Want to also consider **class inheritance rules** when the annotation type has `@Inherited`? Use `getAnnotationsByType(Tag.class)`.
- Want to query **the container itself**? Use `getDeclaredAnnotation(Tags.class)` and `value()`.
- Merely calling `getAnnotation(Tag.class)` and seeing `null` is **not enough to conclude** there are no repeated `Tag` annotations: a container may be holding them.

This container “unwrapping” mechanism is logic implemented by **Reflection based on the annotation type**, not Java modifying bytecode at the moment you call `getAnnotationsByType`.

## 8. The Compiler Does Not Allow Arbitrary Repetition: A Valid Container Is Required

`@Repeatable` both enables repeated syntax and imposes compile-time conditions on the type pair. Common errors include:

### 8.1. Forgetting @Repeatable

```java
@interface Note {
    String value();
}

@Note("a")
@Note("b")
class Example {
}
```

This snippet is **intentionally invalid**. Merely having `@interface Note` with a `value` element does not make it repeatable. Even if you define `Notes { Note[] value(); }` separately, you must still apply `@Repeatable(Notes.class)` to `Note`.

### 8.2. Container Missing a Correctly Typed value() Element

```java
@Repeatable(Notes.class)
@interface Note {
    String value();
}

@interface Notes {
    String[] value(); // Wrong: must be Note[] value().
}
```

The compiler rejects this because `String[]` is not the `Note[]` annotation array type required by the `@Repeatable` relationship.

### 8.3. Container Has an Additional Element Without a Default

```java
@Repeatable(Notes.class)
@interface Note {
    String value();
}

@interface Notes {
    Note[] value();
    String owner(); // Wrong when Notes is a container: missing default.
}
```

The compiler cannot fill in `owner` automatically when grouping repeated `@Note` annotations. You can fix this to `String owner() default "system";` if the additional element is genuinely needed.

### 8.4. Container Retention Is Shorter Than the Primary Annotation

```java
@Retention(RetentionPolicy.RUNTIME)
@Repeatable(Notes.class)
@interface Note {
    String value();
}

@Retention(RetentionPolicy.CLASS)
@interface Notes {
    Note[] value();
}
```

This configuration is **invalid** because the container is retained for a shorter period than the primary annotation. When Reflection is needed, both should use `RUNTIME`.

### 8.5. Incompatible Targets

If `Note` is used on a method, the container must be valid for holding `@Note` uses at the method location. For example, setting both to:

```java
@Target({ElementType.TYPE, ElementType.METHOD})
@Repeatable(Notes.class)
@interface Note {
    String value();
}

@Target({ElementType.TYPE, ElementType.METHOD})
@interface Notes {
    Note[] value();
}
```

This is a compatible target configuration. If the targets differ in an invalid way, the compiler rejects the repeatable relationship. Locations such as `TYPE_USE`, `TYPE_PARAMETER`, `PARAMETER`, and declaration kinds have additional specific rules; do not assume arbitrary target sets are compatible just because they “look similar”.

### 8.6. @Inherited and @Documented

If the primary annotation uses `@Inherited`, the container must also have `@Inherited`. Similarly, if the primary annotation has `@Documented`, the container must also have `@Documented`. These meta-annotations are evaluated by the compiler together with the containing-type relationship.

However, **`@Inherited` does not cause annotations on methods, parameters, or interfaces to propagate automatically along inheritance hierarchies**. It has its own scope limited to classes and the corresponding Reflection lookups.

## 9. How Do a Single Use, Direct Repetition, and an Explicit Container Differ?

Cases using the same `Tag`/`Tags` pair:

| Source | Direct annotation type in the class file on the declaration | `getDeclaredAnnotationsByType(Tag.class)` |
| --- | --- | --- |
| `@Tag("solo")` | `Tag` | `[Tag("solo")]` |
| `@Tag("a") @Tag("b")` | `Tags` with `Tag[2]` | `[Tag("a"), Tag("b")]` |
| `@Tags({@Tag("a"), @Tag("b")})` | Explicit `Tags` | `[Tag("a"), Tag("b")]` |
| `@Tags({})` | `Tags` with an empty array | `[]` |
| No annotation applied | No `Tag`/`Tags` at the declaration | `[]` |

Implication for metadata-reading code: **do not check only for the presence of the container** and treat that as a necessary condition for having a repeatable annotation. A single `@Tag` can reside directly without a container.

When you need to read both single and repeated annotations, calling `getDeclaredAnnotationsByType(Tag.class)` is the simple approach, whereas a bytecode reader must know how to handle **both the direct form and the container form**.

## 10. What Is Different When Applying Repeated Annotations to a Parameter or Type-Use?

The containing annotation type mechanism remains the same: `@Repeatable(Container.class)` and **`T[] value()`**. However, the class file structure that stores the metadata depends on **where the annotation is applied**.

Example declared on a method parameter:

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.PARAMETER)
@Repeatable(Args.class)
@interface Arg {
    String value();
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.PARAMETER)
@interface Args {
    Arg[] value();
}

class Endpoint {
    void handle(@Arg("required") @Arg("public") String name) {
    }
}
```

This is an illustrative snippet; it requires importing the types from `java.lang.annotation` just like the main example.

In the class file, the container for parameter annotations resides in the appropriate **parameter annotations** metadata, such as `RuntimeVisibleParameterAnnotations`, rather than necessarily in the class's top-level `RuntimeVisibleAnnotations` attribute.

When reading with Reflection:

```java
java.lang.reflect.Method method =
        Endpoint.class.getDeclaredMethod("handle", String.class);

java.lang.reflect.Parameter parameter = method.getParameters()[0];

Arg[] values = parameter.getAnnotationsByType(Arg.class);
System.out.println(values.length); // 2
```

Distinguish the target locations:

- **Annotations declared on a parameter:** `Parameter.getAnnotationsByType(Arg.class)`.
- **Annotations applied to the parameter's type (`TYPE_USE`):** use `Parameter.getAnnotatedType()` and the appropriate `AnnotatedType` APIs; the metadata is stored in the corresponding type-annotations group.

Do not assume all annotations reside at the class level just because the attribute names all contain “Annotations”. When using `javap -v`, read the right method declaration section and the right location.

## 11. Why Does the Compiler Not Write Multiple Top-Level Tag Entries?

Class-file annotation metadata is structured around an **annotation type** and a list of **element-name/value** pairs. A container is the standard way to represent a list of annotations of the same type at a single location while preserving the metadata signature declared in the Java program.

Thanks to the container:

1. **The compiler validates the containing type:** `Tags.value()` must be `Tag[]`.
2. **The data is strongly typed:** each `Tag` still has its `value()` or its other elements.
3. **Repetition order is preserved:** repeated annotations are represented by element position in the array.
4. **Bytecode readers have a structured representation to decode:** read the container and extract the array of annotation values.
5. **Reflection can re-present them in a convenient form:** `getAnnotationsByType(Tag.class)` returns a `Tag[]` array suited to application logic.

Even so, **the compiler does not execute application behavior automatically** simply because an annotation is present. For example, `@Tag("red")` does not print `red` by itself; the program must have a consumer that reads the metadata and acts on it.

## 12. Class File Readers Must Handle Both Representations

If you build your own bytecode analysis tool (or use a library such as ASM), avoid assuming there is only the repeated annotation or only the container.

Processing approach:

```text
For annotation type T and container TC:
    read annotation metadata at the right location
    if annotation type T is found directly:
        collect one T
    if TC is found:
        read element "value" of type T[]
        collect each T in the array in order
    account for retention SOURCE/CLASS/RUNTIME
    account for class declaration, method, parameter, type-use
```

The diagram is a **guiding algorithm**, not standalone runnable Java code. For complex configurations, frameworks also need to account for `@Inherited`, multiple superclasses, and how annotations of the same type from parent and child classes are handled. **Merging metadata across multiple levels** does not happen automatically solely through the `@Repeatable` syntax.

If a tool only looks for a direct annotation with descriptor `L.../Tag;` without handling `Tags`, it will **miss repeated cases** packaged by the compiler. Conversely, looking only for `Tags` misses a single `@Tag`.

**Be careful about retention:** a bytecode reader can read `CLASS` annotations from `RuntimeInvisibleAnnotations`, whereas standard Java Reflection cannot read those annotations. Without `RUNTIME`, do not try to fix it by switching from `getAnnotation` to `getAnnotationsByType`; both depend on the appropriate runtime visibility.

## 13. Do Not Draw Wrong Conclusions About Annotation Processors

An annotation processor runs during compilation and uses the model from `javax.lang.model`; it can work with repeated annotations, but **the compile-time model is not simply a copy of runtime Reflection**.

- `getAnnotationMirrors()` works with the annotation model during compilation; its results and direct/container representation must be understood according to the API contract and processing stage.
- The `getAnnotationsByType(...)` APIs on the appropriate elements are designed to read annotations by type, including repeatable annotations according to the specified semantics.
- `javap -v` inspects **the output class file trace** and is the best way to observe the container representation after compilation.

Do not treat runtime Reflection results as absolute proof of callback order or how a particular processor traverses annotation mirrors. If your specific problem involves annotation processing, verify the processor's behavior separately against the compiler/API version in use.

## 14. Common Misconceptions

**“`@Repeatable` makes javac auto-generate a container class.”** False. `Tags` must be declared beforehand and have `Tag[] value()`. The compiler uses it to package the uses.

**“Two `@Tag` annotations will remain two separate direct annotations in `Multi.class`.”** False for the declaration annotation representation in the example: they are wrapped inside `@Tags`.

**“Even a single `@Tag` always turns into `@Tags({@Tag(...)})`.”** False. A single use is normally kept directly; check the `Single` example.

**“The container has `String[] value()` because `Tag.value()` returns `String`.”** False. The container must return an array of **`Tag` annotations**, namely `Tag[]`.

**“If `@Tags` is present, there are definitely at least two `@Tag` instances.”** False. There can be one element or an empty array; `@Tags({})` illustrates an empty array.

**“`getAnnotation(Tag.class)` returning `null` means Multi has no tags.”** False. Use `getAnnotationsByType(Tag.class)` or read `Tags`.

**“An annotation with CLASS retention is not in .class.”** False. It is present in the class file and visible with `javap`; it simply does not appear via standard Java Reflection.

**“Simply having `@Repeatable` makes the data queryable at runtime automatically.”** False. You must choose an appropriate retention (usually `RUNTIME` for both) and write code that reads the annotation.

**“`@Inherited` makes repeated annotations on interfaces or methods propagate down automatically.”** False. Inherited semantics apply appropriately to superclass relationships and Reflection APIs on classes.

**“Seeing a container in the class file guarantees that is how it was written in source.”** False. The source could have used multiple direct `@Tag` annotations **or** one explicit `@Tags({...})`; the class file can represent both through a container. You cannot reliably deduce the original source syntax solely from the presence of a container.

## 15. Practice Exercises

### Exercise 1 — Predicting the Bytecode Form

Given the pair `@Repeatable(Checks.class) @interface Check { int value(); }` and `@interface Checks { Check[] value(); }`, place two annotations `@Check(1) @Check(2)` on a class. In the class file's declaration metadata, what annotation type do you expect to see and what does `value()` contain?

**Answer:** the `Checks` container with an array of two `Check` annotations. Each `Check` has its own `int` value (`1`, `2`).

### Exercise 2 — A Single Use Without a Container

Why can `Single.class.getDeclaredAnnotation(Tags.class)` return `null` while `Single.class.getDeclaredAnnotationsByType(Tag.class).length` equals `1`?

**Answer:** a single direct `@Tag` does not require a container. The by-type API still retrieves it.

### Exercise 3 — CLASS Retention

On `BuildOnly.class` from the main example, `getDeclaredAnnotations().length` equals `0`. Which command is appropriate for verifying that `BuildMarks` is present in the class file?

**Answer:** `javap -v -p BuildOnly`, inspecting `RuntimeInvisibleAnnotations`.

### Exercise 4 — Identifying a Compiler Error

Find the error:

```java
@Repeatable(Checks.class)
@interface Check {
    String value();
}
@interface Checks {
    String[] value();
}
```

**Answer:** `Checks.value()` must be **`Check[] value()`**, not `String[]`.

### Exercise 5 — Annotation on a Parameter

With `@Arg("required") @Arg("public") String name` in section 10, if Reflection wants to retrieve both `Arg` annotations, should it use `Parameter.getAnnotation(Arg.class)` or `Parameter.getAnnotationsByType(Arg.class)`?

**Answer:** use `getAnnotationsByType(Arg.class)`, because `getAnnotation` does not automatically unwrap the container to produce the two-element list.

### Exercise 6 — Compiler Tracing

You only have `Multi.class` and no source code. `javap` shows a `Tags` container with two `Tag` instances. Can you conclude with certainty that the source wrote two `@Tag` lines instead of one `@Tags({...})`?

**Answer:** no. Both syntaxes can produce a similar container trace. The binary representation reveals the metadata structure and does not necessarily recover the exact original source syntax.

### Exercise 7 — Bytecode Scanning Tool

A bytecode scanner only looks for the descriptor of `Tag` in the top-level runtime-visible annotations list on the class. Why might it miss `Multi` while still seeing `Single`?

**Answer:** `Multi` is represented directly by `Tags`, whereas `Single` has `Tag` directly. The scanner needs to recognize both the repeated type and the containing type, and then read `Tags.value()`.

## 16. Checklist for Verifying Repeated Annotation Traces

1. **Identify annotation type T:** does it have `@Repeatable(Container.class)`?
2. **Check the container:** does it have `T[] value()` with the exact name, exact type, one dimension, and defaults on all other elements?
3. **Check meta-annotations:** are retention, target, `@Inherited`, and `@Documented` compatible?
4. **Count uses in source:** one `@T`, multiple `@T`, or an explicit container?
5. **Compile:** use `javac --release 17` or an appropriate JDK version, resolving any type errors before inspecting bytecode.
6. **Inspect the right class file:** run `javap -v -p` on the annotated class, without confusing it with the definition file `T.class`.
7. **Find the right attribute:** runtime-visible/invisible for declaration, parameter, or type-use depending on the target.
8. **Read the `value` array:** count and verify each child annotation rather than merely checking whether a container exists.
9. **Read via Reflection if retention is RUNTIME:** compare `getDeclaredAnnotations()` with `getDeclaredAnnotationsByType(T.class)` to see the difference between the physical representation and type-based querying.
10. **Do not assume business behavior automatically:** annotations are metadata; the program or tool that uses them must implement the consumption logic.

**Conclusion:** `@Repeatable` does not require the JVM to keep multiple identical annotations as independent top-level entries on the same declaration. When **multiple** annotations of type `T` are written repeatedly, the compiler uses a **pre-declared container** with the **`T[] value()`** signature to represent them. Class-file tooling sees the container and the array inside it; Reflection provides the `getAnnotationsByType` APIs to present the `T` annotations back. Understanding both perspectives helps explain why a single annotation, repeated annotations, and an explicit container have different representations yet can still yield the same kind of result when queried by type.
