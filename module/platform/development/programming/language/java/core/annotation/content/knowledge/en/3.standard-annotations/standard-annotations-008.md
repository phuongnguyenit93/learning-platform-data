# `javax.annotation.processing.Generated`: Identifying Generated Code in Java

When a code generator creates classes, methods, or fields from a schema, configuration, or another model, source code readers need to know which parts were created by a tool and which parts were written by a developer. Java provides the standard annotation **`javax.annotation.processing.Generated`** to mark declarations originating from a code generation process.

This annotation was introduced in Java 9, belongs to **module `java.compiler`** of the JDK, and can be used in Java 17/21 without third-party libraries when compiling regular applications. It carries metadata about the **code generator name**, generation date, and comments, but **does not generate code itself, does not lock files against editing, and does not change program behavior**.

## 1. What Is `@Generated` Used For?

Suppose an application generates Java classes from a data definition or API specification. If you open the resulting file, you might see:

```java
import javax.annotation.processing.Generated;

@Generated("com.example.codegen.CustomerGenerator")
public final class CustomerDto {
    private final long id;

    public CustomerDto(long id) {
        this.id = id;
    }

    public long id() {
        return id;
    }
}
```

The line `@Generated("com.example.codegen.CustomerGenerator")` means: **according to the metadata provided by whatever created the file**, the `CustomerDto` class is code generated by a tool named `com.example.codegen.CustomerGenerator`. This value is an identifier string; the compiler does not verify whether that tool actually exists or ran.

This marker helps with reading and maintaining a project:

- Recognize code regions that are typically regenerated from an input source, rather than places that should be edited directly for the long term.
- Distinguish tool-generated declarations from developer-written declarations, even when they reside in the same file.
- Allow certain source code analysis tools or documentation generation systems to recognize the origin of the code, **if the tool is programmed to support this annotation**.
- Provide traceability information for the code generator when multiple generators participate in a project.

**Key distinction:** `@Generated` is only a metadata label. Whether an IDE displays a label, a linter ignores the code, a coverage tool excludes it, or a build task regenerates the file all depend on the configuration and capabilities of each individual tool. Java does not apply those policies automatically.

## 2. Importing the Correct Standard Type

Use the exact fully qualified name:

```java
import javax.annotation.processing.Generated;
```

A simple example:

```java
@Generated("com.example.codegen.EntityGenerator")
class GeneratedEntity {
}
```

Since Java 9, `javax.annotation.processing.Generated` has resided in the JDK module **`java.compiler`**, under the `javax.annotation.processing` package. Even though the package name starts with `javax`, this is a standard API that still exists in modern JDKs such as Java 17 and 21.

Do not confuse it with:

| Name | Distinction |
| --- | --- |
| `javax.annotation.processing.Generated` | Standard API since Java 9, in the `java.compiler` module; this is the subject of this lesson. |
| `javax.annotation.Generated` | Legacy annotation from Java EE/JSR-250 APIs; it is in a different package and cannot be assumed to be present in modern JDKs. |
| `jakarta.annotation.Generated` | Annotation belonging to Jakarta Annotations; it requires the corresponding Jakarta library if the project uses it. |
| `javax.annotation.processing.Processor` | Interface used to **write an annotation processor**; not an annotation for marking generated code. |

When reading documentation or generated code, identify the actual import. Two annotations that share the simple name `Generated` but belong to different packages are not the same Java type.

If an application uses the Java Platform Module System with a *named* module and wants to use types in `java.compiler`, you can declare the dependency in `module-info.java`:

```java
module example.generated.app {
    requires java.compiler;
}
```

For a simple program compiled on the classpath with the JDK, there is no need to create a `module-info.java` file.

## 3. Syntax and the Three Elements of `@Generated`

The annotation has three elements:

| Element | Type | Required? | Meaning |
| --- | --- | --- | --- |
| `value()` | `String[]` | **Yes** | Name of the code generator, by convention the fully qualified name of the generator. |
| `date()` | `String` | No, defaults to `""` | Date/time when the source was generated, following the ISO 8601 convention. |
| `comments()` | `String` | No, defaults to `""` | Additional comments provided by the code generator. |

The shortest usage:

```java
@Generated("com.example.codegen.DtoGenerator")
class OrderDto {
}
```

Although `value()` has type `String[]`, Java allows passing a **single** `String` value without `{}` braces. The example above is equivalent to:

```java
@Generated(value = {"com.example.codegen.DtoGenerator"})
class OrderDto {
}
```

When using multiple elements, write explicit name–value pairs:

```java
@Generated(
    value = "com.example.codegen.DtoGenerator",
    date = "2026-01-15T09:30:00+07:00",
    comments = "Sinh từ lược đồ customer-v2"
)
class CustomerSchemaDto {
}
```

If multiple generators are recorded together, `value` accepts multiple strings:

```java
@Generated(value = {
    "com.example.codegen.ModelGenerator",
    "com.example.codegen.MapperGenerator"
})
class SharedGeneratedType {
}
```

Having multiple names in `value` does not mean the compiler automatically executes those generators. These are just strings supplied by whatever generated the code.

For `date`, the Java Javadoc requires the value to follow the **ISO 8601** standard. Use an accurate value if the generator actually has a generation timestamp; you can omit the element entirely when not needed. Because `date` is simply of type `String`, do not treat `@Generated` as a system that automatically issues or validates timestamps.

## 4. A Compilable and Runnable Java 17+ Example

The following example illustrates how a generator **might emit** Java code bearing `@Generated`. To learn the syntax, we write the sample code by hand; the program itself does not implement a generator.

Create a single file named **`GeneratedMarkerDemo.java`**:

```java
import javax.annotation.processing.Generated;

@Generated(
    value = "com.example.codegen.CustomerGenerator",
    comments = "Example source generated from a model"
)
final class GeneratedCustomer {
    private final long id;

    GeneratedCustomer(long id) {
        this.id = id;
    }

    @Generated("com.example.codegen.CustomerGenerator")
    String label() {
        return "Customer#" + id;
    }
}

public class GeneratedMarkerDemo {
    public static void main(String[] args) {
        GeneratedCustomer customer = new GeneratedCustomer(42);

        System.out.println(customer.label());
        System.out.println(
            GeneratedCustomer.class.isAnnotationPresent(Generated.class)
        );
    }
}
```

Open a terminal in the directory containing the file and run it with Java 17 or later:

```bash
javac -encoding UTF-8 GeneratedMarkerDemo.java
java GeneratedMarkerDemo
```

**`stdout` output:**

```text
Customer#42
false
```

Why is the second line `false`?

1. `@Generated` appears in the **source code** of `GeneratedCustomer` and the `label` method.
2. This standard annotation has `@Retention(RetentionPolicy.SOURCE)`: the information is discarded when the compiler creates the class file.
3. `Class.isAnnotationPresent(Generated.class)` checks for annotations available to reflection **at runtime**. Because `@Generated` is not retained until runtime, the result is `false`.

The `Customer#42` line still prints normally. The marker does not prevent constructors, methods, or Java logic from executing.

Note: the `javac` command here compiles the existing file; it does not invoke `CustomerGenerator` at all. The name in `value` can be any string, though you should record the exact name of the actual generator for the metadata to be useful.

## 5. `@Target` and `@Retention`: Where Can It Mark, and How Long Does It Persist?

In Java 21, the standard declaration of `Generated` has the equivalent meta-annotations:

```java
@java.lang.annotation.Documented
@java.lang.annotation.Retention(
    java.lang.annotation.RetentionPolicy.SOURCE
)
@java.lang.annotation.Target({
    java.lang.annotation.ElementType.PACKAGE,
    java.lang.annotation.ElementType.TYPE,
    java.lang.annotation.ElementType.METHOD,
    java.lang.annotation.ElementType.CONSTRUCTOR,
    java.lang.annotation.ElementType.FIELD,
    java.lang.annotation.ElementType.LOCAL_VARIABLE,
    java.lang.annotation.ElementType.PARAMETER
})
```

This is a **snippet illustrating the metadata** of the standard annotation, not a full redeclaration of `@Generated`.

Some examples of using it on valid locations (standalone illustration, no `main` needed):

```java
import javax.annotation.processing.Generated;

@Generated("com.example.codegen.TypeGenerator")
class GeneratedService {
    @Generated("com.example.codegen.FieldGenerator")
    private String name;

    @Generated("com.example.codegen.ConstructorGenerator")
    GeneratedService(String name) {
        this.name = name;
    }

    @Generated("com.example.codegen.MethodGenerator")
    String getName(
        @Generated("com.example.codegen.ParameterGenerator")
        String prefix
    ) {
        @Generated("com.example.codegen.LocalGenerator")
        String result = prefix + name;
        return result;
    }
}
```

`@Target` also allows marking packages, such as in a `package-info.java` file. Depending on the code structure, there is no need to attach the annotation to every sub-element: mark at a level clear enough to explain which code is owned by the generator.

**Important note on retention:** `RetentionPolicy.SOURCE` differs from `CLASS` and `RUNTIME`. After compilation, this annotation **is not present in the annotation metadata of `.class` files**. Therefore:

- Runtime reflection cannot retrieve `@Generated` from a class, method, or field.
- Libraries that only analyze post-compilation bytecode cannot rely solely on the presence of `javax.annotation.processing.Generated` in the class file.
- **Source code** analysis tools or annotation processors reading source during compilation can process the marker if configured and supported.
- `@Documented` only indicates that the annotation is suitable for inclusion in API documentation when processed by documentation tools; it does not change `SOURCE` to `RUNTIME`.

Do not write an `if` statement checking `@Generated` via reflection expecting to detect generated files. If a runtime signal is needed, you must design a different metadata mechanism with an appropriate `RUNTIME` retention.

## 6. When Should a Generator Attach `@Generated`?

A typical code generation flow looks like:

```text
Schema / configuration / API model
            |
            v
   Code generator reads input
            |
            v
Generates .java file with @Generated(...)
            |
            v
       javac compiles
            |
            v
        .class file
```

For example, a generator takes a `Customer` model and writes out `CustomerDto.java`. The generator should also emit the line:

```java
@Generated(
    value = "com.example.codegen.CustomerGenerator",
    comments = "Input: customer-schema"
)
```

before the class declaration, so readers know where the code originated. This association **is up to the generator**: `javac` does not automatically add the annotation to every piece of code created by a tool.

Some suitable scenarios include DTO classes generated from schemas, proxies or adapters emitted by build tools, client sources generated from OpenAPI, and mappers or helper code generated by annotation processors. However, each tool has its own policy; you should not assume all of them will attach this annotation.

When only **a few declarations** in a file are generated, marking those exact declarations can help distinguish them from handwritten parts. In practice, many projects organize auto-generated source code in a separate directory, yet `@Generated` still helps clearly identify provenance at the code level.

## 7. Avoiding Misconceptions About Builds, Testing, and Coverage

`@Generated` carries provenance information; Java does not assign any automatic governance semantics to it.

| Misconception | Reality |
| --- | --- |
| Adding `@Generated` causes Java to automatically generate a DTO or client | The annotation does not contain a code generator; a separate generator or annotation processor is required. |
| `@Generated` makes the class uneditable | The file can still be edited; the generator may overwrite the file if run again. |
| `@Generated` makes the compiler skip error checks | Generated Java code must still compile validly just like regular code. |
| `@Generated` automatically excludes code from unit tests or coverage | Depends on the tool and configuration; `SOURCE` does not exist in bytecode for post-compilation tools to read that annotation directly. |
| Use reflection to find classes with `@Generated` | Not possible: this annotation has `SOURCE` retention. |
| Having the annotation means the code was definitely generated by a tool | Java does not verify the authenticity of this metadata. |
| Specifying a generator name makes Java verify that the generator class exists | `value` is a `String[]`, not a `Class<?>` reference. |

For example, if you want coverage reports to ignore generated code, consult the specific documentation of your coverage tool or generated-source configuration. Do not rely solely on the `@Generated` marker to assume coverage will change. For tools that only inspect class files, be especially mindful of the `SOURCE` limitation.

## 8. Tips for Generating Stable and Maintainable Code

- **Prefer the fully qualified generator name** in `value`, such as `"com.example.codegen.DtoGenerator"`, rather than an ambiguous string like `"tool"`; this is also the convention stated in the Javadoc.
- **Consider `date` carefully:** if every generation run writes a new timestamp even when the code has not changed, Git diffs can become noisy. `date` defaults to `""`; omit it when timestamp tracking is unnecessary.
- **Write useful and non-sensitive `comments`**, such as a schema name or template version, instead of inserting secrets, tokens, or unnecessary internal information.
- **Edit the generation source or template when making lasting changes.** A file regenerated from scratch can wipe out manual edits in the output file.
- **Mark the exact scope of generated code.** It can be attached to a class or a specific method; avoid mistakenly attaching it to parts actively maintained by developers.
- **Keep generated source code independently compilable per project requirements.** `@Generated` does not make invalid imports or mismatched method signatures valid.

If the generator is written as an annotation processor, APIs such as `javax.annotation.processing.Processor`, `ProcessingEnvironment`, and `Filer` help read inputs and generate source files. **The code generator itself** decides whether to also write `@Generated` into the output source. Using this annotation and **building an annotation processor** are two separate tasks.

## 9. Common Syntax Errors

### Missing the `value` Element

Invalid:

```java
@Generated(date = "2026-01-15T09:30:00+07:00")
class WrongGeneratedMarker {
}
```

`value` is **required**, so there must be at least one generator name:

```java
@Generated(
    value = "com.example.codegen.DtoGenerator",
    date = "2026-01-15T09:30:00+07:00"
)
class CorrectGeneratedMarker {
}
```

### Confusing `comments` with `comment`

`comments` is the correct element name, with a trailing **s**:

```java
@Generated(
    value = "com.example.codegen.DtoGenerator",
    comments = "Generated from a schema"
)
class WithComment {
}
```

Writing `comment = "..."` will be rejected because the standard annotation does not have an element named `comment`.

### Passing the Wrong Type

`value()` is `String[]`, while `date()` and `comments()` are `String`; the following snippets have type errors:

```java
@Generated(123)                         // Wrong: value requires String/String[]
@Generated(value = String.class)        // Wrong: does not accept Class
@Generated(value = "Generator", date = 2026) // Wrong: date requires String
```

These are isolated lines illustrating errors, not a complete program meant to compile.

### Mixing Up Packages When Upgrading Java Versions

If you encounter the error `package javax.annotation does not exist` caused by using `import javax.annotation.Generated`, first determine **which annotation** the project needs. For marking generated code using JDK Java 17+, change the import properly to `javax.annotation.processing.Generated` when the tool/project allows it. If the code-emitting tool requires a different annotation, check the appropriate configuration or dependency; do not swap packages arbitrarily because they are distinct types.

## 10. Self-Check

1. Is `@Generated("com.example.codegen.ApiGenerator")` without `{}` braces valid? **Yes**: a single string is treated as a single element of `String[] value`.
2. Can you call `CustomerDto.class.getAnnotation(Generated.class)` to read the generator name at runtime? **No**: the retention is `SOURCE`, so the annotation will not be found.
3. Is `@Generated(value = "Generator", comments = "v1")` syntactically valid? **Yes**; though it is better to use the fully qualified name of the generator for clearer metadata.
4. Does `@Generated(comments = "from OpenAPI")` compile? **No**: `value` is missing.
5. Is it mandatory to use `date` and `comments`? **No**: both default to an empty string.

Official reference documentation: [Java SE 21 — `javax.annotation.processing.Generated`](https://docs.oracle.com/en/java/javase/21/docs/api/java.compiler/javax/annotation/processing/Generated.html). The standard declaration explicitly specifies `@Documented`, `@Retention(SOURCE)`, `@Target`, the elements, and when the API was introduced.
