# Random Value Streams and Size Limits in Java

When you need 5 die rolls, 1,000 test data points, or a stream of random numbers to process piece by piece, Java can directly create an `IntStream`, `LongStream`, or `DoubleStream`. Instead of allocating and storing a huge array up front, you declare the number source, bound the element count, and attach transformations before execution.

Two questions must be kept separate:

1. **Value range:** What interval is each number drawn from? For example, a die needs integers from 1 to 6, i.e., the Java interval `[1, 7)`.
2. **Stream size:** How many elements are generated? For example, 5 die rolls, i.e., `streamSize = 5` or `limit(5)`.

Value range (`origin`, `bound`) and stream size (`streamSize`, `limit`) are completely different things. This lesson explains how to create random number sources in Java 17+, how to bound streams, how operation order affects results, laziness, resource management, and common mistakes.

## 1. What is a random number stream?

A Java Stream is a **data-processing pipeline**, not a collection holding pre-existing elements. For random numbers, a source like `Random.ints()` supplies values as the pipeline requests them. Processing stages can include `map`, `filter`, and `limit`; a terminal operation such as `toArray`, `sum`, `forEach`, or `count` triggers the pipeline.

~~~text
Random / RandomGenerator
          |
          v
  ints / longs / doubles
          |
          v
 filter / map / limit / skip  (if any)
          |
          v
  toArray / sum / forEach ...  (terminal)
~~~

The three primitive stream types avoid boxing every `int`, `long`, and `double` into `Integer`, `Long`, and `Double` objects across many operations.

| Source | Stream type | Element type |
|---|---|---|
| `random.ints(...)` | `IntStream` | `int` |
| `random.longs(...)` | `LongStream` | `long` |
| `random.doubles(...)` | `DoubleStream` | `double` |
| `Stream.generate(supplier)` | `Stream<T>` | Object type produced by `Supplier` |

A random stream **can be finite or effectively unlimited**. The Javadoc calls overloads that omit a size *effectively unlimited*: they are designed to supply a huge stream of values until the pipeline stops, not meaning the program allocates infinite memory or creates infinitely many objects when the method is called.

**Note:** Numbers generated by `Random` are *pseudorandom*. Java Streams do not turn them into cryptographic random numbers. Probabilistic behavior, seed reproducibility, and security suitability are separate concerns from stream size.

## 2. Random overloads: finite and effectively unlimited

`java.util.Random` provides parallel overload groups for `ints`, `longs`, and `doubles`:

| Method signature | Element count | Value range |
|---|---|---|
| `random.ints()` | Effectively unlimited | Entire `int` range |
| `random.ints(streamSize)` | Exactly `streamSize` before filtering operations | Entire `int` range |
| `random.ints(origin, bound)` | Effectively unlimited | `origin <= x < bound` |
| `random.ints(streamSize, origin, bound)` | Exactly `streamSize` before filtering operations | `origin <= x < bound` |
| `random.longs(...)` | Same four overload forms | `long` numbers |
| `random.doubles(...)` | Same four overload forms | `double` numbers |

With `doubles()` or `doubles(streamSize)` without range arguments, every element lies in `[0.0, 1.0)`. With `ints()` and `longs()` without range arguments, the source emits values across the full range of the respective integer type.

Example:

~~~java
Random random = new Random();

IntStream anyIntegers = random.ints(8);
IntStream dice = random.ints(8, 1, 7);
LongStream ids = random.longs(8, 100L, 1000L);
DoubleStream fractions = random.doubles(8); // 0.0 <= x < 1.0
~~~

These lines are an illustrative snippet inside a method, requiring `import java.util.Random` and `java.util.stream.*`. They describe **four separate streams**. A stream should only be used for one terminal operation; create a new stream when you need to compute again.

Do not confuse `random.ints(5)` with `random.ints(0, 5)`:

- `ints(5)` has **one `long` size parameter**, generating 5 `int` values across the full value range.
- `ints(0, 5)` has **two `int` range parameters**, creating an effectively unlimited stream of 0, 1, 2, 3, or 4.
- `ints(5, 0, 5)` has **three parameters**, generating exactly 5 numbers in `[0, 5)`.

This is a very easy mistake because `5` can mean either a count or a range bound depending on the method signature.

## 3. Bounding size directly at the source with streamSize

To draw exactly `n` generated values, the concise way is to use the overload with `streamSize`:

~~~java
int[] fiveDice = new Random(42L)
        .ints(5, 1, 7)
        .toArray();
~~~

`fiveDice.length == 5`. Every element satisfies `1 <= x && x < 7`. The first argument is **the element count**, and the remaining two are **inclusive lower bound, exclusive upper bound**.

Example showing the difference between `streamSize` and range:

~~~java
new Random().ints(5, 1, 7);    // Finite source: 5 numbers in [1,7)
new Random().ints(100, 1, 7);  // Finite source: 100 numbers in [1,7)
new Random().ints(5, 10);      // Effectively unlimited source: numbers in [5,10)
~~~

These three declaration lines do not run a terminal operation, so they are not data-printing examples. Do not create and discard streams in application code; the example merely illustrates overload semantics.

`streamSize` has type `long` and must be **non-negative**. `streamSize = 0` produces an empty stream; negative values throw `IllegalArgumentException`. A huge size, while valid as an argument, may still be infeasible if you call `toArray()` or collect all elements into memory. For sequential element-by-element processing, `forEach` or a reduction may consume little memory while still taking time proportional to the element count.

**When to choose the finite overload?** When the requirement already knows the sample count up front—such as generating 500 values as a test fixture or 20 values for a report—this expresses the intent most clearly.

## 4. Creating an effectively unlimited stream and applying limit(n)

`limit(long maxSize)` is an *intermediate operation* creating a pipeline with at most `maxSize` elements from the upstream source:

~~~java
int[] fiveDice = new Random(42L)
        .ints(1, 7)     // effectively unlimited source
        .limit(5)       // limit to at most 5 elements
        .toArray();     // trigger generation and collect
~~~

With a pseudorandom source that always has enough values, `limit(5)` with no subsequent filtering yields exactly 5 elements. Yet the general rule of `limit(n)` is **at most n**, not always exactly `n`: if the upstream source only had 3 elements, `limit(5)` would still yield only 3 elements.

Both approaches below express the intent to generate 5 numbers in `[1,7)`:

~~~java
new Random(42L).ints(5, 1, 7).toArray();        // Limit at the source
new Random(42L).ints(1, 7).limit(5).toArray();  // Limit in the pipeline
~~~

Specific numbers may differ by algorithm/generator type and how the source is consumed, especially with parallel streams; for `java.util.Random` with the same sequential call chain, a seed allows sequence replay. **Choose the form that expresses the right rule**, not because it happens to look like a specific sequence of numbers.

`limit(0)` returns an empty stream; `limit(-1)` throws `IllegalArgumentException`. If `n` comes from user input, validate `0 <= n <= maxAllowed` before building the pipeline instead of letting a massive request exhaust CPU/memory.

## 5. Standalone Java 17+ example

Create the file `RandomStreamSizeDemo.java`:

~~~java
import java.util.Arrays;
import java.util.Random;

public class RandomStreamSizeDemo {
    public static void main(String[] args) {
        int[] five = new Random(42L).ints(5, 1, 7).toArray();
        System.out.println("five = " + Arrays.toString(five));
        System.out.println("five length = " + five.length);
        System.out.println("five bounds = "
                + Arrays.stream(five).allMatch(x -> x >= 1 && x < 7));

        int[] four = new Random(99L)
                .ints(0, 100)
                .limit(4)
                .toArray();
        System.out.println("four = " + Arrays.toString(four));
        System.out.println("four length = " + four.length);

        int[] tenEven = new Random(7L)
                .ints(0, 100)
                .filter(x -> x % 2 == 0)
                .limit(10)
                .toArray();
        System.out.println("tenEven length = " + tenEven.length);
        System.out.println("tenEven bounds = "
                + Arrays.stream(tenEven)
                        .allMatch(x -> x >= 0 && x < 100 && x % 2 == 0));

        int[] finiteFiltered = new Random(5L)
                .ints(6, 0, 10)
                .filter(x -> x >= 5)
                .toArray();
        System.out.println("finiteFiltered = "
                + Arrays.toString(finiteFiltered));
        System.out.println("finiteFiltered length = " + finiteFiltered.length);

        System.out.println("empty size = "
                + new Random(8L).ints(0, 10, 11).count());

        long[] longs = new Random(4L).longs(3, 10L, 20L).toArray();
        double[] doubles = new Random(4L)
                .doubles(3, 0.5, 1.5)
                .toArray();
        System.out.println("long bounds = "
                + Arrays.stream(longs).allMatch(x -> x >= 10L && x < 20L));
        System.out.println("double bounds = "
                + Arrays.stream(doubles).allMatch(x -> x >= 0.5 && x < 1.5));
    }
}
~~~

Compile and run:

~~~bash
javac RandomStreamSizeDemo.java
java RandomStreamSizeDemo
~~~

One result with `java.util.Random` per the standard algorithm:

~~~text
five = [3, 4, 1, 3, 1]
five length = 5
five bounds = true
four = [87, 58, 29, 11]
four length = 4
tenEven length = 10
tenEven bounds = true
finiteFiltered = [7, 6, 5]
finiteFiltered length = 3
empty size = 0
long bounds = true
double bounds = true
~~~

Meaning of each part:

1. `ints(5, 1, 7)` gets its size at **the source**, yielding 5 numbers with faces from 1 to 6. Repeated values such as 3 and 1 are valid: random generation **does not mean without duplicates**.
2. `ints(0, 100).limit(4)` uses an effectively unlimited source and takes 4 elements.
3. `filter(even).limit(10)` keeps drawing from the effectively unlimited source until **10 even numbers are collected** in this example; the number of draws can exceed 10.
4. `ints(6, 0, 10).filter(x >= 5)` starts from **6 source elements**, and after filtering only 3 elements remain for the chosen seed. Setting size at the source does not mean the final output after `filter` still has to contain 6 elements.
5. `ints(0, 10, 11)` uses `streamSize = 0`; terminal `count()` returns `0`. The `longs`/`doubles` sources also operate with independent sizes and ranges.

The example uses seeds purely to make output easy to verify. Do not use fixed seeds for security purposes or in production when unpredictable data is required.

## 6. Value range: origin inclusive, bound exclusive

For bounded overloads, the fundamental rule is:

~~~text
origin <= value < bound
~~~

Examples:

| Intent | Call |
|---|---|
| Roll a die 20 times, 1–6 each | `random.ints(20, 1, 7)` |
| Draw 10 integers from 0 to 9 | `random.ints(10, 0, 10)` |
| Draw 4 integers from -3 to 3 | `random.ints(4, -3, 4)` |
| Draw 5 `long` values in [100, 200) | `random.longs(5, 100L, 200L)` |
| Draw 6 `double` values in [0.25, 0.75) | `random.doubles(6, 0.25, 0.75)` |

Passing `origin >= bound` to a bounded overload throws `IllegalArgumentException`; setting both bounds equal does not produce a stream full of that single number as many mistakenly think. For `double`, bounds must be finite and form a valid interval; do not pass `Double.NaN` or infinity as bounds.

Be careful when trying to "include the maximum value": for `int`, do not blindly add `1` to `Integer.MAX_VALUE`, because overflow breaks the interval. Similarly, do not use `(int)(Math.random() * range)` for large ranges if it introduces distribution bias or integer overflow. Prefer overloads with `origin`/`bound` and explicitly check cases that must include an extreme bound.

An interval with only **one valid value**, such as `[5,6)`, produces all 5s. That obeys the contract even though it provides no variety. To get multiple distinct numbers, you need a sufficiently wide range, and duplicates can still occur.

## 7. Order of filter and limit determines result size

`filter` removes elements failing the predicate; `limit` caps the number of elements passing **up to its position** in the pipeline. Therefore, these two chains are not equivalent:

~~~java
// A: take at most 10 source elements, then filter even
int[] a = new Random(7L)
        .ints(0, 100)
        .limit(10)
        .filter(x -> x % 2 == 0)
        .toArray();

// B: filter even first, then take at most 10 even numbers
int[] b = new Random(7L)
        .ints(0, 100)
        .filter(x -> x % 2 == 0)
        .limit(10)
        .toArray();
~~~

These snippets need `import java.util.Random;` and belong inside a method.

| Pipeline | Where the limit applies | Output element count |
|---|---|---|
| `limit(10).filter(even)` | At most 10 source numbers | Anywhere from 0 to 10 |
| `filter(even).limit(10)` | At most 10 **filtered** numbers | 10 if the source eventually supplies enough matching numbers and the terminal finishes |
| `ints(10, 0, 100).filter(even)` | Exactly 10 source numbers | Anywhere from 0 to 10 |
| `ints(10, 0, 100)` | 10 source numbers with no removal | Exactly 10 |

**Application rule:** if the problem says **make at most 10 attempts** and keep valid results, place the source/limit before `filter`. If the problem says **find at most 10 valid results**, place `filter` before `limit` and consider capping attempts or total time.

With an effectively unlimited source, `filter(...).limit(10)` can run for a very long time or never terminate if the condition is never satisfied. For example, `ints(1, 7).filter(x -> x == 7).limit(1)` will never find `7` because the source only generates `1–6`.

To cap both **attempts** and **valid results**, use:

~~~java
int[] accepted = new Random()
        .ints(100, 0, 100)          // try at most 100 samples
        .filter(x -> x > 95)        // keep only 96..99
        .limit(5)                   // at most 5 results
        .toArray();
~~~

The result can have fewer than 5 numbers if not enough valid samples appear. This guarantees a hard bound on the number of samples examined rather than relying solely on the condition eventually occurring.

## 8. Streams are lazy: when does the generator actually run?

The following only **describes the pipeline**:

~~~java
Random random = new Random(42L);
IntStream stream = random.ints(1, 7).limit(3);
~~~

The source emits numbers when elements are requested by a terminal operation. Once you call:

~~~java
int[] values = stream.toArray();
~~~

the pipeline actually pulls numbers from the source.

One easy misconception: `count()` does not always force the pipeline to invoke the generator element by element. A finite stream with a known size can allow the library to optimize `count()` without generating the elements. Therefore, **do not use `peek()` execution counts or generator state after `count()` to verify how many numbers the source emitted**. If you need to inspect actual values, use `toArray()`, `forEach()`, or an actual value-dependent computation.

After executing a terminal operation, that stream **cannot be reused**:

~~~java
IntStream numbers = new Random().ints(5);
int[] first = numbers.toArray();

// numbers.sum(); // IllegalStateException: stream has already been operated upon
~~~

Create a new pipeline from the source or use a supplier returning a fresh stream if you need to run again. If both pipelines share the same `Random` object, the generator's state has advanced when consumed; the second run will usually differ from the first.

## 9. When can Stream.generate and Math.random be used?

Besides `Random.ints(...)`, Java supports:

~~~java
import java.util.stream.Stream;
import java.util.concurrent.ThreadLocalRandom;

int[] dice = Stream.generate(
        () -> ThreadLocalRandom.current().nextInt(1, 7))
        .limit(5)
        .mapToInt(Integer::intValue)
        .toArray();
~~~

`Stream.generate(Supplier<T>)` creates an **effectively unlimited** object stream; `limit(5)` makes the collected portion finite. For primitive numbers, `random.ints(5, 1, 7)` is usually shorter, directly expresses the value range, and avoids boxing/unboxing. `Stream.generate` is useful when elements must be complex objects, such as mock records with multiple fields.

`Math.random()` returns a `double` from 0 (inclusive) to 1 (exclusive). You can write `Stream.generate(Math::random).limit(5)`, but it produces a boxed `Stream<Double>`, and seed control is not as direct as creating `new Random(seed)`. Do not mechanically write `(int)(Math.random() * n)` when range-based integer APIs already exist.

Since Java 17, `java.util.random.RandomGenerator` standardizes the API across many generator algorithms. `java.util.Random` implements this interface. When you need to pick an appropriate algorithm or a specialized generator for parallel execution, you can design around `RandomGenerator`; **regardless of generator, you still must check stream size, value range, and randomness quality for the intended purpose**.

## 10. Seeds and reproducibility in testing

Seeds let pseudorandom results be reproduced when keeping the same algorithm, call pattern, and consumption order. Example:

~~~java
int[] left = new Random(123L).ints(5, 0, 10).toArray();
int[] right = new Random(123L).ints(5, 0, 10).toArray();

System.out.println(Arrays.equals(left, right)); // true
~~~

Add `import java.util.Arrays;` alongside `java.util.Random`.

For `java.util.Random` specifically, Java specifies the algorithm to ensure repeatability when two instances share the same seed and operation sequence. However, do not assume every `RandomGenerator` implementation must produce the **exact same** sequence as `Random`, or that the same seed with a different algorithm/parallelism produces the same sequence.

When writing tests, prioritize verifying properties:

- **Size:** exact expected element count or within imposed bounds.
- **Range:** every value lies in `[origin, bound)`.
- **Valid data:** `filter`, `map`, and invariants are satisfied.
- **Reproducibility:** use seeds and deterministic generators when exact sequence matching is what needs verification.

Never use a fixed seed to create login tokens, temporary passwords, or security values. `Random` is not designed to resist prediction; security cases require `SecureRandom` and proper design.

## 11. Size limits and resource management

**Never collect an effectively unlimited stream without bounding it first.** The example below is dangerous:

~~~java
// Do not run:
new Random().ints().toArray();
~~~

The array to allocate has no feasible size limit, and the program can run out of memory or fail to terminate. An unbounded pipeline with a terminal operation like `sum()` or `forEach()` may likewise never finish without a stopping condition.

If you only need a single value, use `random.nextInt(origin, bound)` on the proper API or `random.ints(origin, bound).findAny()`, rather than creating a large set. For a batch of 50,000 elements where you only need statistics, process directly:

~~~java
long numberOfEven = new Random()
        .ints(50_000, 0, 1_000)
        .filter(x -> x % 2 == 0)
        .count();
~~~

Because `filter` drops elements based on their values, the terminal here must evaluate how many elements satisfy the predicate; the total input count is explicitly finite. Do not rely on `count()` of a plain pipeline alone to conclude all elements were materialized.

**User-supplied limits:** validate size bounds against available resources before calling the source. Some valid `long` `streamSize` values exceed Java array allocation limits; `limit` does not mean free memory if followed by `toArray()`.

**Do not sort an entire infinite source:** `random.ints().sorted().limit(10)` needs to know the order of all inputs before picking ordered elements, so it cannot complete usefully. Conversely:

~~~java
int[] orderedSample = new Random()
        .ints(0, 100)
        .limit(10)
        .sorted()
        .toArray();
~~~

This takes a finite sample **first**, then sorts only the collected samples. It does not find "the 10 smallest numbers out of infinity" and does not guarantee no duplicates.

**`distinct()` and finite domains:** `ints(1, 7)` has only 6 distinct values. Calling `distinct().limit(7)` on this source will never collect 7 values. If you want 6 unique numbers from 1–6, take a finite set and shuffle it using an appropriate method, or sample without replacement; drawing random numbers individually does not guarantee uniqueness.

## 12. Handling parallel streams cautiously

You can call `parallel()` on a stream, yet **enabling parallel is not automatically faster or still reproducible**:

~~~java
long count = new Random()
        .ints(100_000, 0, 1_000)
        .parallel()
        .filter(x -> x % 2 == 0)
        .count();
~~~

`Random` is thread-safe, but multiple threads sharing a generator can contend on state and degrade performance. The order in which numbers are drawn in a parallel stream can vary with execution scheduling, so **the same seed is not enough to guarantee identical element sequences/outputs under parallel processing**. Avoid tests relying on an exact sequence after `parallel()` unless you have fixed, verified, and accepted the full ordering contract of the chosen algorithm/generator.

For high-performance multithreaded workloads, consider `ThreadLocalRandom` or generators in `RandomGenerator.SplittableGenerator` such as `SplittableRandom` with proper state splitting. Never use a single `SplittableRandom` concurrently across threads without explicit thread-management design.

`limit()` on a stream with an *encounter order* can incur heavy coordination overhead in parallel mode because it must preserve the exact first elements; for an unordered source, guarantees and chosen elements may differ. Therefore:
- Determine whether the result needs ordering or only aggregate properties.
- Benchmark on realistic data before choosing parallel execution.
- Keep operations inside lambdas independent of source state and avoid shared side effects.

For exercises or moderately sized batches, **sequential** streams are usually easiest to reason about and verify.

## 13. Parameter errors and boundary cases

| Case | Outcome / handling |
|---|---|
| `new Random().ints(0, 1, 7)` | Empty stream, no samples |
| `new Random().ints(-1, 1, 7)` | `IllegalArgumentException`: negative size |
| `new Random().ints(5, 7, 7)` | `IllegalArgumentException`: lower bound not less than upper bound |
| `new Random().ints(1, 7).limit(-1)` | `IllegalArgumentException`: negative limit |
| `new Random().doubles(5, Double.NaN, 1.0)` | `IllegalArgumentException`: invalid bound |
| `new Random().ints(1, 7).limit(0)` | Empty stream |
| `new Random().ints(3, 1, 7).limit(5)` | At most 3 elements, does not generate extra up to 5 |
| `new Random().ints(3, 1, 7).filter(x -> false)` | No elements pass the filter |

Especially for `int` and `long`, `bound - origin` can overflow in custom range-calculation code. Overloads `Random.ints(origin, bound)` and `longs(origin, bound)` are written to handle valid ranges that are hard to express with simple subtraction. Check `origin < bound` and prefer the standard API over custom integer multiplication/division formulas that could overflow.

When an output element count must be **exact**, account for any `filter` or `distinct` after bounding. Value-transforming steps (like `map`) preserve count; filtering/deduplicating steps like `filter`/`distinct` can reduce count.

## 14. Two complete application scenarios

### A. Generating 12 die rolls to compute their sum

~~~java
Random rng = new Random(2026L);
int total = rng.ints(12, 1, 7).sum();
System.out.println(total);
~~~

Placed inside a method with `import java.util.Random;`. `sum()` consumes a finite stream of 12 die rolls (duplicates allowed). It does not draw 12 unique faces. With large sample counts or large values, watch for `int` overflow when using `sum()`; switch to `mapToLong` or overflow-checked addition as needed.

### B. Generating up to 20 valid values from at most 1,000 attempts

~~~java
Random rng = new Random();
int[] accepted = rng.ints(1_000, 0, 10_000)
        .filter(x -> x % 10 == 0)
        .limit(20)
        .toArray();
System.out.println("accepted = " + accepted.length);
~~~

This example has two independent limits: draw at most 1,000 source samples and keep at most 20 filtered results. If the system **strictly requires 20 results**, handle `accepted.length < 20` with an explicit application strategy (e.g., report insufficient samples, retry with a bounded attempt cap, or switch algorithms). Never assume probability will always supply enough values.

## 15. Self-check

**Question 1:** How many elements does `new Random().ints(5, 10)` have before limiting?

**Answer:** No size limit was passed; this is the overload taking `origin = 5`, `bound = 10`. The source emits integers 5–9 and is effectively unlimited. To generate 5 numbers in this range, write `ints(5, 5, 10)` or `ints(5, 10).limit(5)`.

**Question 2:** Does `random.ints(10, 1, 7).filter(x -> x == 6).count()` always return 10?

**Answer:** No. 10 is the initial sample count; after filtering, only occurrences of `6` are counted. The result lies in `[0,10]`.

**Question 3:** Is `random.ints(1, 7).filter(x -> x == 7).limit(1).findFirst()` guaranteed to terminate?

**Answer:** No. The interval `[1,7)` does not contain `7`; the filter never accepts any value. Control valid ranges and maximum attempts.

**Question 4:** Should you use `random.ints().sorted().limit(10).toArray()` to get the 10 smallest numbers?

**Answer:** No. `sorted()` must consume the entire input to sort, so an effectively unlimited source cannot be processed that way. To sort 10 samples, use `ints().limit(10).sorted().toArray()`.

**Question 5:** Can two `new Random(42)` instances running sequentially with the same `ints(5,1,7).toArray()` pipeline produce the same result?

**Answer:** Yes, for `java.util.Random` with the same seed and call chain per contract. Do not generalize that to "every generator algorithm and every parallel stream produces identical results just because the seed is the same".

**Question 6:** If a requirement states "no more than 100 attempts, yet up to 5 even numbers", where should `limit` be placed?

**Answer:** Use the finite source `ints(100, origin, bound)`, followed by `filter(even).limit(5)`. Fewer than 5 results may be returned if 100 attempts do not produce enough even numbers; the attempt limit is still enforced.

## 16. Key takeaways and official documentation

- `ints(streamSize, origin, bound)` is the direct choice when **both size and value range are known up front**.
- `ints(origin, bound).limit(n)` makes sense when an effectively unlimited source needs to be capped in the pipeline; always attach a terminal operation when actual processing is intended.
- `origin` is **inclusive**, `bound` is **exclusive**; `streamSize` and `limit` must be non-negative. `limit(n)` sets **a ceiling of n elements at its exact position**, not guaranteeing `n` elements survive subsequent filtering.
- Streams are lazy; `count()` can be optimized away when the source has a known size. Do not rely on side effects in the pipeline to conclude all values were generated.
- Bound attempt counts, result counts, and resources; choose a generator suited to your purpose, especially when parallel processing or cryptographic requirements apply.
