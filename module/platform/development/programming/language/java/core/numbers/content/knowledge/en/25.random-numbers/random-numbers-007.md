# Origin, Bound Ranges, and the Exclusive Upper Bound Rule for Random Numbers in Java

## 1. Understanding the [origin, bound) interval

In Java's random number generation APIs that take `origin` and `bound` parameters, the central rule is:

**`origin` is inclusive, while `bound` is exclusive.**

Mathematical notation: **[origin, bound)**, equivalent to the condition:

~~~text
origin <= result < bound
~~~

For **integers**, the set of possible return values is finite and enumerable. For example:

| Java 17 call | Exact interval | Possible `int` values |
|---|---|---|
| `rng.nextInt(0, 5)` | [0, 5) | 0, 1, 2, 3, 4 |
| `rng.nextInt(1, 7)` | [1, 7) | 1, 2, 3, 4, 5, 6 |
| `rng.nextInt(-3, 4)` | [-3, 4) | -3, -2, -1, 0, 1, 2, 3 |
| `rng.nextInt(7, 8)` | [7, 8) | only 7 |
| `rng.nextInt(-5, 0)` | [-5, 0) | -5, -4, -3, -2, -1 |
| `rng.nextInt(5, 5)` | empty interval | throws `IllegalArgumentException` |

For [0, 5), the number 5 **can never** be generated by this exact call. For [-3, 4), `-3` **can** appear and `4` **cannot** appear. The rule remains identical whether `origin` is negative, positive, or zero.

Expressed arithmetically on integers, the number of elements in `[origin, bound)` is `bound - origin`, **interpreted mathematically**. If this difference is computed with `int` subtraction in Java, the operation can overflow; do not take the formula and assume `int` can always hold the result.

### Why choose an exclusive upper bound?

Half-open intervals make interval size calculation and concatenation clean. When `[a, b)` and `[b, c)` are joined, they do not overlap at `b` and cover `[a, c)`. Index-based sequence slicing uses the same convention: an array of length `n` has indices `[0, n)`, so `nextInt(n)` is directly suited to pick a valid index when **n > 0**.

Do not confuse the word “bound” with “maximum possible return value”. In `nextInt(origin, bound)`, if the interval is non-empty, the largest integer that can be returned is **bound - 1**, except when speaking purely mathematically as an explanation; in code, you must still watch for overflow near extreme values.

## 2. Common APIs in Java 17+

Java 17 provides the `java.util.random.RandomGenerator` interface, offering consistent calls across different generators. A `java.util.Random` can be used through this interface:

~~~java
import java.util.Random;
import java.util.random.RandomGenerator;

RandomGenerator rng = new Random(2026L);
int roll = rng.nextInt(1, 7); // 1..6
~~~

The snippet above is an **illustration placed inside a method**, without `main`; a complete program example is in section 5.

| API | Returned range | Main constraints |
|---|---|---|
| `rng.nextInt()` | Any `int` value | No origin/bound limits |
| `rng.nextInt(bound)` | [0, bound) | `bound > 0` |
| `rng.nextInt(origin, bound)` | [origin, bound) | `origin < bound` |
| `rng.nextLong(origin, bound)` | [origin, bound) on `long` | `origin < bound` |
| `rng.nextDouble()` | [0.0, 1.0) | Floating-point value |
| `rng.nextDouble(origin, bound)` | [origin, bound) on `double` | Both bounds finite and `origin < bound` |
| `rng.nextFloat(origin, bound)` | [origin, bound) on `float` | Both bounds finite and `origin < bound` |
| `random.ints(size, origin, bound)` | Stream of `size` `int` values in [origin, bound) | `size >= 0` and `origin < bound` |
| `random.longs(size, origin, bound)` | `long` stream with the same half-open rule | Valid bounds, non-negative size |
| `random.doubles(size, origin, bound)` | `double` stream with the same half-open rule | Finite bounds, non-negative size |

The `rng` rows assume `rng` implements `RandomGenerator`. `Random` has `nextInt(int bound)` and implements `RandomGenerator` in Java 17; thus `nextInt(origin, bound)` and `nextLong(origin, bound)` overloads can be called through the interface. `ThreadLocalRandom.current()` and `SplittableRandom` also provide matching bounded overloads.

Usage example:

~~~java
int dice = java.util.concurrent.ThreadLocalRandom.current().nextInt(1, 7);
long idPart = java.util.concurrent.ThreadLocalRandom.current()
        .nextLong(1_000L, 10_000L);
~~~

This is an illustrative snippet inside a method: `dice` lies in `[1, 7)`, and `idPart` lies in `[1000, 10000)`. This is **not** a way to generate secret codes; ordinary generators are designed for pseudorandom tasks and are not inherently secure against an adversary.

When you need to keep a `seed` that can reproduce tests, `new Random(seed)` is a straightforward choice. `ThreadLocalRandom.current()` fits when multiple threads need random numbers, though it offers no standard API to set a seed directly. `SplittableRandom` supports splitting generators for computational tasks; generators may produce different sequences even for the same seed input.

## 3. How does nextInt(bound) differ from nextInt(origin, bound)?

With `nextInt(bound)`, **the implicit origin is 0**. `nextInt(6)` generates a number in `{0, 1, 2, 3, 4, 5}`. To simulate a die from 1 to 6:

~~~java
int diceA = rng.nextInt(6) + 1; // 1..6, bound must be positive
int diceB = rng.nextInt(1, 7); // 1..6, explicitly states the range
~~~

Both expressions have the same set of possible return values, but do not expect identical results on consecutive calls because each call consumes generator state.

If you want an integer in `[-5, 5)`, you **cannot** pass a negative bound to `nextInt(bound)` and expect negative values:

~~~java
int signed = rng.nextInt(-5, 5); // -5..4
// rng.nextInt(-5);             // IllegalArgumentException
~~~

When `origin` is nonzero—especially with negative numbers or values near numeric type extremes—prefer the two-bound overload to express intent clearly. Do not mechanically convert ranges via `rng.nextInt(bound - origin) + origin`: if `int` subtraction overflows, the computed range width is wrong and the call may fail or behave unexpectedly.

## 4. Invalid inputs and boundary cases

The overloads enforce that **the interval contains at least one valid value**:

- `nextInt(bound)` requires `bound > 0`. `bound = 0` or negative is invalid; `nextInt(0)` has no valid values.
- `nextInt(origin, bound)` and `nextLong(origin, bound)` require `origin < bound`. `[7, 7)` is empty; `[8, 7)` has inverted bounds. Both throw `IllegalArgumentException`.
- For `nextDouble(origin, bound)` and `nextFloat(origin, bound)`, both bounds must be finite, not NaN/Infinity, and satisfy `origin < bound`.
- `size` in finite stream overloads must be non-negative. `size = 0` produces an empty stream, not an error if both bounds are valid.

**A single-element integer interval** is not the same as an empty interval. `[7, 8)` always returns `7`; `[7, 7)` returns no values and is rejected. This is a great test for inclusive/exclusive confusion.

If your API accepts `origin` and `bound` from users, validate early and return clear errors: inputs must have the right type, a non-empty interval, and values within business rules. After validation, still let the standard API perform random generation instead of adjusting bounds arbitrarily.

## 5. Java 17+ program with boundary verification

Save as **`OriginBoundDemo.java`**. The program does not print specific random numbers because drawn values are non-constant by the example's intent; instead, it **checks invariants and prints stable results**. This check verifies the range of *sampled* values, not uniform probability across the entire generator.

~~~java
import java.util.Random;
import java.util.random.RandomGenerator;

public class OriginBoundDemo {
    private static void check(boolean condition) {
        if (!condition) {
            throw new AssertionError("Range invariant violated");
        }
    }

    private static void expectInvalid(Runnable action) {
        try {
            action.run();
            throw new AssertionError("Expected IllegalArgumentException");
        } catch (IllegalArgumentException expected) {
            // Per contract: invalid range arguments.
        }
    }

    // Supports the entire int range, including upper = Integer.MAX_VALUE.
    private static int nextIntInclusive(RandomGenerator rng, int min, int max) {
        if (min > max) {
            throw new IllegalArgumentException("min must not exceed max");
        }
        long upperExclusive = (long) max + 1L;
        long sampled = rng.nextLong((long) min, upperExclusive);
        return Math.toIntExact(sampled);
    }

    public static void main(String[] args) {
        RandomGenerator rng = new Random(2026L);

        for (int i = 0; i < 10_000; i++) {
            int x = rng.nextInt(-3, 4);
            long y = rng.nextLong(-20L, 21L);
            double z = rng.nextDouble(-0.5, 2.5);

            check(x >= -3 && x < 4);
            check(y >= -20L && y < 21L);
            check(z >= -0.5 && z < 2.5);
        }
        System.out.println("Half-open ranges: PASS");

        check(rng.nextInt(7, 8) == 7);
        check(rng.nextInt(Integer.MAX_VALUE - 1,
                          Integer.MAX_VALUE) == Integer.MAX_VALUE - 1);
        check(nextIntInclusive(rng, Integer.MAX_VALUE,
                                   Integer.MAX_VALUE) == Integer.MAX_VALUE);
        check(nextIntInclusive(rng, Integer.MIN_VALUE,
                                   Integer.MIN_VALUE) == Integer.MIN_VALUE);
        System.out.println("Boundary cases: PASS");

        expectInvalid(() -> rng.nextInt(0));
        expectInvalid(() -> rng.nextInt(5, 5));
        expectInvalid(() -> rng.nextInt(6, 5));
        expectInvalid(() -> rng.nextDouble(Double.NaN, 1.0));
        expectInvalid(() -> nextIntInclusive(rng, 9, 8));
        System.out.println("Invalid arguments: PASS");

        check(rng.ints(100, -3, 4)
                 .allMatch(value -> value >= -3 && value < 4));
        System.out.println("Bounded stream: PASS");
    }
}
~~~

Compile and run:

~~~bash
javac OriginBoundDemo.java
java OriginBoundDemo
~~~

Stdout:

~~~text
Half-open ranges: PASS
Boundary cases: PASS
Invalid arguments: PASS
Bounded stream: PASS
~~~

In `nextIntInclusive`, the method has **both-ends-inclusive** semantics: `[min, max]`. Because `max` is an `int`, `(long) max + 1L` is safe in `long`, even when `max` equals `Integer.MAX_VALUE`. The random number is generated as a `long` in `[min, max + 1)`, then converted exactly back to `int` via `Math.toIntExact`; because the result stays within `int` limits by precondition, the conversion succeeds. This is a general version for closed `int` intervals, not a recipe for handling arbitrary `long` intervals.

## 6. Converting [min, max] to [origin, bound) without off-by-one bugs

Classic problem: “pick a random integer from 1 to 6 **including 6**”. That is **[1, 6]**, whereas the two-bound API expects **[origin, bound)**. We write:

~~~java
int roll = rng.nextInt(1, 7); // [1, 7) is equivalent to [1, 6]
~~~

Many bugs come from passing `max` directly:

~~~java
int wrong = rng.nextInt(1, 6); // ONLY 1..5, can never equal 6
~~~

For integers where `max` is not the maximum type value, the conversion rule is:

~~~text
[minimum, maximum]  =>  [minimum, maximum + 1)
~~~

However, **`maximum + 1` must be representable in the data type**. If `maximum = Integer.MAX_VALUE`, the `int` expression `maximum + 1` overflows to `Integer.MIN_VALUE`. Likewise, `rng.nextInt(Integer.MAX_VALUE + 1)` becomes `nextInt(Integer.MIN_VALUE)` and throws an exception. Use `Math.addExact(maximum, 1)` if you want to **detect** overflow; or choose a `long`-widening approach like `nextIntInclusive` in the example when you truly need to include `Integer.MAX_VALUE`.

Do not blindly apply the integer range-conversion formula to `double`: “max + 1.0” adds an entire unit-wide real interval, rather than merely allowing the exact value `max`. The `float`/`double` domain has different representation properties than `int`/`long`; check carefully whether the contract truly needs to include `bound`, as `[origin, bound)` from the API usually suffices.

### Integer cases near extremes

The following calls are valid:

~~~java
int lastBelowMax = rng.nextInt(
        Integer.MAX_VALUE - 1, Integer.MAX_VALUE);
// Unique value: Integer.MAX_VALUE - 1

long maxAsLong = rng.nextLong(
        (long) Integer.MAX_VALUE, (long) Integer.MAX_VALUE + 1L);
// Unique value: 2147483647L
~~~

The value set of `nextInt(Integer.MIN_VALUE, Integer.MAX_VALUE)` covers almost the entire `int` range while still **excluding `Integer.MAX_VALUE` itself**. To cover the entire `int` range, use parameterless `nextInt()`, or use a controlled `long`-based closed-range construction when business logic supplies `min`/`max`.

For `long` itself, `Long.MAX_VALUE + 1L` overflows. You cannot use the widening trick like with `int`; if business rules demand a closed interval ending at `Long.MAX_VALUE`, design a dedicated approach (such as a full-range sampling algorithm or larger integers), rather than incrementing `bound` in `long`.

## 7. Double values: same bracket notation, different representation properties

`nextDouble(origin, bound)` produces floating-point values in **[origin, bound)**. For example:

~~~java
double fraction = rng.nextDouble(0.0, 1.0);
double temperature = rng.nextDouble(-10.0, 35.0);
~~~

`fraction` can equal `0.0` but cannot equal `1.0` per the contract; `temperature` can get close to `35.0` but must be strictly less than `35.0`. **There is no guarantee** that every point in the real interval can appear: `double` only represents a finite set of IEEE 754 numbers; this is not sampling from an ideal real continuum.

If you need random decimal numbers with a fixed step, such as currency amounts spaced by `0.01`, generate an **integer count of the smallest unit** in the defined range and convert to decimal representation. Do not draw `nextDouble`, multiply by 100, and round without analysis: the distribution over discrete values can be biased at the bounds or affected by precision and rounding.

**Why not scale `Math.random()` arbitrarily?**

~~~java
double raw = Math.random();            // [0.0, 1.0)
double shifted = -2.0 + raw * 5.0;    // Intent: [-2.0, 3.0)
~~~

This snippet shows a scaling expression; floating-point numbers are rounded during multiplication/addition. In edge cases, manual arithmetic can cause issues due to rounding up to `bound` or `bound - origin` overflowing to `Infinity`. Given `rng.nextDouble(origin, bound)`, prefer using it to express the `[origin, bound)` policy directly and validate arguments. Floating-point arithmetic in extreme ranges still needs testing.

`Math.random()` returns values in `[0.0, 1.0)`; it has no `origin`/`bound` parameters and is not suitable for generating secret tokens. For very close floating-point bounds, understand resolution and representability; the gap between two bounds must be interpreted in `double`, not ideal decimals.

## 8. Value counts and probability in integer ranges

If a generator distributes roughly uniformly over an integer interval of `n` values, the probability of each value is close to `1/n` (exact guarantees depend on the generator). With `[1, 7)`, `n = 6`, simulating a fair die expects each face with probability around `1/6`. This is why simple modulo arithmetic should be avoided:

~~~java
int wrong = Math.abs(rng.nextInt()) % 6; // Should not do this
int correct = rng.nextInt(6);            // 0..5
~~~

Two risks in the `wrong` formula:

1. `Math.abs(Integer.MIN_VALUE) == Integer.MIN_VALUE` because the positive absolute value cannot be represented in `int`. Thus, the result can be negative.
2. Forcing all random values into a smaller range via `%` without `rejection sampling` can introduce **modulo bias** because the number of source elements is not divisible by the target range width.

Use the standard bounded API to sample from a set of integers; it is designed to handle bounds and reduce distribution bias per the generator contract. Do not write your own bounded generation algorithm unless there is a proven need with proper statistical testing.

### Do not judge uniformity from a few samples

Running 10,000 times and seeing only values in `[origin, bound)` verifies only **the range of observed samples**. Not seeing `bound` in some number of trials does not fully prove the algorithm. Likewise, unequal frequencies in a small sample do not prove a generator is broken. When testing product logic, verify invariants; when evaluating probabilities, use appropriate statistical methods.

## 9. Streams follow the same half-open interval rule

Java APIs such as `Random.ints`, `Random.longs`, and `Random.doubles` allow creating bounded random streams:

~~~java
import java.util.Random;

Random random = new Random(2026L);
long validCount = random.ints(500, 10, 20)
        .filter(x -> x >= 10 && x < 20)
        .count();

System.out.println(validCount); // 500
~~~

This snippet sits inside a method body (with the corresponding import). All elements are in **[10, 20)**, so `20` is never generated. Note that `ints(500, 10, 20)` takes **`streamSize` first, followed by `origin` and `bound`**; do not confuse it with `nextInt(origin, bound)` which takes only two bounds. `ints(origin, bound)` without `streamSize` creates a theoretically unlimited stream, so use `limit` or a conditional terminating operation and control resource usage.

A stream is consumed once. In tests with a fixed seed, avoid assuming operations in different orders or different generators produce the same sequence. Every number-generation call mutates the state of a stateful generator; do not hard-compare a random sample against a sample drawn **after** it.

## 10. Applying to real-world scenarios

### Picking an array/list index

~~~java
if (!items.isEmpty()) {
    int index = rng.nextInt(items.size()); // [0, size)
    var selected = items.get(index);
}
~~~

This is an illustrative snippet inside a method where `items` is a `List`. `items.size() > 0` is a prerequisite: an empty list causes `nextInt(0)` to throw an exception. The exclusive upper bound aligns directly with the last index `size - 1`.

### Generating numbers in a range including negatives

~~~java
int adjustment = rng.nextInt(-10, 11); // [-10, 10]
~~~

To include `+10`, the passed bound is `11`. Do not assume `rng.nextInt(-10, 10)` will include `+10`.

### Generating numeric codes or short session numbers

~~~java
int fourDigits = rng.nextInt(1000, 10_000); // 1000..9999
~~~

This is merely a four-digit pseudorandom number; it does **not** guarantee uniqueness, unpredictability, or replace a sequence or ID allocator. If you need login session tokens, verification codes, keys, or security secrets, you need a cryptographically secure random source like `SecureRandom` and a proper security design. Getting `[origin, bound)` right is only a tiny part of that problem.

### Picking a value of an enum

~~~java
enum TrafficColor { RED, YELLOW, GREEN }

TrafficColor[] values = TrafficColor.values();
TrafficColor randomColor = values[rng.nextInt(values.length)];
~~~

The snippets in section 10 are illustrations placed in an appropriate class/method body; the enum is declared at class level while array indexing happens inside a method. If an enum is empty (has no constants), handle it separately before calling `nextInt(0)`.

## 11. Testing range design more thoroughly

Verify both **range requirement correctness** and **code behavior**:

1. **Simple boundaries:** `[0, 1)` returns only `0`; `[7, 8)` returns only `7`. Single-element cases catch bound mistakes very quickly.
2. **Negative origin:** `[-3, 4)` ensures `x >= -3 && x < 4`. Running many iterations is only sample verification, not a statistical proof.
3. **Invalid inputs:** `bound <= 0` for single-bound overloads; `origin >= bound` for two-bound overloads; `NaN`/`Infinity` for floating bounds.
4. **Integer extremes:** `[Integer.MAX_VALUE - 1, Integer.MAX_VALUE)` contains only `Integer.MAX_VALUE - 1`. For `[MAX, MAX]`, an inclusive helper returns `MAX`; adding `1` in `int` overflows.
5. **Converting “up to and including” requirements:** e.g., die `[1, 6]` must become `[1, 7)`, not `[1, 6)`.
6. **Empty arrays:** never call `nextInt(size)` when `size` is `0`; enforce preconditions or handle the empty branch.
7. **Streams:** verify parameter order `(size, origin, bound)`, output stream size, and that all values fall inside the range.
8. **Reproducibility:** use a fixed seed in tests for controlled call flows, without equating the same seed across all generator classes or threading strategies.
9. **Distribution and security:** invariant testing does not replace randomness tests; `Random`/`ThreadLocalRandom` are not secure token generators.
10. **Floating-point:** check finiteness and `origin <= x < bound`; do not force tests to observe both endpoints since one endpoint is excluded and the allowed endpoint might not be hit in a finite sample.

A small precondition exception check suitable for a unit test:

~~~java
RandomGenerator rng = new Random(1L);
try {
    rng.nextInt(5, 5);
    throw new AssertionError("Expected IllegalArgumentException");
} catch (IllegalArgumentException expected) {
    // PASS: [5, 5) has no elements.
}
~~~

This snippet needs `import java.util.Random` and `java.util.random.RandomGenerator` and sits inside a method. Do not rely on Java's `assert` when tests run without `-ea`; use a test framework or explicit runtime checks as shown.

## 12. Common mistakes to avoid

| Mistake | Why it is wrong | Right approach |
|---|---|---|
| `nextInt(1, 6)` for a 1..6 die | `6` is the exclusive bound | `nextInt(1, 7)` |
| `nextInt(0)` to pick from an empty list | No valid index exists | Handle empty lists beforehand |
| `nextInt(-5)` for negative numbers | Single-bound overload requires a positive bound | `nextInt(-5, 0)` |
| `nextInt(min, max + 1)` when `max = INT_MAX` | `int` addition overflows | Use controlled `long` or a general algorithm |
| `nextInt(max - min) + min` for wide ranges | `int` difference can overflow | Use the `nextInt(min, max)` overload |
| Using `Math.abs(nextInt()) % n` | Can be negative, has modulo bias | Use `nextInt(n)` |
| Measuring `nextDouble` by displayed decimal digits | Floating-point has binary precision | Check using value inequalities |
| Generating security tokens with `Random` | Not designed against adversarial prediction | Use `SecureRandom` with a secure workflow |
| Using a few samples to conclude a bound is included/excluded | Randomness does not guarantee hitting every outcome | Rely on the contract and boundary tests |
| Writing custom algorithms for closed bounds | Prone to off-by-one and overflow bugs | Convert intervals carefully or use a tested helper |
