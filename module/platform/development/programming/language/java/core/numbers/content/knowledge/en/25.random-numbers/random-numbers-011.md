# Choosing Algorithms, Seeds, and Testing Random Numbers in Java: Separating Reproducibility from Security

## 1. Three questions to keep separate

When a program needs random numbers, you cannot choose an API simply because it returns numbers that look hard to guess. First, determine:

1. **What is it used for?** Simulation, test data, sampling, games, load distribution, or generating tokens/secret values?
2. **Do you need to reproduce exact results?** An experiment or bug arising from pseudorandom numbers often needs replay using a seed and the same call order.
3. **Must it resist adversarial prediction?** Login session tokens, password-reset codes, secret keys, and sensitive values must be generated by an appropriate cryptographically secure random number generator (CSPRNG).

The three properties—**testability**, **appropriate distribution**, and **unpredictability against an adversary**—are separate requirements. A chaotic-looking list does not prove security; an exactly reproducible sequence is even less proof of security. A seed initializes a generator, yet does not turn an algorithm into a CSPRNG.

This lesson aims to help you choose the right Java 17+ tool, manage seeds intentionally, design reliable tests, and avoid false security assumptions.

## 2. Nature of pseudorandomness, seeds, and state

A pseudorandom number generator (PRNG) is a **stateful** algorithm. A seed initializes the starting state. After each draw, the state updates; subsequent outputs depend on that state.

~~~text
initial seed
    |
    v
state S0
    | nextInt(...) or generation method
    v
value 1 + state S1
    | next draw
    v
value 2 + state S2
    |
    v
...
~~~

For a deterministic algorithm, given the same initial state and **the exact same sequence of calls with the same arguments**, we can reproduce the output sequence. However:

- **Same seed, different algorithm:** no guarantee of the same sequence.
- **Same algorithm/seed, different call count:** values assigned to each business step can shift.
- **Sharing a generator across multiple threads:** the order in which threads consume numbers can vary across runs.
- **Same seed, different implementation version:** rely on cross-version reproducibility only when the generator's explicit contract guarantees it.

Reproducibility is a tool for testing and diagnostics. Cryptographic security is a separate requirement on the algorithm, seed/entropy source, usage, and operational environment.

## 3. Options in Java 17+

| Tool | Appropriate scope | Seeds and reproducibility | Main limitations |
| --- | --- | --- | --- |
| `java.util.Random` | Examples, tests, small simulations, code needing compatibility with the classic generator | `new Random(long seed)`; same sequence with same calls; core class algorithm is specified | Not for secrets; sharing across threads can cause contention and alter consumption order |
| `java.util.SplittableRandom` | Simulations needing multiple separate streams or work splitting | Constructor accepts seed; `split()` creates a new generator | Not a CSPRNG; do not arbitrarily share one instance across threads |
| `java.util.concurrent.ThreadLocalRandom` | Convenient ordinary number generation in concurrent tasks | Obtained via `ThreadLocalRandom.current()`; not designed for manual per-test seeding | `setSeed(...)` is unsupported; unsuitable when exact sequence replay from a test-supplied seed is needed |
| `java.util.random.RandomGenerator` and `RandomGeneratorFactory` | Selecting specific algorithms, designing APIs that accept an external generator | Can instantiate from algorithm name and seed when supported by factory | Must record **algorithm name**, properties, and runtime version for long-term replay |
| `java.security.SecureRandom` | Tokens, nonces, salts, and values needing unpredictability | Typically instantiated without a fixed seed; seed behavior and algorithm depend on provider | Do not treat `setSeed(fixedValue)` as a replay contract; never replace with `Random` just for easier tests |

In Java 17, `Random`, `SplittableRandom`, and `ThreadLocalRandom` belong to the `RandomGenerator` ecosystem. This grouping does not mean every algorithm yields the same sequence for a seed or shares identical statistical properties.

**Quick selection rules:**

- Need deterministic sequences for tests/simple simulations → choose `Random` with an explicit seed, or a named deterministic algorithm.
- Need separate streams for simulation tasks → consider `SplittableRandom` or splittable generators with transparent seeding and task structure.
- Only need non-security values in multithreaded tasks without seed replay → `ThreadLocalRandom` is usually convenient.
- **Security-sensitive** values → choose `SecureRandom`; fixed seeds and `Random` are not valid substitutes.

## 4. Java 17 example: reproducing test numbers while keeping security boundaries

Create the file `RandomChoiceDemo.java`:

~~~java
import java.security.SecureRandom;
import java.util.ArrayList;
import java.util.List;
import java.util.Random;
import java.util.SplittableRandom;
import java.util.random.RandomGenerator;
import java.util.random.RandomGeneratorFactory;

public class RandomChoiceDemo {
    static List<Integer> sample(Random random, int count) {
        List<Integer> numbers = new ArrayList<>();
        for (int i = 0; i < count; i++) {
            numbers.add(random.nextInt(100));
        }
        return numbers;
    }

    static int rollDie(RandomGenerator random) {
        return random.nextInt(1, 7);
    }

    public static void main(String[] args) {
        List<Integer> run1 = sample(new Random(42L), 5);
        List<Integer> run2 = sample(new Random(42L), 5);

        System.out.println("Seed 42: " + run1);
        System.out.println("Same sequence: " + run1.equals(run2));

        Random stateful = new Random(42L);
        System.out.println("First: " + stateful.nextInt(100));
        System.out.println("Second: " + stateful.nextInt(100));
        stateful.setSeed(42L);
        System.out.println("After reset: " + stateful.nextInt(100));

        RandomGenerator g1 = RandomGeneratorFactory
                .of("L64X128MixRandom")
                .create(2026L);
        RandomGenerator g2 = RandomGeneratorFactory
                .of("L64X128MixRandom")
                .create(2026L);
        System.out.println("Named algorithm replay: "
                + (rollDie(g1) == rollDie(g2)));

        SplittableRandom left = new SplittableRandom(123L);
        SplittableRandom right = new SplittableRandom(123L);
        System.out.println("Splittable seeded replay: "
                + (left.nextLong() == right.nextLong()));

        SecureRandom secure = new SecureRandom();
        byte[] secretBytes = new byte[16];
        secure.nextBytes(secretBytes);
        System.out.println("Secure bytes count: " + secretBytes.length);
    }
}
~~~

Run with JDK 17+:

~~~bash
javac RandomChoiceDemo.java
java RandomChoiceDemo
~~~

Output:

~~~text
Seed 42: [30, 63, 48, 84, 70]
Same sequence: true
First: 30
Second: 63
After reset: 30
Named algorithm replay: true
Splittable seeded replay: true
Secure bytes count: 16
~~~

Step-by-step explanation:

1. `new Random(42L)` produces `[30, 63, 48, 84, 70]` when calling `nextInt(100)` five times. Same seed and same calls yield the same list.
2. `stateful.nextInt(100)` consumes state. After two calls, `setSeed(42L)` resets the starting point, so the next call returns `30`.
3. `RandomGeneratorFactory.of("L64X128MixRandom")` explicitly selects **an algorithm provided in Java 17**, then `create(2026L)` creates two generators with the same seed. The example checks reproducibility of a `nextInt(1, 7)` call; it does not claim this sequence matches `Random(2026L)`.
4. Two `SplittableRandom(123L)` instances receive the same seed and draw their first `nextLong()`, so the results match. This only proves algorithmic reproducibility, not secrecy.
5. `SecureRandom` generates 16 bytes without the program printing their values. Only **the deterministic length** is printed; actual bytes should not be expected to be fixed or predictable. Never send sensitive values to stdout/logs.

The method `rollDie(RandomGenerator random)` is an example of **injecting a generator** (simple dependency injection): business logic does not have to decide the seed itself. Using an interface allows picking the generator at startup, while still obeying the application's algorithm and security requirements.

## 5. Reproducibility takes more than a seed number

A run is genuinely reproducible only when all of the following conditions hold:

| Condition | Why it is needed |
| --- | --- |
| Generator class or algorithm name | `Random` and `SplittableRandom` do not use the same algorithm |
| Seed value | Initializes the corresponding state |
| Call order, count, and bound/origin arguments | Every call consumes state; some APIs consume multiple steps |
| How generators are partitioned across tasks | Prevents different consumption orders across tasks |
| Relevant code and runtime version | Business logic changes can alter where numbers are drawn |
| Input data and configuration | Different conditional branches can call the generator a different number of times |

For example, both snippets below use `Random(42L)`, yet the number mapped to `loot` differs:

~~~java
Random before = new Random(42L);
int enemy = before.nextInt(100); // 30
int loot = before.nextInt(100);  // 63
~~~

~~~java
Random after = new Random(42L);
int enemy = after.nextInt(100);   // 30
int weather = after.nextInt(100); // 63
int loot = after.nextInt(100);    // 48
~~~

These are **illustrative code snippets**; to run standalone, place them in a class/method and import `java.util.Random`. Adding one draw for weather causes `loot` to take a different position in the sequence. The seed did not change at all.

If multiple parts of a simulation need isolation, give each part its own generator with managed seeds:

~~~java
Random weatherRandom = new Random(1001L);
Random lootRandom = new Random(2002L);
~~~

Then drawing extra weather numbers does not advance `lootRandom`'s state. However, two different seeds **do not automatically guarantee** ideal statistical independence; algorithms and stream-splitting strategies must suit the simulation's requirements.

## 6. Fixed seeds, automatic seeds, and limits of java.util.Random

Classic `Random` uses a linear congruential generator (LCG) with a **48-bit** state. The `long` seed is mixed into the state via:

~~~text
state0 = (seed XOR 0x5DEECE66D) AND ((1L << 48) - 1)
stateNext = (state * 0x5DEECE66D + 0xB) mod 2^48
~~~

As a result, seeds `42L` and `42L + (1L << 48)` share the same lower 48 bits and therefore produce the exact same initial state and `Random` sequence. This also demonstrates that **not every distinct `long` seed yields a distinct sequence** for this class.

`new Random()` uses automatic seed initialization, suitable when you do not need to prescribe a sequence; it is **not** a security solution. `new Random(System.currentTimeMillis())` seeds from the clock, which is often predictable and can collide across close initializations. Never use timestamps or obvious values as “secrets” for tokens.

Why is `Random` unsafe for secrets?

- Its algorithm is public, its state is finite, and it is designed for general pseudorandom number generation.
- An observer with enough output information can infer the sequence, so it lacks CSPRNG unpredictability guarantees.
- A fixed seed enables replaying results, directly contradicting the requirement that tokens be hard to guess and non-repeating.

Remember that **same seed → same sequence** in `Random` is a feature for testing, not proof that a token is random enough against an adversary.

## 7. Security: using SecureRandom for its intended purpose

For cryptographic bytes, tokens, or values that must resist guessing, use `java.security.SecureRandom`:

~~~java
SecureRandom secureRandom = new SecureRandom();
byte[] token = new byte[32]; // 256 bits of generated data
secureRandom.nextBytes(token);
~~~

This snippet sits inside a class importing `java.security.SecureRandom`. It illustrates generating **32 bytes** with a CSPRNG, without covering token encoding, storage, expiration, validation, log redaction, or other secure usage workflows. A 32-byte length alone does not prove an entire system is secure.

Principles:

- Prefer letting **the Java provider and OS** initialize appropriate entropy/state via `new SecureRandom()`; specify an algorithm/provider explicitly when environment or security policy mandates it.
- Never use `new Random(seed)`, `SplittableRandom`, or `ThreadLocalRandom` for login tokens, keys, salts, or nonces needing unpredictability.
- Never use a fixed seed to make `SecureRandom` outputs repeat in production. `SecureRandom.setSeed(...)` has provider-dependent semantics and typically **supplements** state rather than guaranteeing a full reset for replay; do not claim “same seed gives same sequence” for `SecureRandom`.
- Never log secret seeds/bytes, and never print real tokens to logs or test output. In contrast, seeds of **non-secret simulations** can be logged for debugging.
- Security depends on how random values are used: context, lifecycle, quantity, storage, uniqueness constraints, and authorization checks.

If business logic requires a 6-digit token, a CSPRNG can select a value in `0` to `999_999` and format it to six digits; however, short tokens allow fewer guesses, so they still require expiration, attempt limits, and proper defenses. Do not assume “SecureRandom” solves all of those issues automatically.

## 8. Necessary tests for random number generators

There are at least four testing categories, with distinct criteria.

### 8.1. Reproducibility tests

For `Random` with a fixed seed:

~~~java
Random a = new Random(42L);
Random b = new Random(42L);

for (int i = 0; i < 100; i++) {
    if (a.nextInt(1000) != b.nextInt(1000)) {
        throw new AssertionError("Different sequences");
    }
}
~~~

This snippet illustrates the expectation that two instances with the same seed and same 100 calls match; place it inside a method/class importing `Random`.

This tests reproducibility and detects changes in how code consumes the generator. It does **not** test statistical quality or cryptographic security.

### 8.2. Property and boundary tests

For a `rollDie(RandomGenerator)` function returning integers in `[1,7)`, verify **every observed result** lies in `1..6`; for `nextInt(bound)`, `bound` must be positive. More valuable tests verify the logic using the generator, such as:

- Outputs never exceed the upper bound or fall below the lower bound.
- Invalid bounds throw appropriate exceptions.
- Code does not create a fresh `Random(fixedSeed)` on every draw when intending to consume a continuous sequence.
- If business logic shuffles a list, the output is a valid permutation without dropping or duplicating elements.

Do not test “100 rolls must definitely include all six die faces” because that is a probabilistic event, not a mathematical guarantee in a finite sample.

### 8.3. Statistical distribution tests

For simulations, testing uniformity, bias, correlation, or algorithm quality requires proper statistical methods. A naive check like counting frequencies after 20 draws is inconclusive. Distribution tests have **false-positive probabilities** and can miss bugs; do not turn them into “must pass 100% of runs” assertions without carefully designing thresholds and sample sizes.

For critical systems, combine vetted statistical test suites, algorithmic property analysis, varied seeds, and reproducibility experiments. Statistical uniformity does not replace CSPRNG security evaluation.

### 8.4. Testing systems that use SecureRandom

A secure application should not write tests like:

~~~java
SecureRandom secure = new SecureRandom();
secure.setSeed(42L);
// Misused purpose: demanding fixed security byte sequences across every provider.
~~~

Because `SecureRandom` offers no universal replay contract when seeded this way, forcing fixed output bytes makes tests provider-dependent or tempts swapping the CSPRNG for an ordinary PRNG.

Instead, test **application behavior**: tokens have the right byte/character length, the API uses the selected CSPRNG source, validation and expiration work properly, errors are handled, and secrets are never leaked externally. For unit tests needing dependency isolation, use an abstraction or test-scoped fake number source to control inputs; production configuration keeps using `SecureRandom`.

## 9. Designing for testability: injecting generators into business logic

A function that directly instantiates `new Random()` inside is hard to reproduce and leads to flaky tests:

~~~java
// Illustrates the inconvenience: state is initialized inside the function.
static int randomIndex(int size) {
    return new Random().nextInt(size);
}
~~~

This is a **method snippet**. For deterministic tests, separate generator selection from logic:

~~~java
static int randomIndex(RandomGenerator rng, int size) {
    if (size <= 0) {
        throw new IllegalArgumentException("size must be positive");
    }
    return rng.nextInt(size);
}
~~~

Example in Java 17 with `import java.util.random.RandomGenerator;`. Tests can pass `new Random(42L)` and check the drawn index; callers using the provided generator can configure it differently as needed. Never hardcode `new Random(42L)` in production code for a feature requiring unpredictable values.

For token-generation functions, separate token structure from the random byte source and enforce `SecureRandom`/an equivalently properly configured service in production. Dependency injection must not accidentally open a path to using an insecure generator in sensitive features.

Good testing usually has two layers:

1. **Unit tests of logic** using fake/controllable inputs to check formatting, boundaries, and error handling.
2. **Integration/security validation** verifying that production configuration uses the required CSPRNG alongside surrounding security controls.

You do not need to “predict the exact bytes SecureRandom will generate” to prove your logic calls the API correctly.

## 10. Multithreading and choosing a seeding strategy

In parallel simulations, passing a single shared `Random(42L)` to all threads is insufficient to guarantee each task receives the same data on every run. If threads A and B interleave differently, values handed to A/B differ as well. Thread safety under concurrent access and **per-task** reproducibility are two separate things.

A strategy for testing:

- Assign each task a **stable identifier**.
- Map that identifier to its own seed using a designed and documented rule.
- Create dedicated generators inside each task; avoid depending on scheduler draw order.
- When using `SplittableRandom.split()`, splitting generators into a tree must also follow a **stable structure and order** if exact per-task reproducibility is required.

Do not assume seeds like `baseSeed + taskIndex` produce perfectly statistically independent sequences; choose seeding schemes and generators suited to your required simulation quality. If using `ThreadLocalRandom`, accept that the API does not support per-thread seeding via `setSeed` for `Random`-style replay.

In Java 17, `RandomGeneratorFactory` supports selecting algorithms by name or properties; verify the algorithm is actually available in your runtime and record the choice for long-term replay. Not all generators share the same distribution, splitting, and performance traits.

## 11. When should seeds be logged, and when should they not?

For **non-sensitive tests/simulations**, logging the seed is usually good practice:

~~~text
simulation=inventory-replay
prng=java.util.Random
seed=42
draws=5 x nextInt(100)
result=[30, 63, 48, 84, 70]
~~~

This log example contains no secrets and gives others the information needed to recheck results. If the program changes branching logic, also log the version or random-usage events.

For **security values**, the situation is completely different: seeds or internal state may be secret data; never log or share them to “replay tokens”. Only log necessary, controlled operational metadata, such as successful token issuance events, non-sensitive correlation IDs, or expiration timestamps per security policy.

Avoid mixing test observability rules with production rules. Even if a seed is non-sensitive in a test environment, reusing that same seed to generate real tokens is still wrong.

## 12. Common mistakes

**Mistake 1 — “Same seed is enough to guarantee the same data.”** Wrong if you change algorithms, change call order, add draws, or let multiple threads race on one generator. Consumption context must also be recorded.

**Mistake 2 — “The seed is fixed, so the token is secure.”** A fixed seed makes outputs reproducible. The `Random` algorithm has no cryptographic security guarantees; use `SecureRandom` for secrets.

**Mistake 3 — “SecureRandom has setSeed, so tests can restore the same sequence on every machine.”** There is no such universal contract. Providers may use different algorithms and seed-mixing mechanisms.

**Mistake 4 — “Different seeds must differ on every number.”** Two sequences can coincidentally share a few results; with 48-bit `Random`, different `long` seeds can even yield the exact same initial state. Never use “each fresh generator must return a different first number” as a pass/fail test.

**Mistake 5 — Calling `new Random(seed)` inside a loop.** Every instance restarts at the beginning of the sequence, repeatedly yielding the same first number. When you need a sequence, create one object and consume it continuously.

**Mistake 6 — Confusing the `nextInt(bound)` range.** `nextInt(6)` returns 0..5; a 1..6 die needs `+ 1` or `nextInt(1, 7)` on supporting APIs.

**Mistake 7 — Testing distribution with a handful of draws.** A short sample can skew naturally. Use properly designed statistical tests rather than arbitrary rules.

**Mistake 8 — Calling `ThreadLocalRandom.setSeed` for reproducibility.** The API intentionally forbids setting a seed after obtaining the instance; calling it throws `UnsupportedOperationException`.

**Mistake 9 — Failing to separate simulation seed logs from secret logs.** Logging seeds for ordinary simulations aids debugging; logging CSPRNG seeds/state or secret tokens can compromise the system.

**Mistake 10 — Swapping generators for speed without revisiting assumptions.** Outputs, statistical quality, thread-splitting ability, and replay compatibility can change; re-evaluate against requirements.

## 13. Worked practice exercises

### Exercise 1. Choosing a generator by scenario

| Scenario | Suitable choice | Reason |
| --- | --- | --- |
| Generating five test numbers needing exact replay | `new Random(42L)` with identical calls | Convenient for deterministic testing |
| Large simulation needing separate generators per branch | `SplittableRandom` or splittable generator | Allows splitting generators and managing state per task |
| Multithreaded task needing ordinary numbers without seeding | `ThreadLocalRandom.current()` | Fits thread-local usage |
| Generating account recovery tokens | `SecureRandom` | Requires an unpredictable source |
| Choosing a named algorithm for experiment configuration | `RandomGeneratorFactory.of(name)` | Explicit algorithm choice, recordable for replay |

**Evaluation point:** A choice is only appropriate alongside requirements for replay, distribution, and security; no single generator is optimal for every problem.

### Exercise 2. Predicting output with the same seed

~~~java
Random a = new Random(42L);
Random b = new Random(42L);

System.out.println(a.nextInt(100));
System.out.println(a.nextInt(100));
System.out.println(b.nextInt(100));
~~~

Answer:

~~~text
30
63
30
~~~

Because `a` has consumed two positions, whereas `b` has only consumed the first position.

### Exercise 3. Fixing a flaky test

Suppose `calculateDiscount()` calls `new Random()` internally, leaving tests unable to know what value the generator will return. Refactor the design so the function accepts a `RandomGenerator` or an external random-provider interface. In tests, pass a generator with a known seed; in production, configure a generator matching business needs. If discounts must resist user prediction/exploitation, design business controls and a secure random source rather than merely changing the seed.

### Exercise 4. Analyzing a claim

“The generated token sequence passed a frequency test, so it must be hard to predict.”

**Answer:** False. A simple deterministic algorithm can exhibit even frequencies yet still be predictable once the seed or state is known. Frequency tests do not replace CSPRNG analysis and selection.

### Exercise 5. Reproducibility logging

A bug occurred after splitting a simulation into four parallel tasks. Is logging only `seed=100` sufficient?

**Answer:** No. You need the generator/algorithm, how seeds are assigned or split per task, the number-consumption order (or independent state-splitting layout), program version, and inputs. If each task has its own generator and processing order is designed to be independent of scheduler timing, results are far easier to reproduce.

## 14. Pre-design checklist

1. **Purpose:** Are numbers for simulation/testing or a secret needing unpredictability?
2. **Algorithm:** Explicitly pick `Random`, `SplittableRandom`, a named `RandomGenerator`, `ThreadLocalRandom`, or `SecureRandom`.
3. **Seed:** Who supplies it? Is it fixed for replay? Does it involve secret data?
4. **Reproducibility:** Which calls, bounds, order, tasks, and versions must remain fixed?
5. **Testing:** Are you verifying logic, sequence replay, statistical distribution, or security controls?
6. **Concurrency:** Is a generator shared across threads; can execution scheduling shift draw positions?
7. **Operations:** Which metadata may be logged, and which secret data must never be stored?

**Key takeaway:** A seed is a tool to **initialize and reproduce PRNG state**; algorithm choice governs sequence generation and properties to evaluate. Testability via a fixed seed **does not mean** cryptographic security. In Java, choose `Random`/appropriate generators for reproducible simulations, and `SecureRandom` for values requiring unpredictability, while separately testing application behavior and security controls.
