# Verifying Algorithms with Boundary Data and Reference Results in Java

## 1. Why Do "Plausible-Looking" Results Not Prove an Algorithm Correct?

For numerical algorithms, a few correct results on ordinary data are not enough to prove the algorithm is right. Bugs may only surface when **inputs hit type limits**, two numbers differ vastly in magnitude, data has negative signs, `NaN`/infinity appears, or many rounding steps occur in sequence.

Example:

```java
int a = 50_000;
int b = 50_000;

long wrong = a * b;          // -1794967296: int multiplication overflows before assignment.
long right = (long) a * b;   // 2500000000: long multiplication.
```

A test using only `a = 2, b = 3` cannot catch the bug above. Floating-point summation algorithms can behave similarly: many small cases succeed, yet `1e16 + 1.0` in `double` rounds back to `1e16`.

For reliable verification, combine **two sources of evidence**:

1. **Boundary data (*boundary and adversarial cases*):** intentionally craft difficult scenarios near limits or prone to exposing bugs.
2. **Reference results (*reference result, test oracle*):** determine expected results in a sufficiently independent, accurate manner matching the algorithm's contract.

This lesson focuses on verifying numerical computations in Java Core: fixed-width integers, `float`/`double` floating-point numbers, numerical stability, and reference-checking strategies. The goal is not merely writing `assert`, but knowing **what is being asserted, on what basis, and what error is acceptable**.

## 2. First Define What "Correct" Means

An algorithm can be correct under several different contracts:

- **Mathematical integers:** requires exact unbounded results conceptually; `BigInteger` can serve as a reference.
- **Fixed-width integers:** a program may deliberately use modulo `2^32`/`2^64` arithmetic, or must error on overflow. Clarify the expectation rather than assuming every wraparound is a bug.
- **IEEE 754 floating-point:** accepts rounding error under a defined model. Verification must account for magnitude, precision, and special values.
- **Exact decimal:** such as monetary amounts or measurements specified to a fixed number of digits, which may require `BigDecimal` and a `RoundingMode` rule.
- **Approximate algorithms:** results are accepted if they satisfy absolute/relative error bounds, confidence intervals, or domain-specific error limits.

An `int` operation giving a negative result from overflow may be **right in modular arithmetic** yet **wrong in revenue-calculation business logic**. A `double` result off by a few ULPs may be **acceptable** in a simulation yet **unacceptable** if the contract requires exactness down to the smallest unit.

Therefore, before writing test cases, state clearly:

| Contract section | Questions to answer |
| --- | --- |
| Input domain | Are negative numbers, zero, `NaN`, infinity, or out-of-range values allowed? |
| Output domain | Must the result be finite, non-negative, within an interval, or of a specific type? |
| Overflow and exceptions | Must overflow throw an error, saturate (*saturate*), or wrap modulo? How is division by 0 handled? |
| Precision | Is exactness required, rounding to a specific digit, or a specific error bound? |
| Stability | Does error grow excessively when slightly perturbing data or changing calculation order? |
| Preconditions | Are empty arrays, `null`, or unsorted data allowed? |

**The test oracle must come from the contract**, not from the output generated by the very function under test.

## 3. Designing Boundary Datasets for Numerical Computations

Do not test only `0` and `MAX_VALUE`. For numerical algorithms, test **values immediately below, at, and immediately above thresholds**, along with combinations prone to instability.

| Data group | Example inputs | Bugs/risks to detect |
| --- | --- | --- |
| Zero and sign | `0`, `-1`, `1`, `+0.0`, `-0.0` | Division by 0, sign rules, signed zero handling |
| Integer bounds | `Integer.MIN_VALUE`, `Integer.MAX_VALUE`, near-bound values | Addition/multiplication overflow, `Math.abs(MIN_VALUE)` |
| `long` bounds | `Long.MIN_VALUE`, `Long.MAX_VALUE` | 64-bit overflow and narrowing casts |
| `float` exactness limit | `2^24` and adjacent integers | Loss of ability to distinguish steps of `1` |
| `double` exactness limit | `2^53` and adjacent integers | Rounding of large integers |
| Magnitude disparity | `1e16 + 1.0` | Small terms swallowed |
| Cancellation | `(1e16 + 1.0) - 1e16` | Information loss prior to subtraction |
| Floating-point extremes | `Double.MAX_VALUE`, `Double.MIN_NORMAL`, `Double.MIN_VALUE` | Overflow, subnormal, underflow |
| Special values | `Double.NaN`, `Double.POSITIVE_INFINITY`, `-0.0` | Comparisons, finiteness checks, value contracts |
| Composite data | Empty array, single element, many same-sign numbers, alternating signs | Off-by-one indices, wrong averages, summation stability |
| Invalid inputs | Zero denominator, negative length, out-of-range numbers | Right exception type, not swallowing errors |

For each boundary `B`, a fundamental pattern is testing **`B-1`, `B`, `B+1`**, while constructing the test data in a **sufficiently wide** type; do not let the test-setup code itself overflow before the test runs:

```java
long below = (long) Integer.MAX_VALUE - 1;
long at = Integer.MAX_VALUE;
long above = (long) Integer.MAX_VALUE + 1;
```

For floating-point numbers, `x - 1`/`x + 1` are not always adjacent values. Use `Math.nextDown(x)`, `Math.nextUp(x)`, and `Math.ulp(x)` when testing boundaries at the resolution of `double`.

### Especially Useful Adversarial Test Cases

- `Integer.MAX_VALUE + 1` and `Long.MAX_VALUE + 1L`: observe integer overflow.
- `Integer.MIN_VALUE / -1`: special integer division case; in `int` the result is `Integer.MIN_VALUE` because the mathematical quotient is out of range.
- `0 / 0` in integers: must throw `ArithmeticException`; `0.0 / 0.0` in floating point: `NaN`.
- `1e16 + 1.0` and `1e16 + 2.0`: distinguish changes that get rounded away from changes that are preserved.
- `Double.MIN_VALUE / 2.0`: result smaller than the smallest positive `double`, rounding to `0.0`.
- `Double.MAX_VALUE * 2.0`: result is `Infinity`.
- Two close floating-point numbers around a comparison threshold: use `Math.nextUp` instead of adding an arbitrary epsilon.

Do not assume more test cases alone are enough. A small dataset where each case was chosen for a reason is often far more effective than thousands of random inputs clustered around average values.

## 4. Building Trustworthy Reference Results

A **reference result** must be generated by a higher-confidence method, sufficiently independent from the code under test so it does not accidentally repeat the same bug.

### 4.1. `BigInteger` as an Oracle for Mathematical Integers

If an algorithm computes integer values that may exceed 32/64 bits, use `java.math.BigInteger`:

```java
import java.math.BigInteger;

int a = 50_000;
int b = 50_000;

BigInteger expected = BigInteger.valueOf(a)
        .multiply(BigInteger.valueOf(b));

System.out.println(expected); // 2500000000
```

Do not perform primitive multiplication **before** passing the result to `BigInteger`:

```java
// Wrong oracle: int multiplication can overflow first.
BigInteger wrongReference = BigInteger.valueOf(a * b);
```

Similarly, to test `long` addition at boundaries, use `BigInteger.valueOf(x).add(BigInteger.valueOf(y))`, not `BigInteger.valueOf(x + y)`. If the contract permits 32/64-bit modular arithmetic, compare the `BigInteger` result after applying **the exact modular reduction** required by the contract.

Under a "must not overflow" contract, instead of comparing wrapped-around results, verify that `Math.addExact`, `Math.multiplyExact`, or boundary-checking logic throws `ArithmeticException` in the appropriate cases.

### 4.2. `BigDecimal` as an Oracle for Decimal Inputs

Suppose the input contract is **ten times the exact decimal value `0.1`**:

```java
import java.math.BigDecimal;

BigDecimal reference = new BigDecimal("0.1")
        .multiply(BigDecimal.TEN);

System.out.println(reference.toPlainString()); // 1.0
```

The critical point is **input definition**. There are two different ways to build a reference:

1. **Intended decimal reference:** `new BigDecimal("0.1")` represents the exact decimal fraction `1/10`.
2. **Exact bit-pattern reference for a received `double`:** `new BigDecimal(0.1)` represents the exact **binary approximation** stored in `double`. Mathematically, it differs from `1/10`.

In Java, `BigDecimal.valueOf(0.1)` converts `double` via its short decimal string representation, usually yielding `0.1`. However, when the goal is computing **the exact value of a `double` bit pattern**, `new BigDecimal(x)` is the right choice. Choose the oracle according to the actual input type, rather than using one `BigDecimal` construction for every problem.

For decimal divisions with infinite expansions like `1/3`, choose a `MathContext` or `RoundingMode` and scale per the contract; otherwise `BigDecimal.divide` may throw `ArithmeticException`. An oracle must not be "infinitely exact" if the problem actually mandates rounding to two decimal places: in that case, the rounding rule **is part of the expected result**.

### 4.3. Using an Independent Implementation or Verified Result Tables

For algorithms with complex formulas, the reference can be:

- A simpler, clearer, slower implementation (e.g., `O(n^2)` for small test sizes).
- Values computed at higher precision with an appropriate numerical model.
- A benchmark suite with values verified manually or from trusted literature.
- An independent computation from another library/algorithm, with **compatible contract, domain, and rounding rules**.

**Never use the output of the function under test as "expected"** and check it via an equivalent transformation. Two implementations sharing the same flawed calculation can produce the same wrong result; oracle independence is a core part of verification.

## 5. Comparing Actual vs. Expected: Exact or Approximate Check?

### For Integers, Enums, or States

If the contract requires **exactness**, compare directly:

```java
long actual = 2_500_000_000L;
long expected = 2_500_000_000L;

if (actual != expected) {
    throw new AssertionError("Wrong integer result");
}
```

For `BigInteger`/`BigDecimal`, use the proper comparison API:

- `BigInteger.equals` checks equality of integer values.
- `BigDecimal.compareTo` compares mathematical values; `BigDecimal.equals` also requires **the same scale**. For example, `1.0` and `1.00` have `compareTo == 0` yet `equals == false`.

### For `float`/`double`, Absolute and Relative Error

Checking `actual == expected` may be inappropriate if results undergo different rounding steps. A common policy is:

```text
|actual - expected| <= max(absTol, relTol * max(|actual|, |expected|))
```

Here:

- `absTol` is the **absolute error threshold**, useful near zero.
- `relTol` is the **relative error threshold**, useful when magnitudes vary.
- Both thresholds must derive from model requirements, measurement units, and target precision.

Java example:

```java
static boolean nearlyEqual(double actual, double expected,
                           double absTol, double relTol) {
    if (!(Double.isFinite(actual) && Double.isFinite(expected))) {
        return false;
    }
    if (!(Double.isFinite(absTol) && Double.isFinite(relTol))
            || absTol < 0.0 || relTol < 0.0) {
        throw new IllegalArgumentException("Invalid tolerances");
    }

    double diff = Math.abs(actual - expected);
    double scale = Math.max(Math.abs(actual), Math.abs(expected));
    return diff <= Math.max(absTol, relTol * scale);
}
```

This is an **illustrative function for comparing finite numbers in normal numeric ranges**, not a flawless universal comparator. Subtracting `actual - expected` can overflow to infinity for two huge finite values of opposite sign; multiplying `relTol * scale` can also encounter edge cases. For high-reliability computations, choose and verify an error calculation suited to the data domain.

**Do not automatically use `1e-6` or `1e-12` for every algorithm**. Too tight a threshold can fail valid results; too loose a threshold can miss serious bugs. Tie thresholds to measurement resolution, result magnitudes, operation counts, and allowable problem error.

### NaN, Infinity, and Signed Zero Need Dedicated Test Cases

```java
System.out.println(Double.isNaN(0.0 / 0.0));         // true
System.out.println(Double.isInfinite(1.0 / 0.0));    // true
System.out.println(+0.0 == -0.0);                   // true
System.out.println(Double.compare(+0.0, -0.0) == 0); // false
```

- `NaN` does not equal itself under the primitive `==` operator, whereas `Double.equals` treats NaNs of the same type as equal. If the contract **forbids NaN**, check `Double.isFinite` instead of approximate comparison.
- `Infinity` can be a valid IEEE 754 result of floating-point division by zero, or a sign of invalid input/unacceptable numerical error per business rules.
- `+0.0` and `-0.0` are equal under `==` yet differ in sign bit. If the sign of zero is part of the contract (e.g., observable through reciprocal operations), deliberately check `Double.doubleToRawLongBits` or `Double.compare`.

In testing, never "fix" `NaN` by setting a large `tolerance`: define explicitly whether it is valid or a distinct error.

## 6. Property and Metamorphic Testing (*Property/Metamorphic Testing*)

Not every calculation has an easily built independent oracle. You can test **proven invariants within the valid domain** instead of checking only a single sample number.

Examples for integers and arrays:

- If a function counts elements, `count(empty) == 0` and adding one element increases the result by exact `1`, provided it does not exceed the type range.
- If an algorithm finds the minimum of a non-empty set, the result must be an element of the set and no greater than any element.
- If an encode-then-decode pair is designed to be lossless, verify `decode(encode(x)).equals(x)` for all valid `x`.
- For summation algorithms, if **computed with exact non-overflowing integers**, changing element order does not change the sum.
- For floating-point algorithms, changing summation order can alter the result because floating-point addition is **not associative**; check an approximate invariant only once a reasonable error bound is established.

**Do not mechanically apply ideal mathematical invariants to machine floating point.** For instance, `(a+b)+c == a+(b+c)` is not a general true property of `double` addition. `x - x == 0` also requires `x` to be finite; for `Infinity`, subtraction yields `NaN`.

Some useful metamorphic relations once the applicable domain is proven:

1. **Adding zero:** `sum(values plus 0)` should not change the mathematical value; however, with signed-zero data, sign representation can change with summation order/method.
2. **Checking independent formulas:** for non-overflowing `long` and `divisor != 0` (except the special case `MIN_VALUE / -1` in mathematical integer arithmetic), `dividend = divisor * quotient + remainder` cross-checks division and remainder.
3. **Checking output range:** valid probability ratios must lie in `0..1` if the contract specifies it; however, floating-point values right on the boundary may need tolerances or specified clamping strategies.
4. **Checking monotonicity:** a function proven to increase with input over a defined domain must not decrease unexpectedly, except for precision or overflow conditions handled separately by the contract.

Good invariants must have **clear preconditions**. A failing test can indicate an algorithmic bug, or it can indicate that the invariant you wrote does not hold in the real arithmetic model.

## 7. Testing Numerical Stability: Conditioning and Algorithm

An algorithm can be mathematically correct in formula yet **computationally unstable** in floating point.

Example computing `a + b + c` with numbers of vastly different magnitudes:

```java
double a = 1e16;
double b = -1e16;
double c = 1.0;

System.out.println((a + b) + c); // 1.0
System.out.println(a + (b + c)); // 0.0
```

All three operands are valid `double` values. The difference comes from **rounding intermediate expressions**. Before optimizing or reordering additions, check:

- Does computation order alter the result beyond acceptable error?
- Are there large opposite-sign numbers likely to cancel and expose relative error?
- Are many small terms "swallowed" when added to an overly large sum?
- Is the problem *ill-conditioned*, causing tiny input noise to produce huge output changes even with a stable algorithm?

**Conditioning** describes the sensitivity of the **mathematical problem** to input perturbations. **Numerical stability** describes whether the implemented algorithm amplifies computational error excessively. The two concepts are related yet distinct: if the problem itself is highly sensitive, even a good algorithm struggles to give strictly accurate results on noisy input data.

Concrete example of "small numbers being swallowed":

```java
double naive = 1e16;
for (int i = 0; i < 10; i++) {
    naive += 1.0;
}
System.out.println(naive - 1e16); // 0.0
```

The mathematical sum ought to increase by `10.0`. Alternatives such as **grouping small terms first**, pairwise summation, or Kahan/Neumaier compensated summation can reduce error for many datasets, yet do not guarantee strictly exact results in every case.

Design dedicated test cases to **demonstrate the effectiveness of a stabilization technique** on representative data, then compare against a higher-precision oracle.

## 8. Boundary Testing, Equivalence Partitioning, and Reproducible Random Data

A strong test suite typically combines three layers:

### Purposeful Boundary Data

Use a small table recording input, oracle, and rationale:

| ID | Input | Expected result | Purpose |
| --- | --- | --- | --- |
| INT-01 | `Integer.MAX_VALUE + 1` under `int` addition | `Integer.MIN_VALUE` if wraparound contract | Check sign/overflow |
| INT-02 | `Math.addExact(Integer.MAX_VALUE, 1)` | `ArithmeticException` | Check overflow reporting |
| DEC-01 | Ten decimal `"0.1"` values | `BigDecimal("1.0")` | Exact decimal oracle |
| FP-01 | `1e16 + 1.0` | Same `double` pattern as `1e16` | Resolution/ULP |
| FP-02 | `Double.MIN_VALUE / 2.0` | `0.0` | Underflow |
| FP-03 | `Double.MAX_VALUE * 2.0` | `+Infinity` | Floating-point overflow |
| FP-04 | `0.0 / 0.0` | `NaN` | Special value |
| FP-05 | Comparing `+0.0` with `-0.0` | `==` gives true, bit comparison gives false | Signed zero |

### Equivalence Partitioning

Divide the input domain into meaningful groups: negative/positive, zero, small/large intervals, finite/non-finite, overflow-prone/safe, valid/invalid domain data. Pick representatives from each group, then add near-boundary values. Partitioning helps avoid testing only easy small positive numbers.

### Randomized/Property-Based Testing

Generate additional data with a **fixed seed** for reproducibility:

```java
java.util.Random random = new java.util.Random(2026L);
for (int i = 0; i < 1_000; i++) {
    int x = random.nextInt();
    int y = random.nextInt();
    // Compare the algorithm against an appropriate independent oracle.
}
```

If a randomized test fails, record the **seed, exact inputs, generation order, environment, and error details** to reproduce it. Do not merely report "1000 test cases passed." Beyond uniform random sampling over a range, explicitly inject boundary values because the probability of randomly hitting `Integer.MIN_VALUE` or an exact ULP boundary is tiny.

For specialized `double` testing, bit patterns can be generated via `Double.longBitsToDouble(random.nextLong())`, though you must partition finite/`NaN`/infinity inputs and handle them per contract rather than forcing everything through one approximate comparison.

## 9. Bugs Inside the Test Code Itself

**Tests can have bugs too.** Common pitfalls:

1. **Oracle overflowing in the same type:** `BigInteger.valueOf(a * b)` receives an already-overflowed `int` result. Convert each operand before multiplying.
2. **Oracle using the same algorithm as the code under test:** if both share the same wrong formula, matching results fail to catch the bug.
3. **Comparing `double` with `==` in all cases:** harmless rounding differences get flagged as failures; conversely, overly loose approximate comparison can mask bugs.
4. **Testing only ordinary random data:** misses `MAX_VALUE` thresholds, exact bit boundaries, zero, and special values.
5. **Ignoring NaN:** in conditional comparisons, `NaN` can make `>`, `<`, and `==` all false, letting manual assertions slip past conditions.
6. **Confusing `Double.MIN_VALUE` with the most negative number:** it is **the smallest positive subnormal number greater than 0**, not a large-magnitude negative number; the negative value with largest magnitude is `-Double.MAX_VALUE`.
7. **Converting an already corrupted `double` to `BigDecimal` expecting to fix the data:** once rounding/information loss has occurred, type conversion does not recover it.
8. **Using one epsilon across all scales:** creates mismatch between near-zero results and very large results.
9. **Not testing exceptions:** for division by 0 or overflow designed to fail loudly, the exception type itself is the expected result.
10. **Relying on timing or unspecified collection iteration order:** these must not act as oracles for numerical values unless specified by the contract.
11. **Testing only the final result while ignoring invariants:** an algorithm can match some inputs yet violate output bounds or monotonicity.
12. **Using Java `assert` without enabling it at runtime:** the `assert` statement is disabled by default in many environments; `java -ea` or a proper testing framework is required. `throw new AssertionError(...)` does not depend on the `-ea` flag.

## 10. Standalone Java 17+ Example with Oracle and Boundary Data

Create the file **`NumericalBoundaryReferenceDemo.java`**:

```java
import java.math.BigDecimal;
import java.math.BigInteger;

public class NumericalBoundaryReferenceDemo {
    static boolean nearlyEqual(double actual, double expected,
                               double absTol, double relTol) {
        if (!Double.isFinite(actual) || !Double.isFinite(expected)) {
            return false;
        }
        if (!Double.isFinite(absTol) || !Double.isFinite(relTol)
                || absTol < 0.0 || relTol < 0.0) {
            throw new IllegalArgumentException("Invalid tolerance");
        }

        double diff = Math.abs(actual - expected);
        double scale = Math.max(Math.abs(actual), Math.abs(expected));
        return diff <= Math.max(absTol, relTol * scale);
    }

    public static void main(String[] args) {
        double sum = 0.0;
        for (int i = 0; i < 10; i++) {
            sum += 0.1;
        }

        BigDecimal decimalReference =
                new BigDecimal("0.1").multiply(BigDecimal.TEN);

        System.out.println("double sum = " + sum);
        System.out.println("decimal reference = "
                + decimalReference.toPlainString());
        System.out.println("strict comparison = "
                + (sum == decimalReference.doubleValue()));
        System.out.println("tolerant comparison = "
                + nearlyEqual(sum, decimalReference.doubleValue(),
                              1e-12, 1e-12));

        int max = Integer.MAX_VALUE;
        System.out.println("int wrap = "
                + (max + 1 == Integer.MIN_VALUE));
        BigInteger exactInteger = BigInteger.valueOf(max)
                .add(BigInteger.ONE);
        System.out.println("BigInteger reference = " + exactInteger);

        try {
            Math.addExact(max, 1);
            System.out.println("unexpected: no overflow");
        } catch (ArithmeticException ex) {
            System.out.println("checked overflow detected");
        }

        double huge = 1e16;
        System.out.println("small increment lost = "
                + (huge + 1.0 == huge));
        System.out.println("ULP at 1e16 = " + Math.ulp(huge));
        System.out.println("BigDecimal exact increment = "
                + new BigDecimal("10000000000000000")
                    .add(BigDecimal.ONE).toPlainString());

        System.out.println("underflow to zero = "
                + (Double.MIN_VALUE / 2.0 == 0.0));
        System.out.println("overflow to infinity = "
                + Double.isInfinite(Double.MAX_VALUE * 2.0));
        System.out.println("NaN detected = "
                + Double.isNaN(0.0 / 0.0));
        System.out.println("signed zero primitive equal = "
                + (+0.0 == -0.0));
        System.out.println("signed zero raw bits equal = "
                + (Double.doubleToRawLongBits(+0.0)
                == Double.doubleToRawLongBits(-0.0)));
    }
}
```

Compile and run with JDK 17 or newer:

```bash
javac NumericalBoundaryReferenceDemo.java
java NumericalBoundaryReferenceDemo
```

Expected output:

```text
double sum = 0.9999999999999999
decimal reference = 1.0
strict comparison = false
tolerant comparison = true
int wrap = true
BigInteger reference = 2147483648
checked overflow detected
small increment lost = true
ULP at 1e16 = 2.0
BigDecimal exact increment = 10000000000000001
underflow to zero = true
overflow to infinity = true
NaN detected = true
signed zero primitive equal = true
signed zero raw bits equal = false
```

The test case groups illustrate **different contracts**: `BigInteger` and `BigDecimal` act as exact references, `Math.addExact` confirms overflow-reporting behavior, approximate checks allow `double` summation, and special values are checked individually.

**Verification note:** the output above is presented for purposeful comparison. In real projects, convert cases into named assertions, run them automatically in CI, and clearly report input/expected/actual on every failure. When modifying an algorithm to improve numerical stability, retain boundary cases as **regression tests** to prevent bugs from returning.

## 11. Verification Checklist Before Accepting a Numerical Algorithm

1. **Contract:** state input domain, rounding rules, data types, exceptions, and allowable error clearly.
2. **Oracle:** choose an independent reference matching the input model; avoid overflow when constructing expected values.
3. **Boundary domain:** include zero, negative values, type extremes, values right around thresholds, and large–small/opposite-sign combinations.
4. **Special floating-point cases:** decide behavior for `NaN`, infinity, signed zero, subnormal, overflow, and underflow.
5. **Comparison method:** use exact equality when required; use justified absolute/relative/ULP thresholds when error is tolerated.
6. **Stability:** test data prone to cancellation, small-term loss, error accumulation, or high sensitivity.
7. **Properties:** verify invariants and metamorphic relations that hold in **the Java execution domain**, without silently assuming all real-number algebraic laws hold.
8. **Reproducibility:** log seed, inputs, and environment in randomized tests; save regression cases after fixing bugs.
9. **Automation:** use JUnit or a clear test harness; rerun the same suite in the pipeline whenever editing code.
10. **Failure diagnostics:** every test failure should report value deviation, threshold, rule, and business meaning, not just "expected != actual."

**Conclusion:** Verifying numerical algorithms cannot rely solely on a few "nice" examples. Combine **purposefully chosen boundary data**, **sufficiently independent/accurate reference results**, and **comparison rules matching the contract**. In Java, `BigInteger`/`BigDecimal`, `Math.*Exact`, `Math.ulp`, and `isFinite`/`isNaN` checks help catch bugs that appear only at type-width boundaries and floating-point precision limits.
