# BigDecimal.valueOf(double) and the Limits of Source double Values in Java

## 1. Core issue: type conversion cannot recover lost information

`BigDecimal.valueOf(double)` is the commonly recommended approach when you **already have a `double` value** and want to create a `BigDecimal` with a short, readable decimal representation. However, this method **does not turn an inaccurate `double` calculation into an exact decimal calculation**, nor can it recover digits that were rounded away earlier.

Three statements look similar yet have different semantics:

```java
import java.math.BigDecimal;

BigDecimal fromText = new BigDecimal("0.1");
BigDecimal viaValueOf = BigDecimal.valueOf(0.1);
BigDecimal fromDoubleConstructor = new BigDecimal(0.1);
```

- `new BigDecimal("0.1")` reads the **original decimal string**, storing exact value 0.1.
- `BigDecimal.valueOf(0.1)` first receives a **`double` literal** close to 0.1, and then uses the string form generated by `Double.toString(0.1)`, in this case `"0.1"`, to create a `BigDecimal` with decimal value 0.1.
- `new BigDecimal(0.1)` represents **the exact binary value stored in `double`** in decimal form. Because that value is not exact 1/10, the resulting object does not equal decimal 0.1.

The `BigDecimal` class does not cause the source error. The error arises **before the call** when we write, parse, compute, or narrow a value into `double`.

**Learning principle:** distinguish **the original decimal value**, **the actually stored binary64 value**, and **the short decimal string used to re-represent that binary64 value**. These three things can differ.

## 2. Recap: how does `double` store binary floating-point numbers?

Java's `double` type is a 64-bit binary floating-point number following the IEEE 754 binary64 format:

| Component | Bits | Meaning |
|---|---:|---|
| Sign | 1 | Positive or negative |
| Exponent | 11 | Value scale by powers of 2 |
| Stored fraction | 52 | Explicit bits of the significand |
| Effective significand precision | 53 | Includes implicit leading bit in normal numbers |

`double` provides roughly **15–17 significant decimal digits**, yet that does not mean every 15-digit decimal number is exact. Fractions like 1/10 generally have infinite binary expansions, so Java must store an **approximated binary value**.

Example:

```java
double x = 0.1;
double y = 0.2;
double sum = x + y;

System.out.println(sum); // 0.30000000000000004
```

Although decimal arithmetic gives 0.1 + 0.2 = 0.3, the operands were already rounded to binary64 and the addition also underwent rounding. Hence the stored `sum` value corresponds to the printed representation `0.30000000000000004`.

At this point, converting `sum` to `BigDecimal` **cannot guess** whether the author wanted 0.3 or wanted exact 0.30000000000000004. It knows only the `double` value passed in.

## 3. What does `BigDecimal.valueOf(double)` actually do?

Per the API contract, `BigDecimal.valueOf(double)` uses the canonical decimal representation provided by `Double.toString(double)`, equivalent in **value and string interpretation** to calling:

```java
double source = 0.1;

BigDecimal viaValueOf = BigDecimal.valueOf(source);
BigDecimal viaText =
        new BigDecimal(Double.toString(source));
```

In this case, both objects have decimal value **0.1** and scale 1.

`Double.toString` produces a canonical decimal string that can **round-trip** back to the same `double` value (with special rules for 0, NaN, and infinity). It **does not print the full exact decimal expansion of the binary64 bit pattern** in all cases.

Example:

```java
System.out.println(Double.toString(0.1)); // 0.1
System.out.println(BigDecimal.valueOf(0.1)); // 0.1
```

Yet:

```java
double sum = 0.1 + 0.2;
System.out.println(Double.toString(sum));
// 0.30000000000000004

System.out.println(BigDecimal.valueOf(sum));
// 0.30000000000000004
```

This difference is **already present in the source value**, not an automatic intuitive "error-fixing" choice by `BigDecimal`.

### Frequently asked question: is `valueOf` an "exact" conversion?

You must specify **"exact with respect to what?"**:

1. **Exact with respect to the string `Double.toString(source)`:** yes. `valueOf` produces the exact decimal for that string.
2. **Exact with respect to the original decimal number a user entered before converting to `double`:** not guaranteed.
3. **Exact with respect to every bit of the binary64 value expanded as a decimal fraction:** no. To get the exact decimal expansion of a binary64 value, the `new BigDecimal(double)` constructor has that semantics.
4. **Exact with respect to the ideal mathematical result before `double` operations:** cannot be claimed.

Therefore `valueOf` is useful, yet it is a **conversion from the current state**, not a mechanism to restore input history.

## 4. Three ways to create `BigDecimal` and their differences

| Creation method | Source of meaning | Result for 0.1 example |
|---|---|---|
| `new BigDecimal("0.1")` | Exact decimal string | Value 0.1, scale 1 |
| `BigDecimal.valueOf(0.1)` | Canonical decimal from `Double.toString` of `double` | Value 0.1, scale 1 |
| `new BigDecimal(0.1)` | Exact expansion of stored binary64 value | Longer decimal, not equal to exact 0.1 |
| `BigDecimal.valueOf(1L)` | `long` integer | Exact integer 1 |
| `BigDecimal.valueOf(12345L, 2)` | Unscaled integer + scale | Exact 123.45 |

The exact decimal representation of the binary64 pattern near 0.1 is:

```text
0.1000000000000000055511151231257827021181583404541015625
```

This is the value of `new BigDecimal(0.1)`, **not** the string printed by `Double.toString(0.1)`.

### Distinguishing `valueOf(double)` and `valueOf(long)` overloads

`BigDecimal.valueOf(123L)` takes a **`long` integer**, so it can preserve every `long` value exactly. Do not cast large integers through `double` before creating a decimal:

```java
long original = 9_007_199_254_740_993L;

BigDecimal exact = BigDecimal.valueOf(original);
BigDecimal potentiallyRounded =
        BigDecimal.valueOf((double) original);
```

`original` exceeds the range where every consecutive integer is exactly representable in binary64, so the path through `double` already lost information.

In addition, `BigDecimal.valueOf(unscaledValue, scale)` is very useful for creating exact decimals from the smallest unit, such as cents, without going through binary floating point.

## 5. Java 17+ example 1: clearly seeing the three creation methods

Create the file `ValueOfBasicsDemo.java`:

```java
import java.math.BigDecimal;

public class ValueOfBasicsDemo {
    public static void main(String[] args) {
        BigDecimal fromText = new BigDecimal("0.1");
        BigDecimal valueOf = BigDecimal.valueOf(0.1);
        BigDecimal fromBinary = new BigDecimal(0.1);

        System.out.println("text: " + fromText.toPlainString());
        System.out.println("valueOf: " + valueOf.toPlainString());
        System.out.println("binary exact: "
                + fromBinary.toPlainString());

        System.out.println("text equals valueOf: "
                + fromText.equals(valueOf));
        System.out.println("text equals binary: "
                + fromText.equals(fromBinary));

        double sum = 0.1 + 0.2;
        System.out.println("double sum: " + sum);
        System.out.println("valueOf(sum): "
                + BigDecimal.valueOf(sum).toPlainString());
        System.out.println("decimal sum: "
                + new BigDecimal("0.1")
                        .add(new BigDecimal("0.2"))
                        .toPlainString());

        System.out.println("valueOf(12345, 2): "
                + BigDecimal.valueOf(12345L, 2).toPlainString());
    }
}
```

Compile and run with Java 17+:

```bash
javac ValueOfBasicsDemo.java
java ValueOfBasicsDemo
```

Output:

```text

valueOf: 0.1
binary exact: 0.1000000000000000055511151231257827021181583404541015625

text equals binary: false

valueOf(sum): 0.30000000000000004
decimal sum: 0.3
valueOf(12345, 2): 123.45
```

In the example, `new BigDecimal("0.1")` and `BigDecimal.valueOf(0.1)` are equal, yet that happens only because the canonical string of the binary64 value near 0.1 is `"0.1"`. Do not overgeneralize that `valueOf` always recovers the original decimal string or automatically rounds to a "nice-looking value."

## 6. Error from **completed `double` arithmetic** before calling `valueOf`

This is the most important limitation.

Compare two data flows:

**Flow A — exact decimal from the start:**

```java
BigDecimal a = new BigDecimal("0.1");
BigDecimal b = new BigDecimal("0.2");
BigDecimal total = a.add(b); // 0.3
```

**Flow B — compute in binary64 and convert afterward:**

```java
double a = 0.1;
double b = 0.2;
double total = a + b;
BigDecimal converted = BigDecimal.valueOf(total);
// 0.30000000000000004
```

In Flow B, the addition already executed under floating-point rules. `valueOf` neither knows that the original sources of the two numbers were decimal literals 0.1 and 0.2, nor has it been told that business logic wants 1 decimal place.

Similarly:

```java
double third = 1.0 / 3.0;
BigDecimal saved = BigDecimal.valueOf(third);
// 0.3333333333333333
```

`saved` is a finite decimal with sixteen 3s after the decimal point. **It cannot be treated as an exact representation of the mathematical fraction 1/3**, because that fraction has an infinite decimal expansion.

### Is "converting to `BigDecimal` and continuing calculations" useful?

Yes, provided you understand the precision boundary:

- `BigDecimal` operations **after the conversion point** can use the object's decimal representation and the rounding policy you define.
- **Errors already present in the input `double` value will carry over** into the `BigDecimal` created from it.
- If original decimal strings or exact integer data are still available, **create `BigDecimal` directly from that source** instead of going through `double`.

Do not arbitrarily call `setScale(2, ...)` and claim "all errors are completely fixed." Rounding may be right if business logic specifies 2 digits, yet that is **a business decision**, not proof that the original value was recovered.

## 7. Loss of large integers: the 53-bit significand limit

Binary64 has 53 bits of significand precision. Every integer with absolute value at most \(2^{53}\) is represented exactly, yet **not every consecutive integer beyond that limit** is exact.

The value:

\[
2^{53} = 9\,007\,199\,254\,740\,992
\]

is an exactly representable integer. The next integer \(2^{53}+1\) is **not** exactly representable in `double` and will be rounded.

Example:

```java
long original = 9_007_199_254_740_993L;
double rounded = (double) original;

BigDecimal wrong = BigDecimal.valueOf(rounded);
BigDecimal right = BigDecimal.valueOf(original);
```

`wrong` holds 9_007_199_254_740_992, whereas `right` holds the exact 9_007_199_254_740_993.

**System lesson:** do not convert large integer IDs, cent counts, counters, nanosecond timestamps, or critical integers to `double` only to call `BigDecimal.valueOf` afterward. If the source is `long`, call `BigDecimal.valueOf(long)` directly.

### JavaScript/JSON and intermediary APIs

Another system may send JSON numbers through a runtime that uses 64-bit binary numbers. If data was already rounded on one side, the Java server **cannot recover the digits using `BigDecimal.valueOf`**. For IDs or exact monetary amounts, specify an appropriate wire type such as a decimal string or an object with explicit integer/unit fields.

The key is **end-to-end exactness**: Java can preserve the original data only if prior steps also preserved it.

## 8. Java 17+ example 2: losing large integers and source decimal digits

Create the file `SourcePrecisionDemo.java`:

```java
import java.math.BigDecimal;

public class SourcePrecisionDemo {
    public static void main(String[] args) {
        long exactId = 9_007_199_254_740_993L;
        double roundedId = (double) exactId;

        System.out.println("long source: " + exactId);
        System.out.println("double as long: " + (long) roundedId);
        System.out.println("via double: "
                + BigDecimal.valueOf(roundedId).toPlainString());
        System.out.println("via long: "
                + BigDecimal.valueOf(exactId).toPlainString());

        String preciseText = "0.1000000000000000000001";
        BigDecimal direct = new BigDecimal(preciseText);
        BigDecimal viaDouble =
                BigDecimal.valueOf(Double.parseDouble(preciseText));

        System.out.println("from decimal text: "
                + direct.toPlainString());
        System.out.println("after double parse: "
                + viaDouble.toPlainString());
        System.out.println("same decimal value: "
                + (direct.compareTo(viaDouble) == 0));
    }
}
```

Run:

```bash
javac SourcePrecisionDemo.java
java SourcePrecisionDemo
```

Output:

```text
long source: 9007199254740993
double as long: 9007199254740992
via double: 9007199254740992
via long: 9007199254740993
from decimal text: 0.1000000000000000000001
after double parse: 0.1

```

In the long decimal case, `Double.parseDouble` retains only the nearest binary64 value, whose canonical string is `"0.1"`. When converted via `valueOf`, the trailing `...0001` digits in the source **no longer exist in the input**.

This is why **data requiring exact decimals must be parsed into exact decimals right from the start**.

## 9. Trailing zeros and `scale` can also be lost

Another bug more subtle than arithmetic rounding error: **the numeric value may be preserved while the representation and `scale` are not**.

Suppose the input source is the string:

```text
"19.90"
```

If you parse it via `double`:

```java
double d = Double.parseDouble("19.90");
System.out.println(Double.toString(d)); // 19.9

BigDecimal fromDouble = BigDecimal.valueOf(d);
System.out.println(fromDouble);         // 19.9
System.out.println(fromDouble.scale()); // 1
```

Meanwhile:

```java
BigDecimal fromText = new BigDecimal("19.90");
System.out.println(fromText);         // 19.90
System.out.println(fromText.scale()); // 2
```

The two objects are mathematically equal, yet:

```java
System.out.println(fromDouble.compareTo(fromText)); // 0
System.out.println(fromDouble.equals(fromText));    // false
```

**Why?** `compareTo` compares numeric value, whereas `BigDecimal.equals` checks **scale** as well. `double` carries no information about "how many trailing zeros after the decimal point the sender wrote."

If scale is meaningful in invoices, stored data, or protocols, **you must preserve the original string or scale metadata**. `valueOf` cannot deduce whether 19.9 was previously written as 19.90 or 19.9000.

### Brief explanation of scale

A `BigDecimal` can be expressed as:

\[
\text{value} = \text{unscaledValue} \times 10^{-\text{scale}}
\]

`new BigDecimal("19.90")` has unscaled integer 1990 and scale 2. `BigDecimal.valueOf(19.9)` has unscaled integer 199 and scale 1. Both represent the same mathematical value 19.9, yet **their representation contracts** differ.

## 10. `BigDecimal.valueOf(double)` has no concept of NaN or Infinity

The `double` type has special values:

- `Double.NaN`.
- `Double.POSITIVE_INFINITY`.
- `Double.NEGATIVE_INFINITY`.

However, `BigDecimal` **has no NaN or ±Infinity values** in its decimal model. Therefore:

```java
// BigDecimal.valueOf(Double.NaN);               // NumberFormatException
// BigDecimal.valueOf(Double.POSITIVE_INFINITY); // NumberFormatException
// BigDecimal.valueOf(Double.NEGATIVE_INFINITY); // NumberFormatException
```

The lines above are commented out so the example does not halt the program. `BigDecimal.valueOf` does not silently turn NaN into 0 or Infinity into a maximum number.

Common scenario:

```java
double invalid = 0.0 / 0.0; // NaN
// BigDecimal result = BigDecimal.valueOf(invalid);
// throws NumberFormatException at runtime
```

Therefore, for a `double` from untrusted input or a calculation chain with overflow risk, check beforehand:

```java
static BigDecimal requireFiniteDecimal(double value) {
    if (!Double.isFinite(value)) {
        throw new IllegalArgumentException(
                "NaN or infinity is not a decimal value");
    }
    return BigDecimal.valueOf(value);
}
```

This is an **illustrative** method to be placed inside a class importing `java.math.BigDecimal`. Checking `Double.isFinite` guarantees only that the argument can convert to a finite decimal; it **does not prove the source was represented accurately**.

## 11. Overflow and underflow before calling `valueOf`

### 11.1. Overflow: finite values turn into Infinity

`double` has a magnitude limit. For example:

```java
double source = Double.MAX_VALUE;
double overflowed = source * 2.0;

System.out.println(Double.isFinite(source)); // true
System.out.println(Double.isFinite(overflowed)); // false
```

The product of two finite numbers can overflow to +Infinity. After this step `BigDecimal.valueOf(overflowed)` will throw `NumberFormatException` instead of inferring an enormous decimal result.

If the problem requires exact arithmetic with numbers exceeding `double` range and **the original data is still exact**, convert to `BigDecimal` before multiplying rather than using an Infinity result as input.

### 11.2. Underflow: tiny values turn into 0.0

The smallest positive nonzero `double` is `Double.MIN_VALUE` (a positive subnormal number). Dividing it by 2 rounds the result to 0:

```java
double smallest = Double.MIN_VALUE;
double underflowed = smallest / 2.0;

System.out.println(underflowed); // 0.0
System.out.println(Double.isFinite(underflowed)); // true
```

Afterward:

```java
BigDecimal converted = BigDecimal.valueOf(underflowed);
// decimal value 0.0
```

The nonzero information was already lost **before calling `valueOf`**. Because 0.0 is still finite, checking `isFinite` alone does not detect underflow.

**Further distinction:** `BigDecimal.valueOf(Double.MIN_VALUE)` is created from the canonical string `Double.toString(Double.MIN_VALUE)`, typically printing `4.9E-324`. That is the short decimal round-tripping to `Double.MIN_VALUE`, not the entire exact decimal expansion of that tiny binary bit pattern.

## 12. Signed zero: `double` distinguishes it, `BigDecimal` does not

IEEE 754 binary64 has two bit patterns for zero:

- +0.0.
- -0.0.

Under `double` arithmetic comparison:

```java
System.out.println(0.0 == -0.0); // true
System.out.println(1.0 / 0.0);   // Infinity
System.out.println(1.0 / -0.0);  // -Infinity
```

Meanwhile, `BigDecimal` has **decimal 0** yet does not store a **negative sign bit on zero** like floating-point types. Therefore:

```java
BigDecimal plus = BigDecimal.valueOf(0.0);
BigDecimal minus = BigDecimal.valueOf(-0.0);

System.out.println(plus.equals(minus)); // true
System.out.println(minus.toPlainString()); // 0.0
```

`Double.toString(-0.0)` can contain the minus sign `"-0.0"`, yet when parsed into `BigDecimal`, decimal zero does not retain a separate negative sign. If a protocol requires distinguishing the exact **+0.0 and -0.0 bit patterns**, you must store the `double` bit pattern separately, e.g., via `Double.doubleToRawLongBits`, rather than expecting `BigDecimal` to preserve that detail.

This is another example showing that **valueOf converts values**, rather than preserving all representation details of `double`.

## 13. Java 17+ example 3: special boundary cases

Create the file `FloatingBoundaryDemo.java`:

```java
import java.math.BigDecimal;

public class FloatingBoundaryDemo {
    private static void tryConvert(String label, double value) {
        try {
            System.out.println(label + " -> "
                    + BigDecimal.valueOf(value).toString());
        } catch (NumberFormatException e) {
            System.out.println(label + " -> NumberFormatException");
        }
    }

    public static void main(String[] args) {
        double overflow = Double.MAX_VALUE * 2.0;
        double underflow = Double.MIN_VALUE / 2.0;

        System.out.println("overflow finite: "
                + Double.isFinite(overflow));
        System.out.println("underflow: " + underflow);
        System.out.println("underflow finite: "
                + Double.isFinite(underflow));

        tryConvert("NaN", Double.NaN);
        tryConvert("+Infinity", Double.POSITIVE_INFINITY);
        tryConvert("-Infinity", Double.NEGATIVE_INFINITY);
        tryConvert("underflowed zero", underflow);

        BigDecimal negativeZero =
                BigDecimal.valueOf(-0.0);
        BigDecimal positiveZero =
                BigDecimal.valueOf(+0.0);

        System.out.println("zero decimals equal: "
                + negativeZero.equals(positiveZero));
        System.out.println("negative zero converted: "
                + negativeZero.toPlainString());
        System.out.println("double raw zero bits equal: "
                + (Double.doubleToRawLongBits(-0.0)
                    == Double.doubleToRawLongBits(+0.0)));
    }
}
```

Compile and run:

```bash
javac FloatingBoundaryDemo.java
java FloatingBoundaryDemo
```

Output:

```text
overflow finite: false
underflow: 0.0
underflow finite: true
NaN -> NumberFormatException
+Infinity -> NumberFormatException
-Infinity -> NumberFormatException
underflowed zero -> 0.0
zero decimals equal: true
negative zero converted: 0.0
double raw zero bits equal: false
```

The example shows that `BigDecimal.valueOf` cannot turn an Infinity or NaN value into a decimal. Nor can it recover a tiny number that underflowed to 0, and it does not preserve zero's negative sign information.

## 14. Be careful when obtaining `double` from strings, JSON, and databases

There are two very different parsing flows.

### Flow A: read exact decimal strings directly

```java
String text = "12345678901234567890.1234500";
BigDecimal value = new BigDecimal(text);
```

The result preserves **exact decimal digits and scale from the string**, provided syntax is valid and resources suffice. This fits data whose contract requires decimal preservation.

### Flow B: read via `double` first

```java
String text = "12345678901234567890.1234500";
double approximate = Double.parseDouble(text);
BigDecimal value = BigDecimal.valueOf(approximate);
```

In Flow B, many digits may already have been rounded when `Double.parseDouble` created binary64. `BigDecimal.valueOf` cannot retrieve those digits, even though the resulting `BigDecimal` object is capable of holding long decimals.

With JSON, spreadsheets, databases, or user interfaces, you must verify:

- Does the parser map numeric fields to `double`, `BigDecimal`, or another type?
- Is there a requirement to preserve **decimal value** or **scale and trailing zeros**?
- Can inputs exceed `double` range or 53 bits of integer precision?
- Could a JSON number generated by another runtime already have been rounded on the sender side?
- For `DECIMAL/NUMERIC` database columns, does the driver/ORM return `BigDecimal` directly or convert via a floating-point type?

**Practical recommendation:** if a value is money, a decimal-specified rate, or a field requiring exactness, **transmit, receive, and parse directly as `BigDecimal` or unit-scaled integers**, rather than passing unnecessarily through `double`.

### Trailing zeros in financial data

If a system receives `"19.90"`, `BigDecimal.valueOf(Double.parseDouble("19.90"))` creates 19.9. That may be numerically equal yet differ in scale from `new BigDecimal("19.90")`. When scale is part of the storage or display contract, this difference cannot be ignored.

## 15. Rounding can be right, yet it must be the chosen rule

Some developers handle `double` error by writing:

```java
BigDecimal amount = BigDecimal.valueOf(value)
        .setScale(2, java.math.RoundingMode.HALF_UP);
```

This is **valid if** business logic specifies rounding to 2 decimal places using `HALF_UP`. However, understand:

1. `value` already held a binary64 value; source error may already have occurred.
2. `BigDecimal.valueOf(value)` takes the canonical decimal from that value.
3. `setScale(2, HALF_UP)` **rounds that decimal value**, without promising to restore the source data.
4. If the application needs rounding by another standard, `HALF_EVEN` or another policy may be more appropriate.

### Midpoint example

```java
import java.math.BigDecimal;
import java.math.RoundingMode;

BigDecimal a = new BigDecimal("2.675");
BigDecimal b = BigDecimal.valueOf(2.675);
BigDecimal c = new BigDecimal(2.675);
```

This is an **illustrative code snippet inside a method**, requiring the corresponding imports. `a` and `b` have decimal value 2.675; `c` represents the exact binary64 approximation of 2.675 (slightly below mathematical 2.675).

When rounding to two decimal places with `HALF_UP`:

- `a.setScale(2, HALF_UP)` → **2.68**.
- `b.setScale(2, HALF_UP)` → **2.68**.
- `c.setScale(2, HALF_UP)` → **2.67**.

This example does not prove `valueOf` "cures binary64." It shows **two different ways of interpreting a binary64 source as decimal**, and how the conversion point determines which number gets rounded.

If the initial input was the string `"2.675"`, the least ambiguous choice is `new BigDecimal("2.675")`. If the input is only a `double` remaining after many calculations, verify whether rounding the `Double.toString` decimal form fits business requirements.

## 17. `valueOf(double)` is not a way to validate whether data is valid

A finite `double` input can still be:

- Negative when business logic accepts only positive numbers.
- Too large for practical limits.
- Fractional when an integer is required.
- Already rounded relative to the decimal source.
- Lower precision than required.
- Equal to -0.0 needing special handling.
- Missing its original scale.

Therefore a conversion method should be only **one step** in the pipeline. Example:

```java
static BigDecimal convertMeasuredRate(double input) {
    if (!Double.isFinite(input)) {
        throw new IllegalArgumentException("non-finite rate");
    }
    if (input < 0.0 || input > 1.0) {
        throw new IllegalArgumentException("rate outside 0..1");
    }
    return BigDecimal.valueOf(input);
}
```

This is an **illustrative method** placed inside a class importing `BigDecimal`. It checks finiteness and `[0, 1]` bounds, yet **does not guarantee decimal accuracy from the source**. It is suitable only if business logic accepts converting an approximated `double` measurement/probability to a canonical decimal.

If the requirement is an **exact user-entered decimal rate**, the API should accept `String` or `BigDecimal` right at the boundary so input data is not lost:

```java
static BigDecimal parseExactRate(String text) {
    BigDecimal value = new BigDecimal(text);
    if (value.compareTo(BigDecimal.ZERO) < 0
            || value.compareTo(BigDecimal.ONE) > 0) {
        throw new IllegalArgumentException("rate outside 0..1");
    }
    return value;
}
```

Do not use `Double.parseDouble` followed by `BigDecimal.valueOf` here if preserving the exact original decimal is required.

## 18. When is using `BigDecimal.valueOf(double)` appropriate?

Situations where it can be appropriate:

1. **The system already has `double` data by design**, such as sensor measurements, statistical analysis results, or library APIs that only return `double`. You accept that binary64 determined the existing value.
2. You need a **short, readable decimal representation** per `Double.toString` rather than the long exact decimal expansion of binary64 bits.
3. You want to perform subsequent decimal arithmetic under a clear policy, **while acknowledging that the source precision is only `double`**.
4. You want to store **a value close to what `Double.toString` communicates**, not digits that may have been lost earlier.

Situations where it **should not be considered a sufficient solution**:

- Original currency strings needing exact fractional digits and scale preserved.
- Large integer IDs, large counts, or timestamps with precision exceeding binary64 capacity.
- Calculations requiring decimal exactness from the start.
- Values that already overflowed to Infinity, underflowed to 0, or fell into NaN.
- Inputs from another system that were already rounded when you must prove data integrity.

### Comparing API choices

| Existing data | Suggested API | What is preserved? |
|---|---|---|
| `String "19.90"` | `new BigDecimal("19.90")` | Original decimal and scale |
| `long cents = 1990` | `BigDecimal.valueOf(cents, 2)` | Exact integer with scale 2 |
| `long count` | `BigDecimal.valueOf(count)` | Every `long` value exactly |
| `double rate` allowed to be approximate | `BigDecimal.valueOf(rate)` | Canonical decimal from `Double.toString(rate)` |
| `double d` needing exact decimal expansion of binary value | `new BigDecimal(d)` | True binary64 value |
| `double` NaN/Infinity | Cannot create a normal `BigDecimal` | Must reject or represent state separately |

Especially for decimal data from JSON, CSV, UI, or databases, **the data contract must determine the input type before choosing an overload**. Do not pick `valueOf(double)` just because it is convenient to write.

## 19. Common mistakes

| Misconception | Reality | Solution |
|---|---|---|
| `BigDecimal.valueOf(0.1 + 0.2)` becomes 0.3 | The `double` result is already 0.30000000000000004 | Compute with `BigDecimal` from decimal sources first |
| `valueOf(double)` always records exact binary64 bits | It uses canonical decimal from `Double.toString` | Use `new BigDecimal(d)` if bit-value expansion is genuinely needed |
| `valueOf` restores lost decimal digits | Original input information is absent | Parse decimal strings directly |
| `valueOf((double) longBig)` preserves every integer | Binary64 has a 53-bit significand limit | Use `valueOf(long)` |
| `valueOf(Double.NaN)` returns decimal NaN | `BigDecimal` has no NaN | Check `Double.isFinite` and handle errors |
| `valueOf(Double.POSITIVE_INFINITY)` clamps to MAX | No such saturation; throws `NumberFormatException` | Handle infinity beforehand |
| Underflow to 0 can still recover the initial tiny number | Source already became 0.0 | Handle decimal or suitable type beforehand |
| `valueOf(-0.0)` preserves negative zero sign | `BigDecimal` does not keep signed zero | Store raw `double` pattern separately if needed |
| Decimal `"19.90"` via `double` keeps scale 2 | `Double.toString` prints 19.9 | Keep `String` or construct decimal with explicit scale |
| `equals` and `compareTo` are always equivalent | `equals` checks scale too | Choose comparison according to goal |
| `setScale(2)` fixes source accuracy by itself | It is a rounding rule on the existing decimal | Configure rounding per business requirements |
| `Double.isFinite` proves exact decimal | Excludes only NaN/Infinity | Validate source and precision separately |
| Every JSON system transmits numbers identically | Runtimes/parsers may round at different steps | Specify type and unit protocol |

## 20. Self-check

**Question 1.** Does `BigDecimal.valueOf(0.1)` equal `new BigDecimal("0.1")` under `equals`?  
**Answer:** Yes, in this case both have value 0.1 and scale 1.

**Question 2.** Is `new BigDecimal(0.1)` exact decimal 0.1?  
**Answer:** No. It stores the exact decimal expansion of the binary64 value near 0.1, which is longer than 0.1.

**Question 3.** Why does `BigDecimal.valueOf(0.1 + 0.2)` not produce 0.3?  
**Answer:** Because the `double` addition occurs first, yielding 0.30000000000000004. `valueOf` uses the canonical decimal representation of the already-computed result.

**Question 4.** If input is the string `"19.90"` and scale 2 must be preserved, what should you do?  
**Answer:** Use `new BigDecimal("19.90")` directly; do not parse through `double`.

**Question 5.** How does `BigDecimal.valueOf(9_007_199_254_740_993L)` differ from `BigDecimal.valueOf((double) 9_007_199_254_740_993L)`?  
**Answer:** The `long` overload preserves the exact 9_007_199_254_740_993; the path via `double` rounds down to 9_007_199_254_740_992.

**Question 6.** Does `BigDecimal.valueOf(Double.NaN)` succeed?  
**Answer:** No. `BigDecimal` has no NaN value; the method throws `NumberFormatException`.

**Question 7.** If a `double` underflows to 0 before conversion, can `valueOf` retrieve the very small positive number?  
**Answer:** No. The value passed in is already equal to 0.0.

**Question 8.** Do `BigDecimal.valueOf(-0.0)` and `BigDecimal.valueOf(+0.0)` preserve two different zero signs?  
**Answer:** No. They are equal under `equals`; `BigDecimal` does not represent signed zero separately.

**Question 9.** When can `new BigDecimal(d)` be more useful than `valueOf(d)`?  
**Answer:** When you need the **exact decimal expansion of the stored binary64 value**, such as error analysis or representation testing; not when trying to recover the source decimal.

**Question 10.** Does `BigDecimal.valueOf(2.675).setScale(2, HALF_UP)` always yield the same result as `new BigDecimal(2.675).setScale(2, HALF_UP)`?  
**Answer:** No. In this example, the first rounds 2.675 to 2.68, whereas the `double` constructor uses the binary64 value slightly less than 2.675, yielding 2.67.

**Question 11.** What does `BigDecimal.valueOf(12345L, 2)` produce?  
**Answer:** Exact decimal 123.45, because the input is a `long` integer and scale 2.

**Question 12.** Does `Double.isFinite(d)` guarantee that `BigDecimal.valueOf(d)` recovers the original decimal string?  
**Answer:** No. `isFinite` checks only that the number is not NaN/Infinity; precision or scale may already have been lost earlier.

## 21. Checklist when bringing `double` into a decimal system

Before choosing `BigDecimal.valueOf(double)`, check:

1. **What is the original data?** Decimal string, `long`, sensor, or a value computed in `double`?
2. **Must every source decimal digit be preserved?** If yes, parse directly from `String` or a decimal type.
3. **Must scale/trailing zeros be preserved?** `double` does not carry this information.
4. **Can the value exceed 53 bits of integer precision?** If yes, avoid passing through binary64.
5. **Have any `double` operations already been performed?** Errors may already have formed beforehand.
6. **Could it be NaN, ±Infinity, or underflowed to 0?** Handle before conversion if business logic disallows it.
7. **Must signed zero or NaN payload be preserved?** `BigDecimal` is not a format for storing all IEEE 754 bits.
8. **Which rounding rule is needed?** Specify timing, scale, and `RoundingMode`.
9. **Do any APIs/JSON/databases perform hidden type conversions?** Verify the entire path.
10. **Are there tests for boundary values and specific source data?** Test trailing zeros, long decimals, large integers, tiny/huge numbers, and parse failures.

**Conclusion:** `BigDecimal.valueOf(double)` is a tool to **convert an existing binary64 value into a decimal per `Double.toString`**. It is very useful when you accept the source's `double` type, yet **does not restore precision, scale, arithmetic results, or bit information lost earlier**. For exact decimal calculations per business data, use `BigDecimal` or integers in specified units **right from the source**.
