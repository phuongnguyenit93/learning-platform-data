# Relationship Between Interfaces and Public Methods of Object in Java

A variable of an interface type can still call the familiar public instance methods of java.lang.Object, even though the interface does not explicitly declare them. This rule belongs to Java's type checking; it does not mean that an interface inherits from the Object class.

## 1. Declared Type and Runtime Type Answer Two Different Questions

~~~java
interface Named {
    String name();
}

final class Person implements Named {
    private final String name;

    Person(String name) {
        this.name = name;
    }

    @Override
    public String name() {
        return name;
    }

    @Override
    public String toString() {
        return "Person(" + name + ")";
    }
}
~~~

With the types above, the following snippet is valid:

~~~java
Named person = new Person("Lan");
System.out.println(person.name());
System.out.println(person.toString());
System.out.println(person.equals(person));
System.out.println(person.hashCode());
System.out.println(person.getClass().getSimpleName());
~~~

Java considers two things:

1. **Compile time:** the declared type Named allows calling name() because the interface declares that method. Calls to toString(), equals(), hashCode(), and getClass() are also valid under the rule for public instance methods of Object.
2. **Runtime:** the actual object is a Person. If Person overrides an overridable instance method, the call runs Person's implementation. getClass() is final, so it returns the actual runtime class.

This is why the same object can be accessed through a Named or Object variable and still run Person.toString(). The declared type determines which methods can be called; dynamic dispatch selects the implementation for overridable instance methods.

An interface cannot use the syntax extends Object because an interface's extends clause only accepts other interfaces. For an interface with no direct superinterfaces, Java specifies the applicable public instance method signatures of Object as implicit abstract members, unless a compatible declaration already exists. Subinterfaces receive these members through interface inheritance rules.

## 2. Which Object Methods Can Be Called?

| Method | Callable through an interface variable? | Things to remember |
| --- | --- | --- |
| toString(), equals(Object), hashCode() | Yes | Behavior can be overridden by the implementing class; equals and hashCode must maintain a consistent contract |
| getClass() | Yes | Is final, returns the runtime class; cannot be overridden |
| wait(), wait(long), wait(long, int) | Yes, at the type level | May throw InterruptedException; must follow monitor rules |
| notify(), notifyAll() | Yes, at the type level | Must own the object's monitor when called |
| clone() | Not automatically | Object.clone() is protected, not a public method automatically exposed by an interface |

A call that is valid at compile time can still fail at runtime. For example, wait() or notify() outside an appropriate monitor-owning context can throw IllegalMonitorStateException. For wait(), the code must also handle InterruptedException. Type rules do not replace synchronization requirements.

Cloneable does not declare clone() either. If an interface wants to require a public copying API, it must declare an appropriate public method itself, and the implementing class must fulfill that contract; the lessons on clone cover this case in depth.

## 3. What This Rule Does Not Mean

An interface does not make every API of the runtime class available. If Person has a method internalDetail() that Named does not declare, the caller cannot call person.internalDetail() simply because the runtime object is a Person. The corresponding public methods of Object are a special case defined by the language.

Similarly, getClass() is useful for diagnostics or reflection, but it should not replace a business contract. Comparing task.getClass() with a specific class can make the code depend on an implementation, a proxy, or a runtime class generated by a lambda. If common behavior is needed, declare that method in the interface; if branching by subtype is needed, clearly define the scope and conditions.

## 4. Explicit Declarations and the Limitation of Default Methods

An interface can explicitly declare compatible abstract signatures:

~~~java
interface Identified {
    String id();
    boolean equals(Object other);
    int hashCode();
    String toString();
}
~~~

These declarations do not create an equals, hashCode, or toString algorithm. The implementing class can inherit the appropriate public implementation from Object or override it according to its own semantics.

An interface is not allowed to provide a default implementation that is override-equivalent to a non-private method of Object. Therefore, declaring default toString(), default equals(Object), or default hashCode() is a compile-time error. This limitation is analyzed in the next lesson; do not repeat it by assuming that an interface can “win” over Object through the default method mechanism.

## 5. Why Do Object Signatures Not Disqualify a Functional Interface?

When determining the single abstract method (SAM), Java does not count the public instance methods corresponding to Object as additional lambda obligations.

~~~java
@FunctionalInterface
interface Task {
    void run();
    boolean equals(Object other);
    String toString();
}

public class Main {
    public static void main(String[] args) {
        Task task = () -> System.out.println("Running");
        task.run();
    }
}
~~~

The program prints:

~~~text
Running
~~~

Task still has one functional method, run(). If an independent abstract method such as stop() is added, the interface is no longer a functional interface under the SAM rule.

## 6. How to Analyze a Call

When encountering reference.method(...) where reference has an interface type:

1. Check whether the method exists in the interface, a superinterface, or the group of Object signatures recognized by Java.
2. Check the parameter types, return type, and access permissions; do not infer that every API of the runtime class is visible.
3. Determine whether the method is overridable or final.
4. For an overridable instance method, trace the implementation of the runtime object.
5. For wait/notify, check both monitor rules and exception handling; a call that is valid at compile time does not guarantee that every runtime context is valid.

Self-check:
- Why does Named not need extends Object to call toString()? Because Java has a special rule for the applicable public instance methods of Object.
- Can protected clone() be called solely through a variable of an interface type? No.
- If the runtime class overrides toString(), which version does a call through the interface variable use? The runtime class's overridden version.
- Can getClass() be overridden? No, because this method is final.

Key takeaway: an interface defines the set of behaviors that calling code is allowed to use; the actual class provides implementations for overridable instance methods. Object's special rules do not turn an interface into a subclass of Object.
