# Records Implementing Interfaces Using Accessors or Additional Methods

## Objectives

In Java, a record can implement an interface just like a regular class. A useful feature is that an accessor automatically generated by Java from the record components can directly satisfy an interface method; when the signature does not match, the record can declare an additional method to fulfill that contract.

After this lesson, you will be able to identify which methods are satisfied by accessors, when you need to write a method yourself, and how to check the interface contract at compile time.

## 1. Records Can Implement Interfaces

A record is a kind of class designed to represent data. For example:

~~~java
record Person(String name, int age) {}
~~~

Java automatically creates public accessors named after the components: `name()` returns `String`, and `age()` returns `int`. These accessors do not use the `get` prefix like many traditional JavaBeans.

A record can declare one or more interfaces using the `implements` keyword:

~~~java
interface HasName {
    String name();
}

record Person(String name, int age) implements HasName {}
~~~

The `HasName` interface requires a public `name()` method with no parameters that returns `String`. The `name()` accessor generated by the record has that exact signature, so it satisfies the interface contract on its own. There is no need to rewrite the accessor in the record.

A record is still a `final` class and directly extends `java.lang.Record`; it cannot extend another arbitrary class. However, a record can implement multiple interfaces and provide the required methods for each interface.

## 2. When an Accessor Satisfies an Interface Method

An accessor can satisfy an abstract method of an interface when the signature is compatible. Check the following points:

- The method name must be the same.
- The parameter list must be the same. A component accessor takes no parameters.
- The return type must be compatible according to Java's overriding rules. For an auto-generated accessor, the return type is the component's type; in typical cases, the interface should be declared with that exact type.
- The implementing method must have public access. The accessor generated for a record is `public`, which matches an abstract method of an interface.

The method name is part of the contract. If an interface requires `getName()`, the `name()` accessor does not automatically satisfy it simply because both return the name. In that case, the record must explicitly provide `getName()`.

## 3. When You Need to Declare Additional Methods

An interface may require a behavior that does not correspond to any accessor. A record can declare a regular instance method to satisfy that requirement, as long as it complies with the signature and access level of the interface.

~~~java
interface HasDisplayName {
    String displayName();
}

record User(String firstName, String lastName) implements HasDisplayName {
    @Override
    public String displayName() {
        return firstName + " " + lastName;
    }
}
~~~

In this example, `firstName()` and `lastName()` are automatically generated accessors. They cannot satisfy `displayName()` because the method name and purpose are different. The record adds `displayName()` to combine the two components into a display name. The `@Override` annotation helps the compiler verify that the method is overriding or implementing an actual method in the parent contract.

If an interface requires `getName()`, a similar approach is to declare `public String getName()` in the record and return the `name` component. Java does not automatically rename an accessor from `name()` to `getName()`.

Interface `default` methods already have a body and can be inherited by the record without needing to be reimplemented. The record only needs to override a default method if it wants to change the behavior. Interface `static` methods are called through the interface and are not instance methods that a record needs to implement.

## 4. Complete Runnable Example

The example below combines both approaches: the `id()` accessor generated by the record fulfills the `HasId` contract, while the additional `description()` method fulfills the `Describable` contract. The `Describable` interface also has a default method to demonstrate using inherited behavior.

Save the entire code content into the file `Main.java`:

~~~java
interface HasId {
    String id();
}

interface Describable {
    String description();

    default boolean hasDescription() {
        return !description().isBlank();
    }
}

record Service(String id, String name, int port)
        implements HasId, Describable {

    @Override
    public String description() {
        return name + " listens on " + port;
    }
}

public class Main {
    public static void main(String[] args) {
        Service service = new Service("svc-1", "Catalog", 8080);

        HasId idView = service;
        Describable descriptionView = service;

        System.out.println(idView.id());
        System.out.println(descriptionView.description());
        System.out.println(descriptionView.hasDescription());
    }
}
~~~

Compile and run with JDK 17 or later:

~~~text
javac Main.java
java Main
~~~

Exact standard output:

~~~text
svc-1
Catalog listens on 8080
true
~~~

Output explanation:

1. `idView.id()` calls the `id()` accessor of the `Service` record. There is no need to redeclare this method in the record.
2. `descriptionView.description()` calls the `description()` method implemented by `Service` itself. The returned content is constructed from the two values `name` and `port`.
3. `descriptionView.hasDescription()` calls the `default` method of `Describable`. This method in turn calls `description()` on the same object and checks whether the result is empty.

The example also demonstrates polymorphism: a variable of an interface type can reference a record object. Through that variable, the program can only call the methods in the corresponding interface, but the implementation is executed on the `Service` object.

## 5. Common Errors

| Error | Why It Fails | How to Fix |
|---|---|---|
| Assuming `name()` satisfies `getName()` | The method names are different | Also declare `getName()` if the interface requires it |
| Omitting `public` when writing an implementing method | Interface methods require public access; access level cannot be reduced when implementing | Declare `public` |
| Wrong number or types of parameters | The method does not have the signature required by the interface | Compare the name, parameters, and return type against the interface |
| Incompatible return type | The method does not satisfy the overriding rules | Use a return type compatible with the contract |
| Forgetting to implement an abstract method | A record is a concrete class and cannot leave an abstract method unsatisfied | Use a matching accessor or declare the missing method |
| Trying to declare an arbitrary superclass | A record already directly extends `java.lang.Record` | Use `implements` to combine behavior through interfaces |

Signature errors are usually detected immediately at compile time. Therefore, when the compiler reports that a record does not implement an abstract method, compare the exact method name, parameter list, return type, and access level before changing the design.

## 6. Process for Choosing an Implementation Approach

1. Read the interface and list the abstract methods that the record must provide.
2. For each method, check whether any record component generates an accessor with the same signature.
3. If an accessor matches, let Java auto-generate the accessor and do not rewrite it unnecessarily.
4. If it does not match, declare a public method in the record with a compatible signature.
5. Check the `default` methods that can be inherited and override them only when there is a reason.
6. Compile the program, read any errors if present, then run it and compare with the expected output.

## Key Takeaways

Records implement interfaces according to Java's method contracts. An auto-generated accessor only satisfies methods with a matching signature; it does not automatically satisfy methods with a different name such as `getName()`, methods with parameters, or custom computed behavior. When an interface requires additional behavior, define that method in the record with the correct access level and signature.
