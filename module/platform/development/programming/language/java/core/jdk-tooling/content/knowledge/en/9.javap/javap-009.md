# Comparing Source with Bytecode Using javap

When Java source is compiled, javac translates statements, expressions, and declarations into bytecode inside a class file. Bytecode is the intermediate instruction format that the JVM loads, verifies, and executes. Using javap to read bytecode and metadata helps you compare a piece of source code with the instructions generated by the compiler.

This comparison is useful when debugging issues, understanding how the compiler handles a language construct, inspecting method calls, analyzing control-flow branches, or verifying an artifact before release. The output is not an exact decompilation of the source: many formatting details are lost, and the compiler may generate additional constructs that were not written directly in the source code.

## 1. How Do Source, Bytecode, and the JVM Relate?

The basic workflow:

1. A developer writes source code in a `.java` file.
2. `javac` parses syntax, checks types, and compiles the source.
3. The compiler produces a `.class` file containing bytecode and attributes.
4. The JVM loads the class file, verifies the bytecode, links references, and executes it.
5. At runtime, the JIT compiler may optimize hot code paths into machine code.

Source code describes intent at the Java language level. Bytecode represents operations at the JVM level, such as loading variables, reading fields, invoking methods, comparing values, branching, creating objects, and returning results.

Two optimization stages should be distinguished:

- `javac` translates source into bytecode and may perform certain compile-time transformations.
- The JIT compiler optimizes based on actual runtime behavior, such as inlining methods or eliminating unreachable branches.

Therefore, bytecode from `javap` is not the final machine code that the CPU will necessarily execute.

## 2. Preparing Source for Comparison

Create the project structure:

~~~text
project/
├── src/
│   └── com/
│       └── example/
│           └── TraceExample.java
└── out/
~~~

Contents of `src/com/example/TraceExample.java`:

~~~java
package com.example;

public class TraceExample {
    private static int adjust(int value) {
        if (value < 0) {
            return -value;
        }
        return value * 2;
    }

    public static void main(String[] args) {
        int input = args.length == 0 ? 4 : Integer.parseInt(args[0]);
        int result = adjust(input);
        System.out.println("result=" + result);
    }
}
~~~

Compile with JDK 17 or later and instruct the compiler to generate debug information:

~~~powershell
New-Item -ItemType Directory -Force -Path out | Out-Null
javac --release 17 -g -d out src/com/example/TraceExample.java
~~~

The `-g` option requests full debug information, including source file, line number, and local variable information. `--release 17` selects the syntax, bytecode, and Java Platform API of Java 17.

Run the application:

~~~powershell
java -cp out com.example.TraceExample
~~~

Output:

~~~text
result=8
~~~

With argument `-3`:

~~~powershell
java -cp out com.example.TraceExample -3
~~~

Output:

~~~text
result=3
~~~

This example includes an `if` branch, an arithmetic operation, a method call, and a string concatenation. Those constructs make it easy to observe the relationship between source code and JVM instructions.

## 3. javap Commands for Viewing Source Alongside Bytecode

`javap` reads a class file and displays declarations, descriptors, bytecode, or metadata depending on the options used.

View the class declaration:

~~~powershell
javap -classpath out com.example.TraceExample
~~~

View the bytecode of methods:

~~~powershell
javap -c -classpath out com.example.TraceExample
~~~

View bytecode together with source line information:

~~~powershell
javap -c -l -classpath out com.example.TraceExample
~~~

Include private members:

~~~powershell
javap -p -c -l -classpath out com.example.TraceExample
~~~

View detailed metadata:

~~~powershell
javap -v -p -classpath out com.example.TraceExample
~~~

Meaning of the main options:

| Option | Description |
|---|---|
| `-c` | Disassemble method bytecode |
| `-l` | Display line number table and local variable table if stored in the class |
| `-p` or `-private` | Display private fields and methods as well |
| `-s` | Display internal descriptors of fields and methods |
| `-v` or `-verbose` | Display constant pool, class-file version, flags, and attributes |
| `-classpath` or `-cp` | Specify where to find classes |
| `-sysinfo` | Display system information about the inspected class |

For source-comparison tasks, you typically start with `-c -l`; when deeper inspection is needed, add `-p`, `-s`, or `-v`.

## 4. Reading a Method's Bytecode

Run:

~~~powershell
javap -c -p -classpath out com.example.TraceExample
~~~

The `adjust` method section looks similar to:

~~~text
private static int adjust(int);
  Code:
     0: iload_0
     1: ifge          7
     4: iload_0
     5: ineg
     6: ireturn
     7: iload_0
     8: iconst_2
     9: imul
    10: ireturn
~~~

Compare with the source:

~~~java
if (value < 0) {
    return -value;
}
return value * 2;
~~~

| Bytecode | Meaning | Corresponding Source |
|---|---|---|
| `iload_0` | Push the int variable at local slot 0 onto the operand stack | Read `value` |
| `ifge 7` | If the value is greater than or equal to 0, jump to offset 7 | Check `value < 0` via the inverted branch |
| `iload_0` | Load `value` again | Use `value` in the negative branch |
| `ineg` | Negate the integer on the stack | Expression `-value` |
| `ireturn` | Return the int value | `return -value` |
| `iconst_2` | Push the constant 2 onto the operand stack | Constant `2` |
| `imul` | Multiply two ints on the stack | `value * 2` |
| `ireturn` | Return the int result | `return value * 2` |

The offset is the bytecode position within the method, measured in bytes. Specific offsets, constant-pool indices, and instructions may vary when the source or compiler changes. The example above illustrates typical bytecode; always inspect the output from your project's actual class file when verifying.

## 5. Understanding the Operand Stack and Local Variables

JVM bytecode primarily operates on two data areas within each frame:

- The local variable array stores parameters and local variables.
- The operand stack stores intermediate values used for computations and method invocations.

In `static int adjust(int value)`, the parameter `value` is in local slot 0. Because a static method has no `this` reference, slot 0 is used directly for the first parameter.

For an instance method, slot 0 typically holds `this`; subsequent parameters start at slot 1. `long` and `double` occupy two local variable slots in the JVM model; other types typically occupy one slot.

Some common instructions:

| Instruction | Function |
|---|---|
| `iload`, `iload_0` | Load an int from a local variable |
| `istore`, `istore_1` | Store an int into a local variable |
| `aload`, `aload_0` | Load a reference from a local variable |
| `astore` | Store a reference into a local variable |
| `iconst_0`, `bipush`, `sipush`, `ldc` | Push a constant onto the operand stack |
| `iadd`, `isub`, `imul`, `idiv` | Integer arithmetic operations |
| `getfield`, `putfield` | Read or write an instance field |
| `getstatic`, `putstatic` | Read or write a static field |
| `new`, `dup` | Create an object and duplicate the reference on the stack |
| `invokevirtual` | Invoke an instance method using virtual dispatch |
| `invokestatic` | Invoke a static method |
| `invokespecial` | Invoke a constructor or certain special calls |
| `invokeinterface` | Invoke a method through an interface |
| `invokedynamic` | Invoke behavior linked via a dynamic call site |
| `ireturn`, `areturn`, `return` | Return a value or exit a void method |

When reading a sequence of instructions, trace which values are pushed onto the stack, which values an instruction consumes, and how results are pushed back. This helps you understand the computation or method call rather than looking at individual instruction names in isolation.

## 6. Comparing Branches and Loops

Control-flow constructs in source code are typically represented using comparison and jump instructions.

### 6.1. if/else Statements

Source:

~~~java
if (score >= 50) {
    return "pass";
} else {
    return "fail";
}
~~~

The compiler typically generates a conditional branch such as `if_icmpge`, `iflt`, or `ifeq`, and then uses `goto` to jump to the appropriate branch. The jump direction may be inverted relative to the source condition because the compiler arranges blocks in a convenient order.

When comparing, do not assume `if` always becomes an instruction named like the keyword. Read the branch condition, target offset, and return instructions of each branch.

### 6.2. Loops

Source:

~~~java
int total = 0;
for (int i = 0; i < 3; i++) {
    total += i;
}
~~~

The compiler typically translates a loop into:

1. Initialize the counter and accumulator variables in local slots.
2. Compare the counter against the bound.
3. Jump out of the loop when the termination condition is met.
4. Execute the loop body and update the variables.
5. Use a jump instruction to return to the check step.

In bytecode, you commonly see branches such as `if_icmpge`, `if_icmplt`, and `goto`. The source uses `for`, but bytecode has no instruction named `for`.

### 6.3. Switch

Depending on the expression and case labels, the compiler may emit `tableswitch` or `lookupswitch`. `tableswitch` suits contiguous or relatively dense integer values; `lookupswitch` represents key/target pairs for sparser key sets.

Inspect the bytecode to see which form the compiler chose:

~~~powershell
javap -c -classpath out com.example.SwitchExample
~~~

Do not predict the instruction solely from the number of cases; key layout and the compiler determine which form is generated.

## 7. Comparing Method Calls and Descriptors

When source code calls a method, bytecode must specify how the JVM locates and invokes that method. Common instructions include `invokevirtual`, `invokestatic`, `invokespecial`, and `invokeinterface`.

Example:

~~~java
int result = adjust(input);
~~~

In `main`, the call to the static method `adjust` is typically represented by `invokestatic`. Bytecode may also reference a descriptor describing parameter types and the return type.

Use `javap -s`:

~~~powershell
javap -s -p -classpath out com.example.TraceExample
~~~

Some basic descriptors:

| Descriptor | Meaning |
|---|---|
| `()I` | Takes no parameters, returns int |
| `(I)I` | Takes one int, returns int |
| `([Ljava/lang/String;)V` | Takes a String array, returns void |
| `(Ljava/lang/String;)V` | Takes a String, returns void |
| `()Ljava/lang/String;` | Takes no parameters, returns String |

A descriptor is a JVM-level type representation. It does not include source parameter names, and generic types are generally subject to type erasure in standard method descriptors. Generic signatures may be stored separately in the `Signature` attribute.

## 8. LineNumberTable: Mapping Bytecode to Source Lines

So that debuggers and analysis tools can map instructions back to source lines, a class file may contain a `LineNumberTable`.

View it with:

~~~powershell
javap -l -classpath out com.example.TraceExample
~~~

The output may include:

~~~text
LineNumberTable:
  line 5: 0
  line 6: 4
  line 8: 7
~~~

Each entry maps a bytecode offset to a source line number. In the example, bytecode starting at offset 0 corresponds to one source line; later offsets may map to other lines.

The line table does not record individual characters or expressions in the source. Multiple instructions may map to the same line, and a single source line may produce multiple bytecode segments. Therefore, this is a debugging mapping, not a one-to-one map between Java statements and JVM instructions.

If a class has no line number information, `javap -l` cannot reconstruct line numbers from the bytecode.

## 9. LocalVariableTable and Debug Information

`LocalVariableTable` can store local variable names, descriptors, slots, and the bytecode range over which each variable is in scope.

For example, when compiling with:

~~~powershell
javac -g:source,lines,vars -d out src/com/example/TraceExample.java
~~~

Then inspect:

~~~powershell
javap -l -p -classpath out com.example.TraceExample
~~~

You may see variable names such as `args`, `input`, `result`, and `value` along with their slots and offset ranges, if the compiler recorded the corresponding entries.

javac debug options:

- `-g`: generate all debug information.
- `-g:none`: generate no debug information.
- `-g:source,lines,vars`: explicitly select source file, line number, and local variable information.

By default, the compiler may retain source file and line numbers without necessarily retaining local variable names. If a debugger needs to display local variable names, verify that the build generated `LocalVariableTable`.

The `-parameters` option serves a different purpose: it stores method parameter names in the `MethodParameters` attribute so reflection can read parameter names. It does not replace `LocalVariableTable`.

## 10. Identifying Compiler-Generated Constructs

Source and bytecode can differ because the compiler generates additional methods or attributes required at runtime.

| Source Construct | What May Appear in the Class File |
|---|---|
| Class without an explicit constructor | The compiler generates a default constructor if the class needs one |
| Generic inheritance with method override | A bridge method may be present to preserve dispatch after type erasure |
| Lambda expression | Typically uses `invokedynamic` with `BootstrapMethods` |
| String concatenation | Newer JDKs typically use `invokedynamic` and a bootstrap method for string concatenation |
| Enum | May have compiler-generated methods and fields |
| Inner/nested class | Has metadata such as `InnerClasses`, nest attributes, or synthetic accessors depending on the version |
| Record | Has a `Record` attribute along with automatically generated members |
| Sealed class | Has a `PermittedSubclasses` attribute |
| Try/catch/finally | Has an exception table and corresponding bytecode blocks |

Use verbose output to view attributes:

~~~powershell
javap -v -p -classpath out com.example.TraceExample
~~~

Look for `BootstrapMethods` when analyzing lambdas or string concatenation; look for `Synthetic`, `Bridge`, `Record`, `PermittedSubclasses`, or `Exception table` depending on the source construct.

Not all compiler-generated methods have the same names or forms across all Java versions. Inspect the actual artifact rather than relying on a fixed bytecode template.

## 11. Exception Table and try/catch/finally

Source:

~~~java
try {
    work();
} catch (IllegalArgumentException ex) {
    recover();
}
~~~

The compiler represents protected regions and handlers in the exception table of the `Code` attribute. The exception table specifies the protected bytecode range, the handler location, and the exception type to catch.

Use:

~~~powershell
javap -c -v -p -classpath out com.example.ExceptionExample
~~~

In the output, locate the `Exception table` section. It helps identify which instructions lie inside the `try` region, at which offset the handler begins, and which exception type is handled.

`finally` may be implemented via additional bytecode blocks or appropriate cleanup mechanisms. For try-with-resources, the compiler also generates logic to call `close()` and handle suppressed exceptions. As a result, short source code can produce significantly longer bytecode.

## 12. Inspecting Classes in a JAR or Module

If a class is inside a JAR, you can include the JAR on javap's classpath:

~~~powershell
javap -c -l -p -classpath app.jar com.example.TraceExample
~~~

If you also need to inspect dependent libraries, use a semicolon on Windows:

~~~powershell
javap -c -classpath "app.jar;lib/*" com.example.TraceExample
~~~

On Linux/macOS, use a colon:

~~~bash
javap -c -classpath "app.jar:lib/*" com.example.TraceExample
~~~

To verify that the class is in the JAR:

~~~powershell
jar --list --file app.jar
~~~

For modules, you can specify the module path and module:

~~~powershell
javap --module-path mods --module com.example.app com.example.app.Main
~~~

`javap` reads the class file from the specified artifact. Make sure you are inspecting the exact JAR or output directory that the application actually runs; if the classpath contains multiple versions of the same class name, results from another artifact can be misleading.

## 13. Limitations When Comparing Source with Bytecode

- Bytecode does not preserve comments, indentation, or original source naming if the corresponding metadata is not stored.
- `LineNumberTable` maps offsets to lines, without pinpointing individual expressions on that line.
- Local variable names can only be viewed if the compiler generated `LocalVariableTable`.
- The compiler may generate constructors, bridge methods, synthetic members, and metadata that do not appear directly in the source.
- Lambdas, string concatenation, switch, and try-with-resources may be represented by multiple instructions and attributes.
- Bytecode does not show all JIT optimizations that occur at runtime.
- Constant-pool indices, offsets, and instruction sequences can change across compilers or JDK versions.

If you need to reconstruct source from a class file, a decompiler can produce approximate Java code, but variable names, generics, control structures, and expressions may differ from the original source. Do not use decompiler output as proof that the original source had the exact same contents.

## 14. Practical Comparison Workflow

When investigating a specific method:

1. Identify the source revision and the artifact built from that revision.
2. Compile with debug information if line or variable mappings are needed.
3. Use `javap -p -c -l` to read declarations, bytecode, and the line table.
4. Select the method to inspect and identify its descriptor.
5. Trace local slots, the operand stack, branch targets, and method invocations.
6. Use `javap -v` to view the constant pool, attributes, exception table, and bootstrap methods when needed.
7. Compare line numbers with the source, keeping in mind that the mapping is not one-to-one.
8. Verify the class file and dependencies in the exact deployed JAR/module.
9. Run tests on the target runtime to confirm actual behavior.

You do not need to analyze the entire class file if you only have one specific question. Use `-c` to understand instructions, `-l` to map source lines, `-s` to read descriptors, and `-v` when deeper metadata is needed.

## 15. Pre-Conclusion Checklist

- [ ] Inspecting the exact class file used by the application.
- [ ] Identified the source revision and the JDK/compiler that built the artifact.
- [ ] Compiled with debug information if line or local variable mapping is needed.
- [ ] Used `javap -c` to inspect the relevant method's bytecode.
- [ ] Used `javap -l` to compare the LineNumberTable.
- [ ] Checked descriptors and members with `-s` or `-p` when needed.
- [ ] Inspected `-v` if attributes, exception table, or bootstrap methods are needed.
- [ ] Distinguished javac-generated bytecode from runtime JIT optimizations.
- [ ] Confirmed behavior with tests on the actual runtime.

Comparing source with bytecode gives you a direct view of how javac represents a program at the JVM level. Combine `javap -c` to read instructions, `-l` to connect offsets to source lines, and `-v` to inspect metadata. Always verify the right artifact and remember that the source-to-bytecode mapping can be many-to-many, not a line-by-line translation.
