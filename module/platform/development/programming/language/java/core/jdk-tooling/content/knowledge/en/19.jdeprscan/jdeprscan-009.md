# Integrating jdeprscan into CI

`jdeprscan` is a static analysis tool bundled with the JDK that scans bytecode in a class directory or JAR to find uses of deprecated Java SE APIs. Integrating this tool into CI helps detect APIs eligible for removal in future JDK releases early, even when source code is not recompiled frequently, warnings have been suppressed, or the application depends on libraries distributed only in binary form.

An effective pipeline typically combines two layers of checks:

- `javac -Xlint:deprecation -Xlint:removal` detects deprecated API usage in source code compiled during the current build.
- `jdeprscan` inspects the generated bytecode, including classes/JARs that may not have been recompiled from source in that pipeline.

## 1. Why run jdeprscan in CI?

Deprecation is a signal advising users to migrate to a replacement API. Ordinarily deprecated APIs may remain available for a long time; APIs marked `forRemoval=true` are already eligible to be removed in a future release.

If an application continues referencing such an API after it is removed, the program may fail to link or run on a newer JDK. Detecting these usages before upgrading the JDK gives the development team time to replace the API and test thoroughly.

`jdeprscan` is especially useful in the following scenarios:

- Certain modules or binary libraries are not recompiled on every JDK upgrade.
- Source code uses `@SuppressWarnings("deprecation")` or `@SuppressWarnings("removal")`.
- The application consumes JARs provided by other teams.
- The team wants to verify the actual artifact to be released, rather than only looking at current source code.
- The team is preparing to upgrade from one JDK version to a newer one.

### 1.1. What does jdeprscan check?

The tool reads bytecode to find references to deprecated APIs defined by Java SE. It can accept the following inputs:

- A directory containing a package/class tree.
- A JAR file.
- A `.class` file.
- A fully qualified class name, for example `java.lang.Thread`.
- A nested class name using `$`, for example `java.lang.Thread$State`.

`jdeprscan` does not scan source code and does not report deprecated APIs defined by third-party libraries. If you need to check deprecated APIs from frameworks or internal libraries, supplement it with compiler warnings, static analysis tools, or project-specific rules.

## 2. Distinguishing compiler warnings and bytecode scans

The two mechanisms complement each other:

| Mechanism | Input | Detects | Limitations |
|---|---|---|---|
| `javac -Xlint:deprecation` | Source compiled during the build | Ordinarily deprecated APIs | Does not check binary JARs that are not recompiled |
| `javac -Xlint:removal` | Source compiled during the build | APIs deprecated for removal | Applies only to source currently being compiled |
| `jdeprscan` | Class files, class directories, or JARs | Bytecode references to deprecated Java SE APIs | Does not report deprecated APIs specific to third-party libraries |

Both compiler warning types can be enabled together:

~~~bash
javac -Xlint:deprecation -Xlint:removal -d out src/com/example/*.java
~~~

In JDK 21, the `removal` warning is enabled by default; specifying the option explicitly keeps the build policy readable and consistent. If the project is ready to block all warnings, you can add `-Werror`:

~~~bash
javac -Xlint:deprecation -Xlint:removal -Werror -d out src/com/example/*.java
~~~

`-Werror` causes the compiler to fail with an error when any warning is emitted. Enable it only after the team has resolved existing warnings or established a baseline.

Some suppressed code still generates bytecode that references deprecated APIs. This is why `jdeprscan` should be run after the compile/package step, even when the compiler emits no warnings.

## 3. Choosing the JDK and release to scan

Use the `jdeprscan` binary from the JDK pinned by the pipeline. Check the version and supported releases of the tool:

~~~bash
jdeprscan --version
jdeprscan --help
~~~

The `--release` option selects the Java SE API set used to determine deprecation. For example, when evaluating an artifact for Java SE 21:

~~~bash
jdeprscan --release 21 target/my-app.jar
~~~

Choose the release based on the verification goal:

- Checking an application running on Java 21: use `--release 21`.
- Preparing to upgrade an application to Java 21: scan against the Java SE 21 API set to surface deprecations relevant to the upgrade target.
- Supporting multiple runtime targets: run separate scans for each release supported by the pipeline's JDK.

The list of valid releases varies by JDK version. Check `jdeprscan --help` on the CI toolchain itself; do not assume every JDK supports the same range of releases.

## 4. Prioritizing APIs deprecated for removal

Use `--for-removal` to report only APIs marked as eligible for removal in a future release:

~~~bash
jdeprscan --release 21 --for-removal target/my-app.jar
~~~

This is a high-priority CI check because these references risk making the application incompatible with future JDKs. This option cannot be combined with releases 6, 7, or 8.

You can combine two passes:

~~~bash
# All deprecated Java SE APIs
jdeprscan --release 21 target/my-app.jar

# Only APIs deprecated for removal
jdeprscan --release 21 --for-removal target/my-app.jar
~~~

The first pass helps the team track overall deprecation debt. The second pass can serve as a stricter quality gate.

To list deprecated APIs for a release without scanning an artifact:

~~~bash
jdeprscan --release 21 --list
~~~

To list only APIs deprecated for removal:

~~~bash
jdeprscan --release 21 --list --for-removal
~~~

When using `--list`, do not pass a JAR, directory, or class to scan. `--list` only prints the API list; it does not perform a scan.

## 5. Including artifacts and dependencies in the scan

Scan the artifact after a successful build:

~~~text
Checkout source
      |
      v
Set up pinned JDK
      |
      v
Compile + run tests
      |
      v
Package JAR / class directory
      |
      v
Run jdeprscan
      |
      v
Save report + apply CI policy
      |
      v
Publish artifact
~~~

Example scanning a JAR:

~~~bash
jdeprscan --release 21 target/my-app.jar
~~~

Or scanning a class directory:

~~~bash
jdeprscan --release 21 target/classes
~~~

### 5.1. Providing the class path when needed

`jdeprscan` needs to resolve the classes that the scanned artifact depends on. Use `--class-path` to supply dependency directories or JARs:

~~~bash
jdeprscan \
  --release 21 \
  --class-path "target/classes:lib/a.jar:lib/b.jar" \
  target/my-app.jar
~~~

On Linux/macOS, class path entries are separated by `:`. On Windows, use `;`:

~~~powershell
jdeprscan --release 21 --class-path "target\classes;lib\a.jar;lib\b.jar" target\my-app.jar
~~~

If the tool cannot find a dependency class, an error message like the following may appear:

~~~text
error: cannot find class ...
~~~

Add the missing dependency to the class path and re-scan. Do not ignore this error or treat the scan as successful, because results with missing dependencies may be incomplete.

Note: `--class-path` helps resolve dependencies during analysis; it does not cause `jdeprscan` to automatically scan the contents of every JAR on the class path. If you want to inspect the bytecode of a binary library as well, pass that JAR itself as a separate scan input.

## 6. Understanding jdeprscan output

Example output:

~~~text
Jar file app.jar:
class DeprecatedApis uses deprecated method java/util/Date::getYear()I
class DeprecatedApis uses deprecated method java/lang/Thread::stop()V (forRemoval=true)
~~~

How to read it:

- `Jar file app.jar:` indicates the artifact being processed.
- `DeprecatedApis` is the class containing the reference to the deprecated API.
- `java/util/Date::getYear()I` identifies the class and method being used.
- `java/lang/Thread::stop()V` is the `stop()` method taking no parameters and returning `void`.
- `(forRemoval=true)` indicates that the API is marked as eligible for removal.

Common symbols in bytecode descriptors:

| Symbol | Meaning |
|---|---|
| `I` | `int` |
| `J` | `long` |
| `D` | `double` |
| `V` | `void` |
| `L...;` | Reference type |
| `<init>` | Constructor |

You can add `--verbose` to see more detailed processing information:

~~~bash
jdeprscan --verbose --release 21 target/my-app.jar
~~~

### 6.1. Exit codes do not replace reading the output

Do not assume that the CLI will return a non-zero exit code simply because deprecated APIs were found. In testing on JDK 24.0.2, a scan found `Date.getYear()` and `Thread.stop()`, yet the command still exited with code 0.

Therefore, CI needs an explicit policy:

- Run the tool and save stdout/stderr as a report.
- Treat tool execution errors or dependency resolution errors as build failures.
- Inspect the report for `uses deprecated` lines.
- Choose how to handle findings: fail immediately, compare against a baseline, or warn only during an initial rollout phase.

The CLI has no `--fail-on-warning` option equivalent to the compiler. If a hard gate is required, the pipeline wrapper must turn findings into a failure status.

## 7. Complete Java example for testing in CI

This example intentionally references one ordinarily deprecated API and one API deprecated for removal. The methods containing the references are only compiled and scanned; the program does not invoke them at runtime.

File `src/DeprecatedApiFixture.java`:

~~~java
import java.util.Date;

public final class DeprecatedApiFixture {
    public static void main(String[] args) {
        System.out.println("Deprecation scan fixture ready");
    }

    static int ordinaryDeprecatedApi() {
        return new Date().getYear();
    }

    static void deprecatedForRemoval(Thread thread) {
        thread.stop();
    }
}
~~~

Compile and package:

~~~bash
mkdir -p out

javac -Xlint:deprecation -Xlint:removal -d out \
  src/DeprecatedApiFixture.java

jar --create --file app.jar -C out .
~~~

Run the program:

~~~bash
java -cp app.jar DeprecatedApiFixture
~~~

Exact stdout:

~~~text
Deprecation scan fixture ready
~~~

Scan all deprecated APIs:

~~~bash
jdeprscan --release 21 app.jar
~~~

The output contains references corresponding to `Date.getYear()` and `Thread.stop()`. When scanning only for removal APIs:

~~~bash
jdeprscan --release 21 --for-removal app.jar
~~~

The output contains only the reference to `Thread.stop()`:

~~~text
Jar file app.jar:
class DeprecatedApiFixture uses deprecated method java/lang/Thread::stop()V (forRemoval=true)
~~~

This is a fixture for testing pipeline behavior. In real applications, replace deprecated APIs with recommended alternatives and avoid calling dangerous methods in fixtures.

## 8. Hard gate example in GitHub Actions

The example below assumes Maven produces `target/my-app.jar`, the runner is Ubuntu, and the project does not yet have a deprecation baseline. Replace the JAR name with your project's actual artifact.

~~~yaml
name: Java deprecation scan

on:
  pull_request:
  push:
    branches: [main]

jobs:
  build-and-scan:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven

      - name: Build and test
        run: ./mvnw -B verify

      - name: Scan deprecated Java SE APIs
        shell: bash
        run: |
          set -euo pipefail

          JAR="target/my-app.jar"
          REPORT="target/reports/jdeprscan.txt"

          mkdir -p target/reports

          if ! jdeprscan --release 21 "$JAR" > "$REPORT" 2>&1; then
            cat "$REPORT"
            echo "jdeprscan could not complete"
            exit 2
          fi

          cat "$REPORT"

          if grep -Eq ' uses deprecated |^error:' "$REPORT"; then
            echo "Deprecated Java SE API usage found"
            exit 1
          fi
~~~

Key parts:

- `setup-java` pins JDK 21 so building and scanning use the same toolchain.
- `mvnw verify` builds the artifact after running tests.
- The report is saved to `target/reports/jdeprscan.txt` so it can be uploaded as a CI artifact.
- Tool execution or dependency resolution errors fail the job.
- `grep` turns finding lines into a hard failure because the scanner may return exit code 0 even when deprecated APIs are found.

The template above uses Bash for a Linux runner. For a Windows runner, use PowerShell or a dedicated script; do not use Unix-style class path separators.

### 8.1. Adding a class path for dependencies

If the artifact needs dependencies to resolve classes, pass the list of JARs resolved by the build system:

~~~bash
jdeprscan \
  --release 21 \
  --class-path "target/classes:lib/a.jar:lib/b.jar" \
  target/my-app.jar
~~~

For Maven or Gradle, generate the class path from the build's dependency configuration rather than maintaining a manual JAR list that can drift from runtime.

### 8.2. Scanning multiple artifacts in a multi-module build

Each module that publishes its own JAR can be scanned individually:

~~~bash
jdeprscan --release 21 module-a/target/module-a.jar
jdeprscan --release 21 module-b/target/module-b.jar
jdeprscan --release 21 module-c/target/module-c.jar
~~~

Save separate reports per module or aggregate the output before applying policy. Scanning one module does not mean that other modules' JARs or third-party dependencies have been scanned.

## 9. Managing a baseline to avoid blocking the whole team immediately

A long-lived codebase may already contain many deprecation findings. Blocking all of them from day one can make CI impractical to adopt.

You can roll it out in phases:

1. Run a scan and save the report as the initial baseline.
2. Review the findings and categorize them by module and priority.
3. Block any new findings compared to the baseline.
4. Create tickets and deadlines for addressing legacy findings.
5. Remove baseline entries as APIs are replaced.
6. Tighten enforcement, such as disallowing any `forRemoval=true` APIs.

The baseline should be version-controlled alongside source code and tied to the release/JDK target. When bumping `--release` or changing the scan JDK, generate a newly reviewed baseline because the set of deprecated APIs may change.

Do not compare only the total warning count. An old finding could disappear while a dangerous new one is introduced; compare normalized lines by class and invoked API instead.

## 10. Integrating with Maven and Gradle

### 10.1. Maven

The simplest approach is to invoke `jdeprscan` after `mvn verify` produces the JAR:

~~~bash
./mvnw -B verify
jdeprscan --release 21 target/my-app.jar
~~~

Apache provides the Maven JDeprScan Plugin with the `jdeprscan:jdeprscan` goal for scanning main classes and `jdeprscan:test-jdeprscan` for scanning test classes. The plugin supports `failOnWarning`, `release`, and `forRemoval` parameters; the plugin documentation states that `failOnWarning` defaults to `true`.

Note that the plugin is marked by Apache as an alpha release. Verify its stability, version, and compatibility before using it as an official release gate. If you prefer not to add an alpha plugin to the build, invoking the JDK executable directly in CI is more straightforward.

### 10.2. Gradle

After building the JAR:

~~~bash
./gradlew clean test jar
jdeprscan --release 21 build/libs/my-app-1.0.jar
~~~

The JAR name depends on `rootProject.name`, the version, and the project's archive configuration. In real pipelines, obtain the path from the `jar` task output instead of hard-coding the artifact name if the project version changes frequently.

You can place the scan command in a shared repository script and invoke that script from GitHub Actions, Jenkins, GitLab CI, or Azure Pipelines.

## 11. Recommended CI policy

A balanced policy can be divided into levels:

| Level | Check | CI behavior |
|---|---|---|
| Required | No scan errors, no missing dependencies, no new findings | Build must pass |
| High priority | No `forRemoval=true` APIs | Block release or require exception review |
| Monitor | Ordinarily deprecated APIs remaining in baseline | Save report and track replacement plan |
| Extended | Deprecated APIs from third-party libraries | Use compiler warnings or dedicated dependency checks |

Not every deprecated API needs to be treated as an immediate production incident. However, `forRemoval=true` APIs should be addressed sooner because they can become compatibility failures on a JDK upgrade.

## 12. Common integration issues

| Symptom | Cause | Resolution |
|---|---|---|
| Scan cannot find a class | Class path is missing a dependency | Add all required dependencies to `--class-path` |
| CI reports pass despite deprecated APIs in report | Checking only `jdeprscan` exit code | Parse the report or use a plugin with `failOnWarning` |
| Local and CI scans produce different results | Different JDK/release used | Pin the JDK and set `--release` explicitly |
| Deprecated APIs from external libraries not shown | `jdeprscan` only recognizes deprecated APIs defined by Java SE | Supplement with compiler warnings or appropriate library tools |
| API in source not showing up | Source not compiled or scanned artifact is not the latest build | Ensure the build succeeds and scan the right JAR |
| App scanned but issues in dependency JARs not shown | Class path only resolves types, does not scan dependency JARs automatically | Pass each JAR to be checked as its own scan input |
| `--for-removal` fails with an older release | Releases 6, 7, or 8 are incompatible with this option | Choose a supported release and check `jdeprscan --help` |
| Legacy findings fail CI too often | No baseline or transition policy in place | Save a reviewed baseline and block new findings first |
| Report is empty because artifact was not built properly | Wrong path or wrong module scanned | Verify artifact path, module list, and build output |

## 13. Checklist before enabling the CI gate

- [ ] JDK toolchain is explicitly pinned.
- [ ] Build and tests run before the scan step.
- [ ] `jdeprscan` receives the latest JAR or class directory.
- [ ] `--release` matches the runtime/migration target.
- [ ] `--class-path` includes all dependencies needed for resolution.
- [ ] `cannot find class` errors are treated as scan failures.
- [ ] Reports are saved for team review.
- [ ] CI enforces a finding policy rather than relying solely on exit code.
- [ ] `forRemoval=true` APIs have high remediation priority.
- [ ] All relevant JARs in a multi-module build are included in the scan.
- [ ] Third-party deprecations are handled by an appropriate check mechanism.
- [ ] Baseline is reviewed and updated when upgrading the target JDK.

## 14. Key takeaways

`jdeprscan` is a bytecode verification step that belongs after compile/package in CI. It detects references to deprecated APIs defined by Java SE, making it especially valuable for binary dependencies, code with suppressed warnings, and JDK upgrade planning.

Use `--release` to select the target API set, `--for-removal` to focus on APIs eligible for removal, and `--class-path` to resolve dependencies. Combine it with `javac -Xlint:deprecation -Xlint:removal`, save reports, and define clear policies to turn findings into warnings or build failures. When you need to block new issues while maintaining a legacy codebase, manage the baseline per API rather than merely counting total warnings.
