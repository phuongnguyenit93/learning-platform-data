# Lệnh jps và jcmd: tìm tiến trình Java và chẩn đoán JVM

## 1. Tổng quan

`jps` và `jcmd` là hai công cụ dòng lệnh đi kèm JDK, thường được dùng liên tiếp khi cần kiểm tra một ứng dụng Java đang chạy.

- `jps` (Java Virtual Machine Process Status Tool) liệt kê các JVM HotSpot được công cụ nhận diện trên máy đích. Nó giúp tìm process ID, tên class chính hoặc JAR và một số tham số khởi chạy.
- `jcmd` gửi diagnostic command đến một JVM đang chạy. Sau khi xác định đúng tiến trình, bạn có thể hỏi phiên bản JVM, command line, VM flags, heap, thread, native memory hoặc ghi Java Flight Recorder (JFR).

Quy trình thông dụng là dùng `jps` để tìm JVM, sau đó dùng PID tìm được với `jcmd` để xem thông tin cụ thể. `jps` chủ yếu phục vụ khám phá tiến trình; `jcmd` thực hiện chẩn đoán.

Cả hai đều là công cụ JDK. Nếu lệnh không được nhận diện, kiểm tra JDK đang được cài và thư mục `bin` của JDK có trong `PATH` hay chưa.

## 2. Phân biệt jps và jcmd

| Tiêu chí | `jps` | `jcmd` |
|---|---|---|
| Mục đích | Liệt kê JVM được nhận diện | Gửi lệnh chẩn đoán đến JVM |
| Thông tin chính | LVMID/PID, class hoặc JAR, tùy chọn hiển thị arguments | Phiên bản, VM flags, heap, thread, JFR và các diagnostic command khác |
| Cách chọn tiến trình | Tùy chọn và host identifier | PID hoặc tên main class |
| Xem danh sách lệnh JVM | Không | Có, dùng `jcmd <pid> help` |
| Chẩn đoán heap/thread | Không trực tiếp | Có |
| Máy đích | Local; có thể truy vấn host từ xa qua `jstatd` | Phải chạy trên cùng máy với JVM đích |
| Lưu ý | Công cụ experimental, unsupported; output có thể thay đổi | Command và impact phụ thuộc JVM đích |

`jps` liệt kê các instrumented HotSpot JVM mà người chạy có quyền nhìn thấy. Nó không đảm bảo liệt kê mọi tiến trình Java trên máy. Một ứng dụng khởi chạy bằng custom launcher có thể không hiện tên class/JAR hoặc arguments như mong đợi.

`jcmd -l` cũng liệt kê JVM cục bộ, kèm main class và command-line arguments. Theo tài liệu JDK 24, danh sách này không bao gồm JVM chạy trong một Docker process riêng. `jcmd` còn có thể gửi diagnostic command, trong khi `jps` không làm việc đó.

Không nên xem hai danh sách là một bản kê đầy đủ, ổn định cho mọi môi trường. Kết quả phụ thuộc quyền truy cập, cách JVM được khởi chạy, namespace và phiên bản công cụ.

## 3. Dùng jps để tìm JVM

Cú pháp cơ bản:

~~~bash
jps
~~~

Liệt kê JVM được nhận diện trên máy hiện tại. Ví dụ:

~~~text
24816 DiagnosticsTarget
39120 jps
~~~

Số đầu dòng là local JVM identifier (LVMID). Với HotSpot, giá trị này thường trùng với operating-system PID, nhưng tài liệu không đảm bảo chúng luôn giống nhau trong mọi triển khai. Hãy xác nhận đúng tiến trình trước khi dùng ID đó để gửi lệnh chẩn đoán.

Xem trợ giúp:

~~~bash
jps -help
~~~

Chỉ in identifier:

~~~bash
jps -q
~~~

Xem tên class đầy đủ hoặc đường dẫn JAR:

~~~bash
jps -l
~~~

Xem arguments truyền vào method main:

~~~bash
jps -m
~~~

Xem arguments truyền cho JVM:

~~~bash
jps -v
~~~

Có thể kết hợp các tùy chọn:

~~~bash
jps -lmv
~~~

Ví dụ output khi ứng dụng được khởi chạy bằng class `demo.DiagnosticsTarget`, có hai main arguments và một số VM arguments:

~~~text
24816 demo.DiagnosticsTarget alpha beta -Xms32m -Xmx128m -Dapp.mode=diagnostic
~~~

Định dạng và thứ tự các token có thể khác theo phiên bản, launcher và hệ điều hành. Arguments chứa khoảng trắng cũng khiến việc phân tích output theo cột trở nên không đáng tin cậy.

`-m` và `-v` có ý nghĩa khác nhau:

- `-m` hiển thị arguments của chương trình Java, tức các giá trị sau tên main class hoặc JAR.
- `-v` hiển thị arguments dùng để khởi động JVM, chẳng hạn `-Xmx`, `-Dproperty=value` và các VM options.

Tùy chọn `-q` hữu ích khi chỉ cần danh sách identifier. Với `-V`, hãy kiểm tra tài liệu và hành vi của đúng bản JDK đang dùng; `jps` là công cụ experimental và unsupported nên không nên phụ thuộc vào tùy chọn ít dùng này trong script.

## 4. Dùng jcmd để liệt kê và chọn tiến trình

Liệt kê JVM cục bộ:

~~~bash
jcmd -l
~~~

Không truyền đối số cũng tương đương:

~~~bash
jcmd
~~~

Ví dụ:

~~~text
24816 demo.DiagnosticsTarget alpha beta
39120 jdk.jcmd/sun.tools.jcmd.JCmd -l
~~~

`jcmd -l` cho thấy PID, main class và arguments dùng để khởi chạy. Chính tiến trình `jcmd` có thể xuất hiện trong danh sách vì nó cũng là một Java process.

Cú pháp gửi lệnh:

~~~bash
jcmd <pid> <command> [arguments]
~~~

Ví dụ:

~~~bash
jcmd 24816 VM.version
~~~

Có thể dùng tên main class thay PID:

~~~bash
jcmd demo.DiagnosticsTarget VM.version
~~~

Khi dùng tên class, công cụ gửi command đến tất cả tiến trình khớp tên main class đó. Nếu có nhiều instance cùng class, dùng PID cụ thể để tránh tác động nhầm tiến trình.

PID `0` có nghĩa gửi command đến tất cả Java process mà công cụ có thể tiếp cận. Không dùng `0` trong lệnh vận hành thông thường nếu bạn chỉ muốn chẩn đoán một ứng dụng.

## 5. Khám phá command mà JVM hỗ trợ

Danh sách diagnostic command phụ thuộc phiên bản JDK, loại JVM và cấu hình tiến trình. Hãy hỏi trực tiếp JVM đích:

~~~bash
jcmd 24816 help
~~~

Xem cú pháp của một command:

~~~bash
jcmd 24816 help Thread.print
jcmd 24816 help GC.heap_dump
jcmd 24816 help JFR.start
~~~

Kết quả help cung cấp mô tả, cú pháp, options, arguments và mức impact nếu command có công bố mức này.

Một số command thường gặp:

| Command | Mục đích |
|---|---|
| `VM.version` | Xem phiên bản JVM và JDK |
| `VM.command_line` | Xem command line dùng để khởi chạy JVM |
| `VM.flags` | Xem các VM flags hiện tại |
| `VM.uptime` | Xem thời gian JVM đã chạy |
| `GC.heap_info` | Xem thông tin tổng quát về Java heap |
| `Thread.print` | In thread dump |
| `GC.class_histogram` | Thống kê instance theo class |
| `GC.heap_dump` | Tạo heap dump |
| `VM.native_memory` | Xem Native Memory Tracking nếu đã bật |
| `JFR.start` / `JFR.check` / `JFR.dump` / `JFR.stop` | Quản lý JFR recording |

Ví dụ kiểm tra thông tin cơ bản:

~~~bash
jcmd 24816 VM.version
jcmd 24816 VM.command_line
jcmd 24816 VM.flags
jcmd 24816 GC.heap_info
~~~

Đọc `help <command>` trước khi chạy command có thể tạo file lớn, gây GC hoặc ảnh hưởng hiệu năng.

## 6. Ví dụ Java 17 hoàn chỉnh: jps tìm, jcmd kiểm tra

Tạo file `src/demo/DiscoveryTarget.java`:

~~~java
package demo;

/** A process used to practice jps and jcmd. */
public final class DiscoveryTarget {
    /**
     * Keeps the JVM alive for local diagnostics.
     *
     * @param args command-line arguments
     * @throws InterruptedException if the sleep is interrupted
     */
    public static void main(String[] args) throws InterruptedException {
        System.out.println("READY");
        System.out.println("args=" + String.join(",", args));

        Thread.sleep(120_000);
    }
}
~~~

Biên dịch:

~~~bash
javac --release 17 -d out src/demo/DiscoveryTarget.java
~~~

Mở Terminal 1 và chạy:

~~~bash
java -Xms32m -Xmx128m -Dapp.mode=diagnostic \
    -cp out demo.DiscoveryTarget alpha beta
~~~

Stdout chính xác:

~~~text
READY
args=alpha,beta
~~~

Tiến trình tiếp tục chạy trong lúc bạn kiểm tra ở Terminal 2.

Bước 1: tìm JVM:

~~~bash
jps -l
~~~

Tìm dòng có `demo.DiscoveryTarget` và ghi lại identifier/PID thực tế.

Bước 2: xem arguments của chương trình và JVM:

~~~bash
jps -m
jps -v
~~~

Bước 3: xác nhận process bằng danh sách của jcmd:

~~~bash
jcmd -l
~~~

Bước 4: gửi diagnostic command đến đúng PID:

~~~bash
jcmd <pid> VM.version
jcmd <pid> VM.command_line
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print -l
~~~

Trong thread dump, thread main của ví dụ sẽ ở trạng thái `TIMED_WAITING` do đang ngủ trong `Thread.sleep`.

Khi hoàn tất, quay lại Terminal 1 và nhấn Ctrl+C để dừng ứng dụng. PID thay đổi theo mỗi lần chạy; không sao chép PID minh họa vào lệnh thực tế.

## 7. Chụp thread dump và kiểm tra heap

Sau khi tìm được đúng PID bằng `jps`, dùng `jcmd` để xem thread:

~~~bash
jcmd <pid> Thread.print
~~~

Hiển thị thêm thông tin lock:

~~~bash
jcmd <pid> Thread.print -l
~~~

Thread dump giúp xem thread đang chạy, chờ monitor, chờ condition hoặc bị block. Khi điều tra request bị treo hoặc deadlock, hãy chụp nhiều dump cách nhau một khoảng thời gian hợp lý rồi so sánh stack trace và lock. Một dump đơn lẻ chỉ thể hiện trạng thái tại một thời điểm.

Xem heap:

~~~bash
jcmd <pid> GC.heap_info
~~~

Thống kê object theo class:

~~~bash
jcmd <pid> GC.class_histogram
~~~

Tạo heap dump:

~~~bash
jcmd <pid> GC.heap_dump /var/tmp/application-heap.hprof
~~~

`GC.class_histogram` và `GC.heap_dump` có thể có impact cao tùy kích thước heap; heap dump còn có thể yêu cầu full GC, tốn dung lượng và chứa dữ liệu nhạy cảm. Chỉ chạy khi có mục tiêu rõ ràng, đã kiểm tra disk space và quyền truy cập output.

## 8. Ghi JFR sau khi xác định PID

Có thể dùng `jcmd` để bắt đầu một recording có thời hạn:

~~~bash
jcmd <pid> JFR.start name=diagnostic settings=default duration=60s filename=diagnostic.jfr
~~~

Kiểm tra recording:

~~~bash
jcmd <pid> JFR.check
~~~

Dump snapshot khi recording còn hoạt động:

~~~bash
jcmd <pid> JFR.dump name=diagnostic filename=diagnostic-snapshot.jfr
~~~

Dừng recording:

~~~bash
jcmd <pid> JFR.stop name=diagnostic
~~~

`settings=default` thường phù hợp theo dõi với overhead thấp hơn; `settings=profile` thu thập nhiều dữ liệu hơn và có thể tăng overhead. Đọc `help JFR.start` trên JVM đích để kiểm tra các tùy chọn và impact. Chọn thư mục output mà user chạy JVM có quyền ghi, rồi phân tích file `.jfr` bằng Java Mission Control hoặc công cụ tương thích.

## 9. Giới hạn khi chạy local, remote và trong container

### jps

Mặc định, `jps` tìm các instrumented HotSpot JVM trên máy local. Nó chỉ báo cáo JVM mà người chạy có quyền truy cập. Một JVM được khởi chạy bằng custom launcher có thể hiện `Unknown` thay cho tên class/JAR hoặc main arguments.

`jps` có thể nhận host identifier để truy vấn một host từ xa. Cách này cần dịch vụ `jstatd` hoạt động trên host đích và quyền truy cập phù hợp. `jps` được Oracle đánh dấu experimental và unsupported; không nên xem remote mode là một giao thức quản trị ổn định.

### jcmd

`jcmd` phải chạy trên cùng máy với JVM đích và thường cần cùng effective user/group identifiers đã dùng để khởi chạy JVM. Nó không phải lệnh gửi diagnostic qua mạng tới một PID trên host khác.

Tài liệu JDK 24 nêu rằng `jcmd -l` không liệt kê JVM đang chạy trong một Docker process riêng. Trong container, hãy xác định PID từ đúng PID namespace và chạy công cụ trong môi trường có thể attach đến JVM đó. Không lấy PID từ host namespace rồi giả định PID đó giống PID bên trong container.

### Quyền attach

JVM có thể tắt attach mechanism bằng `-XX:+DisableAttachMechanism`. Khi đó, `jcmd` không thể attach theo cách thông thường. Một số môi trường bảo mật hoặc container cũng giới hạn quyền truy cập.

## 10. Lưu ý bảo mật và vận hành

`jps -v`, `jcmd VM.command_line` và `jcmd VM.system_properties` có thể hiển thị thông tin nhạy cảm nếu ứng dụng đặt token, mật khẩu hoặc dữ liệu nội bộ trong command line/system properties. Rà soát và che dữ liệu trước khi chia sẻ output.

Các diagnostic command cũng có chi phí khác nhau. `Thread.print` và `GC.heap_info` thường phù hợp để bắt đầu; `GC.class_histogram` và `GC.heap_dump` có thể gây tác động đáng kể. Mức impact được công bố có thể xem bằng:

~~~bash
jcmd <pid> help <command>
~~~

Một số nguyên tắc vận hành:

- Xác nhận đúng PID trước khi gửi lệnh.
- Dùng PID cụ thể thay vì tên class nếu có nhiều instance.
- Không dùng PID `0` trừ khi chủ đích gửi lệnh đến mọi JVM có thể attach.
- Đọc help và impact trước khi chạy command chưa quen.
- Kiểm tra dung lượng, quyền truy cập và độ nhạy của file dump/recording.
- Ghi lại timestamp, PID, JDK version và command đã chạy để kết quả có thể đối chiếu.

## 11. Lỗi thường gặp và cách xử lý

### jps không tìm thấy ứng dụng

Kiểm tra ứng dụng còn chạy, user có quyền nhìn thấy JVM, JVM có phải HotSpot được instrument hay không và process có ở namespace/container khác không. `jps` không cam kết liệt kê mọi Java process.

### jps chỉ hiện tên ngắn hoặc Unknown

Dùng `jps -l` để xem tên class đầy đủ hoặc đường dẫn JAR. Với custom launcher, tên class/JAR và main arguments có thể không được cung cấp.

### jps output khó phân tích bằng script

Định dạng output có thể thay đổi và arguments có thể chứa khoảng trắng. Tài liệu Oracle khuyến nghị không viết script phụ thuộc vào cách phân tách output của `jps`. Nếu cần tự động hóa, ưu tiên cơ chế quản lý process/metrics phù hợp với hệ thống thay vì parse text output không ổn định.

### jcmd không attach được

Xác nhận PID, máy, user/group, container namespace và attach mechanism. Kiểm tra JVM có được khởi chạy với `-XX:+DisableAttachMechanism` hay không.

### Unknown diagnostic command

Command có thể không được JVM đó hỗ trợ. Chạy `jcmd <pid> help` để xem danh sách thực tế và `jcmd <pid> help <command>` để đọc cú pháp.

### Không thấy JVM trong jcmd -l nhưng biết process vẫn chạy

Nếu JVM nằm trong Docker process riêng, `jcmd -l` có thể không liệt kê nó. Xác định PID trong namespace phù hợp và chạy `jcmd` từ cùng môi trường có thể attach đến process đó.

### PID từ jps không attach được

LVMID thường nhưng không phải lúc nào cũng là OS PID. Xác nhận lại process bằng công cụ hệ điều hành và thực hiện attach từ đúng máy/namespace, đúng user.

## 12. Quy trình chẩn đoán gợi ý

Khi một ứng dụng Java có dấu hiệu treo hoặc sử dụng bộ nhớ bất thường:

1. Chạy `jps -l` để tìm tên class/JAR và identifier.
2. Chạy `jps -m` và `jps -v` nếu cần xem main arguments và VM arguments.
3. Dùng `jcmd -l` để đối chiếu danh sách JVM cục bộ.
4. Chọn PID cụ thể và chạy `jcmd <pid> help`.
5. Bắt đầu bằng `VM.version`, `VM.command_line`, `VM.flags` và `GC.heap_info`.
6. Nếu nghi ngờ thread bị kẹt, dùng `Thread.print -l` và so sánh các dump theo thời gian.
7. Nếu cần dữ liệu theo thời gian, thu JFR recording ngắn với settings phù hợp.
8. Chỉ tạo histogram hoặc heap dump sau khi đánh giá impact, dung lượng và quyền truy cập.
9. Lưu kết quả kèm timestamp, PID, JDK version và bối cảnh sự cố.

Không chạy mọi command theo một chuỗi cố định trên production. Chọn command theo giả thuyết cần kiểm tra và mức ảnh hưởng mà JVM công bố.

## 13. Checklist

- [ ] Dùng JDK có `jps` và `jcmd` trong thư mục `bin`.
- [ ] Dùng `jps -l` để nhận diện main class/JAR.
- [ ] Dùng `jps -m` và `jps -v` để phân biệt main arguments với VM arguments.
- [ ] Dùng `jps -q` khi chỉ cần identifiers.
- [ ] Nhớ rằng `jps` chỉ liệt kê JVM được instrument và có quyền truy cập; công cụ này experimental/unsupported.
- [ ] Không viết script phụ thuộc vào định dạng text của `jps`.
- [ ] Dùng `jcmd -l` để đối chiếu JVM cục bộ.
- [ ] Dùng PID cụ thể với `jcmd` khi có nhiều instance.
- [ ] Dùng `jcmd <pid> help` để khám phá command hỗ trợ.
- [ ] Kiểm tra đúng máy, user/group, attach mechanism và container namespace.
- [ ] Đọc impact trước khi chạy heap dump, histogram hoặc command tốn tài nguyên.
- [ ] Bảo vệ output có thể chứa command line, system properties, heap hoặc recording.

`jps` giúp tìm JVM được nhận diện; `jcmd` giúp kiểm tra và chẩn đoán JVM đó. Kết hợp chúng theo thứ tự tìm đúng tiến trình, xác nhận PID, khám phá command và thu thập dữ liệu phù hợp sẽ giúp việc xử lý sự cố rõ ràng và có thể lặp lại.
