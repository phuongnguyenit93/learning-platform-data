# The jps Command in the JDK

`jps` (Java Virtual Machine Process Status Tool) is a command-line tool included with the JDK to list running HotSpot JVMs and display the identifier of each process. It is useful when you need to find an application's JVM before inspecting more detailed information with `jcmd`, `jstat`, or other monitoring tools.

`jps` is primarily intended for process discovery. It does not display heap usage, thread dumps, GC statistics, or an application's HTTP status. Once you have found the JVM ID, use `jcmd` to send the appropriate diagnostic commands.

## 1. What is jps used for?

`jps` discovers HotSpot JVMs whose monitoring information the current user is permitted to access. Each line typically has the form:

~~~text
lvmid main-class-or-jar [main-arguments] [jvm-arguments]
~~~

Where:

- `lvmid` is the local VM identifier, the identifier that the tool uses to reference the JVM.
- `main-class-or-jar` is the launch class name or JAR name.
- `main-arguments` are the arguments passed to the `main` method.
- `jvm-arguments` are the arguments passed to the Java launcher/JVM.

`lvmid` usually matches the operating system process PID, but this is not guaranteed to always be the case. Treat the ID returned by `jps` as the JVM identifier and verify it before using it with OS tools such as `taskkill` or `kill`.

Example:

~~~bash
jps
~~~

Sample output:

~~~text
51276 com.intellij.idea.Main
94336 JShellToolProvider
70620 RemoteExecutionControl
~~~

The class name in the default output is usually the short name without the package. The list may also include tool processes such as `jps` or `jcmd` because those tools themselves run on a JVM.

Common use cases:

- Finding the PID/VM ID of a running Java application.
- Distinguishing between multiple JVMs on the same machine.
- Viewing the class or JAR that launched the application.
- Checking main arguments and JVM arguments when investigating configuration.
- Obtaining the ID to follow up with `jcmd <lvmid> help`.
- Quickly checking which JVMs are still running in the local environment.

## 2. Checking the JDK and syntax

`jps` is a JDK tool. Check the environment:

~~~bash
java -version
jps --help
~~~

On JDK 24.0.2, the help syntax is:

~~~text
usage: jps [--help]
       jps [-q] [-mlvV] [<hostid>]

Definitions:
    <hostid>:      <hostname>[:<port>]
    -? -h --help -help: Print this help message and exit.
~~~

General syntax:

~~~text
jps [options] [hostid]
~~~

- Without `hostid`: searches for JVMs on the local machine.
- With `hostid`: requests the JVM list on the specified host; this mode requires an appropriate `jstatd` service on the target host.
- Display options `-m`, `-l`, `-v`, and `-V` can be combined.
- `-q` prints only the JVM identifier.

Important note: the JDK documentation describes `jps` as an experimental and unsupported tool. It may change or be removed in a future JDK release. You should not build production workflows that depend on a stable output format from `jps`.

## 3. Main options

| Option | Description |
|---|---|
| `-q` | Prints only the local VM identifier, without the class/JAR name or arguments. |
| `-m` | Prints the arguments passed to the `main` method. |
| `-l` | Prints the full package name of the main class or the full path of the JAR. |
| `-v` | Prints the arguments passed to the JVM/Java launcher. |
| `-V` | Prints the VM flags read from the flags file in the inspected JDK; see the section below as behavior may vary by version. |
| `-J<option>` | Passes an option to the JVM running the `jps` tool itself. |
| `--help`, `-h`, `-?`, `-help` | Displays help information. |

Display options can be combined. Example:

~~~bash
jps -lmv
~~~

This command requests the full class/JAR name, main arguments, and JVM arguments.

### -q: print only the ID

~~~bash
jps -q
~~~

Sample output:

~~~text
51276
94336
70620
~~~

Use `-q` when you only need a list of IDs to cross-reference with another data source. This option is useful when you do not want to print application names or command-line arguments.

### -l: full class name or JAR path

~~~bash
jps -l
~~~

Sample output:

~~~text
51276 com.intellij.idea.Main
94336 jdk.jshell/jdk.internal.jshell.tool.JShellToolProvider
70620 jdk.jshell.execution.RemoteExecutionControl
~~~

For applications launched from a module, the output may display the module name along with the main class. For applications run from a JAR, this option displays the full JAR path.

### -m: arguments passed to main

~~~bash
jps -m
~~~

If the application is run with:

~~~bash
java -cp out com.acme.JpsDemo alpha beta
~~~

the corresponding line looks like:

~~~text
70992 JpsDemo alpha beta
~~~

`-m` helps identify the profile, mode, or application parameters passed at startup. For embedded JVMs or custom launchers, main arguments may be absent or unavailable.

### -v: JVM arguments

~~~bash
jps -v
~~~

If the JVM is launched with:

~~~bash
java -Ddemo.flag=row274 -Xmx512m -cp out com.acme.JpsDemo
~~~

the corresponding line looks like:

~~~text
70992 JpsDemo -Ddemo.flag=row274 -Xmx512m
~~~

`-v` displays parameters passed to the JVM, such as `-Xmx`, `-Xms`, `-Dproperty=value`, and other JVM options. This is a quick way to inspect startup configuration.

Note that command-line arguments sometimes contain tokens, passwords, internal paths, or sensitive data. Do not paste `jps -m` and `jps -v` output into public tickets or broadly accessible logs before scrubbing secrets.

### -V: VM flags from a flags file

In Azul OpenJDK 24.0.2 used to verify this article, `-V` displays the VM flags read from a file loaded via `-XX:Flags=<file>`. This differs from `-v`, which displays JVM arguments.

Example `vm.flags` file:

~~~text
+UseSerialGC
CompileThreshold=1500
~~~

Launch the application:

~~~bash
java -XX:Flags=vm.flags -cp out JpsFlagsDemo
~~~

Then run:

~~~bash
jps -V
~~~

Sample output from the test run:

~~~text
61216 JpsFlagsDemo +UseSerialGC CompileThreshold=1500
~~~

The PID changes on each run. Check `jps --help` and the behavior of your exact JDK version if your workflow depends on `-V`; documentation and implementation may differ across versions.

### -J: options for the JVM running jps

`-J` passes an option to the JVM executing the `jps` tool itself:

~~~bash
jps -J-Xmx48m
~~~

This option modifies the JVM of the `jps` process, not the heap or JVM arguments of the listed applications. Do not confuse `jps -J-Xmx48m` with setting the heap for a running Java server.

## 4. Hands-on example: finding a running JVM

The following example creates a small application and keeps the process alive long enough to observe it with `jps`.

Directory structure:

~~~text
jps-demo/
└── src/
    └── com/
        └── acme/
            └── JpsDemo.java
~~~

File `src/com/acme/JpsDemo.java`:

~~~java
package com.acme;

public class JpsDemo {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("JpsDemo started");
        Thread.sleep(60_000);
    }
}
~~~

### Step 1: compile

From the `jps-demo` root directory:

~~~bash
javac --release 17 -d out src/com/acme/JpsDemo.java
~~~

### Step 2: run the application

Open the first terminal:

~~~bash
java -Ddemo.flag=row274 -cp out com.acme.JpsDemo alpha beta
~~~

Exact stdout:

~~~text
JpsDemo started
~~~

The application waits 60 seconds and then exits. During that time, open a second terminal on the same machine under the same user account.

### Step 3: find the process

~~~bash
jps
~~~

Verified sample output:

~~~text
70992 JpsDemo
~~~

Other process names and IDs may appear at the same time. The ID shown here is just an example from a single run.

### Step 4: view the full class name

~~~bash
jps -l
~~~

The application's line:

~~~text
70992 com.acme.JpsDemo
~~~

### Step 5: view main arguments

~~~bash
jps -m
~~~

The application's line:

~~~text
70992 JpsDemo alpha beta
~~~

### Step 6: view JVM arguments

~~~bash
jps -v
~~~

The application's line:

~~~text
70992 JpsDemo -Ddemo.flag=row274
~~~

### Step 7: print only the ID

~~~bash
jps -q
~~~

The application's line:

~~~text
70992
~~~

These results were verified on Azul OpenJDK 24.0.2. Actual PIDs, process counts, and output order vary by machine and execution time.

## 5. Using the ID with jcmd

`jps` helps you find the JVM; `jcmd` performs deeper diagnostic operations.

List local JVMs:

~~~bash
jcmd -l
~~~

Output may contain:

~~~text
70992 com.acme.JpsDemo alpha beta
~~~

Ask the JVM to list supported diagnostic commands:

~~~bash
jcmd 70992 help
~~~

View the JVM command line:

~~~bash
jcmd 70992 VM.command_line
~~~

View JVM flags:

~~~bash
jcmd 70992 VM.flags
~~~

View heap information:

~~~bash
jcmd 70992 GC.heap_info
~~~

Print a thread dump:

~~~bash
jcmd 70992 Thread.print
~~~

Only use commands supported by the target JVM. Run `jcmd <pid> help` to see the actual command list rather than assuming every JDK version has the same set of commands.

`jcmd` must be run on the same machine as the target JVM and usually under the same effective user/group that launched that JVM. `jcmd -l` does not list JVMs running inside separate Docker containers; in that case, determine the PID from the container environment or run the tool from the appropriate namespace.

## 6. How do jps and jcmd differ?

| Criterion | jps | jcmd |
|---|---|---|
| Purpose | List JVMs and IDs | Send diagnostic commands to a JVM |
| Process discovery | Yes | Yes, via `jcmd -l` |
| View main class/arguments | Yes, with corresponding options | Yes, in the `-l` listing |
| View heap/threads/GC | No | Yes, via corresponding commands |
| Send commands to JVM | No | Yes |
| Best suited for | Quick discovery | Investigation and diagnostics |

In modern workflows, `jcmd -l` is often the preferred choice to find a JVM and proceed directly to diagnostics. `jps` remains useful when you need to understand the JVMStat tool and its display options.

If you only need to know which OS processes are running, use OS tools:

Windows PowerShell:

~~~powershell
Get-Process java, javaw -ErrorAction SilentlyContinue |
    Select-Object Id, ProcessName, Path
~~~

Linux/macOS:

~~~bash
ps -ef | grep '[j]ava'
~~~

OS commands can show Java processes even when `jps` cannot recognize them, though they do not provide the same JVM-specific details.

## 7. Limitations when listing JVMs

`jps` is not a tool that lists every Java process in every environment.

Limitations to keep in mind:

- The tool focuses on instrumented HotSpot JVMs whose monitoring data it can read.
- The list depends on the access permissions of the user running `jps`.
- JVMs belonging to other users may not appear.
- JVMs using a custom launcher may display `Unknown` instead of the class/JAR or main arguments.
- JVMs inside containers or other PID namespaces may not appear in the local listing.
- JVMs that exit before or during the scan may not appear in the output.
- Short-lived processes such as `jps` and `jcmd` themselves may appear in the list.
- Output formatting may change between JDK versions.

If you do not see the expected JVM:

1. Confirm the process is still running using OS tools.
2. Check the user running the application and the user running `jps`.
3. Determine whether the JVM is inside a container or a separate namespace.
4. Verify that the correct JDK and tool are being invoked via PATH.
5. Try `jcmd -l` on the same machine and under the same account.
6. If the application uses a custom launcher, rely on the PID and OS tools rather than the displayed class name.

Do not conclude that an application has stopped simply because `jps` does not list it.

## 8. jps with hostid and remote JVMs

`hostid` specifies the target machine for a remote query. According to JDK 24 syntax, the host part can have the form:

~~~text
hostname
hostname:port
~~~

Example:

~~~bash
jps -l app-server.example.com
~~~

Or when the RMI registry uses a non-default port:

~~~bash
jps -m app-server.example.com:2002
~~~

Remote queries require `jstatd` to be running on the target machine with an appropriate RMI registry/port. When `hostid` is omitted, `jps` uses a local protocol optimized for the platform.

**Security warning:** `jstatd` is an experimental, unsupported, and deprecated tool in JDK 24; the documentation notes that it will be removed in a future release. This service does not authenticate remote clients. When running, it can expose monitoring information for any JVMs accessible to the `jstatd` account to users on the network.

Do not start `jstatd` on untrusted networks or in production just to list JVMs remotely. If you still must maintain a legacy system, assess the risks and restrict the network, OS account, and service lifetime. For new systems, prefer monitoring mechanisms with explicit authentication and access control.

## 9. Security when reading process arguments

`jps -m` and `jps -v` can expose sensitive data if an application passes secrets via the command line.

Example of what not to do:

~~~bash
java -Ddb.password=plain-text-secret -jar service.jar
~~~

This value can appear in process-listing tool output, logs, or other observability systems. Do not use JVM arguments to store passwords, access tokens, or private key material.

Best practices:

- Pass secrets through a secret manager or an appropriate credential-provisioning mechanism.
- Do not log full `jps -m`/`-v` output without filtering out sensitive information.
- Restrict which users have permission to view process arguments.
- Do not post output containing internal configuration to public channels.
- Use `-q` if you only need IDs and do not need names or arguments.

`-q` reduces the amount of printed information, but it does not replace OS access controls.

## 10. Common errors and troubleshooting

| Symptom | Common cause | Resolution |
|---|---|---|
| `jps is not recognized` or command not found | JDK `bin` is not in PATH, or only a JRE/runtime is installed. | Check `java -version`, `where.exe jps` on Windows, or `which jps` on Unix. |
| Application JVM is not visible | Wrong user, process is not an instrumented HotSpot JVM, or separate container namespace. | Check with `Get-Process`/`ps`, run as the same user, and check inside the container. |
| Class name displays as `Unknown` | JVM was launched with a custom launcher or main class info is unavailable. | Use the PID and OS tools/`jcmd` to investigate. |
| Main arguments are missing | `-m` was not used, or the JVM does not provide main args info. | Try `jps -m`; note that embedded JVMs may have no arguments. |
| Full package name is missing | Using the default output. | Use `jps -l`. |
| JVM arguments are missing | `-v` option was not enabled. | Use `jps -v` and review the output before sharing. |
| Remote host returns no results | `jstatd` is not running, wrong host/port, RMI registry unreachable, or blocked by firewall. | Check the service and network configuration in a controlled environment; do not expose the service to public networks. |
| ID does not match OS PID | `lvmid` usually, but not always, equals the OS PID. | Cross-check with OS tools before sending signals or terminating the process. |
| Output-parsing script breaks after a JDK upgrade | `jps` format is not guaranteed to be stable. | Avoid parsing output; use monitoring APIs/workflows with more stable formats. |

## 11. Practical workflow

When you need to find a running JVM:

1. Run `jps -l` to view the full class/JAR name.
2. If you need the application arguments, run `jps -m`.
3. If you need the JVM configuration, run `jps -v`.
4. Record the `lvmid` and verify that the process is still running.
5. Run `jcmd <lvmid> help` to list available diagnostic commands.
6. Choose the appropriate `jcmd` command such as `VM.command_line`, `VM.flags`, `GC.heap_info`, or `Thread.print`.
7. Protect the output if it contains sensitive information.
8. If the JVM is inside a container, find the PID in the appropriate namespace and run the tool in that environment.

Do not write automation that relies on column positions or class names in `jps` output if you do not control the JDK version. This format is designed for quick human inspection and is subject to change.

## 12. Key takeaways

`jps` lists instrumented HotSpot JVMs that the current user has permission to observe. `-q` prints only IDs; `-l` displays full class/JAR names; `-m` displays main arguments; `-v` displays JVM arguments; `-V` displays VM flags from a flags file in the tested JDK 24.0.2 build.

`jps` is marked experimental and unsupported, so use it as a quick discovery/investigation tool. When JVM diagnostics are needed, `jcmd -l` and `jcmd <pid> <command>` form a better workflow. Remote queries with `jps hostid` depend on `jstatd`, a deprecated service with no client authentication; avoid deploying it on untrusted networks.
