# Creating Installer Artifacts for Java Applications

An **installer artifact** is a distribution package that enables users to install, update, launch, and uninstall a Java application in a way that fits the operating system. A good installer should include the application, its required dependencies, a compatible Java runtime, metadata, icons, launchers, and installation configuration.

`jpackage` was introduced as an incubator tool in JDK 14 and became an official tool in JDK 16. It supports creating application images and native installers for Windows, macOS, and Linux. `jpackage` can use `jlink` to create a custom runtime image, allowing users to run the application without installing a standalone JDK/JRE.

This lesson explains how to prepare a JAR or module, create an application image, build platform-specific installers, manage versions and upgrades, sign artifacts, test installation/uninstallation, and integrate installer packaging into CI/CD.

## 1. What Is an Installer Artifact?

A Java application can be distributed in several forms:

| Artifact | Contents | How It Is Used |
|---|---|---|
| JAR | Application bytecode and resources | Users need a Java runtime and the appropriate launch command |
| Fat JAR | Application packaged together with its dependencies | Still requires a Java runtime |
| Modular JAR | JAR with a module descriptor | Runs using the module path and a compatible runtime |
| Runtime image | Custom Java runtime created with `jlink` | Does not necessarily include an application launcher or installer |
| Application image | Launcher, application files, and runtime | Can be run directly from the image directory |
| Native installer | OS-specific installation package; can register shortcuts, menus, and file associations | Users install it like a regular desktop application |

### Distinguishing Between an Application Image and an Installer

An **application image** is a directory organized to run the application. This directory typically contains:

- The native launcher for the application.
- JARs/modules and resources.
- Launcher configuration files generated by `jpackage`.
- The bundled Java runtime image.

A **native installer** is an installation package that uses the operating system's native mechanisms. An installer can register shortcuts, menus, file associations, the installation location, and package information managed by the operating system.

An application image is often a very useful intermediate step: build the image, test running it, and then use that exact image to produce an MSI, EXE, PKG, or DMG.

An application image can be compressed into a ZIP archive for manual distribution, but on its own it does not provide the full installation and package-management experience of a native installer.

## 2. Installer Formats by Operating System

`jpackage` supports the following package types:

| Platform | Format | Characteristics |
|---|---|---|
| Windows | MSI | Windows Installer package; supports installation and upgrades via Windows Installer |
| Windows | EXE | Executable installer, typically wrapping an MSI |
| macOS | DMG | Disk image containing the `.app` application for users to install/copy |
| macOS | PKG | macOS installer package |
| Linux | DEB | Package for Debian/Ubuntu and compatible systems |
| Linux | RPM | Package for Fedora/RHEL and compatible systems |
| Cross-purpose within the same OS | app-image | Application directory containing a launcher and runtime |

Choose the format based on how users install software and your organization's distribution system. For example, desktop applications for Windows typically provide MSI or EXE; software managed via Linux package repositories typically provides DEB or RPM.

Do not assume a single format works across all operating systems. `jpackage` builds packages for the platform it is running on and does not support cross-platform packaging.

## 3. How Do `jpackage` and `jlink` Work Together?

`jpackage` takes the application JAR or module, metadata, launcher options, and resources. If no runtime image is provided, `jpackage` invokes `jlink` to create an appropriate Java runtime and places that runtime inside the application image.

Packaging flow:

~~~text
Java source
    |
    v
javac / Maven / Gradle
    |
    v
JAR or modular JAR
    |
    v
jpackage
    |
    +----> jlink creates runtime image
    |
    v
Application image
    |
    v
Native installer
    |
    v
Install / launch / update / uninstall
~~~

This means users can run the application using the generated launcher without manually installing a separate Java runtime.

### A Runtime Image Is Not the Full JDK

The runtime image generated by `jpackage` typically strips out:

- Debug symbols.
- Standard JDK native commands.
- Man pages.
- Header files.
- Development files such as `src.zip`.

The runtime still includes the components needed to run the application.

Therefore, do not assume the runtime directory bundled with the application image contains `java.exe` or `java` like a full JDK. The application's launcher uses the bundled runtime.

### Which Java Runtime Version Does `jpackage` Select?

If `--runtime-image` is not passed, `jpackage` uses the JDK running the tool to invoke `jlink`. The `javac --release` flag only controls the API and class-file target during compilation; it does not force `jpackage` to create a runtime of that same release.

For example:

- Build the source with JDK 24 using `javac --release 17`.
- Run `jpackage` from JDK 24.
- By default, the application image will contain a runtime built from JDK 24.

If the product must run on Java 17, use JDK 17 to create the appropriate runtime image, or create the runtime with JDK 17's `jlink` and pass it via `--runtime-image`.

### `ServiceLoader` and Runtime Modules

For applications that use `ServiceLoader` or provider modules, verify whether the providers are included in the runtime image.

`jpackage` provides a `jlink` option:

~~~bash
--jlink-options "--bind-services --strip-debug --no-man-pages --no-header-files"
~~~

You can add modules with `--add-modules` when dependencies are loaded dynamically or not fully inferred from the module graph.

For modular applications, the default runtime contains the main module and its dependency closure. For classpath/non-modular applications, the default runtime contains a set of JDK modules suitable for classpath applications. Service providers may require `--bind-services`.

## 4. Preparing the Application Before Packaging

Before invoking `jpackage`, you need the built application artifact and the required resources.

A simple input structure:

~~~text
installer-project/
├── src/
│   └── com/acme/desktop/Main.java
├── build/
│   ├── classes/
│   └── installer-input/
│       ├── acme-desktop.jar
│       ├── dependency-a.jar
│       └── dependency-b.jar
├── assets/
│   ├── app.ico
│   ├── app.icns
│   └── app.png
└── dist/
~~~

The directory passed to `--input` contains the files that will be included in the application image. Make sure the main JAR, dependency JARs, and required resources are in the right place.

### Specifying the Main Class

The application must have a valid entry point:

~~~java
package com.acme.desktop;

public final class Main {
    public static void main(String[] args) {
        System.out.println("Acme Desktop started");
    }
}
~~~

Compile:

~~~bash
javac --release 17 -d build/classes src/com/acme/desktop/Main.java
~~~

Package the JAR:

~~~bash
jar --create --file build/installer-input/acme-desktop.jar --main-class com.acme.desktop.Main -C build/classes .
~~~

Test running the JAR first:

~~~bash
java -jar build/installer-input/acme-desktop.jar
~~~

Stdout:

~~~text
Acme Desktop started
~~~

If the application has dependencies, build and copy them into the input folder according to the appropriate classpath configuration. For modular applications, use the module path and main module instead of `--main-jar`.

### Preparing Resources

Resources required by the application must be packaged or installed in an accessible location. For example:

- Default configuration files.
- Templates.
- Required public certificates.
- OS/architecture-specific native libraries.
- Fonts or assets.
- License text.
- File association metadata.

Do not bundle secrets, private keys, passwords, or production tokens into the installer. Users can extract the application image and read the packaged files.

### Separating Installation Data and User Data

Do not write files that users modify frequently into the application's installation directory. Use the user home or application data directory to store:

- Preferences.
- Caches.
- Logs.
- Local databases.
- Downloaded files.
- User-created documents.

Installers and updaters may replace or delete files in the installation directory. Designing a separate data location makes upgrades and uninstallation safer.

## 5. Creating an Application Image for a Non-Modular Application

For applications using the classpath or standard JARs, use `--input`, `--main-jar`, and `--main-class`.

Example:

~~~bash
jpackage --type app-image --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --app-version 1.2.3 --vendor "Acme Corporation" --description "Acme Desktop Application" --dest dist
~~~

On Windows PowerShell, you can write it on a single line or use a backtick for line continuation; the example above does not require a continuation character.

Explanation:

- `--type app-image`: creates only the application image.
- `--input`: directory containing the application JAR and input files.
- `--name`: application and launcher name.
- `--main-jar`: main JAR, relative to the input folder.
- `--main-class`: main class.
- `--app-version`: application/package version.
- `--vendor`: vendor name.
- `--description`: application description.
- `--dest`: destination directory for the output.

Once created, the output typically looks like:

~~~text
dist/
└── AcmeDesktop/
    ├── AcmeDesktop.exe
    ├── app/
    │   ├── AcmeDesktop.cfg
    │   └── acme-desktop.jar
    └── runtime/
~~~

The exact layout depends on the platform. On Linux, the launcher is usually in `bin/`; on macOS, it is a `.app` bundle; on Windows, the launcher can be at the root of the application image.

### Testing the Application Image

Windows:

~~~powershell
.\dist\AcmeDesktop\AcmeDesktop.exe
~~~

Linux:

~~~bash
./dist/AcmeDesktop/bin/AcmeDesktop
~~~

macOS:

~~~bash
open dist/AcmeDesktop.app
~~~

Example stdout for a console application:

~~~text
Acme Desktop started
~~~

For GUI applications, do not enable a console launcher if terminal output is not needed.

## 6. Creating an Application Image for a Modular Application

With JPMS, use `--module-path` and `--module`:

~~~bash
jpackage --type app-image --module-path mods --module com.acme.desktop/com.acme.desktop.Main --name AcmeDesktop --app-version 1.2.3 --dest dist
~~~

If the module path needs both application modules and JDK jmods, pass the appropriate paths using the OS path separator. On Windows, the separator is a semicolon; on Linux/macOS, it is a colon.

The main module must have a valid module descriptor, and all required dependencies must be resolvable.

### Adding Required Modules

If the application needs modules that are not inferred from the dependency graph:

~~~bash
jpackage --type app-image --module-path mods --add-modules java.sql,java.logging --module com.acme.desktop/com.acme.desktop.Main --name AcmeDesktop --dest dist
~~~

Only add modules that are actually needed. Adding too many modules increases the size of the runtime image.

### Creating a Custom Runtime with `jlink`

You can create a custom runtime beforehand:

~~~powershell
jlink --module-path "mods;$env:JAVA_HOME\jmods" --add-modules com.acme.desktop --bind-services --strip-debug --no-header-files --no-man-pages --output build/runtime
~~~

On Linux/macOS, replace the semicolon in the module path with a colon.

Then package the runtime image:

~~~bash
jpackage --type app-image --module-path mods --module com.acme.desktop/com.acme.desktop.Main --runtime-image build/runtime --name AcmeDesktop --dest dist
~~~

The runtime image must be compatible with the target OS, architecture, and JDK release.

## 7. Customizing the Launcher and JVM Options

`jpackage` allows configuring JVM options and application arguments.

Example:

~~~bash
jpackage --type app-image --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --java-options "-Xms256m" --java-options "-Xmx1024m" --java-options "-Dfile.encoding=UTF-8" --arguments "--profile=desktop" --dest dist
~~~

JVM options are passed to the application's runtime. Choose a heap size that fits the device's memory budget; do not set `Xmx` too high for the target environment.

### Creating Secondary Launchers

You can create additional launchers with `--add-launcher`. Example **import.properties** file:

~~~properties
main-class=com.acme.desktop.ImportMain
arguments=--mode=import
java-options=-Xmx512m
description=Import Acme data
~~~

Create the image:

~~~bash
jpackage --type app-image --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --add-launcher Import=import.properties --dest dist
~~~

The application image can contain both the main launcher and the `Import` launcher. The properties file should be managed alongside the source/build configuration for reproducibility.

### Console and GUI Launchers

On Windows, `--win-console` creates a console launcher, which is suitable for CLI applications or apps requiring terminal interaction. For desktop GUIs, this option is usually left disabled to avoid opening an unnecessary console window.

## 8. Metadata, Icons, Licenses, and File Associations

The installer is the first interface users see. Metadata must be accurate and consistent with the product name.

Common options:

| Option | Purpose |
|---|---|
| `--name` | Application/package name |
| `--app-version` | Version |
| `--vendor` | Vendor |
| `--description` | Description |
| `--copyright` | Copyright information |
| `--about-url` | Product website |
| `--icon` | Icon |
| `--license-file` | License file |
| `--install-dir` | Installation directory |
| `--resource-dir` | Override default resources/templates |
| `--file-associations` | Register file types opened by the application |

### Platform-Specific Icons

Common icon formats:

- Windows: `.ico`.
- macOS: `.icns`.
- Linux: `.png`.

Example:

~~~bash
jpackage --type app-image --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --icon assets/acme.ico --dest dist
~~~

The icon must have the correct format and dimensions for the platform. A PNG icon does not automatically substitute for an ICO icon on Windows.

### License File

Example:

~~~bash
jpackage --type msi --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --license-file LICENSE.txt --dest dist
~~~

The license file is used in the installation experience depending on the package format. Make sure the license and copyright contents have been approved.

### File Associations

You can create a properties file to register an extension:

~~~properties
extension=acme
mime-type=application/x-acme
description=Acme Project File
icon=assets/acme-file.ico
~~~

Then:

~~~bash
jpackage --type msi --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --file-associations file-association.properties --dest dist
~~~

Test file associations on an actual target machine. Behavior may vary by OS and installer type.

## 9. Creating Windows MSI and EXE

On Windows, `jpackage` supports `app-image`, `msi`, and `exe`.

Example creating an MSI:

~~~powershell
jpackage --type msi --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --app-version 1.2.3 --vendor "Acme Corporation" --win-menu --win-menu-group "Acme Tools" --win-shortcut --win-upgrade-uuid "8c8f7a40-ecf1-4d6a-91bd-47f2c90f2b10" --dest dist
~~~

Example creating an EXE:

~~~powershell
jpackage --type exe --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --app-version 1.2.3 --win-menu --win-shortcut --dest dist
~~~

### Windows Installer Options

| Option | Meaning |
|---|---|
| `--win-dir-chooser` | Let the user choose the installation directory |
| `--win-menu` | Create a Start Menu shortcut |
| `--win-menu-group` | Start Menu group |
| `--win-shortcut` | Create a desktop shortcut |
| `--win-shortcut-prompt` | Ask the user whether to create a shortcut |
| `--win-per-user-install` | Per-user installation |
| `--win-upgrade-uuid` | Product upgrade identifier |
| `--win-update-url` | Update information URL |
| `--win-help-url` | Support URL |

### WiX Requirement

To create MSI/EXE on Windows, `jpackage` requires WiX Toolset 3.0 or later as specified by JDK 24. Verify that WiX is installed and the required tools are in `PATH` before building the installer.

An application image can still be created without WiX. Therefore, you can test the launcher and runtime first, and then run the MSI/EXE creation step on a Windows build agent with all required tools installed.

### Upgrade UUID

Keep the same `--win-upgrade-uuid` across consecutive versions of the same product so Windows Installer recognizes the upgrade relationship. Do not generate a new random UUID for each release if you want to upgrade existing installations.

Increment `app-version` according to your product's versioning rules. Only change the upgrade identity when creating an independent product/package line with a defined migration policy.

## 10. Creating macOS DMG and PKG

On macOS, `jpackage` supports `app-image` as a `.app` bundle, `dmg`, and `pkg`.

Example creating a DMG:

~~~bash
jpackage --type dmg --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --app-version 1.2.3 --mac-package-identifier com.acme.desktop --icon assets/acme.icns --dest dist
~~~

Example creating a PKG:

~~~bash
jpackage --type pkg --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --app-version 1.2.3 --mac-package-identifier com.acme.desktop --dest dist
~~~

### macOS Package Identifier

Use a stable bundle identifier, typically in reverse-domain format:

~~~text
com.acme.desktop
~~~

The identifier must be valid and consistent across versions so the system recognizes the application.

### Code Signing

You can instruct `jpackage` to sign the bundle:

~~~bash
jpackage --type dmg --input build/installer-input --name AcmeDesktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --mac-package-identifier com.acme.desktop --mac-sign --mac-signing-key-user-name "Developer ID Application: Acme Corporation" --dest dist
~~~

You can select a keychain with `--mac-signing-keychain` and configure entitlements with `--mac-entitlements`. Signing requires a valid certificate and signing identity.

On JDK 24, Xcode command line tools are required when using `--mac-sign` and when using `--icon` to customize a DMG image.

### Notarization

Code signing and notarization are two separate steps. For applications distributed outside the Mac App Store, the release process typically requires:

1. Signing the application bundle and native components.
2. Creating the DMG or PKG.
3. Submitting the artifact to the Apple notarization service using Apple's tools, such as `xcrun notarytool`.
4. Waiting for the result and resolving any errors if they occur.
5. Stapling the ticket to the artifact using `xcrun stapler`.
6. Re-verifying the signature and notarization.

Do not treat a successful `jpackage` run as proof that the application has been notarized.

## 11. Creating Linux DEB and RPM

On Linux, `jpackage` supports DEB and RPM.

DEB example:

~~~bash
jpackage --type deb --input build/installer-input --name acme-desktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --app-version 1.2.3 --linux-package-name acme-desktop --linux-deb-maintainer packages@acme.example --linux-app-category Utility --linux-shortcut --dest dist
~~~

RPM example:

~~~bash
jpackage --type rpm --input build/installer-input --name acme-desktop --main-jar acme-desktop.jar --main-class com.acme.desktop.Main --app-version 1.2.3 --linux-package-name acme-desktop --linux-rpm-license-type MIT --linux-app-category Utility --linux-shortcut --dest dist
~~~

### Linux Package Options

| Option | Meaning |
|---|---|
| `--linux-package-name` | Package name |
| `--linux-deb-maintainer` | Maintainer email for DEB |
| `--linux-package-deps` | Required package dependencies |
| `--linux-rpm-license-type` | License type for RPM |
| `--linux-app-release` | Package release/revision |
| `--linux-app-category` | Category |
| `--linux-menu-group` | Menu group |
| `--linux-shortcut` | Create shortcut |

### Required Tools

According to JDK 24 packaging requirements:

- Ubuntu requires `fakeroot` to create DEB packages.
- Red Hat Linux requires `rpm-build` to create RPM packages.

Build packages on a compatible distro and test on a clean machine. A DEB or RPM can declare dependencies on native OS packages; declare them accurately so the package manager can handle them.

## 12. Creating Packages from an Existing Application Image

A good workflow separates image creation from installer creation:

1. Build the JAR/module.
2. Create the application image.
3. Run smoke tests.
4. Sign the application image if needed.
5. Create the native installer from the tested image.

Example creating an MSI from an image:

~~~powershell
jpackage --type msi --app-image dist/AcmeDesktop --name AcmeDesktop --app-version 1.2.3 --win-menu --win-shortcut --dest installer-output
~~~

This approach lets you test the exact application image before building the installer. When building multiple formats for the same OS, you can reuse the image as input if the formats and options are compatible.

Do not manually modify runtime or launcher files in the image after signing. If contents are changed after signing, you must re-sign according to your process.

## 13. Installer Lifecycle: Install, Upgrade, and Uninstall

An installer artifact should be evaluated across its entire lifecycle, not just whether the file was generated successfully.

### Install

Verify:

- Installation path.
- User/admin permissions.
- Shortcuts and Start Menu entries.
- File associations.
- Bundled runtime.
- Application launcher starts properly.
- Native libraries can be loaded.
- Application data directory is writable.

### Upgrade

Verify:

- Same product identity.
- New version is recognized.
- Application files are replaced properly.
- User data and configuration are preserved.
- Database/schema migration can complete.
- Interrupted upgrades can recover.
- No unintended conflicting dual installations.

For Windows MSI, keep a stable upgrade UUID for the same product. For macOS and Linux, keep an appropriate bundle/package identity so the system recognizes the application properly.

### Uninstall

Verify:

- Application files are removed.
- Shortcuts and file associations are handled properly.
- Services/background processes are stopped.
- No process holds locks on files in the installation directory.
- User data policy is followed properly.

Do not unexpectedly delete user-created documents or local databases. Clearly define which data is removed, which data is preserved, and how users can back it up.

### Installation Directory and User Data

Windows can use `--install-dir` with a sub-path under the default installation directory. Linux/macOS can use an absolute installation path following platform conventions.

Do not place databases or frequently modified configuration files inside the installation directory. Updaters and installers typically have permission to replace files there.

## 14. Signing and Integrity Verification

An installer is an artifact that users execute with system privileges. Its origin and integrity must be verified.

### Windows Authenticode

Windows installers are typically signed with a code-signing certificate using Windows SDK's SignTool. `jpackage` builds the package; signing the MSI/EXE can be done as a separate signing step in the pipeline.

Example command:

~~~powershell
signtool sign /fd SHA256 /tr <timestamp-service-url> /td SHA256 /a AcmeDesktop.msi
~~~

Verify signature:

~~~powershell
signtool verify /pa /v AcmeDesktop.msi
~~~

Use an organization-approved certificate and timestamp service. Protect private keys in a signing service or secure CI secret store; never store private keys in the source repository or installer.

### macOS Signing and Notarization

Use an appropriate Developer ID signing identity, minimal entitlements, and Apple's notarization process. After signing, do not modify the bundle without re-signing.

Verify:

~~~bash
codesign --verify --deep --strict --verbose=2 AcmeDesktop.app
spctl --assess --type execute --verbose AcmeDesktop.app
~~~

After notarization, verify that the ticket has been stapled and the package can be opened on a clean machine under Gatekeeper policy.

### Linux Package Signing

`jpackage` creates DEB/RPM packages; signing packages or repository metadata is typically performed using distro/repository tools and workflows. For example, RPM repositories can use GPG signing. For DEB, many organizations sign repository metadata and verify via `apt` trust configuration.

Do not treat a plain SHA-256 hash as a signature. A hash detects modifications when compared against a trusted reference value; a signature authenticates the publisher and artifact via a trust chain.

### Checksums and Provenance

Record checksums:

Windows PowerShell:

~~~powershell
Get-FileHash .\dist\AcmeDesktop.msi -Algorithm SHA256
~~~

Linux/macOS:

~~~bash
sha256sum dist/AcmeDesktop.deb
~~~

Record alongside:

- Source revision.
- JDK vendor/version.
- `jpackage`/JDK version.
- OS and architecture.
- Build tool/plugin versions.
- Package version.
- Checksum.
- Signing identity and verification results.
- SBOM and provenance if supported by the pipeline.

## 15. Testing Installer Artifacts

A successfully built package does not prove that installation and runtime operation work properly.

### Testing the Application Image

- Launcher exists and runs.
- Bundled runtime image is complete.
- Application runs without a separate Java installation.
- JVM options are applied.
- Resources and native libraries are found.
- Log/config paths are writable.

### Testing the Native Installer

- Install on a clean machine/VM.
- Install as both a standard user and an admin when supported.
- Check shortcuts/menus.
- Open file associations.
- Launch the application after a reboot.
- Test upgrading from the previous version.
- Test uninstallation.
- Check remaining user data against policy.
- Verify certificates and signatures.
- Verify the package manager recognizes the correct version.

### Testing Standalone Runtime Behavior

Do not only test by running the JAR with the build machine's JDK. Run the launcher inside the application image or install the installer on a machine without a JDK to confirm the runtime is bundled properly.

### Testing OS and Architecture

Build and test separately for each target:

- Windows x64/ARM64 if supported.
- macOS Intel/Apple Silicon depending on distribution targets.
- Linux x64/ARM64 and supported distros.

Native libraries, runtime images, and installer packages are platform-dependent. Do not reuse a package built on Windows for Linux or vice versa.

## 16. Organizing CI/CD for Installer Artifacts

A pipeline can be divided into stages:

~~~text
Checkout source
    |
    v
Compile + unit tests
    |
    v
Build JAR / modules
    |
    v
Create application image
    |
    v
Smoke test launcher
    |
    v
Create native installer
    |
    v
Sign + verify
    |
    v
Install / upgrade / uninstall tests
    |
    v
Checksum + SBOM + provenance
    |
    v
Publish artifacts
~~~

### Build Matrix by OS

Use dedicated build runners:

| Runner | Artifact |
|---|---|
| Windows | MSI/EXE and Windows app-image |
| macOS | DMG/PKG and `.app` image |
| Ubuntu/Debian | DEB and Linux app-image |
| RHEL/Fedora | RPM and Linux app-image |

Each runner needs the corresponding JDK, build tools, and native packaging tools.

### Pinning the Toolchain

Pin:

- JDK vendor/version.
- Maven/Gradle Wrapper.
- Plugin versions.
- Dependency versions.
- `jpackage` options.
- Installer toolchain (WiX, Xcode, `rpm-build`, `fakeroot`).
- OS image and architecture.

If the JDK version changes, the runtime image may change even if the application source does not. Treat this as a runtime change that requires testing.

### Consistent Artifact Naming

Example:

~~~text
AcmeDesktop-1.2.3-windows-x64.msi
AcmeDesktop-1.2.3-macos-aarch64.dmg
AcmeDesktop-1.2.3-linux-x64.deb
AcmeDesktop-1.2.3-linux-x64.rpm
~~~

Do not overwrite an artifact of one OS/architecture with an artifact from another target. Store packages, checksums, SBOMs, and build metadata together with the release.

## 17. Troubleshooting

### `jpackage` Reports Main Class Not Found

Verify that `--main-class` is the exact fully qualified class name, the main JAR contains the class and its package path, and the class has `public static void main(String[] args)`.

### `jpackage` Reports Main JAR Not in Input Directory

`--main-jar` must be a filename or relative path inside the `--input` directory. Check spelling and folder structure before running.

### Application Image Is Created, but Launcher Does Not Run

Check:

- Whether the runtime image has all required modules.
- Whether the launcher config has the correct main class/module.
- Whether JARs and resources are present in the application image.
- Whether native libraries match the OS/architecture.
- Whether JVM options are valid.
- Whether logs or console output show error details.

### `ClassNotFoundException` or `NoClassDefFoundError`

Dependencies may not have been packaged, or the launcher classpath/module path may be incorrect. Check the input folder, module descriptor, dependency versions, and launcher configuration.

### `ServiceLoader` Cannot Find Provider

Check `uses`/`provides` in the module descriptor or `META-INF/services`. If `jlink` builds the runtime image, check whether `--bind-services` is needed to link provider modules.

### Runtime Missing Modules

Use `jdeps` to analyze dependencies and add required modules with `--add-modules`, or rebuild the runtime image with `jlink`. Check dynamic reflection and service loading, as some dependencies may not be statically inferred.

### Windows MSI/EXE Cannot Be Created

Verify that WiX Toolset 3.0 or later is installed and its tools are in `PATH`. Inspect `--verbose` output and the `--temp` directory if you need to retain intermediate files for diagnostics.

### Linux DEB/RPM Cannot Be Created

Verify you are building on a compatible Linux distribution and have `fakeroot` for Ubuntu/DEB or `rpm-build` for Red Hat/RPM. Check package name, version, maintainer, category, and dependency syntax.

### macOS Package Is Rejected

Check the icon, bundle identifier, signing identity, entitlements, certificate chain, and notarization. Do not modify the app bundle after signing; if changes are made, re-sign and re-notarize.

### Installer Works on Build Machine but Fails on Another Machine

Check OS version, CPU architecture, native libraries, access permissions, runtime dependencies, environment variables, and package prerequisites. Test on a clean VM with the same target OS version.

### Installer Upgrade Does Not Recognize Old Version

Check the package identity. On Windows, keep the same `--win-upgrade-uuid` for the same product. On macOS/Linux, keep a consistent bundle/package name and identifier. Increment the version according to package manager rules.

## 18. Java 17+ Lab: Creating an Application Image with `jpackage`

Create **Main.java**:

~~~java
package com.acme.installer;

public final class Main {
    public static void main(String[] args) {
        System.out.println("Installer artifact demo");
        System.out.println("Java runtime: "
                + Runtime.version().feature());
        System.out.println("Arguments: "
                + String.join(",", args));
    }
}
~~~

Compile:

~~~bash
javac --release 17 -d classes Main.java
~~~

Create the input folder and JAR:

~~~bash
mkdir input
jar --create --file input/artifact-demo.jar --main-class com.acme.installer.Main -C classes .
~~~

Run the JAR to verify:

~~~bash
java -jar input/artifact-demo.jar alpha beta
~~~

Stdout on JDK 24:

~~~text
Installer artifact demo
Java runtime: 24
Arguments: alpha,beta
~~~

Create an application image on Windows:

~~~powershell
jpackage --type app-image --input input --name ArtifactDemo --main-jar artifact-demo.jar --main-class com.acme.installer.Main --app-version 1.2.3 --vendor "Acme Example" --description "Java installer artifact lab" --dest output --win-console
~~~

Run the launcher:

~~~powershell
.\output\ArtifactDemo\ArtifactDemo.exe alpha beta
~~~

Stdout:

~~~text
Installer artifact demo
Java runtime: 24
Arguments: alpha,beta
~~~

The application image contains the launcher, application files, and runtime image. In testing on OpenJDK 24.0.2, the image runs and has a size of about 126 MB. The size varies depending on the JDK, modules, OS, and application.

The application was compiled with `--release 17`, but the bundled runtime is Java 24 because `jpackage` was run from JDK 24.0.2. If a Java 17 runtime is needed, you must create a runtime image with JDK 17 and pass `--runtime-image` to `jpackage`.

### Trying MSI Creation

After the `app-image` runs successfully, use a Windows runner with WiX installed:

~~~powershell
jpackage --type msi --app-image output\ArtifactDemo --name ArtifactDemo --app-version 1.2.3 --win-menu --win-shortcut --win-upgrade-uuid "8c8f7a40-ecf1-4d6a-91bd-47f2c90f2b10" --dest installer
~~~

Then install the MSI on a clean Windows VM and verify the launcher, shortcuts, upgrade, and uninstallation. The UUID here is an example; real products must use a stable UUID managed by the release team.

## 19. Pre-Release Installer Checklist

- Application JAR/module is built and tested.
- Main class/module is declared accurately.
- Dependencies and resources are packaged.
- Compatible Java runtime is bundled.
- Target OS and architecture are defined.
- Application image runs on a machine without a JDK.
- Version, vendor, description, copyright, and license are accurate.
- Icons and file associations are platform-appropriate.
- Installation directory and user data directory are separated.
- Upgrade identity is stable.
- Installer installs and uninstalls cleanly on a fresh VM.
- Upgrade from the previous version is tested.
- User data is preserved/deleted according to policy.
- Code signing and notarization are completed when required.
- Checksums, SBOM, and provenance are recorded.
- Artifacts are named by version/OS/architecture.
- CI stores logs and verification results.
- Final package is tested in the exact format to be released.

## 20. Key Terminology

| Term | Meaning |
|---|---|
| Installer artifact | Application installation package |
| `jpackage` | Tool for creating application images and native installers |
| `jlink` | Tool for creating custom Java runtime images |
| Application image | Application directory containing launcher, files, and runtime |
| Native installer | Package using the operating system's installation mechanism |
| MSI | Windows Installer package |
| EXE installer | Executable installer for Windows |
| DMG | macOS disk image |
| PKG | macOS installer package |
| DEB | Debian/Ubuntu package |
| RPM | Fedora/RHEL and compatible systems package |
| Runtime image | Linked Java runtime |
| Main JAR | JAR containing the application's main class |
| Module path | Path containing JPMS modules |
| File association | Associating a file type with an application |
| Upgrade UUID | Upgrade identifier for a Windows package |
| Code signing | Digitally signing an artifact with a certificate |
| Notarization | Apple's process for checking software distributed outside the App Store |
| SBOM | List of software components in an artifact |
| Provenance | Information about the origin and build process of an artifact |

A complete installer artifact bundles the application with an appropriate runtime, declares clear metadata and installation behavior, supports upgrades and uninstallation, signs and verifies the package, and is tested in a clean environment. `jpackage` standardizes packaging, while platform-specific CI ensures released artifacts match the target operating system and architecture.
