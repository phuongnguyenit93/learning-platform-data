# Avoiding Oversized Java Runtime Images

An oversized runtime image is a Java packaging anti-pattern: the application only needs a small set of modules to run, yet the artifact ships with many unnecessary JDK modules, locales, resources, tools, or application files. As a result, packages take longer to download, consume more storage, increase deployment time, expand the security update surface, and slow down distribution.

A large size does not automatically mean a build is wrong. Desktop applications with GUIs, multiple locales, fonts, JavaFX, database drivers, or native libraries may legitimately need many components. The goal is to remove what is unnecessary for the committed behavior, keep the required modules and resources, and re-measure on the same platform.

The primary tools are **jdeps** for analyzing dependencies, **jlink** for linking a custom runtime image, and **jpackage** for packaging an application image or installer. The optimization process should be driven by measurements and regression tests, not by removing modules based on guesswork.

## 1. Why Is an Oversized Runtime Image a Problem?

A large runtime image can cause:

- Increased download, storage, and cache usage.
- Longer build, upload, download, and deploy times.
- Larger container images and longer image pull times.
- More modules to track when the JDK receives security updates.
- Harder artifact comparison between releases.
- Duplication of large runtimes across every package when packaging multiple applications.

When deploying hundreds of instances, a difference of a few tens of MB per image can lead to significant storage and network usage.

However, do not optimize for a single number alone. Track these metrics together:

| Metric | Meaning |
|---|---|
| Runtime directory size | Size of the runtime directory after creation |
| Application payload size | Application JARs, dependencies, resources, and native libraries |
| Application image size | Total launcher, payload, and runtime generated by jpackage |
| Installer size | Size of the MSI/EXE/DEB/RPM/PKG/DMG file |
| Installed footprint | Disk usage after installation |
| Startup time | Time from launch until the application is ready |
| Memory usage | RSS, heap, and native memory at runtime |
| Functional coverage | Features that continue to work after removing modules/resources |

A compressed installer can be smaller than the extracted application image. Always compare the same metric type, the same OS/architecture, and the same JDK version.

## 2. Common Causes

### Selecting Too Many JDK Modules

A small command-line application might only need java.base and java.logging, yet the runtime image includes java.desktop, java.sql, java.xml, java.naming, java.management, jdk.jfr, jdk.compiler, and many other modules.

Root modules passed to jlink pull in their transitive dependencies. One large module can expand the entire set of dependent modules.

### Enabling Service Binding When Unnecessary

The --bind-services option links service provider modules along with their dependencies. This is useful when the application needs to discover providers via service binding, but it can significantly expand the module graph.

Do not enable --bind-services by default just to be "complete". Identify the actual service interfaces, providers, and ServiceLoader behavior.

### Keeping All Locale Data

The jdk.localedata module contains additional locale data. If you include this module without restricting locales, the image may carry far more data than the application needs.

An application that only supports English and Vietnamese can consider keeping only en and vi, after testing locale-specific date, number, currency, collation, and message formatting.

### Keeping Unnecessary Debug Information and Documentation

Production runtime images typically do not need debug information, C/C++ header files, or man pages. These can be stripped using the corresponding jlink plugins.

Note: --strip-debug affects the contents of the runtime image created by jlink. It does not automatically remove debug information from application JARs that jpackage places into the payload. If you want to shrink application JARs, review how they are compiled and packaged separately.

### Passing the Entire Build Directory to jpackage

The --input option of jpackage packages every file in the input directory. If pointed at the entire project directory or build output, the artifact may include test classes, test reports, Sources/Javadoc JARs, debug files, non-runtime dependencies, logs, caches, temporary files, and old builds.

This cause is often overlooked because the runtime image itself may already be small while the application image remains huge.

### Packaging Duplicate Runtimes

A container may use a base image that already contains a full JDK, and then copy a custom runtime image into the container as well. In that case, the same Java components appear twice in different layers.

Analyze the container layers and explicitly decide which runtime the container will use.

## 3. Measure Size Before Optimizing

Before making changes, record the baseline sizes and build information. Do not compare images built with different JDKs, different OSes, or different module sets.

### Linux and macOS

~~~bash
du -sh build/runtime
du -h -d 2 build/runtime | sort -h
du -sh app-input
du -h app-input/* | sort -h
du -sh build/packages/MyApp
~~~

### Windows PowerShell

~~~powershell
$path = 'build/runtime'
$bytes = (Get-ChildItem -LiteralPath $path -Recurse -Force -File | Measure-Object -Property Length -Sum).Sum
'{0}: {1:N2} MiB' -f $path, ($bytes / 1MB)
~~~

Compare two runtime images:

~~~powershell
$paths = 'build/runtime-small', 'build/runtime-wide'
foreach ($path in $paths) {
    $bytes = (Get-ChildItem -LiteralPath $path -Recurse -Force -File | Measure-Object -Property Length -Sum).Sum
    '{0}: {1:N2} MiB' -f $path, ($bytes / 1MB)
}
~~~

PowerShell sums the byte lengths of files. The result does not necessarily equal the allocated size on the filesystem because block sizes and sparse files can differ.

### Record the Baseline Configuration

Save the JDK vendor/full version/build number, OS and CPU architecture, module list, jlink/jpackage options, application JAR and dependency list, runtime/payload/app image/installer sizes, build/startup times, and test results. Keep the baseline so you know which changes actually reduce size and what their impact is.

## 4. Identify Required Modules with jdeps

jdeps analyzes dependencies at the package, class, and module levels. For a modular application, you can extract module dependencies to use as input for jlink.

~~~bash
jdeps --module-path "mods:$JAVA_HOME/jmods" --module com.acme.imageapp --print-module-deps
~~~

This command prints a comma-separated list of module dependencies. jdeps can analyze transitive dependencies of the classes and modules it recognizes.

For a JAR application running on the classpath:

~~~bash
jdeps --multi-release 17 --class-path "lib/*" --print-module-deps application.jar
~~~

In this example, lib contains the runtime dependencies. Without passing the right classpath, jdeps may report missing dependencies or miss dependencies of the application.

### Read the Output Carefully

The jdeps output is a starting point, not an exhaustive list of every module the application might need. Static analysis may miss reflection loading classes by string name, ServiceLoader and providers discovered at runtime, JNI and native libraries, dynamically generated or loaded classes/resources, plugins installed after build time, or rare code paths that only run for a specific request or locale.

After obtaining the module list, inspect module descriptors, configurations, tests, and actual plugins. If the application requires a dynamic module, explicitly add it to the root module list and document the reason.

### Inspect Dependencies in Detail

~~~bash
jdeps --verbose:module --module-path "mods:$JAVA_HOME/jmods" --module com.acme.imageapp
~~~

To find missing dependencies:

~~~bash
jdeps --missing-deps --module-path "mods:$JAVA_HOME/jmods" --module com.acme.imageapp
~~~

If the input is an exploded module directory, pass the module name or appropriate module path to jdeps; do not pass module-info.class as if it were a complete JAR.

## 5. Select Narrow Root Modules with jlink

jlink links root modules together with their transitive dependencies. The best approach is usually to start from the application module and add additional JDK modules only when there is evidence they are needed.

~~~bash
jlink --module-path "mods:$JAVA_HOME/jmods" --add-modules com.acme.imageapp --output build/runtime-small
~~~

If module com.acme.imageapp declares requires java.logging, jlink will include java.logging along with its required dependencies in the image.

Avoid adding a large list of modules just as a precaution. If a feature truly requires java.sql or java.desktop, add the corresponding module and test that feature.

### When Is --limit-modules Needed?

--limit-modules restricts the set of observable modules during resolution. It is useful for controlling the module universe when the module path is broad, but it is not a tool for blindly stripping modules.

If an application module or service provider requires a module outside the limit, resolution will fail or the application will not behave as expected. Only use it after understanding the dependency graph.

### Do Not Expand the Module Graph Without Reason

| Choice | Risk |
|---|---|
| Adding java.desktop to a non-GUI server app | Pulls in AWT, fonts, imaging, and related dependencies |
| Adding jdk.localedata without restricting locales | Retains more locale data than needed |
| Adding jdk.compiler | Ships the compiler even though only compiled bytecode is run |
| Adding jdk.jfr to every application | Increases image size even when Flight Recorder is not used at runtime |
| Enabling --bind-services unchecked | Links unnecessary providers and dependencies |
| Adding the entire module path | Defeats the purpose of a custom runtime |

The list above shows examples of modules to review, not strict prohibitions. An application may genuinely need them.

## 6. Strip Unnecessary Resources and Choose Compression

Only optimize the contents of the runtime image after selecting the right modules.

### Strip Debug Information

~~~bash
--strip-debug
~~~

This option strips debug information from the runtime image. Keep debug symbols or information needed for investigation workflows if production support requires them. Do not trade away diagnosability without evaluating the cost.

### Remove Header Files and Man Pages

~~~bash
--no-header-files
--no-man-pages
~~~

These files are typically more useful for development or native compilation than for regular runtime execution. Remove them from production runtime images if the application does not need them.

### Choose Compression

JDK 26 supports:

~~~bash
--compress=zip-0
--compress=zip-6
--compress=zip-9
~~~

zip-0 applies no compression; zip-6 is the default; zip-9 compresses more aggressively. Higher compression can reduce size but increases CPU overhead when accessing resources. Measure both disk size and startup/runtime performance on target hardware.

Do not use the legacy value --compress=2 for new builds. JDK 26 marks the legacy numeric values as deprecated; use the zip-{0-9} syntax.

### Restrict Locales

If the application only needs a specific set of locales:

~~~bash
jlink --module-path "mods:$JAVA_HOME/jmods" --add-modules com.acme.imageapp,jdk.localedata --include-locales=en,vi --output build/runtime-locales
~~~

--include-locales requires the jdk.localedata module. The tags are BCP 47 language tags; choose them based on product requirements and test actual locale behavior. Do not exclude locales based solely on UI language, as libraries may rely on locales for sorting, parsing, or formatting.

### Check Supported Plugins

~~~bash
jlink --list-plugins
~~~

Only use plugins supported by the running JDK. Available plugins and options can change across JDK versions.

## 7. Build Two Images to See the Impact of Module Selection

Example modular app with a module descriptor:

~~~java
module com.acme.imageapp {
    requires java.logging;
}
~~~

Main.java file:

~~~java
package com.acme.imageapp;

import java.util.logging.Logger;

public final class Main {
    private static final Logger LOG = Logger.getLogger(Main.class.getName());

    private Main() {
    }

    public static void main(String[] args) {
        LOG.fine("runtime image check");
        System.out.println("RUNTIME_IMAGE_OK module=" + Main.class.getModule().getName());
    }
}
~~~

Source structure:

~~~text
runtime-image-demo/
  src/
    com.acme.imageapp/
      module-info.java
      com/acme/imageapp/Main.java
  mods/
  build/
~~~

### Compile on Linux/macOS

~~~bash
mkdir -p mods/com.acme.imageapp build
javac -d mods/com.acme.imageapp src/com.acme.imageapp/module-info.java src/com.acme.imageapp/com/acme/imageapp/Main.java
~~~

### Compile on Windows PowerShell

~~~powershell
New-Item -ItemType Directory -Force mods\com.acme.imageapp, build | Out-Null
javac -d mods\com.acme.imageapp src\com.acme.imageapp\module-info.java src\com.acme.imageapp\com\acme\imageapp\Main.java
~~~

### Build the Small Runtime on Linux/macOS

~~~bash
jlink --module-path "mods:$JAVA_HOME/jmods" --add-modules com.acme.imageapp --strip-debug --no-header-files --no-man-pages --compress=zip-6 --output build/runtime-small
~~~

### Build an Intentionally Wide Runtime for Comparison

~~~bash
jlink --module-path "mods:$JAVA_HOME/jmods" --add-modules com.acme.imageapp,java.desktop,java.sql,java.xml,java.naming,java.management,jdk.jfr,jdk.localedata --strip-debug --no-header-files --no-man-pages --compress=zip-6 --output build/runtime-wide
~~~

runtime-wide includes extra modules to demonstrate the cost of broad root modules. This is a comparison example, not a production configuration.

### Build the Small Runtime on Windows PowerShell

~~~powershell
jlink --module-path "$env:JAVA_HOME\jmods;mods" --add-modules com.acme.imageapp --strip-debug --no-header-files --no-man-pages --compress=zip-6 --output build\runtime-small
~~~

### Build the Wide Runtime on Windows PowerShell

~~~powershell
jlink --module-path "$env:JAVA_HOME\jmods;mods" --add-modules com.acme.imageapp,java.desktop,java.sql,java.xml,java.naming,java.management,jdk.jfr,jdk.localedata --strip-debug --no-header-files --no-man-pages --compress=zip-6 --output build\runtime-wide
~~~

Run the application using the small runtime.

Linux/macOS:

~~~bash
build/runtime-small/bin/java -m com.acme.imageapp/com.acme.imageapp.Main
~~~

Windows PowerShell:

~~~powershell
.\build\runtime-small\bin\java.exe -m com.acme.imageapp/com.acme.imageapp.Main
~~~

Exact stdout:

~~~text
RUNTIME_IMAGE_OK module=com.acme.imageapp
~~~

Both runtimes should run the program. Next, measure their sizes and compare their module lists to see where the increase comes from.

## 8. Measure and Compare the Two Runtime Images

Linux/macOS:

~~~bash
du -sh build/runtime-small build/runtime-wide
build/runtime-small/bin/java --list-modules
build/runtime-wide/bin/java --list-modules
~~~

Windows PowerShell:

~~~powershell
$paths = 'build/runtime-small', 'build/runtime-wide'
foreach ($path in $paths) {
    $bytes = (Get-ChildItem -LiteralPath $path -Recurse -Force -File | Measure-Object -Property Length -Sum).Sum
    '{0}: {1:N2} MiB' -f $path, ($bytes / 1MB)
}
.\build\runtime-small\bin\java.exe --list-modules
.\build\runtime-wide\bin\java.exe --list-modules
~~~

Save the results in a build report along with the JDK version and jlink command. If the small runtime fails to run a required feature, add the justified module or resource and re-run the tests.

You can inspect the contents of the module image:

~~~bash
jimage list build/runtime-small/lib/modules
~~~

jimage list helps inspect modules and resources packaged inside the modules file. It does not automatically generate an exact size breakdown per module. To find which modules increase the size, build comparison images by adding or removing groups of modules and compare total sizes.

## 9. Reduce the jpackage Application Payload Size

jpackage creates an application image from the runtime and application files. With --input, **every file in the input directory is packaged**. Therefore, create a staging directory containing only the files that need to be distributed.

Example:

~~~text
app-input/
  imageapp.jar
  lib/
    required-driver.jar
    required-client.jar
  conf/
    application-defaults.properties
  legal/
    THIRD-PARTY-NOTICES.txt
~~~

Do not point --input to the entire project, target directory, build directory, or cache directory. Verify each JAR in lib via the dependency tree and runtime tests before removing it.

Keep licenses, legal notices, sample configurations, and resources required by the product. Do not delete a file simply because its name looks unfamiliar.

### Inspect the Application Input

Linux/macOS:

~~~bash
du -sh app-input
du -h app-input/* | sort -h
find app-input -type f
~~~

Windows PowerShell:

~~~powershell
Get-ChildItem -LiteralPath app-input -Recurse -Force -File |
    Select-Object FullName, Length |
    Sort-Object Length -Descending
~~~

Look for duplicate JAR versions, test artifacts, source archives, Javadocs, and temporary files. If dependencies are packaged separately in lib, verify that the launcher classpath only points to the dependencies actually needed.

## 10. jpackage and the Runtime Module Set

jpackage can invoke jlink itself if no runtime image is provided. How modules are selected depends on the application type:

- Modular application: the runtime image includes the main module and its transitive dependencies.
- Non-modular application running from a main JAR: jpackage uses a default set of modules for classpath applications unless --add-modules is specified.
- You can pass --runtime-image to reuse a custom runtime already created and tested with jlink.

For a non-modular JAR, use jdeps to analyze module dependencies, then specify the appropriate module list with --add-modules. Check reflection, service providers, and native libraries before narrowing down.

Example of creating an application image from a modular app and a custom runtime:

~~~bash
jpackage --type app-image --name ImageApp --module-path mods --module com.acme.imageapp/com.acme.imageapp.Main --runtime-image build/runtime-small --dest build/packages
~~~

An application image contains a launcher, app payload, and runtime. Measure the runtime image, application payload, and total app image separately to see which part takes up space.

### Service Binding in JDK 25+

Starting with JDK 25, runtime images generated by jpackage no longer automatically include service bindings. If the application genuinely needs provider modules discovered via service binding, pass --bind-services through --jlink-options.

Example keeping common default jlink options while enabling service binding:

~~~bash
jpackage --name ImageApp --input app-input --main-jar imageapp.jar --jlink-options "--strip-native-commands --strip-debug --no-man-pages --no-header-files --bind-services"
~~~

When specifying --jlink-options, explicitly list all options you want to keep because the default options list is not automatically merged into the custom value. Enabling --bind-services can increase the module set and size; only use it after verifying ServiceLoader/provider behavior.

## 11. Optimizing Runtime Images in Containers

If the runtime image is copied into an OCI image, inspect all container layers. A small runtime image inside does not guarantee a small final container if the base image or build artifacts remain.

Use a multi-stage build:

~~~dockerfile
FROM eclipse-temurin:26-jdk AS build
WORKDIR /src
COPY . .
RUN ./gradlew --no-daemon clean build
RUN jlink --module-path "$JAVA_HOME/jmods:build/modules" --add-modules com.acme.imageapp --strip-debug --no-header-files --no-man-pages --compress=zip-6 --output /out/runtime

FROM debian:bookworm-slim
WORKDIR /app
COPY --from=build /out/runtime /opt/java
COPY --from=build /src/app-input /app
ENV PATH="/opt/java/bin:$PATH"
ENTRYPOINT ["java", "-m", "com.acme.imageapp/com.acme.imageapp.Main"]
~~~

This is an illustrative structure; build module paths and module names must match the real project. The base image must include the native libraries, libc, CA certificates, and timezone data that the application requires.

Use .dockerignore to avoid sending .git, IDE files, local build caches, test reports, and old outputs into the build context. Do not copy the entire JDK from the build stage to the final stage when the goal is a custom runtime.

Compare container images using layer analysis tools from your registry or build system. Look for large layers, duplicate files, and layers that cannot be eliminated due to COPY ordering. Do not compare tags alone; use immutable image digests to verify promoted artifacts.

## 12. Trade-offs When Reducing Size

| Reduction Technique | Benefit | Risk to Test |
|---|---|---|
| Narrow root modules | Removes unnecessary modules and dependencies | Reflection, ServiceLoader, or rare paths may miss a module |
| Omit jdk.localedata | Reduces locale data | Locale-sensitive formatting, parsing, and collation affected |
| --include-locales | Keeps only supported locales | Locale fallback or libraries may expect other locales |
| --strip-debug | Smaller runtime image | Harder to debug native/JVM runtime content |
| --no-man-pages | Removes CLI documentation | Unsuitable for development-purpose images |
| --no-header-files | Removes C/C++ headers | Unsuitable if the image is used for native compilation |
| --compress=zip-9 | May further reduce disk size | CPU/startup/resource access overhead may increase |
| Omit --bind-services | Reduces provider modules | ServiceLoader may fail to find required providers |
| Trim jpackage --input | Reduces app payload | Missing resources, dependencies, or legal notices |
| Smaller container base | Reduces container footprint | Missing CA certs, libc, or runtime OS dependencies |

There is no single optimal configuration for every application. The theoretically smallest module set is not necessarily the best operational configuration if it sacrifices diagnosability or production support requirements.

## 13. Testing After Optimization

Every time you change modules, locales, service bindings, or resources, run tests on the generated runtime image itself.

### Runtime Validation

~~~bash
build/runtime-small/bin/java --version
build/runtime-small/bin/java --list-modules
build/runtime-small/bin/java --validate-modules
~~~

Verify the Java version, module set, and module resolution. Then run the application using the launcher inside the runtime image.

### Functional Regression

Verify startup/shutdown, all supported commands/entry points, database drivers and JDBC, XML/JSON/compression/crypto, TLS/HTTPS and certificate chains, locale/timezone/date formatting, ServiceLoader/plugins, JNI/native libraries on each OS/architecture, file access/permissions, and logging.

### Performance Regression

Compare before and after for runtime and application image sizes, installer download size, installed footprint, startup time, CPU usage during resource loading/compression, RSS/heap/native memory, and build/package/upload/deploy times.

Only accept an optimization if size decreases while functional and operational requirements are still met.

## 14. Save Reproducible Build Configurations

Do not scatter long jlink commands across multiple scripts without a canonical source. Save an options file:

~~~text
--module-path
mods:/opt/jdk/jmods
--add-modules
com.acme.imageapp
--strip-debug
--no-header-files
--no-man-pages
--compress=zip-6
--output
build/runtime
~~~

Then invoke:

~~~bash
jlink @jlink.options
~~~

Paths in the options file must match the build agent. A jlink options file does not replace metadata; also record the JDK vendor/version, OS, architecture, module list, checksums, and application commit.

You can save the module list generated by jdeps as a build output, but review any changes before releasing. If the module graph changes after upgrading a dependency, inspect it because it may grow the runtime image.

## 15. Anti-Patterns and Fixes

| Anti-pattern | Why It Causes Large Images | Fix |
|---|---|---|
| Always using a full JDK in production | Ships unnecessary compiler and tooling | Use a custom runtime or appropriate runtime base |
| Adding all modules to avoid errors | Pulls in unnecessary dependencies | Run jdeps analysis, review root modules, and test |
| Always enabling --bind-services | May pull in extra provider modules | Enable only when service binding is required |
| Keeping all locales | Increases runtime data | Select only product-supported locales |
| Using low or no compression | Resources occupy more space | Measure zip-6/zip-9 and startup time |
| Passing the entire build directory to --input | Packages tests, sources, logs, and caches | Create a clean staging input directory |
| Packaging both JDK and runtime image in a container | Duplicates runtime across layers | Use multi-stage builds and copy only the custom runtime |
| Removing modules without running tests | Failures only surface in uncovered code paths | Add feature-level regression tests |
| Optimizing for MB without measuring startup | Compression can slow down runtime | Measure footprint and performance together |
| Not recording JDK/options | Image cannot be reproduced | Pin toolchain and save jlink options/provenance |

## 16. Workflow for Handling an Oversized Runtime Image

1. Confirm the sizes of the runtime image, application payload, app image, and installer.
2. Record the JDK vendor/version, OS, architecture, and command line.
3. Measure each directory and file to find what consumes space.
4. Use jdeps to analyze module dependencies of the app and runtime dependencies.
5. Check module descriptors, reflection, ServiceLoader, JNI, and plugins.
6. Compare the current module list against the expected minimal module set.
7. Narrow --add-modules and only include modules with a clear justification.
8. Review --bind-services and jdk.localedata.
9. Apply strip-debug, no-header-files, no-man-pages, and appropriate compression.
10. Create a jpackage input directory containing only necessary runtime files.
11. Inspect container layers if the runtime is placed in an OCI image.
12. Run runtime validation, functional regression, and performance regression tests.
13. Re-measure the same metrics and compare against the baseline.
14. Save options, module list, digests, and test results.
15. Publish the new version and promote the exact tested artifact.

## 17. Optimized Runtime Image Release Checklist

- [ ] Measured runtime, application payload, app image, and installer separately.
- [ ] Identified the largest modules and resources with data.
- [ ] Ran jdeps and reviewed module dependencies.
- [ ] Checked reflection, ServiceLoader, JNI, and dynamic loading.
- [ ] No modules added merely as a general precaution.
- [ ] Reviewed --bind-services.
- [ ] Reviewed jdk.localedata and the locale list.
- [ ] Evaluated strip-debug, no-header-files, and no-man-pages.
- [ ] Compared compression levels on target hardware.
- [ ] jpackage input contains no unnecessary tests, sources, logs, or build caches.
- [ ] Final container does not package duplicate JDK/runtime layers.
- [ ] java --list-modules and --validate-modules pass.
- [ ] Functional regression tests pass on the runtime image.
- [ ] Startup, CPU, RSS, and installed footprint meet requirements.
- [ ] JDK version, options, module list, and digest are recorded.
- [ ] Release artifact is immutable and promoted using the same digest.

## 18. Key Takeaways

- Large runtime images are usually caused by broad root modules, service providers, locale data, or redundant app payloads.
- Measure the runtime image separately from the application image and installer.
- jdeps helps identify module dependencies; review the results because reflection, JNI, and service loading may not appear completely.
- jlink only includes root modules and their transitive dependencies; choose narrow, justified roots.
- --bind-services is useful when the application needs service providers, but it can expand the module set.
- --include-locales requires jdk.localedata and should keep only supported locales.
- --strip-debug, --no-header-files, and --no-man-pages can shrink the runtime image; they do not replace trimming the application payload.
- --compress=zip-6 is the default in JDK 26; zip-9 can be smaller, but measure startup and CPU impact.
- jpackage packages every file in --input; create a staging directory with only distributable files.
- A jpackage app image contains the launcher, application payload, and runtime.
- Starting in JDK 25, jpackage does not automatically include service bindings; enable --bind-services only when the application needs it.
- For containers, use multi-stage builds and inspect every layer to avoid packaging duplicate JDKs.
- Do not trade away features, diagnosability, or security just to hit a target MB number.
- Test on the optimized runtime image itself and promote the same artifact digest.
