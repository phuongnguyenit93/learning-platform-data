# The jps and jcmd Commands: Finding Java Processes and Diagnosing the JVM

## 1. Overview

`jps` and `jcmd` are two command-line tools bundled with the JDK, often used in sequence when you need to inspect a running Java application.

- `jps` (Java Virtual Machine Process Status Tool) lists the HotSpot JVMs detected by the tool on the target machine. It helps find the process ID, main class or JAR name, and certain launch arguments.
- `jcmd` sends diagnostic commands to a running JVM. Once you have identified the right process, you can query the JVM version, command line, VM flags, heap, threads, native memory, or record a Java Flight Recorder (JFR) session.

The typical workflow is to use `jps` to locate the JVM, then use the resulting PID with `jcmd` to inspect specific details. `jps` is primarily for process discovery; `jcmd` performs diagnostics.

Both are JDK tools. If a command is not recognized, check that a JDK is installed and that the JDK's `bin` directory is in your `PATH`.

## 2. Differences Between jps and jcmd

| Criterion | `jps` | `jcmd` |
|---|---|---|
| Purpose | List detected JVMs | Send diagnostic commands to a JVM |
| Primary information | LVMID/PID, class or JAR, optional argument display | Version, VM flags, heap, threads, JFR, and other diagnostic commands |
| Process selection | Options and host identifier | PID or main class name |
| List JVM commands | No | Yes, using `jcmd <pid> help` |
| Heap/thread diagnostics | Not directly | Yes |
| Target machine | Local; can query a remote host via `jstatd` | Must run on the same machine as the target JVM |
| Notes | Experimental, unsupported tool; output may change | Commands and impact depend on the target JVM |

`jps` lists the instrumented HotSpot JVMs that the current user has permission to see. It is not guaranteed to list every Java process on the machine. An application launched with a custom launcher may not display the class/JAR name or arguments as expected.

`jcmd -l` also lists local JVMs, along with their main class and command-line arguments. According to the JDK 24 documentation, this list does not include JVMs running in a separate Docker process. `jcmd` can also send diagnostic commands, whereas `jps` does not.

Do not treat either list as an exhaustive, stable inventory across all environments. Results depend on permissions, how the JVM was launched, namespaces, and the tool version.

## 3. Using jps to Find JVMs

Basic syntax:

~~~bash
jps
~~~

Lists detected JVMs on the current machine. Example:

~~~text
24816 DiagnosticsTarget
39120 jps
~~~

The leading number on each line is the local JVM identifier (LVMID). On HotSpot, this value usually matches the operating-system PID, but the documentation does not guarantee they are always identical across all implementations. Confirm the exact process before using that ID to send diagnostic commands.

Show help:

~~~bash
jps -help
~~~

Print only identifiers:

~~~bash
jps -q
~~~

Show the full class name or JAR path:

~~~bash
jps -l
~~~

Show arguments passed to the `main` method:

~~~bash
jps -m
~~~

Show arguments passed to the JVM:

~~~bash
jps -v
~~~

Options can be combined:

~~~bash
jps -lmv
~~~

Example output when the application is launched with class `demo.DiagnosticsTarget`, two main arguments, and several VM arguments:

~~~text
24816 demo.DiagnosticsTarget alpha beta -Xms32m -Xmx128m -Dapp.mode=diagnostic
~~~

The format and token order may vary by version, launcher, and operating system. Arguments containing spaces also make column-based output parsing unreliable.

`-m` and `-v` serve different purposes:

- `-m` displays the Java program arguments, i.e., the values after the main class or JAR name.
- `-v` displays the arguments used to start the JVM, such as `-Xmx`, `-Dproperty=value`, and other VM options.

The `-q` option is useful when you only need a list of identifiers. For `-V`, check the documentation and behavior of the specific JDK version you are using; `jps` is an experimental and unsupported tool, so you should not rely on rarely used options in scripts.

## 4. Using jcmd to List and Select Processes

List local JVMs:

~~~bash
jcmd -l
~~~

Running without arguments is equivalent:

~~~bash
jcmd
~~~

Example:

~~~text
24816 demo.DiagnosticsTarget alpha beta
39120 jdk.jcmd/sun.tools.jcmd.JCmd -l
~~~

`jcmd -l` shows the PID, main class, and launch arguments. The `jcmd` process itself may appear in the list because it is also a Java process.

Command syntax:

~~~bash
jcmd <pid> <command> [arguments]
~~~

Example:

~~~bash
jcmd 24816 VM.version
~~~

You can use the main class name instead of the PID:

~~~bash
jcmd demo.DiagnosticsTarget VM.version
~~~

When using a class name, the tool sends the command to all processes matching that main class name. If multiple instances of the same class are running, use a specific PID to avoid affecting the wrong process.

PID `0` sends the command to all Java processes accessible to the tool. Do not use `0` in routine operations if you only intend to diagnose a single application.

## 5. Discovering Commands Supported by a JVM

The list of diagnostic commands depends on the JDK version, JVM type, and process configuration. Query the target JVM directly:

~~~bash
jcmd 24816 help
~~~

View the syntax for a specific command:

~~~bash
jcmd 24816 help Thread.print
jcmd 24816 help GC.heap_dump
jcmd 24816 help JFR.start
~~~

The help output provides the description, syntax, options, arguments, and the impact level if the command publishes one.

Common commands:

| Command | Purpose |
|---|---|
| `VM.version` | View the JVM and JDK version |
| `VM.command_line` | View the command line used to launch the JVM |
| `VM.flags` | View the current VM flags |
| `VM.uptime` | View how long the JVM has been running |
| `GC.heap_info` | View summary information about the Java heap |
| `Thread.print` | Print a thread dump |
| `GC.class_histogram` | Show instance statistics by class |
| `GC.heap_dump` | Generate a heap dump |
| `VM.native_memory` | View Native Memory Tracking if enabled |
| `JFR.start` / `JFR.check` / `JFR.dump` / `JFR.stop` | Manage JFR recordings |

Example basic inspection commands:

~~~bash
jcmd 24816 VM.version
jcmd 24816 VM.command_line
jcmd 24816 VM.flags
jcmd 24816 GC.heap_info
~~~

Read `help <command>` before running any command that may create large files, trigger GC, or affect performance.

## 6. Complete Java 17 Example: Find with jps, Inspect with jcmd

Create `src/demo/DiscoveryTarget.java`:

~~~java
package demo;

/** A process used to practice jps and jcmd. */
public final class DiscoveryTarget {
    /**
     * Keeps the JVM alive for local diagnostics.
     *
     * @param args command-line arguments
     * @throws InterruptedException if the sleep is interrupted
     */
    public static void main(String[] args) throws InterruptedException {
        System.out.println("READY");
        System.out.println("args=" + String.join(",", args));

        Thread.sleep(120_000);
    }
}
~~~

Compile:

~~~bash
javac --release 17 -d out src/demo/DiscoveryTarget.java
~~~

Open Terminal 1 and run:

~~~bash
java -Xms32m -Xmx128m -Dapp.mode=diagnostic \
    -cp out demo.DiscoveryTarget alpha beta
~~~

Exact stdout:

~~~text
READY
args=alpha,beta
~~~

The process continues running while you inspect it in Terminal 2.

Step 1: find the JVM:

~~~bash
jps -l
~~~

Locate the line with `demo.DiscoveryTarget` and note the actual identifier/PID.

Step 2: inspect program and JVM arguments:

~~~bash
jps -m
jps -v
~~~

Step 3: confirm the process using `jcmd`'s list:

~~~bash
jcmd -l
~~~

Step 4: send diagnostic commands to the exact PID:

~~~bash
jcmd <pid> VM.version
jcmd <pid> VM.command_line
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print -l
~~~

In the thread dump, the example's `main` thread will be in the `TIMED_WAITING` state because it is sleeping in `Thread.sleep`.

When finished, return to Terminal 1 and press Ctrl+C to stop the application. The PID changes on every run; do not copy example PIDs into real commands.

## 7. Capturing Thread Dumps and Inspecting the Heap

After finding the right PID with `jps`, use `jcmd` to inspect threads:

~~~bash
jcmd <pid> Thread.print
~~~

Include lock information:

~~~bash
jcmd <pid> Thread.print -l
~~~

Thread dumps show which threads are running, waiting on a monitor, waiting on a condition, or blocked. When investigating hung requests or deadlocks, capture multiple dumps spaced at a reasonable interval and compare stack traces and locks. A single dump only captures a point-in-time snapshot.

Inspect the heap:

~~~bash
jcmd <pid> GC.heap_info
~~~

Object statistics by class:

~~~bash
jcmd <pid> GC.class_histogram
~~~

Create a heap dump:

~~~bash
jcmd <pid> GC.heap_dump /var/tmp/application-heap.hprof
~~~

`GC.class_histogram` and `GC.heap_dump` can have high impact depending on heap size; a heap dump may also trigger a full GC, consume significant disk space, and contain sensitive data. Run them only with a clear objective, after verifying available disk space and output permissions.

## 8. Recording JFR After Identifying the PID

You can use `jcmd` to start a time-bounded recording:

~~~bash
jcmd <pid> JFR.start name=diagnostic settings=default duration=60s filename=diagnostic.jfr
~~~

Check active recordings:

~~~bash
jcmd <pid> JFR.check
~~~

Dump a snapshot while the recording is still running:

~~~bash
jcmd <pid> JFR.dump name=diagnostic filename=diagnostic-snapshot.jfr
~~~

Stop the recording:

~~~bash
jcmd <pid> JFR.stop name=diagnostic
~~~

`settings=default` is generally suitable for monitoring with lower overhead; `settings=profile` collects more data and may increase overhead. Read `help JFR.start` on the target JVM to check options and impact. Choose an output directory writable by the user running the JVM, then analyze the `.jfr` file with Java Mission Control or a compatible tool.

## 9. Local, Remote, and Container Limitations

### jps

By default, `jps` searches for instrumented HotSpot JVMs on the local machine. It only reports JVMs that the running user has permission to access. A JVM started with a custom launcher may display `Unknown` instead of the class/JAR name or main arguments.

`jps` can accept a host identifier to query a remote host. This requires the `jstatd` service running on the target host and appropriate access permissions. `jps` is marked by Oracle as experimental and unsupported; remote mode should not be treated as a stable administrative protocol.

### jcmd

`jcmd` must run on the same machine as the target JVM and typically requires the same effective user/group identifiers used to launch the JVM. It is not a command for sending diagnostics over the network to a PID on another host.

The JDK 24 documentation states that `jcmd -l` does not list JVMs running in a separate Docker process. In containers, determine the PID from the appropriate PID namespace and run the tool in an environment that can attach to that JVM. Do not take a PID from the host namespace and assume it matches the PID inside the container.

### Attach Permissions

A JVM can disable the attach mechanism with `-XX:+DisableAttachMechanism`. In that case, `jcmd` cannot attach through the normal mechanism. Some security or container environments also restrict attach access.

## 10. Security and Operational Considerations

`jps -v`, `jcmd VM.command_line`, and `jcmd VM.system_properties` can expose sensitive information if an application places tokens, passwords, or internal data in command-line arguments or system properties. Review and redact output before sharing it.

Diagnostic commands also vary in cost. `Thread.print` and `GC.heap_info` are usually safe starting points; `GC.class_histogram` and `GC.heap_dump` can have significant impact. You can check the published impact level with:

~~~bash
jcmd <pid> help <command>
~~~

Operational guidelines:

- Confirm the exact PID before sending a command.
- Use a specific PID instead of a class name when multiple instances exist.
- Avoid PID `0` unless you intentionally want to send a command to every attachable JVM.
- Read `help` and the impact level before running an unfamiliar command.
- Check disk space, permissions, and data sensitivity for dump and recording files.
- Record the timestamp, PID, JDK version, and command executed so results can be correlated.

## 11. Common Errors and Troubleshooting

### jps Does Not Find the Application

Verify that the application is still running, the user has permission to see the JVM, the JVM is an instrumented HotSpot JVM, and the process is not in another namespace or container. `jps` does not guarantee listing every Java process.

### jps Only Shows a Short Name or Unknown

Use `jps -l` to see the full class name or JAR path. With custom launchers, the class/JAR name and main arguments may not be provided.

### jps Output Is Hard to Parse in Scripts

The output format can change and arguments may contain spaces. Oracle documentation recommends not writing scripts that depend on parsing `jps` output. For automation, prefer process management or metrics mechanisms suited to your environment rather than parsing unstable text output.

### jcmd Cannot Attach

Verify the PID, machine, user/group, container namespace, and attach mechanism. Check whether the JVM was launched with `-XX:+DisableAttachMechanism`.

### Unknown Diagnostic Command

The command may not be supported by that JVM. Run `jcmd <pid> help` to see the actual list of supported commands and `jcmd <pid> help <command>` to check its syntax.

### JVM Missing from jcmd -l Even Though the Process Is Running

If the JVM is inside a separate Docker process, `jcmd -l` may not list it. Identify the PID in the appropriate namespace and run `jcmd` from an environment that can attach to that process.

### Cannot Attach Using the PID from jps

The LVMID is usually, but not always, the OS PID. Verify the process using operating-system tools and attach from the right machine/namespace and user.

## 12. Recommended Diagnostic Workflow

When a Java application appears hung or shows abnormal memory usage:

1. Run `jps -l` to find the class/JAR name and identifier.
2. Run `jps -m` and `jps -v` if you need to inspect main arguments and VM arguments.
3. Use `jcmd -l` to cross-check the local JVM list.
4. Select the specific PID and run `jcmd <pid> help`.
5. Start with `VM.version`, `VM.command_line`, `VM.flags`, and `GC.heap_info`.
6. If stuck threads are suspected, use `Thread.print -l` and compare dumps over time.
7. If time-series data is needed, collect a short JFR recording with appropriate settings.
8. Only generate a histogram or heap dump after evaluating impact, disk space, and permissions.
9. Save the output along with the timestamp, PID, JDK version, and incident context.

Do not run every command in a fixed sequence in production. Choose commands based on the hypothesis being tested and the impact reported by the JVM.

- [ ] Use a JDK that includes `jps` and `jcmd` in its `bin` directory.
- [ ] Use `jps -l` to identify the main class or JAR.
- [ ] Use `jps -m` and `jps -v` to distinguish main arguments from VM arguments.
- [ ] Use `jps -q` when only identifiers are needed.
- [ ] Remember that `jps` only lists instrumented JVMs you have permission to access, and is experimental/unsupported.
- [ ] Do not write scripts that depend on the text format of `jps` output.
- [ ] Use `jcmd -l` to cross-check local JVMs.
- [ ] Use a specific PID with `jcmd` when multiple instances are running.
- [ ] Use `jcmd <pid> help` to discover supported commands.
- [ ] Verify the right machine, user/group, attach mechanism, and container namespace.

- [ ] Protect outputs that may contain command lines, system properties, heap data, or recordings.

`jps` helps you find detected JVMs; `jcmd` helps you inspect and diagnose them. Combining them in order—locating the right process, confirming the PID, discovering available commands, and collecting targeted data—makes troubleshooting clear and repeatable.
