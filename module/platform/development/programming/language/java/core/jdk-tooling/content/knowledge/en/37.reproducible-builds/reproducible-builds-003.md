# Pinning Compiler Release in Java and Maven

Pinning the compiler release means fixing the Java version that the source code is allowed to use and for which class files are generated. In Maven, the common configuration is the maven.compiler.release property combined with an explicitly pinned version of maven-compiler-plugin.

For example, a project sets release 17. The compiler will check Java 17 syntax, allow only APIs belonging to the Java 17 platform, and produce bytecode that can run on Java 17 or later. As a result, developers using a newer JDK can still build an application targeting an agreed-upon Java release.

It is necessary to distinguish three things: the target release of the source, the actual JDK running the compiler, and the JDK running the application/tests. Pinning the release does not automatically pin the other two JDKs. For a stable build, all three must be managed.

## 1. What is compiler release?

The Java compiler can compile source code according to a specific Java release. The release determines:

- The accepted Java syntax and language rules.
- The set of Java SE/JDK APIs allowed to be referenced.
- The class-file version generated by the compiler.

For example, when using JDK 24 to compile with release 17, the compiler must reject syntax introduced only in Java 21 or later, disallow source code from using APIs newer than Java 17, and generate class files with major version 61.

This is the cross-compilation mechanism: using the compiler of a newer JDK to produce output compatible with an older release supported by that compiler.

Release values under the modern Java version scheme are integers such as 8, 11, 17, 21, or 24. For Java 8, write 8, not 1.8.

## 2. Why pin the compiler release?

If the release is not pinned, the compiler may default to the JDK running Maven. When developers upgrade their JDK, new source code can accidentally use new syntax or APIs; artifacts may also be generated with a higher class-file version.

Common consequences:

- The application runs on the developer's machine but fails with UnsupportedClassVersionError in production.
- Source code uses APIs that only exist in a JDK newer than the deployment environment.
- Modules in the same project produce bytecode at different Java levels.
- CI and developer machines accept different source code.
- Upgrading the JDK unintentionally changes the compatibility target.

Pinning the release gives the entire project a clear compatibility contract. CI can enforce this contract and fail immediately when source code exceeds the allowed Java level.

## 3. Distinguishing release, source, target, and compiler JDK

These are four concepts that must be kept separate:

| Configuration | What does it control? |
|---|---|
| Compiler JDK | The actual javac version compiling the source |
| source | The Java syntax/language accepted by the compiler |
| target | The class-file version generated by the compiler |
| release | Combines language rules, class-file target, and the published APIs for that release |

Before Java 9, projects commonly used source and target. These two parameters do not automatically restrict the APIs available in the JDK used for compilation.

For example, using JDK 17 with source 8 and target 8 while calling String.strip() can still compile, because this method exists in JDK 17. The resulting class file may carry the Java 8 version, but running on Java 8 will fail with NoSuchMethodError when calling the non-existent API.

With javac from JDK 9 onward, release should be used. This option checks the APIs of the target release as well, catching compatibility errors earlier.

## 4. How does javac --release work?

The --release option was introduced in JDK 9. It instructs javac to:

1. Apply the language rules of the selected release.
2. Generate class files targeting that release.
3. Compile against the Java SE and JDK APIs published for that release.
4. Disallow using internal APIs or APIs that only appear in newer releases.

Example compiling Java 17:

~~~powershell
javac --release 17 -d out src\main\java\demo\App.java
~~~

Example compiling Java 8 using a newer JDK compiler:

~~~powershell
javac --release 8 -d out src\main\java\demo\App.java
~~~

The compiler only accepts releases supported by the current JDK. Check the list with:

~~~powershell
javac --help
~~~

You cannot use --release simultaneously with --source or --target. javac also does not allow using --add-exports to expand system APIs while --release is in use. This helps preserve the exact API boundary of the target platform.

## 5. Why are source and target alone not enough?

Suppose a project must run on Java 8 while the compiler is running on JDK 17.

Old configuration:

~~~xml
<configuration>
  <source>8</source>
  <target>8</target>
</configuration>
~~~

This configuration sets Java 8 syntax and Java 8 class-file target. However, the compiler still sees the APIs of JDK 17. Source code can call methods that do not exist in Java 8.

Example:

~~~java
public final class ApiCheck {
    public String normalize(String value) {
        return value.strip();
    }
}
~~~

String.strip() was added in Java 11. When compiled with JDK 17 using source 8/target 8, the new API can still be referenced. Running on Java 8 will fail when executing that code path.

If you use:

~~~powershell
javac --release 8 ApiCheck.java
~~~

the compiler reports that the strip() method cannot be found in Java 8's String. This is the most important benefit of release over source/target.

## 6. Configuring Maven Compiler Plugin

Maven Compiler Plugin has supported the release parameter since version 3.6.0. You should pin the plugin version so that every build machine uses the same configuration and behavior.

Example POM:

~~~xml
<properties>
  <maven.compiler.release>17</maven.compiler.release>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.13.0</version>
      <configuration>
        <release>${maven.compiler.release}</release>
      </configuration>
    </plugin>
  </plugins>
</build>
~~~

The maven.compiler.release property is the single place storing the project's Java target. The release configuration in the plugin references that property to avoid duplicating the version number.

You can set only the property without declaring release directly because the Compiler Plugin recognizes the maven.compiler.release user property. However, explicitly declaring the plugin version is still very important; you should not rely on the default version from the Super POM.

## 7. Pinning plugin version and managing it in the parent POM

A multi-module project should place the release and plugin version in the parent POM so that modules inherit the same policy.

Example:

~~~xml
<properties>
  <maven.compiler.release>17</maven.compiler.release>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>

<build>
  <pluginManagement>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.13.0</version>
        <configuration>
          <release>${maven.compiler.release}</release>
          <encoding>${project.build.sourceEncoding}</encoding>
        </configuration>
      </plugin>
    </plugins>
  </pluginManagement>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
    </plugin>
  </plugins>
</build>
~~~

pluginManagement manages the version and default configuration. The plugin still must be declared in build/plugins in the parent or in the modules where it needs to run; placing it only in pluginManagement does not automatically activate the plugin.

For a multi-module project, keep a single release value in the parent unless a module genuinely requires a different Java level. If a module overrides release, document the reason clearly and check dependencies between modules.

## 8. Release affects both main source and test source

Maven Compiler Plugin has two main goals:

- compiler:compile compiles source code in src/main/java.
- compiler:testCompile compiles source code in src/test/java.

The shared release configuration in the plugin applies to both goals. This keeps test source at the same language and API level as production source, unless the project intentionally configures separate executions.

Do not let test source use newer APIs just because the CI machine has a newer JDK. Tests may pass on CI while masking compatibility errors with the target Java runtime.

If tests need a specific JDK runtime, configure Surefire/Failsafe or Maven Toolchains separately. Compiler release only controls compilation; it does not choose the JVM running tests.

## 9. Release does not pin the compiler JDK

Suppose two machines both configure release 17:

- Machine A uses javac from JDK 17.
- Machine B uses javac from JDK 24.

Both can produce class files with major version 61 and use only Java 17 APIs. However, compiler implementation, optimizations, bug fixes, and bytecode generation may differ across JDK patches/vendors.

Therefore, pinning release guarantees the compatibility target of source and bytecode; it does not guarantee byte-for-byte identical artifacts.

If strict reproducible builds are required, additionally pin:

- JDK vendor and version/patch.
- Maven distribution.
- Maven Compiler Plugin version.
- Annotation processors and their dependencies.
- Actual compiler toolchain.
- Other plugins involved in producing artifacts.

Maven Compiler Plugin by default uses the javac of the JDK running Maven. You can select a different compiler JDK using Maven Toolchains when needed. Always check the logs to confirm which toolchain is used.

## 10. Distinguishing compiler release from test/runtime JDK

A release 17 configuration can be built on JDK 24 and produce Java 17 bytecode. However, the mvn test command may run tests in Maven's JVM or another forked JVM.

Cases:

| Component | Example version |
|---|---|
| Maven runtime JDK | 24 |
| Compiler toolchain JDK | 24 |
| Compiler release | 17 |
| Surefire forked test JDK | 17 |
| Production runtime | 17 |

Release 17 does not automatically switch Surefire to Java 17. If Surefire does not fork, tests run in the Maven JVM; if it forks, the test JVM depends on plugin/toolchain configuration.

When you need to guarantee runtime compatibility, run tests on the exact target Java release or use a CI matrix with the supported JDKs. Check Runtime.version() in tests to verify the executing JVM.

## 11. Java version and class-file major version

Each Java release has a corresponding class-file major version. Some common milestones:

| Java release | Class-file major version |
|---|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |
| Java 24 | 68 |

If a class is generated with major version 65, a Java 17 JVM cannot load that class. If the compiler uses release 17, the class file must have major version 61.

Check with javap:

~~~powershell
javap -verbose target\classes\demo\App.class | Select-String "major version"
~~~

Expected output for release 17:

~~~text
major version: 61
~~~

Class-file version is a useful check, but it does not prove API compatibility on its own. You need to use release during compilation to check APIs, and test on the actual runtime to verify behavior.

## 12. Complete Maven example: pinning Java 17

Create the structure:

~~~text
pin-release-demo/
  pom.xml
  src/
    main/
      java/
        demo/
          App.java
~~~

Create pom.xml:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
         https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.example</groupId>
  <artifactId>pin-release-demo</artifactId>
  <version>1.0.0</version>

  <properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-clean-plugin</artifactId>
        <version>3.4.0</version>
      </plugin>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-resources-plugin</artifactId>
        <version>3.3.1</version>
      </plugin>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.13.0</version>
        <configuration>
          <release>${maven.compiler.release}</release>
          <encoding>${project.build.sourceEncoding}</encoding>
        </configuration>
      </plugin>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-surefire-plugin</artifactId>
        <version>3.2.5</version>
      </plugin>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-jar-plugin</artifactId>
        <version>3.4.2</version>
        <configuration>
          <archive>
            <manifest>
              <mainClass>demo.App</mainClass>
            </manifest>
          </archive>
        </configuration>
      </plugin>
    </plugins>
  </build>
</project>
~~~

Create src/main/java/demo/App.java:

~~~java
package demo;

public final class App {
    private App() {
    }

    public static void main(String[] args) {
        System.out.println("Compiler release pinned to Java 17.");
    }
}
~~~

Build:

~~~powershell
mvn clean package
~~~

Run the JAR:

~~~powershell
java -jar target\pin-release-demo-1.0.0.jar
~~~

Stdout:

~~~text
Compiler release pinned to Java 17.
~~~

Check the class-file version:

~~~powershell
javap -verbose target\classes\demo\App.class | Select-String "major version"
~~~

Output:

~~~text
major version: 61
~~~

If Maven runs on JDK 24, the build still produces Java 17 bytecode thanks to release 17. Running the JAR on Java 17 will print the exact same output line as above.

## 13. Checking the actual compiler release in Maven

Use the following commands to inspect the configuration:

~~~powershell
mvn -version
mvn help:effective-pom
mvn help:evaluate -Dexpression=maven.compiler.release -q -DforceStdout
mvn -X clean verify
~~~

Each command answers a question:

- mvn -version: Which JDK is Maven running on?
- help:effective-pom: What is the effective compiler configuration after parent/profile inheritance?
- help:evaluate: What is the final resolved value of release in Maven?
- -X: How does the plugin receive configuration and invoke the compiler?

Do not look only at the source POM, because parent POMs, profiles, and command-line properties can override values. Check the effective POM and logs on the exact CI job that produces the artifact.

## 14. Using Maven Enforcer and CI to prevent misconfiguration

If an organization requires Maven to run on a specific JDK, use Maven Enforcer Plugin to check the runtime. Example:

~~~xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-enforcer-plugin</artifactId>
  <version>3.6.3</version>
  <executions>
    <execution>
      <id>enforce-java-runtime</id>
      <goals>
        <goal>enforce</goal>
      </goals>
      <configuration>
        <rules>
          <requireJavaVersion>
            <version>[17,18)</version>
          </requireJavaVersion>
        </rules>
      </configuration>
    </execution>
  </executions>
</plugin>
~~~

The example above requires the Maven runtime to use Java 17. If policy allows JDK 21 or 24 as the compiler while still producing release 17, do not use this range; replace it with an appropriate range or pin the compiler toolchain separately.

In CI:

1. Use Maven Wrapper to pin the Maven distribution.
2. Provision the compiler JDK according to policy.
3. Read release from the POM/parent POM.
4. Run clean verify.
5. Check the class-file major version of the artifact.
6. Run tests on the Java runtimes that the product claims to support.
7. Save JDK, Maven, and compiler configuration logs along with the build.

Do not let environment variables or -D parameters change maven.compiler.release unintentionally.

## 15. Annotation processors and generated source

Annotation processors run in the compiler JDK environment. The target release restricts the compiled source and the platform APIs that code may use, but it does not automatically restrict the runtime APIs used by the annotation processor itself.

If a processor generates source:

- Pin the version of the processor and its dependencies.
- Check whether generated source uses syntax/APIs newer than the release.
- Fix the inputs and processing order.
- Do not write timestamps, usernames, absolute paths, or random values into generated source.
- Verify that generated source is compiled in the same execution with the pinned release.

A build can pin the compiler release properly and still produce different outputs if an annotation processor changes or depends on the environment.

## 16. Preview features and the module system

Preview features are tied to a specific Java release. When preview is enabled, both compiler and runtime must satisfy the requirements of the corresponding release; preview bytecode is not a stable compatibility target across versions.

If using preview, you must configure the --enable-preview compiler argument and configure the test/runtime JVM accordingly. Only enable preview when the project truly needs it, because it tightens version requirements and reduces portability across other runtimes.

With the module system, release also controls the APIs/modules of the target release. You cannot use --add-exports to expand system APIs when javac is using --release. If an application depends on JDK internal APIs, replace them with supported APIs rather than trying to break compatibility boundaries.

## 17. Java 8 and the limits of --release

JDK 8 does not have javac --release. This option was only introduced in JDK 9.

Maven Compiler Plugin 3.13.0 with the default compilerId javac can accept a release configuration when running on JDK 8 and translate it to the corresponding source/target. On JDK 9 and later, the plugin uses javac --release.

This does not turn JDK 8 into a compiler capable of checking APIs against an older JDK. If using JDK 8 to target Java 8, the APIs seen by the compiler are Java 8 APIs themselves. If you need to target a version lower than the JDK in use and need accurate API checking, prefer JDK 9+ with --release or provide the appropriate platform API/boot class path when source/target must be used.

Do not assume every compilerId or every Maven Compiler Plugin version has the same fallback. Check the documentation for the exact plugin version.

## 18. Common errors

| Symptom | Cause | Resolution |
|---|---|---|
| UnsupportedClassVersionError | Class file is newer than the runtime JVM | Pin release to the Java level supported in production |
| Code using newer APIs still compiles | Only source/target were set | Use release with JDK 9+ |
| Unknown option --release | Running javac from JDK 8 or older | Upgrade the compiler JDK or use compatible configuration |
| Maven ignores the release property | Compiler Plugin is too old or configuration is overridden | Pin plugin to 3.6+ and inspect the effective POM |
| One module has different bytecode from another | Module does not inherit the same parent/config | Centralize release in the parent and check modules |
| Tests compile but fail at runtime | Test/runtime JDK differs from target | Run tests on the right runtime or a CI matrix |
| Newer APIs appear in generated code | Annotation processor/generator is incompatible with release | Pin processor and inspect generated source |
| Local build differs from CI | Different JDK/toolchain/plugin versions | Record and pin compiler JDK, Maven, and plugins |
| Preview feature fails to run | Compiler/runtime release mismatch or missing enable-preview | Use the same release and configure preview on both sides |

### 18.1. Diagnostic workflow

1. Run mvn -version to identify the JDK running Maven.
2. Check maven.compiler.release in the effective POM.
3. Check the Maven Compiler Plugin version.
4. Read compiler logs to identify the actual JDK/toolchain.
5. Use javap -verbose to check the major version.
6. Search for APIs newer than release in source and generated source.
7. Check the runtime JDK of Surefire/Failsafe.
8. Reproduce the build using the exact Maven/JDK/toolchain from CI.

## 19. Best practices when pinning compiler release

- Choose a Java release matching the production runtime.
- Set maven.compiler.release in the parent POM.
- Explicitly pin the Maven Compiler Plugin version.
- Do not configure release together with source/target on JDK 9+.
- Use a newer compiler JDK only when the target release is supported.
- Pin the compiler JDK with Toolchains if reproducible bytecode is needed.
- Check both main source and test source.
- Run tests on the actual supported Java runtime.
- Pin annotation processors and code generators.
- Verify the effective POM and class-file major version in CI.
- Avoid changing release via uncontrolled command-line properties.
- Record Maven/JDK/plugin versions in build metadata.

## 20. Checklist for pinning compiler release

- [ ] Target Java release selected based on the production runtime.
- [ ] maven.compiler.release set in the POM/parent POM.
- [ ] maven-compiler-plugin version pinned.
- [ ] Compiler Plugin supports the release parameter.
- [ ] source/target are not set together with release on JDK 9+.
- [ ] Understood that the actual compiler JDK may differ from the target release.
- [ ] Maven Toolchains used if a separate compiler JDK must be pinned.
- [ ] Main source and test source use release consistently.
- [ ] Surefire/Failsafe run on a defined runtime.
- [ ] Annotation processors and generated source checked.
- [ ] Preview features are not enabled unintentionally.
- [ ] Effective POM and Maven debug logs inspected.
- [ ] Class-file major version matches the target release.
- [ ] CI has a step checking compiler/runtime compatibility.
- [ ] Artifact tested on the lowest supported Java runtime.

Pinning the compiler release establishes a clear compatibility contract for source and bytecode. In Maven, set maven.compiler.release, pin Maven Compiler Plugin, and verify the class-file version. When byte-for-byte reproducible builds are needed, also pin the compiler JDK, Maven, plugins, and annotation processors; when ensuring the application runs properly, test on the actual Java runtime. Release, compiler JDK, and test/runtime JDK must be tracked as three separate configurations.
