# Missing Process in jps

## 1. Symptoms and Meaning

Running **jps** and not seeing an active Java application, or seeing only the **jps** process itself in the list, is a common situation when diagnosing a JVM.

**jps** (Java Virtual Machine Process Status Tool) is a JDK command-line tool used to list instrumented HotSpot JVMs on a target machine. The tool only displays JVMs that the account running the command has permission to access. Therefore, jps output is not a complete list of every Java-containing process across the entire operating system.

Common causes:

- The application has stopped or is running on a different machine, container, or environment.
- jps is being run under a different account than the one that started the application.
- The JVM does not provide the performance data required for discovery.
- The application is inside Docker, WSL, or a separate process namespace.
- The machine is using a different JVM implementation or a custom launcher with different behavior.
- The wrong jps from another JDK or an incomplete installation is being invoked.

Distinguish between **not finding a JVM** and **finding a JVM without displaying the expected class/JAR name**. If the application uses a custom launcher, jps may display Unknown for the class or JAR name; that does not mean the process has disappeared.

## 2. Understanding jps Limitations

According to Oracle documentation, jps lists instrumented HotSpot JVMs on the target system and only reports JVMs that the user running the command has access rights to. This tool is marked experimental/unsupported; the output format may change between JDK versions.

Limitations to keep in mind:

- jps focuses on instrumented HotSpot JVMs, not a listing of all operating system processes.
- The list is restricted by the access permissions of the current account.
- By default, the command searches for JVMs on the local host. Querying a remote host requires configuring jstatd on the target machine.
- The LVMID (local VM identifier) usually matches the OS PID, though this is not guaranteed in all cases.
- With a custom launcher, the class/JAR name and main arguments may appear as Unknown.
- Do not write scripts that depend on column layout or parse jps output as a stable API.

If jps does not show a process, verify the process at the operating system level before concluding that the application is not running.

Reference: [The jps Command — Java SE 26](https://docs.oracle.com/en/java/javase/26/docs/specs/man/jps.html).

## 3. Verifying Which JDK Tool Is Being Invoked

A machine may have multiple JDKs installed. A terminal, IDE, service, or script may invoke different jps binaries.

Windows PowerShell:

```powershell
Get-Command java -All
Get-Command jps -All
$env:JAVA_HOME
java -version
jps --help
```

Linux:

```bash
command -v java
command -v jps
echo "$JAVA_HOME"
java -version
jps --help
```

macOS:

```bash
command -v java
command -v jps
/usr/libexec/java_home -V
java -version
jps --help
```

If jps is not recognized:

1. Check whether a full JDK is installed or only a stripped-down runtime.
2. Check whether the `bin` directory of the right JDK is in PATH.
3. Use the direct path to jps in the JDK you want to inspect.
4. Compare the JDK vendor and version used to run the application with the JDK used to run diagnostic tools.

Do not assume that the terminal's JAVA_HOME is the same JDK used by a Windows service, systemd unit, IDE, or container.

## 4. Using jps Options to Expand Information

When the basic command does not provide enough information, try each option:

| Command | Information Displayed |
|---|---|
| **jps** | LVMID and short class/JAR name |
| **jps -q** | LVMID only |
| **jps -l** | Full class name or JAR path |
| **jps -m** | Arguments passed to main() |
| **jps -v** | JVM arguments |

Examples:

```bash
jps
jps -q
jps -l
jps -m
jps -v
```

Sample output:

```text
24801 com.example.Main
25120 jdk.jcmd/sun.tools.jps.Jps
```

The numbers in the output change with each run. Seeing jps itself in the list is normal because the tool itself runs on a JVM.

How to read the output:

- If jps lists a process but jps -l shows a different name, check the actual module/class/JAR.
- If the name is Unknown, check for a custom launcher or how the application is launched.
- If jps -q shows an ID but no application name appears in other output, verify the ID using OS tools.
- If only the jps process appears, that only proves the current tool sees itself; it does not prove all other JVMs have stopped.

Security note: -m and -v can expose startup arguments. Avoid sharing output without redacting tokens, passwords, or internal paths.

## 5. Checking Whether the Application Is Actually Running

Before changing Java configuration, look for the process using operating system tools. This helps distinguish a stopped process from a running JVM that jps cannot list.

### 5.1. Windows PowerShell

Use CIM to inspect the PID, executable name, path, and command line:

```powershell
Get-CimInstance Win32_Process |
    Where-Object { $_.Name -in @('java.exe', 'javaw.exe') } |
    Select-Object ProcessId, Name, ExecutablePath, CommandLine
```

If the application runs through a service wrapper or native launcher, the executable name may not be java.exe/javaw.exe. In that case, check the corresponding service in Services or query the process by the wrapper's name.

### 5.2. Linux

```bash
ps -eo pid,user,args | grep -E '[j]ava(w)?'
pgrep -af java
```

Check the PID, owning user, and command line. If the service is managed by systemd, inspect the service status and ExecStart configuration:

```bash
systemctl status <service-name>
systemctl show <service-name> -p MainPID -p User -p ExecStart
```

### 5.3. macOS

```bash
ps -axo pid,user,command | grep -E '[j]ava(w)?'
pgrep -fl java
```

If the application is started by a custom launcher, look for the parent process or the service managing the application instead of filtering only for the string `java`.

### 5.4. Interpreting the Results

- No related process: check the service, startup logs, schedule, and startup errors.
- Java process exists but jps does not list it: proceed to check user, perfdata, JVM implementation, and container.
- Native launcher process with an embedded JVM exists: jps may see it if the HotSpot JVM is instrumented and permissions allow; filtering by `java.exe` or the string `java` may miss this type of process.
- PID has changed: the application may have just restarted; use the current PID instead of a PID saved from a previous check.

## 6. Cause 1: Running jps Under a Different Account

This is a common cause in server environments.

For example, the application runs under a service account `appuser`, while the administrator runs jps under a personal account. Operating system access controls may prevent that account from seeing `appuser`'s JVM.

How to check:

```bash
ps -eo pid,user,args | grep -E '[j]ava(w)?'
id
```

If you confirm the service runs under `appuser`, run the diagnostic command under that same account in accordance with system policy:

```bash
sudo -u appuser jps -l
```

On Windows, identify the account running the Windows service and perform diagnostics using an account with appropriate access rights. If administrative privileges are required, follow your organization's authorization policy.

Do not default to running every tool as root or Administrator. Elevated privileges do not automatically resolve mismatches in user, namespace, or instrumentation settings.

## 7. Cause 2: Performance Data Is Disabled or Inaccessible

HotSpot has a performance data mechanism for monitoring tools. The JVM option -XX:+UsePerfData is enabled by default. If an application is started with -XX:-UsePerfData, the JVM does not create the `hsperfdata_<userid>` directories used for performance data.

Check the command line and service configuration for this option:

```bash
jps -v
```

If the PID is already known:

```bash
jcmd <PID> VM.command_line
```

If the configuration includes -XX:-UsePerfData, verify why the option was enabled. When operational policy allows and monitoring tools require performance data, you can remove the disabling option or explicitly re-enable it with -XX:+UsePerfData, then restart the JVM according to your deployment plan.

Notes:

- Changing JVM flags typically requires restarting the process.
- Do not modify production flags without assessing the impact and operational policy.
- Do not manually delete performance data files or directories of a running JVM.
- On Linux, check permissions on the temporary/perfdata directory and the filesystem hosting them.
- If using a different build or non-HotSpot JVM, check the vendor's specific documentation.

Source: [The java Command — Java SE 26](https://docs.oracle.com/en/java/javase/26/docs/specs/man/java.html).

## 8. Cause 3: JVM Is Inside Docker or Another Process Namespace

Running jps on the host will not necessarily see a JVM running inside a Docker container with its own process namespace. Running jcmd -l on the host also does not list JVMs in separate Docker process namespaces according to the JDK documentation.

Check from inside the container:

```bash
docker ps
docker exec <container-name> jps -l
docker exec <container-name> ps -ef
```

If the image only contains a JRE or lacks JDK tools, jps may not exist. In that case, use `ps` inside the container or inspect the PID through the container runtime.

For Kubernetes:

```bash
kubectl get pods -n <namespace>
kubectl exec -n <namespace> <pod-name> -- jps -l
kubectl exec -n <namespace> <pod-name> -- ps -ef
```

If you need to use jcmd, run it in the same container environment and as a user compatible with the JVM:

```bash
docker exec <container-name> jcmd <PID> VM.version
```

The PID visible from the host may differ from the PID inside the container. Do not copy PIDs across namespaces without verifying the exact process mapping.

For WSL or VMs, run jps in the same operating system environment where the JVM is running. A command on the Windows host does not automatically list JVMs inside Linux WSL or a separate VM.

## 9. Cause 4: Checking the Wrong Machine or Environment

jps does not automatically scan all servers on a network. If the application runs on another host, run the command directly on the target host, for example over SSH:

```bash
ssh <user>@<host> 'jps -l'
```

Oracle also supports `hostid` for remote queries:

```bash
jps -l <hostname>
```

This requires jstatd to be running on the target machine with the appropriate registry/port and the caller having access rights. Only configure remote monitoring when approved and with appropriate network access controls in place.

If remote jstatd is not needed, running jps over SSH on the target host itself is usually easier to control.

## 10. Cause 5: Using a Non-HotSpot JVM or Custom Launcher

jps is documented for instrumented Java HotSpot VMs. If the application uses Eclipse OpenJ9 or another JVM implementation, listing capabilities and bundled tools may differ. Use the appropriate tools provided by the runtime vendor.

Check the application's runtime information if you have identified the PID or startup logs:

```bash
java -version
jcmd <PID> VM.version
jcmd <PID> VM.command_line
```

With a custom launcher or a JVM embedded via JNI:

- The process may not be named `java` or `java.exe`.
- jps may display Unknown instead of the class/JAR name and main arguments.
- OS process listings filtering for the string `java` may miss native processes with an embedded JVM.
- Look for the process owner, service wrapper, or original launcher.

Unknown is a limitation in displaying the application name; it does not mean jps failed to find the JVM.

## 11. Once You Have the PID, Use jcmd to Verify the JVM

If the OS process listing found a PID but jps does not display the process, you can try jcmd directly.

List JVMs visible to jcmd:

```bash
jcmd -l
```

Inspect a known process:

```bash
jcmd <PID> help
jcmd <PID> VM.version
jcmd <PID> VM.command_line
```

Meaning:

- help: lists diagnostic commands supported by the target JVM.
- VM.version: prints HotSpot/JDK version information for the process.
- VM.command_line: displays the command line used to start the JVM.

jcmd must run on the same machine and with an effective user/group matching the JVM process. If the target is in a container, run the command in the corresponding container or namespace.

If the OS finds the PID but jcmd cannot attach, verify that the PID actually belongs to a JVM, that the process is still alive, that the user/group matches, and that the runtime supports diagnostic attach. Read the specific error message before changing any configuration.

Reference: [The jcmd Command — Java SE 24](https://docs.oracle.com/en/java/javase/24/docs/specs/man/jcmd.html).

## 12. Step-by-Step Diagnostic Workflow

Follow these steps in order to avoid changing configuration before identifying the root cause:

1. **Check the tools:** confirm the right JDK and jps are being invoked.
2. **Run detailed commands:** try jps -l, then jps -m or jps -v if needed.
3. **Verify the OS process:** use ps, pgrep, or PowerShell CIM to find the PID.
4. **Compare users:** identify the account running the JVM and the account running jps.
5. **Compare environments:** confirm the same host, container, WSL, VM, and process namespace.
6. **Check instrumentation:** see if the JVM disabled UsePerfData or has special configuration.
7. **Check the runtime:** determine whether the JVM is HotSpot or another implementation.
8. **Use the verified PID:** run jcmd <PID> VM.version and VM.command_line when permissions allow.
9. **Check service logs:** if the process does not exist, read logs and service status for startup or restart errors.
10. **Record the findings:** save the command, user, host/container, PID, JDK vendor/version, and error messages.

Do not conclude that the application has stopped solely because jps output is empty or shows only jps itself.

## 13. Quick Troubleshooting Table

| Symptom | Possible Cause | Resolution |
|---|---|---|
| jps only shows itself | Target JVM is not instrumented, lacks permissions, or is in another namespace | Check OS process list, user, and container |
| jps is not recognized | PATH is missing JDK bin or only a stripped-down runtime is installed | Check JAVA_HOME, jps location, and JDK installation |
| jps -l shows Unknown | JVM uses a custom launcher or embedded launcher | Verify PID via OS and use jcmd if permitted |
| jps run by user A cannot see user B's service | OS access controls restrict visibility | Run the tool as an authorized service account |
| Host cannot see JVM in Docker | Separate process namespace/container | Run jps or ps inside the container |
| jps cannot see JVM with perfdata disabled | JVM may be using -XX:-UsePerfData | Check command line and startup configuration |
| Remote jps fails to connect | Missing jstatd, RMI registry, port, or access permissions | Check remote monitoring setup; consider SSHing to the host |
| OS sees PID but jcmd cannot attach | Wrong user/group, invalid PID, or attach restricted | Verify PID, user, namespace, and runtime |
| Multiple java executables exist | PATH or service configured with multiple JDKs | Identify the process's actual executable and service path |
| Script parses output incorrectly | jps format is unstable | Do not use jps output as an API; use an appropriate OS process API |

## 14. Operational and Security Notes

- jps -m and jps -v can expose application arguments, paths, and sensitive values if copied into tickets or logs.
- Do not expose remote jstatd to broad networks without a security review and access controls.
- Do not run tools with higher privileges than necessary.
- Do not arbitrarily delete hsperfdata or change system temporary directory permissions.
- Do not re-enable performance data or change JVM flags in production without a change plan.
- Do not use jps as the sole inventory source for your entire infrastructure; combine it with service managers, container orchestrators, and OS process inventories.
- Because jps is an experimental/unsupported tool and its output may change, avoid using it as a stable automation interface.

## 15. Summary

When a process is missing from jps, first remember that the tool only lists instrumented HotSpot JVMs that the current account has permission to access. Empty output does not mean the application has definitely stopped.

Items to check:

- Correct JDK and jps in PATH.
- Whether the process actually exists in the OS process list.
- Whether the user running jps has permission to access the JVM.
- Whether the JVM disabled performance data with -XX:-UsePerfData.
- Whether the application is in Docker, WSL, a VM, or another host.
- Whether the JVM is HotSpot and whether it uses a custom launcher.
- Once you have the PID, use jcmd <PID> VM.version and VM.command_line to verify.

Identify the right host, user, namespace, and PID before changing JVM configuration. This approach helps find the actual root cause and avoids unnecessary restarts or JVM flag changes.
