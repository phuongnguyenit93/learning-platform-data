# Scanning a Class Directory with jdeps

`jdeps` is a dependency analysis tool included with the JDK. The tool can take a class file, a directory containing compiled classes, or a JAR as input. When you want to scan the entire output of a Java project, pass the **class directory** at the end of the command, typically a directory such as `build/classes` or `target/classes`.

To view relationships at the class level, use `-verbose:class`. To also display dependencies within the same package or the same archive, add `-filter:none`. You should distinguish between the directory path being analyzed and the classpath used to resolve external dependencies: the input directory is the target to be scanned, while `--class-path` provides other classes/JARs that the bytecode references.

## 1. What Is a Class Directory?

When compiling Java source code with `javac -d`, the compiler writes `.class` files to an output directory and creates a directory tree corresponding to the packages. For example:

~~~text
project/
├── src/
│   └── com/acme/
│       ├── app/Main.java
│       ├── service/GreetingService.java
│       └── util/TextFormatter.java
└── build/
    └── classes/
        └── com/acme/
            ├── app/Main.class
            ├── service/GreetingService.class
            └── util/TextFormatter.class
~~~

In this example, `build/classes` is the **class directory root**. It contains the root directory of the `com.acme` package. When scanning, pass `build/classes` as the input. Do not pass `build/classes/com/acme/app` separately if your goal is to analyze the entire application output.

A class directory is usually generated by a build tool or the `javac` command. A directory may contain multiple packages, nested classes, classes generated by annotation processors, and other metadata. `jdeps` focuses on analyzing class files; resource files that are not class dependencies will not form class edges in the report.

## 2. Checking jdeps and Input Syntax

`jdeps` is a JDK tool. Check the tool and its help output:

~~~sh
java -version
jdeps --version
jdeps --help
~~~

On Windows PowerShell:

~~~powershell
Get-Command jdeps
jdeps --version
~~~

General syntax:

~~~sh
jdeps [options] <path ...>
~~~

The input path can be a `.class` file, a directory, or a JAR. Example of scanning a directory:

~~~sh
jdeps build/classes
~~~

The command above analyzes class files in the directory and prints a dependency summary by default. To view each relationship in more detail, choose an appropriate verbosity level.

If the shell cannot find `jdeps`, verify that the JDK is installed and that the JDK's `bin` directory is in `PATH`. The tool is typically located alongside `java`, `javac`, and `javap`.

## 3. Viewing Class-Level Dependencies

Basic command to scan a directory and print class-level dependencies:

~~~sh
jdeps -verbose:class build/classes
~~~

The `-verbose:class` level shows which source class references which target class. By default, this mode filters out dependencies within the same package. If you want to see edges hidden by the default filter as well, use:

~~~sh
jdeps -verbose:class -filter:none build/classes
~~~

`-filter:none` disables filtering for dependencies within the same package and the same archive. This is useful when you need to see all class-level edges in the directory. The short option `-v` is equivalent to `-verbose:class -filter:none` in current `jdeps` versions.

Output lines typically have the form:

~~~text
source.class -> target.class module-or-archive
~~~

Illustrative example:

~~~text
com.acme.app.Main -> com.acme.service.GreetingService build/classes
com.acme.service.GreetingService -> com.acme.util.TextFormatter build/classes
com.acme.app.Main -> java.io.PrintStream java.base
~~~

The module or archive name in the last column depends on where the class is resolved from. Actual output depends on the class files, classpath, module path, JDK version, and filters. The lines above illustrate how to read the relationships, not a fixed output for every project.

## 4. Complete Example: Compiling and Scanning a Class Directory

Create three source files with the following structure:

~~~text
src/
└── com/acme/
    ├── app/Main.java
    ├── service/GreetingService.java
    └── util/TextFormatter.java
~~~

`TextFormatter.java`:

~~~java
package com.acme.util;

public class TextFormatter {
    public String format(String name) {
        return "Hello, " + name + " dependencies!";
    }
}
~~~

`GreetingService.java`:

~~~java
package com.acme.service;

import com.acme.util.TextFormatter;

public class GreetingService {
    private final TextFormatter formatter = new TextFormatter();

    public String greet(String name) {
        return formatter.format(name);
    }
}
~~~

`Main.java`:

~~~java
package com.acme.app;

import com.acme.service.GreetingService;

public class Main {
    public static void main(String[] args) {
        GreetingService service = new GreetingService();
        System.out.println(service.greet("Java"));
    }
}
~~~

Compile all classes into a single directory:

~~~sh
mkdir -p build/classes
javac -d build/classes \
  src/com/acme/util/TextFormatter.java \
  src/com/acme/service/GreetingService.java \
  src/com/acme/app/Main.java
~~~

On Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force build/classes | Out-Null
javac -d build/classes src/com/acme/util/TextFormatter.java src/com/acme/service/GreetingService.java src/com/acme/app/Main.java
~~~

Run the application to verify:

~~~sh
java -cp build/classes com.acme.app.Main
~~~

Stdout output:

~~~text
Hello, Java dependencies!
~~~

Scan the directory at the class level:

~~~sh
jdeps -verbose:class -filter:none build/classes
~~~

Key relationships to observe include:

- `com.acme.app.Main` references `com.acme.service.GreetingService`.
- `com.acme.service.GreetingService` references `com.acme.util.TextFormatter`.
- The application classes also reference Java SE classes such as `java.lang.String`, `java.lang.System`, or `java.io.PrintStream`.

The report may contain additional compiler-generated classes and edges. The key point is that the input to `jdeps` is the `build/classes` directory—the root containing the entire package tree.

## 5. Distinguishing Input Directory and Classpath

These two locations serve different purposes:

| Component | Role |
|---|---|
| Path at the end of the command, e.g. `build/classes` | The artifact being analyzed |
| `--class-path` | Where to find classes/JARs to resolve external references outside the input |
| `--module-path` | Where to find modules when analyzing a modular application |

For example, if the application in `build/classes` uses two external JAR libraries:

~~~sh
jdeps -verbose:class -filter:none \
  --class-path "lib/alpha.jar:lib/beta.jar" \
  build/classes
~~~

On Windows, the classpath uses semicolons:

~~~powershell
jdeps -verbose:class -filter:none --class-path "lib\alpha.jar;lib\beta.jar" build/classes
~~~

On macOS/Linux, classpath entries are separated by colons. On Windows, use semicolons. Placing `build/classes` at the end still means it is the directory being analyzed; the JAR libraries in `--class-path` only help the tool resolve references used by classes in that directory.

If a dependency JAR is missing, `jdeps` may report `not found` or fail to resolve classes. Add the proper libraries and rerun before concluding that a dependency is missing in the product.

## 6. Scanning a Directory with Different Report Levels

You do not always need a full class-level listing. Choose the report level based on the question you need to answer:

| Option | Purpose |
|---|---|
| `-summary` or `-s` | Print a dependency summary |
| `-verbose:package` | Print package-level dependencies |
| `-verbose:class` | Print class-level dependencies |
| `-v` | Print all class-level dependencies and disable package/archive filtering |
| `-filter:none` | Show dependencies within the same package/archive as well |
| `-filter:package` | Filter out dependencies within the same package; this is the default |
| `-filter:archive` | Filter out dependencies within the same archive |
| `-include <regex>` | Restrict the classes included in the analysis using a regular expression |

Example of viewing a summary:

~~~sh
jdeps -summary build/classes
~~~

Viewing package-level dependencies:

~~~sh
jdeps -verbose:package build/classes
~~~

Viewing class-level dependencies, including intra-package edges:

~~~sh
jdeps -v build/classes
~~~

If the directory has hundreds or thousands of classes, summary or package-level output gives a quick overview. When you need to find which class references another class, use class-level output.

Filters only change what appears in the report; they do not modify class files and do not remove dependencies from the program. If an edge does not appear, check whether a filter is hiding it before concluding that no relationship exists.

## 7. Narrowing the Scan Scope in a Class Directory

If the directory is large, you may want to analyze only a subset of classes. The `-include` option accepts a regular expression to restrict which classes are analyzed. For example:

~~~sh
jdeps -verbose:class -filter:none -include "com\.acme\.app\..*" build/classes
~~~

The regular expression pattern must match the class name in the format reported by `jdeps`. Use escaped dots when you want to represent literal package dots. Check the output after filtering to confirm the right group of classes is retained.

You can use the `--package` option to filter dependencies by package:

~~~sh
jdeps -verbose:class --package com.acme.service build/classes
~~~

`--package` filters dependencies matching the specified package; it does not replace the input directory path. If you need both specific source classes and target dependencies, combine class filters with the verbosity level and read the output carefully.

Avoid applying filters too early when taking a full inventory of dependencies. Run a complete pass with `-filter:none` to understand the full set of edges, then narrow the scope to investigate.

## 8. Recursive Dependency Analysis

When scanning only a directory, `jdeps` analyzes the classes in that directory and their referenced dependencies. If you want to continue following resolved runtime dependencies to see transitive dependency chains, use `-R` or `--recursive`:

~~~sh
jdeps -R -verbose:class --class-path "lib/alpha.jar:lib/beta.jar" build/classes
~~~

`-R` requests recursive analysis and implicitly enables `-filter:none`. The tool continues traversing resolvable runtime dependencies. The output can be significantly larger because it includes classes belonging to external libraries.

Use recursive analysis when you need to answer questions such as "what other libraries do the libraries used by this class depend on?". For questions about direct references within the directory only, starting with a non-recursive command is usually easier to follow.

Recursive analysis is still static analysis. It does not prove that every dependency is loaded or executed in every run.

## 9. Finding Missing Dependencies in a Class Directory

You can ask `jdeps` to find unresolved class dependencies:

~~~sh
jdeps --missing-deps --class-path "lib/alpha.jar:lib/beta.jar" build/classes
~~~

This command inspects the input's dependencies and reports references not found in the input class directory or the provided classpath. The `--missing-deps` option cannot be used together with `-p`, `-e`, or `-s` filters according to the current JDK CLI help.

When missing dependencies are reported, check the following in order:

1. Whether the required JAR actually exists in the dependency directory.
2. Whether the classpath is correct and uses the operating system's path separator.
3. Whether the JAR contains the exact package/class referenced by the bytecode.
4. Whether the dependency version is compatible with the application.
5. Whether the class is provided dynamically by a container, application server, or plugin system.

The `--ignore-missing-deps` option lets you ignore certain missing dependencies in appropriate analysis operations. Ignoring warnings does not fix the classpath and does not prove that the application will run successfully.

## 10. Checking JDK Internal APIs from a Class Directory

You can scan for references to JDK internal APIs:

~~~sh
jdeps --jdk-internals build/classes
~~~

This option helps detect classes in the directory that reference internal packages such as `sun.*` or `com.sun.*`. These APIs are not guaranteed to be stable like Java SE public APIs and may change or have restricted access across JDK versions.

If warnings are reported:

- Identify the class in the application making the reference.
- Find a public API provided by Java SE or a supported library.
- Check the migration guide for the target JDK version.
- Upgrade external libraries if the library itself depends on an internal API.
- Only consider `--add-exports` as a transitional measure after evaluating the risks.

## 11. Modular Class Directories and the Module Path

If the directory contains classes of a module, it may include `module-info.class`. When analyzing a modular application, provide the module path:

~~~sh
jdeps --module-path mods -verbose:class build/modules/com.acme.app
~~~

To print the list of module dependencies:

~~~sh
jdeps --module-path mods --print-module-deps build/modules/com.acme.app
~~~

`--module-path` tells `jdeps` where to find dependent modules. It differs from the classpath: the module path holds modules resolved under JPMS, whereas the classpath holds classes/JARs using the traditional classpath mechanism.

If the directory is a module output, ensure its structure and module descriptor remain intact. When analyzing multiple modules, use the correct module path and clearly specify which module is the target of analysis.

## 12. Limitations of Class Directory Scanning

`jdeps` reads recognizable references in class files; the tool does not run the application and does not observe all runtime behavior. Some dependencies may be determined outside bytecode:

- **Reflection**: class names constructed from strings and loaded via `Class.forName`.
- **Service loading**: providers declared in metadata or configuration and loaded dynamically.
- **Configuration/resources**: XML, JSON, properties files, or scripts containing class names or library names.
- **Dependency injection/frameworks**: frameworks scanning the classpath and instantiating objects based on annotations or configuration.
- **JNI/native libraries**: classes calling native code or loading operating system libraries.
- **Custom class loaders/plugins**: classes loaded from a plugin directory, network, database, or dynamic source.

Therefore, directory scan results do not replace integration tests, runtime checks, or dependency lists managed by a build tool. When an application uses reflection, service providers, or plugins, cross-check the results against configuration files and actual process logs.

A dependency edge also does not mean the target class is guaranteed to be invoked in a single run. `jdeps` shows static reference relationships, not a call graph or execution trace.

## 13. Common Errors and Troubleshooting

| Symptom | Common Cause | Resolution |
|---|---|---|
| `jdeps: command not found` | JDK not installed or JDK `bin` missing from `PATH` | Check `JAVA_HOME`, `PATH`, and `jdeps --version` |
| Report is missing expected classes | Wrong directory passed or directory does not contain fresh class files | Check build output and pass the correct class directory root |
| Intra-package edges not shown | Default filter hides intra-package dependencies | Use `-filter:none` |
| `not found` appears | Missing JAR or incorrect classpath | Add the dependency to `--class-path` |
| Only package summary shown | Using `-summary` or `-verbose:package` | Use `-verbose:class` |
| Output is too long | Scanning many classes or recursive mode enabled | Narrow with `-include` or omit `-R` |
| Reflection/plugin dependencies not shown | References resolved dynamically, not directly visible in bytecode | Check configuration, service metadata, and runtime logs |
| Module dependencies not resolved | Missing or incorrect module path | Provide `--module-path` and check the module descriptor |

## 14. Workflow for Scanning a Class Directory

When analyzing a Java project's output, follow these steps in order:

1. Build the project to produce the latest class directory.
2. Identify the root containing the package tree, such as `build/classes` or `target/classes`.
3. Check the tool version with `jdeps --version`.
4. Start with `jdeps -verbose:class -filter:none <class-directory>`.
5. Add `--class-path` if classes reference external dependencies.
6. Use `--missing-deps` to find unresolved classes.
7. Use `-R` when you need to trace transitive dependencies.
8. Use `--jdk-internals` to check for JDK internal API references.
9. For modular applications, provide `--module-path`.
10. Cross-check the static report with reflection, service loading, plugins, and runtime tests.

### Checklist

- [ ] The input directory is the compiled output, not the source directory.
- [ ] Passed the class directory root containing the package tree.
- [ ] Used `-verbose:class` to view class relationships.
- [ ] Used `-filter:none` when intra-package/archive edges are needed.
- [ ] Provided classpath/module path for external dependencies.
- [ ] Checked for missing dependencies if any.
- [ ] Used recursive mode only when transitive analysis is needed.
- [ ] Considered limitations of reflection, service loading, and plugins.
- [ ] Verified the exact build output being deployed.

`jdeps <class-directory>` lets you directly analyze class files in a project's output. Combining `-verbose:class`, appropriate filters, and a complete classpath helps you identify which classes reference which, detect missing dependencies, and understand the dependency structure before testing or deploying the application.
