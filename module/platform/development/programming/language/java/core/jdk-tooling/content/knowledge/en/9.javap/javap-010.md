# Inspecting Compiler Output with `javap`

After `javac` compiles Java source code, the most important result is usually the `.class` files containing bytecode and metadata in the Java class file format. When you need to know what the compiler generated, verify which file is being inspected, see how methods are represented, or check how compilation options affected metadata, you can use the `javap` tool included with the JDK.

`javac` and `javap` have different responsibilities:

- `javac` reads source code, validates it, and produces class files; depending on configuration, it can also generate source files, native headers, and diagnostics.
- `javap` reads a class file or a class inside a JAR/module and displays declarations, descriptors, bytecode, and metadata.
- `java` launches the application; the application's stdout/stderr is runtime output, separate from compiler output.

`javap` does not restore the original source code verbatim. It presents the structure and bytecode generated by the compiler, allowing you to inspect build results directly.

## 1. Types of Output That Can Appear During Compilation

A compilation run can produce several types of output, depending on the source code and `javac` options:

| Output | Option/Mechanism | Contents |
|---|---|---|
| Java class files | `-d directory` | Bytecode and metadata in `.class` files |
| Generated source files | Annotation processing and `-s directory` | `.java` files generated by annotation processors |
| Native header files | `-h directory` | C/C++ headers for matching native methods |
| Compiler diagnostics | Default; can combine with `-Xdiags` | Errors, warnings, and related source locations |
| Compiler activity log | `-verbose` | Information about files the compiler is loading, parsing, and writing |
| Processor diagnostics/log | Annotation processors and `-Xprint...` options | Rounds, invoked processors, and messages emitted by processors |

Several points to distinguish:

- `javac` does not automatically package class files into a JAR. Use the `jar` tool for packaging.
- Resources such as configuration files, images, or data files are not automatically copied into the class output directory just because they sit next to source files.
- If compilation fails, some output files may already have been created before the error occurred. You should not treat an output directory from a failed build as a complete build.
- `javap` inspects generated class files; it does not replace reading `javac` diagnostics.

## 2. Writing Output to a Separate Directory with `-d`

For a Java project with packages, you should separate source code and output class files. For example:

~~~text
project/
  src/
    demo/
      Report.java
  out/
~~~

From the `project` directory, create the `out` directory if it does not exist, then compile:

Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force out | Out-Null
javac -d out src/demo/Report.java
~~~

macOS/Linux:

~~~sh
mkdir -p out
javac -d out src/demo/Report.java
~~~

The `-d out` option specifies the root directory for storing class files. The compiler creates the package structure under that directory, so the `demo.Report` class is written as:

~~~text
out/
  demo/
    Report.class
~~~

When running or inspecting the class, use the `out` root directory as the classpath:

~~~text
java -cp out demo.Report
javap -classpath out demo.Report
~~~

Do not include the `.class` extension in the class name when using the fully qualified class name form. For package `demo`, the class name is `demo.Report`.

If you omit `-d`, `javac` typically writes the class file next to the corresponding source file. This easily mixes source and build output, especially when a project has multiple packages or is compiled repeatedly.

## 3. Inspecting Overview Output with `javap`

`javap` can display the class declaration and its members in a form close to Java signatures:

~~~text
javap -classpath out demo.Report
~~~

This command is useful for checking:

- The class's fully qualified name and superclass.
- Which interfaces the class implements.
- Which public/package-visible constructors and methods are shown by default.
- Parameter types and return types of methods.

By default, `javap` does not display private members. Use `-p` or `-private` to include private members:

~~~text
javap -classpath out -p demo.Report
~~~

`javap` displays declarations inferred from the class file. Generic types can appear if the class file stores `Signature`; parameter names may depend on `MethodParameters`; these details are not always available if the compiler did not emit the corresponding metadata.

## 4. Important `javap` Options

| Option | Purpose |
|---|---|
| `-c` | Disassemble and display method bytecode |
| `-p` or `-private` | Display private members as well |
| `-s` | Display JVM descriptors for fields and methods |
| `-l` | Display line number table and local variable table if present |
| `-v` or `-verbose` | Display detailed class file information, constant pool, and attributes |
| `-constants` | Display values of eligible constant fields |
| `-classpath path` or `--class-path path` | Specify where to find class files/JARs |
| `--module-path path` | Specify where to find modules |
| `--module module` | Specify the module containing the class to inspect |
| `--multi-release version` | Select the class version inside a multi-release JAR |

You can combine multiple options. For example:

~~~text
javap -classpath out -c -p demo.Report
javap -classpath out -v -p demo.Report
javap -classpath out -s -p demo.Report
javap -classpath out -l -p demo.Report
javap -classpath out -constants -p demo.Report
~~~

When investigating a class file, you typically start with `-p` to see all members, then use `-c` or `-v` to dive into bytecode and metadata.

## 5. Reading Bytecode with `javap -c`

`-c` displays the bytecode instructions of each method:

~~~text
javap -classpath out -c -p demo.Report
~~~

For example, the method:

~~~java
public int add(int left, int right) {
    return left + right;
}
~~~

may be represented by instructions similar to:

~~~text
0: iload_1
1: iload_2
2: iadd
3: ireturn
~~~

Meaning:

- `iload_1`: pushes the `int` value from local variable slot 1 onto the operand stack.
- `iload_2`: pushes the `int` value from slot 2 onto the operand stack.
- `iadd`: pops two `int` values from the operand stack, adds them, and pushes the result back onto the stack.
- `ireturn`: returns the `int` result.

The offsets are bytecode positions within the method, not source line numbers. The exact instructions can vary depending on how the code is written, compiler version, optimizations, and method context.

Some common instructions:

| Instruction | General Meaning |
|---|---|
| `aload`, `iload`, `lload`, `dload` | Load a reference or primitive value from a local variable |
| `astore`, `istore`, `lstore`, `dstore` | Store a value into a local variable |
| `getfield`, `putfield` | Read/write an instance field |
| `getstatic`, `putstatic` | Read/write a static field |
| `invokevirtual` | Invoke an instance method using virtual dispatch |
| `invokestatic` | Invoke a static method |
| `invokespecial` | Invoke a constructor or certain special methods |
| `invokeinterface` | Invoke a method through an interface |
| `invokedynamic` | Invoke a call site linked via a bootstrap method |
| `new` | Create a new object |
| `checkcast`, `instanceof` | Check or cast a reference type |
| `ireturn`, `areturn`, `return` | Return a value or exit a void method |

Bytecode helps verify how the compiler translated Java constructs into JVM operations. However, you should not use a bytecode listing as the sole evidence of runtime performance: the JIT can compile and optimize code while the program runs.

## 6. Reading Descriptors with `javap -s`

JVM descriptors describe field types and method parameter/return types at the class file level. The `-s` option prints descriptors next to declarations:

~~~text
javap -classpath out -s -p demo.Report
~~~

Examples:

| Java Type | Descriptor |
|---|---|
| `int` | `I` |
| `long` | `J` |
| `boolean` | `Z` |
| `void` | `V` |
| `String` | `Ljava/lang/String;` |
| `int[]` | `[I` |
| `String[]` | `[Ljava/lang/String;` |

A method descriptor has the form:

~~~text
(parameter-descriptors)return-descriptor
~~~

For example, the method:

~~~java
public String format(int count, boolean active) {
    return "result";
}
~~~

has the descriptor:

~~~text
(IZ)Ljava/lang/String;
~~~

`I` represents `int`, `Z` represents `boolean`, and `Ljava/lang/String;` represents the reference type `String`.

Descriptors do not store full generic types. If you need to see information such as `List<String>`, inspect the `Signature` attribute with `javap -v`.

## 7. Reading Class-File Header, Constant Pool, and Attributes with `javap -v`

To view the detailed structure:

~~~text
javap -classpath out -v -p demo.Report
~~~

Verbose output typically contains:

1. The path of the class file being read.
2. Minor version and major version.
3. Access flags, class name, and superclass.
4. Constant pool.
5. Field and method declarations.
6. Descriptors and generic signatures.
7. Bytecode inside `Code`.
8. Exception table.
9. Attributes such as annotations, debug metadata, `MethodParameters`, `ConstantValue`, `Signature`, and `BootstrapMethods` if present.

### 7.1. Checking the Class File Version

For a class file compiled for Java 17, `javap -v` typically shows:

~~~text
minor version: 0
major version: 61
~~~

The major version indicates the class file format. It helps determine which Java generation the class file was compiled for and investigate `UnsupportedClassVersionError`.

### 7.2. Checking the Constant Pool

The constant pool stores constants and symbolic references used by the class file, for example:

- Class, interface, field, and method names.
- Descriptors.
- String literals.
- Integers, floating-point numbers, and other constants.
- Method handles, method types, dynamic constants, and invokedynamic references.

Constant pool entries are numbered. Bytecode instructions can reference these entries by index. When reading `javap -v`, you can trace from an instruction to the constant pool to understand which method or field the instruction is referencing.

### 7.3. Checking Attributes

In verbose output, look for the attribute name matching your question:

| Attribute | What to Check |
|---|---|
| `Code` | Bytecode, max stack/local, and exception table |
| `SourceFile` | Source file name |
| `LineNumberTable` | Mapping from bytecode offsets to line numbers |
| `LocalVariableTable` | Names, types, and scopes of local variables when debug info is present |
| `LocalVariableTypeTable` | Additional generic signatures for local variables |
| `MethodParameters` | Parameter names and flags when the compiler emits metadata |
| `Signature` | Generic signature of a class/field/method |
| `ConstantValue` | Compile-time constant value of an eligible field |
| `Exceptions` | Exceptions declared in `throws` |
| `RuntimeVisibleAnnotations` | Annotations with runtime retention |
| `StackMapTable` | Frame metadata for bytecode verification |
| `BootstrapMethods` | Bootstrap methods and arguments for invokedynamic/dynamic constants |

Not every class file contains all attributes. Their presence depends on the source code, member kind, Java version, and compiler options.

## 8. Debug Metadata: Combining `javac -g` and `javap -l`

`javac` debug options control what debugger metadata is written into the class file.

~~~text
javac -g -d out src/demo/Report.java
~~~

`-g` requests generating all debug information supported by the compiler. To omit debug metadata:

~~~text
javac -g:none -d out src/demo/Report.java
~~~

You can select specific groups:

~~~text
javac -g:lines,source -d out src/demo/Report.java
javac -g:lines,vars,source -d out src/demo/Report.java
~~~

Then inspect:

~~~text
javap -classpath out -l -p demo.Report
~~~

If debug metadata is present, the output can show:

- `LineNumberTable`: bytecode offsets and source lines.
- `LocalVariableTable`: local variable names, slots, descriptors, and scopes.
- `LocalVariableTypeTable`: additional generic signatures.

If these tables are missing, check the compile command and build tool configuration. You cannot conclude that the source code lacks those variables or lines just because the class file does not store debug metadata.

## 9. Checking Parameter Names with `-parameters`

Parameter names in source code are not necessarily stored in the class file in a way that reflection can read. Use `-parameters` when compiling if your application or framework needs parameter names:

~~~text
javac -parameters -d out src/demo/Report.java
~~~

Inspect with:

~~~text
javap -classpath out -v -p demo.Report
~~~

Look for `MethodParameters` and the corresponding parameter names. At runtime, the Reflection API can read:

~~~java
Parameter parameter = method.getParameters()[0];
System.out.println(parameter.getName());
System.out.println(parameter.isNamePresent());
~~~

If not compiled with `-parameters`, `Parameter.isNamePresent()` is typically `false`; the displayed name may be a synthesized form such as `arg0`.

Distinguish:

- `-parameters` generates parameter name metadata at the method level.
- `-g:vars` generates debug metadata about local variables.
- `javap -l` mainly displays debug tables; `javap -v` displays full attribute details including `MethodParameters`.

## 10. Complete Example: Compiling and Inspecting Compiler Output

Create the file `src/demo/Report.java`:

~~~java
package demo;

import java.io.IOException;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.reflect.Method;
import java.util.List;
import java.nio.file.Files;
import java.nio.file.Path;

@Retention(RetentionPolicy.RUNTIME)
@interface Reviewed {
    String value();
}

@Reviewed("sample")
public class Report {
    public static final int MAX_ITEMS = 5;

    private final String title;

    public Report(String title) {
        this.title = title;
    }

    public String format(List<String> values) {
        String first = values.isEmpty() ? "(empty)" : values.get(0);
        return title + ": " + first + " / " + MAX_ITEMS;
    }

    public static <T> T first(List<T> values) {
        return values.get(0);
    }

    public static String read(Path path) throws IOException {
        return Files.readString(path);
    }

    public static void main(String[] args) throws ReflectiveOperationException {
        Report report = new Report("Inventory");
        System.out.println(report.format(List.of("Java")));
        System.out.println(first(List.of("compiler", "output")));

        Method method = Report.class.getDeclaredMethod("first", List.class);
        System.out.println(method.getParameters()[0].getName());
        System.out.println(method.getParameters()[0].isNamePresent());
        System.out.println(Report.class.getAnnotation(Reviewed.class).value());
    }
}
~~~

From the `project` root directory, create the output folder and compile:

Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force out | Out-Null
javac -g -parameters -encoding UTF-8 -d out src/demo/Report.java
~~~

macOS/Linux:

~~~sh
mkdir -p out
javac -g -parameters -encoding UTF-8 -d out src/demo/Report.java
~~~

After compilation, the output tree is:

~~~text
out/
  demo/
    Reviewed.class
    Report.class
~~~

Run the application:

~~~text
java -cp out demo.Report
~~~

Stdout:

~~~text
Inventory: Java / 5
compiler
values
true
sample
~~~

Now inspect the output at each level:

~~~text
javap -classpath out demo.Report
javap -classpath out -p demo.Report
javap -classpath out -c -p demo.Report
javap -classpath out -s -p demo.Report
javap -classpath out -l -p demo.Report
javap -classpath out -v -p demo.Report
javap -classpath out -constants -p demo.Report
~~~

Notable details in the verbose output:

- `major version: 61` for a Java 17 class file.
- `ConstantValue` for the `MAX_ITEMS` field.
- `Signature` for the generic method `first`.
- `Exceptions` for the `read` method.
- `RuntimeVisibleAnnotations` for `@Reviewed("sample")`.
- `MethodParameters` for the `values` parameter name.
- `Code` for constructor and method bytecode.
- `LineNumberTable` and `LocalVariableTable` due to the `-g` option.
- `BootstrapMethods` may appear when the compiler uses `invokedynamic`, such as for certain string concatenations.

Verbose output can be long. You can redirect it to a log file to search for what you need, for example `javap -v -p -classpath out demo.Report > report-javap.txt`; redirection syntax works similarly in PowerShell, Command Prompt, and Unix shells.

## 11. Comparing Output When Changing Compiler Options

A useful check is to compile the same source with different options and compare the class files.

### 11.1. Build with Debug and Parameter Metadata

~~~text
javac -g -parameters -d out-debug src/demo/Report.java
~~~

Inspect:

~~~text
javap -v -p -classpath out-debug demo.Report
~~~

You can look for `LineNumberTable`, `LocalVariableTable`, and `MethodParameters`.

### 11.2. Build Without Debug and Parameter Metadata

~~~text
javac -g:none -d out-min src/demo/Report.java
~~~

Inspect:

~~~text
javap -v -p -classpath out-min demo.Report
~~~

Debug tables such as `LineNumberTable` and `LocalVariableTable` are not generated with this option. `MethodParameters` is also absent because the command did not use `-parameters`.

The program logic remains the same; metadata for debugging/reflection changes. When comparing binary class files, timestamps, constant pool ordering, or compiler details can make files differ byte-for-byte even when behavior is equivalent. Compare the meaningful sections in `javap` rather than relying solely on checksums.

### 11.3. Checking APIs Against a Target Version

If you are using a newer JDK but need to ensure the output targets Java 17:

~~~text
javac --release 17 -g -parameters -d out src/demo/Report.java
javap -v -classpath out demo.Report
~~~

For Java 17, the class file major version is 61. `--release` controls the language level, class file format, and corresponding public platform API set; it is more useful than setting `-source` and `-target` alone when you need to validate against target APIs.

## 12. Inspecting Compiler Logs and Diagnostics

When you need to understand what the compiler did, use `-verbose`:

~~~text
javac -verbose -d out src/demo/Report.java
~~~

Depending on the JDK version, the log can show activities such as parsing source files, loading classes, and writing class files. This option is useful when you need to know where the compiler is reading dependencies from or where output is being written.

To view more detailed diagnostics:

~~~text
javac -Xdiags:verbose -d out src/demo/Report.java
~~~

To enable warnings:

~~~text
javac -Xlint:all -d out src/demo/Report.java
~~~

To treat warnings as errors:

~~~text
javac -Xlint:all -Werror -d out src/demo/Report.java
~~~

If annotation processors are used, the following options help view rounds and invoked processors:

~~~text
javac -XprintRounds -XprintProcessorInfo -d out src/demo/Report.java
~~~

`-verbose` is the compiler activity log; `-Xdiags:verbose` adjusts diagnostic verbosity; `-Xlint` enables warnings. These serve three different purposes.

Normally, when compilation succeeds without logging enabled, `javac` does not need to print a success message. Check the process exit code and the presence of class files. When using shell scripts or CI, keep stdout, stderr, and exit status separate so you know where a build fails.

## 13. Inspecting Generated Sources and Native Headers

### 13.1. Generated Sources from Annotation Processors

If a processor generates source code, use `-s` to specify the directory for generated sources:

~~~text
javac -processorpath processor-lib.jar -processor com.example.MyProcessor -s generated-src -d out src/demo/App.java
~~~

Inspect `generated-src` to see `.java` files created by the processor. The compiler can include these source files in subsequent processing rounds and compile them in the same run.

If the application references a generated class but `javac` reports `cannot find symbol`, check:

- Whether the processor was loaded and processed the annotations.
- Whether `-s` points to the expected output directory.
- Whether the processor generated the exact package and class name referenced by the application.
- Whether diagnostics from the processor report any errors.

### 13.2. Native Headers from JNI Methods

For Java code declaring native methods, `javac -h` can generate C/C++ headers:

~~~text
javac -h native-headers -d out src/demo/NativeBridge.java
~~~

The `native-headers` directory contains headers generated for eligible native methods. `-h` is a `javac` option; `javap` does not generate these headers.

If you need to inspect the native declarations inside the class file, use:

~~~text
javap -classpath out -p -s demo.NativeBridge
~~~

You can view the `native` modifier and method descriptor, then cross-check with the generated header.

## 14. Inspecting Classes Inside a JAR or Module

### 14.1. Inspecting a Class in a JAR

If the class has been packaged in a JAR, you can specify the JAR as the classpath:

~~~text
javap -classpath app.jar -p com.example.Main
javap -classpath app.jar -c -p com.example.Main
javap -classpath app.jar -v -p com.example.Main
~~~

To list entries in the JAR:

~~~text
jar --list --file app.jar
~~~

If the class depends on other JARs for type resolution, add them to the classpath using the OS-specific path separator. Windows uses `;`; macOS/Linux uses `:`.

### 14.2. Inspecting a Class in a Module

For modular applications, specify the module path and the module to inspect:

~~~text
javap --module-path mods --module com.example.app com.example.Main
~~~

If you need to inspect a class in a JDK module, `javap` module syntax can also be used to specify the module containing the class. Check `javap --help` on your installed JDK to confirm supported options.

### 14.3. Multi-Release JARs

A multi-release JAR can contain different versions of a class for different Java versions. Use `--multi-release` to choose which version to inspect:

~~~text
javap --multi-release 17 -classpath library.jar -p com.example.Api
~~~

This is useful when you need to confirm which class file a Java 17 runtime will select from a multi-release JAR.

## 15. Common Issues When Inspecting Compiler Output

### `Error: class not found`

**Cause:** the classpath does not point to the package root directory, the JAR is missing the class, or the fully qualified class name is incorrect.

**Resolution:** verify where the class file actually resides. If the file is `out/demo/Report.class`, use `javap -classpath out demo.Report`.

### `javap` Displays an Outdated Class

**Cause:** the classpath has multiple versions with the same name, or the output directory has not been rebuilt.

**Resolution:** use an explicit classpath, check your working directory, and run a clean build when needed. Do not assume the class `javap` finds is the one just compiled if the classpath still contains old output.

### No Bytecode Shown

**Cause:** the command did not include `-c`, or the class/method has no `Code` attribute, such as an abstract/native method.

**Resolution:** add `-c`; if the method is abstract/native, check the declaration and keep in mind that it has no normal bytecode method body.

### Variable Names or Line Numbers Missing

**Cause:** the class file was compiled without the corresponding debug metadata.

**Resolution:** recompile with `-g`, then inspect with `javap -l` or `javap -v`.

### Original Parameter Names Missing

**Cause:** `MethodParameters` is missing.

**Resolution:** recompile with `-parameters`; `-g` does not replace this option.

### Generic Types Not Shown as in Source

**Cause:** JVM descriptors reflect type erasure; generic signatures are separate metadata.

**Resolution:** use `javap -v` and look for `Signature`. Do not expect descriptors to always contain full generic types.

### Post-Compilation Output Differs from Expectations

**Cause:** using the wrong JDK, wrong `--release`, a different annotation processor version, stale build cache, or different compiler options.

**Resolution:** record `java --version`, `javac --version`, the full build command, classpath/module path, and relevant environment variables. Run a clean build with the right toolchain and re-inspect the class file.

### Unable to Read Class File

**Cause:** the class file is corrupted, improperly transformed by a bytecode tool, or incompatible with the `javap` version.

**Resolution:** identify the file's origin, re-check with an appropriate JDK, run `javap -v`, and rebuild from source if needed. If the error appears after instrumentation or obfuscation, verify whether the tool preserves valid class file structure and attributes.

## 16. Reproducible Workflow for Inspecting Compiler Output

When investigating a build, follow these steps in order:

1. **Record the toolchain:** `java --version`, `javac --version`, and the build tool version.
2. **Record the compile command:** including `--release`, `-encoding`, `-d`, classpath/module path, processor path, and debug options.
3. **Locate the output directory:** find the class file in the right package and avoid reading stale output.
4. **Inspect declarations:** use `javap -p` to confirm classes, fields, constructors, and methods.
5. **Inspect bytecode:** use `javap -c -p` to view instructions for the methods under analysis.
6. **Inspect descriptors:** use `javap -s -p` to cross-check JVM types.
7. **Inspect metadata:** use `javap -v -p` to read the constant pool, class-file version, and attributes.
8. **Inspect debug/parameter info:** use `javap -l` and verbose output; verify against `-g` and `-parameters`.
9. **Inspect secondary outputs:** check generated sources, native headers, and compiler logs if the project uses those features.
10. **Verify at runtime:** run the program or tests after confirming the class file is right. A bytecode listing does not prove the logic works for all inputs.

Save build command lines and toolchain versions in scripts or CI so others can reproduce the results. When comparing outputs between two builds, compare using the same JDK version, dependencies, and compiler options.

## 17. Checklist

- [ ] Distinguish compiler output, compiler diagnostics, and runtime stdout/stderr.
- [ ] Use `javac -d` to write class files into a separate directory.
- [ ] Use `javap -classpath` to point to the right output directory or JAR.
- [ ] Use `javap -p` to view private members as well.
- [ ] Use `javap -c` to inspect bytecode.
- [ ] Use `javap -s` to inspect JVM descriptors.
- [ ] Use `javap -v` to view class-file version, constant pool, and attributes.
- [ ] Use `javap -l` to inspect debug tables when they exist.
- [ ] Use `javac -g` for debug metadata and `javac -parameters` for reflection parameter names.
- [ ] Use `javac -verbose`, `-Xdiags:verbose`, and `-Xlint` for their respective purposes.
- [ ] Check `-s` if an annotation processor generates sources.
- [ ] Check `-h` if the compiler generates native headers.
- [ ] Verify classpath/module path and avoid reading stale class files.
- [ ] Run the application or tests to verify behavior after inspecting bytecode.

Inspecting compiler output with `javap` helps you connect source code with the actual artifact produced by the compiler. When you know how to read declarations, bytecode, descriptors, the constant pool, and attributes, you can verify build configuration, investigate compatibility errors, inspect metadata for reflection/debugging, and better understand how Java is represented on the JVM.
