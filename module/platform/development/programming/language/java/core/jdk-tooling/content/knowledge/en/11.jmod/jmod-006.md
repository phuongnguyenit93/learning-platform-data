# Hashing in JMOD and Java's ModuleHashes Mechanism

## 1. What are JMOD and module hashes?

JMOD is a JDK archive format used to package a module along with components for build and runtime linking, such as class files, native libraries, headers, commands, man pages, and configuration files. The `jmod` tool supports the `create`, `extract`, `list`, `describe`, and `hash` modes.

A module hash is a hash value recorded in a module descriptor to bind a packaged module to other modules that depend on it. When a module is released alongside its dependent modules, hash metadata helps module tools recognize the exact set of dependent modules used to create that binding.

Key distinctions:

- **JMOD archive**: A module package at the build/link stage; it can contain many types of content beyond class files.
- **Module hash**: Metadata about the contents of dependent modules, recorded in the descriptor of the module being bound.
- **File checksum**: Such as the SHA-256 of the entire JMOD file, which is an artifact verification value at the file level.
- **Digital signature**: Authenticates the publisher and verifies integrity using keys/certificates. A module hash does not replace a digital signature.

`jmod hash` does not simply compute a checksum for the entire JMOD file. It computes the hashes of modules selected by a regular expression that have a direct or indirect dependency on the module being packaged.

## 2. Why record hashes of dependent modules?

Suppose there are two modules:

- `com.example.base` provides a shared API.
- `com.example.app` declares `requires com.example.base` and calls the base module's API.

When packaging the base module, you can record the hash of the app module into the base module's descriptor. This relationship creates a binding between the packaged base version and the selected app module versions.

If a dependent module is replaced with different content after the hash is generated, the hash metadata no longer matches the new dependent content. Module tools can detect this inconsistency when resolving or linking the module graph. This mechanism is useful when building runtime images and managing a set of modules tested together.

Common use cases:

- Binding a foundational module to extension modules that depend on it.
- Packaging a group of tightly coupled modules into a runtime image.
- Helping detect whether a dependent module has been altered compared to the version recorded when the binding was created.
- Supporting build pipelines with strict version and module provenance control.

You do not need to generate module hashes for every Java application. It makes the most sense when a project uses JPMS, JMOD, and a deliberate runtime linking workflow. Simple Java applications running on the classpath typically do not need this step.

## 3. Where are hashes stored in a JMOD?

When recording hashes, `jmod` updates the `module-info.class` module descriptor inside the JMOD. In the class file, this data is represented by the `ModuleHashes` attribute.

The `ModuleHashes` attribute contains:

- The hash algorithm name.
- The list of selected dependent modules.
- The corresponding hash value for each module.

In a created JMOD, the class file is typically located under the `classes/module-info.class` entry. You can extract the JMOD and use `javap -v` to inspect this attribute.

Example of the information `javap` may display:

~~~text
ModuleHashes:
  algorithm: SHA-256
  hashes: 1
  module: com.example.app
  hash: [byte-array hash value]
~~~

The specific algorithm name and digest are generated by the tool/JDK. In verification examples with current JDKs, `jmod` displays the `SHA-256` algorithm. Do not hard-code digests in scripts because any change to module content changes the hash value.

## 4. `jmod hash` syntax

Syntax:

~~~bash
jmod hash --module-path <module-path> --hash-modules <regex-pattern> [--dry-run] <module.jmod>
~~~

Parameter meanings:

| Option | Meaning |
|---|---|
| `hash` | Selects the mode to record module hashes into the target JMOD. |
| `--module-path` or `-p` | Path containing the modules to analyze for finding dependent modules. |
| `--hash-modules` | Regular expression selecting the names of dependent modules to hash. |
| `--dry-run` | Computes and displays the expected result without writing hashes into the JMOD. |
| `<module.jmod>` | Target JMOD that will receive the `ModuleHashes` metadata. |

`--hash-modules` accepts a **regular expression**, not a glob pattern. For example:

- `com\.example\.app` matches the exact module name `com.example.app`.
- `com\.example\..*` matches modules in the group whose names start with `com.example.`.
- `.*` matches all eligible modules on the module path, so use it with caution.

The tool only records hashes for modules selected by the pattern that directly or indirectly depend on the target JMOD's module. A module that does not depend on the target JMOD will not be included in the hash set merely because its name matches the regex.

## 5. Example: two modules with a dependency relationship

Create the directory structure:

~~~text
jmod-hash-demo/
├── src/
│   ├── com.example.base/
│   │   ├── module-info.java
│   │   └── com/example/base/Base.java
│   └── com.example.app/
│       ├── module-info.java
│       └── com/example/app/Main.java
├── mods/
└── jmods/
~~~

Base module, file `src/com.example.base/module-info.java`:

~~~java
module com.example.base {
    exports com.example.base;
}
~~~

File `src/com.example.base/com/example/base/Base.java`:

~~~java
package com.example.base;

public class Base {
    public static String value() {
        return "base";
    }
}
~~~

App module, file `src/com.example.app/module-info.java`:

~~~java
module com.example.app {
    requires com.example.base;
}
~~~

File `src/com.example.app/com/example/app/Main.java`:

~~~java
package com.example.app;

import com.example.base.Base;

public class Main {
    public static void main(String[] args) {
        System.out.println(Base.value());
    }
}
~~~

The module relationship is declared via `requires` and `exports`: `app` reads the `base` module; `base` exports the package used by `app`.

## 6. Compiling and creating the JMOD

From the project root directory, compile both modules using JDK 17:

~~~bash
mkdir -p mods jmods

javac --release 17 --module-source-path src -d mods --module com.example.base,com.example.app
~~~

After compilation, the output structure looks like:

~~~text
mods/
├── com.example.base/
│   ├── module-info.class
│   └── com/example/base/Base.class
└── com.example.app/
    ├── module-info.class
    └── com/example/app/Main.class
~~~

Create the JMOD for the base module:

~~~bash
jmod create --class-path mods/com.example.base --module-version 1.0 jmods/com.example.base.jmod
~~~

Here, `--class-path` points to the directory containing the class files and `module-info.class` of the module being packaged. `--module-version 1.0` records the module version in the descriptor.

So that `jmod hash` can find the app module on the module path, package the app module as a modular JAR:

~~~bash
jar --create --file jmods/com.example.app.jar -C mods/com.example.app .
~~~

The `jmods` directory now contains the target JMOD `com.example.base.jmod` and the dependent modular JAR `com.example.app.jar`.

## 7. Previewing hashes with `--dry-run`

Before modifying the JMOD, run in dry-run mode:

~~~bash
jmod hash --dry-run --module-path jmods --hash-modules 'com\.example\.app' jmods/com.example.base.jmod
~~~

The tool will:

1. Read the base module from the target JMOD.
2. Resolve the modules on the module path.
3. Find the app module matching the regex that has a dependency on base.
4. Compute the digest of the app module.
5. Print the expected result without modifying the JMOD.

The output looks like:

~~~text
Dry run:
com.example.base
  hashes com.example.app SHA-256
~~~

In actual output, a hexadecimal digest string follows the algorithm name. This value depends on the module contents and the specific build.

Use `--dry-run` to confirm that the regex and module path select the right modules before writing metadata into the release artifact.

## 8. Recording hashes into the JMOD

Once the dry-run result is correct, run the command again without `--dry-run`:

~~~bash
jmod hash --module-path jmods --hash-modules 'com\.example\.app' jmods/com.example.base.jmod
~~~

A successful result looks like:

~~~text
Hashes are recorded in module com.example.base
~~~

This command updates the target JMOD and records the hash of the app module into the base module's metadata. Run this step after all dependent modules have been built and before the JMOD is used to create a runtime image or released.

If you change the app module's contents after generating the hash, re-run the hashing process so the metadata reflects the new module version. Avoid updating a JMOD after hashing without regenerating or recalculating the associated hashes.

## 9. Checking hashes with `jmod describe`

Use `jmod describe` to inspect module information:

~~~bash
jmod describe jmods/com.example.base.jmod
~~~

The output may include:

~~~text
com.example.base@1.0
exports com.example.base
requires java.base mandated
hashes com.example.app SHA-256 ...
~~~

The `hashes` line indicates that the base module has recorded the hash of the app module and the algorithm used. The `...` in the example represents the long digest truncated for display; the actual output shows the full value.

`jmod describe` is a fast, readable check suitable for QA scripts after creating a JMOD.

## 10. Inspecting the `ModuleHashes` attribute with `javap`

To view the class file structure inside the JMOD, extract the archive:

~~~bash
jmod extract --dir extracted jmods/com.example.base.jmod
~~~

The JMOD is extracted into component directories, where the module descriptor is located at:

~~~text
extracted/
└── classes/
    └── module-info.class
~~~

Use `javap`:

~~~bash
javap -v extracted/classes/module-info.class
~~~

In the output, look for the `ModuleHashes` attribute. It shows the hash algorithm, the number of recorded modules, the dependent module names, and their corresponding digests.

You can filter on Linux/macOS:

~~~bash
javap -v extracted/classes/module-info.class | grep -A8 ModuleHashes
~~~

On Windows PowerShell:

~~~powershell
javap -v extracted/classes/module-info.class | Select-String -Pattern "ModuleHashes" -Context 0,8
~~~

Use `jmod describe` when you only need a high-level check. Use `javap -v` when you need to deeply inspect attribute structures or investigate class-file-level issues.

## 11. How does `jmod hash` differ from checksums and digital signatures?

| Mechanism | Scope | Purpose |
|---|---|---|
| Module hash in JMOD | Selected modules that have a dependency relationship with the target module. | Binds a packaged module to specific dependent modules. |
| SHA-256 checksum of JMOD file | All bytes of a single JMOD file. | Verifies whether the file has changed compared to the stored checksum. |
| Digital signature | Signed artifact and signing certificate/key. | Authenticates the signer and verifies integrity via signature. |

A module hash is not a publisher authentication mechanism. If an attacker can replace both the dependent module and the JMOD containing the digest, they can regenerate the corresponding metadata. Therefore, you still need to protect artifact repositories, release checksums, and digital signatures when security requirements demand it.

A module hash also does not replace versioning. Continue managing module versions, dependency locks, and clear release processes.

## 12. How is JMOD used with `jlink`?

JMOD is typically used at the runtime image creation stage. The `jlink` tool reads modules on the module path, resolves dependencies, and creates a runtime containing only the required modules.

General workflow:

~~~text
Source modules
     |
     | javac
     v
Compiled modules
     |
     | jar / jmod create
     v
Modular JAR + JMOD
     |
     | jmod hash
     v
JMOD with ModuleHashes
     |
     | jlink
     v
Custom runtime image
~~~

A `jmod` archive is not an executable JAR and is normally not passed directly to `java -cp` as a library. JMOD is a format designed for module tools at link time, especially `jlink`. When running a released application, use the runtime image created by `jlink` or use modular JARs on the module path according to the appropriate distribution structure.

When creating a runtime image, the module path can contain application/extension JMODs, modular JARs, and the JDK's JMOD directory. Ensure you keep the exact set of modules and versions used during the hashing process.

## 13. Related `jmod` options

| Option | Purpose |
|---|---|
| `create` | Creates a new JMOD. |
| `hash` | Computes and records hashes of selected dependent modules into the target JMOD. |
| `--hash-modules regex` | Selects dependent modules using a regular expression. |
| `--module-path path` or `-p path` | Specifies where to find modules analyzed for hash calculation. |
| `--dry-run` | Computes and displays hash results without writing them. |
| `describe` | Displays the module descriptor, version, requires, exports, and recorded hashes. |
| `list` | Lists entries inside a JMOD. |
| `extract --dir path` | Extracts JMOD contents for inspection. |
| `--module-version version` | Records the module version when creating a JMOD. |
| `--compress zip-0 ... zip-9` | Selects archive compression level during creation. |
| `--date timestamp` | Normalizes entry timestamps to the specified time. |
| `--target-platform platform` | Records the target platform for a JMOD when platform-specific packaging is needed. |

You can view the options supported by your installed JDK with:

~~~bash
jmod --help
jmod --help-extra
~~~

Option names and features may vary across JDK versions. Use the help output of the exact JDK in CI rather than assuming all build machines have the same tool version.

## 14. Common errors and troubleshooting

| Symptom | Common cause | Solution |
|---|---|---|
| Dependent module not found | The module is not on the module path or the module name is incorrect. | Check the modular JAR/JMOD, module descriptor, and the path passed to `--module-path`. |
| No hashes recorded | The regex does not match any module name, or the selected module does not depend on the target module. | Check module names with `jmod describe` and fix the regex. |
| `jmod hash` errors when reading module path | The module path is missing artifacts, contains invalid archives, or has unreadable modules. | Place valid modular JARs/JMODs on the module path and verify with `jar --describe-module` or `jmod describe`. |
| `Invalid JMOD file` | The target file is not a valid JMOD or a JAR was mistakenly passed as the target JMOD. | Use `jmod create` to create a JMOD; a modular JAR can be a dependent module on the module path, but not the target JMOD for `jmod hash`. |
| `jmod describe` has no `hashes` line | The JMOD has not been hashed yet, or the regex selected no dependent modules. | Run `jmod hash --dry-run` to check first, then record the hashes. |
| Digest changes after build | Class/resource contents or dependent modules changed. | Rebuild the module set consistently and re-run `jmod hash`. |
| `java` cannot find module when passing JMOD to module path | JMOD is a link-time format, not a modular JAR for direct execution by the launcher. | Use `jlink` to create a runtime image or use modular JARs on the module path. |
| JMOD created, but `jlink` cannot resolve modules | Missing dependent modules, wrong module path, or artifact incompatible with the platform/JDK. | Check the module graph, matching JDK, and the entire module path. |

Diagnostic workflow:

1. Verify the JDK with `jmod --version` or `jmod --help`.
2. Use `jmod describe` to inspect the target module.
3. Use `jar --describe-module` or `jmod describe` to identify dependent module names.
4. Use `jmod hash --dry-run` to confirm the regex and list of selected modules.
5. Record the hashes and verify with `jmod describe`.
6. If bytecode inspection is needed, extract the JMOD and view `ModuleHashes` with `javap -v`.
7. Double-check the module path before running `jlink`.

## 15. Pre-release checklist

- Identified the correct target module to record hashes into.
- Module descriptors properly declare `requires` and `exports`.
- Dependent modules are built and packaged with the expected versions.
- Module path contains the required modular JARs/JMODs for hash calculation.
- The `--hash-modules` regex selects the right dependent module names.
- Ran `jmod hash --dry-run` and reviewed the output before writing.
- Ran `jmod hash` on the target JMOD.
- `jmod describe` displays the expected hash list and algorithm.
- When deep inspection is needed, `javap -v` displays the `ModuleHashes` attribute.
- Recomputed hashes after any changes to dependent modules.
- JMOD is used at the appropriate linking stage; the runtime image is created and verified with `jlink`.
- Release artifact checksums and digital signatures are managed separately if required by the process.

Module hashes in JMOD bind a packaged module to specific dependent modules. Choose the right target module, place dependent modules on the module path, use an appropriate regex, preview with `--dry-run`, then record the hashes and verify with `jmod describe` or `javap -v`.
