# The --release Option of javac

`--release` is a `javac` compiler option used to compile source code for a specific target Java version. This option allows a project to be compiled with a newer JDK while retaining the ability to run on the selected older Java version, within the compatibility scope provided by the Java platform.

For example, you can use JDK 21 to compile an application targeting Java 17:

```sh
javac --release 17 -d out src/com/example/Main.java
```

The command above instructs the compiler to simultaneously enforce Java 17 language syntax, Java 17 bytecode format, and the published Java platform API set for Java 17. This is an important difference compared to only specifying `-source` and `-target`.

## 1. Why Is --release Needed?

A project often needs to support the lowest Java version used by its users or deployment environments. Meanwhile, developer machines or CI servers may already have a newer JDK installed.

If you simply compile with the latest JDK by default, the source code might accidentally use syntax or APIs that only exist in newer versions. The generated bytecode might also require a newer JVM. When deploying the application to a machine with an older Java version, the application may fail to start or encounter class linking errors.

For example, a development team has JDK 21 installed, but the application needs to run on Java 17. Setting `--release 17` helps the compiler detect issues early, such as:

- Using language syntax introduced in Java 18 or later.
- Calling Java SE APIs that do not yet exist in Java 17.
- Generating bytecode with a version higher than what Java 17 can read.

As a result, many compatibility issues are caught right at compile time, instead of only appearing when deployed to the target Java environment.

## 2. Syntax and Usage Requirements

Basic syntax:

```text
javac --release <version> [other-options] source-files
```

Example compiling for Java 17:

```sh
javac --release 17 Main.java
```

Can be combined with other options:

```sh
javac --release 17 -encoding UTF-8 -Xlint:all -d out src/com/example/Main.java
```

Meaning:

- `--release 17`: selects Java 17 as the target platform version.
- `-encoding UTF-8`: reads source files using UTF-8.
- `-Xlint:all`: enables compiler warning groups.
- `-d out`: places the generated `.class` files into the `out` directory.
- `src/com/example/Main.java`: the source file to compile.

The `--release` option has been supported since JDK 9. Therefore, JDK 9 or newer is required to invoke this option. JDK 8 does not recognize `--release`; with JDK 8, you must use JDK 8 itself to compile for Java 8 or upgrade the compiler JDK.

Supported version values depend on the JDK running `javac`. For example, JDK 21 supports releases from 8 to 21. Check the list accepted by the current JDK with:

```sh
javac --help
```

You cannot select a release newer than the JDK running the compiler. JDK 17 cannot compile with `--release 21`; JDK 21 or newer is required for that target.

## 3. Three Compatibility Layers Controlled by --release

`--release N` combines three requirements:

### 3.1. Source Language Version

The compiler only accepts Java syntax available in the target version. For example, when compiling for Java 8, the source code cannot use `var` for local variables because this syntax was introduced after Java 8.

### 3.2. Bytecode Version

The compiler generates the class file format corresponding to the target Java version. Older JVMs will reject newer bytecode with errors such as `UnsupportedClassVersionError`.

### 3.3. Java Platform APIs

The compiler restricts the platform APIs that can be referenced to the API set published for the target version. For example, when compiling for Java 8, you cannot call a method added in Java 11 such as `String.strip()`.

These three layers need to be controlled together. Simply generating older bytecode is not enough if the code still calls APIs only available on a newer JDK.

## 4. Differences Between --release, -source, and -target

The three options have related purposes but are not equivalent:

| Option | Controls | Limitation |
|---|---|---|
| `-source N` | Accepted source language/syntax | Does not automatically restrict platform APIs to Java N |
| `-target N` | Output bytecode format version | Does not automatically restrict APIs that source code can call |
| `--release N` | Source language, bytecode, and platform APIs of release N | Can only select releases supported by the current JDK |

Suppose you use JDK 21 but set:

```sh
javac -source 17 -target 17 Main.java
```

The compiler checks syntax according to Java 17 and generates bytecode targeting Java 17. However, if the source code calls an API that only exists in Java 21 or later, compilation can still succeed because the compiler sees the APIs of JDK 21. When running on Java 17, the program may fail with a linking error such as `NoSuchMethodError`.

With:

```sh
javac --release 17 Main.java
```

The compiler also restricts the platform API set to Java 17 and will catch calls to APIs not present in that version.

Therefore, when using a newer JDK to build an application supporting an older Java release, prefer `--release`. Do not combine `--release` with `-source` or `-target` in the same command; these are mutually exclusive ways of selecting the compilation version.

## 5. Practical Example: Compiling Java 17 with JDK 21

Suppose JDK 21 is installed on your machine and you want to build an application that runs on Java 17.

Create `Main.java`:

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Compiled for Java 17");
    }
}
```

Compile:

```sh
javac --release 17 -d out Main.java
```

Run on a machine with JDK 17 or newer:

```sh
java -cp out Main
```

Output:

```text
Compiled for Java 17
```

When compiled successfully with JDK 21 and `--release 17`, the class file is generated in the Java 17 format. The runtime machine still needs a compatible JVM, and all dependencies of the application must also be compatible with Java 17.

You can inspect the bytecode version using `javap`:

```sh
javap -verbose -classpath out Main
```

In the output, look for the `major version` line. For Java 17, the value is:

```text
major version: 61
```

Some common values:

| Java | Class file major version |
|---:|---:|
| 8 | 52 |
| 11 | 55 |
| 17 | 61 |
| 21 | 65 |

This is the class file format version number, not the JDK version number installed on the machine.

## 6. API Example: Detecting a Method Unavailable in an Older Version

The `String.strip()` method was added in Java 11. Create `ApiCompatibility.java`:

```java
public class ApiCompatibility {
    public static void main(String[] args) {
        String message = "  Java  ";
        System.out.println(message.strip());
    }
}
```

If you use JDK 21 to compile for Java 8:

```sh
javac --release 8 ApiCompatibility.java
```

Compilation fails because the Java 8 API does not have the `strip()` method. The compiler reports that it cannot find the corresponding method on type `String`.

Switch to target Java 11:

```sh
javac --release 11 ApiCompatibility.java
java ApiCompatibility
```

Output:

```text
Java
```

This example shows that `--release` checks platform APIs as well, not just adjusting the bytecode version number.

## 7. Scope and What --release Does Not Guarantee

`--release` is an important compatibility control mechanism, but it does not automatically solve every deployment issue.

**Third-party libraries:** this option controls the Java platform APIs provided by the compiler. It does not guarantee that external JARs are compatible with the target Java version. You need to verify the minimum Java version of each dependency and how it is packaged.

**JDK internal APIs:** you should not rely on unsupported internal classes or APIs such as `sun.*` or `com.sun.*`. Access to internal APIs may be restricted or changed between JDK releases; `--release` targets the supported platform API set for the target release.

**Operating system and CPU architecture:** `--release` does not compile specifically for Windows, Linux, macOS, x64, or ARM. Java bytecode is generally portable, but an application can still depend on native libraries, file paths, system permissions, or platform-specific behavior.

**Runtime behavior:** successful compilation does not prove that the entire program runs correctly in every environment. You must run tests on the actual target JRE/JDK version, especially when the application uses reflection, service loading, serialization, JNI, or relies on specific library behaviors.

**Preview configuration:** preview features are tied to a specific JDK version. If preview is enabled, you must compile with the JDK corresponding to that release and run with `--enable-preview` on that same Java version. Preview is not a way to build preview applications for an older release using a newer JDK.

## 8. --release and Java Preview Features

Preview features allow experimenting with language or platform changes before they become permanent. Preview features are strictly tied to the Java version that introduces them.

For example, with JDK 21, you can enable preview for Java 21 with:

```sh
javac --enable-preview --release 21 Main.java
```

When running, you also need to enable it:

```sh
java --enable-preview Main
```

You cannot use JDK 21 to enable Java 17 preview features by setting `--release 17`. If you need to use preview features, the compiler and runtime must match the exact release that supports them. For applications requiring long-term stable compatibility, prefer standardized Java features over preview features.

## 9. Configuring --release in Maven

With the Maven Compiler Plugin, you can configure the release in `pom.xml`. For example:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.13.0</version>
        </plugin>
    </plugins>
</build>
```

The `maven.compiler.release` property is used by the Maven Compiler Plugin to pass the release selection to the compiler. The example above sets Java 17 as the target platform and UTF-8 as the source encoding.

Run the build:

```sh
mvn clean compile
```

Maven still needs a JDK new enough to support the selected release. If using JDK 21, configuring release 17 is valid. If Maven is actually running on JDK 8, the JDK 8 compiler does not understand `--release`; check with:

```sh
mvn -version
```

The output shows which Java version Maven is running on. An IDE might configure the Maven runner to use a different JDK than the Terminal, so check both environments if results differ.

## 10. Configuring --release in Gradle

In Gradle, you can select the JDK used to run the compiler with a Java toolchain and set the target platform with `options.release`.

Groovy DSL example in `build.gradle`:

```groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
```

In this configuration:

- The toolchain selects JDK 21 as the compiler toolset.
- `options.release = 17` instructs the compiler to compile for Java 17.
- The machine running the application needs Java 17 or newer.
- Dependencies and other tasks also need to be verified against the compatibility target.

Run the compile task:

```sh
./gradlew clean compileJava
```

On Windows:

```powershell
gradlew.bat clean compileJava
```

You can check the JVM version used by Gradle with:

```sh
./gradlew -version
```

The JDK running Gradle, the compiler's toolchain JDK, and the target Java version are related concepts, but they are not necessarily the same. Distinguish between them when diagnosing build errors.

## 11. Common Errors When Using --release

| Symptom | Cause | Resolution |
|---|---|---|
| `invalid flag: --release` | Using a JDK that is too old, such as JDK 8 | Select JDK 9 or newer; check `javac --version` and `where.exe javac` or `command -v javac` |
| `release version ... not supported` | Target version is newer than the JDK running the compiler or outside the supported range | Use a newer JDK or choose a release listed by `javac --help` |
| `option --source cannot be used together with --release` | Both `--release` and `-source` are configured together | Choose one mechanism; prefer `--release` when API restriction is needed |
| `option --target cannot be used together with --release` | Both `--release` and `-target` are configured together | Remove `-target` and keep the target release |
| `cannot find symbol` after lowering release | Source code calls an API that does not exist in the target release | Replace the API with a compatible alternative, raise the target release, or use an appropriate library |
| Terminal build succeeds but IDE fails | IDE and Terminal use different JDKs or compiler configurations | Align Project SDK, Gradle JVM/Maven runner, and release settings |
| `UnsupportedClassVersionError` on older machine | Some bytecode was built with a higher release than the target, or a dependency requires a newer Java version | Inspect bytecode of the application and dependencies; set release consistently and use compatible libraries |
| Compiles successfully but fails at runtime with `NoSuchMethodError` | A dependency or other bytecode references an API missing in the runtime, or there is a library version conflict | Check the dependency tree, runtime classpath, and test on the target runtime |

When encountering errors, first verify the actual compiler being invoked. A machine may have multiple JDKs installed, causing `java` and `javac` to point to two different versions. On Windows:

```powershell
where.exe java
where.exe javac
java -version
javac --version
```

On macOS/Linux:

```sh
command -v java
command -v javac
java -version
javac --version
```

Then check the build configuration of your IDE or build tool. Do not modify source code before confirming the exact compiler and release being used.

## 12. Workflow for Choosing a Release for a Project

When starting a project or changing the target Java version, follow this sequence:

1. Identify the lowest Java version supported by the deployment environment.
2. Choose the JDK used for compilation; this JDK can be newer than the target release.
3. Set `--release` to the exact version that needs to be supported.
4. Check whether third-party libraries support the same version.
5. Compile the entire codebase and resolve warnings/errors.
6. Run unit tests and integration tests on the target version's runtime.
7. Verify artifacts and dependencies before releasing.

Do not choose a release simply because a developer's machine happens to have that version installed. The release should reflect the product's compatibility contract with the user environment.

## 13. Checklist

- [ ] Identified the minimum Java release supported by the product.
- [ ] The JDK used for compilation is new enough to support the target release.
- [ ] Configured `--release N` or the equivalent setting in Maven/Gradle.
- [ ] Not combining `--release` with `-source` or `-target`.
- [ ] Source code does not use syntax or APIs newer than the target release.
- [ ] Third-party dependencies also support the target Java version.
- [ ] Checked the bytecode version when necessary.
- [ ] Executed tests on the actual target runtime.
- [ ] Not unintentionally relying on preview features or internal APIs.

`--release` turns Java compatibility requirements into a condition that can be verified right during compilation. When used properly, it reduces the risk of shipping bytecode or API calls that exceed the Java version the application commits to supporting.
