# Limitations of jps

**jps** is a JDK tool used to list instrumented Java HotSpot Virtual Machines (JVMs) on the target system. It is useful when you need to quickly find a JVM and its local VM identifier (LVMID), but its output is not a complete inventory of every Java process, is not a stable management API, and does not replace operating system monitoring or process management tools.

In Oracle JDK 24, the jps command is explicitly documented as **experimental and unsupported**. Its output format, options, and availability may change or be removed in future JDK releases. Therefore, use jps for manual checks and runtime investigation; for long-term automation, choose an API or tool supported for that purpose.

## 1. jps Only Sees a Specific Set of JVMs

jps does not scan every program related to Java. It lists the **instrumented Java HotSpot VMs** that the user running the command has permission to observe.

This creates three limitations:

1. JVMs that are not HotSpot or are not instrumented via the mechanism jps uses may not appear.
2. JVMs running under a different account may be hidden by operating system access permissions.
3. JVMs in another host/container or process namespace may be outside the scope observable by the current jps command.

Example:

~~~bash
jps
~~~

Sample output:

~~~text
31840 com.example.ApiServer
32004 com.example.BatchWorker
~~~

The output only shows the two JVMs that jps found in the current scope. It does not prove that the machine has only two Java processes.

### jps Is Not a General-Purpose Process Lister

If you need a list of operating system processes, use the corresponding OS tool.

Linux/macOS:

~~~bash
ps -ef
~~~

Windows PowerShell:

~~~powershell
Get-Process
~~~

If you need to find Java processes by executable name or command line, you can filter using OS tools. OS tool results still depend on permissions and namespaces, but they cover a broader process scope than jps.

### Not Seeing a JVM Does Not Mean the JVM Is Not Running

If jps does not list your application, check:

- Whether the application is still alive or has terminated.
- Whether the command is running on the right host and in the right container.
- Whether the user running jps has permission to observe the process.
- Whether the JVM is HotSpot and recognized via the instrumented VM mechanism.
- Whether the application was started with a custom launcher.
- Whether a PID namespace or isolated environment changes the observation scope.

Do not conclude that a service has stopped simply because jps does not print the service's name.

## 2. LVMID Is Not Always the OS PID

jps displays the **local VM identifier (LVMID)** for each JVM found. The LVMID often matches the operating system process identifier, but Oracle does not guarantee that the two values are always the same.

This difference matters when using jps output as input to OS commands such as kill, taskkill, ps -p, or process management tools.

Sample output:

~~~text
31840 com.example.ApiServer
~~~

31840 is the LVMID reported by jps. On many systems, this is also the PID of the JVM process, but you must verify it on the actual host running the application before taking action.

Linux/macOS:

~~~bash
ps -p 31840 -o pid,ppid,user,etime,args
~~~

Windows PowerShell:

~~~powershell
Get-CimInstance Win32_Process -Filter "ProcessId = 31840" |
    Select-Object ProcessId, ParentProcessId, Name, CommandLine
~~~

If the process information does not match the expected application, stop and identify the right process. Do not use LVMID as a global identifier or store it statically in service configuration.

### PIDs Can Be Reused

A PID is only meaningful within a process's lifetime and operating system scope. When a process terminates, the operating system can reassign the same PID to a new process.

An unsafe workflow is saving a PID from an earlier investigation and reusing it hours or days later to send a stop command. Before any impactful action, re-verify the PID, process name, user, command line, and start time.

### Snapshots Can Become Stale Immediately

jps collects information at a point in time. While the command is running:

- A JVM may have just started.
- Another JVM may have just terminated.
- A PID may have been reused.
- Permissions or container state may have changed.

Therefore, the output is a snapshot for investigation, not a continuous state or a guarantee that the process still exists after the command completes.

## 3. Class or JAR Names May Be Incomplete

By default, jps displays the LVMID and the short name of the main class or JAR. The short name may omit the class package or JAR path, so two different applications can look identical.

Use:

~~~bash
jps -l
~~~

The -l option requests the full package name of the main class or the full path of the JAR. However, this information still depends on how the JVM was launched.

### Custom Launchers May Return Unknown

jps uses the Java launcher to obtain the class/JAR name and main arguments. If the JVM was started with a custom launcher, that information may not be available. In that case, jps may print Unknown.

Sample output:

~~~text
31840 Unknown
~~~

Unknown does not necessarily mean the JVM is broken or not running a Java application. It may simply reflect that how the process was launched does not provide the metadata jps expects.

When encountering this case:

- Verify the process using operating system tools.
- Check the service configuration or launcher script.
- Inspect the command line if you have permission and it does not expose secrets.
- Use service/container management tools to identify the workload.
- Use jcmd if the JVM can be attached to and deeper diagnostics are needed.

### Embedded JVMs and Main Arguments

A native application can embed a JVM via the JNI Invocation API. In this case, the main class or arguments information may differ from an application run with the java launcher. Depending on initialization, -m may have no value, and the jps documentation notes that the output may be null for embedded JVMs.

Do not rely on every JVM having the same main class and argument list structure.

## 4. Access Permissions Limit Results

jps only lists JVMs that the principal running the command has permission to access under the operating system's access control mechanisms.

For example, a service running under the appuser account may not be fully visible to another regular user. On production systems, process inspection permissions are often restricted to prevent users from reading other services' information.

When results are missing:

1. Identify the user that owns the JVM.
2. Check OS permissions for reading process metadata and the attach mechanism.
3. Run the tool using an authorized operations account following standard procedures.
4. Do not automatically escalate to administrator/root just to get a complete list.
5. Record the permission scope when saving audit results.

Higher privileges can expose command lines, system properties, or sensitive data. Use only the privileges required and restrict who can view the output.

## 5. Output Is Not Stable for Script Parsing

Oracle recommends against writing scripts to parse jps output because the format may change in future releases.

The general output format is:

~~~text
lvmid [ [ classname | JARfilename | "Unknown" ] [ arg* ] [ jvmarg* ] ]
~~~

Tokens are separated by whitespace. If an argument contains spaces, determining boundaries between arguments can become ambiguous.

Example:

~~~text
31840 com.example.ApiServer -Dapp.label=production server
~~~

You cannot simply split the string on spaces and reliably know whether production server is a single property value or two separate tokens.

### Why Is Parsing jps Dangerous?

- The output format can change because the tool is not supported as a stable API.
- The class/JAR name can be Unknown.
- Arguments can contain whitespace.
- A process can disappear between reading and acting on it.
- A PID can be reused.
- Results are constrained by permissions and namespaces.
- A single line of output does not provide enough data to uniquely identify a service.

Do not use a script like the following as a production management mechanism:

~~~powershell
jps | ForEach-Object {
    $parts = $_ -split " "
    Stop-Process -Id $parts[0]
}
~~~

This example is especially dangerous because it stops every PID printed without verifying which process needs to be stopped.

### Use the Right Tool for Automation

| Need | Suitable Option |
|---|---|
| Get the PID of the current Java application | ProcessHandle.current().pid() |
| List operating system processes | ps, tasklist, PowerShell/CIM |
| Manage services | systemd, Windows Service Manager, or an orchestration platform |
| Diagnose a single JVM | jcmd |
| Continuously monitor a JVM | Protected JMX/monitoring agent |
| Quickly find a JVM manually | jps |

If you need maintainable automation, use APIs with stable contracts and service identities from your deployment management system rather than parsing jps text output.

## 6. Display Options Can Expose Sensitive Data

jps has additional options to display full names and arguments:

| Option | Information | Limitation |
|---|---|---|
| -q | LVMID only | Does not provide a name to distinguish services |
| -l | Full class name or JAR path | May expose package/path structure |
| -m | Arguments passed to the main method | May contain sensitive data |
| -v | JVM arguments | May contain -D properties, paths, and misconfigured secrets |
| -V | LVMID only per JDK 24 documentation | Check help for your exact JDK version |

On OpenJDK 24.0.2, both jps -q and jps -V produce LVMID-only output; behavior and options should be verified against the JDK in use.

### Why Do -m and -v Require Caution?

Example of an improperly launched application:

~~~bash
java -Ddb.password=example-secret -jar app.jar
~~~

If you run jps -v, the property value may appear in the output. This is only an illustrative example of a configuration to avoid; do not put real secrets in JVM arguments.

Similarly, -m can display tokens or user information if the application passes them in main arguments.

Guidelines:

- Use -q if you only need the identifier.
- Only use -m or -v when genuinely needed for investigation.
- Do not post raw output to tickets, chats, or public logs.
- Redact passwords, tokens, URLs with credentials, and sensitive data.
- Do not pass secrets directly on the command line if a more suitable secret management mechanism is available.

## 7. Remote Discovery Depends on jstatd and RMI

jps can query JVMs on a remote host using a hostid, but this is not a remote discovery protocol that works automatically without server-side configuration.

Example:

~~~bash
jps -l app-host.example:1099
~~~

With the default RMI protocol, jps assumes the target machine is running jstatd. If no port is specified, the RMI registry defaults to port 1099.

Prerequisites:

- jstatd is running on the target host.
- The RMI registry and port are configured properly.
- Network routes and firewalls allow the required connections.
- The remote host permits access under policy.
- Appropriate access permissions and RMI security configuration are in place.
- Hostname, port, and server name match the actual configuration.

If any prerequisite is missing, remote listing can fail even while the target JVM is still running.

### Remote RMI Is a Management Surface

Do not expose jstatd/RMI to a public network just for convenience in viewing PIDs. Remote services should be restricted with firewalls, network segmentation, and security configuration per the JDK documentation.

In production, consider using a monitoring agent, protected JMX, or an approved infrastructure management tool. If you only need to identify processes on a host, OS/SSH administration tools may be more appropriate.

### Remote Host LVMID Is Not a Local PID

If jps returns the LVMID of a JVM on app-host.example, that number belongs to the target environment. Do not use it with kill, taskkill, or ProcessHandle on the local machine.

All follow-up actions must be performed on the correct host and namespace.

## 8. Containers and PID Namespaces Change How Processes Appear

Containers typically use PID namespaces. A process can have different PIDs when observed from inside the container versus from the host.

Illustrative example:

~~~text
Host namespace
└── Java process: PID 42000

Container namespace
└── Same Java process: PID 1
~~~

Inside the container, the JVM may be PID 1. On the host, that same process has PID 42000. These are two different views of the same process.

### How to Check

From the host, you can use:

~~~bash
docker top my-java-container
~~~

Or run a process tool inside the container if installed in the image:

~~~bash
docker exec my-java-container ps -ef
~~~

If a minimal image does not have ps, use the container runtime tools or inspect /proc in the appropriate namespace.

With Kubernetes, identify the right cluster, node, pod, and container before checking the PID. A PID inside a container should not be treated as a PID on the node.

### jps Does Not Replace Container Tools

If jps runs on the host while the JVM is in another namespace, the results depend on how process namespaces and permissions are configured. Do not assume that every JVM in a container appears the same as a JVM running directly on the host.

Use docker top, docker exec, kubectl exec, or node-level tools with appropriate operational permissions to find processes in the corresponding environment.

## 9. jps Does Not Provide JVM Health Status or Metrics

jps is only meant to list JVMs and basic launch metadata. It does not tell you:

- Whether the JVM is processing requests or hung.
- CPU usage, memory pressure, or GC pauses.
- How much heap is in use.
- Which threads are blocked or deadlocked.
- The service's HTTP health check status.
- Whether database or queue connections are still active.
- Whether the JVM has business-logic errors or lost connectivity to dependencies.

A line such as:

~~~text
31840 com.example.ApiServer
~~~

only proves that jps identified a JVM at that moment. It does not prove the API server is healthy.

### Use Follow-Up Tools

After verifying the right JVM, you can use jcmd:

~~~bash
jcmd 31840 VM.version
jcmd 31840 VM.flags
jcmd 31840 VM.command_line
jcmd 31840 Thread.print
jcmd 31840 GC.heap_info
~~~

Some diagnostic commands can consume significant resources or write large files. For example, a heap dump can cause a pause, require substantial disk space, and contain sensitive data. Read each command's help before using it in production.

To assess service health, combine:

- Application health endpoints.
- CPU, memory, GC, thread pool, and request latency metrics.
- Logs and distributed tracing.
- Protected JMX/monitoring agents.
- OS/container resource metrics.
- Alerts and service-level objectives.

## 10. jps Is an Experimental and Unsupported Tool

Oracle JDK 24 explicitly documents the jps command as **experimental and unsupported**. This means:

- The output format may change.
- Options may change or be removed.
- The tool may no longer be present in a future JDK release.
- Critical automation interfaces should not be built on its output.
- Behavior observed on one vendor/version should not be assumed as a guarantee across all JDKs.

On OpenJDK 24.0.2, the commands jps, jps -q, jps -l, jps -m, jps -v, and jcmd -l were run in a test environment. This only confirms the behavior of that specific runtime; it does not turn jps into a stably supported API.

Check the syntax of your installed JDK:

~~~bash
jps --help
java --version
~~~

Do not assume every JDK vendor or version has the same options and output.

## 11. Alternatives Based on Your Goal

### Only Need the PID of the Current Java Program

Use the Java ProcessHandle API, available since Java 9:

~~~java
public final class CurrentPid {
    public static void main(String[] args) {
        System.out.println("PID=" + ProcessHandle.current().pid());
    }
}
~~~

Compile with Java 17:

~~~bash
javac --release 17 CurrentPid.java
~~~

Run:

~~~bash
java CurrentPid
~~~

Sample output:

~~~text
PID=31840
~~~

The value varies by actual process. This API is suitable when the application itself needs to know its own PID.

### Need to List Operating System Processes

Linux/macOS:

~~~bash
ps -eo pid,ppid,user,comm
~~~

Windows PowerShell:

~~~powershell
Get-CimInstance Win32_Process |
    Select-Object ProcessId, ParentProcessId, Name
~~~

These tools list processes via OS mechanisms, not just JVMs. Access permissions and namespaces can still limit results.

### Need to Diagnose a Specific JVM

~~~bash
jcmd 31840 help
jcmd 31840 VM.version
~~~

jcmd is suitable for sending diagnostic commands to a JVM. It must run on the same machine as the target JVM and normally requires the same effective user/group ID. Do not use an old PID without re-verifying it.

### Need to Manage Services

Use a service manager or orchestration platform:

- systemd on Linux.
- Windows Service Manager on Windows.
- Docker or Kubernetes for container workloads.
- Your organization's application management platform.

A service manager knows service identity, restart policies, dependencies, and lifecycle better than a temporary PID list.

### Need Continuous Monitoring

Use metrics, JMX, or a protected monitoring agent. jps is not a telemetry system and does not provide process history.

## 12. Troubleshooting When jps Produces Unexpected Results

### Application Not Visible

1. Verify the application is still running via a service manager or OS process tool.
2. Check that you are on the right host, container, and PID namespace.
3. Check the permissions of the account running jps.
4. Confirm the runtime is an instrumented HotSpot JVM.
5. Check for custom launchers and the possibility of the class name showing as Unknown.
6. Use jcmd or a monitoring tool if deeper diagnostics are needed.

### Only Unknown Appears

1. Verify the process with an OS tool.
2. Check for a custom launcher or embedded JVM setup.
3. Do not rely on the class/JAR name in the output.
4. Use service configuration and deployment metadata to identify the application.

### LVMID Does Not Match the PID Observed from the Host

1. Determine whether jps is running inside or outside a container.
2. Check the PID namespace.
3. Verify the process using OS tools in the same environment.
4. Do not use a remote/container LVMID on the local host.

### Remote Query Fails

1. Confirm jstatd is running on the target host.
2. Check the RMI registry, port, and server name.
3. Check firewalls, DNS, and routing.
4. Confirm access permissions and remote management policies.
5. If RMI is not required, switch to approved host administration or monitoring tools.

### Script Mis-parses Output

1. Stop using jps output as an automation interface.
2. Do not split tokens on whitespace to infer arguments.
3. Use ProcessHandle, OS process APIs, or a service manager.
4. Add process identity verification before any impactful action.

## 13. Checklist for Safe Use of jps

- Verify the JDK version and jps --help before relying on options.
- Remember that jps is experimental/unsupported in Oracle JDK 24.
- Understand that jps only lists accessible instrumented HotSpot JVMs.
- Do not conclude a JVM is not running just because jps does not list it.
- Do not assume LVMID is always the OS PID.
- Verify process, user, command line, and start time before acting.
- Remember that PIDs can be reused.
- Use -l to distinguish classes/JARs when short names are insufficient.
- Accept that custom launchers may display Unknown.
- Be cautious with -m and -v because arguments may contain secrets.
- Do not parse jps output in production scripts.
- For remote queries, check jstatd/RMI and secure network access.
- In containers, identify the correct PID namespace.
- Use jcmd for diagnostic commands rather than expecting jps to provide health/metrics.
- Use ProcessHandle to get the current application's own PID.
- Use the OS/service manager/orchestrator to manage processes.
- Redact command lines and diagnostic output before sharing.
- Record timestamp, host, namespace, and JDK version alongside audit evidence.

## 14. Key Terminology

| Term | Meaning |
|---|---|
| jps | JDK tool that lists instrumented HotSpot JVMs |
| Instrumented JVM | A JVM with metadata recognizable by JVM management tools |
| LVMID | Local VM identifier reported by jps |
| PID | Operating system Process ID |
| PID reuse | The operating system reusing a PID after a process terminates |
| Custom launcher | A custom-built launcher used instead of the standard Java launcher |
| Unknown | Class/JAR name or main arguments unavailable from the launcher |
| jstatd | Service supporting remote JVM information queries over RMI |
| RMI registry | Registry used to look up remote objects in Java RMI |
| PID namespace | Isolated PID space, commonly used in containers |
| ProcessHandle | Java API for accessing native process identifiers and information |
| jcmd | Tool for sending diagnostic commands to a JVM |
| Unsupported tool | A tool with no stability guarantee that may change or be removed |
| Snapshot | Observation at a single point in time, not continuous state |

jps is useful for quickly finding JVMs in a local environment with appropriate access permissions. Limitations around HotSpot scope, permissions, LVMID, launchers, containers, remote RMI, and unstable output make it unsuitable as a foundation for automated management. Use jps to guide investigation, verify processes with OS tools, and use ProcessHandle, jcmd, or service monitoring for specialized needs.
