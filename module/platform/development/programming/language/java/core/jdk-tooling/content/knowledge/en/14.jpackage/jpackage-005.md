# Application Name in jpackage

**jpackage** is a JDK tool for packaging a Java application into an application image or an OS-native installer. The **--name** option (abbreviated **-n**) sets the name of the application and/or package. This name is used as the basis for many components generated by jpackage, such as the primary launcher name, the application directory, and the package name. The final package name typically combines the application name with the version.

Example:

~~~bash
jpackage --type app-image --name AcmeDesk --app-version 2.4.0 --input input --main-jar acme-desk.jar --main-class com.acme.Main --dest dist
~~~

Here, **AcmeDesk** is the name of the packaged application; **2.4.0** is the version; **dist** is where the output is placed. The application name does not determine which main class is executed. The program entry point is still determined by **--main-jar**, **--main-class**, or **--module**.

## 1. What is --name used for?

Syntax:

~~~bash
jpackage --name application-name
~~~

Or using the short form:

~~~bash
jpackage -n application-name
~~~

According to the jpackage documentation, --name is the name of the application and/or package. It serves as the product identifier during packaging. Depending on the platform and output type, this name can affect:

- The name of the generated application image or application directory.
- The name of the primary launcher that users run.
- The installer filename when combined with the app version and package extension.
- The default installation directory name.
- The Linux package name if no separate option is specified.
- The application name displayed in certain platform UI elements.
- The resource override filenames that jpackage looks up by launcher/application name.

Therefore, choose a short, stable, and recognizable name. For long-term product releases, use the same product name across versions and manage version numbers with --app-version.

The name may contain spaces if passed by the shell as a single argument. Example:

~~~bash
jpackage --name "Acme Desk" --type app-image ...
~~~

In build scripts, wrap values containing spaces or special characters in quotes so the shell does not split them into multiple arguments.

## 2. If --name is not specified

If --name is omitted, jpackage derives a default name from the primary input, usually the main JAR or module name. The default application version is **1.0**. The package name is formed from the application name and version, followed by an extension that depends on the package type.

Example with a non-modular application whose main JAR is HelloWorld.jar on Windows:

~~~bash
jpackage --input app --main-jar HelloWorld.jar
~~~

Oracle's documentation illustrates the default package named:

~~~text
HelloWorld-1.0.exe
~~~

If the JAR or module name is technical in nature, the default name may not be suitable as the product name presented to users. For releases, pass --name explicitly to avoid depending on build filenames or module names.

You can use --help to view the options supported by the current jpackage version:

~~~bash
jpackage --help
jpackage --version
~~~

## 3. Distinguishing the application name from other names

In jpackage, many options contain the word name or identifier, but they serve different purposes.

| Option | Meaning | Example |
|---|---|---|
| --name | Primary application/package name | AcmeDesk |
| --app-version | Product/package version | 2.4.0 |
| --dest | Directory where jpackage places output | dist |
| --install-dir | Application installation directory on the user's machine | Acme |
| --main-jar | JAR containing the main class | acme-desk.jar |
| --main-class | Fully qualified name of the main class | com.acme.Main |
| --module | Main module, optionally with main class | com.acme.app/com.acme.Main |
| --linux-package-name | Separate package name on Linux | acme-desk |
| --mac-package-identifier | Unique identifier of the app on macOS | com.acme.desk |
| --mac-package-name | Application name shown in the macOS menu bar | Acme Desk |

Key points to remember:

- --name sets the name of the packaged product.
- --main-class or --module specifies the program entry point.
- --app-version manages the version.
- --dest only changes where the output is saved.
- --install-dir changes the default installation location.
- Platform-specific options can set separate package names or identifiers.

Do not use the main class name as the product name just because both appear in the packaging command. An application may have a main class named com.acme.bootstrap.Launcher while the user-facing name is AcmeDesk.

## 4. Application name, version, and package filename

The --app-version option sets the application and/or package version. If not specified, the default version is 1.0.

Example on Windows:

~~~bash
jpackage --type exe --name AcmeDesk --app-version 2.4.0 --input input --main-jar acme-desk.jar --dest dist
~~~

The package name is generated from the name and version, for example:

~~~text
AcmeDesk-2.4.0.exe
~~~

When releasing the next version, keep the product name and change the version:

~~~bash
jpackage --type exe --name AcmeDesk --app-version 2.5.0 --input input --main-jar acme-desk.jar --dest dist
~~~

The new package may be named:

~~~text
AcmeDesk-2.5.0.exe
~~~

Separating name and version helps:

- Keep the product name consistent across releases.
- Easily distinguish artifacts between versions.
- Avoid renaming launchers or application directories just because the version changes.
- Simplify CI/CD scripting and artifact archiving by version.

The exact package filename also depends on the operating system and package type. Check the generated file in --dest rather than assuming all platforms follow the same naming convention.

## 5. How the application name affects the launcher

By default, the primary launcher name is taken from the application name. For example, if you run:

~~~bash
jpackage --type app-image --name AcmeDesk --input input --main-jar acme-desk.jar --dest dist
~~~

The application image will contain a launcher named AcmeDesk according to OS conventions. Common structure examples:

~~~text
Windows:
AcmeDesk/
  AcmeDesk.exe
  app/
  runtime/

Linux:
AcmeDesk/
  bin/
    AcmeDesk
  lib/
  runtime/

macOS:
AcmeDesk.app/
  Contents/
    MacOS/
      AcmeDesk
    Resources/
    app/
    runtime/
~~~

Exact filenames and directory structures may vary by platform and jpackage version. Internal files inside an application image are implementation details; avoid writing scripts that depend on undocumented internal layouts.

### Creating multiple launchers

An application can provide multiple launchers for different tasks. Use **--add-launcher** with the syntax:

~~~bash
jpackage --add-launcher launcher-name=properties-file
~~~

The name before the equals sign is the name of the additional launcher. The properties file contains dedicated settings such as module, main-jar, main-class, description, arguments, java-options, or icon.

Example **diagnostics.properties** file:

~~~properties
main-jar=acme-desk.jar
main-class=com.acme.tools.Diagnostics
description=Acme Desk Diagnostics
arguments=--support-mode
~~~

Create an application image with a primary launcher and a secondary launcher:

~~~bash
jpackage --type app-image --name AcmeDesk --input input --main-jar acme-desk.jar --add-launcher Diagnostics=diagnostics.properties --dest dist
~~~

In the image, the primary launcher is named AcmeDesk; the additional launcher is named Diagnostics according to platform conventions. --add-launcher does not change the primary product name. To change the primary launcher name, set --name.

You can use --add-launcher multiple times to create multiple secondary launchers. Choose short, descriptive names and avoid duplicate names.

## 6. Output directory and installation directory names

Two options are often confused:

- **--dest**: where jpackage writes the application image or package file on the build machine.
- **--install-dir**: the directory where the application is installed on the user's machine for supported package types.

Example:

~~~bash
jpackage --type app-image --name AcmeDesk --input input --main-jar acme-desk.jar --dest build-output
~~~

This command places the output in build-output. It does not specify the installation directory when the user runs the installer.

Installer package example:

~~~bash
jpackage --type exe --name AcmeDesk --install-dir "Acme Tools/AcmeDesk" --input input --main-jar acme-desk.jar --dest packages
~~~

--install-dir controls the installation location according to OS rules. On Windows, the value is typically a relative subpath under the installation root; on Linux or macOS, an appropriate installation path can be specified. Consult the help for the target platform because path semantics and installation permissions differ.

According to Oracle's packaging guide, the default installation directory is usually based on the application name:

| Platform | Illustrative default location |
|---|---|
| Linux | /opt/application-name |
| macOS | /Applications/application-name |
| Windows | C:\\Program Files\\application-name |
| Windows per-user install | AppData\\Local\\application-name in the user profile |

If you want the installation directory to differ from the product name, use --install-dir. Changing --dest does not change where the application is installed on the target machine.

## 7. Separate package name on Linux

On Linux, **--linux-package-name** allows setting a package name different from the application name:

~~~bash
jpackage --type deb --name "Acme Desk" --linux-package-name acme-desk --input input --main-jar acme-desk.jar --dest packages
~~~

In this example:

- The application name is Acme Desk.
- The system package name is acme-desk.
- The output is a DEB package in the packages directory.

If --linux-package-name is not specified, the package name defaults to the application name.

The user-facing display name and the package manager name serve different purposes. The application name can be friendly, with uppercase letters or spaces; the package name should follow the naming conventions of the DEB/RPM format and your organization's distribution policies. Inspect the package metadata after creation to verify the exact name.

Linux supports package types such as DEB and RPM. The package name can affect filenames, metadata, and package management operations on the user's machine. To keep the package identifier stable across upgrades, maintain the same package name and manage version/release separately.

## 8. macOS-specific names and identifiers

macOS has several distinct naming concepts:

- **--name**: the primary application name.
- **--mac-package-identifier**: the unique identifier of the application in the macOS ecosystem.
- **--mac-package-name**: the application name displayed in the menu bar and the Info window.

Example:

~~~bash
jpackage --type dmg --name AcmeDesk --mac-package-identifier com.acme.desk --mac-package-name "Acme Desk" --input input --main-jar acme-desk.jar --dest packages
~~~

### mac-package-identifier

The default identifier is derived from the main class name. It can be set explicitly with --mac-package-identifier.

The jpackage documentation specifies that the identifier may only use ASCII alphanumeric characters, hyphens, and periods. Reverse-DNS format example:

~~~text
com.acme.desk
~~~

The identifier uniquely identifies the application on macOS. It should remain stable across releases of the same product, especially when using code signing, notarization, or update management mechanisms.

The identifier is not the display name in Finder or the launcher name. Changing the identifier can affect how the OS recognizes the bundle and how signing/update workflows behave.

### mac-package-name

The --mac-package-name option sets the name that appears in the menu bar and the Info window. This name can differ from the application name and must be shorter than 16 characters.

Example:

~~~bash
jpackage --name AcmeDesk --mac-package-name "Acme Desk" ...
~~~

The menu bar name needs to be concise to display properly. According to the JDK 26 command documentation, the default value of mac-package-name is the application name.

## 9. Application name on Windows

On Windows, the application name is typically used as the basis for:

- The application image directory name.
- The launcher executable name.
- The package/installer name when combined with the version.
- The default installation directory.
- Certain shortcut or menu item names if the corresponding options are enabled.

Example creating an EXE installer:

~~~powershell
jpackage --type exe --name AcmeDesk --app-version 2.4.0 --input input --main-jar acme-desk.jar --win-menu --win-shortcut --dest packages
~~~

The --win-menu option requests creating a Start Menu entry; --win-shortcut requests creating a desktop shortcut. The default launcher name is based on the application name.

If you need to change the installation location or let the user choose a directory, see --install-dir and --win-dir-chooser. If you need a per-user installer for the current user, see --win-per-user-install.

### Win upgrade UUID

--win-upgrade-uuid is a UUID associated with package upgrades on Windows. It is a technical identifier for the installer, distinct from the application name. For the same product and upgrade family, manage the UUID consistently according to your release policy; do not use this UUID in place of --name.

Example:

~~~powershell
jpackage --type msi --name AcmeDesk --app-version 2.4.0 --win-upgrade-uuid 12345678-1234-1234-1234-1234567890ab --input input --main-jar acme-desk.jar --dest packages
~~~

The UUID in the example is illustrative only; a real project must generate and manage its product UUID according to its release process.

## 10. Application name in the resource directory

The **--resource-dir** option lets you provide custom resources to jpackage, such as icons or installer templates.

~~~bash
jpackage --name AcmeDesk --resource-dir packaging-resources ...
~~~

Some resources are looked up by launcher or application name:

| Platform / purpose | Filename jpackage looks for |
|---|---|
| Linux launcher icon | launcher-name.png |
| Linux desktop file | launcher-name.desktop |
| Windows launcher icon | launcher-name.ico |
| Windows launcher properties | launcher-name.properties |
| macOS launcher icon | launcher-name.icns |
| macOS entitlements | application-name.entitlements |

For example, if the primary launcher name is AcmeDesk, the icon resource can be named:

~~~text
packaging-resources/
  AcmeDesk.ico
~~~

For the additional launcher Diagnostics, its dedicated resource can be named Diagnostics.ico on Windows, Diagnostics.png on Linux, or Diagnostics.icns on macOS.

Resource filenames must match the launcher/application name that jpackage is using. When changing --name or --add-launcher, review the resource directory so icons and templates are still found.

The resource directory also contains template files specific to each installer type. Not all files in the resource directory are used on every operating system.

## 11. Application name and package type

If --type is not specified, jpackage selects the default package type for the platform. Common types:

| Platform | Commonly used package types |
|---|---|
| Windows | exe, msi |
| Linux | deb, rpm |
| macOS | dmg, pkg |
| All supported platforms | app-image |

The package name is generated from the application name and version according to the rules of the package type. For example, a Windows EXE might be named AcmeDesk-2.4.0.exe; a Linux package has a .deb or .rpm extension; macOS can produce .dmg or .pkg.

To test the application before building an installer, it is recommended to build an app image:

~~~bash
jpackage --type app-image --name AcmeDesk --app-version 2.4.0 --input input --main-jar acme-desk.jar --dest image-output
~~~

After testing the launcher and resources, create the native package on the target platform:

~~~bash
jpackage --type deb --name AcmeDesk --app-version 2.4.0 --input input --main-jar acme-desk.jar --dest packages
~~~

jpackage does not support cross-platform packaging. To build Windows, Linux, and macOS installers, run jpackage on each target operating system with consistent name and version settings.

## 12. Complete example for a non-modular application

Suppose you have the following structure:

~~~text
project/
  input/
    acme-desk.jar
    config/
      app.properties
  packages/
~~~

The JAR has the main class in its manifest, or you know the class is com.acme.Main. Create the application image:

~~~bash
jpackage --type app-image --name AcmeDesk --app-version 2.4.0 --vendor "Acme Software" --description "Acme desktop application" --input input --main-jar acme-desk.jar --main-class com.acme.Main --dest packages
~~~

Explanation:

- --name AcmeDesk sets the product name.
- --app-version 2.4.0 sets the version.
- --vendor and --description add metadata.
- --input specifies the directory containing the JAR and resources.
- --main-jar specifies the main JAR relative to the input directory.
- --main-class specifies the main class if it is not defined in the manifest.
- --dest sets where the application image is saved.

If the main class is already declared in the manifest, --main-class can be omitted.

Test the application image using the launcher generated in the output. If the application reads resources via relative paths, check the working directory and how resources are accessed in the packaged environment.

## 13. Complete example for a modular application

For a modular application, specify the module path and main module:

~~~bash
jpackage --type app-image --name AcmeDesk --app-version 2.4.0 --module-path mods --module com.acme.app/com.acme.app.Main --dest packages
~~~

In this example:

- --name sets the product name.
- --module-path specifies where to find modules.
- --module specifies the main module and main class.
- --dest sets where the application image is saved.

Do not use --module and --main-jar together in the same configuration. Choose one packaging model that fits your application: modular or non-modular.

If you want to add modules to the runtime image generated by jpackage, see --add-modules and --jlink-options. If you already have a custom runtime image built with jlink, you can pass --runtime-image for jpackage to use that image.

## 14. Workflow for choosing an application name for a project

1. Choose a short, readable, and stable product name, such as AcmeDesk.
2. Pass --name explicitly in build scripts instead of relying on JAR/module names.
3. Set the version with --app-version and update it on each release.
4. Decide whether the primary launcher should match the product name; if there are multiple launchers, name additional ones with --add-launcher.
5. Define a separate Linux package name with --linux-package-name if needed.
6. Choose a stable macOS bundle identifier with --mac-package-identifier and a short menu bar name with --mac-package-name.
7. Use --install-dir when the installation directory needs to differ from the application name.
8. Name icons and templates in --resource-dir to match the application/launcher names.
9. Build --type app-image first to test launchers, resources, and the runtime.
10. Build installers on each target platform and inspect metadata after packaging.

A helpful convention is to keep the product name and identifier stable throughout the product lifecycle, while managing version, package release, and output locations separately. This makes application updates more predictable.

## 15. Common issues

| Symptom | Possible cause | Resolution |
|---|---|---|
| Package is named after the JAR/module instead of the product | --name was not specified | Set --name explicitly |
| Package filename has the wrong version | Missing or incorrect --app-version | Check the app version and output filename |
| Launcher does not have the expected name | Application name or secondary launcher configuration differs from expectations | Check --name and --add-launcher |
| Icon is not replaced | Icon filename does not match launcher name or wrong resource directory | Check filename conventions per platform |
| Linux package has an unsuitable name | Default package name is taken from the application name | Set an appropriate --linux-package-name |
| Incorrect macOS bundle identifier | Confused --name with --mac-package-identifier | Set a separate, stable identifier |
| Menu bar name is too long | --mac-package-name is 16 characters or longer | Choose a name shorter than 16 characters |
| Installer is saved in the wrong place | Confused --dest with --install-dir | Use --dest for the build machine, --install-dir for the target machine |
| Renaming the application breaks resource scripts | Override files still use the old launcher name | Update the resource directory to match the new name |
| Cannot build a package for another OS | jpackage builds for the current platform only | Run the build on each target operating system |

## 16. Pre-release checklist

- [ ] --name is set explicitly and consistently in the build pipeline.
- [ ] --app-version matches the release version.
- [ ] Main JAR/class or module is specified accurately.
- [ ] Primary and secondary launcher names are verified in the application image.
- [ ] --dest and --install-dir are configured for their intended purposes.
- [ ] Linux package name is set separately if needed.
- [ ] macOS package identifier is stable and menu name is under 16 characters.
- [ ] Resource icons/templates are named to match the application or launcher.
- [ ] Package type matches the platform and the installer is built on the target OS.
- [ ] Installer is tested on a clean environment and shortcuts, launchers, and version metadata are verified.
- [ ] Updates preserve product identifiers in accordance with each platform's upgrade policy.

## 17. Key takeaways

- **--name** or **-n** sets the application and/or package name in jpackage.
- If --name is omitted, the default name is inferred from the main JAR or module; the default version is 1.0.
- The package name typically combines the application name and app version.
- The primary launcher name and default installation directory are usually based on the application name.
- **--dest** sets the output directory on the build machine; **--install-dir** controls the installation directory on the target machine.
- **--main-jar**, **--main-class**, and **--module** specify the application entry point, not the product name.
- Linux has **--linux-package-name**; macOS has **--mac-package-identifier** and **--mac-package-name**.
- **--add-launcher** names additional launchers.
- Application/launcher names can affect icon filenames and resource overrides.
- Test the application image before building native installers and build on the target platform.
