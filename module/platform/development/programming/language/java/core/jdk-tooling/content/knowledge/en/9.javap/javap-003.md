# Inspecting Java Bytecode with javap

After compilation, Java source code is converted into class files containing bytecode and metadata in the class file format. When you need to understand what the compiler generated, inspect method signatures, view bytecode instructions, or investigate a library without source code, `javap` is the JDK's direct tool for the job.

`javap` is a class-file disassembler: it reads one or more class files and prints information to standard output. The tool lets you observe the compiled representation; it does not run the program, nor does it reconstruct the original source code intact.

## 1. What Is Bytecode?

Java bytecode is an intermediate instruction set stored in class files. The JVM reads and executes these instructions; depending on the JVM and runtime behavior, hot code can be further compiled into machine code by the JIT compiler.

A general overview of the flow:

~~~text
Source code (.java)
       |
       v
     javac
       |
       v
Class file (.class)
       |
       v
JVM loads, verifies, and links
       |
       v
Bytecode execution / JIT compilation
~~~

Bytecode is designed so the JVM can execute it independently of any specific CPU architecture. A class file does not only contain a list of instructions; it also holds version information, the constant pool, class declarations, fields, methods, and attributes.

For example, adding two integers can be represented by instructions that load local variables, add them on the operand stack, and return the result. `javap -c` lets you view these instructions in a human-readable form.

## 2. What Is javap Used For?

Common use cases:

- Inspecting the public API of a class or JAR library.
- Viewing the bytecode generated by `javac` from a piece of source code.
- Checking private methods, fields, constructors, and modifiers.
- Reading JVM descriptors to understand parameter and return types at the class-file level.
- Viewing the constant pool, class-file version, and attributes.
- Inspecting line number and local variable metadata for debugging.
- Comparing class files across builds or library versions.
- Inspecting a class belonging to a module or a specific version in a multi-release JAR.

`javap` writes its output to standard output. You can view it directly in the terminal or redirect it to a file for comparison.

## 3. Basic Syntax

General syntax:

~~~text
javap [options] classes...
~~~

You can specify a class by its fully qualified name, the path to a class file, or the URL of a class file.

Examples:

~~~bash
# Inspect a class in the JDK
javap java.lang.String

# Inspect a class file by path
javap out/com/example/Calculator.class

# Inspect a class by fully qualified name via the class path
javap -cp out com.example.Calculator
~~~

If a class is in a package, use its fully qualified name such as `com.example.Calculator` or specify the corresponding class file. When using a class name, `javap` must be able to locate the class via an appropriate class path or module path.

Check the tool version and help:

~~~bash
javap -version
javap --help
~~~

## 4. Example: Compiling a Class to Inspect

Create `src/com/example/Calculator.java`:

~~~java
package com.example;

public class Calculator {
    public int add(int left, int right) {
        return left + right;
    }

    public static void main(String[] args) {
        System.out.println("sum=" + new Calculator().add(3, 4));
    }
}
~~~

Compile with debug information:

~~~bash
javac -g -d out src/com/example/Calculator.java
~~~

Run the application:

~~~bash
java -cp out com.example.Calculator
~~~

Output:

~~~text
sum=7
~~~

At this point, the output directory contains the class file:

~~~text
out/
└── com/
    └── example/
        └── Calculator.class
~~~

We will use this same class file for the following commands. If you recompile with different source code or options, the class file contents may change.

## 5. Viewing Class Declarations and Members

Run:

~~~bash
javap -cp out com.example.Calculator
~~~

The output looks like:

~~~text
Compiled from "Calculator.java"
public class com.example.Calculator {
  public com.example.Calculator();
  public int add(int, int);
  public static void main(java.lang.String[]);
}
~~~

The output shows that the class has a constructor, an `add` method, and a `main` method. This is a view of declarations and signatures, not the list of bytecode instructions.

By default, `javap` displays public and protected members. Member filtering options:

| Option | Description |
|---|---|
| `-public` | Public classes and members only |
| `-protected` | Public and protected |
| `-package` | Package-private, protected, and public |
| `-private` or `-p` | All members, including private |

To inspect private fields and methods as well:

~~~bash
javap -cp out -p com.example.Calculator
~~~

This is useful when inspecting third-party libraries, but keep in mind that private member names and internal structure are not a public API contract that other applications should depend on.

## 6. Disassembling Bytecode with -c

The `-c` option prints the bytecode instructions of each method:

~~~bash
javap -cp out -c com.example.Calculator
~~~

In the `add` method section, typical bytecode looks like:

~~~text
public int add(int, int);
  Code:
     0: iload_1
     1: iload_2
     2: iadd
     3: ireturn
~~~

Reading each instruction:

1. `iload_1` pushes the first local variable (the `left` parameter) onto the operand stack.
2. `iload_2` pushes the second local variable (the `right` parameter) onto the operand stack.
3. `iadd` pops the two int values from the stack, adds them, and pushes the result back onto the stack.
4. `ireturn` pops the resulting int value and returns it to the caller.

In an instance method, local variable slot 0 holds `this`; the two parameters `left` and `right` are therefore in slots 1 and 2. The offset at the beginning of each line is the bytecode position within the method code, not the line number in the source file.

This is a useful way to see how Java expressions are translated by the compiler into operations on the local-variable array and operand stack.

## 7. Combining Key Options

Commonly used options can be combined to produce the view you need:

~~~bash
# Bytecode of all methods, including private ones
javap -cp out -c -p com.example.Calculator

# Include JVM descriptors of members
javap -cp out -s com.example.Calculator

# Include metadata and the constant pool
javap -cp out -v com.example.Calculator

# View line number and local variable tables
javap -cp out -l com.example.Calculator

# View static final constants
javap -cp out -constants com.example.Calculator

# View hash and file info of the located class file
javap -cp out -sysinfo com.example.Calculator
~~~

| Option | Meaning |
|---|---|
| `-c` | Disassemble bytecode instructions of methods |
| `-v` or `-verbose` | Print detailed class information |
| `-p` or `-private` | Show all members |
| `-s` | Print internal type signatures (JVM descriptors) |
| `-l` | Print line number and local variable tables |
| `-constants` | Show constant values of static final fields |
| `-sysinfo` | Show path, size, timestamp, and SHA-256 of the class file |
| `-version` | Show the javap version |
| `-Joption` | Pass an option to the JVM running javap itself |

You can combine `-c`, `-p`, and `-v` when you need to inspect private methods, instructions, and class-file structure together:

~~~bash
javap -cp out -c -p -v com.example.Calculator
~~~

Verbose output is quite long. When investigating a specific question, start with a narrower view and add options as needed.

## 8. Reading the Constant Pool and Class-File Metadata

A class file has a constant pool that stores constants and symbolic references used by the class—for example, class names, method names, field references, string literals, numeric constants, method handles, and related types.

View it with:

~~~bash
javap -cp out -v com.example.Calculator
~~~

Part of the verbose output typically looks like:

~~~text
Classfile /.../out/com/example/Calculator.class
  Last modified ...; size ... bytes
  SHA-256 checksum ...
  Compiled from "Calculator.java"
public class com.example.Calculator
  minor version: ...
  major version: ...
  flags: ...
Constant pool:
   #1 = Methodref ...
   #2 = Class ...
   ...
~~~

Key details:

- **Classfile:** the class file being read.
- **minor/major version:** the class-file format version.
- **flags:** modifiers at the class, field, or method level, such as public, final, abstract, static.
- **Constant pool:** indexed constants and symbolic references.
- **Fields/Methods:** field, constructor, and method declarations.
- **Attributes:** additional metadata for the class, field, or method.

Indices such as `#1` and `#2` in the constant pool are internal reference positions. They can change between compilations; do not write tools that rely on hardcoded index numbers without properly parsing the class file.

### 8.1. Class-File Version

You can use `-v` to read the major version. Some common milestones:

| Java release | Major version |
|---|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

For example, a class file with major version 65 was generated in the Java 21 format. This indicates the bytecode version, not that all dependencies or the runtime environment are compatible.

If you want to control the target version, use `javac --release N` when compiling, then use `javap -verbose` to verify the generated class-file version.

## 9. Reading JVM Descriptors with -s

A JVM descriptor represents parameter types and return types using the internal syntax of the class file. The `-s` option prints descriptors alongside method/field declarations:

~~~bash
javap -cp out -s com.example.Calculator
~~~

Some rules:

| Symbol | Type |
|---|---|
| `B` | byte |
| `C` | char |
| `D` | double |
| `F` | float |
| `I` | int |
| `J` | long |
| `S` | short |
| `Z` | boolean |
| `V` | void |
| `Lpkg/Type;` | Reference to a type |
| `[T` | Array of type T |

Examples:

- `(II)I`: method taking two int parameters and returning int.
- `([Ljava/lang/String;)V`: method taking a `java.lang.String` array and returning void.
- `()Ljava/lang/String;`: method taking no parameters and returning `java.lang.String`.

Descriptors are useful when analyzing linkage errors, generic APIs after type erasure, or comparing signatures between two library versions. Generic type arguments are generally not included in standard method descriptors; generic information may appear in the Signature attribute.

## 10. Reading Attributes and Debug Metadata

Class files contain many attributes that provide information for the JVM, compiler, debugger, or other tools. `javap -v` lets you inspect them; `javap -l` focuses on line number and local variable tables.

Common attributes:

- **SourceFile:** name of the source file recorded by the compiler.
- **LineNumberTable:** mapping from bytecode offsets to source line numbers.
- **LocalVariableTable:** names, types, and scope ranges of local variables, if generated.
- **Code:** method bytecode, stack/local limits, and exception handlers.
- **StackMapTable:** frame information used for bytecode verification.
- **Exceptions:** list of checked exceptions declared on the method.
- **Signature:** generic signature information.
- **InnerClasses / EnclosingMethod:** metadata about nested classes and enclosing methods.
- **BootstrapMethods:** bootstrap data for instructions such as `invokedynamic`.

To include more debug information when compiling:

~~~bash
javac -g -d out src/com/example/Calculator.java
~~~

`-g` instructs the compiler to generate debug information. `javap -l` can only display tables that actually exist in the class file; if a class does not contain local-variable metadata, local variable names may not appear even though the bytecode executes normally.

## 11. Recognizing Common Bytecode Instructions

Commonly seen opcodes:

| Category | Examples | Meaning |
|---|---|---|
| Load/store | `iload`, `aload`, `istore`, `astore` | Read/write local variables |
| Constants | `iconst_0`, `bipush`, `ldc` | Push a constant onto the operand stack |
| Arithmetic | `iadd`, `isub`, `imul`, `idiv` | Perform integer arithmetic operations |
| Object | `new`, `getfield`, `putfield` | Create objects, read/write fields |
| Invocation | `invokevirtual`, `invokestatic`, `invokespecial`, `invokeinterface` | Call methods |
| Dynamic invocation | `invokedynamic` | Invoke via the dynamic call site mechanism |
| Branch | `ifeq`, `if_icmpge`, `goto` | Conditional and unconditional branching |
| Return | `ireturn`, `areturn`, `return` | Return from a method |

A few reading rules:

- Opcodes are often prefixed by data type: `i` for int, `l` for long, `f` for float, `d` for double, `a` for reference.
- Invocation instructions typically reference a constant pool entry containing the owner, method name, and descriptor.
- Control-flow branches use bytecode offsets to specify the target location.
- Some instructions have short forms such as `iload_1` to load a local variable at a fixed slot.
- Instructions operate on the operand stack; when reading a method, track values pushed and popped in order.

You do not need to memorize every opcode up front. Use `javap -c` to locate the instructions relevant to the question you are investigating, then consult the JVM Specification when you need exact semantics.

## 12. Inspecting Classes in JARs and Modules

### 12.1. Classes in JARs

If a class is in a JAR library, use the class path:

~~~bash
javap -cp lib/example.jar com.example.LibraryClass
javap -cp lib/example.jar -c com.example.LibraryClass
~~~

You can pass multiple classes at once:

~~~bash
javap -cp lib/example.jar com.example.First com.example.Second
~~~

When a class depends on other JARs, `javap` usually only needs to locate the class being inspected; if the output references external types, an appropriate class path helps the tool resolve those names.

On macOS/Linux, the class path separator is typically a colon; on Windows, it is a semicolon:

~~~bash
# macOS / Linux
javap -cp "lib/a.jar:lib/b.jar" com.example.LibraryClass
~~~

~~~powershell
# Windows PowerShell
javap -cp "lib/a.jar;lib/b.jar" com.example.LibraryClass
~~~

### 12.2. Classes in Modules

Use `--module` to specify the module containing the class, and `--module-path` to locate application modules:

~~~bash
javap --module java.base java.lang.String
~~~

For an application module:

~~~bash
javap --module-path mods --module com.example.app com.example.Main
~~~

Distinguish between the module path and the class path. The module containing a class is selected via the module option; a regular classpath does not substitute for the module path in all cases.

### 12.3. Multi-Release JARs

A multi-release JAR can contain multiple versions of the same class under `META-INF/versions/N` directories. By default, the classpath form of `javap` displays the base entry and does not automatically select a class version for the target runtime.

Use `--multi-release` to select the version to inspect:

~~~bash
javap --multi-release 17 -cp lib/multi-release.jar com.example.VersionedClass
~~~

This is useful when inspecting JARs that provide different implementations per Java release. Verify that the JAR actually contains an entry for the selected release.

## 13. Limitations of javap

`javap` is a class-file reader; it is important to understand what it tells you:

- It displays bytecode and metadata, not an exact reconstruction of the original source code.
- Variable names, comments, formatting, expression structure, and original syntax may be lost after compilation.
- Bytecode output is not CPU assembly and does not reflect the machine code generated by the JIT at runtime.
- A single class file does not reveal the full behavior of an entire application, as behavior also depends on other classes, configuration, inputs, environment, and runtime.
- `javap` does not replace project-wide dependency analysis tools like `jdeps`.
- Class files may contain debug metadata or internal names; do not treat them as API guarantees.

In particular, Oracle notes that `javap` is not version-aware for multi-release JARs when using a regular classpath. Use `--multi-release` when you need to read an entry for a specific release.

## 14. Common Errors

| Symptom | Cause | Solution |
|---|---|---|
| `class not found` | Wrong class name or classpath does not point to the directory/JAR containing the class | Check package, output directory, and `-cp` |
| Only public/protected members shown | Using default mode | Add `-p` or `-private` |
| No bytecode shown | Running `javap` without `-c` | Add `-c` |
| Local variable names missing | Class file does not contain `LocalVariableTable` | Compile with `javac -g` and re-run `javap -l` |
| Unfamiliar descriptor syntax | Viewing internal JVM notation | Use `-s` and consult the descriptor table |
| Verbose output too long | `-v` prints extensive metadata | Start with `-c`, `-p`, or `-s` and expand as needed |
| Inspecting wrong class in multi-release JAR | Using regular classpath reads the base entry | Use `--multi-release N` |
| Bytecode differs from expectations | Different compiler/JDK or build options | Check `javac --version`, release target, and build configuration |

## 15. Practical Workflow

When you want to inspect a specific class:

1. **Locate the right class file:** identify the package, output directory, or JAR used by the application.
2. **Check signatures:** run `javap -cp out com.example.Calculator` to inspect the API and members.
3. **Inspect bytecode:** add `-c` to read method instructions.
4. **Inspect private members:** add `-p` if you need to examine internal implementation details.
5. **Check descriptors:** add `-s` to verify parameter and return types at the JVM level.
6. **Inspect class metadata:** use `-v` to check the major version, constant pool, flags, and attributes.
7. **Correlate source/debug info:** use `-l` when you need line number or local variable tables.
8. **Verify the right library version:** use the appropriate class path, module path, or `--multi-release`.

Example command sequence:

~~~bash
javac -g -d out src/com/example/Calculator.java
javap -cp out com.example.Calculator
javap -cp out -c com.example.Calculator
javap -cp out -p -s -c com.example.Calculator
javap -cp out -v com.example.Calculator
~~~

## 16. Key Takeaways

`javap` lets you inspect class files at multiple levels: member declarations, bytecode instructions, JVM descriptors, the constant pool, version, and attributes. `-c` is the primary option for viewing bytecode; `-p` expands member visibility; `-s` displays descriptors; `-v` provides detailed metadata; `-l` shows debug information.

When reading bytecode, make sure you have the right class file, start with a small method, trace the operand stack, and relate each instruction back to the corresponding source code. Use the tool to answer a specific question, while keeping in mind that bytecode is the JVM's intermediate representation—not source code and not JIT-compiled machine code.
