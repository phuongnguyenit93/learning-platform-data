# Heap Options in Java Runtime

The heap is the JVM runtime memory area used to allocate Java objects and arrays. The garbage collector (GC) manages the heap and reclaims memory occupied by objects that are no longer referenced. Heap options allow you to configure the initial size, maximum limit, and how the JVM estimates an appropriate heap capacity for the runtime environment.

The two most important options are **-Xms** and **-Xmx**. Choosing reasonable values helps ensure the application has enough memory, reduces frequent heap resizing, and prevents the JVM from consuming too much RAM on the host machine or container.

## 1. Heap in Overall JVM Memory

The heap is not the entire memory used by a Java process. The JVM also requires off-heap memory areas:

| Memory Area | Purpose | Counted toward -Xmx? |
|---|---|---|
| Java heap | Regular Java objects and arrays | Yes |
| Metaspace | Class metadata and related runtime information | No |
| Thread stack | Per-thread stack, containing frames and local variables | No |
| Direct/native memory | Off-heap buffers, native libraries, and JVM-managed memory | No |
| Code cache | Machine code generated by the JIT compiler | No |

Therefore, setting **-Xmx** equal to the entire machine RAM or container memory limit can cause the process to exceed the overall limit even if the heap has not reached its maximum size.

## 2. Two Basic Heap Options

### 2.1. -Xms: Initial Heap

**-Xms** sets the initial heap size requested by the JVM at startup.

~~~powershell
java -Xms256m -jar app.jar
~~~

This example requests an initial heap of about 256 MiB. The actual heap and committed memory also depend on how the JVM manages memory and runtime constraints.

### 2.2. -Xmx: Maximum Heap

**-Xmx** sets the maximum limit of the Java heap.

~~~powershell
java -Xmx1g -jar app.jar
~~~

The command above sets the maximum heap limit to about 1 GiB. The JVM cannot expand the Java heap beyond this limit. If the application needs to allocate more and the GC cannot reclaim enough memory, the JVM may throw **OutOfMemoryError: Java heap space**.

### 2.3. Combining -Xms and -Xmx

Typically, both options are set to control the initial heap and the upper limit:

~~~powershell
java -Xms256m -Xmx1g -jar app.jar
~~~

Meaning:

- The requested initial heap is 256 MiB.
- The heap can grow when the application needs more memory.
- The maximum heap is capped at about 1 GiB.

If both values are set to the same size:

~~~powershell
java -Xms1g -Xmx1g -jar app.jar
~~~

The JVM is configured with both initial and maximum heap set to 1 GiB. This approach can be useful for services with steady load that need to avoid heap resizing at runtime. However, a large heap from the start can increase committed memory and is not always suitable for small applications or environments running many instances.

There is no single optimal pair of values for every application. Measure usage under realistic load before finalizing the configuration.

## 3. Size Units and Syntax

Heap options accept a numeric value followed by a unit suffix:

| Suffix | Meaning |
|---|---|
| k or K | Kilobytes |
| m or M | Megabytes |
| g or G | Gigabytes |

Example:

~~~powershell
java -Xms512m -Xmx2g -jar app.jar
~~~

Values can be written in bytes, but `m` and `g` suffixes are usually easier to read in deployment configurations. Check the JVM message when passing an invalid value. Avoid confusing **-Xmx2g** with **-Xmx2m** because the unit difference is huge.

## 4. Placing Heap Options in the Right Position in the java Command

Heap options are JVM options, so they must be placed before the part specifying how to run the application, such as **-jar**, **-m**, or the main class name.

Running an executable JAR:

~~~powershell
java -Xms256m -Xmx1g -jar app.jar
~~~

Running a class on the classpath:

~~~powershell
java -Xms256m -Xmx1g -cp "out;lib/*" com.example.Main
~~~

Running a named module:

~~~powershell
java -Xms256m -Xmx1g --module-path mlib --module com.example.app/com.example.app.Main
~~~

The heap options in these examples are processed by the JVM before the application starts. Arguments placed after the JAR name, main class, or module/main class are passed to the Java program. If you place a heap option in the application arguments position, the program may receive it in `args` instead of the JVM applying it.

## 5. Choosing an Appropriate Heap Size

### 5.1. Measure Before Increasing the Heap

Monitor the application in representative scenarios:

- Startup and initial data loading.
- Normal load over a sufficiently long duration.
- High load or many concurrent requests.
- Object-intensive tasks such as batch processing, report generation, or reading large datasets.
- Periods of heavy GC activity and after GC completes.

If heap used keeps growing across multiple GC cycles and does not drop back to a stable level, check for unintended reference retention or memory leaks. Simply increasing **-Xmx** may delay the error without addressing the root cause.

### 5.2. Balancing RAM for the Entire Process

The total RAM required by a Java process is usually larger than the maximum heap. Beyond the heap, the JVM needs metaspace, thread stacks, direct buffers, code cache, and other native memory regions. The operating system also needs memory for other processes and caches.

For example, if a container has a 2 GiB limit, you should not set **-Xmx2g** by default. Leave headroom for native memory, thread stacks, the JVM, and sidecar/auxiliary processes if any. Specific values must be based on measurements of the application itself.

### 5.3. When Should -Xms Equal -Xmx?

Setting both values equal can be appropriate when:

- The application is a long-running service with relatively steady load.
- The required heap size has already been measured.
- The host/container has enough RAM for both the heap and off-heap memory.
- You want to reduce variance caused by heap expansion at runtime.

Keeping **-Xms** lower than **-Xmx** can be appropriate when the application has variable load, multiple processes share resources, or you want to avoid requesting a large heap right at startup.

## 6. Configuring Heap by RAM Percentage

In addition to fixed values, the HotSpot JVM supports percentage options to calculate heap size based on the amount of RAM detected by the JVM.

### 6.1. InitialRAMPercentage

**-XX:InitialRAMPercentage** sets the percentage of available memory used by the JVM to calculate the initial heap.

~~~powershell
java -XX:InitialRAMPercentage=10 -jar app.jar
~~~

The value is a percentage; for example, `10` means 10%. This is an environment-based mechanism for calculating the initial heap, not a fixed byte size.

### 6.2. MaxRAMPercentage

**-XX:MaxRAMPercentage** sets the percentage of available memory used by the JVM to calculate the maximum heap.

~~~powershell
java -XX:MaxRAMPercentage=60 -jar app.jar
~~~

This option is useful when running the same application on machines or containers with different RAM limits. Consider off-heap memory and other processes sharing the limit before choosing a percentage.

Both options can be combined:

~~~powershell
java -XX:InitialRAMPercentage=20 -XX:MaxRAMPercentage=60 -jar app.jar
~~~

When using percentage options, the JVM still applies runtime memory limits and policies. If **-Xms** or **-Xmx** is set at the same time, the fixed value may override the corresponding limit; avoid confusing overlapping configurations. Check the effective flags instead of guessing which values the JVM chose.

### 6.3. Running in Containers

Modern JDK releases support detecting container memory limits on supported platforms. The JVM can use that limit when calculating heap size and applying resource defaults.

Verify the actual runtime and environment:

- Check the JDK version and operating system.
- Confirm that the JVM accurately detects the container limit.
- Check the memory limits enforced by the orchestration platform.
- Monitor RSS and overall memory usage, not just heap used.
- Leave headroom for native memory and auxiliary processes within the same limit.

Do not assume **-XX:MaxRAMPercentage** is always calculated against the host's total physical RAM; the JVM uses the amount of memory it detects as available.

## 7. Heap Options and Other Memory Areas

Some out-of-memory errors do not originate from the Java heap. Distinguishing between memory areas helps you choose the right options and diagnostic tools.

| Issue | Related Memory Area | Investigation Approach |
|---|---|---|
| OutOfMemoryError: Java heap space | Java heap | Inspect heap dump, object retention, GC, and -Xmx |
| OutOfMemoryError: Metaspace | Metaspace | Check class loading, classloader leaks, and metadata |
| unable to create native thread | Thread/native memory resources or OS limits | Check thread count, -Xss, process limits, and RAM |
| Direct buffer memory | Off-heap direct buffer memory | Check buffer allocation/release and -XX:MaxDirectMemorySize |
| Process killed by OS/container | Total process memory or system limits | Check RSS, container limit, native memory, and OS logs |

**-Xss** sets the stack size per thread; it is not a heap option. **-XX:MaxMetaspaceSize** limits metaspace, while **-XX:MaxDirectMemorySize** limits the direct buffer capacity allowed by the JVM. Do not increase these limits to fix a heap error without first identifying the actual memory area causing the issue.

## 8. Inspecting the Heap at Runtime

### 8.1. Using Runtime in Java

The Java API provides basic heap information via `Runtime`:

~~~java
public class HeapInfo {
    private static double toMiB(long bytes) {
        return bytes / (1024.0 * 1024.0);
    }

    public static void main(String[] args) {
        Runtime runtime = Runtime.getRuntime();

        System.out.printf("maxMemory  = %.1f MiB%n", toMiB(runtime.maxMemory()));
        System.out.printf("totalMemory= %.1f MiB%n", toMiB(runtime.totalMemory()));
        System.out.printf("freeMemory = %.1f MiB%n", toMiB(runtime.freeMemory()));
        System.out.printf("used in committed heap = %.1f MiB%n",
                toMiB(runtime.totalMemory() - runtime.freeMemory()));
    }
}
~~~

Compile and run with JDK 17 or later:

~~~powershell
javac HeapInfo.java
java -Xms64m -Xmx256m HeapInfo
~~~

Meaning of the values:

- `maxMemory()`: the maximum heap limit the JVM reports to the application.
- `totalMemory()`: the amount of heap currently committed by the JVM.
- `freeMemory()`: the free space within the committed heap.
- `totalMemory() - freeMemory()`: an estimate of the used portion within the committed heap at the time of reading.

These metrics change over time and with GC activity. `totalMemory()` does not necessarily always equal `maxMemory()`, because the JVM can commit heap on demand.

### 8.2. Using jcmd to Inspect a Process

**jcmd** ships with the JDK and can send diagnostic commands to a running JVM that the user has permission to access.

List Java processes:

~~~powershell
jcmd -l
~~~

View effective flags of a process:

~~~powershell
jcmd <pid> VM.flags
~~~

View heap information:

~~~powershell
jcmd <pid> GC.heap_info
~~~

Replace `<pid>` with the actual process ID. You can view additional commands supported by the process with:

~~~powershell
jcmd <pid> help
~~~

Do not run diagnostic commands arbitrarily in production without assessing their impact; some operations such as histograms or heap dumps can consume significant CPU, I/O, and pause time.

### 8.3. Viewing GC Logs

From Java 9 onward, unified logging can record GC activity using **-Xlog**:

~~~powershell
java -Xms256m -Xmx1g -Xlog:gc*:file=gc.log:time,uptime,level,tags -jar app.jar
~~~

GC logs let you observe when garbage collection occurs, heap size before/after GC, pause times, and related events. Use the logs alongside application load metrics to determine whether the heap is too small, allocation pressure is high, or objects are being retained abnormally long.

### 8.4. Generating a Heap Dump on Out of Memory

You can instruct the JVM to generate a heap dump when an `OutOfMemoryError` occurs:

~~~powershell
java -Xmx1g -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./heapdump.hprof -jar app.jar
~~~

A heap dump can contain sensitive application data in memory. Protect the dump file, restrict access permissions, and ensure sufficient disk space is available. Analyze the dump with an appropriate tool to find objects consuming the most memory and the reference chains keeping them alive.

## 9. Garbage Collector and Heap Sizing

The heap is managed by the garbage collector. Heap options set capacity limits; the garbage collector decides how to reclaim and organize memory within those limits.

Some common collectors in HotSpot:

- G1 GC: a general-purpose collector that divides the heap into regions and balances throughput with pause goals.
- Parallel GC: prioritizes throughput by using multiple threads for GC phases.
- ZGC: a collector targeting short pauses, suited for certain large-heap applications with low-latency requirements.
- Serial GC: a simple collector, often suited for small applications or resource-constrained environments.

You can specify a collector, for example:

~~~powershell
java -XX:+UseG1GC -Xms512m -Xmx2g -jar app.jar
~~~

Do not switch collectors solely because of an `OutOfMemoryError`. First determine whether the heap is large enough, whether objects are being unintentionally retained, and what pressure the GC logs show. Changing collectors can alter latency, throughput, and RAM usage characteristics.

With G1, **-XX:MaxGCPauseMillis** is a soft pause-time goal that the collector considers during planning; it is not a guarantee that every pause will be shorter than that value. A heap that is too small for the load can still cause frequent GCs even when a pause goal is set.

## 10. Common Heap Configuration Errors

| Symptom | Common Cause | Resolution |
|---|---|---|
| Invalid initial heap size or option error | Invalid -Xms syntax or unit | Check k, m, g suffixes and number formatting |
| Initial heap size set to a larger value than the maximum heap size | -Xms is greater than -Xmx | Set initial heap smaller than or equal to maximum heap |
| OutOfMemoryError: Java heap space | Insufficient max heap, heavy allocation load, or unnecessary reference retention | Analyze heap dump and GC logs; increase -Xmx only after measuring and checking RAM |
| GC overhead limit exceeded | JVM spends too much time in GC while reclaiming very little heap | Look for object retention, abnormal workload, or an undersized heap |
| OutOfMemoryError: Metaspace | Too much class metadata or unreleased classloaders | Analyze class loading and classloader lifecycle; evaluate metaspace limit |
| Container killed even though heap is not full | Total RAM including native memory exceeds limit | Check RSS, direct memory, metaspace, thread stacks, and container limit |
| Heap option has no effect | Option placed after -jar/-m or wrong Java executable run | Place option before the application target; check `java -version` and `VM.flags` |
| Application starts slowly after setting a very large heap | Large initial heap or unsuitable configuration | Measure startup and consider lowering -Xms |

## 11. Pre-Deployment Checklist for Heap Options

- [ ] Identify the Java version and the exact `java` executable being run.
- [ ] Measure heap used, heap committed, and growth under representative load.
- [ ] Choose `-Xms` based on startup needs and initial load.
- [ ] Choose `-Xmx` large enough for the workload while leaving RAM for native memory and the OS.
- [ ] Place heap options before `-jar`, `-m`, or the main class name.
- [ ] If using percentage options, verify that the JVM detects the RAM or container limit accurately.
- [ ] Enable GC logging when analyzing GC pressure.
- [ ] Have a plan to generate and secure heap dumps on `OutOfMemoryError`.
- [ ] Test the configuration under normal load, peak load, and at startup.
- [ ] Monitor both heap and total process memory after deployment.

Heap options are tools for tuning Java heap capacity, primarily through `-Xms` and `-Xmx`. Choose them based on actual usage metrics and the environment's RAM limits. When out-of-memory errors occur, identify the exact memory area and analyze the root cause before increasing limits; the heap is only one part of a JVM process's total memory.
