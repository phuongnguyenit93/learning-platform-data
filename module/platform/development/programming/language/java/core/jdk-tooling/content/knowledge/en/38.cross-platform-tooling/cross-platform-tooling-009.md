# Native Packages for Java Applications

## 1. What is a native package?

A **native package** is an application distribution bundle in a format familiar to the operating system: a Windows installer, a Debian/RPM package, or a macOS disk image. Users can install, launch the application from the menu, and uninstall it using the standard platform workflow.

In the JDK, the primary tool for this task is jpackage. It takes a JAR or Java module, builds an application image, and can create an OS-specific installer. The application image typically contains a launcher, the application files, and a bundled Java runtime. Users do not need to install a JDK or configure JAVA_HOME to run the packaged application.

The launcher created by jpackage still runs Java bytecode on the JVM bundled with the application. It provides a native installation experience, but it does not compile Java bytecode into machine code.

## 2. Distinguishing app image, native installer, and native executable

| Output | Examples | Meaning |
|---|---|---|
| Application image | Application directory with launcher and runtime | Can be run directly or used as input to create an installer |
| Native installer/package | .msi, .exe, .deb, .rpm, .pkg, .dmg | Installs the app, registers shortcuts/menus, and supports OS uninstallation |
| Native executable (AOT) | Binary generated by GraalVM | Java is analyzed and compiled ahead-of-time into a native executable |

jpackage creates the first two types: application images and native installers. GraalVM Native Image is a separate technology for producing AOT executables. A .exe file created by jpackage is not automatically a GraalVM Native Image.

## 3. Tools in the JDK

| Tool | Role |
|---|---|
| javac | Compiles Java source into class files |
| jar | Packages classes and resources into a JAR |
| jdeps | Analyzes dependencies between classes/JARs and JDK modules |
| jlink | Creates a custom Java runtime image from JDK modules and transitive dependencies |
| jpackage | Creates a platform-specific application image or installer |

jpackage was introduced in JDK 14 as an incubating tool and became a standard tool in JDK 16. It is included in the JDK, not in a standalone JRE. Check tool versions:

~~~bash
java --version
javac --version
jpackage --version
jlink --version
jdeps --version
~~~

Use a JDK matching the operating system and architecture of the target package. Do not use jpackage on Windows to directly build macOS or Linux installers.

## 4. Formats by operating system

JDK 24 supports:

| Operating System | Application image | Native installer/package |
|---|---|---|
| Windows | Directory with EXE launcher and runtime | EXE, MSI |
| Linux | Directory with launcher in bin/ and runtime | DEB, RPM |
| macOS | .app bundle | DMG, PKG |

app-image is used to test the application or deliver a self-contained directory to users. It does not provide an installation wizard, menu registration, or uninstallation like an installer.

Each package must be built on its target platform. If releasing for Windows, Linux, and macOS, the pipeline needs corresponding runners and must run jpackage separately on each runner. To produce multiple formats on the same OS, run a separate command for each format.

## 5. Preparing the application before packaging

Before running jpackage, build a runnable JAR or a compiled Java module. A typical application requires:

- The main JAR containing the main class.
- Dependency JARs and resources needed at runtime.
- Application name, version, vendor, description, and copyright.
- Platform-appropriate icon if a custom icon is desired.
- Required JVM options and application arguments.
- License, file associations, shortcuts, or secondary launchers if required by the product.

With Maven:

~~~bash
mvn -B -ntp clean package
~~~

With Gradle:

~~~bash
./gradlew clean build
~~~

Place the main JAR and required dependencies into the jpackage input directory. For classpath applications, use --input to point to the directory containing the files and --main-jar to specify the entry JAR. --main-class is only needed when the JAR manifest does not declare a main class.

For modular applications, use --module-path and --module. Do not pass --module and --main-jar at the same time.

## 6. What does the generated application image contain?

A typical application image contains three parts:

- **Launcher:** executable file for users to open the application.
- **Application payload:** JARs, resources, and launcher configuration.
- **Runtime:** Java runtime image bundled with the application.

Illustrative Windows structure:

~~~text
NativePackageDemo/
  NativePackageDemo.exe
  app/
    NativePackageDemo.cfg
    NativePackageDemo.jar
  runtime/
    bin/
    conf/
    lib/
~~~

On Linux, the launcher is usually located in bin/. On macOS, the application image is a .app bundle with a Contents/ structure. Internal filenames and layout details may vary across JDK versions; avoid writing scripts that depend on undocumented implementation files.

Users run the image's launcher. Do not ask them to run java -jar or install a separate JDK.

## 7. Packaging a non-modular application with jpackage

This example uses a small Java program with no external dependencies.

Create src/demo/NativePackageDemo.java:

~~~java
package demo;

public final class NativePackageDemo {
    public static void main(String[] args) {
        System.out.println("READY Native package");
    }
}
~~~

Compile with JDK 17 or later:

~~~bash
javac --release 17 -d classes src/demo/NativePackageDemo.java
~~~

Create the input directory and package the JAR:

~~~bash
mkdir input
jar --create --file input/NativePackageDemo.jar --main-class demo.NativePackageDemo -C classes .
~~~

Create the application image on Windows:

~~~powershell
jpackage --type app-image --name NativePackageDemo --input input --main-jar NativePackageDemo.jar --main-class demo.NativePackageDemo --dest dist --app-version 1.0.0 --vendor Example --win-console
~~~

Run the generated launcher:

~~~powershell
.\dist\NativePackageDemo\NativePackageDemo.exe
~~~

Exact stdout:

~~~text
READY Native package
~~~

--win-console tells Windows to open a console for applications that require console input/output. Desktop GUI applications typically do not need this option. On Linux and macOS, omit the Windows option and run the launcher according to the platform's image structure.

## 8. Creating a Windows installer

Windows supports two main formats:

- EXE: executable installer.
- MSI: Windows Installer package, which can integrate with enterprise software management tools.

Example creating an MSI:

~~~powershell
jpackage --type msi --name NativePackageDemo --input input --main-jar NativePackageDemo.jar --main-class demo.NativePackageDemo --dest installers --app-version 1.0.0 --vendor Example --win-menu --win-menu-group "Example Tools" --win-shortcut --win-per-user-install
~~~

You can change --type msi to --type exe to create an EXE installer. On JDK 24, Windows installers require WiX Toolset 3.0 or later. Install and verify this toolchain on the runner before running installer jobs.

Common Windows options:

- --win-menu adds the application to the Start Menu.
- --win-menu-group sets the Start Menu group name.
- --win-shortcut creates a desktop shortcut.
- --win-per-user-install installs for the current user.
- --win-dir-chooser lets the user choose the installation directory.
- --win-upgrade-uuid assigns a product upgrade identifier.

If using --win-upgrade-uuid, generate a dedicated UUID for the product and keep that same UUID across upgrade versions. Increment --app-version when releasing a new version. Test fresh installation, upgrade, and uninstallation on a clean Windows machine.

## 9. Creating a Linux package

Linux supports:

- DEB for Debian, Ubuntu, and compatible systems.
- RPM for Fedora, Red Hat Enterprise Linux, and compatible systems.

Example creating a DEB:

~~~bash
jpackage --type deb \
  --name native-package-demo \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --dest installers \
  --app-version 1.0.0 \
  --vendor Example \
  --linux-package-name native-package-demo \
  --linux-menu-group Development \
  --linux-app-category Development \
  --linux-shortcut
~~~

Example creating an RPM:

~~~bash
jpackage --type rpm \
  --name native-package-demo \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --dest installers \
  --app-version 1.0.0 \
  --vendor Example \
  --linux-package-name native-package-demo \
  --linux-app-category Development
~~~

On Linux, the build environment needs the corresponding native tools. Oracle JDK 24 requires rpm-build on Red Hat-based systems to build RPMs and fakeroot on Ubuntu to build DEBs. You can also configure package dependencies, maintainer, license type, release number, and shortcuts using the appropriate Linux options.

Test the package on the target distro or a compatible container. Do not assume a single DEB file will run on every Linux distribution.

## 10. Creating a macOS package

macOS supports:

- DMG: disk image containing the .app application.
- PKG: package installer.

Example creating a DMG:

~~~bash
jpackage --type dmg \
  --name NativePackageDemo \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --dest installers \
  --app-version 1.0.0 \
  --vendor Example \
  --mac-package-identifier com.example.NativePackageDemo
~~~

Example creating a PKG:

~~~bash
jpackage --type pkg \
  --name NativePackageDemo \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --dest installers \
  --app-version 1.0.0 \
  --vendor Example \
  --mac-package-identifier com.example.NativePackageDemo
~~~

--mac-package-identifier should be a stable, unique reverse-domain identifier. If signing the application, use --mac-sign along with a signing identity in Keychain. Xcode Command Line Tools are required when signing packages and customizing DMG icons. For external distribution, complete Apple's code signing and notarization workflow before release.

## 11. Creating a custom Java runtime with jlink

jpackage runs jlink automatically if --runtime-image is not provided. The default runtime works well for many applications. If you want to control size and included modules, you can build the runtime beforehand.

jdeps analyzes JAR dependencies and prints the required JDK modules:

~~~bash
jdeps --print-module-deps input/NativePackageDemo.jar
~~~

For the demo program, the output is:

~~~text
java.base
~~~

Pass that result as input to jlink:

~~~bash
jlink \
  --add-modules java.base \
  --strip-debug \
  --no-man-pages \
  --no-header-files \
  --output runtime
~~~

Inspect modules in the runtime:

~~~bash
runtime/bin/java --list-modules
~~~

On Windows, use runtime\bin\java.exe --list-modules.

Then package the JAR with the newly created runtime:

~~~bash
jpackage --type app-image \
  --name NativePackageDemoCustom \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --runtime-image runtime \
  --dest dist-custom \
  --app-version 1.0.0 \
  --vendor Example
~~~

--runtime-image tells jpackage to use the pre-built runtime instead of invoking jlink itself. A runtime image is OS- and architecture-specific; it must be built for the target package platform.

## 12. Selecting the exact runtime modules

jdeps --print-module-deps is a good starting point, but static analysis does not always cover every module loaded by the application at runtime.

Also check:

- Reflection or dynamic class loading may load classes that jdeps cannot see.
- Service providers may require provider modules. jlink --bind-services links provider modules and their dependencies.
- Swing/AWT applications require the java.desktop module.
- Non-default locales may require jdk.localedata and --include-locales.
- JavaFX, JNI, drivers, codecs, or third-party native libraries require OS/architecture-specific dependencies.
- Resources, certificates, fonts, and configuration files must be placed in the application payload at the right paths.

Example runtime needing both desktop and logging:

~~~bash
jlink \
  --add-modules java.base,java.desktop,java.logging \
  --bind-services \
  --strip-debug \
  --no-man-pages \
  --no-header-files \
  --output runtime
~~~

Only include modules identified from dependencies and testing. An overly small runtime may build an image successfully yet fail when a feature only exercised in production is opened.

## 13. Metadata and launcher customization

Commonly used options:

| Option | Purpose |
|---|---|
| --name | Display name of the application/package |
| --app-version | Application and package version |
| --vendor | Publisher/vendor |
| --description | Short description |
| --copyright | Copyright information |
| --icon | OS-specific icon |
| --license-file | Attach or display a license |
| --arguments | Default arguments for the main class |
| --java-options | Default JVM options |
| --app-content | Add files/directories to the payload |

Example with metadata and JVM options:

~~~bash
jpackage --type app-image \
  --name NativePackageDemo \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --app-version 1.0.0 \
  --vendor Example \
  --description "Java desktop package demonstration" \
  --copyright "Copyright 2026" \
  --java-options "-Xms64m" \
  --java-options "-Xmx512m" \
  --arguments "--safe-mode" \
  --dest dist
~~~

JVM options are baked into the launcher; users cannot pass arbitrary JVM options as they would when invoking the java command. Inspect the launcher configuration file in the app/ directory if you need to verify that values were written properly.

## 14. Creating multiple launchers and file associations

An application may need multiple launchers, such as a main launcher and an admin launcher. Use --add-launcher with a properties file.

Example admin.properties:

~~~properties
main-jar=NativePackageDemo.jar
main-class=demo.NativePackageDemo
arguments=--mode,admin
java-options=-Xmx512m
win-console=true
~~~

Create the secondary launcher:

~~~bash
jpackage --type app-image \
  --name NativePackageDemo \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --add-launcher Admin=admin.properties \
  --dest dist
~~~

To open a file type with the application, create a properties file:

~~~properties
extension=demo
mime-type=application/x-native-package-demo
description=Native Package Demo file
~~~

Pass that file via --file-associations:

~~~bash
jpackage --type app-image \
  --name NativePackageDemo \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --file-associations demo-file.properties \
  --dest dist
~~~

File associations and shortcuts behave differently across operating systems. Verify registration, file opening, uninstallation, and association restoration when users install a new version.

## 15. Packaging from an existing application image

The workflow can be split into two steps:

1. Create an app image for testing or adjustment.
2. Use the verified app image to build the installer.

Example creating the image:

~~~bash
jpackage --type app-image \
  --name NativePackageDemo \
  --input input \
  --main-jar NativePackageDemo.jar \
  --main-class demo.NativePackageDemo \
  --dest app-images
~~~

After verification, create the installer from the image:

~~~powershell
jpackage --type msi --name NativePackageDemo --app-image app-images/NativePackageDemo --dest installers --app-version 1.0.0 --vendor Example --win-menu --win-shortcut
~~~

Use --app-image when you want to repackage a tested image. Ensure the image was created on the matching OS/architecture and all files were included before the installer step.

## 16. Cross-platform release in CI/CD

Because jpackage does not create installers for an OS different from the host, pipelines should run jobs on each OS:

| Runner | Package type | Artifact |
|---|---|---|
| Windows x64 | MSI or EXE | Windows installer |
| Ubuntu x64 | DEB | Debian/Ubuntu package |
| Linux RPM runner | RPM | RPM package |
| macOS runner | DMG or PKG | macOS disk image or installer |

A typical workflow includes:

1. Check out source and set a pinned JDK version.
2. Build/test the JAR or module with Maven/Gradle.
3. Prepare the input directory containing the JAR, dependencies, and resources.
4. Run jpackage on the corresponding runner.
5. Smoke test the app image or install the package on the target environment.
6. Sign the package according to platform policy.
7. Generate checksums, store artifacts, and attach version/release metadata.

Do not build on one OS and simply rename the file extension to release for another OS. Installers require launchers, runtimes, bundle structures, and metadata suited to the target platform.

## 17. Signing and securing release packages

Code signing helps the operating system and users verify the package origin and detect tampering after signing.

- **Windows:** sign EXE/MSI with Authenticode and a publisher certificate, typically using Windows SDK SignTool after jpackage produces the package.
- **macOS:** use --mac-sign and a valid signing identity in Keychain; complete Apple's notarization workflow when distributing outside test environments.
- **Linux:** distribute via repositories with signed metadata; verify checksums and signatures according to package repository policy.

Never place private signing keys or certificate passwords into the application image, JAR, or build cache. Store secrets in the CI secret store, restrict which jobs are allowed to sign, and retain release logs/audit trails.

Generate checksums after packaging completes:

~~~powershell
Get-FileHash .\installers\NativePackageDemo-1.0.0.msi -Algorithm SHA256
~~~

On Linux/macOS:

~~~bash
sha256sum installers/NativePackageDemo-1.0.0.deb
~~~

## 18. jpackage vs. GraalVM Native Image

jpackage and GraalVM Native Image address different needs:

| Criterion | jpackage | GraalVM Native Image |
|---|---|---|
| Input | JAR or Java module | Bytecode, dependencies, and reachability metadata |
| Output | App image or installer containing a Java runtime | AOT-compiled native executable |
| Execution model | Launcher invokes the bundled JVM | Binary runs on a linked native runtime |
| Startup | Incurs JVM startup time | Typically faster startup |
| Reflection compatibility | Full JVM runtime support | Requires metadata when static analysis cannot determine dynamic elements |
| Toolchain | JDK and OS packaging tools | GraalVM Native Image and OS C/C++ compiler/toolchain |

Native Image performs static reachability analysis. Reflection, JNI, dynamic proxies, resources, and serialization may require reachability metadata. Applications relying heavily on dynamic frameworks must be tested thoroughly because classes or resources omitted from the image can cause runtime failures.

Native Image fits best when you need an AOT executable, fast startup, or a low runtime footprint. If the goal is to provide a familiar installer, bundle the JVM, and integrate with OS menus/shortcuts, jpackage is usually the direct choice.

Native Image must also be built for the target OS/architecture. On Windows it requires MSVC and Windows SDK; on Linux/macOS it requires the corresponding native toolchain.

## 19. Testing packages before release

A successful build only confirms that the tool could produce a package. Test the packaged product afterward:

- Run the app image on a clean machine without a JDK installed.
- Install the installer using a regular user account if per-user install is supported.
- Launch the application from the Start Menu, desktop shortcut, Dock, or application menu.
- Verify resources, configuration files, fonts, locales, timezones, and certificates.
- Verify file associations, default arguments, and JVM options.
- Verify write permissions to data directories; do not write logs or configuration into the installation directory if users lack write access.
- Test upgrading from a previous version, rollback if applicable, and uninstallation.
- Run smoke tests on every published OS and architecture.

Testing on a clean VM or runner helps catch accidental dependencies on a JDK, files, or environment variables present on a developer machine.

## 20. Common issues

### WiX not found when creating MSI/EXE

Check WiX Toolset and PATH on the Windows runner. JDK 24 requires WiX 3.0 or later for Windows installers. You can create an app-image first to test the application while preparing the installer toolchain.

### Package builds successfully, but the launcher fails to run

Check --main-jar, --main-class, the manifest, dependency JARs, and resources. Run the JAR with a clean JDK before packaging, then run the app image launcher.

### Missing modules after using jlink

Re-run jdeps, check dependency JARs, and inspect dynamic call paths. Add missing modules with --add-modules; if using service providers, consider --bind-services.

### Application cannot find configuration files

Do not assume the working directory is the installation directory. Use resource paths relative to the application directory or store user data in the appropriate OS data directory.

### Runtime image is too large

Review which modules are actually needed, run jdeps --print-module-deps, build the runtime with jlink, and measure the image again. Do not remove modules just to shrink size without testing the corresponding features.

### Package runs on the build machine but fails on other machines

Check OS/architecture, native libraries, permissions, runtime modules, locales, and external files. Test on a clean environment of the target platform.

### Upgrade installs as a separate product

Check application name, app version, package identifier, and upgrade UUID. On Windows, keep --win-upgrade-uuid consistent for the same product across versions.

### macOS blocks unsigned application

Check the code signing identity, certificate chain, and notarization workflow. Verify the signed bundle before releasing.

## 21. Hands-on lab

Follow these steps in order on JDK 17+:

1. Create NativePackageDemo.java as shown in the example.
2. Compile the source with javac --release 17.
3. Create the JAR in the input directory.
4. Run the JAR directly to verify stdout.
5. Use jpackage --type app-image to create the application image.
6. Run the generated launcher and verify stdout.
7. Run jdeps --print-module-deps to inspect required JDK modules.
8. Use jlink to create a runtime image.
9. Repackage using --runtime-image.
10. Run the new app image and compare the sizes of both images.
11. On the corresponding OS runner, create an installer and test installing/uninstalling it.

In a test run with Azul JDK 24.0.2 on Windows x64, the demo application was compiled with javac --release 17, packaged into a JAR, and bundled into a Windows app image. The launcher ran successfully and printed:

~~~text
READY Native package
~~~

jdeps returned java.base. The runtime built with jlink using this module was passed to jpackage via --runtime-image; the custom image's launcher also printed the same stdout. In that test environment, the app image using the default runtime was 120.45 MiB; the image using the custom runtime containing only java.base was 44.51 MiB. These measurements are for the demo program on one machine, not a fixed size for every application.

## 22. Pre-release checklist

- [ ] JAR/module built and tested independently.
- [ ] Required dependencies and resources placed in input.
- [ ] Correct OS, architecture, and package type selected.
- [ ] Name, version, vendor, description, and icon configured.
- [ ] Runtime image includes all required modules and service providers.
- [ ] App image runs on a clean machine without a JDK installed.
- [ ] Shortcuts, menus, file associations, and default arguments tested.
- [ ] Installer tested for fresh install, upgrade, and uninstall.
- [ ] Package signed according to platform policy.
- [ ] Checksums generated and release artifacts stored.
- [ ] JDK version, build flags, and toolchain used for packaging recorded.
- [ ] Separate jpackage pipeline jobs configured for each supported OS/architecture.
