# Constant Pool in Java Class Files

## 1. What Is the Constant Pool?

When javac compiles a Java file, the compiler produces a bytecode file containing a structural section called the **constant pool**. This is an indexed data table that stores constant values and information that bytecode needs to reference, such as:

- Names of classes, interfaces, fields, and methods.
- Descriptors describing data types and method signatures.
- String literals and numeric constants.
- Symbolic references to classes, fields, methods, and interface methods.
- Method handles, method types, dynamic constants, and information related to invokedynamic.
- Module and package names in class files that use the module system.

The constant pool is part of the class file format specified in the JVM Specification. The JVM relies on this table to understand bytecode, load classes, and link references at runtime.

The constant pool should not be understood simply as a list of every variable or every object in a program. It is a data structure of the class file, consisting of strongly typed entries that can reference one another by index. Actual Java objects are created in memory when the program runs; the constant pool is not a heap region containing all objects.

## 2. Where Is the Constant Pool Located in a Class File?

A class file has the following general structure:

~~~text
ClassFile {
    magic
    minor_version
    major_version
    constant_pool_count
    constant_pool[]
    access_flags
    this_class
    super_class
    interfaces_count
    interfaces[]
    fields_count
    fields[]
    methods_count
    methods[]
    attributes_count
    attributes[]
}
~~~

The first components serve the following roles:

- **magic**: the class file identification value, always 0xCAFEBABE.
- **minor_version** and **major_version**: the class file format version.
- **constant_pool_count**: the number of entries in the table plus one, according to class file indexing rules.
- **constant_pool[]**: constant entries and symbolic references.
- **this_class** and **super_class**: indices pointing to Class-type entries in the constant pool.
- Fields, methods, and attributes can continue to reference entries in the constant pool.

The constant pool appears immediately after the magic and version fields. It is used throughout the class file: class names, method names, descriptors, bytecode, and many attributes can all contain indices pointing back to this table.

For example, for a class file generated by javac --release 17, the javap tool displays the major version as **61**. The class file version indicates the target bytecode format; it is not the number of entries in the constant pool.

## 3. Indexing and Important Rules

The constant pool uses **1**-based indexing. Index 0 does not represent a valid entry. The constant_pool_count field has a value equal to the number of representable indices plus one according to the format structure; valid entries lie in the range from 1 to constant_pool_count - 1, taking into account the rule for two-slot entries.

Key points to remember:

1. Each entry begins with a **tag** byte that identifies the data type.
2. The subsequent fields of an entry have lengths and meanings that depend on the tag.
3. Entries can reference other entries by index.
4. **CONSTANT_Long** and **CONSTANT_Double** occupy two consecutive index positions. The second position is not an independent entry and must not be referenced like a regular entry.
5. Do not assume that constant pool indices remain the same across two compilations. The compiler may order or add entries differently.

Illustrative example:

~~~text
#10 = Class       #12
#12 = Utf8        demo/OrderService
#13 = Utf8        save
#14 = Utf8        (Ljava/lang/String;)V
#11 = NameAndType #13:#14
#9  = Methodref   #10.#11
~~~

This is a conceptual representation: a Methodref entry combines a Class entry with a NameAndType entry; NameAndType combines a method name with a descriptor. The numbers #9, #10... only have meaning within a specific class file.

## 4. Common Constant Pool Entry Types

Each entry has an integer tag that defines its structure. The tags below belong to the modern class file format; some tags were added in later Java versions.

| Tag | Entry Name | Purpose |
|---:|---|---|
| 1 | CONSTANT_Utf8 | Stores strings used for names, descriptors, and text content |
| 3 | CONSTANT_Integer | 32-bit integer constant |
| 4 | CONSTANT_Float | 32-bit floating-point constant |
| 5 | CONSTANT_Long | 64-bit integer constant, occupies two slots |
| 6 | CONSTANT_Double | 64-bit floating-point constant, occupies two slots |
| 7 | CONSTANT_Class | References a class or interface name |
| 8 | CONSTANT_String | References a String literal |
| 9 | CONSTANT_Fieldref | References a field of a class |
| 10 | CONSTANT_Methodref | References a method of a class |
| 11 | CONSTANT_InterfaceMethodref | References a method of an interface |
| 12 | CONSTANT_NameAndType | Pairs a member name with a descriptor |
| 15 | CONSTANT_MethodHandle | Describes a method handle |
| 16 | CONSTANT_MethodType | Describes a method type |
| 17 | CONSTANT_Dynamic | Constant dynamically linked via a bootstrap method |
| 18 | CONSTANT_InvokeDynamic | Dynamic call site linked via a bootstrap method |
| 19 | CONSTANT_Module | Module name |
| 20 | CONSTANT_Package | Package name in a module context |

Several groups of entries were added according to class file versions:

- **MethodHandle**, **MethodType**, and **InvokeDynamic** appeared in Java 7 (class file version 51).
- **Module** and **Package** appeared in Java 9 (version 53).
- **Dynamic** appeared in Java 11 (version 55).

Older JVMs and compilers do not necessarily understand tags added in newer versions. When a class file uses new entries, the runtime must support the corresponding format version.

## 5. CONSTANT_Utf8, Class, and String

### CONSTANT_Utf8

**CONSTANT_Utf8** stores strings used by the class file for class names, method names, field names, descriptors, attribute names, and other text constants.

The tag name is Utf8, but the data is encoded in **Modified UTF-8** of the class file format; it should not be assumed to be standard UTF-8 of every system. Tools such as javap decode and display the content in a human-readable form.

Example:

~~~text
#12 = Utf8  demo/OrderService
#13 = Utf8  save
#14 = Utf8  (Ljava/lang/String;)V
~~~

### CONSTANT_Class

A **CONSTANT_Class** entry points to a Utf8 entry containing a class or interface name. For ordinary class names, the internal name uses slashes / instead of dots ..

Example:

~~~text
#10 = Class  #12  // demo/OrderService
#12 = Utf8         // demo/OrderService
~~~

A descriptor of a reference type has the form Ljava/lang/String;. Descriptors for arrays, primitives, and methods follow their own JVM rules.

### CONSTANT_String

A **CONSTANT_String** entry points to a Utf8 entry containing the content of a String literal:

~~~text
#40 = String  #41  // JDK
#41 = Utf8          // JDK
~~~

A String entry in a class file is not itself a String object stored in the bytecode table. When the JVM processes a string literal, it creates or reuses a canonical String object according to Java's rules; equivalent string literals are interned.

The **String pool** often mentioned when discussing String.intern() is the mechanism for canonicalizing String objects at runtime. It is related to string literal handling, but it is not identical to the constant_pool structure in a .class file.

## 6. Symbolic References: Fieldref, Methodref, and NameAndType

The constant pool stores many references by name and descriptor rather than direct memory addresses. Those references are called **symbolic references**.

### CONSTANT_NameAndType

This entry combines:

- An index to a Utf8 entry containing the field or method name.
- An index to a Utf8 entry containing the descriptor.

Example:

~~~text
#13 = Utf8         name
#14 = Utf8         Ljava/lang/String;
#11 = NameAndType  #13:#14  // name:Ljava/lang/String;
~~~

The descriptor Ljava/lang/String; describes a field of type java.lang.String.

For a method, the descriptor contains the list of parameter types in parentheses followed by the return type. For example, (I)Ljava/lang/String; means it takes one int parameter and returns a String. ()V means it takes no parameters and returns void.

### CONSTANT_Fieldref

A **Fieldref** entry combines the declaring class of the field with a NameAndType:

~~~text
#9 = Fieldref  #10.#11  // demo/OrderService.name:Ljava/lang/String;
~~~

Bytecode instructions such as getfield, putfield, getstatic, and putstatic use the appropriate field reference index.

### CONSTANT_Methodref and InterfaceMethodref

**Methodref** is used for referencing a class method; **InterfaceMethodref** is used for referencing an interface method. They combine the class/interface name with the method name and descriptor.

Bytecode instructions such as invokevirtual, invokespecial, invokestatic, and invokeinterface reference the corresponding entry in the constant pool. Class lookup, access checking, and method resolution are performed by the JVM according to its linking rules.

Symbolic references avoid storing RAM addresses of methods or fields in the class file. Actual addresses and runtime structures can only be determined during loading, linking, and execution.

## 7. CONSTANT_Integer, Float, Long, and Double

The constant pool has entries for numeric values:

- **Integer**: 32-bit integer value.
- **Float**: 32-bit floating-point value.
- **Long**: 64-bit integer value.
- **Double**: 64-bit floating-point value.

Example:

~~~text
#38 = Integer 42
#39 = Float   3.14f
#40 = Long    9000000000l
#42 = Double  2.71828d
~~~

Long and Double occupy two slots in the table. For example, after a Long entry, the next index is reserved and does not hold an independent entry. Therefore, you cannot always count the number of lines in javap output to deduce constant_pool_count.

Not every number in source code is required to have a constant pool entry. The compiler can use bytecode instructions with immediate operands such as iconst, bipush, or sipush for suitable values. Other values can be loaded using ldc, ldc_w, or ldc2_w.

## 8. ConstantValue and Compile-Time Constants

A class file has a **ConstantValue** attribute to provide the initial value for certain static fields. This attribute is not an independent entry tag in the constant pool; its constantvalue_index field points to the appropriate constant entry.

Example:

~~~java
public class Constants {
    public static final int LIMIT = 42;
    public static final String LABEL = "JDK";
    public static final Integer BOXED = 42;
}
~~~

With javap -v, the field section may display:

~~~text
static final int LIMIT;
  descriptor: I
  flags: ACC_PUBLIC, ACC_STATIC, ACC_FINAL
  ConstantValue: int 42

static final java.lang.String LABEL;
  descriptor: Ljava/lang/String;
  flags: ACC_PUBLIC, ACC_STATIC, ACC_FINAL
  ConstantValue: String JDK
~~~

Java defines a **constant variable** as a final variable of primitive type or String initialized with a constant expression. LIMIT and LABEL in the example are constant variables; BOXED is not because its type is Integer, neither a primitive nor String.

The compiler can embed the value of a constant variable directly into the bytecode of the calling class. This is commonly called **constant inlining**.

Example:

~~~java
public class Client {
    public static void main(String[] args) {
        System.out.println(Constants.LIMIT);
        System.out.println(Constants.LABEL);
        System.out.println(Constants.BOXED);
    }
}
~~~

When inspecting the bytecode of Client, you may see something similar to:

~~~text
bipush        42
ldc           // String JDK
getstatic     // demo/Constants.BOXED:Ljava/lang/Integer;
~~~

The primitive and String values are embedded into the bytecode of Client; the Integer field is still read via a field reference at runtime.

Important consequence: if a library changes the value of a public static final constant variable, previously compiled clients may still retain the old value. Dependent clients must be recompiled to pick up the updated inlined value. This is a binary compatibility concern to consider when designing library APIs.

## 9. What Is the Runtime Constant Pool?

When the JVM creates a runtime representation for a class or interface, it creates a corresponding **runtime constant pool**. The runtime constant pool is constructed from the constant_pool structure in the class file and serves loading, linking, resolving symbolic references, and handling dynamic values.

Distinguishing the two concepts:

| Class-file constant_pool | Runtime constant pool |
|---|---|
| Resides in the .class file | Exists in the runtime representation of the class/interface |
| Has entry structures and indices per the JVM Specification | Created by the JVM from the class file when the class is created |
| Stores constant values and symbolic references | Used during linking and execution |
| Can be inspected with javap -v | Cannot be read directly as a class file table stored on disk |

The runtime constant pool is not a byte-for-byte copy that an application can modify directly. The JVM may represent resolved references in its own internal way.

During **resolution**, the JVM converts symbolic references into appropriate runtime references, such as identifying the referenced class, field, or method. Resolution can be performed eagerly or lazily depending on the JVM implementation, within the bounds defined by the JVM Specification.

If a reference cannot be resolved, the JVM may throw a corresponding linkage error such as NoClassDefFoundError, NoSuchFieldError, NoSuchMethodError, or an access error. Therefore, a class file may compile successfully yet fail at runtime if dependencies or actual APIs are incompatible.

## 10. MethodHandle, MethodType, Dynamic, and InvokeDynamic

Newer Java versions extend the constant pool to support dynamic invocation and flexible linking mechanisms.

### MethodHandle and MethodType

**CONSTANT_MethodHandle** describes a handle pointing to a field or method with a specific reference kind. **CONSTANT_MethodType** describes a method signature type.

These structures form the foundation for the java.lang.invoke API, including MethodHandle and MethodType. They allow the runtime to represent method invocation operations flexibly without relying solely on traditional invoke mechanisms.

### InvokeDynamic

**CONSTANT_InvokeDynamic** describes a call site linked through a bootstrap method. This entry contains an index to a bootstrap entry in the BootstrapMethods attribute and a NameAndType index describing the name and descriptor of the call site.

The invokedynamic bytecode references an InvokeDynamic entry. When linking the call site, the JVM invokes the bootstrap method to obtain a CallSite and uses that call site's target method handle for subsequent invocations.

An easily observable case is string concatenation in modern javac. Since Java 9, javac typically compiles string concatenation using invokedynamic and a bootstrap method from StringConcatFactory. This is a compiler/runtime implementation detail; do not assume every compiler or every version always generates identical bytecode.

### BootstrapMethods attribute

The **BootstrapMethods** attribute resides in the class-level attribute list. It contains the bootstrap method handles and bootstrap arguments referenced by Dynamic or InvokeDynamic entries.

For example, javap output might show:

~~~text
#15 = InvokeDynamic #0:#16
#51 = MethodHandle ... StringConcatFactory.makeConcatWithConstants
...
BootstrapMethods:
  0: REF_invokeStatic StringConcatFactory.makeConcatWithConstants
     Method arguments:
       #49 Hello, \u0001 #\u0001 JDK 42
~~~

The \u0001 placeholders in the StringConcatFactory recipe mark positions where dynamic values are inserted. This is an example of how the compiler represents string concatenation; applications do not need to create these entries manually.

### Dynamic constant

**CONSTANT_Dynamic** (often called condy) describes a constant computed or linked via a bootstrap method. It differs from InvokeDynamic: Dynamic produces a constant value for the constant pool; InvokeDynamic produces a call site for an invocation.

Dynamic constants were added to class files in Java 11. They support values that can be initialized dynamically while still being represented as constants in the constant pool.

## 11. How Bytecode Uses the Constant Pool

Many bytecode instructions contain constant pool indices:

| Instruction | Common Purpose |
|---|---|
| ldc, ldc_w | Load a constant from the constant pool |
| ldc2_w | Load a Long or Double constant |
| getfield, putfield | Read/write an instance field via Fieldref |
| getstatic, putstatic | Read/write a static field via Fieldref |
| invokevirtual | Invoke an instance method via Methodref |
| invokespecial | Invoke a constructor or special method |
| invokestatic | Invoke a static method |
| invokeinterface | Invoke an interface method |
| invokedynamic | Invoke a dynamically linked call site |

When javap displays:

~~~text
5: getfield      #9  // Field name:Ljava/lang/String;
12: invokevirtual #26 // Method greet:(I)Ljava/lang/String;
~~~

The index #9 or #26 points to an entry in the constant pool of the class file being inspected. The trailing comment is how javap decodes the entry into a field or method name for readability.

Do not record numbers like #9 or #26 from one compilation in documentation as if they were fixed. When source code, compiler versions, or compilation options change, the entry ordering may change.

## 12. Hands-On: Compiling and Inspecting the Constant Pool with javap

Create the directory structure:

~~~text
project/
  src/
    demo/
      ConstantPoolDemo.java
  out/
~~~

Create the file src/demo/ConstantPoolDemo.java:

~~~java
package demo;

public class ConstantPoolDemo {
    static final int LIMIT = 42;
    static final String LABEL = "JDK";
    private String name = "Ada";

    public String greet(int number) {
        return "Hello, " + name + " #" + number + " " + LABEL + " " + LIMIT;
    }

    public static void main(String[] args) {
        System.out.println(new ConstantPoolDemo().greet(7));
    }
}
~~~

Compile targeting Java 17:

~~~bash
javac --release 17 -d out src/demo/ConstantPoolDemo.java
~~~

Run:

~~~bash
java -cp out demo.ConstantPoolDemo
~~~

Expected output:

~~~text
Hello, Ada #7 JDK 42
~~~

Inspect the constant pool and attributes:

~~~bash
javap -v -cp out demo.ConstantPoolDemo
~~~

Or view both bytecode and the constant pool together:

~~~bash
javap -c -v -cp out demo.ConstantPoolDemo
~~~

In the output, look for the Constant pool: section. A compilation with a Java 17-compatible javac may produce entries similar to:

~~~text
#1  = Methodref       #2.#3
#2  = Class           #4             // java/lang/Object
#7  = String          #8             // Ada
#9  = Fieldref        #10.#11        // demo/ConstantPoolDemo.name:Ljava/lang/String;
#15 = InvokeDynamic   #0:#16         // makeConcatWithConstants
#35 = Utf8            LIMIT
#38 = Integer         42
#39 = Utf8            LABEL
#41 = Utf8            JDK
#48 = Utf8            BootstrapMethods
~~~

Indices and entry counts may vary across compiler versions or compilation options. Focus on the tags and reference relationships rather than relying on specific index numbers.

In the field declarations section, javap may display:

~~~text
static final int LIMIT;
  descriptor: I
  flags: ACC_PUBLIC, ACC_STATIC, ACC_FINAL
  ConstantValue: int 42

static final java.lang.String LABEL;
  descriptor: Ljava/lang/String;
  flags: ACC_PUBLIC, ACC_STATIC, ACC_FINAL
  ConstantValue: String JDK
~~~

In the greet method section, you can observe the getfield instruction reading the name field and the invokedynamic instruction performing string concatenation. The BootstrapMethods attribute at the end of the class file shows the bootstrap method being used.

## 13. Common Misconceptions

### The constant pool is the same as the String pool

Incorrect. The constant pool is a table of entries in a class file. The String pool is a runtime mechanism related to interning and reusing canonical Strings. A CONSTANT_String entry may cause the JVM to create or retrieve an interned String literal, but the two concepts serve different roles.

### Every literal must be in the constant pool

Incorrect. The compiler can use bytecode instructions that embed small values directly, such as iconst_0, bipush, or sipush. Other values may use ldc and the constant pool. The representation depends on the value type and compiler choices.

### The constant pool stores RAM addresses of methods

Incorrect. Fieldref and Methodref are symbolic references consisting of a class name, member name, and descriptor. The JVM resolves them during linking; a class file does not contain fixed RAM addresses.

### All classes share a single constant pool table

Incorrect. Each class file has its own constant pool. When a class or interface is created in the JVM, it has a corresponding runtime constant pool. Classes may reference the same types or strings, but that does not turn the class-file tables into a single shared table.

### Index numbers #n are fixed

Incorrect. Indices only have meaning within a specific class file. Do not use constant pool indices to identify a method across builds; read the tag, name, descriptor, and content decoded by javap.

### Changing a constant in a library automatically updates all applications

Incorrect for inlined compile-time constants. Already-compiled clients may contain the old value directly in their bytecode. Clients must be recompiled to receive the new value.

## 14. Checklist for Analyzing the Constant Pool

- [ ] Identify the class file and version using javap -v.
- [ ] Locate the Constant pool: section and identify each entry's tag.
- [ ] Distinguish Utf8, Class, String, NameAndType, and symbolic references.
- [ ] Remember that Long and Double occupy two slots.
- [ ] Read descriptors to understand field types and method signatures.
- [ ] Use javap -c -v to correlate constant pool indices with bytecode instructions.
- [ ] Check ConstantValue when analyzing static final constant variables.
- [ ] Recognize InvokeDynamic, MethodHandle, and BootstrapMethods when analyzing lambdas or string concatenation.
- [ ] Distinguish between the class-file constant_pool, runtime constant pool, and String pool.
- [ ] Do not rely on #n index numbers across builds.
- [ ] When changing a compile-time constant in a library, consider recompiling dependent clients.
