# Creating JARs with the `jar` Tool

## 1. What Is a JAR and When Should You Create One?

A JAR (Java Archive) is a ZIP-based archive file used to package Java bytecode, resources, and metadata into a single distributable artifact. A JAR can contain:

- `.class` files generated by the compiler.
- Resources such as `.properties`, `.xml`, `.json`, images, or UI templates.
- A manifest at `META-INF/MANIFEST.MF`.
- A module descriptor `module-info.class` if it is a modular JAR.
- Other metadata for packaging or distribution.

JARs combine multiple files into a single unit that is easy to store, share, and place on the classpath or module path. A library JAR typically provides classes for other applications to use; an executable JAR includes entry-point information so users can run it with `java -jar`.

The `jar` tool is included in the JDK. It creates, lists, updates, and extracts archives. This tool does not compile Java source code itself; use `javac` to generate `.class` files before packaging.

## 2. Input Structure Before Creating a JAR

Suppose a project has one Java class and one resource file:

~~~text
project/
├── src/
│   └── com/
│       └── example/
│           └── Hello.java
├── resources/
│   └── config/
│       └── greeting.txt
├── out/
└── dist/
~~~

Contents of `src/com/example/Hello.java`:

~~~java
package com.example;

import java.io.IOException;
import java.io.InputStream;
import java.nio.charset.StandardCharsets;

public class Hello {
    public static void main(String[] args) throws IOException {
        String name = args.length == 0
                ? "Java"
                : String.join(" ", args);

        try (InputStream input =
                     Hello.class.getResourceAsStream("/config/greeting.txt")) {
            if (input == null) {
                throw new IllegalStateException("Missing greeting resource");
            }

            String greeting = new String(
                    input.readAllBytes(), StandardCharsets.UTF_8).trim();

            System.out.println(greeting + ", " + name + "!");
        }
    }
}
~~~

Contents of `resources/config/greeting.txt`:

~~~text
Hello
~~~

The class reads the resource using `getResourceAsStream("/config/greeting.txt")`. The leading `/` in the path means looking up from the root of the classpath or corresponding module. Therefore, when packaged, the file must appear inside the JAR at `config/greeting.txt`.

## 3. Compiling Source Code Before Packaging

Create the output directories and compile the class:

~~~bash
mkdir -p out dist
javac --release 17 -encoding UTF-8 -d out src/com/example/Hello.java
~~~

On Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force out, dist | Out-Null
javac --release 17 -encoding UTF-8 -d out src/com/example/Hello.java
~~~

The `-d out` option places the bytecode in the `out` directory. Because the class declares the `com.example` package, the compiler generates the file:

~~~text
out/com/example/Hello.class
~~~

The `out` directory is the root of the bytecode tree. When adding it to the JAR, keep the `com/example/Hello.class` structure at the root of the archive so the Java launcher can locate the `com.example.Hello` class.

Do not package `.java` files instead of `.class` files when the goal is a standard JVM-executable JAR. Source files can be included in an archive if a project specifically requires them, but they do not replace compiled bytecode.

## 4. Creating a Basic JAR with `jar --create`

General syntax:

~~~bash
jar --create --file <archive.jar> [options] [-C <directory> <files>...]
~~~

Common options and arguments:

| Component | Meaning |
|---|---|
| `--create` or `-c` | Selects the mode to create a new archive. |
| `--file` or `-f` | Specifies the output JAR file name and path. |
| `-C directory files` | Changes into the specified directory and adds the files/directories relative to it. |
| `--verbose` or `-v` | Prints the names of entries added to the archive. |
| `--main-class` or `-e` | Declares the entry-point class for an executable JAR or modular JAR. |
| `--manifest` or `-m` | Uses a user-supplied manifest file. |

Create a JAR containing the bytecode and resources from the example:

~~~bash
jar --create --file dist/hello.jar --main-class com.example.Hello -C out . -C resources .
~~~

Command breakdown:

1. `--create` creates a new archive.
2. `--file dist/hello.jar` sets the output JAR file name.
3. `--main-class com.example.Hello` declares the class containing the `main` method.
4. `-C out .` changes into `out` and adds all contents of that directory.
5. `-C resources .` changes into `resources` and adds all resources from that directory.

You can enable verbose mode to inspect the entries being added:

~~~bash
jar --create --verbose --file dist/hello.jar --main-class com.example.Hello -C out . -C resources .
~~~

The `-C` option can appear multiple times. Each occurrence changes the working directory of `jar` for the items that follow it. Using `-C out .` places the files in `out` at the root of the JAR; if you add the `out` directory directly without changing into it, the archive may contain `out/com/example/Hello.class`, causing the classpath not to match the class name.

## 5. JAR Structure After Creation

List the archive contents:

~~~bash
jar --list --file dist/hello.jar
~~~

The main entries in the example will look like:

~~~text
META-INF/
META-INF/MANIFEST.MF
com/example/Hello.class
config/greeting.txt
~~~

By default, a JAR includes a manifest generated by the tool. When `--main-class` is used, the manifest contains a `Main-Class` attribute pointing to the entry-point class.

You can inspect the manifest by extracting the archive or opening the JAR with a ZIP tool. The key contents will look similar to:

~~~text
Manifest-Version: 1.0
Created-By: ...

Main-Class: com.example.Hello

~~~

Some attributes such as `Created-By` may vary depending on the JDK. What you need to verify is that `Main-Class` has the correct fully qualified class name and that the manifest is validly formatted.

## 6. Running an Executable JAR

Once the JAR has `Main-Class`, run it with:

~~~bash
java -jar dist/hello.jar Ada
~~~

Stdout:

~~~text
Hello, Ada!
~~~

There is no need to pass the class name after the JAR file name because the launcher reads the entry point from the manifest. Arguments placed after the JAR file name are passed to `main(String[] args)`.

If run without arguments:

~~~bash
java -jar dist/hello.jar
~~~

Stdout:

~~~text
Hello, Java!
~~~

The `java -jar` command requires the JAR to have a manifest declaring `Main-Class`. If the JAR is only a library or the manifest lacks this attribute, the launcher reports no main manifest attribute. In that case, run it using the classpath and the fully qualified class name:

~~~bash
java -cp dist/library.jar com.example.SomeMain
~~~

A regular library JAR does not need `Main-Class`; only add an entry point when the archive is intended to run standalone.

## 7. Creating a Custom Manifest

When you need to declare additional metadata, you can create a separate manifest file, for example `manifest.mf`:

~~~text
Manifest-Version: 1.0
Main-Class: com.example.Hello
Implementation-Title: Hello Demo
Implementation-Version: 1.0.0

~~~

The trailing blank line is required to terminate the main manifest section. The class name in `Main-Class` must be the fully qualified name without the `.class` extension.

Create the JAR using this manifest:

~~~bash
jar --create --file dist/hello.jar --manifest manifest.mf -C out . -C resources .
~~~

Then run it:

~~~bash
java -jar dist/hello.jar Ada
~~~

There are two common ways to set the entry point:

- Use `--main-class com.example.Hello` directly in the `jar` command.
- Declare `Main-Class: com.example.Hello` in a manifest file and pass `--manifest manifest.mf`.

Choose one place as the primary source of configuration to avoid confusion when manifests are generated or updated in a pipeline. Manifest files have specific formatting rules; if an attribute line is long, use manifest line continuation rather than breaking lines arbitrarily.

## 8. Declaring Dependent Libraries in the Manifest

An executable JAR does not automatically bundle all libraries used by the application. If the application depends on external JARs, you can declare `Class-Path` in the manifest.

Example distribution layout:

~~~text
dist/
├── app.jar
└── lib/
    ├── library-a.jar
    └── library-b.jar
~~~

Manifest `manifest.mf`:

~~~text
Manifest-Version: 1.0
Main-Class: com.example.Main
Class-Path: lib/library-a.jar lib/library-b.jar

~~~

Create the JAR:

~~~bash
jar --create --file dist/app.jar --manifest manifest.mf -C out .
~~~

When running `java -jar dist/app.jar`, the Java launcher reads the manifest entries and adds the declared JARs to the class search path. `Class-Path` entries are relative URLs resolved against the location of the JAR containing the manifest; they are not paths relative to the terminal's working directory.

Notes:

- Entries in `Class-Path` are separated by spaces.
- Relative paths must match the distribution directory layout.
- Manifest `Class-Path` does not download dependencies from Maven/Gradle repositories or resolve library versions.
- When using `java -jar`, the classpath supplied via `-cp` does not override the executable JAR's classpath; configure dependencies appropriately for the execution mode.

If you want a single JAR containing both the application and its dependencies, use a build tool's fat/uber JAR packaging workflow or package dependencies in a structure supported by a launcher. The `jar --create` command only packages the files and directories you specify; it does not automatically discover and merge dependencies.

## 9. Creating a Library JAR

A Java library typically only needs bytecode and resources, without an entry-point class. For example, if `out` contains classes from the `com.example.greetings` package, create the library:

~~~bash
jar --create --file dist/greetings.jar -C out .
~~~

Inspect its contents:

~~~bash
jar --list --file dist/greetings.jar
~~~

An application can use the library on the classpath:

~~~bash
java -cp "out:dist/greetings.jar" com.example.Main
~~~

On Windows:

~~~powershell
java -cp "out;dist/greetings.jar" com.example.Main
~~~

The order of classpath entries can affect which class gets loaded if multiple JARs contain classes with the same name. Avoid placing multiple duplicate versions of a library on the same classpath.

For libraries distributed to other users, consider adding API documentation, version information, license, and required metadata. This information can live in the manifest or be managed by an artifact publishing system.

## 10. Creating a Modular JAR

A modular JAR contains `module-info.class` at the root of the archive. The module descriptor declares the module name and its exported packages or required modules.

Example `src/module-info.java`:

~~~java
module com.example.app {
}
~~~

Example `src/com/example/Main.java`:

~~~java
package com.example;

public class Main {
    public static void main(String[] args) {
        System.out.println("Hello from modular JAR!");
    }
}
~~~

Compile the module:

~~~bash
javac --release 17 -d mods/com.example.app src/module-info.java src/com/example/Main.java
~~~

Create the modular JAR:

~~~bash
jar --create --file dist/modular-app.jar --main-class com.example.Main -C mods/com.example.app .
~~~

Inspect the module descriptor:

~~~bash
jar --describe-module --file dist/modular-app.jar
~~~

Run via the module path:

~~~bash
java --module-path dist/modular-app.jar -m com.example.app
~~~

Stdout:

~~~text
Hello from modular JAR!
~~~

The module name in `-m` must match the name declared in `module-info.java`. For a modular JAR with a declared main class, the launcher can use that entry point when running the module. If no main class is declared, specify the fully qualified class name after `/`, for example `-m com.example.app/com.example.Main`.

A modular JAR differs from a regular JAR in its module descriptor and packaging rules. Do not simply rename a JAR file or add a directory to an archive and treat it as a modular JAR; `module-info.class` must be compiled from a valid module descriptor and placed at the root of the archive.

## 11. Multi-Release JARs

A multi-release JAR allows a single archive to contain different versions of classes targeting different Java versions. The JVM selects the class matching the runtime version when loading the archive.

Example structure:

~~~text
library.jar
├── META-INF/
│   ├── MANIFEST.MF
│   └── versions/
│       └── 17/
│           └── com/example/Feature.class
└── com/
    └── example/
        └── Feature.class
~~~

The base version resides at the root of the JAR; the Java 17 alternative resides under `META-INF/versions/17/`. The manifest must include the attribute:

~~~text
Multi-Release: true

~~~

You can create an archive with versioned files using `jar`'s `--release` option:

~~~bash
jar --create --file dist/library.jar --manifest manifest.mf -C base . --release 17 -C java17 .
~~~

Here `base` holds the base classes, while `java17` holds the Java 17 replacement classes. Only files appearing after `--release 17` are placed under `META-INF/versions/17/`.

Use a multi-release JAR when you need to provide optimized implementations for newer runtimes while keeping a base implementation for older ones. Verify that the API remains consistent across versions and test on every target runtime.

Validate consistency:

~~~bash
jar --validate --file dist/library.jar
~~~

This is an advanced packaging feature. If a project only targets a single Java version, a standard JAR is simpler.

## 12. Updating, Listing, and Extracting JARs

Common operations:

~~~bash
# List entries in the archive
jar --list --file dist/hello.jar

# List entries in detail
jar --list --verbose --file dist/hello.jar

# Update or add resources to the archive
jar --update --file dist/hello.jar -C resources .

# Extract the entire archive into the extracted directory
jar --extract --file dist/hello.jar --dir extracted
~~~

`--update` replaces entries with matching names or adds new ones. Use it when you need to update an existing archive, though for release artifacts consider rebuilding from scratch for better reproducibility and verification.

Do not update JAR contents after signing with `jarsigner`. Any modification to signed entries can invalidate the signature. If you need to modify an artifact, rebuild the JAR, re-sign it, and verify the signature afterward.

You can view the module description with:

~~~bash
jar --describe-module --file dist/modular-app.jar
~~~

For a regular JAR without a module descriptor, the tool may display an inferred automatic module name or related details; that does not mean the JAR has an explicit `module-info.class`.

## 13. Controlling Timestamps and JAR Reproducibility

Two builds from the same source code can produce different archives if timestamps, input ordering, manifests, or build environments change. This makes checksum comparison and artifact traceability difficult.

The `--date` option of `jar` lets you set a uniform timestamp for entries:

~~~bash
jar --create --file dist/hello.jar --date=2024-01-01T00:00:00Z --main-class com.example.Hello -C out . -C resources .
~~~

To improve reproducibility:

- Use the same JDK version and compiler configuration.
- Generate outputs from a clean build directory.
- Keep the input file list order deterministic if passing individual files.
- Normalize timestamps with `--date` when the release process requires it.
- Use a deterministic manifest and avoid embedding machine-specific data.
- Record the artifact's checksum after packaging completes.

`--date` only normalizes entry timestamps; it does not guarantee a fully reproducible build if file contents, input ordering, manifests, or compilers differ.

## 14. Common Errors When Creating JARs

| Symptom | Common Cause | Resolution |
|---|---|---|
| `no main manifest attribute` | The JAR has no `Main-Class`. | Use `--main-class` or a manifest containing `Main-Class`. |
| `Could not find or load main class` | The class is not at the expected path inside the JAR or the class name is wrong. | Check `jar --list`; package the output directory contents using `-C out .`. |
| `ClassNotFoundException` at runtime | Missing runtime dependency or incorrect `Class-Path`. | Verify dependent JARs and the manifest. |
| Resource returns `null` | The resource file was not packaged or the resource path is wrong. | List the JAR, check entries, and use the proper path relative to the classpath root. |
| JAR has `out/` directory at root | Added the output directory itself instead of changing into it. | Use `-C out .` when creating the archive. |
| Runs with classpath but `java -jar` fails | The JAR lacks a manifest entry point or dependencies are only on an external classpath. | Declare `Main-Class` and configure dependencies via manifest `Class-Path` or an appropriate packaging method. |
| Module not recognized | `module-info.class` is missing, misplaced, or the module path is wrong. | Check `jar --describe-module` and the archive root structure. |
| JAR signature invalid after update | The archive was modified after signing. | Rebuild the artifact, sign it last, and run `jarsigner -verify`. |
| JAR checksum differs across builds | Timestamps, entry ordering, manifest, or input contents changed. | Normalize inputs and timestamps, and pin the build environment. |

Troubleshooting workflow when errors occur:

1. Use `jar --list --file app.jar` to confirm actual entries.
2. Check the manifest and `Main-Class` if running with `java -jar`.
3. Confirm that package paths in the JAR match the fully qualified class names.
4. Verify that resources are present at the expected paths.
5. Check runtime dependencies and the module descriptor if the application is modular.
6. If the JAR is signed, re-verify the signature after all updates are complete.

## 15. Pre-Release Checklist

- Compiled successfully with the appropriate JDK version.
- Determined whether the JAR is a library, executable JAR, or modular JAR.
- Class files follow the proper package structure at the root of the archive.
- Required resources are included at the correct paths.
- `--main-class` or a proper manifest is used when the JAR is meant to run with `java -jar`.
- Runtime dependencies are bundled or explicitly declared.
- For modular JARs, `module-info.class` is at the root and the module name is valid.
- Verified entries with `jar --list` and module details with `jar --describe-module` if needed.
- Tested the final artifact using the intended execution mode.
- If signing the JAR, sign only after the archive is finalized and verify the signature.
- If reproducible builds are required, normalized timestamps, inputs, and the build environment.

When creating a JAR, start from a prepared directory containing bytecode and resources, and use `jar --create --file ... -C ... .` to preserve proper entry paths. If the archive needs to run standalone, declare `Main-Class`; if it is a modular JAR, package `module-info.class` at the root and test with the module path. Finally, list the contents and test-run the exact artifact you plan to release.
