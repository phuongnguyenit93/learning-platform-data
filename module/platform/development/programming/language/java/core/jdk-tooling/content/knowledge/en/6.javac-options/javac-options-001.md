# source and target Options in javac

When compiling Java with a newer JDK while needing to run the program on an older Java version, you must control the language syntax, the bytecode format, and the platform APIs allowed for use. The **--source** and **--target** options control two different parts of this process. Since Java 9, the **--release** option provides a more complete compatibility configuration in most cases.

This lesson uses the **javac** syntax in JDK 17 and later, explaining the meaning of each option, how to verify compilation results, and common compatibility errors.

## 1. Three Concepts to Distinguish

### 1.1. Source level: Java syntax version

The source level specifies the Java language version that the compiler accepts. It determines which syntax and language features a program can use.

For example, a program using the **var** syntax is only valid from Java 10 onward. If compiled with source level 8, the compiler reports a syntax error even when running on JDK 17.

The option that controls the source level is **--source N**.

### 1.2. Target level: bytecode version

The target level specifies the class file format generated by **javac**. A JVM can only run class files whose version is supported by the runtime.

For example, a Java 11 class file has major version 55; a Java 17 class file has major version 61. If a program is compiled into a class file newer than what the running runtime supports, the JVM may throw **UnsupportedClassVersionError**.

The option that controls the target level is **--target N**.

### 1.3. Platform API: APIs available on the target runtime

Beyond syntax and bytecode, a program also calls classes and methods from the Java Platform API, such as **java.lang.String**, **java.util.List**, or **java.nio.file.Path**.

A newer JDK may know about APIs that did not exist in an older runtime. If you only set **--source** and **--target**, the compiler can still see the APIs of the JDK currently being used. As a result, the bytecode has an older version, yet calls a newer method that the target runtime does not have.

This is why it is necessary to understand the difference between **--source**/**--target** and **--release**.

## 2. Using --source and --target

Syntax:

~~~text
javac --source <release> --target <release> [other-options] source-files
~~~

- **--source** selects the syntax rules and language features of the specified Java version.
- **--target** selects the version of the generated class files.
- Both values are usually set equal to avoid creating a confusing combination of newer syntax and older bytecode.

Example of compiling code using Java 11 syntax and generating class files compatible with Java 11:

~~~powershell
javac --source 11 --target 11 -d out src/com/example/App.java
~~~

You can use the short forms **-source** and **-target**:

~~~powershell
javac -source 11 -target 11 -d out src/com/example/App.java
~~~

The long names with two hyphens are easier to read and are generally preferred in new scripts.

### 2.1. Why aren't these two options enough to guarantee compatibility?

**--source 11** requires Java 11 syntax, and **--target 11** generates class files in the Java 11 format. However, if you use JDK 17, the compiler can still access Java 17 platform APIs during compilation unless the API environment is restricted separately.

The following example uses **String.isBlank()**, which was added in Java 11:

~~~java
public class ApiExample {
    public static void main(String[] args) {
        System.out.println("   ".isBlank());
    }
}
~~~

If you use JDK 17 to compile with **--source 8 --target 8**, the code may be accepted because the syntax is still valid and the Java 17 API has that method. The class file is generated for target 8, but when run on Java 8, the **String** class does not have **isBlank()**. The program may fail at link or method invocation time, typically manifesting as **NoSuchMethodError**.

In addition, when using **--source** and **--target** older than the running JDK, **javac** may warn that the system modules path has not been set alongside the source level. This warning reminds you that the compiler does not automatically restrict platform APIs to the older version.

## 3. Using --release for Compatible Compilation

**--release N** is the recommended option when you need to compile for an older Java version using a newer JDK.

It combines three requirements:

1. Use the source level of the specified version.
2. Generate class files at the target level of that version.
3. Restrict Java Platform APIs to those published for that version.

For example, compiling code for Java 11 using JDK 17:

~~~powershell
javac --release 11 -d out src/com/example/App.java
~~~

If the code calls an API that only appeared in Java 12 or later, the compiler reports an error when compiling with **--release 11** instead of generating bytecode that risks calling an API that does not exist on Java 11.

You can use other release versions supported by the current JDK:

~~~powershell
javac --release 8 -d out src/com/example/App.java
javac --release 11 -d out src/com/example/App.java
javac --release 17 -d out src/com/example/App.java
~~~

The list of supported releases depends on the compiler's JDK version. Check with:

~~~powershell
javac --help
~~~

With JDK 17, **--release** only accepts releases supported by that **javac** version; you cannot use JDK 17 to target Java 21. To compile for a newer release, you need to use the corresponding JDK or a newer one.

Do not combine **--release** with **--source** or **--target** in the same command. **--release** already configures all three compatibility aspects mentioned above.

## 4. Practical Example with Java 11

Create the structure:

~~~text
project/
├── src/
│   └── com/
│       └── example/
│           └── App.java
└── out/
~~~

Contents of **src/com/example/App.java**:

~~~java
package com.example;

public class App {
    public static void main(String[] args) {
        String message = "  Java 11  ".strip();
        System.out.println(message);
    }
}
~~~

The **String.strip()** method has existed since Java 11. From the **project** directory, compile with JDK 17 while setting release to 11:

~~~powershell
New-Item -ItemType Directory -Force -Path out | Out-Null
javac --release 11 -d out src/com/example/App.java
java -cp out com.example.App
~~~

Output when run on a compatible runtime:

~~~text
Java 11
~~~

The **java** command in the last example uses the runtime currently on **PATH**. If you need to confirm actual compatibility with Java 11, run the program using the Java 11 executable, not just Java 17.

The example above demonstrates that a newer JDK can compile code against an older release's APIs and bytecode without needing to install that exact older JDK for compilation.

## 5. Comparing source, target, and release

| Option | Controls | Restricts Java Platform APIs? | When to use |
|---|---|---|---|
| **--source N** | Java syntax/language | Does not automatically restrict APIs | When you need to control the source level separately |
| **--target N** | Class file format | Does not automatically restrict APIs | When you need to control the bytecode target separately |
| **--source N --target N** | Syntax and bytecode | Does not automatically restrict APIs | Syntax and class file compatibility in an already-controlled API environment |
| **--release N** | Syntax, bytecode, and platform APIs | Yes | Preferred choice when building for a specific Java release |

Example:

~~~powershell
# Separate source and target
javac --source 11 --target 11 -d out src/com/example/App.java

# Recommended approach for applications that need to run on Java 11
javac --release 11 -d out src/com/example/App.java
~~~

When the goal is to support a specific runtime, **--release** is usually safer and clearer.

## 6. Mapping Table of Java Release and Class File Version

Each Java version corresponds to a class file major version. The table below lists some common versions:

| Java release | Class file major version |
|---|---:|
| Java 8 | 52 |
| Java 9 | 53 |
| Java 10 | 54 |
| Java 11 | 55 |
| Java 12 | 56 |
| Java 13 | 57 |
| Java 14 | 58 |
| Java 15 | 59 |
| Java 16 | 60 |
| Java 17 | 61 |
| Java 18 | 62 |
| Java 19 | 63 |
| Java 20 | 64 |
| Java 21 | 65 |

A useful rule from Java 9 onward: the major version is usually the release number plus 44. For example, Java 17 has major version 61.

This table helps read errors like **UnsupportedClassVersionError** and identify which version the bytecode was compiled for. However, having the right major version is not enough to prove an application is compatible: the program may still depend on newer APIs, external libraries, or different runtime behaviors.

## 7. Verifying Compilation Results

### 7.1. Checking with javap

**javap** is a tool included with the JDK for reading class file information. Use **-verbose** to view details:

~~~powershell
javap -verbose -classpath out com.example.App
~~~

In the output, look for the **major version** line. If compiled with **--release 11**, the example's class file will have major version 55.

You can filter quickly on PowerShell:

~~~powershell
javap -verbose -classpath out com.example.App | Select-String "major version"
~~~

On Bash or Zsh, you can use **grep**:

~~~bash
javap -verbose -classpath out com.example.App | grep "major version"
~~~

### 7.2. Checking compiler and runtime versions

Use:

~~~powershell
javac -version
java -version
~~~

The two commands may point to two different Java installations if PATH or environment configuration is inconsistent. Checking both helps detect cases where you compile with one JDK but run with another runtime.

### 7.3. Checking APIs and dependent libraries

**--release** restricts the Java Platform APIs that the compiler allows to be used. It does not automatically check every external library that the application depends on.

For example, a third-party library might only support Java 17 even if your application is compiled with **--release 11**. You need to choose library versions that support the target runtime and test the entire application on that runtime.

## 8. Limitations and Notes

### 8.1. The release must be supported by the current JDK

A compiler cannot generate bytecode for a release newer than its own version. For example, JDK 17 cannot use **--release 21**. Use JDK 21 or newer to compile for Java 21.

For very old releases, a newer compiler may have dropped support. Refer to **javac --help** for the exact JDK you are using.

### 8.2. Preview features

Preview features are tied to a specific Java version. **--enable-preview** is only for the current release of the compiler/runtime, and when compiling must be combined with the corresponding source level.

Example on JDK 17:

~~~powershell
javac --enable-preview --release 17 -d out src/com/example/PreviewApp.java
java --enable-preview -cp out com.example.PreviewApp
~~~

You cannot use a Java 17 preview feature and expect it to run on Java 11 simply by setting **--target 11**.

### 8.3. Annotation processors and external libraries

Annotation processors run during compilation and may have their own JDK requirements. Dependencies used at compile time also need versions compatible with the compiler and target release.

Check:

- The JDK version supported by the annotation processor.
- The bytecode version of external libraries.
- The Java APIs used by those libraries.
- Native libraries or environment-dependent components, if any.

### 8.4. Compatible builds do not replace runtime testing

Even when using **--release**, the application still needs to be tested on the target runtime. Compatibility also depends on libraries, configuration, operating system, encoding, timezone, TLS, native code, and application behavior.

## 9. Configuring source/target in Maven and Gradle

For projects using a build tool, you should configure the release in the build file so that every build machine uses the same target.

### 9.1. Maven

With the Maven Compiler Plugin, you can declare the release property:

~~~xml
<properties>
    <maven.compiler.release>11</maven.compiler.release>
</properties>
~~~

Or configure it directly in the plugin:

~~~xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.13.0</version>
    <configuration>
        <release>11</release>
    </configuration>
</plugin>
~~~

Use a consistent release configuration and avoid setting conflicting source/target values simultaneously in multiple places in the POM.

### 9.2. Gradle

With the modern Gradle Java plugin, you can use a toolchain and release target:

~~~kotlin
java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(11)
}
~~~

The example above uses JDK 17 to compile and targets Java 11. The toolchain selects the compiler JDK, while **options.release** sets the compatibility release for the compile task. Exact syntax may vary depending on the Gradle version and Groovy/Kotlin DSL used by the project.

## 10. Common Errors When Configuring source and target

| Symptom | Common cause | Resolution |
|---|---|---|
| **invalid source release** | The current JDK does not support the requested source level | Check **javac -version** and the supported releases |
| **invalid target release** | The target level exceeds the compiler's capability or is unsupported | Use a JDK suitable for the desired target |
| **Source option ... is no longer supported** | Using a source level that is too old and has been removed by the compiler | Raise the source level or use an appropriate older JDK if required by the project |
| **UnsupportedClassVersionError** | The runtime is too old for the class file | Compile with a lower release or upgrade the runtime |
| **NoSuchMethodError** when running on an older runtime | The bytecode calls an API that does not exist in that runtime | Recompile with **--release** for the right version and check dependencies |
| **package ... does not exist** when using **--release** | The API/package is not part of the target Java Platform release or a dependency is missing | Check the target release and classpath/module path |
| **option --release cannot be used together with --source** | Combining mutually exclusive options | Use only **--release** or the **--source**/**--target** pair |
| System modules path warning when using older source/target | The compiler is using the current JDK's APIs without a corresponding platform API path | Prefer **--release** to restrict platform APIs |

## 11. Configuration Selection Workflow

When starting a project or upgrading the build JDK, follow this order:

1. Identify the lowest Java version that the application must support.
2. Choose a compiler JDK new enough to support that release.
3. Use **javac --release N** where N is the target runtime.
4. Check whether external libraries, annotation processors, and plugins support N.
5. Use **javap -verbose** to inspect the class file's major version.
6. Run tests on the exact runtime N.
7. Put the release configuration into Maven/Gradle or a shared build script to avoid discrepancies between developer machines and CI.

## 12. Pre-release Checklist

- [ ] Identified the lowest Java runtime that needs to be supported.
- [ ] Selected a compiler JDK that supports the target release.
- [ ] Used **--release** when compatibility across syntax, bytecode, and Java Platform APIs is needed.
- [ ] Did not mix **--release** with **--source** or **--target** in the same command.
- [ ] Checked the major version with **javap -verbose**.
- [ ] External libraries and annotation processors are compatible with the target runtime.
- [ ] Preview features are only used with the exact Java version that supports them.
- [ ] Ran tests on the actual lowest supported runtime.
- [ ] Build file and CI use the same release configuration.

**--source** controls Java syntax, **--target** controls the bytecode format, while **--release** combines both with Java Platform API restrictions. When compiling with a newer JDK to support an older runtime, prefer **--release** and verify by testing on the exact target Java version.
