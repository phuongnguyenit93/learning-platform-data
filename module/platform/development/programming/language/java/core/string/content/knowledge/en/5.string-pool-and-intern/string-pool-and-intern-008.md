# When `String.intern()` Helps and Its Limits on Untrusted Data

`String.intern()` lets multiple strings **with equal content** share a single representative object (*canonical string*) in the JVM's **string pool**. This idea is helpful when data repeats heavily and the number of distinct values is bounded. Conversely, for values freely generated by users or external systems, the number of distinct strings can grow without bound over time; indiscriminate interning can waste CPU, put pressure on memory and GC, and degrade overall JVM performance.

This lesson explains the mechanism, conditions under which it helps, limits with untrusted data, alternatives, and how to measure impact. The examples use Java 17+.

## 1. Understanding the String Pool and `intern()` Properly

In Java, `String` is *immutable*. Two objects can have the same content yet different references:

- `a.equals(b)` asks whether the **content** is identical.
- `a == b` asks whether they share the same **object reference**.
- `a.intern()` asks the JVM to return the representative object for `a`'s content from the pool. If the pool already has a representative with equal content, it returns that object; otherwise, it places a representative into the pool and returns it.

For two strings with equal content, the `String.intern()` API contract guarantees that both `intern()` results are the same reference. The call **does not modify the receiver variable** unless you reassign it:

~~~java
String a = new String("READY");
String b = new String("READY");

System.out.println(a == b);               // false
System.out.println(a.equals(b));          // true
System.out.println(a.intern() == b.intern()); // true

String canonical = a.intern();
System.out.println(canonical == "READY");  // true
System.out.println(a == "READY");          // false
~~~

Literals such as `"READY"` and constant expressions such as `"REA" + "DY"` are canonicalized through the mechanism tied to the string pool. A concatenation expression evaluated at runtime is not guaranteed to share the same reference:

~~~java
String a = "READY";
String b = "REA" + "DY"; // compile-time constant
String suffix = "DY";
String c = "REA" + suffix; // expression is not a constant expression

System.out.println(a == b);          // true
System.out.println(a.equals(c));     // true
System.out.println(a == c);          // false
System.out.println(a == c.intern()); // true
~~~

**Important principle:** Even if one part of the system interns strings, other APIs can still produce non-interned `String` instances. Therefore, compare business statuses from multiple sources **using `equals()`**, or `Objects.equals(a,b)` if `null` is possible. Use `==` on `String` only when an explicit internal contract guarantees that **every** path creating or receiving the value produces a canonical reference; avoid relying on it as an implicit assumption.

## 2. Is the Pool Like an Application Cache?

The String pool is a JVM-wide resource, not a local cache where code can arbitrarily delete an entry with `remove()`. Specific implementations vary by JVM, JDK, and collector. On modern HotSpot (including Java 17), string object management is tied to the Java heap; historical lore claiming that all interned strings live forever in *PermGen* of very old releases is no longer an accurate model.

Both extremes are wrong:

1. **"Once interned, a string is retained forever."** You cannot assert this universally across JVMs. Whether a representative can be reclaimed depends on whether strong references remain from the application, related literals/constants, the JVM, and collector policies. Some strings can be reclaimed once unreachable.
2. **"GC will definitely reclaim them in time, so interning all inputs is fine."** Also wrong. The program does not dictate when GC runs, there is no dedicated eviction API for the pool, and you still pay the cost of creating, looking up, and managing new values. Values still held by the application will not be reclaimed merely because they were interned.

Do not design assuming interned strings always *leak* permanently, nor rely on them vanishing immediately. Differences between JVMs and GCs must be verified in the actual runtime environment.

## 3. Conditions Where `intern()` Can Provide Value

### 3.1. A small set of values repeated very frequently

Suppose a system retains millions of event objects; each event holds a status created from parsed data, yet the only statuses are `READY`, `RUNNING`, and `DONE`. If parsing creates a new `String` object every time and those event objects live long, many `String` objects holding identical content can occupy heap space.

In an intuitive model with \(N\) occurrences and \(U\) distinct values, when \(U\) is much smaller than \(N\), replacing many live string copies with \(U\) shared representatives can reduce memory usage. However, this is **not an exact byte formula**: object sizes, compact strings, byte-array sharing, JVM optimizations, StringTable overhead, and object lifetimes all affect real-world results.

Criteria to consider:

- **Reliably bounded cardinality**: the set of distinct values is controlled by an allowlist or rules with clear limits.
- **High duplication frequency**: many objects simultaneously hold the same contents.
- **Long enough string lifetimes**: live-heap savings outweigh string creation and pool lookup costs.
- **Controlled inputs**: unexpected, overly long, or policy-violating values are rejected **before** interning.
- **Measured improvement**: live heap after GC, allocation rate, CPU, GC pause behavior, throughput, and latency improve under representative load.

If only a few `static final` string constants or literals are reused, they may already share references; adding `intern()` brings no benefit.

### 3.2. Repeated label names in data structures

In a parser, a large syntax tree, or a metadata system, many nodes can carry the same label names such as `"identifier"`, `"literal"`, or `"property"`. If they are created from separate slices of input data and kept alive long-term, canonicalization can reduce duplicate objects/content retained in memory.

However, you must identify **what you are optimizing**: a program that creates temporary `String` instances and discards them right away will not necessarily benefit. Nor does a `HashMap<String, V>` having many lookups mean keys must be interned: `String.hashCode()` and `String.equals()` already let a `Map` locate a key with the same content despite different references.

### 3.3. Identity optimization inside a closed module

Some internal algorithms rely on canonicalization to use `==` once they know for sure every value passes through a canonicalization gate. This approach is brittle if a new data path bypasses that gate. Consider an `enum`, integer IDs, or a module-local symbol table if the vocabulary is bounded and an internal invariant is hard to maintain.

**Do not treat `intern()` as a default trick to make `String` comparisons "faster."** StringTable lookups also have a cost. Any comparison speedup, if present, must be measured across the entire processing pipeline rather than just the duration of `==`.

## 4. Where Is Uncontrolled Data Dangerous?

"Uncontrolled" means the system cannot guarantee the number of distinct values, their length, or their arrival rate. Typical sources:

- UUIDs, request IDs, trace IDs, session IDs, nonces, and random tokens.
- Usernames or free-form search queries.
- Full URLs with arbitrary query strings.
- HTTP headers, JSON values, log lines, filenames, or client payloads.
- Strings generated by external services with schemas that do not bound cardinality.

Anti-pattern:

~~~java
// Anti-pattern illustration, not a standalone runnable program:
String userInput = request.getParameter("key");
String key = userInput.intern(); // putting unbounded data into the pool
~~~

If a client sends 100,000 mostly distinct values, `intern()` rarely finds duplicates to share. The program still pays the cost of building/probing the table, handling objects, and potentially increasing GC pressure; under heavy load, this can become a bottleneck that lowers throughput or raises tail latency. If new values keep arriving continuously or have large lengths, resources can be consumed in a way controlled by the sender, creating a denial-of-service risk.

**This does not mean "every interned string is retained forever."** Even though the JVM may reclaim unreachable representatives, that does not make `intern()` suitable for unbounded input. Arrival rate, length, application-held references, and reclamation behavior determine the real impact.

Simply calling `strip()`, `toLowerCase()`, or normalizing Unicode does **not** make the value set finite; you still need a real allowlist or bound. Checking entry count while ignoring length is also insufficient: a single entry can hold a huge amount of data.

### Quick decision table

| Data | Should you intern? | Appropriate handling |
|---|---|---|
| Fixed `READY`, `RUNNING`, `DONE` | Possible, though usually unnecessary | Prefer an `enum` or shared constants |
| Token names from a bounded grammar | Consider after measuring | Canonicalize after validation or use a symbol table |
| Labels from a bounded configuration set | Possible | Bound value count and length, measure in practice |
| Per-request Request ID / UUID | No | Keep as ordinary `String`, retain only as needed |
| Arbitrary URLs and query strings | No | Validate format, bound length, avoid retaining unnecessarily |
| Account names / free-form searches | No | Validation and ordinary data structures |
| Arbitrary log lines / JSON payloads | No | Parse needed fields, do not intern whole payloads |
| `HashMap` string keys | Not required | `equals/hashCode` are sufficient for accurate lookup |

## 5. A Controlled Workflow for Using `intern`

A sensible policy is **validate first, intern second, measure last**.

1. First identify which data actually repeats heavily and lives long. Use a profiler, heap dump, or JFR instead of guessing from string creation sites.
2. Define the **accepted value set**. For statuses, use an allowlist or `enum`. For configuration-driven labels, set thresholds on both value count and size.
3. Bound input length and rate at the ingestion boundary. This is a general safeguard against clients supplying huge inputs.
4. Normalize if business rules require it; then validate against exact allowed values. Normalizations can change linguistic semantics; pick `Locale.ROOT` for locale-independent machine codes, and do not apply it blindly to user names.
5. Call `intern()` only for valid values, and **use the returned reference**.
6. Measure and compare against a simpler alternative. Keep `equals()` on all APIs that do not guarantee identity.

## 6. Complete Java 17 Example: Allowlist Before Interning

The snippet below illustrates the difference between `==` and `equals()`, calling `intern()` after validation, and choosing an `enum` when the status set is fixed. Save the UTF-8 file as `InternSafetyDemo.java`.

~~~java
import java.util.Locale;
import java.util.Objects;
import java.util.Set;

public class InternSafetyDemo {
    private static final Set<String> ALLOWED = Set.of("NEW", "READY", "DONE");

    enum Status {
        NEW, READY, DONE
    }

    static String internValidatedStatus(String raw) {
        Objects.requireNonNull(raw, "raw");
        String normalized = raw.strip().toUpperCase(Locale.ROOT);
        if (!ALLOWED.contains(normalized)) {
            throw new IllegalArgumentException("Unknown status");
        }
        return normalized.intern();
    }

    static Status parseStatus(String raw) {
        Objects.requireNonNull(raw, "raw");
        return Status.valueOf(raw.strip().toUpperCase(Locale.ROOT));
    }

    public static void main(String[] args) {
        String first = new String(new char[] {'R', 'E', 'A', 'D', 'Y'});
        String second = new String(new char[] {'R', 'E', 'A', 'D', 'Y'});

        System.out.println("rawIdentity=" + (first == second));
        System.out.println("rawContent=" + first.equals(second));

        String a = internValidatedStatus(first);
        String b = internValidatedStatus(" ready ");
        System.out.println("canonicalIdentity=" + (a == b));
        System.out.println("sameAsLiteral=" + (a == "READY"));

        Status e1 = parseStatus(first);
        Status e2 = parseStatus(" ready ");
        System.out.println("enumIdentity=" + (e1 == e2));

        boolean rejected = false;
        try {
            internValidatedStatus("CLIENT_CUSTOM_00001");
        } catch (IllegalArgumentException expected) {
            rejected = true;
        }
        System.out.println("unknownRejected=" + rejected);
    }
}
~~~

Compile and run with JDK 17 or later:

~~~bash
javac -encoding UTF-8 InternSafetyDemo.java
java InternSafetyDemo
~~~

Stdout:

~~~text
rawIdentity=false
rawContent=true
canonicalIdentity=true
sameAsLiteral=true
enumIdentity=true
unknownRejected=true
~~~

`first` and `second` are two `String` objects explicitly created with `new`, so their references differ while `equals()` returns `true`. `internValidatedStatus()` normalizes and admits only the three allowed codes; the canonical result matches the literal `"READY"` reference. Unknown cases are rejected before interning. An `enum` has fixed unique instances, so comparing with `==` matches enum semantics.

**Why does the code still use `intern` even though an `enum` is better?** To demonstrate the protective boundary. In an example with exactly three fixed statuses, an `enum` or returning the three literals directly is even simpler, because literals are already pooled. Interning is more worth considering when a vocabulary is constructed at runtime yet is **genuinely bounded**, repeats frequently, and is retained long-term; benefits must still be measured.

## 7. Alternatives Worth Considering

### 7.1. Enums, constants, and IDs

When the value set is fixed at development time, an `enum` provides type safety, a finite element set, and stable identity. `switch` on an enum expresses intent more clearly than string comparisons and makes input paths easier to manage. If elements appear inside very large data structures, integer IDs or a dedicated identifier code may be appropriate. When `Enum.valueOf()` receives out-of-set input, handle `IllegalArgumentException`; for `null`, check separately.

### 7.2. Bounded local cache / symbol table

When you need to canonicalize runtime strings, a local cache with a **maximum size**, length limit, TTL/LRU, or explicit eviction can be easier to control than the JVM pool. Account for synchronization if the cache is shared across threads, eviction policy when full, and cache overhead; not every short-lived string needs caching.

Do not assume a `WeakHashMap<String, String>` using **the same object** as both key and value will automatically clean up entries: the strong value keeps the key alive, defeating the weak key. Weak/soft reference structures require understanding the reference graph and memory testing; a bounded cache library is usually much easier to use correctly.

### 7.3. GC String Deduplication differs from `intern`

Some JVMs/collectors support **String Deduplication**, such as G1 on HotSpot when enabled with the appropriate option like `-XX:+UseStringDeduplication`. Deduplication can allow multiple `String` objects to **share the backing byte array holding their content**, yet it **does not necessarily merge the `String` objects themselves**. Therefore:

- String deduplication can reduce content storage, yet `a == b` can still be false.
- `intern()` returns the same `String` representative when contents are equal.
- Both have their own costs and preconditions; availability and effectiveness depend on the JVM and collector and must be verified with the real configuration.

Do not enable flags or change code based solely on guesswork that one technique is always faster.

## 8. How to Measure Effectiveness

At least two workloads are needed:

| Benchmark load | Data | Key metrics |
|---|---|---|
| High repetition, small vocabulary | Millions of occurrences across a few distinct codes | Live heap after GC, String/byte-array counts, allocation, throughput |
| High cardinality, continuous stream | Mostly new values, potentially very long | Lookup CPU, allocation, GC pauses, tail latency, heap usage |

Use allocation/heap profilers, Java Flight Recorder, and GC logs as appropriate. With JDK tools, `jcmd <pid> GC.class_histogram` helps observe object counts per class; **a histogram alone does not prove how many strings have duplicate content**. Run microbenchmarks with JMH rather than a short `System.nanoTime()` loop, because JVM JIT, warmup, and GC skew naive timings.

Decision criteria include: does it reduce **actual live heap**, does it increase CPU/latency/GC, does it worsen performance under workloads introducing new values, and would an `enum` or bounded cache be better? If the difference is negligible, prefer the simpler and more controllable approach.

## 9. Common Mistakes and How to Remember

| False claim | Accurate understanding |
|---|---|
| All `String`s with the same content are `==` | Only `equals()` checks content; `==` checks references |
| `intern()` modifies the original `String` | Returns the canonical reference; reassign if you want to use it |
| `intern()` always saves RAM | There are still lookup, pool, and temporary string creation costs |
| Interned `String`s are immortal | Lifetime depends on JVM, GC, and references; do not make blanket claims |
| GC cleans up fast, so intern every input | You do not control GC or pool lifecycles; continuous new inputs still cause overhead |
| Intern first to make input valid | You must validate and bound **before** interning |
| `HashMap` needs interned keys | `String.equals()` and `hashCode()` already handle keys by content |
| String deduplication makes two `String`s `==` | It can share backing byte data while leaving two distinct objects |

## 10. Practical Checklist

- [ ] The value set is reliably bounded in **cardinality**, **length**, and **frequency**.
- [ ] You have verified that many duplicate-content `String`s live long enough to matter.
- [ ] All untrusted sources go through constraints, validation, and appropriate normalization before interning.
- [ ] You have considered `enum`, constants, IDs, or a bounded local cache.
- [ ] You do not rely on `==` across boundaries where a `String` may not be canonical.
- [ ] You have measured both high-repetition data and workloads with many new values.
- [ ] Memory/performance gains genuinely outweigh CPU, GC, and complexity costs.

`intern()` fits **when inputs come from a bounded vocabulary, repeat heavily, live long, and sharing has been measured to help**. Do not mass-intern strings freely supplied by users or third parties; for such data, prioritize validation, `equals()`, and bounded application-controlled storage.
