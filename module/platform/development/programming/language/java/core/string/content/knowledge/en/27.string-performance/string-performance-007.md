# Benchmarking String Performance with JMH: Warmup, Dead-Code Prevention, and Avoiding Constant Folding

## 1. Why Is JMH Needed?

`String` operations like `indexOf`, `equals`, `substring`, or concatenation execute very quickly, so manual timing easily becomes misleading. Consider this **intentionally flawed code**:

~~~java
long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) {
    "mississippi".indexOf('s');
}
System.out.println(System.nanoTime() - start);
~~~

The result of `indexOf` is not used; the JVM may eliminate that work. Moreover, the input is a fixed literal, so the JVM can precompute the result instead of performing the search a million times. Using `nanoTime` does not fix the issue if the measured code no longer runs as intended.

OpenJDK's **JMH (Java Microbenchmark Harness)** is designed for Java/JVM microbenchmarking. JMH orchestrates measurements, iterations, warmup, JVM forks, annotation processing, and consumption of computed results. It helps guard against three core pitfalls:

1. **Insufficient warmup:** measurements mix in class loading, interpreter execution, JIT compilation, profiling, and deoptimization.
2. **Dead-code elimination (DCE):** the result is never observed, so the optimizer removes the computation entirely.
3. **Constant folding:** inputs are constants, so the optimizer returns a constant result instead of executing the algorithm under test.

**JMH does not guarantee that a poorly designed benchmark becomes valid.** Results are meaningful only when the workload, data, environment, and score interpretation are clearly defined.

## 2. Measurement Lifecycle: Fork, Warmup, Measurement

JMH executes each `@Benchmark` through harness code generated by an annotation processor. During a run, it can launch **independent JVM forks**; within each fork, it executes warmup iterations followed by measurement iterations.

| Component | Meaning |
| --- | --- |
| `@Benchmark` | Marks a method containing the work to be measured. |
| `@Warmup` | Runs the workload to give the JVM time to optimize, without including those iterations in the main measurement score. |
| `@Measurement` | Iterations that collect metrics; each iteration invokes the benchmark many times. |
| `@Fork` | Number of isolated child JVMs, helping expose variance across startups/runtimes. |
| `@BenchmarkMode` | Selects how the score is reported, such as AverageTime, Throughput, or SampleTime. |
| `@OutputTimeUnit` | Selects the display time unit, such as nanoseconds or microseconds. |
| `@Threads` or `-t` | Number of worker threads running the benchmark concurrently. |

Example annotation configuration (fragment inside a benchmark class):

~~~java
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(2)
~~~

In this configuration, each fork runs 5 warmup iterations and 5 measurement iterations, each lasting about one second. Two forks help observe variance across two separate JVMs. This is only a **starting configuration**, not proof that the JVM has stabilized. If the score still shows a clear trend in later iterations, revisit warmup, workload, and environment.

The HotSpot JIT can interpret bytecode, compile at multiple tiers, and deoptimize when assumptions change. Measuring only the first run can accidentally measure **JVM warmup** rather than steady-state performance after the program has been running.

### Reading the Modes Properly

- `Mode.AverageTime` (`-bm avgt`) reports average time per operation: e.g., `ns/op`; lower is generally better when all else is equal.
- `Mode.Throughput` (`-bm thrpt`) reports operations per unit of time; higher is generally better.
- `Mode.SampleTime` (`-bm sample`) samples execution times and can help inspect distribution and tail latency.
- `Mode.SingleShotTime` (`-bm ss`) fits certain single-shot measurement cases and is not equivalent to steady-state throughput measurements.

Do not compare two algorithms across different modes, units, thread counts, or input sets and draw speed conclusions.

## 3. Preventing Dead-Code Elimination

### Wrong Example: Discarding the Result

~~~java
@Benchmark
public void wrongDiscardedResult() {
    text.indexOf(needle);
}
~~~

`String.indexOf` returns an `int`. If nothing uses that value and the JVM sees the call has no observable side effect, the JIT **may** eliminate the computation. A tiny score does not prove `indexOf` is genuinely fast.

### Approach 1: Return the Result

~~~java
@Benchmark
public int correctReturn() {
    return text.indexOf(needle);
}
~~~

JMH consumes the value returned by a `@Benchmark` method. For a single result, this is usually the simplest way to keep the work observable.

### Approach 2: Blackhole

~~~java
@Benchmark
public void correctBlackhole(Blackhole bh) {
    int position = text.indexOf(needle);
    bh.consume(position);
}
~~~

`Blackhole` belongs to the `org.openjdk.jmh.infra` package. The object provided by JMH can consume one or more results to prevent unwanted work elimination.

~~~java
@Benchmark
public void twoResults(Blackhole bh) {
    bh.consume(text.indexOf("a"));
    bh.consume(text.indexOf("Z"));
}
~~~

These examples are fragments inside a benchmark class with appropriate fields and inputs. The complete class appears in section 7.

**Avoid using `System.out.println` or logging inside measured code to prevent DCE:** I/O or logging locks can cost orders of magnitude more than the String operation itself. Likewise, do not sprinkle arbitrary `volatile` accesses, as they introduce synchronization semantics and new overhead into the experiment.

`correctReturn` and `correctBlackhole` are two ways to consume the result **of the exact same computation**; do not compare them against each other as competing algorithms. The sink/harness has its own overhead, especially for measurements of only a few nanoseconds.

## 4. Avoiding Constant Folding

A benchmark can still be wrong **even when returning a value**:

~~~java
@Benchmark
public int wrongConstantFolded() {
    return "mississippi".indexOf('s');
}
~~~

The input is a literal and the result is always `2`. The JVM **may** fold the entire search into returning the constant `2`; measuring that does not represent the time to search a `String` received at runtime. Putting the literal in a `static final` field or wrapping it in a helper does not remove this risk.

### Inputs via State and Param

For benchmarks measuring searches on an existing string, JMH lets you create inputs during setup:

~~~java
@State(Scope.Thread)
public class InputState {
    @Param({"128", "4096"})
    public int length;

    String text;
    String needle;

    @Setup(Level.Trial)
    public void prepare() {
        char[] chars = new char[length];
        java.util.Arrays.fill(chars, 'a');
        text = new String(chars) + "Z";
        needle = "Z";
    }
}
~~~

- `@State(Scope.Thread)` provides dedicated state per worker thread, avoiding unintended sharing of a mutable object.
- `@Param` lets JMH test different input values; `length` is not a constant embedded directly into the benchmark method.
- `@Setup(Level.Trial)` prepares the inputs before measurement so only searching on the existing String is measured.
- Runtime-allocated data reduces unrealistic constant-folding paths.

This is a technical example of **how to supply inputs**, not a standalone class yet. The complete code in section 7 integrates these annotations.

**This does not mean “forbidding JIT optimizations”.** HotSpot can still inline `indexOf`, use intrinsics, branch prediction, and caches. Those may be valid optimizations in a real application.

### Choosing Setup Level

| Annotation | When to use | Notes |
| --- | --- | --- |
| `@Setup(Level.Trial)` | Input is reused across a whole trial, such as a string prepared for searching. | Initialization cost is excluded from the measured operation. |
| `@Setup(Level.Iteration)` | You want to refresh inputs between iterations. | Can alter cache/profile state. |
| `@Setup(Level.Invocation)` | Forces refreshing data for every single invocation. | Overhead can severely distort small microbenchmarks; avoid using by default. |

If the goal is measuring **String creation**, the creation work must sit inside the benchmark method. If measuring only **indexOf on an existing String**, create the String beforehand as shown above.

## 5. Creating a JMH Maven Project

Using the official JMH Maven archetype is recommended so you get JMH core, the annotation processor, and a runnable benchmark JAR setup. Simply adding `@Benchmark` annotations to source code and calling the method from `main` will not run a JMH measurement.

Prerequisites: Maven and JDK 17+ installed. In a clean working directory without an existing Maven project of the same name, run:

~~~bash
mvn archetype:generate -DinteractiveMode=false -DarchetypeGroupId=org.openjdk.jmh -DarchetypeArtifactId=jmh-java-benchmark-archetype -DarchetypeVersion=1.37 -DgroupId=org.example.bench -DartifactId=string-jmh-demo -Dversion=1.0-SNAPSHOT
cd string-jmh-demo
~~~

`1.37` is a **pinned** JMH version for this example so learners can reproduce it; it does not imply this is always the latest release.

Add `src/main/java/org/example/bench/StringJmhPitfalls.java` with the code from section 7. You can use a separate benchmark project that depends on your product module via a Maven dependency. When packaging, make sure to keep the archetype's annotation-processing configuration so JMH generates the runner and benchmark metadata.

The APIs in the example work on Java 17+. If your project specifies a different compiler release/target, configure the Maven compiler plugin to match the JDK in use.

## 6. Designing the String-Search Workload

The example uses `String.indexOf("Z")` on a string of `length` `'a'` characters followed by `'Z'` at the end. This is a simple workload:

- For `length=128`, `indexOf("Z")` returns 128.
- For `length=4096`, `indexOf("Z")` returns 4096.
- `@Param` tests two sizes without merging them into one score.
- `@Setup` builds the String before measurement begins.
- The benchmark consumes the result via return or Blackhole.

This workload represents finding a token at the end of a **uniformly structured ASCII string**. It does **not** represent every `String.indexOf` case: real applications may have early matches, misses, Unicode inputs, or different lengths and character distributions. A meaningful benchmark must be tied to a defined input set and a clear question.

## 7. Complete Runnable Benchmark for Java 17+

File: **`src/main/java/org/example/bench/StringJmhPitfalls.java`**.

~~~java
package org.example.bench;

import java.util.Arrays;
import java.util.concurrent.TimeUnit;

import org.openjdk.jmh.annotations.Benchmark;
import org.openjdk.jmh.annotations.BenchmarkMode;
import org.openjdk.jmh.annotations.Fork;
import org.openjdk.jmh.annotations.Level;
import org.openjdk.jmh.annotations.Measurement;
import org.openjdk.jmh.annotations.Mode;
import org.openjdk.jmh.annotations.OutputTimeUnit;
import org.openjdk.jmh.annotations.Param;
import org.openjdk.jmh.annotations.Scope;
import org.openjdk.jmh.annotations.Setup;
import org.openjdk.jmh.annotations.State;
import org.openjdk.jmh.annotations.Warmup;
import org.openjdk.jmh.infra.Blackhole;

@State(Scope.Thread)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1, timeUnit = TimeUnit.SECONDS)
@Measurement(iterations = 5, time = 1, timeUnit = TimeUnit.SECONDS)
@Fork(2)
public class StringJmhPitfalls {

    @Param({"128", "4096"})
    public int length;

    private String text;
    private String needle;

    @Setup(Level.Trial)
    public void prepare() {
        char[] chars = new char[length];
        Arrays.fill(chars, 'a');
        text = new String(chars) + "Z";
        needle = "Z";
    }

    // Counterexample: JIT may eliminate the work if the result is discarded.
    @Benchmark
    public void wrongDiscardedResult() {
        text.indexOf(needle);
    }

    // Counterexample: the literal may be constant-folded.
    @Benchmark
    public int wrongConstantFolded() {
        return "mississippi".indexOf('s');
    }

    // Simplest way to preserve the result.
    @Benchmark
    public int correctReturn() {
        return text.indexOf(needle);
    }

    // Preserving the result via Blackhole.
    @Benchmark
    public void correctBlackhole(Blackhole bh) {
        bh.consume(text.indexOf(needle));
    }
}
~~~

This is a **JMH benchmark**, so no `main` method is needed: JMH's runner code is packaged into `target/benchmarks.jar`. Running `javac StringJmhPitfalls.java` alone without the JMH dependencies and annotation processor will fail to compile due to missing JMH classes.

| Method | Issue or safeguard | Should the result be used to judge algorithm speed? |
| --- | --- | --- |
| `wrongDiscardedResult` | Result discarded → DCE risk. | No. |
| `wrongConstantFolded` | All literals → constant-folding risk. | No. |
| `correctReturn` | Input via state, return consumed by JMH. | Yes, for the specific workload described. |
| `correctBlackhole` | Input via state, consumed by Blackhole. | Yes, though do not treat sink overhead differences as an algorithm comparison. |

The two `wrong`-prefixed methods are solely **illustrations of why a benchmark can report misleading scores**. This code measures `indexOf` on an existing String; if you also need to measure String creation/GC, write a separate workload with allocations inside the measured method.

## 8. Building, Running, and Reading the JMH Report

Inside the newly created Maven project directory:

~~~bash
mvn clean verify
java -jar target/benchmarks.jar StringJmhPitfalls -wi 5 -i 5 -w 1s -r 1s -f 2 -t 1 -bm avgt -tu ns
~~~

The second command filters methods belonging to `StringJmhPitfalls` and runs with:

| Flag | Meaning |
| --- | --- |
| `-wi 5` | 5 warmup iterations. |
| `-w 1s` | Roughly 1 second per warmup iteration. |
| `-i 5` | 5 measurement iterations. |
| `-r 1s` | Roughly 1 second per measurement iteration. |
| `-f 2` | 2 separate JVM forks. |
| `-t 1` | 1 worker thread. |
| `-bm avgt` | Average time per operation. |
| `-tu ns` | Unit in nanoseconds. |

With 4 benchmark methods × 2 `length` values × 2 forks, this configuration takes considerable time because each fork runs multiple seconds of warmup and measurement. If you only want to verify that the project/build runs, reduce iteration counts/durations **for a smoke test**; when reporting performance, use a sufficiently reliable measurement configuration.

JMH prints warmup, measurement, and summary output with columns such as `Benchmark`, `(length)`, `Mode`, `Cnt`, `Score`, `Error`, `Units`. Here `Score` typically denotes `ns/op`; `Error` reflects the uncertainty JMH estimates from observed data. **There is no single fixed ns/op stdout number** across machines, JDKs, or runs. Never fabricate benchmark numbers without actually measuring.

Saving structured results:

~~~bash
java -jar target/benchmarks.jar StringJmhPitfalls.correctReturn -wi 5 -i 5 -w 1s -r 1s -f 2 -t 1 -bm avgt -tu ns -rf json -rff jmh-results.json
~~~

This command runs only `correctReturn` and exports a JSON report. When comparing figures later, record the JDK vendor/version, JVM flags, JMH version, CPU model, OS, thread count, GC, power profile, code version, and inputs.

## 9. Experimental Pitfalls Beyond Warmup/DCE/Folding

### Valid JVM Optimizations

The JIT can inline methods or use intrinsics for `String` operations. Those optimizations may reflect the actual execution path, so do not disable all optimizations by default. However, if work is unused, the JIT may **eliminate the algorithm itself**; that is a benchmark bug.

**Loop-invariant code motion** can hoist unchanging computations out of a loop; **escape analysis/scalar replacement** can avoid heap-allocating a temporary object. A benchmark where created objects are never used can report meaninglessly low costs compared to real scenarios.

### GC, Caches, and Threads

- JMH does not completely isolate the CPU from background load, caches, branch prediction, thermal throttling, or frequency scaling.
- `@State(Scope.Benchmark)` shares state across threads. Unless you intend to measure contention, use `Scope.Thread` as in the sample and `-t 1` when learning the basics.
- `@Setup(Level.Invocation)` has overhead; using it on tiny benchmarks frequently distorts results.
- If the goal involves allocation, you can try the `-prof gc` profiler for GC/allocation insights; interpret it according to profiler semantics rather than guessing from score alone.
- When one invocation intentionally processes N elements, describe clearly what one operation consists of; `@OperationsPerInvocation(N)` is appropriate only when N is exact and fixed.

### Unrepresentative Data

Measuring on a `String` of repeated `'a'` characters helps learn JMH, but does not represent multilingual logs, URL paths, Unicode strings, early/late tokens, or miss cases. To measure the impact of length, match probability, character sets, or cache size, introduce each dimension via `@Param` or a clearly defined workload.

## 10. Workflow for Designing and Interpreting Useful Benchmarks

1. **Ask a clear question:** are you measuring searching, building, or concatenation? Put that exact operation inside the benchmark method.
2. **Verify correctness:** compared variants must produce identical results on the same inputs. JMH does not replace unit tests.
3. **Design inputs:** use runtime state/params and test several representative sizes and scenarios.
4. **Keep results alive:** return or `Blackhole.consume`; avoid logging or I/O.
5. **Eliminate unrealistic constant folding:** do not benchmark a fixed literal expression and generalize from it.
6. **Warmup, measure, fork:** use enough iterations/duration to observe stability and variance.
7. **Ensure equivalent conditions:** same JDK, flags, machine, thread count, inputs, mode, and units.
8. **Read score together with error:** avoid declaring a winner when the difference is small compared to noise.
9. **Cross-check against the real application:** microbenchmarks measure a very narrow point; end-to-end latency/throughput also depends on many other layers and GC.

### Warning Signs to Investigate

| Observation | Possible cause | Fix |
| --- | --- | --- |
| Method discarding result runs as fast as an empty benchmark | DCE. | Use return or Blackhole. |
| Literal search is “unusually fast” | Constant folding. | Supply inputs from runtime state. |
| Early iterations are slow then drop sharply | JVM is still warming up / JIT compiling. | Increase warmup; inspect per-iteration and per-fork output. |
| High variance across forks | GC, CPU load, profiling, or environment differences. | Check environment, rerun, analyze variance. |
| Adding println makes score jump dramatically | Benchmark is measuring I/O. | Remove logging from the measured region. |
| Two scores are very close with overlapping error | Signal is small relative to noise. | Avoid over-claiming; refine the experiment. |

## 11. Self-Check Questions

**1. Are `System.nanoTime` and a million-iteration loop accurate enough?** No. The compiler may eliminate/fold code, and the measurement does not control warmup or forks.

**2. Does `@Warmup(iterations=5)` guarantee steady state?** No. You must inspect trends across iterations and multiple forks.

**3. `return "mississippi".indexOf('s')` prevents DCE; what pitfall remains?** Constant folding, because the result can be precomputed as `2`.

**4. When should Blackhole be used?** When you want JMH to consume one or more values computed inside the benchmark.

**5. When measuring `indexOf` on an existing string, where should the string be created?** Typically in `@Setup(Level.Trial)`, outside the timed invocation.

**6. Why is there no single ns/op stdout for the example?** JMH measures real runtime behavior, which depends on the machine, JVM, inputs, system load, and optimizations.

**7. Should you compare `correctReturn` against `correctBlackhole` to pick the faster algorithm?** No. They perform the exact same computation and differ only in the sink consuming the result.
