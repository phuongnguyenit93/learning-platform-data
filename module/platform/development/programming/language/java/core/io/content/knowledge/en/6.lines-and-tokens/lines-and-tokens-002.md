# LF, CRLF, CR, and Line Ending Conventions in Java

In text files, a **line ending** is a convention that uses one or more control characters to separate lines. The three most common forms are **LF** (`\n`), **CRLF** (`\r\n`), and **CR** (`\r`). The same visible content can be stored using different character or byte sequences; this affects file reading, string comparison, token processing, line counting, transferring data across operating systems, and complying with formats/protocols that require a specific line ending style.

In Java I/O, two operations must be distinguished:

- **Reading raw text:** preserves the `\r` and `\n` characters present in the data.
- **Reading line by line:** returns line content strings; the API may *recognize and strip* the line terminator.

This lesson clarifies the corresponding bytes and characters, historical conventions, the behavior of `BufferedReader`, `String.lines()`, and `Files.readAllLines`, how to write line endings intentionally, and common processing mistakes.

## 1. What Are LF, CR, and CRLF?

| Name | Java Escape | Unicode | Bytes in ASCII / UTF-8 | Hexadecimal Form | Conventional Meaning |
|---|---|---|---|---|---|
| **LF** — Line Feed | `\n` | U+000A | One byte `0A` | `0x0A` | Advance to the next line |
| **CR** — Carriage Return | `\r` | U+000D | One byte `0D` | `0x0D` | Return the position to the start of the line in typewriter mechanics |
| **CRLF** — Carriage Return + Line Feed | `\r\n` | U+000D then U+000A | Two bytes `0D 0A` | `0x0D 0x0A` | Character pair used as a single line terminator |

In **UTF-8**, LF and CR remain single bytes `0A` and `0D`. In UTF-16LE, those same code units typically appear as `0A 00` and `0D 00` at the byte level; therefore, you must not scan for byte `0A` to find lines in arbitrary encodings without understanding the charset. The table above only asserts byte values for ASCII and UTF-8.

**Java treats CRLF as two `char`s**: `'\r'` and `'\n'`. At the line-reading layer, many APIs treat those two adjacent `char`s as **a single line break**, rather than two independent line breaks. This is distinct from the fact that the string contains two code units.

### Operating System Context

- **Unix/Linux** and modern macOS conventionally use **LF** as the line terminator in text files.
- **Windows** traditionally uses **CRLF** in many text files and APIs/utilities.
- **Classic Mac OS before macOS** used **CR**.
- Many modern editors read and write all three styles; the file format, network protocol, application, and configuration ultimately determine the exact style stored.

Do not assume that *every* file created on Windows always has CRLF or every file on Linux only has LF. For example, files checked out from Git, generated by Java code writing `"\n"`, or exported by external software may retain a line ending style different from the OS convention.

## 2. Line Endings Are Part of the Text, Not Display Formatting

The following two strings usually render identically in a text viewer:

```java
String lf = "first\nsecond";
String crlf = "first\r\nsecond";
```

However:

- `lf.length() == 12`, because there is only one `char` `'\n'` in the middle.
- `crlf.length() == 13`, because there are two `char`s `'\r'` and `'\n'` in the middle.
- `lf.equals(crlf)` is **`false`**; their UTF-8 byte arrays, lengths, checksums/hashes, and offsets also differ.

A piece of text may contain lines `A`, `B`, `C` where the file uses LF, CRLF, CR, or **mixes all three**. When inspecting the content visually, it is not easy to spot the difference.

Do not confuse control characters with the two literal characters `\` and `n`. In Java source code, `"\n"` is **one** LF character at runtime; `"\\n"` is **two** visible characters `\` and `n`. Similarly, `"\r\n"` produces two control characters, whereas `"\\r\\n"` is merely literal notation text.

### Line Terminator, Line Separator, and "Line" Concepts

For I/O, LF, CRLF, and CR are commonly called **line terminators** — a character or pair of characters marking the end of a line. **Line content** is the data between terminators. Line-reading APIs such as `BufferedReader.readLine()` return the **line content** without the terminator.

Depending on the API, `"A\n"` can represent **one line `A` with a terminator**, rather than two lines with a trailing empty line. Distinguish:

- **A true empty line** lies between two consecutive line breaks, or is the line before a line break at the start of the data.
- **End of file immediately after a line break** usually **does not generate an extra** empty line from `readLine()` or `String.lines()`.
- **A file without a trailing line break** still has a final line if content remains.
- **An empty file** may be counted as 0 lines by APIs; do not automatically assume 1 line.

These cases directly affect line counts, parser logic, and saving back the exact original format.

## 3. What Line-Reading Options Does Java Have?

### `BufferedReader.readLine()`

`BufferedReader.readLine()` accepts line terminators consisting of **LF**, **CR**, or **CRLF**. It returns a `String` **excluding** line termination characters and returns `null` at EOF. A valid empty line returns `""`.

One note: adjacent CRLF characters are viewed as **one** terminator. If Java code reads using `readLine()`, the application typically **no longer knows** whether the original line used LF, CRLF, or CR.

### `String.lines()` (Java 11+)

`"text".lines()` returns a `Stream<String>` of lines, recognizing `\n`, `\r`, or `\r\n`. Terminators are stripped from the result. This stream is processed lazily on demand and does not require splitting the whole string into an array upfront.

- The string `""` has no lines: empty stream.
- The string `"A"` has one line `A`.
- The string `"A\n"` has one line `A`, **without automatically generating a trailing empty line**.
- The string `"A\n\n"` has line `A` and one empty line.
- The string `"\n"` contains one empty line.
- CRLF is only **one** terminator even though it consists of two `char`s.

`String.lines()` is **not synonymous** with "splitting on all Unicode line breaks": it recognizes strictly the three forms specified by the API (LF, CR, CRLF), whereas regex `\R` in Java supports a broader set of line breaks (such as Unicode NEL, LS, PS).

### `Files.readAllLines` and `Files.lines`

Two APIs in `java.nio.file.Files` also recognize CRLF, LF, and CR by contract:

- `Files.readAllLines(path, charset)` reads lines into a `List<String>`, stripping line terminators, **holding the entire result in memory**.
- `Files.lines(path, charset)` creates a `Stream<String>` that reads the file lazily. Because the stream holds a file resource, **close the stream** in `try-with-resources`; a terminal operation like `count()` is no substitute for closing it.
- `Files.readString(path, charset)` reads **the entire text content**, including intact CR/LF characters, if decoded properly; do not use `readAllLines` to produce a copy that must preserve every line ending.

Line-based reading is valuable when processing text data at the **line** level; to preserve bytes verbatim, use `Files.readAllBytes` or byte streams, remembering to choose the right charset when reconstructing text.

## 4. Example 1 — Three Conventions in the Same String

Create file `LineEndingDemo.java` (Java 17+):

```java
import java.io.BufferedReader;
import java.io.StringReader;

public class LineEndingDemo {
    public static void main(String[] args) throws Exception {
        String mixed = "A\r\nB\nC\rD\r\n";

        System.out.println("raw length=" + mixed.length());
        System.out.println("String.lines count=" + mixed.lines().count());

        try (BufferedReader reader = new BufferedReader(new StringReader(mixed))) {
            String line;
            int index = 1;
            while ((line = reader.readLine()) != null) {
                System.out.println("line " + index++ + "=[" + line + "]");
            }
        }

        String normalized = mixed.replace("\r\n", "\n").replace('\r', '\n');
        System.out.println("normalized=" + normalized.replace("\n", "<LF>"));
        System.out.println("normalized length=" + normalized.length());
        System.out.println("keeps trailing LF=" + normalized.endsWith("\n"));
    }
}
```

Run:

```bash
javac -encoding UTF-8 --release 17 LineEndingDemo.java
java LineEndingDemo
```

Verified output:

```text
raw length=10
String.lines count=4
line 1=[A]
line 2=[B]
line 3=[C]
line 4=[D]
normalized=A<LF>B<LF>C<LF>D<LF>
normalized length=8
keeps trailing LF=true
```

**How to interpret this:**

1. The variable `mixed` contains CRLF, LF, CR, and CRLF in sequence. Those four line terminators produce four lines carrying content `A`, `B`, `C`, `D`.
2. `mixed.length()` equals `10` UTF-16 code units: four letters, two single LF/CR characters (in the middle), plus four characters inside the two CRLF pairs.
3. `BufferedReader.readLine()` accepts all three terminator forms and **strips the terminators**, so the output consists of four strings containing no `\r` or `\n`.
4. The call `mixed.replace("\r\n", "\n").replace('\r', '\n')` converts **CRLF first**, then single CR to LF. The result `A\nB\nC\nD\n` has length `8` code units.
5. The trailing LF remains in `normalized`. If you immediately call `normalized.lines()` afterward, the stream still has only four lines, without producing a trailing empty line.

**Replacement order is critical:** if you replace `\r` with `\n` **first**, a CRLF sequence becomes `\n\n` — two line breaks, inadvertently adding an empty line.

The normalization above only replaces line-break characters **within the text string itself**. It does not alter original data if you have not written the new string to a file, and it does not choose the charset or line ending style required by an external protocol.

## 5. Example 2 — Bytes in a File and `Files` Behavior

Create file `FileLineEndingDemo.java` (Java 17+):

```java
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.HexFormat;
import java.util.List;

public class FileLineEndingDemo {
    public static void main(String[] args) throws Exception {
        Path file = Files.createTempFile("line-ending-demo-", ".txt");
        String text = "first\nsecond\r\nthird\r";
        try {
            Files.writeString(file, text, StandardCharsets.UTF_8);
            byte[] bytes = Files.readAllBytes(file);
            System.out.println("hex=" + HexFormat.of().formatHex(bytes));
            System.out.println("raw same=" + text.equals(
                    Files.readString(file, StandardCharsets.UTF_8)));
            List<String> lines = Files.readAllLines(file, StandardCharsets.UTF_8);
            System.out.println("lines=" + lines);
            System.out.println("line count=" + lines.size());
        } finally {
            Files.deleteIfExists(file);
        }
    }
}
```

```bash
javac -encoding UTF-8 --release 17 FileLineEndingDemo.java
java FileLineEndingDemo
```

```text
hex=66697273740a7365636f6e640d0a74686972640d
raw same=true
lines=[first, second, third]
line count=3
```

The hex output shows:

- The word `first` is followed by `0A`, which is LF.
- The word `second` is followed by `0D0A`, which is CRLF.
- The word `third` is followed by `0D`, which is CR.
- No bytes or content lines are implicitly altered by Java when `Files.writeString` receives a string with explicit line breaks.

`Files.readString` preserves the exact sequence of line terminators in the decoded text; hence `raw same=true`. Meanwhile `Files.readAllLines` **strips terminators**, returning only three lines. If you join the list of lines back with a chosen separator, the result may look identical on display but **does not restore the original file verbatim**.

The example uses only ASCII data so UTF-8 represents each character as one byte. With Vietnamese text, non-ASCII characters may occupy multiple bytes; LF/CR remain U+000A/U+000D at the Unicode level, though when inspecting bytes you must account for the specific charset.

## 6. Example 3 — Empty Lines, Trailing Terminators, and Tokens

Create file `EndOfLineCasesDemo.java` (Java 17+):

```java
import java.util.Arrays;
import java.util.Scanner;

public class EndOfLineCasesDemo {
    public static void main(String[] args) {
        String[] samples = {"", "A", "A\n", "A\n\n", "\n", "\r\n"};
        for (String sample : samples) {
            String escaped = sample.replace("\r", "\\r").replace("\n", "\\n");
            System.out.println("text=[" + escaped + "], lines="
                    + sample.lines().map(String::length).toList());
        }
        try (Scanner scanner = new Scanner("Ada 42\r\nLinh 7\n")) {
            System.out.println("name=" + scanner.next());
            System.out.println("age=" + scanner.nextInt());
            System.out.println("rest=[" + scanner.nextLine() + "]");
            System.out.println("next line=[" + scanner.nextLine() + "]");
        }
    }
}
```

```bash
javac -encoding UTF-8 --release 17 EndOfLineCasesDemo.java
java EndOfLineCasesDemo
```

```text
text=[], lines=[]
text=[A], lines=[1]
text=[A\n], lines=[1]
text=[A\n\n], lines=[1, 0]
text=[\n], lines=[0]
text=[\r\n], lines=[0]
name=Ada
age=42
rest=[]
next line=[Linh 7]
```

The `lines` list deliberately holds **line lengths** instead of printing each element directly: `List.of("")` also prints as `[]`, making it easy to confuse with an empty list. In the output above, `lines=[0]` is **one empty line**; `lines=[]` is **zero lines**.

`Scanner` is used to illustrate the difference between **tokens** and **lines**:

- `next()` reads token `Ada`; `nextInt()` reads numeric token `42`. By default, Scanner splits tokens on whitespace according to `Character.isWhitespace`, so line breaks act as token boundaries.
- After `nextInt()`, the CRLF line terminator has not yet been consumed by `nextLine()` in the way many people expect. The first `nextLine()` receives **the remainder of the current line**, which is the empty string `""`.
- Only the next `nextLine()` call retrieves the line `Linh 7`.

In interactive input problems, this is the common reason why `nextLine()` right after `nextInt()` appears to be "skipped". You must actively consume the remainder of the line if switching from token operations to reading a full line. Do not casually use `scanner.useDelimiter("\n")` to handle CRLF: a stray CR can remain depending on the delimiter pattern and read operations.

## 7. Writing Line Endings: Which Approach Should You Use?

### When You Want the Runtime Environment's Convention

- `System.lineSeparator()` returns the system-dependent line terminator string (typically `"\n"` on Linux/macOS and `"\r\n"` on Windows).
- `BufferedWriter.newLine()` writes a line break based on the system-defined convention.
- `PrintWriter.println(...)` and `System.out.println(...)` write a line ending according to the formatter/writer and platform behavior.

Example inside a method that already has a `BufferedWriter writer`:

```java
writer.write("Dòng thứ nhất");
writer.newLine();
writer.write("Dòng thứ hai");
```

This is **illustrative code**; it requires an initialized `writer` variable and `IOException` handling where appropriate. If you want text output to use the operating system's line-ending style, `newLine()` expresses that intent clearly.

### When You Must Follow a Specific Format or Protocol

Write the **literal terminator** mandated by the specification:

```java
String dataLf = "A\nB\n";
String dataCrlf = "A\r\nB\r\n";
String dataCr = "A\rB\r";
```

- For LF-standardized files in a project, write `"\n"` explicitly.
- For protocols requiring CRLF, you must write `"\r\n"`. For instance, HTTP/1.1 header lines per protocol syntax use CRLF; do not arbitrarily substitute `System.lineSeparator()`.
- When generating files that must preserve exact structure, **do not blindly call `newLine()` where original terminators differed** if you only have each line's content.

`System.lineSeparator()` is not an input-file inspection feature. It describes the runtime environment's convention; it **cannot infer** which line terminator an input file uses.

### Must the Last Line Have a Newline?

There is no single answer for every file. Some Unix-tradition tools prefer or require a **trailing newline at the end of a file**; some protocols/formats specify their own rules; many applications still read a final line without a terminator. For example:

```text
"A\nB"   -> line B ends at EOF, no trailing terminator
"A\nB\n" -> line B has a trailing LF
```

Both strings have **two content lines** according to `String.lines()` and `BufferedReader.readLine()`, yet **different bytes**. Check output requirements before automatically adding or removing a trailing newline.

## 8. Normalizing Newlines Without Losing Content You Need to Keep

In many applications, normalizing to LF enables consistent comparison and processing. For a **Java string** using only the three types CRLF, CR, and LF:

```java
String normalized = original.replace("\r\n", "\n").replace('\r', '\n');
```

This is **illustrative code**; `original` must be a string created in your program. This approach:

1. Converts CRLF pairs into a single LF.
2. Converts remaining standalone CRs into LF.
3. Keeps existing LFs; does not trim whitespace, remove empty lines, or append a trailing newline.

This is a lossy transformation regarding the **previous line-break type**, though it preserves line structure for the three terminator types above. If you need to **preserve exact bytes**, leave the original data untouched and do not apply normalization.

### Normalization Pitfalls

**Wrong order:**

```java
// WRONG when you want CRLF to be equivalent to one LF:
String wrong = original.replace('\r', '\n');
// CRLF -> LF LF, which may inadvertently add an empty line.
```

**Implicitly trimming whitespace:**

```java
// Different from the goal of normalizing newlines:
String changed = original.strip();
```

`strip()` also removes leading/trailing whitespace according to Unicode rules, including a trailing newline; this can break document formatting or meaningful blank data. `trim()` is not a line-ending normalization operation either.

**Splitting and rejoining:**

```java
String rebuilt = String.join("\n", original.lines().toList());
```

This operation typically loses the trailing line terminator and cannot tell where CR, CRLF, or LF originally appeared. It is useful when you **intentionally rebuild a file in a new format**, but you cannot claim it preserves the data verbatim.

**Regex `\R` has a broader scope:**

```java
String normalizedUnicodeBreaks = original.replaceAll("\\R", "\n");
```

In Java regex, `\R` matches more Unicode line-break forms than the three CRLF/CR/LF types. Use it only if explicitly required to unify Unicode breaks such as NEL, LS, and PS; otherwise, it may alter characters you did not intend to treat as line terminators. `replaceAll` uses a regex and replacement, whereas `replace` performs literal substring/character replacement.

## 9. Why Can `String.split("\n")` Fail on Real-World Data?

A common reflex is to read a text file and then write:

```java
String[] lines = text.split("\n");
```

That only works if you **know for certain** the source uses LF and the trailing-line behavior of `String.split` is what you want. Important differences:

| Input | `split("\n")` | `String.lines()` |
|---|---|---|
| `"A\nB"` | `["A", "B"]` | Two lines `A`, `B` |
| `"A\r\nB"` | First element is `"A\r"` | Two lines `A`, `B` without CR |
| `"A\rB"` | Single element containing the whole string | Two lines `A`, `B` |
| `"A\n"` | Drops trailing empty string by default | One line `A` |
| `"\n"` | May return a zero-element array by default | One empty line |
| `""` | `split` may return one empty element | Zero lines |

`String.split(regex)` operates by **regular expression**, not by the "Java line" concept if the regex pattern is insufficient. In particular, `split(regex)` uses a default limit of `0`, which **discards trailing empty strings**. To keep trailing empty entries, pass a negative limit such as `text.split("\\R", -1)`; however, that can produce **an empty entry after a trailing terminator**, differing from `String.lines()` semantics.

For straightforward line iteration, prefer `String.lines()` (in-memory string), `BufferedReader.readLine()`, or `Files.lines(...)`. When line breaks must be preserved, read raw text and parse/store the corresponding breaks yourself.

## 10. Mixed CRLF, LF, and CR Data: How Should You Handle It?

Suppose you ingest files from multiple systems containing all three types. First establish the **input contract**:

- If the file only requires extracting **line-by-line data**, `BufferedReader.readLine()` or `Files.lines` splits all three forms without manual character replacement.
- If you must subsequently write out a consistent LF format, you can normalize on the string or use `BufferedWriter` writing each line plus literal `"\n"`. Decide whether a final line terminator is needed.
- If you must preserve the **exact** newline style of each line, do not use terminator-stripping APIs as the sole storage; parse raw text and record each line's terminator as well.
- If a file is opened as bytes to process structured data, first know the **charset**. Do not search for `0A`/`0D` by blindly scanning binary data or UTF-16 without understanding the encoding.
- If the data follows a **protocol**, use the line terminator required by the protocol, even if it differs from the host machine's `System.lineSeparator()`.

### A Parser That Needs to Preserve Terminator Types

At the data level, do not store only `List<String> lines` when the application needs a 100% round-trip:

```text
Original content:  "A\r\nB\nC\rD"
Logical segments:  ("A", "\r\n"), ("B", "\n"), ("C", "\r"), ("D", "")
```

In this example, each pair stores the **line content** and **original terminator** (`""` for a final line without a terminator). Concatenating the content and terminator of each pair in order reconstructs the exact string. If original **bytes** must be preserved rather than just characters, you must also preserve the original charset/BOM and byte stream or an exact equivalent encoding mechanism.

Do not silently strip a BOM (Byte Order Mark), change charset, or trim whitespace while "only normalizing line endings"; those transformations fall outside handling LF/CRLF/CR.

## 11. Lines, Tokens, and Document Structure

Because this lesson belongs to the **Lines and Tokens** group, keep these clearly separate:

- **Line:** a segment of text bounded by line terminators according to API rules.
- **Token:** a unit defined by a **delimiter** (whitespace, comma, semicolon, regex, parser syntax, etc.). One line may contain multiple tokens, and a token may span across lines if the parser/format permits.
- `Scanner` uses a whitespace delimiter by default to read tokens via `next()`, `nextInt()`, etc.; `nextLine()` reads the remainder of the current line and consumes the line terminator.
- `BufferedReader.readLine()` does not split tokens; it only reads one line. You can parse tokens within the line string afterward.

For example, `"Ada 42\r\nLinh 7\n"` has two lines yet four whitespace-delimited tokens (Ada, 42, Linh, 7). When switching from reading tokens to reading lines, actively handle the leftover delimiter as shown in Example 3.

An important note for **CSV**: if CSV allows newline characters inside quoted fields, **one logical record is not necessarily one physical line**. CSV parsers should follow CSV syntax rather than relying solely on `readLine()` followed by `split(",")`. Similarly, newlines inside string literals of a structured format may carry distinct meaning.

## 12. Common Mistakes

1. **Calling CRLF "one Java character."** It consists of two `char`s (`\r` then `\n`), even though many line-reading APIs treat it as one terminator.
2. **Using `split("\n")` on CRLF.** Results may retain `\r` at the end of tokens/lines, breaking `equals` and data parsing.
3. **Assuming `readLine()` preserves newlines.** It strips the terminator; after line-based reading, you cannot accurately deduce the old terminator from the returned content.
4. **Confusing an empty line with EOF.** With `BufferedReader.readLine()`, `""` is an empty line; `null` is end of input.
5. **Using `System.lineSeparator()` to split files from another system.** That is the convention of the platform where the program is running, not metadata of the input file.
6. **Normalizing CR before CRLF.** `\r\n` becomes `\n\n`, increasing the empty line count.
7. **Replacing line-ending handling with `strip()`/`trim()`.** Those methods also remove leading/trailing whitespace and can drop a trailing newline.
8. **Automatically rewriting whole files when only reading is needed.** If a parser already recognizes CRLF/LF/CR, reading lines does not require rewriting the file; rewriting can create diffs, change hashes, and break original fidelity.
9. **Keeping the lines while ignoring EOF rules.** `"A"` and `"A\n"` have the same content line but different representations and potentially different format contracts.
10. **Scanning byte `0A` to split lines across all charsets.** UTF-16 and some other encodings have different byte layouts; decode properly first or parse bytes according to the format.
11. **Implicitly using `println` when a protocol requires CRLF.** Output will depend on the operating system instead of protocol rules.
12. **Equating physical lines with logical records.** CSV, multiline content in quoted strings, and syntax-defined formats require an appropriate parser.
13. **Guessing newlines solely from the operating system.** Files may pass through Git, networks, editors, and tools; inspect actual data or follow a published contract.
14. **Attempting to normalize every character that looks like a "line break."** `\R` in regex is broader than the LF/CR/CRLF set; use it only when intending to handle the full Unicode line-break group.

## 13. Solution Selection Checklist

| Need | Appropriate Approach |
|---|---|
| Read line by line regardless of original terminator | `BufferedReader.readLine()` or `Files.lines(path, charset)` |
| Process lines in an existing string | `String.lines()` |
| Preserve CR, LF, and CRLF in text | `Files.readString(path, charset)`, avoiding split/rejoin if exact preservation is needed |
| Preserve file **bytes** verbatim | `Files.readAllBytes(path)` or byte I/O, without transcoding or rewriting |
| Normalize all three styles to LF in a string | `replace("\r\n","\n").replace('\r','\n')` |
| Write line endings matching the OS | `BufferedWriter.newLine()`, `System.lineSeparator()` |
| Write data in LF standard | Write literal `"\n"` |
| Write in CRLF standard | Write literal `"\r\n"` |
| Count text lines with Java 11+ behavior | `String.lines().count()`; watch trailing-line conventions |
| Process tokens by delimiter | `Scanner` or a dedicated parser; keep line and token concepts separate |

## 14. Self-Check Knowledge Quiz

**Question 1.** How many `char`s and how many lines does `"x\r\ny"` have according to `String.lines()`?  
**Answer:** 4 `char`s (`x`, CR, LF, `y`) and 2 lines.

**Question 2.** What does `BufferedReader.readLine()` return when encountering `"\n"` at the start of a file?  
**Answer:** The first read returns the empty string `""`; the next call, if the file ends, returns `null`.

**Question 3.** Why is `System.lineSeparator()` not used to guess a file's line ending?  
**Answer:** Its value depends on the environment where the program is running, whereas the file's content could have been created on any system or convention.

**Question 4.** What happens when `"A\r\nB"` goes through `replace('\r','\n')`?  
**Answer:** It becomes `"A\n\nB"`, inadvertently introducing an empty line. Replace `"\r\n"` first, then replace standalone CR.

**Question 5.** Do `"A\n"` and `"A"` have different `String.lines().count()` values?  
**Answer:** No; both have one line, though their lengths and byte representations differ.

**Question 6.** If data requires an exact round-trip of LF, CRLF, and CR, should you store only the result of `Files.readAllLines`?  
**Answer:** No. You must keep the raw text or keep each line's content **alongside its corresponding terminator**, and preserve the original charset/bytes if exact bytes must be reconstructed.

**Question 7.** Can `Scanner.nextLine()` immediately after `Scanner.nextInt()` return an empty string even when more data remains?  
**Answer:** Yes, because it may consume the (empty) remainder of the line containing the numeric token, and only the subsequent call reads the next line.

## Conclusion

**LF** is `\n` (U+000A), **CR** is `\r` (U+000D), and **CRLF** is the pair `\r\n`. The difference exists in string content and file bytes even when rendered output looks identical. In Java, `BufferedReader.readLine()`, `String.lines()`, and line-reading `Files` APIs generally understand all three forms and strip the line terminator. When you need **verbatim preservation**, read and retain raw data; when you need **normalization**, deliberately choose a target convention and handle CRLF before CR. When **writing**, choose the line break required by the format or protocol rather than defaulting to the runtime environment's convention.
