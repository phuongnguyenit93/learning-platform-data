# Reading `Caused by`, `Suppressed`, and Abbreviated Frames in Java Stack Traces

When a Java program reports an error, the stack trace often contains multiple layers beyond the first exception line: `Caused by`, `Suppressed`, and `... N more`. Misreading these parts easily leads to fixing the wrong location, missing the root error, or mistakenly assuming the log was truncated. This lesson belongs to the **Java Core – Exception / Diagnostics and Logging** group, using Java 17+.

Goal: read the structure of a standard stack trace produced by `Throwable.printStackTrace(...)`, follow the **cause chain**, understand **suppressed exceptions** (especially in `try-with-resources`), reconstruct the meaning of **abbreviated common frames**, and apply a useful diagnostics and logging workflow.

## 1. Viewing a Stack Trace as a Contextual Error Graph

An exception in Java stores several different pieces of information:

- **Exception type**: for example, `java.lang.IllegalStateException`.
- **Message**: the descriptive text after `:`; may be `null`.
- **Stack trace**: a sequence of `StackTraceElement` objects representing the call stack at the time the stack trace was recorded; usually includes the class name, method, file, and line number.
- **Cause**: the cause linked via `Throwable.getCause()`, typically an underlying exception wrapped into a higher-level exception with more context.
- **Suppressed exceptions**: a set of secondary exceptions retrieved via `Throwable.getSuppressed()`. They do not replace the cause and often appear when resource cleanup also fails.

A typical printout has the following structure. This is an **illustrative stack trace**—the file names and line numbers are for explanation, not guaranteed output from a specific program:

```text
java.lang.IllegalStateException: Không thể xử lý yêu cầu
    at app.OrderService.placeOrder(OrderService.java:52)
    at app.OrderController.submit(OrderController.java:31)
    Suppressed: java.io.IOException: Lỗi đóng bộ ghi
        at app.AuditWriter.close(AuditWriter.java:18)
        at app.OrderService.placeOrder(OrderService.java:52)
        ... 1 more
Caused by: java.lang.IllegalArgumentException: Mã đơn hàng rỗng
    at app.OrderParser.parse(OrderParser.java:14)
    at app.OrderService.placeOrder(OrderService.java:49)
    ... 1 more
```

Reading by semantic layers:

1. The first line shows the **exception being printed**: `IllegalStateException` with the message “Không thể xử lý yêu cầu”.
2. The `at ...` lines immediately following are the **stack frames of that exception**. In the example, execution flowed through `OrderController.submit` and then `OrderService.placeOrder`.
3. The indented `Suppressed:` branch records a **secondary error** while closing the writer. This error does not necessarily explain the primary reason the request failed.
4. `Caused by:` links to the **cause exception**: `IllegalArgumentException` about the order ID. This is usually where to start tracing invalid input conditions.
5. `... 1 more` indicates that **one frame at the bottom of the child exception's stack matches the bottom of the enclosing exception's stack in the same print branch** and has been omitted; it does not mean “one more error”.

Do not assume the first exception line is the **root cause**. The outermost exception usually represents the application operation that failed, while the cause layers explain why the operation could not complete.

## 2. What Does a Stack Frame Contain?

A frame typically has the form:

```text
at package.ClassName.methodName(FileName.java:123)
```

Meaning of each part:

| Component | Role |
|---|---|
| `package.ClassName` | Name of the class containing the method in the stack |
| `methodName` | Method of the frame; may be `lambda$...` or a compiler-generated name |
| `FileName.java` | Source file name if corresponding debug information is available |
| `:123` | Corresponding source line number if the JVM has line metadata |
| Order of `at` lines | The top frame is closest to where the stack was recorded; lower frames are outer calling contexts |

Example:

```text
at com.example.repo.UserRepository.find(UserRepository.java:88)
at com.example.service.UserService.load(UserService.java:41)
at com.example.web.UserController.show(UserController.java:27)
```

Reading from **top to bottom** goes from where the error was recorded outward to the callers; the actual call path before the error is in the reverse direction: `UserController.show` → `UserService.load` → `UserRepository.find`.

Some special forms:

- `(Native Method)`: a native method frame, usually without a Java line number.
- `(Unknown Source)`: no matching source file/line information is available to print.
- `lambda$...`, `invoke`, `run`, `execute`: frames that may be generated by lambdas, reflection, proxies, or frameworks. Not all of them are places you should modify.
- A stack frame only shows **where control passed through**, not proof that that specific method is the business-logic root cause.
- Line numbers depend on the code version, optimizations, debug information, and the printed stack; never apply line numbers from one build to a different deployed version.

`Throwable.getStackTrace()` returns a `StackTraceElement[]` array. Each element provides methods such as `getClassName()`, `getMethodName()`, `getFileName()`, `getLineNumber()`, and `isNativeMethod()`. Module/class loader names may be included in modern stack trace printouts; the display format can vary slightly depending on the JDK version and logging mechanism.

### Standalone example: reading frames via API, independent of line numbers

Create the file `TraceFramesDemo.java`:

```java
public class TraceFramesDemo {
    static void leaf() {
        throw new IllegalStateException("dữ liệu hỏng");
    }

    static void middle() {
        leaf();
    }

    public static void main(String[] args) {
        try {
            middle();
        } catch (IllegalStateException e) {
            System.out.println("type = "
                    + e.getClass().getSimpleName());
            System.out.println("message = " + e.getMessage());

            StackTraceElement[] frames = e.getStackTrace();
            for (int i = 0; i < Math.min(3, frames.length); i++) {
                System.out.println("frame " + i + " = "
                        + frames[i].getMethodName());
            }
        }
    }
}
```

Compile and run with JDK 17 or later:

```bash
javac TraceFramesDemo.java
java TraceFramesDemo
```

Output:

```text
type = IllegalStateException
message = dữ liệu hỏng
frame 0 = leaf
frame 1 = middle
frame 2 = main
```

The output is written using method names because source line numbers in a stack trace can change when editing the example. `frames[0]` is the frame closest to where the exception was created in `leaf`. A `Throwable` that is **created earlier and thrown later** can retain the stack trace from its creation point rather than the rethrow site; if you need to re-record it at another location, there is the `fillInStackTrace()` API, though altering a stack trace changes diagnostic information and should not be done casually.

## 3. `Caused by`: An Exception Wrapping Context Around a Previous Exception

When a lower layer throws an error, a higher layer can wrap it in an exception type meaningful to that layer:

```java
try {
    repository.load();
} catch (java.io.IOException cause) {
    throw new IllegalStateException("Không đọc được hồ sơ", cause);
}
```

This is an **illustrative snippet**: assume `repository.load()` can throw `IOException`. The constructor taking a `cause` argument establishes a link to the original error. The reader can trace:

```text
IllegalStateException: Không đọc được hồ sơ
Caused by: IOException: ...
```

`Caused by` is a **causal relationship recorded by the code or library author**, not something the JVM automatically infers between arbitrary errors. If an upper layer creates a new exception **without passing the cause**, the chain breaks even though an earlier error occurred.

### Standalone example: creating and traversing three levels of `Caused by`

File `CauseChainDemo.java`:

```java
public class CauseChainDemo {
    static void parse() {
        throw new IllegalArgumentException("id phải dương");
    }

    static void service() {
        try {
            parse();
        } catch (IllegalArgumentException e) {
            throw new IllegalStateException(
                    "không tải được người dùng", e);
        }
    }

    static void controller() {
        try {
            service();
        } catch (IllegalStateException e) {
            throw new RuntimeException(
                    "request thất bại", e);
        }
    }

    public static void main(String[] args) {
        try {
            controller();
        } catch (RuntimeException e) {
            int level = 0;
            for (Throwable current = e;
                    current != null;
                    current = current.getCause()) {
                System.out.println("level " + level + ": "
                        + current.getClass().getSimpleName()
                        + ": " + current.getMessage());
                level++;
            }
        }
    }
}
```

Run:

```bash
javac CauseChainDemo.java
java CauseChainDemo
```

Output:

```text
level 0: RuntimeException: request thất bại
level 1: IllegalStateException: không tải được người dùng
level 2: IllegalArgumentException: id phải dương
```

From the API, `e.getCause()` steps **one level** inward; looping until `null` finds the deepest exception in the *cause chain*. `printStackTrace()` prints the same relationship using `Caused by:` branches and typically abbreviates common frames.

Do not confuse “deepest exception” with “the only place that needs fixing” in every system. A deep `SocketTimeoutException` may be a symptom of a network issue, resource exhaustion, or an overly short deadline; you must inspect request context, timeouts, retries, and surrounding logs. Similarly, an input validation error may be detected at a low layer while the fix belongs in the data sent from a higher layer.

### How to preserve the cause when translating exception types

Use a constructor that accepts a cause:

```java
throw new IllegalStateException("Không hoàn tất nghiệp vụ", original);
```

Instead of:

```java
throw new IllegalStateException("Không hoàn tất nghiệp vụ");
```

In the example, `original` is a `Throwable` caught in `catch`. The second approach loses the causal link. If a library provides its own exception type, choose a constructor or factory that preserves the cause. Statements that simply do `throw original;` where appropriate preserve the existing stack trace, though they add no higher-level context.

If using `initCause(...)`, the cause can only be set in valid cases when it has not yet been initialized; usually an explicit constructor is preferred to avoid double-initialization errors.

## 4. `Suppressed`: Secondary Exceptions That Do Not Hide the Primary Error

A `Throwable` can hold multiple **suppressed** exceptions, accessed via `getSuppressed()`. This relationship differs from `getCause()`:

- **Cause**: describes why the current exception occurred; typically forms a causal chain.
- **Suppressed**: additional errors that occurred during handling, cleanup, or closing resources; they are attached to an existing exception to **preserve both the primary and secondary errors**.
- An exception can simultaneously have **one cause** and **multiple suppressed exceptions**.
- Suppressed exceptions can also have their own cause/suppressed exceptions; error information is therefore a **branching graph**, not merely a linear list.

The most common case is `try-with-resources`. When the `try` body has already thrown an exception, one or more `close()` calls may also fail. Java keeps the exception from the **`try` body as the primary exception** and attaches exceptions from `close()` to the primary's suppressed array.

### Standalone example: closing two resources both fail

Create the file `SuppressedResourcesDemo.java`:

```java
import java.io.IOException;

public class SuppressedResourcesDemo {
    static class Resource implements AutoCloseable {
        private final String name;

        Resource(String name) {
            this.name = name;
        }

        @Override
        public void close() throws IOException {
            throw new IOException("đóng " + name + " thất bại");
        }
    }

    static void execute() throws Exception {
        try (Resource first = new Resource("first");
             Resource second = new Resource("second")) {
            throw new IllegalStateException("xử lý thất bại");
        }
    }

    public static void main(String[] args) {
        try {
            execute();
        } catch (Exception e) {
            System.out.println("primary = "
                    + e.getClass().getSimpleName()
                    + ": " + e.getMessage());

            for (Throwable suppressed : e.getSuppressed()) {
                System.out.println("suppressed = "
                        + suppressed.getClass().getSimpleName()
                        + ": " + suppressed.getMessage());
            }
        }
    }
}
```

Compile and run:

```bash
javac SuppressedResourcesDemo.java
java SuppressedResourcesDemo
```

Exact output:

```text
primary = IllegalStateException: xử lý thất bại
suppressed = IOException: đóng second thất bại
suppressed = IOException: đóng first thất bại
```

Explanation:

1. `try` declares `first` and then `second`.
2. The `try` body throws `IllegalStateException`; this is the primary exception.
3. Resources are closed **in reverse order of declaration**: `second` first, then `first`.
4. Both `close()` calls throw `IOException`, but the primary exception is preserved; the closing errors are attached in order as suppressed exceptions.
5. `getSuppressed()` returns an array in the order they were added, so the example output shows `second` before `first`.

This is very important when working with I/O, JDBC, files/streams, and other `AutoCloseable` types. If you only look at the first line “xử lý thất bại” and ignore all `Suppressed` entries, you can miss failed resource closures. Conversely, if you focus only on the suppressed exceptions, you can miss the `try`-body error that was the primary failure.

### When `close()` is the first error

If the `try` body **completes normally**, but `close()` throws an exception, the error from the first close operation in reverse closing order can become the **primary** exception. If subsequent closes also fail, they may be suppressed onto this primary exception. Therefore, you cannot assume every `Suppressed` comes with an exception from the `try` body; examine the execution order and the outermost exception.

Illustrative example:

```java
try (Resource first = new Resource("first");
     Resource second = new Resource("second")) {
    System.out.println("thân try thành công");
}
```

Assuming `Resource` is the same class as in the example above, both `close()` calls throw `IOException`. The closing order is `second` then `first`; `second`'s `close()` error becomes primary, and `first`'s `close()` error becomes suppressed. This is a **snippet reusing Resource**, not a standalone program.

### `addSuppressed(...)` to preserve errors manually

Java allows attaching secondary exceptions manually:

```java
try {
    doWork();
} catch (Exception primary) {
    try {
        cleanup();
    } catch (Exception cleanupFailure) {
        primary.addSuppressed(cleanupFailure);
    }
    throw primary;
}
```

This is an **illustrative snippet** inside a method with `throws Exception`; `doWork()` and `cleanup()` are application-defined methods. `Throwable.addSuppressed(...)` does not allow self-suppression and does not accept `null`. In general, use `try-with-resources` rather than rewriting complex close-management logic.

**Do not mechanically turn suppressed exceptions into causes.** A resource-closing exception is usually an **additional error during cleanup**, not the cause of the original exception.

## 5. Reading `... N more` Accurately

In stack traces printed by `Throwable.printStackTrace()`, Java looks for frames at the **bottom of a child throwable's stack trace** (cause or suppressed) that match the bottom of the **immediately enclosing throwable's stack trace currently being printed**. Instead of repeating identical frames, the printer writes:

```text
... 3 more
```

Exact meaning: **three stack frames at the bottom of the child branch match the last three frames of the parent stack** and have been omitted from the child branch's printout.

This is **duplicate-frame abbreviation**, not:

- Three more exceptions.
- Three log lines lost due to a limit.
- Three retry loops.
- Three undiscovered parts of the root cause.
- A claim that the exception has no other stack frames.

### Illustrative diagram example

Suppose the outermost exception's stack trace is:

```text
java.lang.IllegalStateException: service lỗi
    at demo.Service.load(Service.java:30)
    at demo.Controller.handle(Controller.java:20)
    at demo.Main.main(Main.java:10)
```

Full stack of the inner cause:

```text
java.lang.IllegalArgumentException: id sai
    at demo.Parser.parse(Parser.java:12)
    at demo.Service.load(Service.java:26)
    at demo.Controller.handle(Controller.java:20)
    at demo.Main.main(Main.java:10)
```

The last two frames, `Controller.handle(...)` and `Main.main(...)`, form a **common suffix**, so the cause section may be printed as:

```text
Caused by: java.lang.IllegalArgumentException: id sai
    at demo.Parser.parse(Parser.java:12)
    at demo.Service.load(Service.java:26)
    ... 2 more
```

To reconstruct the **meaning** of the cause branch, read `... 2 more` by appending the last two frames of the corresponding parent stack. The number is the **length of the common suffix** between the two stack traces in the print tree, not an arbitrary number of omitted upper frames.

### `Suppressed` also has `... N more`

Under `Suppressed:`, the common-frame rule is similar, except the suppressed branch is indented deeper and compared against the enclosing stack of **the parent branch being printed**. Do not always compare against the top-level root exception's frames if the suppressed exception is nested deep inside a cause.

Structural example:

```text
java.lang.IllegalStateException: xử lý lỗi
    at demo.Service.run(Service.java:27)
    at demo.Main.main(Main.java:7)
    Suppressed: java.io.IOException: đóng stream lỗi
        at demo.Stream.close(Stream.java:16)
        at demo.Service.run(Service.java:27)
        ... 1 more
Caused by: java.lang.IllegalArgumentException: đầu vào lỗi
    at demo.Parser.parse(Parser.java:9)
    at demo.Service.run(Service.java:21)
    ... 1 more
```

Here, `... 1 more` in both branches refers to the trailing frame matching the stack of their respective enclosing exception. Each branch is abbreviated **independently**.

### Default abbreviation vs. log truncation

`Throwable.printStackTrace(...)` **has a duplicate-frame abbreviation rule**. A logging system may add other mechanisms: line limits, printing only the last few causes, data masking, `%ex{short}` pattern configurations, or truncating oversized log events. When you see a stack trace missing sections **without the standard `... N more` form**, check the logger/appender configuration, ingest limits, centralized log service, and event size.

For standard `... N more`, those frames can be inferred from the parent stack in **the same complete printout**; if the parent printout itself was truncated by the logging system, that inference may no longer be possible.

## 6. Practical Order for Reading a Stack Trace

An effective investigation workflow:

1. **Gather all relevant log event metadata**: timestamp, service name, request/correlation ID, thread, build version, deployment location. A standalone stack trace often lacks the context in which the error occurred.
2. **Read the outermost exception**: which application-level operation reported failure? What condition does the message describe? Are there signs of error wrapping across layers?
3. **Scan `Caused by` branches**: identify the deep-layer exception with the most specific information, such as a SQL constraint, connection timeout, parse error, validation error, or I/O failure.
4. **Find a frame you own** near where the error originated: prioritize application classes/packages over generic framework wrapper frames, while still reading the calling context.
5. **Check `Suppressed`**: did any resource-closing, cleanup, or secondary operation fail? Did those failures worsen the problem?
6. **Resolve `... N more`**: trailing frames of each branch may have been printed in the parent stack; do not ignore common frames when reconstructing the call path.
7. **Cross-check against the exact code and build version**: line numbers in production must match the running artifact or commit.
8. **Check the timeline and impact**: rejected requests, retried tasks, unclosed resources, rolled-back transactions, or partially written data.
9. **Verify the hypothesis via observation or targeted tests**: do not apply a fix based solely on the exception class if the triggering condition has not been reproduced.

Reading the deepest cause first **is a helpful heuristic**, not an absolute rule. A deep `NullPointerException` may be a local bug; a deep `IOException` may be the consequence of a network disconnect; another suppressed error may indicate cleanup also failed. Consider both structure and context.

## 7. Printing and Traversing Causes and Suppressed Exceptions in Java

`Throwable` provides these APIs:

| API | Return / Effect | Notes |
|---|---|---|
| `getMessage()` | Message | May be `null` |
| `getLocalizedMessage()` | Localized message if supported by the implementation | Usually defaults to `getMessage()` |
| `getCause()` | Cause `Throwable` or `null` | Follows the cause chain |
| `getSuppressed()` | Array of suppressed `Throwable`s | May be empty |
| `getStackTrace()` | Array of `StackTraceElement` | A copy; may be empty or modified via API |
| `printStackTrace()` | Prints exception, frames, suppressed, and cause | Defaults to `System.err` |
| `printStackTrace(PrintStream)` | Prints to the specified stream | E.g., `System.out` for demonstrations |
| `addSuppressed(Throwable)` | Attaches a secondary error to the primary exception | Cannot attach itself or `null` |
| `setStackTrace(StackTraceElement[])` | Replaces the stack trace array stored in the throwable | Only for special cases; avoid losing real diagnostic info |

Traversing causes with `for (Throwable t = e; t != null; t = t.getCause())` suffices for most ordinary Java exceptions. If you build a **general-purpose error traverser** that reads `Throwable`s created by plugins or unfamiliar libraries, use an identity set to avoid infinite loops on unusual exception graphs, and distinguish cause from suppressed.

### Standalone example: reporting each branch via API

File `ThrowableTreeDemo.java`:

```java
import java.io.IOException;

public class ThrowableTreeDemo {
    public static void main(String[] args) {
        IOException root = new IOException("không đọc được tệp");
        IllegalStateException primary =
                new IllegalStateException("không tải được dữ liệu", root);

        primary.addSuppressed(
                new IOException("đóng stream thất bại"));
        primary.addSuppressed(
                new IllegalArgumentException("định dạng log không hợp lệ"));

        System.out.println("primary = "
                + primary.getClass().getSimpleName());

        Throwable cause = primary.getCause();
        System.out.println("cause = "
                + cause.getClass().getSimpleName()
                + ": " + cause.getMessage());

        for (Throwable suppressed : primary.getSuppressed()) {
            System.out.println("suppressed = "
                    + suppressed.getClass().getSimpleName()
                    + ": " + suppressed.getMessage());
        }
    }
}
```

Run:

```bash
javac ThrowableTreeDemo.java
java ThrowableTreeDemo
```

Output:

```text
primary = IllegalStateException
cause = IOException: không đọc được tệp
suppressed = IOException: đóng stream thất bại
suppressed = IllegalArgumentException: định dạng log không hợp lệ
```

This example demonstrates that **cause and suppressed coexist** on a single exception. When printed with `primary.printStackTrace(System.out)`, Java displays details of both branches along with their frames. If `printStackTrace(...)` were added to this lesson, source line numbers in the output would depend on code positions; therefore, the example above uses the API for exact, easily comparable output.

## 8. When Does `Caused by` Not Appear?

Not every stack trace has `Caused by`:

- The exception was created without a cause.
- Code wrapped an exception but omitted `cause` in the constructor.
- A framework/logger is configured to print only the outer exception or only the root cause.
- The log was truncated, split, or only logged `e.getMessage()`.
- A `Throwable` was constructed/transformed unusually and the cause was not preserved.
- An exception carries only suppressed exceptions and no cause.

Example of insufficient logging:

```java
System.err.println(e.getMessage());
```

This line prints only the message and **provides no stack trace, cause, or suppressed exceptions**. Even with a very descriptive message, it is difficult for a reader to determine the code path and accompanying error branches.

When using a logging framework, pass the **`Throwable` object** to the proper API overload to preserve the full stack. Illustrative example assuming `logger` has an SLF4J-compatible API:

```java
logger.error("Không xử lý được yêu cầu", e);
```

This is an **integration snippet**, not a standalone program, because `logger` and the library are not declared. Depending on the logging API, parameter position of the throwable and printer configuration vary; consult the documentation for the logger in use. Avoid logging only `logger.error("{}", e.getMessage())` if the goal is full diagnostics.

## 9. How `printStackTrace()` Differs from Logging Frameworks

`Throwable.printStackTrace()` prints directly from the exception object, defaulting to `System.err`. It is useful when learning, in small examples, or during local troubleshooting.

In production services, a logger typically needs to provide:

- **Structured context**: module, operation, request ID, trace ID, component name, retry status, deployment version.
- **Timestamps and severity levels**: an invalid-data error may differ in severity from a critical DB outage.
- **Full `Throwable` output**: configurable printing of causes, suppressed exceptions, and frames.
- **Data protection**: never log tokens, passwords, keys, sensitive data, or unauthorized request bodies.
- **Deduplication and collection limits**: avoid logging the same exception at every layer, which creates duplicate logs and obscures the real failure.

A common strategy: at lower layers, **rethrow with cause** and necessary context; at the application boundary responsible for handling the failure, **log once with complete information**. If a lower layer genuinely recovers and does not propagate the error, it may log at that layer, but avoid duplicating logs for the same event.

Stack traces can expose file paths, class names, SQL, parameters, or values inside messages. Do not expose raw stack traces in public responses to end users; instead, return an error code or correlation ID and store details in a controlled logging system.

## 10. `getStackTrace()` Is Not the “Cause” and Does Not Replace `getCause()`

A `StackTraceElement[]` describes only a single recorded call stack. It does not by itself show every exception that occurred. For example, a wrapper created in `service()` has its top frame in `service()`, while the cause created in `repository()` has its own top frame. Therefore, to know **why** the wrapper appeared, you need `getCause()`, not just the wrapper's top frame.

```text
Outer exception: IllegalStateException
  stack[0] = Service.load(...)
  cause    = IOException
                 stack[0] = Repository.read(...)
```

A similar situation occurs with suppressed exceptions:

```text
Primary exception: IllegalStateException
  cause         → IOException("đọc dữ liệu lỗi")
  suppressed[0] → IOException("đóng dữ liệu lỗi")
```

The `cause` and `suppressed` branches represent **different execution paths, timings, and responsibilities**. They may share trailing frames because they were invoked from the same processing flow.

Also do not assume the deepest cause always has the most frames. Each `Throwable` has its own stack array; Java may abbreviate frames when printing, but that is purely presentation.

## 11. Analyzing Long Stack Traces with Frameworks, Proxies, and Async Code

Stack traces in modern Java applications can contain many framework or library frames:

```text
at java.base/java.util.concurrent.CompletableFuture$AsyncSupply.run(...)
at java.base/java.util.concurrent.ThreadPoolExecutor.runWorker(...)
at java.base/java.util.concurrent.ThreadPoolExecutor$Worker.run(...)
at java.base/java.lang.Thread.run(...)
```

This is an **example of frame patterns you may encounter**, with no guarantee that every JDK build has the same internal classes, line numbers, or order. When investigating:

1. Find the most specific exception message and cause.
2. Identify the first frame belonging to an application package **within the specific `Throwable` branch you are reading**.
3. Look at nearby frames to understand the path from scheduler, executor, HTTP handler, or service.
4. For async code, note that the stack trace is recorded when the `Throwable` is created/filled, **so it cannot automatically reconstruct the full caller chain that submitted the task earlier**.
5. If you need to trace work across threads, add request IDs, trace/span IDs, context propagation, and structured logging.

A `CompletionException` or `ExecutionException` is often a **wrapper** indicating that an asynchronous task completed exceptionally:

```text
java.util.concurrent.CompletionException: java.io.IOException: ...
Caused by: java.io.IOException: ...
```

When `CompletableFuture.join()` encounters exceptional completion, the observer typically sees `CompletionException`; with `Future.get()` or `CompletableFuture.get()`, the caller may see `ExecutionException`. Do not change code solely because you see the wrapper; inspect the cause to find the error inside the worker or pipeline. Cancellation and interruption on the caller side should be distinguished from worker failures.

In async code, wrapping an exception in another layer does not break the cause chain if the cause is properly preserved. However, each `Throwable`'s stack may originate on a different thread; do not stitch all frames together as one continuous synchronous call.

## 12. Concrete Investigation Scenarios

### Scenario A: service reports an error, root cause is input data

```text
java.lang.IllegalStateException: Không tạo được hóa đơn
    at app.InvoiceService.create(InvoiceService.java:70)
Caused by: java.lang.NumberFormatException: For input string: "abc"
    at java.base/java.lang.Integer.parseInt(Integer.java:...)
    at app.InvoiceParser.parseId(InvoiceParser.java:24)
    ... 1 more
```

This is an **illustrative log**; `...` in the JDK class line number is not standard literal output. If the error occurred while parsing `"abc"` into a number, the fix may lie in input validation, the error message returned to the caller, or mapping rules. Check `InvoiceParser.parseId` and the actual input data rather than concluding from the outer `IllegalStateException` that JVM state is corrupted.

### Scenario B: operation failed, and closing the resource also failed

```text
java.lang.IllegalStateException: Ghi báo cáo thất bại
    at app.ReportService.write(ReportService.java:55)
    Suppressed: java.io.IOException: Đóng output thất bại
        at app.ReportFile.close(ReportFile.java:20)
        ... 1 more
Caused by: java.io.IOException: Ghi tệp thất bại
    at app.ReportFile.write(ReportFile.java:15)
    ... 1 more
```

You need to investigate **two issues**: why writing failed (cause), and whether the failed cleanup/close left dangling resources or partial data (suppressed). If you only fix `close()`, the original write error may still occur.

### Scenario C: `... N more` makes the reader think error layers are missing

```text
Caused by: java.lang.IllegalArgumentException: id rỗng
    at app.Parser.readId(Parser.java:18)
    ... 4 more
```

In a standard printout, the common frames are already in **that branch's parent stack**. If the full printout is available, read the last four frames of the parent to reconstruct the context. If the logging system captured only this `Caused by` line without its parent, fetch the **complete log event**—you cannot reliably guess the four frames from the abbreviated line alone.

### Scenario D: logger only printed the message

```text
Không xử lý được request: connection refused
```

There is not enough data to distinguish socket errors, wrapper errors, call site, and suppressed exceptions. If the original stack trace exists, use a logging API that accepts a `Throwable` and include a correlation ID; avoid hastily changing `catch` blocks to swallow errors.

## 13. Common Mistakes When Reading or Logging

### Reading only the first line

The first line may be a wrapper like `CompletionException` or a service-level `IllegalStateException`. Follow `Caused by`, read the root exception's frames, and check request context. Still, the deepest root cause is not always the final conclusion.

### Treating `Suppressed` as the root cause

Suppressed is a **secondary error branch**; in `try-with-resources`, it is usually a `close()` error that happened **after** the `try` body failed. Investigate both primary and cleanup failures without reversing their relationship by guesswork.

### Reading `... 2 more` as “two more errors”

It means **two trailing frames match the trailing frames of the enclosing stack trace** and were abbreviated. Additional exceptions are only represented by `Throwable` branches such as `Caused by` or `Suppressed`.

### Keeping the message but forgetting the cause when wrapping an exception

Wrong:

```java
throw new IllegalStateException("Tải dữ liệu thất bại");
```

If wrapping a caught exception, use a constructor that takes `cause`. Creating only a new message breaks the origin of the error and makes the log look as if the exception started in the service layer.

### Logging at every `catch` and then rethrowing

Logging the same stack at every layer causes a log storm, increases ingestion cost, and makes grouping errors harder. Attach context, preserve the cause, and let the layer responsible for handling the error log it once when possible.

### Blaming framework frames

A stack may contain many Spring, servlet, executor, or reflection frames. They show the execution context, not automatic proof of a framework bug. Pick the relevant application frame and read the cause.

### Trusting line numbers blindly when builds change

Line numbers in an exception reflect the compiled class and actual debug metadata. If CI/CD changes the source, comparing against the wrong commit easily leads to fixing the wrong line. Record the artifact version/commit ID in logs.

### Ignoring suppressed exceptions when `close` or rollback fails

Cleanup failures can leak resources or leave data in an unwanted state. Do not dismiss every suppressed exception as a harmless warning; evaluate it based on the nature of the resource.

### Truncating stack traces manually with string manipulation

Cutting `stackTraceString` by line count can drop causes or suppressed exceptions. Use properly configured loggers/appenders, retain full events where authorized, and abbreviate only in a controlled way at display surfaces.

### Returning raw stack traces to end users

Stacks can reveal internal packages, file names, queries, endpoints, metadata, and data inside messages. Separate public error messages from internal log details, and use error codes for correlation.

## 14. Stack Trace Reading Exercise and Answers

Examine the illustrative printout:

```text
java.lang.IllegalStateException: Không xuất được CSV
    at export.CsvService.export(CsvService.java:40)
    at export.Main.main(Main.java:10)
    Suppressed: java.io.IOException: Lỗi đóng writer
        at export.CsvWriter.close(CsvWriter.java:21)
        at export.CsvService.export(CsvService.java:40)
        ... 1 more
Caused by: java.lang.IllegalArgumentException: Thiếu tên cột
    at export.CsvValidator.check(CsvValidator.java:15)
    at export.CsvService.export(CsvService.java:36)
    ... 1 more
```

Questions and answers:

1. **Outermost exception?** `IllegalStateException`, message “Không xuất được CSV”.
2. **Declared cause?** `IllegalArgumentException` about missing column name, linked via `Caused by`.
3. **Secondary error?** `IOException` when closing the writer, attached via `Suppressed`.
4. **How many cause levels are printed?** One direct cause in the example; do not count suppressed as a cause.
5. **What does `... 1 more` mean?** Each child branch abbreviates one trailing frame that matches its enclosing stack.
6. **Which code should be inspected?** `CsvValidator.check`, the call flow in `CsvService.export`, and `CsvWriter.close`; also check CSV input and the writer-closing policy.
7. **Is there evidence the close error caused the missing column name?** No. The two branches represent two distinct errors in the execution flow.

## 15. Diagnostics and Logging Checklist

Before closing a Java incident, verify:

- Have you read the **exception type + message** of the outer exception and every important `Caused by`?
- Have you located the **application frame** and matched it against source code from the exact build?
- Have you checked `Suppressed` and determined whether cleanup errors have their own consequences?
- Have you interpreted `... N more` as **abbreviated common frames**?
- Does the log include the full `Throwable`, timestamp, thread, request/trace ID, and necessary context?
- Can you distinguish worker exceptions from caller-side `ExecutionException`/`CompletionException` wrappers?
- Was a cause accidentally dropped during exception translation, or was the same error logged redundantly at multiple layers?
- Is there any sensitive data in the message, stack trace, or log context that needs to be masked?
- Have you checked the real-world impact (transactions, files, resources, retries) beyond the error message?

**Remember:** `Caused by` links **the cause**, `Suppressed` preserves **secondary errors**, and `... N more` abbreviates **matching trailing stack frames**. Only by reading all three components in the right `Throwable` branch and cross-referencing source code, build version, and event context can you reach a reliable diagnostic conclusion.
