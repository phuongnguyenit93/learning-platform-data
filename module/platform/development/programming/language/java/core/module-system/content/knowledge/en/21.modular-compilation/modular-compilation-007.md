# Annotation Processors in Modular Compilation

## 1. Annotation Processing in the Module Compilation Workflow

An annotation processor is a program that runs during Java compilation to read annotations, analyze source code structure, and optionally generate additional source files or resources. Common examples are processors that generate mappers, builders, metadata, registries, or code supporting dependency injection.

When migrating a project to the Java Platform Module System (JPMS), processors still use the standard APIs in \`javax.annotation.processing\` and \`javax.lang.model\`. The important change is how the compiler locates and loads processors:

- A processor on the compiler's classpath is typically located via \`--processor-path\` and the service file \`META-INF/services/javax.annotation.processing.Processor\`.
- A processor that is a named module can be located via \`--processor-module-path\`; the module descriptor registers the service with \`provides javax.annotation.processing.Processor with ...\`.
- The application modules being compiled are still located via \`--module-path\` or the module source path. The processor path and the module path serve two different purposes.

A processor is usually only a build dependency. The application that uses the annotation and generated sources may not need the processor module when running in production.

## 2. Separating the Annotation API, Processor, and Application into Modules

This example uses three modules:

| Module | Responsibility |
| --- | --- |
| \`com.acme.annotations\` | Declares the annotation used in the application's source code. |
| \`com.acme.processor\` | Reads the annotation and generates Java sources during compilation. |
| \`com.acme.app\` | Uses the annotation and calls the class generated by the processor. |

Directory structure:

~~~text
src/
  com.acme.annotations/
    module-info.java
    com/acme/annotations/GenerateGreeting.java
  com.acme.processor/
    module-info.java
    com/acme/processor/GreetingProcessor.java
  com.acme.app/
    module-info.java
    com/acme/app/Main.java
~~~

The module directory names match the module names in \`module-info.java\`. When using \`--module-source-path\`, javac can locate multiple modules using this structure.

### 2.1. Annotation Module

File \`src/com.acme.annotations/module-info.java\`:

~~~java
module com.acme.annotations {
    exports com.acme.annotations;
}
~~~

The annotation is exported so the processor module and the application module can reference it:

~~~java
package com.acme.annotations;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateGreeting {
}
~~~

\`RetentionPolicy.SOURCE\` means the annotation only needs to exist in source at compile time. It does not need to appear in the application's bytecode. Therefore, the application module can declare the annotation dependency with \`requires static\` if the annotation is only for compilation.

### 2.2. Annotation Processor Module

File \`src/com.acme.processor/module-info.java\`:

~~~java
module com.acme.processor {
    requires java.compiler;
    requires com.acme.annotations;

    provides javax.annotation.processing.Processor
            with com.acme.processor.GreetingProcessor;
}
~~~

\`java.compiler\` contains APIs such as \`Processor\`, \`AbstractProcessor\`, \`RoundEnvironment\`, \`Filer\`, \`Element\`, and \`TypeElement\`. The processor needs \`requires java.compiler\` to use those APIs.

The \`provides\` directive registers the implementation with the \`javax.annotation.processing.Processor\` service. When javac searches for processors on the processor module path, it can discover this class through JPMS service binding.

The package containing the processor does not need \`exports\` just for javac to load the provider declared with \`provides\`. Export the package separately only if another module needs to call the processor's public API directly.

### 2.3. Application Module

File \`src/com.acme.app/module-info.java\`:

~~~java
module com.acme.app {
    requires static com.acme.annotations;
}
~~~

The application only needs the annotation during the compilation phase. \`requires static\` requires the annotation module to be present at compile time while allowing that module to be absent at runtime. The application module does not need to declare \`requires com.acme.processor\`, because the processor is executed by the compiler rather than by the application.

Source using the annotation:

~~~java
package com.acme.app;

import com.acme.annotations.GenerateGreeting;

@GenerateGreeting
public class Main {
    public static void main(String[] args) {
        System.out.println(MainGenerated.message());
    }
}
~~~

\`MainGenerated\` is the class that will be created during annotation processing. The compiler will process the generated source in subsequent rounds and compile it together with the application module.

## 3. Writing a Processor Using the Standard API

The processor extends \`AbstractProcessor\`, declaring the annotations to process and the Java source version it supports.

~~~java
package com.acme.processor;

import com.acme.annotations.GenerateGreeting;

import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.FilerException;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.Element;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;
import java.io.IOException;
import java.io.Writer;
import java.util.HashSet;
import java.util.Set;

@SupportedAnnotationTypes("com.acme.annotations.GenerateGreeting")
@SupportedSourceVersion(SourceVersion.RELEASE_21)
public final class GreetingProcessor extends AbstractProcessor {

    private final Set<String> generatedNames = new HashSet<>();

    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {

        if (roundEnv.processingOver()) {
            return false;
        }

        for (Element element :
                roundEnv.getElementsAnnotatedWith(GenerateGreeting.class)) {

            if (!(element instanceof TypeElement type)) {
                continue;
            }

            String packageName = processingEnv.getElementUtils()
                    .getPackageOf(type)
                    .getQualifiedName()
                    .toString();

            String simpleName = type.getSimpleName() + "Generated";
            String qualifiedName = packageName.isEmpty()
                    ? simpleName
                    : packageName + "." + simpleName;

            if (!generatedNames.add(qualifiedName)) {
                continue;
            }

            try (Writer writer = processingEnv.getFiler()
                    .createSourceFile(qualifiedName, type)
                    .openWriter()) {

                if (!packageName.isEmpty()) {
                    writer.write("package " + packageName + ";\\n\\n");
                }

                writer.write("public final class " + simpleName + " {\\n");
                writer.write("    private " + simpleName + "() {}\\n");
                writer.write("    public static String message() {\\n");
                writer.write("        return \\"Generated during compilation\\";\\n");
                writer.write("    }\\n");
                writer.write("}\\n");

            } catch (FilerException exception) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "Generated source already exists: " + qualifiedName,
                        element);
            } catch (IOException exception) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "Cannot generate " + qualifiedName + ": "
                                + exception.getMessage(),
                        element);
            }
        }

        return true;
    }
}
~~~

Key points to understand in the example:

- \`@SupportedAnnotationTypes\` specifies the annotations the processor is interested in. Wildcards can be used, but declaring specific names lets the compiler know which annotation types the processor handles.
- \`@SupportedSourceVersion\` declares the supported source version. This example targets Java 21.
- \`RoundEnvironment\` represents a processing round. Generated sources can trigger subsequent processing rounds.
- \`Elements\` and \`Types\` in \`processingEnv\` allow analyzing the Java language model without loading application classes via reflection.
- \`Filer\` creates sources or resources in the compiler's output. Passing the originating element \`type\` to \`createSourceFile\` helps the compiler and build tools know which element generated the source.
- The processor reports diagnostics through \`Messager\`; use \`Diagnostic.Kind.ERROR\` to fail compilation when required sources cannot be generated.
- The \`generatedNames\` set prevents the processor from attempting to create the same source multiple times within a single compilation.

A processor does not need to open the application's packages with \`opens\` to read annotations and source structure. Prefer the model APIs \`Element\`, \`TypeMirror\`, \`Elements\`, and \`Types\`. Generated source code must still obey module access rules when the compiler compiles it.

## 4. Compiling the Processor and Application with javac

You should compile the annotation module first, then compile the processor, and finally compile the application module that uses the processor. This order clarifies dependencies among the modules.

The following commands illustrate execution on a Unix/macOS/Linux shell with JDK 21. On Windows, replace the module path separator \`:\` with \`;\`.

### 4.1. Compiling the Annotation Module

~~~bash
mkdir -p build/mods

javac --release 21 \\
  --module-source-path src \\
  -d build/mods \\
  -m com.acme.annotations
~~~

After this command, the compiled module resides in \`build/mods/com.acme.annotations\`.

### 4.2. Compiling the Processor Module

~~~bash
mkdir -p build/processor-mods

javac --release 21 \\
  --module-path build/mods \\
  --module-source-path src \\
  -d build/processor-mods \\
  -m com.acme.processor
~~~

In this step, javac locates the annotation module via \`--module-path\`. The processor output is an exploded module in \`build/processor-mods/com.acme.processor\`. That module directory can be packaged into a modular JAR if the build workflow requires it.

### 4.3. Compiling the Application Module and Running the Processor

~~~bash
mkdir -p build/app-mods build/generated

javac --release 21 \\
  --module-path build/mods \\
  --processor-module-path build/processor-mods:build/mods \\
  -proc:full \\
  --module-source-path src \\
  -d build/app-mods \\
  -s build/generated \\
  -m com.acme.app
~~~

Meaning of the options:

| Option | Role |
| --- | --- |
| \`--module-path\` | Locates the modules needed by the application source, here \`com.acme.annotations\`. |
| \`--processor-module-path\` | Locates named modules providing annotation processors. The example path also contains the annotation module that the processor depends on. |
| \`-proc:full\` | Instructs javac to perform both annotation processing and compilation. |
| \`--module-source-path\` | Specifies the root of the source tree containing the modules. |
| \`-d\` | Output directory for compiled classes. |
| \`-s\` | Output directory for sources generated by processors. |
| \`-m\` | Specifies the module to compile in the source tree. |

In the command above, \`build/processor-mods:build/mods\` uses \`:\` to join two module locations on Unix-like OSes. On Windows, use \`build/processor-mods;build/mods\`.

When compilation finishes, you can inspect the generated sources in \`build/generated\` and the compiled classes in \`build/app-mods\`. With a module source path, outputs are usually partitioned by module name, for example \`build/generated/com.acme.app\` and \`build/app-mods/com.acme.app\`.

\`-s\` specifies where generated sources are stored; \`-d\` specifies where bytecode is stored. If you only look at the \`-d\` output, you may miss evidence of which sources the processor created.

## 5. Distinguishing Processor Module Path and Processor Classpath

The two ways of registering a processor cannot be swapped arbitrarily.

### 5.1. Processor Is a Named Module

A modular processor JAR contains \`module-info.class\` with a declaration:

~~~java
module com.acme.processor {
    requires java.compiler;
    provides javax.annotation.processing.Processor
            with com.acme.processor.GreetingProcessor;
}
~~~

Place the modular JAR or exploded module on:

~~~bash
javac --processor-module-path processors \\
     --module-path app-dependencies \\
     ...
~~~

javac discovers the processor via the service declaration in the module descriptor. Modules that the processor depends on must also be resolvable from the appropriate module paths.

### 5.2. Processor Runs on the Compiler's Classpath

If the processor is used as a classpath library, it can be registered via the resource:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

File contents:

~~~text
com.acme.processor.GreetingProcessor
~~~

Then use:

~~~bash
javac \\
  --processor-path processors.jar \\
  --module-path app-dependencies \\
  -proc:full \\
  ...
~~~

In this mode, the processor is loaded using the classpath mechanism. If the JAR has \`module-info.class\` yet is placed on \`--processor-path\`, do not assume javac will use the descriptor's \`provides\` directive; provide the service resource or specify the processor explicitly.

You can select a specific processor with:

~~~bash
javac -processor com.acme.processor.GreetingProcessor ...
~~~

This is the fully qualified class name of the processor, not the module name. Explicit selection is useful when the processor path contains multiple processors and only certain processors should run in that compilation.

A modular processor JAR can package both \`module-info.class\` and \`META-INF/services\` if it needs to support both modes. However, verify the exact mode that your build tool actually passes to javac.

## 6. Annotation Processing Modes

javac provides three main modes:

- \`-proc:none\`: do not run annotation processors; the compiler only compiles sources. Use this when determining whether an error is related to a processor.
- \`-proc:only\`: run annotation processing without performing regular compilation afterward. Suitable for pipelines that only want to generate sources/resources.
- \`-proc:full\`: run annotation processing and compilation in the same invocation.

In modular builds, explicitly configure the processor path and processing mode rather than relying on javac scanning a broad classpath automatically. Automatic processor discovery behavior has changed across JDK versions; explicit configuration makes builds more reproducible when upgrading the JDK or build tool.

If compilation suddenly stops generating sources after a JDK upgrade, check the actual compiler arguments: \`--processor-path\`, \`--processor-module-path\`, \`-processor\`, and \`-proc\`. Do not jump to the conclusion that the module descriptor is broken when the processor simply has not been enabled.

## 7. Annotation Processors and Module Boundaries

Annotation processing takes place inside the compiler's JVM. It does not make the processor a runtime dependency of the application.

Several important boundaries:

1. **Annotation module:** the application source must read the module containing the annotation. If the annotation only has `SOURCE` retention and is not used at runtime, \`requires static\` is usually appropriate.
2. **Processor module:** the processor must read \`java.compiler\` and any annotation modules it references. Consumers do not need to declare \`requires\` on the processor module.
3. **Generated source:** generated sources belong to the module being compiled according to the context and originating element provided by the processor. Generated code must obey \`exports\`, \`requires\`, and normal access rules.
4. **Reflection:** processors should use the compile-time model API. JPMS does not automatically open the application's internal packages for processor reflection.
5. **Runtime image:** if a processor only runs at build time, do not include the processor module in the runtime image merely because the application used it during compilation. Only the annotation module or related libraries need to be present at runtime if the application's bytecode and descriptor actually depend on them.

In particular, \`Filer.createSourceFile\` should receive an originating element:

~~~java
processingEnv.getFiler().createSourceFile(
        "com.acme.app.MainGenerated",
        originatingType
);
~~~

This helps the compiler associate the generated file with the appropriate source element. In multi-module compilation, do not generate sources by guessing a matching package name and ignoring which module owns it.

## 8. Using Annotation Processors in Gradle or Maven

Build tools can configure the processor path separately. What needs to be verified in a modular project is that the compiler ultimately receives the right type of path:

- A classpath processor must be passed via \`--processor-path\` or \`-processorpath\`.
- A modular processor must be passed via \`--processor-module-path\`.
- Modules needed by the application source must still be on the module path.
- The processor module and its dependencies must be resolvable when the compiler starts.

The Gradle Java plugin typically uses the \`annotationProcessor\` configuration for a classpath-style processor path. Do not assume that merely adding a modular JAR to that configuration will make javac automatically use \`--processor-module-path\`. If the project requires a processor module path, configure the corresponding compiler arguments and inspect the actual command line via build logs.

Similarly, with the Maven Compiler Plugin, verify the annotation processor configuration and the compiler arguments generated by the plugin. The configuration name in a build tool does not by itself determine whether a processor is loaded as a named module or a classpath library.

Keep processors in the compile-time dependency configuration. Avoid putting them into the application's runtime dependencies unless separate runtime functionality needs that library itself.

## 9. Common Errors in Modular Compilation

| Symptom | Possible Cause | Where to Check |
| --- | --- | --- |
| Processor is not invoked | Wrong path or processing not enabled | Check the command line; verify \`--processor-module-path\`, \`--processor-path\`, \`-processor\`, \`-proc\`. |
| Processor provider not found | Module descriptor missing \`provides\` or classpath missing service file | Check \`jar --describe-module\` or \`jar --list\` and the contents of \`META-INF/services\`. |
| \`java.compiler\` cannot be read | Processor module missing \`requires java.compiler\` | Add the module dependency in the processor's descriptor. |
| Cannot resolve annotation module | Annotation module missing from the module path used for compilation or processor resolution | Check \`--module-path\`, \`--processor-module-path\`, and the dependency graph. |
| Annotation not recognized | Wrong annotation name in \`@SupportedAnnotationTypes\`, package not exported, or app does not read annotation module | Check the fully qualified name, \`exports\`, and the app's \`requires\`. |
| Source is generated but app cannot see the class | Generated source is not in compilation output or not assigned to the right module | Check \`-s\`, \`-d\`, and originating elements passed to `Filer`. |
| \`FilerException\` reports file already exists | Processor created the same qualified name multiple times or file was already created from another source | Track generated names and avoid duplicate creation across processing rounds. |
| Compiles fine but runtime lacks annotation module | App descriptor uses mandatory \`requires\` while the annotation is only needed at compile time | Consider \`requires static\` if the annotation has `SOURCE` retention and is not needed at runtime. |
| Works on one JDK but warns or fails on another | Processor discovery behavior or source version changed | Configure the processor path explicitly, set \`-proc\`, and set an appropriate source version. |

## 10. Diagnostic Workflow

When an annotation processor does not work in modular compilation, check in order:

1. Confirm the source module has the annotation and its module descriptor declares the right dependencies.
2. Confirm the processor module compiles, reads \`java.compiler\`, and has \`provides javax.annotation.processing.Processor\`.
3. Inspect the actual javac command to see whether the processor is placed on \`--processor-module-path\` or \`--processor-path\`.
4. Confirm the processor module and its dependencies can be resolved from the configured path.
5. Explicitly enable annotation processing with \`-proc:full\` or select the processor with \`-processor\`.
6. Check generated sources in the \`-s\` directory, compiled classes in \`-d\`, and errors reported via \`Messager\`.
7. If generated sources are not visible to the application, check the originating element and which module owns the generated source.
8. Finally, confirm the runtime application does not accidentally depend on a processor module that is only used at build time.

Separating the annotation, processor, and application modules keeps dependencies clear. When configured properly, javac can load the processor as a named module, process annotations in source modules, and compile the generated sources within the same modular compilation.
