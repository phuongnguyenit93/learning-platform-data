# Verifying That a Runtime Image Contains the Right Modules

> Scope: Java Platform Module System (JPMS) and the **jlink** tool. This lesson guides you through checking whether a generated runtime image contains the exact required modules, verifying descriptors, and test-running an application directly with the Java runtime inside that image.

## Objectives

After this lesson, you can:

- Identify the exact runtime image to inspect and run the exact executable inside the image.
- List the modules actually present in the image using **java --list-modules**.
- Inspect a module's descriptor using **java --describe-module**.
- Inspect JIMAGE structure using the **jimage** tool.
- Cross-check required modules against linked modules using **jdeps** and **jlink**.
- Detect errors caused by missing modules, dependencies, service providers, or the wrong runtime.
- Test-run the application on the exact runtime image that will be distributed.

## 1. What Is a Runtime Image?

A **runtime image** is a Java runtime packaged into a standalone runnable directory tree. With JPMS, the **jlink** tool creates an image from selected modules along with their dependencies.

An image generated by `jlink` typically has a structure like:

~~~text
runtime-image/
├── bin/
│   └── java
├── conf/
├── include/
├── legal/
├── lib/
│   ├── modules
│   └── ...
└── release
~~~

On Windows, the executable is typically **bin/java.exe**. A runtime image may be stripped down, so it does not necessarily include every directory or tool of a full JDK.

The **lib/modules** file is the module image store in JIMAGE format. Modules linked into the image live inside it. The **bin** directory contains the launcher used to start applications with the generated runtime.

What needs to be verified is: **whether the target runtime image contains the exact modules the application needs, and whether that runtime itself can launch the application**. Checking the JDK used for building is not enough, because the build JDK may contain more modules than the linked image.

## 2. Identify the Exact Runtime Image Before Inspecting

Suppose the image was created at:

~~~text
project/
├── mods/
│   └── com.acme.app.jar
└── runtime-image/
    ├── bin/
    └── lib/
        └── modules
~~~

Invoke the executable using a direct path to the image:

Linux/macOS:

~~~bash
./runtime-image/bin/java --version
~~~

Windows PowerShell:

~~~powershell
.\runtime-image\bin\java.exe --version
~~~

This command confirms the Java version of the image being inspected. Do not just run **java --version** from the machine's PATH, because that command might invoke a different JDK/JRE.

You can view the Java home path that the JVM actually uses:

~~~bash
./runtime-image/bin/java -XshowSettings:properties -version
~~~

In the system properties section, look for **java.home**. Its value should point to the runtime image you intend to inspect.

Also check the **release** file at the image root for version and platform information such as **JAVA_VERSION**, **OS_NAME**, and **OS_ARCH** if present. This helps identify the artifact; running the launcher from the image remains the direct way to check which modules the runtime sees.

## 3. Listing Modules Present in the Runtime Image

The fastest way is to run:

~~~bash
./runtime-image/bin/java --list-modules
~~~

On Windows:

~~~powershell
.\runtime-image\bin\java.exe --list-modules
~~~

The launcher will list the modules observable from the running runtime and then exit. Each line typically has the format:

~~~text
java.base@21.0.2
java.logging@21.0.2
com.acme.app
~~~

The part before the **@** symbol is the module name; the part after is the version if the module has version information.

For example, if the application requires:

- **java.base**;
- **java.logging**;
- **com.acme.app**;

then the output must contain all of these module names. **java.base** is always present in a Java runtime; the remaining modules depend on the application and the link configuration.

When inspecting an image, run the exact **runtime-image/bin/java** and do not add an external module path to the command. If you pass **--module-path**, the output may reflect modules observable from the additional path, causing you to mistake external modules for modules linked into the image.

### Quickly Filtering the Module List

Linux/macOS:

~~~bash
./runtime-image/bin/java --list-modules | grep -E '^(java.base|java.logging|com\.acme\.app)@?'
~~~

Windows PowerShell:

~~~powershell
.\runtime-image\bin\java.exe --list-modules | Select-String '^(java.base|java.logging|com\.acme\.app)@?'
~~~

Filtering commands only help with quick observation. When confirming the complete module set, save and compare the full **--list-modules** output against the expected module list.

## 4. Inspecting the Descriptor of a Specific Module

After confirming the module name appears in the list, use **--describe-module**:

~~~bash
./runtime-image/bin/java --describe-module java.logging
~~~

Inspect the application module:

~~~bash
./runtime-image/bin/java --describe-module com.acme.app
~~~

The output displays the module name and directives in the descriptor, such as **requires**, **exports**, **opens**, **uses**, or **provides** if present.

This helps verify:

- Whether the actual module name matches the name the application requires.
- Whether the module has the expected descriptor and dependencies.
- Which packages are exported.
- Which services are used or which providers are declared.

If the module is not in the image, the launcher will report module not found when describing it. Do not infer that a package existing in a JAR on disk means that module is already in the runtime image.

## 5. Verifying the Module Image with jimage

**jimage** is a JDK tool for inspecting the contents of a JIMAGE module store. The file to inspect is typically located at:

~~~text
runtime-image/lib/modules
~~~

List contents:

~~~bash
jimage list runtime-image/lib/modules
~~~

On Windows:

~~~powershell
jimage.exe list .\runtime-image\lib\modules
~~~

The output displays the modules and entries inside the image, such as class paths belonging to **java.base** or **java.logging**. You can search for expected module names or packages to assist investigation when the launcher list and image structure show signs of mismatch.

Verify the integrity of the image store:

~~~bash
jimage verify runtime-image/lib/modules
~~~

**jimage verify** checks the structure and integrity of the JIMAGE file. It does not substitute for confirming the module graph, application dependencies, or test-running the application.

Note: **jimage** is a JDK tool and may not be included in a minimal runtime image. Use the tool from a compatible JDK to inspect the target image's **lib/modules** file. When running **jimage list**, pass the exact **runtime-image/lib/modules** file, not the image root directory.

## 6. Cross-Checking Required Modules Before Creating the Image

Before linking, you need to know which modules the application actually needs.

For example, a modular application has the descriptor:

~~~java
module com.acme.app {
    requires java.logging;
}
~~~

The application has main module **com.acme.app** and depends on **java.logging**. When resolved, **java.base** is also always present.

You can use **jdeps** to statically analyze the JAR's dependencies:

~~~bash
jdeps --print-module-deps --module-path mods mods/com.acme.app.jar
~~~

Depending on project structure, add dependent JARs/modules to **--module-path** so `jdeps` can perform a complete analysis. The **--print-module-deps** output is a list of module dependencies suitable to help determine inputs for `jlink`.

Sample output might be:

~~~text
java.base,java.logging
~~~

This is the dependency analysis that `jdeps` detects from bytecode and observable modules. Reflection, dynamically constructed class names, external configuration, plugins, or dependencies loaded only at runtime may not be fully detected by static analysis. Therefore, combine `jdeps` results with module descriptors, runtime configuration, and real testing.

## 7. Creating a Runtime Image with jlink

**jlink** links explicit modules and their dependencies into a runtime image. This tool requires a compatible JDK and suitable input modules; automatic modules cannot be linked directly. If a library is still an automatic module, convert it into an explicit module before using it as input to `jlink`.

For example, the application module is packaged at **mods/com.acme.app.jar**, while JDK modules reside in **$JAVA_HOME/jmods**.

Linux/macOS:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --output runtime-image
~~~

Windows PowerShell:

~~~powershell
jlink --module-path "$env:JAVA_HOME\jmods;mods" --add-modules com.acme.app --output runtime-image
~~~

Explanation:

- **--module-path** provides the JDK modules in the **jmods** directory and application modules in **mods**.
- **--add-modules com.acme.app** selects the root module to link.
- `jlink` resolves dependencies declared in the module graph and includes them in the image.
- **--output runtime-image** specifies the output directory.

If the application requires service providers, you can use the **--bind-services** option to link provider modules for used services along with their dependencies:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --bind-services --output runtime-image
~~~

Only add **--bind-services** when you want to link providers via service binding. If the application loads plugins or providers from locations outside the image itself, design and test the corresponding module path/layer at runtime.

You can add size optimization options such as **--strip-debug**, **--no-header-files**, **--no-man-pages**, or **--compress=2**. These options affect packaged contents; after changing link settings, re-verify the new image.

## 8. Verifying the Image After Linking

After `jlink` finishes, check in order:

1. Confirm the image has an executable at **bin/java** (or **bin/java.exe**).
2. Run **runtime-image/bin/java --version** to confirm the right runtime.
3. Run **runtime-image/bin/java --list-modules** to list modules in the image.
4. Cross-check that all expected modules are present, including application modules and dependencies.
5. Run **runtime-image/bin/java --describe-module <module-name>** for important modules.
6. Use **jimage list** or **jimage verify** when you need to inspect the contents and integrity of **lib/modules**.
7. Test-run the application using the exact executable in the image.

Example verification:

~~~bash
./runtime-image/bin/java --list-modules
./runtime-image/bin/java --describe-module com.acme.app
./runtime-image/bin/java --validate-modules
~~~

**--validate-modules** asks the launcher to validate observable modules in the current configuration and then exit. Run it using the image's Java without adding an external module path if the goal is to validate the image standalone.

Some builds may display modules with versions, while others may not. When cross-checking, compare module names first; only compare versions when deployment requirements have specific version constraints.

## 9. Test-Running the Application from the Runtime Image Itself

A correct module list still does not prove the application can run. Launch the main module using Java inside the image:

~~~bash
./runtime-image/bin/java --module com.acme.app/com.acme.app.Main
~~~

On Windows:

~~~powershell
.\runtime-image\bin\java.exe --module com.acme.app/com.acme.app.Main
~~~

If the application accepts arguments:

~~~bash
./runtime-image/bin/java --module com.acme.app/com.acme.app.Main --config config/app.properties
~~~

Arguments after **module/main-class** are passed into **String[] args** of the `main` method.

You can create a custom launcher when linking the image:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --launcher app=com.acme.app/com.acme.app.Main --output runtime-image
~~~

Then run the generated launcher:

~~~bash
./runtime-image/bin/app
~~~

On Windows, use **runtime-image\bin\app.bat** if the launcher was generated as a batch script. Check the actual filename in the image's **bin** directory.

Testing on the final image helps uncover issues that the module list does not show, such as missing config files, unpackaged resources, wrong-platform native libraries, working directories, or dynamically loaded dependencies.

## 10. Common Errors and Troubleshooting

| Symptom | Common Cause | Resolution |
|---|---|---|
| Required module does not appear in **--list-modules** | Module was not selected as a root, was not on the module path during linking, or was not resolved into the image | Check **--add-modules**, module path, and **requires** descriptors; recreate the image |
| **--describe-module** reports module not found | Calling the wrong Java runtime or the module is not in the image | Use the full path to **runtime-image/bin/java** and check **--list-modules** |
| Works on build JDK but fails on runtime image | Build JDK has more modules than the minimal image | Run the application using the image's executable; add required modules when linking |
| **jlink** reports automatic modules are not supported | An input lacks an explicit module descriptor | Add **module-info.java** and package as an explicit modular JAR |
| Application uses ServiceLoader but provider is missing | Provider was not resolved/bound into the image or is not in the layer the application searches | Check **uses/provides**, module path, and consider **--bind-services** |
| Module is present but application still fails to run | Missing resources, configuration, native libraries, or dynamically loaded dependencies | Test-run the application on the image and check the specific runtime error |
| Image runs on build machine but fails on target machine | Image is incompatible with the target machine's OS, CPU architecture, or native environment | Create an image matching the target platform and test on a corresponding environment |
| **jimage verify** fails | **lib/modules** file is corrupted or not a valid image | Recreate the image from trusted inputs and check the packaging process |

### Note on Missing Modules

If the application module declares **requires java.sql** but **java.sql** is not in the image, inspect the module graph before recreating it. For an explicit module, required dependencies must resolve successfully in order to link. Do not add modules in bulk by guessing; identify direct dependencies as well as dependencies required by services, reflection, or runtime configuration.

### Note on Service Providers

If the application uses **ServiceLoader**, the application module must declare **uses** and the provider module must declare **provides**. Depending on how the image is built, **--bind-services** helps `jlink` find and link providers for used services. After linking, check that the provider module appears in **--list-modules**, describe it with **--describe-module**, and then test-run the flow that uses the service.

## 11. Runtime Image Verification Checklist

- [ ] Identified the exact runtime image directory to distribute.
- [ ] Invoked **bin/java** directly inside the image.
- [ ] Java version and platform match the deployment target.
- [ ] **--list-modules** includes all expected application modules and dependencies.
- [ ] Key modules have appropriate descriptors when inspected with **--describe-module**.
- [ ] **--validate-modules** completes successfully.
- [ ] If investigating JIMAGE contents is needed, checked **lib/modules** with **jimage**.
- [ ] If the application uses services, confirmed providers are linked and discoverable.
- [ ] Application launches successfully using the runtime image itself.
- [ ] Tested the image on the target platform or an equivalent environment.

This checklist is an operational procedure to verify artifacts. A correct **--list-modules** output does not replace application testing, and a successful application test on the build machine does not prove the image is compatible with every platform.

## 12. Takeaways

- A runtime image created by **jlink** contains the linked modules along with their resolved dependencies.
- Use **runtime-image/bin/java --list-modules** to see which modules the image provides.
- Use **--describe-module** to view the descriptor of a specific module.
- Use **jimage list** and **jimage verify** to inspect the contents and integrity of the **lib/modules** store.
- Use **jdeps --print-module-deps** to assist dependency analysis before linking, while still testing dynamic dependencies.
- **jlink** requires explicit input modules; automatic modules cannot be linked directly.
- **--bind-services** is useful when service providers need to be included in the runtime image.
- The final test is running the application using the exact Java executable inside the image to be released.
