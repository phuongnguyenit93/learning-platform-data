# Return Types, Unboxing, and Limits of `null` in Java Dynamic Proxies

In Java Dynamic Proxies, an interface method can declare a specific return type such as `int`, `String`, `Integer`, or `void`, yet `InvocationHandler.invoke(...)` always has return type **`Object`**. When a method on the proxy is called, the JDK-generated proxy class is responsible for converting that `Object` value to the type declared by the interface. **A wrong type causes `ClassCastException`; returning `null` for a primitive causes `NullPointerException`.** For reference types, `null` is generally valid; for `void`, the return value from the handler is ignored.

This article focuses on **the return type contract at the boundary between `InvocationHandler` and the proxy method**, not to be confused with calling `Method.invoke` on an arbitrary target object.

## 1. How does a value pass through a proxy?

Suppose an interface declares:

~~~java
interface Counter {
    int getCount();
}
~~~

The `Counter.getCount()` method requires the caller to receive an `int`, whereas the handler has the signature:

~~~java
Object invoke(Object proxy, Method method, Object[] args) throws Throwable;
~~~

These are **two different type levels**:

~~~text
Caller: Counter.getCount() -> int
                |
                v
Method in the JDK-generated proxy class
                |
                v
InvocationHandler.invoke(...) -> Object
                |
                v
Proxy checks/casts wrapper then unboxes to int
                |
                v
Returns int to caller, or throws on conversion failure
~~~

In terms of **semantics**, the conversion for `int` resembles:

~~~java
Object result = handler.invoke(proxy, method, args);
return ((Integer) result).intValue();
~~~

This is only **illustrative pseudocode**: you cannot drop these two lines directly into an ordinary method without defining the variables and handling exceptions. The actual bytecode of the proxy class is generated by the JDK and may differ from the illustration above.

- Handler returns `Integer.valueOf(7)`: casting to `Integer` succeeds, and `intValue()` produces `7`.
- Handler returns `null`: casting the reference to `Integer` still yields `null`, and calling `intValue()` on `null` causes `NullPointerException`.
- Handler returns `Long.valueOf(7)`: casting from `Long` to `Integer` is invalid, causing `ClassCastException`.
- Handler returns an `int` value via `return 7;`: the compiler **autoboxes** it to `Integer` before the handler returns `Object`.

**When the error occurs:** In the scenarios above, the handler itself may already have finished normally. The NPE/CCE arises when the proxy's code converts the result to the interface's required type; a `try/catch` block wrapping only logic inside the handler will not automatically catch an error occurring after the handler `return`s.

## 2. Return type contract to remember

| Interface return type | Value returned by handler | Result of the call on the proxy |
|---|---|---|
| `int` | `Integer.valueOf(7)` or `return 7;` | `7`, unboxed to `int` |
| `int` | `null` | `NullPointerException` |
| `int` | `Long.valueOf(7)` | `ClassCastException` |
| `long` | `Long.valueOf(7)` or `return 7L;` | `7L`, unboxed to `long` |
| `long` | `Integer.valueOf(7)` | `ClassCastException`, does **not** widen `int` to `long` |
| `boolean` | `Boolean.TRUE` | `true` |
| `boolean` | `null` or a wrapper other than `Boolean` | NPE if `null`; CCE if wrong wrapper |
| `Integer` | `null` or an `Integer` | Valid because `Integer` is a reference type |
| `String` | `null` or a `String` | Valid |
| `String` | `Integer.valueOf(7)` | `ClassCastException` |
| `Object` | Any object or `null` | Valid |
| `void` | `null`, `Integer.valueOf(1)`, or another object | Value is ignored; caller receives no result |

**For every primitive type, the wrapper must match exact type:**

| Primitive | Wrapper to return from handler |
|---|---|
| `boolean` | `Boolean` |
| `byte` | `Byte` |
| `short` | `Short` |
| `char` | `Character` |
| `int` | `Integer` |
| `long` | `Long` |
| `float` | `Float` |
| `double` | `Double` |

An easy point of confusion: in ordinary Java, `long value = 7;` is allowed due to primitive conversion from `int` to `long`. However, if **the proxy method declares `long`** and the handler returns `Integer`, the proxy expects `Long` to unbox. It does not accept `Integer` and automatically infer a widening conversion. Likewise, `Float` cannot substitute for `Double`.

For a reference type `T`, a non-`null` value must be an instance assignable to `T` (including a compatible subtype/implementing class). For instance, a method returning `CharSequence` can accept `String`, whereas a method returning `String` cannot accept `StringBuilder`.

## 3. Running a Java 17+ example covering all cases

Save the following complete program as **`ProxyReturnDemo.java`**. The program creates real proxies via `Proxy.newProxyInstance`, then tests both valid results and controlled errors. `check(...)` prints only the **exception class name** so stdout stays stable and independent of per-JDK error messages.

~~~java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;

public class ProxyReturnDemo {
    interface Probe {
        int primitive();
        long wider();
        Integer boxed();
        String text();
        void tick();
    }

    static Probe create(InvocationHandler handler) {
        return (Probe) Proxy.newProxyInstance(
                Probe.class.getClassLoader(),
                new Class<?>[]{Probe.class}, handler);
    }

    static void check(String label, Runnable action) {
        try {
            action.run();
            System.out.println(label + " -> OK");
        } catch (RuntimeException e) {
            System.out.println(label + " -> " + e.getClass().getSimpleName());
        }
    }

    public static void main(String[] args) {
        Probe normal = create((proxy, method, values) ->
                switch (method.getName()) {
                    case "primitive" -> 7;
                    case "wider" -> 9L;
                    case "boxed", "text" -> null;
                    case "tick" -> 123;
                    default -> throw new UnsupportedOperationException(method.getName());
                });

        System.out.println("int = " + normal.primitive());
        System.out.println("long = " + normal.wider());
        System.out.println("Integer null = " + (normal.boxed() == null));
        System.out.println("String null = " + (normal.text() == null));
        normal.tick();
        System.out.println("void = OK");

        Probe nullResult = create((proxy, method, values) -> null);
        check("int <- null", () -> nullResult.primitive());

        Probe longForInt = create((proxy, method, values) -> 7L);
        check("int <- Long", () -> longForInt.primitive());

        Probe intForLong = create((proxy, method, values) -> 7);
        check("long <- Integer", () -> intForLong.wider());

        Probe intForString = create((proxy, method, values) -> 7);
        check("String <- Integer", () -> intForString.text());
    }
}
~~~

Compile and run in the directory containing the file:

~~~bash
javac --release 17 -encoding UTF-8 ProxyReturnDemo.java
java ProxyReturnDemo
~~~

Standard output (stdout):

~~~text
int = 7
long = 9
Integer null = true
String null = true
void = OK
int <- null -> NullPointerException
int <- Long -> ClassCastException
long <- Integer -> ClassCastException
String <- Integer -> ClassCastException
~~~

Explanation of key points:

1. `case "primitive" -> 7` returns `Integer` via autoboxing; `Probe.primitive()` receives `int` after unboxing.
2. `case "wider" -> 9L` returns `Long`, the exact wrapper for `long`.
3. `boxed()` and `text()` both return `null` successfully because the interface declares reference types.
4. `tick()` is declared `void`. The handler deliberately returns `123`, yet the proxy **discards this value**, so calling `normal.tick()` still succeeds.
5. `nullResult.primitive()` raises an NPE even though the handler call returned `null` normally.
6. `longForInt.primitive()` and `intForLong.wider()` both throw CCE: the wrappers do not match exactly; automatic numeric promotion like in static Java code is not performed at this boundary.
7. `intForString.text()` throws CCE because an `Integer` value is not assignable to the `String` return type.

The `Probe` example declares no parameters; for these calls, `values` received by the handler is `null`. If a method has a primitive parameter, the corresponding element in `args` received by the handler is its wrapper—for example, an `int` argument is boxed into `Integer`. **Boxing input arguments** and **unboxing output values** are two distinct processes.

## 4. `null` can appear in different places

`null` is a value of reference types; a primitive variable itself cannot hold `null`. Distinguish at least three scenarios:

**Scenario A — interface returns a primitive**

~~~java
int count = proxy.primitive();
~~~

Code at the call site is valid at compile time because `Probe.primitive()` is declared `int`. If the handler returns `null`, the proxy throws NPE **during call dispatch**; the caller never receives an `int`.

**Scenario B — interface returns a wrapper**

~~~java
Integer maybeCount = proxy.boxed();  // may be null
~~~

This is a valid call. However, if the caller continues with:

~~~java
int count = proxy.boxed();          // auto-unboxing null -> NPE
~~~

The NPE this time comes from **caller code unboxing a `null` `Integer`**, not from the proxy violating the `boxed()` contract. The two origins can show up differently in stack traces.

**Scenario C — interface returns `void`**

~~~java
proxy.tick();
~~~

Outside the call there is no result to store; the handler must still complete `Object invoke(...)` by returning an `Object` value such as `null`. **Standard practice** is to return `null` for `void` methods to make intent clear rather than returning a value that gets discarded.

A method returning `Void` (capital `V`, a reference wrapper class) is **not the same** as a method returning primitive `void`: `Void` can accept `null` like other reference types. Do not equate `Void.class` with `void.class`.

## 5. Designing contracts when data may be missing

When a value may be absent, choose the return type according to business needs before writing the handler:

- **Always a valid count:** the interface returns `int`; the handler guarantees returning a non-`null` `Integer`. If missing data is an error, throw a meaningful exception instead of returning `null`.
- **Count allowed to be absent:** the interface returns `Integer` and clearly documents the meaning of `null`; callers check before unboxing.
- **Want to represent absence explicitly:** consider `OptionalInt` for an optional integer or `Optional<T>` for a reference type; the handler must return an actual compatible `OptionalInt`/`Optional` instance, such as `OptionalInt.empty()`, instead of an ambiguous `null`.
- **Operation only performs a side effect:** the interface returns `void` and the handler returns `null` after finishing; do not use an ignored value to signal an outcome.
- **Need to report success/failure:** consider `boolean` with `Boolean.TRUE`/`Boolean.FALSE`, or a structured result type if error details are needed, instead of using `null` for `boolean`.

`0`, `false`, or an empty string are **not** default values automatically generated by Dynamic Proxy when a handler returns `null`. If business logic allows a fallback value, **the handler must explicitly decide** that value.

## 6. Detecting errors early in `InvocationHandler`

In a system with many methods, returning `null` as a default for every unhandled method is dangerous: it can cause NPE on primitive-returning methods, drop data on reference-returning methods, and break `Object` methods.

One design approach relies on `method.getReturnType()`:

~~~java
Class<?> returnType = method.getReturnType();

if (returnType == void.class) {
    // Perform side effect then return null.
} else if (returnType == int.class) {
    // Return non-null Integer, or throw a clear business error.
} else if (returnType == Integer.class) {
    // May return Integer or null if the contract allows.
}
~~~

This is an **illustrative snippet inside a handler**, not a complete Java program. For large interfaces, define explicit return contracts and method dispatch rather than inferring behavior solely from return types.

If you want to fail fast, the handler can check the result **before returning**:

~~~java
static Object requireIntResult(Method method, Object result) {
    if (method.getReturnType() != int.class) {
        throw new IllegalArgumentException("Method must return int");
    }
    if (!(result instanceof Integer)) {
        throw new IllegalStateException("Expected non-null Integer result");
    }
    return result;
}
~~~

This is an **illustrative helper method** that must be placed inside a class with `import java.lang.reflect.Method;` before use. A handler for an `int`-returning method can call `return requireIntResult(method, calculated);`. This turns a hard-to-trace unboxing error into an exception with a clear message right where the result is produced; it does not alter the proxy's conversion rules. For other primitives, check the corresponding wrapper; for reference types, use `returnType.isInstance(result)` for non-`null` values.

In particular, when returning `String`, `List`, or another class type, **the runtime checks only type assignability**. With `List<String>`, generics are erased at runtime; the proxy does not automatically verify whether every element is a `String`. Fetching an element of the wrong type and casting it to `String` later can still cause a CCE at the point of use.

## 7. Common pitfalls

| Mistake | Why it is wrong | How to handle it |
|---|---|---|
| `return null;` for every unknown method | `int`, `boolean`, `long`, etc. will NPE; `Object.hashCode()` also returns `int` | Handle each method, or throw `UnsupportedOperationException` when unimplemented |
| Returning `7` for a method returning `long` | `7` autoboxes to `Integer`, while the proxy needs `Long` | Return `7L` or `Long.valueOf(7)` |
| Using `return null` and expecting `0`/`false` | Dynamic Proxy does not auto-generate primitive defaults | Choose an explicit fallback value or throw an error |
| Thinking every `null` breaks the proxy | Reference types and `Void`/`Integer` can accept `null` | Check the return type and business contract |
| Thinking `void` forces the handler to return `null` | The proxy ignores the value; however `null` is more readable | Return `null` for clarity, without expecting another value |
| Catching errors only **inside** the handler | Conversion NPE/CCE can occur **after** the handler `return`s | Validate results early in the handler or handle exceptions at the caller |
| Using `== Integer.class` to detect `int` | Primitive `int.class` differs from wrapper `Integer.class` | Compare `getReturnType()` against `int.class`/`Integer.class` accurately |
| Ignoring `equals`, `hashCode`, `toString` | These calls also reach the handler and have their own return contracts | Handle `Object` methods intentionally |

For methods sharing the same name and parameter list across multiple interfaces, Java Dynamic Proxy also enforces rules on **return type compatibility** when creating the proxy. If a shared signature has a primitive or `void` return type, those interfaces must declare the exact same return type; for reference types, one return type must be assignable to the remaining return types. Do not assume that merely because two methods share a name, the handler can return an arbitrary type.

## 8. Distinguishing Dynamic Proxy from reflective method invocation

Two APIs that are easy to confuse:

- `InvocationHandler.invoke(proxy, method, args)` is called by the **Dynamic Proxy class**. The handler returns `Object`, and the proxy class converts the result according to the interface signature.
- `Method.invoke(target, args)` is the **Reflection API** directly invoking a method on a target, also returning `Object`; primitive results are boxed, and `void` methods yield `null`. If the target method throws an exception, `Method.invoke` normally wraps it in `InvocationTargetException`.

A handler can use `method.invoke(delegate, args)` to delegate to a real implementation. When doing so, handle reflective exceptions appropriately, and still ensure **the final value the handler returns to the proxy** matches the type required by the interface. Proxy type conversion is not skipped just because the handler calls Reflection internally.

If the handler throws a **checked exception** not declared by the interface method, calling through the proxy typically translates it into `UndeclaredThrowableException`. This is an **exception** rule, completely distinct from NPE/CCE caused by **result types**; do not conflate them into a single cause.

1. For `boolean active()`, if the handler returns `Boolean.FALSE`, `Integer.valueOf(0)`, and `null`, what result/error does each call produce? Why does `0` not automatically turn into `false`?
2. For `Long total()` (wrapper), does returning `null` from the handler fail inside the proxy? If the caller writes `long x = proxy.total();`, where does the error occur?
3. Why does `double avg()` require `Double`, and why is `return 2.5f;` invalid? Try replacing it with `return 2.5d;`.
4. Why does returning an object from the handler for a `void tick()` method not make the caller see that object?
5. Write a rule for `String name()` that accepts `null` yet still rejects an `Integer` object, and for `int count()` that rejects `null`.
6. Add `int hashCode()` to a scenario where the handler processes all methods; comment on the impact if the handler returns `null` when the client calls `proxy.hashCode()`.

**Takeaway:** the return type of `InvocationHandler.invoke` is always `Object`, yet the external contract belongs to the **interface method**. The proxy must cast and unbox to return the right result. `null` is valid for reference types and ignored when the method is `void`; `null` for a primitive causes NPE, while an incompatible object causes CCE. Decide clearly what "no data" means in the API contract and validate results before leaving the handler if early diagnosis is needed.
