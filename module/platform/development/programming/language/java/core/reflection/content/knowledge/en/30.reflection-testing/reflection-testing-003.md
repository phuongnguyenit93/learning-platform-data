# Testing Primitive, Wrapper, Overload, and Generic Erasure Lookup with Java Reflection

## 1. Goal: Verify Actual Behavior Rather Than Guessing How Reflection Selects a Method

When using `Class.getMethod(...)` or `Class.getDeclaredMethod(...)`, bugs often come from confusing the rules for **looking up a method by signature** with the rules for **invoking a method in Java**. The Java compiler can choose an overload via autoboxing, unboxing, primitive widening, and inheritance-type references; whereas `getMethod(name, parameterTypes)` requires a parameter type list that **matches the exact** declared signature. Reflection does not automatically search for the "closest overload."

Scope of this test lesson:

1. Distinguish `int.class` and `Integer.class` during lookup.
2. Prove that overloads `choose(int)`, `choose(Integer)`, `choose(Number)`, and `choose(Object)` are independent methods.
3. Verify that `Method.invoke` can unbox/widen certain arguments after a method is found, but does not choose an overload itself.
4. Look up a method declared with `List<String>` using `List.class` due to **generic erasure**, while reading `ParameterizedType` metadata still stored in the class file.
5. Recognize bridge methods generated by the compiler when overriding generic methods.
6. Write tests with assertions that run standalone on JDK 17+, with deterministic output that reports mismatches immediately at runtime.

**Key takeaway:** whether a method **is found** is one question; which arguments a found `Method` **accepts at `invoke`** is another question.

## 2. Distinguishing Three Layers of Rules

| Situation | Java compiler on direct call | `getMethod(...)` during lookup | `Method.invoke(...)` after obtaining `Method` |
| --- | --- | --- | --- |
| `choose(5)` with multiple overloads | Performs overload resolution at compile time; `int` is typically preferred if exact match | Must explicitly specify `int.class` to find `choose(int)` | Accepts boxed `Integer` as argument for an `int` parameter via unboxing |
| `choose(Integer.valueOf(5))` | Prefers the `Integer` overload if present | Must explicitly specify `Integer.class` | `Integer` argument matches `Integer` parameter |
| `choose(Short.valueOf((short) 5))` | Can pick an overload per method invocation applicability/most-specific rules | Does not automatically find `choose(int)` when passing `short.class` | If `choose(int)` is already obtained, can unbox `Short` to `short` and widen to `int` |
| `accept(new ArrayList<String>())` with parameter `List<String>` | Compiles because `ArrayList<String>` implements `List<String>` | Look up by the **declared** type `List.class`, not `ArrayList.class` | An `ArrayList` instance matches the `List` parameter |
| `accept(List<String>)` | Compiler uses generics to check element types | Erased runtime parameter type: `List.class` | Checks runtime argument type; does not automatically check that every element is `String` |

`getMethod`/`getDeclaredMethod` has no concept of "selecting a method whose parameter is a superclass of the passed type," does not box `int.class` into `Integer.class`, and does not select overloads based on return type.

Notes on `Method.invoke`: the argument for a primitive parameter must be an unboxable wrapper; the API permits primitive widening when valid, but forbids primitive narrowing. `null` cannot be converted to a primitive. For reference types, the object must have a compatible type. `invoke` can also fail due to a wrong receiver, access control, argument errors, or an exception thrown by the target method (wrapped in `InvocationTargetException`).

## 3. Primitive and Wrapper Lookup: You Must Specify the Exact `Class`

Suppose we have two declarations:

```java
public String choose(int value) { return "int"; }
public String choose(Integer value) { return "Integer"; }
```

These are **two distinct signatures**, because `int` is a primitive while `java.lang.Integer` is a reference type. The following statements differ:

- `int.class == Integer.TYPE` is `true`: the `TYPE` field on the wrapper describes primitive `int`.
- `int.class == Integer.class` is `false`: `int.class` and `Integer.class` are two `Class` objects for **two different types**.
- `type.getMethod("choose", int.class)` finds the method with primitive `int` parameter.
- `type.getMethod("choose", Integer.class)` finds the method with wrapper `Integer` parameter.
- `type.getMethod("choose", Long.class)` throws `NoSuchMethodException` if there is no exact `Long` overload, even if the class has `choose(Number)` or `choose(Object)`.

`Class.forName("int")` is **not** equivalent to `int.class`: `"int"` is not the binary name of a normal class that `Class.forName` can find. For primitives, use the literal `int.class` or `Integer.TYPE`.

Do not call `getClass()` on a primitive variable: `int` is not an object. If it gets autoboxed into `Integer` before calling `getClass()`, the result reflects the wrapper `Integer.class`, not `int.class`.

## 4. Overloads: Exact Lookup vs. Applying Conversion Rules

Given same-named overloads:

```java
public String choose(int value) { return "int"; }
public String choose(Integer value) { return "Integer"; }
public String choose(Number value) { return "Number"; }
public String choose(Object value) { return "Object"; }
```

The expressions `type.getMethod("choose", int.class)`, `getMethod("choose", Integer.class)`, `getMethod("choose", Number.class)`, and `getMethod("choose", Object.class)` are all valid and return **four `Method` objects describing four distinct declarations**.

Conversely, `getMethod("choose", Short.class)` and `getMethod("choose", short.class)` both throw `NoSuchMethodException` if those two exact signatures do not exist. Reflection does not infer `Number` or `int` based on `Short`'s compatibility.

Once you have stored `Method chooseInt = type.getMethod("choose", int.class)`, `chooseInt.invoke(target, Integer.valueOf(5))` can return `"int"` because the boxed argument is unboxed; this **does not mean** `getMethod("choose", Integer.class)` returns `choose(int)`. Similarly, `Short.valueOf((short) 5)` can unbox to `short` and widen to `int` during `invoke`. However, `chooseInt.invoke(target, Long.valueOf(5))` does not narrow `long` to `int`: the call is invalid.

Additional cases worth testing:

- `null` is allowed for reference parameters like `Integer` (if the method handles it), but not for a primitive `int` parameter.
- When `Method.invoke` calls an instance method, a valid receiver is required; for a static method, the receiver does not need to be an instance.
- With varargs, the arguments passed to `invoke` at the reflection level must match the compiled array parameter; do not assume it always packs varargs like normal Java call syntax.
- If the target method throws an exception, `invoke` wraps it in `InvocationTargetException`; this differs from `NoSuchMethodException` occurring during signature lookup.

## 5. Generic Erasure: Looking Up by Erased Parameter Types

Consider the declaration:

```java
public int accept(java.util.List<String> values) {
    return values.size();
}
```

`List<String>` only supports generic checking at compile time. At runtime, the method parameter type is erased to `java.util.List`; therefore:

- `Sample.class.getMethod("accept", List.class)` — **found**.
- `Sample.class.getMethod("accept", ArrayList.class)` — **not found**: the declared method parameter is `List`, not `ArrayList`, even though the method can be invoked with an `ArrayList` instance.
- `method.getParameterTypes()[0] == List.class` — `true`: this API returns the erased `Class<?>`.
- `method.getGenericParameterTypes()[0]` can be a `ParameterizedType` describing `List<String>` if the class file has proper `Signature` metadata.
- When `method.invoke(target, new ArrayList<String>())` runs, Reflection checks the raw/runtime `List` parameter; it does not individually inspect each instance's `String` generic type argument.

**Do not confuse:** "type erasure" does **not** mean all generic metadata is stripped from `.class`. The generic `Signature` of a **declaration** can be preserved by the compiler and read by Reflection via `getGenericParameterTypes()`, `getGenericReturnType()`, or `getGenericSuperclass()`. Metadata can be missing or corrupted after bytecode processing, so tools must not assume every `.class` file always contains full signatures.

Two overloads differing only in generic arguments, such as `accept(List<String>)` and `accept(List<Integer>)`, **cannot be declared together in the same class** because after erasure their signatures collide as `accept(List)`: the compiler reports a name clash.

## 6. Bridge Methods: Notes When Counting and Selecting Methods

A subtle consequence of generic erasure appears when overriding:

```java
class Parent<T> {
    public T echo(T value) { return value; }
}

class Child extends Parent<String> {
    @Override
    public String echo(String value) { return value.toUpperCase(); }
}
```

In `Parent`, `echo(T)` has erased parameter `Object`. In `Child`, the author-declared method takes `String`. To ensure a polymorphic call on a `Parent` reference after erasure still dispatches to `Child.echo(String)`, the standard Java compiler generates a **bridge method** taking `Object` and forwarding to the method taking `String`.

Therefore, when iterating over `Child.class.getDeclaredMethods()`, you can encounter both:

- The author-declared `echo(String)` method: `isBridge() == false`.
- The compiler-generated `echo(Object)` method: `isBridge() == true` and typically `isSynthetic() == true`.

A bridge method is a real method in bytecode that can be listed by Reflection or looked up by its erased parameter. An annotation/dispatcher tool must decide whether to skip bridge/synthetic methods to avoid duplicate processing or map bridges back to the original method; you should not assume the reflected method count equals the number of methods visible to a programmer in the `.java` file.

Bridges also appear in overrides with covariant return types or after generic erasure under binary compatibility rules. Determining exactly which methods are generated depends on the inheritance structure and compiler; inspect with `javap -p -v` when designing advanced tools.

## 7. Standalone Java 17+ Test Program with Assertions

Create file `ReflectionLookupTests.java`. The tests use `check(label, condition)`; if false, the program throws `AssertionError` and terminates abnormally, independent of the JVM `-ea` flag.

```java
import java.lang.reflect.Method;
import java.lang.reflect.ParameterizedType;
import java.lang.reflect.Type;
import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

public class ReflectionLookupTests {
    public static class Sample {
        public String choose(int value) { return "int"; }
        public String choose(Integer value) { return "Integer"; }
        public String choose(Number value) { return "Number"; }
        public String choose(Object value) { return "Object"; }

        public int accept(List<String> values) {
            return values.size();
        }
    }

    public static class Parent<T> {
        public T echo(T value) { return value; }
    }

    public static class Child extends Parent<String> {
        @Override
        public String echo(String value) {
            return value.toUpperCase(Locale.ROOT);
        }
    }

    static void check(String label, boolean condition) {
        if (!condition) {
            throw new AssertionError(label);
        }
        System.out.println("PASS " + label);
    }

    static boolean lookupMissing(Class<?> type, String name,
            Class<?> parameter) {
        try {
            type.getMethod(name, parameter);
            return false;
        } catch (NoSuchMethodException expected) {
            return true;
        }
    }

    public static void main(String[] args) throws Exception {
        Class<Sample> type = Sample.class;
        Sample target = new Sample();

        Method primitive = type.getMethod("choose", int.class);
        Method wrapper = type.getMethod("choose", Integer.class);
        Method number = type.getMethod("choose", Number.class);
        Method object = type.getMethod("choose", Object.class);

        check("primitive != wrapper", int.class != Integer.class);
        check("Integer.TYPE == int.class", Integer.TYPE == int.class);
        check("four exact signatures",
                primitive.getParameterTypes()[0] == int.class
                && wrapper.getParameterTypes()[0] == Integer.class
                && number.getParameterTypes()[0] == Number.class
                && object.getParameterTypes()[0] == Object.class);

        check("missing Long overload",
                lookupMissing(type, "choose", Long.class));
        check("missing short overload",
                lookupMissing(type, "choose", short.class));

        check("invoke unboxes Integer",
                "int".equals(primitive.invoke(target, Integer.valueOf(7))));
        check("invoke widens short to int",
                "int".equals(primitive.invoke(target,
                        Short.valueOf((short) 7))));
        check("invoke wrapper exact",
                "Integer".equals(wrapper.invoke(target, Integer.valueOf(7))));
        check("invoke Number accepts Integer",
                "Number".equals(number.invoke(target, Integer.valueOf(7))));

        boolean narrowingRejected = false;
        try {
            primitive.invoke(target, Long.valueOf(7L));
        } catch (IllegalArgumentException expected) {
            narrowingRejected = true;
        }
        check("long to int rejected", narrowingRejected);

        Method accept = type.getMethod("accept", List.class);
        check("List erased parameter",
                accept.getParameterTypes()[0] == List.class);
        check("ArrayList not declared",
                lookupMissing(type, "accept", ArrayList.class));
        check("ArrayList argument accepted",
                Integer.valueOf(2).equals(accept.invoke(target,
                        new ArrayList<>(List.of("a", "b")))));

        Type generic = accept.getGenericParameterTypes()[0];
        check("generic signature retained",
                generic instanceof ParameterizedType
                && ((ParameterizedType) generic)
                        .getActualTypeArguments()[0] == String.class);

        Method declared = Child.class.getDeclaredMethod("echo", String.class);
        Method bridge = Child.class.getDeclaredMethod("echo", Object.class);
        check("source method not bridge", !declared.isBridge());
        check("generated bridge method", bridge.isBridge()
                && bridge.isSynthetic());
        check("bridge dispatch",
                "HELLO".equals(bridge.invoke(new Child(), "hello")));

        boolean primitiveNameMissing = false;
        try {
            Class.forName("int");
        } catch (ClassNotFoundException expected) {
            primitiveNameMissing = true;
        }
        check("Class.forName int not primitive", primitiveNameMissing);
    }
}
```

Compile and run commands:

```bash
javac -encoding UTF-8 ReflectionLookupTests.java
java ReflectionLookupTests
```

Expected output:

```text
PASS primitive != wrapper
PASS Integer.TYPE == int.class
PASS four exact signatures
PASS missing Long overload
PASS missing short overload
PASS invoke unboxes Integer
PASS invoke widens short to int
PASS invoke wrapper exact
PASS invoke Number accepts Integer
PASS long to int rejected
PASS List erased parameter
PASS ArrayList not declared
PASS ArrayList argument accepted
PASS generic signature retained
PASS source method not bridge
PASS generated bridge method
PASS bridge dispatch
PASS Class.forName int not primitive
```

The program guarantees the following:

- Overload names are identical, yet `Method.getParameterTypes()` shows **distinct signatures**; there is no autoboxing at the `getMethod` step.
- The `lookupMissing(...)` branch directly verifies `NoSuchMethodException` instead of treating "not found" as an unexpected error.
- The `invoke` calls clearly illustrate **unboxing + primitive widening** versus rejected primitive narrowing.
- Passing `ArrayList<String>` into a method declaring `List<String>` succeeds on invocation because `ArrayList` is compatible with raw runtime `List`, yet lookup with `ArrayList.class` still fails.
- `getGenericParameterTypes()` reads the `List<String>` declaration retained by `javac` in `Signature`. This step verifies actual metadata in the class file compiled by the test; it is not a guarantee for arbitrary external bytecode.
- `Child` has a bridge method per Java 17 compilation output; invoking through the bridge calls the override and returns `HELLO`.
- `Class.forName("int")` confirms primitive literals must be obtained via `int.class` or `Integer.TYPE`.

**If a test reports FAIL or throws an exception**, inspect the first occurrence to distinguish lookup failure, invocation conversion, generic metadata, and compiler bridges. Never alter assertions just to make a test PASS.

## 8. Designing a Test Matrix for Reflection-Based Tools

When building a mapper, serializer, DI container, RPC dispatcher, or test framework, test a **matrix** rather than only a few "happy paths":

| Group | Test case | Expected result |
| --- | --- | --- |
| Primitive lookup | `getMethod("choose", int.class)` | Finds exact `choose(int)` |
| Wrapper lookup | `getMethod("choose", Integer.class)` | Finds exact `choose(Integer)` |
| Missing overload | `getMethod("choose", Long.class)` | `NoSuchMethodException`, even though `choose(Number)` exists |
| Widening invocation | Call `choose(int)` with `Short` | Can unbox then widen `short → int` |
| Narrowing invocation | Call `choose(int)` with `Long` | `IllegalArgumentException` |
| Reference invocation | Call `choose(Number)` with `Integer` | Valid because subtype reference is assignable to `Number` |
| Generic erased lookup | Look up `accept(List<String>)` via `List.class` | Finds `accept(List)` |
| Generic concrete lookup | Look up `accept(ArrayList.class)` | No exact signature, fails |
| Generic signature | `getGenericParameterTypes()` | Can yield `List<String>` when `Signature` is preserved |
| Bridge method | `getDeclaredMethods()` on subclass overriding generic | May see bridge/synthetic method |
| Inherited public | `getMethod` vs. `getDeclaredMethod` | `getMethod` can find inherited public; `getDeclaredMethod` only finds directly declared methods |
| Access control | Look up private method with `getDeclaredMethod` | Metadata can be seen, but invoke still follows access/module rules |
| Negative paths | Wrong name, null parameter, wrong receiver, checked target exception | Check the right exception at the right **stage** |

For Reflection-based tests, clearly separate three kinds of assertions:

1. **Lookup contract:** the method is located by exact name and parameter type list; a missing signature raises `NoSuchMethodException`.
2. **Invocation contract:** receiver and actual arguments are compatible with declared parameter types; the target method runs/throws exceptions as expected.
3. **Metadata contract:** generic `Type`, annotations, and bridge/synthetic flags exist in the class file being used; such information can be altered by compilers or bytecode processing tools.

When testing bytecode generated dynamically by frameworks or proxy classes, do not apply identical `javac` expectations to auto-generated methods: inspect the actual bytecode structure and pick appropriate rules.

## 9. Common Testing Pitfalls

### Relying on `getDeclaredMethods()` to Pick the "First" Overload

The order of methods returned by `getDeclaredMethods()`/`getMethods()` **is not guaranteed to be stable** relative to source code. Do not use `methods[0]` to infer overload priority, nor use reflection order as a substitute for compiler overload resolution. Filter by name, exact parameter types, visibility, and an explicit selection policy.

### Calling `getMethod` and Assuming It Invokes the Method

`getMethod` only returns a `Method`; it does not execute the body. Calling `invoke` may encounter `IllegalAccessException` or `InvocationTargetException`; for static methods, receiver can be `null`, whereas instance methods need an appropriate object. Test "correct lookup" and "correct invocation" separately.

### Comparing Wrapper and Primitive Types by Simple Name

`int.class.getSimpleName()` is `"int"`, `Integer.class.getSimpleName()` is `"Integer"`; using strings to infer convertibility is fragile. Use `Class<?>` and an explicit primitive conversion table if the framework genuinely needs dynamic overload selection.

### Confusing Method Signature with the Actual Argument Type

`List.class` is the declared parameter class after erasure of `accept(List<String>)`. Passing `new ArrayList<>()` to `invoke` is a matter of runtime compatibility; it does not change the method signature to `ArrayList`.

### Inferring Generics from an Object

`new ArrayList<String>().getClass()` does not carry the instance's `String` type argument. `Field.getGenericType()` or `Method.getGenericParameterTypes()` describes the **declaration** stored in the class file; `TypeToken` or an explicit schema/token is more suitable when an API must accept a type argument at runtime.

### Ignoring Bridge/Synthetic Methods

If a framework loops over `getDeclaredMethods()` to auto-register handlers, bridge methods can cause duplicate registrations. Use `isBridge()`/`isSynthetic()` when needed, while remembering bridges perform real dispatch and should not be blindly discarded in runtime analysis tools.

### Concluding "Java Reflection Is Broken" from `NoSuchMethodException`

Before blaming the API, print in a controlled way `method.getParameterTypes()`, `method.isBridge()`, `getDeclaringClass()`, and check `getMethod` (public, with inheritance) versus `getDeclaredMethod` (directly declared, including private). Especially distinguish `int.class` from `Integer.class` and `List.class` from `ArrayList.class`.

## 10. Self-Check Exercises

**Question 1.** A class only has `run(int)`. Will `getMethod("run", Integer.class)` succeed due to autoboxing?

**Answer:** No. Lookup requires the exact signature `int.class`; autoboxing/unboxing belongs to the argument conversion phase at invocation time, not method lookup.

**Question 2.** You already have the `Method` for `run(int)`. Can you pass `Short.valueOf((short) 3)` via `invoke`?

**Answer:** Yes: unboxing `Short → short` followed by primitive widening `short → int`. Passing `Long` to an `int` parameter is invalid because it requires narrowing.

**Question 3.** Why is `getMethod("accept", List.class)` right for `accept(List<String>)`, whereas `getMethod("accept", ArrayList.class)` is wrong?

**Answer:** The erased signature is `accept(List)`. `ArrayList` is an implementation type usable as an actual argument, not the declared parameter type.

**Question 4.** Can the same class overload `process(List<String>)` and `process(List<Integer>)`?

**Answer:** No. Both erase to `process(List)`, causing a name clash.

**Question 5.** Does `getGenericParameterTypes()` reporting `List<String>` prove that an existing `ArrayList` instance only contains `String`?

**Answer:** No. It describes metadata of the method declaration; generic erasure does not enforce runtime checking of collection elements as `String`.

**Question 6.** Why can a subclass overriding `echo(String)` also show `echo(Object)` when inspecting methods via reflection?

**Answer:** The compiler generates a bridge method to preserve polymorphic dispatch of the generic method after erasure. Use `isBridge()` and `isSynthetic()` to identify it.

**Question 7.** If a framework needs to select an overload by actual runtime arguments, is calling `getMethod(name, arg.getClass())` enough?

**Answer:** Not yet. Primitives, `null`, subtypes/interfaces, boxing/unboxing, widening, varargs, and specificity priority among overloads require an explicitly designed method-selection algorithm; Java Reflection API `getMethod` does not perform full overload resolution for the framework.

**Conclusion:** Test in three layers: **exact signature lookup → invocation with valid argument conversions → generic/bridge metadata inspection**. Primitives and wrappers are distinct types, overloads are not auto-selected by Reflection, and generic erasure governs the runtime signature even though the class file can still retain generic metadata for introspection.
