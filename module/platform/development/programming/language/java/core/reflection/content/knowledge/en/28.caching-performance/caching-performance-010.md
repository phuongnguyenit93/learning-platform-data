# Reflection Implementation Details Can Change Across JDK Versions

## 1. Distinguishing the API Contract from JDK Internals

In Java, **core reflection** is the standard API set including `java.lang.Class`, `java.lang.reflect.Method`, `Constructor`, `Field`, and `AccessibleObject`. Applications use these APIs to inspect type information and operate on members at runtime. For instance:

```java
Method add = Counter.class.getMethod("add", int.class);
Object result = add.invoke(counter, 2);
```

This fragment requires `Counter`, `counter`, and `import java.lang.reflect.Method`. The critical contract is finding the right method, checking access permissions, validating arguments, executing the method, returning the result, and reporting exceptions as specified by Javadoc. **How the JDK translates a reflective call into JVM operations is not part of the public API's stability guarantee.**

A JDK may use native entry points, dynamically generated helper classes, `MethodHandle`, `VarHandle`, JIT intrinsics, or other mechanisms. Those details may change as long as they continue satisfying the Java SE specification, unless an upgrade also announces explicit API/semantic changes. Therefore:

- You can expect `Method.invoke`, `Field.get`, and `Constructor.newInstance` to behave according to the **Javadoc of the target version**.
- Do not treat internal call paths, class names like `DelegatingMethodAccessorImpl`, private JDK field names, or optimization thresholds as a public interface.
- Do not assume the same reflective call always has the same execution time across different JDKs, or even across warmup phases of the same JVM.
- Do not equate implementation changes with API semantic changes; a JDK upgrade still requires regression tests to verify real behavior and performance.

This lesson belongs to **caching and performance**: understanding how reflection implementations evolved helps you design caches, evaluate benchmarks, and plan JDK upgrades more accurately.

## 2. A Real-World Example: JEP 416 in JDK 18

[**JEP 416 — Reimplement Core Reflection with Method Handles**](https://openjdk.org/jeps/416) was introduced in **JDK 18**. Its main goal was simplifying maintenance: implementing core reflection on top of `java.lang.invoke` to reduce duplicate internal code paths.

| OpenJDK Era | Notable Implementation Model | What to Understand |
| --- | --- | --- |
| JDK 17 and earlier (traditional model) | Initial reflective `Method.invoke`/constructor calls could go through native accessors; after a threshold, *inflation* generated bytecode accessors to support repeated calls | This is an **implementation detail**, not a contract that N calls always trigger a specific accessor class on every JVM |
| JDK 18–21 | Core reflection reimplemented on top of `MethodHandle` for `Method`/`Constructor` and `VarHandle` for `Field` | Callers keep using the same public API; internal classes and performance characteristics may differ |
| JDK 22 onward (OpenJDK) | Old core reflection implementation removed | Do not rely on temporary flags to fall back to the legacy implementation; JDK 22 docs confirm it no longer has any effect |

### Pre-JDK 18 Model: What Was “Inflation”?

In some HotSpot/OpenJDK implementations prior to JDK 18, early reflective calls could go through an accessor backed by native code. After a certain number of calls, the JDK could switch to a dynamically generated bytecode accessor to avoid repeated native transitions. This mechanism was called *inflation*. Those internal helper classes and how the JIT processed them incurred warmup cost, code generation, and multiple code paths to maintain.

That is why older benchmarks observed differing reflection call times before and after warmup. **Do not turn this observation into a fixed rule of the Java language**: thresholds, internal property names, optimization effects, and implementation choices depend on the JDK/vendor.

### After JEP 416: What Does “Using MethodHandles” Mean?

In OpenJDK starting with JDK 18, `Method.invoke` is backed by method handles, constructor invocation by method handles, and field accessors by var handles. This **does not mean** the `Method.invoke` API turned into `MethodHandle.invokeExact` for callers.

Public API differences remain:

- `Method.invoke` still accepts `Object...` and returns `Object`; when the target method throws an exception, reflection wraps the cause in `InvocationTargetException`.
- `MethodHandle.invokeExact` requires the call-site signature to match the handle's `MethodType` exactly and propagates exceptions directly from the target (aside from errors when the handle itself is invoked incorrectly).
- `Field.get/set` still follows reflection typing, access checks, and conversion rules; `VarHandle` additionally exposes access modes with distinct memory/atomic semantics.
- `AccessibleObject` and JPMS access checks retain their own contracts and are not removed just because the underlying implementation uses `java.lang.invoke`.

The [Oracle JDK 18](https://www.oracle.com/java/technologies/javase/18-relnote-issues.html) release notes describe compatibility risks for code **relying on undocumented details**. For example, code inspecting internal accessor classes or attempting to mutate private `modifiers` fields inside `Method`/`Field`/`Constructor` could break. This is a clear example of why you should avoid depending on JDK internals.

### Legacy Compatibility Flags Are Not a Long-Term Solution

JEP 416 temporarily provided the system property `-Djdk.reflect.useDirectMethodHandle=false` to fall back to the old implementation in JDKs that still contained it. **JDK 22 removed the old implementation and turned that flag into a no-op** according to the [JDK 22 Release Notes](https://www.oracle.com/java/technologies/javase/22-relnote-issues.html). Never use this property as a performance setting or long-term workaround on modern JDKs.

If regression testing on JDK 18–21 is needed, treat that property strictly as a diagnostic tool *scoped to supported versions*, not a public contract. Different JDK distributions can differ; always check the release notes of the distribution you run.

## 3. What Stays Stable, and What Can Change?

### Behavior Defined by the Public API

Applications should rely on the following **per the target JDK's Javadoc**:

- `Class#getMethod(name, parameterTypes)` finds a public method by name and parameter types, or throws `NoSuchMethodException` if not found.
- `Method#invoke(receiver, args)` requires a compatible receiver for instance methods; static methods ignore the receiver; argument count and types must be compatible.
- `Constructor#newInstance(args)` instantiates via the selected constructor, enforcing access and argument checks.
- `Field#get(receiver)`/`set(receiver, value)` reads/writes fields subject to access and type rules; `final` fields have specific restrictions.
- When target method/constructor code throws an exception, `Method.invoke`/`Constructor.newInstance` surfaces it via `InvocationTargetException`.
- Reflective access is governed by Java language rules and the Java Platform Module System; `setAccessible(true)` does not bypass module boundaries by default.

These guarantees are enough for an application to interact with reflection without caring whether internal accessors use native code, bytecode, or method handles.

### Details Not to Treat as a Contract

| Internal Assumption | Why It Is Risky |
| --- | --- |
| Specific `MethodAccessor`/`FieldAccessor` implementation classes | JEP 416 changed the implementation path; a JDK release can remove internal classes |
| “Inflation” thresholds or undocumented properties | Can be changed, removed, or rendered completely ineffective in later releases |
| Order of `getDeclaredMethods()`/`getDeclaredFields()` | Javadoc does not guarantee source order; sort explicitly if deterministic output is needed |
| How `Method`/`Field` stores internal caches/accessors | Private field layout and caching strategies can change |
| A single figure like “reflection is X times slower than direct” | Varies with JDK, workload, call shape, compiler, warmup, and metadata retention |
| Private JDK packages like `jdk.internal.reflect` | Not part of the public Java SE API; also restricted by module encapsulation |
| Stack traces always containing the same internal frames | Implementation changes alter helper frames; do not parse by internal class names |

Even when the public API stays stable, a JDK upgrade can introduce **documented** changes to APIs, access control, warnings, or behavior. Compatibility checks must therefore involve reading release notes and running tests rather than just saying “implementation detail.”

## 4. Java 17+ Example: Public APIs Produce Consistent Results

The following program uses reflection to construct an object, invoke a method, and read/write a field; uses `ClassValue<Method>` as an **example of per-class metadata caching**; and invokes the same logic via `MethodHandle` to show that external APIs differ while business results remain unchanged. It does not read private JDK classes, inspect accessor internals, or rely on timing measurements.

Save as **`ReflectionUpgradeDemo.java`**:

```java
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;
import java.lang.reflect.Constructor;
import java.lang.reflect.Field;
import java.lang.reflect.Method;

public class ReflectionUpgradeDemo {
    public static final class Counter {
        public int value;

        public Counter(int start) {
            value = start;
        }

        public int add(int delta) {
            return value += delta;
        }
    }

    // Cache metadata by Class<?>; do not cache per-object values.
    private static final ClassValue<Method> ADD = new ClassValue<>() {
        @Override
        protected Method computeValue(Class<?> type) {
            try {
                return type.getMethod("add", int.class);
            } catch (NoSuchMethodException e) {
                throw new IllegalStateException(e);
            }
        }
    };

    public static void main(String[] args) throws Throwable {
        Constructor<Counter> constructor =
                Counter.class.getConstructor(int.class);
        Counter counter = constructor.newInstance(5);

        Method method = ADD.get(Counter.class);
        Object result = method.invoke(counter, 2);

        Field field = Counter.class.getField("value");
        System.out.println("reflection invoke: " + result);
        System.out.println("reflection field: " + field.getInt(counter));
        System.out.println("metadata cached: "
                + (method == ADD.get(Counter.class)));

        MethodHandle handle = MethodHandles.lookup().findVirtual(
                Counter.class,
                "add",
                MethodType.methodType(int.class, int.class));
        Counter other = new Counter(5);
        int fromHandle = (int) handle.invokeExact(other, 2);
        System.out.println("method handle: " + fromHandle);

        field.setInt(counter, 11);
        System.out.println("field after set: " + field.getInt(counter));
    }
}
```

Compile and run with JDK 17+:

```bash
javac --release 17 ReflectionUpgradeDemo.java
java ReflectionUpgradeDemo
```

Expected stdout:

```text
reflection invoke: 7
reflection field: 7
metadata cached: true
method handle: 7
field after set: 11
```

Meaning:

1. `Constructor.newInstance(5)` creates `Counter(5)`; `Method.invoke(counter, 2)` yields `7`.
2. `ClassValue` stores `Method` per `Class<?>`. Two `ADD.get(Counter.class)` calls in the same run return the same metadata object in this example; there is no `remove` or cache change between reads.
3. `MethodHandle` invokes `Counter.add` on another instance with the explicit signature `(Counter,int)int` and returns `7`.
4. `Field.setInt` updates the value on the first instance to `11`, and `getInt` reads back `11`.
5. **The code does not claim both invocation styles have the same speed**. It serves as a regression test for public behavior that can be re-run across JDKs to compare stdout.

The following commands record the running JDK, though their output **depends on the machine** and is therefore excluded from the fixed stdout above:

```bash
java -version
javac -version
```

If multiple JDKs are installed, verify that `java` and `javac` use the intended version (via `JAVA_HOME`/`PATH` or full paths). The `--release 17` flag compiles against Java 17 target APIs; **it does not turn the running JVM itself into JDK 17**.

## 5. Reflection Performance Depends on Call Site and “Constantness”

JEP 416 highlights an important detail: when a `Method`/`Constructor`/`Field` object is recognized by the JVM as a constant at the call site (for example, held in a `static final` field and suitably optimized by the compiler), the new implementation can optimize very well; when metadata lives in dynamic data that the JIT cannot see as constant, the call path can perform worse in some microbenchmarks.

**Do not misunderstand `final` as automatically making every call site fast:** constant folding and inlining are JVM/JIT decisions, not language guarantees. Not every cached `Method` becomes constant in the way the JIT requires; `ClassValue` is a per-class metadata caching solution, not an automatic guarantee of `static final`-level invocation optimization.

Separate at least four cost categories when analyzing:

| Stage | Examples | What to Measure |
| --- | --- | --- |
| Member discovery | `clazz.getMethod(...)`, `getDeclaredFields()` | Call frequency, cache misses, classloader |
| Access checks / argument normalization | Receiver, access checks, boxing/unboxing | Access kind, signature, argument count |
| Call execution | `Method.invoke(...)`, `MethodHandle.invokeExact(...)`, direct method | JIT inlining, target polymorphism, method kind, call site |
| Metadata/cache lifetime | `ClassValue`, map keyed by `Class<?>` | Memory retention, module/classloader unloading, cache invalidation |

Typical benchmarking mistake:

```java
// Measures both lookup and invoke, failing to isolate invocation cost:
for (int i = 0; i < count; i++) {
    Method method = type.getMethod("run");
    method.invoke(target);
}
```

This is an illustrative fragment (requiring variables `type`, `target`, `count`, and exception handling). The measured result includes lookup, potentially mixed with JDK internal caching, JIT effects, and exception overhead. To learn the **isolated invocation cost**, move lookup outside the timed region; yet still test dynamic-lookup workloads if that reflects real application behavior.

Using `MethodHandle` is also not automatically faster than `Method.invoke`: typed/exact calls and constant handles optimize more readily; dynamic handles, type conversions, or `invokeWithArguments` can incur overhead. Choose APIs first by semantics and access permissions, then benchmark if speed genuinely matters.

## 6. Safe Metadata Caching Across JDK Versions

Caching pays off when the same classes and policies are reused repeatedly, especially in frameworks scanning many objects. However, **the caching strategy** must avoid retaining unloaded classloaders/plugins.

### `ClassValue<T>`

`ClassValue<T>` attaches a computed value to a `Class<?>` object and lets the runtime manage cache lifetime alongside the class. It fits type-immutable metadata such as normalized property lists or corresponding `Method` objects. In the program above, `ClassValue<Method>` avoids repeating `getMethod("add", int.class)` every time.

Note: `ClassValue.computeValue` may execute multiple times under contention; design the computation as an operation **without dangerous side effects**. If policies change, cached values must also be invalidated or cache keys/structures must include policy versions. Never cache field values or per-instance method results by `Class<?>` when values belong to individual instances.

### Maps and Classloader Retention

`ConcurrentHashMap<Class<?>, AccessPlan>` is typically fast and convenient, yet keys/values can hold references to `Class<?>`, `Method`, `Field`, or `MethodHandle`, preventing classloaders from being GC'd after hot reloads/plugin unloads. Consider `ClassValue`, lifecycle-bounded caches, or appropriate weak-key mechanisms; also check **whether values hold backward references to the class**.

### Do Not Cache Non-Contractual State

Do not access private fields of `Method` to hold internal accessors or guess inflation thresholds. Use public metadata, and if you need strongly typed handle invocation, build/configure handles via `MethodHandles.Lookup` with valid permissions. Reflective access errors can depend on module and caller context; never treat cached results acquired under different privileges as proof that every caller has permission.

## 7. How to Benchmark Reflection Properly During a JDK Upgrade

Do not run a single `System.nanoTime()` loop on JDK A and JDK B and claim the newer JDK is “faster/slower” from one number. JIT, warmup, garbage collection, CPU scaling, and dead-code elimination easily invalidate naive benchmarks.

A proper plan:

1. Lock down **JDK vendor, build, CPU architecture, OS, and JVM flags** for each trial; record `java -version`.
2. Use **JMH** (Java Microbenchmark Harness) for microbenchmarks with explicit forks, warmup, and measurement; do not use the demo in section 4 as a benchmark.
3. Measure `lookup`, `invoke`, and end-to-end workloads independently. Include cases: `static final` members, metadata/handles in instance fields, dynamic class lookups, methods with 0/1/many parameters, primitive/reference types, and valid public/private access.
4. Prevent the JIT from eliminating work: consume results via `Blackhole` or return valid values following JMH guidelines.
5. Compare throughput/latency together with variance across multiple forks; also observe allocations, GC, classloader retention, and cold-startup speed if your application is sensitive to them.
6. Run **functional regression tests** separately: permissions/JPMS, exceptions, varargs, conversions, and field/constructor behavior. Microbenchmarks do not replace regression tests.
7. If discrepancies appear, find the root cause using a profiler/JFR and make evidence-based design changes (such as metadata caching or call-site normalization). Do not force the JVM back onto unsupported legacy mechanisms.

There is no single “`Method.invoke` is X times slower” factor true for every JDK. JEP 416 presented figures for specific workloads and JVM builds at the time of the JEP; those illustrate **trade-offs** and why re-measuring matters, not fixed predictions for every future release.

## 8. Diagnosing Differences When Upgrading the JDK

When upgrading from JDK 17 to JDK 21, 22, or newer, classify changes systematically:

| Symptom | Likely Related To | Action |
| --- | --- | --- |
| Tests on `Method.invoke` with identical arguments return different results | App dependency/behavior change, JDK bug, or wrong contract assumption | Write a minimal test, compare Javadocs of both JDKs, and file a bug if evidenced |
| `InaccessibleObjectException` or access failures | Module boundaries, `opens`, and lookup permissions | Switch to public APIs or grant proper module access; stop reading JDK internals |
| New `java.lang.invoke` frames appear in stack traces | New core reflection implementation | Debug by API and cause; never branch logic on internal helper frame names |
| Startup or steady-state latency changed | Initialization cost, JIT, and call-site shape | Use JFR/JMH; separate cold vs. warmed cases |
| Legacy system property no longer works on JDK 22+ | Old implementation was removed | Remove the workaround and check the exact release notes |
| Plugin/hot reload fails to free classloaders | Metadata cache retains `Class<?>`/`Method` or classloader | Review cache lifecycle, `ClassValue`, or weak-reference design |

For example: if a framework relied on internal `MagicAccessorImpl`, succeeding on an older JDK does not prove the code is portable. Express the same logic using `Method`, `Constructor`, `Field`, `MethodHandles.Lookup`, or public interfaces rather than “patching” private fields of the reflection implementation itself via reflection.

If an application breaks after a JDK upgrade, record **exact versions of all JVMs involved** (build container, test worker, IDE, production); verify dependencies support that JDK and build a minimal reproducer. Do not toggle VM flags randomly before isolating the cause.

## 9. Common Mistakes and Self-Check Questions

**Mistake 1 — Equating JEP 416 with removing reflection:** JEP 416 changed the implementation **underneath** `java.lang.reflect`; it does not require replacing every `Method.invoke` with `MethodHandle`.

**Mistake 2 — Treating `jdk.reflect.useDirectMethodHandle=false` as a stable performance setting:** that was a temporary workaround in some post-JEP 416 JDKs; JDK 22 removed the old implementation.

**Mistake 3 — Concluding `ClassValue`/`static final` always guarantees higher speed:** caching cuts discovery cost; the JIT may optimize call sites conditionally, with no automatic performance guarantee.

**Mistake 4 — Using `getDeclaredMethods()` and trusting its default order:** the API makes no source-order promise. If you need deterministic output for schema generation or tests, sort explicitly.

**Mistake 5 — Using private JDK fields, `sun.reflect.*`, or `jdk.internal.reflect.*` as public APIs:** risks compile, access, and behavioral failures across JDK upgrades. Use public reflection/invoke APIs.

**Mistake 6 — Running only performance tests while skipping functional tests:** JIT benchmarks do not verify module access, exception wrapping, null receivers, or primitive conversions.

Self-check answers:

1. Did JDK 18 change `Method.invoke` syntax for callers? **No; JEP 416 changed the internal implementation.**
2. Once JDK 22 removed the old path, can `-Djdk.reflect.useDirectMethodHandle=false` restore it? **No; the flag became a no-op.**
3. If a framework calls `Class.getDeclaredMethods()` and needs deterministic output, what should it do? **Define an explicit sorting criterion.**
4. Does caching `Method` in a map guarantee both performance and zero memory leaks? **No; you must verify the workload and classloader lifecycle.**
5. How should you compare two JDKs on reflective overhead? **JMH with warmup/forks, separating lookup/invoke, keeping workload and environment equivalent, combined with functional tests.**
6. Why should you still read the Java SE Javadoc after learning reflection uses method handles? **Because the public API contract and the underlying implementation are two distinct layers.**
