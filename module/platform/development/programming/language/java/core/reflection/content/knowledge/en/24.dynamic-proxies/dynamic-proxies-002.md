# Creating a Proxy with `Proxy.newProxyInstance` in Java

`Proxy.newProxyInstance` is an API in `java.lang.reflect.Proxy` used to **create a proxy object at runtime**, implementing one or more specified interfaces and routing method calls on that object to an `InvocationHandler`. This is Java's built-in way to create a *JDK dynamic proxy*, without having to manually write a wrapper class for each implementation.

Article goal: accurately understand the three parameters of `newProxyInstance`, the call flow through the handler, how to create a runnable proxy on Java 17+, how to return values/propagate exceptions, and the limits to control when applying it in practice.

## 1. When do you need to create a proxy?

Suppose an application has an interface `Greeter` and a real implementation. Many objects need to call `greet`, and you want to log before/after the call, measure time, check permissions, or count invocations. A direct call goes straight to the real object:

```text
caller ──greet("An")──> Greeter implementation
```

If the caller receives a **proxy with the same interface**, you can place shared processing in between:

```text
caller (knows interface Greeter)
      │ calls greet("An")
      ▼
dynamic proxy (implements Greeter)
      │ forwards call information
      ▼
InvocationHandler.invoke(proxy, method, args)
      │ before call: log / validate / measure
      │ by design: method.invoke(target, args)
      │ after call: handle result / exception
      ▼
result or exception returns to caller
```

The caller still writes `service.greet("An")` just like with a normal `Greeter` object. The difference lies in **the object passed to the caller**: it is the proxy, and the handler executes whenever a call goes through the proxy.

Crucially, a proxy is **not required** to forward to a real object. The handler can also return a result directly, fetch data from elsewhere, or reject the call. The *proxy wrapping a target* model is simply the most common and easiest case to understand.

## 2. Signature and meaning of the three parameters

```java
public static Object newProxyInstance(
        ClassLoader loader,
        Class<?>[] interfaces,
        InvocationHandler h)
```

| Parameter | Role | How to choose? |
| --- | --- | --- |
| `loader` | Class loader used to define the proxy class generated at runtime | Commonly use `Greeter.class.getClassLoader()`; the loader must see all interfaces to proxy |
| `interfaces` | List of interfaces that the proxy will implement | For example `new Class<?>[] {Greeter.class}`; multiple interfaces are possible if JDK constraints are satisfied |
| `h` | The `InvocationHandler` object handling calls on the proxy | Typically a lambda or a class implementing the `invoke` method |

The method **returns `Object`**, because the interface list is only determined from the parameter at runtime. Callers usually cast it to the known interface:

```java
Greeter proxy = (Greeter) Proxy.newProxyInstance(
        Greeter.class.getClassLoader(),
        new Class<?>[] {Greeter.class},
        handler);
```

The snippet above assumes `Greeter` and `handler` are already declared; a complete runnable program is in section 4.

### Distinguishing the proxy from the target object

- `proxy instanceof Greeter` is `true` if `Greeter.class` is in the list of implemented interfaces.
- `proxy` is **not** an instance of the implementation class `BasicGreeter`; casting `(BasicGreeter) proxy` will fail.
- Proxies dispatch calls on **interfaces**. `Proxy.newProxyInstance` does not create a subclass of an ordinary Java class. If you need to proxy a concrete class, you must use another strategy that supports it.
- `Proxy.isProxyClass(proxy.getClass())` helps determine whether an object's class was generated by the JDK proxy mechanism. `Proxy.getInvocationHandler(proxy)` returns the corresponding handler, but requires the input object to actually be a proxy.

This is also why the proxy API is typically used alongside **interface-oriented programming**: the caller depends on the `Greeter` contract, not on the underlying implementation.

## 3. What does `InvocationHandler` receive on a call?

The `InvocationHandler` interface has one abstract method:

```java
Object invoke(Object proxy, Method method, Object[] args) throws Throwable;
```

| Parameter of `invoke` | Meaning |
| --- | --- |
| `proxy` | The proxy object itself receiving the call; **not** the target |
| `method` | `java.lang.reflect.Method` metadata describing the method invoked on the interface (or one of the three special `Object` methods) |
| `args` | The arguments of the invocation, in order; may be `null` when the method has no parameters |

The handler can inspect `method.getName()`, `method.getParameterTypes()`, annotations, and other metadata to decide what action to perform. You should not rely **solely** on the method name if the interface has overloads.

The value returned by the handler becomes the result of the call on the proxy. If the return type is primitive such as `int`, the handler must return the matching wrapper such as `Integer` for Java to unbox; returning `null` for a primitive type leads to a `NullPointerException`. For a `void` method, the handler should return `null`; the caller receives no value.

**Avoiding infinite loops:** inside `invoke`, calling the same method again on `proxy` will trigger the handler again. If you want to forward to the real implementation, invoke it on `target` (an object distinct from the proxy).

## 4. Complete Java 17+ example: creating a proxy, logging, and forwarding to a target

Save the following program as **`ProxyDemo.java`**. The example uses an interface `Greeter`, an implementation `BasicGreeter`, and a handler that both logs and forwards calls.

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Proxy;

public class ProxyDemo {
    public interface Greeter {
        String greet(String name);
        int count();
    }

    public static class BasicGreeter implements Greeter {
        private int calls;

        @Override
        public String greet(String name) {
            calls++;
            return "Hello, " + name + "!";
        }

        @Override
        public int count() {
            return calls;
        }
    }

    public static void main(String[] args) {
        Greeter real = new BasicGreeter();

        InvocationHandler handler = (proxy, method, passedArgs) -> {
            // These three Object methods also pass through the handler.
            if (method.getDeclaringClass() == Object.class) {
                return switch (method.getName()) {
                    case "toString" -> "GreeterProxy";
                    case "hashCode" -> System.identityHashCode(proxy);
                    case "equals" -> proxy == passedArgs[0];
                    default -> throw new UnsupportedOperationException(
                            method.getName());
                };
            }

            System.out.println("Before: " + method.getName());
            try {
                // Call the real implementation, do not call back into proxy.
                Object result = method.invoke(real, passedArgs);
                System.out.println("After: " + method.getName());
                return result;
            } catch (InvocationTargetException exception) {
                // Preserve the real cause from the invoked method.
                throw exception.getCause();
            }
        };

        Greeter proxy = (Greeter) Proxy.newProxyInstance(
                Greeter.class.getClassLoader(),
                new Class<?>[] {Greeter.class},
                handler);

        System.out.println(proxy.greet("An"));
        System.out.println("Count: " + proxy.count());
        System.out.println(proxy.toString());
        System.out.println("Equals self: " + proxy.equals(proxy));
        System.out.println("Is proxy: "
                + Proxy.isProxyClass(proxy.getClass()));
    }
}
```

Compile and run with JDK 17 or later:

```bash
javac ProxyDemo.java
java ProxyDemo
```

Expected output:

```text
Before: greet
After: greet
Hello, An!
Before: count
After: count
Count: 1
GreeterProxy
Equals self: true
Is proxy: true
```

**What happens at runtime:**

1. `real` is an actual `BasicGreeter` and holds the `calls` state.
2. `newProxyInstance` creates an object implementing the `Greeter` interface, connecting that object to `handler`.
3. `proxy.greet("An")` is routed by Java to `handler.invoke(proxy, method, passedArgs)`. `method.getName()` is `"greet"` and `passedArgs[0]` is `"An"`.
4. The handler prints the "Before" line, calls `method.invoke(real, passedArgs)`; `BasicGreeter.greet` increments `calls` and returns the string. The handler prints "After" and then returns the same result to the caller.
5. `proxy.count()` continues through the handler; this time `passedArgs` is `null` because `count()` takes no parameters. The `method.invoke(real, passedArgs)` call is still valid in this case.
6. `toString()` and `equals(Object)` also enter the handler but are handled separately for clear semantics. `hashCode()` is handled similarly using identity hash code, consistent with identity comparison in the example.

`InvocationTargetException` is the exception wrapper Reflection uses when code in the target throws an error. The `catch` block rethrows `getCause()` so the proxy propagates the real cause instead of accidentally letting the caller receive an undeclared wrapper.

Note that the "After" line in the example **only prints when the target succeeds**. If you need to measure or log regardless of success or failure, use `try/finally` and track the error state separately; do not turn a real error into a successful result.

## 5. Workflow for creating a proxy in a project

When applying `newProxyInstance` in production code, you can follow this workflow:

1. **Identify the interface contract** the caller is using, such as `Greeter` or `Repository`. Verify the target actually implements that contract if you intend to delegate.
2. **Choose a class loader** that can see the interfaces. Using the interface's own loader is a good choice for examples in the same module; when running with plugins or multiple class loaders, visibility of every interface must be ensured.
3. **Build a handler** with clear behavior: pre-processing, target selection, delegation, post-processing, exception handling, and rules for `equals`/`hashCode`/`toString`.
4. **Create the proxy once at the configuration point** and pass it to callers by its interface. Do not create a new proxy per call without a specific reason.
5. **Test behavior through the proxy reference**: success, exceptions, parameterless methods, overloads, return types, `Object` methods, and concurrent flows if state is shared.

A proxy can implement **multiple interfaces** by passing the corresponding `Class<?>` entries in the array, provided the interfaces satisfy JDK constraints. However, callers must choose the right interface to cast to, and you still need to design dispatch logic for methods sharing the same signature.

## 6. Real-world use cases and what a proxy does not do automatically

| Purpose | What the handler needs to do | Notes |
| --- | --- | --- |
| Logging | Log method name, loggable inputs, result or error | Avoid logging passwords, tokens, and sensitive data |
| Timing | Record timestamp before delegation, measure in `finally` | Distinguish execution time from I/O wait time |
| Authorization | Verify permissions then allow or deny the call | Must have a clear contract for denial errors |
| Transaction/cross-cutting logic | Begin, commit, or roll back by policy | Requires rules for exceptions, propagation, and state synchronization |
| Adapter/client | Use `Method` and args to send to a remote service | Proxy does not automatically create a network client or serializer |

`newProxyInstance` only provides the **call dispatch infrastructure**. It does not implement logging, authorization, transactions, retries, caching, or serialization on its own. All such behavior comes from the `InvocationHandler` or components used by the handler.

Distinguish this from `java.net.Proxy`: that class describes a network proxy (such as SOCKS/HTTP) and is **unrelated to creating a JDK dynamic proxy via Reflection**.

## 7. Common limitations and pitfalls

### 7.1. Must be interfaces and visible through the class loader

The `interfaces` array must contain valid interfaces, not ordinary classes, primitive types, hidden interfaces, or sealed interfaces. Do not pass duplicate entries of the same `Class<?>`; each interface must be visible by name through the chosen loader. Combinations of interfaces with conflicting return types, or non-public interfaces from incompatible packages/modules, can also cause `newProxyInstance` to throw `IllegalArgumentException`.

With named modules (JPMS), the accessibility and location of the generated proxy class depend on the accessibility of the interfaces. Do not assume the generated proxy class name is fixed or that its constructor can be accessed directly. Use `newProxyInstance` to create instances.

### 7.2. The handler must handle `Object` methods

JDK proxies route `equals(Object)`, `hashCode()`, and `toString()` to the handler as well. `method.getDeclaringClass()` for these three methods is `Object.class`.

If you blindly delegate with `method.invoke(real, args)`, `proxy.equals(proxy)` can become `real.equals(proxy)` and return `false` even when comparing the proxy with itself. If the handler calls `proxy.toString()` to log a `toString()` invocation itself, it can also enter infinite recursion.

Choose a clear equality policy: use proxy identity (as in the example), or design value equality suited to the abstraction and ensure `equals` is consistent with `hashCode`.

### 7.3. Exceptions and return types

- `Method.invoke(target, args)` wraps errors thrown by the target in `InvocationTargetException`. Proper delegation typically needs to unwrap `getCause()`.
- The handler may throw unchecked exceptions. For a **checked exception** incompatible with the interface method's `throws` clause, the proxy wraps it in `UndeclaredThrowableException`. Therefore, you cannot arbitrarily throw a checked exception from the handler and expect the caller to receive it unwrapped.
- If the handler returns a type incompatible with the declared return type, the proxy call may throw `ClassCastException`; for a primitive return type when the handler returns `null`, `NullPointerException` is thrown.
- If you want to handle every completion, including when the target throws an exception, place cleanup and metric recording in `finally`; do not swallow exceptions unless the contract permits it.

### 7.4. `default` methods and interfaces with matching signatures

Interface `default` methods can also be routed to the handler. On Java 17+, when you want to invoke the default method body of a proxy interface directly from the handler, you can use `InvocationHandler.invokeDefault(proxy, method, args)` after verifying `method.isDefault()` and validity conditions. This API has existed since Java 16; not all default method calls automatically bypass the handler.

When a proxy implements multiple interfaces with the same method name and parameter list, the handler may receive the `Method` associated with the interface appearing earlier in the interface array, regardless of which interface reference the caller used. Therefore, interface ordering and dispatch rules for methods with matching signatures must be considered.

### 7.5. Direct calls and self-invocation bypass the proxy

Only calls **actually going through the proxy object** are intercepted by the handler. If code calls `real.greet("An")`, the handler does not run. Similarly, if a method on the target calls another method on `this`, this internal call does not automatically route back through the proxy. This is a source of subtle bugs when using interceptors for transactions, caching, or authorization.

### 7.6. Performance overhead, concurrency, and untrusted input

Dynamic proxies incur dispatch/Reflection overhead and may add allocations or extra logic. Do not assert a fixed slowdown; benchmark in realistic scenarios and avoid repeatedly creating proxies or looking up metadata unnecessarily.

If the same handler/target holds shared state and multiple threads call the proxy concurrently, handler code must follow appropriate thread-safety rules. A proxy does not automatically make counters, caches, or transaction state thread-safe.

Do not use interface/class/action names from untrusted sources to freely instantiate or invoke methods; restrict allowed contracts and validate input data and execution permissions at appropriate boundaries.

## 8. When to use JDK dynamic proxy vs. alternatives?

**Prefer `Proxy.newProxyInstance`** when callers already work through interfaces and you need shared runtime behavior around calls. Typical examples are logging, metrics, remote adapters, invocation routing, and many interceptor mechanisms in libraries/frameworks.

**Prefer a hand-written decorator** if there are only a few stable interfaces/classes, wrapping logic is simple, and you want explicit code that is easy to trace in an IDE and type-checked at compile time.

**Consider subclass-based or bytecode proxy tools** if the contract must rely on concrete classes. Those solutions have their own rules regarding final methods, constructors, and access; they cannot directly use the same mechanism as `java.lang.reflect.Proxy`.

One design note: even though proxies can implement cross-cutting concerns, using a dynamic proxy **does not automatically turn every call in the system into an intercepted call**. The scope always depends on where you hand the proxy object to callers.

## 9. Checklist and self-check

Before putting a JDK dynamic proxy into an application, verify:

- The interfaces and class loader are appropriate; callers hold references to the **proxy**.
- The handler identifies methods accurately and handles `args == null`.
- Return values have the right types, especially for primitives or `void`.
- Exceptions thrown by the target propagate according to the interface contract.
- `equals`, `hashCode`, and `toString` have no unexpected behavior or recursion.
- Internal calls on the target, shared state, and performance have been accounted for.

**Practice questions:**
