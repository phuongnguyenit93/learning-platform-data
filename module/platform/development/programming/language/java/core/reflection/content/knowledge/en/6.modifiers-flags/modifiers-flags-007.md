# Bridge Methods and `Method.isBridge()` in Java Reflection

## 1. What is a bridge method and why should we care?

A **bridge method** is an additional method generated by the Java compiler in certain cases to preserve method overriding rules at the JVM bytecode level. It particularly appears when **generic type erasure** makes the bytecode signature of a subclass method differ from the signature that compiled code or the original interface expects to call, and when a **covariant return type** makes the overriding method's return type more specific.

In Java source code, we only see the method declared by the programmer. Yet at runtime, Java Reflection can see **both the real method and the compiler-generated bridge method**. Without proper recognition, an API scanner may display two seemingly duplicate methods, an annotation filter may misbehave, or a framework may pick the wrong method to reflect upon.

`java.lang.reflect.Method.isBridge()` indicates whether a `Method` is marked as a **bridge method**. Because this is a **method flag**, this topic belongs to the *Modifiers and Flags* group in Reflection.

**Learning outcomes:** understand why bridges exist, spot bridges in bytecode and Reflection, distinguish `isBridge()` from `isSynthetic()`, handle method scanning properly, and know when to keep or exclude bridges.

## 2. Mechanism from Java source to the JVM

At the Java source level, generics enable compile-time type checking:

```java
interface Sink<T> {
    void accept(T value);
}

class StringSink implements Sink<String> {
    @Override
    public void accept(String value) {
        System.out.println(value);
    }
}
```

The snippet above is **illustrative**, not a standalone program since it has no `main` method. A Java reader sees a valid implementation `accept(String)` of `Sink<String>`.

However, generics in Java are primarily based on **type erasure**. After erasing an unbounded type variable, the signature of the method declared in `Sink<T>` becomes:

```text
Sink.accept(T)              -> bytecode descriptor: (Ljava/lang/Object;)V
StringSink.accept(String)    -> bytecode descriptor: (Ljava/lang/String;)V
```

The JVM links calls based on name and descriptor; a method descriptor in the JVM includes parameter types and return type. Therefore, the `accept(String)` method alone does not provide the exact `accept(Object)` entry point that compiled callers via the `Sink` type may invoke.

To uphold the overriding contract, `javac` generates an additional method conceptually equivalent to:

```java
// Code simulating the bridge behavior generated by javac; MUST NOT be manually declared
// alongside accept(String) in the example to replace the compiler.
public void accept(Object value) {
    accept((String) value);
}
```

The bridge forwards the call to the `accept(String)` method and inserts the required cast. The bridge preserves polymorphism for calls through the interface; it does not change the generic type semantics checked at compile time.

**Note:** `accept(Object)` above is only a functional explanation. In the source code of `StringSink`, we **do not write** that method. The compiler emits the bridge into bytecode with the `ACC_BRIDGE` flag, and `javac` usually also adds `ACC_SYNTHETIC`.

### 2.1. Second case: covariant return types

Java allows an overriding method to return a subtype of the superclass's return type:

```java
class Parent {
    public Number read() {
        return 1;
    }
}

class Child extends Parent {
    @Override
    public Integer read() {
        return 2;
    }
}
```

At the source level, `read()` is a valid override. However, the JVM descriptor includes **the return type as well**:

```text
Parent.read()  -> ()Ljava/lang/Number;
Child.read()   -> ()Ljava/lang/Integer;
```

So that a call linked against descriptor `()Ljava/lang/Number;` still reaches `Child`'s implementation, `javac` can generate a bridge `Number read()` that calls `Integer read()`. Two methods with the same name and same parameters differing only in return type can coexist in compiler-generated bytecode; **you cannot declare two methods differing only in return type in ordinary Java source code**.

Thus, bridges **do not appear solely because of generics**. When analyzing with Reflection, also account for overrides with covariant return types.

## 3. Related APIs and flags

| API / element | Meaning |
| --- | --- |
| `Method.isBridge()` | `true` when the method carries the bridge attribute; this is the direct Reflection API to identify a bridge. |
| `Method.isSynthetic()` | `true` when the method is marked synthetic (does not appear as an ordinary source declaration); synthetic **is not synonymous** with bridge. |
| `Method.getModifiers()` | Retrieves the method's modifier bit set; use `isBridge()` specifically to ask about bridges. |
| `Class.getDeclaredMethods()` | Lists methods declared in the type itself, including compiler-generated bridges; does not automatically include merely inherited methods. |
| `Class.getMethods()` | Lists visible `public` methods on the type, including inherited methods; may include qualifying bridges. |
| `Method.getParameterTypes()` / `getReturnType()` | Reads runtime parameter/return types, useful for comparing a bridge and its target method. |
| `Method.getGenericParameterTypes()` / `getGenericReturnType()` | Reads generic type metadata represented by `Type`; requires understanding generics and erasure when analyzing. |
| `javap -p -c -v` | JDK tool to inspect methods, descriptors, `ACC_BRIDGE`/`ACC_SYNTHETIC` flags, and bytecode instructions. |

There are two important distinctions:

- **Bridge is a specialized role**: creating a forwarding path to preserve overriding/binary-linkage semantics after compilation. **Synthetic is a broader property**: the compiler can generate other auxiliary methods that are not bridges. Therefore, `isSynthetic()` alone **does not accurately identify** a bridge.
- `Modifier` provides common queries such as `isPublic`, `isStatic`, and `isFinal`, yet **there is no `Modifier.isBridge(...)`**. Moreover, some class-file bits carry different meanings by member kind: do not manually decode bits of `getModifiers()` using checks meant for fields. For a `Method` object, use `method.isBridge()`.

## 4. Complete Java 17+ example: observing bridges with Reflection

Save the following source code as **`BridgeMethodDemo.java`**:

```java
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.Comparator;
import java.util.stream.Collectors;

public class BridgeMethodDemo {
    interface Sink<T> {
        void accept(T value);
    }

    static class StringSink implements Sink<String> {
        @Override
        public void accept(String value) {
            System.out.println("accept(String): " + value);
        }
    }

    static class Parent {
        public Number read() {
            return 1;
        }
    }

    static class Child extends Parent {
        @Override
        public Integer read() {
            return 2;
        }
    }

    private static String signature(Method method) {
        String parameters = Arrays.stream(method.getParameterTypes())
                .map(Class::getSimpleName)
                .collect(Collectors.joining(", "));
        return method.getName() + "(" + parameters + ") -> "
                + method.getReturnType().getSimpleName();
    }

    private static void inspect(Class<?> type, String methodName) {
        System.out.println(type.getSimpleName() + ":");
        Arrays.stream(type.getDeclaredMethods())
                .filter(method -> method.getName().equals(methodName))
                .sorted(Comparator.comparing(BridgeMethodDemo::signature))
                .forEach(method -> System.out.println(
                        "  " + signature(method)
                                + " | bridge=" + method.isBridge()
                                + " | synthetic=" + method.isSynthetic()));
    }

    public static void main(String[] args) throws Exception {
        inspect(StringSink.class, "accept");
        inspect(Child.class, "read");

        Method bridge = StringSink.class.getDeclaredMethod("accept", Object.class);
        System.out.println("invoke accepted:");
        bridge.invoke(new StringSink(), "hello");
        try {
            bridge.invoke(new StringSink(), 42);
        } catch (InvocationTargetException exception) {
            System.out.println("cause: "
                    + exception.getCause().getClass().getSimpleName());
        }
    }
}
```

Run with JDK 17+:

```bash
javac --release 17 BridgeMethodDemo.java
java BridgeMethodDemo
```

Output with `javac` and Java 17+:

```text
StringSink:
  accept(Object) -> void | bridge=true | synthetic=true
  accept(String) -> void | bridge=false | synthetic=false
Child:
  read() -> Integer | bridge=false | synthetic=false
  read() -> Number | bridge=true | synthetic=true
invoke accepted:
accept(String): hello
cause: ClassCastException
```

This example was compiled with `--release 17` and run on JDK 21; the stdout above matches line by line.

### 4.1. Analyzing `StringSink`

`getDeclaredMethods()` sees two `accept` methods:

1. `accept(String)`: the real source method written by the programmer; `isBridge() == false`.
2. `accept(Object)`: `javac`'s bridge to match the erased descriptor of `Sink<T>`; `isBridge() == true` and `isSynthetic() == true`.

Both can be looked up via Reflection using the appropriate parameter type list:

```java
Method source = StringSink.class.getDeclaredMethod("accept", String.class);
Method bridge = StringSink.class.getDeclaredMethod("accept", Object.class);
```

This lookup snippet is only illustrative, using the `StringSink` and `Method` types already declared/imported in the program above.

Sorting the methods with `Comparator` inside `inspect` is deliberate: **`Class.getDeclaredMethods()` does not guarantee result order**. Do not rely on the first array position to conclude which method is the bridge.

### 4.2. Analyzing `Child`

In `Child`, the name and parameter list do not distinguish the two `read()` methods. You must inspect `getReturnType()` and the bridge flag. The `read() -> Integer` method is the user-declared method; the `read() -> Number` method is the compiler-generated bridge to maintain linkage with the signature in `Parent`.

Do not naively "deduplicate" by *only* `method.getName()` or name plus parameter list when analyzing JVM methods: doing so can merge the bridge with the source method by mistake and lose important descriptor or return-type information.

### 4.3. Why does `ClassCastException` appear?

Calling:

```java
bridge.invoke(new StringSink(), "hello");
```

is valid because the bridge's runtime parameter is `Object`; inside the bridge, the `String` value casts successfully and is forwarded to `accept(String)`.

Conversely, `bridge.invoke(new StringSink(), 42)` still passes Reflection's `Object` parameter check, yet the bridge bytecode must cast `Integer` to `String`. The cast fails; `Method.invoke` wraps the exception thrown by the invoked method inside `InvocationTargetException`. Therefore the `catch` block retrieves `exception.getCause()` and prints `ClassCastException`.

This is also why **you should not infer that invoking a bridge via Reflection will be type-safe in the same way as calling a generic method in compiled Java source code**.

## 5. Inspecting bytecode: verifying the `ACC_BRIDGE` flag

After compiling `BridgeMethodDemo.java`, run:

```bash
javap -p -c -v 'BridgeMethodDemo$StringSink'
javap -p -c -v 'BridgeMethodDemo$Child'
```

The example commands use single quotes to protect the `$` character in the nested class's binary name when running in shells like PowerShell or Bash. Read the method descriptions and look for:

- `descriptor: (Ljava/lang/Object;)V` for `accept(Object)`.
- `flags: ... ACC_BRIDGE, ACC_SYNTHETIC` on the bridge generated by `javac`.
- The cast instruction `checkcast java/lang/String` inside the bridge and the subsequent call to `accept:(Ljava/lang/String;)V`.
- For `Child`, the method returning `Number` is marked bridge, and then forwards to the method returning `Integer`.

The `javap` command serves **compilation verification**, not a mandatory step when writing Reflection applications. When querying a `Method` object, `isBridge()` is more readable and less dependent on bit representation details.

Note on compilers: the Java language specifies overriding compatibility, while details of how a compiler generates bridges, the ordering of methods in a class file, and additional synthetic flags may vary across compilers or bytecode transformation tools. Therefore, do not bake assumptions like "every synthetic method is a bridge" or "each class has at most one bridge" into general-purpose code.

## 6. Choosing methods when scanning with Reflection

### 6.1. Displaying only user-declared APIs

When generating documentation or a readable method table from `getDeclaredMethods()`, you usually want to display only the primary methods and filter out bridge forwarding paths:

```java
Method[] visibleMethods = Arrays.stream(type.getDeclaredMethods())
        .filter(method -> !method.isBridge())
        .toArray(Method[]::new);
```

This is an **illustrative snippet**, assuming a `Class<?> type` variable and imports for `Method` and `Arrays`; it is not a standalone program. If the goal also requires excluding *other* compiler-generated methods, you can add `!method.isSynthetic()`, though you must consider whether your application wants to keep synthetic methods.

There is no single filter right for every framework. Bytecode analysis tools, debuggers, compilers, AOP, dynamic invocation models, or override resolution may **need to keep bridges** to understand the actual dispatch path.

### 6.2. Needing to execute or map a runtime method

Do not assume every bridge has only a single target method easily inferred by name. To map a bridge to a business method, you may have to examine:

- The declaring class and superclass/interface hierarchy, not just `getDeclaredMethods()` on one class.
- Parameter lists, return types, and generic type variables after erasure.
- Overriding rules, visibility, candidate methods, and covariant return relationships.
- The compiler or bytecode generation/transformation library, when applicable.

**Decision examples by goal:**

| Need | How to handle bridges |
| --- | --- |
| Generating documentation for author-declared APIs | Usually hide `isBridge() == true` to avoid duplicate entries. |
| Inspecting compilation/JVM output | Keep bridges and display flags alongside descriptors. |
| Finding methods for annotation processing | Identify source/target methods and annotation policy before filtering. |
| Checking override compatibility or dispatch paths | Treat bridges as important data. |
| Invoking methods via `Method.invoke` | Check the signature of the chosen method and exceptions that may arise inside the bridge. |

### 6.3. `getDeclaredMethods()` vs `getMethods()`

`getDeclaredMethods()` is convenient for observing bridges **generated directly in the inspected class**, including non-public methods. `getMethods()` returns only visible public methods, including inherited methods, so its scope differs and can make it less obvious where a method was declared.

If you need to distinguish a subclass's bridge from an inherited method, check `method.getDeclaringClass()` and analyze the class/interface hierarchy. Do not assume every `Method` returned by `getMethods()` was declared in the queried class itself.

## 7. Common misconceptions

**Misconception 1 — "A bridge is an ordinary user-defined overload."** A bridge usually has no separate source declaration. It is an artifact to preserve overriding at runtime; seeing two entry points in Reflection does not prove the programmer intentionally created that overload.

**Misconception 2 — "Only generics produce bridges."** Generic erasure is a very common case, yet the `Child.read()` example shows covariant returns can also produce bridges.

**Misconception 3 — "`isSynthetic()` is the same as `isBridge()`."** In `javac`-generated bytecode in the example, the bridge is also synthetic. However, synthetic covers methods generated by the compiler for other purposes. Query `isBridge()` when you specifically need to know about bridges.

**Misconception 4 — "A bridge's modifiers will show a bridge label."** `Modifier.toString(method.getModifiers())` is not an appropriate API to interpret `ACC_BRIDGE`. The JVM bridge bit can share a numeric bit value with a flag that means something else on another member kind. Use `Method.isBridge()` or inspect with `javap -v`.

**Misconception 5 — "Matching only name and parameters finds the right method."** A covariant-return bridge may differ only in return type in its descriptor. You must examine `getReturnType()`, the bridge flag, and the declaring origin.

**Misconception 6 — "`Method.invoke` through a bridge is always as type-safe as calling the concrete-typed source method."** Reflection accepts arguments based on the observed runtime signature. A bridge can perform a cast internally and throw `ClassCastException` from within, as in the `accept(Object)` example.

**Misconception 7 — "Every compiler emits the exact same set of methods."** Presence, number of bridges, synthetic flags, and exact bytecode depend on type relationships and how the compiler emits code. Tooling should inspect actual metadata rather than hardcoding method counts.

## 9. Key takeaways

- A **bridge method** is a compiler-generated forwarding method to maintain overriding/linkage compatibility at the bytecode level, especially with generic erasure and covariant returns.
- **`Method.isBridge()`** is the standard Reflection way to identify a method carrying the bridge flag.
- **`isSynthetic()` is not synonymous with `isBridge()`**; the two concepts serve different purposes.
- **`getDeclaredMethods()` can return both source methods and bridges**; always check flags before generating documentation or selecting methods.
- **The dispatch path can still cast and throw exceptions**; this is observable via `Method.invoke` and `InvocationTargetException`.
- **Whether to filter bridges depends on the goal**: API display usually filters them out, while JVM/override analysis usually keeps them.
