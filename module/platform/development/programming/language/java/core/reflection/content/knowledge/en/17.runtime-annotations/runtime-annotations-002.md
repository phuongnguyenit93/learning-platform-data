# Retention SOURCE, CLASS, RUNTIME and Annotation Visibility Limits in Java

## 1. What question does Retention answer?

Annotations add metadata to declarations or type-use sites in Java code. However, **not every annotation that appears in source code still exists at runtime**, and having an annotation in a class file does not necessarily mean standard Reflection can read it.

`java.lang.annotation.RetentionPolicy` specifies **how long the compiler must retain an annotation**. An annotation type is declared with the `@Retention(...)` meta-annotation:

~~~java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

@Retention(RetentionPolicy.RUNTIME)
@interface Audit {
}
~~~

In this example, places marked with `@Audit` will be stored in the class file in a form observable by Reflection at runtime. If `@Retention` is not declared on an annotation type, **the default is `RetentionPolicy.CLASS`**, not `RUNTIME`.

There are three policies:

| Policy | In source code | In class file generated by `javac` | Standard Reflection at runtime |
| --- | --- | --- | --- |
| `SOURCE` | Yes | Annotation not kept at the use site | Not found |
| `CLASS` | Yes | Yes, but JVM is not required to preserve it for Reflection visibility | Not found through standard `getAnnotation` |
| `RUNTIME` | Yes | Yes, as runtime-visible metadata | Can be found when querying the **right object/location** and the right API |

**Important:** “`RUNTIME`” is a **necessary condition** for Java Reflection to read an annotation from a class file, but it does not guarantee that every `getAnnotation` call will return it. You must consider whether the annotation is placed on a class, method, field, parameter, record component, or **TYPE_USE** site, and whether the API is querying that exact location.

## 2. The roles of `@Retention` and `@Target` are different

The two meta-annotations answer two different questions:

- `@Retention`: up to which stage does the annotation survive?
- `@Target`: what kinds of locations is the annotation allowed to be placed on? For example, `TYPE`, `METHOD`, `FIELD`, `PARAMETER`, `CONSTRUCTOR`, `TYPE_USE`, `TYPE_PARAMETER`, or `ANNOTATION_TYPE`.

Example:

~~~java
import java.lang.annotation.*;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface RunMe {}

class Jobs {
    @RunMe
    public void run() {}
}
~~~

`RunMe` is only allowed on methods and can be read by Reflection via `Jobs.class.getDeclaredMethod("run").getAnnotation(RunMe.class)`. However, `Jobs.class.getAnnotation(RunMe.class)` is not meant to search for annotations located on methods, so its result will be `null`.

You must not assume that `@Retention(RUNTIME)` means the annotation **automatically appears on every Reflection API related to the class**.

## 3. Standalone Java 17+ example: the three retention levels

Create the file **`RetentionDemo.java`** with the following full contents:

~~~java
import java.lang.annotation.*;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
@interface SourceMark {}

@Retention(RetentionPolicy.CLASS)
@Target(ElementType.TYPE)
@interface ClassMark {}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface RuntimeMark {
    String value();
}

@SourceMark
@ClassMark
@RuntimeMark("ready")
class Service {}

@Inherited
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface InheritedFlag {}

@InheritedFlag
class Parent {}

class Child extends Parent {}

public class RetentionDemo {
    public static void main(String[] args) {
        System.out.println("source found: "
                + Service.class.isAnnotationPresent(SourceMark.class));
        System.out.println("class found: "
                + Service.class.isAnnotationPresent(ClassMark.class));
        System.out.println("runtime found: "
                + Service.class.isAnnotationPresent(RuntimeMark.class));
        System.out.println("runtime value: "
                + Service.class.getAnnotation(RuntimeMark.class).value());
        System.out.println("declared annotation count: "
                + Service.class.getDeclaredAnnotations().length);

        System.out.println("Child declared inherited: "
                + (Child.class.getDeclaredAnnotation(InheritedFlag.class) != null));
        System.out.println("Child inherited lookup: "
                + (Child.class.getAnnotation(InheritedFlag.class) != null));
        System.out.println("SourceMark policy: "
                + SourceMark.class.getAnnotation(Retention.class).value());
    }
}
~~~

From the directory containing that file, run:

~~~bash
javac --release 17 RetentionDemo.java
java RetentionDemo
~~~

Exact stdout, verified by compiling with Java 17 and running the program:

~~~text
source found: false
class found: false
runtime found: true
runtime value: ready
declared annotation count: 1
Child declared inherited: false
Child inherited lookup: true
SourceMark policy: SOURCE
~~~

**Explanation:**

1. `Service` is annotated with all three annotations in source code. Reflection only sees `RuntimeMark` because it is retained with `RUNTIME`. `getDeclaredAnnotations().length` equals `1`, not `3`.
2. `SourceMark` is not present in the class file of `Service` generated by the compiler under the `SOURCE` policy.
3. `ClassMark` still has metadata in the class file, but `Class.getAnnotation(ClassMark.class)` does not return it because the annotation lacks runtime visibility.
4. `RuntimeMark("ready")` has a `value()` element. Once `RuntimeMark` is retrieved via Reflection, `value()` can be called to obtain `"ready"`.
5. `Child.class.getDeclaredAnnotation(InheritedFlag.class)` returns `null` because `Child` does not declare the annotation directly. `Child.class.getAnnotation(InheritedFlag.class)` finds the annotation **inherited under `@Inherited` rules** from `Parent`.
6. `SourceMark.class.getAnnotation(Retention.class).value()` outputs `SOURCE`, because here we read the **`@Retention` meta-annotation on the `SourceMark` annotation type itself**, not the `@SourceMark` usage on `Service`. These are two different queried objects.

The code uses `@Inherited` to further illustrate visibility limits: retention allows an annotation to be present, while whether a query considers inherited declarations is an orthogonal axis.

## 4. Bytecode comparison: where does CLASS differ from SOURCE?

After compiling the file in section 3, you can inspect the class file:

~~~bash
javap -v -p Service
~~~

In the annotation section of the `javap -v` output, you will see two main groups:

~~~text
RuntimeVisibleAnnotations:
    RuntimeMark(
        value="ready"
    )
RuntimeInvisibleAnnotations:
    ClassMark
~~~

This is an **abridged excerpt** from `javap` output, keeping only the lines that show retention groups; the actual output also contains the constant pool, encoded type names, constant indices, and other metadata.

- `RuntimeVisibleAnnotations` contains `RuntimeMark`, corresponding to the `RUNTIME` policy.
- `RuntimeInvisibleAnnotations` contains `ClassMark`, corresponding to the `CLASS` policy. The word “invisible” here refers to **runtime Reflection**, not that class-file-reading tools cannot inspect it.
- There is no usage of `SourceMark` on `Service` in the class file's annotation metadata. A source annotation can be seen by an **annotation processor** during compilation even though it is not kept in the class file afterward.

**Caution regarding inspection methods:** `javap -v` reads class file data; `Class.getAnnotation(...)` uses Reflection in the running JVM. The two tools serve different stages. Seeing `ClassMark` in `javap` **does not contradict** `getAnnotation(ClassMark.class) == null`.

For bytecode that has passed through other compilers, processors, or class-file manipulation tools, actual metadata may vary. The retention table describes standard Java behavior when the compiler follows language rules, and does not allow assuming the same for any class file modified by external tools.

## 5. SOURCE: still useful even though Reflection cannot see it

`RetentionPolicy.SOURCE` suits annotations that have value **at compile time** and do not need to enter the running application. An annotation processor can access source elements during compilation using `javax.annotation.processing` and the `javax.lang.model` model.

Typical use cases:

- Checking source rules or linting at compile time.
- Generating source code, metadata, or documentation from annotations at compile time.
- Signaling the compiler or build tools without needing runtime usage.

Example:

~~~java
import java.lang.annotation.*;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
@interface GenerateAdapter {}

@GenerateAdapter
class CustomerDto {}
~~~

This is an **illustrative annotation and class snippet**, without `main` and producing no output on its own. If an annotation processor is configured to process `GenerateAdapter`, it can see the annotation during compilation; however, after compilation, `CustomerDto.class.getAnnotation(GenerateAdapter.class)` still returns `null`.

**Do not confuse two statements:**

1. “A `SOURCE` annotation does not exist at runtime in normally compiled classes” — true.
2. “A `SOURCE` annotation never has any effect” — false: it can influence analysis and code generation at compile time.

A `SOURCE` annotation type does not trigger code generation by itself. There must be a compiler/plugin/annotation processor or corresponding tool actually processing it.

## 6. CLASS: present in the class file but not visible to standard Reflection

`RetentionPolicy.CLASS` is intended for metadata that needs to be stored in the class file without needing the VM to make it available through standard Reflection APIs. It is the **default if `@Retention` is omitted** on an annotation type.

Example:

~~~java
import java.lang.annotation.*;

@Target(ElementType.TYPE)
@interface BytecodeTag {}  // Default RetentionPolicy.CLASS

@BytecodeTag
class AnnotatedClass {}
~~~

The snippet above is illustrative code without `main`. `BytecodeTag` will be stored at its usage on `AnnotatedClass` in a normal class file, but `AnnotatedClass.class.getAnnotation(BytecodeTag.class)` will not detect that annotation at runtime.

A bytecode analyzer/instrumenter can **read the class file directly** and interpret `CLASS` annotations using a bytecode analysis library (or `javap` for manual inspection). This is completely different from Reflection having access to find that annotation in the JVM.

Questions to ask when choosing retention:

- Is the metadata only needed up to compile time? Choose `SOURCE`.
- Does the metadata need to be read by bytecode tooling, without needing runtime Reflection? You can choose `CLASS`.
- Does the application or framework need to query the annotation on classes, methods, fields, etc. at runtime? Choose `RUNTIME` and identify the exact query location.

## 7. RUNTIME: necessary, but you must ask in the right place

A `RUNTIME` annotation can be observed according to **where the annotation is attached**, but Reflection has multiple corresponding objects:

| Where is the annotation attached? | Commonly used Reflection API |
| --- | --- |
| Class/interface | `SomeClass.class.getAnnotation(...)` or `getDeclaredAnnotations()` |
| Method | `Method.getAnnotation(...)`, `Method.getDeclaredAnnotations()` |
| Field | `Field.getAnnotation(...)`, `Field.getDeclaredAnnotations()` |
| Constructor | `Constructor.getAnnotation(...)` |
| Parameter declaration | `Parameter.getAnnotation(...)` via `Executable.getParameters()` |
| Type use (generic argument, array component, return type...) | Forms of `AnnotatedType`, e.g., `Field.getAnnotatedType()` or `Method.getAnnotatedReturnType()` |
| Record component | `RecordComponent.getAnnotation(...)` or `getAnnotatedType()` depending on target |

Method example:

~~~java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Handler {}

class Controller {
    @Handler
    public void run() {}
}
~~~

This code requires `import java.lang.annotation.*`; it is an illustrative declaration snippet without `main`. For the method declared on `Controller`:

~~~java
boolean present = Controller.class
        .getDeclaredMethod("run")
        .isAnnotationPresent(Handler.class);
~~~

The snippet above is an illustrative expression inside a method that handles `NoSuchMethodException`. The result is `true` because it queries the right **`Method`**, not `Controller.class`.

### TYPE_USE is not always an annotation of a field declaration

An annotation marking a generic type argument such as `List<@NonNull String>` is attached to **the use site of type `String`**. With `@Target(TYPE_USE)`, you should not assume calling `Field.getAnnotation(NonNull.class)` will find it; you must traverse the field's `AnnotatedType` and its type arguments.

Section 9 provides a runnable example of this scenario.

## 8. @Inherited and annotation inheritance scope

`@Inherited` is a special meta-annotation, yet it **does not automatically make annotations appear on methods/fields or interfaces of a subclass**.

Basic rules:

- Only meaningful for annotations on a **class declaration** queried via the inheritance mechanism applicable to classes; it does not make interface annotations automatically propagate to classes implementing the interface.
- `getAnnotation(...)` and `getAnnotations()` can see `@Inherited` annotations from a superclass if the subclass does not declare an annotation of that kind in the corresponding way.
- `getDeclaredAnnotation(...)` and `getDeclaredAnnotations()` only inspect annotations directly present on the class being examined, excluding inherited annotations.
- If the subclass declares a matching annotation of the same kind, its direct annotation is used according to query rules.
- `@Inherited` does not solve the issue of an annotation having `SOURCE` or `CLASS` retention making it invisible to runtime Reflection: querying at runtime still requires `RUNTIME`.

The program in section 3 illustrates this exact difference: `Child.class.getDeclaredAnnotation(InheritedFlag.class)` returns `null`, whereas `Child.class.getAnnotation(InheritedFlag.class)` is non-`null`.

When a framework scans interfaces, methods, fields, or override hierarchies on its own, it may define rules to **search the inheritance tree itself** beyond default Java Reflection; do not confuse custom framework behavior with `@Inherited`.

## 9. Repeatable annotations and TYPE_USE: standalone extended example

Save the entire following program to **`RetentionExtraDemo.java`**:

~~~java
import java.lang.annotation.*;
import java.lang.reflect.*;
import java.util.List;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@Repeatable(Tags.class)
@interface Tag {
    String value();
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface Tags {
    Tag[] value();
}

@Tag("a")
@Tag("b")
class Tagged {}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE_USE)
@interface TypeUseMark {}

class TypeSample {
    List<@TypeUseMark String> names;
}

public class RetentionExtraDemo {
    public static void main(String[] args) throws Exception {
        System.out.println("direct tag count: "
                + (Tagged.class.getAnnotation(Tag.class) == null ? 0 : 1));
        System.out.println("by type count: "
                + Tagged.class.getAnnotationsByType(Tag.class).length);
        System.out.println("container present: "
                + (Tagged.class.getDeclaredAnnotation(Tags.class) != null));

        Field field = TypeSample.class.getDeclaredField("names");
        AnnotatedParameterizedType t =
                (AnnotatedParameterizedType) field.getAnnotatedType();

        System.out.println("field declaration marked: "
                + field.isAnnotationPresent(TypeUseMark.class));
        System.out.println("type argument marked: "
                + t.getAnnotatedActualTypeArguments()[0]
                        .isAnnotationPresent(TypeUseMark.class));
    }
}
~~~

Compile/run:

~~~bash
javac --release 17 RetentionExtraDemo.java
java RetentionExtraDemo
~~~

Verified stdout:

~~~text
direct tag count: 0
by type count: 2
container present: true
field declaration marked: false
type argument marked: true
~~~

**This illustrates two distinct limits:**

1. `@Tag` is a **repeatable annotation**. When used twice on a class, the compiler stores the container annotation `@Tags` at the appropriate location. `getAnnotation(Tag.class)` does not necessarily return either `Tag`; use `getAnnotationsByType(Tag.class)` to retrieve both. In the example, the container appears in `getDeclaredAnnotation(Tags.class)`.
2. `@TypeUseMark` sits on the type argument `String` in `List<@TypeUseMark String>`. `Field.isAnnotationPresent(TypeUseMark.class)` returns `false` because the field declaration is not annotated under that target. However, via `AnnotatedParameterizedType.getAnnotatedActualTypeArguments()[0]`, Reflection reads the annotation at the type argument location.

For repeatable annotations, both the containing annotation and the repeatable child annotation must declare compatible `@Retention`/`@Target`. Marking only one of them as `RUNTIME` is not sufficient for runtime to reliably recover the repeated annotation list.

In addition, be careful to distinguish `getAnnotationsByType(...)` (which can account for direct and indirect annotations via container) from `getDeclaredAnnotationsByType(...)` (only annotations related to the current declaration site; does not traverse superclass inheritance). Choose the API matching your goal.

## 10. Retention is not synonymous with a guarantee to observe everything

Some common diagnostic questions:

**“I used `@Retention(RUNTIME)` yet `getAnnotation()` still returns `null`.”**

Check in order: whether the annotation is attached to the right class/method/field/parameter or TYPE_USE; whether `getAnnotation` is called on the right `AnnotatedElement`; whether a repeatable annotation container is involved; whether `@Inherited` is mistakenly relied on across interfaces or method overrides; and whether the annotation is actually present in the loaded class file.

**“`javap -v` sees the annotation while Java Reflection does not find it.”**

Check whether the annotation is under `RuntimeInvisibleAnnotations` (`CLASS` policy), or in another section such as `RuntimeVisibleTypeAnnotations`. If it is `CLASS`, the difference is by design. If it is TYPE_USE, use `AnnotatedType` at the right location.

**“A `SOURCE` annotation cannot be found at runtime, so an annotation processor cannot use it.”**

False. An annotation processor works at compile time and uses the source/language model; it does not need `Class.getAnnotation`. Retention scope and tool execution scope are two separate matters.

**“Seeing an annotation type that has `@Retention(SOURCE)` at runtime means SOURCE annotations are still runtime-visible.”**

False. You can read `@Retention` **on the annotation type itself**, because the `Retention` meta-annotation is itself retained at runtime. That **does not turn usages of the SOURCE annotation on other targets into runtime-visible metadata**.

**“CLASS and RUNTIME retention are the same because both are in `.class`.”**

False: the class file separates visible/invisible attributes; runtime Reflection only exposes information defined as runtime-visible through the appropriate APIs.
