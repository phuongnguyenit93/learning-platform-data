# Candidate Lists by Language, Script, Region, and Variant

## 1. The Problem: One Translation Has Multiple Levels of Specificity

A Java application often has multiple resource files, for example:

```text
Messages.properties
Messages_en.properties
Messages_en_US.properties
Messages_en_Latn.properties
Messages_en_Latn_US.properties
Messages_en_Latn_US_POSIX.properties
```

If a user requests the locale `en-Latn-US-POSIX` but the application does not yet have an exact-match bundle, Java must determine **which bundles can substitute and in what order to try them**. That is the purpose of **candidate locales** in the `java.util.ResourceBundle` mechanism.

Lesson objectives:

- Understand the roles and ordering of **language, script, region/country, and variant** when looking up a `ResourceBundle`.
- Inspect the list generated by `ResourceBundle.Control.getCandidateLocales(...)` and convert each candidate into a bundle name.
- Recognize the two important branches when a script is present: prioritizing the **with-script** branch first, then trying the **without-script** branch.
- Distinguish between the **candidate list**, the **bundles that actually exist**, **per-key parent-chain fallback**, and **fallback to the JVM default locale**.
- Know Java's special cases, such as script inference for Chinese, multi-part variants, Norwegian codes, and ignoring Unicode extensions when building the candidate list.

This topic belongs to the **Fallback chain** group, focusing on the resource bundle lookup process. Candidates do not mean that all locales in the list are installed or have translations.

## 2. `Locale` Components Related to the Candidate List

Consider a common BCP 47 tag:

```text
en-Latn-US-POSIX
│  │    │  │
│  │    │  └── variant
│  │    └───── region / country
│  └────────── script
└───────────── language
```

| Component | API in `Locale` | Example | Meaning |
| --- | --- | --- | --- |
| Language (L) | `getLanguage()` | `en`, `vi`, `sr` | Language |
| Script (S) | `getScript()` | `Latn`, `Cyrl`, `Hant` | Writing system / script |
| Region / country (C) | `getCountry()` | `US`, `VN`, `TW` | Territory / region |
| Variant (V) | `getVariant()` | `POSIX`, `rozaj_biske` | Specific variant |
| Extension | `getExtension(...)` or Unicode extension API | `u-nu-thai` | Extension information; does not participate in the default candidate list |

The order of components in a BCP 47 tag does not mean simply removing subtags one by one for fallback. Java has its own rule: **if a script is present, after trying the branch with the script, it retries the branch containing only language + country + variant (without the script)**.

Traditional `.properties` filenames use underscores (`_`), whereas BCP 47 tags use hyphens (`-`). For example, the tag `sr-Latn-RS` corresponds to a candidate named `Messages_sr_Latn_RS.properties`. Do not pass a filename with a `.properties` suffix into `Locale.forLanguageTag`.

## 3. Standard Rule Without a Script

For a locale with language, country, and variant populated, but an **empty script**, the default candidate list order is:

```text
[L, C, V]  ->  [L, C]  ->  [L]  ->  ROOT
```

Example `en-US-POSIX`:

```text
en-US-POSIX  -> Messages_en_US_POSIX.properties
en-US        -> Messages_en_US.properties
en           -> Messages_en.properties
ROOT         -> Messages.properties
```

If the request only has `en-US`, candidates with a variant are omitted; if it only has `en`, only `en` and `ROOT` remain. **Candidates whose trailing component is empty are skipped**; Java does not need to generate a bundle name like `Messages_en_.properties`.

`Locale.ROOT` is the locale object with empty language/script/country/variant. In the bundle mechanism, it represents the **root bundle without a locale suffix**, such as `Messages.properties`. `Locale.ROOT.toString()` returns an empty string, so when debugging you should explicitly label it `ROOT` to avoid mistaking it for a missing element.

When variant and region are absent, think of prioritization going from specific to general, but **do not assume `en-US` automatically falls back to `en-GB`**: `en-GB` is a different regional branch and is not on the default candidate path for `en-US`.

## 4. Rule When a Script Is Present: Two Clear Branches

For a locale consisting of language (L), script (S), country (C), and variant (V), the default list is:

```text
[L, S, C, V]
      ↓
[L, S, C]
      ↓
[L, S]
      ↓
[L, C, V]    ← retry with script removed, keeping region and variant
      ↓
[L, C]
      ↓
[L]
      ↓
ROOT
```

Example `en-Latn-US-POSIX`, taking `Messages` as the base name:

| Order | Candidate locale | Corresponding bundle filename |
| --- | --- | --- |
| 1 | `en-Latn-US-POSIX` | `Messages_en_Latn_US_POSIX.properties` |
| 2 | `en-Latn-US` | `Messages_en_Latn_US.properties` |
| 3 | `en-Latn` | `Messages_en_Latn.properties` |
| 4 | `en-US-POSIX` | `Messages_en_US_POSIX.properties` |
| 5 | `en-US` | `Messages_en_US.properties` |
| 6 | `en` | `Messages_en.properties` |
| 7 | `ROOT` | `Messages.properties` |

Notice the fourth position: Java does not jump straight from `en-Latn` to `en`. It **restores region/variant on the non-script branch**. Therefore, a general US bundle like `Messages_en_US.properties` can be used if Latin-script-specific resources are missing.

For `sr-Latn-RS`, the list is:

```text
sr-Latn-RS
sr-Latn
sr-RS
sr
ROOT
```

The `sr-RS` branch can be useful when an application has Serbian resources for Serbia without yet splitting Latin and Cyrillic scripts. **This is how Java looks up candidates**, which does not mean Cyrillic and Latin content can always safely substitute for each other; the application must decide which resource sets should actually exist.

## 5. Multi-Part Variants: Trimming from Right to Left

`Locale.getVariant()` can contain multiple parts separated by `_`. For example, parsing BCP 47 `sl-rozaj-biske` produces language `sl` and a two-part variant `rozaj`, `biske`. When generating the candidate list, Java tries the **full variant**, then the **shortened variant**, before dropping the variant completely:

```text
sl-rozaj-biske  -> Messages_sl__rozaj_biske.properties
sl-rozaj        -> Messages_sl__rozaj.properties
sl              -> Messages_sl.properties
ROOT            -> Messages.properties
```

Why does the filename have **two underscores** between `sl` and `rozaj`? Because the region position in the `toBundleName` convention is empty, while the variant is still present. The fact that `Locale.forLanguageTag("sl-rozaj-biske").toLanguageTag()` uses `-` **does not change** Java's bundle naming convention with `_`.

When multiple components are present at the same time, suppose the variant consists of `V1_V2`, and script and region are also present:

```text
L_S_C_V1_V2
L_S_C_V1
L_S_C
L_S
L_C_V1_V2
L_C_V1
L_C
L
ROOT
```

Both branches prioritize the full variant version first and then shorten it. **Not every variant string is valid BCP 47:** `Locale` instances created from legacy constructors may contain variants following legacy rules. When creating new data, prefer `Locale.Builder` or `Locale.forLanguageTag` with valid tags.

## 6. Java 17+: Printing Exact Candidates and Bundle Names

The following snippet runs standalone on the classpath with JDK 17+. It uses `ResourceBundle.Control` with the default format list to **observe the algorithm**, without needing actual `Messages.properties` files.

Create `CandidateLocalesDemo.java`:

```java
import java.util.List;
import java.util.Locale;
import java.util.ResourceBundle;

public class CandidateLocalesDemo {
    private static final ResourceBundle.Control CONTROL =
            ResourceBundle.Control.getControl(
                    ResourceBundle.Control.FORMAT_DEFAULT);

    private static void show(String tag) {
        Locale requested = Locale.forLanguageTag(tag);
        List<Locale> candidates =
                CONTROL.getCandidateLocales("Messages", requested);

        System.out.println(tag + ":");
        for (Locale candidate : candidates) {
            String display = candidate.equals(Locale.ROOT)
                    ? "ROOT"
                    : candidate.toLanguageTag();
            String bundleName =
                    CONTROL.toBundleName("Messages", candidate);
            System.out.println("  " + display
                    + " -> " + bundleName + ".properties");
        }
    }

    public static void main(String[] args) {
        show("en-Latn-US-POSIX");
        show("zh-TW");
        show("sl-rozaj-biske");
    }
}
```

Compile and run:

```bash
javac CandidateLocalesDemo.java
java CandidateLocalesDemo
```

Output on a standard JDK:

```text
en-Latn-US-POSIX:
  en-Latn-US-POSIX -> Messages_en_Latn_US_POSIX.properties
  en-Latn-US -> Messages_en_Latn_US.properties
  en-Latn -> Messages_en_Latn.properties
  en-US-POSIX -> Messages_en_US_POSIX.properties
  en-US -> Messages_en_US.properties
  en -> Messages_en.properties
  ROOT -> Messages.properties
zh-TW:
  zh-Hant-TW -> Messages_zh_Hant_TW.properties
  zh-Hant -> Messages_zh_Hant.properties
  zh-TW -> Messages_zh_TW.properties
  zh -> Messages_zh.properties
  ROOT -> Messages.properties
sl-rozaj-biske:
  sl-rozaj-biske -> Messages_sl__rozaj_biske.properties
  sl-rozaj -> Messages_sl__rozaj.properties
  sl -> Messages_sl.properties
  ROOT -> Messages.properties
```

`getCandidateLocales` returns `Locale` objects, not filenames. `toBundleName` turns each candidate into an underscore-delimited bundle name; in the example, `.properties` is appended to illustrate one possible file format. `FORMAT_DEFAULT` also allows `java.class`; a single candidate name can match a class bundle or a properties bundle, and the format search order also affects which bundle is actually loaded.

This API provides clear observation of the algorithm in a **classpath/unnamed module** application. In Java applications packaged as a **named module**, certain `ResourceBundle.getBundle` overloads taking `Control` are not supported the way they are on the classpath; follow module/service provider rules for resource bundles instead. The example above only calls `Control.getCandidateLocales` to illustrate the ordering, without needing to write a custom loader.

## 7. Important Exception: Script Can Be Inferred for Chinese

With language `zh` and an **empty script**, the default `ResourceBundle.Control` has a special rule:

- Region `CN` or `SG`: adds script `Hans` (Simplified).
- Region `TW`, `HK`, or `MO`: adds script `Hant` (Traditional).
- Other regions or no region: does not automatically add a script under this rule.

Therefore, `Locale.forLanguageTag("zh-TW")`, even though `getScript()` on the input locale is empty, produces the candidate list:

```text
zh-Hant-TW
zh-Hant
zh-TW
zh
ROOT
```

Similarly, `zh-CN` can produce:

```text
zh-Hans-CN
zh-Hans
zh-CN
zh
ROOT
```

This is a **special exception in the bundle selection algorithm**. It does not mean the `Locale.forLanguageTag("zh-TW")` object itself was modified to contain `Hant`, nor does it allow inferring scripts for any language from country codes. When predicting the actual fallback chain, rely on `getCandidateLocales` output rather than deducing mechanically from the BCP 47 tag.

## 8. Other Special Cases: Norwegian and Extensions

### 8.1. The `nn`, `nb`, and `no` Codes

Java has historical compatibility logic for Norwegian forms. For `nn-NO` (Nynorsk), the default candidate list includes some legacy `no` names as well:

```text
Messages_nn_NO
Messages_nn
Messages_no_NO_NY
Messages_no_NO
Messages_no
Messages
```

For `nb-NO` (Bokmål), the `nb` code and its historical synonym `no` are interleaved:

```text
Messages_nb_NO
Messages_no_NO
Messages_nb
Messages_no
Messages
```

This list exists for compatibility with existing resource names and must not be generalized into a rule that every language code has synonyms. In new systems, name resources consistently and verify against the exact target JDK.

### 8.2. Unicode Extensions Do Not Add Default Bundle Levels

For example:

```text
en-US-u-nu-thai
```

This has a Unicode extension requesting Thai digits (`nu=thai`), yet the default `ResourceBundle.Control` candidate list remains:

```text
en-US
en
ROOT
```

It does not generate `Messages_en_US_u_nu_thai.properties`. Extensions can matter for number/calendar formatters, but **are not used in default ResourceBundle naming rules**. If a resource set needs to differentiate content by extension, the application must design custom keys/lookups or an appropriate custom mechanism.

## 9. Candidate List Differs from Actual Bundle Resolution

Three related but distinct concepts:

1. **Candidate locale:** a locale Java *may* try. `getCandidateLocales` only generates the list based on rules; it does not read files to check whether a bundle exists.
2. **Selected resource bundle:** the bundle actually found according to search order and supported formats. If the first candidate has no file/class, Java proceeds to the next candidate.
3. **Parent chain / key fallback:** after selecting a bundle, `ResourceBundle.getString(key)` can retrieve a value from a parent bundle if the child bundle does not declare that key. This is different from automatically switching locales per key.

Suppose only these exist:

```text
Messages.properties             -> hello=Default
Messages_en.properties          -> hello=Hello; help=Help
Messages_en_Latn_US.properties  -> hello=Howdy
```

For the request `en-Latn-US-POSIX`, `Messages_en_Latn_US` is the first candidate that exists (since the `POSIX` bundle does not exist), so:

- `hello` comes from `Messages_en_Latn_US`: `Howdy`.
- `help` is absent in the specific bundle but exists in parent `Messages_en`: `Help`.
- A key present only in `Messages.properties` can be retrieved from the root parent, provided the parent chain fits.

The names and values above are **illustrative scenarios**, not existing files in the project. When evaluating runtime behavior, pay attention to classpath/modules, `Control`, caching, and whether a resource bundle sets its parent manually.

### What if Not Even a Specific Locale Has a Bundle?

Under the default `ResourceBundle.Control`, `getFallbackLocale(baseName, requestedLocale)` typically returns the **JVM default locale** if it differs from the requested locale, or `null` if they are equal. In a normal lookup, if only the root bundle is found, root may be **held back temporarily** to attempt fallback via the default locale before deciding to use root. Therefore:

- `getCandidateLocales("Messages", requested)` **does not include** the candidate sequence of the JVM default locale.
- `getBundle(...)` may try an additional **new candidate list pass** from the default locale if no suitable localized bundle is found for the requested locale.
- If a non-root bundle matching the requested locale exists, it is selected, and missing key lookups follow the parent chain rather than switching to another default language per key.

For example, the application requests `fr-CA`, but neither `Messages_fr_CA` nor `Messages_fr` exists; Java may try the default chain such as `en-US → en → ROOT` before returning root (if present) or throwing `MissingResourceException` (if no bundle is found). You cannot deduce the final result from the candidate list alone; you must know which bundles are present, the default environment, the loader, and the fallback policy.

**Do not call `Locale.setDefault(...)` per request to force fallback:** the default is JVM-wide shared state, and changing it between requests can cause conflicts. If a server needs a fixed fallback, the application should explicitly pick the locale/priority chain and pass it explicitly to the lookup call or implement a controlled resource lookup policy.

## 10. How to Predict Filenames and Troubleshoot Issues

To analyze a "file exists but Java isn't using it" issue:

1. **Verify the base name**: `Messages`, `com.example.i18n.Messages`, etc. The base name specifies the corresponding package path, not an arbitrary path to `.properties`.
2. **Verify the requested locale**: print `toLanguageTag()` and the getters `getLanguage()`, `getScript()`, `getCountry()`, `getVariant()`.
3. **Print the candidate list** using `ResourceBundle.Control.getCandidateLocales` when using default classpath rules.
4. **Print the corresponding bundle names** via `Control.toBundleName`. Do not guess script/variant placement or drop double `_` characters in filenames.
5. **Verify the file/class actually exists** in the right package and classpath/module path; pay attention to case sensitivity on the filesystem.
6. **Verify the default locale and fallback policy**, especially when only root or another language's bundle exists.
7. **Verify keys and the parent chain**. Bundle not found and key not found are two different errors.
8. **Watch out for `ResourceBundle` caching** right after updating resources: results can depend on loader/cache; when reloading is needed, use appropriate cache APIs in development environments.

Examples of common naming mistakes:

| Written name | Problem |
| --- | --- |
| `Messages_zh_TW_Hant.properties` | Wrong script/region order compared to `toBundleName`; Java may look for `Messages_zh_Hant_TW.properties` |
| `Messages_en-US.properties` | Uses tag hyphen `-` instead of `_` in the bundle name |
| `Messages_sl_rozaj_biske.properties` | Missing empty region slot when variant is present; by default `Messages_sl__rozaj_biske.properties` is needed |
| `Messages_en_US_u_nu_thai.properties` | Expects a Unicode extension to become a default candidate level |
| Creating only `Messages_en_GB` and requesting `en-US` | `en-GB` is not automatically a candidate for `en-US` |

## 11. Self-Check

1. For locale `en-US`, what are the candidates in order? **`en-US → en → ROOT`**.
2. For `sr-Latn-RS`, why does `sr-RS` appear after `sr-Latn`? **Java tries the script branch first, then the non-script branch while restoring region/variant**.
3. For `sl-rozaj-biske`, why does the bundle filename contain `sl__rozaj`? **Region is empty while variant is present; the bundle naming convention preserves this slot with a second `_`**.
4. Why does `zh-TW` generate candidate `zh-Hant-TW` even though the original tag has no `Hant`? **Special script-inference rule for Chinese by region**.
5. Can `getCandidateLocales` be treated as proof that all corresponding files exist? **No**; it only generates candidate names.
6. If `Messages_en` has `help` while `Messages_en_Latn_US` lacks that key, how is it resolved? **Looked up through the parent chain, potentially retrieving `help` from `Messages_en`**.
7. Does `en-US-u-nu-thai` have a dedicated candidate bundle for `nu-thai`? **Not under the default `Control`**.
8. When all bundles for the requested locale are missing, is the JVM default locale retry pass already inside `getCandidateLocales(requested)`? **No**; that is an additional fallback step in the `getBundle` process.
