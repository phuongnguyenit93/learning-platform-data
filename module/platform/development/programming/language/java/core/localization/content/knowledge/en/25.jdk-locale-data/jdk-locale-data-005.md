# Changes in Names, Symbols, Grouping Separators, or Whitespace After a JDK Upgrade

## 1. Why does text change solely from upgrading the JDK?

A Java application may make **zero source code changes**, continuing to use `Locale.FRANCE`, `NumberFormat`, and `DateTimeFormatter` just as before, yet generate different strings after a JDK upgrade. Language names, region names, month names, currency symbols, decimal separators, grouping separators, digit types, and **Unicode whitespace characters** can all be determined by the runtime's **locale data**.

For example, the same numeric value `1234567.89` can be presented differently depending on the locale:

```text
en-US: 1,234,567.89
de-DE: 1.234.567,89
fr-FR: 1 234 567,89
vi-VN: 1.234.567,89
```

In the `fr-FR` line of the example, the grouping separators look like spaces, but they are **U+202F NARROW NO-BREAK SPACE**, not U+0020 ASCII SPACE. Data on other runtimes/versions may use different characters; this illustrative table must not be treated as a stable contract across all JDK releases.

Existing translations in the project's `ResourceBundle` do not automatically change just because the JDK updates. The issue centers on text **generated by the JDK from locale data**, not every string in the application.

### Learning objectives

After this lesson, you will be able to:

1. Explain the relationship between **JDK, CLDR, locale providers, and data versions**.
2. Identify changes in **display names**, **currency symbols**, **number/date patterns**, **grouping separators**, and **Unicode whitespace**.
3. Understand why snapshot tests, legacy data parsers, searches, and string comparisons can break after an upgrade.
4. Use Java 17+ to **print code points** and capture a baseline snapshot of locale state before and after an upgrade.
5. Design **storage independent of display strings**; specify locale, currency, numbering system, and zone explicitly.
6. Distinguish between fixing **storage formats** and **allowing display data to evolve** with updated locale standards.
7. Plan migrations, regression testing, and JDK upgrade adoption without locking the entire application to legacy locale data.

## 2. Data source: CLDR is not all Java APIs

**CLDR** (Common Locale Data Repository), maintained by the Unicode Consortium, supplies localization conventions and translations, such as:

- language, territory, script names, and locale display items;
- weekday names, month names, day periods (AM/PM), and date/time formats;
- decimal numbers, percentages, currencies, symbols, patterns, and numbering systems;
- region-based rules such as first day of the week and minimum days in the first week;
- time presentation data and time zone names.

The JDK uses a **version** of CLDR data to implement many locale-sensitive APIs in `java.util`, `java.text`, and `java.time`. **A new major JDK release may bundle a newer CLDR version**, so output text changes are possible. Even with the same CLDR version, the selected provider and runtime configuration can affect results.

However, not every internationalization class pulls its full data directly from CLDR. According to Oracle JDK's Supported Locales page, `BreakIterator` and `Collator` data have separate limitations/sources, so do not claim "upgrading CLDR definitely changes every collation or word-breaking rule." Inspect each API individually.

### Historical examples of JDK and CLDR releases

According to JDK `LocaleServiceProvider` documentation:

| JDK Line | Bundled CLDR per Oracle docs |
| --- | --- |
| JDK 17 | CLDR 39 |
| JDK 18 | CLDR 39 |
| JDK 19 | CLDR 41 |
| JDK 20 | CLDR 42 |
| JDK 21 | CLDR 43 |
| JDK 22 | CLDR 44 |
| JDK 23 | CLDR 45 |

These are **historical reference milestones**, not a way to deduce the CLDR version of every future Java build. JDK vendors, update releases, backports, and locale providers can affect actual behavior. When verification is needed, consult the release notes/documentation of the **specific JDK build** deployed and run a probe on that exact runtime.

### Three notable transition milestones

1. **JDK 9:** CLDR became the default prioritized locale data source (JEP 252). Systems moving from Java 8 to Java 9+ may see formatted strings change even without API changes.
2. **JDK 21:** specifying the `JRE`/`COMPAT` legacy provider causes the runtime to emit a warning about planned removal.
3. **JDK 23:** the `JRE`/`COMPAT` legacy locale data provider **was removed**; adding that name to `java.locale.providers` no longer restores JDK 8 formatting.

Therefore, the advice "if something breaks, just add `-Djava.locale.providers=COMPAT`" only worked on certain older releases and is not a long-term migration strategy for JDK 23+.

## 3. Locale providers and startup configuration

An application can obtain locale data from providers:

| Provider | Role | Things to note |
| --- | --- | --- |
| `CLDR` | CLDR data bundled with the JDK | Default in modern JDKs |
| `HOST` | Certain OS settings/languages, if supported by the platform | Unavailable on some runtimes; varies across machines |
| `SPI` | Data supplied by applications/libraries via service-provider interfaces | Requires designing and registering a provider |
| `COMPAT`/`JRE` | Legacy Java 8-compatible locale data | **No longer provided starting in JDK 23** |

Provider priority can be selected via the system property:

```bash
java -Djava.locale.providers=CLDR -cp . LocaleDataProbe
java -Djava.locale.providers=HOST,CLDR -cp . LocaleDataProbe
```

These two commands are meant to **compare providers when the HOST provider is supported**; they do not guarantee different outputs. For modular applications, the classpath/module path and packaging may differ.

**Key takeaway:** `java.locale.providers` should be set on the **JVM startup command**; APIs read/cache the provider configuration during initialization. Calling `System.setProperty("java.locale.providers", ...)` while the program is already running is neither a safe nor guaranteed way to switch providers.

Do not confuse `java.locale.providers` with `user.language`, `user.country`, or `Locale.setDefault(...)`. One selects the **locale data source**, while the others affect the **default locale**. Mutating the JVM-wide default locale per HTTP request can also cause race conditions; pass `Locale` explicitly to formatters.

## 4. Types of text that can change

### 4.1. Language, country, and script names

APIs such as:

```java
locale.getDisplayLanguage(displayLocale);
locale.getDisplayCountry(displayLocale);
locale.getDisplayScript(displayLocale);
locale.getDisplayName(displayLocale);
```

read localized names. Spelling, punctuation, capitalization, accepted political/geographic names, and terminology can be updated with CLDR. A change may affect the **translated wording**, not the `Locale`'s identity value.

Example:

```text
Locale.forLanguageTag("de-DE") → tag remains de-DE
English display name           → may be German / Germany by component
German display name            → may be Deutsch / Deutschland by component
```

**Never use `getDisplayName()` as a data key.** BCP 47 language tags or domain-contract country codes are appropriate as identifiers, while display names are strictly for UI presentation. Language selector lists should store tag/code values; display names can update per runtime and product decisions.

### 4.2. Month names, weekdays, and day periods

`DateTimeFormatter.ofLocalizedDate(...)`, `ofLocalizedTime(...)`, `DateFormat`, and `DateFormatSymbols` can depend on locale data. A newer release may change abbreviated month names, delimiters, field order, whitespace, or 12/24-hour time patterns.

For instance, the Oracle Migration Guide documents that `Locale.UK` formatted medium dates in the legacy style `19-Mar-2024` in JDK 8, whereas CLDR data in JDK 9 used `19 Mar 2024`. A single hyphen changing to a space is enough to break snapshot tests or parsers built around a fixed pattern.

This is a **historical example documented by Oracle**, not a claim that every locale or every date changes in that exact manner.

### 4.3. Numbers and decimal/grouping separators

`NumberFormat` and `DecimalFormatSymbols` select characters by locale:

- `getDecimalSeparator()`: decimal point/comma symbol.
- `getGroupingSeparator()`: grouping separator.
- `getZeroDigit()`: representative zero character of the numbering system.
- `getNumberInstance`, `getPercentInstance`, and `getCurrencyInstance` factories use various patterns/variants.

There is no universal rule that "a comma is a decimal separator." In `en-US`, `1,234.50` typically uses `,` for grouping; in `de-DE`, `1.234,50` typically means the same value. In `ar-EG`, digit characters and grouping marks can differ entirely from Latin.

### 4.4. Unicode whitespace

Several characters look similar yet have **different code points**:

| Character | Unicode Code | Name | Notes |
| --- | --- | --- | --- |
| ` ` | U+0020 | SPACE | ASCII space |
| ` ` | U+00A0 | NO-BREAK SPACE (NBSP) | Disallows line wrapping at this space |
| ` ` | U+202F | NARROW NO-BREAK SPACE (NNBSP) | Narrow, non-breaking whitespace |
| ` ` | U+2009 | THIN SPACE | Thin space, not identical to the above |

If testers only look at the UI or text diffs that hide invisible characters, they may assume two strings are equal, yet `String.equals` still returns `false`. `replace(" ", "")` only handles **U+0020**, missing other Unicode spaces; attempting to replace all whitespace can also break **line-wrapping rules and numeric meaning**.

### 4.5. Currency symbols

`Currency.getInstance("USD").getCurrencyCode()` is the ISO currency code, whereas `getSymbol(locale)` is a **display string that can depend on locale/provider**. Sometimes a short symbol cannot distinguish multiple dollar currencies; display formatting may change to a prefixed form or alter whitespace.

Never store symbols like `$`/`€` as currency identifiers. Store the **currency code** and **schema-defined decimal value**, then use `NumberFormat.getCurrencyInstance(locale)` for display, calling `setCurrency(currency)` when the transaction currency differs from the locale's default. Fractional digits, currency rounding, and patterns must also obey domain rules rather than being inferred solely from visible symbols.

## 5. Java 17+ example: probing numbers, symbols, and Unicode code points

A reliable way to investigate after an upgrade is to **print the code point of every character** rather than only printing visible strings. Create `LocaleDataProbe.java`:

```java
import java.text.DecimalFormatSymbols;
import java.text.NumberFormat;
import java.util.Locale;

public class LocaleDataProbe {
    static String codePoint(char ch) {
        return String.format(Locale.ROOT, "U+%04X", (int) ch);
    }

    static String codePoints(String s) {
        return s.codePoints()
                .mapToObj(cp -> String.format(
                        Locale.ROOT, "U+%04X", cp))
                .toList().toString();
    }

    static void inspect(String tag) {
        Locale locale = Locale.forLanguageTag(tag);
        DecimalFormatSymbols symbols =
                DecimalFormatSymbols.getInstance(locale);
        NumberFormat formatter = NumberFormat.getNumberInstance(locale);
        formatter.setMinimumFractionDigits(2);
        formatter.setMaximumFractionDigits(2);

        String value = formatter.format(1234567.89);
        System.out.println("[" + tag + "]");
        System.out.println("decimal: "
                + codePoint(symbols.getDecimalSeparator()));
        System.out.println("group: "
                + codePoint(symbols.getGroupingSeparator()));
        System.out.println("zero: "
                + codePoint(symbols.getZeroDigit()));
        System.out.println("number code points: " + codePoints(value));
    }

    public static void main(String[] args) {
        System.out.println("java: " + Runtime.version());
        System.out.println("providers: " + System.getProperty(
                "java.locale.providers", "<default>"));

        for (String tag : new String[] {
                "en-US", "de-DE", "fr-FR", "ru-RU",
                "vi-VN", "ar-EG"
        }) {
            inspect(tag);
        }
    }
}
```

Run:

```bash
javac -encoding UTF-8 LocaleDataProbe.java
java -Djava.locale.providers=CLDR LocaleDataProbe
```

**Reference** results observed on a tested JDK 24 using CLDR (version/properties depend on runtime):

| Locale | Decimal | Group | Zero digit |
| --- | --- | --- | --- |
| `en-US` | U+002E | U+002C | U+0030 |
| `de-DE` | U+002C | U+002E | U+0030 |
| `fr-FR` | U+002C | **U+202F** | U+0030 |
| `ru-RU` | U+002C | **U+00A0** | U+0030 |
| `vi-VN` | U+002C | U+002E | U+0030 |
| `ar-EG` | U+066B | U+066C | U+0660 |

This is **not an immutable table across all JDKs**: the entire purpose of the probe is to let you run it on **old and new JDKs** and compare actual outputs. Here `NumberFormat` sets two fraction digits so test outputs are easy to compare, not because every locale enforces two digits.

For `fr-FR`, the string `1234567.89` on the reference runtime produces the code points:

```text
[U+0031, U+202F, U+0032, U+0033, U+0034, U+202F,
 U+0035, U+0036, U+0037, U+002C, U+0038, U+0039]
```

Here U+202F appears twice and U+002C is the decimal separator. When a bug report says "the space changed," attach a **code point trace**, Java version, provider, locale tag, and actual formatted snippet—do not send only a screenshot.

## 6. Example of AM/PM whitespace changing on JDK upgrade

A real documented case: **JDK 20** integrated CLDR 42, in which date/time patterns for several locales changed the **space before the day period (AM/PM)** from standard U+0020 to **U+202F**. Spring Framework also noted that this change could cause applications parsing/formatting dates and times with default patterns to fail or diverge from snapshots.

Two strings can look almost identical:

```text
"8:30 PM"   — between 30 and PM is U+0020
"8:30 PM"   — between 30 and PM is U+202F
```

Do not claim every locale/JDK prints the exact pattern `8:30 PM`: **the testing point is the separator character code**, not a single global fixed format. Day names, AM/PM markers, and spelling also depend on the locale/pattern.

### Why is this failure dangerous?

- Application parsers using pattern literals with U+0020 will not inherently treat it as equivalent to U+202F in every case.
- Code storing localized date/time strings and parsing them after an upgrade may throw `DateTimeParseException`.
- A unit test `assertEquals("8:30 PM", actual)` can fail even though users still see reasonable text.
- HTML, screens, and PDFs may handle **line breaking differently**, since U+202F is non-breaking.
- Systems receiving input from older mobile clients may get U+0020 while newer versions emit U+202F; you cannot simply "re-format with the new JDK" and assume it matches raw historical input.

**Do not fix this by globally replacing every U+202F with U+0020 across the whole application.** For French text, numbers, and names/currencies, non-breaking spacing can be an important linguistic rule. Separate places needing a **legacy-compatible input parser** from places needing a **renderer displaying current locale conventions**.

## 7. Parsing old data: look-alike characters do not guarantee equality

If a locale parser expects U+202F as the grouping separator while previously stored input uses ASCII space, it may:

- fail to parse right from the start;
- parse **only part of the string** and discard the remainder;
- return an unintended number;
- or accept it under some provider, depending on parser/version.

Because `NumberFormat.parse(String)` can accept a **prefix**, a non-`null` result is not enough to prove the input is valid.

### Java 17+ example: checking full-string consumption

Create `GroupingParseProbe.java`:

```java
import java.text.NumberFormat;
import java.text.ParsePosition;
import java.util.Locale;

public class GroupingParseProbe {
    static String codes(String s) {
        return s.codePoints()
                .mapToObj(cp -> String.format(
                        Locale.ROOT, "U+%04X", cp))
                .toList().toString();
    }

    static void parseAll(NumberFormat format, String text) {
        ParsePosition at = new ParsePosition(0);
        Number value = format.parse(text, at);
        boolean consumed = value != null
                && at.getIndex() == text.length();

        System.out.println("input: " + codes(text));
        System.out.println("parsed: " + value);
        System.out.println("consumed: " + at.getIndex()
                + "/" + text.length());
        System.out.println("full input: " + consumed);
    }

    public static void main(String[] args) {
        Locale france = Locale.FRANCE;
        NumberFormat format = NumberFormat.getNumberInstance(france);

        String current = format.format(1234567.89);
        System.out.println("runtime format: " + codes(current));
        parseAll(format, current);

        // Simulate input where the grouping separator was replaced with an ASCII SPACE.
        String changed = current.replace('\u202F', ' ');
        parseAll(format, changed);
    }
}
```

```bash
javac -encoding UTF-8 GroupingParseProbe.java
java -Djava.locale.providers=CLDR GroupingParseProbe
```

On the reference runtime where `fr-FR` grouping is U+202F, testing shows `changed` is parsed only up to the first digit:

```text
runtime format: [U+0031, U+202F, U+0032, U+0033, U+0034, U+202F, U+0035, U+0036, U+0037, U+002C, U+0038, U+0039]
input: [U+0031, U+202F, U+0032, U+0033, U+0034, U+202F, U+0035, U+0036, U+0037, U+002C, U+0038, U+0039]
parsed: 1234567.89
consumed: 12/12
full input: true
input: [U+0031, U+0020, U+0032, U+0033, U+0034, U+0020, U+0035, U+0036, U+0037, U+002C, U+0038, U+0039]
parsed: 1
consumed: 1/12
full input: false
```

This is a **reference result from a verified runtime**, not an API contract guaranteed across every JDK. If another provider uses U+00A0 or U+0020, `replace('\u202F', ' ')` may leave the string unchanged or the parser may behave differently. Retrieve the active separator from `DecimalFormatSymbols` and test real data.

**Very important:** even `full input: true` does not mean grouping positions are strictly valid; `DecimalFormat` can be lenient toward non-standard grouping. For monetary inputs, add syntactic validation, range checks, scale, and currency checks. Never use format/parse as your sole validator.

## 8. Language names and currency symbols: for display, not as keys

Keep retrievable codes more stable than localized strings:

```text
Stored data:
  locale tag = "de-DE"
  currency code = "EUR"

Display when locale is chosen:
  locale.getDisplayLanguage(...)
  currency.getSymbol(displayLocale)
```

Do not use `"Deutsch"` or `"€"` as primary/foreign keys: both depend on locale, provider, and system evolution. `"€"` is used across many countries, and `EUR` is what identifies the currency unit by standard.

### Java 17+ example: names and symbols by locale

File `NamesAndCurrencyProbe.java`:

```java
import java.util.Currency;
import java.util.Locale;

public class NamesAndCurrencyProbe {
    public static void main(String[] args) {
        Locale german = Locale.forLanguageTag("de-DE");
        Currency euro = Currency.getInstance("EUR");

        System.out.println("tag: " + german.toLanguageTag());
        System.out.println("code: " + euro.getCurrencyCode());
        System.out.println("language en: "
                + german.getDisplayLanguage(Locale.ENGLISH));
        System.out.println("language de: "
                + german.getDisplayLanguage(Locale.GERMAN));
        System.out.println("currency fr: "
                + euro.getSymbol(Locale.FRANCE));
    }
}
```

```bash
javac -encoding UTF-8 NamesAndCurrencyProbe.java
java -Djava.locale.providers=CLDR NamesAndCurrencyProbe
```

Example output on the reference runtime:

```text
tag: de-DE
code: EUR
language en: German
language de: Deutsch
currency fr: €
```

An upgrade may alter **display names or symbols**, whereas `toLanguageTag()` and `getCurrencyCode()` serve as **data codes**, not translated names. Because country, language, or currency codes themselves occasionally evolve over the years per standards, even code systems need domain and version governance—though they remain far superior to unschematized display strings.

### When are strictly immutable display names required?

If legal contracts, mandatory product labels, or signed reports demand fixed wording, **do not rely solely on the JVM's default CLDR**. Store names as managed translations inside application resources alongside content versioning. This requires its own translation review/update process; do not expect JDK upgrades to preserve old wording automatically.

## 9. Which Unicode characters cause the most issues?

| Type | Example | Symptom |
| --- | --- | --- |
| U+0020 vs U+202F | regular space vs narrow no-break space | Snapshot diffs, parser stops early |
| U+00A0 vs U+202F | two non-breaking spaces of different widths | Layout/PDF/test shifts |
| `,` vs `.` | grouping/decimal separators swap roles by locale | Wrong value or parse failure |
| U+066B/U+066C | Arabic separators | Latin parser fails on Arabic numbers |
| U+0030–U+0039 vs U+0660–U+0669 | Latin vs Arabic-Indic digits | Lookup, regex, width differences |
| Currency `$` vs coded/prefixed forms | Multiple regions share the same symbol | Currency ambiguity |
| Abbreviated month names | dot differences, updated names, spelling | Parser/snapshot errors |
| Hyphen `-` vs space in dates | short/medium pattern updates | Legacy inputs fail to parse |
| Text with bidi controls or no-break | mixed RTL/LTR | Visual ordering or line-wrapping changes |
| Updated country/language names | terminology updates | UI snapshots and search keys differ |

**Do not globally "normalize" all whitespace and symbols to ASCII.** Unicode NFC only addresses canonical equivalence; U+0020, U+00A0, and U+202F **are not semantically identical spaces** in all contexts.

## 10. Why do snapshot tests break easily after an upgrade?

Hardcoded tests like:

```java
assertEquals("1 234 567,89", actual);
```

can fail when CLDR changes the grouping separator to U+00A0 or U+202F. Another test might fail merely because a country name, month name, or currency symbol changed, while **the business logic remains correct**.

Yet some tests **need** to catch these changes: when an API outputs a display string in a format partners expect to follow a fixed pattern, a format change is a **contract break**. Thus you cannot solve every snapshot failure simply by deleting assertions.

### Categorizing tests by purpose

| Purpose | Appropriate assertion |
| --- | --- |
| Domain amount | Compare `BigDecimal.compareTo(...) == 0` or contract-specified scale |
| Current locale display | Verify runtime separators/locale metadata and proper rendering |
| Canonical exchange format | Assert exact contract, e.g., numeric field or canonical decimal string |
| UI snapshot | Run against pinned JDK/provider/font/locale and accept updates with review |
| Legacy parser | Test real pre-upgrade data, including both ASCII/Unicode spaces and old samples |
| Length/line breaking | Verify in the UI and text engine, not solely `String.length()` |
| Currency identity | Assert `Currency.getCurrencyCode()`, not isolated symbols |
| Display names | Assert product wording policy rather than arbitrary CLDR names |

**Ideal:** tests protecting semantics assert semantics; tests protecting presentation assert exact presentation and record **locale + provider/version**.

### Snapshots should record extra metadata

```text
java.runtime.version
java.vendor
java.locale.providers (or <default>)
Locale.toLanguageTag()
numbering system extension (u-nu if present)
zone ID, currency code, rounding mode
fixed input number/date
formatted output + Unicode code points
```

Do not infer the CLDR version from `java.version` using a hardcoded table inside the application. Consult the relevant release docs and **measure actual outputs**.

## 11. Check configuration before comparing two JDKs

Two runtimes can differ for many reasons besides CLDR:

1. **JDK vendor/build/update**: the same major version does not guarantee every component is identical.
2. **`java.locale.providers`**: CLDR/HOST/SPI, or legacy on supporting JDKs.
3. **`Locale` and Unicode extensions**: e.g., `en-US-u-nu-arab` differs from `en-US`.
4. **Default locale**: process/container/CI environments may use different locales, especially when omitting `Locale`.
5. **Currency**: formatters may pick the locale's default currency rather than the transaction currency.
6. **Time zone and tzdb**: name/offset/date-time shifts can also come from timezone data, **distinct from CLDR**.
7. **Font/UI renderer**: text looking different does not always mean the formatted string changed.
8. **Application resource bundles/custom SPI**: internal resources can override runtime presentation.
9. **Packaged modules**: slim `jlink` images may omit `jdk.localedata` or specific locales.
10. **System default charset**: starting in JDK 18, UTF-8 is the default charset under JEP 400; file encoding/decoding bugs can corrupt Unicode **independently** of locale data.

When outputs differ, isolate each factor instead of blaming every change on CLDR.

## 12. Storage strategy: never turn display strings into source data

An anti-pattern to avoid:

```java
// Do not store numbers long-term in a locale-formatted display form:
String stored = NumberFormat.getNumberInstance(userLocale)
        .format(amount);
```

After an upgrade, the newer runtime itself may fail to parse old strings accurately if separators or patterns changed. It is even more dangerous when the record's locale was not stored.

### Store schema-typed data

- Numbers: `BigDecimal`/DECIMAL column, or canonical decimal string with a dot and **no grouping** per contract.
- Dates/times: `Instant`/ISO offset timestamp; if regional timezone semantics matter, also store `ZoneId`.
- Currency: `amount + ISO 4217 currency code`; render symbols only per locale.
- Locale: BCP 47 tag like `vi-VN`, never translated display names.
- Country: domain code, not visible country name.
- Signed/approved text data: store the exact text/content version when verbatim preservation is required.

### Java 17+ example: domain vs. presentation

Create `CanonicalVsDisplayDemo.java`:

```java
import java.math.BigDecimal;
import java.text.NumberFormat;
import java.util.Locale;

public class CanonicalVsDisplayDemo {
    public static void main(String[] args) {
        BigDecimal amount = new BigDecimal("1234567.89");

        String canonical = amount.toPlainString();
        BigDecimal restored = new BigDecimal(canonical);

        NumberFormat france =
                NumberFormat.getNumberInstance(Locale.FRANCE);
        france.setMinimumFractionDigits(2);
        france.setMaximumFractionDigits(2);

        System.out.println("stored: " + canonical);
        System.out.println("restored equal: "
                + (amount.compareTo(restored) == 0));
        System.out.println("display codepoints: "
                + france.format(restored).codePoints()
                .mapToObj(cp -> String.format(
                        Locale.ROOT, "U+%04X", cp))
                .toList());
    }
}
```

```bash
javac CanonicalVsDisplayDemo.java
java CanonicalVsDisplayDemo
```

The **schema-stable** portion:

```text
stored: 1234567.89
restored equal: true
```

The `display codepoints` line may **vary by provider/JDK**; that is completely valid when the goal is purely displaying in the current locale. For `BigDecimal` values with **negative scale**, `toPlainString()` does not preserve every scale attribute upon reconstruction; if full round-tripping of `BigDecimal` across all scales is needed, use `toString()` or store `unscaledValue + scale` in your schema.

## 13. When you must support strings saved from older JDKs

If your data store currently holds numbers/dates as **display strings**, you cannot immediately switch all formats without accounting for legacy records.

A controlled migration plan:

1. **Inventory:** find all fields storing localized strings and their corresponding parse/format paths.
2. **Identify each record's source:** locale, JDK/provider/version if known; rely on metadata/data characteristics rather than arbitrary guessing.
3. **Define an explicit legacy parser:** support the exact legacy formats **confirmed to exist**, rather than accepting arbitrary variants without bounds.
4. **Validate full input:** `ParsePosition`, length limits, grouping marks, decimal precision, valid dates, and value bounds.
5. **Flag ambiguous cases:** `1,234` could be one thousand two hundred thirty-four or one point two three four; do not auto-decide when locale is missing.
6. **Normalize to domain values and the new schema:** decimal/date/time/currency code, retaining source traces per security policy.
7. **Audited backfill:** count successes, failures, ambiguities, and collisions before cutover.
8. **Temporary dual-read if needed:** prefer the new schema; invoke the legacy parser only for records tagged with legacy origin.
9. **Never use current data rules as the answer for history:** parsing old strings with a new JDK's default formatter can silently misinterpret values.
10. **Monitor production metrics:** parse errors by locale, legacy record share, backfill rates, and fallbacks.
11. **Establish a sunset policy:** once data migration finishes, remove the legacy parser in a controlled manner to avoid permanent permissiveness.

In some systems, accepting U+0020/U+00A0/U+202F when reading a numeric field can make sense **if** schema, locale, and grouping rules are strictly validated. Never globally swap one character for another across French/Arabic prose, personal names, or free-form text.

## 14. What to choose when truly immutable formatting is required

Not every output is permitted to evolve with locale data:

| Output type | Strategy |
| --- | --- |
| User-friendly UI | Use `NumberFormat`, `DateTimeFormatter`, and locale display names; accept standard-compliant updates |
| Schema-governed JSON/CSV interchange | Use explicit machine formats, independent of default locale |
| Published/signed reports | Store the issued snapshot or a versioned formatter policy |
| Legal documents and approved notices | Store approved translations under content governance |
| Legacy protocol parsers | Use fixed patterns and strict validation per published contract |
| Need legacy locale patterns on JDK 23+ | Consider custom formatters/patterns or a managed **SPI**; do not rely on removed `COMPAT` |

**Do not freeze grouping characters across the entire UI just because of an old snapshot.** CLDR updates to improve linguistic/regional accuracy; for user-facing displays, a standards-aligned change can be a welcome improvement. Lock outputs to old patterns only when a **genuine business requirement** exists and is documented.

If you construct a custom `DecimalFormat` with `DecimalFormatSymbols`, every explicitly set symbol/pattern may remain more stable, yet you **take on maintenance responsibility** when currency symbols, default decimals, or local conventions evolve. It is not a zero-cost choice.

## 15. `java.locale.providers` is not a universal compatibility cure-all

For example, on JDK 17–22 you could select legacy data:

```bash
java -Djava.locale.providers=COMPAT,CLDR MyApp
```

On **JDK 23 and later**, `COMPAT`/`JRE` has been removed; setting that name no longer restores old locale data. On modern JDKs, ways to preserve a contract include:

- passing **explicit patterns and symbols** to `DecimalFormat`/`DateTimeFormatter` when the contract is sufficiently specific;
- installing a custom `LocaleServiceProvider` via SPI if warranted by scope and scale;
- storing/exchanging **canonical values** instead of localized strings;
- building a bounded legacy parser for stored historical data;
- keeping UI translation sources separate and version-controlled.

The `java.locale.providers` property only prioritizes among **providers supported by the runtime**; it cannot reinstall a removed provider or guarantee identical data across every API.

## 16. Regression tests to run during an upgrade

### Minimal locale matrix

Select representative locales for your application:

- `en-US`: `,` and `.` separators, English with common dates/currencies.
- `de-DE`: grouping/decimal separators swapped relative to en-US.
- `fr-FR`: Unicode non-breaking spaces.
- `ru-RU`: may use NBSP or similar characters in number formatting.
- `vi-VN`: grouping/decimal marks, month names, and Vietnamese UI.
- `ar-EG`: Arabic-Indic digits and Arabic separators; RTL/BiDi testing.
- `ja-JP`: region name display and date/time formatting.
- `hi-IN`: test number/grouping patterns per provider if the product requires Indian formatting.

Results **must not be inferred manually from locale tags**; run probes and verify empirically.

### Input suite

| Group | Inputs to test |
| --- | --- |
| Decimals | `0`, `1.2`, `1234567.89`, negative numbers, many-digit numbers |
| Currency | USD, EUR, VND, and actual transaction currencies |
| Date/time | 12h AM/PM, 24h, long/short month names, timezones |
| Unicode whitespace | U+0020, U+00A0, U+202F |
| Decimal/grouping | Swapped commas/dots, valid/invalid grouping |
| Numbering | `latn`, `arab`, or supported extensions |
| Locale display | language/country/script names |
| Legacy data | Sample strings stored by the previous JDK version |
| Runtime | Old JDK, new JDK, default providers, and configured providers |

### Execution workflow

1. Pin **input values** and **locale tags** across both runtimes.
2. Run `LocaleDataProbe` on both and save Unicode code point outputs.
3. Run parser tests on **real data previously written by the old runtime**, not only newly generated data.
4. Classify diffs: **aligned with updated standards** vs. **contract break**.
5. Test UI layouts, especially non-breaking spaces, RTL, overflow, and font fallback.
6. Test integrated systems/DBs/caches if display strings were previously used as keys.
7. Run a canary release and monitor date/number parse errors post-deploy.
8. Review snapshot changes with i18n owners rather than bulk-updating golden files without understanding the diff.

## 17. Common mistakes

| Mistake | Risk | Solution |
| --- | --- | --- |
| Assuming JDK upgrades only alter JVM bytecode behavior | Locale display outputs can change | QA locale data / JDK behavior |
| Visually comparing whitespace strings | Misses U+0020/U+00A0/U+202F differences | Print Unicode code points |
| Using `replace(" ", "")` to strip grouping | Misses non-breaking spaces, corrupts text | Parse by locale + validate |
| Using `Locale.getDefault()` in multi-user servers | Output depends on JVM/environment | Pass `Locale` explicitly |
| Using `Currency.getSymbol` as a currency key | Symbols are neither unique nor stable | Use ISO currency codes |
| Storing `getDisplayLanguage()` as a language ID | Translated names can change | Store BCP 47 language tags |
| Storing `NumberFormat.format(amount)` for machine exchange | Provider upgrades break parsing | Store canonical decimals/numbers |
| Treating non-null `parse(String)` as full success | May have parsed only a prefix | Use `ParsePosition` and validation |
| Ignoring the Java 20 AM/PM U+202F risk | Snapshot/date parsers diverge | Inspect characters, separate legacy parser |
| Adding `COMPAT` to fix issues on JDK 23+ | Legacy provider was removed | Explicit patterns/SPI/canonical data |
| Using HOST across CI and production on different OSes | Inconsistent locale data | Pin providers or test explicitly |
| Treating one runtime's snapshot as universal truth | CLDR updates cause unnecessary test churn | Separate domain vs presentation tests |
| Replacing all Unicode spaces with ASCII | Loses non-breaking semantics | Apply per-field input policies |
| Assuming a jlink image contains every locale | Slim images can lack locale data | Check `jdk.localedata` and included locales |
| Not testing parsing of legacy JDK data | Migration breaks post-deploy | Golden legacy inputs + backfill |
| Regex-replacing `,`/`.` without a locale | Corrupts numeric values | Parse using the right locale/source |
| Blaming CLDR for charset/tzdb bugs | Fixes the wrong root cause | Distinguish data sources and runtime settings |

## 18. Self-check

1. **Why can identical date-formatting code return a different string on a newer JDK?** Because the JDK may ship a newer CLDR/provider/pattern.
2. **Which JDK enabled CLDR by default?** JDK 9, via JEP 252.
3. **From JDK 23 onward, can `COMPAT` still revert to legacy data?** No, that provider was removed.
4. **How does U+202F differ from U+0020?** It is a narrow no-break space with different line-breaking rules and a distinct character code.
5. **If `fr-FR` replaces U+202F with ASCII SPACE, will the parser definitely accept it?** No. Empirical testing may show it consumes only a prefix.
6. **Does `NumberFormat.parse(String)` guarantee the entire input was parsed?** No; use `ParsePosition` to verify.
7. **Why is `Locale.getDisplayLanguage()` unsuitable as a key?** Display names depend on the display locale and locale data.
8. **Why can `Currency.getSymbol()` not replace ISO currency codes?** Symbols can collide and change across locales.
9. **Should all U+202F occurrences be converted to U+0020?** No; non-breaking semantics may be important.
10. **Is a new CLDR version the only possible cause when output changes after an upgrade?** No; providers, default locale, tzdb, charset, and UI fonts can also differ.
11. **How should snapshots be compared?** Attach JDK/provider/locale metadata, print code points, and separate domain from presentation contracts.
12. **When a database stores `1 234,50`, should you simply parse it with the new JDK and overwrite?** No; identify the source locale/format, flag ambiguities, and validate before migrating.
13. **If an API returns typed numbers instead of localized strings, how does a JDK upgrade affect it?** Schema-based API representations stay stable; the UI can reformat per updated locales without altering values.
14. **Is changing `java.locale.providers` mid-program via `System.setProperty` safe?** Not guaranteed; configure it at launcher startup.
15. **If a country name changes in a new CLDR release, must ID data change?** Not automatically; UI display names and identity codes are separate concerns.
16. **When is there a valid reason to pin a fixed pattern?** When legal contracts, protocols, legacy parsers, or interchange systems mandate an exact format.
17. **When should updated locale display output be accepted?** When it is user-facing UI and the updated data reflects appropriate locale standards.
18. **What test detects invisible Unicode space differences?** Printing code points in `U+XXXX` form and testing full-input consumption with `ParsePosition`.
