# Record Accessors and Differences from JavaBeans Getters in Java

> **Module:** Java Core — Class/Object  
> **Knowledge Group:** Record  
> **Direct Topic:** Record accessors and differences from JavaBeans getters  
> **Version:** Java 17+ — records have been a standard feature since Java 16.

## 1. Quick Summary

For a Java record:

~~~java
record Person(String name, int age, boolean active) {
}
~~~

Java provides **record component accessor methods**:

~~~java
Person person = new Person("Lan", 22, true);

System.out.println(person.name());    // Lan
System.out.println(person.age());     // 22
System.out.println(person.active());  // true
~~~

The accessor name **matches the component name exactly**, without automatically adding a `get` or `is` prefix:

| Record component | Accessor provided by the record | Common JavaBeans-style getter |
| --- | --- | --- |
| `String name` | `name()` | `getName()` |
| `int age` | `age()` | `getAge()` |
| `boolean active` | `active()` | `isActive()` or `getActive()` |
| `Boolean verified` | `verified()` | Usually `getVerified()` |
| `List<String> tags` | `tags()` | `getTags()` |

**The accessors `name()`, `age()`, and `active()` are public instance methods implicitly declared by the record if you do not define them yourself.** They return the value of the corresponding component field according to record semantics. There is no need to write getters manually for basic cases.

Here are the key differences:

- A **record accessor** is part of the **Java language contract for record components**.
- A **JavaBeans getter** is a **method naming convention** on Java objects: `getX()` or `isX()` for boolean properties according to JavaBeans rules. It is not automatically generated by the Java compiler for each record component.
- A record can **add methods `getName()`/`isActive()`** for compatibility with JavaBeans-based libraries, but those are additional methods and do not replace the required component accessors.
- A JavaBeans getter can represent a computed property or a property without a field of the same name; a record component accessor is tightly bound to the component declaration and has its own signature rules.

Understanding this difference will help you call the right methods, design DTOs, use method references, integrate JSON/ORM/UI frameworks, write reflection code, and protect mutable data held inside a record.

## 2. What Is a Record Before Talking About Accessors?

A record declaration:

~~~java
record Point(int x, int y) {
}
~~~

declares a **record class** with two components `x` and `y`.

In Java 17, the compiler provides the corresponding members according to the rules of a record:

- Private final component fields `x` and `y`.
- A canonical constructor that accepts values for all components, if not explicitly declared.
- Public accessors `x()` and `y()`, if not explicitly written.
- `equals(Object)`, `hashCode()`, and `toString()` based on the record components, if not explicitly written.

A record class implicitly extends `java.lang.Record`, cannot extend a custom superclass, and is final. These belong to the record model, but **this lesson focuses on component accessors** rather than diving deep into the entire record lifecycle.

### 2.1. A Record Component Is More Than Just a Field

In:

~~~java
record OrderLine(String sku, int quantity) {
}
~~~

`sku` and `quantity` are **record components** in the declaration header. For each component, Java establishes a related group of parts consisting of a field, a canonical constructor parameter, and an accessor method according to the rules. Users should call `line.sku()`/`line.quantity()`, rather than trying to read private fields.

### 2.2. Why Are Accessors Different from Getters?

A record expresses “what components this data consists of” directly through its header. Therefore, the accessor carries the component name and does not need to be inferred from an external property naming convention. This is a transparent API for source code and record-specific reflection.

A traditional JavaBeans class is commonly written as:

~~~java
class CustomerBean {
    private String name;

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }
}
~~~

The getter `getName()` is a method written by a developer/tool following a convention. The Java compiler **does not automatically add getters/setters** just because there is a `name` field in a regular class.

### 2.3. Records Do Not Have Default Component Setters

With `record Point(int x, int y)`, calling `point.setX(9)` will not compile unless you write another `setX` method yourself. Component fields are final, so a record does not support regular setters to change component field values after construction.

You can create a **new** record with a different value, such as `new Point(9, point.y())`. This is the typical choice when modeling immutable value data.

## 3. Complete Program 1: Default Accessors

Create the file **`RecordAccessorBasicsDemo.java`**:

~~~java
public class RecordAccessorBasicsDemo {
    record Member(String name, int age, boolean active) {
    }

    public static void main(String[] args) {
        Member member = new Member("Lan", 22, true);

        System.out.println("name = " + member.name());
        System.out.println("age = " + member.age());
        System.out.println("active = " + member.active());
        System.out.println("record = " + member);
        System.out.println("identity = "
                + member.equals(new Member("Lan", 22, true)));
    }
}
~~~

Compile and run on JDK 17+:

~~~bash
javac -encoding UTF-8 RecordAccessorBasicsDemo.java
java RecordAccessorBasicsDemo
~~~

**Exact stdout:**

~~~text
name = Lan
age = 22
active = true
record = Member[name=Lan, age=22, active=true]
identity = true
~~~

### 3.1. Which Methods Exist?

`Member` has component accessors `name()`, `age()`, and `active()` without needing code in the body. They are public instance methods according to record rules.

### 3.2. Why Is There No `getName()`?

The header `record Member(String name,...)` **does not require the compiler to generate a JavaBeans-style `getName()`**. Calling `member.getName()` in the demo will not compile if the developer has not declared that method.

### 3.3. Why Does Another Record with Equal Data Return True for equals?

The record's default `equals` checks component field values according to record equality semantics. Two Member instances with the same name, age, and active are equal in value. `==` between two objects created by two `new Member(...)` calls is still false because they are two separate references.

### 3.4. Why Is the Record Name Member in toString?

The record's generated `toString` has a format consisting of the record class name and the component names/values; here `Member[name=Lan, age=22, active=true]`. Accessor names match the names of the components.

## 4. Signature and Scope of Implicit Accessors

With:

~~~java
public record Account(String id, long balance) {
}
~~~

(in a separate `Account.java` file if Account is a top-level public type), the accessors have the corresponding signatures:

~~~java
public String id()
public long balance()
~~~

These methods:

1. Are **instance methods**, not static methods.
2. Have **public** access, even though the record class itself may be package-private.
3. Accept no parameters.
4. Have a return type **of the exact type of the record component**.
5. Declare no type parameters of their own.
6. Do not declare a `throws` clause for the component accessor.
7. Can be **written explicitly** if intentional behavior is needed, but must follow the constraints.

### 4.1. Name and Type Must Match the Record Component

Component `String id` has accessor `String id()`. You cannot turn it into `Object id()` just because String is a subtype of Object, or `CharSequence id()` to narrow the API. The return type of the accessor must be **the exact same type** as the component (not merely compatible via covariance).

### 4.2. Access Level Cannot Be Lowered

If a record declares:

~~~java
record Item(String code) {
    String code() {
        return code;
    }
}
~~~

this **intentionally does not compile**: an explicit component accessor must be `public`; package-private is not sufficient.

Correct:

~~~java
record Item(String code) {
    public String code() {
        return code;
    }
}
~~~

### 4.3. Cannot Create a Static Accessor with the Same Signature

~~~java
record Item(String code) {
    public static String code() {
        return "X";
    }
}
~~~

**Intentionally does not compile**. A component requires an instance accessor; a static method with the same signature cannot fulfill the record accessor contract.

### 4.4. Cannot Declare Checked Exceptions from an Accessor

An explicit accessor like:

~~~java
record Data(String value) {
    public String value() throws java.io.IOException {
        return value;
    }
}
~~~

**Intentionally does not compile**: an explicit record component accessor must not declare a `throws` clause. This is a language constraint even when the method body does not actually throw an exception.

### 4.5. Cannot Genericize an Accessor

A component `String text` requires `String text()`. You cannot replace the accessor with a method of the form `<T> T text()` to return an arbitrary type. That is not a method signature corresponding to the component.

## 5. Boolean Accessors: `active()` Differs from `isActive()`

A very common practical difference:

~~~java
record Feature(boolean enabled, Boolean verified) {
}
~~~

The correct accessors are:

~~~java
feature.enabled();
feature.verified();
~~~

**Not**:

~~~java
feature.isEnabled();
feature.getVerified();
~~~

unless the developer provides those methods themselves.

### 5.1. JavaBeans Convention for Booleans

A JavaBeans getter typically takes the form `isEnabled()` if the property type is primitive `boolean`, or `getEnabled()` according to the corresponding convention. For the wrapper type `Boolean`, `getVerified()` is the common form.

Some libraries have their own options/naming strategies; do not assume that **every framework** supports only a single naming style.

### 5.2. Records Still Name Accessors After the Component

A record component `boolean isReady` will have the accessor `isReady()` because **the component name is actually `isReady`**, not because the compiler applies JavaBeans boolean naming. This is a pitfall that easily causes confusion:

~~~java
record State(boolean isReady) {
}
~~~

`state.isReady()` is the record component accessor. When reflecting using the JavaBeans convention, the property name inferred from a getter may differ from how record metadata defines the component; frameworks may have to handle the mapping.

Naming the component `ready` and using `ready()` is usually simpler if the domain model wants the data name to be ready.

### 5.3. Do Not Treat `is` as a Modifier in a Record Header

In `record State(boolean isReady)`, `isReady` is a normal Java identifier. The Java compiler does not automatically strip the `is` prefix to turn it into a component named `ready`.

## 6. JavaBeans Getters Are an API Convention

JavaBeans-style getters and setters are defined through naming/signature conventions in the JavaBeans ecosystem. A property named `firstName` is typically represented by:

~~~java
public String getFirstName()
public void setFirstName(String value)
~~~

A boolean property `active` can be read with `isActive()`:

~~~java
public boolean isActive()
~~~

Traditional JavaBeans tools typically discover property descriptors by analyzing public methods according to the convention.

### 6.1. A Getter Does Not Need to Correspond to a Field

A Bean can write:

~~~java
class RectangleBean {
    private int width;
    private int height;

    public int getArea() {
        return width * height;
    }
}
~~~

The method `getArea()` can be recognized as a **read-only property** named `area` even though the class has no `area` field. This is an important difference from a **record component**: a record component resides in the header and always has a corresponding state component.

### 6.2. A Read-Only Getter Does Not Necessarily Have a Setter

A JavaBeans-style property can be read-only. Not every property needs both a getter and a setter:

~~~java
public String getCode() {
    return code;
}
~~~

Libraries that handle mutable Beans may require a no-arg constructor and setters; read-only libraries may not. This is a framework/application requirement, not a mandatory rule of records.

### 6.3. JavaBeans Naming Has Edge Cases

For example, acronym names (`getURL()`) and `Introspector.decapitalize` have special naming behavior. `getURL()` can correspond to a property named `URL` rather than necessarily `uRL`. A record explicitly states the component name in its header, with no need to infer it from a getter method name.

### 6.4. Both Getters and Record Accessors Are Java Methods

These two styles do not differ in bytecode because one is “not a method”. Both `person.name()` and `bean.getName()` are instance method invocations in Java. The differences are **generation/signature rules**, metadata sources, and ecosystem conventions.

## 7. Complete Program 2: Bean vs. Record Method Calls

Create the file **`BeansVsRecordDemo.java`**:

~~~java
public class BeansVsRecordDemo {
    static final class CustomerBean {
        private String name;
        private boolean active;

        CustomerBean(String name, boolean active) {
            this.name = name;
            this.active = active;
        }

        public String getName() {
            return name;
        }

        public boolean isActive() {
            return active;
        }

        public void setName(String name) {
            this.name = name;
        }
    }

    record CustomerRecord(String name, boolean active) {
    }

    public static void main(String[] args) {
        CustomerBean bean = new CustomerBean("Mai", true);
        CustomerRecord record = new CustomerRecord("Mai", true);

        System.out.println("Bean name = " + bean.getName());
        System.out.println("Bean active = " + bean.isActive());
        System.out.println("Record name = " + record.name());
        System.out.println("Record active = " + record.active());

        bean.setName("An");
        System.out.println("Bean renamed = " + bean.getName());

        CustomerRecord changed = new CustomerRecord("An", record.active());
        System.out.println("New record = " + changed);
        System.out.println("Original record = " + record);
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 BeansVsRecordDemo.java
java BeansVsRecordDemo
~~~

**Exact stdout:**

~~~text
Bean name = Mai
Bean active = true
Record name = Mai
Record active = true
Bean renamed = An
New record = CustomerRecord[name=An, active=true]
Original record = CustomerRecord[name=Mai, active=true]
~~~

### 7.1. A Bean Can Mutate State After Construction

`bean.setName("An")` changes the name field of the same CustomerBean object.

### 7.2. Records Do Not Have Built-In Setters

`CustomerRecord` has final component fields, so the demo creates a new object `changed` to represent the new name, while the original `record` keeps "Mai".

### 7.3. Why Does the Naming Convention Not Determine Mutability?

JavaBeans can be read-only and records can contain nested mutable objects. The getter prefix itself does not make a class mutable; the component accessor name() itself does not make the entire object graph immutable either. Mutability comes from fields, referenced objects, constructors, and the API.

## 8. JavaBeans Introspection and Record Component Reflection Are Two Metadata Sources

Java 17 has record-specific reflection APIs:

~~~java
SomeRecord.class.isRecord()
SomeRecord.class.getRecordComponents()
~~~

With `java.lang.reflect.RecordComponent`, you can read:

- `getName()` — component name.
- `getType()` — runtime Class for the component type.
- `getGenericType()` — generic type information.
- `getAccessor()` — Method of the component accessor.
- Relevant annotations according to targets and rules.

Meanwhile, JavaBeans has:

~~~java
java.beans.Introspector.getBeanInfo(SomeClass.class)
~~~

and `PropertyDescriptor`s, with naming conventions `getX()`/`isX()`. For the Java 17 standard JavaBeans Introspector, **a bare record does not automatically appear as a set of JavaBeans properties solely because of its component methods `x()`**. Modern frameworks may have their **own record-aware handling**, so do not assume that any arbitrary library behaves identically to Introspector.

### 8.1. `Introspector.getBeanInfo(type, Object.class)`

Using `Object.class` as the stop class helps avoid inherited Object-level descriptors such as `class` in the output, making the properties with getters of the type under inspection clearly visible.

### 8.2. Record Reflection Does Not Depend on JavaBeans Getter Names

`RecordComponent.getAccessor()` returns the methods `name()`, `age()`, etc. Thanks to this, a record-aware framework can access components accurately according to the Java language model without needing to guess get/is prefixes.

### 8.3. Module Dependency to Keep in Mind

`java.beans` resides in the JDK's `java.desktop` module. With **named modules**, code using `java.beans.Introspector` needs to read the java.desktop module (`requires java.desktop;` in module-info.java if not already readable in the module graph). The record reflection APIs `java.lang.Class`/`java.lang.reflect.RecordComponent` belong to the standard Java platform.

## 9. Complete Program 3: JavaBeans Introspector vs. Record Reflection

Create the file **`BeanIntrospectionDemo.java`**:

~~~java
import java.beans.Introspector;
import java.beans.PropertyDescriptor;
import java.lang.reflect.RecordComponent;
import java.util.Arrays;
import java.util.List;

public class BeanIntrospectionDemo {
    public static final class BeanItem {
        private final String sku;
        private final boolean available;

        public BeanItem(String sku, boolean available) {
            this.sku = sku;
            this.available = available;
        }

        public String getSku() {
            return sku;
        }

        public boolean isAvailable() {
            return available;
        }
    }

    public record PlainRecord(String sku, boolean available) {
    }

    public record BridgedRecord(String sku, boolean available) {
        public String getSku() {
            return sku();
        }

        public boolean isAvailable() {
            return available();
        }
    }

    static List<String> beanProperties(Class<?> type) throws Exception {
        return Arrays.stream(Introspector.getBeanInfo(
                        type, Object.class).getPropertyDescriptors())
                .map(PropertyDescriptor::getName)
                .sorted()
                .toList();
    }

    static List<String> componentNames(Class<?> type) {
        RecordComponent[] components = type.getRecordComponents();
        if (components == null) {
            return List.of();
        }

        return Arrays.stream(components)
                .map(RecordComponent::getName)
                .toList();
    }

    public static void main(String[] args) throws Exception {
        System.out.println("Bean properties = "
                + beanProperties(BeanItem.class));
        System.out.println("Plain record properties = "
                + beanProperties(PlainRecord.class));
        System.out.println("Bridged record properties = "
                + beanProperties(BridgedRecord.class));
        System.out.println("Record components = "
                + componentNames(PlainRecord.class));
        System.out.println("Record accessor = "
                + PlainRecord.class.getRecordComponents()[0]
                        .getAccessor().getName());
    }
}
~~~

Compile/run with **JDK 17**:

~~~bash
javac -encoding UTF-8 BeanIntrospectionDemo.java
java BeanIntrospectionDemo
~~~

**Expected stdout on standard JDK 17:**

~~~text
Bean properties = [available, sku]
Plain record properties = []
Bridged record properties = [available, sku]
Record components = [sku, available]
Record accessor = sku
~~~

### 9.1. Why Are Plain Record Properties Empty?

`PlainRecord` has `sku()` and `available()` but does not have `getSku()` or `isAvailable()`. The JavaBeans Introspector following the JDK 17 convention does not interpret these component-named methods as JavaBeans getters.

### 9.2. Why Is the Bridged Record Recognized?

`BridgedRecord` explicitly declares `getSku()` and `isAvailable()`, so Introspector can find the JavaBeans properties according to the getter naming convention. The record still has the component accessors `sku()` and `available()` alongside them.

### 9.3. Why Is componentNames Correct for the Plain Record?

Record reflection reads record component metadata from the class file, without needing the JavaBeans getter convention. It returns the declaration order `[sku, available]`.

### 9.4. Limitations When Testing Real-World Frameworks

The `Introspector` output in the demo reflects the **standard JavaBeans API on Java 17**. Jackson, Spring, Jakarta frameworks, Hibernate, build-time mappers, or IDEs may use their own introspection, annotations, method handles, or record component APIs. To know whether a specific framework version supports records, you need to test integration with that exact framework and version; do not draw conclusions solely from Introspector.

## 10. Explicit Accessors in a Record: Allowed, but Must Follow the Contract

You can write an explicit accessor:

~~~java
record Greeting(String message) {
    public String message() {
        return message.trim();
    }
}
~~~

This `message()` replaces the default accessor implementation. It **does not** add a new component and **does not** change the `message` field that was already assigned by the canonical constructor.

Valid cases must ensure:

- The method is `public`.
- The method is not `static`.
- There are no parameters.
- The return type is exactly the component type.
- No type parameters/throws clause are declared.
- If you want to return the actual state, typically read the component field or a suitable representation.
- Differing from the field value must be designed intentionally because it can create discrepancies between the accessor and other auto-generated methods.

### 10.1. An Explicit Accessor Can Compute a Value

A record can be written as:

~~~java
record Person(String name) {
    public String name() {
        return name.toUpperCase(java.util.Locale.ROOT);
    }
}
~~~

This is a record declaration fragment. When calling `person.name()`, the result is uppercase; however, the **component field name** still holds the value assigned by the constructor, unless it was normalized in the constructor.

### 10.2. Do Not Confuse an Overridden Accessor with a Setter

The accessor still takes 0 parameters and returns the component type. It cannot modify the final component field after construction, even with custom code logic. A `withName(String)` method that creates a new record can be valid as a value update pattern.

### 10.3. Why Should You Not Overuse Transformations in Accessors?

A record is understood as a value composed of its components. If `name()` returns a value completely different from the component field, developers may be surprised when comparing `equals`/`hashCode`/`toString` against the accessor result. Typically, you should **normalize/validate in the canonical constructor**, so that the field and the accessor reflect a consistent state.

## 11. What Do Auto-Generated `equals()`, `hashCode()`, and `toString()` Look At?

This is a very important detail of Java records.

**The auto-generated implementations of `equals()`, `hashCode()`, and `toString()` are based on the component fields, and are not required to call custom accessor methods.** Therefore, if you manually write `String name()` returning a trimmed String while the field still contains spaces, the generated equality/toString still inspects the raw field value.

### 11.1. Example of Two Records with the Same Accessor Value That Are Not Equal

File **`RecordAccessorNormalizationDemo.java`**:

~~~java
public class RecordAccessorNormalizationDemo {
    record Raw(String text) {
        public String text() {
            return text.trim();
        }
    }

    record Normalized(String text) {
        Normalized {
            text = text.trim();
        }
    }

    public static void main(String[] args) {
        Raw rawA = new Raw(" A ");
        Raw rawB = new Raw("A");

        System.out.println("Raw accessor = " + rawA.text());
        System.out.println("Raw equal accessor values = "
                + rawA.text().equals(rawB.text()));
        System.out.println("Raw equals = " + rawA.equals(rawB));
        System.out.println("Raw toString = " + rawA);

        Normalized normalizedA = new Normalized(" A ");
        Normalized normalizedB = new Normalized("A");

        System.out.println("Normalized accessor = "
                + normalizedA.text());
        System.out.println("Normalized equals = "
                + normalizedA.equals(normalizedB));
        System.out.println("Normalized toString = " + normalizedA);
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 RecordAccessorNormalizationDemo.java
java RecordAccessorNormalizationDemo
~~~

**Exact stdout:**

~~~text
Raw accessor = A
Raw equal accessor values = true
Raw equals = false
Raw toString = Raw[text= A ]
Normalized accessor = A
Normalized equals = true
Normalized toString = Normalized[text=A]
~~~

### 11.2. Why Does the Raw Accessor Return A While equals Is False?

`Raw(" A ")` stores the `text` field with leading and trailing spaces, while the custom accessor only trims **when returning it**. `Raw("A")` stores a different text field. The generated equals compares the fields, so the two records are not equal.

### 11.3. Why Does toString Still Have Spaces?

The generated toString reads the state of the component fields; the custom accessor does not change the storage state. Therefore, `Raw[text= A ]` contains spaces just like the raw field.

### 11.4. Why Is a Compact Canonical Constructor Better for Normalization?

In `Normalized`, the compact constructor `Normalized { text = text.trim(); }` adjusts the constructor parameter before the canonical constructor assigns it to the final component field. As a result, the field actually holds "A". The default accessor, equals, and toString all reflect the normalized representation.

### 11.5. When Is a Custom Accessor Still Reasonable?

- Defensive copy of a mutable component.
- Returning a projection clearly specified in the API where differing from the field is accepted.
- Internally hiding a mutable representation per contract (though record equality/toString semantics must be considered).
- Adding specific behavior while keeping the exact record component type.

For mutable objects, make sure both the constructor and the accessor protect ownership, not just one side.

## 12. Records Are Shallowly Immutable, Not Deeply Immutable by Default

Record component fields are final, but **the referent of a reference-type field can still be mutable**.

For example:

~~~java
record Group(java.util.List<String> names) {
}
~~~

`Group.names()` returns the stored List reference. If the caller keeps an alias to an `ArrayList` and calls `add()`, the record can observe changes after construction. If the caller invokes `group.names().add(...)` and the List is mutable, they can also mutate the internal state.

Therefore, the statement “a record is immutable” needs these distinctions:

1. **The field reference cannot be reassigned after construction**.
2. **The object pointed to by the field may be mutable**.
3. Records do not automatically defensive-copy arrays/Lists/maps/nested objects.
4. Generated equals/hashCode may depend on mutable state or the identity of referenced objects.
5. A custom accessor can make a defensive copy, but does not automatically make deep nested state immutable.

### 12.1. `List.copyOf` for an Unmodifiable Structural Snapshot

A record with a List<String> can be written as:

~~~java
record Tags(java.util.List<String> values) {
    Tags {
        values = java.util.List.copyOf(values);
    }
}
~~~

After construction, the internal List is an unmodifiable structural snapshot according to the `List.copyOf` contract. If the source List is modified afterward, the record's List does not change (assuming immutable String elements). The default accessor `values()` returns the internal unmodifiable List; there is no need to copy it again each time.

### 12.2. What `List.copyOf` Does Not Do

- Does not accept null elements.
- Does not deep-copy mutable element objects.
- Does not automatically turn mutable objects held inside the List into immutable ones.
- May reuse a suitable immutable/unmodifiable input List instead of always allocating a new List.

When a record component contains mutable elements, consider immutable DTOs or defensive copying to the exact ownership depth needed.

### 12.3. Arrays Need Protection in Both the Constructor and the Accessor

A `byte[]` is a mutable object. If you only clone in the constructor while the accessor returns the field directly, the caller can mutate the record state from outside. If you only clone in the accessor while the constructor stores the original input array, the caller can still mutate the array via the initial alias.

You need **copy on input and copy on output** if you want to prevent external mutations.

## 13. Complete Program 5: Defensive Copies for Lists and Arrays

Create the file **`RecordDefensiveAccessorDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;
import java.util.Objects;

public class RecordDefensiveAccessorDemo {
    record Tags(String owner, List<String> values) {
        Tags {
            Objects.requireNonNull(owner);
            values = List.copyOf(values);
        }
    }

    record Packet(byte[] payload) {
        Packet {
            payload = Objects.requireNonNull(payload).clone();
        }

        public byte[] payload() {
            return payload.clone();
        }
    }

    public static void main(String[] args) {
        List<String> input = new ArrayList<>(List.of("A"));
        Tags tags = new Tags("Lan", input);

        input.add("B");
        System.out.println("Saved tags = " + tags.values());

        try {
            tags.values().add("C");
        } catch (UnsupportedOperationException ex) {
            System.out.println("Tags unmodifiable");
        }

        byte[] source = {1, 2};
        Packet packet = new Packet(source);
        source[0] = 9;

        System.out.println("After input mutation = "
                + Arrays.toString(packet.payload()));

        byte[] output = packet.payload();
        output[1] = 7;

        System.out.println("After accessor mutation = "
                + Arrays.toString(packet.payload()));

        Packet sameContents = new Packet(new byte[]{1, 2});
        System.out.println("Arrays equal by record equals = "
                + packet.equals(sameContents));
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 RecordDefensiveAccessorDemo.java
java RecordDefensiveAccessorDemo
~~~

**Exact stdout:**

~~~text
Saved tags = [A]
Tags unmodifiable
After input mutation = [1, 2]
After accessor mutation = [1, 2]
Arrays equal by record equals = false
~~~

### 13.1. Why Do Tags Not Change When Calling input.add?

The compact canonical constructor uses `List.copyOf(values)` to create a structural snapshot of the initial List. `input.add("B")` does not change the snapshot inside the record.

### 13.2. Why Does the `values()` Accessor Not Need to Be Overridden?

Inside Tags, an unmodifiable List<String> with immutable String elements is already stored for the demo's contract. Returning the same List via the default accessor is safe against external structural mutation.

### 13.3. Why Must Packet Override `payload()`?

`payload` is a mutable byte[]. The constructor already clones the input, but without cloning in the accessor, the caller could do `packet.payload()[0] = 9` and modify the internal array. A custom public `payload()` returns a clone so the caller only modifies the copy.

### 13.4. Why Do Two Packets with the Same Bytes Have equals Return False?

Generated equality for an array component uses **array reference equality**, rather than automatically using `Arrays.equals` by content. Two Packet constructors clone two different arrays; therefore, generated equals is false even when the bytes are identical.

If value semantics truly must rely on array contents, you need to design custom equality/hashCode according to the contract or switch to an appropriate immutable value representation. Simply customizing the accessor is not enough: generated equality still reads the raw fields.

### 13.5. Pitfall of Storing Mutable State and Hash-Based Collections

If a record holds a mutable List/Map/array and those fields are modified via an alias, the record's hashCode can change according to the nested object's hash behavior, causing bugs if the record is already a key in a HashMap. With arrays, the default hashCode typically follows reference identity rather than content; another surprise occurs there. Define value semantics and ownership before using a record as a key.

## 14. Why Should You Not Use Accessors to Mutate State?

A component field is final; a regular setter cannot change it. An accessor is designed to **read** a component value, not to update the record.

~~~java
record Point(int x, int y) {
    Point withX(int nextX) {
        return new Point(nextX, y);
    }
}
~~~

`withX` is a regular method that creates a **new record**. This is an appropriate choice for immutable value records.

Do not write a `public int x()` method with side effects just to turn “reading x” into an unexpected mutation. Even though Java allows arbitrary code in an explicit accessor, side-effecting logic makes debugging, caching, and equality very hard to understand.

### 14.1. If a Record Truly Needs Mutable Collaborators

For example, a component `AtomicInteger counter` allows mutating state inside the referent even though the record field is final. In that case, the record is no longer deeply immutable; concurrency/ownership semantics must be clearly stated. Avoid choosing a record just to reduce boilerplate if the domain concept is a mutable entity with a lifecycle and setters.

### 14.2. The Canonical Constructor Is a Good Place to Validate

~~~java
record Range(int start, int end) {
    Range {
        if (start > end) {
            throw new IllegalArgumentException("start > end");
        }
    }
}
~~~

After successful construction, the invariant `start <= end` always holds for the component fields. The default accessors return valid data without needing to re-validate on every read.

### 14.3. Do Not Confuse Constructor Normalization with Display Formatting

If you need to keep raw data for auditing while the UI wants a formatted version, keep the default accessor `rawName()` and add a `displayName()` method. You should not ambiguously change the meaning of the component `name()` if generated equality/toString still follow the raw field.

## 15. Adding JavaBeans-Style Getters to a Record When Truly Needed

A record can declare **extra methods** with JavaBeans names:

~~~java
record Product(String sku, boolean available) {
    public String getSku() {
        return sku();
    }

    public boolean isAvailable() {
        return available();
    }
}
~~~

This is a record declaration fragment. The compiler still provides `sku()` and `available()`. You add `getSku()`/`isAvailable()` so that a JavaBeans-style API/client can read the property according to convention.

### 15.1. This Is a Bridge, Not an Accessor Replacement

`getSku()` is not the component accessor of `sku`. If you write `getSku()` and omit `sku()`, the implicit `sku()` is still present. If you write a separate explicit `sku()`, it must obey the accessor constraints.

### 15.2. Setters Are Not Needed for Read-Only Bean Properties

`Product` cannot mutate component fields using setters after construction. Adding `getSku` can help tools **read** the property, but does not help frameworks that require writable setters or a no-arg constructor. Such frameworks may still not be able to use records unless they have record-specific support.

### 15.3. Avoid Unexpected Duplicate JSON Properties

A framework might detect record components via reflection while simultaneously detecting getX/isX methods via the JavaBeans convention. If you add bridge getters, it may see duplicate/differently named property paths, or apply annotations differently depending on the framework. You should test actual serialization/deserialization and configure appropriate naming/annotations; do not assume every framework will deduplicate correctly on its own.

### 15.4. When Should You Add a Bridge?

- Interfacing with a legacy component that requires a `getX()` method.
- Implementing an interface that already has a JavaBeans getter contract.
- A tool performs introspection strictly according to JavaBeans getter naming without supporting records.
- Maintaining compatibility when migrating an API from an ordinary class to a record, if the old behavior/signatures need to be preserved.

Conversely, if the entire codebase/mapper already supports records, avoid adding unnecessary getter boilerplate.

## 16. Complete Program 6: A Record Implementing Two Interface Naming Contracts

Create the file **`RecordInterfaceBridgeDemo.java`**:

~~~java
public class RecordInterfaceBridgeDemo {
    interface ComponentNamed {
        String name();
    }

    interface LegacyNamed {
        String getName();
    }

    record Member(String name)
            implements ComponentNamed, LegacyNamed {

        @Override
        public String getName() {
            return name();
        }
    }

    public static void main(String[] args) {
        Member member = new Member("Mai");

        ComponentNamed modern = member;
        LegacyNamed legacy = member;

        System.out.println("Component accessor = " + member.name());
        System.out.println("Modern interface = " + modern.name());
        System.out.println("Legacy interface = " + legacy.getName());
        System.out.println("Same object = " + (modern == legacy));
    }
}
~~~

Commands:

~~~bash
javac -encoding UTF-8 RecordInterfaceBridgeDemo.java
java RecordInterfaceBridgeDemo
~~~

**Exact stdout:**

~~~text
Component accessor = Mai
Modern interface = Mai
Legacy interface = Mai
Same object = true
~~~

### 16.1. A Record Accessor Can Implement an Interface Method

`Member.name()` is provided by the compiler and is public; it matches the `ComponentNamed.name()` method in the interface. There is no need to declare an explicit method just to implement this interface.

### 16.2. A JavaBeans-Style Interface Needs an Explicit Bridge

`LegacyNamed.getName()` does not match the component accessor `name()`. Therefore, Member explicitly declares `getName()` and uses `name()` to return the component value.

### 16.3. Why Are Two Interface References Still One Object?

`modern` and `legacy` both point to `member`. `modern == legacy` is true (the two references of interface types are related through the implementor; Java allows identity comparison in this case). Interface naming conventions do not create a new object.

## 17. Method References and Stream APIs Use Accessors Like Ordinary Methods

A record accessor is a zero-argument instance method, making it well-suited for method references:

~~~java
record User(String name, int age) {
}

java.util.function.Function<User, String> readName = User::name;
~~~

`User::name` is a reference to the `name()` accessor. It has the same name-reading semantics as the lambda `user -> user.name()`.

With a JavaBeans class, the method reference would be `CustomerBean::getName`.

### 17.1. Stream Mapping

~~~java
List<String> names = users.stream()
        .map(User::name)
        .toList();
~~~

Java knows `User::name` returns String, so the method reference matches `Function<User,String>`.

### 17.2. Sorting via Accessor

~~~java
users.stream()
        .sorted(Comparator.comparing(User::name))
        .toList();
~~~

The comparator uses the name values returned from the accessor. If the accessor has normalization or side effects, sorting behavior can differ from raw component fields, so you should design the accessor to be deterministic and appropriate.

### 17.3. Distinguishing from a Field Reference

Java has no source syntax `User::nameField` for an arbitrary field getter like a method reference. A record provides the `name()` method out of the box, so `User::name` can be used directly.

## 18. Complete Program 7: Accessor Method References

Create the file **`RecordMethodReferenceDemo.java`**:

~~~java
import java.util.Comparator;
import java.util.List;
import java.util.function.Function;

public class RecordMethodReferenceDemo {
    record User(String name, int age) {
    }

    public static void main(String[] args) {
        List<User> users = List.of(
                new User("Mai", 25),
                new User("An", 20));

        System.out.println("Reference = "
                + readName.apply(users.get(0)));

        System.out.println("Names = "
                + users.stream().map(User::name).toList());

        System.out.println("Sorted = "
                + users.stream()
                        .sorted(Comparator.comparing(User::name))
                        .map(User::name)
                        .toList());

        System.out.println("Ages = "
                + users.stream().map(User::age).toList());
    }
}
~~~



### 18.1. `getName` Is Not Needed for Method References

`User::name` is a public accessor that actually exists in the compiled record. The Java compiler does not need a bridge getter.

### 18.2. Sorting Does Not Modify the Original List

`stream().sorted(...)` produces a newly ordered stream; `toList()` collects the result. `users` remains the List.of created from the initial input [Mai, An]. The Sorted output [An, Mai] is due to the comparator ordering by String name.

### 18.3. Avoid Methods with Side Effects When Sorting

A comparator may call an accessor multiple times. If an explicit accessor mutates state or returns unstable values across invocations, the comparator can violate its contract, causing unexpected results. Good practice is to keep component accessors pure, with no side effects.

## 19. Reflection: The Record Component API Is the Standard Evidence

Use `Class.isRecord()` to determine whether a type is a record, and `Class.getRecordComponents()` to retrieve components in declaration order.

For example:

~~~java
record Coordinates(int row, int col) {
}
~~~

You can obtain:

~~~java
RecordComponent[] components =
        Coordinates.class.getRecordComponents();
~~~

Each RecordComponent has `getAccessor()` returning the public Method. The accessor name must match the component name exactly.

### 19.1. Complete Program 8: Introspection via RecordComponent

Create the file **`RecordReflectionDemo.java`**:

~~~java
import java.lang.reflect.Modifier;
import java.lang.reflect.RecordComponent;

public class RecordReflectionDemo {
    record Coordinates(int row, int col) {
    }

    public static void main(String[] args) throws Exception {
        Class<?> type = Coordinates.class;

        System.out.println("is record = " + type.isRecord());

        for (RecordComponent component
                : type.getRecordComponents()) {
            System.out.println(
                    component.getName()
                    + ":" + component.getType().getSimpleName()
                    + ":" + component.getAccessor().getName());
            System.out.println("public accessor = "
                    + Modifier.isPublic(
                            component.getAccessor().getModifiers()));
        }

        System.out.println("Has row() = "
                + (type.getDeclaredMethod("row") != null));

        try {
            type.getDeclaredMethod("getRow");
        } catch (NoSuchMethodException ex) {
            System.out.println("No getRow() by default");
        }
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 RecordReflectionDemo.java
java RecordReflectionDemo
~~~

**Exact stdout:**

~~~text
is record = true
row:int:row
public accessor = true
col:int:col
public accessor = true
Has row() = true
No getRow() by default
~~~

### 19.2. `getDeclaredMethod("row")` Differs from the JavaBeans Convention

Reflection looks up the exact method name `row` that the compiler generates for the record. `getDeclaredMethod("getRow")` cannot find the method because there is no default JavaBeans getter.

### 19.3. Component Order Is Meaningful

RecordComponent[] is returned in the declaration order in the record header. This order corresponds to the canonical constructor parameters and the generated `toString` representation; preserve the mapping according to the metadata, and do not sort alphabetically on your own unless required.

### 19.4. With Generic Components

`component.getType()` gives the raw runtime Class. `getGenericType()` provides generic type metadata when applicable, such as List<String>. If building a serializer/mapper, read the proper metadata to avoid losing type information.

## 20. Typical Compilation Errors

### 20.1. Calling getX on a Record Without a Bridge

~~~java
record User(String name) {}

User u = new User("Lan");
System.out.println(u.getName()); // Intentionally does not compile.
~~~

**Fix:** call `u.name()` or add `getName()` for a genuine API compatibility reason.

### 20.2. Calling a Component Accessor Like a Public Field

~~~java
record User(String name) {}

User u = new User("Lan");
System.out.println(u.name); // Intentional private field access error.
~~~

**Fix:** call `u.name()`. Record component fields are private final by contract.

### 20.3. Defining a Non-Public Explicit Accessor

~~~java
record User(String name) {
    String name() { // Intentionally does not compile.
        return name;
    }
}
~~~

**Fix:** `public String name()`.

### 20.4. Returning a Type Different from the Component

~~~java
record User(String name) {
    public Object name() { // Intentionally does not compile.
        return name;
    }
}
~~~

**Fix:** exact return type `String`.

### 20.5. Adding a throws Clause

~~~java
record User(String name) {
    public String name() throws Exception { // Intentionally does not compile.
        return name;
    }
}
~~~

**Fix:** an accessor does not declare a `throws` clause; validate/copy in the constructor or use another method with an appropriate contract.

### 20.6. Assuming a Boolean Record Accessor Is Automatically isX

~~~java
record Flag(boolean ready) {}
Flag f = new Flag(true);
System.out.println(f.isReady()); // Intentionally does not compile.
~~~

**Fix:** `f.ready()` or a self-defined `isReady()` bridge.

### 20.7. Trying to Modify a Component Field from a Setter

~~~java
record User(String name) {
    public void setName(String value) {
        name = value; // Intentionally does not compile; component field is final.
    }
}
~~~

**Fix:** create a new record instead of mutating the component field.

### 20.8. Believing a Custom Accessor Also Normalizes Equality

With `record Raw(String s){ public String s(){return s.trim();}}`, generated equals still checks the raw stored fields. **Fix:** normalize s in the canonical constructor if the invariant requires the stored field to also be normalized.

## 21. Design Comparison Between Records and Traditional JavaBeans Classes

| Criterion | Record | Ordinary JavaBeans class |
| --- | --- | --- |
| Data declaration | Header `record User(String name, ...)` | Fields, constructors, accessor methods |
| Default accessor | `name()` | No default compiler-generated getter |
| Getter convention | Not `getName()` by default | Usually `getName()` |
| Boolean getter | `active()` | Usually `isActive()` |
| Component fields | Private final | Depends on class design |
| Setter to update field | No default component setter | Can provide setters |
| Canonical constructor | Tied to record components | No record-specific canonical constructor |
| Generated equality/hashCode/toString | Yes, based on record fields | Not auto-generated from fields |
| Dedicated reflection | `isRecord()`, `getRecordComponents()` | JavaBeans Introspector convention, ordinary reflection |
| JavaBeans Introspector JDK 17 | Does not automatically detect plain component accessors as get/is properties | Detects getter-style properties |
| Method reference | `User::name` | `BeanUser::getName` |
| Custom getter | Can add `getName` | Serves as the primary implementation by convention |
| Deep immutability | Not guaranteed automatically | Not guaranteed automatically either |
| Framework binding | Needs record support or an appropriate bridge | Usually supports JavaBeans getters/setters |

### 21.1. A Record Is Not a “Shorthand Bean”

A record is a kind of class with a fixed state description, a canonical constructor, and value-like methods. It does not have all the conventions of a mutable JavaBean: no-arg constructors, setters, property change listeners, etc. are not auto-generated.

### 21.2. JavaBeans Are Not Required to Be Mutable

A Bean can have read-only properties or immutable state with constructor injection; JavaBeans getter naming does not mean “every Bean must have a setter”. However, many older frameworks assume a no-arg constructor/setters and may require adaptation when using records.

### 21.3. What Kinds of Data Are Records Suitable For?

- DTOs and API response/request models with known components.
- Immutable value-like models, when nested components are managed.
- Tuples/keys carrying value identity.
- Intermediate results when code needs clear names/types without needing a mutable lifecycle.

### 21.4. When Are Class + JavaBeans Getters Easier to Make Compatible?

- Legacy frameworks that only read JavaBeans getters/setters.
- Mutable entities with complex persistence lifecycles.
- Domain models needing inheritance from a custom class.
- APIs requiring a no-arg constructor and property setters.

Choose based on the contract, not just the number of lines of code.

## 22. Frameworks and Serialization: Avoid Over-Inferring

Many modern frameworks recognize records via reflection or support the record canonical constructor, but **that capability depends on version** and configuration:

- A serializer may inspect record components and retrieve values using `component.getAccessor()`.
- A legacy Bean mapper may only look for `getName()/isActive()` and conclude that properties are missing.
- A deserializer may need to invoke the canonical constructor, unable to set private final fields in the usual Bean manner.
- A UI binding library may rely on PropertyDescriptor conventions.
- Annotations have different targets (FIELD, METHOD, PARAMETER, RECORD_COMPONENT, TYPE_USE), so annotation placement on a record component can affect the propagation/metadata that a library reads.
- A library may create JavaBeans-like property descriptions for records using its own logic, independent of JDK 17's `Introspector`.

### 22.1. Compatibility Checking Process

1. Identify the target JDK and framework versions.
2. Check whether the framework has native record support.
3. Check whether serialization reads `name()` or `getName()`.
4. Check whether deserialization supports the canonical constructor.
5. Verify that annotations are placed with the right target/mapping.
6. Write a round-trip integration test with real data.
7. Only add bridge getters/adapters when there is a clear benefit.

### 22.2. Do Not Create Empty Setters to “Make the Framework Happy”

With a record, component fields are final; they cannot actually be reassigned. A no-op `setName` will make tools think the object is mutable while the data never changes, which is more dangerous than requiring a proper adapter. If a framework demands setters, use an appropriate DTO class or upgrade/configure record-aware binding.

### 22.3. Generated Methods Do Not Guarantee JSON Key Conventions

JSON key naming is determined by serializer configuration and annotations. Do not infer that Java's `name()` is guaranteed to serialize to `name` in every library. Conversely, do not conclude that records can never be serialized simply because `getName` is missing.

## 23. Null, Optional, and Validation

A component accessor can return null if the component field stores null; records do not automatically enforce non-null:

~~~java
record User(String name) {
}

User u = new User(null);
System.out.println(u.name() == null); // true
~~~

If a business invariant forbids null, validate in the canonical constructor:

~~~java
record User(String name) {
    User {
        java.util.Objects.requireNonNull(name, "name");
    }
}
~~~

### 23.1. Do Not Wrap Every Accessor in Optional

If the component type is String, the accessor must return String; you cannot explicitly change the signature to `Optional<String> name()`. If you want an Optional view, create another method `optionalName()` or declare the component itself as Optional<String> according to the appropriate API design.

### 23.2. JavaBeans Getters Do Not Validate Automatically Either

`getName()` can return null, throw an exception, compute a dynamic value, or read from a database if a developer writes it that way. The naming convention does not grant any special non-null guarantee. Validation belongs to constructors, fields/invariants, and API contracts.

### 23.3. Compact Constructors and Null

If the record component type is List, `List.copyOf(null)` will throw an NPE; you can use `Objects.requireNonNull` with a clear message if desired. Rejecting null should be stated as the record constructor contract, not merely an accidental side effect of an accessor.

## 24. Testing Record Accessors Properly

When testing:

~~~java
record Item(String id, int amount) {
}
~~~

consider:

1. `item.id()` and `item.amount()` return the expected values.
2. Component accessor methods are public and have the exact return types.
3. JavaBeans getX/isX do not exist unless added.
4. `RecordComponent.getAccessor()` points to the exact method.
5. Constructor validation/normalization is tested.
6. Defensive copies protect input and output if components are mutable.
7. Generated equals/hashCode/toString have semantics matching the raw fields.
8. When an explicit accessor transforms the result, tests must verify whether generated methods use the raw field.
9. JavaBeans bridge getters, if present, must return the same logical values as component accessors per contract.
10. Integration test with the actual serializer/framework/version, not just reflection.
11. Method references `Item::id` compile and work.
12. Records have no default setters and cannot mutate final component fields.

### 24.1. Do Not Test Only `record.toString()`

Generated toString may reflect the raw field even when a custom accessor returns a normalized view. Do not use toString as proof that all accessors have been normalized.

### 24.2. Do Not Test Only Equality

Generated equality may be true/false based on component fields while a custom accessor computes something different. You need to test both state consistency and the equality contract according to the domain.

### 24.3. With a byte[] Component

A test doing `packet.payload()[0] = 99` and then reading it back is necessary to confirm the defensive copy. Also test the constructor alias `input[0]=99` after creating the record. Testing only one side will miss a vulnerability on the other side.

## 25. Common Mistakes

1. **Calling `getName()` on a bare record:** The compiler only generates `name()`.
2. **Calling `isActive()` for `boolean active`:** A record generates `active()`.
3. **Treating a record component as a public field:** The field is private final.
4. **Assuming the Java compiler automatically creates JavaBeans getters:** It does not, unless a separate tool/library intervenes.
5. **Treating every Bean as mutable:** Getter-only Beans also exist.
6. **Treating every record as deeply immutable:** Mutable List/array components can still be modified.
7. **Writing a package-private explicit accessor:** It must be public.
8. **Writing an explicit accessor with return type Object for a String component:** Wrong return type.
9. **Adding a throws clause to an accessor:** Violates a record-specific rule.
10. **Writing a static accessor with the same name as the component:** Does not satisfy the instance method contract.
11. **Writing a JavaBeans bridge and thinking the `name()` accessor disappears:** It is still present.
12. **Overriding an accessor to trim without normalizing the field:** Generated equals/toString inspect the raw field.
13. **Using an accessor to modify a final field:** A record component field cannot be updated.
14. **Cloning an array only in the constructor:** The getter can still expose the internal array.
15. **Cloning an array only in the getter:** The input alias can still modify the internal array.
16. **Assuming `List.copyOf` deep-copies every element:** It only protects the List structure and keeps element references.
17. **Using a byte[] record component and expecting default equals by contents:** Arrays are normally compared by reference.
18. **Using a mutable record as a HashMap key without control:** Nested mutable content can make hash behavior unstable.
19. **Relying on `Introspector` to conclude records cannot be used with any framework:** Framework-specific record support may exist.
20. **Assuming every framework understands record components:** You need to check the actual version and configuration.
21. **Writing a no-op setter for a record:** Breaks the API contract.
22. **Naming `boolean isReady` and thinking the component is named `ready`:** The component is actually isReady.
23. **Treating a getter prefix as a type safety guarantee:** Property naming does not validate null/format.
24. **Replacing a class with a record without reviewing clients calling getX/setX:** Can break source compatibility.
25. **Using `getClass()` instead of record introspection APIs:** Record-specific metadata resides in Class.getRecordComponents.
26. **Not considering annotation targets when migrating a field/Bean to a record:** Can change serializer mapping.
27. **Creating an expensive/side-effectful accessor used in a Comparator:** Results can be unstable.
28. **Confusing the record name and the component type:** The accessor name comes from the component identifier.
29. **Confusing `getName()` of RecordComponent reflection with an object's getter:** RecordComponent.getName() returns a metadata String about the component; it is not a getName() method on the record instance.
30. **Not distinguishing canonical constructor input from accessor output:** If normalization/copying differs, invariants can drift.

## 26. Record API Design Checklist

1. Do you actually need a record/value-like data type?
2. Are component names clear and stable?
3. Should clients call `name()` or require `getName()` compatibility?
4. Is the boolean component `active` properly understood as `active()`?
5. Is there a legacy framework using Introspector/property conventions?
6. Does the framework version have record-specific support?
7. Do you need to add JavaBeans bridge methods or an adapter DTO?
8. Is an explicit accessor public, with the exact return type, and without params/throws/generics?
9. Does a custom accessor cause the result to diverge from the raw component field?
10. If normalization is needed, is it done in the canonical constructor before storing the field?
11. Is there constructor validation for null/blank/range?
12. Are components primitive/immutable values or mutable references?
13. For a mutable List, are there appropriate snapshots and immutable elements?
14. For arrays, is there copy-on-input and copy-on-output?
15. Do generated equals/hashCode/toString fit the component field semantics?
16. If a component is an array, is identity-based equality acceptable?
17. Is a `withX()` method needed to create a new record instead of a setter?
18. Are record accessor method references used in streams/comparators?
19. Is it ensured that accessors have no unintended side effects?
20. Does reflection code use `RecordComponent` instead of just guessing getter names?
21. Do named modules need `requires java.desktop` for JavaBeans APIs?
22. Do integration tests verify serialization/deserialization with the actual framework?
23. Are duplicate/conflicting property names avoided when adding bridge getters?
24. Are record components and external schema mappings kept versioned?
25. Are mutable alias isolation and hash-based collection behavior tested when needed?

## 27. Self-Check Exercises with Answers

**Question 1.** What accessor methods does `record User(String name, int age)` generate?

**Answer:** `public String name()` and `public int age()`.

**Question 2.** Does the compiler automatically generate `getName()` for a record?

**Answer:** No. That is a JavaBeans-style getter convention, not a default record component accessor.

**Question 3.** For `record Flag(boolean active)`, what is the default accessor?

**Answer:** `active()`, not `isActive()`.

**Question 4.** What accessor does `record Flag(boolean isActive)` have?

**Answer:** `isActive()`, because the actual component identifier is isActive.

**Question 5.** Is a record component field public?

**Answer:** No; the corresponding component field is private final, and the public accessor is the standard way to read it.

**Question 6.** Can an explicit accessor be written?

**Answer:** Yes, but it must be public, an instance method, take no parameters, have the exact return type, and declare no throws/type parameters.

**Question 7.** Is `String name()` without writing public valid in a record?

**Answer:** No, when it is an explicit accessor; it must be public.

**Question 8.** Can `Object name()` replace the accessor for `String name`?

**Answer:** No, the return type must be exact String.

**Question 9.** Can `name() throws IOException` be written as a component accessor?

**Answer:** No, an explicit accessor must not have a throws clause.

**Question 10.** Does adding `getName()` remove `name()`?

**Answer:** No. That is an extra method; the implicit/explicit component accessor still exists.

**Question 11.** Must a JavaBeans getter necessarily correspond to a field of the same name?

**Answer:** No; a getter can compute a property from multiple fields or perform calculations.

**Question 12.** Does a getter-only JavaBeans property require a setter?

**Answer:** No; read-only properties can exist.

**Question 13.** Does JDK 17's JavaBeans Introspector automatically treat a bare record's `name()` as `getName()`?

**Answer:** Not according to the standard convention; use record component metadata or a bridge getter if a legacy library requires it.

**Question 14.** Is there a reflection API that retrieves all record components?

**Answer:** `Class.getRecordComponents()`, combined with `RecordComponent.getAccessor()`.

**Question 15.** What does `RecordComponent.getAccessor()` return?

**Answer:** A `java.lang.reflect.Method` representing the accessor corresponding to the component.

**Question 16.** Can a record component accessor be used in a method reference?

**Answer:** Yes, for example `User::name`.

**Question 17.** Does a custom accessor that trims a String automatically make generated equals compare trimmed values?

**Answer:** No. Generated equals is based on component fields and does not automatically call custom accessors.

**Question 18.** If you want the entire record state normalized, where should it be handled?

**Answer:** In the canonical/compact constructor before component fields are assigned.

**Question 19.** Does auto-generated `toString()` necessarily print the output of a custom accessor?

**Answer:** No; generated toString is based on component fields.

**Question 20.** Can a record have a mutable List as a component?

**Answer:** Yes, but a record is not automatically deeply immutable; an ownership/copy policy is needed.

**Question 21.** Does `List.copyOf(source)` prevent source.add after construction from changing the structure of the stored List?

**Answer:** Yes, within the appropriate snapshot contract, though it does not deep-copy mutable elements.

**Question 22.** For a byte[] component, is cloning only in the constructor enough?

**Answer:** No, if the accessor returns the raw internal array; you must copy when returning if you need to prevent mutation by the caller.

**Question 23.** Is cloning the array only in the accessor enough?

**Answer:** No, if the constructor stored the raw input reference; the caller can mutate it via the input alias.

**Question 24.** Does default record equals compare byte[] by contents like Arrays.equals?

**Answer:** No. Array component equality normally uses reference identity.

**Question 25.** Does `record P(int x)` have an auto-generated `setX` setter?

**Answer:** No.

**Question 26.** What is the appropriate way to “change x” for a value-style record?

**Answer:** Create a new record object with the new x, such as `new P(9)` or a `withX` method returning a new instance.

**Question 27.** Can a Bean getter bridge be used for the interface `LegacyNamed.getName`?

**Answer:** Yes. The record declares `getName()` calling `name()`, while the component accessor still exists.

**Question 28.** Can a record implement the interface `NameBearing { String name(); }` via its implicit accessor?

**Answer:** Yes, if the component accessor is public with a signature matching the interface.

**Question 29.** Which module does `java.beans.Introspector` belong to?

**Answer:** `java.desktop`; named modules using the JavaBeans API need appropriate module readability.

**Question 30.** Should you assume every JSON library handles records automatically?

**Answer:** No; you need to check the library version, annotations, and native record support.

**Question 31.** Why should you not write a no-op setter in a record?

**Answer:** Because a client/framework might assume mutation succeeded even though state did not change, breaking the contract.

**Question 32.** Are both record accessors and JavaBeans getters instance methods?

**Answer:** When speaking of regular getters/accessors in this lesson, yes; a record accessor is required to be an instance method, and a JavaBeans property getter is also typically an instance method.

**Question 33.** Is a boolean JavaBeans getter `isReady()` equivalent to a record component `boolean ready`?

**Answer:** Only in domain meaning if the developer maps them. The record compiler still generates `ready()`; `isReady()` must be explicitly declared if needed.

**Question 34.** Does adding `getName()` to a record turn the record into a mutable Bean?

**Answer:** No; adding a getter does not add a setter and does not remove the final component fields.

**Question 35.** What is the most important takeaway of this lesson?

**Answer:** **Record accessor = component name with `()`, auto-generated by Java per the record contract; JavaBeans getter = naming convention `getX()/isX()`.** To bridge, you must add the method yourself or use record-aware tooling; when customizing an accessor, keep an accurate understanding of raw fields, equality, and ownership.

## 29. Conclusion

A **record accessor** is determined by Java directly from the **record component name**. For `record User(String name, boolean active)`, the default read methods are `user.name()` and `user.active()`, **not `getName()` or `isActive()`**. These accessors are public instance methods, have signatures tied to the component types, and can be declared explicitly within the constraints of the record language.

A **JavaBeans getter** is a different convention: `getName()`, `isActive()`, and related method patterns for tools to recognize read-only/read-write properties. A bare record does not automatically generate these names; if legacy clients need to be supported, you can add bridge getters or choose a mapper that understands record components via `Class.getRecordComponents()` and `RecordComponent.getAccessor()`.

Do not forget that **a record component field is final, but the referent may be mutable**. If you write an accessor yourself to normalize or defensive-copy, you must account for the canonical constructor and generated `equals/hashCode/toString`, which rely on the component fields rather than automatically calling the transformed accessor. For Lists/arrays, control ownership using an immutable representation or appropriate copy-on-input/output.

Properly understanding **component declaration → public accessor `component()`**, while distinguishing **JavaBeans naming → getX/isX**, will help you design clear records, use method references and reflection correctly, and integrate frameworks safely without accidentally breaking value semantics.
