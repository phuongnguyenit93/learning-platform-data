# Distinguishing Class Loading, Linking, and Initialization in Java

When the JVM uses a Java type, three concepts that are often lumped together are **class loading**, **class linking**, and **class initialization**. In fact, they have distinct roles:

- **Loading** enables the JVM to find/define the runtime representation of a class or interface from suitable binary data.
- **Linking** checks and prepares the type so that references, fields, and methods can be used safely; it consists of **verification**, **preparation**, and **resolution**.
- **Initialization** executes the **static field initializers** and **static initializer blocks** of a class, or the field initializers of an interface, according to the initialization rules.

These are steps belonging to the **type lifecycle in the JVM**, distinct from **per-object initialization** when calling a constructor. Seeing a line printed by `static { ... }` to the console indicates that the class has reached the initialization phase, **not the exact moment the class file was first read into the JVM**.

This article is part of Java Core — *class-object*, **Initialization Order** group. The standalone examples run with **Java 17 or later** and are designed to clearly illustrate ordering, deferred initialization cases, class loaders, compile-time constants, superclasses/interfaces, initialization failures, and diagnostics.

## 1. A Map of the Three Phases

A common conceptual model:

~~~text
Type identity information (binary name + defining class loader)
                         |
                         v
        1. LOADING — create class/interface representation
                         |
                         v
        2. LINKING
           ├─ Verification: check validity of the representation
           ├─ Preparation : allocate/prepare static fields, default values
           └─ Resolution  : resolve symbolic references when needed
                         |
                         v
        3. INITIALIZATION
           ├─ ensure required superclass is initialized
           ├─ process applicable superinterfaces per JLS
           └─ execute static initializers and field initializers
                         |
                         v
        Class is ready for uses requiring initialization
~~~

This is a **conceptual diagram**, not a record of an absolute sequence of operations at runtime. The JVM may choose to **resolve symbolic references early or late** within specified bounds; therefore, do not interpret this as meaning that all resolution of every dependency must complete as a single block before initialization.

Important constraints:

1. A type must be **completely loaded** before linking.
2. Verification and preparation must be satisfied before initialization.
3. Resolution may be deferred according to JVM rules.
4. A class is not necessarily initialized immediately once loaded or linked.
5. Each class or interface is initialized according to its own state, with safe coordination when multiple threads concurrently request initialization.

Authoritative sources for reference are [JLS 17, Chapter 12](https://docs.oracle.com/javase/specs/jls/se17/html/jls-12.html) and [JVMS 17, Chapter 5](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-5.html).

## 2. Loading: The JVM Finds and Defines a Type

**Loading** is the process by which the JVM obtains the runtime representation of a class/interface based on the type's identity and its **defining class loader**. For ordinary application types, the loader locates the class bytes and the JVM uses the appropriate binary representation to create the type information.

In a Java application, sources that can lead to loading include:

- Class files found on the classpath or module path.
- Classes belonging to the JDK, libraries, and the application managed by appropriate class loaders.
- Classes defined from bytecode supplied by a custom loader.
- Types dynamically generated by runtime mechanisms; for array classes, the JVM has specific creation rules.

**Loading does not mean Java source is compiled at that time.** In the normal `javac` workflow, `.java` source has already been compiled into `.class` before the application runs. The JVM consumes the binary representation; `.java` files do not need to exist in the runtime environment.

### Does the loader read every class right when `java Main` runs?

No. The JVM and class loaders may load many types at startup or on demand; there is no requirement to load every class of the project before running the first line of `main`.

Do not rely on a "class loaded" log to conclude that a static block has run. A class may be known to the runtime earlier, while its static initializer has still not been executed.

## 3. Class Identity Depends on Both Name and Loader

A very important principle in the JVM: two classes with the **same binary name** but **defined by two different class loaders** can be **two different runtime types**.

~~~text
Loader A defines org.example.Task  ---> Class object A
Loader B defines org.example.Task  ---> Class object B

The same name string "org.example.Task"
is not enough to establish the same runtime type.
~~~

This distinction explains certain advanced classpath/plugin/server errors: an object looks as if it belongs to a class with the "same name", yet casting can fail due to a different class loader. Each runtime class/interface has its own corresponding initialization state, rather than a shared static state across all definitions of the same name.

The class loader delegation model typically helps limit duplicate type definitions, though custom loaders may use other strategies within what the JVM allows. Just keep in mind at the Java Core level: **a class name is not the entire runtime identity**.

Distinguish:

- `ClassLoader.loadClass(...)` relates to a type-loading request; this operation itself is **not an instruction to run the static initializer**.
- The single-argument `Class.forName(name)` by default **requests initialization** of the corresponding class.
- `Class.forName(name, false, loader)` requests the `Class` object but **does not request initialization** of that class.

## 4. Linking: Three Different Tasks, Not Running the Constructor

Linking consists of three activities per [JLS §12.3](https://docs.oracle.com/javase/specs/jls/se17/html/jls-12.html#jls-12.3):

| Component | Main Role | Should Not Be Confused With |
| --- | --- | --- |
| **Verification** | Checks structural/safety constraints of the binary representation | Running business tests of the class |
| **Preparation** | Creates and prepares static fields with initial values per JVM rules | Executing arbitrary initializer expressions in source |
| **Resolution** | Resolves symbolic references from the constant pool to the appropriate runtime entities | Requiring all dependencies to be resolved immediately |

A verification error usually relates to invalid bytecode or violating JVM constraints; it is not the same as a constructor throwing `IllegalArgumentException` when validating input.

A resolution error can appear if a field/method or type referenced by a class does not exist or is incompatible at runtime; for example, errors in the `NoSuchMethodError` or `NoSuchFieldError` family in incompatible binary change scenarios. These are **linkage errors**, distinct from exceptions thrown by the static initializer itself.

**The order cannot be simplified** to "verification → preparation → resolve everything → initialization". The JVM may resolve eagerly or on demand, but must comply with the requirements set by the JVM Specification.

## 5. Preparation: Static Fields Have Storage, Yet Initializers Have Not Run

Consider the class:

~~~java
class Metrics {
    static int count = calculateInitialCount();

    private static int calculateInitialCount() {
        System.out.println("calculate");
        return 7;
    }
}
~~~

This is an **illustrative class** without `main`. During **preparation**, the `count` field is prepared with the default value for `int` (`0`) under the standard JVM model. However, the expression `calculateInitialCount()` **has not been called merely because of preparation**. Calling `calculateInitialCount()` is the job of **initialization**.

Familiar default values for static fields not belonging to the special constant-value group:

| Type | Default Value During Preparation |
| --- | --- |
| `int`, `short`, `byte` | `0` |
| `long` | `0L` |
| `float`, `double` | `0.0` |
| `boolean` | `false` |
| `char` | `'\u0000'` |
| Reference | `null` |

**Technical exception to know:** for a `static final` field with a `ConstantValue` class-file attribute, the JVM handles the constant value via a dedicated mechanism during the corresponding preparation/initialization; one should not conclude that every `static final` always only holds `0` or `null` right up until the static block runs. For example, `static final int SIZE = 16;` is a constant variable and has a compile-time constants mechanism different from `static int x = compute();`.

In ordinary code, trying to observe a class field from outside before the class is initialized **usually causes that very read action to trigger initialization**. Therefore, do not predict that a typical program will print `0` on the first read of `Metrics.count`.

## 6. Program: Seeing Initialization, Without Confusing It With Preparation

Create the standalone file **`PreparationVsInitializationDemo.java`**:

~~~java
class MetricsStage {
    static int count = compute();

    static {
        System.out.println("MetricsStage.static block, count=" + count);
    }

    private static int compute() {
        System.out.println("MetricsStage.compute()");
        return 7;
    }
}

public class PreparationVsInitializationDemo {
    public static void main(String[] args) {
        System.out.println("before first active use");
        System.out.println("count=" + MetricsStage.count);
        System.out.println("again=" + MetricsStage.count);
    }
}
~~~

Compile and run:

~~~bash
javac -encoding UTF-8 PreparationVsInitializationDemo.java
java PreparationVsInitializationDemo
~~~

**Exact stdout:**

~~~text
before first active use
MetricsStage.compute()
MetricsStage.static block, count=7
count=7
again=7
~~~

Step-by-step explanation:

1. The JVM may load/link `MetricsStage` before or upon reaching the line reading `MetricsStage.count`; this stdout **does not prove the timing of loading/linking**.
2. The `count` line accesses a `static` field that is **not a constant variable**, so it requires initialization of `MetricsStage`.
3. During initialization, the expression `compute()` runs first, prints the message, and then returns 7.
4. The static block appears **after the `count` declaration**, so it can read the already-assigned value 7.
5. The subsequent read call does not re-run the entire static initializer; it only prints `again=7`.

Distinguishing between **defaults at preparation** and **values present after initialization** avoids the mistaken deduction: "because preparation initializes numbers to 0, the first static read will see 0". For this example, that conclusion is wrong.

## 7. Resolution: Why Might Linking Not Have Resolved Every Name Yet?

In a class file, many references to types, fields, and methods initially appear as **symbolic references** in the *run-time constant pool*. Resolution is the step of determining which actual class, field, method, or runtime entity a symbolic reference points to.

Source example:

~~~java
String text = Integer.toString(42);
~~~

This is an **illustrative statement**. The bytecode contains information to reference the appropriate method; the JVM may need to resolve this reference upon execution or earlier, according to its implementation strategy and the rules of [JVMS §5.4.3](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-5.html#jvms-5.4.3).

Points to remember:

- **Loading a class does not mean loading every type the class mentions.** Verification/resolution may lead to loading additional types as needed.
- **Resolution does not always happen entirely before initialization.** The JVM is allowed to choose among multiple points in time within the specified limits.
- Errors such as not finding a method with the matching binary signature may surface **when that linkage is used**, rather than necessarily right at startup.
- Resolution and initialization are two distinct tasks: resolving a name to a method does not mean running the static initializer of every related class.

If a library version is changed after compilation and a method signature has changed, code that compiled successfully earlier may fail at runtime with a form of `LinkageError`. When handling this situation, check the classpath/module path and binary compatibility, **without mistaking it for an error in a constructor**.

## 8. When Must a Class or Interface Be Initialized?

According to [JLS 17 §12.4.1](https://docs.oracle.com/javase/specs/jls/se17/html/jls-12.html#jls-12.4.1), important situations include:

- Creating an **instance** of the class using an appropriate object creation expression.
- Invoking a **static method actually declared** by the class.
- Assigning a **static field** declared by the class/interface.
- Reading a **static field that is not a constant variable**.
- Certain reflection operations specified to require initialization.
- The JVM requires initialization of the entry class when starting application execution; superclasses and superinterfaces with default methods may be involved in this sequence.

Cases that **typically do not by themselves trigger initialization of the component type**:

- Merely writing a variable declaration `SomeType ref;` or using the type name in source comments.
- Taking a class literal `SomeType.class`.
- Creating a **reference array** like `new SomeType[10]` without creating a `SomeType` instance.
- Reading a **compile-time constant variable** of primitive/`String` type meeting JLS conditions, because the constant may be inlined.
- Requesting the `Class` object via `Class.forName(name, false, loader)`.

Do not equate **referenced by source** with **actively used at runtime**. A type appearing multiple times in source does not guarantee that its static initializer has run.

## 9. Program: `Class.forName` With and Without Initialization

Create the file **`LoadWithoutInitializeDemo.java`**:

~~~java
class DeferredService {
    static {
        System.out.println("DeferredService initialized");
    }

    static int version = 42;
}

public class LoadWithoutInitializeDemo {
    public static void main(String[] args) throws Exception {
        ClassLoader loader =
                LoadWithoutInitializeDemo.class.getClassLoader();

        System.out.println("before");
        Class<?> metadata =
                Class.forName("DeferredService", false, loader);
        System.out.println("class=" + metadata.getSimpleName());
        System.out.println("after false");

        Class.forName("DeferredService");
        System.out.println("after true");
        System.out.println("version=" + DeferredService.version);
    }
}
~~~

Commands:

~~~bash
javac -encoding UTF-8 LoadWithoutInitializeDemo.java
java LoadWithoutInitializeDemo
~~~

**Stdout:**

~~~text
before
class=DeferredService
after false
DeferredService initialized
after true
version=42
~~~

### What do these lines prove?

- `Class.forName("DeferredService", false, loader)` returns `Class<?> ` for `DeferredService` **without requiring the static initializer to run**.
- `metadata.getSimpleName()` reads information about the type name; in the example, it does not cause the static block to run.
- `Class.forName("DeferredService")` requires the class to be initialized. Therefore, the static block prints `DeferredService initialized` **before** `after true`.
- The subsequent read of `DeferredService.version` does not initialize the class a second time.

If `Class.forName("DeferredService")` is called from the outset, the static block may be executed right at that call. Conversely, `ClassLoader.loadClass("DeferredService")` is an operation requesting loading and **does not automatically force initialization** of the type just because the method name contains the word "load".

**Scope of conclusion:** `false` means **do not initialize**, not a guarantee that the JVM will strictly perform no linking/verification at all. Do not use the same `static` line log to infer every internal phase.

## 10. Program: Class Literals and Arrays Do Not Automatically Run Static Blocks

Create the file **`ClassLiteralAndArrayDemo.java`**:

~~~java
class Widget {
    static {
        System.out.println("Widget initialized");
    }

    Widget() {
        System.out.println("Widget constructed");
    }
}

public class ClassLiteralAndArrayDemo {
    public static void main(String[] args) {
        System.out.println("start");

        Widget[] widgets = new Widget[2];
        System.out.println("array length=" + widgets.length);

        Class<Widget> type = Widget.class;
        System.out.println("class=" + type.getSimpleName());

        System.out.println("before new");
        Widget actual = new Widget();
        System.out.println("done");
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 ClassLiteralAndArrayDemo.java
java ClassLiteralAndArrayDemo
~~~

**Stdout:**

~~~text
start
array length=2
class=Widget
before new
Widget initialized
Widget constructed
done
~~~

Explanation:

- `new Widget[2]` creates an **array object**, containing two reference elements initially set to `null`; it **does not invoke the `Widget()` constructor twice**.
- `Widget.class` lets you obtain the `Class` token and does not by itself trigger initialization of `Widget`.
- Upon reaching `new Widget()`, the JVM requires `Widget` to be initialized before executing the constructor; the static block prints once, and then the constructor prints.
- The variable `actual` holds a reference to the created instance; whether or not it is read again does not affect why the static block ran.

In a large file, seeing `Widget.class` can cause the compiler/JVM to **already know about the type** before creating an instance. However, the point to remember is that **this does not mean static initialization occurs when obtaining the class literal**.

## 11. Compile-Time Constants Do Not Necessarily Initialize Their Enclosing Class

A `static final` field is not automatically a *constant variable*. According to the JLS, a constant variable is a `final` field or variable of primitive type or `String` initialized with a **constant expression** that satisfies the conditions.

Compare:

~~~java
static final int LITERAL = 17;
static final String LABEL = "OK";
static final int COMPUTED = Integer.parseInt("18");
~~~

`LITERAL` and `LABEL` are constant variables; `COMPUTED` is **not**, because calling the `Integer.parseInt` method is not a constant expression.

Create the file **`ConstantInitializationDemo.java`**:

~~~java
class Tokens {
    static final int LITERAL = 17;
    static final String LABEL = "OK";
    static final int COMPUTED = Integer.parseInt("18");

    static {
        System.out.println("Tokens static block");
    }
}

public class ConstantInitializationDemo {
    public static void main(String[] args) {
        System.out.println("before");
        System.out.println("literal=" + Tokens.LITERAL);
        System.out.println("label=" + Tokens.LABEL);
        System.out.println("computed=" + Tokens.COMPUTED);
        System.out.println("after=" + Tokens.COMPUTED);
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 ConstantInitializationDemo.java
java ConstantInitializationDemo
~~~

**Stdout:**

~~~text
before
literal=17
label=OK
Tokens static block
computed=18
after=18
~~~

The two lines reading `Tokens.LITERAL` and `Tokens.LABEL` do not cause `Tokens` to be initialized. Upon reaching the line reading `Tokens.COMPUTED`, the JVM performs initialization of `Tokens`, runs the `Integer.parseInt("18")` evaluation and the static block. The subsequent read simply retrieves the existing result.

### Why does this matter in practice?

- References to a compile-time constant can be **replaced by the compiler with the direct value** in the client's bytecode.
- If such a public constant is changed in a library without recompiling the clients, old client code may continue using the inlined value.
- A `static final int` assigned inside a **static block** is not a constant variable merely because it carries the `final` modifier.
- A `static final List<String>`, even though its reference does not change, is **not** a constant variable in the sense of a primitive/`String` constant expression.

Therefore, the statement "whenever a static field is read, the class will be initialized" **is missing a condition**: one must check whether the field **is a constant variable** or not.

## 12. Order of Static Initialization Within a Class

Within a class, static field initializers and static initializer blocks are executed in the **order they appear in source**, following the appropriate initialization steps and conditions.

Create the file **`StaticTextualOrderDemo.java`**:

~~~java
class Ordered {
    static int first = announce("first field", 1);

    static {
        System.out.println("first block");
    }

    static int second = announce("second field", 2);

    static {
        System.out.println("second block");
    }

    private static int announce(String label, int value) {
        System.out.println(label);
        return value;
    }

    Ordered() {
        System.out.println("constructor");
    }
}

public class StaticTextualOrderDemo {
    public static void main(String[] args) {
        System.out.println("before");
        new Ordered();
        new Ordered();
        System.out.println("fields=" + Ordered.first
                + "," + Ordered.second);
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 StaticTextualOrderDemo.java
java StaticTextualOrderDemo
~~~

**Stdout:**

~~~text
before
first field
first block
second field
second block
constructor
constructor
fields=1,2
~~~

Explanation:

1. Static field `first` is assigned during the initialization phase, printing `first field`.
2. The first static block runs, printing `first block`.
3. `second` is computed next, printing `second field`.
4. The second static block runs, printing `second block`.
5. The instance constructor runs for the first object and then the second object, so `constructor` is printed twice.
6. Static initializers **do not repeat every time `new Ordered()` is called**.

Note that source code may reference a static field declared later in contexts permitted by Java, subject to **illegal forward reference** rules; you should not design logic that relies on unassigned fields to obscurely read default values.

## 13. Order Between Superclass and Subclass

When the JVM needs to initialize a subclass, it ensures that an **uninitialized superclass** is initialized first. This rule concerns **class initialization** of `static` fields/blocks and does not mean all constructors have run.

~~~java
class Base {
    static { System.out.println("Base static"); }
    Base() { System.out.println("Base constructor"); }
}
class Derived extends Base {
    static { System.out.println("Derived static"); }
    Derived() { System.out.println("Derived constructor"); }
}
~~~

If these are standalone declarations and the caller invokes `new Derived()` for the first time, the four lines printed in order are `Base static`, `Derived static`, `Base constructor`, and `Derived constructor`. On the next `new Derived()` call within the same successfully initialized runtime identity, **only the two constructor bodies** run again. This is a **snippet** to distinguish the two rules; the complete trace program on parent–child ordering belongs to the lesson "Initializing the Superclass Before the Subclass".

Also distinguish: accessing a static field **declared in Base** by writing `Derived.FIELD` does not necessarily force Derived to be initialized; examine where the member is actually declared. A subclass instance is not two separate Base/Derived objects: the Base constructor initializes the inherited portion of **the same Derived object**.

## 14. Accessing an Inherited Static Field May Not Initialize the Subclass

An easily overlooked distinction: if a static field is **actually declared in the superclass**, accessing that field via the subclass name does not by itself force the subclass to be initialized.

Example:

~~~java
class BaseConfig {
    static int PORT = 8080;

    static {
        System.out.println("BaseConfig initialized");
    }
}

class AppConfig extends BaseConfig {
    static {
        System.out.println("AppConfig initialized");
    }
}
~~~

If a separate `main` writes:

~~~java
System.out.println(AppConfig.PORT);
~~~

then the `PORT` field actually belongs to `BaseConfig`. According to the JLS, triggering initialization applies to the **class declaring the field**, which is `BaseConfig`; merely using the syntax `AppConfig.PORT` does not force the `AppConfig` static block to run.

Code readers can be misled by the name to the left of the dot. To express the true source, it is generally better to write `BaseConfig.PORT` when possible. Do not confuse this with "lazy initialization of the superclass"; the superclass may already be initialized, while the subclass simply **has no reason to be initialized yet**.

For static methods, Java also considers **which type declares** the method, not merely the type written before the dot. Read the initialization rules according to the actually declared member and the name resolution mechanism.

## 15. Interface Initialization Does Not Always Trigger Superinterface Initialization

Interfaces have fields that are implicitly `public static final`, yet **not every field is a compile-time constant**. A field computed via a method call can trigger initialization of the interface when read.

Create the file **`InterfaceInitializationDemo.java`**:

~~~java
final class InitTrace {
    private InitTrace() {
    }

    static int record(String name) {
        System.out.println(name + " initialized");
        return 1;
    }
}

interface RootRule {
    int ROOT = InitTrace.record("RootRule");
}

interface ChildRule extends RootRule {
    int CHILD = InitTrace.record("ChildRule");
}

public class InterfaceInitializationDemo {
    public static void main(String[] args) {
        System.out.println("before");
        System.out.println("child=" + ChildRule.CHILD);
        System.out.println("root=" + RootRule.ROOT);
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 InterfaceInitializationDemo.java
java InterfaceInitializationDemo
~~~

**Stdout:**

~~~text
before
ChildRule initialized
child=1
RootRule initialized
root=1
~~~

Why does `ChildRule` run before `RootRule`?

- `CHILD` is a static final field, yet **not a constant variable**, because its initializer calls `InitTrace.record(...)`. Reading it requires initialization of `ChildRule`.
- **Initialization of an interface does not by itself force initialization of its superinterfaces**.
- When `RootRule.ROOT` is read afterward, `RootRule` is then initialized for its own use.

**Exception when a class implements an interface:** when initializing a **class**, Java must also initialize relevant superinterfaces that have **default methods** according to specific rules in JLS 17. Do not interpret the example above as "an interface is never initialized before a class implementing it". This is a subtle aspect of initialization order.

To avoid confusion, prefer analyzing a concrete example: which field is declared where, whether it is a constant variable, which class or interface has default methods, and which action is requesting initialization.

## 16. Operations That Do Not Automatically Run the Instance Constructor

In the JVM lifecycle, there are two distinct concepts:

| Operation | Can Execute Static Initialization? | Does It Create an Object Instance of That Class? |
| --- | --- | --- |
| Loading a class | Not necessarily | No |
| Linking a class | Not running the constructor | No |
| Class initialization | Runs static code conditionally | Not necessarily |
| `SomeClass.class` | Typically does not initialize the class | No |
| `new SomeClass[3]` | Does not initialize the component class merely by creating the array | Creates only the array object |
| `Class.forName(name)` | Yes, requests initialization | Does not create an instance of the target class |
| `new SomeClass()` | Yes, if the class is not yet initialized | Yes, if creation succeeds |
| Reading a static nonconstant field | Yes, if the field requires initialization | No |

An instance constructor runs only when there is an appropriate **instance creation** process. A class may already be initialized from calling a static method or reading a nonconstant static field, while **no object** of that class has yet been created.

Conversely, creating an instance requires the class to be initialized first, but after the class is successfully initialized, the constructor can continue to run multiple times to create multiple objects. Thus, **static code once per class lifecycle** and **constructors per instance** are two separate layers.

## 17. When Class Initialization Fails: Consequences Differ From a Failing Constructor

Static initialization can throw an exception. An unhandled error during this phase can cause **the runtime class to be marked in an erroneous initialization state**. Within the same class loader, subsequent initialization requests may fail rather than being "retried as if for the first time".

Create the file **`InitializationFailureDemo.java`**:

~~~java
class BrokenService {
    static int port = readConfiguration();

    private static int readConfiguration() {
        System.out.println("BrokenService initializing");
        throw new IllegalStateException("bad config");
    }
}

public class InitializationFailureDemo {
    static void use() {
        System.out.println(BrokenService.port);
    }

    public static void main(String[] args) {
        try {
            use();
        } catch (ExceptionInInitializerError ex) {
            System.out.println("first="
                    + ex.getClass().getSimpleName());
        }

        try {
            use();
        } catch (NoClassDefFoundError ex) {
            System.out.println("second="
                    + ex.getClass().getSimpleName());
        }
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 InitializationFailureDemo.java
java InitializationFailureDemo
~~~

**Stdout:**

~~~text
BrokenService initializing
first=ExceptionInInitializerError
second=NoClassDefFoundError
~~~

Explanation:

1. The first read of `BrokenService.port` requires the class to be initialized.
2. `readConfiguration()` prints the message and then throws `IllegalStateException`.
3. The JVM handles this failure under the class initialization mechanism; in this situation where a non-`Error` exception is thrown, the caller observes `ExceptionInInitializerError`.
4. The class is now in an erroneous initialization state. The next usage request does not restart the initializer; in the example, the caller catches `NoClassDefFoundError`.

**Distinguishing from an instance creation failure:** if a normal constructor throws `IllegalArgumentException` while validating input data, that does not necessarily mark the class as having failed initialization. The caller can fix the input and create another instance. Static initialization is part of the **class lifecycle**, so errors here are typically more severe and require appropriate configuration design.

## 18. `ClassNotFoundException`, `NoClassDefFoundError`, and `ExceptionInInitializerError`

These three names are often confused:

| Error/Exception Type | Example Meaning | Where Commonly Seen |
| --- | --- | --- |
| `ClassNotFoundException` | An API looking up a class by name cannot find the requested definition | `Class.forName("...")`, `ClassLoader.loadClass` |
| `NoClassDefFoundError` | The JVM cannot use a required class definition at runtime; can also occur when the class is in a failed initialization state | Executing code referencing a missing or failed-to-initialize class |
| `ExceptionInInitializerError` | An exception arising during class initialization is wrapped by the JVM into the corresponding error | Static initializer or static field initializer throws an error |

A `NoClassDefFoundError` does not conclusively prove that the `.class` file does not exist: it **can also be the consequence of a previous failed initialization**, as in the example just run.

A `ClassNotFoundException` is typically a checked exception thrown by name-based lookup APIs. Conversely, `NoClassDefFoundError` and `ExceptionInInitializerError` belong to the `Error` hierarchy. In an application, do not use a broad `catch (Error)` to swallow these errors and continue as if nothing happened; investigate the classpath, binary compatibility, static initializer errors, and the startup process.

## 19. Class Initialization When Multiple Threads Trigger It Concurrently

The JVM must coordinate when multiple threads concurrently request initialization of the same runtime class. [JLS §12.4.2](https://docs.oracle.com/javase/specs/jls/se17/html/jls-12.html#jls-12.4.2) describes the state and synchronization mechanism so that a valid initialization is not executed concurrently like two independent programs.

For example, if two threads concurrently invoke a static method of `Settings` for the first time:

~~~java
Settings.getInstance();
~~~

this is an **illustrative** call, with no standalone `Settings` definition here. The JVM ensures the class initialization process is managed under its own rules, rather than letting two threads run two copies of the same class's static initializer simultaneously.

However, **safely coordinated class initialization does not mean every mutable static field is thread-safe afterward**. For example:

~~~java
class SharedCounter {
    static int value;

    static void increment() {
        value++;
    }
}
~~~

After initialization, if multiple threads concurrently call `increment()`, the `value++` operation remains a non-atomic read–modify–write sequence. You need `synchronized`, atomics, or an equivalent mechanism if cross-thread consistency is required.

A common pattern is the *initialization-on-demand holder idiom*: a static nested class holds a `static final` instance initialized through class initialization when the holder class is first actively used. The simplicity of this pattern comes from the JVM's class initialization guarantee, not because every static method is automatically synchronized.

## 20. The Holder Pattern: Using Initialization on Demand

Create the file **`HolderInitializationDemo.java`**:

~~~java
final class ConfigService {
    private ConfigService() {
        System.out.println("ConfigService constructed");
    }

    static ConfigService instance() {
        System.out.println("request");
        return Holder.INSTANCE;
    }

    private static class Holder {
        static final ConfigService INSTANCE = new ConfigService();

        static {
            System.out.println("Holder initialized");
        }
    }
}

public class HolderInitializationDemo {
    public static void main(String[] args) {
        System.out.println("begin");
        ConfigService first = ConfigService.instance();
        ConfigService second = ConfigService.instance();
        System.out.println("same=" + (first == second));
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 HolderInitializationDemo.java
java HolderInitializationDemo
~~~

**Stdout:**

~~~text
begin
request
ConfigService constructed
Holder initialized
request
same=true
~~~

Execution flow:

1. `ConfigService.instance()` is a static method of `ConfigService`, so the outer class is initialized if needed. However, the `Holder` class **is not forced to initialize merely because it is nested inside**.
2. When the method accesses `Holder.INSTANCE` for the first time, the JVM requires initialization of the `Holder` class.
3. The static field initializer creates a `ConfigService` (the constructor prints `ConfigService constructed`), and then Holder's static block prints `Holder initialized`.
4. The second `instance()` call simply reads the existing `Holder.INSTANCE` without creating another object. Both references compare equal with `==` because they point to the same instance.

This example introduces **the benefit of controlled on-demand initialization**. In a real-world application, if a singleton has mutable state, the methods operating on that state must still follow their own thread-safety rules.

## 21. Observation Tools: `javap` and Class Loading Logs

For deeper study, you can compile an example and inspect its bytecode/class file:

~~~bash
javac -encoding UTF-8 StaticTextualOrderDemo.java
javap -c -p Ordered
javap -v -p Ordered
~~~

`javap` lets you inspect methods and instructions. For classes with static field initializers or static initializer blocks, the compiler may generate a special method named **`<clinit>`** in the class file to perform class initialization. Not every class must have `<clinit>`; a class containing only constant variables may not need the corresponding initialization code.

When using Java 17, common HotSpot/OpenJDK JVMs can enable class loading logs with an option such as:

~~~bash
java -Xlog:class+load=info SuperclassInitializationDemo
~~~

Actual logs include class loading information from the JVM/JDK and the application; **the content, order, and line count depend on the runtime**, so this lesson does not provide hypothetical stdout for this command. Do not assume every Java runtime shares the exact same log format or diagnostic configuration.

A more reliable observation workflow for this lesson:

1. Run the program **without logging enabled** to confirm the listed application stdout.
2. Use `javap` to inspect the methods/bytecode related to static code.
3. Enable class loading logs when you need to find out from which source a class was loaded.
4. Compare: a class may appear in the **loading log** earlier than when its static initializer prints a message.

**Avoid confusing class loading logs with initialization logs.** A "class loaded" line does not mean `<clinit>` has completed; to know that, check actual behavior and use the appropriate tools.

## 22. Distinguishing Several Common Points in Time

| Operation | Requires Loading/Linking? | Requires Initialization of the Target Type? |
| --- | --- | --- |
| JVM runs `Main.main` | Must prepare the required types | `Main` must be initialized before `main` |
| `Class.forName("T")` | Uses mechanism to find/define the type | Yes, per the single-parameter API |
| `Class.forName("T", false, loader)` | May load/link to obtain `Class` | **Does not** require initialization |
| `loader.loadClass("T")` | Requests loading | Does not by itself require initialization |
| `T.class` | JVM processes the class literal | Does not by itself require initialization |
| `new T[3]` | Creates the appropriate array class/object | Does not by itself initialize component `T` |
| `new T()` | JVM must be ready to use `T` | Yes, if not yet initialized |
| `T.staticMethod()` | Resolves the call | Yes, for the class actually declaring the method |
| `T.staticNonconstantField` | Resolves the field | Yes, for the type declaring the field |
| `T.COMPILE_TIME_CONSTANT` | May be inlined at compile time | Not merely from reading the constant variable |
| Accessing an inherited static field via a subclass | Resolves to the declared field | Only requires initializing the type that **declares** the field |
| Creating a second instance of an already-initialized class | Can reuse the class state | Does not re-run static code |

The loading/linking column **describes type requirements**, not a guarantee of when each substep executes in the JVM. As for resolution, one cannot claim "all related references must complete" based solely on a single Java expression.

## 23. Common Reasoning Mistakes

| Incorrect Claim | Why It Is Wrong | Correct Understanding |
| --- | --- | --- |
| "Once a class file is loaded, the static block has already run." | Loading and initialization are two distinct phases | Wait for an initialization trigger |
| "Linking is running the static initializer." | Linking primarily performs verification/preparation/resolution | Static code runs during initialization |
| "Preparation calls `static int x = compute();`." | Preparation does not execute arbitrary source initializer expressions | `compute()` runs when the class is initialized |
| "Resolution always completes entirely before initialization." | The JVM is allowed to defer resolution | Do not collapse the three substeps into a rigid order |
| "Whenever a type name is used, it gets initialized." | Many operations are only class literals, type declarations, or arrays | Check the active-use triggers |
| "`new T[5]` invokes constructor `T` five times." | It only creates an array object with 5 reference elements | `new T()` is needed for each instance |
| "Reading a `static final` always triggers init." | Compile-time constant variables are an exception | Check whether it is a constant expression |
| "`Class.forName(name,false,...)` still runs the static block." | The false argument requests no initialization | Use true or an active use when needed |
| "`Class.forName(name)` creates an object of that class." | The API returns `Class` metadata and requests initialization | It does not invoke the instance constructor |
| "The subclass static block always runs when accessing an inherited field." | Initialization depends on the type actually declaring the field | Access `Base.field` for clarity |
| "Initializing an interface always initializes its superinterfaces." | The JLS does not establish that rule by default | Examine which interface is actively used |
| "Does the superclass constructor run before the subclass static block?" | Confuses class initialization with object construction | Class initialization follows inheritance before instance constructors |
| "If class init fails, the JVM automatically re-runs the static block next time." | The class may be marked as having erroneous initialization | Fix the root cause and the loader/runtime environment |
| "Since static initialization is safe, any `static int++` is also safe." | Initialization guarantees do not make increment operations atomic | Use synchronization/atomics when sharing mutable state |
| "The same class name in two loaders always shares the same static field." | Runtime identity includes the defining loader | They can be two separate classes with separate static state |

If you see an unexpected output order, note **the class declaring the field/method**, **which line causes active use**, **the textual order of initializers**, and **the superclass/interface relationship**. That is usually sufficient to explain it without guessing that the JVM "loaded randomly".

## 24. Guide to Solving Initialization-Order Exercises

When a problem gives a class hierarchy and asks what the program prints, proceed step by step:

1. **List the classes/interfaces that have static blocks or nonconstant field initializers.**
2. **Identify the first active-use action** for each type: `new`, static method, nonconstant static field, reflection requiring init.
3. **Eliminate false assumptions**: class literals, reference-only arrays, and compile-time constants do not by themselves require component/class initialization.
4. **Check the superclass** before executing the subclass's static initializers; for interfaces and default methods, apply the appropriate JLS rules.
5. For a class currently being initialized, **execute field initializers and static blocks in source order**.
6. Mark that class as **initialized**; subsequent uses do not re-run static code.
7. If there is a `new`, continue analyzing the constructor chain, instance field initializers, and superclass/subclass constructors for **each object**.
8. If static initialization throws an error, account for the erroneous class state and subsequent uses; do not try to keep computing stdout as if the class had still initialized successfully.

For questions asking only about the **loading/linking phase**, do not use static output logs to assert the exact timing of resolution: that depends on the implementation and broader JVM rules.

1. Loading defines the runtime type; linking consists of verification/preparation/resolution; initialization runs static field initializers and static blocks.
2. No. Preparation prepares the field with the appropriate initial value; `compute()` runs upon initialization.

**Conclusion:** Loading enables the JVM to **obtain the runtime definition of a type**; linking **verifies, prepares, and resolves the necessary linkages**; initialization is the phase that **runs static initializers**. The three steps are not three synonyms. Only actions specified by Java force a class/interface to be initialized; class literals, reference-only arrays, and compile-time constants are easily confused cases. After a class is successfully initialized, static initializers do not run again for each object creation, whereas constructors still run for every instance.
