# Programmer-Declared No-Argument Constructors in Java

## Learning Objectives

After this lesson, you will be able to:

- Correctly write a programmer-declared **no-argument constructor** (or *no-arg constructor*) in a Java class.
- Distinguish an **explicitly declared** no-argument constructor from a **default constructor** automatically generated by the compiler when a class declares no constructors at all.
- Explain the meaning of `new ClassName()`, how instance fields are initialized, the initialization order, and the role of constructors in ensuring a valid object state.
- Understand why Java no longer automatically provides a default constructor once you declare a parameterized constructor, and know how to declare an additional no-arg constructor if the API requires one.
- Use `this(...)` to delegate to another constructor, and distinguish it from `super(...)` and the implicit `super()` call.
- Apply `public`, `protected`, package-private, and `private` to constructors; distinguish constructor invocation access from class accessibility.
- Diagnose common errors: declaring a return type, misspelling the name, calling a nonexistent constructor, failing to assign a `final` field, or being unable to invoke the superclass constructor.
- Compile and run Java 17+ examples with deterministic output.

## 1. What Is a No-Argument Constructor?

A **constructor** is a special member of a class that executes during object creation via `new` or another appropriate Java object-creation mechanism. A constructor:

- Has the **exact same name as the class**.
- **Does not declare a return type** — neither `void` nor any other type.
- Has its own parameter list, which can be empty or have multiple parameters.
- Can initialize instance fields, check conditions, and establish object *invariants*.
- Is not an ordinary method: a constructor is not inherited, overridden, or invoked like `object.ConstructorName()`.

A **programmer-declared no-argument constructor** is a constructor explicitly written in source code with **empty `()`** parentheses, for example:

~~~java
public class Lamp {
    private boolean on;
    private int brightness;

    public Lamp() {
        on = false;
        brightness = 50;
    }

    public boolean isOn() {
        return on;
    }

    public int getBrightness() {
        return brightness;
    }
}
~~~

This is a compilable `Lamp.java` file, without a `main` method to run directly. `public Lamp()` is a constructor with no formal parameters, written by the programmer. When external code with appropriate access calls `new Lamp()`, the new object has `on == false` and `brightness == 50` once the constructor completes normally.

General structure for a class named `ClassName`:

~~~java
[accessModifier] ClassName() {
    // Valid initialization statements
}
~~~

The `[accessModifier]` part represents an optional component in the syntax diagram, **not** literal `[]` characters to type in Java. The access modifier can be `public`, `protected`, `private`, or omitted for package-private access. A constructor can also declare a `throws` clause and, in some cases, appropriate annotations or type parameters; however, it **must not** declare `static`, `final`, `abstract`, or a return type like a method.

## 2. Distinguishing a Programmer-Written No-Arg Constructor from a Compiler-Generated Default Constructor

Both of the following classes can be instantiated with `new Type()`, but **their constructors come from two different sources**:

~~~java
class AutoCreated {
    int quantity = 7;
    // No constructor declared: the compiler provides a default constructor.
}

class ManuallyCreated {
    private final int quantity;

    ManuallyCreated() {
        quantity = 7; // Explicit no-argument constructor.
    }
}
~~~

In `AutoCreated`, the value 7 comes from a **field initializer**, not from user-written code in a default constructor. In `ManuallyCreated`, the assignment of 7 is inside the `ManuallyCreated()` constructor, and the compiler **does not** generate an additional default constructor.

| Condition | No-argument constructor invoked |
| --- | --- |
| Class declares no constructors | *Default constructor* implicitly provided by the compiler |
| Class explicitly declares `X()` | Programmer's *explicit no-arg constructor* |
| Class only declares `X(int n)` | No automatic `X()`; `new X()` is a compile-time error |

The chapter on *default constructors* thoroughly explains the conditions under which the compiler generates one, its accessibility, and superclass relationships. **The focus of this lesson** is: when you **actively write `X()`**, you can choose meaningful initial values, initialize `final` fields, check invariants, or call `this(...)` to reuse a parameterized constructor. Looking at `new X()` alone does not tell you whether the constructor is implicitly generated or explicitly written; you must read the class declaration.

## 3. Correct Syntax of a No-Argument Constructor

~~~java
public class Device {
    private String model;
    private boolean enabled;

    public Device() {
        model = "Generic";
        enabled = true;
    }
}
~~~

This is a compilable `Device.java` file. Points to check:

1. The constructor name is **`Device`**, matching the class name `Device` exactly, which is case-sensitive.
2. There are no parameters between `(` and `)`.
3. There is no `void` or return type before `Device`.
4. The constructor body is a `{ ... }` block; this is where state can be validated and initialized.
5. The constructor has `public` access; calling it from another class also depends on class accessibility and the corresponding module/package rules.

Comparison of forms:

| Declaration | Conclusion |
| --- | --- |
| `public Device() { }` | Valid explicit no-argument constructor |
| `Device() { }` | No-argument constructor with package-private access |
| `private Device() { }` | No-argument constructor that can only be invoked where private access is permitted |
| `public void Device() { }` | **Ordinary method** with a `void` return type, not a constructor |
| `public device() { }` in class `Device` | Invalid constructor declaration because the casing differs; typically causes an error for a method declaration missing a return type |
| `public static Device() { }` | Invalid syntax/declaration; constructors cannot be `static` |
| `public final Device() { }` | Invalid; `final` is not a valid constructor modifier |
| `public Device(int id) { }` | Constructor **with one parameter**, not a no-arg constructor |

A constructor **does not declare `return value;`**. Within a constructor, an empty `return;` without a value can be used according to language rules to return early, though it should be avoided if it can easily leave the object state inconsistent.

## 4. Complete Java 17+ Example: No-Arg Constructor and Parameterized Constructor

Save the code below as **`NoArgConstructorDemo.java`**:

~~~java
public class NoArgConstructorDemo {
    static final class Notebook {
        private final String title;
        private int pages = 20;
        private boolean archived;
        private static int created;

        Notebook() {
            this("Untitled");
        }

        Notebook(String title) {
            if (title == null || title.isBlank()) {
                throw new IllegalArgumentException("title is required");
            }
            this.title = title;
            created++;
        }

        void addPages(int more) {
            if (more <= 0) {
                throw new IllegalArgumentException("more must be positive");
            }
            pages += more;
        }

        String summary() {
            return title + ": pages=" + pages + ", archived=" + archived;
        }

        static int createdCount() {
            return created;
        }
    }

    public static void main(String[] args) {
        Notebook first = new Notebook();
        Notebook second = new Notebook("Java");

        second.addPages(5);

        System.out.println(first.summary());
        System.out.println(second.summary());
        System.out.println("created=" + Notebook.createdCount());
    }
}
~~~

Compile and run with JDK 17 or later in the directory containing the file:

~~~bash
javac -encoding UTF-8 NoArgConstructorDemo.java
java NoArgConstructorDemo
~~~

Output:

~~~text
Untitled: pages=20, archived=false
Java: pages=25, archived=false
created=2
~~~

**Analysis:**

1. `new Notebook()` selects the programmer-written **no-argument** `Notebook()` constructor.
2. The first line of the `Notebook()` constructor body is `this("Untitled");`. This calls **another constructor in the same class**.
3. The `Notebook(String title)` constructor validates `title` and assigns `"Untitled"` to the `final title` field. It increments `created` once.
4. `new Notebook("Java")` directly invokes the parameterized constructor. It initializes the `title` field to `"Java"` and increments `created` once more.
5. `pages = 20` is an **instance field initializer**, which runs during the initialization of **each object**; both objects initially have `20` pages.
6. `archived` has no initializer, so it receives the default value `false`.
7. `second.addPages(5)` modifies `pages` of the second object from `20` to `25`. The first object remains at `20`.
8. `created` is a static field shared across the `Notebook` class, so after two successful instantiations its value is `2`.

This example is important because the `()` constructor **is not required to assign every field itself**: it can delegate via `this(...)` to avoid duplicating logic and let the parameterized constructor serve as the centralized point for data validation.

### 4.1. Why Is `this(...)` Useful?

If you write two constructors manually as follows:

~~~java
class Example {
    private final String title;
    private int pages;

    Example() {
        this.title = "Untitled";
        this.pages = 20;
    }

    Example(String title) {
        this.title = title;
        this.pages = 20;
    }
}
~~~

This is a valid illustrative class, but the `pages = 20` logic is duplicated. When requirements change, it is easy to update one place and forget the other.

It can be replaced with **constructor chaining**:

~~~java
class Example {
    private final String title;
    private final int pages;

    Example() {
        this("Untitled", 20);
    }

    Example(String title, int pages) {
        this.title = title;
        this.pages = pages;
    }
}
~~~

Now the logic for assigning `final` fields resides in a single primary constructor. The two `Example` class snippets above are **two alternative approaches**, not two `Example` classes declared simultaneously in the same package/file.

## 5. Field Default Values and No-Argument Constructors

If a field has no initializer, Java still assigns a **default value** to the field during object creation. A no-arg constructor can keep those values as is or overwrite them.

| Field type | Default value |
| --- | --- |
| `byte`, `short`, `int` | `0` |
| `long` | `0L` |
| `float` | `0.0f` |
| `double` | `0.0d` |
| `boolean` | `false` |
| `char` | UTF-16 code value of 0 |
| Reference types: `String`, arrays, collections, other classes | `null` |

For example, an empty constructor does not automatically change a `String name;` field to an empty string `""` and does not automatically create `new ArrayList<>()`. If business logic requires a non-null value, the programmer must initialize it in a field initializer, instance initializer, constructor, or another valid design path.

Save **`DefaultVsExplicitDemo.java`**:

~~~java
public class DefaultVsExplicitDemo {
    static class Implicit {
        int value = 7;
        // No constructor declared: the compiler provides a default constructor.
    }

    static class Explicit {
        int value;
        Explicit() {
            value = 9;
        }
    }

    static class OnlyParameterized {
        int value;

        OnlyParameterized(int value) {
            this.value = value;
        }
    }

    static class EmptyExplicit {
        int number;
        boolean ready;
        String text;

        EmptyExplicit() {
            // Empty explicit constructor.
        }
    }

    public static void main(String[] args) {
        System.out.println("implicit=" + new Implicit().value);
        System.out.println("explicit=" + new Explicit().value);
        System.out.println("parameterized=" + new OnlyParameterized(11).value);

        EmptyExplicit empty = new EmptyExplicit();
        System.out.println("empty=" + empty.number + ","
                + empty.ready + "," + empty.text);

        // new OnlyParameterized(); // Does not compile: missing () constructor.
    }
}
~~~

Run:

~~~bash
javac DefaultVsExplicitDemo.java
java DefaultVsExplicitDemo
~~~

Output:

~~~text
implicit=7
explicit=9
parameterized=11
empty=0,false,null
~~~

`Implicit` declares no constructor, so it has a compiler-provided default constructor. `Explicit` and `EmptyExplicit` declare explicit no-arg constructors. `OnlyParameterized` only has a constructor taking an `int`, so it **does not have** a default `()` constructor.

In `EmptyExplicit`, the empty constructor is valid because ordinary fields receive default values; you **should not** infer that every resulting object thereby satisfies business requirements such as "`text` is non-null".

## 6. Initialization Order When Calling `new ClassName()`

Do not assume that the constructor is the first statement to run on a new object. For an ordinary class, the general order is:

1. **Object allocation**, where all instance fields first receive **default values**.
2. Execution of the appropriate constructor chain, including superclass constructors, according to the rules for calling `super(...)` or `this(...)`.
3. Each class's **field initializers** and **instance initializer blocks** are executed at the appropriate point during that class's initialization, in the order they appear in the source code.
4. Execution of the corresponding constructor body after the superclass initialization steps and the current class's instance initializers.
5. If the constructor completes normally, the `new` expression returns a reference to the initialized object.

In the no-arg constructor example with the `this("Untitled")` call, delegation **does not cause field initializers to run twice** for the same object. Only when the constructor chain ends at a constructor that no longer calls `this(...)` does execution proceed through the superclass call and run the class's field initializers according to the rules.

### 6.1. Initialization Order Example with Inheritance

Save as **`NoArgInitializationOrderDemo.java`**:

~~~java
public class NoArgInitializationOrderDemo {
    static int trace(String text, int value) {
        System.out.println(text);
        return value;
    }

    static class Base {
        int baseValue = trace("base field initializer", 1);

        Base() {
            System.out.println("Base constructor");
        }
    }

    static class Child extends Base {
        int count = trace("child field initializer", 2);

        {
            System.out.println("child initializer block");
            count += 3;
        }

        Child() {
            // Java 17 inserts an implicit super() call here.
            System.out.println("Child constructor");
            count += 4;
        }
    }

    public static void main(String[] args) {
        Child child = new Child();
        System.out.println("result=" + child.baseValue + "," + child.count);
    }
}
~~~

Run:

~~~bash
javac NoArgInitializationOrderDemo.java
java NoArgInitializationOrderDemo
~~~

Output:

~~~text
base field initializer
Base constructor
child field initializer
child initializer block
Child constructor
result=1,9
~~~

The output shows that:

- The initialization of `Base` executes before that of `Child`.
- `count` is assigned `2`, then the block increments it to `5`, and then the constructor body increments it to `9`.
- There is no explicit `super()` call written in the `Child()` constructor, so under Java 17 rules the compiler inserts an implicit `super();` call at the beginning of the constructor.
- The superclass must have an **accessible** no-argument constructor if the subclass constructor relies on an implicit `super()` call.

**Note:** A comment line is not a `super();` statement. If you want to write it explicitly, Java 17 requires `super();` or `this(...);` to be placed as the first constructor invocation statement; do not place a logging statement before it.

## 7. Constructor Chaining: `this()`, `this(...)`, and `super()`

A constructor can invoke another constructor using:

- **`this(...)`**: calls another constructor of the **same class**, for example `this("Guest")`.
- **`super(...)`**: calls a constructor of the **superclass**, for example `super(5)`.

In **Java 17**, an explicit `this(...)` or `super(...)` constructor call must be the **first statement** in the constructor body. If there is no explicit call, the compiler inserts an implicit `super();` for the constructor of an appropriate ordinary class. Two explicit calls cannot simultaneously occupy the first position in a constructor.

Example:

~~~java
class User {
    private final String name;

    User() {
        this("Guest");
    }

    User(String name) {
        this.name = name;
    }
}
~~~

The no-arg constructor `User()` delegates the responsibility of assigning `name` to the `User(String)` constructor. This avoids duplicating logic and requires validating the name in only one place if the problem requires validation.

Constructors **must not form a recursive cycle**:

~~~java
// Invalid example; do not include in the same program for compilation:
// class Loop {
//     Loop() { this(1); }
//     Loop(int n) { this(); }
// }
~~~

The cycle `Loop() -> Loop(int) -> Loop()` results in a compile-time error due to recursive constructor invocation. Each delegation chain must reach a constructor that does not delegate further within the same class.

### 7.1. When the Superclass Has No No-Argument Constructor

Suppose:

~~~java
class Parent {
    Parent(String name) {
    }
}

class Child extends Parent {
    Child() {
        // Java attempts to call super() implicitly,
        // but Parent has no () constructor.
    }
}
~~~

This is an **intentionally invalid example**: `Parent` only has the `Parent(String)` constructor; `Child()` cannot call `super()` implicitly because that superclass constructor does not exist.

Fix it by calling the appropriate superclass constructor **on the very first line**:

~~~java
class Parent {
    private final String name;

    Parent(String name) {
        this.name = name;
    }

    String name() {
        return name;
    }
}

class Child extends Parent {
    Child() {
        super("Default parent");
    }
}
~~~

The alternative class snippet above **compiles validly** in an appropriate Java file, even though it does not yet have a `main` method to run. `Child()` is a **programmer-written no-argument constructor**; it still has the right to call `super("Default parent")` inside. "No-argument" describes **`Child()`'s parameter list**, not a requirement that the constructor must call a no-argument `super()`.

**Distinction:** a no-argument constructor in a subclass **does not require** the superclass to have a no-arg constructor, provided the subclass constructor selects a valid superclass invocation path. However, if the subclass constructor **has no explicit call**, the compiler tries `super()` by default.

## 8. Initializing `final` Fields in a No-Argument Constructor

A `final` instance field without an initializer at its declaration is called a **blank final field**. Java requires any constructor that completes normally to ensure this field is assigned according to definite assignment rules.

Valid example:

~~~java
class Session {
    private final String token;
    private final int attempts;

    Session() {
        token = "anonymous";
        attempts = 0;
    }
}
~~~

The no-arg constructor assigns both blank final fields, so it is valid.

**Invalid** example:

~~~java
// Intentionally invalid code:
// class Session {
//     private final String token;
//     Session() {
//         // Missing assignment to token on the normal completion path of the constructor.
//     }
// }
~~~

The compiler rejects a constructor that has a normal completion path where a required blank final field has not yet been assigned.

You can use chaining so that another constructor assigns the final fields:

~~~java
class Session {
    private final String token;

    Session() {
        this("anonymous");
    }

    Session(String token) {
        this.token = token;
    }
}
~~~

This is an **alternative approach** to declaring the `Session` class, not an additional snippet placed simultaneously beneath the previous `Session` class. In the no-arg constructor, you should not attempt to assign `token` **a second time** after the `Session(String)` constructor has already assigned it: `final` prevents reassignment under Java rules.

**Note:** A reference-type `final` field does not automatically make the referenced object immutable. For instance, `final List<String> tags` can point to an `ArrayList` whose elements can still be modified. The no-arg constructor must ensure a valid state rather than relying on `final` to protect the entire object graph.

## 9. Access Scope of a No-Argument Constructor

A constructor can have its own access modifier, which affects where `new ClassName()` is permitted to be called.

| Declaration | Callability under normal scope rules |
| --- | --- |
| `public Widget() { }` | Anywhere the class, constructor, and corresponding module/package are accessible |
| `protected Widget() { }` | Same package and inheritance contexts permitted by Java; specific rules apply when called from another package |
| `Widget() { }` | Package-private: callable from authorized code in the same package |
| `private Widget() { }` | Callable within the private scope permitted by Java (including *nestmates* cases) |

**A public class does not automatically create a public constructor.** For example:

~~~java
public class Service {
    Service() {
    }
}
~~~

This is a valid `Service.java` file. `Service` is a `public` type, whereas the `Service()` constructor is **package-private** because it has no modifier; code in another package cannot use `new Service()` directly.

If the class serves as a public API and external callers are expected to instantiate it using `()`, explicitly declare the constructor `public`:

~~~java
public class Service {
    public Service() {
    }
}
~~~

The two `Service` snippets are **two alternative approaches**.

### 9.1. Private No-Arg Constructor to Control Object Creation

Save the file **`PrivateConstructorDemo.java`**:

~~~java
public class PrivateConstructorDemo {
    static final class Config {
        private final int port;

        private Config() {
            port = 8080;
        }

        static Config createDefault() {
            return new Config();
        }

        int port() {
            return port;
        }
    }

    public static void main(String[] args) {
        Config config = Config.createDefault();
        System.out.println("port=" + config.port());

        // In an enclosing class within the same nest, some private accesses
        // can still be valid; avoid inferring that private is an absolute
        // security boundary against code allowed to run with the same privileges.
    }
}
~~~

Compile and run:

~~~bash
javac PrivateConstructorDemo.java
java PrivateConstructorDemo
~~~

Output:

~~~text
port=8080
~~~

Here `Config()` is a **private no-arg constructor**, which cannot be directly accessed by arbitrary code outside the private scope. The `createDefault()` method provided by the class is a **static factory** to control object creation. This pattern can be used when you want to keep object creation control in one place, but a private constructor **does not automatically turn a class into a singleton**: each time the factory executes `new Config()`, it still creates a new object.

For a **utility class** containing only static methods, an empty private constructor is also commonly used to prevent unnecessary `new` calls. However, if the design is intended for inheritance, a private constructor can prevent subclasses from invoking the superclass constructor, so an appropriate access modifier must be chosen.

### 9.2. Implicit Default Constructors Also Have an Access Level

If a class declares no constructor, the compiler provides a default constructor with accessibility determined by the rules of the corresponding Java class. Therefore, **do not assume** that a class with an implicit constructor can always be instantiated from any package. For libraries, writing an explicit constructor often helps readers clearly see the object-creation API, especially when non-default access levels are required.

## 10. Validation and Exceptions in a No-Arg Constructor

A no-argument constructor **does not receive data directly from the caller**, yet it can still establish a valid state, use intentional default values, or throw an exception if initialization cannot succeed.

Example:

~~~java
class Counter {
    private int value;

    Counter() {
        value = 0;
    }

    int current() {
        return value;
    }
}
~~~

This is a valid class snippet. Even though an `int` field already defaults to `0`, the explicit assignment `value = 0;` can still have value in **communicating intent**: the new object starts in state 0.

If business logic requires a default timestamp or configuration value, consider:

- **An explicit fixed value** if behavior needs to be deterministic, for example `timeoutSeconds = 30`.
- **Computing from the time of object creation**, if required by the specification, while understanding that output may vary on each run; do not promise fixed stdout for the current time.
- **Calling another constructor with `this(...)`** to reuse data validation.
- **A factory method** when object creation requires complex steps, potential I/O errors, or multiple configuration sources.

If a constructor throws an exception before completing normally, the `new` expression does not return an object to the caller along that execution path. Side effects performed before the exception (such as modifying a static field or writing logs) are not automatically rolled back. Therefore, you should avoid exposing a partially initialized `this` object to external code.

### 10.1. A Constructor Can Declare `throws`

Example:

~~~java
class Connection {
    Connection() throws java.io.IOException {
        // Example illustrating the ability to declare a checked exception.
    }
}
~~~

The declaration above is **syntactically valid**; callers of `new Connection()` must handle or declare the corresponding checked exception according to Java rules. A no-argument constructor can still have **`throws`**, because `throws` is not a formal parameter.

However, you should not arbitrarily declare checked exceptions when the constructor performs no corresponding failure-prone operation. A class that requires network or file connections may be better designed with a factory or a separate resource-opening operation, depending on requirements.

## 11. No-Argument Constructors and Overloading

**Constructor overloading** allows a class to declare multiple constructors with **different parameter type lists**. Example:

~~~java
class Point {
    private final int x;
    private final int y;

    Point() {
        this(0, 0);
    }

    Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
}
~~~

This class compiles validly when placed in an appropriate file. The two constructors have different signatures: `Point()` and `Point(int,int)`.

- `new Point()` selects the no-argument constructor.
- `new Point(3, 4)` selects the two-parameter constructor.
- `new Point(3)` is **invalid** because the class does not provide a single-parameter constructor.

Java **does not support default parameter syntax** such as `Point(int x = 0)` in constructor declarations. If you want to provide default values, you can use a `()` overload and delegate with `this(...)` as shown above.

You cannot create two overloads that differ only by access modifier or `throws` while having the same parameter list:

~~~java
// These two lines cannot appear together in class Point:
// public Point() { }
// private Point() throws Exception { }
~~~

Both declare a constructor with an empty parameter list `Point()`; differing access modifiers and `throws` clauses do not create a new constructor signature.

### 11.1. Impact of Adding a Parameterized Constructor to an Existing Class

Initially:

~~~java
class Settings {
    int timeout = 10;
}
~~~

The compiler generates a default constructor, so `new Settings()` is valid. If you modify the class to:

~~~java
class Settings {
    int timeout;

    Settings(int timeout) {
        this.timeout = timeout;
    }
}
~~~

then client code still calling `new Settings()` will **fail to compile** when recompiled, because the implicit default constructor has disappeared.

If you want to preserve the existing API, explicitly declare:

~~~java
class Settings {
    int timeout;

    Settings() {
        this(10);
    }

    Settings(int timeout) {
        this.timeout = timeout;
    }
}
~~~

The three `Settings` class snippets are **three alternative design versions**, not declared simultaneously. Modifying constructors can affect both **source compatibility** and binary compatibility of a library already in use, so call sites should be tested.

## 12. When Should You Declare a No-Arg Constructor?

### Appropriate

1. **Objects with a valid default state**: `new Counter()` starts at 0; `new Notebook()` creates an object with a default title and initial page count.
2. **Needing a convenient object-creation API** alongside a detailed constructor: `new Point()` delegates via `this(0,0)`.
3. **Needing to preserve `new X()` usage** when adding a parameterized constructor to an existing class.
4. **Libraries or frameworks requiring an accessible 0-argument constructor**: this requirement may exist in reflection tools, serializers, ORMs, and DI containers. You should read the specific contract of the framework, as each framework has different rules regarding visibility and instantiation.
5. **Needing to control instantiation capability**: `private X()` or a factory helps restrict where objects can be created.

### Requires Consideration or Inappropriate

- When every object **must have data that cannot be validly self-supplied**, such as a non-empty transaction ID or a business key required immediately upon creation, a parameterized constructor or a factory is a better choice.
- When a no-arg constructor creates an object in a **half-initialized state**, forcing the caller to remember to invoke `setX`, `setY`, and `initialize` in the right order. That approach easily leads to omission errors.
- When you want to use a no-arg constructor solely to silence a `new X()` error without understanding why the object needs to be created that way.
- When fields hold mutable data, you need to ensure each instance has its own resources/state if independence is required; avoid using a shared `static` collection while assuming the no-arg constructor created a separate collection.

**Design principle:** a constructor should establish the **object's invariants** so that after successful initialization, public methods can use the state without having to guard against an unready object.

## 13. Common Compile-Time Errors and Misconceptions

| Situation | Cause | Fix |
| --- | --- | --- |
| `constructor X cannot be applied to given types` on `new X()` | The class only has parameterized constructors or an unsuitable no-arg constructor | Declare a valid `X()`, or pass the right arguments |
| `constructor X() is undefined` | There is no `()` constructor usable by the caller | Check the list of existing constructors |
| `void X() { }` written to "create a constructor" | This is a `void` **method**, not a constructor | Write `X() { }` without a return type |
| Writing `static X() { }` | Constructors cannot be `static` | Remove `static`; if a factory is needed, create a static method returning `X` |
| Constructor name differs in letter case | The name must match the class name | Correct it to the exact `ClassName()` |
| Duplicate no-argument constructor declaration | Two constructors share an empty parameter list | Keep a single `()` constructor |
| Adding a parameterized constructor breaks `new X()` | The compiler no longer generates a default constructor | Declare an explicit `X()` if needed |
| `implicit super constructor Parent() is undefined` | `Parent` does not have a suitable no-arg constructor | Write `super(args)` explicitly or redesign the superclass |
| `call to this must be first statement` in Java 17 | Logging or field assignment placed before `this(...)` | Move `this(...)` to the top of the constructor body |
| `recursive constructor invocation` | `this(...)` calls form a cycle | Design a target constructor that does not delegate further |
| `variable x might not have been initialized` for a blank final field | Some constructor completion path fails to assign the `final` field | Assign it on every valid path or delegate to a constructor that assigns it completely |
| `private` constructor cannot be called from another class | Restricted access scope | Use the designed public constructor or factory |
| `public` class with non-`public` constructor | Class access and constructor access are two separate things | Declare `public ClassName()` if needed |
| Assuming an empty constructor initializes `String` to `""` | The default value of a reference field is `null` | Assign explicitly in an initializer or constructor |
| Assuming `new X()` always calls a compiler-generated default constructor | `X()` might be programmer-written | Check the actual declaration in the class |
| Assuming `this(...)` creates another object | Constructor chaining runs on the **same object** | `this(...)` is not `new` |
| Calling `X()` on an object like a method | Constructors are not methods inherited or callable with instance-method syntax | Instantiate with `new X()` or use a factory |

### 13.1. Why Removing an Explicit Constructor May Not Be a Good Fix

If a class has a no-arg constructor that performs validation or assigns important values, deleting it just so the compiler provides an implicit default constructor can alter behavior: those special checks and assignments will disappear. Even though `new X()` still compiles, the object may end up in a different state.

Conversely, if the explicit constructor is **truly empty**, with no special requirements for access modifiers, APIs, frameworks, or documentation, letting the compiler provide a default constructor for a simple class can sometimes be cleaner. However, you should consider accessibility and maintainability before deleting it.

## 14. Self-Check Questions

**Question 1.** Does the class `class Book { String title; }` declare a constructor? Is `new Book()` valid?  
**Answer:** The class has no programmer-declared constructor; the compiler generates an appropriate default constructor, so `new Book()` is valid from locations with access. The `title` field defaults to `null`.

**Question 2.** In the class `class Book { Book(String title) {} }`, does `new Book()` compile?  
**Answer:** No. A parameterized constructor has been declared, so the compiler does not generate an implicit default constructor. You must add `Book()` or pass an appropriate `String`.

**Question 3.** Is `public void Book() { }` a no-argument constructor?  
**Answer:** No. This is an ordinary method because it has a `void` return type. The constructor must be written `public Book() { }`.

**Question 4.** Why is `Book() { this("Untitled"); }` usually better than repeating all assignments across multiple constructors?  
**Answer:** It delegates to a primary constructor to reuse validation and state initialization, avoiding duplicated logic.

**Question 5.** If `Book()` delegates via `this("Untitled")`, does Java create two `Book` objects or run field initializers twice?  
**Answer:** No. This is a constructor chain on the same object; the class's field initializers do not run repeatedly per delegation link.

**Question 6.** The `Child()` constructor writes neither `this(...)` nor `super(...)`, yet `Parent` only has `Parent(int n)`. What is the result?  
**Answer:** If there is no accessible no-argument superclass constructor, the implicit `super()` call causes a compile-time error. It can be fixed with an explicit `super(value)` at the valid position in the subclass constructor.

**Question 7.** `public class Widget` has `Widget() { }` without `public`; can code in another package directly call `new Widget()`?  
**Answer:** No. The class is public, but the constructor is package-private.

**Question 8.** Can a `private Widget() { }` no-arg constructor be called by a `Widget.create()` static factory within the same class?  
**Answer:** Yes. The factory has access to the class's own private constructor and can create and return the object according to the API.

**Question 9.** A blank final instance field has no initializer. Is it valid for a no-arg constructor to complete normally without assigning that field?  
**Answer:** No, unless it has already been initialized in another valid place. The constructor must ensure definite assignment under `final` rules.

**Question 10.** Does `new Lamp()` with an empty `Lamp()` automatically give every field a valid business value?  
**Answer:** No. Fields still receive default values and any applicable initializers, but default values like `null` or `0` may not satisfy application requirements.

**Question 11.** Can two `X()` constructors differing only in `public` and `private` be declared simultaneously?  
**Answer:** No. Both have an empty parameter list, so their constructor signatures collide; access modifiers do not create a distinct overload.

**Question 12.** Does `class C { C() { } }` have an additional compiler-provided default constructor?  
**Answer:** No. This is an explicit no-arg constructor; the compiler does not provide a second default constructor.

## Summary

A **programmer-declared no-argument constructor** is a constructor with the same name as the class, no return type, and an empty parameter list, such as `public User() { ... }`. It differs from a **default constructor**, which is generated by the compiler only when a class declares no constructors at all. Declaring any constructor yourself prevents the compiler from automatically generating a default constructor, so if `new X()` needs to be supported, an explicit no-arg constructor must be written.

A no-arg constructor can initialize fields, check invariants, call `this(...)` to reuse another constructor, or call an appropriate `super(...)`. When neither `this(...)` nor `super(...)` is called explicitly, the implicit `super()` rule requires the superclass to have an accessible no-argument constructor. Pay attention to `final` fields, access modifiers, initialization order, and valid object state: **the goal of a constructor is not merely to make `new X()` compile, but to ensure the object is ready for use after creation**.
