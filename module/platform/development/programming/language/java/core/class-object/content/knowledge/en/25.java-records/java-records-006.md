# Additional Constructors and Delegation to the Canonical Constructor in Java Records (Java 17)

## Objectives and Core Idea

A `record` in Java represents a data class whose **state is defined by the list of record components**. Each record has a **canonical constructor** that accepts the exact component values in declaration order to initialize those component fields.

In addition to the canonical constructor, a record can declare **non-canonical constructors**, also called **additional constructors** or **overloaded constructors**, to provide more convenient ways to create objects: using default values, receiving data in another form, converting parameters, or constructing from a composite input.

**Mandatory rule in Java 17:**

> **Every non-canonical constructor of a record must start with an alternate constructor invocation `this(...)`. The delegation chain can pass through another additional constructor, but must ultimately lead to the canonical constructor of the same record.**

Therefore, an additional constructor **must not directly assign the record component fields itself** like a constructor of a regular class.

Core example:

```java
public record User(String name, int age) {
    public User(String name) {
        this(name, 0);
    }
}
```

- The canonical constructor of `User` has the signature `User(String name, int age)`. Because it is not explicitly declared, Java provides it implicitly.
- `User(String name)` is an **additional** constructor, because it accepts a parameter list different from the component list.
- `this(name, 0);` must be the first statement of the additional constructor.
- The canonical constructor itself ultimately initializes the component fields `name` and `age`.
- `new User("An")` creates `User[name=An, age=0]`, not a second kind of User.

## 1. What Does a Record Have?

Consider the declaration:

```java
record Point(int x, int y) {
}
```

The list `(int x, int y)` declares two **record components**.

According to Java 17, record components lead to:
- Corresponding private final fields.
- Public accessor methods `x()` and `y()`.
- A canonical constructor `Point(int x, int y)` if not explicitly declared.
- Default implementations of `equals`, `hashCode`, and `toString`.
- A special inheritance structure: a record is final and inherits from `java.lang.Record`.

You can create:

```java
Point point = new Point(3, 4);
```

The arguments `3` and `4` are passed to the **canonical constructor**. It assigns the final state `x=3` and `y=4`.

**Note:** a record is not automatically deeply immutable. If a component is a mutable array/list/object, the final field holds a **reference** that cannot be reassigned, but the referent can change if not defensively protected.

## 3. How Many Parameters Does the Canonical Constructor Accept?

Given:

```java
record OrderItem(String sku, int quantity, long unitPrice) {
}
```

The canonical constructor has **three** parameters with the exact types and order:
1. `String sku`;
2. `int quantity`;
3. `long unitPrice`.

By nature, the canonical signature derives from the record header, not from a method name or a convention. When declaring a constructor that accepts **one or two parameters**, it is a non-canonical constructor.

### Distinguishing by Signature

```java
record OrderItem(String sku, int quantity, long unitPrice) {
    OrderItem(String sku) {
        this(sku, 1, 0L);
    }

    OrderItem(String sku, int quantity) {
        this(sku, quantity, 0L);
    }
}
```

Both constructors above are additional constructors:
- `OrderItem(String)`;
- `OrderItem(String, int)`.

They both delegate to the canonical `OrderItem(String, int, long)`. The set of overloads does not introduce any additional state fields beyond the three components.

## 4. Why Does Java Force Additional Constructors to Delegate?

With a regular class, a constructor can directly assign instance fields:

```java
class Person {
    private final String name;
    private final int age;

    Person(String name) {
        this.name = name;
        this.age = 0;
    }
}
```

For a **record**, Java uses the canonical constructor as **a single point of complete initialization for the component fields**. Every non-canonical constructor must go through that constructor instead of choosing its own set of field assignments.

Benefits:
- No constructor overload forgets to initialize a component.
- Canonical validation/normalization is not bypassed.
- Record component state is initialized consistently.
- When adding a new component, the compiler forces constructor delegations to be updated accordingly.
- Preserves the invariant “every record instance has a canonical representation”.

**Important:** the compiler guarantees the **constructor path** and does not automatically prove all business invariants. You still have to code validation properly in the canonical constructor.

## 6. Placement Rule: `this(...)` Must Be the First Statement

In Java 17, an additional constructor must **start with an alternate constructor invocation**:

```java
record Ticket(String id, int priority) {
    Ticket(String id) {
        this(id, 1);
    }
}
```

Invalid:

```java
record Ticket(String id, int priority) {
    Ticket(String id) {
        System.out.println("before");
        this(id, 1);
    }
}
```

This is a **compile-negative snippet**, because `this(...)` is not at the start of the constructor body according to Java 17 rules. Even a log statement, an `if` check, or a local variable declaration before `this(...)` is a violation.

**Version note:** some newer Java versions have changes regarding statements before an explicit constructor invocation. This lesson uses **`--release 17`**; do not apply rules from newer Java versions to Java 17.

### How Do You Compute Values Before Passing Them to the Canonical Constructor?

Put the logic into the **argument expressions** of the `this(...)` call, for example calling a static helper:

```java
record Ticket(String id, int priority) {
    Ticket(String id) {
        this(normalize(id), 1);
    }

    private static String normalize(String id) {
        return id.trim();
    }
}
```

Make sure the helper does not depend on uninitialized instance fields.

## 8. Is a Multi-Constructor Delegation Chain Allowed?

Yes. Additional constructor A can call additional constructor B, and then B calls canonical constructor C.

```text
A (1 argument)
  └── this(...) → B (2 arguments)
                    └── this(...) → C (canonical)
                                      └── initializes components
```

It is not required for **every** non-canonical constructor to call the canonical constructor directly. What is mandatory is that every valid chain of constructor invocations must **ultimately** reach the canonical constructor, must not be circular, and cannot skip the step of initializing the record state.

Example:

```java
record ConnectionOptions(String host, int port, boolean tls) {
    ConnectionOptions(String host) {
        this(host, 443);
    }

    ConnectionOptions(String host, int port) {
        this(host, port, true);
    }
}
```

`new ConnectionOptions("example.com")` calls the one-parameter constructor, then the two-parameter constructor, and then the three-parameter canonical constructor.

### Non-Matching Parameter Count but Different Types?

It is possible to overload with the same number of parameters if the types differ and do not violate signature conflicts; Java uses standard overload resolution. You should avoid ambiguity such as `null` when both `String` and `Integer` exist.

## 10. What Forms Does a Canonical Constructor Have?

Semantically, a Java record has exactly one canonical constructor, which can be provided in one of three ways:

1. **Implicit canonical**, generated by the compiler if you do not declare an explicit canonical constructor.
2. **Normal canonical**, declared by you with a full parameter list matching the components.
3. **Compact canonical**, declared by you using `RecordName { ... }`, without listing parameters.

You **cannot** simultaneously declare both a normal canonical constructor and a compact canonical constructor for the same record.

### 10.1. Implicit Canonical

```java
record Size(int width, int height) {
    Size(int edge) {
        this(edge, edge);
    }
}
```

No normal/compact canonical constructor is declared, yet `this(edge, edge)` still calls the implicit canonical constructor.

### 10.2. Normal Canonical

```java
record Size(int width, int height) {
    Size(int width, int height) {
        if (width < 0 || height < 0) {
            throw new IllegalArgumentException("negative size");
        }
        this.width = width;
        this.height = height;
    }

    Size(int edge) {
        this(edge, edge);
    }
}
```

A normal canonical constructor **must assign all component fields completely**, and the parameter **names and types** must match the record components according to Java 17 rules.

### 10.3. Compact Canonical

```java
record Size(int width, int height) {
    Size {
        if (width < 0 || height < 0) {
            throw new IllegalArgumentException("negative size");
        }
    }

    Size(int edge) {
        this(edge, edge);
    }
}
```

A compact canonical constructor **does not repeat the parameter list**. The compiler automatically assigns the component fields from the implicit parameters **after the compact body completes normally**. Use this form when validation/normalization is the main goal.

## 13. Compact Canonical: Automatic Field Assignment After the Body

Syntax:

```java
record Email(String address) {
    Email {
        address = address.strip().toLowerCase(
                java.util.Locale.ROOT);
    }
}
```

Inside a compact constructor:
- The identifier `address` is an **implicit constructor parameter**.
- You can reassign the parameter `address` to normalize it.
- After the compact body, Java performs the implicit assignment `this.address = address`.
- You must not write `this.address = ...` inside the compact body.
- You must not write `this(...)` inside a compact canonical body.

For a record with multiple components, each component field is assigned from its corresponding parameter after the body.

### The Difference Between `address` and `this.address`

Inside the compact body, `address` represents the parameter, whereas the component field `this.address` has not yet reached the point of being assigned by the implicit assignment. Do not read uninitialized fields to validate; use the parameters.

## 15. Execution Order and Placement of Default Values

Given:

```java
record Value(int x, int y) {
    Value {
        System.out.println("canonical");
    }

    Value(int x) {
        this(x, 0);
        System.out.println("auxiliary");
    }
}
```

`new Value(7)`:
1. Evaluate argument `7`.
2. Select auxiliary constructor `Value(int)`.
3. Execute the `this(7, 0)` call first.
4. The compact canonical constructor runs, performing checks/conversions if any.
5. The compiler assigns component fields from the parameters after the body.
6. Return to the auxiliary constructor and run the `auxiliary` log.
7. Return the completed object to the caller.

It is **not** that the auxiliary constructor creates a temporary object first and then the canonical constructor creates another object. In a single `new`, only **one object** is initialized along the constructor chain.

### When Validation Fails

If the canonical constructor throws an exception:
- Control **does not return to** the statements after `this(...)` in the auxiliary constructor.
- The constructor caller does not receive a completed record instance.
- Side-effect logic before the exception may have already run (avoid unnecessary side effects in constructors).
- The exception propagates until it reaches an appropriate handler.

## 17. Why Is Directly Assigning Component Fields Not Allowed in an Auxiliary Constructor?

Compile-negative:

```java
record Pair(int left, int right) {
    Pair(int value) {
        this.left = value;
        this.right = value;
    }
}
```

Invalid for two related reasons:
- A non-canonical constructor **must begin with an alternate `this(...)` invocation**.
- The component field initialization path belongs to the canonical constructor, not an auxiliary constructor manually assigning fields itself.

Fix:

```java
record Pair(int left, int right) {
    Pair(int value) {
        this(value, value);
    }
}
```

### Do Not Use Initializer Blocks as a Workaround

Records also restrict instance state outside of components:
- Additional non-static instance fields cannot be declared.
- Instance initializer blocks cannot be declared.
- Static members can be declared when appropriate.

The reason is that record state is described by the component header, not by an arbitrarily extended set of fields.

## 18. Compile-Negative: Auxiliary Constructor Omits `this(...)`

```java
record Point(int x, int y) {
    Point() {
        // Missing this(...).
    }
}
```

**Invalid on Java 17.** There is no alternate constructor call at the start of the body.

Fix:

```java
record Point(int x, int y) {
    Point() {
        this(0, 0);
    }
}
```

Java does not automatically “fill in default 0,0” for component fields when a developer declares an empty additional constructor. The record still has a canonical constructor, and the additional constructor must use it.

## 19. Compile-Negative: `super(...)` Does Not Replace `this(...)`

Wrong:

```java
record Point(int x, int y) {
    Point() {
        super();
    }
}
```

`Point` is a record and inherits specially from `java.lang.Record`. A non-canonical constructor of Point must still call **another constructor of the same Point via `this(...)`**, and cannot use an explicit `super()` instead of the component field initialization path.

Fix:

```java
record Point(int x, int y) {
    Point() {
        this(0, 0);
    }
}
```

**Do not confuse `this(...)` with `this.x`**: one is a constructor invocation, and the other is a field access. The two syntaxes have completely different roles.

## 20. Invalid Circular Constructor Chain

Constructor A calls B, B calls A, with no path to the canonical constructor:

```java
record Example(int value, String note) {
    Example(int value) {
        this(String.valueOf(value));
    }

    Example(String note) {
        this(0);
    }
}
```

This is **compile-negative**: recursive constructor invocation. The compiler detects the cycle.

Fix:

```java
record Example(int value, String note) {
    Example(int value) {
        this(value, "generated");
    }

    Example(String note) {
        this(0, note);
    }
}
```

Now both constructors end at the canonical `Example(int, String)`.

### Be Careful with Multiple Overloads

When writing multiple constructors, you can draw a directed graph where nodes are constructor signatures and edges are `this(...)`. The graph must be acyclic and **every path from an additional constructor must reach the canonical constructor**.

## 21. Overload Resolution Rules Apply Normally

Suppose:

```java
record Label(String text, int priority) {
    Label(int priority) {
        this("default", priority);
    }

    Label(String text) {
        this(text, 0);
    }
}
```

`new Label(3)` selects `Label(int)`; `new Label("A")` selects `Label(String)`.

Java still considers:
- Exact match.
- Primitive widening.
- Boxing/unboxing.
- Varargs.
- Most-specific selection.
- Ambiguity between unrelated reference types when passing `null`.

**There is no special “prefer canonical” rule**: overload resolution chooses the constructor that matches the expressions. If `new Label("A", 1)`, the canonical constructor with two parameters is chosen. If `new Label("A")`, the one-parameter overload is chosen.

### Be Careful with `null`

If `Label(String)` and `Label(Integer)` exist, `new Label(null)` can be ambiguous. A cast or a clearly named factory method helps eliminate ambiguity.

## 23. Parameter Names and Types of a Normal Canonical Constructor

Given the record:

```java
record User(String name, int age) {
}
```

An **explicitly declared normal canonical constructor** must have parameters matching the **names and types** of the record components:

```java
record User(String name, int age) {
    User(String name, int age) {
        this.name = name;
        this.age = age;
    }
}
```

Attempting to rename a parameter:

```java
record User(String name, int age) {
    User(String name, int years) {
        this.name = name;
        this.age = years;
    }
}
```

This is **compile-negative**. The constructor `User(String, int)` has the canonical signature by parameter types, but the parameter `years` does not match the component `age`. Java does not treat it as an “additional overload” just because the parameter name is different.

### Cannot Create an Overload Differing Only by Parameter Name

For Java constructors/methods, parameter names **do not distinguish signatures**. The two constructors `User(String name,int age)` and `User(String n,int a)` are not two different overloads.

## 24. Normal Canonical and Compact Canonical Cannot Coexist

Intentionally invalid example:

```java
record Counter(int value) {
    Counter(int value) {
        this.value = value;
    }

    Counter {
        if (value < 0) {
            throw new IllegalArgumentException();
        }
    }
}
```

Both are canonical constructor declarations of the same record `Counter`: one normal, one compact. Java rejects duplicate canonical signatures.

Choose **one**:
- Normal if you need explicitly controlled assignments.
- Compact if you only need validation/normalization.

For most value records, the compact form is usually shorter and avoids repeating error-prone component field assignments.

## 25. Compact Constructor Does Not Call `this(...)`

Incorrect form:

```java
record Value(int x, int y) {
    Value {
        this(x, y);
    }
}
```

This is **compile-negative**: the compact constructor **is itself the canonical constructor**, so it must not contain an explicit constructor invocation `this(...)`. It does not need to “delegate to the canonical constructor” because it **already is the canonical constructor**.

Instead:

```java
record Value(int x, int y) {
    Value {
        if (x < 0 || y < 0) {
            throw new IllegalArgumentException("negative");
        }
    }
}
```

The component fields are assigned by the compiler after the compact body.

### A Compact Constructor Also Must Not `return;`

A compact canonical body cannot have a `return` statement, even a bare `return;` for early exit. If validation fails, throw an exception; if there is branching logic, use normal control flow without an explicit return.

## 26. Compact Constructor Must Not Directly Assign Fields

Wrong:

```java
record Email(String address) {
    Email {
        this.address = address.strip();
    }
}
```

Fix:

```java
record Email(String address) {
    Email {
        address = address.strip();
    }
}
```

`address` without `this.` is the **implicit formal parameter**. When the body finishes, the implicit assignment assigns the `this.address` field.

If you want clarity when reading data before normalizing:

```java
record Email(String address) {
    Email {
        String normalized = address.strip();
        address = normalized;
    }
}
```

The compiler still assigns the field at the end.

## 27. Access Modifiers on Canonical and Auxiliary Constructors

A record can be declared public or package-private at the top level, or use appropriate member visibility when nested.

The canonical constructor **must have accessibility at least as accessible as the record** according to Java 17:
- `public record R(...)` → an explicitly declared canonical constructor must be public.
- Package-private top-level record → the canonical constructor cannot be private.
- A private member record has rules matching the accessibility of the record.
- An implicitly declared canonical constructor has accessibility matching the record.

Valid example:

```java
public record PublicPoint(int x, int y) {
    public PublicPoint {
        if (x < 0 || y < 0) {
            throw new IllegalArgumentException();
        }
    }

    private PublicPoint(int same) {
        this(same, same);
    }
}
```

Here the auxiliary constructor taking one `int` can be **private** because it is not the canonical constructor. A public static factory **inside the record** can still call it.

**Note:** the example above is a snippet of the file `PublicPoint.java`, not a complete Main class.

### Invalid with a Public Record

```java
public record R(int x) {
    private R {
    }
}
```

This is compile-negative because a private canonical constructor has narrower accessibility than the public record.

## 29. Checked Exceptions: Canonical and Additional Constructors Have Different Rules

**Java 17:** an explicitly declared normal canonical constructor **must not have a `throws` clause**. A compact canonical constructor also does not use a `throws` clause like a normal constructor with a parameter list. Validation usually uses unchecked exceptions such as `IllegalArgumentException` or `NullPointerException`.

Intentionally invalid canonical example:

```java
record Document(String text) {
    Document(String text) throws java.io.IOException {
        this.text = text;
    }
}
```

**Compile-negative** because the normal canonical constructor has a checked `throws` clause. Even if the body does not throw an exception, `throws` on the canonical constructor is still prohibited.

**A non-canonical constructor** can declare a checked `throws` clause, for example when it reads a file/parses a source and then **delegates** via `this(...)`.

### Note on Argument Evaluation

A checked exception can be thrown **while evaluating an argument expression for `this(...)`**. The additional constructor needs to catch/declare appropriately; you cannot place a `try` statement before `this(...)` in Java 17.

## 34. Record with a Varargs Component

A record can declare varargs on the last component:

```java
record Tags(String... values) {
}
```

The canonical constructor has the corresponding variable arity form `String... values`. You can add a no-arg additional constructor:

```java
record Tags(String... values) {
    Tags() {
        this(new String[0]);
    }
}
```

**Be careful of overload ambiguity:** a `this()` statement inside `Tags()` would call the no-arg constructor itself, causing recursion. Use `this(new String[0])` to explicitly select the canonical constructor (varargs accepts an array).

### Snapshot Arrays

The final component fields only hold references. A String array is still mutable. If you want the record to have safe value-like behavior, you need to clone the array when receiving it and when returning from the accessor if the public API needs isolation.

## 36. Additional Constructors Do Not Change Generated Accessors/toString

For `record Item(String sku,int qty)`, constructor overloads are only **paths for creating Item**. Once an Item has been initialized:
- `sku()` returns the `sku` component.
- `qty()` returns the `qty` component.
- `toString()` reflects the record components.
- `equals/hashCode` are based on the record components (unless validly overridden).
- There is no default information about which overload was used to create the object.

Example of two paths creating the same state:

```java
Item a = new Item("A");      // this("A", 1)
Item b = new Item("A", 1);   // canonical
```

If the component values are equal and equality is not customized, `a.equals(b)` is true. There is no implicit “usedConstructor” component.

### How This Guides Design

A constructor overload should produce **the same record meaning** with normalized canonical arguments. Do not use overloads to secretly create different “modes” that are not represented in the record components, because those modes are not reflected in value equality or toString.

## 38. Avoid Repeating Validation in Every Auxiliary Constructor

Anti-pattern:

```java
record Person(String name, int age) {
    Person {
        if (age < 0) {
            throw new IllegalArgumentException("negative age");
        }
    }

    Person(String name) {
        this(name, 0);
        // No need to re-check age >= 0 here.
    }
}
```

Validation regarding **the validity of the record state** should reside in the canonical constructor (compact/normal) so that all initialization paths pass through it.

An auxiliary constructor can check **its own input format** before the canonical call using a static helper:
- Parse a string.
- Convert units.
- Decode an external code.
- Set a default.
- Validate input that only exists in that overload.

**Distinction:** validating the record's state invariant ≠ validating the input format of a constructor adapter.

## 40. Defaults Differ from Language-Level “Default Parameters”

Java **does not** support declaring constructor parameters with default expressions like:

```java
// Not Java syntax:
record Person(String name, int age = 0) {}
```

Alternatives:
- Additional constructors with `this(...)`.
- Static factory methods with meaningful names.
- A builder when there are many independent options.
- Method overloads if appropriate for the API.

An auxiliary constructor `Person(String name)` is equivalent to a **convenience overload**, not a language-level default argument on the canonical constructor.

### How Many Overloads Are Too Many?

If a record has 10 components and you create 20 overloads depending on default combinations, it is very hard for the caller to know which exact combination is selected. Consider a parameter object, static named factories, or a builder. Records are usually most effective when state components are few, clear, and share a common invariant.

## 41. Static Factory Instead of Constructor Overload

A factory can be useful when:
- You want to name the intent: `Money.zero(currency)`, `Range.single(value)`.
- There are multiple overloads with the same types that can easily cause confusion.
- Input parsing can fail and needs to return `Optional`/`Result`.
- You want to cache certain immutable values (whereas record constructors still create an object on every `new`).
- You need version/migration logic before deciding the state.

```java
record Money(long cents, String currency) {
    static Money zero(String currency) {
        return new Money(0L, currency);
    }
}
```

The factory `zero` is not a constructor and does not have to follow the `this(...)` rule, yet it still uses canonical construction in the end to maintain the invariant.

**Do not mistakenly think that because a factory is not forced to use `this(...)`, it can assign component fields arbitrarily**: record component fields remain final and belong to the instance created by the canonical constructor.

## 43. Record Constructors + Escaping `this` and Inheritance

A record:
- Is `final`, and cannot extend an arbitrary class.
- Implicitly extends `java.lang.Record`.
- Has fixed record components.
- Has no mutable inherited instance fields from a user-defined superclass.
- Cannot use a subclass constructor to extend the record's schema.

Therefore, an additional constructor should **convert input data into a valid component tuple** instead of simulating inheritance polymorphic construction.

Be careful when passing `this` out of a canonical/auxiliary constructor elsewhere before initialization completes. Record rules do not make publishing a partially constructed object safe. In Java 17, a non-canonical constructor cannot access instance members before explicit `this(...)`, and a canonical constructor should avoid calling overridable behavior/passing the object reference out to a global registry even though the record is final.

### Mutable Data Requires Extra Attention

A record holding a `List` or array can still involve shared mutable referents. Constructor overloads should pass through the defensive-copy policy in the canonical constructor. Do not let a one-parameter overload copy the list while the two-parameter canonical constructor keeps a live alias if the contract intends an immutable snapshot.

## 44. Constructor Overloading and Java Serialization of Records

Java object serialization has a dedicated mechanism for record classes. Record deserialization can invoke the **canonical constructor** when restoring state, according to the corresponding record serialization rules.

This makes validation in the canonical constructor more important than validation in only one overload:
- If the invariant resides only in an additional constructor, direct canonical construction paths can bypass it.
- Java record serialization does not mean every non-canonical overload will be selected when reading data.
- External serializers/JSON mappers have different constructor-binding rules; do not assume they always choose the canonical constructor or always choose the no-arg constructor.

**You should centralize state invariants in the canonical constructor**, while serializer integration needs tests suited to the actual library/version.

### Distinguishing Construction from Wire Format

Adding a convenience overload usually does not change the record component schema; adding/removing/renaming/changing component types is a major change for consumers relying on schema, reflection, and serialization.

## 45. Reflection: Canonical and Additional Constructors Are Both Constructors

Java reflection can list `getDeclaredConstructors()` on a record class. Additionally, `Class.isRecord()` indicates whether a class is a record and `getRecordComponents()` returns metadata about the components.

However, reflection does not provide “which auxiliary constructor was called” for a record instance after creation.

When you need to know the canonical signature:
1. Read `getRecordComponents()` in order.
2. Get the types of each component.
3. The canonical constructor has parameter types corresponding to that order.
4. The other constructor signatures are overloads.

If there is generic erasure or varargs, use the appropriate Java reflection types and understand compiler-generated signatures. Do not rely on the order of `getDeclaredConstructors()` to pick “the first constructor” as the canonical constructor.

### Role of Access Modifiers

Private additional constructors can still appear in `getDeclaredConstructors()`. “Having metadata via reflection” does not mean code outside the package/module is allowed to invoke them without access checks.

## 47. Compile-Negative Summary: 8 Common Errors

Each snippet below **intentionally does not compile**; they are not runnable programs.

**Error A — Not calling `this(...)`:**

```java
record R(int x) {
    R() { }
}
```

**Error B — Another statement before `this(...)` (Java 17):**

```java
record R(int x) {
    R() {
        System.out.println("start");
        this(0);
    }
}
```

**Error C — Using `super()` instead of `this(...)`:**

```java
record R(int x) {
    R() {
        super();
    }
}
```

**Error D — Assigning a field in an auxiliary constructor without delegating:**

```java
record R(int x) {
    R() {
        this.x = 0;
    }
}
```

**Error E — Compact canonical calling `this(...)` itself:**

```java
record R(int x) {
    R {
        this(x);
    }
}
```

**Error F — Compact canonical assigning a component field:**

```java
record R(int x) {
    R {
        this.x = x;
    }
}
```

**Error G — Canonical constructor with a throws clause:**

```java
record R(int x) {
    R(int x) throws Exception {
        this.x = x;
    }
}
```

**Error H — Recursive constructor chain:**

```java
record R(int x, String s) {
    R(int x) { this("x"); }
    R(String s) { this(0); }
}
```

Fixes:
- A/B/C/D → make `this(...)` the first statement in the additional constructor.
- E/F → remove the explicit invocation/field assignment, and handle the implicit parameters of the compact constructor.
- G → remove `throws` from the canonical constructor, or move the input adapter with checked errors to an additional constructor/factory.
- H → ensure every chain ultimately reaches the canonical constructor with all components.

## 49. If an Argument Helper Throws an Exception

Example:

```java
record Config(String name, int port) {
    Config() {
        this(readName(), 8080);
    }

    private static String readName() {
        throw new IllegalArgumentException("bad name");
    }
}
```

`readName()` can throw before the canonical constructor `Config(String,int)` begins. The auxiliary constructor also cannot run any statement after the `this(...)` call.

If a checked exception is desired, the additional constructor can declare `throws` appropriately as already explained.

**Good design:** avoid side effects that cannot be rolled back in argument helpers; prefer pure normalization/parsing whenever possible.

## 50. Distinguishing Record Constructors from Overloaded Static Factories

Ways to create `Profile`:

```java
Profile a = new Profile("An", 20);      // canonical
Profile b = new Profile("An");          // auxiliary
Profile c = Profile.guest();            // factory
```

- Canonical is always tied to the exact component tuple.
- Auxiliary uses `this(...)`, and the compiler checks delegation.
- Factory is a static method that can perform branching/IO/caching before calling a constructor.
- Builder is an object supporting a set of options, which when built can call the canonical constructor.

If a factory returns a cached record instance, not every factory call creates a new object. That differs from `new` construction semantics.

Do not try to simulate factory names using multiple overloaded constructors with the same parameter count/types but different meanings.

## 51. Design Smell: Overly Ambiguous Constructor Overload

Suppose:

```java
record Appointment(String location, String timezone) {
    Appointment(String value) {
        this(value, "UTC");
    }
}
```

Does a string `"Asia/Ho_Chi_Minh"` passed to the one-String constructor mean a location or a timezone? A single overload has difficulty expressing the intent.

Clearly named factories:

```java
record Appointment(String location, String timezone) {
    static Appointment atLocation(String location) {
        return new Appointment(location, "UTC");
    }

    static Appointment inTimezone(String timezone) {
        return new Appointment("unspecified", timezone);
    }
}
```

This is a design snippet; using default location/timezone values must have clear domain meaning and should not be chosen arbitrarily in real production code.

### How to Choose

- One common default without ambiguity → constructor overload.
- Two conversion paths with the same parameter type → named static factories.
- Many interacting options → a builder or separate config record.
- External system input with parsing/IO/checked errors → a factory or additional constructor with a clear contract.

## 52. Testing: Invariants Must Apply to All Initialization Paths

Some important tests:
- Canonical constructor directly with valid data.
- Each additional overload with valid data.
- Each overload with data rejected by canonical validation.
- Is input normalization applied identically for every overload?
- Does the `this(...)` chain produce the correct defaults?
- Boundary null/empty/range limits.
- Checked exceptions from converter helpers.
- Array/list aliasing if the record accepts mutable references.
- Value equality when creating two records with the same components via two different paths.
- Backward compatibility when adding a component or changing the schema.

**Do not test only the default output of a single constructor**, because a bug can lie in an overload passing the wrong parameter to the canonical constructor.

## 53. Runnable: Testing All Overloads with Library-Free Assertions

Save **`RecordConstructorContractTestDemo.java`**:

```java
record Account(String owner, int limit, boolean enabled) {
    Account {
        if (owner == null || owner.isBlank() || limit < 0) {
            throw new IllegalArgumentException("invalid");
        }
    }

    Account(String owner, int limit) {
        this(owner, limit, true);
    }

    Account(String owner) {
        this(owner, 0);
    }
}

public class RecordConstructorContractTestDemo {
    public static void main(String[] args) {
        Account one = new Account("An");
        Account two = new Account("An", 0);
        Account three = new Account("An", 0, true);

        require(one.equals(two));
        require(two.equals(three));
        require(one.enabled());

        try {
            new Account("An", -1);
            throw new AssertionError("expected exception");
        } catch (IllegalArgumentException expected) {
            require(expected.getMessage().equals("invalid"));
        }

        System.out.println("CONTRACT_PASS");
    }

    private static void require(boolean condition) {
        if (!condition) {
            throw new AssertionError("contract failed");
        }
    }
}
```

```bash
javac --release 17 -encoding UTF-8 RecordConstructorContractTestDemo.java
java RecordConstructorContractTestDemo
```

Stdout:

```text

```

The test verifies that the overloads produce the same record value when given the same effective components, while canonical validation still applies when calling the two-parameter overload.

## 54. Exercise 1 — Identify the Canonical Constructor

```java
record Person(String name, int age) {
    Person(String name) {
        this(name, 0);
    }
}
```

**Question:** which constructor is canonical?

**Answer:** `Person(String,int)` is the implicit canonical constructor from the record header. `Person(String)` is an additional constructor.

## 55. Exercise 2 — Is It Necessary to Write the Canonical Constructor Explicitly?

If a record only declares `Person(String name) { this(name,0); }` without writing `Person(String,int)`, does the program compile?

**Answer:** Yes. Java implicitly generates the canonical constructor because there is no explicit normal/compact canonical constructor yet.

## 56. Exercise 3 — Placement of `this(...)`

```java
record Port(int value, String protocol) {
    Port(int value) {
        System.out.println("creating");
        this(value, "tcp");
    }
}
```

**Answer:** Does not compile on Java 17. `this(...)` must be the first statement of a non-canonical constructor.

## 57. Exercise 4 — Is a Statement After `this(...)` Valid?

```java
record Pair(int x, int y) {
    Pair(int x) {
        this(x, 0);
        System.out.println("constructed");
    }
}
```

**Answer:** Valid. The auxiliary constructor continues executing **after** the canonical call `this(x,0)` completes.

## 58. Exercise 5 — Chain of Multiple Overloads

`Point()` calls `Point(int)`, and `Point(int)` calls `Point(int,int)`. Is this valid?

**Answer:** Yes, if the signatures are compatible and there is no recursion. Ultimately `Point(int,int)` is the canonical constructor.

## 59. Exercise 6 — Auxiliary Constructor Directly Assigns Fields

```java
record Pair(int a, int b) {
    Pair(int a) {
        this.a = a;
        this.b = 0;
    }
}
```

**Answer:** Invalid. An additional constructor must start with `this(a,0)`, not initialize the fields itself.

## 60. Exercise 7 — Does a Compact Canonical Constructor Have Parameters?

```java
record User(String name) {
    User {
        name = name.trim();
    }
}
```

**Answer:** A compact canonical constructor has the implicit parameter `name` from the record header; the body does not rewrite the parameter list.

## 61. Exercise 8 — Compact Assignment

Is `this.name = name.trim();` valid inside a compact constructor?

**Answer:** No. Assign the implicit parameter `name = name.trim();`; the compiler will assign the component field when the compact body finishes.

## 62. Exercise 9 — Compact `this(...)`

```java
record User(String name) {
    User {
        this(name);
    }
}
```

**Answer:** Invalid. The compact constructor already is the canonical constructor and does not make an explicit constructor invocation.

## 63. Exercise 10 — Must a Normal Canonical Constructor Assign Fields Itself?

```java
record User(String name) {
    User(String name) {
        // Does not assign this.name.
    }
}
```

**Answer:** Invalid because the final component field has not been definitely assigned in the normal canonical constructor. The compact form has implicit assignment; in the normal canonical form, you must assign it completely.

## 64. Exercise 11 — Renaming a Parameter of a Normal Canonical Constructor

Is `record User(String name,int age) { User(String n,int age){...} }` considered another auxiliary constructor?

**Answer:** No. The signature by types matches the canonical constructor, so the parameter names must match the record components (`name`, `age`). This is an error in declaring the normal canonical constructor.

## 65. Exercise 12 — Can Canonical Have `throws`?

A normal canonical constructor declares `throws IOException`. Is this valid?

**Answer:** No on Java 17. A canonical constructor cannot declare a throws clause. Place IO parsing in an additional constructor/factory.

## 66. Exercise 13 — Additional `throws`?

`Record(Path path) throws IOException { this(Files.readString(path)); }` with a record header having one String component. Can this be valid?

**Answer:** Yes, when imports/overloads are correct. An additional constructor can declare checked throws and pass data to the canonical constructor.

## 67. Exercise 14 — Private Additional Constructor

Can a public record have a private convenience overload?

**Answer:** Yes, because the accessibility rule “not narrower than the record” applies to the canonical constructor, and does not require every non-canonical constructor to be public. A factory inside the record can call the private overload.

## 68. Exercise 15 — Private Canonical Constructor of a Public Record

Is `public record User(String name) { private User { } }` valid?

**Answer:** No. A public record requires an explicit canonical constructor to be public.

## 69. Exercise 16 — Recursive Invocation

Constructor `A()` calls `A(int)` and `A(int)` calls `A()`. Is this valid?

**Answer:** No. A recursive constructor invocation has no path to the canonical constructor.

## 70. Exercise 17 — Generic Record

`record Box<T>(T value,String label)` with additional `Box(T value){this(value,"default");}`. Can a `Box<String>` use `new Box<>("A")`?

**Answer:** Yes in Java 17 with appropriate type inference.

## 71. Exercise 18 — Zero-Component Record

What is the canonical signature of `record Marker()`?

**Answer:** `Marker()`. An additional overload must have different parameter types/list, for example `Marker(String) { this(); }`.

## 72. Exercise 19 — Varargs and Constructor Recursion

Is `record Tags(String... values) { Tags() { this(); } }` valid?

**Answer:** No. `this()` in `Tags()` calls the no-arg constructor itself, causing recursion. Use `this(new String[0])` to select the varargs canonical constructor with an array.

## 73. Exercise 20 — Two Ways to Create the Same Value

What are `equals` and `==` for `new Item("A")` and `new Item("A",1)` when the one-parameter overload calls `this("A",1)`?

**Answer:** By default, record equality is based on components so `equals` is true, and `==` is false for two different `new` calls.

## 74. Exercise 21 — Constructor Overloads for Optional Config

A record has 12 optional parameters, and 20 constructors are created. Is that good?

**Answer:** Usually it is a sign of an overly complex API. Consider named factories, a builder, or a reasonable config structure to reduce overload ambiguity and keep invariants clear.

## 75. Exercise 22 — Mutable Array Parameter

An auxiliary constructor accepts `String[]` and passes it to the canonical constructor, but the canonical constructor does not copy it. Is the record immutable yet?

**Answer:** Not necessarily. The final component field holds the array reference, and the array is still mutable. The canonical constructor needs a defensive copy if the contract is a value snapshot; the accessor needs to be reviewed for exposure.

## 76. Exercise 23 — Where Should Validation Go?

A record has three auxiliary constructors and a canonical constructor. Where should an `age >= 0` invariant be written?

**Answer:** In the canonical constructor (compact or normal). Every additional constructor delegates through it, avoiding validating only a single path.

## 77. Exercise 24 — Log Order

`R() { this(1); print("A"); }`, `R(int) { this(1,2); print("B"); }`, and the canonical constructor prints `C`. What is the output for `new R()`?

**Answer:** `C`, then `B`, then `A` (on separate lines if using println). The chain enters the canonical constructor first and then unwinds back up.

## 78. Exercise 25 — Adding a New Record Component

`record User(String name)` has auxiliary `User(){this("Guest");}`. Add component `int age` to the header. What needs to be checked?

**Answer:** The canonical signature changes to `User(String,int)`. `this("Guest")` can become a recursive call to the one-String constructor if that constructor exists on its own, or fail to resolve/compile; update the delegation and default for age, and then test external schema/API compatibility.

## 79. Exercise 26 — Reflection

Does `getDeclaredConstructors()` return both canonical and additional constructors?

**Answer:** Yes, for that declared record, including non-public constructors; the array order must not be used to infer the canonical constructor. Identify the canonical constructor via the component-derived signature.

## 80. Exercise 27 — Default Values

Is the Java record header `record Item(int qty=1)` valid?

**Answer:** No. Java does not declare default parameters directly in the record header. Use an additional constructor `Item() { this(1); }` or a named factory.

## 81. Exercise 28 — Normal or Compact Canonical Constructor?

You want to strip a String and validate a range without needing manual field assignment. Which should be preferred?

**Answer:** The compact canonical form is usually clearer: modify the implicit parameters, throw an exception when invalid, and let the compiler assign the fields after the body.

## 82. Exercise 29 — Argument Side Effects

`this(left(),right());` inside an auxiliary constructor: which method runs first?

**Answer:** Java evaluates argument expressions from left to right: left() before right(), and only then enters the invoked constructor if there is no exception.

In Java 17, mark True/False:

2. A non-canonical constructor can omit `this(...)` if it assigns all fields itself.

## 84. Common Errors and Fixes Table

| Error or Misconception | Cause | Fix |
| --- | --- | --- |
| `record R(int x) { R() {} }` | Missing `this(...)` in the auxiliary constructor | `R(){this(0);}` |
| Printing a log before `this(...)` | `this(...)` is not first according to Java 17 | Move the log after the invocation, or use a pure helper in arguments |
| `super()` in an auxiliary record constructor | Must delegate within the same record | Use `this(...)` |
| Assigning `this.x=...` in an auxiliary constructor | Bypasses the canonical path | Pass all component arguments to the canonical constructor |
| Compact constructor assigns `this.x` | Compact fields are implicitly assigned from parameters | Assign parameter `x` |
| Compact constructor calls `this(...)` | Compact already is the canonical constructor | Remove the explicit invocation |
| Both normal and compact canonical constructors | Duplicate signature | Keep only one canonical constructor |
| Explicit canonical missing field assignment | Final fields are not initialized | Assign completely in normal canonical or use compact |
| Canonical parameter name differs from component | Violates JLS normal canonical rules | Match names/types with the header |
| Public record with private canonical constructor | Access narrower than the record | Make canonical public |
| Canonical has `throws` | JLS forbids a throws clause on canonical | Unchecked validation; checked IO in auxiliary/factory |
| Delegation A→B→A | Constructor recursion | Every chain must reach canonical |
| `new Tags()` where `Tags()` calls `this()` | The no-arg overload calls itself | `this(new String[0])` |
| Wrong overload selected due to `null` | Multiple reference-type constructors exist | Explicit cast or named factory |
| Copying validation across every constructor | Duplicates logic and risks invariant drift | Validation in canonical |
| Mutating component array from caller | No defensive copy | Copy in canonical and accessor |
| Constructors with too many combinations | Confusing API | Builder/named factories |
| Testing only one constructor | Misses other paths | Contract tests for every overload |
| Thinking `this(...)` creates a second object | Misunderstanding chaining | One `new`, one object, multiple ctor bodies |
| Using default parameters in record header | Unsupported by Java syntax | Auxiliary constructor/factory |

## 85. Checklist When Designing Additional Constructors for a Record

- [ ] The record header fully describes the state/components.
- [ ] The canonical signature is identified according to the order of component types.
- [ ] Chose implicit, normal, or compact canonical constructor (only one).
- [ ] If normal canonical, parameter names/types match the header.
- [ ] If normal canonical, every component field is assigned exactly once.
- [ ] If compact canonical, use implicit parameters to normalize.
- [ ] Compact body does not `return`/`this(...)`/assign component fields.
- [ ] Explicit canonical does not declare `throws`.
- [ ] Canonical access is not narrower than the record.
- [ ] Every additional constructor has a signature different from the canonical constructor.
- [ ] Every additional constructor starts with `this(...)` in Java 17.
- [ ] No statement/log/assignment precedes `this(...)`.
- [ ] Do not use `super(...)` instead of `this(...)`.
- [ ] Every constructor chain has no cycles and ultimately reaches the canonical constructor.
- [ ] Default values have clear domain meaning.
- [ ] Helpers computing arguments do not depend on uninitialized instance fields.
- [ ] State invariant validation is centralized in the canonical constructor.
- [ ] Input-format-specific validation resides in an appropriate helper/adapter.
- [ ] Overload resolution and `null` are unambiguous.
- [ ] If there are checked exceptions from input, the auxiliary constructor/factory has a clear contract.
- [ ] If the record is generic, type inference and erasure are checked.
- [ ] If the record has varargs, `this(new T[0])` avoids self-recursion.
- [ ] If components are mutable, the defensive copy policy is consistent across all paths.
- [ ] Named factories replace overloads when that makes the API clearer.
- [ ] No hidden “constructor-private mode” is needed outside record components.
- [ ] Reflection/serialization/framework expectations are tested when relevant.
- [ ] Compiled with `--release 17`, without accidentally relying on newer language features.
- [ ] Compile-negative examples are separated from runnable source files.
- [ ] Tests cover the canonical path and each auxiliary path.
- [ ] Tests verify normalization, validation, defaults, and equality.
- [ ] When adding a record component, all constructor delegates have been updated.
- [ ] Public API/serialization compatibility has been evaluated when the record schema changes.

## 86. Core Summary

**Every record has a canonical constructor** derived from its record components. The canonical constructor can be compiler-generated, written normally with full parameters, or written **compactly** for concise validation/normalization.

**Every additional constructor of a record in Java 17 must begin with `this(...)`**. That constructor can call another overload, but the chain must terminate at the canonical constructor. You must not directly assign component fields yourself, place a log before `this(...)`, replace it with `super()`, or create a constructor cycle.

Place **invariant validation in the canonical constructor**, use additional constructors for input adapters and defaults, and consider named factories when overloads could cause confusion. For mutable components, the canonical constructor is the appropriate place to unify the defensive-copy policy.

**Quick mnemonic:** A record allows many **entry points**, but only one **canonical gate to initialize state**. Auxiliary constructors only bring data to that gate; they do not construct state along a separate path.
