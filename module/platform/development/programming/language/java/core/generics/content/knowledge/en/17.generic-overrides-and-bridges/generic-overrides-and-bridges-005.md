# Identifying `bridge` and `synthetic` Methods via Reflection in Java Generics

## 1. Objective

When reading a class's methods using Java Reflection, you sometimes see **more methods than the ones written in source**. For instance, a class declares only `String map(String)`, yet Reflection also lists `Object map(Object)`. This can happen because the compiler generates a **bridge method** to preserve overriding behavior after generics undergo type erasure.

Java provides two direct checks on `java.lang.reflect.Method`:

- `method.isBridge()` — whether the method has the JVM bridge flag.
- `method.isSynthetic()` — whether the method has the JVM synthetic flag.

This lesson focuses on reading those two flags accurately, connecting them with **method signatures, override rules, and `javap` output**, distinguishing a bridge from other compiler-generated helper methods, and using Reflection results in API-scanning tools.

After this lesson, you will be able to:

1. Explain why a generic subclass can exhibit extra methods in Reflection.
2. Write a program listing declared methods along with parameter types, return type, `isBridge()`, and `isSynthetic()`.
3. Spot the difference between `bridge=true, synthetic=true`, `bridge=false, synthetic=true`, and an ordinary method.
4. Choose between `getDeclaredMethods()` and `getMethods()` when inspecting a class.
5. Avoid double-counting public API methods when building frameworks, annotation scanners, API documentation, or test tools.

## 2. Why Can a Generic Override Need a Bridge?

Consider a generic interface:

```java
interface Mapper<T> {
    T map(T value);
}
```

An implementing class binds `T` to `String`:

```java
final class StringMapper implements Mapper<String> {
    @Override
    public String map(String value) {
        return value.strip();
    }
}
```

In **source**, `String map(String)` satisfies the contract of `Mapper<String>`. However, the JVM descriptor of `Mapper.map(T)`, since `T` has no explicit bound, has the form:

```text
(Ljava/lang/Object;)Ljava/lang/Object;
```

The method declared by the programmer in `StringMapper` has the descriptor:

```text
(Ljava/lang/String;)Ljava/lang/String;
```

If only `map(String)` existed, a compiled call targeting the interface method with descriptor `map(Object):Object` would not directly match the `map(String):String` descriptor in the subclass.

To ensure polymorphism, the compiler can generate a **bridge** method in `StringMapper`. Behaviorally, the bridge resembles:

```java
// ILLUSTRATES COMPILER-GENERATED BYTECODE, DO NOT ADD TO SOURCE:
public Object map(Object input) {
    return map((String) input);
}
```

The bridge accepts the erased type, forwards to the real implementation, and may insert necessary casts.

Diagram:

```text
Mapper<String> variable
        |
        | map(...) call, original descriptor map(Object):Object
        v
StringMapper.map(Object):Object       [bridge + synthetic]
        |
        | cast Object to String, call implementation
        v
StringMapper.map(String):String       [programmer-written method]
```

Crucially, the class file can contain **two** methods named `map` because their parameter/return types in bytecode descriptors differ. Programmers should not try to manually declare an overload with such a colliding erasure.

### 2.1. How does a bridge protect the generic contract?

With a properly typed reference:

```java
Mapper<String> mapper = new StringMapper();
String text = mapper.map("  Java  ");
```

Java checks that the argument is a `String` at compile time; the bridge lets the call pass through the interface with the erased descriptor and dispatch to the subclass implementation.

If you force use of a raw type:

```java
// Illustrates risky behavior; may emit raw/unchecked warnings:
Mapper raw = new StringMapper();
raw.map(123);
```

The bridge can throw `ClassCastException` when casting `Integer` to `String`. The root issue is that the call violated the `Mapper<String>` contract via a raw type. A bridge is not an arbitrary data-conversion mechanism.

## 3. `Method.isBridge()` and `Method.isSynthetic()` Differ

A `Method` object represents a method visible to Reflection. The inspection methods:

```java
boolean bridge = method.isBridge();
boolean synthetic = method.isSynthetic();
```

have independent meanings:

| State | Practical interpretation |
| --- | --- |
| `bridge=false`, `synthetic=false` | Ordinary method without either flag. |
| `bridge=true`, `synthetic=true` | Typical bridge generated by `javac` when needed to preserve overrides/polymorphism after erasure or with covariant returns. |
| `bridge=false`, `synthetic=true` | Method generated by the compiler for another purpose, such as a lambda implementation helper under a specific compilation strategy. |
| `bridge=true`, `synthetic=false` | The two JVM flags are separate concepts; do not write tool logic assuming `isBridge()` and `isSynthetic()` always match across all class files and bytecode generators. |

`isBridge()` asks whether the method has the `ACC_BRIDGE` flag in the class file. `isSynthetic()` asks whether the method has the `ACC_SYNTHETIC` flag in the class file. Normally, a Java compiler-generated bridge is synthetic, but **synthetic does not mean bridge**.

Here `synthetic` is a JVM term for a member that does not appear as an ordinary declaration in source. It is **not** a generic property, has no direct connection to the `synchronized` keyword, and does not mean the method cannot be discovered or invoked via Reflection.

### 3.1. Related Reflection APIs

| API | Purpose |
| --- | --- |
| `Method.isBridge()` | Checks the bridge flag. |
| `Method.isSynthetic()` | Checks the method's synthetic flag. |
| `Method.getName()` | Method name. |
| `Method.getParameterTypes()` | Runtime raw/erased parameter types. |
| `Method.getReturnType()` | Runtime return type of the method. |
| `Method.getGenericParameterTypes()` | Reads generic parameter info from declaration/metadata if present. |
| `Method.getGenericReturnType()` | Reads generic return type declaration if present. |
| `Method.getDeclaringClass()` | Class/interface that actually declares this method in the class file. |
| `Class.getDeclaredMethods()` | Reads methods declared directly in that class/interface, including non-public and compiler-generated methods; excludes inherited-only methods. |
| `Class.getMethods()` | Reads visible `public` methods of the class/interface, including inherited public methods. |
| `java.lang.reflect.Modifier` | Checks ordinary modifiers such as `public`, `private`, `static`. |

**Do not look for `isBridge()` on `Class<?>` or `Field`.** It is a `Method` API. `isSynthetic()` also appears on some other Reflection objects, though its meaning depends on the inspected member.

## 4. Complete Java 17 Example: Bridge, Covariant Return, and Synthetic Lambda

Create the file **`BridgeReflectionDemo.java`**:

```java
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.Comparator;
import java.util.stream.Collectors;

public class BridgeReflectionDemo {
    interface Mapper<T> {
        T map(T input);
    }

    static final class StringMapper implements Mapper<String> {
        @Override
        public String map(String input) {
            return input.strip();
        }
    }

    static class Base {
        Number score() {
            return 1;
        }
    }

    static final class Derived extends Base {
        @Override
        Integer score() {
            return 2;
        }
    }

    static final class LambdaHolder {
        Runnable callback() {
            return () -> { };
        }
    }

    static void inspect(Class<?> type) {
        System.out.println("[" + type.getSimpleName() + "]");
        Arrays.stream(type.getDeclaredMethods())
                .sorted(Comparator.comparing(Method::getName)
                        .thenComparing(m -> Arrays.toString(m.getParameterTypes())))
                .forEach(m -> System.out.println(format(m)));
    }

    static String format(Method m) {
        String params = Arrays.stream(m.getParameterTypes())
                .map(Class::getSimpleName)
                .collect(Collectors.joining(","));
        return m.getName() + "(" + params + ")->"
                + m.getReturnType().getSimpleName()
                + " | bridge=" + m.isBridge()
                + " synthetic=" + m.isSynthetic();
    }

    public static void main(String[] args) throws Exception {
        Mapper<String> mapper = new StringMapper();
        System.out.println("result=" + mapper.map("  Java  "));
        System.out.println("score=" + new Derived().score());
        inspect(StringMapper.class);
        inspect(Derived.class);
        inspect(LambdaHolder.class);
        Method bridge = StringMapper.class.getDeclaredMethod(
                "map", Object.class);
        System.out.println("erasedParam="
                + bridge.getParameterTypes()[0].getSimpleName());
    }
}
```

Compile with Java 17 or a newer JDK supporting `--release 17`:

```bash
javac --release 17 BridgeReflectionDemo.java
java BridgeReflectionDemo
```

Verified output with `javac --release 17` and `java`:

```text
result=Java
score=2
[StringMapper]
map(Object)->Object | bridge=true synthetic=true
map(String)->String | bridge=false synthetic=false
[Derived]
score()->Integer | bridge=false synthetic=false
score()->Number | bridge=true synthetic=true
[LambdaHolder]
callback()->Runnable | bridge=false synthetic=false
lambda$callback$0()->void | bridge=false synthetic=true
erasedParam=Object
```

The lines above reflect output from the tested **`javac`** compilation. Exact names like `lambda$callback$0`, presence/absence of lambda helpers, and the order of compiler-generated methods can differ across compilers, JDKs, or desugaring strategies; do not write business logic directly depending on such lambda helper names. In the example, `sorted(...)` is used to make listing deterministic for the methods generated by this compiler.

### 4.1. Reading the `StringMapper` group

```text
map(Object)->Object | bridge=true synthetic=true
map(String)->String | bridge=false synthetic=false
```

`map(String)` is the author-written method. `map(Object)` is generated to match the erasure of `Mapper<T>.map(T)`; hence it carries both the bridge flag and the synthetic flag.

Both methods share the same name but have **different runtime parameter types**, so:

```java
StringMapper.class.getDeclaredMethod("map", String.class);
StringMapper.class.getDeclaredMethod("map", Object.class);
```

can both find a method in the class file after the Java compiler generates the bridge. The second lookup represents the bridge; that Reflection capability does not mean `StringMapper`'s source declares a new `map(Object)` overload for ordinary Java callers.

### 4.2. Reading the `Derived` group: bridges are not tied solely to generics

```text
score()->Integer | bridge=false synthetic=false
score()->Number | bridge=true synthetic=true
```

Here `Base.score()` returns `Number`, while `Derived.score()` validly overrides it with the narrower return type `Integer` (*covariant return*). Because JVM descriptors include the return type, `javac` can generate a `Number score()` bridge to keep dispatch compatible with callers compiled against the `Number` return type.

This shows: **seeing `isBridge() == true` is not enough to conclude the parent method has a generic type parameter.** Bridges can also arise from covariant returns on non-generic methods.

If you only want to know whether a subclass has a compiler-generated method preserving an override, check both the inheritance relationship and raw signatures. If you want to know which cases involve generic erasure, read the generic declaration of the supertype.

### 4.3. Reading the `LambdaHolder` group: synthetic is not necessarily a bridge

```text
callback()->Runnable | bridge=false synthetic=false
lambda$callback$0()->void | bridge=false synthetic=true
```

In the bytecode `javac` uses for the lambda in the example, the compiler creates a helper `lambda$callback$0()` and marks it synthetic. This helper **does not perform override-signature adaptation**, so `isBridge() == false`.

A source-level lambda is implemented via mechanisms involving `invokedynamic` and the Java runtime. Distinguish the helper method appearing in the enclosing class from the runtime `Runnable` instance created during execution. Reflection on `LambdaHolder.class` inspects methods declared in that class, not every method that might exist on the lambda's runtime implementation object.

## 5. Confirming with `javap`: Inspecting Bytecode Descriptors and Flags Directly

After compiling the example, use `javap` to inspect the nested class files:

```bash
javap -p -s 'BridgeReflectionDemo$StringMapper'
javap -p -s 'BridgeReflectionDemo$Derived'
javap -p -s 'BridgeReflectionDemo$LambdaHolder'
```

Key descriptor excerpts:

```text
public java.lang.String map(java.lang.String);
  descriptor: (Ljava/lang/String;)Ljava/lang/String;

public java.lang.Object map(java.lang.Object);
  descriptor: (Ljava/lang/Object;)Ljava/lang/Object;
```

```text
java.lang.Integer score();
  descriptor: ()Ljava/lang/Integer;

java.lang.Number score();
  descriptor: ()Ljava/lang/Number;
```

```text
java.lang.Runnable callback();
  descriptor: ()Ljava/lang/Runnable;

private static void lambda$callback$0();
  descriptor: ()V
```

Switch to verbose mode:

```bash
javap -p -v 'BridgeReflectionDemo$StringMapper'
javap -p -v 'BridgeReflectionDemo$Derived'
javap -p -v 'BridgeReflectionDemo$LambdaHolder'
```

Look for the `flags` lines of the methods. Example display format:

```text
flags: (...) ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
```

For the lambda helper:

```text
flags: (...) ACC_PRIVATE, ACC_STATIC, ACC_SYNTHETIC
```

These flags directly explain the values reflected by `isBridge()` and `isSynthetic()`. Use `javap -c -p` when you need to inspect the bridge body: it typically reads the `Object` parameter, casts it, and invokes the `String` implementation. Exact opcodes can vary across compilers; follow the **forwarding contract** rather than memorizing individual opcodes.

In PowerShell and Unix shells, single quotes around nested class names prevent `$StringMapper` from being treated as a shell variable name.

## 6. `getDeclaredMethods()` or `getMethods()`?

This is an important choice when writing Reflection-based tools.

### 6.1. `getDeclaredMethods()`: directly declared methods

```java
Method[] methods = StringMapper.class.getDeclaredMethods();
```

The result includes methods declared directly in `StringMapper`'s class file: `map(String)` and the `map(Object)` bridge. It may also include `private`, `protected`, `package-private`, or synthetic methods if declared there.

It **excludes** methods merely inherited from a superclass or interface that the class has not directly declared. It does not return constructors; use `getDeclaredConstructors()` to read constructors.

Use it when you want to:

- Check exactly which methods the compiler placed in **this class**.
- Find bridges or synthetic helpers of the class.
- Debug bytecode changes in a specific class.
- Scan annotations declared only by the current class, if that is your scanner's policy.

### 6.2. `getMethods()`: visible public methods

```java
Method[] methods = StringMapper.class.getMethods();
```

The result includes declared `public` methods and inherited `public` methods under Reflection rules. It can include public bridges as well as methods from `Object`, interfaces, or superclasses.

Use it when you need the **public surface** callable on the class. However, if your goal is “count how many methods the programmer wrote”, `getMethods().length` will give the wrong count due to inherited methods and compiler-generated methods.

Note: `getDeclaredMethods()` and `getMethods()` **do not guarantee ordering**. Sort by deterministic criteria before displaying, comparing snapshots, or testing.

### 6.3. Why can `getDeclaredMethod` be misleading?

```java
Method real = StringMapper.class.getDeclaredMethod(
        "map", String.class);

Method bridge = StringMapper.class.getDeclaredMethod(
        "map", Object.class);
```

Arguments passed to `getDeclaredMethod` are **runtime parameter types**, not source-level type arguments. After erasure, the bridge takes `Object`, so the second lookup finds a real method in the class file.

If two JVM methods have the same name and same parameter types but different return types (possible due to covariant returns and bridges), Reflection applies specific resolution rules when using `getDeclaredMethod`; do not rely on a single name/parameter lookup to **thoroughly inspect all methods**. Use `getDeclaredMethods()` and check return type, `isBridge`, and `isSynthetic` on each element.

## 7. Generic Signatures and Raw Descriptors: Do Not Conflate Them

`Method.getReturnType()` and `Method.getGenericReturnType()` return related but distinct information:

```java
Method m = Mapper.class.getDeclaredMethod("map", Object.class);

System.out.println(m.getReturnType());        // class java.lang.Object
System.out.println(m.getGenericReturnType()); // T
```

`Mapper<T>.map(T)` uses a type variable `T` in source. After erasure, the runtime return type is `Object`, yet the generic metadata of the method declared on the interface lets Reflection report `T`.

For the bridge `StringMapper.map(Object)`, you typically see raw/erased info (such as `Object`) because the bridge is generated by the compiler to adapt descriptors, whereas the `map(String)` implementation has return type `String`.

To inspect the relationship between a subclass and a generic interface, check:

```java
StringMapper.class.getGenericInterfaces();
```

The output can contain a `ParameterizedType` representing `Mapper<String>`. This is **metadata of the supertype relationship**; it does not mean every `Mapper<String>` instance carries a runtime type argument checkable with `instanceof Mapper<String>`.

### 7.1. Parameters with bounds other than `Object`

If the interface is declared as:

```java
interface NumberMapper<T extends Number> {
    T map(T value);
}
```

then the erasure of type variable `T` is `Number`, so the corresponding descriptor uses `Number`, not `Object`. When using Reflection, look up the bridge method with the appropriate raw parameter (`Number.class`) and do not assume every generic bridge accepts `Object`.

For example, the signature:

```text
map(Number):Number
```

can be the forwarding entry point to a concrete implementation taking `Integer`. `Object` appeared in our earlier example solely because the interface's type variable **had no explicit bound**.

### 7.2. Synthetic and bridge are not “type erasure itself”

Erasure is the rule compiling generic types into bytecode-compatible forms. A generic method can undergo erasure **without generating a bridge**:

```java
static <T> T identity(T value) {
    return value;
}
```

When there is no override relationship needing to connect two different descriptors, `identity` needs no bridge. Conversely, a non-generic method with a covariant return can require a bridge. Therefore:

- Having generics **does not imply** `isBridge() == true`.
- Having a bridge **does not imply** the parent method is generic.
- Having synthetic methods **does not imply** a bridge exists.
- Having no bridge **does not imply** no type erasure occurred.

## 8. Filtering Methods When Building API-Scanning Tools

A framework may scan methods to build REST routes, record audit metadata, build schemas, or register handlers. Without distinguishing bridges, a single source method could be processed twice when a class file contains both the implementation and a bridge.

### 8.1. Filtering out compiler-generated methods in a scan

A reasonable policy **when you only want methods declared directly by programmers on the class**:

```java
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.List;

static List<Method> sourceLikeDeclaredMethods(Class<?> type) {
    return Arrays.stream(type.getDeclaredMethods())
            .filter(m -> !m.isBridge())
            .filter(m -> !m.isSynthetic())
            .toList();
}
```

The snippet above is **an illustrative utility method** that must be placed inside a class with proper imports when used. It retains methods lacking both flags, though it does not guarantee finding “the entire source API” in every context:

- **Inherited** methods are not in `getDeclaredMethods()`.
- Interface default methods, annotations, overrides, and generic hierarchies still require their own policies.
- Class file structures generated by different compilers or bytecode tools may carry different flags/metadata.
- Not every non-synthetic method is publicly exposed; you still need to check `Modifier.isPublic(...)` or other access rules.

If you only want to exclude bridges while **still observing synthetic helpers**, use only:

```java
.filter(m -> !m.isBridge())
```

There is no single filter suitable for all tasks. A “source-like methods only” policy makes sense for simple internal documentation, but drops useful data when debugging bytecode.

### 8.2. Avoiding duplicate counts while preserving annotation info

Suppose a scanner creates one API descriptor per implementing method. A bridge may sit beside the method serving the same business role. One approach:

1. Scan `getDeclaredMethods()` or `getMethods()` depending on scanner scope.
2. Decide upfront whether the scanner needs **implementation methods**, **interface contracts**, or both.
3. Identify bridges via `isBridge()`, not by guessing from names or return types alone.
4. When a bridge represents an implementation, resolve the target method via **name, parameter-type relationship, return-type relationship, and hierarchy**; do not blindly match the first method with the same name.
5. For annotations, determine where annotations are declared and whether framework rules merge metadata from interfaces, superclasses, implementation methods, or bridges.
6. Test with generic interfaces, covariant returns, overloads, inherited methods, and raw types to verify the scanner neither misses methods nor double-registers them.

Do not assume annotations on source methods are always—or never—copied to bridges across all tools and JDKs. If annotation metadata has legal or business impact, inspect the actual bytecode and framework policy. Do not strip bridges from results **before** resolving override relationships if your scanner needs them to locate an underlying method.

### 8.3. Do not identify bridges by method name

In the example, the bridge is still named `map`, just like the implementation. In the covariant return example, the bridge is named `score`, just like the real method. It **has no standard prefix** such as `bridge$`.

Conversely, the name `lambda$callback$0` in the example is a `javac` code-generation detail; different names or compilation strategies are entirely possible.

The standard criterion for identifying a bridge in Reflection is `Method.isBridge()`. Use `isSynthetic()` to recognize synthetic methods in general, without guessing from name prefixes.

## 9. Typical Diagnostic Scenarios

### Scenario A: Reflection sees `map(Object)` even though source only has `map(String)`

Check:

```java
for (Method m : StringMapper.class.getDeclaredMethods()) {
    System.out.println(m.getName() + ": " + m.isBridge());
}
```

If `map(Object)` is a bridge, you will see `true`. Use `javap -v` to verify `ACC_BRIDGE` and `ACC_SYNTHETIC`. Do not modify the source class to “remove” a compiler-generated method: it is needed for proper dispatch.

### Scenario B: Handler scanning causes the same operation to appear twice

If two `Method` objects have the same name and one has `isBridge() == true`, check whether they correspond to the same business implementation. For scanners targeting source-level APIs, filter or merge bridges according to proper resolution rules. Test with annotations on both interfaces and implementations before considering filtering sufficient.

### Scenario C: A synthetic method appears even though the class uses no generics

For example, a lambda helper method. A method with `isSynthetic() == true` and `isBridge() == false` does not prove the class has generics. Use `javap` and source declarations to see why the compiler generated it.

### Scenario D: A covariant return override yields two entries with the same name and parameters

With `Number score()` in the parent and `Integer score()` in the child, the JVM can have a bridge returning `Number` and an implementation returning `Integer`. Use **all of `getDeclaredMethods()`** to inspect the method pair; a single lookup by name and parameter list may not reveal the full return-type difference.

### Scenario E: Scan output varies unpredictably across runs

By the Reflection specification, the element order in the array returned by `getDeclaredMethods()` is not guaranteed. Sort by stable criteria such as name, parameter list, and return type when generating reports. Do not rely on index `[0]` to decide which method is “real” or “bridge”.

### Scenario F: Bytecode libraries or compilers other than javac

Do not assume every class file matches bytecode generated by `javac --release 17`. Some class files are produced by runtime tools, bytecode weaving, or other JVM language compilers. `isBridge()`/`isSynthetic()` reflect the actual flags on the method; business meaning or method origin must be verified against the specific toolchain.

## 10. Practical Debugging Workflow

When a Reflection tool reports an unfamiliar method:

1. **Pinpoint the class to inspect** and call `getDeclaredMethods()` to see the exact methods inside that class file.
2. **Print at minimum**: name, parameter types, return type, `isBridge()`, `isSynthetic()`, `getDeclaringClass()`.
3. **Sort the results**, because Reflection guarantees no order.
4. If it is a bridge, **locate the generic supertype or covariant-return method** and compare descriptors before and after erasure.
5. If it is only synthetic, **check lambdas/helpers or other code-generation mechanisms**; do not assume it is a bridge.
6. Use `javap -p -s` for descriptors and `javap -p -v` for flags. When you need to verify the forwarding target, use `javap -p -c`.
7. **Decide based on scanner purpose**: keep the method for bytecode debugging, or filter/merge it when displaying a logical API.
8. **Re-test** with generic interfaces, generic subclasses, covariant returns, overloads, and lambda-containing code to validate classification logic.

Quick lookup table:

| Observed result | Meaning to investigate |
| --- | --- |
| `bridge=true, synthetic=true`, parameter `Object` | Bridge due to erasure of an unbounded generic type. |
| `bridge=true, synthetic=true`, different return type | Possibly a bridge supporting a covariant return. |
| `bridge=false, synthetic=true`, lambda-helper-like name | Compiler-generated helper, not performing override bridging. |
| `bridge=false, synthetic=false` | Ordinary method, though still check access/public/inherited rules if describing an API. |
| `getMethods()` returns more methods than `getDeclaredMethods()` | Likely due to inherited public methods, not necessarily all bridges. |
| Compiler reports `name clash` | Source signature and erasure conflict; do not solve by writing a manual bridge method. |

## 11. Conceptual Pitfalls to Avoid

**Pitfall 1 — `isSynthetic()` means `isBridge()`.** In reality, synthetic covers many kinds of compiler-generated methods. For example, the lambda helper in the runnable program is synthetic but not a bridge.

**Pitfall 2 — every generic method has a bridge.** A standalone generic method not participating in an override usually needs no bridge. Bridges are generated when needed to maintain call/override compatibility after compilation.

**Pitfall 3 — a bridge is a source overload callers should invoke.** A bridge is a compilation detail to ensure dispatch. Frameworks and reflection can see it; Java source calls should follow the published generic or covariant-return contract.

**Pitfall 4 — `getDeclaredMethods()` returns only programmer-written methods.** It can also return bridges and synthetic helpers declared in the class file.

**Pitfall 5 — all synthetic methods can be filtered blindly without evaluating needs.** For source API docs, filtering synthetic methods may make sense. Yet in debuggers, coverage tools, or bytecode instrumentation, dropping all synthetic methods can lose essential data.

**Pitfall 6 — reflection method order is fixed.** Java promises no ordering; all reports and comparison tests should sort explicitly or compare as sets.

**Pitfall 7 — `getGenericReturnType()` always reveals an object's runtime type argument.** This API describes the generic declaration/metadata of the method, not a reconstruction of runtime specialization for every `List<T>` instance.

**Pitfall 8 — `isBridge()` identifies the exact target method being called.** The flag only identifies a bridge. To know where the bridge forwards, inspect type relationships or bytecode (`javap -c`) and avoid name-only heuristics.

## 12. Self-Check Questions

**Question 1.** Why can `StringMapper.class.getDeclaredMethods()` contain both `map(String)` and `map(Object)` when source defines only `map(String)`?

<details>
<summary>Answer</summary>

`Mapper<T>.map(T)` erases to `map(Object):Object`; the implementation after binding `T = String` is `map(String):String`. The compiler generates a `map(Object):Object` bridge to preserve dispatch from the interface/supertype. Reflection sees the bridge with `isBridge() == true`.

</details>

**Question 2.** Does `isSynthetic() == true` prove a method is a bridge?

<details>
<summary>Answer</summary>

No. A synthetic method can be a compiler-generated helper for implementing a lambda or another purpose. Check `isBridge()` separately; if needed, read `ACC_BRIDGE`/`ACC_SYNTHETIC` with `javap -v`.

</details>

**Question 3.** When scanning a class for methods declared by that class, should you start with `getMethods()` or `getDeclaredMethods()`?

<details>
<summary>Answer</summary>

`getDeclaredMethods()`, because it retrieves methods declared on the current class, including non-public and synthetic ones. If the goal is the entire public surface including inherited methods, consider `getMethods()`. Both can return compiler-generated methods; an appropriate filtering policy is needed.

</details>

**Question 4.** Why can `Derived.score()` also generate a bridge even without using generics?

<details>
<summary>Answer</summary>

`Base.score()` returns `Number`, and `Derived.score()` overrides it with `Integer` (covariant return). Because JVM descriptors differ in return type, the compiler can generate a `Number score()` bridge to satisfy calls compiled against the superclass descriptor.

</details>

**Question 5.** Why should you not identify synthetic methods by a `lambda$...` name?

<details>
<summary>Answer</summary>

Helper names are a compiler detail, not a standard identifier for all synthetic methods. Reflection provides `isSynthetic()`, and `javap -v` shows `ACC_SYNTHETIC`. A synthetic method may have no `lambda$` prefix, and a bridge method normally shares the same name as its implementation.

</details>

## 13. Technical Summary

**`Method.isBridge()` checks for bridge methods; `Method.isSynthetic()` checks for synthetic methods.** Bridges are typically generated by the compiler to reconcile descriptor differences after generic erasure or covariant returns, whereas synthetic is a broader category that also includes compiler-generated lambda helpers.

When accurate analysis is required, combine **`getDeclaredMethods()` + parameter/return types + `isBridge()` + `isSynthetic()`**, along with `javap -s/-v` to verify descriptors and flags. When building API-scanning tools, decide clearly whether you want **methods present in bytecode** or **methods representing the source contract**, then filter or merge accordingly. Do not rely on helper names or the method order returned by Reflection.
