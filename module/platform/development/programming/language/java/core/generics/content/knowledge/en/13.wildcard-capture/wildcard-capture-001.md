# What Problem Does Capture Conversion Solve in Java Generics?

**Capture conversion** is a Java compiler mechanism that treats a generic type with a **wildcard** (`?`, `? extends T`, `? super T`) as an **unknown but definite type within a type-checking context**. The compiler temporarily assigns an internal type name to `?`, often shown in error messages as `capture#1 of ?` or `CAP#1`. As a result, a generic method can preserve the relationship between an **element retrieved from** a collection and an **element put back into that same collection**, even when the caller does not know the actual type argument.

The problem capture conversion solves is not “turning `List<?>` into `List<Object>`.” It solves **maintaining a single consistent hidden type within one operation**, enabling genuinely safe operations on a collection whose element type is unknown.

A core example:

```java
static void swap(List<?> items, int i, int j) {
    swapCaptured(items, i, j);
}

private static <T> void swapCaptured(List<T> items, int i, int j) {
    T saved = items.get(i);
    items.set(i, items.get(j));
    items.set(j, saved);
}
```

`swap` can accept `List<String>`, `List<Integer>`, `List<Number>`, and many other list types. `swapCaptured` uses **a single type variable `T` for the entire operation on one list**, so it reads and writes back an element of the right type without an unsafe cast.

## 1. The Problem: Java Knows “There Is a Type” Without Knowing Its Name

Example:

```java
List<Integer> integers = new ArrayList<>(List.of(10, 20));
List<?> unknown = integers;
```

At runtime, the list contains `Integer` objects. However, according to the declared type `List<?>` of `unknown`, the compiler only knows that the type argument is **an unspecified reference type**.

Simple read operations remain safe:

```java
Object element = unknown.get(0);  // Valid.
int length = unknown.size();      // Valid.
```

By contrast, these two operations are rejected:

```java
// unknown.add(10);            // COMPILE ERROR.
// unknown.set(0, unknown.get(0)); // COMPILE ERROR.
```

`add(10)` is unsafe in general because `unknown` could point to a `List<String>`. But `set(0, unknown.get(0))` looks reasonable: take the element from that same list and put it back at the same position—no other type could be introduced.

**The issue lies in the type information that the expression gives to the compiler.** Through `List<?>`, the result of `get(0)` has a hidden element type; when checking the `set` call, Java does not automatically unify the captured types at the two wildcard occurrences into a named, stably usable type. Therefore, the expression `unknown.set(0, unknown.get(0))` does not compile, even though the operation is conceptually safe when both accesses truly belong to the same list.

We need a way to **name the unknown element type**, to prove that the value read out can be written back to the exact place that produced it. Capture conversion combined with a generic helper makes this possible.

## 2. What Is Capture Conversion?

Consider the type:

```java
List<?> values;
```

In a simplified mental model, when Java needs to check an expression of type `List<?>`, it can open the wildcard into a **fresh type variable generated by the compiler**:

```text
List<?>            --capture conversion-->  List<CAP#1>

CAP#1 is an unknown type with an upper bound of Object.
```

The name `CAP#1` is purely illustrative; programmers cannot declare or directly reference `CAP#1` in source code. Error messages in various `javac` versions may call it `capture#1 of ?` or use a different number.

What matters is not the value of this name, but the type relationship:

- An element retrieved from `List<CAP#1>` has type `CAP#1`.
- A method accepting `List<CAP#1>` can use `CAP#1` as **a single unified type within the method body**.
- Because the list has type `List<CAP#1>`, it accepts a `CAP#1` element for appropriate write operations.
- Java does not need to know whether the actual type is `Integer` or `String`; the type constraints are sufficient to verify safety.

**Capture conversion happens at compile time.** It does not modify the list at runtime, create a copy, lose/change the element's type, or turn `List<Integer>` into `List<Object>`.

### Relationship with Wildcard Kinds

| Wildcard | Bound model of the captured type | Safe to read as | Guaranteed non-null write |
| --- | --- | --- | --- |
| `?` | A hidden type with default upper bound `Object` | `Object` | No specific type through the wildcard reference |
| `? extends Number` | A hidden type beneath upper bound `Number` | `Number` | No specific type through the wildcard reference |
| `? super Integer` | A hidden type with lower bound `Integer`; for `List<E>` the upper bound is typically `Object` | `Object` | `Integer` |
| `T` in `List<T>` | A named type variable, reusable in the method signature/body | `T` | `T` |

This is an explanatory model for common cases. The exact bound rules also depend on the constraints of the original generic type parameter per the Java Language Specification; `CAP#1` should not be treated as a Java type you can write in source code.

## 3. A Wildcard Does Not Allow Arbitrary Element Writes

For example, the following method tries to add an element to an arbitrary list:

```java
static void addValue(List<?> items) {
    // items.add("Java"); // COMPILE ERROR.
}
```

If `items` is a `List<Integer>`, adding a `String` would violate the type contract. Capture conversion **does not** make this statement legal.

Calling `items.add(null)` is allowed from a type-checking standpoint because `null` is compatible with every reference type. Even so, a list like `List.of(...)` does not support modification, and some implementations may reject `null`. You must distinguish **type validity** from **runtime modifiability**.

`List<?>` can be read as `Object`, but that does not mean the collection is actually a `List<Object>`:

```java
List<String> names = new ArrayList<>();
List<?> unknown = names;    // Valid.
// List<Object> objects = names; // COMPILE ERROR.
```

Java Generics are **invariant**. If a `List<String>` could be assigned to a `List<Object>`, code could insert an `Integer` into a list that promised to hold only `String`s. Wildcards and capture preserve type safety without breaking that rule.

## 4. Where Does the “capture of ?” Error Come From?

A classic example:

```java
static void replaceWithItself(List<?> list) {
    list.set(0, list.get(0)); // COMPILE ERROR.
}
```

This is **code intentionally written not to compile**. During compilation, `javac` may mention one or more `capture#... of ?` types or report `Object cannot be converted to capture#...`. The exact wording and numbering depend on the compiler.

The input parameter is declared as `List<?>`. The call `set(int, E)` expects an element of the list's exact type `E`. The `get` expression uses one type check/capture, while the argument position of `set` may use another capture. The compiler lacks a **named type variable** linking those two operations under a single stable generic contract.

Therefore, a “capture of ?” message usually indicates: **the compiler opened the wildcard into a hidden type, but the available constraints are insufficient to prove that the assignment or call is safe**.

You should distinguish:

- **Type-expression error:** an operation that is inherently safe (such as swapping elements within the same list), but the signature only uses a wildcard so it lacks an explicit type relationship.
- **Genuine design error:** an operation moving an element from `List<String>` to `List<Integer>` with no compatibility relationship. No capture helper can turn a mismatched write into a valid one.

## 5. A Generic Helper “Names” an Existing Concrete Type

Suppose a public API needs to accept any list:

```java
static void preserveFirst(List<?> values) {
    preserveCaptured(values);
}

private static <E> void preserveCaptured(List<E> values) {
    if (!values.isEmpty()) {
        E first = values.get(0);
        values.set(0, first);
    }
}
```

These are **illustrative methods** that belong inside a class importing `java.util.List`. From the outside, `?` does not specify an element type name. When passing `values` to the helper, the compiler captures the wildcard and infers a suitable `E`; both `get` and `set` inside use the same `E`. There is no raw type or unchecked cast.

The example simply writes back the existing value to isolate the mechanism: **the element type does not need a known name, only consistency within a single helper call**. If the list does not support `set`, the program can still throw `UnsupportedOperationException`. Practical variants such as swapping, duplicating elements, or working with bounds must also consider indices, mutability, and type boundaries; capture does not permit writing an arbitrary external value.

## 6. When Is a Helper Needed, and When Is It Not?

Not every read of `List<?>` requires a capture helper.

Normal reading:

```java
static void show(List<?> items) {
    for (Object item : items) {
        System.out.println(item);
    }
}
```

This code is valid because the output of `get` or iteration can be treated as `Object`.

A single-parameter generic method can also accept `List<?>`:

```java
static <T> T first(List<T> values) {
    return values.get(0);
}

static void printFirst(List<?> unknown) {
    Object firstValue = first(unknown);
    System.out.println(firstValue);
}
```

At the call `first(unknown)`, the compiler can capture the wildcard to find a suitable `T`. The return type is safely used by the caller as `Object`. The `first` method does not need to know the concrete `T` and does not insert elements of the wrong type.

**A generic helper is most needed when multiple internal operations must reuse the same hidden type**, such as reading and then writing back an element in the same collection. If you only iterate and call `toString()`, `size()`, or `contains(Object)`, adding a helper may add unnecessary complexity.

## 7. Two Wildcards Can Be Two Different Types

This is a very important limitation of capture conversion:

```java
static <T> void requireSameType(List<T> left, List<T> right) {
    // Both parameters must match the same T.
}

static void cannotProveSame(List<?> first, List<?> second) {
    requireSameType(first, second); // COMPILE ERROR.
}
```

`first` could be a `List<Integer>`, while `second` could be a `List<String>`. Each `?` can produce a different capture. No single `T` can be inferred to satisfy both `List<T>` parameters.

Notably, **even passing the same variable twice can be rejected**:

```java
static void stillCannotProveSame(List<?> items) {
    requireSameType(items, items); // COMPILE ERROR.
}
```

The two occurrences of the expression `items` in two argument positions can undergo separate capture conversions. The type system does not automatically prove that two captures are **one shared named type**, even though a human knows the same object is passed twice.

By contrast:

```java
static void worksWithKnownType(List<Integer> items) {
    requireSameType(items, items); // Valid: T = Integer.
}
```

Here the type argument `Integer` is already known from the signature. If an API genuinely requires multiple parameters of the same type, convey that information via a generic type variable `<T>` right in the appropriate signature, rather than erasing them into independent `List<?>` parameters.

### Why Does a Single-Parameter Helper Work While a Two-Parameter Helper Fails?

- `swapCaptured(List<T>)` needs **one hidden type** to read and write within the same list. One capture can be inferred as `T`.
- `requireSameType(List<T>, List<T>)` requires **two arguments** to have the same `T`. From two uses of `List<?>`, the compiler cannot guarantee that the two captures are identical.

That is the boundary between **naming an unknown type** and **inventing a type relationship not present in the signature**.

## 8. Capture Conversion with Bounded Wildcards

The capture mechanism also applies to `? extends T` and `? super T`, not just `?`.

### `? extends Number`: reading numbers as `Number`

```java
static double sum(List<? extends Number> source) {
    double result = 0.0;
    for (Number n : source) {
        result += n.doubleValue();
    }
    return result;
}
```

The hidden element type satisfies the upper bound `Number`. Thus reading as `Number` is safe, but you cannot add a specific `Integer` to `source`: the source might actually be a `List<Double>`.

For example, an element from the list itself can be written back using a helper:

```java
static void repeatFirst(List<? extends Number> source) {
    repeatCaptured(source);
}

private static <T extends Number> void repeatCaptured(List<T> source) {
    if (!source.isEmpty()) {
        T value = source.get(0);
        source.add(value);
    }
}
```

This operation only inserts **an existing element of the exact type `T`** into the same `List<T>`. It is type-safe, though the collection must support adding elements; if it is `List.of(1, 2)`, the operation will throw `UnsupportedOperationException`.

### `? super Integer`: writing `Integer` to a destination

```java
static void addDefaults(List<? super Integer> target) {
    target.add(10);
    target.add(20);

    Object any = target.get(0);  // Only guaranteed to read as Object.
    System.out.println(any);
}
```

With a lower-bounded type, the actual type argument could be `Integer`, `Number`, or `Object`. The target is guaranteed to accept `Integer`, but existing elements are not necessarily `Integer`s.

**Capture does not alter the safe read/write permissions determined by bounds.** It cannot turn `List<? extends Number>` into a target that accepts any `Number`, nor turn `List<? super Integer>` into a source guaranteed to contain only `Integer`s.

## 9. When Transferring Elements Between Two Lists: Describe the Type Relationship

A single-parameter helper solves reading/writing within **the same list**. If you want to **transfer elements between two different lists**, explicitly describe the source–destination relationship:

```java
static <T> void appendAll(
        List<? extends T> source,
        List<? super T> destination) {
    for (T element : source) {
        destination.add(element);
    }
}
```

`source` is a producer that supplies elements usable as `T`; `destination` is a consumer that accepts `T`.

Example:

```java
List<Integer> integers = List.of(3, 5);
List<Number> numbers = new ArrayList<>();

appendAll(integers, numbers); // Valid: Integer is a Number.
```

A function accepting two arbitrary `List<?>` parameters cannot offer the same contract:

```java
static void unsafeAttempt(List<?> destination, List<?> source) {
    // destination.add(source.get(0)); // COMPILE ERROR.
}
```

The reason is not a missing capture trick. The two lists could hold unrelated types (`String` and `Integer`); the API must express a **genuine compatibility relationship** if it wants to transfer elements.

You can call `appendAll` between lists with a valid relationship; however, you should not allow source and destination to be the same mutable list being modified during iteration without handling that case. With `ArrayList`, iterating and adding simultaneously typically causes `ConcurrentModificationException`. When designing an API, you can stipulate that the two arguments must not alias or take an appropriate snapshot before operating.

## 10. Complete Java 17+ Example

The program below illustrates five points:

1. `List<?>` accepts lists with different element types.
2. A single-parameter generic method reads from `List<?>` thanks to capture conversion.
3. A `<T>` helper swaps and duplicates elements **within the same list**.
4. Two lists without the same element type are still handled separately without casting.
5. When transferring elements between a source and a destination list, the API uses `extends/super` to express the type relationship.

Save as **`CaptureConversionDemo.java`**:

```java
import java.util.ArrayList;
import java.util.List;

public class CaptureConversionDemo {
    static Object first(List<?> items) {
        return items.get(0);
    }

    static void swap(List<?> items, int a, int b) {
        swapCaptured(items, a, b);
    }

    private static <T> void swapCaptured(List<T> items, int a, int b) {
        T saved = items.get(a);
        items.set(a, items.get(b));
        items.set(b, saved);
    }

    static void duplicateFirst(List<?> items) {
        duplicateCaptured(items);
    }

    private static <T> void duplicateCaptured(List<T> items) {
        if (!items.isEmpty()) {
            items.add(items.get(0));
        }
    }

    static <T> void appendAll(
            List<? extends T> source,
            List<? super T> destination) {
        for (T element : source) {
            destination.add(element);
        }
    }

    public static void main(String[] args) {
        List<Integer> ids = new ArrayList<>(List.of(7, 8, 9));
        List<String> tags = new ArrayList<>(List.of("core", "java"));

        List<?> hiddenIds = ids;
        List<?> hiddenTags = tags;

        System.out.println("first ids = " + first(hiddenIds));
        System.out.println("first tags = " + first(hiddenTags));

        swap(hiddenIds, 0, 2);
        swap(hiddenTags, 0, 1);
        duplicateFirst(hiddenIds);

        System.out.println("ids = " + ids);
        System.out.println("tags = " + tags);

        List<Number> destination = new ArrayList<>();
        appendAll(ids, destination);
        System.out.println("destination = " + destination);
    }
}
```

Compile/run:

```bash
javac CaptureConversionDemo.java
java CaptureConversionDemo
```

Stdout:

```text
first ids = 7
first tags = core
ids = [9, 8, 7, 9]
tags = [java, core]
destination = [9, 8, 7, 9]
```

Explanation:

- `hiddenIds` points to `List<Integer>` and `hiddenTags` points to `List<String>`; both can be used with `List<?>`.
- `first` only retrieves a value as `Object`, so it needs no write permission.
- `swapCaptured` holds a single `T` per call, so `Integer` is only swapped with `Integer` and `String` only with `String`.
- `duplicateCaptured` takes the first element of type `T` and adds that same element to `List<T>`. `ids` gains `9`, while `tags` undergoes no structural change after `swap`.
- `appendAll` reads `Integer`s from `ids` and puts them into the destination list `List<Number>`. This differs from an ill-typed assignment `List<Number> x = ids`.

The program uses modifiable `ArrayList` instances; if replaced with lists created by `List.of(...)` where `swap`/`duplicateFirst` mutate elements, runtime modification exceptions must be considered.

## 11. How Does Capture Conversion Differ from Type Inference and Type Erasure?

These three concepts are related but not synonymous.

| Mechanism | Where does it mainly occur? | Purpose |
| --- | --- | --- |
| **Capture conversion** | Compiler, when processing a type containing a wildcard | Opens `?` into a fresh hidden type variable with appropriate bounds |
| **Type inference** | Compiler, when inferring type arguments of a generic call | Finds a suitable `T` from arguments, bounds, and context; can work together with capture |
| **Type erasure** | Compilation to bytecode | Represents generics at runtime primarily through erased types and appropriate casts/bridges |

A call `swapCaptured(items)` where `items` has type `List<?>` typically requires both **capture conversion** (a hidden type for `?`) and **type inference** (inferring `T` in the helper call). After compilation, having a temporary type variable `T` does not create a new runtime class named `CAP#...`.

The following example **cannot** use capture to inspect elements at runtime:

```java
// Invalid: cannot check the Integer type argument using instanceof.
// if (unknown instanceof List<Integer>) { ... }
```

Similarly, an unchecked cast may silence compiler warnings, but it does not prove that two wildcards have the same type and does not make a mismatched write safe.

## 12. Limitations to Keep in Mind

### Capture conversion does not grant arbitrary write permission

`List<?>` still does not allow adding `"text"`; `List<? extends Number>` still does not allow adding an arbitrary `Integer`. Capture only permits using **an element already known to be of the same type `T`** through an appropriate helper.

### Capture does not unify two independent wildcards

`List<?> a` and `List<?> b` may correspond to two different types. You cannot deduce that elements are interchangeable merely because both variables have the form `List<?>`.

### Capture does not recover generic type arguments at runtime

Type erasure still applies. There is no runtime operation that automatically “reads the real type of `List<?>`” from capture conversion.

### Capture does not eliminate other runtime errors

A type-safe generic helper can still throw `IndexOutOfBoundsException` for an invalid index, `UnsupportedOperationException` when the list is unmodifiable, or `NullPointerException` if using a `null` reference without checking.

### Capture does not replace API signature design

If a method needs to add numbers to a destination, use `Collection<? super Integer>` or `Collection<? super T>`. If it only retrieves numbers from a source, use `Collection<? extends Number>`. If it needs to constrain multiple arguments together, use a type variable `<T>` expressing that relationship. Only use a capture helper when an internal operation genuinely needs to name **an existing hidden type**.

## 13. Workflow for Handling “capture#... of ?” Errors

When you encounter a compile error mentioning `capture of ?`, check in order:

1. **Which parameter contains the wildcard?** For example `List<?>`, `List<? extends Number>`, or `List<? super Integer>`.
2. **Is the operation reading or writing?** Reading as the upper bound is usually valid; writing must be compatible with the specific hidden type.
3. **Does the written value originate from that same object?** If reading from the same list and reusing it, a generic helper `<T>` taking **a single `List<T>`** can express the relationship safely.
4. **Are there two different lists/wildcards?** If so, do not assume they share the same type; express the source–destination relationship or use a more specific type.
5. **Are you trying to cast or use a raw type to bypass the compiler?** Fix the signature, remove unchecked casts, and let the compiler prove the relationship before writing.
6. **Does the solution still satisfy the runtime contract?** Valid indices, mutable collections, and aliasing conditions still need to be ensured.

Quick-fix example:

```java
// Wrong: no shared type name to both get and set.
// static void wrong(List<?> x) {
//     x.set(0, x.get(0));
// }

// Right: helper keeps T consistent inside.
static void right(List<?> x) {
    rightCaptured(x);
}

private static <T> void rightCaptured(List<T> x) {
    if (!x.isEmpty()) {
        T value = x.get(0);
        x.set(0, value);
    }
}
```

The `right`/`rightCaptured` methods are illustrative snippets to place inside a class; the `wrong` lines are commented out to indicate a compile error. When using them, import `java.util.List`.

## 14. Self-Check Exercises

Suppose you have:

```java
List<Integer> ints = new ArrayList<>(List.of(1, 2));
List<String> words = new ArrayList<>(List.of("a", "b"));
List<?> a = ints;
List<?> b = words;
```

Evaluate the following statements:

| Expression/operation | Result | Reason |
| --- | --- | --- |
| `Object x = a.get(0);` | Valid | Reads `List<?>` as `Object` |
| `a.add(3);` | Compile error | Concrete element type is unknown |
| `a.set(0, a.get(0));` | Compile error | Lacks a unified `T` across both wildcard operations |
| `swap(a, 0, 1);` with helper from section 10 | Valid | Java captures a single hidden type for the helper call |
| `swap(b, 0, 1);` | Valid | Another capture, applied to the `String` list |
| `requireSameType(a, b);` with `<T> void requireSameType(List<T>, List<T>)` | Compile error | Two captures have no equality relationship |
| `a.add(null);` | Type-valid | Still depends on whether the collection supports writes/nulls |
| `Object first = first(a);` with `first(List<?>)` from section 10 | Valid | Reads as `Object` |
| `appendAll(ints, new ArrayList<Number>());` | Valid | Source `Integer` and destination `Number` are compatible |

Calls requiring valid elements or indices can still throw exceptions if the collection is empty; the table only evaluates **Java type validity**.

## Takeaways

- **Capture conversion** “opens” a wildcard into a **bounded hidden type** so the compiler can check generic usages consistently.
- With `List<?>`, you can read as `Object` but cannot arbitrarily add a non-null element.
- `list.set(0, list.get(0))` on `List<?>` is usually rejected due to the lack of a shared named type relationship; a **generic helper `<T>`** resolves this safe case by accepting a `List<T>`.
- **One wildcard is not automatically equal to another.** Two uses of `List<?>` can create independent captures, even when passing the same variable to two arguments.
- Capture cannot make moving a `String` into a `List<Integer>` valid, does not remove Java Generics invariance, and does not change types at runtime.
- If an API truly relates two parameters, use `<T>` with `? extends T` for the source and `? super T` for the destination to express a safe relationship.
- When you see a `capture#... of ?` error, check whether **you need one consistent hidden type within the same collection**, or are mistakenly assuming two independent hidden types are the same.

Understanding capture conversion helps you write methods that accept wildcards flexibly while still operating on data in a type-safe manner, and distinguish errors solvable with a generic helper from errors requiring an API contract change.
