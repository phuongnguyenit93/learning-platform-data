# Bridge Methods Preserving Polymorphism in Java Generics

## 1. The Problem: After Type Erasure, the JVM Must Still Invoke the Right Override

In Java, **polymorphism** means that when calling an overridable method through a superclass or interface reference, execution must select the implementation matching the object's actual runtime class.

~~~java
Box<String> box = new StringBox();
box.set("java");
String result = box.get();
~~~

Given a generic base class `Box<T>` and a subclass `StringBox extends Box<String>`, a programmer expects the overridden `set` and `get` in `StringBox` to execute when called through `Box<String>`.

However, **type erasure** creates a difference between the type signature in Java source and the descriptor used by the JVM:

- In `Box<T>`, the unbounded parameter `T` is erased to **Object**.
- In `StringBox`, the specialized methods have a **String** parameter or return type.
- The JVM resolves methods by name and descriptor; the signature `set(Object)` differs from `set(String)`, and `get():Object` differs from `get():String` at the descriptor level.

To preserve the override relationship determined by the compiler from Java source, **javac can generate a bridge method**. This is a method with actual bytecode that forwards calls from the erased signature to the specialized implementation.

For `set`, the bridge needs to cast the `Object` argument to `String` before forwarding to `set(String)`. For `get`, the bridge may simply call `get():String` and return the result as `Object`.

A bridge method is a compiler-generated detail to preserve **polymorphism and binary compatibility**, not a method programmers are required to write manually.

## 2. Visualizing the Typical Case

Suppose we have two classes:

~~~java
class Box<T> {
    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}

class StringBox extends Box<String> {
    @Override
    public void set(String value) {
        super.set(value.toUpperCase());
    }

    @Override
    public String get() {
        return super.get();
    }
}
~~~

In **Java source**, `StringBox`'s `set(String)` and `get():String` validly override the two generic methods of `Box<String>`.

After type erasure, the base methods correspond to the descriptors:

~~~text
Box.set(java.lang.Object): void
Box.get(): java.lang.Object
~~~

Meanwhile, the methods declared directly in `StringBox` correspond to:

~~~text
StringBox.set(java.lang.String): void
StringBox.get(): java.lang.String
~~~

Without bridges, a call using the `set(Object)` descriptor from the base class could bypass the `set(String)` specialization in the subclass. `javac` therefore generates additional entry points with descriptors compatible with the erased form of the superclass.

You can think of `StringBox` as **roughly equivalent** to having the following additional methods:

~~~java
// PSEUDOCODE: do not copy directly into StringBox,
// because Java source signatures and rules may cause a name clash.
public void set(Object value) {
    set((String) value);
}

public Object get() {
    return get(); // Delegates to get() returning String under its own descriptor.
}
~~~

Those two methods are **illustrative pseudocode representing bytecode in Java-like syntax**, not valid source code to add. In bytecode, the JVM distinguishes different descriptors; in Java source, overloads cannot differ solely by return type, and trying to write `set(Object)` can cause an erasure clash.

**Key point:** `@Override` and generic type checking happen on the original Java program. The compiler is responsible for generating the bridges needed so that override relationship remains intact after removing most type parameter information.

## 3. Complete Java 17+ Program

Save the following content in the file **BridgeMethodDemo.java**:

~~~java
import java.lang.reflect.Method;
import java.util.Arrays;

public class BridgeMethodDemo {
    static class Box<T> {
        private T value;

        public void set(T value) {
            this.value = value;
        }

        public T get() {
            return value;
        }
    }

    static final class StringBox extends Box<String> {
        @Override
        public void set(String value) {
            super.set(value.toUpperCase());
        }

        @Override
        public String get() {
            return super.get();
        }
    }

    public static void main(String[] args) {
        // Calling through the generic parent type must select StringBox's override.
        Box<String> box = new StringBox();
        box.set("java");
        System.out.println("value=" + box.get());

        // Reflection detects the bridge methods generated by the compiler.
        System.out.println(
                "bridge names=" +
                Arrays.stream(StringBox.class.getDeclaredMethods())
                        .filter(Method::isBridge)
                        .map(Method::getName)
                        .sorted()
                        .toList()
        );

        // Raw type bypasses generic checking at the call site and triggers a warning.
        Box raw = box;
        try {
            raw.set(123);
        } catch (ClassCastException ex) {
            System.out.println("raw call=ClassCastException");
        }

        System.out.println("value after=" + box.get());
    }
}
~~~

Compile and run:

~~~bash
javac -Xlint:unchecked BridgeMethodDemo.java
java BridgeMethodDemo
~~~

Because of calling `raw.set(123)` on raw `Box`, the compiler will emit an **unchecked warning**. The warning appears in the compiler output, not in the program's stdout.

Stdout when running:

~~~text
value=JAVA
bridge names=[get, set]
raw call=ClassCastException
value after=JAVA
~~~

Explanation:

1. `box` has static type `Box<String>` but holds a `StringBox` object. Calling `box.set("java")` must execute the override in `StringBox`, converting the data to uppercase. The result of `box.get()` is `JAVA`.
2. `StringBox.class.getDeclaredMethods()` includes methods generated by the compiler directly on `StringBox`. `Method.isBridge()` identifies bridge methods. This example has bridges for both `set` and `get`; the list is sorted for deterministic output order.
3. A raw `Box` reference allows calling `set(123)` at compile time with a warning. At runtime, the `set(Object)` call dispatches to `StringBox`'s bridge, where the compiler inserted **`checkcast String`** before forwarding to `set(String)`.
4. The argument is an `Integer`, incompatible with `String`, so the bridge throws `ClassCastException`. The existing value inside `Box` is unchanged; the final call still prints `JAVA`.

**Note:** The raw type here is only to observe the runtime check inside the bridge. Production APIs should keep `Box<String>`; a normal `box.set(123)` statement would be rejected by `javac` at compile time.

## 4. Inspecting Bridge Methods in Bytecode with javap

After compiling, run:

~~~bash
javap -c -p 'BridgeMethodDemo$StringBox'
~~~

Depending on the shell, you need to quote the nested class name so the `$` character is not expanded; on Windows CMD you can use double quotes. You can also inspect synthetic and bridge flags in the class file:

~~~bash
javap -v -p 'BridgeMethodDemo$StringBox'
~~~

You will see **both the specialized `String` methods and the compiler-generated methods**. The essential bytecode form for `set`:

~~~text
public void set(java.lang.Object);
  ... aload_0
  ... aload_1
  ... checkcast java/lang/String
  ... invokevirtual set:(Ljava/lang/String;)V
  ... return
~~~

The `get` bridge has the conceptual form:

~~~text
public java.lang.Object get();
  ... aload_0
  ... invokevirtual get:()Ljava/lang/String;
  ... areturn
~~~

Offsets, constant-pool numbers, and minor opcode details may vary across `javac` versions. What to verify is **a descriptor matching the base class, bridge/synthetic flags, and the forwarding invocation to the specialized method**.

When using `javap -v`, a bridge generated by `javac` normally has the flags **ACC_BRIDGE** and **ACC_SYNTHETIC**. Reflection provides corresponding methods:

~~~java
method.isBridge();
method.isSynthetic();
~~~

In Java, the two properties have distinct meanings: `isBridge` indicates that the method is a bridge, whereas `isSynthetic` indicates a method not declared directly in source code; not every synthetic method is a bridge.

### Understanding JVM descriptors accurately

For `Box<T>` without an explicit bound:

| Method | JVM Descriptor |
| --- | --- |
| `Box.set(T)` after erasure | `(Ljava/lang/Object;)V` |
| `StringBox.set(String)` | `(Ljava/lang/String;)V` |
| Bridge `StringBox.set(Object)` | `(Ljava/lang/Object;)V` |
| `Box.get()` after erasure | `()Ljava/lang/Object;` |
| `StringBox.get():String` | `()Ljava/lang/String;` |
| Bridge `StringBox.get():Object` | `()Ljava/lang/Object;` |

The character `V` represents `void`, while `Ljava/lang/String;` represents the reference type `java.lang.String`. The JVM can distinguish method descriptors including the return type; Java source does not allow overloading based solely on return type.

## 5. Bridge Methods for Generic Interfaces

Bridge methods do not appear only when a class extends a generic superclass. Generic interfaces have the same issue:

~~~java
interface Converter<T> {
    T convert(T input);
}

final class TrimConverter implements Converter<String> {
    @Override
    public String convert(String input) {
        return input.trim();
    }
}
~~~

In source, `convert(String)` validly overrides `convert(T)` after `T` is substituted with `String`.

After erasure, the method in the interface has a descriptor roughly equivalent to:

~~~text
Converter.convert(Object) -> Object
~~~

In `TrimConverter`, the specialized method is:

~~~text
TrimConverter.convert(String) -> String
~~~

`javac` adds a compatible bridge `convert(Object) -> Object`. The bridge checks that the `Object` is a `String` before calling the specialized method and returns the result as `Object`.

Usage example:

~~~java
Converter<String> converter = new TrimConverter();
String result = converter.convert("  Java  "); // "Java"
~~~

Without the bridge, invocation through the generic interface after erasure might not find the specialized implementation. The bridge structure keeps interface calls behaving according to the override contract in Java source.

**This is an illustrative snippet meant to be placed into a program containing the definitions shown**, not a standalone Java file since it has no `main` method or public class.

## 6. Bounded Methods: Erasure Does Not Always Produce Object

Type bounds can make the erased type something other than `Object`.

~~~java
class NumberHolder<T extends Number> {
    public void accept(T input) {
        System.out.println(input.intValue());
    }
}

final class IntegerHolder extends NumberHolder<Integer> {
    @Override
    public void accept(Integer input) {
        System.out.println(input + 1);
    }
}
~~~

In `NumberHolder`, the erasure of `T` is **Number** because `T extends Number`. Therefore, the base method's descriptor accepts `Number`, while the override accepts `Integer`:

~~~text
NumberHolder.accept(Number)
IntegerHolder.accept(Integer)
bridge IntegerHolder.accept(Number) → cast Integer → accept(Integer)
~~~

A bridge **is not required to use `Object`**. It must match the signature on the base class/interface side after erasure. The erasure rule for a type variable takes its leftmost bound, so if there are more complex class/interface bounds, bridge generation likewise follows the actual runtime signature.

If you use raw `NumberHolder` and pass a non-`Integer` `Number` object to an `IntegerHolder`, the bridge can throw `ClassCastException` on `checkcast Integer`. A properly typed `NumberHolder<Integer>` API will normally reject incompatible arguments at compile time.

## 7. Bridges Also Appear with Covariant Return Types

**Covariant return types** allow an override to return a subtype of the original return type:

~~~java
class Animal {
    Animal copy() {
        return new Animal();
    }
}

final class Dog extends Animal {
    @Override
    Dog copy() {
        return new Dog();
    }
}
~~~

Even **without generics**, the return types of `Animal.copy()` and `Dog.copy()` differ in their JVM descriptors. The compiler can generate a bridge with a descriptor returning `Animal` in `Dog` to maintain proper dispatch through an `Animal` reference.

Hence, the rule “bridge methods are always caused by generics” is incorrect. There are at least two common situations: **type erasure changing an override signature** and **overrides with covariant return types**.

Example:

~~~java
Animal animal = new Dog();
Animal duplicate = animal.copy();
System.out.println(duplicate instanceof Dog); // true
~~~

Polymorphism is preserved: the executed method belongs to `Dog` and returns a `Dog`, even though the outer variable has type `Animal`.

## 8. How Bridges Preserve Polymorphism, Step by Step

With the `Box`/`StringBox` example, when calling:

~~~java
Box<String> box = new StringBox();
box.set("java");
~~~

one logical way to trace the process is:

1. `javac` verifies that `StringBox.set(String)` validly overrides `Box<String>.set(String)` at the source level.
2. After erasure, the call through `Box` carries the `set(Object)` descriptor.
3. `StringBox` has the `set(Object)` bridge, matching the descriptor needed to override in bytecode.
4. Dynamic dispatch selects the bridge on the runtime `StringBox` object.
5. The bridge casts the argument to `String`, then invokes `StringBox.set(String)`.
6. The specialized method performs uppercase conversion; the resulting behavior obeys the polymorphic meaning of the source code.

Similarly for `get`:

~~~java
String value = box.get();
~~~

The call through `Box` has a descriptor returning `Object` after erasure; the JVM can dispatch to the `get():Object` bridge in `StringBox`, the bridge calls the actual `get():String`, and the caller uses the result as a `String`. `javac` may insert **`checkcast String` at the caller** because the caller receives `Object` from the erased call.

Therefore, you can encounter **two checks at different places** in the same example:

- The cast inside the **`set(Object)`** bridge checks the argument before delegating to `set(String)`.
- The cast at the **`get()`** call site checks the returned `Object` result before using it as `String`.

They serve different operations. A bridge method is **a generated method**, whereas `checkcast` is **an opcode**; they should not be treated as the same concept.

## 9. Why Should You Not Write a Bridge Method Manually?

Trying to manually write a `set(Object)` method alongside `set(String)` in a generic subclass can trigger a **name clash** due to erasure or alter the overload/override contract, depending on the exact signatures.

Example that **intentionally does not compile**:

~~~java
class Base<T> {
    void set(T value) {}
}

class BadChild extends Base<String> {
    void set(Object value) {} // Name clash with the inherited method.
}
~~~

Because `set(T)` is erased to `set(Object)`, the subclass declaration cannot be arbitrarily used to “replace the bridge” in Java source. If the subclass wants to properly override the specialized method, write:

~~~java
class GoodChild extends Base<String> {
    @Override
    void set(String value) {}
}
~~~

Then let the compiler generate the bridge when needed. For proper generic methods, `@Override` is an essential tool: it asks the compiler to verify that the signature actually overrides an existing method.

## 10. Distinguishing Bridge, Overload, Override, and Method Hiding

| Mechanism | Meaning | When does it dispatch to the subclass implementation? |
| --- | --- | --- |
| **Override** | A subclass replaces the implementation of an inherited instance method according to Java rules. | Calling the instance method through a superclass/interface still selects the override based on the runtime object. |
| **Overload** | Same method name but different parameter lists in source. | Overload selection happens mainly at compile time based on expression and parameter types. |
| **Bridge method** | Compiler generates an additional method with a matching descriptor forwarding to the specialized implementation. | Keeps overriding working when erasure or covariant return types make descriptors differ. |
| **Method hiding** | A `static` method in a subclass hides a `static` method with the same signature in a parent. | `static` methods do not participate in dynamic dispatch like instance overrides; bridges do not turn `static` hiding into overriding. |

Overload example:

~~~java
class Printer {
    void print(Object value) {
        System.out.println("Object");
    }
    void print(String value) {
        System.out.println("String");
    }
}
~~~

The choice between `print(Object)` and `print(String)` depends on the static type of the argument at compile time. This differs from what bridges solve: a bridge enables **an already established override** to continue participating in dynamic dispatch properly after erasure.

## 11. Inspecting Bridges with Reflection

The JDK provides:

~~~java
Method.isBridge()
Method.isSynthetic()
Method.getParameterTypes()
Method.getReturnType()
Method.getDeclaredMethods()
~~~

Distinguishing check example:

~~~java
for (Method method : StringBox.class.getDeclaredMethods()) {
    if (method.isBridge()) {
        System.out.println(method.getName() + ": " + method.isSynthetic());
    }
}
~~~

The snippet above assumes `StringBox` is declared in the same scope. The order returned by `getDeclaredMethods()` **is not guaranteed by the API**, so if you need deterministic repeatable output, use `sorted()` by name or descriptor.

A `javac`-generated bridge method is normally also synthetic, but you should use `isBridge()` to accurately identify bridges rather than inferring from `isSynthetic()` alone. Reflection can observe compiler-generated methods that have no explicit declaration in source code, which is normal.

### When reflection yields multiple “same-named” methods

API-scanning tools may see multiple `get()`, `set(...)`, or `convert(...)` methods that appear to have duplicate names. Do not rush to conclude that the class defines redundant APIs. Check:

- `isBridge()` and `isSynthetic()`.
- Parameter list from `getParameterTypes()`.
- Return type from `getReturnType()`.
- Generic superclass/interface relationships and specialized overrides.

When generating API documentation, many tools choose to filter out or hide bridge methods from developer-facing API listings while keeping them in bytecode to ensure runtime behavior.

## 12. Common Mistakes and Misconceptions

### Misconception “erasure breaks polymorphism”

Type erasure can alter signatures in bytecode, but `javac` uses bridges to preserve valid override contracts established in source. Calls through a parent type still select the subclass implementation as expected.

### Misconception “StringBox is allowed to accept Integer because set accepts Object after erasure”

The source signature of `Box<String>.set` accepts `String`. When using a properly parameterized reference, the compiler blocks `Integer`. Wrongly typed arguments can only slip through via raw/unchecked paths or other unsafe access; a bridge may catch the error at runtime.

### Misconception “bridge = cast”

A bridge is a method that may contain `checkcast`, `invoke`, and `return`. By contrast, `checkcast` is a reference-checking instruction. A bridge returning `Object` from `get():String` usually does not need a `String` cast inside the bridge itself; the caller's cast is a separate matter.

### Misconception “every generic method generates a bridge”

A generic class does not automatically need bridges merely because it has `T`. Bridges appear when signatures/descriptors must be connected for an override relationship to work properly. If a subclass does not specialize an override or descriptors already match, no bridge may be generated.

### Misconception “bridges always return Object”

The descriptor must match the method on the superclass/interface side after erasure. If a type variable has bounds, the descriptor may use `Number`, `Serializable`, or another corresponding class/interface. Non-generic covariant return cases can also return a superclass other than `Object`.

### Misconception “bridge names and counts are part of the public API contract”

The exact shape of bridges depends on overriding methods, hierarchy, compiler, and target bytecode. You should not write business logic depending on the bridge count or bytecode offsets of a specific `javac` version. Inspecting those attributes is suitable only for learning, analysis, and specialized tooling.

## 13. When Do Bridge Methods Matter in Practice?

**When debugging `ClassCastException`:** if a stack trace involves a synthetic/bridge method or a raw generic call, check whether the runtime argument matches the subtype the subclass actually accepts. A raw `set(Object)` call may be cast to `String` by a bridge and fail.

**When using reflection or building frameworks:** bridges can appear as extra entries in `getDeclaredMethods()`. When scanning annotations, building routing, or registering handlers, distinguish user-written methods from forwarding bridge methods to avoid processing the same method twice. Exact annotation/bridge mapping rules also depend on the framework in use.

**When analyzing bytecode:** compare `javap -c -p` of the generic superclass and the specialized subclass, checking descriptors, `ACC_BRIDGE`/`ACC_SYNTHETIC`, `checkcast`, and forwarding invoke instructions.

**When designing generic classes:** write overrides with accurate types and add `@Override`. Do not interfere with compiler-generated bridges, and do not rely on assumptions that erasure lets the JVM guess generic types at runtime.

**When assessing binary compatibility:** bridges are one mechanism helping class files and callers compiled against erased descriptors remain compatible. However, changing public APIs, generic bounds, or inheritance relationships can still introduce compatibility breakages; bridges do not guarantee that every library change is safe.

## 14. Self-Check Questions

**1.** Why does `StringBox.set(String)` need a bridge matching `set(Object)`?

**Answer:** After erasure, `Box.set(T)`'s signature is `set(Object)`. The bridge has that descriptor so dynamic dispatch through `Box` still reaches the `set(String)` override.

**2.** When a raw `Box` reference calls `set(123)` on `StringBox`, why can it throw `ClassCastException` before entering `set(String)`?

**Answer:** The `set(Object)` bridge checks the argument using `checkcast String` before forwarding. `Integer` is incompatible with `String`, so the check fails.

**3.** Does a `get():Object` bridge have to cast to `String` inside the bridge?

**Answer:** No. It can call `get():String` and return that reference as `Object`. A caller using the erased result as `String` may perform its own `checkcast String`.

**4.** Is `method.isSynthetic()` sufficient to conclude a method is a bridge?

**Answer:** No. Synthetic covers members generated by the compiler for various reasons; you must check `isBridge()` to identify bridges.

**5.** Can bridge methods exist without using generics?

**Answer:** Yes, when an override uses a covariant return type, such as `Animal.copy():Animal` and `Dog.copy():Dog`.

**6.** If a generic type parameter has bound `T extends Number`, does the bridge accept `Object` or `Number`?

**Answer:** The erased signature of `T` uses `Number`, so the bridge for a specialized override accepts `Number` when needed.

**Key takeaway:** **A bridge method is a compiler-generated bytecode bridge ensuring that override relationships in Java source remain valid after erasure or covariant return-type changes.** When invoked through a superclass/interface, the JVM still dispatches the call to the subclass implementation; the bridge adapts the descriptor and performs necessary casts. Understanding bridges helps accurately explain polymorphism, unchecked calls, reflection, and cast errors in generic programs.
