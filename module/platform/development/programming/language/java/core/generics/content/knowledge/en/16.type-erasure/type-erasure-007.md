# Distinguishing Type Erasure from Generating Specialized Classes per Type Argument

When encountering `Box<String>`, `Box<Integer>`, `List<String>`, or `List<Integer>`, you can imagine two ways to implement generics:

- **Type erasure:** the compiler checks type arguments in source code and then compiles to code using erased types; different uses of the same generic class declaration typically share **the same runtime class**.
- **Generating specialized classes per type argument (specialization/monomorphization):** a compilation or execution system can generate a separate execution form for each concrete type combination, such as one specialized version for `String` and another for `Integer`. This is a contrasting model, **not the default behavior of standard Java generics**.

The key difference lies in **how concrete types affect executable code and data representation**. Java primarily uses erasure to implement generics in bytecode. Do not equate multiple generic types being checked differently in source code with the JVM having that many specialized classes.

## 1. One generic declaration, two implementation approaches

Suppose we define:

```java
// Snippet describing the declaration; the complete runnable program is in section 6.
class Box<T> {
    private final T value;

    Box(T value) {
        this.value = value;
    }

    T get() {
        return value;
    }
}
```

And use it:

```java
Box<String> greeting = new Box<>("Java");
Box<Integer> number = new Box<>(42);
```

At the **source level**, the compiler knows `greeting.get()` has type `String` and `number.get()` has type `Integer`. Hence, `String s = number.get();` is rejected at compile time. Yet that alone does not tell you how many class definitions the JVM stores.

### Approach A — type erasure as used by Java

Because `T` has no explicit upper bound, the erasure of `T` is `Object`. You can visualize the equivalent form at the descriptor layer as:

```java
// Pseudocode explaining erasure, not Java code to declare alongside.
class Box {
    private final Object value;

    Box(Object value) {
        this.value = value;
    }

    Object get() {
        return value;
    }
}
```

This is an **explanatory model**: `javac` actually generates bytecode, without emitting a new `Box.java` file as illustrated. There is one `Box` class definition used for both parameterizations, and the compiler can insert a `String` or `Integer` cast where the result is received.

```text
Java source:
  Box<String>         Box<Integer>
        \                  /
         \                /
          v              v
       same runtime class Box
        field value: Object
        method get(): Object
```

### Approach B — hypothetical type-based specialization

A system choosing specialization might produce two semantically equivalent versions:

```java
// Pseudocode: illustrating a specialization strategy.
// These are NOT two classes auto-generated by javac from Box<T>.
final class BoxForString {
    private final String value;
    BoxForString(String value) { this.value = value; }
    String get() { return value; }
}

final class BoxForInteger {
    private final Integer value;
    BoxForInteger(Integer value) { this.value = value; }
    Integer get() { return value; }
}
```

Under this hypothesis, using `Box<String>` and `Box<Integer>` has two distinct execution forms, potentially with different field reads, signatures, and optimizations. However, **specialization does not always necessarily mean creating separate `.class` files or separately named classes**; depending on language design, the runtime can generate specialized code forms or reuse parts of executable code. The example above deliberately picks "separate classes" to make the contrast clear.

## 2. Direct comparison table

| Aspect | Type erasure in standard Java generics | Model generating specialized forms per type argument |
| --- | --- | --- |
| After source-level type checking | Erases type parameters from regular descriptors, using bounds or `Object` | Can generate execution forms with concrete types |
| `Box<String>` and `Box<Integer>` | Same runtime class `Box` | Can map to two specialized forms |
| Field type `T value` | `Object` when `T` is unbounded | Can use `String` and `Integer` in each form |
| Return type `T get()` | Descriptor returns `Object`; call sites may need a cast | Can have corresponding concrete signatures/execution paths |
| Amount of code generated | Does not multiply class count for every parameterization | Can grow with the number of specialized cases |
| Does runtime know the type argument? | No concrete type argument attached directly to each ordinary generic instance | Design-dependent; code specialization and type reflection are distinct traits |
| Primitive types in Java | `List<int>` is invalid; uses `List<Integer>` with boxing/unboxing | A specialized design may support primitive values directly if the language permits |
| Legacy Java library compatibility | Erasure was chosen to support introducing generics into the legacy bytecode ecosystem | Needs a separate compatibility strategy; does not automatically preserve old descriptors |
| Runtime cost | One common class form; casts, boxing, and dispatch have context-dependent costs | May reduce some overhead, at the risk of larger code size and cache pressure |
| Source-code type safety | Compiler checks generics | Compiler can also check generics; execution strategy alone does not determine safety |

Note: the second column describes **Java's current generic design**, whereas the third column is a **hypothetical implementation model** used to separate concepts. Do not use this table to conclude that every language with specialization generates one class copy for every type argument.

## 3. How exactly does Java erase types?

Before comparing the two strategies, identify precisely **which parts of Java undergo erasure**:

| Source-level form | Type typically used in JVM descriptor | Creates a new class per `T`? |
| --- | --- | --- |
| Unbounded `T` | `Object` | No |
| `T extends Number` | `Number` | No |
| `T extends Number & Comparable<T>` | `Number` (first bound) | No |
| `List<String>` | `List` | No |
| `T[]` | Array of the erasure of `T` | No |
| `List<T>` in method parameter | `List` | No |

The compiler checks generic relationships **before** erasure, can insert `checkcast` when callers read data, and generates **bridge methods** when needed to preserve overriding. Those mechanisms do not equate to specialization: bridges handle linkage/dispatch, casts check values at usage sites; neither turns `Box<Integer>` into a primitive `Box<int>`.

Separate lessons on **type variable bounds**, **method/array descriptors**, and **`checkcast`** already described each rule. Here they are brought together to evaluate the difference between a **shared** generic binary and specialized implementations.

## 4. Why did Java choose erasure instead of one class per type argument?

When Java 5 added generics, `List`, `Collection`, and many legacy libraries already existed. **Migration compatibility** was a major reason for choosing erasure: generified APIs often keep the **same erased JVM method descriptors**, allowing compiled classes and legacy source code to transition gradually to generic forms.

```java
// Model comparing two source versions of an API:
void accept(java.util.List values) {}          // Legacy raw-typed API
// void accept(java.util.List<String> values) {} // Generified form
```

These two signatures **cannot coexist as overloads** in one class because they share the same erasure; they illustrate the choice between two API declarations. Erasure does not guarantee every source/binary change is completely compatible: inheritance, overloads, generic `Signature`, bridges, runtime class-file versions, and API semantics must still be checked. The trade-off with specialization is **the number of artifacts/code versions** and the ability to optimize per representation.

## 5. Same runtime class does not mean two generic types are mutually assignable

Java treats `Box<String>` and `Box<Integer>` as two **statically distinct** parameterizations. Erasure is an implementation mechanism; it does not erase `javac`'s assignment rules.

```java
// Illustrative snippet, not a standalone program:
List<String> names = new java.util.ArrayList<>();
List<Integer> ids = new java.util.ArrayList<>();

// names = ids;             // Does not compile
// List<Object> all = names; // Also does not compile
```

Standard generics in Java are **invariant**: `List<String>` is not a subtype of `List<Object>` even though `String` is a subtype of `Object`. You can use wildcard `List<? extends Object>` when you only need to read objects at the `Object` level, or `List<? super String>` when an API needs to accept `String` elements in the appropriate direction.

The two `new ArrayList<>()` lines above have the same runtime class **because both chose the `ArrayList` implementation**. However, an `ArrayList<String>` and a `LinkedList<String>` have different runtime classes because the **collection implementations themselves differ**, unrelated to having equal type arguments.

## 6. Java 17+ program demonstrating the difference

Save the following code in **`ErasureVsSpecializationDemo.java`**:

```java
import java.lang.reflect.Method;
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

public class ErasureVsSpecializationDemo {
    static final class Box<T> {
        private final T value;

        Box(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

    static final class NumberBox<N extends Number> {
        private final N value;

        NumberBox(N value) {
            this.value = value;
        }

        N get() {
            return value;
        }
    }

    static class Holder<T> {
        private T value;

        void set(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

    static final class StringHolder extends Holder<String> {
        @Override
        void set(String value) {
            super.set(value);
        }
    }

    static final class Counter<T> {
        static int created;

        Counter() {
            created++;
        }
    }

    public static void main(String[] args) throws NoSuchMethodException {
        Box<String> stringBox = new Box<>("Java");
        Box<Integer> integerBox = new Box<>(42);
        List<String> texts = new ArrayList<>();
        List<Integer> ids = new ArrayList<>();

        System.out.println("Box<String> va Box<Integer> cung class: "
                + (stringBox.getClass() == integerBox.getClass()));
        System.out.println("ArrayList<String> va ArrayList<Integer> cung class: "
                + (texts.getClass() == ids.getClass()));

        Method boxGet = Box.class.getDeclaredMethod("get");
        System.out.println("Kieu tra ve da xoa cua Box.get: "
                + boxGet.getReturnType().getSimpleName());
        System.out.println("Kieu tra ve generic cua Box.get: "
                + boxGet.getGenericReturnType().getTypeName());
        System.out.println("Kieu tra ve da xoa cua NumberBox.get: "
                + NumberBox.class.getDeclaredMethod("get").getReturnType()
                    .getSimpleName());

        String text = stringBox.get();
        System.out.println("Gia tri String: " + text);

        Holder<String> holder = new StringHolder();
        holder.set("bridge");
        System.out.println("Gia tri qua Holder<String>: " + holder.get());
        System.out.println("StringHolder co bridge: "
                + Arrays.stream(StringHolder.class.getDeclaredMethods())
                    .anyMatch(Method::isBridge));

        new Counter<String>();
        new Counter<Integer>();
        System.out.println("Counter.created dung chung: " + Counter.created);
    }
}
```

Compile and run:

```bash
javac -encoding UTF-8 ErasureVsSpecializationDemo.java
java ErasureVsSpecializationDemo
```

Output:

```text
Box<String> va Box<Integer> cung class: true
ArrayList<String> va ArrayList<Integer> cung class: true
Kieu tra ve da xoa cua Box.get: Object
Kieu tra ve generic cua Box.get: T
Kieu tra ve da xoa cua NumberBox.get: Number
Gia tri String: Java
Gia tri qua Holder<String>: bridge
StringHolder co bridge: true
Counter.created dung chung: 2
```

These results were verified by running equivalent classes and methods in the JDK with Java 17-compatible syntax. Point-by-point explanation:

1. **Both `Box` instances share the same class:** `getClass()` compares two `Class` objects representing the same runtime declaration `Box`. If Java generated a separate class per `T`, this comparison would not reflect a shared model like this.
2. **Both `ArrayList` instances share the same class:** the `String`/`Integer` difference is source-level type information; `ArrayList` itself is shared.
3. **`Box.get` returns `Object` in normal reflection:** the method descriptor is the erased form of unbounded `T`. `getGenericReturnType()` reads metadata showing the original declaration has type variable `T`. It does **not** return `String` specifically for the `stringBox` variable.
4. **`NumberBox.get` returns `Number`:** the bound `N extends Number` determines erasure, showing "type erasure" does not always mean replacing everything with `Object`.
5. **Reading `String` remains safe in source code:** the compiler already checked `Box<String>`; if a cast is needed, it occurs at the appropriate site. This is not a separate `BoxForString` class.
6. **Bridge methods are real:** `StringHolder` is an **explicitly programmer-declared subclass**; the bridge preserves overriding after erasure of `Holder<T>`. The `isBridge()` flag does not prove specialization by type parameter.
7. **Static variables are shared:** `Counter<String>` and `Counter<Integer>` share a single `Counter.created` field, so after two instantiations the value is 2. Within a single class loaded by the same class loader, each type-argument parameterization does not create a separate set of static fields.

To inspect deeper, after compiling run:

```bash
javap -p -s 'ErasureVsSpecializationDemo$Box'
javap -p -s 'ErasureVsSpecializationDemo$NumberBox'
javap -p -v 'ErasureVsSpecializationDemo$StringHolder'
```

These commands inspect `Object`/`Number` descriptors, `Signature` metadata, and bridge methods in bytecode. Nested class names contain `$`; use quotes so the shell does not expand this character unexpectedly. Different `javap` versions may format auxiliary attributes slightly differently, yet the meaning of descriptors and bridges is the same.

## 7. Does "one shared class" really retain no generic information at all?

No. A shared generic binary can still contain a `Signature` attribute describing the **declaration**: type parameters, bounds, generic superclasses, fields, and methods. Reflection calls such as `Box.class.getTypeParameters()` can read the name `T`; a subclass declaring `extends Box<String>` can store the `String` argument on its **superclass type**.

What it does not automatically have is **each `new Box<T>()` instance's individual actual type argument**. `getClass()` returns the shared runtime class; if type verification is needed across an API boundary, intentionally accept a `Class<T>` token or other metadata. The final lesson in this chapter on `Signature` illustrates descriptors, field/method metadata, and `TypeVariable`/`ParameterizedType` in full.

## 8. Erasure, specialization, and reification are three related but distinct concepts

**Erasure** refers to how generic declarations are represented/compiled: type parameters are replaced by erased types in regular descriptors and code is shared. **Specialization** refers to the ability to generate distinct execution forms for type combinations. **Reification** refers to the extent to which type information is present so the runtime can observe or check it.

For example:

- Java arrays such as `String[]` have a runtime component type, so `Object[] array = new String[1]; array[0] = 123;` throws `ArrayStoreException` at runtime (assuming it is placed in a valid Java block). The array's component type carries the needed runtime information.
- `List<String>` is **not a reifiable type** for checking via `instanceof List<String>`. You can check `instanceof List<?>` because the wildcard does not force the JVM to verify element types.
- A system can store type arguments at runtime without necessarily creating full copies of every piece of generic code. Conversely, generating specialized code can serve optimization without automatically promising a full reflection API for all type arguments.

Therefore, do not define specialization simply as "the runtime knows generics" or erasure simply as "the runtime no longer distinguishes `String` from `Integer`". Ask precisely: **what does the runtime distinguish, on which class/object, and via which mechanism?**

## 9. Readily visible consequences of erasure in Java

From having a shared generic binary, common limitations include:

- Cannot overload solely on `List<String>` vs. `List<Integer>` because erased method descriptors collide.
- Cannot use `instanceof List<String>` to check all elements at runtime; `List<?>` only checks the class.
- Cannot directly write `new T()`, `T.class`, or `new T[n]` for a non-reifiable type variable.
- Raw/unchecked APIs can create heap pollution, causing a cast at another call site to fail.
- Standard Java reference generics do not accept `List<int>`; `List<Integer>` is not synonymous with a primitive representation.

These limitations **do not prove** specialization is always better: it can improve certain primitive paths while also increasing code size or complexity. Compare by representation goals and workload metrics, not merely by mechanism names. For custom code needing a primitive field, you can define `IntBox` explicitly; that is **manual API design**, not automatic generic specialization.

## 10. Memory and performance costs: why no single strategy always wins

There are two different kinds of cost:

**Number of code versions:** if separate executions are generated for many type combinations (`Box<Customer>`, `Box<Order>`, `Box<Product>`, etc.), code size can grow. Many code copies can increase compilation or loading time, consume more code memory, and affect instruction caches. Erasure produces fewer class variants, which generally favors library reuse.

**Data representation and operations:** a generic form holding `Object` may require casts; when generics take wrappers for primitives, boxing/unboxing and allocations can affect performance. Specialized forms for suitable data can reduce those costs, improve locality, and optimize directly per type.

However, **do not conclude** "erasure is always faster because there are fewer classes" or "specialization is always faster because it removes casts". The HotSpot JVM has JIT compilation, profiling, inlining, escape analysis, and other optimizations. It can generate efficient machine code paths for the actual runtime types being executed without **creating a new Java class `BoxForString` for every type argument**. Many casts are also very cheap or optimized away.

For example, `String` and `Integer` inside two `Box` instances do not force the `Object` field to hold an "erased string" or "erased integer"; it holds references to real objects. Valid benchmarking must control warm-up, JIT, allocation, and workload type using tools like JMH; runtime speed cannot be predicted solely from the generics mechanism.

## 11. Can you manually create separate classes per type in Java?

Yes, though that is an **API programming decision**, not automatic specialization of `Box<T>`:

```java
// Snippet designing two separate classes; independent of Box<T>'s erasure mechanism.
final class StringBox {
    private final String value;
    StringBox(String value) { this.value = value; }
    String get() { return value; }
}

final class IntBox {
    private final int value;
    IntBox(int value) { this.value = value; }
    int get() { return value; }
}
```

These two classes have two real runtime classes. `IntBox` holds an `int` field rather than needing `Integer`; this is specialization **hand-written by the programmer**. If many types are needed, substantial code duplication can arise. This is also why Java's standard library provides primitive-specialized APIs in certain cases, such as `IntStream`, `LongStream`, and `DoubleStream` alongside `Stream<T>`.

Distinguish clearly:

- `Box<String>` and `Box<Integer>` using the same `Box<T>` declaration: **one erased generic class**.
- Hand-declared `StringBox` and `IntBox`: **two distinct classes** whose field types can differ.
- `StringHolder extends Holder<String>`: **a real programmer-written subclass**, yet `Holder<T>` is still not multiplied into separate `Holder<String>` and `Holder<Integer>` classes.
- Machine code optimized by the JIT per runtime type: there may be **specialized machine code for hot execution paths**, yet that does not mean the JVM introduces a new Java generic class for each `T`.

Do not treat the existence of a dedicated subclass or specialized JIT machine code as evidence that the Java compiler switched from erasure to monomorphization of the original generic declaration.

## 12. Thought exercises: choose the accurate statement

**Scenario A.** Two variables `List<String>` and `List<Integer>` are initialized with `new ArrayList<>()`. What can be concluded?

You can conclude both runtime classes are `ArrayList`. You cannot conclude they are mutually assignable; the compiler still knows the type arguments differ in source code.

**Scenario B.** An object of `class Data<T extends Number>` has `T data;`. After erasure, what is the field's typical descriptor type?

It is `Number`, not `Object`, and it does not automatically become `Integer` merely because `Data<Integer>` was written somewhere.

**Scenario C.** Reflection returns `T` when calling `getGenericReturnType()`. Is the runtime storing `T = String` for each individual instance?

No. Reflection is reading the **generic declaration**; an ordinary `Box<String>` object has no separate runtime class carrying `String` as a parameter of that class itself.

**Scenario D.** A bridge method `set(Object)` appears in the subclass `StringHolder`. Does that prove the compiler created a specialization for `Holder<String>`?

No. The bridge is generated to **preserve overriding** when a generic method undergoes type erasure.

**Scenario E.** A compiler chooses to emit separate machine code for `int` and `double`. Does that mean it necessarily creates two Java classes visible via `Class`?

Not necessarily. Specialized executable code, runtime class structure, and reflection capabilities can be designed independently to certain degrees.

## 13. Checklist when analyzing a generic API

When you want to know whether a piece of Java code uses erasure or dedicated classes, check in order:

1. **What is the original declaration?** `class Box<T>`, or two actually defined classes `StringBox` and `IntBox`?
2. **What is the type parameter's bound?** Unbounded `T` erases to `Object`; `T extends Number` erases to `Number`.
3. **Do type arguments create separate classes?** Do not guess from `<String>` syntax. Use `getClass()` to observe the runtime classes of objects sharing a generic class.
4. **Are there casts or bridges?** These are usually signs of mechanisms preserving type safety/polymorphism under erasure, not class specialization.
5. **What runtime metadata exists?** `getReturnType()` shows the erased type; `getGenericReturnType()` reflects the generic declaration if metadata is present.
6. **Where is the real bottleneck?** Check boxing, allocation, data layout, and benchmark results before hand-writing specialized classes.

**Core conclusion:** in standard Java generics, `Box<String>` and `Box<Integer>` are two usages with **different static types** sharing the **same runtime class declaration `Box`**. Type erasure achieves this by removing type parameters from descriptors, inserting casts, and generating bridges when needed. Creating separate classes or executable code per type argument is a different specialization strategy with its own optimization opportunities and costs; Java does not automatically perform "one class per `T`" just because you use generic syntax.
