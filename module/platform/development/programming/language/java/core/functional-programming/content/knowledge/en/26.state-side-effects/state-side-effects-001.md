# Stream Non-Interference Requirement

## 1. The Problem: Why Shouldn't You Modify the Source in a Stream Pipeline?

The Java Stream API lets you describe data processing in steps such as `filter`, `map`, `sorted` and finish with `toList`, `collect`, `sum`, or `forEach`. A Stream usually **does not own an independent copy of the source data**. When creating a stream from an `ArrayList`, an array, or another collection, the pipeline remains attached to that source until it is consumed.

Valid example:

~~~java
List<String> names = new ArrayList<>(
        List.of("An", "Binh", "Chi"));

List<String> longNames = names.stream()
        .filter(s -> s.length() >= 4)
        .map(String::toUpperCase)
        .toList();

System.out.println(names);     // [An, Binh, Chi]
System.out.println(longNames); // [BINH]
~~~

`filter` and `map` produce processed results through the pipeline; they do not add, remove, or replace elements in the `names` list themselves. However, what happens if a callback **actively modifies the `names` list while that same list is being traversed**?

~~~java
// WRONG by design; do not run as a safe example.
List<String> names = new ArrayList<>(List.of("An", "Binh", "Chi"));

names.stream()
        .forEach(name -> {
            if (name.equals("An")) {
                names.add("Dung"); // Modifies the source being traversed by the Stream.
            }
        });
~~~

This is **interference** with the source. It violates the requirement for proper Stream usage with a source that does not support concurrent modification. The program may throw `ConcurrentModificationException`, observe abnormal results, or exhibit behavior not guaranteed by the Stream contract. You cannot use "it works on my machine" as proof that the code above is correct.

**Core rule:** for a Stream source not designed for concurrent modification, the behavioral parameters passed to Stream operations must **not modify the source while the pipeline is executing** (*non-interfering*).

## 2. What Does Non-Interference Mean?

In the context of Java Streams, a behavioral parameter such as a predicate, mapper, or action is called **non-interfering** if it **does not modify the data source** that the pipeline is traversing, unless the source explicitly supports concurrent modification by contract.

Some examples:

| Behavior in the pipeline | Interferes with source? | Explanation |
| --- | --- | --- |
| `filter(s -> !s.isBlank())` | No | Only reads the element and decides whether to keep or discard it |
| `map(String::trim)` | No | Creates a new representation value; does not modify the source List |
| `map(s -> s.toUpperCase(Locale.ROOT))` | No | Creates a new result value |
| `filter(s -> { source.remove(s); return true; })` | **Yes** | Removes an element from the source being traversed |
| `peek(s -> source.add("X"))` | **Yes** | Adds to the source right inside the pipeline |
| `forEach(s -> source.clear())` | **Yes** | Clears the source contents while the terminal operation is consuming |
| `map(s -> { source.set(0, "X"); return s; })` | **Yes** | Writes to the source structure, even though the size does not change |
| `map(s -> { externalCounter++; return s; })` | Not necessarily source interference, but **has a stateful side effect** | Violates stateless/thread-safe expectations if relying on the counter |

It is necessary to distinguish two related but **not identical** principles:

1. **Non-interference:** do not modify the Stream's **source** while the pipeline is being traversed.
2. **Stateless behavioral parameters:** the callback's behavior does not depend on state that may change during pipeline execution (especially state updated by other callbacks).

A lambda that logs without modifying the source may not violate non-interference, but side effects still carry other risks regarding ordering, execution count, optimization, and thread-safety. Conversely, a lambda that removes an element from the source violates non-interference even when running sequentially without multiple threads.

This principle applies to callbacks of both intermediate operations and terminal operations. The fact that `forEach` is a terminal operation does not by itself allow it to modify the source being traversed.

## 3. What Is a Stream's Source and When Is It Read?

The source can be:

- A `Collection`, for example `ArrayList`, `HashSet`, `TreeSet`.
- An object array or primitive array via `Arrays.stream`.
- A sequence generated by `IntStream.range`, `Stream.iterate`, `Stream.generate`.
- A `Spliterator` or an I/O source converted into a Stream via the corresponding API.

For Streams based on collections or arrays, calling `stream()` usually only **sets up the source description**, while actual traversal happens when the terminal operation requests the result.

~~~java
List<Integer> source = new ArrayList<>(List.of(1, 2, 3));

Stream<Integer> pipeline = source.stream()
        .map(n -> n * 10);

// No terminal operation here yet.
List<Integer> result = pipeline.toList();
System.out.println(result); // [10, 20, 30]
~~~

This leads to an important distinction:

- **Modifying the source before the pipeline starts executing:** some sources are *late-binding*, so they may reflect that change. However, you must understand the contract of the source/Spliterator and not assume every case behaves the same.
- **Modifying the source while the pipeline is executing:** for a non-concurrent source, this is prohibited by the non-interference requirement.

You should not rely on the timing "after `stream()` but before `toList()`" as a deliberate technique to mutate the source; instead, **finish transforming the data first**, then create and consume the pipeline. This approach is easier to read, safer, and does not depend on the late-binding details of each source.

## 4. Classic Mistake: Modifying an `ArrayList` in `forEach`

Counterexample:

~~~java
List<Integer> numbers = new ArrayList<>(List.of(1, 2, 3, 4));

// Do not do this:
// numbers.stream().forEach(n -> {
//     if (n % 2 == 0) {
//         numbers.remove(n);
//     }
// });
~~~

It is easy to mistakenly assume that because there is only one thread, a "concurrent" error cannot occur. However, `ConcurrentModificationException` does not appear only in multithreading: a **fail-fast** Iterator or Spliterator can detect that the very thread traversing the collection modified its structure outside the permitted mechanism.

**Nor is there any guarantee that the error will always be detected.** Fail-fast is a best-effort detection mechanism, not a mechanism for proving code correctness. An incorrect pipeline might not throw an exception in one run yet still violate the contract.

### 4.1. The Right Way When You Only Need to Filter: Create a Result Collection

~~~java
List<Integer> numbers = List.of(1, 2, 3, 4);

List<Integer> odds = numbers.stream()
        .filter(n -> n % 2 != 0)
        .toList();

System.out.println(numbers); // [1, 2, 3, 4]
System.out.println(odds);    // [1, 3]
~~~

`filter` only determines the output elements; it does not modify the source. In Java 17, `Stream.toList()` returns an **unmodifiable** List; if you need to modify the result, create an `ArrayList` from it:

~~~java
List<Integer> mutableOdds = new ArrayList<>(
        numbers.stream()
                .filter(n -> n % 2 != 0)
                .toList());

mutableOdds.add(5); // Valid: modifies the new result collection.
~~~

### 4.2. The Right Way When You Need to Modify the Original Collection: Operate Outside the Stream

If the actual goal is to remove even numbers from a mutable list, use `removeIf` **outside an active Stream traversal**:

~~~java
List<Integer> numbers = new ArrayList<>(List.of(1, 2, 3, 4));

numbers.removeIf(n -> n % 2 == 0);

System.out.println(numbers); // [1, 3]
~~~

`removeIf` is designed to handle removing elements from a collection based on a predicate. Do not place `removeIf` on the same collection inside a callback of `source.stream()`.

Similarly, `List.replaceAll` and `List.sort` are appropriate APIs when you **want to transform a List in place**; call them in a separate phase, not overlapping with a Stream traversing that list.

## 5. Changing Size Is Not the Only Form of Interference

Many people only worry about `add`/`remove` changing `size()`, but **overwriting existing elements** in the source is also not the right way to build a Stream:

~~~java
List<String> data = new ArrayList<>(List.of("A", "B", "C"));

// WRONG: still modifies the source even though the size remains the same.
// data.stream().map(s -> {
//     data.set(0, "X");
//     return s;
// }).toList();
~~~

A collection might not treat `set` as a *structural modification*, so the fail-fast mechanism does not report an error, but that **does not make modifying the source inside a callback valid**. A predicate/mapper may read a value that was altered in an unguaranteed way or produce unpredictable results.

For arrays:

~~~java
String[] array = {"A", "B", "C"};

// Also avoid:
// Arrays.stream(array).map(s -> {
//     array[1] = "changed";
//     return s;
// }).toList();
~~~

Arrays do not have a `modCount` or fail-fast behavior like `ArrayList`, yet modifying the source array while traversing it is still interference. Not throwing `ConcurrentModificationException` **does not** prove safety.

If you want to transform values, let the mapper produce the output values:

~~~java
String[] array = {"A", "B", "C"};

List<String> lower = Arrays.stream(array)
        .map(s -> s.toLowerCase(Locale.ROOT))
        .toList();

System.out.println(Arrays.toString(array)); // [A, B, C]
System.out.println(lower);                   // [a, b, c]
~~~

## 6. Mutating Element Object State: Distinguishing Two Data Layers

Suppose the source is `List<User>`, where each `User` is a mutable object:

~~~java
class User {
    String name;
    User(String name) { this.name = name; }
}

List<User> users = new ArrayList<>(List.of(
        new User("An"), new User("Binh")));
~~~

Operations like `users.remove(...)` or `users.add(...)` change the structure of the source List. Meanwhile, `user.name = ...` changes the **state of the element object**, without necessarily changing the List structure.

However, that **does not mean mutating inside a mapper is always a safe design**:

~~~java
// Using Stream to mutate User is discouraged:
// users.stream().forEach(user -> user.name = user.name.toUpperCase());
~~~

Depending on how the data is used, mutating element state can affect other callbacks, filtering/sorting criteria, or data on other threads. It makes behavior harder to reason about, especially with parallel streams. In cases where an element is also part of a source or classification structure (for example, mutating a field used as a key in a `HashSet`), mutation can break the collection's invariant even without calling `add`/`remove`.

**A design that is easier to verify:** transform into new objects or immutable DTOs:

~~~java
record UserView(String name) {}

List<UserView> views = users.stream()
        .map(user -> new UserView(
                user.name.toUpperCase(Locale.ROOT)))
        .toList();
~~~

New values are created without modifying the original `User`. For data with complex relationships, you must distinguish between shallow copy and deep copy; creating a new List does not automatically deep-copy all objects inside it.

## 7. Snapshotting Before Traversal and Copy Limitations

If a collection may be modified between stages of an application and you want to process a fixed version, you can create a **snapshot before starting the Stream**:

~~~java
List<String> source = new ArrayList<>(List.of("A", "B"));

List<String> snapshot = new ArrayList<>(source);
source.set(0, "X");

List<String> upper = snapshot.stream()
        .map(String::toUpperCase)
        .toList();

System.out.println(upper); // [A, B]
System.out.println(source); // [X, B]
~~~

Here `snapshot` contains the elements as of the time of copying; replacing an index in `source` afterward does not affect the snapshot list. However, there are two limitations:

1. `new ArrayList<>(source)` creates a **shallow copy**. If the elements are mutable objects, the snapshot may still reference the same objects, so internal state changes on those objects will be observed through both Lists.
2. If another thread is modifying an `ArrayList` while the snapshot is being created, the copy operation by itself **does not automatically create a synchronization-consistent snapshot**. You must coordinate synchronization or choose an appropriate data source design.

`List.copyOf(source)` creates an unmodifiable List and rejects `null` elements, yet it is still not a deep copy. Choosing `copyOf`, `new ArrayList<>(...)`, or an immutable model must be based on the data contract, especially regarding nulls and element mutability.

### 7.1. A Copy and a Stream Result Are Not the Same Concept

~~~java
List<String> source = new ArrayList<>(List.of(" a ", " b "));

List<String> result = source.stream()
        .map(String::trim)
        .toList();
~~~

`result` is a List created by the terminal operation, not the source List modified in place. It holds the mapper results, while `source` retains the strings with whitespace. `Stream.toList()` creates an unmodifiable List; that **does not mean** the List's elements have been deep-copied.

## 8. Parallel Streams: Additional Shared-State Issues

When calling `parallel()` or `parallelStream()`, callbacks may execute on multiple threads. If you modify the source inside a callback, you both violate non-interference and risk creating a **data race** or corrupting the data structure.

~~~java
List<Integer> source = new ArrayList<>(
        IntStream.rangeClosed(1, 1_000).boxed().toList());

// NEVER USE THIS APPROACH:
// source.parallelStream().forEach(n -> source.remove(n));
~~~

Even modifying a **different collection** from a callback can cause errors when that collection is not thread-safe:

~~~java
List<Integer> shared = new ArrayList<>();

// Wrong with parallel stream because ArrayList is not safe for concurrent add:
// IntStream.range(0, 1_000).parallel().forEach(shared::add);
~~~

The second example does not necessarily modify the Stream's **source** (the source is the number sequence from `IntStream.range`), but it is a **side effect using shared state** and can lose elements, cause races, or corrupt the result. Therefore, you must distinguish:

- **Non-interference:** do not modify the source.
- **Statelessness / side-effect safety:** callbacks do not depend on or update unsynchronized shared mutable state.

A better approach when collecting numbers from a parallel stream:

~~~java
List<Integer> values = IntStream.range(0, 1_000)
        .parallel()
        .boxed()
        .toList();

System.out.println(values.size()); // 1000
~~~

A Collector or terminal operation designed by the Stream API to collect results manages splitting and merging data according to its contract. For a source with encounter order like `IntStream.range`, the `toList` result preserves encounter order even though processing may run in parallel.

Do not conclude that "having `synchronizedList` makes modifying the source inside a Stream permissible." Synchronizing a List does not turn mutations occurring inside a callback into non-interfering operations with respect to the source being traversed.

## 9. Exception: Sources Designed for Concurrent Access/Modification

The Java Stream documentation recognizes one conditional exception: a source whose Spliterator has the **`CONCURRENT`** characteristic is designed to support concurrent modification during traversal. Typical examples are suitable concurrent collections, such as data obtained from `ConcurrentHashMap`.

~~~java
ConcurrentHashMap<String, Integer> scores =
        new ConcurrentHashMap<>();
scores.put("A", 1);
scores.put("B", 2);

List<String> keys = scores.keySet().stream()
        .sorted()
        .toList();

System.out.println(keys); // [A, B]
~~~

In the example above there is no concurrent mutation: `sorted` is used to produce stable output. The goal is to recognize the source type. With collections that support concurrent traversal, an iterator/spliterator may be **weakly consistent**: it does not necessarily throw `ConcurrentModificationException` and does not promise a complete, immutable snapshot at the moment of traversal.

**Do not infer that every kind of Map or every kind of Stream accepts concurrent mutation.** You must read the contract of the specific collection/spliterator: some sources have `IMMUTABLE`, some have `CONCURRENT`, and some have fail-fast mechanisms; each has different semantics.

If you require statistics that are **consistent at a single point in time**, simply using a concurrent collection is not enough; you need a snapshot, locking, or an appropriate consistency design. The fact that a source allows concurrent modification and traversal does not mean an aggregate operation will observe an exact instantaneous snapshot.

### 9.1. `CopyOnWriteArrayList` Differs from `ConcurrentHashMap`

`CopyOnWriteArrayList` uses a mechanism that copies its backing array upon mutation, while traversal can rely on a snapshot of the array. It does not share the same visibility contract as `ConcurrentHashMap`. Therefore, even though both are designed for multithreaded usage models, **do not lump them together into a single rule that "concurrent means seeing every change instantaneously."**

The core takeaway remains: when writing general-purpose Stream pipelines, **keep the source stable during traversal** unless a deliberate concurrent design truly requires otherwise and you clearly understand the source's contract.

## 10. Side Effects, `peek`, `map`, and Pipeline Optimizations

A lambda might not modify the source yet still have side effects:

~~~java
AtomicInteger counter = new AtomicInteger();

long count = List.of("a", "b", "c").stream()
        .map(s -> {
            counter.incrementAndGet();
            return s.toUpperCase(Locale.ROOT);
        })
        .count();
~~~

Do not expect `counter.get() == 3`. When the source has a known size and `map` does not change the element count, some implementations can compute `count()` **without executing the mapper**. This is a valid optimization under the Stream contract. Therefore, placing a side effect that must definitely occur inside `map` or `peek` is a flawed design.

`peek` is often used for observation/debugging:

~~~java
List<String> result = List.of(" a ", " b ").stream()
        .peek(s -> System.out.println("raw=" + s))
        .map(String::trim)
        .toList();
~~~

In this example, `toList` needs the values so logs can be observed during traversal, but you should not rely on the execution count or order of `peek` in every pipeline, especially when short-circuiting, parallelism, or terminal optimizations are involved.

Recommendations:

- Use `map` to **create new values**.
- Use `filter` to **keep or discard elements in the result**, not to modify the source collection.
- Use `collect`, `toList`, or an appropriate terminal operation to **produce the result**.
- If you genuinely need a side-effect action executed as the primary goal, use a terminal operation like `forEach`/`forEachOrdered` on an **unmodified** source, along with evaluating the action's thread-safety. `forEachOrdered` relates to encounter order; it does not automatically make external mutations outside the source thread-safe.
- Do not base business-logic correctness on logs, counters, or side effects inside intermediate operations.

## 11. Common Confusions About Data Modification Ordering

| Situation | Assessment |
| --- | --- |
| Calling `list.removeIf(p)` before creating the stream | Reasonable if you want to modify the original List and there is no concurrent traversal |
| Calling `list.sort(c)` and then `list.stream()` | Reasonable; the data modification finishes before traversal |
| Calling `list.replaceAll(f)` after a terminal operation has completed | Reasonable if no other concurrent traversal is active |
| Calling `list.add(x)` directly inside `list.stream().forEach(...)` | Violates non-interference |
| Calling `list.clear()` inside `list.stream().map(...)` | Violates non-interference |
| Calling `list.set(i,x)` from a callback traversing the same List | Violates non-interference, even without incrementing `modCount` |
| Calling `array[i] = x` from a callback traversing the same array | Violates non-interference |
| Calling `otherList.add(x)` from a parallel Stream | Does not necessarily modify the source, but carries shared-data risk; use a collector |
| Creating `new ArrayList<>(list)` and traversing the copy | Usually suitable if the copy is created consistently before traversal |
| Traversing a source with a `CONCURRENT` spliterator per its contract | May support concurrent mutation; semantics must follow the specific source |

**Do not interpret the table as "a List can never be modified during the entire program lifecycle."** A mutable collection can be updated normally **before or after** a traversal. The critical constraint is **not modifying the source while the pipeline is using that source**.

## 12. Complete Java 17+ Program and Deterministic Stdout

Create the file **`StreamNonInterferenceDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.stream.Collectors;
import java.util.stream.IntStream;

public class StreamNonInterferenceDemo {
    record Person(String name, int age) {}
    record PersonView(String name, boolean adult) {}

    public static void main(String[] args) {
        List<String> source = new ArrayList<>(
                List.of(" an ", " ", " binh ", "chi "));

        List<String> normalized = source.stream()
                .map(String::trim)
                .filter(s -> !s.isBlank())
                .map(s -> s.toUpperCase(Locale.ROOT))
                .toList();

        System.out.println("source=" + source);
        System.out.println("normalized=" + normalized);

        List<Integer> numbers = List.of(1, 2, 3, 4);
        List<Integer> odd = numbers.stream()
                .filter(n -> n % 2 != 0)
                .toList();
        System.out.println("originalNumbers=" + numbers);
        System.out.println("odd=" + odd);

        List<Integer> mutable = new ArrayList<>(numbers);
        mutable.removeIf(n -> n % 2 == 0);
        System.out.println("removedOutsideStream=" + mutable);

        List<String> snapshot = new ArrayList<>(source);
        source.set(0, "changed");
        List<String> saved = snapshot.stream()
                .map(String::trim)
                .toList();
        System.out.println("snapshot=" + saved);
        System.out.println("modifiedSourceFirst=" + source.get(0));

        List<Person> people = List.of(
                new Person("An", 20),
                new Person("Binh", 17));
        List<PersonView> views = people.stream()
                .map(p -> new PersonView(
                        p.name().toUpperCase(Locale.ROOT),
                        p.age() >= 18))
                .toList();
        System.out.println("views=" + views);

        long parallelSum = IntStream.rangeClosed(1, 100)
                .parallel()
                .mapToLong(n -> n)
                .sum();
        System.out.println("parallelSum=" + parallelSum);

        List<Integer> generated = IntStream.range(0, 5)
                .parallel()
                .boxed()
                .toList();
        System.out.println("parallelList=" + generated);

        String[] letters = {"A", "B", "C"};
        List<String> lower = Arrays.stream(letters)
                .map(s -> s.toLowerCase(Locale.ROOT))
                .toList();
        System.out.println("arraySource=" + Arrays.toString(letters));
        System.out.println("arrayResult=" + lower);

        ConcurrentHashMap<String, Integer> scores =
                new ConcurrentHashMap<>();
        scores.put("B", 2);
        scores.put("A", 1);
        System.out.println("concurrentKeys=" + scores.keySet().stream()
                .sorted()
                .toList());
    }
}
~~~

Compile and run with JDK 17 or later:

~~~bash
javac StreamNonInterferenceDemo.java
java StreamNonInterferenceDemo
~~~

Stdout:

~~~text
source=[ an ,  ,  binh , chi ]
normalized=[AN, BINH, CHI]
originalNumbers=[1, 2, 3, 4]
odd=[1, 3]
removedOutsideStream=[1, 3]
snapshot=[an, , binh, chi]
modifiedSourceFirst=changed
views=[PersonView[name=AN, adult=true], PersonView[name=BINH, adult=false]]
parallelSum=5050
parallelList=[0, 1, 2, 3, 4]
arraySource=[A, B, C]
arrayResult=[a, b, c]
concurrentKeys=[A, B]
~~~

Explanation of the parts:

1. The `map`/`filter` pipeline creates `normalized` without modifying `source`; the whitespace in the source strings remains intact.
2. `odd` is a new list containing the retained elements, while `numbers` is unchanged.
3. `removeIf` modifies `mutable` in an independent operation, **not** inside a traversal of the same collection.
4. The snapshot is created before `source.set`, so `saved` is still based on the old data; modifying the source after copying does not alter the snapshot List (with immutable `String`s).
5. `map` creates new `PersonView` instances instead of modifying the source data.
6. The parallel stream performs associative addition into the `sum` terminal operation instead of writing to a shared mutable counter.
7. `parallel().boxed().toList()` preserves the encounter order of `IntStream.range` in the result.
8. Transforming from the array creates a new List without writing to `letters`.
9. `ConcurrentHashMap` is demonstrated as a source type with its own concurrent semantics; here it is not modified during traversal. `sorted` guarantees output order when printing keys.

The program **deliberately does not execute** invalid snippets that might throw `ConcurrentModificationException` or cause races. Instead, the example shows correct behavior and directly comparable output.

## 13. Common Mistakes and How to Fix Them

| Mistake | Problem | Solution |
| --- | --- | --- |
| Modifying `ArrayList` in `stream().forEach` | Violates non-interference, may throw CME | Use `removeIf` outside traversal or create a result collection |
| Modifying elements with `set` in `map` | Modifies the source even though size does not change | Return new values with `map` |
| Modifying array elements while `Arrays.stream` traverses | Array source is mutated | Transform into a new result List/array |
| Relying on `ConcurrentModificationException` to catch every bug | Fail-fast is best-effort, not a guarantee | Design non-interfering pipelines |
| Assuming sequential streams are safe when modifying the source | A single thread can still cause interference | Do not modify the source inside callbacks |
| Assuming `Collections.synchronizedList` allows source modification during traversal | Synchronizing an API does not change the Stream contract | Separate mutation and traversal or design dedicated synchronization |
| `parallelStream().forEach(sharedArrayList::add)` | Side effect on a non-thread-safe List | `collect`/`toList` |
| Thinking `peek` always runs on every element | Lazy/short-circuit/optimization | Do not use `peek` for required side effects |
| Thinking concurrent sources provide instantaneous snapshots | Many concurrent sources have weak consistency | Read the contract; snapshot/lock if consistency is required |
| Thinking `new ArrayList<>(source)` deep-copies objects | Only creates a shallow copy | Create new objects/defensive copies if needed |
| Mutating a field used as a hash key of an element in a Set | Breaks the Set's lookup invariant | Use immutable key objects, create new structures |
| Reusing a Stream after a terminal operation | A Stream is consumed only once | Create a new stream when further processing is needed |

## 14. Self-Check Exercises

**Question 1.** Why is the following approach invalid in terms of Stream design?

~~~java
List<Integer> values = new ArrayList<>(List.of(1, 2, 3));
values.stream().forEach(v -> values.add(v * 10));
~~~

**Answer:** The callback adds to the `values` source itself while the terminal operation is traversing it. This is interference; errors or unguaranteed results may occur. If you want a list of values multiplied by 10, use `values.stream().map(v -> v * 10).toList()`.

**Question 2.** If `List.set` does not increment `modCount`, can it be called inside `map` on the same list?

**Answer:** No. Not throwing `ConcurrentModificationException` does not prove that modifying the source is valid. Non-interference does not only check structural changes that alter `size()`.

**Question 3.** Does `IntStream.range(0,1000).parallel().forEach(sharedList::add)` modify the Stream's source?

**Answer:** The source is the number sequence generated by `IntStream.range`, so it does not necessarily modify the source. However, it updates a shared List from multiple threads, violating state-safety requirements if the List is not protected. Use `boxed().toList()` or an appropriate collector.

**Question 4.** When you need to remove negative numbers from an original `ArrayList`, which API should you use outside of a Stream?

**Answer:** `list.removeIf(n -> n < 0)`, executed when there is no concurrent traversal of that List.

**Question 5.** Can you modify a `ConcurrentHashMap` while traversing its key stream?

**Answer:** Some sources from concurrent collections have contracts supporting concurrent modification and appropriate Spliterators, but the result is usually not a fixed snapshot. You must read the specific contract; do not apply that conclusion to `ArrayList`/arrays or to requirements for strict consistency.

**Question 6.** Does copying `List<User>` into `new ArrayList<>(users)` completely isolate the `User` data?

**Answer:** No. This is a shallow copy. If `User` is mutable, both lists can still reference the same `User` objects. To isolate state, you must copy each object according to the domain design.

**Question 7.** Why is incrementing a counter in `stream.map(...)` and then calling `count()` not a reliable way to count?

**Answer:** Intermediate operations are lazy and Streams can optimize: for a source of known size and a mapper that does not change the element count, `count()` can return the result without invoking the mapper. A counter side effect is not a contractually guaranteed product of the pipeline.

## 15. Key Takeaways

**Non-interference is a fundamental Stream requirement:** behavioral parameters passed to a pipeline must **not modify the data source being traversed**, except for sources with an explicit concurrent contract. For ordinary collections or arrays, modifying the source inside `filter`, `map`, `peek`, `forEach`, or any other callback should be avoided.

- Use `filter` and `map` to produce new result data, not to modify the source collection.
- If you need to modify the original collection, perform the mutation before or after traversal using an appropriate API such as `removeIf`, `replaceAll`, or `sort`.
- Do not rely on `ConcurrentModificationException` as a guaranteed bug-detection mechanism: fail-fast is usually only best effort.
- Distinguish **modifying the source** from **side effects on shared state**. Both cause problems, especially in parallel streams, though the reasons and remedies are not entirely the same.
- Snapshotting before traversal can be useful, but it is usually only a shallow copy and requires synchronization when copying a source being modified by another thread.
- Concurrent collections have their own semantics; they may support traversal during modification, which does not equate to a consistent snapshot.
- Prefer stateless, non-interfering callbacks with minimal side effects so pipelines are correct, easy to understand, and safer to optimize or parallelize.

The goal is not "never modify a List," but rather **clearly separating the data-modification phase from the Stream-traversal phase**, keeping the source stable during each traversal.
