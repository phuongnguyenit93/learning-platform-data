# Reference Components in Java Records Use the Equality Relation of the Component Type Itself

## 1. What "Equal" Means in a Record

A `record` declares a set of **record components** describing the data of a value. When not manually overridden, Java generates the necessary members, including the canonical constructor, corresponding accessors, `equals(Object)`, `hashCode()`, and `toString()`.

Example:

~~~java
record Customer(String name, int age) {}
~~~

Two distinct `Customer` objects can be value-equal if their corresponding components are equal. However, **each component type decides what counts as equal**:

- Primitive components such as `int` are compared by the appropriate primitive value.
- **Reference components** such as `String`, `List<String>`, `BigDecimal`, custom class objects, or arrays are compared based on the **`equals()` semantics of the component object itself**.
- Two reference components that are both `null` are considered equal; if only one side is `null`, they are not equal.
- All corresponding components must be compared; the declaration order and types of components are part of the record's structure.

In other words, a record does not inherently know what "same contents" means for every kind of object it holds. If a component has a type whose `equals()` is defined by value, the record inherits that meaning. If a component uses `Object.equals()` by identity, the record is also subject to that identity rule for that component.

## 2. How to Picture Generated `equals()` and `hashCode()`

Given a record such as:

~~~java
record Product(String code, int quantity) {}
~~~

**Semantically**, a record's equality check is understood through these steps:

1. If two references point to the same object, they are equal.
2. The compared object must be a record of **the same runtime record class**.
3. Corresponding primitive components must have equal values according to the rules for their types.
4. Corresponding reference components must be equal according to the component object's `equals` relation, including `null` handling.

To illustrate, you can picture logic like this:

~~~java
// Only to explain Product's behavior; not Java source generated by the compiler.
if (this == other) return true;
if (!(other instanceof Product p)) return false;
return quantity == p.quantity
        && java.util.Objects.equals(code, p.code);
~~~

This snippet is **illustrative code**, not a required bytecode implementation of the JVM, nor a standalone method you can paste and run directly. For records, the compiler/JVM may implement the generated methods via dynamic mechanisms; you should rely on the **behavioral contract**, not on a specific sequence of bytecode instructions. Records are `final`, so there is no subclass of that record itself.

`hashCode()` is generated based on the corresponding components, consistent with the equality relation produced by `equals()`. For reference components, the hash code depends on the component object's `hashCode()`; for `null`, there is an appropriate rule. **Do not rely on a specific numeric hash value** or assume the record's algorithm is identical to `Objects.hash(...)`: what must hold is that **two equal records must have equal hashes**.

The generated `toString()` also displays the components; this is a representation for reading/debugging, not a basis for defining equality. In particular, arrays are not automatically printed as element lists when appearing as an object in the string.

## 3. `String`, `List`, and `BigDecimal`: Three Reference Types with Different Semantics

Several commonly used types have value-based `equals()`, yet **value** is defined differently:

- `String.equals` compares character sequences (case-sensitive); two distinct `String` objects containing the same characters are still equal.
- `List.equals` compares **size and order**, then compares each pair of elements via the elements' equality relation. Two lists of different implementations can still be equal if they have the same sequence of elements according to `List` rules.
- `BigDecimal.equals` compares **value and scale**; `new BigDecimal("1.0")` is not `equals` to `new BigDecimal("1.00")` even though `compareTo` returns `0`. A record containing `BigDecimal` uses this exact `equals` rule.
- Other value types such as `LocalDate`, `UUID`, primitive wrappers, and enums have their own `equals` semantics. The record uses the appropriate semantics of the component object.
- If a component is declared as an interface, **the actual object's runtime type** provides the `equals()` implementation when the method is called; the interface name does not automatically create a single uniform `equals` definition for every implementation.

### Runnable Example: Record with Multiple Reference Components

Create the file `ReferenceComponentsDemo.java`:

~~~java
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public class ReferenceComponentsDemo {
    record Invoice(String customer, List<String> tags, BigDecimal amount) {}

    public static void main(String[] args) {
        Invoice first = new Invoice(
                new String("An"),
                new ArrayList<>(List.of("java", "core")),
                new BigDecimal("1.0")
        );
        Invoice equal = new Invoice(
                "An",
                List.of("java", "core"),
                new BigDecimal("1.0")
        );
        Invoice differentScale = new Invoice(
                "An",
                List.of("java", "core"),
                new BigDecimal("1.00")
        );
        Invoice differentOrder = new Invoice(
                "An",
                List.of("core", "java"),
                new BigDecimal("1.0")
        );

        System.out.println("same identity: " + (first == equal));
        System.out.println("same components: " + first.equals(equal));
        System.out.println("same hash: "
                + (first.hashCode() == equal.hashCode()));
        System.out.println("different BigDecimal scale: "
                + first.equals(differentScale));
        System.out.println("different List order: "
                + first.equals(differentOrder));
        System.out.println("BigDecimal numeric compare: "
                + first.amount().compareTo(differentScale.amount()));
    }
}
~~~

Compile and run with Java 17+:

~~~bash
javac -encoding UTF-8 ReferenceComponentsDemo.java
java ReferenceComponentsDemo
~~~

Stdout:

~~~text
same identity: false
same components: true
same hash: true
different BigDecimal scale: false
different List order: false
BigDecimal numeric compare: 0
~~~

Explanation: `first` and `equal` are two distinct `Invoice` objects, yet `String.equals`, `List.equals`, and `BigDecimal.equals` for the three components all return `true`, so the two records are equal. A difference in `BigDecimal` scale or a change in list element order makes the records unequal, because records do not automatically normalize components according to business expectations.

If business requirements treat `1.0` and `1.00` as the same value, you can **normalize the `BigDecimal` before storing it in the component** with a defined rule, or design `equals/hashCode` accordingly; do not change only the `equals` comparison while forgetting to update the hash.

## 4. Component Classes That Do Not Override `equals()`: Record Compares by Component Identity

A custom class by default inherits `Object.equals`, which essentially treats two references as equal only if they point to **the same object**. A record containing that class does not automatically deduce that "same fields mean equal components".

Create the file `IdentityComponentDemo.java`:

~~~java
public class IdentityComponentDemo {
    static final class Token {
        private final String code;

        Token(String code) {
            this.code = code;
        }

        String code() {
            return code;
        }
    }

    record Session(Token token) {}
    record ValueToken(String code) {}
    record ValueSession(ValueToken token) {}

    public static void main(String[] args) {
        Token leftToken = new Token("X");
        Token rightToken = new Token("X");

        Session first = new Session(leftToken);
        Session second = new Session(rightToken);
        Session aliasValue = new Session(leftToken);

        System.out.println("Token content: "
                + leftToken.code().equals(rightToken.code()));
        System.out.println("distinct Token objects: " + first.equals(second));
        System.out.println("same Token object: " + first.equals(aliasValue));

        ValueSession valueA = new ValueSession(new ValueToken("X"));
        ValueSession valueB = new ValueSession(new ValueToken("X"));
        System.out.println("nested record value: "
                + valueA.equals(valueB));
        System.out.println("nested record hash: "
                + (valueA.hashCode() == valueB.hashCode()));
    }
}
~~~

~~~bash
javac -encoding UTF-8 IdentityComponentDemo.java
java IdentityComponentDemo
~~~

Stdout:

~~~text
Token content: true
distinct Token objects: false
same Token object: true
nested record value: true
nested record hash: true
~~~

Both `Token("X")` instances have equal `code` strings, yet `Token` does not override `equals` so distinct `Token` objects are not equal; hence the two corresponding `Session` instances are not equal either. In contrast, `ValueToken` is a record with a `String` component and receives value-based equality; two `ValueSession` instances holding two distinct `ValueToken("X")` instances are still equal.

If a component class has a **value-based equality relation**, implement `equals` and `hashCode` consistently on that class itself. Designing value objects as records is also a good choice when you want equality to be determined by components.

### The `StringBuilder` Trap

`StringBuilder` is a mutable object and does not override `equals(Object)` to compare character contents. Therefore:

~~~java
record Text(StringBuilder builder) {}

Text a = new Text(new StringBuilder("hello"));
Text b = new Text(new StringBuilder("hello"));
System.out.println(a.equals(b)); // false
~~~

This is an illustrative snippet placed in a valid Java context, not a standalone file. If the intent is equality by text contents, use an immutable `String` component or convert `builder.toString()` to a string when constructing the record.

## 5. Special Case: Array Components

A `byte[]`, `int[]`, or `String[]` component inherits `Object.equals` by identity, so two records receiving two arrays with different references are still unequal even if their contents match. This is an exception to remember when examining equality of **reference types**. If business logic requires comparing contents, you must use the proper `Arrays.equals`/`Arrays.hashCode` pair (or `deepEquals`/`deepHashCode` for nested arrays) and guard every path that could mutate the array via constructor/accessor. The next lesson on arrays presents runnable examples and specific limitations; the core point here is that a record follows its component's `equals` contract.

## 6. Collection Components: Set-Based Equality Without Automatic Immutability

Common collections have their own equality relations:

| Component Type | Typical `equals` Semantics | Impact on Record |
| --- | --- | --- |
| `List<T>` | Same size, same order, and corresponding elements equal | Reordering elements usually makes records unequal |
| `Set<T>` | Same set of elements (ignoring iteration order) | Two Sets of different implementations can still be equal |
| `Map<K,V>` | Same key → value mappings per the `Map` contract | Two Maps containing the same mappings can be equal |
| `Optional<T>` | Two empty Optionals are equal, or both present with equal values | Record follows `Optional.equals` semantics |
| `StringBuilder` | Defaults to object identity comparison | Two builders with identical characters but different objects are usually unequal |
| `byte[]` or `Object[]` | Defaults to array identity comparison | Must override if content comparison is desired |
| Custom class not overriding `equals` | Defaults to object identity comparison | Record does not compare internal fields of that class |
| Nested record | Follows the nested record's `equals` | Can compare values across multiple levels, unless a deeper component uses identity |

**Note on collections containing arrays:** a `List<int[]>` uses `List.equals` to compare each element, yet the `int[]` elements still use identity equality. Thus, even though a `List` has positional `equals`, that **does not mean deep comparison of array contents inside the List**.

### Mutability Affects Equality and Hash

A record guarantees its component fields are `private final`, meaning a component reference **cannot be reassigned** after initialization. This does **not** prevent the state of the referenced object from changing.

Create the file `MutableComponentDemo.java`:

~~~java
import java.util.ArrayList;
import java.util.List;

public class MutableComponentDemo {
    record Roles(List<String> names) {}

    public static void main(String[] args) {
        List<String> external = new ArrayList<>(List.of("reader"));
        Roles first = new Roles(external);
        Roles baseline = new Roles(List.of("reader"));

        System.out.println("before mutation: " + first.equals(baseline));
        external.add("writer");
        System.out.println("after mutation: " + first.equals(baseline));
        System.out.println("record sees mutation: " + first.names());

        Roles safe = new Roles(List.copyOf(external));
        external.add("admin");
        System.out.println("defensive snapshot: " + safe.names());
    }
}
~~~

~~~bash
javac -encoding UTF-8 MutableComponentDemo.java
java MutableComponentDemo
~~~

Stdout:

~~~text
before mutation: true
after mutation: false
record sees mutation: [reader, writer]
defensive snapshot: [reader, writer]
~~~

Here `first.names()` and `external` point to the same mutable list. Modifying `external` changes the equality result of `first`. If the record is used as a **`HashMap` key or `HashSet` element**, mutating a component that determines the hash can cause lookups to stop working as expected.

`List.copyOf(external)` creates a list that cannot be modified via the list API and preserves a snapshot of the existing elements in the example. It **does not automatically deep-copy** mutable elements: if the list contains objects that are still mutable, their state can still change.

### Compact Constructor for Defensive Copying on Record Creation

If a component is `List<String>` and should always keep an immutable snapshot, you can write:

~~~java
import java.util.List;
import java.util.Objects;

record SafeRoles(List<String> names) {
    SafeRoles {
        names = List.copyOf(Objects.requireNonNull(names));
    }
}
~~~

This is a standalone compilable record class example; `List.copyOf` does not accept `null` elements. After the compact constructor, the component field receives the copied/normalized list; the default generated accessor returns a list that cannot be modified through its API. For immutable `String` elements, this approach is suitable for protecting equality. For array components, you must clone both on input and on output if you want to prevent direct mutation.

## 7. `null`, Reference Types, and the `==` Operator

Given the record:

~~~java
record Person(String firstName, String lastName) {}
~~~

Two `Person(null, "A")` instances are equal because their first components are both `null` and their second components are two `String`s with equal contents. A `Person(null, "A")` and a `Person("", "A")` are not equal: `null` and the empty string are two different values.

For reference components, the fact that a record uses the component object's `equals` relation does not mean using `==` on that component. For `String`, `==` can return `false` for two distinct string objects with identical contents, while records holding them can be equal.

Two **record instances** compared with `==` are equal only when they are the same object; use `recordA.equals(recordB)` when comparing values under the record contract. This is the difference between **record identity** and **component equality**.

## 8. Some Design Boundaries to Know

### Different Record Classes Are Not Automatically Equal

Two record types, even if declared with identical component names and values, are still two different classes. The generated `equals` method requires the records to have **the same actual record type**, and does not structurally match across classes.

~~~java
record A(String code) {}
record B(String code) {}
// new A("x").equals(new B("x")) == false
~~~

This snippet illustrates behavior and can be declared inside the same enclosing class or the same package with distinct names.

### `float` and `double` Components

They are **primitives**, so the rule of calling `equals` on a reference object does not apply. However, a record's generated comparison uses an appropriate policy to preserve the hash contract, in which **`NaN` values are considered equal to one another** and **`+0.0` differs from `-0.0`**. Do not mechanically generalize from the primitive `==` operator to all record comparison behavior. This clarifies the boundary of this lesson: **reference components** are governed by the component type's equality rules; **primitive components** follow primitive-specific rules in records.

### Manually Overriding `equals/hashCode` Changes the Contract

Records allow manually implementing `equals` and `hashCode`, in which case the programmer is responsible for reflexivity, symmetry, transitivity, consistency, `null` behavior, and the **equal implies equal hash** rule. If overriding to compare array contents, normalize `BigDecimal`, or ignore a component, update both methods in sync and test the impact on objects used as keys.

### Do Not Infer Deep Immutability Just from the `record` Keyword

Records have final component fields, yet the object behind a reference can be mutable. If a component's `equals` or `hashCode` depends on mutable state, the record's equality/hash result can also fluctuate. If a stable value object is needed, prefer immutable components, defensive copying, and avoiding exposing internal mutable data.

## 9. Common Misconceptions

| Misconception | What Is True |
| --- | --- |
| A record automatically compares all fields inside a reference component object. | Default generated records use the `equals` relation provided by the component type; they do not deep-reflect over all fields. |
| Two distinct `String` objects make two records holding them unequal. | `String.equals` compares contents; the two records can be equal. |
| `BigDecimal("1.0")` and `BigDecimal("1.00")` components are equivalent in a record because they have the same numeric value. | `BigDecimal.equals` also checks scale; the record follows that exact rule. |
| Array components are always compared by records using `Arrays.equals`. | False. Default record equality sees arrays as objects and compares array identity. |
| A `List<int[]>` component causes all child arrays to be compared element-by-element. | `List.equals` calls each element's equality, and `int[]` uses identity. |
| Record fields are `final`, so the entire state is immutable. | `final` only stabilizes the reference; the component object can be mutable. |
| You can override `equals` alone to compare array contents while keeping the default record hash. | Unsafe, because two equal records could receive different hashes. |
| Two records of different types with identical data structure will be equal. | Default equality requires the same record type. |
| Seeing matching `hashCode` values means two records are equal. | Hashes can collide; you must check `equals`. |

## 10. Application Workflow and Self-Check

When designing a record with reference components:

1. **List each component** and its type: `String`, `List`, `BigDecimal`, array, custom type, or nested record.
2. **Identify the `equals` semantics of each type**: by contents, by order, by scale, by identity, or by a custom rule.
3. **Check business fit**: should two records with visually identical contents truly be equal? For arrays, builders, or custom classes without an `equals` override, data model adjustments are often needed.
4. **Assess mutability**: can the component object be modified externally after the record is created? Can `List.copyOf`, array copies, or immutable types be used?
5. **Keep `equals` and `hashCode` synchronized** if manually overriding: use the same set of attributes and the same shallow/deep/normalization policy.
6. **Test distinguishing scenarios**: two different component objects with identical contents; same component reference; `null`; reordered list; changed `BigDecimal` scale; two arrays with identical elements; mutating data after using as a `HashMap` key.
7. **Prefer a concise record declaration** when generated equality already fits the intended meaning; only write custom implementations for a concrete design reason and thoroughly test the contract.

**Remember:** records provide equality by components, yet for **reference components**, "equality" directly depends on how **the component object's type defines `equals()`**. `String`, `List`, `BigDecimal`, arrays, and custom classes can yield very different results. Choosing the right component types, protecting mutable data, and keeping `equals/hashCode` consistent matter more than simply looking at the shape of the record declaration.
