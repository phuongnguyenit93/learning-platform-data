# Binding to a Backend in SLF4J

**SLF4J (Simple Logging Facade for Java)** provides a common API for applications and libraries to write logs through `org.slf4j.Logger`. **Binding to a backend** is the process of connecting those calls to an actual logging system capable of processing and outputting log records, such as **Logback**, **Log4j 2**, **java.util.logging (JUL)**, or SimpleLogger.

For example, the call `LOG.info("Payment {} started", paymentId)` can compile with only `slf4j-api`, but **the SLF4J API itself does not configure log files, appenders, or output formats**. For events to be processed, the application needs a **compatible SLF4J provider/binding at runtime**. If a provider is missing, SLF4J 2.x typically logs a warning and uses a **NOP** (no-operation) logger, causing logging calls to produce no output.

It is important to distinguish terminology by version:

- **SLF4J 1.7.x and earlier:** usually refers to the connection component as a **binding**. Implementation discovery relies on the `org.slf4j.impl.StaticLoggerBinder` class.
- **SLF4J 2.x:** uses a **provider** via Java's `ServiceLoader` mechanism. A provider implements the `org.slf4j.spi.SLF4JServiceProvider` interface; `StaticLoggerBinder` is no longer used to select a backend.
- In much documentation, the word "binding" is still used in the general sense of **connecting the API to a backend**. However, when managing dependencies, you must identify the **SLF4J major version**, because 1.7 bindings and 2.x providers are not arbitrarily interchangeable.

## 1. Why Does SLF4J Need a Binding/Provider?

A facade decouples business code from a concrete implementation:

~~~text
Application / library using org.slf4j.Logger
                    |
                    v
              slf4j-api 2.x
                    |
       find SLF4JServiceProvider at runtime
                    |
                    v
         Compatible provider selected
                    |
                    v
      Actual backend and configuration
                    |
          Appender / Handler / filter
                    |
                    v
           Console / file / collector
~~~

For example: **SLF4J API → Logback provider → Logback → ConsoleAppender**. The application only imports `org.slf4j.Logger` and `LoggerFactory`; Logback decides the layout, level, and output destination.

Benefits:

1. **Application code has minimal implementation coupling:** replacing Logback with another compatible backend usually does not require modifying hundreds of `LOG.info(...)` or `LOG.error(...)` calls.
2. **Reusable libraries:** libraries can depend only on `slf4j-api`, while the final running application decides the backend.
3. **Centralized management:** a single backend can receive logs from multiple components and libraries when all of them go through SLF4J or appropriate bridges.
4. **Separation of operational configuration:** log levels, file destinations, layouts, rotation, and filters are typically configured by the backend rather than hardcoded in services.

**Limitation:** the facade only standardizes the capabilities exposed by SLF4J. Backend-specific features, structured key/value representations, async appenders, or XML/JSON configuration formats may differ when changing implementations.

## 2. Separating API, Provider, Backend, and Bridge

| Component | Example | Function |
| --- | --- | --- |
| **Facade/API** | `org.slf4j:slf4j-api` | Defines Logger, LoggerFactory, and info/debug/warn/error methods |
| **SLF4J 2.x provider** | Implementation part in `logback-classic` or `log4j-slf4j2-impl` | Allows LoggerFactory to discover a compatible implementation via ServiceLoader |
| **Backend** | Logback, Log4j 2 Core, JUL | Executes logging, filters events, manages destinations and formatting |
| **Appender/handler** | Logback ConsoleAppender, JUL ConsoleHandler | Dispatches log records to console, file, or another system |
| **Source bridge/adapter** | `jul-to-slf4j`, `log4j-to-slf4j` | Routes calls from another logging API **into SLF4J** |
| **NOP implementation** | `slf4j-nop` or fallback when provider is missing | Accepts calls but intentionally emits no logs |

A single artifact can serve **multiple roles**. For example, `logback-classic` both provides the SLF4J provider for SLF4J 2.x and acts as the Logback backend component; you do not need to add a separate "Logback binding" JAR just because you see `slf4j-api`.

**A bridge is not a provider.** The `jul-to-slf4j` bridge routes events from JUL to SLF4J; for them to appear on the console via Logback, the application still needs an appropriate provider/backend and must activate the JUL bridge properly.

## 3. How Does SLF4J 2.x Discover a Provider?

During initialization, SLF4J 2.x's `LoggerFactory` searches for implementations of the `SLF4JServiceProvider` interface using Java's `ServiceLoader` mechanism. A provider is typically declared in the standard JAR service provider resource:

~~~text
META-INF/services/org.slf4j.spi.SLF4JServiceProvider
~~~

That service file points to the backend's provider class. **Business applications usually do not write their own provider**: they simply need a compatible backend/provider dependency on the **runtime classpath**, ensuring that JAR packaging and classloading preserve that service descriptor.

Scenarios:

- **Exactly one compatible provider:** SLF4J selects that provider and returns a Logger backed by it.
- **No provider:** SLF4J 2.x reports a missing provider and usually falls back to **NOP**. Application calls continue to run normally, but no logs are produced.
- **Multiple providers:** SLF4J warns that multiple providers were found; which provider gets used may depend on classpath/classloader order. Do not rely on arbitrary selection order; clarify and keep **only one intentional provider**.
- **An SLF4J 1.7 binding is present with API 2.x:** legacy `StaticLoggerBinder`-style bindings **are not used by SLF4J 2.x as providers**. You must choose a 2.x-compatible implementation.
- **Provider is present, but no messages appear:** backend levels, filters, or appenders may be blocking the logs, or the backend may be writing to a different destination.

Here, `ServiceLoader` selects the **provider**; it does not decide whether an INFO log statement is printed. Level filtering and output routing remain the responsibility of the selected backend.

### Distinguishing SLF4J 1.7 and 2.x Behavior

| Topic | SLF4J 1.7.x | SLF4J 2.x |
| --- | --- | --- |
| Implementation discovery mechanism | `org.slf4j.impl.StaticLoggerBinder` class | Java `ServiceLoader` and `SLF4JServiceProvider` |
| Common terminology | Binding | Provider |
| When implementation is missing | Warns about missing `StaticLoggerBinder`; uses NOP | Warns that no provider was found; uses NOP |
| Logback version to choose | Artifact/version supporting API 1.7 | Artifact/version providing a provider for API 2.x |
| How to resolve mismatch | Align API with legacy binding or upgrade the entire group | Align API 2.x with a 2.x provider |
| Can libraries depend only on the API? | Yes | Yes |

**Do not judge compatibility by artifact name alone.** Check the actual version of `slf4j-api`, the backend version, and the provider/binding mechanism it supports. In particular, a legacy JAR containing `StaticLoggerBinder` is not sufficient for `slf4j-api:2.x`.

## 4. Common Providers/Backends for SLF4J 2.x

| Dependency/provider | Routing direction | Suitable use case |
| --- | --- | --- |
| `ch.qos.logback:logback-classic` (version supporting SLF4J 2.x) | SLF4J → Logback | Full-featured backend with appenders, patterns, filters, and Logback configuration |
| `org.apache.logging.log4j:log4j-slf4j2-impl` | SLF4J 2.x → Log4j 2 | Applications that already use Log4j 2 API/Core as their backend |
| `org.slf4j:slf4j-simple` (matching 2.x branch) | SLF4J → SimpleLogger | Small programs, experiments, and minimal logging needs |
| `org.slf4j:slf4j-jdk14` (matching 2.x branch) | SLF4J → JUL | When you want to use the JDK's built-in logging backend |
| `org.slf4j:slf4j-nop` (matching 2.x branch) | SLF4J → NOP | Intentionally disabling logging in controlled situations |

These are **mutually exclusive alternatives for the same SLF4J pipeline**, not a list to add all at once. Normally, an application only needs **one provider**, and that single backend handles output destinations.

If you choose Logback, you need Logback configuration such as `logback.xml`. If you choose Log4j 2, you will use Log4j 2 configuration such as `log4j2.xml`; a `logback.xml` file does not automatically configure Log4j 2. If you choose JUL, JUL's handlers/configuration determine the output.

**`log4j-core` alone is not an SLF4J 2.x provider.** An application using SLF4J that wants to route logs to Log4j 2 typically needs `log4j-slf4j2-impl` along with compatible Log4j 2 components.

## 5. Complete Example: SLF4J 2.x Binding to Logback with Maven

The example below uses Java 17+, **SLF4J API 2.0.17**, and **Logback 1.5.18**. This is an illustrative compatible version combination verified in a test environment; **it does not imply these are the latest versions for every project**.

Project structure:

~~~text
slf4j-provider-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── demo/
        │       └── BindingDemo.java
        └── resources/
            └── logback.xml
~~~

### 5.1. Declaring Dependencies in pom.xml

~~~xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
  xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>
  <groupId>demo</groupId>
  <artifactId>slf4j-provider-demo</artifactId>
  <version>1.0.0</version>

  <properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.slf4j</groupId>
      <artifactId>slf4j-api</artifactId>
      <version>2.0.17</version>
    </dependency>
    <dependency>
      <groupId>ch.qos.logback</groupId>
      <artifactId>logback-classic</artifactId>
      <version>1.5.18</version>
    </dependency>
  </dependencies>

  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.13.0</version>
      </plugin>
      <plugin>
        <groupId>org.codehaus.mojo</groupId>
        <artifactId>exec-maven-plugin</artifactId>
        <version>3.5.1</version>
      </plugin>
    </plugins>
  </build>
</project>
~~~

`slf4j-api` provides the Logger/LoggerFactory types. `logback-classic` provides the implementation/provider, and Maven resolves the required Logback transitive components via the dependency graph. In real-world applications, you can use appropriate dependency management/BOMs instead of pinning individual versions; just ensure the final versions on the runtime classpath are compatible.

### 5.2. Source Code Using Only the SLF4J API

Create the file **src/main/java/demo/BindingDemo.java**:

~~~java
package demo;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class BindingDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(BindingDemo.class);

    public static void main(String[] args) {
        System.out.println("ILoggerFactory="
                + LoggerFactory.getILoggerFactory().getClass().getName());
        LOG.info("event=payment_started orderId={}", "ord-7");
        LOG.debug("event=internal_check orderId={}", "ord-7");
        LOG.warn("event=payment_retry orderId={} attempt={}", "ord-7", 2);
    }
}
~~~

This code **does not import any Logback classes**. Calling `LoggerFactory.getILoggerFactory().getClass().getName()` lets you observe the implementation selected by SLF4J at runtime; this is a diagnostic/demonstration aid and does not need to be added to every production class.

### 5.3. Backend Configuration via logback.xml

Create the file **src/main/resources/logback.xml**:

~~~xml
<configuration>
  <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder><pattern>%level | %logger{40} | %msg%n</pattern></encoder>
  </appender>
  <root level="INFO"><appender-ref ref="CONSOLE"/></root>
</configuration>
~~~

This configuration file is read by **Logback**, not by the SLF4J API itself. The CONSOLE appender prints to the console using a fixed pattern; the root level of INFO excludes DEBUG.

### 5.4. Compiling and Running

From the directory containing `pom.xml`, with Maven and JDK 17+:

~~~bash
mvn -q compile exec:java -Dexec.mainClass=demo.BindingDemo
~~~

The **program output** with the configuration above:

~~~text
ILoggerFactory=ch.qos.logback.classic.LoggerContext
INFO | demo.BindingDemo | event=payment_started orderId=ord-7
WARN | demo.BindingDemo | event=payment_retry orderId=ord-7 attempt=2
~~~

The `LOG.debug(...)` line **is not printed** because the root level is INFO. Detailed Maven output may vary by environment if you omit the `-q` option.

The output shows:

1. **The SLF4J API connected to the right backend:** the actual ILoggerFactory is `ch.qos.logback.classic.LoggerContext`.
2. The `LOG.info` and `LOG.warn` calls are written by Logback according to the pattern in `logback.xml`.
3. The `{}` placeholders are formatted into actual values by the SLF4J/Logback logging stack.
4. The DEBUG level is blocked by the backend; it is not a missing-provider error.

Changing the backend affects the implementation, dependencies, and configuration; the business code above can keep its SLF4J calls unchanged as long as the new backend is compatible with the API in use.

## 6. Same Principle with Gradle

In a Gradle project using SLF4J 2.x and Logback, a simple configuration looks like:

~~~groovy
plugins {
    id 'java'
    id 'application'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.slf4j:slf4j-api:2.0.17'
    runtimeOnly 'ch.qos.logback:logback-classic:1.5.18'
}

application {
    mainClass = 'demo.BindingDemo'
}
~~~

You can use the same Java file and `logback.xml` as in the Maven section, then run:

~~~bash
./gradlew run
~~~

This command requires the project to have a **Gradle Wrapper**. If there is no Wrapper, use a compatible installed Gradle version.

`implementation` is used for `slf4j-api` because the source code **compiles** against SLF4J interfaces. `runtimeOnly` is used for Logback when the source code does not directly reference Logback classes: the implementation is loaded at **runtime**, rather than being needed to compile business classes. Some frameworks/starters manage the backend automatically, so you may not need to declare both dependencies this way.

There is no need to write `new LoggerContext()` in the application or call `bind()` manually. The provider is discovered through the classpath and ServiceLoader when SLF4J initializes.

## 7. Interaction Between Provider and Level Configuration

Successfully connecting to a backend **does not guarantee every message will be displayed**. There are two independent questions:

1. **Which provider is loaded?** This is a question of dependencies, classpath, ServiceLoader, and versions.
2. **Is the event emitted?** This is a question of effective log level, filters, appenders/handlers, layout, destination, and policies.

In the program above, for example, the factory is Logback and INFO/WARN produce output, so the provider is working. DEBUG is filtered out because root is INFO. You can adjust a specific package for diagnostics in `logback.xml`:

~~~xml
<logger name="demo" level="DEBUG"/>
~~~

This XML snippet goes **inside `<configuration>`** in Logback; it is not a complete standalone `logback.xml` file. It raises the detail level for loggers named `demo.*`; other components continue to follow their appropriate parent configuration.

If the backend has an appender filter that only accepts WARN and above, enabling DEBUG on the logger alone is still not enough to see DEBUG. When investigating, check the **effective logger level**, filters, and actual appenders.

## 8. Missing Provider, Extra Providers, and Version Mismatches

### 8.1. Only slf4j-api on the Runtime Classpath

An application may compile successfully, but at runtime SLF4J 2.x may print a message similar to:

~~~text
SLF4J: No SLF4J providers were found.
SLF4J: Defaulting to no-operation (NOP) logger implementation
~~~

Exact messages may vary slightly by SLF4J version. NOP does not write logs, so `logger.info(...)` calls produce no expected output. **Fix:** add **one** SLF4J 2.x-compatible provider to your runtime dependencies and verify that the final artifact includes the provider.

`LoggerFactory.getILoggerFactory().getClass().getName()` can help confirm which implementation is running. When the result is a NOP factory, the cause is either a missing provider or an intentional use of NOP.

### 8.2. Multiple SLF4J 2.x Providers Present

For example, a dependency pulls in `slf4j-simple` while the application already includes `logback-classic`. SLF4J may report that multiple providers were found. The outcome can become unpredictable when the classpath changes, so **do not rely on whichever provider happens to be picked**.

Fix:

1. Inspect the dependency tree or runtimeClasspath.
2. Decide which backend the application should use.
3. Remove **competing providers** by dropping the dependency or excluding it from the dependency that pulled it in.
4. Re-run and verify that only the intended provider remains.

Having one provider selected does not mean the remaining providers will also process the same event. If logs are duplicated, you must also check for multiple appenders/handlers, additivity, and bridges; do not assume every duplicate log issue is caused by multiple providers.

### 8.3. SLF4J 2.x API with an SLF4J 1.7 Binding

If a legacy `StaticLoggerBinder`-style JAR is on the runtime classpath, SLF4J 2.x does not treat it as a provider. A warning may appear about a binding targeting SLF4J 1.7 or earlier, and that binding is ignored.

The fix is to **align major versions**: use API 2.x with a provider that supports 2.x, or, if constrained by a legacy system, choose a compatible legacy API/binding combination. Do not try to fix this by randomly adding more logging JARs.

### 8.4. API 1.7 with Only a 2.x Provider

SLF4J 1.7 looks for `StaticLoggerBinder`, so it cannot automatically use a provider that only implements the 2.x ServiceLoader mechanism. If you switch backends while keeping API 1.7, you must choose a compatible 1.7 binding. Application code may use a fairly similar API, but **the implementation loading mechanism is different**.

### 8.5. Provider Is in Maven/Gradle, Yet the Application Still Uses NOP

This can happen if the dependency is only on the **test classpath** and does not make it into the running artifact; is missing in the container; packaging strips out JARs/service descriptors; there is a classloader conflict; or the file actually being executed is different from the one just built.

Inspect the **runtime classpath of the actual running process**, rather than just checking whether the dependency appears in `pom.xml` or `build.gradle`.

## 9. Binding and Bridge: Check the Forwarding Direction

A common mistake is adding a dependency with SLF4J in its name without checking **which direction it routes**.

~~~text
Other API source -> [BRIDGE] -> SLF4J API -> [PROVIDER] -> BACKEND
~~~

| Artifact | Primary direction | Role |
| --- | --- | --- |
| `jul-to-slf4j` | JUL → SLF4J | Bridge that routes `java.util.logging` logs into the SLF4J facade |
| `log4j-to-slf4j` | Log4j 2 API → SLF4J | Bridge that routes Log4j 2 calls into SLF4J |
| `jcl-over-slf4j` | Compatible Jakarta/Apache Commons Logging API → SLF4J | Bridge from the commons-logging API to SLF4J in compatible cases |
| `log4j-slf4j2-impl` | SLF4J 2.x → Log4j 2 | Provider/adapter when Log4j 2 is the backend |
| `slf4j-jdk14` | SLF4J → JUL | Provider that routes SLF4J events to JUL |
| `logback-classic` | SLF4J → Logback | Provider and Logback backend |

### Two Forwarding Loops to Avoid

**Loop 1: Log4j 2 and SLF4J**

~~~text
Log4j 2 API -> log4j-to-slf4j -> SLF4J
     ^                              |
     |                              |
     +---- log4j-slf4j2-impl -------+
~~~

`log4j-to-slf4j` and `log4j-slf4j2-impl` point in **opposite directions**; do not place both in the same runtime pipeline. When you want Log4j 2 to be SLF4J's backend, use `log4j-slf4j2-impl` and compatible Log4j 2 dependencies—**you do not need `log4j-to-slf4j`**.

**Loop 2: JUL and SLF4J**

If an application selects JUL as its backend via `slf4j-jdk14`, and also configures `jul-to-slf4j` to send JUL into SLF4J, events can loop. When you want to centralize all logs in Logback, you can use `jul-to-slf4j` in the direction JUL → SLF4J → Logback, but do not simultaneously use `slf4j-jdk14` as the provider.

With JUL, simply adding `jul-to-slf4j` to the classpath **is not necessarily enough** to forward all JUL events. You need to configure and install `SLF4JBridgeHandler`, while checking existing JUL handlers to avoid duplicate logs. If a framework has already set up the bridge, do not add a second configuration yourself.

### A Bridge Does Not Replace a Provider

If you only have `jul-to-slf4j` and `slf4j-api` with no provider, JUL events bridged to SLF4J can still fall into NOP. To complete the pipeline, you need a **compatible backend/provider** behind the facade.

Conversely, if a library already calls SLF4J directly, **you do not need the JUL bridge just to run SLF4J calls**. A bridge is useful when another component still emits logs via JUL.

## 10. Choosing a Backend in Libraries and Applications

**Shared libraries** should prefer depending only on `slf4j-api`, letting the application decide the final backend. If a library bundles a provider (for example `logback-classic`) as a default runtime dependency, applications using Log4j 2 or another backend may run into multiple providers or conflicts.

**End applications** choose one provider based on their needs: Logback for common setups, Log4j 2 if the architecture already uses Log4j, JUL if JDK logging is desired, or SimpleLogger for small programs. Then configure levels, outputs, policies, and bridges for other APIs if actually needed.

With frameworks like Spring Boot, logging may already be configured by a starter. Before adding `logback-classic` or `log4j-slf4j2-impl`, inspect the actual application's dependency tree. When switching backends, update dependencies according to the framework's guide to avoid keeping both the default backend and the new one.

Some backends can output JSON logs or add asynchronous logging; however, the SLF4J API only commits to its own interface contract. Verify backend-specific features after selecting the backend rather than assuming the facade guarantees them across all implementations.

## 11. Diagnosing Classpath and Actual Provider

### Gradle

If the project has a Wrapper:

~~~bash
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency slf4j-api --configuration runtimeClasspath
./gradlew dependencyInsight --dependency logback-classic --configuration runtimeClasspath
~~~

`dependencies` shows which artifacts are actually on `runtimeClasspath`; `dependencyInsight` helps trace which dependency brings a module in and determines its version. For other backends, substitute the corresponding module name to investigate the provider.

### Maven

~~~bash
mvn dependency:tree
~~~

Check `slf4j-api`, providers such as `logback-classic` or `log4j-slf4j2-impl`, bridges, and dependencies that transitively pull in other backends.

### Checking Directly at Runtime

Inside an SLF4J program:

~~~java
System.out.println(
        org.slf4j.LoggerFactory.getILoggerFactory()
                .getClass().getName());
~~~

This is a **diagnostic snippet**, not a standalone program. The output might be `ch.qos.logback.classic.LoggerContext` when using Logback as in the example, or another implementation depending on the actual provider.

If logging works in your IDE but `java -jar` or a container produces no logs, check:

1. Does the final runnable artifact contain the **provider JAR** and backend dependencies?
2. Are `META-INF/services/...` files preserved if packaged as a shaded/uber JAR?
3. Are configuration files such as `logback.xml`/`log4j2.xml` on the resources/classpath in the right environment?
4. Does the runtime have multiple providers, different classloaders, or incorrectly excluded dependencies?
5. Are logs being written to stderr, stdout, a file, or a collector system different from where you are looking?

Some provider loading errors are printed by SLF4J to stderr as soon as LoggerFactory initializes; preserve startup logs rather than only checking after the application has been running for a while.

## 12. Common Errors and Fixes

| Symptom | Likely cause | Action |
| --- | --- | --- |
| API compiles, `LOG.info` is silent | Missing SLF4J 2.x provider, NOP fallback | Add exactly one provider to runtime; check startup warnings |
| SLF4J reports multiple providers | Two or more implementations pulled in together | Pick one backend; exclude competing providers |
| SLF4J 2.x ignores old binding | Binding uses 1.7 `StaticLoggerBinder` | Align API/provider by major version |
| `LoggerFactory` selects unexpected backend | Transitive dependencies and classloader | Check runtimeClasspath/Maven tree and actual factory |
| Logback is present, but DEBUG is missing | Root logger is INFO or filter/appender blocks DEBUG | Check effective level and `logback.xml`; provider may still be working |
| Switched Logback to Log4j 2, config has no effect | Still using `logback.xml` | Use the proper Log4j 2 config and remove the old backend |
| JUL is not collected into Logback | JUL → SLF4J bridge not used/installed | Enable bridge only when needed; check JUL handlers |
| Loop error or abnormal logging | Reversed Log4j ↔ SLF4J or JUL ↔ SLF4J bridge | Remove the incorrect forwarding direction |
| Duplicate logs | Two appenders with same target, additivity, parent handler, or double bridge | Trace an event's path through backends/handlers |
| Logs appear in IDE, missing in packaged JAR | Missing provider/service descriptor/resources | Inspect artifact contents and runtime classpath |
| Multiple SLF4J versions in dependency graph | Version conflict / transitive dependency | Use dependency management, exclude old versions, verify loaded version at runtime |
| `System.out.println` prints even with SLF4J NOP | println does not go through SLF4J | Do not confuse direct stdout output with backend-processed log events |

**Do not try to solve a "missing provider" error merely by raising the log level or adding `logback.xml`**. A configuration file cannot create a missing implementation on the runtime classpath. Conversely, do not try to solve every "missing DEBUG" issue by adding a second provider when the first provider is already working.

## 13. Practical Scenarios: Determining Whether the Connection Is Right or Wrong

### Scenario A — API Present, Backend Missing

~~~text
runtimeClasspath:
  slf4j-api 2.x
~~~

The application calls `LOG.info(...)` but no logs appear. Look for the **No SLF4J providers were found** warning; if present, add a compatible provider to runtime. There is no need to modify the `LOG.info` calls.

### Scenario B — Two Competing Providers

~~~text
runtimeClasspath:
  slf4j-api 2.x
  logback-classic (supports SLF4J 2.x)
  slf4j-simple 2.x
~~~

This configuration has **two providers**. Choose either Logback or SimpleLogger as needed, keep only one provider, and verify the runtime after fixing. Keeping both JARs thinking "more loggers will write more logs" is a misconception.

### Scenario C — Provider Present, Only DEBUG Missing

~~~text
runtimeClasspath:
  slf4j-api 2.x
  logback-classic (supports SLF4J 2.x)

logback.xml:
  root level = INFO
~~~

`LOG.info` produces output, while `LOG.debug` does not. This is backend **level filtering**, not a binding error. Enable DEBUG on the logger/package under investigation if needed and ensure the corresponding appender/filter allows it.

### Scenario D — Loading a Provider with the Wrong Major Version

~~~text
runtimeClasspath:
  slf4j-api 2.x
  a binding that only supports the SLF4J 1.7 mechanism
~~~

Check startup warnings and the dependency tree. SLF4J 2.x requires a provider implementing `SLF4JServiceProvider`. Keeping an old artifact name does not guarantee compatibility with the new major version.

### Scenario E — Bridge Present, Still No Logs

~~~text
JUL -> jul-to-slf4j -> slf4j-api -> (no provider)
~~~

Adding a bridge only forwards the **event source**. Provide a backend/provider after SLF4J, or intentionally use another route with a complete backend.

## 14. Checklist When Integrating SLF4J with a Backend

Before deploying the application to a runtime environment:

1. Source code uses **`org.slf4j.Logger`** and has the desired `slf4j-api` version.
2. Choose **one provider** compatible with the API major version.
3. Both the provider and backend dependencies are actually on the **runtime classpath** of the running artifact.
4. Backend configuration is the right type (`logback.xml`, `log4j2.xml`, or JUL config), at the right path, and for the right environment.
5. Test INFO, WARN, and DEBUG output by level; clearly distinguish a missing provider from level filtering.
6. Audit transitive dependencies so they do not pull in competing providers or outdated 1.7 bindings.
7. If using JUL, Commons Logging, or Log4j 2 API bridges, map out the **forwarding direction** to avoid loops.
8. For packaged/shaded JARs, verify that `META-INF/services` resources and runtime dependencies are preserved.
9. Watch SLF4J startup warnings, and test an actual message at the intended destination.
10. For shared libraries, depend only on the API; let the final application choose the backend and logging policy.

**Remember:** SLF4J is a facade. The **binding/provider** is the link that lets `LoggerFactory` select an implementation at runtime; the **backend** determines how logs are filtered, formatted, and output. In SLF4J 2.x, providers are discovered via Java `ServiceLoader`, whereas `StaticLoggerBinder`-style bindings are the legacy mechanism from SLF4J 1.7. Choosing **one compatible provider**, checking the runtime classpath, and distinguishing providers from bridges will help you avoid missing logs, duplicate logs, or an unexpected backend.
