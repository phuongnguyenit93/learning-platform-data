# SLF4J: Facade cho logging trong Java

## 1. SLF4J là gì?

**SLF4J** (*Simple Logging Facade for Java*) là một **facade**, tức lớp API thống nhất để mã Java ghi log mà không phải phụ thuộc trực tiếp vào cách một hệ thống logging cụ thể lưu hoặc xuất log. Thay vì mỗi class sử dụng API riêng của Logback, Log4j2 hay Java Util Logging (JUL), mã ứng dụng có thể dùng `org.slf4j.Logger` và `org.slf4j.LoggerFactory`.

SLF4J trả lời câu hỏi: **“Ứng dụng gọi logging bằng giao diện nào?”**. Một **provider** và **logging backend** sẽ trả lời các câu hỏi: “Level nào được bật? Log ra console hay file? Dùng định dạng nào? Có lưu/thu thập log ở nơi khác không?”

```text
Service / Controller / Library
            │
            │  Logger.info(), Logger.warn(), Logger.error()...
            ▼
        SLF4J API
  org.slf4j.Logger / LoggerFactory
            │
            ▼
   Provider SLF4J tương thích
            │
            ├── Logback Classic
            ├── Log4j2 thông qua provider phù hợp
            ├── JUL thông qua slf4j-jdk14
            └── slf4j-simple (triển khai logging đơn giản)
            │
            ▼
       Console / file / collector
```

Các nhánh trong sơ đồ là **phương án lựa chọn**, không phải khuyến nghị đưa toàn bộ provider vào một ứng dụng. Trong một tiến trình thông thường, hãy chọn **một provider SLF4J chính**.

**SLF4J không tự động lưu log** chỉ vì ứng dụng thêm `slf4j-api`. Nó cũng không phải một hệ thống lưu trữ tập trung, dashboard hoặc distributed tracing. Để ghi log thật sự cần có provider tương thích khi chạy.

## 2. Vì sao facade có ích?

Giả sử một thư viện thanh toán dùng Logback API trực tiếp, một thư viện khác dùng JUL và ứng dụng chính dùng Log4j2 API. Mã nguồn, level, định dạng và đường đi của log có thể khác nhau. Một facade chung giúp các thư viện **chủ động chọn một API viết log ổn định** và để ứng dụng cuối quyết định backend thực thi.

Các lợi ích quan trọng:

- **Giảm phụ thuộc của mã nghiệp vụ vào backend**: lớp Java viết `LOG.info(...)` và `LOG.error(...)`, không phải cấu hình appender hay file handler.
- **Dễ tổ chức dependency**: thư viện dùng `slf4j-api`; ứng dụng triển khai chọn provider theo yêu cầu vận hành.
- **Nhất quán cú pháp và ngữ nghĩa**: sử dụng chung các mức `TRACE`, `DEBUG`, `INFO`, `WARN` và `ERROR`; hỗ trợ tham số, exception, context.
- **Tập trung cấu hình**: provider/backend quyết định level, formatter, filter, sink, retention hoặc tích hợp với hệ thống thu thập.
- **Cho phép thay backend trong phạm vi hợp lý**: nhiều lời gọi logging có thể giữ nguyên khi đổi provider, dù cấu hình và các tính năng đặc thù backend vẫn cần điều chỉnh.

Facade **không làm mọi backend có tính năng giống nhau**. Nếu mã ứng dụng ép kiểu SLF4J logger về một class riêng của Logback hoặc gọi API appender trực tiếp, phần đó vẫn phụ thuộc vào Logback. Lợi ích lớn nhất đến từ việc giữ ranh giới giữa **ghi sự kiện** và **cấu hình cách ghi**.

## 3. Phân biệt API, provider, backend và bridge

| Thuật ngữ | Vai trò | Ví dụ |
| --- | --- | --- |
| **Facade/API** | Giao diện mà mã nguồn gọi | `slf4j-api`, `org.slf4j.Logger` |
| **Provider** | Kết nối SLF4J API với phần thực thi logging | `slf4j-simple`, `logback-classic`, `log4j-slf4j2-impl`, `slf4j-jdk14` |
| **Backend** | Lọc sự kiện, format, ghi ra đích, rotation... | Logback, Log4j2, JUL, triển khai đơn giản |
| **Bridge** | Chuyển các sự kiện được phát bằng một API khác vào API/đích đã chọn | `jul-to-slf4j` chuyển JUL API sang SLF4J |

Một số provider chính là backend gọn, như `slf4j-simple`. Với Logback hoặc Log4j2, có nhiều phần triển khai và dependency liên quan. Vì vậy không nên áp một mô hình “một JAR cho mỗi thành phần” vào mọi cấu hình.

### Lựa chọn phổ biến

- **`slf4j-simple`**: tiện cho bài học, chương trình nhỏ; cấu hình và quản lý file hạn chế.
- **Logback Classic**: hỗ trợ appender, encoder, bộ lọc, file rolling và nhiều tính năng vận hành; thường dùng trong hệ sinh thái Spring Boot khi backend được chọn là Logback.
- **Log4j2**: backend khác; khi dùng **SLF4J 2.x** cần provider phù hợp như `log4j-slf4j2-impl`, cùng các thành phần Log4j2 cần thiết.
- **JUL**: có thể nhận sự kiện SLF4J bằng `slf4j-jdk14`; các mức và handler thực tế vẫn thuộc JUL.

Không dùng nhiều provider cạnh tranh chỉ để “chắc chắn có log”: trường hợp này thường dẫn đến cảnh báo và cấu hình khó dự đoán.

## 4. Viết log bằng Logger và LoggerFactory

Mẫu thông dụng là tạo logger theo class:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class PaymentService {
    private static final Logger LOG =
            LoggerFactory.getLogger(PaymentService.class);

    public void process(String paymentId) {
        LOG.info("Processing payment {}", paymentId);
    }
}
```

Đây là **class minh họa**; để biên dịch cần có dependency SLF4J API. `LoggerFactory.getLogger(PaymentService.class)` sử dụng tên class làm logger name, giúp backend cấu hình level theo package hoặc class. `LOG` thường được khai báo `private static final` và dùng lại; không cần tạo một logger cho mỗi request.

### Năm level SLF4J

| Level | Cách dùng điển hình |
| --- | --- |
| `ERROR` | Thao tác thất bại, sự cố đáng báo |
| `WARN` | Tình huống bất thường nhưng có thể phục hồi |
| `INFO` | Mốc vận hành quan trọng như startup, hoàn tất xử lý |
| `DEBUG` | Chi tiết chẩn đoán khi tìm lỗi |
| `TRACE` | Thông tin rất chi tiết của luồng thực thi |

Ví dụ lời gọi:

```java
LOG.error("Unable to complete payment");
LOG.warn("Retry scheduled");
LOG.info("Payment accepted");
LOG.debug("Cache entry found");
LOG.trace("Entered validation branch");
```

**Mức `TRACE` ở đây chỉ là một mức log**; việc bật `LOG.trace(...)` không tự tạo trace/span của distributed tracing.

SLF4J khác JUL ở tên level. JUL có `SEVERE`, `WARNING`, `INFO`, `CONFIG`, `FINE`, `FINER`, `FINEST`. Không viết `java.util.logging.Level.DEBUG` hoặc truyền một `Level` của JUL vào API SLF4J; mỗi hệ API có hợp đồng riêng.

### Placeholder và chi phí tạo message

SLF4J hỗ trợ placeholder `{}`:

```java
LOG.info("Payment {} completed for customer {}", paymentId, customerId);
```

Đoạn này giả định các biến đã được khai báo. Provider format message khi xử lý sự kiện, thường tránh việc nối chuỗi khi level bị tắt.

So sánh:

```java
LOG.debug("Payment details: " + details);
LOG.debug("Payment details: {}", details);
```

Dòng đầu nối chuỗi và có thể gọi `details.toString()` **trước khi** SLF4J kiểm tra level. Dòng thứ hai trì hoãn format object. Tuy nhiên, nếu đối số là một biểu thức gọi hàm:

```java
LOG.debug("Computed state: {}", expensiveStateCalculation());
```

Java **vẫn chạy `expensiveStateCalculation()`** trước khi gọi `debug`, kể cả khi DEBUG bị tắt. Nếu việc tính toán tốn kém, cần dùng `LOG.isDebugEnabled()` hoặc Supplier của fluent API SLF4J 2.x. Không đưa side effect nghiệp vụ quan trọng vào đoạn code chỉ phục vụ logging.

## 5. Ví dụ Java 17 + Maven chạy được

Chương trình sử dụng SLF4J API để ghi log và `slf4j-simple` để hiển thị ra console. Đây là ví dụ **Maven độc lập**, không yêu cầu Spring Boot.

Cấu trúc thư mục:

```text
facade-demo/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── demo/
                └── FacadeDemo.java
```

Tạo file `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>demo</groupId>
    <artifactId>facade-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.17</version>
        </dependency>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-simple</artifactId>
            <version>2.0.17</version>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
            </plugin>
        </plugins>
    </build>
</project>
```

Các phiên bản trên là **một tổ hợp ví dụ cố định**; ứng dụng thật cần đồng bộ phiên bản theo dependency management và khả năng tương thích của backend.

Tạo `src/main/java/demo/FacadeDemo.java`:

```java
package demo;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class FacadeDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(FacadeDemo.class);

    public static void main(String[] args) {
        String orderId = "ORD-7";

        LOG.info("Order {} started", orderId);
        LOG.debug("Checking inventory for {}", orderId);

        try {
            processPayment(orderId);
        } catch (IllegalStateException exception) {
            LOG.error("Order {} could not complete", orderId, exception);
        }

        System.out.println("application-finished");
    }

    private static void processPayment(String orderId) {
        if ("ORD-7".equals(orderId)) {
            throw new IllegalStateException("Payment service unavailable");
        }
    }
}
```

Chạy từ thư mục `facade-demo` với JDK 17+ và Maven:

```bash
mvn -q compile exec:java -Dexec.mainClass=demo.FacadeDemo
```

**Kết quả cần thấy với `slf4j-simple` mặc định:**

1. Log `INFO` có message `Order ORD-7 started`.
2. Log `DEBUG` không xuất ở cấu hình mặc định nhận từ INFO trở lên.
3. Log `ERROR` có message `Order ORD-7 could not complete` cùng `IllegalStateException: Payment service unavailable` và stack trace.
4. Chương trình gọi `System.out.println` một lần, in đúng:

```text
application-finished
```

`slf4j-simple` thường ghi log vào **stderr** với tiền tố level/thread/logger; prefix và stack frame thay đổi theo môi trường nên không có bản output log cố định để so sánh nguyên văn. Dòng `application-finished` là output mà chính chương trình ghi vào stdout, tách khỏi các dòng logging và thông báo của Maven.

**Vì sao mã ứng dụng dùng facade?** File `FacadeDemo.java` chỉ import `org.slf4j.Logger` và `org.slf4j.LoggerFactory`. Nó không gọi class nội bộ của `slf4j-simple`. Đổi provider phù hợp ở dependency runtime có thể giữ nguyên đa số lời gọi `LOG.info/error`; phần cấu hình backend/format cần điều chỉnh riêng.

Với dự án Gradle kiểu Groovy, ý tưởng tương tự là:

```groovy
dependencies {
    implementation 'org.slf4j:slf4j-api:2.0.17'
    runtimeOnly 'org.slf4j:slf4j-simple:2.0.17'
}
```

Đây là **đoạn cấu hình dependency**, cần nằm trong dự án có plugin Java và repository Maven phù hợp.

## 6. SLF4J 2.x tìm provider bằng cách nào?

Trong SLF4J 2.x, `LoggerFactory` sử dụng cơ chế Java `ServiceLoader` để tìm triển khai `org.slf4j.spi.SLF4JServiceProvider` trên runtime classpath/module path. Provider trả về các thành phần như logger factory, nhờ đó lời gọi facade có nơi xử lý thực sự.

```text
Mã ứng dụng: LoggerFactory.getLogger(...)
                     │
                     ▼
                 slf4j-api 2.x
                     │ ServiceLoader
                     ▼
              SLF4JServiceProvider
                     │
                     ▼
              backend / appender
                     │
                     ▼
                  log output
```

**Lưu ý về tương thích phiên bản:** SLF4J **1.7.x** trước đây dùng binding dựa trên `org.slf4j.impl.StaticLoggerBinder`. SLF4J **2.x** dùng provider SPI mới. Một binding 1.7 cũ có thể bị SLF4J 2.x bỏ qua; chỉ thấy JAR tên “slf4j” trên classpath **không đủ** để kết luận đã có provider hợp lệ. Nên thống nhất API/provider theo tài liệu tương thích của phiên bản được triển khai.

### Không có provider

Nếu chỉ thêm `slf4j-api` mà không có provider tương thích, SLF4J 2.x thường cảnh báo tương tự:

```text
SLF4J: No SLF4J providers were found.
SLF4J: Defaulting to no-operation (NOP) logger implementation
```

Dạng thông báo và dấu câu có thể khác theo phiên bản. **NOP** cho phép mã gọi API nhưng không xuất những log như mong muốn. Đây là lý do một chương trình có `LOG.error(...)` vẫn có thể không ghi được thông tin chẩn đoán.

**Khắc phục:** kiểm tra dependency ở runtime và thêm **một provider tương thích**. Một dependency chỉ có `test` scope không đảm bảo production có provider.

### Nhiều provider

Nếu classpath có đồng thời `slf4j-simple` và `logback-classic` cùng cung cấp SLF4J 2.x provider, framework có thể cảnh báo nhiều provider và chọn một. Điều này làm format, đích log và cấu hình thực tế khó dự đoán.

Cách xử lý là kiểm tra dependency tree và loại provider thừa bằng dependency exclusions hoặc cấu hình build phù hợp. Không phụ thuộc vào thứ tự classpath để mong provider cụ thể luôn thắng.

Kiểm tra bằng Maven:

```bash
mvn dependency:tree
```

Có thể in logger factory đang được nạp (đoạn minh họa **bên trong class có import LoggerFactory**):

```java
System.out.println(
        LoggerFactory.getILoggerFactory().getClass().getName());
```

Tên class in ra có ích khi chẩn đoán nhưng không phải một chuỗi cố định cho mọi backend. Khi runtime có nhiều classloader, hãy kiểm tra classpath và provider thực tế của đúng tiến trình đang chạy.

## 7. Provider khác bridge: chú ý hướng chuyển log

Không phải mọi thư viện dùng JUL hay Log4j2 API tự động đi qua SLF4J chỉ vì ứng dụng có `slf4j-api`. Khi cần tập trung sự kiện của API khác vào pipeline chung, có thể cấu hình **bridge**.

```text
Hướng A:
java.util.logging.Logger (JUL API)
             │
             ▼
        jul-to-slf4j
             │
             ▼
          SLF4J API
             │
             ▼
           Logback

Hướng B:
org.slf4j.Logger (SLF4J API)
             │
             ▼
         slf4j-jdk14
             │
             ▼
      JUL Logger / Handler
```

`jul-to-slf4j` chuyển sự kiện JUL sang SLF4J, trong khi `slf4j-jdk14` cung cấp SLF4J bằng backend JUL. **Không kết hợp hai hướng thành vòng lặp**: sự kiện có thể bị chuyển qua lại và gây recursion/stack overflow hoặc các lỗi logging khác. Việc cài bridge JUL có thể cần các bước cài handler/chuyển hướng phù hợp, không phải chỉ thêm dependency thì tất cả log JUL tự động chuyển.

Một ứng dụng nên xác định đường đi rõ ràng từ **API nguồn → bridge (nếu cần) → provider → backend/sink**. Khi dùng Spring Boot hoặc một framework đã tích hợp logging, kiểm tra cấu hình và bridge hiện tại trước khi tự thêm mới.

## 8. Level, định dạng và file log thuộc backend

Mã dùng SLF4J có thể gọi:

```java
LOG.info("Application ready");
LOG.debug("Selected rule {}", ruleName);
LOG.warn("Retry attempt {}", retryCount);
```

Các biến là minh họa. SLF4J định nghĩa các lời gọi và mức log, nhưng backend mới quyết định:

- Logger/package nào đang bật INFO/DEBUG/TRACE.
- Log xuất qua console, file hay gửi tới đích tập trung.
- Formatter/encoder có hiển thị timestamp, thread, logger name, stack trace, MDC hay key–value hay không.
- Chính sách filter, rotation, retention và giới hạn kích thước.

Với provider `slf4j-simple` của ví dụ, có thể tạo `src/main/resources/simplelogger.properties`:

```properties
org.slf4j.simpleLogger.defaultLogLevel=info
org.slf4j.simpleLogger.log.demo=debug
org.slf4j.simpleLogger.showDateTime=false
org.slf4j.simpleLogger.showThreadName=false
org.slf4j.simpleLogger.showLogName=true
```

Dòng `org.slf4j.simpleLogger.log.demo=debug` cho phép package `demo` ghi thêm `DEBUG`, nên ví dụ mục 5 có thêm log `Checking inventory for ORD-7`. File này là cấu hình **riêng của slf4j-simple**; không thể mặc định dùng nó để cấu hình Logback hoặc Log4j2.

SLF4J `org.slf4j.Logger` **không có phương thức chung `setLevel(...)`**. Nếu cần đổi level khi chạy, dùng API/công cụ quản trị của backend hoặc framework đang thực thi. Sửa file cấu hình có tự cập nhật trong JVM hay không cũng phụ thuộc backend và cơ chế reload, không phải cam kết chung của facade.

## 9. API fluent SLF4J 2.x và chi tiết tính toán message

SLF4J 2.x còn có fluent API như `atInfo()`, `atDebug()`, `atError()`, ví dụ minh họa trong class có `LOG`, `orderId`, `attempt`:

```java
LOG.atInfo()
   .addKeyValue("orderId", orderId)
   .addKeyValue("attempt", attempt)
   .log("Order accepted");
```

Các cặp key–value là metadata có thể được backend/encoder thể hiện trong log; gọi `addKeyValue` **không tự động đảm bảo output JSON** hoặc có đủ trường đó ở mọi provider. Luôn kiểm tra kết quả thực tế của provider đang chọn.

Đối với biểu thức tạo chuỗi đắt đỏ, có thể dùng `Supplier`:

```java
LOG.atDebug()
   .addArgument(() -> expensiveDiagnosticText())
   .log("Diagnostics: {}");
```

`expensiveDiagnosticText()` là method minh họa cần tồn tại trong class. Khi DEBUG tắt, builder bị vô hiệu hóa và supplier thường không được tính. **Phải gọi `.log(...)` ở cuối** mới phát sự kiện. Không đặt side effect nghiệp vụ thiết yếu vào supplier phục vụ logging.

### Ghi exception nguyên object

Khi cần stack trace, truyền `Throwable` cho logger:

```java
try {
    processPayment(orderId);
} catch (IllegalStateException exception) {
    LOG.error("Payment {} failed", orderId, exception);
}
```

Đoạn này giả định method và các biến đã tồn tại. Với API SLF4J, throwable ở vị trí cuối trong lời gọi parameterized logging được dùng như exception của sự kiện. Có thể dùng overload rõ ràng:

```java
LOG.error("Payment failed", exception);
```

Tránh chỉ ghi:

```java
LOG.error("Payment failed: {}", exception.getMessage());
```

Cách cuối chỉ gửi **chuỗi message**, không truyền đầy đủ Throwable/cause chain cho backend. Formatter/encoder cũng cần hỗ trợ exception để thực sự xuất stack trace. Nên chọn một boundary thích hợp để log lỗi, tránh in cùng stack trace lặp lại từ repository đến service và handler.

## 10. MDC và thông tin tương quan

Trong server xử lý nhiều request cùng lúc, log có thể xen kẽ khó đọc. SLF4J cung cấp **MDC** (*Mapped Diagnostic Context*) để mã có thể gắn thêm các trường ngữ cảnh như `requestId` hoặc `traceId`.

Ví dụ **minh họa trong class đã khai báo LOG** và dùng backend có hỗ trợ MDC:

```java
import org.slf4j.MDC;

try (MDC.MDCCloseable ignored =
        MDC.putCloseable("requestId", "REQ-204")) {
    LOG.info("Validating request");
    LOG.info("Request accepted");
}
```

Các import ở đầu file, code nằm trong method. `putCloseable` giúp dọn context sau khối `try`, giảm nguy cơ rò ngữ cảnh giữa request. **Không phải provider nào cũng hỗ trợ và xuất MDC giống nhau**; muốn thấy `requestId` phải có MDC adapter/backend phù hợp và formatter/encoder được cấu hình để hiển thị.

Trong xử lý bất đồng bộ hoặc thread pool, MDC có thể cần được truyền qua ranh giới tác vụ; không giả định một context gắn ở thread ban đầu tự đi theo mọi `CompletableFuture`. `traceId` trong log hỗ trợ liên kết với hệ thống tracing khi đã cấu hình tracing, nhưng **SLF4J không tự tạo distributed trace/span**.

Không ghi mật khẩu, token, API key, cookie, dữ liệu thẻ hay thông tin cá nhân nhạy cảm vào message hoặc MDC. Logging thường được thu thập và lưu lâu hơn vòng đời request.

## 11. Thư viện nên phụ thuộc vào API; ứng dụng chọn provider

Ví dụ một thư viện dùng `org.slf4j.Logger`:

```java
public class LibraryJob {
    private static final org.slf4j.Logger LOG =
            org.slf4j.LoggerFactory.getLogger(LibraryJob.class);

    public void run() {
        LOG.info("Library job started");
    }
}
```

Thư viện cần có `slf4j-api` để biên dịch, còn ứng dụng cuối có thể chọn Logback, Log4j2 hoặc JUL qua provider tương thích. Điều đó tránh việc một thư viện vô tình buộc mọi ứng dụng dùng một backend cố định.

Ví dụ dependency Gradle **minh họa cho multi-project** có plugin `java-library`:

```groovy
// Thư viện:
dependencies {
    implementation 'org.slf4j:slf4j-api:2.0.17'
}

// Ứng dụng:
dependencies {
    implementation project(':logging-library')
    runtimeOnly 'org.slf4j:slf4j-simple:2.0.17'
}
```

Đây là các snippet của **hai module khác nhau**; cần có `repositories` và module `:logging-library` hợp lệ trong dự án thật. Nếu API công khai của thư viện lộ kiểu SLF4J, có thể cần `api` thay vì `implementation`. Nguyên tắc chính là **ứng dụng chịu trách nhiệm chọn provider**, còn thư viện không tự mang provider logging riêng khi không có lý do rõ ràng.

## 12. Các lỗi hay gặp và hướng chẩn đoán

| Hiện tượng | Nguyên nhân có thể | Cách kiểm tra/sửa |
| --- | --- | --- |
| Có `LOG.error(...)` nhưng không có dòng log | Thiếu provider SLF4J ở runtime, fallback NOP | Đọc cảnh báo khởi động; thêm provider tương thích |
| Cảnh báo nhiều provider | Classpath có nhiều implementation cạnh tranh | Kiểm tra dependency tree; giữ một provider chính |
| API SLF4J 2.x nhưng chỉ thấy binding 1.7 | `StaticLoggerBinder` không phải cơ chế provider 2.x | Thay bằng provider 2.x tương thích |
| Đổi `logback.xml` nhưng không thấy tác dụng | Backend được nạp không phải Logback hoặc config sai | In logger factory, xác nhận dependency và config thực tế |
| `LOG.debug(...)` không xuất | Backend đang lọc ở INFO/WARN hoặc logger không đúng tên | Kiểm tra level và logger name của backend |
| Log có message nhưng mất stack trace | Chỉ truyền `getMessage()` hoặc encoder bỏ Throwable | Truyền nguyên exception; kiểm tra format |
| Exception xuất nhiều lần | Nhiều layer log lại hoặc nhiều appender/bridge | Xác định nơi log một lỗi và đường định tuyến |
| JUL log nằm ngoài pipeline | Chưa cấu hình bridge từ JUL sang SLF4J | Kiểm tra `jul-to-slf4j` và chiều định tuyến |
| Vòng lặp khi tích hợp | Dùng bridge SLF4J→JUL và JUL→SLF4J đồng thời | Giữ một hướng phù hợp |
| MDC không xuất trong log | Provider/encoder không hỗ trợ hoặc chưa cấu hình | Kiểm tra MDC adapter và pattern/encoder |
| Gọi `LOG.setLevel(...)` lỗi biên dịch | `org.slf4j.Logger` không có API đó | Dùng công cụ/API backend |
| Tốn CPU dù DEBUG đang tắt | Đối số method được tính trước khi gọi LOG | Dùng guard hoặc supplier khi cần |

Quy trình kiểm tra gọn:

1. Xác nhận mã dùng `org.slf4j.Logger` hay một API khác.
2. Kiểm tra `slf4j-api` và **provider tại runtime**, đặc biệt những dependency gián tiếp.
3. Xác định provider thực sự được nạp; sửa cảnh báo không có hoặc nhiều provider.
4. Xác nhận level, logger name, filter và formatter của backend.
5. Xác nhận log đến đúng console/file/collector và không bị rotation, quyền ghi hoặc retention làm mất.
6. Kiểm tra bridge nếu có các thư viện phát log qua JUL/Log4j2 API.
7. Dùng một message INFO và một exception ERROR thử nghiệm trong môi trường kiểm soát.

## 13. Câu hỏi tự kiểm tra

**Câu 1:** Tại sao SLF4J được gọi là facade?  
**Đáp án:** Vì nó cung cấp API thống nhất mà mã nguồn dùng để ghi log, còn provider/backend thực hiện việc lọc, format và xuất sự kiện.

**Câu 2:** Chỉ thêm `slf4j-api` có bảo đảm thấy log trên console?  
**Đáp án:** Không. Cần provider runtime tương thích; nếu thiếu, SLF4J 2.x thường dùng NOP và cảnh báo.

**Câu 3:** Có nên thêm `slf4j-simple` và `logback-classic` cùng lúc?  
**Đáp án:** Thông thường không; một tiến trình nên có một provider chính, tránh cảnh báo và provider được chọn ngoài ý muốn.

**Câu 4:** `LOG.debug("{}", expensiveMethod())` có tránh chạy `expensiveMethod()` khi DEBUG tắt không?  
**Đáp án:** Không. Java tính đối số trước lời gọi; dùng guard hoặc fluent Supplier nếu cần hoãn tính.

**Câu 5:** `LOG.atInfo().addKeyValue(...).log(...)` có tự bảo đảm xuất JSON không?  
**Đáp án:** Không. Kết quả phụ thuộc provider/encoder; metadata gắn vào sự kiện không tự quyết định format.

**Câu 6:** `jul-to-slf4j` và `slf4j-jdk14` khác nhau thế nào?  
**Đáp án:** Cái đầu chuyển sự kiện JUL sang SLF4J; cái sau thực thi SLF4J bằng JUL. Tránh cấu hình vòng lặp hai chiều.

**Câu 7:** Library Java nên chọn provider hay ứng dụng cuối chọn?  
**Đáp án:** Thông thường library chỉ dùng API facade, còn ứng dụng cuối chọn provider và cấu hình logging tương ứng.

**Ghi nhớ:** **SLF4J tách API ghi log khỏi backend thực thi.** Nắm rõ ba vai trò **facade – provider – bridge** giúp bạn xây dựng thư viện dễ tái sử dụng, chọn một pipeline log nhất quán và chẩn đoán đúng khi bản ghi bị thiếu hoặc xuất trùng.
