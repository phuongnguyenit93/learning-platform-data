# Appender trong Log4j2: khái niệm, cấu hình và thực hành

**Appender** trong **Apache Log4j 2 Core** là thành phần nhận một sự kiện log (`LogEvent`) và **xuất sự kiện đó ra một đích hoặc chuyển tiếp qua một cơ chế xử lý**. Đích có thể là stdout/stderr, một tệp, tệp luân phiên (*rolling file*), appender bất đồng bộ, hoặc hệ thống nhận log khác. Trong hệ thống Java, logger là nơi ứng dụng *phát sự kiện*; appender quyết định *đưa sự kiện đã được chấp nhận đi đâu*. `Layout` quyết định hình thức nội dung; `Filter` có thể giới hạn bản ghi tới đích.

Ví dụ: `LOG.info("event=order.accepted orderId={}", orderId)` phát một sự kiện. Log4j2 có thể gửi cùng event ấy đến console để collector thu thập và đến tệp để lưu cục bộ mà ứng dụng không cần gọi `info(...)` hai lần.

## 1. Appender nằm ở đâu trong kiến trúc Log4j2?

```text
Ứng dụng Java
    |
    | org.apache.logging.log4j.Logger.info(...)
    v
Log4j API
    |
    v
Log4j Core: LoggerContext / LoggerConfig
    |  level, filter, additivity
    v
LogEvent
    |
    +---- AppenderRef --> ConsoleAppender --> Layout --> stdout/stderr
    |
    +---- AppenderRef --> RollingFileAppender
                           |        |
                           |        +-- rollover policies / strategy
                           +--> Layout --> file hiện tại
```

Sơ đồ trên để làm rõ trách nhiệm; cơ chế lọc và luồng xử lý chi tiết còn phụ thuộc cấu hình. Trong hệ thống Log4j2 thường gặp các thành phần:

| Thành phần | Trách nhiệm | Ví dụ |
| --- | --- | --- |
| `Logger` | API mà code dùng để phát event, có tên ổn định. | `LogManager.getLogger(OrderService.class)` |
| `LoggerConfig` | Quy tắc level, filter, additivity và tham chiếu appender cho một namespace. | `<Logger name="demo.orders" level="DEBUG">` |
| `LogEvent` | Sự kiện mang thời gian, level, logger name, message, Throwable, context. | `event=payment.failed paymentId=42` |
| `AppenderRef` | Nối LoggerConfig/root với appender được đặt tên; có thể có filter hoặc level riêng. | `<AppenderRef ref="STDOUT"/>` |
| `Appender` | Xuất/chuyển event đến đích. | `Console`, `File`, `RollingFile`, `Async` |
| `Layout` | Định dạng event; có thể biểu diễn thành text/JSON khi dùng module phù hợp. | `PatternLayout` |
| `Filter` | Chấp nhận hoặc từ chối event ở tầng được gắn. | `ThresholdFilter` |
| `TriggeringPolicy` | Quy định lúc nào cần rollover. | `SizeBasedTriggeringPolicy` |
| `RolloverStrategy` | Quản lý các thế hệ file khi rollover. | `DefaultRolloverStrategy` |

**Không nhầm API và backend:** `log4j-api` chứa `Logger`, `LogManager` mà code nghiệp vụ thường gọi; `log4j-core` cung cấp implementation và các appender thông dụng. Nếu code gọi SLF4J thì cần provider/bridge tương thích để chuyển tới Log4j2; chỉ thêm `log4j-core` không có nghĩa tự động chuyển tất cả JUL hay SLF4J log qua nó.

## 2. Appender được định nghĩa và được sử dụng thế nào?

Cấu hình Log4j2 thường đặt trong `src/main/resources/log4j2.xml` (classpath). Một mẫu tối giản:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="STDOUT" target="SYSTEM_OUT">
            <PatternLayout pattern="%level | %logger | %msg%n"/>
        </Console>
    </Appenders>

    <Loggers>
        <Root level="INFO">
            <AppenderRef ref="STDOUT"/>
        </Root>
    </Loggers>
</Configuration>
```

Ý nghĩa:

1. `<Appenders>` khai báo các đích xuất có tên; `STDOUT` là **tên appender**, không phải tên logger.
2. `<Console>` chọn đầu ra `SYSTEM_OUT`, còn `PatternLayout` cho dạng một dòng.
3. `<Root level="INFO">` là cấu hình logger gốc; các logger không có level riêng thường kế thừa từ root.
4. `<AppenderRef ref="STDOUT"/>` nối root với appender đã khai báo.
5. **Chỉ khai báo appender không đủ**: cần appender reference từ logger/root tương ứng.
6. Nếu một event bị loại vì level ở logger hoặc filter, việc appender cho phép level thấp hơn không thể khôi phục event đã bị loại.

Trong chương trình, dùng logger theo class:

```java
// Đoạn minh họa trong một class, cần dependency log4j-api.
private static final org.apache.logging.log4j.Logger LOG =
        org.apache.logging.log4j.LogManager.getLogger(OrderService.class);

void accept(String orderId) {
    LOG.info("event=order.accepted orderId={}", orderId);
}
```

Đây là **đoạn minh họa**, giả định có class `OrderService` và tham số đầu vào phù hợp; phần thực hành chạy độc lập nằm ở mục 7.

## 3. ConsoleAppender: ghi ra stdout hoặc stderr

Đầu ra console hữu ích trong môi trường container/kubernetes vì collector thường thu thập stdout và stderr:

```xml
<Console name="STDOUT" target="SYSTEM_OUT">
    <PatternLayout pattern="%d{ISO8601} %-5p %c - %m%n"/>
</Console>
```

- `target="SYSTEM_OUT"` ghi ra stdout; `SYSTEM_ERR` dành cho stderr.
- `%d` là thời gian của event, `%p` là level, `%c` là logger name, `%m` là message, `%n` là ký tự xuống dòng.
- Formatter có thể có timestamp, thread, correlation ID, exception; lựa chọn dựa trên hệ thống thu thập.
- Ghi ra console không tự bảo đảm collector thực sự thu hoặc giữ được mọi sự kiện. Cần kiểm tra cấu hình hạ tầng.

**Khi nào chọn:** ứng dụng container đã có nền tảng tập trung thu log, CLI tool hoặc dịch vụ không muốn tự quản lý file. Không nên ghi ra console **và** file cục bộ chỉ vì thói quen nếu việc đó gây tăng I/O và dữ liệu trùng.

## 4. FileAppender: ghi vào một tệp xác định

```xml
<File name="FILE" fileName="logs/application.log" append="true">
    <PatternLayout pattern="%d{ISO8601} %-5p %c - %m%n"/>
</File>
```

`FileAppender` ghi trực tiếp đến tệp ở `fileName`. Một số điểm quan trọng:

- Đường dẫn tương đối dựa trên **working directory của tiến trình**; có thể khác giữa IDE, Maven, service launcher và container.
- `append="true"` tiếp tục file hiện có khi mở; `append="false"` có thể thay nội dung cũ khi handler khởi tạo.
- Tiến trình cần quyền tạo/mở file, dung lượng ổ đĩa và quyền truy cập phù hợp.
- Khi file viết thất bại, cơ chế báo lỗi thuộc pipeline Log4j Core; không giả định mọi `LOG.info(...)` sẽ ném exception nghiệp vụ.
- `FileAppender` không tự có chính sách rotation theo thời gian/kích thước. Nếu lưu lượng cao, file có thể tăng vô hạn.

Trong container không dùng volume, file có thể mất khi instance bị thay thế. Đối với hệ thống nhiều replica, không cho tất cả JVM cùng ghi vào một đường dẫn chia sẻ nếu chưa thiết kế cơ chế phối hợp, vì thứ tự event và an toàn ghi file không mặc nhiên được bảo đảm.

## 5. RollingFileAppender: luân phiên file theo chính sách

`RollingFileAppender` kết hợp file đang ghi với một hoặc nhiều **triggering policies** và **rollover strategy**. Ví dụ cấu hình sau là một appender hợp lệ để đặt trong `<Appenders>`, sau đó cần tham chiếu bằng `AppenderRef`:

```xml
<RollingFile name="ROLLING"
             fileName="logs/application.log"
             filePattern="logs/archive/application-%d{yyyy-MM-dd}-%i.log.gz">
    <PatternLayout pattern="%d{ISO8601} %-5p %c - %m%ex%n"/>

    <Policies>
        <TimeBasedTriggeringPolicy interval="1"/>
        <SizeBasedTriggeringPolicy size="10 MB"/>
    </Policies>

    <DefaultRolloverStrategy max="7"/>
</RollingFile>
```

| Thành phần | Chức năng |
| --- | --- |
| `fileName` | File đang hoạt động, ví dụ `logs/application.log`. |
| `filePattern` | Mẫu tên file lịch sử; `%d` theo kỳ thời gian, `%i` để phân biệt nhiều lần rollover trong một kỳ. |
| `.gz` | Hậu tố cho file được nén theo pattern lịch sử. |
| `TimeBasedTriggeringPolicy` | Kích hoạt rollover khi đến kỳ thời gian phù hợp; thường được kiểm tra khi có event ghi, không có nghĩa tự chạy đúng 00:00 nếu ứng dụng không log. |
| `SizeBasedTriggeringPolicy` | Kích hoạt theo kích thước file; đơn vị ví dụ `10 MB`. |
| `DefaultRolloverStrategy max="7"` | Giới hạn chỉ số/thế hệ theo chiến lược rollover, **không phải giữ đúng bảy ngày**. |

Đối với file lớn, một event có thể khiến tệp vượt ngưỡng ít nhiều trước khi rollover, vì vậy `10 MB` không phải hạn mức tuyệt đối cho mỗi byte đã ghi.

**Phân biệt rotation và retention:** Rotation tạo thế hệ file mới, còn retention quy định bao lâu/tổng dung lượng nào được giữ. `max="7"` không thay thế chính sách dọn file lịch sử theo tuổi và dung lượng. Cần kiểm tra tốc độ sinh log, chính sách cleanup, nén, quyền truy cập và backup nếu hệ thống cần lịch sử dài hạn.

Khi dùng nhiều appender hoặc nhiều tiến trình, tổng dung lượng file có thể lớn hơn tưởng tượng từ một cấu hình rolling. Nếu muốn rotation theo ngày, dung lượng và xóa sau một khoảng thời gian, cần đặt các policy/strategy và điều kiện delete phù hợp, kiểm thử với phiên bản Log4j2 thực tế.

## 6. Các appender khác và khi nào dùng

| Appender | Đặc trưng | Điều cần cân nhắc |
| --- | --- | --- |
| `RandomAccessFileAppender` | Triển khai ghi file dùng mô hình random-access/buffering. | Kiểm tra khả năng flush, chi phí I/O và đúng API cấu hình của phiên bản. |
| `RollingRandomAccessFileAppender` | Kết hợp random-access và file rollover. | Không mặc định tốt hơn RollingFile trong mọi môi trường; cần benchmark. |
| `AsyncAppender` | Queue event rồi chuyển đến một appender phía sau. | Queue đầy, blocking/dropping, shutdown và nguy cơ mất log. |
| `RoutingAppender` | Định tuyến event dựa trên context/route key. | Nếu khóa theo request ID có cardinality cao sẽ làm bùng nổ appender/file. |
| `FailoverAppender` | Có thể chuyển sang đích dự phòng khi primary appender báo lỗi theo hợp đồng. | Không thay thế journal/audit có cam kết bền vững. |
| `SocketAppender` | Gửi log đến nơi nhận qua mạng. | Kiểm soát an ninh, độ tin cậy, TLS, mất kết nối và dữ liệu truyền. |

Một số loại appender/layout cần module hoặc plugin bổ sung; không phải mọi tính năng tồn tại trong cùng một artifact hay mọi phiên bản Log4j2. Trước khi lựa chọn, kiểm tra tài liệu phù hợp version, tính bảo mật của đích và đặc tính tải.

### AsyncAppender và AsyncLogger không phải một

`AsyncAppender` là appender có hàng đợi và chuyển tiếp tới đích:

```xml
<!-- Đoạn minh họa: appender FILE đã được khai báo. -->
<Async name="ASYNC">
    <AppenderRef ref="FILE"/>
</Async>
```

Sau đó root/logger có thể tham chiếu `ASYNC` thay vì `FILE`. Nếu tham chiếu cả hai trên cùng một đường đi, một event có thể bị ghi hai lần. Khi queue đầy, tùy thuộc cấu hình và chính sách có thể block caller hoặc loại bớt event; sự kiện trong queue chưa được flush có thể mất khi tiến trình chết.

**AsyncLogger** là mô hình bất đồng bộ tại tầng logger/logging context và khác loại với `AsyncAppender`. Tùy cách sử dụng, nó có yêu cầu dependency và cấu hình riêng. Không kết luận sử dụng bất đồng bộ đồng nghĩa với ghi bền hoặc đảm bảo thứ tự tuyệt đối giữa nhiều tiến trình.

## 7. Thực hành Java 17: gửi một event đến console và file

Mục tiêu bài thực hành: phân biệt **hai appender cho cùng một event**, effective level và `additivity`. Mã ứng dụng chỉ gọi Log4j API; Log4j Core dùng `log4j2.xml` để xuất log ra console và tệp. Bài dùng **JDK 17 + Maven**.

Phiên bản Log4j2 **2.24.3** được cố định để ví dụ dễ tái lập, **không khẳng định là bản mới nhất**. Với dự án thực, phải chọn version còn được hỗ trợ, cập nhật bảo mật và tương thích với toàn bộ dependency của hệ thống.

### 7.1. Cấu trúc dự án

```text
log4j2-appender-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── demo/
        │       └── AppenderDemo.java
        └── resources/
            └── log4j2.xml
```

### 7.3. src/main/resources/log4j2.xml

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="STDOUT" target="SYSTEM_OUT">
            <PatternLayout pattern="%p | %c | %m%n"/>
        </Console>
        <File name="FILE"
              fileName="target/logs/application.log"
              append="false">
            <PatternLayout pattern="%p | %c | %m%n"/>
        </File>
    </Appenders>

    <Loggers>
        <Logger name="demo.orders" level="DEBUG"
                additivity="false">
            <AppenderRef ref="STDOUT"/>
            <AppenderRef ref="FILE"/>
        </Logger>

        <Root level="INFO">
            <AppenderRef ref="STDOUT"/>
            <AppenderRef ref="FILE"/>
        </Root>
    </Loggers>
</Configuration>
```

Cấu hình này có:

- **ConsoleAppender** ghi stdout và **FileAppender** ghi `target/logs/application.log`; hai layout giống nhau.
- LoggerConfig `demo.orders` ở DEBUG, có hai appender riêng và `additivity="false"` để không tiếp tục chuyển event đến appender của root.
- Root ở INFO, cũng có hai AppenderRef; nhóm billing kế thừa root INFO.
- `append="false"` để file demo được ghi mới sau mỗi lượt chạy; không nên tự động chọn cho hệ thống thật nếu phải giữ lịch sử sau restart.
- File có đường dẫn tương đối tới working directory; cần quyền tạo/ghi thư mục. Khi lỗi file, kiểm tra diagnostic của Log4j Core thay vì giả định file luôn được tạo.

### 7.4. src/main/java/demo/AppenderDemo.java

```java
package demo;

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class AppenderDemo {
    private static final Logger ORDERS =
            LogManager.getLogger("demo.orders.OrderService");
    private static final Logger BILLING =
            LogManager.getLogger("demo.billing.PaymentService");

    public static void main(String[] args) {
        ORDERS.debug("event=order.validated orderId={}", "ord-42");
        ORDERS.info("event=order.accepted orderId={}", "ord-42");

        // Logger BILLING kế thừa INFO từ Root.
        BILLING.debug("event=payment.internal_check");
        BILLING.warn(
                "event=payment.retry paymentId={} attempt={}",
                "pay-7",
                2
        );

        ORDERS.error(
                "event=order.failed orderId={} reason={}",
                "ord-99",
                "timeout"
        );

        // Dừng context ở cuối chương trình demo để flush/close appender.
        LogManager.shutdown();
    }
}
```

### 7.5. Biên dịch, chạy và đối chiếu

Đứng tại thư mục chứa `pom.xml`:

```bash
mvn -q compile exec:java
```

**Bốn dòng log trên standard output do chương trình phát ra**, không tính thông báo hoặc cảnh báo riêng của Maven/môi trường nếu có:

```text
DEBUG | demo.orders.OrderService | event=order.validated orderId=ord-42
INFO | demo.orders.OrderService | event=order.accepted orderId=ord-42
WARN | demo.billing.PaymentService | event=payment.retry paymentId=pay-7 attempt=2
ERROR | demo.orders.OrderService | event=order.failed orderId=ord-99 reason=timeout
```

Khi cấu hình được nạp và file mở thành công, **`target/logs/application.log` chứa cùng bốn dòng log**. `BILLING.debug(...)` bị loại ở root/effective level INFO nên không xuất ra console lẫn file.

Giải thích rõ các đường đi:

1. `ORDERS` có namespace `demo.orders.OrderService` và nhận effective level DEBUG từ `demo.orders`.
2. LoggerConfig `demo.orders` tham chiếu hai appender, khiến một event được xuất tới **hai sink riêng biệt**.
3. `additivity="false"` ngăn event của orders tiếp tục đi tới các appender ở root, tránh bị ghi hai lần vào chính cùng đích.
4. `BILLING` không có cấu hình riêng, kế thừa INFO từ root nên DEBUG bị loại nhưng WARN được nhận.
5. Pattern `%p | %c | %m%n` không phụ thuộc timestamp/thread, giúp expected output ổn định.
6. `LogManager.shutdown()` chỉ đặt ở cuối chương trình demo; một ứng dụng server phải giữ logging context sống đến lúc shutdown của ứng dụng, không dừng sau mỗi request.

Nếu đọc file không thấy bốn dòng, kiểm tra đường dẫn tương đối, quyền ghi, file `log4j2.xml` trên classpath, hiệu lực LoggerConfig và status log nội bộ. Không chỉnh level của event chỉ để “ép” nó qua cấu hình sai.

## 8. Log level, AppenderRef và Filter

Một event có thể bị loại ở một trong nhiều tầng:

```text
LOG.debug(...)
    |
    +-- Logger/LoggerConfig chấp nhận? -- không --> bỏ qua
    |
    v
AppenderRef có level/filter cho phép? -- không --> bỏ qua tại ref
    |
    v
Appender filter cho phép? -- không --> bỏ qua tại appender
    |
    v
Layout --> xuất log
```

Ví dụ cùng root INFO nhưng chỉ gửi WARN trở lên đến file:

```xml
<!-- Đoạn minh họa; STDOUT và FILE phải được khai báo trước. -->
<Root level="INFO">
    <AppenderRef ref="STDOUT"/>
    <AppenderRef ref="FILE" level="WARN"/>
</Root>
```

Hoặc appender có filter riêng:

```xml
<Console name="WARN_ONLY" target="SYSTEM_OUT">
    <ThresholdFilter level="WARN"
                     onMatch="ACCEPT"
                     onMismatch="DENY"/>
    <PatternLayout pattern="%p | %m%n"/>
</Console>
```

Một DEBUG event bị logger INFO loại không thể được “cứu” bởi appender chấp nhận DEBUG. Ngược lại, một event đã được logger DEBUG chấp nhận vẫn có thể bị AppenderRef hoặc Appender filter loại. Không nhầm **root level** với việc filter lại mọi event đã được namespace con chấp nhận trên đường truyền đến appender root.

**Additivity** chỉ điều khiển việc truyền event đến appender của ancestor LoggerConfig, **không đồng nghĩa với ngắt kế thừa level** của các logger con.

## 9. Layout, exception và structured logging

Với `PatternLayout`, các ký hiệu thường gặp:

| Pattern | Dữ liệu đầu ra |
| --- | --- |
| `%d{ISO8601}` | Thời điểm event (cần cấu hình timezone nhất quán khi vận hành phân tán). |
| `%-5p` | Level căn trái, tối thiểu năm ký tự. |
| `%c` / `%logger` | Tên logger. |
| `%t` | Tên thread. |
| `%m` / `%msg` | Message sau khi format tham số `{}`. |
| `%ex` | Dữ liệu Throwable/stack trace khi record có ngoại lệ. |
| `%X{requestId}` | Trường `requestId` từ ThreadContext khi tồn tại. |
| `%n` | Dấu xuống dòng phù hợp nền tảng. |

Appender không thay đổi ý nghĩa level hay message. Pattern chỉ là hình thức xuất; `%m` ghi text không tự biến event thành JSON có field riêng. Khi cần phân tích theo trường hoặc lưu vào hệ thống observability, sử dụng layout có khả năng structured output tương thích, ví dụ `JsonTemplateLayout` với dependency/template phù hợp.

Khi log exception:

```java
// Đoạn mã minh họa trong một catch; LOG và orderId đã tồn tại.
catch (RuntimeException ex) {
    LOG.error("event=order.failed orderId={}", orderId, ex);
    throw ex;
}
```

Đối tượng `Throwable` cuối cho phép Log4j2 gắn exception vào `LogEvent`. Nếu chỉ nối `ex.getMessage()` vào chuỗi, có thể mất stack trace và chuỗi cause. Layout/pipeline phải được kiểm chứng với exception thật để biết đã hiển thị đầy đủ hay chưa. Chỉ log rồi ném lại khi tầng này thực sự chịu trách nhiệm, tránh nhiều tầng cùng ghi một lỗi thành nhiều bản ghi ERROR.

Thông tin exception có thể chứa dữ liệu nhạy cảm; tránh ghi mật khẩu, token, cookie, private key, toàn bộ payload người dùng hoặc URL có bí mật ở mọi mức log. Với dữ liệu chưa đáng tin cậy có ký tự điều khiển, dùng encoder/escaping và giới hạn chiều dài thay vì tự ghép JSON thủ công.

## 10. ThreadContext và RoutingAppender

Log4j2 cung cấp `ThreadContext` cho dữ liệu ngữ cảnh như `requestId` hoặc `traceId`:

```java
// Đoạn minh họa trong method; LOG, requestId, orderId đã có.
org.apache.logging.log4j.ThreadContext.put("requestId", requestId);
try {
    LOG.info("event=order.accepted orderId={}", orderId);
} finally {
    org.apache.logging.log4j.ThreadContext.remove("requestId");
}
```

Trong pattern có thể thêm `%X{requestId}`. Context gắn với luồng/thực thi không mặc nhiên đi theo tất cả tác vụ qua `ExecutorService`, `CompletableFuture`, reactive pipeline hay virtual thread. Khi chuyển luồng cần cơ chế propagation phù hợp; luôn dọn context để không lẫn dữ liệu request khác.

`RoutingAppender` có thể chọn appender đích dựa trên context hoặc thuộc tính sự kiện. Nhưng **không tạo một file/appender mới cho mọi request ID** nếu không có cơ chế kiểm soát cardinality và dọn dẹp: điều đó có thể làm cạn file descriptor, đầy đĩa và tăng chi phí cấu hình. Thông thường, giữ logger/appender ổn định, đưa request ID vào field để hệ thống tập trung truy vấn.

## 11. Tình huống vận hành cần lưu ý

### Lỗi ghi vào sink

Appender không phải giao dịch cơ sở dữ liệu. Nếu ổ đĩa đầy, stream lỗi hoặc mạng mất kết nối, Log4j Core có cơ chế báo lỗi nội bộ và cấu hình hành vi lỗi. Không coi việc `LOG.info(...)` chạy xong là bằng chứng log đã được lưu bền. Với yêu cầu độ bền cao, thiết kế pipeline bền vững riêng, giám sát việc thu log và thử lỗi sink trong môi trường kiểm thử.

### Queue bất đồng bộ

Bật AsyncAppender có thể cải thiện latency ở một số tải nhưng tăng khả năng mất event trong queue lúc process chết; khi đầy queue tùy cấu hình có thể chặn hoặc drop. Cần benchmark, thử graceful shutdown, xem metric của logging pipeline và đánh giá chính sách bỏ event. Không dùng async logging thông thường làm audit trail bắt buộc không mất.

### File và container

File bên trong container có thể mất khi container bị thay thế. Nếu dùng file, cần volume, quyền ghi, retention, collector và chiến lược rotation rõ. Khi nhiều replica hoạt động, không dựa vào một đường dẫn file chung để có thứ tự log toàn cục.

### Bảo mật và phiên bản

Giữ Log4j2 ở bản đã vá và tương thích với Java/backend hiện tại. Không cho nguồn dữ liệu không đáng tin cậy điều khiển tên file, đường dẫn, route, cấu hình plugin hoặc thông tin nhạy cảm trong message. Xem xét quyền đọc file log và dữ liệu exception/stack trace trước khi gửi đến bên thứ ba.

## 12. Lỗi thường gặp

| Hiện tượng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Không có dòng log | Appender chưa được tham chiếu, config XML chưa nạp hoặc logger level loại event. | Kiểm tra classpath, `AppenderRef`, tên appender, LoggerConfig, status output. |
| Console có log nhưng file trống | FileAppender không được gắn hoặc mở file thất bại. | Kiểm tra path, working directory, quyền ghi, appender reference. |
| DEBUG không xuất hiện | Effective level hoặc filter ở logger/ref/appender chặn. | Kiểm tra từng tầng lọc thay vì đổi level sự kiện tùy tiện. |
| Log bị in trùng | Gắn cùng appender ở logger con và root, additivity bật, hoặc có hai pipeline. | Rà LoggerConfig, `additivity` và AppenderRef. |
| File log tăng mãi | Dùng FileAppender không có rotation. | Dùng RollingFileAppender cùng policy phù hợp. |
| File cũ biến mất quá nhanh | Rollover index/chính sách retention chưa theo lưu lượng. | Kiểm tra max strategy, filePattern, cleanup và dung lượng tổng. |
| Không có stack trace | Chỉ ghi `ex.getMessage()` hoặc layout/pipeline không xuất Throwable. | Truyền exception đúng API, kiểm tra `%ex`. |
| File không có JSON dù đuôi .json | Layout tạo text thường. | Dùng structured layout phù hợp, không chỉ đổi phần mở rộng. |
| Async bị thiếu event | Queue quá tải, drop policy hoặc process dừng bất thường. | Đo lường queue, cấu hình block/drop và graceful shutdown. |
| Log của request A lẫn request B | ThreadContext không được clear/propagate đúng. | Dọn `ThreadContext` trong `finally`, propagation khi đổi luồng. |
| Routing tạo rất nhiều file | Route key có cardinality quá cao (request/user ID). | Thiết kế khóa phân vùng hữu hạn, kiểm soát lifecycle appender. |
| Log4j API không dùng Log4j Core | Dependency thiếu/lệch phiên bản hoặc bridge/backend khác. | Kiểm tra `log4j-api` + `log4j-core`, dependency tree và provider thực tế. |

## 13. Checklist khi thiết kế Appender

1. **Đúng đích:** Console, File, RollingFile hay Async phục vụ nhu cầu nào? Có collector tập trung không?
2. **Kết nối:** Appender có tên hợp lệ và được tham chiếu đúng qua `AppenderRef` chưa?
3. **Ngưỡng lọc:** Logger/effective level, AppenderRef và Appender filter có thống nhất không?
4. **Additivity:** Một event có cần xuất nhiều sink, hay đang bị nhân bản ngoài ý muốn?
5. **Layout:** Có đủ timestamp, timezone, level, logger, request ID, exception và format đọc được không?
6. **Rotation/retention:** File có giới hạn và chính sách giữ/xóa rõ ràng, không mặc định `max` là số ngày?
7. **Hiệu năng:** I/O, Async queue, lưu lượng và chi phí có được đo trên tải thực không?
8. **An toàn:** Token, dữ liệu cá nhân, exception và input có ký tự điều khiển đã được kiểm soát?
9. **Khả năng chịu lỗi:** Hệ thống theo dõi lỗi sink và không coi log thông thường là giao dịch lưu bền?
10. **Kiểm chứng:** Đã chạy ví dụ/kiểm thử INFO-DEBUG-WARN-ERROR, mở file và thử tình huống thiếu quyền/rollover chưa?

**Ghi nhớ:** **Logger/LoggerConfig** chọn và định tuyến sự kiện; **AppenderRef** nối cấu hình logger với một đích; **Appender** ghi/chuyển sự kiện; **Layout** định dạng; **Filter** loại record; các chính sách rolling/async quyết định hành vi bổ sung. Hiểu đúng ranh giới này giúp hệ thống Java ghi log hữu ích mà không trùng, không mất ngữ cảnh và không tạo chi phí vận hành ngoài dự kiến.
