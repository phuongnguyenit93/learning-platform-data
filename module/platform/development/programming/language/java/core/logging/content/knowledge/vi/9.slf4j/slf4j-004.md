# SLF4J API trong Java

## 1. SLF4J giải quyết vấn đề gì?

Một ứng dụng Java thường có mã nghiệp vụ, tầng truy cập dữ liệu, HTTP client và nhiều thư viện bên ngoài. Nếu mỗi thành phần trực tiếp phụ thuộc vào một hệ thống ghi log khác nhau, việc thay đổi nơi xuất log, mức ghi hoặc định dạng sẽ khó quản lý.

**SLF4J (Simple Logging Facade for Java)** cung cấp một **giao diện lập trình (API) thống nhất** để mã Java ghi log. Mã ứng dụng thường làm việc với `org.slf4j.Logger` và `org.slf4j.LoggerFactory`, trong khi một **provider/backend** ở lúc chạy thực hiện việc ghi thật.

Ví dụ lời gọi trong một lớp Java:

```java
private static final org.slf4j.Logger LOG =
        org.slf4j.LoggerFactory.getLogger(OrderService.class);

LOG.info("event=order_created order_id={}", orderId);
```

Đây là **mã minh họa bên trong lớp `OrderService`**, chưa phải chương trình độc lập. Mã gọi SLF4J API để biểu đạt sự kiện; nó chưa quyết định log đi tới file, console hay hệ thống tập trung.

Mô hình:

```text
Mã Java (OrderService, PaymentService, ...)
                 |
                 v
             SLF4J API
       Logger / LoggerFactory
                 |
                 v
     Provider / Logging backend
   (Logback, slf4j-simple, ...)
                 |
                 v
    Formatter / Appender / Filter
                 |
          +------+------+
          |             |
          v             v
       Console         File / collector
```

**Facade khác với backend:** SLF4J API định nghĩa cách *gọi* logging; backend quyết định cách *thực hiện*. Chỉ có `slf4j-api` chưa có nghĩa chương trình sẽ tạo file log. Với SLF4J 2.x, chương trình cần một provider tương thích ở runtime để xuất các sự kiện theo mong muốn.

## 2. Các thành phần quan trọng trong API

| Thành phần | Vai trò |
| --- | --- |
| `org.slf4j.Logger` | Giao diện ghi log: `trace`, `debug`, `info`, `warn`, `error` |
| `org.slf4j.LoggerFactory` | Lấy logger theo tên hoặc theo lớp |
| `org.slf4j.Marker` | Nhãn sự kiện phục vụ lọc/phân loại khi backend hỗ trợ |
| `org.slf4j.MarkerFactory` | Tạo hoặc tìm marker theo tên |
| `org.slf4j.MDC` | Ngữ cảnh chẩn đoán chứa các cặp khóa–giá trị của luồng xử lý, tùy khả năng backend/adapter |
| `org.slf4j.event.Level` | Kiểu biểu diễn mức log cho các API cần một giá trị level |
| `org.slf4j.spi.LoggingEventBuilder` | Giao diện xây sự kiện theo cú pháp fluent, có từ SLF4J 2.x |

Phần lớn code nghiệp vụ chỉ cần `LoggerFactory` và `Logger`. Marker, MDC, fluent builder và trường dữ liệu có cấu trúc được dùng khi có yêu cầu truy vết hoặc vận hành cụ thể.

Vì SLF4J là một API, backend có thể thay đổi mà những lời gọi `LOG.info(...)` vẫn giữ nguyên. Tuy nhiên **khả năng hiển thị key-value, MDC, caller location, cách format stack trace và mức lọc** có thể khác giữa các provider. Việc thay backend vẫn cần kiểm chứng cấu hình và đầu ra.

## 3. Lấy logger theo lớp bằng `LoggerFactory`

Trong lớp Java thông thường, dùng:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class OrderService {
    private static final Logger LOG =
            LoggerFactory.getLogger(OrderService.class);

    public void create(String orderId) {
        LOG.info("event=order_created order_id={}", orderId);
    }
}
```

Đoạn này là **một lớp hợp lệ khi đã có SLF4J API trên classpath**, nhưng chưa có `main`. Những ý chính:

- `LoggerFactory.getLogger(OrderService.class)` lấy logger có tên gắn với lớp. Với package, tên thường là tên lớp đầy đủ như `com.example.orders.OrderService`.
- `private static final` giữ tham chiếu logger tại cấp lớp, cho phép nhiều đối tượng `OrderService` dùng chung.
- Mỗi lần gọi `create` vẫn truyền `orderId` riêng. Việc chia sẻ logger **không có nghĩa** chia sẻ mã đơn hàng hoặc dữ liệu request.
- Mã nghiệp vụ không cần tạo logger mới cho từng đơn hàng, không cần thêm appender cho từng request và không nên tự thay đổi cấu hình log toàn cục trong phương thức xử lý.

Có thể lấy logger theo một tên chuỗi bằng `LoggerFactory.getLogger("com.example.order")`. Cách theo lớp thường dễ nhận diện nguồn phát và hỗ trợ lọc theo package; tên tùy chỉnh phù hợp khi dự án cần một nhóm sự kiện đặc biệt.

Đừng tạo một logger mang tên động như `"order." + orderId` cho từng đơn hàng. Logger name nên là danh tính của **nguồn phát**; `order_id` và `correlation_id` là thuộc tính của **bản ghi**.

## 4. Năm mức log trong SLF4J

| Mức | Ý nghĩa tham khảo | Ví dụ |
| --- | --- | --- |
| `ERROR` | Lỗi ngoài dự kiến hoặc thất bại quan trọng cần điều tra | Không thể lưu đơn hàng dù đã thử khôi phục |
| `WARN` | Suy giảm hoặc bất thường có thể ảnh hưởng hệ thống | Cache lỗi, hệ thống sử dụng đường dự phòng |
| `INFO` | Sự kiện bình thường có giá trị vận hành | Đơn hàng được tạo hoặc bị từ chối đúng quy tắc |
| `DEBUG` | Chi tiết kỹ thuật phục vụ điều tra | Lựa chọn nhánh xử lý, kết quả kiểm tra nội bộ |
| `TRACE` | Chi tiết rất sâu của luồng thực thi | Các bước nhỏ thường chỉ cần khi chẩn đoán |

Tương ứng là `LOG.error`, `LOG.warn`, `LOG.info`, `LOG.debug`, `LOG.trace`. SLF4J `Logger` chuẩn **không có phương thức `fatal`**, cũng không dùng `Level.SEVERE` của `java.util.logging` (JUL).

**Chọn mức theo tác động, không chỉ theo sự tồn tại của exception.** Một lần thanh toán bị ngân hàng từ chối có thể là kết quả `INFO`. Một lần retry thất bại nhưng yêu cầu sau đó vẫn thành công có thể là `WARN` hoặc `DEBUG`. Khi toàn bộ thao tác quan trọng thất bại ngoài dự kiến, `ERROR` thường phù hợp.

Gọi `LOG.error` không tự động rollback transaction, ném lại exception hay trả HTTP 500. Logging chỉ ghi nhận sự kiện; luồng xử lý lỗi vẫn phải được thực hiện trong code.

Khi backend đặt ngưỡng thông thường là `INFO`, `DEBUG` và `TRACE` có thể bị lọc. Một appender/filter khác cũng có thể lọc thêm, nên **gọi API không bảo đảm bản ghi sẽ đến mọi đích**.

## 5. Ghi message có tham số bằng `{}`

SLF4J hỗ trợ **parameterized logging**: dùng thông điệp mẫu cố định và truyền các giá trị thay đổi thành tham số.

```java
LOG.info("event=order_created order_id={}", orderId);

LOG.warn("event=dependency_slow service={} duration_ms={}",
        serviceName, durationMs);

LOG.debug("event=page_loaded page={} count={}",
        page, count);
```

Đây là ba lời gọi minh họa bên trong một lớp đã có `LOG`. Ký hiệu `{}` là **placeholder của SLF4J**, không phải cú pháp `String.format` hoặc `MessageFormat`. Với JUL, placeholder tham số thường có dạng `{0}`, `{1}`; không dùng lẫn hai kiểu.

So sánh:

```java
// Chuỗi được tạo bởi phép nối ở phía mã gọi:
LOG.debug("order=" + orderId + ", state=" + state);

// SLF4J nhận template và đối số riêng:
LOG.debug("order={} state={}", orderId, state);
```

Cách thứ hai giúp thông điệp có một mẫu ổn định và có thể tránh việc format sớm khi mức `DEBUG` tắt. Nó cũng giúp người phát triển dễ thống nhất tên `event` và tên trường trong nhiều vị trí code.

Một số nguyên tắc:

1. Số vị trí `{}` nên phù hợp số tham số dùng để định dạng. Rà soát message khi thêm/bỏ trường.
2. Giá trị `null` được xử lý qua API/backend; đừng tự tạo thông điệp mơ hồ khi có thể dùng mã kết quả rõ ràng.
3. Tham số động không đồng nghĩa dữ liệu an toàn. Một chuỗi chứa xuống dòng vẫn có thể gây **log injection** nếu encoder không escape đúng.
4. `{}` không tự biến câu log thành **structured JSON**. Đầu ra chỉ có trường dữ liệu riêng khi backend/encoder hoặc pipeline có hỗ trợ tương ứng.
5. Không ghi mật khẩu, token, OTP, số thẻ đầy đủ hoặc dữ liệu cá nhân nhạy cảm vào tham số.

Message template ổn định không có nghĩa mọi nghiệp vụ phải dùng cùng một câu chung chung. `order_created` và `order_cancelled` là hai sự kiện khác nghĩa; chúng cần tên sự kiện phản ánh đúng điều đã xảy ra.

## 6. Ví dụ Java 17+ chạy với Maven và SLF4J 2.x

SLF4J là thư viện ngoài JDK. Ví dụ này sử dụng bản `2.0.16` cho cả `slf4j-api` và `slf4j-simple` để dễ tái lập, **không khẳng định đây là phiên bản mới nhất**. `slf4j-simple` là provider nhỏ, thích hợp minh họa lời gọi API.

Cấu trúc dự án:

```text
slf4j-api-demo/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── example/
                └── logging/
                    └── Slf4jApiDemo.java
```

Nội dung `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>example.logging</groupId>
    <artifactId>slf4j-api-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.16</version>
        </dependency>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-simple</artifactId>
            <version>2.0.16</version>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
                <configuration>
                    <release>17</release>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

Nội dung `src/main/java/example/logging/Slf4jApiDemo.java`:

```java
package example.logging;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class Slf4jApiDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(Slf4jApiDemo.class);

    private Slf4jApiDemo() {
    }

    private static void checkout(String orderId, boolean approved) {
        LOG.info("event=checkout_started order_id={}", orderId);

        if (!approved) {
            LOG.info(
                    "event=payment_declined order_id={} reason_code={}",
                    orderId, "CARD_EXPIRED");
            return;
        }

        LOG.atInfo()
                .addArgument(orderId)
                .log("event=payment_authorized order_id={}");
    }

    public static void main(String[] args) {
        checkout("ORD-101", true);
        checkout("ORD-102", false);
        System.out.println("flow_finished");
    }
}
```

Để biên dịch, từ thư mục `slf4j-api-demo`, dùng JDK 17+ và Maven:

```bash
mvn -q -DskipTests package
mvn -q org.apache.maven.plugins:maven-dependency-plugin:3.7.1:copy-dependencies -DoutputDirectory=target/dependency
```

Chạy trên Linux/macOS:

```bash
java -cp "target/classes:target/dependency/*" example.logging.Slf4jApiDemo
```

Chạy trên Windows (classpath dùng dấu `;`):

```powershell
java -cp "target\classes;target\dependency\*" example.logging.Slf4jApiDemo
```

Maven cần tải dependency/plugin ở lần đầu nếu máy chưa có trong cache. Lệnh chạy cần cả API và provider ở classpath. Không thêm một provider khác bên cạnh `slf4j-simple` trong bài tập này.

**Stdout chính xác của chương trình:**

```text
flow_finished
```

Với `slf4j-simple` mặc định chấp nhận `INFO`, các phần **message** sau được ghi lần lượt ra stderr. Provider có thể thêm tên thread, mức log, tên logger và các thông tin tiền tố; những dòng sau **chỉ là phần message**, không khẳng định định dạng toàn dòng:

```text
event=checkout_started order_id=ORD-101
event=payment_authorized order_id=ORD-101
event=checkout_started order_id=ORD-102
event=payment_declined order_id=ORD-102 reason_code=CARD_EXPIRED
```

Terminal có thể hiển thị stdout và stderr cùng nhau mà không bảo đảm thứ tự xen kẽ. Chương trình mô phỏng nhánh nghiệp vụ, không kết nối cổng thanh toán hay database: các sự kiện minh họa **đường đi của code**, không chứng minh đã phát sinh giao dịch thực.

Điểm đáng quan sát:

- Cả hai lượt `checkout` dùng cùng một logger theo lớp.
- `LOG.info("...{}", orderId)` và `LOG.atInfo().addArgument(orderId).log("...{}")` tạo thông điệp với tham số cùng nguyên tắc.
- `payment_declined` là một kết quả được mô phỏng là bình thường, nên dùng `INFO`.
- `slf4j-simple` là provider được chọn để cho log xuất hiện mà không cần viết appender riêng.

## 7. Chọn provider đúng với SLF4J API

Một số phương án runtime:

| Thành phần | Chức năng |
| --- | --- |
| `slf4j-api` | Giao diện cho mã Java gọi logging; tự nó không chọn đích lưu |
| `slf4j-simple` | Provider đơn giản, thích hợp ví dụ và ứng dụng nhỏ |
| `logback-classic` phiên bản tương thích | Provider với các khả năng cấu hình logging của Logback |
| `slf4j-jdk14` | Provider đưa lời gọi SLF4J tới JUL |
| `log4j-slf4j2-impl` phiên bản tương thích | Provider đưa SLF4J 2.x tới backend Log4j 2 |

Trong một ứng dụng, nên có **một provider chủ đích**. Nếu có nhiều provider trên classpath, SLF4J có thể cảnh báo và chọn một trong số đó; đừng phụ thuộc vào thứ tự lựa chọn.

Với **SLF4J 2.x**, provider được phát hiện thông qua cơ chế dịch vụ của Java (`ServiceLoader`). **SLF4J 1.7** trước đây dùng binding với `org.slf4j.impl.StaticLoggerBinder`. Một binding 1.7 không tự trở thành provider đúng chuẩn 2.x; cần đồng bộ phiên bản API/provider.

Nếu chỉ có `slf4j-api` 2.x mà không tìm thấy provider phù hợp, SLF4J có thể thông báo ở lúc khởi tạo rồi sử dụng logger **NOP (no-operation)**. Khi đó code vẫn có thể chạy nhưng lời gọi `info`/`warn` không tạo ra log ứng dụng như mong đợi.

Nếu ứng dụng có framework như Spring Boot, logging provider có thể đã được đưa vào qua starter/dependency management. Trước khi thêm `slf4j-simple` hoặc Logback thủ công, cần xem phần phụ thuộc runtime hiện có của dự án để tránh nhiều provider.

## 8. Các overload của `Logger` và Throwable

SLF4J cung cấp các dạng lời gọi:

```java
LOG.info("Start processing");
LOG.info("order_id={}", orderId);
LOG.warn("service={} attempt={}", serviceName, attempt);
LOG.error("event=order_save_failed order_id={}", orderId, error);
```

Đây là mã minh họa trong một lớp có `LOG`. `error` ở dòng cuối giả định `error` là một đối tượng `Throwable`. Trong những overload phù hợp, Throwable ở đối số cuối được tách khỏi các đối số format để provider có thể hiển thị stack trace.

So sánh hai cách:

```java
// Không truyền Throwable, chỉ truyền String:
LOG.error("save failed: {}", error.getMessage());

// Truyền Throwable để backend có thể ghi stack trace:
LOG.error("save failed for order_id={}", orderId, error);
```

Lời gọi thứ nhất có thể mất stack trace và cause chain. Lời gọi thứ hai giữ đối tượng exception trong sự kiện logging, tùy khả năng hiển thị của provider.

**Ghi một exception ở đúng ranh giới.** Nếu tầng repository, service và controller đều `LOG.error(..., e)` rồi ném tiếp, cùng một lỗi có thể sinh nhiều bản ghi `ERROR`. Thường nên chọn nơi biết kết quả cuối của request/job, giữ cause khi chuyển ngoại lệ giữa tầng và ghi log có đủ ngữ cảnh tại ranh giới chịu trách nhiệm.

Câu lệnh log không thay thế xử lý exception. Nếu bước bắt buộc thất bại, ứng dụng vẫn phải trả trạng thái lỗi, retry, rollback hoặc ném tiếp theo hợp đồng nghiệp vụ. Việc đã ghi `ERROR` không khiến Java tự dừng.

## 9. Fluent logging trong SLF4J 2.x

SLF4J 2.x bổ sung cách xây dựng một sự kiện qua builder:

```java
LOG.atInfo()
        .addArgument(orderId)
        .log("event=order_created order_id={}");
```

- `atInfo()` chọn mức `INFO`.
- `addArgument(orderId)` bổ sung đối số thay placeholder.
- `log(...)` **phát sự kiện**. Nếu không gọi `log` thì chưa hoàn tất lời gọi logging.

Những phương thức quan trọng:

| API fluent | Tác dụng |
| --- | --- |
| `atTrace()`, `atDebug()`, `atInfo()`, `atWarn()`, `atError()` | Bắt đầu builder theo mức |
| `atLevel(org.slf4j.event.Level.INFO)` | Chọn mức qua enum |
| `setMessage("...")` | Đặt thông điệp |
| `addArgument(value)` | Thêm đối số định dạng |
| `addArgument(() -> expensive())` | Trì hoãn tạo đối số bằng supplier |
| `addKeyValue("order_id", id)` | Gắn thuộc tính khóa–giá trị vào event |
| `addMarker(marker)` | Gắn marker |
| `setCause(throwable)` | Gắn exception |
| `log()` / `log("...")` | Hoàn tất lời gọi |

Ví dụ có Throwable:

```java
LOG.atError()
        .addArgument(orderId)
        .setCause(error)
        .log("event=order_save_failed order_id={}");
```

Ví dụ truyền key-value:

```java
LOG.atInfo()
        .addKeyValue("event", "order_created")
        .addKeyValue("order_id", orderId)
        .addKeyValue("outcome", "SUCCESS")
        .log("Order created");
```

**Không nhầm `addKeyValue` với việc xuất JSON tự động.** Builder có thể đưa thuộc tính vào sự kiện, nhưng provider/encoder/collector quyết định thuộc tính đó được hiển thị hoặc lưu thành trường riêng hay không. Muốn hệ thống tập trung tìm kiếm được `order_id`, hãy kiểm tra dữ liệu đầu ra thật của pipeline.

## 10. Hiệu năng: parameterization và cách tính tham số

Một hiểu nhầm phổ biến là `LOG.debug("{}", expensive())` không tốn chi phí khi DEBUG bị tắt. Thực tế, **Java đánh giá đối số trước khi gọi phương thức**.

```java
// expensive() chạy trước cả khi DEBUG bị tắt:
LOG.debug("snapshot={}", expensive());

// Cách thứ nhất: kiểm tra mức trước:
if (LOG.isDebugEnabled()) {
    LOG.debug("snapshot={}", expensive());
}

// Cách thứ hai: supplier với SLF4J 2.x:
LOG.atDebug()
        .addArgument(() -> expensive())
        .log("snapshot={}");
```

Các đoạn trên là mẫu dùng bên trong lớp có `LOG` và `expensive()`. Supplier giúp hoãn tính dữ liệu nếu mức log không được bật. Chỉ dùng cách phức tạp hơn khi phép tạo dữ liệu thực sự đáng kể; ghi một ID hoặc số nguyên thông thường không cần tối ưu quá mức.

Đừng đưa side effect nghiệp vụ vào supplier: nếu log bị vô hiệu hóa, supplier có thể không chạy. Tính đúng đắn của giao dịch phải độc lập với việc log có bật hay không.

Tối ưu logging còn liên quan tới độ dài message, việc gọi `toString()` của object, formatter, đồng bộ, I/O, buffer, mạng và chi phí lưu trữ. Không lấy số lần gọi `LoggerFactory` làm thước đo duy nhất về hiệu năng.

## 11. `Marker`: gắn nhãn sự kiện

`Marker` giúp nhận diện các nhóm sự kiện theo chính sách:

```java
import org.slf4j.Marker;
import org.slf4j.MarkerFactory;

Marker security = MarkerFactory.getMarker("SECURITY");
LOG.warn(security, "event=login_blocked reason_code={}",
        "TOO_MANY_ATTEMPTS");
```

Đây là mã minh họa trong một lớp có `LOG`. Marker `SECURITY` **không tự làm** message trở thành bản ghi audit bất biến hoặc tự chuyển log sang file bảo mật. Backend/filter cần được cấu hình để dùng marker.

Với fluent API:

```java
LOG.atWarn()
        .addMarker(security)
        .addKeyValue("reason_code", "TOO_MANY_ATTEMPTS")
        .log("event=login_blocked");
```

Marker nên là tên phân loại ổn định như `SECURITY` hoặc `AUDIT`. Không tạo marker mới cho mọi `orderId`, `requestId` hoặc số tài khoản. Những giá trị thay đổi nên là trường dữ liệu của từng sự kiện.

## 12. `MDC`: gắn mã tương quan cho một luồng xử lý

**Mapped Diagnostic Context (MDC)** là API hỗ trợ những thuộc tính chẩn đoán theo ngữ cảnh thực thi, chẳng hạn mã yêu cầu, mã tương quan và mã tác vụ.

Ví dụ trong một lớp đã có `LOG`:

```java
import org.slf4j.MDC;

void process(String requestId, String orderId) {
    try (MDC.MDCCloseable ignored =
                 MDC.putCloseable("request_id", requestId)) {
        LOG.info("event=order_received order_id={}", orderId);
        LOG.info("event=order_checked order_id={}", orderId);
    }
}
```

Đây là **đoạn phương thức minh họa**, không phải chương trình chạy độc lập. Khi đóng `MDCCloseable`, khóa đã đặt được **xóa** khỏi context; phương thức này không tự khôi phục giá trị cũ của cùng khóa. Nếu lồng nhiều phạm vi với cùng khóa, cần cơ chế lưu và khôi phục phù hợp.

Những giới hạn quan trọng:

- MDC là **ngữ cảnh**; không phải biến nằm trong logger `static final`.
- Backend/adapter phải hỗ trợ MDC và encoder phải được cấu hình để xuất các trường đó. Không phải provider nào cũng in MDC.
- Thread pool tái sử dụng thread: phải dọn context, tránh request sau mang metadata cũ.
- Khi xử lý bất đồng bộ hoặc đổi thread, context không nhất thiết tự truyền theo. Cần truyền `correlation_id` bằng cơ chế framework hỗ trợ hoặc tường minh.
- Không ghi mật khẩu, token hoặc thông tin nhạy cảm vào MDC; chúng có thể đi qua nhiều hệ thống thu thập.

Nếu hai lượt xử lý cùng một đơn hàng, `order_id` có thể giống nhau nhưng `request_id` khác nhau. Mã đơn hàng giúp tìm vòng đời đối tượng; mã request giúp phân biệt từng lần thực thi.

## 13. Bridge khác với provider

Một dự án có thể chứa thư viện gọi JUL hoặc Log4j 2 API thay vì SLF4J. **Bridge** chuyển sự kiện từ API này sang API khác. **Provider** thực thi log nhận được từ SLF4J.

```text
Mã dùng SLF4J ----------------> SLF4J API ---> Provider ---> Đích
Thư viện dùng JUL ---> JUL-to-SLF4J ---------> Provider ---> Đích
```

Một số ví dụ:

| Thư viện | Chiều chuyển log |
| --- | --- |
| `jul-to-slf4j` | JUL → SLF4J, khi đã cài bridge đúng |
| `jcl-over-slf4j` | Commons Logging API → SLF4J |
| `log4j-to-slf4j` | Log4j 2 API → SLF4J |
| `slf4j-jdk14` | SLF4J → JUL, đóng vai trò provider |
| `log4j-slf4j2-impl` | SLF4J 2.x → Log4j 2, đóng vai trò provider |

Không cấu hình bridge hai chiều như **JUL → SLF4J** đồng thời chọn **SLF4J → JUL** làm provider. Tương tự, cần tránh tạo vòng lặp giữa Log4j 2 API và provider SLF4J → Log4j 2. Vòng lặp có thể gây log lặp hoặc lỗi khởi tạo.

Một library dùng SLF4J API thường **không nên ép ứng dụng cuối dùng một backend cụ thể**. Ứng dụng quyết định provider, còn bridge do tầng cấu hình hệ thống quản lý. Trong Spring Boot hay ứng dụng có bộ starter, cần xem dependency logging đã có trước khi thêm adapter khác.

## 14. Log có cấu trúc và message ổn định

Mã nguồn có thể phát một message dạng:

```java
LOG.info("event=payment_declined order_id={} reason_code={}",
        orderId, "CARD_EXPIRED");
```

Một nền tảng log tập trung có thể mong đợi dữ liệu cấu trúc:

```json
{
  "timestamp": "2026-11-09T12:00:00Z",
  "level": "INFO",
  "service": "checkout-service",
  "event": "payment_declined",
  "order_id": "ORD-102",
  "reason_code": "CARD_EXPIRED",
  "correlation_id": "req-7a"
}
```

Đây là **JSON minh họa**, không phải output mặc định của `slf4j-simple` hay bảo đảm của `LOG.info`. Muốn đầu ra dạng này cần backend, encoder hoặc collector được cấu hình phù hợp.

Cách thiết kế có giá trị:

1. Giữ `event` ổn định, dùng tên biểu thị đúng sự kiện xảy ra.
2. Dùng `reason_code` nằm trong một tập mã được quản lý; không phụ thuộc nguyên văn thông báo từ thư viện bên ngoài.
3. Có tên trường và đơn vị rõ ràng như `duration_ms`, tránh khi thì giây, khi thì mili giây.
4. Truyền `request_id`/`correlation_id` có vòng đời đúng để tìm toàn bộ log thuộc một lượt xử lý.
5. Phân biệt một lần thử lại với kết quả cuối: nhiều dòng log không mặc nhiên là nhiều giao dịch thành công.
6. Tránh lấy log làm nguồn duy nhất của số liệu tài chính, kiểm toán hoặc trạng thái dữ liệu chính thức.

Việc thay tên `event` hoặc đổi đơn vị một trường đang được dashboard sử dụng có thể làm hỏng truy vấn và cảnh báo; hãy xem các trường này như hợp đồng quan sát hệ thống.

## 15. An toàn dữ liệu và xử lý lỗi ở ranh giới

Logging API có nhiều overload tiện lợi, nhưng không tự bảo đảm dữ liệu ghi ra luôn an toàn:

- Không đưa password, API key, token, OTP, số thẻ hoặc toàn bộ request/response vào log.
- Giá trị đầu vào chứa xuống dòng, ký tự điều khiển hay dấu phân cách cần được xử lý bởi encoder/formatter phù hợp để tránh **log injection**.
- Exception message có thể chứa URL nội bộ, dữ liệu người dùng hoặc mã truy cập; đừng mặc định `e.getMessage()` là dữ liệu vô hại.
- Mức log bật quá chi tiết có thể tạo lưu lượng lớn và tăng chi phí lưu trữ; theo dõi retention và quyền truy cập ở hệ thống đích.
- Ghi log ở đúng nơi quyết định kết quả cuối, hạn chế nhiều stack trace cho một thất bại.

Sự khác nhau giữa event nghiệp vụ và event kỹ thuật vẫn quan trọng. Ví dụ thẻ đã hết hạn là kết quả có thể dự kiến; lỗi mất kết nối cổng thanh toán trong lúc thanh toán có thể là sự cố kỹ thuật. Đặt đúng `event`/`reason_code` và level giúp người vận hành biết phải hành động như thế nào.

## 16. Những lỗi SLF4J API thường gặp

**Lỗi 1 — chỉ khai báo API mà quên provider:** code biên dịch, nhưng không thấy sự kiện. Xem thông báo khởi tạo SLF4J và cấu hình dependency runtime.

**Lỗi 2 — thêm nhiều provider:** classpath có `slf4j-simple` và Logback cùng lúc. Chọn một provider phù hợp.

**Lỗi 3 — dùng binding SLF4J 1.7 với API 2.x:** cách phát hiện provider khác nhau. Đồng bộ dependency và loại binding cũ không phù hợp.

**Lỗi 4 — nhầm `{}` với `{0}`:** SLF4J và JUL có cú pháp khác nhau; message có thể hiện nguyên placeholder.

**Lỗi 5 — chỉ truyền `error.getMessage()`:** mất đối tượng Throwable cho việc in stack trace. Dùng overload có Throwable hoặc `setCause`.

**Lỗi 6 — tính dữ liệu đắt trước khi kiểm tra level:** `LOG.debug("{}", expensive())` vẫn đánh giá đối số. Dùng `isDebugEnabled()` hoặc fluent supplier khi đáng giá.

**Lỗi 7 — quên `log()` trong fluent API:** builder không tự phát sự kiện nếu chưa gọi phương thức kết thúc.

**Lỗi 8 — nghĩ `addKeyValue` luôn ra JSON:** phải có backend/encoder và kiểm tra pipeline.

**Lỗi 9 — để context request trong trường `static`:** có thể lẫn dữ liệu giữa các thread. Dùng tham số hoặc MDC đúng vòng đời.

**Lỗi 10 — không xóa MDC khi request kết thúc:** thread pool có thể mang ngữ cảnh cũ vào yêu cầu mới.

**Lỗi 11 — thêm bridge hai chiều:** log có thể quay vòng hoặc lặp vô hạn. Kiểm tra chiều chuyển của từng adapter/provider.

**Lỗi 12 — coi marker `AUDIT` là sổ kiểm toán:** marker chỉ là metadata; yêu cầu kiểm toán và bảo toàn dữ liệu cần hệ thống riêng.

## 17. Chọn API theo nhu cầu

| Nhu cầu | Cách gọi gợi ý |
| --- | --- |
| Ghi sự kiện thông thường | `LOG.info("event=order_created id={}", id)` |
| Ghi suy giảm cần theo dõi | `LOG.warn("event=cache_unavailable cache={}", cache)` |
| Ghi thất bại cuối kèm exception | `LOG.error("event=save_failed id={}", id, e)` |
| Ghi chi tiết kỹ thuật | `LOG.debug("step={} count={}", step, count)` |
| Tránh tạo dữ liệu đắt khi DEBUG tắt | `LOG.atDebug().addArgument(() -> expensive()).log("data={}")` |
| Gắn trường cho backend hỗ trợ | `LOG.atInfo().addKeyValue("order_id", id).log("created")` |
| Gắn nhãn sự kiện | `LOG.warn(marker, "event=security_alert")` |
| Gắn mã theo request | `MDC.putCloseable("request_id", id)` kèm phạm vi `try` |
| Đặt tên logger ổn định theo lớp | `LoggerFactory.getLogger(MyClass.class)` |

Đây là các lời gọi minh họa; những biến như `id`, `e`, `marker` hay `expensive` cần được khai báo tương ứng. Chọn API phù hợp là bước đầu, còn mức log, cấu hình provider và xử lý dữ liệu quyết định khả năng quan sát thực tế.

## 18. Tự kiểm tra kiến thức

1. **SLF4J có phải một backend tự ghi file log không?** Không. Nó là API; backend/provider thực hiện ghi log.
2. **Lấy logger theo lớp bằng phương thức nào?** `LoggerFactory.getLogger(MyClass.class)`.
3. **SLF4J dùng placeholder gì cho tham số?** `{}`, không phải `{0}` của JUL.
4. **`LOG.error(...)` có tự ném exception không?** Không. Đó là lời gọi logging.
5. **Không có provider trong SLF4J 2.x thì có thể xảy ra gì?** Có cảnh báo khởi tạo và logger NOP, không xuất các sự kiện như mong muốn.
6. **Có nên đưa hai provider vào cùng runtime?** Thường không; chọn một provider chủ đích.
7. **`LOG.error("{}", e.getMessage())` có giữ đối tượng `Throwable` không?** Không. Khi cần stack trace, truyền `e` bằng overload thích hợp hoặc `setCause`.
8. **Trong fluent API, `LOG.atInfo().addArgument(id)` đã ghi chưa?** Chưa, cần gọi `log(...)`.
9. **`addKeyValue` có tự động tạo JSON không?** Không. Cần provider/encoder tương thích.
10. **MDC có phải dữ liệu nằm trong logger `static final` không?** Không. Đây là ngữ cảnh xử lý cần quản lý vòng đời.
11. **Nếu `DEBUG` tắt, `LOG.debug("{}", expensive())` có tính `expensive()` không?** Có, vì Java tính đối số trước khi gọi.
12. **Có thể dùng bridge JUL → SLF4J cùng provider SLF4J → JUL không?** Không nên, vì tạo chiều chuyển vòng lặp.
13. **Marker `SECURITY` có tự bảo đảm log là audit trail không?** Không. Marker chỉ giúp phân loại sự kiện.
14. **Vì sao nên giữ tên `event` và `reason_code` ổn định?** Để truy vấn, cảnh báo, thống kê và so sánh giữa các bản triển khai ít bị phá vỡ.
15. **Có thể dựa vào số dòng `payment_authorized` để kết luận số giao dịch được ghi nhận chính thức không?** Không; log có thể mất, trùng hoặc đến chậm. Phải đối chiếu trạng thái nghiệp vụ thực.

**Ghi nhớ:** dùng `Logger` và `LoggerFactory` để mã Java ghi log qua một API nhất quán. Chọn một provider SLF4J 2.x phù hợp ở runtime; dùng `{}` với tham số, chọn level theo ý nghĩa, truyền `Throwable` khi cần, tận dụng fluent API, Marker và MDC có kiểm soát. Khả năng ghi, định dạng, lưu giữ và tìm kiếm log thuộc trách nhiệm của backend và hạ tầng quan sát.
