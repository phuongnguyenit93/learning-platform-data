# Request-Scoped MDC in Java Logging: Attaching requestId, Context Propagation, and Preventing Thread Leakage

## 1. What Is Request-Scoped MDC?

**MDC** (*Mapped Diagnostic Context*) is a set of **string key–value** pairs associated with an execution context by the logging backend. When applying **request-scoped MDC**, the system places fields such as `requestId`, `correlationId`, `traceId`, or `operation` at the request-receiving boundary so that log statements in deeper layers automatically carry that correlation information, without needing to pass `requestId` into every `LOG.info(...)` call.

Example of two requests passing through a service simultaneously:

~~~text
requestId=req-A level=INFO  logger=OrderController msg="request received"
requestId=req-B level=INFO  logger=OrderController msg="request received"
requestId=req-A level=INFO  logger=OrderService    msg="inventory reserved"
requestId=req-B level=WARN  logger=PaymentService  msg="retry scheduled"
requestId=req-A level=INFO  logger=OrderController msg="request completed"
~~~

By looking at `requestId`, an investigator can group related logs even though they are interleaved across multiple threads and Java classes.

**MDC is not a request object and does not automatically create a distributed trace.** It is a way to enrich **log events** with context. To track a request across multiple services, you must ensure the ID is propagated across HTTP/message boundaries and logging is configured in each service; if you want to analyze causal relationships, duration, and spans, you need a dedicated distributed tracing mechanism.

**Distinguish between two core concerns:**

- **MDC scope:** when a request starts, fields are set; when it finishes or throws an exception, the MDC must be cleared/restored.
- **MDC propagation:** when processing jumps from the request-receiving thread to a thread pool, `CompletableFuture`, scheduler, or callback, the MDC must be passed and applied on the appropriate execution thread. MDC generally does not automatically cross every asynchronous boundary.

These two concerns are independent. An application might clean up the request thread very well yet still **lose `requestId`** in a worker; or propagate it properly to the worker yet forget to clean up, causing the next request to have the **wrong `requestId`**.

## 2. Where Does MDC Fit in the Logging Flow?

In the **SLF4J + Logback** ecosystem, applications typically call these APIs:

~~~java
// Snippet inside a method with SLF4J/Logback on the classpath.
org.slf4j.MDC.put("requestId", "req-A");
LOG.info("operation=checkout phase=started");
org.slf4j.MDC.remove("requestId");
~~~

MDC is read at the time the log event is created/prepared according to the backend mechanism, after which the layout/encoder can output that value into a text line or JSON.

~~~text
HTTP request / background job
          |
          v
[Boundary: select and validate requestId]
          |
          v
[MDC.put("requestId", requestId)]
          |
          +----> Controller LOG.info("received")
          |
          +----> Service    LOG.info("processing")
          |
          +----> Repository LOG.warn("retry")
          |
          +----> Async task [need to copy/install context on worker]
          |
          v
[Boundary finally: remove/clear/restore MDC]
          |
          v
Thread returns to thread pool, ready for another request
~~~

**Components to distinguish:**

- **SLF4J MDC API:** `org.slf4j.MDC.put`, `get`, `remove`, `clear`, `getCopyOfContextMap`, and `setContextMap`.
- **Backend:** Logback Classic provides the MDC storage/semantics that logging events can use. Other backends/providers have varying levels of MDC support.
- **Layout/encoder:** Logback's `PatternLayout` has `%X{requestId}` to retrieve the value. If the pattern does not print MDC, calling `MDC.put(...)` **does not automatically make `requestId` appear** on the console.
- **Collector:** needs to parse text or receive structured fields from an encoder to search by `requestId`.

### 2.1. MDC Is Typically Thread-Bound, Not a Global Map

Suppose thread `http-1` is processing `req-A` while `http-2` is processing `req-B`. Each thread needs its own corresponding MDC. An MDC value can be used by multiple loggers on the same thread without passing it as a parameter to every business method.

This is **different from a static variable**:

~~~java
// WRONG: shared state across all requests can be overwritten.
static String currentRequestId;
~~~

Two concurrent requests writing to the same variable will mix up IDs. MDC has an adapter that manages context in a backend-specific way; however, you must still understand the thread-local and propagation policies, especially when the application uses asynchronous frameworks.

### 2.2. MDC Only Adds Metadata, Not Messages or Exceptions

A useful log line still needs the operation, event code (if any), outcome, and exception when needed:

~~~java
// Snippet: LOG is an SLF4J Logger, e is a Throwable to diagnose.
LOG.error("operation=checkout outcome=failed", e);
~~~

If MDC has `requestId=req-A` and the layout prints `%X{requestId}`, the record above will contain the ID without needing to embed `req-A` again in the message. **MDC does not automatically hold stack traces/causes**; that depends on how the `Throwable` is passed and how the formatter/encoder outputs it.

## 3. Choosing requestId and Fields to Put in MDC

A minimal, practical set of fields for an HTTP request:

| Field | Purpose | Notes |
| --- | --- | --- |
| `requestId` | Correlates logs of the same request within a service | Short/concise ID, validated for length and characters |
| `correlationId` | Correlates business steps across services or messages | May equal `requestId` or differ; requires a clear contract |
| `traceId` | Links to a distributed trace if instrumentation is present | Do not invent a valid trace using MDC alone |
| `spanId` | Links to the corresponding span if present | ID must come from the actual trace context |
| `operation` | Operation name from a finite set of values | For example, `checkout`, `load-order` |
| `tenantId` | Supports partitioned investigation when permitted | Only use approved IDs; protect authorization |
| `userId` | Links to an account when policy allows | Do not log email/name/PII by default |
| `clientIp` | Network info when justified for business/security reasons | May be personal data; consider retention |

**Do not stuff everything into MDC.** MDC is typically attached to many log events and multiple appenders, so adding a long or sensitive field can increase storage volume and data exposure. The key/value set should be small, stable, controlled, and documented.

### 3.1. Client Header IDs Are Untrusted Input

A system might receive `X-Request-ID` from a trusted reverse proxy or from an external request. If you take the raw header value without validation, a sender can inject CR/LF, quotes, overly long strings, or deliberately noisy values into logs.

Recommended policy:

1. Prefer IDs issued by a **trusted ingress/gateway** following an agreed contract.
2. If accepting from a header, **enforce length limits and a syntax whitelist**.
3. When the header is missing or invalid, generate a new ID or use an ID from a trusted tracing system; do not use the raw invalid header.
4. Never let the header determine user identity, tenant membership, or access permissions.
5. If you need to return `requestId` in a response header for customer support, return the server-validated/selected ID.

Example of a syntax check (this is only a snippet, not a mandatory policy):

~~~java
// rawHeader may be null or contain untrusted input.
boolean valid = rawHeader != null
        && rawHeader.matches("[A-Za-z0-9_-]{1,64}");

String requestId = valid
        ? rawHeader
        : java.util.UUID.randomUUID().toString();
~~~

The regex rejects slashes, newlines, and overly long strings; actual policies may vary by system. **Syntax validation does not mean the header's origin is trustworthy**: an attacker can still send an ID matching the regex that collides with someone else's ID. For uniqueness/authenticity guarantees, ID generation must be managed at a trusted boundary.

### 3.2. requestId Differs from traceId

`requestId` is an application-level identifier for a single request; `traceId` belongs to the trace context of a tracing system. A single trace can contain multiple spans and span multiple downstream requests. If using OpenTelemetry/W3C Trace Context, prefer **extracting `traceId` from the real context** and configuring log/trace correlation, rather than putting an arbitrary string into `traceId`.

Do not conflate these three values across all applications:

~~~text
requestId = ID of the local HTTP request
correlationId = business correlation ID across multiple steps
traceId = ID generated/maintained by the tracing system
~~~

They can be mapped to each other by convention, but their differences must be documented so dashboards and tracing are not misinterpreted.

## 4. MDC Lifecycle for a Synchronous Request

A simple request follows these steps:

1. **Receive the request** at a filter/interceptor/middleware.
2. **Read or generate `requestId`**, and validate it.
3. **Snapshot the previous context if needed**, so as not to break the MDC of an outer scope.
4. **Install the request context** before any log statements that need correlation.
5. **Execute business logic**; loggers across layers automatically pick up `requestId` from MDC.
6. **Log the outcome and handle errors** within the same context.
7. **Restore/clear MDC in `finally`**, even if business logic throws an exception or returns early.

Diagram:

~~~text
Thread P1
  |
  +-- request A: put req-A --> log A1 --> log A2 --> finally cleanup
  |
  +-- request B: put req-B --> log B1 --> log B2 --> finally cleanup
  |
  +-- idle/housekeeping: MDC no longer holds req-A or req-B
~~~

Dangerous approach:

~~~java
// WRONG if processing throws an exception before remove().
MDC.put("requestId", requestId);
processRequest();
MDC.remove("requestId");
~~~

If `processRequest()` throws an exception, `remove` never runs. The thread may be reused by the thread pool, and the next request's events will be tagged with the stale ID.

**Use `finally`:**

~~~java
// Snippet inside a method that has requestId and processRequest().
MDC.put("requestId", requestId);
try {
    processRequest();
} finally {
    MDC.remove("requestId");
}
~~~

This works when the current scope **exclusively owns the `requestId` key** and does not need to restore a previous value. If there are nested scopes or MDC was set before entering, you should snapshot and **restore the old map** to avoid accidentally deleting the caller's context.

### 4.1. MDC.putCloseable Can Help with Short Scopes

SLF4J provides `MDC.putCloseable(key, value)`:

~~~java
// Snippet: SLF4J MDC on a supported backend.
try (MDC.MDCCloseable ignored =
        MDC.putCloseable("requestId", requestId)) {
    LOG.info("request accepted");
}
~~~

`MDCCloseable` is a `Closeable` object suitable for `try-with-resources`. When closed, it **removes the key**, making it less likely to forget cleanup.

**Subtlety:** per the SLF4J contract, closing `MDCCloseable` removes the key; **it does not guarantee restoring the previous value of that same key**. Therefore, with nested scopes that already have a different `requestId`, do not treat `putCloseable` as a self-restoring context stack. In that situation, use explicit snapshot + restore.

## 5. Snapshot, Restore, and MDC Leakage

Core SLF4J APIs:

| API | Purpose |
| --- | --- |
| `MDC.put(key, value)` | Sets/overwrites a key in the current context |
| `MDC.get(key)` | Reads a key's value from the current context |
| `MDC.remove(key)` | Removes one key without affecting other keys |
| `MDC.clear()` | Clears the entire current MDC map |
| `MDC.getCopyOfContextMap()` | Returns a **copy** of the current map; may return `null` |
| `MDC.setContextMap(map)` | Replaces the current map with a copy of the provided map |
| `MDC.putCloseable(key, value)` | Creates a scope that automatically removes the key on close |

To use snapshot/restore:

~~~java
// Snippet in a class importing org.slf4j.MDC and java.util.Map.
Map<String, String> before = MDC.getCopyOfContextMap();
try {
    MDC.clear();
    MDC.put("requestId", requestId);
    performRequest();
} finally {
    if (before == null || before.isEmpty()) {
        MDC.clear();
    } else {
        MDC.setContextMap(before);
    }
}
~~~

This is an example inside a method that already has `requestId`/`performRequest()`. It **intentionally opens a clean context for the request**, then restores the exact map that existed before entry. If the application has non-request fields that must persist throughout processing (such as environment or service name), design an **allowlist merge** or configure those fields in the encoder/configuration rather than wiping out all meaningful context by default.

**Copying the map is necessary** when crossing thread boundaries: you should not pass a shared mutable reference and mutate it after enqueuing. `getCopyOfContextMap()` returns a copy at the time of the call. `setContextMap(...)` replaces the executing thread's context; it does not magically transfer data to other threads.

### 5.1. Distinguishing clear and remove

- `remove("requestId")` deletes only one key: suitable when the current code owns that key and other keys must remain intact.
- `clear()` wipes the entire MDC of the **current thread**: suitable at a boundary that owns the full scope, but can erase framework context if used in the wrong place.
- `restore(snapshot)` restores the state prior to the scope: suitable for nested scopes, thread pool workers, and applications with multiple context sources, though it **cannot fix a snapshot that was already leaked beforehand**.

You need to define the contract: who owns the context? Who sets it and who cleans it up? When there are nested scopes or async callbacks, who is responsible for restoring it? Without this, a project can easily end up with logs carrying the wrong `requestId`.

## 6. Complete Java 17 Example: Request-Scoped MDC Across Two Requests and One Worker Thread

The following example uses **Java 17**, **SLF4J API 2.0.17**, and **Logback Classic 1.5.18**. Goals:

- Two simulated requests with different IDs, running sequentially while using **the same worker thread**.
- Both request-thread logs and worker logs carry the correct `requestId`/`orderId`.
- The caller's MDC is restored after each request.
- The worker's MDC is restored after each task.
- After both requests, a log running **outside any request scope** no longer carries the old request's ID.
- Stdout order is deterministic, because `Future.get()` waits for the task to complete before the request thread continues.

This example demonstrates how MDC behaves with a thread pool; a real web application needs to integrate with the corresponding filter/interceptor and execution model.

Create the structure:

~~~text
request-mdc-demo/
  pom.xml
  src/main/java/example/RequestMdcDemo.java
  src/main/resources/logback.xml
~~~

### 6.2. RequestMdcDemo.java

~~~java
package example;

import java.util.Map;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class RequestMdcDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(RequestMdcDemo.class);

    private RequestMdcDemo() {
    }

    private static void restore(Map<String, String> context) {
        if (context == null || context.isEmpty()) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }

    private static void processRequest(
            ExecutorService executor, String requestId, String orderId)
            throws InterruptedException, ExecutionException {

        Map<String, String> callerBefore = MDC.getCopyOfContextMap();

        try {
            // Create a clean, isolated context for this request.
            MDC.clear();
            MDC.put("requestId", requestId);
            MDC.put("orderId", orderId);
            LOG.info("stage=received");

            // Capture the context at task submission time.
            Map<String, String> captured = MDC.getCopyOfContextMap();

            Future<?> worker = executor.submit(() -> {
                Map<String, String> workerBefore =
                        MDC.getCopyOfContextMap();
                try {
                    // Install the request context onto the worker thread.
                    restore(captured);
                    LOG.info("stage=background");
                } finally {
                    // Do not leave request context behind in the thread pool.
                    restore(workerBefore);
                }
            });

            // Wait for the worker so the example produces deterministic log ordering.
            worker.get();
            LOG.info("stage=completed");
        } finally {
            // Even if worker.get() fails, the caller context is still restored.
            restore(callerBefore);
        }
    }

    public static void main(String[] args) throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();

        try {
            processRequest(executor, "req-A", "order-1");
            processRequest(executor, "req-B", "order-2");

            // Run a non-request task on the same worker.
            executor.submit(
                    () -> LOG.info("stage=worker-idle")).get();

            // Log on the caller after both requests have finished.
            LOG.info("stage=main-idle");
        } finally {
            executor.shutdown();
            if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
                executor.shutdownNow();
            }
        }
    }
}
~~~

**Why is this example verifiable?**

- `MDC.getCopyOfContextMap()` returns a copy of the map on the calling thread; it does not return a global variable holding MDC for all requests.
- At the request boundary, `callerBefore` is captured and the request sets up a new context. `finally` calls `restore(callerBefore)`.
- When creating the task, `captured` snapshots the request's context; the task calls `restore(captured)` **inside** the worker thread before logging.
- The worker snapshots `workerBefore` and restores it in `finally` so the next use of the thread does not carry data from the finished request.
- `Future.get()` guarantees that the task's `stage=background` log completes before `stage=completed` is logged. This waiting is only for deterministic example output; real async applications should not unnecessarily block requests.
- `newSingleThreadExecutor()` has exactly one worker thread serving tasks, so the `stage=worker-idle` task uses the same pool after both requests. With no prior MDC on the worker, the `none` fallback appears.

### 6.3. logback.xml

~~~xml
<configuration>
    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <pattern>requestId=%X{requestId:-none} orderId=%X{orderId:-none} %msg%n</pattern>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>

~~~

This is a Logback configuration. `%X{requestId}` retrieves the MDC value. The `%X{requestId:-none}` syntax tells Logback to use `none` when the key does not exist; the same applies to `orderId`. `%msg%n` outputs the message followed by a newline. The pattern omits timestamp/thread so the output is easy to compare.

**Do not use this pattern as a mandatory production format**: real logs should include level, timestamp, service/logger, and when appropriate `traceId`/`spanId`. Here the goal is to observe MDC being propagated and cleaned up.

In the `request-mdc-demo` directory:

Maven or the runtime environment may emit their own messages; the eight lines above are the **logs emitted by the application** via `ConsoleAppender` according to the pattern. **Try an intentional bug in a learning environment:** remove the `restore(workerBefore)` line in the worker. With a reused thread pool and no other cleanup step, the `worker-idle` task can print `requestId=req-B`/`orderId=order-2` even though it does not belong to request B. That is **MDC leakage**. Do not modify production code to test data leaks; only practice this in the demo.

**You do not need a thread pool to have synchronous request-scoped MDC.** Adding `MDC.put(...)` at the boundary and cleaning up in `finally` is enough if all processing runs on the same thread. The executor part here illustrates the additional problem when switching threads.

## 7. Integrating into Real HTTP Requests

In web applications, set MDC at **a well-defined boundary** such as a Servlet Filter, framework interceptor, or middleware. Controllers/services/repositories can use loggers normally without looking up `requestId` themselves.

### 7.1. Servlet Filter Pseudocode

~~~java
// PSEUDOCODE depending on the Servlet API and ID validation functions.
// Not a standalone Java program.
void doFilter(request, response, chain) {
    String requestId = selectTrustedOrNewId(request);
    Map<String, String> previous = MDC.getCopyOfContextMap();

    try {
        MDC.clear();
        MDC.put("requestId", requestId);

        response.setHeader("X-Request-ID", requestId);
        LOG.info("event=request.received");
        chain.doFilter(request, response);
        LOG.info("event=request.completed");
    } finally {
        restore(previous);
    }
}
~~~

This is a **processing flow model**, not complete `jakarta.servlet.Filter` code. A Servlet project needs the appropriate imports, types, checked exceptions, and framework dependencies. `selectTrustedOrNewId` is a conceptual function for choosing a validated ID, not a built-in JDK method.

In a real implementation, you must decide:

- Whether to log start/end in the filter or controller; avoid duplicate logs when an exception handler also logs the same failure.
- When an exception is thrown, `finally` still cleans up; code logging completion after `chain.doFilter` will not run if an exception occurs, so outcome logging should be placed appropriately or inside `finally` with a result status.
- Asynchronous requests (Servlet async dispatch) can resume on a **different thread**; the filter may be invoked across multiple dispatches and must apply scoping properly.
- Some frameworks use their own interceptor/filter to attach MDC and auto-cleanup; avoid installing two independent layers that both overwrite and remove the same key.
- In Spring MVC, `OncePerRequestFilter` is a common integration point; pay attention to async/error dispatches per framework configuration, and do not assume the class name alone guarantees every thread has MDC.
- For WebFlux/Reactor, the execution model does not rely simply on a single fixed thread for the whole request; context must be attached via Reactor Context/context propagation, not just `MDC.put` inside one method of a reactive chain.

### 7.2. Do Not Assume finally in a Filter Covers Async Tasks

A synchronous filter can finish and clean up on the request-receiving thread while a task submitted to an executor is still running. That worker must have **its own context snapshot** and restore it after the task. If the task logs after the request has already returned a response, clearly define whether it is part of the request or an independent background job. Do not keep the entire request/response object as task context unnecessarily, as that can retain sensitive data in memory for too long.

## 8. Propagating MDC Across ExecutorService and CompletableFuture

### 8.1. Why Does MDC Often Disappear When Switching Threads?

A common mistake:

~~~java
// Illustrative snippet: does not propagate MDC to the thread pool.
MDC.put("requestId", "req-A");
executor.submit(() -> LOG.info("stage=worker"));
MDC.remove("requestId");
~~~

Whether MDC is inherited by a new thread **depends on the backend/adapter**, and thread pools **reuse existing threads**. With Logback Classic per its MDC documentation, you should not expect the parent thread's MDC to automatically propagate to workers. The worker may print an empty `requestId` or, worse, a **stale** ID left over from a previous task.

### 8.2. Capture on Submit; Install and Restore on Execute

Pattern using a reusable wrapper:

~~~java
// Java 17 snippet in a class importing org.slf4j.MDC,
// java.util.Map, and the restore(Map<String,String>) method.
static Runnable withMdc(Runnable task) {
    Map<String, String> captured = MDC.getCopyOfContextMap();

    return () -> {
        Map<String, String> before = MDC.getCopyOfContextMap();
        try {
            restore(captured);
            task.run();
        } finally {
            restore(before);
        }
    };
}
~~~

Usage:

~~~java
// Snippet: executor and LOG are already declared.
executor.submit(withMdc(() -> LOG.info("stage=async")));
~~~

**Capture on submit**, not when the worker starts running. If the request thread has already cleared MDC before the worker executes and we wait until execution time to read the request thread, the context may no longer be valid. Carrying a snapshot with the task is the solution for code that explicitly controls the thread boundary.

**Restore on the worker** even when `task.run()` throws an exception. Otherwise, the thread pool retains the previous task's context. In a thread pool with pre-existing values set by a framework, restoring the prior snapshot is better than unconditionally deleting keys not owned by the wrapper.

### 8.3. CompletableFuture Has Multiple Boundaries

~~~java
// Illustration: withMdc(Runnable) already exists.
CompletableFuture<Void> future =
        CompletableFuture.runAsync(
                withMdc(() -> LOG.info("stage=async-start")),
                executor);
~~~

`runAsync` takes a `Runnable`, so the wrapper can be reused. For `supplyAsync` or `thenApplyAsync`, you need an equivalent wrapper for `Supplier<T>`/`Function<T,R>`, or a framework's `TaskDecorator`/context-propagation facility.

**Note:** a `CompletableFuture` chain can run multiple stages on different executors/threads. Propagating context to the first stage **does not guarantee** subsequent stages will have MDC. With non-`Async` `thenApply`, the callback may sometimes run on the thread that completed the future, but you should not rely on this to infer MDC. Design propagation for **every execution boundary**.

### 8.4. AsyncAppender Differs from Business Thread Switching

Logback's `AsyncAppender` receives log events and has its own worker dedicated to writing. Logback prepares the necessary event data before enqueuing, including event-level MDC in supported configurations/versions. This is **different from** the application calling `executor.submit(...)` to run business logic on another thread. `AsyncAppender` does not automatically propagate MDC to your business executor.

You still need to verify that the logger/encoder outputs MDC, and monitor queue/drop/shutdown behavior if events require high reliability.

## 9. Request-Scoped MDC in Spring, Servlet, Reactor, and Messaging

| Environment | Common Integration Approach | Risks to Handle |
| --- | --- | --- |
| Servlet/Jakarta Servlet | Filter or interceptor at request boundary | Async/error dispatch, thread reuse, cleanup |
| Spring MVC | `OncePerRequestFilter`/appropriate interceptor | Double filtering, exception/async request lifecycle |
| Spring `@Async` | `TaskDecorator` or executor wrapper | MDC does not automatically cross to worker threads |
| `ExecutorService` / `CompletableFuture` | Capture Map on submit, install/restore on worker | Missing a stage or forgetting `finally` |
| Reactor / WebFlux | Reactor Context and configured context-propagation | Multiple threads, no single MDC thread across the chain |
| Kafka/RabbitMQ consumer | Validated correlation ID from message headers, per-message scope | Consumer thread pool mixing context across messages |
| Scheduler/batch job | Scope by job/run ID instead of HTTP `requestId` | Accidentally using `requestId` from an unrelated event |
| Outbound HTTP client | Forward accepted ID via header if contracted | Header spoofing, conflict with trace context |
| gRPC interceptor | Attach context in interceptor and propagate across execution boundaries | Callbacks on other threads, stream lifecycle |

MDC should be treated as a **cross-cutting capability** with a clear contract, not a responsibility each service method handles ad hoc. Framework/observability instrumentation may already attach `traceId`/`spanId`; check to avoid key collisions or overwriting instrumentation-managed values.

### 9.1. Designing with a Tracing System

If the application uses OpenTelemetry, request logs can usually be correlated with traces via `traceId`/`spanId` taken from the active span context. Request-scoped MDC for `requestId` remains useful for operational support, but you should not set `traceId=requestId` just because both are IDs.

Trace context data travels across HTTP/gRPC/message headers according to its own standard. Having the logger print `traceId` is only useful if the context is created and propagated properly. Check whether your stack's instrumentation already auto-injects MDC or exports structured fields, to avoid adding a competing manual propagation layer.

### 9.2. An HTTP Request Can Have Multiple Phases and Threads

In streaming responses, long polling, reactive pipelines, or requests with async dispatch, a single request outlives the lifetime of one method on the initial thread. In those cases, "filter start → `finally` cleanup" only applies to **the scope of that execution on that thread**; for logs in another callback to have the ID, a new scope must be created for that callback/task.

**Do not hold MDC indefinitely** on a thread just because the request has not finished at the application layer. Event context should be captured and attached on the actual executing callback, then cleaned up after the callback.

## 10. Configuring Logback: Printing MDC as Text and JSON

### 10.1. Text PatternLayout

Production example with level, logger, thread, and request ID:

~~~xml
<configuration>
    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX} %-5level [%thread] requestId=%X{requestId:-none} traceId=%X{traceId:-none} %logger{36} - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
~~~

`%X{key}` is Logback's converter for an MDC key; `%X{key:-none}` adds a fallback. Using `%X` without a key to print the entire MDC can expose unwanted fields and make output unstable; usually you should print only approved keys.

When an error log includes a `Throwable`, the layout configuration must display the stack trace according to policy. Logback's `PatternLayout` has throwable conversion mechanisms (e.g., `%ex{full}`) and in some configurations automatically appends the exception if no converter is declared; verify the actual output rather than assuming `%msg` always shows the cause.

### 10.2. Structured JSON Logging

With a JSON encoder, we expect an event to have fields like:

~~~json
{
  "timestamp": "2026-11-09T10:15:00Z",
  "level": "INFO",
  "service": "order-service",
  "requestId": "req-A",
  "traceId": "ba7a63b30a8248ff92b79a5665d7320e",
  "operation": "checkout",
  "eventCode": "ORD-1001",
  "message": "stage=received"
}
~~~

This is an **illustrative schema**, not Logback's default output. The encoder must be configured to emit `requestId`/`traceId` from MDC as JSON fields, with field names and types consistent with the collector. A text line containing `requestId=req-A` is just plain text if the pipeline does not parse it into a field.

For Logback, there are JSON encoders from appropriate libraries; for Log4j2, `JsonTemplateLayout` and ThreadContext/MDC can serve a similar role with the right module/template. **Do not copy-paste configs verbatim between the two backends.**

### 10.3. Beware of Log Forging

MDC values may come from untrusted input. If printed as raw text and the ID contains newlines, an attacker can forge fake log lines; a standard JSON encoder escapes strings to preserve structure, but **escaping does not remove sensitive data**. Perform validation right at the boundary, enforce length limits, and use an encoder with proper string handling.

## 11. Testing Request-Scoped MDC: Mandatory Scenarios

A thorough test suite does not just check the logs of one successful request.

### 11.1. Test Two Sequential Requests on the Same Thread

- Request A sets `req-A`, emits two events, and finishes.
- The same thread handles request B with `req-B`.
- Assert that request B's logs **do not** contain `req-A`.
- After request B, background logs have no `requestId` or use the defined fallback.

This scenario catches the most common bug: omitting `finally` or forgetting `MDC.remove`/`clear`.

### 11.2. Test Two Concurrent Requests

- Create two requests with distinct IDs and interleave their operations.
- Each event must carry the ID matching its request.
- No shared `static` `currentRequestId` variable.
- With the same logger or appender, logs may interleave, but each event's context must be accurate.

Do not assert absolute ordering between two concurrent requests; only assert the event → `requestId` mapping and the expected event counts.

### 11.3. Test Tasks Running on a Reused Thread Pool

- Run A's task on a worker and verify it has `req-A`.
- Run B's task on **the same pool** and verify it has `req-B`.
- Submit an "idle" task not belonging to any request; it must not retain `req-B`.
- Make a task throw a `RuntimeException` and confirm `finally` still restores MDC.

This is a critical test because thread pools outlive individual requests.

### 11.4. Test Exceptions, Timeouts, and Task Cancellation

- Business logic throws an exception: the request boundary must still clean up.
- `Future.get()` throws `ExecutionException`: the outer `finally` still runs.
- Worker is interrupted: the task must handle interruption properly; cleanup always lives in `finally`.
- Task is cancelled before running: the wrapper may not have installed context yet; no leak should occur.
- If the app server stops mid-request, there is no guarantee `finally` runs when the JVM is killed; the log pipeline needs its own durability mechanisms.

Do not just check "API returned 200 OK" and assume the MDC lifecycle is correct.

### 11.5. Test Actual Fields in Output

Verify end-to-end from log emission to ingestion:

1. Is the logger actually using a provider/backend that supports MDC?
2. Does the pattern/JSON encoder render `requestId`?
3. Does the search UI/collector index the `requestId` field with the right name and type?
4. Is it being altered/overwritten by other instrumentation or filters?
5. Are any non-request logs carrying an old ID?
6. Do `ERROR` logs with a `Throwable` retain the right diagnostics and context?

**Testing with an in-memory appender or test appender** is usually easier than comparing console text with changing timestamps and thread ordering. If testing text output, strip/control timestamps/threads and assert on stable fields.

## 12. Common Mistakes with Request-Scoped MDC

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Setting MDC in controller without `finally` | Subsequent thread picks up old `requestId` | Scope at boundary, cleanup/restore in `finally` |
| Setting MDC only on the request thread | Async workers lack IDs | Capture on submit, install on worker |
| Setting MDC on worker without restoring | Other requests on pool inherit old ID | Worker wrapper with `try`/`finally` |
| Using static `currentRequestId` | Concurrent requests overwrite data | Per-thread/context MDC, no global variables |
| Calling `MDC.clear()` deep in a service | Wipes `traceId`/fields set by framework | Remove only owned keys or restore snapshot |
| Assuming `putCloseable` always restores old value | Nested scopes lose previous ID | Snapshot/restore when preserving outer context |
| Calling `MDC.get()` on another thread expecting parent's value | Missing ID or stale value | Propagate explicitly across thread boundaries |
| Wrapping only the first stage of `CompletableFuture` | Later stages on other threads lose context | Wrap each async stage or use context-propagation |
| Not validating `X-Request-ID` | Log injection, oversized IDs, correlation spoofing | Trusted boundary, whitelist, limits, server IDs |
| Putting emails/tokens into MDC | Sensitive data spreads across many logs | Use safe internal IDs, data minimization |
| Configuring MDC without `%X` in pattern | Logs lack the field despite MDC being set | Configure layout/encoder properly |
| Treating MDC as distributed tracing | IDs exist without span/trace relationships | Use proper tracing instrumentation |
| Using `requestId` as per-request log filename | Explosion of files/appenders and FDs | Structured logging by `requestId` into shared stream |
| Logging the same event at multiple layers | Duplicate failures, inflated log volume | Pick one boundary responsible for logging |
| Logging in async callback after filter cleanup | Missing `requestId` | Install scope inside the callback/task itself |
| Attaching correlation field to logs but collector drops it | Cannot search by request | Verify schema and ingestion end-to-end |
| MDC is a `String`→`String` map, yet stuffing large objects | Overhead/broken serialization | Choose small fields with dedicated structure and schema |

## 13. Performance, Reliability, and Observability

MDC reduces the effort of passing context through logger calls, but it is not free:

- Every `put`/`get`/map copy has a cost; calling `getCopyOfContextMap()` to snapshot for **every event** unnecessarily can cause allocations.
- Layouts/JSON encoders must serialize fields, increasing bytes/event.
- Adding long or high-cardinality fields increases storage/indexing costs; in particular, never use `requestId` as an unbounded metrics label.
- If a logger uses `AsyncAppender`, it may need to prepare MDC alongside the event before enqueuing; do not confuse this with propagation to business tasks.
- If the collector drops/truncates logs, having the right `requestId` at the appender still does not guarantee an investigator will find the final log.
- Thread pools can process vast numbers of requests; a leak not only corrupts logs but can inadvertently retain another request's data in thread-locals longer than necessary.

**Metrics to measure:** log events/s, bytes/s, CPU, GC/allocations, queue depth, dropped log events, p95/p99 request latency, count of records missing `requestId` at the request boundary, and rate of logs missing `traceId` when tracing is expected.

Do not attach all headers, claims, HTTP bodies, or Java objects to MDC just for debugging convenience. MDC is meant for a **small, approved set of metadata**.

## 14. Security and Privacy

A `requestId` used for log correlation must be treated as **access-controlled operational data**, not an authentication mechanism.

1. **Validate ID origin:** if accepted from clients, restrict syntax/length; never let clients pick user/tenant identity via `requestId`.
2. **Never put secrets in MDC:** access tokens, passwords, refresh tokens, cookies, or API keys can be repeated across many logs.
3. **Minimize PII:** avoid putting emails, phone numbers, addresses, or personal data directly in MDC.
4. **Protect logging outputs:** files, collectors, JSON archives, and backups need appropriate access controls and retention.
5. **Prevent log forging:** filter CR/LF/control characters and use encoders that escape for the target format.
6. **Do not log full request payloads** even when `requestId` is present; only extract fields needed for investigation per data policy.
7. **Avoid IDs with security semantics:** a public ID in a response header must not be used as proof that a request came from a specific user.
8. **Limit retention/thread-local leaks:** clean up context in `finally`, check thread reuse, and verify how frameworks close scopes.
9. **Do not expose stack traces publicly:** internal logs keep `Throwable` under access control; HTTP responses should only return error codes, safe messages, and `requestId` when appropriate.

Proper MDC aids traceability, but retaining context too long can become a source of cross-request data mixing and heightened investigative/security risk.

## 15. Production Checklist for Request-Scoped MDC

1. **Choose field names:** `requestId`/`correlationId`/`traceId` have a shared contract, not ad-hoc names per service.
2. **Choose ID source:** trusted gateway or server-generated; validate headers and enforce length limits.
3. **Attach at boundary:** filter/interceptor/middleware matching the project's execution model.
4. **Clean up in `finally`:** on success, exception, or early return.
5. **Nested scopes:** snapshot/restore if preserving the caller's context is required.
6. **Async propagation:** every `ExecutorService`/`CompletableFuture`/callback has a wrapper/decorator or propagation facility.
7. **Worker cleanup:** restore pre-task context; never leak to subsequent tasks.
8. **Framework compatibility:** MVC/Servlet, async dispatch, and WebFlux/Reactor have different mechanisms.
9. **Backend:** compatible SLF4J provider; Logback pattern/JSON encoder actually prints MDC.
10. **Tracing:** extract `traceId`/`spanId` from real trace context if instrumentation is present.
11. **Schema:** `requestId` field exists in the collector, not just in unparsed text.
12. **Privacy:** no unnecessary secrets/PII, escape input, and set retention.
13. **Exceptions:** log `ERROR` with `Throwable` and accurate context; avoid duplicate logging across every layer.
14. **Concurrency tests:** concurrent requests, sequential requests, worker reuse, exceptions/timeouts/cancellation.
15. **Monitoring:** alert on rate of events missing `requestId`, logging errors, dropped events, and collector lag.

If you only have time to prioritize one test, run **two requests with different IDs on a reused thread pool**, then emit an event outside any request scope. This test exposes both missing context propagation and missing context cleanup.

**Takeaway:** **Request-scoped MDC is a context lifecycle, not just a single `MDC.put(...)` call**. Set a selected/validated ID at the boundary, emit it in logs via layout/JSON encoder, **clean up/restore in `finally`**, and **copy/install/restore when crossing thread pools or callbacks**. That way, logs from multiple requests can interleave while remaining accurately traceable, without letting a later request inherit the previous request's context.
