# Java Logging Security Checklist — Summary and Pre-Production Verification Practices

## 1. Purpose of the Checklist

**Logging security** is not just about not printing passwords. A secure logging system must simultaneously ensure:

1. **Confidentiality and privacy:** do not collect or disclose information beyond permitted purposes.
2. **Integrity:** attackers cannot easily forge, modify, or delete audit trails; information about the actor and outcome must be trustworthy.
3. **Availability:** the pipeline must not be crippled by log storms, oversized inputs, full queues, or disk exhaustion, which could paralyze both the application and observability.
4. **Accountability:** significant events record the actor, action, target, outcome, and appropriate timestamp without leaking secrets.
5. **Lifecycle governance:** access control, data transit/storage, retention, backup, deletion, incident response, and testing all have clear ownership.

The **“Security Checklist”** topic belongs to the **Java Logging Summary** section: its goal is to turn principles from application code to collectors into verifiable, evidence-backed items for use in code reviews, integration testing, releases, and operations.

Example path of an event:

```text
HTTP / message / scheduled job
             |
             v
       Java business code
             |
       Allowlist + masking
             |
       JUL / SLF4J / Log4j 2
             |
       Encoder + appender
             |
       stdout / file / socket
             |
       sidecar / node collector
             |
     gateway / log storage / SIEM
             |
      search / alert / archive
```

**Security must be applied end-to-end.** If application code masks a token in one event, but an HTTP client debug logger, exception cause, MDC, or collector debug log writes the raw value, the policy still fails.

### 1.1. “Secure logging” does not mean “log as little as possible”

Stripping away all context can make intrusion investigations impossible. Conversely, logging every request/response for easier debugging can turn your log store into a secondary repository of PII and secrets. The goal is **minimal data sufficient for investigation**, with a clear schema and controlled storage paths.

Example:

```text
Dangerous:
INFO Login failed, user=alice@example.com password=letmein123

Safer:
INFO event=auth.login.result outcome=DENIED reasonCode=BAD_CREDENTIALS requestId=req-101
```

`requestId` is an ID authenticated or generated by the system at a trust boundary according to policy; do not treat a client-supplied header as proof of identity. The `BAD_CREDENTIALS` code in internal logs should avoid overly granular distinctions between “account exists” and “wrong password” if doing so creates an account enumeration channel.

## 2. Identifying Assets, Actors, and Trust Boundaries

A checklist is only meaningful when grounded in a **threat model**. Common scenarios:

| Actor / failure | Risk source | Consequence |
| --- | --- | --- |
| Client intentionally sends malicious strings | Headers, request ID, URL, exception message | Forged log lines, broken JSON, log flooding |
| Developer logs an entire DTO | `toString()`, JSON serialization | Exposed passwords, tokens, PII |
| Third-party library | HTTP/SQL debug logging | Raw headers, queries, or connection strings logged |
| Insider with log read access | Dashboards, object storage, backups | Accessing sensitive data beyond job needs |
| Collector or transport failure | Buffers, retries, TLS, auth | Lost, duplicated, or leaked logs in transit |
| Actor with write access to files/agent | Log path, filesystem permissions | Tampering/deleting evidence, injecting forged events |
| Event bursts or large payloads | Hot-path logging, async queue, disk quota | Increased latency, OOM, disk exhaustion, log loss |
| Misconfiguration / wrong retention | DEBUG level, archives, backups | Prolonged exposure or premature evidence deletion |

**Boundaries to distinguish:** external users, Java process, host/Pod filesystem, collector agent, network gateway, storage backend, and query users. Two components in the same Kubernetes Pod may share a volume or failure domain; a sidecar is not an absolute trust boundary against a compromised application.

## 3. Checklist A — Minimal Collection and Data Classification

Before every log statement, determine **why this event needs to exist** and what data is truly required.

- [ ] Each event has a specific purpose: operations, diagnostics, security, or audit.
- [ ] Log only fields that genuinely support that purpose; prefer a **field allowlist**.
- [ ] Do not log raw request bodies, response bodies, cookies, headers, or entire Java objects by default.
- [ ] Do not log passwords, OTPs, access/refresh tokens, private keys, secret keys, session cookies, or recovery codes.
- [ ] Personal data such as email, phone, IP, address, or user ID is reviewed against legal requirements and internal policies.
- [ ] If a partial identifier is needed, evaluate re-identification risks when combined with other fields.
- [ ] New fields in DTOs/events must be classified before entering logs.
- [ ] Log sources from frameworks, HTTP clients, JDBC, ORMs, and messaging SDKs are also included in the inventory.
- [ ] Separate logging policies exist for dev/test/staging/production environments; production must not accidentally enable verbose payload logging.
- [ ] Test data contains **synthetic secrets**, never real credentials, to verify masking behavior.

### 3.1. Data Handling Matrix

| Category | Examples | Default action |
| --- | --- | --- |
| Secret/credential | `Authorization: Bearer ...`, password, OTP, private key | **DROP** or `[REDACTED]` completely |
| Personal data | Email, phone, address, date of birth | **OMIT/MASK** when the value is not needed |
| Payment sensitive | PAN, CVV, account number | **Never log raw**, comply with industry regulations |
| Technical identifier | Correlation ID, message ID, request ID | **ALLOW after validation**, per trust policy |
| Event code | `order.create.result`, `PERMISSION_DENIED` | **ALLOW per catalog** |
| Metrics/numbers | `durationMs`, status, attempt | **ALLOW with explicit data types** |
| Raw object/payload | DTO, headers map, arbitrary metadata | **DROP by default** |
| Exception | Class, safe error code, cause/stack message | Separate safely by channel and access level |
| Audit entity/actor | Authenticated actor, resource, action, outcome | Follow audit schema; never log secret values |

**Data minimization is stronger than masking.** If you never write an email address to the logs, you do not need to hunt down every email variant to mask it. Conversely, if the business genuinely needs to correlate events by subject, you can use a system-issued pseudonymous reference or a keyed HMAC with an appropriate scope, while evaluating linkability and key management.

## 4. Checklist B — Masking, Redaction, and Safe Defaults

Use precise terminology:

- **Omit/drop:** do not include the field in the event at all.
- **Full redaction:** replace with `[REDACTED]`, revealing zero characters of the secret.
- **Masking:** hide all or part of a value per policy; partial masking can still leak information.
- **Pseudonymization/tokenization:** replace an identifier with a linkable tag/token; not synonymous with anonymous data by default.
- **Keyed HMAC:** usable for linkable pseudonyms; requires key protection, rotation, and scope control.
- **Encryption:** protects data in encrypted form but can be decrypted; does not replace data minimization.

Checklist:

- [ ] Field-handling rules are centralized, versioned, and reviewed.
- [ ] Unclassified fields **do not fall back to raw logging** when unrecognized by the policy.
- [ ] If masking/serialization fails, do not call `logger.error("raw={}", rawValue)` to debug the masking failure.
- [ ] Do not keep the last four characters of access tokens, passwords, private keys, or cookies by default.
- [ ] Do not use unkeyed `SHA-256(email)` and claim it is anonymous; predictable values are vulnerable to dictionary attacks.
- [ ] Verify masking across formatted messages, structured fields, MDC, exception/cause, markers, and custom metadata.
- [ ] Test across appenders, files, stdout, remote exporters, and collectors—not just a single output path.
- [ ] Do not allow a separately configured logger to bypass the safe event builder.
- [ ] Emit schema violation alerts **without** logging the offending raw value.
- [ ] Assign a policy owner who approves when the allowlist may be expanded.

### 4.1. Per-Event Policy Examples

A `profile.update.result` event may need `requestId`, authenticated actor ref, outcome, and duration; it does not necessarily need the full old and new email/phone values.

A `config.change.result` event may need `settingName`, approved `changeId`, actor, and outcome, but **must not log before/after values of secret fields**. Instead, log `secretChanged=true` or a policy-compliant version/hash without exposing the secret.

A `payment.capture.result` event needs a status and a safe payment reference. **Never** include a full PAN/CVV in logs, even inside validation errors or exception messages.

## 5. Checklist C — Logging APIs and Java Code

Security bugs often start at the logger call site.

### 5.1. Patterns to Reject in Code Review

```java
// Avoid: DTO toString() may contain secrets.
log.info("request={}", request);

// Avoid: printing authentication header.
log.debug("Authorization={}", authorizationHeader);

// Avoid: query string may contain tokens.
log.info("URL={}", requestUrlWithQuery);

// Avoid: dumping all environment/system properties.
log.debug("system={}", System.getProperties());

// Avoid: exception message from dependency may contain raw data.
log.error("Downstream error: {}", failure.getMessage());
```

These are **snippets for recognizing anti-patterns**, not a standalone runnable Java file. Variable names and `log` assume the application has already declared them.

Replace with a schema-backed event:

```java
// Integration snippet: only pass validated/safely transformed data.
log.info("event=profile.update.result requestId={} outcome={} durationMs={}",
         safeRequestId, outcomeCode, durationMs);
```

**The SLF4J `{}` placeholder is not a sanitizer.** It does not mask data, prevent log injection, or guarantee that output is a separate JSON field. With SLF4J 2.x, `addKeyValue` can carry structured fields, but you must still supply **sanitized values** and use an appropriate encoder/provider.

### 5.2. Structured Logging Must Have a Schema

- [ ] Event name, outcome, and error code come from an approved catalog; never take arbitrary unvalidated input directly.
- [ ] Request/trace IDs are validated for length, format, and trusted source.
- [ ] Fields have stable types, e.g., `durationMs` is numeric, `retryable` is boolean.
- [ ] JSONL has **one event per line** and escapes newlines/control characters properly.
- [ ] Do not accept client-controlled dynamic field names, as they can break indexes/mappings.
- [ ] Enforce limits on field count, string length, and nested object depth.
- [ ] Do not use manual string concatenation to build production JSON.
- [ ] Formatter/encoder outputs only policy-approved fields; verify against actual output.

Example of a safe event:

```json
{
  "timestamp": "2026-11-10T02:00:00Z",
  "level": "WARN",
  "service": "accounts-api",
  "event": "profile.update.denied",
  "requestId": "req-101",
  "actorRef": "actor-42",
  "outcome": "DENIED",
  "reasonCode": "FORBIDDEN"
}
```

This is illustrative JSON, not data from a real request. `actorRef` must come from a proper authentication/authorization mechanism, not copied from a client-claimed username.

## 6. Standalone Java 17 Example: Checking the Checklist at the Source

The following example uses only JDK 17—no Maven, Gradle, or SLF4J required. It simulates an allowlist-based **safe event builder** to demonstrate three things simultaneously:

1. Secrets and email addresses are masked **before** calling JUL.
2. Fields outside the allowlist never enter the message.
3. A request ID containing newlines/forged lines is replaced with `[INVALID]`.

Both log calls produce **deterministic output** so learners can verify the result after running.

Save the file **`SecureLoggingChecklistDemo.java`**:

```java
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Set;
import java.util.logging.Handler;
import java.util.logging.Level;
import java.util.logging.LogRecord;
import java.util.logging.Logger;

public class SecureLoggingChecklistDemo {
    private enum Rule { ID, OUTCOME, REASON, MASK, REDACT }

    private static final Map<String, Rule> POLICY = Map.of(
            "requestId", Rule.ID,
            "actorRef", Rule.ID,
            "outcome", Rule.OUTCOME,
            "reasonCode", Rule.REASON,
            "email", Rule.MASK,
            "authorization", Rule.REDACT
    );

    private static final Set<String> EVENTS = Set.of(
            "profile.update.denied", "profile.update.failed"
    );

    private static String safeId(String value) {
        return value != null
                && value.matches("[A-Za-z0-9_-]{1,32}")
                ? value : "[INVALID]";
    }

    private static String safeEnum(
            Set<String> allowed, String value) {
        return value != null && allowed.contains(value)
                ? value : "[INVALID]";
    }

    private static String safeValue(
            String fieldName, Rule rule, String raw) {
        return switch (rule) {
            case ID -> safeId(raw);
            case OUTCOME -> safeEnum(
                    Set.of("DENIED", "FAILED", "SUCCEEDED"), raw);
            case REASON -> safeEnum(
                    Set.of("FORBIDDEN", "STORAGE_TIMEOUT", "NONE"), raw);
            case MASK -> raw == null ? "-" : "[MASKED]";
            case REDACT -> raw == null ? "-" : "[REDACTED]";
        };
    }

    private static String buildSafeEvent(
            String event, Map<String, String> rawFields) {
        String safeEventName = event != null
                && EVENTS.contains(event) ? event : "event.invalid";

        StringBuilder message = new StringBuilder("event=")
                .append(safeEventName);

        for (Map.Entry<String, String> field
                : rawFields.entrySet()) {
            Rule rule = POLICY.get(field.getKey());
            if (rule == null) {
                continue; // Unknown field: fail-closed, do not log raw.
            }

            message.append(' ')
                    .append(field.getKey())
                    .append('=')
                    .append(safeValue(
                            field.getKey(), rule, field.getValue()));
        }

        return message.toString();
    }

    private static void assertNoLeaks(String text) {
        String[] forbidden = {
            "alice@example.com", "Bearer secret-token",
            "4111111111111111", "ERROR forged"
        };
        for (String secret : forbidden) {
            if (text.contains(secret)) {
                throw new AssertionError("A test secret leaked");
            }
        }
        if (text.contains("\n") || text.contains("\r")) {
            throw new AssertionError("Log injection detected");
        }
    }

    public static void main(String[] args) {
        Logger logger = Logger.getLogger("demo.secure-checklist");
        logger.setUseParentHandlers(false);
        logger.setLevel(Level.ALL);

        Handler stdout = new Handler() {
            {
                setLevel(Level.ALL);
            }

            @Override
            public void publish(LogRecord record) {
                if (record != null && isLoggable(record)) {
                    System.out.println(record.getLevel().getName()
                            + " " + record.getMessage());
                }
            }

            @Override
            public void flush() {
                System.out.flush();
            }

            @Override
            public void close() {
                flush();
            }
        };

        logger.addHandler(stdout);
        try {
            Map<String, String> denied = new LinkedHashMap<>();
            denied.put("requestId", "req-101");
            denied.put("actorRef", "actor-42");
            denied.put("outcome", "DENIED");
            denied.put("reasonCode", "FORBIDDEN");
            denied.put("email", "alice@example.com");
            denied.put("authorization", "Bearer secret-token");
            denied.put("rawBody", "card=4111111111111111");

            String a = buildSafeEvent(
                    "profile.update.denied", denied);
            assertNoLeaks(a);
            logger.info(a);

            Map<String, String> failed = new LinkedHashMap<>();
            failed.put("requestId", "req-102\nERROR forged");
            failed.put("actorRef", "actor-43");
            failed.put("outcome", "FAILED");
            failed.put("reasonCode", "STORAGE_TIMEOUT");
            failed.put("authorization", "Bearer secret-token");

            String b = buildSafeEvent(
                    "profile.update.failed", failed);
            assertNoLeaks(b);
            logger.warning(b);
        } finally {
            logger.removeHandler(stdout);
            stdout.close();
        }
    }
}
```

Run with JDK 17 or later:

```bash
javac SecureLoggingChecklistDemo.java
java SecureLoggingChecklistDemo
```

**Exact stdout** when all checks pass:

```text
INFO event=profile.update.denied requestId=req-101 actorRef=actor-42 outcome=DENIED reasonCode=FORBIDDEN email=[MASKED] authorization=[REDACTED]
WARNING event=profile.update.failed requestId=[INVALID] actorRef=actor-43 outcome=FAILED reasonCode=STORAGE_TIMEOUT authorization=[REDACTED]
```

No raw email, Bearer token, test card number, or `ERROR forged` string appears. `WARNING` is **JUL**'s level name, not SLF4J/Logback's `WARN`. If an assertion throws `AssertionError`, the program is **not a PASS**.

### 6.1. Analyzing the Example

- `POLICY` is an allowlist **specific to the demo events**, not a sufficient list for every domain.
- `LinkedHashMap` preserves insertion order, keeping output deterministic when the formatter prints a text line.
- `safeId` restricts ID syntax and length; it **does not prove the ID came from a trusted source**. Real applications must also verify source/trust boundaries.
- `safeEnum` enforces that `outcome` and `reasonCode` belong to an approved catalog, preventing external content from entering those fields.
- `MASK` and `REDACT` replace actual values with constant sentinels, avoiding partial masking.
- `rawBody` is not in the allowlist and is therefore dropped. Dropping unknown fields is safer than falling back to printing the object.
- The `requestId` field in the second event contains an injected newline, so it is replaced with `[INVALID]`, preventing a forged log line.
- `assertNoLeaks` is a **smoke assertion on known synthetic secrets**; it does not replace property-based tests or checks on other logging paths.
- The stdout handler intentionally disables parent handlers, timestamps, and default formatters, making stdout reproducible.
- The example **does not prove** that remote logs are stored, that audit logs have integrity, or that a production JSON encoder is secure.

### 6.2. Intentional Limitations of This Practice Demo

**Do not copy the demo class verbatim as a production security library** without designing an appropriate threat model and API. It does not handle nested objects, invalid Unicode, field-level JSON serialization, full Unicode normalization, third-party logging, MDC, `Throwable`, sidecars, archives, or dynamic configuration. A regex checking only alphanumeric/hyphen/underscore characters for `requestId` also cannot detect every secret that happens to use valid characters.

In real code, centralize policies by **event type**, construct objects containing only validated values, restrict APIs that accept arbitrary `Object` parameters, add negative tests, and run checks against output at the final sink.

## 7. Checklist D — Preventing Log Injection and Data Poisoning

**Log injection** occurs when attacker-controlled input is concatenated into a message or log field in a way that causes parsers or viewers to misinterpret event boundaries, content, or meaning.

Example input:

```text
req-102
ERROR user=admin action=grantAccess outcome=SUCCEEDED
```

If an application prints raw `requestId` in text logs, the part after the newline can look like a forged `ERROR` event. Even when using JSON, a buggy serializer or misconfigured parser/collector can still be exploited.

Checklist:

- [ ] Never concatenate raw user input directly into text formats; validate/normalize or encode it.
- [ ] Escape newlines, CR, tabs, quotes, backslashes, and control characters appropriately for the output format.
- [ ] If using JSONL, **one event must be one JSON object on a single line**; use a JSON encoder with standard escaping.
- [ ] Do not let user input determine field names, logger names, file paths, index names, storage buckets, or destinations.
- [ ] Never trust client-supplied level/status values as proof that the system performed that action.
- [ ] Cap input size and field count before logging to prevent memory/CPU exhaustion.
- [ ] Test CR, LF, CRLF, Unicode, quote/backslash sequences, percent-encoding, and extremely long values.
- [ ] For multiline exceptions, configure collectors to recognize a single event rather than splitting stack traces into separate records.
- [ ] For terminal log viewers, consider escaping control/ANSI sequences that can distort display output.
- [ ] Prevent log data poisoning (malicious data causing misleading queries/alerts) through schemas and trusted field sources.

**SLF4J `{}` is not an injection defense.** Placeholders only format arguments; if the formatter outputs raw newlines, text logs can still be split across lines. A standard JSON encoder handles syntax escaping, but does not automatically make input trustworthy for authorization decisions.

## 8. Checklist E — Exceptions, Stack Traces, and Root Causes

**Preserving the cause chain** helps troubleshoot failures, but exception messages from HTTP clients, database drivers, parsers, or libraries may contain secrets.

- [ ] Do not discard the original cause when wrapping: use `new ServiceException("context", original)` when appropriate.
- [ ] Do not print dependency `Throwable.getMessage()` values into public messages by default.
- [ ] Inspect rendering paths for **wrappers, causes, suppressed exceptions**, and MDC/structured arguments.
- [ ] Classify exceptions using **stable error codes**; never use full exception messages as metric labels.
- [ ] Log stack traces only at boundaries where truly needed, avoiding duplicate `ERROR` logs at every layer.
- [ ] Expected validation errors should not automatically print long stack traces for every request.
- [ ] Public HTTP/gRPC responses must not expose raw stack traces, file paths, SQL queries, tokens, or internal hosts.
- [ ] Diagnostic-rich log channels have appropriate ACLs/retention and tested renderers.
- [ ] Do not serialize a `Throwable` with a generic JSON object mapper, which can emit an uncontrolled object graph.
- [ ] Do not lose `InterruptedException` state; rethrow or restore the interrupt flag per contract.

Example integration snippet in JUL:

```java
// failure is a Throwable permitted in the appropriate internal log channel.
logger.log(java.util.logging.Level.SEVERE,
        "event=order.persist.failed errorCode=STORAGE_UNAVAILABLE",
        failure);
```

**Caution:** passing a `Throwable` lets the backend print the stack/cause, but **does not automatically mask** exception messages containing tokens. If emitting raw `Throwable` objects is not allowed, log a safe summary (`exceptionType`, `errorCode`) to the standard channel and design a restricted-access investigation workflow for deep details. Stripping stack traces entirely can cripple incident response; this is a threat-model decision, not a one-size-fits-all regex fix.

## 9. Checklist F — HTTP, Messaging, Jobs, and MDC

### 9.1. HTTP

- [ ] Access events record method, route **template**, status, duration, requestId, and appropriate outcome.
- [ ] Do not log raw `Authorization`, `Cookie`, `Set-Cookie`, or credential query parameters.
- [ ] Do not enable generic request/response body logging in production without an approved policy.
- [ ] Do not trust `X-Forwarded-For`, user-supplied request IDs, or `User-Agent` without trust/validation checks.
- [ ] Do not log `outcome=SUCCEEDED` before the response or business transaction actually reaches that milestone.
- [ ] Do not treat HTTP `202 Accepted` as confirmation that a downstream job has completed.
- [ ] Return error codes and request IDs in public responses instead of stack traces.

### 9.2. Message Consumers

- [ ] Include safe message ID, consumer group, topic/queue, attempt, event, outcome, and errorCode.
- [ ] Do not log full message bodies or headers when payloads may contain sensitive data.
- [ ] On retry/redelivery, distinguish the logical message ID from delivery attempt or offset/broker coordinates.
- [ ] Do not treat “processing succeeded,” “ack requested,” and “offset committed” as the same state.
- [ ] Implement idempotency/transaction handling for redelivered messages; never rely on logs to prevent duplicate side effects.
- [ ] DLQ/quarantine records also require ACLs and retention because they may contain sensitive payloads.
- [ ] Collector and broker client internal DEBUG logs must not print tokens, passwords, or raw message contents.

### 9.3. Scheduled Jobs / Batch

- [ ] Log `jobName`, `runId`, `attempt`, outcome, counts, and duration per schema.
- [ ] Do not dump input/output data records instead of summaries.
- [ ] For partial batch success, do not mark the entire job as `SUCCEEDED`.
- [ ] When a job fails, ensure the scheduler receives the accurate failure/retry status per contract.
- [ ] Backup/export logs must not expose secret-bearing paths or filenames containing PII outside policy.

### 9.4. MDC and Context Propagation

- [ ] Put only allowlisted, short, validated fields into SLF4J `MDC` or Log4j 2 `ThreadContext`.
- [ ] **Restore/clear in `finally`** when thread pools reuse threads.
- [ ] Use proper propagation mechanisms for executors, `CompletableFuture`, Reactor/WebFlux, schedulers, or virtual threads where applicable.
- [ ] Never store raw headers, JWTs, or account objects in thread-local context.
- [ ] `traceId` aids correlation, but is not an authenticated principal.
- [ ] Do not use raw `requestId`/`userId`/`traceId` as high-cardinality metric labels.

An SLF4J integration snippet:

```java
import org.slf4j.MDC;

// validatedRequestId is generated/validated by the application before use.
String previous = MDC.get("requestId");
try {
    if (validatedRequestId == null) {
        MDC.remove("requestId");
    } else {
        MDC.put("requestId", validatedRequestId);
    }

    processRequest();
} finally {
    if (previous == null) {
        MDC.remove("requestId");
    } else {
        MDC.put("requestId", previous);
    }
}
```

This is not a standalone file: it requires the SLF4J dependency, variables, and an actual `processRequest()` method. Its purpose is to **prevent context from a previous request from leaking into the next request**.

## 10. Checklist G — Log Transit, Storage, and Access Control

Even a masked event can carry sensitive metadata; both transit paths and storage must be protected.

| Boundary | Checklist |
| --- | --- |
| **Java → stdout/file** | File/directory permissions, UID/GID; never write to world-readable paths |
| **Java → remote appender** | TLS, certificate validation, authentication, reasonable timeouts/retries |
| **Sidecar → gateway** | TLS/mTLS where appropriate, minimal identity, egress policy |
| **Gateway → storage** | IAM/RBAC, tenant isolation, encryption at rest, key management |
| **Search/dashboards** | Least privilege, audited queries, export/download controls |
| **Archive/backup** | Encryption, ACLs, and retention consistent with the source |
| **Dev/staging** | Never copy sensitive production data into uncontrolled test logs |

- [ ] Log read permissions are role-based; users who do not need PII/stack traces are not granted access by default.
- [ ] Policies govern operator/admin access, break-glass procedures, and audit logging of log access where required.
- [ ] TLS is genuinely verified; never disable certificate verification for convenience.
- [ ] Secrets for connecting to log gateways are stored via a secret manager or workload identity, never hardcoded in `logback.xml`, public YAML, or environment dumps.
- [ ] Log files, archives, and temporary spools have proper permissions/ownership and are unreadable by unrelated services.
- [ ] Containers use `runAsNonRoot`, filesystem security contexts, and read-only mounts where compatible.
- [ ] Do not grant service account tokens or Kubernetes API privileges to collectors unless necessary.
- [ ] Partition sensitive logs by tenant or domain per access policy.
- [ ] Support key revocation/rotation and verify impact on historically encrypted data.
- [ ] Never expose an unauthenticated or unbounded log export API.

**Encryption in transit and encryption at rest do not hide data from authorized readers.** Therefore, masking and data minimization remain essential alongside RBAC, encryption, retention, and access auditing.

## 11. Checklist H — Retention, Deletion, and Privacy Over Time

Sensitive data can persist across multiple locations:

```text
app.log
  -> rolled app.1.log.gz
  -> node/sidecar spool
  -> gateway buffer
  -> search index
  -> object storage/archive
  -> backup/snapshot
  -> export CSV / screenshots / incident tickets
```

- [ ] Define retention policies by **purpose and log type**: debug, access, security, audit.
- [ ] Limit retention periods per regulations and investigative needs; never retain indefinitely for convenience.
- [ ] File rotation/cleanup actually enforces the policy, not just a `maxHistory` setting on paper.
- [ ] Backups, snapshots, DLQs, collector buffers, and exported dashboards are included in the data scope.
- [ ] Establish deletion/minimization workflows when data no longer has a permitted purpose, aligned with any evidence-preservation obligations.
- [ ] When a leaked token/PII is discovered, evaluate **already-shipped and backed-up data**, not just the masking code fix.
- [ ] Maintain procedures to restrict access, rotate/revoke exposed credentials, and handle incidents based on actual severity.
- [ ] Retention is long enough for incident investigation and mandatory audits, but not excessive for diagnostic logs.
- [ ] Test retention changes against older files/periods; avoid accidentally deleting mandatory audit records.
- [ ] Deleting from one sink does not mean all copies on other systems have been deleted.

Retention is a policy that requires **an accountable owner and verifiable evidence**. In regulated systems, balance deletion rights, legal holds, and actual retention rules rather than applying a single number to every case.

## 12. Checklist I — Audit Logs, Trustworthy Identity, and Integrity

**Diagnostic logs** support debugging and observability. **Audit logs** prove that a sensitive security or business action was performed or attempted, with distinct requirements for completeness and tamper resistance.

An audit event may look like:

```json
{
  "event": "security.permission.change.result",
  "eventId": "evt-1001",
  "actorId": "admin-7",
  "action": "REVOKE_PERMISSION",
  "targetType": "USER_ROLE",
  "targetRef": "role-42",
  "outcome": "SUCCEEDED",
  "changeId": "chg-21",
  "timestamp": "2026-11-10T02:00:00Z"
}
```

This is an illustrative schema; `actorId` must come from an **authenticated security context** with access control, not copied from a client-sent `user=admin-7` parameter. If the actor is unknown, record `UNKNOWN` explicitly per policy rather than fabricating an identity.

- [ ] Audit critical actions: login/deny, permission changes, configuration changes, key creation/deletion, data exports, privileged access.
- [ ] Record both **attempt** and **result/outcome** where needed, including success, denial, and technical failure.
- [ ] Include `eventId`/`operationId` for reconciliation and duplicate detection.
- [ ] Obtain timestamps from a trusted/synchronized source, distinguishing `occurredAt` from `ingestedAt` when necessary.
- [ ] Clearly define the milestone at which `SUCCEEDED` is emitted: commit, ack, or merely request receipt.
- [ ] Secret fields must not be logged raw in before/after snapshots; log `secretChanged=true` instead.
- [ ] Audit write paths have separated read/write permissions, retention, and health monitoring.
- [ ] Implement appropriate **tamper-evidence** mechanisms such as append-only/WORM storage, managed-key hashing/signing, or infrastructure protections—never rely on filenames alone.
- [ ] If the audit sink fails, policy defines fail-open vs. fail-closed behavior per business type and is tested.
- [ ] Reconcile business actions with audit evidence at the proper transaction boundary when completeness is required.
- [ ] Never use best-effort `logger.info(...)` as a guarantee that an audit record was durably stored.

**A hash chain alone cannot stop an attacker with full access to all keys and files.** Integrity requires key management, trusted timestamp sources, separation of duties, append-only storage, and independent verification. Non-repudiation also does not magically emerge simply from having an `actorId` field in JSON.

## 13. Checklist J — Preventing Denial of Service via Logging

A system can be attacked indirectly through log volume:

- Attackers repeatedly trigger failing requests to generate huge stack traces.
- Multi-megabyte inputs are passed into loggers.
- `DEBUG`/`TRACE` is unexpectedly enabled on a hot path.
- Async logging queues fill up, causing writers to block or drop events.
- Collector network loss causes file backlogs and ephemeral disk growth.
- Regex masking consumes excessive CPU or suffers from catastrophic backtracking.
- Loggers/encoders allocate large objects, increasing GC pauses.
- Queries with high-cardinality labels/structures overload storage/indexes.

Checklist:

- [ ] Cap string length, field count, nesting depth, and total log event size.
- [ ] Apply rate limiting/sampling **only to appropriate diagnostic event types**.
- [ ] Never arbitrarily sample mandatory audit events.
- [ ] Monitor log rate, dropped events, async queue depth, encoder latency, and bytes per event.
- [ ] Test disk quotas, rotation, and retention; define clear behavior when disks fill up.
- [ ] Bound buffer sizes, retries, and backoff for remote logging and collectors.
- [ ] Detect log storms (the same error repeating thousands of times) while retaining aggregated events/alerts sufficient for investigation.
- [ ] Avoid expensive `String.format`, JSON serialization, or `toString()` calls when the log level is disabled whenever possible.
- [ ] Prevent logger errors from triggering recursive logging back into the same logger.
- [ ] When a log sink fails, maintain an **independent metrics/health channel** to alert—do not only log `ERROR logging failed` to the broken sink.

### 13.1. Trade-Off Decisions

**Block or drop?** For diagnostic logs, dropping with a metric when the queue is full can preserve application latency. For audit/security logs, losing records may be unacceptable and requires durable storage or fail-closed behavior. Never apply a blanket “never block” or “never drop” policy to all logs.

**Truncate stack traces?** Reducing bytes and cost can be reasonable, but truncating the cause chain hinders investigation. Tailor strategies by level/event and security needs; test with deep exceptions, suppressed exceptions, and Unicode.

**Cut costs by disabling logs?** Log levels and sampling can help, but avoid turning off security/audit events required by regulations or internal policy.

## 14. Checklist K — Configuration and Runtime Changes

**Logging configuration itself** is a security surface:

| Config group | Risk |
| --- | --- |
| Log level | Enabling DEBUG exposes raw payloads, SQL, or headers |
| Appender destination | Redirecting logs to untrusted URLs/buckets |
| Encoder/layout | Disabling masking, breaking JSONL into multiline, losing escaping |
| Filters | Accidentally dropping security events or stripping exceptions |
| Retention | Deleting evidence early or retaining PII too long |
| Remote endpoint/auth | Disabling TLS validation or exposing credentials |
| Audit logger | Writing to a shared sink where records can be modified/deleted |
| Async buffers | Dropping or blocking contrary to policy |

- [ ] Review logging configurations as security configurations, with versioning and rollback.
- [ ] Runtime level/destination changes require authorization/approval per policy.
- [ ] Log/audit **who requested the change, safe before/after values, outcome, and `changeId`**, without logging secret values.
- [ ] Masking rules are not disabled simply by enabling DEBUG or switching appenders.
- [ ] Never hardcode secrets in XML/YAML or log configuration states containing secrets.
- [ ] Test startup/reload behavior on invalid config: could the backend fall back to an unsafe default?
- [ ] In clusters, verify configuration consistency across replicas after rollout.
- [ ] Check file permissions, path traversal, and symbolic links per the threat model when destinations are configurable.
- [ ] Alert when a security-critical logger unexpectedly stops emitting events.
- [ ] Use appropriate versions of dependencies, encoders, and collectors, and track security updates.

Config changes must distinguish **success**, **denied**, **failed**, **partial**, and **rolled back**. Never log `AUDIT_APPLIED` when half the replicas are still running the old configuration.

## 15. Checklist L — Third-Party Dependencies and Framework Integration

Real-world Java applications use many libraries that log simultaneously: Spring Boot, Tomcat/Jetty, JDBC drivers, Hibernate, HTTP clients, Kafka, RabbitMQ, schedulers, and cloud SDKs.

- [ ] Maintain an inventory of logging frameworks, bindings/providers, encoders, and exporters in use.
- [ ] Ensure no accidental multiple SLF4J bindings/providers cause unexpected routing or logging behavior.
- [ ] Check whether library debug modes dump `Authorization`, SQL bind values, full HTTP bodies, or raw message payloads.
- [ ] Review configurations for framework-level request logging and access logs.
- [ ] Ensure masking policies cover library-emitted events, or selectively restrict library loggers.
- [ ] Test when upgrading encoder/provider versions, as field names and `Throwable` rendering can change.
- [ ] For agents/sidecars, verify that parse errors do not cause them to log raw invalid input to stdout.
- [ ] Ensure container runtimes/node collectors do not collect raw output from another appender.
- [ ] Catalog log export destinations; avoid accidentally sending the same event through two routes.
- [ ] Scan vulnerabilities/SBOMs for logging dependencies and collector images per update policy.

Do not assume a dependency is dangerous merely because it has a DEBUG mode; risk depends on how the application enables and configures it, what data it sees, and the final sink.

## 16. Checklist M — Repeatable Security Testing

A good checklist must be backed by **test evidence**, not gut-feel checkmarks.

### 16.1. Unit Tests for Policy

| Case | Assertion |
| --- | --- |
| Unknown field | Neither raw name nor raw value appears in the event |
| Email/phone | No raw PII; sentinel matches policy |
| Password/token/cookie | Dropped or fully redacted; no suffix retained |
| Request ID > length limit | Rejected or safe fallback; raw value not printed |
| CR/LF/tab and quotes | No forged log lines; JSON remains valid |
| Null value or unexpected type | Follows schema; does not fall back to `toString()` |
| Nested object containing secret | Object is not serialized raw |
| ErrorCode outside catalog | Arbitrary value is not emitted |
| New field added to DTO | Test fails if an unclassified field is logged |
| Exception message with URL/token | Not emitted raw to unauthorized sinks |

### 16.2. Integration Tests for the Java Logging Backend

- [ ] Use the exact production encoder/formatter in tests, not just a stub formatter.
- [ ] Capture events at the Logback/Log4j 2/JUL appender or a dedicated test file.
- [ ] For JSONL, parse with a real JSON parser and assert field types.
- [ ] Test messages, arguments, MDC, `Throwable`, causes, and suppressed exceptions.
- [ ] Enable `DEBUG`/`TRACE` in test environments to uncover newly exposed raw paths.
- [ ] Exercise concurrency and thread-pool reuse to detect MDC/context leaks.
- [ ] Test rotation, compression, and startup/reload; archives must not leak raw data.
- [ ] Use distinct synthetic canary secrets per path to pinpoint leak sources.
- [ ] Verify no secrets appear in the logging backend's own status/error logs.

### 16.3. End-to-End Tests Through Collector/Storage

1. Emit a set of `eventId`s and synthetic canaries according to the test scenario.
2. Wait for data to reach the sink with acknowledgment per system semantics.
3. Query **every index/bucket/tenant** within the flow's scope.
4. Search for the raw canary, including URL/base64-encoded variants when required by the threat model.
5. Verify masking/field schemas and event counts.
6. Test retries, network timeouts/429/503, full backlogs, collector restarts, and Pod replacements.
7. Check for missing/duplicate events by ID, not just line counts.
8. Test rotation/retention and whether deleting unshipped files causes log loss.
9. Verify that unauthorized users cannot read or export logs.
10. Record test evidence containing no real secrets—only synthetic canaries.

**Never use production secrets as canaries.** If a test fails, tickets, dashboard screenshots, and CI artifacts can also become copies of sensitive data.

## 17. Checklist N — Alert and Dashboard Security

Safely stored logs can still leak through side channels:

- Alerts send full exceptions/payloads to email or broad group chats.
- Default dashboards let everyone view queries containing PII.
- CSV exports are downloaded to unmanaged personal devices.
- Log search APIs lack tenant filtering or rate limits.
- Metrics use `userId`/`requestId`/message as high-cardinality labels, exposing individual activity.
- Saved searches or incident tickets contain tokens copied from logs.

Checklist:

- [ ] Alert templates contain only **safe event code, service, severity, correlation ID**, and access-controlled links.
- [ ] Dashboards/search APIs enforce appropriate RBAC/ABAC/tenant isolation.
- [ ] Omit raw exceptions/PII from notifications unless strictly necessary.
- [ ] Control downloads/exports, sharing, and auditing of sensitive queries.
- [ ] Never use dynamic identifiers as metric labels; labels need bounded value sets.
- [ ] Links to logs must respect viewer permissions; never embed query tokens in public URLs.
- [ ] Enforce retention controls on alert notifications and incident attachments.
- [ ] Incident response tooling has procedures for handling records containing exposed credentials.

A correlation ID can still link behavior across events; do not assume it is always harmless simply because it lacks a name or email.

## 18. Acceptance Matrix by Role

Use this matrix during PR reviews or security gates:

| Role | What to verify | Evidence |
| --- | --- | --- |
| **Developer** | Event schema, safe fields, exception handling, MDC clear/restore | Unit tests, code review |
| **Tech lead** | Log levels, domain-appropriate retention, no double logging | Config review, design decision |
| **Security/AppSec** | Threat model, PII/secret classification, log injection, key/access policy | Security review, canary tests |
| **SRE/Platform** | TLS, quotas, rotation, backpressure, collector health, storage ACLs | Integration runs, dashboards |
| **Data/Compliance** | Retention, data lifecycle, audit obligations, access records | Policy/retention evidence |
| **Release owner** | CI gates, rollback, version compatibility, secret leak response | Release checklist and test reports |

These items are **suggested responsibilities**, not mandatory job titles for every organization. In small projects, one person may wear multiple hats; what matters is having **real ownership**.

### 18.1. Prioritizing Findings

**Block release** when there is evidence of:

- Passwords, tokens, or private keys appearing raw in logs/collectors/sinks outside permitted scope.
- Client input capable of forging events that lead to wrong security decisions or data leaks.
- Security-critical audit logs being completely lost without compensating policy/controls.
- Log storage/sinks lacking proper authorization or exposed publicly.
- TLS verification disabled on paths carrying sensitive logs.
- Masking failures **falling back to raw logging**.

**Require a time-bound remediation plan** when:

- Some diagnostic events lack `errorCode` or correlation context without leaking data.
- Retention/rotation lacks metrics or poses capacity risks that have not yet materialized.
- Data is masked, but schemas are inconsistent across services.
- Alerts are overly noisy and volume is not yet controlled.
- Failover testing is incomplete for some collector paths.

Actual priority should reflect impact, data sensitivity, and organizational obligations; this table is a reference framework.

## 19. Incident Response When Sensitive Data Is Found in Logs

Once a token or personal data leaks into logs, **fixing the code alone is not enough**, because older logs may still exist in many places.

1. **Confirm scope:** identify the event source, timeframe, environment, and data type. Do not continue copying raw tokens across tickets/chats.
2. **Contain the spread:** disable or reconfigure the leaking log call through change control.
3. **Restrict access:** tighten search/export permissions on affected sinks during investigation.
4. **Revoke/rotate exposed secrets** as appropriate; an exposed token is no longer safe simply because it is absent from new logs.
5. **Assess all copies:** active files, rolled archives, shipper spools, search indexes, object storage, backups, notifications, and CI artifacts.
6. **Apply deletion/retention/incident response** per legal and investigative policies; preserve minimal protected evidence if required.
7. **Add automated tests** with synthetic canaries covering the exact leak path.
8. **Identify systemic root cause:** was it a raw DTO, encoder, DEBUG config, third-party library, exception renderer, or collector?
9. **Review access logs and query audits** if there is a risk unauthorized users read the data.
10. **Verify post-fix:** scan with canaries and inspect the destination sink, not just JVM-side unit tests.

Never write a generic incident closure like “masking added” without evaluating historical data. Logs may have been replicated to buckets, indexes, or backups unknown to the source application.

## 20. Common Misconceptions

### 20.1. “We have HTTPS/TLS, so we don’t need masking”

TLS protects data in transit, but storage, dashboards, archives, and authorized readers still see the content. Data minimization and masking are still required.

### 20.2. “The JSON encoder automatically strips passwords”

Serializers primarily ensure syntax and escaping. They do not know which data is sensitive or who is allowed to read it. Field policy is a separate responsibility.

### 20.3. “Collector regexes catch every secret”

Regexes easily miss encodings, unusual field names, nested values, and malformed messages. Collectors may also sit **downstream** of where raw data has already been written to disk.

### 20.4. “Showing only the last four characters is always safe”

Partial masking can still be enough to identify subjects in small datasets, especially for emails or phone numbers. Secrets like JWTs, API keys, or passwords usually require dropping or full redaction.

### 20.5. “`SHA-256(email)` is completely anonymous”

No. Emails can be guessed, and hashes are vulnerable to dictionary attacks. Keyed HMACs also remain linkable and require a privacy assessment.

### 20.6. “DEBUG logging is off, so there’s no risk”

A runtime config change or incident debugging session can turn DEBUG on. The rule against logging secrets must hold at **every log level**.

### 20.7. “A log entry with `actorId` proves who did it”

Not if `actorId` came from client input or the process was compromised. Audits require trusted authentication contexts and integrity controls.

### 20.8. “MDC automatically propagates across all async tasks”

No. Propagation varies by thread pool, framework, and version. Failing to clear context can attribute actions to the wrong user or request ID.

### 20.9. “Logback and Log4j 2 share the same configuration”

No. Providers, appenders, encoders, filters, and `MDC`/`ThreadContext` have distinct APIs and semantics; always test on the actual backend and version.

### 20.10. “Logging more always makes investigation better”

Excessive logging increases PII exposure, costs, and flooding while lowering signal-to-noise. Contextual events with schemas, rate policies, and security controls outperform dumping entire payloads.

### 20.11. “Reading the log file means the central system has stored it”

No. File tail offset, local buffer, send attempt, remote acknowledgment, and storage durability are distinct milestones. Rotation or retention can delete unshipped backlogs.

### 20.12. “Audit logs only need `logger.info`”

Not when tamper resistance or transaction proof is required. Audits may need append-only sinks, acknowledgments, separated permissions, reconciliation, and mandatory retention.

## 21. Minimal Checklist to Paste into a Pull Request

You can use this checklist verbatim in PR descriptions:

```markdown
### Java Logging Security Gate
- [ ] No passwords, tokens, cookies, private keys, OTPs, or raw DTOs logged.
- [ ] Only classified fields enter logs; unknown fields fail-closed.
- [ ] IDs and client inputs are validated, length-bounded, and CR/LF/control-escaped.
- [ ] JSONL/structured encoders and Throwable/MDC do not leak secrets.
- [ ] No parallel logger, appender, or collector writes raw copies.
- [ ] Security events include trusted actor, action, target, outcome, and timestamp.
- [ ] Log level, retention, and remote endpoints change only via change control.
- [ ] TLS, storage ACLs, least privilege, and retention are verified.
- [ ] Capacity, queue, and disk backpressure metrics and independent alerts exist.
- [ ] Unit, integration, and end-to-end synthetic secret canary tests PASS.
- [ ] Masking failures do not fall back to raw logging.
- [ ] If auditing is mandatory, dedicated durability/integrity and failure policies exist.
```

This checklist is an **initial gate**, not a replacement for a detailed threat model in payments, healthcare, government, or other regulated domains. The key is that every critical item must have evidence—config files, tests, runbooks, or observed behavior.

## 22. How to Run a Logging Security Review

An effective review can follow this sequence:

1. **Pick a request flow** that handles sensitive data, such as login, profile update, or payment.
2. List every logging point: controller, filter, service, repository, HTTP client, DB driver, message consumer, job, and exception handler.
3. Trace the output path: console, file, sidecar, gateway, search index, archive, and alerts.
4. Send a synthetic canary through the flow and check whether raw data appears at any stage.
5. Inspect logs for valid requests, validation failures, permission denials, timeouts, retries, transaction rollbacks, and shutdowns.
6. Verify event context, trusted actors, outcomes, and boundaries corresponding to the data.
7. Deliberately test inputs with quotes, newlines, control characters, large payloads, nested secrets, and exceptions containing URLs/tokens.
8. Test rotation/restarts, collector network loss, and log read/export permissions.
9. Record risks, priorities, and owners; fix code/configs/tests and re-run.
10. Approve only when **mandatory** items have verifiable evidence, not just checked boxes.

A useful closing question during review: **“If an attacker controls all input strings of a request and can view part of a dashboard, could they make someone believe an action happened when it didn’t, or recover sensitive data from the logs?”** And equally important: **“If the log pipeline stalls or is tampered with, will we detect it and what trustworthy evidence remains?”**

## 23. Summary of Principles and Priorities

To summarize the Java Logging Security Checklist:

1. **Never putting secrets into logs** is the strongest line of defense.
2. **Allowlists, validation, and masking before the logger** reduce risk at the source.
3. **Structured encoding + injection defenses** keep logs resilient against parser breaks and forged lines.
4. **Protecting MDC, `Throwable`, third-party loggers, and all appenders** closes bypass paths.
5. **TLS, encryption at rest, IAM/RBAC, and tenant isolation** protect transit and storage.
6. **Retention, backup controls, and incident response** manage residual data risk.
7. **Trustworthy audit events, append-only/tamper-evidence, and durability policies** serve higher accountability needs than diagnostic logs.
8. **Resource budgets, backpressure, rate limits, metrics, and independent alerts** protect availability.
9. **Synthetic canary tests across every sink** provide proof that policies are actually enforced.
10. **Reviewing and updating after every code, config, library, or collector change** prevents regressions.

**Conclusion:** Secure logging is not a regex filter bolted onto the end of a pipeline—it is a **safety contract from the Java event source to storage and end users**. A strong checklist preserves investigative capability through event codes, correlation IDs, and semantically accurate outcomes while preventing secret/PII leaks, resisting tampering, controlling resource usage, and preserving evidence during incidents. Use this checklist as part of **code reviews, CI, deployment reviews, and ongoing operations**, backed by real test criteria rather than mere checkboxes.
