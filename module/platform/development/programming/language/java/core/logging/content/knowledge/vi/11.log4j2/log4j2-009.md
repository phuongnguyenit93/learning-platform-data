# Cầu nối Log4j2 trong Java Logging: hướng chuyển tiếp, cấu hình và tránh vòng lặp

**Cầu nối Log4j2 (Log4j 2 bridge/adapter)** là thành phần giúp ứng dụng hoặc thư viện đang dùng một **logging API** có thể gửi sự kiện tới một **logging implementation** khác, mà không phải sửa từng lời gọi log trong mã nguồn. Chẳng hạn, mã viết bằng SLF4J có thể được xử lý bởi Log4j 2 Core; hoặc mã viết trực tiếp bằng Log4j 2 API có thể chuyển sự kiện tới SLF4J và sau đó đến Logback.

Điểm quan trọng nhất: **cầu nối có chiều**. `log4j-slf4j2-impl` và `log4j-to-slf4j` **không làm cùng một việc**. Chọn sai chiều hoặc đưa hai cầu nối ngược chiều vào cùng runtime có thể tạo tuyến chuyển tiếp vòng tròn, làm logging lỗi hoặc không khởi tạo được.

Bài học tập trung vào **Log4j 2** và giải thích API, bridge, backend, lựa chọn dependency, ví dụ Java 17+ với Maven, cách kiểm tra log thực tế và các lỗi cấu hình dễ gặp.

## 1. Vì sao cần cầu nối logging?

Ứng dụng Java thường sử dụng nhiều thư viện:

- Mã ứng dụng có thể gọi `org.slf4j.Logger`.
- Một thư viện khác gọi `org.apache.logging.log4j.Logger` của Log4j 2 API.
- Một thư viện cũ hơn dùng `java.util.logging.Logger` (JUL).
- Một số thành phần dùng Apache Commons Logging (JCL) hoặc Java Platform Logging.

Nếu mỗi API dùng một backend độc lập, ứng dụng có thể có **nhiều cách đặt level, nhiều formatter, nhiều đích và nhiều file cấu hình**, gây khó vận hành. Cầu nối tạo một hướng chuyển tiếp để những sự kiện cần thiết có thể được xử lý bởi một **backend chính được chọn có chủ đích**.

```text
Các API gọi log khác nhau
    |
    +-- SLF4J ----------------------+
    +-- JUL ------------------------+--> bridge phù hợp --> Log4j 2 API --> Log4j Core --> appender
    +-- Apache Commons Logging ----+
    +-- Log4j 2 API ------------------------------- trực tiếp -------+
```

Sơ đồ này thể hiện **mô hình Log4j 2 Core làm đích cuối**. Nếu ứng dụng chọn **Logback làm backend chính**, đường đi được đảo lại ở nhánh Log4j 2 API:

```text
Log4j 2 API --> log4j-to-slf4j --> SLF4J --> Logback --> appender
SLF4J ----------------------------------------^
```

Trong cả hai trường hợp, **ứng dụng không cần khởi tạo hai backend cùng quản lý một event**. Chọn một đích xử lý chính, sau đó thêm các adapter cần thiết để đưa những API còn lại đến đích đó.

### Các thuật ngữ dễ nhầm

| Thành phần | Chức năng | Ví dụ |
| --- | --- | --- |
| **Logging API** | Interface/lời gọi mà mã Java trực tiếp dùng | Log4j 2 API, SLF4J API, JUL API |
| **Backend/implementation** | Xử lý event và cấu hình đầu ra | Log4j Core, Logback, JUL |
| **Bridge/adapter** | Nhận event từ API này và chuyển sang API khác | `log4j-slf4j2-impl`, `log4j-to-slf4j` |
| **Appender/handler** | Phân phối event đã qua backend tới đích ghi | Log4j Console/RollingFile, JUL ConsoleHandler |
| **Facade** | API giúp mã ứng dụng ít lệ thuộc backend | SLF4J, Log4j API trong thiết kế tách API/Core |

**Bridge không phải appender.** Cầu nối giải quyết câu hỏi “mã đang gọi API A thì backend B có nhận được không?”; appender giải quyết “sự kiện đã tới backend thì được gửi đến console, file hay collector nào?”.

## 2. Bảng chiều chuyển tiếp quan trọng của Log4j 2

| API phát log | Đích xử lý mong muốn | Artifact/cầu nối thường dùng | Ghi chú |
| --- | --- | --- | --- |
| **SLF4J 2.x** | Log4j 2 API → Log4j Core | `log4j-slf4j2-impl` | Cấu hình đầu ra bằng Log4j 2 |
| **SLF4J 1.7.x** | Log4j 2 API → Log4j Core | `log4j-slf4j-impl` | Dành cho nhánh SLF4J cũ; không dùng thay cho adapter 2.x |
| **Log4j 2 API** | SLF4J → backend như Logback | `log4j-to-slf4j` | **Chiều ngược** với hai artifact trên |
| **JUL** | Log4j 2 API → Log4j Core | `log4j-jul` | Thường cần cấu hình `java.util.logging.manager` sớm khi khởi động JVM |
| **Apache Commons Logging (JCL)** | Log4j 2 API → Log4j Core | `log4j-jcl` | Cân nhắc phiên bản JCL và logging environment hiện có |
| **API Log4j 1.x cũ** | Log4j 2 API/Core | `log4j-1.2-api` | Lớp tương thích trong quá trình di trú; không bảo đảm 100% mọi API cũ |

Tên các artifact thuộc nhóm **Apache Log4j 2**. Dependency chính xác, phạm vi Maven/Gradle và khả năng hỗ trợ một API cũ cần kiểm tra theo phiên bản hệ thống. Bảng không có nghĩa mọi ứng dụng phải cài hết những cầu nối này: **chỉ thêm nhánh API thực sự được sử dụng**.

### Hai quy tắc an toàn cần nhớ

1. **Đã chọn Log4j Core làm backend:** nhận SLF4J 2.x qua `log4j-slf4j2-impl`; không thêm `log4j-to-slf4j`.
2. **Đã chọn Logback làm backend:** nhận lời gọi Log4j 2 API qua `log4j-to-slf4j`; không thêm `log4j-slf4j2-impl` hoặc `log4j-slf4j-impl`.

Không đặt `log4j-slf4j2-impl` và `log4j-slf4j-impl` đồng thời vào runtime để “hỗ trợ cả hai phiên bản”: hai nhánh SLF4J có yêu cầu API khác nhau; chọn theo phiên bản SLF4J hiện có và giải quyết dependency tree một cách nhất quán.

## 3. Mô hình A: SLF4J 2.x → Log4j 2 Core

Đây là trường hợp hay gặp khi mã nghiệp vụ hoặc thư viện gọi SLF4J, nhưng bạn muốn **Log4j 2 Core** chịu trách nhiệm ghi log.

```text
OrderService dùng SLF4J API
          |
          | LoggerFactory.getLogger(...)
          | LOG.info(...)
          v
      SLF4J 2.x
          |
          | log4j-slf4j2-impl
          v
      Log4j 2 API
          |
          v
      Log4j 2 Core
          |
          +--> ConsoleAppender
          +--> RollingFileAppender
```

Dependency thông thường gồm `slf4j-api`, `log4j-slf4j2-impl`, `log4j-api` và `log4j-core` (có thể nhận một số artifact theo transitive dependency). Để quản lý version, sử dụng **Log4j BOM** hoặc dependency management của framework. Việc chỉ thêm `log4j-slf4j2-impl` **không thay cho một backend/implementation đã được cấu hình đầy đủ** nếu mong muốn Log4j Core ghi ra file/console.

Ví dụ mã ứng dụng dùng SLF4J:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class OrderService {
    private static final Logger LOG =
            LoggerFactory.getLogger(OrderService.class);

    public void create(String orderId) {
        LOG.info("event=order_created orderId={}", orderId);
    }
}
```

Đây là một **lớp minh họa**, không có `main` và cần dependency SLF4J. Class không import `log4j-core` hoặc biết tên appender. Nếu chuyển backend trong tương lai, mã sử dụng API SLF4J có thể giữ nguyên trong nhiều trường hợp.

Một thư viện dùng trực tiếp Log4j 2 API cũng có thể gửi log tới **chính Log4j Core** mà không qua bridge:

```java
// Fragment trong lớp có dependency Log4j API.
private static final org.apache.logging.log4j.Logger LOG =
        org.apache.logging.log4j.LogManager.getLogger(OrderService.class);
```

Nếu hai API cùng gửi về Log4j Core, hãy đặt cấu hình level, layout và appender ở **Log4j 2** để thống nhất kết quả.

## 4. Ví dụ Java 17 + Maven: hai API cùng ghi qua Log4j Core

Ví dụ này làm rõ cơ chế hơn bằng một chương trình dùng **hai API**:

- `org.slf4j.Logger` được bridge sang Log4j 2 bằng `log4j-slf4j2-impl`.
- `org.apache.logging.log4j.Logger` đi trực tiếp vào Log4j 2.
- Một `Console` appender ghi ra **stderr**, với pattern cố định để đọc output.

Chương trình chạy với **JDK 17 và Maven**. Các phiên bản được ghim để có một ví dụ cụ thể, **không phải tuyên bố phiên bản mới nhất**.

Cấu trúc dự án:

```text
log4j2-bridge-demo/
├── pom.xml
└── src/main/
    ├── java/com/example/logging/Log4j2BridgeDemo.java
    └── resources/log4j2.xml
```

### 4.1. `pom.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>log4j2-bridge-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <log4j.version>2.26.1</log4j.version>
    </properties>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.apache.logging.log4j</groupId>
                <artifactId>log4j-bom</artifactId>
                <version>${log4j.version}</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.17</version>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-api</artifactId>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-core</artifactId>
            <scope>runtime</scope>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-slf4j2-impl</artifactId>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
                <configuration>
                    <mainClass>com.example.logging.Log4j2BridgeDemo</mainClass>
                    <classpathScope>runtime</classpathScope>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

**Kiểm tra POM:** `log4j-bom` cố định các version của `log4j-api`, `log4j-core` và `log4j-slf4j2-impl` cùng nhánh. `slf4j-api` được khai báo riêng vì Log4j BOM không nhất thiết quản lý version SLF4J. Chuỗi `${log4j.version}` trong POM là **Maven property interpolation**, không có dấu backslash trong nội dung XML thực tế.

### 4.2. `log4j2.xml`

Đặt file `src/main/resources/log4j2.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="Console" target="SYSTEM_ERR">
            <PatternLayout pattern="%level | %logger - %msg%n"/>
        </Console>
    </Appenders>
    <Loggers>
        <Root level="info">
            <AppenderRef ref="Console"/>
        </Root>
    </Loggers>
</Configuration>
```

File này dùng cú pháp của **Log4j 2** (không phải `logback.xml`). `Root level="info"` nhận INFO trở lên. `PatternLayout` cố tình không có timestamp để dễ kiểm chứng; triển khai thực tế nên bổ sung thời điểm có múi giờ và ngữ cảnh truy vết.

### 4.3. `Log4j2BridgeDemo.java`

```java
package com.example.logging;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class Log4j2BridgeDemo {
    private static final Logger SLF4J_LOG =
            LoggerFactory.getLogger(Log4j2BridgeDemo.class);

    private static final org.apache.logging.log4j.Logger LOG4J_LOG =
            org.apache.logging.log4j.LogManager.getLogger(
                    "com.example.logging.native");

    public static void main(String[] args) {
        System.out.println("slf4jName=" + SLF4J_LOG.getName());

        SLF4J_LOG.info("source=slf4j event=accepted id={}", "req-17");
        LOG4J_LOG.warn("source=log4j2 event=retry attempt={}", 2);

        System.out.println("completed=true");
    }
}
```

Class dùng SLF4J cho event đầu và Log4j API cho event thứ hai; **không** gọi hai API cho cùng một event, nên không gây ghi trùng do mã nguồn. Cả hai API có thể cùng đi tới `Console` appender Log4j 2 đã cấu hình.

### 4.4. Chạy và kiểm tra

Trong thư mục chứa `pom.xml`:

```bash
mvn -q compile exec:java
```

**Các dòng stdout do chương trình in, theo đúng thứ tự:**

```text
slf4jName=com.example.logging.Log4j2BridgeDemo
completed=true
```

**Các dòng logging từ ứng dụng trên stderr, theo đúng pattern:**

```text
INFO | com.example.logging.Log4j2BridgeDemo - source=slf4j event=accepted id=req-17
WARN | com.example.logging.native - source=log4j2 event=retry attempt=2
```

Plugin Maven hoặc môi trường chạy có thể in thông tin build riêng; nếu terminal gộp stdout và stderr, **thứ tự xen kẽ giữa hai luồng không được đảm bảo**. Kết quả cần kiểm tra là logger SLF4J và logger Log4j API đều được ghi **bởi cùng Log4j 2 PatternLayout** với một dòng cho mỗi event.

Nếu bỏ provider `log4j-slf4j2-impl` khỏi runtime và không thay bằng provider SLF4J khác, lệnh `SLF4J_LOG.info(...)` sẽ không còn được Log4j Core nhận theo đường này; SLF4J 2.x có thể cảnh báo không tìm thấy provider rồi dùng NOP logger. Ngược lại, lời gọi Log4j API có thể vẫn đi tới Log4j Core. Đây là cách phân biệt **thiếu bridge** với **sai appender**.

## 5. Mô hình B: Log4j 2 API → SLF4J → Logback

Một ứng dụng dùng **Logback làm backend chính** có thể phụ thuộc một thư viện phát log qua Log4j 2 API. Bạn muốn giữ cấu hình và các appender của Logback, không khởi tạo Log4j Core riêng chỉ để ghi log từ thư viện.

Khi đó:

```text
Thư viện dùng Log4j API
           |
           v
      log4j-to-slf4j
           |
           v
        SLF4J
           |
           v
   Logback (backend chính)
           |
           +--> ConsoleAppender / RollingFileAppender
```

Các thành phần điển hình gồm `log4j-api`, `log4j-to-slf4j`, `slf4j-api` và một backend SLF4J như `logback-classic`, với **phiên bản tương thích**. Không cài `log4j-core` chỉ để “kết hợp” nếu mục tiêu là đưa toàn bộ event về Logback; không cài `log4j-slf4j2-impl` ở cấu hình này.

**Code thư viện không nhất thiết đổi:**

```java
// Fragment bên trong thư viện đã dùng Log4j 2 API.
private static final org.apache.logging.log4j.Logger LOG =
        org.apache.logging.log4j.LogManager.getLogger(LibraryWorker.class);
```

Với `log4j-to-slf4j`, các lời gọi Log4j API được chuyển về SLF4J, sau đó backend Logback xử lý. `LibraryWorker` ở đây là lớp minh họa; fragment không chạy độc lập.

Trong Spring Boot, `spring-boot-starter-logging` thường cung cấp Logback và các adapter cần cho cấu hình mặc định của Boot. Nếu chuyển ứng dụng sang `spring-boot-starter-log4j2`, phải xem lại dependency và loại bỏ các bridge/provider xung đột thay vì chỉ thêm starter mới lên trên starter cũ. Không mặc định mọi phiên bản Boot có cùng dependency tree.

## 6. Vì sao hai bridge ngược chiều không được cài cùng nhau?

Đây là lỗi nghiêm trọng nhất trong chủ đề này:

```text
SLF4J API
   |
   | log4j-slf4j2-impl
   v
Log4j 2 API
   |
   | log4j-to-slf4j
   v
SLF4J API
   |
   +--> quay lại Log4j 2 API, ...
```

Hai adapter ở trên tạo một **đường chuyển tiếp vòng tròn**, trái với mục tiêu có một backend cuối. Tùy phiên bản, cấu hình có thể bị framework từ chối, phát lỗi khi khởi tạo hoặc rơi vào tình trạng logging không đúng; **không thử xử lý bằng cách tăng thêm provider**.

**Không kết hợp:**

- `log4j-to-slf4j` với `log4j-slf4j2-impl`;
- `log4j-to-slf4j` với `log4j-slf4j-impl`;
- `log4j-slf4j2-impl` với `log4j-slf4j-impl` trong cùng một đường runtime.

Tuy nhiên, việc vừa có **`slf4j-api`** vừa có **`log4j-api`** không tự động là lỗi: hai API có thể tồn tại để các thư viện biên dịch và chạy. Điều cần kiểm soát là **implementation/provider/bridge nào đang được chọn**.

### Cách tự kiểm tra bằng Maven

```bash
mvn dependency:tree
```

Nếu dự án có cây dependency lớn, có thể lọc các nhóm liên quan:

```bash
mvn dependency:tree -Dincludes=org.apache.logging.log4j:*,org.slf4j:*,ch.qos.logback:*
```

Đây là lệnh Maven Dependency Plugin thông thường; cú pháp filter có thể cần escape/quote phù hợp với shell đang dùng. Quan sát cả **dependency trực tiếp và transitive**, vì starter hoặc thư viện có thể kéo vào `log4j-to-slf4j`, `logback-classic`, `slf4j-simple` hay provider khác.

Tập trung vào câu hỏi: “**Mã dùng API nào? Backend duy nhất nào sẽ ghi cuối cùng? Mỗi API khác phải đi qua đúng một hướng bridge nào?**”

Nếu cần loại bỏ dependency đi kèm thư viện, dùng `<exclusions>` của Maven hoặc cơ chế tương đương trong Gradle ở đúng dependency đang kéo bridge/provider không mong muốn. Việc loại một JAR chỉ dựa vào tên mà không kiểm tra ai dùng có thể làm mất log của thư viện khác.

## 7. Bridge JUL (java.util.logging) vào Log4j 2

Một ứng dụng hoặc thư viện có thể viết log bằng JDK API:

```java
// Fragment chỉ dùng java.util.logging.
java.util.logging.Logger jul =
        java.util.logging.Logger.getLogger("com.example.legacy");
jul.info("event=legacy_ready");
```

Muốn chuyển các lời gọi JUL tới Log4j API/Core, Log4j 2 cung cấp **`log4j-jul`**. Một cấu hình khởi động thường dùng là đưa artifact vào runtime rồi truyền **JVM system property**:

```bash
java -Djava.util.logging.manager=org.apache.logging.log4j.jul.LogManager -cp "..." com.example.Main
```

Lệnh này là **mẫu minh họa**, không chạy được độc lập vì `...` và `com.example.Main` đại diện classpath/lớp main của ứng dụng thực. Cần cấu hình classpath chứa Log4j 2 modules tương thích.

**Tại sao phải khai báo ở dòng lệnh JVM?** `java.util.logging.LogManager` có thể được khởi tạo rất sớm và chỉ chọn implementation của nó trong quá trình khởi tạo. Đặt property sau khi JUL đã được khởi tạo thường quá muộn để thay thế LogManager. Không trông đợi gán `System.setProperty` trong một service đang chạy sẽ tái cấu hình đường bridge JUL đúng như việc khởi động JVM.

Có các phương án cài đặt/khởi tạo bridge JUL khác được tài liệu Log4j hỗ trợ; cần chọn theo kiến trúc framework/container. Cần đặc biệt thận trọng khi chạy trong application server đã tự quản lý JUL.

**Nhầm lẫn thường gặp:** `log4j-jul` hướng **JUL → Log4j 2 API**; `log4j-to-jul` hướng **Log4j API → JUL**. Tên tương tự nhau nhưng đích cuối hoàn toàn khác. Cũng không đặt đồng thời `jul-to-slf4j` và `slf4j-to-jul` theo hai chiều khi chúng dẫn về nhau.

## 8. Bridge các API khác và di trú ứng dụng cũ

Một ứng dụng lớn có thể mang thư viện sử dụng JCL hoặc API Log4j 1.x. Khi đích chính là Log4j Core, các module tương ứng có thể giúp gom log:

| Nguồn | Module liên quan | Ghi chú quan trọng |
| --- | --- | --- |
| Apache Commons Logging | `log4j-jcl` | Kiểm tra JCL version, cơ chế discovery và các bridge JCL khác đã có |
| Log4j 1.x API | `log4j-1.2-api` | Hỗ trợ một phần API/cấu hình cũ; có thể cần sửa code và cấu hình khi di trú |
| Java Platform Logging (`System.Logger`) | `log4j-jpl` | Tùy cơ chế `System.LoggerFinder`, Java module và thời điểm khởi tạo |
| SLF4J 1.x | `log4j-slf4j-impl` | Dành cho mã/API 1.x, không nhầm với `log4j-slf4j2-impl` |

**Di trú không chỉ là thay JAR.** Với API Log4j 1.x, các lớp, appender, configuration syntax và lifecycle có thể khác Log4j 2. Tránh tiếp tục triển khai runtime Log4j 1.x cũ chỉ để né việc sửa cấu hình. Đánh giá module tương thích, tìm API bị thiếu và kiểm thử cả lúc khởi động, quay vòng file, exception stack trace và shutdown.

Nếu thư viện dùng SLF4J nhưng app chính dùng Log4j 2, không cần đổi toàn bộ `LoggerFactory` sang `LogManager`: một bridge đúng chiều giải quyết vấn đề. Nếu một thư viện Java thuần chỉ muốn cung cấp logging API cho ứng dụng chủ, thư viện nên tránh ép ứng dụng chọn một logging backend cụ thể.

## 9. Cầu nối tác động gì đến level, exception và context?

### Level

Các API không có cùng bộ level. Log4j 2 có `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL`; SLF4J chủ yếu dùng `TRACE` đến `ERROR`; JUL dùng `FINE`, `INFO`, `WARNING`, `SEVERE` và những mức khác.

Trong một bridge, level được **chuyển đổi** theo chính sách của module. Khi Log4j API chuyển tới SLF4J, những mức không có tương đương trực tiếp (chẳng hạn `FATAL`) phải được ánh xạ; không thể yêu cầu backend đích giữ nguyên đầy đủ mọi ngữ nghĩa của API nguồn.

Khi không thấy một event, kiểm tra:

1. Logger **API nguồn** có cho phép mức tương ứng không?
2. Bridge có thực sự được chọn và đang chạy đúng chiều không?
3. Logger/filter của **backend đích** có cho phép event không?
4. Appender/collector có ghi và giữ event không?

### Throwable

Bridge thích hợp thường chuyển theo đối tượng exception/cấu trúc sự kiện của API nguồn, nhưng **việc hiển thị stack trace cuối cùng** do layout/encoder/appender quyết định. Ví dụ với SLF4J:

```java
// Fragment trong catch block đã có log, requestId và Throwable e.
log.error("event=payment_failed requestId={}", requestId, e);
```

Không coi `e.getMessage()` là dữ liệu thay thế stack trace; hãy truyền `Throwable` vào API và kiểm tra đích ghi có thể hiện `Caused by`/stack frames hay không.

### MDC / ThreadContext

SLF4J hỗ trợ MDC, trong khi Log4j 2 có `ThreadContext`. Bridge có thể ánh xạ một phần ngữ cảnh, nhưng khả năng chuyển và hiển thị phụ thuộc implementation; **không giả định mọi MDC key, marker, location info hoặc thuộc tính có ngữ nghĩa giống nhau ở mọi bridge**.

Khi dùng executor/async/reactive, context theo thread có thể không tự đi theo request. Cần truyền, làm sạch context và cấu hình layout chứa những field cần thiết, chẳng hạn `requestId`/`traceId`. Không tạo tên logger theo request hoặc log token/credentials chỉ để phục vụ tương quan.

### Độ trễ và lượng dữ liệu

Mỗi bridge thêm một lớp chuyển đổi; nối nhiều bridge liên tiếp có thể tăng chi phí và làm khó debug. Với ứng dụng có yêu cầu throughput cao, nên ưu tiên đường đi **trực tiếp từ API nguồn sang backend chính** thay vì nhiều adapter nối tầng không cần thiết. Khi dùng async appender, cần xem queue capacity, chính sách drop/backpressure và shutdown để tránh thất thoát bản ghi.

## 10. Cách chọn backend khi triển khai Spring Boot

Trong một ứng dụng Spring Boot điển hình, backend mặc định từ starter logging thường là **Logback**. Nếu sử dụng Logback làm đích cuối và thư viện gọi Log4j API, đường **`log4j-to-slf4j`** là mô hình thường gặp.

Nếu dự án quyết định chuyển sang **Log4j 2 Core**, có thể dùng `spring-boot-starter-log4j2` thay cho starter logging mặc định, đồng thời rà soát các starter/library khác có kéo Logback hoặc bridge ngược chiều.

Một quy trình quyết định:

1. Xác định backend mong muốn: **Logback** hay **Log4j Core**.
2. Xem dependency tree thực tế, không suy đoán chỉ từ import trong một lớp.
3. Với **Logback**: giữ provider Logback và dùng `log4j-to-slf4j` nếu cần nhận Log4j API.
4. Với **Log4j Core**: giữ Log4j Core và dùng `log4j-slf4j2-impl` nếu nhận SLF4J 2.x; kiểm tra các bridge JUL/JCL nếu cần.
5. Loại bỏ provider/bridge chiều ngược và những backend không còn là đích cuối.
6. Dùng cấu hình backend thích hợp: `logback-spring.xml` cho Logback được Spring Boot nạp, hoặc `log4j2-spring.xml`/`log4j2.xml` theo tích hợp Log4j 2.
7. Chạy thử một event từ mỗi API trong dependency tree và đối chiếu **một backend cuối**, level, logger name, throwable, correlation ID và đích ghi.

**Không dùng file `logback-spring.xml` để cấu hình Log4j Core**, và cũng không dựa vào `log4j2.xml` để điều khiển Logback: mỗi backend có cú pháp và cơ chế nạp khác nhau.

## 11. Các lỗi thường gặp khi cấu hình bridge Log4j2

| Triệu chứng | Nguyên nhân khả dĩ | Hướng khắc phục |
| --- | --- | --- |
| SLF4J log không xuất hiện, Log4j API vẫn in | Không có provider SLF4J thích hợp hoặc dùng provider sai version | Kiểm tra `log4j-slf4j2-impl` với SLF4J 2.x, classpath và warnings |
| Báo lỗi vòng lặp logging | Có `log4j-to-slf4j` và `log4j-slf4j2-impl`/binding ngược | Chọn một chiều, loại bridge không mong muốn |
| SLF4J báo “multiple providers” | Nhiều provider như Logback và Log4j bridge cùng có mặt | Chỉ giữ provider đúng backend đã chọn |
| Dùng SLF4J 2.x nhưng chỉ có `log4j-slf4j-impl` | Binding dành cho SLF4J 1.x | Chuyển sang `log4j-slf4j2-impl` tương thích |
| Dùng Logback nhưng cài `log4j-slf4j2-impl` | Đã chọn bridge tới Log4j thay vì tới SLF4J | Dùng `log4j-to-slf4j` và provider Logback |
| JUL log chưa đi tới Log4j | Thiếu `log4j-jul` hoặc `java.util.logging.manager` không được thiết lập sớm | Cấu hình bridge đúng lúc khởi động JVM |
| JCL log đi đường khác | Có nhiều bridge JCL hoặc cơ chế discovery khác | Rà soát JCL API và `log4j-jcl`/adapter cạnh tranh |
| `DEBUG` không hiện | Logger/backend đích đặt ngưỡng `INFO` hoặc filter ở appender | Kiểm tra level/filter theo category và appender |
| Có event hai lần | Appender additivity, nhiều đường API, hoặc mã ghi trùng | Kiểm tra 1 event phát qua đúng một tuyến và cấu hình additivity |
| Không ghi stack trace | Throwable không được truyền hoặc layout bỏ exception | Dùng overload nhận Throwable và layout có exception |
| Log4j 2 config không được nạp | File sai tên/vị trí hoặc backend thực tế không phải Log4j Core | Kiểm tra `log4j2.xml`, classpath và startup logs |
| Có vấn đề an ninh sau khi thêm bridge | Chọn version không được hỗ trợ hoặc kéo dependency cũ | Dùng version được duy trì, quét dependency và tuân thủ chính sách cập nhật |

Đừng sửa sự cố “không thấy log” bằng cách thêm tất cả artifact có tên `log4j`. Điều đó thường làm tăng số đường chuyển tiếp, xung đột provider và gánh nặng xác định backend cuối.

## 12. Checklist để chứng minh cấu hình bridge đúng

1. **Vẽ sơ đồ một chiều**: với mỗi API nguồn, đi đến một backend cuối và appender rõ ràng.
2. **Rà soát runtime classpath**: bảo đảm không có hai bridge SLF4J↔Log4j đi ngược nhau; chỉ giữ provider phù hợp với SLF4J API đang dùng.
3. **Chọn version tương thích**: dùng BOM/dependency management, không trộn ngẫu nhiên phiên bản Log4j 2 và SLF4J.
4. **Kiểm tra cấu hình backend**: `log4j2.xml`/Log4j Core hoặc `logback.xml`/Logback đúng nơi.
5. **Phát một event từ mỗi API**: kiểm tra số log thực tế, tên logger, level, message và throwable.
6. **Đối chiếu đích ghi**: console stdout/stderr, file và collector phải nhận đúng event theo thiết kế.
7. **Kiểm tra bridge JUL sớm**: nếu dùng `log4j-jul`, property LogManager phải có từ lúc JVM khởi động hoặc dùng phương án chính thức tương thích runtime.
8. **Kiểm tra context xuyên luồng**: requestId/traceId có được truyền và làm sạch đúng, tránh lẫn request.
9. **Không ghi dữ liệu nhạy cảm**: token, password, cookie phiên và dữ liệu người dùng không cần thiết không được đưa vào message/context.
10. **Chạy lại sau mỗi thay đổi dependency**: cả startup, lỗi exception và shutdown phải được kiểm chứng; không chỉ nhìn số JAR đã tải thành công.

**Kết luận:** “Cầu nối Log4j2” không phải một JAR chung dùng trong mọi hệ thống. Chọn bridge phải dựa trên **API nào đang phát log** và **backend nào được phép ghi cuối cùng**. Khi chọn đúng chiều, mã thư viện viết bằng SLF4J, Log4j 2 API, JUL hoặc JCL có thể cùng được quản lý bởi một hệ logging nhất quán; khi chọn sai, hệ thống dễ gặp vòng lặp, ghi trùng, mất log và lỗi khởi tạo.
