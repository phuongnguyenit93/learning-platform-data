# Async Logger in Log4j 2 — Asynchronous Logging with LMAX Disruptor

## 1. What Is an Async Logger?

**Async Logger** is the asynchronous logging mechanism of **Apache Log4j 2**. Instead of forcing the request-handling thread to perform most of the logging work to an appender/file/console/network at the exact moment `logger.info(...)` is called, Async Logger hands the event off to a **ring buffer** managed by the **LMAX Disruptor** library. A background thread consumes the events and performs the logging work behind the scenes.

The primary goal is to **reduce the time business threads spend waiting on logging work**, especially under high log volume. This can increase throughput and reduce latency in many configurations, but it is **not an absolute guarantee that logging will be faster, lossless, always strictly ordered across threads, or durably persisted**.

For example, an order-processing request calls:

```java
// Illustrative snippet in a service that already has a Log4j 2 Logger.
logger.info("Order {} accepted", orderId);
```

When using Async Logger, the typical path is:

```text
Application thread
  |
  | logger.info("Order {} accepted", orderId)
  v
Level/filter check + event data preparation
  |
  | Publish event
  v
LMAX Disruptor ring buffer (bounded buffer)
  |
  |                            Background consumer thread
  +--------------------------------------> |
                                          v
                                  Logger configuration
                                          |
                                  Layout + Appender
                                          |
                                  Console/File/Network
                                          |
                                  Collector/Storage
```

**Note on boundaries:** In full async and mixed async modes, the exact point where checks, formatting, and filtering occur may differ. Some work (including part of message preparation or formatting) still happens on the caller thread, depending on the API and configuration. The diagram illustrates the handoff mechanism; it does not mean all logging work is deferred.

Async Logger is part of the **logging architecture**; it does not make business operations asynchronous and does not replace database transactions, message brokers, or durable audit systems.

## 2. Comparing Synchronous Logger, Async Logger, and AsyncAppender

Log4j 2 offers more than one way to achieve asynchronous logging. It is important to distinguish them clearly:

| Approach | Mechanism | Advantages | Caveats |
| --- | --- | --- | --- |
| **Synchronous logger + synchronous appender** | The caller executes event output through the standard pipeline. | Easy to understand, simple, easy to observe errors near the call site. | Slow I/O can increase response time. |
| **Async Logger** | Uses **LMAX Disruptor** and a background consumer to pass events to appenders. | Targets high throughput, low latency, and reduced caller wait overhead under suitable conditions. | Requires the Disruptor dependency; bounded ring buffer; requires queue-full and shutdown policies. |
| **AsyncAppender** | An appender with a queue (typically backed by `ArrayBlockingQueue`) that delegates writes to downstream appenders. | Can introduce asynchrony to a specific appender branch without changing the logger type. | Buffer/error appender behavior differs from Async Logger; must be evaluated per configuration. |

**Async Logger is not the same as AsyncAppender.** Although both use a background thread, they rely on separate components and mechanisms. Placing an `AsyncAppender` behind an Async Logger **does not automatically make logging twice as fast**; it can introduce two layers of buffering, increasing latency, memory usage, and difficulty in tracing events.

**Synchronous logging is not always slower in every workload.** With low log volume, CPU-constrained containers, or already optimized appenders, thread-handoff overhead may provide little benefit. Choose the mechanism based on benchmarks and real load data.

## 3. Disruptor Mechanism and Ring Buffer

LMAX Disruptor is a library for inter-thread event communication. In Async Logger, it uses a **fixed-capacity ring buffer**: a circular container with pre-allocated slots to reduce allocation overhead and support efficient event processing.

```text
Producer threads                  Ring buffer                  Consumer
     P1 ---> publish ---+       +------+------+------+------+      |
                        +------>| ev01 | ev02 | ev03 |  ... |-----> appender
     P2 ---> publish ---+       +------+------+------+------+      |
                                  ^                          |
                              slots reused after consumer processes them
```

Key properties:

- **Bounded capacity:** The buffer does not grow indefinitely. When producers generate logs sustainably faster than the consumer/appender can process them, the buffer fills up.
- **Publish and consume:** Producers publish events; the consumer processes them and releases slots for reuse.
- **Reduced contention:** Disruptor's design targets efficient event exchange in multi-threaded environments, though actual performance still depends on appender type, log payload, and configuration.
- **Not a storage system:** Events in the ring buffer exist **only in process memory**. If the JVM is killed, crashes, or loses power before flushing, pending records may be lost.
- **Not a transaction:** A normal return from `logger.info(...)` does not prove that data has been written to a file, received by a collector, indexed, or durably stored.

An asynchronous pipeline has multiple "completion points": event created, enqueued, picked up by the consumer, written by the appender, received by the collector, and stored. When analyzing operational guarantees, you must specify **which point** is being discussed.

### Event Ordering

When a single thread logs sequentially to the same typical Async Logger pipeline, events are generally processed in their publish order. **Do not rely on this to infer absolute business ordering across multiple threads, multiple JVMs, multiple appenders, or multiple services**. Timestamps, correlation IDs, event IDs, and transaction boundaries must still be designed when ordering affects conclusions.

## 4. Two Ways to Enable Async Logger in Log4j 2

Log4j 2 supports **full asynchronous** and **mixed synchronous/asynchronous** modes. These are two distinct configuration approaches.

### 4.1. Full Async: All Loggers Use Async Logger ContextSelector

To make most loggers use the Async Logger mechanism, set the system property **before Log4j 2 initializes**:

```text
log4j2.contextSelector=org.apache.logging.log4j.core.async.AsyncLoggerContextSelector
```

When running a Java application:

```bash
java -Dlog4j2.contextSelector=org.apache.logging.log4j.core.async.AsyncLoggerContextSelector -jar app.jar
```

This is a **command template**; `app.jar` is just a placeholder name for a deployment artifact, not a file created by this lesson. Another class name that may be used in some scenarios is `org.apache.logging.log4j.core.async.BasicAsyncLoggerContextSelector`: this option uses a single shared logger context and Disruptor across the JVM, whereas `AsyncLoggerContextSelector` manages contexts per classloader.

**Critical rule:** Once you use an Async Logger ContextSelector, configure loggers using **standard `<Root>` and `<Logger>` elements**, and do not also use `<AsyncRoot>` or `<AsyncLogger>`. Combining both can create **two asynchronous boundaries**, increasing overhead and complexity instead of performance.

Example configuration skeleton for full async:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration>
  <Appenders>
    <Console name="Console" target="SYSTEM_OUT">
      <PatternLayout pattern="%level|%msg%n"/>
    </Console>
  </Appenders>
  <Loggers>
    <Root level="INFO">
      <AppenderRef ref="Console"/>
    </Root>
  </Loggers>
</Configuration>
```

Use this XML configuration **together with** the ContextSelector system property and the Disruptor dependency. The XML defines destinations and levels; the **ContextSelector** is what enables full async. Without the property, the `<Root>` above is a standard synchronous logger configuration.

**Early runtime configuration:** Do not rely on calling `System.setProperty(...)` after a static logger has already initialized. The property must be set before the first logging context initialization. In Spring Boot, application servers, or containers, use a configuration mechanism that takes effect at the proper startup phase.

### 4.2. Mixed Async: Only Selected Loggers or Root Are Asynchronous

Keep `log4j2.contextSelector` at its default value, and use **`<AsyncLogger>`** for namespaces that need async logging or **`<AsyncRoot>`** for the root. At the same time, you can keep `<Logger>`/`<Root>` synchronous for actions that need a separate logging path.

Example:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration>
  <Appenders>
    <Console name="Console" target="SYSTEM_OUT">
      <PatternLayout pattern="%level|%msg%n"/>
    </Console>
  </Appenders>

  <Loggers>
    <AsyncLogger name="com.example.orders"
                 level="INFO" additivity="false">
      <AppenderRef ref="Console"/>
    </AsyncLogger>

    <Root level="ERROR">
      <AppenderRef ref="Console"/>
    </Root>
  </Loggers>
</Configuration>
```

In this example, loggers under the `com.example.orders` namespace can be configured on the async branch, while root remains synchronous. `additivity="false"` prevents events from the async branch from propagating up to root, avoiding duplicate output or unintended extra routing.

**`<AsyncRoot>`** is the option when you want an asynchronous root in **mixed mode** without enabling the full-async ContextSelector. Only one root configuration can exist at a time: either `<Root>` or `<AsyncRoot>`. `AsyncLogger`/`AsyncRoot` in mixed mode use the async configuration's ring buffer mechanism, which differs from swapping the ContextSelector for the entire application.

**Common pitfall:** Do not put `<AsyncLogger>` in XML while also enabling `AsyncLoggerContextSelector` thinking you will get "double-fast async." This configuration typically adds an extra barrier and degrades efficiency.

## 5. Required Dependencies and Java Compatibility

Using Async Logger requires **Log4j 2 API, Log4j Core**, and a compatible **LMAX Disruptor** library. Application classes usually only import `org.apache.logging.log4j.Logger` and `LogManager` from `log4j-api`, but the backend and Disruptor must still be present on the **runtime classpath**.

Example of a specific, released version set for reproducibility on **Java 17**:

| Artifact | Role | Version used in example |
| --- | --- | --- |
| `org.apache.logging.log4j:log4j-api` | Logging API | `2.26.1` |
| `org.apache.logging.log4j:log4j-core` | Backend, AsyncLogger configuration, and appenders | `2.26.1` |
| `com.lmax:disruptor` | Ring buffer for async logging | `4.0.0` |

These versions are **pinned for example reproducibility**, not claimed to always be the latest releases. For real projects, use the Log4j BOM/dependency management or your framework's BOM to keep Log4j modules aligned, verify JDK requirements, and apply security patches according to policy.

In particular, **Disruptor 4.x requires JDK 11 or later**; that is why the example uses Java 17. Projects still on Java 8 must check compatible Disruptor versions and the support matrix of that Log4j release rather than copying this dependency set blindly.

**If Disruptor is missing** while Async Logger is configured, the application may fail to create the async components or report initialization errors. Do not assume that "adding only `log4j-api`" is enough to use Async Logger.

## 6. Runnable Java 17 Example: Mixed Mode with AsyncLogger

This example creates a small Maven project with a **real AsyncLogger** configured via `<AsyncLogger>`, writing business logs through a Console appender. It does not set the full-async ContextSelector property, avoiding overlapping async boundaries.

### 6.1. Structure

```text
log4j2-async-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── demo/
        │       └── AsyncLog4jDemo.java
        └── resources/
            └── log4j2.xml
```

### 6.2. File pom.xml

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>demo</groupId>
    <artifactId>log4j2-async-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <maven.compiler.release>17</maven.compiler.release>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-api</artifactId>
            <version>2.26.1</version>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-core</artifactId>
            <version>2.26.1</version>
            <scope>runtime</scope>
        </dependency>
        <dependency>
            <groupId>com.lmax</groupId>
            <artifactId>disruptor</artifactId>
            <version>4.0.0</version>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.3.0</version>
                <configuration>
                    <mainClass>demo.AsyncLog4jDemo</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

### 6.3. File src/main/resources/log4j2.xml

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration>
    <Appenders>
        <Console name="Console" target="SYSTEM_OUT">
            <PatternLayout pattern="%level|%msg%n"/>
        </Console>
    </Appenders>
    <Loggers>
        <AsyncLogger name="demo.AsyncLog4jDemo"
                     level="INFO"
                     additivity="false">
            <AppenderRef ref="Console"/>
        </AsyncLogger>
        <Root level="ERROR">
            <AppenderRef ref="Console"/>
        </Root>
    </Loggers>
</Configuration>
```

- `AsyncLogger` is bound to logger name `demo.AsyncLog4jDemo`, matching the program's class.
- `level="INFO"` allows INFO, WARN, and ERROR events through to the appender; lower DEBUG events are filtered out.
- `additivity="false"` prevents events from propagating to root, avoiding duplicate logs on the Console.
- `Root` exists for general logging configuration; other classes can fall back to the root policy.
- `PatternLayout` prints only the level and message, omitting timestamp/thread so the lesson's output can be verified deterministically.
- `log4j2.contextSelector` is not set: this is a **mixed async logger configuration**.

### 6.4. File src/main/java/demo/AsyncLog4jDemo.java

```java
package demo;

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class AsyncLog4jDemo {

    private static final Logger LOG =
            LogManager.getLogger(AsyncLog4jDemo.class);

    private AsyncLog4jDemo() {
    }

    public static void main(String[] args) {
        LOG.debug("This message is filtered");
        LOG.info("orderId={} accepted", "O-17");
        LOG.warn("primary gateway unavailable; fallback selected");
        LOG.error("payment failed for orderId={}", "O-18");

        // In a standalone demo program, wait for the logger context
        // to complete its lifecycle, preventing the JVM from exiting while events remain buffered.
        LogManager.shutdown();
    }
}
```

**Build and run** from the directory containing `pom.xml`, with Maven and JDK 17 or later installed:

```bash
mvn -q compile exec:java
```

**Expected application stdout, exact for the configuration above** (excluding warnings/tool output if the Maven or Log4j environment is configured differently):

```text
INFO|orderId=O-17 accepted
WARN|primary gateway unavailable; fallback selected
ERROR|payment failed for orderId=O-18
```

Explanation:

1. `LOG.debug(...)` does not appear because the INFO level filters out DEBUG before writing.
2. `LOG.info(...)` is turned into an INFO event and sent to `AsyncLogger`.
3. `LOG.warn(...)` and `LOG.error(...)` are accepted under the same policy.
4. The ring buffer delivers the events to the consumer; the Console appender outputs each event as one line formatted with `%level|%msg%n`.
5. `LogManager.shutdown()` shuts down the `LoggerContext` and waits for pending logging work to drain according to Log4j's shutdown mechanism. For logs not yet acknowledged by an external sink, this operation **does not guarantee physical durability or collector delivery**.
6. Because the calls in this example come from a single thread with no other writers to that logger, the illustrated order is INFO, WARN, then ERROR. In a real multi-threaded environment, do not treat this pattern as a system-wide ordering guarantee.

**Explicit limitations:** This is a Maven project depending on Log4j 2 and Disruptor; it **cannot be compiled with JDK `javac` alone without the dependencies on the classpath**. The example does not execute real payments, has no business retries, writes no files, and uses no collector. The code only demonstrates routing and an async sink.

If your project uses Spring Boot or another logging backend, do not randomly add Log4j Core and a second provider; configure the framework's proper starter and dependencies, and inspect the classpath to avoid conflicts.

## 7. Differences When Using Full Async in the Same Program

If you want all loggers in full async mode, do the following:

1. Keep compatible Log4j 2 + Disruptor dependencies.
2. Replace `<AsyncLogger>` in XML with `<Logger>`, or use `<Root>` for everything.
3. Set the system property `log4j2.contextSelector` to `AsyncLoggerContextSelector` **before the context initializes**.
4. Review namespaces that require synchronous behavior, such as audit or security policies, before deciding on "all async."

Example of a standard logger configuration for full async:

```xml
<Loggers>
    <Logger name="demo.AsyncLog4jDemo" level="INFO"
            additivity="false">
        <AppenderRef ref="Console"/>
    </Logger>
    <Root level="ERROR">
        <AppenderRef ref="Console"/>
    </Root>
</Loggers>
```

This is only a **configuration snippet**, not a complete XML file. When paired with the full-async ContextSelector, loggers will use the async pipeline; **do not combine this ContextSelector with `<AsyncLogger>` from Section 6**.

Some older configurations use the system property name `Log4jContextSelector`; with current Log4j 2 documentation, prefer the standard name `log4j2.contextSelector` and verify your runtime version. Choose only one mechanism matching your intended architecture.

## 8. Queue Full and Backpressure Policies

Async Logger cannot bypass load laws: if the application produces 100,000 events/s while the sink can only sustain 20,000 events/s, backlog grows until the ring buffer is full, even though Disruptor is very fast at thread handoff.

```text
    Producer rate > Consumer rate
                 |
            Buffer grows
                 |
             Buffer full
                 |
        +--------+------------+
        |        |            |
   Wait to    Caller writes  Drop some events
   enqueue    synchronously  (if discard configured)
        |        |            |
   Higher     Higher         Loss of
   latency    latency        observability data
```

Depending on **`AsyncQueueFullPolicy`**, when the buffer is full, the system can block to enqueue, route some events synchronously on the caller thread, or discard events matching the policy. Log4j 2 provides `Default` and `Discard` policies; **never assume the default always drops** or that async is always non-blocking. In some cases, the default policy may log on the caller thread to reduce deadlock risk, causing unexpected latency spikes.

Deployment requirements:

- Size the **ring buffer capacity** based on peak bursts, RAM, event size, and appender processing time. Do not tune sizes by guesswork.
- **Measure discarded event counts** if discarding is allowed. Never treat "fewer logs" as proof of a healthy system.
- **Alert when sinks slow down, buffers near capacity, synchronous fallbacks increase, or ingestion lag exceeds thresholds**.
- Do not use discard policies for mandatory audit/security events that must be recorded and traced.
- For extreme log volumes, consider reducing log noise, applying controlled sampling at the appropriate layer, scaling sink capacity, and verifying network/transport throughput.
- Choose a strategy that avoids deadlocks when logging occurs inside custom formatters, appenders, or logging error handlers.

### Ring Buffer Size

For **full async**, the typical tuning property is:

```properties
log4j2.asyncLoggerRingBufferSize=8192
```

For **mixed async** using `<AsyncLogger>`/`<AsyncRoot>`:

```properties
log4j2.asyncLoggerConfigRingBufferSize=8192
```

In this example, `8192` is only an **illustrative slot count**, not a universal recommendation for every system. The ring buffer is pre-allocated and does not grow unboundedly; choose a slot count that fits Disruptor constraints and your sizing criteria. Set the property via system properties, environment variables, or `log4j2.component.properties` before async components initialize. The two property names **differ by mode** and must not be mixed up.

### Queue-Full Policy

```properties
# Example only, for environments where dropping low-priority logs is acceptable:
log4j2.asyncQueueFullPolicy=Discard
log4j2.discardThreshold=INFO
```

The `Discard` policy can drop events at or below the threshold level when the ring buffer is full, depending on the implementation/version. **Do not copy this configuration into production systems with mandatory audit logs**. Unless explicitly required, avoid enabling discard by default, and test under load and sink-failure scenarios first.

## 9. Wait Strategy and CPU/Latency Trade-offs

The background thread needs a way to wait for new events. Disruptor supports different strategies that trade off CPU usage against response time:

| Strategy | Overview | When to consider |
| --- | --- | --- |
| `Block` | Thread waits using synchronization/condition signaling. | CPU-constrained environments where wakeup overhead is acceptable. |
| `Timeout` | Uses a timed wait and rechecks. | General balanced choice across many configurations. |
| `Sleep` | Combines spin/yield/sleep/park depending on implementation. | When you want lower CPU than busy spinning while still tuning latency. |
| `Yield` | May consume high CPU to react quickly, yielding when other threads need CPU. | Consider only after thorough measurement on hardware with sufficient CPU. |

Properties:

```properties
# Full async:
log4j2.asyncLoggerWaitStrategy=Timeout

# Mixed async:
log4j2.asyncLoggerConfigWaitStrategy=Timeout
```

Do not arbitrarily switch to a busy-waiting strategy on VMs/containers with few vCPUs, as it can contend for CPU with business threads. **Benchmarks must measure CPU, p99 latency, throughput, GC, and actual logs delivered to the sink**, not just a peak number on an idle machine.

## 10. Message Formatting Timing and Mutable Objects

A common misconception is: "Async Logger moves all message computation to the background thread." In reality, part of message construction still happens on the caller:

```java
// expensive() runs immediately when Java evaluates the arguments.
LOG.debug("debug value=" + expensive());

// Parameterized logging can avoid string concatenation when the level is disabled,
// but expensive() still runs before the call.
LOG.debug("debug value={}", expensive());
```

These snippets illustrate code that has an `expensive()` function; they are not a standalone program. To defer computation, use lazy logging features supported by the API/backend or check the level before calling the function, provided that fits your business boundaries.

Log4j 2 provides the property:

```properties
log4j2.formatMsgAsync=false
```

In common configurations, `false` (the documented default) causes **message formatting to be prepared on the caller** so the content remains consistent with the call time. Setting `true` allows formatting on the background thread in supported cases, but can cause the rendered content to change if parameter objects are mutated before the formatter runs.

**Mutable messages:** Types such as `MapMessage`, `StructuredDataMessage`, and custom `Message` implementations may allow data updates after the event is created. Do not mutate them after calling the logger and still expect Async Logger to record the earlier snapshot. When correctness matters, capture **small, immutable, safe** attributes at event creation time.

### ThreadContext and Request Correlation

Log4j 2's `ThreadContext` is commonly used for contextual maps/stacks such as request IDs or correlation IDs:

```java
// Illustrative snippet in a request-handling block with Log4j 2 on the classpath.
try (org.apache.logging.log4j.CloseableThreadContext.Instance ignored =
        org.apache.logging.log4j.CloseableThreadContext
                .put("correlationId", "req-1001")) {
    LOG.info("Processing order {}", "O-17");
}
```

This snippet illustrates context scoping, not a standalone runnable program. Context data is typically captured when the event is created and used later, but **this does not mean context is automatically propagated across every executor, `CompletableFuture`, or reactive scheduler**. When switching business threads, use an appropriate propagation mechanism. With thread pools, always restore or clear context after a request so user IDs do not leak across executions.

**Never log** access tokens, session cookies, passwords, private keys, or full request bodies in `ThreadContext` or logs. Context data may be routed to multiple sinks and retained long-term.

## 11. IncludeLocation, Exceptions, and Caller Information

Layout patterns such as `%class`, `%line`, and `%location` require **call-site origin information**. With Async Logger, this information is typically **disabled by default** because capturing call-site location is expensive and cannot be inferred accurately from the background thread's stack trace.

When truly needed, consider:

```xml
<AsyncLogger name="com.example.orders"
             level="INFO"
             includeLocation="true"
             additivity="false">
    <AppenderRef ref="Console"/>
</AsyncLogger>
```

Enabling `includeLocation="true"` must be benchmarked because it can increase CPU usage and latency. When class/method/line locations are unnecessary, prefer logger names, event codes, and correlation IDs. If a layout uses caller location while configuration disables capture, the output may be missing or show placeholder values.

**Exceptions:** Use the `Throwable`-aware API to preserve stack traces properly:

```java
// Inside a catch block with exception variable ex.
LOG.error("Order {} failed", orderId, ex);
```

Do not just concatenate `"failed: " + ex` and lose the stack trace. With async logging, errors thrown by an **appender** on the background thread may not surface back to the caller as an exception from `LOG.error(...)`. Therefore, configure reporting via the status logger, appropriate exception handlers, and sink error monitoring instead of relying solely on `try/catch` at the log call site.

## 12. Flush, Shutdown, and Potential Log Loss

### Typical Lifecycle

```text
Startup: load config + init async infrastructure
    |
   LOG.info(...)
    |
 Async queue / ring buffer
    |
 Background thread -> appender -> sink
    |
Shutdown: stop accepting work, process remaining events per
          logger context mechanism and timeout
    |
      Close appenders/resources
```

In the Java 17 example, `LogManager.shutdown()` is called after the final events to demonstrate context closure. In real applications, the lifecycle is usually managed by the application server, framework, or container, and requires proper **shutdown hooks, draining, and timeouts**. Never close the `LoggerContext` on every request.

There are several distinct failure modes for data loss:

1. **Loss before enqueue:** Events are rejected due to level/filter/policy or message construction errors.
2. **Loss in the buffer:** The JVM is killed or crashes before the consumer drains it.
3. **Loss at the appender/network:** I/O failures, timeouts, or unacknowledged responses.
4. **Loss after export:** Collector fails to receive, parser errors, indexing lag, or retention deletion.
5. **Loss due to overload:** When a discard policy is configured or the system cannot keep up with backlog.

**Flush is not fsync, and fsync does not automatically mean a remote system received the data.** Async Logger serves throughput and caller-latency reduction, not transactional audit guarantees. For mandatory audit or security records, consider a **synchronous path with acknowledgments and durable storage**, or a transactional outbox / dedicated audit store aligned with business risk. Do not use a potentially discarding async pipeline as the sole source of evidence.

## 13. Performance: What to Measure Before Choosing Async Logger?

Do not conclude based solely on "higher logs/sec" in synthetic benchmarks. A meaningful evaluation should include:

| Metric | Why it matters |
| --- | --- |
| Request p50/p95/p99 latency | Shows whether offloading I/O to the background actually reduces caller wait time. |
| Business throughput | Faster logging does not guarantee higher request throughput if the bottleneck is DB or CPU elsewhere. |
| Actual throughput received at the sink | Only events persisted by the appender/collector matter operationally. |
| Buffer occupancy and queue-full events | Reveals backlog buildup and slow fallbacks during sustained bursts. |
| Producer/consumer CPU usage | Busy waiting or heavy formatters can compete with business logic for CPU. |
| Allocation/GC pauses | Messages, stack traces, `ThreadContext`, and layouts can increase memory pressure. |
| Discarded/errored/retried log counts | Data loss can create an illusion of "improved throughput." |
| End-to-end ingestion lag | How long until logs reach the search store; whether alerts are delayed. |

A sound comparison process:

1. Keep **identical log content, levels, layouts, and sinks**.
2. Measure the synchronous logger baseline after the system has warmed up and reached steady load.
3. Measure mixed/full Async Logger under the same load and resource constraints.
4. Generate bursts exceeding sink throughput to observe queue-full behavior, latency, and log-loss rate.
5. Test normal restarts, timed shutdowns, simulated crashes, and collector disconnects.
6. Select the configuration that meets latency/throughput goals **and** data-reliability requirements.

If the system has only one vCPU or very low log volume, a background thread and Disruptor may offer negligible benefit. Base decisions on your own application's benchmarks rather than treating numbers from another machine as a production guarantee.

## 14. Common Async Logger Configuration Errors

| Symptom | Possible Cause | How to Check |
| --- | --- | --- |
| AsyncLogger initialization fails | Missing or mismatched Disruptor or Log4j Core. | Runtime dependency tree, Java version, Status Logger messages. |
| No logs after running | Log4j did not load the XML file, level/filter dropped events, or wrong provider/backend. | Confirm `src/main/resources/log4j2.xml` location; check classpath and status output. |
| AsyncLogger enabled but no improvement | Appender is already fast, CPU is scarce, or message formatting still runs on caller. | Profiler, end-to-end pipeline benchmark, and ring buffer metrics. |
| Two async boundaries exist | `AsyncLoggerContextSelector` enabled **and** `<AsyncLogger>`/`<AsyncRoot>` used. | Choose either full async or mixed async only. |
| Events emitted twice | Logger additivity propagates to root/appender with the same target. | Logger hierarchy, `additivity`, and appender refs. |
| Logs arrive slowly | Slow consumer/appender, large backlog, collector lag. | Sink throughput, queue capacity, flush behavior, and collector health. |
| Request p99 spikes under high load | Queue full forces caller to wait or fall back to synchronous writes. | `AsyncQueueFullPolicy`, appender speed, burst testing. |
| Missing class/line names | Async Logger disables `includeLocation` by default. | Layout pattern and `includeLocation` on the relevant logger. |
| Message reflects newer object state | Mutable object modified before background formatting/encoding. | Safe snapshots, `formatMsgAsync`, and custom `Message` implementations. |
| Logs lost on service shutdown | JVM exited before draining or sink had not acknowledged. | Shutdown lifecycle, timeouts, crash tests, durable transport. |
| Logs exist but audit is unreliable | In-memory buffer only, drop policy enabled, lacks durable acknowledgment. | Separate audit path or acknowledgment/outbox design per requirements. |

**An especially dangerous mistake:** logging appender errors **using the same failing logger/appender** inside a custom handler or formatter. This can create a logging loop and deadlock when the queue is full. Use Log4j's status reporting mechanism and appropriate observability channels instead of recursion.

## 15. Layered Testing for Async Logger

Essential test cases:

1. **Configuration:** The project loads the exact intended configuration; `AsyncLogger` names match code loggers, and `Root` and `additivity` are correct.
2. **Levels:** INFO/WARN/ERROR are recorded; DEBUG is filtered out under an INFO configuration.
3. **Output:** Each message matches the template, with no duplicates and no missing lines under light load.
4. **Burst:** Drive producer rate above consumer rate; verify queue-full policy behavior and impact on enqueue time.
5. **Multi-threading:** Emit many events with IDs; verify all logical events arrive and do not infer wrong ordering from timestamps.
6. **Mutable messages:** Mutate an object after logging; verify snapshot integrity and no unintended data leakage.
7. **ThreadContext:** Correlation IDs remain accurate per request even across thread pools and async frameworks.
8. **Caller location:** When enabled, verify accurate locations; when disabled, ensure nothing depends on `%line`/`%class`.
9. **Shutdown:** Stop the service after a burst of events and check how many reach the sink; test both graceful and forced termination.
10. **Appender failures:** Simulate disk full, permission errors, or network disconnects; verify error signals and impact on business threads.
11. **Sensitive data:** Payloads with newlines, tokens, and exception details; encoders/allowlists must prevent injection and secret exposure.
12. **End-to-end:** Starting from a known correlation ID, confirm logs flow through the appender, collector, and storage to queryable results.

**When a log line disappears**, investigate in order: code branch → level/filter → whether async mode is actually enabled → whether Disruptor initialized → queue-full policy → appender → stdout/file/network → collector/index → query/retention. Never look only at the `logger.info(...)` call and assume the system persisted the event.

## 16. Async Logger Design Checklist for Java Services

- [ ] Verified a genuine throughput/latency need and measured a synchronous logging baseline.
- [ ] Selected **full async** *or* **mixed async** by policy; never stacked ContextSelector on top of `AsyncLogger`.
- [ ] Confirmed `log4j-api`, `log4j-core`, and `com.lmax:disruptor` are mutually compatible and match the JDK.
- [ ] Configured logger names, levels, `additivity`, and appender refs accurately.
- [ ] Sized ring buffer capacity, queue-full policy, wait strategy, and CPU/RAM resources.
- [ ] Controlled message formatting, mutable data, `ThreadContext`, and call-site location.
- [ ] Implemented shutdown/drain handling and procedures for crashes, network loss, and sink failures.
- [ ] Added metrics/alerts for dropped logs, backlog, ingestion lag, and appender errors.
- [ ] For mandatory audit/security logs, used a separate durable and acknowledged mechanism rather than relying on an in-memory queue.
- [ ] Verified from the **final artifact** (JAR/container) through to the sink and query store, not only inside an IDE.
- [ ] Excluded passwords, tokens, and unnecessary PII from logs; applied proper schema/encoding/escaping.
- [ ] Configured framework dependencies (Spring Boot, server, SLF4J bridge) without unintended providers or conflicts.

**Key takeaway:** Async Logger is a technique for **decoupling logging work from business threads using Disruptor**. It can improve throughput and latency, but it introduces **a bounded buffer, consumption lag, potential event loss, and shutdown/backpressure management requirements**. Choose the right full or mixed async mode, measure the quality of data reaching the sink, and never equate "enqueued" with "durably stored."
