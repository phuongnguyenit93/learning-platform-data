# Setting MDC Values in Java: From a Single Request to Multithreaded Logging

## 1. What Is MDC and Why Set Values?

**MDC (Mapped Diagnostic Context)** is a **key–value map for diagnostic context**, typically bound to the currently executing thread, so that log calls within the same processing flow can include metadata without repeatedly passing those values into every `LOG.info` statement. In Java applications, MDC is especially useful for attaching **requestId**, **traceId**, an **allowed tenantId**, **operation**, **jobId**, or a safe correlation ID to logs.

For example, a request that executes multiple steps:

~~~text
INFO req=req-42 event=order.received
INFO req=req-42 event=inventory.checked
INFO req=req-42 event=payment.authorized
INFO req=req-42 event=order.completed
~~~

You do not need to write **req=req-42** manually in every message. At the entry point of the request, you can **set the MDC value**:

~~~java
MDC.put("requestId", "req-42");
~~~

The logging backend can then use the **requestId** field in a PatternLayout or JSON encoder for records emitted in that context. **MDC.put only stores the data; it does not automatically print the field to the console.** To see the value, you must configure the backend's layout or encoder.

This lesson focuses on **setting MDC values** in the **MDC** group of **Java Core Logging**, covering API usage, lifecycle, asynchronous contexts, handling previous values, differences across backends, and verification with Java 17. This is foundational knowledge for tracing a request across multiple layers without mixing logs from different requests.

After this lesson, you will be able to:

- Understand how MDC differs from Logger name, message, and business data.
- Use **org.slf4j.MDC.put**, **get**, **remove**, **clear**, and **putCloseable** appropriately.
- Validate keys/values, understand overwrite behavior, and know the limitations with null values.
- Manage scope with **try/finally** or **try-with-resources**.
- Recognize why thread pools do not automatically inherit MDC and use **snapshot + restore** for controlled propagation.
- Configure Logback PatternLayout to read **%X{requestId}** and verify stdout.
- Distinguish SLF4J MDC from **Log4j2 ThreadContext** and JUL.
- Avoid cross-request data leaks, duplicate logs, stale context values, and sensitive data exposure.
- Test MDC in unit tests, integration tests, and multithreaded applications.

## 2. Where Does MDC Fit in the Logging Architecture?

Conceptual model:

~~~text
Request / Job / Operation
   |
   | MDC.put("requestId", "req-42")
   v
Current thread's MDC map
   |
   +-- business service -> LOG.info("event=order.received")
   +-- repository       -> LOG.info("event=inventory.checked")
   +-- payment client   -> LOG.warn("event=payment.retry")
   |
   v
Logging API / backend
   |
   | captures message + level + logger name + MDC snapshot
   v
Layout / Encoder
   |
   v
stdout / file / collector
~~~

MDC helps **carry the same context** across multiple log events. It does not replace Logger, LogRecord, or Appender. Role of each component:

| Component | Answers the Question | Example |
| --- | --- | --- |
| **Logger name** | Which component emitted the log? | demo.checkout.OrderService |
| **Level** | How important is it? | INFO, WARN, ERROR |
| **Message/event** | What happened? | event=order.created |
| **MDC fields** | Which request/operation does the event belong to? | requestId=req-42 |
| **Exception** | What is the cause and stack trace? | GatewayTimeout |
| **Layout/encoder** | How is the event formatted as text/JSON? | %X{requestId} or JSON field |
| **Appender/Handler** | Where is the event sent? | console, file, collector |

**Do not use Logger names to hold requestId.** Creating a Logger named **request-req-42** for every request makes the namespace hard to manage and configure. Keep Logger names stable by class/package; requestId belongs in MDC.

### 2.1. MDC Is Not Business State Storage

MDC should only hold metadata sufficient for diagnostics. **Do not use MDC as a source of truth** for authorization decisions, pricing, transactions, data partitioning, or business checks. Even if requestId is missing, the application must still execute business logic accurately using explicit parameters and the canonical security context.

### 2.2. MDC Is Typically Thread-Bound

In common backends, the MDC map is maintained via a **thread-local context** or an equivalent mechanism. Therefore, multiple `LOG.info` calls on the same thread can usually read the value that was set; however, a task running on another thread **does not automatically receive** the map from the calling thread.

This is the most important characteristic when moving from a simple console example to a server with thread pools or `CompletableFuture`. The exact mechanism can vary by logging provider and execution model, because SLF4J only defines the facade API while the implementation handles how MDC is stored and routed.

## 3. Core SLF4J MDC API

SLF4J provides the **org.slf4j.MDC** class with static methods. When the backend/provider supports MDC, the API delegates operations to the implementation's MDC adapter.

| Method | Meaning | When to Use |
| --- | --- | --- |
| **MDC.put(key, value)** | Sets or overwrites a value by key on the current thread | Starting a request, attaching jobId, operation |
| **MDC.get(key)** | Reads the value set for a key | Inspecting context in tests or debugging |
| **MDC.remove(key)** | Removes a single key | Ending the scope of a specific field |
| **MDC.clear()** | Clears the entire current MDC map | Cleaning up context at a request boundary that owns the whole map |
| **MDC.putCloseable(key, value)** | Sets a key and returns a Closeable that removes it on close | Scoping a single key in try-with-resources |
| **MDC.getCopyOfContextMap()** | Returns a copy of the current thread's map, possibly null | Snapshotting to pass across an executor |
| **MDC.setContextMap(map)** | Replaces the current map with a copy of the provided map | Setting context on another thread, then restoring |

This is the **SLF4J** API: import **org.slf4j.MDC**. **Do not confuse it with** **java.util.logging.Logger** or Log4j2's **org.apache.logging.log4j.ThreadContext**, even though they serve similar purposes.

### 3.1. Setting a Single Key/Value

~~~java
import org.slf4j.MDC;

// Inside a method:
MDC.put("requestId", "req-42");
~~~

This snippet is **integration code**, without a `main()` method or backend setup. It stores a **String** value under the key **requestId** in the current thread's diagnostic context.

**The value is attached to subsequent logging events** if the backend records MDC and the Layout/Encoder is configured to extract the field. Calling `MDC.put` is not a logging call, so by itself it produces no output line.

### 3.2. Setting Multiple Keys

~~~java
MDC.put("requestId", "req-42");
MDC.put("operation", "checkout");
MDC.put("component", "payment");
~~~

Keys should follow a **consistent convention** across services. If one service uses `requestId` and another uses `req_id` for the same meaning, cross-service log queries will require special mapping. Choose one naming contract and verify it against the final output.

**Do not put every property of a domain object into MDC.** Some fields, such as item count or payment amount, may only be relevant to a specific event and should be logged as structured event attributes at the point of emission rather than kept long-term in the thread context.

### 3.3. Reading a Value

~~~java
String currentRequestId = MDC.get("requestId");
~~~

**MDC.get** can return **null** if the key does not exist. It is suitable for verifying that context is attached properly in tests or in context-management code, but should not be used as the sole input for critical business logic.

### 3.4. Setting the Same Key Again Overwrites It

~~~java
MDC.put("requestId", "req-42");
MDC.put("requestId", "req-43");
String current = MDC.get("requestId"); // "req-43"
~~~

MDC is a **map**; writing to the same key replaces the previous value. That is why you need to understand the lifecycle of each key. If a nested method changes `requestId` on the same thread, the outer method can lose its original value unless restore logic is in place.

### 3.5. Removing One Key vs. Clearing All

~~~java
MDC.remove("operation"); // Remove a single field
MDC.clear();             // Clear all fields in the current MDC
~~~

**MDC.remove** is appropriate when you only own a single key. **MDC.clear** is appropriate at a request boundary where you intentionally end the entire diagnostic context. Calling `clear` inside a nested helper, however, can wipe out `traceId`, `requestId`, or fields managed by another layer.

### 3.6. Null Values and Invalid Keys

According to the SLF4J API:
- **key must not be null**; `put(null, ...)` is invalid.
- **a null value is only accepted if the underlying implementation supports it**. Do not treat **MDC.put(key, null)** as a portable way to remove a field.
- To remove a key, call **MDC.remove(key)**.
- Values in the MDC map are fundamentally **Strings**, not a place to store mutable objects or business entities.

For integers or UUIDs, convert them to String in a stable format after the data has been validated:

~~~java
MDC.put("attempt", Integer.toString(attempt)); // attempt is an int in the method
MDC.put("requestId", requestId.toString());     // requestId is already non-null
~~~

This is an illustrative snippet using existing variables, not a standalone runnable program. In systems with a structured encoder, **MDC data types are typically strings**; if you need numbers for aggregation, use typed event attributes or explicit pipeline normalization.

## 4. Lifecycle of an MDC Value

A typical flow:

~~~text
Thread receives request req-42
  |
  +--> MDC.put("requestId","req-42")
  |
  +--> logger.info(...) -> record includes req-42
  +--> service.run(...) -> logger.warn(...) includes req-42
  |
  +--> finally: MDC.remove("requestId")
  |
Thread is reused for request req-43
  |
  +--> MDC.put("requestId","req-43")
  +--> logger.info(...) -> record includes req-43
  +--> finally: MDC.remove("requestId")
~~~

Without cleanup, request `req-43` could inherit log metadata from `req-42` on a reused thread pool thread, causing **incorrect correlation** and potential cross-tenant data leaks.

### 4.1. The try/finally Pattern for a Single Key

~~~java
MDC.put("requestId", requestId);
try {
    processRequest();
} finally {
    MDC.remove("requestId");
}
~~~

This is **integration code**, requiring `requestId` and `processRequest()` in the method scope. The `finally` block runs even if `processRequest` throws an exception. If you **exclusively** own the `requestId` key, removing that specific key is less disruptive than clearing the entire map.

However, this pattern **does not restore a previous requestId value** if the method is called nested inside a scope that already has `requestId`. For nested scopes, see Section 4.3.

### 4.2. The try-with-resources Pattern with putCloseable

~~~java
try (MDC.MDCCloseable ignored =
             MDC.putCloseable("operation", "reserve")) {
    LOG.info("event=inventory.check");
}
~~~

When the block exits, **close() removes the operation key**. This practice helps prevent forgetting cleanup and is suitable when the `operation` key **did not exist** before entering the scope.

**Common pitfall:** SLF4J **MDC.putCloseable** is documented to **remove the key on close**; it **does not promise to restore a previous value** if the same key already existed. Therefore, do not assume it always behaves like a context stack supporting exact push/pop of old values.

### 4.3. Nested Scopes and Restoring Previous Values

Suppose the outer scope has `operation=checkout`, and an inner scope temporarily uses `operation=payment`. Upon exiting the inner scope, the outer scope still expects `operation=checkout`.

~~~java
String previous = MDC.get("operation");
MDC.put("operation", "payment");
try {
    LOG.info("event=payment.started");
} finally {
    if (previous == null) {
        MDC.remove("operation");
    } else {
        MDC.put("operation", previous);
    }
}
~~~

This snippet illustrates usage inside a class that has `LOG` and is not standalone. It **restores the previous value** after overriding, unlike **putCloseable** which removes the key on close.

Another approach is to snapshot the entire map and restore it after the block, which fits scopes with many fields to preserve; however, copying the map has overhead and must be scoped carefully.

### 4.4. When to Use MDC.clear?

**MDC.clear()** removes all keys on the current thread. Use it when you are certain you own the entire context—for example, at the end of a request boundary designed to wipe any leftover diagnostic data. Never call `clear` inside a DAO or helper, as it will destroy the caller's context.

In middleware or web filters, `clear` can be used at the boundary when the architecture dictates that **every request starts with an empty MDC and ends with an empty MDC**. If a framework-managed MDC scope already exists and must be preserved, use snapshot/restore instead of blindly calling `clear`.

## 5. MDC from Java Code to Actual Logs

**MDC.put does not write to a file or console by itself.** Think of it as two separate parts:

1. **Producer:** code that attaches `requestId` and emits logs.
2. **Presentation:** backend/encoder that includes `requestId` in the output format.

Example Logback PatternLayout:

~~~text
%level|%thread|req=%X{requestId:-none}|%msg%n
~~~

In Logback:
- **%level**: severity.
- **%thread**: thread name.
- **%X{requestId}**: reads the MDC value for the `requestId` key.
- **%X{requestId:-none}**: uses **none** when no matching value is present.
- **%msg**: rendered message.
- **%n**: newline.

With the exact same MDC code, if the Layout only has **%msg%n**, the output will not contain `requestId`. **Do not conclude that MDC.put is broken just because the key does not appear on the console**; check the backend/provider and layout first.

### 5.1. MDC and Structured Logging

In JSON logging, an event might be emitted as:

~~~json
{
  "level": "INFO",
  "logger": "demo.mdc.MdcDemo",
  "message": "event=request.started",
  "requestId": "req-42",
  "tenant": "demo"
}
~~~

This is an **illustrative JSON example**, not the stdout of the program below. To produce real JSON output, use an encoder/JSON layout configured to map MDC entries into corresponding fields. Do not manually concatenate strings to build JSON, because `requestId` could contain quotes or control characters.

**MDC's underlying type is String.** A JSON field such as `attemptCount` must be designed carefully if downstream consumers expect a JSON number rather than a string; use typed structured attributes or an explicit normalization step.

### 6.4. src/main/java/demo/mdc/MdcDemo.java

~~~java
package demo.mdc;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public final class MdcDemo {
    private static final Logger LOG = LoggerFactory.getLogger(MdcDemo.class);

    public static void main(String[] args) throws Exception {
        MDC.clear();
        LOG.info("event=boot");

        MDC.put("requestId", "req-42");
        MDC.put("tenant", "demo");
        LOG.info("event=request.started");
        System.out.println("get-requestId=" + MDC.get("requestId"));

        try (MDC.MDCCloseable ignored = MDC.putCloseable("operation", "reserve")) {
            LOG.info("event=inventory.check");
        }
        LOG.info("event=request.finished");

        MDC.remove("tenant");
        LOG.info("event=after.tenant.remove");
        MDC.clear();
        LOG.info("event=after.cleanup");

        ExecutorService pool = Executors.newSingleThreadExecutor(r ->
                new Thread(r, "worker-mdc"));
        try {
            MDC.put("requestId", "req-99");
            pool.submit(() -> LOG.info("event=async.without.context")).get();

            Map<String, String> snapshot = MDC.getCopyOfContextMap();
            pool.submit(() -> {
                Map<String, String> previous = MDC.getCopyOfContextMap();
                try {
                    if (snapshot == null) MDC.clear();
                    else MDC.setContextMap(snapshot);
                    LOG.info("event=async.with.context");
                } finally {
                    if (previous == null) MDC.clear();
                    else MDC.setContextMap(previous);
                }
            }).get();

            pool.submit(() -> LOG.info("event=async.after.cleanup")).get();
        } finally {
            MDC.clear();
            pool.shutdown();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) pool.shutdownNow();
        }
    }
}
~~~

**This is a complete Java 17 program with no undefined helper methods.** It uses **java.util.concurrent** to actually execute tasks on a worker thread. The thread name is explicitly set to **worker-mdc**, making output comparison independent of default thread pool naming.

## 7. Propagating MDC Across ExecutorService Properly

This is the most common place where setting MDC values goes wrong.

### 7.1. Why Calling put on the Submitting Thread Is Not Enough

Example:

~~~java
MDC.put("requestId", "req-42");
executor.submit(() -> LOG.info("event=async.started"));
~~~

This is integration code, assuming `executor` and `LOG` already exist. **The ThreadLocal context of the submitting thread is not automatically transferred to the executor thread running the task**. Some runtimes or instrumentation agents provide their own propagation mechanisms, but you should not assume this happens just from calling `submit`.

Even worse, if a worker thread still holds MDC from an older task that was not cleaned up, the new log can carry the **wrong requestId**, which is more dangerous than showing `none`.

### 7.2. Capture Before Submit, Set and Restore in Worker

Safe pattern:

~~~java
Map<String, String> captured = MDC.getCopyOfContextMap();

executor.submit(() -> {
    Map<String, String> previous = MDC.getCopyOfContextMap();
    try {
        if (captured == null) MDC.clear();
        else MDC.setContextMap(captured);

        LOG.info("event=async.started");
        doWork();
    } finally {
        if (previous == null) MDC.clear();
        else MDC.setContextMap(previous);
    }
});
~~~

This is an illustrative snippet inside a method where `executor`, `LOG`, and `doWork` are defined. **Capture on the submitting thread**, not inside the worker after the task has started. **Restore in finally** so the worker is not polluted for the next task.

**Why not just call MDC.clear in the worker?** If the worker is running inside a nested context managed by a framework, `clear` could destroy existing context. Saving **previous** and restoring it preserves whatever state the worker had before the task. If your architecture guarantees workers always start empty, `previous` will be null and `finally` will clear it.

### 7.3. A Snapshot Is a Copy, Not a Shared Map

**MDC.getCopyOfContextMap()** returns a **copy** of the entries at the time of the call, or null. Do not share a single mutable `HashMap` across multiple threads without a clear contract. If the context is updated after submission, a task that already captured a snapshot will keep its version; that matches the intended design of capturing at submit time.

### 7.4. CompletableFuture, Scheduled Tasks, and Virtual Threads

APIs such as **CompletableFuture.supplyAsync**, **ExecutorService**, scheduled pools, and virtual threads have different execution models, yet none should be assumed to automatically carry the caller's MDC:
- **CompletableFuture:** tasks may run on `ForkJoinPool` or a custom executor; use a context-aware executor or wrapper.
- **ScheduledExecutorService:** decide whether capturing at schedule time or execution time fits the request/job semantics; avoid retaining request data too long.
- **Virtual threads:** context bound to one virtual thread does not mean it automatically propagates across other virtual threads; manage scope and propagation explicitly.
- **Reactive pipelines:** a logical request may hop threads multiple times; ThreadLocal MDC usually needs integration with the corresponding reactor/coroutine context.

**Do not copy entire request payloads or security objects into MDC to pass business data.** Context propagation for trace/log fields is distinct from propagating security contexts and transaction state.

## 8. Where to Set MDC in a Web Application

In HTTP applications, the usual place is a **middleware/filter/interceptor at the request boundary**, so `requestId` is set before services/repositories log anything and cleaned up when the request finishes.

Model:

~~~text
Incoming HTTP request
  |
  v
Request filter / interceptor
  |
  +--> Validate or generate requestId
  +--> MDC.put("requestId", requestId)
  |
  v
Controller -> Service -> Repository -> remote client
  |
  +--> all sync logs on the matching thread include requestId
  |
  v
finally -> MDC.remove("requestId") / restore previous
  |
  v
HTTP response
~~~

### 8.1. Pseudocode of a Request Boundary

~~~java
String previous = MDC.get("requestId");
String requestId = validateOrGenerateRequestId(incomingRequest);
MDC.put("requestId", requestId);
try {
    invokeNextHandler();
} finally {
    if (previous == null) MDC.remove("requestId");
    else MDC.put("requestId", previous);
}
~~~

This is **conceptual code**, not a standalone Java class: `incomingRequest`, `validateOrGenerateRequestId`, and `invokeNextHandler` must be defined according to your framework. The key is to set the context **before** business code logs and restore it properly **after** the request completes on that thread.

### 8.2. Do Not Trust Arbitrary Client Request IDs

Clients may send unusually long request IDs or strings containing newlines/control characters. Before putting a value into MDC:
- Validate format, length, and allowed character set.
- Prefer correlation IDs generated or validated by a trusted gateway or service.
- Never use an arbitrary header as proof of identity/authentication.
- Never accept raw credentials or secrets as context keys/values.

For example, you can enforce a UUID format or a short string of allowed characters, depending on your architecture. If a client sends an invalid ID, generate a safe new ID or handle it per your API contract.

### 8.3. Thread Pools and Servlet Async

A servlet or request may switch to async processing, callbacks, or executors. **MDC set in a synchronous filter is not guaranteed to exist in tasks on other threads**. Your framework may provide built-in context propagation; if so, use the official framework mechanism rather than writing overlapping custom adapters.

If the filter cleans up before an async callback finishes, the callback needs its own captured/restored context; do not leave a request's ThreadLocal MDC on a container thread indefinitely.

## 9. SLF4J MDC, Log4j2 ThreadContext, and JUL

Different logging frameworks manage diagnostic context in different ways.

### 9.1. SLF4J MDC

~~~java
import org.slf4j.MDC;

MDC.put("requestId", "req-42");
String id = MDC.get("requestId");
MDC.remove("requestId");
~~~

This is the SLF4J facade API. Actual behavior depends on the **MDCAdapter** supplied by the runtime provider. With Logback Classic in our example, data is passed into Logback's PatternLayout.

### 9.2. Log4j2 ThreadContext

When using the Log4j2 API directly:

~~~java
import org.apache.logging.log4j.ThreadContext;

ThreadContext.put("requestId", "req-42");
try {
    // Logging calls for the current context.
} finally {
    ThreadContext.remove("requestId");
}
~~~

Log4j2 calls the diagnostic context map the **Thread Context Map**, and also supports a **Thread Context Stack** for NDC-style nested contexts. In Log4j2's PatternLayout, **%X{requestId}** reads the matching key when supported by the encoder/layout.

Log4j2 provides **CloseableThreadContext.put** to create an auto-closing scope. **A notable difference:** Log4j2 documentation states that **CloseableThreadContext.put** **restores the previous value** of the key when the scope closes, whereas **SLF4J MDC.putCloseable** only guarantees **removing the key**. Do not assume the two APIs have identical nested-scope semantics just because their method names are similar.

Log4j2 example:

~~~java
try (org.apache.logging.log4j.CloseableThreadContext.Instance ignored =
             org.apache.logging.log4j.CloseableThreadContext.put(
                     "requestId", "req-42")) {
    // Logging in this scope includes requestId when the Layout reads ThreadContext.
}
~~~

This is an illustrative snippet and requires Log4j2 dependencies to compile; the complete runnable program in Section 6 uses only SLF4J and Logback.

### 9.3. JUL

The JDK's **java.util.logging (JUL)** has `Logger` and `LogRecord`, but **there is no org.slf4j.MDC.put method on JUL Logger**. When using SLF4J with a provider/bridge targeting JUL, MDC behavior and field rendering depend on the actual adapter/formatter; do not assume JUL's `ConsoleHandler` will automatically include `requestId`.

### 9.4. Bridges and Multiple Backends

If an application uses the SLF4J facade with a Log4j2 backend, SLF4J's MDC can be bridged/synced with `ThreadContext` according to the implementation's contract. However, if multiple providers/bridges are installed or wired in the wrong direction, values may never reach the intended Appender.

**Do not install multiple backends/providers hoping MDC will somehow work.** Pick one logging backend that supports MDC, verify the dependency graph, configure the Layout/Encoder, and test the output.

## 10. MDC and Async Logging Are Not Context Propagation

These are two distinct concepts:

1. **Application async task:** business logic switches threads, such as an executor or `CompletableFuture`. You must propagate MDC to the thread running the task.
2. **Async logging backend:** the log event is emitted on the application thread, while an Appender/encoder processes it on a background thread. The backend is responsible for capturing the relevant context when creating/queuing the event according to its implementation contract.

**Setting MDC inside an AsyncAppender worker does not replace setting context on the application thread.** In common backends, MDC may be snapshotted into the event before queuing; still, test your exact version/encoder, especially when using custom `LogEvent`s, layouts, or adapters.

If a log event is emitted **after** the scope has been cleared, it will not magically inherit `requestId` just because a previous task had it. If an event is emitted **inside** the scope but the appender flushes later, the backend should use the event's context snapshot by design. Avoid assumptions based on line order when async queues and multiple threads run concurrently.

### 10.1. Async Error Handling and Data Loss

MDC only **attaches correlation context**. It does not guarantee that async log records are flushed, retried, persisted, or never dropped. If you need durable audit logs, you need separate policies for queues, sinks, backpressure, shutdown, and retention.

## 11. MDC in Structured Logging and Observability

When a system has **traceId/spanId**, MDC is often used to add those IDs to log events so messages do not have to repeat them:

~~~text
INFO trace=t-02 span=s-05 event=payment.authorized
~~~

If the backend outputs JSON, these values should be explicit fields consistent with your analytics schema. However:
- **Putting traceId in MDC does not create a span.**
- **MDC does not automatically propagate traceId over HTTP, message queues, or across processes.**
- **A requestId is not necessarily the same as a traceId.**
- Tracing frameworks may automatically inject trace/span IDs into the logging context; avoid overwriting them with other IDs.
- Do not use MDC to store an OpenTelemetry Context or a security principal.

MDC assists with **log correlation**, whereas distributed tracing requires proper instrumentation, context propagation, and span lifecycle management.

### 11.1. Choosing Production Keys/Values

Useful keys, if permitted by policy:

| Key | Example | Notes |
| --- | --- | --- |
| requestId | req-42 | Generated/validated at the boundary |
| traceId | Valid tracing ID | Keep format compatible with tracing |
| spanId | Span ID | Usually managed by the tracing library |
| operation | checkout | Stable value, no embedded PII |
| jobId | job-108 | Used for background jobs |
| tenant | tenant-code | Use only safe, log-approved IDs |
| correlationId | corr-77 | Clear contract across services |

**Do not log** passwords, tokens, cookies, private keys, OTPs, full request bodies, raw authorization headers, or unnecessary PII. If tenant/user identifiers can be considered personal or sensitive data in your application's context, follow access and retention policies.

### 11.2. Cardinality: Keep IDs for Querying, Not Unbounded Labels

`requestId` and `traceId` typically have very high cardinality. They are essential for **filtering and drilling down** into a specific request, but should not be used as metric labels or overview dashboard group-bys with millions of buckets. Dashboards should group by **service**, **operation**, **environment**, and stable dimensions; request IDs are for targeted investigation.

### 11.3. Key Count and Overhead

The MDC map is often copied/snapshotted when switching threads or creating log events. Putting hundreds of large keys increases allocations, memory usage, and output size. Keep **only a small set of high-value diagnostic fields**, set them at the right time, and clean them up promptly.

## 12. Testing MDC

A useful test suite verifies the **context lifecycle**, not just a single `MDC.put` call.

### 12.1. Direct API Check

~~~java
MDC.clear();
MDC.put("requestId", "req-test");
if (!"req-test".equals(MDC.get("requestId"))) {
    throw new AssertionError("MDC requestId was not set");
}
MDC.remove("requestId");
if (MDC.get("requestId") != null) {
    throw new AssertionError("MDC requestId was not removed");
}
~~~

This is an integration snippet inside a method with SLF4J MDC; it is not a standalone program. It verifies set/get/remove. If the provider does not support MDC or the adapter behaves differently, the test will catch the unexpected runtime configuration.

### 12.2. Scope Checks

- Before the scope, `operation` is absent.
- Inside the `putCloseable` scope, `operation=reserve`.
- After the scope, `operation` is gone.
- When a nested scope has a previous value, verify **save/restore** logic rather than assuming `putCloseable` restores it.

### 12.3. Thread Pool Checks

Use an executor with **a single worker thread** and submit:
1. A task without context propagation: must not see the main thread's `requestId`.
2. A task with a snapshot: must see the expected `requestId`.
3. A task after cleanup on the same worker: must not see the old `requestId`.

These three events are demonstrated by the actual stdout of the program in Section 6.

### 12.4. Formatted Output Checks

A test that only checks **MDC.get** is insufficient if your goal is observing logs in the console or a collector. Also verify:
- The backend/provider actually supports MDC.
- The layout/encoder outputs the fields.
- The formatter/JSON encoder preserves Unicode and escaping.
- Null/missing values are rendered according to policy.
- Log events carry the right context when passing through an async backend.
- Request cleanup runs on exception paths as well.

### 12.5. Avoiding Cross-Test MDC Pollution

JUnit may reuse threads across test cases or run tests in parallel. If a test sets MDC without clearing or restoring it, other tests can fail flakily. In each test, use `try/finally` and restore the initial context per contract; do not call `MDC.clear` inside a helper when the test framework has another active context.

## 13. Common Mistakes When Setting MDC Values

### Mistake 1 — Setting MDC but Seeing Nothing on the Console

**Cause:** The layout only prints the message without **%X{requestId}**, or the backend/provider does not support MDC as expected.

**Check:** `MDC.get("requestId")` on the right thread, the runtime provider, the Logback/Log4j layout, and actual output.

### Mistake 2 — Forgetting Cleanup

**Cause:** Setting `requestId` and then returning or throwing an exception without a `finally` block.

**Consequence:** The thread pool reuses the same thread for another request, and logs may carry the old correlation ID.

**Fix:** Use `try/finally`, `putCloseable` for appropriate keys, or a request filter that manages the lifecycle.

### Mistake 3 — Calling MDC.clear in a Nested Helper

**Cause:** A helper only owns `operation` but wipes out the caller's `traceId`/`requestId` as well.

**Fix:** Remove only the specific key or snapshot/restore the previous map if needed.

### Mistake 4 — Assuming putCloseable Restores the Previous Value

**Cause:** Using `putCloseable` for a key that already exists and expecting `close` to restore the old value.

**Fix:** SLF4J `MDCCloseable` removes the key; when overriding in a nested scope, save **previous** and restore it manually.

### Mistake 5 — Overwriting requestId in a Deep Layer

**Cause:** Service B generates a new `requestId` even though the request already has a gateway correlation ID.

**Fix:** Only generate/validate at the appropriate boundary; deeper layers preserve the correlation field or set a different field such as `operation` or `attemptId` when needed.

### Mistake 6 — Capturing Context at the Wrong Time

**Cause:** Calling `getCopyOfContextMap` inside the worker instead of before submitting.

**Fix:** Capture on the submitting thread before execution, then set and restore on the receiving thread.

### Mistake 7 — Setting MDC on Thread A and Reading on Thread B

**Cause:** Assuming ThreadLocal is automatically inherited across `ExecutorService`, `CompletableFuture`, or async frameworks.

**Fix:** Use a task decorator, context-aware executor, or official propagation mechanism.

### Mistake 8 — Using MDC as a Business Data Store

**Cause:** A payment service reads `tenant` from MDC to decide which data can be accessed.

**Fix:** Pass security/business context explicitly; MDC is strictly for logging/diagnostics.

### Mistake 9 — Using MDC.put(key, null) to Remove a Key

**Cause:** Null value handling depends on the implementation; it is not a portable remove command.

**Fix:** Use `MDC.remove(key)`, or restore the previous value in nested scopes.

### Mistake 10 — Key Mismatch Between Code and Layout

**Cause:** Code sets **requestId**, while the layout reads **request_id**.

**Fix:** Use a unified key schema and test the layout end-to-end.

### Mistake 11 — Wrong Backend or Multiple Providers Installed

**Cause:** Source code uses SLF4J, but the runtime lacks an MDC-capable provider or routes logs through another backend.

**Fix:** Inspect the dependency graph, pick one appropriate backend/provider, and avoid installing conflicting bridges.

### Mistake 12 — Leaking Sensitive Data

**Cause:** Putting session cookies, tokens, emails, or raw URL queries into MDC, which the encoder then dumps automatically.

**Fix:** Allowlist fields, validate/normalize IDs, limit size, redact sensitive data, and enforce proper access controls.

### Mistake 13 — Using Raw Input as a Log Line

**Cause:** `requestId` contains newlines or control characters, allowing log text to be forged with fake lines.

**Fix:** Validate IDs, use proper encoders/escaping, and never trust client request headers without validation.

### Mistake 14 — Confusing Async Appender with Async Task

**Cause:** Assuming an async logging backend automatically propagates MDC to business executors.

**Fix:** Capture context at the task boundary; verify separately when the backend snapshots the event.

## 14. Practical Workflow for Implementing MDC

### Step 1 — Define the Contract

Choose the list of keys and formats for **requestId**, **traceId**, **operation**, and other truly necessary fields. Document clearly which fields are allowed in logs and which are strictly forbidden.

### Step 2 — Choose an MDC-Capable Backend

If using SLF4J, identify the runtime provider. With Logback, configure **%X{key}** or a structured encoder. With Log4j2, you can use **ThreadContext** or a compatible SLF4J provider.

### Step 3 — Set Values at the Boundary

HTTP filters, message listeners, or job runners generate/validate IDs and set MDC before inner operations emit logs.

### Step 4 — Clean Up at the Right Scope

Use `try/finally` or a safe scoping mechanism. In nested scopes, restore the previous value; at a request boundary that owns the full context, clean up according to policy.

### Step 5 — Handle Thread Transitions

Identify which tasks run on executors, callbacks, schedulers, virtual threads, or reactive pipelines. Use context-aware wrappers/framework support and test propagation and cleanup.

### Step 6 — Test the Output

Emit logs at entry, inside services, after closing a scope, inside async tasks, and after cleanup. Verify there are no wrong/missing IDs or leaks to other requests.

### Step 7 — Verify Observability and Security

Confirm the log collector sees fields in the expected schema, contains no secrets, has appropriate retention, does not spike log volume/cost, and does not create high-cardinality metric labels.

## 16. Questions and Answers

**1. What is MDC?**  
A diagnostic key–value map typically bound to the current thread/context so logging events share common metadata.

**2. Does MDC.put output a log line by itself?**  
No. It only sets the context; the Logger and Layout/Encoder create and format the event.

**3. What happens if you set the same key twice?**  
The new value overwrites the old value in the current map.

**4. When should you use remove instead of clear?**  
When you only want to delete a key you own without destroying the caller's context.

**5. Does SLF4J MDC.putCloseable automatically restore the previous value?**  
It does not promise to; it removes the key on close. For accurate nested overrides, save and restore manually.

**6. Why might MDC.get("requestId") return null?**  
The key was not set, was removed/cleared, you are on a different thread, or the MDCAdapter/backend does not hold that data.

**7. Why does LOG.info not display requestId even though MDC.get is right?**  
The layout/encoder is not reading the MDC field, or the logging provider/output is not configured as expected.

**8. Does a thread pool automatically inherit the submitting thread's MDC?**  
Do not assume so. Capture a snapshot on the caller and set/restore it on the worker.

**9. Why is finally needed in a worker task?**  
So the task's values do not leak into the next task running on the same worker thread.

**10. Does MDC replace distributed tracing?**  
No. It helps attach `traceId` to logs, but tracing requires instrumentation and context propagation across services.

**11. Do SLF4J MDC and Log4j2 CloseableThreadContext have the same nested semantics?**  
Not quite. SLF4J `MDCCloseable` removes the key; Log4j2 `CloseableThreadContext.put` is contracted to restore the previous value.

**12. What data should be stored in MDC?**  
Only diagnostic IDs/fields that are permitted, small in size, and have a clear lifecycle.

**13. Should you put tokens into MDC and disable DEBUG in production?**  
No. Backends/levels can change, and sensitive data can still leak into logs.

**14. Why shouldn't requestId be used as the Logger name?**  
Because Logger names should stay stable per class/package; correlation IDs vary per request and belong in event context.

## 18. Conclusion

**Setting MDC values is a small operation with a major impact on log investigation quality.** Calling **MDC.put("requestId", ...)** at the right boundary and configuring the layout to read that key allows multiple log events from the same request to carry a consistent correlation ID without editing every message.

Three rules to remember: **set the right context, clean up at the right scope, and propagate context intentionally across thread boundaries**. Use **remove/clear** responsibly, avoid assuming `putCloseable` restores old keys, use **getCopyOfContextMap + setContextMap + finally restore** with `ExecutorService`, and never put sensitive data into MDC. The verified Java 17 example clearly demonstrates the difference between logging on the main thread, a worker without context, a worker with propagated context, and a worker after cleanup.
