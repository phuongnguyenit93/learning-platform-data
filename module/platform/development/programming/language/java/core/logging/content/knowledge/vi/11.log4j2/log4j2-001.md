# Log4j2 là gì? Tổng quan Apache Log4j2 trong Java

## 1. Log4j2 là gì?

**Apache Log4j2** (thường gọi là **Log4j 2**) là một framework logging cho ứng dụng Java thuộc dự án Apache Logging Services. Nó cung cấp API để ghi những sự kiện quan trọng hoặc thông tin chẩn đoán, cùng một hệ thống triển khai để **lọc, định dạng và chuyển log** tới console, file hoặc các đích được cấu hình.

Ví dụ: một ứng dụng thương mại điện tử muốn ghi thời điểm đơn hàng được tạo, cảnh báo tồn kho thấp hoặc một exception khi thanh toán thất bại. Mã nghiệp vụ có thể ghi các sự kiện bằng `Logger`; Log4j2 quyết định sự kiện nào được giữ lại, cách trình bày và nơi nhận.

**Phân biệt ngay từ đầu:**

- **Log4j2 không phải Log4j 1.x.** Đây là thế hệ kiến trúc khác, với API, Core và cách cấu hình khác. Log4j 1.x đã hết vòng đời hỗ trợ và không nên được chọn cho dự án mới.
- **Log4j2 không đồng nghĩa với SLF4J.** SLF4J là facade/API chung; Log4j2 có API riêng và cũng có thể làm backend cho những lời gọi SLF4J khi cài đúng provider.
- **Log4j2 không phải hệ thống lưu trữ tập trung.** Nó có thể xuất log để một hệ thống khác thu thập và tìm kiếm; muốn có dashboard, alert, retention tập trung hay distributed tracing cần thêm thành phần phù hợp.
- **Mức `TRACE` của Log4j2 là mức độ chi tiết của log**, không tự tạo distributed trace/span.

Một bản ghi log có thể có timestamp, level, logger name, message, exception, thread và context như request ID. Việc xuất đủ các trường hay không phụ thuộc vào cấu hình layout/backend.

## 2. Vì sao dùng Log4j2 thay vì System.out.println?

`System.out.println(...)` có thể hữu ích khi học hoặc kiểm tra nhanh, nhưng nó không cung cấp sẵn hệ thống logging có quản lý. Log4j2 hỗ trợ:

1. **Log level:** bật/tắt sự kiện theo mức `ERROR`, `WARN`, `INFO`, `DEBUG`, `TRACE`...
2. **Đặt tên logger:** cấu hình mức chi tiết riêng theo package/class.
3. **Appender:** đưa sự kiện ra console, file và những đích khác thông qua các module hỗ trợ.
4. **Layout:** định dạng bản ghi thành text có cấu trúc, pattern hoặc JSON với module thích hợp.
5. **Filter:** lọc theo level, marker, nội dung hoặc ngữ cảnh với các bộ lọc được hỗ trợ.
6. **Throwable logging:** ghi exception cùng stack trace để chẩn đoán.
7. **Context:** gắn dữ liệu tương quan như `requestId`, `traceId`, service hoặc môi trường bằng `ThreadContext`.
8. **Tùy chọn bất đồng bộ:** giảm việc xử lý I/O log trực tiếp trên luồng nghiệp vụ khi cấu hình phù hợp.
9. **Rolling file:** chuyển file theo kích thước hoặc thời gian, hỗ trợ chiến lược giữ file theo cấu hình.

Ví dụ, môi trường production có thể chỉ bật `INFO` trở lên cho phần lớn ứng dụng, nhưng tạm bật `DEBUG` với package thanh toán khi cần điều tra. Khi đó không phải sửa từng lời gọi log trong source code.

## 3. Kiến trúc: Log4j API, Log4j Core và cấu hình

Trong Log4j2, nên phân biệt rõ:

| Thành phần | Vai trò | Ví dụ |
| --- | --- | --- |
| **Log4j API** | Các interface và class mà mã ứng dụng gọi | `org.apache.logging.log4j.Logger`, `LogManager`; dependency `log4j-api` |
| **Log4j Core** | Triển khai việc cấu hình, xử lý sự kiện, appender, layout và filter | Dependency `log4j-core` |
| **Configuration** | Quy định logger, level, appender, layout, filter và đường đi của log | `log4j2.xml`, cấu hình properties, JSON/YAML nếu module hỗ trợ |
| **Provider/adapter tích hợp** | Cho phép API khác gửi log tới Log4j2, hoặc chuyển Log4j2 API sang nơi khác | Ví dụ `log4j-slf4j2-impl` cho SLF4J 2.x → Log4j2 |

Luồng xử lý tổng quát:

```text
Mã Java: LogManager.getLogger(...)
                 │
                 ▼
        Logger từ Log4j API
                 │
                 ▼
       Cấu hình Logger/Root
         (level, filters)
                 │
                 ▼
           Log4j Core
                 │
           AppenderRef
                 ▼
       Appender + Layout
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Console    File      Đích khác
```

**API không phải Core.** Nếu chỉ thêm `log4j-api` mà thiếu Core hoặc provider triển khai thích hợp, lời gọi có thể sử dụng cơ chế dự phòng tùy môi trường nhưng **không có đầy đủ tính năng Core** và không nên kỳ vọng cấu hình `log4j2.xml` với các appender hoạt động như mong muốn. Đối với ví dụ Log4j2 dùng backend Core trong bài, cần cả `log4j-api` và `log4j-core` trên runtime classpath.

Cấu hình của Log4j2 được đọc khi framework khởi tạo. Trong một ứng dụng, có thể có nhiều logger nhưng chúng thường được quản lý tập trung bằng cùng cấu hình và tập các appender.

## 4. Logger, Appender, Layout và Filter

### Logger

Logger là đối tượng dùng để tạo sự kiện:

```java
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class InventoryService {
    private static final Logger LOG =
            LogManager.getLogger(InventoryService.class);

    public void checkStock(int remaining) {
        LOG.info("Checking inventory");
        if (remaining < 3) {
            LOG.warn("Low stock: {}", remaining);
        }
    }
}
```

Đây là class minh họa. Muốn biên dịch cần `log4j-api`; để Log4j2 Core thực thi và xuất log theo cấu hình cần `log4j-core`. Logger thường được đặt theo tên class/package, cho phép đặt level riêng theo namespace. Có thể viết `LogManager.getLogger("com.example.payment")` nếu cần tên cụ thể.

### Appender

**Appender** là thành phần xử lý nơi đưa log ra. Ví dụ:

- `Console`: xuất sự kiện lên `SYSTEM_OUT` hoặc `SYSTEM_ERR`.
- `File`: ghi vào một file cụ thể.
- `RollingFile`: ghi file và chuyển file theo chính sách.
- Các appender khác tùy module/dependency và môi trường triển khai.

Một logger có thể tham chiếu nhiều appender: ví dụ console cho vận hành và rolling file cho lưu cục bộ. Chọn đích theo hạ tầng thực tế; trong container thường ưu tiên stdout/stderr rồi để hệ thống bên ngoài thu thập.

### Layout

**Layout** quyết định định dạng của sự kiện, ví dụ PatternLayout:

```text
%d{ISO8601} %-5level [%t] %logger - %msg%n
```

Các ký hiệu phổ biến: `%d` là thời gian, `%level` là level, `%t` là thread, `%logger` là logger name, `%msg` là message, `%n` là xuống dòng. Cấu hình có thể thêm exception converter như `%ex` khi cần stack trace. Muốn JSON có cấu trúc nên dùng layout/encoder phù hợp, ví dụ **JsonTemplateLayout** cùng module `log4j-layout-template-json` thay vì tự ghép chuỗi JSON bằng tay.

### Filter

**Filter** có thể quyết định nhận, từ chối hoặc để các bước tiếp tục đánh giá sự kiện. Nó có thể được đặt tại các mức trong pipeline tùy cấu hình, không chỉ tại logger. Vì vậy một log có level phù hợp vẫn có thể không xuất nếu appender, filter hoặc đường đi không cho phép.

## 5. Các log level của Log4j2

Các level thường dùng được xếp từ ít chi tiết/nặng nhất đến chi tiết nhiều hơn:

| Level | Ý nghĩa thường gặp |
| --- | --- |
| `FATAL` | Sự cố rất nghiêm trọng, ứng dụng hoặc thành phần không thể tiếp tục bình thường |
| `ERROR` | Thao tác thất bại hoặc lỗi cần điều tra |
| `WARN` | Bất thường có thể phục hồi nhưng đáng theo dõi |
| `INFO` | Các mốc hoạt động quan trọng |
| `DEBUG` | Thông tin phục vụ lập trình viên chẩn đoán |
| `TRACE` | Thông tin rất chi tiết của luồng xử lý |
| `ALL` | Giá trị đặc biệt, cho phép mọi level ở ngưỡng tương ứng |
| `OFF` | Giá trị đặc biệt, tắt việc ghi ở ngưỡng tương ứng |

Ví dụ với cấu hình logger `INFO`, các bản ghi `INFO`, `WARN`, `ERROR` và `FATAL` có thể được chấp nhận; `DEBUG` và `TRACE` không được tạo/đi tiếp từ logger đó. Nếu đổi logger thành `DEBUG`, các bản ghi DEBUG cũng có thể đi tiếp.

Lựa chọn level dựa vào **mức độ quan trọng của sự kiện trong ngữ cảnh ứng dụng**, không chỉ dựa vào tên exception. Một lỗi validation được xử lý dự kiến không nhất thiết là ERROR; một lỗi khởi tạo khiến dịch vụ không thể chạy có thể là ERROR hoặc FATAL tùy chính sách.

### Cần phân biệt với JUL và SLF4J

- JUL dùng các tên `SEVERE`, `WARNING`, `INFO`, `CONFIG`, `FINE`, `FINER`, `FINEST`; không có hằng `Level.DEBUG` chuẩn.
- SLF4J thường dùng `ERROR`, `WARN`, `INFO`, `DEBUG`, `TRACE` (không có `FATAL` trong bộ level API thông dụng).
- Log4j2 có mức `FATAL` trong API riêng.

Đừng dùng enum/class level của framework này làm đối số cho API của framework khác. Khi dùng bridge/provider, việc ánh xạ level do lớp tích hợp thực hiện.

## 6. Ví dụ Maven + Java 17 đầy đủ: Log4j2 xuất console

Ví dụ dùng **Log4j2 API + Core trực tiếp**, không qua SLF4J, để thấy rõ ý nghĩa framework. Mỗi file được trình bày đầy đủ; có thể chạy bằng JDK 17+ và Maven.

### Cấu trúc dự án

```text
log4j2-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── demo/
        │       └── Log4j2Demo.java
        └── resources/
            └── log4j2.xml
```

### Tệp pom.xml

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>demo</groupId>
    <artifactId>log4j2-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-api</artifactId>
            <version>2.24.3</version>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-core</artifactId>
            <version>2.24.3</version>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
            </plugin>
        </plugins>
    </build>
</project>
```

**Chú ý phiên bản:** `2.24.3` ở trên chỉ là **phiên bản được ghim cho ví dụ có thể lặp lại**, không phải lời khẳng định đó là bản mới nhất hoặc bản nên triển khai production tại mọi thời điểm. Với ứng dụng thật, chọn phiên bản đang được duy trì, cập nhật các bản vá bảo mật và quản lý đồng bộ phiên bản `log4j-api`/`log4j-core`.

### Tệp src/main/resources/log4j2.xml

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="Console" target="SYSTEM_OUT">
            <PatternLayout pattern="%level | %logger{1} | %msg%n"/>
        </Console>
    </Appenders>

    <Loggers>
        <Logger name="demo" level="debug" additivity="false">
            <AppenderRef ref="Console"/>
        </Logger>

        <Root level="info">
            <AppenderRef ref="Console"/>
        </Root>
    </Loggers>
</Configuration>
```

Ở đây:

- `Console` là appender với tên `Console`, ghi vào `SYSTEM_OUT`.
- `PatternLayout` chọn một format ngắn, ổn định để học. `%logger{1}` lấy phần cuối của logger name như `Log4j2Demo`.
- Logger có tên `demo` cho phép các class trong package `demo` ghi đến mức DEBUG.
- `additivity="false"` tránh gửi lại sự kiện thuộc logger `demo` lên root, nếu không có thể xuất log trùng khi cả hai đều tham chiếu cùng appender.
- `Root level="info"` cung cấp ngưỡng mặc định cho những logger không có cấu hình riêng.

### Tệp src/main/java/demo/Log4j2Demo.java

```java
package demo;

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class Log4j2Demo {
    private static final Logger LOG =
            LogManager.getLogger(Log4j2Demo.class);

    public static void main(String[] args) {
        String orderId = "ORD-42";
        int remaining = 2;

        LOG.info("Application ready");
        LOG.debug("Validating order {}", orderId);

        if (remaining < 3) {
            LOG.warn("Low stock: {}", remaining);
        }

        LOG.error("Checkout rejected: {}", orderId);
        System.out.println("business-finished");
    }
}
```

Từ thư mục `log4j2-demo`, thực hiện:

```bash
mvn -q compile exec:java -Dexec.mainClass=demo.Log4j2Demo
```

**Kết quả stdout do chương trình và appender Console tạo ra** với cấu hình trên:

```text
INFO | Log4j2Demo | Application ready
DEBUG | Log4j2Demo | Validating order ORD-42
WARN | Log4j2Demo | Low stock: 2
ERROR | Log4j2Demo | Checkout rejected: ORD-42
business-finished
```

Đây là kết quả dự kiến của mã demo và PatternLayout cố định. Maven hoặc môi trường có thể in thêm cảnh báo riêng ngoài những dòng do ứng dụng tạo. Vì `Console target="SYSTEM_OUT"` và `System.out.println` cùng dùng stdout trong một chương trình đồng bộ, thứ tự trên là thứ tự thực hiện trong ví dụ.

**Điểm quan trọng:** mặc dù `Root` đặt INFO, logger package `demo` có ngưỡng DEBUG riêng nên bản ghi DEBUG vẫn hiển thị qua appender đã tham chiếu. Nếu bỏ cấu hình logger `demo`, bản ghi DEBUG sẽ bị ngưỡng INFO của root lọc.

## 7. Giải thích chi tiết log4j2.xml

Một cấu hình Log4j2 thường được chia thành:

1. **`<Configuration>`:** phần gốc; có thể chứa thuộc tính điều khiển việc phát hiện thay đổi cấu hình, cấu hình trạng thái nội bộ, v.v.
2. **`<Appenders>`:** khai báo các đích xử lý log, mỗi appender có tên để tham chiếu.
3. **`<Loggers>`:** đặt level và danh sách appender theo logger/package.
4. **`<Root>`:** logger gốc cho những logger thừa kế cấu hình chung.
5. **`<AppenderRef>`:** kết nối logger với một appender đã đặt tên.

### Additivity và log trùng

Giả sử có logger `demo` với Console appender và root cũng có Console appender. Khi `additivity="true"` (giá trị thường dùng nếu không cấu hình khác), một sự kiện từ logger `demo` có thể được xử lý ở appender của `demo` **và** chuyển lên cấu hình của root. Nếu hai đường dẫn cùng xuất vào console, một sự kiện có thể hiện **hai lần**.

Tắt `additivity` ở logger có appender riêng khi muốn ngăn sự kiện đi tiếp đến appender của logger cha/root. Nhưng nếu tắt additivity mà không gắn appender thích hợp cho logger đó, log có thể không có nơi nhận. Additivity liên quan tới **đường đi của sự kiện**, không đồng nghĩa với việc ngừng kế thừa mọi cấu hình.

### Level của logger và filter của appender

Level logger quyết định sự kiện nào được cho đi tiếp. Sau đó appender hoặc appender reference còn có thể lọc. Ví dụ trong một cấu hình có cả Console và RollingFile, có thể chọn xuất INFO ra console nhưng chỉ đưa WARN/ERROR vào một appender riêng. Do có nhiều tầng lọc, **thấy DEBUG được bật ở logger chưa đủ để kết luận DEBUG đã xuất đến mọi nơi**.

Khi sửa XML, kiểm tra đúng tên appender trong `AppenderRef`. Nếu tham chiếu sai tên, appender mong đợi không được kết nối.

## 8. Ghi exception và stack trace

Log4j2 hỗ trợ truyền nguyên đối tượng `Throwable` để backend có thể hiển thị stack trace và cause chain. Ví dụ minh họa **bên trong class có Logger LOG**:

```java
try {
    Integer.parseInt("bad-value");
} catch (NumberFormatException exception) {
    LOG.error("Cannot parse configured port", exception);
}
```

Khi exception được đưa cho logger, `Log4j2 Core` có thể format stack trace bằng layout thích hợp. Nếu chỉ gọi:

```java
LOG.error("Cannot parse configured port: {}", exception.getMessage());
```

bạn chỉ truyền chuỗi message, không tự đính kèm đối tượng `Throwable` cho event.

Một ví dụ dùng placeholder và Throwable cuối cùng:

```java
LOG.error("Order {} failed during processing", orderId, exception);
```

Đoạn trên giả định `orderId` và `exception` đã tồn tại. Dạng parameterized logging có thể nhận Throwable cuối cùng làm lỗi đi kèm sự kiện. Trong thực tế nên kiểm tra formatter/encoder xuất lỗi theo cách mong muốn, đặc biệt nếu sử dụng layout tùy biến hoặc hệ thống thu thập log có giới hạn kích thước.

Khi bọc exception, nhớ giữ `cause`: `new IllegalStateException("Cannot submit order", exception)` giúp tầng xử lý cuối cùng ghi được cả ngữ cảnh và nguyên nhân gốc. Tránh vừa `printStackTrace()` vừa `LOG.error(..., exception)` cho cùng lỗi nếu không có mục đích rõ ràng.

## 9. Ghi file và RollingFile

Log4j2 không bị giới hạn ở console. Một appender `RollingFile` có thể ghi log và xoay file theo kích thước hoặc thời gian. Ví dụ sau là **mảnh XML minh họa** đặt bên trong phần `<Appenders>` của một cấu hình Log4j2, không phải toàn bộ file XML:

```xml
<RollingFile name="RollingFile"
             fileName="logs/application.log"
             filePattern="logs/application-%d{yyyy-MM-dd}-%i.log.gz">
    <PatternLayout
        pattern="%d{ISO8601} %-5level %logger - %msg%n"/>
    <Policies>
        <TimeBasedTriggeringPolicy/>
        <SizeBasedTriggeringPolicy size="10 MB"/>
    </Policies>
    <DefaultRolloverStrategy max="5"/>
</RollingFile>
```

Để appender này nhận sự kiện, logger hoặc root cần tham chiếu tên `RollingFile` trong `<AppenderRef ref="RollingFile"/>`. Cần có quyền ghi vào thư mục, kiểm soát dung lượng và kiểm thử rotation dưới tải thực.

`DefaultRolloverStrategy max="5"` liên quan đến chiến lược giới hạn các phiên bản file rollover trong cấu hình phù hợp; **không nên hiểu nó là chính sách retention tổng quát bảo đảm xóa mọi file log cũ sau đúng năm ngày**. Với hệ thống cần quy định retention rõ ràng, hãy cấu hình cơ chế dọn dẹp phù hợp và kiểm chứng trong môi trường thực tế.

Trong môi trường container, console output được nền tảng thu thập thường phù hợp hơn việc tự ghi file vào filesystem ngắn hạn. Điều này tùy kiến trúc vận hành, không phải quy tắc cố định.

## 10. Log4j2 và SLF4J: dùng chung như thế nào?

**SLF4J** là facade độc lập được nhiều thư viện Java dùng. **Log4j2** có API và Core riêng; nó cũng có thể là backend cho những lời gọi SLF4J.

Hai trường hợp:

| Ứng dụng gọi API nào? | Dependency chính | Hướng thực thi |
| --- | --- | --- |
| `org.apache.logging.log4j.Logger` | `log4j-api` + `log4j-core` | Log4j2 API → Log4j2 Core |
| `org.slf4j.Logger` với SLF4J 2.x | `slf4j-api` + `log4j-slf4j2-impl` và các module Log4j2 phù hợp | SLF4J API → Log4j2 Core |

Nếu dùng SLF4J 1.7.x, adapter đời cũ có tên `log4j-slf4j-impl`, **khác** provider cho SLF4J 2.x. Không tự trộn các phiên bản lớn vì “đều có chữ slf4j”.

Ngoài ra, `log4j-to-slf4j` thực hiện hướng **Log4j2 API → SLF4J**. Không nên dùng đồng thời `log4j-to-slf4j` (Log4j2 → SLF4J) với `log4j-slf4j2-impl` (SLF4J → Log4j2), vì có thể tạo vòng lặp chuyển tiếp log.

```text
Hướng phù hợp khi chọn Log4j2 làm backend:
SLF4J API --(log4j-slf4j2-impl)--> Log4j2 Core

Hướng ngược khi chọn backend SLF4J khác:
Log4j2 API --(log4j-to-slf4j)--> SLF4J API --> backend khác
```

Nếu dự án Spring Boot đã cung cấp starter logging và dependency transitively, nên kiểm tra backend đang có trước khi thay thế. Một ứng dụng có **nhiều SLF4J provider** hoặc cặp bridge ngược chiều dễ gặp cảnh báo, mất log, trùng log hoặc cấu hình không có hiệu lực.

## 11. ThreadContext: thêm ngữ cảnh cho bản ghi

Trong ứng dụng server, nhiều request thực thi đồng thời nên các dòng log có thể xen kẽ. Log4j2 cung cấp `ThreadContext` để gắn ngữ cảnh vào sự kiện, ví dụ `requestId`.

Ví dụ minh họa bên trong method có `LOG`:

```java
import org.apache.logging.log4j.ThreadContext;

ThreadContext.put("requestId", "REQ-204");
try {
    LOG.info("Starting order validation");
    LOG.info("Order validation completed");
} finally {
    ThreadContext.remove("requestId");
}
```

Các import đặt ở đầu file Java. Để hiển thị `requestId` trong PatternLayout, có thể thêm `%X{requestId}` vào pattern:

```text
%d{ISO8601} [%t] %-5level requestId=%X{requestId} %logger - %msg%n
```

Nếu không cấu hình layout xuất context, chỉ gọi `ThreadContext.put(...)` **không bảo đảm trường requestId sẽ xuất trong console log**. Không đưa token hoặc thông tin nhạy cảm vào context; chúng có thể được sao chép vào nhiều bản ghi.

`ThreadContext` thường gắn với ngữ cảnh thực thi theo thread. Trong hệ thống dùng thread pool, `CompletableFuture` hoặc xử lý bất đồng bộ, context có thể **không tự truyền** sang worker thread. Cần truyền/khôi phục context đúng ranh giới nhiệm vụ để tránh log của request này mang ID của request khác. Context ID giúp tương quan log, nhưng **không thay thế** hệ thống distributed tracing có span/trace propagation.

## 12. Logging bất đồng bộ (asynchronous logging)

Log4j2 hỗ trợ các cách ghi log bất đồng bộ để giảm việc luồng nghiệp vụ chờ công việc xuất log. Hai khái niệm thường gặp:

- **AsyncAppender:** nhận event và chuyển cho appender đích qua hàng đợi bất đồng bộ, theo cấu hình.
- **AsyncLogger:** kiến trúc logger bất đồng bộ với cơ chế và dependency/cấu hình tương ứng.

Đây là **hai cơ chế khác nhau**; không nên mặc định rằng chỉ đổi một tùy chọn là mọi logger trở thành AsyncLogger. Tùy phiên bản và cách triển khai, AsyncLogger có thể cần module như LMAX Disruptor cùng cấu hình cụ thể.

Đánh đổi cần cân nhắc:

1. **Thông lượng và độ trễ:** luồng nghiệp vụ có thể giảm thời gian chờ I/O log, nhưng không miễn phí CPU, bộ nhớ hoặc chi phí xả hàng đợi.
2. **Hàng đợi đầy:** cơ chế có thể fallback, block hoặc xử lý theo chính sách đã đặt; cần kiểm tra rõ hành vi.
3. **Shutdown/crash:** nếu tiến trình kết thúc đột ngột khi còn event trong hàng đợi, một số log có thể chưa được ghi bền vững.
4. **Thứ tự:** logging bất đồng bộ và nhiều thread có thể ảnh hưởng cách quan sát trình tự event.
5. **Exception/context:** bảo đảm các dữ liệu cần thiết được bắt lại đúng lúc phát sự kiện.

Không mặc định “async luôn nhanh hơn” mà không đo bằng tải và backend thực. Với ứng dụng học tập hoặc nhu cầu logging nhỏ, cấu hình đồng bộ đơn giản thường giúp quan sát dễ hơn.

## 13. Bảo mật: Log4Shell và quản lý dependency

Log4j2 từng có lỗ hổng nghiêm trọng được biết đến rộng rãi với tên **Log4Shell** (CVE-2021-44228) trong một số phiên bản Log4j2 Core cũ, liên quan đến cơ chế lookup/JNDI. Điều đó **không có nghĩa mọi phiên bản Log4j2 đều đang có cùng lỗ hổng**; tình trạng bảo mật phụ thuộc phiên bản, thành phần thực tế được đóng gói và cấu hình.

Các nguyên tắc quan trọng khi dùng Log4j2 hiện nay:

- Sử dụng **phiên bản được duy trì và có bản vá bảo mật**, thay vì sao chép dependency cũ từ bài hướng dẫn.
- Kiểm tra **dependency tree và artifact trong bản build cuối**, kể cả các thư viện có thể kéo Log4j2 vào gián tiếp.
- Không dùng Log4j 1.x cho dự án mới hoặc giữ các bản Log4j2 cũ không được vá.
- Chỉ bật plugin/appender/lookup cần thiết, hạn chế cấu hình động không đáng tin và kiểm soát quyền sửa file cấu hình.
- Không ghi mật khẩu, khóa API, token, cookie, thông tin thanh toán hoặc dữ liệu riêng tư vào log.
- Dùng formatter, hệ thống thu thập và retention phù hợp; bảo vệ quyền truy cập và xử lý log từ dữ liệu không đáng tin cậy.

Nếu ứng dụng chỉ dùng `slf4j-api`, đừng mặc định nó đã kéo `log4j-core` vào. Ngược lại, nếu ứng dụng đóng gói Core qua provider hoặc dependency gián tiếp, cần kiểm kê **version Core thực tế** để đánh giá rủi ro.

## 14. Các lỗi thường gặp

| Triệu chứng | Nguyên nhân thường gặp | Hướng chẩn đoán |
| --- | --- | --- |
| Có `LOG.info(...)` nhưng không thấy bản ghi | Thiếu Core/provider thích hợp, config chưa được nạp, level/filter chặn | Kiểm tra runtime dependencies, thông báo trạng thái cấu hình và logger level |
| Chỉ thấy ERROR, không thấy INFO | Cấu hình mặc định hoặc root ở ngưỡng cao | Kiểm tra `log4j2.xml`, logger name và level |
| Không thấy DEBUG khi root INFO | Logger tương ứng đang kế thừa INFO, hoặc appender/filter loại DEBUG | Đặt DEBUG cho đúng package và kiểm tra appender/filter |
| Một sự kiện xuất hai lần | Có appender trực tiếp và qua logger cha/root, additivity bật | Xem lại `AppenderRef` và `additivity` |
| XML đã sửa nhưng log không đổi | File không nằm trên runtime classpath, file khác được nạp hoặc chưa có reload | Xác minh file trong resources, cấu hình active và cơ chế reload |
| Console có log nhưng file không có | RollingFile chưa được tham chiếu, thiếu quyền ghi hoặc filter | Kiểm tra AppenderRef, directory, file pattern, policies |
| Thiếu stack trace | Chỉ truyền `exception.getMessage()` hoặc layout bỏ exception | Truyền `Throwable` và kiểm tra exception converter/layout |
| Log format khác dự kiến | Backend thực tế khác Log4j2 Core hoặc file config không được dùng | Kiểm tra provider/bridge, dependency tree |
| Có lỗi vòng lặp tích hợp | Kết hợp Log4j2 → SLF4J và SLF4J → Log4j2 | Chỉ giữ một hướng chuyển log |
| MDC/ThreadContext sai request | Thread được tái sử dụng hoặc context không được dọn/truyền | Dọn trong finally và triển khai propagation phù hợp |
| Log nhiều làm tăng latency hoặc tốn đĩa | Level quá chi tiết, event lớn, appender chậm | Giảm phạm vi DEBUG/TRACE, đo tải và kiểm soát retention |

### Quy trình kiểm tra đơn giản

1. Xác định mã gọi **Log4j2 API** trực tiếp hay **SLF4J facade**.
2. Kiểm tra dependency runtime: `log4j-api`, `log4j-core` hoặc provider/adapter được chọn.
3. Xác nhận file `log4j2.xml` nằm trong resources và được nạp; xem cảnh báo nội bộ nếu cấu hình lỗi.
4. Kiểm tra tên logger, level hiệu lực, filter, `additivity` và `AppenderRef`.
5. Kiểm tra appender đích: stdout/stderr, thư mục file, quyền ghi và cấu hình rolling.
6. Thử ghi một INFO, một DEBUG và một ERROR ở môi trường kiểm soát.
7. Với exception, truyền nguyên Throwable và xác nhận stack trace trong đích log thực tế.

## 15. Khi nào nên dùng Log4j2?

Log4j2 phù hợp nếu ứng dụng cần backend logging có thể cấu hình khá linh hoạt: nhiều appender, phân cấp logger, filters, layout, rolling file hoặc yêu cầu vận hành đặc thù. Trong một dự án đã chọn Logback/JUL và đang vận hành ổn định, **không cần đổi sang Log4j2 chỉ vì nó là một lựa chọn phổ biến**. Hãy so sánh khả năng hiện có, mức độ phức tạp của migration, tương thích dependency và chính sách vận hành.

Nếu đang xây một **thư viện Java tái sử dụng**, hãy cân nhắc dùng facade như SLF4J thay vì buộc mọi ứng dụng gọi trực tiếp Log4j2. Nếu đang xây **ứng dụng cuối** và muốn sử dụng Log4j2 Core làm backend, có thể gọi Log4j2 API trực tiếp hoặc dùng SLF4J qua provider phù hợp; lựa chọn nào cũng cần một hướng logging nhất quán.

## 16. Tự kiểm tra kiến thức

**Câu 1:** Log4j2 có phải là một bản cập nhật tương thích hoàn toàn với Log4j 1.x không?  
**Đáp án:** Không. Log4j2 có kiến trúc/API/cấu hình khác; Log4j 1.x không phải lựa chọn được duy trì cho dự án mới.

**Câu 2:** `log4j-api` và `log4j-core` làm gì?  
**Đáp án:** API cung cấp Logger/LogManager cho code; Core thực hiện pipeline xử lý, layout, filter, appender theo cấu hình.

**Câu 3:** Appender và Layout khác nhau thế nào?  
**Đáp án:** Appender quyết định nơi xử lý/xuất sự kiện; Layout quyết định cách định dạng nội dung sự kiện.

**Câu 4:** Vì sao root INFO mà logger `demo` vẫn ghi DEBUG trong ví dụ?  
**Đáp án:** Logger `demo` có cấu hình level DEBUG riêng, tham chiếu Console appender, nên không bị ngưỡng INFO của root lọc ở điểm phát.

**Câu 5:** `additivity="false"` dùng để làm gì?  
**Đáp án:** Ngăn sự kiện tiếp tục tới appender của logger cha/root, thường nhằm tránh log trùng khi logger đã có appender riêng.

**Câu 6:** `LOG.error("Failure", exception)` có ích gì hơn `LOG.error(exception.getMessage())`?  
**Đáp án:** Dạng đầu chuyển nguyên Throwable cho backend để có thể in stack trace, cause và thông tin lỗi cần chẩn đoán.

**Câu 7:** Muốn dùng Log4j2 làm backend cho SLF4J 2.x cần phân biệt adapter nào?  
**Đáp án:** Dùng provider theo hướng SLF4J → Log4j2, ví dụ `log4j-slf4j2-impl`; không phối hợp với `log4j-to-slf4j` theo hướng ngược để tránh vòng lặp.

**Câu 8:** Có phải bật TRACE là tự có distributed tracing?  
**Đáp án:** Không. TRACE là log level; distributed tracing cần instrumentation, trace context và các span riêng.

**Câu 9:** Vì sao phải cập nhật Log4j2 thường xuyên?  
**Đáp án:** Logging là một phần của bề mặt tấn công và vận hành; cần dùng phiên bản được bảo trì, bản vá an ninh và kiểm tra dependency thực tế.

**Ghi nhớ:** **Log4j2 là framework logging gồm API và phần thực thi Core**. Mã Java phát sự kiện qua Logger; cấu hình điều khiển level, appender, layout, filter và đường đi của log. Hiểu sự khác nhau giữa Log4j2, SLF4J, Logback và JUL giúp bạn xây được một pipeline logging rõ ràng, dễ chẩn đoán và an toàn hơn.
