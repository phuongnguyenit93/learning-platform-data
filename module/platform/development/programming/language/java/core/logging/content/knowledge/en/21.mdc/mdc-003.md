# Reading MDC Values in Java Logging: MDC.get, Snapshots, Layouts, and Testing

## 1. What Does Reading MDC Values Mean?

**MDC** (Mapped Diagnostic Context) is a **key–value** context area that helps log records within a processing scope carry the same correlation information, such as `request_id`, `trace_id`, or `job_id`. In a Java application using **SLF4J** and a compatible backend such as **Logback**, an MDC value can be:

1. Placed into the context with `MDC.put(key, value)`.
2. Read directly in Java code with `MDC.get(key)`.
3. Read as a copy of the entire context with `MDC.getCopyOfContextMap()`.
4. Output into a text line via a layout converter such as `%X{request_id}`.
5. Emitted as a separate field in JSON when the encoder supports MDC and is configured appropriately.

Example of handling a single request:

```java
MDC.put("request_id", "req-42");
try {
    String currentId = MDC.get("request_id");
    log.info("event=order.created");
} finally {
    MDC.remove("request_id");
}
```

This is an **illustrative snippet inside a method** that already has a `log` variable, not a standalone Java program. When run with a compatible MDC backend, the `currentId` variable receives the string `"req-42"`. The logging backend can simultaneously attach that value to the event. After removing the key, `MDC.get("request_id")` typically returns `null`.

**Key takeaway:** `MDC.get` reads the **current context at the call site**; it does not query a historical log store, does not read another thread's context, and does not guarantee that a logging event has already been written to the console or a collector.

### Real-World Scenario

Two requests A and B are processed interleaved:

```text
INFO  request_id=req-A event=request.received
INFO  request_id=req-B event=request.received
WARN  request_id=req-A event=inventory.cache_miss
ERROR request_id=req-B event=payment.failed
INFO  request_id=req-A event=request.completed
```

MDC helps attach the appropriate ID to an event right when the log is emitted. However, a call to `MDC.get("request_id")` during request B must read **B**'s ID, not a leftover ID from A. Therefore, learning how to **read** MDC must go hand in hand with understanding **scope, lifecycle, and context propagation**.

## 2. Essential SLF4J MDC Methods

With the SLF4J API, the main methods are:

| API | Meaning | Result / Notes |
| --- | --- | --- |
| `MDC.put(String key, String val)` | Set/update a value in the current context | Key and value are strings; not typed objects. |
| `MDC.get(String key)` | Read the value for a key | Returns `String`, or `null` if the key is absent. |
| `MDC.remove(String key)` | Remove a key from the current context | Does not remove other keys. |
| `MDC.clear()` | Clear the entire MDC of the current scope | May wipe out context set by a framework or parent scope. |
| `MDC.getCopyOfContextMap()` | Get a copy of the context map | Returns `Map<String,String>`, or `null` if no map exists. |
| `MDC.setContextMap(map)` | Replace the current context with the specified map | Suitable for restoring a saved snapshot. |
| `MDC.putCloseable(key, val)` | Set a key and receive a closeable `MDCCloseable` scope | Closing removes the key; do not assume it always restores a previous value in nested scopes. |
| `MDC.getMDCAdapter()` | Access the adapter provided by the provider/backend | Mainly for diagnostics/integration; avoid depending on implementation details in business logic. |

SLF4J's MDC is a **facade API**: how data is stored, copied, synchronized with the backend, and attached to events depends on the provider/adapter. With Logback Classic, per-thread reading is the familiar usage; asynchronous frameworks may require explicit context propagation.

### What Return Type Does `get` Have?

`MDC.get("request_id")` always returns **`String` or `null`** per the SLF4J contract—never an `Optional`, an integer, or an object containing metadata.

Example:

```java
String requestId = MDC.get("request_id");
if (requestId == null) {
    // No request_id in the current context.
}
```

This is a code snippet inside a method where `org.slf4j.MDC` has already been imported.

**Do not conflate these cases**:

| Case | Value Read | Meaning |
| --- | --- | --- |
| Key has not been set | `null` | No such entry exists in the current MDC. |
| Key is set to `"req-42"` | `"req-42"` | An ID is available for logging/correlation. |
| Key is set to the empty string `""` | `""` | The entry may exist, but the value is not useful. |
| Key is set to the string `"null"` | `"null"` | This is the **four characters** n-u-l-l, not Java `null`. |
| Reading on a different thread | Possibly `null` or that thread's own context | Does not automatically inherit the calling thread's request context. |

Do not use `if (requestId == "")` to check for an empty string; in Java, use `requestId.isEmpty()` or `requestId.isBlank()` after checking for `null`.

### Key Names Are Case-Sensitive

`"request_id"` is different from `"requestId"` or `"REQUEST_ID"`. When the program sets:

```java
MDC.put("request_id", "req-42");
```

then:

```java
MDC.get("request_id"); // "req-42"
MDC.get("requestId");  // null if that key does not exist
```

There is no default mechanism that automatically converts camelCase to snake_case. **Choose consistent key names** across filters, Java code, patterns, JSON encoders, and collectors.

## 3. Reading a Key Properly: Missing Data and Fallbacks

Not every log record occurs inside an HTTP request. Startup jobs, scheduled tasks, shutdown hooks, and background workers may not have a `request_id`. Therefore, a `null` value **can be completely normal**.

### Simple Reading Pattern

```java
String requestId = MDC.get("request_id");

if (requestId != null && !requestId.isBlank()) {
    log.debug("event=context.found request_id={}", requestId);
} else {
    log.debug("event=context.absent");
}
```

This is an **illustrative snippet** in a method that has `log`. When a safe display string is needed, a fallback can be used:

```java
String requestId = MDC.get("request_id");
String displayId = (requestId == null || requestId.isBlank())
        ? "unavailable"
        : requestId;
```

**Be careful with synthetic fallbacks:** `"unavailable"` is convenient for UIs or diagnostic logs, but it is **not a real request ID**. If every request missing an ID is tagged with `"unavailable"`, searches may accidentally group unrelated requests together.

### `getOrDefault` Belongs to Map, Not MDC

A common API mistake:

```java
// There is NO MDC.getOrDefault method in the standard SLF4J API.
// MDC.getOrDefault("request_id", "none");
```

The right approach is to read `MDC.get(...)` and handle `null`, or use a snapshot map safely:

```java
Map<String, String> context = MDC.getCopyOfContextMap();
String requestId = context == null
        ? "none"
        : context.getOrDefault("request_id", "none");
```

This is an illustrative snippet with `java.util.Map` already imported. `Map.getOrDefault` is a Java `Map` API; it is not a special MDC feature. Also, if a map implementation allows keys mapped to `null`, `getOrDefault` does not necessarily substitute the default; define a clear absence convention for your application.

### Reading Numeric/Boolean Values Requires Parsing and Validation

MDC values are normally strings:

```java
String attemptText = MDC.get("attempt");
Integer attempt = null;

if (attemptText != null) {
    try {
        attempt = Integer.valueOf(attemptText);
    } catch (NumberFormatException badValue) {
        // Choose fallback behavior according to policy.
    }
}
```

This is illustrative code. For `duration_ms` or `attempt`, it is better to preserve **numeric types** in structured event data if the backend supports it, rather than using MDC to turn every business attribute into a string and parsing it back.

**Do not use values read from MDC for critical business decisions** such as authorization, tenant isolation, billing, or fraud prevention. MDC is for logging and tracing; context may be missing, improperly restored, or derived from an unverified header.

## 4. Reading the Entire MDC with `getCopyOfContextMap()`

When you need to pass the context to another task or inspect multiple fields, you can take a snapshot:

```java
Map<String, String> snapshot = MDC.getCopyOfContextMap();

if (snapshot != null) {
    String requestId = snapshot.get("request_id");
    String traceId = snapshot.get("trace_id");
}
```

`snapshot` is a copy at the moment of the call. Depending on the provider/adapter, when MDC has no data, this method may return `null`. **Always handle `null`**—do not immediately call `snapshot.get(...)` or `snapshot.size()` without checking first.

### A Snapshot Is Not a Live View

Example:

```java
MDC.put("request_id", "req-1");
Map<String, String> snapshot = MDC.getCopyOfContextMap();

MDC.put("request_id", "req-2");

String oldValue = snapshot.get("request_id"); // "req-1"
String newValue = MDC.get("request_id");      // "req-2"
```

With an MDC adapter that copies the map according to the contract, the snapshot preserves the old value. This is what makes it possible to pass the context as of **task submission time**, without accidentally picking up a new value after the calling thread has moved on to another request.

**Do not mutate the snapshot map and expect the current MDC to change.** For example, `snapshot.put("request_id", "...")` only modifies the copied map if that map is mutable. To update the active context, use `MDC.put(...)`; to replace the whole context, use `MDC.setContextMap(...)` within a controlled scope.

### Can You Log the Entire Map for Debugging?

Technically yes, but **do not use**:

```java
log.info("MDC={}", MDC.getCopyOfContextMap());
```

in production without knowing the exact contents of every key. The map may contain tenant/user IDs, correlation IDs, or sensitive fields added by frameworks or libraries. Instead, log an approved **allowlist of fields**:

```java
String requestId = MDC.get("request_id");
log.debug("event=context.read request_id={}", requestId);
```

This is illustrative code; `log` and the necessary imports must be present. For client-supplied IDs, validation and escaping still apply before placing them into MDC.

## 5. Why Reading MDC Requires Understanding Lifecycle

A service typically uses a thread pool. Thread A handles request 1 and is then reused to handle request 2. If request 1 calls `MDC.put("request_id","req-1")` and does not clean it up, request 2 can read the stale ID.

### Basic Scope Limiting

```java
MDC.put("request_id", requestId);
try {
    doWork();
} finally {
    MDC.remove("request_id");
}
```

This is an illustrative snippet inside a method that already has `requestId` and `doWork()`.

`finally` ensures the key is cleaned up whether the code completes normally or throws an exception on the same thread. However, **`remove` does not restore a previous value** if an outer scope had already set `request_id`.

Nested scope example:

```text
Parent scope: request_id=req-parent
    |
    +-- Child scope sets request_id=req-child
    |
    +-- Child scope calls remove(request_id)
    |
Parent scope: request_id is lost instead of req-parent
```

If the application has nested scopes, choose **snapshot and restore**.

### Safe Snapshot and Restore for Nested Scopes

```java
Map<String, String> previous = MDC.getCopyOfContextMap();

try {
    MDC.put("request_id", requestId);
    doWork();
} finally {
    if (previous == null) {
        MDC.clear();
    } else {
        MDC.setContextMap(previous);
    }
}
```

This is illustrative code. It restores the entire context to its state before entering the scope, including framework and tracing keys. One important design note: if a framework **intentionally updates the parent context while the child scope is running**, restoring the snapshot can overwrite that update. Therefore, you need clear rules for **who owns each key and the lifecycle of each scope**.

### Does `MDC.putCloseable` Replace All Restore Patterns?

SLF4J provides `MDC.putCloseable`:

```java
try (MDC.MDCCloseable ignored =
        MDC.putCloseable("request_id", requestId)) {
    doWork();
}
```

This is an illustrative snippet requiring `requestId` and `doWork()`. After `try-with-resources`, the closeable removes the key that was set. **Do not rely on it as a guarantee that previous values are automatically restored in every nested override case.** If a parent scope's `request_id` may already exist, snapshot/restore or a scope abstraction that explicitly tracks the previous value is easier to reason about and verify.

## 6. Runnable Java 17 + Maven Example: Reading a Key, Reading a Snapshot, Passing Across an Executor, and Restoring

The following hands-on example uses **SLF4J + Logback** to demonstrate both sides:

- `MDC.get` / `getCopyOfContextMap` are read **by Java code**.
- `%X{request_id}` is read **by the layout** and printed to the console.
- A worker thread does not automatically inherit the submitting thread's MDC.
- Explicitly passing a snapshot through the executor lets the worker read the right values.
- Upon completion, the context is restored so data does not leak.

To keep the output deterministic and verifiable, we use a single worker thread, wait on `Future.get()`, and omit timestamps and dynamic thread names.

### 6.4. `src/main/java/demo/MdcReadDemo.java`

```java
package demo;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class MdcReadDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(MdcReadDemo.class);

    private MdcReadDemo() {
    }

    private static String display(String value) {
        return value == null ? "<null>" : value;
    }

    private static void restore(Map<String, String> oldContext) {
        if (oldContext == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(oldContext);
        }
    }

    private static Runnable withContext(Runnable action) {
        Map<String, String> captured =
                MDC.getCopyOfContextMap();

        return () -> {
            Map<String, String> workerBefore =
                    MDC.getCopyOfContextMap();

            try {
                restore(captured);
                action.run();
            } finally {
                restore(workerBefore);
            }
        };
    }

    public static void main(String[] args) throws Exception {
        Map<String, String> mainBefore =
                MDC.getCopyOfContextMap();

        ExecutorService pool =
                Executors.newSingleThreadExecutor();

        try {
            System.out.println("read.before="
                    + display(MDC.get("request_id")));

            MDC.put("request_id", "req-42");
            MDC.put("tenant_id", "tenant-7");

            System.out.println("read.request_id="
                    + display(MDC.get("request_id")));
            System.out.println("read.missing="
                    + display(MDC.get("missing")));

            LOG.info("event=request.started");

            Map<String, String> snapshot =
                    MDC.getCopyOfContextMap();

            System.out.println("read.snapshot.request_id="
                    + snapshot.get("request_id"));

            MDC.put("request_id", "req-43");
            System.out.println("read.current_after_change="
                    + display(MDC.get("request_id")));
            System.out.println("read.snapshot_unchanged="
                    + snapshot.get("request_id"));

            MDC.put("request_id", "req-42");

            Future<?> noPropagation = pool.submit(() ->
                    LOG.info("event=worker.without_context"));
            noPropagation.get();

            Future<?> withPropagation = pool.submit(
                    withContext(() ->
                            LOG.info("event=worker.with_context")));
            withPropagation.get();

            LOG.info("event=request.completed");
        } finally {
            restore(mainBefore);
            pool.shutdown();
        }

        System.out.println("read.after="
                + display(MDC.get("request_id")));
        LOG.info("event=outside.request");
        System.out.println("PASS mdc_read_and_restore");
    }
}
```

From the `mdc-read-demo` directory:


### 6.6. Why Each Line Is Correct

1. `read.before=<null>`: before setting the key, `MDC.get("request_id")` has no value; the `display` helper prints `<null>` instead of Java `null`.
2. `read.request_id=req-42`: directly reads the key just set on the main thread.
3. `read.missing=<null>`: the key `missing` has never been set in this scope.
4. `event=request.started`: the Logback layout reads both `request_id` and `tenant_id` via the two `%X` converters.
5. `read.snapshot.request_id=req-42`: the snapshot was captured right after the starting log record.
6. After `MDC.put("request_id","req-43")`, `MDC.get` sees `req-43`, while the old snapshot still holds `req-42`.
7. The code restores `req-42` before submitting the tasks.
8. `worker.without_context` runs on a new worker thread, which does not automatically inherit the main thread's MDC in this sample Logback setup, so both fields are empty.
9. `withContext` captures a snapshot when creating the `Runnable` on the main thread and applies it on the worker during `action.run()`; therefore, the second worker event reads both fields correctly.
10. The wrapper's `finally` block restores the worker's previous context, preventing stale IDs when the thread is reused.
11. `Future.get()` waits for each task to finish before moving on, so the log order in the example is deterministic.
12. `restore(mainBefore)` returns the main thread to its initial context; `read.after=<null>` and the `outside.request` event prove the demo scope leaves no leftover IDs.
13. The `PASS mdc_read_and_restore` line is only an indicator that the program path completed. For more accurate **automated assertions**, add tests that inspect each event and output as shown in the testing section below.

**Important:** this example does not prove that every framework, every SLF4J provider, and every executor has the exact same inheritance behavior as Logback here. Always test against your actual backend when switching.

## 7. Reading MDC in Layouts: How `%X{key}` Differs from `MDC.get(key)`

The two ways of reading serve two different purposes:

```java
String requestId = MDC.get("request_id");
```

reads for **executing Java code**.

In `logback.xml`:

```xml
<pattern>%d{HH:mm:ss.SSS} %-5level rid=%X{request_id} %logger - %msg%n</pattern>
```

tells the **layout** to take `request_id` from the logging event's context to print into text.

Keep them clearly separated:

| Action | Consumer Receiving the Value | When Is It Meaningful? |
| --- | --- | --- |
| `MDC.get("request_id")` | Java code | When code needs to log or inspect the current context. |
| `MDC.getCopyOfContextMap()` | Java code | When a context snapshot is needed or multiple keys must be checked. |
| `%X{request_id}` | Logback/Log4j 2 layout | When the encoder formats text from a pattern based on the context attached to the event. |
| JSON MDC provider | JSON encoder | When a separate `request_id` field is needed for searching in a collector. |
| `ILoggingEvent.getMDCPropertyMap()` | Logback test/integration code | When inspecting the context that actually entered the **event**. |

### Setting MDC Alone Does Not Mean the Console Will Display It

Suppose code calls:

```java
MDC.put("request_id", "req-42");
LOG.info("event=order.created");
```

but the pattern is:

```xml
<pattern>%level|%msg%n</pattern>
```

then the text output will not include the request ID, because the layout **only prints the level and message**. To display it, use the `%X{request_id}` converter or configure a JSON encoder to emit MDC.

This is a common mistake: a developer checks `MDC.get`, sees the right value, and concludes the collector must have the field. **That is not enough**: you must verify the encoder, appender, and collector.

### Converters with Absent Values

In Logback, `%X{request_id}` produces an empty string if no matching entry exists in the sample pattern. Some backends/converters support fallback or default syntax, but syntax and semantics vary by library and version.

Do not copy a fallback pattern from Log4j 2 into Logback without testing it. If the system genuinely needs a meaningful default value, define it at the event boundary or choose a converter appropriate for your backend.

### When Does `AsyncAppender` Read MDC?

A backend may process events on a different thread when using async logging. In Logback, events have their MDC data prepared/captured for deferred appender processing as needed. Do not assume the layout always calls `MDC.get` again on the business thread at the exact moment bytes are written.

What you should verify is the **MDC map inside the logging event** and the actual output, especially when code clears the context right after the logger call. A properly configured async pipeline can still emit the event's request ID even if the final processing thread does not hold the request's MDC.

## 8. Reading MDC in Log4j 2: `ThreadContext.get`

Log4j 2 provides `org.apache.logging.log4j.ThreadContext` to manage its diagnostic context map. It serves a similar purpose but is **not the same class** as SLF4J `MDC`.

Example:

```java
import org.apache.logging.log4j.ThreadContext;

ThreadContext.put("request_id", "req-42");
try {
    String requestId = ThreadContext.get("request_id");
    log.info("event=request.received");
} finally {
    ThreadContext.remove("request_id");
}
```

This is an illustrative snippet in a method that already has `log`. With the Log4j 2 API, you can read the entire context using a map API such as `ThreadContext.getImmutableContext()`, which returns a view/map that should not be modified directly; if you need an independent snapshot, make a copy with `new HashMap<>(...)`.

Example:

```java
Map<String, String> snapshot =
        new java.util.HashMap<>(ThreadContext.getImmutableContext());

String requestId = snapshot.get("request_id");
```

This snippet assumes `java.util.Map` is already imported. The map getter name differs from SLF4J's `MDC.getCopyOfContextMap()`; **do not treat the two APIs as syntax-interchangeable**.

A Log4j 2 pattern might look like:

```xml
<PatternLayout
    pattern="%level|rid=%X{request_id}|%c{1}|%m%n"
    charset="UTF-8" />
```

This XML snippet belongs inside an appropriate appender in `log4j2.xml`, not in a Logback configuration.

### Using the SLF4J API with a Log4j 2 Backend

When SLF4J 2.x is wired to Log4j 2 via a compatible provider, how `MDC` maps to the backend context depends on the active adapter/provider. Standardize on **the API that application code uses**, and avoid calling `MDC.put` and `ThreadContext.put` side by side for the same field without knowing whether they share the same underlying data.

A proper test in this architecture includes: calling the application API, checking `MDC.get` if that is part of the contract, inspecting the backend event, and confirming the `request_id` field in the final output. Do not infer from JAR names alone that all adapter classes behave identically.

### Does JUL Have a Standard MDC?

The JDK's `java.util.logging` has `Logger`, `LogRecord`, `Handler`, and `Formatter`, but it has no standard MDC API equivalent to `org.slf4j.MDC`. If an application uses only JUL, you must choose an appropriate correlation mechanism (passing IDs explicitly, wrappers, filters/formatters, or bridges) and test it. **Do not call `MDC.get` and assume JUL automatically understands this context** unless a compatible bridge/backend is in place.

## 9. Reading MDC Across Thread and Async Boundaries

The MDC values of a request-receiving thread are **not automatically** available on every other thread. This is the number-one reason behind debugging "`MDC.get("request_id")` returns null inside an executor."

### Misguided Expectation Example

```java
MDC.put("request_id", "req-42");

executor.submit(() -> {
    String id = MDC.get("request_id");
    log.info("event=background.started request_id={}", id);
});
```

This is an illustrative code snippet. The task may run on a worker thread that does not carry the submitting thread's MDC. It may return `null`, or read **a stale context left on the worker** if an earlier task failed to clean up.

### Propagation Principles

1. Read `MDC.getCopyOfContextMap()` on the **thread creating/submitting the task**.
2. Attach the snapshot to the `Runnable`/`Callable` or use your framework's context propagation mechanism.
3. On the worker thread, save any existing context.
4. Apply the request snapshot for the duration of task execution.
5. Run the logic and emit logs.
6. Restore the previous context in `finally`, even on failure.
7. Test that worker threads are reused cleanly between request A and request B.

The complete runnable example in Section 6 implements these steps for a `Runnable`. In real systems, there are also `Callable`s, callbacks, `CompletableFuture`s, cancellations, nested tasks, and framework-specific constructs. **Do not assume a single wrapper covers every async boundary.**

### Does `InheritableThreadLocal` Solve This?

Not completely. Worker pools are usually created before requests arrive and are reused across many requests. "Inheriting when a child thread is created" is not the same as "receiving context when a task is submitted." Those are two different points in time.

Logback should not be assumed to automatically inherit all MDC from a parent thread to pooled worker threads. Verify according to your actual backend and thread-creation model.

### Reactive and Tracing Instrumentation

In Reactor/WebFlux or reactive frameworks, callbacks can hop across multiple threads. Calling `MDC.get` directly in a callback may not return the incoming request's values unless context propagation is integrated. Use the framework's context mechanism and an MDC bridge supported by the framework or tracing SDK.

With OpenTelemetry or similar tracing systems, `trace_id` may come from the **span context**. If the application uses a standard tracing SDK, prefer obtaining IDs from the trusted tracing source and letting instrumentation populate the log context rather than manually setting non-standard `trace_id` values.

## 10. Reading MDC in HTTP Filters and Message Consumers

### HTTP Requests

A common pattern is to set `request_id` at the start of the request lifecycle:

```java
String requestId = chooseTrustedRequestId(request);
Map<String, String> before = MDC.getCopyOfContextMap();

try {
    MDC.put("request_id", requestId);
    service.handle(request);
} finally {
    if (before == null) MDC.clear();
    else MDC.setContextMap(before);
}
```

This is a **snippet** inside a framework where the corresponding variables/methods exist, not a standalone program. `chooseTrustedRequestId` represents policy-compliant ID validation/generation; never use an unvalidated header value verbatim.

When service code calls `MDC.get("request_id")`, it reads the context set by the filter. However, async dispatch, callbacks, or requests leaving the initial thread may require additional lifecycle/propagation hooks.

**Where should the request ID come from?** The rule should be defined by the gateway/framework. If you accept a header such as `X-Request-ID`, enforce length and character limits, never trust the header for authorization, reject IDs containing newlines or secrets, and agree on when to generate a fresh ID.

### Message Consumers

Message queues often carry a `message_id` or `correlation_id`. Handling a single message might look like:

```java
String messageId = metadata.messageId();
MDC.put("message_id", messageId);

try {
    String current = MDC.get("message_id");
    consumer.handle(message);
} finally {
    MDC.remove("message_id");
}
```

This is a snippet using the application's `metadata`, `consumer`, and `message`. If the consumer runs in a nested scope or the framework already populates MDC, snapshot/restore of the full context is safer than a plain `remove`.

**Do not treat `MDC.get("request_id")` as mandatory in every background job.** A scheduled task may not have an HTTP request, yet have a useful `job_run_id`. Choose keys that fit the type of work.

## 11. Reading MDC and Structured JSON Logging

A text log line might look like:

```text
INFO rid=req-42 event=order.created order_id=O-17
```

To query `request_id` as a separate field, you need an appropriate JSON encoder configured to include MDC. Example target output schema:

```json
{
  "timestamp": "2026-01-01T10:15:30Z",
  "level": "INFO",
  "service": "checkout",
  "event_code": "order.created",
  "request_id": "req-42",
  "order_id": "O-17",
  "message": "Đã tạo đơn"
}
```

This is only an **example of structured output**, not the default output from `PatternLayoutEncoder`.

Distinguish these three places where data lives:

| Data | Where Should It Come From? | Why? |
| --- | --- | --- |
| `request_id` | MDC / request context | Shared across many events in a request. |
| `trace_id` | Tracing context or synchronized MDC | Used for trace correlation. |
| `event_code` | Per-event key-value | The event type changes on each log call. |
| `order_id` | Event field or intentional narrow scope | Not every event in a request pertains to the same order. |
| `service`, `environment` | Deployment/encoder configuration | Relatively constant across the process. |
| `duration_ms` | Numeric event field | Needs to stay numeric for queries and aggregations. |

An SLF4J 2.x call:

```java
log.atInfo()
        .addKeyValue("event_code", "order.created")
        .addKeyValue("order_id", orderId)
        .log("Đã tạo đơn");
```

does not automatically put `event_code` into MDC. They are two separate data streams: **event key-values** and the **context map**. An encoder can output both if configured to do so.

**MDC stores String values**, so if you call `MDC.put("attempt", "3")`, an encoder may emit it as a **JSON string** rather than automatically converting it to an integer. For retry counts or durations, prefer typed logging event fields if your encoder supports them.

### Why Does `MDC.get` Succeed While JSON Is Missing the Field?

Possible reasons:

- The encoder does not output MDC by default, or the MDC provider is disabled.
- An encoder field filter allows only specific keys.
- The key name in MDC does not match the output schema.
- The event was created before MDC was set or after cleanup already ran.
- Async propagation did not carry the key to the thread creating the event.
- The collector fails to parse JSON properly or drops/remaps the field type.
- The runtime is loading a different backend or configuration than expected.

Inspect the pipeline end-to-end: **current MDC → event → encoder → byte output → collector/index**.

## 12. Testing `MDC.get` and Context Maps

A proper test should verify both **the value at read time** and **that data does not leak into other scopes**.

### Direct Assertions

In a unit test with an MDC-supporting backend:

```java
Map<String, String> before = MDC.getCopyOfContextMap();

try {
    MDC.put("request_id", "req-42");

    String requestId = MDC.get("request_id");
    if (!"req-42".equals(requestId)) {
        throw new AssertionError("wrong MDC request_id");
    }

    Map<String, String> copy = MDC.getCopyOfContextMap();
    if (copy == null
            || !"req-42".equals(copy.get("request_id"))) {
        throw new AssertionError("wrong MDC snapshot");
    }
} finally {
    if (before == null) MDC.clear();
    else MDC.setContextMap(before);
}
```

This is a code snippet inside a test method where `MDC` and `java.util.Map` are available. It checks the key and snapshot on the **same thread**; it does not yet prove that the final log output contains the context.

### Testing Snapshot Immutability

Steps:

1. `MDC.put("request_id", "req-A")`.
2. `Map snapshot = MDC.getCopyOfContextMap()`.
3. `MDC.put("request_id", "req-B")`.
4. Assert `MDC.get(...)` is `req-B`.
5. Assert `snapshot.get(...)` is still `req-A`.
6. Restore the pre-test context.

This is a core test for any code that relies on snapshots when submitting async tasks.

### Testing Nested Scopes

Open a parent scope with `request_id=req-parent`, enter a child scope that sets `req-child`, and then exit the child scope. Assert that the parent reads `req-parent` again. Also test the path where the child throws an exception; restoration must happen in `finally`.

### Testing Thread Pools

Use `Executors.newSingleThreadExecutor()` to force **reuse of a single worker thread**:

- Task A has context A.
- Task B has context B.
- Task C has no context.
- After each task, the worker must not retain the previous task's ID.

Test both succeeding tasks and tasks that throw exceptions. If using a propagation wrapper or SDK, assert the context at the **point where the log is emitted** inside the worker, not just on the submitting thread.

### Testing the Logging Event, Not Just Current MDC

With Logback Classic, you can attach a `ListAppender<ILoggingEvent>` to the test logger and inspect:

```java
event.getMDCPropertyMap().get("request_id")
```

This is a snippet: `event` must be an `ILoggingEvent` captured in a test where Logback and the appropriate appender have been initialized. The result reflects the context that traveled with the **event**, rather than calling `MDC.get` again on the test thread afterward.

You can also check `getLevel()`, `getFormattedMessage()`, and `getThrowableProxy()`. After the test, detach/stop the temporary appender and restore logger configuration to avoid affecting tests running in parallel.

### Testing Actual Output and the Collector

Once event tests pass:

1. Use the real encoder/layout to format the event.
2. Check `%X{request_id}` in text or the `request_id` JSON field.
3. Verify UTF-8, quotes, newlines, missing data, and schema fallbacks.
4. Send two requests with distinct IDs through a real server or consumer.
5. Confirm the centralized log store does not mix up IDs between requests.
6. Confirm events outside requests do not carry stale values.
7. Verify sensitive data is not accidentally emitted in any channel.

**Do not treat `MDC.get` returning the right value in a unit test as proof that the collector received the log.** You can only conclude that after verifying the full export and ingestion path.

## 13. Security When Reading and Emitting MDC Values

Context keys can hold user/tenant identifiers, routes, or header-derived data. Risks include:

- `MDC.get("tenant_id")` returning an unverified ID from a client header.
- `request_id` containing newlines or control characters, causing **log injection**.
- `MDC.getCopyOfContextMap()` being logged verbatim and exposing the entire context.
- `MDC` storing tokens, cookies, `Authorization` headers, or personal data.
- Context lingering on a worker thread and getting attached to another request.
- A JSON encoder emitting more fields than operators intended.
- A collector allowing unauthorized users to search logs by sensitive IDs.

**Do not use MDC as a source of truth for authorization.** Checking access permissions based on `MDC.get("tenant_id")` is the wrong model if MDC can be missing or originate from an untrusted source. Security decisions must rely on an authenticated security context; MDC is strictly observability data and should be populated from trusted sources when logging.

### Validating Values Before Putting Them into MDC

A simple request ID contract might be:

- 1–64 characters long.
- Only letters, digits, dots, underscores, and hyphens.
- No newlines, tabs, control characters, or secrets.
- If the header is missing or invalid, generate a new ID per policy.

Example validation helper:

```java
static boolean validRequestId(String value) {
    return value != null
            && value.length() >= 1
            && value.length() <= 64
            && value.matches("[A-Za-z0-9._-]+");
}
```

This is an illustrative helper inside a Java class. It is **not** a W3C trace ID validator; standard trace IDs should be handled by tracing instrumentation. Likewise, having a syntactically valid field **does not prove** it is trustworthy for authenticating a caller.

### Does Reading and Logging Again Create Duplicate Logs?

When code does:

```java
String id = MDC.get("request_id");
log.info("request_id={}", id);
```

you have **embedded the context into the message**. If the layout also uses `%X{request_id}`, a single line may contain the ID twice:

```text
INFO rid=req-42 request_id=req-42
```

This is not strictly wrong, but it bloats logs, increases volume, and can confuse parsers. If the goal is simply to attach the ID to every event, **setting MDC once and letting the layout/encoder read it** is usually cleaner than manually adding the ID to every message.

## 14. Performance and Usage Conventions

`MDC.get("key")` is a small operation, but that does not mean you can call it indiscriminately on hot paths without measuring. The overall cost of logging also includes formatting, JSON serialization, I/O, queuing, and collection.

Useful rules of thumb:

1. Set `request_id` once at the request boundary; do not generate a new ID per log message.
2. Use stable key names; avoid per-request key names like `"request_" + id` that grow the map unboundedly.
3. Keep context small and free of large objects; SLF4J MDC stores string values.
4. Only call `getCopyOfContextMap()` when you actually need a full snapshot; for a single key, `MDC.get` is clearer.
5. Avoid printing the entire snapshot on every log line.
6. If using propagation wrappers, weigh the cost of map copying across millions of tiny tasks.
7. Do not treat `MDC.get` as a cross-thread state-sharing mechanism; choose proper data-passing APIs for business logic.
8. Do not use `request_id` as a high-cardinality metric label; look up IDs in logs/traces and group metrics by stable service/event/error codes.
9. Check when MDC is captured when using async appenders or backends.
10. When propagating context over the network, transmit only allowed fields and enforce header/metadata size limits.

**MDC is neither durable nor historical.** When the process exits, in-memory context disappears; calling `MDC.get` cannot retrieve yesterday's request ID. To search past logs, use a log/trace store with appropriate retention and access controls.

## 15. Troubleshooting Table for Reading MDC

| Symptom | Common Cause | How to Check |
| --- | --- | --- |
| `MDC.get("request_id") == null` | Key not set, already removed, or outside request scope | Identify where it is set, its scope, and its lifecycle. |
| `MDC.get("requestId")` returns null even though logs show `request_id` | Wrong key name or casing | Standardize exact key names. |
| `getCopyOfContextMap()` returns null | No map/context at call time, depending on adapter | Check for null before reading; verify provider. |
| Snapshot retains old ID after a new `MDC.put` | Snapshot is a copy, not a live view | Take a fresh snapshot if you actually need the current map. |
| Worker thread does not see the ID | Missing context propagation | Snapshot at submit time, apply and restore in the worker. |
| Worker B reads task A's ID | Forgot to clean up/restore in thread pool | Use `finally`; test worker reuse. |
| Parent scope loses ID after child scope | Child called `MDC.remove` or `clear` without restoring | Use snapshot/restore or scoped ownership. |
| `%X{request_id}` is empty in logs | Event has no MDC, wrong pattern, or different backend | Check the event map, converter, and runtime config. |
| `MDC.get` works but JSON is missing the field | Encoder does not emit MDC or collector drops the field | Check encoder/JSON mapping and ingestion. |
| Async event is missing ID after cleanup | Context was not captured properly at event creation | Check async appender/deferred processing. |
| `MDC.get` is always null right after `put` | Provider/adapter does not support it or wrong logging runtime | Check SLF4J provider/backend and startup warnings. |
| JUL logs work but `MDC.get` has no effect | JUL has no standard MDC and lacks a bridge/integration | Design appropriate context/handler integration. |
| ID appears in message but cannot be queried as a field | Context was concatenated into text instead of emitted as a JSON field | Use a structured encoder or a tested parser. |
| Output shows another request's ID | Thread reuse, misplaced context, or buggy HTTP filter lifecycle | Test interleaved requests, cleanup, and cancellation. |
| Text contains forged multi-line entries | Unvalidated ID contains newlines | Enforce length/charset limits; encode/escape properly. |
| Same ID appears twice on one line | Both `%X` is printed and ID is manually added to `%msg` | Pick one place to display it or accept intentionally. |
| No logs appear even though MDC is right | Logger level, filter, appender, or collector | Diagnose the event-to-output path, not just MDC. |

### Verification Flow from Source Code to Log Store

```text
Did MDC.put(key,value) run in the scope?
   |
   +-- No --> Check filter/interceptor/job wrapper.
   |
   +-- Yes --> Is MDC.get(key) in the same thread/scope correct?
                |
                +-- No --> Wrong key, premature cleanup, or adapter.
                |
                +-- Yes --> Was there a thread/process switch?
                             |
                             +-- Yes --> Check propagation and trust boundary.
                             |
                             v
                         Does the logging event have the right MDC map?
                             |
                             +-- No --> Check capture/async/backend.
                             |
                             v
                         Does the layout/encoder output the key?
                             |
                             +-- No --> %X / JSON MDC provider / config.
                             |
                             v
                         Does the collector parse and keep the field?
                             |
                             +-- No --> Check ingest/filter/mapping.
                             |
                             v
                         Are you querying the right service, time, and permissions?
```

Do not debug missing MDC by scattering `System.out.println(MDC.getCopyOfContextMap())` everywhere. That risks leaking data and alters log volume. Prefer small tests with dummy IDs and trace the pipeline layer by layer.

## 16. Self-Check Exercises

### Exercise 1 — Reading an Existing Key

Given:

```java
MDC.put("request_id", "req-91");
String a = MDC.get("request_id");
String b = MDC.get("requestId");
```

Determine `a` and `b` in a compatible MDC backend when `requestId` was not previously set.

**Answer:** `a` is `"req-91"`. `b` is `null` because the two keys are different. Not because `get` failed, but because key names are case-sensitive.

### Exercise 2 — Reading After Cleanup

Given:

```java
MDC.put("request_id", "req-A");
MDC.remove("request_id");
String result = MDC.get("request_id");
```

**Answer:** `result` is `null` in this scope. If request code needs the ID after cleanup, it must hold it in an appropriate business variable or parameter rather than expecting MDC to retain it forever.

### Exercise 3 — Snapshot vs. Current Value

```java
MDC.put("request_id", "A");
Map<String, String> copy = MDC.getCopyOfContextMap();
MDC.put("request_id", "B");
```

What do `copy.get("request_id")` and `MDC.get("request_id")` return?

**Answer:** `copy` holds `"A"`, while `MDC.get` returns `"B"`. A snapshot is a copy taken at the moment of the call.

### Exercise 4 — Choosing How to Read When Data May Be Missing

An application has both HTTP requests and scheduled jobs; `MDC.get("request_id")` sometimes returns null. Are all of these bugs?

**Answer:** No. A job may not have an HTTP request. Treat it as a bug only when **that specific context's contract** requires the field to be present. For jobs, `job_run_id` may be more appropriate.

### Exercise 5 — Reading Across an Executor

The main thread sets `request_id=req-A`. A task on a thread pool calls `MDC.get("request_id")` and gets null. Why, and how do you fix it?

**Answer:** MDC does not automatically propagate safely to worker pools. Capture the context on the submitting thread, apply it on the worker before running the task, and restore the previous context in `finally`; or use an official framework propagation mechanism.

### Exercise 6 — Nested Scopes

A parent scope has `request_id=req-parent`. A child scope sets `req-child` and then calls `MDC.remove("request_id")`. What goes wrong?

**Answer:** The parent's value is lost. If scopes can nest, save the previous value/map and restore it rather than blindly calling remove.

### Exercise 7 — Logs Have MDC, but Text Output Shows Nothing

A developer set `MDC.put("request_id", "req-42")`; `MDC.get` returns the right value. Yet the pattern is just `%level %msg%n`. Why is the ID missing from the console?

**Answer:** The pattern has no converter that reads MDC. Add `%X{request_id}` or configure a structured encoder to emit MDC, then verify both the logging event and actual output.

### Exercise 8 — What Type Does JSON Preserve?

`MDC.put("attempt", "3")` is called and a JSON encoder emits MDC. Does `attempt` automatically become a JSON number?

**Answer:** Do not assume so. MDC stores strings; an encoder may output `"attempt":"3"`. If consumers need a number, pass a typed field on the event via an appropriate API/encoder or a controlled mapping.

### Exercise 9 — Distinguishing Diagnostic Data from Security Data

An application reads `tenant_id` from MDC to authorize a user to view that tenant's orders. Is this safe?

**Answer:** Never use MDC as an authorization source. The allowed tenant must come from an authenticated security context and permission checks. MDC should only reflect a trusted ID for logging, and that data still needs to be protected.

### Exercise 10 — Verifying Reads Without Context Leakage

Write a test that runs two tasks A and B on the same worker thread, followed by an out-of-request task. What is the expected behavior?

**Answer:** Task A reads A, task B reads B, and the out-of-request task reads neither A nor B. The wrapper must capture/restore for each task; test the case where a task throws an exception as well.

### Exercise 11 — MDC and Throwable

An error is logged with `log.error("failed", ex)` and the event has `request_id`. If the console does not show the request ID, can you conclude that `MDC.get` returned null?

**Answer:** Not yet. You must check the event's MDC map and whether the pattern/encoder outputs the field. Printing a `Throwable` does not imply an MDC converter is configured.

### Exercise 12 — Reading Context Outside Request Scope

An application logs during startup, on request threads, and in a shutdown hook. Where can `request_id` be relied upon?

**Answer:** When a valid request scope has been established and propagated properly. Startup and shutdown typically have no request ID; use service/environment, operation, or job metadata instead. Do not fabricate a generic fake request ID for all events.

## 17. Checklist for Applying MDC in a Java Project

- [ ] Know the active backend/provider and its corresponding MDC API.
- [ ] Standardize key names; `request_id` is different from `requestId`.
- [ ] Handle `MDC.get(key)` as `String | null`, without blind casting.
- [ ] Define rules for absent keys, empty strings, and display fallbacks.
- [ ] Use MDC strictly for logging context, never as an authorization source.
- [ ] Set context at the proper request/job/message boundaries.
- [ ] For nested scopes, snapshot and restore the parent context in `finally`.
- [ ] Test two consecutive requests on a single reused worker thread.
- [ ] Ensure async/executor/reactive flows have proper propagation and cleanup.
- [ ] Use `getCopyOfContextMap` when a snapshot is genuinely needed; check for null.
- [ ] Understand that a snapshot does not update on subsequent `MDC.put` calls.
- [ ] Include `%X{key}` in the layout if text output should display MDC.
- [ ] Configure the JSON encoder with the right MDC provider/field mapping for structured logging.
- [ ] Test logging event maps separately from output/collector tests.
- [ ] Do not log the entire context map or headers containing secrets.
- [ ] Validate client-supplied IDs; block newlines and log injection.
- [ ] Do not attach dynamic request IDs to high-cardinality metric labels.
- [ ] Ensure events after cleanup do not carry IDs from previous requests.
- [ ] Do not expect MDC to retain history after a request or process ends.

**Conclusion:** `MDC.get(key)` reads **a single string value from the current context**, `MDC.getCopyOfContextMap()` provides a **snapshot** for inspection or passing to another task, and `%X{key}` / a JSON encoder determines **whether that value is emitted in the logs**. Using it correctly requires handling `null`, naming keys consistently, understanding thread boundaries, restoring context when a scope ends, and testing both events and actual output.
