# MDC in Async Java Logging: Propagating Context Correctly Across Thread Switches

## 1. What Is MDC and Why Does Async Cause Confusion?

**MDC (Mapped Diagnostic Context)** is a mechanism for attaching key–value pairs to the logging context of the execution thread, so that multiple log events from the same request, job, or operation carry correlation fields without manually concatenating IDs into every message.

For example, a checkout request:

```text
INFO  req=req-42 op=op-17 - event=checkout_started
INFO  req=req-42 op=op-17 - event=payment_authorized
WARN  req=req-42 op=op-17 - event=inventory_retry attempt=2
INFO  req=req-42 op=op-17 - event=checkout_finished
```

Here, `req-42` and `op-17` are **request/operation context**, not fixed properties of the logger. Without correlation IDs, log lines from hundreds of concurrent requests are very difficult to link together.

An SLF4J example:

```java
import org.slf4j.MDC;

// Snippet inside a method where LOG is org.slf4j.Logger:
MDC.put("requestId", "req-42");
try {
    LOG.info("event=checkout_started");
    LOG.info("event=checkout_finished");
} finally {
    MDC.remove("requestId");
}
```

The snippet above is **not yet a standalone Java program**; it assumes an existing logger `LOG`. `MDC.put` typically stores the value in a context bound to the current thread, while the encoder/layout decides whether `requestId` is rendered.

When a program uses asynchronous processing, two different questions must be answered:

1. **Logs are written to the destination on another thread** because of an AsyncAppender/AsyncLogger: is the event's MDC still accurate?
2. **Business logic executes on another thread** because of an `ExecutorService`, `CompletableFuture`, scheduler, callback, reactive pipeline, or message consumer: where does the new thread get its MDC from?

These two situations are **not equivalent**. Clearly understanding the boundary between *emitting a log event* and *handing off business work* is the key to avoiding lost or mixed-up MDC.

## 2. Two Kinds of Async You Must Distinguish

### 2.1. Async logging: offloading log output to a worker

With Logback `AsyncAppender`, the request thread creates the event and puts it onto a queue; the appender thread handles writing to the console/file afterward:

```text
REQUEST THREAD                         LOGGING WORKER
  |
  | MDC: requestId=req-42
  |      operationId=op-17
  |
  +-- LOG.info("event=started")
        |
        +-- Create logging event
        +-- Prepare data for deferred processing
        +-- Snapshot required MDC
        +-- Enqueue ----------------------> Dequeue event
                                            |
                                            +-- Encoder reads MDC
                                            |   attached to event
                                            +-- Write to console/file
  |
  +-- MDC.clear() in finally
```

In Logback Classic, `AsyncAppender` prepares the `ILoggingEvent` for deferred processing, in which the event's MDC data is captured in the log-emitting context before the worker writes it. Therefore, **the caller clearing MDC after the logging call does not necessarily lose the MDC of an already-enqueued event**.

This is the behavior of the Logback mechanism under discussion. **Do not generalize that every custom appender, hand-written formatter, or other backend automatically snapshots MDC identically.** If you build a custom appender, you must check the event's API/contract and when the context is captured.

### 2.2. Async business work: handing off work to another thread

With `ExecutorService`:

```text
REQUEST THREAD                         BUSINESS WORKER
  |
  | MDC requestId=req-42
  |
  +-- executor.submit(task) -----------> run task
                                           |
                                           | MDC.get("requestId") ?
                                           | Not = req-42 by default
                                           |
                                           +-- LOG.info("event=worker_done")
```

`MDC` relies on a context adapter typically bound to the thread, so **a task running on another thread does not automatically receive the caller's snapshot**. If the worker uses a thread pool, it may have:

- An empty MDC.
- Leftover MDC from a previous task that was cleaned up improperly.
- MDC actively set by a framework or another library.
- MDC properly propagated by middleware/context propagation integration configured by the application.

Consequently, async business work requires a **capture → install → execute → restore** rule at the task boundary, or official framework propagation integration.

### 2.3. Both kinds of async can appear together

```text
HTTP request thread
  | MDC=req-42
  |
  +-- submit business task ------------------------+
                                                   |
                                                   v
                                              Worker thread
                                              MDC=? if not propagated
                                                   |
                                                   +-- LOG.info(...)
                                                          |
                                                          v
                                              AsyncAppender queue
                                                          |
                                                          v
                                              Logging worker -> file
```

Even when `AsyncAppender` preserves the **event's MDC on the worker**, that event can still contain **an empty MDC from the moment it was emitted** if the business worker was never given the context. The backend cannot recover a `requestId` that was never attached to the event.

**Rule of thumb:** AsyncAppender preserves *event context* according to its mechanism; context propagation must deliver *execution context* to the exact place where the event is created.

## 3. What Makes Up the MDC Context

A log record may need:

| Field | Meaning | Example |
|---|---|---|
| `requestId` | Correlates logs within a single request | `req-42` |
| `operationId` | Correlates events of a business operation | `op-17` |
| `parentOperationId` | Parent–child relationship of operations | `op-16` |
| `jobId` | Background job identifier | `job-104` |
| `traceId` | Distributed trace identifier | Value provided by the tracing SDK |
| `spanId` | Span identifier within a trace | Value provided by the tracing SDK |
| `tenantId` | Tenant being processed, when logging it is permitted | `tenant-A` |
| `attempt` | Retry attempt number | `2` |

**Not every field belongs in MDC.** Traditional MDC is typically a **`String → String`** map; complex or numeric values need to be represented under a consistent convention. With JSON structured logging, an encoder can add more strongly typed fields from the API/event model.

- `requestId` is not necessarily `traceId`.
- `operationId` is not necessarily `spanId`.
- One request can spawn multiple operations.
- An operation may not originate from an HTTP request (batch, cron, queue).
- MDC values may be copied into the event without becoming JSON fields unless the encoder is configured to output them.

Keep **key names stable** and avoid keys built from dynamic IDs. For example, use `"operationId" → "op-17"`, not a key like `"operation_op-17"`.

## 4. How MDC Works in SLF4J and Logback

With SLF4J:

```java
import org.slf4j.MDC;

MDC.put("requestId", "req-42");

String requestId = MDC.get("requestId");

java.util.Map<String, String> snapshot =
        MDC.getCopyOfContextMap();

MDC.remove("requestId");
MDC.clear();
```

These are **illustrative API calls**. You should not execute all of them in sequence as a production workflow without understanding their effects; `remove` deletes a single key, `clear` wipes the entire MDC of the current thread, and `getCopyOfContextMap` returns a snapshot map or `null` if there is no map.

### 4.1. Context is per-thread data

Many SLF4J MDC adapters use thread-bound data. Events emitted on the same thread see the MDC set at the time of logging, unless the framework/backend handles context differently.

Do not confuse `ThreadLocal` with a global variable. If you use a shared `static Map` for `requestId` and mutate it per request, request A can be tagged with B's ID under concurrency. MDC isolates context per thread or per adapter abstraction, but its lifecycle must still be managed.

### 4.2. Taking a snapshot is not transferring permanent ownership

`MDC.getCopyOfContextMap()` is a key API: it returns a **point-in-time copy of the key/value data**, typically as `Map<String, String>` or `null`. Afterward, you can:

- Pass the snapshot into a task.
- Install it with `MDC.setContextMap(snapshot)` when the task runs.
- Call `MDC.clear()` when the snapshot is null.
- Restore the worker's previous context in `finally`.

A snapshot differs from holding a reference to a mutable map being continuously modified by requests. Even so, if you yourself store the snapshot in a mutable map and keep mutating it, you still risk races in application code; it is best to treat the snapshot as read-only or make a valid immutable copy before passing it along.

### 4.3. The actual runtime provider/backend determines behavior

The `SLF4J API` is a facade. `MDC` goes through the provider/runtime's `MDCAdapter`. When running with Logback Classic, full MDC features are supported; with another backend, a simple/NOP provider, or a specialized bridge, storage and retrieval may differ. Do not conclude "SLF4J has MDC, so every provider and every JSON encoder will definitely output the field."

Check the `slf4j-api` version, provider/backend, layout/encoder, and startup warnings. With SLF4J 2.x, use a 2.x-compatible provider; do not randomly mix in a 1.7 binding.

## 5. What Happens When AsyncAppender Receives an Event with MDC

Logback Classic `AsyncAppender` is responsible for:

1. Receiving the event from the caller if it has passed the logger level/filter.
2. Preparing the data needed for deferred processing.
3. Putting the event into the queue; it may block or drop the event depending on policy.
4. Having the worker take the event and pass it to the target appender.
5. Having the target's encoder/layout read the context attached to the event and write it to the console/file.

Flow example:

```text
Thread A: MDC.put("requestId", "req-42")
Thread A: LOG.info("event=started")
Thread A: MDC.clear()

Logback async worker:
  event.getMDCPropertyMap() -> requestId=req-42 data
  encoder %X{requestId}   -> "req-42"
```

**Note:** this is a logical description of **Logback AsyncAppender/ILoggingEvent**, not a claim that calling `MDC.get("requestId")` directly on the logging worker will return `req-42`. The encoder can read MDC from the **event snapshot**, while the logging worker's actual thread-local MDC still does not carry that ID.

### 5.1. What does snapshotting mean for changes after logging?

```java
// Illustration: LOG is an SLF4J Logger.
MDC.put("requestId", "req-42");
LOG.info("event=first");

MDC.put("requestId", "req-99");
LOG.info("event=second");
MDC.clear();
```

In standard Logback AsyncAppender, events are prepared for deferred processing, so `first` retains the context at the time the first event was emitted, and `second` retains the context at the second; they do not both read `req-99` after the queue drains.

If you design a custom appender that only holds a mutable reference to the context instead of a snapshot, that can be **incorrect**. When writing a custom encoder/appender, test mutating MDC immediately after `LOG.info` to catch bugs.

### 5.2. AsyncAppender does not solve everything

- If business code emits logs from a thread without MDC, the event still lacks IDs.
- If a level/filter already dropped the event, there is no event to snapshot.
- If the queue is full and the policy drops events, the event may be discarded even with complete MDC.
- If the process dies while events are still in the queue, events can be lost.
- If the encoder only prints `%msg` without `%X{requestId}`, the context may exist in the event without being displayed.
- If the collector only parses the message string, MDC may not become structured fields.

**Preserving an event's MDC does not guarantee the event is delivered to the collector.**

## 6. Configuring Logback AsyncAppender and MDC

Example `logback.xml`:

```xml
<configuration>
    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <pattern>%level req=%X{requestId} op=%X{operationId} - %msg%n</pattern>
        </encoder>
    </appender>

    <appender name="ASYNC"
              class="ch.qos.logback.classic.AsyncAppender">
        <queueSize>64</queueSize>
        <discardingThreshold>0</discardingThreshold>
        <neverBlock>false</neverBlock>
        <maxFlushTime>0</maxFlushTime>
        <includeCallerData>false</includeCallerData>
        <appender-ref ref="CONSOLE"/>
    </appender>

    <root level="INFO">
        <appender-ref ref="ASYNC"/>
    </root>
</configuration>
```

This is a **Logback Classic** configuration file, not JUL's `logging.properties` or Log4j 2's `log4j2.xml`.

| Property | Meaning | Relation to MDC |
|---|---|---|
| `queueSize` | Maximum number of events waiting in the queue | A backlog can hold many events with MDC snapshots, increasing memory |
| `discardingThreshold` | Threshold allowing selective discarding of less important log levels when nearly full | Being dropped means losing the entire event, including context |
| `neverBlock` | If true, do not wait when the queue is full; may drop events | Latency vs. log completeness trade-off, not a propagation choice |
| `maxFlushTime` | Time limit to wait for draining the queue on stop, usually in ms | Stopping too early can leave unwritten events; 0 in Logback means wait indefinitely |
| `includeCallerData` | Whether to collect caller class/method/file/line | Caller data is separate from MDC; enabling it can incur stack-lookup cost |
| `appender-ref` | Target appender to which the worker forwards events | Target encoder must be configured to print/export MDC |
| `root level="INFO"` | Filters DEBUG/TRACE below threshold | Level policy does not generate MDC |

In many versions of Logback Classic, the default `discardingThreshold` creates a mechanism that prioritizes WARN/ERROR over TRACE/DEBUG/INFO when nearly full. Setting `0` disables that threshold-based discarding, **but does not guarantee zero log loss due to crashes, sink errors, or other policies**.

With `neverBlock=false`, when the queue is full the caller can block until space becomes available. With `neverBlock=true`, events can be dropped if enqueuing fails, even at high levels when the queue is full. You need to measure p99 latency, queue depth, dropped events, and shutdown policy.

### 6.1. Avoiding duplicate output

If `ASYNC` wraps `CONSOLE`, root **should only attach `ASYNC`** in this simple configuration. If root references both `ASYNC` and `CONSOLE`, an event can travel two paths and be output twice.

### 6.2. Is MDC automatically added to the pattern?

No. The pattern needs `%X{requestId}` or the corresponding syntax, or a JSON encoder configured to export MDC. If you only use:

```xml
<pattern>%level - %msg%n</pattern>
```

the event may still contain MDC internally, but the text output will not show `requestId`. Do not conclude that context was lost before checking the exact encoder/layout.

## 7. Runnable Java 17 + Maven Example: MDC Across Both Async Layers

This example uses **Java 17**, **SLF4J 2.x**, **Logback Classic**, and `ExecutorService`. Goals:

- Set `requestId=req-42`, `operationId=op-17` on the main thread.
- Emit an event so Logback AsyncAppender enqueues it with the current MDC.
- Open a child operation `op-18`, then **restore op-17** after the scope.
- Propagate the MDC snapshot **explicitly** to a business worker in a thread pool.
- Have the business worker emit an event, processed asynchronously by the Logback worker while keeping the right context.
- After the worker task, **prove the worker thread does not leak MDC**.
- Stop `LoggerContext` to drain the queue, then print the worker check result.
- Keep **stdout deterministic for comparison** by waiting for the task to complete and stopping the appender before the final check line.

**This example is for demo/educational purposes only.** In a long-running web application, the framework manages the logging lifecycle; do not stop the logger context after every request.

### 7.4. `src/main/java/com/example/logging/MdcAsyncDemo.java` file

```java
package com.example.logging;

import ch.qos.logback.classic.LoggerContext;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public final class MdcAsyncDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(MdcAsyncDemo.class);

    private static void install(Map<String, String> context) {
        if (context == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }

    /**
     * Scope that installs a new context and restores the previous context on close.
     * Nestable: closing a child scope restores the parent scope's values.
     */
    private static final class MdcScope implements AutoCloseable {
        private final Map<String, String> previous;
        private boolean closed;

        private MdcScope(Map<String, String> next) {
            previous = MDC.getCopyOfContextMap();
            install(next);
        }

        @Override
        public void close() {
            if (closed) {
                return;
            }
            install(previous);
            closed = true;
        }
    }

    /**
     * Captures MDC on the submitting thread, installs it on the task-executing thread,
     * then restores the worker thread's previous context.
     */
    private static Runnable withMdc(
            Map<String, String> captured, Runnable task) {
        return () -> {
            try (MdcScope ignored = new MdcScope(captured)) {
                task.run();
            }
        };
    }

    public static void main(String[] args) throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();
        boolean workerContextClean = false;

        try {
            Map<String, String> root = Map.of(
                    "requestId", "req-42",
                    "operationId", "op-17");

            try (MdcScope rootScope = new MdcScope(root)) {
                LOG.info("event=checkout_started");

                Map<String, String> child = Map.of(
                        "requestId", "req-42",
                        "operationId", "op-18");

                try (MdcScope childScope = new MdcScope(child)) {
                    LOG.info("event=inventory_reserved");
                }

                // Child scope closed: caller is back to op-17.
                Map<String, String> snapshot =
                        MDC.getCopyOfContextMap();

                Future<?> payment = executor.submit(
                        withMdc(snapshot, () ->
                                LOG.info("event=payment_authorized")));
                payment.get();

                LOG.info("event=checkout_finished");
            }

            // Same worker thread is reused, but requestId/operationId
            // are no longer present because the wrapper restored MDC.
            Future<Boolean> noLeak = executor.submit(
                    () -> MDC.get("requestId") == null
                            && MDC.get("operationId") == null);
            workerContextClean = noLeak.get();
        } finally {
            executor.shutdown();

            // Short demo: stop so the appender worker drains the queue before
            // printing the check result line on the same System.out.
            LoggerContext context =
                    (LoggerContext) LoggerFactory.getILoggerFactory();
            context.stop();
        }

        System.out.println(
                "workerContextClean=" + workerContextClean);
    }
}
```

### 7.5. Running

In the `mdc-async-demo` directory containing `pom.xml`, with JDK 17+, Maven, and dependency download access:

```bash
mvn -q compile exec:java
```

**Stdout lines produced by the application code and Logback appender in a normal demo run:**

```text
INFO req=req-42 op=op-17 - event=checkout_started
INFO req=req-42 op=op-18 - event=inventory_reserved
INFO req=req-42 op=op-17 - event=payment_authorized
INFO req=req-42 op=op-17 - event=checkout_finished
workerContextClean=true
```

This is the output of the program and appender, without guaranteeing that Maven will have no messages of its own in every environment. In the demo, the queue has enough capacity, `discardingThreshold=0`, and `neverBlock=false`, so normal events are not dropped by the demonstrated drop policy. Calling `LoggerContext.stop()` gives the worker a chance to flush all events before the final line; if the backend hits an I/O error or the process is forcibly killed, complete output is not guaranteed.

### 7.6. Why are the order and MDC values correct?

1. `root` contains two keys. `MdcScope(root)` installs them on the main thread; the first event outputs `op-17`.
2. `MdcScope(child)` changes `operationId` to `op-18` for the `inventory_reserved` event.
3. The child scope is closed by try-with-resources. `close()` **restores the `previous` snapshot**, so the main thread returns to `op-17`.
4. `snapshot = MDC.getCopyOfContextMap()` is taken **after closing the child scope**; the worker therefore receives `req-42/op-17`.
5. `withMdc(...)` opens a scope on the business worker, logs the event, and automatically restores the worker thread's MDC in `close()`.
6. `payment.get()` waits for the business worker's **`LOG.info` call** to finish before the caller emits `checkout_finished`; it is **not** confirmation that the collector has written it. Logback's single-worker queue preserves the order of enqueued events in the demo, and `context.stop()` drains the queue before printing the check line.
7. The root scope closes, leaving no `req-42/op-17` on the main thread; the worker is reused to check both keys and returns `true`.
8. `LOG.info` uses the SLF4J API; Logback's `ASYNC` keeps each event's MDC snapshot; `CONSOLE` writes to `System.out` according to the pattern.
9. In production, you should not create a new `ExecutorService` per request or stop `LoggerContext` every time. This mechanism is scaled down to illustrate and verify the lifecycle.

If you omit `withMdc(snapshot, ...)` and submit `LOG.info` directly to the executor, the event emitted on the worker can have an empty MDC. **AsyncAppender cannot retroactively add the `requestId` MDC to an event created without context.**

### 7.7. Key point about Scope

`MdcScope` restores the entire map rather than just calling `MDC.clear()` after a child scope. With nested operations, clearing everything in a child can wipe out the parent's MDC as well. Snapshot-based restoration is a safe way to manage synchronous scopes.

Limitation: `MdcScope` must be closed on **the same thread where it was opened** because restoration affects the current thread's MDC. Do not pass an open scope instance from thread A to thread B and call `close` on B; instead, capture the data and open a **new scope** on B.

## 8. Practical Wrapper Pattern for ExecutorService

In real applications, people commonly write a helper that takes a `Runnable`/`Callable` and returns a task with propagation built in. Two critical jobs:

1. Capture MDC **at submission time**, on the caller thread.
2. Restore the worker's MDC **in `finally`**, even when the task throws an exception.

### 8.1. Wrapper for Runnable

```java
// Snippet in a utility class that already imports MDC, Map, Runnable:
static Runnable wrap(Runnable delegate) {
    Map<String, String> captured = MDC.getCopyOfContextMap();

    return () -> {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        try {
            if (captured == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(captured);
            }
            delegate.run();
        } finally {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    };
}
```

**Snippet only**, without full class/imports. Simply call:

```java
// Assuming executor, LOG, and wrap already exist:
executor.submit(wrap(() -> LOG.info("event=task_done")));
```

If you call `wrap(...)` **inside the worker** instead of at the caller, the snapshot will be the worker's context at that moment, which may be empty or belong to another request. The capture boundary must be placed accurately.

### 8.2. Wrapper for Callable with a result

```java
// Snippet in a utility class that already imports Callable, Map, MDC:
static <T> java.util.concurrent.Callable<T> wrap(
        java.util.concurrent.Callable<T> delegate) {

    Map<String, String> captured = MDC.getCopyOfContextMap();
    return () -> {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        try {
            if (captured == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(captured);
            }
            return delegate.call();
        } finally {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    };
}
```

This form preserves the result and exception of `Callable<T>`. When `delegate.call()` throws an error, `finally` still restores MDC. Do not catch the exception just to log and "swallow" it if the business API needs to propagate the failure to the caller.

### 8.3. Wrap each task or decorate the executor?

If hundreds of call sites use `executor.submit`, forcing every developer to remember `wrap(...)` is error-prone. A framework can provide an executor decorator, task decorator, middleware, or context propagation integration. The advantage is that capture/install/restore is applied at a central boundary.

However, you must check carefully:

- Is the decorator applied to `execute`, `submit`, scheduled tasks, and `CompletableFuture`, or only a subset of APIs?
- Does capture happen at submission time or when the worker thread actually runs?
- Is restoration guaranteed when a task is canceled or throws an exception?
- Do contexts other than MDC (security/tracing/locale) have their own policies?
- Does it nest scopes properly without wiping out the framework's context?

Do not treat a `Runnable` wrapper as a complete solution for every async framework.

## 9. CompletableFuture and Async Pipelines

`CompletableFuture.supplyAsync` or `runAsync` may run on `ForkJoinPool.commonPool()` if no executor is passed, or on a specified executor. Either way, you cannot assume the caller's MDC automatically follows the task.

Example:

```java
// Snippet with executor, LOG, and wrap() already existing:
java.util.concurrent.CompletableFuture<Void> job =
        java.util.concurrent.CompletableFuture.runAsync(
                wrap(() -> LOG.info("event=stage_one")),
                executor);

job.join();
```

Points to note:

- `wrap(...)` is called at the caller, **before** the task is executed.
- `join()` waits for the work to finish, which **does not mean** the async appender/collector has flushed.
- A chain of `thenApplyAsync(...)`, `thenComposeAsync(...)` can run on different threads at each stage; you must capture/propagate at **every boundary** or use a context-aware executor/integration.
- Callbacks without the `Async` suffix may run on the thread that completed the previous stage; that is also not a contract to rely on for accidental MDC.

Do not use `InheritableThreadLocal` as a simple fix for thread pools: workers are usually pre-created and reused, so inheritance at thread creation time does not reflect each task's context.

## 10. Reactive Streams, Schedulers, and Virtual Threads

### 10.1. Reactive pipelines

In Reactor/RxJava and other reactive systems, a single request can hop across multiple schedulers/threads along the processing path. Thread-based MDC is easily lost or mixed up if code merely calls `MDC.put` at request ingress and expects all operators to stay on the same thread.

The right approach is to use the **context propagation mechanism** supported by the version of the reactive framework and tracing/logging system in use. Many frameworks have a request/reactive context independent of `ThreadLocal`; the logging bridge needs to know when to install/restore MDC around callbacks/events.

Do not attach a `ThreadLocal` at the start of a pipeline and fail to clean it up after each operator. This is especially dangerous with event loops or heavily reused thread pools.

### 10.2. Virtual threads

Java 21 provides virtual threads as a standard feature; the demo uses Java 17 and therefore does not use them. Virtual threads also have thread-local context via the corresponding APIs, but **that does not mean all contexts are automatically propagated when spawning a new task/virtual thread**. When adopting a new concurrency model, choose an appropriate propagation policy and measure the cost of context entries.

Do not infer that virtual threads are always equivalent to "the same request thread" across all callbacks, or that an MDC adapter already supports every concurrency model out of the box.

### 10.3. Structured concurrency / tracing context

Some ecosystems provide scoped or task-local context mechanisms distinct from SLF4J MDC. When integrating, distinguish business operation data, security principal, locale, and trace/span context. MDC **is only a log correlation layer**, not a place to store primary business state or authorization information.

If the system uses OpenTelemetry instrumentation, use the official context propagation mechanism for trace/span, and configure log correlation so the encoder outputs valid IDs. Do not generate your own `traceId` string and call that distributed tracing.

## 11. MDC in Log4j 2 Async Logging

Log4j 2 has **Thread Context** (e.g., `ThreadContext.put`/`ThreadContext.getImmutableContext`), along with different asynchronous mechanisms such as `AsyncAppender` and `AsyncLogger`.

Log4j 2 API example:

```java
import org.apache.logging.log4j.ThreadContext;

// Snippet: LOG is a Log4j 2 Logger:
ThreadContext.put("requestId", "req-42");
try {
    LOG.info("event=started");
} finally {
    ThreadContext.remove("requestId");
}
```

This snippet is **not a standalone program**; it requires Log4j 2 dependencies and a `LOG` of the right type. It merely shows the equivalent idea: set the thread's context when creating the event, then clean it up afterward.

With Log4j 2 `PatternLayout`, the context can be accessed using conversion patterns supported by Log4j 2, such as:

```xml
<PatternLayout pattern="%level req=%X{requestId} - %msg%n"/>
```

This is a **Log4j 2 fragment**, not a complete `log4j2.xml`. You must check the backend/API/version, the type of async mechanism, and the JSON layout in use. Do not directly apply Logback's `discardingThreshold` or `neverBlock` properties to Log4j 2, as their implementations and queue-full policies differ.

### 11.1. Log4j 2 ThreadContext and SLF4J MDC

When an application calls SLF4J and the backend is Log4j 2, the `MDCAdapter`/bridge/provider determines how context is integrated. Do not assume `org.slf4j.MDC` and `org.apache.logging.log4j.ThreadContext` are always in sync across all topologies/versions. Choose one logging API/propagation policy intentionally and test with the actual runtime provider.

### 11.2. AsyncLogger vs AsyncAppender

Log4j 2 has an `AsyncLogger` architecture that differs from simply wrapping an appender. Differences in queue/ring buffer, thread handoff, snapshot/context, and event lifecycle depend on configuration/version. Whichever approach you use, the core questions remain **which log-emitting thread the event's context is captured on** and **whether the business context has reached that emitting thread**.

Do not infer from the name "async" any guarantee of global ordering, zero log loss, or automatic context propagation across application tasks.

## 12. MDC, JSON Logging, and Structured Fields

In text output, a pattern such as:

```text
INFO req=req-42 op=op-17 - event=checkout_started
```

helps humans see the IDs, but a collector might store the entire line as a single `message`. If you want to query by field, use a JSON encoder/layout configured to output MDC/structured arguments as separate fields:

```json
{
  "timestamp": "2026-11-09T08:15:03.125Z",
  "level": "INFO",
  "service": "orders-api",
  "event": "checkout_started",
  "requestId": "req-42",
  "operationId": "op-17",
  "message": "Checkout started"
}
```

This is an **illustrative schema**, not the output of the Maven program in section 7. Example 7's `ConsoleAppender` outputs pattern-based text, **not JSON**.

Things to check:

- Whether the JSON encoder includes MDC fields.
- Whether MDC map keys are placed at the top level or in a nested object.
- Whether field names conflict with reserved fields such as `level`, `timestamp`, `message`.
- Whether key names and values are properly allowlisted/sanitized.
- Whether the collector preserves the schema, escaping, and trace/operation correlation data.
- Whether a single event is emitted through multiple appenders—avoid duplicates.
- Whether fields have appropriate types: MDC is typically string-based, so `durationMs` in MDC can become `"145"` instead of the number `145`; for numeric metrics that need querying, use a structured event API or controlled type conversion in the encoder.

**MDC does not automatically generate JSON fields.** It supplies context data to the logging event; the encoder decides the output representation.

### 12.1. One event per line

If JSON is written to console/file for a line-reading collector, prefer **one JSON object per line** (JSON Lines/NDJSON). Newlines in messages/exceptions must be escaped inside the JSON string by the serializer rather than printing loose stack traces outside the object. Use a standard encoder instead of concatenating JSON strings with user input.

### 12.2. Correlation in the collector

To find all events belonging to request `req-42`, you can query by the `requestId` field if the collector has parsed it. With text logs, you need an appropriate parser/regex; if `requestId` is only in the message and the format changes, queries break easily.

Operation context and trace context can be kept on the same event, but do not conflate `requestId`, `operationId`, `traceId`, and `spanId`. They describe different relationships in the system.

## 13. Errors, Throwables, and Async MDC Data

When logging an error:

```java
// Snippet: LOG is an SLF4J Logger, error is a real Throwable.
LOG.error("event=checkout_failed orderId={}", orderId, error);
```

The logger/backend can accept a `Throwable` as the cause and attach the exception to the event. MDC must be set before calling the logger so the error record carries `requestId`/`operationId`.

You should distinguish:

- **Throwable**: stack trace, cause chain, suppressed exceptions, and error message.
- **MDC**: context such as request/operation/tenant ID, primarily for correlation.
- **Message parameters**: values filled into `{}` when formatting the message.
- **Structured attributes**: specific fields that a JSON encoder can output independently.

An event with valid MDC **does not guarantee** the stack trace is output: the encoder still has to know how to render the `Throwable`. And logging only `error.getMessage()` can lose the cause and stack trace.

### 13.1. Mutable arguments and snapshots

An async appender may prepare the message, thread name, and MDC at enqueue time, but you should not rely on every backend deep-copying all mutable objects in arguments. If you log an object and mutate it immediately afterward, the output can depend on how the backend defers formatting/serialization.

For identifiers used in correlation, prefer immutable values such as String IDs. Do not put an entire request/entity object into MDC; the simple MDC map is designed for short, controlled fields.

### 13.2. When an exception occurs in a business task

The MDC wrapper must restore the context **even if the task fails**. For example:

```java
// Snippet: executor and wrap(...) already exist.
Future<?> failure = executor.submit(wrap(() -> {
    throw new IllegalStateException("payment failed");
}));

// failure.get() will throw ExecutionException;
// inside wrap, finally has still restored the worker's MDC.
```

This snippet only illustrates control flow, not a standalone program; in real code, the caller must handle `ExecutionException`, return an appropriate outcome, and decide where to log the error to avoid duplicates. If logging on the worker inside `catch`, keep the scope active until the log event is created; do not clear MDC first and then log the error.

## 14. Security of MDC in Async Execution

MDC is so convenient that it is also easy to abuse. Once a key is set, many log events can automatically carry that value throughout the scope.

**Do not put into MDC:**
- Access tokens, passwords, API keys, session cookies, or raw `Authorization` headers.
- Card data, OTPs, credentials, or JDBC URLs containing passwords.
- Unnecessary personal data or full payloads.
- Large objects or unbounded arbitrary strings.
- Untrusted user values used for access control or logger configuration.

Prefer:
- Opaque system-issued or validated request/operation IDs.
- Stable service/route/operation names.
- Error codes, attempt counts, and approved business IDs.
- Standard instrumentation-provided trace/span IDs when needed.

### 14.1. A context leak is also a security bug

If a worker thread still holds the `tenantId` or `requestId` of request A and later processes request B, B's logs can be mistakenly tagged with A's information. This leads to wrong investigations and potential cross-tenant metadata leakage.

How to prevent it:

1. Capture a validated snapshot.
2. Install it at the exact task boundary.
3. Always restore the previous value in `finally`.
4. Check callback, exception, and cancellation paths.
5. Test reused thread pools and nested scopes.

Do not call `MDC.clear()` indiscriminately inside a child component if the framework/outer layer still needs the context; restoring the previous snapshot can be critical.

### 14.2. JSON escaping is not masking

A JSON encoder escapes quotes, backslashes, newlines, and control characters to produce valid JSON. It **does not automatically filter secrets**. A field `"accessToken":"secret"` is still valid JSON, yet wrong from a security standpoint.

Apply allowlists/redaction, log access controls, retention/quotas, and data transport policies.

## 15. Performance and Reliability

### 15.1. MDC snapshotting has a cost

Copying the MDC map and resetting it on every task creates allocations and processing work proportional to the number of fields. Do not stuff hundreds of arbitrary keys into MDC when you only need `requestId`/`operationId`/`traceId`.

If an application spawns millions of tiny tasks, propagation overhead can be measurable. Benchmark under realistic workloads, select only the needed context, and use an appropriate decorator/integration. However, **do not drop propagation just to save a few allocations and render all logs impossible to correlate**.

### 15.2. AsyncAppender reduces caller blocking but does not eliminate I/O

While the queue has room, callers can enqueue quickly and move on. When the file/console/collector is slow for a sustained period, the queue fills up and producers may block or drop. Using MDC does not fix a sink bottleneck. Conversely, events with fairly large MDCs can consume more RAM in the queue.

Monitor:
- Queue depth and remaining capacity.
- Dropped/discarded events if the backend provides telemetry.
- Log delivery lag: time from event creation to collector receipt.
- CPU/heap/GC and logger p95/p99 latency.
- Shutdown drain time, write/flush errors, and collector health.

### 15.3. MDC does not guarantee zero log loss

If the async logging queue drops events or the process is killed, events can be lost even when the MDC snapshot is completely accurate. For mandatory audit logs, do not rely on an in-memory queue as the sole source of truth; consider a durable audit/event store or transactional outbox depending on the system.

### 15.4. Caller data is not MDC

`includeCallerData=true` in Logback AsyncAppender requests early collection of stack-derived caller metadata such as class, method, file, and line; this can be CPU-expensive. Snapshotting `requestId`/`operationId` in MDC is a separate matter. Do not enable caller data thinking it is the switch to "keep MDC."

## 16. Essential Tests for Async MDC

### Test A: caller clears MDC immediately after logging

Emit an event when MDC is `req-42`, call `LOG.info`, then clear in `finally`. With standard Logback AsyncAppender, the output must contain `req-42` in the enqueued event, without mistakenly reading the logging worker's current MDC.

### Test B: task without propagation

Set MDC in `main`, then submit a task without a wrapper. When the worker logs, `requestId` may be empty. This demonstrates why AsyncAppender does not fix business context propagation bugs.

### Test C: task with wrapper

Capture on the caller, install on the worker, log, and restore. Verify `requestId` in the output and check the value after the task completes.

### Test D: reusing a single worker for two requests

Use `newSingleThreadExecutor` with requests A and B having different IDs. Each task must see its own context. After each task, verify the worker thread does not retain the old ID. This is a crucial test for detecting context leaks.

### Test E: nested operation

Root `op-17` opens child `op-18`, then closes the child. The next event must revert to `op-17`; it must neither lose the root context nor keep the child ID.

### Test F: exceptions and cancellation

Have a task throw an exception, return early, be interrupted, or be canceled in a test environment. Verify that the wrapper's `finally` still restores if the task actually started and entered that code; do not assume a task canceled before running ever installed context.

### Test G: queue overload and shutdown

Use a controlled slow sink and a small queue in a test environment. Distinguish events **missing MDC** from events **dropped** or **not yet flushed**; monitor backend status, queue depth, timeouts, and the number of events reaching the sink. Do not run crash-style tests in production without a safety plan.

### Test H: JSON collector

Verify that raw JSON/events already contain `requestId`/`operationId`, then verify that the collector parses and indexes those same fields. If the raw log has the fields but the dashboard is empty, the issue may be in the schema/parser/index rather than MDC propagation.

## 17. Troubleshooting: Why Is MDC Lost in Async?

| Symptom | Possible Cause | Fix |
|---|---|---|
| Caller log has reqId, worker task log is empty | MDC does not auto-propagate to `ExecutorService` | Capture/install/restore at the task boundary |
| AsyncAppender prints the right ID, but `MDC.get` on the logging worker is empty | Encoder reads the event snapshot, not the worker's ThreadLocal | Inspect `ILoggingEvent` and the pattern instead of reading worker MDC directly |
| Request B has request A's ID | Thread pool reused, task did not clear/restore | Use a scope with previous snapshot restoration in `finally` |
| Closing child operation loses parent operation | `MDC.clear()` or remove overwrote without restoring | Nested scope restores previous values |
| `%X{requestId}` is empty even though MDC was set | Event was created on another thread or wrong key | Compare event creation time/thread, check key/pattern |
| JSON only has message, no `requestId` field | Encoder does not have MDC field extraction enabled | Configure JSON encoder, schema, and field mapping |
| MDC is right, but WARN/ERROR are lost at peak | Async queue discard/drop or sink error | Check queue policy, metrics, and backend status |
| Final events do not appear on shutdown | Async worker did not drain; timeout/kill | Stop/flush properly in lifecycle with a reasonable grace period |
| Later `CompletableFuture` stage loses context | Different `thenApplyAsync` boundary | Decorate each stage or use a context-aware executor |
| Reactive callback has the wrong ID | Thread reuse / missing context propagation | Use the reactive framework's integration |
| MDC does not work on another provider | SLF4J MDCAdapter/backend support differs | Check runtime provider and configuration |
| Caller data is wrong or empty | `includeCallerData` disabled or encoder doesn't print it | Evaluate need for caller metadata and its cost |
| Logs appear twice | Root attaches both ASYNC and CONSOLE, additivity | Check appender topology; do not blame MDC |
| MDC contains tokens/PII | Middleware copies all headers/request into MDC | Allowlist, mask, clean context, and protect the collector |
| Searching logs by traceId does not match | Trace ID not propagated by tracing SDK | Check trace context; do not equate `requestId` with `traceId` |

### Investigation procedure

1. Determine **which thread created the event**; what was MDC on that thread right before the logger call?
2. Check the **business async boundary**: where is the task submitted, and is there a wrapper/decorator?
3. Check **whether capture happens before or after** the caller clears/changes MDC.
4. Check whether the worker installs the snapshot properly and restores it even on exceptions.
5. Check the **actual backend** (Logback/Log4j 2/JUL bridge) and `MDCAdapter`.
6. Check whether AsyncAppender/AsyncLogger snapshots the required data and what drop policy it uses.
7. Check whether the encoder/layout outputs the MDC field/pattern with the exact key.
8. Check raw stdout/file before the collector; distinguish missing raw data from parser/index dropping fields.
9. Check shutdown lifecycle, queue backlog, and duplicates.
10. Check for cross-request/cross-tenant context leaks in thread pools.

## 18. Practice Exercises

### Exercise 1 — Why couldn't AsyncAppender save `requestId`?

The main thread sets `MDC.put("requestId", "req-42")` and then calls `executor.submit(() -> LOG.info("event=done"))`. Logback has `AsyncAppender`, yet the line from the worker lacks `requestId`.

**Answer:** The event was created on the worker without the main thread's MDC. `AsyncAppender` only snapshots the event's MDC **at the moment the worker calls the logger**. You must capture on the caller and install on the worker, or use the framework's context propagation.

### Exercise 2 — Restoring nested context

Root `op-17`, child `op-18`. When the child finishes, calling `MDC.clear()` causes subsequent root logs to lose `operationId`.

**Answer:** You need to save the previous map before the child scope and restore it in `finally`/`AutoCloseable`. Wiping the entire MDC in the child can destroy the parent's data.

### Exercise 3 — Reading JSON and not seeing the field

The raw log contains `"message":"requestId=req-42 event=done"`, but there is no separate `requestId` field.

**Answer:** That is a message string, not a structured attribute. Configure the encoder to output MDC as fields, or use a structured arguments API with an appropriate schema.

### Exercise 4 — Task fails and the next request gets the wrong ID

A wrapper only calls `MDC.clear()` when the task succeeds. The task throws a `RuntimeException`, so it is not cleaned up; the next worker carries the old ID.

**Answer:** Restoration must be in `finally`. Restore the previous context snapshot rather than just clearing unconditionally; test with a reused thread pool.

### Exercise 5 — AsyncAppender and lost logs

An event has complete MDC, yet disappears after the queue fills up with `neverBlock=true`.

**Answer:** This is event loss due to queue policy, not an MDC bug. You must decide the block/drop trade-off, measure overload, and design a durable storage path if auditing is required.

## 19. Pre-Deployment Checklist for MDC with Async

- [ ] Clearly distinguish **business async** from **async logging**.
- [ ] MDC is set **before the event is created** on the right thread.
- [ ] Logback AsyncAppender is configured properly, snapshotting MDC on the event at enqueue time.
- [ ] Across `ExecutorService`/`CompletableFuture`, capture/install/restore is applied at the right boundaries.
- [ ] Do not rely on `ThreadLocal` or `InheritableThreadLocal` auto-propagating across thread pools.
- [ ] Nested scopes restore the previous context without accidentally wiping the parent.
- [ ] Wrappers restore in `finally`, including on exceptions, early returns, or cancellation after start.
- [ ] Worker reuse tests exist to catch `requestId`/`tenantId` leaking to the next task.
- [ ] Do not use dynamic logger names per request ID.
- [ ] Text/JSON encoders actually output MDC, with consistent schema/field names.
- [ ] Throwables, messages, and structured fields are handled separately; do not mistake MDC for a stack trace.
- [ ] SLF4J MDC provider/adapter or Log4j 2 `ThreadContext` has been verified at runtime.
- [ ] Clear policies exist for queue full, drop/block, flush, shutdown, and collector.
- [ ] Tracing SDK propagates `traceId`/`spanId` separately; MDC serves log correlation.
- [ ] No unnecessary secrets/PII are written to MDC; allowlists and retention are enforced.
- [ ] Tested under high load, async callbacks, nested operations, task failures, and JSON parsing.

**Conclusion:** **MDC in async** requires solving **two distinct context handoffs**. When only offloading log writing to Logback AsyncAppender, the event typically carries the MDC snapshot from the moment of logging. When **handing off business work** to another thread/task, the application or framework must **capture → install → execute → restore** MDC so events are created with the right `requestId`/`operationId`. Preserving context enables accurate tracing of logs, but it does not turn logging into a tracing system, does not eliminate queue-related event loss, and does not replace data security policies.
