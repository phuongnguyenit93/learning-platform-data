# Layouts in Log4j2: Formatting Log Events

## 1. Where does a Layout fit in the logging system?

When a Java application calls a logger, the Log4j2 system creates a **LogEvent** containing information such as the level, logger name, timestamp, message, thread, ThreadContext, and exception (if any). A LogEvent is not necessarily a line of text yet. Before an Appender writes it to the console, a file, or another destination, the event may need to be **serialized**.

A **Layout** is the component that defines **how to represent a LogEvent as output content**. For example, the same event can become:

- Human-readable text: `INFO OrderService - event=order_created order_id=ORD-101`.
- Structured JSON: an object carrying fields `level`, `logger`, `message`, `correlation_id`.
- Another representation required by the receiving tool.

Simple diagram:

```text
OrderService: LOG.info("event=order_created order_id={}", id)
                               |
                               v
                            LogEvent
                   level, logger, message,
                   timestamp, context, ...
                               |
                               v
                     LoggerConfig / Filter
                               |
                    +----------+----------+
                    |                     |
                    v                     v
              Console Appender        File Appender
                    |                     |
                    v                     v
              PatternLayout        JsonTemplateLayout
                    |                     |
                    v                     v
               Text line             JSON line
                    |                     |
                    v                     v
               stdout/stderr         File / collector
```

Distinguishing the roles:

| Component | Question it answers |
| --- | --- |
| **Logger / LoggerConfig** | Where does the event come from, and what are its log level and routing configuration? |
| **Filter** | Is the event allowed to proceed? |
| **Appender** | Which resource is the event sent to, such as the console or a file? |
| **Layout** | Is the event represented as a text pattern, JSON, or another format? |
| **LogEvent** | Which attributes does the original event record contain? |

**A Layout does not decide the log level and does not choose the storage destination on its own.** When a single LogEvent is sent to two Appenders with two Layouts, it can produce two different representations—not two occurrences of the business action.

## 2. Common Layouts

| Layout | Characteristics | When to use |
| --- | --- | --- |
| `PatternLayout` | Assembles LogEvent information into text according to a pattern containing tokens starting with `%` | Reading console output, writing text logs, local diagnostics |
| `JsonTemplateLayout` | Generates JSON using an event template and resolvers; suited for structured schemas | Centralized log collection/search systems |
| `JsonLayout` | Legacy JSON output style from Log4j Core | Mainly when maintaining compatibility with existing systems |
| `XmlLayout` | Represents events as XML | Systems or pipelines that accept XML |
| `HtmlLayout` | Presents logs in HTML format | Cases where logs are viewed as HTML documents |
| `MessageLayout` | Extracts only the Message from a LogEvent | Specific cases such as JDBC Appender |

For new projects, the two options to learn thoroughly are **PatternLayout** and **JsonTemplateLayout**. The Log4j2 documentation recommends JSON Template Layout for structured logging sent to ingestion systems; you should not manually build complex JSON by concatenating strings in PatternLayout.

Do not assume every Layout belongs to `log4j-api`. Concrete Layout implementations belong to **Log4j Core**, and some types also require additional artifacts. Having only the API to call `Logger.info(...)` does not guarantee that Layout plugins will be discovered at runtime.

## 3. How does PatternLayout work?

`PatternLayout` takes a **conversion pattern** string consisting of literal text and **pattern converters**. For example:

```xml
<PatternLayout charset="UTF-8"
    pattern="%d{ISO8601} %-5p [%t] %c{1} - %m%n"/>
```

This is **part of an Appender configuration**, not a standalone XML file.

| Converter | Meaning |
| --- | --- |
| `%d{ISO8601}` | Event timestamp in the ISO8601 date-time format supported by Log4j |
| `%p` or `%level` | Log level, such as `INFO` or `WARN` |
| `%-5p` | Log level, left-aligned with a minimum width of 5 characters |
| `%t` | Name of the thread that generated the event |
| `%c` or `%logger` | Logger name |
| `%c{1}` | Last component of the logger name, typically the class name |
| `%m` or `%msg` | Message content |
| `%n` | Platform-dependent line separator |
| `%X{correlation_id}` | Value of the `correlation_id` key from the ThreadContext map |
| `%marker` | Marker of the LogEvent, if present |
| `%ex` | Exception/stack trace data of the LogEvent, if present |
| `%%` | A literal percent sign |

For example, given a logger named `example.orders.OrderService`, thread `main`, level `INFO`, and message `event=order_created order_id=ORD-101`, the pattern `%-5p [%t] %c{1} - %m%n` can produce:

```text
INFO  [main] OrderService - event=order_created order_id=ORD-101
```

This is an **illustration of converter values**, not the output of the complete example program in the next section.

### Width and alignment

`%-5p` does not mean truncating the level to 5 characters. The `-` character here requests left alignment; the number `5` is the **minimum width**. `INFO` is padded with one space; `ERROR` is already 5 characters long so it needs no padding. A value longer than 5 characters is not truncated by this modifier.

Converters with a maximum length limit, such as `%.30c`, can truncate the logger name. Use them only when shortening the source name is acceptable. A literal `%` sign in a pattern must be written as `%%`.

### Message template vs. conversion pattern

Compare these two snippets:

```java
LOG.info("event=order_created order_id={}", orderId);
```

```xml
<PatternLayout pattern="%p %c{1} - %m%n"/>
```

**`{}`** belongs to the message template of the Log4j2 API call and is used to substitute parameters such as `orderId`. **`%m`** belongs to the Layout and retrieves the formatted message from the LogEvent. Do not use `%m` in a message template to substitute an ID, and do not use `{}` in PatternLayout to substitute the logger name.

## 4. Complete Java 17+ Example with PatternLayout

The following example creates a small Java program using the Log4j2 API and Core, a Console Appender that sends logs to **stdout**, and a PatternLayout that prints the level, logger name, correlation ID, and message.

The dependency version is **pinned to 2.26.1** so the example is reproducible. In real projects, check maintenance/patch versions and compatibility before deploying; the version in this article does not replace security update policies.

Directory structure:

```text
log4j-layout-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── example/
        │       └── logging/
        │           └── LayoutDemo.java
        └── resources/
            └── log4j2.xml
```

### 4.1. Maven configuration: `pom.xml`

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>example.logging</groupId>
    <artifactId>log4j-layout-demo</artifactId>
    <version>1.0.0</version>
    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>
    <dependencies>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-api</artifactId>
            <version>2.26.1</version>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-core</artifactId>
            <version>2.26.1</version>
            <scope>runtime</scope>
        </dependency>
    </dependencies>
</project>
```

`log4j-api` provides `Logger`, `LogManager`, and `ThreadContext`. `log4j-core` is the backend containing configuration, Appenders, and `PatternLayout`.

### 4.2. Configuration file `src/main/resources/log4j2.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="STDOUT" target="SYSTEM_OUT">
            <PatternLayout charset="UTF-8"
                pattern="%p %c{1} correlation_id=%X{correlation_id} - %m%n"/>
        </Console>
    </Appenders>
    <Loggers>
        <Root level="INFO">
            <AppenderRef ref="STDOUT"/>
        </Root>
    </Loggers>
</Configuration>
```

Explanation:

- `Console` is the **Appender**. `target="SYSTEM_OUT"` directs output to stdout; it is not an attribute of PatternLayout.
- `PatternLayout` chooses the content and order of the printed fields. `charset="UTF-8"` encodes the text into appropriate bytes.
- `%c{1}` shortens the logger `example.logging.LayoutDemo` to `LayoutDemo`.
- `%X{correlation_id}` reads the corresponding context value.
- `Root level="INFO"` and `AppenderRef` route `INFO` and `WARN` events to the Appender in this example, provided no other configuration or filter alters them.
- `%n` ensures each event ends with a newline.

Place the file in the `resources` directory so Maven includes it on the classpath. If Log4j2 does not load this configuration and instead uses another file, the output content and destination will change.

### 4.3. File `src/main/java/example/logging/LayoutDemo.java`

```java
package example.logging;

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;
import org.apache.logging.log4j.ThreadContext;

public final class LayoutDemo {
    private static final Logger LOG =
            LogManager.getLogger(LayoutDemo.class);

    private LayoutDemo() {
    }

    public static void main(String[] args) {
        try {
            ThreadContext.put("correlation_id", "req-17");
            LOG.info("event=order_created order_id={}", "ORD-101");
            LOG.warn("event=payment_retry order_id={} attempt={}",
                    "ORD-101", 2);
        } finally {
            ThreadContext.clearMap();
        }
    }
}
```

The program creates two LogEvents at two levels with the same correlation ID. `ThreadContext.clearMap()` clears the current thread's map when processing finishes; this is especially important in environments that reuse threads.

### 4.4. Compile and run

From the directory containing `pom.xml`, with JDK 17+ and Maven:

```bash
mvn -q -DskipTests package
mvn -q org.apache.maven.plugins:maven-dependency-plugin:3.7.1:copy-dependencies -DoutputDirectory=target/dependency
```

On Linux/macOS:

```bash
java -cp "target/classes:target/dependency/*" example.logging.LayoutDemo
```

On Windows:

```powershell
java -cp "target\classes;target\dependency\*" example.logging.LayoutDemo
```

Maven may need to download plugins and dependencies from the configured repository if they are not yet cached.

**Exact stdout output of the program** with the configuration above:

```text
INFO LayoutDemo correlation_id=req-17 - event=order_created order_id=ORD-101
WARN LayoutDemo correlation_id=req-17 - event=payment_retry order_id=ORD-101 attempt=2
```

**Stderr:** no application logs under normal initialization conditions. Maven/JVM diagnostics or environment configuration errors are not considered business output of the example.

Breakdown of each output component:

| Segment | Source |
| --- | --- |
| `INFO`, `WARN` | `%p` converter |
| `LayoutDemo` | `%c{1}` converter |
| `correlation_id=req-17` | Literal text and `%X{correlation_id}` |
| `event=...` | Message from `%m` |
| Two separate lines | `%n` |
| Printed to stdout | Console Appender with `SYSTEM_OUT` |

If you only change the pattern to `%m%n`, the same program will print only the message (without the leading level/logger/context). If you only change `SYSTEM_OUT` to `SYSTEM_ERR`, the data goes to stderr while the text format stays the same. This is the most intuitive way to distinguish **Layout** from **Appender**.

## 5. JsonTemplateLayout: JSON for Centralized Systems

`PatternLayout` is meant for quickly readable text. When you need to search by `level`, `service`, `order_id`, `request_id`, or `exception` across many machines and versions, structured logs spare the collector from having to parse a text sentence with regular expressions.

**JsonTemplateLayout** uses a **JSON event template** and **resolvers** to represent LogEvent attributes. According to the Apache Log4j documentation, this is the recommended option for JSON logs used in production ingestion.

To use it with Maven, **add** the following dependency to the example's `pom.xml`, keeping the version synchronized:

```xml
<dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-layout-template-json</artifactId>
    <version>2.26.1</version>
    <scope>runtime</scope>
</dependency>
```

This is a **snippet to add inside the `<dependencies>` block**, not a standalone Maven file.

Replace the `STDOUT` Appender content in `log4j2.xml` with:

```xml
<Console name="STDOUT" target="SYSTEM_OUT">
    <JsonTemplateLayout eventTemplateUri="classpath:EcsLayout.json"/>
</Console>
```

The rest of the `Root`/`AppenderRef` configuration can remain as in the example. `EcsLayout.json` is a built-in template of JsonTemplateLayout based on the Elastic Common Schema; you do not need to write your own if it meets your requirements.

**Important:** after switching to JsonTemplateLayout, the output is **no longer the exact two text lines** shown in section 4. It is JSON conforming to the template, with field names and structure defined by that template. Do not assume there is automatically a separate `"order_id"` field just because the message text contains `order_id=ORD-101`.

Example JSON format **illustrating a custom schema**:

```json
{
  "timestamp": "2026-11-09T12:00:00.000Z",
  "level": "INFO",
  "logger": "example.logging.LayoutDemo",
  "message": "event=order_created order_id=ORD-101",
  "correlation_id": "req-17"
}
```

This is **not the verbatim output of `EcsLayout.json`**. To produce the exact schema above, you need the corresponding template and resolvers, and you should verify the output against the actual backend.

### Event template and resolvers

A custom JSON template file might contain:

```json
{
  "level": {
    "$resolver": "level",
    "field": "name"
  },
  "message": {
    "$resolver": "message",
    "stringified": true
  }
}
```

Save this JSON to `src/main/resources/MyLayout.json` and reference it:

```xml
<JsonTemplateLayout eventTemplateUri="classpath:MyLayout.json"/>
```

This is a **template that outputs only level and message**. It does not automatically include a timestamp or exception. The `"$resolver"` key in a JSON template instructs the Layout to extract a LogEvent attribute, quite different from `%m` in PatternLayout. To add a timestamp, context, or stack trace, add the appropriate resolvers according to the documentation rather than guessing syntax.

### Why not use PatternLayout to assemble JSON manually?

The following snippet **should not be used to generate production JSON**:

```xml
<PatternLayout pattern="{&quot;level&quot;:&quot;%p&quot;,&quot;message&quot;:&quot;%m&quot;}%n"/>
```

A message containing double quotes, backslashes, or control characters can produce invalid JSON. Even with escaping converters, ensuring proper data types, schema, exceptions, and complete context is harder than using a dedicated layout.

## 6. Layout, ThreadContext, and Correlation IDs

Log4j2 provides `ThreadContext` to attach data that should be carried across multiple events within an execution flow:

```java
ThreadContext.put("request_id", requestId);
try {
    LOG.info("event=order_received order_id={}", orderId);
    LOG.info("event=order_checked order_id={}", orderId);
} finally {
    ThreadContext.remove("request_id");
}
```

This is an **illustrative snippet** inside a class where `LOG`, `requestId`, and `orderId` exist.

In PatternLayout, use:

```xml
<PatternLayout pattern="%p request_id=%X{request_id} - %m%n"/>
```

When the key has not been set, `%X{request_id}` may evaluate to an empty string; the literal text `request_id=` still appears. Consider how missing fields should be handled when the pipeline requires a consistent schema.

Notes:

- A Logger is shared across many requests, but context **must not be shared via a mutable static variable**.
- With thread pools, you must clean up the context after each request so a subsequent request does not inherit an old ID.
- When work is handed off to another thread, do not assume context is propagated automatically; use an appropriate propagation mechanism.
- Do not put passwords, tokens, card numbers, or sensitive data into ThreadContext just because the Layout can print them.
- When outputting JSON, verify that the template/pipeline preserves context entries as independent fields if you need to query by them.

Log4j has both **property lookup** syntax and pattern converters. To retrieve a key from ThreadContext in PatternLayout, `%X{key}` is usually the clearest choice; do not arbitrarily use a higher-overhead lazy lookup mechanism when a dedicated converter suffices.

## 7. Exceptions in Layouts: `%ex`

When a `LogEvent` carries a `Throwable`, PatternLayout provides exception converters:

```xml
<PatternLayout charset="UTF-8"
    pattern="%d{ISO8601} %-5p %c{1} - %m%n%ex"/>
```

Here `%n` inserts a newline between the message and the stack trace; `%ex` displays the error if the event has a Throwable. Common variants:

- `%ex` or `%ex{full}`: full stack trace.
- `%ex{short}`: short summary at the top.
- `%ex{none}`: do not print the exception via this converter.
- `%rEx`: a way to display the cause chain starting from the root cause.

**Common misconception:** if PatternLayout does not contain an exception converter and `alwaysWriteExceptions` has not been disabled, Log4j2 automatically appends an implicit exception converter. Therefore, omitting `%ex` **does not guarantee** that stack traces will not be printed. When you need explicit placement and depth, configure it explicitly and verify the actual output.

A Layout does not create exceptions. For the formatter to have data, the code must pass the Throwable properly:

```java
try {
    doWork();
} catch (RuntimeException e) {
    LOG.error("event=operation_failed", e);
    throw e;
}
```

This is a **non-standalone** illustrative snippet; `doWork` and `LOG` must be declared. Do not mechanically apply "log and rethrow" at every layer because an outer layer may log the same error again. Decide on responsible error-reporting boundaries and preserve the cause when translating exceptions.

Calling `LOG.error("failed: {}", e.getMessage())` only inserts a string into the message; it does not pass the Throwable object for the Layout to print a stack trace. The `ERROR` level and the presence of a Throwable are two **separate** attributes.

## 8. Timestamps, Time Zones, and Multi-Service Formatting

PatternLayout supports date/time converters, for example:

```xml
<PatternLayout pattern="%d{ISO8601} %p %m%n"/>
```

A pattern can request UTC time and an explicit offset:

```xml
<PatternLayout
    pattern="%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX}{UTC} %p %m%n"/>
```

These snippets illustrate Layout configuration. When deploying across multiple machines, standardizing the timestamp format and time zone helps investigate events across services.

Do not assume all `ISO8601` variants include the same offset information. Some date-time formats do not explicitly show the time zone; investigators need to know which time zone the timestamp was generated in.

When switching to JsonTemplateLayout, the timestamp is determined by the template/resolver. Do not forget to include a timestamp field if the collector uses it for indexing. The time a LogEvent is created and the time the collector receives the record can differ; these two timestamps are not interchangeable.

## 9. Escaping and Log Injection

User-supplied data may contain newlines or control characters. If printed verbatim into a text line, a single logger call can look like multiple events:

```text
WARN Invalid request: bad value
INFO Payment approved
```

Meanwhile, the second line could simply be content injected into a data field. This is a **log injection** risk.

PatternLayout supports the encoding converter `%enc`. For example:

```xml
<PatternLayout charset="UTF-8"
    pattern="%p %c{1} - %enc{%m}{CRLF}%n"/>
```

`%enc{%m}{CRLF}` escapes CR/LF characters inside the message; `%n` outside still produces the newline separating events. If an untrusted value appears in ThreadContext, you must handle that field as well, not only the message:

```xml
<PatternLayout charset="UTF-8"
    pattern="%p id=%enc{%X{request_id}}{CRLF} - %enc{%m}{CRLF}%n"/>
```

`%enc{...}{JSON}` performs escaping for JSON string contexts, but **does not turn PatternLayout into JsonTemplateLayout**. For structured JSON output, use the dedicated Layout.

Additional security considerations:

1. Do not log passwords, tokens, API keys, OTPs, card details, or sensitive payloads in messages or context.
2. Limit the length of dynamic values, as oversized logs increase costs and may be truncated by the collector.
3. Choose the right encoding for the destination. CRLF escaping is not equivalent to full escaping for HTML, XML, or JSON.
4. Control who can read logs and set retention periods.
5. Do not rely on the default Layout to hide secrets. Prefer **not logging** sensitive data in the first place; masking must be designed and tested separately.
6. For Vietnamese (or other non-ASCII) data, configure a compatible charset and collector, typically UTF-8.

## 10. PatternLayout in File and RollingFile

A Layout can be placed inside Appenders other than Console.

**File Appender** example:

```xml
<File name="TEXT_FILE" fileName="logs/application.log">
    <PatternLayout charset="UTF-8"
        pattern="%d{ISO8601} %p %c - %m%n%ex"/>
</File>
```

**RollingFile Appender** example:

```xml
<RollingFile name="ROLLING"
             fileName="logs/application.log"
             filePattern="logs/application-%i.log.gz">
    <PatternLayout charset="UTF-8"
        pattern="%d{ISO8601} %-5p %c - %m%n%ex"/>
    <Policies>
        <SizeBasedTriggeringPolicy size="10 MB"/>
    </Policies>
    <DefaultRolloverStrategy max="5"/>
</RollingFile>
```

The two snippets above are **Appender snippets**; they must be placed inside `<Appenders>` and referenced via `<AppenderRef>` in a logger/root to work. The directory/path and write permissions must be properly configured.

**Rotation is the responsibility of RollingFile, triggering policies, and rollover strategies**, not of the Layout. `PatternLayout` does not decide when to rotate files or how many archives to keep. When writing JSON output to a file, ensure the collector parses the structure correctly and tracks file rotation.

A local file appender does not guarantee that the file will be collected in a containerized environment. If the infrastructure only reads stdout/stderr, the file may not appear in the centralized system unless an agent or volume is configured.

## 11. Performance Considerations When Choosing a Layout

Layouts execute on the logging path and can affect CPU usage, memory allocation, disk/network volume, and latency.

- **True class/method/line converters** such as `%C`, `%M`, or `%L` may require capturing caller location, incurring significant overhead, especially with asynchronous logging. Do not enable them broadly unless needed.
- **Long patterns** with many rarely used fields increase bytes written and storage costs.
- **Complex regex/property lookups** per event can be more expensive than direct converters. Use `%X{key}` instead of lazy lookups when you only need ThreadContext in PatternLayout.
- **JsonTemplateLayout** is designed for structured JSON and optimized for that use case; avoid manually concatenating JSON text via patterns.
- **UTF-8 and encoding** must be consistent with the collector to avoid corrupting Vietnamese diacritics and special characters.
- **Multiple Appenders** can cause a single event to be serialized multiple times; this does not mean business operations ran multiple times, but I/O cost can increase.
- **Expensive log arguments** are separate from Layouts. Java still evaluates `expensive()` when calling `LOG.debug("{}", expensive())` even if the level is disabled; consider guards or suppliers depending on the API in use.
- Test at realistic throughput before concluding which pattern is "fastest"; measure CPU, GC, event size, write time, and collection reliability.

Do not put business side effects inside converters/formatters. An event may be filtered out before the Layout runs, so business outcomes must never depend on whether the Layout executes.

## 12. Two Layouts for One LogEvent

You can design two Appenders:

```text
              One LogEvent
              /          \
             v            v
     Console Appender   File Appender
             |            |
             v            v
       PatternLayout   JsonTemplateLayout
             |            |
             v            v
     Readable stdout   JSON lines
             |            |
             v            v
         terminal      collector/index
```

This design makes sense when serving two different purposes, but you should check:

- An event emitted to two destinations is **two copies of one event**, not two transactions.
- If the collector gathers both stdout and the file, duplicates may be written to the centralized store.
- Filtering log levels differently per destination can cause a given event type to reach only one Appender.
- If you need to query JSON, verify the destination's parser and schema.
- Avoid configuring unnecessary duplicate outputs, as they increase I/O and retention costs.
- If logging over the network, durability also depends on queues, retries, transport, and the collector; a Layout does not guarantee delivery.

## 13. Layout Testing Checklist

A pattern or JSON schema change should be tested in both the application and the pipeline:

1. Log an `INFO` event with a known message, a known request ID, and a Vietnamese character to verify encoding.
2. Verify that Log4j loaded the intended `log4j2.xml` at runtime, not another default file.
3. Confirm that `LoggerConfig`/`Filter` accepts the level and the Appender is referenced properly.
4. Distinguish **stdout**, **stderr**, and **file**: terminals often display both standard streams together.
5. For PatternLayout, verify `%p`, `%c`, `%m`, `%n`, and `%X{key}`.
6. Log an exception with a cause, and confirm that error details are preserved and formatted according to policy.
7. Test messages containing double quotes, backslashes, newlines, and control characters to catch escaping/log injection bugs.
8. For JSON, parse each line as valid JSON; verify field names, types, timestamps, time zones, and searchability in the collector.
9. With multiple Appenders, check the copy count in the centralized search store.
10. When changing the output structure, update related parsers, dashboards, alerts, documentation, and integration tests.

Common symptoms:

| Symptom | What to check |
| --- | --- |
| Log lines do not match the new pattern | `log4j2.xml` was not loaded, another config is active, or another Appender is used |
| `INFO` logs do not appear | Level/Filter on logger or appender is dropping the events |
| `%X{request_id}` is empty | ThreadContext was not set at the right time/thread or was already cleared |
| Stack trace does not appear | Throwable was not passed or converter/template configuration is unsuitable |
| Duplicate copies appear | Additivity, multiple Appenders, or collector reading overlapping sources |
| JsonTemplateLayout is not recognized | Missing `log4j-layout-template-json` or incompatible dependency/plugin |
| JSON is missing expected fields | Template/resolver has not included those fields in the output |
| Vietnamese characters are garbled | Wrong charset or collector using a different encoding |
| File does not appear on dashboard | Agent is not reading the file, wrong path, rotation, or permissions |

## 14. Design Mistakes to Avoid

**1. Confusing Layout with Filter.** Changing a pattern does not enable the `DEBUG` level. Check levels and routing.

**2. Confusing Layout with Appender.** `PatternLayout` does not choose stdout; `Console target="SYSTEM_OUT"` does.

**3. Confusing `{}` with `%m`.** Message template placeholders belong to the Log4j2 API; Layout converters belong to the LogEvent formatting stage.

**4. Forgetting `%n` in line-based logs.** Records can run together, making it hard for collectors to process them.

**5. Assuming omitting `%ex` guarantees no stack trace.** PatternLayout has a mechanism that automatically appends an exception converter in certain configurations.

**6. Printing all ThreadContext data without clearing or filtering.** Request data can leak across threads or expose sensitive information.

**7. Manually assembling JSON with PatternLayout.** Easy to get escaping and schema wrong; JsonTemplateLayout is better suited for structured logs.

**8. Using `%L`/`%M` widely without measuring cost.** Caller location has significant overhead.

**9. Changing the Layout but forgetting the collector.** The pipeline may fail to parse logs even though the application still runs.

**10. Treating RollingFile configuration as part of the Layout.** Rotation and retention are Appender policies, not pattern settings.

**11. Adding only `log4j-api` while trying to use JsonTemplateLayout.** You need Core and the corresponding Layout dependency.

**12. Treating a JSON log line as official transaction evidence.** Logs can be filtered, lost, duplicated, or delayed; reconcile against business sources of truth when exact numbers are required.

## 15. Self-Check Questions

1. **What is a Layout used for?** Representing a LogEvent as text/JSON or another format before an Appender writes it.
2. **How does an Appender differ from a Layout?** An Appender determines the destination; a Layout determines the format.
3. **Does `%-5p` truncate `ERROR` or `WARNING` to 5 characters?** No; it specifies minimum width and left alignment.
4. **Is `%m` in PatternLayout the same as `{}` in `LOG.info`?** No; one retrieves the message, while the other substitutes parameters in the message template.
5. **What is used to insert a newline between events?** `%n`.
6. **What is used to print the `request_id` from ThreadContext?** `%X{request_id}`.
7. **Does changing Console target from `SYSTEM_OUT` to `SYSTEM_ERR` require editing the Layout?** No; that is an Appender configuration.
8. **Which dependency must be added to use JsonTemplateLayout?** `log4j-layout-template-json` with a version compatible with Log4j2 Core.
9. **Where does `"$resolver"` appear?** In a JSON event template, to select which LogEvent attribute to encode.
10. **Should you build JSON with PatternLayout?** Not for serious structured logging; it is error-prone for escaping, types, and schema.
11. **Does `%ex` require a Throwable in the LogEvent?** Yes; the converter does not generate error causes on its own.
12. **Does omitting `%ex` guarantee no stack trace is printed?** No; PatternLayout may append an exception converter depending on configuration.
13. **Does `%enc{%m}{CRLF}` automatically remove sensitive tokens?** No; it handles CR/LF in the message and does not mask secrets.
14. **Do two Appenders receiving the same LogEvent mean two transactions?** No, just two output copies of one event.
15. **Will a JSON file in a container automatically appear on a dashboard if the collector only reads stdout?** No; the proper source must be wired up.
16. **Why should you think twice before using `%L` or `%M`?** They may require caller location and increase overhead.

**Takeaway:** **LogEvent is the event data, Appender decides where to output, and Layout decides how to represent it.** For human readers, PatternLayout is concise and readable; for structured JSON pipelines, JsonTemplateLayout provides a clear schema. Always preserve context, exceptions, timestamps, and data safety when designing a Layout, and verify the output under real runtime configuration.
