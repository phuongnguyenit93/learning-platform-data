# Thread Names in Java Logging

## 1. What is a thread name and why does it matter?

In Java, every `Thread` object has a **thread name** of type `String`. This name helps humans identify which thread is executing a piece of code when reading logs, thread dumps, debugger views, or monitoring tools.

An application can perform many tasks concurrently. Log lines interleave over time; if only the log level and message are present, it is very hard to tell which lines belong to the same thread. For example:

```text
14:20:01.123 [orders-worker-1] INFO  OrderService - Started order 101
14:20:01.125 [orders-worker-2] INFO  OrderService - Started order 102
14:20:01.130 [orders-worker-1] INFO  OrderService - Finished order 101
```

The name `orders-worker-1` helps you see that the first and third lines were emitted by the same worker. **That alone does not prove they belong to the same request:** a thread pool can reuse a worker to process many different tasks.

A thread name is a **diagnostic label**, not a business identifier, request ID, trace ID, or synchronization mechanism. Names can be changed, and multiple threads can share the same name if the program sets them that way.

## 2. Related Java APIs

| API | Purpose | Notes |
| --- | --- | --- |
| `Thread.currentThread()` | Gets the `Thread` object running the current code | Used in logging code to identify the thread emitting the event |
| `thread.getName()` | Reads the current name of the thread | Returns a `String`, not guaranteed to be unique |
| `thread.setName("...")` | Changes the name of an already created thread | Affects subsequent name reads; be careful when threads are reused |
| `new Thread(runnable, "name")` | Creates a platform thread with the specified name | Suitable when you own the thread lifecycle |
| `ThreadFactory` | Defines how threads created by an executor are named | The appropriate approach for thread pools |
| `Thread.ofVirtual().name(...)` | Sets the name of a virtual thread | Available since Java 21; does not compile on Java 17 |

Default names generated by the JDK or frameworks may look like `main`, `Thread-0`, `pool-1-thread-1`, or `ForkJoinPool.commonPool-worker-1`. **Do not rely on a specific default naming pattern** for application logic: the JDK, executor, and application configuration may produce different patterns.

Calling `getName()` only reads thread metadata. It does not change scheduling, priority, or the thread's execution state. Calling `setName()` likewise does not make a task run faster or create a new thread.

## 3. Java 17 example: naming a thread directly

Save the following code as `ThreadNameDemo.java`:

```java
public class ThreadNameDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(
                () -> System.out.println(
                        "Running in: " + Thread.currentThread().getName()),
                "orders-worker-1"
        );

        worker.start();
        worker.join();

        System.out.println(
                "Running in: " + Thread.currentThread().getName());
    }
}
```

Compile and run:

```bash
javac ThreadNameDemo.java
java ThreadNameDemo
```

`stdout`:

```text
Running in: orders-worker-1
Running in: main
```

Explanation:

1. The constructor `new Thread(task, "orders-worker-1")` attaches the name to the thread before it runs.
2. `start()` asks the JVM to launch the task on the new thread; `Thread.currentThread()` inside the lambda is the `orders-worker-1` thread.
3. `join()` waits for the worker to finish, so the order of the two output lines in this example is deterministic.
4. The `Thread.currentThread()` call after `join()` runs on `main`, so it prints `main`.

In real applications, the logging framework usually adds the thread name automatically; there is no need to manually concatenate `Thread.currentThread().getName()` into every message.

## 4. Displaying the thread name in logs

### 4.1. Logback with SLF4J

When an application uses **SLF4J + Logback**, a sample `src/main/resources/logback.xml` configuration might look like this:

```xml
<configuration>
    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>
    <root level="INFO">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
```

In this pattern:

- `%d{HH:mm:ss.SSS}`: the timestamp when the log event was created.
- `[%thread]`: the name of the thread associated with the log event; Logback also supports the shorthand `%t`.
- `%-5level`: the log level, left-aligned to a minimum width of five characters.
- `%logger{36}`: the abbreviated logger name; `%msg%n`: the message and a newline.

The logger usage below **illustrates a class in a project already configured with SLF4J/Logback**, not a standalone JDK-only program:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class OrderService {
    private static final Logger log =
            LoggerFactory.getLogger(OrderService.class);

    public void process(long orderId) {
        log.info("Processing order {}", orderId);
    }
}
```

When `process(101)` runs on a thread named `orders-worker-1`, a log line might look like this (the timestamp is illustrative only):

```text
14:20:01.123 [orders-worker-1] INFO  OrderService - Processing order 101
```

Each logging framework has its own configuration syntax; the `%thread` pattern above is specific to **Logback**. The logger configuration, dependencies, and appender must be present in the project for this pattern to take effect.

### 4.2. When should you explicitly record the thread name?

Enable the thread name field in pattern or structured logging when you need to investigate race conditions, thread pools, background processing, deadlocks, or asynchronous operations. With JSON logs, write the name into a dedicated field such as `thread.name` or `threadName` so you can filter by attribute; the exact field name depends on your system's logging schema.

Do not use thread names to store sensitive information: they can appear in logs, thread dumps, and monitoring tools.

## 5. Naming a thread pool with ThreadFactory

In server applications, **an executor usually manages the thread lifecycle**. Therefore, instead of creating `new Thread(...)` for each task, provide a `ThreadFactory` when building the executor. A consistent name like `report-worker-1`, `report-worker-2` makes the pool's role and the worker's sequence number clear.

Standalone Java 17 example, saved as `NamedThreadPoolDemo.java`:

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.ThreadFactory;
import java.util.concurrent.atomic.AtomicInteger;

public class NamedThreadPoolDemo {
    public static void main(String[] args) throws Exception {
        AtomicInteger nextNumber = new AtomicInteger(1);
        ThreadFactory defaults = Executors.defaultThreadFactory();
        ThreadFactory namedFactory = task -> {
            Thread thread = defaults.newThread(task);
            thread.setName("report-worker-" + nextNumber.getAndIncrement());
            return thread;
        };

        ExecutorService executor =
                Executors.newSingleThreadExecutor(namedFactory);
        try {
            Future<String> first = executor.submit(() ->
                    "job-A: " + Thread.currentThread().getName());
            Future<String> second = executor.submit(() ->
                    "job-B: " + Thread.currentThread().getName());

            System.out.println(first.get());
            System.out.println(second.get());
        } finally {
            executor.shutdown();
        }
    }
}
```

Run:

```bash
javac NamedThreadPoolDemo.java
java NamedThreadPoolDemo
```

`stdout`:

```text
job-A: report-worker-1
job-B: report-worker-1
```

This is a **single-thread executor**, so both tasks are processed sequentially on the same reused worker. `Future.get()` also ensures the results are ready before printing. If you switch to `Executors.newFixedThreadPool(2, namedFactory)`, the runtime may create `report-worker-1` and `report-worker-2`, but **the assignment order of tasks to individual threads is not guaranteed**; do not write tests that depend on that order.

`AtomicInteger` is used because `ThreadFactory.newThread(...)` may be called from multiple threads. Wrapping `Executors.defaultThreadFactory()` preserves sensible defaults from the base factory while customizing only the name. Always manage the executor lifecycle and call `shutdown()` when it is no longer needed.

## 6. Temporarily renaming a worker: always restore it

A thread in a pool may serve request A and then request B. If you rename the thread to `request-A` without restoring it, logs for request B may still carry request A's name, leading to confusion during investigation.

Standalone Java 17 example, saved as `TemporaryThreadNameDemo.java`:

```java
public class TemporaryThreadNameDemo {
    public static void main(String[] args) {
        Thread current = Thread.currentThread();
        String originalName = current.getName();

        try {
            current.setName("batch-export-42");
            System.out.println("Inside: " + current.getName());
        } finally {
            current.setName(originalName);
        }

        System.out.println("After: " + current.getName());
    }
}
```

Run:

```bash
javac TemporaryThreadNameDemo.java
java TemporaryThreadNameDemo
```

`stdout`:

```text
Inside: batch-export-42
After: main
```

The `try/finally` pattern guarantees the name is restored even if the task throws an exception. However, if the goal is to track a **request ID**, use a proper logging context mechanism rather than renaming the thread for each request; the thread name is primarily meant to describe the worker or execution role.

## 7. Thread names in asynchronous tasks

When work crosses thread boundaries, **the thread name can change** even within the same business flow:

- `ExecutorService.submit(...)`: the name comes from the thread chosen by the executor.
- `CompletableFuture.supplyAsync(...)` without an `Executor`: by default it typically runs on `ForkJoinPool.commonPool()` (under suitable execution conditions), so the name does not necessarily match the calling thread.
- `CompletableFuture.supplyAsync(..., executor)`: the name reflects a worker from the provided executor.
- Web frameworks, schedulers, and reactive libraries may hop across multiple threads; each log line displays the thread that actually emitted that event.

An example sequence of events might look like:

```text
[http-worker-3]  INFO  Request accepted
[report-worker-2] INFO  Report generated
[http-worker-3]  INFO  Response returned
```

From the thread name alone, **you cannot conclude** that those three lines belong to the same request. Use a correlation ID / trace ID to link them together.

### Virtual threads (Java 21+)

A virtual thread is also a `Thread` and has `getName()`. Do not assume every virtual thread has a human-readable auto-generated name: the creation configuration may leave the name empty. You can set the name directly for easier diagnostics.

**Java 21+** specific example, saved as `VirtualThreadNameDemo.java`:

```java
public class VirtualThreadNameDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread virtualWorker = Thread.ofVirtual()
                .name("virtual-report-1")
                .start(() ->
                        System.out.println(Thread.currentThread().getName()));

        virtualWorker.join();
    }
}
```

```bash
javac VirtualThreadNameDemo.java
java VirtualThreadNameDemo
```

`stdout`:

```text
virtual-report-1
```

The name here is the name of the **virtual thread executing the task**, not the carrier/platform thread supporting it. A virtual thread may be mounted on different carrier threads over time. On Java 17, this example will not compile because the `Thread.ofVirtual()` API does not exist.

## 8. Thread names vs. MDC/trace ID: two different purposes

| Data | Question answered | Limitations |
| --- | --- | --- |
| Thread name | "Which worker is running this code?" | A worker can handle multiple requests; one request can use multiple workers |
| MDC `requestId` | "Which logical request/task does this log line belong to?" | Must be attached, propagated across async boundaries, and cleaned up |
| Trace ID | "Which operations are related across threads/services?" | Requires tracing/correlation instrumentation |

With SLF4J MDC, the following code is **an integration snippet** requiring SLF4J and a logging backend that supports MDC:

```java
import org.slf4j.MDC;

MDC.put("requestId", requestId);
try {
    log.info("Starting calculation");
    performCalculation();
} finally {
    MDC.remove("requestId");
}
```

If using Logback, you can add `%X{requestId}` to the pattern, for example:

```text
%d{HH:mm:ss.SSS} [%thread] [request=%X{requestId}] %-5level %logger - %msg%n
```

In common logging systems, MDC is bound to the thread's execution context and **is not automatically propagated to every executor or `CompletableFuture`**. When switching threads, you need a propagation mechanism designed for your framework; when workers are reused, you must clear MDC in `finally` to avoid context leaks. `requestId`, `log`, and `performCalculation()` in the snippet above are application variables/methods, not a standalone runnable class.

## 9. Useful naming conventions

An easy-to-read name usually consists of **role + sequence number**, such as `billing-worker-1`, `email-sender-2`, or `scheduler-cleanup-1`. With multiple pools, give each pool a distinct prefix. Keep names short, stable, consistent, and easy to search; if you must include a task identifier in a temporary name, restore it after execution.

Avoid manually assigning generic names like `Thread-1` across multiple pools, as they are hard to distinguish. Do not put passwords, tokens, customer emails, or personal data into thread names. Do not build business logic such as `if (thread.getName().contains("admin"))`: the name is mutable data and guarantees neither uniqueness nor authorization.

When analyzing multithreaded issues, combine **timestamp + level + logger + thread name + request/trace ID**. Thread dumps and JFR help you see which threads are waiting on locks, running, or blocked; logs help you trace the sequence of events.

## 10. Common pitfalls and how to verify

1. **Thread name missing from logs:** check whether your logging backend's pattern/appender includes `%thread` or the equivalent field; calling `setName()` alone does not make it appear in logs.
2. **Every task has the same name:** a single-thread executor intentionally reuses one worker. In a fixed pool, the number of names depends on how many workers have been created; do not infer the number of tasks from the number of distinct names.
3. **Thread name "leaks" from a previous task:** you may have renamed a pooled thread and forgotten to restore it in `finally`.
4. **Log lines for one request show different names:** the request may have crossed an executor, callback, scheduler, or event loop. Use a correlation ID or trace ID to tie them together.
5. **Confusing thread name with a unique identifier:** two different `Thread` instances can have the same name, and a name can also change at runtime.
6. **Flaky tests:** tasks running concurrently do not guarantee log ordering; use `join()`, `Future.get()`, or appropriate synchronization primitives to establish completion points in tests.
7. **Stale MDC on the next request:** clean up MDC and propagate context properly across async tasks. Renaming the thread does not solve MDC propagation.

**Quick self-check:** When you see `[report-worker-1] Finished task` in a log, you can conclude the event was recorded by a worker named `report-worker-1`. From that alone, you cannot conclude which request the task belonged to, whether that worker is unique in the system, or whether the thread will continue handling the same request. Rely on correlation IDs and safely logged business context as well.
