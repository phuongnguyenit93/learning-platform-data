# MDC trong async Java Logging: truyền ngữ cảnh đúng khi đổi thread

## 1. MDC là gì và vì sao async gây nhầm lẫn?

**MDC (Mapped Diagnostic Context)** là cơ chế gắn các cặp khóa–giá trị vào ngữ cảnh logging của luồng thực thi, để nhiều log event của cùng một request, job hoặc operation mang các trường tương quan mà không phải nối ID thủ công vào từng message.

Ví dụ một request thanh toán:

```text
INFO  req=req-42 op=op-17 - event=checkout_started
INFO  req=req-42 op=op-17 - event=payment_authorized
WARN  req=req-42 op=op-17 - event=inventory_retry attempt=2
INFO  req=req-42 op=op-17 - event=checkout_finished
```

Ở đây `req-42` và `op-17` là **ngữ cảnh của request/operation**, không phải thuộc tính cố định của logger. Nếu không có correlation ID, các dòng từ hàng trăm request chạy đồng thời sẽ rất khó liên kết.

Một ví dụ SLF4J:

```java
import org.slf4j.MDC;

// Snippet trong method có LOG là org.slf4j.Logger:
MDC.put("requestId", "req-42");
try {
    LOG.info("event=checkout_started");
    LOG.info("event=checkout_finished");
} finally {
    MDC.remove("requestId");
}
```

Đoạn trên **chưa phải một chương trình Java độc lập**; nó giả định đã có logger `LOG`. `MDC.put` thường lưu giá trị trong context gắn với thread hiện hành, còn encoder/layout quyết định có hiển thị `requestId` hay không.

Khi chương trình có xử lý bất đồng bộ, cần trả lời hai câu khác nhau:

1. **Log được ghi ra đích trên thread khác** vì có AsyncAppender/AsyncLogger: MDC của sự kiện có còn đúng không?
2. **Nghiệp vụ thực thi trên thread khác** vì có `ExecutorService`, `CompletableFuture`, scheduler, callback, reactive pipeline hay message consumer: thread mới nhận MDC từ đâu?

Hai tình huống này **không tương đương**. Nắm rõ ranh giới giữa *phát sự kiện log* và *chuyển công việc nghiệp vụ* là chìa khóa tránh mất/trộn MDC.

## 2. Hai loại bất đồng bộ phải phân biệt

### 2.1. Async logging: chuyển việc xuất log sang worker

Với Logback `AsyncAppender`, thread của request tạo event và đưa event vào queue; thread appender xử lý việc ghi console/file sau đó:

```text
REQUEST THREAD                         LOGGING WORKER
  |
  | MDC: requestId=req-42
  |      operationId=op-17
  |
  +-- LOG.info("event=started")
        |
        +-- Tạo logging event
        +-- Chuẩn bị dữ liệu cho xử lý hoãn
        +-- Snapshot MDC cần thiết
        +-- Enqueue ----------------------> Dequeue event
                                            |
                                            +-- Encoder đọc MDC
                                            |   đã gắn vào event
                                            +-- Ghi console/file
  |
  +-- MDC.clear() trong finally
```

Ở Logback Classic, `AsyncAppender` chuẩn bị `ILoggingEvent` cho việc xử lý hoãn, trong đó dữ liệu MDC của event được lấy trong ngữ cảnh phát log trước khi worker ghi. Vì vậy **caller dọn MDC sau lời gọi logging không nhất thiết làm mất MDC của event đã được enqueue**.

Đây là hành vi của cơ chế Logback đang xét. **Không được suy rộng rằng mọi appender tùy chỉnh, formatter tự viết hoặc backend khác đều tự snapshot MDC giống hệt**. Nếu xây appender riêng, phải kiểm tra API/contract của event và thời điểm lấy context.

### 2.2. Async business work: chuyển công việc sang thread khác

Với `ExecutorService`:

```text
REQUEST THREAD                         BUSINESS WORKER
  |
  | MDC requestId=req-42
  |
  +-- executor.submit(task) -----------> run task
                                           |
                                           | MDC.get("requestId") ?
                                           | Không mặc định = req-42
                                           |
                                           +-- LOG.info("event=worker_done")
```

`MDC` dựa trên context adapter thường gắn với thread, nên **một task chạy trên thread khác không tự động nhận snapshot của caller**. Nếu worker dùng thread pool, nó có thể có:

- MDC trống.
- MDC còn sót từ một task trước bị dọn sai.
- MDC do framework hoặc thư viện khác chủ động đặt.
- MDC được truyền đúng bởi middleware/context propagation integration mà ứng dụng đã cấu hình.

Do đó, với nghiệp vụ async cần một quy tắc **capture → install → execute → restore** ở ranh giới task, hoặc tích hợp propagation chính thức của framework.

### 2.3. Cả hai loại async có thể cùng xuất hiện

```text
HTTP request thread
  | MDC=req-42
  |
  +-- submit business task ------------------------+
                                                   |
                                                   v
                                              Worker thread
                                              MDC=? nếu không propagate
                                                   |
                                                   +-- LOG.info(...)
                                                          |
                                                          v
                                              AsyncAppender queue
                                                          |
                                                          v
                                              Logging worker -> file
```

Ngay cả khi `AsyncAppender` bảo toàn MDC **của event ở worker**, event đó vẫn có thể chứa **MDC rỗng ngay từ khi được phát**, nếu business worker chưa được cấp context. Backend không thể khôi phục `requestId` chưa từng gắn vào sự kiện.

**Quy tắc ghi nhớ:** AsyncAppender bảo toàn *event context* theo cơ chế của nó; context propagation phải đưa *execution context* đến đúng nơi event được tạo.

## 3. Những thành phần tạo thành MDC context

Một bản log có thể cần:

| Field | Ý nghĩa | Ví dụ |
|---|---|---|
| `requestId` | Liên kết các log trong một request | `req-42` |
| `operationId` | Liên kết các event của một operation nghiệp vụ | `op-17` |
| `parentOperationId` | Quan hệ cha–con của thao tác | `op-16` |
| `jobId` | Định danh job nền | `job-104` |
| `traceId` | Định danh distributed trace | Giá trị do tracing SDK cung cấp |
| `spanId` | Định danh span trong trace | Giá trị do tracing SDK cung cấp |
| `tenantId` | Tenant đang xử lý, khi được phép lưu log | `tenant-A` |
| `attempt` | Lần thử lại | `2` |

**Không phải mọi field đều nên đưa vào MDC.** MDC truyền thống thường là map **`String → String`**; những giá trị phức tạp hoặc số cần được biểu diễn theo quy ước nhất quán. Với JSON structured logging, encoder có thể bổ sung các field có kiểu rõ hơn từ API/event model.

- `requestId` không nhất thiết là `traceId`.
- `operationId` không nhất thiết là `spanId`.
- Một request có thể tạo nhiều operations.
- Một operation có thể không xuất phát từ HTTP request (batch, cron, queue).
- Giá trị MDC có thể được copy vào event nhưng không biến thành field JSON trừ khi encoder được cấu hình để xuất chúng.

Giữ **tên key ổn định**, tránh key tạo từ ID động. Ví dụ nên dùng `"operationId" → "op-17"`, không tạo key `"operation_op-17"`.

## 4. Cơ chế MDC trong SLF4J và Logback

Với SLF4J:

```java
import org.slf4j.MDC;

MDC.put("requestId", "req-42");

String requestId = MDC.get("requestId");

java.util.Map<String, String> snapshot =
        MDC.getCopyOfContextMap();

MDC.remove("requestId");
MDC.clear();
```

Đây là **các lời gọi API minh họa**. Không nên thực hiện tất cả theo chuỗi như một workflow production mà không hiểu effect; `remove` xóa một key, `clear` xóa toàn bộ MDC của thread hiện tại, còn `getCopyOfContextMap` trả snapshot map hoặc `null` nếu không có map.

### 4.1. Context là dữ liệu của từng thread

Nhiều SLF4J MDC adapters sử dụng dữ liệu gắn với thread. Những event phát trên cùng thread sẽ nhìn thấy MDC được đặt tại thời điểm phát log, trừ khi framework/backend xử lý context theo cách khác.

Đừng nhầm `ThreadLocal` với biến global. Nếu dùng một `static Map` dùng chung cho requestId rồi thay đổi ở từng request, request A có thể bị gắn ID của B khi chạy đồng thời. MDC tách context theo thread hoặc theo abstraction của adapter, nhưng vẫn phải quản lý vòng đời.

### 4.2. Lấy snapshot không phải chuyển quyền sở hữu vĩnh viễn

`MDC.getCopyOfContextMap()` là API quan trọng: nó trả về **bản sao dữ liệu key/value tại một thời điểm**, thường dưới dạng `Map<String, String>` hoặc `null`. Sau đó có thể:

- Truyền snapshot vào một task.
- Cài bằng `MDC.setContextMap(snapshot)` khi task chạy.
- Dùng `MDC.clear()` khi snapshot null.
- Khôi phục context trước của worker trong `finally`.

Snapshot khác với việc giữ một tham chiếu đến map mutable đang được các request sửa liên tục. Tuy vậy, nếu chính bạn lưu snapshot vào một map mutable và tiếp tục sửa nó, bạn vẫn có nguy cơ tạo race ở application code; tốt nhất coi snapshot là read-only hoặc tạo bản sao bất biến hợp lệ trước khi chuyển.

### 4.3. Provider/backend thật ở runtime mới quyết định hành vi

`SLF4J API` là facade. `MDC` đi qua `MDCAdapter` của provider/runtime. Nếu chạy với Logback Classic, nhiều tính năng MDC được hỗ trợ; nếu dùng backend khác, simple/NOP provider hoặc một bridge đặc thù, cách lưu/truy xuất có thể khác. Không kết luận “SLF4J có MDC nên mọi provider và mọi JSON encoder chắc chắn xuất field”.

Hãy kiểm tra version `slf4j-api`, provider/backend, layout/encoder và cảnh báo lúc khởi động. Với SLF4J 2.x, dùng provider tương thích 2.x, không ghép ngẫu nhiên binding của 1.7.

## 5. Điều xảy ra khi AsyncAppender nhận event có MDC

Logback Classic `AsyncAppender` có nhiệm vụ:

1. Nhận event từ caller nếu nó đã vượt qua logger level/filter.
2. Chuẩn bị dữ liệu cần thiết cho xử lý hoãn.
3. Đưa event vào queue; có thể chặn hoặc bỏ event tùy chính sách.
4. Worker lấy event, chuyển cho appender đích.
5. Encoder/layout của đích đọc context được gắn với event và ghi ra console/file.

Ví dụ luồng:

```text
Thread A: MDC.put("requestId", "req-42")
Thread A: LOG.info("event=started")
Thread A: MDC.clear()

Logback async worker:
  event.getMDCPropertyMap() -> dữ liệu requestId=req-42
  encoder %X{requestId}   -> "req-42"
```

**Chú ý:** đây là mô tả logic của **Logback AsyncAppender/ILoggingEvent**, không phải khẳng định rằng khi gọi `MDC.get("requestId")` ngay trên logging worker sẽ trả `req-42`. Encoder có thể lấy MDC từ **event snapshot**, trong khi thread-local MDC thực của logging worker vẫn không mang ID đó.

### 5.1. Snapshot có nghĩa gì với thay đổi sau khi log?

```java
// Minh họa: LOG là SLF4J Logger.
MDC.put("requestId", "req-42");
LOG.info("event=first");

MDC.put("requestId", "req-99");
LOG.info("event=second");
MDC.clear();
```

Trong Logback AsyncAppender chuẩn, các event được chuẩn bị để xử lý hoãn, nên `first` giữ context ở thời điểm phát event thứ nhất, `second` giữ context ở thời điểm thứ hai; không phải cùng đọc giá trị `req-99` sau khi queue được xả.

Nếu tự thiết kế appender chỉ giữ một tham chiếu mutable tới context thay vì snapshot, điều đó có thể **không đúng**. Khi viết custom encoder/appender, kiểm thử thay đổi MDC ngay sau `LOG.info` để phát hiện lỗi.

### 5.2. AsyncAppender không giải quyết mọi việc

- Nếu mã nghiệp vụ phát log từ thread chưa có MDC, event vẫn thiếu ID.
- Nếu level/filter đã loại event, không có event để snapshot.
- Nếu queue đầy và chính sách drop, event có thể bị bỏ dù MDC đầy đủ.
- Nếu process chết khi event còn trong queue, event có thể mất.
- Nếu encoder chỉ in `%msg` mà không in `%X{requestId}`, context có thể tồn tại trong event nhưng không hiển thị.
- Nếu collector chỉ parse message string, MDC có thể không thành structured fields.

**Bảo toàn MDC của một event không đồng nghĩa bảo đảm event được giao đến collector.**

## 6. Cấu hình Logback AsyncAppender và MDC

Ví dụ `logback.xml`:

```xml
<configuration>
    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <pattern>%level req=%X{requestId} op=%X{operationId} - %msg%n</pattern>
        </encoder>
    </appender>

    <appender name="ASYNC"
              class="ch.qos.logback.classic.AsyncAppender">
        <queueSize>64</queueSize>
        <discardingThreshold>0</discardingThreshold>
        <neverBlock>false</neverBlock>
        <maxFlushTime>0</maxFlushTime>
        <includeCallerData>false</includeCallerData>
        <appender-ref ref="CONSOLE"/>
    </appender>

    <root level="INFO">
        <appender-ref ref="ASYNC"/>
    </root>
</configuration>
```

Đây là file cấu hình **Logback Classic**, không phải `logging.properties` của JUL hoặc `log4j2.xml` của Log4j 2.

| Thuộc tính | Ý nghĩa | Liên hệ với MDC |
|---|---|---|
| `queueSize` | Số event tối đa chờ trong queue | Backlog có thể giữ nhiều event kèm MDC snapshot, tăng memory |
| `discardingThreshold` | Ngưỡng cho phép bỏ có chọn lọc những mức log ít quan trọng khi gần đầy | Bị drop nghĩa là mất toàn bộ event, kể cả context |
| `neverBlock` | Nếu true, không chờ queue đầy; có thể drop event | Chọn latency hay độ đầy đủ của log, không phải lựa chọn propagation |
| `maxFlushTime` | Giới hạn thời gian chờ xả queue khi stop, thường tính ms | Stop quá sớm có thể để lại event chưa ghi; 0 trong Logback có nghĩa chờ không giới hạn |
| `includeCallerData` | Có thu caller class/method/file/line không | Caller data khác với MDC; bật có thể tốn chi phí tìm stack |
| `appender-ref` | Appender đích mà worker chuyển event đến | Encoder đích phải được cấu hình để in/export MDC |
| `root level="INFO"` | Lọc DEBUG/TRACE dưới ngưỡng | Level policy không tự sinh MDC |

Trong nhiều phiên bản Logback Classic, `discardingThreshold` mặc định tạo cơ chế ưu tiên WARN/ERROR hơn TRACE/DEBUG/INFO khi gần đầy. Đặt `0` tắt kiểu discard theo ngưỡng đó, **nhưng không bảo đảm không mất log vì crash, lỗi sink hoặc chính sách khác**.

Với `neverBlock=false`, khi queue đầy caller có thể bị chặn cho tới khi có chỗ. Với `neverBlock=true`, event có thể bị bỏ nếu enqueue thất bại, kể cả level cao trong tình huống queue đầy. Cần đo p99 latency, queue depth, dropped events và chính sách shutdown.

### 6.1. Tránh duplicate output

Nếu `ASYNC` bọc `CONSOLE`, root **chỉ nên gắn `ASYNC`** trong cấu hình đơn giản này. Nếu root tham chiếu cả `ASYNC` và `CONSOLE`, một event có thể đi hai đường và xuất hai lần.

### 6.2. MDC có tự được thêm vào pattern không?

Không. Pattern cần `%X{requestId}` hoặc cú pháp tương ứng, hoặc một JSON encoder được thiết lập để xuất MDC. Nếu chỉ dùng:

```xml
<pattern>%level - %msg%n</pattern>
```

sự kiện vẫn có thể có MDC bên trong nhưng output text không hiển thị `requestId`. Đừng kết luận context bị mất trước khi kiểm tra chính xác encoder/layout.

## 7. Ví dụ Java 17 + Maven chạy được: MDC qua cả hai lớp async

Ví dụ này dùng **Java 17**, **SLF4J 2.x**, **Logback Classic** và `ExecutorService`. Mục tiêu:

- Đặt `requestId=req-42`, `operationId=op-17` ở thread chính.
- Phát một event để Logback AsyncAppender enqueue với MDC hiện tại.
- Mở một operation con `op-18` rồi **khôi phục op-17** sau scope.
- Truyền snapshot MDC **tường minh** sang business worker trong thread pool.
- Business worker phát event, Logback worker xử lý async nhưng vẫn giữ context đúng.
- Sau worker task, **chứng minh worker thread không bị rò MDC**.
- Dừng `LoggerContext` để xả queue, rồi in kết quả kiểm tra worker.
- Giữ **stdout có thể đối chiếu được** bằng cách chờ task hoàn thành và stop appender trước dòng kiểm tra cuối.

**Ví dụ chỉ dành cho môi trường demo/giáo dục**. Trong ứng dụng web dài hạn, framework quản lý lifecycle logging; không stop logger context sau mỗi request.

### 7.4. Tệp `src/main/java/com/example/logging/MdcAsyncDemo.java`

```java
package com.example.logging;

import ch.qos.logback.classic.LoggerContext;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public final class MdcAsyncDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(MdcAsyncDemo.class);

    private static void install(Map<String, String> context) {
        if (context == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }

    /**
     * Scope cài context mới và khôi phục context trước khi đóng.
     * Có thể lồng: đóng scope con trả lại giá trị của scope cha.
     */
    private static final class MdcScope implements AutoCloseable {
        private final Map<String, String> previous;
        private boolean closed;

        private MdcScope(Map<String, String> next) {
            previous = MDC.getCopyOfContextMap();
            install(next);
        }

        @Override
        public void close() {
            if (closed) {
                return;
            }
            install(previous);
            closed = true;
        }
    }

    /**
     * Capture MDC tại thread submit, install ở thread chạy task,
     * sau đó restore context cũ của thread worker.
     */
    private static Runnable withMdc(
            Map<String, String> captured, Runnable task) {
        return () -> {
            try (MdcScope ignored = new MdcScope(captured)) {
                task.run();
            }
        };
    }

    public static void main(String[] args) throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();
        boolean workerContextClean = false;

        try {
            Map<String, String> root = Map.of(
                    "requestId", "req-42",
                    "operationId", "op-17");

            try (MdcScope rootScope = new MdcScope(root)) {
                LOG.info("event=checkout_started");

                Map<String, String> child = Map.of(
                        "requestId", "req-42",
                        "operationId", "op-18");

                try (MdcScope childScope = new MdcScope(child)) {
                    LOG.info("event=inventory_reserved");
                }

                // Scope con đóng: caller đã trở lại op-17.
                Map<String, String> snapshot =
                        MDC.getCopyOfContextMap();

                Future<?> payment = executor.submit(
                        withMdc(snapshot, () ->
                                LOG.info("event=payment_authorized")));
                payment.get();

                LOG.info("event=checkout_finished");
            }

            // Cùng một worker thread được dùng lại, nhưng không còn
            // requestId/operationId do wrapper đã restore MDC.
            Future<Boolean> noLeak = executor.submit(
                    () -> MDC.get("requestId") == null
                            && MDC.get("operationId") == null);
            workerContextClean = noLeak.get();
        } finally {
            executor.shutdown();

            // Demo ngắn: stop để worker appender xả queue trước khi
            // in dòng kết quả kiểm tra trên cùng System.out.
            LoggerContext context =
                    (LoggerContext) LoggerFactory.getILoggerFactory();
            context.stop();
        }

        System.out.println(
                "workerContextClean=" + workerContextClean);
    }
}
```

### 7.5. Chạy

Trong thư mục `mdc-async-demo` có `pom.xml`, cần JDK 17+, Maven và quyền tải dependency:

```bash
mvn -q compile exec:java
```

**Các dòng stdout do code ứng dụng và Logback appender tạo ra trong tình huống demo bình thường:**

```text
INFO req=req-42 op=op-17 - event=checkout_started
INFO req=req-42 op=op-18 - event=inventory_reserved
INFO req=req-42 op=op-17 - event=payment_authorized
INFO req=req-42 op=op-17 - event=checkout_finished
workerContextClean=true
```

Đây là phần output của chương trình và appender, không cam kết Maven không có thông báo riêng ở mọi môi trường. Trong demo, queue đủ chỗ, `discardingThreshold=0` và `neverBlock=false` nên các event bình thường không bị bỏ vì chính sách drop được minh họa. Việc gọi `LoggerContext.stop()` cho worker cơ hội flush toàn bộ event trước dòng cuối; nếu backend bị lỗi I/O hoặc process bị kill cưỡng bức, không có cam kết output đầy đủ.

### 7.6. Vì sao thứ tự và giá trị MDC đúng?

1. `root` chứa hai key. `MdcScope(root)` cài chúng lên thread main; event đầu xuất `op-17`.
2. `MdcScope(child)` thay operationId thành `op-18` cho event `inventory_reserved`.
3. Scope con được đóng bằng try-with-resources. `close()` **khôi phục snapshot `previous`** nên thread main trở về `op-17`.
4. `snapshot = MDC.getCopyOfContextMap()` được lấy **sau khi đóng child scope**; worker vì thế nhận `req-42/op-17`.
5. `withMdc(...)` mở scope ở business worker, ghi event, rồi tự restore MDC của thread worker trong `close()`.
6. `payment.get()` đợi event business worker **được gọi LOG.info** xong trước khi caller phát `checkout_finished`; nó **không phải** xác nhận collector đã ghi. Queue Logback một worker giữ thứ tự các event được enqueue trong demo, còn `context.stop()` xử lý queue trước khi in dòng kiểm tra.
7. Scope root đóng, không để lại `req-42/op-17` trên thread main; worker được dùng lại để kiểm tra hai key và cho kết quả `true`.
8. `LOG.info` dùng SLF4J API; `ASYNC` của Logback giữ MDC snapshot của từng event; `CONSOLE` output `System.out` theo pattern.
9. Trong production, không nên tự tạo mỗi request một `ExecutorService` hoặc dừng `LoggerContext` mỗi lần. Cơ chế này được thu nhỏ để minh họa và kiểm chứng lifecycle.

Nếu bỏ `withMdc(snapshot, ...)` và submit trực tiếp `LOG.info` lên executor, event phát trên worker có thể có MDC rỗng. **AsyncAppender không thể tự bổ sung MDC requestId cho event đã bị tạo thiếu context.**

### 7.7. Điểm cần nhớ về Scope

`MdcScope` giúp khôi phục map toàn bộ, thay vì chỉ gọi `MDC.clear()` sau scope con. Với nested operation, việc clear toàn bộ trong child có thể xóa luôn MDC của parent. Cơ chế restore dựa trên snapshot là một cách an toàn khi quản lý scope đồng bộ.

Giới hạn: `MdcScope` phải được đóng trên **cùng thread nơi nó mở** vì việc restore tác động tới MDC của thread hiện tại. Không truyền một instance scope đang mở từ thread A sang thread B rồi gọi `close` ở B; thay vào đó capture dữ liệu và mở **scope mới** trên B.

## 8. Mẫu wrapper thực tế cho ExecutorService

Trong ứng dụng thật, người ta thường viết một helper nhận `Runnable`/`Callable` và trả về một task đã có propagation. Hai công việc quan trọng:

1. Capture MDC **tại thời điểm submit**, trong caller thread.
2. Restore MDC của worker **trong finally**, kể cả khi task ném exception.

### 8.1. Wrapper cho Runnable

```java
// Snippet trong class tiện ích đã import MDC, Map, Runnable:
static Runnable wrap(Runnable delegate) {
    Map<String, String> captured = MDC.getCopyOfContextMap();

    return () -> {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        try {
            if (captured == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(captured);
            }
            delegate.run();
        } finally {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    };
}
```

**Chỉ là snippet**, không có class/import đầy đủ. Chỉ gọi:

```java
// Giả định executor, LOG, wrap đã tồn tại:
executor.submit(wrap(() -> LOG.info("event=task_done")));
```

Nếu bạn gọi `wrap(...)` **bên trong worker** thay vì tại caller, snapshot sẽ là context ở worker lúc đó, có thể trống hoặc thuộc request khác. Ranh giới capture phải được xác định chính xác.

### 8.2. Wrapper cho Callable có kết quả

```java
// Snippet trong utility class đã import Callable, Map, MDC:
static <T> java.util.concurrent.Callable<T> wrap(
        java.util.concurrent.Callable<T> delegate) {

    Map<String, String> captured = MDC.getCopyOfContextMap();
    return () -> {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        try {
            if (captured == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(captured);
            }
            return delegate.call();
        } finally {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    };
}
```

Dạng này giữ kết quả và exception của `Callable<T>`. Khi `delegate.call()` ném lỗi, `finally` vẫn khôi phục MDC. Không nên bắt exception rồi chỉ ghi log và “nuốt” lỗi nếu API business cần truyền thất bại lên caller.

### 8.3. Wrap từng task hoặc decorate executor?

Nếu hàng trăm call sites dùng `executor.submit`, việc bắt từng developer nhớ `wrap(...)` có thể dễ sai. Một framework có thể cung cấp executor decorator/task decorator/middleware hoặc context propagation integration. Ưu điểm là capture/install/restore được áp dụng tại boundary tập trung.

Nhưng cần kiểm tra chính xác:

- Decorator được áp dụng với `execute`, `submit`, scheduled task và `CompletableFuture` hay chỉ một số API?
- Capture được thực hiện lúc submit hay lúc thread worker thực sự chạy?
- Restore có đảm bảo khi task bị cancel hoặc ném exception?
- Các context khác ngoài MDC (security/tracing/locale) có policy riêng không?
- Có tạo nested scopes đúng, không xóa context của framework không?

Không coi một wrapper cho `Runnable` là giải pháp toàn bộ cho mọi async framework.

## 9. CompletableFuture và các pipeline async

`CompletableFuture.supplyAsync` hoặc `runAsync` có thể chạy trên `ForkJoinPool.commonPool()` nếu không truyền executor, hoặc trên executor được chỉ định. Dù cách nào, không thể giả định MDC của caller tự đi theo task.

Ví dụ:

```java
// Snippet với executor, LOG, wrap() đã tồn tại:
java.util.concurrent.CompletableFuture<Void> job =
        java.util.concurrent.CompletableFuture.runAsync(
                wrap(() -> LOG.info("event=stage_one")),
                executor);

job.join();
```

Điểm cần chú ý:

- `wrap(...)` được gọi tại caller, **trước** khi task được thực thi.
- `join()` đợi công việc hoàn tất nhưng **không đồng nghĩa** async appender/collector đã flush.
- Một chuỗi `thenApplyAsync(...)`, `thenComposeAsync(...)` có thể chạy trên thread khác ở từng stage; cần capture/propagate tại **mỗi boundary** hoặc dùng context-aware executor/integration.
- Callback không có hậu tố `Async` có thể chạy trên thread hoàn thành stage trước; đó cũng không phải contract để dựa vào MDC tình cờ.

Không dùng `InheritableThreadLocal` như một phép sửa đơn giản cho thread pool: worker thường được tạo từ trước và được tái sử dụng, inheritance khi tạo thread không phản ánh context của từng task.

## 10. Reactive streams, scheduler và virtual threads

### 10.1. Reactive pipeline

Trong Reactor/RxJava và những hệ reactive khác, một request có thể chuyển qua nhiều scheduler/thread trên đường xử lý. MDC dựa trên thread dễ bị mất hoặc lẫn ngữ cảnh nếu code chỉ `MDC.put` tại điểm nhận request rồi kỳ vọng mọi operator giữ cùng thread.

Hướng thích hợp là sử dụng **context propagation mechanism** mà reactive framework và hệ tracing/logging của phiên bản đang dùng hỗ trợ. Nhiều framework có request/reactive context độc lập với `ThreadLocal`; logging bridge cần biết lúc nào install/restore MDC tại callback/event.

Không tự gắn `ThreadLocal` ở đầu một pipeline rồi không dọn sau mỗi operator. Đặc biệt nguy hiểm với event loop hoặc thread pool có mức tái sử dụng cao.

### 10.2. Virtual threads

Java 21 cung cấp virtual threads như một tính năng chính thức; bài demo dùng Java 17 nên không sử dụng chúng. Virtual threads cũng có ngữ cảnh thread-local theo API tương ứng, nhưng **không vì vậy mọi context tự động được truyền khi tạo task/virtual thread mới**. Khi dùng concurrency model mới, chọn chính sách propagation phù hợp và đo chi phí của các context entries.

Không suy ra rằng virtual thread luôn tương đương “cùng một request thread” trong mọi callback, hay rằng một MDC adapter đã hỗ trợ tất cả mô hình concurrency từ trước.

### 10.3. Structured concurrency / tracing context

Một số hệ sinh thái cung cấp cơ chế context scoped hoặc task-local khác với SLF4J MDC. Khi tích hợp, cần phân biệt dữ liệu business operation, security principal, locale và trace/span context. MDC **chỉ là lớp log correlation**, không phải nơi lưu state nghiệp vụ chính hoặc thông tin ủy quyền.

Nếu hệ thống dùng OpenTelemetry instrumentation, nên dùng cơ chế context propagation chính thức cho trace/span, rồi cấu hình log correlation để encoder xuất ID hợp lệ. Không tự tạo chuỗi `traceId` rồi gọi đó là distributed tracing.

## 11. MDC trong Log4j 2 async logging

Log4j 2 có **Thread Context** (ví dụ `ThreadContext.put`/`ThreadContext.getImmutableContext`), cùng những cơ chế bất đồng bộ khác nhau như `AsyncAppender` và `AsyncLogger`.

Ví dụ API Log4j 2:

```java
import org.apache.logging.log4j.ThreadContext;

// Snippet: LOG là Log4j 2 Logger:
ThreadContext.put("requestId", "req-42");
try {
    LOG.info("event=started");
} finally {
    ThreadContext.remove("requestId");
}
```

Đoạn này **không phải chương trình độc lập**; cần các dependencies Log4j 2 và `LOG` đúng loại. Nó chỉ cho thấy ý tưởng tương đương: đặt context của thread khi tạo event rồi dọn sau.

Với Log4j 2 PatternLayout, phần context có thể được truy xuất bằng các conversion pattern do Log4j 2 hỗ trợ, chẳng hạn:

```xml
<PatternLayout pattern="%level req=%X{requestId} - %msg%n"/>
```

Đây là **fragment của Log4j 2**, không phải toàn bộ `log4j2.xml`. Cần kiểm tra cả backend/API/version, loại async mechanism và JSON layout đang dùng. Không áp dụng trực tiếp các thuộc tính `discardingThreshold`, `neverBlock` của Logback cho Log4j 2, vì implementation và chính sách đầy queue khác nhau.

### 11.1. Log4j 2 ThreadContext và SLF4J MDC

Khi ứng dụng gọi SLF4J và backend là Log4j 2, `MDCAdapter`/bridge/provider xác định cách context được tích hợp. Không mặc nhiên coi `org.slf4j.MDC` và `org.apache.logging.log4j.ThreadContext` luôn đồng bộ trong mọi topology/version. Chọn một logging API/propagation policy có chủ đích, kiểm thử với provider runtime thực tế.

### 11.2. AsyncLogger vs AsyncAppender

Log4j 2 có kiến trúc `AsyncLogger` khác việc chỉ bọc một appender. Sự khác biệt về queue/ring buffer, thread handoff, snapshot/context và event lifecycle phụ thuộc cấu hình/version. Dù dùng hướng nào, câu hỏi chính vẫn là **event được chụp context ở thread phát log nào** và **business context đã đến thread phát đó chưa**.

Không suy từ tên “async” ra đảm bảo về thứ tự toàn cục, không mất log hoặc tự động propagate context giữa các application tasks.

## 12. MDC, JSON logging và structured fields

Trong output text, một pattern như:

```text
INFO req=req-42 op=op-17 - event=checkout_started
```

giúp người đọc thấy ID, nhưng collector có thể chỉ lưu toàn bộ dòng là một `message`. Nếu muốn truy vấn theo field, nên dùng JSON encoder/layout được cấu hình để xuất MDC/structured arguments dưới dạng các trường riêng:

```json
{
  "timestamp": "2026-11-09T08:15:03.125Z",
  "level": "INFO",
  "service": "orders-api",
  "event": "checkout_started",
  "requestId": "req-42",
  "operationId": "op-17",
  "message": "Checkout started"
}
```

Đây là **schema minh họa**, không phải output của chương trình Maven ở mục 7. `ConsoleAppender` của ví dụ 7 xuất text theo pattern, **không phải JSON**.

Cần kiểm tra:

- JSON encoder có include MDC field hay không.
- Map key MDC được đưa vào top-level hay object nested.
- Field name có xung đột với reserved fields như `level`, `timestamp`, `message` hay không.
- Tên key và value có được allowlist/sanitize đúng không.
- Collector có giữ đúng schema, escaping và dữ liệu liên kết với trace/operation không.
- Một event có thể xuất qua nhiều appenders, tránh duplicate.
- Các field có kiểu phù hợp: MDC thường là string nên `durationMs` trong MDC có thể trở thành `"145"` thay vì number `145`; với số liệu cần truy vấn, dùng structured event API hoặc encoder chuyển kiểu có kiểm soát.

**MDC không tự sinh ra JSON fields.** Nó cung cấp dữ liệu ngữ cảnh cho logging event; encoder quyết định hình thức biểu diễn.

### 12.1. Mỗi dòng một event

Nếu JSON được xuất vào console/file để collector đọc theo dòng, ưu tiên **một JSON object trên một dòng** (JSON Lines/NDJSON). Newline trong message/exception phải được serializer escape trong JSON string, không in stack trace rời rạc ngoài object. Dùng encoder chuẩn thay vì tự nối chuỗi JSON với input người dùng.

### 12.2. Correlation trong collector

Để tìm toàn bộ events thuộc request `req-42`, có thể truy vấn theo field `requestId` nếu collector đã parse. Với log text, cần parser/regex phù hợp; nếu `requestId` chỉ ở message và thay format, query sẽ dễ gãy.

Operation context và trace context có thể được giữ cùng event, nhưng không đồng nhất `requestId`, `operationId`, `traceId` và `spanId`. Chúng mô tả các quan hệ khác nhau trong hệ thống.

## 13. Error, Throwable và dữ liệu MDC bất đồng bộ

Khi ghi lỗi:

```java
// Snippet: LOG là SLF4J Logger, error là Throwable thật.
LOG.error("event=checkout_failed orderId={}", orderId, error);
```

Logger/backend có thể nhận `Throwable` làm cause và đưa exception vào event. MDC cần được gắn trước khi gọi log để record lỗi mang `requestId`/`operationId`.

Nên phân biệt:

- **Throwable**: stack trace, cause chain, suppressed exceptions và thông điệp lỗi.
- **MDC**: ngữ cảnh như request/operation/tenant ID, chủ yếu hỗ trợ correlation.
- **Message parameters**: giá trị điền vào `{}` khi format message.
- **Structured attributes**: field cụ thể có thể được JSON encoder xuất độc lập.

Một event có MDC đúng **không bảo đảm** stack trace được xuất: encoder vẫn phải biết cách render Throwable. Và chỉ log `error.getMessage()` có thể làm mất cause/stack.

### 13.1. Mutable arguments và snapshot

Async appender có thể chuẩn bị message, thread name, MDC tại điểm enqueue, nhưng không nên dựa vào việc mọi backend deep-copy tất cả objects mutable trong arguments. Nếu log một object rồi thay đổi nó ngay sau đó, output có thể phụ thuộc cách backend deferred formatting/serialization.

Đối với định danh cần tương quan, ưu tiên các giá trị immutable như String ID. Không đưa cả một request/entity object vào MDC; MDC map đơn giản được thiết kế cho những trường ngắn, có kiểm soát.

### 13.2. Khi exception xảy ra trong business task

Wrapper MDC phải khôi phục context **dù task thất bại**. Ví dụ:

```java
// Snippet: executor và wrap(...) đã tồn tại.
Future<?> failure = executor.submit(wrap(() -> {
    throw new IllegalStateException("payment failed");
}));

// failure.get() sẽ ném ExecutionException;
 // trong wrap, finally vẫn đã restore MDC worker.
```

Đoạn này chỉ minh họa control flow, không phải chương trình độc lập; ở bài thực tế, caller phải xử lý `ExecutionException`, trả outcome phù hợp và quyết định nơi ghi lỗi tránh duplicate. Nếu log ở worker ngay trong catch, phải giữ scope cho tới khi log event được tạo; đừng clear MDC trước rồi mới log lỗi.

## 14. Bảo mật của MDC khi chạy async

MDC rất tiện nên cũng rất dễ bị lạm dụng. Một khi đặt một key, nhiều log event có thể tự động mang giá trị đó trong suốt scope.

**Không đặt vào MDC**:
- Access token, password, API key, session cookie hoặc raw `Authorization` header.
- Card data, OTP, credential, JDBC URL có mật khẩu.
- Dữ liệu cá nhân không cần thiết hoặc payload đầy đủ.
- Object có kích thước lớn, chuỗi tùy ý không có giới hạn.
- Giá trị người dùng không đáng tin được dùng làm quyền truy cập hoặc logger configuration.

Nên dùng:
- Request/operation ID opaque do hệ thống cấp hoặc được validate.
- Service/route/operation name ổn định.
- Error code, attempt và các ID nghiệp vụ đã được phép ghi.
- Trace/span ID do instrumentation cung cấp đúng chuẩn khi cần.

### 14.1. Context leak cũng là lỗi bảo mật

Nếu worker thread còn giữ `tenantId` hoặc `requestId` của request A, sau đó xử lý request B, log của B có thể gắn nhầm thông tin A. Kết quả là điều tra sai và có thể rò metadata xuyên tenant.

Cách ngăn:

1. Capture một snapshot đã được kiểm tra.
2. Install ở đúng task boundary.
3. Luôn restore giá trị trước trong `finally`.
4. Kiểm tra các callback/exception/cancellation paths.
5. Test thread pool được tái sử dụng và nested scope.

Không gọi `MDC.clear()` bừa bãi trong component con nếu framework/tầng ngoài vẫn đang cần context; khôi phục snapshot trước có thể quan trọng.

### 14.2. JSON escaping khác masking

Encoder JSON giúp escape dấu nháy, backslash, newline và control characters để tạo JSON hợp lệ. Nó **không tự lọc secrets**. Một field `"accessToken":"secret"` vẫn là JSON hợp lệ nhưng là sai về bảo mật.

Áp dụng allowlist/redaction, quyền truy cập log, retention/quota và chính sách vận chuyển dữ liệu.

## 15. Hiệu năng và độ tin cậy

### 15.1. Snapshot MDC có chi phí

Copy MDC map và set lại ở mỗi task tạo allocations và công xử lý, phụ thuộc số field. Đừng nhét hàng trăm key tùy ý vào MDC khi chỉ cần requestId/operationId/traceId.

Nếu application tạo hàng triệu tiny tasks, overhead của propagation có thể đo được. Hãy benchmark theo workload thật, chọn context cần thiết và dùng decorator/integration thích hợp. Nhưng **đừng bỏ propagation chỉ vì muốn giảm vài allocations rồi khiến toàn bộ log không thể correlate**.

### 15.2. AsyncAppender giảm caller blocking nhưng không làm I/O biến mất

Với queue còn chỗ, caller có thể enqueue nhanh rồi tiếp tục xử lý. Khi file/console/collector chậm lâu, queue đầy và producer có thể block/drop. Sử dụng MDC không sửa được bottleneck của sink. Ngược lại, event có MDC khá lớn có thể dùng thêm RAM trong queue.

Theo dõi:
- Queue depth, remaining capacity.
- Dropped/discarded events nếu backend có telemetry.
- Log delivery lag: thời điểm event tạo → collector nhận.
- CPU/heap/GC và logger p95/p99 latency.
- Shutdown drain time, lỗi write/flush và collector health.

### 15.3. MDC không bảo đảm log không mất

Nếu async logging queue drop hoặc process bị kill, event có thể mất dù snapshot MDC hoàn toàn đúng. Với log audit bắt buộc, không dùng in-memory queue làm nguồn chân lý duy nhất; cân nhắc durable audit/event store hoặc transactional outbox tùy hệ thống.

### 15.4. Caller data khác MDC

`includeCallerData=true` trong Logback AsyncAppender yêu cầu thu stack-derived caller metadata như class, method, file, line sớm; việc này có thể tốn CPU. MDC snapshot của requestId/operationId là một vấn đề khác. Đừng bật caller data chỉ vì tưởng đó là công tắc “giữ MDC”.

## 16. Kiểm thử bắt buộc với async MDC

### Test A: caller dọn MDC ngay sau log

Phát event khi MDC là `req-42`, gọi `LOG.info`, rồi clear trong `finally`. Với Logback AsyncAppender chuẩn, kết quả cần chứa req-42 trong event đã enqueue, không đọc nhầm MDC hiện tại của logging worker.

### Test B: task không propagate

Gắn MDC trong main rồi submit một task không có wrapper. Khi worker log, requestId có thể trống. Điều này minh họa vì sao AsyncAppender không sửa lỗi business context propagation.

### Test C: task có wrapper

Capture ở caller, install ở worker, log, restore. Đối chiếu `requestId` ở output, kiểm tra giá trị sau khi task hoàn thành.

### Test D: reuse một worker cho hai requests

Dùng `newSingleThreadExecutor` với request A và B khác ID. Mỗi task phải thấy đúng context của mình. Sau task, kiểm tra worker thread không giữ ID cũ. Đây là test rất quan trọng để phát hiện context leak.

### Test E: nested operation

Root `op-17` mở child `op-18` rồi đóng child. Event tiếp theo phải trở về `op-17`; không được mất root context hoặc giữ child ID.

### Test F: exception và cancellation

Cho task ném exception, trả về sớm, bị interrupt hoặc cancel trong môi trường test. Khẳng định wrapper `finally` vẫn restore nếu task đã bắt đầu và đi qua code; không giả định task bị cancel trước khi chạy đã cài context.

### Test G: queue overload và shutdown

Dùng sink chậm có kiểm soát và queue nhỏ tại môi trường test. Phân biệt event **thiếu MDC** với event **bị drop** hoặc **chưa được flush**; theo dõi status/backend, queue depth, timeout và số event đã đến sink. Không test kiểu crash lên production thiếu kế hoạch an toàn.

### Test H: JSON collector

Kiểm tra raw JSON/event đã có `requestId`/`operationId` chưa, rồi kiểm tra collector parse/index cùng fields. Nếu raw có field nhưng dashboard trống, vấn đề có thể ở schema/parser/index thay vì MDC propagation.

## 17. Troubleshooting: vì sao MDC mất trong async?

| Hiện tượng | Nguyên nhân có thể | Cách khắc phục |
|---|---|---|
| Caller log có reqId, worker task log trống | MDC không tự propagate sang `ExecutorService` | Capture/install/restore tại task boundary |
| AsyncAppender in đúng ID nhưng `MDC.get` ở logging worker trống | Encoder đọc event snapshot, không phải worker ThreadLocal | Kiểm tra `ILoggingEvent` và pattern thay vì đọc worker MDC trực tiếp |
| Request B có ID của request A | Thread pool reused, task không clear/restore | Dùng scope với previous snapshot trong finally |
| Operation con đóng thì mất operation cha | `MDC.clear()` hoặc remove override mà không restore | Nested scope khôi phục previous values |
| `%X{requestId}` trống dù MDC đã set | Event được tạo trên thread khác hoặc key sai | So thời điểm/thread phát event, kiểm tra key/pattern |
| JSON chỉ có message, không có requestId field | Encoder chưa bật MDC field extraction | Cấu hình JSON encoder, schema và field mapping |
| MDC đúng nhưng WARN/ERROR mất khi peak | Async queue discard/drop hoặc sink lỗi | Kiểm tra queue policy, metrics, backend status |
| Sự kiện cuối không xuất khi shutdown | Worker async chưa drain; timeout/kill | Stop/flush đúng lifecycle, grace period hợp lý |
| `CompletableFuture` stage sau mất context | Có boundary `thenApplyAsync` khác | Decorate từng stage hoặc dùng context-aware executor |
| Reactive callback có ID sai | Thread reuse/context thiếu propagation | Dùng integration của reactive framework |
| MDC không hoạt động trên provider khác | SLF4J MDCAdapter/backend hỗ trợ khác nhau | Kiểm tra provider/runtime và cấu hình |
| Caller data sai hoặc trống | `includeCallerData` không bật hay encoder không in | Đánh giá nhu cầu caller metadata và chi phí |
| Log xuất hai lần | Root gắn cả ASYNC và CONSOLE, additivity | Kiểm tra topology, không đổ lỗi cho MDC |
| MDC chứa token/PII | Middleware copy toàn bộ headers/request vào MDC | Allowlist, masking, dọn context và bảo vệ collector |
| Tìm log theo traceId không khớp | trace ID không được propagate bằng tracing SDK | Kiểm tra trace context, không đồng nhất requestId với traceId |

### Quy trình điều tra

1. Xác định **event được tạo ở thread nào**; MDC ở thread đó có giá trị gì ngay trước lời gọi logger?
2. Kiểm tra **business async boundary**: task được submit ở đâu, có wrapper/decorator không?
3. Kiểm tra **capture xảy ra trước hay sau** khi caller clear/đổi MDC.
4. Kiểm tra worker có install đúng snapshot và restore dù có exception không.
5. Kiểm tra **backend thực tế** (Logback/Log4j 2/JUL bridge) và MDCAdapter.
6. Kiểm tra AsyncAppender/AsyncLogger có snapshot dữ liệu cần thiết và drop policy gì.
7. Kiểm tra encoder/layout có xuất MDC field/pattern đúng key.
8. Kiểm tra raw stdout/file trước collector; phân biệt raw thiếu với parser/index làm mất field.
9. Kiểm tra lifecycle shutdown, queue backlog và duplicate.
10. Kiểm tra context leak chéo request/tenant trong thread pool.

## 18. Bài tập thực hành

### Bài 1 — Tại sao AsyncAppender không cứu được requestId?

Main thread đặt `MDC.put("requestId", "req-42")` rồi gọi `executor.submit(() -> LOG.info("event=done"))`. Logback có AsyncAppender nhưng dòng từ worker thiếu requestId.

**Đáp án:** event được tạo trên worker không có MDC của main. AsyncAppender chỉ snapshot MDC **của event lúc worker gọi logger**. Phải capture ở caller và install ở worker, hoặc dùng context propagation của framework.

### Bài 2 — Khôi phục nested context

Root op-17, child op-18. Khi child kết thúc, gọi `MDC.clear()` khiến log root sau đó mất operationId.

**Đáp án:** cần lưu previous map trước scope con rồi restore trong finally/AutoCloseable. Việc xóa toàn bộ MDC ở child có thể phá dữ liệu của parent.

### Bài 3 — Đọc JSON không thấy field

Raw log chứa `"message":"requestId=req-42 event=done"` nhưng không có field `requestId` riêng.

**Đáp án:** đây là message string, không phải structured attribute. Cấu hình encoder xuất MDC thành field, hoặc dùng API structured arguments và schema phù hợp.

### Bài 4 — Task thất bại nhưng request sau bị lẫn ID

Một wrapper chỉ `MDC.clear()` khi task thành công. Task ném `RuntimeException` nên chưa dọn; worker sau mang ID cũ.

**Đáp án:** restore phải trong `finally`. Dùng snapshot context trước, không chỉ clear vô điều kiện; test với thread pool được tái sử dụng.

### Bài 5 — AsyncAppender và mất log

Một event có đầy đủ MDC nhưng biến mất sau khi queue đầy và `neverBlock=true`.

**Đáp án:** đây là mất event do chính sách queue, không phải lỗi MDC. Cần quyết định trade-off block/drop, đo overload và thiết kế đường lưu bền vững nếu yêu cầu audit.

## 19. Checklist trước khi triển khai MDC với async

- [ ] Phân biệt rõ **business async** và **async logging**.
- [ ] MDC được đặt **trước khi event được tạo** trên đúng thread.
- [ ] Logback AsyncAppender được cấu hình đúng, snapshot MDC ở event khi enqueue.
- [ ] Qua `ExecutorService`/`CompletableFuture` có capture/install/restore đúng boundary.
- [ ] Không dựa vào `ThreadLocal` hoặc `InheritableThreadLocal` tự truyền qua thread pool.
- [ ] Nested scope khôi phục previous context, không xóa nhầm parent.
- [ ] Wrapper restore trong `finally`, kể cả exception/return/cancellation đã bắt đầu.
- [ ] Có test worker reuse để phát hiện rò requestId/tenantId sang task kế.
- [ ] Không dùng logger name động theo request ID.
- [ ] Encoder text/JSON xuất MDC thực sự, schema/field names nhất quán.
- [ ] Throwable, message và structured field được xử lý riêng, không nhầm MDC là stack trace.
- [ ] Có kiểm tra provider/adapter MDC của SLF4J hoặc ThreadContext Log4j 2 ở runtime.
- [ ] Có policy rõ cho queue full, drop/block, flush, shutdown và collector.
- [ ] Tracing SDK truyền traceId/spanId riêng; MDC phục vụ log correlation.
- [ ] Không ghi secrets/PII không cần thiết vào MDC, áp dụng allowlist và retention.
- [ ] Đã kiểm tra tải cao, async callback, nested operation, lỗi task và JSON parsing.

**Kết luận:** **MDC trong async** cần giải quyết **hai lần chuyển ngữ cảnh khác nhau**. Khi chỉ chuyển việc ghi log sang Logback AsyncAppender, event thường mang MDC snapshot ở thời điểm phát log. Khi **chuyển nghiệp vụ** sang một thread/task khác, ứng dụng hoặc framework phải **capture → install → execute → restore** MDC để event được tạo với đúng requestId/operationId. Bảo toàn context giúp truy vết chính xác, nhưng không biến logging thành cơ chế tracing, không loại bỏ rủi ro mất event do queue và không thay thế chính sách bảo mật dữ liệu.
