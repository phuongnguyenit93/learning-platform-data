# Parameter Substitution in SLF4J: Parameterized Logging with `{}`

## 1. The Problem to Solve

In Java, log statements often need to include the data being processed: order IDs, retry counts, statuses, execution times, or error causes. Direct string concatenation looks simple:

```java
log.debug("Đang xử lý đơn " + orderId + ", attempt=" + attempt);
```

This snippet is an illustration assuming the variables `log`, `orderId`, and `attempt` are already defined. Even when the `DEBUG` level is disabled, Java still has to evaluate the string concatenation expression and all arguments before calling the method. If the content involves expensive computations, the cost can be significant.

**Parameter substitution** in SLF4J allows placing `{}` placeholders in the message template and passing the corresponding values as arguments:

```java
log.debug("Đang xử lý đơn {}, attempt={}", orderId, attempt);
```

When the log level is enabled, the logging system can produce the corresponding message:

```text
Đang xử lý đơn O-17, attempt=2
```

Meaning: `"Đang xử lý đơn {}, attempt={}"` is the **message template**; `orderId` and `attempt` are **parameters** that will be rendered at the positions of the two `{}` placeholders in order of appearance.

In standard calls, SLF4J provides an API layer (facade), while a backend such as Logback, Log4j2, or another provider determines the final formatting, output destination, and logging policy. **Parameter substitution helps construct the message content; it does not by itself define JSON structure, log level, destination, or distributed context.**

## 2. Exact Syntax: `{}`, Ordering, and Value Types

`{}` is SLF4J's placeholder. Each standard placeholder receives **one argument in order**:

```java
log.info("order={} amount={} currency={}",
        orderId, amount, currency);
```

For example, with `orderId="O-17"`, `amount=1200`, and `currency="VND"`, the message will be:

```text
order=O-17 amount=1200 currency=VND
```

Some important rules:

- **Do not use `%s` or `%d` like `String.format`:** SLF4J understands `{}`; it does not interpret `%s` as a placeholder in standard calls.
- **Variable names directly inside placeholders (template-style) are not supported:** `{orderId}` is treated as literal text; SLF4J does not automatically look up a variable named `orderId`.
- **Order determines meaning:** `log.info("user={} order={}", orderId, userId)` still runs, but assigns the wrong semantics to the positions.
- **Pass the exact number of data arguments:** the number of placeholders should match the formatted values; avoid relying on behavior when arguments are missing or extra.
- **`null` values:** rendered as the literal text `null` in the formatted message.
- **Primitive types:** `int`, `long`, `boolean`, etc., are boxed into objects when passed to an API accepting `Object`; method overloads and how arguments are passed can affect boxing overhead.
- **Arrays:** SLF4J's formatter handles arrays to produce readable strings such as `[2, 4]`, instead of Java's default array identity string.
- **Objects:** when formatting is needed, SLF4J may call the object's `toString()`. Keep `toString()` safe, without exposing secrets, performing I/O, or running expensive computations.

Example using properly typed variables:

```java
log.info("discount={}%", discountPercent);
```

The percent sign `%` is a normal character; this is not a `printf` expression. If `discountPercent=15`, the message is `discount=15%`. There is no need to write `%%` as in `String.format`.

### What Does a Single Placeholder Represent?

If you want to log a pair of values, each value usually has its own `{}`:

```java
log.info("range=[{}, {}]", min, max);
```

The square brackets are part of the message text; only `{}` is a placeholder. Placing labels next to the placeholders such as `min={}`, `max={}` is usually easier to search and understand than an unlabeled sequence of values.

When passing objects with important properties, do not assume `toString()` is a stable format. If the system needs to search by `order_id`, log a structured field along with a human-readable message; this will be explained in Section 8.

## 3. Why Is Parameter Substitution Usually Better Than String Concatenation?

Compare three approaches:

```java
// 1. String concatenation: evaluation and concatenation happen before the logger call.
log.debug("id=" + orderId + " state=" + state);

// 2. String.format: builds the string before the logger checks the level.
log.debug(String.format("id=%s state=%s", orderId, state));

// 3. SLF4J placeholders:
log.debug("id={} state={}", orderId, state);
```

With approach (3), when `DEBUG` is disabled, the logger can normally skip formatting the string and calling `toString()` on the passed objects. This usually reduces unnecessary work. In addition, the template is explicit and can be used by observability tools to group messages of the same shape.

**Limits of laziness:** Java always **evaluates argument expressions before invoking a method**. For example:

```java
log.debug("report={}", buildExpensiveReport());
```

`buildExpensiveReport()` still executes even if `DEBUG` is disabled, because that method call produces the argument value. Parameter substitution saves formatting work **after receiving the values**, and does not automatically defer Java expressions.

When creating an argument is genuinely expensive, use a level check:

```java
if (log.isDebugEnabled()) {
    log.debug("report={}", buildExpensiveReport());
}
```

With **SLF4J 2.x**, the fluent API also supports a value supplier (`Supplier`) to defer computation:

```java
log.atDebug()
        .addArgument(() -> buildExpensiveReport())
        .log("report={}");
```

These are **illustrative snippets**, assuming `log` and the `buildExpensiveReport()` method exist. `atDebug()` and `addArgument(Supplier<?>)` belong to the SLF4J 2.x fluent API; you cannot copy this syntax into SLF4J 1.7.x without upgrading the version. A supplier defers value creation until the event actually needs to be logged. The function inside the lambda must still behave appropriately when invoked and should not have required business side effects.

### When Should You Check the Level Manually?

You do not need to wrap **every** `log.debug("id={}", id)` in `if (log.isDebugEnabled())`. If the arguments are already available and cheap to evaluate, the placeholder call is usually sufficient. A level check is useful when argument expressions do expensive work, build large strings, query additional data, or serialize complex objects.

Avoid performing side effects inside `toString()` or in helper functions used only to prepare log data: business behavior must never depend on whether a log level is enabled or disabled.

## 4. How to Escape a `{}` Placeholder to Print It Literally

Sometimes you want to display the literal `{}` characters as part of the message—for example, when showing syntax to a user—and only substitute a `{}` that appears later.

At SLF4J's **format template** level, a backslash immediately before `{}` indicates that the brace pair is literal text. Because Java uses backslashes in string literals, you must write **two backslashes in Java source code** to produce one backslash in the actual string:

```java
log.info("Mẫu \\{} và kết quả {}", result);
```

With `result="OK"`, the expected message is:

```text
Mẫu {} và kết quả OK
```

Here, `\\{}` in **Java source code** produces the input string `\{}`, which SLF4J interprets as a literal brace pair. The subsequent placeholder still consumes `result`. If you need to output multiple literal backslashes, write a dedicated test case because Java and SLF4J are **two separate escaping layers**.

Do not use `\{` alone in a Java string literal, as that is an invalid Java escape sequence. And do not confuse `{}` with `java.text.MessageFormat` syntax (e.g., `{0}`) or `String.format` (e.g., `%s`): they are different mechanisms.

## 5. Passing Exceptions (`Throwable`) Properly with Placeholders

This is a common source of bugs when using SLF4J. An exception log entry typically needs both context and a stack trace:

```java
log.error("event=payment.failed order={} code={}",
        orderId, errorCode, exception);
```

This is an **illustration** with `log`, `orderId`, `errorCode`, and `exception` already declared. Under SLF4J's standard formatting rules, a `Throwable` as the last argument is recognized as the **exception cause** so the backend can print the stack trace, while the preceding two arguments fill the two `{}` placeholders.

The resulting message may be:

```text
event=payment.failed order=O-17 code=GATEWAY_UNAVAILABLE
```

The `Throwable` information is attached **separately** to the event, rather than being a string inserted into a third placeholder. The backend can additionally output the exception class name, nested causes, and stack trace depending on configuration.

Comparison:

| Call | Meaning |
| --- | --- |
| `log.error("payment failed", exception)` | Logs a fixed message and passes `Throwable` via the exception-accepting overload. |
| `log.error("payment failed for {}", orderId, exception)` | Fills in `orderId` and keeps `exception` as the cause. |
| `log.error("failed order={} code={}", orderId, code, exception)` | Two data fields plus a trailing `Throwable`. |
| `log.error("payment failed: {}", exception.getMessage())` | Inserts only the exception's message string; does not ensure the backend receives the `Throwable` or prints a stack trace. |

**Common pitfall:** writing `log.error("failure={}", exception)` when intending to insert `exception.toString()`. Java may select the `error(String, Throwable)` overload, treating the exception parameter as the cause rather than normal formatted data. When you want to log both a message and a stack trace, prefer `log.error("operation failed", exception)` or add an **explicit data argument**:

```java
log.error("operation failed, id={}", orderId, exception);
```

In SLF4J 2.x's fluent API, you can separate the cause from arguments even more explicitly:

```java
log.atError()
        .addArgument(orderId)
        .setCause(exception)
        .log("operation failed, id={}");
```

Keep in mind that `exception.getMessage()` may contain URLs, tokens, or sensitive values from dependencies. Passing a `Throwable` for diagnostic logging still requires secret-redaction policies, access controls, and exception formatting controls.

### Do Not Leave Missing or Extra Placeholders When Passing a `Throwable`

Unintended example:

```java
log.error("order={} cause={}", orderId, exception);
```

If `exception` is interpreted as the trailing `Throwable`, the message only receives `orderId` for the first placeholder; `cause={}` will **not be replaced with the exception string as expected**. To record a technical cause, put searchable information into a field like `error_code` and pass the `Throwable` in the last position. Do not rely on an exception argument automatically "occupying" a placeholder.

## 6. Runnable Java 17 Example: Checking Substitution Results

To observe **the exact message formatting** and `Throwable` extraction rules without interference from timestamps, threads, console patterns, or backends, we can use `org.slf4j.helpers.MessageFormatter` directly from `slf4j-api`.

**This example is for learning and testing**: in normal application code, call `Logger.info/debug/error(...)` instead of formatting manually with `MessageFormatter`. The helper class is used here solely to test the substitution mechanism and print deterministic stdout.

Requirements: JDK 17+, Maven, and ability to fetch Maven dependencies.

Directory structure:

```text
slf4j-parameters/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── edu/
                └── example/
                    └── logging/
                        └── ParameterSubstitutionDemo.java
```

Create **`pom.xml`**:

```xml

         https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>edu.example</groupId>
    <artifactId>slf4j-parameters</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.16</version>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>

                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
            </plugin>
        </plugins>
    </build>
</project>
```

Create **`src/main/java/edu/example/logging/ParameterSubstitutionDemo.java`**:

```java
package edu.example.logging;

import org.slf4j.helpers.FormattingTuple;
import org.slf4j.helpers.MessageFormatter;

public final class ParameterSubstitutionDemo {
    public static void main(String[] args) {
        FormattingTuple order = MessageFormatter.arrayFormat(
                "order={} amount={} approved={}",
                new Object[] {"O-17", 1200, true});
        System.out.println(order.getMessage());

        System.out.println(MessageFormatter
                .format("ids={}", new int[] {2, 4})
                .getMessage());

        System.out.println(MessageFormatter
                .format("value={}", (Object) null)
                .getMessage());

        System.out.println(MessageFormatter
                .format("literal \\{} result={}", "OK")
                .getMessage());

        IllegalStateException failure =
                new IllegalStateException("gateway down");

        FormattingTuple failed = MessageFormatter.arrayFormat(
                "event=payment.failed order={}",
                new Object[] {"O-17", failure});

        System.out.println(failed.getMessage());
        System.out.println("cause="
                + failed.getThrowable().getClass().getSimpleName());
    }
}
```

From the `slf4j-parameters` directory, run:

```bash
mvn -q compile exec:java -Dexec.mainClass=edu.example.logging.ParameterSubstitutionDemo
```

**Stdout lines printed by the Java program (excluding environment-dependent Maven messages):**

```text
order=O-17 amount=1200 approved=true
ids=[2, 4]
value=null
literal {} result=OK
event=payment.failed order=O-17
cause=IllegalStateException
```

Line-by-line analysis:

1. `MessageFormatter.arrayFormat` receives a template with three placeholders and three values, so the output follows that order. `1200` and `true` have their respective types, but when formatted into the message they are rendered as text.
2. `int[]` is displayed as `[2, 4]`; this is SLF4J's array formatting behavior, rather than Java's standard `int[].toString()`.
3. A `null` argument is rendered as the text `null`.
4. `"literal \\{} result={}"` is a Java string literal containing an escaped first placeholder followed by a real placeholder.
5. `IllegalStateException` is passed in the last position of the argument array. `getMessage()` returns the message with `order` substituted; `getThrowable()` returns the separate exception object, allowing the exception class name to be printed on the final line.
6. No logging provider is required because the program only calls the formatting helper. **When using a real `Logger`**, a suitable backend/provider is needed for messages to be written to the console or a log collection system.

### Why Does the Example Use a Helper While Production Code Calls `Logger`?

In an application, the code should look like:

```java
private static final org.slf4j.Logger LOG =
        org.slf4j.LoggerFactory.getLogger(PaymentService.class);

// Inside a method that already has orderId, amount, failure:
LOG.info("order={} amount={}", orderId, amount);
LOG.error("payment failed for {}", orderId, failure);
```

This is an **illustrative snippet** and does not compile standalone because `PaymentService` and the variables belong to business code. `Logger` handles level checks, event creation, exception attachment, and delegation to the provider; calling the helper directly only performs formatting and is not a substitute for logging. When using SLF4J 2.x without a provider, `Logger` calls may not produce the expected logs; you must verify dependencies and the binding/provider.

## 7. Three Situations That Produce Incorrect Log Output

### 7.1. Swapping Parameter Order

```java
log.info("account={} action={}", action, accountId);
```

If `action="WITHDRAW"` and `accountId="A-7"`, the message becomes `account=WITHDRAW action=A-7`, which is semantically wrong even though no exception is thrown. SLF4J **does not know variable names**; it substitutes strictly by position. You should verify messages with tests for critical events; better yet, attach structured fields to reduce mistakes.

### 7.2. Expecting `String.format` Syntax

```java
log.info("count=%d duration=%s", count, durationMs);
```

In standard SLF4J, `%d` and `%s` are not placeholders; the log message will not be populated as in `String.format`. The proper form is:

```java
log.info("count={} duration_ms={}", count, durationMs);
```

If you need special decimal formatting (such as exactly two digits after the decimal point), format it conditionally when the log level is enabled or use typed fields with an appropriate encoder. Avoid calling `String.format(...)` unconditionally in high-frequency `DEBUG` calls.

### 7.3. Passing an Exception as the Last Argument Expecting It to Be Treated as Regular Data

```java
log.warn("retry={} exception={}", retryCount, ex);
```

If `ex` is a `Throwable`, SLF4J may extract it as the cause instead of filling `exception={}`. A clearer approach is:

```java
log.warn("retry={} code={}", retryCount, errorCode, ex);
```

When you only want to display the exception type **without sending a stack trace**, pass a controlled string such as `ex.getClass().getSimpleName()`, while considering whether losing the stack trace is acceptable for diagnostic goals.

## 8. Parameter Substitution Is Not Structured Logging

Suppose a formatted log line is:

```text
order=O-17 amount=1200 result=SUCCESS
```

Humans can read it, but a log collector has to **parse the text** to extract the `order`, `amount`, and `result` pairs. If values contain spaces, equals signs, newlines, or brackets, free-text parsing easily breaks.

With **structured logging**, fields can be attached separately to the event:

```json
{
  "timestamp": "2026-01-01T00:00:00Z",
  "level": "INFO",
  "event_code": "order.completed",
  "order_id": "O-17",
  "amount": 1200,
  "result": "SUCCESS",
  "message": "Hoàn tất đơn hàng"
}
```

In SLF4J 2.x, the fluent API allows adding key-value pairs:

```java
log.atInfo()
        .addKeyValue("event_code", "order.completed")
        .addKeyValue("order_id", orderId)
        .addKeyValue("amount", amount)
        .log("Hoàn tất đơn hàng");
```

This snippet assumes `log`, `orderId`, and `amount` already exist. It requires a backend and encoder configured to output key-value pairs. **Not every console pattern automatically displays fluent API fields**; you must verify the actual output. You can combine typed fields with a clear message template, and you should not re-parse the message when structured fields are already present.

**MDC (Mapped Diagnostic Context)** is a related but distinct concept: MDC stores contextual fields scoped to an execution context, such as `trace_id` or `request_id`, so multiple logging calls share them. Parameter substitution supplies values for **a single call**, whereas MDC provides shared context that must be propagated and cleaned up properly during asynchronous processing. The two mechanisms complement each other rather than replacing one another.

### Queryability and Cardinality

Bounded fields such as `event_code`, `service`, and `result` are generally suitable for grouping. Values like `order_id` or `trace_id` are used to look up a specific execution; do not turn millions of such values into high-cardinality metric labels. Parameter substitution does not by itself control grouping granularity or data access permissions in the backend.

## 9. Performance, Reliability, and Sensitive Data

Using `{}` avoids formatting when logging is disabled, but it is not an absolute guarantee of performance or security.

### Performance

- SLF4J's API provides overloads for one and two arguments; these can avoid some `Object...` array allocation overhead compared to multi-argument calls. Exact optimizations depend on the SLF4J version and JVM; prioritize clear messages before micro-optimizing.
- When passing more than two values, the varargs API may allocate an argument array. This cost is usually smaller than logging I/O when enabled; optimize only based on actual measurements.
- Argument evaluation, boxing, temporary object creation, and expensive computations can still happen before the logger call; use level checks or suppliers when needed.
- The backend may write synchronously or asynchronously, buffer, send over the network, format JSON, and print stack traces; these costs lie outside `{}` substitution.
- Logging excessive `DEBUG`/`TRACE` events on hot paths can still cause significant load even when using parameter substitution.

### Reliability

A call to `logger.info("event={}", eventCode)` does not guarantee that the record has reached a centralized store. Filters, levels, appenders, queues, network errors, or container shutdowns can drop records; retries in a collector can create duplicates. Metrics that require exact counts or audit events with strong delivery guarantees need dedicated collection designs rather than relying solely on log message templates.

### Security

Parameter substitution **does not automatically mask data**. For example:

```java
log.info("Authorization header={}", authorizationHeader);
```

Even with a placeholder, the token can still appear in logs if the backend writes that line. Avoid logging passwords, access keys, payment cards, sensitive personal data, or entire uncontrolled domain objects. An object's `toString()` might inadvertently expose secret fields; design safe objects/formatters or pass only permitted fields.

Inputs containing newlines or control characters can corrupt text-based logs. Use a reliable structured encoder, verify character escaping, and establish clear event boundaries. Do not treat `{}` as an automatic defense against log injection.

## 10. How to Test Parameter Substitution

You should test the **stable semantics** of logs, without depending on timestamps, thread names, or the full line pattern.

Common testing layers:

1. **Message formatting:** pass a template and fixed arguments, then compare the substituted message. The example in Section 6 uses `MessageFormatter` to test this mechanism in isolation.
2. **Actual logger events:** attach a test appender/handler for your backend and assert the level, logger name, original template, formatted message, and `Throwable`.
3. **Encoder output:** if using JSON or key-value output, parse and verify fields, data types, and character escaping.
4. **Operational pipeline:** verify in staging that the collector receives the expected events, searchable by `event_code` or `trace_id`, without unexpected drops or duplicates.
5. **Security:** use dummy secret data to verify it does not appear in the message, additional fields, or stack traces.

With Logback, `ILoggingEvent.getMessage()` can represent the original template, while `getFormattedMessage()` is the text after parameter substitution. `getArgumentArray()` exposes the parameter data when retained by the backend, and `getThrowableProxy()` allows inspecting the exception. Tests should run against the actual backend used by the project.

Example test matrix:

| Template | Data arguments | What to assert |
| --- | --- | --- |
| `"id={}"` | `"O-17"` | Message is `id=O-17`. |
| `"a={} b={}"` | `1, true` | `a=1 b=true` in order. |
| `"ids={}"` | `new int[]{2,4}` | Array renders as `[2, 4]`. |
| `"value={}"` | `null` | Literal text `null`. |
| `"literal \\{} value={}"` | `"OK"` | First placeholder stays literal; the second is filled. |
| `"order={}"` + trailing `Throwable` | `"O-17", exception` | Message only substitutes `order`; the event holds the `Throwable` separately. |

If tests interact with the backend, detach appenders and restore log levels in `finally` blocks so other tests are not affected; if logging asynchronously, use a bounded wait mechanism instead of assuming logs appear immediately. Do not assert entire stack traces down to source line numbers, as harmless refactors can break those tests.

## 11. Common Mistakes and How to Fix Them

| Mistake | Consequence | How to fix |
| --- | --- | --- |
| Using `%s` instead of `{}` | Message keeps literal printf placeholders | Use `{}` in SLF4J; only use `String.format` when you intentionally want to build the string yourself. |
| String concatenation at a disabled `DEBUG` level | Expressions are still evaluated and concatenated | Use parameter substitution. |
| Passing `expensive()` directly | Function still runs when logging is disabled | Check `isDebugEnabled()` or use an SLF4J 2.x `Supplier`. |
| Swapping argument order | Log fields have wrong semantics | Verify placeholder positions with tests. |
| Missing or extra placeholders | Message has unfilled `{}` or arguments do not appear as expected | Match the number of data arguments; keep `Throwable` last. |
| Using `log.error("{}", exception)` expecting `exception` as a string | May select the `Throwable` overload | Use a call with a clear message and pass the exception as the cause. |
| Logging only `exception.getMessage()` | Loses exception type, cause chain, and stack trace | Pass the `Throwable` object when diagnostics are needed. |
| Assuming placeholders create JSON fields | Cannot query typed fields | Use structured key-value pairs and a structured encoder. |
| Using `toString()` on an object containing tokens | Leaks sensitive data | Pass only permitted fields and control formatters. |
| Assuming all backends print identically | Tests or queries depend on timestamps/patterns | Test stable fields and the actual backend configuration. |
| Embedding dynamic IDs directly in the template | Hard to group messages of the same type | Keep the template fixed; pass IDs as parameters or fields. |
| Not verifying exceptions in the backend | Message looks fine, but stack trace is missing | Inspect `Throwable`/`ThrowableProxy` and the encoder. |

## 12. Practice Exercises

An order processing service has `orderId="O-17"`, `attempt=3`, `errorCode="GATEWAY_UNAVAILABLE"`, and `failure` as an `IllegalStateException`.

**Exercise 1.** Write an `INFO` call using parameter substitution to produce the message:

```text
order=O-17 attempt=3
```

**Suggested answer:**

```java
log.info("order={} attempt={}", orderId, attempt);
```

**Exercise 2.** Write an `ERROR` call when payment finally fails, preserving the `Throwable` and providing a message that is easy to filter by error code.

**Suggested answer:**

```java
log.error("event=payment.failed order={} code={}",
        orderId, errorCode, failure);
```

`failure` is the last argument and is handled as the cause; the two placeholders are for `orderId` and `errorCode`. If using structured logging, move stable metadata into separate fields.

**Exercise 3.** Evaluate the following call when `DEBUG` is disabled:

```java
log.debug("preview={}", renderLargePreview(order));
```

**Suggested answer:** `renderLargePreview(order)` still runs before the logger call. Use `isDebugEnabled()` or SLF4J 2.x's `addArgument(Supplier<?>)` to avoid generating the preview unnecessarily; ensure generating the preview has no required side effects.

**Exercise 4.** A system wants to query the count of `payment.failed` events by `error_code`, but the current log only has the string `"payment={} code={}"`. Is parameter substitution enough?

**Suggested answer:** No. It produces a human-readable message, but `error_code` is not guaranteed to be stored as a separate field. You need structured logging or a verified parser mechanism; `event_code` and `error_code` should be kept as stable fields.

**Exercise 5.** Explain why `log.error("failed: {}", exception.getMessage())` can make investigation harder than `log.error("failed", exception)`, even when both lines appear to show the same text.

**Suggested answer:** The first call only passes a string message; it does not preserve the `Throwable` with its exception type, cause chain, and stack trace. The second call gives the backend the opportunity to record full diagnostic information; you still need to check the formatter and exception message security.

You have mastered **parameter substitution** when you can write `{}` templates in the right order, explain how they differ from string concatenation/`String.format`, know when arguments are evaluated, pass `Throwable` in the right position, and distinguish formatted messages from structured log data.
