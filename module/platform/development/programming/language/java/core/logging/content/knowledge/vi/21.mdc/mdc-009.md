# MDC và structured log trong Java

## 1. Vì sao cần kết hợp MDC với structured logging?

Một ứng dụng Java có thể xử lý hàng nghìn HTTP request, tác vụ nền, thông điệp và giao dịch cùng lúc. Khi mọi thành phần ghi log với một logger theo lớp, người vận hành cần tìm những bản ghi thuộc **cùng một lần xử lý** mà không dựa vào việc đọc một chuỗi message tự do.

**MDC (Mapped Diagnostic Context)** là API lưu một tập các cặp **khóa–giá trị dạng chuỗi** làm ngữ cảnh chẩn đoán, chẳng hạn `request_id`, `correlation_id`, `tenant_id`. Logging framework có thể gắn những giá trị ngữ cảnh này vào các sự kiện được tạo trên thread tương ứng.

**Structured logging** là cách biểu diễn một sự kiện thành **các trường có tên và kiểu rõ ràng**, thường là JSON; các trường có thể được collector và hệ thống tìm kiếm phân tích độc lập.

Hai khái niệm liên quan nhưng **không đồng nghĩa**:

- **MDC cung cấp ngữ cảnh** cho nhiều lời gọi log trong cùng một scope.
- **Structured log cung cấp định dạng/schema** để một sự kiện có thể được máy phân tích.
- **Encoder/Layout/Provider quyết định MDC có được xuất ra JSON hay không**, nằm ở root hay object lồng nhau, và những key nào được giữ.
- **Collector quyết định việc parse/mapping** để các trường có thể tìm kiếm, lọc và tổng hợp trong hệ thống lưu trữ.

Ví dụ cùng một nghiệp vụ:

```java
LOG.info("event=order_created order_id={}", orderId);
```

Nếu request không có MDC, đầu ra text có thể chỉ là:

```text
INFO event=order_created order_id=ORD-101
```

Nếu ứng dụng đặt MDC và backend xuất nó, một biểu diễn JSON có thể là:

```json
{
  "timestamp": "2026-11-09T12:00:00Z",
  "level": "INFO",
  "logger": "order-service",
  "request_id": "req-17",
  "tenant_id": "tenant-A",
  "event": "order_created",
  "order_id": "ORD-101"
}
```

Đây là **schema minh họa do ứng dụng định nghĩa**. **Không** có một lời gọi `MDC.put(...)` duy nhất nào bảo đảm mọi backend sẽ tự phát đúng JSON trên.

**Điểm học quan trọng nhất:** dữ liệu request/tenant/trace dùng lặp lại nên được quản lý như **context có scope**; dữ liệu chỉ thuộc **một sự kiện** nên ưu tiên gắn vào LogEvent dưới dạng thuộc tính riêng, thay vì đưa mọi thứ vào MDC.

## 2. Đường đi từ MDC tới hệ thống tìm kiếm log

```text
HTTP request / Message / Job
          |
          v
  Xác định trusted context
  request_id, tenant_id, trace_id
          |
          v
  MDC / ThreadContext của scope
          |
          +-----------+-----------+
          |           |           |
          v           v           v
    LOG.info(...) LOG.warn(...) LOG.error(...)
          |           |           |
          +-----------+-----------+
                      |
                      v
                Logging event
             level, time, message,
            throwable, mdc, kv pairs
                      |
                      v
             Backend / Encoder
           (Pattern / JSON template)
                      |
                +-----+-----+
                |           |
                v           v
             Text line    JSON object
                |           |
                +-----+-----+
                      |
                      v
              stdout/file/socket
                      |
                      v
             Agent / Collector
            decode / parse / map
                      |
                      v
              Index / Log query
```

Từng bước có thể làm mất hoặc thay đổi thông tin:

1. **MDC không được đặt đúng thời điểm:** LogEvent không có `request_id`.
2. **MDC không đi qua thread mới:** sự kiện của async task không có context hoặc có context của request khác.
3. **Encoder không đưa MDC vào output:** Logger ghi thành công, nhưng file JSON chỉ chứa `message`.
4. **Encoder đưa MDC thành text:** collector không tự có trường `request_id` nếu không parse.
5. **Collector không parse JSON:** toàn bộ object bị lưu dưới một trường `log` hoặc `message`.
6. **Schema không khớp:** dashboard tìm `request.id` nhưng JSON chứa `request_id`.
7. **Pipeline lọc hoặc mất dữ liệu:** một event có thể không xuất hiện do sampling, queue, retention hoặc lỗi transport.

Cho nên cần kiểm chứng **đầu-cuối**, không kết luận chỉ từ việc `MDC.get("request_id")` trả về một giá trị.

## 3. MDC lưu những gì và không nên lưu những gì?

Các key thường có giá trị:

| MDC key | Ý nghĩa | Khi nào đặt? |
| --- | --- | --- |
| `request_id` | ID của một request ở service hiện tại | Khi bắt đầu xử lý request |
| `correlation_id` | ID kết nối nhiều bước/service của một luồng | Sau khi xác minh hoặc tạo ở boundary tin cậy |
| `trace_id` | Trace identifier dùng để liên kết với tracing | Khi context tracing đã sẵn có |
| `span_id` | Span identifier nếu cần | Tại scope span thích hợp |
| `tenant_id` | Tenant đã được resolve/authorize | Sau khi xác minh quyền tenant |
| `job_id` | Một lần chạy tác vụ | Trong scope job |
| `message_id` | Một thông điệp được tiêu thụ | Khi xử lý message |
| `operation` | Nhóm thao tác ổn định | Khi nó mô tả cả scope |
| `attempt` | Lần thử thứ mấy | Chỉ nếu thật sự thuộc scope retry cụ thể |

**Không nên đưa vào MDC**: password, access token, API key, session cookie, OTP, dữ liệu thẻ, object chứa PII, toàn bộ HTTP request/response, stack trace, body lớn hoặc giá trị có số lượng key tùy ý do user tự tạo.

**MDC là Map<String, String> theo API SLF4J**, vì vậy `MDC.put("duration_ms", "1500")` lưu giá trị **chuỗi** `"1500"`. Một encoder JSON thường xuất:

```json
{"duration_ms":"1500"}
```

thay vì:

```json
{"duration_ms":1500}
```

Trường hợp thứ hai có kiểu JSON **number**; chỉ có khi encoder/transform được cấu hình chuyển kiểu phù hợp hoặc khi dữ liệu được đưa vào event bằng API hỗ trợ kiểu số.

Vì vậy:

- **Context có phạm vi:** `request_id`, `tenant_id`, `trace_id`.
- **Thuộc tính của một sự kiện:** `duration_ms`, `http_status`, `retry_count`, `bytes_sent` nên là **typed event attributes/key-value pairs** khi backend hỗ trợ.
- **Message:** mô tả dễ đọc, nhưng không làm nguồn dữ liệu duy nhất cho dashboard.

Không biến logger name thành `logger.getLogger("order-" + orderId)`. Tên logger nên đại diện nguồn code; ID thay đổi là dữ liệu của sự kiện.

## 4. MDC trong SLF4J, Logback, Log4j2 và JUL

Trong Java có nhiều API và backend. Cần biết chính xác thành phần nào sở hữu MDC và thành phần nào serialize:

| Hệ thống | API ngữ cảnh | Đưa vào output bằng gì? | Lưu ý |
| --- | --- | --- | --- |
| **SLF4J 2.x** | `org.slf4j.MDC` | Phụ thuộc provider/encoder thực tế | SLF4J là facade, không mặc định sản xuất JSON |
| **Logback Classic** | `org.slf4j.MDC` | Pattern `%X{key}` hoặc JSON encoder có MDC provider | Thường dùng trong ứng dụng SLF4J |
| **Log4j2** | `org.apache.logging.log4j.ThreadContext` | `PatternLayout` với `%X{key}` hoặc `JsonTemplateLayout` với `mdc` resolver | Log4j2 dùng tên Thread Context Map |
| **JUL** | Không có API MDC chuẩn trong `java.util.logging.LogRecord` | Custom Handler/Formatter/adapter nếu cần | JUL `ConsoleHandler` mặc định ghi stderr |
| **SLF4J Simple / NOP** | SLF4J MDC API có thể là NOP tùy adapter/provider | Không nên coi là backend MDC có structured JSON | Đọc/ghi MDC API không thay thế kiểm tra adapter và output |

Với SLF4J, `MDC.put` ủy quyền thao tác tới MDC adapter của provider. Không được giả định một hệ thống dùng `slf4j-simple` hay NOP sẽ cho output giống Logback. Nếu ứng dụng dùng framework có sẵn provider, hãy kiểm tra dependency runtime trước khi thêm backend mới, tránh nhiều provider hoặc bridge vòng lặp.

**Đổi backend không chỉ là đổi file cấu hình.** Nó có thể thay đổi:

- Tên và vị trí trường `mdc`, `contextMap`, `threadContext`.
- Cách hiển thị `Throwable`, tên logger, timestamp và level.
- API/adapter nào ghi được MDC và thời điểm snapshot.
- Việc hỗ trợ SLF4J 2.x fluent `addKeyValue`.
- Kiểu JSON của từng trường và cách xử lý dữ liệu thiếu.

## 5. Đặt MDC đúng vòng đời

Trong một HTTP request:

```text
Request bắt đầu
  |
  v
Xác thực / xác minh metadata
  |
  v
Tạo hoặc xác nhận request_id
  |
  v
Lưu MDC của scope
  |
  +-- Controller log
  +-- Service log
  +-- Repository log
  |
  v
Gửi response
  |
  v
Khôi phục/clear MDC trong finally
```

Một mẫu SLF4J thông dụng:

```java
String oldRequestId = MDC.get("request_id");
MDC.put("request_id", requestId);
try {
    handleRequest();
} finally {
    if (oldRequestId == null) {
        MDC.remove("request_id");
    } else {
        MDC.put("request_id", oldRequestId);
    }
}
```

Đây là **snippet trong lớp đã import `org.slf4j.MDC`** và có `requestId`/`handleRequest()`, không phải chương trình độc lập.

Những điều cần phân biệt:

- Nếu **request boundary sở hữu toàn bộ MDC map**, một cơ chế reset cả map có thể hợp lý.
- Nếu là **thư viện con**, đừng gọi `MDC.clear()` tùy tiện: nó có thể xóa cả `trace_id`, `tenant_id` hoặc dữ liệu của scope bên ngoài.
- Với scope lồng nhau trên **cùng key**, cần **khôi phục giá trị trước đó**.
- `try/finally` bảo đảm chạy đường dọn khi return sớm hoặc exception (trừ tình huống tiến trình bị chấm dứt cưỡng bức).
- MDC không phải bảo đảm auth; chỉ đặt `tenant_id` đã được xác minh ở tầng nghiệp vụ.

### `MDC.putCloseable` có đặc điểm gì?

SLF4J có:

```java
try (MDC.MDCCloseable ignored =
             MDC.putCloseable("request_id", requestId)) {
    LOG.info("event=request_started");
}
```

Đoạn này dùng `try-with-resources` để **xóa key `request_id` khi đóng**. Theo Javadoc, `MDCCloseable.close()` **remove key**, không tự khôi phục giá trị cũ của cùng key. Vì vậy nó phù hợp khi bạn **sở hữu key tại scope hiện tại** và không cần nested restore. Nếu scope A có `request_id=A` rồi scope B đặt `request_id=B` bằng `putCloseable`, đóng B có thể khiến A mất key. Trong thư viện hỗ trợ nested scope, mẫu lưu–khôi phục cũ an toàn hơn.

## 6. Ví dụ Java 17+ hoàn chỉnh: MDC qua hai request và thread pool

Ví dụ này sử dụng **SLF4J API 2.x + Logback Classic** để chứng minh:

1. `MDC.put` đặt `request_id` và `tenant_id` cho request.
2. Nhiều lời gọi logger cùng nhận các trường context.
3. Thread pool **không được mặc định kế thừa MDC**; phải chụp context khi submit và đặt lại trong worker.
4. Worker chỉ có một thread để có thể tái sử dụng cho **hai request thuộc hai tenant khác nhau**.
5. Context được **khôi phục/clear trong `finally`**, tránh request thứ hai mang dữ liệu request thứ nhất.
6. Pattern encoder in context thành text để dễ xác minh. Sau đó sẽ chuyển sang JSON encoder ở phần riêng.

Phiên bản trong bài được cố định để tái lập, **không khẳng định đây là các phiên bản mới nhất**. Dự án thật cần đồng bộ dependency và cập nhật bản vá phù hợp.

Cấu trúc:

```text
mdc-structured-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── example/
        │       └── logging/
        │           └── MdcStructuredDemo.java
        └── resources/
            └── logback.xml
```

### 6.2. `src/main/resources/logback.xml`

```xml
<configuration>
    <appender name="STDOUT"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <charset>UTF-8</charset>
            <pattern>%level request_id=%X{request_id} tenant_id=%X{tenant_id} %logger - %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
```

Đây là cấu hình **Logback**, không phải `log4j2.xml`. Các converter:

- `%level`: mức log (ví dụ `INFO`).
- `%X{request_id}` và `%X{tenant_id}`: đọc dữ liệu MDC trong LogEvent.
- `%logger`: tên logger; trong code ví dụ là tên cố định `demo`.
- `%msg`: message sau khi thay tham số `{}`.
- `%n`: newline để tách sự kiện.

ConsoleAppender ghi vào **System.out** nên stdout và stderr có thể kiểm tra riêng. Pattern không có timestamp để **stdout của bài học cố định**, không đồng nghĩa production nên bỏ timestamp.

### 6.3. `src/main/java/example/logging/MdcStructuredDemo.java`

```java
package example.logging;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class MdcStructuredDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger("demo");

    private MdcStructuredDemo() {
    }

    private static final class ContextScope
            implements AutoCloseable {
        private final Map<String, String> previous;

        private ContextScope(String requestId, String tenantId) {
            previous = MDC.getCopyOfContextMap();
            MDC.put("request_id", requestId);
            MDC.put("tenant_id", tenantId);
        }

        @Override
        public void close() {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    }

    private static void process(
            ExecutorService pool, String requestId,
            String tenantId, String orderId) throws Exception {

        try (ContextScope ignored =
                     new ContextScope(requestId, tenantId)) {

            LOG.info("event=order_received order_id={}", orderId);

            // Chụp context ở thread đang xử lý request.
            Map<String, String> captured =
                    MDC.getCopyOfContextMap();

            Future<?> result = pool.submit(() -> {
                Map<String, String> oldWorker =
                        MDC.getCopyOfContextMap();
                try {
                    // captured khác null trong ví dụ này.
                    MDC.setContextMap(captured);
                    LOG.info("event=order_confirmed order_id={}",
                            orderId);
                } finally {
                    // Không để context của task A sang task B.
                    if (oldWorker == null) {
                        MDC.clear();
                    } else {
                        MDC.setContextMap(oldWorker);
                    }
                }
            });

            // Chờ để output giữa hai request là xác định.
            result.get();
        }
    }

    public static void main(String[] args) throws Exception {
        MDC.clear();

        ExecutorService pool =
                Executors.newSingleThreadExecutor();

        try {
            process(pool, "req-101", "tenant-A", "ORD-101");
            process(pool, "req-102", "tenant-B", "ORD-102");
        } finally {
            pool.shutdown();
            MDC.clear();
        }
    }
}
```

Đây là **chương trình độc lập có `main`**, cần Maven dependencies ở trên. Nó không kết nối database hay HTTP server, chỉ mô phỏng hai request và một thread pool.

### 6.5. Vì sao đây là kiểm thử có ý nghĩa?

- Hai request chạy **lần lượt** trên main thread, nhưng đều dùng **cùng một worker** của pool.
- Khi phát sự kiện trong request A, MDC chứa `req-101`/`tenant-A`.
- Snapshot `captured` được chụp **trước khi submit task**.
- Worker đặt snapshot vào MDC **của chính worker thread** trước khi `LOG.info`.
- Khi task hoàn tất hoặc ném exception, `finally` khôi phục MDC cũ của worker.
- `Future.get()` bảo đảm task thứ nhất hoàn thành trước khi request thứ hai bắt đầu.
- Scope của request cũng khôi phục map trước đó dù xử lý thất bại.
- Chương trình không dựa vào sự kế thừa ThreadLocal tự động và không lưu tenant ID trong biến `static`.
- `%X{key}` xuất MDC thành text; đây là **kiểm chứng context**, chưa phải JSON structured logging.

Nếu bỏ đoạn `MDC.setContextMap(captured)` trong worker, LogEvent ở worker có thể thiếu request ID/tenant ID. Nếu bỏ cleanup trong worker, task B có thể nhận context cũ trong những nhánh code không đặt lại đầy đủ.

**Không dùng MDC làm security principal.** ID tenant trong ví dụ là dữ liệu mô phỏng đã được coi là hợp lệ. Trong ứng dụng thật, tenant phải được resolve và authorize trước khi đưa vào context.

## 7. Từ PatternLayout sang JSON: khác nhau ở output

Cấu hình phần 6:

```text
INFO request_id=req-101 tenant_id=tenant-A demo - event=order_received order_id=ORD-101
```

chỉ là **text**, dù có key-value. Một collector có thể cần parser tách từng phần nếu muốn truy vấn trường `request_id`.

Một JSON có cấu trúc lý tưởng:

```json
{
  "timestamp": "2026-11-09T12:00:00Z",
  "level": "INFO",
  "logger": "demo",
  "message": "Order received",
  "request_id": "req-101",
  "tenant_id": "tenant-A",
  "event": "order_received",
  "order_id": "ORD-101",
  "duration_ms": 25
}
```

Đây là **schema minh họa do hệ thống định nghĩa**, không phải JSON thực tế được tạo tự động bởi Logback PatternLayout trong phần 6.

Muốn làm được như vậy cần:

1. Một **JSON encoder/layout** thay cho text pattern.
2. Encoder đưa `request_id`/`tenant_id` từ MDC vào JSON.
3. `event`/`order_id` được bổ sung thành **field của event** (hoặc collector trích xuất từ message, nếu bắt buộc).
4. `duration_ms` vẫn là **number**, không bị ép thành string.
5. Timestamp, severity, logger, exception được serialize theo schema đã thống nhất.
6. Collector hiểu **một event mỗi dòng** và parse field đúng đường dẫn.

**Sự thay đổi cốt lõi:** MDC không “trở thành structured” chỉ vì code lưu cặp key-value; chính output của encoder và quá trình ingestion mới quyết định dữ liệu có cấu trúc.

## 8. Ví dụ Logback với JSON encoder có MDC

Logback Classic có encoder text mặc định, nhưng có thể dùng thư viện encoder JSON, ví dụ **`logstash-logback-encoder`**. Thư viện này là thành phần bổ sung, không nằm trong `slf4j-api`.

Để sử dụng, dự án cần thêm dependency encoder **phiên bản tương thích với Logback/JDK của dự án**; không lấy một phiên bản ngẫu nhiên từ ví dụ cũ khi tổ chức đã có dependency management. Cấu hình sau là **snippet appender** dùng encoder đó:

```xml
<appender name="JSON_STDOUT"
          class="ch.qos.logback.core.ConsoleAppender">
    <target>System.out</target>
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
        <includeMdc>true</includeMdc>
        <includeMdcKeyName>request_id</includeMdcKeyName>
        <includeMdcKeyName>tenant_id</includeMdcKeyName>
    </encoder>
</appender>
```

Đây **không phải một `logback.xml` hoàn chỉnh**. Để dùng, gắn `<appender-ref ref="JSON_STDOUT"/>` ở root/logger và bỏ `STDOUT` text nếu không muốn cùng một event xuất hai lần.

Theo tài liệu của `logstash-logback-encoder`:

- `LogstashEncoder` có thể đưa MDC entries vào JSON. Khi chọn `includeMdcKeyName`, chỉ các MDC keys được liệt kê mới được đưa ra.
- Khi không hạn chế keys, encoder có thể xuất **toàn bộ MDC**: điều này rủi ro nếu MDC chứa dữ liệu không nên được thu thập.
- MDC values mặc định là **chuỗi**; có những `MdcEntryWriter` hỗ trợ chuyển kiểu, nhưng cần giới hạn theo field và kiểm tra schema.
- Encoder có thể hỗ trợ SLF4J 2.x **key-value pairs** của từng event theo cấu hình.
- Tên trường chuẩn mặc định của encoder (như `@timestamp`, `message`, `logger_name`) khác schema minh họa `timestamp`/`logger` ở trên.

Một kết quả JSON **minh họa hình dạng**, không khẳng định thứ tự key hoặc timestamp chính xác của appender:

```json
{"@timestamp":"2026-11-09T12:00:00Z","level":"INFO","logger_name":"demo","message":"event=order_received order_id=ORD-101","request_id":"req-101","tenant_id":"tenant-A"}
```

Muốn có typed event fields thay vì phải parse `event=...` từ message, có thể dùng fluent logging ở phần 10 cùng encoder thực sự hỗ trợ. Khi chuyển code demo phần 6 sang JSON, **stdout sẽ khác** bốn dòng text đã công bố ở phần 6; không dùng đồng thời hai cấu hình để yêu cầu một đầu ra cố định.

### Lưu ý về phiên bản

`logstash-logback-encoder` được bảo trì độc lập và phiên bản có thể đòi hỏi **mức Java tối thiểu hoặc Jackson version** khác nhau. Trước khi thêm artifact vào dự án Java 17, kiểm tra bảng tương thích chính thức; không khẳng định mọi phiên bản encoder đều chạy trên Java 17. Cấu hình minh họa ở trên là **mẫu cách hoạt động**, không phải full runnable Maven project.

Nguồn: https://github.com/logfellow/logstash-logback-encoder

## 9. Log4j2: ThreadContext và JsonTemplateLayout

Trong Log4j2, cơ chế tương đương MDC là **Thread Context Map**, thao tác bằng `org.apache.logging.log4j.ThreadContext`:

```java
import org.apache.logging.log4j.ThreadContext;

String previous = ThreadContext.get("request_id");
ThreadContext.put("request_id", requestId);
try {
    LOG.info("event=order_received order_id={}", orderId);
} finally {
    if (previous == null) {
        ThreadContext.remove("request_id");
    } else {
        ThreadContext.put("request_id", previous);
    }
}
```

Đây là snippet trong lớp dùng **Log4j2 API**, không phải chương trình độc lập.

### PatternLayout

Nếu chỉ cần text:

```xml
<PatternLayout charset="UTF-8"
    pattern="%p request_id=%X{request_id} tenant_id=%X{tenant_id} - %m%n"/>
```

Converter `%X{key}` lấy trường từ ThreadContext Map của LogEvent. Cấu hình nằm trong Appender; nó **không tự trở thành JSON**.

### JsonTemplateLayout

Log4j2 có **`JsonTemplateLayout`** dùng template và resolver; cần artifact `org.apache.logging.log4j:log4j-layout-template-json` phiên bản tương thích với `log4j-api`/`log4j-core`.

Ví dụ Appender:

```xml
<Console name="JSON" target="SYSTEM_OUT">
    <JsonTemplateLayout
        eventTemplateUri="classpath:MdcEvent.json"/>
</Console>
```

Đây là snippet nằm trong `<Appenders>` của `log4j2.xml`. Cần có `AppenderRef` ở root/logger. Đặt file `MdcEvent.json` trên classpath, ví dụ `src/main/resources/MdcEvent.json`.

Nội dung template **tối giản**:

```json
{
  "level": {
    "$resolver": "level",
    "field": "name"
  },
  "message": {
    "$resolver": "message",
    "stringified": true
  },
  "request_id": {
    "$resolver": "mdc",
    "key": "request_id"
  },
  "tenant_id": {
    "$resolver": "mdc",
    "key": "tenant_id"
  }
}
```

Các resolver trên là những thành phần được Log4j2 hỗ trợ: `level`, `message` và `mdc` với `key`. Template này **chỉ chọn bốn trường**; nó không tự đưa timestamp, exception, thread name hay event fields khác vào output. Muốn dùng production, cần bổ sung resolver theo schema, xác minh type/missing-value behavior và bảo đảm parser collector hiểu format.

**Không nhầm Log4j2 `ThreadContext` và SLF4J `MDC` là hai kho tách biệt luôn đồng bộ.** Khi dùng SLF4J qua một provider Log4j2 được cấu hình đúng, adapter có thể chuyển tới backend tương ứng; nếu runtime chọn backend khác, hành vi có thể khác. Tránh bridge vòng lặp và dùng một logging stack có chủ đích.

Tài liệu: https://logging.apache.org/log4j/2.x/manual/thread-context.html và https://logging.apache.org/log4j/2.x/manual/json-template-layout.html

## 10. MDC khác key-value pairs của một LogEvent

SLF4J 2.x có fluent logging API:

```java
LOG.atInfo()
        .addKeyValue("event", "order_created")
        .addKeyValue("order_id", orderId)
        .addKeyValue("duration_ms", durationMs)
        .log("Order created");
```

Đây là đoạn code minh họa trong lớp có `LOG` kiểu `org.slf4j.Logger`, `orderId` và `durationMs`. `addKeyValue` nhận `Object` nên `durationMs` có thể là số nguyên/long trong event, khác với `MDC.put` chỉ lưu chuỗi.

**Nên dùng gì?**

| Dữ liệu | Cơ chế gợi ý | Vì sao? |
| --- | --- | --- |
| `request_id` có trong nhiều sự kiện của request | MDC | Không cần truyền lại ID ở mọi lời gọi logger |
| `tenant_id` đã verified trong scope | MDC | Context chung của request/message/job |
| `trace_id` và `span_id` tương ứng scope | MDC hoặc tích hợp tracing/backend | Liên kết log và trace, quản lý vòng đời |
| `order_id` của một event | Per-event key-value | Đúng sự kiện, tránh rò sang operation khác |
| `duration_ms` là số | Per-event typed key-value | Giữ kiểu numeric cho thống kê |
| `http_status` là số | Per-event typed key-value | Giữ đúng type |
| `reason_code` của một kết quả | Per-event field | Giúp phân nhóm kết quả |
| `message` mô tả | Message template + parameters | Dễ đọc và có định dạng ổn định |
| `Throwable` | Cause của event | Giữ stack trace/cause chain |

**Lưu ý quan trọng:** fluent `addKeyValue` **không đảm bảo JSON field xuất hiện** nếu provider/encoder không hỗ trợ key-value serialization. Với PatternLayout text của phần 6, các cặp key-value có thể không được in vì pattern chỉ chứa `%msg`. Với một encoder JSON tương thích, chúng có thể trở thành các trường.

MDC và per-event fields có thể có key trùng nhau, ví dụ cả hai đều chứa `order_id`. Khi đó backend có thể ghi trùng JSON key, đặt object lồng nhau hoặc áp một quy tắc ưu tiên. **Đặt quy tắc ownership**: key nào thuộc MDC, key nào thuộc event, key nào do collector thêm. Tránh hai nguồn tự ghi cùng một field root.

## 11. Vì sao MDC values là string và cách giữ type

`MDC.put("attempt", "2")` có vẻ tiện, nhưng đầu ra thông thường:

```json
{"attempt":"2"}
```

khác:

```json
{"attempt":2}
```

Cả hai đều là JSON hợp lệ; tuy nhiên kiểu field khác:

- String `"2"` thích hợp nếu đó là **định danh**, ví dụ account code có số 0 đầu.
- Number `2` thích hợp nếu muốn **tính toán**, ví dụ số lần thử.
- Boolean `true` thích hợp với trạng thái nhị phân; string `"true"` không tương đương với boolean.
- Timestamp cần hợp đồng rõ: RFC 3339 string hay epoch milliseconds/nanoseconds.

**Không dùng cơ chế “tự đoán kiểu mọi MDC field” một cách mù quáng.** Một tenant ID như `"00123"` phải giữ số 0 đầu, không chuyển thành number `123`. Nếu dùng LogstashEncoder `MdcEntryWriter`, chỉ chuyển kiểu những trường được định nghĩa trước và có test schema.

Quy tắc hợp lý:

1. Giữ MDC cho **ID dạng chuỗi**.
2. Dùng per-event typed fields cho `duration_ms`, `retry_count`, `success`.
3. Encoder thống nhất names/types trước khi vào collector.
4. Ở collector, không tự biến mọi giá trị có vẻ numeric thành number nếu sẽ làm hỏng identifiers.
5. Schema test xác nhận cả **field value lẫn kiểu dữ liệu**.

## 12. JSON Lines và collector: “MDC đã xuất” chưa phải xong

Một hệ thống thu thập log container thường đọc **stdout/stderr** và mong **một event trên một dòng**. Với JSON Lines (NDJSON), mỗi LogEvent thường cần thành **một JSON object hoàn chỉnh trên một dòng UTF-8**, kết thúc bằng newline.

Ví dụ:

```json
{"level":"INFO","request_id":"req-101","tenant_id":"tenant-A","message":"Order received"}
{"level":"INFO","request_id":"req-102","tenant_id":"tenant-B","message":"Order received"}
```

Không nhầm với một JSON object pretty-printed nhiều dòng:

```json
{
  "level": "INFO",
  "request_id": "req-101"
}
```

Đó là JSON hợp lệ nếu đọc cả khối, nhưng collector có line framing có thể coi mỗi dòng là một event riêng và parse thất bại.

Checklist pipeline:

- **Một event / một dòng**, nếu collector không cấu hình multiline.
- **Escaping** đúng đối với newline, quote, backslash, control characters và stack trace.
- **MDC fields được xuất** đúng tên/path.
- **Timestamp** có múi giờ/đơn vị rõ, không bị collector thay bằng thời điểm ingest ngoài ý muốn.
- **Severity** mapping từ SLF4J/Logback/Log4j2 sang schema đích.
- **Collector parse JSON**, không chỉ giữ toàn bộ dòng dưới raw field `log`.
- **Không trùng nguồn** nếu vừa gửi stdout vừa ghi file được agent thu.
- **Không mất dữ liệu im lặng** vì queue, filter, size limit, sampling và retention.
- **Có bảo mật** cho đường truyền, dữ liệu và quyền truy cập kho log.

Một log có thể có MDC đúng ở stdout nhưng vẫn không tìm được `request_id` trên dashboard nếu collector chỉ index `message`. Cần thử **query trên field thực**.

## 13. Context propagation: thread pool là nguồn rủi ro lớn

MDC qua nhiều provider thường gắn với **thread hiện tại** hoặc cơ chế tương đương. Một task submit sang `ExecutorService` chạy trên thread khác không nên giả định MDC tự truyền.

Hai kiểu lỗi:

**Mất context:**

```text
HTTP thread: MDC.request_id=req-101
    |
    +--> executor.submit(task)
                 |
                 v
          worker thread: MDC.request_id rỗng
```

**Rò context khi tái sử dụng:**

```text
Worker xử lý task tenant-A -> còn MDC.tenant_id=tenant-A
     |
     v
Worker xử lý task tenant-B -> chưa đặt context -> log sai tenant-A
```

Giải pháp chung là **capture → set → run → restore**:

```java
Map<String, String> captured = MDC.getCopyOfContextMap();

executor.submit(() -> {
    Map<String, String> oldWorker = MDC.getCopyOfContextMap();
    try {
        if (captured == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(captured);
        }
        performWork();
    } finally {
        if (oldWorker == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(oldWorker);
        }
    }
});
```

Đây là snippet trong ứng dụng đã import `java.util.Map`/`org.slf4j.MDC`; `executor` và `performWork()` là thành phần có sẵn của ứng dụng.

**`getCopyOfContextMap` có thể trả `null`.** `setContextMap` thay thế map thread hiện tại theo API; không chỉ cập nhật một key. Vì vậy một decorator/framework cần có ownership rõ, tránh xóa nhầm context do library khác thiết lập.

Trong production, dùng task decorator/context propagation của framework nếu có và kiểm thử với thread pool thật. Đừng sao chép thủ công một đoạn wrap ở tất cả nơi submit task mà không quản lý thống nhất.

## 14. CompletableFuture, reactive, virtual threads và async logging

### CompletableFuture

`thenApplyAsync`, `thenComposeAsync` hoặc `supplyAsync` có thể chạy trên worker khác. Snapshot của thread submit phải được **áp dụng tại callback thực tế**; một context chỉ đặt ở đầu HTTP handler không mặc nhiên tồn tại trong toàn bộ chuỗi CompletableFuture.

### Reactive stack

Trong Reactor/RxJava, các tín hiệu có thể chuyển qua nhiều thread. **ThreadLocal không luôn theo được cả chuỗi xử lý**. Reactor có **Reactor Context** và cơ chế context propagation; nếu logging backend dùng MDC, cần bridge tại điểm phát LogEvent theo mô hình phù hợp.

### Virtual threads

Trong JDK 21+, virtual threads có ngữ cảnh ThreadLocal riêng theo thread. Chúng không tạo ra bảo đảm rằng context của task submit sẽ tự đến mọi virtual thread mới. Thiết kế theo đơn vị công việc, không chỉ theo tên thread.

### Async Appender / Async Logger

Một vấn đề khác là **thời điểm chụp MDC**:

- Context cần gắn với **LogEvent khi sự kiện được phát**.
- Async logging có thể xử lý formatting ở thread consumer khác.
- Nếu custom formatter tự gọi `MDC.get` tại **thời điểm format** ở consumer thread, nó có thể đọc sai/nghèo context.
- Logging framework thường có cơ chế snapshot/deferred processing theo implementation, nhưng **cần kiểm chứng backend, encoder và phiên bản cụ thể**.
- Không dựa vào việc MDC vẫn đang tồn tại khi hàng đợi xử lý sau này.

Khi thử tải lớn, xác minh ID context không bị trộn giữa events, kể cả lúc queue đầy, exception, shutdown hoặc deploy.

## 15. Structured logs và distributed tracing

MDC thường chứa `trace_id`, `span_id` hoặc `correlation_id` giúp đi từ một log event tới trace.

Một event liên kết trace có thể có:

```json
{
  "level": "ERROR",
  "service.name": "checkout-service",
  "trace_id": "4f9e7a1c",
  "span_id": "2a7c",
  "request_id": "req-101",
  "event": "payment_failed",
  "message": "Payment gateway unavailable"
}
```

Đây là **schema minh họa**; các giá trị trace ID giả định trong bài không phải trace context tuân đủ định dạng OpenTelemetry/W3C. Trong hệ thống thật, trace/span ID có độ dài và encoding quy định; phải lấy từ tracing instrumentation chứ không tự bịa.

**MDC không tự tạo distributed trace.** Nó chỉ giúp gắn và serialize context nếu code/instrumentation đã đưa ID đúng vào đó. Ngược lại, việc tracer có span đang chạy không bảo đảm MDC đã có `trace_id` nếu không có bridge/instrumentation.

OpenTelemetry có những khái niệm:

- **SpanContext**: trace/span IDs và flags.
- **LogRecord attributes**: dữ liệu có kiểu của sự kiện log.
- **Resource**: dữ liệu ổn định của entity phát telemetry, ví dụ `service.name`.
- **Baggage**: key-value có thể truyền qua service/process boundaries.

**Không dùng Baggage làm bằng chứng tenant authorization hoặc security principal.** Baggage có thể đến từ client không tin cậy và được truyền qua nhiều điểm. Nếu cần gắn tenant ID, hãy lấy từ trusted resolver/authorization và chỉ propagate những metadata được phép. Không đưa token vào MDC/Baggage.

Khi xuất log JSON để collector dùng OpenTelemetry data model, có thể phải mapping từ trường `request_id`/`trace_id` dạng text sang LogRecord attributes/TraceId thật. JSON object và OTLP payload **không phải hai thứ tương đương** chỉ vì cùng “structured”.

## 16. Xử lý Throwable trong structured logs

Một lỗi Java thường mang nhiều dữ liệu:

- Loại exception.
- Message của exception.
- Stack trace và cause chain.
- Context request/tenant/trace của thời điểm lỗi.
- Mức log và sự kiện nghiệp vụ như `order_save_failed`.

Ví dụ lời gọi:

```java
try {
    saveOrder();
} catch (RuntimeException e) {
    LOG.atError()
            .addKeyValue("event", "order_save_failed")
            .addKeyValue("order_id", orderId)
            .setCause(e)
            .log("Could not save order");
    throw e;
}
```

Đây là snippet SLF4J 2.x trong lớp có `LOG`, `saveOrder()` và `orderId`; không chạy độc lập. `setCause(e)` giữ đối tượng Throwable trong logging event cho encoder/backend xử lý. `throw e` là quyết định của code nghiệp vụ; logging tự nó **không throw hoặc rollback**.

JSON encoder có thể đưa exception vào `exception.class`, `exception.message`, `stack_trace` hoặc một trường khác tùy schema. Stack trace có xuống dòng phải được escape trong JSON string hoặc cấu trúc riêng; không để nó phá NDJSON framing.

**Không mặc định `e.getMessage()` là dữ liệu an toàn**: nó có thể chứa URL có token, path, input hoặc thông tin cá nhân. Cần chính sách ghi exception phù hợp và masking ở đầu nguồn.

**Tránh log trùng stack trace ở mọi tầng.** Cùng một Throwable được `ERROR` tại repository, service và controller rồi rethrow có thể tạo nhiều sự kiện gần giống nhau. Chọn ranh giới có trách nhiệm và giữ context đủ để điều tra.

## 17. JSON field collision và quyền sở hữu schema

Khi encoder lấy dữ liệu từ nhiều nguồn:

```text
LogEvent level, logger, message
MDC: request_id, tenant_id, event
Per-event: event, order_id, duration_ms
Collector: service_name, environment, trace_id
```

có thể xuất hiện **trùng key**. Đặc biệt:

- `event` có trong MDC và per-event attributes với giá trị khác.
- `service_name` do app viết nhưng collector lại gán lại.
- `timestamp` có cả thời điểm tạo và thời điểm nhận.
- `trace_id` từ tracing instrumentation mâu thuẫn với giá trị tự đặt.
- `user_id` do nhiều middleware cùng thêm vào context.

Một JSON object có thể chứa key trùng, nhưng nhiều parser chọn giá trị cuối hoặc có hành vi khác. Điều này khiến truy vấn khó tin cậy.

**Nên có quy tắc ownership:**

| Trường | Nguồn dữ liệu có trách nhiệm |
| --- | --- |
| `timestamp` | Logging event/encoder (event time) |
| `level` | Backend/encoder |
| `logger` | Backend/encoder |
| `service.name` | Cấu hình deployment/resource |
| `request_id` | Request context middleware |
| `tenant_id` | Trusted tenant resolver |
| `trace_id`/`span_id` | Tracing instrumentation/context |
| `event` | Lời gọi logging của nghiệp vụ |
| `order_id` | Event-specific value |
| `duration_ms` | Giá trị được đo cho từng event |
| `collector.received_at` | Collector khi cần, khác event time |

Đây là **quy ước minh họa**; tổ chức có thể có schema khác. Điều quan trọng là không để ba nơi viết cùng một tên field mà không có chính sách precedence và kiểm thử.

## 18. Bảo mật dữ liệu và chi phí lưu trữ

Structured logs có thể dễ tìm kiếm hơn, nhưng cũng dễ làm lộ dữ liệu nếu mọi giá trị MDC bị xuất hết.

### Dữ liệu nhạy cảm

- Không đưa password, API keys, bearer tokens, session cookies hoặc OTP vào MDC.
- Không sao chép mọi HTTP headers thành MDC; có thể chứa `Authorization`, cookie và dữ liệu cá nhân.
- Với `tenant_id`, `user_id` hoặc `account_id`, dùng ID nội bộ an toàn và kiểm soát chính sách riêng tư.
- Không cho user quyết định **tên MDC key** tùy ý; key động tạo schema và index biến động.
- Giới hạn độ dài value; sanitize CR/LF nếu xuất text. JSON encoder cần escape quote/control characters đúng.
- Đừng giả định việc filter dữ liệu ở collector đã bảo vệ những chặng **trước khi collector nhận**.
- Quy định retention, quyền truy cập, masking/redaction và audit truy vấn hệ thống log.

### Cardinality

`request_id` và `trace_id` thường có **rất nhiều giá trị duy nhất**. Trong hệ thống như Loki, không nên biến chúng thành indexed labels cho mọi event vì số lượng streams có thể tăng mạnh.

Chúng vẫn có thể được lưu ở **log line hoặc structured metadata** tùy hệ thống và phiên bản. Những nhãn có cardinality thấp hơn như `service`, `environment` hoặc `namespace` thường phù hợp hơn, nhưng vẫn cần kiểm tra thực tế.

### Chi phí

MDC map lớn làm tăng số trường trong mỗi event, byte xuất, chi phí encoding, mạng và storage. Đừng để toàn bộ request/session state vào MDC rồi xuất hết trên từng lời gọi logger.

**Nguyên tắc:** chỉ giữ những trường context lặp lại, nhỏ, hữu ích và đã được cho phép. Những payload lớn hoặc detail của một thao tác nên được xử lý trong event riêng với giới hạn cụ thể.

## 19. MDC trong HTTP filter, message consumer và scheduled job

### HTTP request

1. Xác thực/resolve metadata cần thiết.
2. Tạo hoặc chấp nhận `request_id` theo trust model.
3. Mở context scope; gắn `request_id`, tenant đã xác minh, trace ID nếu có.
4. Gọi controller/service/repository; context có mặt ở các lời gọi logger cùng execution scope.
5. Nếu chuyển sang async, dùng propagation bridge.
6. Đóng scope trong `finally`.
7. Không cho context của request A rò sang request B trên worker thread được tái sử dụng.

### Message consumer

Message có thể có `message_id`, `correlation_id` và tenant metadata. Không tin mọi trường đến từ producer bên ngoài khi chưa xác minh. Mỗi lần xử lý message nên có scope riêng; retry và dead-letter path cũng phải cleanup.

### Scheduled job

Đối với tác vụ định kỳ, thường cần `job_id`, `run_id`, `attempt` và `operation`. Nếu job xử lý nhiều tenant, **mỗi tenant cần scope riêng**, không gắn tenant A cho toàn bộ batch rồi xử lý tenant B dưới context A.

### Library hoặc interceptor

Một thư viện chỉ sở hữu `operation_id` không nên xóa toàn bộ MDC của request. Nên lưu giá trị cũ của **key mình sở hữu** và restore, hoặc dùng context scope abstraction có hợp đồng rõ.

### Authentication chưa hoàn tất

Log `auth_failed` xảy ra trước khi xác minh tenant thì **không nên** gắn `tenant_id` từ header chưa tin cậy. Nếu cần ghi tenant được yêu cầu, dùng field `requested_tenant_id_untrusted` theo schema/chính sách bảo mật và không để nó thay `tenant_id` tin cậy.

## 20. Kiểm thử đầu-cuối MDC và structured logging

Khi kiểm tra một triển khai, không dừng ở việc “thấy ID trên terminal”.

| Bước | Kiểm tra | Kết quả mong đợi |
| --- | --- | --- |
| 1 | Đặt MDC của request A | Event có `request_id=A` |
| 2 | Request B chạy cùng worker | Event B không mang `request_id=A` |
| 3 | Ném exception giữa xử lý | `finally` dọn hoặc khôi phục context |
| 4 | Nested scope A → B → A | Giá trị sau khi đóng B trở lại A |
| 5 | Async callback đổi thread | Có snapshot/apply context đúng |
| 6 | Structured JSON output | `request_id` là JSON field thực |
| 7 | Type check | `duration_ms` là number, `tenant_id` là string |
| 8 | Dữ liệu tiếng Việt | UTF-8 đúng trên collector |
| 9 | Quote/newline trong message | JSON parse được, không phá framing |
| 10 | Throwable có cause | Stack trace được xuất phù hợp schema |
| 11 | Backend khác hoặc nâng cấp encoder | Field names/paths không đổi ngoài kế hoạch |
| 12 | Collector nhận JSON từ stdout | Parser decode thành object và field |
| 13 | Dashboard query `request_id` | Trả đúng các sự kiện thuộc request |
| 14 | Không có request context | System events hợp lệ; tenant-scoped events được đánh giá theo policy |
| 15 | Secret/PII test | Không có token, password hoặc payload nhạy cảm |
| 16 | Hai nguồn thu stdout + file | Không tạo bản sao ngoài ý muốn |
| 17 | Load test queue async | Không trộn context, có số liệu drop/backpressure |
| 18 | Cardinality dashboard/labels | Không nổ indexed streams |
| 19 | Message consumer retry | Context theo từng attempt, không tái dùng sai |
| 20 | Dịch vụ khởi động trước request | Không gán tenant giả vào log khởi động |

### Cách xem JSON có phải structured không

Ví dụ log:

```json
{"message":"request_id=req-101 order_id=ORD-101"}
```

không tương đương với:

```json
{"message":"Order received","request_id":"req-101","order_id":"ORD-101"}
```

Cái thứ nhất có **một field message**; hệ thống phải parse text mới tìm riêng được `request_id`. Cái thứ hai có các **JSON fields độc lập**. Nhưng cả hai vẫn cần collector parse object và lưu đúng đường dẫn; JSON string thô trong wrapper container cũng chưa tự trở thành indexed fields.

### Với stdout và stderr

JUL `ConsoleHandler` mặc định ghi stderr, trong khi Logback ConsoleAppender có thể cấu hình `System.out`. Trong container, agent có thể thu cả hai stream. Kiểm chứng **đích thực** bằng cách tách stdout/stderr hoặc xem metadata của collector; đừng chỉ dựa vào việc log hiển thị trên terminal.

## 21. Những lỗi phổ biến cần tránh

**1. “MDC là structured log.”** Sai. MDC là context map; structured output cần encoder và collector phù hợp.

**2. “`MDC.put` tự tạo JSON field.”** Không được bảo đảm. Backend có thể không in MDC hoặc chỉ in vào text message.

**3. “Mọi MDC value có kiểu dữ liệu như Java object.”** SLF4J MDC map là string-to-string; number cần typed event field hoặc convert có kiểm soát.

**4. “Chỉ cần đặt MDC ở HTTP thread.”** Task async có thể chạy ở thread khác; cần propagation.

**5. “Thread pool tự dọn MDC.”** Không nên giả định. Cần cleanup/restore trong `finally`.

**6. “`MDC.putCloseable` khôi phục previous value.”** Nó remove key khi close; nested scopes phải chú ý.

**7. “Đọc MDC trong async formatter là an toàn.”** Formatter có thể chạy ở consumer thread khác; nên dựa vào snapshot context trong LogEvent.

**8. “SLF4J Simple, Logback và Log4j2 giống nhau.”** API/provider/encoder có khả năng và cấu hình khác.

**9. “Log có `request_id=...` trong message thì collector đã có field `request_id`.”** Không, có thể chỉ là text.

**10. “Mọi MDC key nên xuất JSON.”** Không. Whitelist keys và tránh secret/PII.

**11. “Mọi MDC key nên thành indexed label.”** Sai với cardinality cao như request/trace IDs.

**12. “`tenant_id` ở MDC đủ để phân quyền.”** Không. Authorization phải độc lập và dùng nguồn đáng tin.

**13. “Baggage cho phép tin tenant ID từ mọi request.”** Không. Baggage có thể bị giả mạo và truyền qua service boundary.

**14. “JSON hợp lệ thì mọi collector hiểu schema.”** Không. Collector còn cần đúng input, framing, parser, mapping và type.

**15. “`addKeyValue` bảo đảm encoder đưa đủ key/value vào JSON.”** Không. Provider/encoder hỗ trợ và cấu hình thế nào mới quyết định.

**16. “Có thể dùng cùng tên key trong MDC và event để dự phòng.”** Có thể gây collision, dữ liệu mâu thuẫn hoặc parser giữ một giá trị tùy ý.

**17. “Dùng logger name chứa request ID.”** Không nên tạo logger name động số lượng lớn; dùng metadata.

**18. “Log exception luôn an toàn.”** Exception message và stack trace có thể chứa dữ liệu nhạy cảm.

**19. “Đếm số dòng JSON là số giao dịch thành công.”** Logging có thể mất, trùng, lọc hoặc retry; trạng thái nghiệp vụ cần nguồn chính thức.

**20. “Đổi provider không ảnh hưởng dashboard.”** Field names, nested paths, severity, MDC support và schema có thể thay đổi.

## 22. Câu hỏi tự kiểm tra

1. **MDC giải quyết vấn đề gì?** Giữ một tập metadata chung cho nhiều sự kiện trong một scope xử lý.
2. **Structured logging khác MDC như thế nào?** Structured logging là biểu diễn sự kiện bằng các field typed; MDC là một nguồn ngữ cảnh có thể được encoder sử dụng.
3. **`MDC.put("duration_ms", "25")` tạo JSON number không?** Không mặc định; đó là string trong MDC.
4. **Muốn một `duration_ms` đúng kiểu number thì làm gì?** Dùng typed event field hoặc mapping/encoder chuyển kiểu có kiểm soát.
5. **Vì sao không đưa `order_id` của mọi event vào MDC?** Nó thường chỉ liên quan một event/operation và dễ rò sang event khác.
6. **SLF4J MDC có tự chọn JSON backend không?** Không; provider/encoder quyết định output.
7. **Logback PatternLayout lấy `request_id` từ MDC bằng gì?** `%X{request_id}`.
8. **Trong Log4j2, API ngữ cảnh tương đương là gì?** `ThreadContext`; JsonTemplateLayout có `mdc` resolver.
9. **`MDC.putCloseable` có tự restore previous value khi close không?** Không, nó remove key.
10. **`getCopyOfContextMap()` có thể trả null không?** Có.
11. **`MDC.setContextMap(map)` bổ sung hay thay thế map thread hiện tại?** Thay thế context map theo API.
12. **Vì sao phải khôi phục MDC của worker sau task?** Tránh bẩn context cho tác vụ tiếp theo trên thread tái sử dụng.
13. **`CompletableFuture.thenApplyAsync` có chắc cùng thread với request không?** Không.
14. **Vì sao một async JSON formatter không nên tự đọc ThreadLocal của caller?** Caller có thể là thread khác; LogEvent cần snapshot ngữ cảnh.
15. **Một JSON có `"message":"tenant_id=A"` đã có field `tenant_id` chưa?** Chưa, chỉ có message string.
16. **MDC có dùng làm xác thực tenant được không?** Không; nó chỉ là logging metadata.
17. **MDC có nên chứa token/access key không?** Không.
18. **Có nên đưa `request_id` vào label Loki có cardinality cao không?** Thường không.
19. **Nếu collector parse sai timestamp, điều gì xảy ra?** Log có thể nằm sai thời gian và gây sai kết quả truy vấn/cảnh báo.
20. **Có thể vừa có MDC và `addKeyValue` trên cùng event không?** Có, nhưng cần ownership/collision policy và encoder hỗ trợ.
21. **Một event có Throwable có tự được ghi đầy đủ trong JSON không?** Còn tùy encoder/schema và cách code truyền Throwable.
22. **Trong demo, vì sao bốn dòng có đúng request ID cho từng tenant?** Mỗi request có scope, worker nhận snapshot và khôi phục context; `Future.get` buộc hai task hoàn thành theo thứ tự đã gọi.

## 23. Checklist triển khai production

### Xác định ngữ cảnh

- Các MDC key có chủ sở hữu và mục đích rõ ràng.
- `request_id` được tạo/xác minh tại boundary.
- `tenant_id` là kết quả resolve/authorization, không phải header không tin cậy.
- Trace/span IDs lấy từ hệ thống tracing khi có, không tự tạo giả.
- Context được gắn vào mỗi request, message, job và callback thích hợp.

### Bảo vệ vòng đời

- Scope mở/đóng trong `try/finally`.
- Nested scope khôi phục giá trị trước đó khi cần.
- ExecutorService/CompletableFuture/reactive có propagation thích hợp.
- Không giữ object MDC mutable dùng chung giữa requests.
- Async logging chụp context đúng thời điểm; backend được kiểm thử khi upgrade.

### Output JSON

- Encoder hỗ trợ MDC và chỉ xuất những keys được whitelist.
- Event-specific fields có type đúng, đặc biệt number/boolean.
- Tránh key collision giữa MDC, event attributes và collector metadata.
- Có timestamp, level, logger, message và exception theo schema.
- Mỗi JSON event hoàn chỉnh trên một dòng nếu pipeline là NDJSON.
- JSON parser/collector giữ đúng field path, names, types và encoding.

### Vận hành và bảo mật

- Có test tìm theo `request_id`/`tenant_id` ở kho log.
- Không log secret, token hoặc PII không cần thiết.
- Có giới hạn size/cardinality, retention và quyền xem.
- Có metrics/thông báo parser errors, log drops, queue backlog.
- Không có hai đường thu trùng không chủ ý.
- Có contract tests khi thay provider/encoder.
- Cấu trúc log được quản lý như hợp đồng quan sát, không tùy tiện đổi field.
