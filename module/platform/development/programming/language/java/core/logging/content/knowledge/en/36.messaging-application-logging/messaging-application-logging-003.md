# Message Identifiers in Messaging Application Logging (Java Core)

## 1. Why Do We Need a Message Identifier?

Asynchronous applications often communicate via queues, topics, or brokers. When a producer sends a message, a consumer might process it seconds or hours later; when an error occurs, the broker may redeliver the message to another consumer, route it to a dead-letter queue (DLQ), or resend it after a retry. Consequently, producer and consumer logs can no longer be linked simply by a single Java call stack.

A **message identifier (message ID)** is an identifier that uniquely identifies a **logical message** or a **record in a messaging system**, depending on the application/broker contract. When designed properly, an ID helps answer:

- Which message was created, published, accepted by the broker, and received by a consumer?
- Did the consumer see the **same message** twice (redelivery), or two different messages with identical payloads?
- Which processing step failed, on which delivery/attempt, and was it acknowledged/committed?
- Which source message triggered a reply, derived event, or downstream task?
- Do logs across different services, threads, pods, and timestamps belong to the same message?

Example of logs correlated by `messageId`:

~~~text
service=checkout event=message_created   messageId=msg-1001 correlationId=flow-42
service=checkout event=publish_confirmed messageId=msg-1001 destination=orders
service=billing  event=message_received  messageId=msg-1001 correlationId=flow-42 attempt=1
service=billing  event=processing_failed messageId=msg-1001 attempt=1
service=billing  event=message_received  messageId=msg-1001 correlationId=flow-42 attempt=2
service=billing  event=message_processed messageId=msg-1001 attempt=2
~~~

Both deliveries here share the **same message ID** but have different `attempt` values, because the same message can be redelivered. However, having the same identifier **does not by itself prove** that business processing happened only once: that requires an explicit idempotency contract and dedicated state-tracking mechanism.

## 2. Distinguishing Commonly Confused IDs

| Field | Unit Identified | Where Is It Generated? | Should It Persist Across Retry/Redelivery? |
| --- | --- | --- | --- |
| **`messageId`** (application logical ID) | A logical message defined by the application | Usually generated by the producer or outbox before publishing | **Yes**, if resending the same logical message |
| **Broker record identity** | A specific record in the broker | Provided by the broker/transport, e.g., Kafka topic–partition–offset | Usually preserved when re-reading the same record; republishing creates a new record with a new identity |
| **`deliveryId`/delivery tag** | A specific message delivery attempt | Broker, client, or application wrapper | **Not necessarily**; a new delivery has a different identity |
| **`correlationId`** | A processing chain/request/transaction or request–reply pair | Origin application or protocol | Usually preserved across steps in the same workflow |
| **`causationId`** | The message/event that led to a new message | Producer at the downstream step | Usually points to the parent message ID |
| **`requestId`** | An HTTP/gRPC request or incoming system command | Gateway/entry point | Can be passed into the message as context, but does not replace the message ID |
| **`traceId` and `spanId`** | Distributed trace and individual spans | Tracing framework/instrumentation | Used for observability correlation, **not** as an idempotency key |
| **`idempotencyKey`** | A business operation that must not be executed repeatedly | Client/server per business contract | Depends on the goal; usually durable across retries of the same operation |
| **`eventId` of a log record** | An individual log event | Logging/ingest pipeline, if present | Preserved only when that specific log record itself is re-transported |

**No single ID replaces all others.** One request may emit multiple messages; one message may be delivered multiple times; one consumer may spawn multiple child messages. When all of these fields are logged under a generic `id` name, investigators struggle to tell a legitimate retry apart from unintended duplication.

Example of a relationship chain:

~~~text
HTTP request: requestId=req-1, correlationId=flow-42
   |
   +--> Message A: messageId=msg-A, causationId=req-1
          |
          +--> delivery 1 of A -> failed
          +--> delivery 2 of A -> succeeded
          |
          +--> Message B: messageId=msg-B,
                          causationId=msg-A,
                          correlationId=flow-42
~~~

Message B **must have a new ID** if it is a new logical message. It retains `correlationId` to participate in the same workflow, and carries `causationId=msg-A` to record the causal link. If you are only republishing A due to a timeout or uncertain ACK, you should keep **A's logical message ID**; the broker may assign a **new record identity** to that republished copy.

## 3. Choosing a Message ID with a Clear Scope and Contract

A useful contract should define:

1. **Who issues the ID?** Usually the producer generates it before sending, then writes the ID to both logs and headers/envelope. Do not wait until the consumer receives the message to generate the ID, as you lose the link to the publishing side.
2. **What is the uniqueness scope?** A single broker, tenant, cluster, environment, workflow, or the entire system? If `messageId` is used as a cross-system deduplication key, you must define a namespace/source or ensure sufficient uniqueness.
3. **Lifecycle and versioning:** Is the ID preserved across retries, republishes, and DLQ/re-drives, or replaced when creating a new business event? Distinguish it from the delivery ID to avoid confusion.
4. **Immutability:** Once a message is emitted, the ID of the same logical message must not be arbitrarily changed by a consumer.
5. **Format:** A string safe for logs, headers, and indexes, such as UUID v4, ULID, or an ID generated by a distributed unique-ID system. Do not assume any format guarantees absolute uniqueness; collisions, seeding bugs, or deployment errors still need to be evaluated at scale.
6. **Security semantics:** An ID is **not** proof of authentication, tenant permission, an access token, or a secret. Users can send forged IDs; you must authenticate the source, verify the tenant, and authorize independently.
7. **Cardinality:** Almost every message has a distinct ID; storing it as a **log field** is suitable for lookup, but you should not put every `messageId` into a metric label such as Prometheus labels.

Do not derive an ID solely from `payload.hashCode()` or a SHA-256 hash of the payload: two valid messages can have identical payloads, the input may contain sensitive data, and a raw hash does not represent the identity of each publish action. If the business requires a request-based **idempotency key**, build a separate canonicalization and key-expiration contract.

### Generating an ID in a Java Producer

In Java 17, the simplest approach is `UUID.randomUUID()`:

~~~java
import java.util.UUID;

// Snippet at the time a logical message is created.
String logicalMessageId = UUID.randomUUID().toString();
String correlationId = incomingCorrelationId != null
        ? incomingCorrelationId
        : UUID.randomUUID().toString();

MessageEnvelope envelope = new MessageEnvelope(
        logicalMessageId, correlationId, "order.created", payload);
publisher.publish(envelope);
~~~

This snippet is **not a standalone program**: `MessageEnvelope`, `publisher`, `payload`, and `incomingCorrelationId` are application-defined components. `UUID.randomUUID()` generates a version 4 UUID from a cryptographically strong random number generator suitable for general use, though it has no mechanism to mathematically guarantee zero collisions. If the payload/tenant or incoming headers have not been validated, do not use a client-supplied correlation ID as a security boundary.

**Critical step:** generate `logicalMessageId` **once when creating the envelope**, and persist it in an outbox if durable delivery is required. When retrying a publish due to a network error, reuse the **same envelope/ID**; do not call `randomUUID()` on every retry if you intend to identify the same logical message.

## 4. Where Should the Message ID Be Stored So Both Producer and Consumer Can Read It?

The message ID should reside in the **envelope or metadata/headers carried over the transport**, with consistent field names across services. Do not put it only in the producer's MDC: MDC lives in the producer thread's memory and does not travel automatically with the message to the consumer.

Example JSON envelope (illustrative, containing no real data):

~~~json
{
  "messageId": "msg-1001",
  "correlationId": "flow-42",
  "causationId": "cmd-9",
  "type": "order.created",
  "schemaVersion": 1,
  "occurredAt": "2026-11-10T08:00:00Z",
  "tenantId": "tenant-a",
  "payload": {
    "orderRef": "order-demo-7"
  }
}
~~~

There are two common implementation approaches:

- **Broker headers:** `message-id`, `correlation-id`, `traceparent` (if tracing), and application fields in headers. Suitable when you do not want to place metadata inside the body, though you must account for header preservation across connectors/brokers/bridges as well as length and data-type limits.
- **Application envelope:** metadata sits alongside the payload under a versioned schema. Suitable when messages move across multiple brokers or are stored in an outbox; you must validate it, avoid arbitrary object serialization, and avoid logging the entire body.

You may keep the ID in both the envelope and headers for convenience, but there **must be a single source of truth** and checks for mismatch/inconsistency: if `header.messageId` differs from `body.messageId`, treat it as a schema or tampering error rather than picking one arbitrarily and mixing logs. Never grant access solely because an ID or tenant header is present.

### Why Shouldn't the ID Be Embedded Only in Unstructured Log Text?

~~~java
logger.info("received {}", message.toString());
~~~

If `toString()` includes the payload, logs may leak emails, tokens, or PII; if the format changes, extracting the ID via substring matching becomes fragile. Prefer clear event messages with structured fields:

~~~java
// Snippet using SLF4J in a real application.
logger.info("event=message_received messageId={} correlationId={} type={}",
        messageId, correlationId, messageType);
~~~

The variables above should already be extracted and validated from the envelope. There is no need to dump the payload just to log the message identifier.

## 5. Kafka: Topic + Partition + Offset Is Not Equivalent to an Application Message ID

In Kafka, `ConsumerRecord<K,V>` provides `topic()`, `partition()`, `offset()`, `key()`, `headers()`, and other metadata. **Topic + partition + offset** identifies the position of a **record in the Kafka log** within a known cluster/namespace. It is very useful for locating the exact record a consumer received or debugging offset commits.

Kafka does not automatically provide a **universal, mandatory logical application `messageId`** to identify the same message across republishes or transformations. Nor is the Kafka record key **by default a message ID**: keys are typically used for partitioning or grouping records by entity, and multiple records can share the same key.

Kafka client **snippet** example, requiring the `org.apache.kafka:kafka-clients` dependency and a `ConsumerRecord` received by a consumer:

~~~java
import org.apache.kafka.clients.consumer.ConsumerRecord;

static void logRecord(ConsumerRecord<String, byte[]> record) {
    // Illustrative only: logger and decodeHeader are application helpers.
    String messageId = decodeHeader(record.headers(), "message-id");
    logger.info(
        "event=kafka_record_received topic={} partition={} offset={} messageId={}",
        record.topic(), record.partition(), record.offset(), messageId);
}
~~~

This is **not a standalone program**: `logger` and `decodeHeader` are not defined. Kafka headers can contain multiple values for the same key and store payloads as byte arrays; your helper must specify which header occurrence to read, which charset to use, size limits, and how to handle missing or invalid values. Do not call `new String(header.value())` with the platform default charset and assume all producers use the same encoding.

**Identification example:**

~~~text
Kafka record: topic=orders.events partition=2 offset=105 messageId=msg-1001
Consumer A re-reads record 105 after restart:
              topic=orders.events partition=2 offset=105 messageId=msg-1001
Producer republishes the same logical message:
              topic=orders.events partition=2 offset=118 messageId=msg-1001
~~~

In this example, re-reading the old record has the **same offset**; republishing creates a **new record with a different offset**, while preserving the same `messageId` if the application keeps the header. Seeing the same message ID alone does not tell you whether the consumer read the same record or a republished one; when investigating, keep **both the broker record identity and the logical message ID**. An offset is not a global ID across topics/partitions/clusters and is not an appropriate idempotency key for all republish scenarios.

Even with Kafka transactions and idempotent producers, delivery semantics still depend on producer/consumer configuration, isolation levels, offset commits, and external side-effect boundaries. Do not claim that "Kafka guarantees exactly-once for every database/email/HTTP call" solely based on having an offset or an ID.

## 6. RabbitMQ: `message_id` Is Different from Delivery Tag

In RabbitMQ AMQP 0-9-1, `message_id` and `correlation_id` are **optional message properties set by the publisher**. RabbitMQ **does not automatically require or generate a `message_id`** for every message. Therefore, an application that needs a stable ID should generate it at the producer and set it in properties/headers.

In addition to message properties, when the broker delivers a message to a consumer, it provides **delivery metadata**:

| Property | Nature | Notes |
| --- | --- | --- |
| `message_id` | Message ID defined by publisher convention | May be absent; uniqueness depends on the application contract |
| `correlation_id` | Links requests and replies/workflows | Does not have to equal `message_id` |
| `deliveryTag` | Delivery identifier used for ACK/NACK on a **channel** | **Scoped only to that channel**; not a global message ID |
| `redelivered` | Flag indicating the delivery may be a redelivery | Useful for diagnostics, **insufficient** to determine idempotency |
| `exchange`, `routingKey`, `consumerTag` | Routing/consumer context | Does not replace the logical message ID |

Publisher code **snippet**, requiring the RabbitMQ Java client and an existing `Channel`:

~~~java
import com.rabbitmq.client.AMQP;
import java.nio.charset.StandardCharsets;
import java.util.UUID;

String messageId = UUID.randomUUID().toString();
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
        .messageId(messageId)
        .correlationId("flow-42")
        .contentType("application/json")
        .deliveryMode(2)
        .build();

channel.basicPublish("orders.exchange", "orders.created",
        props, jsonBody.getBytes(StandardCharsets.UTF_8));
~~~

`channel` and `jsonBody` belong to the application; this is not a standalone runnable file. `deliveryMode(2)` expresses intent for a persistent message in the appropriate context, but **does not by itself guarantee** that the publisher knows the message was safely persisted. Use publisher confirms and verify routing/queue durability by design. When retrying a publish of the same logical message after an uncertain ACK error, reuse `messageId` rather than generating a new ID on each retry.

On the consumer side, log `message_id`, `deliveryTag` (along with channel/consumer context), `redelivered`, queue, and attempt if available. **Do not use `deliveryTag` as an idempotency key across channels**: tags can be reused across different channels and are not preserved across redeliveries.

## 7. Jakarta Messaging / JMS: Provider-Assigned Message ID

In Jakarta Messaging (JMS), **`JMSMessageID`** is a value **assigned by the provider upon sending**; by specification it starts with `ID:` and its uniqueness scope is provider-defined. Because the producer may not know the final value before sending, if the application needs an ID across multiple brokers or prior to `send`, it should maintain a **separate application logical ID** in a message property or envelope.

`JMSCorrelationID` is a separate property, typically set by the application to link a request with a reply or one message with another. `JMSRedelivered` indicates that the provider marks the message as redelivered; it does not replace an idempotency mechanism.

Consumer **snippet** requiring `jakarta.jms.Message`:

~~~java
import jakarta.jms.Message;

static void auditDelivery(Message message) throws Exception {
    String providerId = message.getJMSMessageID();
    String correlationId = message.getJMSCorrelationID();
    boolean redelivered = message.getJMSRedelivered();

    // Application-defined logger.
    logger.info(
        "event=jms_message_received providerMessageId={} correlationId={} redelivered={}",
        providerId, correlationId, redelivered);
}
~~~

This snippet is **not standalone** because `logger` is undefined and it requires the JMS API/provider. You should also avoid forcing `JMSMessageID` into a UUID-formatted application message ID; it belongs to the JMS provider's namespace. When correlating logs across two providers, also log `broker/system` or use a dedicated application-level ID.

## 8. Runnable Java 17 Example: One Message ID, Two Deliveries

To clearly observe the difference between **message ID** and **attempt**, the program below uses **JDK 17 only**, with no Kafka/RabbitMQ/JMS dependencies. It simulates receiving a single message envelope twice. Each delivery has its own attempt number, while **`messageId` remains the same**.

Create the file **`MessageIdentifierDemo.java`**:

~~~java
import java.util.HashSet;
import java.util.Set;
import java.util.logging.Handler;
import java.util.logging.Level;
import java.util.logging.LogRecord;
import java.util.logging.Logger;

public class MessageIdentifierDemo {
    record Envelope(
            String messageId,
            String correlationId,
            String causationId,
            String type) {}

    private static final Logger LOG =
            Logger.getLogger("demo.messaging.ids");

    // Test handler that prints only the message so stdout is independent of timestamps.
    private static final class PlainHandler extends Handler {
        @Override
        public void publish(LogRecord record) {
            if (isLoggable(record)) {
                System.out.println(record.getMessage());
            }
        }

        @Override
        public void flush() {
            // No I/O buffer.
        }

        @Override
        public void close() {
            // Holds no external resources.
        }
    }

    private static void receive(
            Envelope message, int attempt, Set<String> completed) {

        LOG.info("event=received messageId=" + message.messageId()
                + " correlationId=" + message.correlationId()
                + " causationId=" + message.causationId()
                + " attempt=" + attempt);

        // In-memory simulation only, NOT production idempotency.
        if (!completed.add(message.messageId())) {
            LOG.info("event=duplicate_skipped messageId="
                    + message.messageId());
            return;
        }

        LOG.info("event=processed messageId=" + message.messageId());
    }

    public static void main(String[] args) {
        LOG.setUseParentHandlers(false);
        LOG.setLevel(Level.ALL);

        PlainHandler handler = new PlainHandler();
        handler.setLevel(Level.ALL);
        LOG.addHandler(handler);

        try {
            Envelope message = new Envelope(
                    "msg-1001", "flow-42", "cmd-9", "order.created");
            Set<String> completed = new HashSet<>();

            receive(message, 1, completed);
            receive(message, 2, completed);

            System.out.println("logical_messages=" + completed.size());
        } finally {
            LOG.removeHandler(handler);
            handler.close();
        }
    }
}
~~~

Compile and run:

~~~bash
javac -encoding UTF-8 MessageIdentifierDemo.java
java MessageIdentifierDemo
~~~

**Deterministic stdout:**

~~~text
event=received messageId=msg-1001 correlationId=flow-42 causationId=cmd-9 attempt=1
event=processed messageId=msg-1001
event=received messageId=msg-1001 correlationId=flow-42 causationId=cmd-9 attempt=2
event=duplicate_skipped messageId=msg-1001
logical_messages=1
~~~

Key takeaways:

1. `msg-1001` is a fixed demo ID so stdout can be verified deterministically, **not how real IDs should be generated**. A real producer can use `UUID.randomUUID()` or a domain ID.
2. The two `event=received` lines represent **two deliveries/attempts**, not two logical messages. Both carry `messageId=msg-1001`.
3. `correlationId=flow-42` ties to the workflow; `causationId=cmd-9` describes the relationship to the preceding command.
4. `HashSet` only demonstrates the concept of recognizing an already-seen ID **within a single process and single run**. It is not durable across restarts, has no concurrency control, is not tied to a real transaction, has no expiration/retention, and updating the set before a real side effect succeeds can cause **lost processing** on crash. **Do not use this code as-is for exactly-once guarantees or duplicate-payment prevention in production.**
5. `PlainHandler` demonstrates how records flow through `java.util.logging` without injecting random timestamps or thread names into stdout; real applications use structured handlers/layouts, proper lifecycle management, and appropriate log levels.

### Why Not "One UUID per Consume"?

If a consumer generates `UUID.randomUUID()` on every receive and uses it as `messageId`, redeliveries of the same message will have two different IDs and their history cannot be linked. A consumer may create a separate **delivery processing ID** for each receive, but it must preserve the **original `messageId`** from the envelope/broker.

## 9. Using MDC to Correlate Logs Within a Single Message Execution

With SLF4J + an MDC-capable backend (such as Logback), an application can place `messageId` and `correlationId` into the **Mapped Diagnostic Context** so logs inside the handler automatically carry that context. **MDC is a thread-local context** and does not automatically cross broker boundaries.

Helper **snippet**, requiring `org.slf4j.MDC` (not a JDK-only program):

~~~java
import java.util.Map;
import org.slf4j.MDC;

static void withMessageContext(
        String messageId, String correlationId, Runnable processing) {

    Map<String, String> previous = MDC.getCopyOfContextMap();
    try {
        MDC.put("messageId", messageId);
        if (correlationId == null) {
            MDC.remove("correlationId");
        } else {
            MDC.put("correlationId", correlationId);
        }
        processing.run();
    } finally {
        if (previous == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(previous);
        }
    }
}
~~~

This is an illustrative method inside an application class; the caller must validate that `messageId` is non-null/non-blank, enforce character/length limits, and avoid putting tokens or PII into it. When a consumer pulls a message, it reads metadata from the envelope/broker, sets MDC inside `try/finally`, processes the message, and cleans up. Preserving `previous` avoids clobbering valid context in nested calls.

Example Logback pattern (snippet for an existing appender configuration):

~~~xml
<encoder>
    <pattern>%d{ISO8601} [%thread] %-5level msg=%X{messageId} corr=%X{correlationId} %logger - %msg%n%ex</pattern>
</encoder>
~~~

`%X{messageId}` only displays values **explicitly placed into MDC by code**. The pattern neither generates IDs nor propagates them automatically. Code running outside a message scope (startup, scheduled jobs without a message) may not have these fields; do not assign a random `messageId` system-wide just to keep the field non-empty.

### Worker Threads and Async Boundaries

When a message handler delegates work to an `ExecutorService` or `CompletableFuture`, the task may run on another thread. If MDC is set only on the consumer thread, the worker may lose the context; if not cleaned up, a task for message B may inherit message A's ID.

Capture/restore **snippet**:

~~~java
import java.util.Map;
import org.slf4j.MDC;

static Runnable withCapturedMdc(Runnable task) {
    Map<String, String> captured = MDC.getCopyOfContextMap();
    return () -> {
        Map<String, String> original = MDC.getCopyOfContextMap();
        try {
            if (captured == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(captured);
            }
            task.run();
        } finally {
            if (original == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(original);
            }
        }
    };
}
~~~

Call `withCapturedMdc(...)` **at submission time**, while the original message's context is still active. If a worker pool already has stale context leaked by earlier code, restoring `original` will not fix that leak; the system needs a clear lifecycle so each independent task exits with the right context.

When using async loggers/appenders, filters and encoders must read the context snapshot attached to the **log event** (or a backend-supported context carrier), rather than calling `MDC.get("messageId")` on the writer thread and assuming it belongs to the original message.

## 10. Message ID and Distributed Tracing

A message ID links **sends/receives of the same message**, whereas a trace ID links related execution spans across services and time. Both are valuable and do not replace each other.

A publish may create a message, which a consumer processes and then publishes another message. To preserve the trace, instrumentations typically propagate **W3C trace context** such as `traceparent` in message headers/envelope, and the consumer **extracts** it before starting a new span. OpenTelemetry defines semantic conventions for messaging spans and rules for producer/consumer context; passing a `correlationId` string alone should not be considered sufficient for cross-service distributed tracing.

~~~text
traceId=trace-1
  producer span: publish A, messageId=msg-A
  consumer span: process A, messageId=msg-A
  producer span: publish B, messageId=msg-B, causationId=msg-A
  consumer span: process B, messageId=msg-B
~~~

This is an illustrative model, not the actual `traceparent` format. Trace parents/links can vary depending on the messaging API and instrumentation—especially for batch receives, redeliveries, or fan-out where multiple contexts exist. Never fabricate a `traceparent` value by concatenating `messageId`. And **`traceId` is not an idempotency key**: multiple attempts/spans can process the same message.

When designing structured logging, you can include `messageId`, `correlationId`, `traceId`, and `spanId`, while ensuring you do not introduce unnecessary sensitive data or bloat each log line.

## 11. Idempotency, Redelivery, and Business Correctness

A message ID helps **recognize a previously seen message**, but it does not by itself prevent duplicate processing. In practice, message brokers typically provide at-least-once delivery under retries or reconnects, so side effects can occur before a consumer crashes prior to ACK/commit.

~~~text
Consumer receives msg-1001
  -> writes order to DB successfully
  -> crashes before ACK
Broker redelivers msg-1001
  -> without idempotency: writes/charges a second time
~~~

To handle this correctly, you typically need a **durable inbox/deduplication store** or a unique constraint scoped to a clear **processing scope**, committing the processed state in the **same transaction** as the side effect wherever atomicity can be guaranteed. For example, uniqueness on `(consumerName, messageId)` or `(businessOperationType, idempotencyKey)`, depending on the contract. Using `messageId` as a global lock across all consumers can be wrong: two different consumers may **both need** to process the same message.

A reference flow:

~~~text
Receive message
    |
    v
Validate schema, ID, tenant, and source permissions
    |
    v
Transaction: check claim/idempotency key
    |
    +-- Already successfully processed -> do not apply additional side effects
    |
    +-- Not yet processed -> apply side effect + record processed status
    |
    v
DB transaction commits successfully
    |
    v
ACK/commit broker progress per contract
~~~

You cannot conclude "system-wide exactly-once" merely because you logged a message ID. For emails, webhooks, payment gateways, or external databases, an internal transaction does not necessarily cover external side effects; you need idempotent APIs, an outbox, or saga/compensation mechanisms depending on the case.

**Relationships between IDs during retries:**

- **Broker redelivers the same message:** keep `logicalMessageId`; increment `deliveryAttempt` if the application/broker provides reliable metadata; delivery tag/offset follow transport-specific semantics.
- **Producer retries publish after confirm timeout:** try to keep the same logical ID, accepting that the broker may create a new record; deduplicate at the consumer/storage layer per contract.
- **Routing to DLQ:** preserve `originalMessageId` and error/source metadata; if the DLQ uses a new wrapper message, it may have its own `dlqMessageId` without losing the source ID.
- **Re-drive/repair:** if reprocessing the same message, retain the source identity and record a separate `replayId`/`replayAttempt`; if creating a genuinely new business event, use a new ID and point `causationId` to the old ID.
- **Creating downstream messages:** generate a new `messageId`, preserve the appropriate `correlationId`, and set `causationId` to the source message.

## 12. Which Lifecycle Milestones Should Be Logged?

A message typically follows the lifecycle below. Log only at meaningful milestones; avoid `INFO` for every individual item under high throughput when metrics/traces already cover it.

| Milestone | Suggested Event | Useful Metadata |
| --- | --- | --- |
| Envelope created | `message_created` | `messageId`, `type`, `correlationId` |
| Publish requested | `publish_requested` | `messageId`, `destination`, `producerInstance` |
| Broker confirm/ack publish | `publish_confirmed` | `messageId`, `brokerRecordIdentity` if available |
| Consumer received | `message_received` | `messageId`, `consumer`, `destination`, delivery metadata |
| Processing started | `processing_started` | `messageId`, `attempt`, `traceId` |
| Business processing succeeded | `processing_succeeded` | `messageId`, processing outcome, duration |
| Retryable failure | `processing_retry_scheduled` | `messageId`, `attempt`, `reasonCode`, retry policy |
| Skipped because already completed | `duplicate_ignored` | `messageId`, consumer scope |
| ACK/commit broker progress | `message_acknowledged` | `messageId`, `offset`/`deliveryTag` (within proper scope) |
| Routed to DLQ | `message_dead_lettered` | `originalMessageId`, `reasonCode`, source/destination |

**Do not equate "processed" with "acked".** Business logic may commit successfully while the ACK fails; a redelivery is not necessarily a new business execution. Similarly, "publish requested" does not prove the broker accepted the message; log the confirmation or delivery result when the API/transport supports it.

Example structured log line:

~~~json
{
  "event": "message_processed",
  "messageId": "msg-1001",
  "correlationId": "flow-42",
  "causationId": "cmd-9",
  "transport": "kafka",
  "destination": "orders.events",
  "partition": 2,
  "offset": 105,
  "consumer": "billing-worker",
  "attempt": 2,
  "outcome": "success",
  "durationMs": 27
}
~~~

This JSON is **illustrative only**. In real environments, `offset`/`partition` only make sense for applicable brokers; `attempt=2` must come from policy-backed metadata rather than guessing from `redelivered=true`. If logs span multiple tenants, `tenantId` must come from an authenticated source, never trusting a client-supplied header directly as an access boundary.

## 13. Security, Personal Data, and Untrusted Input

Message headers sent by producers are **potentially untrusted data**; another service or external client can pass an arbitrary ID. Before writing an ID to logs, indexes, or MDC:

- **Enforce size and character-set limits**, such as UUIDs or an allowed ASCII subset; reject newlines, carriage returns, and control characters to mitigate log injection.
- **Do not trust an ID as proof of authentication/authorization.** An attacker may know a `messageId` and attach it to a forged message; tenant permissions must be verified at the business layer.
- **Do not use access tokens, cookies, emails, phone numbers, or government IDs as `messageId`.** Stable IDs can still enable historical correlation, so retention policies, RBAC, and re-identification risks must still be evaluated.
- **Do not dump all headers/body** just to capture an ID. Headers can contain `Authorization`, JWTs, PII, payloads, or routing secrets.
- **Keep schemas consistent and avoid formatting bugs:** a missing identifier must not silently turn into `"null"` that conflates unrelated messages; emit a separate `missing_message_id` indicator to surface issues.
- **Do not create metric labels per `messageId`.** Use metrics keyed by `event type`, `queue`, `consumer`, `outcome`, and `reasonCode` (bounded sets). Looking up by `messageId` belongs in indexed logs/traces with appropriate retention.

Safer code must sanitize/validate nulls and control characters **before** passing an ID to the logger; do not rely on `logger.info("id={}", id)` to sanitize input automatically. When a source ID cannot be verified, you can generate a temporary ID for a **delivery** (named `deliveryLogId`), without pretending it is a verified logical `messageId`; log a warning about missing metadata and handle it per policy.

## 14. Testing Message IDs and Observability

### Functional Tests

1. **Producer creates a logical message:** ID is present, matches the expected format, and does not change across publish retries of the same envelope.
2. **Two distinct messages:** IDs differ per contract (for random UUIDs, tests should not rely on absolute uniqueness guarantees; you can inject a deterministic ID generator).
3. **Redelivery:** same `messageId` across two attempts, with logs containing `attempt`/delivery metadata distinguishing each delivery.
4. **Kafka:** re-reading the same record preserves topic/partition/offset; republishing creates a different record identity while the application message ID can be preserved.
5. **RabbitMQ:** `message_id` is optional, `correlation_id` is separate; `deliveryTag` is channel-scoped; never use the tag as a global ID.
6. **JMS:** `JMSMessageID` is provider-assigned, `JMSCorrelationID` is client-correlated; do not assume `JMSMessageID` is a UUID.
7. **Consumer fan-out:** downstream messages receive new IDs, causation points to the parent message, and correlation is preserved per workflow.
8. **MDC:** on a single-worker thread pool, process message A, then B, then a task without a message, and verify no ID leaks.
9. **DLQ/re-drive:** `originalMessageId` remains traceable after routing/replay; retry/attempt metadata is not wiped out.
10. **Idempotency:** side effects do not repeat for the same message within the same processing scope, even after a crash post-commit and pre-ACK (requires integration tests with a durable store/broker).
11. **Malicious input:** IDs containing newlines, excessive length, wrong tenant, or missing/conflicting header vs. body; must be validated or rejected per policy.
12. **Performance:** high-throughput messages do not cause index/metric cardinality or log volume explosions from dumping payloads or headers.

### Troubleshooting Table

| Symptom | Common Cause | Fix |
| --- | --- | --- |
| Producer logs an ID, consumer logs are empty | Header/envelope not propagated, wrong key/charset | Standardize schema, assert in integration tests |
| Same message gets a different ID after retry | Retry constructs a new envelope/UUID | Generate once, persist ID in outbox/message |
| Kafka offset differs but application ID is the same | Republished as a new record | Log both logical ID and topic/partition/offset |
| RabbitMQ `deliveryTag` matches across two channels | Tag is scoped only to a single channel | Never use `deliveryTag` as a global message ID |
| Log for A carries B's ID in a worker pool | Stale MDC or broken propagation | Capture/restore MDC and clean up per task |
| Logs show one message processed twice | Redelivery after crash or uncertain ACK | Durable deduplication + idempotent side effects |
| Cannot correlate reply with request | Missing or misconfigured correlation ID | Define request–reply convention, preserve correlation on reply |
| DLQ cannot trace back to source | New wrapper dropped `originalMessageId` | Preserve source metadata/causation |
| Dashboard counts one retry as multiple failures | Counting every delivery/`ERROR` as a logical operation | Count by outcome/idempotency scope, distinguish attempts |
| Message ID leaks sensitive data | Using email/token/PII as the ID | Generate independent IDs, enforce log safety and access control |
| Trace cannot be linked despite having `messageId` | Message ID is not a trace context | Propagate `traceparent`/context via instrumentation |

## 15. Concise Implementation Checklist for Java Applications

1. **Define the contract:** specify the scope in which `messageId` identifies a logical message; use `correlationId` for workflows, `causationId` for parent–child links, and separate fields for broker record/delivery metadata.
2. **Generate the ID at the producer** and place it in the envelope/headers, persisting it in an outbox if using durable publishing. Never change `messageId` when retrying the same message.
3. **Validate at the consumer:** ensure the ID is trustworthy/well-formed, the schema version matches, and the tenant/source is authenticated. Never treat an ID as an access-control credential.
4. **Log clear milestones:** created, publish requested/confirmed, received, processing outcome, retry, ACK/commit, DLQ. Distinguish different success/skip states.
5. **Bind MDC to the message scope** and clear it in `finally`; propagate snapshots across async boundaries so `messageId` never leaks between threads or tasks.
6. **Preserve broker identity** such as Kafka topic/partition/offset, RabbitMQ delivery tag + channel, or JMS provider ID, without treating any of them as equivalent to a logical message ID.
7. **Design idempotency separately** using transactions, an inbox table/unique constraints, and side-effect contracts; `messageId` is only one input for identification.
8. **Test redelivery, republish, DLQ, and multi-consumer flows**, including crashes/failed ACKs and messages with missing headers.
9. **Protect logs:** do not log payloads/PII/secrets, constrain input IDs, enforce RBAC/retention, and avoid high-cardinality metric labels.
10. **Measure and alert:** track missing-ID rates, duplicate deliveries, retries, DLQ volume, lag/offset commits, and publish–ack discrepancies by backend.

**Remember:** A message identifier traces a **logical message**; broker record identity locates a **record in the transport**; delivery metadata identifies a **delivery attempt**; correlation/causation/trace link **steps of a workflow**. Keeping these roles distinct—especially across retries and redeliveries—ensures your logs tell you what actually happened without conflating multiple deliveries with multiple business messages.
