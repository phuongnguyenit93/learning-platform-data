# MDC theo request trong Java Logging: gắn requestId, truyền ngữ cảnh và tránh rò rỉ giữa các luồng

## 1. MDC theo request là gì?

**MDC** (*Mapped Diagnostic Context*) là một tập các cặp **key–value dạng chuỗi** được logging backend liên kết với ngữ cảnh thực thi. Khi áp dụng **MDC theo request**, hệ thống đặt những trường như `requestId`, `correlationId`, `traceId` hoặc `operation` tại ranh giới nhận request để các lệnh log ở những lớp sâu hơn tự mang thông tin liên kết đó, không cần truyền `requestId` vào mọi lời gọi `LOG.info(...)`.

Ví dụ hai request cùng đi qua một service:

~~~text
requestId=req-A level=INFO  logger=OrderController msg="request received"
requestId=req-B level=INFO  logger=OrderController msg="request received"
requestId=req-A level=INFO  logger=OrderService    msg="inventory reserved"
requestId=req-B level=WARN  logger=PaymentService  msg="retry scheduled"
requestId=req-A level=INFO  logger=OrderController msg="request completed"
~~~

Nhìn `requestId`, người điều tra có thể gom các log liên quan mặc dù chúng xen kẽ trên nhiều thread và lớp Java.

**MDC không phải request object và không tự tạo distributed trace.** Nó là một cách bổ sung ngữ cảnh cho **log event**. Muốn theo dõi request đi qua nhiều service, cần bảo đảm ID được truyền qua ranh giới HTTP/message và cấu hình logging ở từng service; nếu muốn phân tích quan hệ nhân quả, duration và span, cần cơ chế distributed tracing riêng.

**Phân biệt hai vấn đề cốt lõi:**

- **MDC scope:** khi request bắt đầu, trường được đặt; khi kết thúc hoặc xảy ra exception, MDC phải được dọn/khôi phục.
- **MDC propagation:** khi xử lý nhảy từ thread nhận request sang thread pool, CompletableFuture, scheduler hoặc callback, MDC phải được truyền và áp dụng tại thread thực thi phù hợp. MDC thường không tự đi qua mọi ranh giới bất đồng bộ.

Hai vấn đề này độc lập. Một ứng dụng có thể dọn request thread rất tốt nhưng vẫn **mất requestId** trong worker; hoặc truyền đúng tới worker nhưng quên dọn, khiến request tiếp theo có **requestId sai**.

## 2. MDC nằm ở đâu trong luồng logging?

Trong hệ sinh thái **SLF4J + Logback**, ứng dụng thường gọi các API:

~~~java
// Snippet trong một phương thức có SLF4J/Logback trên classpath.
org.slf4j.MDC.put("requestId", "req-A");
LOG.info("operation=checkout phase=started");
org.slf4j.MDC.remove("requestId");
~~~

MDC được đọc tại thời điểm tạo/chuẩn bị log event theo cơ chế backend, sau đó layout/encoder có thể đưa giá trị đó vào dòng text hoặc JSON.

~~~text
HTTP request / background job
          |
          v
[Boundary: chọn và xác thực requestId]
          |
          v
[MDC.put("requestId", requestId)]
          |
          +----> Controller LOG.info("received")
          |
          +----> Service    LOG.info("processing")
          |
          +----> Repository LOG.warn("retry")
          |
          +----> Async task [cần copy/install context ở worker]
          |
          v
[Boundary finally: remove/clear/restore MDC]
          |
          v
Thread quay lại thread pool, sẵn sàng nhận request khác
~~~

**Các phần cần phân biệt:**

- **SLF4J MDC API:** `org.slf4j.MDC.put`, `get`, `remove`, `clear`, `getCopyOfContextMap` và `setContextMap`.
- **Backend:** Logback Classic cung cấp cơ chế lưu/ngữ nghĩa MDC mà logging event có thể sử dụng. Backend/provider khác có mức hỗ trợ MDC khác nhau.
- **Layout/encoder:** Logback PatternLayout có `%X{requestId}` để lấy giá trị. Nếu pattern không in MDC, việc đặt `MDC.put(...)` **không tự khiến requestId xuất hiện** trên console.
- **Collector:** cần parse text hoặc nhận field structured từ encoder để tìm kiếm theo `requestId`.

### 2.1. MDC thường gắn với thread, không phải global map

Giả sử thread `http-1` đang xử lý `req-A` còn `http-2` xử lý `req-B`. Mỗi thread cần có MDC tương ứng. Một giá trị MDC có thể được dùng bởi nhiều logger trên cùng thread mà không truyền nó qua tham số của mọi phương thức nghiệp vụ.

Điều này **khác với biến static**:

~~~java
// SAI: state dùng chung mọi request có thể bị ghi đè.
static String currentRequestId;
~~~

Hai request đồng thời ghi cùng một biến sẽ gây lẫn ID. MDC có adapter quản lý ngữ cảnh theo cách chuyên biệt của backend; tuy nhiên bạn vẫn phải nắm rõ chính sách thread-local và propagation, đặc biệt khi ứng dụng dùng framework bất đồng bộ.

### 2.2. MDC chỉ bổ sung metadata, không thay message và exception

Một dòng log hữu ích vẫn cần operation, event code (nếu có), outcome và exception khi cần:

~~~java
// Snippet: LOG là SLF4J Logger, e là Throwable cần chẩn đoán.
LOG.error("operation=checkout outcome=failed", e);
~~~

Nếu MDC có `requestId=req-A` và layout in `%X{requestId}`, bản ghi trên sẽ chứa ID mà không cần chèn lại `req-A` trong message. **MDC không tự giữ stack trace/cause**; điều đó phụ thuộc cách truyền `Throwable` và cách formatter/encoder xuất nó.

## 3. Chọn requestId và các trường đặt trong MDC

Một bộ field tối thiểu, thực dụng cho HTTP request:

| Field | Mục đích | Lưu ý |
| --- | --- | --- |
| `requestId` | Nối các log cùng một request trong service | ID ngắn/gọn, được kiểm tra độ dài và ký tự |
| `correlationId` | Nối các bước nghiệp vụ qua dịch vụ hoặc message | Có thể bằng requestId hoặc khác, cần hợp đồng rõ |
| `traceId` | Liên kết tới distributed trace nếu có instrumentation | Không tự sáng tạo trace hợp lệ bằng MDC |
| `spanId` | Liên kết tới span tương ứng nếu có | ID phải lấy từ trace context thực |
| `operation` | Tên thao tác có tập giá trị hữu hạn | Ví dụ `checkout`, `load-order` |
| `tenantId` | Hỗ trợ phân vùng điều tra khi được phép | Chỉ dùng ID đã được phê duyệt, bảo vệ phân quyền |
| `userId` | Liên kết tới tài khoản khi chính sách cho phép | Không mặc định ghi email/tên/PII |
| `clientIp` | Thông tin mạng khi có lý do nghiệp vụ/bảo mật | Có thể là dữ liệu cá nhân; cân nhắc retention |

**Đừng nhét mọi thứ vào MDC.** MDC thường được đính kèm vào nhiều log event và nhiều appender, vì vậy thêm một trường dài hoặc nhạy cảm có thể làm tăng dữ liệu lưu trữ và mức độ lộ thông tin. Tập key/value nên nhỏ, ổn định, được kiểm soát và có tài liệu.

### 3.1. ID từ header của client là input không tin cậy

Một hệ thống có thể nhận `X-Request-ID` từ reverse proxy đáng tin hoặc từ request bên ngoài. Nếu lấy nguyên giá trị header mà không kiểm tra, người gửi có thể đưa CR/LF, dấu ngoặc, chuỗi dài hoặc giá trị cố tình gây nhiễu vào log.

Chính sách đề xuất:

1. Ưu tiên ID do **ingress/gateway đáng tin** cấp theo hợp đồng đã thống nhất.
2. Nếu nhận từ header, **giới hạn độ dài và whitelist cú pháp**.
3. Khi header thiếu/sai, tạo ID mới hoặc dùng ID từ tracing system tin cậy; không dùng nguyên header lỗi.
4. Không cho header tự quyết định user identity, tenant membership hay quyền truy cập.
5. Nếu cần trả requestId trong response header để hỗ trợ khách hàng, trả ID đã được xác thực/chọn bởi server.

Ví dụ một phép kiểm cú pháp (đây chỉ là snippet, không phải policy bắt buộc):

~~~java
// rawHeader có thể là null hoặc chứa input không tin cậy.
boolean valid = rawHeader != null
        && rawHeader.matches("[A-Za-z0-9_-]{1,64}");

String requestId = valid
        ? rawHeader
        : java.util.UUID.randomUUID().toString();
~~~

Regex từ chối dấu gạch chéo, newline và chuỗi quá dài; chính sách thực tế có thể khác tùy hệ thống. **Kiểm tra cú pháp không đồng nghĩa header đáng tin về nguồn gốc**: một attacker vẫn có thể gửi một ID đúng regex nhưng trùng ID của người khác. Với yêu cầu bảo đảm tính duy nhất/tính xác thực, cần quản lý việc phát sinh ID ở trusted boundary.

### 3.2. requestId khác traceId

`requestId` là định danh một request theo thiết kế ứng dụng; `traceId` thuộc trace context của một hệ thống tracing. Một trace có thể chứa nhiều span và có thể gắn với nhiều downstream request. Nếu có OpenTelemetry/W3C Trace Context, ưu tiên **lấy traceId từ context thật** và cấu hình tương quan logs/traces, thay vì tự đặt một string bất kỳ vào `traceId`.

Không đồng nhất ba giá trị này trong mọi ứng dụng:

~~~text
requestId = ID của request HTTP cục bộ
correlationId = ID liên kết nghiệp vụ xuyên nhiều bước
traceId = ID do tracing system tạo/duy trì
~~~

Chúng có thể được ánh xạ với nhau theo quy ước riêng, nhưng sự khác nhau cần được giải thích để dashboard và tracing không hiểu sai.

## 4. Vòng đời MDC cho một request đồng bộ

Một request đơn giản có các bước:

1. **Nhận request** tại filter/interceptor/middleware.
2. **Đọc hoặc sinh requestId**, kiểm tra tính hợp lệ.
3. **Chụp lại ngữ cảnh trước đó nếu cần**, để không phá MDC của một scope bên ngoài.
4. **Cài context của request** trước những lệnh log cần tương quan.
5. **Thực hiện business logic**; logger tại nhiều lớp tự lấy requestId từ MDC.
6. **Ghi kết quả và xử lý lỗi** trong cùng ngữ cảnh.
7. **Khôi phục/dọn MDC ở finally**, kể cả khi business logic ném exception hoặc response trả sớm.

Sơ đồ:

~~~text
Thread P1
  |
  +-- request A: put req-A --> log A1 --> log A2 --> finally cleanup
  |
  +-- request B: put req-B --> log B1 --> log B2 --> finally cleanup
  |
  +-- idle/housekeeping: MDC không còn req-A hoặc req-B
~~~

Cách nguy hiểm:

~~~java
// SAI nếu xử lý ném exception trước dòng remove().
MDC.put("requestId", requestId);
processRequest();
MDC.remove("requestId");
~~~

Nếu `processRequest()` ném exception, dòng `remove` không chạy. Thread có thể được thread pool tái sử dụng và sự kiện của request kế tiếp bị gắn ID cũ.

**Dùng finally:**

~~~java
// Snippet trong phương thức có requestId và processRequest().
MDC.put("requestId", requestId);
try {
    processRequest();
} finally {
    MDC.remove("requestId");
}
~~~

Cách này phù hợp khi phạm vi hiện tại **sở hữu riêng key requestId** và không cần phục hồi giá trị cũ. Nếu có scope lồng nhau hoặc MDC được set trước khi vào, nên chụp và **restore map cũ**, tránh xóa nhầm context của caller.

### 4.1. MDC.putCloseable có thể giúp scope ngắn

SLF4J cung cấp `MDC.putCloseable(key, value)`:

~~~java
// Snippet: MDC của SLF4J trên backend hỗ trợ.
try (MDC.MDCCloseable ignored =
        MDC.putCloseable("requestId", requestId)) {
    LOG.info("request accepted");
}
~~~

`MDCCloseable` là đối tượng `Closeable` phù hợp với `try-with-resources`. Khi đóng, nó **remove key**, giúp quên dọn ít xảy ra hơn.

**Điểm tinh tế:** theo hợp đồng SLF4J, đóng `MDCCloseable` loại bỏ khóa; **không cam kết khôi phục giá trị cũ của cùng key**. Vì vậy, với nhiều scope lồng nhau đã có `requestId` khác, đừng xem `putCloseable` là một stack context tự phục hồi. Với tình huống đó, dùng snapshot + restore rõ ràng.

## 5. Snapshot, restore và MDC leakage

Các API chính của SLF4J:

| API | Công dụng |
| --- | --- |
| `MDC.put(key, value)` | Đặt/ghi đè một key trên context hiện tại |
| `MDC.get(key)` | Đọc giá trị của key tại context hiện tại |
| `MDC.remove(key)` | Gỡ một key, không ảnh hưởng các key khác |
| `MDC.clear()` | Xóa toàn bộ map MDC hiện tại |
| `MDC.getCopyOfContextMap()` | Lấy **bản sao** map hiện tại; có thể trả null |
| `MDC.setContextMap(map)` | Thay map hiện tại bằng một bản sao của map được đưa vào |
| `MDC.putCloseable(key, value)` | Tạo scope tự gỡ key khi close |

Để dùng snapshot/restore:

~~~java
// Snippet trong lớp có import org.slf4j.MDC và java.util.Map.
Map<String, String> before = MDC.getCopyOfContextMap();
try {
    MDC.clear();
    MDC.put("requestId", requestId);
    performRequest();
} finally {
    if (before == null || before.isEmpty()) {
        MDC.clear();
    } else {
        MDC.setContextMap(before);
    }
}
~~~

Đây là ví dụ trong phương thức có sẵn `requestId`/`performRequest()`. Nó **cố ý mở một context sạch cho request**, rồi phục hồi chính xác map trước khi vào. Nếu ứng dụng có những field ngoài request cần duy trì trong suốt xử lý (chẳng hạn môi trường hoặc service), hãy thiết kế **allowlist merge** hoặc đặt field đó trong encoder/configuration, không mặc định xóa hết mọi ngữ cảnh có ý nghĩa.

**Sao chép map là cần thiết** khi đi qua ranh giới thread: bạn không nên truyền một tham chiếu mutable được chia sẻ rồi thay đổi dữ liệu sau khi enqueue. `getCopyOfContextMap()` trả bản sao tại thời điểm gọi. `setContextMap(...)` thay context của thread thực thi, không chuyển dữ liệu một cách kỳ diệu tới mọi thread khác.

### 5.1. Phân biệt clear và remove

- `remove("requestId")` chỉ xóa một key: phù hợp nếu code hiện tại sở hữu key đó và các key khác phải giữ nguyên.
- `clear()` xóa toàn bộ MDC của **thread hiện tại**: phù hợp ở boundary sở hữu toàn bộ scope, nhưng có thể xóa context của framework nếu dùng không đúng chỗ.
- `restore(snapshot)` khôi phục trạng thái trước scope: phù hợp với nested scopes, thread pool worker và ứng dụng có nhiều nguồn context, nhưng **không tự sửa một snapshot vốn đã bị rò từ trước**.

Cần xác định contract: ai là owner của context? Ai đặt/ai dọn? Khi có nested scope hoặc async callback, ai chịu trách nhiệm restore? Nếu không xác định, dự án rất dễ có log sai requestId.

## 6. Ví dụ đầy đủ trên Java 17: MDC theo hai request và một worker thread

Ví dụ sau dùng **Java 17**, **SLF4J API 2.0.17** và **Logback Classic 1.5.18**. Mục tiêu:

- Hai request giả lập có ID khác nhau, chạy tuần tự nhưng sử dụng **cùng một worker thread**.
- Cả log của request thread và log của worker đều có đúng requestId/orderId.
- MDC của caller được khôi phục sau mỗi request.
- MDC của worker được khôi phục sau mỗi task.
- Sau hai request, một log chạy **ngoài scope request** không còn mang ID của request cũ.
- Thứ tự stdout có thể dự đoán, vì `Future.get()` chờ task hoàn tất trước khi request thread tiếp tục.

Đây là ví dụ minh họa hoạt động của MDC với thread pool; một ứng dụng web thực tế cần tích hợp vào filter/interceptor và execution model tương ứng.

Tạo cấu trúc:

~~~text

  src/main/java/example/RequestMdcDemo.java
  src/main/resources/logback.xml
~~~

### 6.2. RequestMdcDemo.java

~~~java
package example;

import java.util.Map;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class RequestMdcDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(RequestMdcDemo.class);

    private RequestMdcDemo() {
    }

    private static void restore(Map<String, String> context) {
        if (context == null || context.isEmpty()) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }

    private static void processRequest(
            ExecutorService executor, String requestId, String orderId)
            throws InterruptedException, ExecutionException {

        Map<String, String> callerBefore = MDC.getCopyOfContextMap();

        try {
            // Tạo context sạch và độc lập cho request này.
            MDC.clear();
            MDC.put("requestId", requestId);
            MDC.put("orderId", orderId);
            LOG.info("stage=received");

            // Chụp context tại thời điểm submit task.
            Map<String, String> captured = MDC.getCopyOfContextMap();

            Future<?> worker = executor.submit(() -> {
                Map<String, String> workerBefore =
                        MDC.getCopyOfContextMap();
                try {
                    // Cài context của request lên đúng worker thread.
                    restore(captured);
                    LOG.info("stage=background");
                } finally {
                    // Không để context request lưu lại trong thread pool.
                    restore(workerBefore);
                }
            });

            // Chờ worker để ví dụ có thứ tự log cố định.
            worker.get();
            LOG.info("stage=completed");
        } finally {
            // Kể cả khi worker.get() lỗi, caller vẫn được restore.
            restore(callerBefore);
        }
    }

    public static void main(String[] args) throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();

        try {
            processRequest(executor, "req-A", "order-1");
            processRequest(executor, "req-B", "order-2");

            // Chạy một task không thuộc request trên cùng worker.
            executor.submit(
                    () -> LOG.info("stage=worker-idle")).get();

            // Log trên caller sau khi hai request đã kết thúc.
            LOG.info("stage=main-idle");
        } finally {
            executor.shutdown();
            if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
                executor.shutdownNow();
            }
        }
    }
}
~~~

**Vì sao ví dụ có thể kiểm tra được?**

- `MDC.getCopyOfContextMap()` trả bản sao map ở thread gọi; không trả một biến global chứa MDC của mọi request.
- Ở request boundary, `callerBefore` được chụp rồi request thiết lập ngữ cảnh mới. `finally` gọi `restore(callerBefore)`.
- Khi tạo task, `captured` chụp ngữ cảnh của request; task dùng `restore(captured)` **bên trong** worker thread trước khi ghi log.
- Worker chụp `workerBefore` và khôi phục trong `finally` để lần dùng thread tiếp theo không mang dữ liệu từ request vừa xong.
- `Future.get()` bảo đảm việc ghi `stage=background` của task đã thực hiện xong trước khi ghi `stage=completed`. Cách chờ này chỉ phục vụ ví dụ xác định; ứng dụng async thực tế không nên block request một cách vô lý.
- `newSingleThreadExecutor()` có đúng một worker thread đang phục vụ các tác vụ, vì vậy task `stage=worker-idle` dùng cùng pool sau hai request. Khi không có MDC trước đó trên worker, fallback `none` xuất hiện.

### 6.3. logback.xml

~~~xml
<configuration>
    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <pattern>requestId=%X{requestId:-none} orderId=%X{orderId:-none} %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
~~~

Đây là cấu hình dành cho Logback. `%X{requestId}` lấy giá trị MDC. Cú pháp `%X{requestId:-none}` yêu cầu Logback dùng `none` khi key không tồn tại; tương tự với `orderId`. `%msg%n` xuất message rồi xuống dòng. Pattern không chứa timestamp/thread để output có thể so sánh dễ dàng.

**Không dùng pattern này như một định dạng production bắt buộc**: log thật nên có level, timestamp, service/logger và khi thích hợp traceId/spanId. Ở đây mục tiêu là thấy MDC truyền vào và dọn đi.

### 6.4. Chạy trên JDK 17

Ở thư mục `request-mdc-demo`:

~~~bash
mvn -q compile exec:java
~~~

**Tám dòng log ứng dụng trên stdout** theo ví dụ và cấu hình đã cho:

~~~text
requestId=req-A orderId=order-1 stage=received
requestId=req-A orderId=order-1 stage=background
requestId=req-A orderId=order-1 stage=completed
requestId=req-B orderId=order-2 stage=received
requestId=req-B orderId=order-2 stage=background
requestId=req-B orderId=order-2 stage=completed
requestId=none orderId=none stage=worker-idle
requestId=none orderId=none stage=main-idle
~~~

Maven hoặc môi trường chạy có thể phát thông báo riêng; tám dòng trên là **log do ứng dụng xuất** qua ConsoleAppender theo pattern. Dòng `stage=background` của mỗi request có đúng ID vì context được copy/install. Hai dòng `idle` có `none` vì MDC được restore/clear sau request và task.

**Thử một lỗi có chủ đích trong môi trường học tập:** bỏ dòng `restore(workerBefore)` ở worker. Với một thread pool tái sử dụng và không có bước dọn nào khác, task `worker-idle` có thể in `requestId=req-B`/`orderId=order-2` dù không thuộc request B. Đó chính là **MDC leakage**. Không thay đổi code production để thử rò dữ liệu; chỉ thực hành trong bản demo.

**Không cần thread pool để có MDC theo request đồng bộ.** Thêm `MDC.put(...)` tại boundary và dọn bằng `finally` là đủ nếu toàn bộ xử lý chạy trên cùng thread. Phần executor ở đây minh họa vấn đề bổ sung khi chuyển thread.

## 7. Tích hợp vào HTTP request thực tế

Trong ứng dụng web, đặt MDC ở **một boundary được định nghĩa rõ** như Servlet Filter, framework interceptor hoặc middleware. Controller/service/repository có thể dùng logger bình thường mà không cần tự tìm requestId.

### 7.1. Pseudocode Servlet Filter

~~~java
// PSEUDOCODE có phụ thuộc Servlet API và các hàm kiểm tra ID.
// Không phải chương trình Java độc lập.
void doFilter(request, response, chain) {
    String requestId = selectTrustedOrNewId(request);
    Map<String, String> previous = MDC.getCopyOfContextMap();

    try {
        MDC.clear();
        MDC.put("requestId", requestId);

        response.setHeader("X-Request-ID", requestId);
        LOG.info("event=request.received");
        chain.doFilter(request, response);
        LOG.info("event=request.completed");
    } finally {
        restore(previous);
    }
}
~~~

Đây là **mô hình luồng xử lý**, không phải code `jakarta.servlet.Filter` hoàn chỉnh. Một project Servlet cần các import, types, checked exceptions và framework dependency phù hợp. Hàm `selectTrustedOrNewId` là khái niệm chọn ID đã được xác thực, không phải hàm JDK có sẵn.

Trong triển khai thật, cần quyết định:

- Ghi bắt đầu/kết thúc ở filter hay controller; tránh log trùng khi exception handler cũng ghi cùng failure.
- Khi exception ném ra, `finally` vẫn dọn; mã ghi kết thúc ở sau `chain.doFilter` sẽ không chạy nếu có exception, vì vậy log outcome cần đặt ở nơi phù hợp hoặc trong finally có trạng thái kết quả.
- Request không đồng bộ (Servlet async dispatch) có thể quay lại một **thread khác**, filter có thể được gọi trên nhiều dispatch và phải áp dụng scope đúng cách.
- Một số framework dùng interceptor/filter riêng để gắn MDC và tự động cleanup; tránh cài hai lớp độc lập vừa ghi đè vừa remove cùng key.
- Với Spring MVC, `OncePerRequestFilter` là một điểm tích hợp thường dùng; cần chú ý async/error dispatch theo cấu hình framework, không coi tên lớp là bảo đảm mọi thread có MDC.
- Đối với WebFlux/Reactor, execution model không dựa đơn thuần vào một thread cố định cho cả request; phải gắn context qua Reactor Context/context propagation, không chỉ `MDC.put` trong một method của reactive chain.

### 7.2. Không tin rằng finally trong filter bao phủ mọi async task

Một filter đồng bộ có thể kết thúc và cleanup trên thread nhận request, trong khi tác vụ đã gửi vào executor vẫn chạy. Worker đó phải có **bản snapshot context riêng** và restore sau task. Nếu tác vụ ghi log sau khi request đã trả response, cần định nghĩa rõ nó là phần của request hay background job độc lập. Đừng giữ toàn bộ request/response object làm context của task nếu không cần, vì có thể giữ dữ liệu nhạy cảm trong bộ nhớ quá lâu.

## 8. Truyền MDC qua ExecutorService và CompletableFuture

### 8.1. Vì sao MDC thường biến mất khi đổi thread?

Một cách làm sai thường gặp:

~~~java
// Snippet minh họa: không truyền MDC vào thread pool.
MDC.put("requestId", "req-A");
executor.submit(() -> LOG.info("stage=worker"));
MDC.remove("requestId");
~~~

Việc MDC có được kế thừa bởi thread mới hay không **phụ thuộc backend/adapter**, và thread pool thường **tái sử dụng thread đã tồn tại**. Với Logback Classic theo hướng dẫn MDC, không nên trông chờ MDC của parent thread tự lan sang worker. Worker có thể in requestId trống hoặc, nguy hiểm hơn, một ID **cũ** còn sót từ task trước.

### 8.2. Capture tại submit; install và restore tại execute

Mẫu dùng một wrapper để có thể tái sử dụng:

~~~java
// Snippet Java 17 trong lớp có import org.slf4j.MDC,
// java.util.Map và hàm restore(Map<String,String>).
static Runnable withMdc(Runnable task) {
    Map<String, String> captured = MDC.getCopyOfContextMap();

    return () -> {
        Map<String, String> before = MDC.getCopyOfContextMap();
        try {
            restore(captured);
            task.run();
        } finally {
            restore(before);
        }
    };
}
~~~

Sử dụng:

~~~java
// Snippet: executor và LOG đã được khai báo.
executor.submit(withMdc(() -> LOG.info("stage=async")));
~~~

**Capture khi submit**, không phải khi worker bắt đầu chạy. Nếu request thread đã dọn MDC trước lúc worker thực thi mà ta chờ tới lúc đó mới đọc request thread, context có thể không còn đúng. Snapshot đi kèm task là giải pháp cho đoạn code chủ động kiểm soát thread boundary.

**Restore ở worker** ngay cả khi `task.run()` ném exception. Nếu không, thread pool giữ lại context của tác vụ vừa qua. Ở một thread pool có các giá trị sẵn do framework đặt, restore snapshot trước đó phù hợp hơn việc xóa vô điều kiện những key không do wrapper sở hữu.

### 8.3. CompletableFuture có nhiều ranh giới

~~~java
// Minh họa: withMdc(Runnable) đã tồn tại.
CompletableFuture<Void> future =
        CompletableFuture.runAsync(
                withMdc(() -> LOG.info("stage=async-start")),
                executor);
~~~

`runAsync` dùng Runnable nên có thể tái sử dụng wrapper. Với `supplyAsync` hoặc `thenApplyAsync`, cần wrapper tương đương dành cho `Supplier<T>`/`Function<T,R>`, hoặc TaskDecorator/context-propagation facility của framework.

**Chú ý:** một chuỗi CompletableFuture có thể chạy nhiều stage trên các executor/thread khác nhau. Việc truyền context cho stage đầu **không bảo đảm** các stage tiếp theo đều có MDC. Với `thenApply` không có chữ Async, callback đôi lúc có thể chạy trên thread hoàn thành future, nhưng không nên dựa vào điều này để suy luận MDC. Thiết kế propagation theo **mỗi ranh giới thực thi**.

### 8.4. AsyncAppender khác với chuyển thread nghiệp vụ

Một `AsyncAppender` của Logback nhận log event và có worker riêng phục vụ ghi. Logback có cơ chế chuẩn bị dữ liệu cần thiết của event trước khi chuyển qua queue, bao gồm MDC theo event trong những cấu hình/version hỗ trợ. Điều này **khác với** việc ứng dụng tự gọi `executor.submit(...)` để chạy business logic trên thread khác. AsyncAppender không tự truyền MDC tới business executor của bạn.

Vẫn phải kiểm tra logger/encoder có xuất MDC, và theo dõi queue/drop/shutdown nếu event cần độ tin cậy cao.

## 9. MDC theo request trong Spring, Servlet, Reactor và messaging

| Môi trường | Cách tích hợp thường gặp | Rủi ro cần xử lý |
| --- | --- | --- |
| Servlet/Jakarta Servlet | Filter hoặc interceptor tại request boundary | Async/error dispatch, thread reuse, cleanup |
| Spring MVC | OncePerRequestFilter/interceptor phù hợp | Double filter, lifecycle của exception/async request |
| Spring @Async | TaskDecorator hoặc wrapper executor | MDC không tự sang worker thread |
| ExecutorService / CompletableFuture | Capture Map tại submit, install/restore ở worker | Bỏ sót stage hoặc quên finally |
| Reactor / WebFlux | Reactor Context và context-propagation được cấu hình | Nhiều thread, không có một MDC thread duy nhất xuyên suốt chain |
| Kafka/RabbitMQ consumer | Chọn correlation ID từ message headers có kiểm soát, scope theo message | Thread pool consumer bị lẫn context giữa message |
| Scheduler/batch job | Scope theo job/run ID thay vì HTTP requestId | Dùng nhầm requestId từ event không liên quan |
| HTTP client outbound | Truyền ID được chấp nhận qua header nếu có hợp đồng | Header spoofing, xung đột với trace context |
| gRPC interceptor | Gắn context tại interceptor và truyền qua execution boundary | Callback trên thread khác, lifecycle stream |

MDC nên được xem như một **khả năng cross-cutting** có hợp đồng, không phải trách nhiệm mà mỗi service method tự làm. Framework/observability instrumentation có thể đã gắn traceId/spanId; cần kiểm tra tránh trùng key hoặc ghi đè các giá trị do instrumentation quản lý.

### 9.1. Thiết kế với tracing system

Nếu ứng dụng có OpenTelemetry, request logs thường có thể được liên kết với trace thông qua traceId/spanId lấy từ active span context. MDC cho requestId vẫn có ích cho hỗ trợ vận hành, nhưng không nên gán `traceId=requestId` chỉ vì cả hai là ID.

Dữ liệu trace context đi qua HTTP/gRPC/message headers theo chuẩn riêng. Việc logger in `traceId` chỉ có ích nếu context được tạo và truyền đúng. Hãy xem instrumentation của stack đang chạy có tự inject MDC hoặc xuất fields structured chưa, tránh thêm một bộ propagation thủ công cạnh tranh.

### 9.2. HTTP request có thể có nhiều phase và thread

Trong streaming response, long polling, reactive pipeline hoặc request có async dispatch, một request kéo dài hơn lifetime của một method trên thread ban đầu. Khi đó khái niệm “bắt đầu filter → finally cleanup” chỉ đúng cho **scope của lần thực thi trên thread ấy**; để log ở callback khác có ID, phải tạo scope mới tương ứng với callback/task.

**Không giữ MDC vô thời hạn** trên thread chỉ vì request chưa hoàn thành ở tầng ứng dụng. Context của event nên được capture và gắn ở đúng callback thực thi, rồi dọn sau callback.

## 10. Cấu hình Logback: in MDC ra text và JSON

### 10.1. PatternLayout dạng text

Ví dụ production có level, logger, thread và request ID:

~~~xml
<configuration>
    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX} %-5level [%thread] requestId=%X{requestId:-none} traceId=%X{traceId:-none} %logger{36} - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
~~~

`%X{key}` là converter của Logback cho một MDC key; `%X{key:-none}` thêm fallback. Dùng `%X` không có key để in toàn bộ MDC có thể làm lộ những trường không mong muốn và khiến output không ổn định; thường nên in những key đã được duyệt.

Khi error log có Throwable, cấu hình layout cần hiển thị stack trace đúng policy. Logback PatternLayout có cơ chế throwable conversion (ví dụ `%ex{full}`) và ở một số cấu hình tự bổ sung exception nếu không khai báo converter; hãy kiểm tra output thay vì giả định `%msg` luôn thể hiện nguyên nhân.

### 10.2. Structured JSON logging

Với JSON encoder, ta mong một event có fields như:

~~~json
{
  "timestamp": "2026-11-09T10:15:00Z",
  "level": "INFO",
  "service": "order-service",
  "requestId": "req-A",
  "traceId": "ba7a63b30a8248ff92b79a5665d7320e",
  "operation": "checkout",
  "eventCode": "ORD-1001",
  "message": "stage=received"
}
~~~

Đây là **schema minh họa**, không phải output mặc định của Logback. Encoder cần được cấu hình để xuất `requestId`/`traceId` từ MDC ra field JSON, với tên field và kiểu nhất quán với collector. Một dòng text có `requestId=req-A` chỉ là text nếu pipeline không parse ra field.

Với Logback, có các encoder JSON từ thư viện phù hợp; với Log4j2, `JsonTemplateLayout` và ThreadContext/MDC có thể đóng vai trò tương tự khi có đúng module/template. **Không hoán đổi nguyên xi config của hai backend**.

### 10.3. Cảnh giác log forging

MDC value có thể đến từ input chưa tin cậy. Nếu in raw text và ID chứa newline, attacker có thể tạo dòng giả; JSON encoder chuẩn sẽ escape string để giữ cấu trúc, nhưng **escape không loại dữ liệu nhạy cảm**. Thực hiện validation ngay tại boundary, giới hạn độ dài và dùng encoder có xử lý string phù hợp.

## 11. Kiểm thử MDC theo request: những tình huống bắt buộc

Một bài test đầy đủ không chỉ kiểm tra log của một request thành công.

### 11.1. Test hai request nối tiếp trên cùng thread

- Request A đặt `req-A`, phát hai event, rồi kết thúc.
- Cùng thread xử lý request B với `req-B`.
- Assert log B **không** chứa `req-A`.
- Sau request B, log background không có requestId hoặc dùng fallback đã định nghĩa.

Trường hợp này phát hiện lỗi phổ biến: bỏ `finally` hoặc quên `MDC.remove`/`clear`.

### 11.2. Test hai request chạy đồng thời

- Tạo hai request với ID riêng và cho các thao tác xen kẽ.
- Mỗi event phải gắn đúng ID theo request của nó.
- Không có biến static `currentRequestId` dùng chung.
- Với cùng một logger hoặc appender, log có thể xen kẽ nhưng context của mỗi event phải đúng.

Không assert thứ tự tuyệt đối giữa hai request chạy song song; chỉ assert mapping event → requestId và số sự kiện mong đợi.

### 11.3. Test task chạy trên thread pool được tái sử dụng

- Chạy task của A trên một worker, kiểm tra nó có `req-A`.
- Chạy task của B trên **cùng pool**, kiểm tra nó có `req-B`.
- Gửi một task “idle” không thuộc request; nó không được giữ `req-B`.
- Cho task ném RuntimeException rồi xác nhận `finally` vẫn restore MDC.

Đây là kiểm thử trọng tâm vì thread pool có tuổi thọ lâu hơn request.

### 11.4. Test khi exception, timeout và hủy task

- Business logic ném exception: request boundary vẫn phải cleanup.
- `Future.get()` ném `ExecutionException`: outer `finally` vẫn chạy.
- Worker bị interrupt: task cần xử lý interrupt đúng; cleanup luôn nằm trong finally.
- Task bị hủy trước khi chạy: wrapper có thể chưa cài context; không nên phát sinh leak.
- Nếu app server dừng giữa request, không có bảo đảm finally luôn chạy khi JVM bị kill; log pipeline cần có cơ chế độ bền riêng.

Không chỉ kiểm tra “API trả 200 OK” rồi cho rằng MDC lifecycle đã đúng.

### 11.5. Test field thật ở output

Kiểm tra từ nơi phát log cho tới nơi ingest:

1. Logger có thực sự dùng provider/backend hỗ trợ MDC không?
2. Pattern/JSON encoder có render `requestId` không?
3. Giao diện tìm kiếm/collector có tạo field `requestId` đúng tên và kiểu không?
4. Có bị thay/ghi đè bởi các instrumentation hoặc filter khác không?
5. Có log nào không thuộc request nhưng lại mang ID cũ không?
6. Có log ERROR với Throwable cần chẩn đoán và context đúng không?

**Test bằng appender in-memory hoặc appender kiểm thử** thường dễ hơn so sánh text console có timestamp và thứ tự thread thay đổi. Nếu test output text, loại/kiểm soát timestamp/threads và kiểm tra các trường ổn định.

## 12. Các lỗi phổ biến với MDC theo request

| Lỗi | Hậu quả | Cách xử lý |
| --- | --- | --- |
| Đặt MDC trong controller nhưng quên finally | Thread sau nhận requestId cũ | Scope ở boundary, cleanup/restore trong finally |
| Chỉ đặt MDC ở request thread | Worker async không có ID | Capture tại submit, install ở worker |
| Đặt MDC trong worker nhưng không restore | Request khác trên thread pool mang ID cũ | Worker wrapper với try/finally |
| Dùng static `currentRequestId` | Request đồng thời ghi đè dữ liệu | MDC theo thread/context, không dùng biến global |
| `MDC.clear()` sâu trong service | Xóa cả traceId/field do framework đặt | Chỉ remove key sở hữu hoặc restore snapshot |
| Hiểu `putCloseable` luôn restore giá trị cũ | Nested scope mất ID trước đó | Snapshot/restore khi cần giữ context cũ |
| Dùng `MDC.get()` trên thread khác rồi mong thấy giá trị parent | Không thấy ID hoặc thấy stale value | Propagate đúng ranh giới thread |
| Chỉ wrap stage đầu của CompletableFuture | Stage sau chạy ở thread khác mất context | Wrap từng async stage hoặc dùng context-propagation |
| Không kiểm tra `X-Request-ID` | Log injection, ID quá dài, giả mạo correlation | Trusted boundary, whitelist, giới hạn, ID server |
| Đặt email/token vào MDC | Dữ liệu nhạy cảm lan sang nhiều log | Dùng ID nội bộ an toàn, data minimization |
| Cấu hình MDC nhưng pattern không dùng `%X` | Log không có field dù MDC tồn tại | Cấu hình layout/encoder đúng |
| Coi MDC là distributed tracing | Có ID nhưng không có span/trace relation | Dùng tracing instrumentation phù hợp |
| Dùng requestId làm tên file per request | Bùng nổ file/appender và FD | Structured logging theo requestId vào luồng chung |
| Cùng một event được log nhiều tầng | Trùng failure, tăng volume | Chọn boundary chịu trách nhiệm logging |
| Log ở async callback sau khi filter cleanup | Missing requestId | Cài scope trong callback/task riêng |
| Gắn correlation field vào log nhưng collector bỏ field | Không tìm kiếm được theo request | Kiểm tra schema và ingest end-to-end |
| MDC là map String→String nhưng cố nhét object lớn | Overhead/serialization sai | Chọn field nhỏ, có cấu trúc và schema riêng |

## 13. Hiệu năng, độ tin cậy và khả năng quan sát

MDC giúp giảm công truyền context qua logger call, nhưng không miễn phí:

- Mỗi thao tác `put`/`get`/copy map có chi phí; việc `getCopyOfContextMap()` tạo snapshot cho **mỗi event** khi không cần thiết có thể gây allocations.
- Layout/JSON encoder phải serialize các field, tăng byte/event.
- Thêm trường dài hoặc có cardinality cao khiến storage/indexing tốn chi phí; đặc biệt không dùng `requestId` làm nhãn metrics không giới hạn.
- Nếu logger dùng AsyncAppender, có thể cần chuẩn bị MDC cùng event trước khi enqueue; không lẫn việc này với propagation sang business task.
- Nếu collector drop/truncate log, việc có requestId đúng ở appender vẫn chưa bảo đảm người điều tra tìm thấy log cuối cùng.
- Thread pool có thể xử lý rất nhiều request; leak không chỉ làm log sai mà có thể vô tình lưu dữ liệu của request khác trong thread-local lâu hơn cần thiết.

**Các chỉ số nên đo:** số log event/s, bytes/s, CPU, GC/allocations, queue depth, dropped log events, p95/p99 request latency, số bản ghi thiếu requestId tại request boundary và tỷ lệ log không gắn được traceId khi kỳ vọng có tracing.

Đừng gắn toàn bộ headers, claims, HTTP body hoặc một Java object vào MDC chỉ để tiện debug. MDC vốn phù hợp với **tập metadata nhỏ và được phép ghi**.

## 14. Bảo mật và quyền riêng tư

Một requestId được dùng để liên kết log phải được xem như **dữ liệu vận hành có quyền truy cập**, không phải cơ chế xác thực.

1. **Xác thực nguồn ID:** nếu nhận từ client, giới hạn cú pháp/độ dài; không cho phép client chọn user/tenant identity qua requestId.
2. **Không gắn secret vào MDC:** access token, password, refresh token, cookie hoặc khóa API có thể bị lặp trên nhiều log.
3. **Hạn chế PII:** cân nhắc không đưa email, số điện thoại, địa chỉ hay dữ liệu cá nhân trực tiếp vào MDC.
4. **Bảo vệ logging output:** file, collector, JSON archive và backup cần quyền truy cập/retention phù hợp.
5. **Chống log forging:** lọc CR/LF/ký tự điều khiển và dùng encoder có escaping đúng định dạng đích.
6. **Đừng log request payload toàn phần** dù đã có requestId; chỉ lấy trường cần điều tra theo data policy.
7. **Tránh ID mang nghĩa bảo mật:** một mã công khai trong response header không được dùng làm bằng chứng rằng request đến từ người dùng xác định.
8. **Hạn chế retention/thread-local leak:** dọn context trong finally, kiểm tra thread reuse và cách framework đóng scope.
9. **Không công khai stack trace:** log nội bộ giữ Throwable với kiểm soát; HTTP response chỉ nên trả mã lỗi, message an toàn và requestId khi phù hợp.

MDC đúng giúp truy vết, nhưng nếu lưu context quá lâu, nó có thể trở thành nguồn lẫn dữ liệu giữa các request và làm rủi ro điều tra/bảo mật tăng.

## 15. Checklist áp dụng MDC theo request vào production

1. **Chọn tên field:** `requestId`/`correlationId`/`traceId` có hợp đồng, không tự đặt mỗi service một tên.
2. **Chọn nguồn ID:** trusted gateway hoặc server-generated; kiểm tra header, giới hạn độ dài.
3. **Gắn ở boundary:** filter/interceptor/middleware phù hợp execution model của dự án.
4. **Dọn trong finally:** cả khi thành công, exception hoặc response sớm.
5. **Nested scope:** snapshot/restore nếu cần bảo toàn context của caller.
6. **Async propagation:** mọi ExecutorService/CompletableFuture/callback có wrapper/decorator hoặc propagation facility.
7. **Worker cleanup:** restore context trước task, không leak sang task sau.
8. **Framework compatibility:** MVC/Servlet, async dispatch và WebFlux/Reactor có cơ chế khác nhau.
9. **Backend:** SLF4J provider tương thích; Logback pattern/JSON encoder thật sự in MDC.
10. **Tracing:** lấy traceId/spanId từ trace context thật nếu có instrumentation.
11. **Schema:** field requestId tồn tại trong collector, không chỉ trong text không parse.
12. **Privacy:** không đính kèm secret/PII không cần thiết, escape input và đặt retention.
13. **Exception:** logging ERROR với Throwable và context đúng, không log trùng mọi tầng.
14. **Concurrency tests:** request đồng thời, nối tiếp, worker reuse, exception/timeout/cancel.
15. **Monitoring:** cảnh báo tỷ lệ event thiếu requestId, logging errors, dropped events và collector lag.

Nếu chỉ có thời gian ưu tiên một phép thử, hãy chạy **hai request với ID khác nhau trên một thread pool được tái sử dụng**, sau đó phát một event ngoài scope request. Test này phơi bày cả lỗi không truyền context lẫn lỗi không dọn context.

## 16. Bài tập thực hành

1. **Khái niệm:** giải thích MDC theo request và khác biệt giữa requestId, correlationId, traceId.
2. **JDK 17 + Maven:** tạo ba file `pom.xml`, `RequestMdcDemo.java`, `logback.xml`; chạy và đối chiếu tám dòng output đã nêu.
3. **Leak:** trong bản demo ở máy học tập, bỏ bước restore worker. Dự đoán `stage=worker-idle` sẽ có requestId nào; vì sao?
4. **Lost context:** bỏ `restore(captured)` trong task và giữ cleanup. Dự đoán hai dòng `stage=background` có trường requestId/orderId như thế nào.
5. **Exception path:** thêm một task ném RuntimeException; chứng minh `finally` của worker và caller vẫn restore MDC, không để request B ảnh hưởng request C.
6. **Nested scope:** đặt sẵn `MDC.put("traceId", "T-1")` ở caller trước `processRequest`. Với code demo hiện tại, field này có còn tồn tại **trong** request không, và có được khôi phục **sau** request không? Thiết kế policy merge nếu cần giữ traceId xuyên scope.
7. **Header validation:** request gửi `X-Request-ID` chứa newline hoặc 300 ký tự. Viết logic tạo ID server an toàn và nêu cách không biến request ID thành user identity.
8. **Spring MVC:** nêu vị trí gắn `requestId` trong filter và cách xử lý asynchronous/error dispatch nếu request tiếp tục trên thread khác.
9. **CompletableFuture:** một chain gồm `runAsync` và `thenApplyAsync`; tại sao wrap stage đầu không bảo đảm MDC của stage sau? Đề xuất wrapper cho mỗi stage.
10. **JSON logging:** thiết kế schema JSON có `timestamp`, `level`, `service`, `requestId`, `traceId`, `eventCode`, `message` và `error.type`. Cần kiểm thử điều gì để các field này được index?
11. **Concurrency:** thiết kế test gửi 100 request chia 8 worker, mỗi request có ID riêng. Viết assertion để bắt cả event thiếu ID và event mang ID của request khác.
12. **Security:** phân tích tại sao không nên dùng JWT, email hoặc HTTP body làm MDC value và vì sao JSON encoding không thay thế bảo mật dữ liệu.

**Ghi nhớ:** **MDC theo request là một vòng đời ngữ cảnh, không chỉ một lời gọi `MDC.put(...)`**. Đặt ID đã được chọn/kiểm tra tại boundary, đưa nó ra log qua layout/JSON encoder, **dọn/restore trong `finally`** và **copy/install/restore khi qua thread pool hoặc callback**. Nhờ đó log của nhiều request có thể xen kẽ mà vẫn truy vết chính xác, không để request sau bị gắn nhầm ngữ cảnh của request trước.
