# SLF4J Version Compatibility in Java

## 1. Why Must You Check Version Compatibility?

**SLF4J (Simple Logging Facade for Java)** is an API that lets Java applications and libraries call `logger.info(...)`, `logger.warn(...)`, or `logger.error(...)` without coupling source code to a single backend. SLF4J **does not handle all logging by itself**: at runtime, it requires an appropriate implementation connected via a *binding* or *provider*.

An application may compile successfully because `slf4j-api` is present, yet **produce no logs at runtime** due to a missing provider, a provider from the wrong generation, or the wrong one being selected. Upgrading Java, Spring Boot, Logback, Log4j 2, or a library that transitively depends on SLF4J can all change which dependency is ultimately loaded.

To check version compatibility, you need to evaluate these factors together:

1. **SLF4J API:** the version used at compile time and the version actually loaded in the JVM.
2. **Binding/provider:** the component connecting the API to the backend; its registration mechanism must match the SLF4J API.
3. **Backend:** Logback, Log4j 2, JUL, Simple, or NOP; each backend has its own version and Java requirements.
4. **Build/runtime classpath:** direct dependencies, transitive dependencies, BOMs, bridges, fat JARs, and container classloaders.
5. **API features being called:** code using the 2.0 fluent API cannot assume the 1.7 API has the corresponding methods.

**Distinguish three layers of compatibility:** whether the source code can recompile (*source compatibility*); whether bytecode can link (*binary compatibility*); and whether the entire logging stack initializes and outputs logs to the right destination at runtime (*runtime compatibility*). The three conclusions can differ.

## 2. SLF4J API, Binding/Provider, and Backend

```text
                  Java application / library
                              |
                  org.slf4j.Logger API
                              |
                         slf4j-api
                              |
              +---------------+---------------+
              |                               |
       1.7.x: binding                  2.0.x: provider
       StaticLoggerBinder             SLF4JServiceProvider
              |                         via ServiceLoader
              +---------------+---------------+
                              |
                 Exactly one implementation
             /            |             \
        Logback      Log4j 2 adapter    slf4j-simple
             \            |             /
                    Appender / sink
                              |
                   stdout / file / collector
```

- **API:** classes in the `org.slf4j` package such as `Logger`, `LoggerFactory`, `MDC`, and `Marker`. Applications typically program against this API.
- **Binding in SLF4J 1.7 and earlier:** a JAR that advertises an implementation via the `org.slf4j.impl.StaticLoggerBinder` class.
- **Provider in SLF4J 2.0 and later:** a JAR/module that provides an implementation of `org.slf4j.spi.SLF4JServiceProvider` and is discovered via `ServiceLoader`.
- **Backend:** executes level policies, filters, formatters, appenders, and I/O. For example, `logback-classic` is a direct SLF4J implementation; `log4j-slf4j2-impl` is a bridge from SLF4J 2 to Log4j 2.
- **Bridge:** forwards events from another logging API into SLF4J or vice versa. Bridge and provider are not synonymous; the forwarding direction matters greatly.

In a typical application, there should be **one clearly chosen SLF4J provider** on the runtime classpath. Multiple providers are not the standard way to "log simultaneously to multiple places"; choose one backend and configure multiple appenders/sinks in that backend.

## 3. The Biggest Change: SLF4J 1.7 vs. 2.0

### SLF4J 1.7.x: Looking Up StaticLoggerBinder

SLF4J 1.7 looks for a specific class:

```text
org.slf4j.impl.StaticLoggerBinder
```

This is the legacy *binding* mechanism. Historical examples include `slf4j-simple:1.7.x` and `logback-classic:1.2.x`. They were designed to pair with the 1.7 generation API.

### SLF4J 2.0.x: Using Java ServiceLoader

Starting in 2.0, SLF4J switched to looking up:

```text
org.slf4j.spi.SLF4JServiceProvider
```

using `java.util.ServiceLoader`. When running on the classpath, a provider is typically registered via the file:

```text
META-INF/services/org.slf4j.spi.SLF4JServiceProvider
```

SLF4J 2.0 **no longer uses `StaticLoggerBinder` to select a backend**. Therefore, if you upgrade `slf4j-api` from 1.7 to 2.0 while keeping `slf4j-simple:1.7.x` or `logback-classic:1.2.x`, the new API may report that legacy bindings are ignored and then fall back to NOP because no valid provider is found. The code may still run while business logs disappear.

Conversely, the 1.7 API has no mechanism to discover a 2.0 provider via `ServiceLoader`. Simply adding `slf4j-simple:2.0.x` to an application running the 1.7 API does not create a 1.7 binding.

### SLF4J 2.0 Adds the Fluent Logging API

In addition to the familiar calls, SLF4J 2.0 allows:

```java
// Illustrative snippet in an application that already has SLF4J 2.x.
logger.atInfo()
      .addKeyValue("orderId", "O-17")
      .log("Order accepted");
```

The `atInfo()` method does not exist in SLF4J 1.7's `Logger` interface. If code compiles against 2.0 but the runtime loads `slf4j-api:1.7.x`, calling the new method can throw `NoSuchMethodError`. Backward compatibility of legacy API calls **does not mean every new feature exists in the old API**.

## 4. Version Pairing Matrix

| SLF4J API at runtime | Provider/binding | Expected outcome |
| --- | --- | --- |
| `1.7.x` | `slf4j-simple:1.7.x` | **Compatible:** same StaticLoggerBinder generation. |
| `2.0.x` | `slf4j-simple:2.0.x` | **Compatible:** ServiceLoader and 2.0 provider. |
| `1.7.x` | `logback-classic:1.2.x` | **Compatible historical combination:** though this Logback line is old. |
| `2.0.x` | `logback-classic:1.6.x` | **Generation-compatible:** requires JDK 11+ and a consistent Logback set. |
| `2.0.x` | `slf4j-simple:1.7.x` | **Incompatible:** legacy binding is ignored by the 2.0 API. |
| `1.7.x` | `slf4j-simple:2.0.x` | **Incompatible:** 1.7 API does not look up 2.0 providers. |
| `2.0.x` | `logback-classic:1.2.x` | **Incompatible:** old implementation uses 1.7 binding. |
| `2.0.x` | No provider | Warning about missing provider; usually defaults to NOP. |
| `2.0.x` | Two or more 2.0 providers | May warn about multiple providers; a single valid set must be chosen. |

For providers published under the `org.slf4j` group, **the API and provider major.minor versions must match**, for example `slf4j-api:2.0.20` paired with `slf4j-simple:2.0.20`. Patch versions may differ within the same line per SLF4J rules, though aligning patch versions is usually easier to verify and keep updated for security.

**Logback and Log4j 2 use their own versioning.** Do not look for `logback-classic:2.0.20` just because the API is at `2.0.20`; check the official compatibility matrices of Logback, Log4j, and your JDK.

Every row in the table also depends on other conditions such as Java version, internal dependencies, and configuration. **Having the same API/provider generation is necessary, but does not by itself guarantee every runtime configuration will work.**

## 5. Source Compatibility and Binary Compatibility

SLF4J aims to keep the API used by applications stable. Long-standing calls like:

```java
// Code inside a service that has already declared an SLF4J logger.
logger.info("Loaded orderId={}", orderId);
logger.warn("Retry for orderId={}", orderId);
logger.error("Failed for orderId={}", orderId, exception);
```

can usually continue working when an application moves from a 1.7 runtime to 2.0, as long as the runtime API and provider are properly paired. A library dependency **compiled against slf4j-api 1.7** does not necessarily need to be recompiled just because the application uses 2.0.

However, you must check:

- **Does the library use only the public API or internal SPIs?** If it uses `org.slf4j.impl.StaticLoggerBinder` or internal implementation classes, its compatibility differs from code that only calls `Logger.info`.
- **Are new methods used?** Code calling `atDebug()` or `atInfo()` requires the 2.x API at both compile time and runtime.
- **Which API JAR is actually loaded?** Maven/Gradle may resolve conflicts according to their own rules; an application server may provide a different JAR than the runtime classpath in your IDE.
- **Is a class loaded multiple times across different classloaders?** Container/plugin architectures can cause a provider to be invisible to the API even when the dependency is present in the system.

*Source compatibility* is the ability to recompile source code. *Binary compatibility* is the ability of existing bytecode to link against a new API. *Runtime compatibility* also requires the right backend/provider, actual log emission, and preserved operational behavior.

If you encounter `NoSuchMethodError`, `NoClassDefFoundError`, `ClassNotFoundException`, `AbstractMethodError`, or `ServiceConfigurationError`, do not guess the cause from the error name alone: inspect the stack trace, which class caused the error, and which JAR actually contains the loaded class.

## 6. JDK Version and Backend Version

SLF4J 2.0.x **requires Java 8 or later**, so the API can be used with Java 17. However, backends have independent requirements:

| Component | JDK / version notes |
| --- | --- |
| SLF4J 1.7.x | Legacy API; no 2.0 fluent API. |
| SLF4J 2.0.x | Java 8+, uses ServiceLoader. |
| Logback 1.3.x | Supports SLF4J 2.0, Java 8; older line. |
| Logback 1.4.x | Supports SLF4J 2.0, Java 11; older line. |
| Logback 1.6.x | Supports SLF4J 2.0, Java 11+; has configuration changes compared to older lines. |
| Log4j 2 with `log4j-slf4j2-impl` | Choose a Log4j version from the matching dependency family and JDK per the Log4j documentation. |

If the Java runtime is older than the backend/provider bytecode, the JVM can throw `UnsupportedClassVersionError`. Basic check commands:

```bash
java -version
javac -version
```

Your project's toolchain/`--release 17` controls the bytecode **compiled by your project itself**; it does not recompile third-party dependencies published for a different JDK.

Especially with **Spring Boot**, the logging starter and BOM usually select a Logback/SLF4J set tested by the framework. If you want to upgrade SLF4J/Logback separately, verify compatibility against your **running Spring Boot version**, dependency management, `javax.*`/`jakarta.*` namespace, and JDK before overriding. Do not treat the standalone POM example below as a dependency list to copy into every Spring Boot application.

## 7. Choosing Logback, Log4j 2, and Bridges in the Right Direction

### Logback

Logback provides a direct backend for SLF4J via `logback-classic` along with a matching `logback-core`. A common version layout with Java 17:

```text
slf4j-api:2.0.x
        |
logback-classic:1.6.x
        |
logback-core:1.6.x
```

This illustrates the relationship, not a strict directed dependency graph as in a POM. When choosing versions, let dependency management resolve the entire set consistently. If you have chosen Logback as your provider, do not also put `slf4j-simple` on the runtime classpath.

Upgrading Logback may also require updating XML configuration. For example, newer Logback releases changed how conditional processing with Janino is handled. Therefore, **do not stop testing at compile time**—start up with the actual configuration and verify that appenders, filters, and rolling files work properly.

### Log4j 2

If your target backend is Log4j 2, choose the adapter matching the SLF4J generation:

| Source API | Adapter forwarding to Log4j 2 |
| --- | --- |
| SLF4J 1.7.x/earlier | `org.apache.logging.log4j:log4j-slf4j-impl` |
| SLF4J 2.0.x | `org.apache.logging.log4j:log4j-slf4j2-impl` |

Do not confuse this with `log4j-to-slf4j`, which is a bridge from **Log4j API → SLF4J**. Combining it with `log4j-slf4j2-impl` in the same pipeline can create a loop:

```text
SLF4J -> log4j-slf4j2-impl -> Log4j API
   ^                             |
   +-------- log4j-to-slf4j ------+
```

If using Log4j 2 as the target, align Log4j modules with the appropriate BOM/constraints and keep only the required forwarding direction.

### JUL and Forwarding Direction

- `slf4j-jdk14`: direction **SLF4J → java.util.logging (JUL)**.
- `jul-to-slf4j` with `SLF4JBridgeHandler`: direction **JUL → SLF4J**.

If both directions are deployed and the bridge is installed, a loop can occur:

```text
SLF4J -> slf4j-jdk14 -> JUL -> jul-to-slf4j -> SLF4J -> ...
```

The rule is **one target backend, with bridges feeding into that target**. Do not add every artifact with "logging" in its name hoping the system will unify itself.

## 8. Runnable Java 17 Example: SLF4J API 2.0 and Matching Provider

Here is a small Maven project using `slf4j-api:2.0.20` and `slf4j-simple:2.0.20`. The two version numbers are **pinned to demonstrate a reproducible combination**; this does not claim they will always be the latest release.

Directory structure:

```text
slf4j-version-demo/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── demo/
                └── Slf4jVersionDemo.java
```

File `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>demo</groupId>
    <artifactId>slf4j-version-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <maven.compiler.release>17</maven.compiler.release>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.20</version>
        </dependency>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-simple</artifactId>
            <version>2.0.20</version>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.3.0</version>
                <configuration>
                    <mainClass>demo.Slf4jVersionDemo</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

File `src/main/java/demo/Slf4jVersionDemo.java`:

```java
package demo;

import org.slf4j.ILoggerFactory;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class Slf4jVersionDemo {

    private static final Logger LOG =
            LoggerFactory.getLogger(Slf4jVersionDemo.class);

    private Slf4jVersionDemo() {
    }

    public static void main(String[] args) {
        ILoggerFactory factory = LoggerFactory.getILoggerFactory();

        System.out.println("FACTORY="
                + factory.getClass().getSimpleName());
        System.out.println("INFO_ENABLED=" + LOG.isInfoEnabled());

        LOG.info("Order {} accepted", "O-17");

        LOG.atInfo()
                .addKeyValue("orderId", "O-17")
                .log("Order accepted with fluent API");
    }
}
```

Run from the directory containing `pom.xml` with JDK 17+ and Maven able to download dependencies:

```bash
mvn -q -Dorg.slf4j.simpleLogger.defaultLogLevel=info compile exec:java
```

**Exact stdout from the program's two `System.out.println` statements:**

```text
FACTORY=SimpleLoggerFactory
INFO_ENABLED=true
```

The two calls `LOG.info(...)` and `LOG.atInfo()...` also emit messages via the `slf4j-simple` backend, which defaults to **stderr**. The format of those log lines (logger name, thread, key-value) depends on the backend/configuration and may interleave with stdout differently across environments. Therefore, **do not treat the two lines above as the entire terminal output**.

Why this example is useful:

1. `slf4j-api:2.0.20` enables compiling both classic calls and the fluent API.
2. `slf4j-simple:2.0.20` supplies a runtime provider from the same `2.0.x` family.
3. `LoggerFactory.getILoggerFactory()` reveals which implementation was selected; `SimpleLoggerFactory` indicates the Simple provider.
4. The provider is declared with Maven `runtime` scope because Java code only imports the API, while the implementation is only needed at runtime.
5. If you remove the provider, SLF4J 2.0 typically warns about a missing provider and falls back to NOP; if you replace the provider with a legacy 1.7 binding, the 2.0 API cannot use that binding.

When writing a **shared library**, you normally declare only the `slf4j-api` dependency in the required scope and let the final application choose the provider. Adding a provider to a library in runtime/compile scope can unintentionally force a backend onto every application that uses the library.

## 9. Gradle Equivalent (Groovy DSL)

For a Java project with the same `demo.Slf4jVersionDemo` source as above:

```groovy
plugins {
    id 'java'
    id 'application'
}

repositories {
    mavenCentral()
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    implementation 'org.slf4j:slf4j-api:2.0.20'
    runtimeOnly 'org.slf4j:slf4j-simple:2.0.20'
}

application {
    mainClass = 'demo.Slf4jVersionDemo'
}
```

Run with the Gradle Wrapper:

```bash
./gradlew run
```

On Windows, use `gradlew.bat run`. This is a standalone build example; in a Spring Boot project, do not add `slf4j-simple` if the starter already provides Logback unless you have a reason to switch backends.

## 10. Version Compatibility Warnings and How to Handle Them

### 10.1. No Provider Found

Typical message in SLF4J 2.x:

```text
SLF4J: No SLF4J providers were found.
SLF4J: Defaulting to no-operation (NOP) logger implementation
```

This indicates the API initialized but could not find a suitable implementation. The application may keep running normally while SLF4J events are silently dropped. Check your **runtime dependencies**, verify the provider is declared in the right scope, and inspect the packaged JAR.

### 10.2. Legacy Bindings Ignored by SLF4J 2.x

Typical message:

```text
SLF4J: Class path contains SLF4J bindings targeting slf4j-api versions 1.7.x or earlier.
```

Look for `logback-classic:1.2.x`, `slf4j-simple:1.7.x`, or other legacy bindings in your dependency tree. Switch to a compatible 2.0 provider and remove the unused artifact. Do not work around it by adding another 1.7 binding.

### 10.3. Multiple Providers Present

If both `logback-classic` and `slf4j-simple` act as providers, SLF4J may emit a multiple-providers warning. Code may still output logs through one implementation, but that selection should not be considered stable or intentional for the application. Find which transitive dependency pulls in the extra provider and exclude the right artifact.

### 10.4. NoSuchMethodError or NoClassDefFoundError

Inspect the method/class in the stack trace and the origin of the JAR actually loaded. For instance, `atInfo()` does not exist in the 1.7 API even if code was compiled against 2.0. A backend/SPI mismatch can also cause initialization failures. If the dependency tree in your IDE looks right while the deployed artifact fails, inspect classloaders, fat JARs, and container-provided libraries.

### 10.5. Failures When Packaging a Fat JAR

SLF4J 2.x providers are discovered via `ServiceLoader`. When shading/merging JARs, if the file:

```text
META-INF/services/org.slf4j.spi.SLF4JServiceProvider
```

is dropped or overwritten, the provider may not be found even though the implementation classes are inside the artifact. Configure service descriptor merging properly when shading, inspect the packaged JAR contents, and test **the actual deployed artifact**, not just running the application from your IDE.

In applications using the JPMS module path, service declaration/provision also depends on module descriptors; do not assume copying JARs into an arbitrary directory is enough.

## 11. Inspecting Effective Dependencies with Maven/Gradle

**Maven:**

```bash
mvn dependency:tree
mvn dependency:tree -Dincludes=org.slf4j:*,ch.qos.logback:*,org.apache.logging.log4j:*
```

Read the dependency tree to see which `slf4j-api` version is selected, which provider is brought into runtime, which Logback/Log4j group appears, and which artifacts pull in additional bindings/bridges. Maven's dependency management and nearest-definition mediation can make the effective version differ from what a library expects.

**Gradle:**

```bash
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --configuration runtimeClasspath --dependency slf4j-api
./gradlew dependencyInsight --configuration runtimeClasspath --dependency logback-classic
```

In multi-module builds, substitute the specific application module tasks such as `:app:dependencies` and `:app:dependencyInsight`. Inspect **runtimeClasspath**, not just `compileClasspath`, because providers may only appear at runtime.

If a project contains multiple JARs or runs inside an application server, compare the build tool output with the **actual classpath of the deployed process**. You can print it in diagnostic mode:

```java
// Illustrative code inside a program with the SLF4J runtime present.
System.out.println(
        org.slf4j.LoggerFactory.getILoggerFactory()
                .getClass().getName());
```

The factory information is useful evidence of which provider is loaded; it does not yet guarantee that levels, appenders, formats, and remote collectors are all correct. Emit a test event and verify it reaches the expected destination.

## 12. Compatibility with Frameworks and Third-Party Libraries

**Libraries:** program against `slf4j-api` and let the application decide the implementation. A library compiled against SLF4J 1.7 can run fine on a 2.0 API runtime as long as it only uses stable public methods. Do not rush to add `slf4j-api:1.7.x` as a second JAR just because an older dependency used it.

**Standalone applications:** pick one provider with a suitable backend, and pin or manage versions using a BOM/constraints to prevent versions from "drifting" as transitive dependencies are updated.

**Spring Boot:** starters usually bring the appropriate logging implementation and bridges onto the classpath. When upgrading or switching backends, consult the documentation for your running Spring Boot version. Manually adding `slf4j-simple` alongside Logback is a common cause of multiple providers.

**JUL/Commons Logging/Log4j integration:** determine the bridge direction for each API. For example, `jul-to-slf4j` only routes JUL to SLF4J when its bridge handler is installed; simply having a bridge JAR on the classpath does not automatically redirect every JUL call. Conversely, using `slf4j-jdk14` together with an installed `jul-to-slf4j` can cause logging loops.

## 13. Verified SLF4J 1.7 → 2.0 Upgrade Procedure

1. **Record the current state:** API, binding, backend, bridges, JDK version, Spring Boot/framework version, dependency tree, and deployed artifact.
2. **Choose the target version set:** SLF4J 2.0.x API, one matching 2.0 provider, and a backend and JDK satisfying compatibility docs; consider framework BOMs.
3. **Replace legacy bindings:** remove artifacts meant only for `StaticLoggerBinder`, add a `ServiceLoader`-based provider, and replace the 1.7 Log4j adapter with the 2.0 adapter if needed.
4. **Review bridges:** map out the event flow direction to avoid JUL ↔ SLF4J or Log4j ↔ SLF4J loops.
5. **Inspect transitive dependencies:** verify which API and provider are actually resolved; remove extra providers and align Logback-core/classic and backend modules.
6. **Compile and test on the target JDK:** if using the fluent API, compile and run against the 2.0 API; do not rely on your Java project's bytecode alone to conclude that dependency JARs will work.
7. **Verify provider initialization:** ensure there are no NOP, legacy binding, or multiple-provider warnings; confirm the expected factory is selected.
8. **Verify logs at the destination:** INFO, WARN, ERROR, exception stack traces, MDC/context, markers/structured attributes, and key levels/filters.
9. **Run the final artifact:** test the fat JAR/WAR or container image in a production-like environment; verify `ServiceLoader` metadata and classpath.
10. **Monitor after deployment:** compare key event counts and what the sink actually receives; keep a rollback path to the previous dependency set if issues arise.

Do not treat an upgrade as done just because "pom.xml says 2.0". The completion criterion is **the actual deployed application writing proper logs with no hidden mismatches**.

## 14. Common Scenarios

**Scenario A — upgrading only the API:** A project has `slf4j-api:2.0.x` but `logback-classic:1.2.x`. This is a provider generation mismatch. Choose a Logback version compatible with SLF4J 2.0 and your JDK/framework, and remove the old binding.

**Scenario B — Log4j 2 + SLF4J 2:** Adding `log4j-slf4j-impl` instead of `log4j-slf4j2-impl`. Wrong adapter generation; switch to the adapter matching the actual API. Ensure `log4j-to-slf4j` does not create a reverse forwarding path.

**Scenario C — legacy library:** A library was compiled against SLF4J 1.7, while the application runs API 2.0 with a 2.0 provider. Standard public calls from the library can still work; check whether the library uses SLF4J internals or legacy bindings.

**Scenario D — fluent code deployed against the wrong API:** Source uses `logger.atInfo()` and compiles cleanly with 2.0, but at runtime the server supplies the 1.7 API. Fix the classpath/classloader so the right API is loaded; this cannot be fixed by swapping providers alone.

**Scenario E — failure appears only after packaging:** Runs fine via Maven, but the fat JAR is missing `META-INF/services` entries. Fix the shade/merge services step and test the built artifact.

**Exercise 1:** Run the Maven example in Section 8. Explain why `FACTORY=SimpleLoggerFactory` proves the Simple provider was selected, yet does not by itself verify that logs were written to a file or collector.

**Exercise 2:** Look at the pair `slf4j-api:2.0.x` and `slf4j-simple:1.7.x`. Predict why logs are dropped, distinguishing `StaticLoggerBinder` from `SLF4JServiceProvider`.

**Exercise 3:** Diagram the direction of the four artifacts `jul-to-slf4j`, `slf4j-jdk14`, `log4j-to-slf4j`, and `log4j-slf4j2-impl`. Explain why combining opposing directions can create a loop.

**Exercise 4:** A Java 17 application has `slf4j-api:2.0.x`, `logback-classic:1.2.x`, and `slf4j-simple:2.0.x`. Identify the two problems: Logback 1.2 is the wrong generation, and the Simple provider is redundant if Logback is intended. Plan the dependency removals/updates before testing.

**Code review checklist:**

- [ ] Verified the exact `slf4j-api` version **at runtime**, the matching provider/binding, and the JDK.
- [ ] For SLF4J-group providers, major.minor matches the API; patch versions are managed intentionally.
- [ ] One intended provider is selected, with no accidental NOP fallback or multiple providers.
- [ ] Logback/Log4j backend, core modules, configuration, and JDK are compatible per the official matrix.
- [ ] All bridges point toward the chosen backend, with no circular forwarding pairs.
- [ ] The 2.0 fluent API is only used where the corresponding API methods exist.
- [ ] Dependency tree/BOM/Spring Boot version and deployment classpath have been cross-checked.
- [ ] Packaging preserves the `ServiceLoader` service descriptor for the 2.0 provider.
- [ ] Smoke tests from the actual running artifact produce logs at the expected sink.
- [ ] No warnings about missing providers, ignored legacy bindings, or unintended multiple providers.

The core difference between 1.7 and 2.0 is **`StaticLoggerBinder` → `ServiceLoader`**. Prove compatibility with the actual running artifact and confirm logs reach their intended destination after upgrading.
