# MDC là gì? Mapped Diagnostic Context trong Java Logging

## Mục tiêu bài học

Khi nhiều request được xử lý đồng thời trong một ứng dụng Java, những dòng log thường xen kẽ nhau. Chỉ nhìn timestamp và thread name không phải lúc nào cũng biết dòng nào thuộc request nào. **MDC (Mapped Diagnostic Context)** giúp gắn **các cặp key–value mô tả ngữ cảnh** vào những logging event phát sinh trong một phạm vi xử lý, để cùng một requestId, traceId hoặc operation xuất hiện nhất quán trong các dòng log mà không phải truyền chúng thủ công vào mọi message.

Bài này thuộc nhóm **MDC** của **Java Core Logging**, trả lời trực tiếp câu hỏi **“MDC là gì?”**. Bạn sẽ học:

- Khái niệm và mục đích của MDC trong ứng dụng Java nhiều request/thread.
- Sự khác nhau giữa **MDC**, message, logger name, level, thread, Marker, SLF4J fluent key–value và distributed tracing.
- Các API **put, get, remove, clear, putCloseable, getCopyOfContextMap, setContextMap** của **org.slf4j.MDC**.
- Cách Logback in MDC qua **%X{key}** và cung cấp giá trị mặc định khi thiếu key.
- Vòng đời **đặt → ghi log → gỡ** để không rò ngữ cảnh giữa các request trong thread pool.
- Vì sao MDC **không tự động truyền qua mọi executor, CompletableFuture hoặc ranh giới dịch vụ**, và cách sao chép/khôi phục context một cách có kiểm soát.
- Cách các field MDC có thể đi vào JSON logging, giới hạn bảo mật, cardinality và những trường hợp lỗi thường gặp.
- Ví dụ **Java 17 + SLF4J + Logback** đã biên dịch/chạy thử, với output ổn định cho cả request thread và worker thread.

## 1. MDC là gì?

**MDC** là viết tắt của **Mapped Diagnostic Context**, nghĩa là **ngữ cảnh chẩn đoán dạng ánh xạ**. Nói đơn giản, đó là một tập những cặp **key–value**, thường là String, được hệ logging gắn với ngữ cảnh thực thi hiện tại.

Ví dụ:

~~~text
requestId = req-17
operation = payment
~~~

Giả sử application log liên tiếp:

~~~text
INFO  | requestId=req-17 | event=request.started
WARN  | requestId=req-17 | event=dependency.retry attempt=2
INFO  | requestId=req-17 | event=request.completed status=200
~~~

Ba dòng trên có cùng **requestId=req-17**, giúp người vận hành liên kết chúng thành một luồng xử lý. Người viết code không phải luôn nối **requestId=...** vào từng message nếu backend/encoder được cấu hình lấy giá trị từ MDC.

**MDC không phải một hệ thống lưu trữ hay cơ sở dữ liệu.** Nó không tự lưu event, không mở file log, không tạo trace phân tán và không bảo đảm mọi record được xuất. MDC chỉ cung cấp **ngữ cảnh bổ sung** cho logging API/backend có khả năng đọc thông tin đó.

### Bài toán MDC giải quyết

Hãy tưởng tượng service nhận hai request:

~~~text
Request A: tạo đơn hàng OD-42
Request B: hoàn tiền RF-19
~~~

Nếu chỉ ghi:

~~~text
INFO  validating input
INFO  validating input
WARN  retry downstream
INFO  completed
INFO  completed
~~~

bạn khó biết retry thuộc request nào. Nếu mỗi request có một requestId riêng trong MDC, format log có thể thành:

~~~text
INFO  requestId=req-A validating input
INFO  requestId=req-B validating input
WARN  requestId=req-A retry downstream
INFO  requestId=req-B completed
INFO  requestId=req-A completed
~~~

Thông tin requestId giải quyết bài toán **correlation**: liên kết các event của cùng một đơn vị xử lý. Nó **không thay thế** message có nghĩa, kết quả nghiệp vụ hoặc thông tin exception.

## 2. MDC nằm ở đâu trong logging pipeline?

Một pipeline điển hình dùng **SLF4J API + Logback**:

~~~mermaid
flowchart LR
    A["HTTP request / Job"] --> B["Đặt MDC"]
    B --> C["Business code gọi SLF4J Logger"]
    C --> D["Logback tạo LoggingEvent"]
    D --> E["Appender + Layout/Encoder"]
    E --> F["Console / File / Collector"]
    B -. "requestId, operation" .-> D
~~~

Giải thích theo thứ tự:

1. Ở đầu request hoặc job, code/framework nhận diện **requestId** và đặt nó vào MDC.
2. Các lớp bên trong xử lý vẫn có thể dùng logger quen thuộc như **LOG.info** hoặc **LOG.warn**.
3. Backend logging như **Logback** lấy thông tin MDC liên quan đến event theo cơ chế của nó.
4. Layout hoặc JSON encoder quyết định **trường MDC nào được xuất và in như thế nào**.
5. Khi request kết thúc, code phải **gỡ các key được đặt**, thường trong **finally** hoặc scope có AutoCloseable.
6. Với tác vụ chuyển thread, context cần được **truyền theo cơ chế của ứng dụng**; chỉ đặt MDC trên thread cha không đảm bảo worker nhìn thấy nó.

MDC trong **SLF4J** là một API facade. Hành vi lưu trữ/đọc MDC ở runtime phụ thuộc **MDCAdapter** của provider/backend. Logback Classic hỗ trợ MDC theo luồng xử lý thread; hệ thống không hỗ trợ hoặc dùng adapter no-op có thể không mang lại output tương tự.

## 3. MDC khác message, logger và các loại context khác

| Thứ | Ví dụ | Ý nghĩa |
| --- | --- | --- |
| **MDC key/value** | requestId=req-17 | Bối cảnh chung cho nhiều event cùng phạm vi |
| **Logger name** | com.example.checkout.OrderService | Tên nguồn phát logger, thường theo class/package |
| **Log level** | INFO, WARN, ERROR | Mức severity/độ chi tiết của event |
| **Message** | event=order.created orderId=OD-42 | Điều gì đã xảy ra |
| **Thread name** | http-worker-4 | Thread phát/ghi event; không phải request ID |
| **Marker** | AUDIT, SECURITY | Nhãn bổ sung cho một event hoặc nhóm event theo API |
| **Fluent key–value** | status=200 gắn vào một log call | Field riêng cho một logging event |
| **Trace context** | traceId/spanId | Ngữ cảnh tracing phân tán được quản lý bởi tracing system |
| **MDC** | requestId, operation, tenantId | Bản đồ ngữ cảnh logging có thể xuất trên nhiều event |

**Logger name không nên chứa requestId động.** Một logger thường được giữ lâu dài và dùng lại cho nhiều request; requestId là dữ liệu biến thiên, nên đưa vào MDC hoặc một field của event.

**MDC không tự biến message thành structured JSON.** Nếu pattern là text, MDC có thể chỉ xuất thành chuỗi. Nếu dùng JSON encoder hỗ trợ MDC, từng key có thể được xuất thành field JSON; cấu trúc và kiểu dữ liệu còn phụ thuộc encoder.

**MDC cũng không thay distributed tracing.** Chỉ thêm traceId vào log không tự sinh trace/span, không truyền traceId qua HTTP headers và không gửi telemetry đến tracing backend. Với tracing thật, cần instrumentation và propagator phù hợp; MDC chỉ là một cách thể hiện context trong log.

## 4. API quan trọng của org.slf4j.MDC

Với **SLF4J**, những thao tác MDC cơ bản đều là phương thức static của **org.slf4j.MDC**.

| API | Tác dụng | Khi dùng |
| --- | --- | --- |
| **MDC.put(key, value)** | Đặt/thay giá trị theo key trong context hiện tại | Khi request bắt đầu hoặc bổ sung ngữ cảnh |
| **MDC.get(key)** | Đọc giá trị của key hiện tại | Kiểm tra/điều kiện chẩn đoán |
| **MDC.remove(key)** | Xóa một key | Dọn key do phạm vi này sở hữu |
| **MDC.clear()** | Xóa toàn bộ context hiện tại | Khi phạm vi này sở hữu toàn bộ context |
| **MDC.putCloseable(key, value)** | Đặt key và trả scope có thể đóng, gọi close để xóa key | Dùng trong try-with-resources |
| **MDC.getCopyOfContextMap()** | Lấy bản sao các cặp String–String hiện tại hoặc null | Chuẩn bị truyền context sang worker |
| **MDC.setContextMap(map)** | Thay context hiện tại bằng một bản sao map được cung cấp | Khôi phục/thiết lập context trên thread nhận |
| **MDC.getMDCAdapter()** | Truy cập adapter backend đang sử dụng | Chẩn đoán tích hợp khi thực sự cần |

Ví dụ nhỏ:

~~~java
// Đoạn minh họa bên trong method của ứng dụng đã có LOG.
MDC.put("requestId", "req-17");
try {
    LOG.info("event=request.started");
    LOG.info("event=request.completed status=200");
} finally {
    MDC.remove("requestId");
}
~~~

Dù code trong try ném exception, finally vẫn gỡ requestId khi luồng thực thi tới đó. Điều này đặc biệt cần thiết với **thread pool**, vì một worker thread có thể xử lý request tiếp theo ngay sau đó.

### putCloseable và try-with-resources

~~~java
// Đoạn minh họa: LOG đã được khai báo.
try (MDC.MDCCloseable ignored =
             MDC.putCloseable("requestId", "req-17")) {
    LOG.info("event=request.started");
}
~~~

Khi rời scope, **close() xóa key requestId**. Lợi thế là không cần tự viết finally cho một key. **Quan trọng:** theo SLF4J API, putCloseable là một scope **remove key khi đóng**, không phải ngữ nghĩa **tự phục hồi giá trị cũ**. Nếu key đã có giá trị từ outer scope và bạn ghi đè nó, đóng scope không mặc nhiên đưa giá trị cũ trở lại.

Nếu muốn override rồi **khôi phục nguyên context**, lưu snapshot trước và thiết lập lại snapshot sau, thay vì kỳ vọng putCloseable hoạt động như một stack các giá trị.

### clear() hay remove()?

- Nếu bạn chỉ tạo **requestId**, tốt nhất là **remove("requestId")** khi kết thúc.
- Nếu một middleware sở hữu toàn bộ MDC tại đầu/cuối task, có thể **clear()** theo hợp đồng đó.
- Nếu code nằm trong một scope đã được framework đặt thêm traceId/tenantId, việc gọi **clear()** tùy tiện có thể xóa các key của scope bên ngoài.

**Nguyên tắc ownership:** thành phần nào thêm key cần chịu trách nhiệm dọn key, nhưng không nên xóa thông tin ngữ cảnh mà thành phần khác đang sở hữu.

## 5. MDC là ngữ cảnh nào: thread, request hay process?

Một cách nghĩ phổ biến là “MDC là biến toàn cục của request”. Điều này **không chính xác**.

Với **Logback Classic**, MDC thường được quản lý theo **thread**. Một request được xử lý tuần tự trên một thread có thể có context riêng, nhưng khi công việc đổi thread, context **không được bảo đảm tự đi theo**.

Ví dụ:

~~~text
Thread http-1: MDC.requestId = req-A
Thread http-2: MDC.requestId = req-B
Thread worker-1: có thể chưa có requestId
~~~

MDC không tự biến thành biến toàn cục toàn JVM hoặc một map dùng chung cho mọi request. Những lời gọi static của API không có nghĩa **map là global shared map**; chúng thao tác với adapter/context của thread theo backend.

Trong ứng dụng đồng bộ cổ điển, ranh giới thread và request có thể trùng phần lớn thời gian. Nhưng với **ExecutorService, CompletableFuture, async servlet, message consumer hoặc reactive pipeline**, một request có thể di chuyển qua nhiều thread; ngược lại một thread có thể xử lý nhiều request.

Vì vậy:

- **Không giả định mọi thread con kế thừa MDC**; riêng với executor/thread pool, Logback tài liệu hóa việc cần copy và set context.
- **Không giả định context cũ tự được xóa** khi thread pool tái sử dụng thread.
- **Không dùng ThreadLocal/MDC làm phương pháp truyền context phân tán** qua network.
- Nếu framework hỗ trợ context propagation, dùng cơ chế đã được framework/tracing layer quản lý thay vì viết lại ở từng callback.

## 6. Ví dụ hoàn chỉnh Java 17 + Logback: scope và async propagation

Bài thực hành sử dụng **Java 17**, **SLF4J API** và **Logback Classic**. Nó chứng minh bốn hiện tượng bằng log có output cố định:

1. Ngoài scope, **requestId** chưa có nên pattern in **missing**.
2. Trong scope, nhiều event có **requestId=req-17** dù message không tự nối ID.
3. Một tác vụ gửi sang **ExecutorService** không tự có requestId.
4. Sau khi **copy context vào worker**, event có requestId; cuối task, context được khôi phục, tránh rò sang task sau.

Maven cần có dependency từ kho Maven được cấu hình hoặc cache hợp lệ.

### File src/main/resources/logback.xml

~~~xml
<configuration>
  <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="ch.qos.logback.classic.encoder.PatternLayoutEncoder">
      <charset>UTF-8</charset>
      <pattern>%level | requestId=%X{requestId:-missing} | operation=%X{operation:-none} | %msg%n</pattern>
    </encoder>
  </appender>

  <root level="INFO">
    <appender-ref ref="CONSOLE"/>
  </root>
</configuration>
~~~

Pattern giải nghĩa:
- **%level** xuất INFO/WARN...
- **%X{requestId:-missing}** đọc MDC key requestId; khi không có thì dùng **missing**.
- **%X{operation:-none}** đọc key operation; nếu thiếu in **none**.
- **%msg** lấy message đã format theo tham số SLF4J.
- **%n** thêm dấu xuống dòng.
- Root **INFO** cho phép cả INFO và WARN của bài thực hành.

**Các chữ missing/none là giá trị fallback chỉ để đọc dễ hơn**, không được hiểu như requestId thật. Backend chỉ xuất những field mà pattern hoặc encoder được cấu hình chọn. Nếu không có %X trong pattern này, việc code đặt MDC vẫn không tự làm ID xuất hiện trên console.

### File src/main/java/com/example/logging/MdcDemo.java

~~~java
package com.example.logging;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public class MdcDemo {
    private static final Logger LOG = LoggerFactory.getLogger(MdcDemo.class);

    private static void restoreContext(Map<String, String> previous) {
        if (previous == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(previous);
        }
    }

    public static void main(String[] args) throws Exception {
        LOG.info("event=application.ready");

        try (MDC.MDCCloseable request =
                     MDC.putCloseable("requestId", "req-17")) {
            LOG.info("event=request.started orderId={}", "OD-42");

            try (MDC.MDCCloseable operation =
                         MDC.putCloseable("operation", "payment")) {
                LOG.warn("event=dependency.retry attempt={}", 2);
            }

            ExecutorService executor = Executors.newSingleThreadExecutor();
            try {
                executor.submit(
                        () -> LOG.info("event=async.without_context")).get();

                Map<String, String> captured = MDC.getCopyOfContextMap();
                executor.submit(() -> {
                    Map<String, String> previous = MDC.getCopyOfContextMap();
                    try {
                        restoreContext(captured);
                        LOG.info("event=async.with_context");
                    } finally {
                        restoreContext(previous);
                    }
                }).get();

                executor.submit(
                        () -> LOG.info("event=async.after_context")).get();
            } finally {
                executor.shutdown();
                if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
                    executor.shutdownNow();
                }
            }

            LOG.info("event=request.completed status={}", 200);
        }

        LOG.info("event=application.idle");
    }
}
~~~

### Biên dịch và chạy

Tại thư mục có pom.xml:

~~~bash
mvn -q compile exec:exec "-Dexec.executable=java" "-Dexec.args=-classpath %classpath com.example.logging.MdcDemo"
~~~

Maven Exec Plugin dùng **JVM con** với classpath của project, giúp chương trình không bị ảnh hưởng bởi logging runtime của Maven. Ví dụ đã biên dịch và chạy thành công với JDK 17+/Logback theo dependency ở trên.

**Tám dòng output đúng thứ tự từ Logback ConsoleAppender** (không tính những dòng riêng của Maven hoặc terminal):

~~~text
INFO | requestId=missing | operation=none | event=application.ready
INFO | requestId=req-17 | operation=none | event=request.started orderId=OD-42
WARN | requestId=req-17 | operation=payment | event=dependency.retry attempt=2
INFO | requestId=missing | operation=none | event=async.without_context
INFO | requestId=req-17 | operation=none | event=async.with_context
INFO | requestId=missing | operation=none | event=async.after_context
INFO | requestId=req-17 | operation=none | event=request.completed status=200
INFO | requestId=missing | operation=none | event=application.idle
~~~

Đây là output đã được **chạy thử và đối chiếu**. Không in timestamp và thread name vào pattern để kết quả không biến đổi theo máy hoặc thời điểm.

### Phân tích chi tiết tám dòng

1. **application.ready** phát trước khi đặt MDC nên requestId và operation đều dùng fallback.
2. **request.started** chạy trong scope requestId, chỉ có requestId=req-17.
3. **dependency.retry** chạy trong scope requestId lồng operation=payment, nên cả hai field xuất hiện. **WARN** không tự chứng minh request thất bại; đây có thể là retry được phục hồi.
4. **async.without_context** được phát trên worker của ExecutorService; worker không tự thấy MDC của main thread.
5. **async.with_context** dùng **getCopyOfContextMap()** tại thread gửi task và **setContextMap()** tại worker, nên requestId có mặt.
6. **async.after_context** chạy tiếp trên worker đó sau khi restore context cũ. requestId lại missing, chứng minh code không làm rò context vào task tiếp theo trong ví dụ.
7. **request.completed** quay về main thread, nơi requestId vẫn đang có hiệu lực; thao tác truyền snapshot tới worker không xóa MDC trên main.
8. **application.idle** chạy sau khi try-with-resources đóng request scope, nên requestId không còn.

**Kỹ thuật kiểm tra:** việc gọi **Future.get()** sau mỗi task làm kết quả output có thứ tự xác định. Nếu gửi nhiều tác vụ bất đồng bộ không chờ, các dòng có thể xen kẽ; MDC giúp correlation, **không tự bảo đảm thứ tự toàn cục**.

### Phân tích restoreContext

~~~java
// Đây là hàm của MdcDemo, không phải API built-in của SLF4J.
private static void restoreContext(Map<String, String> previous) {
    if (previous == null) {
        MDC.clear();
    } else {
        MDC.setContextMap(previous);
    }
}
~~~

Mục tiêu là **khôi phục đúng context đã có sẵn của worker trước khi thực hiện task**:
- Nếu worker trước đó chưa có MDC, ta clear sau task.
- Nếu worker đang có một context hợp lệ khác, ta phục hồi map cũ.
- Không nên chỉ **MDC.clear()** trong mọi trường hợp khi code không sở hữu toàn bộ context.
- Vì **getCopyOfContextMap()** trả bản sao, ta không chia sẻ cùng một mutable map giữa hai thread theo cách thiếu kiểm soát.

**Cảnh báo:** khi một framework đã có cơ chế tự động context propagation, bạn không nên lồng thêm nhiều wrapper tự viết thiếu nhất quán. Hãy thống nhất ownership và quy tắc copy/restore ở một tầng thích hợp.

## 7. Một mẫu đơn giản cho HTTP request

Trong một ứng dụng server truyền thống, đầu request thường là nơi thích hợp để thiết lập correlation ID. Ví dụ minh họa:

~~~java
// Đây là pseudocode Java trong request handler/filter, không phải chương trình độc lập.
String requestId = validateOrGenerateRequestId(request);
try (MDC.MDCCloseable scope =
             MDC.putCloseable("requestId", requestId)) {
    handleRequest(request);
}  // MDC key được remove tại đây.
~~~

**validateOrGenerateRequestId(request)** là hàm nghiệp vụ giả định, phải được triển khai trong framework thực. Không nhận nguyên một header do client cung cấp mà không kiểm tra: một ID quá dài, có newline/control character hoặc chứa dữ liệu nhạy cảm có thể gây rủi ro log injection và chi phí lưu trữ.

Trong servlet filter, interceptor hoặc middleware thực tế, thường cần:

1. Nhận requestId có định dạng hợp lệ hoặc tạo ID mới.
2. Đặt các key MDC được phép, ví dụ requestId, traceId, route.
3. Chuyển tiếp đến xử lý nghiệp vụ.
4. Ghi log kết thúc và số liệu cần thiết **trước khi dọn context**, nếu muốn các dòng này mang cùng ID.
5. **Dọn key trong finally**, kể cả khi handler ném exception.
6. Nếu request chuyển sang async processing, dùng lifecycle/propagation framework tương ứng thay vì giả định filter đồng bộ đã bao trọn thời gian xử lý.

**Không đồng nhất requestId với userId.** RequestId nhận diện một lần xử lý; userId/tenantId có thể là dữ liệu nhạy cảm tùy chính sách. Đừng tự gắn email, tên khách hàng hoặc access token vào MDC chỉ để tìm log nhanh hơn.

## 8. MDC trong thread pool và CompletableFuture

Thread pool làm cho bài toán MDC vừa hữu ích vừa dễ mắc lỗi. Ví dụ:

~~~text
HTTP thread A: MDC.requestId=req-A
Executor worker-1: chạy task từ A
HTTP thread B: MDC.requestId=req-B
Executor worker-1: sau đó chạy task từ B
~~~

Nếu task A đã set MDC trên worker-1 nhưng không dọn, task B có thể **đọc nhầm req-A**, mặc dù task B thuộc request khác. Nguy hiểm hơn việc thiếu requestId là một dòng log mang **sai requestId**.

### Quy tắc truyền context

Một wrapper an toàn về nguyên tắc:

~~~java
// Đoạn minh họa trong method có executor và Runnable task.
Map<String, String> captured = MDC.getCopyOfContextMap();

executor.submit(() -> {
    Map<String, String> previous = MDC.getCopyOfContextMap();
    try {
        if (captured == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(captured);
        }
        task.run();
    } finally {
        if (previous == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(previous);
        }
    }
});
~~~

**Điều kiện quan trọng:** snapshot phải được chụp trên thread **đang có context đúng**, thường là trước khi submit task. Chụp trong worker sau khi task đã chuyển thread không giúp lấy lại requestId của thread gửi.

Mẫu này cần được đóng gói ở **executor decorator, task wrapper hoặc cơ chế framework** chứ không copy-paste vào mọi lệnh submit. Trong code production, cần lưu ý exception, cancellation, đồng bộ kết quả, shutdown, context nesting và task được tái sử dụng.

### CompletableFuture

Với **CompletableFuture.supplyAsync(...)** hoặc **thenApplyAsync(...)**, callback có thể chạy trên thread khác hoặc pool khác. **Không mặc định MDC tự đi theo future chain**. Nếu hệ thống có context propagation của Spring, Micrometer, OpenTelemetry hoặc framework async khác, hãy tìm đúng integration của framework và kiểm thử bằng log có requestId. Nếu không, áp dụng snapshot và restore ở ranh giới thực thi phù hợp.

### Reactive pipeline và virtual threads

Với reactive programming, việc dựa duy nhất vào ThreadLocal của MDC có thể sai vì một request được chuyển giữa nhiều thread. Hãy ưu tiên context của framework reactive và tích hợp logging tương ứng. Với virtual threads trên các JDK mới hơn Java 17, cần đánh giá cơ chế truyền context theo runtime thực; **không suy diễn mỗi mô hình concurrency đều giống thread pool cổ điển**.

**Bài học nền tảng:** MDC là **ngữ cảnh logging cục bộ theo execution mechanism của backend**, không tự là một chuẩn truyền dữ liệu qua mọi ranh giới bất đồng bộ.

## 9. MDC trong JSON logging

MDC có thể đi vào text pattern:

~~~text
INFO requestId=req-17 operation=payment event=dependency.retry
~~~

Hoặc được một **JSON encoder** xuất thành các field:

~~~json
{
  "@timestamp": "2026-11-09T13:20:30.123Z",
  "level": "WARN",
  "logger_name": "com.example.logging.MdcDemo",
  "message": "event=dependency.retry attempt=2",
  "requestId": "req-17",
  "operation": "payment"
}
~~~

JSON trên là **ví dụ cấu trúc minh họa**, không phải output cố định của project Maven ở mục 6 vì project đó dùng **PatternLayoutEncoder** và xuất text.

Trong hệ **logstash-logback-encoder**, **LogstashEncoder** có khả năng xuất MDC entries thành các JSON fields. Theo tài liệu của thư viện, cấu hình mặc định thường gồm tất cả MDC entries, nhưng bạn nên **chỉ xuất key được phép** để tránh lộ dữ liệu và va chạm schema.

Một fragment cấu hình JSON encoder:

~~~xml
<!-- Fragment minh họa: cần thêm dependency logstash-logback-encoder
     và đặt encoder này trong appender Logback phù hợp. -->
<encoder class="net.logstash.logback.encoder.LogstashEncoder">
  <includeMdc>true</includeMdc>
  <includeMdcKeyName>requestId</includeMdcKeyName>
  <includeMdcKeyName>operation</includeMdcKeyName>
</encoder>
~~~

Khi chỉ định những **includeMdcKeyName** này, các MDC keys khác không được xuất qua provider MDC của encoder theo cơ chế được tài liệu hóa. **Không đặt thêm một encoder khác trong cùng appender**; đây là cấu hình thay thế cho PatternLayoutEncoder, không phải phần bổ sung vào ví dụ text đang chạy.

### MDC values và kiểu JSON

API MDC thường sử dụng các cặp **String–String**. Khi encoder xuất JSON, chúng thường mang kiểu JSON string:

~~~json
{"requestId":"req-17","attempt":"2"}
~~~

Chuỗi **"2"** khác số **2** trong JSON. Một số encoder có cơ chế chuyển kiểu cho field được cấu hình, nhưng không suy ra mọi giá trị MDC đều tự là number/boolean. Nếu backend phân tích cần kiểu số, hãy thống nhất schema và encoder hoặc đưa dữ liệu đó vào event structured field đúng kiểu.

### Tránh trùng key

Nếu MDC chứa key **level**, **logger_name** hoặc **message** và JSON encoder cũng xuất các field chuẩn cùng tên, có thể sinh **duplicate JSON keys** hoặc xảy ra xung đột khi ingest. Không dùng MDC để ghi đè field hệ thống. Hãy chọn namespace rõ ràng, giới hạn danh sách key và kiểm tra JSON thực bằng parser.

Dùng JSON không có nghĩa dữ liệu tự được redaction. Nếu put một access token vào MDC, encoder có thể lặp lại token trên rất nhiều event trước khi scope được dọn.

## 10. MDC khác SLF4J fluent key–value pairs ở đâu?

SLF4J 2 cho phép đặt key–value **cho một logging event** qua fluent API. Ví dụ:

~~~java
// Đoạn minh họa; LOG thuộc kiểu org.slf4j.Logger.
LOG.atInfo()
        .addKeyValue("orderId", "OD-42")
        .addKeyValue("itemCount", 2)
        .log("event=order.created");
~~~

Điểm khác nhau:

| MDC | Fluent key–value |
| --- | --- |
| Gắn context cho nhiều log calls trong một scope | Gắn field vào một log call cụ thể |
| Dùng put/remove/clear hoặc putCloseable | Dùng LoggingEventBuilder trước log() |
| Thích hợp cho requestId/traceId/operation chung | Thích hợp cho orderId, status, durationMs của event |
| Cần quản lý vòng đời và propagation | Không tự duy trì context giữa các lần gọi |
| Có thể xuất qua %X hoặc MDC JSON provider | Cần encoder/backend hỗ trợ key–value pairs |

**Không có lựa chọn tuyệt đối một bên thay bên kia.** Một bản ghi có thể cần cả:
- **MDC.requestId** để gắn với request.
- **event-level orderId/status/durationMs** để mô tả hành động cụ thể.

Backend phải được cấu hình để những field cần thiết thực sự xuất ra. Nếu bạn chỉ sử dụng PatternLayoutEncoder với **%msg** và **%X**, fluent key–value không nhất thiết tự thành các cột JSON; cần kiểm tra formatter/encoder.

## 11. Phân biệt MDC với distributed tracing

Một hệ thống phân tán có thể xử lý:

~~~text
Gateway -> Order Service -> Payment Service -> Database
~~~

Để truy vết qua nhiều service, cần **trace context propagation** qua network (ví dụ HTTP headers theo một chuẩn) và các instrumentation phù hợp. Một **traceId** có thể được đưa vào MDC để hiện trên log của từng service, nhưng **MDC chỉ là nơi trình bày ID trong logging context**, không phải cơ chế tạo/propagate spans.

Ví dụ một log minh họa:

~~~json
{
  "service.name": "payment-api",
  "traceId": "7cfa...",
  "spanId": "c410...",
  "logger": "com.example.payment.PaymentService",
  "message": "event=payment.authorized"
}
~~~

Các key **service.name, traceId, spanId** chỉ là **schema ví dụ**; backend/OpenTelemetry integration có thể dùng tên hoặc cấu trúc khác. Không tự sinh một traceId bất kỳ trong từng service rồi kỳ vọng các trace nối được với nhau.

### Correlation ID và trace ID

- **requestId**: ID do ứng dụng hoặc gateway chọn để nhận diện một request; định dạng/độ tin cậy tùy hệ thống.
- **traceId**: ID được quản lý bởi tracing system cho một trace, có các quy tắc định dạng/propagation riêng.
- **spanId**: ID của một span trong trace.
- **tenantId**: chỉ danh tenant, có thể nhạy cảm và phải tuân thủ chính sách.
- **operation**: tên bước xử lý, thích hợp cho scope ngắn hoặc event field.

**Một ID không tự chứng minh kết quả thành công.** Cần kết hợp level, event name, status, exception, timestamp và nguồn dữ liệu nghiệp vụ để hiểu sự kiện.

## 12. Lỗi thường gặp khi dùng MDC

| Triệu chứng | Nguyên nhân thường gặp | Hướng xử lý |
| --- | --- | --- |
| Pattern in requestId=missing | Key chưa đặt, key khác chữ hoa/thường hoặc scope đã kết thúc | Xác nhận MDC.put đúng tên và thời điểm log |
| Trong main thấy ID, trong Executor không thấy | Context không được truyền qua thread pool | Snapshot ở thread gửi, set/restore ở worker |
| Task B hiển thị requestId của task A | Worker thread tái sử dụng nhưng MDC chưa dọn | Gỡ/restore trong finally của mỗi task |
| Log xuất đúng message nhưng không có MDC | Pattern thiếu %X hoặc JSON encoder không include MDC | Kiểm tra layout/encoder và field name |
| RequestId mất giữa CompletableFuture stages | Mỗi stage có thể chạy trên thread khác | Dùng context propagation tại ranh giới async |
| Sau khi close putCloseable, key cũ không trở lại | putCloseable chỉ remove key khi close | Snapshot và restore nếu đang ghi đè outer value |
| Gọi MDC.clear xóa luôn traceId của framework | Code xóa toàn bộ context không thuộc quyền sở hữu | Chỉ remove key tự thêm hoặc restore snapshot |
| Có hai requestId trong JSON | MDC và event fields trùng key, hoặc encoder cấu hình hai nguồn | Chuẩn hóa schema, hạn chế key được include |
| Có MDC trong code nhưng backend khác không xuất | Adapter/provider không hỗ trợ hoặc config khác | Xác minh SLF4J provider và MDC adapter |
| Log bị lẫn khi gửi sang HTTP service khác | MDC không truyền qua network | Dùng headers/tracing propagation phù hợp |
| requestId quá dài hoặc chứa newline | Dùng ID không tin cậy từ client | Kiểm tra định dạng, giới hạn chiều dài, escape |
| Hệ thống log quá lớn | Gắn nhiều field dài vào mọi event | Giữ tập key nhỏ, giảm dữ liệu lặp |
| ERROR mất traceId | Exception được xử lý sau khi scope MDC đóng | Ghi exception trong scope hoặc bảo toàn context cho logging |
| MDC chỉ hiện ở text nhưng thiếu trong JSON index | Collector/ingest thay tên/drop field | Đọc JSON raw và kiểm tra mapping |
| Context rò giữa test cases | Test không dọn MDC sau khi chạy | Gỡ key/clear đúng ownership ở teardown |

**Bẫy đáng chú ý:** việc ghi log trong **catch** hoặc callback sau khi request scope đã thoát có thể làm mất ID, dù business method ban đầu đặt MDC đúng. Khi thiết kế vòng đời, phải biết **log cuối cùng cần correlation** được phát trước khi đóng context hay không.

## 13. Hiệu năng, cardinality và bảo mật

MDC hữu ích, nhưng không miễn phí.

### Hiệu năng

- MDC operations có chi phí quản lý context; theo tài liệu Logback, không nên thay đổi MDC với tần suất quá cao trên từng dòng log trong các vòng lặp nóng.
- Một snapshot/copy map cho mọi task cũng tiêu thụ bộ nhớ và CPU; cần đo khi dùng ở lưu lượng rất lớn.
- Mỗi field MDC được xuất lặp lại trên nhiều record, làm tăng bytes ghi, indexing và chi phí lưu trữ.
- Có những pipeline async mà snapshot/log event được chuẩn bị theo thời điểm riêng; phải kiểm thử đầu ra thực tế, không dựa vào suy đoán rằng một map bị thay sau đó sẽ ảnh hưởng mọi event trước đó.
- Tránh đưa object rất lớn, JSON payload nguyên vẹn hoặc chuỗi không có giới hạn chiều dài vào MDC.

### Cardinality

Các field như **requestId** có số giá trị rất cao, vì mỗi request mới có một ID mới. Hệ thống tìm kiếm có thể index chúng như keyword để truy vấn, nhưng không nên dùng requestId làm **metric label** cho những phép tổng hợp có giới hạn cardinality. Đây là hai bài toán lưu trữ và phân tích khác nhau.

Những field như **operation** hoặc **environment** có tập giá trị nhỏ hơn, nhưng vẫn cần tránh tạo giá trị động không kiểm soát.

### Bảo mật và riêng tư

Không ghi vào MDC:
- Password, access token, API key, session cookie hoặc OTP.
- Số thẻ thanh toán, private key hoặc credential.
- Toàn bộ request/response payload hoặc headers chứa secret.
- Dữ liệu cá nhân không có căn cứ xử lý và chính sách bảo vệ phù hợp.

Nếu tenantId/userId phải ghi để chẩn đoán, cần đánh giá có được phép không, có cần pseudonymization/masking, giới hạn lưu giữ và phân quyền đọc log. **MDC được xuất nhiều lần trên nhiều record**, nên một dữ liệu nhạy cảm đặt sai chỗ có thể làm mức độ rò rỉ nghiêm trọng hơn.

Đầu vào không tin cậy có thể chứa **newline, control character hoặc ký tự giả mạo log**. Hãy kiểm tra, làm sạch và giới hạn dữ liệu; dùng JSON encoder có escaping đúng khi phù hợp. Tuy nhiên, JSON hợp lệ không thay thế kiểm soát dữ liệu bí mật.

### Ownership của context

Thành phần thiết lập context phải nắm rõ:
- Key nào thuộc quyền quản lý của mình?
- Scope kết thúc khi nào?
- Có tác vụ async nào còn chạy sau khi scope kết thúc không?
- Có đang overwrite một key có sẵn không?
- Cần remove một key hay restore toàn bộ map?
- Backend nào thực sự sử dụng MDC adapter?

Nếu không trả lời được, khả năng rò context hoặc gắn sai correlation ID rất cao.

## 14. Thiết kế một quy ước MDC gọn và rõ

Một schema thực dụng cho Java service có thể là:

| Key | Giá trị ví dụ | Khi nào dùng |
| --- | --- | --- |
| **requestId** | req-17 | Gắn nhiều event của cùng request |
| **traceId** | ID do tracing system cấp | Liên kết telemetry giữa các service |
| **spanId** | ID span hiện tại | Định vị đoạn xử lý trong trace |
| **operation** | payment.authorize | Gắn với một bước xử lý có scope rõ |
| **tenantId** | mã đã được phép ghi | Chỉ khi chính sách cho phép và có kiểm soát |
| **jobId** | batch-2026-11-09 | Correlation cho background job |
| **messageId** | msg-42 | Correlation ở message consumer |
| **environment** | staging | Có thể đặt từ deployment config thay vì MDC |

**Không cần gắn tất cả field vào mỗi request.** Chọn dữ liệu thực sự giúp điều tra và xác định độ nhạy cảm của từng trường.

Một quy ước tốt nên quy định:
1. **Tên key nhất quán** về kiểu chữ (requestId khác requestID).
2. **Nguồn tạo giá trị**, ví dụ gateway, tracing system hoặc job scheduler.
3. **Phạm vi sống** và thành phần chịu trách nhiệm cleanup.
4. **Propagation khi đổi thread/service**.
5. **Giá trị fallback** khi chưa có context.
6. **Danh sách field được phép xuất** trong text và JSON.
7. **Giới hạn độ dài, kiểm tra định dạng và chính sách dữ liệu**.
8. **Tương thích parser, dashboard và alert** khi đổi backend/encoder.

Dùng một tập key nhỏ và rõ ràng thường giúp vận hành tốt hơn cố nhồi toàn bộ thông tin nghiệp vụ vào MDC.

## 15. Cách tự kiểm tra MDC trong một ứng dụng Java

Một checklist kiểm thử:

1. **Không có MDC:** ghi log trước scope, xác nhận fallback hiện đúng.
2. **Có một key:** đặt requestId và xác nhận nhiều log calls cùng mang ID.
3. **Có nhiều key:** đặt operation trong một scope ngắn và kiểm tra nó chỉ hiện ở scope đó.
4. **Sau khi kết thúc scope:** log thêm một record; requestId/operation phải không còn nếu được dọn đúng.
5. **Hai request liên tiếp trên cùng worker:** đảm bảo không lẫn ID của request trước.
6. **Async task không propagation:** xác nhận thiếu context như thiết kế, không coi đó là lỗi của formatter.
7. **Async task có propagation:** snapshot trước submit, set trên worker, đối chiếu event nhận đúng ID.
8. **Task sau propagation:** kiểm tra context được restore, không rò sang task khác.
9. **Throwable:** ghi exception trong scope để bảo toàn ngữ cảnh, kiểm tra stack trace thuộc đúng request.
10. **JSON encoder:** parse record, kiểm tra key có mặt/không trùng, kiểu String và schema đã cam kết.
11. **Thông điệp Unicode/quote/newline:** xác nhận encoder xử lý đúng và không làm vỡ parser.
12. **Provider khác:** nếu chuyển Logback sang provider khác, xác minh tính năng MDC và format thực tế.
13. **Load test:** theo dõi chi phí context copy và số bytes dữ liệu lặp.
14. **Security:** thử ID không tin cậy trong môi trường test và xác nhận validation/escaping.
15. **Tài liệu vận hành:** mô tả cách truy một requestId/traceId qua service và khoảng thời gian.

Không nên chỉ grep một dòng có requestId rồi kết luận toàn pipeline đã đúng. **Lỗi nguy hiểm là ID sai nhưng vẫn có vẻ hợp lệ**, chẳng hạn task B ghi nhầm requestId của A do thread reuse.

### Một phép kiểm tra bằng chương trình

Ví dụ của mục 6 đã chứng minh:
- Ở main thread, requestId tồn tại trong scope.
- Executor worker không tự nhận ID.
- Worker có ID khi nhận snapshot.
- Worker được restore sau khi hoàn thành.
- Main thread được dọn sau khi kết thúc request.

Với application thật, hãy thêm unit/integration test tại **filter/interceptor/task decorator** là nơi context được thiết lập và truyền đi, thay vì chỉ test mã nghiệp vụ.

## 16. Những câu hỏi tự kiểm tra

**Câu 1.** MDC viết tắt của gì?  
**Đáp án:** Mapped Diagnostic Context, ngữ cảnh chẩn đoán dạng ánh xạ key–value.

**Câu 2.** Vì sao dùng MDC thay vì nối requestId vào mọi message?  
**Đáp án:** Nó cho phép backend xuất context nhất quán trong nhiều logging event cùng scope, giảm lặp code và hỗ trợ correlation.

**Câu 3.** MDC có tự tạo trace phân tán giữa các microservice không?  
**Đáp án:** Không. Cần tracing context và network propagation riêng; MDC chỉ có thể thể hiện các ID đó trong log.

**Câu 4.** Vì sao requestId hiện trong main thread nhưng thiếu trong Executor?  
**Đáp án:** MDC Logback không tự bảo đảm inheritance qua executor; cần truyền snapshot hoặc dùng context propagation của framework.

**Câu 5.** Vì sao phải dọn MDC trong finally hoặc try-with-resources?  
**Đáp án:** Để tránh context rò sang request/task sau trên cùng thread và đảm bảo cleanup cả khi có exception.

**Câu 6.** putCloseable có tự khôi phục giá trị cũ của cùng key không?  
**Đáp án:** Không theo hợp đồng SLF4J: close xóa key. Muốn khôi phục outer context, cần snapshot và restore có chủ đích.

**Câu 7.** MDC.clear có luôn tốt hơn remove một key không?  
**Đáp án:** Không. clear xóa mọi key, có thể xóa context do framework hoặc outer scope quản lý.

**Câu 8.** Nếu đã gọi MDC.put nhưng pattern thiếu %X, requestId có tự xuất trên console không?  
**Đáp án:** Không nhất thiết. Layout/encoder phải được cấu hình để xuất MDC.

**Câu 9.** MDC chứa attempt="2" thì JSON encoder chắc chắn xuất number 2 không?  
**Đáp án:** Không. MDC thường giữ String; kiểu JSON do encoder/schema quyết định.

**Câu 10.** Có nên đặt access token vào MDC để debug không?  
**Đáp án:** Không. Token có thể bị lặp trên mọi dòng log trong scope và bị thu thập/lưu giữ.

**Câu 11.** Tại sao context propagation phải restore cả map cũ của worker?  
**Đáp án:** Để task mới không rò requestId sang task tiếp theo và không phá context hợp lệ đã có trên worker.

**Câu 12.** Nếu thread name giống nhau ở hai record, có chắc hai record thuộc cùng request không?  
**Đáp án:** Không. Thread pool tái sử dụng thread; cần correlation ID/trace context đúng.

## Ghi nhớ

**MDC là bộ key–value context giúp nhiều logging event của cùng một request/job có chung thông tin chẩn đoán, điển hình là requestId hoặc traceId.** Trong SLF4J + Logback, code đặt context bằng MDC API và backend xuất qua **%X** hoặc JSON encoder. **MDC cần lifecycle rõ ràng**: đặt trước lúc log, dọn trong finally/try-with-resources, copy và restore ở ranh giới async. Đừng coi nó là biến global, một tracing system, kho lưu bền vững hay nơi chứa thông tin nhạy cảm. Một MDC đúng phải giúp **gắn đúng event với đúng ngữ cảnh** mà không rò dữ liệu sang yêu cầu khác.
