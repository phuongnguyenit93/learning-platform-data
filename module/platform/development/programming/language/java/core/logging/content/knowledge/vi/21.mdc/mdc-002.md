# Đặt giá trị MDC trong Java: từ một request đến logging đa luồng

## 1. MDC là gì và tại sao cần đặt giá trị?

**MDC (Mapped Diagnostic Context)** là một **bản đồ key–value dành cho ngữ cảnh chẩn đoán**, thường được gắn với thread đang chạy, để những lời gọi log bên trong cùng luồng xử lý có thể sử dụng metadata mà không cần truyền lặp lại các giá trị đó vào từng câu LOG.info. Trong ứng dụng Java, MDC đặc biệt hữu ích để gắn **requestId**, **traceId**, **tenantId đã được phép ghi**, **operation**, **jobId** hoặc mã correlation an toàn vào log.

Ví dụ một request thực hiện nhiều bước:

~~~text
INFO req=req-42 event=order.received
INFO req=req-42 event=inventory.checked
INFO req=req-42 event=payment.authorized
INFO req=req-42 event=order.completed
~~~

Không cần viết **req=req-42** vào mọi message bằng tay. Tại điểm bắt đầu request, ta có thể **đặt giá trị MDC**:

~~~java
MDC.put("requestId", "req-42");
~~~

Sau đó backend logging có thể sử dụng field **requestId** trong PatternLayout hoặc JSON encoder cho các bản ghi được phát trong ngữ cảnh tương ứng. **MDC.put chỉ đặt dữ liệu; nó không tự xuất field ra console.** Để nhìn thấy giá trị, cần cấu hình layout/encoder của backend.

Bài học tập trung vào **đặt giá trị MDC** thuộc nhóm **MDC** của **Java Core Logging**, bao gồm cách dùng API, vòng đời, ngữ cảnh bất đồng bộ, xử lý giá trị cũ, sự khác biệt giữa các backend và kiểm chứng bằng Java 17. Đây là kiến thức nền để điều tra request xuyên nhiều lớp mà không trộn log của những request khác nhau.

Sau khi học, bạn có thể:

- Biết MDC khác với Logger name, message và business data như thế nào.
- Dùng **org.slf4j.MDC.put**, **get**, **remove**, **clear** và **putCloseable** đúng mục đích.
- Kiểm tra key/value, hiểu thao tác ghi đè và giới hạn với giá trị null.
- Quản lý scope bằng **try/finally** hoặc **try-with-resources**.
- Nhận ra vì sao thread pool không tự kế thừa MDC và dùng **snapshot + restore** để truyền có kiểm soát.
- Cấu hình Logback PatternLayout để đọc **%X{requestId}** và kiểm chứng stdout.
- Phân biệt SLF4J MDC với **Log4j2 ThreadContext** và JUL.
- Tránh rò dữ liệu giữa request, log trùng, giá trị context cũ và thông tin nhạy cảm.
- Kiểm thử MDC trong unit test, integration test và ứng dụng đa luồng.

## 2. MDC nằm ở đâu trong hệ logging?

Mô hình khái niệm:

~~~text
Request / Job / Operation
   |
   | MDC.put("requestId", "req-42")
   v
Current thread's MDC map
   |
   +-- business service -> LOG.info("event=order.received")
   +-- repository       -> LOG.info("event=inventory.checked")
   +-- payment client   -> LOG.warn("event=payment.retry")
   |
   v
Logging API / backend
   |
   | lấy message + level + logger name + MDC snapshot
   v
Layout / Encoder
   |
   v
stdout / file / collector
~~~

MDC giúp **mang cùng một context** tới nhiều log events. Nó không thay Logger, LogRecord hay Appender. Vai trò của từng thành phần:

| Thành phần | Trả lời câu hỏi | Ví dụ |
| --- | --- | --- |
| **Logger name** | Thành phần nào phát log? | demo.checkout.OrderService |
| **Level** | Mức độ quan trọng? | INFO, WARN, ERROR |
| **Message/event** | Điều gì đã xảy ra? | event=order.created |
| **MDC fields** | Event thuộc request/operation nào? | requestId=req-42 |
| **Exception** | Nguyên nhân và stack trace ra sao? | GatewayTimeout |
| **Layout/encoder** | Event được xuất thành text/JSON thế nào? | %X{requestId} hoặc JSON field |
| **Appender/Handler** | Event được gửi tới đâu? | console, file, collector |

**Không sử dụng Logger name để chứa requestId.** Tạo Logger tên **request-req-42** cho mỗi request sẽ làm namespace khó quản lý và khó cấu hình. Hãy để Logger name ổn định theo class/package; requestId thuộc MDC.

### 2.1. MDC không phải bộ nhớ nghiệp vụ

MDC chỉ nên chứa metadata đủ để phục vụ chẩn đoán. **Không dùng MDC làm nguồn sự thật** cho quyết định authorization, tính giá, giao dịch, phân vùng dữ liệu hay các kiểm tra nghiệp vụ. Nếu thiếu requestId, ứng dụng vẫn phải thực thi nghiệp vụ đúng theo tham số và security context chính thống.

### 2.2. MDC thường gắn với thread

Trong các backend phổ biến, MDC map được duy trì theo **thread-local context** hoặc cơ chế tương đương. Vì vậy, nhiều lời gọi LOG.info trên cùng thread thường đọc được giá trị đã đặt; nhưng task chạy ở thread khác **không tự động nhận** map từ thread gọi.

Đây là đặc điểm quan trọng nhất khi đi từ ví dụ console đơn giản sang server có thread pool hoặc CompletableFuture. Cơ chế cụ thể có thể thay đổi theo logging provider và execution model, vì SLF4J chỉ định nghĩa facade API còn implementation phụ trách cách lưu/định tuyến MDC.

## 3. API SLF4J MDC quan trọng nhất

SLF4J cung cấp class **org.slf4j.MDC** với các phương thức static. Khi backend/provider hỗ trợ MDC, API chuyển các thao tác tới MDC adapter của implementation.

| Phương thức | Ý nghĩa | Khi sử dụng |
| --- | --- | --- |
| **MDC.put(key, value)** | Đặt hoặc ghi đè giá trị theo key trên thread hiện hành | Bắt đầu request, gắn jobId, operation |
| **MDC.get(key)** | Đọc giá trị đã đặt theo key | Kiểm tra context trong test hoặc debug |
| **MDC.remove(key)** | Xóa một key | Kết thúc scope của một field |
| **MDC.clear()** | Xóa toàn bộ MDC map hiện hành | Dọn context ở request boundary có quyền sở hữu toàn bộ map |
| **MDC.putCloseable(key, value)** | Đặt key và trả đối tượng Closeable dùng để remove khi đóng | Scope một key trong try-with-resources |
| **MDC.getCopyOfContextMap()** | Lấy bản sao map của thread hiện hành, có thể null | Snapshot để truyền qua executor |
| **MDC.setContextMap(map)** | Thay map hiện hành bằng bản sao của map được cung cấp | Thiết lập context cho thread khác, sau đó restore |

Đây là API **SLF4J**: import **org.slf4j.MDC**. **Không nhầm với** **java.util.logging.Logger** hoặc Log4j2 **org.apache.logging.log4j.ThreadContext**, dù các công cụ có mục đích tương tự.

### 3.1. Đặt một key/value

~~~java
import org.slf4j.MDC;

// Trong một phương thức:
MDC.put("requestId", "req-42");
~~~

Đoạn này là **mã tích hợp**, chưa có main() hoặc setup backend. Nó đặt giá trị dạng **String** dưới key **requestId** trong diagnostic context của thread hiện tại.

**Giá trị được gắn vào các logging events về sau** nếu backend ghi nhận MDC và Layout/Encoder được cấu hình lấy field. Câu gọi MDC.put không phải lời gọi phát log, nên bản thân nó không tạo dòng output.

### 3.2. Đặt nhiều key

~~~java
MDC.put("requestId", "req-42");
MDC.put("operation", "checkout");
MDC.put("component", "payment");
~~~

Những key nên có **quy ước nhất quán** giữa các service. Nếu một service dùng requestId và service khác dùng req_id cho cùng ngữ nghĩa, query log xuyên dịch vụ sẽ cần mapping đặc biệt. Chọn một contract đặt tên và kiểm thử trên output cuối cùng.

**Không đặt mọi thuộc tính của domain object vào MDC.** Một số field, ví dụ item count hoặc payment amount, có thể chỉ liên quan một event cụ thể và nên được ghi dưới dạng structured event attributes ở đúng điểm phát sinh thay vì giữ lâu trong thread context.

### 3.3. Đọc giá trị

~~~java
String currentRequestId = MDC.get("requestId");
~~~

**MDC.get** có thể trả **null** nếu key không tồn tại. Nó phù hợp để xác minh context được gắn đúng trong test hoặc trong mã quản lý context, nhưng không dùng làm đầu vào duy nhất cho logic nghiệp vụ quan trọng.

### 3.4. Đặt lại cùng key sẽ ghi đè

~~~java
MDC.put("requestId", "req-42");
MDC.put("requestId", "req-43");
String current = MDC.get("requestId"); // "req-43"
~~~

MDC là **map**; ghi vào cùng key sẽ thay giá trị trước đó. Bởi vậy cần hiểu vòng đời của từng key. Nếu một method lồng nhau thay requestId trong cùng thread, method bên ngoài có thể mất giá trị của mình nếu không có logic restore.

### 3.5. Xóa một key và xóa toàn bộ

~~~java
MDC.remove("operation"); // Xóa đúng một trường
MDC.clear();             // Xóa mọi trường trong MDC hiện hành
~~~

**MDC.remove** thích hợp khi chỉ sở hữu một key. **MDC.clear** thích hợp ở request boundary nơi bạn cố ý kết thúc toàn bộ diagnostic context. Nhưng clear trong một helper lồng nhau có thể làm mất cả traceId, requestId hoặc field mà lớp khác đang quản lý.

### 3.6. Giá trị null và key không hợp lệ

Theo API SLF4J:
- **key không được null**; put(null, ...) không hợp lệ.
- **value null chỉ được chấp nhận nếu implementation phía dưới hỗ trợ**. Không coi **MDC.put(key, null)** là cách xóa field portable.
- Để xóa, gọi **MDC.remove(key)**.
- Giá trị trong MDC map cơ bản là **String**, không phải nơi lưu đối tượng mutable hoặc entity nghiệp vụ.

Với số nguyên hoặc UUID, chuyển thành String theo format ổn định sau khi dữ liệu đã được xác minh:

~~~java
MDC.put("attempt", Integer.toString(attempt)); // attempt là int trong method
MDC.put("requestId", requestId.toString());     // requestId đã non-null
~~~

Đây là mảnh minh họa với các biến đã tồn tại, không phải chương trình chạy độc lập. Trong hệ thống có structured encoder, **kiểu dữ liệu của MDC thường là string**; nếu cần số để aggregate, có thể dùng event attributes có kiểu số riêng hoặc mapping chuẩn hóa ở pipeline.

## 4. Vòng đời một giá trị MDC

Một flow điển hình:

~~~text
Thread nhận request req-42
  |
  +--> MDC.put("requestId","req-42")
  |
  +--> logger.info(...) -> record chứa req-42
  +--> service.run(...) -> logger.warn(...) chứa req-42
  |
  +--> finally: MDC.remove("requestId")
  |
Thread được tái sử dụng cho request req-43
  |
  +--> MDC.put("requestId","req-43")
  +--> logger.info(...) -> record chứa req-43
  +--> finally: MDC.remove("requestId")
~~~

Nếu không cleanup, request req-43 có thể nhận log metadata từ req-42 trên một thread pool được tái sử dụng, tạo **sai correlation** và có thể gây rò dữ liệu giữa các tenant.

### 4.1. Mẫu try/finally với một key

~~~java
MDC.put("requestId", requestId);
try {
    processRequest();
} finally {
    MDC.remove("requestId");
}
~~~

Đây là **mã tích hợp**, cần requestId và processRequest() trong scope của method. finally chạy kể cả khi processRequest ném exception. Nếu bạn sở hữu **duy nhất** key requestId thì remove đúng key ít gây ảnh hưởng hơn clear toàn bộ map.

Tuy nhiên mẫu này **không khôi phục giá trị requestId cũ** nếu method được gọi lồng trong một scope đã có requestId. Đối với nested scopes, xem mục 5.

### 4.2. Mẫu try-with-resources với putCloseable

~~~java
try (MDC.MDCCloseable ignored =
             MDC.putCloseable("operation", "reserve")) {
    LOG.info("event=inventory.check");
}
~~~

Khi block kết thúc, **close() loại bỏ key operation**. Thực hành này giúp hạn chế quên cleanup và thích hợp khi key operation **chưa có** trước khi vào scope.

**Điểm rất dễ nhầm:** SLF4J **MDC.putCloseable** được mô tả là **remove key lúc close**, **không hứa khôi phục giá trị trước** nếu cùng key đã tồn tại. Do đó đừng coi nó luôn giống một context stack hỗ trợ push/pop chính xác giá trị cũ.

### 4.3. Scope lồng nhau và khôi phục giá trị cũ

Giả sử bên ngoài có operation=checkout, bên trong tạm thời dùng operation=payment. Khi ra khỏi inner scope, bên ngoài vẫn muốn operation=checkout.

~~~java
String previous = MDC.get("operation");
MDC.put("operation", "payment");
try {
    LOG.info("event=payment.started");
} finally {
    if (previous == null) {
        MDC.remove("operation");
    } else {
        MDC.put("operation", previous);
    }
}
~~~

Đoạn này minh họa trong một class có LOG, không chạy độc lập. Nó **khôi phục giá trị cũ** sau khi override; khác **putCloseable** có semantics remove key khi close.

Một cách khác là snapshot toàn bộ map rồi restore sau block, phù hợp với những scope có nhiều field cần giữ nguyên; nhưng tạo/copy map có chi phí và phải dùng đúng phạm vi.

### 4.4. Khi nào dùng MDC.clear?

**MDC.clear()** xóa tất cả keys trên thread hiện hành. Dùng nó khi bạn chắc chắn sở hữu cả context, ví dụ tại cuối request boundary được thiết kế để xóa mọi diagnostic data còn sót. Không gọi clear trong DAO/helper vì sẽ phá context của caller.

Ở middleware/web filter, có thể dùng clear tại boundary khi kiến trúc quy định **mỗi request bắt đầu từ MDC trống và kết thúc bằng MDC trống**. Nếu có scope MDC của framework đã tồn tại và cần khôi phục, phải dùng snapshot/restore thay vì clear mù quáng.

## 5. MDC từ code Java tới log thực tế

**MDC.put không tự ghi ra file hay console.** Hãy xem hai phần tách biệt:

1. **Producer:** code gắn requestId và phát log.
2. **Presentation:** backend/encoder sử dụng requestId trong format.

Ví dụ Logback PatternLayout:

~~~text
%level|%thread|req=%X{requestId:-none}|%msg%n
~~~

Trong Logback:
- **%level**: severity.
- **%thread**: tên thread.
- **%X{requestId}**: đọc giá trị MDC của key requestId.
- **%X{requestId:-none}**: sử dụng **none** khi không có giá trị phù hợp.
- **%msg**: message đã render.
- **%n**: newline.

Với cùng code MDC, nếu Layout chỉ có **%msg%n** thì output có thể không chứa requestId. **Đừng kết luận MDC.put không hoạt động chỉ vì không thấy key trên console**; hãy kiểm tra backend/provider và layout.

### 5.1. MDC và log có cấu trúc

Trong JSON logging, một event có thể được xuất:

~~~json
{
  "level": "INFO",
  "logger": "demo.mdc.MdcDemo",
  "message": "event=request.started",
  "requestId": "req-42",
  "tenant": "demo"
}
~~~

Đây là **ví dụ JSON minh họa**, không phải stdout của chương trình bên dưới. Để có output JSON thực, cần dùng encoder/JSON layout được cấu hình đưa MDC thành fields tương ứng. Đừng tự nối chuỗi tạo JSON vì requestId có thể chứa quote hoặc ký tự điều khiển.

**Kiểu MDC cơ bản là String**. Một field JSON như attemptCount cần được thiết kế cẩn thận nếu downstream mong đợi JSON number thay vì string; dùng structured attributes có kiểu dữ liệu thực hoặc bước normalize rõ ràng.

## 6. Ví dụ chạy độc lập Java 17 + SLF4J 2 + Logback

Ví dụ này có đầy đủ **pom.xml**, **logback.xml** và một **main class**. Nó đã được biên dịch và chạy với:
- Java target **17**;
- **SLF4J API 2.0.17**;
- **Logback Classic 1.5.18**;
- Maven Compiler Plugin **3.14.0**.

Dùng phiên bản cố định giúp tái lập kết quả học tập. Khi triển khai production, cập nhật theo các bản được duy trì và hướng dẫn bảo mật/tương thích của dự án.

Chương trình thể hiện:
1. Một log chưa đặt MDC.
2. Đặt requestId và tenant.
3. Đọc lại requestId bằng MDC.get.
4. Gắn operation bằng putCloseable và thấy nó biến mất khi scope đóng.
5. Xóa tenant bằng remove và toàn bộ context bằng clear.
6. Một task executor **không tự nhận MDC**.
7. Truyền snapshot tới worker thread rồi restore map cũ.
8. Một task khác trên cùng worker thread không còn requestId cũ.

~~~

### 6.3. src/main/resources/logback.xml

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
  <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
    <target>System.out</target>
    <encoder>
      <pattern>%level|%thread|req=%X{requestId:-none}|tenant=%X{tenant:-none}|op=%X{operation:-none}|%msg%n</pattern>
    </encoder>
  </appender>
  <root level="INFO"><appender-ref ref="STDOUT"/></root>
</configuration>
~~~

**Mẫu hiển thị:** severity | thread | requestId | tenant | operation | event message. Chọn **System.out** giúp kết quả dễ kiểm tra ở stdout; có thể dùng backend khác hoặc JSON layout trong môi trường thực tế.

Các giá trị **none** chỉ là default khi key chưa tồn tại, không phải một request ID thật. Việc đặt default hữu ích để phân biệt event có context và event không có context.

### 6.4. src/main/java/demo/mdc/MdcDemo.java

~~~java
package demo.mdc;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public final class MdcDemo {
    private static final Logger LOG = LoggerFactory.getLogger(MdcDemo.class);

    public static void main(String[] args) throws Exception {
        MDC.clear();
        LOG.info("event=boot");

        MDC.put("requestId", "req-42");
        MDC.put("tenant", "demo");
        LOG.info("event=request.started");
        System.out.println("get-requestId=" + MDC.get("requestId"));

        try (MDC.MDCCloseable ignored = MDC.putCloseable("operation", "reserve")) {
            LOG.info("event=inventory.check");
        }
        LOG.info("event=request.finished");

        MDC.remove("tenant");
        LOG.info("event=after.tenant.remove");
        MDC.clear();
        LOG.info("event=after.cleanup");

        ExecutorService pool = Executors.newSingleThreadExecutor(r ->
                new Thread(r, "worker-mdc"));
        try {
            MDC.put("requestId", "req-99");
            pool.submit(() -> LOG.info("event=async.without.context")).get();

            Map<String, String> snapshot = MDC.getCopyOfContextMap();
            pool.submit(() -> {
                Map<String, String> previous = MDC.getCopyOfContextMap();
                try {
                    if (snapshot == null) MDC.clear();
                    else MDC.setContextMap(snapshot);
                    LOG.info("event=async.with.context");
                } finally {
                    if (previous == null) MDC.clear();
                    else MDC.setContextMap(previous);
                }
            }).get();

            pool.submit(() -> LOG.info("event=async.after.cleanup")).get();
        } finally {
            MDC.clear();
            pool.shutdown();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) pool.shutdownNow();
        }
    }
}
~~~

**Đây là một chương trình Java 17 đầy đủ, không có hàm phụ chưa định nghĩa.** Nó dùng **java.util.concurrent** để thực sự chạy task trên một worker thread. Tên thread được đặt cố định **worker-mdc**, giúp đối chiếu output không phụ thuộc tên mặc định của thread pool.

### 6.7. Giải thích từng nhóm dòng

**event=boot:** main thread chưa đặt context, các key được layout hiển thị mặc định là none.

**event=request.started:** hai lời gọi MDC.put đã đặt requestId và tenant, nên Logback xuất **req=req-42** và **tenant=demo**.

**get-requestId=req-42:** đây là dòng **System.out.println** để minh họa MDC.get; nó không tự đi qua Logger.

**event=inventory.check:** key operation được đặt bằng **putCloseable**, nên dòng nằm trong scope có **op=reserve**.

**event=request.finished:** ra khỏi try-with-resources, **operation** đã được remove và được layout hiển thị thành **op=none**, trong khi requestId/tenant vẫn tồn tại.

**event=after.tenant.remove:** remove("tenant") chỉ xóa tenant; requestId vẫn còn.

**event=after.cleanup:** MDC.clear dọn toàn bộ context của main thread.

**event=async.without.context:** main thread đã đặt **req-99**, nhưng worker thread không tự kế thừa giá trị, nên log có **req=none**.

**event=async.with.context:** trước khi submit, main thread lấy snapshot bằng getCopyOfContextMap. Worker thread dùng setContextMap để đặt snapshot rồi ghi log, nên có **req=req-99**.

**event=async.after.cleanup:** task trước đã restore context cũ trong finally. Task sau trên chính worker-mdc không mang requestId cũ; đây là bằng chứng quan trọng về cleanup.

## 7. Truyền MDC qua ExecutorService đúng cách

Đây là điểm dễ sai nhất khi đặt giá trị MDC.

### 7.1. Vì sao put ở thread gọi chưa đủ?

Ví dụ:

~~~java
MDC.put("requestId", "req-42");
executor.submit(() -> LOG.info("event=async.started"));
~~~

Đây là đoạn mã tích hợp, giả định executor và LOG đã tồn tại. **ThreadLocal context của thread submit không tự được chuyển sang thread chạy task trong executor**. Một số runtime/instrumentation cung cấp cơ chế propagation riêng, nhưng không nên mặc định điều đó chỉ từ lời gọi submit.

Nếu worker thread đang giữ MDC của task cũ và không được cleanup, log mới còn có thể mang **requestId sai**, nguy hiểm hơn việc hiển thị none.

### 7.2. Capture trước khi submit, set và restore trong worker

Mẫu an toàn:

~~~java
Map<String, String> captured = MDC.getCopyOfContextMap();

executor.submit(() -> {
    Map<String, String> previous = MDC.getCopyOfContextMap();
    try {
        if (captured == null) MDC.clear();
        else MDC.setContextMap(captured);

        LOG.info("event=async.started");
        doWork();
    } finally {
        if (previous == null) MDC.clear();
        else MDC.setContextMap(previous);
    }
});
~~~

Đây là mảnh minh họa trong một phương thức có executor, LOG và doWork đã định nghĩa. **Capture ở thread gửi công việc**, không ở worker sau khi task đã bắt đầu. **Restore trong finally** để không làm bẩn worker cho task tiếp theo.

**Tại sao không chỉ gọi MDC.clear trong worker?** Nếu worker đang chạy bên trong một nested context được framework quản lý, clear có thể phá context có sẵn. Lưu **previous** rồi restore giúp giữ trạng thái mà worker có trước task. Nếu kiến trúc bảo đảm worker luôn bắt đầu trống, previous sẽ null và finally dọn trống.

### 7.3. Snapshot là bản sao, không phải map chia sẻ

**MDC.getCopyOfContextMap()** trả về **bản sao** các entry tại thời điểm gọi hoặc null. Không dùng một shared mutable HashMap rồi để nhiều thread thay đổi đồng thời mà không có contract. Nếu context được cập nhật sau khi submit, task đã có snapshot có thể vẫn giữ phiên bản cũ; đó là hành vi phù hợp với thiết kế capture tại submit time.

### 7.4. CompletableFuture, scheduled task và virtual threads

Các API như **CompletableFuture.supplyAsync**, **ExecutorService**, scheduled pools và virtual threads có mô hình thực thi khác nhau nhưng đều không nên bị giả định tự mang MDC của caller:
- **CompletableFuture:** task có thể được chạy bởi ForkJoinPool hoặc executor tùy chọn; cần một context-aware executor/wrapper.
- **ScheduledExecutorService:** capture lúc schedule hay lúc chạy phải phù hợp ý nghĩa request/job; tránh giữ dữ liệu request quá lâu.
- **Virtual threads:** context gắn với một virtual thread không đồng nghĩa tự propagate qua các virtual thread khác; quản lý scope và propagation rõ ràng.
- **Reactive pipelines:** logical request có thể chuyển thread nhiều lần; ThreadLocal MDC thường cần tích hợp với reactor/coroutine context tương ứng.

**Không copy toàn bộ thông tin request hoặc security object vào MDC để truyền nghiệp vụ.** Context propagation cho trace/log fields khác với propagation security context và transaction state.

## 8. Đặt MDC ở đâu trong web application?

Trong HTTP application, vị trí thường là **middleware/filter/interceptor ở ranh giới request**, để requestId được đặt trước khi service/repository ghi log và được cleanup khi request kết thúc.

Mô hình:

~~~text
Incoming HTTP request
  |
  v
Request filter / interceptor
  |
  +--> Validate or generate requestId
  +--> MDC.put("requestId", requestId)
  |
  v
Controller -> Service -> Repository -> remote client
  |
  +--> tất cả sync logs trên thread phù hợp có requestId
  |
  v
finally -> MDC.remove("requestId") / restore previous
  |
  v
HTTP response
~~~

### 8.1. Pseudocode của một request boundary

~~~java
String previous = MDC.get("requestId");
String requestId = validateOrGenerateRequestId(incomingRequest);
MDC.put("requestId", requestId);
try {
    invokeNextHandler();
} finally {
    if (previous == null) MDC.remove("requestId");
    else MDC.put("requestId", previous);
}
~~~

Đây là **mã khái niệm**, không phải một Java class độc lập: cần định nghĩa incomingRequest, validateOrGenerateRequestId và invokeNextHandler theo framework. Điểm quan trọng là đặt context **trước** khi phần nghiệp vụ ghi log, và khôi phục đúng **sau** khi request hoàn tất trên thread đó.

### 8.2. Không tin tưởng request ID tùy ý từ client

Client có thể gửi request ID dài bất thường hoặc chứa newline/ký tự điều khiển. Trước khi đặt giá trị vào MDC:
- Kiểm tra format, chiều dài và charset cho phép.
- Ưu tiên correlation ID do gateway hoặc service đáng tin cậy tạo/xác thực.
- Không dùng một header tùy ý làm bằng chứng xác thực danh tính.
- Không nhận raw credential hoặc dữ liệu bí mật làm context key/value.

Ví dụ có thể dùng định dạng UUID hoặc một chuỗi ngắn chỉ gồm ký tự được phép, nhưng chính sách cụ thể tùy kiến trúc. Nếu client gửi ID không hợp lệ, tạo ID an toàn mới hoặc xử lý theo hợp đồng API.

### 8.3. Thread pool và Servlet async

Một servlet/request có thể chuyển sang async processing, callback hoặc executor. **MDC được đặt ở filter đồng bộ không tự đảm bảo tồn tại ở mọi task khác thread**. Framework có thể hỗ trợ context propagation riêng; nếu có, nên dùng phương án chính thức của framework thay vì tự viết nhiều lớp adapter trùng nhau.

Nếu filter cleanup trước khi async callback hoàn tất, callback cần context riêng được capture/restore; không giữ ThreadLocal MDC của request mãi trên container thread.

## 9. SLF4J MDC, Log4j2 ThreadContext và JUL

Các hệ logging có cách quản lý diagnostic context khác nhau.

### 9.1. SLF4J MDC

~~~java
import org.slf4j.MDC;

MDC.put("requestId", "req-42");
String id = MDC.get("requestId");
MDC.remove("requestId");
~~~

Đây là SLF4J facade API. Hành vi thực tế phụ thuộc **MDCAdapter** mà runtime provider cung cấp. Với Logback Classic trong ví dụ, data được đưa vào Logback PatternLayout.

### 9.2. Log4j2 ThreadContext

Khi dùng trực tiếp Log4j2 API:

~~~java
import org.apache.logging.log4j.ThreadContext;

ThreadContext.put("requestId", "req-42");
try {
    // Các logging calls của ngữ cảnh hiện tại.
} finally {
    ThreadContext.remove("requestId");
}
~~~

Log4j2 gọi map diagnostic context là **Thread Context Map**, đồng thời hỗ trợ **Thread Context Stack** cho nested context dạng NDC. Trong PatternLayout của Log4j2, **%X{requestId}** đọc một key tương ứng khi encoder/layout hỗ trợ.

Log4j2 có **CloseableThreadContext.put** để tạo scope tự đóng. **Một khác biệt đáng chú ý:** tài liệu Log4j2 mô tả **CloseableThreadContext.put** sẽ **khôi phục giá trị cũ** của key khi scope đóng, trong khi **SLF4J MDC.putCloseable** chỉ bảo đảm **remove key**. Không coi hai API có semantics nested scope giống hệt chỉ vì tên method gần nhau.

Ví dụ Log4j2:

~~~java
try (org.apache.logging.log4j.CloseableThreadContext.Instance ignored =
             org.apache.logging.log4j.CloseableThreadContext.put(
                     "requestId", "req-42")) {
    // Logging trong scope này có requestId khi Layout đọc ThreadContext.
}
~~~

Đây là đoạn minh họa, cần dependencies Log4j2 nếu muốn biên dịch; chương trình chạy hoàn chỉnh ở mục 6 chỉ dùng SLF4J và Logback.

### 9.3. JUL

**java.util.logging (JUL)** của JDK có Logger và LogRecord, nhưng **không có phương thức org.slf4j.MDC.put trong JUL Logger**. Khi dùng SLF4J với một provider/bridge hướng tới JUL, MDC behavior và field rendering phụ thuộc adapter/formatter thực tế; không mặc định JUL ConsoleHandler sẽ tự thêm requestId.

### 9.4. Bridge và multiple backends

Nếu ứng dụng dùng SLF4J facade với Log4j2 backend, MDC của SLF4J có thể được bridge/provider đồng bộ với ThreadContext theo hợp đồng của implementation. Nhưng nếu cài nhiều providers/bridges hoặc dùng không đúng chiều, giá trị có thể không được nhìn thấy tại Appender mong muốn.

**Không cài cả backend/providers chỉ để hy vọng MDC sẽ hoạt động.** Chọn một logging backend có hỗ trợ MDC, xác minh dependency graph, cấu hình Layout/Encoder và kiểm thử output.

## 10. MDC và async logging không giống context propagation

Hai khái niệm khác nhau:

1. **Application async task:** business logic chuyển thread, ví dụ executor hoặc CompletableFuture. Phải đưa MDC sang thread chạy task.
2. **Async logging backend:** logging event được phát ở application thread nhưng Appender/encoder xử lý ở background thread. Backend có trách nhiệm chụp thông tin context phù hợp khi tạo/queue event theo hợp đồng của implementation.

**MDC đặt trong worker của AsyncAppender không thay việc đặt context ở application thread.** Với các backend phổ biến, MDC có thể được snapshot vào event trước khi gửi queue; nhưng cần kiểm thử phiên bản/encoder thực tế, nhất là khi có custom LogEvent, layout hoặc adapter.

Nếu log event được phát **sau khi** scope đã được dọn, nó sẽ không tự có requestId chỉ vì task trước đã mang ID đó. Nếu event được phát **trong** scope nhưng appender xuất muộn, backend nên dùng context snapshot của event theo thiết kế. Tránh giả định dựa trên thứ tự dòng khi async queue và nhiều thread đồng thời.

### 10.1. Async error handling và mất dữ liệu

MDC chỉ giúp **gắn correlation context**. Nó không bảo đảm các bản ghi async đã được flush, retry, lưu trữ hoặc không bị drop. Nếu cần audit bền vững, phải có chính sách riêng về queue, sink, backpressure, shutdown và retention.

## 11. MDC trong structured logging và observability

Khi hệ thống có **traceId/spanId**, MDC thường được dùng để thêm các ID vào log events. Ví dụ message không cần tự nhắc lại trace ID:

~~~text
INFO trace=t-02 span=s-05 event=payment.authorized
~~~

Nếu backend xuất JSON, các giá trị này nên là fields rõ ràng, nhất quán với schema phân tích. Tuy nhiên:
- **Đặt traceId trong MDC không tạo span.**
- **MDC không tự propagate traceId qua HTTP, message queue hoặc giữa process.**
- **Một requestId không nhất thiết trùng traceId**.
- Tracing framework có thể có cơ chế tự chèn trace/span IDs vào logging context; tránh tự ghi đè với ID khác.
- Đừng lấy MDC làm nơi lưu OpenTelemetry Context hoặc security principal.

MDC giúp **log correlation**, còn distributed tracing yêu cầu instrumentation, context propagation và span lifecycle đúng.

### 11.1. Chọn key/value cho production

Những key có thể hữu ích, nếu policy cho phép:

| Key | Ví dụ | Lưu ý |
| --- | --- | --- |
| requestId | req-42 | Sinh/xác thực tại boundary |
| traceId | ID tracing hợp lệ | Giữ format tương thích tracing |
| spanId | ID span | Thường do tracing library quản lý |
| operation | checkout | Giá trị ổn định, không nhúng PII |
| jobId | job-108 | Dùng cho background job |
| tenant | tenant-code | Chỉ dùng ID an toàn được phép log |
| correlationId | corr-77 | Hợp đồng rõ giữa services |

**Không ghi** password, token, cookie, private key, OTP, toàn bộ body, raw authorization header hay PII không cần thiết. Nếu tenant/user identifiers có thể được coi là dữ liệu cá nhân hoặc nhạy cảm trong bối cảnh ứng dụng, phải theo policy truy cập/retention.

### 11.2. Cardinality: giữ ID để truy vấn, đừng tạo label vô hạn

requestId và traceId thường có cardinality rất cao. Đây là dữ liệu cần thiết để **lọc/drill-down** theo một request, nhưng không nên làm metric labels hoặc group-by dashboard tổng quan có hàng triệu buckets. Dashboard nên nhóm theo **service**, **operation**, **environment** và các dimension ổn định; request ID phục vụ điều tra cụ thể.

### 11.3. Số lượng key và chi phí

MDC map thường được copy/snapshot khi đổi thread hoặc tạo log event. Đặt hàng trăm key kích thước lớn làm tăng allocations, memory và kích thước output. Hãy giữ **ít field có giá trị chẩn đoán**, đặt ở thời điểm hợp lý và dọn đúng lúc.

## 12. Kiểm thử MDC

Một bộ test hữu ích cần kiểm tra **context lifecycle**, không chỉ có một lời gọi MDC.put.

### 12.1. Kiểm tra trực tiếp API

~~~java
MDC.clear();
MDC.put("requestId", "req-test");
if (!"req-test".equals(MDC.get("requestId"))) {
    throw new AssertionError("MDC requestId was not set");
}
MDC.remove("requestId");
if (MDC.get("requestId") != null) {
    throw new AssertionError("MDC requestId was not removed");
}
~~~

Đây là đoạn tích hợp trong method có SLF4J MDC; không phải chương trình standalone. Nó kiểm tra set/get/remove. Nếu provider không hỗ trợ MDC hoặc adapter hoạt động khác, test sẽ phát hiện cấu hình runtime không đúng kỳ vọng.

### 12.2. Kiểm tra scope

- Trước scope, operation không có.
- Trong putCloseable scope, operation=reserve.
- Sau scope, operation không còn.
- Khi nested scope có giá trị cũ, kiểm tra logic **save/restore** thay vì giả định putCloseable khôi phục.

### 12.3. Kiểm tra thread pool

Dùng một executor **một worker thread** rồi submit:
1. Task không truyền context: phải không thấy requestId của main thread.
2. Task có snapshot: phải thấy requestId mong đợi.
3. Task sau cleanup trên cùng worker: không được thấy requestId cũ.

Ba event này đã được minh họa bằng stdout thật của chương trình ở mục 6.

### 12.4. Kiểm tra formatted output

Một test chỉ kiểm tra **MDC.get** chưa đủ nếu mục tiêu là quan sát log ở console/collector. Còn phải xác minh:
- Backend/provider thật sự hỗ trợ MDC.
- Layout/encoder có xuất field.
- Formatter/JSON encoder bảo toàn Unicode và escaping.
- Null/missing values được hiển thị theo policy.
- Log event mang đúng context khi chuyển qua async backend.
- Request cleanup xảy ra cả trên đường exception.

### 12.5. Tránh các test gây nhiễm MDC lẫn nhau

JUnit có thể tái sử dụng thread giữa test cases hoặc chạy song song. Nếu test đặt MDC rồi không clear/restore, test khác có thể thất bại không ổn định. Trong mỗi test, dùng try/finally và khôi phục context ban đầu theo hợp đồng; không gọi MDC.clear ở một helper khi test framework có context khác đang dùng.

## 13. Lỗi thường gặp khi đặt giá trị MDC

### Lỗi 1 — Đặt MDC nhưng không thấy trên console

**Nguyên nhân:** Layout chỉ in message, không có **%X{requestId}**, hoặc backend/provider không hỗ trợ MDC như mong đợi.

**Kiểm tra:** MDC.get("requestId") trong đúng thread, runtime provider, Logback/Log4j layout và output thực tế.

### Lỗi 2 — Quên cleanup

**Nguyên nhân:** Đặt requestId rồi return hoặc ném exception mà không có finally.

**Hậu quả:** Thread pool tái sử dụng cùng thread cho request khác, log có thể mang correlation ID cũ.

**Cách sửa:** try/finally, putCloseable cho key thích hợp hoặc request filter quản lý lifecycle.

### Lỗi 3 — Gọi MDC.clear trong nested helper

**Nguyên nhân:** Helper chỉ sở hữu operation nhưng xóa cả traceId/requestId của caller.

**Cách sửa:** remove đúng key hoặc snapshot/restore map cũ nếu cần.

### Lỗi 4 — Cho rằng putCloseable khôi phục giá trị cũ

**Nguyên nhân:** Dùng putCloseable cho một key đã tồn tại và kỳ vọng close sẽ phục hồi key cũ.

**Cách sửa:** SLF4J MDCCloseable remove key; khi override nested scope cần lưu **previous** và restore thủ công.

### Lỗi 5 — Ghi đè requestId ở lớp sâu

**Nguyên nhân:** Service B tự tạo một requestId mới dù request đang có correlation ID của gateway.

**Cách sửa:** Chỉ tạo/xác thực tại boundary thích hợp; lớp sâu giữ correlation field hoặc đặt một field khác như operation/attemptId khi cần.

### Lỗi 6 — Truyền context sai thời điểm

**Nguyên nhân:** Gọi getCopyOfContextMap ở worker thay vì trước khi submit.

**Cách sửa:** Capture tại thread gửi task, trước thời điểm thực thi, rồi set/restore ở thread nhận.

### Lỗi 7 — Đặt MDC ở thread A và đọc ở thread B

**Nguyên nhân:** Giả định ThreadLocal tự kế thừa qua ExecutorService, CompletableFuture hoặc framework async.

**Cách sửa:** Dùng task decorator/context-aware executor hoặc cơ chế propagation chính thức.

### Lỗi 8 — Dùng MDC như một store dữ liệu nghiệp vụ

**Nguyên nhân:** Payment service lấy tenant từ MDC để quyết định dữ liệu được truy cập.

**Cách sửa:** Truyền security/business context rõ ràng; MDC chỉ phục vụ logging/diagnostics.

### Lỗi 9 — Dùng MDC.put(key, null) để xóa

**Nguyên nhân:** Giá trị null phụ thuộc implementation; không phải lệnh xóa portable.

**Cách sửa:** MDC.remove(key), hoặc restore giá trị cũ nếu scope lồng nhau.

### Lỗi 10 — Mismatch key trong code và layout

**Nguyên nhân:** Code đặt **requestId**, layout đọc **request_id**.

**Cách sửa:** Dùng một schema key thống nhất, test layout end-to-end.

### Lỗi 11 — Cài sai backend hoặc nhiều providers

**Nguyên nhân:** Source dùng SLF4J nhưng runtime thiếu provider hỗ trợ MDC hoặc xuất log qua backend khác.

**Cách sửa:** Kiểm tra dependency graph, chỉ chọn backend/provider phù hợp; đừng cài nhiều bridge ngược chiều.

### Lỗi 12 — Rò dữ liệu nhạy cảm

**Nguyên nhân:** Đặt session cookie, token, email hoặc raw URL query vào MDC, rồi encoder tự xuất map.

**Cách sửa:** Allowlist field, validate/normalize IDs, giới hạn kích thước, redaction và quyền truy cập phù hợp.

### Lỗi 13 — Dùng raw input làm một dòng log

**Nguyên nhân:** requestId chứa newline/ký tự điều khiển làm log text có thể bị giả mạo dòng mới.

**Cách sửa:** Validate ID, sử dụng encoder/escaping đúng chuẩn và không tin request header từ client nếu chưa kiểm tra.

### Lỗi 14 — Nhầm async Appender với async task

**Nguyên nhân:** Nghĩ backend async sẽ tự propagate MDC sang business executor.

**Cách sửa:** Chụp context tại task boundary; kiểm tra riêng thời điểm backend snapshot event.

## 14. Quy trình thực tế khi triển khai MDC

### Bước 1 — Định nghĩa contract

Chọn danh sách key và format cho **requestId**, **traceId**, **operation** và những fields thật sự cần. Viết rõ field nào được phép có trong log, field nào tuyệt đối không được có.

### Bước 2 — Chọn backend hỗ trợ MDC

Nếu dùng SLF4J, xác định provider runtime. Nếu dùng Logback, cấu hình **%X{key}** hoặc structured encoder. Nếu dùng Log4j2, có thể dùng **ThreadContext** hoặc provider SLF4J tương thích.

### Bước 3 — Đặt giá trị ở boundary

HTTP filter, message listener hoặc job runner tạo/xác thực ID và đặt MDC trước khi thực hiện các thao tác phát log bên trong.

### Bước 4 — Dọn ở đúng scope

Dùng try/finally hoặc cơ chế scope an toàn. Ở nested scope, khôi phục giá trị trước; ở request boundary sở hữu toàn bộ context, dọn theo policy.

### Bước 5 — Xử lý chuyển luồng

Xác định task nào chạy trên executor, callback, scheduler, virtual thread hoặc reactive pipeline. Dùng context-aware wrapper/framework support và kiểm thử propagation/cleanup.

### Bước 6 — Kiểm thử output

Phát log ở điểm bắt đầu, bên trong service, sau một scope được đóng, trong async task và sau cleanup. Kiểm tra không có ID sai/thiếu hoặc rò sang request khác.

### Bước 7 — Kiểm tra quan sát và bảo mật

Xác nhận log collector thấy fields trong schema, không chứa secret, retention phù hợp, không tăng mạnh log volume/cost và không tạo metric labels high-cardinality.

## 15. Bài tập

**Bài 1 — Put/Get/Remove.** Trong demo mục 6, thêm key **jobId=job-17**, dùng MDC.get kiểm tra trong scope, sau đó remove và xác minh output không còn jobId khi layout được bổ sung để in key này.

**Bài 2 — Ghi đè.** Đặt operation=checkout, tạm thời thay bằng operation=payment trong một block try/finally và khôi phục giá trị checkout. So sánh với putCloseable trên key đã tồn tại.

**Bài 3 — Thread pool.** Bỏ phần setContextMap(snapshot) trong task async; so sánh output trước/sau. Sau đó bỏ finally restore trong bản chạy test có kiểm soát và quan sát nguy cơ giá trị cũ xuất hiện ở task tiếp theo.

**Bài 4 — Request filter.** Viết một filter cho framework bạn sử dụng: validate request ID, đặt MDC, gọi chain, restore trong finally. Thử nhánh controller ném exception và kiểm tra cleanup.

**Bài 5 — Structured output.** Thay PatternLayout text bằng một JSON encoder được backend hỗ trợ. Kiểm tra requestId là field của event chứ không chỉ nằm trong message.

**Bài 6 — Context khi CompletableFuture.** Dùng một executor và submit CompletableFuture có/không có wrapper MDC. Kiểm tra correlation IDs khi task đổi thread.

**Bài 7 — Bảo vệ thông tin.** Giả sử request header chứa token và requestId có newline. Thiết kế chính sách allowlist/validation để log không chứa secret và không thể tạo dòng giả.

**Bài 8 — Test cách cleanup.** Viết test đặt requestId trong worker thread, chạy một task thứ hai trên cùng executor, assert MDC.get("requestId")==null sau restore. Không dùng thread name ngẫu nhiên làm điều kiện duy nhất.

## 16. Câu hỏi và đáp án

**1. MDC là gì?**  
Là map key–value chẩn đoán thường gắn với thread/context hiện hành để logging events có metadata dùng chung.

**2. MDC.put có tự xuất một dòng log không?**  
Không. Nó chỉ đặt context; Logger và Layout/Encoder mới tạo/hiển thị event.

**3. Đặt cùng key hai lần thì sao?**  
Giá trị mới ghi đè giá trị cũ trong map hiện hành.

**4. Khi nào dùng remove thay vì clear?**  
Khi chỉ muốn xóa key mình sở hữu, không phá context của caller.

**5. SLF4J MDC.putCloseable có tự restore giá trị cũ không?**  
Không hứa điều đó; nó remove key lúc close. Muốn nested override chính xác cần save/restore.

**6. Vì sao MDC.get("requestId") có thể trả null?**  
Key chưa được đặt, đã bị remove/clear, đang ở thread khác, hoặc MDCAdapter/backend không có dữ liệu đó.

**7. Vì sao LOG.info không hiển thị requestId dù MDC.get đã đúng?**  
Layout/encoder không đọc MDC field hoặc logging provider/output không đúng kỳ vọng.

**8. Thread pool có tự kế thừa MDC của thread submit không?**  
Không nên giả định. Capture snapshot ở caller rồi set/restore ở worker.

**9. Vì sao cần finally trong worker task?**  
Để giá trị của task không rò sang task tiếp theo trên cùng worker thread.

**10. MDC có thay thế distributed trace không?**  
Không. Nó hỗ trợ gắn traceId vào log, nhưng tracing cần instrumentation và context propagation qua các service.

**11. SLF4J MDC và Log4j2 CloseableThreadContext có cùng nested semantics không?**  
Không hoàn toàn. SLF4J MDCCloseable remove key; Log4j2 CloseableThreadContext.put có hợp đồng khôi phục giá trị cũ.

**12. Nên lưu dữ liệu gì vào MDC?**  
Chỉ những IDs/fields cần chẩn đoán, được phép lưu, kích thước nhỏ và có vòng đời rõ ràng.

**13. Có nên đặt token vào MDC rồi tắt DEBUG ở production?**  
Không. Backend/level có thể thay đổi và thông tin nhạy cảm có thể lọt vào logs.

**14. Vì sao requestId không nên là Logger name?**  
Vì Logger name nên ổn định theo class/package; correlation IDs thay đổi theo request và thuộc event context.

## 18. Kết luận

**Đặt giá trị MDC là một thao tác nhỏ nhưng có tác động lớn đến chất lượng điều tra log.** Khi gọi **MDC.put("requestId", ...)** tại ranh giới phù hợp và cấu hình layout đọc key đó, nhiều log events của cùng một request có thể mang correlation ID nhất quán mà không sửa từng message.

Ba quy tắc cần nhớ: **đặt đúng ngữ cảnh, dọn đúng scope và truyền context có chủ đích khi đổi thread**. Dùng **remove/clear** đúng trách nhiệm, tránh giả định putCloseable khôi phục key cũ, dùng **getCopyOfContextMap + setContextMap + finally restore** khi làm việc với ExecutorService, và không đưa dữ liệu nhạy cảm vào MDC. Ví dụ Java 17 đã kiểm chứng cho thấy chính xác sự khác nhau giữa logging trong main thread, worker không có context, worker có context được truyền và worker sau cleanup.
