# Kiểm thử MDC trong Java Logging: đúng request, đúng thread và không rò ngữ cảnh

## 1. Vì sao phải kiểm thử MDC?

**MDC (Mapped Diagnostic Context)** là cơ chế gắn các cặp khóa–giá trị chẩn đoán vào ngữ cảnh logging. Trong Java, mã ứng dụng thường sử dụng API `org.slf4j.MDC` để đưa `requestId`, `traceId`, `jobId` hoặc `operation` vào log. Backend như Logback có thể đưa các giá trị này vào từng sự kiện, hiển thị bằng `%X{requestId}` hoặc xuất thành JSON.

Ví dụ ứng dụng xử lý đồng thời hai request:

```text
INFO  requestId=req-A event=order.received
INFO  requestId=req-B event=order.received
WARN  requestId=req-A event=payment.retry
INFO  requestId=req-B event=order.completed
```

Nếu code quên thiết lập, truyền hoặc xóa MDC, các dòng log có thể mất ID hoặc mang **ID của request trước**. Đây không chỉ là lỗi dễ đọc log: nó có thể gây điều tra nhầm giao dịch, sai dashboard và rò thông tin giữa các request trên thread pool.

**Kiểm thử MDC** cần xác nhận cả **dữ liệu trong MDC** lẫn **dữ liệu thật đã được gắn vào logging event**. Một test chỉ gọi `MDC.put("requestId", "req-A")` rồi `assertEquals("req-A", MDC.get("requestId"))` chỉ chứng minh thao tác map trong một thread, **chưa chứng minh log thật có ID**.

Bài này tập trung vào các phép thử quan trọng:

1. MDC có đúng giá trị trong phạm vi xử lý.
2. Log event thực sự mang `requestId` mong đợi.
3. MDC được **khôi phục hoặc xóa** khi scope kết thúc bình thường.
4. MDC vẫn được dọn khi phương thức ném exception.
5. MDC **không tự truyền** sang task trên `ExecutorService`.
6. Khi chủ động truyền snapshot, worker có context đúng và không rò sang task kế tiếp.
7. Hai request chạy đồng thời không lấy nhầm context của nhau.
8. Layout/encoder thực sự xuất MDC ra format mong muốn.
9. Test không bị sai do thread scheduling, global logger configuration hoặc logging backend khác.

Bộ ví dụ hoàn chỉnh sử dụng **Java 17, SLF4J 2.x, Logback Classic, JUnit Jupiter 5 và Logback `ListAppender`**. Không cần mock static `MDC`: kiểm thử trên provider/backend thực giúp phát hiện lỗi mà một mock có thể che đi.

## 2. MDC khác tên thread và biến toàn cục

Hãy phân biệt:

| Khái niệm | Mục đích | Lưu ý khi test |
| --- | --- | --- |
| `requestId` | Liên kết log thuộc một request | Phải đúng qua các bước và được dọn sau request |
| `traceId` | Liên kết hoạt động trong distributed trace | Cần propagation qua process/network, MDC chỉ hỗ trợ xuất log |
| `spanId` | Xác định span hiện tại | Có thể đổi khi bước xử lý/span đổi |
| `jobId` | Liên kết log của background job | Không nhất thiết có HTTP request |
| Thread name | Thread phát event tại thời điểm đó | Thread pool tái sử dụng thread cho nhiều request |
| Logger name | Nguồn log ổn định theo package/class | Không dùng tên Logger chứa ID động |
| MDC map | Tập key–value chẩn đoán gắn với thread hiện tại | Không phải global map dùng chung mọi thread |
| Logging event | Bản ghi log đã được tạo | Cần có snapshot context tại lúc phát log |

**Một thread có thể phục vụ nhiều request; một request có thể đi qua nhiều thread.** Do đó, khẳng định `Thread.currentThread().getName()` đúng không đủ để chứng minh `requestId` đúng.

SLF4J là facade, còn việc lưu và xuất MDC phụ thuộc **MDC adapter/provider** đang hoạt động. Với Logback, MDC có thể được lấy từ event bằng `ILoggingEvent.getMDCPropertyMap()`. Một backend/provider không hỗ trợ MDC như bạn kỳ vọng có thể khiến test in log bình thường nhưng không có context.

### 2.1. Các API MDC cần hiểu

| API | Ngữ nghĩa chính | Điều cần kiểm tra |
| --- | --- | --- |
| `MDC.put(key, value)` | Ghi một entry cho thread hiện tại | Key/value đúng và chỉ có ở scope cần thiết |
| `MDC.get(key)` | Lấy giá trị theo key trong thread hiện tại | Không nhầm với context của task khác |
| `MDC.remove(key)` | Xóa một entry của thread hiện tại | Không để entry cũ sang request sau |
| `MDC.clear()` | Xóa toàn bộ context map của thread hiện tại | Không xóa nhầm context của scope bên ngoài |
| `MDC.getCopyOfContextMap()` | Lấy bản sao map hiện tại, có thể là `null` | Capture ở thread gọi **trước khi submit** |
| `MDC.setContextMap(map)` | Thay map thread hiện tại bằng bản sao map truyền vào | Phải lưu/khôi phục map cũ trong `finally` |
| `MDC.putCloseable(key,value)` | Scope tiện dụng tự remove key khi đóng | Không mặc định khôi phục giá trị cũ cùng key |
| `ILoggingEvent.getMDCPropertyMap()` | Map MDC gắn với một Logback logging event | Kiểm tra event thực tế thay vì chỉ kiểm tra `MDC.get` |

**Lưu ý phiên bản:** từ SLF4J 2.0, `MDC.setContextMap(null)` được API hỗ trợ; để mã ví dụ dễ đọc và tường minh, ta dùng `MDC.clear()` khi snapshot là `null`. MDC map truyền qua API có key và value kiểu `String`.

## 3. Chiến lược kiểm thử: ba lớp kiểm tra

Một bộ test có ích nên kiểm tra ở ba mức.

### 3.1. Unit test: ngữ nghĩa của scope MDC

Kiểm tra:

- `MDC.put` gắn đúng key/value.
- Sau khi hàm xử lý kết thúc, MDC không còn request ID cũ.
- Nếu trước đó có `requestId=req-parent`, một scope lồng nhau tạm đặt `req-child` phải khôi phục `req-parent` khi đóng.
- Scope không xóa nhầm các key khác như `traceId` hoặc `jobId`.
- Khi ném exception, `finally` hoặc `AutoCloseable.close()` vẫn dọn context.
- Input không hợp lệ không được biến thành context động ngoài dự kiến.

Loại test này nhanh và hữu ích, nhưng vẫn cần kiểm tra **event thực tế**.

### 3.2. Integration test: event được Logback thu nhận

Gắn một `ListAppender<ILoggingEvent>` vào Logger dành riêng cho test, phát log thật rồi kiểm tra:

- Số event: không mất, không trùng.
- `getLevel()`: đúng INFO/WARN/ERROR.
- `getFormattedMessage()`: tham số `{}` đã được thay.
- `getLoggerName()`: tên Logger đúng.
- `getMDCPropertyMap().get("requestId")`: ID gắn với **event** đúng.
- `getThrowableProxy()`: chứa Throwable khi phát log lỗi.

Ưu tiên **assert trên ILoggingEvent**, tránh chỉ bắt `System.out` hoặc tìm một chuỗi trong cả stdout. Capture stdout toàn JVM dễ bị nhiễu bởi Gradle, framework, log của test khác hoặc thay đổi encoder.

### 3.3. Integration/end-to-end: output ở collector có đúng không?

Kiểm tra `ListAppender` chưa đảm bảo file JSON, console pattern hoặc collector xuất đúng field. Với một bài test integration riêng, có thể gắn `PatternLayout` hoặc `OutputStreamAppender`, kiểm tra `%X{requestId}` xuất vào output, hoặc parse JSON Lines và assert trường MDC.

Trong hệ thống web, có thể gửi request qua test HTTP client, lấy ID, sau đó kiểm tra event được thu tại appender/collector. Nhưng các phép thử dựa vào agent/network thật chậm và không ổn định; giữ phần unit/integration cục bộ nhanh, chạy end-to-end ở tầng kiểm thử phù hợp.

## 4. Ma trận các tình huống nên test

| Tình huống | Điều cần chứng minh | Chống lỗi nào? |
| --- | --- | --- |
| Một request bình thường | Event có ID đúng, sau xử lý MDC được dọn | Thiếu context |
| Scope lồng nhau | Event lấy ID scope trong, sau đó khôi phục scope ngoài | Ghi đè hoặc xóa nhầm context |
| Xử lý ném exception | Log lỗi có ID, MDC vẫn được dọn trong `finally` | Rò ID khi exception |
| Không thiết lập MDC | Event không chứa `requestId` giả | ID cũ lọt sang request khác |
| Task executor không bọc | Worker không mặc nhiên có MDC của caller | Hiểu sai ThreadLocal |
| Task executor có snapshot | Event từ worker có ID đúng của caller | Mất context khi async |
| Task kế tiếp dùng lại worker | ID task trước không còn trên worker | Context leak trong thread pool |
| Task async ném exception | Sau failure, worker vẫn sạch | Cleanup bỏ sót exception |
| Hai request đồng thời | A chỉ mang ID A, B chỉ mang ID B | Race và cross-request contamination |
| PatternLayout/JSON encoder | Output có field `requestId` đúng | Event đúng nhưng encoder không hiển thị |
| Provider sai hoặc thiếu | Test phát hiện MDC adapter/backend không hoạt động | False positive do mock hoặc NOP |
| Khởi động lại/test lặp | Kết quả giống nhau, không phụ thuộc test order | Shared state gây flaky test |

**Không so sánh thứ tự toàn cục của log khi hai thread chạy song song.** Hãy so event theo `event name`/ID và đối chiếu tập hoặc map; dùng `Future.get`/`CountDownLatch` để đồng bộ thay vì `Thread.sleep`.

## 5. Dự án Java 17 hoàn chỉnh: SLF4J + Logback + JUnit

Ví dụ sau gồm một lớp nghiệp vụ có scope MDC an toàn và **9 phép thử JUnit**. Các test kiểm tra logging event thật bằng Logback `ListAppender`; một test riêng kiểm tra `PatternLayout` có xuất MDC.

Chúng ta dùng các phiên bản **được ghim để có thể tái lập bài học**, không khẳng định phiên bản mới nhất: Java 17, SLF4J API 2.0.17, Logback Classic 1.5.18 và JUnit Jupiter 5.11.4. Dự án thực tế cần quản lý phụ thuộc theo BOM/starter và cập nhật các bản sửa lỗi bảo mật tương thích.

```xml

```

Cấu hình root tắt log không liên quan trong test. Lớp test sẽ đặt **Logger chuyên dụng** thành INFO và gắn `ListAppender` trực tiếp vào Logger đó. Vì vậy root OFF **không chặn** event tại Logger test có level riêng. Logger test cũng được đặt `additivity=false` để event không tiếp tục đến root.

Không dùng file cấu hình production đầy Appender trong suite kiểm thử này: như vậy log có thể bị ghi file/console ngoài ý muốn hoặc tạo record trùng. `logback-test.xml` trên test runtime classpath được Logback ưu tiên theo quy tắc tìm cấu hình thông thường.

### 5.5. File `src/main/java/demo/RequestWorker.java`

```java
package demo;

import java.util.Map;
import java.util.Objects;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class RequestWorker {
    public static final String LOGGER_NAME = "demo.mdc.verify";

    private static final Logger LOG =
            LoggerFactory.getLogger(LOGGER_NAME);

    private RequestWorker() {
    }

    public static void processOrder(String requestId, String orderId) {
        try (MdcScope ignored = new MdcScope(requestId)) {
            LOG.info("event=order.accepted orderId={}", orderId);
        }
    }

    public static void processFailure(String requestId) {
        try (MdcScope ignored = new MdcScope(requestId)) {
            IllegalStateException error =
                    new IllegalStateException("simulated failure");
            LOG.error("event=order.failed", error);
            throw error;
        }
    }

    public static void logWorker(String message) {
        LOG.info(message);
    }

    // Gọi từ thread submit để chụp context của caller.
    public static Runnable captureMdc(Runnable task) {
        Objects.requireNonNull(task, "task");
        Map<String, String> captured = MDC.getCopyOfContextMap();

        return () -> {
            Map<String, String> previous =
                    MDC.getCopyOfContextMap();
            try {
                if (captured == null) {
                    MDC.clear();
                } else {
                    MDC.setContextMap(captured);
                }
                task.run();
            } finally {
                restore(previous);
            }
        };
    }

    private static void restore(Map<String, String> snapshot) {
        if (snapshot == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(snapshot);
        }
    }

    private static final class MdcScope implements AutoCloseable {
        private final Map<String, String> previous;

        private MdcScope(String requestId) {
            Objects.requireNonNull(requestId, "requestId");
            previous = MDC.getCopyOfContextMap();
            MDC.put("requestId", requestId);
        }

        @Override
        public void close() {
            restore(previous);
        }
    }
}
```

**Giải thích mã nghiệp vụ:**

- `MdcScope` chụp **toàn bộ map trước khi scope bắt đầu**, thay requestId tạm thời và khôi phục map cũ khi đóng. Scope lồng nhau giữ được `traceId` cùng các key khác.
- `try-with-resources` gọi `close()` kể cả khi xử lý ném exception, tránh rò MDC sang công việc tiếp theo trên cùng thread.
- `captureMdc` phải được gọi ở **thread nguồn trước khi submit task**; nó giữ một snapshot của MDC để cài vào worker.
- Worker lưu context có sẵn của chính worker, cài snapshot, chạy task và restore trong `finally`. Điều này hỗ trợ các wrapper lồng nhau; nó không giả định worker luôn rỗng trước task.
- `MDC.clear()` được gọi nếu không có snapshot; nếu có snapshot, `setContextMap` thay toàn bộ map.
- `LOGGER_NAME` cố định theo subsystem, không gắn từng request ID vào tên Logger.
- Code source chỉ import SLF4J; backend Logback nằm trong test configuration.

**Giới hạn:** `captureMdc` chỉ mang dữ liệu MDC dành cho logging. Nó không tự truyền security context, span thực của distributed tracing, transaction hay mọi ThreadLocal khác. Framework có thể có cơ chế context propagation phù hợp hơn.

### 5.6. File `src/test/java/demo/MdcLoggingTest.java`

```java
package demo;

import static org.junit.jupiter.api.Assertions.*;

import ch.qos.logback.classic.Level;
import ch.qos.logback.classic.Logger;
import ch.qos.logback.classic.PatternLayout;
import ch.qos.logback.classic.spi.ILoggingEvent;
import ch.qos.logback.core.read.ListAppender;
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.parallel.Execution;
import org.junit.jupiter.api.parallel.ExecutionMode;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

@Execution(ExecutionMode.SAME_THREAD)
final class MdcLoggingTest {
    private Logger logger;
    private Level oldLevel;
    private boolean oldAdditivity;
    private ListAppender<ILoggingEvent> capture;

    @BeforeEach
    void attachCapture() {
        // Không để MDC của test trước ảnh hưởng test hiện tại.
        MDC.clear();

        logger = (Logger) LoggerFactory.getLogger(
                RequestWorker.LOGGER_NAME);
        oldLevel = logger.getLevel();
        oldAdditivity = logger.isAdditive();

        logger.setLevel(Level.INFO);
        logger.setAdditive(false);

        capture = new ListAppender<>() {
            @Override
            protected synchronized void append(ILoggingEvent event) {
                // Chụp data trên thread phát log, trước MDC cleanup.
                event.prepareForDeferredProcessing();
                super.append(event);
            }
        };

        capture.setContext(logger.getLoggerContext());
        capture.setName("TEST_CAPTURE");
        capture.start();
        logger.addAppender(capture);
    }

    @AfterEach
    void detachCapture() {
        if (logger != null && capture != null) {
            logger.detachAppender(capture);
            capture.stop();
            logger.setLevel(oldLevel);
            logger.setAdditive(oldAdditivity);
        }
        MDC.clear();
    }

    private ILoggingEvent oneEvent() {
        assertEquals(1, capture.list.size());
        return capture.list.get(0);
    }

    @Test
    void eventContainsRequestIdAndFormattedMessage() {
        RequestWorker.processOrder("req-01", "ord-17");

        assertNull(MDC.get("requestId"));

        ILoggingEvent event = oneEvent();
        assertEquals(Level.INFO, event.getLevel());
        assertEquals(RequestWorker.LOGGER_NAME,
                event.getLoggerName());
        assertEquals("event=order.accepted orderId=ord-17",
                event.getFormattedMessage());
        assertEquals("req-01",
                event.getMDCPropertyMap().get("requestId"));
    }

    @Test
    void nestedScopeRestoresOuterContext() {
        MDC.put("requestId", "req-outer");
        MDC.put("traceId", "trace-42");

        RequestWorker.processOrder("req-inner", "ord-2");

        assertEquals("req-outer", MDC.get("requestId"));
        assertEquals("trace-42", MDC.get("traceId"));

        ILoggingEvent event = oneEvent();
        assertEquals("req-inner",
                event.getMDCPropertyMap().get("requestId"));
        assertEquals("trace-42",
                event.getMDCPropertyMap().get("traceId"));
    }

    @Test
    void failureStillRestoresContextAndRecordsThrowable() {
        IllegalStateException failure = assertThrows(
                IllegalStateException.class,
                () -> RequestWorker.processFailure("req-fail"));

        assertEquals("simulated failure", failure.getMessage());
        assertNull(MDC.get("requestId"));

        ILoggingEvent event = oneEvent();
        assertEquals(Level.ERROR, event.getLevel());
        assertEquals("req-fail",
                event.getMDCPropertyMap().get("requestId"));
        assertNotNull(event.getThrowableProxy());
    }

    @Test
    void eventWithoutContextDoesNotInventRequestId() {
        RequestWorker.logWorker("event=no.context");

        assertFalse(oneEvent().getMDCPropertyMap()
                .containsKey("requestId"));
    }

    @Test
    void rawExecutorTaskDoesNotInheritCallerMdc() throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();
        try {
            MDC.put("requestId", "req-caller");

            Future<String> result = executor.submit(() -> {
                RequestWorker.logWorker("event=async.raw");
                return MDC.get("requestId");
            });

            assertNull(result.get(5, TimeUnit.SECONDS));
            assertFalse(oneEvent().getMDCPropertyMap()
                    .containsKey("requestId"));
        } finally {
            executor.shutdownNow();
        }
    }

    @Test
    void snapshotPropagatesThenWorkerIsClean() throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();
        try {
            MDC.put("requestId", "req-async");

            Runnable wrapped = RequestWorker.captureMdc(() ->
                    RequestWorker.logWorker("event=async.wrapped"));
            MDC.clear();

            executor.submit(wrapped).get(5, TimeUnit.SECONDS);
            executor.submit(() ->
                    RequestWorker.logWorker("event=async.after"))
                    .get(5, TimeUnit.SECONDS);

            assertEquals(2, capture.list.size());
            assertEquals("req-async",
                    capture.list.get(0)
                            .getMDCPropertyMap().get("requestId"));

    @Test
```

### 5.7. Tại sao test Appender có `prepareForDeferredProcessing()`?

Đây là chi tiết kỹ thuật rất quan trọng khi kiểm thử **MDC trong event**.

Trong Logback, một `ILoggingEvent` có thể **lấy dữ liệu MDC theo cách trì hoãn** khi `getMDCPropertyMap()` lần đầu được gọi. `ListAppender` thông thường chỉ giữ tham chiếu tới event. Nếu test:

1. Phát log trong lúc MDC có `requestId=req-A`.
2. Scope kết thúc và MDC được xóa.
3. Sau đó test mới gọi `event.getMDCPropertyMap()`.

thì một số tình huống có thể khiến test lấy snapshot **quá muộn**, phản ánh context đã bị dọn, thay vì context đúng lúc event được phát.

Trong bộ test, `ListAppender` được tùy chỉnh để gọi:

```java
event.prepareForDeferredProcessing();
```

**Ngay trong `append` trên thread phát event**, trước khi scope bị dọn. Lời gọi này chuẩn bị thông tin cho deferred processing, gồm message và MDC theo cơ chế Logback. Vì vậy test đo đúng **event đã phát**, không đọc lại context thread ở một thời điểm khác.

`protected synchronized void append(...)` còn bảo đảm phần cập nhật `ListAppender.list` diễn ra tuần tự khi hai worker cùng log. Phải đọc danh sách **sau khi các `Future` hoàn tất**; không đọc `ArrayList` đang bị worker cập nhật nếu không có đồng bộ.

**Điểm phân biệt:** test này không mock logging. Nó dùng Logger và MDC thật, Logback backend thật và event thật. Tuy nhiên nó vẫn là **test nội bộ ứng dụng**, chưa chứng minh collector production đã nhận event.

### 6.1. Tám kết luận quan trọng của chín test

1. **MDC gắn vào event:** test đầu xác nhận `requestId=req-01` vẫn có trên event sau khi scope đã đóng.
2. **Scope lồng nhau:** ID trong event là `req-inner` nhưng thread gọi được khôi phục về `req-outer`.
3. **Exception cleanup:** lỗi được ném ra nhưng `requestId` không rò và event ERROR có Throwable.
4. **Không có context thì không tự tạo ID:** test negative bảo vệ khỏi false positive.
5. **Executor không kế thừa MDC của caller một cách mặc định:** worker raw không có `req-caller`.
6. **Snapshot propagation:** wrapper chuyển `req-async` sang worker; task kế tiếp không mang ID này.
7. **Task async thất bại:** cleanup vẫn chạy trong `finally`, không mang `req-error` sang task kế tiếp.
8. **Pattern output:** `%X{requestId}` thật sự biến thành `requestId=req-layout` trên text.
9. **Hai request song song:** A và B được so **theo message → requestId**, không dựa thứ tự thread.

Điểm mạnh của suite là kiểm chứng cả **trạng thái MDC** và **ảnh chụp sự kiện logging**; điểm giới hạn là test này chưa đo được collector hay tracing headers giữa các process.

## 7. Test qua `PatternLayout`, `OutputStreamAppender` và JSON encoder

`ListAppender` chứng minh event có MDC; `PatternLayout` chứng minh layout text sử dụng MDC. Trong production, output còn đi qua Appender/Encoder, có thể thay đổi hoặc lọc field.

### 7.1. PatternLayout test

Một pattern điển hình:

```text
%d{yyyy-MM-dd HH:mm:ss.SSS,UTC} %-5level [%thread] %logger{36} requestId=%X{requestId} - %msg%n
```

Ở unit test, tránh so toàn bộ timestamp/thread biến thiên. Chọn pattern đơn giản như trong test:

```text
requestId=%X{requestId} level=%level - %msg
```

và assert chính xác chuỗi. Khi cần thử format production, tạo `PatternLayout`/`PatternLayoutEncoder` với đúng pattern dùng khi deploy rồi kiểm tra **các field bắt buộc**, timezone và cách escape riêng, thay vì so một timestamp hardcoded.

### 7.2. OutputStreamAppender test

Nếu mục tiêu là bytes cuối cùng, có thể dùng `OutputStreamAppender<ILoggingEvent>` và `ByteArrayOutputStream` trong một integration test riêng:

1. Tạo `PatternLayoutEncoder`, đặt `LoggerContext` và pattern có `%X{requestId}`.
2. Tạo `OutputStreamAppender`, gắn encoder và output stream.
3. Start encoder/appender rồi gắn vào Logger test.
4. Phát log trong một MDC scope.
5. Chuyển byte sang UTF-8 và assert dòng output.
6. Tháo Appender, stop và khôi phục Logger trong `finally`.

Đây là **quy trình**, không phải chương trình hoàn chỉnh. `ByteArrayOutputStream` phải thuộc test riêng để không thay đổi cấu hình chính của chín test trên; không đồng thời gắn hai Appender cùng output khi không muốn log trùng.

### 7.3. JSON encoder

Nếu dùng JSON Lines, cần parse mỗi dòng bằng JSON parser chuẩn rồi assert trường MDC, ví dụ:

```json
{
  "level": "INFO",
  "message": "event=order.accepted",
  "mdc": {
    "requestId": "req-42"
  }
}
```

Đây là **JSON minh họa**, không phải schema mặc định của mọi encoder. Logback JsonEncoder gốc, LogstashEncoder hoặc encoder của framework có **tên field và cấu trúc khác nhau**; test phải theo **schema thực tế**. Kiểm tra đúng kiểu dữ liệu, JSON escaping và một event trên một physical line.

Không chỉ kiểm tra chuỗi có `req-42`: ID có thể vô tình xuất trong `message` nhưng không hề tồn tại trong field MDC mà collector/dashboard sử dụng.

## 8. Kiểm thử concurrency: tránh flaky test

Các phép thử logging dễ bị sai vì tranh chấp global state.

### 8.1. Đừng dùng `Thread.sleep` làm công cụ đồng bộ

Code kiểu:

```java
executor.submit(() -> logger.info("event=async"));
Thread.sleep(100);
assertEquals(1, captured.size());
```

Đây là **anti-pattern minh họa**: sau 100ms, worker có thể chưa được schedule trên CI đang tải nặng. Test sẽ chập chờn dù ứng dụng đúng.

Hãy dùng `Future.get(timeout, unit)` để biết task đã hoàn tất; dùng `CountDownLatch`/`CyclicBarrier` khi cần phối hợp các thread. Đặt timeout để một test lỗi **thất bại rõ ràng** thay vì treo vô hạn.

### 8.2. Không assert thứ tự giữa hai thread độc lập

Trong test song song:

```text
A: event=order.accepted orderId=A
B: event=order.accepted orderId=B
```

Hệ thống không bảo đảm A hay B xuất trước. So `Map<message,requestId>` hoặc `Set` thay vì `capture.list.get(0)` là A và `capture.list.get(1)` là B. Trong suite ví dụ, việc lặp qua danh sách chỉ diễn ra **sau khi cả hai Future hoàn tất**.

### 8.3. ListAppender và shared Logger phải được cô lập

Logback `Logger` thường được dùng chung trong một `LoggerContext`. Nếu các test đồng thời thay level, additivity hoặc gắn/dỡ cùng Appender lên cùng Logger, chúng có thể ảnh hưởng lẫn nhau.

Ví dụ áp dụng:

- Logger có tên riêng cho suite: `demo.mdc.verify`.
- `@BeforeEach` lưu level/additivity, gắn test Appender.
- `@AfterEach` tháo/stop Appender, khôi phục trạng thái Logger và `MDC.clear()`.
- `@Execution(SAME_THREAD)` không chạy song song các test **trong lớp** dùng Logger chung.
- Mỗi test tạo executor riêng và shutdown trong `finally`.
- Khi test muốn chạy song song ở cấp suite giữa nhiều lớp, phải dùng tên Logger/LoggerContext riêng hoặc cơ chế cô lập phù hợp; annotation của một lớp không bảo đảm toàn bộ code khác không tác động Logger của nó.

### 8.4. Đừng giả định `ListAppender.list` là thread-safe

`ListAppender` dùng danh sách nội bộ, không nên để nhiều worker ghi đồng thời vào nó một cách không kiểm soát. Ví dụ đã override `append` với `synchronized` và gọi `prepareForDeferredProcessing` ngay tại worker. Việc đọc danh sách sau `Future.get` bảo đảm các task đã xong, tránh đọc khi còn đang ghi.

Trong hệ thống cần capture số lượng event lớn hoặc test chạy concurrent cao, có thể viết một Appender test riêng sử dụng cấu trúc concurrency thích hợp, thay vì áp dụng `ListAppender` ngoài phạm vi nó được thiết kế.

## 9. Test propagation qua thread pool, CompletableFuture và framework

### 9.1. ExecutorService

Chu trình đúng:

```text
Thread request:
  MDC.put("requestId","req-A")
  snapshot = MDC.getCopyOfContextMap()
  submit(wrapped task)

Thread worker:
  previous = MDC.getCopyOfContextMap()
  install snapshot (MDC.setContextMap hoặc MDC.clear)
  tạo log event
  finally: restore previous
```

**Capture phải được gọi ở thread submit.** Nếu gọi `MDC.getCopyOfContextMap()` lần đầu bên trong worker, bạn lấy context của worker, không phải của request. Vì thế test raw và test wrapped có ý nghĩa đối lập.

### 9.2. CompletableFuture

`CompletableFuture.supplyAsync`, `runAsync`, `thenApplyAsync` có thể chạy trên các thread khác nhau. Test phải bao phủ **mỗi ranh giới chuyển thread**, không chỉ bước async đầu tiên.

Ví dụ **mảnh code**:

```java
Runnable wrapped = RequestWorker.captureMdc(() ->
        RequestWorker.logWorker("event=async.stage"));

CompletableFuture<Void> future =
        CompletableFuture.runAsync(wrapped, executor);

future.join();
```

Mảnh trên giả sử `executor` đã có và import `CompletableFuture`; nó không phải lớp độc lập. `join` bảo đảm task xong nhưng không tự truyền MDC. Chính `captureMdc` của helper đảm nhận phần đó. Nếu có stage tiếp theo trên executor khác, cần wrap tiếp hoặc dùng cơ chế propagation xuyên pipeline.

### 9.3. Spring MVC / servlet filter

Khi ứng dụng có `OncePerRequestFilter` hoặc interceptor đặt MDC ở đầu request, integration test nên:

1. Gửi request có hoặc không có correlation header hợp lệ.
2. Xác nhận filter tạo/kiểm tra ID trước khi service phát log.
3. Kiểm tra log event có đúng ID của request.
4. Gửi request kế tiếp trên cơ chế thread tái sử dụng và xác nhận không mang ID trước.
5. Gây exception hoặc gửi response lỗi để kiểm tra `finally`.
6. Nếu dùng async dispatch, xác minh propagation và cleanup trên đúng lifecycle mà framework hỗ trợ.

Không mặc định `@WebMvcTest` hay mock HTTP server luôn tạo hoàn cảnh thread pool giống production; các trường hợp async có thể cần integration test với executor/filter thực.

### 9.4. Reactive và messaging

Với Reactor, callback có thể chuyển thread và **Reactor Context** không đồng nghĩa ThreadLocal MDC. Test phải dùng context propagation của stack reactive/tracing. Với Kafka/RabbitMQ, cần tạo context **theo từng message** và cleanup trước message tiếp theo, nhất là khi consumer thread được tái sử dụng.

Một test chỉ đặt MDC trên thread gọi rồi gửi message không chứng minh context tự có trong consumer ở process khác. Context xuyên process phải được đưa qua **headers/metadata** và được phía nhận xác thực/khôi phục phù hợp.

## 10. Kiểm thử MDC cùng logging output bất đồng bộ

Có hai loại async khác nhau:

1. **Async nghiệp vụ:** request chuyển từ thread A sang business worker B. Phải truyền MDC **trước khi worker B phát log**.
2. **Async logging:** event đã tạo ở B, nhưng một `AsyncAppender` đưa việc encode/ghi sang thread C. MDC cần được **chụp vào event khi tạo**, không đọc lại MDC của thread C.

```text
Request A (MDC req-42)
    |
    | propagate snapshot
    v
Business worker B (MDC req-42)
    |
    | logger.info -> event chứa context req-42
    v
AsyncAppender worker C
    |
    | encode event (không đọc ThreadLocal của C)
    v
stdout / file / collector
```

Nếu thiếu propagation A→B, `AsyncAppender` không thể đoán ID đã mất. Ngược lại, nếu custom encoder đọc `MDC.get("requestId")` bên trong thread C thay vì event MDC map, nó có thể xuất ID sai hoặc rỗng.

### 10.1. Test nên kiểm tra hai tầng

- **Business propagation:** event do worker B phát có `getMDCPropertyMap().get("requestId") == req-42`.
- **Output snapshot:** sau khi worker B clear MDC, bản ghi đã xếp hàng vẫn xuất `req-42` ở formatter/encoder của thread C.

Muốn kiểm tra đường async thật, dùng một Appender/queue có cơ chế chờ drain, timeout rõ và assert output sau khi flush/shutdown bình thường. Không dùng `Thread.sleep` như một bảo đảm “queue đã rỗng”.

### 10.2. Không dùng logging để kiểm thử quyền truy cập

`MDC.get("tenantId")` có thể chứa chuỗi bất kỳ và chỉ dành cho chẩn đoán. Test security authorization không được dựa vào MDC như một nguồn xác thực. Khi cần context bảo mật, hãy dùng cơ chế security context riêng với propagation/lifecycle có bảo đảm phù hợp.

## 11. Negative tests quan trọng

Một suite kiểm thử tốt không chỉ chứng minh đường thành công.

### 11.1. Khi thiếu provider hỗ trợ MDC

Nếu runtime chỉ có `slf4j-api` mà không có backend phù hợp, logging có thể dùng NOP fallback. Nếu dùng một provider có `NOPMDCAdapter`, việc `MDC.put` có thể không lưu context hữu ích. Test nên fail rõ khi `ILoggingEvent` không xuất hiện hoặc không chứa field mong đợi.

Không mock `MDC.get` để luôn trả `req-42` rồi kết luận integration thành công. Mục tiêu ở đây là xác minh **backend thật và event thật**.

### 11.2. Key bị ghi sai tên hoặc dùng sai scope

Ví dụ producer đặt `MDC.put("requestID", "...")` nhưng encoder đọc `%X{requestId}`: key khác nhau và output bị thiếu. Test nên assert **đúng tên field** trong event và trong format.

Scope lồng nhau có thể ghi đè `requestId` cũ. Nếu code chỉ `MDC.remove("requestId")` lúc đóng mà không khôi phục giá trị trước, context ngoài sẽ mất. Test `nestedScopeRestoresOuterContext` phát hiện lỗi này.

### 11.3. Worker vẫn có context cũ

Khi thread pool tái sử dụng một worker, một task thất bại có thể để lại `requestId` nếu không có `finally`. Test gửi task tiếp theo trên **cùng single-thread executor** và assert event sau không có request ID. Đây là phép thử phát hiện leak mạnh hơn chỉ assert `MDC.get(...)` ở thread main.

### 11.4. Missing ID và input không tin cậy

Khi header `X-Request-ID` thiếu hoặc không hợp lệ, ứng dụng có thể tạo ID mới theo policy. Test nên xác minh không bao giờ dùng giá trị rỗng, quá dài, chứa newline hoặc path fragment nguy hiểm vào log context mà không kiểm tra.

Để tránh log injection, có thể thử request ID chứa xuống dòng hoặc ký tự điều khiển và xác minh middleware từ chối/sanitize trước khi `MDC.put`; riêng backend JSON escape không thay thế việc xác thực ID.

### 11.5. Thứ tự/timeout gây flaky trên CI

Kiểm thử song song cần có các điều kiện chờ rõ, không dùng timestamp hoặc số mili-giây giả định. Với test rất nhạy cảm tài nguyên, hãy kiểm tra timeout, loại bỏ side effect không cần thiết và đảm bảo executor shutdown.

## 12. Bảo mật và dữ liệu nhạy cảm trong MDC

MDC không phải nơi chứa tất cả dữ liệu request. Một snapshot `MDC.getCopyOfContextMap()` sẽ giữ lại mọi key được đặt trên thread gọi; nếu trong đó có token/cookie/PII thì task và log có thể mang theo dữ liệu không được phép.

Nguyên tắc:

- **Allowlist field** phục vụ chẩn đoán: `requestId`, `traceId`, `spanId`, `operation`, `errorCode`, `jobId` khi cần.
- Không đưa password, bearer token, cookie, khóa bí mật hoặc nội dung thanh toán nhạy cảm vào MDC.
- Xác minh/giới hạn `requestId` do client gửi; không tin giá trị chỉ vì nó có trong MDC.
- Không tạo Logger theo ID động hoặc file path từ dữ liệu MDC không tin cậy.
- Không sử dụng MDC làm cơ chế authorization hay isolation tenant.
- Kiểm tra JSON/text encoder không phát secret từ message, throwable hoặc custom fields.
- Cấu hình retention/quyền đọc log ở tất cả nơi sao chép dữ liệu.
- Khi test, dùng ID giả như `req-A`/`req-B`; không dùng dữ liệu cá nhân thật trong fixtures.

MDC là tiện ích chẩn đoán; yêu cầu privacy/security cần được thực hiện ở **nguồn tạo event và cả pipeline logging**.

## 13. Lỗi thường gặp và cách sửa

| Triệu chứng | Nguyên nhân khả dĩ | Cách xác minh/sửa |
| --- | --- | --- |
| `MDC.get` đúng nhưng log không có ID | Encoder không xuất MDC hoặc không có backend phù hợp | Kiểm tra event map và layout riêng |
| Event thiếu ID sau `MdcScope.close()` | `ListAppender` đọc MDC quá muộn | `prepareForDeferredProcessing` ngay trong `append` |
| Test thỉnh thoảng có ID request trước | Test quên `MDC.clear()` hoặc thread pool rò context | Cleanup ở `@AfterEach` và trong task `finally` |
| Async task không có ID | Chưa capture/propagate từ caller | Snapshot trước `submit`, install trong worker |
| Task sau exception có ID cũ | Thiếu cleanup trong `finally` | Test failure và task kế tiếp cùng worker |
| Scope ngoài mất ID sau scope con | Chỉ remove key mà không restore | Lưu map/value trước rồi khôi phục |
| Test song song fail thất thường | Assert sai thứ tự event; Appender không thread-safe | Latch/Future, đồng bộ `append`, so map/set |
| Chạy test bị in log trùng | Root có Appender và Logger test vẫn additive | Logger test riêng, `setAdditive(false)` |
| Log test khác làm sai số event | Gắn appender vào root hoặc dùng Logger chung | Gắn riêng vào Logger tên chuyên dụng |
| `ListAppender` không bắt được event | Appender chưa start, Logger level OFF hoặc backend khác | Start appender và đặt level Logger test |
| Field `requestId` trống trong JSON | Tên field/path schema khác, MDC chưa được bật | Parse JSON thật, kiểm tra field mapping |
| Console test có timestamp khác mong đợi | Test phụ thuộc clock/thread | Assert field ổn định, không hardcode time |
| Test qua `System.out` không ổn định | Text từ Gradle/framework xen vào | Kiểm tra `ILoggingEvent` hoặc stream riêng |
| Unit test pass nhưng production mất trace | Không propagate context qua network/reactive boundary | Integration/E2E với headers/instrumentation |
| CI treo ở executor | Không shutdown hoặc Future chờ vô hạn | Dùng timeout và `shutdownNow()` trong `finally` |
| MDC chứa secret trong output test | Fixture hoặc code ghi quá nhiều dữ liệu | Giảm field, masking và kiểm tra policy |

## 14. Checklist chất lượng trước khi chốt test

- [ ] Test dùng **SLF4J API và provider/backend thực** của môi trường cần xác minh.
- [ ] Test event `getMDCPropertyMap()`, không chỉ `MDC.get()`.
- [ ] Test formatted message, level và logger name khi liên quan.
- [ ] `ListAppender` được start/stop, attach/detach ở scope test.
- [ ] Event được prepare trước khi MDC bị cleanup nếu test lưu reference event.
- [ ] `@BeforeEach`/`@AfterEach` xử lý MDC và khôi phục Logger config.
- [ ] Có test không có MDC, test scope lồng nhau và test exception.
- [ ] Có test executor **không propagation** để ghi nhận giới hạn thực.
- [ ] Có test executor **có propagation**, task sau không rò ID.
- [ ] Có test task worker ném exception và worker được tái sử dụng.
- [ ] Có test hai request chạy đồng thời, không phụ thuộc thứ tự log.
- [ ] Có test layout/encoder xuất đúng field `requestId` mà collector đọc.
- [ ] Có timeout và shutdown executor, không dựa vào `Thread.sleep`.
- [ ] Biết giới hạn của test cục bộ với distributed tracing/framework async.
- [ ] MDC chỉ chứa field diagnostic cần thiết, không mang dữ liệu nhạy cảm.
- [ ] Đã rà schema JSON, key naming, escaping và nơi lưu nếu dùng log tập trung.

### Nguồn tham khảo chính thức

- [SLF4J MDC Javadoc](https://www.slf4j.org/api/org/slf4j/MDC.html): `put`, `get`, `getCopyOfContextMap`, `setContextMap`, `clear`, `putCloseable`.
- [Logback MDC Manual](https://logback.qos.ch/manual/mdc.html): MDC với các thread được Executor quản lý, pattern `%X` và context propagation.
- [Logback Layouts](https://logback.qos.ch/manual/layouts.html): `PatternLayout` và cách trình bày MDC.
- [Logback Javadoc — ILoggingEvent](https://logback.qos.ch/apidocs/ch.qos.logback.classic/ch/qos/logback/classic/spi/ILoggingEvent.html): `getMDCPropertyMap()`, `getFormattedMessage()` và deferred processing.
- [JUnit Jupiter User Guide](https://docs.junit.org/current/user-guide/): lifecycle, assertions, `@Test` và thực thi song song.
- [Java 17 ExecutorService](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ExecutorService.html): submit, Future và thread pool.

**Kết luận:** **Kiểm thử MDC đạt yêu cầu** khi xác nhận *đúng context gắn vào từng logging event*, *đúng format xuất*, *truyền context qua các ranh giới thread cần thiết* và *không rò ID khi scope kết thúc hoặc task thất bại*. Bộ test hiệu quả nhất kết hợp **MDC thực + Logback ListAppender + JUnit**, capture event đúng thời điểm, dùng `Future`/`CountDownLatch` thay cho sleep, và kiểm tra cả negative cases. Một vài assertion `MDC.get` trên main thread chưa đủ để bảo đảm hệ thống logging an toàn trong môi trường concurrent.
