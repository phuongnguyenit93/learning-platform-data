# Logger trong Log4j2 — cách dùng và cơ chế hoạt động

## 1. Logger là gì và cần học những gì?

Trong **Apache Log4j 2**, **Logger** là đối tượng mà mã Java sử dụng để phát sự kiện logging. Mã ứng dụng gọi các phương thức như **trace()**, **debug()**, **info()**, **warn()**, **error()** hoặc **fatal()** trên Logger; hệ thống logging dựa vào cấu hình để quyết định sự kiện nào được xử lý, chuyển tới Appender nào và xuất dưới dạng gì.

Ví dụ điển hình:

~~~java
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public class OrderService {
    private static final Logger LOG = LogManager.getLogger(OrderService.class);

    public void create(String orderId) {
        LOG.info("event=order.created orderId={}", orderId);
    }
}
~~~

Đoạn mã này là một class thành phần, **không có main()** nên chưa phải ứng dụng độc lập. Nó dùng **Log4j API**, cần dependency phù hợp. Điểm quan trọng là business code chỉ nói **sự kiện gì xảy ra**; cấu hình Log4j2 quyết định **sự kiện được chấp nhận và ghi ở đâu**.

Sau bài này, bạn có thể:

- Tạo và tái sử dụng Logger bằng **org.apache.logging.log4j.LogManager.getLogger(...)**.
- Phân biệt **Logger (API)**, **LoggerConfig (cấu hình)**, **LoggerContext**, **LogEvent** và **Appender**.
- Hiểu hệ thống tên Logger, mức log và quan hệ kế thừa cấu hình theo package.
- Dùng **parameterized logging** với placeholder **{}**, kiểm tra **isDebugEnabled()** và hiểu giới hạn của kiểm tra này.
- Gắn **Marker**, **ThreadContext** và exception đúng cách, phân biệt dữ liệu event với nội dung message.
- Đọc cấu hình **log4j2.xml** gồm Root, Logger, AppenderRef, PatternLayout và **additivity**.
- Chạy một dự án Java 17 + Maven + Log4j2, đối chiếu đầu ra đã kiểm thử.
- Nhận diện các sai lầm về Logger name, log trùng, context qua thread, async, hiệu năng và bảo mật.

**Phạm vi:** Bài thuộc nhóm **Log4j2** trong **Java Core Logging**, tập trung vào Logger. Phần Appender, Filter, Layout, async và reconfiguration được giải thích đủ để hiểu Logger hoạt động, không biến thành hướng dẫn tùy biến toàn bộ Log4j Core.

## 2. Kiến trúc: Logger không tự ghi file hoặc console

Một mô hình hữu ích:

~~~text
Application Java
    |
    | LogManager.getLogger(LoggerDemo.class)
    v
Log4j API Logger
    | (name, level methods, message, Marker, Throwable...)
    v
LoggerContext + active Configuration
    |
    +--> LoggerConfig phù hợp với logger name
    |       |
    |       +--> level + Filters
    |       +--> AppenderRef(s)
    |       +--> additivity lên LoggerConfig cha
    |
    v
LogEvent
    |
    v
Appender (Console, File, RollingFile, ...)
    |
    v
Layout/Encoder (PatternLayout, JSON Template Layout, ...)
    |
    v
stdout / file / đích quan sát
~~~

Sơ đồ nhấn mạnh **các vai trò**, không mô tả mọi chi tiết thứ tự gọi ở tất cả cấu hình. Filters có thể được áp dụng ở nhiều vị trí và async logging có thể đưa một phần công việc sang thread khác. Tuy nhiên, hai sự phân biệt nền tảng phải luôn rõ:

1. **Logger** là đối tượng ở phía code và thuộc Log4j API. Nó có tên và phát logging requests.
2. **LoggerConfig** thuộc hệ cấu hình của **Log4j Core**. Nó gắn level, Filter, AppenderRef và additivity với những Logger tương ứng.

Không cần tạo một LoggerConfig cho từng class để có Logger. Nếu code gọi Logger tên **com.example.order.OrderService** nhưng cấu hình chỉ khai báo **com.example.order**, Log4j Core có thể gắn Logger của class với LoggerConfig ở phạm vi package đó.

| Thành phần | Trách nhiệm | Dấu hiệu nhận biết |
| --- | --- | --- |
| **Logger** | Điểm gọi từ ứng dụng, tên Logger và phương thức phát log | LOG.info(...), LOG.warn(...) |
| **LogManager của Log4j2** | Factory/truy cập Logger và LoggerContext thích hợp | org.apache.logging.log4j.LogManager |
| **LoggerContext** | Ngữ cảnh của một hệ logging, giữ cấu hình đang hoạt động | Một ứng dụng có thể có nhiều context tùy môi trường |
| **Configuration** | Định nghĩa LoggerConfigs, Appenders, Filters, Layouts | log4j2.xml, cấu hình khác |
| **LoggerConfig** | Quyết định level, appender routing và additivity theo tên | Logger name/package được cấu hình |
| **LogEvent** | Dữ liệu một sự kiện: level, message, context, marker, Throwable | Được pipeline chuyển cho Appender |
| **Appender** | Nhận event và chuyển tới đích ghi | Console, RollingFile, Async... |
| **Layout** | Biểu diễn event thành text/bytes có cấu trúc | PatternLayout, JSON Template Layout |
| **Filter** | Có thể chấp nhận, từ chối hoặc để quy tắc khác xét tiếp | Theo level, marker, thông tin sự kiện |

**Không nhầm với JUL:** **org.apache.logging.log4j.LogManager** của Log4j2 khác với **java.util.logging.LogManager** trong JDK. Cả hai cùng tên ngắn LogManager nhưng phục vụ hai API/hệ cấu hình khác nhau.

## 3. Lấy Logger đúng cách

### 3.1. Mẫu phổ biến: một Logger theo class

~~~java
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public class PaymentService {
    private static final Logger LOG = LogManager.getLogger(PaymentService.class);

    public void accept(String paymentId) {
        LOG.info("event=payment.accepted paymentId={}", paymentId);
    }
}
~~~

Đây là class thành phần có thể biên dịch khi có dependencies, không có main. Trường **private static final** là cách phổ biến để tái sử dụng Logger thay vì yêu cầu tạo Logger mỗi lần gọi phương thức.

**Vì sao dùng class name?** Log4j2 có thể dùng tên fully qualified class name, chẳng hạn **com.example.payment.PaymentService**, làm logger name. Người vận hành có thể bật DEBUG riêng cho package **com.example.payment** mà không phải bật trên toàn hệ thống.

Có thể viết:

~~~java
private static final Logger LOG = LogManager.getLogger();
~~~

Trong cách gọi phổ biến, **getLogger() không tham số** tự suy ra class đang gọi; dùng **getLogger(PaymentService.class)** giúp người đọc thấy tên class trực tiếp. Cả hai là pattern hợp lệ theo API Log4j2, nhưng với wrapper/utility dùng chung, cần chú ý tên Logger sẽ gắn với class gọi ở vị trí nào.

### 3.2. Đặt tên Logger tùy ý

Có thể dùng tên chuỗi:

~~~java
Logger audit = LogManager.getLogger("com.example.audit");
~~~

Cách này có ích khi ứng dụng muốn một nhóm logging theo chức năng. Tuy nhiên, tên tùy ý cần theo quy ước ổn định. Không nên tạo Logger mới với tên chứa **userId**, **requestId**, timestamp hoặc một giá trị ngẫu nhiên cho từng request: tên động khó cấu hình, dễ gây phình namespace và không thay thế correlation fields.

**Thường nên chọn:** class/package name cho log kỹ thuật; những event names như **order.created** hoặc **payment.failed** nằm trong message/structured attributes, chứ không biến thành hàng nghìn logger names riêng.

### 3.3. Logger có thể tái sử dụng và thread-safe

Log4j API Logger được thiết kế để dùng lại từ nhiều thread. Bạn không cần đồng bộ hóa mọi lệnh **LOG.info** trong service. Tuy nhiên, khả năng thread-safe của Logger **không có nghĩa mọi dữ liệu bạn truyền vào đều bất biến**; object được format hoặc tham chiếu về sau có thể thay đổi, đặc biệt với pipeline async. Hãy bảo đảm dữ liệu log có vòng đời và cách snapshot phù hợp.

**Không nên** lưu Logger trong một trường thay đổi theo từng request hoặc truyền Logger như một loại transaction context. Logger là công cụ phát sự kiện; request context nên được truyền riêng.

## 4. Cây tên Logger và cách chọn LoggerConfig

Log4j2 sử dụng quy tắc tên có dấu chấm để tìm LoggerConfig phù hợp. Ví dụ:

~~~text
Logger trong code:
  com.example.order.OrderService
  com.example.order.CheckoutService
  com.example.payment.PaymentService

LoggerConfig:
  Root                         level=ERROR
  com.example                  level=INFO
  com.example.payment          level=DEBUG
~~~

Nếu không có LoggerConfig đặc biệt cho **com.example.order**, các Logger trong package đó dùng LoggerConfig phù hợp gần nhất, chẳng hạn **com.example**. Logger trong payment sẽ dùng cấu hình cụ thể **com.example.payment**.

**Chú ý tên phân cấp:** tên cấu hình là prefix theo ranh giới dấu chấm. **com.example.pay** không phải ancestor của **com.example.payment.Service** chỉ vì hai chuỗi có cùng vài ký tự đầu. Cần ghi đúng tên package/class.

### 4.1. Logger hierarchy khác LoggerConfig hierarchy

Đây là một khác biệt kiến trúc đáng học:

- **Logger trong mã** không cần tự chứa con trỏ cha/con như cấu trúc Logger ở một số phiên bản logging cũ.
- **LoggerConfig** mới là thành phần tạo quan hệ cấu hình theo tên và quyết định kế thừa mức log, cách routing Appender.
- **Root LoggerConfig** là cấu hình nền được dùng khi không có cấu hình cụ thể hơn.

Tại runtime, Logger được liên kết với LoggerConfig hiện hành. Sau khi Log4j2 nạp lại configuration, Logger có thể được liên kết với một LoggerConfig khác mà code vẫn giữ nguyên trường Logger. Vì vậy, thay đổi cấu hình không yêu cầu sửa mọi lời gọi **LOG.info()**.

### 4.2. Root Logger có vai trò gì?

Root LoggerConfig cung cấp mặc định cho các Logger không có cấu hình phù hợp hơn. Trong Log4j2 XML, nó được viết như:

~~~xml
<Root level="ERROR">
  <AppenderRef ref="STDOUT"/>
</Root>
~~~

Cách khai báo này **chỉ là đoạn cấu hình**, cần có phần Appenders và Configuration đầy đủ để chạy. Root khác với một package LoggerConfig:

~~~xml
<Logger name="com.example.order" level="DEBUG" additivity="false">
  <AppenderRef ref="FILE"/>
</Logger>
~~~

Root không có name dạng package. Nếu logger của ứng dụng không được định nghĩa riêng, mức và Appender do Root hoặc ancestor LoggerConfig xác định.

## 5. Log level: Logger chấp nhận sự kiện nào?

Các mức chuẩn thường dùng trong Log4j2, từ ưu tiên thấp đến cao:

~~~text
ALL < TRACE < DEBUG < INFO < WARN < ERROR < FATAL < OFF
~~~

**ALL** và **OFF** thường dùng làm ngưỡng đặc biệt: ALL cho qua mọi mức thông thường tại điểm kiểm tra; OFF chặn các sự kiện thông thường. TRACE rất chi tiết; DEBUG hỗ trợ điều tra; INFO phản ánh hoạt động; WARN nêu điều kiện bất thường; ERROR/FATAL chỉ các mức lỗi nghiêm trọng tùy policy ứng dụng.

Ví dụ:

~~~java
LOG.trace("attempted parse details");
LOG.debug("selected strategy={}", strategy);
LOG.info("event=order.created orderId={}", orderId);
LOG.warn("event=inventory.retry retry={}", retry);
LOG.error("event=payment.failed orderId={}", orderId);
~~~

Đây là đoạn minh họa trong một phương thức có biến tương ứng, chưa phải chương trình độc lập. Khi ngưỡng của LoggerConfig phù hợp là **INFO**, những event ở TRACE/DEBUG thường bị loại bởi kiểm tra level; INFO/WARN/ERROR được xét tiếp.

| LoggerConfig level | TRACE | DEBUG | INFO | WARN | ERROR |
| --- | --- | --- | --- | --- | --- |
| ERROR | Loại | Loại | Loại | Loại | Cho qua |
| WARN | Loại | Loại | Loại | Cho qua | Cho qua |
| INFO | Loại | Loại | Cho qua | Cho qua | Cho qua |
| DEBUG | Loại | Cho qua | Cho qua | Cho qua | Cho qua |
| TRACE | Cho qua | Cho qua | Cho qua | Cho qua | Cho qua |
| OFF | Loại | Loại | Loại | Loại | Loại |

Bảng giả định **level chuẩn, không có Filter can thiệp và LoggerConfig phù hợp được chọn**. Khi event qua được level, nó vẫn có thể bị Filter hoặc AppenderRef từ chối, hoặc gặp lỗi ở sink; **“cho qua” chưa chắc đồng nghĩa đã lưu thành công**.

### 5.1. isDebugEnabled() có ích khi nào?

~~~java
if (LOG.isDebugEnabled()) {
    LOG.debug("expensive diagnostic={}", computeDiagnostic());
}
~~~

Đây là đoạn tích hợp minh họa, với **computeDiagnostic()** là hàm do ứng dụng định nghĩa. Java đánh giá đối số trước khi gọi phương thức; nếu hàm tạo dữ liệu chẩn đoán tốn CPU/I/O, việc kiểm tra level trước giúp tránh tính khi debug đang tắt.

Tuy nhiên:

- Với giá trị rẻ, **parameterized logging** thường đủ rõ và thuận tiện; không cần bọc mọi câu lệnh bằng if.
- **isDebugEnabled()** chủ yếu trả lời việc Logger hiện cho phép mức DEBUG, không đảm bảo một Appender cuối cùng sẽ ghi record.
- Nếu cấu hình thay đổi giữa lúc kiểm tra và lúc phát log, kết quả có thể thay đổi; đừng dùng isDebugEnabled làm điều kiện quyết định logic nghiệp vụ.
- Fluent API có cách ghi log với Supplier để trì hoãn tạo message theo hợp đồng API; dùng theo nhu cầu và kiểm thử thực tế.

**Không dùng log level để thay if business:** “cho phép thanh toán” là quyết định nghiệp vụ; không được phụ thuộc Logger có bật INFO hay không.

## 6. Parameterized logging và Message trong Log4j2

### 6.1. Placeholder mặc định là {}

Mẫu tốt:

~~~java
LOG.info("event=order.created orderId={} amount={}", orderId, amount);
~~~

Log4j API mặc định dùng kiểu placeholder **{}** cho parameterized messages. Giá trị orderId và amount được truyền thành tham số; backend/MessageFactory tham gia tạo message tương ứng.

So sánh với ghép chuỗi:

~~~java
LOG.debug("state=" + expensiveState.toString());
~~~

Ở ví dụ ghép chuỗi, biểu thức **expensiveState.toString()** có thể được tính ngay cả khi DEBUG bị tắt. Với parameterized logging, cách biểu diễn các tham số được xử lý theo hợp đồng của API và implementation, nhưng **Java vẫn đánh giá các biểu thức đối số trước khi gọi**. Do đó, **LOG.debug("value={}", expensiveOperation())** vẫn gọi expensiveOperation() trước khi backend biết event có bị lọc hay không. Dùng kiểm tra level hoặc cơ chế lazy phù hợp khi chi phí thực sự đáng kể.

### 6.2. MessageFactory có thể ảnh hưởng cách format

Log4j2 hỗ trợ các **MessageFactory** khác nhau. Mẫu **{}** là quy ước mặc định phổ biến, nhưng một Logger được tạo với MessageFactory đặc biệt có thể hiểu message khác, ví dụ dạng printf. Không tự thay **{}** thành **%s** hoặc **{0}** mà chưa kiểm tra API/MessageFactory đang dùng.

Ngoài String đơn giản, Log4j2 còn có kiểu **Message** cho dữ liệu có cấu trúc. Điều này hữu ích nếu cần phân tích event ở backend; nhưng lựa chọn cấu trúc phải phù hợp encoder/layout đang dùng, không chỉ đổi kiểu của đối số.

### 6.3. Message khác event code

Một message như:

~~~text
Order ORD-42 was created
~~~

có thể thay cách viết, ngôn ngữ hoặc định dạng. Trong hệ thống cần tra cứu ổn định, nên có **event key** như **order.created**, cùng structured fields như **order_id**, **service**, **request_id**. Không xây dựng dashboard bằng regex phụ thuộc toàn bộ câu văn.

Ví dụ vừa đủ cho môi trường học:

~~~java
LOG.info("event=order.created orderId={}", orderId);
~~~

Trong production, nếu log được xuất dưới dạng JSON hoặc schema chung, nên đưa event name và orderId thành thuộc tính có cấu trúc thật qua cơ chế Message/Context/encoder phù hợp, tránh chỉ parse lại message text.

## 7. Logger, Marker, ThreadContext và Throwable

Logger có nhiều cách đính kèm thông tin giúp điều tra sự cố. Các cơ chế này giải quyết các nhu cầu khác nhau.

### 7.1. Marker: nhãn phân loại event

**Marker** là nhãn có tên, có thể gắn vào logging request. Ví dụ:

~~~java
import org.apache.logging.log4j.Marker;
import org.apache.logging.log4j.MarkerManager;

private static final Marker AUDIT = MarkerManager.getMarker("AUDIT");

// Trong một phương thức:
LOG.info(AUDIT, "event=order.accepted orderId={}", orderId);
~~~

Đây là đoạn tích hợp trong class có Logger, không phải chương trình độc lập. Marker có thể được đưa vào layout hoặc dùng ở filter/routing nếu cấu hình hỗ trợ.

**Marker không tự tạo một audit log đáng tin cậy**. Nếu sự kiện có nghĩa vụ bảo toàn, cần thiết kế sink, quyền truy cập, retention và bảo đảm delivery riêng; chỉ gắn chữ AUDIT không làm dữ liệu tự trở nên an toàn.

### 7.2. ThreadContext: thông tin request/trace hiện hành

**ThreadContext** cung cấp map/stack context để thêm các cặp key–value vào event, ví dụ **requestId**, **traceId**, **spanId**. Một cách quản lý scope rõ ràng:

~~~java
import org.apache.logging.log4j.CloseableThreadContext;

try (CloseableThreadContext.Instance ignored =
             CloseableThreadContext.put("requestId", requestId)) {
    LOG.info("event=order.accepted orderId={}", orderId);
}
~~~

Đoạn trên cần biến requestId/orderId trong phương thức; nó chưa phải chương trình độc lập. Khi ra khỏi khối try, scope close giúp khôi phục/dọn context do scope quản lý, tránh để requestId bám sang tác vụ tiếp theo trên thread được tái sử dụng.

**Một số giới hạn quan trọng:**

- Context map thường gắn với thread. Chuyển việc sang **ExecutorService**, **CompletableFuture**, virtual threads hoặc pipeline async có thể không tự mang đúng context.
- Nếu cần truyền context, dùng cơ chế propagation có hợp đồng rõ, thu thập snapshot khi cần và dọn context trong scope/finally.
- Đưa **traceId/spanId** vào event không tự tạo distributed tracing; cần instrumentation và propagation phù hợp.
- Không đặt password, access token, cookie phiên hoặc dữ liệu nhạy cảm vào ThreadContext.

Trong PatternLayout, một trường có thể được đọc bằng **%X{requestId}**. Nếu không có key ở scope hiện tại, nó thường được render thành chuỗi rỗng trong mẫu layout tương ứng.

### 7.3. Throwable: thông tin lỗi và stack trace

Khi có exception, hãy gắn **Throwable** để logging backend có thể xử lý stack trace:

~~~java
try {
    chargeCard();
} catch (PaymentGatewayException ex) {
    LOG.atError()
       .withThrowable(ex)
       .log("event=payment.charge_failed orderId={}", orderId);
}
~~~

Đây là đoạn minh họa cần định nghĩa **chargeCard**, **PaymentGatewayException** và biến orderId; **không** phải chương trình độc lập. **Fluent API** làm rõ exception được gắn vào event, tránh sự mơ hồ trong overload nhận tham số cuối là Throwable.

Để dùng fluent logging, gọi **LOG.atInfo()**, **LOG.atWarn()**, **LOG.atError()** rồi kết thúc bằng **log(...)**. Nếu quên bước kết thúc, event có thể không được phát.

**Không ghi cùng một exception ở mọi tầng** nếu không có thêm ý nghĩa xử lý; điều đó dễ tạo log trùng. Ghi lỗi tại ranh giới có quyết định xử lý và giữ cause chain phù hợp. Exception message có thể chứa bí mật hoặc dữ liệu người dùng, nên cần chính sách redaction.

## 8. Appender, LoggerConfig và additivity

### 8.1. Appender nhận được event nào?

LoggerConfig chứa references tới các Appender. Một LoggerConfig có thể gửi event tới Console, File, RollingFile hoặc Appender khác. Mỗi nơi có format, filter và chính sách xử lý riêng.

~~~text
Logger: com.example.order.OrderService
  -> LoggerConfig com.example.order (level INFO)
      -> AppenderRef FILE
      -> ancestor LoggerConfig/Root AppenderRef CONSOLE (nếu additivity cho phép)
~~~

**AppenderRef** có thể có điều kiện level hoặc filter riêng; Appender cũng có filter. Việc Logger ở DEBUG không ép tất cả các sink nhận DEBUG.

### 8.2. additivity=true có thể làm log tới nhiều đích

Theo mặc định, LoggerConfig không phải Root thường có **additivity=true**: event đã được cho phép có thể được chuyển tới các Appender của LoggerConfig phù hợp **và các ancestor LoggerConfig**, cho đến khi gặp một LoggerConfig đặt additivity=false hoặc tới Root.

Ví dụ:

~~~xml
<Logger name="com.example.order" level="INFO">
  <AppenderRef ref="FILE"/>
</Logger>
<Root level="ERROR">
  <AppenderRef ref="CONSOLE"/>
</Root>
~~~

Đây là đoạn XML minh họa cần các Appender đã khai báo. Khi order LoggerConfig ở INFO chấp nhận một INFO event, event có thể tới cả FILE và CONSOLE vì additivity mặc định cho phép, dù Root được cấu hình ERROR. **Đừng giả định Root level sẽ lọc lại một sự kiện đã được LoggerConfig con cho phép trên đường additivity.** Các Filter/AppenderRef vẫn có thể ảnh hưởng.

Nếu FILE và CONSOLE cùng xuất về một nơi tập trung, bạn có thể thấy log trùng.

### 8.3. additivity=false chặn chuyển event tới ancestor Appenders

~~~xml
<Logger name="com.example.order" level="INFO" additivity="false">
  <AppenderRef ref="FILE"/>
</Logger>
~~~

LoggerConfig đó sử dụng AppenderRef của chính nó và không tiếp tục cộng dồn các Appender của ancestor. Đây là cách xử lý khi thật sự muốn một pipeline độc lập. **Không đặt additivity=false theo thói quen** nếu LoggerConfig không có đích xuất riêng, vì event có thể không còn nơi ghi.

**Vấn đề cần phân biệt:** Logger name trong Java là tên nguồn. Attribute **name** của LoggerConfig xác định phạm vi cấu hình. **ref** trong AppenderRef phải đúng tên Appender đã khai báo.

## 9. Ví dụ Java 17 + Maven + Log4j2 chạy đầy đủ

Ví dụ này sử dụng **Log4j2 2.25.3**, gồm **log4j-api** và **log4j-core** cùng phiên bản, với Maven Compiler Plugin target **Java 17**. Đây là phiên bản cụ thể đã được dùng để **biên dịch và kiểm chứng stdout**; khi làm dự án thực tế, hãy dùng phiên bản Log4j 2 được duy trì và quản lý đồng bộ dependencies bằng BOM khi thích hợp.

Kết quả thực hành sẽ cho thấy:

1. Logger tên **demo.logging.LoggerDemo** dùng LoggerConfig **demo.logging** ở mức INFO.
2. Lệnh DEBUG bị loại; INFO và WARN đi tiếp.
3. Marker **AUDIT** được in khi có.
4. **requestId** xuất hiện chỉ trong khối **CloseableThreadContext**.
5. **additivity=false** ngăn event được nhân đôi bởi Root Appender.

### 9.1. Cấu trúc thư mục

~~~text
logger-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── demo/
        │       └── logging/
        │           └── LoggerDemo.java
        └── resources/
            └── log4j2.xml
~~~

**Vì sao cần hai dependencies?**

- **log4j-api** chứa Logger và LogManager dùng trong source.
- **log4j-core** là implementation được dùng trong ví dụ để đọc log4j2.xml, xử lý LoggerConfig, Appender và PatternLayout.

Nếu chỉ có API, có thể rơi vào một cơ chế logging tối thiểu hoặc provider khác tùy môi trường, khiến output không giống bài. Khi sử dụng framework lớn, cần kiểm tra dependency graph và provider/runtime thực tế, tránh vô tình có nhiều implementation hoặc bridge ngược chiều.

### 9.3. Tệp src/main/resources/log4j2.xml

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration>
  <Appenders>
    <Console name="STDOUT" target="SYSTEM_OUT">
      <PatternLayout pattern="%level|%logger{1}|%marker|req=%X{requestId}|%message%n"/>
    </Console>
  </Appenders>
  <Loggers>
    <Logger name="demo.logging" level="INFO" additivity="false">
      <AppenderRef ref="STDOUT"/>
    </Logger>
    <Root level="ERROR">
      <AppenderRef ref="STDOUT"/>
    </Root>
  </Loggers>
</Configuration>
~~~

Giải thích:

- **Console name="STDOUT" target="SYSTEM_OUT"** định nghĩa đích output trên stdout.
- **PatternLayout** quyết định format: severity, tên Logger rút gọn, Marker, requestId, message và newline.
- **Logger name="demo.logging"** áp dụng cho những Logger thuộc namespace tương ứng, trong đó có class **demo.logging.LoggerDemo**.
- **level="INFO"** loại các logging requests DEBUG/TRACE theo quy tắc mức chuẩn.
- **additivity="false"** chặn chuyển các event đã được logger cấu hình này chấp nhận tới Appender của Root, tránh output trùng.
- **Root level="ERROR"** là cấu hình dự phòng cho các Logger không có cấu hình cụ thể hơn; Root không khiến INFO của LoggerConfig demo.logging bị chặn lại theo cách kiểm tra level lần thứ hai.

Nếu muốn nhìn tất cả các dòng ở TRACE/DEBUG trong ví dụ, đổi level tại LoggerConfig **demo.logging**, đồng thời kiểm tra filter/đích nếu đã thêm vào cấu hình.

### 9.4. Tệp src/main/java/demo/logging/LoggerDemo.java

~~~java
package demo.logging;

import org.apache.logging.log4j.CloseableThreadContext;
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;
import org.apache.logging.log4j.MarkerManager;

public final class LoggerDemo {
    private static final Logger LOG = LogManager.getLogger(LoggerDemo.class);

    public static void main(String[] args) {
        LOG.debug("order.trace id={}", "ORD-42");
        LOG.info("order.created id={}", "ORD-42");
        try (CloseableThreadContext.Instance ignored =
                     CloseableThreadContext.put("requestId", "req-42")) {
            LOG.info(MarkerManager.getMarker("AUDIT"), "order.accepted id={}", "ORD-42");
            LOG.warn("payment.retry count={}", 1);
        }
        System.out.println("debugEnabled=" + LOG.isDebugEnabled());
        System.out.println("infoEnabled=" + LOG.isInfoEnabled());
    }
}
~~~

Điểm đáng học:

- **Logger** được giữ bởi một trường static final.
- Các placeholder **{}** nhận đối số như orderId và số lần retry.
- Marker AUDIT chỉ có ở event cụ thể.
- ThreadContext được gắn trong khối có phạm vi rõ và được dọn khi kết thúc.
- **isDebugEnabled** và **isInfoEnabled** cho thấy trạng thái mức tương ứng tại Logger, không bảo đảm sink đã lưu thành công.

### 9.5. Chạy và đối chiếu stdout

Tại thư mục chứa **pom.xml**, chạy:

~~~bash
mvn -q -B compile exec:java "-Dexec.mainClass=demo.logging.LoggerDemo"
~~~

Lệnh trên dùng Maven để tải dependency, compile target Java 17 và thực thi class. Cần JDK hỗ trợ target 17 và Maven truy cập được dependencies (hoặc đã có các artifact trong cache).

**stdout chính xác đã kiểm chứng khi biên dịch/chạy** với Log4j2 2.25.3:

~~~text
INFO|LoggerDemo||req=|order.created id=ORD-42
INFO|LoggerDemo|AUDIT|req=req-42|order.accepted id=ORD-42
WARN|LoggerDemo||req=req-42|payment.retry count=1
debugEnabled=false
infoEnabled=true
~~~

Nếu Maven không dùng tùy chọn **-q**, nó có thể hiển thị thêm log riêng của Maven trước/sau output chương trình; các dòng trên là **stdout của demo** với lệnh đã nêu.

### 9.6. Vì sao không có dòng debug?

Logger thuộc phạm vi **demo.logging**, cấu hình **level=INFO**. Lệnh **LOG.debug(...)** không đạt ngưỡng. Vì vậy:

- Không có dòng **order.trace id=ORD-42** trong output;
- **LOG.isDebugEnabled()** in **false**;
- **LOG.isInfoEnabled()** in **true**;
- INFO và WARN đi qua LoggerConfig và Appender.

### 9.7. Vì sao requestId biến mất ở đầu/cuối nhưng có ở giữa?

**CloseableThreadContext.put("requestId", "req-42")** chỉ được dùng trong scope của hai câu log giữa. PatternLayout đọc **%X{requestId}**, nên:

- INFO đầu tiên không có requestId;
- INFO có Marker AUDIT và WARN bên trong scope mang **req-42**;
- Khi scope kết thúc, context được dọn, tránh để giá trị dính sang tác vụ sau.

Với hệ thống server đa luồng, vẫn cần kiểm thử propagation qua executor/async; scope đúng trong cùng thread **không tự giải quyết** mọi trường hợp chuyển luồng.

### 9.8. Vì sao mỗi event chỉ có một dòng?

LoggerConfig **demo.logging** đã gắn STDOUT. Thuộc tính **additivity=false** khiến event không tiếp tục cộng dồn lên Root Appender. Nếu đổi thành true, những event đã được chấp nhận ở LoggerConfig này có thể được chuyển đến Root STDOUT và xuất trùng vì cả hai cấu hình cùng tham chiếu một đích console. Đây là hệ quả của routing Appender, không phải lỗi vì code gọi LOG.info hai lần.

## 10. Dùng Logger trong ứng dụng thực tế

### 10.1. Chọn level theo sự kiện

Không có quy tắc duy nhất cho mọi nhóm, nhưng bảng sau là điểm bắt đầu hữu ích:

| Level | Ví dụ phù hợp |
| --- | --- |
| TRACE | Diễn biến rất chi tiết của parser hoặc một bước xử lý |
| DEBUG | Thông tin phục vụ tìm nguyên nhân khi điều tra |
| INFO | Sự kiện vận hành có giá trị, trạng thái vòng đời |
| WARN | Retry, fallback, bất thường có thể xử lý được |
| ERROR | Tác vụ thất bại hoặc lỗi đáng quan tâm tại ranh giới xử lý |
| FATAL | Sự cố nghiêm trọng ảnh hưởng khả năng hoạt động của thành phần |

Không ghi INFO cho mọi lời gọi hàm nếu lượng request lớn. Không dùng ERROR cho mọi trường hợp nghiệp vụ được dự đoán trước (ví dụ input người dùng sai có phản hồi hợp lệ), vì sẽ tạo dashboard/cảnh báo nhiễu.

### 10.2. Tên sự kiện ổn định, dữ liệu biến thiên ở parameters

Ví dụ:

~~~java
LOG.info("event=order.submitted orderId={} channel={}", orderId, channel);
LOG.warn("event=inventory.lookup_retry attempt={} timeoutMs={}", attempt, timeoutMs);
~~~

Đây là đoạn mã dùng trong phương thức có các biến tương ứng. Mục đích là cho người đọc và công cụ hiểu **event** nhất quán. Với hệ thống cần structured logging thực thụ, hãy dùng Message/ThreadContext/JSON Layout phù hợp thay vì giả định parser luôn có thể bóc mọi field từ text.

### 10.3. Không biến Logger thành một nơi xử lý nghiệp vụ

Sai:

~~~java
if (LOG.isInfoEnabled()) {
    sendReceiptEmail();
}
~~~

Điều này khiến tính năng gửi email phụ thuộc cấu hình log. Điều kiện business phải được kiểm tra độc lập, còn logging ghi lại kết quả:

~~~java
sendReceiptEmail();
LOG.info("event=receipt.sent orderId={}", orderId);
~~~

Hai đoạn là minh họa trong phương thức đã định nghĩa các biến/hàm cần thiết, không chạy độc lập.

### 10.4. Ghi Throwable đúng nơi

Ghi lỗi ở nơi có thể diễn giải/ra quyết định xử lý, kèm error code và thông tin cần thiết:

~~~java
LOG.atError()
   .withThrowable(error)
   .log("event=inventory.lookup_failed dependency={} orderId={}",
        dependencyName, orderId);
~~~

Đoạn này cần biến error, dependencyName, orderId trong phương thức. Không ghi cùng lỗi ở cả controller, service và repository nếu không có lý do riêng; dễ nhân số lượng bản ghi và khiến người trực hệ thống khó xác định lần xử lý thực sự thất bại.

### 10.5. Log và UI message có mục đích khác nhau

Một Logger phục vụ vận hành; message cho người dùng có thể được bản địa hóa. Không phát nguyên stack trace cho UI. Mã sự kiện và thuộc tính kỹ thuật nên ổn định, còn câu văn có thể thay đổi theo ngôn ngữ và cách diễn đạt.

## 11. Cấu hình Logger theo package và thay đổi khi vận hành

Với Log4j2, bạn thường điều chỉnh level trong **log4j2.xml** hoặc một kiểu cấu hình Log4j Core khác được hỗ trợ. Có thể đặt file cấu hình trong classpath dưới tên được framework nhận diện hoặc dùng thuộc tính khởi động phù hợp, chẳng hạn **log4j2.configurationFile** khi cần chỉ rõ nguồn cấu hình.

Ví dụ muốn bật DEBUG chỉ ở payment:

~~~xml
<Loggers>
  <Logger name="com.example.payment" level="DEBUG"/>
  <Root level="INFO">
    <AppenderRef ref="STDOUT"/>
  </Root>
</Loggers>
~~~

Đây là đoạn cấu hình cần Appender STDOUT đã khai báo ở phần khác. Vì LoggerConfig payment không có AppenderRef riêng và additivity mặc định là true, các event phù hợp có thể được chuyển đến Appender của ancestor/Root. Nếu đã thêm filter hoặc tham chiếu Appender có mức giới hạn riêng, các sự kiện DEBUG vẫn có thể bị loại ở đó.

**Lưu ý reconfiguration:** Logger trong code có thể tiếp tục được giữ bởi trường static final, trong khi association tới LoggerConfig thay đổi khi cấu hình mới được kích hoạt. Tuy nhiên, không nên thay đổi cấu hình runtime bằng các thao tác nội bộ không có quản lý vòng đời; có thể gây thiếu/đúp Appender, mất output, hoặc vấn đề khi sink đang ghi.

### 11.1. Khi chỉ muốn điều chỉnh một Logger

Không sửa tất cả các package bằng cách bật root TRACE trên production. Ưu tiên logger name cụ thể:

~~~xml
<Logger name="com.example.payment" level="DEBUG"/>
~~~

Nếu Log4j2 được cấu hình theo file, hãy xác nhận file được nhận diện và setting mới có hiệu lực trên đúng Logger. Các ứng dụng framework có thể dùng lớp cấu hình logging riêng hoặc điều phối lại Log4j2; cần xác định runtime provider thực tế.

### 11.2. Lưu ý async Logger

Log4j2 hỗ trợ **async logging**, trong đó công việc I/O có thể chuyển sang thread khác. Có **AsyncAppender** và **AsyncLogger**; chúng không phải cùng một cơ chế và có yêu cầu dependency/cấu hình khác nhau.

Async có thể giảm thời gian chặn luồng gọi Logger trong một số workload, nhưng có rủi ro **queue đầy, block/drop, mất record khi ứng dụng dừng đột ngột hoặc thứ tự output thay đổi**. Không khẳng định async luôn tốt hơn: phải đo latency, throughput, memory và backpressure với workload thật.

Đừng làm bất kỳ tác vụ nghiệp vụ quan trọng nào phụ thuộc việc một log async đã được ghi bền vững, trừ khi hệ thống có hợp đồng audit riêng.

## 12. Phân biệt Log4j2 Logger với các API logging khác

Trong Java có nhiều API cùng xuất hiện trong một ứng dụng:

| API | Logger class | Lấy Logger bằng |
| --- | --- | --- |
| **Log4j2 API** | org.apache.logging.log4j.Logger | org.apache.logging.log4j.LogManager.getLogger(...) |
| **JUL** | java.util.logging.Logger | java.util.logging.Logger.getLogger(...) |
| **SLF4J** | org.slf4j.Logger | org.slf4j.LoggerFactory.getLogger(...) |

Các API không thể tùy tiện thay package imports rồi giữ nguyên mọi cú pháp. Cấu hình JUL dùng **java.util.logging.LogManager**, khác Log4j2; SLF4J thường là facade và cần provider/backend tương thích.

Nếu ứng dụng dùng SLF4J API nhưng muốn Log4j Core làm backend, cần adapter/provider được hỗ trợ và dependency đúng hướng. Nếu thư viện dùng JUL, có thể có bridge vào backend chung. **Không cài cả hai hướng chuyển đồng thời** vì có thể tạo vòng lặp logging hoặc output trùng.

**Log4j 1.x** với import **org.apache.log4j.Logger** là thế hệ cũ, khác API **org.apache.logging.log4j.Logger** của Log4j2. Đừng trộn ví dụ và configuration giữa Log4j 1 và Log4j 2.

## 13. Những lỗi thường gặp khi dùng Logger

### 13.1. Dùng sai tên Logger trong cấu hình

**Hiện tượng:** Đã cấu hình **com.example.orders** DEBUG nhưng Logger trong code tên **com.example.order.OrderService** vẫn không in debug.

**Giải thích:** Hai tên khác nhau. Kiểm tra package/class và tên Logger thực tế. Tên có dấu chấm tạo ranh giới; không dựa vào “trông gần giống” để đoán cấu hình khớp.

### 13.2. Có Log4j API nhưng không có backend phù hợp

**Hiện tượng:** Log4j2 không đọc log4j2.xml hoặc output khác dự kiến.

**Giải thích:** Dependency runtime/implementation có thể thiếu hoặc bị framework thay bằng lựa chọn khác. Kiểm tra log4j-api, log4j-core, provider và các adapter; không cài chồng nhiều backend khi chưa hiểu dependency graph.

### 13.3. DEBUG được bật nhưng không thấy dòng log

Kiểm tra LoggerConfig phù hợp, level của nó, Filter trên nhiều tầng, AppenderRef và đích xuất. **LOG.isDebugEnabled()** là một thông tin hữu ích nhưng không xác nhận đã ghi ra file hoặc collector.

### 13.4. Dòng log xuất hai lần

**Nguyên nhân phổ biến:** Cùng event được chuyển tới cả Appender của LoggerConfig con và ancestor do **additivity=true**. Xem cấu hình và xác định rõ nơi cần ghi; nếu muốn cô lập, đặt additivity=false với AppenderRef thực sự phù hợp.

### 13.5. additivity=false làm log biến mất

Nếu LoggerConfig riêng không có Appender được gắn phù hợp và additivity bị tắt, event không được forward đến Appender của cha. Sửa đường routing trước khi kết luận rằng Logger không hoạt động.

### 13.6. Ghép String hoặc gọi hàm đắt tiền ở DEBUG

Ngay cả khi log không xuất, Java có thể đã tạo String hoặc chạy hàm để tính argument. Dùng **{}**, tránh toString tự gọi, cân nhắc isDebugEnabled hoặc Supplier theo API khi dữ liệu đắt tiền.

### 13.7. Để ThreadContext rò sang request khác

Thread pool tái sử dụng thread; nếu gọi ThreadContext.put rồi không dọn, request kế tiếp có thể mang ID cũ. Dùng scope/try-with-resources, kiểm chứng propagation và cleanup ở cả nhánh lỗi.

### 13.8. Cho rằng Marker là bằng chứng bảo toàn audit

Marker chỉ là nhãn; sink vẫn có thể mất dữ liệu, bị filter, sampling hoặc gặp lỗi I/O. Cần policy audit có kiểm thử và kiểm soát truy cập nếu dữ liệu bắt buộc phải lưu.

### 13.9. Ghi exception nhiều lần hoặc bỏ mất Throwable

Chỉ ghi message kiểu **"Something went wrong"** thì không đủ. Nhưng ghi toàn stack trace ở mọi lớp lại làm log ồn. Chọn boundary xử lý, gắn Throwable khi cần và thêm error code/ngữ cảnh đủ điều tra.

### 13.10. Dùng bản Log4j2 lỗi thời

Logging framework là dependency chạy trong môi trường thật, cần được cập nhật theo các bản phát hành bảo trì và khuyến cáo bảo mật. Không sao chép các phiên bản Log4j 2 cũ không được bảo trì từ bài hướng dẫn trên mạng. Trong project, quản lý phiên bản đồng nhất cho API/Core và các module mở rộng (có thể bằng **log4j-bom**), kiểm tra dependency tree.

## 14. Hiệu năng, an toàn dữ liệu và logging quality

### 14.1. Chọn dữ liệu đủ để hành động

Một event tốt có **event name**, level phù hợp, service/version, requestId/traceId nếu có, dependency, outcome và error code khi cần. Không dùng message quá ngắn như “Error” hoặc “Failed” mà không có ngữ cảnh.

Ví dụ:

~~~text
event=inventory.lookup_failed dependency=inventory-db requestId=req-42 errorType=TimeoutException
~~~

Nội dung cụ thể cần phù hợp chính sách dữ liệu. Một event kỹ thuật có thể chứa ID vận hành phi nhạy cảm, nhưng không nên in toàn bộ dữ liệu giao dịch hoặc payload mà không có lý do.

### 14.2. Không ghi dữ liệu bí mật vào bất kỳ level nào

Không ghi password, token, API key, session cookie, private key, toàn bộ thẻ thanh toán hoặc payload nhạy cảm. Việc đặt log ở DEBUG **không bảo đảm an toàn**, vì DEBUG có thể được bật khi điều tra. Các trường trong ThreadContext, Marker-associated data hoặc exception message cũng phải được kiểm soát.

Log injection có thể xảy ra khi dữ liệu người dùng chứa newline/ký tự điều khiển. Nếu cần structured logging, dùng encoder/layout có escaping hợp lệ thay vì tự nối chuỗi tạo JSON.

### 14.3. Lượng log và cardinality

Không tạo Logger name khác nhau cho từng request. Không đưa requestId/userId/raw URL có ID thành metric label cardinality cao. Nếu cần liên kết chi tiết, đưa ID vào fields của log/traces đã kiểm soát retention và quyền truy cập.

Log chi tiết ở mức TRACE/DEBUG có thể tăng CPU, allocations, I/O, network và dung lượng. Bật theo phạm vi package trong thời gian cần thiết; kiểm tra tình huống sink chậm, queue đầy và shutdown.

### 14.4. Một event và nhiều nguồn telemetry

Logger phát event; nó **không tự tạo metrics hoặc distributed traces**. ThreadContext có thể mang traceId nhưng cần instrumentation/propagation khác để sinh span. Khi điều tra, kết hợp log event với metrics (tỷ lệ lỗi, latency) và traces nếu hệ thống có.

## 15. Checklist xác minh Logger trong production

Khi “không thấy log” hoặc “log quá nhiều”, đi theo thứ tự:

1. **Đúng Logger instance/name?** Kiểm tra package/class, không nhầm Log4j2 API với JUL/SLF4J.
2. **Đúng runtime provider?** Có implementation tương thích và cấu hình log4j2.xml đã được load?
3. **LoggerConfig nào đang áp dụng?** Tên cụ thể hoặc ancestor gần nhất? Root level ra sao?
4. **Level có phù hợp?** DEBUG/INFO/WARN/ERROR có đạt ngưỡng được chọn?
5. **Filter có loại record?** Xét Filter ở những tầng liên quan.
6. **AppenderRef có đúng?** Appender đã khai báo, được start, đang nhận record?
7. **Additivity có tạo trùng hoặc chặn forwarding?** Xem đường tới ancestor Appenders.
8. **Layout có xuất fields cần thiết?** Marker và requestId có trong pattern/encoder không?
9. **Context propagation có chính xác?** Không rò request ID khi thread được tái sử dụng.
10. **Sink/collector có nhận được dữ liệu?** Kiểm tra stdout/stderr, file permission, buffer, queue, exporter và downstream filters.

Đừng chỉ nhìn lệnh LOG.info rồi khẳng định chắc chắn có một dòng log ở file. Cần kiểm tra cả API, cấu hình và đích xuất thực tế.

## 16. Bài tập tự thực hành

### Bài A — Thay level

Trong **log4j2.xml**, đổi **demo.logging** từ INFO sang DEBUG, giữ phần còn lại. Chạy lại. Dự đoán **order.trace id=ORD-42** xuất hiện ở DEBUG và **debugEnabled=true**. Giải thích vì sao ví dụ gốc không có dòng này.

### Bài B — Thử additivity

Đổi **additivity="false"** sang **true** trong LoggerConfig demo.logging. Cùng một STDOUT được tham chiếu ở LoggerConfig đó và Root; dự đoán khả năng mỗi log event qua ngưỡng của LoggerConfig được xuất hai lần. Thử thực tế và xác nhận sự khác biệt.

### Bài C — Thêm một Logger theo package

Tạo class **demo.logging.payment.PaymentService** với Logger có tên lớp. Giữ cấu hình **demo.logging** INFO. Sau đó thêm LoggerConfig **demo.logging.payment** DEBUG và quan sát logger của PaymentService có nhận DEBUG không. Phân biệt logger name của class với LoggerConfig dùng chung cho package.

### Bài D — Context scope

Đưa một câu **LOG.info** ra sau khối CloseableThreadContext trong demo; kiểm tra requestId không còn xuất ở bản ghi mới. Tiếp theo thử một CompletableFuture chạy trên executor và giải thích vì sao phải thiết kế context propagation riêng.

### Bài E — Exception

Bổ sung một nhánh bắt lỗi có **atError().withThrowable(ex).log(...)**. Cấu hình layout để hiển thị Throwable và xác nhận error type/stack trace không bị mất. Kiểm tra exception message không chứa thông tin nhạy cảm.

### Bài F — Structured logging

Thay cách chỉ ghi text **"order.created id=ORD-42"** bằng event schema có các thuộc tính **event**, **order_id**, **service**, **request_id**. Mô tả loại layout/encoder cần dùng để downstream query theo trường ổn định.

## 17. Câu hỏi kiểm tra và đáp án

**1. Logger trong Log4j2 có phải LoggerConfig không?**  
Không. Logger là API handle ở mã Java. LoggerConfig thuộc cấu hình của Log4j Core, quyết định level/filter/Appender routing.

**2. Có cần LoggerConfig riêng cho mỗi class không?**  
Không. Một LoggerConfig theo package có thể phục vụ nhiều Logger theo class trong package đó.

**3. Logger tên com.example.order.CheckoutService có thể dùng cấu hình com.example.order không?**  
Có, nếu không có LoggerConfig khác phù hợp hơn và hệ hierarchy theo tên áp dụng như dự kiến.

**4. Vì sao Logger level INFO nhưng một số INFO vẫn không tới file?**  
Vì Filter, AppenderRef, Appender, sink hoặc pipeline phía sau có thể chặn/lỗi. Qua level mới chỉ là một bước.

**5. Nếu Root level ERROR, LoggerConfig con INFO với additivity=true có thể đưa INFO tới Root Appender không?**  
Có. Routing appender theo additivity không mặc định tái áp ngưỡng Root như một lời gọi mới vào Root Logger. Filter/AppenderRef vẫn có thể loại.

**6. Có nên đặt additivity=false cho mọi LoggerConfig?**  
Không. Phải bảo đảm LoggerConfig có AppenderRef phù hợp; nếu không event có thể không còn nơi xuất.

**7. isDebugEnabled() false có nghĩa DEBUG không phát ở Logger đó?**  
Có thể dùng để biết Logger tại thời điểm kiểm tra không chấp nhận DEBUG; không dùng nó làm điều kiện nghiệp vụ và không thay xác minh sink cuối cùng.

**8. Parameterized logging {} có tự khiến expensiveOperation() không chạy khi DEBUG bị tắt?**  
Không. Java đánh giá biểu thức đối số trước lời gọi; nếu đối số thực sự tốn kém, dùng kiểm tra level hoặc lazy API.

**9. Marker AUDIT có tự đảm bảo bản ghi đã được lưu bền vững?**  
Không. Marker chỉ là nhãn; delivery/retention/audit policy phụ thuộc pipeline.

**10. Vì sao cần dọn ThreadContext?**  
Để tránh requestId/traceId của một tác vụ rò sang tác vụ khác trên thread được tái sử dụng.

**11. Khác nhau giữa org.apache.logging.log4j.LogManager và java.util.logging.LogManager là gì?**  
Một API thuộc Log4j2; một API thuộc JUL của JDK. Chúng không cùng hệ cấu hình nếu không có tích hợp/bridge tương ứng.

**12. Bật DEBUG toàn root trên production có nên là bước đầu tiên khi điều tra?**  
Thường không. Chọn package cụ thể, thời hạn và kế hoạch quan sát log volume trước khi tăng mức chi tiết trên diện rộng.

## 19. Ghi nhớ cốt lõi

**Logger là điểm phát sự kiện từ mã ứng dụng.** **LoggerConfig mới quyết định chính sách level, filter, appender và additivity theo tên Logger** trong Log4j Core. Một Logger theo class thường được giữ **static final**, sử dụng message có tham số **{}**, và ghi dữ liệu context/Throwable có kiểm soát.

Khi log không xuất đúng mong đợi, hãy kiểm tra **logger name → LoggerConfig → level/filter → AppenderRef/additivity → layout → sink**. Ví dụ Maven đã kiểm chứng cho thấy một Logger có thể ghi INFO/WARN, gắn Marker và requestId theo scope, trong khi DEBUG bị loại và event không bị nhân đôi nhờ additivity=false.
