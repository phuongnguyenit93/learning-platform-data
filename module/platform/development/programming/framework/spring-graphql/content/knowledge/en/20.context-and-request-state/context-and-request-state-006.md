# Request metadata

A GraphQL operation often needs extra information beyond the document, variables, and operation name. For example, the server may need a correlation ID to tie logs together, a locale to format messages, a tenant ID to scope data, or authentication information to check permissions. Together, these pieces of data are called **request metadata**.

With Spring for GraphQL, metadata can come from HTTP headers or transport information, be validated at the request layer, and then be placed into **GraphQLContext** for resolvers to use throughout a single execution. This organization ensures handlers receive the exact data they need without reading the HTTP request directly or requiring the client to repeat metadata in every argument.

This lesson explains the types of request metadata, how to collect metadata with **WebGraphQlInterceptor**, how to put data into `GraphQLContext`, how to read it in handlers and services, along with principles for trust boundaries, lifecycle, and testing.

## 1. What is request metadata?

Request metadata is information accompanying a request that describes the processing context. It is generally not the business data that the client wants to query or mutate.

Examples:

| Metadata | Purpose |
|---|---|
| Correlation ID / request ID | Link logs and trace a single request across multiple components |
| Trace ID / span context | Track a request in distributed tracing |
| Locale / language preference | Choose the language for messages or localized data |
| Tenant ID | Restrict data access within a single tenant |
| Principal / authentication | Identify the authenticated user or service |
| Client application ID | Identify the calling application if authenticated and assigned an identifier |
| API version / feature metadata | Select compatible behavior when the API has versioning or feature flags |

Metadata may be transmitted via HTTP headers, connection info, security context, or generated by a server-side gateway/interceptor. Not every value sent by a client is trustworthy; the server must validate and normalize it before use.

### Metadata differs from GraphQL arguments

Arguments are part of the schema and operation:

~~~graphql
type Query {
  books(status: BookStatus, first: Int): [Book!]!
}
~~~

The client passes `status` and `first` to specify the business data to retrieve.

Metadata typically resides outside the GraphQL document, for example:

~~~http
POST /graphql
Content-Type: application/json
X-Correlation-Id: req-8f3a
Accept-Language: vi-VN
Authorization: Bearer <token>
~~~

The correlation ID, language, and credentials describe the request context. They do not need to be repeated as arguments on every field.

## 2. Layers of metadata in a GraphQL request

Metadata can be distinguished by where it is created and its scope of use:

| Layer | Examples | Scope |
|---|---|---|
| Transport metadata | HTTP headers, URI, cookies, remote address | Transport-dependent |
| Verified request metadata | Valid correlation ID, tenant derived from principal | Single request |
| Execution context | `GraphQLContext` holding tenant, locale, correlation ID | Single GraphQL execution |
| Field-local context | Data needed only for one field branch | One branch of the resolution tree |
| Business input | Filters, IDs, pagination arguments | Specific field or operation |

In an HTTP application, **WebGraphQlRequest** exposes request details at the web layer. **WebGraphQlInterceptor** can read headers and prepare the execution input. Afterward, `GraphQLContext` is the right place to share verified values with DataFetchers and annotated controllers.

If the application supports multiple transports such as HTTP, WebSocket, or RSocket, each transport may have its own metadata. Translate truly shared values into `GraphQLContext` or an application-layer abstraction instead of coupling services to `WebGraphQlRequest`.

## 3. Lifecycle of request metadata

A typical HTTP processing flow:

~~~mermaid
flowchart TD
    A[HTTP request] --> B[WebGraphQlInterceptor]
    B --> C[Read headers and request metadata]
    C --> D[Validate / normalize / enrich metadata]
    D --> E[configureExecutionInput]
    E --> F[GraphQLContext]
    F --> G[GraphQL execution]
    G --> H[Controller / DataFetcher]
    H --> I[Service and repository]
    I --> J[GraphQL response]
~~~

Main steps:

1. The client sends the GraphQL document, variables, and transport headers.
2. The interceptor reads metadata at the web layer.
3. The server verifies trusted values, generates missing values, and normalizes formats.
4. The interceptor adds metadata to the execution's `GraphQLContext`.
5. Resolvers read the context as needed.
6. Metadata is used within the operation scope and does not become shared state across requests.

`GraphQLContext` propagates data per execution explicitly. It avoids forcing resolvers to pull data from servlet requests or relying on `ThreadLocal`, which easily leads to bugs in async/reactive processing.

## 4. Reading HTTP headers with WebGraphQlInterceptor

Spring for GraphQL provides **WebGraphQlInterceptor** to intercept requests/responses at the web transport layer.

Example: an interceptor reading correlation ID and language:

~~~java
import java.util.Locale;
import java.util.UUID;

import org.springframework.graphql.server.WebGraphQlInterceptor;
import org.springframework.graphql.server.WebGraphQlRequest;
import org.springframework.graphql.server.WebGraphQlResponse;
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;
import reactor.core.publisher.Mono;

@Component
public class RequestMetadataInterceptor implements WebGraphQlInterceptor {

    @Override
    public Mono<WebGraphQlResponse> intercept(
            WebGraphQlRequest request,
            Chain chain) {

        String correlationId =
                request.getHeaders().getFirst("X-Correlation-Id");

        if (!StringUtils.hasText(correlationId)) {
            correlationId = UUID.randomUUID().toString();
        }

        Locale locale = request.getHeaders()
                .getAcceptLanguageAsLocales()
                .stream()
                .findFirst()
                .orElse(Locale.ENGLISH);

        String requestId = correlationId;

        request.configureExecutionInput((input, builder) ->
                builder.graphQLContext(context -> {
                    context.put("correlationId", requestId);
                    context.put("locale", locale);
                }).build());

        return chain.next(request);
    }
}
~~~

In this example:

- **request.getHeaders()** reads HTTP headers.
- **X-Correlation-Id** is used if it has a valid value per application policy; otherwise, the server generates a new ID.
- **Accept-Language** is converted into a `Locale`.
- **configureExecutionInput** adds metadata to `GraphQLContext` before the operation runs.
- **chain.next(request)** continues the GraphQL processing chain.

The example focuses on interceptor structure. In production, an external correlation ID should be length-limited and checked for allowed characters before being written to logs or tracing. Locale should also be constrained to the languages supported by the application.

### How is an interceptor registered?

When an interceptor is a Spring bean, Spring for GraphQL's configuration discovers it and includes it in the web transport interceptor chain. You can use bean ordering such as **@Order** if the application has multiple interceptors and needs a defined processing order.

Example:

~~~java
@Component
@Order(10)
public class RequestMetadataInterceptor implements WebGraphQlInterceptor {
    // ...
}
~~~

Ordering should reflect dependencies between interceptors. For example, authentication must run before an interceptor that builds tenant context if the tenant is derived from the principal.

## 5. Putting metadata into GraphQLContext

`GraphQLContext` is a context map attached to a single GraphQL execution. An interceptor can add values via the `ExecutionInput` builder:

~~~java
request.configureExecutionInput((input, builder) ->
        builder.graphQLContext(context -> {
            context.put("correlationId", correlationId);
            context.put("tenantId", tenantId);
            context.put("locale", locale);
        }).build());
~~~

The keys in the example are application-defined conventions. Group them into constants to avoid typos:

~~~java
public final class GraphQlContextKeys {

    public static final String CORRELATION_ID = "correlationId";
    public static final String TENANT_ID = "tenantId";
    public static final String LOCALE = "locale";

    private GraphQlContextKeys() {
    }
}
~~~

Then:

~~~java
context.put(GraphQlContextKeys.CORRELATION_ID, correlationId);
context.put(GraphQlContextKeys.TENANT_ID, tenantId);
context.put(GraphQlContextKeys.LOCALE, locale);
~~~

`GraphQLContext` is shared within the execution scope so DataFetchers can access it. Do not store mutable data shared across multiple requests in a static map or a singleton field of an interceptor.

### Choosing data types for context

Put clear, well-typed objects into the context:

- `String` for a normalized correlation ID or tenant ID.
- `Locale` for language.
- Verified `Principal` or authentication object when needed.
- An immutable request metadata record if there are multiple related attributes.

Example record:

~~~java
public record RequestMetadata(
        String correlationId,
        String tenantId,
        Locale locale) {
}
~~~

The interceptor can store a single `RequestMetadata` object instead of multiple separate keys. This keeps related values together and reduces the risk of missing keys or inconsistent updates.

## 6. Reading metadata in an annotated controller with @ContextValue

Spring for GraphQL provides **@ContextValue** to retrieve a value from `GraphQLContext`:

~~~java
@Controller
public class BookController {

    private final BookService bookService;

    public BookController(BookService bookService) {
        this.bookService = bookService;
    }

    @QueryMapping
    public List<Book> books(
            @ContextValue("tenantId") String tenantId,
            @ContextValue("locale") Locale locale) {

        return bookService.findBooks(tenantId, locale);
    }
}
~~~

The parameters above are not GraphQL arguments. They come from the `GraphQLContext` prepared by the interceptor.

If the context stores a record:

~~~java
@QueryMapping
public List<Book> books(
        @ContextValue("requestMetadata") RequestMetadata metadata) {

    return bookService.findBooks(
            metadata.tenantId(),
            metadata.locale());
}
~~~

Use a required context value when the handler cannot operate safely without the metadata. If a value is genuinely optional, declare explicit handling for the absent case instead of silently falling back to a default that could produce the wrong tenant or permissions.

## 7. Reading GraphQLContext directly in a DataFetcher

When multiple values are needed or when accessing context in a custom DataFetcher, you can accept **DataFetchingEnvironment**:

~~~java
@QueryMapping
public List<Book> books(
        DataFetchingEnvironment environment) {

    GraphQLContext context = environment.getGraphQlContext();

    String correlationId = context.get("correlationId");
    String tenantId = context.get("tenantId");

    return bookService.findBooks(tenantId);
}
~~~

`GraphQLContext` can also be retrieved from the corresponding GraphQL Java execution context API. In annotated controllers, **@ContextValue** usually makes method signatures easier to read if only a few keys are needed.

Do not pass the entire `DataFetchingEnvironment` down into services. Services should accept business data or a plain Java request context, such as tenant ID and actor ID, instead of depending on GraphQL Java.

## 8. Tenant metadata and trust boundaries

Tenant ID is metadata that directly affects which data a user is allowed to access. Therefore, the server must determine the tenant from a trusted source.

Do not blindly trust a header:

~~~http
X-Tenant-Id: tenant-admin
~~~

Clients can modify headers themselves. If the server uses this value directly in repository queries, a user could access another tenant's data.

More trustworthy sources for determining the tenant can include:

- A tenant claim inside an authenticated token whose signature has been verified.
- A tenant associated with the principal in the identity system.
- A host/subdomain routed by a trusted gateway and verified by the server.
- A server-side mapping between the authenticated client and authorized tenants.

For example, an interceptor or security component can derive the tenant from the authenticated principal:

~~~java
String tenantId = tenantResolver.resolveFromAuthentication(authentication);
~~~

Only then add it to `GraphQLContext`:

~~~java
request.configureExecutionInput((input, builder) ->
        builder.graphQLContext(context ->
                context.put("tenantId", tenantId))
            .build());
~~~

The service still needs to apply the tenant filter in data queries. Having `tenantId` in context only supplies information; it does not automatically isolate the database or guarantee authorization.

If the application allows a principal to access multiple tenants, verify that the chosen tenant is within the principal's authorized scope before putting it into context.

## 9. Correlation ID and logging

Correlation ID helps link logs from multiple processing layers of the same request:

~~~java
@QueryMapping
public Book book(
        @Argument String id,
        @ContextValue("correlationId") String correlationId) {

    log.info("Resolving book id={} correlationId={}", id, correlationId);
    return bookService.findById(id);
}
~~~

In practice, avoid forcing every resolver to accept `correlationId` if your logging infrastructure already manages trace context. You can use a logging context or tracing integration to attach IDs to logs consistently.

Distinguish:

- **Correlation ID**: application-level identifier used to link logs or events of one request.
- **Trace ID**: trace identifier in distributed tracing.
- **Span ID**: identifier of a unit of work within a trace.

These three values may be linked, but they do not have to be identical. If your application already uses Micrometer Tracing or OpenTelemetry, leverage the trace context instead of building a parallel tracing system.

### Rules when accepting a correlation ID from clients

- Enforce a maximum length.
- Allow only a safe character set.
- Never use this value as authorization data.
- Never interpolate arbitrary content into log format strings.
- Generate a new ID if the supplied value is invalid.
- If the ID needs to be returned to the client, use a response header or response metadata per transport design.

A correlation ID is an observability tool, not a credential.

## 10. Locale and display language

A client can send:

~~~http
Accept-Language: vi-VN,vi;q=0.9,en;q=0.8
~~~

The interceptor reads the locale and places it into `GraphQLContext`. Resolvers or services can use the locale to:

- Select translated content.
- Format business error messages.
- Format dates/times or monetary values at the presentation layer.
- Select localized records when the domain stores multiple languages.

Do not use locale to alter core business values. For instance, prices should be returned as numeric amounts and currency codes; the client can format them by locale, or the server can provide a dedicated presentation field.

A locale received from `Accept-Language` should be matched against supported locales. If unsupported, the server should select an explicit fallback.

Example resolver:

~~~java
@QueryMapping
public Product product(
        @Argument String id,
        @ContextValue("locale") Locale locale) {

    return productService.findLocalized(id, locale);
}
~~~

## 11. Authentication and Principal

Authentication is usually handled by Spring Security before or within the request processing chain. A request metadata interceptor can use verified authentication details to place the actor or tenant into `GraphQLContext`.

If a handler only needs the principal, Spring for GraphQL can inject **Principal** as a method argument when the security integration provides it:

~~~java
@QueryMapping
public List<Book> myBooks(Principal principal) {
    return bookService.findOwnedBy(principal.getName());
}
~~~

Do not parse raw tokens from the `Authorization` header manually inside each resolver. The authentication filter/security infrastructure is responsible for validating credentials; resolvers and services consume the verified principal.

Likewise, do not put raw bearer tokens into `GraphQLContext` unless there is a specific requirement. Tokens are secrets; copying them into context, logs, or downstream requests increases credential exposure risk.

## 12. Metadata in async and reactive execution

A GraphQL handler can return `CompletionStage`, `Mono`, or `Publisher`. Execution may switch threads or continue asynchronously.

`GraphQLContext` is bound to the execution, so DataFetchers can retrieve metadata from context within the execution scope without relying on `ThreadLocal`.

Example:

~~~java
@QueryMapping
public Mono<List<Book>> books(
        @ContextValue("tenantId") String tenantId) {

    return bookService.findBooksReactive(tenantId);
}
~~~

Do not assume `ThreadLocal` or MDC automatically survives when a reactive pipeline switches threads. If using logging context, configure propagation matching your tracing/logging stack. `GraphQLContext` is suited for passing metadata needed by resolvers; tracing context should be managed by your tracing integration.

When calling external services, pass only the required values via request objects or controlled headers. Do not pass the entire `GraphQLContext` down to every service, as it may contain data intended only for GraphQL execution.

## 13. Transport-specific metadata and multi-transport extensibility

**WebGraphQlInterceptor** applies to web transports. If the application also supports RSocket or WebSocket, inspect the corresponding interceptor and metadata model for that transport.

Not all metadata can be transferred verbatim across transports:

| Metadata | HTTP | WebSocket/RSocket |
|---|---|---|
| HTTP headers | Present | May only be present at handshake or setup |
| Connection metadata | Not a general concept | May exist per transport |
| Principal | Available via security integration | Available if provided by transport/security |
| Correlation ID | Can come from header | Can come from handshake or be generated on server |
| Locale | Can come from `Accept-Language` | Needs an equivalent convention |
| GraphQLContext | Available during execution | Available during execution |

If business logic needs tenant or actor, translate them into shared types at the application layer. Do not couple services to HTTP headers or WebSocket sessions.

## 14. Distinguishing GraphQLContext and local context

`GraphQLContext` holds metadata shared across an entire execution. Local context is passed from a parent field to child fields within its branch.

| Criterion | GraphQLContext | Local context |
|---|---|---|
| Scope | Entire execution | Field branch |
| Source | `ExecutionInput`/context setup | Parent field's `DataFetcherResult` |
| Example | Correlation ID, tenant, locale, actor | Display options or branch-specific auxiliary data |
| How read in controller | `@ContextValue` | `@LocalContextValue` |

Do not place request metadata such as correlation ID into local context, because other branches also need it. Conversely, data meaningful only in a single branch should not be put into the shared `GraphQLContext` unnecessarily.

## 15. Testing request metadata

To verify that an interceptor reads HTTP headers and puts data into `GraphQLContext`, test through the web transport. A test that only invokes `GraphQlService` or an execution-level `GraphQlTester` directly may bypass `WebGraphQlInterceptor`.

For HTTP, you can use **HttpGraphQlTester** with `WebTestClient` and set headers before sending the operation:

~~~java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class RequestMetadataTest {

    @LocalServerPort
    int port;

    @Test
    void shouldMakeCorrelationIdAvailableToResolver() {
        WebTestClient webTestClient = WebTestClient.bindToServer()
                .baseUrl("http://localhost:" + port)
                .defaultHeader("X-Correlation-Id", "test-request-123")
                .defaultHeader("Accept-Language", "vi-VN")
                .build();

        HttpGraphQlTester tester = HttpGraphQlTester.create(webTestClient);

        tester.document("""
                query {
                    requestMetadata {
                        correlationId
                        language
                    }
                }
                """)
            .execute()
            .path("requestMetadata.correlationId")
            .entity(String.class)
            .isEqualTo("test-request-123");
    }
}
~~~

This example assumes the application has a test-only `requestMetadata` field to observe metadata. Do not expose such debug fields in a production schema unless there is a genuine API requirement.

You should verify:

1. A valid correlation ID header is placed into context.
2. Missing or invalid headers are handled via fallback.
3. `Accept-Language` is normalized and falls back properly.
4. Tenant is derived from an authenticated source, without trusting arbitrary tenant headers.
5. Principal matches the logged-in user.
6. Concurrent requests do not share `GraphQLContext`.
7. Async resolvers still read metadata properly.
8. Metadata does not appear in logs if it contains sensitive information.
9. Interceptors execute in the intended order.
10. Different transports produce the same metadata abstraction if multiple transports are supported.

If you need to test `GraphQLContext` without testing HTTP headers, you can use `GraphQlTester` at the execution layer and configure the execution input/context directly. Clearly distinguish interceptor tests from resolver tests.

## 16. Common mistakes when handling request metadata

| Symptom | Possible cause | How to fix |
|---|---|---|
| `@ContextValue` cannot find key | Interceptor did not add the key or key name mismatch | Use context key constants and inspect the interceptor |
| Header has a value but resolver receives null | Metadata was not transferred into `GraphQLContext` | Check `configureExecutionInput` |
| Tenant can be spoofed by client | Blindly trusting `X-Tenant-Id` | Derive tenant from authentication or a trusted source |
| Correlation ID missing in logs | No fallback generated or logging context not propagated | Generate server-side ID and configure tracing/logging |
| Incorrect locale | `Accept-Language` not parsed or missing fallback | Normalize locale and restrict to supported locales |
| Context leaks between requests | Using static map or singleton mutable state | Use per-execution `GraphQLContext` |
| Metadata lost in reactive callbacks | Relying on `ThreadLocal`/MDC | Pass context explicitly and configure propagation |
| Service depends on HTTP APIs | Passing `WebGraphQlRequest` deep into application layer | Convert metadata into plain Java request context/command |
| Raw token logged | Putting credentials into context or logging all headers | Never log secrets and only pass needed values |
| Test does not run interceptor | Using an execution-layer tester instead of web transport | Use `HttpGraphQlTester` or appropriate transport tester |

## 17. Workflow for implementing request metadata

When an application needs request metadata:

1. Identify metadata needed for observability, localization, tenancy, or authentication.
2. Choose metadata sources: headers, security principal, gateway, or server.
3. Classify which sources are trusted and which require validation/normalization.
4. Use **WebGraphQlInterceptor** to read metadata on the web transport.
5. Provide fallbacks for optional values such as correlation ID or locale.
6. Put verified metadata into `GraphQLContext` via `configureExecutionInput`.
7. Use **@ContextValue** or `DataFetchingEnvironment` to read it in resolvers.
8. Convert needed values into a plain Java request context/command before calling services.
9. Enforce tenant and actor authorization at the service/data access layer.
10. Never store request state in singletons or static mutable state.
11. Test through the real transport and confirm no context sharing across requests.
12. Track correlation/tracing without logging credentials or sensitive data.

Request metadata enriches GraphQL execution with context without bloating the schema with repeated arguments across many fields. In Spring for GraphQL, `WebGraphQlInterceptor` is the right place to read HTTP metadata, validate it, and put required values into `GraphQLContext`. Resolvers can obtain them via `@ContextValue` or `DataFetchingEnvironment`, while services should receive plain Java data. Take special care to protect tenant and identity, scope context to each execution, and test through the real transport to ensure metadata propagates accurately.
