# application/graphql-response+json

## Objectives

After this lesson, you will be able to:

- Explain the meaning of the `application/graphql-response+json` media type.
- Distinguish the request media type from the response media type.
- Use the `Accept` header to request a GraphQL response in the dedicated format.
- Understand the differences between `application/graphql-response+json` and legacy `application/json`.
- Distinguish GraphQL request errors, execution errors, and HTTP transport errors.
- Read HTTP status codes together with the GraphQL response body accurately.
- Understand how Spring for GraphQL supports this media type and what to verify per version.
- Test content negotiation, response bodies, and HTTP statuses using `WebTestClient` and `HttpGraphQlTester`.

## 1. Why do we need application/graphql-response+json?

GraphQL defines a request and response structure, but GraphQL itself does not require HTTP. When exposed over HTTP, the server needs a media type so clients can recognize that the response content is a GraphQL result.

Previously, many GraphQL servers used `application/json` for responses. That JSON could contain a GraphQL result, yet clients could not rely solely on the media type to distinguish it from a JSON error generated by a proxy, API gateway, or middleware.

For example, a client sends a GraphQL query, but the gateway returns JSON:

~~~json
{
  "error": "upstream unavailable"
}
~~~

If both GraphQL responses and infrastructure errors use `application/json`, clients need extra logic to guess whether the received payload is a GraphQL response.

The `application/graphql-response+json` media type solves this identification problem. When a response has:

~~~http
Content-Type: application/graphql-response+json
~~~

the client knows the body is declared as a GraphQL-over-HTTP response and can process it according to the GraphQL structure, even when the HTTP status is not in the 2xx range.

This media type is a dedicated JSON response format for GraphQL. It does not invent an entirely new body structure; the key point is the meaning of the response media type and how it pairs with HTTP status codes.

## 2. This is a response media type, not a request media type

Distinguish the two headers clearly:

- `Content-Type` describes the format of the body the client sends.
- `Accept` describes the response format the client wants to receive.

For standard HTTP GraphQL JSON, the request still uses:

~~~http
Content-Type: application/json
~~~

And the client requests the dedicated response with:

~~~http
Accept: application/graphql-response+json
~~~

Example of a complete request:

~~~http
POST /graphql HTTP/1.1
Content-Type: application/json
Accept: application/graphql-response+json

{
  "query": "query BookById($id: ID!) { book(id: $id) { id title } }",
  "operationName": "BookById",
  "variables": {
    "id": "b-01"
  }
}
~~~

Do not send `Content-Type: application/graphql-response+json` just because you want to receive a response with that media type. According to GraphQL-over-HTTP, `application/graphql-response+json` is a JSON response media type; standard JSON request bodies are still sent as `application/json`.

## 3. Requesting the response via Accept

Clients inform the server of acceptable response media types through the `Accept` header.

To prefer the new media type while remaining compatible with legacy servers/clients, you can send:

~~~http
Accept: application/graphql-response+json, application/json;q=0.9
~~~

Meaning:

- `application/graphql-response+json` has the highest default priority.
- `application/json;q=0.9` is a lower-priority compatibility fallback.
- The server picks an appropriate media type based on content negotiation and support.

If the client only accepts the new media type:

~~~http
Accept: application/graphql-response+json
~~~

the server should return that media type if supported. If none of the server's response media types are acceptable to the client, the server can reject content negotiation with `406 Not Acceptable` per GraphQL-over-HTTP rules.

If the client does not send `Accept`, the server may pick a default media type depending on the implementation. For predictable behavior across environments, clients should send `Accept` explicitly.

## 4. The GraphQL response structure is still JSON

A response with `application/graphql-response+json` still uses the familiar GraphQL result structure.

When an operation executes successfully:

~~~http
HTTP/1.1 200 OK
Content-Type: application/graphql-response+json; charset=utf-8
~~~

~~~json
{
  "data": {
    "book": {
      "id": "b-01",
      "title": "GraphQL in Practice"
    }
  }
}
~~~

When a field fails during execution, but GraphQL can still produce a result:

~~~http
HTTP/1.1 200 OK
Content-Type: application/graphql-response+json; charset=utf-8
~~~

~~~json
{
  "data": {
    "book": null
  },
  "errors": [
    {
      "message": "Book was not found",
      "path": ["book"],
      "extensions": {
        "code": "BOOK_NOT_FOUND"
      }
    }
  ]
}
~~~

When GraphQL cannot start execution due to an invalid document, the response may contain only `errors` with no `data` key:

~~~http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/graphql-response+json; charset=utf-8
~~~

~~~json
{
  "errors": [
    {
      "message": "Cannot query field 'unknownField' on type 'Query'."
    }
  ]
}
~~~

The body structure helps clients distinguish request errors from execution results. HTTP status codes add transport-layer and observability information.

## 5. Difference between request errors and execution errors

To understand this media type, distinguish two error categories relative to GraphQL execution.

### Request errors

Request errors prevent GraphQL from executing the operation. Examples:

- GraphQL document fails to parse.
- Field does not exist in the schema.
- Argument has the wrong type.
- Variable cannot be coerced per its declaration.
- Target operation to execute cannot be determined.

In this case, the GraphQL error response result has no `data` key. With `application/graphql-response+json`, the GraphQL-over-HTTP specification guides servers to use an appropriate 4xx or 5xx HTTP status corresponding to the cause.

Examples:

| Cause | Typical HTTP status per spec |
|---|---:|
| Malformed JSON request body | 400 |
| GraphQL document parse failure | 400 |
| GraphQL validation failure | 422 |
| Variable coercion failure | 422 |
| Operation cannot be determined | 422 |
| Request uses an unsupported `Content-Type` | 415 |
| `Accept` has no matching media type | 406 |
| Client is unauthenticated | 401 |
| Client lacks permission to call the endpoint | 403 |

This is guidance from the GraphQL-over-HTTP specification; applications must verify the actual behavior of their server and framework version.

### Execution errors

Execution errors arise after the operation has passed parsing and validation and begun executing. Examples:

- Resolver cannot find the data.
- Database or downstream service encounters an error.
- A field is denied by authorization.
- Custom scalar fails to serialize a return value.

GraphQL can return partial data alongside `errors`:

~~~json
{
  "data": {
    "book": {
      "id": "b-01",
      "title": "GraphQL in Practice",
      "author": null
    }
  },
  "errors": [
    {
      "message": "Author is not available",
      "path": ["book", "author"]
    }
  ]
}
~~~

This is still a GraphQL execution result. Clients should inspect `data` and `errors` rather than treating every response containing `errors` as a complete request failure.

## 6. The new media type changes how HTTP status codes are used

A key benefit of `application/graphql-response+json` is that servers can use more meaningful HTTP status codes.

According to the GraphQL-over-HTTP September 2026 Edition:

| GraphQL result | Status code guidance |
|---|---|
| Has non-null `data`, no errors | SHOULD return 200 |
| Has non-null `data` and has errors | MUST return 2xx |
| Has both `data` key (even if null) and `errors` | SHOULD return 294 Partial Success |
| No `data` key due to request error | Appropriate 4xx or 5xx |
| Cannot produce a valid GraphQL-over-HTTP response | Appropriate 4xx or 5xx; do not use the GraphQL response media type |

`294 Partial Success` is the status code recommended by this edition of the specification when GraphQL has both `data` and `errors`. It is a custom code described in the specification, not yet a widely registered standard HTTP status code. Proxies, gateways, monitoring tools, and clients must be checked before relying on this code.

What matters for clients is: when receiving `application/graphql-response+json`, process the body as a valid GraphQL response regardless of status code. Status codes are useful for logging, metrics, gateways, and operational observability; the body provides the detailed GraphQL result.

## 7. Comparison with legacy application/json

`application/json` is still supported by many systems for compatibility. However, traditional HTTP status behavior can differ from the newer media type.

| Criterion | Legacy `application/json` | `application/graphql-response+json` |
|---|---|---|
| Purpose | Legacy-style JSON response | Dedicated media type for GraphQL responses |
| Identifying GraphQL responses | Ambiguous from media type alone | Explicit via `Content-Type` |
| Parse/validation error | Many older servers return 200 | Can use 4xx |
| Execution error | Typically 200 with errors | Can use status per GraphQL-over-HTTP |
| Proxy/monitoring compatibility | Hard to separate GraphQL errors from intermediary errors | Easier to identify GraphQL responses |
| Recommendation | Use when legacy client support is needed | Prefer for modern clients |

Do not conclude that every server using `application/json` behaves identically. This table summarizes the design differences and common compatibility behaviors; the final status code depends on the implementation.

## 8. Spring for GraphQL support for this media type

Spring for GraphQL supports `application/graphql-response+json` in its HTTP transport. According to the current Server Transports documentation:

- HTTP request bodies default to `application/json`.
- Clients can request `application/graphql-response+json` via `Accept`.
- If the client expresses no preference, Spring selects the newer media type as the response content type.
- Clients can still request `application/json` to receive legacy HTTP behavior.
- When using the newer media type, GraphQL document parse or validation errors are returned with HTTP 4xx.
- With legacy `application/json`, those parse/validation errors still return HTTP 200.
- Once a GraphQL request has been validated successfully, Spring documentation describes the HTTP status as 200 even when execution has errors; errors appear in the `errors` section of the response.

This last point deserves attention when comparing with the GraphQL-over-HTTP September 2026 Edition. The newer specification recommends status 294 for responses containing both `data` and `errors`, whereas current Spring for GraphQL 2.1.0 documentation describes status 200 for all post-validation execution results. Therefore, do not assume Spring automatically returns 294 simply because the client requests the newer media type.

If strict compliance with a specific GraphQL-over-HTTP edition's status mapping is required, check your Spring for GraphQL version, test the endpoint, and evaluate whether customizing the HTTP handler is necessary. Do not change status codes arbitrarily without verifying compatibility across clients, proxies, and API gateways.

## 9. Sending requests to a Spring endpoint with curl

Example requesting the newer response media type:

~~~bash
curl -i http://localhost:8080/graphql \
  -X POST \
  -H "Content-Type: application/json" \
  -H "Accept: application/graphql-response+json" \
  -d '{
    "query": "query BookById($id: ID!) { book(id: $id) { id title } }",
    "operationName": "BookById",
    "variables": {
      "id": "b-01"
    }
  }'
~~~

Points to inspect in the response:

~~~http
HTTP/1.1 200 OK
Content-Type: application/graphql-response+json
~~~

- Status code returned matches the behavior of the running Spring version.
- `Content-Type` is compatible with the media type requested by the client.
- Body follows the GraphQL result structure.
- If errors exist, inspect `path` and `extensions` as well.

To check legacy behavior:

~~~bash
curl -i http://localhost:8080/graphql \
  -X POST \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "query": "{ unknownField }"
  }'
~~~

In Spring for GraphQL per current documentation, parse/validation errors in the legacy `application/json` case are still returned with status 200. This is one reason modern clients should prefer the dedicated media type.

## 10. Content negotiation when a client supports both media types

A client may need compatibility with older servers while preferring the newer response media type.

Example:

~~~http
Accept: application/graphql-response+json, application/json;q=0.9
~~~

Cases to test:

| Accept | Goal |
|---|---|
| `application/graphql-response+json` | Accept only the newer response media type |
| `application/json` | Request legacy behavior |
| `application/graphql-response+json, application/json;q=0.9` | Prefer newer media type, fall back to legacy |
| `application/xml` | No acceptable GraphQL JSON media type |

When client and server cannot agree on a media type, content negotiation can fail. Under GraphQL-over-HTTP, `406 Not Acceptable` is the appropriate status when the server cannot satisfy the `Accept` header per deployment policy.

If a client uses fallback, check the actual response `Content-Type` rather than assuming the server always chose the first media type.

## 11. How should clients handle responses?

With the newer media type, clients should not stop processing just because `response.ok` is false. A GraphQL request error can be represented as HTTP 4xx accompanied by a valid GraphQL body.

A general handling strategy:

1. Read the HTTP status and `Content-Type`.
2. If `Content-Type` is `application/graphql-response+json`, parse the body according to the GraphQL response format even when status is 4xx.
3. Check the `data` key to see whether the operation produced an execution result.
4. Check `errors` to handle request errors or per-field errors.
5. Use `path` to identify which field failed.
6. Use codes in `extensions` if the server publishes stable error codes.
7. If the response does not have a GraphQL media type, treat it as an HTTP/intermediary error and do not assume the body is a GraphQL result.

Client-side JavaScript example:

~~~javascript
const response = await fetch("/graphql", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Accept": "application/graphql-response+json, application/json;q=0.9"
  },
  body: JSON.stringify({
    query: "query { book(id: \"b-01\") { id title } }"
  })
});

const contentType = response.headers.get("Content-Type") ?? "";

if (contentType.includes("application/graphql-response+json")) {
  const result = await response.json();

  if (result.errors?.length) {
    console.error("GraphQL errors:", result.errors);
  }

  if (result.data !== undefined) {
    renderBook(result.data);
  }
} else {
  const body = await response.text();
  throw new Error(
    `HTTP ${response.status}: ${body}`
  );
}
~~~

This example illustrates the processing flow. In real applications, also handle empty bodies, invalid JSON, network errors, and media types with parameters such as `charset=utf-8`. Parse the media type rather than relying solely on rigid string comparisons.

## 12. Testing media types with WebTestClient

`HttpGraphQlTester` is helpful for asserting GraphQL response content. When you need to verify exact HTTP status codes and headers, use `WebTestClient` directly.

Example testing success:

~~~java
@Test
void shouldReturnGraphQlResponseJson() {
    webTestClient.post()
            .uri("/graphql")
            .contentType(MediaType.APPLICATION_JSON)
            .accept(MediaType.parseMediaType(
                    "application/graphql-response+json"))
            .bodyValue(Map.of(
                    "query", """
                            { book(id: "b-01") { id title } }
                            """))
            .exchange()
            .expectStatus().isOk()
            .expectHeader().contentTypeCompatibleWith(
                    MediaType.parseMediaType(
                            "application/graphql-response+json"))
            .expectBody()
            .jsonPath("$.data.book.id").isEqualTo("b-01");
}
~~~

Example testing a validation error under the newer media type behavior:

~~~java
@Test
void shouldUseClientErrorForInvalidDocument() {
    webTestClient.post()
            .uri("/graphql")
            .contentType(MediaType.APPLICATION_JSON)
            .accept(MediaType.parseMediaType(
                    "application/graphql-response+json"))
            .bodyValue(Map.of(
                    "query", "{ unknownField }"))
            .exchange()
            .expectStatus().is4xxClientError()
            .expectHeader().contentTypeCompatibleWith(
                    MediaType.parseMediaType(
                            "application/graphql-response+json"))
            .expectBody()
            .jsonPath("$.errors").isArray();
}
~~~

These two tests verify the characteristics Spring describes in its current documentation: the new response media type is selected via `Accept`, and parse/validation errors can use HTTP 4xx.

You can configure `HttpGraphQlTester` with an `Accept` header:

~~~java
HttpGraphQlTester tester =
        HttpGraphQlTester.builder(webTestClient)
                .headers(headers -> headers.setAccept(List.of(
                        MediaType.parseMediaType(
                                "application/graphql-response+json"),
                        MediaType.APPLICATION_JSON)))
                .build();
~~~

Use the tester to check the GraphQL body:

~~~java
tester.document("""
        query {
          book(id: "b-01") {
            id
            title
          }
        }
        """)
        .execute()
        .path("book.id")
        .entity(String.class)
        .isEqualTo("b-01");
~~~

If you need to verify status 294 per the GraphQL-over-HTTP September 2026 Edition, write a separate test for an execution result containing both `data` and `errors`. Do not enforce that assumption on Spring if your current version follows status 200 after validation.

## 13. Impact on proxies, gateways, and observability

The newer media type is not just for clients. It also helps infrastructure components recognize GraphQL responses.

Benefits include:

- Access logs can distinguish GraphQL responses from ordinary JSON errors.
- API gateways can classify request errors and execution results based on status codes.
- Monitoring can track validation failures, partial responses, and server errors.
- Clients can parse GraphQL error responses even when the HTTP status is 4xx.
- Systems supporting multiple client versions can use content negotiation for gradual migration.

However, proxies or gateways may alter status codes, bodies, or `Content-Type`. Configure them to:

- Avoid replacing GraphQL responses with unintended HTML error pages.
- Preserve `application/graphql-response+json` when forwarding valid responses.
- Avoid rewriting every HTTP 4xx into 200.
- Avoid retrying mutations solely because the response is 4xx/5xx when it is unknown whether the operation already ran.
- Account for custom status codes like 294 if the application chooses to use them.

If a response carries the GraphQL media type but a proxy rewrote the body into different JSON, clients could misinterpret the payload. Therefore, test end-to-end through your actual gateway/proxy, not only directly against the application server.

## 14. Security and error data

The media type does not provide authentication or authorization by itself. It only identifies the response type and supports HTTP semantics.

When returning GraphQL errors:

- Never send stack traces or SQL queries to clients.
- Never include access tokens, session IDs, or secrets in `extensions`.
- Expose only error codes and field paths that clients need.
- Control logging of variables since they may contain personal data.
- Ensure proxies and caches do not share user-specific responses across users.
- Never treat `application/graphql-response+json` as proof that a request was authenticated.

The server still requires Spring Security, field/service authorization, and standard data-protection policies.

## 15. Common errors

| Symptom | Possible cause | How to handle |
|---|---|---|
| Response is still `application/json` | Client sent legacy `Accept` or server chose fallback | Check `Accept` and response `Content-Type` |
| Sending the new media type in request `Content-Type` fails | Confused response media type with request media type | Use request `Content-Type: application/json` |
| Client treats 422 as a network error | Client only parses body on 2xx status | Parse GraphQL responses whenever `Content-Type` matches |
| Parse/validation error still returns HTTP 200 | Client requested legacy `application/json` | Prefer `application/graphql-response+json` |
| Execution error still returns HTTP 200 on Spring | Behavior described in current Spring docs after validation | Read `errors` in the body and check your version |
| Client does not get the desired response media type | `Accept` header or q-value mismatch | Inspect content negotiation |
| Gateway returns HTML instead of GraphQL JSON | Middleware replaces responses on 4xx/5xx | Configure gateway to pass GraphQL responses through |
| Status 294 handled unexpectedly | Infrastructure does not recognize the custom status | Check clients, proxies, caches, and metrics |
| No GraphQL body present | Error occurred before building a valid response or middleware blocked the request | Inspect the actual HTTP status and `Content-Type` |

## 16. Implementation checklist

Before using `application/graphql-response+json` in production:

- [ ] POST requests still use `Content-Type: application/json`.
- [ ] Clients send `Accept: application/graphql-response+json`.
- [ ] Fallback `application/json` is included if legacy server support is needed.
- [ ] Clients inspect response `Content-Type` before parsing the body.
- [ ] Clients can parse GraphQL responses even when HTTP status is 4xx.
- [ ] Clients read both `data` and `errors`.
- [ ] Server returns status codes matching verified framework version behavior.
- [ ] Request errors and execution errors are separated in logging/metrics.
- [ ] Proxies/gateways do not unintentionally alter GraphQL responses.
- [ ] Caches do not leak user- or tenant-dependent responses.
- [ ] Tested successful responses, validation errors, and execution errors.
- [ ] If using status 294, all infrastructure has been verified for compatibility.

## Conclusion

`application/graphql-response+json` is the dedicated JSON media type for GraphQL responses. Clients request it via the `Accept` header, while standard JSON request bodies continue using `Content-Type: application/json`. This media type helps clients, proxies, and observability tools clearly recognize GraphQL responses while enabling more meaningful HTTP status codes than legacy `application/json`.

In Spring for GraphQL, the HTTP transport supports this media type. However, distinguish the behavior described in Spring documentation from the newer guidance in the GraphQL-over-HTTP September 2026 Edition, particularly regarding status codes for partial responses. Test on your actual deployment version, process bodies according to `Content-Type`, and read both `data` and `errors` for reliable client behavior.
