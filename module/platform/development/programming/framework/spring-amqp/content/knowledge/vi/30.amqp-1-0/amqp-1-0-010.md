# Chuyển đổi thông điệp và tương thích với broker AMQP 1.0 mục tiêu

**AMQP 0-9-1 và AMQP 1.0 là hai giao thức khác nhau**, dù có cùng tên AMQP. Khi học **SPRING_AMQP**, ta thường dùng `RabbitTemplate`, `@RabbitListener`, exchange, queue và binding để trao đổi message qua RabbitMQ bằng **AMQP 0-9-1**. Nếu hệ thống tích hợp cần gửi message tới một **broker AMQP 1.0**, chỉ thay host hoặc port của `RabbitTemplate` là chưa đủ: phải có client triển khai đúng giao thức, chuyển đổi thông điệp theo một hợp đồng chung và kiểm thử các đặc điểm của broker đích.

Bài thuộc chương **AMQP 1.0**, tập trung vào **chuyển đổi thông điệp và tương thích với broker AMQP 1.0 mục tiêu**. Ta sẽ xây mô hình message trung gian, ánh xạ payload/metadata, cấu hình Spring JMS với một client 1.0, nhận message, phân biệt acknowledgment/settlement, và thiết kế bridge có retry, dead-letter cùng idempotency. Vì đầu vào không chỉ định sản phẩm broker đích, cú pháp routing, policy DLQ, độ bền và semantics xác nhận phải được **xác minh trực tiếp trên broker được lựa chọn**.

## 1. Phân biệt hai phiên bản giao thức và đúng client Java

| Thành phần | Spring Rabbit / AMQP 0-9-1 | AMQP 1.0 |
|---|---|---|
| API Spring điển hình | `RabbitTemplate`, `@RabbitListener`, `RabbitAdmin` | Spring JMS (`JmsTemplate`, `@JmsListener`) với provider AMQP 1.0, hoặc native AMQP 1.0 client |
| Kết nối | `org.springframework.amqp.rabbit.connection.ConnectionFactory` | `jakarta.jms.ConnectionFactory` nếu dùng JMS |
| Đường gửi | `basic.publish` với exchange + routing key | Sender link và target address |
| Đường nhận | `basic.deliver` từ queue | Receiver link với source address, link credit |
| Định dạng message | BasicProperties + headers + body bytes | Sections: header, annotations, properties, application-properties, body, footer |
| Xác nhận ở consumer | `basic.ack`, `basic.nack`, `basic.reject` | Delivery disposition/settlement; JMS acknowledge/transaction được provider ánh xạ |
| Routing và dead-letter | Exchange/binding, DLX của RabbitMQ | Address, entity, subscription, DLQ tùy sản phẩm broker |
| Giao dịch | AMQP 0-9-1 `tx.select/commit/rollback` | Cơ chế khác; JMS local session transaction nếu broker/provider hỗ trợ |

Hai loại `ConnectionFactory` trên **không hoán đổi cho nhau** dù tên giống nhau. `RabbitTemplate` không thể tự trở thành native AMQP 1.0 producer bằng cách chọn một listener mới. Đồng thời, Spring JMS chỉ là API tích hợp: **giao thức thực tế do JMS provider đảm nhiệm**. Một JMS provider không sử dụng AMQP 1.0 sẽ không đáp ứng yêu cầu này.

Một số broker hỗ trợ đồng thời AMQP 0-9-1 và AMQP 1.0 trên cùng hạ tầng, một số broker chỉ hỗ trợ một giao thức hoặc giới hạn tính năng. Số cổng 5672 hoặc 5671 **không phải bằng chứng giao thức**; phải xác định endpoint AMQP 1.0 theo cấu hình broker.

### 1.1. Hai kiểu kiến trúc

**Ứng dụng gửi trực tiếp bằng AMQP 1.0**:

```text
OrderService -> CanonicalEvent -> AMQP 1.0 sender -> Broker 1.0
                     |                  |
                   JSON               JMS/native client
```

**Bridge giữa RabbitMQ AMQP 0-9-1 và broker AMQP 1.0**:

```text
RabbitMQ 0-9-1               Bridge application              AMQP 1.0 broker
orders.outbound ---> @RabbitListener ---> decode/validate    orders.intake
                           |                canonical             ^
                           |                  event               |
                           +------------> AMQP 1.0 sender --------+
                                            (JMS/native)

              ACK nguồn và kết quả gửi đích là hai bước độc lập
```

Một bridge đáng tin cậy không chỉ biết serialize JSON: nó phải xác định lúc nào ACK nguồn, cách retry khi đích không sẵn sàng và cách chống duplicate nếu broker nguồn giao lại.

## 2. Lập compatibility profile của broker đích trước khi triển khai

AMQP 1.0 định nghĩa protocol và message format, nhưng **không buộc mọi broker dùng cùng quy ước tên queue/topic, routing, bảo mật và dead-letter**. Cần ghi rõ:

| Năng lực | Câu hỏi cần trả lời |
|---|---|
| Listener/endpoint | Host, port, TLS/SASL và virtual host/namespace là gì? |
| Address | Target/source address là queue, topic, entity path hay broker-specific URI? |
| Provision | Destination được tạo tự động hay cần tạo trước bằng console/IaC/API? |
| Body | Broker/receiver hỗ trợ `Data` bytes, `AmqpValue` string, `AmqpSequence` như thế nào? |
| JMS mapping | Provider có tương thích với broker và bộ `jakarta.jms` của Spring đang dùng? |
| Metadata | `message-id`, `correlation-id`, `application-properties` được giữ nguyên kiểu hay chuyển đổi? |
| Settlement | Khi nào nhận `accepted`? Broker hỗ trợ reject/release/redelivery thế nào? |
| Durability | Persistent delivery, TTL, priority, quota, giới hạn kích thước, replication ra sao? |
| Retry/DLQ | Khi xử lý lỗi, message quay lại, bị loại hoặc chuyển tới dead-letter entity nào? |
| Transactions | Có hỗ trợ JMS transacted session/AMQP 1.0 transaction đúng cách không? |
| Observability | Có thể lấy delivery outcome, redelivery count, dead-letter reason và latency không? |

**Không suy diễn** rằng exchange + routing key của RabbitMQ 0-9-1 sẽ tự ánh xạ sang queue/topic trên broker AMQP 1.0. Quy ước định tuyến là quyết định của **broker mục tiêu**; cần kiểm tra trên hệ thống thật trước khi vận hành.

## 3. Cấu trúc message AMQP 1.0: cái gì được chuyển đổi?

Một AMQP 1.0 message có thể gồm các section:

```text
+-------------------------------------------------------------+
| Header                 durable, priority, ttl, delivery-count|
+-------------------------------------------------------------+
| Delivery Annotations   metadata gắn với việc chuyển delivery|
+-------------------------------------------------------------+
| Message Annotations    metadata AMQP/broker                  |
+-------------------------------------------------------------+
| Properties             message-id, correlation-id, to,      |
|                        reply-to, content-type, creation-time|
+-------------------------------------------------------------+
| Application-Properties key/value ứng dụng                    |
+-------------------------------------------------------------+
| Body                   Data | AmqpValue | AmqpSequence       |
+-------------------------------------------------------------+
| Footer                 metadata tùy cách dùng               |
+-------------------------------------------------------------+
```

**Body** có ba dạng đáng chú ý:

- `Data` chứa binary payload; thường phù hợp JSON dưới dạng UTF-8 bytes, Protobuf, Avro hoặc format nhị phân.
- `AmqpValue` chứa một giá trị AMQP, ví dụ string, map hay list.
- `AmqpSequence` chứa một chuỗi giá trị theo kiểu AMQP.

Hai producer cùng gửi nội dung `{"orderId":"O-1"}` chưa chắc tương thích nếu một bên tạo **`Data` bytes** còn receiver chỉ hỗ trợ **`AmqpValue` string**. Với JMS `TextMessage`, cách ánh xạ xuống section thực tế phụ thuộc provider; phải kiểm tra bằng native AMQP 1.0 receiver hoặc công cụ của broker.

### 3.1. Properties khác application-properties

| Trường AMQP 1.0 | Mục đích | Lưu ý |
|---|---|---|
| `properties.message-id` | ID message ở mức protocol | AMQP cho nhiều kiểu giá trị; không mặc định là chuỗi UUID |
| `properties.correlation-id` | Tương quan request/reply hoặc luồng nghiệp vụ | Phải thống nhất kiểu và encoding với receiver |
| `properties.to` | Địa chỉ mô tả bên nhận | Không thay thế việc chọn sender target link đúng |
| `properties.reply-to` | Địa chỉ phản hồi | Địa chỉ/authorization phụ thuộc broker |
| `properties.subject` | Subject của message | Không tương đương tự động với routing key 0-9-1 |
| `properties.content-type` | Ví dụ `application/json` | Phải khớp body encoding và decoder |
| `properties.content-encoding` | Encoding bổ sung (như compression) | Không tự suy từ charset của một String Java |
| `header.durable` | Mong muốn persistence theo giao thức | Mức bảo đảm thực tế phụ thuộc broker |
| `header.ttl` | Thời gian sống tương đối | Kiểm tra đơn vị và policy expiration |
| `application-properties` | Metadata ứng dụng có kiểu AMQP hợp lệ | Không gửi tùy ý một Java object phức tạp |

`Delivery annotations`, `message annotations` và các metadata nội bộ khác có thể được broker thêm/xóa/chỉnh sửa khi đi qua link; **không dùng chúng làm hợp đồng nghiệp vụ ổn định** nếu broker không cam kết.

## 4. Tạo canonical event độc lập với transport

Để tránh thiết kế domain dựa vào một Java client, định nghĩa JSON contract dùng được ở cả hai phía:

```json
{
  "eventId": "6b98254b-79d8-4e65-8d91-fdf471f7d609",
  "eventType": "OrderPlaced",
  "schemaVersion": 1,
  "aggregateId": "ORDER-190",
  "aggregateVersion": 1,
  "occurredAt": "2026-11-26T02:00:00Z",
  "data": {
    "totalMinor": 125000,
    "currency": "VND"
  }
}
```

Định nghĩa Java DTO:

```java
public record OrderPlacedEvent(
        UUID eventId,
        String eventType,
        int schemaVersion,
        String aggregateId,
        long aggregateVersion,
        Instant occurredAt,
        OrderData data) {

    public record OrderData(long totalMinor, String currency) {}
}
```

**Các quy tắc hợp đồng:**

1. `eventId` phải **giữ nguyên qua mọi lần retry, redelivery và bridge chuyển giao**. Nếu tạo UUID mới khi retry, consumer khó nhận diện duplicate.
2. `schemaVersion` mô tả định dạng JSON; `aggregateVersion` mô tả trình tự thay đổi của một aggregate. Không dùng hai giá trị thay thế nhau.
3. `eventType` phải thuộc một allowlist được consumer hỗ trợ; payload mới không được âm thầm giải mã như message cũ.
4. JSON UTF-8 là lựa chọn minh họa; không truyền Java `Serializable`/`ObjectMessage` xuyên hệ thống chỉ vì cả hai cùng chạy Java.
5. Các trường như `totalMinor`, `currency`, thời gian và trạng thái phải được định nghĩa rõ đơn vị, timezone và quy tắc nullable. Với số tiền, kiểm soát đơn vị nhỏ nhất giúp tránh sai số floating-point.
6. Metadata truyền qua header có thể là **bản sao để lọc/trace**, nhưng payload vẫn nên chứa ID/version bắt buộc để thích nghi giữa các client/broker.

### 4.1. Ánh xạ thuộc tính 0-9-1 sang 1.0

| Spring Rabbit / AMQP 0-9-1 | Đích AMQP 1.0 / JMS | Quy tắc |
|---|---|---|
| `messageProperties.messageId` | `message-id` hoặc `JMSMessageID` | Provider có thể tạo/chuyển ID; giữ `eventId` nghiệp vụ độc lập |
| `correlationId` | `correlation-id` hoặc `JMSCorrelationID` | Chuẩn hóa kiểu dữ liệu; test round-trip |
| `replyTo` | `reply-to` / `JMSReplyTo` | Chuyển đổi địa chỉ theo namespace broker đích |
| `contentType` | `properties.content-type` hoặc metadata tương ứng | Không nhầm JMS application property với AMQP `content-type` |
| `contentEncoding` | `content-encoding` nếu client hỗ trợ | Phân biệt charset/serialization và compression |
| `deliveryMode=PERSISTENT` | `header.durable` / JMS persistent delivery | Kiểm tra mức bảo đảm broker đích |
| `expiration`, `priority` | TTL, priority nếu được hỗ trợ | Kiểm tra đơn vị/giới hạn/policy |
| `timestamp` | `creation-time` hoặc field ứng dụng | Không dùng để bảo đảm thứ tự nghiệp vụ |
| `headers[eventType]` | `application-properties[eventType]` / JMS property | Chỉ cho phép các kiểu scalar được hỗ trợ |
| `x-death`, deliveryTag, consumerTag | **Không copy mặc định** | Metadata xử lý delivery riêng RabbitMQ |
| `exchange` + `routingKey` | Sender target address/JMS destination | **Không có công thức ánh xạ portable** |

Đặc biệt không copy các header nội bộ của Spring converter như `__TypeId__` thành hợp đồng bắt buộc cho receiver đa ngôn ngữ. Nếu cần tên event class, dùng `eventType` + `schemaVersion` có tài liệu rõ.

## 5. Lựa chọn Spring JMS + AMQP 1.0 provider

Một hướng triển khai phù hợp với ứng dụng Spring Boot là dùng **Spring JMS** và client triển khai AMQP 1.0, ví dụ **Apache Qpid JMS**. Spring JMS cung cấp `JmsTemplate` và `@JmsListener`, còn provider thực hiện kết nối, chuyển JMS message thành các section AMQP 1.0 và xử lý link/settlement.

Cần chú ý: Spring Framework 6/Spring Boot 3 dùng namespace **`jakarta.jms`**. Chọn bản JMS provider có hỗ trợ Jakarta tương ứng; thư viện chỉ triển khai `javax.jms` của thế hệ cũ sẽ không tương thích source/API.

### 5.1. Dependency và cấu hình endpoint

Những nhóm thư viện cần có:

- Spring JMS (`spring-jms` hoặc starter phù hợp stack đang dùng);
- JMS provider triển khai **AMQP 1.0** và `jakarta.jms.ConnectionFactory`;
- Jackson JSON;
- Spring AMQP/Rabbit chỉ khi ứng dụng đồng thời có đầu vào/đầu ra AMQP 0-9-1;
- Spring JDBC/JPA nếu xử lý idempotency hoặc outbox trong database.

Ví dụ `application.yml`:

```yaml
interop:
  amqp10:
    uri: "amqps://broker10.example.internal:5671"
    username: "integration-user"
    password: "REPLACE_USING_SECRET_MANAGER"
    destination: "orders.intake"
```

Cổng, URI scheme, SASL/TLS và destination chỉ để minh họa. **Không đưa mật khẩu thật vào repository**; production cần inject secret từ môi trường hoặc secret manager. Cấu hình phù hợp broker đích mới là nguồn sự thật.

### 5.2. Tạo bean connection và JMS template

Ví dụ cấu hình bằng `@ConfigurationProperties`, tránh nhầm với Spring Rabbit `ConnectionFactory`:

```java
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "interop.amqp10")
public record Amqp10Properties(
        String uri,
        String username,
        String password,
        String destination) {
}
```

```java
@Configuration
@EnableJms
@EnableConfigurationProperties(Amqp10Properties.class)
public class Amqp10JmsConfiguration {

    @Bean("amqp10JmsConnectionFactory")
    jakarta.jms.ConnectionFactory amqp10JmsConnectionFactory(
            Amqp10Properties props) {
        // Chọn Apache Qpid JMS artifact hỗ trợ Jakarta JMS.
        return new JmsConnectionFactory(
                props.username(), props.password(), props.uri());
    }

    @Bean("amqp10JmsTemplate")
    JmsTemplate amqp10JmsTemplate(
            @Qualifier("amqp10JmsConnectionFactory")
            jakarta.jms.ConnectionFactory connectionFactory) {
        JmsTemplate template = new JmsTemplate(connectionFactory);
        template.setExplicitQosEnabled(true);
        template.setDeliveryPersistent(true);
        return template;
    }

    @Bean("amqp10JmsListenerFactory")
    DefaultJmsListenerContainerFactory amqp10JmsListenerFactory(
            @Qualifier("amqp10JmsConnectionFactory")
            jakarta.jms.ConnectionFactory connectionFactory) {
        DefaultJmsListenerContainerFactory factory =
                new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setConcurrency("1-3");
        factory.setSessionTransacted(true);
        return factory;
    }
}
```

Import cần thiết:

```java
import org.apache.qpid.jms.JmsConnectionFactory;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.annotation.EnableJms;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;
import org.springframework.jms.core.JmsTemplate;
```

**Điều kiện áp dụng:** Phiên bản Qpid JMS cụ thể phải xuất kiểu `jakarta.jms.ConnectionFactory` tương thích với Spring Framework đang dùng; kiểm tra constructor/API, lựa chọn transport, timeout và SSL options theo tài liệu client. Không mặc định mọi broker AMQP 1.0 đều chấp nhận JMS destination name theo cùng một quy ước.

`setSessionTransacted(true)` yêu cầu transaction cục bộ cho JMS session khi xử lý listener. Nó **không tạo transaction phân tán** với database, RabbitMQ AMQP 0-9-1 hoặc một broker khác.

### 5.3. Dùng JmsTemplate gửi JSON

```java
@Service
public class Amqp10OrderPublisher {
    private final JmsTemplate template;
    private final ObjectMapper mapper;

    public Amqp10OrderPublisher(
            @Qualifier("amqp10JmsTemplate") JmsTemplate template,
            ObjectMapper mapper) {
        this.template = template;
        this.mapper = mapper;
    }

    public void publish(String destination, OrderPlacedEvent event) {
        final String json;
        try {
            json = mapper.writeValueAsString(event);
        } catch (JsonProcessingException ex) {
            throw new IllegalArgumentException("Không tạo được JSON event", ex);
        }

        template.send(destination, session -> {
            TextMessage message = session.createTextMessage(json);
            message.setStringProperty("eventId", event.eventId().toString());
            message.setStringProperty("eventType", event.eventType());
            message.setIntProperty("schemaVersion", event.schemaVersion());
            message.setStringProperty("contentType", "application/json");
            return message;
        });
    }
}
```

Import tiêu biểu: `org.springframework.jms.core.JmsTemplate`, `org.springframework.stereotype.Service`, `org.springframework.beans.factory.annotation.Qualifier`, `com.fasterxml.jackson.databind.ObjectMapper`, `com.fasterxml.jackson.core.JsonProcessingException` và `jakarta.jms.TextMessage`.

Đây là **JMS TextMessage**. Application property `contentType` không tự tương đương AMQP 1.0 `properties.content-type`; nếu receiver native client yêu cầu field protocol chính xác, phải dùng tùy chọn của provider hoặc native AMQP 1.0 API, sau đó kiểm chứng message trên wire.

Tương tự, `JMSMessageID` do provider tạo có thể khác `eventId`. Giữ `eventId` trong JSON và property riêng, rồi dùng nó làm khóa chống xử lý trùng.

### 5.4. Spring JMS listener đọc message từ broker 1.0

```java
@Component
public class Amqp10OrderListener {
    private final ObjectMapper mapper;
    private final OrderProjectionService projection;

    public Amqp10OrderListener(
            ObjectMapper mapper,
            OrderProjectionService projection) {
        this.mapper = mapper;
        this.projection = projection;
    }

    @JmsListener(
            destination = "orders.intake",
            containerFactory = "amqp10JmsListenerFactory")
    public void onMessage(TextMessage message) throws Exception {
        OrderPlacedEvent event =
                mapper.readValue(message.getText(), OrderPlacedEvent.class);

        if (event.eventId() == null
                || event.schemaVersion() != 1
                || !"OrderPlaced".equals(event.eventType())) {
            throw new IllegalArgumentException("Event không đúng hợp đồng");
        }

        projection.applyOnce(event);
    }
}
```

Import `jakarta.jms.TextMessage`, `org.springframework.jms.annotation.JmsListener`, `org.springframework.stereotype.Component` và Jackson tương ứng.

`OrderProjectionService` là service nghiệp vụ cần triển khai, chẳng hạn ghi projection và bảng `processed_events` có khóa duy nhất `(consumer_name, event_id)` trong **cùng một transaction DB**. Nếu method ném exception, JMS container xử lý transaction/rollback/redelivery theo provider/broker. Nếu DB commit nhưng JMS acknowledgment hoặc commit session thất bại, message có thể được nhận lại; idempotency ngăn lặp tác dụng phụ.

**Không nhầm:** `@RabbitListener` do Spring Rabbit quản lý và chỉ định `SimpleRabbitListenerContainerFactory`; `@JmsListener` do Spring JMS quản lý và chỉ định `DefaultJmsListenerContainerFactory`. Hai annotation không thể hoán đổi cho nhau.

## 6. Bridge 0-9-1 sang 1.0 bằng canonical event

Một bridge nhận message từ RabbitMQ nguồn bằng `@RabbitListener`, parse và validate JSON rồi publish tới broker 1.0:

```java
@Component
public class OrderInteropBridge {

    private final ObjectMapper mapper;
    private final Amqp10OrderPublisher publisher;

    public OrderInteropBridge(
            ObjectMapper mapper, Amqp10OrderPublisher publisher) {
        this.mapper = mapper;
        this.publisher = publisher;
    }

    @RabbitListener(queues = "orders.outbound")
    public void transfer(org.springframework.amqp.core.Message source)
            throws Exception {
        OrderPlacedEvent event = mapper.readValue(
                source.getBody(), OrderPlacedEvent.class);

        if (event.eventId() == null
                || event.schemaVersion() != 1
                || !"OrderPlaced".equals(event.eventType())) {
            throw new IllegalArgumentException("Không nhận event này");
        }

        publisher.publish("orders.intake", event);
    }
}
```

**Đây là skeleton minh họa chuyển đổi**, không phải cam kết exactly-once. `RabbitListener` có thể ACK delivery nguồn khi method trả về; quá trình gửi đích vẫn có giới hạn về xác nhận, routing và bền vững theo JMS provider/broker.

```text
RabbitMQ 0-9-1 A          Spring bridge               AMQP 1.0 broker B
       |                      |                             |
       |--- deliver event --->|                             |
       |                      |--- send canonical event --->|
       |                      |<-- outcome/exception? ------|
       |<---- ACK source -----|                             |
                              ^
                        Nếu crash ở khoảng này:
                        kết quả của hai broker có thể khác nhau
```

### 6.1. Những khoảng hở khi chuyển tiếp

| Điểm xảy ra sự cố | Hậu quả có thể gặp |
|---|---|
| B đã nhận message, A chưa nhận ACK | A có thể redeliver; B nhận một bản duplicate |
| A đã ACK nhưng kết quả publish B chưa chắc chắn | B có thể chưa có event, nếu thiết kế ACK quá sớm |
| B down hoặc không có address hợp lệ | Bridge phải retry hoặc lưu intent bền vững |
| B chấp nhận publish nhưng consumer B lỗi | Send thành công không có nghĩa nghiệp vụ B đã hoàn tất |
| Payload nguồn sai schema | Không tự nuốt lỗi/ACK; cần quarantine hoặc DLQ nguồn |
| Retry publish tạo eventId mới | Duplicate khó nhận biết ở downstream |

Nếu yêu cầu độ tin cậy đầu cuối cao, dùng **inbox + transactional outbox** trong bridge:

1. Nhận event nguồn; xác thực và lấy `eventId`.
2. Trong **một DB transaction**, ghi inbox với unique event ID và outbox mô tả ý định gửi tới B.
3. Commit DB thành công rồi cho listener ACK nguồn.
4. Relay riêng đọc outbox, publish AMQP 1.0, ghi nhận kết quả có thể kiểm chứng; timeout/unknown outcome cần retry với **cùng event ID**.
5. Consumer B tiếp tục deduplicate, vì bridge có thể đã publish thành công rồi crash trước khi đánh dấu outbox `SENT`.

Không có local transaction nào tự ghép ACK AMQP 0-9-1, gửi AMQP 1.0 và DB commit thành một transaction nguyên tử xuyên hệ thống. Outbox chấp nhận **at-least-once**, kết hợp idempotent consumer để quản lý hiệu ứng nghiệp vụ.

## 7. Settlement của AMQP 1.0 và kết quả publish

AMQP 1.0 có khái niệm **delivery disposition/settlement** thay vì sử dụng `basic.ack`/`basic.nack` từ AMQP 0-9-1.

| Kết quả | Ý nghĩa mức protocol | Lưu ý vận hành |
|---|---|---|
| `accepted` | Receiver chấp nhận delivery | Không có nghĩa downstream service đã commit DB |
| `rejected` | Receiver từ chối delivery, có thể kèm error | Không mặc định chuyển DLQ trên mọi broker |
| `released` | Trả delivery để broker có thể phân phối lại | Không đồng nghĩa retry ngay hoặc đúng thứ tự |
| `modified` | Receiver kết thúc với thay đổi delivery state | Semantics redelivery phụ thuộc broker |
| `unsettled` / timeout | Chưa quan sát được trạng thái kết thúc | Không kết luận broker chắc chắn chưa nhận |

**Phân biệt hai hướng:** sender nhận outcome cho việc gửi và receiver settle sau khi xử lý. Giống phân biệt publisher confirms với consumer acknowledgments trong Spring Rabbit, một publish được broker `accepted` không đảm bảo tác dụng phụ ở consumer đích đã hoàn thành.

Với JMS, việc send trả về bình thường, commit session, acknowledge và redelivery có thể được provider ánh xạ thành các lệnh/outcome AMQP 1.0 khác nhau. Phải kiểm tra **broker mục tiêu thực tế** để biết khi nào nó bảo đảm persistence, khi nào báo unroutable và khi nào consumer có thể retry.

### 7.1. Transactions không tự phối hợp với JDBC

Dù Spring JMS listener đặt `sessionTransacted=true`, nếu nó gọi service ghi DB:

```text
DB transaction                  JMS session/AMQP 1.0 delivery
       |                                      |
       +----- commit nghiệp vụ ------------->|
       |                                      +--- settle/commit
       |
       +-- crash giữa hai bước => broker có thể giao lại
```

Không giả định đây là XA/2PC. Dùng business/event ID bền vững, unique constraint và xử lý idempotent; nếu business liên quan external API, dùng idempotency key hoặc workflow bù trừ.

### 7.2. Retry, dead-letter và TTL

Broker AMQP 1.0 đích có thể có retry policy, delivery count, dead-letter entity, message lock hoặc expiration khác RabbitMQ. **Không copy** `x-death`, `x-dead-letter-exchange`, `AmqpRejectAndDontRequeueException` hoặc các argument riêng của RabbitMQ 0-9-1 và giả định broker khác sẽ hiểu.

Bộ câu hỏi vận hành cần trả lời: rollback có redeliver không; khi vượt số lần thử thì message đi đâu; có thể lấy lý do dead-letter không; replay DLQ có giữ event ID/correlation không; TTL được áp dụng ở đâu; một address không tồn tại sẽ fail attach, reject publish hay bị discard?

## 8. Kiểm thử message body và metadata bằng client độc lập

Một lỗi thường gặp là publisher và consumer cùng dùng **một JMS provider**, nên chúng đọc/ghi thành công dù mapping body đặc thù không tương thích với client khác. Kiểm thử nên dùng ít nhất một **native AMQP 1.0 client** hoặc SDK chính thức của broker bên cạnh JMS.

### 8.1. Ma trận body

| Producer | Receiver | Điều cần đối chiếu |
|---|---|---|
| JMS `TextMessage` JSON | JMS `TextMessage` | Unicode UTF-8, number/string/null, schema version |
| JMS `TextMessage` JSON | Native AMQP 1.0 client | Body là `AmqpValue` string hay `Data` bytes; content-type |
| Native AMQP 1.0 `Data` JSON | JMS client | Có ánh xạ thành `BytesMessage` hoặc kiểu khác không? |
| JMS `BytesMessage` binary | Native client | Byte-for-byte payload, content-type |
| JSON schema phiên bản mới | Receiver cũ | Reject/quarantine/fallback có kiểm soát |
| Payload gần giới hạn broker | JMS và native client | Quota, timeout, rejection và memory |

### 8.2. Ma trận metadata

Kiểm tra `message-id`, `correlation-id`, `to`, `reply-to`, `content-type`, `ttl`, `durable` và application properties. Đừng chỉ so sánh giá trị in ra từ cùng một JMS provider; native receiver phải ghi lại **kiểu AMQP** và vị trí section.

Ví dụ `JMSMessageID` có thể là chuỗi do provider tạo, không nhất thiết đúng UUID `eventId` trong JSON. `schemaVersion` có thể được chuyển dưới dạng integer trong application properties, trong khi JMS property `contentType` là custom key chứ không phải field `properties.content-type`.

### 8.3. Không dùng Java serialization làm hợp đồng chung

Không truyền `ObjectMessage` chứa một Java class rồi giả định .NET, Go hoặc Java client khác giải mã an toàn. Với JSON, không gửi metadata `__TypeId__` nội bộ của Spring converter như điều kiện bắt buộc. Hãy tách **business schema** và **transport envelope**, có test fixture/version policy và cơ chế migration.

## 9. Routing: điểm khác nhau lớn nhất giữa các broker

Trong Spring Rabbit, ta thường publish:

```java
rabbitTemplate.convertAndSend(
        "orders.events", "orders.placed", event);
```

Ở AMQP 1.0, sender mở link tới **target address** mà broker hiểu. Địa chỉ `orders.intake` ở ví dụ có thể là queue, topic, address path hoặc một logical entity tuỳ sản phẩm. Không có công thức chung “`orders.events/orders.placed`” áp dụng cho mọi broker.

Cách thiết kế adapter:

1. Đặt **routing policy** ở cấu hình, ví dụ `OrderPlaced -> orders.intake`; không nhét đường dẫn nội bộ broker đích vào DTO nghiệp vụ.
2. Provision và kiểm tra destination/permissions trên broker mục tiêu.
3. Xác nhận nó là queue một-consumer hay topic fan-out và có subscription cần tạo trước không.
4. Gửi message không có route để biết broker báo lỗi thế nào; cấu hình xử lý unknown outcome.
5. Dùng tenant namespace/vhost hợp lệ; không cho message tự sửa destination theo dữ liệu không tin cậy.

**Không dùng `JMSReplyTo` hay `properties.to` để thay thế việc cấu hình sender target một cách thiếu kiểm chứng**. Cách JMS provider diễn giải queue/topic hoặc address phải được đối chiếu với tài liệu broker.

## 10. Bảo mật, hiệu năng và quan sát end-to-end

### 10.1. Bảo mật

- Kết nối TLS đúng endpoint khi broker hỗ trợ; xác minh hostname/certificate.
- Cấu hình SASL/identity và quyền tối thiểu trên destination, không log password/connection URI chứa credential.
- Không tin message chỉ vì nó đã qua broker; validate `eventType`, `schemaVersion`, `eventId`, kích thước, kiểu số và quyền tenant.
- Quản lý khóa bí mật qua môi trường triển khai/secret manager, không ghi giá trị thật vào YAML repository.
- Không deserialize Java object tùy ý từ hệ thống không tin cậy.

### 10.2. Flow control và concurrency

AMQP 1.0 có **link credit** để điều khiển số delivery in-flight. JMS provider có cấu hình prefetch/concurrency riêng; không đánh đồng chúng với `prefetchCount` của `SimpleRabbitListenerContainerFactory`. Khi DB hoặc downstream chậm, phải giới hạn in-flight và backpressure; tăng concurrency không kiểm soát có thể đảo thứ tự nghiệp vụ.

Nếu sự kiện có `aggregateVersion`, receiver cần phát hiện duplicate, gap và stale event khi có nhiều consumer. Event ID dùng deduplication; protocol order không thay thế transaction boundary hoặc state machine.

### 10.3. Metrics cần theo dõi

| Chỉ số | Ý nghĩa |
|---|---|
| AMQP 1.0 connection/link attach failures | Sai TLS/SASL, endpoint, address, permissions |
| Publish accepted/rejected/timeout | Biết tỷ lệ thành công và unknown outcome phía broker đích |
| Publish/settlement latency | Broker hoặc mạng chậm |
| Schema/encoding failures | Receiver không hiểu body hoặc phiên bản dữ liệu |
| Duplicate eventId count | Bridge retries, redelivery hoặc upstream resend |
| JMS listener rollback/redelivery count | Lỗi xử lý hoặc poison message |
| DLQ/quarantine depth | Message không xử lý được cần điều tra |
| Bridge outbox pending và tuổi message cũ nhất | Độ trễ chuyển đổi qua protocol |
| End-to-end commit latency | Từ sự kiện nguồn đến nghiệp vụ DB đích commit |
| In-flight delivery/link credit | Backpressure, sức tải consumer |

Log có cấu trúc chứa `eventId`, `correlationId`, `eventType`, `schemaVersion`, tên broker/target, outcome và exception category; tránh metric label theo từng event ID vì cardinality quá cao.

## 11. Thực hành kiểm chứng tính tương thích

Chuẩn bị một broker AMQP 1.0 mục tiêu đã bật đúng protocol và destination, cùng ứng dụng Spring có client AMQP 1.0. Nếu thực hiện bridge, chuẩn bị thêm RabbitMQ 0-9-1 nguồn.

### Thí nghiệm 1 — Xác nhận đúng giao thức

Dùng AMQP 1.0 client kết nối đúng URI/TLS/SASL, thử khai báo/open sender link tới destination. Cố ý dùng endpoint/protocol sai trong môi trường test để phân biệt lỗi protocol handshake với sai credential hay address.

### Thí nghiệm 2 — JSON/TextMessage round-trip

Gửi `OrderPlaced` có Unicode tiếng Việt và số tiền dạng integer. Nhận lại bằng JMS `TextMessage`; kiểm tra đủ `eventId`, `eventType`, `schemaVersion`, `totalMinor` và `currency`.

### Thí nghiệm 3 — Đọc bằng native AMQP 1.0 client

Lấy message JMS đã gửi, đọc bằng client native. Ghi lại body section (`Data`/`AmqpValue`), `content-type` thực, `message-id`, `correlation-id` và application properties. Sửa adapter nếu client native không đọc được.

### Thí nghiệm 4 — Gửi Data bytes từ native producer

Publish JSON UTF-8 dưới dạng `Data` bytes. JMS receiver phải xử lý kiểu message thật sự provider tạo (có thể `BytesMessage`), **không ép cast thành `TextMessage`** khi chưa kiểm chứng.

### Thí nghiệm 5 — Address sai và unroutable

Cố ý publish đến address không tồn tại hoặc không có quyền. Quan sát link attach failure, send exception, disposition rejected hoặc hành vi broker riêng. Xác định signal nào khiến relay không được ghi `SENT`.

### Thí nghiệm 6 — Retry/settlement

Cho consumer throw exception trước DB commit rồi quan sát redelivery và DLQ policy của broker. Sau đó mô phỏng DB commit nhưng session settlement thất bại; cùng event ID có thể được nhận lại mà không làm lặp hiệu ứng DB nhờ unique constraint.

### Thí nghiệm 7 — Schema nâng cấp

Gửi `schemaVersion=2` khi receiver chỉ hỗ trợ version 1. Phải có cách xử lý rõ: reject/quarantine, metric lỗi schema và chính sách nâng cấp, **không âm thầm đánh dấu event đã xử lý**.

### Thí nghiệm 8 — Bridge duplicate

Bridge nhận `eventId=E-100` trên RabbitMQ 0-9-1, publish sang AMQP 1.0. Giả lập broker B đã nhận nhưng ACK A bị mất. Xác minh A redeliver; consumer B bỏ qua tác dụng phụ trùng nhờ `eventId` ổn định.

### Thí nghiệm 9 — Broker ngắt kết nối

Dừng broker 1.0 ở giai đoạn publish, theo dõi timeout/unknown outcome. Nếu có outbox, row chưa được xác nhận vẫn pending và được retry với backoff khi broker hồi phục. Đánh giá số duplicate và thời gian trễ.

### Thí nghiệm 10 — Kiểm tra persistence

Với cấu hình broker cho phép persistent message, publish, nhận outcome phù hợp, restart broker trong môi trường test và kiểm tra message còn tồn tại theo cam kết lưu trữ của sản phẩm. Không suy rằng một lần test chứng minh broker không thể mất dữ liệu dưới mọi kiểu sự cố cluster.

**Tiêu chí đạt:** Ghi lại compatibility profile thật của broker, payload được giải mã bằng client độc lập, metadata ánh xạ đúng, routing lỗi được phát hiện, retry không làm lặp nghiệp vụ và có cách khôi phục khi bridge/broker lỗi.

## 14. Tổng kết

**Chuyển đổi thông điệp để tương thích với broker AMQP 1.0** đòi hỏi phân biệt ranh giới giao thức và **thiết kế hợp đồng dữ liệu độc lập transport**. Spring Rabbit dùng `RabbitTemplate`/`@RabbitListener` chủ yếu theo AMQP 0-9-1; khi tích hợp AMQP 1.0, ứng dụng có thể dùng Spring JMS với provider AMQP 1.0 hoặc native client tương thích.

Body (`Data`, `AmqpValue`, `AmqpSequence`), protocol properties, application-properties, sender target address và settlement đều cần **đối chiếu với broker mục tiêu**. Với luồng chuyển tiếp giữa hai broker, kết hợp event ID ổn định, inbox/outbox, xác nhận phù hợp, retry có backoff, idempotent consumer và giám sát DLQ để có độ tin cậy đầu cuối, thay vì giả định các transaction và acknowledgment sẽ tự tương thích.
