# clientIdSuffix

## 1. Role of clientIdSuffix in Spring Kafka

When a Spring Kafka listener runs with concurrency greater than one, the framework creates multiple consumers to read partitions in parallel. Each consumer is a separate Kafka client with its own poll loop, connections, and metric set. To distinguish these clients in logs, broker metrics, and monitoring tools, Spring Kafka can append a suffix to the client ID.

**clientIdSuffix** is the suffix Spring Kafka appends to the base client ID of each child consumer managed by `ConcurrentMessageListenerContainer`. With concurrency enabled, child consumers typically receive client IDs such as:

~~~text
orders-fulfillment-0
orders-fulfillment-1
orders-fulfillment-2
~~~

In this example, `orders-fulfillment` is the client ID prefix and `-0`, `-1`, `-2` are the suffixes generated by the concurrent container.

The suffix helps operators identify which consumer is emitting metrics, writing logs, or sending requests to brokers. It serves identification and observability. It does not determine which group a consumer belongs to, which partitions are assigned, or which records are processed.

## 2. Distinguishing client.id, clientIdPrefix, clientIdSuffix, and group.id

These names are related but represent different concepts:

| Property | Meaning | Example |
|---|---|---|
| `client.id` | Kafka client identifier sent with requests and used in metrics/logs | `orders-fulfillment-0` |
| `clientIdPrefix` | Prefix Spring Kafka uses as the base to construct listener client IDs | `orders-fulfillment` |
| `clientIdSuffix` | Suffix distinguishing child consumers of a concurrent container | `-0`, `-1`, `-2` |
| `group.id` | Consumer group identifier; consumers in the same group share partitions | `order-fulfillment` |
| `group.instance.id` | Static group member identifier when using static membership | `order-fulfillment-pod-a` |

`client.id` and `group.id` are not interchangeable. Two consumers can have different client IDs yet share the same group ID to divide partitions. Conversely, two consumers with identical client IDs but different group IDs still belong to two independent consumer groups.

`clientIdSuffix` is also not a partition number. A consumer whose client ID ends in `-0` can receive one or multiple partitions; after a rebalance, assignments may change while the client ID remains the same.

## 3. How Concurrent Containers Generate Suffixes

`ConcurrentMessageListenerContainer` manages multiple child `KafkaMessageListenerContainer` instances. Each child container creates a Kafka consumer. When Spring Kafka creates child consumers, it takes the base client ID and appends a suffix so they can be identified individually.

Suppose a listener has concurrency three and the prefix is `billing-consumer`:

~~~text
ConcurrentMessageListenerContainer
    |
    +-- Child container 0
    |      +-- KafkaConsumer
    |      +-- client.id = billing-consumer-0
    |
    +-- Child container 1
    |      +-- KafkaConsumer
    |      +-- client.id = billing-consumer-1
    |
    +-- Child container 2
           +-- KafkaConsumer
           +-- client.id = billing-consumer-2
~~~

Typically, the suffix index starts at 0 and increments per child container. This is a consumer identification index within the concurrent container, not a partition ordinal.

### 3.1. When Concurrency Is One

By default, the suffix is usually added when concurrency is greater than one. With concurrency equal to one, the client ID may use the prefix without a suffix.

Spring Kafka provides the `alwaysClientIdSuffix` option on `ConcurrentMessageListenerContainer`. When enabled, the container always appends the suffix, even when concurrency is one. The resulting format is:

~~~text
billing-consumer-0
~~~

This is useful when you want all listeners to follow a consistent naming convention, or when multiple containers share the same prefix and need to be distinguished in metrics.

This option is a Spring Kafka container setting, not the standard Kafka consumer property `client.id`. Check the API of the Spring Kafka version your application uses when configuring it.

## 4. Setting clientIdPrefix on @KafkaListener

For annotation-declared listeners, the common approach is setting `clientIdPrefix`:

~~~java
@Service
public class OrderListener {

    private final FulfillmentService fulfillmentService;

    public OrderListener(FulfillmentService fulfillmentService) {
        this.fulfillmentService = fulfillmentService;
    }

    @KafkaListener(
        id = "orders-fulfillment-listener",
        topics = "orders.created",
        groupId = "order-fulfillment",
        concurrency = "3",
        clientIdPrefix = "orders-fulfillment"
    )
    public void consume(OrderCreated event) {
        fulfillmentService.process(event);
    }
}
~~~

With concurrency three, the child consumers receive distinct client IDs based on the prefix. For example:

~~~text
orders-fulfillment-0
orders-fulfillment-1
orders-fulfillment-2
~~~

The listener `id` is the Spring Kafka endpoint ID, whereas `clientIdPrefix` names the Kafka consumer clients. Both values can be identical, though they do not serve the same role.

### 4.1. Using Environment-Specific Placeholders

You can include the application or instance name in the prefix to make client IDs easier to identify:

~~~java
@KafkaListener(
    id = "orders-listener",
    topics = "orders.created",
    groupId = "order-fulfillment",
    concurrency = "${orders.consumer.concurrency:3}",
    clientIdPrefix = "${spring.application.name:orders}-${INSTANCE_ID:local}"
)
public void consume(OrderCreated event) {
    fulfillmentService.process(event);
}
~~~

Configuration example:

~~~yaml
spring:
  application:
    name: order-service

orders:
  consumer:
    concurrency: 3
~~~

If the pod's `INSTANCE_ID` environment variable is `pod-a7`, the client IDs can be:

~~~text
order-service-pod-a7-0
order-service-pod-a7-1
order-service-pod-a7-2
~~~

Placeholders must be resolved by Spring in the runtime environment. If the application does not supply `INSTANCE_ID`, the default `local` is used in this example. For multi-replica deployments, supply an actual instance identifier so pods do not generate identical sets of client IDs.

## 5. Configuring on ConcurrentMessageListenerContainer

When constructing a concurrent container manually instead of using `@KafkaListener`, you can set concurrency and the suffix option directly on the container:

~~~java
ContainerProperties containerProperties =
    new ContainerProperties("orders.created");

containerProperties.setGroupId("order-fulfillment");
containerProperties.setClientId("orders-fulfillment");

ConcurrentMessageListenerContainer<String, OrderCreated> container =
    new ConcurrentMessageListenerContainer<>(
        consumerFactory,
        containerProperties
    );

container.setConcurrency(3);
container.setAlwaysClientIdSuffix(true);
~~~

This snippet focuses on container configuration. The application must still configure a message listener, deserializer, lifecycle, and appropriate security properties before starting the container.

If using `ConcurrentKafkaListenerContainerFactory`, you can apply the option to containers created by the factory using a container customizer in Spring Kafka versions that support this API:

~~~java
@Bean
public ConcurrentKafkaListenerContainerFactory<String, OrderCreated>
        orderKafkaListenerContainerFactory(
                ConsumerFactory<String, OrderCreated> consumerFactory) {

    var factory =
        new ConcurrentKafkaListenerContainerFactory<String, OrderCreated>();

    factory.setConsumerFactory(consumerFactory);
    factory.setConcurrency(3);
    factory.setContainerCustomizer(container ->
        container.setAlwaysClientIdSuffix(true)
    );

    return factory;
}
~~~

If your library version does not yet include a container customizer, configure the container directly after creation or upgrade according to your application's dependency plan. Do not assume a YAML property named `client-id-suffix` exists in every version; the suffix is usually controlled via the concurrent container API.

## 6. Suffixes and Multiple Application Instances

An easily overlooked detail is that the suffix typically only distinguishes child consumers within a single concurrent container. It does not automatically guarantee unique client IDs across the entire deployment.

For example, two pods running concurrently:

- concurrency = 2
- clientIdPrefix = `orders-fulfillment`

Each pod can then create:

~~~text
Pod A:
  orders-fulfillment-0
  orders-fulfillment-1

Pod B:
  orders-fulfillment-0
  orders-fulfillment-1
~~~

The consumers can still function normally in the same group; client ID is not the group membership key. However, dashboards or centralized metrics systems may aggregate data from identically named clients, making per-pod investigation harder.

The solution is to include an instance identifier in the prefix:

~~~java
@KafkaListener(
    id = "orders-listener",
    topics = "orders.created",
    groupId = "order-fulfillment",
    concurrency = "2",
    clientIdPrefix = "orders-${POD_NAME:local}"
)
public void consume(OrderCreated event) {
    fulfillmentService.process(event);
}
~~~

Illustrative output:

~~~text
Pod A:
  orders-pod-a-0
  orders-pod-a-1

Pod B:
  orders-pod-b-0
  orders-pod-b-1
~~~

You can use pod name, hostname, or a deployment-provided instance ID. The prefix should remain stable enough to track an instance over its lifetime, yet differ across replicas if they must be distinguished in telemetry.

Avoid putting high-cardinality values like event ID, order ID, or request ID into the client ID. Those values belong in per-event logs/traces, not in the Kafka consumer identity.

## 7. Where Is client.id Used?

The Kafka client sends `client.id` in requests so brokers and operational tools can identify the request source. It commonly appears in:

- Broker logs when investigating requests or connection errors.
- Kafka client metrics and JMX metrics.
- Metric labels produced by exporters or Micrometer integrations.
- Consumer group inspection tools, depending on whether the tool displays client IDs.
- Application logs when appropriate consumer/client logging is enabled.

When client IDs have suffixes, operators can compare child consumers:

| Client ID | Data to inspect |
|---|---|
| `orders-fulfillment-0` | Request rate, fetch latency, assigned partitions, and processing rate |
| `orders-fulfillment-1` | Lag, retries, rebalances, and processing duration |
| `orders-fulfillment-2` | Consumer errors, throughput, and resource usage |

If one consumer shows a low fetch rate and high lag while other consumers remain healthy, inspect assignments, hot partitions, or errors specific to that instance. Client ID helps locate the consumer for investigation; it does not provide the root cause on its own.

Exact metric names depend on the Kafka client, Spring Kafka, Micrometer, and exporters. Check the actual exported metrics before writing dashboards or alert rules.

## 8. Suffixes Do Not Affect Group Membership or Partition Assignment

Kafka uses `group.id` to identify a consumer group. The group coordinator manages members, generations, and partition assignments. `client.id` is primarily used for request identification and telemetry.

Components to distinguish:

| Component | Primary impact |
|---|---|
| `client.id` | Identifies the Kafka client in requests, logs, and metrics |
| `group.id` | Defines the consumer group and partition-sharing boundary |
| `group.instance.id` | Static member identifier when using static membership |
| `member.id` | Kafka-managed group member identifier |
| Partition assignor | Determines how partitions are distributed among consumers |

Changing the suffix does not move a consumer to a different group, create new partitions, or alter producer key partitioning. Changing `group.id` can yield completely different consumption behavior; changing only client ID primarily affects client identification.

### 8.1. Do Not Use the Suffix as a Static Member ID

Static membership uses `group.instance.id` to reduce rebalances during certain brief restarts. This is a group member identifier that must follow uniqueness rules within the group.

`clientIdSuffix` does not replace `group.instance.id`. Do not use client ID as a static membership identity unless the application deliberately configures group.instance.id per Kafka's rules. Specifically, multiple consumers in the same group cannot share a single static member ID.

## 9. Interaction with Concurrency and Partitions

Suppose the `orders.created` topic has six partitions and a listener runs with concurrency three:

~~~text
Topic:
  P0  P1  P2  P3  P4  P5

Consumer clients:
  orders-fulfillment-0
  orders-fulfillment-1
  orders-fulfillment-2
~~~

Kafka can assign two partitions per consumer in a balanced assignment. However, the suffix does not indicate which consumer owns P0 or P1. Partition assignment can change after a rebalance while the suffix stays tied to its corresponding child container.

If the topic has only two partitions while concurrency is four, there can still be four child consumers and four client IDs, yet at most two consumers receive partitions at a time. The remaining two consumers do not read records for that topic. Having a suffix does not mean a consumer is processing data.

Therefore, when investigating lag or throughput, combine client ID with partition assignment. Do not infer assignment solely from the suffix.

## 10. Interaction with Multiple Listeners in the Same Application

An application can have multiple listener containers, each with its own prefix:

~~~java
@KafkaListener(
    id = "orders-listener",
    topics = "orders.created",
    groupId = "order-fulfillment",
    concurrency = "3",
    clientIdPrefix = "orders"
)
public void consumeOrder(OrderCreated event) {
    orderService.process(event);
}

@KafkaListener(
    id = "audit-listener",
    topics = "orders.audit",
    groupId = "audit-indexer",
    concurrency = "2",
    clientIdPrefix = "audit"
)
public void consumeAudit(OrderAudit event) {
    auditService.index(event);
}
~~~

The client IDs can be:

~~~text
orders-0
orders-1
orders-2

audit-0
audit-1
~~~

Separate prefixes make it easy to filter metrics by endpoint. If two listeners share the same prefix and suffix index, client IDs can collide. Choose meaningful prefixes that are unique within the application, then include an instance ID if pods need to be distinguished.

## 11. Diagnosing Incidents with clientIdSuffix

Suffixes are useful when one child consumer behaves differently from others. For example:

| Symptom | How to use client ID to investigate |
|---|---|
| One consumer has high lag | Identify client ID, inspect partition assignment and throughput for that consumer |
| Low fetch rate on one consumer | Check assigned partitions, broker leaders, and client metrics |
| One consumer errors frequently | Filter logs by client ID and compare with peer consumers on the same listener |
| Metrics merged across pods | Check whether the prefix includes an instance ID |
| Multiple duplicate client IDs | Check whether listeners share the same clientIdPrefix and concurrency index |
| Consumer ID changes after deployment | Inspect how the prefix and pod instance identity are constructed |

When a client ID does not appear in metrics, check whether the consumer was created and started successfully, whether it received any partitions, and whether the exporter collects metrics by that client ID. Missing metrics do not necessarily mean the consumer failed.

### 11.1. What Information Should Logs Contain?

Useful application logs should include listener ID, group ID, client ID or instance ID where obtainable, along with the topic/partition/offset of the record being processed.

Structured log example:

~~~text
listener=orders-listener
groupId=order-fulfillment
clientId=orders-pod-a-1
topic=orders.created
partition=3
offset=12840
eventId=evt-92
result=processed
~~~

These fields connect event processing logs with consumer metrics. Avoid using event ID or order ID as metric labels because cardinality can explode; those IDs belong in logs or traces.

## 12. Common Misconceptions

**Assuming the suffix is a partition ID.** The suffix identifies a child consumer, whereas partition assignment is managed by the Kafka group coordinator and assignor.

**Assuming the suffix puts a consumer in a separate group.** Group membership is governed by group.id and the coordinator mechanism, not client.id.

**Assuming the suffix is globally unique across the deployment.** The suffix typically distinguishes child consumers only within one container. Multiple pods with the same prefix can generate duplicate names.

**Assuming client ID controls event ordering.** Ordering depends on partitions and how the application processes records. Changing client ID does not change log order.

**Using clientIdSuffix as group.instance.id.** These are separate concepts. Static membership requires a unique, stable group.instance.id per member.

**Putting per-event IDs into client ID.** Client ID represents a consumer process, not a message. Dynamic IDs make telemetry unmanageable.

**Omitting prefixes for different listeners.** Multiple listeners can produce duplicate client IDs if they share the same prefix and suffix index.

**Assuming concurrency one always gets a suffix.** By default, the suffix is usually added only when concurrency is greater than one. Enable alwaysClientIdSuffix if a suffix is needed even with one consumer.

## 13. Configuration and Operations Workflow

1. Identify the listener endpoint and how many child consumers need to run.
2. Set a meaningful `clientIdPrefix` for each listener.
3. Use the default suffix to distinguish child consumers when concurrency exceeds one.
4. If a suffix is needed when concurrency is one, configure `alwaysClientIdSuffix` on the concurrent container.
5. With multiple pods, include a pod/instance ID in the prefix to prevent name collisions in telemetry.
6. Keep `group.id` and `group.instance.id` for their intended purposes; do not substitute the suffix for them.
7. Verify actual client IDs in logs or metrics after container startup.
8. Build dashboards filterable by listener, client ID, group ID, topic, and partition.
9. When investigating lag, always inspect partition assignments alongside client IDs.
10. Document naming conventions in the runbook so every environment stays consistent.

## 14. End-to-End Example: Order Fulfillment

An Order Fulfillment application has an `orders.created` topic with 12 partitions. Each pod runs the listener with concurrency three. The deployment has three pods, and all consumers use group ID `order-fulfillment`.

Listener configuration:

~~~java
@KafkaListener(
    id = "orders-fulfillment-listener",
    topics = "orders.created",
    groupId = "order-fulfillment",
    concurrency = "3",
    clientIdPrefix = "orders-${POD_NAME:local}"
)
public void consume(OrderCreated event) {
    fulfillmentService.process(event);
}
~~~

Suppose the three pods are named `orders-a`, `orders-b`, and `orders-c`. The client IDs will look like:

~~~text
orders-orders-a-0
orders-orders-a-1
orders-orders-a-2

orders-orders-b-0
orders-orders-b-1
orders-orders-b-2

orders-orders-c-0
orders-orders-c-1
orders-orders-c-2
~~~

Total consumers created:

`3 pods × 3 consumers = 9 consumers`

With 12 partitions, Kafka can distribute partitions across the nine consumers. A consumer may receive one or two partitions depending on assignment.

If the dashboard shows `orders-orders-b-1` has rising lag, operations can pinpoint the exact consumer and inspect its assigned partitions, fetch rate, processing duration, and downstream latency. If that consumer holds no partitions, the lag cannot be explained by slow processing on it; inspect assignments and whichever peer consumer owns the lagging partition.

If the deployment scales to five pods without pod name in the prefix, pods may generate identical client IDs such as `orders-0`, `orders-1`, `orders-2`. This makes it hard for dashboards to distinguish instances. Adding instance ID to the prefix keeps telemetry isolated per pod.

## 15. Key Takeaways

`clientIdSuffix` is the suffix Spring Kafka uses to distinguish client IDs of child consumers in `ConcurrentMessageListenerContainer`. When concurrency exceeds one, Spring Kafka typically appends suffixes such as `-0`, `-1`, `-2` to the client ID prefix.

Suffixes aid consumer observability in logs and metrics. They do not determine group membership, partition assignment, event ordering, or static membership. When running multiple pods, include an instance ID in `clientIdPrefix` if unique client IDs are needed in your monitoring system. If a suffix is needed even when concurrency is one, configure `alwaysClientIdSuffix` on the concurrent container according to the API of your running Spring Kafka version.
