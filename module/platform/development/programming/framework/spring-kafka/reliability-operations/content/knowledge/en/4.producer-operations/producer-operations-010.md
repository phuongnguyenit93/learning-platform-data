# Setting traceable client.id

In Kafka, **client.id** is a logical name that a Kafka client sends along with requests to brokers. With Spring Kafka, the producer underlying `KafkaTemplate` uses this property so brokers and observability systems can identify which client originated a request. Setting a clear `client.id` helps locate logs, analyze metrics, distinguish send flows, and investigate production incidents.

`client.id` is one part of producer operability. It does not replace event IDs, trace IDs, producer IDs, or security identities. Each identifier answers a different question: `client.id` tells you which Kafka client sent the request; event ID tells you which business event is being published; trace ID links steps across a distributed request; producer ID is a Kafka-managed identifier supporting idempotence and transactions.

## 1. What is client.id?

A Kafka producer is created from Kafka client configuration. In that configuration, the **client.id** property sets a logical name for the producer. Spring Kafka passes this configuration down to the `KafkaProducer` used by `KafkaTemplate`.

When the producer sends a request, the client ID is included in the Kafka protocol request header. Brokers can use this information in logs, metrics, and quota policies. On the application side, the Kafka client also uses the client ID as a label in client-related metrics and log entries.

High-level flow:

~~~text
Spring Application
       |
       | KafkaTemplate.send(...)
       v
ProducerFactory
       |
       | creates / manages KafkaProducer
       v
KafkaProducer
       |
       | client.id = orders-prod-publisher
       | ProduceRequest + request header
       v
Kafka broker
       |
       +--> broker log / request log
       |
       +--> request metrics / client quota

Application observing producer metrics
       |
       +--> client-id = orders-prod-publisher
~~~

For example, if multiple applications send to the `orders` topic, brokers can distinguish requests coming from `orders-api`, `order-replay`, and `billing-service` via their different client IDs. When one publish flow experiences a high retry rate, operators can filter logs and metrics by client ID to isolate it.

`client.id` is an application-configured string. If left unset, the Kafka client may auto-generate a default name like `producer-1`. Auto-generated names are fine for some development logs, but are hard to interpret when many services, instances, and producers run concurrently.

## 2. What does client.id help trace?

A client ID with a clear naming convention supports many operational tasks:

| Need | How client.id helps |
|---|---|
| Finding logs | Identifies requests or log messages belonging to a specific producer. |
| Metric analysis | Separates metrics across Kafka clients; allows filtering by client ID label if the collector retains it. |
| Investigating send errors | Correlates retries, request latency, broker errors, and logs of the originating service. |
| Distinguishing business streams | Distinguishes producers sending orders, replaying data, sending audits, or sending notifications. |
| Quota management | Brokers can enforce client quotas per client ID to limit data rates or request utilization. |
| Environment separation | Distinguishes local, staging, and production producers when environments appear in the same monitoring system. |

For instance, a dashboard can group producer metrics by client ID:

~~~text
orders-prod-publisher
  record-send-rate
  record-error-rate
  record-retry-rate
  request-latency-avg
  request-latency-max

orders-prod-replay
  record-send-rate
  record-error-rate
  record-retry-rate
  request-latency-avg
  request-latency-max
~~~

Exact metric names and available metrics depend on Kafka client version, exporter collection, and monitoring system. The key point is that client ID provides a meaningful label to separate statistics for each Kafka client.

`client.id` can also appear in broker logs, especially when request- or client-related logging is enabled. Level of detail depends on broker logging configuration. Do not assume every broker log records every request by default; check the deployed log levels and formats.

## 3. Distinguishing identifier types

A Spring Kafka system may use multiple ID types simultaneously. Using one ID for the wrong purpose can mislead tracing.

| Identifier | Who creates / configures? | Scope and purpose |
|---|---|---|
| client.id | Application config for Kafka client | Identifies a producer or consumer client in logs, metrics, and quotas. |
| producer ID | Assigned by Kafka to producer | Identifies the producer in Kafka protocol for idempotence and transactions. |
| event ID | Generated by application or domain | Identifies a business event across replays or reprocessing. |
| trace ID | Created or propagated by tracing system | Connects spans of a request across multiple services. |
| correlation ID | Created by application or integration layer | Correlates related operations in logs or business workflows. |
| consumer group ID | Application config for consumer group | Identifies a consumer group coordinating reads and partition splits. |

### client.id is not producer ID

The producer ID is managed by Kafka and plays a role in the idempotent producer mechanism. `client.id` is a logical name set by the application that can stay stable across restarts. Changing `client.id` does not create a new event, nor does it replace idempotence sequence numbers.

### client.id is not event ID

A single producer can send millions of events with the same client ID. This is normal: `client.id` identifies the producer process or role, whereas event ID identifies each individual event.

If you put an event ID into `client.id`, every event creates a distinct client name from an observability perspective. This inflates metric cardinality and breaks quotas, dashboards, and log searches. Put event IDs in the payload or record headers.

### client.id is not trace ID

Trace IDs change per trace or request. `client.id` generally remains constant over the lifetime of a `KafkaProducer`. One producer can send records belonging to many different traces, so never set `client.id` to the current request's trace ID.

If you need to link a Kafka event to its originating trace, propagate trace context via record headers using your application's compatible tracing mechanism. When investigating, use `client.id` to pinpoint the producer and trace ID to follow the request that generated the event.

### client.id is not a security identity

`client.id` is a self-declared client label. It does not prove which service an application is and does not replace SASL principals, TLS client certificates, or other authentication mechanisms. Broker authorization relies on principals and ACLs, not on `client.id`, to grant topic access.

A client could declare a `client.id` matching another service's name unless restricted by policy. Therefore, using client ID for observability and quotas is appropriate; using it as authentication proof or a trust boundary is not.

## 4. Traceable naming conventions

A useful client ID should be readable, stable, and distinguish roles. Choose a simple structure, such as:

~~~text
<service>-<environment>-<role>
~~~

Examples:

| client.id | Meaning |
|---|---|
| orders-prod-publisher | Primary producer of the orders service in production. |
| orders-prod-replay | Producer used to replay orders data in production. |
| billing-prod-publisher | Producer of the billing service in production. |
| orders-staging-publisher | Producer of orders in staging. |
| inventory-dev-publisher | Producer of inventory in the development environment. |

If individual instances must be distinguished, append an instance suffix:

~~~text
<service>-<environment>-<role>-<instance>
~~~

Examples:

~~~text
orders-prod-publisher-pod-7f8c9
orders-prod-publisher-pod-a31d2
~~~

An instance suffix helps pinpoint which pod or process is having trouble. It is especially helpful when only one replica has network errors, high retries, or latency diverging from other replicas.

### Shared ID or per-instance ID?

This is a decision about observability granularity. Both approaches are useful, serving different goals:

| Naming style | Benefit | Trade-off |
|---|---|---|
| Same client ID for all instances of a role | Metrics aggregate by service/role; stable names and fewer labels. | Harder to spot a single failing pod solely from client ID. |
| Separate client ID per instance | Can filter logs and metrics by process or pod. | Label count grows with scale; dashboards and metrics backends face higher cardinality. |

You can combine approaches: keep client ID stable by service and role for overview dashboards, while logging instance ID, hostname, or pod name in application logs and telemetry resource attributes. If per-instance metric breakdown is required, add a lifecycle-appropriate suffix and monitor cardinality.

Do not generate a new client ID for every HTTP request, user, or message. `KafkaProducer` is a long-lived client; client ID should describe that client, not a single API call.

### Naming principles

- Use lowercase letters, numbers, and hyphens for readability, searchability, and consistency across environments.
- Include service or application, environment, and producer role as needed.
- Pick a name stable across restarts when long-term trend comparison is the goal.
- Add an instance suffix only when instance-level observability is required.
- Never put usernames, emails, access tokens, customer data, or secrets into client IDs.
- Avoid overly generic names like `producer`, `kafka-client`, or `app` when multiple clients of the same kind exist.
- Avoid long names packed with frequently changing attributes that make logs and metrics hard to filter.

## 5. Configuring client.id in Spring Boot

Spring Boot has a common property **spring.kafka.client-id** to set the client ID for Kafka clients configured via auto-configuration. To set it specifically for the producer, pass the Kafka **client.id** property inside the **spring.kafka.producer.properties** map.

Example setting a producer-specific ID in `application.yml`:

~~~yaml
spring:
  application:
    name: orders-service
  kafka:
    producer:
      acks: all
      properties:
        "[client.id]": orders-prod-publisher
        "[enable.idempotence]": true
~~~

In this example, the producer created by Spring Boot's producer configuration uses client ID `orders-prod-publisher`. Other clients such as consumers or `AdminClient` can be configured with their own client IDs depending on observability goals.

To set a shared client ID for Kafka clients created by Spring Boot auto-configuration, declare:

~~~yaml
spring:
  kafka:
    client-id: orders-prod
~~~

The shared property is convenient when all clients of an application can share one service label. When you need to separate producers from consumers, set distinct IDs inside each client type's specific configuration. For the producer, a property inside the producer map overrides the general value when applied to producer configuration.

Equivalent in `application.properties`:

~~~properties
spring.kafka.producer.acks=all
spring.kafka.producer.properties[client.id]=orders-prod-publisher
spring.kafka.producer.properties[enable.idempotence]=true
~~~

In YAML, square brackets around map keys preserve dotted Kafka property names. In properties files, bracket syntax retains the `client.id` key as a map entry.

### Setting client ID per environment

Do not hard-code production names in a shared configuration file used across all environments. Use environment-specific profiles and set stable client ID values in each corresponding profile.

Example in `application-prod.yml`:

~~~yaml
spring:
  application:
    name: orders-service
  kafka:
    producer:
      properties:
        "[client.id]": orders-service-prod-publisher
~~~

Example in `application-local.yml`:

~~~yaml
spring:
  application:
    name: orders-service
  kafka:
    producer:
      properties:
        "[client.id]": orders-service-local-publisher
~~~

If per-instance distinction is needed, configure environment profiles or deployment settings with a pod/process suffix. Weigh the impact of hostnames or pod names on cardinality. If the system frequently creates and destroys pods, metrics keyed by client ID can generate many short-lived label series.

## 6. Configuring client.id with ProducerFactory

When the application constructs `ProducerFactory` manually, set the client ID directly via `ProducerConfig.CLIENT_ID_CONFIG`. `KafkaTemplate` uses `ProducerFactory` to create or manage `KafkaProducer` with that configuration.

~~~java
Map<String, Object> producerProps = new HashMap<>();

producerProps.put(
        ProducerConfig.BOOTSTRAP_SERVERS_CONFIG,
        "kafka-1:9092,kafka-2:9092");
producerProps.put(
        ProducerConfig.CLIENT_ID_CONFIG,
        "orders-prod-publisher");
producerProps.put(
        ProducerConfig.ACKS_CONFIG,
        "all");
producerProps.put(
        ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG,
        true);

ProducerFactory<String, OrderEvent> producerFactory =
        new DefaultKafkaProducerFactory<>(producerProps);

KafkaTemplate<String, OrderEvent> kafkaTemplate =
        new KafkaTemplate<>(producerFactory);
~~~

This snippet only illustrates the relevant properties. In real applications, also specify serializers, security, bootstrap servers, and other environment-appropriate settings.

If there are two sending streams with distinct purposes, create two separate `ProducerFactory` and `KafkaTemplate` beans with distinct client IDs:

~~~java
// Primary ProducerFactory
producerProps.put(
        ProducerConfig.CLIENT_ID_CONFIG,
        "orders-prod-publisher");

// Replay ProducerFactory
replayProducerProps.put(
        ProducerConfig.CLIENT_ID_CONFIG,
        "orders-prod-replay");
~~~

This separation distinguishes normal publishing traffic from replay traffic in logs and metrics. Manage the lifecycle of factories, producers, and templates so resources close properly.

### Multiple KafkaTemplates sharing a ProducerFactory

If multiple `KafkaTemplate` beans share a single `ProducerFactory`, they may share the same configuration and the same `KafkaProducer` managed by the factory. In that case, `client.id` identifies the shared `KafkaProducer` and does not automatically distinguish individual templates or business methods.

If you need to distinguish streams at the template level while still sharing a producer, include event type, correlation ID, or trace context in logs and record headers. If genuinely separate client IDs are needed, create separate configurations and producer factories.

### When changing client.id

`client.id` is read when `KafkaProducer` is initialized. Changing the value in a configuration file does not rename an already-created, running producer. Recreate the producer or restart the application via deployment workflows so the new client picks up the new ID.

With Spring Kafka, check how `ProducerFactory` caches and manages producers. If updating configuration dynamically, ensure the old producer closes cleanly and the new producer is built from the updated config; never mutate a configuration map in active use without lifecycle management.

## 7. Combining client.id with logs and metrics

`client.id` is only useful if observability systems collect and display it. Configure logging and metrics so operators can filter using the same naming convention.

### Application-side logs

When logging send outcomes, include event ID together with Kafka metadata and contextual info. `client.id` is usually already present in Kafka client metrics or internal logs, though adding the send stream name to business logs can also make searching convenient.

~~~java
public CompletableFuture<SendResult<String, OrderEvent>> publish(
        OrderEvent event) {

    return kafkaTemplate
            .send("orders", event.orderId(), event)
            .whenComplete((result, exception) -> {
                if (exception != null) {
                    log.error(
                            "Kafka publish failed, eventId={}, orderId={}",
                            event.eventId(),
                            event.orderId(),
                            exception);
                    return;
                }

                RecordMetadata metadata = result.getRecordMetadata();
                log.info(
                        "Kafka publish succeeded, eventId={}, topic={}, partition={}, offset={}",
                        event.eventId(),
                        metadata.topic(),
                        metadata.partition(),
                        metadata.offset());
            });
}
~~~

This example logs the event ID and metadata returned by the broker. `client.id` is configured at the `KafkaProducer` level; there is no need to pass it as a business field in every message.

When sends fail, logs should include event ID, exception type, topic, and necessary correlation info. Avoid logging full payloads if payloads contain personal data or sensitive information.

### Producer metrics

The Kafka producer provides useful metrics for investigation:

| Metric group | Examples | Operational question |
|---|---|---|
| Send rate | `record-send-rate`, `byte-rate` | How many records and bytes per second is the producer sending? |
| Errors and retries | `record-error-rate`, `record-retry-rate` | Are final errors or retries spiking abnormally? |
| Request latency | `request-latency-avg`, `request-latency-max` | Are brokers responding quickly or slowly to requests? |
| Buffer | `bufferpool-wait-time-total`, `buffer-available-bytes` | Is the producer waiting on buffer space or experiencing backpressure? |
| Batching | `batch-size-avg`, `records-per-request-avg` | Is the producer batching efficiently? |

When exporters expose client ID as a metric tag, filter or group by client ID to compare producers. For instance, if `orders-prod-replay` shows high retries while `orders-prod-publisher` looks normal, the issue likely lies in the replay flow, its separate configuration, or how that flow generates load.

Exact metrics and metric names vary by Kafka client and exporter. Check the actual metrics exposed in your environment before building dashboards or alerts tied to specific names.

### Broker logs and quotas

Brokers receive the client ID in the request header. Depending on logging config, broker logs can show the client ID accompanying requests or related errors. When traffic throttling is needed, Kafka supports client quotas based on client ID, such as limiting producer byte rates.

Example setting a producer quota for client ID `orders-prod-publisher`:

~~~bash
kafka-configs.sh --bootstrap-server kafka-1:9092 \
  --alter \
  --add-config 'producer_byte_rate=1048576' \
  --entity-type clients \
  --entity-name orders-prod-publisher
~~~

The command above illustrates a producer byte-rate quota for the selected client ID. The unit of `producer_byte_rate` is bytes per second. Broker admin privileges and the running Kafka version can affect execution; verify active configuration before applying production quotas.

Per-client-ID quotas are helpful for isolating load across send streams. However, because client ID is client-declared, do not use client-ID quotas as an authentication mechanism. If multiple producers share the same ID, they match the same quota configuration. If each instance uses a different ID, quota enforcement behaves differently than grouping all instances under one shared ID.

## 8. Distinguishing producer client ID and consumer client ID in Spring Kafka

A Spring Kafka application can both produce and consume records. Producer and consumer are two separate Kafka clients and can have different client IDs.

Example:

~~~yaml
spring:
  kafka:
    producer:
      properties:
        "[client.id]": orders-prod-publisher
    consumer:
      properties:
        "[client.id]": orders-prod-consumer
      group-id: orders-worker
~~~

Here:

- `orders-prod-publisher` identifies the producer sending records.
- `orders-prod-consumer` identifies the consumer client reading records.
- `orders-worker` is the group ID identifying the consumer group coordinating topic reads.

Spring Kafka also offers `clientIdPrefix` on `@KafkaListener` to prefix client IDs for consumers created by the listener container. When a listener uses concurrency, the framework may append suffixes to distinguish consumer instances in the container. That attribute serves consumer client IDs and does not replace producer `client.id` configuration.

Do not reuse the exact same name for producer, consumer, and `AdminClient` if the goal is investigating each client type separately. Adding role suffixes makes logs and metrics clearer, such as `publisher`, `consumer`, and `admin`.

## 9. Common mistakes when setting client.id

**Letting Kafka auto-generate default names in production.** Default names do not reveal service, environment, or role. When many applications share a cluster, searching logs and metrics becomes harder.

**Using a different client ID per message.** `client.id` identifies a Kafka client, not a message. Generating per-record IDs inflates cardinality and makes dashboards unusable.

**Using client.id as event ID.** One producer sends many events that share its client ID. Generate a dedicated event ID in the payload or header.

**Using client.id as trace ID.** One producer sends records from many traces. Propagate trace context per record when distributed steps must be linked.

**Assuming client.id authenticates a service.** `client.id` is self-declared by the client. Use SASL/TLS and ACLs for authentication and authorization.

**Assigning the same ID to streams with different purposes.** If replay, primary publishing, and audit publishing require separate investigation, assign distinct roles or appropriate labels.

**Adding pod names to every client ID without considering cardinality.** This helps trace individual instances, yet creates many short-lived metric series when workloads scale continuously. Consider using logs and resource attributes for instance identity.

**Changing client.id in config and expecting a running producer to rename itself.** `KafkaProducer` captures configuration at initialization. Recreate the producer to apply the new value.

## 10. Setup and verification workflow

When deploying a new producer, define tracing goals first and then choose a naming pattern:

1. Identify the publishing service and runtime environment.
2. Identify the producer role, such as primary publisher, replay, or audit.
3. Choose a stable client ID based on service, environment, and role.
4. Decide whether an instance suffix is needed; evaluate metric cardinality.
5. Configure client ID via Spring Boot producer properties or `ProducerFactory`.
6. Start the producer and check configuration logs to confirm the client ID took effect.
7. Verify producer metrics carry the corresponding client ID label.
8. Send a test record and inspect broker logs if request header verification is needed.
9. If using client quotas, confirm the quota entity client ID matches the actual producer name.
10. Document the naming convention so other services and environments apply it consistently.

During incident investigation, use `client.id` to isolate the producer, then combine event ID, topic, partition, offset, and trace ID to trace a specific event. Combining them tells you which client sent the request, where the record sits in Kafka, and which business flow created it.

## 11. Naming convention template for Spring Kafka systems

A convention applicable across multiple services:

~~~text
<service>-<environment>-<role>
~~~

Examples:

| Component | client.id |
|---|---|
| Primary orders producer | orders-prod-publisher |
| Orders replay producer | orders-prod-replay |
| Orders consumer | orders-prod-consumer |
| Billing producer | billing-prod-publisher |
| Orders admin client | orders-prod-admin |

If per-instance tracking is needed, append the instance suffix to the client ID of the relevant client type. Keep event ID and trace ID separate in record headers or payloads to trace individual messages across services.

`client.id` enables effective tracing when names are chosen intentionally, configurations are applied consistently, and logs/metrics actually collect the label. Treat it as the operational identity of the Kafka client, paired with event and trace identifiers at their proper scopes to investigate from producer to broker and downstream processing.
