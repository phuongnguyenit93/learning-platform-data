# Multiple Listeners Sharing the Same Retry Topic

In Spring Kafka, **non-blocking retry** routes failed records to one or more retry topics so the main topic's consumer can continue reading other records. Another listener container reads the retry topic once the record becomes eligible for retry. This mechanism is commonly declared with `@RetryableTopic` or a matching `RetryTopicConfiguration`.

When **multiple `@KafkaListener` endpoints consume the same source topic**, sharing retry topic names can cause unintended behavior: records from business flow A get delivered to listener B, the same record gets reprocessed by multiple consumer groups, or the DLTs of two flows get mixed together. This is an issue of **topology, topic identity, and consumer groups**, not merely a choice of backoff duration.

For resilient operations, distinguish three scenarios: multiple instances of *the same listener logic* scaling load; multiple listeners with *independent business logic* reading the same main topic; and multiple listeners *intentionally sharing* a retry queue in a custom-designed architecture. Each scenario requires different topic and group boundaries.

## 1. How Do Retry Topics Work?

With non-blocking retry, when a listener fails to process a record, Spring Kafka can publish the record to a retry topic and let the main consumer process subsequent records. A retry consumer receives the record, checks when retry is permitted, and passes the record to the corresponding listener once due. If attempts are exhausted or the exception is non-retryable, the record can route to a Dead Letter Topic (DLT).

```text
orders (main topic)
   |
   v
@KafkaListener processes business logic
   |
   +---- success ----------> complete, advance source offset
   |
   +---- retryable error --> orders-retry-... 
                                  |
                                  v
                            retry listener
                                  |
                     +------------+-------------+
                     |                          |
                  success                  still failing
                     |                          |
                  complete                retry onward / DLT
```

Actual topic names depend on retry topic suffixes, backoffs, attempt counts, suffixing strategy, and the Spring Kafka version's retry-topic reuse behavior. `orders-retry-...` in the diagram is illustrative only, not a guarantee of a fixed name string.

A retry topic is still a **normal Kafka topic**. It has partitions, retention, replication, ACLs, and consumer groups with their own committed offsets. Kafka itself does not know which Java method or listener bean a record belongs to. Delivering records to the right processor is the responsibility of retry topology configuration.

## 2. Three "Multiple Listener" Patterns to Distinguish

| Scenario | Intent | Typically suitable retry design |
|---|---|---|
| Multiple instances of the same service and same listener logic | Same group shares partitions to increase throughput | Instances share the retry topology of the same flow; Kafka distributes partitions across the group |
| Two independent business listeners subscribing to one source topic | Each business flow must receive and process every event | Use independent group IDs and separate retry/DLT topics per business flow |
| Two different listeners sharing the same source group | Split load or partitions between two handlers | Ensure handlers are business-equivalent; otherwise records reach only one handler and cause wrong results |
| Multiple handlers intending to share a manual retry topic | Deliberately funnel retry handling to one entry point | Design a single dispatcher/owner or explicit routing; do not rely on name collisions generated by `@RetryableTopic` |

For example, `billing-service` and `audit-service` both read `orders` for two different purposes: billing creates transactions, audit archives history. They must have different group IDs so each service reads all events. If they also subscribe to the same retry topic, each group can read **the other service's retry records as well**.

Conversely, if multiple replicas of `billing-service` share the same group and retry topology, that is usually valid load sharing: each partition of a retry topic is assigned to one member in the corresponding retry group. Instances must run compatible code, schemas, and processing policies.

## 3. Why Can Two `@RetryableTopic` Declarations Collide on Names?

Under automatic topology creation, Spring Kafka builds retry topic names from the main topic plus suffixes or backoff metadata. If two listeners both subscribe to `orders` and use retry configurations with identical suffixes, the topics the framework attempts to create or subscribe to can collide on name.

Example illustrating an unsafe setup:

```java
@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1_000))
@KafkaListener(topics = "orders", groupId = "billing-service")
public void bill(OrderEvent event) {
    billingService.process(event);
}

@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1_000))
@KafkaListener(topics = "orders", groupId = "audit-service")
public void audit(OrderEvent event) {
    auditService.archive(event);
}
```

The two listeners have different group IDs, so both read `orders` independently. However, if their retry topologies are created with identical retry/DLT topic names, both can point at those shared auxiliary topics. Then:

1. Billing fails processing and publishes the record to the shared retry topic name.
2. Billing's retry consumer reads the record using billing's retry group.
3. Audit's retry consumer, if subscribed to the same retry topic under a different group, can also read this record.
4. Both processing flows may execute different side effects on a record intended only for billing's retry.

If the retry consumers share a group, Kafka splits partitions across members without guaranteeing delivery to **the exact business listener that triggered the retry**. With different consumer groups on the same topic, records can be processed multiple times by unrelated business logic. Both failure modes must be avoided.

**Separating main-topic group IDs is necessary for two independent workflows, but insufficient to isolate retry topics.** You must also separate the names and ownership of the corresponding retry/DLT topologies.

## 4. Isolating Retries and DLTs with Distinct Suffixes

For multiple independent listeners on the same source topic, the clean approach is setting **distinct `retryTopicSuffix` and `dltTopicSuffix` per business flow**. Each listener then gets its own retry/DLT tree even though both read `orders`.

```java
@RetryableTopic(
        attempts = "4",
        backoff = @Backoff(delay = 1_000, multiplier = 2.0),
        retryTopicSuffix = "-billing-retry",
        dltTopicSuffix = "-billing-dlt",
        autoCreateTopics = "false")
@KafkaListener(
        id = "billingOrdersListener",
        topics = "orders",
        groupId = "billing-service")
public void bill(OrderEvent event) {
    billingService.processIdempotently(event);
}
```

The audit listener uses different suffixes:

```java
@RetryableTopic(
        attempts = "3",
        backoff = @Backoff(delay = 2_000),
        retryTopicSuffix = "-audit-retry",
        dltTopicSuffix = "-audit-dlt",
        autoCreateTopics = "false")
@KafkaListener(
        id = "auditOrdersListener",
        topics = "orders",
        groupId = "audit-service")
public void audit(OrderEvent event) {
    auditService.archiveIdempotently(event);
}
```

With this illustrative configuration, the topology can be visualized as:

```text
                       +--> billing-service
                       |      |
                       |      +--> orders-billing-retry[-...]
                       |      |           |
orders ----------------+      |           +--> orders-billing-dlt
                       |      |
                       +--> audit-service
                              |
                              +--> orders-audit-retry[-...]
                                          |
                                          +--> orders-audit-dlt
```

Names with `[-...]` indicate the framework may append delay/index segments. Verify final names from configuration and actual topic lists before provisioning. The two auxiliary topic sets must be **disjoint**.

`autoCreateTopics = "false"` in the example reflects a governed topic-provisioning model; retry/DLT topics must be pre-created with matching names and partitions. Without external provisioning, design topic creation into your deployment pipeline. Do not simply copy an example and expect retry topics to appear automatically.

## 5. Consumer Groups Do Not Replace Topic Isolation

Kafka stores committed offsets per **group ID + topic-partition** pair. If two groups read the same retry topic, they advance offsets independently; records remain available for both groups to receive.

| Retry topic | Consumer group | Kafka behavior |
|---|---|---|
| `orders-shared-retry` | `billing-retry-group` | Reads records in the topic with billing's own offsets |
| `orders-shared-retry` | `audit-retry-group` | Also reads records in the topic with audit's own offsets |
| `orders-shared-retry` | Two consumers in `shared-retry-group` | Consumers split partitions; each record goes to at most one consumer in the group at a time |

The two-different-groups case can cause **unwanted fan-out**. The same-group case can cause **wrong-handler routing** if consumers are not business-equivalent. Merely changing `group.id` cannot turn a shared retry topic into a private channel for each listener.

In Spring Kafka versions supporting non-blocking retry, the framework creates appropriate listener containers and group IDs for generated topics. Exact group ID naming can depend on listener configuration and framework version; check startup logs and consumer group state rather than assuming retry group IDs always match the main group ID.

When two workflows must process all original events, they need **independent main group IDs**. When they must retry independently, they also need **independent retry/DLT topics**. Both decisions complement each other.

## 6. Multiple Instances of the Same Listener: When Is Sharing Right?

Not every case of sharing a retry topic is problematic. A service running multiple instances with identical listener config and the same processing group can share a retry topology to scale processing capacity.

Example:

```text
orders
   |
   +--> billing instance A --+
   |                         |
   +--> billing instance B --+--> same group billing-service
                             |
                             v
                      billing's retry topic
                             |
                     +-------+-------+
                     |               |
                 retry A         retry B
                 same billing retry group
```

Instances must run identical or compatible logic. Kafka distributes partitions among consumers in the same group; there is no need to create separate retry suffixes per pod/instance. Creating a dedicated retry topic per pod can spawn excessive topics, hinder scaling, and complicate progress tracking when pods are replaced.

Distinguish **multiple replicas of the same flow** from **multiple independent business flows**. Only the latter needs separate retry topologies by business name, not by running instance count.

## 7. Ownership Boundaries When Intentionally Sharing a Retry Topic

Sometimes an architecture wants a shared retry queue for multiple event types or business producers—such as a centralized error-handling service. This is safe only with a **designated single consumer owner** and an explicit routing contract.

An intentional design might look like:

```text
orders / payments / shipments
            |
            v
  services emit records needing retry
            |
            v
     shared-retry topic
            |
            v
    shared-retry-dispatcher
            |
    +-------+--------+
    |       |        |
  order   payment  shipment
 handler  handler   handler
```

In this model, the dispatcher must know message types, schema versions, owning business flows, and retry rules. It also needs idempotency, retry budgets, scheduling if delays are needed, DLTs, and per-record-type observability. **A plain `@KafkaListener` reading a shared topic does not automatically provide `@RetryableTopic`'s non-blocking delay behavior**; you must use proper retry-topic infrastructure or build scheduler/consumer-pause logic yourself.

Never achieve sharing by letting multiple `@RetryableTopic` annotations collide on names and hoping the framework routes by listener ID. Kafka topics do not store "which method should receive this record" as an independent routing guarantee.

For two flows with different retry policies, schemas, transaction boundaries, or owners, separating topics is usually easier to operate and safer than merging them. Merge only with clear architectural justification and processing ownership.

## 8. DLTs Must Also Be Isolated Properly

Many teams catch retry-topic collisions yet still leave the default shared DLT. That can dump failed records from multiple flows into one investigation bucket, obscuring ownership and replay policies.

Example where billing and audit use different retry suffixes yet share `orders-dlt`:

```text
orders-billing-retry-* ----+
                           +----> orders-dlt
orders-audit-retry-* ------+
```

If each listener has its own DLT consumer on the same topic with different groups, both can read every DLT record. If they share a group, they split records with no guarantee of reaching the right owner. This repeats the retry-topic problem.

Choose one of two options:

1. **Per-business DLT:** `orders-billing-dlt`, `orders-audit-dlt`, with dedicated consumers, runbooks, and replay procedures.
2. **Intentional centralized DLT:** one shared owner receives all records, classifies by headers or a stable envelope, and owns routing/replay.

Do not use a shared DLT merely to reduce topic counts without resolving data access permissions, retention, schema compatibility, replay, and incident ownership.

## 9. Topic Names, Attempt Counts, and Reuse Strategies

`@RetryableTopic` does not necessarily create one retry topic per retry attempt. The number of retry topics depends on the backoff schedule and suffix/reuse strategy. With exponential backoff, the framework may create multiple delay-based topics. With fixed delay, depending on version and reuse configuration, several retries may reuse one retry topic within **the same topology**.

Two concepts not to confuse:

- **Reusing a retry topic within one topology:** multiple attempts of the same listener logic reuse a topic per retry framework configuration.
- **Sharing a retry topic across two independent business listeners:** two listeners with different owners or groups accidentally subscribe/publish to the same topic name.

The first strategy can be a valid Spring Kafka optimization. The second demands explicit design due to crosstalk risk. Choose `retryTopicSuffix` so topology names never collide, even with identical delays or attempt counts.

Document the actual topic map after application startup or provisioning. Never rely solely on `@RetryableTopic(attempts = "4")` to guess how many topics exist or what they are named.

## 10. Partitions, Ordering, and Latency

Retry topics generally need partition counts matching how the framework publishes failed records and how listeners consume them. If retry/DLT targets preserve source partitions, target topics must have enough partitions to accept them. When a source topic adds partitions, auxiliary topics may also need updates per design.

**Non-blocking retry can alter processing order.** While a failed record waits in a retry topic, the main topic listener can process subsequent records before the failed record is retried. For workflows requiring per-key ordering, such as balance updates or order state transitions, evaluate whether out-of-order completion is acceptable.

Example:

```text
orders partition 0:
  offset 100: OrderConfirmed  --> fails, to retry topic
  offset 101: OrderCancelled  --> succeeds on main topic

Later:
  retry offset 100 runs again
```

If `OrderCancelled` must run after `OrderConfirmed`, using retry topics can break business invariants. Splitting retry topics per listener **does not fix ordering**. Design idempotent state transitions, version checks, or choose blocking retry if strict ordering is mandatory.

Additionally, each independent listener has its own retry schedule and backlog. When billing hits an outage, billing's retry backlog can grow while audit runs normally. Topic isolation helps separate load pressure, yet you still must plan total retry consumers, broker connections, partitions, and cluster resources.

## 11. Error Classification and DLT Handlers per Flow

Two workflows may classify the same exception differently. For instance, a payment gateway error may be retryable for billing yet irrelevant to audit. If they share a retry chain, policies and ownership blur quickly.

With `@RetryableTopic`, you can declare listener-specific exclusions:

```java
@RetryableTopic(
        attempts = "4",
        backoff = @Backoff(delay = 1_000),
        exclude = {
                InvalidBillingPayloadException.class,
                UnsupportedBillingVersionException.class
        },
        retryTopicSuffix = "-billing-retry",
        dltTopicSuffix = "-billing-dlt")
@KafkaListener(topics = "orders", groupId = "billing-service")
public void consumeBilling(OrderEvent event) {
    billingService.processIdempotently(event);
}
```

For audit, exception classification and backoffs can differ. Separating topologies empowers each team to tune retry budgets, DLT policies, and runbooks without directly impacting other teams.

When configuring `@DltHandler`, verify which topology the handler is bound to. Do not assume that merely having `@DltHandler` methods in the same app guarantees DLT records from different listeners route to the right handler when topic names collide.

## 12. Topic Provisioning Configuration and Resource Limits

Splitting retry/DLT topics per business flow increases topic and partition counts. That is a cost to budget for, not a reason to share topologies improperly.

Suppose 8 independent flows each use a 12-partition source topic, three retry topics, and one DLT. If each auxiliary topic also has 12 partitions, total auxiliary partitions equal:

```text
8 flows × (3 retry + 1 DLT) × 12 partitions
= 384 auxiliary partitions
```

This number is illustrative; actual retry topic count depends on backoff/reuse configuration. Capacity planning must include replication, physical replicas, file handles, broker memory, and network bandwidth. You can reduce retry topic count with appropriate reuse strategies while preserving independent processing boundaries.

Provision topics via IaC or clear operational workflows with these parameters:

| Attribute | What to decide |
|---|---|
| Partition count | Parallelism and source/target partition mapping |
| Replication factor | Broker fault tolerance |
| `min.insync.replicas` | Durability requirement when producers use `acks=all` |
| Retention | How long retry/DLT records must be kept during incidents and investigations |
| ACL | Which services may publish/consume each flow's topics |
| Monitoring | Lag, retry rate, publish errors, DLT backlog, and record age |

If using `autoCreateTopics = "false"`, all corresponding topics must exist before listeners receive traffic. If using auto-creation, verify the created topic configuration in production rather than assuming broker defaults suit critical events.

## 13. Observability: Identifying Which Topology Holds a Record

In systems with multiple listeners reading the same main topic, main-topic metrics alone cannot reveal which business flow's retries are failing. Observe per listener ID, group ID, retry topic, and DLT.

Signals to collect:

- Records published to each flow's retry topics.
- Consumer lag and age of waiting records on retry topics.
- Success/failure rate per retry attempt and actual wait times.
- Records entering the DLT by business flow, exception class, and schema version.
- Retry/DLT publish failures: timeouts, authorization, serializers, and partition mapping.
- Rebalances, retry consumer counts, committed offsets, and pause/resume status.
- Gap between failed source records and successfully recovered records.

An investigation log should include `eventId`, source topic, partition, offset, listener ID or owner, current retry topic, attempt, exception, and destination. Keep event IDs out of metric labels to avoid excessive cardinality. If multiple topologies share auxiliary topic names, logs become much harder to attribute—a configuration red flag worth checking.

A dashboard layout that works well:

```text
Orders event pipeline
  billing-service:
    main lag  | billing retry lag | billing DLT count
  audit-service:
    main lag  | audit retry lag   | audit DLT count
```

With isolated topic names, operations can pause or fix one flow without touching another flow's retry backlog.

## 14. Common Failure Scenarios

| Symptom | Possible cause | Resolution direction |
|---|---|---|
| Billing fails yet audit also receives billing's retry records | Two listeners share a retry topic with different groups | Set distinct `retryTopicSuffix` per business flow; inspect consumers subscribed to auxiliary topics |
| Retry record handled by the wrong method | Listeners with different logic share a retry topic and same group | Split topologies; never rely on group assignment for business routing |
| One record appears in two DLT consumers | Colliding DLT names read independently by two groups | Separate `dltTopicSuffix` or designate one shared DLT owner/dispatcher |
| Listener receives no retries after deploy | Retry topic not provisioned, bad ACLs, or mismatched subscription/topic name | Check actual topics, groups, ACLs, and retry topic infrastructure |
| More auxiliary topics created than expected | Backoff/suffixing or reuse strategy creates multiple retry topics | Map topic names and partitions per topology; review reuse settings |
| Retry succeeds yet side effects duplicate | Record redelivered after crash/rebalance; another group reads same retry topic | Design idempotency and verify topic/group ownership |
| Audit starts processing out of order | Older record sits in retry topic while newer records pass through main topic | Review ordering requirements; consider blocking retry or version checks |
| One congested flow drives up cluster-wide load | Retry storm, too many retry consumers, or DLT publisher failing | Bound backoff/attempts, monitor capacity, and apply load shedding |

When investigating an incident, verify the **actual topics being published to and subscribed to**, not just annotation parameters in source code. Two different-looking annotations can still produce colliding topic names after suffixing strategies apply; conversely, one annotation can create multiple retry topics whose full names are not written verbatim in code.

## 15. Safe Rollout When Adding a New Listener

Suppose an app already has a billing listener and wants to add a fraud detection listener also reading `orders`. A safe rollout process should include:

1. Decide whether fraud needs **every** event or shares load with billing. If it needs all events, use a separate `group.id`.
2. Define fraud's retry/backoff, exception classification, and DLT owner.
3. Pick unique `retryTopicSuffix` and `dltTopicSuffix` that do not collide with billing or existing flows.
4. Determine exact retry topic names per Spring Kafka version, backoff schedule, and suffixing strategy.
5. Provision auxiliary topics with matching partitions, replication, retention, and ACLs.
6. Set explicit listener IDs and confirm the framework builds the expected retry/DLT consumer topologies.
7. Use test data to fail only billing, verifying audit/fraud never receive billing's retry records.
8. Fail only fraud, verifying records traverse only fraud's retry/DLT topics.
9. Verify committed offsets, duplicates/idempotency, restarts, and rebalances for each group.
10. Roll out incrementally, watching per-flow lag and DLT rates before ramping traffic.

In tests, use records with clear event IDs and origins. Seeing records enter a retry topic is not enough; confirm **which listener actually processes the record** and **how many times side effects execute**.

## 16. Core Principles

1. Retry topics are normal Kafka topics; brokers do not know which listener method owns a record.
2. Multiple replicas of the same listener logic may share a retry topology; never create per-pod suffixes.
3. Multiple independent business listeners on one main topic generally need separate group IDs **and** separate retry/DLT topics.
4. Never assume separate group IDs isolate records when two groups still read the same retry topic.
5. Set business-unique retry and DLT suffixes via `retryTopicSuffix` and `dltTopicSuffix`.
6. Verify actual topic names because backoff, suffixing strategy, and topic reuse change the generated topology.
7. If intentionally sharing a retry topic, build an explicit dispatcher/ownership design and proper delay mechanism—never rely on accidental name collisions.
8. Non-blocking retry can change processing order; idempotency, schema compatibility, and side-effect controls remain mandatory.
9. Provision retry/DLT topics and monitor per flow, not just per source topic.
10. Test cross-listener crosstalk before rollout to avoid misrouted processing or unintended replays.

**Conclusion:** "Multiple listeners sharing the same retry topic" is not always wrong: replicas of the same listener logic can share a retry topology to scale. But when listeners have independent business logic or consumer groups, sharing retry topics due to name collisions leads to cross-reads, duplicate processing, and unclear DLT ownership. Reliable operation requires defining clear per-flow boundaries, setting distinct retry/DLT suffixes where needed, and verifying the real topology through testing and production observability.
