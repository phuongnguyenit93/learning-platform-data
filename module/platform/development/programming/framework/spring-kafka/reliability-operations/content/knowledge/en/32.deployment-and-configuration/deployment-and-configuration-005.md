# Configuring `transactionIdPrefix` per Instance in Spring Kafka

## 1. The Problem When Multiple Instances Share Kafka Transactions

Suppose the `orders-event-service` is deployed across three replicas:

```text
Kubernetes Deployment: orders-event-service (replicas=3)
    |
    +-- pod-A: reads orders, sends Kafka events in a transaction
    +-- pod-B: reads orders, sends Kafka events in a transaction
    +-- pod-C: reads orders, sends Kafka events in a transaction
```

Each replica uses Spring Kafka with `KafkaTemplate` or a transactional `@KafkaListener`. If all three share a configuration like:

```yaml
spring:
  kafka:
    producer:
      transaction-id-prefix: orders-tx-
```

then the prefix is **identical** across every replica. When the producer factory creates transactional producers, each producer requires a complete `transactional.id`. If two active producers end up receiving the **same `transactional.id`**, the Kafka broker grants the newer producer a higher producer epoch and **fences** the older one.

The consequences can include:

- A pod mid-processing unexpectedly hits `ProducerFencedException`.
- Open transactions are aborted or fail to commit.
- Listener transactions fail, causing messages to be reprocessed according to offset/error-handler policy.
- Errors appear intermittently, commonly right after scale-outs, rolling deployments, or restarts.
- Dashboards record transaction aborts and Kafka listener failures even though business logic did not change.

**Goal of this lesson:** design `transactionIdPrefix` to be **distinct across application instances that may run concurrently**, while still supporting producer caching, restarts, scaling, and intentional broker fencing of stale producers when truly needed.

In the context of *Spring Kafka Reliability Operations → Deployment and Configuration*, this is a **deployment decision**, not merely setting a property in `application.yml`.

## 2. Understanding `transactional.id` and `transactionIdPrefix`

### 2.1. What Is `transactional.id`?

`transactional.id` is the producer's transactional identity at the Kafka broker. It enables the broker and transaction coordinator to recognize producer sessions sharing the same logical identity for recovery and **fencing older sessions**.

In a raw Kafka client, a transactional producer is typically created with:

```java
Properties properties = new Properties();
properties.put(
        ProducerConfig.BOOTSTRAP_SERVERS_CONFIG,
        "kafka:9092");
properties.put(
        ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
        StringSerializer.class);
properties.put(
        ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
        StringSerializer.class);
properties.put(
        ProducerConfig.TRANSACTIONAL_ID_CONFIG,
        "orders-prod-instance-01-producer-0");

KafkaProducer<String, String> producer =
        new KafkaProducer<>(properties);

producer.initTransactions();
```

This snippet illustrates Kafka client producer configuration and assumes imports from `org.apache.kafka.clients.producer`, `java.util.Properties`, and `org.apache.kafka.common.serialization.StringSerializer`. When using Spring Kafka, you **do not** need to manually manage `initTransactions()`/`beginTransaction()`/`commitTransaction()` per message if you use the framework's transaction support.

### 2.2. What Is `transactionIdPrefix`?

In Spring Kafka, `DefaultKafkaProducerFactory` supports a **transaction ID prefix**. From this prefix, the factory manages producers with concrete `transactional.id` values, typically combining the prefix with a suffix determined by the factory/strategy.

Conceptual example:

```text
Spring Kafka transactionIdPrefix:
    orders-prod-podA-

Transactional IDs generated by producer factory:
    orders-prod-podA-0
    orders-prod-podA-1
    orders-prod-podA-2
```

The suffixes in the example illustrate the concept, **not a guarantee of suffix ordering across every Spring Kafka version**. The objective is ensuring the ID set generated on pod A **never overlaps** with the ID set actively used by pod B or pod C.

In short:

\[
\text{transactional.id} = \text{transactionIdPrefix} + \text{suffix managed by factory}
\]

Never hardcode a static `transactional.id` inside the producer properties of a factory expected to create **multiple concurrent transactional producers** and assume Spring Kafka will automatically make it unique.

### 2.3. Distinguishing Commonly Confused Identifiers

| Property | Role | Needs to Be Unique per Pod? |
| --- | --- | --- |
| `transactional.id` | Producer transaction identity at the broker; governs fencing | Must not collide across **concurrent producers that are not intentional replacements** |
| `transactionIdPrefix` | Prefix Spring Kafka uses to generate transactional IDs | **Should be unique per instance/factory that may run concurrently** |
| `client.id` | Client name for metrics, logs, and broker-side observability | Should help distinguish clients, but does not replace transactional ID |
| `group.id` | Consumer group identity for partition distribution and offset commits | Usually **shared across consumer instances** of one workload |
| `member.id` or `group.instance.id` | Consumer group member identity with specific membership semantics | Not a transactional producer ID |
| Kubernetes `Pod UID` | Unique identity of a single Pod object | Suitable as an instance ID component |
| Kafka `producerId`/`producer epoch` | Broker-coordinated producer identity and epoch | Never chosen manually to replace `transactionIdPrefix` |

A common mistake is setting `transactionIdPrefix` equal to `group.id` under the assumption that "same consumer group means same transaction." That confuses **the set of consumers sharing partitions** with **the set of transactional producers needing distinct identities**.

## 3. How Does Kafka Producer Fencing Happen?

Suppose two replicas use the exact same full transactional ID:

```text
T0  Pod A creates producer:
    transactional.id = orders-prod-0
    broker assigns producer epoch = 7

T1  Pod A starts a transaction and sends messages.

T2  Pod B creates producer:
    transactional.id = orders-prod-0
    broker accepts new session, epoch increments to 8

T3  Pod A tries to send more or commit with old epoch.
    Broker rejects old session -> producer is fenced.

T4  Pod A must treat the old producer as invalid.
```

Fencing is a **data-protection mechanism**, not a Kafka bug. It stops two producer sessions with the same logical identity from committing conflicting transactions simultaneously.

However, distinguish two different scenarios:

1. **Intentional fencing:** an old instance lost ownership or was replaced; the new producer reuses the same logical transactional ID to invalidate the stale "zombie" producer.
2. **Misconfiguration fencing:** two independent pods doing normal work accidentally receive the same transactional ID; each pod keeps fencing the other.

Configuring a per-instance prefix aims to **prevent the second scenario**, without disabling protective fencing when a stale session truly needs to be replaced.

### A Distinct Prefix Does Not Eliminate Every `ProducerFencedException`

A producer can still be fenced if a new session with the **same ID** appears due to restarts, improper factory sharing, or producer cache behavior. Kafka also throws other exceptions such as transaction timeouts, authorization failures, or broker/network errors. Diagnose root causes from actual logs and configs rather than assuming every transaction error is a prefix bug.

## 4. Rules for Designing a Per-Instance Prefix

An easy-to-read prefix convention:

```text
<environment>-<application>-<workload>-<instance-id>-
```

Examples:

```text
prod-orders-event-service-order-consumer-7e42a3-
prod-orders-event-service-order-consumer-8f58c1-
staging-orders-event-service-order-consumer-42ad91-
```

Shortened IDs here are illustrative only; in real configs, use an identifier strong and stable enough to guarantee uniqueness across the Kafka cluster.

### 4.1. Mandatory Conditions

- **No collisions among producers that can run concurrently** on the same Kafka cluster, unless intentionally reusing an ID to fence a prior producer.
- **Each instance gets its own suffix namespace:** pod A's prefix differs from pod B's, even if both factories generate suffixes `0`, `1`, `2`.
- **Distinct across workloads sharing a cluster** if they could generate overlapping IDs—for example, a billing deployment and an orders deployment.
- **Determined before the producer factory begins creating transactional producers**; never mutate a running factory's prefix per message.
- **No credentials or sensitive info**; transactional IDs can appear in logs, broker state, and observability systems.

### 4.2. Where Does the Instance ID Come From?

| Source | Strengths | Things to Watch |
| --- | --- | --- |
| Kubernetes `metadata.uid` | Unique per Pod object; fits Deployment/ReplicaSet | Changes when a Pod is recreated; requires Downward API env var |
| Kubernetes `metadata.name` | Readable in logs; distinct across live Pods | Can be reused in StatefulSets or after recreate; check overlap and semantics |
| StatefulSet ordinal | Stable positional identity when a Pod is replaced | Reuses prefix with the same ordinal for replacement; must ensure no two active workers hold the same identity |
| Orchestrator-assigned VM/container instance ID | Tied to managed instances | Needs allocation/reclamation policy to avoid collisions |
| Startup-generated UUID | Easily unique for new processes, including local | Changes on every restart; cannot pin stable logical ownership |
| Hostname | Convenient in simple setups | Not always unique across containers, especially with static configs or multiple processes/host |
| Consumer group ID | Usually shared across replicas | **Unsuitable as the unique instance component** |
| `client.id` | Used for client observability | Does not guarantee a unique transactional ID |

**Sensible default for Kubernetes Deployments:** use Pod UID combined with app name and environment. For StatefulSets that want to leverage fencing of older sessions when an ordinal is replaced, you can choose a stable ordinal, provided rollout/membership guarantees two valid instances never hold the same identity concurrently.

### 4.3. Prefix Must Remain Consistent Over an Instance's Lifetime

Do not generate a new value on every message send:

```java
// Avoid: changing the transaction prefix on every message.
String prefix = "orders-" + UUID.randomUUID() + "-";
```

That defeats `DefaultKafkaProducerFactory`'s producer caching and identity management. Generate or supply the instance identity **once at startup**, configure the prefix before the factory creates producers, and keep it constant throughout the instance's lifetime.

Important distinction: **one UUID per process startup is fine**, whereas **a new UUID per transaction/message** misuses the prefix.

## 5. Configuring via Spring Boot `application.yml`

With Spring Boot 3.x and Spring Kafka 3.x, the standard property is:

```yaml
spring:
  kafka:
    bootstrap-servers: "kafka-1:9092,kafka-2:9092,kafka-3:9092"
    producer:
      transaction-id-prefix: "orders-${APP_ENV:local}-${INSTANCE_ID:local-dev}-"
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.apache.kafka.common.serialization.StringSerializer
      acks: all
```

In a Spring Boot project, `${APP_ENV:local}` and `${INSTANCE_ID:local-dev}` are **property placeholders**. The part after the colon is a fallback when no corresponding environment variable or property is set.

**Warning on static fallbacks:** `local-dev` is safe only when running **strictly one local instance** with that configuration. If two local processes run together or a production deploy omits `INSTANCE_ID`, they share the same prefix and risk fencing. Production should **require an instance ID** rather than falling back to a static value.

A multi-process local variant generates an ID at startup or passes one from the launcher:

```bash
APP_ENV=dev INSTANCE_ID=developer-one ./mvnw spring-boot:run
```

On Windows/PowerShell, set environment variables with PowerShell syntax or pass properties via your Spring Boot run command. Never reuse a fixed host name or dummy instance ID across multiple JVMs hitting the same Kafka cluster.

### How Does Spring Boot Auto-Configure Transactions?

When `spring.kafka.producer.transaction-id-prefix` is set and the required auto-configurations are present, Spring Boot can auto-configure a transactional `ProducerFactory` and `KafkaTransactionManager` bound to the Kafka producer, enabling `KafkaTemplate` to send within transactions.

These components **can be overridden by application-declared beans**. If you declare a custom `ProducerFactory` or `KafkaTransactionManager`, ensure the prefix and transaction manager use **the exact same factory**; never assume custom beans still inherit all Boot auto-configured properties.

Setting a producer prefix **does not automatically turn all business logic into a Kafka transaction**. You must still execute sends inside a transaction scope or configure listener container transactions for consume-process-produce flows.

## 6. Kubernetes: Injecting Pod UID into `transactionIdPrefix`

### 6.1. Why Does Pod UID Fit Deployments?

A Kubernetes Deployment can have multiple Pods alive concurrently, including both old-version and new-version Pods during a rolling update:

```text
before rollout:
  orders-abc-1  uid=1111
  orders-abc-2  uid=2222

during rollout:
  orders-abc-1  uid=1111  (old Pod still running)
  orders-abc-2  uid=2222  (old Pod still running)
  orders-def-1  uid=3333  (new Pod already running)
  orders-def-2  uid=4444  (new Pod already running)
```

If the prefix is simply `orders-prod-`, all pods can generate colliding transactional IDs. Including the Pod UID separates ID sets per pod even when old and new pods overlap during rollouts.

### 6.2. Illustrative Deployment Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-event-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders-event-service
  template:
    metadata:
      labels:
        app: orders-event-service
    spec:
      containers:
        - name: app
          image: example/orders-event-service:1.0
          env:
            - name: APP_ENV
              value: "prod"
            - name: INSTANCE_ID
              valueFrom:
                fieldRef:
                  fieldPath: metadata.uid
            - name: SPRING_KAFKA_PRODUCER_TRANSACTION_ID_PREFIX
              value: "orders-prod-$(INSTANCE_ID)-"
```

Kubernetes supports expanding earlier environment variables inside later variable values using `$(VARIABLE_NAME)`. Here `INSTANCE_ID` must appear before `SPRING_KAFKA_PRODUCER_TRANSACTION_ID_PREFIX`. Kubelet substitutes `$(INSTANCE_ID)` with the actual Pod UID when starting the container.

Spring Boot relaxed binding maps `SPRING_KAFKA_PRODUCER_TRANSACTION_ID_PREFIX` to `spring.kafka.producer.transaction-id-prefix`. With this approach, the Deployment's environment variable overrides defaults in `application.yml`.

**Do not unintentionally supply two independent prefix sources.** For example, if `application.yml` builds the prefix from `INSTANCE_ID` while the Deployment also sets `SPRING_KAFKA_PRODUCER_TRANSACTION_ID_PREFIX`, know which takes precedence. Pick one deployment convention for clarity.

### 6.3. A Simpler Configuration

To keep prefix formatting logic inside the application:

```yaml
spring:
  kafka:
    producer:
      transaction-id-prefix: "orders-${APP_ENV}-${INSTANCE_ID}-"
```

And Kubernetes only needs:

```yaml
env:
  - name: APP_ENV
    value: "prod"
  - name: INSTANCE_ID
    valueFrom:
      fieldRef:
        fieldPath: metadata.uid
```

In production, omit fallbacks on `APP_ENV`/`INSTANCE_ID` so the application fails startup if either variable is missing. That is far safer than accidentally running an entire deployment under `orders-local-local-dev-`.

**Tip:** keep the prefix short enough for easy observability; there is no need to cram full deployment metadata, Git SHAs, or timestamps into the prefix when Pod UID already guarantees uniqueness. Record app versions in logs/traces/metrics instead of making them churn transactional identities.

## 7. StatefulSet, Stable Identity, and Producer Replacement

In a StatefulSet, Pod names and ordinals are positionally stable, such as `orders-worker-0`, `orders-worker-1`. Two main strategies exist:

**Strategy A — Prefix by Pod UID:**

```text
orders-prod-uid-1111-
orders-prod-uid-2222-
```

Every newly created Pod gets a fresh prefix. The advantage is isolation between overlapping instances. The trade-off is that upon Pod replacement, old transactional IDs are not reused to fence old producers under the same identity. The broker still manages transaction timeouts and state, though there is no same-ID replacement fencing across UIDs.

**Strategy B — Prefix by ordinal/stable slot:**

```text
orders-prod-worker-0-
orders-prod-worker-1-
```

When `worker-0` is replaced, the new producer with the same suffix/transactional ID can fence any lingering old producer. This works when ownership logic guarantees **at most one active `worker-0` at a time**. However:

- You must coordinate ownership when an old node/pod has not yet terminated cleanly.
- If two processes both believe they are `worker-0`, producers will fence each other continuously.
- If the suffix strategy/cache does not generate the same suffix at the same moment, do not assume every old session is fenced immediately.
- Never treat a stable prefix as a complete leader-election mechanism; pair it with membership/leases and business idempotency.

**Decision criterion:** if the primary goal is **collision avoidance during Deployment scale-outs**, Pod UID is the simplest choice. If you specifically require fencing old sessions under a fixed logical identity, use a stable ID with deliberate ownership and fencing procedures.

## 8. When One Instance Has Multiple Concurrent Producers

A unique prefix **per instance** does not solve the entire problem. Within a single Spring Boot instance, multiple transactions may run concurrently:

```text
Pod A: prefix = orders-prod-podA-
    |
    +-- listener thread 1 --> producer suffix 0
    +-- listener thread 2 --> producer suffix 1
    +-- listener thread 3 --> producer suffix 2
    +-- KafkaTemplate transaction from service --> producer suffix 3
```

`DefaultKafkaProducerFactory` uses a cache/strategy to supply transactional producers for concurrent transactions. Spring Kafka has evolved how suffixes are allocated and reused across versions, so verify options against **your project's actual Spring Kafka version**.

Core design principles:

1. **Prefixes separate instances/factories.**
2. **Suffixes separate producers within the same factory** when concurrent transactions run.
3. **Producer cache** settings and concurrency levels must be compatible.
4. When no producer is available in the cache/suffix pool, transactions may fail or wait/retry according to configuration.

### 8.1. Kafka Listener Concurrency

Suppose:

```yaml
spring:
  kafka:
    listener:
      concurrency: 6
```

and a listener container is configured with transactions using that producer factory. In Spring Kafka versions that cache transactional producers with a suffix limit, ensure cache/suffix capacity **is sufficient for peak concurrent transactions**. If transactions also originate from `KafkaTemplate` outside listeners, add that demand too.

Do not infer from `concurrency=6` that every app uses exactly six `transactional.id`s: concurrent transaction count depends on containers, partition assignments, listener setup, producer usage, nested operations, and framework version. Still, setting the limit too low for concurrency is a frequent cause of producer-unavailable errors.

### 8.2. `TransactionIdSuffixStrategy` and `maxCache`

In Spring Kafka 3.2+, `TransactionIdSuffixStrategy` manages suffix allocation for transactional producers; matching versions include `DefaultTransactionIdSuffixStrategy` and cache/suffix pool bounds. Under certain configurations, exhausting available suffixes raises `NoProducerAvailableException`.

Therefore, when upgrading versions:

- Check the producer factory transaction docs for your **exact Spring Kafka version**.
- Identify the default suffix strategy and suffix reuse behavior.
- Match `maxCache` against actual concurrency.
- Test scale-outs, rolling restarts, and concurrent transactions.

**Do not confuse `NoProducerAvailableException` with cross-pod fencing:** one means the local factory's producer/suffix pool is exhausted; the other means the broker rejected an older producer due to a duplicate transactional identity. They require different fixes.

## 9. Setting the Prefix on `ProducerFactory` in Java

If not using Boot's auto-configuration property, create `DefaultKafkaProducerFactory` manually and set the prefix **before the factory is used**.

Spring Kafka 3.x, Java 17+ example using `String` serializers:

```java
import java.util.HashMap;
import java.util.Map;
import org.apache.kafka.clients.producer.ProducerConfig;
import org.apache.kafka.common.serialization.StringSerializer;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.core.DefaultKafkaProducerFactory;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.core.ProducerFactory;
import org.springframework.kafka.transaction.KafkaTransactionManager;

@Configuration
public class KafkaTxConfiguration {

    @Bean
    ProducerFactory<String, String> orderProducerFactory(
            @Value("${spring.kafka.bootstrap-servers}") String bootstrap,
            @Value("${app.kafka.instance-tx-prefix}") String txPrefix) {

        Map<String, Object> configs = new HashMap<>();
        configs.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrap);
        configs.put(
                ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class);
        configs.put(
                ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class);
        configs.put(ProducerConfig.ACKS_CONFIG, "all");

        DefaultKafkaProducerFactory<String, String> factory =
                new DefaultKafkaProducerFactory<>(configs);

        factory.setTransactionIdPrefix(txPrefix);
        return factory;
    }

    @Bean
    KafkaTemplate<String, String> orderKafkaTemplate(
            ProducerFactory<String, String> orderProducerFactory) {

        return new KafkaTemplate<>(orderProducerFactory);
    }

    @Bean
    KafkaTransactionManager<String, String> orderKafkaTransactionManager(
            ProducerFactory<String, String> orderProducerFactory) {

        return new KafkaTransactionManager<>(orderProducerFactory);
    }
}
```

Configuration:

```yaml
app:
  kafka:
    instance-tx-prefix: "orders-${APP_ENV}-${INSTANCE_ID}-"
spring:
  kafka:
    bootstrap-servers: "kafka:9092"
```

**Choose one approach:**

- Option A: use `spring.kafka.producer.transaction-id-prefix` for Spring Boot auto-configuration.
- Option B: explicitly declare the producer factory and transaction manager as above.

Do not declare two competing factories without knowing which factory `KafkaTemplate`, listener containers, and the transaction manager actually use. When an application has multiple producer factories, give each a distinct prefix if they can allocate transactional producers with overlapping suffixes.

### Never Hardcode `transactional.id` in the Properties Map

With Spring Kafka's producer factory approach:

```java
// Avoid configuring a fixed transactional.id for all producers
// while expecting the factory to generate independent IDs.
configs.put(
        ProducerConfig.TRANSACTIONAL_ID_CONFIG,
        "orders-shared-id");
```

Instead, pass the prefix to `DefaultKafkaProducerFactory` so the framework manages producers and suffixes cleanly.

## 10. Sending Messages Inside a Transaction

Setting a prefix only enables creating transactional producers. For messages to commit or abort as an atomic Kafka transaction unit, execute sends inside a transaction scope.

### 10.1. `KafkaTemplate.executeInTransaction`

```java
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Service;

@Service
public class OrderEventPublisher {

    private final KafkaTemplate<String, String> kafkaTemplate;

    public OrderEventPublisher(
            KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void publishOrderAndAudit(
            String orderId, String payload) {

        kafkaTemplate.executeInTransaction(operations -> {
            operations.send("orders.events", orderId, payload);
            operations.send(
                    "orders.audit",
                    orderId,
                    "published:" + orderId);
            return null;
        });
    }
}
```

Both sends run within the same Kafka transaction managed by `executeInTransaction`. If an exception aborts the transaction, consumers with `isolation.level=read_committed` will not see the aborted records under Kafka transaction semantics.

**Do not misread "atomic" as a transaction spanning all systems:** this covers only Kafka messages/offsets within the transaction scope. It does not pull database operations, HTTP APIs, or object storage into the same ACID transaction.

### 10.2. `@Transactional` with `KafkaTransactionManager`

Applications can also use `@Transactional` bound to the Kafka transaction manager:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.kafka.core.KafkaTemplate;

@Service
public class TransactionalPublisher {

    private final KafkaTemplate<String, String> template;

    public TransactionalPublisher(
            KafkaTemplate<String, String> template) {
        this.template = template;
    }

    @Transactional("orderKafkaTransactionManager")
    public void publish(String orderId, String payload) {
        template.send("orders.events", orderId, payload);
        template.send("orders.audit", orderId, "audit");
    }
}
```

This example references the bean named `orderKafkaTransactionManager` from Section 9's Java config. If using Spring Boot's auto-configured manager, the actual bean name may differ—verify in your Spring context. `@Transactional` requires transaction management to be enabled and calls to pass through the Spring proxy; internal calls within the same object (*self-invocation*) bypass the interceptor.

Do not use a default `DataSourceTransactionManager` assuming it manages Kafka transactions. In apps with multiple transaction managers, explicit qualifiers prevent mixing up transaction boundaries.

## 11. Consume-Process-Produce and Exactly-Once Semantics

A common use case:

```text
orders.input topic
       |
       v
  Kafka @Listener
       |
       v
  transform event
       |
       v
  orders.output topic
       |
       v
  commit consumer offset
```

When the listener container is properly configured with a Kafka transaction manager/producer factory, output records and processed consumer offsets can join **the same Kafka transaction**. On the broker, an aborted transaction hides its output from `read_committed` consumers, and the consumer group offset is not committed as processed.

This is the core of **exactly-once semantics (EOS) in Kafka-to-Kafka flows**. It does **not** mean:

- A message is never reprocessed in Java.
- An HTTP service is called strictly once.
- Database writes join the same Kafka transaction.
- Output topics never receive duplicates from non-transactional sources/flows.

In practice, listeners can reprocess records after a rollback. Therefore, side effects outside Kafka still need idempotency or an outbox pattern.

### 11.1. Consumer Reading Committed Records

For consumers that must ignore aborted messages:

```yaml
spring:
  kafka:
    consumer:
      properties:
        isolation.level: read_committed
```

`read_committed` does not restrict a consumer to a single producer; it controls visibility of records belonging to uncommitted or aborted transactions. Non-transactional messages remain readable under normal semantics.

### 11.2. Listener Containers Need Transaction Configuration

Giving a producer `transactionIdPrefix` **does not automatically make every Kafka listener execute consume-process-produce with EOS**. You must verify that the listener container factory uses a matching `KafkaTransactionManager` and container properties are wired for your Spring Kafka version.

In Spring Kafka 3.x, custom listener container factories must attach the corresponding transaction manager to container properties (exact APIs vary slightly across minor versions). With Spring Boot auto-configuration, verify the active factory actually receives the right manager, especially when declaring multiple producer or listener factories.

Simple listener example:

```java
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Component;

@Component
public class OrderEventListener {

    private final KafkaTemplate<String, String> template;

    public OrderEventListener(
            KafkaTemplate<String, String> template) {
        this.template = template;
    }

    @KafkaListener(
            topics = "orders.input",
            groupId = "orders-processors")
    public void onOrder(String payload) {
        String orderId = extractOrderId(payload);
        template.send("orders.output", orderId, payload);
    }

    private String extractOrderId(String payload) {
        // Illustrative example; production requires proper parser and validation.
        return payload;
    }
}
```

**The annotation above alone does not prove EOS.** You need a transaction-enabled listener container, the right producer factory, proper consumer group/offset management, and downstream `read_committed` consumers. If a listener runs without a Kafka transaction, `template.send(...)` may fail because the template uses a transactional producer outside an active transaction, or behave differently per config; test the actual transaction boundary.

## 12. Transaction IDs and Rolling Deployment Lifecycles

A rolling update can keep old versions running alongside new versions:

```text
             Rolling update

Old pod A (UID=A)  ------------------- shutdown
Old pod B (UID=B)  ----------- shutdown
New pod C (UID=C)       -------------------------
New pod D (UID=D)              ------------------

Prefixes:
    orders-prod-A-
    orders-prod-B-
    orders-prod-C-
    orders-prod-D-
```

Distinct prefixes prevent transactional producers from fencing each other merely because they belong to the same deployment. Even so, the system must account for:

- Consumer group rebalances as pods join and leave.
- Transaction duration vs. `max.poll.interval.ms` and `transaction.timeout.ms`.
- Graceful shutdown to avoid unnecessary transaction aborts.
- Record reprocessing after rebalances or crashes.
- Idempotent application side effects.

Never use a prefix unique **only per deployment version** like `orders-v1-` or `orders-v2-` when multiple pods run that version: all pods of that version still share the prefix.

### Rolling Restarts Can Change Prefixes

With Pod UID, the prefix changes whenever a Pod is recreated. This isolates instances, though old transactional IDs remain on the broker until the transaction coordinator expires/cleans them up per Kafka configuration.

That trade-off is usually acceptable for Deployments prioritizing collision avoidance. If your system needs to reuse a stable transactional ID to fence zombie producers, design stable ownership rather than random UIDs.

## 13. Transaction Timeout, Expiration, and Producer Cache

Beyond uniqueness, a transactional Kafka setup must understand these lifetimes:

| Config / Concept | Relates To | Risk |
| --- | --- | --- |
| Producer `transaction.timeout.ms` | Max duration a transaction may stay open | Long-running transactions can be aborted by the broker |
| Broker `transaction.max.timeout.ms` | Maximum transaction timeout the broker accepts | Producers requesting larger timeouts can be rejected |
| Broker `transactional.id.expiration.ms` | Expiration of idle transactional ID state | Producers cached idle too long may hit errors upon reuse |
| `DefaultKafkaProducerFactory` cache | Reusing transactional producers | Requires managing producer lifecycle and concurrent transaction count |
| Spring Kafka `maxAge` on producer factory | Proactively evicting idle/old producers before an age limit | Avoids reusing producers already expired by the broker |

Spring Kafka supports capping cached producer age in versions offering `DefaultKafkaProducerFactory#setMaxAge(Duration)`. When a transactional producer sits idle approaching broker expiration, refreshing it before reuse helps avoid unexpected fencing errors.

**Do not solve expiration by inventing a new prefix on every send.** Per-instance prefixes solve identity separation; producer refreshes and cache age limits solve a different lifecycle problem.

### A Transaction Should Not Encompass Overly Long Work

```text
beginTransaction()
  call slow 4-minute API
  process large 10-minute file
  send to Kafka
commitTransaction()
```

Long transactions can exceed timeouts, stall consumer progress, and raise abort rates. Keep work inside a Kafka transaction bounded; perform heavy work outside or split units architecturally while keeping offset/output semantics clear.

## 14. Multi-Instance Does Not Mean Shared Producer Factory

Some systems use:

- Multiple `KafkaTemplate` beans in the same process.
- Multiple `ProducerFactory` beans for different topics or clusters.
- Multiple listener container factories.
- One service performing both consume-process-produce and scheduled publishing.

### 14.1. Same Factory

If two `KafkaTemplate` instances reference **the same `DefaultKafkaProducerFactory`** configured with a prefix, that factory manages their shared producer cache as designed. Account for combined concurrency.

### 14.2. Multiple Factories

If two independent factories in the **same instance** share the prefix `orders-prod-podA-`, they can generate overlapping suffixes and collide on `transactional.id`. When multiple transactional factories target **the same Kafka cluster**, give each a distinct namespace prefix:

```text
orders-prod-podA-events-
orders-prod-podA-audit-
```

If factories target different Kafka clusters, uniqueness is scoped per cluster, though distinct naming still makes logs/metrics far easier to investigate.

### 14.3. Sharing Prefixes with Other Applications

Two applications may live in different Kubernetes namespaces yet bootstrap to the same Kafka cluster. Relying solely on hostname/pod name without an app/workload prefix may not prevent ID collisions everywhere. Put app/service/workload before instance ID:

```text
prod-order-sync-podA-
prod-billing-export-podA-
```

The Kafka transaction coordinator cannot tell these are "two different microservices" if they pick the same transactional ID.

## 15. Monitoring and Logging Transaction Identity

When fencing happens, you need to know **which producer and which instance** competed for the transaction identity.

Useful log fields:

```text
service
environment
podName
podUid / instanceId
transactionIdPrefix
producer clientId
topic
consumerGroupId
partition
listenerId
exceptionClass
transactionOutcome
deploymentVersion
```

Example event:

```json
{
  "event": "kafka_transaction_failed",
  "service": "orders-event-service",
  "environment": "production",
  "instanceId": "pod-uid-A",
  "transactionIdPrefix": "orders-prod-pod-uid-A-",
  "consumerGroupId": "orders-processors",
  "exceptionClass": "ProducerFencedException",
  "transactionOutcome": "ABORTED"
}
```

This is an illustrative log schema. Never assume Spring Kafka logs all these fields automatically; add appropriate logging/instrumentation.

**Cardinality note:** instance IDs and transactional IDs churn frequently across deploys and scaling. They are valuable in **logs/traces**, not as long-lived metric labels. Aggregate metrics should use bounded-cardinality labels such as `service`, `environment`, `listenerId`, `errorCategory`, and transaction outcome.

Signals to monitor:

| Signal | Meaning |
| --- | --- |
| Rising `ProducerFencedException` | Duplicate transactional ID or replacement/fencing needing investigation |
| Rising transaction aborts | Timeouts, application errors, or producer/consumer coordination anomalies |
| `NoProducerAvailableException` | Cache/suffix pool exhausted under high concurrency |
| Listener failures / error handler activations | Failed messages that may be reprocessed |
| Consumer lag | Failing flows building up backlog |
| Transaction duration | Transactions nearing timeout or slow downstreams |
| Restarts / rolling updates | Context for correlating incidents |
| Last successful processing | Detects services no longer completing transactions |

Exact metric names depend on Kafka client JMX metrics, Micrometer, Spring Kafka, and your exporter. Never assume identical metric names across versions; verify the actual metrics emitted in your deployment.

## 16. Testing Per-Instance Prefix Generation

Extract prefix construction into a unit-testable function instead of scattering it across YAML or multiple config classes.

### 16.1. Prefix Builder Function with an Explicit Contract

```java
package com.example.kafka.config;

import java.util.Objects;

public final class TransactionPrefix {

    private TransactionPrefix() {}

    public static String create(
            String environment,
            String application,
            String instanceId) {

        return valid(environment, "environment")
                + "-" + valid(application, "application")
                + "-" + valid(instanceId, "instanceId") + "-";
    }

    private static String valid(String value, String name) {
        Objects.requireNonNull(value, name + " is required");
        if (value.isBlank() || !value.matches("[A-Za-z0-9_-]+")) {
            throw new IllegalArgumentException(
                    name + " must contain only letters, digits, _ or -");
        }
        return value;
    }
}
```

This is an **application naming convention**, not a mandatory Kafka limit. Its aim is clean logging, traceability, and rejecting blank instance IDs before the producer factory initializes.

### 16.2. JUnit 5 Unit Tests

```java
package com.example.kafka.config;

import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class TransactionPrefixTest {

    @Test
    void twoInstancesHaveDifferentPrefixes() {
        String first = TransactionPrefix.create(
                "prod", "orders", "podA");
        String second = TransactionPrefix.create(
                "prod", "orders", "podB");

        assertNotEquals(first, second);
        assertEquals("prod-orders-podA-", first);
        assertEquals("prod-orders-podB-", second);
    }

    @Test
    void sameInstanceHasStablePrefix() {
        String first = TransactionPrefix.create(
                "prod", "orders", "podA");
        String again = TransactionPrefix.create(
                "prod", "orders", "podA");

        assertEquals(first, again);
    }

    @Test
    void missingInstanceIdFailsFast() {
        assertThrows(IllegalArgumentException.class,
                () -> TransactionPrefix.create(
                        "prod", "orders", ""));
    }

    @Test
    void differentWorkloadsDoNotShareNamespace() {
        assertNotEquals(
                TransactionPrefix.create("prod", "orders", "podA"),
                TransactionPrefix.create("prod", "billing", "podA")
        );
    }
}
```

These tests verify naming logic; they **do not prove Kafka transactions work** or that producers can never be fenced. Use broker integration tests for real behavior.

## 17. Integration Testing with a Kafka Broker

A test strategy can use `@EmbeddedKafka` or Testcontainers Kafka depending on environment and complexity. For Kafka transactions, the test broker must be configured appropriately for single-broker transaction state; otherwise tests can fail on internal transaction state topics rather than prefixes.

### 17.1. Testing Two Concurrent Instances

Model:

```text
Test broker
   |
   +-- ProducerFactory A:
   |     prefix = test-orders-A-
   |
   +-- ProducerFactory B:
         prefix = test-orders-B-
```

Steps:

1. Create two independent transactional producer factories, each with a distinct prefix.
2. Create corresponding `KafkaTemplate` instances.
3. Run multiple overlapping transactions from A and B.
4. Send messages with different keys to the test topic.
5. Using a `read_committed` consumer, verify committed outputs arrive with no duplicate-ID fencing.
6. Stop/close producer factories and verify cleanup.

For an identity-collision test, intentionally give two factories the same prefix in a scenario **strictly on a test broker**, and observe producer fencing once they allocate the same transactional ID. This test may need explicit timing around producer creation and suffix strategy, because **sharing a prefix does not always produce identical IDs immediately** across every version/configuration.

### 17.2. Testing Commit and Abort

```text
Transaction A:
  send record 1
  send record 2
  commit

Transaction B:
  send record 3
  abort

read_committed consumer:
  sees records 1, 2
  does not see aborted record 3
```

Never use `read_uncommitted` when asserting that aborted messages are hidden; the isolation level must match the test contract.

### 17.3. Testing Rolling Restarts and Scaling

Test:

- 1 → 3 → 5 replicas with Pod-UID-based prefixes.
- Rolling updates with overlapping old/new Pods.
- Restarting a Pod, assigning a new identity per the Deployment model.
- Restarting a stable StatefulSet slot to verify intentional fencing.
- Raising listener concurrency and launching concurrent transactions; watch for producer cache/suffix exhaustion.

Tests should capture each instance's actual prefix and broker errors, not merely end-to-end message counts. Distinguish failures caused by consumer group rebalances, transaction timeouts, networking, and producer fencing.

## 18. Common Configuration Errors

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `ProducerFencedException` appears after scale-out | Multiple replicas use a static prefix with colliding suffixes | Add a unique instance ID to the prefix |
| Works with one replica, fails with two replicas | Shared transactional identity | Inspect prefixes and producer factories on both |
| Rolling updates spike transaction aborts | Old/new pods overlap, prefix collision, or interrupted transactions | Check Pod identity, rollout, graceful shutdown, and broker logs |
| `NoProducerAvailableException` | Cache/suffix pool exhausted under high concurrency | Review `maxCache`/suffix strategy for your Spring Kafka version |
| Fenced after long idle period | Cached producer expired on the broker | Check broker `transactional.id.expiration.ms` and factory `maxAge` |
| Prefix looks right in YAML yet identical across Pods | Env var overridden wrongly or unexpanded | Verify effective property at startup and Pod UID |
| Two different `KafkaTemplate`s share one prefix | Two independent producer factories sharing namespace | Differentiate prefixes per factory/workload |
| Consumer reads records from aborted transactions | `isolation.level=read_uncommitted` or non-transactional flow | Configure `read_committed` and verify transaction scope |
| Transactional Kafka sends yet DB has duplicates | Kafka transactions do not cover the DB | Add idempotency/outbox with explicit data boundaries |
| Re-running job creates duplicate business events | Transactions do not replace business deduplication | Use business keys/idempotency by design |
| Prefix changes on every message | Generating UUID per send outside factory lifecycle | Generate prefix once at startup |
| Pod UID present yet Kafka still uses old prefix | Custom `ProducerFactory` ignores Boot property | Configure the exact factory and manager directly |
| Running two local JVMs triggers fencing | Static `local-dev` fallback | Assign a distinct `INSTANCE_ID` per process |
| Changing `group.id` under the same group to avoid fencing | Confusing consumer membership with producer identity | Keep `group.id` per consumer design; change the prefix |

## 19. Procedure for Investigating a Producer Fencing Incident

When `ProducerFencedException` or transaction commit failures appear in logs:

1. **Identify the instance:** capture service name, environment, pod name/UID, deployment version, and timestamp.
2. **Determine the effective prefix:** do not read only `application.yml`; inspect env vars, property overrides, and the actual factory bean in use.
3. **Enumerate producer factories:** how many factories run in the process, and do they share a Kafka cluster and prefix?
4. **Check for overlaps:** did a new pod start, rolling update run, autoscale trigger, restart happen, or consumer rebalance coincide?
5. **Find the colliding transactional ID:** compare full IDs if instrumentation/broker logs expose them, not just prefixes.
6. **Rule out other errors:** transaction timeouts, missing authorization, cache exhaustion, or broker instability can resemble transaction incidents.
7. **Fix configuration:** supply a unique instance identity or controlled stable ownership, then roll out cleanly.
8. **Audit data:** verify records/offsets committed properly per isolation level and idempotency; do not stop just because error logs stopped.
9. **Add alerting:** if fencing recurs after scaling, alert by error category and link a runbook.

Never react to fencing by immediately disabling Kafka transactions. Transactions may be preventing corrupt writes; first determine whether it is an ID collision or a lifecycle bug.

## 20. Hands-On Exercises

**Exercise 1 — Prove prefix collision.** On a test Kafka broker, create two `DefaultKafkaProducerFactory` instances with the same prefix. Drive them so two producers receive the same transactional ID and watch the older producer get fenced. Then assign separate prefixes and compare.

**Exercise 2 — Spring Boot configuration.** Run two local processes against the same Kafka cluster with `APP_ENV=dev` and two distinct `INSTANCE_ID`s. Send transactional messages from each process and verify both succeed.

**Exercise 3 — 3-replica Deployment.** Write a Kubernetes Deployment injecting `INSTANCE_ID` from `metadata.uid`. Use `spring.kafka.producer.transaction-id-prefix` to build per-pod prefixes. Verify all three pods have distinct prefixes.

**Exercise 4 — Rolling update.** Run a rolling update on the Deployment with overlapping old and new Pods. Monitor error rates, consumer lag, and transaction outcomes; confirm zero fencing from duplicate prefixes.

**Exercise 5 — Concurrent transactions.** Increase `spring.kafka.listener.concurrency` and add service-level transactional producer calls. Observe producer caching, suffix strategy, and producer-exhaustion errors, tuning for your version.

**Exercise 6 — Transaction commit/abort.** In one Kafka transaction, send two records and commit; in another, send one record and intentionally throw an exception. Use a `read_committed` consumer to verify only committed records are visible.

**Exercise 7 — Restart and stable identity.** Compare Pod-UID prefixes with StatefulSet-ordinal prefixes. Simulate an old instance still running while a new one starts; explain when fencing is desirable.

**Exercise 8 — DB side effects.** A listener reads Kafka, updates a database, and sends Kafka output. Trigger a failure after DB commit but before Kafka commit to observe duplicate side-effect risk; propose idempotency or an outbox.

**Exercise 9 — Monitoring.** Add structured logs containing `instanceId`, prefix, `consumerGroupId`, and error category. Design a dashboard for producer fencing, transaction aborts, consumer lag, and restarts.

**Exercise 10 — Multi-factory.** Inside a single pod, create two transactional producer factories for two workloads with distinct per-factory prefixes. Temporarily set both to the same prefix to observe suffix collision risk.

## 21. Conclusion

In Spring Kafka, `transactionIdPrefix` is not an arbitrary label: it is the namespace `DefaultKafkaProducerFactory` uses to generate `transactional.id`s that the broker relies on to manage transactions and **fence stale producer sessions**.

For **multiple concurrent instances**, configure a prefix containing a unique instance identifier (such as Kubernetes Deployment Pod UID), combined with environment, application, and workload to avoid collisions. For **stable worker identities**, reuse prefixes intentionally only when fencing and ownership requirements are well understood. At the same time, provision enough producer/suffix capacity for concurrency, respect transaction timeouts/expiration, and configure listeners/consumers properly to achieve Kafka-to-Kafka EOS.

Most importantly, **avoiding transactional ID collisions does not replace idempotency, restart handling, and data consistency design**. Kafka transactions protect messages and offsets inside Kafka; database and API side effects require their own boundaries and deduplication.
