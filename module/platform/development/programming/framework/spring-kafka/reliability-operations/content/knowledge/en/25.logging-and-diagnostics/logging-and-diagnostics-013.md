# Diagnosing duplicates from logs

When a Spring Kafka system processes the same order, payment, or notification multiple times, logs are usually the first place operations looks for evidence. However, seeing two identical log lines **is not enough to conclude Kafka delivered a duplicate record**. A record can be redelivered because the consumer had not committed its offset; a business event can be published twice by the producer at two different Kafka offsets; a listener can retry the same record multiple times; or a log collector can ingest the same log entry twice.

Accurate diagnosis requires identifying **which layer has the duplicate**:

- **Duplicate log entry:** the same log event appears multiple times in the log backend.
- **Duplicate Kafka delivery:** the same Kafka record is reprocessed by a consumer, usually sharing the same topic-partition-offset.
- **Duplicate publication:** the producer wrote two Kafka records for the same business event, usually at different offsets.
- **Duplicate business command/event:** a client or upstream service created two distinct events for the same business request.
- **Duplicate side effect:** the same business action executed multiple times, e.g., deducting inventory or charging a payment twice.
- **Duplicate recovery/replay:** a record was retried, sent to a DLT, and replayed or recovered through multiple paths.

These layers can occur together yet are not synonymous. For instance, a consumer may receive the same record twice (duplicate delivery), while an inbox/idempotency check protects the side effect so the business operation runs once. Conversely, a producer sending the same event twice at two different offsets can cause the consumer to process twice even though the consumer group never redelivered the same offset.

This lesson belongs to the **Logging and Diagnostics** chapter in the **Spring Kafka Reliability Operations** module. It focuses on building evidence from structured logs, using event IDs and topic-partition-offsets properly, tracing retries/rebalances/commits, distinguishing producer duplicates from consumer replays and log ingestion duplicates, and cross-checking metrics, traces, and business data.

## 1. Four questions before concluding a duplicate occurred

When receiving a report of “Kafka duplicate processing”, ask in order:

1. **Are the two log lines the exact same log event?** Check log event ID, original timestamp, logger, thread, trace/span, and collector metadata.
2. **Do both runs share the same Kafka record identity?** Compare cluster, topic, partition, offset, and source/original metadata.
3. **Do both records share the same business event identity?** Compare eventId, commandId, or idempotency key.
4. **Did the business side effect actually execute twice?** Check database transactions, payment providers, downstream APIs, and audit records.

A sound conclusion pinpoints both identity and boundary. Example:

~~~text
Conclusion: consumer redelivery of the same Kafka record.
Kafka cluster: prod-a
Consumer group: inventory-service
Topic-partition-offset: orders.events-2-18420
Observed processing: pod-3 at 10:01:02, pod-5 at 10:01:08
Likely reason: first pass committed DB before offset committed ahead of rebalance.
Business effect: inbox unique constraint allowed stock reservation only once.
~~~

This is a verifiable conclusion. Saying “saw two OrderCreated lines so Kafka sent duplicates” lacks proof.

## 2. Identity layers must not be conflated

A Kafka pipeline uses multiple ID types:

| Identity | Example | Answers |
|---|---|---|
| Log event ID | UUID generated by logging appender | Are two log lines the same log entry ingested twice? |
| Trace ID | 4bf92f... | Do spans belong to the same request/distributed trace? |
| Span ID | 00f067... | Which specific operation in a trace is this? |
| Business event ID | evt-7b91 | Do two Kafka records represent the same business event? |
| Command/idempotency key | create-order-req-42 | Did the client resend the same request? |
| Kafka record identity | cluster + topic + partition + offset | Is this the exact same record in the Kafka log? |
| Consumer group | inventory-worker | For which group is offset progress tracked? |
| Delivery attempt | 2 | Which delivery/processing pass is this within the attempt tracker's scope? |
| Original record identity | original topic/partition/offset | Which record did a retry/DLT record originate from? |

**Topic-partition-offset** identifies a record within one specific Kafka log. It is not a cross-topic business event ID. When a record is published to a retry topic or DLT, it receives a new topic/partition/offset.

**Business event ID** can stay intact across retry stages, yet is reliable only if producers generate it stably and services honor the contract.

**Trace ID** may be absent or change across long-term replays. Never use trace ID as a business deduplication key unless your system explicitly defines its lifecycle.

## 3. One business event can appear at multiple Kafka offsets

Example of a producer publishing OrderCreated twice:

~~~text
orders.events partition 2:
  offset 100 -> eventId=E-42, orderId=O-123
  offset 101 -> eventId=E-42, orderId=O-123
~~~

These are **two distinct Kafka records** because their offsets differ, yet they share the same business event ID. Possible causes:

- HTTP client retried CreateOrder and the service was not idempotent.
- Outbox publisher resent after a timeout/ack ambiguity.
- Producer code published on two branches.
- Event handler re-processed a command and minted a new event reusing the business ID.
- Upstream replayed a message without deduplication.

The consumer group may read offset 100 and then offset 101 in normal order. No consumer redelivery had to occur.

Comparing only offsets misses duplicate business events. Comparing only eventId risks mistaking two distinct records for a single Kafka delivery. Keep both identities.

## 4. Same topic-partition-offset processed twice

Example:

~~~text
orders.events-2 offset 18420

10:01:02 pod-3 listener started
10:01:03 pod-3 database transaction committed
10:01:04 pod-3 process crashed

10:01:08 pod-5 assigned partition 2
10:01:09 pod-5 listener started offset 18420
~~~

This is **redelivery/reprocessing of the same Kafka record**. The first pass may have executed side effects before the consumer group persisted the next offset.

Kafka consumers normally track progress via committed offsets and have no knowledge of whether external database transactions committed. If the app commits the DB and crashes before committing the Kafka offset, the record will be reprocessed.

That is why consumers need idempotency or an inbox pattern whenever side effects must apply once per business semantics.

## 5. Duplicate log entries caused by the log pipeline

Not all duplicate logs originate in Kafka. Logs can duplicate when:

- Log agents retry sending a batch after a timeout.
- Two collectors tail the same file or read the same stdout stream.
- Log forwarders deliver at-least-once without deduplication.
- The application attaches two appenders writing to the same destination.
- Root logger and package logger additivity logs twice.
- Pod restarts cause a collector to re-read uncheckpointed file segments.
- A log aggregator reindexes a document.
- A multiline log line is split/merged improperly.

Example of the same log event:

~~~json
{
  "logEventId": "log-8f31",
  "timestamp": "2026-11-15T10:01:02.123Z",
  "message": "kafka_listener_started",
  "eventId": "evt-42",
  "topic": "orders.events",
  "partition": 2,
  "offset": 18420
}
~~~

If the log backend stores two documents with the same logEventId and original timestamp yet different collector receipt times, this is likely **duplicate ingestion**.

If two log entries have different logEventIds, different timestamps, and the same Kafka identity, the listener likely actually ran twice.

If the application does not emit a dedicated log event ID, correlate via original timestamp, pod, thread, logger, message, trace/span, and Kafka identity—recognizing that combination is a heuristic rather than an absolute unique key.

## 6. Designing structured logs to investigate duplicates

Free-form prose logs:

~~~text
Received order event
Processing order
Order processed
~~~

make it hard to answer which event, which record, which consumer, and which attempt.

Structured logs should carry fields:

~~~json
{
  "timestamp": "2026-11-15T10:01:02.123Z",
  "level": "INFO",
  "event": "kafka_listener_started",
  "service": "inventory-service",
  "instance": "inventory-pod-3",
  "listener_id": "orders-listener",
  "consumer_group": "inventory-worker",
  "cluster": "prod-a",
  "topic": "orders.events",
  "partition": 2,
  "offset": 18420,
  "key": "O-123",
  "event_id": "evt-42",
  "delivery_attempt": 1,
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7"
}
~~~

This is a suggested schema, not a default format emitted automatically by Spring Kafka on every log. Applications must attach metadata at the listener boundary or through appropriate interceptors/observations.

### 6.1. Recommended fields

- **timestamp:** when the log event was created, preferring UTC.
- **event:** stable event name, e.g., kafka_listener_started.
- **service/instance:** service and pod/instance identity.
- **listener_id/group:** listener and consumer group.
- **cluster/topic/partition/offset:** Kafka record identity.
- **event_id/command_id:** business identity.
- **delivery_attempt:** attempt metadata if available and clearly scoped.
- **trace_id/span_id:** distributed trace correlation.
- **outcome:** started/succeeded/failed/recovered.
- **exception_group:** bounded error taxonomy.
- **duration_ms:** processing duration.

Not every log line needs every field. However, key events such as delivery started, processing succeeded, failed, recovery, and DLT publication should share consistent correlation fields.

## 7. Log distinct boundaries, not just a single “received” line

A minimal flow should emit event logs:

~~~text
kafka_listener_started
kafka_listener_succeeded
kafka_listener_failed
kafka_retry_scheduled
kafka_retry_started
kafka_recovery_started
kafka_recovery_succeeded
kafka_recovery_failed
kafka_dlt_published
~~~

Example:

~~~json
{
  "event": "kafka_listener_succeeded",
  "event_id": "evt-42",
  "topic": "orders.events",
  "partition": 2,
  "offset": 18420,
  "listener_id": "orders-listener",
  "consumer_group": "inventory-worker",
  "delivery_attempt": 2,
  "duration_ms": 18
}
~~~

Do not log every event at INFO on high-volume workloads if it inflates log volume excessively. Use metrics for every attempt, selective logs for failures/recovery, and sampling for successful runs while preserving correlation fields needed for investigations.

## 8. Example listener logging with ConsumerRecord

A listener can read topic, partition, offset, and key directly from ConsumerRecord:

~~~java
@KafkaListener(
    id = "orders-listener",
    topics = "orders.events",
    groupId = "inventory-worker"
)
public void consume(
        ConsumerRecord<String, OrderEvent> record) {

    log.info(
        "kafka_listener_started topic={} partition={} offset={} key={} eventId={}",
        record.topic(),
        record.partition(),
        record.offset(),
        record.key(),
        record.value().eventId()
    );

    inventoryService.apply(record.value());

    log.info(
        "kafka_listener_succeeded topic={} partition={} offset={} eventId={}",
        record.topic(),
        record.partition(),
        record.offset(),
        record.value().eventId()
    );
}
~~~

This example assumes the payload exposes eventId and non-sensitive fields. If keys/payloads hold identifying or confidential data, mask them or omit them from logs. Never print full payloads solely to investigate duplicates.

### 8.1. Why log started and succeeded separately?

If you only log received at listener entry, two identical received lines could mean:

- One record was delivered twice.
- One delivery plus one log collector duplicate.
- Two Kafka records sharing the same eventId.

With both started and succeeded, you also know how far the first pass got. For example, started on Pod A without succeeded, followed by started on Pod B, points to redelivery after a crash or timeout. Succeeded on both pods for the same Kafka identity warns that side effects may have run twice.

## 9. Delivery attempt header is not a global identity

Spring Kafka can supply **delivery attempt** metadata in matching versions/configurations, e.g., via KafkaHeaders.DELIVERY_ATTEMPT and ContainerProperties.

Illustrative example:

~~~java
@KafkaListener(topics = "orders.events")
public void consume(
        ConsumerRecord<String, OrderEvent> record,
        @Header(
            name = KafkaHeaders.DELIVERY_ATTEMPT,
            required = false
        ) Integer deliveryAttempt) {

    log.info(
        "delivery topic={} partition={} offset={} attempt={}",
        record.topic(),
        record.partition(),
        record.offset(),
        deliveryAttempt
    );

    inventoryService.apply(record.value());
}
~~~

Verify the API to enable the header, data type, and behavior for your Spring Kafka version. When the header is absent, do not assume attempt 1 without marking it unknown.

**Delivery attempt** is typically scoped to an error handler/container path. It does not track lifetime retries of a business event across:

- multiple retry topics;
- multiple consumer groups;
- restarts or rebalances;
- DLT replays;
- producer republishes;
- independent services.

For end-to-end investigations, rely on business event IDs and original record metadata.

## 10. Correlating retry and DLT records back to the source record

When a record moves to a retry topic or DLT, it receives a new Kafka offset. Example:

~~~text
Source:
  orders.events-2 offset 18420

Retry:
  orders-retry-5000-1 offset 900

DLT:
  orders.events.DLT-0 offset 55
~~~

Three distinct Kafka identities can all belong to one source event.

Spring Kafka retry topics and DeadLetterPublishingRecoverer can attach headers holding original topic, partition, offset, exception, and retry details depending on mechanism/version. Preserve required headers and verify actual header names/formats before writing parsers.

In logs, normalize to:

~~~json
{
  "event_id": "evt-42",
  "current_topic": "orders-retry-5000",
  "current_partition": 1,
  "current_offset": 900,
  "original_topic": "orders.events",
  "original_partition": 2,
  "original_offset": 18420,
  "stage": "retry"
}
~~~

Do not overwrite current record identity with original identity. Both matter:

- Current identity finds the record currently handled by the consumer.
- Original identity reconstructs the event's lineage.

## 11. Using a stable event ID across the pipeline

An event ID should be minted when the business event is created and kept unchanged across:

- Producer retries.
- Kafka retry topics.
- Consumer redeliveries.
- DLT publication.
- DLT replays.
- Downstream service processing.

Envelope example:

~~~json
{
  "eventId": "evt-42",
  "eventType": "OrderCreated",
  "schemaVersion": 1,
  "aggregateId": "O-123",
  "occurredAt": "2026-11-15T10:00:00Z",
  "payload": {
    "orderId": "O-123"
  }
}
~~~

If a producer generates a fresh UUID every time it retries sending the same event, eventId ceases to support deduplication. Event ID must be generated once at the command/event creation boundary and persisted if using an outbox.

Never reuse the same eventId for two distinct business events just because they share aggregateId. One order can emit OrderCreated, OrderPaid, and OrderCancelled; each event needs its own identity.

## 12. Distinguishing producer duplicates from consumer redeliveries using offsets

This is the first classification check:

| Two log entries | Likely cause |
|---|---|
| Same cluster, topic, partition, offset; different timestamp/instance | Same Kafka record reprocessed |
| Same cluster, topic, partition; different offset; same eventId | Two Kafka records for the same business event |
| Different topic/partition/offset and different eventId yet same payload | Possibly two distinct business events, or producer minted wrong ID |
| Same logEventId and original log timestamp | Likely duplicate log collector ingestion |
| Same eventId yet different source metadata | Republish/replay or identity reuse; trace the source |
| Same offset yet different cluster | Two distinct records on two Kafka clusters |

**Cluster identity** matters. Topic-partition-offset has meaning only within one Kafka cluster/log. Two environments with identical topic names and offsets are not the same record.

## 13. Consumer group and instance identity

When a consumer group runs multiple instances:

~~~text
inventory-worker
  +-- pod-1 owns P0, P3
  +-- pod-2 owns P1, P4
  +-- pod-3 owns P2, P5
~~~

After a rebalance, partition P2 may transfer from pod-3 to pod-1. If a record was uncommitted, pod-1 may reprocess the old offset.

Logs should include:

- service name;
- pod/instance ID;
- consumer group;
- listener ID;
- client ID if needed;
- assignment/rebalance context;
- topic-partition-offset.

Logging only eventId makes it hard to tell whether duplicates came from producer republishes or consumer group redeliveries. Logging only pod ID leaves unknown whether two pods processed the same record or different records.

## 14. Rebalances are a common cause of redelivery

Timeline:

~~~text
Pod A receives offset 500
       |
       v
Listener commits business DB work successfully
       |
       v
Consumer has not committed next offset 501 yet
       |
       v
Pod A restarts or loses group membership
       |
       v
Rebalance assigns partition to Pod B
       |
       v
Pod B starts from prior committed offset
       |
       v
Offset 500 is redelivered
~~~

This is expected behavior under at-least-once processing. Kafka does not know Pod A's DB committed.

To verify:

1. Compare cluster/topic/partition/offset.
2. Compare instance IDs and timestamps.
3. Look for rebalances, partition revoked/lost events, and member changes.
4. Check committed offsets before/after the incident.
5. Check processing success on the first pod.
6. Check idempotency/deduplication in the business DB.

Never conclude the producer sent duplicates solely because two pods logged the same eventId.

## 15. How offset commit failures cause replays

Suppose AckMode.BATCH:

~~~text
Poll returns offsets 100, 101, 102
Listener processes whole batch successfully
Database commit succeeds
Container commits next offsets
        |
        +-- Commit succeeds -> group advances
        |
        +-- Commit fails -> records may replay
~~~

If a commit failure or process crash happens after business side effects, records can be reprocessed.

Logs must distinguish:

- listener_started
- business_processing_succeeded
- offset_commit_requested
- offset_commit_succeeded or commit failure if instrumented

A listener_succeeded line does not prove the offset committed. A commit-intent line does not prove the broker acknowledged it.

## 16. Producer retries and idempotence

Kafka producers can retry sends on transient errors. **enable.idempotence=true** helps producers avoid writing duplicate Kafka log entries from internal producer protocol retries within a producer session/protocol scope.

However:

- Idempotence does not deduplicate two separate `send()` calls made by application code for the same event.
- Idempotence does not stop an HTTP client from resending the same command and the service minting a new event.
- Idempotence does not replace business event IDs.
- Idempotence does not protect database or downstream HTTP side effects.
- A producer restart or distinct producer identity/session has separate semantics; do not treat idempotence as a global deduplication registry.

When suspecting producer duplicates, logs need eventId and metadata for each send invocation:

~~~text
event_id=evt-42
send_invocation_id=send-1
topic=orders.events
key=O-123
result=success
~~~

If the same eventId has two distinct send invocations and two distinct Kafka offsets, the producer/application published two records. Check call paths, HTTP-boundary retries, duplicate event listeners, and outbox publishers.

## 17. Duplicate producer logs are not always broker duplicates

Example:

~~~text
10:00:00 application calls KafkaTemplate.send(E-42)
10:00:01 send callback times out
10:00:02 application logs "retry publish E-42"
10:00:03 application calls send(E-42) again
~~~

On the first call, the broker may have appended the record while the acknowledgement was lost. The second send may create a second record if these are two distinct application-level sends.

A send-failed log may only reflect that the client missed the ACK; it does not prove the broker never stored the record.

For diagnostics:

- Record a distinct send invocation ID.
- Keep business eventId stable.
- Log producer callback outcomes and RecordMetadata on success.
- Inspect Kafka topic records by eventId.
- Check producer idempotence and transactional ID.
- Verify whether application retry called a new send or the Kafka producer retried the request internally.

Do not automatically replay publishes on callback timeouts without a matching event identity/dedup policy.

## 18. Producer idempotence vs. application-level duplicates

Two cases:

**Producer protocol retry:**

~~~text
Application send invocation #1
       |
       v
Producer sends request
       |
       v
Network retry inside producer protocol
       |
       v
Broker deduplicates by producer sequence
~~~

**Application calling send twice:**

~~~text
Application send invocation #1 -> E-42
Application send invocation #2 -> E-42
       |
       v
Two separate logical sends
       |
       v
May create two Kafka records
~~~

An idempotent producer solves the first case at protocol level. The second case requires idempotency in the application/outbox or downstream.

## 19. Kafka transactions do not automatically eliminate all duplicate business events

Kafka producer transactions atomically commit multiple Kafka writes and consumed offsets within a consume-transform-produce pipeline.

They handle:

- Output Kafka records within one transaction.
- Input offsets sent into the same transaction.
- Aborting outputs when the transaction fails.
- Ensuring `read_committed` consumers see only committed transactional records.

However, Kafka transactions do not automatically:

- Encompass non-Kafka database transactions.
- Deduplicate two identical commands from a client.
- Prevent two independent services from minting the same business event.
- Protect HTTP side effects.
- Collapse two separate application `send()` calls into one business event.

When logs show the same eventId at two offsets, check transaction logs/producer identity while still tracing back to the event creation boundary.

## 20. Consumer retries can create duplicate logs without creating duplicate Kafka records

With DefaultErrorHandler, the same source record can be redelivered across a blocking retry sequence:

~~~text
orders.events-2 offset 18420

Attempt 1 -> failure
Attempt 2 -> failure
Attempt 3 -> success
~~~

Logs may show three `listener_started` lines with the exact same topic/partition/offset, while the Kafka log contains **only one record** at that offset.

When attempt metadata is enabled, delivery attempt clarifies attempt order within the error handler's scope. Without metadata, timestamps and the identical Kafka identity still show repeated processing, though not necessarily the exact attempt count.

Do not call this a producer duplicate. This is **consumer redelivery/retry**.

## 21. Non-blocking retries create new Kafka records

With @RetryableTopic:

~~~text
orders.events P2 offset 18420
       |
       +-- listener failure
       |
       v
orders-retry-5000 P1 offset 900
       |
       +-- retry listener failure
       |
       v
orders-retry-30000 P0 offset 410
       |
       +-- success
~~~

Each retry topic publication writes a record to another Kafka log with a new identity. Logs for the same eventId across multiple topics represent **the same business event traversing processing stages**, not necessarily unexpected producer duplicates.

When searching logs:

- Keep eventId.
- Log current topic/partition/offset.
- Log original topic/partition/offset.
- Log retry stage and delivery attempt when available.
- Log the outcome of each stage.

Never group solely by eventId and label every entry a duplicate. Moving across stages is normal retry behavior.

## 22. DLT replays can make a record reappear

A record goes to a DLT and an operator later replays it to the source topic or a retry topic. Then:

- Business event ID can remain unchanged.
- Current Kafka topic/partition/offset are new.
- Original record metadata may persist in headers.
- Processing attempts restart in the new scope.

Logs should distinguish:

~~~text
stage=source
stage=retry
stage=dlt
stage=manual_replay
~~~

If an operator replays the same DLT record multiple times, those runs may be intentional. Log replay request ID, actor, reason, and eventId to distinguish manual replays from automatic retries.

Replaying a DLT record should not mint a new eventId if business semantics represent the same event. However, if an operator issues a compensating/new command, that may be a new business event requiring a new identity.

## 23. Outbox publishers and duplicate publications

Transactional Outbox stores business state and event intent in the same database transaction. Yet polling publishers usually have a window:

~~~text
Outbox row E-42
       |
       v
Kafka send succeeds
       |
       v
Process crashes before marking row SENT
       |
       v
Publisher runs again
       |
       v
Sends E-42 again
~~~

This is at-least-once publication; the same eventId can appear at two Kafka offsets. Never delete outbox rows or mark them SENT before confirmed publish evidence, as doing so can turn a duplicate into silent event loss.

When logs show duplicate eventId at different offsets:

1. Locate outbox row ID/eventId.
2. Check publisher claim/lease logs.
3. Check send acknowledgements and timeout ambiguity.
4. Check for crashes between Kafka ACK and DB markSent.
5. Verify consumer idempotency.

Outbox does not automatically create a distributed exactly-once transaction between database and Kafka.

## 24. Client retries and duplicate commands

An often-overlooked duplicate source sits upstream of Kafka:

~~~text
Client POST /orders
       |
       v
Service creates order O-123
       |
       v
DB commits
       |
       v
HTTP response is lost
       |
       v
Client retries POST /orders
       |
       v
Service creates order O-124
~~~

Two orders may generate two valid OrderCreated events from the service's perspective even though the client wanted only one order.

If the API must be idempotent, use an **Idempotency-Key** or command ID:

- Client sends the same key on retry.
- Service persists the key alongside command outcome in the DB.
- Unique constraint blocks creating a second command/order.
- Retries return the stored outcome.
- Outbox event is created only once for the deduplicated command.

In logs, record appropriately masked or hashed commandId/idempotencyKey—never log secrets. Without a command ID, matching payloads alone do not prove two requests were identical.

## 25. Consumer idempotency: duplicate deliveries do not become duplicate effects

A common pattern is an **inbox/processed_events** table with a unique constraint, updated in the same transaction as the business side effect.

~~~sql
CREATE TABLE processed_events (
    event_id VARCHAR(128) NOT NULL,
    consumer_name VARCHAR(100) NOT NULL,
    processed_at TIMESTAMP NOT NULL DEFAULT now(),
    PRIMARY KEY (event_id, consumer_name)
);
~~~

Illustrative Spring service:

~~~java
@Service
public class InventoryProcessor {

    private final JdbcTemplate jdbc;
    private final InventoryRepository inventoryRepository;

    public InventoryProcessor(
            JdbcTemplate jdbc,
            InventoryRepository inventoryRepository) {
        this.jdbc = jdbc;
        this.inventoryRepository = inventoryRepository;
    }

    @Transactional
    public void process(OrderCreated event) {
        int inserted = jdbc.update(
            """
            INSERT INTO processed_events(event_id, consumer_name)
            VALUES (?, ?)
            ON CONFLICT DO NOTHING
            """,
            event.eventId(),
            "inventory-service"
        );

        if (inserted == 0) {
            return; // Event was already processed successfully earlier.
        }

        inventoryRepository.reserve(
            event.orderId(),
            event.items()
        );
    }
}
~~~

**Mandatory requirement:** inserting into processed_events and updating inventory must share the same DB transaction. If reserve fails, both the processed marker and side effect must roll back. Recording the processed marker in a separate earlier transaction risks permanently skipping the record on replay if reserve fails.

Listener:

~~~java
@KafkaListener(topics = "orders.events", groupId = "inventory-worker")
public void onOrderCreated(OrderCreated event) {
    inventoryProcessor.process(event);
}
~~~

If the DB commits while the Kafka offset commit fails, the record may redeliver. The unique constraint lets the consumer detect eventId was already handled and skip repeating side effects.

## 26. Event IDs must have the right scope

A processed_events table keyed only by eventId may fall short when:

- Multiple tenants independently generate colliding event IDs.
- Multiple consumer applications need to process the same event.
- One service processes the event across multiple independent workflows.
- An intentional replay needs to populate a new projection.

Deduplication keys can be:

~~~text
(tenant_id, event_id, consumer_name)
~~~

Or:

~~~text
(event_source, event_id, processing_contract)
~~~

Choose based on your uniqueness contract. Never use topic-partition-offset as a business dedup key if the same event can be republished to another topic; and never rely on a bare eventId if producers do not guarantee global uniqueness.

## 27. Logs for idempotency decisions

When a consumer detects an event was already handled, log a distinct event with outcome **duplicate_suppressed**:

~~~json
{
  "event": "kafka_duplicate_suppressed",
  "service": "inventory-service",
  "consumer_group": "inventory-worker",
  "event_id": "evt-42",
  "topic": "orders.events",
  "partition": 2,
  "offset": 18421,
  "reason": "processed_event_exists"
}
~~~

For example, offset 18421 may be a brand-new Kafka record whose eventId was already processed. This log separates **deduplicated duplicate business events** from **same-offset redeliveries**.

Do not log every duplicate suppression at ERROR. In at-least-once systems, duplicate delivery is expected behavior. Use sampled DEBUG/INFO and metric counters; alert only when rates exceed baseline or involve risky side effects.

## 28. Log collector duplicates: how to verify

To distinguish log collector replays from genuine application reprocessing:

1. Check logEventId if the appender/collector generates a stable ID.
2. Compare original event timestamp with ingestion/receipt timestamp.
3. Compare host/pod, process ID, thread, and logger.
4. Check whether both documents share exact raw message bytes and log file source offset.
5. Inspect collector checkpoints, retry batches, and duplicate ingestion metrics.
6. Inspect root logger/additivity and appender wiring.

Example:

~~~text
Document A:
  event timestamp = 10:00:01.100
  collector time  = 10:00:02
  logEventId      = L-77

Document B:
  event timestamp = 10:00:01.100
  collector time  = 10:00:15
  logEventId      = L-77
~~~

If the raw source event is identical and the collector resent after a retry, duplicate ingestion is highly likely.

Conversely:

~~~text
Document A:
  event timestamp = 10:00:01.100
  pod             = pod-1
  thread          = kafka-consumer-1

Document B:
  event timestamp = 10:00:07.200
  pod             = pod-2
  thread          = kafka-consumer-2
~~~

Same Kafka identity across two distinct app log events at different times/instances points to true redelivery.

## 29. Logger additivity and double-attached appenders

In Logback, child loggers propagate log events up to the root logger via **additivity**. If the same appender is attached to both a child logger and root, every log event is written twice.

Example config prone to duplication:

~~~xml
<root level="INFO">
    <appender-ref ref="CONSOLE"/>
</root>

<logger name="com.example.inventory" level="INFO">
    <appender-ref ref="CONSOLE"/>
</logger>
~~~

If the child logger keeps default additivity=true while referencing the same appender in both places, one event travels two paths to console.

Solutions:

- Attach appenders at only one level whenever possible.
- If a child logger needs its own appender, consider additivity="false" and verify other logs are not lost.
- Audit appender references and logback-spring.xml.
- Compare log event IDs and source streams.

Never alter Kafka consumers or producers to fix duplicate logs caused by logging configuration.

## 30. MDC and thread reuse

MDC normally relies on thread-local context. Consumer threads are reused across many records. Failing to clear MDC leaks the prior record's eventId/topic/offset onto the next record.

Wrong example:

~~~java
MDC.put("event_id", event.eventId());
inventoryService.process(event);
// Missing MDC removal
~~~

The next log on that thread will carry stale metadata, skewing duplicate investigations.

Safe approach:

~~~java
try {
    MDC.put("event_id", event.eventId());
    MDC.put("kafka.topic", record.topic());
    MDC.put("kafka.partition", Integer.toString(record.partition()));
    MDC.put("kafka.offset", Long.toString(record.offset()));

    inventoryService.process(event);
}
finally {
    MDC.remove("event_id");
    MDC.remove("kafka.topic");
    MDC.remove("kafka.partition");
    MDC.remove("kafka.offset");
}
~~~

Or use proper context copy/restore helpers. With asynchronous executors, MDC does not transfer across threads automatically without instrumentation/context propagation.

A log line whose eventId mismatches the actual message may be an MDC propagation bug rather than a Kafka duplicate.

## 31. Timestamps and clock skew

When comparing logs across pods, timestamps can diverge due to:

- NTP synchronization differences.
- VM/container clock drift.
- Log pipeline timezone parsing bugs.
- Original event timestamp vs. collector receipt timestamp.
- Producer occurredAt vs. consumer processing time.

For investigations:

- Log UTC timestamps.
- Log event occurredAt and log timestamp separately when needed.
- Use monotonic clocks for durations inside one JVM.
- Cross-check trace/span timestamps and collector ingest times.
- Never infer causality order solely from timestamps when clock skew is significant.

Offsets within one partition provide a stable log order; timestamps do not replace offsets for record ordering.

## 32. Using traces to follow duplicates

Distributed tracing can link:

~~~text
HTTP request
   |
   v
Order service writes DB + outbox
   |
   v
Kafka publish
   |
   v
Inventory consumer
   |
   v
Inventory DB transaction
~~~

If an event redelivers, each pass can start a new span. Keep business event ID as a span attribute and use appropriate links/parent context for asynchronous messaging.

Do not force the same span ID across multiple processing passes. A span represents one operation; redelivery is a new operation that can still link to the same event ID/original context.

Trace ID is also not a durable dedup key:

- Traces may expire before DLT replays.
- Retry consumers may start fresh traces.
- Sampling can drop some traces.
- Producers and consumers may fail to propagate context properly.

Use traces to understand causal paths; use eventId and idempotency stores to identify business events.

## 33. Additional metrics for duplicate investigation

Useful metrics:

| Metric | Meaning |
|---|---|
| listener_attempts_total | How many times listeners started processing |
| listener_failures_total | Failed attempts count |
| retry_attempts_total | Retry attempts actually started per definition |
| recovery_attempts_total | Recovery invocations count |
| dlt_publish_success_total | Confirmed DLT publishes |
| idempotency_duplicate_hits_total | Times deduplication blocked repeat side effects |
| same_record_redelivery_total | Times the same topic-partition-offset reprocessed if instrumented |
| duplicate_event_id_observed_total | Times an eventId reappeared within defined scope |
| offset_commit_failures_total | Commit failures count |
| rebalance_total | Rebalance count |
| producer_send_retry_total | Producer send retries per metric/client semantics |
| consumer_lag | Lag per group/partition |

These names are custom/conceptual metrics; not all exist out of the box in Spring Kafka. Never put eventId or offset as labels in Prometheus. Keep detailed identities in logs/traces.

### 33.1. Duplicate rate requires a clear denominator

Example:

~~~text
duplicate_event_rate =
  duplicate_event_id_observed
  / distinct_or_total_input_events
~~~

Explicitly specify whether the denominator is:

- Total Kafka deliveries?
- Distinct event IDs?
- Producer send invocations?
- Business commands?

If the numerator counts duplicate deliveries while the denominator counts producer sends, the ratio has no direct meaning.

## 34. Example PromQL queries

Assuming the application exports custom counters:

~~~promql
sum by (service, consumer_group) (
  rate(app_kafka_idempotency_duplicate_hits_total[5m])
)
~~~

Listener failure rate:

~~~promql
sum by (listener_id, exception_group) (
  rate(app_kafka_listener_failures_total[5m])
)
~~~

Duplicate suppression ratio over listener attempts:

~~~promql
sum(rate(app_kafka_idempotency_duplicate_hits_total[10m]))
/
clamp_min(
  sum(rate(app_kafka_listener_attempts_total[10m])),
  0.000001
)
~~~

This query is valid only if duplicate hits and listener attempts share the exact same scope, stage, labels, and units. If idempotency hits count distinct business events while listener attempts count record deliveries, the ratio is only a rough indicator.

## 35. Never use event ID as a metric label

A new event ID per message has nearly unbounded cardinality. If a metric carries an `event_id` label:

~~~text
app_kafka_duplicate_total{event_id="evt-1"}
app_kafka_duplicate_total{event_id="evt-2"}
app_kafka_duplicate_total{event_id="evt-3"}
...
~~~

Time-series counts grow alongside event volume and consume huge metric memory/storage.

Metric labels should come from bounded sets:

- service;
- listener_id;
- consumer_group;
- topic (if topic list is finite);
- stage=main/retry/dlt;
- duplicate_type=redelivery/republished/log_ingestion;
- exception_group.

Event ID, command ID, trace ID, and topic-partition-offset belong in structured logs or traces.

## 36. Diagnosing from log patterns

### Pattern A: same Kafka identity, two pods

~~~text
10:00:01 pod-A listener_started topic=orders.events p=2 o=18420 eventId=E-42
10:00:02 pod-A business_succeeded topic=orders.events p=2 o=18420 eventId=E-42
10:00:05 pod-B listener_started topic=orders.events p=2 o=18420 eventId=E-42
~~~

Highly likely redelivery of the same record. Check commits, crashes, rebalances, and idempotency. Pod B may repeat side effects if no inbox exists.

### Pattern B: same eventId, different offsets

~~~text
10:00:01 pod-A listener_started topic=orders.events p=2 o=18420 eventId=E-42
10:00:05 pod-A listener_started topic=orders.events p=2 o=18421 eventId=E-42
~~~

Two different Kafka records for the same business event. Look for producer/outbox/client retries or upstream replays.

### Pattern C: same logEventId, different collector times

~~~text
source_time=10:00:01.100 logEventId=L-77 collector_time=10:00:02
source_time=10:00:01.100 logEventId=L-77 collector_time=10:00:15
~~~

Highly likely duplicate log ingestion. Check collector retries/checkpoints and appender config.

### Pattern D: same eventId across main and retry topics

~~~text
topic=orders.events offset=18420 eventId=E-42 stage=main
topic=orders-retry-5000 offset=900 eventId=E-42 stage=retry
~~~

Likely non-blocking retries working as designed. Inspect original metadata and stage rather than jumping to producer duplicates.

### Pattern E: same eventId, DLT then replay

~~~text
topic=orders.events.DLT offset=55 eventId=E-42 stage=dlt
topic=orders.events offset=19000 eventId=E-42 stage=manual_replay
~~~

Likely an intentional replay. Check replay request, actor, reason, and idempotency behavior.

## 37. Workflow for investigating duplicates from logs

A practical workflow:

**Step 1 — Pull both complete log entries**

Do not copy only message text. Collect original timestamps, pods, loggers, threads, event IDs, trace IDs, topics, partitions, offsets, and stages.

**Step 2 — Determine duplicate type**

- Same log event ID?
- Same Kafka identity?
- Same business event ID?
- Or merely similar payloads?

**Step 3 — Reconstruct the timeline**

Order by source timestamp, offset, instance, and rebalances. Pinpoint processing started/succeeded/failed, commit requests/outcomes, restarts, and retries.

**Step 4 — Verify Kafka group state**

Inspect consumer group, committed offsets, lag, and assignments at incident time if telemetry recorded them.

**Step 5 — Trace the producer path**

If offsets differ while eventId matches, inspect command IDs, outbox rows, producer send invocations, retries, and ack ambiguity.

**Step 6 — Verify business side effects**

Inspect unique constraints, processed_events/inbox, payment provider idempotency keys, database audits, or downstream request IDs.

**Step 7 — Classify and remediate**

Identify root cause: redelivery, producer republish, retry/replay, duplicate command, log collector duplication, or buggy instrumentation.

**Step 8 — Verify after fixing**

Monitor duplicate rates, lag, commit failures, idempotency hits, and business outcomes—not merely whether log line counts dropped.

## 38. Runbook: same offset processed on two pods

### Step 1: Verify identity

Ensure both log entries share the same Kafka cluster, topic, partition, and offset. Check consumer group and listener ID.

### Step 2: Inspect timeline

Check processing started/succeeded on the first pod. Look for crashes, SIGTERM, OOMKilled, timeouts, or rebalances nearby.

### Step 3: Inspect commits

Compare commit intents/outcomes with consumer group committed offsets. Remember committed offset is the next offset.

### Step 4: Check business transactions

Did the first pod commit the DB? Did the second pod deduplicate via eventId/inbox? Did side effects actually repeat?

### Step 5: Remediate

If this is expected at-least-once behavior, enforce idempotency. If caused by misconfigured max.poll.interval.ms/rebalancing, shorten blocking work, set timeouts, and tune batch/poll settings.

### Step 6: Verify

Confirm the record completes cleanly, committed offsets advance, duplicate side effects remain zero, and rebalances stabilize.

## 39. Runbook: same eventId yet different offsets

1. Verify current topic/partition/offset of each record.
2. Compare eventId, eventType, aggregateId, and payload fingerprint.
3. Search commandId/idempotency key at the API boundary.
4. Search outbox row ID and publisher logs.
5. Check producer send invocation IDs and acknowledgement timeouts.
6. Check whether the app has two call paths publishing the same event.
7. Check manual replays or retry-topic routing.
8. Cross-check business event/audit tables in the database.
9. Add unique constraints/dedup at the command/outbox boundary if duplicate creation is the root cause.
10. Keep consumer idempotency to guard against existing duplicates.

Never delete Kafka records or reset offsets to hide evidence before capturing needed logs/audits.

## 40. Runbook: duplicate log lines yet Kafka offsets did not change

Likely causes:

- Collector resent the same log event.
- Logback appender attached twice.
- Root logger additivity logged along two paths.
- Application code called the logger twice.
- Log aggregator reindexed documents.

Checks:

1. logEventId or source file offset.
2. Raw event timestamp vs. collector ingest time.
3. Appender refs/root logger configuration.
4. Collector retry/checkpoint metrics.
5. Pod/process/thread identities.
6. Whether one or two genuine listener_started events ran.

If Kafka group offsets and listener invocation metrics did not move while log documents doubled, investigate the logging pipeline first.

## 41. Runbook: side effect executed twice

This scenario requires the highest business priority.

1. Identify business event ID and side effect ID.
2. Check whether two Kafka records existed or one record redelivered.
3. Check whether the first pass committed the database or called the external API successfully.
4. Check inbox/unique constraints/idempotency keys.
5. Check whether the external provider supports idempotency and request lookups.
6. Halt or throttle the source creating further duplicates if needed and safe.
7. Reconcile business state: refund, restore inventory, or repair state per domain workflow.
8. Fix transaction and retry boundaries.
9. Test crashing between side effects and offset commits in a test environment.

Do not merely tweak logs or raise retry limits. If business side effects are not idempotent, duplicates will keep causing harm even after logs are deduplicated.

## 42. Testing duplicate delivery

An integration test should:

1. Publish an event with a stable eventId.
2. Have the consumer write business state and inbox in the same transaction.
3. Prevent the consumer from committing the offset after the first pass, or simulate a crash/rebalance in test.
4. Let the consumer receive the same topic-partition-offset again.
5. Assert the listener logs two attempts.
6. Assert the inbox records only one event ID and the business side effect executes once.
7. Assert the consumer group eventually advances the offset.

What matters is testing that **the same Kafka identity** redelivers while side effects remain idempotent.

## 43. Testing duplicate publication

1. Create a business event with a stable eventId.
2. Send the first producer send and force the ACK to time out/be uncertain in test.
3. Trigger an application-level retry or outbox reclaim.
4. Assert two Kafka offsets can exist for the same eventId.
5. Assert the consumer inbox/dedup executes the side effect only once.
6. Capture send invocation IDs and producer outcomes.

Tests must distinguish producer protocol retries from two separate application sends. Do not assume every timeout creates a duplicate or never creates a duplicate.

## 44. Testing log collector duplicates

In a logging test environment:

- Emit a log event with a stable event ID.
- Simulate a collector batch retry or sending the same source event twice.
- Assert the log backend holds two documents with the identical source log event identity.
- Verify application listener attempts and Kafka offsets did not change.
- Assert dashboards can separate ingestion duplicates from processing duplicates.

Never change consumer logic to work around duplicate log ingestion when the bug lives in the collector/appender.

## 45. Testing retry and DLT correlation

A scenario:

~~~text
Source event E-42
   |
   v
Blocking retry attempt 1
   |
   v
Non-blocking retry topic
   |
   v
Retry listener fails
   |
   v
DLT publication
   |
   v
Manual replay
~~~

Assert:

- Event ID remains constant.
- Current Kafka identity updates per topic/stage.
- Original topic/partition/offset are preserved accurately.
- Retry stage and delivery attempt are logged clearly.
- Replay request ID/actor are recorded.
- Idempotency behaves per business policy.

## 46. Common diagnostic mistakes

| Mistake | Why it is wrong | Adjustment |
|---|---|---|
| Two identical log lines = Kafka sent duplicates | May be duplicate log collector ingestion | Check log event identity and Kafka offsets |
| Same eventId = same Kafka record | Two records can sit at different offsets | Compare cluster/topic/partition/offset |
| Same offset = same record across clusters | Offsets apply only within one cluster/log | Record cluster identity |
| Listener ran twice = producer sent two records | Consumer may have redelivered the same offset | Check rebalances/commits/retries |
| Two different offsets = certain business duplicate | Identical payloads may be two valid events | Check event/command identity and domain |
| Trace ID is a dedup key | Trace sampling/retention/replays vary | Use durable eventId |
| DeliveryAttempt is lifetime attempt count | Scope can reset across retry stages/restarts | Use stage-aware correlation |
| Producer idempotence stops all duplicates | Does not dedup two separate app sends | Enforce idempotency/outbox at app boundary |
| Kafka transactions protect database side effects | Kafka transactions exclude DB/HTTP | Use inbox/outbox/sagas |
| Succeeded log proves offset commit | Listener success and commit are separate boundaries | Log/measure commit outcomes separately |
| Offset commit proves business success | Record may have routed to DLT | Separate DLT and business metrics |
| Deduplicating logs is enough | Side effects may still have duplicated | Inspect business DB/external providers |
| MDC needs no cleanup | Thread reuse leaks metadata to next record | Clean up/propagate context explicitly |
| Event ID as metric label | Cardinality explodes with event volume | Keep IDs in logs/traces |
| Resetting offsets to clear duplicates | Can skip data and destroy evidence | Reconcile first; operate only per runbook |

## 47. Production checklist

When building duplicate diagnostic capabilities:

1. Do structured logs include cluster, consumer group, listener, topic, partition, and offset?
2. Do logs include stable business event IDs/command IDs?
3. Do retry/DLT logs include both current and original topic-partition-offset?
4. Are instance/pod IDs and trace/span contexts recorded?
5. Are listener started/succeeded/failed, retry, recovery, and DLT publication events separated?
6. Is delivery attempt metadata enabled and accurately scoped?
7. Are same Kafka identity and same business event identity distinguished?
8. Do producer send logs include invocation ID and acknowledgement outcomes?
9. Can consumer group committed offsets/rebalances be cross-checked with logs?
10. Are side effects protected by idempotency/inbox unique constraints?
11. Does the outbox publisher have stable event IDs and retry observability?
12. Do DLT replays record actor/reason/request ID and dedup policy?
13. Have logging appenders/root loggers/collectors been checked for duplicate ingestion?
14. Does MDC clean up on consumer threads and propagate on async executors?
15. Are clocks/timestamps UTC and durations measured with monotonic clocks?
16. Do metrics count duplicate suppressions, retries, recoveries, rebalances, and commit failures?
17. Do Prometheus labels avoid event IDs and high-cardinality fields?
18. Do dashboards separate producer duplicates, consumer redeliveries, and log ingestion duplicates?
19. Are crashes between DB commit and Kafka offset commit tested?
20. Is a runbook ready to reconcile side effects when duplicates occur?

## 48. Conclusion

**Diagnosing duplicates from logs must start with identity and boundary.** Same topic-partition-offset on the same cluster indicates the same Kafka record was reprocessed; same eventId with different offsets indicates multiple Kafka records represent one business event; same logEventId with different ingestion times likely means a log collector resent an entry. These situations have distinct causes and fixes.

In Spring Kafka, write structured logs at listener, retry, recovery, DLT, and commit boundaries; keep business event IDs stable; preserve current/original Kafka metadata; and cross-check against consumer group offsets, rebalances, producer acknowledgements, and transaction outcomes. Use inbox/idempotency to guard side effects against redelivery, and outbox/idempotent command handling to curb duplicate upstream publications. Logs tell **what was observed**, metrics show **frequency and trends**, traces connect **the path**, and databases/audits confirm **whether business effects actually happened**.

A reliable system does not assume duplicates will never appear. It identifies duplicates at the right layer, preserves traceable records, and guarantees reprocessing causes no unintended side effects.
