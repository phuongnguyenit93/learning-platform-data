# HAL là gì

HAL (Hypertext Application Language) là một định dạng biểu diễn tài nguyên có hypermedia, thường được dùng để xây dựng REST API. HAL định nghĩa cách đặt dữ liệu tài nguyên, liên kết và tài nguyên nhúng trong một tài liệu JSON. Nhờ cấu trúc thống nhất, client có thể đọc các relation trong response rồi theo href để khám phá tài nguyên tiếp theo.

Spring HATEOAS hỗ trợ HAL JSON thông qua media type `application/hal+json`. Các lớp như `EntityModel`, `CollectionModel` và `PagedModel` mô tả tài nguyên ở phía Java; bộ chuyển đổi hypermedia của Spring HATEOAS tuần tự hóa chúng thành cấu trúc HAL. Vì vậy, ứng dụng có thể tập trung tạo representation và link, còn định dạng HAL xác định cách các thành phần đó xuất hiện trong JSON.

Bài học này giới thiệu mục đích và cấu trúc HAL, hai thuộc tính quan trọng `_links` và `_embedded`, relation, metadata link, URI template, CURIE, cách Spring HATEOAS xuất HAL JSON và cách client sử dụng response để điều hướng API.

## 1. HAL giải quyết vấn đề gì?

Một response JSON thông thường thường chứa dữ liệu nghiệp vụ nhưng không chỉ rõ client nên truy cập tài nguyên liên quan bằng cách nào. Client có thể phải tự biết URL, tự ghép ID vào đường dẫn hoặc phụ thuộc vào cấu trúc endpoint do server triển khai.

Ví dụ response chỉ có dữ liệu:

~~~json
{
  "id": "ORD-42",
  "status": "PROCESSING",
  "total": 125000
}
~~~

Client biết mã đơn và trạng thái, nhưng không biết URI canonical của đơn hàng, URI tập hợp đơn hàng hoặc đường dẫn đến khách hàng liên quan. Nếu client tự xây URL như `/orders/ORD-42`, nó đang phụ thuộc vào cấu trúc route của server.

HAL cho phép server công bố các liên kết ngay trong representation:

~~~json
{
  "id": "ORD-42",
  "status": "PROCESSING",
  "total": 125000,
  "_links": {
    "self": {
      "href": "/orders/ORD-42"
    },
    "orders": {
      "href": "/orders"
    },
    "customer": {
      "href": "/customers/CUS-7"
    }
  }
}
~~~

Client tìm relation `self`, `orders` hoặc `customer` rồi dùng `href` tương ứng. Khi server thay đổi route, client vẫn có thể tiếp tục điều hướng nếu relation và hợp đồng hypermedia được giữ ổn định.

HAL tập trung vào cấu trúc biểu diễn và điều hướng. Nó không tự định nghĩa quy tắc nghiệp vụ của relation, không quyết định quyền truy cập và cũng không tự mô tả đầy đủ mọi thao tác HTTP. Những ngữ nghĩa đó đến từ hợp đồng API, relation, affordance hoặc media type mở rộng.

## 2. HAL JSON và media type

HAL JSON sử dụng media type:

~~~http
application/hal+json
~~~

Client thường gửi header `Accept` để yêu cầu định dạng:

~~~http
GET /orders/ORD-42 HTTP/1.1
Host: api.example.com
Accept: application/hal+json
~~~

Server có thể trả:

~~~http
HTTP/1.1 200 OK
Content-Type: application/hal+json
~~~

Trong Spring HATEOAS, hằng số `MediaTypes.HAL_JSON` và `MediaTypes.HAL_JSON_VALUE` biểu diễn media type này.

HAL là một định dạng hypermedia dựa trên JSON. Nó không phải một kiểu Java và cũng không phải tên của controller hay endpoint. Phía Java, ứng dụng xây dựng representation model; khi response được tuần tự hóa với HAL, dữ liệu và link được ghi theo quy ước HAL JSON.

## 3. Cấu trúc tài liệu HAL JSON

Một tài liệu HAL có thể chứa các trường dữ liệu thông thường và hai thuộc tính dành riêng:

- `_links`: các liên kết từ tài nguyên hiện tại đến tài nguyên hoặc đích khác.
- `_embedded`: các tài nguyên được nhúng trong representation hiện tại.

Ví dụ:

~~~json
{
  "id": "ORD-42",
  "status": "PROCESSING",
  "total": 125000,
  "_links": {
    "self": {
      "href": "/orders/ORD-42"
    },
    "customer": {
      "href": "/customers/CUS-7"
    }
  },
  "_embedded": {
    "customer": {
      "id": "CUS-7",
      "name": "Nguyen An",
      "_links": {
        "self": {
          "href": "/customers/CUS-7"
        }
      }
    }
  }
}
~~~

Trong ví dụ:

- `id`, `status`, `total` là dữ liệu nghiệp vụ.
- `_links` công bố các đường dẫn điều hướng.
- `_embedded.customer` chứa một representation khách hàng được nhúng.
- Tài nguyên nhúng có thể có `_links` riêng để client tiếp tục điều hướng.

Không phải tài nguyên liên quan nào cũng cần nhúng. API có thể chỉ công bố link và để client tải dữ liệu đích khi cần. Việc chọn link hay embedding phụ thuộc use case, kích thước payload, vòng đời tài nguyên và số request mà client cần thực hiện.

## 4. _links: công bố quan hệ và URI

Trong HAL, `_links` là object chứa các relation. Mỗi tên relation ánh xạ đến một link hoặc một danh sách link.

Ví dụ:

~~~json
{
  "_links": {
    "self": {
      "href": "/orders/ORD-42"
    },
    "customer": {
      "href": "/customers/CUS-7"
    },
    "payments": [
      {
        "href": "/payments/PAY-1"
      },
      {
        "href": "/payments/PAY-2"
      }
    ]
  }
}
~~~

Một relation có thể có một link hoặc nhiều link. Client nên xử lý cả hai hình dạng nếu API có thể trả nhiều link cùng relation. Ví dụ, một đơn hàng có thể liên quan đến nhiều khoản thanh toán.

### 4.1. Relation có ý nghĩa gì?

Relation mô tả ngữ nghĩa của link đối với tài nguyên hiện tại:

| Relation | Ý nghĩa thường gặp |
|---|---|
| `self` | URI của chính tài nguyên hiện tại |
| `orders` | Tập hợp đơn hàng theo quy ước API |
| `customer` | Tài nguyên khách hàng liên quan |
| `next` | Phần tiếp theo trong chuỗi hoặc kết quả phân trang |
| `prev` | Phần trước trong chuỗi hoặc kết quả phân trang |
| `search` | Đích hỗ trợ tìm kiếm |
| `describedby` | Tài liệu mô tả tài nguyên hoặc ngữ cảnh liên quan |
| `profile` | Profile bổ sung ngữ nghĩa cho representation |

Các relation như `self`, `next` và `prev` có định nghĩa phổ biến trong Web Linking/IANA. Các relation như `orders`, `customer` hoặc `payments` thường là relation tùy chỉnh của API và cần được tài liệu hóa.

Client nên dựa vào relation để tìm link thay vì dựa vào thứ tự xuất hiện trong JSON hoặc tự tạo URI từ ID. Tên relation là một phần hợp đồng công khai; hãy giữ ngữ nghĩa ổn định khi thay đổi implementation.

### 4.2. Metadata của link

Ngoài `href`, một link HAL có thể chứa metadata tùy chọn:

~~~json
{
  "_links": {
    "manual": {
      "href": "/docs/orders",
      "title": "Tài liệu đơn hàng",
      "type": "text/html",
      "hreflang": "vi"
    },
    "search": {
      "href": "/orders{?status,page}",
      "templated": true
    }
  }
}
~~~

| Thuộc tính | Ý nghĩa |
|---|---|
| `href` | URI đích |
| `templated` | Cho biết href là URI template |
| `type` | Media type dự kiến của đích |
| `deprecation` | URI cung cấp thông tin về trạng thái deprecated của link |
| `name` | Tên phân biệt link, hữu ích khi một relation có nhiều link |
| `profile` | URI tham chiếu profile liên quan |
| `title` | Nhãn mô tả link |
| `hreflang` | Ngôn ngữ của tài nguyên đích |

Metadata giúp client hiểu thêm về link, nhưng không thay thế việc gửi request và xử lý status HTTP thực tế. Ví dụ, `type` mô tả media type dự kiến; nó không bảo đảm server luôn trả đúng loại nội dung trong mọi tình huống.

## 5. _embedded: nhúng tài nguyên liên quan

`_embedded` chứa representation của tài nguyên liên quan được nhúng bên trong tài liệu hiện tại. Mỗi phần tử được nhóm theo relation.

Ví dụ một collection đơn hàng:

~~~json
{
  "_links": {
    "self": {
      "href": "/orders"
    }
  },
  "_embedded": {
    "orders": [
      {
        "id": "ORD-42",
        "status": "PROCESSING",
        "_links": {
          "self": {
            "href": "/orders/ORD-42"
          }
        }
      },
      {
        "id": "ORD-43",
        "status": "DELIVERED",
        "_links": {
          "self": {
            "href": "/orders/ORD-43"
          }
        }
      }
    ]
  }
}
~~~

Relation `orders` nhóm các representation đơn hàng trong collection. Mỗi phần tử có thể chứa dữ liệu và link riêng.

### 5.1. Khi nào nên nhúng?

Nhúng dữ liệu có ích khi client thường xuyên cần phần dữ liệu đó cùng tài nguyên gốc, dữ liệu nhỏ và có thể công bố an toàn trong cùng response. Ví dụ, đơn hàng có thể nhúng tên khách hàng và mã khách hàng để hiển thị trong một dòng danh sách.

Nên ưu tiên link khi:

- Tài nguyên liên quan lớn hoặc có nhiều phần tử.
- Tài nguyên có vòng đời và quyền truy cập độc lập.
- Client chỉ thỉnh thoảng cần dữ liệu liên quan.
- Việc nhúng làm response quá sâu hoặc gây vòng tham chiếu.
- Tập hợp cần phân trang riêng.

Link và embedding có thể cùng xuất hiện. Một tài nguyên nhúng vẫn có thể có link self đến URI canonical của nó.

### 5.2. Relation của tài nguyên nhúng

Tên khóa trong `_embedded` là relation xác định loại tài nguyên được nhúng. Trong Spring HATEOAS, relation của item và collection có thể được cấu hình bằng `@Relation`.

~~~java
import java.math.BigDecimal;
import java.util.UUID;

import org.springframework.hateoas.server.core.Relation;

@Relation(
    itemRelation = "order",
    collectionRelation = "orders"
)
public record OrderRepresentation(
    UUID id,
    String status,
    BigDecimal total
) {}
~~~

Trong ví dụ, `order` là relation cho một phần tử đơn hàng và `orders` là relation cho collection đơn hàng. Relation provider của Spring HATEOAS sử dụng metadata này khi tạo representation tương ứng.

Nếu không cấu hình tường minh, relation provider mặc định có thể suy ra tên từ kiểu tài nguyên. Khi tên class Java thay đổi nhưng hợp đồng API cần giữ nguyên, `@Relation` giúp tách tên relation công khai khỏi tên implementation.

## 6. URI template trong HAL

Một link có thể trỏ đến URI template thay vì URI đã hoàn chỉnh. URI template chứa biến mà client có thể điền để tạo URI cuối cùng.

Ví dụ:

~~~json
{
  "_links": {
    "search": {
      "href": "/orders{?status,page,size}",
      "templated": true
    }
  }
}
~~~

Client có thể mở rộng template với các giá trị:

~~~text
/orders{?status,page,size}
              |
              +-- status=PROCESSING
              +-- page=2
              +-- size=20
              |
              v
/orders?status=PROCESSING&page=2&size=20
~~~

Thuộc tính `templated: true` cho biết `href` cần được mở rộng theo quy tắc URI Template trước khi sử dụng. Client không nên gửi nguyên chuỗi còn chứa dấu ngoặc nhọn như thể đó là URI cuối cùng.

Trong Spring HATEOAS, có thể tạo link template trực tiếp:

~~~java
Link search = Link.of(
    "/orders{?status,page,size}",
    "search"
);
~~~

Hoặc tạo URI từ mapping controller với các request parameter phù hợp. Dù dùng cách nào, hãy kiểm tra tên biến và cách mở rộng template trong test để bảo vệ hợp đồng client.

## 7. CURIE: viết gọn relation URI

Khi API dùng relation mở rộng dưới dạng URI, tên relation có thể dài. HAL hỗ trợ CURIE (Compact URI Expression) để ánh xạ một prefix ngắn đến một URI template.

Ví dụ:

~~~json
{
  "_links": {
    "curies": [
      {
        "name": "ex",
        "href": "https://api.example.com/rels/{rel}",
        "templated": true
      }
    ],
    "self": {
      "href": "/orders/ORD-42"
    },
    "ex:cancel": {
      "href": "/orders/ORD-42/cancellation"
    }
  }
}
~~~

CURIE khai báo prefix `ex` và URI template dùng biến `{rel}`. Relation `ex:cancel` là dạng rút gọn của URI relation được tạo bằng cách thay giá trị `cancel` vào template.

CURIE hữu ích khi API cần namespace cho relation tùy chỉnh hoặc muốn công bố tài liệu định nghĩa relation. Không cần dùng CURIE cho mọi relation. Các relation chuẩn như `self`, `next` hoặc relation tùy chỉnh đơn giản có thể dùng trực tiếp khi không có nhu cầu namespace.

Trong Spring HATEOAS, CURIE có thể được cấu hình qua cơ chế hỗ trợ CURIE và link provider phù hợp. Hãy kiểm tra response HAL thực tế để xác nhận prefix, template và relation compact được xuất đúng như hợp đồng API.

## 8. HAL và các representation model của Spring HATEOAS

Spring HATEOAS cung cấp các kiểu Java để mô hình hóa tài nguyên trước khi tuần tự hóa:

| Kiểu Java | Vai trò |
|---|---|
| `RepresentationModel<T>` | Model cơ sở chứa tập hợp Link |
| `EntityModel<T>` | Bọc một nội dung cùng các Link |
| `CollectionModel<T>` | Biểu diễn tập hợp các phần tử cùng link cấp collection |
| `PagedModel<T>` | Biểu diễn tập hợp có metadata phân trang và link điều hướng |

Khi được tuần tự hóa dưới dạng HAL JSON:

- Link của model được đưa vào `_links`.
- Nội dung của EntityModel được biểu diễn cùng các thuộc tính của tài nguyên.
- Phần tử của CollectionModel có thể được nhóm dưới `_embedded` theo relation collection.
- Metadata và link phân trang của PagedModel được biểu diễn trong tài liệu HAL.

Ví dụ tạo một EntityModel:

~~~java
import org.springframework.hateoas.EntityModel;

import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.linkTo;
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.methodOn;

OrderRepresentation body = new OrderRepresentation(
    order.getId(),
    order.getStatus(),
    order.getTotal()
);

EntityModel<OrderRepresentation> model = EntityModel.of(
    body,
    linkTo(methodOn(OrderController.class).one(order.getId()))
        .withSelfRel(),
    linkTo(methodOn(OrderController.class).all())
        .withRel("orders")
);
~~~

Ví dụ collection:

~~~java
CollectionModel<EntityModel<OrderRepresentation>> model =
    assembler.toCollectionModel(orders)
        .add(
            linkTo(methodOn(OrderController.class).all())
                .withSelfRel()
        );
~~~

Các kiểu model cung cấp cấu trúc Java; HAL là định dạng JSON mà serializer dùng để công bố cấu trúc đó cho client. Không cần tự tạo chuỗi JSON `_links` trong controller nếu đã dùng Spring HATEOAS representation model.

## 9. Bật HAL trong Spring HATEOAS

Với ứng dụng Spring Boot có Spring HATEOAS trên classpath, auto-configuration thường thiết lập hỗ trợ hypermedia và HAL JSON. Hãy ưu tiên cấu hình mặc định của Boot nếu ứng dụng đã dùng starter phù hợp.

Trong ứng dụng Spring không dùng auto-configuration của Boot hoặc khi muốn khai báo rõ loại hypermedia, có thể bật hỗ trợ HAL:

~~~java
import org.springframework.context.annotation.Configuration;
import org.springframework.hateoas.config.EnableHypermediaSupport;

@Configuration
@EnableHypermediaSupport(
    type = EnableHypermediaSupport.HypermediaType.HAL
)
public class HypermediaConfiguration {
}
~~~

Không nên thêm cấu hình này một cách máy móc nếu Boot đã cấu hình hypermedia. Kiểm tra cấu hình hiện tại và tránh đăng ký các thành phần serializer hoặc hypermedia support trùng lặp.

## 10. Công bố HAL từ controller

Controller có thể trả trực tiếp EntityModel hoặc CollectionModel. Khai báo media type giúp làm rõ định dạng mà endpoint công bố:

~~~java
import java.util.UUID;

import org.springframework.hateoas.EntityModel;
import org.springframework.hateoas.MediaTypes;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OrderController {

    private final OrderService service;
    private final OrderModelAssembler assembler;

    public OrderController(
            OrderService service,
            OrderModelAssembler assembler) {
        this.service = service;
        this.assembler = assembler;
    }

    @GetMapping(
        value = "/orders/{id}",
        produces = MediaTypes.HAL_JSON_VALUE
    )
    public EntityModel<OrderRepresentation> one(
            @PathVariable UUID id) {

        Order order = service.findById(id);
        return assembler.toModel(order);
    }
}
~~~

Khi client gửi `Accept: application/hal+json`, Spring MVC chọn converter hypermedia phù hợp để serialize representation model thành HAL JSON.

Nếu endpoint hỗ trợ nhiều media type, có thể để content negotiation chọn định dạng dựa trên `Accept`. Cần kiểm thử cả status và `Content-Type` để bảo đảm response thực sự là HAL JSON khi client yêu cầu.

## 11. Ví dụ response HAL hoàn chỉnh

Một tài nguyên đơn hàng có thể được biểu diễn như sau:

~~~json
{
  "id": "ORD-42",
  "status": "PROCESSING",
  "total": 125000,
  "customer": {
    "id": "CUS-7",
    "name": "Nguyen An"
  },
  "_links": {
    "self": {
      "href": "https://api.example.com/orders/ORD-42"
    },
    "orders": {
      "href": "https://api.example.com/orders"
    },
    "customer": {
      "href": "https://api.example.com/customers/CUS-7"
    },
    "items": {
      "href": "https://api.example.com/orders/ORD-42/items"
    },
    "cancel": {
      "href": "https://api.example.com/orders/ORD-42/cancellation"
    }
  }
}
~~~

Client có thể:

1. Đọc dữ liệu đơn hàng và thông tin khách hàng tóm tắt.
2. Theo `self` để xác định URI canonical của đơn hàng.
3. Theo `items` khi cần xem các dòng hàng.
4. Theo `customer` khi cần thông tin khách hàng đầy đủ.
5. Dùng `cancel` nếu server công bố link hành động đó.

Sự xuất hiện của link cancel không thay thế kiểm tra quyền hoặc trạng thái ở endpoint. Client có thể giữ response cũ; server vẫn phải xác thực request khi thao tác thực sự được gửi.

## 12. HAL không mô tả đầy đủ mọi hành động

HAL định nghĩa cách biểu diễn link và tài nguyên nhúng. Một link HAL cơ bản có href và relation; metadata có thể mô tả thêm title, type hoặc trạng thái deprecated. Nhưng HAL không cung cấp một mô hình biểu mẫu đầy đủ để mô tả mọi HTTP method, trường request body và ràng buộc đầu vào.

Nếu client cần khám phá biểu mẫu hoặc dữ liệu đầu vào của thao tác, có thể xem xét HAL-FORMS. HAL-FORMS mở rộng cách biểu diễn hypermedia để công bố các template thao tác; trong response, phần template thường được thể hiện bằng thuộc tính `_templates`.

Phân biệt:

| Định dạng | Trọng tâm |
|---|---|
| HAL JSON | Link và tài nguyên nhúng |
| HAL-FORMS | HAL cùng mô tả template thao tác và biểu mẫu |
| JSON thông thường | Dữ liệu JSON, không có quy ước hypermedia bắt buộc |

Không giả định một response HAL cơ bản tự mô tả method POST hoặc schema body chỉ từ href. Nếu API cần công bố thao tác phong phú, hãy chọn media type có semantics phù hợp và kiểm thử client tương ứng.

## 13. Client nên tiêu thụ HAL như thế nào?

Một client hypermedia nên bắt đầu từ URI entry point được cấu hình hoặc được cung cấp. Sau đó, nó đọc relation trong response để tìm đường đi tiếp theo.

Luồng tổng quát:

~~~text
Entry point
    |
    v
GET resource
    |
    v
Parse HAL document
    |
    +-- Read data fields
    |
    +-- Find relation "orders"
    |       |
    |       v
    |    Follow href
    |
    +-- Find relation "customer"
            |
            v
         Follow href
~~~

Client nên:

- Tìm link theo relation thay vì ghép URL từ ID.
- Xử lý href tương đối theo URI cơ sở của response.
- Nhận biết `templated: true` và mở rộng URI template.
- Chấp nhận một relation có thể có một link hoặc nhiều link.
- Xử lý trường hợp relation hoặc link hành động không xuất hiện.
- Không giả định tài nguyên nhúng luôn có mặt.
- Xử lý status HTTP và lỗi khi theo link.

Client không nên phụ thuộc vào thứ tự các thuộc tính JSON. JSON object không đảm bảo thứ tự thuộc tính có ý nghĩa; relation mới có thể được thêm mà không cần client biết trước toàn bộ danh sách.

## 14. Kiểm thử HAL JSON

Kiểm thử endpoint nên xác nhận media type, dữ liệu và cấu trúc link. Ví dụ với MockMvc:

~~~java
mockMvc.perform(get("/orders/{id}", orderId)
        .accept(MediaTypes.HAL_JSON))
    .andExpect(status().isOk())
    .andExpect(content().contentTypeCompatibleWith(MediaTypes.HAL_JSON))
    .andExpect(jsonPath("$.id").value(orderId.toString()))
    .andExpect(jsonPath("$._links.self.href").exists())
    .andExpect(jsonPath("$._links.customer.href").exists());
~~~

Với collection, kiểm tra relation nhúng:

~~~java
mockMvc.perform(get("/orders")
        .accept(MediaTypes.HAL_JSON))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$._links.self.href").exists())
    .andExpect(jsonPath("$._embedded.orders").isArray());
~~~

Nếu collection có thể rỗng, hãy kiểm tra cấu trúc thực tế theo hợp đồng của ứng dụng. Không nên giả định mọi serializer đều phải phát ra một mảng `_embedded` rỗng cho mọi trường hợp; quan trọng là client có thể hiểu collection và các link cấp collection.

Ngoài JSONPath, có thể giải mã response thành `EntityModel<T>` hoặc `CollectionModel<T>` bằng các kiểu tham chiếu generic của Spring HATEOAS. Cách đó hữu ích khi muốn kiểm tra relation qua API Java thay vì kiểm tra JSON thô.

## 15. Những lỗi thường gặp khi dùng HAL

| Lỗi | Hệ quả | Cách xử lý |
|---|---|---|
| Trả JSON thường nhưng client kỳ vọng HAL | Không có `_links` và cấu trúc hypermedia | Yêu cầu và công bố `application/hal+json` |
| Client tự tạo URL từ ID | Phụ thuộc cấu trúc route | Theo href server cung cấp |
| Dùng relation không có ngữ nghĩa rõ | Client không biết link dẫn đến loại tài nguyên nào | Chọn relation chuẩn hoặc tài liệu hóa relation tùy chỉnh |
| Nhúng toàn bộ association | Payload lớn và coupling mạnh | Dùng link hoặc DTO summary |
| Nghĩ link tự động tải tài nguyên đích | Nhầm điều hướng với embedding | Theo href bằng request riêng khi cần |
| Nghĩ HAL cơ bản mô tả đầy đủ HTTP method và request body | Client không đủ thông tin thao tác | Dùng affordance hoặc media type mở rộng như HAL-FORMS |
| Không xử lý URI template | Client gửi href chưa được mở rộng | Kiểm tra `templated` và mở rộng biến |
| Đổi tên relation tùy tiện | Client cũ không tìm thấy link | Quản lý relation như hợp đồng API |
| Bật hypermedia support trùng lặp | Cấu hình serializer hoặc converter khó dự đoán | Kiểm tra auto-configuration trước khi khai báo thủ công |

## 16. Quy trình áp dụng HAL cho API

Khi xây dựng một endpoint HAL bằng Spring HATEOAS, có thể thực hiện theo thứ tự:

1. Xác định tài nguyên và các trường dữ liệu cần công bố.
2. Chọn DTO hoặc representation model để tránh phụ thuộc trực tiếp vào entity persistence.
3. Dùng EntityModel cho tài nguyên đơn, CollectionModel cho tập hợp hoặc PagedModel cho dữ liệu phân trang.
4. Thêm self link và các relation có ý nghĩa bằng Link.
5. Chọn association nào nên nhúng và association nào chỉ nên công bố bằng link.
6. Dùng `@Relation` khi cần kiểm soát tên relation item và collection.
7. Công bố media type `application/hal+json` và cấu hình hypermedia support phù hợp.
8. Kiểm thử `_links`, `_embedded`, URI template và Content-Type.
9. Thiết kế client theo relation và href, không phụ thuộc route nội bộ.
10. Nếu cần mô tả biểu mẫu thao tác, đánh giá HAL-FORMS hoặc affordance.

HAL cung cấp một cấu trúc đơn giản để kết hợp dữ liệu tài nguyên với khả năng điều hướng. Spring HATEOAS giúp tạo cấu trúc đó từ các representation model Java, giảm việc tự viết JSON hypermedia và hỗ trợ API công bố relation ổn định. Khi chọn đúng giữa link và embedding, giữ relation rõ nghĩa và kiểm thử media type cùng response, client có thể khám phá API theo những đường dẫn mà server cung cấp.
