# HAL và JSON thường

JSON là định dạng dữ liệu phổ biến để trao đổi giữa client và server. Tuy nhiên, một response JSON chỉ chứa các trường dữ liệu chưa chắc đã cho client biết cách tiếp tục điều hướng tới tài nguyên liên quan hoặc thao tác tiếp theo. HAL (Hypertext Application Language) bổ sung một quy ước hypermedia trên nền JSON: tài nguyên có thể công bố các liên kết trong `_links` và các representation được nhúng trong `_embedded`.

Với Spring HATEOAS, controller có thể trả `EntityModel`, `CollectionModel` hoặc một lớp kế thừa `RepresentationModel`. Spring HATEOAS và Jackson sẽ tuần tự hóa các model này thành HAL JSON khi response được thương lượng theo media type `application/hal+json`. Nhờ vậy, API vẫn dùng JSON quen thuộc nhưng có thêm cấu trúc để client khám phá tài nguyên qua relation và `href`.

## JSON thường và HAL khác nhau ở đâu?

JSON là cú pháp biểu diễn dữ liệu. Nó cho phép tạo object, array, string, number, boolean và null. JSON không tự quy định một trường URL có ý nghĩa quan hệ nào hoặc client cần dùng URL đó để điều hướng ra sao.

Ví dụ response JSON thường:

```json
{
  "id": "ORD-2048",
  "status": "PENDING",
  "customerId": "C-100",
  "total": 1250000
}
```

Client muốn tải khách hàng phải biết trước endpoint và cách ghép URL, chẳng hạn `/api/customers/{customerId}`. Nếu cấu trúc URL thay đổi, client có thể phải cập nhật logic điều hướng.

HAL vẫn là JSON nhưng có quy ước dành riêng cho hypermedia:

```json
{
  "id": "ORD-2048",
  "status": "PENDING",
  "total": 1250000,
  "_links": {
    "self": {
      "href": "/api/orders/ORD-2048"
    },
    "customer": {
      "href": "/api/customers/C-100"
    }
  }
}
```

Client tìm relation `customer`, đọc `href` rồi theo link đó. Client không cần tự ghép URL từ `customerId`. Nếu server thay đổi đường dẫn khách hàng, nó có thể trả `href` mới trong response mà vẫn giữ relation `customer`.

| Tiêu chí | JSON thường | HAL JSON |
|---|---|---|
| Định dạng nền | JSON | JSON |
| Trường dữ liệu | Theo hợp đồng ứng dụng | Theo hợp đồng ứng dụng |
| Liên kết hypermedia | Không có cấu trúc link chuẩn bắt buộc | `_links` chứa relation và link object |
| Tài nguyên nhúng | Có thể tự thiết kế cấu trúc | `_embedded` xác định embedded resource theo relation |
| Điều hướng | Client thường cần biết trước URL hoặc quy ước riêng | Client khám phá qua relation và `href` |
| Media type điển hình | `application/json` | `application/hal+json` |

HAL không phải một cú pháp thay thế JSON. Nó là một media type JSON có quy ước biểu diễn liên kết và tài nguyên nhúng. Một response JSON tự chứa trường `url` vẫn có thể dùng được, nhưng nếu không theo một quy ước hypermedia thống nhất, client phải tự biết ý nghĩa của trường đó.

## Hai thành phần chính của HAL

### `_links`: các liên kết

`_links` là object chứa các link relation. Mỗi khóa relation định nghĩa ý nghĩa của liên kết; giá trị là link object có thuộc tính `href` và có thể có metadata bổ sung.

```json
{
  "_links": {
    "self": {
      "href": "https://api.example.com/api/orders/ORD-2048"
    },
    "customer": {
      "href": "https://api.example.com/api/customers/C-100",
      "title": "Khách hàng đặt đơn"
    },
    "items": {
      "href": "https://api.example.com/api/orders/ORD-2048/items"
    }
  }
}
```

Một link object thường có `href`. HAL cũng hỗ trợ một số thuộc tính link như `templated`, `type`, `deprecation`, `name`, `profile`, `title` và `hreflang` khi phù hợp. Ví dụ link có URI template có thể đánh dấu `templated: true`:

```json
{
  "search": {
    "href": "/api/orders{?status,page,size}",
    "templated": true
  }
}
```

Client cần hiểu URI template theo quy tắc URI Template khi `templated` là `true`; không nên tự nối chuỗi query vào một URL template.

Nếu một relation có nhiều link, HAL cho phép giá trị relation là một mảng link object. Client cần xử lý cả link đơn và nhiều link khi hợp đồng API có sử dụng dạng này.

### `_embedded`: các representation được nhúng

`_embedded` chứa representation của tài nguyên liên quan hoặc phần tử của collection. Khóa của mỗi entry là relation mô tả loại tài nguyên được nhúng.

```json
{
  "_embedded": {
    "customer": {
      "id": "C-100",
      "displayName": "Nguyen An",
      "_links": {
        "self": {
          "href": "/api/customers/C-100"
        }
      }
    }
  },
  "_links": {
    "self": {
      "href": "/api/orders/ORD-2048"
    },
    "customer": {
      "href": "/api/customers/C-100"
    }
  }
}
```

Trong ví dụ, client có thể hiển thị thông tin khách hàng ngay từ response đơn hàng. Link `customer` vẫn cho phép client truy cập tài nguyên khách hàng đầy đủ. Không bắt buộc phải vừa nhúng vừa cung cấp link trong mọi response; lựa chọn phụ thuộc vào nhu cầu đọc và hợp đồng API.

## Khi nào dùng JSON thường, khi nào dùng HAL?

JSON thường phù hợp khi client và server đã thống nhất một schema dữ liệu cố định, response không cần điều hướng tới tài nguyên khác hoặc endpoint chỉ phục vụ một tác vụ đơn giản. Ví dụ health check, dữ liệu nội bộ cho một workflow cố định hoặc response của một lệnh có cấu trúc nhỏ.

HAL phù hợp khi API muốn công bố các đường điều hướng giữa tài nguyên, có collection, có tài nguyên liên quan hoặc muốn client khám phá endpoint từ response. Ví dụ:

- Đơn hàng có link tới khách hàng, dòng hàng, thanh toán và giao hàng.
- Khách hàng có link tới collection đơn hàng.
- Collection phân trang có link `self`, `next`, `prev`, `first` và `last`.
- Một tài nguyên có action link như `cancel` khi trạng thái cho phép.

HAL không tự mô tả đầy đủ mọi thao tác. Link thông thường chỉ cho biết quan hệ và đích. Nếu client cần biết HTTP method, content type và trường đầu vào của thao tác, có thể dùng affordance với định dạng hỗ trợ như HAL-FORMS.

## Media type và Content Negotiation

Media type tiêu chuẩn của HAL JSON là:

```http
application/hal+json
```

Client gửi `Accept` để yêu cầu HAL:

```http
GET /api/orders/ORD-2048 HTTP/1.1
Accept: application/hal+json
```

Server trả response với `Content-Type` phù hợp:

```http
HTTP/1.1 200 OK
Content-Type: application/hal+json
```

Phân biệt hai header:

- `Accept` mô tả media type client muốn nhận.
- `Content-Type` mô tả media type của body mà server trả về (hoặc client gửi lên trong request có body).

Nếu endpoint chỉ hỗ trợ HAL mà client yêu cầu media type không được hỗ trợ, server có thể trả `406 Not Acceptable`. Nếu client gửi `Accept: application/hal+json`, server cần tuần tự hóa model theo HAL và trả đúng content type.

## Cấu hình Spring HATEOAS cho HAL

Trong ứng dụng Spring Boot dùng Spring MVC, có thể thêm starter Spring HATEOAS để tích hợp model hypermedia và cấu hình tự động:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-hateoas'
}
```

Với Maven:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-hateoas</artifactId>
</dependency>
```

Khi tự cấu hình Spring MVC, có thể bật hỗ trợ HAL rõ ràng:

```java
import org.springframework.context.annotation.Configuration;
import org.springframework.hateoas.config.EnableHypermediaSupport;
import org.springframework.hateoas.config.EnableHypermediaSupport.HypermediaType;

@Configuration
@EnableHypermediaSupport(type = HypermediaType.HAL)
public class HypermediaConfiguration {
}
```

Nếu ứng dụng đã dùng Spring Boot auto-configuration, hãy kiểm tra cấu hình hiện có trước khi thêm annotation hoặc tự đăng ký converter. Tránh cấu hình trùng lặp làm thay đổi cách Jackson và hypermedia module được thiết lập.

## Trả EntityModel để tạo HAL cho một tài nguyên

`EntityModel<T>` bọc nội dung của một tài nguyên cùng các link. Ví dụ assembler cho đơn hàng:

```java
import java.util.UUID;

import org.springframework.hateoas.EntityModel;
import org.springframework.hateoas.server.RepresentationModelAssembler;
import org.springframework.stereotype.Component;

import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.linkTo;
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.methodOn;

@Component
public class OrderModelAssembler implements
        RepresentationModelAssembler<Order, EntityModel<OrderResponse>> {

    @Override
    public EntityModel<OrderResponse> toModel(Order order) {
        UUID id = order.getId();

        return EntityModel.of(
                new OrderResponse(id, order.getStatus().name(), order.getTotal()),
                linkTo(methodOn(OrderController.class).one(id)).withSelfRel(),
                linkTo(methodOn(CustomerController.class)
                        .one(order.getCustomerId())).withRel("customer")
        );
    }
}
```

Controller trả `EntityModel` thay vì trả DTO trực tiếp:

```java
import java.util.UUID;

import org.springframework.hateoas.MediaTypes;
import org.springframework.hateoas.EntityModel;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService service;
    private final OrderModelAssembler assembler;

    public OrderController(OrderService service, OrderModelAssembler assembler) {
        this.service = service;
        this.assembler = assembler;
    }

    @GetMapping(value = "/{id}", produces = MediaTypes.HAL_JSON_VALUE)
    public EntityModel<OrderResponse> one(@PathVariable UUID id) {
        return assembler.toModel(service.findRequired(id));
    }
}
```

Khi Spring HATEOAS được cấu hình, HTTP message converter và Jackson module sẽ chuyển `EntityModel` thành HAL JSON. Không cần tự tạo object `_links` hoặc gọi `ObjectMapper` trong controller.

Response có dạng minh họa:

```json
{
  "id": "ORD-2048",
  "status": "PENDING",
  "total": 1250000,
  "_links": {
    "self": {
      "href": "http://localhost:8080/api/orders/ORD-2048"
    },
    "customer": {
      "href": "http://localhost:8080/api/customers/C-100"
    }
  }
}
```

Địa chỉ có thể là URI tương đối hoặc tuyệt đối tùy cấu hình request và triển khai. Client nên dùng `href` được trả về thay vì giả định host hoặc port.

## Trả CollectionModel cho danh sách

`CollectionModel<T>` biểu diễn một tập hợp representation và link cấp collection. Với collection đơn giản:

```java
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.linkTo;
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.methodOn;

import org.springframework.hateoas.MediaTypes;
import org.springframework.hateoas.CollectionModel;
import org.springframework.hateoas.EntityModel;
import org.springframework.web.bind.annotation.GetMapping;

@GetMapping(produces = MediaTypes.HAL_JSON_VALUE)
public CollectionModel<EntityModel<OrderResponse>> all() {
    return assembler.toCollectionModel(service.findAll())
            .add(linkTo(methodOn(OrderController.class).all()).withSelfRel());
}
```

Một response HAL collection có thể có cấu trúc:

```json
{
  "_embedded": {
    "orders": [
      {
        "id": "ORD-2048",
        "status": "PENDING",
        "_links": {
          "self": {
            "href": "/api/orders/ORD-2048"
          }
        }
      },
      {
        "id": "ORD-2049",
        "status": "PAID",
        "_links": {
          "self": {
            "href": "/api/orders/ORD-2049"
          }
        }
      }
    ]
  },
  "_links": {
    "self": {
      "href": "/api/orders"
    }
  }
}
```

Relation `orders` trong `_embedded` định danh các phần tử của collection. Có thể dùng `@Relation` trên lớp representation riêng để xác định `collectionRelation` và `itemRelation` rõ ràng:

```java
import org.springframework.hateoas.RepresentationModel;
import org.springframework.hateoas.server.core.Relation;

@Relation(itemRelation = "order", collectionRelation = "orders")
public class OrderModel extends RepresentationModel<OrderModel> {
    // Các trường dữ liệu công khai của đơn hàng.
}
```

Tên `orders` trong JSON minh họa giả định collection relation đã được cấu hình như trên hoặc được cung cấp bởi relation provider của ứng dụng. Nếu dùng một kiểu DTO khác, hãy xác nhận relation provider tạo đúng tên mà client mong đợi; không nên dựa vào tên suy ra nếu đó là một phần ổn định của hợp đồng API.

Với ví dụ `CollectionModel<EntityModel<OrderResponse>>` ở trên, relation provider cần xác định `orders` từ kiểu content `OrderResponse` hoặc từ cấu hình tương ứng. Có thể đặt annotation trực tiếp trên DTO:

```java
import java.math.BigDecimal;
import java.util.UUID;

import org.springframework.hateoas.server.core.Relation;

@Relation(itemRelation = "order", collectionRelation = "orders")
public record OrderResponse(UUID id, String status, BigDecimal total) {}
```

Một lựa chọn khác là dùng `CollectionModel<OrderModel>` với lớp `OrderModel` kế thừa `RepresentationModel` như ví dụ trước. Annotation cần nằm trên kiểu representation/content mà relation provider thực sự dùng để xác định tên relation.

Với collection phân trang, Spring HATEOAS có thể tạo `PagedModel` và các link điều hướng như `next`, `prev`, `first` và `last`. Client nên theo các link do server cung cấp để giữ nguyên bộ lọc và cách phân trang.

Collection rỗng có thể không có `_embedded` vì không có phần tử để nhúng. Link ở cấp collection như `self` vẫn có thể xuất hiện để client biết collection hiện tại và tiếp tục điều hướng.

## Client đọc HAL như thế nào?

Một HAL client không nên ghép URL từ ID hoặc dựa vào cấu trúc đường dẫn. Thay vào đó, nó thực hiện theo trình tự:

1. Gửi request tới entry point đã được cấu hình.
2. Đọc response và tìm relation cần thiết trong `_links`.
3. Lấy `href` của link relation đó.
4. Gửi request tới URI vừa nhận, với `Accept` phù hợp.
5. Tiếp tục khám phá relation trong response mới.

Ví dụ logic giả mã:

```text
order = GET(entryPoint)
customerHref = order._links.customer.href
customer = GET(customerHref)
```

Client chỉ cần biết relation `customer` có ý nghĩa gì theo hợp đồng API. Nó không cần tự xây dựng `/api/customers/{id}`.

Trong ứng dụng thực tế, client cần xử lý trường hợp relation không xuất hiện, link là mảng, URI được đánh dấu `templated`, response không có `_embedded` hoặc server trả lỗi HTTP. Việc không có link có thể có nghĩa quan hệ không được công bố trong ngữ cảnh hiện tại.

## HAL và affordance

HAL cơ bản cung cấp cấu trúc để biểu diễn link và embedded resource. Nó không mô tả đầy đủ method HTTP và input template cho một thao tác cập nhật. Ví dụ, link `cancel` cho biết có một hướng điều hướng mang quan hệ hủy, nhưng không tự cho client biết phải gửi `POST`, `DELETE` hay body nào.

Khi cần mô tả thao tác có thể thực hiện, có thể kết hợp Spring HATEOAS affordance với định dạng như HAL-FORMS. HAL-FORMS sử dụng `_templates` để mô tả method, target, content type và property đầu vào. Đây là một media type khác (`application/prs.hal-forms+json`), không phải trường `_templates` tiêu chuẩn của HAL JSON.

Vì vậy, hãy chọn HAL khi client cần khám phá tài nguyên và quan hệ; chọn HAL-FORMS khi hợp đồng cần mô tả thêm cách gửi thao tác và dữ liệu đầu vào.

## Kiểm thử response HAL

MockMvc có thể xác nhận media type, dữ liệu và link trong response:

```java
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import org.springframework.hateoas.MediaTypes;

mockMvc.perform(get("/api/orders/{id}", orderId)
        .accept(MediaTypes.HAL_JSON))
    .andExpect(status().isOk())
    .andExpect(content().contentTypeCompatibleWith(MediaTypes.HAL_JSON))
    .andExpect(jsonPath("$.id").value(orderId.toString()))
    .andExpect(jsonPath("$._links.self.href").exists())
    .andExpect(jsonPath("$._links.customer.href").exists());
```

Với collection, kiểm tra `_embedded` và link cấp collection:

```java
mockMvc.perform(get("/api/orders").accept(MediaTypes.HAL_JSON))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$._links.self.href").exists())
    .andExpect(jsonPath("$._embedded.orders").isArray());
```

Nên có thêm test cho collection rỗng, link tùy chọn và media type không được hỗ trợ. Các test này bảo vệ cấu trúc HAL mà client đang sử dụng, thay vì chỉ xác nhận response có status `200`.

## Những lỗi thường gặp

| Lỗi | Hệ quả | Cách xử lý |
|---|---|---|
| Nghĩ HAL là cú pháp JSON khác | Thiết kế serializer không cần thiết | Hiểu HAL là media type JSON có quy ước hypermedia |
| Trả DTO trực tiếp khi client cần link | Client phải tự ghép URL | Trả `EntityModel` hoặc `CollectionModel` |
| Tự tạo object `_links` bằng tay | Relation và cấu trúc dễ không nhất quán | Dùng Spring HATEOAS model và link builder |
| Nhầm `href` với relation | Client phụ thuộc URL thay vì ngữ nghĩa | Đọc link qua relation rồi theo `href` |
| Nhúng toàn bộ tài nguyên liên quan | Response lớn và dễ tạo vòng lặp | Chọn embedded resource có kiểm soát, phần còn lại dùng link |
| Chỉ kiểm tra JSON fields | Không phát hiện lỗi hypermedia | Kiểm tra `_links`, `_embedded` và media type |
| Mong HAL tự mô tả PUT/POST input | Client không biết method và body | Dùng affordance và HAL-FORMS khi cần |
| Hard-code host hoặc path ở client | Client hỏng khi server đổi URL | Dùng `href` do server cung cấp |

## Quy trình chọn và triển khai HAL

1. Xác định client có cần điều hướng giữa các tài nguyên hay chỉ cần dữ liệu JSON.
2. Nếu cần hypermedia, chọn relation có ý nghĩa rõ ràng cho từng liên kết.
3. Tạo DTO hoặc representation model chỉ chứa dữ liệu công khai.
4. Dùng `EntityModel` cho tài nguyên đơn và `CollectionModel` cho tập hợp.
5. Tạo link từ mapping controller bằng `WebMvcLinkBuilder`.
6. Cấu hình Spring HATEOAS và thương lượng `application/hal+json`.
7. Dùng `_embedded` khi client cần dữ liệu liên quan ngay trong response; dùng `_links` để điều hướng.
8. Dùng HAL-FORMS nếu client cần metadata về method và input template.
9. Kiểm thử media type, relation, `href`, collection rỗng và các trường hợp link tùy chọn.

## Kết luận

JSON thường tập trung vào dữ liệu; HAL giữ nền JSON và bổ sung cấu trúc hypermedia qua `_links` và `_embedded`. Với Spring HATEOAS, `EntityModel`, `CollectionModel`, assembler và link builder giúp tạo response HAL mà không phải tự dựng cấu trúc liên kết. Khi client điều hướng theo relation và `href`, server có thể thay đổi URL mà không buộc client ghép lại đường dẫn. Nếu cần mô tả method và input của thao tác, hãy mở rộng bằng affordance và HAL-FORMS thay vì kỳ vọng HAL cơ bản cung cấp metadata đó.
