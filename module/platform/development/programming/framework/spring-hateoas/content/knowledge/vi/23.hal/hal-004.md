# _embedded

## Mục tiêu

Sau bài này, bạn có thể giải thích vai trò của `_embedded` trong HAL, phân biệt tài nguyên nhúng với liên kết chỉ dẫn đến tài nguyên, đặt tên relation cho phần tử nhúng bằng Spring HATEOAS, tạo collection và representation lồng nhau, đồng thời kiểm thử cấu trúc HAL mà client sử dụng.

## 1. _embedded biểu diễn điều gì?

HAL (Hypertext Application Language) là một định dạng hypermedia JSON. Trong HAL, một representation thường có hai nhóm metadata quan trọng:

- `_links` chứa các liên kết đến tài nguyên hoặc thao tác liên quan.
- `_embedded` chứa representation của các tài nguyên được nhúng trực tiếp trong response hiện tại.

Ví dụ, endpoint đơn hàng trả về thông tin đơn hàng và nhúng thông tin khách hàng:

```json
{
  "id": "order-42",
  "status": "PENDING",
  "_links": {
    "self": {
      "href": "/orders/order-42"
    }
  },
  "_embedded": {
    "customer": {
      "id": "customer-7",
      "name": "Nguyen An",
      "_links": {
        "self": {
          "href": "/customers/customer-7"
        }
      }
    }
  }
}
```

Trong ví dụ:

- Các trường `id` và `status` là dữ liệu của đơn hàng.
- `_links.self` trỏ đến chính đơn hàng.
- `_embedded.customer` chứa representation của khách hàng ngay trong response.
- `_embedded.customer._links.self` vẫn cho phép client truy cập riêng tài nguyên khách hàng.

Nhúng tài nguyên giúp client nhận được dữ liệu liên quan trong cùng một lần gọi HTTP. Client không cần gửi thêm request chỉ để lấy tên khách hàng trong trường hợp màn hình hiện tại cần hiển thị thông tin đó.

## 2. Phân biệt embedded resource và link

Một link và một embedded resource có mục đích khác nhau:

| Cách biểu diễn | HAL | Ý nghĩa |
|---|---|---|
| Chỉ cung cấp link | `_links.customer.href` | Cho client biết URI để tải khách hàng |
| Nhúng tài nguyên | `_embedded.customer` | Trả representation khách hàng ngay trong response |
| Nhúng kèm link | `_embedded.customer._links.self` | Trả dữ liệu khách hàng và giữ khả năng truy cập tài nguyên độc lập |

Ví dụ chỉ có link:

```json
{
  "id": "order-42",
  "_links": {
    "self": {
      "href": "/orders/order-42"
    },
    "customer": {
      "href": "/customers/customer-7"
    }
  }
}
```

Client muốn hiển thị tên khách hàng phải theo link `customer` và gửi request riêng.

Nếu nhúng khách hàng:

```json
{
  "id": "order-42",
  "_links": {
    "self": {
      "href": "/orders/order-42"
    }
  },
  "_embedded": {
    "customer": {
      "id": "customer-7",
      "name": "Nguyen An"
    }
  }
}
```

Client có dữ liệu khách hàng ngay trong response. Tuy nhiên, embedded resource không nhất thiết thay thế link đến tài nguyên độc lập. Nếu client cần làm mới, xem chi tiết hoặc điều hướng đến khách hàng, hãy giữ self link của embedded resource hoặc một link quan hệ phù hợp.

Nhúng dữ liệu có thể giảm số lần gọi API, nhưng cũng làm response lớn hơn và khiến dữ liệu được lặp lại ở nhiều representation. Hãy nhúng theo nhu cầu thực tế của client, không nhúng toàn bộ đồ thị domain một cách tự động.

## 3. Relation đặt tên cho embedded resource

Mỗi embedded resource được đặt dưới một relation trong `_embedded`. Tên relation là một phần hợp đồng hypermedia mà client dùng để tìm dữ liệu.

Ví dụ:

- `customer` mô tả một khách hàng liên quan.
- `items` mô tả danh sách dòng hàng của đơn hàng.
- `orders` mô tả collection các đơn hàng.
- `address` mô tả địa chỉ giao hàng.

Trong Spring HATEOAS, có thể dùng annotation `@Relation` trên representation model để định nghĩa tên relation cho item và collection:

```java
import java.math.BigDecimal;
import java.util.UUID;

import org.springframework.hateoas.RepresentationModel;
import org.springframework.hateoas.server.core.Relation;

@Relation(value = "order", collectionRelation = "orders")
public class OrderModel extends RepresentationModel<OrderModel> {

    private final UUID id;
    private final String status;
    private final BigDecimal total;

    public OrderModel(UUID id, String status, BigDecimal total) {
        this.id = id;
        this.status = status;
        this.total = total;
    }

    public UUID getId() {
        return id;
    }

    public String getStatus() {
        return status;
    }

    public BigDecimal getTotal() {
        return total;
    }
}
```

Hai thuộc tính có ý nghĩa:

- `value = "order"` đặt relation cho một item.
- `collectionRelation = "orders"` đặt relation cho collection các item.

Khi một `CollectionModel<OrderModel>` được tuần tự hóa thành HAL, collection relation có thể được dùng làm tên trong `_embedded.orders`. Việc khai báo rõ relation giúp tránh phụ thuộc vào quy tắc suy luận tên từ class hoặc cách đặt tên mặc định.

Relation cần ổn định qua các phiên bản API. Nếu client đang đọc `_embedded.orders`, đổi tên thành `_embedded.orderList` có thể làm client không tìm thấy dữ liệu dù các trường bên trong không đổi.

## 4. Tạo embedded collection bằng CollectionModel

Khi endpoint trả về một danh sách tài nguyên, Spring HATEOAS dùng `CollectionModel<T>` để biểu diễn tập hợp cùng các link ở cấp collection. Mỗi phần tử có thể là một representation model mang link riêng.

Assembler cho một đơn hàng:

```java
@Component
public class OrderModelAssembler
        implements RepresentationModelAssembler<Order, OrderModel> {

    @Override
    public OrderModel toModel(Order order) {
        OrderModel model = new OrderModel(
                order.getId(),
                order.getStatus().name(),
                order.getTotal()
        );

        model.add(linkTo(methodOn(OrderController.class)
                .getOrder(order.getId())).withSelfRel());

        return model;
    }
}
```

Controller trả về collection:

```java
@GetMapping
public CollectionModel<OrderModel> getOrders() {
    List<OrderModel> items = orderService.findAll()
            .stream()
            .map(orderAssembler::toModel)
            .toList();

    Link self = linkTo(methodOn(OrderController.class)
            .getOrders())
            .withSelfRel();

    return CollectionModel.of(items, self);
}
```

Với `@Relation(value = "order", collectionRelation = "orders")`, response HAL có dạng:

```json
{
  "_embedded": {
    "orders": [
      {
        "id": "order-42",
        "status": "PENDING",
        "total": 125000,
        "_links": {
          "self": {
            "href": "/orders/order-42"
          }
        }
      },
      {
        "id": "order-43",
        "status": "PAID",
        "total": 89000,
        "_links": {
          "self": {
            "href": "/orders/order-43"
          }
        }
      }
    ]
  },
  "_links": {
    "self": {
      "href": "/orders"
    }
  }
}
```

`_embedded.orders` chứa các item; mỗi item giữ self link riêng. `_links.self` ở cấp ngoài trỏ đến collection. Đây là hai cấp representation khác nhau và nên được kiểm thử riêng.

Các import chính cho controller:

```java
import java.util.List;

import org.springframework.hateoas.CollectionModel;
import org.springframework.hateoas.Link;

import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.linkTo;
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.methodOn;
```

## 5. Nhúng tài nguyên liên quan vào một representation cha

Một response có thể cần nhúng nhiều loại tài nguyên. Ví dụ trang chi tiết đơn hàng hiển thị thông tin khách hàng và các dòng hàng. Có thể dùng `HalModelBuilder` để tạo representation HAL và chỉ định relation cho từng tài nguyên nhúng.

```java
import org.springframework.hateoas.LinkRelation;
import org.springframework.hateoas.RepresentationModel;
import org.springframework.hateoas.mediatype.hal.HalModelBuilder;

public RepresentationModel<?> toOrderDetail(Order order) {
    OrderView view = new OrderView(
            order.getId(),
            order.getStatus().name(),
            order.getTotal()
    );

    Link self = linkTo(methodOn(OrderController.class)
            .getOrder(order.getId()))
            .withSelfRel();

    EntityModel<CustomerView> customer =
            customerAssembler.toModel(order.getCustomer());

    CollectionModel<OrderItemModel> items =
            itemAssembler.toCollectionModel(order.getItems());

    return HalModelBuilder.halModelOf(view)
            .link(self)
            .embed(customer, LinkRelation.of("customer"))
            .embed(items, LinkRelation.of("items"))
            .build();
}
```

Trong ví dụ:

- `halModelOf(view)` tạo representation cha từ dữ liệu đơn hàng.
- `link(self)` thêm liên kết đến chính đơn hàng.
- `embed(customer, LinkRelation.of("customer"))` nhúng một representation khách hàng.
- `embed(items, LinkRelation.of("items"))` nhúng collection các dòng hàng.
- `build()` tạo HAL representation để Spring tuần tự hóa.

Cấu trúc response minh họa:

```json
{
  "id": "order-42",
  "status": "PENDING",
  "total": 125000,
  "_links": {
    "self": {
      "href": "/orders/order-42"
    }
  },
  "_embedded": {
    "customer": {
      "id": "customer-7",
      "name": "Nguyen An",
      "_links": {
        "self": {
          "href": "/customers/customer-7"
        }
      }
    },
    "items": [
      {
        "id": "item-1",
        "name": "Keyboard",
        "quantity": 1,
        "_links": {
          "self": {
            "href": "/orders/order-42/items/item-1"
          }
        }
      }
    ]
  }
}
```

Tên relation trong lời gọi `embed(..., LinkRelation.of(...))` xác định tên phần tử trong `_embedded`. Với collection, giá trị nhúng là một mảng representation. Với một tài nguyên đơn, giá trị thường là một object representation.

`HalModelBuilder` phù hợp khi muốn chủ động tạo cấu trúc HAL lồng nhau. Nó gắn cách xây dựng response với HAL; nếu cần representation độc lập định dạng, hãy cân nhắc các model Spring HATEOAS thông thường và để message converter xử lý serialization.

## 6. Embedded resource vẫn nên có links phù hợp

Nhúng tài nguyên không có nghĩa client mất khả năng điều hướng đến nó. Một embedded representation có thể chứa `_links` riêng, đặc biệt là relation `self`.

Ví dụ:

```json
{
  "_embedded": {
    "customer": {
      "id": "customer-7",
      "name": "Nguyen An",
      "_links": {
        "self": {
          "href": "/customers/customer-7"
        },
        "orders": {
          "href": "/customers/customer-7/orders"
        }
      }
    }
  }
}
```

Client có thể hiển thị tên khách hàng ngay lập tức, sau đó theo `self` để mở trang chi tiết hoặc theo `orders` để tải các đơn hàng của khách hàng.

Không cần lặp lại tất cả link có thể có trên mọi embedded resource. Hãy cung cấp những relation có ý nghĩa trong ngữ cảnh response. Nếu một tài nguyên chỉ được nhúng để hiển thị một vài trường tóm tắt và không cần điều hướng độc lập, có thể dùng DTO tóm tắt gọn; nếu client cần tương tác tiếp, hãy cung cấp link phù hợp.

## 7. Collection nhúng và phân trang

Một embedded collection lớn có thể làm response tăng nhanh về kích thước. Ví dụ một đơn hàng có hàng nghìn dòng hàng hoặc một khách hàng có hàng chục nghìn đơn. Không nên nhúng toàn bộ collection chỉ vì có thể làm được.

Với collection lớn, có thể nhúng một phần dữ liệu tóm tắt và cung cấp link đến endpoint collection riêng:

```json
{
  "id": "customer-7",
  "name": "Nguyen An",
  "_links": {
    "self": {
      "href": "/customers/customer-7"
    },
    "orders": {
      "href": "/customers/customer-7/orders"
    }
  },
  "_embedded": {
    "recentOrders": [
      {
        "id": "order-42",
        "status": "PENDING"
      },
      {
        "id": "order-43",
        "status": "PAID"
      }
    ]
  }
}
```

Trong ví dụ, `recentOrders` là phần dữ liệu tóm tắt được nhúng; `orders` là link đến collection đầy đủ. Client có thể tải collection theo nhu cầu.

Nếu endpoint collection hỗ trợ phân trang, dùng `PagedModel<T>` hoặc `PagedResourcesAssembler` để trả metadata và link `first`, `prev`, `next`, `last`. Một response phân trang HAL có thể có dạng:

```json
{
  "_embedded": {
    "orders": [
      {
        "id": "order-42",
        "status": "PENDING"
      }
    ]
  },
  "_links": {
    "self": {
      "href": "/orders?page=0&size=20"
    },
    "next": {
      "href": "/orders?page=1&size=20"
    }
  },
  "page": {
    "size": 20,
    "totalElements": 85,
    "totalPages": 5,
    "number": 0
  }
}
```

Phân trang giới hạn số item trong một response và cung cấp cách điều hướng đến phần còn lại. Khi giữ link đến collection trong representation cha, client có thể tải dữ liệu lớn theo từng trang thay vì nhận toàn bộ ngay từ đầu.

## 8. Collection rỗng và relation nhúng

Collection không có phần tử vẫn là một collection hợp lệ. Ví dụ khách hàng chưa có đơn hàng có thể trả về collection rỗng cùng link self:

```java
CollectionModel<OrderModel> emptyOrders =
        CollectionModel.empty(OrderModel.class);

emptyOrders.add(linkTo(methodOn(CustomerOrderController.class)
        .getOrders(customerId)).withSelfRel());

return emptyOrders;
```

Fallback type `OrderModel.class` cung cấp thông tin kiểu phần tử để Spring HATEOAS xác định collection relation khi không có item để suy luận. Điều này hữu ích khi tên relation như `orders` cần ổn định ngay cả lúc collection rỗng.

Nếu nhúng collection rỗng bằng `HalModelBuilder`, hãy kiểm tra response thực tế ở phiên bản Spring HATEOAS đang dùng để xác nhận relation và hình dạng JSON đúng với hợp đồng. Không nên giả định serializer luôn phát ra một mảng rỗng theo cùng cách trong mọi cấu hình hoặc mọi model.

Collection rỗng khác với việc không công bố collection. Nếu client cần biết quan hệ đó tồn tại nhưng hiện không có phần tử, hãy giữ relation collection và biểu diễn trạng thái rỗng theo định dạng đã thống nhất. Nếu không công bố relation, client có thể hiểu rằng API không hỗ trợ quan hệ đó.

## 9. Lưu ý về dữ liệu, bảo mật và hiệu năng

Embedded resource là dữ liệu được trả trực tiếp trong response hiện tại. Vì vậy, cần kiểm tra các vấn đề sau:

- **Quyền truy cập:** chỉ nhúng trường mà người gọi được phép xem. Không để việc nhúng bỏ qua chính sách bảo mật của endpoint tài nguyên gốc.
- **Kích thước response:** giới hạn số phần tử và số tầng nhúng. Dùng pagination cho collection lớn.
- **Truy vấn dữ liệu:** tránh N+1 khi assembler truy cập từng quan hệ. Dùng projection hoặc fetch plan phù hợp để tải dữ liệu cần thiết.
- **Dữ liệu lặp:** cùng một tài nguyên có thể xuất hiện trong nhiều response hoặc nhiều nhánh embedded. Chỉ nhúng trường thực sự cần thiết.
- **Tính nhất quán:** embedded data là snapshot tại thời điểm response được tạo. Client không nên mặc định nó luôn đồng bộ với response của endpoint riêng ở thời điểm sau.
- **Cache:** khi dữ liệu con thay đổi, representation cha có thể cũng thay đổi. Cân nhắc chính sách cache và validator phù hợp với phạm vi dữ liệu được nhúng.

Đặc biệt, không nên trả trực tiếp entity JPA có quan hệ hai chiều rồi để Jackson tự duyệt object graph. Điều đó có thể tạo vòng tham chiếu, lazy loading ngoài dự kiến hoặc làm lộ dữ liệu nội bộ. Hãy dùng DTO, assembler và các model hypermedia để quyết định rõ tài nguyên nào được nhúng.

## 10. Kiểm thử _embedded bằng MockMvc

Kiểm thử HTTP nên xác nhận media type HAL, relation embedded, dữ liệu của item và links bên trong embedded resource.

Với collection đơn hàng:

```java
mockMvc.perform(get("/orders")
        .accept(MediaTypes.HAL_JSON))
    .andExpect(status().isOk())
    .andExpect(content().contentTypeCompatibleWith(
            MediaTypes.HAL_JSON))
    .andExpect(jsonPath("$._embedded.orders").isArray())
    .andExpect(jsonPath("$._embedded.orders[0].id").exists())
    .andExpect(jsonPath("$._embedded.orders[0]._links.self.href").exists())
    .andExpect(jsonPath("$._links.self.href").exists());
```

Với representation đơn hàng có nhúng khách hàng và dòng hàng:

```java
mockMvc.perform(get("/orders/{id}", orderId)
        .accept(MediaTypes.HAL_JSON))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$._embedded.customer.id").exists())
    .andExpect(jsonPath("$._embedded.customer._links.self.href").exists())
    .andExpect(jsonPath("$._embedded.items").isArray())
    .andExpect(jsonPath("$._embedded.items[0].id").exists());
```

Nên có thêm các trường hợp:

1. Relation trong `_embedded` dùng đúng tên đã cam kết.
2. Embedded item có các trường công khai cần thiết và không lộ trường nội bộ.
3. Collection rỗng vẫn giữ relation hoặc self link theo hợp đồng.
4. Collection lớn được phân trang hoặc giới hạn số phần tử.
5. Người dùng không có quyền không nhận được dữ liệu embedded bị hạn chế.
6. Link self bên trong embedded resource trỏ đến endpoint riêng hợp lệ.
7. Khi thay đổi mapping nội bộ, relation và semantics của embedded resource vẫn ổn định.

Không nên chỉ kiểm tra `_embedded` tồn tại. Hãy kiểm tra relation cụ thể, cấu trúc object/array và các link cần thiết để client có thể tiếp tục điều hướng.

## 11. Lỗi thường gặp

**Nhầm link với embedded resource.** Link chỉ cung cấp URI; embedded resource cung cấp representation trong response. Chọn theo nhu cầu dữ liệu của client.

**Không kiểm soát relation name.** Tên relation có thể thay đổi theo quy tắc suy luận. Dùng `@Relation` hoặc relation tường minh trong `HalModelBuilder` khi tên là một phần hợp đồng.

**Nhúng toàn bộ entity graph.** Điều này có thể gây vòng tham chiếu, truy vấn quá nhiều hoặc lộ dữ liệu. Dùng DTO và assembler.

**Nhúng collection không giới hạn.** Response có thể quá lớn. Giới hạn số phần tử hoặc cung cấp link đến collection phân trang.

**Bỏ self link của embedded resource khi client cần điều hướng.** Client nhận được dữ liệu nhưng không có URI chuẩn để tải tài nguyên riêng. Thêm link phù hợp vào representation con.

**Không phân biệt self link collection với self link item.** Link ở cấp ngoài trỏ đến collection; link trong từng item trỏ đến tài nguyên đó. Kiểm thử cả hai.

**Không kiểm tra quyền trên dữ liệu nhúng.** Một endpoint được phép trả đơn hàng không có nghĩa mọi trường khách hàng hoặc thông tin liên quan đều được phép công bố. Áp dụng chính sách truy cập cho từng phần dữ liệu.

## 12. Nguyên tắc thiết kế

- Dùng `_embedded` khi client cần dữ liệu tài nguyên liên quan ngay trong response.
- Dùng `_links` khi chỉ cần công bố URI để client tải tài nguyên sau.
- Chọn relation ngắn, rõ nghĩa và ổn định.
- Dùng `@Relation` để xác định item relation và collection relation cho model.
- Dùng `CollectionModel` cho collection và `HalModelBuilder` khi cần chủ động tạo HAL lồng nhau.
- Giữ self link trên embedded resource khi client cần truy cập độc lập.
- Phân trang hoặc giới hạn collection lớn; kiểm soát độ sâu của representation lồng nhau.
- Dùng DTO và assembler để tránh phụ thuộc vào entity persistence.
- Kiểm thử relation, cấu trúc embedded, link và quyền truy cập bằng MockMvc.

## Kết luận

Trong HAL, `_embedded` chứa representation của các tài nguyên liên quan được nhúng trực tiếp trong response; `_links` cung cấp URI để client điều hướng. Spring HATEOAS hỗ trợ tạo embedded collection bằng `CollectionModel`, đặt tên relation bằng `@Relation` và xây dựng representation HAL lồng nhau bằng `HalModelBuilder`. Hãy nhúng đúng dữ liệu client cần, giữ relation ổn định, giới hạn kích thước response và kiểm thử cả embedded content lẫn links để bảo vệ hợp đồng hypermedia.
