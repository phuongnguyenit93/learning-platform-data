# HAL pagination

Một API trả về danh sách đơn hàng có thể chỉ gửi một phần dữ liệu trong mỗi response để tránh tải quá nhiều bản ghi. Khi client cần xem trang tiếp theo hoặc quay lại trang trước, response phải cho biết vị trí hiện tại và các URI điều hướng tương ứng. Với Spring HATEOAS, `PagedModel` biểu diễn một trang dữ liệu cùng metadata phân trang; khi serialize thành HAL, metadata nằm ở `page`, các phần tử nằm trong `_embedded` và các link điều hướng nằm ở `_links` cấp cao nhất.

`PagedResourcesAssembler` của Spring Data giúp chuyển `Page<T>` thành `PagedModel`, đồng thời tạo link `first`, `prev`, `self`, `next` và `last` theo request hiện tại. Client có thể theo các link này thay vì tự ghép query parameter hoặc tính số trang tiếp theo. Đây là cách kết hợp phân trang dữ liệu với hypermedia navigation trong REST API.

## HAL pagination là gì?

Pagination chia một collection lớn thành nhiều phần nhỏ. Mỗi response đại diện cho một trang và cần trả lời ba câu hỏi:

1. Trang hiện tại chứa những phần tử nào?
2. Trang hiện tại nằm ở vị trí nào trong toàn bộ kết quả?
3. Client có thể điều hướng đến trang nào tiếp theo hoặc trước đó?

HAL biểu diễn nội dung trang và điều hướng bằng các thành phần sau:

| Thành phần | Vai trò |
| --- | --- |
| `_embedded` | Chứa các item trong trang hiện tại, thường dưới một embedded relation như `orders`. |
| `_links` | Chứa link của collection/page như `self`, `first`, `prev`, `next`, `last`. |
| `page` | Chứa metadata như kích thước trang, tổng số phần tử, tổng số trang và số trang hiện tại. |

Ví dụ response minh họa:

```json
{
  "_embedded": {
    "orders": [
      {
        "id": "ord-1042",
        "status": "PENDING",
        "_links": {
          "self": {
            "href": "https://api.example.com/api/orders/ord-1042"
          }
        }
      }
    ]
  },
  "_links": {
    "first": {
      "href": "https://api.example.com/api/orders?page=0&size=20"
    },
    "self": {
      "href": "https://api.example.com/api/orders?page=1&size=20"
    },
    "prev": {
      "href": "https://api.example.com/api/orders?page=0&size=20"
    },
    "next": {
      "href": "https://api.example.com/api/orders?page=2&size=20"
    },
    "last": {
      "href": "https://api.example.com/api/orders?page=4&size=20"
    }
  },
  "page": {
    "size": 20,
    "totalElements": 87,
    "totalPages": 5,
    "number": 1
  }
}
```

Đây là ví dụ cấu trúc, không phải response cố định cho mọi trang. Ở trang đầu có thể không có `prev`; ở trang cuối có thể không có `next`. Khi collection rỗng, metadata và tập link có thể khác tùy page và cấu hình. Client nên kiểm tra link có tồn tại trước khi theo.

## Các relation phân trang

Các relation thường được dùng trong HAL pagination:

| Relation | Ý nghĩa | Khi xuất hiện |
| --- | --- | --- |
| `self` | Trang hiện tại | Đại diện cho đúng tập kết quả và vị trí đang xem. |
| `first` | Trang đầu tiên | Điều hướng về trang đầu của collection. |
| `prev` | Trang ngay trước | Có trang trước trang hiện tại. |
| `next` | Trang ngay sau | Có trang sau trang hiện tại. |
| `last` | Trang cuối cùng | Điều hướng đến trang cuối của tập kết quả. |

Đây là link ở cấp page/collection, không phải link của từng item trong `_embedded`. Một item vẫn có thể có link `self`, `customer` hoặc các relation nghiệp vụ riêng.

Không giả định mọi relation luôn có mặt. Ví dụ, response trang đầu thường không có `prev`, còn response trang cuối không có `next`. Client nên khám phá quan hệ bằng `_links` thay vì suy luận chỉ từ `page.number`.

## Metadata trong page

`PagedModel` có thể chứa metadata trang được biểu diễn trong HAL dưới object `page`:

| Trường | Ý nghĩa |
| --- | --- |
| `size` | Kích thước trang được yêu cầu hoặc áp dụng. |
| `totalElements` | Tổng số phần tử khớp truy vấn. |
| `totalPages` | Tổng số trang theo kích thước trang hiện tại. |
| `number` | Chỉ số trang hiện tại, thường bắt đầu từ `0` trong Spring Data. |

Ví dụ `number: 0` là trang đầu khi dùng `Pageable` mặc định của Spring Data. Nếu API cấu hình page parameter hoặc page numbering khác, hãy công bố rõ quy ước đó. Metadata cho biết vị trí; link mới là cách điều hướng mà client nên theo.

`totalElements` và `totalPages` thường được lấy từ `Page<T>`. Để tính chúng, repository thường cần thực hiện count query ngoài truy vấn lấy nội dung. Với tập dữ liệu lớn, count query có thể tốn chi phí đáng kể.

## Page, Pageable và PagedModel

Spring Data cung cấp `Page<T>` và `Pageable` để truy vấn dữ liệu theo trang. Spring HATEOAS cung cấp `PagedModel<T>` để biểu diễn trang theo hypermedia.

| Kiểu | Trách nhiệm |
| --- | --- |
| `Pageable` | Mô tả yêu cầu phân trang và sắp xếp, thường lấy từ query parameter `page`, `size`, `sort`. |
| `Page<T>` | Kết quả truy vấn gồm nội dung trang và metadata về tổng số phần tử/trang. |
| `PagedModel<T>` | Representation hypermedia của một trang, chứa item models, page metadata và links. |
| `PagedResourcesAssembler<T>` | Chuyển `Page<T>` thành `PagedModel`, có thể dùng assembler cho từng item. |

Không nên trả `Page<T>` trực tiếp như một DTO tùy tiện nếu hợp đồng API yêu cầu HAL pagination. Hãy chuyển thành `PagedModel` để metadata và link điều hướng được serialize theo định dạng hypermedia.

## Tạo HAL pagination bằng PagedResourcesAssembler

Giả sử `OrderModelAssembler` chuyển `Order` thành `EntityModel<OrderView>`:

```java
import java.math.BigDecimal;
import java.util.UUID;

import org.springframework.hateoas.server.core.Relation;

@Relation(itemRelation = "order", collectionRelation = "orders")
public record OrderView(UUID id, String status, BigDecimal total) {
    static OrderView from(Order order) {
        return new OrderView(order.getId(), order.getStatus().name(), order.getTotal());
    }
}
```

`collectionRelation = "orders"` cố định tên embedded relation được dùng trong ví dụ HAL. Tiếp theo, assembler tạo link cho từng item:

```java
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.linkTo;
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.methodOn;

import org.springframework.hateoas.EntityModel;
import org.springframework.hateoas.server.RepresentationModelAssembler;
import org.springframework.stereotype.Component;

@Component
class OrderModelAssembler
        implements RepresentationModelAssembler<Order, EntityModel<OrderView>> {

    @Override
    public EntityModel<OrderView> toModel(Order order) {
        OrderView view = OrderView.from(order);

        return EntityModel.of(view,
            linkTo(methodOn(OrderController.class).one(order.getId()))
                .withSelfRel());
    }
}
```

Controller nhận `Pageable`, truy vấn `Page<Order>` và chuyển nó thành `PagedModel`:

```java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.web.PagedResourcesAssembler;
import org.springframework.data.web.PageableDefault;
import org.springframework.data.domain.Sort;
import org.springframework.hateoas.PagedModel;
import org.springframework.hateoas.EntityModel;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/orders")
class OrderController {

    private final OrderService orders;
    private final OrderModelAssembler orderAssembler;

    OrderController(OrderService orders, OrderModelAssembler orderAssembler) {
        this.orders = orders;
        this.orderAssembler = orderAssembler;
    }

    @GetMapping
    PagedModel<EntityModel<OrderView>> all(
            @PageableDefault(size = 20, sort = "createdAt",
                direction = Sort.Direction.DESC) Pageable pageable,
            PagedResourcesAssembler<Order> pagedAssembler) {

        Page<Order> page = orders.findAll(pageable);
        return pagedAssembler.toModel(page, orderAssembler);
    }
}
```

Ví dụ giả định `OrderService.findAll(Pageable)` trả về `Page<Order>` và `OrderModelAssembler` có kiểu `RepresentationModelAssembler<Order, EntityModel<OrderView>>`. `PagedResourcesAssembler` được Spring Data Web cung cấp làm method argument khi hạ tầng Spring Data web được cấu hình. Trong Spring Boot, cấu hình này thường được auto-configure khi có dependency phù hợp.

`toModel(page, orderAssembler)` thực hiện hai việc: chuyển từng `Order` thành `EntityModel<OrderView>` qua assembler và tạo metadata cùng các link phân trang cho `PagedModel`. Controller không cần tự viết vòng lặp tạo `first`, `prev`, `next` hoặc `last`.

Nếu không cần link riêng cho từng item, có thể dùng overload `toModel(page)` để bọc nội dung trang bằng entity model mặc định. Khi cần DTO và link item cụ thể, truyền `RepresentationModelAssembler` như ví dụ.

## Query parameter page, size và sort

Spring Data Web thường nhận phân trang qua query parameter:

```http
GET /api/orders?page=1&size=20&sort=createdAt,desc
Accept: application/hal+json
```

Ý nghĩa thông thường:

- `page=1`: trang thứ hai nếu page index bắt đầu từ `0`.
- `size=20`: tối đa 20 item trong trang.
- `sort=createdAt,desc`: sắp xếp theo `createdAt` giảm dần.

Có thể thay đổi mặc định bằng `@PageableDefault` hoặc cấu hình `PageableHandlerMethodArgumentResolver`. API cần giới hạn kích thước trang tối đa để tránh client yêu cầu hàng trăm nghìn item trong một response.

Khi sort theo một cột có giá trị trùng nhau, nên bổ sung tie-breaker ổn định như ID. Ví dụ sắp xếp theo `createdAt DESC, id DESC` giúp thứ tự giữa các trang ít thay đổi hơn khi nhiều bản ghi có cùng timestamp. Tên field sort phải được kiểm soát và ánh xạ đến thuộc tính được phép truy vấn; không nên để client yêu cầu tùy ý field nội bộ hoặc field nhạy cảm.

## Giữ filter và sort trong các page link

Một collection có thể được lọc theo trạng thái hoặc khách hàng:

```http
GET /api/orders?status=PENDING&page=1&size=20&sort=createdAt,desc
```

Các link `self`, `next`, `prev`, `first`, `last` cần giữ ngữ cảnh truy vấn như `status`, `sort` và những filter khác. Nếu link `next` bỏ `status=PENDING`, client có thể chuyển sang trang của toàn bộ đơn hàng thay vì trang tiếp theo của tập kết quả đang lọc.

`PagedResourcesAssembler` xây dựng page links từ request hiện tại và cấu hình pageable resolver. Hãy kiểm thử rằng query parameter ngoài phân trang được giữ lại theo đúng hợp đồng. Với custom resolver, alias parameter hoặc URI prefix riêng, cần xác nhận link được tạo phù hợp với cấu hình thực tế.

Không tự tạo link bằng cách nối chuỗi `"?page=" + (page + 1)`. Cách đó dễ làm mất filter, sort, context path hoặc encoding. Hãy để assembler tạo link, rồi kiểm thử URI cuối cùng.

## Client nên theo link thay vì tự tính trang

Một client HAL có thể đọc `next.href` và gửi request đến URI đó. Client không cần biết server dùng page index bắt đầu từ `0` hay `1`, tên query parameter là `page` hay một alias khác, hoặc server có thay đổi cấu trúc URI trong tương lai.

Ví dụ logic điều hướng ở mức khái niệm:

```text
Đọc response hiện tại
        |
        v
Tìm _links.next
        |
   Có next link?
     /       \
   Có         Không
   |            |
Theo href     Dừng ở trang cuối
   |
   v
Đọc response trang kế tiếp
```

Không nên viết client phụ thuộc vào việc tăng `page` thủ công nếu API đã cung cấp hypermedia links. Theo link giúp client thích nghi khi server đổi quy tắc phân trang hoặc URI.

## CollectionModel khác PagedModel thế nào?

`CollectionModel<T>` biểu diễn một collection nhưng không có metadata phân trang chuyên biệt. `PagedModel<T>` biểu diễn một trang của collection và bổ sung `PageMetadata`.

| Tiêu chí | `CollectionModel<T>` | `PagedModel<T>` |
| --- | --- | --- |
| Nội dung | Một tập hợp item | Item của trang hiện tại |
| Metadata trang | Không có `size`, `totalElements`, `totalPages`, `number` mặc định | Có `PageMetadata` |
| Link | Có thể thêm `self`, `search` hoặc link collection | Có thể thêm `first`, `prev`, `self`, `next`, `last` |
| Use case | Collection nhỏ hoặc không phân trang | Collection lớn được chia trang |
| Nguồn dữ liệu phổ biến | `Iterable<T>` hoặc danh sách đã giới hạn | `Page<T>` |

Không nên dùng `CollectionModel` chỉ vì service trả `Page.getContent()` nếu client cần metadata và điều hướng trang. Làm vậy sẽ làm mất thông tin tổng số trang và các link navigation.

## Collection rỗng và trang cuối

Khi truy vấn không có kết quả, `Page<T>` vẫn có thể đại diện cho trang rỗng với metadata tổng số phần tử bằng `0`. Representation HAL cần giữ cấu trúc và link `self` theo hợp đồng, dù `_embedded` có thể không chứa item.

Khi client yêu cầu page index vượt quá trang cuối, Spring Data có thể trả `Page` rỗng với page metadata tương ứng tùy repository và cấu hình. API cần quyết định có chấp nhận trang ngoài phạm vi như một trang rỗng hay trả lỗi. Hãy thống nhất hành vi và kiểm thử vì client không nên phải đoán.

Không mặc định `totalPages == 0` sẽ luôn có `first` hoặc `last` link. Hãy kiểm tra response thực tế của `PagedResourcesAssembler` cho trường hợp không có kết quả và chỉ yêu cầu client theo các relation được công bố.

## Giới hạn của offset pagination

Phân trang dựa trên `page` và `size` thường dùng offset/limit. Cách này dễ hiểu và phù hợp với collection vừa phải, nhưng có một số giới hạn:

- Trang rất sâu có thể yêu cầu database bỏ qua nhiều bản ghi trước khi lấy nội dung.
- `Page<T>` thường cần count query để tính `totalElements` và `totalPages`.
- Khi dữ liệu được thêm hoặc xóa giữa hai request, item có thể dịch chuyển giữa các trang; client có thể thấy trùng hoặc bỏ sót item nếu sort không ổn định.
- Tổng số phần tử có thể thay đổi trong lúc client đang duyệt collection.

Để giảm vấn đề, dùng sort ổn định, giới hạn page size, tối ưu index và query. Với collection rất lớn hoặc dữ liệu thay đổi liên tục, cân nhắc `Slice<T>` hoặc cursor/keyset pagination.

## Slice và cursor pagination

`Slice<T>` cho biết có trang tiếp theo hay không nhưng không nhất thiết tính tổng số phần tử và tổng số trang. Vì vậy nó phù hợp khi chỉ cần điều hướng `next`/`prev`, không cần `totalElements` hoặc `totalPages`.

Cursor pagination dùng một cursor opaque do server tạo, thường dựa trên khóa sắp xếp ổn định. Response có thể công bố link `next` chứa cursor:

```json
{
  "_embedded": {
    "orders": [
      { "id": "ord-1042", "status": "PENDING" }
    ]
  },
  "_links": {
    "self": {
      "href": "/api/orders?after=cursor-current"
    },
    "next": {
      "href": "/api/orders?after=cursor-next"
    }
  }
}
```

JSON trên chỉ minh họa link cursor; trong response thật, self và next thường có cursor khác nhau tương ứng vị trí hiện tại và vị trí tiếp theo. Cursor nên được xem là opaque: client không giải mã, chỉnh sửa hoặc tự tạo nó.

`PagedResourcesAssembler` hướng đến `Page<T>` và page metadata. Với `Slice` hoặc cursor pagination, ứng dụng thường tự xây `CollectionModel`/custom model và các link `self`/`next` theo cursor. Không nên giả lập `totalPages` nếu server không biết tổng số trang.

## HAL media type và cấu hình

Client thường yêu cầu HAL bằng:

```http
Accept: application/hal+json
```

Response cần có media type phù hợp và cấu trúc `_links`, `_embedded`, `page`. Trong Spring Boot, starter HATEOAS thường cấu hình converter và hypermedia support tự động. Với cấu hình MVC thủ công, bật hỗ trợ HAL theo cấu hình Spring HATEOAS của phiên bản đang sử dụng.

Nếu API có nhiều representation format, kiểm thử riêng từng `Accept` header. Không giả định JSON thông thường sẽ có cùng cấu trúc pagination với HAL.

## Kiểm thử HAL pagination bằng MockMvc

Kiểm thử nên xác nhận metadata, link cấp trang và embedded item. Ví dụ:

```java
mockMvc.perform(get("/api/orders?page=1&size=20")
        .accept(MediaType.parseMediaType("application/hal+json")))
    .andExpect(status().isOk())
    .andExpect(content().contentTypeCompatibleWith(
        MediaType.parseMediaType("application/hal+json")))
    .andExpect(jsonPath("$.page.size").value(20))
    .andExpect(jsonPath("$.page.number").value(1))
    .andExpect(jsonPath("$.page.totalElements").exists())
    .andExpect(jsonPath("$.page.totalPages").exists())
    .andExpect(jsonPath("$._links.self.href").exists())
    .andExpect(jsonPath("$._links.next.href").exists())
    .andExpect(jsonPath("$._embedded.orders").isArray());
```

Test này giả định có ít nhất ba trang dữ liệu và embedded relation được cấu hình là `orders`. Với trang đầu, kiểm tra `first` và không giả định `prev` có mặt. Với trang cuối, kiểm tra `last` và không giả định `next` có mặt.

Nên kiểm tra thêm filter và sort được giữ trong link:

```java
mockMvc.perform(get(
        "/api/orders?status=PENDING&page=1&size=20&sort=createdAt,desc")
        .accept(MediaType.parseMediaType("application/hal+json")))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$._links.next.href")
        .value(org.hamcrest.Matchers.containsString("status=PENDING")))
    .andExpect(jsonPath("$._links.next.href")
        .value(org.hamcrest.Matchers.containsString("sort=createdAt")));
```

Ngoài ra, nên có test cho collection rỗng, trang ngoài phạm vi, page size tối đa, sort không hợp lệ, quyền truy cập và URI công khai khi chạy sau reverse proxy. Nếu dùng cursor pagination, kiểm tra cursor trong `next.href` được tạo và xác thực đúng.

## Những lỗi thường gặp

| Lỗi | Hệ quả | Cách xử lý |
| --- | --- | --- |
| Trả `Page<T>` mà không chuyển thành `PagedModel` | Client không nhận được HAL pagination links theo hợp đồng. | Dùng `PagedResourcesAssembler` để tạo `PagedModel`. |
| Dùng `CollectionModel` rồi bỏ page metadata | Client không biết số trang và tổng số phần tử. | Dùng `PagedModel` khi API cần phân trang kiểu Page. |
| Tự ghép `page + 1` để tạo next URL | Dễ làm mất filter, sort, encoding hoặc URI prefix. | Dùng link do assembler tạo và yêu cầu client theo `next.href`. |
| Đặt link `next` trong từng item | Sai phạm vi của relation điều hướng trang. | Đặt link phân trang ở top-level `_links`. |
| Không giới hạn page size | Client có thể yêu cầu payload rất lớn. | Cấu hình kích thước tối đa và kiểm tra đầu vào. |
| Sort không ổn định | Item có thể trùng hoặc bị bỏ sót giữa các trang. | Thêm tie-breaker ổn định như ID. |
| Bỏ filter khỏi page links | Client chuyển sang tập kết quả khác khi điều hướng. | Kiểm thử link giữ nguyên query context. |
| Dùng `Page` cho dữ liệu lớn mà không xem xét count query | Độ trễ tăng do truy vấn đếm tổng. | Cân nhắc `Slice` hoặc cursor pagination nếu không cần tổng số. |
| Giả định luôn có `prev` và `next` | Client xử lý lỗi ở trang đầu hoặc cuối. | Kiểm tra relation có tồn tại trước khi theo. |

## Ghi nhớ

- HAL pagination đặt item trong `_embedded`, page links trong top-level `_links` và metadata trong `page`.
- `PagedModel<T>` biểu diễn một trang cùng `PageMetadata`; `CollectionModel<T>` không có metadata phân trang chuyên biệt.
- Dùng `PagedResourcesAssembler` để chuyển `Page<T>` thành `PagedModel`, có thể truyền `RepresentationModelAssembler` cho item links.
- Các relation thường gặp là `first`, `prev`, `self`, `next`, `last`; relation có thể vắng ở biên trang.
- `page.number` thường zero-based trong Spring Data; client nên theo link thay vì tự tính số trang.
- Giữ filter, sort và query context trong page links; giới hạn page size và dùng sort ổn định.
- `Page` thường cần count query; cân nhắc `Slice` hoặc cursor khi collection lớn hoặc thay đổi liên tục.
- Kiểm thử metadata, link điều hướng, embedded relation, trang đầu/cuối, collection rỗng và query parameters bằng MockMvc.
