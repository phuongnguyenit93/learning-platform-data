# Giới hạn của HAL

HAL (Hypertext Application Language) là một định dạng JSON để biểu diễn tài nguyên và các liên kết hypermedia. HAL giúp client khám phá tài nguyên qua `_links` và đọc dữ liệu liên quan qua `_embedded`. Tuy nhiên, HAL cố ý giữ phạm vi nhỏ: nó mô tả cách điều hướng giữa các tài nguyên, chứ không định nghĩa đầy đủ ngữ nghĩa nghiệp vụ, biểu mẫu thao tác, schema request hay quy tắc bảo mật của API.

Khi thiết kế REST API bằng Spring HATEOAS, cần hiểu rõ phần nào thuộc hợp đồng HAL và phần nào cần một cơ chế bổ sung. Chọn đúng media type và profile giúp client hiểu cách điều hướng, thực hiện hành động, xử lý lỗi và tiến hóa cùng API mà không gán cho HAL những khả năng định dạng này không cung cấp.

## Mục tiêu

Sau bài học, bạn có thể:

- Mô tả phạm vi mà HAL chuẩn hóa: `_links`, `_embedded` và cấu trúc link.
- Nhận diện những thông tin HAL không mô tả trực tiếp như HTTP method, request schema và quy tắc nghiệp vụ.
- Phân biệt URI template với mô tả đầy đủ của một thao tác.
- Giải thích giới hạn của relation, embedded resource và metadata phân trang.
- Chọn HAL-FORMS, profile, Problem Details hoặc tài liệu schema để bổ sung hợp đồng.
- Thiết kế API Spring HATEOAS có kiểm thử cho các phần mở rộng và quy tắc tương thích.

## HAL chuẩn hóa những gì?

Một representation HAL JSON thường có ba phần:

- **Content:** các thuộc tính dữ liệu của tài nguyên, chẳng hạn `id`, `status` và `total`.
- **`_links`:** các liên kết để client điều hướng tới tài nguyên khác hoặc chính tài nguyên hiện tại.
- **`_embedded`:** representation của những tài nguyên liên quan được nhúng trong response.

Ví dụ:

```json
{
  "id": 42,
  "status": "NEW",
  "total": 1250000,
  "_links": {
    "self": {
      "href": "https://api.example.test/orders/42"
    },
    "customer": {
      "href": "https://api.example.test/customers/7"
    }
  },
  "_embedded": {
    "customer": {
      "id": 7,
      "name": "Nguyen An"
    }
  }
}
```

HAL định nghĩa vị trí để đặt liên kết và tài nguyên nhúng. Nó không áp đặt cấu trúc các thuộc tính nghiệp vụ như `status`, `total` hay `name`; những thuộc tính đó do API thiết kế. Tương tự, relation `customer` xác định tên quan hệ, nhưng ý nghĩa chi tiết của quan hệ vẫn cần được quy ước hoặc mô tả trong profile/tài liệu API.

## Giới hạn 1: link không mô tả đầy đủ thao tác HTTP

Một link HAL chứa `href` và relation cùng một số metadata tùy chọn như `title`, `type`, `hreflang`, `name`, `profile`, `deprecation` hoặc `templated`. Link object không có trường chuẩn để mô tả HTTP method, request body, schema đầu vào hay kết quả dự kiến của thao tác.

Ví dụ:

```json
{
  "_links": {
    "self": {
      "href": "https://api.example.test/orders/42"
    },
    "cancel": {
      "href": "https://api.example.test/orders/42/cancellation"
    }
  }
}
```

Client biết URI của tài nguyên và URI có relation `cancel`. Chỉ từ HAL này, client không biết endpoint `cancel` nhận `POST` hay `DELETE`, có cần body hay không, và body có trường nào. `type` trong link mô tả media type của tài nguyên đích nếu được cung cấp; nó không phải schema của request.

Spring HATEOAS cho phép tạo affordance trên `Link`, nhưng affordance là metadata trong model của framework. Định dạng được thương lượng mới quyết định metadata ấy được serialize ra sao. HAL JSON thuần không có cấu trúc form chuẩn để biểu diễn toàn bộ affordance.

### Cách bổ sung: HAL-FORMS và affordance

Nếu client cần khám phá HTTP method và các trường cần gửi, có thể dùng affordance cùng HAL-FORMS. HAL-FORMS là một media type riêng dựa trên cách biểu diễn của HAL, bổ sung `_templates` để mô tả thao tác và property đầu vào; hai media type có hình thức gần nhau nhưng không thể xem là thay thế trực tiếp cho nhau.

Controller có thể gắn affordance vào link:

```java
Link self = linkTo(methodOn(OrderController.class).one(id))
    .withSelfRel()
    .andAffordance(afford(methodOn(OrderController.class)
        .cancel(id)));

return EntityModel.of(orderView, self);
```

Client yêu cầu media type HAL-FORMS:

```http
GET /orders/42 HTTP/1.1
Accept: application/prs.hal-forms+json
```

Representation minh họa:

```json
{
  "id": 42,
  "status": "NEW",
  "_links": {
    "self": {
      "href": "https://api.example.test/orders/42"
    }
  },
  "_templates": {
    "cancel": {
      "method": "post",
      "target": "https://api.example.test/orders/42/cancellation"
    }
  }
}
```

HAL-FORMS phù hợp khi client cần mô tả form và thao tác. Nếu client chỉ cần điều hướng tới tài nguyên, HAL JSON đơn giản hơn. Dù dùng HAL-FORMS, server vẫn phải xác thực request, kiểm tra quyền và validate dữ liệu ở thời điểm thực thi.

## Giới hạn 2: URI template không phải schema truy vấn

HAL hỗ trợ link templated với thuộc tính `templated: true`. URI template cho biết tên biến và vị trí chúng được mở rộng, ví dụ:

```json
{
  "_links": {
    "search": {
      "href": "/orders{?status,page,size}",
      "templated": true
    }
  }
}
```

Client có thể mở rộng template thành `/orders?status=NEW&page=0&size=20`. Tuy nhiên, template không mô tả đầy đủ:

- `status` chấp nhận những giá trị nào.
- `page` bắt đầu từ 0 hay 1.
- `size` tối đa là bao nhiêu.
- Có thể lặp tham số `sort` hay không.
- Tham số nào bắt buộc, tham số nào có giá trị mặc định.
- Hai bộ lọc kết hợp với nhau theo logic nào.

RFC 6570 quy định cách mở rộng URI template, không quy định ngữ nghĩa nghiệp vụ của từng biến. Vì vậy, link template giúp client tạo URI đúng cấu trúc nhưng không thay thế tài liệu hoặc metadata mô tả tham số.

Trong Spring HATEOAS, có thể tạo link template:

```java
Link search = Link.of(
    "/orders{?status,page,size}",
    "search"
);
```

Nếu cần mô tả tham số truy vấn như một phần của thao tác, affordance và HAL-FORMS có thể cung cấp metadata query parameter. Tài liệu API hoặc profile vẫn cần giải thích tập giá trị hợp lệ, mặc định và quy tắc kết hợp bộ lọc.

## Giới hạn 3: relation đặt tên quan hệ nhưng không tự định nghĩa ngữ nghĩa

Trong HAL, key trong `_links` và `_embedded` chính là relation. `self`, `next`, `customer` hoặc `cancel` giúp client nhận diện loại quan hệ. Tuy nhiên, HAL không tự định nghĩa ý nghĩa nghiệp vụ của relation tùy chỉnh.

Ví dụ, hai API có thể cùng sử dụng relation `status` nhưng một API dùng nó để chỉ trạng thái vận chuyển, API khác dùng để chỉ trạng thái thanh toán. Cùng một tên không bảo đảm cùng ngữ nghĩa.

Với relation chuẩn, nên dùng tên đã được IANA đăng ký khi ngữ nghĩa phù hợp. Với relation riêng, nên dùng URI tuyệt đối để định danh và công bố tài liệu mô tả. CURIE có thể rút gọn URI relation trong HAL, nhưng client vẫn cần biết cách mở rộng prefix.

Ví dụ relation tùy chỉnh trong Spring HATEOAS:

```java
Link cancel = linkTo(methodOn(OrderController.class).cancel(id))
    .withRel("https://api.example.test/rels/order/cancel");
```

Không nên đổi relation đã công bố mà không đánh giá client đang sử dụng nó. Đổi `href` trong khi giữ relation có thể tương thích với client đi theo link; đổi relation có thể khiến client không còn tìm thấy quan hệ đó.

## Giới hạn 4: `_embedded` không định nghĩa freshness hoặc đồng bộ dữ liệu

`_embedded` giúp gửi representation của tài nguyên liên quan trong cùng response. Nhưng HAL không nói rằng dữ liệu nhúng luôn mới nhất, không định nghĩa cơ chế đồng bộ giữa tài nguyên cha và con, và cũng không đảm bảo embedded resource tương đương một lần đọc độc lập tới URI canonical.

Ví dụ, đơn hàng nhúng bản xem trước khách hàng:

```json
{
  "id": 42,
  "_links": {
    "self": { "href": "/orders/42" },
    "customer": { "href": "/customers/7" }
  },
  "_embedded": {
    "customer": {
      "id": 7,
      "name": "Nguyen An"
    }
  }
}
```

Tên khách hàng trong embedded resource là dữ liệu được chụp tại thời điểm response được tạo. Nếu tên thay đổi sau đó, client có thể vẫn giữ snapshot cũ. Khi cần dữ liệu mới nhất, client nên theo link `customer` tới tài nguyên canonical hoặc làm mới representation cha.

Chính sách cache cũng cần tính đến dữ liệu nhúng. Một response đơn hàng có thể thay đổi khi dữ liệu khách hàng hoặc dòng hàng thay đổi. Dùng `ETag`, `Last-Modified`, `Cache-Control` và chiến lược invalidation phù hợp để tránh client giữ snapshot quá lâu.

Nhúng một collection lớn cũng làm response tăng kích thước và chi phí serialize. Với danh sách dài, nên nhúng một preview nhỏ hoặc chỉ cung cấp link tới collection phân trang.

## Giới hạn 5: HAL không chuẩn hóa metadata phân trang

HAL có thể chứa link `first`, `prev`, `self`, `next` và `last`, nhưng HAL không quy định một cấu trúc metadata phân trang chuẩn như số trang hiện tại, tổng số trang hoặc tổng số phần tử. Các relation điều hướng giúp client đi tới trang khác; chúng không tự cung cấp mọi con số cần cho giao diện phân trang.

Spring HATEOAS bổ sung metadata `page` khi serialize `PagedModel`, ví dụ:

```json
{
  "_links": {
    "self": { "href": "/orders?page=0&size=20" },
    "next": { "href": "/orders?page=1&size=20" },
    "last": { "href": "/orders?page=2&size=20" }
  },
  "page": {
    "size": 20,
    "totalElements": 53,
    "totalPages": 3,
    "number": 0
  }
}
```

`page` trong ví dụ là metadata do Spring HATEOAS cung cấp cho `PagedModel`, không phải thuộc tính phân trang được HAL core quy định. Client phụ thuộc vào metadata này cần biết API đang dùng quy ước của Spring HATEOAS hoặc profile tương ứng. Một API dùng cursor pagination có thể chọn metadata khác, chẳng hạn cursor tiếp theo và trạng thái còn dữ liệu.

## Giới hạn 6: HAL không phải định dạng lỗi chuẩn

HAL mô tả resource và liên kết, nhưng không định nghĩa một schema lỗi ứng dụng thống nhất. API có thể trả lỗi JSON tùy biến, nhưng client sẽ phải biết schema riêng của từng dịch vụ.

Để biểu diễn lỗi HTTP theo một cấu trúc chung, có thể dùng Problem Details theo RFC 9457 với media type `application/problem+json`:

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
```

```json
{
  "type": "https://api.example.test/problems/order-state-conflict",
  "title": "Order cannot be cancelled",
  "status": 409,
  "detail": "The order has already been shipped.",
  "instance": "/orders/42/cancellation"
}
```

Client có thể xử lý các trường chuẩn như `type`, `title`, `status`, `detail` và `instance`. Ứng dụng có thể thêm extension members cho thông tin lỗi cụ thể, nhưng nên giữ chúng ổn định và không đưa dữ liệu nhạy cảm vào response.

Spring Framework hỗ trợ Problem Details cho Spring MVC và WebFlux. Có thể dùng `ProblemDetail` hoặc `ErrorResponse` để xây dựng response lỗi, đồng thời giữ HAL cho representation tài nguyên thành công. Media type được chọn theo loại response; không cần ép mọi lỗi vào cấu trúc HAL.

## Giới hạn 7: link và affordance không thay thế bảo mật

Việc một link hoặc affordance xuất hiện trong response chỉ cho biết server đang công bố khả năng đó trong ngữ cảnh hiện tại. Nó không phải quyền truy cập được cấp vĩnh viễn. Client có thể lưu URI, tự tạo request hoặc gửi request sau khi trạng thái tài nguyên đã thay đổi.

Ví dụ, server chỉ thêm link `cancel` khi đơn hàng còn ở trạng thái `NEW`. Khi client gửi request hủy, server vẫn cần:

- Xác thực danh tính người gọi.
- Kiểm tra quyền trên đúng đơn hàng.
- Kiểm tra trạng thái hiện tại và điều kiện chuyển trạng thái.
- Kiểm tra dữ liệu request nếu thao tác có body.
- Trả mã lỗi phù hợp nếu thao tác không còn hợp lệ.

Ẩn link có thể giúp giao diện phản ánh hành động hiện có, nhưng không thay thế authorization ở endpoint. Tương tự, affordance mô tả HTTP method và input không đảm bảo server sẽ chấp nhận request tại thời điểm client gửi.

## Giới hạn 8: HAL không phải schema hay từ điển dữ liệu nghiệp vụ

Các thuộc tính content trong HAL là JSON do ứng dụng định nghĩa. HAL không định nghĩa kiểu dữ liệu nghiệp vụ, đơn vị đo, miền giá trị, quy tắc nullability hoặc quan hệ giữa các trường. Ví dụ, trường `total: 1250000` không cho biết đó là VND hay một đơn vị tiền khác nếu API không mô tả thêm.

Có thể bổ sung mô tả bằng profile link, tài liệu API, JSON Schema hoặc OpenAPI. Profile cung cấp một định danh cho tập quy tắc/ý nghĩa bổ sung của representation; nó không tự động khiến mọi client hiểu schema nếu client không đọc tài liệu profile đó.

Ví dụ thêm profile link:

```java
Link profile = Link.of(
    "https://api.example.test/profiles/order",
    "profile"
);
```

Tài liệu profile nên mô tả các trường, đơn vị, enum, quy tắc tương thích và ngữ nghĩa relation. Nếu client cần validate payload hoặc sinh SDK, OpenAPI/JSON Schema có thể bổ sung cấu trúc dữ liệu chi tiết. HAL tiếp tục đảm nhiệm vai trò điều hướng tài nguyên.

## Bảng chọn cơ chế bổ sung

| Nhu cầu | HAL cung cấp | Cơ chế bổ sung phù hợp |
|---|---|---|
| Điều hướng tới resource | `_links` và relation | Không cần nếu link đủ |
| Nhúng dữ liệu liên quan | `_embedded` | DTO preview và chính sách cache |
| Mở rộng URI tìm kiếm | Templated link | Tài liệu query hoặc HAL-FORMS cho tham số thao tác |
| Mô tả HTTP method và form input | Không có cấu trúc chuẩn trong HAL JSON | Affordance và HAL-FORMS |
| Định nghĩa ngữ nghĩa field/relation | Tên thuộc tính và relation | Profile, tài liệu API, từ điển nghiệp vụ |
| Mô tả schema và sinh client | Không có schema chuẩn | OpenAPI hoặc JSON Schema |
| Metadata phân trang | Link điều hướng có thể dùng | `PagedModel` của Spring HATEOAS hoặc profile phân trang |
| Cấu trúc lỗi thống nhất | Không định nghĩa schema lỗi | Problem Details (RFC 9457) |
| Bảo mật thao tác | Không cấp quyền | Authentication, authorization và kiểm tra nghiệp vụ tại server |
| Cập nhật dữ liệu liên tục | Không có push/event protocol | SSE, WebSocket hoặc cơ chế event riêng |

## Thiết kế response trong Spring HATEOAS

Một controller có thể dùng HAL cho điều hướng và nhúng preview, trong khi cung cấp affordance khi client thương lượng HAL-FORMS:

```java
import org.springframework.hateoas.EntityModel;
import org.springframework.hateoas.Link;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.afford;
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.linkTo;
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.methodOn;

record OrderView(long id, String status, long total) {
}

interface OrderService {
    OrderView findById(long id);
    void cancel(long id);
}

@RestController
@RequestMapping("/orders")
class OrderController {

    private final OrderService orders;

    OrderController(OrderService orders) {
        this.orders = orders;
    }

    @PostMapping("/{id}/cancellation")
    ResponseEntity<Void> cancel(@PathVariable long id) {
        orders.cancel(id);
        return ResponseEntity.noContent().build();
    }

    @GetMapping("/{id}")
    EntityModel<OrderView> one(@PathVariable long id) {
        OrderView order = orders.findById(id);

        Link self = linkTo(methodOn(OrderController.class).one(id))
            .withSelfRel()
            .andAffordance(afford(methodOn(OrderController.class)
                .cancel(id)));

        return EntityModel.of(order, self);
    }
}
```

Trong ví dụ này, `OrderView` là DTO được trả về bởi `OrderService.findById`, còn `OrderService.cancel` thực hiện nghiệp vụ hủy. Phương thức `cancel` được khai báo trong cùng controller để `methodOn()` có thể đọc mapping của nó.

Khi client yêu cầu `application/hal+json`, response cung cấp link và content theo HAL. Khi client yêu cầu `application/prs.hal-forms+json`, Spring HATEOAS có thể serialize affordance thành `_templates`. Nếu API cần mô tả schema chi tiết cho các consumer khác, công bố thêm profile hoặc tài liệu OpenAPI/JSON Schema.

Không nên thêm tất cả cơ chế vào mọi response. Hãy chọn phần bổ sung theo khả năng client cần và giữ media type được công bố rõ ràng trong hợp đồng API.

## Kiểm thử giới hạn và phần mở rộng của hợp đồng

Kiểm thử không chỉ xác nhận JSON có parse được. Nên kiểm tra media type, relation, URI, metadata bổ sung và hành vi khi client yêu cầu một định dạng khác.

Ví dụ kiểm thử HAL JSON:

```java
import static org.mockito.BDDMockito.given;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.hateoas.MediaTypes;
import org.springframework.test.web.servlet.MockMvc;

@WebMvcTest(OrderController.class)
class OrderHalContractTest {

    @Autowired
    MockMvc mockMvc;

    @MockBean
    OrderService orders;

    @Test
    void exposesNavigationLinksInHalJson() throws Exception {
        given(orders.findById(42L))
            .willReturn(new OrderView(42L, "NEW", 1_250_000L));

        mockMvc.perform(get("/orders/{id}", 42).accept(MediaTypes.HAL_JSON))
            .andExpect(status().isOk())
            .andExpect(content().contentTypeCompatibleWith(MediaTypes.HAL_JSON))
            .andExpect(jsonPath("$.id").value(42))
            .andExpect(jsonPath("$._links.self.href").exists());
    }
}
```

Đây là khung kiểm thử; `OrderView`, `OrderService` và controller phải khớp với ứng dụng thực tế. Có thể bổ sung test riêng cho HAL-FORMS để xác nhận `_templates`, test Problem Details để xác nhận `application/problem+json`, và test profile link để giữ ổn định URI tài liệu. Không nên kiểm tra host/port cố định nếu môi trường test tạo URI theo request động; khi đó hãy kiểm tra relation và phần path cần thiết.

Các kiểm thử hợp đồng nên bao gồm:

- Client cũ vẫn tìm thấy relation đã công bố sau khi mapping URI thay đổi.
- URI template giữ đúng tên biến và encoding.
- Embedded relation giữ nguyên tên và cấu trúc object/array.
- `PagedModel` giữ metadata và navigation links theo quy ước đã chọn.
- HAL-FORMS chỉ công bố affordance phù hợp trạng thái và quyền hiện tại.
- Error response dùng Problem Details với status và `type` ổn định.
- Thay đổi schema content có tài liệu và kiểm tra tương thích.

## Lỗi thường gặp

| Lỗi | Hệ quả | Cách xử lý |
|---|---|---|
| Kỳ vọng HAL mô tả HTTP method và request body | Client không biết cách thực hiện thao tác | Dùng affordance và HAL-FORMS |
| Coi URI template là schema truy vấn | Client không biết miền giá trị và giới hạn tham số | Tài liệu hóa query hoặc dùng metadata thao tác bổ sung |
| Dùng relation tùy chỉnh mà không định nghĩa | Client không biết ý nghĩa quan hệ | Dùng relation chuẩn hoặc URI relation có tài liệu |
| Cho rằng `_embedded` luôn mới nhất | Client hiển thị snapshot cũ | Cung cấp link canonical và cache policy phù hợp |
| Coi `page` là một phần bắt buộc của HAL | Client phụ thuộc ngầm vào một extension | Tài liệu hóa quy ước `PagedModel` hoặc profile phân trang |
| Trả lỗi theo nhiều schema tùy endpoint | Client phải viết parser riêng | Dùng Problem Details cho lỗi HTTP |
| Ẩn link để thay thế authorization | Endpoint vẫn có thể bị gọi trực tiếp | Kiểm tra quyền tại server trên mỗi request |
| Đưa toàn bộ schema nghiệp vụ vào suy luận từ JSON | Client phụ thuộc vào chi tiết chưa được mô tả | Công bố profile, OpenAPI hoặc JSON Schema |

## Ghi nhớ

HAL chuẩn hóa cấu trúc `_links` và `_embedded`, đồng thời cho phép payload content do API định nghĩa. Nhờ đó client khám phá tài nguyên và điều hướng theo relation. HAL không mô tả đầy đủ HTTP method, request schema, ngữ nghĩa nghiệp vụ, giới hạn query, freshness của dữ liệu nhúng, metadata phân trang chuẩn, lỗi ứng dụng hay quyền truy cập. Khi cần mô tả thao tác, dùng affordance và HAL-FORMS; khi cần schema hoặc ngữ nghĩa, công bố profile và OpenAPI/JSON Schema; khi cần lỗi có cấu trúc, dùng Problem Details. Giữ relation ổn định, kiểm tra quyền tại server và kiểm thử các phần mở rộng để hợp đồng API có thể tiến hóa an toàn.
