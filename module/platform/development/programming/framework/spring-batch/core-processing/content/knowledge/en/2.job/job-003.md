# JobExecution represents a single run

In Spring Batch, `JobExecution` is a metadata object that describes **one specific execution of a Job**. It records when the run started, when it ended, what state it is in, what the result was, and which `StepExecution`s were created in that run.

The key distinction is that a Job can be run many times, and the same `JobInstance` can also have multiple `JobExecution`s if an earlier run failed or was stopped and then restarted. Therefore, a `JobExecution` represents one execution attempt; it is neither the Job definition nor the long-lived identifier of the business work to be processed.

## 1. Distinguishing Job, JobInstance, and JobExecution

These three concepts are closely related but play different roles:

| Concept | Meaning | Example |
|---|---|---|
| `Job` | The definition of a batch process: the Job name, the Steps, and the execution flow | `importOrdersJob` |
| `JobInstance` | One unit of business processing identified by the Job together with the identifying JobParameters | Importing orders for the date `2026-11-15` from a specific data source |
| `JobExecution` | One specific execution of that JobInstance | The first run failed; the next run restarted and completed |

For example, the application has a Job `importOrdersJob` that imports order data by day. When run with the identifying parameter `businessDate=2026-11-15`, Spring Batch creates a `JobInstance` for the order import work of that date. If the first run fails because an external service is temporarily unresponsive, the restart can use the same identifying parameters. In that case Spring Batch keeps the same `JobInstance` but creates a new `JobExecution` for the next attempt.

```text
Job: importOrdersJob
  |
  +-- JobInstance: businessDate=2026-11-15
        |
        +-- JobExecution #101: FAILED
        |     +-- StepExecution: readAndImportStep
        |
        +-- JobExecution #108: COMPLETED
              +-- StepExecution: readAndImportStep
```

The two `JobExecution`s have different IDs because they are two different executions. They belong to the same `JobInstance` because the Job and the identifying JobParameters did not change.

### JobParameters determine the JobInstance

Spring Batch determines a `JobInstance` based on the Job name and the JobParameters marked as *identifying*. A change to an identifying parameter can create a new JobInstance; a non-identifying parameter does not change the identity of the JobInstance.

For example, `businessDate` can be an identifying parameter of the order import Job. A parameter such as the email address that receives notifications can be marked non-identifying if changing it does not mean processing new business work. Which parameters are identifying depends on the application's business rules.

You should not equate "each call to `JobLauncher.run`" with "each new JobInstance". If the Job and the identifying parameters are the same, the next run can be a new execution of an existing JobInstance.

## 2. The lifecycle of a JobExecution

Typically, a run proceeds in the following sequence:

1. The application calls `JobLauncher.run(job, jobParameters)`.
2. The `JobRepository` checks the corresponding JobInstance and creates the metadata for the `JobExecution`. If this is the first run with this set of identifying parameters, the repository also creates a new JobInstance.
3. When the Job starts executing, Spring Batch updates the start time and the status of the JobExecution.
4. The Job runs the Steps one by one. Each time a Step is executed, Spring Batch creates a `StepExecution` linked to the current JobExecution.
5. During the run, the metadata, status, and execution context are updated by the repository following the lifecycle of the Job and Steps.
6. When the Job ends, the JobExecution receives its end time, its final status, and an ExitStatus describing the result.

The `JobLauncher` is responsible for launching the Job; the `JobRepository` manages the metadata about JobInstance, JobExecution, StepExecution, and ExecutionContext. In a real configuration, the metadata is usually stored in a database so that the application can track the run history and recover an interrupted Job.

### Common statuses

The `status` field of a JobExecution has the type `BatchStatus`. Some important statuses:

| BatchStatus | Meaning |
|---|---|
| `STARTING` | The Job is being initialized in order to start running |
| `STARTED` | The Job is executing |
| `STOPPING` | A request to stop the Job has been made and the Job is handling that request |
| `STOPPED` | The Job stopped on request; a restart can be considered if the configuration allows it |
| `COMPLETED` | The Job completed successfully according to the framework's status |
| `FAILED` | The Job ended because of an error |
| `ABANDONED` | The execution has been marked as not to be restarted |
| `UNKNOWN` | The execution status cannot be determined with certainty |

A running JobExecution usually has an `endTime` that has not been set. When it finishes, Spring Batch updates `endTime` and the corresponding status. `isRunning()` is a utility method to check whether the JobExecution is in a running state.

You should not infer the status from a timestamp alone. For example, a non-null `startTime` indicates the Job has started, but to know whether the Job has completed you need to look at `status` and `endTime`.

## 3. Important data in a JobExecution

`JobExecution` is a metadata object that can be read in a listener, during execution, or through Spring Batch's query API. Commonly used getters include:

| Getter | Information |
|---|---|
| `getId()` | The ID of the execution; each persisted JobExecution has its own ID |
| `getJobInstance()` | The JobInstance this execution belongs to |
| `getJobParameters()` | The parameters provided when the Job was launched |
| `getStatus()` | The current or final BatchStatus |
| `getExitStatus()` | The result code and description of the execution result |
| `getCreateTime()` | The time the JobExecution metadata was created |
| `getStartTime()` | The time the Job started executing |
| `getEndTime()` | The time the Job ended; usually not set while the Job is still running |
| `getLastUpdated()` | The time the metadata was most recently updated |
| `getExecutionContext()` | The ExecutionContext at the JobExecution scope |
| `getStepExecutions()` | The StepExecutions belonging to this execution |
| `getFailureExceptions()` | The exceptions recorded in the current JobExecution object |

The JobExecution ID is useful for looking up history, correlating logs, and pinpointing exactly which run hit an error. When you need to know which JobInstance a run belongs to, access `getJobInstance()` instead of inferring it from the JobExecution ID.

### Distinguishing BatchStatus and ExitStatus

These two fields describe two different aspects of the result:

- `BatchStatus` reflects the lifecycle state managed by Spring Batch, such as `STARTED`, `COMPLETED`, `FAILED`, or `STOPPED`.
- `ExitStatus` is a result in the form of a code and a description. It can contain a standard code such as `COMPLETED`, `FAILED`, `STOPPED`, or a custom code set by the application.

For example, the application may want to distinguish a Job that completed normally from a Job that completed but had records skipped. Both cases can be handled under the `COMPLETED` lifecycle status, while the `ExitStatus` carries a distinct business code such as `COMPLETED_WITH_SKIPS` for the Job flow or the monitoring system to recognize.

Therefore, you should not replace checking `getStatus()` with `getExitStatus()` or vice versa. When deciding whether a Job can be restarted, look at the status and the Job's restart rules. When routing the flow based on the result or displaying detailed results, ExitStatus usually provides more suitable information.

## 4. JobExecution and StepExecution

A JobExecution can contain multiple StepExecutions. Each StepExecution records one execution of a Step within that JobExecution, including the status, timing, the number of items read/written/skipped, and the Step's own ExecutionContext.

For example, an order import Job with three Steps:

```text
JobExecution #108
  |
  +-- StepExecution: validateInputStep
  |
  +-- StepExecution: importOrdersStep
  |
  +-- StepExecution: generateReportStep
```

These StepExecutions belong to the same Job run. If the Job is restarted, Spring Batch creates a new JobExecution. Depending on the execution history and the configuration, Steps that have already completed can be skipped in the restart; the Step's `allowStartIfComplete` property affects whether a completed Step is run again.

During processing, you can go from a StepExecution to its JobExecution with `stepExecution.getJobExecution()`. This relationship lets a Step access the JobParameters, the Job-level ExecutionContext, or information about the current run when needed.

## 5. ExecutionContext at the Job scope

A JobExecution has an `ExecutionContext` at the Job scope. This is where you store state that needs to be preserved between Steps or that is required for restartability. Each StepExecution also has its own ExecutionContext, usually used to store the progress and checkpoints of that Step itself.

For example, a Job can store the last processed order ID for a subsequent Step to use:

```java
ExecutionContext jobContext = jobExecution.getExecutionContext();
jobContext.putLong("lastProcessedOrderId", 4200L);

long lastProcessedOrderId = jobContext.getLong("lastProcessedOrderId");
```

Some principles when using the ExecutionContext:

- Use the Job-level ExecutionContext for state data that needs to be shared across the whole Job or between Steps.
- Use the Step-level ExecutionContext for checkpoints and state that only matter within a single Step.
- Store small values that the application's serializer can support; avoid putting all business data or large objects into the context.
- Understand clearly when the context is persisted by the JobRepository. Changing an in-memory object does not mean every change has been written to the metadata immediately.
- Name keys clearly and keep data types stable so that a restart can read back the saved state.

The ExecutionContext supports recovering progress but does not replace the transaction mechanism for business data. If a Step both updates business data and saves a checkpoint, you need to design consistent transactions and commit boundaries to avoid reprocessing or missing data when a failure occurs.

## 6. Launching a Job and reading the JobExecution

The example below creates JobParameters and calls the JobLauncher. The `businessDate` parameter is marked identifying so that the business date takes part in determining the JobInstance:

```java
JobParameters jobParameters = new JobParametersBuilder()
        .addString("businessDate", "2026-11-15", true)
        .addString("inputFile", "orders-2026-11-15.csv", true)
        .toJobParameters();

JobExecution execution = jobLauncher.run(importOrdersJob, jobParameters);

log.info(
        "jobExecutionId={}, jobInstanceId={}, status={}, exitCode={}",
        execution.getId(),
        execution.getJobInstance().getId(),
        execution.getStatus(),
        execution.getExitStatus().getExitCode()
);
```

The code shows that the two IDs have different meanings: `execution.getId()` identifies the execution; `execution.getJobInstance().getId()` identifies the JobInstance the execution belongs to.

Note that when `JobLauncher.run` returns depends on the launcher configuration. With a synchronous launcher, the call usually returns after the Job completes. With an asynchronous launcher, the method may return the JobExecution while the Job is still running; in that case `status` may be `STARTED` and `endTime` is not yet set. Therefore, you should not assume that receiving the returned object means the processing is done.

### Tracking with a JobExecutionListener

`JobExecutionListener` provides callbacks at the start and end of the Job lifecycle. This is a suitable place to log or perform monitoring actions based on the JobExecution:

```java
public class ImportJobListener implements JobExecutionListener {

    @Override
    public void beforeJob(JobExecution jobExecution) {
        log.info(
                "Starting jobExecutionId={}, jobName={}",
                jobExecution.getId(),
                jobExecution.getJobInstance().getJobName()
        );
    }

    @Override
    public void afterJob(JobExecution jobExecution) {
        log.info(
                "Finished jobExecutionId={}, status={}, exitStatus={}",
                jobExecution.getId(),
                jobExecution.getStatus(),
                jobExecution.getExitStatus()
        );
    }
}
```

Register the listener when building the Job:

```java
@Bean
public Job importOrdersJob(
        JobRepository jobRepository,
        Step importOrdersStep,
        ImportJobListener listener) {

    return new JobBuilder("importOrdersJob", jobRepository)
            .listener(listener)
            .start(importOrdersStep)
            .build();
}
```

`beforeJob` receives the JobExecution of the run that is about to start; `afterJob` receives the object after the Job has ended. You can use its ID to tag the Steps' logs and to query metadata when investigating incidents. You should not log all JobParameters if they may contain sensitive information.

## 7. Restart and subsequent executions

Restartability is an important reason Spring Batch separates JobInstance from JobExecution. A JobInstance represents the logical work to be completed; a JobExecution records each attempt to complete that work.

Suppose the Job runs with `businessDate=2026-11-15`:

| Run | JobInstance | JobExecution | Result |
|---|---|---|---|
| First run | ID 50 | ID 101 | `FAILED` due to a connection error |
| Restart | ID 50 | ID 108 | `COMPLETED` |

When restarting with the same Job and identifying parameters, Spring Batch can create a new JobExecution on the old JobInstance if the previous execution is in a restartable state and the Job is configured to allow it. The framework uses the metadata together with the saved ExecutionContext to decide how to continue processing.

A few cases to distinguish:

- If the JobInstance has already completed with the same identifying parameters, launching again usually results in a `JobInstanceAlreadyCompleteException`.
- If a JobExecution of that JobInstance is still running, a duplicate launch can result in a `JobExecutionAlreadyRunningException`.
- If the Job is configured not to allow restart, a restart request can fail with a `JobRestartException`.
- If you want to start new logical work, provide a new identifying JobParameter or use an appropriate `JobParametersIncrementer`, instead of trying to reuse a completed JobInstance.

Not every restart re-runs all Steps from the beginning. Spring Batch relies on the metadata and the previous Step state. Steps that have completed are usually skipped in a restart unless the configuration allows rerunning them; Steps that have not completed can continue from the saved checkpoint if the Step is designed to be restartable.

## 8. Looking up a saved JobExecution

In operational applications, you often need to look up a run by ID to display its status, timing, or to investigate errors. `JobExplorer` provides an API for reading metadata from the JobRepository:

```java
JobExecution execution = jobExplorer.getJobExecution(executionId);

if (execution != null) {
    log.info("Job execution status: {}", execution.getStatus());
    log.info("Job execution exit status: {}", execution.getExitStatus());
    log.info("Job execution start time: {}", execution.getStartTime());
    log.info("Job execution end time: {}", execution.getEndTime());
}
```

`JobExplorer` is useful for monitoring screens or history lookup APIs. Creating and updating metadata is the responsibility of the JobRepository and Spring Batch during execution. You should not directly update metadata records in the database to force a JobExecution's status, because that can break consistency between the JobExecution, StepExecution, and ExecutionContext.

## 9. Common misconceptions

**Treating a JobExecution as a JobInstance.** A JobInstance can have multiple JobExecutions across restarts. Use the JobInstance to identify the logical work and the JobExecution to identify each run.

**Believing every JobLauncher call creates a new JobInstance.** A JobInstance depends on the Job name and the identifying JobParameters. An identical set of identifying parameters can point to an existing JobInstance.

**Believing `BatchStatus` and `ExitStatus` are the same.** BatchStatus describes the execution lifecycle; ExitStatus describes the result code. When monitoring or routing a flow, you need to choose the field that suits the purpose.

**Believing `JobLauncher.run` always waits for the Job to complete.** This is only true for a synchronous configuration. With an asynchronous configuration, you need to track the JobExecution after the call returns.

**Using a JobExecution as a container for business data.** JobExecution and ExecutionContext serve metadata, state, and checkpoint management. Large business results should be stored in a suitable data store; the context should only contain the state needed for orchestration or restart.

**Manually editing metadata state to fix an error.** Investigate the cause, check the JobExecution/StepExecution history, and use Spring Batch's operational mechanisms. Editing metadata directly can cause the next restart to no longer reflect the actual progress.

When reading Spring Batch logs or metadata, start with three questions: which Job is being executed, which JobInstance represents that logical work, and which JobExecution ID represents the run being investigated. Being able to distinguish these three layers helps track retries, restarts, and run history more accurately.
