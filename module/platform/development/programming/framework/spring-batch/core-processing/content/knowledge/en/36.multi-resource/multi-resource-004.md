# Saving the current resource in the checkpoint

When a Spring Batch Step reads multiple files or resources, the reader must know which resource it is currently on so it can resume at the exact position after a Job restart. `MultiResourceItemReader` supports this by storing the current resource position in `ExecutionContext`. The inner delegate reader, such as `FlatFileItemReader`, additionally saves the read position within that resource.

The checkpoint therefore has two related parts: **the index of the current resource in the resource list** and **the delegate's state within the current resource**. On restart, Spring Batch reopens the same resource list, jumps to the saved resource, and restores the delegate's read position. This mechanism is reliable only when the resource list, sort order, file contents, and reader names remain stable across runs.

## 1. The challenge when reading multiple resources

Suppose a Job reads daily transaction files:

```text
transactions-2026-11-13.csv
transactions-2026-11-14.csv
transactions-2026-11-15.csv
transactions-2026-11-16.csv
```

Each file contains many records. `MultiResourceItemReader` coordinates a delegate reader to read each file sequentially as a continuous item stream.

```text
MultiResourceItemReader
        |
        +--> Resource 0: transactions-2026-11-13.csv
        |       |
        |       +--> FlatFileItemReader reads line by line
        |
        +--> Resource 1: transactions-2026-11-14.csv
        |       |
        |       +--> FlatFileItemReader reads line by line
        |
        +--> Resource 2: transactions-2026-11-15.csv
        |       |
        |       +--> FlatFileItemReader reads line by line
        |
        +--> Resource 3: transactions-2026-11-16.csv
                |
                +--> FlatFileItemReader reads line by line
```

If the process stops while reading the third file, the restart must know:

- Which resource in the selected list is the third file.
- Which line or record in that file the delegate had reached at the last checkpoint.
- That prior files are already complete and do not need to be re-read from the start.
- That remaining files still belong to the same `JobInstance` input set.

Saving only the current line number without the resource index is insufficient, because line 500 can exist in multiple files. Conversely, saving only the resource index without the intra-file position is also insufficient for accurate resumption.

## 2. What does MultiResourceItemReader save?

`MultiResourceItemReader<T>` is an `ItemStreamReader<T>` that coordinates multiple `Resource` items and a delegate capable of reading each resource. When saving state, the reader writes the current resource position to `ExecutionContext`. The delegate is also opened, updated, and closed across the lifecycle of each resource; the delegate's state restores the position within the current file.

You can visualize the checkpoint as follows:

```text
ExecutionContext
  |
  +-- multiOrderReader.resourceIndex = 2
  |
  +-- orderFileDelegate.currentItemCount = 451
  |
  +-- ...other delegate/Step state
```

Exact key names are generated by Spring Batch based on the reader name and implementation/version. The example above illustrates the concept, not a key contract for the application to read or edit directly.

The two state parts serve distinct roles:

| Component | Restored state | Responsibility |
|---|---|---|
| `MultiResourceItemReader` | Current resource index in the list | Selects the right file to resume. |
| Delegate reader | Read position within the current resource | Resumes from that file's checkpoint. |

The outer reader does not serialize entire `Resource` objects into the checkpoint. It stores the position within the resource list. Consequently, the same index must continue pointing to the same file after restart; the resource list and order must not change unexpectedly.

## 3. Role of ExecutionContext

`ExecutionContext` is the state storage area persisted by Spring Batch in `JobRepository`. Components implementing `ItemStream` use three primary callbacks:

- `open(ExecutionContext)`: reads saved state and restores operation.
- `update(ExecutionContext)`: writes current state to the context at checkpoint points.
- `close()`: releases resources when the reader lifecycle ends normally.

Both `MultiResourceItemReader` and its delegate participate in this lifecycle. In a chunk Step, the framework invokes stream state updates as part of chunk commit processing. When metadata commits, the checkpoint becomes the recovery point for restarts.

Do not manually add a parallel index key to the Job `ExecutionContext` and try to steer the reader when `MultiResourceItemReader` already manages its own state. Overwriting internal keys can cause the reader to open the wrong file or the delegate to restore the wrong position. Configure `name`, `saveState`, and the resource list properly so the reader manages checkpoints itself.

## 4. Configuring MultiResourceItemReader with FlatFileItemReader

Spring Batch 5 example reading multiple CSV files sharing the same schema. The `JobParameter` `input.pattern` holds a resource pattern such as `file:/data/in/transactions-*.csv`.

```java
@Bean
@StepScope
MultiResourceItemReader<TransactionRecord> transactionReader(
        ResourcePatternResolver resolver,
        @Value("#{jobParameters['input.pattern']}") String inputPattern)
        throws IOException {

    Resource[] resources = resolver.getResources(inputPattern);

    Arrays.sort(resources,
            Comparator.comparing(Resource::getFilename,
                    Comparator.nullsLast(String::compareTo)));

    FlatFileItemReader<TransactionRecord> delegate =
            new FlatFileItemReaderBuilder<TransactionRecord>()
                    .name("transactionFileDelegate")
                    .delimited()
                    .names("transactionId", "accountId", "amount")
                    .targetType(TransactionRecord.class)
                    .saveState(true)
                    .build();

    return new MultiResourceItemReaderBuilder<TransactionRecord>()
            .name("multiTransactionReader")
            .resources(resources)
            .delegate(delegate)
            .saveState(true)
            .strict(true)
            .build();
}
```

Key points:

- `multiTransactionReader` has a stable name for storing the resource index.
- `transactionFileDelegate` has a stable name for storing the read position inside the file.
- `saveState(true)` is enabled on both the outer reader and the delegate.
- `ResourcePatternResolver` discovers files matching the pattern.
- The list is explicitly sorted before the reader uses it.
- The delegate is configured without binding to a fixed file; `MultiResourceItemReader` assigns the current resource to the delegate when switching files.
- `strict(true)` throws an error if no resources are found per the reader's strict configuration.

In this example, `ResourcePatternResolver` and `Resource` belong to Spring Core; `MultiResourceItemReaderBuilder` and `FlatFileItemReaderBuilder` belong to Spring Batch. Domain imports, `Arrays`, `Comparator`, and `IOException` are included as required by your application.

If input files must be supplied via a manifest list rather than a wildcard, resolve the manifest into `Resource[]` and pass it the same way. What matters is that the exact same list is reconstructed on restart.

## 5. Why must both the outer reader and delegate save state?

`MultiResourceItemReader` manages the position within the file list. The delegate manages the position within a file. Enabling state on only one of the two layers leaves the checkpoint incomplete.

| MultiResourceItemReader | Delegate | Consequence |
|---|---|---|
| `saveState(true)` | `saveState(true)` | Saves both resource index and position inside the resource. |
| `saveState(false)` | `saveState(true)` | No reliable index to pick the right file on restart. |
| `saveState(true)` | `saveState(false)` | Can pick the right file again, but the delegate lacks the position to resume inside the file. |
| `saveState(false)` | `saveState(false)` | No full reader checkpoint; typically must re-read from the start depending on configuration. |

For proper restarts, enable state on both the outer reader and the delegate, and ensure the delegate implements `ItemStreamReader`/`ItemStream` and can restore position. `FlatFileItemReader` is a commonly used delegate for this.

## 6. Resource index is not the filename

Suppose the following list is used on the initial run:

| Index | Resource |
|---:|---|
| 0 | `transactions-01.csv` |
| 1 | `transactions-02.csv` |
| 2 | `transactions-03.csv` |

The checkpoint saves `resourceIndex = 2`. If, before a restart, a new file `transactions-00.csv` is added to the front of the list and the list is re-sorted, index 2 now points to `transactions-02.csv`. The reader then opens the wrong file even though the numeric index metadata appears valid.

Therefore, the resource index is meaningful only when the resource list is stable. Never treat an index as a durable identifier for a file on the filesystem.

To keep the list stable:

- Generate an input manifest once per `JobInstance`.
- Persist the ordered list of paths/URIs in durable metadata.
- Keep the comparator ordering identical between the initial run and restarts.
- Do not add or remove files in the input directory of a running Job.
- Verify checksum/size/version to confirm files were not replaced.
- If the resource set changes, create a new `JobInstance` with an appropriate business identifier rather than silently reusing an old checkpoint.

## 7. Deterministic resource sorting

`MultiResourceItemReader` accepts a comparator to establish resource order. Configure an explicit comparator whenever order carries business significance.

Example sorting by filename:

```java
Comparator<Resource> resourceComparator =
        Comparator.comparing(Resource::getFilename,
                Comparator.nullsLast(String::compareTo));

return new MultiResourceItemReaderBuilder<TransactionRecord>()
        .name("multiTransactionReader")
        .resources(resources)
        .delegate(delegate)
        .comparator(resourceComparator)
        .saveState(true)
        .build();
```

Do not rely on filesystem ordering returned from wildcards or directory listings. Ordering can differ across operating systems, filesystems, storage providers, or runs.

If filenames contain sequence numbers, avoid lexicographical sorting that yields unexpected order:

```text
batch-1.csv
batch-10.csv
batch-2.csv
```

Lexicographical sorting puts `batch-10.csv` before `batch-2.csv`. When numeric ordering is required, parse the sequence number and use a numeric comparator, or use zero-padded names like `batch-001.csv`, `batch-002.csv`.

The comparator used on restart must match the original comparator. Changing the sorting rule in a deployment can make a checkpointed index point to a different resource.

## 8. How does the delegate save its position inside a file?

With `FlatFileItemReader`, the delegate stores reading progress for the current file in `ExecutionContext`. When reopening the same reader with the persisted context, it restores the read position instead of always starting from line one.

Example file:

```text
transactionId,accountId,amount
T001,A001,100.00
T002,A002,200.00
T003,A003,300.00
T004,A004,400.00
T005,A005,500.00
```

If a checkpoint commits after reading `T003`, restarting on that resource resumes from the next record according to the delegate's state. The resource index identifies which file it is; the delegate checkpoint identifies where inside that file to resume.

Never store `BufferedReader`, `InputStream`, file handles, or parser objects in `ExecutionContext`. The context must hold small, serializable state values. The delegate reader is responsible for translating its internal state into appropriate checkpoint values.

## 9. Checkpoints are updated at chunk commits

A reader may read ahead multiple items to build a chunk. Durable checkpoints correspond to commit boundaries managed by Spring Batch, not simply the last in-memory `read()` call.

For example, with a chunk size of 100:

```text
Read items 1..100
        |
        v
Processor + Writer
        |
        v
update ExecutionContext
        |
        v
Commit chunk and metadata
```

If the next chunk fails and rolls back, the uncommitted chunk's checkpoint does not become a committed restart point. On restart, the reader restores from the last committed checkpoint; some items read during the failed chunk may be read again.

This is why writers must be idempotent or participate in appropriate transactions, especially when side effects occur outside the database. Never treat an in-memory read position as proof that an item was durably written.

## 10. Example checkpoint state across multiple resources

Suppose there are three files of 1,000 records each and the chunk size is 100. The Job has finished file 1, committed 400 records of file 2, and is currently processing file 2:

```text
Resource 0: file-01.csv  [1,000 records committed]
Resource 1: file-02.csv  [400 records committed | next records ...]
Resource 2: file-03.csv  [not started]

Checkpoint concept:
  current resource index = 1
  delegate position       = after committed record 400
```

If the process is killed, a restart re-selects resource index 1, and the delegate restores its position inside `file-02.csv`. Once file 2 finishes, the reader continues to file 3.

The index and delegate position are updated at chunk checkpoints. You do not need to store a copy of the entire file contents in `ExecutionContext`.

## 11. Resource transitions and checkpointing

When the delegate reaches EOF of the current resource, `MultiResourceItemReader` advances to the next resource and assigns the new resource to the delegate. The delegate is reopened for that resource with appropriate initial state.

For example:

```text
file-01.csv: read to EOF
       |
       v
currentResource++
       |
       v
delegate.setResource(file-02.csv)
       |
       v
delegate.open(new state for this resource)
       |
       v
read first item of file-02.csv
```

When the Step updates the checkpoint, the outer reader saves the index of the resource being processed and the delegate saves its progress within that resource. If a chunk spans the boundary between two files, the checkpoint reflects the resource and position corresponding to the last item in the committed chunk.

Never mutate the current resource manually while the Step is running. `MultiResourceItemReader` manages file transitions; modifying the resource array or calling `setResource` from business code can corrupt state and break restarts.

## 12. Keeping the resource list stable with a manifest

With an input pattern like `file:/data/in/*.csv`, the file count can change between runs. A safer approach is locking the input list when creating the `JobInstance`.

A manifest can contain:

```json
{
  "jobInstanceKey": "daily-transactions-2026-11-15",
  "resources": [
    {
      "sequence": 1,
      "path": "file:/data/in/transactions-01.csv",
      "size": 125004,
      "checksum": "sha256:..."
    },
    {
      "sequence": 2,
      "path": "file:/data/in/transactions-02.csv",
      "size": 138902,
      "checksum": "sha256:..."
    }
  ]
}
```

The Job reads the manifest to reconstruct the exact `Resource[]` in sequence order. If a resource no longer exists or its checksum changed, stop and request input remediation rather than applying an old index to a different list.

The manifest can live in object storage, a database, or a durable file. If you pass the manifest path in `JobParameters`, maintain appropriate identifying/non-identifying semantics and never generate a new manifest when restarting the same `JobInstance`.

## 13. Wildcard patterns and resource discovery

Wildcards are convenient for discovering multiple files:

```java
Resource[] resources = resolver.getResources(
        "file:/data/in/transactions-*.csv");
```

However, a wildcard result is a snapshot at resolution time. If new files arrive after the Job starts, a restart could receive a different list if the resolver runs again.

Options:

- Lock the resource list and save a manifest before launching the Job.
- Copy inputs into a `JobInstance`-specific staging directory and read from there.
- Use a batch membership table listing the exact files belonging to the Job.
- Use an identifying parameter representing the input set/version.
- Validate the input list and checksums before opening the reader on restart.

Do not let a producer continue writing into the same wildcard directory while the Batch consumer is reading, unless an explicit handoff protocol exists. Partially written files could enter the resource list and cause the reader to parse incomplete data.

## 14. Recording the current resource name for logging or auditing

`MultiResourceItemReader` manages the resource index in the checkpoint, but business code may need the current filename for logging, auditing, or tagging rejected records. Do not read the reader's internal keys using hardcoded names not guaranteed by the API.

One approach is using a custom resource-aware delegate or a listener/collaborator updated when a resource opens. Example delegate wrapper:

```java
public class TrackingFlatFileReader<T>
        extends FlatFileItemReader<T> {

    private final Consumer<Resource> resourceObserver;

    public TrackingFlatFileReader(Consumer<Resource> resourceObserver) {
        this.resourceObserver = resourceObserver;
    }

    @Override
    public void setResource(Resource resource) {
        super.setResource(resource);
        resourceObserver.accept(resource);
    }
}
```

This example illustrates observing the resource assigned to the delegate. `resourceObserver` must be a step-scoped collaborator and avoid non-idempotent side effects because resources can be reassigned on restart. If you need to persist the filename for durable auditing, write to `StepExecution`/`ExecutionContext` through supported APIs or store it alongside the business record; never use a singleton field shared across Jobs.

A simpler option is having each item carry the source filename if the reader/delegate attaches source metadata to items. This is useful when rejects or audits must pinpoint the exact source file for each record.

## 15. Reader names must be stable

`ItemStreamSupport` uses the reader name to build keys in `ExecutionContext`. Therefore, `.name(...)` is not just a log label; it forms part of the checkpoint namespace.

For example:

```java
.name("multiTransactionReader")
```

and the delegate:

```java
.name("transactionFileDelegate")
```

These names must be:

- Non-empty when saving state.
- Stable across restarts of the same Step.
- Unique from other readers/streams in the same `StepExecution`.
- Never generated randomly based on timestamp or `JobExecution` ID.

If you rename a reader in a newer application release, old checkpoint keys may no longer be found. When renaming, determine whether older `JobExecution` instances still need to restart on the new release and plan migrations or drain running executions first.

## 16. When to use saveState(false)?

`saveState(false)` disables saving reader checkpoints. This can be appropriate when:

- The reader runs once and does not need restartability.
- Input can be re-read completely at low cost.
- The application actively manages checkpoints through another designed and tested mechanism.
- You do not want the component saving state in a special context, such as a parallelized reader that does not support compatible state.

With `MultiResourceItemReader`, if the requirement is to resume from the current file and position, do not disable state on either the outer reader or the delegate. Enable `saveState(true)` on both layers.

Never use `saveState(false)` to work around restart errors caused by a mutating resource list. Doing so merely drops checkpoints without fixing the unstable input set.

## 17. Strict mode and empty resource lists

When no resources are found, define how the Job should behave. With `strict(true)`, the reader fails when no resources exist per implementation semantics. If business rules allow zero files, configure non-strict behavior and handle the zero-item path in the appropriate flow.

Never treat an empty list as success if doing so could mask upstream failures like un-uploaded files or misconfigured patterns. You can check the resource count before launch and record an explicit status.

On restart, an empty resource list when the checkpoint indicates a prior resource index signals that the input set changed or resources were deleted. Fail with enough diagnostic context for operations to restore the proper manifest/files.

## 18. Missing or modified resources between runs

Common failures:

- Files were archived or deleted after the initial run.
- A file was overwritten with new contents at the same path.
- Permissions changed so the process can no longer read it.
- A wildcard picked up additional new files.
- A file in the list was renamed.
- Comparator ordering changed.

The reader index may still be numerically valid yet point to a different resource. To detect this:

- Store a manifest containing path, size, and checksum.
- Verify resource identity before opening the delegate.
- Keep inputs immutable until the `JobInstance` restart window expires.
- Archive or delete inputs only after the Job completes and retention allows.
- When the input set changes, create a new `JobInstance` or run controlled recovery.

Never automatically skip a missing resource and move on to the next file if that silently loses data without auditing or reconciliation.

## 19. Resource checkpoints and partitioning

When using partitioning, each partition typically gets its own reader and `ExecutionContext`. You can split the resource list into groups and create a separate `MultiResourceItemReader` per partition.

```text
Manager Step
    |
    +--> Partition 0: files 01, 02 --> MultiResourceReader 0
    |
    +--> Partition 1: files 03, 04 --> MultiResourceReader 1
    |
    +--> Partition 2: files 05, 06 --> MultiResourceReader 2
```

Each partition requires:

- Its own resource list with no unintended overlap.
- Stable resource order within the partition.
- Distinct reader names/`ExecutionContext` keys appropriate for the partition.
- Independent delegate state.
- A manifest or partition metadata sufficient to reconstruct the exact same input set on restart.

Never share a mutable `MultiResourceItemReader` instance across multiple workers. The reader holds `currentResource` and the current delegate; concurrent mutation from multiple threads corrupts files and checkpoints.

## 20. Common pitfalls when saving the current resource

### Saving only the current line without the resource index

A line number alone does not identify which file is being read. Use `MultiResourceItemReader` to manage the resource index and the delegate to manage position within the file.

### Enabling saveState only on the outer reader

The reader knows the current file, but the delegate cannot restore the position inside that file. Enable state on the restartable delegate.

### Enabling saveState only on the delegate

The delegate lacks the information needed to select the right resource from the list. Enable state on `MultiResourceItemReader`.

### Using a wildcard whose list changes on restart

The resource index can point to a different file. Lock the input list using a manifest or staging directory.

### Not sorting resources explicitly

Filesystem return order can vary. Use a deterministic comparator and keep it identical across restarts.

### Renaming the reader

`ExecutionContext` keys change and old checkpoints may not be restored. Keep names stable for restartable `JobExecution` instances.

### Modifying file contents at the same path

The old delegate position may point to a different record. Keep inputs immutable and verify checksums.

### Editing internal ExecutionContext keys manually

Keys are implementation details derived from reader name and version. Let the reader write and read state through the `ItemStream` lifecycle.

### Sharing a singleton delegate across concurrent Jobs

The delegate holds mutable resource and read state. Scope instances appropriately per `StepExecution` or enforce exclusive ownership.

### Deleting already-read files before Job completion

A restart might need to reopen them. Archive or delete only after the Job reaches a terminal state and retention/recovery policies allow.

### Assuming checkpoints update immediately after every read

Durable checkpoints are tied to chunk commits. Items in rolled-back chunks can be re-read.

## 21. Testing MultiResourceItemReader checkpointing

Tests must prove the reader restores both the right resource and the right position within that resource.

### Multi-file fixture

Create two small files:

```text
file-01.csv
id,value
1,A
2,B
3,C

file-02.csv
id,value
4,D
5,E
6,F
```

Sort resources by filename and configure the `FlatFileItemReader` delegate with `saveState(true)`. Read the first two items, call `update` to save the checkpoint to `ExecutionContext`, then close the reader.

### Opening a new reader with the saved checkpoint

Create a new reader instance with the exact same:

- Reader name.
- Delegate name.
- Resource list and order.
- File contents.
- Mapping and encoding configuration.

Open the new reader with the saved `ExecutionContext` and verify the next item is the third item of the first file, not the first item. Continue reading into the second file and confirm ordering with no duplicates or gaps.

### Testing across file boundaries

Place a chunk/checkpoint near the end of the first file so the next read crosses into the second file. After saving state, restart and verify the reader lands on the second resource at the corresponding position.

### Testing a mutated resource list

Insert a new file ahead of the checkpointed resource or change the comparator between opens. The test should show the input list is no longer compatible; in production, manifest/checksum checks should detect the difference and stop rather than silently misprocessing.

## 22. Reader-level state testing example

The snippet below illustrates reusing the same `ExecutionContext` across two reader instances. The helper creating the reader must use the exact same resource array, comparator, and reader names:

```java
@Test
void resumesFromSavedResourceAndDelegatePosition() throws Exception {
    Resource[] resources = {
            new FileSystemResource(file01),
            new FileSystemResource(file02)
    };

    ExecutionContext checkpoint = new ExecutionContext();
    MultiResourceItemReader<String> firstReader =
            createReader(resources);

    firstReader.open(checkpoint);
    try {
        assertThat(firstReader.read()).isEqualTo("1,A");
        assertThat(firstReader.read()).isEqualTo("2,B");
        firstReader.update(checkpoint);
    } finally {
        firstReader.close();
    }

    MultiResourceItemReader<String> restartedReader =
            createReader(resources);

    restartedReader.open(checkpoint);
    try {
        assertThat(restartedReader.read()).isEqualTo("3,C");
        assertThat(restartedReader.read()).isEqualTo("4,D");
    } finally {
        restartedReader.close();
    }
}
```

`createReader(resources)` is a helper returning a `MultiResourceItemReader` with a `FlatFileItemReader` delegate sharing the same name, `saveState(true)`, and the same comparator. This example tests the reader lifecycle directly; a full integration test with a Spring Batch Step is still required to confirm checkpoints persist in `JobRepository` alongside chunk transactions.

When calling `open`, `update`, and `close` manually, the test simulates stream-level lifecycle; it does not test transaction rollbacks or `JobExecution` metadata. Never rely on this test alone as proof of production restartability.

## 23. Job-level restart testing

Integration tests should use `@SpringBatchTest` and `JobLauncherTestUtils` to run a real Job:

1. Create a fixed resource manifest for the test.
2. Launch the Job with identifying parameters representing the input set.
3. Stop or fail the Job after several committed chunks using a controlled test fixture.
4. Verify `ExecutionContext` stores the resource index and delegate position at the last checkpoint.
5. Restart the same `JobInstance` using the exact same identifying parameters.
6. Verify files processed before the checkpoint are not unintentionally re-read.
7. Verify the remainder of the current resource and subsequent resources are read completely.
8. Verify writer output has no duplicates and no missing items.

Do not alter input files between runs. If you need to test input mutation, write a separate test verifying the Job detects the manifest/checksum mismatch and fails clearly.

## 24. Operational procedure for restarting multi-resource jobs

Before restarting a multi-file Job:

1. Identify the prior `JobInstance` and `JobExecution`.
2. Confirm the previous process has stopped and the execution is eligible for restart.
3. Load the input manifest for that exact `JobInstance`.
4. Reconstruct the resource list in its original order.
5. Verify all required resources still exist and checksums/sizes match.
6. Keep reader name, delegate name, fragment/line mapping, and `JobParameters` unchanged.
7. Let `MultiResourceItemReader` read the checkpointed index and the delegate restore file position.
8. Monitor the new `JobExecution`, current resource, and counters.
9. Reconcile committed data and writer side effects.
10. Archive or delete input files only after the Job completes and the restart/reprocess window ends.

If the manifest does not match or a current file was replaced, do not force the reader to use the old checkpoint. Decide on reprocessing or a new `JobInstance`, or restore the proper inputs before proceeding.

## 25. Resource checkpoint design workflow

When building a multi-resource reading Step, follow this sequence:

1. Choose `MultiResourceItemReader` and a delegate supporting `ItemStream`.
2. Lock the resource set belonging to the `JobInstance`.
3. Sort resources with a deterministic comparator.
4. Assign stable, Step-unique names to the outer reader and delegate.
5. Enable `saveState(true)` on both the outer reader and delegate.
6. Ensure the delegate can persist its position within the current resource.
7. Keep resource paths, contents, encoding, and schema stable across restarts.
8. Let the framework update `ExecutionContext` on chunk commits; do not edit internal keys manually.
9. Use manifests and checksums to detect resource list or file alterations.
10. Write tests spanning multiple files, multiple pages/records, and resource boundaries.
11. Run restart integration tests against `JobRepository` to verify real checkpoints.
12. Clean up inputs only when Job status and retention policies allow.

| Needs restoration | Managing component |
|---|---|
| Which file in the list is being read | `MultiResourceItemReader` resource index |
| Which line/record in the current file | Delegate reader `ExecutionContext` |
| File ordering between first run and restart | Resource list + comparator/manifest |
| Whether files still match original contents | Input immutability, size/checksum |
| Last committed position | Spring Batch chunk transactions and `JobRepository` |
| Side effects already applied in target system | Writer idempotency and reconciliation |

## Conclusion

`MultiResourceItemReader` stores the current resource index in `ExecutionContext`; a delegate such as `FlatFileItemReader` stores the read position within that resource. For reliable restarts, enable `saveState(true)` on both layers, use stable reader names, and preserve the resource list and sort order across runs. Because checkpoints store list position rather than an immutable file identifier, wildcards can yield different file sets on restart; lock inputs with a manifest, verify path/size/checksum, and keep files unchanged through the restart window. Spring Batch updates checkpoints on chunk commits, so items from uncommitted chunks may be re-read. Never modify internal `ExecutionContext` keys manually; let the reader and delegate manage the `open`, `update`, and `close` lifecycle.
