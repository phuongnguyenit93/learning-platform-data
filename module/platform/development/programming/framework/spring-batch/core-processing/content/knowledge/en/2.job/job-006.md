# Can a Job be rerun?

Yes. Spring Batch supports restarting a Job that has failed or been stopped, provided the Job and its Steps are designed for restart and the necessary metadata is still in the `JobRepository`. When restarted properly, Spring Batch can skip the Steps that have already completed and continue from the Step that has not completed. For Steps that process data in chunks, the framework can also restore the processing position from the saved checkpoint.

However, "rerun" has two different meanings: **restarting the same logical run after a failure**, and **launching a new business run from scratch**. Understanding this difference clearly is the most important thing when operating Spring Batch.

## 1. Distinguishing JobInstance and JobExecution

Spring Batch uses metadata to identify a run and to record each of its executions.

- **Job:** the definition of a batch process, consisting of Steps and the execution flow.
- **JobParameters:** the input parameters when launching, for example the business date, a file code, or the data range to process. Each parameter can be marked as identifying or non-identifying.
- **JobInstance:** one logical run of a Job. A JobInstance is identified by the Job name and the set of identifying JobParameters.
- **JobExecution:** one specific execution of a JobInstance. A JobInstance can have multiple JobExecutions if an earlier run failed or was stopped and then restarted.
- **StepExecution:** the execution information of a Step within a JobExecution, including the status, timing, and the counters for reads, processing, writes, skips, or commits.

For example, the Job `dailyBillingJob` runs for the business date `2026-11-15`. If the date parameter is identifying, the pair of the Job name and that date identifies a JobInstance. If the first execution fails, the restart creates a new JobExecution but still belongs to the JobInstance for 15/11.

```text
Job: dailyBillingJob
Identifying parameter: businessDate=2026-11-15
                    |
                    v
          JobInstance (15/11)
                    |
          +---------+---------+
          |                   |
          v                   v
   JobExecution #1      JobExecution #2
      FAILED             COMPLETED
          |                   ^
          +---- restart ------+
```

Thus, a restart does not create a new business JobInstance. It creates the next execution for the very instance that failed or was stopped.

## 2. When can a Job be restarted?

Restartability depends on the saved state of the JobInstance, the Job and Step configuration, and the metadata in the JobRepository.

| State or situation | Can the same JobInstance be launched again? | Meaning |
|---|---|---|
| The previous run is `FAILED` | Usually yes | Can be restarted if the Job is not configured to forbid restart and the Step allows continued execution |
| The previous run is `STOPPED` | Usually yes | A Job that was stopped in a controlled way can be continued |
| The previous run is `COMPLETED` | No | The instance has completed; to run a new business run you need different identifying parameters |
| The instance is `STARTED` | Cannot be launched concurrently again | You need to determine whether the current execution is still running or was left behind after an incident |
| The Job is configured with `preventRestart()` | No | The Job is marked as not restartable after a failure |
| The necessary metadata is lost | Cannot restart reliably | The framework no longer has enough execution state and checkpoints to continue at the right position |

Common exceptions when launching again include:

- `JobInstanceAlreadyCompleteException`: the JobInstance with those identifying parameters has already completed.
- `JobExecutionAlreadyRunningException`: the JobInstance has an active execution.
- `JobRestartException`: the instance cannot be restarted, for example the Job does not allow restart or the current state is not appropriate.
- `JobParametersInvalidException`: the parameters passed in are invalid according to the Job's validator.

If a Job is running and the application is shut down abruptly, the metadata may still show the execution as running. You should not arbitrarily delete metadata or create new parameters to avoid the error. First verify that the old process has really stopped, check the state in the JobRepository, and apply an appropriate operational procedure to handle the abandoned execution.

## 3. Restarting with the same JobParameters

To restart a failed JobInstance, you usually need to launch the Job with the same Job name and the same identifying JobParameters. Spring Batch looks up the corresponding JobInstance in the JobRepository, checks the previous execution, and then decides whether the next JobExecution can be created.

For example, the application launches the Job using the `JobLauncher`:

```java
@Service
public class BillingJobService {

    private final JobLauncher jobLauncher;
    private final Job dailyBillingJob;

    public BillingJobService(JobLauncher jobLauncher, Job dailyBillingJob) {
        this.jobLauncher = jobLauncher;
        this.dailyBillingJob = dailyBillingJob;
    }

    public JobExecution runFor(LocalDate businessDate)
            throws Exception {

        JobParameters parameters = new JobParametersBuilder()
                .addLocalDate("businessDate", businessDate, true)
                .toJobParameters();

        return jobLauncher.run(dailyBillingJob, parameters);
    }
}
```

The `businessDate` parameter is marked identifying with the value `true`. Calling `runFor()` again with the same date after the previous execution failed targets the same JobInstance. If the previous run is already `COMPLETED`, calling again with the same parameters is rejected because that instance has completed.

In this example, the method returns the `JobExecution` so the caller can check the status. Depending on the launcher configuration, the Job may run synchronously or be executed through another mechanism; receiving an execution should not be mistaken for the whole Job having completed successfully.

## 4. Where does Spring Batch continue from on restart?

Spring Batch stores state at the Job and Step levels. On a restart, the framework uses that state to decide which Steps need to be run again.

### Steps that have completed are usually skipped

Suppose a Job has three Steps:

```text
importFileStep
       |
       v
validateRecordsStep
       |
       v
writeReportStep
```

If `importFileStep` and `validateRecordsStep` are `COMPLETED` but `writeReportStep` fails, a normal restart will skip the two completed Steps and rerun the report Step. This helps avoid repeating work that has already been completed.

You can configure a completed Step to still be run again with `allowStartIfComplete(true)`. This configuration is useful for a Step that needs to be performed again every time the Job restarts, for example a cleanup Step or a Step that synchronizes a state that can safely be repeated.

```java
@Bean
Step prepareWorkspaceStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        Tasklet prepareWorkspaceTasklet) {

    return new StepBuilder("prepareWorkspaceStep", jobRepository)
            .tasklet(prepareWorkspaceTasklet, transactionManager)
            .allowStartIfComplete(true)
            .build();
}
```

Only enable `allowStartIfComplete(true)` when executing the Step multiple times is valid. If the Step sends emails, creates transactions, or writes data without a duplicate-prevention mechanism, rerunning the Step can create repeated side effects.

### Checkpoints in chunk processing

For a Step that processes many records in chunks, Spring Batch stores the necessary state at the commit boundaries. For example, a Step reads a 100,000-line file with a chunk size of 500. After some chunks have committed, the process hits an error in the next chunk. On restart, the reader can continue from the most recent saved checkpoint instead of starting again from the first line.

```text
Read and process data
       |
       v
Chunk 1 (500 items) ----> Commit + save checkpoint
       |
       v
Chunk 2 (500 items) ----> Commit + save checkpoint
       |
       v
Chunk 3 (in progress) --> Error / rollback
       |
       v
       Restart
       |
       v
Continue from the most recent committed checkpoint
```

The `ExecutionContext` stores the state that needs to be preserved between executions. Readers and writers that support state saving can write checkpoint information into the context for use on restart. For a custom-built reader, you need to implement an appropriate state saving and restoring mechanism; if the reader cannot save its progress, the Step may have to read again from the beginning or cannot be restarted in the desired way.

A checkpoint is usually tied to committed state. If an error occurs while a chunk has not been committed, the changes belonging to that chunk's transaction are rolled back and that data may be read and processed again in the restart. Therefore, you should not assume that every item read before the error has been written successfully.

## 5. Job and Step configuration affects restart

By default, a Job is designed to be restartable when the state and metadata allow it. There are a few options that adjust this behavior.

### Preventing restart at the Job level

If a Job is not allowed to restart, you can call `preventRestart()` when building the Job:

```java
@Bean
Job oneTimeImportJob(JobRepository jobRepository, Step importStep) {
    return new JobBuilder("oneTimeImportJob", jobRepository)
            .start(importStep)
            .preventRestart()
            .build();
}
```

When this Job fails, restarting the same JobInstance will be rejected. Only use this configuration when the business truly does not allow continuing on the same instance and there is a separate incident handling process.

### Limiting the number of Step executions

`startLimit()` limits the number of times a Step is allowed to start executing within the same JobInstance. For example:

```java
@Bean
Step transferStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        Tasklet transferTasklet) {

    return new StepBuilder("transferStep", jobRepository)
            .tasklet(transferTasklet, transactionManager)
            .startLimit(3)
            .build();
}
```

With a limit of 3, if the Step has used up its allowed number of starts, the next restart cannot start that Step. This limit is useful when an operation is high-risk or when continuous retrying is meaningless. You need to count the earlier times the Step has started when designing the limit.

### Allowing a completed Step to be rerun

`allowStartIfComplete(true)` allows a Step to be executed again when the JobInstance is restarted, even if the Step is `COMPLETED`. If this option is not enabled, a completed Step is usually skipped in the restart.

The three mechanisms above play different roles:

| Configuration | Scope | Effect |
|---|---|---|
| `preventRestart()` | Job | Forbids restarting the JobInstance after a failure |
| `startLimit(n)` | Step | Limits the number of times the Step is started |
| `allowStartIfComplete(true)` | Step | Allows rerunning a completed Step on restart |

## 6. A restart is different from running a new JobInstance

If you want to reprocess all the data from the beginning as a new business run, you need to create a new JobInstance by changing at least one identifying JobParameter. For example, the billing Job for 15/11 and the billing Job for 16/11 are two different instances.

You should not arbitrarily add a timestamp or UUID to the identifying parameters on every rerun attempt. That creates a new JobInstance, causing Spring Batch to treat it as new work and possibly reprocess all of the data. It is not a restart of the instance that failed.

Spring Batch has `JobParametersIncrementer`, for example `RunIdIncrementer`, to create the parameter set for the next instance in processes that need to run multiple instances. The incrementer serves to create new parameters; it does not restore the checkpoint of the failed instance. When the goal is a restart, reuse the identifying parameters of the old instance.

You can distinguish the two goals as follows:

| Goal | How to do it | Starting point |
|---|---|---|
| Continue failed work | Reuse the identifying parameters of the old JobInstance and restart when the state allows | From the appropriate Step or checkpoint |
| Run a new business period | Use new identifying parameters, for example a new business date | From the start of the new JobInstance |
| Deliberately reprocess the whole same period | Create a new instance with a separate run identifier and have a duplicate-write prevention process | From the start; side effects need to be controlled |

The case of deliberately rerunning an entire same period needs to be considered carefully. If the previous run already wrote part of the data to the target system, the new instance can write duplicates or corrupt figures unless there is a unique key, a data replacement mechanism, or an appropriate undo step.

## 7. Conditions for a reliable restart

A restart is only safe when the application preserves state and the work's side effects are controlled.

### Maintaining the JobRepository and metadata

The `JobRepository` stores JobInstance, JobExecution, StepExecution, and ExecutionContext information. In an environment that needs to restart after the application restarts, the metadata must be stored in a durable store, usually a database with the Spring Batch schema configured correctly.

If the metadata is deleted, reset, or not stored durably, the framework may not know how far the Job has processed. Having only the business data in the database is not enough to recover batch progress on its own.

### Keeping the input stable

Suppose a reader saved a checkpoint at line 20,000 of the file `customers.csv`. If the file is replaced or its contents are reordered before the restart, the position at line 20,001 may no longer represent the truly next record. You should use input files that are immutable by code or version, check the checksum when needed, and keep the run's data source until the Job completes.

### Designing write operations that can be safely repeated

Spring Batch transactions usually protect operations within the same transaction manager. But side effects such as calling an HTTP service, sending email, writing a file, or publishing a message may not roll back together with the database transaction.

For example, the writer calls a payment service and the service successfully collected the money, but the process dies before the JobRepository saves the commit state. On restart, the same item may be sent to the payment service again. To reduce the risk:

- Use a stable idempotency key for each business operation, such as the source transaction code.
- Set a unique constraint or check the processed state in the target system.
- Write the event publication request into a transactional outbox and then publish through a retryable mechanism.
- Separate the step that creates intermediate data from the step that confirms the result so that reconciliation is possible.
- Record the errors and results of each item so that operations can handle cases whose state is unclear.

### Understanding the reader, processor, and writer clearly

The reader needs to know how to restore its read position. The processor should avoid creating uncontrolled side effects because an item can be processed again on rollback or retry. The writer needs a strategy to prevent duplicate writes or to update in an idempotent way. For a custom-implemented reader/processor/writer, clearly determine what state is saved, when it is committed, and what happens if the process stops in the middle of a chunk.

## 8. Procedure when a Job fails

When a Job reports `FAILED`, the operator should determine the cause before restarting:

1. Look up the JobInstance by the Job name and identifying parameters to make sure you are handling the right business period.
2. Check the most recent JobExecution and StepExecution, identify the failed Step, the exception, and the number of items read/written/skipped.
3. Verify that the old process has stopped and that no other execution is running for the same instance.
4. Fix the root cause, such as restoring the database, correcting the input data, or fixing a dependent service.
5. Confirm that the reader, writer, and external side effects can be restarted safely.
6. Launch again with the same identifying JobParameters so that Spring Batch continues the old JobInstance.
7. Monitor the new execution until its end state and reconcile the business results.

You should not delete the Spring Batch metadata tables just to make the Job runnable again. That action can delete the history and checkpoints the framework needs to restart. If you need to rerun from the beginning, clearly determine how to create a new instance and how to handle the data written in the previous run.

## 9. A real-world scenario example

A Job imports 50,000 customers from a fixed file, processing chunks of 500 items. After 12,000 items have been committed, the target database temporarily loses its connection and the Step fails.

If the reader saves a checkpoint and the JobRepository metadata is intact, the operator can restore the database and then restart with the same identifying parameters. Spring Batch uses the saved state to continue the part that has not completed. The chunks committed earlier are kept as they are; the failing chunk is processed again according to the transaction boundary and the checkpoint.

If the operator instead adds a new timestamp to the identifying parameters, Spring Batch will create a new JobInstance. The import Job may read again from the beginning. If the writer only inserts without a unique key or a check for an existing customer, the data may be duplicated. Therefore, changing parameters to create a new instance is not the way to fix a restart error.

## Conclusion

A Job in Spring Batch can be rerun after `FAILED` or `STOPPED` if the Job allows restart, the Step still has execution attempts remaining, and the necessary metadata is preserved. A restart reuses the identifying JobParameters to continue the same JobInstance; the new JobExecution records the next execution. Spring Batch relies on the Step state and the checkpoint in the ExecutionContext to skip the completed part or continue processing data. For a reliable restart, you need to maintain the JobRepository, keep the input stable, and design write operations and external side effects so that they can be safely retried.
