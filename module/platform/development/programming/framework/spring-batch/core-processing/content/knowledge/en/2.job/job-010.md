# Restarting a Job from a failed execution

In a batch application, a job can process thousands or millions of records and run for a long time. If the application stops midway, the database loses its connection, or a processing step hits an error, rerunning the entire job from the beginning can be time-consuming and create duplicate data. Spring Batch provides a **restart** mechanism to continue a logical run that has failed or been stopped, based on the saved metadata and state.

Restart is part of the Spring Batch execution model. To use it correctly, you need to understand the relationship among `JobInstance`, `JobExecution`, `StepExecution`, `JobParameters`, `JobRepository`, and `ExecutionContext`. You also need to design the reader, writer, and business operations so that they can recover safely.

## 1. Distinguishing restart, rerun, and creating a new job instance

Spring Batch distinguishes the job definition, a logical run, and each specific execution:

| Concept | Meaning |
|---|---|
| `Job` | The definition of the process, consisting of steps and the control flow. |
| `JobInstance` | One logical run, identified by the job name and the identifying `JobParameters`. |
| `JobExecution` | One specific execution of a `JobInstance`. |
| `StepExecution` | One specific execution of a step within a `JobExecution`. |

For example, the job `importOrdersJob` processes the order file for the business date `2026-11-15`. The job name combined with the identifying parameter `businessDate=2026-11-15` identifies a `JobInstance`. If the first run fails, the restart creates a new `JobExecution` but still belongs to the same `JobInstance`.

```text
Job: importOrdersJob
          |
          +-- JobInstance (businessDate=2026-11-15)
                    |
                    +-- JobExecution #1: FAILED
                    |
                    +-- JobExecution #2: COMPLETED  <- restart
```

The following cases have different meanings:

- **Restart:** continue the same `JobInstance` after the previous execution failed or was stopped in a way that allows restart. Spring Batch creates a new `JobExecution` and uses the saved state.
- **Rerun with new identifying parameters:** creates a new `JobInstance`. This is a different logical run, even though it may use the same file or the same type of job.
- **Calling a JobInstance that has already completed again:** normally not allowed. Spring Batch reports an error because that instance has completed.

Therefore, a restart does not mean creating a completely new job instance. The goal is to continue the logical work that was identified in the previous run.

## 2. JobParameters determine which instance is restarted

`JobParameters` is the set of input parameters of a job. Each parameter has an identifying attribute that indicates whether it takes part in determining the `JobInstance`.

An example of creating parameters:

```java
JobParameters parameters = new JobParametersBuilder()
        .addString("inputFile", "data/orders-2026-11-15.csv", true)
        .addString("businessDate", "2026-11-15", true)
        .addString("requestedBy", "scheduler", false)
        .toJobParameters();
```

In the example above:

- `inputFile` and `businessDate` have `identifying=true`, so they take part in determining the JobInstance.
- `requestedBy` has `identifying=false`, so it does not change the identity of the JobInstance.

When restarting with `JobLauncher`, pass back the same job name and the same identifying values used in the previous run:

```java
JobExecution execution = jobLauncher.run(importOrdersJob, parameters);
```

If the previous execution of that instance failed and the job allows restart, Spring Batch creates the next execution for the same instance. If you change `businessDate` or another identifying parameter, the application is requesting a new JobInstance.

A common mistake is always adding a new timestamp or UUID to the identifying parameters on every launch. In that case each call creates a different JobInstance, so the restart mechanism cannot continue the failed instance. Only create a new identifying value when the business genuinely requires a new logical run.

## 3. State affects restartability

Spring Batch stores the execution state as `BatchStatus`. Some common statuses:

| `BatchStatus` | Meaning and ability to continue |
|---|---|
| `STARTING`, `STARTED` | The job is being initialized or executed. Do not launch another execution concurrently for the same instance. |
| `COMPLETED` | The job has completed. The same JobInstance usually cannot be run again as an ordinary restart. |
| `FAILED` | The job failed. It can be restarted if the job and the related steps allow it. |
| `STOPPING`, `STOPPED` | The job is stopping or has stopped in a controlled way. An execution in the `STOPPED` state can usually be restarted. |
| `ABANDONED` | The execution has been marked as not to be continued. It is not treated as an ordinary failed execution to restart. |
| `UNKNOWN` | The state is undetermined; you need to investigate the metadata and the data condition before deciding how to handle it. |

Some exceptions that can occur at launch:

- `JobExecutionAlreadyRunningException`: the instance has an active execution.
- `JobInstanceAlreadyCompleteException`: the instance has already completed.
- `JobRestartException`: the job or execution cannot be restarted given the current state or configuration.
- `JobParametersInvalidException`: the parameters are invalid according to the job's validator.

The job's state and the step's state are related but not the same. A job can fail because a step fails. In a restart, Spring Batch uses each step's metadata to determine which step needs to be rerun and which has completed.

### BatchStatus and ExitStatus

`BatchStatus` reflects the execution lifecycle state such as `COMPLETED` or `FAILED`. `ExitStatus` is the result code that a step or job returns, commonly used to control the flow and able to carry custom values such as `COMPLETED`, `FAILED`, `NO_DATA`, or `VALIDATION_ERROR`.

These two concepts are related but not interchangeable. When configuring a flow, make sure the ending branch correctly reflects the business result. If a job ends with `BatchStatus.COMPLETED`, Spring Batch considers the JobInstance to have completed, even if the application uses a custom `ExitStatus` to describe a special business result. If you need to restart, design an end state that fits that goal.

## 4. Where does Spring Batch continue from?

A restart does not mean the framework continues at exactly the last Java statement before the process was stopped. Spring Batch recovers based on execution boundaries and the saved state.

For a job with multiple steps, the general rule is:

- A completed step is usually skipped on restart.
- A failed or incomplete step is executed again according to the step's restart configuration.
- A completed step can be rerun if configured with `allowStartIfComplete(true)`.
- Data in the `ExecutionContext` can help a step continue from the saved checkpoint.

For example, a job of three steps:

```text
validateFileStep  -> COMPLETED
importOrdersStep  -> FAILED
publishReportStep -> not run
```

When restarting the same JobInstance, the flow usually works as follows:

```text
validateFileStep  -> skipped because it is already COMPLETED
importOrdersStep  -> rerun from the saved checkpoint
publishReportStep -> runs when importOrdersStep completes
```

This is the normal behavior when the job flow and steps are configured in the default way. Restart options, flow transitions, or manually set states can change the actual path.

## 5. ExecutionContext and checkpoints

`ExecutionContext` is a key-value storage area attached to a `JobExecution` or `StepExecution`. Spring Batch uses it to record the state needed to continue processing after a restart.

In chunk processing, the framework usually saves the step state at commit boundaries. A reader that supports restart can save the position it has read, the number of records processed, or equivalent information into the Step `ExecutionContext`. After a restart, the reader reads that state back and continues from an appropriate position.

For example, with a file of 1,000 lines and a chunk size of 100:

```text
Chunk 1: lines   1 - 100  -> written successfully, commit, save checkpoint
Chunk 2: lines 101 - 200  -> written successfully, commit, save checkpoint
Chunk 3: lines 201 - 300  -> error before commit, rollback
                           |
                           v
                       RESTART
                           |
                           v
              continue from the checkpoint after line 200
```

This example assumes the reader can save and restore state, the earlier chunks have committed, and the write resource takes part in the corresponding transaction. If the reader does not save state, or the write operation is outside the transaction, the result may differ.

### ItemStream and restartable readers

Some of Spring Batch's built-in readers support saving state. Components of the `ItemStream` type have a lifecycle of `open`, `update`, and `close`. The framework calls `update` so the component writes its state into the `ExecutionContext` before the checkpoint is saved.

For a custom-written reader, if you want to support restart, implement `ItemStream` or a corresponding abstraction such as `ItemStreamReader`, save the necessary state in `update` and restore it in `open`. The state must be sufficient to determine the next read position consistently.

An example file reader configuration for Spring Batch 5:

```java
@Bean
@StepScope
FlatFileItemReader<String> orderFileReader(
        @Value("#{jobParameters['inputFile']}") String inputFile) {

    return new FlatFileItemReaderBuilder<String>()
            .name("orderFileReader")
            .resource(new FileSystemResource(inputFile))
            .lineMapper((line, lineNumber) -> line)
            .saveState(true)
            .build();
}
```

The reader name needs to be stable so that its state is identified consistently on restart. `saveState(true)` lets the reader save the necessary state. With a custom reader or a reader that does not support checkpoints, the application must design how to save the position and restore it itself.

### Job ExecutionContext and Step ExecutionContext

- **Job ExecutionContext** stores data at the job scope. A later step can use values that an earlier step placed in the job context, through the configured data-passing mechanisms.
- **Step ExecutionContext** stores the step's own state, commonly used for the checkpoints of a reader, writer, or tasklet.

You should not store all business data in the ExecutionContext. Only store the small values needed to restore progress; large data should be stored in an appropriate storage system and referenced by a key or identifier.

## 6. Step configuration affects restart

Two important options are `startLimit` and `allowStartIfComplete`.

### startLimit

`startLimit` limits the number of times a step is allowed to start within a JobInstance. The default value usually allows a very large number of starts. When the limit is exceeded, Spring Batch throws a `StepStartLimitExceededException`.

```java
@Bean
Step importOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<Order> reader,
        ItemWriter<Order> writer) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<Order, Order>chunk(100, transactionManager)
            .reader(reader)
            .writer(writer)
            .startLimit(3)
            .build();
}
```

In the example, the step is allowed to start at most three times within the same JobInstance. This is a limit on the number of step starts, not on the number of items processed or the number of retries of an item. If you design retry at the item level, clearly distinguish the retry policy from the step's start limit.

### allowStartIfComplete

By default, a step that is `COMPLETED` is skipped when restarting the same JobInstance. If a step needs to run again every time the job is restarted, you can enable `allowStartIfComplete(true)`:

```java
@Bean
Step refreshReferenceDataStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager) {

    return new StepBuilder("refreshReferenceDataStep", jobRepository)
            .tasklet((contribution, chunkContext) -> {
                // Refresh the reference data.
                return RepeatStatus.FINISHED;
            }, transactionManager)
            .allowStartIfComplete(true)
            .build();
}
```

This option is useful for a step that needs to refresh reference data, check environment conditions, or prepare resources again each time the job continues. Only enable it when rerunning a completed step is safe. If the step writes business data without a duplicate-prevention mechanism, rerunning can cause unintended side effects.

### preventRestart

A job can be configured to disallow restart with `preventRestart()`:

```java
@Bean
Job oneTimeJob(JobRepository jobRepository, Step oneTimeStep) {
    return new JobBuilder("oneTimeJob", jobRepository)
            .start(oneTimeStep)
            .preventRestart()
            .build();
}
```

When a job is configured this way, rerunning the same JobInstance after a failure is rejected. Only use this option when the business truly does not allow continuing the same instance and there is an appropriate way to handle the failure case.

## 7. A full example: launching and restarting a job

Suppose the order import job has one chunk-oriented step. The `reader` reads the file, the `processor` validates the data, and the `writer` writes the valid orders into the database.

```java
@Configuration
public class ImportOrdersJobConfiguration {

    @Bean
    Job importOrdersJob(JobRepository jobRepository, Step importOrdersStep) {
        return new JobBuilder("importOrdersJob", jobRepository)
                .start(importOrdersStep)
                .build();
    }

    @Bean
    Step importOrdersStep(
            JobRepository jobRepository,
            PlatformTransactionManager transactionManager,
            ItemReader<Order> reader,
            ItemProcessor<Order, Order> processor,
            ItemWriter<Order> writer) {

        return new StepBuilder("importOrdersStep", jobRepository)
                .<Order, Order>chunk(100, transactionManager)
                .reader(reader)
                .processor(processor)
                .writer(writer)
                .startLimit(3)
                .build();
    }
}
```

The code illustrates configuring a step with a start limit of three. The `reader`, `processor`, `writer`, `JobRepository`, and transaction manager beans are assumed to have been configured in the application.

First launch:

```java
JobParameters parameters = new JobParametersBuilder()
        .addString("inputFile", "data/orders-2026-11-15.csv", true)
        .addString("businessDate", "2026-11-15", true)
        .toJobParameters();

JobExecution firstExecution = jobLauncher.run(importOrdersJob, parameters);
```

Suppose `firstExecution` ends with `BatchStatus.FAILED`. After determining that the cause of the error has been handled, you can call the job again with the same identifying parameters:

```java
JobExecution restartedExecution = jobLauncher.run(importOrdersJob, parameters);
```

Spring Batch looks up the corresponding JobInstance in the JobRepository. If the instance is allowed to restart, the framework creates a new JobExecution and re-executes the necessary step. A reader that supports checkpoints can continue from the saved state.

In practice, `JobLauncher.run` can run synchronously or asynchronously depending on the configuration. With an asynchronous launcher, you need to look up the execution status from the repository instead of assuming the job has completed right after the method returns.

## 8. Restarting with JobOperator

In a real operational application, you may need an administration screen or a supporting process to select a failed execution to restart. `JobOperator` provides a high-level operational API, including a restart operation based on the execution ID.

A typical flow:

1. Use `JobExplorer` or an administration interface to find the failed JobExecution.
2. Check the JobInstance, JobParameters, the status of the steps, and the cause of the error.
3. Handle the cause of the error, for example restoring the database connection or putting the input file back in the right place.
4. Call `JobOperator`'s restart operation with the appropriate execution ID.
5. Monitor the newly created JobExecution and the results of the steps.

`JobOperator` suits building remote job management features or operational tools. For simple flows, `JobLauncher` together with JobParameters is enough to launch or restart an instance when the state allows it.

You should not directly edit the metadata tables to force a job to restart. These tables are managed by Spring Batch; manual changes can corrupt the relationships among JobInstance, JobExecution, StepExecution, and ExecutionContext.

## 9. The JobRepository must store durable metadata

Restarting after the application process stops depends on the metadata stored in the `JobRepository`. In a real environment, the repository usually uses a database to store the JobInstance, JobExecution, StepExecution, and ExecutionContext.

If the metadata lives only in memory, the state can be lost when the application restarts or the process ends. In that case the framework no longer has enough information to identify the old instance and recover the checkpoint.

When deploying the application, pay attention to:

- Initialize the correct metadata schema corresponding to the Spring Batch version in use.
- Use a durable datasource for the JobRepository in environments that need to restart across application startups.
- Make sure the application instances participating in the same process see consistent repository metadata.
- Protect the metadata tables from manual deletion or updates outside a controlled administration process.
- Have a backup and retention policy for the metadata that fits the operational requirements.

The JobRepository stores the framework's execution state; it does not itself store all business data or undo every external operation.

## 10. Transactions, rollback, and side effects on restart

Chunk processing usually places the write operation in a transaction. If a chunk fails before commit, the changes in the same transaction can be rolled back. When the step is restarted, the items belonging to the uncommitted chunk can be read and processed again.

This has an important consequence: the processor or writer can be called again for an item that was already processed in a previous execution. Therefore, business operations should be designed to tolerate being performed again.

For example, if the writer writes orders into the database, you can use a unique business key or an appropriate upsert operation to avoid creating two orders for the same code. If the processor sends an email or calls an external API, that operation is not automatically rolled back when the database transaction fails.

Some ways to reduce the risk:

- Use a unique key or an idempotency mechanism in the receiving system.
- Record the processing state by business code so you can detect records that have completed.
- Separate external side effects from the section that can be retried, or use the outbox pattern when appropriate.
- Design the writer so it can reprocess the same data without producing duplicate results.
- Check the actual transaction boundaries of each resource; do not assume that the database and external services participate in the same transaction.

A restart ensures the framework can continue orchestration based on the metadata. The correctness of the data after the rerun still depends on the business design and the recoverability of the integrated components.

## 11. Common scenarios and how to handle them

| Scenario | Possible cause | How to handle |
|---|---|---|
| Rerun but a new JobInstance is created | An identifying parameter changed, for example a new timestamp or UUID. | Reuse exactly the identifying parameters of the instance to restart. |
| Cannot restart a failed job | The job uses `preventRestart()`, the execution is in a state that does not allow restart, or the step has exceeded `startLimit`. | Check the job configuration, the metadata state, and the step's limit. |
| The job reports the instance has completed | The JobInstance already has an execution that ended with the `COMPLETED` status. | If the business needs to process a new period, create new identifying parameters; if you need to rerun a completed step, consider `allowStartIfComplete` in the job design. |
| The step starts again from the beginning | The reader does not save a checkpoint or does not restore state from the ExecutionContext. | Use a reader that supports restart or implement ItemStream to save and restore state. |
| Data is written twice after a restart | The side effects of the earlier chunk were not rolled back or the writer is not idempotent. | Design a business key, idempotency, or an appropriate reconciliation mechanism. |
| A finished step is skipped | This is the default behavior when restarting the same JobInstance. | Only enable `allowStartIfComplete(true)` if the step needs to rerun and is safe to perform again. |
| The step is not allowed to start again | `startLimit` has been exceeded. | Review the limit, the StepExecution history, and the error handling; do not arbitrarily edit the metadata to exceed the limit. |
| State is not found after the application restarts | The repository does not store durable metadata or the metadata was deleted. | Configure the JobRepository to use durable storage and keep the metadata schema intact. |

## 12. A process for operating a safe restart

When a job fails, you should not immediately call it again without understanding the data state. A clear operational process helps avoid repeated errors or creating inconsistent data.

1. **Identify the failed execution:** find the related JobExecution and StepExecution in the metadata or the administration screen.
2. **Check the JobInstance:** confirm the job name and identifying parameters to make sure you are handling the right business period.
3. **Find the cause:** read the logs, the exception, the reader/writer state, and the transaction information of the failed step.
4. **Assess the data written:** determine the last committed chunk and the external side effects that may have occurred.
5. **Fix the cause:** for example fix the input file, restore the service, or adjust the connection configuration.
6. **Check the restart conditions:** does the job allow restart, does the step have starts remaining, can the reader recover, and do the completed steps need to be rerun.
7. **Launch the correct instance again:** reuse the identifying parameters or the appropriate restart operation through JobOperator.
8. **Monitor the result:** check the new JobExecution, the status of each step, the number of items read/written/skipped, and the business data after completion.

You should not delete the metadata to "rerun from scratch" without assessing the impact. Deleting metadata can lose traceability and cause Spring Batch to treat the next run as a new instance, while the business data from the previous run still exists.

## 13. Points to remember

- A restart continues the same `JobInstance`; the restart creates a new `JobExecution`.
- The job name and the identifying `JobParameters` determine the JobInstance. To restart, you must identify the failed instance correctly.
- A job in the `FAILED` or `STOPPED` state can usually be restarted if the configuration allows. A job that is `COMPLETED` cannot be run again as an ordinary restart.
- Completed steps are usually skipped; failed steps are executed again according to the state and configuration.
- `ExecutionContext` and readers that support `ItemStream` help save checkpoints to continue from the committed data.
- `startLimit`, `allowStartIfComplete`, and `preventRestart` directly affect restart behavior.
- The JobRepository needs to store durable metadata if you want to restart after the application or server restarts.
- Operations outside the transaction can be repeated. The reader, writer, and business logic need to be designed to handle reruns safely.

When building a restartable job, treat restart as a design requirement from the start: identify the JobInstance correctly with parameters, store durable metadata, choose a reader with checkpoints, configure the steps appropriately, and make sure write operations are recoverable. That way, a failed execution can be continued in a controlled manner without distorting the business results.
