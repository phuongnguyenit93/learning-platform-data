# Sequential job flow and conditional flow

In Spring Batch, a job usually consists of multiple steps and needs to specify the execution order among them. For a linear process, the steps run one after another in the declared order. For a process with many branches, the next step depends on the result of the previous step or on a decision made while the job is running.

Spring Batch represents these two kinds of control with a job flow. A flow defines the starting point, the transition states, and the conditions for ending the job. A clearly designed flow helps correctly handle the success path, invalid data, technical errors, and cases that need a restart.

## 1. What is a job flow?

A job flow is a graph of processing steps and the transitions between them. Each step is a unit of work; a transition specifies when the flow moves to another step or ends the job.

An example of a simple data import process:

```text
validateInput -> importRecords -> archiveFile
```

An example of a process with a branch:

```text
                     +--> importRecords --> archiveFile
                     |
validateInput -------+
                     |
                     +--> rejectFile
```

In the second example, the result of the input validation decides whether the job imports the data or moves the file to the rejection area. Spring Batch uses the execution result to choose the appropriate transition.

## 2. Sequential flow with start() and next()

When all steps need to run in a fixed order, you can declare the job with `start()` and `next()`. This approach suits simple processes that do not need to branch on the result of each step.

An example using the Spring Batch 5 builder API:

```java
@Bean
Job importOrdersJob(
        JobRepository jobRepository,
        Step validateInputStep,
        Step importOrdersStep,
        Step archiveInputStep) {

    return new JobBuilder("importOrdersJob", jobRepository)
        .start(validateInputStep)
        .next(importOrdersStep)
        .next(archiveInputStep)
        .build();
}
```

The job performs `validateInputStep` first, then `importOrdersStep`, and finally `archiveInputStep`. Each step starts only after the step before it in the sequential flow.

With an ordinary sequential flow, if a step ends in failure, the job ends in failure and the subsequent steps are not performed in that execution. When the job is validly restarted, Spring Batch can skip the completed steps and continue from the step that needs to be rerun.

### When should you use a sequential flow?

- The steps have clear dependencies: validate the data, import the data, and then archive the file.
- Every normal outcome leads to the same next step.
- There is no need to branch by data type, business result, or a custom status.

If a step can return multiple results and each result needs a different path, use a conditional flow.

## 3. Conditional flow with on() and to()

A conditional flow declares transitions based on the step's exit code. Instead of just calling `next()`, we declare which result leads to which step.

The main methods:

| Method | Role |
|---|---|
| `start(step)` | Selects the starting step of the job or flow |
| `on(pattern)` | Selects the transition when the exit code matches the pattern |
| `to(step)` | Moves the flow to the specified step |
| `from(step)` | Declares an additional transition originating from a step already added to the flow |
| `end()` | Ends the job with a completed status |
| `fail()` | Ends the job with a failed status |
| `stop()` | Ends the execution with a stopped status |
| `stopAndRestart(step)` | Stops the execution and specifies the step to start from on restart |

For example, after validating a file, the job can import the data if the validation succeeds, move to a step that handles the rejected file if the data is invalid, or mark the job failed for unexpected results.

```java
@Bean
Job importOrdersJob(
        JobRepository jobRepository,
        Step validateInputStep,
        Step importOrdersStep,
        Step rejectInputStep,
        Step archiveInputStep) {

    return new JobBuilder("importOrdersJob", jobRepository)
        .start(validateInputStep)
            .on("COMPLETED").to(importOrdersStep)
        .from(validateInputStep)
            .on("INVALID_INPUT").to(rejectInputStep)
        .from(validateInputStep)
            .on("*").fail()
        .from(importOrdersStep)
            .on("COMPLETED").to(archiveInputStep)
        .from(importOrdersStep)
            .on("*").fail()
        .from(rejectInputStep)
            .on("COMPLETED").end()
        .from(rejectInputStep)
            .on("*").fail()
        .from(archiveInputStep)
            .on("COMPLETED").end()
        .from(archiveInputStep)
            .on("*").fail()
        .end()
        .build();
}
```

In this example, `INVALID_INPUT` is a business exit code returned by the validation step. It makes it possible to distinguish an invalid file from a technical error such as a lost database connection. If the file is rejected and `rejectInputStep` completes successfully, the job ends with a completed status because the rejection process has finished handling that business case. If the rejection step fails, the job ends in failure.

`on("*")` is the fallback branch for the remaining exit codes. Place the fallback branch after the specific patterns so that special results are handled correctly.

## 4. ExitStatus determines a step's transition

When using `on()` after a step, Spring Batch matches the pattern against the step's **ExitStatus exit code**. This is the result used to control the flow.

`BatchStatus` and `ExitStatus` are related but not the same:

| Concept | Meaning | Example |
|---|---|---|
| `BatchStatus` | The execution status managed by Spring Batch | `COMPLETED`, `FAILED`, `STOPPED` |
| `ExitStatus` | The result code used to describe the result and to control transitions | `COMPLETED`, `FAILED`, `INVALID_INPUT` |

Normally, a successful step has `BatchStatus.COMPLETED` and a default `ExitStatus` of `COMPLETED`. However, a step or listener can supply its own exit code. Therefore, a step may complete in terms of execution while the flow still receives a business result such as `INVALID_INPUT` or `COMPLETED WITH SKIPS`.

For example, if a step returns the exit code `COMPLETED WITH SKIPS`, the transition `on("COMPLETED")` is not an appropriate choice for handling that case separately. Declare a pattern that matches the actual exit code:

```java
.start(importStep)
    .on("COMPLETED WITH SKIPS").to(reviewSkippedRecordsStep)
.from(importStep)
    .on("COMPLETED").to(publishStep)
.from(importStep)
    .on("FAILED").fail()
```

In this example, the data import step can report a result of completed with skipped records, completed normally, or failed. Each result follows its own branch.

### Creating a custom exit code

A step can set a custom exit status in its logic or through a `StepExecutionListener`. An illustrative example:

```java
public class ValidationExitStatusListener implements StepExecutionListener {

    @Override
    public ExitStatus afterStep(StepExecution stepExecution) {
        boolean invalid = stepExecution.getExecutionContext()
            .getBoolean("invalidInput", false);

        if (invalid) {
            return new ExitStatus("INVALID_INPUT");
        }
        return null;
    }
}
```

The listener snippet assumes the validation step has written the `invalidInput` flag into the `ExecutionContext`. When the flag is set, the listener returns the exit code `INVALID_INPUT`; the flow can use `on("INVALID_INPUT")` to select the corresponding branch. In a real application, you need to clearly determine where the flag is set and how to distinguish data errors from system errors.

## 5. Transition patterns and declaration order

`on(pattern)` supports patterns to match the exit code. The most common patterns are:

- `on("COMPLETED")`: matches the exit code `COMPLETED`.
- `on("FAILED")`: matches the exit code `FAILED`.
- `on("INVALID_INPUT")`: matches a custom business exit code.
- `on("*")`: matches all remaining exit codes.

When there are multiple transitions from the same step, declare the specific patterns first and the general pattern afterward. For example:

```java
.from(validateStep).on("INVALID_INPUT").to(rejectStep)
.from(validateStep).on("COMPLETED").to(importStep)
.from(validateStep).on("*").fail()
```

The `*` branch is the fallback. If you place it in a position that causes every result to be handled the same way, the specific branches will no longer have the intended effect. Every exit code that can occur should have a clear path, especially for important jobs.

You should not rely on the step name to infer the transition result. The condition in `on()` is the exit code, so check the exit status the step actually produces when investigating a flow that went down the wrong branch.

## 6. The meaning of end(), fail(), and stop()

When a transition does not lead to another step, it can end the job. How it ends affects the JobExecution status and the restartability of the JobInstance.

| Transition | Result at the job level | How to interpret it operationally |
|---|---|---|
| `end()` | The job ends with `BatchStatus.COMPLETED` | The work is considered complete; the same JobInstance cannot be restarted as an incomplete job |
| `fail()` | The job ends with `BatchStatus.FAILED` | The job failed; the same JobInstance can be restarted if the job allows it and the metadata is valid |
| `stop()` | The job ends with `BatchStatus.STOPPED` | The job is stopped; it can be continued according to the restart rules |
| `stopAndRestart(step)` | The job stops and saves the target step for the restart | On restart, the flow continues from the specified step |

An example of using `end()` is when an invalid file has been successfully moved to the rejection area. From a business perspective, the system has finished handling that request, even though the data import step did not run.

Conversely, if the validation error stems from an inaccessible file system, you should not regard it as a business result that has been handled. The `fail()` transition keeps the JobInstance in a failed state so it can be investigated and restarted when appropriate.

`stop()` is usually used when a controlled pause is needed. `stopAndRestart(step)` is useful when the next run needs to start from a specific step. A restart still depends on the metadata state, the job's restart configuration, and the step's rerun limit.

## 7. Using JobExecutionDecider for runtime decisions

Not every decision stems from the exit code of the immediately preceding step. In some cases you need to choose a branch based on the JobParameters, data in the JobExecution, or a business state computed while the job is running. In that case you can use a `JobExecutionDecider`.

A decider receives the `JobExecution` and `StepExecution` (which can be null in some positions), and then returns a `FlowExecutionStatus`. The flow uses this status name to choose a transition.

An example of choosing a reader by the file type passed in JobParameters:

```java
@Bean
JobExecutionDecider fileTypeDecider() {
    return (jobExecution, stepExecution) -> {
        String fileType = jobExecution.getJobParameters()
            .getString("fileType");

        if ("CSV".equalsIgnoreCase(fileType)) {
            return new FlowExecutionStatus("CSV");
        }
        if ("XML".equalsIgnoreCase(fileType)) {
            return new FlowExecutionStatus("XML");
        }
        return new FlowExecutionStatus("UNSUPPORTED");
    };
}
```

Declaring a flow that uses the decider:

```java
@Bean
Job importFileJob(
        JobRepository jobRepository,
        JobExecutionDecider fileTypeDecider,
        Step importCsvStep,
        Step importXmlStep) {

    return new JobBuilder("importFileJob", jobRepository)
        .start(fileTypeDecider)
            .on("CSV").to(importCsvStep)
        .from(fileTypeDecider)
            .on("XML").to(importXmlStep)
        .from(fileTypeDecider)
            .on("*").fail()
        .from(importCsvStep)
            .on("COMPLETED").end()
        .from(importCsvStep)
            .on("*").fail()
        .from(importXmlStep)
            .on("COMPLETED").end()
        .from(importXmlStep)
            .on("*").fail()
        .end()
        .build();
}
```

Here, `CSV`, `XML`, and `UNSUPPORTED` are statuses returned by the decider. `on("CSV")` and `on("XML")` match the `FlowExecutionStatus`, while the transitions originating from a step match the step's `ExitStatus`. If the file type is not supported, the fallback branch ends the job in failure.

You can use a decider to decide based on the record count, the run mode, the business date, or an earlier validation result. You should keep the decider focused on choosing the branch; the reading, writing, and updating of data should still live in an appropriate step.

## 8. Combining sub-flows and steps

When a process has multiple groups of steps, you can define a separate `Flow` and then reuse that flow in a job or another flow. This helps group related steps into a clearly named unit, such as a data import flow or a reconciliation flow.

A conceptual example:

```java
@Bean
Flow importFlow(
        JobRepository jobRepository,
        Step readStep,
        Step transformStep,
        Step writeStep) {

    return new FlowBuilder<SimpleFlow>("importFlow")
        .start(readStep)
        .next(transformStep)
        .next(writeStep)
        .build();
}
```

A job can use this flow as a component in a larger flow. When the flow has multiple branches, the transitions are declared inside the sub-flow; the job invokes that flow in the same way it orchestrates a flow component.

Splitting out a flow is useful when a group of steps has independent meaning or is reused. For a job with only a few sequential steps, declaring directly with `start()` and `next()` is usually easier to read.

## 9. Restart and conditional flow

Flow and restart work together with the metadata stored in the JobRepository. When restarting a JobInstance after an error or a stop:

1. Spring Batch creates a new JobExecution for the same JobInstance.
2. Completed steps are usually skipped, unless configured to rerun with `allowStartIfComplete(true)`.
3. The transitions are evaluated based on the status and exit code of the steps in the flow.
4. Steps that have not completed are executed again; steps that support checkpoints can restore state from the `ExecutionContext`.

This means a branch chosen in the previous run can continue to affect the path on restart. Therefore, the exit code and the data that decide the branch should be stored and managed consistently. If the branch selection logic depends on external data that changes over time, you need to clearly determine whether a restart must reuse the old decision or recompute it from the new data.

You should not add a new identifying JobParameter just to force the flow to rerun from the beginning when an execution fails. Doing so creates a different JobInstance and separates the run from the restart history of the old work. If you need a new business processing run, create a new identifier deliberately.

## 10. Common mistakes when designing flows

| Mistake | Consequence | How to handle |
|---|---|---|
| Using `next()` even though a step has multiple results that need branching | Cannot clearly express the paths by result | Use `on()` and explicit transitions |
| Checking only `BatchStatus` while the flow needs to distinguish business results | Confusing the execution status with the exit code that controls the flow | Design and check the `ExitStatus` |
| Using `on("*")` too early | The fallback branch shadows specific cases | Declare specific patterns first, wildcard afterward |
| Using `end()` for a technical error | The job is marked completed and is not restartable as a failed instance | Use `fail()` for errors that need investigation or restart |
| Treating invalid data as a system error | The reported job status does not correctly reflect the business result | Use a separate business exit code such as `INVALID_INPUT` |
| Not declaring a path for an exit code that can occur | The flow has no appropriate transition and the job may fail | List the results and add an appropriate fallback branch |
| Putting too much business logic into a decider | Hard to test and hard to follow the decision | Let the decider choose the branch, while data processing lives in the step |

When debugging, look at the step's exit code, the transition that matched, the JobExecution status, and the StepExecution history. Logging an individual step name is usually not enough to explain why the flow chose a particular branch.

## 11. How to choose a flow type

| Need | Suitable implementation |
|---|---|
| Run the steps in a fixed order | `start(stepA).next(stepB).next(stepC)` |
| Branch by a step's result | `start(step).on(...).to(...)` and `from(step).on(...).to(...)` |
| Choose a branch by JobParameters or runtime data | `JobExecutionDecider` |
| Group steps for reuse | Define a separate `Flow` |
| Pause and continue from a chosen step | `stopAndRestart(step)` with an appropriate restart configuration |

A sequential flow is suitable when the process always follows the same path. A conditional flow is suitable when the processing result determines the next step. A decider adds the ability to choose a branch from runtime information not directly tied to a step's exit code. Whichever approach you use, each path should have a clear ending and correctly reflect the business meaning of the result.

## Conclusion

Spring Batch supports sequential flow with `start()` and `next()`, while conditional flow is built from `on()` and `to()` transitions. Step transitions are based on `ExitStatus`; `end()`, `fail()`, and `stop()` determine the job's end status. When a decision based on runtime information is needed, `JobExecutionDecider` returns a `FlowExecutionStatus` to choose a branch.

A job flow that is easy to operate needs to distinguish business results from technical errors, declare specific branches before the wildcard, handle every possible result, and keep restart behavior consistent with the stored metadata.
