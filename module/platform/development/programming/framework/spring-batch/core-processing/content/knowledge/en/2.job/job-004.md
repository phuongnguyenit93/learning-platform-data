# JobParameters take part in determining the instance

In Spring Batch, a Job call does not necessarily create a new JobInstance. The framework uses the Job name and the JobParameters marked as **identifying** to determine which logical run is being requested. This mechanism lets Spring Batch recognize a new run with different business data, and also recognize when a Job is being restarted after a failed run.

Understanding the role of JobParameters correctly helps you design restartability, avoid running the same data twice, and look up metadata accurately.

## 1. Distinguishing Job, JobInstance, and JobExecution

These three concepts describe three different layers of processing:

| Concept | Meaning |
| --- | --- |
| **Job** | The definition of a batch process, consisting of Steps and the configuration that controls execution |
| **JobInstance** | One logical run of a Job for a specific set of identifying parameters |
| **JobExecution** | One specific execution of a JobInstance; an instance can have multiple executions when a restart is needed |

For example, the system has a Job named **dailyOrderImport**. This Job imports order data by day. For the business date 15/11/2026, the logical run is identified by the Job name and the identifying parameter **businessDate=2026-11-15**.

If the first run fails midway, a restart with the same Job name and the same identifying parameters still belongs to **that JobInstance**. Spring Batch creates a new JobExecution to record the next attempt. If it runs for 16/11/2026, that is a different JobInstance.

You can picture the relationship as follows:

~~~text
Job: dailyOrderImport
    |
    +-- JobInstance: businessDate=2026-11-15
    |       |
    |       +-- JobExecution #1: FAILED
    |       |
    |       +-- JobExecution #2: COMPLETED  (successful restart)
    |
    +-- JobInstance: businessDate=2026-11-16
            |
            +-- JobExecution #1: COMPLETED
~~~

Therefore, you should not equate "one JobLauncher call" with "one JobInstance". A JobInstance represents the business scope to be processed; a JobExecution records each execution of that scope.

## 2. The formula for determining a JobInstance

Conceptually, Spring Batch determines a JobInstance by:

~~~text
JobInstance = Job name + identifying JobParameters
~~~

Both components matter:

- **The Job name** identifies which Job definition is requested. Two Jobs with different names are two different JobInstances, even when they receive the same parameters.
- **The identifying JobParameters** determine the data scope or business work of the instance. Only the parameters marked identifying take part in distinguishing instances.

JobParameters is a collection of JobParameters that have a name, a value, a data type, and an identifying flag. Each parameter can be marked:

- **identifying = true**: the value takes part in determining the JobInstance.
- **identifying = false**: the value is provided to the run and stored in the metadata, but does not change the JobInstance identity.

Spring Batch uses the identifying parameters to create the JobInstance key in the JobRepository. The application usually does not need to create or compute this key itself; what is necessary is to choose the right identifying parameters and pass the same values again on a restart.

## 3. Which parameters should be identifying?

A parameter should be identifying when changing its value means the Job is processing **a different business scope**. A parameter that only serves recording or operational control can usually be non-identifying, as long as it does not change the business result.

| Parameter | Typical marking | Reason |
| --- | --- | --- |
| **businessDate** | Identifying | Each business date is a separate data scope |
| **inputFileId** or an immutable file name | Identifying | Each input file represents a data set to be processed |
| **tenantId** | Identifying | Each tenant's data is a separate scope |
| **requestedBy** | Non-identifying | The person or system that triggers the run usually only serves auditing |
| **correlationId** | Non-identifying | Used to link logs or requests, does not determine business data |
| **notificationEmail** | Non-identifying | Used only to send notifications, provided it does not change the processing result |
| **dryRun** | Depends on semantics | If this mode changes behavior or a result that needs to be distinguished, mark it identifying |

There is no fixed rule that a specific type of data must always be identifying. The decision depends on the business meaning of the parameter in the Job.

For example: if **requestedBy** only records who pressed the run button, two requests from two different people can still be the same data import. In that case this parameter should be non-identifying. Conversely, if **tenantId** is left out of the identity, two runs for two tenants may be treated as the same JobInstance. This is usually a wrong design because the data scopes are already different.

### Creating JobParameters with an explicit identifying flag

You can use **JobParametersBuilder** to declare each parameter together with its identifying flag:

~~~java
JobParameters parameters = new JobParametersBuilder()
        .addString("businessDate", "2026-11-15", true)
        .addString("inputFileId", "orders-2026-11-15", true)
        .addLong("tenantId", 42L, true)
        .addString("requestedBy", "scheduler", false)
        .addString("correlationId", "request-8f31", false)
        .toJobParameters();
~~~

In the example:

- **businessDate**, **inputFileId**, and **tenantId** determine the JobInstance.
- **requestedBy** and **correlationId** can still be read in the Job or Step, but changing them does not create a new JobInstance.

The **addString**, **addLong** overloads and the corresponding methods that take a boolean parameter let you set this flag directly. When you need to control the instance identity, declare the flag explicitly instead of relying on the builder's default overload.

After creating the parameters, the Job is launched through the JobLauncher:

~~~java
JobExecution execution = jobLauncher.run(dailyOrderImport, parameters);
~~~

The JobLauncher passes the request to the JobRepository. The repository looks up the JobInstance by the Job name and the identifying parameters, and then decides whether to create a new instance or create an execution for an existing instance.

## 4. How do the same and different identifying parameters affect things?

Suppose a Job is named **dailyOrderImport** and uses two parameters:

~~~java
JobParameters firstRun = new JobParametersBuilder()
        .addString("businessDate", "2026-11-15", true)
        .addString("requestedBy", "scheduler", false)
        .toJobParameters();
~~~

Common cases:

| Call | Job name | **businessDate** | **requestedBy** | Identity result |
| --- | --- | --- | --- | --- |
| A | dailyOrderImport | 2026-11-15 | scheduler | Create or find instance A |
| B | dailyOrderImport | 2026-11-15 | operator | Still instance A |
| C | dailyOrderImport | 2026-11-16 | scheduler | New instance |
| D | monthlyOrderImport | 2026-11-15 | scheduler | New instance because the Job name is different |

In call B, **requestedBy** changes but it is a non-identifying parameter. Spring Batch still considers the request to belong to instance A. In call C, **businessDate** changes, so the business scope changes and a new JobInstance is determined.

The point to remember is that a non-identifying parameter can still be used in the Job logic. The identifying flag only controls how the repository identifies the instance; it does not automatically make the parameter disappear from the JobParameters.

## 5. The relationship between identifying parameters and restart

Restart is an important reason Spring Batch needs to distinguish JobInstance from JobExecution.

Suppose a Job imports a file for 15/11/2026. The first run created a JobInstance with **businessDate=2026-11-15**, but the Step that processes the file failed and the JobExecution ended in the **FAILED** state.

When restarting, the application needs to pass the same Job name and the same identifying values. If the Job is configured to allow restart, the JobRepository recognizes this as an existing instance and creates the next JobExecution for that instance. Spring Batch can rely on the saved execution context to continue from an appropriate state.

~~~text
First run:
  dailyOrderImport
  businessDate = 2026-11-15
        |
        v
  JobInstance A
        |
        v
  JobExecution #1 -> FAILED

Restart with the same identifying parameters:
  dailyOrderImport
  businessDate = 2026-11-15
        |
        v
  JobInstance A
        |
        v
  JobExecution #2 -> continue / complete
~~~

The previous state affects the result of the next launch:

- If the previous execution is running, the repository usually rejects a duplicate launch with a **JobExecutionAlreadyRunningException**.
- If the JobInstance has completed, launching again with the same identifying parameters is usually rejected with a **JobInstanceAlreadyCompleteException**.
- If the previous execution failed or stopped and the Job allows restart, Spring Batch can create a new JobExecution for the same JobInstance.
- If the Job is configured not to allow restart, a restart request can be rejected with a **JobRestartException**.

Therefore, changing a non-identifying parameter does not create a new instance and is also not a way to rerun a completed JobInstance. To process a new business scope, pass a new set of identifying parameters that correctly reflects that scope.

### Restart and running a new instance are two different purposes

If the input file for a given day failed to process, you usually need to restart that same JobInstance. If the system receives a new business file, you need to create a new instance with a new identifying parameter, such as **inputFileId**.

You should not add a random timestamp or UUID to the identifying group just to avoid the "instance already completed" error. That makes every call a different JobInstance, so Spring Batch can no longer recognize a restart request for the earlier run.

## 6. Passing JobParameters into Job and Step logic

Both identifying and non-identifying parameters are data in the JobParameters. Both can be read in components with an appropriate scope, for example a **@StepScope** bean.

~~~java
@Bean
@StepScope
public FlatFileItemReader<Order> orderReader(
        @Value("#{jobParameters['inputFile']}") String inputFile) {

    return new FlatFileItemReaderBuilder<Order>()
            .name("orderReader")
            .resource(new FileSystemResource(inputFile))
            .delimited()
            .names("orderId", "amount")
            .targetType(Order.class)
            .build();
}
~~~

In this example, **inputFile** is obtained from the JobParameters when the Step runs. If the file determines the data set to import, the parameter representing the file should be marked identifying. The marking does not change how the value is accessed through the **jobParameters** expression.

One important point: Spring Batch identifies the instance based on the **parameter values that are passed in**, not by reading the file's content to determine identity. If the file at the same path has its content replaced but the JobParameters stay the same, the repository still treats it as the same JobInstance. For input that can be replaced, use an immutable identifier such as a file ID, a data version, or a checksum that suits the business process.

## 7. The role of RunIdIncrementer

**RunIdIncrementer** is a convenient mechanism for creating the next set of JobParameters by incrementing the **run.id** parameter. This parameter is commonly used to request a new JobInstance for each subsequent run.

Example Job configuration:

~~~java
@Bean
public Job dailyOrderImport(
        JobRepository jobRepository,
        Step importOrdersStep) {

    return new JobBuilder("dailyOrderImport", jobRepository)
            .incrementer(new RunIdIncrementer())
            .start(importOrdersStep)
            .build();
}
~~~

When a client uses a mechanism such as **JobOperator.startNextInstance** to request the next instance, the incrementer creates the next set of parameters with **run.id** incremented. Because **run.id** is added as an identifying parameter, the new value changes the JobInstance identity.

**RunIdIncrementer** does not mean that every call to **JobLauncher.run(job, parameters)** automatically increments **run.id**. With **JobLauncher.run**, the application passes the exact JobParameters set it wants to use. If you pass the old set of identifying parameters again, the request still points to the old JobInstance.

Clearly distinguish the two intents:

- **Restarting an unfinished run:** reuse the identifying parameters of the current JobInstance.
- **Starting a new logical run:** provide new identifying parameters, possibly through an incrementer if the operational process requires it.

## 8. Observing instance identity in the JobRepository

The JobRepository stores metadata to track JobInstances and JobExecutions. In the default schema, the two tables usually of interest are:

- **BATCH_JOB_INSTANCE**: stores the Job name and the JobInstance key.
- **BATCH_JOB_EXECUTION**: stores each JobExecution and links it to **JOB_INSTANCE_ID**.

You can query to see the executions that belong to the same instance:

~~~sql
SELECT
    ji.JOB_INSTANCE_ID,
    ji.JOB_NAME,
    je.JOB_EXECUTION_ID,
    je.STATUS
FROM BATCH_JOB_INSTANCE ji
LEFT JOIN BATCH_JOB_EXECUTION je
    ON je.JOB_INSTANCE_ID = ji.JOB_INSTANCE_ID
WHERE ji.JOB_NAME = 'dailyOrderImport'
ORDER BY ji.JOB_INSTANCE_ID, je.JOB_EXECUTION_ID;
~~~

If a JobInstance has multiple JobExecutions, it can be a sign that the Job has been restarted or that multiple executions have been recorded for the same business scope. Look at the status of each execution and its run time to understand the history.

Table names can change if the application configures a different table prefix. The column structure and how parameters are stored can also differ between Spring Batch versions, so when writing queries for operations, check them against the schema the application is using.

## 9. Common design mistakes

### Putting the current timestamp into the identifying group

If every call passes **runTime=now()** and marks it identifying, every call creates a different identity. After the Job fails, the next call with a new timestamp may create a new JobInstance instead of restarting the old instance.

Use time as an identifying parameter only when that moment genuinely defines a separate business scope, for example an hourly data window. If you only need to record the request time, leave it non-identifying or store it in an audit system.

### Omitting the parameter that defines the data scope

If a Job processes by day but **businessDate** is non-identifying, two different days may be treated as the same instance. A later run may hit the "instance already completed" state or reuse the history of the previous data scope.

Fully identify the business dimensions that make up one processing run, such as the date, tenant, file code, or data type, and then mark them identifying.

### Treating a file path as a content identifier

A path can point to different content at different times. The repository does not detect on its own that the file content has changed. If replacing the content means a new import, you need to pass an additional version identifier or an immutable file code.

### Using operational parameters to split instances

Values such as **requestedBy**, **hostName**, and **correlationId** usually should not be identifying if they do not change the processing scope. Marking them identifying can create multiple instances for the same business work and make tracking restarts harder.

### Thinking that changing a non-identifying parameter creates a new run

Changing **requestedBy** or **correlationId** does not change the JobInstance. If the instance has completed, changing these parameters does not let you rerun the same instance. Clearly determine whether the request is a restart or a new business job.

### Changing the type or meaning of a parameter between runs

A JobParameter has a data type. Pass the same key with a stable type and meaning between runs, especially when a restart is needed. Avoid passing a code as a number one time and as a string another time if the two values represent the same concept.

In addition, JobParameters are stored in the JobRepository metadata. You should not put passwords, access tokens, or secrets directly into JobParameters; use an appropriate configuration and secret management mechanism and only pass the necessary reference.

## 10. A process for choosing identifying parameters

When designing a new Job, you can answer the following questions in turn:

1. **Which Job is running?** Choose a stable, meaningful Job name.
2. **What distinguishes one business processing run?** List values such as the business date, tenant, file ID, period code, or data version.
3. **If a value changes, does it mean processing a different business scope?** If so, that parameter should usually be identifying.
4. **Is the value only for audit, tracing, or notification?** If it does not change the business scope and result, it should usually be non-identifying.
5. **On a restart, can the system recreate the exact original set of identifying parameters?** If not, you need to store or recreate those values in a stable way.
6. **Can the external input change under the same identifier?** If so, add a version or an immutable ID to distinguish the data sets.

After choosing, you should create the JobParameters at the launch boundary, pass them into the JobLauncher, and use the same convention in restart flows. Validating required parameters with a JobParametersValidator is still useful, but validation and identifying are two separate responsibilities: the validator checks the validity of the input data, while the identifying flag determines the JobInstance identity.

## Conclusion

JobParameters take part in determining the JobInstance through the identifying flag. By combining the Job name with the identifying parameters, Spring Batch distinguishes a new processing scope from a restart of an existing scope. Choosing the right identifying parameters makes the metadata correctly reflect the business, supports restart, and prevents accidentally treating two different data sets as the same run.
