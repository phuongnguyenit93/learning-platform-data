# Root tag và fragment trong XML

Khi xử lý XML bằng Spring Batch, một file thường có một phần tử gốc bao quanh nhiều phần tử con. Mỗi phần tử con có thể đại diện cho một bản ghi nghiệp vụ cần đọc, xử lý và ghi riêng. Vì vậy, cần phân biệt **document root** của toàn bộ file với **fragment root** của từng bản ghi.

Spring Batch cung cấp StaxEventItemReader để đọc XML theo từng fragment. Reader nhận tên phần tử bắt đầu một fragment, lấy nội dung XML tương ứng và chuyển fragment thành object thông qua một OXM Unmarshaller, chẳng hạn JAXB. Cách này cho phép một file XML lớn được xử lý theo chunk mà không cần nạp toàn bộ tài liệu thành một object duy nhất.

## 1. Cấu trúc document root và fragment

Một tài liệu XML well-formed có đúng một document element, thường gọi là root element. Root element bao quanh các phần tử khác và tạo cấu trúc tổng thể của tài liệu.

Ví dụ:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <metadata>
        <source>ERP</source>
        <businessDate>2026-11-15</businessDate>
    </metadata>

    <order>
        <orderId>ORD-1001</orderId>
        <customerId>C-001</customerId>
        <amount>125000.00</amount>
    </order>

    <order>
        <orderId>ORD-1002</orderId>
        <customerId>C-002</customerId>
        <amount>98000.00</amount>
    </order>
</orders>
~~~

Trong ví dụ:

- orders là document root của toàn bộ file.
- metadata chứa thông tin chung của file.
- Mỗi order là một fragment đại diện cho một bản ghi đơn hàng.
- orderId, customerId và amount là các phần tử dữ liệu bên trong fragment.

Khi muốn mỗi đơn hàng trở thành một item của Spring Batch, fragment root cần là order. Reader sẽ lấy từng phần tử order và chuyển thành một object Order. Phần tử orders chỉ là wrapper của tài liệu, không phải item cần ghi trong ví dụ này.

| Khái niệm | Vai trò | Ví dụ |
|---|---|---|
| XML document | Toàn bộ tài liệu XML | File orders.xml |
| Document root | Phần tử gốc duy nhất của tài liệu | orders |
| Fragment | Một đoạn XML được tách ra làm đơn vị đọc | Một phần tử order cùng nội dung con |
| Fragment root | Phần tử bắt đầu mỗi fragment | order |
| Child element | Trường dữ liệu bên trong fragment | orderId, customerId, amount |

Tên fragment root thường lặp lại nhiều lần trong tài liệu, còn document root chỉ xuất hiện một lần. Chọn đúng fragment root quyết định ranh giới item mà reader trả về.

## 2. Fragment là gì trong Spring Batch?

Trong ngữ cảnh StaxEventItemReader, fragment là phần XML bắt đầu tại một phần tử được cấu hình làm fragment root và kết thúc khi phần tử đó được đóng tương ứng. Fragment được chuyển cho Unmarshaller để tạo ra một item.

Ví dụ với file có 1.000 phần tử order:

~~~text
orders
  metadata
  order 1  -> item 1
  order 2  -> item 2
  order 3  -> item 3
  ...
  order 1000 -> item 1000
~~~

Reader không cần trả toàn bộ orders thành một object duy nhất. Nó lần lượt trả từng Order để processor và writer xử lý theo chunk.

Một fragment có thể chứa nhiều phần tử con, phần tử lồng nhau, thuộc tính XML và text. Unmarshaller chịu trách nhiệm ánh xạ cấu trúc fragment sang Java object.

Ví dụ:

~~~xml
<order id="ORD-1001" status="NEW">
    <customer>
        <id>C-001</id>
        <name>An Nguyen</name>
    </customer>
    <lines>
        <line>
            <sku>SKU-01</sku>
            <quantity>2</quantity>
        </line>
        <line>
            <sku>SKU-02</sku>
            <quantity>1</quantity>
        </line>
    </lines>
</order>
~~~

Toàn bộ phần tử order, bao gồm customer và lines, là một fragment. Hai phần tử line không tự động trở thành hai item riêng nếu fragment root được cấu hình là order.

Nếu muốn mỗi line là một item, cần chọn fragment root phù hợp với cấu trúc nghiệp vụ hoặc xây dựng reader/processor riêng để tách các line từ Order.

## 3. StaxEventItemReader đọc fragment như thế nào?

StaxEventItemReader sử dụng StAX (Streaming API for XML) để đọc sự kiện XML theo luồng. Nó tìm phần tử có tên khớp với fragment root được cấu hình, gom sự kiện của fragment đó và chuyển fragment tới Unmarshaller.

Luồng tổng quát:

~~~text
XML Resource
    |
    v
StAX XMLInputFactory / XMLEventReader
    |
    v
Tìm fragment root đã cấu hình
    |
    v
Thu thập sự kiện đến thẻ đóng tương ứng
    |
    v
XML fragment
    |
    v
OXM Unmarshaller (ví dụ JAXB)
    |
    v
Java item
    |
    v
ItemProcessor
    |
    v
ItemWriter
~~~

Streaming giúp tránh phải xây dựng toàn bộ document tree trong bộ nhớ. Sau khi một fragment được unmarshalling, reader có thể tiếp tục tìm fragment tiếp theo.

StAX là mô hình đọc theo sự kiện. Nó khác với cách parse toàn bộ XML thành DOM, nơi ứng dụng thường giữ một cây node lớn trong bộ nhớ. Với file lớn có nhiều record, xử lý theo fragment thường tiết kiệm bộ nhớ hơn.

## 4. Cấu hình fragmentRootElementName

StaxEventItemReader cần biết phần tử nào đại diện cho một item. Trong Java configuration, dùng StaxEventItemReaderBuilder và cấu hình fragmentRootElementName:

~~~java
@Bean
StaxEventItemReader<Order> orderReader(
        Resource orderResource,
        Unmarshaller orderUnmarshaller) {

    return new StaxEventItemReaderBuilder<Order>()
            .name("orderReader")
            .resource(orderResource)
            .addFragmentRootElements("order")
            .unmarshaller(orderUnmarshaller)
            .saveState(true)
            .strict(true)
            .build();
}
~~~

Một số phiên bản Spring Batch cung cấp API builder với tên fragmentRootElementName(String); các phiên bản mới có thể cung cấp biến thể addFragmentRootElements(String...). Hãy dùng đúng API của phiên bản dependency trong dự án. Ý nghĩa cấu hình vẫn là chỉ định phần tử XML làm ranh giới của item.

Với API fragmentRootElementName:

~~~java
return new StaxEventItemReaderBuilder<Order>()
        .name("orderReader")
        .resource(orderResource)
        .fragmentRootElementName("order")
        .unmarshaller(orderUnmarshaller)
        .saveState(true)
        .build();
~~~

Trong ví dụ, reader trả từng phần tử order. Nếu cấu hình nhầm thành orders, reader có thể coi toàn bộ phần tử wrapper là một fragment và Unmarshaller phải ánh xạ toàn bộ document root. Điều này thay đổi hoàn toàn số lượng item và cách ánh xạ dữ liệu.

Đối với XML có nhiều loại phần tử con, hãy chọn fragment root đại diện cho đơn vị nghiệp vụ cần xử lý. Không chọn một tag chỉ vì nó xuất hiện thường xuyên; cần xem ranh giới transaction và output mong muốn.

## 5. Tạo Unmarshaller bằng JAXB

StaxEventItemReader không tự quyết định cách chuyển XML thành object. Nó cần một OXM Unmarshaller. Một lựa chọn phổ biến là Jaxb2Marshaller của Spring OXM.

Ví dụ model:

~~~java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {

    private String orderId;
    private String customerId;
    private BigDecimal amount;

    public String getOrderId() {
        return orderId;
    }

    public String getCustomerId() {
        return customerId;
    }

    public BigDecimal getAmount() {
        return amount;
    }
}
~~~

Khai báo JAXB marshaller:

~~~java
@Bean
Jaxb2Marshaller orderUnmarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Order.class);
    return marshaller;
}
~~~

Sau đó truyền marshaller vào StaxEventItemReader:

~~~java
@Bean
StaxEventItemReader<Order> orderReader(
        @Value("file:/data/orders.xml") Resource resource,
        Jaxb2Marshaller orderUnmarshaller) {

    return new StaxEventItemReaderBuilder<Order>()
            .name("orderReader")
            .resource(resource)
            .fragmentRootElementName("order")
            .unmarshaller(orderUnmarshaller)
            .saveState(true)
            .build();
}
~~~

Model và annotation JAXB phải khớp với XML thực tế. Nếu XML có attribute, namespace, phần tử lồng nhau hoặc danh sách line, model cần khai báo tương ứng. Không nên giả định chỉ cần khai báo fragment root là Spring tự tạo được object mà không có mapping.

Với ứng dụng Spring Boot 3/Spring Framework 6, cần dùng JAXB API tương thích Jakarta. Dự án cũ có thể dùng javax JAXB. Không trộn hai namespace annotation vì JAXB runtime có thể không nhận diện model.

## 6. Ánh xạ XML có phần tử lồng nhau

Một fragment thường có cấu trúc nhiều tầng. Ví dụ:

~~~xml
<order>
    <orderId>ORD-1001</orderId>
    <customer>
        <customerId>C-001</customerId>
        <name>An Nguyen</name>
    </customer>
    <lines>
        <line>
            <sku>SKU-01</sku>
            <quantity>2</quantity>
            <unitPrice>15000.00</unitPrice>
        </line>
        <line>
            <sku>SKU-02</sku>
            <quantity>1</quantity>
            <unitPrice>25000.00</unitPrice>
        </line>
    </lines>
</order>
~~~

Có thể ánh xạ sang các class:

~~~java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {

    private String orderId;
    private CustomerInfo customer;

    @XmlElementWrapper(name = "lines")
    @XmlElement(name = "line")
    private List<OrderLine> lines;
}

@XmlAccessorType(XmlAccessType.FIELD)
public class CustomerInfo {
    private String customerId;
    private String name;
}

@XmlAccessorType(XmlAccessType.FIELD)
public class OrderLine {
    private String sku;
    private int quantity;
    private BigDecimal unitPrice;
}
~~~

Một fragment order được chuyển thành một Order có một CustomerInfo và danh sách OrderLine. Processor có thể kiểm tra tổng tiền, tính thuế hoặc chuyển đổi sang model database.

Nếu danh sách con rất lớn và cần xử lý độc lập, unmarshalling toàn bộ danh sách vào một Order có thể dùng nhiều bộ nhớ. Khi đó, hãy cân nhắc chọn line làm đơn vị fragment nếu cấu trúc cho phép, hoặc viết một reader streaming tùy chỉnh để giữ được ngữ cảnh order trong khi phát từng line.

## 7. XML có namespace

XML có thể dùng namespace mặc định:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders xmlns="urn:example:orders">
    <order>
        <orderId>ORD-1001</orderId>
        <amount>125000.00</amount>
    </order>
</orders>
~~~

Hoặc dùng prefix:

~~~xml
<ord:orders xmlns:ord="urn:example:orders">
    <ord:order>
        <ord:orderId>ORD-1001</ord:orderId>
        <ord:amount>125000.00</ord:amount>
    </ord:order>
</ord:orders>
~~~

Namespace URI là phần định danh namespace; prefix chỉ là bí danh trong tài liệu. Hai prefix khác nhau vẫn có thể đại diện cùng một namespace URI.

Khi dùng JAXB, model cần khai báo namespace phù hợp. Ví dụ:

~~~java
@XmlRootElement(name = "order", namespace = "urn:example:orders")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {
    @XmlElement(namespace = "urn:example:orders")
    private String orderId;
}
~~~

Việc chọn fragment root trong XML có namespace cần được kiểm tra với phiên bản Spring Batch và XMLInputFactory đang dùng. Một số API cấu hình nhận tên fragment dạng String và việc so khớp có thể phụ thuộc cách implementation xử lý QName/local name. Không nên chỉ thử với XML không namespace rồi giả định file namespace sẽ hoạt động giống hệt.

Hãy tạo integration test bằng chính XML có namespace của hệ thống, xác nhận reader nhận được đúng số fragment và JAXB map đúng trường. Nếu có nhiều namespace hoặc namespace prefix thay đổi, dựa vào namespace URI và mapping JAXB thay vì phụ thuộc prefix cố định.

## 8. Document root không phải lúc nào cũng là fragment root

Một lỗi cấu hình phổ biến là chọn document root thay vì phần tử đại diện cho item.

Ví dụ file:

~~~xml
<catalog>
    <generatedAt>2026-11-15T10:00:00Z</generatedAt>
    <products>
        <product>
            <sku>P-001</sku>
            <name>Keyboard</name>
        </product>
        <product>
            <sku>P-002</sku>
            <name>Mouse</name>
        </product>
    </products>
</catalog>
~~~

Nếu mỗi product là một item, fragment root phải là product. catalog là document root; products là container trung gian.

| Tag | Vai trò | Có nên làm fragment root? |
|---|---|---|
| catalog | Document root | Không, nếu muốn từng product là item |
| generatedAt | Metadata của file | Không |
| products | Container danh sách | Chỉ khi muốn một item chứa toàn bộ danh sách |
| product | Bản ghi sản phẩm | Có, nếu mỗi sản phẩm là item |

Chọn fragment root quá cao làm item lớn, có thể tăng bộ nhớ và làm mất lợi ích chunk processing. Chọn quá thấp có thể làm mất ngữ cảnh cha cần thiết để hiểu dữ liệu con.

## 9. Fragment root và phần tử lồng nhau cùng tên

Một XML phức tạp có thể có các phần tử cùng tên ở nhiều cấp:

~~~xml
<orders>
    <order>
        <orderId>ORD-1</orderId>
        <relatedOrders>
            <order>
                <orderId>ORD-OLD-1</orderId>
            </order>
        </relatedOrders>
    </order>
</orders>
~~~

Nếu tag order xuất hiện lồng nhau, cần xác định reader xử lý fragment boundary như thế nào trong phiên bản framework đang dùng. Không nên giả định mọi phần tử cùng local name đều luôn được coi là item cấp ngoài theo ý muốn nghiệp vụ.

Để tránh mơ hồ:

- Thiết kế XML dùng tên phần tử khác nhau cho record chính và record lồng nhau nếu có thể.
- Kiểm tra cấu trúc XML và mức lồng nhau bằng fixture thực tế.
- Viết test xác nhận số item mà reader trả về.
- Nếu cần phân biệt theo đường dẫn cha/con, dùng reader tùy chỉnh hoặc bước chuyển đổi XML trước khi đọc.

Một fragment cần có ranh giới xác định. Cấu trúc lồng nhau phức tạp có thể cần logic đọc theo depth và QName thay vì chỉ tên tag.

## 10. XML có metadata bên ngoài các fragment

Document root có thể chứa metadata trước hoặc sau các record:

~~~xml
<orders>
    <header>
        <batchId>B-20261115</batchId>
        <recordCount>2</recordCount>
    </header>
    <order>
        <orderId>ORD-1</orderId>
    </order>
    <order>
        <orderId>ORD-2</orderId>
    </order>
    <trailer>
        <totalAmount>250000.00</totalAmount>
    </trailer>
</orders>
~~~

Nếu reader chỉ phát các fragment order, metadata header và trailer không tự động trở thành item. Nếu cần dùng batchId hoặc recordCount trong Job, có thể:

- Đọc metadata bằng một bước validation/preparation riêng.
- Dùng một reader hoặc parser chuyên biệt để trích metadata.
- Truyền metadata qua JobParameters hoặc JobExecutionContext.
- Kiểm tra trailer sau khi đọc hết file bằng listener hoặc Step riêng.

Không nên chọn orders làm fragment root chỉ để lấy metadata nếu output chính vẫn cần từng order riêng. Điều đó khiến một item bao trùm cả file.

## 11. XML schema và validation

Fragment root xác định đơn vị đọc, còn XML Schema (XSD) xác định cấu trúc và kiểu dữ liệu hợp lệ. Hai khái niệm này bổ trợ nhau:

- Fragment root cho reader biết đoạn XML nào trở thành một item.
- XSD mô tả element, attribute, thứ tự, cardinality và kiểu dữ liệu.
- JAXB/OXM mapping chuyển fragment sang Java object.
- Processor áp dụng quy tắc nghiệp vụ sau khi parse.

Có thể cấu hình Jaxb2Marshaller với schema:

~~~java
@Bean
Jaxb2Marshaller orderUnmarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Order.class);
    marshaller.setSchema(new ClassPathResource("xsd/order.xsd"));
    return marshaller;
}
~~~

Schema validation giúp phát hiện cấu trúc không hợp lệ trong quá trình unmarshal. Cần quyết định lỗi schema nào được skip và lỗi nào phải dừng Job. Nếu một fragment vi phạm schema nhưng vẫn có ranh giới rõ, có thể phân loại exception tương ứng là skippable; tuy nhiên, lỗi XML làm mất cấu trúc hoặc không xác định được ranh giới fragment có thể khiến reader không thể tiếp tục an toàn.

Không phải mọi cấu hình OXM đều bật schema validation mặc định. Hãy cấu hình và kiểm thử rõ ràng nếu hợp đồng đầu vào yêu cầu XSD.

## 12. Khai báo Step đọc XML

Sau khi có reader, cấu hình Step giống một chunk-oriented Step thông thường:

~~~java
@Bean
Step importOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        StaxEventItemReader<Order> orderReader,
        ItemProcessor<Order, OrderRecord> orderProcessor,
        ItemWriter<OrderRecord> orderWriter) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<Order, OrderRecord>chunk(100, transactionManager)
            .reader(orderReader)
            .processor(orderProcessor)
            .writer(orderWriter)
            .build();
}
~~~

Reader trả về từng Order fragment. Processor có thể validate hoặc chuyển đổi sang OrderRecord. Writer ghi các output theo chunk. Chunk size 100 có nghĩa Step gom tối đa 100 item output trước khi gọi writer và commit theo transaction.

Nếu một order không hợp lệ về nghiệp vụ, processor có thể ném exception được cấu hình skip. Nếu fragment XML không thể unmarshal, lỗi phát sinh ở reader và được xử lý theo skip policy của read.

## 13. Late binding resource đầu vào

Một Job có thể đọc các file XML khác nhau theo từng lần chạy. Dùng StepScope để inject đường dẫn từ JobParameters:

~~~java
@Bean
@StepScope
StaxEventItemReader<Order> orderReader(
        @Value("#{jobParameters['input.file']}") String inputFile,
        Unmarshaller orderUnmarshaller) {

    if (inputFile == null || inputFile.isBlank()) {
        throw new IllegalArgumentException("input.file is required");
    }

    return new StaxEventItemReaderBuilder<Order>()
            .name("orderReader")
            .resource(new FileSystemResource(inputFile))
            .fragmentRootElementName("order")
            .unmarshaller(orderUnmarshaller)
            .saveState(true)
            .strict(true)
            .build();
}
~~~

JobParameters xác định file của lần chạy. Fragment root vẫn xác định mỗi item là một order. Hai cấu hình giải quyết hai việc khác nhau.

Nếu file đầu vào được xác định theo batch ID hoặc ngày nghiệp vụ, cần chọn identifying JobParameters phù hợp để một lần restart tiếp tục đúng JobInstance và đúng file. Không thay file mới vào cùng JobInstance nếu checkpoint cũ được tạo từ file khác.

## 14. Restart và checkpoint của StaxEventItemReader

StaxEventItemReader triển khai ItemStreamReader, nên có thể lưu trạng thái đọc vào StepExecutionContext khi saveState được bật. Khi Step restart, reader khôi phục vị trí dựa trên trạng thái đã lưu theo implementation.

Luồng ví dụ:

~~~text
Lần chạy đầu:
  open XML resource
  đọc order 1..100
  update checkpoint
  commit chunk
  đọc order 101..200
  update checkpoint
  commit chunk
  lỗi ở chunk tiếp theo
  close resource

Restart cùng JobInstance:
  open lại cùng resource
  khôi phục checkpoint đã lưu
  tiếp tục đọc fragment còn lại
~~~

Để restart an toàn:

- Giữ nguyên file nguồn hoặc kiểm tra checksum/version.
- Giữ tên reader ổn định để key checkpoint không đổi.
- Bật saveState nếu cần khôi phục tiến độ.
- Không thay đổi fragment root hoặc mapping giữa lần chạy đầu và restart mà không có kế hoạch tương thích.
- Bảo đảm writer idempotent nếu có khả năng đọc lại item của chunk chưa commit.

Nếu file XML bị thay đổi, vị trí event/checkpoint cũ có thể không còn tương ứng với cùng fragment. Với dữ liệu quan trọng, nên lưu file bất biến theo batch ID hoặc copy vào vùng lưu trữ staging trước khi xử lý.

## 15. Xử lý fragment lỗi và skip

Lỗi trong XML có thể xảy ra khi:

- XML không well-formed, chẳng hạn thiếu thẻ đóng.
- Fragment có element hoặc attribute không đúng schema.
- Unmarshaller không chuyển đổi được kiểu dữ liệu.
- Phần tử bắt buộc bị thiếu.
- Giá trị enum hoặc ngày không hợp lệ.

Nếu reader xác định được ranh giới fragment và lỗi chỉ thuộc một fragment, có thể xem xét skip exception phù hợp. Tuy nhiên, nếu XML bị hỏng đến mức parser không thể xác định phần tử đóng hoặc tiếp tục đọc an toàn, bỏ qua một fragment có thể không khả thi.

Ví dụ cấu hình skip cho lỗi unmarshal đã được phân loại:

~~~java
.faultTolerant()
.skip(InvalidOrderXmlException.class)
.skipLimit(20)
~~~

Trong thực tế, cần kiểm tra exception cụ thể do OXM/StAX ném và có thể bọc thành exception nghiệp vụ riêng ở lớp reader nếu muốn phân loại chính xác. Tránh skip mọi XMLStreamException hoặc mọi Exception một cách rộng rãi, vì lỗi parser có thể ảnh hưởng cấu trúc của phần còn lại trong file.

SkipListener.onSkipInRead nhận Throwable, không nhận Order vì object chưa được tạo thành công. Có thể ghi nhận file, vị trí, exception type và thông tin fragment nếu exception cung cấp. Không phải exception nào cũng chứa raw fragment hoàn chỉnh.

## 16. XML không well-formed và XML hợp lệ nhưng sai nghiệp vụ

Hai nhóm lỗi này cần được xử lý khác nhau:

| Nhóm | Ví dụ | Tầng phát hiện |
|---|---|---|
| Không well-formed | Thẻ mở không có thẻ đóng, quote attribute chưa kết thúc | XML parser/StAX |
| Sai schema | Thiếu element bắt buộc, sai thứ tự hoặc sai kiểu theo XSD | Schema validation/OXM |
| Sai mapping | JAXB không tìm được property hoặc kiểu không chuyển đổi được | Unmarshaller |
| Sai nghiệp vụ | amount âm, customer không tồn tại | ItemProcessor |

XML không well-formed có thể làm parser không thể tiếp tục vì ranh giới fragment bị mất. XML well-formed nhưng một fragment không đúng schema thường dễ cô lập hơn, nếu parser vẫn đọc được đến fragment kế tiếp.

Một object parse thành công vẫn có thể sai nghiệp vụ. Trường hợp này nên dùng exception riêng từ processor và callback onSkipInProcess nếu được phép skip. Đừng cố dùng FlatFileParseException hoặc cơ chế flat-file cho XML.

## 17. Nhiều loại fragment trong cùng một tài liệu

Một document có thể chứa nhiều loại phần tử nghiệp vụ:

~~~xml
<exchange>
    <trade>
        <tradeId>T-001</tradeId>
        <symbol>ABC</symbol>
    </trade>
    <cancel>
        <tradeId>T-002</tradeId>
        <reason>Duplicate</reason>
    </cancel>
</exchange>
~~~

Nếu Job cần đọc cả trade và cancel như hai loại item khác nhau, một StaxEventItemReader với một fragment root đơn có thể không đáp ứng đầy đủ yêu cầu. Có thể:

- Dùng hai Step hoặc hai reader nếu dữ liệu được tổ chức thành các resource riêng.
- Dùng reader tùy chỉnh trả về một kiểu chung có discriminator.
- Chuẩn hóa XML đầu vào thành các loại record thống nhất trước khi xử lý.
- Dùng parser streaming tùy chỉnh để nhận diện nhiều QName và tạo item tương ứng.

Không nên giả định một reader được cấu hình fragment root trade sẽ tự phát thêm cancel. Thiết kế reader phải phản ánh rõ các loại item mà Job cần nhận.

## 18. Root tag, fragment và kích thước bộ nhớ

Lựa chọn fragment root ảnh hưởng trực tiếp đến kích thước item:

- Chọn document root có thể làm toàn bộ file trở thành một item rất lớn.
- Chọn record root thường tạo item có kích thước phù hợp với chunk.
- Chọn element con quá nhỏ có thể làm mất ngữ cảnh cha hoặc tạo quá nhiều item.

Ví dụ với một order có 10.000 line:

- Nếu fragment root là order, một item Order chứa 10.000 line.
- Nếu fragment root là line, mỗi line có thể trở thành một item nhưng cần thêm orderId/customer context.

Không có lựa chọn đúng cho mọi file. Hãy chọn đơn vị fragment theo yêu cầu nghiệp vụ, transaction và bộ nhớ. Nếu cần xử lý từng line nhưng vẫn cần metadata của order, có thể thiết kế reader giữ ngữ cảnh cha và phát từng line cùng khóa order.

StAX giúp streaming qua document, nhưng Unmarshaller vẫn tạo object graph cho từng fragment. Một fragment quá lớn vẫn có thể dùng nhiều bộ nhớ dù toàn file không được nạp vào DOM.

## 19. Bảo mật khi đọc XML

XML đến từ hệ thống bên ngoài cần được xem là input không tin cậy. Cần chú ý:

- Không cho phép parser tải external entity hoặc DTD không cần thiết.
- Hạn chế khả năng truy cập file/network thông qua external entity.
- Giới hạn kích thước file, độ sâu lồng nhau và số fragment nếu nguồn có thể gây tải lớn.
- Validate namespace và schema theo hợp đồng.
- Không log toàn bộ fragment nếu có dữ liệu nhạy cảm.
- Kiểm soát đường dẫn resource được truyền qua JobParameters.

StaxEventItemReader cho phép cấu hình XMLInputFactory. Có thể tạo factory với các thuộc tính bảo mật mà implementation StAX hỗ trợ:

~~~java
@Bean
XMLInputFactory secureXmlInputFactory() {
    XMLInputFactory factory = XMLInputFactory.newFactory();
    factory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
    factory.setProperty(
            "javax.xml.stream.isSupportingExternalEntities", false);
    return factory;
}
~~~

Sau đó truyền factory vào builder nếu phiên bản Spring Batch hỗ trợ cấu hình XMLInputFactory:

~~~java
return new StaxEventItemReaderBuilder<Order>()
        .name("orderReader")
        .resource(resource)
        .fragmentRootElementName("order")
        .unmarshaller(orderUnmarshaller)
        .xmlInputFactory(secureXmlInputFactory)
        .build();
~~~

Tên property và hỗ trợ của StAX provider có thể khác nhau. Một provider có thể từ chối property không hỗ trợ. Hãy kiểm tra cấu hình trên runtime thực tế và có test xác nhận external entity bị vô hiệu hóa; không chỉ dựa vào việc gọi setProperty mà không quan sát hành vi parser.

## 20. Kiểm thử root tag và fragment

Nên tạo XML fixture nhỏ có document root, metadata, nhiều fragment và các trường hợp biên. Test phải xác nhận reader trả đúng số item và mỗi item chứa dữ liệu của đúng fragment.

Các trường hợp nên kiểm tra:

1. Một document root chứa một fragment: reader trả một item.
2. Một document root chứa nhiều fragment cùng tên: reader trả đúng số item.
3. Metadata trước và sau fragment: metadata không bị phát nhầm thành item.
4. Fragment có nested elements và list: object mapping giữ đúng cấu trúc.
5. Document có namespace mặc định hoặc prefix: fragment selection và JAXB mapping đúng.
6. Fragment root cấu hình sai: test phát hiện reader không trả item hoặc ánh xạ sai.
7. XML thiếu thẻ đóng: Step thất bại theo hành vi parser.
8. Một fragment sai schema: kiểm tra skip/fail policy.
9. Nhiều phần tử cùng tên lồng nhau: xác nhận boundary theo cấu trúc thực tế.
10. Restart: reader tiếp tục từ checkpoint và không xử lý trùng các chunk đã commit.

Ví dụ test Step:

~~~java
@SpringBatchTest
@SpringJUnitConfig(XmlImportTestConfiguration.class)
class XmlFragmentReaderTest {

    @Autowired
    JobLauncherTestUtils jobLauncherTestUtils;

    @Autowired
    OrderRepository orderRepository;

    @Test
    void readsEachOrderFragmentAsOneItem() throws Exception {
        JobParameters parameters = new JobParametersBuilder()
                .addString("input.file", "src/test/resources/orders.xml", true)
                .toJobParameters();

        JobExecution execution = jobLauncherTestUtils.launchJob(parameters);

        assertEquals(BatchStatus.COMPLETED, execution.getStatus());
        assertEquals(2, orderRepository.count());
        assertTrue(orderRepository.existsByOrderId("ORD-1001"));
        assertTrue(orderRepository.existsByOrderId("ORD-1002"));
    }
}
~~~

Test này giả định file fixture chứa đúng hai fragment order và writer lưu mỗi order một lần. Nên kiểm tra thêm StepExecution readCount/writeCount và dữ liệu từng field, không chỉ số lượng record.

## 21. Các lỗi thường gặp

**Nhầm document root với fragment root:** chọn orders thay vì order có thể khiến cả wrapper trở thành một item. Xác định đơn vị nghiệp vụ trước khi cấu hình.

**Không cấu hình fragment root:** reader không biết element nào là item và có thể không trả dữ liệu như mong đợi.

**Unmarshaller không khớp fragment:** JAXB model khai báo root hoặc namespace khác với fragment thực tế, gây lỗi mapping.

**Chọn fragment quá nhỏ:** mất dữ liệu ngữ cảnh của phần tử cha hoặc tạo quá nhiều item cần ghép lại.

**Chọn fragment quá lớn:** một item có thể chứa hàng nghìn phần tử con và tiêu tốn nhiều bộ nhớ.

**Bỏ qua namespace:** prefix không phải namespace identity; cần kiểm tra namespace URI và JAXB annotations.

**Giả định lỗi XML nào cũng skip được:** XML không well-formed có thể làm parser không thể xác định fragment kế tiếp.

**Coi metadata là record:** header/trailer hoặc phần tử tổng hợp không tự động trở thành item nếu fragment root khác.

**Không kiểm thử tag lồng nhau cùng tên:** boundary có thể khác kỳ vọng khi cấu trúc XML phức tạp.

**Không giữ resource ổn định khi restart:** checkpoint cũ có thể không còn đúng nếu file thay đổi.

**Không bảo vệ parser trước external entity:** XML không tin cậy có thể gây truy cập tài nguyên ngoài ý muốn.

## Kết luận

Trong Spring Batch, document root là phần tử gốc của toàn bộ XML, còn fragment root là phần tử đánh dấu từng đơn vị dữ liệu mà StaxEventItemReader trả về. Với file có root orders và nhiều phần tử order, chọn order làm fragment root nếu mỗi đơn hàng là một item. Reader dùng StAX để đọc fragment theo luồng rồi chuyển từng fragment thành object qua OXM Unmarshaller như JAXB. Hãy cấu hình fragment root khớp cấu trúc nghiệp vụ, ánh xạ đúng phần tử lồng nhau và namespace, giữ resource ổn định cho restart, đồng thời kiểm thử số item, lỗi parse/schema và ranh giới fragment. Chọn đúng fragment giúp chunk processing giữ được lợi ích streaming và tránh biến cả file thành một item quá lớn hoặc tách dữ liệu khỏi ngữ cảnh cần thiết.
