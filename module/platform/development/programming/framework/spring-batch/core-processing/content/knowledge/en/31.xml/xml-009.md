# Root tag and fragments in XML

When processing XML with Spring Batch, a file usually has one root element enclosing many child elements. Each child element can represent a business record that needs to be read, processed, and written individually. Therefore, distinguish the **document root** of the entire file from the **fragment root** of each record.

Spring Batch provides StaxEventItemReader to read XML fragment by fragment. The reader takes the name of the element starting a fragment, extracts the corresponding XML content, and converts the fragment into an object through an OXM Unmarshaller, such as JAXB. This allows a large XML file to be processed in chunks without loading the entire document into a single object.

## 1. Document root and fragment structure

A well-formed XML document has exactly one document element, often called the root element. The root element wraps all other elements and defines the overall document structure.

Example:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <metadata>
        <source>ERP</source>
        <businessDate>2026-11-15</businessDate>
    </metadata>

    <order>
        <orderId>ORD-1001</orderId>
        <customerId>C-001</customerId>
        <amount>125000.00</amount>
    </order>

    <order>
        <orderId>ORD-1002</orderId>
        <customerId>C-002</customerId>
        <amount>98000.00</amount>
    </order>
</orders>
~~~

In the example:

- orders is the document root of the whole file.
- metadata holds general file information.
- Each order is a fragment representing an order record.
- orderId, customerId, and amount are data elements inside the fragment.

When you want each order to become an item in Spring Batch, the fragment root must be order. The reader extracts each order element and converts it into an Order object. The orders element is just the document wrapper, not an item to write in this example.

| Concept | Role | Example |
|---|---|---|
| XML document | The entire XML document | File orders.xml |
| Document root | The single root element of the document | orders |
| Fragment | An XML segment extracted as a unit of reading | One order element with its child content |
| Fragment root | The element starting each fragment | order |
| Child element | Data field inside a fragment | orderId, customerId, amount |

The fragment root name usually repeats many times in the document, whereas the document root appears only once. Choosing the right fragment root determines the item boundaries returned by the reader.

## 2. What is a fragment in Spring Batch?

In the context of StaxEventItemReader, a fragment is the XML section starting at an element configured as a fragment root and ending at its matching closing element. The fragment is passed to the Unmarshaller to create one item.

Example with a file containing 1,000 order elements:

~~~text
orders
  metadata
  order 1  -> item 1
  order 2  -> item 2
  order 3  -> item 3
  ...
  order 1000 -> item 1000
~~~

The reader does not have to return the entire orders element as one giant object. It returns each Order sequentially so processor and writer can process them in chunks.

A fragment can contain multiple child elements, nested elements, XML attributes, and text. The Unmarshaller is responsible for mapping the fragment structure to a Java object.

Example:

~~~xml
<order id="ORD-1001" status="NEW">
    <customer>
        <id>C-001</id>
        <name>An Nguyen</name>
    </customer>
    <lines>
        <line>
            <sku>SKU-01</sku>
            <quantity>2</quantity>
        </line>
        <line>
            <sku>SKU-02</sku>
            <quantity>1</quantity>
        </line>
    </lines>
</order>
~~~

The entire order element, including customer and lines, is one fragment. The two line elements do not automatically become two separate items when the fragment root is configured as order.

If each line must be a separate item, select a fragment root matching that business structure or build a dedicated reader/processor to split lines from the Order.

## 3. How does StaxEventItemReader read fragments?

StaxEventItemReader uses StAX (Streaming API for XML) to read XML events in a stream. It searches for elements matching the configured fragment root, collects that fragment's events, and passes the fragment to the Unmarshaller.

General flow:

~~~text
XML Resource
    |
    v
StAX XMLInputFactory / XMLEventReader
    |
    v
Find configured fragment root
    |
    v
Collect events until matching closing tag
    |
    v
XML fragment
    |
    v
OXM Unmarshaller (e.g., JAXB)
    |
    v
Java item
    |
    v
ItemProcessor
    |
    v
ItemWriter
~~~

Streaming avoids building the entire document tree in memory. Once a fragment is unmarshalled, the reader can continue searching for the next fragment.

StAX is an event-driven reading model. It differs from parsing the whole XML into a DOM, where the application usually retains a large node tree in memory. For large files with many records, fragment-based processing is generally more memory-efficient.

## 4. Configuring fragmentRootElementName

StaxEventItemReader needs to know which element represents an item. In Java configuration, use StaxEventItemReaderBuilder and configure fragmentRootElementName:

~~~java
@Bean
StaxEventItemReader<Order> orderReader(
        Resource orderResource,
        Unmarshaller orderUnmarshaller) {

    return new StaxEventItemReaderBuilder<Order>()
            .name("orderReader")
            .resource(orderResource)
            .addFragmentRootElements("order")
            .unmarshaller(orderUnmarshaller)
            .saveState(true)
            .strict(true)
            .build();
}
~~~

Some Spring Batch versions provide a builder API named fragmentRootElementName(String); newer versions may provide the addFragmentRootElements(String...) variant. Use the exact API of the dependency version in your project. The configuration purpose remains specifying which XML element acts as the item boundary.

With the fragmentRootElementName API:

~~~java
return new StaxEventItemReaderBuilder<Order>()
        .name("orderReader")
        .resource(orderResource)
        .fragmentRootElementName("order")
        .unmarshaller(orderUnmarshaller)
        .saveState(true)
        .build();
~~~

In the example, the reader returns each order element. Misconfiguring it as orders can make the reader treat the entire wrapper element as a single fragment and require the Unmarshaller to map the entire document root. This completely alters the item count and data mapping.

For XML containing multiple child element types, pick the fragment root representing the business unit to process. Do not pick a tag merely because it appears frequently; consider transaction boundaries and desired output.

## 5. Creating an Unmarshaller with JAXB

StaxEventItemReader does not decide how XML turns into objects by itself. It needs an OXM Unmarshaller. A common choice is Spring OXM's Jaxb2Marshaller.

Model example:

~~~java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {

    private String orderId;
    private String customerId;
    private BigDecimal amount;

    public String getOrderId() {
        return orderId;
    }

    public String getCustomerId() {
        return customerId;
    }

    public BigDecimal getAmount() {
        return amount;
    }
}
~~~

Declaring the JAXB marshaller:

~~~java
@Bean
Jaxb2Marshaller orderUnmarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Order.class);
    return marshaller;
}
~~~

Then pass the marshaller into StaxEventItemReader:

~~~java
@Bean
StaxEventItemReader<Order> orderReader(
        @Value("file:/data/orders.xml") Resource resource,
        Jaxb2Marshaller orderUnmarshaller) {

    return new StaxEventItemReaderBuilder<Order>()
            .name("orderReader")
            .resource(resource)
            .fragmentRootElementName("order")
            .unmarshaller(orderUnmarshaller)
            .saveState(true)
            .build();
}
~~~

The model and JAXB annotations must match the actual XML. If the XML has attributes, namespaces, nested elements, or line lists, the model must declare them accordingly. Do not assume declaring only the fragment root lets Spring instantiate objects without proper mapping.

With Spring Boot 3/Spring Framework 6 applications, use Jakarta-compatible JAXB APIs. Legacy projects may use javax JAXB. Do not mix the two annotation namespaces, or the JAXB runtime may fail to recognize the model.

## 6. Mapping XML with nested elements

A fragment often has a multi-level structure. Example:

~~~xml
<order>
    <orderId>ORD-1001</orderId>
    <customer>
        <customerId>C-001</customerId>
        <name>An Nguyen</name>
    </customer>
    <lines>
        <line>
            <sku>SKU-01</sku>
            <quantity>2</quantity>
            <unitPrice>15000.00</unitPrice>
        </line>
        <line>
            <sku>SKU-02</sku>
            <quantity>1</quantity>
            <unitPrice>25000.00</unitPrice>
        </line>
    </lines>
</order>
~~~

This can map to these classes:

~~~java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {

    private String orderId;
    private CustomerInfo customer;

    @XmlElementWrapper(name = "lines")
    @XmlElement(name = "line")
    private List<OrderLine> lines;
}

@XmlAccessorType(XmlAccessType.FIELD)
public class CustomerInfo {
    private String customerId;
    private String name;
}

@XmlAccessorType(XmlAccessType.FIELD)
public class OrderLine {
    private String sku;
    private int quantity;
    private BigDecimal unitPrice;
}
~~~

One order fragment is converted into one Order containing a CustomerInfo and a list of OrderLines. The processor can verify total amounts, compute taxes, or convert to database models.

If the child list is huge and needs independent processing, unmarshalling the entire list into one Order can consume a lot of memory. In that case, consider picking line as the fragment unit if the structure permits, or writing a custom streaming reader that preserves parent order context while emitting each line.

## 7. XML with namespaces

XML can use a default namespace:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders xmlns="urn:example:orders">
    <order>
        <orderId>ORD-1001</orderId>
        <amount>125000.00</amount>
    </order>
</orders>
~~~

Or use prefixes:

~~~xml
<ord:orders xmlns:ord="urn:example:orders">
    <ord:order>
        <ord:orderId>ORD-1001</ord:orderId>
        <ord:amount>125000.00</ord:amount>
    </ord:order>
</ord:orders>
~~~

The namespace URI is the namespace identifier; prefixes are only document-local aliases. Two different prefixes can still represent the exact same namespace URI.

When using JAXB, models must declare appropriate namespaces. Example:

~~~java
@XmlRootElement(name = "order", namespace = "urn:example:orders")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {
    @XmlElement(namespace = "urn:example:orders")
    private String orderId;
}
~~~

Fragment root selection in namespaced XML must be verified against your Spring Batch and XMLInputFactory versions. Some configuration APIs accept fragment names as Strings, and matching may depend on how the implementation handles QNames/local names. Do not test only with non-namespaced XML and assume namespaced files behave identically.

Write integration tests using your system's actual namespaced XML, verifying the reader receives the exact fragment count and JAXB maps fields properly. When multiple namespaces exist or prefixes vary, rely on namespace URIs and JAXB mappings rather than hardcoding fixed prefixes.

## 8. The document root is not always the fragment root

A common configuration mistake is picking the document root instead of the element representing an item.

Example file:

~~~xml
<catalog>
    <generatedAt>2026-11-15T10:00:00Z</generatedAt>
    <products>
        <product>
            <sku>P-001</sku>
            <name>Keyboard</name>
        </product>
        <product>
            <sku>P-002</sku>
            <name>Mouse</name>
        </product>
    </products>
</catalog>
~~~

If each product is an item, the fragment root must be product. catalog is the document root; products is an intermediate container.

| Tag | Role | Should it be fragment root? |
|---|---|---|
| catalog | Document root | No, if you want each product as an item |
| generatedAt | File metadata | No |
| products | List container | Only if you want one item containing the entire list |
| product | Product record | Yes, if each product is an item |

Picking a fragment root too high makes items huge, increasing memory and losing chunk processing benefits. Picking too low loses parent context needed to interpret child data.

## 9. Fragment roots and nested elements with the same name

Complex XML can have elements sharing the same name at multiple levels:

~~~xml
<orders>
    <order>
        <orderId>ORD-1</orderId>
        <relatedOrders>
            <order>
                <orderId>ORD-OLD-1</orderId>
            </order>
        </relatedOrders>
    </order>
</orders>
~~~

If the order tag appears nested, determine how your framework version's reader handles fragment boundaries. Do not assume all elements with the same local name are always treated as outer-level items matching business intent.

To avoid ambiguity:

- Design XML using distinct element names for primary records and nested records whenever possible.
- Verify XML structure and nesting depth with real fixtures.
- Write tests verifying the item count returned by the reader.
- If distinguishing by parent/child path is required, use a custom reader or an XML transformation step prior to reading.

A fragment needs unambiguous boundaries. Deeply nested structures may require depth- and QName-aware reading logic instead of tag names alone.

## 10. XML with metadata outside fragments

The document root may hold metadata before or after the records:

~~~xml
<orders>
    <header>
        <batchId>B-20261115</batchId>
        <recordCount>2</recordCount>
    </header>
    <order>
        <orderId>ORD-1</orderId>
    </order>
    <order>
        <orderId>ORD-2</orderId>
    </order>
    <trailer>
        <totalAmount>250000.00</totalAmount>
    </trailer>
</orders>
~~~

If the reader only emits order fragments, header and trailer metadata do not automatically become items. If the Job needs batchId or recordCount, you can:

- Read metadata in a separate validation/preparation step.
- Use a specialized reader or parser to extract metadata.
- Pass metadata via JobParameters or JobExecutionContext.
- Verify trailer totals after reading the entire file using a listener or separate Step.

Do not pick orders as the fragment root just to capture metadata if main output still requires each order individually. That turns the entire file into a single item.

## 11. XML schemas and validation

The fragment root defines the reading unit, while an XML Schema (XSD) defines valid structure and data types. These two concepts complement each other:

- Fragment root tells the reader which XML segment becomes an item.
- XSD describes elements, attributes, ordering, cardinality, and data types.
- JAXB/OXM mapping converts fragments into Java objects.
- Processors apply business rules after parsing.

Jaxb2Marshaller can be configured with a schema:

~~~java
@Bean
Jaxb2Marshaller orderUnmarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Order.class);
    marshaller.setSchema(new ClassPathResource("xsd/order.xsd"));
    return marshaller;
}
~~~

Schema validation detects invalid structure during unmarshalling. Decide which schema errors are skippable and which must stop the Job. If a fragment violates the schema while still having clear boundaries, the corresponding exception can be classified as skippable; however, XML errors that break structure or obscure fragment boundaries can prevent the reader from safely continuing.

Not every OXM configuration enables schema validation by default. Explicitly configure and test it if the input contract requires an XSD.

## 12. Declaring the XML-reading Step

Once you have the reader, configure the Step like a normal chunk-oriented Step:

~~~java
@Bean
Step importOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        StaxEventItemReader<Order> orderReader,
        ItemProcessor<Order, OrderRecord> orderProcessor,
        ItemWriter<OrderRecord> orderWriter) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<Order, OrderRecord>chunk(100, transactionManager)
            .reader(orderReader)
            .processor(orderProcessor)
            .writer(orderWriter)
            .build();
}
~~~

The reader returns each Order fragment. The processor can validate or convert to OrderRecord. The writer writes outputs per chunk. A chunk size of 100 means the Step collects up to 100 output items before calling the writer and committing the transaction.

If an order fails business rules, the processor can throw an exception configured for skipping. If an XML fragment cannot be unmarshalled, the error arises in the reader and is handled according to the read skip policy.

## 13. Late-binding input resources

A Job may read different XML files across runs. Use StepScope to inject paths from JobParameters:

~~~java
@Bean
@StepScope
StaxEventItemReader<Order> orderReader(
        @Value("#{jobParameters['input.file']}") String inputFile,
        Unmarshaller orderUnmarshaller) {

    if (inputFile == null || inputFile.isBlank()) {
        throw new IllegalArgumentException("input.file is required");
    }

    return new StaxEventItemReaderBuilder<Order>()
            .name("orderReader")
            .resource(new FileSystemResource(inputFile))
            .fragmentRootElementName("order")
            .unmarshaller(orderUnmarshaller)
            .saveState(true)
            .strict(true)
            .build();
}
~~~

JobParameters determines which file the run reads. Fragment root still defines each item as an order. These two settings solve different concerns.

If the input file is identified by batch ID or business date, choose appropriate identifying JobParameters so a restart resumes the right JobInstance and exact file. Do not swap a new file into the same JobInstance if old checkpoints were created from a different file.

## 14. Restart and checkpoints in StaxEventItemReader

StaxEventItemReader implements ItemStreamReader, so it can save read state in StepExecutionContext when saveState is enabled. When the Step restarts, the reader restores its position from saved state per implementation.

Example flow:

~~~text
First run:
  open XML resource
  read order 1..100
  update checkpoint
  commit chunk
  read order 101..200
  update checkpoint
  commit chunk
  error in next chunk
  close resource

Restart same JobInstance:
  reopen same resource
  restore saved checkpoint
  continue reading remaining fragments
~~~

For safe restarts:

- Keep the source file unchanged or verify checksum/version.
- Keep the reader name stable so checkpoint keys do not change.
- Enable saveState if progress recovery is needed.
- Do not alter fragment root or mappings between the initial run and restart without a compatibility plan.
- Ensure the writer is idempotent in case items from an uncommitted chunk are reread.

If the XML file changes, old event/checkpoint positions may no longer match the same fragments. For critical data, store immutable files keyed by batch ID or copy into staging storage before processing.

## 15. Handling bad fragments and skipping

Errors in XML can occur when:

- XML is not well-formed, e.g., missing a closing tag.
- A fragment has elements or attributes violating the schema.
- The Unmarshaller fails to convert data types.
- Required elements are missing.
- Enum or date values are invalid.

If the reader can identify fragment boundaries and the error belongs to a single fragment, skipping the matching exception can be considered. However, if XML is damaged such that the parser cannot locate closing elements or continue safely, skipping one fragment may be impossible.

Example skip configuration for classified unmarshal errors:

~~~java
.faultTolerant()
.skip(InvalidOrderXmlException.class)
.skipLimit(20)
~~~

In practice, inspect the exact exceptions thrown by OXM/StAX and optionally wrap them in a custom business exception in the reader layer for precise classification. Avoid broadly skipping all XMLStreamException or Exception types, because parser errors can corrupt structure for the remainder of the file.

SkipListener.onSkipInRead receives a Throwable rather than an Order, because the object was never constructed. Log the file, position, exception type, and fragment details if provided by the exception. Not every exception includes the complete raw fragment.

## 16. Non-well-formed XML vs valid XML with business errors

These two error groups must be handled differently:

| Group | Example | Detection layer |
|---|---|---|
| Non-well-formed | Unclosed opening tag, unterminated attribute quote | XML parser/StAX |
| Invalid schema | Missing required element, wrong order or type per XSD | Schema validation/OXM |
| Invalid mapping | JAXB cannot find property or convert type | Unmarshaller |
| Business error | Negative amount, non-existent customer | ItemProcessor |

Non-well-formed XML can halt the parser because fragment boundaries are lost. Well-formed XML where one fragment fails schema checks is usually easier to isolate, provided the parser can still reach the next fragment.

A successfully parsed object can still violate business rules. In this case, throw a dedicated exception from the processor and use onSkipInProcess if skipping is permitted. Do not try to use FlatFileParseException or flat-file mechanics for XML.

## 17. Multiple fragment types in one document

One document can contain multiple business element types:

~~~xml
<exchange>
    <trade>
        <tradeId>T-001</tradeId>
        <symbol>ABC</symbol>
    </trade>
    <cancel>
        <tradeId>T-002</tradeId>
        <reason>Duplicate</reason>
    </cancel>
</exchange>
~~~

If a Job needs to read both trade and cancel as distinct item types, a StaxEventItemReader with a single fragment root may not suffice. Options include:

- Using two Steps or two readers if data is organized into separate resources.
- Using a custom reader returning a common type with a discriminator.
- Normalizing input XML into uniform record types prior to processing.
- Using a custom streaming parser to recognize multiple QNames and instantiate matching items.

Do not assume a reader configured with fragment root trade will automatically emit cancel elements as well. Reader design must explicitly reflect all item types the Job expects to receive.

## 18. Root tags, fragments, and memory footprint

Fragment root selection directly affects item size:

- Choosing the document root can turn the entire file into one huge item.
- Choosing the record root usually creates chunk-appropriate items.
- Choosing too small a child element can lose parent context or generate too many items.

For example, with an order containing 10,000 lines:

- If the fragment root is order, one Order item holds 10,000 lines.
- If the fragment root is line, each line becomes an item, but needs orderId/customer context.

There is no universal choice for all files. Pick the fragment unit according to business, transaction, and memory needs. If each line needs individual processing alongside order metadata, design a reader that retains parent context while emitting each line with its order key.

StAX streams through the document, yet the Unmarshaller still builds an object graph per fragment. An oversized fragment can still use substantial memory even though the entire file is not loaded into a DOM.

## 19. Security when reading XML

XML from external systems must be treated as untrusted input. Pay attention to:

- Disallowing parsers from loading external entities or unnecessary DTDs.
- Restricting file/network access via external entities.
- Limiting file size, nesting depth, and fragment count if sources can induce heavy load.
- Validating namespaces and schemas per contract.
- Avoiding logging full fragments if they hold sensitive data.
- Controlling resource paths passed through JobParameters.

StaxEventItemReader allows configuring XMLInputFactory. Create a factory with security properties supported by your StAX implementation:

~~~java
@Bean
XMLInputFactory secureXmlInputFactory() {
    XMLInputFactory factory = XMLInputFactory.newFactory();
    factory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
    factory.setProperty(
            "javax.xml.stream.isSupportingExternalEntities", false);
    return factory;
}
~~~

Then pass the factory into the builder if your Spring Batch version supports configuring XMLInputFactory:

~~~java
return new StaxEventItemReaderBuilder<Order>()
        .name("orderReader")
        .resource(resource)
        .fragmentRootElementName("order")
        .unmarshaller(orderUnmarshaller)
        .xmlInputFactory(secureXmlInputFactory)
        .build();
~~~

Property names and StAX provider support may vary. A provider may reject unsupported properties. Verify the configuration against the actual runtime and test that external entities are disabled; do not rely merely on calling setProperty without observing parser behavior.

## 20. Testing root tags and fragments

Create small XML fixtures with a document root, metadata, multiple fragments, and edge cases. Tests must verify the reader returns the right item count and each item holds data from the right fragment.

Cases to test:

1. Document root with one fragment: reader returns one item.
2. Document root with multiple fragments of the same name: reader returns exact item count.
3. Metadata before and after fragments: metadata is not mistakenly emitted as items.
4. Fragment with nested elements and lists: object mapping preserves structure.
5. Document with default or prefixed namespaces: fragment selection and JAXB mapping work properly.
6. Misconfigured fragment root: test detects reader returns no items or maps wrongly.
7. XML missing a closing tag: Step fails per parser behavior.
8. One fragment failing schema: verify skip/fail policy.
9. Multiple nested elements sharing a name: confirm boundaries match actual structure.
10. Restart: reader resumes from checkpoint without reprocessing committed chunks.

Step test example:

~~~java
@SpringBatchTest
@SpringJUnitConfig(XmlImportTestConfiguration.class)
class XmlFragmentReaderTest {

    @Autowired
    JobLauncherTestUtils jobLauncherTestUtils;

    @Autowired
    OrderRepository orderRepository;

    @Test
    void readsEachOrderFragmentAsOneItem() throws Exception {
        JobParameters parameters = new JobParametersBuilder()
                .addString("input.file", "src/test/resources/orders.xml", true)
                .toJobParameters();

        JobExecution execution = jobLauncherTestUtils.launchJob(parameters);

        assertEquals(BatchStatus.COMPLETED, execution.getStatus());
        assertEquals(2, orderRepository.count());
        assertTrue(orderRepository.existsByOrderId("ORD-1001"));
        assertTrue(orderRepository.existsByOrderId("ORD-1002"));
    }
}
~~~

This test assumes the fixture contains exactly two order fragments and the writer persists each order once. Also verify StepExecution readCount/writeCount and individual field values, not just record counts.

## 21. Common pitfalls

**Confusing document root with fragment root:** selecting orders instead of order can turn the entire wrapper into one item. Identify the business unit before configuring.

**Not configuring a fragment root:** the reader does not know which element is an item and may fail to return expected data.

**Unmarshaller mismatching the fragment:** JAXB model declares a different root or namespace from the actual fragment, causing mapping errors.

**Choosing too small a fragment:** loses parent element context or produces too many items needing reassembly.

**Choosing too large a fragment:** a single item may hold thousands of child elements and consume excessive memory.

**Ignoring namespaces:** prefixes are not namespace identity; check namespace URIs and JAXB annotations.

**Assuming any XML error can be skipped:** non-well-formed XML can prevent the parser from locating the next fragment.

**Treating metadata as records:** headers/trailers or summary elements do not automatically become items when the fragment root differs.

**Not testing nested tags with the same name:** boundaries may differ from expectations in complex XML structures.

**Not keeping resources stable on restart:** old checkpoints can become invalid if the file changes.

**Not hardening parsers against external entities:** untrusted XML can cause unintended resource access.

## Conclusion

In Spring Batch, the document root is the top-level element of the entire XML, whereas the fragment root marks each data unit returned by StaxEventItemReader. For a file with root orders and many order elements, choose order as the fragment root if each order is an item. The reader uses StAX to stream fragments and passes each fragment to an OXM Unmarshaller such as JAXB to construct objects. Configure the fragment root to match business structure, map nested elements and namespaces accurately, keep resources stable for restarts, and test item counts, parse/schema errors, and fragment boundaries. Picking the right fragment keeps chunk processing streaming efficiently without turning the whole file into an oversized item or stripping required context.
