# JobInstance and identifying a logical job

In Spring Batch, a `Job` is the definition of a processing workflow configured in the application. When that workflow is run for a specific unit of work, Spring Batch identifies a `JobInstance`. A `JobInstance` represents **one logical run** of the job, such as processing the settlement data for 15/11/2026 or importing a specific order file.

The key point is that a `JobInstance` does not represent a single call to `JobLauncher.run`. A logical job may need several technical executions because an earlier run failed or was stopped. Spring Batch uses the `JobInstance` to recognize that those executions belong to the same logical job and to support restarting at the right place.

## Distinguishing Job, JobInstance, and JobExecution

These three concepts are closely related but play different roles:

| Concept | Meaning | Example |
| --- | --- | --- |
| `Job` | The definition of a process consisting of processing steps, control flow, and restart configuration | `dailySettlementJob` |
| `JobInstance` | A logical unit of work of a `Job`, identified by the job name and the identifying parameters | Settlement for the date `2026-11-15` |
| `JobExecution` | A specific attempt to execute a `JobInstance` | The first run failed; the next run is a restart |

A common relationship:

```text
Job: dailySettlementJob
  |
  +-- JobInstance: businessDate=2026-11-15
  |     |
  |     +-- JobExecution #101 (FAILED)
  |     +-- JobExecution #108 (COMPLETED)  <- successful restart
  |
  +-- JobInstance: businessDate=2026-11-16
        |
        +-- JobExecution #109 (COMPLETED)
```

In the diagram, the first two `JobExecution`s belong to the same `JobInstance`: they are two attempts to process the same settlement data for 15/11. 16/11 is a different logical unit of work, so it produces a new `JobInstance`.

A `JobExecution` can contain multiple `StepExecution`s, each of which records one execution of a step in that run. Therefore, when analyzing the run history, you need to distinguish the state of the `JobInstance` from the state of each `JobExecution` and `StepExecution`.

## Rules for identifying a JobInstance

Spring Batch determines a `JobInstance` based on two components:

1. **The name of the `Job`**.
2. **The `JobParameter`s that are marked as identifying**.

You can picture this rule as follows:

```text
JobInstance identity = Job name + identifying JobParameters
```

The identifying parameters make up the identity of the logical unit of work. When the job name and the set of identifying values are the same, Spring Batch treats it as the same `JobInstance`. When the job name or one identifying value changes, Spring Batch treats it as a different `JobInstance`.

For example, the application has a job `dailySettlementJob` that processes settlement by day. The `businessDate` parameter specifies which data date to process:

| Job name | Identifying parameters | Result |
| --- | --- | --- |
| `dailySettlementJob` | `businessDate=2026-11-15` | One `JobInstance` |
| `dailySettlementJob` | `businessDate=2026-11-15` | The same `JobInstance` as the row above |
| `dailySettlementJob` | `businessDate=2026-11-16` | A new `JobInstance` |
| `monthlySettlementJob` | `businessDate=2026-11-15` | A new `JobInstance` because the job name is different |

This explains why a run on the same day does not automatically become a new logical job just because an operator presses the run button one more time. If the work identity does not change, Spring Batch looks up the existing `JobInstance` and applies the rerun or restart rules for that instance.

## Identifying and non-identifying JobParameters

`JobParameters` is the set of input parameters of a job execution. Each parameter has a name, a data type, a value, and a flag that determines whether it takes part in identifying the `JobInstance`.

### Identifying parameter

An identifying parameter answers the question: **which logical unit of work is this?**

Common examples:

- `businessDate`: the business date to process.
- `sourceFile`: the name or identifier of the input file to import.
- `tenantId`: the customer or tenant the data belongs to, if each tenant is an independent processing unit.
- `partitionKey`: the data range key, if the business logic defines each range as a separate logical job.

Identifying values must be stable across restarts. If the first run for `businessDate=2026-11-15` fails, the restart must still identify the work of that date correctly.

### Non-identifying parameter

A non-identifying parameter provides operational information for the run but does not change the identity of the logical job. Examples include `requestedBy`, the name of the launching machine, or information used for logging.

These values can differ between executions of the same `JobInstance`. However, you should mark a parameter as non-identifying only when changing it does not create a new unit of business work. If a parameter changes the data set, the result, or the processing scope, it usually has to take part in identification.

### Declaring JobParameters in Java

With `JobParametersBuilder`, you can specify the identifying flag explicitly using a boolean argument:

```java
JobParameters parameters = new JobParametersBuilder()
        .addString("businessDate", "2026-11-15", true)
        .addString("requestedBy", "scheduler", false)
        .toJobParameters();

JobExecution execution = jobLauncher.run(dailySettlementJob, parameters);

JobInstance instance = execution.getJobInstance();
Long instanceId = instance.getInstanceId();
Long executionId = execution.getId();
```

In this example, `businessDate` is identifying, so it determines the `JobInstance`. `requestedBy` is non-identifying, so it does not create a new instance when the launcher changes. The simple overloads such as `addString(key, value)` mark the parameter as identifying by default; use the overload with the boolean when you want to make the intent explicit.

A useful design rule is to classify parameters by business meaning before writing code:

| Parameter | Question to ask | Typical classification |
| --- | --- | --- |
| Settlement date | Is a different date a different settlement unit? | Identifying |
| Source file | Is a different file a different import batch? | Identifying |
| Requester | Does changing the requester create new business work? | Non-identifying |
| Processing mode that changes the result | Are the two modes two different logical runs? | Usually identifying |

There is no single correct list of parameters for every application. The identifying flag must reflect the boundary of the unit of work that the business wants to track and restart.

## What happens when the same Job is launched multiple times?

When `JobLauncher.run(job, parameters)` is called, the `JobRepository` looks up or creates a `JobInstance` based on the job name and the identifying parameters, and then decides whether a new `JobExecution` can be created.

| Situation | Typical behavior |
| --- | --- |
| No instance with this identity exists yet | Create the `JobInstance` and the first `JobExecution` |
| The previous instance is `FAILED` or `STOPPED` | A new `JobExecution` can be created to restart, if the job allows restart and the state is appropriate |
| The instance has an execution running | Another execution is not allowed to run concurrently for the same instance; you usually get a `JobExecutionAlreadyRunningException` |
| The instance is `COMPLETED` | It is not run again with the same identity; you usually get a `JobInstanceAlreadyCompleteException` |
| An identifying parameter changes | A new `JobInstance` is created and a new logical job begins |

The specific exceptions are declared in the Spring Batch API. The final behavior also depends on the state stored in the repository and the job's restart configuration.

For example: the first time, `dailySettlementJob` runs with `businessDate=2026-11-15` but fails while writing data. When launched again with the same job name and the same identifying parameter, Spring Batch finds the `JobInstance` for 15/11. If the instance can be restarted, the repository creates a new `JobExecution` attached to that instance. This is a restart of the same logical job, not the creation of a new logical job.

If `businessDate` is changed to `2026-11-16`, the identity changes. Spring Batch creates a new `JobInstance` for 16/11, regardless of whether the instance for 15/11 succeeded or failed.

## How does JobInstance support restart?

A restart is continuing to process a logical job that has had a previous execution but has not completed successfully. Spring Batch keeps the metadata of the instance and its executions so that the repository can determine the processing history.

A general restart flow:

```text
JobLauncher.run(job, identifying parameters)
                 |
                 v
       JobRepository finds the JobInstance
                 |
                 v
        Create the first JobExecution
                 |
          execute the steps
                 |
          +------+------+
          |             |
       FAILED        COMPLETED
          |
          v
 Launch again with the same identity
          |
          v
 Create a new JobExecution for the old instance
          |
          v
 Continue according to the restart state
```

A correct restart also depends on how the step and the data reading/writing components are designed. Readers or writers need to save appropriate state in the `ExecutionContext` if they want to continue from the position already processed. The step must have an appropriate restart configuration, and the processing operations must be designed to avoid creating duplicate data or causing inconsistencies when part of the work had been committed before the failure.

You should not add a random parameter or a new timestamp on each restart. If that parameter is identifying, Spring Batch will treat the new call as a different `JobInstance` and will not continue the history of the failed instance. Keep the identifying parameters unchanged so that you restart the correct logical job.

## When do you need to create a new JobInstance for the same Job?

There are cases where the business genuinely requires running another independent piece of work even though the job name and the main input data appear the same. For example, the system allows rerunning a settlement batch for the same day as a separate processing version after a new business request.

In that case, you need to add an identifying parameter that represents the identity of the processing run, such as `runId` or `revision`. Spring Batch also provides the `JobParametersIncrementer` mechanism, commonly used together with `RunIdIncrementer`, to generate the parameter set for the next instance in suitable launch flows.

```text
dailySettlementJob
  businessDate=2026-11-15, runId=1  -> JobInstance A
  businessDate=2026-11-15, runId=2  -> JobInstance B
```

Each different `runId` produces a different identity if it is marked identifying. This is the way to create a new logical job; it is not a mechanism for restarting instance A. Use this approach only when the business truly distinguishes those runs. If the goal is merely to continue a failed job, reuse the old identifying parameters.

## JobRepository and JobInstance metadata

The `JobRepository` manages the metadata of jobs, instances, executions, and step executions. With a repository configuration that uses a relational database, Spring Batch stores the metadata in tables with the `BATCH_` prefix.

Some important tables:

| Table | Role |
| --- | --- |
| `BATCH_JOB_INSTANCE` | Stores the identity of the `JobInstance`, including the job name and the key generated from the identifying parameters |
| `BATCH_JOB_EXECUTION` | Stores each execution, links back to the `JobInstance`, and records the time, status, and exit code |
| `BATCH_JOB_EXECUTION_PARAMS` | Stores the parameters attached to each execution, including the identifying information |
| `BATCH_STEP_EXECUTION` | Stores the execution history of each step within a job execution |
| `BATCH_JOB_EXECUTION_CONTEXT` | Stores the job-level execution context to support state recovery |
| `BATCH_STEP_EXECUTION_CONTEXT` | Stores the step-level execution context |

In `BATCH_JOB_INSTANCE`, the pair of job name and identifying parameters key is used to look up the instance. Therefore, two launches with the same job name and the same identifying parameters will resolve to the same logical job. Column names and schema details may differ between Spring Batch versions, but the roles of these metadata groups remain similar.

When investigating a run, you can follow the relationships:

```text
BATCH_JOB_INSTANCE
        |
        | JOB_INSTANCE_ID
        v
BATCH_JOB_EXECUTION
        |
        +---- BATCH_JOB_EXECUTION_PARAMS
        |
        +---- BATCH_STEP_EXECUTION
        |             |
        |             +---- BATCH_STEP_EXECUTION_CONTEXT
        |
        +---- BATCH_JOB_EXECUTION_CONTEXT
```

The `JobInstance` groups the attempts of the same logical job. The `JobExecution` stores the result of each attempt. The execution context stores the state needed for the continuation process. Do not confuse a `BATCH_JOB_EXECUTION` row with a `JobInstance`: one instance can have multiple executions according to its restart history.

## Practical design principles

**Choose identifying parameters according to business boundaries.** If a day, a file, a tenant, or a data range represents an independent unit of work, put that identifier into the identifying parameters.

**Keep identifying parameters stable across restarts.** The parameter set used to restart must point to the exact logical job that failed. Changing an identifying parameter creates a new instance and splits the restart history.

**Do not mark every parameter as identifying out of habit.** Operational information such as the requester or the trigger source usually does not determine the work identity. Use the non-identifying flag for values that truly do not change the processing scope and meaning.

**Do not use non-identifying for data that changes the business result.** If changing a parameter causes the job to process a different data set or produce a different logical result, keeping the same `JobInstance` can make the run history confusing and create risk when restarting.

**Distinguish a restart from an independent rerun.** A restart continues the old instance with the same identity. An independent rerun creates a new instance with a new identifying parameter, such as a processing session code.

**Rely on metadata for traceability.** When inspecting a job, look at the `JobInstance` first to understand the unit of work, then look at the `JobExecution`s to see each attempt and its state.

## Common scenarios

### Same day but a different launcher

Two calls to `dailySettlementJob` both have `businessDate=2026-11-15`, but `requestedBy` is `scheduler` and `operator` respectively. If `requestedBy` is non-identifying, both calls still point to the same `JobInstance`. If the previous execution has completed, the later call is still prevented from running again by the completed-instance rule.

### Restarting but accidentally changing the timestamp

The application adds `runTimestamp` to the parameters itself and leaves it as identifying by default. Each relaunch has a new timestamp and therefore creates a new `JobInstance`. The repository does not treat it as a restart of the old instance. If the timestamp is only for logging, mark it non-identifying; if it defines a separate business processing run, keep it identifying and accept that each value creates a new instance.

### Wanting to reprocess data that has completed

If the `JobInstance` is `COMPLETED`, relaunching with the same identifying parameters is usually rejected. First determine whether the request is to restart an incomplete run or to create an independent business processing run. For an independent request, use a new processing-run identifier according to the business rules and make sure the system is deliberate about writing the data again.

### Two different jobs using the same parameter

`dailySettlementJob` and `monthlySettlementJob` can both receive `businessDate=2026-11-15`. Because the job name is part of the identity, the two jobs still have two different `JobInstance`s.

## Key takeaways

A `JobInstance` is the representation of a logical job in Spring Batch. Its identity is determined by the `Job` name together with the `JobParameters` marked as identifying. An instance can have multiple `JobExecution`s, each execution corresponding to one execution attempt. By correctly distinguishing these three concepts, an application can identify work, store history, and restart a failed job without accidentally creating a different logical job.
