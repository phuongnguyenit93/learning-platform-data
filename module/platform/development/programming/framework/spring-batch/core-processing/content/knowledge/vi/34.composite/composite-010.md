# Output nhất quán giữa nhiều writer

Trong Spring Batch, một Step có thể cần ghi cùng một item ra nhiều nơi: bảng nghiệp vụ và bảng audit, hai bảng đích, file export và database, hoặc database và message broker. `CompositeItemWriter` hỗ trợ gọi nhiều Writer theo thứ tự trên cùng một chunk. Tuy nhiên, việc gọi nhiều Writer không tự động làm cho mọi output cùng commit hoặc rollback như một giao dịch nguyên tử.

Để output nhất quán, cần xác định rõ các Writer dùng chung transaction resource hay ghi sang các hệ thống độc lập. Với nhiều Writer ghi cùng database và cùng transaction manager, chunk transaction có thể bảo vệ tất cả thay đổi. Với nhiều database, file hoặc API bên ngoài, cần cơ chế phù hợp như XA/JTA, staging và publish, transactional outbox, idempotency key hoặc quy trình bù.

## 1. Khi nào một Step cần nhiều Writer?

Một item sau khi xử lý có thể cần được ghi vào nhiều đích:

- Bảng chính để lưu dữ liệu nghiệp vụ.
- Bảng audit để lưu lịch sử thay đổi.
- Bảng thống kê hoặc bảng tổng hợp.
- File CSV/XML để chuyển cho hệ thống khác.
- Message broker hoặc REST API để thông báo sự kiện.
- Bảng outbox để giao tiếp bất đồng bộ với hệ thống bên ngoài.

Ví dụ một Job import đơn hàng cần lưu cả bản ghi chính và lịch sử import:

```text
ItemReader
    |
    v
ItemProcessor
    |
    v
CompositeItemWriter
    |
    +--> OrderWriter       -> imported_order
    |
    +--> AuditWriter       -> order_audit
    |
    +--> OutboxWriter      -> outbox_event
```

Các Writer nhận cùng dữ liệu của chunk theo thứ tự đã cấu hình. Khi tất cả thao tác ghi hoàn tất, Spring Batch mới đi đến commit transaction của chunk. Kết quả cuối có nhất quán hay không còn phụ thuộc các delegate có thực sự tham gia cùng transaction hay không.

## 2. CompositeItemWriter hoạt động như thế nào?

`CompositeItemWriter<T>` là một Writer ủy quyền việc ghi cho danh sách Writer con. Mỗi lần `write(chunk)` được gọi, composite lần lượt gọi từng delegate theo thứ tự trong danh sách và truyền cùng chunk cho từng delegate.

Ví dụ có ba Writer A, B và C:

```text
write(chunk)
    |
    v
  Writer A
    |
    v
  Writer B
    |
    v
  Writer C
    |
    v
  return to Step
    |
    v
  transaction commit (nếu không có lỗi)
```

Điều này có nghĩa:

- Mọi delegate đều nhận cùng các item trong chunk.
- Các delegate được gọi tuần tự theo thứ tự cấu hình.
- Composite không tự chia chunk thành các nhóm item khác nhau.
- Nếu một delegate ném exception, quá trình ghi dừng tại delegate đó; các delegate phía sau có thể chưa được gọi.
- Exception được truyền về Step để transaction/retry/skip policy xử lý.

`CompositeItemWriter` phù hợp khi mọi đích đều cần nhận cùng một tập item. Nếu mỗi item chỉ nên đi đến một Writer tùy theo loại hoặc điều kiện, cần một cơ chế routing như `ClassifierCompositeItemWriter` thay vì broadcast toàn bộ chunk.

## 3. Cấu hình CompositeItemWriter bằng builder

Với Spring Batch 5, có thể cấu hình bằng `CompositeItemWriterBuilder`:

```java
import java.util.List;

import org.springframework.batch.item.ItemWriter;
import org.springframework.batch.item.support.CompositeItemWriter;
import org.springframework.batch.item.support.builder.CompositeItemWriterBuilder;
import org.springframework.context.annotation.Bean;

@Bean
public CompositeItemWriter<Order> compositeOrderWriter(
        ItemWriter<Order> orderWriter,
        ItemWriter<Order> auditWriter) {

    return new CompositeItemWriterBuilder<Order>()
            .delegates(List.of(orderWriter, auditWriter))
            .build();
}
```

`orderWriter` và `auditWriter` là hai delegate đã được cấu hình ở nơi khác. Thứ tự trong `List.of(...)` là thứ tự gọi. Nếu audit cần ghi sau khi bản ghi chính đã được xử lý, đặt `orderWriter` trước `auditWriter`.

Composite không tự biến các delegate thành transaction-aware. Mỗi delegate cần dùng transaction resource phù hợp và không được tự commit độc lập nếu muốn chunk rollback có tác dụng.

## 4. Ví dụ hai Writer ghi hai bảng trong cùng database

Đây là trường hợp dễ đạt tính nhất quán nhất: hai Writer ghi hai bảng trong cùng database, cùng dùng một `DataSource` và transaction manager của Step.

Giả sử có hai bảng:

```sql
CREATE TABLE imported_order (
    order_id VARCHAR(80) PRIMARY KEY,
    customer_id VARCHAR(80) NOT NULL,
    amount DECIMAL(18, 2) NOT NULL
);

CREATE TABLE order_audit (
    audit_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id VARCHAR(80) NOT NULL,
    action VARCHAR(40) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Writer chính:

```java
@Bean
public JdbcBatchItemWriter<Order> orderWriter(
        @Qualifier("businessDataSource") DataSource dataSource) {

    return new JdbcBatchItemWriterBuilder<Order>()
            .dataSource(dataSource)
            .sql("""
                    INSERT INTO imported_order(order_id, customer_id, amount)
                    VALUES (:orderId, :customerId, :amount)
                    """)
            .beanMapped()
            .build();
}
```

Writer audit:

```java
@Bean
public JdbcBatchItemWriter<Order> orderAuditWriter(
        @Qualifier("businessDataSource") DataSource dataSource) {

    return new JdbcBatchItemWriterBuilder<Order>()
            .dataSource(dataSource)
            .sql("""
                    INSERT INTO order_audit(order_id, action, created_at)
                    VALUES (:orderId, 'IMPORTED', CURRENT_TIMESTAMP)
                    """)
            .beanMapped()
            .build();
}
```

Hai Writer dùng cùng bean `businessDataSource`. Bảng `Order` trong ví dụ là JavaBean có các property `orderId`, `customerId` và `amount` để `beanMapped()` lấy giá trị.

Kết hợp và gắn vào Step:

```java
@Bean
public CompositeItemWriter<Order> compositeOrderWriter(
        @Qualifier("orderWriter") ItemWriter<Order> orderWriter,
        @Qualifier("orderAuditWriter") ItemWriter<Order> auditWriter) {

    return new CompositeItemWriterBuilder<Order>()
            .delegates(List.of(orderWriter, auditWriter))
            .build();
}

@Bean
public Step importOrdersStep(
        JobRepository jobRepository,
        @Qualifier("businessTransactionManager")
        PlatformTransactionManager transactionManager,
        ItemReader<Order> orderReader,
        CompositeItemWriter<Order> compositeOrderWriter) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<Order, Order>chunk(200, transactionManager)
            .reader(orderReader)
            .writer(compositeOrderWriter)
            .build();
}
```

`businessTransactionManager` phải quản lý đúng `businessDataSource` mà cả hai `JdbcBatchItemWriter` sử dụng. Nếu delegate thứ hai thất bại trước khi commit, các câu lệnh của delegate thứ nhất trong cùng transaction cũng được rollback. Đây là cách giữ bảng chính và bảng audit nhất quán trong một database transaction.

## 5. Transaction boundary quyết định tính nhất quán

Composite chỉ điều phối thứ tự gọi Writer. Transaction manager của Step quyết định những thay đổi nào được commit hoặc rollback cùng chunk.

| Cấu hình | Kết quả khi delegate sau thất bại |
|---|---|
| Hai JDBC Writer cùng DataSource và cùng transaction manager | Các thay đổi trong chunk có thể rollback cùng nhau. |
| Hai Writer dùng hai DataSource với hai local transaction manager | Transaction của Step không tự động rollback resource còn lại. |
| Writer JDBC cùng transaction và Writer gọi REST API | Database có thể rollback; API đã thành công không tự bị hoàn tác. |
| Hai file writer trên filesystem | Không có một transaction database chung bảo đảm hai file cùng commit nguyên tử. |
| Writer ghi DB và outbox cùng database transaction | Business data và outbox event có thể commit/rollback cùng nhau. |

Một chunk Step nhận một `PlatformTransactionManager` cho transaction chunk. Không nên cho rằng chỉ cần đặt nhiều delegate vào CompositeItemWriter thì mọi resource đều tham gia transaction đó.

Để một thao tác JDBC tham gia transaction của Step, `JdbcTemplate` hoặc `JdbcBatchItemWriter` phải dùng đúng `DataSource` mà transaction manager quản lý. Không tự mở connection riêng rồi gọi `commit()` bên trong Writer.

## 6. Điều gì xảy ra khi một delegate thất bại?

Giả sử composite gọi Writer A trước rồi Writer B. A ghi thành công, B ném exception:

```text
CompositeItemWriter.write(chunk)
    |
    +--> Writer A: ghi thành công
    |
    +--> Writer B: exception
              |
              v
        Exception về Step
              |
              v
        Chunk transaction rollback
              |
              v
        Retry / Skip / Job FAILED
```

Nếu A và B cùng ghi vào một database transaction, rollback sẽ hoàn tác thay đổi của A. Nếu A đã gửi HTTP request hoặc ghi vào một resource không tham gia transaction, tác dụng phụ của A có thể vẫn tồn tại dù Step rollback.

Khi retry chunk, CompositeItemWriter có thể gọi A lần nữa. Do đó, các delegate cần được thiết kế idempotent nếu có khả năng tạo side effect ngoài transaction hoặc có thể được chạy lại sau restart.

Không bắt rồi bỏ qua exception của delegate chỉ để Job tiếp tục. Nếu một output bắt buộc bị thiếu, Job có thể báo thành công trong khi các đích không còn nhất quán. Chỉ skip khi nghiệp vụ cho phép và trạng thái các output còn lại đã được xử lý rõ ràng.

## 7. Phân biệt CompositeItemWriter và ClassifierCompositeItemWriter

Hai cơ chế này có mục đích khác nhau:

| Cơ chế | Cách hoạt động | Khi sử dụng |
|---|---|---|
| `CompositeItemWriter` | Gửi toàn bộ chunk đến từng delegate theo thứ tự | Mỗi item cần được ghi vào nhiều output. |
| `ClassifierCompositeItemWriter` | Chọn Writer theo từng item bằng classifier | Mỗi item chỉ được gửi đến một output phù hợp. |

Ví dụ routing:

```text
Item A (priority)   -> PriorityWriter
Item B (standard)   -> StandardWriter
Item C (priority)   -> PriorityWriter
```

Nếu dùng CompositeItemWriter với hai delegate `PriorityWriter` và `StandardWriter`, cả hai sẽ nhận tất cả item. Điều đó có thể tạo dữ liệu sai. Với routing, dùng classifier để chọn delegate dựa trên thuộc tính của item.

Nếu yêu cầu là vừa route item đến một Writer, vừa ghi audit cho tất cả item, có thể xây dựng routing writer kết hợp với audit writer hoặc xử lý trong Processor/Writer chuyên biệt. Cần xác định rõ item nào phải xuất hiện ở từng output trước khi chọn pattern.

## 8. Đảm bảo thứ tự ghi giữa các delegate

Composite gọi delegate theo thứ tự cấu hình. Thứ tự này có thể quan trọng nếu Writer sau phụ thuộc vào kết quả Writer trước, ví dụ:

1. Ghi bản ghi cha.
2. Ghi bản ghi con tham chiếu khóa của bản ghi cha.
3. Ghi audit hoặc outbox event.

Ví dụ:

```java
.delegates(List.of(
        parentWriter,
        childWriter,
        auditWriter))
```

Tuy nhiên, thứ tự gọi không đồng nghĩa với commit riêng theo từng delegate. Trong cùng transaction, tất cả thao tác vẫn chờ transaction của chunk commit. Nếu `childWriter` thất bại, thao tác của `parentWriter` có thể rollback cùng chunk.

Không nên để một delegate phụ thuộc vào việc delegate trước đã commit độc lập, trừ khi kiến trúc transaction được thiết kế rõ ràng cho điều đó. Nếu cần giao tiếp bất đồng bộ, outbox thường phù hợp hơn việc gọi một hệ thống ngoài trực tiếp từ delegate kế tiếp.

## 9. Delegate có ItemStream và lifecycle

Một số Writer triển khai `ItemStreamWriter` hoặc `ItemStream`, ví dụ `FlatFileItemWriter`. Chúng cần lifecycle `open()`, `update()` và `close()` để mở file, lưu checkpoint và giải phóng tài nguyên.

`CompositeItemWriter` có thể quản lý lifecycle của các delegate `ItemStream` theo cấu hình mặc định. `CompositeItemWriterBuilder` có tùy chọn `ignoreItemStream`; không bật tùy chọn này nếu delegate cần checkpoint hoặc quản lý tài nguyên. Nếu một wrapper/composite tùy chỉnh không chuyển tiếp lifecycle, cần đăng ký delegate bằng `.stream(...)` trên Step.

Ví dụ khái quát:

```java
return new StepBuilder("exportStep", jobRepository)
        .<Order, Order>chunk(100, transactionManager)
        .reader(orderReader)
        .writer(compositeWriter)
        .build();
```

Khi composite tự quản lý stream delegate đúng cách, Step chỉ cần đăng ký composite. Nếu custom wrapper không chuyển tiếp `ItemStream`, có thể đăng ký delegate:

```java
.writer(customCompositeWriter)
.stream(fileWriterDelegate)
```

Không đăng ký cùng một delegate hai lần nếu wrapper đã chuyển tiếp lifecycle. Điều đó có thể khiến `open`, `update` hoặc `close` được gọi lặp.

Mỗi delegate có state cần một tên ổn định và key `ExecutionContext` không xung đột. Khi nhiều file writer cùng tham gia Step, đặt tên khác nhau và giữ nguyên qua các lần restart.

## 10. Ghi database và file trong cùng một Step

Một yêu cầu phổ biến là ghi dữ liệu vào database và đồng thời tạo file export. Có thể dùng CompositeItemWriter với `JdbcBatchItemWriter` và `FlatFileItemWriter`:

```java
@Bean
public CompositeItemWriter<Order> databaseAndFileWriter(
        JdbcBatchItemWriter<Order> databaseWriter,
        FlatFileItemWriter<Order> fileWriter) {

    return new CompositeItemWriterBuilder<Order>()
            .delegates(List.of(databaseWriter, fileWriter))
            .build();
}
```

`FlatFileItemWriter` có hỗ trợ transaction-aware buffering và checkpoint khi được cấu hình, đăng ký lifecycle và sử dụng đúng cách trong chunk Step. Tuy nhiên, filesystem không phải một database resource được local JDBC transaction manager quản lý. Không nên khái quát rằng mọi thao tác file, rename, copy hoặc delete đều rollback nguyên tử cùng database.

Với file bàn giao quan trọng, cách an toàn hơn là:

1. Ghi file vào tên tạm, ví dụ `orders.csv.part`.
2. Hoàn tất việc ghi database và file theo transaction semantics của từng resource.
3. Chạy bước kiểm tra số dòng, checksum và trạng thái Job.
4. Chỉ khi flow thành công mới publish/rename file sang tên chính thức.
5. Ghi manifest hoặc trạng thái `PUBLISHED` để consumer biết file sẵn sàng.

Nếu file và database cần cùng một kết quả nghiệp vụ, phải có quy trình xử lý khi một bên thành công còn bên kia thất bại. Staging và publish sau cùng thường dễ vận hành hơn việc giả định filesystem và database có một transaction chung.

## 11. Ghi vào nhiều database

Nếu các delegate dùng nhiều database khác nhau, một local `DataSourceTransactionManager` chỉ quản lý một DataSource. CompositeItemWriter không tự cung cấp distributed transaction.

Ví dụ rủi ro:

```text
Writer A -> Database A: COMMIT thành công
Writer B -> Database B: lỗi
Step     -> ROLLBACK transaction cục bộ

Database A vẫn có thể giữ dữ liệu đã commit.
```

Nếu bắt buộc mọi database cùng commit hoặc rollback như một giao dịch nguyên tử, cần transaction coordinator JTA/XA và các resource hỗ trợ XA, cùng cấu hình recovery phù hợp. Đây là lựa chọn có chi phí vận hành và độ phức tạp cao; phải kiểm thử tình huống coordinator hoặc database dừng giữa prepare/commit.

Nếu chấp nhận eventual consistency, có thể dùng:

- Outbox để lưu sự kiện cần gửi trong transaction của database nguồn.
- Consumer/Writer riêng ghi sang database đích.
- Idempotency key để nhận biết message được gửi lại.
- Retry có giới hạn và backoff.
- Reconciliation Step để phát hiện và sửa dữ liệu lệch.
- Compensating action nếu một bước không thể hoàn thành.

Chia các đích thành nhiều Step cũng giúp xác định rõ trạng thái từng giai đoạn, nhưng không tự tạo atomicity giữa các Step. Cần có khóa batch, trạng thái tiến trình và khả năng chạy lại an toàn.

## 12. Transactional outbox thay cho gọi API trong Composite Writer

Nếu một item cần được lưu database và gửi event, tránh gọi broker/API trực tiếp trong một delegate rồi kỳ vọng transaction database rollback được request bên ngoài.

Trong cùng transaction của chunk, ghi business data và outbox row:

```sql
CREATE TABLE outbox_event (
    event_id VARCHAR(120) PRIMARY KEY,
    event_type VARCHAR(80) NOT NULL,
    payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

```text
Chunk transaction
   |
   +--> BusinessWriter -> UPDATE order
   |
   +--> OutboxWriter   -> INSERT outbox_event
   |
COMMIT
   |
   v
Outbox dispatcher
   |
   +--> Gửi message tới broker/API
   +--> Đánh dấu đã gửi
```

BusinessWriter và OutboxWriter dùng cùng DataSource và transaction manager. Nếu một trong hai thất bại, cả business update và outbox insert rollback. Sau commit, dispatcher gửi event bên ngoài.

Dispatcher vẫn có thể gửi lại nếu broker đã nhận message nhưng ứng dụng dừng trước khi đánh dấu outbox row đã gửi. Consumer phải deduplicate bằng `event_id` hoặc idempotency key. Outbox giúp tránh mất event giữa database commit và send, còn consumer idempotent xử lý delivery lặp.

## 13. Idempotency cho từng delegate

Khi CompositeItemWriter được retry, tất cả delegate có thể được gọi lại từ đầu cho chunk đó. Do đó, mỗi delegate phải chịu được replay theo cách phù hợp với resource của nó.

Các biện pháp:

- Database Writer: unique constraint, upsert hoặc processed-item table theo business key.
- File Writer: checkpoint, tên file ổn định và staging/publish có kiểm soát.
- API Writer: idempotency key được server hỗ trợ.
- Message Writer: event ID ổn định và consumer deduplication.
- Audit Writer: unique key theo business event để không tạo nhiều audit record cho cùng một event nếu retry.

Không dùng `UUID.randomUUID()` bên trong `write()` để tạo định danh mới cho mỗi lần thử. Cùng một item phải có cùng key qua retry và restart.

Nếu audit cần ghi mỗi lần thử kỹ thuật để phục vụ vận hành, hãy phân biệt rõ attempt log với business audit. Attempt log có thể có execution ID/attempt number; business audit thường cần một event ID ổn định để không bị nhân đôi.

## 14. Xử lý exception và skip/retry trong CompositeItemWriter

Exception từ một delegate được truyền về Step. Step có thể rollback chunk và áp dụng retry/skip policy nếu exception thuộc nhóm được cấu hình.

Ví dụ:

```java
return new StepBuilder("importStep", jobRepository)
        .<Order, Order>chunk(100, transactionManager)
        .reader(orderReader)
        .writer(compositeWriter)
        .faultTolerant()
        .retry(TransientDataAccessException.class)
        .retryLimit(3)
        .skip(InvalidOrderException.class)
        .skipLimit(20)
        .build();
```

Chỉ cấu hình skip cho lỗi mà nghiệp vụ thực sự cho phép bỏ qua. Nếu delegate A đã tạo side effect ngoài transaction rồi delegate B ném exception, skip item có thể khiến output A tồn tại trong khi output B thiếu. Khi đó dữ liệu giữa các đích không nhất quán.

Không dùng `noRollback()` để che lỗi của một delegate khi chưa xác định tác động của việc commit các output trước đó. Nếu một output bắt buộc thất bại, thường nên rollback chunk và retry/fail theo policy, đồng thời bảo đảm các side effect ngoài transaction có idempotency.

## 15. Custom Writer điều phối nhiều output

Có thể tự viết một Writer điều phối khi cần logic phức tạp hơn CompositeItemWriter, ví dụ chuẩn hóa item, tính chung một metadata record hoặc ghi theo điều kiện. Tuy nhiên, custom composite phải xử lý đúng exception, transaction và ItemStream lifecycle.

Ví dụ khung đơn giản:

```java
import org.springframework.batch.item.Chunk;
import org.springframework.batch.item.ItemWriter;

public class OrderFanOutWriter implements ItemWriter<Order> {

    private final ItemWriter<Order> databaseWriter;
    private final ItemWriter<Order> auditWriter;

    public OrderFanOutWriter(
            ItemWriter<Order> databaseWriter,
            ItemWriter<Order> auditWriter) {
        this.databaseWriter = databaseWriter;
        this.auditWriter = auditWriter;
    }

    @Override
    public void write(Chunk<? extends Order> chunk) throws Exception {
        databaseWriter.write(chunk);
        auditWriter.write(chunk);
    }
}
```

Đây chỉ là minh họa fan-out. Trong ứng dụng thực tế, nếu delegate triển khai `ItemStream`, custom wrapper cần chuyển tiếp `open`, `update`, `close` hoặc đăng ký stream delegate trong Step. Không bắt exception rồi tiếp tục delegate tiếp theo khi output trước đã thất bại, trừ khi đó là chính sách nghiệp vụ được thiết kế rõ.

Nếu không có logic đặc biệt, `CompositeItemWriter` thường dễ bảo trì hơn custom wrapper vì nó đã cung cấp cơ chế delegate và hỗ trợ lifecycle.

## 16. Chọn thứ tự delegate và thiết kế output bắt buộc/tùy chọn

Không phải mọi output đều có cùng mức độ quan trọng. Hãy phân loại:

| Output | Tính bắt buộc | Cách xử lý khi lỗi |
|---|---|---|
| Bảng nghiệp vụ chính | Bắt buộc | Chunk rollback và Job retry/fail. |
| Audit phục vụ pháp lý | Thường bắt buộc | Ghi cùng transaction với dữ liệu chính nếu cùng database. |
| Outbox event | Bắt buộc nếu cần phát sự kiện | Ghi cùng transaction với business data. |
| Báo cáo phụ | Có thể tùy chọn | Tách Step riêng và cho phép tạo lại. |
| Email thông báo | Thường không nên là điều kiện commit dữ liệu chính | Gửi bất đồng bộ qua outbox; retry độc lập. |

Nếu một báo cáo phụ thất bại, có thể không cần rollback dữ liệu nghiệp vụ đã hoàn tất. Khi đó, tách báo cáo thành Step riêng giúp failure và retry của báo cáo không làm lặp side effect chính.

Đừng dùng CompositeItemWriter cho mọi output chỉ vì chúng cùng xuất phát từ một item. Hãy nhóm các output cần cùng transaction; tách những output có vòng đời hoặc mức độ quan trọng khác nhau thành Step hoặc workflow riêng.

## 17. Kiểm thử output consistency

Kiểm thử cần xác nhận dữ liệu ở tất cả đích, đặc biệt khi một delegate thất bại sau khi delegate trước đã ghi.

Các kịch bản quan trọng:

1. **Tất cả delegate thành công:** xác nhận cùng business key xuất hiện ở mọi output bắt buộc.
2. **Delegate thứ hai thất bại:** xác nhận các thay đổi database của delegate đầu rollback nếu chúng dùng cùng transaction.
3. **Retry chunk:** xác nhận delegate được gọi lại nhưng dữ liệu cuối không bị nhân đôi.
4. **Restart Job:** làm Step thất bại sau một số chunk đã commit, restart cùng JobInstance và kiểm tra mọi output.
5. **Nhiều database:** mô phỏng lỗi ở database thứ hai và xác nhận chính sách XA hoặc eventual consistency thực tế.
6. **File output:** xác nhận file tạm không được publish khi Job thất bại; file cuối chỉ xuất hiện khi publish Step thành công.
7. **Outbox:** xác nhận business row và outbox row cùng commit/rollback; dispatcher replay không tạo hiệu ứng trùng ở consumer.
8. **Concurrency:** hai worker cùng business key không tạo dữ liệu trùng ở các đích.
9. **Lifecycle:** xác nhận các delegate ItemStream được open/update/close đúng số lần và checkpoint được lưu.

Ví dụ assertion với hai bảng cùng database:

```java
Integer orderCount = jdbcTemplate.queryForObject(
        "select count(*) from imported_order where order_id = ?",
        Integer.class,
        "ORD-1001");

Integer auditCount = jdbcTemplate.queryForObject(
        "select count(*) from order_audit where order_id = ? and action = ?",
        Integer.class,
        "ORD-1001",
        "IMPORTED");

assertEquals(1, orderCount);
assertEquals(1, auditCount);
```

Để kiểm tra rollback, cấu hình audit Writer ném exception có kiểm soát sau khi order Writer đã chạy; sau Job failure, xác nhận cả hai bảng không giữ thay đổi của chunk thất bại. Nếu các delegate ghi ra resource độc lập, viết test phản ánh chính xác giới hạn transaction của kiến trúc đó thay vì kỳ vọng rollback không được hỗ trợ.

## 18. Những lỗi thường gặp

| Lỗi | Hậu quả | Cách xử lý |
|---|---|---|
| Nghĩ Composite tự tạo distributed transaction | Một database/file/API có thể đã ghi dù delegate khác thất bại. | Xác định transaction resource và dùng XA/outbox/staging khi cần. |
| Nhầm fan-out với routing | Mọi item bị ghi vào tất cả delegate dù chỉ cần một đích. | Dùng classifier writer cho routing theo item. |
| Delegate dùng DataSource khác transaction manager | Rollback chunk không hoàn tác mọi thay đổi. | Dùng cùng DataSource/TM hoặc cơ chế phân tán. |
| Nuốt exception của delegate | Job có thể thành công với output thiếu. | Truyền exception về Step và xử lý bằng policy rõ ràng. |
| Delegate không idempotent | Retry/restart có thể tạo side effect trùng. | Business key, unique constraint, idempotency key. |
| Bỏ qua ItemStream lifecycle | File writer hoặc delegate không lưu checkpoint/đóng tài nguyên. | Để Composite chuyển tiếp lifecycle hoặc đăng ký `.stream(...)`. |
| Đăng ký delegate stream hai lần | Lifecycle có thể bị gọi lặp. | Chỉ đăng ký một đường lifecycle cho mỗi delegate. |
| Dùng chung output file cho nhiều execution | Dữ liệu có thể xen kẽ hoặc ghi đè. | Tạo file riêng theo batch/JobInstance và publish có kiểm soát. |
| Đưa email/API trực tiếp vào delegate cùng transaction DB | Side effect ngoài DB không rollback khi chunk lỗi. | Dùng outbox và gửi bất đồng bộ. |
| Dùng `noRollback()` tùy tiện | Một phần output có thể được commit dù output khác lỗi. | Chỉ dùng khi đã chứng minh trạng thái sau commit vẫn hợp lệ. |

## Kết luận

`CompositeItemWriter` gửi cùng chunk lần lượt đến nhiều delegate, phù hợp khi mỗi item cần xuất hiện ở nhiều output. Tính nhất quán phụ thuộc vào transaction resource: các JDBC Writer dùng cùng DataSource và transaction manager có thể commit/rollback cùng chunk; file, API hoặc database độc lập không tự động tham gia một transaction nguyên tử. Hãy giữ thứ tự delegate có chủ đích, quản lý `ItemStream` lifecycle, truyền exception về Step và thiết kế từng delegate idempotent. Với output ngoài database, dùng staging/publish, transactional outbox, XA/JTA hoặc reconciliation theo yêu cầu thực tế. Kiểm thử tình huống delegate sau thất bại, retry, restart và concurrency để xác nhận tất cả output bắt buộc cùng phản ánh một kết quả nghiệp vụ.
