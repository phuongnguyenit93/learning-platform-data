# Large XML resources and streaming

When Spring Batch needs to process a very large XML file, reading the entire document into a DOM tree is usually unsuitable. DOM creates objects representing most or all of the XML structure in memory. With files containing millions of elements, memory usage can grow rapidly, causing continuous garbage collection or OutOfMemoryError.

A more suitable approach is **streaming**: the parser reads XML sequentially, locates each business element to process, converts one fragment into an object, and hands that object to the chunk pipeline. Spring Batch provides **StaxEventItemReader** to read XML fragments in streaming fashion and combines with Spring OXM, such as Jaxb2Marshaller, to convert fragments into Java objects.

Streaming makes memory depend mainly on the fragment being read and the chunk being processed, rather than the entire document. However, it does not make every XML lightweight: an overly large single fragment, a deeply nested object graph, or too high a chunk size can still consume substantial memory.

## 1. Why does large XML need streaming?

An XML file can contain hundreds of thousands or millions of records:

~~~xml
<orders>
    <order>
        <id>1001</id>
        <customerId>C001</customerId>
        <amount>125.50</amount>
    </order>
    <order>
        <id>1002</id>
        <customerId>C002</customerId>
        <amount>89.00</amount>
    </order>
    <!-- Millions of other orders -->
</orders>
~~~

If the application uses a DOM parser to parse the entire file, the parser may create a node for every element, attribute, and text node. Then the code typically holds the entire Document or list of objects in memory.

With large files, the cost is not only the file size on disk. A 1 GB XML file can create a significantly larger object graph in the JVM due to object headers, references, Strings, collections, and decoded data.

Streaming processes sequentially:

~~~text
XML file
   |
   v
StAX parser reads events
   |
   v
Find <order> fragment
   |
   v
Unmarshal one order
   |
   v
ItemProcessor
   |
   v
ItemWriter
   |
   v
Commit chunk
   |
   v
Read next fragment
~~~

The parser does not need to keep the entire document in memory. Once the current fragment has been converted into an object and processed, unreferenced events and objects can be reclaimed by the garbage collector.

## 2. How do DOM, SAX, and StAX differ?

Java has multiple XML parsing models. Choosing the right model depends on how the application needs to access the document.

| Model | How it works | Memory and usage |
|---|---|---|
| DOM | Parses into a document tree | Easy random access, typically keeps many nodes in memory |
| SAX | Parser emits callbacks on start/end elements and text | Streaming, low memory, but callback code must manage state |
| StAX | Application actively pulls events from the parser | Streaming, easy to control sequential reading progress |
| JAXB | Maps XML to Java objects | A binding layer; can be used with StAX to unmarshal fragment by fragment |

DOM is convenient when the document is small and random access to multiple locations is needed. SAX fits event-driven pipelines. StAX fits when the application wants to actively pull the next event and process fragments in order.

JAXB is not a standalone streaming model for an entire file. If you unmarshal the entire root document into an object containing a large list, the application may still retain the full object graph. Combining StAX with JAXB fragment by fragment limits the scope of instantiated objects.

## 3. What is StAX?

StAX (Streaming API for XML) provides a way to read and write XML via events or a cursor.

Two primary reading APIs:

- XMLStreamReader: cursor-based; the application calls next() to move to the next event.
- XMLEventReader: iterator/event-based; returns each XMLEvent.

Some common events:

- START_DOCUMENT and END_DOCUMENT.
- START_ELEMENT and END_ELEMENT.
- CHARACTERS or CDATA.
- COMMENT and PROCESSING_INSTRUCTION.

Example reading events with XMLStreamReader:

~~~java
XMLInputFactory factory = XMLInputFactory.newFactory();

try (InputStream input = Files.newInputStream(path)) {
    XMLStreamReader reader =
            factory.createXMLStreamReader(input);

    try {
        while (reader.hasNext()) {
            int event = reader.next();

            if (event == XMLStreamConstants.START_ELEMENT) {
                System.out.println(reader.getLocalName());
            }
        }
    } finally {
        reader.close();
    }
}
~~~

This is a basic example illustrating the cursor. In real applications, handle exceptions, close both the stream and parser following proper lifecycle rules, and configure the parser securely for untrusted XML.

Spring Batch's StaxEventItemReader uses the StAX event model to locate fragments and pass each fragment to the Unmarshaller.

## 4. What is a fragment?

In a large XML document, a fragment is a child element representing an independently processable business unit.

Example:

~~~xml
<orders>
    <order>
        <id>1001</id>
        <amount>125.50</amount>
    </order>
    <order>
        <id>1002</id>
        <amount>89.00</amount>
    </order>
</orders>
~~~

Here:

- orders is the document root element.
- order is the fragment root.
- Each order can become an item in Spring Batch.

The reader finds each order element, builds a representation for that fragment, and calls the Unmarshaller to convert it into an Order object.

Do not choose an overly large root element if it contains the entire list of records. If the fragment root is orders, the reader may have to unmarshal the whole set of orders at once, losing the benefits of streaming.

## 5. StaxEventItemReader in Spring Batch

StaxEventItemReader is an ItemReader that uses StAX to read individual XML fragments. It is usually paired with a Spring OXM Unmarshaller.

Key configurations:

- Resource: the input XML file or resource.
- Fragment root element: element name representing one item.
- Unmarshaller: converts the fragment into a Java object.
- saveState: saves reader state to support restarts.
- strict: determines whether the reader fails if the resource does not exist.
- XMLInputFactory: configures the StAX parser.

The reader is used in a chunk Step like a standard ItemReader. Each read() call returns one unmarshalled object; when no fragments remain, the reader returns null.

## 6. Declaring a Java model for XML fragments

Suppose each order has an ID, customer ID, and amount:

~~~java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    private Long id;

    private String customerId;

    private BigDecimal amount;

    public Long getId() {
        return id;
    }

    public String getCustomerId() {
        return customerId;
    }

    public BigDecimal getAmount() {
        return amount;
    }
}
~~~

Element names and mappings must match the actual XML. If the XML uses namespaces, declare the corresponding namespaces in JAXB annotations or package-level schema mappings.

XML example:

~~~xml
<order>
    <id>1001</id>
    <customerId>C001</customerId>
    <amount>125.50</amount>
</order>
~~~

If the model uses a field name different from the element name, use annotations like XmlElement. For attributes instead of child elements, use XmlAttribute.

## 7. Configuring Jaxb2Marshaller

Spring OXM provides Jaxb2Marshaller to configure JAXB bindings:

~~~java
@Bean
public Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    return marshaller;
}
~~~

You can use context path or packagesToScan depending on how models are organized. With an explicit list of classes, classesToBeBound precisely defines the supported object types.

The Unmarshaller receives the XML fragment and creates an OrderXml. Because the reader only passes one fragment at a time, the application does not need to instantiate an object containing the entire list of orders.

JAXB mappings still must be controlled: data types, nullability, namespaces, date/time formats, adapters, and validation can all cause unmarshalling failures.

## 8. Configuring StaxEventItemReaderBuilder

Example reader processing each order element:

~~~java
@Bean
@StepScope
public StaxEventItemReader<OrderXml> orderXmlReader(
        @Value("#{jobParameters['inputFile']}") Resource resource,
        Jaxb2Marshaller orderMarshaller) {

    XMLInputFactory inputFactory = XMLInputFactory.newFactory();
    inputFactory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
    inputFactory.setProperty(
            XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES,
            false);

    return new StaxEventItemReaderBuilder<OrderXml>()
            .name("orderXmlReader")
            .resource(resource)
            .addFragmentRootElements("order")
            .unmarshaller(orderMarshaller)
            .xmlInputFactory(inputFactory)
            .saveState(true)
            .strict(true)
            .build();
}
~~~

Meaning:

- name provides a stable name for the reader and checkpoints.
- resource specifies the input XML file.
- addFragmentRootElements("order") specifies the element read as an item.
- unmarshaller converts the fragment into OrderXml.
- xmlInputFactory supplies the configured parser.
- saveState(true) allows the reader to save reading progress.
- strict(true) requires the resource to exist under the reader's strict mode.

Builder methods must match the project's Spring Batch version. On versions with a different API, use the corresponding setters on StaxEventItemReader.

Creating XMLInputFactory inside the StepScope bean gives each StepExecution its own parser factory. Do not share a mutable parser or reader across multiple workers if the implementation does not guarantee thread safety.

## 9. XMLInputFactory and parser security

XML can contain DTDs and external entities. If the parser allows resolving external entities from files or URLs, untrusted XML can access unintended resources, causing data leaks or unnecessary load.

For untrusted input files, disable DTDs and external entities when supported by the parser provider:

~~~java
XMLInputFactory factory = XMLInputFactory.newFactory();

factory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
factory.setProperty(
        XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES,
        false);
~~~

Depending on the StAX provider, some properties may be unsupported or behave differently. Verify the actual configuration and fail startup if mandatory security policies cannot be applied. Do not silently ignore security configuration errors.

Do not enable DTDs or external entities just to handle a file with entity references without evaluating the data source. If the XML needs internal entities, define safe support and restrict the parser per the file contract.

## 10. Streaming memory depends on fragments and chunks

Streaming does not mean memory is always tiny. One way to picture it:

~~~text
Step Memory
  =
  parser buffers
  + current XML fragment
  + unmarshalled object
  + items in chunk
  + processor/writer working set
~~~

If the order fragment is small and chunk size is 100, memory is usually much easier to control than parsing the entire document into one huge List.

However, if one fragment contains hundreds of thousands of child transactions, that fragment alone can still be huge. JAXB will build an object graph for the entire fragment. Pick the fragment root at a reasonable processing unit level.

Measures to take:

- Pick small, self-contained fragment roots.
- Do not retain processed item lists in singletons or listeners.
- Limit nested collections inside a single fragment if possible.
- Pick chunk size according to actual object size.
- Avoid having the processor retain references to fragments after processing.
- Monitor heap, allocation rate, and garbage collection when running representative data.

## 11. Chunk size affects memory and transactions

StaxEventItemReader returns one fragment at a time, while chunk size determines how many items are held within one transaction before committing.

Example:

~~~java
@Bean
public Step importOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<OrderXml> orderXmlReader,
        ItemProcessor<OrderXml, Order> orderProcessor,
        ItemWriter<Order> orderWriter) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<OrderXml, Order>chunk(100, transactionManager)
            .reader(orderXmlReader)
            .processor(orderProcessor)
            .writer(orderWriter)
            .build();
}
~~~

Small chunk size:

- Reduces the number of objects simultaneously in the working set.
- Commits more frequently.
- May increase transaction and I/O overhead.

Large chunk size:

- May improve throughput with batch writers.
- Holds more items in memory.
- Longer transactions and more expensive rollbacks.

Benchmark with realistic fragment sizes. Do not pick a chunk size based solely on total file size.

## 12. XML with namespaces

XML often uses namespaces:

~~~xml
<orders xmlns="urn:example:orders">
    <order>
        <id>1001</id>
        <amount>125.50</amount>
    </order>
</orders>
~~~

The order element has the namespace URI urn:example:orders. Two elements with the same local name but different namespaces are two distinct XML names.

When using JAXB, the model must declare the appropriate namespace:

~~~java
@XmlRootElement(
        name = "order",
        namespace = "urn:example:orders")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {
    // Fields...
}
~~~

Check how your version of StaxEventItemReader matches fragments when namespaces are present. The builder accepts fragment root names per its API; if the document uses multiple namespaces with the same local name, verify the reader can distinguish them properly or use a custom QName-based fragment reader.

Do not remove namespaces from XML just to simplify mapping if the namespace is part of the data contract.

## 13. Nested XML and picking the fragment root

Not every repeating element is an independent record.

Example:

~~~xml
<orders>
    <order>
        <id>1001</id>
        <lines>
            <line>
                <sku>A-01</sku>
                <quantity>2</quantity>
            </line>
            <line>
                <sku>B-02</sku>
                <quantity>1</quantity>
            </line>
        </lines>
    </order>
</orders>
~~~

If you choose order as the fragment root, one OrderXml item contains the entire line list. This is usually the right choice if business logic processes orders intact.

If you choose line as the fragment root, the reader yields each line separately, but you need to know the order ID and parent context. A StAX fragment reader does not automatically retain ancestor objects like an ORM graph. A custom reader or a change in processing structure may be needed.

Select the fragment root by the business unit that can be processed independently. Do not pick a child element just because it repeats many times.

## 14. Multiple fragment types in one file

A document can contain multiple record types:

~~~xml
<batch>
    <order>...</order>
    <customer>...</customer>
    <order>...</order>
</batch>
~~~

StaxEventItemReader can be configured to accept multiple fragment roots per the corresponding version's API, but the return type and handling of different record types must be designed clearly.

One option is creating a common envelope class or hierarchy model. Another option is using a custom reader returning a sealed type or interface, then having the processor branch by fragment type.

If record order and type matter, the reader must preserve document order. If fragment types have distinct schemas and lifecycles, splitting into separate Steps or ingest pipelines may be easier to operate.

Do not configure a reader to return a generic item type if the unmarshaller cannot safely determine the fragment type.

## 15. XML encoding and XML declaration

XML can declare encoding in its prolog:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    ...
</orders>
~~~

When the parser receives a raw byte stream, the XML parser can use the BOM and XML declaration to determine encoding per XML rules. Avoid wrapping InputStream in an InputStreamReader using the platform default charset before passing it to StAX, because bytes will already be decoded with a potentially wrong charset.

With Spring Resource, StaxEventItemReader works with the resource and StAX parser. Ensure the input is a byte stream and the XML declaration matches the actual encoding.

If the file has no declaration, XML has its own default encoding and autodetection rules. Do not guess arbitrarily; require the source to state its charset and test with real bytes.

## 16. Non-well-formed XML and end-of-file errors

A streaming parser discovers errors when it reaches the position with invalid structure. A file may contain hundreds of thousands of valid fragments before the parser hits a missing closing tag at the end.

Example:

~~~xml
<orders>
    <order><id>1</id></order>
    <order><id>2</id></order>
    <!-- End of file is truncated -->
~~~

Earlier chunks may have already committed. When the parser reaches EOF and detects non-well-formed XML, the Step fails. Rollback applies only to the current chunk's transaction; previously committed chunks remain persisted.

Therefore, if consumers expect output as a complete document, do not publish the final output before the Job succeeds. Writing to staging and publishing after Step/Job completion reduces the risk of consumers reading incomplete results.

## 17. Validating XML with XSD without loading the entire document

A large file may need validation against an XML Schema. Avoid parsing the entire file into DOM just to validate.

The Java XML Validation API can work over streams or SAX sources. You can use Validator with SAXSource or a properly designed SAX/StAX pipeline to validate while reading.

Conceptual example using Validator and StreamSource:

~~~java
SchemaFactory schemaFactory =
        SchemaFactory.newInstance(
                XMLConstants.W3C_XML_SCHEMA_NS_URI);

Schema schema = schemaFactory.newSchema(xsdResource.getURL());

Validator validator = schema.newValidator();

try (InputStream input = xmlResource.getInputStream()) {
    validator.validate(new StreamSource(input));
}
~~~

This approach validates the stream without requiring the application to build a full DOM manually. However, it performs a separate read pass before Spring Batch processing, so the file may be read twice.

If you need to validate and process in a single pass, design a streaming pipeline attaching schema validation to the parser or a custom reader. Do not assume StaxEventItemReader automatically validates XSD just because JAXB mapping succeeds.

For XSD imports/includes, control schema locations and external access. Do not allow untrusted XML or schemas to fetch arbitrary resources.

## 18. Handling invalid records

A fragment may be well-formed yet invalid against a schema or business rules.

There are three distinct error classes:

1. **XML syntax error**: XML structure is not well-formed; the parser may not safely continue.
2. **Binding error**: the fragment cannot map to Java types, such as invalid number or date formats.
3. **Business validation error**: the object is created, but the data fails business rules.

Not all XML errors are suitable for skipping. If the whole document is truncated or tags are improperly nested, subsequent fragment boundaries may be indeterminable. The Step should usually fail.

If an individual fragment is structurally valid but has an invalid value, translate it into a business exception in the processor and apply a skip policy if business rules allow.

For unmarshal errors, classify specific exceptions if the reader throws stable exception types in your framework version. Test actual exceptions and avoid overly broad skips.

## 19. Restart and StaxEventItemReader state

StaxEventItemReader supports ItemStream and can save state when saveState(true) is set. The reader name must be stable so the reader restores its corresponding checkpoint.

Example:

~~~java
return new StaxEventItemReaderBuilder<OrderXml>()
        .name("orderXmlReader")
        .resource(resource)
        .addFragmentRootElements("order")
        .unmarshaller(orderMarshaller)
        .saveState(true)
        .build();
~~~

When the Step restarts, the reader uses saved state to resume at the item position. The exact positioning mechanism depends on the implementation and version. Some readers count read items and must parse/skip fragments prior to the checkpoint upon reopening; therefore, restarting near the end of a huge XML file can take noticeable startup time.

Measure restarts with realistically sized files, not only the initial run. If seek/replay time becomes an issue, split the source into smaller files, build an index/manifest, or design resource-based partitioning.

Conditions that must remain stable:

- Reader name.
- Fragment root configuration.
- Immutable resource content.
- Charset and XML namespace/schema mapping.
- Ordering of fragments in the document.

If the file is modified between the initial run and restart, the item-count checkpoint may point to a different fragment.

## 20. StepScope and runtime XML resources

File paths are usually passed via JobParameters. The reader should use StepScope to late-bind the Resource:

~~~java
@Bean
@StepScope
public StaxEventItemReader<OrderXml> orderXmlReader(
        @Value("#{jobParameters['inputFile']}") Resource resource,
        Jaxb2Marshaller orderMarshaller) {
    // ...
}
~~~

StepScope ensures the reader is instantiated within the StepExecution scope and receives the current run's resource.

JobParametersValidator should validate required inputFile parameters before the Step runs. You can check resource existence and readability in a preparation step. Do not wait until the reader opens a massive file to discover a missing parameter or wrong path.

If the resource resides on network storage or object storage, verify content stability across restarts and the streaming capabilities of the Resource implementation.

## 21. Large XML and compressed files

XML can be gzip-compressed to reduce storage and network transfer. When using compressed resources, open a decompression stream before the parser receives XML bytes.

A pipeline might look like:

~~~text
orders.xml.gz
     |
     v
GZIPInputStream
     |
     v
StAX parser
     |
     v
XML fragments
     |
     v
Unmarshaller
     |
     v
Chunk processing
~~~

Things to keep in mind:

- The resource must be reopenable multiple times if reader restart needs to reopen it.
- GZIPInputStream is a sequential stream; you cannot seek arbitrarily like a regular file.
- Restart may need to decompress and skip past fragments before the checkpoint.
- Decompression CPU speed can become a bottleneck.
- A corrupted gzip file may only reveal checksum errors at the end of the stream.

For very large compressed files with frequent restarts, consider splitting the archive into independent files or using an indexed format. A non-random-access stream resource can make restarts slow.

## 22. Partitioning large XML

You can split a large XML source into multiple parts for parallel processing, but XML is a structured document. Never split files arbitrarily by bytes or lines, as you may cut in the middle of a tag, attribute, entity, or multibyte character.

Safer strategies:

- Split the file upstream into multiple independent XML documents, each with a valid root.
- Use a streaming ingest step to produce valid shards aligned on fragment boundaries.
- Store a manifest with shard names, checksums, and record counts.
- Have each worker read one shard using its own StaxEventItemReader.
- Use the partition context to pass resource paths and metadata to workers.

If you want to partition a single XML file directly, you need an indexing/byte-offset mechanism that understands XML structure and encoding. Do not split purely by byte ranges.

## 23. StAX parsers and concurrency

XMLInputFactory and parser/reader objects are typically not designed to be shared arbitrarily across threads. An XMLStreamReader or XMLEventReader is a stateful cursor; do not share it across multiple workers.

With partitioning:

- Each worker should have its own reader and parser state.
- Each worker receives its own resource or shard.
- Use StepScope for stateful readers.
- Do not share XMLStreamReader across threads.
- If workers read the same resource, use an explicit partitioning/indexing design.

An XMLInputFactory may be shared depending on the provider, but the safest approach is creating a factory per reader or confirming provider concurrency support in documentation. Do not infer thread safety merely because a factory is a singleton object.

## 24. Streaming large XML output

If a Job needs to export large XML, avoid building a DOM or an object graph holding the entire output. You can use a StAX XMLStreamWriter to write records sequentially.

Conceptual example:

~~~java
XMLStreamWriter writer =
        XMLOutputFactory.newFactory()
                .createXMLStreamWriter(outputStream, "UTF-8");

writer.writeStartDocument("UTF-8", "1.0");
writer.writeStartElement("orders");

for (Order order : orders) {
    writer.writeStartElement("order");

    writer.writeStartElement("id");
    writer.writeCharacters(order.id().toString());
    writer.writeEndElement();

    writer.writeStartElement("amount");
    writer.writeCharacters(order.amount().toPlainString());
    writer.writeEndElement();

    writer.writeEndElement();
}

writer.writeEndElement();
writer.writeEndDocument();
writer.flush();
writer.close();
~~~

In Spring Batch, a custom ItemWriter can keep the XMLStreamWriter open across the ItemStream lifecycle and write chunk by chunk. Implement open/update/close to manage resources and restarts.

The writer must produce well-formed XML across multiple committed chunks. If the Job stops mid-way, the file may lack a closing root element. Write to staging and publish only after the Job completes successfully.

## 25. Custom streaming writers and restart

With a custom XML writer, checkpoints must store enough information to resume at the exact position, or the restart strategy must be redesigned.

Some options:

- Write independent XML shard files instead of appending to a single document.
- Store byte positions if safe recovery is possible and encoding/format is stable.
- Write individual fragments to temporary files and assemble the root document in a final step.
- Use a restart-capable writer that manages state via ItemStream.
- On restart, recreate output from the checkpoint or clean up incomplete staging files per policy.

Do not simply store a byte offset if the writer cannot guarantee the offset aligns with an XML boundary and encoding. In UTF-8, a miscalculated offset can land mid-multibyte character. Also account for closing tags, namespace declarations, and XMLStreamWriter state.

For many systems, producing independent XML shard files and merging them in a final streaming step is easier to restart and reconcile than appending to a single document across multiple transactions.

## 26. Handling errors mid-way through a large XML file

A large file can fail due to:

- Malformed XML.
- Unmarshallable fragment.
- Business validation failure.
- Database writer error.
- Lost resource or out of disk space.
- JVM termination while reading or writing.

When the reader hits an XML parse error on a late fragment, previously committed chunks remain persisted. Restart can restore reader state if the file is unchanged and the reader supports saveState.

If the input file was replaced, the checkpoint is no longer trustworthy. Store a checksum or immutable resource identifier as Job metadata.

If an XML output is partially written, prevent consumers from reading it as a finished document. Use staging names, publish states, or manifests so it is exposed only upon completion.

## 27. Monitoring and resource limits

For large XML, track these metrics:

| Metric | Purpose |
|---|---|
| readCount | Number of fragments read successfully |
| processCount | Number of items processed |
| writeCount | Number of items written |
| readSkipCount | Fragments skipped due to read errors |
| processSkipCount | Items skipped due to business errors |
| commitCount | Number of committed chunks |
| rollbackCount | Number of rollbacks |
| read/processor/write duration | Identify bottlenecks |
| heap usage | Monitor memory |
| GC pause/allocation rate | Detect object allocation pressure |
| input bytes and checksum | Identify the resource being processed |

Logs should include JobExecution ID, StepExecution ID, resource name, and fragment business key if available. Do not log entire XML fragments, as that can bloat logs or expose sensitive data.

Enforce limits on file size, XML depth, fragment count, and fragment size if the source is untrusted. Streaming parsers reduce whole-document memory but do not automatically protect against an enormous single fragment or malicious input.

## 28. Testing streaming readers

Include fixtures with multiple fragments and assert each fragment is returned as a separate item.

XML example:

~~~xml
<orders>
    <order><id>1</id><amount>10.00</amount></order>
    <order><id>2</id><amount>20.00</amount></order>
    <order><id>3</id><amount>30.00</amount></order>
</orders>
~~~

Tests should verify:

- Reader returns three OrderXml objects.
- ID and amount are unmarshalled accurately.
- The next read returns null.
- Reader close releases the stream.
- Reader can reopen and restore state from ExecutionContext.
- Namespaces and encoding are handled accurately.

Do not only test JAXB unmarshalling on a single object directly. Test StaxEventItemReader to confirm fragment boundaries and record ordering.

## 29. Testing large XML and memory behavior

Create test files with enough fragments to exercise real streaming, without necessarily committing a huge file into the repository.

You can stream-generate fixtures:

~~~java
try (BufferedWriter writer = Files.newBufferedWriter(
        xmlPath,
        StandardCharsets.UTF_8)) {

    writer.write("<orders>");

    for (int i = 1; i <= 1_000_000; i++) {
        writer.write("<order><id>");
        writer.write(Integer.toString(i));
        writer.write("</id></order>");
    }

    writer.write("</orders>");
}
~~~

Run the Step and verify total readCount/writeCount. Monitor heap in an appropriate test environment to observe whether memory grows linearly with fragment count or stays relatively flat.

A purely functional test does not prove streaming if the file is too small. Verify the implementation does not hold all items in a List, no listener accumulates objects, and the writer does not buffer the entire output.

## 30. Testing malformed XML and invalid fragments

Cases to include:

- Missing closing tag at the end of the file.
- Improperly nested tags.
- Attribute or element incompatible with JAXB types.
- Mismatched namespace.
- Entity reference rejected per security policy.
- Business fragment missing required field.
- Empty file or missing root element.
- File truncated mid-multibyte character.
- Compressed file corrupted at end of stream.

Verify error type, Step status, and committed data. For malformed XML, do not assume the reader can skip one fragment and continue, because the parser may lose the ability to determine document structure.

## 31. Testing restart with large XML

A restart test should run the same JobInstance across two JobExecutions:

~~~text
Input: 10 fragments
Chunk size: 3

First run:
  Fragments 1-3 -> COMMIT
  Fragments 4-6 -> COMMIT
  Fragments 7-9 -> error before COMMIT

Restart:
  Reader restores committed checkpoint
  Uncommitted fragments are re-read
  Fragment 10 is processed

Result:
  Every valid fragment is processed exactly once
~~~

Verify:

- Reader name is unchanged.
- saveState is enabled.
- Identifying JobParameters remain unchanged.
- Input file has the same checksum.
- Reader resumes at the right fragment.
- Committed chunks are not written twice.
- Uncommitted chunk is reprocessed.
- Output is published after Job succeeds.

For very large files, also measure reader initialization time on restart. If the reader must re-read fragments before the checkpoint, that time can grow with the checkpoint position.

## 32. Common pitfalls

### Using DOM for very large files

DOM keeps many nodes of the entire document in memory. Use StAX/SAX or split the file into smaller documents.

### Picking the document root as fragment

The Unmarshaller receives the entire huge record list and builds a massive object graph. Choose a child element representing one business item.

### Thinking JAXB streams automatically

Unmarshalling the entire root can still load the whole list into memory. Combine JAXB with StAX fragment by fragment.

### Overly large single fragment

Streaming still must materialize the current fragment. Pick a smaller fragment root or process nested contents with custom streaming logic.

### XMLInputFactory allowing external entities

Risks unintended resource access. Disable DTDs and external entities as supported by the provider, and test security policies.

### Ignoring namespaces

Fragment matching or JAXB binding fails to match elements properly. Declare namespaces and test actual QNames.

### Picking the wrong fragment root on multiline or complex nested XML

The reader may produce items that do not match the business unit. Choose fragments along independent boundaries.

### Broadly skipping parser errors

When a document is malformed, the parser cannot safely continue. Separate document-wide syntax errors from single-fragment data errors.

### Splitting XML by bytes for parallel execution

May split mid-tag, mid-entity, or mid-multibyte character. Split into valid XML shards at fragment boundaries.

### Sharing parser state across workers

XMLStreamReader is a stateful cursor. Create a separate reader/parser per worker.

### Publishing output before Job completion

Consumers may read a document missing its closing tag. Write to staging and publish upon success.

### Changing input between restarts

The checkpoint no longer points to the same fragment. Keep resources immutable and verify checksums.

## 33. Workflow for designing streaming XML

When handling large XML in Spring Batch, determine:

1. File size and expected fragment count.
2. Which fragment root represents an independent business item.
3. Maximum size of a single fragment.
4. Whether the XML has namespaces, attributes, nested collections, or multiline text.
5. Whether charset and XML declaration match source bytes.
6. Whether JAXB binding or a custom StAX reader is needed.
7. Whether XMLInputFactory disables DTDs/external entities for untrusted inputs.
8. Whether XSD validation runs via streaming or builds a DOM.
9. Whether chunk size fits object size and writer behavior.
10. Whether the reader has saveState and a stable name.
11. Whether the resource is immutable across restarts.
12. Whether partitioning uses valid XML shards rather than byte cuts.
13. Whether output stays in staging until Job completion.
14. Whether tests cover namespaces, encoding, malformed XML, restarts, and large files.

With large XML, StAX streaming allows Spring Batch to read fragment by fragment and pass each item into the chunk pipeline without holding the full document in memory. StaxEventItemReader paired with an Unmarshaller such as Jaxb2Marshaller is an appropriate choice when each fragment is an independent business unit. Pick small fragment roots, harden the parser, keep inputs stable across restarts, and publish output only after Job completion so large XML processing remains controllable in memory, performance, and recoverability.
