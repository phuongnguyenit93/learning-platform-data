# Where should JobExecution metadata be stored?

In Spring Batch, the information that describes a job run is managed by the `JobRepository`. In a real runtime environment, this metadata should be stored in a durable relational database, usually through Spring Batch's standard metadata tables with the `BATCH_` prefix. The `JobRepository` reads and updates those tables throughout the lifecycle of the job, steps, and the restart process.

The metadata tells Spring Batch which job has been launched, which execution is running or has ended, which steps have completed, which parameters were used, and which checkpoint state needs to be restored. Thanks to durable metadata storage, the application can look up history and continue a failed job even when the application process has stopped or been redeployed.

## JobRepository is where metadata is managed

`JobRepository` is the central infrastructure component of Spring Batch, responsible for storing and retrieving metadata. When the `JobLauncher` launches a job, it coordinates with the repository to find or create the `JobInstance`, create the `JobExecution`, and save the state changes during processing.

The main objects managed by the repository include:

| Object | Information stored |
| --- | --- |
| `JobInstance` | The identity of a logical job, determined by the job name and the identifying `JobParameters` |
| `JobExecution` | One specific execution: start/end time, status, exit code, error message, and the link to the instance |
| `StepExecution` | One execution of a step: status, the number of items read/written/skipped, commits, rollbacks, and run time |
| `JobParameters` | The input parameters of the execution, including the values and the identifying information |
| `ExecutionContext` | The state values that need to be saved to continue processing, at the job or step scope |

`JobRepository` is an abstraction, so architecturally it does not have to be a specific type of database. However, a repository based on JDBC and a relational database is a common choice for production applications because the data can survive multiple startups and be shared among multiple application instances.

## Which tables is the metadata stored in?

When using the JDBC `JobRepository`, Spring Batch uses a group of metadata tables. The standard table names usually begin with `BATCH_`:

| Table | Role |
| --- | --- |
| `BATCH_JOB_INSTANCE` | Stores the identity of each `JobInstance`, including the job name and the identifying parameters key |
| `BATCH_JOB_EXECUTION` | Stores each run of an instance, the status, times, exit code, and result information |
| `BATCH_JOB_EXECUTION_PARAMS` | Stores the `JobParameters` attached to the execution |
| `BATCH_STEP_EXECUTION` | Stores the status and figures of each step execution |
| `BATCH_JOB_EXECUTION_CONTEXT` | Stores the `ExecutionContext` at the job scope |
| `BATCH_STEP_EXECUTION_CONTEXT` | Stores the `ExecutionContext` at the step scope |

Depending on the database management system and the Spring Batch version, the schema set also has sequence tables or a corresponding ID generation mechanism. The names of some columns and the way parameters are represented have also changed between versions, so you need to use the schema that ships with the correct framework version.

The metadata relationships can be pictured as follows:

```text
BATCH_JOB_INSTANCE
        |
        | one instance can have multiple executions
        v
BATCH_JOB_EXECUTION
        |
        +---- BATCH_JOB_EXECUTION_PARAMS
        |
        +---- BATCH_JOB_EXECUTION_CONTEXT
        |
        +---- BATCH_STEP_EXECUTION
                      |
                      +---- BATCH_STEP_EXECUTION_CONTEXT
```

For example, `dailySettlementJob` processes settlement by day. If the run for 15/11 fails and is then restarted, `BATCH_JOB_INSTANCE` still represents the same logical work. `BATCH_JOB_EXECUTION` can have two records: the first execution has the `FAILED` status, and the later execution has the `COMPLETED` status. The step metadata and execution context help Spring Batch understand how far the previous run got.

## Distinguishing metadata from business data

Spring Batch metadata and the data the job is processing are two different kinds of data.

**Metadata** describes the run process: which job, which instance, which execution, which step, the current status, the number of items processed, and the checkpoint for restart. This is data managed by Spring Batch in the `BATCH_*` tables.

**Business data** is the input content and results processed by the application, for example transaction lines, orders, invoices, customer records, or settlement results. This data is stored in business tables, data stores, or target systems designed by the application.

For example, a job that imports an order file:

| Data type | Example | Suitable storage location |
| --- | --- | --- |
| Metadata | Which file is being imported, whether the job is `STARTED` or `COMPLETED`, how many lines have been read | The `BATCH_*` tables via the `JobRepository` |
| Restart state | The next read position, the page number, or the last processed record key | `ExecutionContext`, stored by the repository in the context tables |
| Business data | Orders, order details, payment status | Business tables or target systems |
| Source file | The input CSV or JSON content | A file store, object storage, or an appropriate file storage system |

You should not use `BATCH_JOB_EXECUTION_CONTEXT` as a large business data store. `ExecutionContext` is suited to storing small state values needed for restart, such as an offset, a page number, a file name, or the last processed key. File contents, lists of millions of objects, or complete business data should live in a dedicated store.

## Choosing where to store metadata

### A relational database using the JDBC JobRepository

This is the common choice for production. The application configures a `DataSource` for the repository; Spring Batch uses it to read and write the metadata tables. You can use the same database management system as the business data or a separate database/schema dedicated to batch metadata.

Common choices include PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, and the database management systems supported by Spring Batch. What matters is that the schema is compatible with the database and the Spring Batch version, the connection is durable, and all processes need to share the same repository if they jointly operate a batch flow.

A separate database or schema for metadata can help manage access permissions, backup, retention, and query load independently. Separating it this way does not change the `JobRepository` concept; you only need to configure the repository to point to the correct `DataSource`.

### In-memory repository

A non-durable repository or one that stores state only in memory can be useful for small examples, simple experiments, or cases that do not require history or restart across startups. But the metadata is lost when the process ends, and separate application instances have no shared source of state.

Therefore, this type of storage is not suitable for production batch that needs restart, historical auditing, or running on multiple nodes. How a non-durable repository is implemented also depends on the Spring Batch version; use the mechanism supported by the project's version for testing or for runs that don't need long-term metadata.

### Do not use logs as the primary metadata store

Application logs are useful for diagnostics but do not replace the `JobRepository`. Logs can be rotated, moved to another system, or lack consistent relationships among instance, execution, and step. Spring Batch needs the repository to control state and decide whether a restart is possible.

## Configuring metadata storage with Spring Boot

In a Spring Boot application with a configured `DataSource`, Spring Batch can usually auto-configure the JDBC repository infrastructure and use the declared database. This spares the application from writing code to insert or update the `BATCH_*` tables.

An example of datasource configuration and the schema initialization option in `application.yml`:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/batch_app
    username: batch_user
    password: change-me
    driver-class-name: org.postgresql.Driver

  batch:
    jdbc:
      initialize-schema: always
```

This is an illustrative example. Real connection information should come from environment variables or a secret manager instead of writing real passwords in a configuration file committed to a repository.

The `spring.batch.jdbc.initialize-schema` property controls Spring Boot's initialization of the metadata schema in the Boot versions that support this property. Common values:

| Value | Meaning |
| --- | --- |
| `always` | Always run the schema initialization script when the application starts |
| `embedded` | Only auto-initialize for an embedded database |
| `never` | Do not automatically run the schema initialization script |

In a development or test environment, `always` can be convenient if the database is frequently created anew. For production, you should usually manage the schema through a controlled migration process, deploy the appropriate script before running the application, and then configure it not to re-initialize the schema automatically. Do not use a create script to overwrite or delete existing metadata.

Spring Boot and Spring Batch differ between versions. Check the documentation for the project's exact version to confirm property names, defaults, and auto-configuration behavior. If the application declares its own batch configuration such as `@EnableBatchProcessing` or its own repository configuration, part of Spring Boot's auto-configuration may no longer apply; in that case the development team is responsible for configuring the `DataSource`, the transaction manager, and the schema.

## Configuring the JobRepository in an application that manages its own infrastructure

If you don't use auto-configuration, the JDBC repository needs to be connected to the appropriate infrastructure components:

- `DataSource`: the connection to the database containing the metadata tables.
- `PlatformTransactionManager`: manages transactions when reading and writing the metadata.
- The Spring Batch schema: the required tables and sequences have been created in the correct version.
- Repository configuration: the table prefix, the isolation level when creating executions, and related options if the application needs to change the defaults.

At the architectural level, the configuration flow is as follows:

```text
DataSource ----------------------+
                                 |
PlatformTransactionManager ------+----> JDBC JobRepository
                                 |             |
Spring Batch metadata schema ----+             v
                                         BATCH_* tables
```

In Java configuration, you can use the Spring Batch configuration mechanism supported by the project's version to register the `JobRepository` and point it at the `DataSource` and the transaction manager. You should not create your own repository implementation or write SQL directly into the metadata tables without a special requirement, because the framework needs to manage relationships, state, and concurrency rules consistently.

If the application has multiple `DataSource`s, you need to clearly determine which database is for the batch metadata. You should not assume Spring Batch automatically picks the right datasource based on the bean name alone. Configure the datasource and transaction manager dedicated to the repository explicitly according to the API of the version in use.

## Transactions and consistency between metadata and business data

Spring Batch updates the metadata at important points in the job and step lifecycle. With a chunk-oriented step, the step state and execution context are usually updated in association with the chunk commit boundaries so that the point to continue from after an error can be determined.

This makes transaction configuration important. If the metadata and the business data use the same database resource and an appropriate transaction manager, the application can coordinate the updates in the same transaction according to the step configuration. When the transaction commits, the business data and the related checkpoint can be stored consistently.

If the metadata lives in a different database or uses a different transaction manager from where the business data is written, the two sides do not implicitly commit or roll back atomically together. A situation can occur where the business data has committed but the metadata has not recorded the checkpoint, or vice versa. When designing for this case, account for idempotency, business keys, reconciliation mechanisms, recording intermediate state, or an appropriate transaction coordination solution.

For example, the writer has written a chunk of orders into the business database but the application stops before the metadata records the checkpoint. On restart, that chunk may be processed again. The writer should have a safeguard so that writing the same orders again does not create duplicate data, such as a unique business key or an upsert operation designed correctly for the business.

Therefore, choosing the database for the `JobRepository` is not only a storage decision. You need to consider the location of the business data, the step's transaction manager, the commit interval, how the writer handles repeats, and the restart strategy.

## Why must all nodes share the JobRepository?

In a system deployed with multiple application instances, the nodes may receive job launch requests or execute different parts of the work. If each node writes metadata to its own repository, they may each think a `JobInstance` does not exist yet or not know that an execution is running on another node.

With a JDBC repository, the nodes that participate in the same batch system should share the metadata database/schema and the same conventions for job identity and parameters. The repository can work with transactions and locking/concurrency control mechanisms to prevent conflicting launches of the same instance.

```text
Application node A ----+
                       |
Application node B ----+----> Shared JobRepository database
                       |             |
Application node C ----+             +-- BATCH_JOB_INSTANCE
                                     +-- BATCH_JOB_EXECUTION
                                     +-- BATCH_STEP_EXECUTION
                                     +-- BATCH_*_CONTEXT
```

The nodes need to be compatible in Spring Batch version and schema. Do not let each node initialize or upgrade the schema in a way that can produce an inconsistent state. Running in parallel still requires appropriately designed identifying parameters, concurrency, and thread-safety of the reader/writer.

## Where is the ExecutionContext stored and what should it hold?

`ExecutionContext` is a key-value state area that Spring Batch manages for a job or step. With the JDBC repository, the job execution context is stored in `BATCH_JOB_EXECUTION_CONTEXT`, while the step execution context is stored in `BATCH_STEP_EXECUTION_CONTEXT`.

For example, a reader that processes a file line by line can store the file name and the next read position in the context. When the job is stopped midway, the restart can restore the state to continue from the appropriate checkpoint.

```java
public class ImportStepListener implements StepExecutionListener {

    @Override
    public ExitStatus afterStep(StepExecution stepExecution) {
        ExecutionContext context = stepExecution.getExecutionContext();
        context.putString("sourceFile", "orders-2026-11-15.csv");
        context.putLong("lastProcessedId", 8450L);
        return stepExecution.getExitStatus();
    }
}
```

The snippet only illustrates how to write values into the context; the actual place where the checkpoint is updated must fit the reader/step lifecycle and the commit timing. For a reader/writer with built-in state management, you should prefer the state-saving mechanism that component provides instead of writing a value yourself that could drift from the committed data.

When putting data into the context, note that:

- Only store small, necessary information to restore progress, such as an offset, page number, resource name, or the last processed key.
- Use data types and values that the application's serializer can support; avoid storing arbitrary objects or objects that depend on the lifecycle of a process.
- Do not store passwords, access tokens, secret information, or unnecessary personal data in the context.
- Do not store entire input data or large lists; store a reference to where the data lives instead.
- Keep key names and the meaning of values stable across restarts and compatible application versions.

The execution context can be serialized into the database. When changing the serializer or the structure of the stored objects, you need to assess whether old contexts can still be read after upgrading the application. An incompatible change can make an old job unable to restart even though the metadata tables are still there.

## Checking that metadata has been stored

After the application runs, you can inspect the metadata tables with a SQL tool. The query below lists the executions together with their corresponding job instances:

```sql
SELECT
    ji.JOB_INSTANCE_ID,
    ji.JOB_NAME,
    je.JOB_EXECUTION_ID,
    je.STATUS,
    je.START_TIME,
    je.END_TIME
FROM BATCH_JOB_INSTANCE ji
JOIN BATCH_JOB_EXECUTION je
    ON je.JOB_INSTANCE_ID = ji.JOB_INSTANCE_ID
ORDER BY je.JOB_EXECUTION_ID DESC;
```

The column names used in the query are common columns of the JDBC metadata schema. If the project uses a custom table prefix or a schema adjusted for a version, change the table/column names accordingly. Only use queries for observation; do not update the execution status or context directly with manual SQL.

At the application layer, `JobExplorer` provides an API for reading the stored metadata, for example looking up job instances, executions, and step executions. `JobOperator` can support operational actions such as launching, stopping, or restarting according to the application's configuration and permissions. Using these APIs helps avoid depending directly on the table structure when building a batch administration screen.

## Initializing, upgrading, and maintaining the schema

Spring Batch provides schema scripts for the supported database management systems. When creating a new database, you need to run the appropriate script to create all the required tables, primary keys, foreign keys, and sequences. You should not just create a few tables with standard-looking names yourself, because the repository also depends on the structure and constraints of the whole schema.

When upgrading Spring Batch, check the migration guide from the current version to the target version. The schema, the parameter data types, how the context is stored, and the metadata columns may change. Perform a controlled migration, back up before changing the schema, and test reading old metadata in a staging environment.

Metadata has operational and audit value. If you delete `BATCH_*` records too early, the application may lose the ability to restart unfinished jobs and lose the history for investigation. A retention policy should clearly define how long completed jobs are kept, how to handle running or failed executions, the foreign key relationships, and the audit needs. Only clean up with a process designed for the schema and version in use.

Operational points to care about:

- Back up and restore the metadata database together with the backup process of the related business data.
- Grant minimal permissions to the application account for reading/writing the metadata tables; the migration account can have separate DDL permissions.
- Monitor size, write throughput, the connection pool, locks, and query time as the number of executions grows.
- Ensure the metadata database is ready before launching workers or the scheduler.
- Keep the framework version and schema in sync across deployment nodes.
- Do not edit state or delete context with manual SQL while jobs are running.

## Common configuration mistakes

### The job runs but the metadata disappears after the application restarts

The cause is usually that the repository is using non-durable storage, or the application connects to a temporary database that is recreated after each run. Confirm the type of `JobRepository`, the datasource URL, and the database lifecycle. Production needs a repository pointing to a long-lived database.

### The table BATCH_JOB_INSTANCE is not found

The database has not had the schema initialized, the script did not run, the application is connected to the wrong database/schema, or the table prefix does not match. Check the actual datasource, the user's permissions, and the schema script for the correct database system and Spring Batch version.

### Multiple nodes create inconsistent run history

The nodes may be using different datasources, separate databases, or inconsistent identifying parameter configuration. Confirm that all nodes share the repository, the same job names, and the same parameter rules; also check the transaction and concurrency configuration.

### Restart fails after upgrading the application

It may be that the schema has not been migrated, the old context is no longer compatible with the new serializer, or the step logic no longer understands the old checkpoint. Check the logs, the execution metadata, the context structure, and the upgrade guide for the Spring Batch version; test the migration and restart on a copy of the data before applying to production.

### Metadata and business data do not match

If the metadata and business data use different transaction managers or databases, they may not commit together. Check the step's transaction boundaries, where the business data is stored, the commit interval, and the writer's ability to handle repeats. Design idempotency and reconciliation to recover safely after errors.

## How to decide where to store metadata for an application

When designing a Spring Batch application, you can follow this sequence:

1. Determine whether the job needs to restart after the process stops. If so, use a durable repository.
2. Choose a relational database supported by the system and determine the database/schema for the metadata.
3. Configure the `DataSource` and transaction manager for the `JobRepository`.
4. Create or migrate the full Spring Batch schema in the correct version.
5. Determine which repository the batch-running nodes will all access.
6. Design where the business data is stored and how to coordinate transactions with the metadata.
7. Determine the checkpoint data to store in the `ExecutionContext`, avoiding putting large data or secrets into the context.
8. Set up backup, access control, monitoring, and a retention policy for the metadata.

In a typical production system, the usual choice is a JDBC `JobRepository` stored in a durable relational database, shared by the batch processing nodes. Spring Batch itself manages the `BATCH_*` tables to store the `JobInstance`, `JobExecution`, `StepExecution`, parameters, and execution context; the application continues to store business data in a data store suited to its own domain.

## Key takeaways

`JobExecution` metadata is managed by the `JobRepository`. For a production application, configure a JDBC repository pointing to a durable relational database that has a compatible Spring Batch schema. The metadata usually resides in the tables `BATCH_JOB_INSTANCE`, `BATCH_JOB_EXECUTION`, `BATCH_JOB_EXECUTION_PARAMS`, `BATCH_STEP_EXECUTION`, and the execution context tables. This data serves tracking, state control, and restart; it is separate from the business data the job is processing. When deploying multiple nodes, the nodes need to share the repository and have appropriate transaction, schema, backup, and retention configuration.
