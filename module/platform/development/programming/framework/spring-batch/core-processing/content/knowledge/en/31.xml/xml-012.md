# Mid-stream XML errors

In Spring Batch, XML inputs are typically read fragment by fragment using `StaxEventItemReader`. If a file is corrupted mid-stream, the parser may read and process several fragments before hitting an XML syntax error. Already committed chunks can remain persisted, whereas the remainder of the document usually cannot be read safely because an XML parser requires valid document structure to determine element boundaries.

The key distinction is between **non-well-formed XML** and **a structurally valid XML record with invalid business data**. Structural errors like missing closing tags, mismatched nesting, or broken markup are severe parser errors; a skip policy cannot reliably relocate boundaries to continue. Conversely, a complete XML element containing invalid business values can be checked in the Processor and handled via skip/reject if business rules permit.

## 1. How can mid-stream XML errors occur?

An XML file can fail before the Job starts, while the Reader is reading, or at the end of the file when the parser discovers an incomplete document.

Example valid XML file:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order>
        <id>ORD-1001</id>
        <amount>125.50</amount>
    </order>
    <order>
        <id>ORD-1002</id>
        <amount>89.90</amount>
    </order>
</orders>
```

Common error examples:

```xml
<!-- Missing order closing tag -->
<orders>
    <order><id>ORD-1001</id></order>
    <order><id>ORD-1002</id>
</orders>
```

```xml
<!-- Improperly nested tags -->
<orders>
    <order>
        <id>ORD-1001</order>
    </id>
</orders>
```

```xml
<!-- File truncated mid-content -->
<orders>
    <order><id>ORD-1001</id></order>
    <order><id>ORD-1002</id><amount>89.
```

The parser may have already returned the initial `order` elements before hitting an error on a later element. When a file is truncated at the end, earlier records may be valid while the root element or final record remains unclosed.

## 2. StaxEventItemReader reads XML by fragment

`StaxEventItemReader<T>` uses StAX (Streaming API for XML) to read XML as an event stream without loading the entire document into memory. Normally, the application specifies the root element name of each record using `addFragmentRootElements(...)` and supplies an `Unmarshaller` to convert fragments into objects.

Structure example:

```text
orders.xml
  |
  +--> <orders>                 document root element
         |
         +--> <order> ... </order>  fragment 1 -> Order
         +--> <order> ... </order>  fragment 2 -> Order
         +--> <order> ... </order>  fragment 3 -> Order
```

The Reader returns only individual `order` fragments to the chunk pipeline. The `<orders>` root element is the outer wrapper; each `<order>` is one item. Fragment-based reading enables processing large files item by item and chunk by chunk.

## 3. Configuring StaxEventItemReader

Example configuration with Spring Batch 5 and JAXB:

```java
import org.springframework.batch.core.configuration.annotation.StepScope;
import org.springframework.batch.item.xml.StaxEventItemReader;
import org.springframework.batch.item.xml.builder.StaxEventItemReaderBuilder;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.core.io.FileSystemResource;
import org.springframework.oxm.jaxb.Jaxb2Marshaller;

@Bean
public Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    return marshaller;
}

@Bean
@StepScope
public StaxEventItemReader<OrderXml> orderXmlReader(
        @Value("#{jobParameters['inputFile']}") String inputFile,
        Jaxb2Marshaller orderMarshaller) {

    return new StaxEventItemReaderBuilder<OrderXml>()
            .name("orderXmlReader")
            .resource(new FileSystemResource(inputFile))
            .addFragmentRootElements("order")
            .unmarshaller(orderMarshaller)
            .saveState(true)
            .build();
}
```

`OrderXml` is the JAXB class matching one `<order>` element. `@StepScope` allows the Reader to receive the file from the current StepExecution's JobParameters. `saveState(true)` enables saving reading progress so Spring Batch can restore position on restart.

Minimal JAXB class example:

```java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    @XmlElement(name = "id")
    private String id;

    @XmlElement(name = "amount")
    private String amount;

    public String getId() { return id; }
    public String getAmount() { return amount; }
}
```

Keeping input values as `String` inside the XML class can help distinguish XML parse errors from business conversion errors. The Processor can parse `amount` into `BigDecimal` and throw a clearly typed exception if the value is invalid.

## 4. Distinguishing XML syntax errors from single-record data errors

Not every error encountered when reading XML has the same recoverability.

| Error type | Example | Appropriate handling |
|---|---|---|
| Non-well-formed XML | Missing closing tag, mismatched nesting, broken markup | Stop processing file, quarantine, and fix/re-obtain the file. |
| Truncated XML | File ends mid-element | Treat file as incomplete; re-obtain or regenerate the file. |
| XSD mismatch | Missing required element, invalid schema structure | Validate and reject file, or apply record-level rules if architecture allows. |
| Unmarshal error in complete fragment | Field type or structure cannot map | Can classify separately; skip only when fragment was safely extracted and parser can continue. |
| Business error after mapping | Negative amount, unsupported status code | Validate in Processor; skip/reject if business rules permit. |
| Database write error | Deadlock, timeout, constraint violation | Retry or fail per exception and transaction policy. |

Well-formedness errors are structural errors in the XML stream. After a fatal parser error, standard parsers usually cannot reliably locate the start of the next record. Therefore, do not treat that error as an isolated item that can be skipped with `.skip(...)` to read the rest.

## 5. Why cannot a skip policy automatically recover broken XML?

A skip policy in Spring Batch decides whether to skip an exception during reading, processing, or writing. However, the policy does not repair parser state and does not know how to resynchronize a corrupted XML document.

Example:

```text
<orders>
  <order>...</order>     fragment 1: readable
  <order>...</order>     fragment 2: readable
  <order>                 start of fragment 3
    <id>ORD-3</id>
  <wrong-close>           broken markup
  <order>...</order>     parser cannot trust next boundary
</orders>
```

Even if `.skip(XMLStreamException.class)` is configured, it does not guarantee the StAX reader can proceed from the next record. The parser may already be in an error state and unable to emit valid events. Actual behavior also depends on how the Reader wraps exceptions and stream state; do not rely on skipping parser exceptions to recover document structure.

If skipping a bad record and continuing subsequent records is required, the input format must have independent, safely re-identifiable record boundaries. Standard XML documents do not provide such resynchronization after a fatal well-formedness error.

## 6. What happens when an error occurs after several chunks have committed?

Suppose a Job reads 1,000 orders per chunk. The first two chunks commit, but the parser hits broken markup while reading the third chunk:

```text
JobExecution #1
  Chunk 1: 1,000 items -> COMMIT
  Chunk 2: 1,000 items -> COMMIT
  Chunk 3: parser error -> ROLLBACK / Step FAILED
  Items after error: not yet read
```

Business changes in committed chunks usually remain persisted. The failing chunk does not commit; checkpoint metadata normally reflects only the previous commit boundary.

If you restart the same JobInstance with the same corrupted file, the Reader restores the saved checkpoint and rereads the uncommitted portion. Upon reaching the broken XML position, the parser fails identically. Restarting cannot heal the source file.

```text
Restart same JobInstance
  |
  v
Restore checkpoint after Chunk 2
  |
  v
Reread start of Chunk 3
  |
  v
Hit same broken markup
  |
  v
Step remains FAILED
```

If the error is at the end of the file, the Reader may have returned the final valid fragments while the parser detects the missing closing tag only upon reaching EOF. Committed chunks remain persisted, yet the subsequent read on restart may keep failing at EOF.

## 7. Pre-job XML validation workflow

For XML files exchanged between systems, a reliable operational practice is verifying the file is completely written and structurally valid before launching the business processing Job.

A common workflow:

```text
Producer writes orders.xml.part
          |
          v
Producer closes file completely
          |
          v
Rename to orders.xml
          |
          v
Validate well-formedness / XSD
          |
      +---+---+
      |       |
      v       v
   Valid    Invalid
      |       |
      v       v
Launch Job  Quarantine + report error
```

The producer should write under a temporary name, then close the file and rename it to the final name. The Job picks up only files with the final name. This reduces the risk of the Reader opening a file while the producer is still writing.

If the filesystem supports it, `Files.move(..., StandardCopyOption.ATOMIC_MOVE)` can publish the finished file via an atomic rename within the same filesystem. Not every filesystem or network mount supports atomic move; verify your deployment environment.

## 8. Checking XML well-formedness before processing

You can use the Java XML Validation API to parse the entire document before launching the Job. Validating with `StreamSource` streams through the parser without requiring the full XML tree to be loaded into memory like DOM.

```java
import java.nio.file.Path;

import javax.xml.XMLConstants;
import javax.xml.transform.stream.StreamSource;
import javax.xml.validation.SchemaFactory;

public class XmlPreValidator {

    public void validateWellFormed(Path xmlFile) throws Exception {
        SchemaFactory factory = SchemaFactory.newInstance(
                XMLConstants.W3C_XML_SCHEMA_NS_URI);
        factory.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
        factory.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");

        // Parse XML to check structure; no schema needed when checking well-formedness only.
        var schema = factory.newSchema();
        var validator = schema.newValidator();
        validator.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
        validator.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
        validator.validate(new StreamSource(xmlFile.toFile()));
    }
}
```

The example above illustrates parsing and checking the document with a Validator not bound to a specific XSD. If schema validation is needed, build a `Schema` from the XSD file and use that Validator:

```java
var schema = factory.newSchema(xsdFile.toFile());
var validator = schema.newValidator();
validator.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
validator.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
validator.validate(new StreamSource(xmlFile.toFile()));
```

The `ACCESS_EXTERNAL_DTD` and `ACCESS_EXTERNAL_SCHEMA` properties restrict external resource access while the parser processes XML/XSD. For untrusted XML, configure the parser securely and disallow arbitrary DTD/schema downloads from the network.

Pre-validation means the file is read an extra time: once to confirm structure, and once by the batch Reader to process records. In exchange, the Job can reject broken files before writing business data. For huge files, validation still streams, though it adds extra I/O.

## 9. Validating with XSD to detect schema violations

Well-formed XML is not guaranteed to match the business schema. For instance, `<order>` may be syntactically valid yet miss `id`, have elements out of order, or contain structures disallowed by the XSD.

Simple XSD example:

```xml
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="orders">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="order" minOccurs="0" maxOccurs="unbounded">
          <xs:complexType>
            <xs:sequence>
              <xs:element name="id" type="xs:string"/>
              <xs:element name="amount" type="xs:decimal"/>
            </xs:sequence>
          </xs:complexType>
        </xs:element>
      </xs:sequence>
    </xs:complexType>
  </xs:element>
</xs:schema>
```

If a file must conform to the full schema before importing, run full-file XSD validation before starting the Job. On XSD failure, log the error location and quarantine the file.

If business rules require accepting valid records while rejecting only invalid records, avoid default full-file validation in a way that causes one bad record to reject the whole file. You can read fragments, map into a flexible DTO, and validate each record in the Processor. Define rules clearly for fragments with missing fields or wrong types so unmarshalling does not halt the parser before the Processor receives the item.

## 10. Handling record-level business errors

An XML fragment can be completely well-formed while holding invalid values:

```xml
<order>
    <id>ORD-1003</id>
    <amount>-25.00</amount>
</order>
```

This record is structurally valid XML; business rules may disallow negative amounts. To classify errors at the item level, parse values into target types inside the Processor and throw a business exception:

```java
import java.math.BigDecimal;

import org.springframework.batch.item.ItemProcessor;

public class OrderProcessor
        implements ItemProcessor<OrderXml, ProcessedOrder> {

    @Override
    public ProcessedOrder process(OrderXml item) {
        BigDecimal amount;
        try {
            amount = new BigDecimal(item.getAmount());
        } catch (NumberFormatException ex) {
            throw new InvalidOrderException("Invalid amount", ex);
        }

        if (amount.signum() < 0) {
            throw new InvalidOrderException("Amount cannot be negative");
        }

        return new ProcessedOrder(item.getId(), amount);
    }
}
```

Then configure skip for the business exception if policy permits:

```java
return new StepBuilder("importOrdersStep", jobRepository)
        .<OrderXml, ProcessedOrder>chunk(500, transactionManager)
        .reader(orderXmlReader)
        .processor(orderProcessor)
        .writer(orderWriter)
        .faultTolerant()
        .skip(InvalidOrderException.class)
        .skipLimit(100)
        .listener(orderSkipListener)
        .build();
```

Here the parser has already constructed a complete `OrderXml`; the error is caught in the Processor and can be skipped per policy. Record rejected items by business key to avoid duplicates if a chunk rolls back and items are reprocessed on restart.

## 11. When continuing past a broken XML record is mandatory

A standard XML document has no general recovery boundary after broken markup. If business requirements strictly demand continuing to process subsequent records, change how data is packaged or define an explicit framing protocol.

Options:

1. **One XML document per record:** each file can be parsed and isolated independently. One corrupted file does not block reading the next file.
2. **An archive containing multiple independent XML files:** e.g., each ZIP entry is a standalone XML document, with a manifest and per-entry processing status.
3. **Producer emits independent records per message:** each message carries one complete XML document and its own ID.
4. **Framed record format:** each record has an explicit outer length or delimiter outside XML, letting the reader relocate boundaries without guessing XML structure.
5. **Custom recovery parser:** use only if the format specifies formal resynchronization rules, is thoroughly tested, and can be proven never to splice wrong records.

Never use regex to search for the next `<order>` string after a parser error. That string can appear inside CDATA, comments, attributes, or text content; the parser cannot reliably verify it is a genuine element. String-search recovery can fabricate corrupted records or silently drop data.

## 12. Handling broken files in the batch workflow

A clear operational workflow should classify files before importing:

| File status | Action |
|---|---|
| Incomplete, still named `.part` | Do not launch Job yet. |
| Closed but non-well-formed XML | Quarantine file, log parser error, and request producer resend. |
| Well-formed but fails XSD | Quarantine or apply appropriate schema-version handling workflow. |
| Well-formed and schema-valid, with invalid business records | Import valid records; log rejects for invalid records per skip policy. |
| Valid file and all records succeed | Publish results and mark batch completed. |

Error details can be stored in a `batch_file_audit` table:

```text
batch_file_audit
--------------------------------------------------------------
file_id | checksum | status     | error_line | error_message
--------------------------------------------------------------
F-1001  | ...      | REJECTED   | 2451       | XML not well-formed
F-1002  | ...      | PROCESSING | null       | null
F-1003  | ...      | COMPLETED  | null       | null
```

Auditing prevents duplicate launches of the same file, traces root causes, and distinguishes structurally broken files from rejected records. Store checksums or versions to detect whether a file was modified between runs.

## 13. Restarting when the XML file was modified

Suppose a JobInstance was created with `inputFile=orders.xml` and committed several chunks before a parser failure. Afterward, the producer modifies the file at the exact same path.

Restarting the same JobInstance uses the old checkpoint. If file contents changed, the old item position may no longer correspond to the same records. This can skip records or process duplicates.

Safety rules:

- Never edit an input file once a JobInstance has started processing it.
- Keep files immutable throughout the restart lifecycle.
- Store checksum, size, receipt timestamp, or object version as batch metadata.
- If a file needs fixes or the producer resends a new version, create a new versioned file and a new JobInstance with identifying parameters reflecting the version/checksum.
- Only reset/reprocess the same JobInstance when an explicit operational procedure accounts for checkpoints and already-committed data.

JobParameters example:

```java
JobParameters parameters = new JobParametersBuilder()
        .addString("fileId", "orders-2026-11-15-v2", true)
        .addString("inputFile", "/data/in/orders-v2.xml", true)
        .addString("checksum", checksum, true)
        .toJobParameters();
```

If revised content represents a new business batch, new identifying parameters create a separate JobInstance. The Writer still needs idempotency/business keys to protect data if identical records appear in both file versions.

## 14. Distinguishing XML errors from transaction and Writer errors

Not every Job failure while reading XML comes from the parser:

- The parser can throw errors on non-well-formed documents.
- The Unmarshaller can fail to map fragments.
- The Processor can throw exceptions due to business data.
- The Writer can fail due to database, disk, or constraints.
- JobRepository can fail to persist checkpoints due to lost metadata database connectivity.

When investigating, inspect the exception cause chain, line/column numbers if available, StepExecution, read/process/write counts, and checkpoints. Never rely solely on a generic `Job failed` message.

If the parser reports an error at line 2451, match the original file by checksum and inspect content around that position. If the error occurred in the Writer, the XML may be completely valid; inspect database and transactions. If a metadata error happened after target data committed, restart must rely on an idempotent Writer to avoid duplicates.

## 15. Testing mid-stream XML errors

Test files corrupted at multiple positions and verify committed data, Job status, and restart behavior.

Useful scenarios:

1. **Valid XML:** all fragments are read and written properly.
2. **Broken markup mid-file:** initial chunks commit, parser hits error, Step/Job fails.
3. **Missing root closing tag:** fragments may have been read before failure occurs at EOF.
4. **File truncated mid-fragment:** final record is incomplete and parser cannot return a complete item.
5. **Invalid schema:** pre-validation rejects the file before writing data if policy is all-or-nothing.
6. **Invalid business data in valid fragment:** Processor throws exception and skips/rejects per policy.
7. **Restarting with still-broken file:** same JobInstance fails again at the same uncommitted region.
8. **Fixing file and creating a new versioned instance:** Job processes the new version with fresh checkpoints, without applying old checkpoints to changed content.
9. **Duplicates on restart:** Writer does not create duplicate business records for committed chunks or retried items.

Integration test assertions should verify:

```java
assertEquals(BatchStatus.FAILED, jobExecution.getStatus());
assertEquals(expectedCommittedCount, countRowsInTarget(batchId));
assertTrue(jobExecution.getAllFailureExceptions().stream()
        .anyMatch(this::hasXmlParsingCause));
```

These are illustrative assertions; `hasXmlParsingCause` is a test helper checking the cause chain for parser errors. Avoid relying on a single exception class if the Reader wraps XML errors in different exception classes across versions.

When testing restarts, use the same identifying JobParameters and file checksum to reproduce the exact JobInstance. Then modify the file into a new version and verify a new JobInstance is created when business rules call for reprocessing.

## 16. Common pitfalls

| Error | Consequence | Fix |
|---|---|---|
| Skipping all XML parser exceptions | Parser may have lost synchronization and cannot read later fragments. | Fail file, quarantine, and request producer resend or fix. |
| Assuming committed chunks roll back on XML error | Data from already-committed chunks remains persisted. | Track checkpoints and design idempotent Writers. |
| Restarting a still-broken file expecting it to pass | Reader hits the exact same broken uncommitted XML region. | Fix/re-obtain the file or use independent record framing. |
| Editing the file at the same path and restarting old checkpoint | Checkpoint position may point to different records. | Keep files immutable; new version/checksum creates a new JobInstance. |
| Using regex to find the next tag for recovery | May mistake text, comments, CDATA, or attributes for elements. | Use standard parsers and specified framing if recovery is needed. |
| Confusing business errors with well-formedness errors | Rejects whole file when one record is bad, or dangerously skips structural errors. | Separate parsing, schema validation, and business validation. |
| Producer writing file while Reader opens it | Job may read an incomplete file. | Use temporary `.part` names, close file, then publish via rename. |
| Treating footer or read record count as proof of valid file | Parser can discover an EOF error after many records. | Validate full file and publish only after Job completion. |

## Conclusion

When XML fails mid-stream, `StaxEventItemReader` may have already returned and Spring Batch may have committed several fragments before the parser hits the error. Committed chunks normally stay persisted; uncommitted chunks can be reread on restart. If a document is not well-formed, standard parsers cannot safely locate subsequent record boundaries on their own, so skip policies are not a reliable recovery mechanism for broken markup. Validate complete files and XSDs before processing when all-or-nothing is required, keep inputs immutable across restarts, quarantine corrupted files, and use Processors/skip policies for business errors inside valid fragments. If continuing past broken XML records is required, design inputs as independent XML documents or framed records with clear recovery boundaries.
