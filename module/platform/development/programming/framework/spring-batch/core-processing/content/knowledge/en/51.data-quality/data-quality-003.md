# Skipping and Reporting Rejected Items in Spring Batch

A Spring Batch Job often reads thousands to millions of records from CSV, a database, or a message source. In a large dataset, some records may have malformed formats, missing required fields, business rule violations, or cannot be written to the target system. If every error stops the entire Job, valid records are delayed. Conversely, ignoring errors without recording them causes silent data loss and makes reconciliation difficult.

In the **Data quality** group of **Spring Batch Core Processing**, **skipping and reporting rejected items** allows a Job to continue processing accepted records while leaving a clear audit trail of rejected ones. The solution must design **error acceptance rules**, **error limits**, **storage for rejected results**, and **verification mechanisms**.

This article explains fault-tolerant chunk processing, `SkipListener`, rejected item report structures, Java Spring Batch 5.x examples, testing approaches, and operational principles. With Spring Batch 6.x, some packages and builder APIs have been reorganized; when implementing, use the exact APIs matching your project's dependencies.

## 1. Distinguishing Skip, Filter, Retry, and Job Failure

Before writing code, define each type of processing outcome.

| Concept | What Happens | Counted as a Rejected Item? |
| --- | --- | --- |
| **Filter** | `ItemProcessor` returns `null`; the record is excluded from output by normal rules. | Not by default. This is a valid processing decision counted in `filterCount`. |
| **Skip** | Reader/processor/writer throws an exception configured as skippable within the allowed limit. | Yes. This is an error record that must be classified and reported per the data contract. |
| **Retry** | Spring Batch retries an operation that encountered a transient error. | Not necessarily. If retry succeeds, there is no rejected item; if the error persists, it may skip or fail per policy. |
| **Fail** | A non-skippable exception or total skips exceeding the threshold causes the Step/Job to fail per the flow. | There may be earlier rejected items, but the Job result is `FAILED`. |
| **Stop** | The Job stops in a controlled manner, e.g., an operational action. | Not synonymous with rejected data. |

Example of a Job reading 10 data rows (excluding the header):

```text
10 source rows
  |
  +-- 1 row with invalid amount format -----> READ SKIP
  |
  +-- 9 records read successfully
        |
        +-- 2 business-invalid records -----> PROCESS SKIP
        |
        +-- 7 valid records ----------------> WRITE SUCCESS
```

With a Step configured to skip the three errors above, an illustrative result could be:

```text
BatchStatus         = COMPLETED
readCount           = 9
readSkipCount       = 1
processSkipCount    = 2
writeSkipCount      = 0
skipCount           = 3
writeCount          = 7
```

The counts above depend on the fixture and the reader/processor/writer implementation used. **`COMPLETED` does not mean every input row was accepted**; it may mean the Job finished under a policy permitting a certain number of errors to be skipped.

## 2. What Is a Rejected Item?

A **rejected item** is an input unit not accepted at a processing stage, accompanied by a clear enough reason for analysis, data correction, or reprocessing.

A rejection report record typically needs to answer:

- Which **data source**, position, or key did the record come from?
- Was it rejected during **READ**, **PROCESS**, or **WRITE**?
- Which **business or technical error category** does the failure belong to?
- Which `JobInstance`, `JobExecution`, and `StepExecution` processed it?
- Can the record be fixed and reloaded, or does it need manual intervention?
- Can the same record be identified on rerun without misleadingly duplicating reports?

Example of a report entry:

```json
{
  "jobName": "importPaymentsJob",
  "jobInstanceId": 42,
  "jobExecutionId": 811,
  "stepExecutionId": 1311,
  "source": "payments-2026-11-16.csv",
  "sourceKey": "line:5",
  "phase": "READ",
  "errorCode": "INVALID_AMOUNT_FORMAT",
  "exceptionType": "FlatFileParseException",
  "reportedAt": "2026-11-16T02:30:00Z",
  "resolutionStatus": "NEW"
}
```

This is a **business model**, not a structure auto-generated by Spring Batch. Projects must design how to store, secure, query, and handle rejected items.

**Do not equate a rejected item with a raw exception message.** Exception messages can contain sensitive data, change across versions, or be unhelpful to operators. Use a standardized `errorCode` and controlled descriptive text.

## 3. Fault-Tolerant Chunk Processing Mechanism

A chunk-oriented Step generally executes in this model:

```text
ItemReader
    |
    v
ItemProcessor
    |
    v
ItemWriter
    |
    v
Commit transaction

If an error occurs:
    |
    +-- Retry? ---> retry according to policy
    |
    +-- Skippable + skipLimit not exceeded?
    |      |
    |      +-- Yes --> drop failed item, record skip, continue
    |      |
    |      +-- No ---> Step fails
    |
    +-- Non-skippable error -> Step fails
```

In Spring Batch 5.x, `faultTolerant()` enables skip and retry policies on `StepBuilder`. Example:

```java
@Bean
Step importPaymentsStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<Payment> paymentReader,
        ItemProcessor<Payment, Payment> paymentProcessor,
        ItemWriter<Payment> paymentWriter) {

    return new StepBuilder("importPaymentsStep", jobRepository)
            .<Payment, Payment>chunk(100, transactionManager)
            .reader(paymentReader)
            .processor(paymentProcessor)
            .writer(paymentWriter)
            .faultTolerant()
            .skip(FlatFileParseException.class)
            .skip(InvalidPaymentException.class)
            .skipLimit(100)
            .build();
}
```

Here:

1. `chunk(100, transactionManager)` defines the read/process/write unit per chunk using the configured transaction manager.
2. `faultTolerant()` enables fault-tolerance capabilities for the Step.
3. `skip(FlatFileParseException.class)` allows skipping line-parsing errors from `FlatFileItemReader`.
4. `skip(InvalidPaymentException.class)` allows skipping errors thrown by business validation logic.
5. `skipLimit(100)` allows at most **100 skips** in the Step; upon the **101st** skip, the Step fails instead of skipping indefinitely.

**The skip limit applies to the sum of read skips, process skips, and write skips for the Step**, not 100 per phase. The limit policy can be customized if the project uses a custom `SkipPolicy`.

### When Should Skip Be Used?

Skip errors belonging to **isolated invalid data that do not compromise processing the remaining items**, for example:

- A CSV line with a malformed amount.
- An order missing a required product code.
- An event with a business date outside the allowed domain.
- A transaction violating a business rule defined as rejectable.

Do not configure broad skipping for errors such as:

- Inability to connect to the database or storage system.
- Broken driver, transaction manager, or schema mismatch.
- Prolonged system-wide timeouts.
- Unexpected programming bugs such as `NullPointerException`.
- Data constraint errors that may indicate a writer, mapping, or transaction bug.

**Avoid `skip(Exception.class)` or `skip(Throwable.class)` as a default setting.** That can convert severe infrastructure failures into skip counts and cause a Job to report completion even when the system is not functioning properly.

## 4. Classifying READ, PROCESS, and WRITE Errors

### 4.1. READ Skip

Errors occurring while calling `ItemReader.read()`. With `FlatFileItemReader`, a line containing an unparseable number can throw `FlatFileParseException`.

Example:

```csv
source_key,payment_id,amount
r01,p01,100.00
r02,p02,not-a-number
r03,p03,25.00
```

At row `r02`, the reader has not yet created a valid `Payment` object. Therefore the callback:

```java
void onSkipInRead(Throwable error)
```

receives only the **exception**, not a mapped item. If the exception is `FlatFileParseException`, you can call `getLineNumber()` and `getInput()` to identify the source line. However, `getInput()` is raw content and may contain sensitive information; do not write it directly into general logs.

For I/O errors where reading the source cannot continue, skipping is meaningless; classify them as infrastructure errors with an appropriate fail/retry policy.

### 4.2. PROCESS Skip

The reader creates an item, but `ItemProcessor` detects a business rule violation:

```java
public final class PaymentValidationProcessor
        implements ItemProcessor<Payment, Payment> {

    @Override
    public Payment process(Payment payment) {
        if (payment.amount().signum() <= 0) {
            throw new InvalidPaymentException(
                    "AMOUNT_MUST_BE_POSITIVE");
        }
        return payment;
    }
}
```

If `InvalidPaymentException` is configured as skippable, that item is rejected and recorded in `processSkipCount`. The callback:

```java
void onSkipInProcess(Payment item, Throwable error)
```

receives both the read item and the exception. This is a convenient place to record `sourceKey`, error code, and sanitized data for reporting.

Contrast with:

```java
return null;
```

Returning `null` from a processor is **filtering**, and does not automatically trigger `onSkipInProcess`. If a business condition must appear in the rejected item report, design an explicit policy: is it a valid filtered item, or a rejected item due to rule violation?

### 4.3. WRITE Skip

Errors occur when `ItemWriter` writes one or more items—for example, an item violating a unique constraint in the database.

If the error is configured as skippable and the framework isolates the offending item, the callback:

```java
void onSkipInWrite(Payment item, Throwable error)
```

notifies about the rejected item. However, write skips are more complex than read/process skips: writers typically receive an entire **chunk**, an error can trigger a transaction rollback, and Spring Batch must run recovery logic to pinpoint the failing item.

Points requiring caution:

- A writer call can contain multiple items; the initial exception does not always identify which item failed.
- The writer may be invoked repeatedly while isolating the error; **do not use the number of times the writer threw an exception as the rejected item count**.
- External side effects outside the transaction (sending email, calling APIs, publishing messages) may have occurred before rollback; idempotency and reliable integration mechanisms are required.
- Only allow skipping write error types that the business explicitly designates as skippable. A unique violation caused by an intentional duplicate input differs from a unique violation caused by a writer bug.

When producing a rejected item report, always record the **failure phase**, because the meaning and remediation differ significantly.

## 5. Designing the Rejected Item Table

A common approach is persisting rejections into a dedicated table, e.g., PostgreSQL:

```sql
CREATE TABLE batch_rejected_item (
    rejection_id       BIGSERIAL PRIMARY KEY,
    job_execution_id   BIGINT NOT NULL,
    step_execution_id  BIGINT NOT NULL,
    phase              VARCHAR(16) NOT NULL,
    source_key         VARCHAR(255) NOT NULL,
    error_code         VARCHAR(100) NOT NULL,
    exception_type     VARCHAR(255) NOT NULL,
    reported_at        TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    resolution_status  VARCHAR(32) NOT NULL DEFAULT 'NEW',
    CONSTRAINT uq_batch_rejected_attempt
        UNIQUE (
            job_execution_id,
            step_execution_id,
            phase,
            source_key
        )
);
```

This is an **illustrative schema**; adapt column types and table names to your database. This table is **application reporting data**, not a default table in Spring Batch's metadata schema.

Column meanings:

| Column | Role |
| --- | --- |
| `rejection_id` | Internal primary key for each report record. |
| `job_execution_id` | Links to a specific Job run. |
| `step_execution_id` | Links to the StepExecution that rejected the item. |
| `phase` | `READ`, `PROCESS`, or `WRITE`. |
| `source_key` | Stable input key, e.g., source row ID or file line number. |
| `error_code` | Business-defined error code for analysis and aggregation. |
| `exception_type` | Exception class name for technical diagnostics. |
| `reported_at` | Timestamp when the report entry was persisted. |
| `resolution_status` | Subsequent handling status, e.g., `NEW`, `REVIEWED`, `CORRECTED`. |

### Choosing `source_key` Properly

For CSV inputs, you can use filename + line number. For database readers, use the source primary key; for message queues, use message ID or partition + offset.

**Do not use only the business key if the source allows multiple rows with the same business key.** Two rows with the same `payment_id` appearing at two different positions are two occurrences that must be distinguished; an overly broad unique constraint can hide a real rejected item.

To deduplicate within a single execution, the key can include:

```text
jobExecutionId + stepExecutionId + phase + sourceKey
```

If you want to group rejections **of the same business record across multiple restarts**, add another key scoped to `JobInstance` or dataset + source key. Do not merge both goals into one unique constraint without clearly defining the desired behavior.

### Where to Store Original Data?

There are three main options:

1. **Store only keys and error codes:** safe and compact, provided the source remains accessible.
2. **Store a sanitized snapshot:** useful when the source may change, while restricting allowed fields.
3. **Store raw payloads in an isolated store:** for workflows requiring full evidence, with separate encryption, access control, retention, and auditing.

Never default to writing whole CSV rows containing customer data into exception messages, application logs, or unprotected rejected-item tables.

## 6. Implementing `SkipListener` to Report Rejected Items

`SkipListener<I, O>` provides three callbacks corresponding to the three phases:

```java
public interface SkipListener<I, O> {
    void onSkipInRead(Throwable t);

    void onSkipInProcess(I item, Throwable t);

    void onSkipInWrite(O item, Throwable t);
}
```

The example below uses Spring Batch 5.x. Suppose we have an input model:

```java
import java.math.BigDecimal;

public record Payment(
        String sourceKey,
        String paymentId,
        BigDecimal amount) {
}
```

A dedicated business exception:

```java
public final class InvalidPaymentException
        extends RuntimeException {

    public InvalidPaymentException(String errorCode) {
        super(errorCode);
    }
}
```

Data structure for saving a rejection:

```java
public record Rejection(
        Long jobExecutionId,
        Long stepExecutionId,
        String phase,
        String sourceKey,
        String errorCode,
        String exceptionType) {
}
```

Reporting target interface:

```java
public interface RejectionSink {
    void save(Rejection rejection);
}
```

Illustrative listener:

```java
import org.springframework.batch.core.StepExecution;
import org.springframework.batch.core.listener.SkipListenerSupport;
import org.springframework.batch.core.scope.context.StepContext;
import org.springframework.batch.core.scope.context.StepSynchronizationManager;
import org.springframework.batch.item.file.FlatFileParseException;

public final class PaymentSkipListener
        extends SkipListenerSupport<Payment, Payment> {

    private final RejectionSink sink;

    public PaymentSkipListener(RejectionSink sink) {
        this.sink = sink;
    }

    @Override
    public void onSkipInRead(Throwable error) {
        String sourceKey;

        if (error instanceof FlatFileParseException parse) {
            sourceKey = "line:" + parse.getLineNumber();
        } else {
            // Other read errors should be classified separately.
            sourceKey = "unknown-read-position";
        }

        save("READ", sourceKey,
                "INVALID_INPUT_FORMAT", error);
    }

    @Override
    public void onSkipInProcess(
            Payment payment, Throwable error) {

        save("PROCESS", payment.sourceKey(),
                "INVALID_PAYMENT", error);
    }

    @Override
    public void onSkipInWrite(
            Payment payment, Throwable error) {

        save("WRITE", payment.sourceKey(),
                "PAYMENT_WRITE_REJECTED", error);
    }

    private void save(
            String phase,
            String sourceKey,
            String errorCode,
            Throwable error) {

        StepContext context = StepSynchronizationManager.getContext();
        if (context == null) {
            throw new IllegalStateException(
                    "Skip callback outside a Step context");
        }

        StepExecution step = context.getStepExecution();

        sink.save(new Rejection(
                step.getJobExecutionId(),
                step.getId(),
                phase,
                sourceKey,
                errorCode,
                error.getClass().getSimpleName()
        ));
    }
}
```

Key points:

- In `onSkipInRead`, a parsed item is **not available**; identify the line using the exception type, reader, or suitable source metadata.
- In `onSkipInProcess` and `onSkipInWrite`, the item is available to obtain the source key.
- `StepSynchronizationManager` uses the active Step context to retrieve Batch IDs. This assumes the listener is invoked inside a Step context managed by Spring Batch.
- `errorCode` must have stable meaning. The example uses a fixed code per phase; in a real project, classify each validation, write, or format error accurately.
- Do not put `error.getMessage()` or raw input into reports without sanitization; they may contain sensitive data.
- If multiple READ skips cannot determine their position, `unknown-read-position` is not a good unique key. Enrich position metadata or route such errors to a fail branch instead of silently deduplicating.

`SkipListenerSupport` is used for clarity in Spring Batch 5.x. If your version supports default methods on `SkipListener`, you can implement the interface directly. Avoid mixing Spring Batch 5 and 6 packages when copying examples.

## 7. Persisting Rejections to a Database with JDBC

A simple `RejectionSink` implementation can use `JdbcTemplate`:

```java
import org.springframework.jdbc.core.JdbcTemplate;

public final class JdbcRejectionSink implements RejectionSink {

    private final JdbcTemplate jdbc;

    public JdbcRejectionSink(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public void save(Rejection r) {
        jdbc.update(
            """
            INSERT INTO batch_rejected_item (
                job_execution_id,
                step_execution_id,
                phase,
                source_key,
                error_code,
                exception_type
            )
            VALUES (?, ?, ?, ?, ?, ?)
            """,
            r.jobExecutionId(),
            r.stepExecutionId(),
            r.phase(),
            r.sourceKey(),
            r.errorCode(),
            r.exceptionType()
        );
    }
}
```

In a Spring Batch configuration sharing the same `DataSource` and `PlatformTransactionManager`, the `JdbcTemplate` call from the callback can join the active chunk transaction. **Transactional consistency must be verified against your actual configuration**, especially if the rejection table resides in a different datasource or the Job uses a different transaction manager.

Per Spring Batch's contract, `SkipListener` is invoked at an appropriate point to record skipped items before the transaction commits. Even so, you must still handle process crashes, transaction rollbacks, listener re-invocations, or report persistence failures.

### If the Rejection Table Is in Another Database

When the rejection sink uses a different datasource or service, the chunk transaction does not automatically cover that call. This can happen:

```text
Chunk transaction              Rejection service
-----------------              -----------------
skip item A
send rejection A ------------> persisted
commit chunk -> FAILED

=> Report saved, but chunk did not commit.
```

If reports must stay strongly consistent with processing outcomes, prefer writing to the same database/transaction or using a **transactional outbox** with a separate worker exporting reports after commit. When using an outbox/message broker, handle events idempotently so one event is not double-counted.

A `SkipListener` callback should also never send emails or make direct HTTP calls per bad record: this slows down the Job, risks duplicate side effects, and lets a transient reporting outage disrupt main data processing.

## 8. Wiring the Listener into a Step

Complete Step example for fault tolerance configuration, using beans provided by the application:

```java
@Bean
Step importPaymentsStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<Payment> paymentReader,
        ItemProcessor<Payment, Payment> paymentProcessor,
        ItemWriter<Payment> paymentWriter,
        PaymentSkipListener paymentSkipListener) {

    return new StepBuilder("importPaymentsStep", jobRepository)
            .<Payment, Payment>chunk(100, transactionManager)
            .reader(paymentReader)
            .processor(paymentProcessor)
            .writer(paymentWriter)
            .faultTolerant()
            .skip(FlatFileParseException.class)
            .skip(InvalidPaymentException.class)
            .skipLimit(100)
            .listener(paymentSkipListener)
            .build();
}
```

Registering the related beans:

```java
@Bean
PaymentSkipListener paymentSkipListener(RejectionSink sink) {
    return new PaymentSkipListener(sink);
}

@Bean
RejectionSink rejectionSink(JdbcTemplate jdbcTemplate) {
    return new JdbcRejectionSink(jdbcTemplate);
}
```

If a class is already managed as a Spring bean via `@Component`, do not also declare the same bean with `@Bean` unless intentionally using distinct names/qualifiers. Most importantly, the listener must be **registered on the Step** for callbacks to fire.

### Distinguishing a Registered Listener from an Executed Listener

Simply declaring `PaymentSkipListener` in source code does not cause Spring Batch to invoke it. A listener bean may exist without being attached to the Step; or the Step may not execute in the Job flow; or no item may qualify for skip.

In those cases, the report can be completely empty without any JDBC error. When tests verify exact rejection counts, build a fixture with reproducible errors and confirm the callbacks execute on the real code path.

```java

FlatFileItemReader<Payment> paymentReader() {

```

Key imports:

```java

import org.springframework.batch.item.file.FlatFileItemReader;
import org.springframework.batch.item.file.builder.FlatFileItemReaderBuilder;
import org.springframework.core.io.ClassPathResource;
```

When the reader encounters `not-a-number`, `readBigDecimal` mapping fails and the reader's parse error can be wrapped as `FlatFileParseException`. With the Step configured with `skip(FlatFileParseException.class)`, this line is skipped if within the limit.

Processor:

```java
@Bean
ItemProcessor<Payment, Payment> paymentProcessor() {
    return payment -> {
        if (payment.amount().signum() <= 0) {
            throw new InvalidPaymentException(
                    "AMOUNT_MUST_BE_POSITIVE");
        }
        return payment;
    };

```

Because `r02` and `r06` have non-positive amounts, they are process-skipped. The remaining records with positive amounts proceed to the writer.

```java
@Bean

            .dataSource(dataSource)
            .sql(
                """
                INSERT INTO accepted_payment (payment_id, amount)
                VALUES (:paymentId, :amount)
```

This is a data-loading example; the application must create the `accepted_payment` table with matching types and clean old data before each test run. Key imports include `javax.sql.DataSource`, `JdbcBatchItemWriter`, `JdbcBatchItemWriterBuilder`, and `MapSqlParameterSource`.

| --- | --- | --- |

## 10. Using `SkipPolicy` for Complex Rules

`skipLimit(...)` and `skip(...)` are usually enough for common cases. If a project needs rules combining multiple error types, you can implement `SkipPolicy`.

Example policy with an absolute limit and an exception allowlist:

```java
import org.springframework.batch.core.step.skip.SkipLimitExceededException;
import org.springframework.batch.core.step.skip.SkipPolicy;
import org.springframework.batch.item.file.FlatFileParseException;

public final class PaymentSkipPolicy implements SkipPolicy {

    private static final long MAX_SKIPS = 100;

    @Override
    public boolean shouldSkip(
            Throwable error, long skipCount)
            throws SkipLimitExceededException {

        boolean eligible =
                error instanceof FlatFileParseException
                || error instanceof InvalidPaymentException;

        if (!eligible) {
            return false;
        }

        if (skipCount >= MAX_SKIPS) {
            throw new SkipLimitExceededException(
                    MAX_SKIPS, error);
        }

        return true;
    }
}
```

Registration:

```java
.faultTolerant()
.skipPolicy(new PaymentSkipPolicy())
```

`SkipPolicy.shouldSkip(...)` decides whether an exception at that moment can be skipped. Be especially careful with **`skipCount` semantics** in the API and cases where the framework checks the policy before incrementing the counter. Do not invent a complex policy when `skipLimit` plus an exception allowlist already expresses the business rule accurately.

If you want to enforce a maximum rejection ratio (e.g., skips must not exceed 1% of total input), do not look only at `skipCount`. Design how to obtain the exact denominator, choose when to evaluate, and decide what happens when exceeded:

- If the total row count is only known after reading everything, add a quality-gate Step at the end and **fail the Job** when the ratio exceeds the threshold.
- If the input row count is known upfront from a manifest, build the policy using that count and the derived absolute threshold.
- If you need to stop immediately during processing, accurately compute read/accepted counts under rollback, retry, and concurrency.

Avoid "ad-hoc" percentage limits based on a transient counter that does not yet reflect overall data state.

## 11. Combining Retry and Skip by Error Category

A Job can encounter both permanent data errors and transient technical errors. For example:

- `InvalidPaymentException`: input data lacks required validity → skip.
- `FlatFileParseException`: unparseable line → skip.
- `DeadlockLoserDataAccessException` or recoverable transient timeout → consider retry per policy.
- Prolonged database unavailability → fail and alert.

Illustrative configuration:

```java
.faultTolerant()
.skip(FlatFileParseException.class)
.skip(InvalidPaymentException.class)
.skipLimit(100)
.retry(TransientDataAccessException.class)
.retryLimit(3)
```

This illustrates **separating error categories**; database retries must account for writer idempotency, transaction boundaries, and recoverability. When a writer calls an external system, retries can cause duplicate side effects if the target lacks idempotency keys.

### When Is an Item Considered Rejected?

An item that **succeeds on retry** is not a rejected item. An item is considered skipped only when the framework decides to skip it under the skip policy and invokes the corresponding callback.

Therefore, do not emit a rejection report immediately whenever an exception is caught in a processor or writer. If the exception can still succeed on retry, the report will contain "false errors" and double-counts. Place rejected-item reporting in `SkipListener` or in a mechanism invoked after the skip decision is finalized.

## 12. Transactions, Callbacks, and Report Consistency

Distinguish three concepts:

1. **An item is skipped** per Spring Batch policy.
2. **A rejected item record is persisted**.
3. **The chunk transaction commits successfully**.

They are related, but do not always occur atomically if the report is persisted in an external system.

### 12.1. Saving Reports in the Same Step Transaction

If rejected items are written via JDBC to the same datasource and transaction manager as the Step, strong consistency is achievable: processing metadata, writer output, and rejection reports participate in the same transaction when the callback runs.

Still verify that:

- `RejectionSink` does not inadvertently use `REQUIRES_NEW` propagation.
- The report DAO/repository uses the same datasource.
- Whether a report persistence failure should fail the Step.
- If the transaction rolls back after the callback, the report is not permanently committed without corresponding handling.

### 12.2. Writing a Rejected CSV File

Some projects want to export:

```csv
source_key,phase,error_code
line:5,READ,INVALID_AMOUNT_FORMAT
r02,PROCESS,AMOUNT_MUST_BE_POSITIVE
r06,PROCESS,AMOUNT_MUST_BE_POSITIVE
```

A file report is convenient for operators, but file writes do not automatically roll back with the database. If the listener appends directly to a file, a chunk rollback followed by a rerun can produce duplicate lines.

A safer design for restartable Jobs is **storing rejections in a table/outbox with a deduplication key**, and exporting the consolidated file from committed data after the Job completes. The export file can be written to a temporary name and renamed upon completion, with filesystem-appropriate retry/update handling.

### 12.3. Sending Rejected Items to a Message Queue

If you want to stream rejected items to a data quality system:

```text
SkipListener
    |
    +-- Write rejection/outbox in same transaction
           |
           v
      Transaction commit
           |
           v
      Outbox publisher
           |
           v
      Data quality queue/topic
```

The publisher may redeliver after failure, so consumers must be **idempotent**. Use a stable event ID and clear deduplication rules. Avoid publishing messages directly from the callback if the goal is "only report committed skipped items."

## 13. Summary Metric Reporting via `StepExecution`

Spring Batch maintains counters per `StepExecution`:

| API | Meaning |
| --- | --- |
| `getReadCount()` | Number of items read successfully per Step mechanics. |
| `getWriteCount()` | Number of items recorded as written successfully. |
| `getFilterCount()` | Number of items filtered by the processor returning `null`. |
| `getReadSkipCount()` | Number of skips at the reader. |
| `getProcessSkipCount()` | Number of items skipped at the processor. |
| `getWriteSkipCount()` | Number of items skipped at the writer. |
| `getSkipCount()` | Total skips for the Step. |
| `getCommitCount()` | Number of recorded commits. |
| `getRollbackCount()` | Number of recorded rollbacks. |

You can use `StepExecutionListener.afterStep` to emit summary logs, or query via `JobExplorer` after the Job ends:

```java
for (StepExecution step : execution.getStepExecutions()) {
    log.info(
        "batch.step.quality jobExecutionId={} "
            + "stepExecutionId={} stepName={} status={} "
            + "read={} written={} filtered={} "
            + "readSkipped={} processSkipped={} writeSkipped={} "
            + "totalSkipped={}",
        execution.getId(),
        step.getId(),
        step.getStepName(),
        step.getStatus(),
        step.getReadCount(),
        step.getWriteCount(),
        step.getFilterCount(),
        step.getReadSkipCount(),
        step.getProcessSkipCount(),
        step.getWriteSkipCount(),
        step.getSkipCount()
    );
}
```

A useful summary report:

```text
Job: importPaymentsJob
JobInstance: 42
JobExecution: 811
Status: COMPLETED
Input physical records: 10
Read successfully: 9
Read rejected: 1
Process rejected: 2
Write rejected: 0
Filtered: 0
Written: 7
Total rejected: 3
Rejection report: payment-rejections-811.csv
```

`Input physical records` is not a built-in counter in every `StepExecution`. It must come from a source manifest or a dedicated counting mechanism. Do not infer physical line counts across all readers purely from `readCount + readSkipCount` if headers, blank lines, multi-line records, or other reader mechanics exist.

### Why Reconcile the Rejection Table Against Step Counters?

In a normal `JobExecution`, stored rejected items are expected to align with Step skip counts. However, if the reporting system uses a different transaction, deduplicates by business key, or has a different retention policy, counts can diverge.

An illustrative query:

```sql
SELECT
    step_execution_id,
    phase,
    COUNT(*) AS rejection_count
FROM batch_rejected_item
WHERE job_execution_id = :jobExecutionId
GROUP BY step_execution_id, phase
ORDER BY step_execution_id, phase;
```

When counts diverge, check transactions, duplicate keys, listener registration, skip policies, and query timing. Never assume "Spring Batch metadata is wrong" or manually alter metadata counters to match the report.

## 14. Designing Structured Errors to Support Reprocessing

Operators need to know **what to do with a rejection**. A stack trace string is not a good data quality report.

Design error codes and remediation categories, for example:

| Error code | Phase | Meaning | Remediation |
| --- | --- | --- | --- |
| `INVALID_AMOUNT_FORMAT` | READ | Amount cannot be parsed. | Fix amount column or adjust upstream export. |
| `AMOUNT_MUST_BE_POSITIVE` | PROCESS | Amount is not positive. | Verify business rule or source data. |
| `MISSING_REQUIRED_FIELD` | READ/PROCESS | Required field is missing. | Supply missing field or verify schema. |
| `UNKNOWN_CUSTOMER` | PROCESS | Valid customer ID not found. | Sync master data or update mapping. |
| `DUPLICATE_BUSINESS_KEY` | PROCESS/WRITE | Duplicate business key. | Check idempotency or duplicate-detection logic. |
| `WRITE_CONSTRAINT_REJECTED` | WRITE | Violated a specific skippable constraint. | Inspect cause and decide whether rejection is acceptable. |

Do not turn all infrastructure failures into `WRITE_CONSTRAINT_REJECTED`. Error codes must accurately distinguish **correctable data issues** from **operational incidents**.

### Retrying/Reprocessing Rejected Items After Fixing Data

A common workflow:

1. The main Job persists rejected items and completes per policy.
2. Operations or a data quality pipeline reviews the report and fixes source data.
3. Build a **reprocess** dataset containing the items to retry.
4. Run a dedicated reprocessing Job or Step with `JobParameters` identifying the recovery batch.
5. Link reprocessing outcomes back to original rejections and update `resolution_status`.
6. Use business/idempotency keys so previously succeeded items are not duplicated.

Do not delete original rejected items immediately upon successful reprocessing if auditing is needed. Mark them `RESOLVED` and record timestamp, data fix version, and reprocessing `JobExecution`.

## 15. Data Quality Limits: Absolute Counts and Ratios

`skipLimit(100)` is easy to understand, but may not suit every data volume:

- Job reads 1,000 records, rejects 100 → 10% failure rate.
- Job reads 10 million records, rejects 100 → 0.001% failure rate.

Same skip count, very different severity. You can define all of these:

- **Hard limit:** at most 100 rejected items in one Step.
- **Error-rate threshold:** at most 1% of source records.
- **Critical-rule threshold:** severe-category violations must never be skipped.
- **Customer/partition threshold:** at most X errors within a single independent data group.

A typical policy:

```text
Valid READ parse error ----------> skip if within limit
PROCESS validation error --------> skip if within limit
Known WRITE duplicate -----------> skip if business allows
Database unavailable ------------> fail/retry per infrastructure
Critical violation --------------> fail immediately
Total rejects exceed threshold --> fail or mark quality check failed
```

Checking the percentage at the end of the Job can be done with a dedicated quality-gate Step reading committed counters and total source records. If the quality gate fails, the Job should have an unambiguous outcome (`FAILED` or a business exit code per contract). Do not silently mark `COMPLETED` and leave operators to discover poor data quality later.

## 16. Testing Skip and Rejected Item Reporting

An integration test must verify **two layers of outcomes**:

1. Did Spring Batch skip the right errors and update `StepExecution` status/counters?
2. Does the rejected item report have the right count, phase, error codes, and execution linkage?

Example using Spring Batch 5.x, JUnit Jupiter, and AssertJ. Assume Job `importPaymentsJob` uses the CSV fixture in section 9, the writer inserts into `accepted_payment`, and `PaymentSkipListener` writes to `batch_rejected_item`.

```java
import java.util.UUID;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.batch.core.BatchStatus;
import org.springframework.batch.core.Job;
import org.springframework.batch.core.JobExecution;
import org.springframework.batch.core.JobParametersBuilder;
import org.springframework.batch.core.StepExecution;
import org.springframework.batch.test.JobLauncherTestUtils;
import org.springframework.batch.test.JobRepositoryTestUtils;
import org.springframework.batch.test.context.SpringBatchTest;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBatchTest
@SpringBootTest(properties = "spring.batch.job.enabled=false")
class PaymentRejectionIT {

    @Autowired
    private JobLauncherTestUtils jobLauncherTestUtils;

    @Autowired
    private JobRepositoryTestUtils jobRepositoryTestUtils;

    @Autowired
    private JdbcTemplate jdbc;

    @Autowired
    @Qualifier("importPaymentsJob")
    private Job job;

    @BeforeEach
    void resetTestData() {
        // Only use on a dedicated test database/schema.
        jdbc.update("DELETE FROM batch_rejected_item");
        jdbc.update("DELETE FROM accepted_payment");
        jobRepositoryTestUtils.removeJobExecutions();
        jobLauncherTestUtils.setJob(job);
    }

    @Test
    void shouldSkipAndReportThreeInvalidRows() throws Exception {
        var params = new JobParametersBuilder()
                .addString("runId", UUID.randomUUID().toString(), true)
                .toJobParameters();

        JobExecution execution =
                jobLauncherTestUtils.launchJob(params);

        assertThat(execution.getStatus())
                .isEqualTo(BatchStatus.COMPLETED);

        StepExecution step = execution.getStepExecutions().stream()
                .filter(it -> "importPaymentsStep".equals(it.getStepName()))
                .findFirst()
                .orElseThrow();

        assertThat(step.getReadCount()).isEqualTo(9);
        assertThat(step.getReadSkipCount()).isEqualTo(1);
        assertThat(step.getProcessSkipCount()).isEqualTo(2);
        assertThat(step.getWriteSkipCount()).isZero();
        assertThat(step.getSkipCount()).isEqualTo(3);
        assertThat(step.getWriteCount()).isEqualTo(7);

        Integer rejected = jdbc.queryForObject(
                """
                SELECT COUNT(*)
                FROM batch_rejected_item
                WHERE job_execution_id = ?
                  AND step_execution_id = ?
                """,
                Integer.class,
                execution.getId(),
                step.getId());

        Integer accepted = jdbc.queryForObject(
                "SELECT COUNT(*) FROM accepted_payment",
                Integer.class);

        assertThat(rejected).isEqualTo(3);
        assertThat(accepted).isEqualTo(7);
    }
}
```

In a real test, add assertions on `phase`, `source_key`, and `error_code`, for example:

```java
Integer readRejected = jdbc.queryForObject(
        """
        SELECT COUNT(*) FROM batch_rejected_item
        WHERE job_execution_id = ? AND phase = 'READ'
        """,
        Integer.class,
        execution.getId());

Integer processRejected = jdbc.queryForObject(
        """
        SELECT COUNT(*) FROM batch_rejected_item
        WHERE job_execution_id = ? AND phase = 'PROCESS'
        """,
        Integer.class,
        execution.getId());

assertThat(readRejected).isEqualTo(1);
assertThat(processRejected).isEqualTo(2);
```

**Test assumptions:** The CSV contains exactly 10 data records, the reader creates no item for unparseable rows, the processor rejects the two non-positive amounts, the writer completes the remaining seven, and the listener shares the appropriate transaction to persist three rejections. Test libraries and database schema must be preconfigured. This tests **expected behavior**, not a standalone runnable test without application/fixture setup.

### Testing Exceeding `skipLimit`

Create a fixture with more invalid items than the limit:

- `skipLimit(2)`.
- Three items violate skippable rules.
- Assert `JobExecution.status == FAILED` when the next skip exceeds the limit.
- Inspect Step logs/metadata and committed report entries.
- Do not assume all items after the failing record were read.

Note that writer outputs and rejections committed before the failure may still exist. Spring Batch does not roll back the entire history of previously committed chunks just because the Job ultimately ended `FAILED`.

### Testing Non-Skippable Errors

Have the reader or writer throw an exception **not in the skip policy**, such as an unrecoverable datasource error. Assert the Job fails and does not record a rejection labeled "invalid data error."

### Testing Rollback/Retry

Use a fixture producing a writer error that is retried and then succeeds. Assert:

- The item is written exactly once by business key.
- No rejected item is recorded for an error that succeeded on retry.
- No duplicate report entries occur from writer re-invocations.
- `rollbackCount` / retry instrumentation reflect expected behavior.

## 17. Restart and Rejected Item Reporting

A `JobInstance` can have multiple `JobExecution` records when it fails and restarts:

```text
JobInstance #42
  |
  +-- JobExecution #811: FAILED
  |     |
  |     +-- read skip r04
  |     +-- process skip r02
  |
  +-- JobExecution #812: COMPLETED (restart)
        |
        +-- process skip r06 or reprocessed depending on checkpoint
```

Reporting should preserve both perspectives:

- **By JobExecution:** which items did run `811` reject?
- **By JobInstance or dataset:** how many **unique source items** in total were rejected across retries/restarts?

If the report deduplicates only by `jobExecutionId`, the same source item can reappear under the new execution ID. That is right for per-execution auditing, but not a list of unique rejected business records.

When producing a final consolidated business report, group by dataset/source key and final resolution status, distinguishing unresolved errors from items successfully resolved after reprocessing.

**Do not delete Spring Batch metadata between failure and restart.** `ExecutionContext` and Step history determine the resumption point. Also do not purge the rejected-item table before preserving audits if traceability is required.

## 18. Concurrency and Partitioning

When a Step uses multi-threaded chunk processing or partitioning, rejected-item reporting has additional requirements:

- Shared listeners/sinks must be thread-safe.
- Do not store `currentItem` or `currentStepExecution` in mutable singleton fields assuming a single thread.
- `source_key` must be unique across partitions; `"line:10"` in two different files is not the same record.
- Summary queries should group by `JobExecution` and `StepExecution`; with partitioning, `StepExecution` names may look like `workerStep:partition0`, `workerStep:partition1`.
- If multiple workers write to the same report table, unique keys and indexes must support the throughput without causing unnecessary lock contention.
- If one worker fails, other partitions may have committed; final status and restart policy must be understood per the flow and partition handler.

Example of a safer source key for partitions:

```text
sourceSystem + datasetId + partitionId + recordOffset
```

Do not rely on log line order to reconstruct data order under concurrency.

## 19. Observability and Operating Rejection Reports

A data quality system should expose these metrics:

| Metric | Meaning |
| --- | --- |
| `batch_read_skip_total` | Total skips at the reader by Job/Step and error type. |
| `batch_process_skip_total` | Total skips at the processor. |
| `batch_write_skip_total` | Total skips at the writer. |
| `batch_rejected_ratio` | Rejection ratio against a defined denominator. |
| `batch_job_status` | Final status of the `JobExecution`. |
| `batch_rejection_backlog` | Number of rejected items not yet reprocessed or confirmed. |
| `batch_reprocess_success_total` | Number of rejected items fixed and reprocessed successfully. |

For metrics, avoid attaching `jobExecutionId`, `source_key`, or exception messages to **metric labels** due to excessive cardinality. Put those in detailed logs/reports instead. Metric tags should be restricted to `jobName`, `stepName`, `phase`, `errorCode`, and bounded values.

A Job completion log might include:

```text
INFO batch.job.dataQuality
  jobName=importPaymentsJob
  jobExecutionId=811
  stepName=importPaymentsStep
  status=COMPLETED
  readCount=9
  writeCount=7
  readSkipped=1
  processSkipped=2
  writeSkipped=0
  totalSkipped=3
  reportId=payment-rejections-811
```

If a Job completes (`COMPLETED`) with rejected items, dashboards should not just show green "complete success" without quality context. Add a "completed with rejected data" warning in the reporting layer or a custom exit code if agreed upon in the operational contract.

### Designing the Rejected-Item Handling Workflow

A manageable operational workflow might include:

1. **NEW:** Job detects and persists the rejected item.
2. **REVIEWED:** Operator or system classifies the root cause.
3. **CORRECTED:** Source data has been fixed or supplemented.
4. **REPROCESSED:** Another Job attempts reprocessing.
5. **RESOLVED:** Output verified written successfully; close rejection.
6. **WAIVED:** Business rule accepts not processing the record, with reason/approval.

These states are a suggested business design. Ensure data cannot enter an infinite retry loop or repeatedly report the same error without corrective action.

## 20. Common Mistakes

### 20.1. Using `skip(Exception.class)` for All Error Types

A database failure or bug can be turned into a skip, hiding systemic issues. Only skip exceptions explicitly classified as isolated skippable data errors.

### 20.2. Equating Filter with Reject

`ItemProcessor` returning `null` typically increments `filterCount` without calling `SkipListener`. If every dropped row must be reported, design explicit observability for filtered items according to business rules.

### 20.3. Writing Rejected Items Inside a Processor `catch` Block

An error might succeed on retry or the transaction might roll back. Reporting as soon as an exception appears causes duplicates and fails to reflect the final skip decision. Prefer `SkipListener` or a transaction/commit-aware mechanism.

### 20.4. Using Raw Exception Messages as `errorCode`

Messages can change or expose sensitive data. Create stable error codes and record only sanitized details when needed.

### 20.5. Failing to Identify Item Origin in Read Skips

The reader has not created an item yet; `onSkipInRead` has no mapped source object. Extract line position, offset, or source info from the exception/reader when available. If the origin cannot be reliably identified, report an unknown-origin error category rather than fabricating a record ID.

### 20.6. Using an Overly Broad Unique Key in Reports

Grouping solely by `paymentId` can lose information when two different source rows share the same payment ID. Use a source occurrence ID for per-execution audits, and a separate business key for consolidated reports.

### 20.7. Forgetting That Chunks Can Roll Back

The writer is called again, listeners may run in another transaction, and external side effects can repeat. Persist rejections with proper rollback/idempotency guarantees.

### 20.8. Asserting Only `JobExecution.COMPLETED`

A Job can finish with many rejected items. Tests must verify per-phase `skipCount`, output data, and rejection reports, not just final status.

### 20.9. Purging Metadata Before Exporting Reports

If reports depend on `jobExecutionId`, `StepExecution` counters, or Job parameters, deleting metadata before aggregation destroys reconciliation context. Retain metadata long enough per retention policy and complete report exports first.

### 20.10. Ignoring Rejected Data

If reports are generated and then ignored, data quality degrades over time. Establish review, data correction, reprocessing, and closure workflows with backlog metrics and SLAs.

## 21. Practice Exercise

Suppose `importCustomersJob` receives a CSV file of 1,000 customers containing:

- 20 rows missing a required email.
- 5 rows with an unparseable birth date.
- 3 rows with duplicate customer IDs per business rules.
- Remaining rows are valid.

Build a Step capable of skipping permitted data errors and generating a rejected-item report.

### Technical Requirements

1. Define `MissingRequiredEmailException`, `InvalidBirthDateException`, and `DuplicateCustomerException`; decide exactly which exceptions are skippable.
2. Configure `faultTolerant()`, an exception allowlist, and a reasonable `skipLimit`.
3. Write a `SkipListener` capturing source position in READ and source key from the item in PROCESS/WRITE.
4. Persist rejections in a table with `jobExecutionId`, `stepExecutionId`, `phase`, `sourceKey`, and `errorCode`.
5. After the Job, export a CSV/JSON report only from committed rejection data.
6. Use `JobExplorer` or `JobExecution.getStepExecutions()` to reconcile skip counts per phase.
7. Verify valid records are written exactly once by business key.
8. Add a test exceeding `skipLimit` and confirm the Job fails per policy.
9. Test a database error not in the allowlist and confirm it is **not** silently skipped.
10. Test a controlled restart after failure and verify rejection history per `JobExecution`.

### One Expected Outcome

If all 28 bad records are recognized as distinct skips, no other filter applies, the skip limit allows at least 28, and the Job and writer operate normally:

```text
Input records       : 1000
Rejected READ       : 5
Rejected PROCESS    : 23
Rejected WRITE      : 0
Total rejected      : 28
Accepted / written  : 972
Job status          : COMPLETED
```

These numbers are an **illustrative scenario**; whether duplicates or missing emails appear in READ vs. PROCESS depends on which layer runs validation. If duplicates are only detected when the writer inserts into the DB, write skips may occur instead of process skips; adjust reports and tests to match your actual setup.

### Self-Check Questions

- How many items does `skipLimit(10)` allow to be skipped before the Step fails?
- Why might a READ error not provide a successfully mapped item?
- When should `ItemProcessor` return `null`, and when should it throw an exception to skip?
- Why should `onSkipInWrite` not record a rejected item via a direct HTTP request?
- If the writer retries three times and succeeds, is that record a rejected item?
- Why is `readCount` not necessarily equal to the physical line count in a file?
- If a restart creates a new `JobExecution`, how do you report both execution history and unique rejected items?
- Why might a `COMPLETED` Job still require a data quality alert?
