# StaxEventItemReader

Trong Spring Batch, `StaxEventItemReader<T>` đọc dữ liệu XML theo kiểu streaming bằng StAX (Streaming API for XML). Thay vì nạp toàn bộ tài liệu XML thành một cây DOM, reader duyệt các XML event và tách những element được chọn thành các fragment. Mỗi fragment thường đại diện cho một record nghiệp vụ và được chuyển thành object Java thông qua một `Unmarshaller` của Spring OXM.

Ví dụ một file XML có root `<trades>` chứa hàng trăm nghìn element `<trade>`. Reader có thể đọc từng `<trade>` thành một `Trade`, rồi đưa item vào chunk Step để processor và writer xử lý. Cách này phù hợp với file XML lớn có cấu trúc lặp lại, nơi mỗi record được bao bởi một element rõ ràng.

## 1. StAX và cách đọc XML theo event

StAX là API Java để đọc XML theo hướng pull/event. Ứng dụng yêu cầu parser cung cấp event tiếp theo, chẳng hạn bắt đầu document, bắt đầu element, text, kết thúc element hoặc kết thúc document.

Một số event thường gặp:

| Event | Ý nghĩa |
|---|---|
| `START_DOCUMENT` | Bắt đầu tài liệu XML |
| `START_ELEMENT` | Bắt đầu một element |
| `CHARACTERS` | Nội dung text bên trong element |
| `END_ELEMENT` | Kết thúc một element |
| `END_DOCUMENT` | Kết thúc tài liệu XML |

Ví dụ XML:

```xml
<trades>
    <trade>
        <isin>US0378331005</isin>
        <quantity>100</quantity>
        <price>215.75</price>
    </trade>
    <trade>
        <isin>US5949181045</isin>
        <quantity>50</quantity>
        <price>420.10</price>
    </trade>
</trades>
```

Parser StAX duyệt các event trong document. `StaxEventItemReader` tìm element được cấu hình làm fragment root, đọc trọn fragment đó và chuyển fragment cho `Unmarshaller`. Sau khi fragment được map thành object, reader trả object cho Spring Batch. Lần gọi `read()` tiếp theo sẽ tìm fragment tiếp theo.

## 2. Vì sao dùng StaxEventItemReader?

DOM thường tạo object tree cho toàn bộ tài liệu XML trong bộ nhớ. Với file rất lớn, cách này có thể tiêu thụ nhiều heap. StAX cho phép xử lý tuần tự theo event, chỉ giữ phần dữ liệu cần thiết để tạo item hiện tại cùng buffer của parser và chunk.

`StaxEventItemReader` phù hợp khi:

- XML chứa nhiều record lặp lại dưới một root element chung.
- Mỗi record có thể được biểu diễn bởi một fragment element hoàn chỉnh.
- File lớn cần được đọc tuần tự mà không nạp toàn bộ DOM.
- Có thể ánh xạ từng fragment thành một object Java bằng JAXB hoặc OXM `Unmarshaller` khác.
- Cần tích hợp đọc XML với chunk processing, transaction, skip/retry và restart của Spring Batch.

Streaming giảm nhu cầu giữ toàn bộ document trong bộ nhớ, nhưng không có nghĩa bộ nhớ luôn cố định tuyệt đối. Parser giữ buffer, mỗi fragment tạo object graph và Spring Batch giữ các item trong chunk cho đến khi xử lý/commit. Kích thước object và chunk vẫn ảnh hưởng heap.

## 3. Fragment root element là gì?

`StaxEventItemReader` không mặc định tạo một item cho mọi element trong XML. Cần chỉ định element nào đại diện cho một record cần đọc. Element đó được gọi là *fragment root element*.

Trong ví dụ trên, `<trades>` là document root, còn mỗi `<trade>` là một fragment:

```xml
<trades>
    <trade>...</trade>  <!-- item 1 -->
    <trade>...</trade>  <!-- item 2 -->
    <trade>...</trade>  <!-- item 3 -->
</trades>
```

Reader tìm fragment root `trade`, lấy cả nội dung con bên trong element đó và chuyển thành một object `Trade`. Nó không tạo một item cho `<trades>` nếu ta cấu hình fragment root là `trade`.

Chọn element đại diện cho một đơn vị nghiệp vụ. Nếu chọn element quá rộng, một fragment có thể chứa nhiều record. Nếu chọn element quá nhỏ, reader có thể tạo item từ một phần dữ liệu không đủ để tạo object nghiệp vụ.

## 4. Cấu hình StaxEventItemReader cơ bản

Spring Batch cung cấp `StaxEventItemReaderBuilder` để cấu hình reader. Ví dụ:

```java
@Bean
public StaxEventItemReader<Trade> tradeReader(
        Resource tradeResource,
        Unmarshaller tradeUnmarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(tradeResource)
            .addFragmentRootElements("trade")
            .unmarshaller(tradeUnmarshaller)
            .saveState(true)
            .strict(true)
            .build();
}
```

Các cấu hình chính:

- `name("tradeReader")`: tên ổn định để reader lưu và khôi phục state.
- `resource(tradeResource)`: file XML cần đọc.
- `addFragmentRootElements("trade")`: xác định element đại diện cho một item.
- `unmarshaller(tradeUnmarshaller)`: chuyển XML fragment thành object Java.
- `saveState(true)`: bật lưu checkpoint trong Step `ExecutionContext`.
- `strict(true)`: yêu cầu resource phải tồn tại khi mở reader theo hành vi strict của reader.

Tên method builder có thể khác theo phiên bản Spring Batch. Với các phiên bản hỗ trợ nhiều fragment root, có thể truyền nhiều tên vào `addFragmentRootElements(...)`.

## 5. Tạo Unmarshaller bằng JAXB

`StaxEventItemReader` cần một `Unmarshaller` để chuyển fragment XML thành object. Spring OXM cung cấp `Jaxb2Marshaller`, có thể cấu hình các class JAXB được bind.

Ví dụ model:

```java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

import java.math.BigDecimal;

@XmlRootElement(name = "trade")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {

    @XmlElement(name = "isin")
    private String isin;

    @XmlElement(name = "quantity")
    private int quantity;

    @XmlElement(name = "price")
    private BigDecimal price;

    public Trade() {
    }

    public String getIsin() {
        return isin;
    }

    public int getQuantity() {
        return quantity;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
```

Khai báo marshaller:

```java
@Bean
public Jaxb2Marshaller tradeMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    return marshaller;
}
```

`Jaxb2Marshaller` của Spring OXM triển khai contract `Unmarshaller`, nên có thể truyền trực tiếp vào reader. Ví dụ dùng package `jakarta.xml.bind` phù hợp với các phiên bản Spring mới dùng Jakarta EE; dự án cũ có thể dùng `javax.xml.bind` tùy phiên bản Spring/JAXB dependency.

Tên root element và các element con trong JAXB mapping phải khớp với XML fragment. Nếu tên khác, dùng annotation như `@XmlRootElement` và `@XmlElement` để khai báo mapping rõ ràng.

## 6. Ví dụ XML và object mapping hoàn chỉnh

File `trades.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<trades>
    <trade>
        <isin>US0378331005</isin>
        <quantity>100</quantity>
        <price>215.75</price>
    </trade>
    <trade>
        <isin>US5949181045</isin>
        <quantity>50</quantity>
        <price>420.10</price>
    </trade>
</trades>
```

Reader:

```java
@Bean
public StaxEventItemReader<Trade> tradeReader(Jaxb2Marshaller tradeMarshaller) {
    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(new ClassPathResource("data/trades.xml"))
            .addFragmentRootElements("trade")
            .unmarshaller(tradeMarshaller)
            .saveState(true)
            .build();
}
```

Mỗi lần `read()` trả về một `Trade`:

| Lần đọc | `isin` | `quantity` | `price` |
|---:|---|---:|---:|
| 1 | `US0378331005` | 100 | 215.75 |
| 2 | `US5949181045` | 50 | 420.10 |
| 3 | EOF | — | — |

Khi không còn fragment phù hợp, reader trả `null` để báo hết dữ liệu cho Spring Batch.

## 7. Đọc file XML từ JobParameters

Trong production, file XML thường thay đổi theo từng lần chạy. Có thể dùng `@StepScope` để inject file path từ JobParameters:

```java
@Bean
@StepScope
public StaxEventItemReader<Trade> tradeReader(
        @Value("#{jobParameters['inputFile']}") String inputFile,
        Jaxb2Marshaller tradeMarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(new FileSystemResource(inputFile))
            .addFragmentRootElements("trade")
            .unmarshaller(tradeMarshaller)
            .saveState(true)
            .strict(true)
            .build();
}
```

`@StepScope` giúp biểu thức JobParameters được đánh giá khi StepExecution hiện tại đã tồn tại. Mỗi lần chạy có thể đọc file khác nhau mà không phải tạo một singleton reader giữ mutable path.

Nếu `inputFile` là tham số bắt buộc, hãy validate trước khi mở reader. Nếu dùng default path, cần quyết định liệu default đó có phải được materialize vào JobParameters để bảo đảm restart luôn dùng đúng file ban đầu hay không.

## 8. Tích hợp vào chunk-oriented Step

Reader được đăng ký trong Step giống các reader khác:

```java
@Bean
public Step importTradesStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        StaxEventItemReader<Trade> tradeReader,
        ItemProcessor<Trade, Trade> tradeProcessor,
        ItemWriter<Trade> tradeWriter) {

    return new StepBuilder("importTradesStep", jobRepository)
            .<Trade, Trade>chunk(100, transactionManager)
            .reader(tradeReader)
            .processor(tradeProcessor)
            .writer(tradeWriter)
            .build();
}
```

Với chunk size 100, Step đọc tối đa 100 fragment, xử lý và ghi chúng trong một chunk theo transaction manager. Reader vẫn giữ trạng thái parser để tiếp tục fragment kế tiếp; nó không mở lại toàn bộ file cho từng chunk.

Chunk size ảnh hưởng số object được giữ trong chunk và tần suất commit. Nếu fragment XML lớn, cần đo heap và thời gian mapping để chọn chunk size phù hợp.

## 9. Nhiều loại fragment root

Một tài liệu XML có thể chứa nhiều loại record cần xử lý. Một số phiên bản Spring Batch hỗ trợ khai báo nhiều fragment root element:

```java
return new StaxEventItemReaderBuilder<Object>()
        .name("mixedXmlReader")
        .resource(resource)
        .addFragmentRootElements("trade", "cashMovement")
        .unmarshaller(mixedUnmarshaller)
        .build();
```

Khi dùng nhiều loại fragment, `Unmarshaller` cần biết cách chuyển từng root element thành kiểu object tương ứng. Có thể dùng JAXB model với nhiều class được bind hoặc một lớp wrapper/base type phù hợp.

Nếu mỗi fragment có cấu trúc rất khác nhau, một reader trả về interface/base class có thể cần custom unmarshaller để phân biệt root element và chọn class đích. Đừng giả định một `Jaxb2Marshaller` có thể tự động tạo đúng mọi kiểu chỉ vì các class đã được đăng ký; cần cấu hình JAXB mapping và kiểm thử từng fragment.

Nếu phiên bản Spring Batch đang dùng chỉ cấu hình được một fragment root, có thể tạo reader riêng cho từng loại file/nhánh hoặc viết component mapping phù hợp thay vì dựa vào API chưa được hỗ trợ.

## 10. XML namespace

XML có thể dùng namespace mặc định hoặc prefix:

```xml
<trades xmlns="urn:example:trades">
    <trade>
        <isin>US0378331005</isin>
        <quantity>100</quantity>
    </trade>
</trades>
```

Namespace là một phần của tên XML đầy đủ (QName). JAXB model cần khai báo namespace phù hợp nếu XML sử dụng namespace:

```java
@XmlRootElement(name = "trade", namespace = "urn:example:trades")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {
    // fields và annotation tương ứng
}
```

Khi cấu hình fragment root, kiểm tra cách phiên bản Spring Batch đang dùng so khớp tên element và namespace. Ví dụ `"trade"` thường được dùng làm tên fragment trong cấu hình cơ bản; với XML có namespace, cần xác nhận local name/QName behavior của API và kiểm thử file thực tế. Việc JAXB mapping có namespace đúng không tự bảo đảm reader tìm fragment đúng nếu cấu hình root không khớp.

Không loại bỏ namespace khỏi XML chỉ để làm mapping dễ hơn nếu namespace thuộc hợp đồng dữ liệu. Namespace giúp phân biệt các vocabulary XML có thể dùng chung tên element.

## 11. Element lồng nhau và lựa chọn fragment root

Một fragment root có thể chứa nhiều element con, thậm chí các element con có cùng tên với fragment root:

```xml
<orders>
    <order>
        <orderId>1001</orderId>
        <lines>
            <line>
                <sku>A-10</sku>
                <quantity>2</quantity>
            </line>
        </lines>
    </order>
</orders>
```

Ở đây nên chọn `order` làm fragment root nếu một item là một đơn hàng. Không chọn `line` nếu processor/writer cần toàn bộ order cùng các dòng chi tiết.

Khi cùng một tên element xuất hiện ở nhiều cấp, cần kiểm tra parser/reader nhận diện fragment theo tên và cấu trúc như thế nào. Chọn tên fragment đặc thù và cấu trúc XML không mơ hồ giúp tránh tách nhầm element con thành item độc lập.

Nếu XML lồng nhiều record cùng loại và muốn xử lý cả record cha lẫn record con, một reader đơn giản với cùng fragment root có thể không diễn đạt đúng yêu cầu. Hãy cân nhắc custom event processing hoặc tách các loại record thành các Step riêng.

## 12. strict và kiểm tra schema XML

`strict` của reader chủ yếu liên quan đến việc yêu cầu resource tồn tại khi mở reader. Nó không đồng nghĩa với việc xác thực toàn bộ XML theo XSD.

Hai vấn đề khác nhau:

- **Resource strictness:** file đầu vào có tồn tại hay không.
- **XML schema validation:** cấu trúc, namespace, element và kiểu dữ liệu có tuân theo XSD hay không.

Nếu cần xác thực XML theo XSD, cấu hình validation cho JAXB/OXM unmarshaller hoặc thực hiện validation ở một bước riêng. Ví dụ với `Jaxb2Marshaller`:

```java
@Bean
public Jaxb2Marshaller tradeMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.setSchemas(new ClassPathResource("xsd/trades.xsd"));
    return marshaller;
}
```

Schema cần phù hợp namespace và version của XML. Nếu nguồn XML không tin cậy, cần cấu hình parser an toàn và kiểm tra cả hành vi xử lý external entity; XSD validation không thay thế bảo vệ parser.

## 13. Bảo mật XML parser và XXE

XML từ nguồn bên ngoài có thể chứa DTD hoặc external entity. Nếu parser cho phép tải external entity, dữ liệu XML độc hại có thể khiến ứng dụng đọc file cục bộ hoặc truy cập tài nguyên mạng ngoài ý muốn (XXE).

Khi cấu hình StAX `XMLInputFactory`, nên tắt DTD và external entity nếu nghiệp vụ không cần:

```java
XMLInputFactory inputFactory = XMLInputFactory.newFactory();
inputFactory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
inputFactory.setProperty(
        XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES,
        false
);
```

Nếu phiên bản `StaxEventItemReader` cung cấp setter cho `XMLInputFactory`, truyền factory đã cấu hình vào reader. Ví dụ:

```java
StaxEventItemReader<Trade> reader = new StaxEventItemReader<>();
reader.setName("tradeReader");
reader.setResource(resource);
reader.setFragmentRootElementName("trade");
reader.setUnmarshaller(tradeMarshaller);
reader.setXmlInputFactory(inputFactory);
reader.setSaveState(true);
```

Tên API cụ thể phụ thuộc phiên bản Spring Batch. Một số StAX provider có thể không hỗ trợ property giống nhau hoặc ném exception khi đặt property không được hỗ trợ. Hãy xác nhận cấu hình thực tế bằng test với provider trong production và dùng chính sách fail-closed nếu không thể tắt external entity theo yêu cầu bảo mật.

Không bật DTD/external entity chỉ để xử lý một file đặc biệt mà chưa đánh giá nguồn dữ liệu và nguy cơ truy cập tài nguyên ngoài. Nếu XML cần tham chiếu schema, ưu tiên schema được quản lý cục bộ hoặc cấu hình resolver an toàn.

## 14. Checkpoint và restart

`StaxEventItemReader` hỗ trợ lưu state thông qua cơ chế item-counting reader. Khi `saveState(true)`, reader lưu tiến độ đọc vào Step `ExecutionContext` để có thể tiếp tục khi Job restart cùng JobInstance.

Ví dụ:

```java
return new StaxEventItemReaderBuilder<Trade>()
        .name("tradeReader")
        .resource(resource)
        .addFragmentRootElements("trade")
        .unmarshaller(tradeMarshaller)
        .saveState(true)
        .build();
```

Khi restart:

1. Spring Batch tạo StepExecution mới cho lần thực thi lại.
2. Reader mở lại XML resource và tạo StAX event reader mới.
3. Reader đọc checkpoint đã lưu trong ExecutionContext.
4. Reader bỏ qua các fragment đã được ghi nhận trong item count để đến vị trí cần tiếp tục.
5. Reader trả fragment tiếp theo cho Step.

Parser/event reader cũ không được giữ qua process restart. Reader phải mở lại resource và tái tạo vị trí từ state đã lưu.

Vì checkpoint dựa trên số item/fragment đã đọc, nội dung và thứ tự fragment trong file cần ổn định giữa lần chạy đầu và restart. Nếu upstream thay file hoặc thêm/xóa fragment ở đầu tài liệu, item count cũ có thể trỏ sang record khác.

## 15. Resource và JobParameters phải ổn định

Với file đầu vào thay đổi theo lần chạy, thường dùng `@StepScope` để inject path:

```java
@Bean
@StepScope
public StaxEventItemReader<Trade> tradeReader(
        @Value("#{jobParameters['inputFile']}") String inputFile,
        Jaxb2Marshaller tradeMarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(new FileSystemResource(inputFile))
            .addFragmentRootElements("trade")
            .unmarshaller(tradeMarshaller)
            .saveState(true)
            .build();
}
```

Để restart đúng dữ liệu:

- Giữ nguyên identifying JobParameters của JobInstance.
- Truyền cùng `inputFile` khi restart nếu file path là một phần của đầu vào.
- Giữ nguyên nội dung file, không ghi đè file đang được Job xử lý.
- Dùng tên reader ổn định để checkpoint key không thay đổi.
- Lưu checksum/version/manifest nếu cần xác nhận file vẫn là bản ban đầu.
- Không tạo path hoặc tên file tạm ngẫu nhiên mới khi restart nếu checkpoint phụ thuộc nội dung cũ.

Nếu file được chuyển vào thư mục inbound, có thể copy sang thư mục staging bất biến trước khi khởi chạy Job. Sau khi Job hoàn tất, chuyển file sang archive theo quy trình vận hành.

## 16. Lỗi parse và lỗi unmarshal

Lỗi có thể xảy ra ở nhiều giai đoạn:

| Giai đoạn | Ví dụ | Hướng xử lý |
|---|---|---|
| Mở resource | File không tồn tại, không có quyền đọc | Kiểm tra path/quyền; fail sớm nếu file bắt buộc |
| Parse StAX | XML không well-formed, tag đóng/mở sai | Sửa nguồn XML; thường nên fail vì parser có thể không tiếp tục an toàn |
| Tìm fragment | Không có fragment root được cấu hình | Kiểm tra root element và cấu trúc file |
| Unmarshal | Element/attribute không map được, sai kiểu | Kiểm tra JAXB mapping, converter và schema |
| Validation | XML không tuân thủ XSD hoặc quy tắc nghiệp vụ | Phân loại lỗi cấu trúc và lỗi nghiệp vụ |

Không nên cấu hình skip rộng cho mọi exception parse XML. Nếu document bị malformed ở giữa file, parser có thể không biết cách đồng bộ lại vị trí fragment tiếp theo. Skip phù hợp hơn với lỗi dữ liệu cô lập ở một fragment hoàn chỉnh mà parser vẫn tiếp tục được.

Nếu chỉ một fragment có giá trị nghiệp vụ sai nhưng XML vẫn well-formed, có thể để unmarshaller tạo object rồi processor validate và ném exception riêng để áp dụng skip policy. Cách này giữ việc parse XML tách biệt với quy tắc nghiệp vụ.

## 17. Kết hợp retry và skip

Reader có thể tham gia fault-tolerant Step. Tuy nhiên, cần phân biệt lỗi tạm thời ở resource/I/O với lỗi XML cố định:

- Lỗi filesystem/network tạm thời có thể retry nếu reader có thể mở lại resource an toàn.
- Fragment không hợp lệ theo quy tắc nghiệp vụ có thể được skip nếu parser đã đọc được fragment và việc bỏ item được chấp nhận.
- XML malformed làm parser mất đồng bộ thường nên làm Step thất bại.
- Lỗi JAXB mapping do cấu hình sai thường không thể tự phục hồi bằng retry.

Ví dụ Step có skip policy cho exception nghiệp vụ từ processor:

```java
return new StepBuilder("importTradesStep", jobRepository)
        .<Trade, Trade>chunk(100, transactionManager)
        .reader(tradeReader)
        .processor(tradeValidationProcessor)
        .writer(tradeWriter)
        .faultTolerant()
        .skip(InvalidTradeException.class)
        .skipLimit(25)
        .build();
```

Ở đây `InvalidTradeException` được ném sau khi fragment đã được map thành `Trade`. Không nên tự động skip `XMLStreamException` hoặc mọi `UnmarshalException` nếu chưa xác nhận reader có thể tiếp tục an toàn.

## 18. Hiệu năng và quản lý bộ nhớ

StAX streaming tránh tạo DOM cho toàn bộ file, nhưng hiệu năng vẫn phụ thuộc cấu trúc XML và object graph:

- Fragment càng lớn, object graph mỗi item càng tốn heap.
- Chunk size lớn giữ nhiều object trước khi commit.
- JAXB mapping và validation XSD có chi phí CPU.
- Namespace, converter và collection lồng nhau có thể tăng chi phí mapping.
- Processor/writer có thể giữ thêm state hoặc cache ngoài reader.

Khi tối ưu:

- Chỉ bind các element cần thiết vào model.
- Chọn chunk size dựa trên kích thước object và thời gian transaction.
- Dùng JAXB class binding rõ ràng thay cho mapping động phức tạp nếu schema ổn định.
- Đo heap, GC, throughput và thời gian parse bằng file gần kích thước production.
- Tránh giữ toàn bộ danh sách item trong processor hoặc writer.
- Kiểm tra số lượng fragment và kích thước lớn nhất của từng fragment.

Không nên giả định StAX sẽ giải quyết mọi vấn đề bộ nhớ nếu một fragment chứa hàng trăm nghìn node con hoặc processor tích lũy toàn bộ item vào collection.

## 19. Khi nào dùng StaxEventItemReader thay cho DOM hoặc custom StAX?

| Cách đọc | Đặc điểm | Khi phù hợp |
|---|---|---|
| DOM | Nạp document thành cây object XML | File nhỏ, cần truy cập ngẫu nhiên/nhiều lần vào cấu trúc |
| `StaxEventItemReader` | Đọc event tuần tự và map fragment thành item | File XML lớn với record element lặp lại |
| Custom StAX reader | Tự điều khiển event, state và mapping | Cấu trúc phức tạp, cần logic streaming đặc biệt hoặc không có fragment root ổn định |
| JAXB unmarshal toàn document | Map cả document thành object graph | File vừa/nhỏ, cần xử lý document như một đơn vị |

`StaxEventItemReader` là lựa chọn tốt khi XML có ranh giới record rõ ràng. Nếu mỗi record được phân tán ở nhiều vị trí trong document hoặc cần tổng hợp state qua nhiều nhánh event, custom reader có thể phù hợp hơn.

## 20. Kiểm thử StaxEventItemReader

Nên kiểm thử reader với các XML fixture đại diện cho schema thực tế:

1. XML hợp lệ với một fragment và nhiều fragment.
2. XML không có fragment root được cấu hình.
3. XML có namespace mặc định và namespace prefix.
4. XML có element con lồng nhau hoặc tên trùng ở cấp khác.
5. Giá trị thiếu, giá trị rỗng và kiểu dữ liệu không hợp lệ.
6. XML malformed ở đầu, giữa và cuối file.
7. Resource không tồn tại và resource không đọc được khi strict bật.
8. XSD validation thành công và thất bại nếu ứng dụng bật validation.
9. Restart sau một số chunk đã commit với cùng file và JobParameters.
10. Thay đổi file giữa lần chạy và restart để xác nhận cơ chế phát hiện đầu vào thay đổi.
11. DTD/external entity bị từ chối theo cấu hình bảo mật parser.
12. Đo heap và throughput với file lớn, fragment lớn và chunk size dự kiến.

Ví dụ unit/integration test có thể mở reader, gọi `read()` liên tiếp và xác nhận mỗi fragment tạo đúng object. Khi test trực tiếp `ItemStreamReader`, cần gọi `open(ExecutionContext)` trước và `close()` sau; với Job integration test, Spring Batch quản lý lifecycle đó.

Test restart cần dùng JobRepository giữ metadata giữa hai lần chạy. Nếu repository hoặc ExecutionContext bị tạo mới, test không chứng minh được checkpoint có thể khôi phục.

## 21. Những nhầm lẫn thường gặp

**Cho rằng reader tạo một item cho mỗi dòng XML.** Reader tạo item cho mỗi fragment root element đã cấu hình, có thể chứa nhiều dòng text và element con.

**Cho rằng document root luôn là fragment root.** Root tài liệu thường chỉ là wrapper chứa các record. Chọn element đại diện cho một đơn vị nghiệp vụ.

**Cho rằng StAX không dùng bộ nhớ.** StAX tránh DOM toàn document nhưng vẫn cần parser buffer, object fragment và item của chunk.

**Cho rằng `strict(true)` bật XSD validation.** Strict chủ yếu kiểm tra resource; schema validation cần cấu hình riêng cho unmarshaller hoặc bước validation.

**Cho rằng JAXB mapping tự xác định fragment root.** Reader cần được cấu hình fragment root; JAXB chịu trách nhiệm map fragment đã tách.

**Cho rằng XML malformed có thể luôn skip.** Parser có thể mất đồng bộ sau lỗi cấu trúc. Chỉ skip lỗi fragment cô lập khi có thể tiếp tục an toàn.

**Cho rằng restart chỉ cần `saveState(true)`.** File, thứ tự fragment, reader name và JobParameters cũng phải ổn định.

**Cho rằng tắt DTD là tùy chọn không quan trọng.** XML không tin cậy cần parser an toàn để tránh XXE và truy cập tài nguyên ngoài ý muốn.

## 22. Cách thiết kế Job đọc XML bằng StaxEventItemReader

Hãy xác định element nào đại diện cho một record nghiệp vụ và dùng element đó làm fragment root. Tạo model JAXB/OXM phù hợp, cấu hình `Unmarshaller`, rồi khai báo reader với resource, tên ổn định và `saveState(true)`. Đưa reader vào chunk Step như một `ItemStreamReader` bình thường.

Với file thay đổi theo lần chạy, dùng `@StepScope` để inject JobParameters và giữ nguyên file/parameters qua restart. Xác định rõ namespace, kiểm tra schema nếu cần và tắt DTD/external entity cho XML không tin cậy. Chỉ skip lỗi dữ liệu cô lập khi parser vẫn có thể tiếp tục; lỗi XML malformed hoặc cấu hình mapping nên được xử lý như lỗi cần sửa.

StaxEventItemReader phù hợp với XML lớn có cấu trúc record lặp lại và ranh giới fragment rõ ràng. Kết hợp đúng streaming, unmarshalling, checkpoint và quản lý resource sẽ giúp Job đọc XML theo từng item, tiết kiệm bộ nhớ hơn cách nạp DOM toàn bộ và hỗ trợ xử lý batch có thể restart.
