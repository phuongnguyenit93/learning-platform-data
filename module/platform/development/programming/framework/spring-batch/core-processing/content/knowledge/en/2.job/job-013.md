# Distinguishing job definition from job execution

In Spring Batch, a **job definition** describes the batch process that the application can run; a **job execution** records one specific time that process is launched and executed. The two concepts are directly related but belong to two different moments and two different roles: the definition is reusable configuration, while the execution is the runtime data of each run.

For example, the application has a Job named `importOrdersJob` that reads an order file, validates the data, and writes the orders to the database. The configuration consisting of the Steps and the order in which they run is the job definition. When the application launches the Job to import the file for 15/11/2026, Spring Batch creates a JobExecution to track that run. If the run hits an error and is then restarted, the same definition can create another new JobExecution.

## 1. What is a job definition?

In Spring Batch, the term *job definition* usually refers to the `Job` object that the application has declared and configured. It describes **what the Job needs to do and how it is organized**, not the result of a single run.

A Job definition usually specifies:

- The Job name, used to identify the Job in the application and the metadata.
- The Steps that take part in the process.
- The order in which the Steps run, or the control flow among the Steps.
- Branching conditions, deciding whether to continue or end the Job when needed.
- Listeners that are called at certain points in the Job lifecycle.
- Options such as restartability or a `JobParametersIncrementer`, if configured.

For example, a Job can consist of three Steps: validating the input file, importing data, and generating a report. That is the structure of the definition. This structure does not change just because one run failed or another run completed successfully.

Spring Batch represents the definition with the `Job` abstraction. In a Spring application, the Job object is usually declared as a bean:

```java
@Bean
public Job importOrdersJob(
        JobRepository jobRepository,
        Step validateFileStep,
        Step importOrdersStep,
        Step generateReportStep) {

    return new JobBuilder("importOrdersJob", jobRepository)
            .start(validateFileStep)
            .next(importOrdersStep)
            .next(generateReportStep)
            .build();
}
```

The configuration above builds a Job named `importOrdersJob` with three Steps that run in order. When Spring creates the application context, the Job bean is configured and ready for the `JobLauncher` to use. Creating the bean does not mean the Job has started processing a specific file.

`Job` is a framework abstraction; the phrase *job definition* helps express its configuration role. You should not assume the application must create a class or a database table named `JobDefinition` to represent this concept.

## 2. What is a job execution?

`JobExecution` is a metadata object that represents **one specific execution of a JobInstance**. It is created when the Job is launched and carries information about that run, such as:

- The execution's own ID.
- The JobInstance the execution belongs to.
- The JobParameters used at launch.
- The current or final status (`BatchStatus`).
- The exit result (`ExitStatus`).
- The creation, start, end, and last-updated times.
- The ExecutionContext at the Job scope.
- The StepExecutions that arose in the run.
- The exceptions recorded during execution.

Therefore, a JobExecution answers questions such as: which run is being tracked, when did it start, has it completed, what was the result, and which Steps have run. It does not redefine the Job structure.

When launching, the application passes the Job definition and the JobParameters to the `JobLauncher`:

```java
JobParameters parameters = new JobParametersBuilder()
        .addString("businessDate", "2026-11-15", true)
        .toJobParameters();

JobExecution execution = jobLauncher.run(importOrdersJob, parameters);

log.info(
        "jobExecutionId={}, status={}, exitStatus={}",
        execution.getId(),
        execution.getStatus(),
        execution.getExitStatus()
);
```

Here, `importOrdersJob` is the configured Job definition; `execution` is the metadata of the execution initiated for this run request. The `JobLauncher` coordinates with the `JobRepository` to create and manage the execution metadata.

If the launcher runs synchronously, the call usually returns after the Job ends. If the launcher is configured to run asynchronously, the call can return while the Job is still executing. Therefore, receiving a `JobExecution` does not automatically mean its status is already `COMPLETED`.

## 3. Job definition, JobInstance, and JobExecution

To understand precisely the relationship between configuration and runs, you need to place the `JobInstance` between the two concepts above.

| Concept | Role | Question answered |
|---|---|---|
| `Job` (job definition) | Defines the process, including the Job name, Steps, and flow | What batch processes does the application have and how do they run? |
| `JobInstance` | Represents one logical business job, identified by the Job and the identifying JobParameters | Which job is being processed, for example importing orders for which date? |
| `JobExecution` | Represents one attempt to execute a JobInstance | How did this specific run start, end, and what was its result? |

You can picture the relationship as follows:

```text
Job definition: importOrdersJob
       |
       +-- JobInstance: businessDate=2026-11-15
       |       |
       |       +-- JobExecution #101: FAILED
       |       |
       |       +-- JobExecution #108: COMPLETED
       |
       +-- JobInstance: businessDate=2026-11-16
               |
               +-- JobExecution #112: COMPLETED
```

One Job definition can be used to create multiple JobInstances, for example each day processing a different data set. One JobInstance can have multiple JobExecutions if the run needs to be restarted. Each JobExecution has its own ID to distinguish each execution.

### JobParameters affect the JobInstance

A JobInstance is determined by the Job name together with the JobParameters marked as *identifying*. If an identifying parameter changes, the run request can correspond to a new JobInstance. A non-identifying parameter does not change the identity of the JobInstance.

In the order import example, `businessDate` can usually be an identifying parameter because the business date determines the data set to process. A parameter used to send notifications can be non-identifying if changing the notification recipient address does not mean a new business job.

Therefore, not every `JobLauncher.run` call creates a new JobInstance. When the Job and the identifying parameters are the same, Spring Batch finds the existing corresponding JobInstance and applies the run or restart rules for that instance.

## 4. Direct comparison of job definition and job execution

| Criterion | Job definition (`Job`) | Job execution (`JobExecution`) |
|---|---|---|
| Nature | Process configuration | Runtime metadata of one run |
| Timing | Built when the application configures the Job | Created when the Job is launched |
| Main content | Job name, Steps, flow, listeners, and options | ID, JobInstance, JobParameters, status, ExitStatus, times, context |
| Reusability | Can be used for many JobInstances and many runs | Each execution has its own JobExecution |
| Has a completion status? | Has no completion status of a run | Has `BatchStatus` and `ExitStatus` |
| Storage | Usually configured in source code and the Spring application context | Metadata managed by the JobRepository |
| Purpose | Describes the process to be performed | Tracks the actual progress and result |

The most important difference is that the definition describes **structure**, while the execution describes an **execution event**. A Job can keep the same definition across many runs, while each run has its own time, status, and result.

## 5. The lifecycle from definition to execution

The usual process can be divided into stages:

1. **Declare the Job:** the application builds the Job bean with `JobBuilder`, combining the Steps and configuring the flow.
2. **Request a run:** the application calls `JobLauncher.run(job, parameters)` with the Job definition and the JobParameters set.
3. **Create metadata:** the `JobRepository` determines the appropriate JobInstance and creates a JobExecution for the execution, if the launch rules allow it.
4. **Execute the Steps:** the framework runs the Steps belonging to the Job. Each Step execution is recorded with a StepExecution linked to the current JobExecution.
5. **Finish:** Spring Batch updates the status, ExitStatus, end time, and related metadata.

```text
Application starts up
       |
       v
Declare the Job definition (Job bean)
       |
       v
JobLauncher.run(job, parameters)
       |
       v
JobRepository determines the JobInstance
       |
       v
Create a JobExecution for the run
       |
       v
Run the Steps -> create StepExecutions
       |
       v
Update BatchStatus and ExitStatus
```

The `JobRepository` manages the metadata of the JobInstance, JobExecution, StepExecution, and ExecutionContext. The metadata is usually stored in a database so that history can be tracked, restart can be supported, and the Job can be monitored after the application process ends.

The JobRepository does not store an executable copy of the entire Java Job bean. The application still has to load the configuration and provide the corresponding Job definition when running or restarting. The metadata links the run to the Job through the Job name and the related identifiers.

## 6. One definition can create many executions

Suppose `importOrdersJob` is configured once in the application. The Job processes data by day and `businessDate` is an identifying parameter.

**Case A: running for two different days.**

- The run with `businessDate=2026-11-15` creates a JobInstance for 15/11.
- The run with `businessDate=2026-11-16` creates a different JobInstance for 16/11.
- Each JobInstance has its own JobExecution.

**Case B: restarting the same day after an error.**

- The first run with `businessDate=2026-11-15` creates JobInstance ID 50 and JobExecution ID 101.
- JobExecution 101 ends with `FAILED` because the storage service was temporarily unresponsive.
- When launched again with the same Job and identifying parameters, Spring Batch can create JobExecution ID 108 on JobInstance ID 50, if the previous state and the Job configuration allow restart.
- The new run can continue based on the saved metadata and ExecutionContext.

```text
importOrdersJob (one definition)
       |
       +-- JobInstance #50 (15/11)
       |       +-- JobExecution #101: FAILED
       |       +-- JobExecution #108: COMPLETED  <- restart
       |
       +-- JobInstance #51 (16/11)
               +-- JobExecution #112: COMPLETED
```

The IDs in the diagram only illustrate the relationships. In a real application, IDs are issued by the JobRepository according to the metadata configuration.

Some common launch rules:

- If the JobInstance is already `COMPLETED` with the same identifying parameters, a rerun request is usually rejected with a `JobInstanceAlreadyCompleteException`.
- If an execution of the JobInstance is still running, a duplicate run request can encounter a `JobExecutionAlreadyRunningException`.
- If the Job does not allow restart, a restart request can fail with a `JobRestartException`.
- If you need to process a new business data set, provide a new identifying JobParameter or use a `JobParametersIncrementer` according to the Job's design.

These rules show that the Job definition does not by itself decide whether a run succeeded or failed. The status belongs to the JobExecution and the history of the JobInstance.

## 7. Reading Job definition and Job execution information in code

In code, the two kinds of objects often appear side by side but have different APIs.

For the Job definition, the application usually passes the Job bean to the JobLauncher or uses it to configure a flow:

```java
Job job = importOrdersJob;
String jobName = job.getName();
boolean restartable = job.isRestartable();
```

For the JobExecution, the application reads the run's metadata:

```java
Long executionId = execution.getId();
JobInstance instance = execution.getJobInstance();
JobParameters parameters = execution.getJobParameters();
BatchStatus status = execution.getStatus();
ExitStatus exitStatus = execution.getExitStatus();

log.info("jobName={}", instance.getJobName());
log.info("jobInstanceId={}", instance.getId());
log.info("jobExecutionId={}", executionId);
log.info("status={}, exitStatus={}", status, exitStatus);
```

The JobExecution also contains the StepExecutions of that run. You can use them to see which Steps have executed and the status of each Step:

```java
for (StepExecution stepExecution : execution.getStepExecutions()) {
    log.info(
            "stepName={}, status={}, readCount={}, writeCount={}",
            stepExecution.getStepName(),
            stepExecution.getStatus(),
            stepExecution.getReadCount(),
            stepExecution.getWriteCount()
    );
}
```

If you need to look up a saved execution by ID, `JobExplorer` provides an API for reading metadata:

```java
JobExecution savedExecution = jobExplorer.getJobExecution(executionId);

if (savedExecution != null) {
    log.info("status={}", savedExecution.getStatus());
    log.info("startTime={}", savedExecution.getStartTime());
    log.info("endTime={}", savedExecution.getEndTime());
}
```

These APIs serve different purposes: the Job bean is used to configure and launch the process; the JobExecution is used to observe a single run; the JobExplorer is used to read stored metadata.

## 8. Design mistakes from confusing the two concepts

### Storing each run's data in fields of the Job bean

A Job bean is usually managed as a shared bean in the Spring application context. If you store a single run's state in a mutable field of the Job bean, other runs can read or write that data by mistake, especially when the application allows multiple JobInstances to run concurrently.

Pass the input data through JobParameters and store the state needed for restart in the ExecutionContext at the appropriate scope. Do not use fields of the definition as a container for each execution's progress.

### Believing the Job definition has a `COMPLETED` status

One definition can be used in a successful run and a failed run. `COMPLETED` or `FAILED` is a status of the JobExecution, not a fixed status of the Job bean. When displaying results, you need to query the specific execution.

### Creating a new Job definition for each run

Normally, the application declares a stable Job bean and passes the changing data through JobParameters. Creating a Job definition dynamically for each day or each file usually makes the configuration hard to manage and is unnecessary if the processing flow is still the same.

### Treating a JobExecution as a copy of the Job definition

A JobExecution does not contain an independent definition that describes the entire process structure by itself. It references the JobInstance and stores the run's metadata. On restart, the application needs the corresponding Job definition for Spring Batch to continue executing.

### Using the JobExecution ID to identify business work

The execution ID changes between restarts. If you need to group the runs of the same logical job, use the JobInstance. If you need to trace one specific run, use the JobExecution ID.

## 9. How to choose the right object when working

When writing configuration or changing the order of Steps, work with the Job definition (`Job`, `JobBuilder`, `Step`). When launching, pass the Job definition and the JobParameters to the `JobLauncher`. When logging, tracking status, investigating errors, or viewing the result of one run, use the JobExecution. When you need to group multiple restarts into the same logical job, use the JobInstance.

Remember the three corresponding questions: **how the process is defined** belongs to the Job; **which business job is being processed** belongs to the JobInstance; and **what the result of the specific run is** belongs to the JobExecution. Separating these three roles lets the Job configuration be reusable while the runtime metadata accurately reflects each execution.
