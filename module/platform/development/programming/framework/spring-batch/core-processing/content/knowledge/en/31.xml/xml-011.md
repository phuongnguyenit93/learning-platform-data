# XML Encoding

In Spring Batch, XML is commonly used as a data exchange format between systems. When reading or writing XML, encoding determines how Unicode characters are converted into bytes and back. A file can have valid XML structure yet still fail to read properly if bytes are decoded using the wrong charset, or if the encoding declared in the XML mismatches the file's actual encoding.

When processing XML in batch jobs, distinguish three layers:

1. **Characters in Java data:** Java strings are represented in Unicode.
2. **Byte encoding:** the charset used when reading bytes from a file or writing bytes to a file, such as UTF-8 or UTF-16.
3. **XML declaration:** the encoding attribute in the document's opening declaration, describing the encoding used for the XML entity's bytes.

All three layers must align. If a writer produces UTF-8 bytes while declaring ISO-8859-1 encoding, the consumer may decode characters wrongly or reject the document. If a reader decodes bytes with the wrong charset before handing characters to the parser, the XML declaration cannot restore characters that have already been corrupted.

## 1. What is XML encoding?

XML is a text format. The logical content of XML is a sequence of characters, whereas a file on disk is a sequence of bytes. Encoding defines how to convert between those two representations.

Example:

~~~xml
<customer>
    <name>Nguyễn Thị An</name>
    <city>Hồ Chí Minh</city>
</customer>
~~~

The content contains Vietnamese diacritical characters. In UTF-8, each character is encoded as one or more bytes. In UTF-16, characters are usually encoded using one or two 16-bit code units. The logical XML character content is identical, yet the byte sequences of the two files differ.

Encoding does not change XML structure such as elements, attributes, namespaces, or node ordering. It only specifies how characters are represented as bytes. XML escaping rules such as `&amp;`, `&lt;`, and `&quot;` are syntax/serialization concerns, not charset concerns.

## 2. XML declaration and the encoding attribute

An XML document normally begins with an XML declaration:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order id="ORD-1001">
        <customerName>Nguyễn Thị An</customerName>
    </order>
</orders>
~~~

The encoding attribute tells the XML processor which charset encodes the document's bytes. The XML declaration may include version, encoding, and standalone declarations; encoding is normally written explicitly so systems exchanging files interpret them consistently.

Points to remember:

- The XML declaration must sit at the very start of the document, before the root element.
- The encoding name must match the actual byte encoding.
- UTF-8 is a common and widely supported choice.
- Without an XML declaration, the XML processor relies on XML encoding detection rules and leading bytes; never rely on the host machine's default charset.
- The XML declaration is not a byte-conversion mechanism. It only describes the document's encoding.

Do not insert logs or other characters before the XML declaration when the writer emits a declaration at the top of the file. Some parsers permit a BOM before the declaration per encoding rules; stray garbage data before the declaration can invalidate the document.

## 3. UTF-8, UTF-16, and other charsets

Commonly encountered encodings:

| Encoding | Characteristics | When used |
|---|---|---|
| UTF-8 | Byte-oriented Unicode encoding, ASCII-compatible for basic characters | Good default choice for most new XML files |
| UTF-16 | Unicode encoding in 16-bit code units, may require byte order identification | When the integration contract mandates UTF-16 |
| ISO-8859-1 | Single-byte charset for Western European characters | Only when required by legacy systems |
| Windows-1252 | Single-byte charset common on some legacy Windows systems | When source/target files have an explicit contract |

UTF-8 is generally the preferred choice because it supports Vietnamese, other languages, and most modern systems. Never pick ISO-8859-1 just because a sample file looks ASCII; Vietnamese characters will not be represented fully.

If an external system mandates a legacy charset, document that charset in the integration contract, verify which characters are representable, and specify how out-of-repertoire characters are handled. Never silently replace unsupported characters with question marks, as data loses information while the job still reports completion.

## 4. Byte Order Mark (BOM)

A BOM is a leading byte sequence in a file that helps identify encoding or byte order. For UTF-8, a BOM is optional; for UTF-16, a BOM is commonly used to distinguish big-endian and little-endian when encoding is declared generically as UTF-16.

Examples:

- UTF-8 BOM: `EF BB BF`.
- UTF-16 big-endian BOM: `FE FF`.
- UTF-16 little-endian BOM: `FF FE`.

Not every system expects a UTF-8 BOM. Some parsers handle it fine, whereas some legacy systems or custom line-reading code may treat the BOM as the first character of an element name or header. When integrating, agree explicitly whether files carry a BOM.

For XML parsers reading a byte stream directly, the parser can typically use both BOM and XML declaration to detect encoding per XML rules. Do not strip the BOM blindly before understanding the parser and data source. If the application converts bytes to a String manually before parsing, handle the BOM properly so no U+FEFF character remains at the start of the text.

## 5. Choosing encoding when reading XML with StAX

Spring Batch provides `StaxEventItemReader<T>` to read XML fragments into items. The reader uses StAX to read the XML stream and a Spring OXM `Unmarshaller` to convert fragments into objects.

Configuration example:

~~~java
@Bean
@StepScope
StaxEventItemReader<Order> orderXmlReader(
        @Value("#{jobParameters['inputFile']}") Resource inputFile,
        Unmarshaller orderUnmarshaller) {

    return new StaxEventItemReaderBuilder<Order>()
            .name("orderXmlReader")
            .resource(inputFile)
            .addFragmentRootElements("order")
            .unmarshaller(orderUnmarshaller)
            .saveState(true)
            .build();
}
~~~

When the reader accepts a Resource and the parser reads from a byte stream, the StAX/XML processor can determine encoding from the BOM and XML declaration. This is the proper way for the parser to handle the encoding declared in the file.

Do not read the file into a String using the default charset and then create a character Reader without knowing the source byte encoding. Once the parser receives only a character stream, byte decoding has already happened; the parser loses the ability to decide how the original bytes should be decoded.

If the source contract fixes UTF-8, you can validate bytes or configure the reading layer appropriately to catch misencoded files. What matters is having a single place responsible for decoding bytes, using the right charset.

## 6. XML declaration cannot fix a misdecoded charset

Suppose a file was written as UTF-8, yet the application reads bytes using Windows-1252 to construct a String. The bytes of Vietnamese characters have already been mapped to wrong characters. If you then pass that String to an XML parser, the parser only sees the decoded character string; `encoding=UTF-8` inside the string cannot reconstruct the original bytes.

Pattern to avoid:

~~~java
String xml = new String(
        Files.readAllBytes(path), Charset.defaultCharset());
XMLStreamReader parser =
        XMLInputFactory.newFactory().createXMLStreamReader(
                new StringReader(xml));
~~~

When reading a file whose encoding is governed by the XML declaration, open an InputStream and let the XML parser read bytes:

~~~java
try (InputStream input = Files.newInputStream(path)) {
    XMLStreamReader parser =
            XMLInputFactory.newFactory().createXMLStreamReader(input);
    // Read XML events or pass to an appropriate processing component.
}
~~~

If the source is not a standard XML byte stream and a system supplies a Reader instead, the responsibility for picking the charset lies with whoever creates that Reader. Know the exact charset of the bytes before converting them to characters.

## 7. Configuring encoding when writing XML in Spring Batch

Spring Batch provides `StaxEventItemWriter<T>` to marshal items into XML fragments and write them to an XML file. Output encoding must be configured consistently with the XML declaration.

Example:

~~~java
@Bean
StaxEventItemWriter<Order> orderXmlWriter(
        Marshaller orderMarshaller,
        Resource outputResource) {

    return new StaxEventItemWriterBuilder<Order>()
            .name("orderXmlWriter")
            .resource(outputResource)
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .encoding("UTF-8")
            .overwriteOutput(true)
            .build();
}
~~~

`encoding("UTF-8")` configures the charset used when the writer produces bytes. The writer can also emit a matching XML declaration per configuration. Verify actual output by inspecting bytes and re-parsing the file; do not merely look at editor display, because editors may guess charsets.

When using `Jaxb2Marshaller`, you can configure the JAXB encoding property where appropriate:

~~~java
@Bean
Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Order.class);
    marshaller.setMarshallerProperties(Map.of(
            Marshaller.JAXB_ENCODING, "UTF-8",
            Marshaller.JAXB_FORMATTED_OUTPUT, Boolean.TRUE));
    return marshaller;
}
~~~

In a Spring Batch pipeline, the writer/output stream encoding determines the written bytes. Marshaller configuration must stay aligned with the writer. Never let one layer declare UTF-8 in XML while another layer writes bytes in a different charset.

## 8. XML escaping is distinct from encoding

Special characters in XML must be properly escaped in text nodes or attributes:

| Data character | Representation in XML |
|---|---|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | Can be written literally in most contexts; `&gt;` is often used for clarity |
| `"` | `&quot;` inside double-quoted attributes |
| `'` | `&apos;` inside single-quoted attributes |

For example, the company name A&B Logistics is serialized as:

~~~xml
<company>A&amp;B Logistics</company>
~~~

This is escaping to keep the XML well-formed. UTF-8 encoding then converts XML characters (including `&` and Vietnamese characters) into bytes. Do not manually replace `&` with `&amp;` before passing objects to JAXB when the marshaller already handles escaping; doing so causes double escaping into `&amp;amp;`.

Likewise, do not convert every Unicode character into a numeric character reference just because the file uses UTF-8. The serializer can emit valid Unicode characters directly under the chosen encoding.

## 9. XML character validity and illegal characters

Just because an encoding can represent a character does not mean that character is valid in XML. XML 1.0 restricts the set of characters allowed inside a document. Some control characters are forbidden even though UTF-8 can encode them.

For example, a NUL character or certain control characters from source data can cause serializers/parsers to throw errors. Numeric character references do not make a forbidden character legal either.

When source data contains illegal characters:

- Identify which upstream source introduced the character.
- Decide explicitly whether to reject the record, sanitize per business rules, or fail the batch.
- Never silently strip characters if doing so alters identifiers or business meaning.
- Log the source ID and data position for investigation.

A separate pre-marshal validation step can detect code points illegal under your system's XML version.

## 10. JAXB configuration and Unicode data types

Java Strings store text as Unicode. JAXB maps String properties to XML text nodes or attributes. Encoding is applied only when the marshaller writes to a byte stream or writer.

Model example:

~~~java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {

    @XmlAttribute
    private String id;

    @XmlElement
    private String customerName;

    @XmlElement
    private BigDecimal amount;

    public Order() {
    }

    // constructors/accessors omitted
}
~~~

When marshalling an object whose customerName is Nguyễn Thị An, JAXB produces XML events/text with Unicode characters. The StAX writer or output stream then encodes them into bytes according to the configured charset.

Do not convert Strings to byte arrays inside the processor. Doing so mixes business responsibilities with I/O and easily introduces double encoding. Keep data in String/Java types until the serialization layer.

## 11. Encoding of XML fragments and document root

`StaxEventItemReader` normally reads fragments by root element name. Fragments are part of a single XML document sharing a common encoding. Do not assume each fragment has its own XML declaration or separate encoding.

Document example:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order id="ORD-1001">
        <customerName>Nguyễn Thị An</customerName>
    </order>
    <order id="ORD-1002">
        <customerName>Trần Minh Khoa</customerName>
    </order>
</orders>
~~~

The root document declares encoding once. The reader locates order fragment roots and unmarshals each fragment into an object. Encoding is handled at the document/byte-stream level, not configured per item.

When a writer builds a document with root orders, each item marshals into an order fragment inside that root. The XML declaration belongs to the output document; item fragments should never emit their own standalone XML declarations.

## 12. Namespaces are not encoding

XML namespaces and character encoding are two independent concepts:

- Namespaces qualify element/attribute names by URI.
- Encoding defines how document characters are represented as bytes.

Example:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders xmlns="urn:example:orders:v1">
    <order id="ORD-1001">
        <customerName>Nguyễn Thị An</customerName>
    </order>
</orders>
~~~

The default namespace urn:example:orders:v1 has nothing to do with the file using UTF-8. When configuring StaxEventItemReader, specify the fragment root with the proper QName/namespace per API and actual configuration; never try changing encoding to fix missing-element errors caused by a wrong namespace.

If the parser reads the XML yet finds no fragments, check local name, namespace URI, and prefix mapping. If the parser reports byte/character errors or garbled text, check encoding.

## 13. Handling XML from legacy systems with legacy charsets

In real integrations, XML files may come from legacy systems using encodings like Windows-1252 or ISO-8859-1. Handle them per contract:

1. Confirm the actual byte encoding with the file provider, not merely by the .xml extension.
2. Check whether the XML declaration states the right encoding.
3. Check for a BOM if present.
4. Read the byte stream with an XML parser that supports that encoding.
5. After unmarshalling, keep data in Java Strings/Unicode.
6. When writing output, choose encoding per the receiving system's contract; prefer UTF-8 if both parties agree.

If converting from a legacy charset to UTF-8, perform conversion at the I/O boundary: decode source bytes using the true source charset, then re-encode as UTF-8 on output. Never change the encoding label in the XML declaration without converting the bytes.

## 14. Machine default charset and mojibake errors

Never use the OS/JVM default charset for integration data. The exact same file can be decoded differently across a developer laptop, a Linux container, and a Windows server if code relies on the default charset.

Examples to avoid:

~~~java
new InputStreamReader(inputStream);
new OutputStreamWriter(outputStream);
~~~

Those constructors may use the default charset. Specify it explicitly:

~~~java
new InputStreamReader(inputStream, StandardCharsets.UTF_8);
new OutputStreamWriter(outputStream, StandardCharsets.UTF_8);
~~~

For XML, it is best to let the parser read the byte stream directly so it honors the BOM/XML declaration. If you must create a Reader/Writer yourself, specify the charset explicitly and ensure the XML declaration aligns with that conversion.

Mojibake is garbled text caused by decoding bytes with the wrong charset. For instance, Vietnamese data may show up as strange character sequences. Never work around it by string-replacing broken characters; fix the initial decoding boundary and inspect raw source bytes.

## 15. Handling encoding errors in a batch step

Encoding errors can manifest in several ways:

| Symptom | Possible cause | How to investigate |
|---|---|---|
| Parser reports malformed byte/invalid encoding | Bytes invalid for declared charset | Inspect input bytes, BOM, and XML declaration |
| Vietnamese becomes garbled text while XML parses | Bytes were decoded using the wrong charset | Check charset at the byte-reading boundary |
| Parser cannot find root/fragment | Garbage bytes added before XML declaration; or wrong namespace | Check leading file bytes, prolog, and QName |
| Writer outputs parseable file with wrong text | Byte encoding mismatches declaration or consumer uses different charset | Inspect output bytes and encoding declaration |
| Invalid XML character error | Data contains code points disallowed by XML version | Inspect code points and data policy |
| Error occurs only in production | Differences in source files, default charset, driver, or parser implementation | Compare charsets and runtime configuration |

Do not configure skip for all XML/encoding errors. If the whole file uses the wrong charset or is corrupted, skipping fragment by fragment can produce incomplete output. Usually fail fast and move the file to reject/quarantine for source correction.

If an error affects only a single record and business rules permit skipping, use a bounded skip policy while capturing fragment/source location. Distinguish document-wide failures from single-item data errors.

## 16. Enforcing strict decoding policies

When manually decoding bytes with Java NIO, configure CharsetDecoder to report errors instead of silently substituting bad bytes:

~~~java
CharsetDecoder decoder = StandardCharsets.UTF_8.newDecoder()
        .onMalformedInput(CodingErrorAction.REPORT)
        .onUnmappableCharacter(CodingErrorAction.REPORT);

try (Reader reader = new InputStreamReader(inputStream, decoder)) {
    // Read strictly decoded characters.
}
~~~

This is useful when the application has a fixed encoding contract and wants to catch invalid bytes. If the XML declaration can pick encoding dynamically, do not hard-code a UTF-8 decoder before reading the declaration; pass a byte stream to the XML parser so it runs autodetection rules, or detect encoding per source contract first.

Never use CodingErrorAction.REPLACE on critical business data if character substitution could alter names, codes, or identifiers. If substitution is required by business rules, record the count and origin of replacements.

## 17. Writing XML safely and finalizing files

In batch jobs, output XML files are usually written across multiple chunks. The writer must manage root elements, header/declaration, fragments, and footers per lifecycle. Never write an XML declaration inside individual items.

A safe operational procedure:

- Write the file to a staging location keyed by batch ID.
- Configure output encoding explicitly, usually UTF-8.
- Ensure the writer closes the document and writes the footer when the step finishes normally.
- Mark output ready only after the job completes and reconciliation succeeds.
- If the job fails, prevent downstream from reading incomplete files.
- On restart, use the writer's state mechanism with the same resource/configuration to resume cleanly; verify append/overwrite behavior per configuration.

With StaxEventItemWriter, check root tag, encoding, overwrite, header/footer callbacks, and state saving for your Spring Batch version. Never modify an XML file currently open by the writer from another process.

## 18. Testing XML encoding

Merely testing that XML parses is not enough. Verify byte encoding and Unicode content after a round-trip.

Cases to test:

1. UTF-8 without BOM: read files with UTF-8 XML declaration and Vietnamese characters.
2. UTF-8 with BOM: verify the parser handles it per integration requirements.
3. UTF-16: verify BOM, byte order, and XML declaration.
4. Legacy charsets: read files using the exact contracted charset.
5. Declaration mismatch: byte encoding differs from declaration; verify errors are detected or rejected.
6. Multilingual Unicode: Vietnamese, CJK characters, and valid supplementary characters.
7. XML escaping: names with ampersands, angle brackets, or quotes marshal/unmarshal properly.
8. Invalid XML characters: verify records/files follow policy without silently dropping characters.
9. Writer/reader round-trip: marshal objects to a file, inspect XML declaration, re-parse, and compare values.
10. Runtime consistency: run tests in environments with different default charsets to ensure zero reliance on defaults.

Example checking output bytes:

~~~java
byte[] bytes = Files.readAllBytes(outputPath);
String prefix = new String(
        bytes,
        0,
        Math.min(bytes.length, 100),
        StandardCharsets.UTF_8);

assertTrue(prefix.contains("encoding=\"UTF-8\""));
~~~

The snippet above illustrates reading the prefix when output is guaranteed UTF-8; it does not replace an XML parser. With a BOM, the decoded prefix may begin with U+FEFF. A thorough test should parse the byte stream with an XML parser and check objects after unmarshalling.

Conceptual round-trip example:

~~~java
Order original = new Order("ORD-1001", "Nguyễn Thị An");

// Use StaxEventItemWriter or JAXB marshaller to write UTF-8.
writeOrderXml(original, outputPath, StandardCharsets.UTF_8);

try (InputStream input = Files.newInputStream(outputPath)) {
    Order restored = readOrderXml(input);
    assertEquals(original.getCustomerName(), restored.getCustomerName());
}
~~~

writeOrderXml and readOrderXml represent your application's writer/reader configurations. In integration tests, run the real step/job to verify lifecycle, header/footer, checkpoints, and encoding working together.

## 19. Security and untrusted XML data

Encoding does not replace XML security controls. When reading XML from untrusted sources, configure the parser to block dangerous features like external entity resolution (XXE), local file access, or unintended network access.

With StAX, configure XMLInputFactory to disable DTDs and external entities if your application does not need them. Property names and support vary across parser implementations, so confirm with tests against your actual parser implementation.

Never enable external entities just to work around encoding or namespace errors. Encoding and parser security are independent settings, though both belong at the XML reading boundary.

## 20. Common mistakes

**Changing only the XML declaration without converting bytes.** Declaring UTF-8 does not turn ISO-8859-1 bytes into UTF-8. Decode with the source charset and re-encode with the target charset.

**Using the machine default charset.** Results can differ across environments. Specify charsets explicitly or let the XML parser read the byte stream per XML rules.

**Reading into a String before passing the file to the parser.** Once misdecoded initially, the XML declaration cannot fix a corrupted string. Prefer passing an InputStream to the XML parser.

**Ignoring the BOM.** A BOM can break older parsers or custom line-reading code. Clarify the BOM contract and test both with and without a BOM.

**Confusing escaping with encoding.** &amp; addresses XML syntax; UTF-8/UTF-16 address byte representation. Let the marshaller escape once properly.

**Using legacy charsets for broad Unicode data.** ISO-8859-1 cannot represent full Vietnamese text. Pick UTF-8 or a compatible Unicode contract.

**Skipping encoding errors as per-record errors.** A misencoded file can corrupt the entire output. Separate document errors from single-fragment errors.

**Not inspecting output bytes.** Editors may guess charsets. Check raw bytes, XML declarations, and round-trip parsing.

**Confusing namespaces with encoding.** Namespace URIs do not determine charsets. Investigate QNames when fragments are not matched.

**Assuming UTF-8 allows every character in XML.** Certain control characters are invalid in XML 1.0 even though UTF-8 can encode them.

## 21. Workflow for implementing encoding in XML batches

When integrating an XML file, determine in order:

1. Lock down the charset per source/target contract; prefer UTF-8 when both sides agree.
2. Check whether the XML declaration and BOM match the actual bytes.
3. Let the StAX/XML parser read an InputStream when encoding autodetection from bytes is needed.
4. When decoding manually, use a verified charset and avoid default charsets.
5. Configure StaxEventItemReader with the unmarshaller for the right fragment root.
6. Configure StaxEventItemWriter encoding consistently with the marshaller and XML declaration.
7. Separate whole-file parse errors, encoding errors, and single-fragment data errors.
8. Define reject/skip/fail policies; never silently substitute critical characters.
9. Write outputs to staging and publish only after the writer closes the file, the job completes, and reconciliation passes.
10. Test bytes, BOM, declarations, Unicode round-trips, illegal XML characters, and runtime environments.

## Conclusion

XML encoding defines how Unicode characters map to bytes and back. The XML declaration describes the byte stream's encoding; it does not convert data itself. When reading XML, prefer passing an InputStream directly to the StAX parser so it handles BOMs and declarations. When writing, configure encoding explicitly on the writer and keep the XML declaration, marshaller, and output bytes consistent.

UTF-8 is generally the best choice for new integrations. For legacy systems, verify the actual charset and convert at the I/O boundary. Keep XML escaping separate from encoding, validate legal characters for your XML version, and never rely on the host machine's default charset. In Spring Batch, configure readers/writers carefully, distinguish file-wide errors from per-record errors, and run round-trip tests on real bytes to prevent Vietnamese data from being corrupted or output XML from becoming unreadable to downstream systems.
