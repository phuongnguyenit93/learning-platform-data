# Optimistic Locking

When Spring Batch processes JPA data, a record may be updated concurrently by another Job or an online application. If two transactions read the same version and overwrite each other, the later transaction risks losing the earlier transaction's changes. **Optimistic locking** detects such conflicts at update time using an entity version.

In JPA, optimistic locking is typically declared with `@Version`. The provider includes the current version value in the update predicate and succeeds only if the database version still equals the version read by the transaction. If another transaction has already updated the record, the version no longer matches and JPA raises an optimistic lock error. Spring Batch receives this error across the writer/transaction boundary and applies the Step's rollback, retry, skip, or failure policy.

Optimistic locking works well when conflicts are infrequent and you want to avoid holding row locks throughout processing. However, retrying only helps when the next attempt reloads fresh state and recomputes the operation. Resubmitting the exact same detached entity with the stale version usually repeats the same conflict.

## 1. The lost update problem

Suppose an order has status `PENDING` and amount `100`. Both transactions read that record:

```text
Transaction A                         Transaction B
-------------                         -------------
Read order version 5                  Read order version 5
Set status = APPROVED                 Set amount = 120
Write to database                     Write to database
Commit                                Commit later
```

Without conflict detection, the later write can overwrite using stale data and lose the earlier transaction's change. This is a lost update.

Optimistic locking adds a version check to the write:

```text
Transaction A                         Transaction B
-------------                         -------------
Read version 5                        Read version 5
UPDATE ... WHERE version = 5
Write succeeds, version becomes 6
Commit
                                      UPDATE ... WHERE version = 5
                                      No row matches version 5
                                      Optimistic lock exception
```

Transaction B is notified that the data changed since it was read. The application can roll back and decide to reload, merge, or reject the change according to business rules.

## 2. How @Version works

JPA defines optimistic versioning via a property annotated with `@Version`. The provider manages this value throughout the entity lifecycle.

Example entity:

```java
@Entity
@Table(name = "orders")
public class OrderEntity {

    @Id
    private Long id;

    @Version
    private Long version;

    @Column(nullable = false)
    private String status;

    @Column(nullable = false, precision = 19, scale = 2)
    private BigDecimal amount;

    protected OrderEntity() {
    }

    public void approve() {
        this.status = "APPROVED";
    }

    public void changeAmount(BigDecimal amount) {
        this.amount = amount;
    }

    public Long getId() {
        return id;
    }

    public Long getVersion() {
        return version;
    }
}
```

When the entity is persisted for the first time, JPA initializes the version. On update, the provider checks the old version and increments it upon a successful write. Application code should not manually increment the version in normal entity code or assign arbitrary version numbers to managed entities.

Supported version types depend on the specification/provider version; `Long` is a common choice. Avoid using a regular field like `updatedAt` instead of `@Version` when standard JPA optimistic locking is the goal.

## 3. Version column in the database

The table needs a column matching the version attribute:

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    version BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    amount DECIMAL(19, 2) NOT NULL
);
```

The column name can be customized with `@Column(name = "row_version")`. Schema migrations must be applied before the application uses an entity with `@Version`.

Exact SQL is generated by the JPA provider, though the logic is typically equivalent to:

```sql
UPDATE orders
SET status = ?, amount = ?, version = ?
WHERE id = ? AND version = ?;
```

The `WHERE version = ?` predicate is the core mechanism. If zero rows are updated because the version changed or the row was deleted, the provider detects the unexpected update count and throws an optimistic lock exception.

Do not write manual SQL updating a `@Version` entity without the version condition. Any native SQL or bulk update must check and increment the version itself.

## 4. When does an optimistic lock exception surface?

Conflicts are normally detected when JPA synchronizes the persistence context with the database. This happens on `flush()` or at transaction commit, not necessarily right when a setter runs.

Example:

```java
@Transactional
public void approveOrder(Long orderId) {
    OrderEntity order = entityManager.find(OrderEntity.class, orderId);
    order.approve();
    // SQL update may execute during flush/commit.
}
```

In this method, `order.approve()` only mutates state in the persistence context. At flush/commit, the provider executes the version-checked update. Consequently, the error can appear at method exit or at Spring Batch's chunk transaction boundary.

If you need errors to surface inside `write`, you can flush explicitly after merge/persist. Even then, flush does not commit the transaction; commit and rollback remain managed by the Step.

Common exceptions include `jakarta.persistence.OptimisticLockException` at the JPA layer and Spring-translated exceptions such as `OptimisticLockingFailureException` or specific subclasses in Spring Data/JPA integration. Observe the actual exception in stack traces to configure retries accurately.

## 5. JPA transactions in Spring Batch

A chunk-oriented Step executes its reader, processor, and writer in chunk cycles. When the writer uses JPA, entity operations must join the Step's configured transaction, typically via a `JpaTransactionManager` bound to the matching `EntityManagerFactory`.

```java
@Bean
PlatformTransactionManager transactionManager(
        EntityManagerFactory entityManagerFactory) {
    return new JpaTransactionManager(entityManagerFactory);
}
```

Example Step:

```java
@Bean
Step approveOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<OrderCommand> reader,
        ItemProcessor<OrderCommand, OrderEntity> processor,
        ItemWriter<OrderEntity> writer) {

    return new StepBuilder("approveOrdersStep", jobRepository)
            .<OrderCommand, OrderEntity>chunk(100, transactionManager)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .build();
}
```

When an optimistic lock exception fails a chunk, the chunk transaction rolls back as configured. Uncommitted database operations in that transaction are undone. The Step can then retry, skip, or fail according to its fault-tolerance policy.

Ensure the reader, writer, and repositories use the right `EntityManagerFactory`/transaction manager. If part of the work runs on a different datasource or transaction, chunk rollback does not automatically cover that resource.

## 6. Using JpaItemWriter

When output is a JPA entity, use the built-in `JpaItemWriter` instead of hand-rolling an `EntityManager` loop:

```java
@Bean
JpaItemWriter<OrderEntity> orderJpaWriter(
        EntityManagerFactory entityManagerFactory) {

    return new JpaItemWriterBuilder<OrderEntity>()
            .entityManagerFactory(entityManagerFactory)
            .build();
}
```

`JpaItemWriter` accepts the chunk, writes entities via JPA, and flushes per the writer lifecycle. For existing entities, the writer defaults to `merge`. If an entity carries an old version, a conflict can surface during merge/flush.

The built-in writer manages JPA lifecycles per Spring Batch conventions, but it does not eliminate optimistic lock conflicts. `@Version` still detects when another transaction modified the entity before the write.

Never share a single mutable entity instance across threads. Likewise, never store a singleton `EntityManager` in a field shared across executions; `EntityManager` is not thread-safe.

## 7. Reading entities and updating via JPA

A common pattern is reading entities with `JpaPagingItemReader`, then transforming or updating them in the processor/writer.

Example reader:

```java
@Bean
@StepScope
JpaPagingItemReader<OrderEntity> orderReader(
        EntityManagerFactory entityManagerFactory,
        @Value("#{jobParameters['tenant.id']}") Long tenantId) {

    return new JpaPagingItemReaderBuilder<OrderEntity>()
            .name("orderReader")
            .entityManagerFactory(entityManagerFactory)
            .queryString("""
                    select o
                    from OrderEntity o
                    where o.tenantId = :tenantId
                      and o.status = 'PENDING'
                    order by o.id
                    """)
            .parameterValues(Map.of("tenantId", tenantId))
            .pageSize(100)
            .saveState(true)
            .build();
}
```

An entity read at a given moment captures a specific version. If another application updates the entity before the writer writes, the in-memory object's version is stale. When JPA synchronizes changes, optimistic locking catches the conflict.

This is especially important for long-running Jobs or jobs reading many pages: the gap between read and write can be long, increasing the probability of stale entities.

## 8. Why retrying the same stale entity rarely resolves conflicts

Suppose the reader produces an `OrderEntity` with `version = 5`. Another application updates the row and bumps the database version to 6. The writer attempts to write the old entity and hits an optimistic lock exception.

If the retry merely resubmits the exact same object with version 5, the update predicate still fails to match. Repeating the same stale data will not make the conflict disappear.

```text
Attempt 1:
  Entity in item: version 5
  Database:       version 6
  => Conflict

Attempt 2 (still using old item):
  Entity in item: version 5
  Database:       version 6
  => Conflict again
```

Retrying helps when the new attempt can read fresh state, recompute, and build an update against the current version. Without a reload/recompute step, fail or route the item to conflict handling rather than retrying fruitlessly.

## 9. Reloading and reapplying business commands

A more resilient design emits commands/IDs from the reader instead of carrying full detached entities through the pipeline. During processing, a service loads the latest entity inside a transaction, validates state, and applies the command.

Example:

```java
public record ApproveOrderCommand(Long orderId) {
}

@Service
public class OrderApprovalService {

    private final OrderRepository repository;

    public OrderApprovalService(OrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void approve(ApproveOrderCommand command) {
        OrderEntity current = repository.findById(command.orderId())
                .orElseThrow(() -> new OrderNotFoundException(
                        command.orderId()));

        if ("APPROVED".equals(current.getStatus())) {
            return; // Idempotent for an already completed command.
        }

        if (!"PENDING".equals(current.getStatus())) {
            throw new InvalidOrderStateException(command.orderId());
        }

        current.approve();
    }
}
```

The service loads the current entity within the transaction and mutates the managed entity. JPA checks the version at flush/commit. If a conflict happens right at write time, the transaction fails; a new attempt reloads the entity and re-evaluates business preconditions.

If a Job passes previously read detached entities into `JpaItemWriter`, that alone does not make the writer reload and reapply commands. Explicitly decide whether items are entity snapshots or commands, and where fresh state is loaded.

## 10. Retrying optimistic locking in a Step

Spring Batch fault tolerance can retry specific exceptions when the writer or processor fails:

```java
return new StepBuilder("approveOrdersStep", jobRepository)
        .<ApproveOrderCommand, OrderEntity>chunk(100, transactionManager)
        .reader(orderCommandReader)
        .processor(orderReloadingProcessor)
        .writer(orderJpaWriter)
        .faultTolerant()
        .retry(OptimisticLockingFailureException.class)
        .retry(OptimisticLockException.class)
        .retryLimit(3)
        .build();
```

In this example, both exceptions cover Spring Data/Spring translation and direct JPA exceptions. Not every application needs both; configure the exact exception types thrown by your stack after transaction rollback/translation.

The retry limit must be finite. When multiple Jobs continuously update the same row, excessive retries only add load and prolong contention. You may need backoff, lower concurrency, data partitioning, or a different locking strategy.

Crucially, a retry policy does not magically refresh a stale entity into a fresh one. The processor/service must reload and reapply the command when business rules allow. Write integration tests proving retries actually use fresh state rather than replaying the same payload.

## 11. Retry, rollback, and where exceptions occur

An optimistic lock exception can be thrown when:

- Calling `EntityManager.flush()` in the writer.
- A Spring Data repository flushes.
- The transaction manager commits the chunk and JPA auto-flushes before commit.
- A merge/persist operation detects a version mismatch.

If the exception surfaces only at commit, `write()` may have already returned normally before the transaction fails. Therefore, do not wrap a single statement in the writer with a `try/catch` assuming you caught all optimistic lock failures.

When you want errors to appear within the writer scope for cleaner error classification, flush explicitly after JPA operations. Flushing still occurs inside the chunk transaction and does not replace commit.

Never catch `OptimisticLockException` and keep processing further items in the same rollback-only transaction. Let the transaction fail and let Spring Batch orchestrate retry/skip/fail at the proper boundary.

## 12. Skip conflict vs. retry conflict?

Not every optimistic lock conflict should be retried. The decision depends on business meaning:

| Scenario | Typically appropriate handling |
|---|---|
| Short-lived conflict where reloading and reapplying the command is safe | Finite retry with backoff and reload. |
| Another process already completed the transition, making the command redundant | Treat as idempotent success or skip per business rules. |
| Two conflicting mutations requiring human resolution | Record conflict/reject and route to manual resolution. |
| Record no longer exists | Handle via not-found policy; do not retry endlessly. |
| Constant conflicts from multiple workers owning the same row | Fix partitioning, ownership, concurrency, or switch locking strategy. |

Skip should not be used to hide arbitrary `OptimisticLockException` errors. If a conflict means output may be wrong or updates lost, skipping items can make a Job report success with missing business updates.

If you choose to skip, log enough context for reconciliation: entity ID, read version, conflict timestamp, Job/Step execution, and reason for skipping. Avoid logging sensitive payloads.

## 13. Bulk JPQL updates do not automatically enforce @Version like entity updates

An easily missed detail is that JPQL bulk updates and native SQL bypass per-entity dirty checking. They run directly against the database and do not automatically perform the optimistic version check of managed entity updates.

Bulk update example:

```java
@Modifying
@Query("""
       update OrderEntity o
       set o.status = :status
       where o.id = :id
       """)
int updateStatus(Long id, String status);
```

This query bypasses the version check the application may expect. When optimistic locking is required on a bulk update, include the expected version in the predicate and increment it explicitly:

```java
@Modifying
@Query("""
       update OrderEntity o
       set o.status = :status,
           o.version = o.version + 1
       where o.id = :id
         and o.version = :expectedVersion
       """)
int updateStatusIfVersionMatches(
        Long id,
        Long expectedVersion,
        String status);
```

After executing, inspect the updated row count:

```java
int updated = repository.updateStatusIfVersionMatches(
        command.orderId(), command.expectedVersion(), "APPROVED");

if (updated == 0) {
    throw new OptimisticLockingFailureException(
            "Order changed before update: " + command.orderId());
}
```

Bulk updates can also leave an active persistence context out of sync with the database. Clear or refresh the context appropriately and avoid continuing to use stale objects after bulk operations.

## 14. Native SQL and JDBC writers

If a custom writer uses JDBC or native SQL, JPA `@Version` does not automatically protect that SQL statement. You must include the expected version in `WHERE`, increment the version, and verify the update count.

```sql
UPDATE orders
SET status = :newStatus,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
```

Java:

```java
int updated = jdbcTemplate.update(
        """
        UPDATE orders
        SET status = ?, version = version + 1
        WHERE id = ? AND version = ?
        """,
        newStatus,
        orderId,
        expectedVersion);

if (updated != 1) {
    throw new OptimisticLockingFailureException(
            "Concurrent update detected for order " + orderId);
}
```

This executes a database-level compare-and-set. If zero rows match the ID and version, the row may have been deleted or the version may have changed; if you need to distinguish the two cases, run a diagnostic query after rollback or in a new transaction.

If a JPA persistence context in the same transaction holds that entity, refresh or clear it so stale in-memory state does not overwrite the JDBC update.

## 15. @Version does not protect every business invariant

Optimistic locking protects concurrent updates to a versioned entity/row. It does not automatically solve race conditions spanning multiple rows or aggregate invariants.

For example, two transactions both check "at least one seat available" and then each inserts a booking on separate rows. Unless they update a shared entity/version, both can succeed even if total bookings exceed capacity.

Situations requiring additional mechanisms:

- Invariants spanning multiple entities or tables.
- Duplicate business key inserts.
- Concurrent check-then-insert for row nonexistence.
- Totals or limits computed across multiple rows.
- Collection relationship changes that do not update the root entity's version as expected.
- Bulk updates or native SQL that omit version checks.

Solutions may include unique constraints, aggregate versions, pessimistic locks, atomic SQL updates, serializable isolation, or redesigning data so the invariant is guarded by a single row or constraint. Never assume adding `@Version` to an entity protects every invariant.

## 16. Optimistic locking in multi-threaded Steps and partitioning

If multiple workers read and update overlapping rows, optimistic lock conflicts will occur frequently. `@Version` detects conflicts, but it does not distribute ownership across workers.

A sound design typically partitions by key so each worker owns a disjoint set of rows:

```text
Manager Step
    |
    +--> Partition A: order_id 1..100000
    |
    +--> Partition B: order_id 100001..200000
    |
    +--> Partition C: order_id 200001..300000
```

When data is partitioned without overlap, the probability of two workers updating the same entity drops sharply. Still, online apps or other Jobs can modify the same rows; partitioning inside one Job does not protect against external writers.

Mitigations:

- Partition by non-overlapping business keys or ID ranges.
- Avoid letting two Steps/Jobs concurrently own the same records.
- Use claim/lease patterns or a `PROCESSING` status when ownership is needed.
- Monitor optimistic lock conflict rates per partition.
- Lower concurrency if the database or workload experiences contention.
- Use short-scoped pessimistic locking if conflicts are frequent and business rules permit.

Never share a single `EntityManager` across workers. Each transaction/thread requires a persistence context managed by the transaction manager.

## 17. Optimistic locking vs. pessimistic locking

These two strategies handle update contention differently:

| Aspect | Optimistic locking | Pessimistic locking |
|---|---|---|
| Protection mechanism | Checks version at write time | Database holds locks during transaction |
| On conflict | Detected at update/flush/commit | Other transactions may wait or be rejected |
| Cost when conflicts are rare | Usually low | Pays lock/wait overhead |
| When conflicts are high | Retries can become expensive | Can fit better if lock scope is short and controlled |
| Lock held during slow processing | No need to hold row locks across read/processing | Risks holding locks long and causing contention |
| Restart | Requires reloading fresh state/version after conflict | Requires handling transaction/lock timeouts and retries |

JPA supports lock modes such as `LockModeType.PESSIMISTIC_WRITE` when locking during read/update is needed. Do not switch to pessimistic locking merely to suppress exceptions without measuring contention and throughput impact.

For long-running Batch jobs, optimistic locking usually fits well when conflicts are rare and recoverable. If hot rows are updated constantly by multiple workers, partitioning, ownership, or strategic locking may be better.

## 18. Version and detached data

An entity read in a persistence context becomes detached once the context closes or clears. A detached entity still holds the version value captured when it was read.

When merging a detached entity, JPA synchronizes its state onto a managed entity. If the detached version is stale relative to the database, the provider can throw an optimistic lock exception. Never copy the current database version onto an old object to "fix" a conflict; doing so masks concurrent modifications and causes lost updates.

Instead:

- Pass only IDs/commands through the pipeline when possible.
- Reload the latest entity inside the processing transaction.
- Validate business state before applying the command.
- Use an explicit expected version when the caller wants to detect changes since read time.
- When merging two changes is required, write field-level merge logic instead of overwriting the newer entity with the entire stale object.

Do not treat `EntityManager.merge()` as an "unconditional overwrite." `merge` does not bypass version checks and does not automatically resolve business conflicts.

## 19. Conflicts between two Jobs or between a Job and online apps

Optimistic locking can detect conflicts between:

- Two concurrently running Spring Batch Jobs.
- A Batch Job and a REST/API application.
- Two online requests.
- A Job retry after another worker already finished updating.

All writers modifying the entity must honor the version column. If one application updates via direct SQL without incrementing the version, another JPA application may fail to detect the change as expected.

Database conventions must be consistent:

- Every out-of-band update must check/increment the version.
- Maintenance scripts must not bypass version updates without a synchronization plan.
- Version columns must not be reset during partial imports or restores.
- Services must not assign arbitrary version values.
- Bulk operations changing multiple rows must manage persistence context and version updates consistently.

## 20. Monitoring optimistic lock conflicts

An optimistic lock exception is a contention signal, not just a random technical glitch. Monitor:

- Conflict counts per Job/Step.
- Conflict counts per entity type or operation type.
- Average retry counts and retry exhaustion.
- Which partitions or workers generate conflicts.
- Conflict rate relative to total updates.
- Processing latency growth due to retries.
- Frequently conflicting business keys (in controlled logs, not as high-cardinality metric tags).

If conflicts rise, inspect Job overlaps, partition ranges, hot rows, transaction durations, batch sizes, and online writers. Increasing retry limits does not always improve throughput.

Do not log full entities or personal data on conflict. Log internal IDs, expected/observed versions if safely obtainable, `JobExecution`/`StepExecution` IDs, and correlation IDs.

## 21. Testing optimistic locking with two transactions

The most important test creates two independent persistence contexts reading the same version and then updating sequentially.

```java
@Test
void secondTransactionFailsWhenEntityVersionIsStale() {
    OrderEntity first = transactionTemplate.execute(status ->
            entityManager.find(OrderEntity.class, orderId));

    OrderEntity second = transactionTemplate.execute(status ->
            entityManager.find(OrderEntity.class, orderId));

    transactionTemplate.executeWithoutResult(status -> {
        OrderEntity current = entityManager.find(OrderEntity.class, orderId);
        current.approve();
        entityManager.flush();
    });

    assertThatThrownBy(() -> transactionTemplate.executeWithoutResult(status -> {
        second.changeAmount(new BigDecimal("125.00"));
        entityManager.merge(second);
        entityManager.flush();
    })).hasRootCauseInstanceOf(OptimisticLockException.class);
}
```

This is illustrative pseudocode; actual tests must guarantee each transaction uses its own persistence context/`EntityManager`. Never reuse the same `EntityManager` across both transactions, as the persistence context may return the same managed instance and fail to reproduce a stale version.

You can use two `TransactionTemplate` calls with properly scoped transaction managers and `EntityManager`, or open two independent `EntityManager` instances from `EntityManagerFactory`. The test must flush/commit the first transaction before the second transaction flushes.

## 22. Testing with independent EntityManagers

A more explicit way to control persistence contexts in an integration test is opening two `EntityManager` instances:

```java
@Test
void detectsConcurrentUpdateAcrossPersistenceContexts() {
    EntityManager em1 = entityManagerFactory.createEntityManager();
    EntityManager em2 = entityManagerFactory.createEntityManager();

    try {
        em1.getTransaction().begin();
        em2.getTransaction().begin();

        OrderEntity first = em1.find(OrderEntity.class, orderId);
        OrderEntity second = em2.find(OrderEntity.class, orderId);

        first.approve();
        em1.getTransaction().commit();

        second.changeAmount(new BigDecimal("125.00"));

        assertThatThrownBy(() -> {
            try {
                em2.flush();
                em2.getTransaction().commit();
            } catch (RuntimeException exception) {
                if (em2.getTransaction().isActive()) {
                    em2.getTransaction().rollback();
                }
                throw exception;
            }
        }).hasRootCauseInstanceOf(OptimisticLockException.class);
    } finally {
        if (em1.isOpen()) {
            em1.close();
        }
        if (em2.isOpen()) {
            em2.close();
        }
    }
}
```

This test uses manual transaction management to make the two persistence contexts explicit. In Spring projects, you may prefer testing via `TransactionTemplate` or real configured repositories/services. Clean up active transactions in `finally` and do not reuse an `EntityManager` after an optimistic lock failure, as the transaction/persistence context may no longer be usable.

## 23. Testing retries in Spring Batch

Entity unit tests do not prove Step retries work properly. Batch integration tests should inject controlled conflicts:

1. Seed an entity with a known version.
2. Have the reader or processor fetch the command/entity for the item.
3. Have a test hook or second transaction update the same row before the writer flushes.
4. The writer hits the stale version and raises an optimistic lock exception.
5. The retry path reloads the entity in a new transaction and reapplies the command if business rules allow.
6. Verify the Step completes or fails according to the retry limit.
7. Verify the final version and state are accurate without losing the competing transaction's update.

Tests should verify retry counts and confirm reloading actually happened. If the retry keeps using the old entity, the test should expose repeated conflicts rather than pretending the retry policy solved the issue.

Cases to include:

- No conflict: succeeds on the first write.
- Single conflict followed by reload and successful retry.
- Conflicts exceeding retry limit: Step fails or recovers per policy.
- Conflict skipped per business rules: skip listener/audit receives the right item.
- Row deleted before retry: explicit not-found handling.
- Two Jobs processing the same business key: final state matches ownership/idempotency contracts.

## 24. Common pitfalls

### Forgetting @Version

Without a JPA-managed version field, standard optimistic version checking is not applied to that entity. Add the version field and corresponding database migration.

### Manually incrementing version in the entity

The provider manages the version. Modifying it yourself corrupts state or triggers provider errors. Only update version manually in bulk/native SQL with explicit expected-version predicates.

### Assuming exceptions always happen at setters

Conflicts are usually detected at flush/commit. Place tests and logging at the true transaction boundaries.

### Retrying the same stale entity

The old version still will not match. Reload the entity in a fresh transaction and reapply the command per business rules.

### Catching the exception and continuing the transaction

The transaction may already be rollback-only. Let the exception propagate and retry in a new transaction.

### Enabling overly broad retries

Retrying every exception increases load and masks permanent failures. Only retry transient/conflict exceptions with an appropriate reload strategy.

### Skipping every optimistic lock exception

This can drop important business updates. Only skip when conflicts are acceptable and backed by auditing/reconciliation.

### Using bulk JPQL and forgetting version

Bulk updates bypass normal dirty checking. Add expected version predicates, increment version, and verify update counts when optimistic semantics are needed.

### Using JDBC/native SQL without incrementing version

JPA cannot detect changes via version if writer SQL skips updating the version column according to contract.

### Overlapping partitions

Multiple workers update hot rows and trigger constant conflicts. Partition by non-overlapping ownership or claim records.

### Sharing one EntityManager across multiple threads

`EntityManager` is not thread-safe. Each transaction/thread needs its own persistence context.

### Assuming @Version protects multi-row invariants

Versions protect versioned entities/rows, not aggregates or cross-row predicates. Use constraints, atomic updates, or appropriate locking.

## 25. Workflow for applying optimistic locking in Batch JPA

When a Step updates entities that may be modified concurrently, follow these steps:

1. Identify which entities can experience concurrent updates.
2. Add `@Version` and a database migration for the version column.
3. Ensure every write path (JPA, repositories, bulk SQL, native SQL) honors the version contract.
4. Decide whether items are entity snapshots or commands/IDs; prefer commands when reloading fresh state is needed.
5. Configure `JpaTransactionManager` and `EntityManagerFactory` matching the Step.
6. Use `JpaItemWriter` or a custom writer with clear transaction/flush semantics.
7. Identify the exact exceptions thrown at flush/commit.
8. Retry conflicts only when the next attempt can safely reload and reapply logic.
9. Set finite retry limits and backoff; route unmergeable conflicts to reject/failure handling.
10. Keep side effects idempotent and never share an `EntityManager` across threads.
11. Reduce contention via disjoint partitioning or ownership/claim patterns when needed.
12. Test dual persistence contexts, stale entities, bulk updates, retry/reload, and restarts on a production-like database.
13. Monitor conflict rates and tune concurrency/locking from observed metrics.

| Need | Handling |
|---|---|
| Detect entity edits since read time | JPA `@Version` |
| Write JPA entities in a chunk | `JpaItemWriter` + matching transaction manager |
| Recover from resolvable conflicts | Roll back, reload fresh entity, and reapply command in a new transaction |
| Version-checked bulk JPQL/native SQL | `WHERE id = ? AND version = ?`, increment version, and check update count |
| Reduce worker-to-worker conflicts | Disjoint partitions/ownership or record claiming |
| Frequent conflicts on hot rows | Evaluate pessimistic locking or redesign concurrency |
| Test for lost updates | Two independent `EntityManager`s read the same version then update sequentially |

## Conclusion

Optimistic locking in JPA uses `@Version` to detect whether an entity was updated by another transaction since being read. When versions no longer match, JPA throws an optimistic lock exception during flush or commit; Spring Batch rolls back the chunk and applies retry, skip, or fail per Step configuration. Retrying resolves conflicts only when the new attempt loads current state and reapplies the business command; resubmitting a detached entity with an old version typically repeats the same error. Ensure all write paths respect the version contract, watch out for bulk JPQL and native SQL, use the proper JPA transaction manager, partition data to reduce contention, and test using multiple independent persistence contexts. `@Version` protects individual entity updates, whereas multi-row invariants still require constraints, atomic updates, or appropriate locking.
