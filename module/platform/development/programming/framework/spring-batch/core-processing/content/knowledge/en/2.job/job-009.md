# Job name and JobRegistry in Spring Batch

In Spring Batch, each job has a **technical name** by which the framework identifies and manages it. When an application has many jobs, Spring Batch also provides `JobRegistry` to look up jobs by name. These two concepts often appear together, but they solve two different problems: the job name identifies a job, while the registry is where the `Job` objects in the application are registered and looked up again.

The job name also takes part in the identity of the `JobInstance` stored in the metadata. Therefore, the choice of job name affects the execution history, restartability, and how operational tools find the job. Understanding the role of `JobRegistry` correctly also helps avoid confusing the registry, the Spring application context, and the `JobRepository`.

## 1. What is a job name?

A `Job` is the definition of a batch process, usually consisting of one or more steps orchestrated in a processing flow. Each `Job` has a name that is supplied when the job is created. This name is returned through the `getName()` method of the `Job` object.

With the builder API commonly used in Spring Batch 5, the name is passed into `JobBuilder`:

```java
@Bean
Job importOrdersJob(JobRepository jobRepository,
                    Step importOrdersStep) {
    return new JobBuilder("importOrders", jobRepository)
        .start(importOrdersStep)
        .build();
}
```

In the example above, the job's name is `importOrders`. The method name `importOrdersJob` is the default bean name in the Spring application context; it does not necessarily have to match the job name. The name passed into `JobBuilder` is the name that the `Job` object returns through `getName()` and that Spring Batch uses in the metadata.

In older versions of Spring Batch, the application could create jobs through `JobBuilderFactory`. The way configuration is written changes by version, but the meaning of the job name stays the same: it is the identifying name of the job in the batch model.

A job name is a technical identifier, not just a label displayed on a screen. It often appears in logs, metadata, operational commands, and job lookup APIs. Therefore, you should choose a name that is easy to understand, stable, and accurately describes the business purpose, for example `importOrders`, `closeDailyAccounts`, or `generateMonthlyReport`.

## 2. How does the job name take part in determining a JobInstance?

Spring Batch distinguishes the job definition from each logical unit of work that is run. A `JobInstance` is identified by the job name and the `JobParameters` marked as identifying.

For example, the job `importOrders` runs by business date:

```text
Job name: importOrders
Identifying parameter: businessDate=2026-11-15
                  |
                  v
        JobInstance of the date 2026-11-15
                  |
          +-------+-------+
          |               |
          v               v
    JobExecution 1   JobExecution 2
       FAILED          COMPLETED
                    (restart)
```

Two executions with the same job name and the same identifying parameters belong to the same `JobInstance`. If the first one fails, a rerun can create a new `JobExecution` for that instance. If the business date changes, the identifying parameters change and Spring Batch creates a different `JobInstance`.

This also means that renaming a job changes the logical identity of the work. For example, `importOrders` and `importCustomerOrders` are regarded by Spring Batch as two different job names, even if they use the same steps and the same parameters. Old executions still carry the job name that was stored earlier in the metadata; renaming does not automatically move the old history to the new name.

Therefore, you should not change a job name arbitrarily between deployments. If you need to rename, treat it as a change that affects operations and plan for the metadata history, the restart process, and the systems that call the job by name.

## 3. Rules for choosing and managing job names

A good job name should meet the following principles:

- **Business meaning:** an operator can guess the purpose of the job from the name, such as `reconcilePayments`.
- **Stable:** do not attach the run date, the attempt number, or a random value to the job name. Data that changes per run should be `JobParameters`.
- **Unique within the management scope:** jobs registered into the same `JobRegistry` need distinct names. Registering two different jobs under the same name will cause a conflict.
- **Consistent:** use one naming convention throughout the application, for example camelCase by action and business object.
- **Separate identity from configuration:** the job name denotes the type of process; parameters such as the business date, batch code, or input file name denote the specific unit of work.

For example, an application that imports data every day should have a fixed job name of `importOrders`, while the date to import is passed through `businessDate`. You should not create a new name such as `importOrders20261115` for each day, because that bloats the job catalog and makes lookup, configuration, and operations difficult.

## 4. What is JobRegistry?

`JobRegistry` is a Spring Batch abstraction used to register and look up `Job` objects by name. You can think of it as a job catalog that other components in the application can ask: "Which object is the job named `importOrders`?"

The main operations of `JobRegistry` include:

- Registering a `JobFactory` that represents a job.
- Getting a `Job` object by name through `getJob(String name)`.
- Getting the list of registered job names through `getJobNames()`.
- Unregistering a job by name through `unregister(String name)`.

When looking up a name that does not exist, the registry reports a `NoSuchJobException`. When there is a name conflict during registration, registration can fail with a `DuplicateJobException`.

A common implementation is `MapJobRegistry`. This implementation keeps the job factories in an in-memory map structure, with the job name as the key. It suits applications that need a simple registry within a single process.

`JobRegistry` does not create batch processing logic and does not execute jobs itself. It provides the ability to look up `Job` objects that the application has created and registered. Execution is still handled by components such as `JobLauncher` or `JobOperator`.

## 5. Registering a job into the JobRegistry

Declaring a bean of type `Job` in the Spring application context does not mean that job automatically appears in every `JobRegistry`. The application needs to configure an appropriate registration mechanism.

Conceptually, the registration process has three parts:

1. Create an implementation of `JobRegistry`, usually `MapJobRegistry`.
2. Detect the `Job` beans in the application context or create the corresponding `JobFactory`.
3. Register the factory with the registry so the job can be looked up by name.

In traditional Spring Batch configurations, `JobRegistryBeanPostProcessor` is commonly used to automatically register `Job` beans when Spring initializes the beans. In newer versions, the recommended registration mechanism may change; for example, Spring Batch 5.2 adds `JobRegistrySmartInitializingSingleton` as an alternative. Use the mechanism appropriate to the application's Spring Batch version and avoid configuring multiple components that register the same job into the same registry at the same time.

At the API level, the registry takes a `JobFactory`, not a plain name string. A `ReferenceJobFactory` can represent an already-created `Job` object. Whether registration is automatic or manual depends on the structure of the application context and how the application organizes its job modules.

Once a job is registered, you can look it up as follows:

```java
Job job = jobRegistry.getJob("importOrders");
```

If you want to see the jobs currently in the registry:

```java
Collection<String> jobNames = jobRegistry.getJobNames();

for (String jobName : jobNames) {
    System.out.println(jobName);
}
```

The examples above focus on the lookup API. For them to work, the job must have been registered successfully beforehand and the consuming component must receive the correct `JobRegistry` instance that manages that job.

## 6. Using JobRegistry to look up and launch jobs

When the application directly knows the `Job` bean, it can pass that object to the `JobLauncher`. But in some situations, the application only knows the job name at run time, for example an operations screen that lets a user choose a job, or a service that receives launch requests from another system. In that case, `JobRegistry` helps find the corresponding `Job` object.

Example:

```java
Job job = jobRegistry.getJob("importOrders");

JobParameters parameters = new JobParametersBuilder()
    .addString("businessDate", "2026-11-15", true)
    .toJobParameters();

JobExecution execution = jobLauncher.run(job, parameters);
```

In this flow:

1. The application looks up the job by the name `importOrders`.
2. The application creates the `JobParameters` for the unit of work to process.
3. The `JobLauncher` receives the `Job` object and the parameters to launch.
4. The `JobRepository` manages the metadata of the `JobInstance`, `JobExecution`, and the resulting `StepExecution`s.

Another way to use it is through `JobOperator`. `JobOperator` provides operational actions based on the job name and the execution ID, such as launching, stopping, or restarting under the framework's conditions. `JobOperator` implementations typically use the `JobRegistry` to find jobs by name. Therefore, when operating through `JobOperator`, registering the job under the correct name is an important part of the configuration.

Not every `JobLauncher` call needs a `JobRegistry`. If the code already has a `Job` object injected directly, it can pass that object to the launcher. The registry is useful when you need dynamic lookup by name or integration with job control tools.

## 7. Distinguishing JobRegistry, ApplicationContext, and JobRepository

These three components are related but not interchangeable.

| Component | Role | Data or objects managed |
| --- | --- | --- |
| Spring `ApplicationContext` | The container that manages the application's beans and dependencies. | `Job`, `Step`, service, reader, writer, and other beans. |
| `JobRegistry` | A lookup catalog of jobs by name. | The registered `JobFactory`s, which in turn provide the `Job` objects. |
| `JobRepository` | Stores and queries the metadata of batch execution. | `JobInstance`, `JobExecution`, `StepExecution`, `ExecutionContext`, and related state. |

For example, the application context can contain the bean `importOrdersJob`. When configured for registration, this job can be looked up through the `JobRegistry` by the name `importOrders`. When the job runs, the `JobRepository` records the execution and the state of that run.

This difference is very important: the registry is usually an in-memory lookup structure, while the repository usually stores durable metadata in a database. Restarting the application may cause the in-memory registry to be recreated and the jobs to be registered again; the execution metadata in the repository remains if the database is kept intact.

## 8. Multiple application contexts and applications with many jobs

In a small application, the jobs are usually declared in the same application context. As the application grows, groups of jobs can be split into modules or child application contexts to manage configuration independently.

In that case, `JobRegistry` provides a common lookup point for the jobs registered from the related contexts. Spring Batch has mechanisms such as `AutomaticJobRegistrar` to support registering jobs declared in child contexts. This mechanism is useful when the application wants to load or manage multiple groups of jobs by module.

When using a shared registry across multiple modules, pay attention to:

- Job names must be unique within the shared registry, even if the jobs are in different application contexts.
- Each job must be registered exactly once according to the intended configuration lifecycle.
- When a module is removed, the corresponding job needs to be unregistered if the context management mechanism does not handle that itself.
- The dependencies that a job needs must exist in a context with a lifecycle appropriate to the job.
- Do not let modules arbitrarily register two different jobs with the same name, because lookups become ambiguous or fail due to the name collision.

If the system runs multiple application instances on multiple machines, you need to distinguish the registry in each process from the shared metadata repository. Each process can have its own registry containing the jobs that process knows about. To coordinate history and execution state, processes that jointly operate a group of jobs usually need to share a consistently configured metadata repository.

## 9. Error handling and common scenarios

**Job not found on lookup:** `JobRegistry.getJob("importOrders")` can throw a `NoSuchJobException` if the name does not exist or the job has not been registered. Check the name in `JobBuilder`, the registration configuration, and the timing of the lookup call. A bean already existing in the application context is not enough to conclude that the registry has the job.

**Duplicate job name:** if two different jobs are registered under the same name, the registry can refuse the registration with a `DuplicateJobException`. Check the modules and application contexts that contribute jobs to the registry, then rename to ensure uniqueness.

**Bean name differs from job name:** this is usually not an error. The bean can be named `importOrdersJob`, while `Job.getName()` returns `importOrders`. When looking up through the `JobRegistry`, use the job name configured in `JobBuilder`.

**A rerun job is treated as a different instance:** check the job name and the identifying parameters. Changing the job name changes the instance identity; changing one identifying parameter also creates a different instance. Non-identifying parameters do not take part in determining the logical identity.

**The job has metadata but the registry cannot find it:** the repository stores the execution history, while the registry holds the catalog of jobs currently registered in the application. Old metadata may still exist in the database even though the current configuration no longer declares or registers that job.

**Renaming a job in a deployment:** before deploying, identify the schedulers, APIs, scripts, and operational tools that call the job by its old name. Also consider how to handle running instances, failed instances that need a restart, and the metadata history. Do not regard renaming as merely renaming a Java bean.

## 10. Design and operations practice

When building a Spring Batch application with many jobs, make a list of job names along with their business purposes and identifying parameters. Use stable names so the execution history can be looked up consistently across deployments. Register all jobs that need to be controlled dynamically into an appropriate registry, and confirm there are no duplicate names.

For flows that run directly from code, you can inject the `Job` and call the `JobLauncher`. For flows that need to choose a job by name or be controlled through `JobOperator`, make sure the `JobRegistry` is configured and registration is complete before receiving operational requests. When the application has multiple modules or child contexts, manage the registration and unregistration lifecycle clearly.

When checking the configuration, you can confirm a job's name with `job.getName()`, view the registered names through `jobRegistry.getJobNames()`, and try looking up a specific job with `jobRegistry.getJob(name)`. In a production environment, log the job name along with the identifying parameters and the execution ID to help trace a run.

The job name helps Spring Batch identify the type of process and takes part in determining the `JobInstance`. The `JobRegistry` helps the application find `Job` objects by name for launching and operations. When the two mechanisms are configured consistently with the `JobRepository`, the application can manage multiple jobs clearly, look them up accurately, and maintain the execution history across runs.
