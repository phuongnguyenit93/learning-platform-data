# HeaderCallback and FooterCallback

In Spring Batch, `FlatFileItemWriter` supports writing extra content at the beginning and end of a file via `FlatFileHeaderCallback` and `FlatFileFooterCallback`. Headers typically hold column names, batch info, or file metadata; footers can hold total record counts, batch IDs, or end-of-file markers.

These two callbacks belong to the Writer lifecycle. The header is written when the Writer opens a file for a new write; the footer is called when the Writer closes. They are not `ItemReader`, `ItemProcessor`, or separate `ItemWriter` instances, and they do not run once per item or per chunk.

## 1. Headers and footers in batch files

An exported file typically has three sections:

```text
HEADER
order_id,customer_id,amount

DATA RECORDS
ORD-1001,CUST-01,125.50
ORD-1002,CUST-02,89.90
ORD-1003,CUST-03,240.00

FOOTER
# records=3
# batch=orders-2026-11-15
```

- The header describes the file's structure or origin.
- Data rows are generated by `FlatFileItemWriter`'s `LineAggregator`.
- The footer can record total line counts, checksums, batch IDs, or a marker indicating the file was closed.

Headers and footers are useful when exchanging files with external systems, when schemas must be self-describing, or when record counts need verification after transfer. If the receiving system's format forbids header/footer lines, do not add them arbitrarily as that would violate the contract.

## 2. FlatFileHeaderCallback and FlatFileFooterCallback

Spring Batch provides two callback interfaces:

```java
public interface FlatFileHeaderCallback {
    void writeHeader(Writer writer) throws IOException;
}

public interface FlatFileFooterCallback {
    void writeFooter(Writer writer) throws IOException;
}
```

Each callback receives a `java.io.Writer` to write characters to the output stream managed by `FlatFileItemWriter`.

- `writeHeader(Writer)`: writes header content when the Writer initializes the output file.
- `writeFooter(Writer)`: writes footer content when the Writer closes.

Because callbacks write directly to `Writer`, write a newline explicitly whenever you want the header/footer on its own line. Callbacks do not receive `Chunk` or the current item. If a footer needs processing metrics, fetch them from a suitable source such as `StepExecution` or an appropriately scoped accumulator.

Do not call `close()` on the Writer passed into a callback. Stream lifecycle is managed by Spring Batch; the callback only writes its own content.

## 3. Configuring headers with FlatFileItemWriterBuilder

In Spring Batch 5 and later, headers can be configured using `headerCallback(...)` on `FlatFileItemWriterBuilder`:

```java
import java.io.IOException;
import java.io.Writer;

import org.springframework.batch.item.file.FlatFileItemWriter;
import org.springframework.batch.item.file.FlatFileHeaderCallback;
import org.springframework.batch.item.file.builder.FlatFileItemWriterBuilder;
import org.springframework.core.io.FileSystemResource;

FlatFileHeaderCallback headerCallback = writer -> {
    writer.write("order_id,customer_id,amount");
    writer.write("\n");
};

FlatFileItemWriter<ExportOrder> itemWriter =
        new FlatFileItemWriterBuilder<ExportOrder>()
                .name("orderExportWriter")
                .resource(new FileSystemResource("/data/out/orders.csv"))
                .encoding("UTF-8")
                .lineSeparator("\n")
                .lineAggregator(order -> String.join(",",
                        order.orderId(),
                        order.customerId(),
                        order.amount().toPlainString()))
                .headerCallback(headerCallback)
                .saveState(true)
                .shouldDeleteIfExists(true)
                .build();
```

When the Writer opens a new file, the callback writes the column header before the records. `lineSeparator("\n")` configures the line ending for items emitted by the Writer; the callback writes its own newline because it interacts directly with `Writer`.

This example uses `String.join()` for illustration. If fields can contain commas, quotes, or newlines, use proper CSV escaping/quoting or a dedicated CSV library. The header must match the exact field order emitted by `lineAggregator`.

## 4. Configuring footers with FlatFileFooterCallback

The footer callback is registered using `footerCallback(...)`:

```java
import org.springframework.batch.item.file.FlatFileFooterCallback;

FlatFileFooterCallback footerCallback = writer -> {
    writer.write("# end-of-export");
    writer.write("\n");
};

FlatFileItemWriter<ExportOrder> itemWriter =
        new FlatFileItemWriterBuilder<ExportOrder>()
                .name("orderExportWriter")
                .resource(new FileSystemResource("/data/out/orders.csv"))
                .encoding("UTF-8")
                .lineSeparator("\n")
                .lineAggregator(this::toCsvLine)
                .headerCallback(writer -> {
                    writer.write("order_id,customer_id,amount\n");
                })
                .footerCallback(footerCallback)
                .saveState(true)
                .shouldDeleteIfExists(true)
                .build();
```

The footer can hold a marker or summary info. For example, `# end-of-export` helps consumers recognize the end-of-file boundary if the interchange format allows comment lines.

The footer callback runs when the Writer closes, not after every chunk. Do not place email sending, API calls, or long-running business workflows inside the callback. Use the callback only to write file content; coordinate publishing and notifications separately.

## 5. Writing dynamic headers/footers from JobParameters

Headers often need to carry a batch ID, business date, or source name. You can inject `JobParameters` into a `@StepScope` Writer and capture those values in the callbacks:

```java
import org.springframework.batch.core.configuration.annotation.StepScope;
import org.springframework.batch.item.file.FlatFileItemWriter;
import org.springframework.batch.item.file.builder.FlatFileItemWriterBuilder;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.core.io.FileSystemResource;

@Bean
@StepScope
public FlatFileItemWriter<ExportOrder> orderExportWriter(
        @Value("#{jobParameters['outputFile']}") String outputFile,
        @Value("#{jobParameters['batchId']}") String batchId,
        @Value("#{jobParameters['businessDate']}") String businessDate) {

    return new FlatFileItemWriterBuilder<ExportOrder>()
            .name("orderExportWriter")
            .resource(new FileSystemResource(outputFile))
            .encoding("UTF-8")
            .lineSeparator("\n")
            .lineAggregator(this::toCsvLine)
            .headerCallback(writer -> {
                writer.write("# batch=" + batchId + "\n");
                writer.write("# business-date=" + businessDate + "\n");
                writer.write("order_id,customer_id,amount\n");
            })
            .footerCallback(writer -> {
                writer.write("# batch-end=" + batchId + "\n");
            })
            .saveState(true)
            .shouldDeleteIfExists(true)
            .build();
}
```

`@StepScope` ensures the Writer target is instantiated per `StepExecution` and receives that run's `JobParameters`. When multiple `JobExecution` runs execute concurrently, never store batch IDs in mutable fields on a shared singleton Writer.

Only include metadata in headers/footers if the receiving system allows it. If the file is a strict CSV contract expecting only a single column-header line, adding comment lines can break consumer parsing. You can store metadata in a separate manifest instead of inside the CSV.

## 6. Writing dynamic metrics in footers

Footers sometimes need the total number of written records or skipped errors. Because the callback only receives `Writer`, metrics must be supplied from another source. One approach is injecting `StepExecution` into a Step-scoped Writer:

```java
import org.springframework.batch.core.StepExecution;
import org.springframework.batch.core.configuration.annotation.StepScope;
import org.springframework.beans.factory.annotation.Value;

@Bean
@StepScope
public FlatFileItemWriter<ExportOrder> orderExportWriter(
        @Value("#{jobParameters['outputFile']}") String outputFile,
        @Value("#{stepExecution}") StepExecution stepExecution) {

    return new FlatFileItemWriterBuilder<ExportOrder>()
            .name("orderExportWriter")
            .resource(new FileSystemResource(outputFile))
            .lineAggregator(this::toCsvLine)
            .footerCallback(writer -> {
                writer.write("# written=" + stepExecution.getWriteCount() + "\n");
                writer.write("# skipped=" + stepExecution.getSkipCount() + "\n");
            })
            .saveState(true)
            .build();
}
```

This example illustrates reading `StepExecution` counters when the Writer closes. `writeCount` is the number of written items per Step metadata; `skipCount` is the total skipped errors in `StepExecution`. If the footer needs complex aggregations or metrics spanning multiple Steps/JobExecutions, compute and store results in a dedicated service or Step and publish after the Job finishes.

Do not use a mutable `int totalRows` on a singleton callback object to accumulate across multiple `JobExecution` runs. Values can mix across concurrent runs and be lost on restart. If an accumulator is needed, place it in `@StepScope` or persist data keyed by execution/batch ID.

## 7. Do callbacks re-run on restart?

Headers and footers behave differently during restart:

- When the Writer opens for a fresh execution, the header callback is invoked to write the header.
- On restart with a saved `ExecutionContext`, the Writer restores its write position from the checkpoint; the header should not be written again mid-file.
- When the Writer closes, the footer callback is invoked to write the footer.

Suppose a Job writes two chunks and fails on the third chunk:

```text
Initial run
  open -> write header
  chunk 1 -> commit
  chunk 2 -> commit
  chunk 3 -> error / rollback
  close -> footer callback

Restart same JobInstance
  open -> restore checkpoint, truncate uncommitted/footer after checkpoint
  resume chunk 3
  close -> write footer for new close
```

The footer may be written when the Writer closes even if the Job did not reach `COMPLETED`, such as when a Step stops or fails. Therefore, never treat the presence of a footer as sole proof of Job success. If consumers may only read completed files, use a publish Step after processing succeeds or write a completion status manifest.

Restart also relies on `saveState(true)`, a stable Writer name, and output files remaining untouched outside Spring Batch. Deleting the file or editing contents after a checkpoint can invalidate the saved write position.

## 8. HeaderCallback with append and existing files

`FlatFileItemWriterBuilder` exposes options such as `append(true)` and `shouldDeleteIfExists(true)`. They govern how the Writer handles an existing file when opening for a fresh write.

```java
new FlatFileItemWriterBuilder<ExportOrder>()
        .name("auditWriter")
        .resource(new FileSystemResource(outputFile))
        .lineAggregator(this::toCsvLine)
        .append(true)
        .saveState(true)
        .build();
```

Appending can fit log files or append-only formats, but decide clearly whether headers should be written when opening an existing file. If the callback always writes a header on an already-populated file, duplicate headers can appear mid-file. Test the exact append behavior of your Spring Batch version and choose one of these approaches:

1. Use a fresh output file per `JobInstance`/batch ID.
2. Record headers/metadata in a separate manifest file.
3. Use a conditional callback based on file state if the contract allows it and checking creates no race condition.
4. Avoid appending if the file format mandates a single leading header.

`append(true)` does not replace the restart mechanism. When restarting a Step, the Writer must restore the checkpoint of that execution; do not manually swap files or append via an external process while a Job is running.

## 9. Footers are not a Job success signal

The footer callback is bound to the Writer's close lifecycle. The Writer can be closed when a Step finishes successfully, fails, or stops. Consequently, a footer like `# COMPLETE` can be misleading if the Job has not completed its full flow.

If consumers need to know a file is ready, use an explicit publish workflow:

```text
Export Step
   |
   +--> write orders.csv.part
   +--> header + records + technical footer
   |
   v
Job/flow confirms Steps succeeded
   |
   v
Publish Step
   |
   +--> validate file / checksum / line count
   +--> rename or copy to orders.csv
   +--> write COMPLETE status manifest
   |
   v
Consumer allowed to read final file
```

Writing to a temporary file and publishing after success prevents consumers from reading partially written files. When using an atomic rename, source and destination usually must reside on the same filesystem; verify exact storage semantics in your environment.

If the Job fails, the `.part` file can be retained for restart or investigation. Never automatically publish it merely because the footer callback executed.

## 10. Handling errors inside callbacks

Callbacks can throw `IOException` when writing headers or footers—for example, disk full, lost filesystem mount, or an unwritable Writer. This error can fail the Step.

Example callback handling:

```java
.headerCallback(writer -> {
    writer.write("order_id,amount\n");
})
.footerCallback(writer -> {
    writer.write("# end-of-file\n");
})
```

Do not catch and ignore `IOException` inside a callback. If the header fails to write, the file violates its schema; if the footer fails to write, the file is incomplete under the contract. Let the failure surface in Step/Job status and log enough context to investigate.

Do not perform non-file work inside callbacks, such as sending emails or calling APIs. If a callback fails while closing the Writer, extra side effects make recovery hard to reason about. Move notifications or publishing into separate Steps or listeners, using outboxes or idempotency where needed.

## 11. Headers/Footers and CSV formatting

Headers must match the column order of `LineAggregator`. Example:

```java
.headerCallback(writer -> {
    writer.write("order_id,customer_id,amount\n");
})
.lineAggregator(order -> String.join(",",
        order.orderId(),
        order.customerId(),
        order.amount().toPlainString()))
```

If `lineAggregator` changes order to `customer_id,order_id,amount`, the header must change to match. If the header mislabels data, consumers can map columns incorrectly even though the file parses cleanly.

Footers in strict CSV files are usually not data records. If the receiving system parses every line as an order, a `# records=...` line will cause mapping errors. Either use a contract-supported trailer format or store total record counts in a sidecar file such as `orders.csv.manifest`.

For CSV requiring quoting/escaping, ensure both data and headers follow identical encoding, delimiter, and quoting rules. Callbacks write raw text and do not automatically escape metadata values.

## 12. Headers/Footers in fixed-width or custom formats

Callbacks are not limited to CSV. You can write fixed-width header/footer records:

```java
.headerCallback(writer -> {
    writer.write(String.format(
            "%-8s%-10s%08d",
            "BATCH",
            businessDate,
            expectedRecordCount));
    writer.write("\n");
})
.footerCallback(writer -> {
    writer.write(String.format(
            "%-8s%08d",
            "TRAILER",
            actualRecordCount));
    writer.write("\n");
})
```

Illustrative formats must be adjusted to match the receiving system's specification: field widths, padding, charset, digit counts, and checksum rules. `String.format()` without a locale can vary across locales for some types; when numeric formatting must be fixed, specify an explicit locale or format per contract.

If a footer needs a checksum of the entire file, compute the checksum over the exact encoded bytes written, including or excluding headers/footers as specified. Never compute checksums over pre-encoded Java strings if the receiving system verifies byte-level checksums.

## 13. Combining callbacks with JobExecution/StepExecution

Headers may need `JobExecution` info such as `JobInstance` ID, business date, or source code. Footers may need Step counters. Inject these values into a Step-scoped Writer:

```java
@Bean
@StepScope
public FlatFileItemWriter<ExportOrder> exportWriter(
        @Value("#{jobExecution.id}") Long executionId,
        @Value("#{jobParameters['businessDate']}") String businessDate,
        @Value("#{stepExecution}") StepExecution stepExecution,
        @Value("#{jobParameters['outputFile']}") String outputFile) {

    return new FlatFileItemWriterBuilder<ExportOrder>()
            .name("exportWriter")
            .resource(new FileSystemResource(outputFile))
            .lineAggregator(this::toCsvLine)
            .headerCallback(writer -> writer.write(
                    "# execution=" + executionId
                            + ", businessDate=" + businessDate + "\n"))
            .footerCallback(writer -> writer.write(
                    "# written=" + stepExecution.getWriteCount() + "\n"))
            .saveState(true)
            .build();
}
```

This example uses `jobExecution.id` for tracing and `stepExecution` for counters. The `JobExecution` ID changes on restart, so if the header must stay identical across restarts of the same `JobInstance`, omit execution IDs from headers since the Writer does not rewrite headers on restart. Use `JobInstance` ID or a stable identifying business key instead.

Never write sensitive `JobParameters` such as tokens, passwords, or unnecessary personal data into headers. File outputs are often shared externally and may outlive internal execution metadata.

## 14. Testing HeaderCallback and FooterCallback

Inspect the actual generated file, header/data/footer ordering, encoding, and restart behavior. Simply verifying that the callback was invoked is not enough to prove file formatting is valid.

Cases to test:

1. **New file:** header appears exactly once at the top of the file.
2. **With data:** records are written in the exact field order and delimiter.
3. **Zero items:** verify whether an empty file keeps its header/footer or is deleted per `shouldDeleteIfEmpty`.
4. **Footer:** footer appears at the end after the Writer closes.
5. **Restart:** header is not duplicated mid-file; Writer resumes at the committed position and the final footer sits only where expected.
6. **Append:** confirm whether headers duplicate per configuration and file contract.
7. **Callback failure:** simulate a write failure to verify Step/Job reflects the failure properly.
8. **Job failure:** verify the footer is never misconstrued as a signal that the file published successfully.

Example test with JUnit and a temporary directory:

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.io.TempDir;

class ExportHeaderFooterTest {

    @TempDir
    Path tempDir;

    @Test
    void writesHeaderRecordsAndFooter() throws Exception {
        Path output = tempDir.resolve("orders.csv");

        // Launch Step test with output path pointing to output.

        List<String> lines = Files.readAllLines(output);
        assertEquals("order_id,customer_id,amount", lines.get(0));
        assertTrue(lines.get(lines.size() - 1).startsWith("# records="));
    }
}
```

This is a test skeleton; the launch step must wire into your application's test Job/Step and `JobLauncherTestUtils`. For restart tests, keep identifying `JobParameters` and output path constant across both runs. Inject a failure after a committed chunk, restart the same `JobInstance`, and confirm there is no duplicate header, no duplicate records, and the final footer sits in the right spot.

## 15. Common pitfalls

| Pitfall | Cause | Mitigation |
|---|---|---|
| Incorrect newlines in callbacks | Callbacks write raw text and do not append line separators automatically. | Explicitly write `\n` or the contract newline. |
| Header mismatches LineAggregator | Column order or names changed without updating the header. | Manage header and mapping from a shared schema. |
| Treating the footer as proof of Job success | Writer closes even when a Step fails or stops. | Publish files in a separate Step after the flow succeeds. |
| Footer using mutable singleton fields | Concurrent executions mix metrics. | Use `@StepScope`, `StepExecution`, or stores keyed by execution ID. |
| Duplicate headers when appending | Callback may emit headers when opening in append mode. | Test append; use separate files or a manifest if needed. |
| Duplicate headers on restart | Writer fails to restore state or config/file changed. | Enable `saveState`, keep Writer name and file stable. |
| Calling APIs inside footer callbacks | Callback runs whenever the Writer closes, including failures. | Move side effects to Steps, listeners, or outboxes. |
| Footer line violates CSV schema | Consumers parse the trailer as a data record. | Use a supported trailer format or a sidecar manifest. |
| Swallowing IOException | File may lack headers/footers while the Step still reports success. | Let I/O errors surface and be handled explicitly. |

## Conclusion

`FlatFileHeaderCallback` and `FlatFileFooterCallback` allow `FlatFileItemWriter` to emit metadata at the beginning and end of files. The header callback writes column names or batch info when the Writer opens the file; the footer callback writes summaries or trailers when the Writer closes. Manage newlines explicitly, keep headers aligned with `LineAggregator`, read metrics via Step-scoped state, and understand callback behavior during appends and restarts. A footer does not prove a Job reached `COMPLETED`, because the Writer also closes when a Step fails or stops. For critical deliverables, write to a temporary file and publish in a separate Step after the Job flow succeeds; test actual files across both fresh runs and restarts to prevent duplicate headers/footers or malformed output.
