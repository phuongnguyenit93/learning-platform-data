# Output Consistency Across Multiple Writers

In Spring Batch, a Step may need to write the same item to multiple places: a business table and an audit table, two target tables, an export file and a database, or a database and a message broker. `CompositeItemWriter` supports calling multiple Writers in order on the same chunk. However, calling multiple Writers does not automatically cause all outputs to commit or roll back together as one atomic transaction.

For consistent outputs, you must clearly establish whether the Writers share a transaction resource or write to independent systems. When multiple Writers write to the same database with the same transaction manager, the chunk transaction can protect all changes. For multiple databases, files, or external APIs, appropriate mechanisms are needed, such as XA/JTA, staging and publishing, a transactional outbox, idempotency keys, or compensating workflows.

## 1. When Does a Step Need Multiple Writers?

After processing, an item may need to be written to several targets:

- A primary table storing business data.
- An audit table storing change history.
- A statistics or aggregation table.
- A CSV/XML file for transfer to another system.
- A message broker or REST API to publish events.
- An outbox table for asynchronous communication with external systems.

For example, an order import Job needs to store both the main record and import history:

```text
ItemReader
    |
    v
ItemProcessor
    |
    v
CompositeItemWriter
    |
    +--> OrderWriter       -> imported_order
    |
    +--> AuditWriter       -> order_audit
    |
    +--> OutboxWriter      -> outbox_event
```

The Writers receive the same chunk data in the configured order. Only after all write operations complete does Spring Batch proceed to commit the chunk transaction. Whether the final outcome is consistent also depends on whether the delegates genuinely participate in the same transaction.

## 2. How Does CompositeItemWriter Work?

`CompositeItemWriter<T>` is a Writer that delegates writing to a list of child Writers. Each time `write(chunk)` is called, the composite invokes each delegate in list order and passes the same chunk to each delegate.

For example, with three Writers A, B, and C:

```text
write(chunk)
    |
    v
  Writer A
    |
    v
  Writer B
    |
    v
  Writer C
    |
    v
  return to Step
    |
    v
  transaction commit (if no error)
```

This means:

- All delegates receive the same items in the chunk.
- Delegates are called sequentially in the configured order.
- The composite does not split the chunk into different item groups on its own.
- If a delegate throws an exception, writing stops at that delegate; later delegates may not have been called.
- The exception propagates back to the Step for transaction/retry/skip policy handling.

`CompositeItemWriter` fits when all destinations must receive the same set of items. If each item should only go to one Writer depending on type or condition, a routing mechanism like `ClassifierCompositeItemWriter` is needed instead of broadcasting the entire chunk.

## 3. Configuring CompositeItemWriter with a Builder

With Spring Batch 5, you can configure it using `CompositeItemWriterBuilder`:

```java
import java.util.List;

import org.springframework.batch.item.ItemWriter;
import org.springframework.batch.item.support.CompositeItemWriter;
import org.springframework.batch.item.support.builder.CompositeItemWriterBuilder;
import org.springframework.context.annotation.Bean;

@Bean
public CompositeItemWriter<Order> compositeOrderWriter(
        ItemWriter<Order> orderWriter,
        ItemWriter<Order> auditWriter) {

    return new CompositeItemWriterBuilder<Order>()
            .delegates(List.of(orderWriter, auditWriter))
            .build();
}
```

`orderWriter` and `auditWriter` are two delegates configured elsewhere. The order in `List.of(...)` is the invocation order. If audit must be written after the main record has been processed, place `orderWriter` before `auditWriter`.

The composite does not automatically make delegates transaction-aware. Each delegate must use the right transaction resource and must not commit independently if chunk rollback is expected to take effect.

## 4. Example: Two Writers Writing Two Tables in the Same Database

This is the easiest case for achieving consistency: two Writers writing to two tables in the same database, sharing one `DataSource` and the Step's transaction manager.

Suppose there are two tables:

```sql
CREATE TABLE imported_order (
    order_id VARCHAR(80) PRIMARY KEY,
    customer_id VARCHAR(80) NOT NULL,
    amount DECIMAL(18, 2) NOT NULL
);

CREATE TABLE order_audit (
    audit_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id VARCHAR(80) NOT NULL,
    action VARCHAR(40) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Main writer:

```java
@Bean
public JdbcBatchItemWriter<Order> orderWriter(
        @Qualifier("businessDataSource") DataSource dataSource) {

    return new JdbcBatchItemWriterBuilder<Order>()
            .dataSource(dataSource)
            .sql("""
                    INSERT INTO imported_order(order_id, customer_id, amount)
                    VALUES (:orderId, :customerId, :amount)
                    """)
            .beanMapped()
            .build();
}
```

Audit writer:

```java
@Bean
public JdbcBatchItemWriter<Order> orderAuditWriter(
        @Qualifier("businessDataSource") DataSource dataSource) {

    return new JdbcBatchItemWriterBuilder<Order>()
            .dataSource(dataSource)
            .sql("""
                    INSERT INTO order_audit(order_id, action, created_at)
                    VALUES (:orderId, 'IMPORTED', CURRENT_TIMESTAMP)
                    """)
            .beanMapped()
            .build();
}
```

Both Writers use the same `businessDataSource` bean. `Order` in the example is a JavaBean with properties `orderId`, `customerId`, and `amount` so `beanMapped()` extracts values.

Combining and wiring into the Step:

```java
@Bean
public CompositeItemWriter<Order> compositeOrderWriter(
        @Qualifier("orderWriter") ItemWriter<Order> orderWriter,
        @Qualifier("orderAuditWriter") ItemWriter<Order> auditWriter) {

    return new CompositeItemWriterBuilder<Order>()
            .delegates(List.of(orderWriter, auditWriter))
            .build();
}

@Bean
public Step importOrdersStep(
        JobRepository jobRepository,
        @Qualifier("businessTransactionManager")
        PlatformTransactionManager transactionManager,
        ItemReader<Order> orderReader,
        CompositeItemWriter<Order> compositeOrderWriter) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<Order, Order>chunk(200, transactionManager)
            .reader(orderReader)
            .writer(compositeOrderWriter)
            .build();
}
```

`businessTransactionManager` must manage the exact `businessDataSource` used by both `JdbcBatchItemWriter`s. If the second delegate fails before commit, statements from the first delegate in the same transaction are also rolled back. This keeps the main table and audit table consistent within one database transaction.

## 5. Transaction Boundaries Determine Consistency

The composite only coordinates Writer call order. The Step's transaction manager decides which changes commit or roll back together with the chunk.

| Configuration | Outcome When a Later Delegate Fails |
|---|---|
| Two JDBC Writers sharing DataSource and transaction manager | Changes in the chunk can roll back together. |
| Two Writers using two DataSources with two local transaction managers | The Step's transaction does not automatically roll back the other resource. |
| One transactional JDBC Writer and one Writer calling a REST API | The database can roll back; an already-succeeded API call is not automatically undone. |
| Two file writers on the filesystem | No single shared database transaction guarantees both files commit atomically. |
| Writers writing DB and outbox in the same database transaction | Business data and outbox events can commit/roll back together. |

A chunk Step takes one `PlatformTransactionManager` for the chunk transaction. Do not assume merely placing multiple delegates inside CompositeItemWriter makes all resources join that transaction.

For a JDBC operation to join the Step's transaction, `JdbcTemplate` or `JdbcBatchItemWriter` must use the exact `DataSource` managed by the transaction manager. Do not open a separate connection manually and call `commit()` inside a Writer.

## 6. What Happens When One Delegate Fails?

Suppose the composite calls Writer A first and then Writer B. A writes successfully, and B throws an exception:

```text
CompositeItemWriter.write(chunk)
    |
    +--> Writer A: write succeeded
    |
    +--> Writer B: exception
              |
              v
        Exception returns to Step
              |
              v
        Chunk transaction rollback
              |
              v
        Retry / Skip / Job FAILED
```

If A and B write to the same database transaction, rollback undoes A's changes. If A already sent an HTTP request or wrote to a resource outside the transaction, A's side effects may persist even though the Step rolls back.

On chunk retry, CompositeItemWriter may call A again. Thus, delegates must be designed to be idempotent if they can produce non-transactional side effects or be re-run after restart.

Do not catch and ignore a delegate's exception just to keep the Job going. If a required output is missing, the Job could report success while targets are inconsistent. Only skip when business rules allow it and the state of remaining outputs is explicitly handled.

## 7. Distinguishing CompositeItemWriter and ClassifierCompositeItemWriter

These two mechanisms have different purposes:

| Mechanism | How It Works | When to Use |
|---|---|---|
| `CompositeItemWriter` | Sends the entire chunk to each delegate in order | Each item must be written to multiple outputs. |
| `ClassifierCompositeItemWriter` | Picks a Writer per item via classifier | Each item is sent to only one appropriate output. |

Routing example:

```text
Item A (priority)   -> PriorityWriter
Item B (standard)   -> StandardWriter
Item C (priority)   -> PriorityWriter
```

If you use CompositeItemWriter with `PriorityWriter` and `StandardWriter` as delegates, both will receive all items. That would produce wrong data. For routing, use a classifier to select a delegate based on item attributes.

If the requirement is both routing an item to one Writer and writing an audit for all items, you can combine a routing writer with an audit writer or handle it in a specialized Processor/Writer. Clarify which items belong in each output before choosing a pattern.

## 8. Ensuring Write Order Between Delegates

The composite calls delegates in configured order. This order can matter if a later Writer depends on results from an earlier Writer, for example:

1. Write parent record.
2. Write child record referencing the parent record's key.
3. Write audit or outbox event.

Example:

```java
.delegates(List.of(
        parentWriter,
        childWriter,
        auditWriter))
```

However, call order does not mean per-delegate commits. Within the same transaction, all operations still wait for the chunk transaction to commit. If `childWriter` fails, `parentWriter`'s operations can roll back with the chunk.

Do not let one delegate depend on an earlier delegate having committed independently unless transaction architecture is explicitly designed for it. For asynchronous communication, an outbox is usually better than calling an external system directly from the next delegate.

## 9. Delegates with ItemStream and Lifecycle

Some Writers implement `ItemStreamWriter` or `ItemStream`, such as `FlatFileItemWriter`. They require `open()`, `update()`, and `close()` lifecycle callbacks to open files, save checkpoints, and release resources.

`CompositeItemWriter` can manage the lifecycle of `ItemStream` delegates by default. `CompositeItemWriterBuilder` has an `ignoreItemStream` option; do not enable it if delegates need checkpoints or resource management. If a custom wrapper/composite does not forward lifecycle callbacks, register delegates via `.stream(...)` on the Step.

General example:

```java
return new StepBuilder("exportStep", jobRepository)
        .<Order, Order>chunk(100, transactionManager)
        .reader(orderReader)
        .writer(compositeWriter)
        .build();
```

When the composite properly manages stream delegates itself, the Step only needs to register the composite. If a custom wrapper does not forward `ItemStream`, you can register the delegate:

```java
.writer(customCompositeWriter)
.stream(fileWriterDelegate)
```

Do not register the same delegate twice if the wrapper already forwards lifecycle callbacks. That can cause `open`, `update`, or `close` to fire repeatedly.

Each stateful delegate needs a stable name and non-conflicting `ExecutionContext` keys. When multiple file writers participate in a Step, give them distinct names and keep them unchanged across restarts.

## 10. Writing to a Database and a File in the Same Step

A common requirement is writing data to a database while simultaneously creating an export file. You can use CompositeItemWriter with `JdbcBatchItemWriter` and `FlatFileItemWriter`:

```java
@Bean
public CompositeItemWriter<Order> databaseAndFileWriter(
        JdbcBatchItemWriter<Order> databaseWriter,
        FlatFileItemWriter<Order> fileWriter) {

    return new CompositeItemWriterBuilder<Order>()
            .delegates(List.of(databaseWriter, fileWriter))
            .build();
}
```

`FlatFileItemWriter` supports transaction-aware buffering and checkpoints when properly configured, lifecycle-registered, and used in a chunk Step. However, the filesystem is not a database resource managed by a local JDBC transaction manager. Do not generalize that all file operations, renames, copies, or deletes roll back atomically with the database.

For critical deliverable files, a safer approach is:

1. Write the file to a temporary name, such as `orders.csv.part`.
2. Complete database and file writes per each resource's transaction semantics.
3. Run a verification step for row counts, checksums, and Job status.
4. Only when the flow succeeds, publish/rename the file to its official name.
5. Write a manifest or `PUBLISHED` status so consumers know the file is ready.

If the file and database must reflect the same business result, have a handling procedure for when one succeeds and the other fails. Staging and publishing last is usually easier to operate than assuming the filesystem and database share one transaction.

## 11. Writing to Multiple Databases

If delegates use different databases, a local `DataSourceTransactionManager` only manages one DataSource. CompositeItemWriter does not provide a distributed transaction on its own.

Risk example:

```text
Writer A -> Database A: COMMIT succeeded
Writer B -> Database B: error
Step     -> ROLLBACK local transaction

Database A may still retain committed data.
```

If all databases must strictly commit or roll back as one atomic transaction, a JTA/XA transaction coordinator, XA-capable resources, and proper recovery configuration are required. This option carries high operational cost and complexity; test scenarios where the coordinator or a database stops between prepare and commit.

If eventual consistency is acceptable, you can use:

- An outbox to save events to emit inside the source database transaction.
- A separate Consumer/Writer writing to the target database.
- Idempotency keys to detect replayed messages.
- Bounded retries with backoff.
- A reconciliation Step to detect and fix data drift.
- Compensating actions if a step cannot complete.

Splitting targets into multiple Steps also clarifies each stage's state, though it does not automatically create atomicity across Steps. Batch keys, progress status, and safe rerun capabilities are required.

## 12. Transactional Outbox Instead of API Calls in a Composite Writer

If an item must be saved to a database and emit an event, avoid calling a broker/API directly in a delegate and expecting a database transaction to roll back the external request.

Within the same chunk transaction, write business data and an outbox row:

```sql
CREATE TABLE outbox_event (
    event_id VARCHAR(120) PRIMARY KEY,
    event_type VARCHAR(80) NOT NULL,
    payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

```text
Chunk transaction
   |
   +--> BusinessWriter -> UPDATE order
   |
   +--> OutboxWriter   -> INSERT outbox_event
   |
COMMIT
   |
   v
Outbox dispatcher
   |
   +--> Send message to broker/API
   +--> Mark as sent
```

BusinessWriter and OutboxWriter share the same DataSource and transaction manager. If either fails, both the business update and outbox insert roll back. After commit, the dispatcher sends the external event.

The dispatcher may still resend if the broker accepted the message but the app stopped before marking the outbox row sent. Consumers must deduplicate by `event_id` or idempotency key. The outbox prevents losing events between database commit and sending, while idempotent consumers handle duplicate deliveries.

## 13. Idempotency for Each Delegate

When CompositeItemWriter is retried, all delegates may be invoked again from the beginning for that chunk. Thus, each delegate must tolerate replay in a manner suited to its resource.

Measures:

- Database Writer: unique constraints, upserts, or a processed-item table keyed by business key.
- File Writer: checkpoints, stable filenames, and controlled staging/publishing.
- API Writer: server-supported idempotency keys.
- Message Writer: stable event IDs and consumer deduplication.
- Audit Writer: unique key per business event so retries do not create multiple audit records for the same event.

Do not call `UUID.randomUUID()` inside `write()` to generate a new identifier on every attempt. The same item must keep the same key across retries and restarts.

If auditing needs to record every technical attempt for operations, distinguish attempt logs from business audits. Attempt logs can carry execution ID/attempt number; business audits usually need a stable event ID to avoid duplication.

## 14. Exception Handling and Skip/Retry in CompositeItemWriter

An exception from a delegate propagates to the Step. The Step can roll back the chunk and apply retry/skip policies if the exception belongs to configured classes.

Example:

```java
return new StepBuilder("importStep", jobRepository)
        .<Order, Order>chunk(100, transactionManager)
        .reader(orderReader)
        .writer(compositeWriter)
        .faultTolerant()
        .retry(TransientDataAccessException.class)
        .retryLimit(3)
        .skip(InvalidOrderException.class)
        .skipLimit(20)
        .build();
```

Only configure skip for errors that business rules genuinely allow skipping. If delegate A created a non-transactional side effect and then delegate B throws an exception, skipping the item can leave output A present while output B is missing. Targets then become inconsistent.

Do not use `noRollback()` to mask a delegate error without assessing the impact of committing earlier outputs. If a required output fails, normally roll back the chunk and retry/fail per policy while ensuring non-transactional side effects are idempotent.

## 15. Custom Writer Coordinating Multiple Outputs

You can write a custom coordinating Writer when logic is more complex than CompositeItemWriter, such as normalizing items, computing a shared metadata record, or writing conditionally. However, a custom composite must handle exceptions, transactions, and the ItemStream lifecycle properly.

Simple skeleton example:

```java
import org.springframework.batch.item.Chunk;
import org.springframework.batch.item.ItemWriter;

public class OrderFanOutWriter implements ItemWriter<Order> {

    private final ItemWriter<Order> databaseWriter;
    private final ItemWriter<Order> auditWriter;

    public OrderFanOutWriter(
            ItemWriter<Order> databaseWriter,
            ItemWriter<Order> auditWriter) {
        this.databaseWriter = databaseWriter;
        this.auditWriter = auditWriter;
    }

    @Override
    public void write(Chunk<? extends Order> chunk) throws Exception {
        databaseWriter.write(chunk);
        auditWriter.write(chunk);
    }
}
```

This only illustrates fan-out. In real applications, if delegates implement `ItemStream`, a custom wrapper must forward `open`, `update`, `close`, or stream delegates must be registered on the Step. Do not catch exceptions and move to the next delegate after an earlier output failed, unless that is an explicitly designed business policy.

If no special logic is needed, `CompositeItemWriter` is usually easier to maintain than a custom wrapper because it already provides delegate orchestration and lifecycle support.

## 16. Choosing Delegate Order and Designing Required/Optional Outputs

Not all outputs have the same criticality. Classify them:

| Output | Criticality | Error Handling |
|---|---|---|
| Primary business table | Required | Chunk rollback and Job retry/fail. |
| Compliance audit | Usually required | Write in the same transaction as primary data if same database. |
| Outbox event | Required if event emission needed | Write in the same transaction as business data. |
| Secondary report | May be optional | Split into a separate Step and allow regeneration. |
| Notification email | Should usually not gate primary data commit | Send asynchronously via outbox; retry independently. |

If a secondary report fails, there may be no need to roll back completed business data. In that case, splitting the report into a separate Step keeps report failures and retries from repeating primary side effects.

Do not force every output into CompositeItemWriter simply because they originate from the same item. Group outputs needing the same transaction; separate outputs with different lifecycles or criticality into separate Steps or workflows.

## 17. Testing Output Consistency

Tests must verify data across all destinations, especially when one delegate fails after an earlier delegate has written.

Key scenarios:

1. **All delegates succeed:** verify the same business key appears in every required output.
2. **Second delegate fails:** verify the first delegate's database changes roll back if they share a transaction.
3. **Chunk retry:** verify delegates are invoked again without duplicating final data.
4. **Job restart:** fail the Step after several committed chunks, restart the same JobInstance, and inspect all outputs.
5. **Multiple databases:** simulate failure in the second database and verify actual XA or eventual consistency behavior.
6. **File output:** verify temporary files are not published on Job failure; final files only appear when the publish Step succeeds.
7. **Outbox:** verify business rows and outbox rows commit/roll back together; dispatcher replay produces no duplicate effects at consumers.
8. **Concurrency:** two workers with the same business key do not create duplicate data across targets.
9. **Lifecycle:** verify ItemStream delegates receive open/update/close the expected number of times and checkpoints are saved.

Example assertion across two tables in the same database:

```java
Integer orderCount = jdbcTemplate.queryForObject(
        "select count(*) from imported_order where order_id = ?",
        Integer.class,
        "ORD-1001");

Integer auditCount = jdbcTemplate.queryForObject(
        "select count(*) from order_audit where order_id = ? and action = ?",
        Integer.class,
        "ORD-1001",
        "IMPORTED");

assertEquals(1, orderCount);
assertEquals(1, auditCount);
```

To test rollback, configure the audit Writer to throw a controlled exception after the order Writer has run; after Job failure, verify neither table retains changes from the failed chunk. If delegates write to independent resources, write tests that reflect the exact transaction limits of that architecture instead of expecting unsupported rollbacks.

## 18. Common Mistakes

| Mistake | Consequence | Fix |
|---|---|---|
| Thinking Composite creates a distributed transaction | One database/file/API may already have written even when another delegate fails. | Identify transaction resources and use XA/outbox/staging when needed. |
| Confusing fan-out with routing | Every item is written to all delegates when only one target was needed. | Use a classifier writer for per-item routing. |
| Delegates using a different DataSource from transaction manager | Chunk rollback does not undo all changes. | Use the same DataSource/TM or a distributed mechanism. |
| Swallowing delegate exceptions | Job can succeed with missing outputs. | Propagate exceptions to the Step and handle with an explicit policy. |
| Non-idempotent delegates | Retries/restarts can create duplicate side effects. | Business keys, unique constraints, idempotency keys. |
| Ignoring ItemStream lifecycle | File writers or delegates fail to save checkpoints/close resources. | Let the Composite forward lifecycle or register `.stream(...)`. |
| Registering stream delegates twice | Lifecycle callbacks may fire repeatedly. | Register only one lifecycle path per delegate. |
| Sharing an output file across executions | Data can interleave or overwrite. | Create separate files per batch/JobInstance and publish safely. |
| Putting email/API directly in a delegate inside a DB transaction | External side effects do not roll back on chunk error. | Use an outbox and send asynchronously. |
| Using `noRollback()` arbitrarily | Partial outputs may commit while another output fails. | Use only when post-commit state has been proven valid. |

## Conclusion

`CompositeItemWriter` sends the same chunk sequentially to multiple delegates, fitting cases where each item must appear in multiple outputs. Consistency depends on transaction resources: JDBC Writers using the same DataSource and transaction manager can commit/roll back with the chunk; files, APIs, or independent databases do not automatically join one atomic transaction. Keep delegate order intentional, manage the `ItemStream` lifecycle, propagate exceptions to the Step, and make each delegate idempotent. For non-database outputs, use staging/publishing, a transactional outbox, XA/JTA, or reconciliation as required. Test scenarios where later delegates fail, retries, restarts, and concurrency to verify all required outputs reflect a single consistent business outcome.
