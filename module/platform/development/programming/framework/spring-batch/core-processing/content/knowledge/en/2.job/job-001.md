# How does a Job represent a batch process?

In Spring Batch, a `Job` is the unit that describes a batch process at the highest level. A Job groups processing steps (`Step`) into a workflow with a clear purpose, such as importing order data, calculating daily revenue, or generating an end-of-month report. A Job specifies which steps the process consists of and in what order or under what conditions they are controlled.

The key distinction is that a **Job describes the process**, while a specific run of the process is represented by Spring Batch with execution objects such as `JobInstance` and `JobExecution`. Because the definition is separated from the run, the same Job can be run for many days of data, be tracked, and be restarted when a run fails.

## 1. A Job is the definition of a batch process

Imagine a daily revenue processing workflow made up of three tasks:

1. Check whether the sales data file is valid.
2. Read the transactions, calculate the total revenue, and store the result.
3. Generate a report for other systems to consume.

In Spring Batch, this entire process can be represented by a Job named `dailySalesJob`. Each independent task inside it is represented by a Step:

```text
dailySalesJob (Job)
    |
    +--> validateInputStep (Step)
    |
    +--> aggregateSalesStep (Step)
    |
    +--> publishReportStep (Step)
```

The Job is responsible for linking the Steps into a complete process. It describes the starting point, the execution order, and the control branches if the process needs to branch. Each Step focuses on performing one specific part of the work.

Therefore, a Job is not the same as a SQL statement, a Java function, or one run of the application. A Job is a process model that Spring Batch can launch and manage. A Job is usually declared as a bean in the Spring configuration and has a stable name so that the system can identify it.

## 2. A Job is composed of Steps and control flow

A `Step` is the basic processing unit inside a Job. A Job usually consists of one or more Steps. Depending on the requirements, each Step can process data in chunks or perform a single task.

### Sequential processing

The simplest case is Steps running one after another. The next Step starts only when the previous Step finishes according to the defined flow:

```text
Job
  |
  v
Step 1: Validate input
  |
  v
Step 2: Process records
  |
  v
Step 3: Publish result
  |
  v
Job completed
```

For example, a report should not be generated if the input data has not been validated and processed successfully. Separating the tasks into individual Steps makes the process explicit and allows Spring Batch to track the status of each part.

### Branching based on results

Not every Job runs along a straight line. The result of one Step can determine the next Step. For example, after validating the input file:

```text
                 +--> valid ----> Process data ----> Publish report
                 |
Job --> Validate -+
                 |
                 +--> invalid --> Reject input
```

Spring Batch supports defining conditional flows based on the exit status (`ExitStatus`) of a Step, or using a `JobExecutionDecider` when a decision needs to be made with custom logic. A Job can also organize more complex Step flows, for example running independent branches in parallel when the business logic allows it.

This shows that a Job is not just a list of Steps. A Job also represents **how the parts of the work relate to each other across the whole process**.

## 3. Declaring a Job in Java

With Spring Batch 5 and later, you can use `JobBuilder` to create a Job and chain Steps in order. The following example illustrates the definition of the daily revenue process:

```java
import org.springframework.batch.core.Job;
import org.springframework.batch.core.Step;
import org.springframework.batch.core.job.builder.JobBuilder;
import org.springframework.batch.core.repository.JobRepository;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class DailySalesJobConfig {

    @Bean
    public Job dailySalesJob(
            JobRepository jobRepository,
            Step validateInputStep,
            Step aggregateSalesStep,
            Step publishReportStep) {

        return new JobBuilder("dailySalesJob", jobRepository)
                .start(validateInputStep)
                .next(aggregateSalesStep)
                .next(publishReportStep)
                .build();
    }
}
```

In this example:

- `dailySalesJob` is the identifying name of the Job.
- `JobRepository` provides the metadata store used to manage and track runs.
- `start(validateInputStep)` specifies the first Step.
- The `next(...)` calls chain the subsequent Steps into the processing flow.
- `build()` completes the creation of the Job definition.

The Steps passed into the Job have already been declared in their respective configurations. The detailed processing of each Step lives in that Step itself; the Job focuses on describing the overall structure and execution flow.

## 4. Distinguishing Job, JobInstance, and JobExecution

These are the three most important concepts for understanding how Spring Batch represents a process and its runs.

| Concept | Meaning | Example |
|---|---|---|
| `Job` | The definition of a batch process, including a name and a Step flow | `dailySalesJob` |
| `JobInstance` | A logical run identified by the Job name and the identifying JobParameters | `dailySalesJob` for the date `2026-11-15` |
| `JobExecution` | A specific attempt to execute a JobInstance | The first run failed, the next run was a restart |

### How is a JobInstance identified?

When launching a Job, the application passes in parameters (`JobParameters`). Spring Batch uses the Job name together with the parameters marked as identifying (*identifying parameters*) to determine the `JobInstance`.

For example, if `businessDate` is an identifying parameter:

```text
dailySalesJob + businessDate=2026-11-15
    = JobInstance A

dailySalesJob + businessDate=2026-11-16
    = JobInstance B
```

Two business dates produce two different JobInstances, even though they use the same Job definition. Conversely, if you launch `dailySalesJob` again with the same identifying parameters for the date `2026-11-15`, Spring Batch recognizes it as the same JobInstance.

Not every JobParameter has to take part in determining identity. A parameter can be marked as non-identifying; in that case it does not cause a new JobInstance to be created. The choice of identifying parameters must correctly reflect one unit of business work, for example the data date, a reconciliation period code, or an import batch code.

### One JobInstance can have multiple JobExecutions

A `JobExecution` records one attempt to run a JobInstance. If the first run fails and the process is validly restarted, Spring Batch creates a new JobExecution for the same JobInstance:

```text
Job: dailySalesJob
  |
  +--> JobInstance: businessDate=2026-11-15
         |
         +--> JobExecution #1: FAILED
         |
         +--> JobExecution #2: COMPLETED
```

Therefore, a JobInstance represents the *logical work that needs to be completed*, while a JobExecution represents *one attempt to perform that work*. A Job can have multiple JobInstances for different sets of identifying parameters; each JobInstance can have multiple JobExecutions if restarts are needed.

If a JobInstance has already completed, Spring Batch normally does not allow it to be run again with the same identifying parameters as if it were a new job. To process a new unit of work, you need to use appropriate identifying parameters to create a new JobInstance. If the JobInstance is currently running, a duplicate launch is also usually rejected to avoid two executions of the same instance running concurrently.

## 5. Who launches the Job and who stores the state?

A Job definition does not run by itself. When the application wants to execute the process, the `JobLauncher` receives the Job together with the `JobParameters` and asks Spring Batch to launch it. The Job invocation can be triggered from the application, a periodic schedule, or an external orchestration mechanism.

The main components have different roles:

| Component | Role |
|---|---|
| `Job` | Defines the process and the flow of Steps |
| `JobLauncher` | Launches a Job with a set of JobParameters |
| `JobRepository` | Stores the metadata of JobInstance, JobExecution, StepExecution, and ExecutionContext |
| `JobParameters` | Provides input data for a launch and determines the JobInstance through the identifying parameters |
| `Step` | Performs one part of the work in the process |

The overall flow can be pictured as follows:

```text
Application / Scheduler
        |
        v
   JobLauncher
        |
        | Job + JobParameters
        v
      Job
        |
        v
   JobExecution
        |
        +------> The Steps / StepExecution
        |
        v
   JobRepository
   (stores metadata)
```

The `JobRepository` stores information for managing the run, such as start and end times, status, result, execution errors, the number of records read/written by a Step, and checkpoint data. It does not replace the application's business data store. For example, order data is still stored in the business tables; the JobRepository stores information that tells how far the order import process has progressed.

## 6. A Job supports tracking and restarting the process

An important benefit of representing a process with a Job and Steps is that Spring Batch can save the execution progress. Each `JobExecution` has a status such as `STARTING`, `STARTED`, `COMPLETED`, `FAILED`, or `STOPPED`. Each Step also has its own execution status through `StepExecution`.

For example, a Job has three Steps and the second Step encounters an error:

```text
dailySalesJob
  |
  +--> validateInputStep     COMPLETED
  |
  +--> aggregateSalesStep    FAILED
  |
  +--> publishReportStep     not executed
```

This information helps operators know where the process failed. When restarting the same JobInstance, Spring Batch can use the saved metadata and checkpoints to continue according to the Step's configuration. The ability to resume precisely depends on how the Step is designed, the state that is saved, and whether the operation is safe to repeat.

With chunk-oriented processing, Spring Batch typically saves state at commit boundaries. The `ExecutionContext` can hold the information needed to restore progress, such as the next read position. However, you should not assume that all code automatically resumes exactly at the statement that failed. Operations that write to external systems, send notifications, or update data need to be designed to tolerate retries, usually with an appropriate transaction, duplicate checks, or idempotent handling.

A Job can also be configured not to allow restarts. Therefore, restartability depends both on the Job's policy and on whether the Steps save and restore state safely.

## 7. BatchStatus and ExitStatus have different roles

When observing a run, you need to distinguish the execution status from the exit result used to control the flow:

- `BatchStatus` describes the execution status of a JobExecution or StepExecution, for example `COMPLETED`, `FAILED`, or `STOPPED`.
- `ExitStatus` represents the exit result code. A Job can use this code to decide the next flow, for example going to the branch that handles invalid data.

The two concepts are related but not interchangeable. `BatchStatus` answers the question of what state the execution is in; `ExitStatus` provides a result that the control flow can use. When branching is needed, you should design clear exit codes so that the Job's routing rules are easy to understand and operate.

## 8. Example of launching a Job

Suppose a Job processes sales data by day. The application can create a business date parameter and pass the Job together with that parameter to the `JobLauncher`:

```java
import org.springframework.batch.core.Job;
import org.springframework.batch.core.JobParameters;
import org.springframework.batch.core.JobParametersBuilder;
import org.springframework.batch.core.launch.JobLauncher;
import org.springframework.stereotype.Component;

@Component
public class DailySalesJobRunner {

    private final JobLauncher jobLauncher;
    private final Job dailySalesJob;

    public DailySalesJobRunner(
            JobLauncher jobLauncher,
            Job dailySalesJob) {
        this.jobLauncher = jobLauncher;
        this.dailySalesJob = dailySalesJob;
    }

    public void runForDate(String businessDate) throws Exception {
        JobParameters parameters = new JobParametersBuilder()
                .addString("businessDate", businessDate)
                .toJobParameters();

        jobLauncher.run(dailySalesJob, parameters);
    }
}
```

With this declaration, `businessDate` is added as an identifying parameter by default. Calling `runForDate("2026-11-15")` requests a run of the Job for that date. Calling it with a different date creates a different JobInstance. Calling it again with the same date refers to the existing JobInstance; the specific outcome depends on the previous state, for example whether the earlier run completed or failed.

The example above illustrates how a Job is launched. In a real application, the trigger can be integrated with a scheduler or an API; the Spring Batch infrastructure configuration and whether it runs synchronously or asynchronously depend on the deployment environment.

## 9. Common misconceptions

| Misconception | Correct understanding |
|---|---|
| A Job is a single run | A Job is the process definition; a JobExecution is a specific execution. |
| Each day's run is a different Job | You can use the same Job; each day creates its own JobInstance if the date is an identifying parameter. |
| A Job contains all of the data processing code | A Job organizes Steps; the logic for reading, processing, and writing data usually lives in each Step. |
| JobRepository stores business data | JobRepository stores metadata and execution state; business data has its own store. |
| A restart always resumes from exactly the line that failed | Resuming depends on checkpoints, ExecutionContext, restart configuration, and the Step's design for safe retries. |
| `COMPLETED` and `ExitStatus` are the same concept | `BatchStatus` describes the execution status; `ExitStatus` represents the exit result and can take part in controlling the flow. |

## 10. How to design a Job for a real process

When turning a business requirement into a Job, you can start by describing the process end to end, then split it into Steps according to clear responsibilities and processing boundaries.

Some useful principles:

1. **Name the Job after its business purpose.** Names such as `dailySalesJob` or `customerImportJob` help identify the process in metadata and logs.
2. **Split Steps by meaningful work.** Input validation, record processing, and result output are usually responsibilities that can be tracked independently.
3. **Choose JobParameters that reflect the unit of processing.** A business date, batch code, or data period can be an identifying parameter if it determines a single logical job.
4. **Clearly define the branches and end conditions.** A Step's result code should be able to express the business scenarios that need routing.
5. **Design for retry and restart.** Determine the checkpoint data, the transaction boundaries, and how to avoid duplicate writes when a Step is run again.
6. **Keep the Job focused on orchestration.** Put detailed processing logic into Steps or appropriate business components so that each part is easy to understand and maintain.

A well-designed Job lets developers see the whole process in the configuration, while operators can track each run through the metadata that Spring Batch manages.

## Conclusion

In Spring Batch, a `Job` represents a complete batch process by combining Steps and defining the control flow between them. When launched with `JobParameters`, that definition produces a `JobInstance` for one logical unit of work; each execution attempt is recorded as a `JobExecution`. The `JobLauncher` launches the process, while the `JobRepository` stores metadata for tracking, inspection, and restart support. This organization gives a batch process a clear structure and makes it observable and manageable across multiple runs.
