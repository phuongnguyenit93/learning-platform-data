# JAXB or marshallers in XML processing

In Spring Batch, XML input/output is commonly handled using StAX components combined with an object-to-XML mapping mechanism. **JAXB** is a popular binding technology: it converts XML into Java objects when reading and converts Java objects into XML when writing. Spring provides the `Marshaller` and `Unmarshaller` abstractions in Spring OXM so Spring Batch can use JAXB or another mapping technology.

For large XML files, the typical pattern uses `StaxEventItemReader` to read each XML fragment and `StaxEventItemWriter` to write each item as a fragment. `Jaxb2Marshaller` handles mapping fragments to and from Java classes. This separation enables chunk-based data processing, transaction/checkpoint management, and avoids loading the entire XML document into memory.

## 1. What are JAXB, Marshaller, and Unmarshaller?

JAXB (Jakarta XML Binding in newer versions) is a mapping mechanism between XML and Java objects based on metadata such as annotations or binding configurations.

Two main operations:

- **Unmarshal:** read XML and create Java objects.
- **Marshal:** convert Java objects into XML.

XML example:

```xml
<customer>
    <id>C001</id>
    <name>Nguyen An</name>
    <email>an@example.com</email>
</customer>
```

The corresponding Java object can be described with JAXB annotations. During unmarshalling, the XML is converted into a `CustomerXml`. During marshalling, the object is converted back into XML elements according to the mapping.

In Spring OXM:

| Component | Responsibility |
|---|---|
| `Marshaller` | Converts Java objects into XML. |
| `Unmarshaller` | Converts XML into Java objects. |
| `Jaxb2Marshaller` | Spring OXM adapter that uses JAXB to perform both marshalling and unmarshalling. |
| `StaxEventItemReader` | Reads XML fragment by fragment and calls `Unmarshaller` to create items. |
| `StaxEventItemWriter` | Calls `Marshaller` to write items as XML fragments. |

`Marshaller` and `Unmarshaller` are Spring OXM abstractions. As a result, Spring Batch readers/writers do not have to depend directly on JAXB APIs in their file orchestration logic.

## 2. JAXB models and annotations

JAXB needs to know how to map XML elements/attributes to Java class properties. You can use annotations such as `@XmlRootElement`, `@XmlAccessorType`, `@XmlElement`, `@XmlAttribute`, and `@XmlType`.

Model example:

```java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;
import jakarta.xml.bind.annotation.XmlType;

@XmlRootElement(name = "customer")
@XmlAccessorType(XmlAccessType.FIELD)
@XmlType(propOrder = {"id", "name", "email"})
public class CustomerXml {

    @XmlElement(required = true)
    private String id;

    private String name;

    private String email;

    public CustomerXml() {
    }

    public CustomerXml(String id, String name, String email) {
        this.id = id;
        this.name = name;
        this.email = email;
    }

    public String getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public String getEmail() {
        return email;
    }
}
```

Commonly used annotations:

| Annotation | Meaning |
|---|---|
| `@XmlRootElement` | Declares the root element name representing the class. |
| `@XmlAccessorType` | Specifies whether JAXB accesses fields or properties. |
| `@XmlElement` | Maps a field/property to an XML element. |
| `@XmlAttribute` | Maps a field/property to an XML attribute. |
| `@XmlType` | Controls element order and XML type name. |
| `@XmlTransient` | Excludes a field/property from binding. |
| `@XmlElementWrapper` | Creates a wrapper element around a collection. |

In the example, `@XmlAccessorType(XmlAccessType.FIELD)` instructs JAXB to bind fields directly. A no-arg constructor lets JAXB instantiate objects in the standard way. If using property access or custom adapters, configure them according to your model.

## 3. Differences between javax.xml.bind and jakarta.xml.bind

This is an important point when upgrading Spring Batch or Spring Framework:

- Legacy Java EE/JAXB applications commonly use the `javax.xml.bind.*` package.
- Spring Framework 6 and Spring Batch 5 belong to the Jakarta ecosystem and use `jakarta.xml.bind.*`.
- Spring Batch 4/Spring Framework 5 typically use the `javax` APIs.

Do not mix both package families in the same binding model. A class annotated with `javax.xml.bind.annotation.XmlRootElement` is not equivalent to `jakarta.xml.bind.annotation.XmlRootElement` for a Jakarta JAXB runtime.

On Java 11 and later, JAXB is no longer bundled in the JDK as in older Java versions. Applications must declare the appropriate API and runtime via dependency management. With Spring Boot, let Boot's BOM manage compatible versions.

## 4. Configuring Jaxb2Marshaller

`Jaxb2Marshaller` is Spring OXM's implementation for JAXB. You can configure the list of bound classes:

```java
@Bean
Jaxb2Marshaller customerMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(CustomerXml.class);
    return marshaller;
}
```

Or scan packages containing JAXB models:

```java
@Bean
Jaxb2Marshaller customerMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setPackagesToScan("com.example.batch.xml.model");
    return marshaller;
}
```

Choose one configuration approach clearly. `setClassesToBeBound` is suitable when the number of classes is small and you want exact control over supported types. `setPackagesToScan` is convenient when a package holds many JAXB models.

You can configure properties for marshalling:

```java
@Bean
Jaxb2Marshaller customerMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(CustomerXml.class);
    marshaller.setMarshallerProperties(Map.of(
            jakarta.xml.bind.Marshaller.JAXB_FORMATTED_OUTPUT, true));
    return marshaller;
}
```

`JAXB_FORMATTED_OUTPUT` requests formatted XML for readability. In production, pretty formatting can make files larger; if output is only meant for machine consumption, you can choose a compact configuration as appropriate.

## 5. Reading XML with StaxEventItemReader and JAXB

`StaxEventItemReader<T>` uses StAX to iterate through the XML stream and extract fragments with the specified root element. Each fragment is passed to the `Unmarshaller` to produce an item of type `T`.

Example input file containing multiple customers:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<customers>
    <customer>
        <id>C001</id>
        <name>Nguyen An</name>
        <email>an@example.com</email>
    </customer>
    <customer>
        <id>C002</id>
        <name>Tran Binh</name>
        <email>binh@example.com</email>
    </customer>
</customers>
```

The reader can be configured as follows:

```java
@Bean
@StepScope
StaxEventItemReader<CustomerXml> customerReader(
        @Value("#{jobParameters['inputFile']}") String inputFile,
        Jaxb2Marshaller customerMarshaller) {

    StaxEventItemReader<CustomerXml> reader = new StaxEventItemReader<>();
    reader.setName("customerReader");
    reader.setResource(new FileSystemResource(inputFile));
    reader.setFragmentRootElementName("customer");
    reader.setUnmarshaller(customerMarshaller);
    reader.setSaveState(true);
    return reader;
}
```

The reader does not need to unmarshal the entire `<customers>` element into a collection. It reads each `<customer>` fragment and returns one `CustomerXml` per `read()` call.

`setFragmentRootElementName` determines which element counts as an item. If the file has multiple nesting levels, pick the right element to avoid reading the wrong fragment. For XML with namespaces, test how the reader recognizes fragments by local name/namespace in your version and configure the XML accordingly.

## 6. XML fragments and document root

A well-formed XML document has exactly one root element. However, each Spring Batch item is usually only a child fragment within that document.

Example:

```xml
<orders>
    <order>...</order>
    <order>...</order>
    <order>...</order>
</orders>
```

In the reader configuration:

- `<orders>` is the root of the entire document.
- `<order>` is the fragment root for each item.
- The JAXB model `OrderXml` describes one `<order>`.

If you choose `orders` as the fragment root, the reader may treat the entire collection as a single item rather than individual orders. If you choose the wrong element name, the reader may return no items or return an unintended structure.

When XML contains multiple record types, such as `<customer>` and `<address>`, decide which type the step should read. You can configure the appropriate fragment root or design separate models/writers per record type. Avoid trying to unmarshal completely different elements into an incompatible class.

## 7. Writing XML with StaxEventItemWriter and JAXB

`StaxEventItemWriter<T>` writes each item as an XML fragment using a `Marshaller`. The writer typically creates a root tag wrapping the fragments so the result is a valid XML document.

Example:

```java
@Bean
@StepScope
StaxEventItemWriter<CustomerXml> customerWriter(
        @Value("#{jobParameters['outputFile']}") String outputFile,
        Jaxb2Marshaller customerMarshaller) {

    StaxEventItemWriter<CustomerXml> writer = new StaxEventItemWriter<>();
    writer.setName("customerWriter");
    writer.setResource(new FileSystemResource(outputFile));
    writer.setMarshaller(customerMarshaller);
    writer.setRootTagName("customers");
    writer.setOverwriteOutput(true);
    writer.setSaveState(true);
    return writer;
}
```

With two items, the output looks like:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<customers>
    <customer>
        <id>C001</id>
        <name>Nguyen An</name>
        <email>an@example.com</email>
    </customer>
    <customer>
        <id>C002</id>
        <name>Tran Binh</name>
        <email>binh@example.com</email>
    </customer>
</customers>
```

`rootTagName` is the root of the entire output; `@XmlRootElement(name = "customer")` specifies the fragment name produced by JAXB marshalling. These two settings serve different roles.

`setOverwriteOutput(true)` allows the writer to write new output over an existing resource on a fresh run according to the writer's policy. For restartable jobs, keep state and resource stable; do not treat overwrite as a directive to delete the file on every open, including restarts. Test the writer lifecycle with JobRepository and checkpoints.

## 8. Combining reader, processor, and writer in a chunk step

XML readers and writers are used like standard item components in a chunk-oriented step.

```java
@Bean
Step transformCustomersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        StaxEventItemReader<CustomerXml> customerReader,
        ItemProcessor<CustomerXml, CustomerXml> customerProcessor,
        StaxEventItemWriter<CustomerXml> customerWriter) {

    return new StepBuilder("transformCustomersStep", jobRepository)
            .<CustomerXml, CustomerXml>chunk(100, transactionManager)
            .reader(customerReader)
            .processor(customerProcessor)
            .writer(customerWriter)
            .build();
}
```

With a chunk size of 100, the step reads and processes up to 100 items per chunk and then calls the writer. Transaction boundaries are managed by the step and transaction manager. The XML reader/writer manage streams and state according to the `ItemStream` contract.

The processor can convert `CustomerXml` to a domain model or validate data. Separate the XML transport model from the domain model when the partner's XML structure differs from your internal data structure.

## 9. Separating XML DTOs and domain objects

You do not have to put JAXB annotations directly on entities or domain models. A clean architecture often has two layers:

```text
XML document
     |
     v
JAXB model / transport DTO
     |
     v
ItemProcessor mapping + validation
     |
     v
Domain model
     |
     v
Writer / database / downstream system
```

Example:

```java
public record Customer(
        String customerId,
        String displayName,
        String emailAddress) {
}

@Bean
ItemProcessor<CustomerXml, Customer> customerProcessor() {
    return xml -> {
        if (xml.getId() == null || xml.getId().isBlank()) {
            throw new InvalidCustomerException("Customer id is required");
        }

        return new Customer(
                xml.getId().trim(),
                xml.getName() == null ? "" : xml.getName().trim(),
                xml.getEmail());
    };
}
```

Benefits of separating DTOs:

- The XML schema can change without forcing the domain model to change with it.
- JAXB annotations do not leak into entities or business services.
- Easy to unit-test mapping and validation independently.
- Multiple input XML versions can be supported via different DTOs/adapters.
- The domain model does not have to follow the no-arg constructor or property access requirements imposed by JAXB.

For simple batch jobs, using the JAXB model directly as the item may be enough. For long-term integrations or multiple partners, separating the layers usually makes change control easier.

## 10. XML attributes, elements, and collections

JAXB supports mapping XML attributes and elements.

XML example:

```xml
<order id="O-100" status="NEW">
    <customerId>C001</customerId>
    <lines>
        <line>
            <sku>SKU-01</sku>
            <quantity>2</quantity>
        </line>
        <line>
            <sku>SKU-02</sku>
            <quantity>1</quantity>
        </line>
    </lines>
</order>
```

The JAXB model can be declared as:

```java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    @XmlAttribute(name = "id")
    private String id;

    @XmlAttribute(name = "status")
    private String status;

    @XmlElement(name = "customerId")
    private String customerId;

    @XmlElementWrapper(name = "lines")
    @XmlElement(name = "line")
    private List<OrderLineXml> lines = new ArrayList<>();

    public OrderXml() {
    }
}
```

The `OrderLineXml` model further declares `sku` and `quantity`. `@XmlElementWrapper` maps the `<lines>` container, while `@XmlElement` maps each `<line>`.

When a large collection sits inside a very large fragment, unmarshalling that fragment can still consume significant memory. The StAX reader splits by fragment root and does not automatically split nested collections. Choose a fragment root aligned with the business unit of work.

## 11. Namespaces in JAXB

XML integrated between systems often uses namespaces:

```xml
<customers xmlns="urn:example:customer:v1">
    <customer>
        <id>C001</id>
        <name>Nguyen An</name>
    </customer>
</customers>
```

The JAXB model needs to declare the corresponding namespace:

```java
@XmlRootElement(name = "customer", namespace = "urn:example:customer:v1")
@XmlAccessorType(XmlAccessType.FIELD)
public class CustomerXml {

    @XmlElement(namespace = "urn:example:customer:v1")
    private String id;

    @XmlElement(namespace = "urn:example:customer:v1")
    private String name;

    public CustomerXml() {
    }
}
```

You can use `package-info.java` with `@XmlSchema` to set a default namespace for the model package. This avoids repeating the namespace on every field.

When reading namespaced XML, check whether `StaxEventItemReader`'s fragment selection matches the element name and namespace in the document. Setting only `fragmentRootElementName("customer")` without checking namespaces may not suffice for all formats/versions. Use real namespaced XML fixtures in integration tests.

When writing, namespaces and prefixes can affect consumer compatibility. Prefixes usually carry no semantic difference if the namespace URI is the same, but some legacy systems make specific assumptions. Verify the output against the XSD and integration contract.

## 12. XML schema validation

JAXB binding defines how elements map to fields, but does not automatically guarantee that all partner XSD rules are satisfied unless validation is configured.

`Jaxb2Marshaller` can be configured with schema resources to validate XML during marshalling/unmarshalling:

```java
@Bean
Jaxb2Marshaller customerMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(CustomerXml.class);
    marshaller.setSchemas(
            new ClassPathResource("xsd/customer-v1.xsd"));
    return marshaller;
}
```

When schema validation is enabled, XML that does not conform to the schema can fail unmarshalling. Marshalled output can also be rejected if it violates the schema. Test both valid and invalid documents.

Schema validation can be CPU-intensive. For large files, measure performance and pick the right place to validate. If you need per-item error reporting, read by fragment and catch exceptions per fragment; if schema errors apply to the whole-document structure, a full-file validation step before processing may be required.

## 13. Business validation after unmarshalling

Schema validation and business validation are two separate layers:

- XSD checks XML structure, elements, attributes, data types, and cardinality against the schema.
- Business validation checks rules such as whether the customer ID exists, whether the amount must be positive, or whether the order status is valid.

For example, XSD can verify `<amount>` is a decimal. Only the processor or a business validator knows whether an order is allowed to have an amount of 0.

Classify errors clearly:

- Malformed XML or unmarshallable fragment: parsing/mapping error.
- Schema-valid XML that violates business rules: business validation error.
- Unavailable database or API: infrastructure error.

A skip policy may allow skipping specific item errors, but should not skip every exception from JAXB or StAX. If the entire file has the wrong namespace/schema, continuing to skip fragment after fragment can discard most of the data.

## 14. Encoding and XML declaration

Encoding must be consistent across the file, XML declaration, and resource reader/writer.

XML declaration example:

```xml
<?xml version="1.0" encoding="UTF-8"?>
```

For the writer, you can configure the encoding:

```java
writer.setEncoding("UTF-8");
```

For the reader, the StAX parser reads XML using the encoding declared in the XML declaration or determined from the resource/parser configuration. Do not convert the file into a String using the machine's default charset before passing it to the parser.

Points to verify:

- Whether the source file actually uses UTF-8, UTF-16, or a legacy charset.
- Whether the XML declaration matches the actual encoding.
- Whether Vietnamese diacritical characters and non-ASCII characters are read/written properly.
- Whether the consumer requires an XML declaration, BOM, or specific encoding.
- Whether any intermediate step unintentionally alters the charset or line endings.

## 15. XML parser security

XML can contain DTDs or external entities. If the parser allows resolving external entities, untrusted documents can cause the application to read local files or make unintended network calls (XXE).

With StAX, configure `XMLInputFactory` to disable DTDs and external entities if the application does not need those features:

```java
XMLInputFactory inputFactory = XMLInputFactory.newFactory();
inputFactory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
inputFactory.setProperty(
        "javax.xml.stream.isSupportingExternalEntities", false);

StaxEventItemReader<CustomerXml> reader = new StaxEventItemReader<>();
reader.setName("customerReader");
reader.setResource(resource);
reader.setFragmentRootElementName("customer");
reader.setUnmarshaller(customerMarshaller);
reader.setXmlInputFactory(inputFactory);
```

Supported properties may depend on the StAX provider. Test the configuration against the actual provider and verify the parser rejects or does not resolve external entities as expected. Do not rely on production environment defaults.

If XSDs import/include external resources, manage schema resources via trusted configuration or a suitable resolver; do not open arbitrary network access just to make validation work.

## 16. Handling marshal/unmarshal errors

XML errors can arise at multiple stages:

| Stage | Error examples |
|---|---|
| StAX parse | Malformed XML, unclosed tags, encoding error. |
| Fragment selection | Target element not found or wrong root selected. |
| JAXB unmarshal | Unmappable element/attribute, conversion failure, schema violation. |
| Processor | XML parsed cleanly but violates business rules. |
| JAXB marshal | Object missing required data or invalid mapping. |
| File output | No write permission, disk full, I/O error. |

Do not configure skip for all `Exception` types. Syntax errors early in the document can prevent the parser from locating subsequent fragments. I/O errors or marshaller configuration errors are usually step-stopping failures.

If only a single fragment is invalid and the parser can safely continue, you can design a per-item error logging mechanism. However, not all StAX/JAXB errors allow the reader to recover position and continue. Test with real malformed files and determine explicitly whether the reader can proceed after an exception.

## 17. Dependencies for JAXB and Spring OXM

In applications using Spring Batch 5/Spring Framework 6, you can declare Spring OXM and an appropriate JAXB runtime:

```groovy
dependencies {
    implementation("org.springframework:spring-oxm")
    runtimeOnly("org.glassfish.jaxb:jaxb-runtime")
}
```

In many Spring Boot projects, dependency management controls versions for Spring Framework and the JAXB runtime. Without a BOM, pick versions compatible with the Jakarta JAXB API required by Spring OXM.

`spring-batch-infrastructure` provides Spring Batch's XML readers/writers; `spring-oxm` provides the abstractions and `Jaxb2Marshaller`. Verify the required modules are present in the application's dependency graph.

## 18. Testing Jaxb2Marshaller independently

You can verify JAXB bindings without launching a job. Test marshalling an object to XML and unmarshalling it back to confirm the mapping.

```java
class CustomerMarshallerTest {

    private final Jaxb2Marshaller marshaller = new Jaxb2Marshaller();

    @BeforeEach
    void setUp() throws Exception {
        marshaller.setClassesToBeBound(CustomerXml.class);
        marshaller.afterPropertiesSet();
    }

    @Test
    void marshalsAndUnmarshalsCustomer() throws Exception {
        CustomerXml customer = new CustomerXml(
                "C001", "Nguyen An", "an@example.com");

        StringWriter output = new StringWriter();
        marshaller.marshal(customer, new StreamResult(output));

        String xml = output.toString();
        assertThat(xml).contains("<customer>");
        assertThat(xml).contains("<id>C001</id>");

        CustomerXml restored = (CustomerXml) marshaller.unmarshal(
                new StreamSource(new StringReader(xml)));

        assertThat(restored.getId()).isEqualTo("C001");
        assertThat(restored.getName()).isEqualTo("Nguyen An");
    }
}
```

This test only verifies JAXB mapping and does not test Spring Batch's StAX reader/writer. If classes use namespaces, adapters, or schema validation, add XML fixtures demonstrating those cases.

## 19. Testing StaxEventItemReader

Reader tests should verify fragment discovery and per-item unmarshalling. Use XML fixtures with multiple records and edge cases:

```java
@Test
void readsEachCustomerFragment() throws Exception {
    StaxEventItemReader<CustomerXml> reader = new StaxEventItemReader<>();
    reader.setName("customerReader");
    reader.setResource(new ClassPathResource("customers.xml"));
    reader.setFragmentRootElementName("customer");
    reader.setUnmarshaller(customerMarshaller);

    reader.afterPropertiesSet();
    reader.open(new ExecutionContext());
    try {
        CustomerXml first = reader.read();
        CustomerXml second = reader.read();
        CustomerXml end = reader.read();

        assertThat(first.getId()).isEqualTo("C001");
        assertThat(second.getId()).isEqualTo("C002");
        assertThat(end).isNull();
    } finally {
        reader.close();
    }
}
```

Tests should cover:

- Document with multiple fragments.
- Document with no matching fragments.
- Nested fragments or elements sharing names at multiple levels.
- Default namespaces and prefixed namespaces.
- Malformed XML.
- Encoding and Unicode characters.
- Schema validation if enabled.

## 20. Testing StaxEventItemWriter

Writer tests can open the writer, write several items, and inspect the XML output.

```java
@Test
void writesCustomerFragmentsInsideRootElement() throws Exception {
    Path output = tempDir.resolve("customers.xml");

    StaxEventItemWriter<CustomerXml> writer = new StaxEventItemWriter<>();
    writer.setName("customerWriter");
    writer.setResource(new FileSystemResource(output));
    writer.setMarshaller(customerMarshaller);
    writer.setRootTagName("customers");
    writer.setOverwriteOutput(true);

    writer.afterPropertiesSet();
    writer.open(new ExecutionContext());
    try {
        writer.write(Chunk.of(
                new CustomerXml("C001", "Nguyen An", "an@example.com"),
                new CustomerXml("C002", "Tran Binh", "binh@example.com")));
    } finally {
        writer.close();
    }

    String xml = Files.readString(output);
    assertThat(xml).contains("<customers");
    assertThat(xml).contains("<customer>");
    assertThat(xml).contains("<id>C001</id>");
    assertThat(xml).contains("<id>C002</id>");
}
```

In real tests, parse the output file with an XML parser and verify structure/namespaces rather than relying solely on string matching, since XML can vary in whitespace or namespace prefixes while remaining structurally equivalent.

## 21. Integration testing an XML chunk step

Unit tests for marshaller, reader, and writer do not verify transactions, checkpoints, and JobRepository. For critical jobs, add integration tests:

1. Prepare an XML input fixture.
2. Launch the job using JobLauncherTestUtils with JobParameters specifying input/output.
3. Verify JobExecution and StepExecution complete.
4. Parse the output XML and verify item count and values.
5. Simulate an error in one chunk and restart the same JobInstance.
6. Verify the writer does not create duplicate or missing fragments.
7. Check metadata and ExecutionContext if the reader/writer must be restartable.

If the job uses schema validation, namespaces, or XSD imports, tests should run with real schema resources. Minimal synthetic XML unit tests are not enough to verify the XML contract with partner systems.

## 22. When to use JAXB, and when to use another marshaller?

JAXB is suitable when:

- The XML has a schema or relatively stable structure.
- You want to declare mappings using annotations or binding configurations.
- You need to convert XML into strongly-typed Java DTOs.
- You need schema validation and namespace/element control.

Spring OXM abstractions allow using other marshallers/unmarshallers if the project has special requirements. Choose the technology based on format, schema, performance, and maintainability. Do not choose JAXB solely for popularity if the actual data consists of highly flexible XML fragments or needs node-level streaming instead of building large objects.

For very large XML files, avoid unmarshalling a huge root collection into a single object holding all data. Pick a fragment root so each item has a reasonable memory footprint. If a single fragment still contains millions of nested elements, split the format or use specialized StAX cursor/event processing.

## 23. Common pitfalls when using JAXB or marshallers

| Symptom | Common cause | Resolution |
|---|---|---|
| JAXB does not recognize class | Class/package not configured in `Jaxb2Marshaller`. | Use `setClassesToBeBound` or `setPackagesToScan`. |
| `javax` and `jakarta` incompatible | Model and runtime use two different package families. | Align with your Spring Batch/Spring Framework version. |
| Reader returns no items | Wrong fragment root or XML namespaces not handled properly. | Check XML fixture and fragment selection. |
| Whole collection read as one item | Document root selected instead of individual record element. | Select a fragment root like `customer` or `order`. |
| JAXB reports missing constructor | Model does not satisfy JAXB object instantiation requirements. | Provide an appropriate constructor or binding config. |
| Fields always null | Wrong element name, namespace, or annotation access strategy. | Check `@XmlElement`, `@XmlAccessorType`, and namespace URI. |
| Output has wrong root | `rootTagName` and `@XmlRootElement` roles confused. | Writer root wraps the whole document; JAXB root defines the fragment. |
| XML fails schema check | Mapping or data does not conform to XSD. | Enable schema validation and test with the official schema. |
| Vietnamese characters are corrupted | Inconsistent encoding. | Configure proper UTF-8/charset and test Unicode data. |
| Parser accesses external resources | DTD/external entities are enabled. | Disable DTD/external entities and test the StAX provider. |
| Job uses too much memory | Unmarshalling overly large fragments or holding collections in RAM. | Choose a smaller fragment and process in chunks. |
| Restart produces duplicate XML fragments | Writer state not saved/restored or resource changed. | Keep `saveState`, writer name, and output path stable. |
| Mass record skipping | Whole-file error treated as per-item error. | Stop the job and check schema, namespace, encoding, and fragment root. |

## 24. Workflow for implementing XML processing with JAXB

When integrating a new XML file into Spring Batch, you can follow this sequence:

1. **Inspect sample XML and XSD:** identify document root, fragment root, namespace, encoding, and cardinality.
2. **Create JAXB model:** declare elements, attributes, collections, and order according to the schema.
3. **Configure `Jaxb2Marshaller`:** register classes/packages, schemas, and required properties.
4. **Configure StAX reader:** choose resource, fragment root, unmarshaller, encoding, and checkpointing.
5. **Create processor:** convert XML DTO to domain model and run business validation.
6. **Configure StAX writer if needed:** marshaller, root tag, resource, encoding, and save state.
7. **Design fault tolerance:** classify XML, data, and infrastructure errors; only skip item errors recoverable by business rules.
8. **Harden parser:** disable DTD/external entities if unneeded and verify trusted schema resources.
9. **Test components individually:** marshal/unmarshal, fragment reader, writer, namespaces, and schema validation.
10. **Integration test:** run chunk step, transactions, restart, and inspect final XML output.

Keep verified XML fixtures from the source system. Testing on real fixtures often uncovers namespace, padding, element ordering, and encoding issues that simple synthetic XML fails to expose.

## 25. Key takeaways

- JAXB converts between XML and Java objects; marshalling is object-to-XML, unmarshalling is XML-to-object.
- Spring OXM defines the `Marshaller` and `Unmarshaller` abstractions; `Jaxb2Marshaller` implements both using JAXB.
- Spring Batch uses `StaxEventItemReader` to read XML fragments and `StaxEventItemWriter` to write fragments per chunk.
- `fragmentRootElementName` selects the element representing one item; the writer's `rootTagName` wraps fragments into a document.
- JAXB annotations such as `@XmlRootElement`, `@XmlElement`, `@XmlAttribute`, `@XmlAccessorType`, and `@XmlType` describe the mapping.
- Spring Framework 6/Spring Batch 5 use the Jakarta package `jakarta.xml.bind`; older versions may use `javax.xml.bind`. Do not mix them.
- `Jaxb2Marshaller` requires bound classes/packages to be registered and can configure schemas/properties.
- XML schema validation differs from business validation; the processor still needs to enforce domain rules.
- Encoding, namespaces, and fragment selection must match the source/target XML contract.
- For untrusted XML, disable DTD/external entities and verify the StAX provider.
- Pick a reasonably sized fragment root to preserve streaming and chunk processing benefits.
- Readers/writers need state saving and stable resources if jobs must be restartable.
- Test marshaller, reader, writer, and integration steps separately; parse output XML instead of just comparing strings whenever possible.

JAXB or another marshaller handles mapping XML to and from Java objects, while Spring Batch manages how items are read, processed, written in chunks, and recovered on restart. Combining `Jaxb2Marshaller` with StAX readers/writers enables fragment-based XML processing without loading the entire document into memory. For reliable results, define the JAXB model, namespaces, schema, encoding, fragment root, and error policy according to the actual data contract.
