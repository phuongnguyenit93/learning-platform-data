# Reconciling Logs with Metadata in Spring Batch

When a Spring Batch Job runs on a schedule or is invoked via API, the system normally leaves two trails for the same execution: **application logs** and **`JobRepository` metadata**. Logs describe events recorded by application code, listeners, and observability infrastructure; metadata stores the identity, statuses, and execution statistics of `JobInstance`, `JobExecution`, and `StepExecution`.

These two sources complement each other yet are not necessarily updated at the exact same instant. A “job completed” log line can appear before the final update commits to the repository; a `COMPLETED` Job may lack logs if collector connectivity dropped; and when a JVM is killed abruptly, metadata may stay `STARTED` even though the process is gone.

**Reconciling logs with metadata** is the process of joining the right records, reading them in temporal context, and verifying whether they reflect the same processing run. This supports incident investigation, restart verification, detecting missing telemetry, building dashboards, and preparing recovery runbooks.

This lesson belongs to the **Logging** group of **Spring Batch Core Processing**. It walks through the identity model, data collection, querying Spring Batch, reconciliation rules, testing examples, and operations.

## 1. What Do the Two Data Sources Reflect?

### 1.1. Application Logs

Log lines can be emitted when a scheduler requests a Job run, when a listener receives a callback, or when a Step throws an error. Example:

```text
2026-11-16T02:00:00.042Z INFO  batch.job.launch.requested
  jobName=importInvoicesJob businessDate=2026-11-16 trigger=scheduler requestId=rq-91

2026-11-16T02:00:00.108Z INFO  batch.job.started
  jobName=importInvoicesJob jobInstanceId=51 jobExecutionId=7001

2026-11-16T02:00:04.214Z INFO  batch.step.finished
  jobExecutionId=7001 stepExecutionId=9101 stepName=readInvoices
  batchStatus=COMPLETED readCount=120 writeCount=120

2026-11-16T02:00:06.793Z INFO  batch.job.finished
  jobName=importInvoicesJob jobInstanceId=51 jobExecutionId=7001
  batchStatus=COMPLETED exitCode=COMPLETED
```

The values above are illustrative. Logs answer **which events were observed, in which process, and at what time**. Logs can also capture trace IDs, error causes, scheduler details, and business events outside Batch metadata.

A log line does not by itself guarantee the database committed all changes or that the Job stopped executing right after the event reached the logger.

### 1.2. Spring Batch Metadata

`JobRepository` persists structured run state to manage `JobInstance`, `JobExecution`, `StepExecution`, and restartability. With a relational database repository, metadata lives in tables prefixed with `BATCH_`.

Example after Job completion:

```text
BATCH_JOB_INSTANCE
  JOB_INSTANCE_ID=51
  JOB_NAME=importInvoicesJob

BATCH_JOB_EXECUTION
  JOB_EXECUTION_ID=7001
  JOB_INSTANCE_ID=51
  STATUS=COMPLETED
  EXIT_CODE=COMPLETED

BATCH_STEP_EXECUTION
  STEP_EXECUTION_ID=9101
  JOB_EXECUTION_ID=7001
  STEP_NAME=readInvoices
  STATUS=COMPLETED
  READ_COUNT=120
  WRITE_COUNT=120
```

Metadata answers **which execution Spring Batch recorded and what status/counters were persisted**. It is the authoritative reference for lifecycle and restarts, though metadata does not store every business detail, every log line, or full stack traces like a log collector.

### 1.3. Never Treat Both Sources as Mirrors of Each Other

| Perspective | Logs | Spring Batch Metadata |
| --- | --- | --- |
| Generated by | Scheduler, launcher, listeners, Steps, logging pipeline | Spring Batch via `JobRepository` |
| Primary identifiers | Event ID, trace/request ID, and Batch IDs attached to logs | Job name, JobInstance ID, JobExecution ID, StepExecution ID |
| Job status | Snapshot at log emission time | State persisted and updated across transactions |
| Error details | May carry filtered messages, exception types, or stack traces | Status, exit code/description, and repository failure info |
| Item counters | Present only if explicitly logged by application | Columns `READ_COUNT`, `WRITE_COUNT`, `SKIP_COUNT`, etc. |
| Data loss cases | Logs unsent, dropped, or rotated | Uncommitted transactions, DB outage, purged metadata |
| Role in restarts | Supports investigation | Metadata and execution context drive restart mechanics |

**Reconciliation** verifies valid overlap between the two rather than forcing every log field to appear in metadata.

## 2. Join Keys: JobInstance ID and JobExecution ID

Before comparing statuses, join the right records. In Spring Batch:

- `Job` is the job definition, e.g. `importInvoicesJob`.
- `JobInstance` represents a logical unit of work, identified by **Job name + identifying JobParameters**.
- `JobExecution` is a single attempt to run a JobInstance.
- `StepExecution` is a single Step run within a JobExecution.

```text
Job: importInvoicesJob
│
├── JobInstance #51 (businessDate=2026-11-16)
│   ├── JobExecution #7001 -> FAILED
│   │   ├── StepExecution #9101 -> COMPLETED
│   │   └── StepExecution #9102 -> FAILED
│   └── JobExecution #7002 -> COMPLETED (restart)
│       └── StepExecution #9103 -> COMPLETED
│
└── JobInstance #52 (businessDate=2026-11-17)
    └── JobExecution #7003 -> COMPLETED
```

Here `7001` and `7002` share `jobInstanceId=51` yet are **two distinct runs**. Filtering logs solely by `jobName` or business date risks mixing errors from the initial run with outcomes from the restart.

Recommended join keys:

| Level | Key to Use | Notes |
| --- | --- | --- |
| Launch request | `requestId` or `triggerId` | May exist before a JobExecution is created. |
| Logical job | `jobName` + identifying parameters or `jobInstanceId` | Groups restarts of the same logical unit of work. |
| Single run | `jobExecutionId` | Primary key for comparing lifecycle logs with JobExecution metadata. |
| Single Step run | `stepExecutionId` plus `jobExecutionId` | Distinguishes identically named Steps across runs, partitions, or restarts. |
| Distributed work | `partitionId`/`workerId` plus Batch IDs | Aids aggregating logs across multiple workers. |

**`jobExecutionId` is repository-assigned**, usually sufficient for reconciliation within one repository. Across multiple environments or independent databases, numeric IDs can collide. In centralized logs, include **environment/service/repository identifier** so records from dev, staging, production, or separate deployments never cross-match.

### Why Can't You Rely Only on JobParameters?

Consider two launch requests:

```java
JobParameters parameters = new JobParametersBuilder()
        .addString("businessDate", "2026-11-16", true)
        .addString("requestId", "rq-91", false)
        .toJobParameters();
```

This snippet uses Spring Batch 5.x. `businessDate` is an identifying parameter; `requestId` is marked non-identifying. If a restart passes a fresh `requestId` while keeping the same identifying parameters, it still belongs to the same `JobInstance`.

Conversely, if an application adds a fresh identifying `run.id`, every launch creates a different JobInstance. When reconciling, verify the actual identifying parameter configuration rather than guessing instance relationships solely from parameter values seen in logs.

## 3. Designing Reconcilable Logs

Searchable logs should use standardized event names and explicit fields, e.g. JSON:

```json
{
  "timestamp": "2026-11-16T02:00:06.793Z",
  "level": "INFO",
  "event": "batch.job.finished",
  "environment": "test",
  "service": "invoice-batch",
  "jobName": "importInvoicesJob",
  "jobInstanceId": 51,
  "jobExecutionId": 7001,
  "batchStatus": "COMPLETED",
  "exitCode": "COMPLETED",
  "durationMs": 6685
}
```

Depending on your stack, you can emit plain-text `key=value` pairs instead of JSON. What matters is keeping **field names and data types consistent**.

Minimum field set:

1. `event`: `batch.job.launch.requested`, `batch.job.started`, `batch.job.finished`, `batch.step.finished`, or `batch.job.launch.rejected`.
2. `jobName` and whatever Batch IDs exist at log emission time.
3. `batchStatus` and `exitCode` on finish events.
4. `timestamp` with explicit timezone, preferring UTC in centralized logs.
5. `environment`/`repositoryAlias` if multiple repositories ship to one log system.

Useful extra fields: `traceId`, `requestId`, `trigger`, `stepName`, `stepExecutionId`, `durationMs`, `readCount`, `writeCount`, `skipCount`, `failureType`.

Avoid logging all `JobParameters` or the entire `ExecutionContext`. They can contain personal data, tokens, sensitive paths, or internal payloads. Only include business keys approved for logging by policy.

### Distinguishing `accepted` from `finished` Events

```text
Scheduler           JobLauncher              Worker/Step          JobRepository
   │                     │                       │                       │
   ├─ requested ────────>│                       │                       │
   │                     ├─ createExecution ────────────────────────────>│
   │<── accepted ────────┤                       │                       │
   │                     └────────── start ─────>│                       │
   │                                             ├─ STARTED ────────────>│
   │                                             ├─ process              │
   │                                             └─ COMPLETED ──────────>│
   │                                             └─ finished log         │
```

With an asynchronous launcher, **`accepted` only confirms the request was accepted**, not that the Job finished. Failures before JobExecution creation may emit only `requested` and `rejected`, with no new `jobExecutionId` to look up in `BATCH_JOB_EXECUTION`.

Account for this distinction when designing reconciliation rules so you do not raise false “missing metadata” alerts.

## 4. Metadata Tables Used for Verification

For a relational-database `JobRepository` using default table prefixes:

| Table | Commonly Used Columns | Log Fields to Reconcile |
| --- | --- | --- |
| `BATCH_JOB_INSTANCE` | `JOB_INSTANCE_ID`, `JOB_NAME`, `JOB_KEY` | `jobInstanceId`, `jobName` |
| `BATCH_JOB_EXECUTION` | `JOB_EXECUTION_ID`, `JOB_INSTANCE_ID`, `STATUS`, `EXIT_CODE`, `CREATE_TIME`, `START_TIME`, `END_TIME` | `jobExecutionId`, `batchStatus`, `exitCode`, timestamps |
| `BATCH_JOB_EXECUTION_PARAMS` | Parameters persisted with execution | Approved business keys for investigation |
| `BATCH_JOB_EXECUTION_CONTEXT` | JobExecution-level context | Restart/checkpoint diagnostics when permitted |
| `BATCH_STEP_EXECUTION` | `STEP_EXECUTION_ID`, `JOB_EXECUTION_ID`, `STEP_NAME`, `STATUS`, `READ_COUNT`, `WRITE_COUNT`, `SKIP_COUNT` | `stepExecutionId`, `stepName`, Step status, item counters |
| `BATCH_STEP_EXECUTION_CONTEXT` | StepExecution-level context | Checkpoint/restart state |

Table names can be customized via `tablePrefix` and column definitions vary across Spring Batch versions. The SQL examples below assume the default relational schema compatible with Spring Batch 5.x/6.x. Always consult the actual DDL of your repository.

### SQL to Fetch Job Status by Execution ID

```sql
SELECT
    ji.JOB_NAME,
    ji.JOB_INSTANCE_ID,
    je.JOB_EXECUTION_ID,
    je.STATUS AS BATCH_STATUS,
    je.EXIT_CODE,
    je.CREATE_TIME,
    je.START_TIME,
    je.END_TIME,
    je.LAST_UPDATED
FROM BATCH_JOB_EXECUTION je
JOIN BATCH_JOB_INSTANCE ji
  ON ji.JOB_INSTANCE_ID = je.JOB_INSTANCE_ID
WHERE je.JOB_EXECUTION_ID = :executionId;
```

`:executionId` is a query-tool or JDBC placeholder; substitute your SQL console's bind-parameter syntax when running interactively.

For instance, if logs show `jobExecutionId=7001`, the query should return a JobExecution matching the logged `jobName` and `jobInstanceId`. If metadata status is `COMPLETED`, that reflects persisted Batch state, though you should still check update timestamps if the log was just emitted.

### SQL to Fetch StepExecutions of a JobExecution

```sql
SELECT
    se.JOB_EXECUTION_ID,
    se.STEP_EXECUTION_ID,
    se.STEP_NAME,
    se.STATUS AS BATCH_STATUS,
    se.EXIT_CODE,
    se.READ_COUNT,
    se.WRITE_COUNT,
    se.FILTER_COUNT,
    se.SKIP_COUNT,
    se.COMMIT_COUNT,
    se.ROLLBACK_COUNT,
    se.START_TIME,
    se.END_TIME
FROM BATCH_STEP_EXECUTION se
WHERE se.JOB_EXECUTION_ID = :executionId
ORDER BY se.STEP_EXECUTION_ID;
```

Results explain why a Job `FAILED` or why total processed records differed from expectations. Never blindly sum counters across all runs by `stepName`: the same Step name can appear in a later restart or carry partition suffixes.

### SQL to View All Runs of a JobInstance

```sql
SELECT
    JOB_INSTANCE_ID,
    JOB_EXECUTION_ID,
    STATUS,
    EXIT_CODE,
    START_TIME,
    END_TIME
FROM BATCH_JOB_EXECUTION
WHERE JOB_INSTANCE_ID = :instanceId
ORDER BY JOB_EXECUTION_ID;
```

One instance having multiple executions is normal during restarts. In reconciliation reports, group by `JobInstance` to see full history, while comparing each execution's status by its **individual execution ID**.

## 5. Reading Metadata via `JobExplorer`

In Java code, `JobExplorer` is the read-only API for querying history without coupling observability code to raw SQL tables.

Spring Batch 5.x example:

```java
import org.springframework.batch.core.JobExecution;
import org.springframework.batch.core.StepExecution;
import org.springframework.batch.core.explore.JobExplorer;

public final class BatchExecutionSnapshotReader {

    private final JobExplorer jobExplorer;

    public BatchExecutionSnapshotReader(JobExplorer jobExplorer) {
        this.jobExplorer = jobExplorer;
    }

    public void printExecution(long executionId) {
        JobExecution execution =
                jobExplorer.getJobExecution(executionId);

        if (execution == null) {
            System.out.println("Execution not found: " + executionId);
            return;
        }

        System.out.printf(
                "job=%s instance=%d execution=%d status=%s exitCode=%s%n",
                execution.getJobInstance().getJobName(),
                execution.getJobInstance().getInstanceId(),
                execution.getId(),
                execution.getStatus(),
                execution.getExitStatus().getExitCode()
        );

        for (StepExecution step : execution.getStepExecutions()) {
            System.out.printf(
                    "  step=%s stepExecution=%d status=%s "
                        + "read=%d write=%d skip=%d%n",
                    step.getStepName(),
                    step.getId(),
                    step.getStatus(),
                    step.getReadCount(),
                    step.getWriteCount(),
                    step.getSkipCount()
            );
        }
    }
}
```

`System.out` is used here to illustrate returned data. In real applications, map to a DTO or emit structured logs rather than printing metadata indiscriminately to production stdout.

**Version note:** Spring Batch 5.x places `JobExecution` and `StepExecution` in `org.springframework.batch.core`. Spring Batch 6.x organizes these types into subpackages such as `org.springframework.batch.core.job` and `org.springframework.batch.core.step`; adjust imports for your actual dependency. `JobExplorer`'s role in querying metadata remains central.

### Why Re-Read from the Repository?

The `JobExecution` returned by the launcher reflects launch time. When a Job runs asynchronously, that object's status may still be `STARTING` or `STARTED`. Querying freshly via `JobExplorer.getJobExecution(id)` retrieves the **persisted state** at inspection time.

In automated reconciliation, re-querying after a bounded wait with a timeout makes sense while a Job is still running. Never use infinite polling loops or fixed `Thread.sleep(...)` calls assuming every execution has finished.

## 6. Step-by-Step Reconciliation Workflow

When receiving an alert or a `batch.job.finished` log, follow this sequence.

### Step 1: Identify Source and Scope

Extract `environment`, `service`/`repositoryAlias`, `jobName`, `jobInstanceId`, and `jobExecutionId`. If the log has no ID because the launch was rejected, switch to launch-failure diagnostics (`requestId`, exception, identifying parameters) instead of searching for an execution that was never created.

Before querying, confirm your tool points to the **right JobRepository datasource**. An application may have separate business and Batch metadata datasources.

### Step 2: Query Metadata for the Execution ID

Use `JobExplorer.getJobExecution(executionId)` or SQL joining the two Job tables. Verify:

- Does `jobName` match the log?
- Does `jobInstanceId` match?
- Does `jobExecutionId` exist?
- What are the current `BatchStatus` and `ExitStatus`?
- Does the execution have an `END_TIME`, or is it still running?
- How recent is `LAST_UPDATED` relative to observation time?

If the ID exists across multiple independent databases, disambiguate by environment/repository before drawing conclusions.

### Step 3: Distinguish Intermediate States from Terminal States

A `batch.job.started status=STARTED` log alongside metadata showing `COMPLETED` at a later time is **not a contradiction**. The log describes state at start time; metadata shows a newer snapshot.

Only compare `batch.job.finished` against terminal metadata after confirming the Job truly ended and final updates committed.

Common terminal statuses are `COMPLETED`, `FAILED`, `STOPPED`, and in certain cases `ABANDONED`. `STARTING`, `STARTED`, and `STOPPING` are non-terminal states.

### Step 4: Reconcile Each StepExecution

If the Job has multiple Steps, inspect `BATCH_STEP_EXECUTION` or `JobExecution.getStepExecutions()`, joining on `stepExecutionId` and `jobExecutionId`. Compare statuses, exit codes, and counters logged at the **same Step completion milestone**.

If a Step uses skips/filters, `readCount` and `writeCount` need not match. If a Step did not run due to conditional branching or restart skipping, having no new StepExecution can also be completely valid.

### Step 5: Reconcile Business Data If Necessary

Metadata tracks framework counters, not proof that every external side effect applied exactly once. When investigating data writes, inspect target tables, output files, messages, or target APIs using **business keys** and process idempotency.

### Step 6: Record Discrepancy Category and Findings

Never lump all outcomes into “bad logs” or “bad metadata”. Classify clearly:

```text
reconciliation.status = matched | pending | mismatch | missing_log
                        | missing_metadata | unknown
reconciliation.reason = status_not_final | telemetry_delay | wrong_repo
                        | launch_rejected | crash_suspected | ...
```

These values are suggested data-model fields for a monitoring app, not built-in Spring Batch enums.

## 7. Reconciling State Over Time: Handling Eventual Consistency

Logs and metadata are not written in a shared transaction with log collection services. Even within one process, externally observed ordering can vary.

Example:

```text
T0  Job starts; repository writes STARTED
T1  Final Step completes
T2  afterJob callback logs "batch.job.finished status=COMPLETED"
T3  Framework updates JobExecution in repository, transaction commits
T4  Log collector receives event from T2
T5  Dashboard queries repository and sees COMPLETED
```

Depending on implementation, log emission and commit steps can have different ordering or latency. Therefore, if a query right after log arrival still sees `STARTED`, allow a **bounded convergence window** before flagging a mismatch.

Simple mechanism:

1. Receive `batch.job.finished` with `jobExecutionId`.
2. Query the repository.
3. If status is still non-terminal, mark `pending` and retry per policy.
4. If metadata reaches the matching terminal state before timeout, mark `matched`.
5. If timeout expires with a discrepancy remaining, raise a mismatch alert carrying both snapshots for investigation.

No single wait window fits every system. Tune the timeout to metadata write latency, log pipeline lag, and your observability SLA. **Never use timeouts to mask an infinitely hung Job**; detecting stuck workers/JobExecutions belongs to a separate alerting path.

### Timestamps Need a Common Standard

- Logs should carry UTC timestamps with explicit timezone offsets.
- Spring Batch metadata columns may use timezone-naive SQL timestamps; interpretation depends on JDBC/database settings.
- Never infer strict ordering solely from two timestamps when host clocks drift.
- For reliable tracking, rely on execution IDs, statuses, and update timestamps; timestamps are supporting evidence, not the primary join key.

## 8. `BatchStatus`, `ExitStatus`, and Outcome Logs

`JobExecution.getStatus()` returns `BatchStatus`; `getExitStatus()` returns `ExitStatus` containing `exitCode` and `exitDescription`.

Example:

```text
Metadata:
  STATUS    = COMPLETED
  EXIT_CODE = COMPLETED_WITH_WARNINGS

Log:
  batchStatus=COMPLETED
  exitCode=COMPLETED_WITH_WARNINGS
```

This can be **100% valid** when an application uses a custom exit code to signal business warnings. Do not flag a mismatch merely because `exitCode` is not the string `COMPLETED` while `BatchStatus` is `COMPLETED`.

Suggested comparison rules:

| Field | How to Compare |
| --- | --- |
| `BatchStatus` | Compare enum/status code of the same execution in its terminal state. |
| `ExitStatus.getExitCode()` | Compare strings, including custom codes. |
| `ExitStatus.getExitDescription()` | Mainly for investigation; avoid exact string equality since content can vary or hold sensitive text. |
| `failureCount` in logs | May be computed by listeners from exceptions; does not map by default to a metadata error-count column. |
| `durationMs` | Compare within a reasonable tolerance when timestamps have sufficient precision; do not require exact equality across implementations. |

For `StepExecution`, distinguish `STATUS` and `EXIT_CODE` as well. A `FAILED` Step can still result in a `COMPLETED` Job if a flow intentionally handles the failure via transition rules. Never conclude a Job must be `FAILED` simply because one Step failed.

## 9. Comparing Step Counters with Output Data

Common metadata counters:

| Field | Meaning |
| --- | --- |
| `READ_COUNT` | Items read per Step mechanics. |
| `WRITE_COUNT` | Items written per Step statistics. |
| `FILTER_COUNT` | Items filtered out by processor. |
| `SKIP_COUNT` | Total skipped items. |
| `READ_SKIP_COUNT`, `PROCESS_SKIP_COUNT`, `WRITE_SKIP_COUNT` | Skips broken down by phase. |
| `COMMIT_COUNT`, `ROLLBACK_COUNT` | Step commit/rollback statistics. |

Suppose a Step reads 100 records, filters 5, skips 3 invalid records, and writes 92 successfully:

```text
Log:
  event=batch.step.finished
  jobExecutionId=7001 stepExecutionId=9101
  readCount=100 writeCount=92 filterCount=5 skipCount=3

Metadata:
  JOB_EXECUTION_ID=7001 STEP_EXECUTION_ID=9101
  READ_COUNT=100 WRITE_COUNT=92 FILTER_COUNT=5 SKIP_COUNT=3
```

Numbers here are illustrative fixtures. Exact filter/skip accounting depends on reader, processor, writer, and retry/rollback configuration; never enforce a universal `readCount = writeCount + filterCount + skipCount` rule for every Job.

### Comparison Caveats

- Logs emitted while a Step is **in progress** hold transient counters that differ from final metadata.
- A Step with many retries or rollbacks can emit item-processing logs repeatedly, whereas final Step counters are not log-line counts.
- Logs emitted from `ItemProcessor`/`ItemWriter` can be affected by concurrency, retries, sampling, and async appenders.
- In multi-threaded Steps, log order does not guarantee item order.
- In partitioned Steps, join each `StepExecution`/partition by its exact ID and aggregate only with a clear understanding of the Job's partitioning model.

**`writeCount` does not replace checking target data.** For Jobs writing to APIs or message brokers outside Spring Batch's transaction, verify downstream results by business key to ensure zero lost or duplicate records.

## 10. Restart: One JobInstance, Multiple JobExecutions

This is a particularly critical reconciliation scenario.

```text
Log:
  jobInstanceId=51 jobExecutionId=7001 batchStatus=FAILED
  jobInstanceId=51 jobExecutionId=7002 batchStatus=COMPLETED

Metadata:
  BATCH_JOB_INSTANCE: JOB_INSTANCE_ID=51
  BATCH_JOB_EXECUTION:
    7001 -> FAILED
    7002 -> COMPLETED
```

Both runs belong to one logical unit of work. If a dashboard only displays “JobInstance #51 ultimately completed”, it hides the earlier failure. If it simply counts `FAILED` across all JobExecutions, it keeps alerting on historical failures even after a restart resolved them.

Therefore, separate two questions:

- **By execution:** “Why did run `7001` fail?” → filter `jobExecutionId=7001`.
- **By instance:** “Has logical unit `51` finished yet, and after how many attempts?” → group JobExecutions of instance `51`.

During a restart, previously completed Steps may be skipped per configuration. Never assume every StepExecution from the first run has a counterpart in the restart.

### Never Sum Counters Across Runs Mechanically

If the first run read 80 items before failing and the restart read the remaining 20, summing `READ_COUNT` may reflect total reads—yet with rollbacks, retries, misaligned checkpoints, or reprocessed items, that sum is not guaranteed to equal **unique** records in the target system.

When reporting business totals for a JobInstance, rely on business record keys and actual target state. StepExecution metadata provides the explanatory trail, not automatic unique-entity counts.

## 11. Common Discrepancy Scenarios

| Observed Scenario | Possible Cause | How to Investigate |
| --- | --- | --- |
| Log shows `finished COMPLETED`, metadata still `STARTED` moments later | Final update uncommitted or read-replica lag | Wait with timeout, read from primary repository, check update timestamps. |
| Metadata `COMPLETED`, missing `finished` log | Collector dropped event, logger muted, async appender unflushed, listener unregistered | Check listener/appender config, filter with exact ID and time window. |
| `launch.requested` log exists, no execution | Request rejected before JobExecution creation or repository error | Search `launch.rejected` by request ID and exception type. |
| Multiple `jobExecutionId`s for same `jobName` | Different JobInstances or Job restarted | Reconcile per ID, grouping by `jobInstanceId` when appropriate. |
| Log says `FAILED` while metadata shows `COMPLETED` | Log belongs to an earlier execution, later retry/restart succeeded, or intermediate snapshot | Check execution ID and timestamp. |
| Step log shows 100 processing passes, `READ_COUNT` is lower | Retries, rollbacks, duplicate logs, or event counted at another layer | Compare `stepExecutionId` and timestamps; inspect retries/skips. |
| Metadata stuck `STARTED` long-term, no new logs | Job hung, process died, worker disconnected, or logging broke | Check process/worker liveness, locks, JobRepository, and checkpoints before restarting. |
| `jobExecutionId` not found in database | Wrong environment/repository, metadata purged by retention, or wrong ID logged | Verify datasource/prefix, purge policy, and log fields. |
| `BatchStatus` matches, `exitCode` differs | Custom exit code, stale log timing, or mapping bug | Compare `ExitStatus` separately; inspect flow and listeners. |
| Multiple `batch.job.finished` logs for one execution | Multiple listeners/pipelines or at-least-once log ingestion | Inspect event ID/source; deduplicate by event key. |

**Never manually edit metadata to match logs.** Batch metadata governs restartability; ad-hoc SQL status updates can corrupt checkpoints or audit trails.

## 12. Investigating Mid-Run JVM Crashes

When a JVM is killed or a host loses power, listener callbacks may never execute. Meanwhile, the repository may still show:

```text
JOB_EXECUTION_ID = 7008
STATUS = STARTED
START_TIME = 2026-11-16 02:00:00
END_TIME = NULL
LAST_UPDATED = 2026-11-16 02:03:12
```

If logs stop at `02:03`, that only shows **no further logs were observed**. It does not prove the process died; the log collector could be down or the Job could be blocked on I/O.

Verification steps:

1. Identify environment, node/pod, process ID, and batch execution ID.
2. Check whether the process/worker is alive, blocked on threads, out of DB connections, or processing a massive chunk.
3. Inspect the latest JobExecution/StepExecution metadata and execution context state.
4. Reconcile committed business data to assess safe restartability.
5. Only after confirming the old execution is truly dead, execute recovery/restart procedures per the Job's restartability design.
6. Record the incident event and handled execution ID.

Never assume `FAILED` solely because `END_TIME IS NULL`. In Spring Batch, an abrupt crash can leave metadata `STARTED`; transitioning statuses for restart must follow operational policy.

## 13. Example Reconciliation Service Using `JobExplorer`

This section builds a small function comparing a parsed **job finished** log event against the snapshot in `JobRepository`. The example uses Java 17 and Spring Batch 5.x APIs; the `record` and `enum` types are application-defined structures.

```java
import org.springframework.batch.core.BatchStatus;
import org.springframework.batch.core.JobExecution;
import org.springframework.batch.core.explore.JobExplorer;

public final class BatchLogReconciler {

    private final JobExplorer explorer;

    public BatchLogReconciler(JobExplorer explorer) {
        this.explorer = explorer;
    }

    public ReconciliationResult compare(FinishedJobLog event) {
        JobExecution execution =
                explorer.getJobExecution(event.jobExecutionId());

        if (execution == null) {
            return new ReconciliationResult(
                    Outcome.MISSING_METADATA,
                    "Execution ID is absent from this repository"
            );
        }

        String actualName =
                execution.getJobInstance().getJobName();
        Long actualInstanceId =
                execution.getJobInstance().getInstanceId();

        if (!actualName.equals(event.jobName())
                || !actualInstanceId.equals(event.jobInstanceId())) {
            return new ReconciliationResult(
                    Outcome.MISMATCH,
                    "Job identity differs"
            );
        }

        BatchStatus status = execution.getStatus();

        if (status == BatchStatus.STARTING
                || status == BatchStatus.STARTED
                || status == BatchStatus.STOPPING) {
            return new ReconciliationResult(
                    Outcome.PENDING,
                    "Job metadata has not reached a terminal state"
            );
        }

        String actualExitCode =
                execution.getExitStatus().getExitCode();

        boolean sameStatus =
                status.name().equals(event.batchStatus());
        boolean sameExitCode =
                actualExitCode.equals(event.exitCode());

        if (sameStatus && sameExitCode) {
            return new ReconciliationResult(
                    Outcome.MATCHED,
                    "Stored terminal status matches the log"
            );
        }

        return new ReconciliationResult(
                Outcome.MISMATCH,
                "Terminal status or exit code differs"
        );
    }

    public record FinishedJobLog(
            String jobName,
            Long jobInstanceId,
            Long jobExecutionId,
            String batchStatus,
            String exitCode) {
    }

    public record ReconciliationResult(
            Outcome outcome,
            String reason) {
    }

    public enum Outcome {
        MATCHED,
        PENDING,
        MISMATCH,
        MISSING_METADATA
    }
}
```

This method illustrates **single-snapshot comparison**; it omits retries, time limits, repository identification, `ABANDONED` handling, log deduplication, and retention policies. In production, the outer orchestration layer should:

- Feed only `batch.job.finished` events with valid schemas from the right environment.
- Wait for a bounded convergence window when the result is `PENDING`.
- Classify missing metadata by retention, repository, and launch state.
- Record mismatch reasons, observation timestamps, and exact discrepancy details.
- Avoid using `jobExecutionId` as a metric tag since every execution creates a new value.

This is metadata reconciliation—it **does not automatically prove the job executed business logic correctly**.

### Why Not Compare Timestamps with Equality?

Logs typically have millisecond/nanosecond precision, whereas database timestamp columns may be rounded by the driver. The two timestamps are recorded in different layers. When checking order or duration, define acceptable tolerances and keep time sources distinct rather than requiring strict `log.timestamp == metadata.END_TIME`.

## 14. Writing Tests Proving Logs and Metadata Match

An integration test can run a real Job, capture the `JobExecution`, and assert that logs contain the exact IDs and statuses read back from `JobExplorer`.

The example below uses **Spring Batch 5.x**, **JUnit Jupiter**, **Spring Boot Test**, and **AssertJ**. It assumes the application provides an `importInvoicesJob` bean, a listener emitting `batch.job.finished` with IDs and statuses, and sufficient fixture data for the Job to complete:

```java
import java.util.UUID;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.springframework.batch.core.BatchStatus;
import org.springframework.batch.core.Job;
import org.springframework.batch.core.JobExecution;
import org.springframework.batch.core.JobParameters;
import org.springframework.batch.core.JobParametersBuilder;
import org.springframework.batch.core.explore.JobExplorer;
import org.springframework.batch.test.JobLauncherTestUtils;
import org.springframework.batch.test.context.SpringBatchTest;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.system.CapturedOutput;
import org.springframework.boot.test.system.OutputCaptureExtension;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBatchTest
@SpringBootTest(properties = "spring.batch.job.enabled=false")
@ExtendWith(OutputCaptureExtension.class)
class BatchMetadataLogReconciliationIT {

    @Autowired
    private JobLauncherTestUtils jobLauncherTestUtils;

    @Autowired
    private JobExplorer jobExplorer;

    @Autowired
    @Qualifier("importInvoicesJob")
    private Job importInvoicesJob;

    @Test
    void finishedLogShouldMatchStoredExecution(CapturedOutput output)
            throws Exception {
        jobLauncherTestUtils.setJob(importInvoicesJob);

        JobParameters parameters = new JobParametersBuilder()
                .addString("businessDate", "2026-11-16", true)
                .addString("testRunId", UUID.randomUUID().toString(), true)
                .toJobParameters();

        JobExecution launched =
                jobLauncherTestUtils.launchJob(parameters);

        assertThat(launched.getStatus())
                .isEqualTo(BatchStatus.COMPLETED);

        JobExecution stored =
                jobExplorer.getJobExecution(launched.getId());

        assertThat(stored).isNotNull();
        assertThat(stored.getId()).isEqualTo(launched.getId());
        assertThat(stored.getJobInstance().getInstanceId())
                .isEqualTo(launched.getJobInstance().getInstanceId());
        assertThat(stored.getStatus())
                .isEqualTo(BatchStatus.COMPLETED);
        assertThat(stored.getExitStatus().getExitCode())
                .isEqualTo("COMPLETED");

        assertThat(output.getOut())
                .contains("batch.job.finished")
                .contains("jobExecutionId=" + stored.getId())
                .contains("jobInstanceId="
                        + stored.getJobInstance().getInstanceId())
                .contains("batchStatus=" + stored.getStatus().name())
                .contains("exitCode="
                        + stored.getExitStatus().getExitCode());
    }
}
```

Conditions for this test to be meaningful:

1. `importInvoicesJob` has a listener emitting the asserted fields.
2. Logs write through an appender captured by `OutputCaptureExtension`.
3. The test launcher runs **synchronously**. If async, wait until the Job reaches a terminal state and flush logs before asserting.
4. Test metadata and business data are isolated; `testRunId` is identifying here so each test gets its own instance.
5. Fixture data is valid so the Job truly completes; the snippet demonstrates reconciliation rather than provisioning application fixtures.

Avoid asserting entire raw log lines containing timestamps, thread names, code locations, or durations. Those details are not a stable reconciliation contract.

### Testing the Restart Scenario

Add another test that intentionally fails the Job on the first run, fixes the failure condition, and restarts with the **same identifying parameters**. Assert:

- `jobInstanceId` matches across both runs.
- `jobExecutionId` differs.
- `finished` logs have two events tied to the two executions.
- Metadata holds distinct statuses for the failed and successful runs.
- Target data has zero duplicates after restart.

Do not purge metadata between the two runs in a restart test. Clean up only after all assertions pass.

## 15. Monitoring Asynchronous Steps or Jobs

If a Job runs on an async `TaskExecutor`, `JobLauncher.run(...)` can return before the Job completes. Meanwhile:

```text
T0  Launcher returns executionId=7001 status=STARTING
T1  Worker executes Step; metadata status=STARTED
T2  Step listener logs step.finished
T3  Repository saves StepExecution
T4  Job listener logs job.finished
T5  Repository saves JobExecution terminal status
```

This is a conceptual timeline; exact commit and log emission order depends on implementation. Crucially, **never compare the launcher's initial status against the finish log**.

A sensible observation mechanism:

```java
JobExecution snapshot = jobExplorer.getJobExecution(executionId);
if (snapshot != null) {
    BatchStatus status = snapshot.getStatus();

    if (status == BatchStatus.COMPLETED
            || status == BatchStatus.FAILED
            || status == BatchStatus.STOPPED) {
        // Record final status snapshot for reconciliation.
    } else {
        // Wait/retry per configured timeout.
    }
}
```

When waiting for Job completion in an async integration test, use bounded polling such as Awaitility or `Future.get(timeout, unit)` when the test controls the worker. When polling the repository, execute a fresh query each check to observe persisted state.

For multi-threaded or partitioned Steps, logger MDC may not automatically propagate to worker threads. Pass `jobExecutionId`/`stepExecutionId` directly into logs or configure explicit context propagation; avoid correlating logs by thread name.

## 16. Logs Without Metadata and Metadata Without Logs

### 16.1. Logs Have an Event, Yet Metadata Is Absent

Possible causes:

- `launch.requested` or `launch.rejected` was emitted before creating a `JobExecution`.
- Querying the wrong datasource or wrong `tablePrefix`.
- Metadata was purged by tests, retention jobs, or maintenance.
- Centralized logging aggregates multiple environments with overlapping IDs.
- The execution-creation transaction failed or rolled back.
- The ID field in logs was miswritten or altered during parsing.

Recommended checks: inspect event type, environment, JobRepository configuration, time window, cleanup policies, and JobInstance existence.

### 16.2. Metadata Has an Execution, Yet Logs Are Missing

Possible causes:

- Logging listener was not registered on the Job/Step.
- Log level or appender filtered out the event.
- JVM died before the callback ran.
- Async appender had not flushed when the process was killed.
- Collector lost connectivity, overloaded, or changed retention.
- Log query filtered the wrong time range, index, or field.
- Batch metadata was validly created, yet execution never reached the expected log phase.

Never automatically conclude a Job failed just because `finished` is missing from logs. Inspect metadata, worker status, and business outputs to understand true state.

### 16.3. When Absolute Durable Auditing Is Required

Standard logs are observability signals, not atomic transactions tied to metadata or business outcomes. If strict auditing demands that **every business event must be persisted** and emitted reliably, add an audit table or transactional outbox within the **same appropriate transaction scope** as the business change, then deliver events externally using a retryable, idempotent worker.

Even an outbox requires deduplication and error handling; it does not turn Spring Batch metadata into a full mirror of logs. Audit requirements belong at the business layer rather than being inferred from log-line presence.

## 17. Operational Rules to Prevent Alert Fatigue

An automated reconciliation system needs explicit rules:

| Rule | Reason |
| --- | --- |
| Join on `environment/repositoryAlias + jobExecutionId` | Prevents cross-matching execution IDs across independent repositories. |
| Compare only terminal events against terminal metadata | Prevents flagging valid state transitions as discrepancies. |
| Allow a convergence window with timeout | Accounts for asynchronous timing between logs and database commits. |
| Separate `launch.rejected` from `JobExecution` `FAILED` | Launch rejections may never create an execution. |
| Distinguish JobInstance and JobExecution | Preserves restart history accurately. |
| Process duplicate log events idempotently | Log pipelines can deliver the same event more than once. |
| Record reasons for missing metadata | Could stem from retention, cleanup, or wrong datasource. |
| Limit sensitive fields and cardinality | Protects data and keeps monitoring backends healthy. |

If `batch.job.finished` events flow through a message queue or an at-least-once log pipeline, the same event can arrive multiple times. Use a deduplication key such as `environment + jobExecutionId + eventType` plus an event ID if present. For Steps, include `stepExecutionId`. Never increment a “Jobs completed” counter every time the same event is re-ingested.

Never use `jobExecutionId` as a high-cardinality metric tag; use `jobName`, status, and bounded labels instead. Keep execution IDs in logs or detailed query stores.

## 18. Hands-on Exercise

Build a `syncInventoryJob` processing hourly inventory snapshots at the end of each hour. Give the Job two Steps: `readStockStep` and `publishStockStep`. Set up structured logs and a reconciliation view reading metadata via `JobExplorer`.

### Scenario A: Job Completes

1. Run the Job with 50 valid inventory records.
2. Log `launch.requested`, `job.started`, `step.finished`, and `job.finished` with matching IDs.
3. Query `BATCH_JOB_EXECUTION` by the `jobExecutionId` from logs.
4. Query `BATCH_STEP_EXECUTION` and reconcile `stepExecutionId`, status, and item counts.
5. Verify the target store holds exactly 50 valid records by business key.

### Scenario B: Job Fails Then Restarts

1. Introduce a controlled failure causing `publishStockStep` to fail.
2. Record `jobInstanceId` and `jobExecutionId` from the failed run.
3. Fix the error condition and restart with the same identifying parameters.
4. Confirm two different `jobExecutionId`s share the same `jobInstanceId`.
5. Filter logs by instance for full history, and by execution to separate the failed attempt from the completed one.
6. Confirm target data has no duplicate writes.

### Scenario C: Delayed or Missing Logs

1. Add a latch in a test Job to control completion timing.
2. Have the reconciler check metadata before the Job is terminal: result must be `pending`, not mismatch.
3. Release the latch and wait for final metadata update; re-reconcile to `matched`.
4. Simulate a missing `finished` log event; ensure the system flags “missing log” after timeout while still displaying real metadata status.
5. Emit a `launch.rejected` event without a new `jobExecutionId`; confirm the system does not attempt to query a non-existent execution.

Self-check questions:

- If a JobInstance has two JobExecutions, why can't `jobInstanceId` alone be used to compare terminal status logs?
- If `BATCH_JOB_EXECUTION.STATUS=COMPLETED` yet `job.finished` is missing from logs, what causes are unrelated to business errors?
- If a Step read 100 items yet processor logs show 120 lines, does that always mean metadata is wrong?
- If the `job.finished` log arrives before metadata commits, how should the interim result be classified?
- If two environments both have `jobExecutionId=7001`, what extra key must centralized logging include?
