# StaxEventItemWriter

In Spring Batch, StaxEventItemWriter is an ItemWriter used to write each item as XML elements within a single XML document. The writer uses the StAX (Streaming API for XML) mechanism combined with a Spring OXM Marshaller to convert Java objects into XML. It fits batch jobs that need to export large datasets chunk by chunk without building the entire XML tree in memory.

The writer creates a root element, then marshals each item into a child element. For example, each Order is converted into an order element inside an orders element. StaxEventItemWriter also participates in the Step lifecycle and supports saving checkpoints for restarts. To use it safely, configure marshaller, root tag, resource, encoding, and state consistently; also understand how the output file interacts with chunk transactions.

## 1. What does StaxEventItemWriter do?

StaxEventItemWriter receives items from a chunk and writes them as XML elements. It does not read data itself nor decide business rules for items; its responsibility is serializing objects into XML and managing the output document.

Example of three Orders written to a file:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order>
        <id>1001</id>
        <customerId>501</customerId>
        <amount>125.50</amount>
    </order>
    <order>
        <id>1002</id>
        <customerId>502</customerId>
        <amount>89.00</amount>
    </order>
    <order>
        <id>1003</id>
        <customerId>503</customerId>
        <amount>210.00</amount>
    </order>
</orders>
~~~

In the example:

- orders is the document's root element.
- Each order is one marshalled item.
- Fields inside the element are determined by the object mapping and marshaller.
- The writer manages the prologue, root element, items, and document closing.

If a Job processes millions of items, StAX enables writing sequentially to the resource instead of holding the whole document in a DOM tree. Memory is still needed for the chunk, current object, buffers, and marshaller work, but does not have to hold the entire XML output.

## 2. StAX and Spring OXM Marshaller

StAX is a streaming XML processing API. Spring Batch uses a StAX event writer to emit XML events to the output. Spring OXM provides the Marshaller abstraction, responsible for converting a Java object into XML.

Write flow:

~~~text
ItemReader
    |
    v
ItemProcessor
    |
    v
Chunk
    |
    v
StaxEventItemWriter
    |
    +--> root element
    |
    +--> OXM Marshaller for item 1
    |
    +--> OXM Marshaller for item 2
    |
    +--> OXM Marshaller for item N
    |
    v
XML Resource
~~~

The Marshaller can be implemented using Jaxb2Marshaller or another OXM implementation supporting StAX results. With JAXB, annotations on the model specify element names, attributes, ordering, and field representation.

Choose the right dependency/API for your Spring version:
- Spring Framework 6 and Spring Batch 5 use the Jakarta XML Binding namespace (jakarta.xml.bind).
- Older Spring Framework 5/Spring Batch 4 applications typically use Javax XML Binding (javax.xml.bind).

Do not mix javax and jakarta JAXB annotations in the same model if the marshaller runtime supports only one family.

## 3. Creating an XML model with JAXB

Example model representing an order:

~~~java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

import java.math.BigDecimal;

@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    @XmlElement
    private long id;

    @XmlElement
    private long customerId;

    @XmlElement
    private BigDecimal amount;

    public OrderXml() {
    }

    public OrderXml(long id, long customerId, BigDecimal amount) {
        this.id = id;
        this.customerId = customerId;
        this.amount = amount;
    }
}
~~~

@XmlRootElement(name = "order") defines the root element when an OrderXml object is marshalled. StaxEventItemWriter places this element inside the document root managed by the writer.

@XmlAccessorType(XmlAccessType.FIELD) instructs JAXB to read fields directly. Property access or finer annotations can be used depending on the model. JAXB models usually require a no-arg constructor depending on the provider and binding style used.

If batch input items are domain objects, you do not have to attach JAXB annotations to domain models. A processor can convert domain objects into dedicated XML DTOs to preserve the boundary between business models and exchange formats.

## 4. Configuring Jaxb2Marshaller

Declare a marshaller and specify the JAXB classes to bind:

~~~java
@Bean
Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    return marshaller;
}
~~~

If there are multiple related models, register multiple classes or use package scanning as appropriate. For XML with namespaces, schemas, or special adapters, configure the corresponding properties on the marshaller.

Example marshaller with a schema:

~~~java
@Bean
Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    marshaller.setSchema(
            new ClassPathResource("xml/order-export.xsd"));
    return marshaller;
}
~~~

Configuring a schema on a JAXB marshaller can help validate during marshalling, depending on the implementation and setup. Verify that the schema matches actual namespaces, elements, types, and field ordering. Do not assume every XML file produced by the writer is validated against an XSD unless the application explicitly configures validation.

## 5. Configuring StaxEventItemWriter with Builder

Spring Batch provides StaxEventItemWriterBuilder to configure the writer:

~~~java
@Bean
StaxEventItemWriter<OrderXml> orderXmlWriter(
        Marshaller orderMarshaller,
        Resource outputResource) {

    return new StaxEventItemWriterBuilder<OrderXml>()
            .name("orderXmlWriter")
            .resource(outputResource)
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .encoding("UTF-8")
            .overwriteOutput(true)
            .saveState(true)
            .build();
}
~~~

Key configurations:

- name(...): stable writer name used when saving state in ExecutionContext.
- resource(...): file or resource receiving XML output.
- marshaller(...): converts each item into XML.
- rootTagName(...): name of the root element wrapping all items.
- encoding(...): document encoding, commonly UTF-8.
- overwriteOutput(...): controls handling of an existing resource when starting new output.
- saveState(...): enables checkpoint saving to support restarts.

The writer name must remain stable across runs and deployments if old checkpoints need recovery. Renaming it can cause state keys in ExecutionContext to stop matching.

Available methods may vary by Spring Batch version. When using a specific version's builder, check its API for options such as XML version, standalone, header/footer callbacks, transactional, and force sync.

## 6. Setting the root element and item element names

rootTagName defines the outer element enclosing all items. Each item's element name typically comes from the marshalled class's JAXB metadata or OXM marshaller mapping.

Example:

~~~java
.rootTagName("orders")
~~~

and model:

~~~java
@XmlRootElement(name = "order")
public class OrderXml {
    // Order fields
}
~~~

The result is:

~~~xml
<orders>
    <order>...</order>
    <order>...</order>
</orders>
~~~

The root tag should be a valid XML name consistent with the contract required by the receiving system. Do not set the root tag to the item name if the document must hold multiple items of the same type.

If you need to write multiple item types in one document, design models/Marshallers so each item marshals into a valid element under the same root. Verify the schema and consumer support those child element types.

## 7. Passing domain objects through a processor before marshalling

You do not have to write entities or domain objects directly. Data can be transformed into an XML DTO in the processor:

~~~java
@Bean
ItemProcessor<Order, OrderXml> orderXmlProcessor() {
    return order -> new OrderXml(
            order.getId(),
            order.getCustomerId(),
            order.getAmount());
}
~~~

The Step then has distinct input and output types:

~~~java
@Bean
Step exportOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<Order> orderReader,
        ItemProcessor<Order, OrderXml> orderXmlProcessor,
        ItemWriter<OrderXml> orderXmlWriter) {

    return new StepBuilder("exportOrdersStep", jobRepository)
            .<Order, OrderXml>chunk(200, transactionManager)
            .reader(orderReader)
            .processor(orderXmlProcessor)
            .writer(orderXmlWriter)
            .build();
}
~~~

This keeps the XML format independent of the database schema and domain model. If the XML schema changes, you can update the DTO/processor/marshaller without modifying business entities.

The processor is also the right place to normalize values, map enums to codes, format datetimes per contract, or omit internal fields not meant for export.

## 8. Configuring XML declaration and encoding

The XML declaration normally contains version and encoding, e.g.:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
~~~

The writer encoding must match the encoding declared in the XML and how the consumer reads the file. UTF-8 is the common choice for multilingual data exchange.

If output contains Vietnamese text, verify all of:
- Writer encoding.
- Actual file encoding on the filesystem.
- XML declaration.
- Encoding used by the downstream system when reading.
- Characters needing escaping in XML content.

Do not simply change the declared string encoding="UTF-8" while writing bytes in another charset. Doing so creates a document whose declaration contradicts the actual data.

If a specific XML version or standalone declaration is required, use configuration supported by your writer version and verify actual output with an XML parser.

## 9. HeaderCallback and FooterCallback

StaxEventItemWriter supports callbacks to add XML content at the beginning or end of the document, such as comments, processing instructions, or metadata per contract. Callbacks receive a StAX event writer to emit events.

Example adding a comment in the header:

~~~java
StaxWriterCallback header = writer -> {
    XMLEventFactory factory = XMLEventFactory.newFactory();
    writer.add(factory.createComment("Generated by Spring Batch"));
};
~~~

Callbacks can be configured via the builder or setter corresponding to your Spring Batch version:

~~~java
@Bean
StaxEventItemWriter<OrderXml> orderXmlWriter(
        Marshaller orderMarshaller,
        Resource outputResource) {

    StaxWriterCallback header = writer -> {
        XMLEventFactory factory = XMLEventFactory.newFactory();
        writer.add(factory.createComment("Order export"));
    };

    return new StaxEventItemWriterBuilder<OrderXml>()
            .name("orderXmlWriter")
            .resource(outputResource)
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .headerCallback(header)
            .saveState(true)
            .build();
}
~~~

Callbacks must write valid XML events at the right lifecycle point. Do not write a separate root element in the header when the writer already manages the root element. Likewise, a footer callback must not emit structure that closes the root twice or leaves the document with multiple roots.

If you only need to add comments or processing instructions, callbacks fit well. For complex XML structural changes, design a dedicated model/marshaller or custom writer instead of injecting arbitrary XML strings.

## 10. Writing XML by chunks

StaxEventItemWriter participates in a chunk-oriented Step like other ItemWriters. When a chunk finishes, the writer writes the chunk's items; transaction boundaries and writer buffering determine when content is actually flushed to the resource.

Example with chunk size 200:

~~~text
Chunk 1: 200 OrderXml -> marshal -> write XML items -> commit
Chunk 2: 200 OrderXml -> marshal -> write XML items -> commit
Chunk 3: 200 OrderXml -> marshal -> write XML items -> commit
...
Step ends -> close root/document and resource
~~~

Chunk size does not determine the root tag or item structure. It determines the batch of items processed within one transaction. When a chunk fails, items may be reprocessed per the Step's retry/restart semantics.

Do not split the file into multiple independent XML documents if the contract requires a single document. The writer manages one root element for the Step's resource and writes items as child elements.

## 11. Transactional writer and rollback

The writer can support transactional behavior by buffering chunk content and writing completed output only when the transaction commits. When a transaction rolls back, uncommitted output can be discarded from the buffer instead of leaving partial chunks in the file.

StaxEventItemWriter's transactional property must be understood according to the framework version and configured transaction synchronization. If transactional behavior is disabled, data may be written directly to the resource before the database transaction commits.

Critical point: the filesystem does not automatically participate in JDBC transactions. Even when the writer coordinates commit/rollback at the chunk level, never treat the database and file as a distributed atomic transaction. A process crash or filesystem error at the wrong moment can leave business data and output files out of sync.

To protect data:
- Keep transactional behavior aligned with requirements.
- Test writer failures and mid-chunk rollbacks.
- Use staging files keyed by JobInstance.
- Publish output only after Job/Step completion and verification.
- Maintain checksums, record counts, or manifests for reconciliation.
- Design the publish step to be safely retryable.

## 12. Checkpoint and restart

StaxEventItemWriter is an ItemStream writer and can save state in the Step ExecutionContext. When the Step restarts, the writer uses the saved checkpoint to resume the output resource.

Key conditions:

- The writer has a stable name.
- The resource path does not change between the initial run and restart.
- saveState(true) is enabled when checkpoints are needed.
- The partially written file still exists and has not been modified externally.
- Marshaller, root tag, encoding, and format remain compatible.
- The Job restarts with the same JobInstance and identifying JobParameters.
- Upstream components maintain the same data meaning and item order.

If the output file is deleted or replaced while metadata still holds checkpoints, the writer may fail to recover properly. Do not delete the old file before restart and do not manually append outside the writer's lifecycle.

For restarts, test the exact behavior of your version of StaxEventItemWriter: how it saves position, how it reopens the resource, and how it handles root/footer elements written previously. Do not guess that the writer merely appends bytes to the end of the file.

## 13. Stable file names per JobInstance

If each JobInstance produces one XML document, the output path should remain stable across restarts of that instance.

You can derive the path from the JobInstance ID in a JobExecutionListener:

~~~java
public class XmlOutputPathListener implements JobExecutionListener {

    @Override
    public void beforeJob(JobExecution execution) {
        long instanceId =
                execution.getJobInstance().getInstanceId();

        String path =
                "/batch/output/orders-" + instanceId + ".xml";

        execution.getExecutionContext().putString(
                "xml.output.path", path);
    }
}
~~~

A step-scoped writer reads the path from Job ExecutionContext:

~~~java
@Bean
@StepScope
StaxEventItemWriter<OrderXml> orderXmlWriter(
        Marshaller orderMarshaller,
        @Value("#{jobExecutionContext['xml.output.path']}")
        String outputPath) {

    return new StaxEventItemWriterBuilder<OrderXml>()
            .name("orderXmlWriter")
            .resource(new FileSystemResource(outputPath))
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .encoding("UTF-8")
            .saveState(true)
            .build();
}
~~~

The JobInstance ID stays the same across restarts of the same instance, whereas JobExecution ID changes. Therefore, naming outputs by JobInstance helps the writer reopen the right resource and restore checkpoints.

In multi-JobRepository or multi-environment deployments, IDs may only be unique within a single repository. You can include normalized Job name, tenant, or environment in the output directory path.

## 14. overwriteOutput and existing files

overwriteOutput determines whether the writer is allowed to replace an existing resource when starting to write new output. Choose this policy based on the JobInstance lifecycle.

Distinguish:
- **New JobInstance:** usually creates a new output file with its own name.
- **Restart of same JobInstance:** must resume the existing resource using the checkpoint.
- **Rerunning with new business logic:** create a new JobInstance and new output path if preserving history.

Do not blindly enable overwrite assuming restarts are always safe. Verify how your writer version distinguishes a fresh launch from a checkpointed restart. Do not delete files before the framework has a chance to restore state.

If a file exists without a valid checkpoint, it may be orphaned output from a crash or unsynchronized metadata. Investigate JobExecution/StepExecution and committed data before deciding to delete, rename, or recreate the file.

## 15. shouldDeleteIfEmpty

Some StaxEventItemWriter configurations allow deleting the resource if zero items were written, via the shouldDeleteIfEmpty option.

This option can be useful when downstream expects a file only when data exists. However, define the contract clearly:
- Is an empty file a valid outcome?
- How does the consumer distinguish no file from an XML file with an empty root?
- Is a Job completing with zero items considered successful?
- Can a restart proceed after a zero-item state?

If downstream requires a valid XML document even with zero items, keeping a file with an empty root element may be better. If absence of a file means "no data", delete-if-empty may fit. Test both cases and align with the consumer.

## 16. XML namespaces and schemas

An XML contract may require namespaces, prefixes, attributes, or schema versions. These are typically defined in JAXB annotations or marshaller mappings.

Example:

~~~java
@XmlRootElement(
        name = "order",
        namespace = "urn:example:orders:v1")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    @XmlElement(namespace = "urn:example:orders:v1")
    private long id;
}
~~~

Ensure the root element produced by the writer and item elements produced by the marshaller are namespace-compatible. If the root has no namespace while items use another namespace, the consumer or XSD may reject the document.

Regarding namespace prefixes, the JAXB provider may pick a default or configured prefix. Do not rely on a specific prefix if the contract only requires the namespace URI. If downstream insists on a fixed prefix, configure the provider or custom namespace mapping and verify the output.

Validate XML against the consumer's XSD/contract, covering:
- Namespace URI.
- Root element.
- Item element.
- Required/optional elements.
- Attribute and element ordering if enforced by schema.
- Date/time formats.
- Decimal precision.
- Null/empty value handling.

## 17. Handling nulls, collections, and data types

The Marshaller determines how Java values are represented in XML. Cases to watch:

- null may be omitted or represented using xsi:nil, depending on JAXB annotations and configuration.
- Collections may be wrapped by a wrapper element or written as repeated elements, depending on the model.
- BigDecimal needs precision/scale matching the contract.
- Date/time values need consistent timezones and formats.
- Enums may be marshalled by enum name or by values defined via an adapter.
- Booleans and numeric types need formatting understood by the consumer.

Example wrapped collection:

~~~java
@XmlElementWrapper(name = "lines")
@XmlElement(name = "line")
private List<OrderLineXml> lines;
~~~

The output looks like:

~~~xml
<order>
    <lines>
        <line>...</line>
        <line>...</line>
    </lines>
</order>
~~~

Do not rely on default mappings when XML is an integration interface across multiple systems. Explicitly declare key elements and verify against the schema or consumer-accepted sample files.

## 18. Header/footer and complete XML documents

An XML document must have exactly one root element. The writer manages the root and closes the document when the Step ends. Header/footer callbacks should only add appropriate events at the lifecycle points where they are invoked.

Do not write a second root element in the header or footer. Do not let a footer close a root element that the writer will close again. Do not write unescaped free-form text into the XML event stream.

If document-level metadata is needed, you can:
- Place metadata in attributes or child elements of the root per schema.
- Create an appropriate wrapper model.
- Use callbacks to add comments or processing instructions.
- Build a custom writer if the document structure exceeds standard writer capabilities.

If a metadata element is needed before all orders, yet still inside the root, check the event ordering emitted by the writer and callbacks. Consumers often rely on schemas and element order, so never insert elements arbitrarily.

## 19. Resource lifecycle and file locking

StaxEventItemWriter opens the resource during the Step lifecycle and closes it when the Step finishes. Never open the same file from another component while the writer is active.

Principles:
- Only one writer owns an output resource at a time.
- Do not let logs, callbacks, or other services write directly into the same file.
- Ensure the output directory exists and the process has write permissions.
- Close the writer through the framework lifecycle.
- Do not read the file as finished output before the Step finishes.
- Do not delete or rename the file while the writer is open.
- Monitor disk space and handle I/O errors.

If a Job is killed abruptly, the file may lack its closing root element or footer. That is incomplete output and must not be processed by consumers. Use a staging directory or a .part extension, then publish after verification succeeds.

## 20. Partitioning and multiple parallel writers

StaxEventItemWriter must not be used concurrently by multiple workers writing to the same file without explicit coordination. An XML event stream requires consistent ordering; independent writers can interleave events or corrupt the document.

With partitioning, a common pattern is having each partition write its own file:

~~~text
orders-instance-52/
    partition-0.xml
    partition-1.xml
    partition-2.xml
    partition-3.xml
~~~

After workers complete, an aggregation or publish Step can:
- Read each XML file and merge items into a final document.
- Use a dedicated Job/Step to produce the combined file.
- Publish a manifest pointing to multiple partition files if the consumer supports it.

Do not concatenate XML files by simple byte joining if each file has its own XML declaration and root element. Parse each document and write items under a new root document, or design output as a multi-file format with a manifest.

Each partition should have a stable resource path across partition restarts. File names can combine the JobInstance ID and partition name/key.

## 21. Observing and handling marshal errors

Marshal errors can occur due to invalid models, wrong annotations, unsupported data types, schema mismatches, or unconvertible runtime values.

Log/record:
- JobInstance ID and JobExecution ID.
- Step name.
- Writer name.
- Item business key if safely identifiable.
- Marshal exception type.
- Number of items/chunks committed before the error.
- Output resource and file size.

Do not log entire objects if they contain personal or secret data. A marshal error may happen on one specific item; if the Step has a skip policy, skip only when business rules permit and the item can be isolated. Do not skip all XML errors, as mapping/schema bugs can affect every item.

If the schema or marshaller configuration is broken, fail the Step early rather than continuing to produce an incompatible file.

## 22. Testing StaxEventItemWriter

Test output using an XML parser or schema validation, not solely XML string comparison. Whitespace, attribute ordering, and namespace prefixes can vary while the document remains structurally equivalent.

Key scenarios:

| Scenario | What to verify |
|---|---|
| Single item | Valid root and one item element |
| Multiple items | Each item is marshalled into a separate element |
| Zero items | Empty file / empty root / delete-if-empty matches contract |
| Unicode | Vietnamese and special characters preserve encoding |
| XML special characters | &, <, >, quotes are escaped properly |
| Null fields | Omitted or represented per schema |
| Namespace | Root and items have matching namespaces |
| XSD | Output validates against consumer's schema |
| Header/footer | Callbacks do not break document structure |
| Marshal exception | Step handles errors per policy and does not publish broken files |
| Chunk rollback | Uncommitted chunk parts are not treated as finished output |
| Restart | Writer restores checkpoint and does not duplicate items |
| Existing file | overwrite/restart behaves per configuration |
| Partitioning | Workers do not overwrite or interleave each other's output |
| Disk/I/O error | Job fails clearly and resources are closed |

A restart integration test:
1. Run the Job with multiple chunks.
2. Fail the writer or Step after a few chunks have committed.
3. Verify JobExecution is FAILED and the staging file remains.
4. Restart the same JobInstance with the same output path.
5. Verify the writer resumes from the checkpoint.
6. Parse the complete XML, checking root, item count, and zero duplicate business keys.
7. Validate XSD and publish only when all required checks pass.

## 23. Common mistakes when configuring StaxEventItemWriter

**Forgetting to configure a Marshaller.** The writer does not know how to convert Java items to XML.

**Root tag mismatches contract.** The document has a different structure than the consumer expects.

**Model lacks proper JAXB mapping.** Items may marshal to the wrong element, wrong namespace, or fail to marshal.

**Mixing javax and jakarta JAXB.** Annotations and runtime providers are incompatible.

**Declared encoding mismatches actual bytes.** Consumers may read garbled characters.

**Not enabling saveState when restarts are needed.** The writer lacks checkpoints to resume properly.

**Changing writer name or resource path.** Old metadata no longer points to the right output state.

**Deleting the file on restart.** Previously committed chunks may be lost.

**Sharing one writer across multiple partitions.** XML events can interleave and corrupt the document.

**Letting consumers read an actively written file.** Consumers may receive a document missing its closing root.

**Writing XML via arbitrary string callbacks.** Can produce non-well-formed XML or broken namespaces.

**Assuming file and database commits are atomic.** The filesystem does not automatically join JDBC transactions.

## 24. Workflow for implementing StaxEventItemWriter

When building an XML export Step, follow this sequence:

1. Define the XML contract: root, item element, namespace, schema, and encoding.
2. Create an XML DTO or JAXB model matching the contract.
3. Configure the Spring OXM Marshaller and pick Jakarta/Javax matching your version.
4. Declare StaxEventItemWriter with name, resource, marshaller, and rootTagName.
5. Choose encoding, overwrite, saveState, and transactional settings per requirements.
6. Use a processor to map domain objects into XML DTOs if needed.
7. Wire the writer into a chunk-oriented Step with an appropriate chunk size.
8. Keep writer name, output path, and mappings stable when restart is needed.
9. Use separate staging and publishing so downstream receives only complete XML.
10. With partitioning, create separate output resources per worker and aggregate cleanly.
11. Test XML via parser/XSD, Unicode, nulls, marshal failures, rollbacks, and restarts.
12. Monitor I/O, file size, written item counts, and marshal errors in operations.

StaxEventItemWriter fits when exporting many items into a single XML document in a streaming fashion. The Marshaller determines how each object becomes an element; the writer manages the root, resource, and checkpoints; chunk transactions define processing boundaries. By keeping configuration stable, controlling resource lifecycles, and publishing files only after completion, the application can generate large XML files while supporting restarts and delivering valid documents to downstream systems.
