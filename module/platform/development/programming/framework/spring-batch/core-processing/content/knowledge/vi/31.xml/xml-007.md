# Restart vị trí trong XML

Trong Spring Batch, một job đọc file XML có thể xử lý hàng nghìn hoặc hàng triệu fragment. Nếu job dừng giữa chừng, lần chạy tiếp theo cần tiếp tục từ vị trí đã commit thay vì xử lý lại toàn bộ file hoặc bỏ sót dữ liệu.

Với `StaxEventItemReader`, Spring Batch hỗ trợ restart bằng cách lưu trạng thái đọc vào `ExecutionContext`. Reader theo dõi số item XML đã đọc, lưu checkpoint theo từng chunk và khôi phục vị trí logic khi job được restart. Vị trí này là vị trí theo số fragment/item đã xử lý, không phải byte offset tùy ý trong file.

Để restart chính xác, reader phải có tên ổn định, bật lưu state, dùng cùng JobInstance khi restart và đọc lại đúng resource có nội dung không thay đổi. Cần phân biệt vị trí của reader bên trong file XML với việc Spring Batch chọn step nào để chạy lại.

## 1. XML reader và restart trong Spring Batch

Spring Batch thường dùng `StaxEventItemReader<T>` để đọc các fragment XML thành item Java. Reader dựa trên StAX streaming API nên không cần nạp toàn bộ document vào bộ nhớ như cách parse DOM.

Ví dụ file có root `<orders>` và nhiều phần tử `<order>`:

```xml
<orders>
    <order>
        <id>1001</id>
        <customerId>C001</customerId>
        <amount>125.50</amount>
    </order>
    <order>
        <id>1002</id>
        <customerId>C002</customerId>
        <amount>89.00</amount>
    </order>
    <order>
        <id>1003</id>
        <customerId>C003</customerId>
        <amount>210.00</amount>
    </order>
</orders>
```

Nếu `fragmentRootElementName` là `order`, mỗi phần tử `<order>` được ánh xạ thành một item. Reader lần lượt trả về order 1001, 1002, 1003 rồi trả `null` khi hết dữ liệu.

Khi step commit một chunk, Spring Batch lưu state của reader. Nếu execution bị dừng sau khi đã commit hai order, lần restart sẽ khôi phục checkpoint và tiếp tục từ order chưa được commit.

## 2. Phân biệt vị trí XML với vị trí step trong job

Có hai khái niệm restart thường bị nhầm:

| Khái niệm | Ý nghĩa | Được quản lý bởi |
|---|---|---|
| Vị trí trong XML input | Fragment/item tiếp theo mà reader cần xử lý | Reader state trong `ExecutionContext` |
| Vị trí trong job flow | Step nào đã hoàn thành, step nào cần chạy lại | `JobRepository`, `JobExecution` và `StepExecution` metadata |

Ví dụ job có ba step:

```text
validateXmlStep       -> COMPLETED
importXmlStep         -> FAILED ở giữa file
archiveXmlStep        -> chưa chạy
```

Khi restart cùng JobInstance, Spring Batch thường bỏ qua `validateXmlStep` đã hoàn thành, khởi chạy lại `importXmlStep` theo checkpoint reader và chỉ chạy `archiveXmlStep` khi step import hoàn tất.

Việc reader khôi phục fragment không thay thế cơ chế restart step. Cả metadata của job/step lẫn state của reader đều cần được lưu đúng.

## 3. StaxEventItemReader lưu vị trí như thế nào?

`StaxEventItemReader` thuộc nhóm reader có khả năng đếm item và lưu state. Khi mở reader, nó đọc state đã lưu trong `ExecutionContext`; khi restart, reader mở lại resource và tiến tới số fragment đã được checkpoint trước đó.

Với XML ở ví dụ trên, nếu checkpoint ghi nhận hai item đã hoàn thành, vị trí logic cần tiếp tục là fragment thứ ba.

```text
File XML: order 1001 | order 1002 | order 1003 | order 1004
                         
Lần chạy đầu:
  đọc order 1001
  đọc order 1002
  ghi chunk và COMMIT
  checkpoint = 2 item
  lỗi trước khi chunk tiếp theo commit

Restart:
  mở lại XML resource
  khôi phục checkpoint = 2
  bỏ qua hai fragment đã được checkpoint
  tiếp tục từ order 1003
```

Đây là vị trí theo item/fragment mà reader nhận diện, không phải byte offset chính xác trong file. Với XML, độ dài mỗi fragment có thể khác nhau và parser cần hiểu cấu trúc XML để xác định ranh giới.

## 4. ExecutionContext giữ checkpoint

`ExecutionContext` là vùng lưu trạng thái của một `StepExecution` hoặc `JobExecution`. Reader triển khai `ItemStream`, vì vậy Spring Batch gọi các callback lifecycle để mở resource, cập nhật state và đóng reader.

Ba callback quan trọng:

- `open(executionContext)`: mở resource và khôi phục state đã lưu nếu có.
- `update(executionContext)`: ghi state hiện tại vào context để Spring Batch lưu checkpoint.
- `close()`: giải phóng parser và resource khi step kết thúc.

Trong chunk processing, checkpoint được cập nhật theo ranh giới commit của chunk. Nếu chunk chưa commit và execution gặp lỗi, lần restart phải tiếp tục từ checkpoint gần nhất đã được lưu bền vững.

`ExecutionContext` không phải biến Java tạm trong memory. Với cấu hình JDBC repository thông thường, Spring Batch lưu context vào metadata repository để có thể đọc lại ở JobExecution tiếp theo.

## 5. Cấu hình StaxEventItemReader bằng Java

Ví dụ reader đọc từng fragment `<order>` và ánh xạ bằng `Jaxb2Marshaller`:

```java
@Bean
Jaxb2Marshaller orderUnmarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Order.class);
    return marshaller;
}

@Bean
@StepScope
StaxEventItemReader<Order> orderXmlReader(
        @Value("#{jobParameters['input.file']}") String inputFile,
        Jaxb2Marshaller orderUnmarshaller) {

    return new StaxEventItemReaderBuilder<Order>()
        .name("orderXmlReader")
        .resource(new FileSystemResource(inputFile))
        .addFragmentRootElements("order")
        .unmarshaller(orderUnmarshaller)
        .saveState(true)
        .build();
}
```

Những cấu hình quan trọng:

- `name("orderXmlReader")`: tên ổn định được dùng để định danh state của reader trong `ExecutionContext`.
- `resource(...)`: resource XML cần đọc; có thể late-bind từ JobParameters.
- `addFragmentRootElements("order")`: xác định phần tử gốc của mỗi item.
- `unmarshaller(...)`: chuyển fragment XML thành object Java.
- `saveState(true)`: cho phép reader lưu state phục vụ restart.
- `@StepScope`: tạo reader target theo StepExecution và resolve input file khi step chạy.

Đừng đổi tên reader giữa lần chạy và restart cùng JobInstance. Tên reader tham gia vào việc tạo key state; thay tên có thể khiến reader không tìm được checkpoint cũ.

## 6. Cấu hình XML namespace cho reader

Nếu cấu hình Spring Batch bằng XML, reader có thể được khai báo như một bean Spring. Ví dụ dưới đây dùng step scope để lấy file path từ JobParameters:

```xml
<bean id="orderXmlReader"
      class="org.springframework.batch.item.xml.StaxEventItemReader"
      scope="step">
    <property name="name" value="orderXmlReader"/>
    <property name="resource" value="#{jobParameters['input.file']}"/>
    <property name="fragmentRootElementName" value="order"/>
    <property name="unmarshaller" ref="orderUnmarshaller"/>
    <property name="saveState" value="true"/>
    <aop:scoped-proxy/>
</bean>
```

Để dùng `<aop:scoped-proxy/>`, file cấu hình cần khai báo namespace AOP tương ứng. Bean `orderUnmarshaller` cần được cấu hình để ánh xạ fragment `Order` theo schema XML của ứng dụng.

Scoped proxy cho phép step bean được tạo trong application context trước khi có JobExecution, trong khi reader target chỉ được tạo khi StepScope hoạt động.

## 7. Khai báo job và chunk step trong XML

Job XML có thể dùng chunk step với reader đã khai báo ở trên:

```xml
<batch:job id="importOrdersJob" restartable="true">
    <batch:step id="importOrdersStep">
        <batch:tasklet transaction-manager="transactionManager">
            <batch:chunk
                    reader="orderXmlReader"
                    processor="orderProcessor"
                    writer="orderWriter"
                    commit-interval="100"/>
        </batch:tasklet>
    </batch:step>
</batch:job>
```

`restartable="true"` cho phép job được restart theo quy tắc Spring Batch. `commit-interval="100"` đặt chunk size là 100 item; reader state được checkpoint theo tiến độ chunk đã commit.

Trong cấu hình thực tế, cần khai báo đầy đủ namespace `batch`, `aop`, schema location và bean `transactionManager`, `orderProcessor`, `orderWriter`. Tên reader trong step phải trỏ đúng bean scoped proxy.

## 8. saveState và name quyết định khả năng khôi phục

Reader phải lưu state nếu muốn khôi phục vị trí sau restart. Với `StaxEventItemReader`, nên cấu hình rõ `saveState(true)` thay vì dựa vào giá trị mặc định.

```java
return new StaxEventItemReaderBuilder<Order>()
    .name("orderXmlReader")
    .resource(resource)
    .addFragmentRootElements("order")
    .unmarshaller(unmarshaller)
    .saveState(true)
    .build();
```

`saveState(false)` khiến reader không ghi checkpoint của chính nó vào `ExecutionContext`. Nếu step thất bại rồi được restart, reader không thể dùng state đã lưu để khôi phục item count như mong đợi; ứng dụng có thể phải đọc lại từ đầu hoặc dùng một cơ chế phục hồi khác.

Không dùng cùng một reader name cho nhiều reader stateful trong cùng step nếu chúng có thể ghi đè key trong context. Đặt tên ổn định, duy nhất và không phụ thuộc thời gian chạy.

## 9. Restart phải dùng cùng JobInstance

Spring Batch xác định `JobInstance` bằng tên job và các identifying `JobParameters`. Khi restart, cần dùng lại cùng bộ identifying parameters của lần chạy ban đầu.

Ví dụ lần đầu:

```java
JobParameters parameters = new JobParametersBuilder()
    .addString("input.file", "/data/orders-2026-11-15.xml", true)
    .addString("businessDate", "2026-11-15", true)
    .toJobParameters();

jobLauncher.run(importOrdersJob, parameters);
```

Nếu execution thất bại giữa file, hãy launch lại cùng job với cùng identifying parameters:

```java
JobParameters restartParameters = new JobParametersBuilder()
    .addString("input.file", "/data/orders-2026-11-15.xml", true)
    .addString("businessDate", "2026-11-15", true)
    .toJobParameters();

jobLauncher.run(importOrdersJob, restartParameters);
```

Đây là restart cùng JobInstance nếu instance trước đó ở trạng thái có thể restart. Spring Batch tạo JobExecution mới nhưng sử dụng metadata và checkpoint đã lưu của instance cũ.

Nếu thêm timestamp hoặc `run.id` mới dưới dạng identifying parameter, Spring Batch tạo JobInstance mới. Reader khi đó không tiếp tục checkpoint của instance thất bại.

## 10. Resource XML phải ổn định giữa các lần chạy

Checkpoint chỉ có ý nghĩa khi lần restart đọc đúng cùng một nguồn dữ liệu. Nếu file tại cùng đường dẫn bị thay thế, vị trí item đã lưu có thể trỏ sang một nội dung hoàn toàn khác.

Ví dụ:

```text
Lần chạy đầu:
  /data/orders.xml chứa 10.000 order
  checkpoint = 4.000 order

Trước khi restart:
  file tại /data/orders.xml bị thay bằng file mới
  thứ tự và nội dung fragment thay đổi

Restart:
  reader bỏ qua 4.000 fragment trong file mới
  các order còn lại không còn tương ứng với lần chạy đầu
```

Các biện pháp nên áp dụng:

- Đưa file vào thư mục immutable theo batch ID hoặc file ID.
- Không ghi đè file nguồn trong khi job đang chạy hoặc có thể restart.
- Tính checksum hoặc lưu version nguồn để xác nhận file không đổi.
- Đưa source ID, file version hoặc checksum vào identifying JobParameters khi chúng xác định tập dữ liệu.
- Nếu cần restart, giữ lại đúng file gốc cho đến khi JobInstance hoàn tất.

Không chỉ dùng tên file làm identity nếu cùng tên có thể được tái sử dụng cho nội dung khác. Một mã file bất biến hoặc checksum có thể mô tả nguồn tốt hơn.

## 11. Checkpoint được lưu theo chunk, không theo từng byte

Giả sử chunk size là 100. Reader có thể đọc trước một số fragment để tạo chunk; khi writer và transaction hoàn tất, Spring Batch cập nhật state để lần restart tiếp tục từ checkpoint phù hợp.

```text
Chunk 1: fragments 1..100   -> COMMIT -> checkpoint 100
Chunk 2: fragments 101..200 -> COMMIT -> checkpoint 200
Chunk 3: fragments 201..300 -> lỗi trước commit

Restart:
  khôi phục checkpoint 200
  tiếp tục từ fragment 201
```

Vị trí được khôi phục là tiến độ đã commit. Nếu process chết sau khi đọc item nhưng trước khi chunk commit, item đó có thể được đọc lại. Điều này là hành vi cần thiết để không bỏ sót dữ liệu chưa commit.

Vì vậy, writer và các side effect ngoài transaction phải an toàn khi item được xử lý lại. Không dựa vào giả định mỗi fragment chỉ được đọc hoặc xử lý đúng một lần.

## 12. Reader phải có thứ tự fragment xác định

Restart theo item count giả định rằng thứ tự các fragment khi đọc lại vẫn giống lần chạy trước. Nếu thứ tự thay đổi, cùng một checkpoint có thể dẫn tới item khác.

Với một file XML tĩnh, thứ tự phần tử thường được xác định bởi thứ tự xuất hiện trong document. Nhưng nếu XML được tạo lại, sort lại hoặc ghép từ nhiều nguồn trước khi restart, thứ tự có thể thay đổi.

Nếu nguồn được tạo động, hãy lưu snapshot bất biến hoặc tạo một manifest có thứ tự ổn định. Không chỉnh sửa file giữa lần chạy và restart.

Với nhiều file XML, cần giữ cả danh sách resource và thứ tự sắp xếp ổn định. Việc thêm/xóa file ở đầu danh sách có thể làm thay đổi ý nghĩa vị trí đã checkpoint.

## 13. Restart với nhiều file XML

Nếu job đọc nhiều resource, có thể dùng `MultiResourceItemReader` với `StaxEventItemReader` làm delegate. Wrapper lưu trạng thái resource hiện tại và delegate lưu trạng thái đọc trong file hiện tại.

```java
@Bean
@StepScope
MultiResourceItemReader<Order> allOrderFilesReader(
        @Value("#{jobParameters['input.directory']}") String directory,
        StaxEventItemReader<Order> orderXmlReader) throws IOException {

    Resource[] resources = new PathMatchingResourcePatternResolver()
        .getResources("file:" + directory + "/*.xml");
    Arrays.sort(resources, Comparator.comparing(Resource::getFilename));

    return new MultiResourceItemReaderBuilder<Order>()
        .name("allOrderFilesReader")
        .resources(resources)
        .delegate(orderXmlReader)
        .saveState(true)
        .build();
}
```

Danh sách resource phải được sắp xếp ổn định. Nếu lần đầu danh sách là `a.xml`, `b.xml`, `c.xml` nhưng restart lại thêm `0.xml` vào đầu, index resource đã lưu có thể trỏ đến file khác.

Đối với nhiều file, giữ nguyên danh sách file hoặc manifest của lần chạy ban đầu. Nếu file được phát sinh liên tục, hãy chụp manifest trước khi launch và dùng manifest đó cho restart.

## 14. XML fragment và unmarshaller phải ổn định

`StaxEventItemReader` xác định item dựa trên fragment root element được cấu hình. Nếu đổi `fragmentRootElementName`, unmarshaller hoặc mapping schema giữa lần chạy và restart, cùng vị trí item có thể được diễn giải khác.

Các thành phần cần giữ ổn định:

- Tên fragment root, ví dụ `order`.
- Cấu hình namespace XML nếu nguồn dùng namespace.
- Unmarshaller và class mapping.
- Quy tắc xử lý version schema.
- Thứ tự fragment trong resource.

Nếu nhà cung cấp thay schema XML trong khi job còn khả năng restart, cần giữ phiên bản mapping tương ứng hoặc chuyển file sang snapshot/version mới. Không restart một JobInstance cũ bằng parser có semantics khác mà không có kế hoạch migration.

## 15. Namespace XML

XML có thể dùng namespace mặc định hoặc prefix. Fragment root và unmarshaller cần tương thích với cấu trúc namespace thực tế. Một file có `<o:order>` hoặc namespace mặc định vẫn có local name là `order`, nhưng mapping JAXB cần khai báo namespace theo schema.

Ví dụ:

```xml
<orders xmlns="urn:example:orders:v1">
    <order>
        <id>1001</id>
    </order>
</orders>
```

Class JAXB có thể cần `@XmlRootElement(name = "order", namespace = "urn:example:orders:v1")` hoặc package-level namespace mapping tương ứng.

Nếu namespace hoặc schema version thay đổi, reader có thể không tìm thấy fragment hoặc unmarshaller có thể thất bại. Lỗi schema không nên được xử lý bằng cách thay checkpoint; hãy xác định đúng parser/schema version của nguồn.

## 16. Reader name và ExecutionContext key

Reader name là một phần của định danh state được lưu. Khi tên thay đổi, reader có thể tìm key khác và không khôi phục được vị trí cũ.

Ví dụ tên ổn định:

```java
.name("orderXmlReader")
.saveState(true)
```

Tránh tạo tên động như:

```java
// Tránh tên thay đổi theo từng lần launch
.name("orderXmlReader-" + System.currentTimeMillis())
```

Tên động làm mất liên kết giữa state cũ và reader mới. Với nhiều reader trong cùng step, chọn tên khác nhau nhưng ổn định theo vai trò.

## 17. allow-start-if-complete và start-limit

Restart vị trí trong XML còn phụ thuộc việc step có được chạy lại hay không. Mặc định, step đã hoàn thành trong JobInstance thường không chạy lại khi job được restart. Hai thuộc tính step thường được cấu hình trong XML là:

- `allow-start-if-complete`: cho phép một step đã hoàn thành được chạy lại khi job restart.
- `start-limit`: giới hạn số lần step được phép bắt đầu.

Ví dụ:

```xml
<batch:step id="importXmlStep"
            allow-start-if-complete="false"
            start-limit="3">
    <batch:tasklet transaction-manager="transactionManager">
        <batch:chunk reader="orderXmlReader"
                     writer="orderWriter"
                     commit-interval="100"/>
    </batch:tasklet>
</batch:step>
```

`allow-start-if-complete="true"` chỉ nên dùng khi có chủ đích chạy lại step đã hoàn thành trong cùng JobInstance. Nếu bật tùy tiện, step có thể xử lý lại dữ liệu và tạo side effect trùng.

`start-limit` giới hạn số lần khởi chạy step; nó không phải số lần retry item và cũng không phải checkpoint XML. Nếu vượt giới hạn, step không thể được khởi chạy thêm theo cấu hình đó.

## 18. Job restartable và JobInstance đã hoàn tất

Job có thể được cấu hình `restartable="false"` trong XML. Khi đó Spring Batch không cho phép restart JobInstance theo cách thông thường.

```xml
<batch:job id="importOrdersJob" restartable="true">
    <!-- steps -->
</batch:job>
```

Để restart một execution thất bại, cần:

1. Job được phép restart.
2. JobInstance ở trạng thái có thể restart.
3. Dùng cùng identifying JobParameters.
4. Reader có state đã lưu và resource vẫn đúng.
5. Step không bị giới hạn start count hoặc cấu hình ngăn chạy lại.

Nếu JobInstance đã `COMPLETED`, launch cùng identifying parameters thường bị từ chối. Muốn xử lý lại dữ liệu đã hoàn tất như một lần nghiệp vụ mới, hãy tạo identifying parameters mới hoặc thiết kế job reprocessing riêng.

## 19. Skip, retry và vị trí XML

Reader có thể gặp lỗi parse ở một fragment XML. Nếu step cho phép skip loại exception phù hợp, Spring Batch có thể loại item lỗi và tiếp tục. Nếu lỗi không thể phục hồi hoặc vượt skip limit, step thất bại.

```java
return new StepBuilder("importXmlStep", jobRepository)
    .<Order, Order>chunk(100, transactionManager)
    .reader(orderXmlReader)
    .writer(orderWriter)
    .faultTolerant()
    .skip(InvalidXmlRecordException.class)
    .skipLimit(20)
    .build();
```

Ví dụ exception cụ thể phụ thuộc unmarshaller và cách ứng dụng bọc lỗi parse. Chỉ skip lỗi thuộc riêng một fragment và có thể loại bỏ theo nghiệp vụ. Nếu XML malformed ở cấp document, thiếu closing tag hoặc sai namespace/schema trên toàn file, bỏ qua từng item có thể không khả thi; nên fail để điều tra nguồn.

Retry cũng cần được phân loại. Lỗi tạm thời khi truy cập resource có thể retry theo policy thích hợp; lỗi XML malformed cố định không tự hết khi đọc lại.

## 20. Reader state không bảo đảm exactly-once side effect

Checkpoint bảo vệ tiến độ reader tại ranh giới commit, nhưng không tự bảo đảm mọi side effect bên ngoài chỉ xảy ra một lần.

Ví dụ processor/writer gửi message hoặc gọi API trước khi chunk commit. Nếu process chết sau khi hệ thống ngoài nhận request nhưng trước khi JobRepository lưu checkpoint, restart có thể đọc lại fragment và gửi request lần nữa.

Các biện pháp:

- Dùng idempotency key dựa trên ID nghiệp vụ của fragment.
- Ghi event vào outbox trong cùng database transaction với dữ liệu batch rồi publish sau commit.
- Dùng unique constraint/upsert cho output có thể được ghi lại.
- Ghi output vào staging và chỉ publish sau khi step hoàn tất.
- Đối soát request timeout vì client có thể không biết hệ thống ngoài đã xử lý hay chưa.

Không coi `saveState(true)` là cam kết exactly-once cho HTTP, email, message broker hoặc filesystem.

## 21. XML file lớn và chi phí restart

`StaxEventItemReader` dùng streaming để tránh giữ toàn bộ XML document trong memory. Tuy nhiên, khôi phục vị trí theo item count có thể cần mở lại file và tiến qua các fragment đã được checkpoint.

Với file rất lớn và checkpoint nằm gần cuối file, thời gian restart có thể tăng vì reader phải đọc/skip các fragment trước vị trí đó. Đây là trade-off của cách khôi phục theo item count thay vì seek đến byte offset.

Nếu restart từ vị trí rất xa là yêu cầu thường xuyên, có thể cân nhắc:

- Chia nguồn thành nhiều file hoặc nhiều batch nhỏ.
- Tạo manifest với các segment độc lập.
- Partition theo file hoặc theo khóa dữ liệu nếu có thể xác định ranh giới độc lập.
- Dùng nguồn dữ liệu có hỗ trợ seek/checkpoint trực tiếp nếu workload yêu cầu.
- Lưu snapshot bất biến để việc đọc lại các fragment đầu không bị thay đổi.

Không tự sửa `ExecutionContext` để đặt item count tùy ý nếu không hiểu reader state và dữ liệu tương ứng. Sai checkpoint có thể bỏ sót hoặc xử lý trùng fragment.

## 22. Lỗi thường gặp khi restart XML

| Lỗi | Hệ quả | Cách xử lý |
|---|---|---|
| Không bật `saveState` | Reader không có checkpoint để khôi phục vị trí | Bật `.saveState(true)` hoặc property `saveState=true` |
| Đổi reader `name` | Không tìm thấy state key cũ | Giữ tên reader ổn định |
| Đổi identifying JobParameters khi restart | Tạo JobInstance mới, không dùng checkpoint cũ | Dùng lại identifying parameters ban đầu |
| Thay nội dung file tại cùng path | Item count cũ trỏ tới fragment khác | Giữ input immutable và dùng source version/checksum |
| Thay thứ tự nhiều resource | Resource index cũ có thể trỏ sai file | Dùng manifest và thứ tự ổn định |
| Đổi fragment root hoặc unmarshaller | Cùng vị trí được parse theo cấu trúc khác | Giữ mapping/schema version cho JobInstance cũ |
| Nghĩ checkpoint là byte offset | Tìm vị trí sai trong XML | Hiểu state theo item/fragment count |
| Dùng `allow-start-if-complete=true` không chủ đích | Step đã hoàn thành có thể chạy lại và tạo side effect trùng | Chỉ bật khi step idempotent và nghiệp vụ cần |
| Tắt `restartable` ở job | Không thể restart JobInstance theo quy tắc thông thường | Cấu hình restartable nếu cần phục hồi |
| Coi skip là giải pháp cho XML malformed toàn file | Parser có thể không tiếp tục được | Fail file và xử lý nguồn/schema |
| Dùng reader singleton cho nhiều execution | State hoặc resource có thể bị chia sẻ sai | Dùng StepScope cho reader phụ thuộc execution |

## 23. Kiểm thử restart vị trí trong XML

Integration test nên tạo XML có các fragment dễ nhận diện, chạy job đến khi một chunk commit rồi cố ý làm step thất bại ở chunk sau.

Các trường hợp cần kiểm tra:

1. Đọc file XML bình thường: số fragment và object mapping đúng.
2. `saveState(true)`: state được ghi vào StepExecution `ExecutionContext` sau chunk commit.
3. Restart cùng JobInstance: reader tiếp tục từ fragment kế tiếp sau checkpoint.
4. Lỗi trước commit: fragment chưa commit được đọc lại khi restart.
5. Reader name thay đổi: test chứng minh state key không còn khớp; tránh thay đổi tên trong production.
6. JobParameters thay đổi: tạo JobInstance mới thay vì restart instance cũ.
7. File bị thay đổi: quy trình phát hiện source version/checksum không còn khớp.
8. MultiResource reader: thứ tự file và vị trí trong file hiện tại được khôi phục đúng.
9. `allow-start-if-complete`: step đã hoàn thành chỉ chạy lại khi cấu hình cho phép.
10. Output idempotency: item được đọc lại không tạo dữ liệu hoặc side effect trùng.

Test cần kiểm tra cả `JobInstance` ID, `JobExecution` ID, `StepExecution` status, `ExecutionContext` và dữ liệu đầu ra. Chỉ kiểm tra job hoàn thành sau restart là chưa đủ để chứng minh reader tiếp tục đúng vị trí.

## 24. Quy trình vận hành khi XML job cần restart

Khi một job đọc XML thất bại, hãy thực hiện theo thứ tự:

1. Xác định JobInstance và JobExecution thất bại trong JobRepository.
2. Kiểm tra step nào thất bại và reader nào đang lưu checkpoint.
3. Xác nhận `saveState` đang bật và reader name không thay đổi.
4. Xác nhận file nguồn, checksum/version và thứ tự resource giống lần chạy ban đầu.
5. Kiểm tra exception có phải lỗi tạm thời, lỗi một fragment hay lỗi cấu trúc toàn file.
6. Khắc phục nguyên nhân nhưng giữ nguyên identifying JobParameters nếu tiếp tục cùng nghiệp vụ.
7. Restart cùng JobInstance để Spring Batch dùng checkpoint đã lưu.
8. Đối chiếu số item đã đọc/ghi/skip và dữ liệu output sau restart.
9. Chỉ archive hoặc xóa file nguồn sau khi job hoàn tất và kết quả được xác minh.

Không tạo JobInstance mới chỉ để vượt trạng thái thất bại nếu mục tiêu là tiếp tục đúng lần xử lý đang dang dở.

## Kết luận

Restart vị trí trong XML của Spring Batch dựa trên state của reader được lưu trong `ExecutionContext`. `StaxEventItemReader` lưu tiến độ theo số fragment/item đã xử lý; khi restart, reader mở lại resource và khôi phục vị trí logic từ checkpoint gần nhất đã commit. Đây không phải byte offset trong file.

Để khôi phục đúng, giữ reader name và cấu hình fragment/unmarshaller ổn định, bật `saveState`, dùng lại identifying JobParameters và bảo đảm XML input cùng thứ tự resource không thay đổi. Cấu hình restart của job/step quyết định step nào được chạy lại; checkpoint của reader quyết định fragment nào được đọc tiếp. Kết hợp hai cơ chế với output idempotent và integration test để restart an toàn.
