# Encoding XML

Trong Spring Batch, XML thường được dùng làm định dạng trao đổi dữ liệu giữa các hệ thống. Khi đọc hoặc ghi XML, encoding quyết định cách chuyển ký tự Unicode thành byte và ngược lại. Một file có thể có cấu trúc XML hợp lệ nhưng vẫn bị lỗi khi đọc nếu byte được giải mã bằng charset sai, hoặc nếu khai báo encoding trong XML không khớp với encoding thực tế của file.

Khi xử lý XML trong batch job, cần phân biệt ba lớp:

1. **Ký tự trong dữ liệu Java:** chuỗi Java được biểu diễn bằng Unicode.
2. **Encoding của byte:** charset được dùng khi đọc byte từ file hoặc ghi byte ra file, ví dụ UTF-8 hoặc UTF-16.
3. **XML declaration:** thuộc tính encoding trong phần khai báo đầu tài liệu, mô tả encoding được dùng cho byte của XML entity.

Ba lớp này phải nhất quán. Nếu writer tạo byte UTF-8 nhưng khai báo encoding là ISO-8859-1, consumer có thể giải mã sai hoặc từ chối tài liệu. Nếu reader tự giải mã byte bằng charset sai trước khi đưa ký tự cho parser, XML declaration không thể khôi phục những ký tự đã bị biến dạng.

## 1. Encoding XML là gì?

XML là định dạng văn bản. Nội dung logic của XML là một chuỗi ký tự, nhưng file trên đĩa là một dãy byte. Encoding định nghĩa cách chuyển giữa hai dạng đó.

Ví dụ:

~~~xml
<customer>
    <name>Nguyễn Thị An</name>
    <city>Hồ Chí Minh</city>
</customer>
~~~

Nội dung có các ký tự tiếng Việt có dấu. Với UTF-8, mỗi ký tự được mã hóa thành một hoặc nhiều byte. Với UTF-16, ký tự thường được mã hóa bằng một hoặc hai code unit 16-bit. Nội dung XML về mặt ký tự vẫn như nhau, nhưng byte của hai file khác nhau.

Encoding không thay đổi cấu trúc XML như element, attribute, namespace hoặc thứ tự node. Nó chỉ quy định cách biểu diễn ký tự thành byte. Các quy tắc escape của XML như `&amp;`, `&lt;` và `&quot;` là vấn đề cú pháp/serialization, không phải charset.

## 2. XML declaration và thuộc tính encoding

Một XML document thường bắt đầu bằng XML declaration:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order id="ORD-1001">
        <customerName>Nguyễn Thị An</customerName>
    </order>
</orders>
~~~

Thuộc tính encoding cho XML processor biết byte của document được mã hóa theo charset nào. XML declaration có thể có version, encoding và standalone declaration; encoding thường được ghi tường minh để các hệ thống trao đổi file dễ hiểu thống nhất.

Một số điểm cần nhớ:

- XML declaration phải nằm ở đầu document, trước element gốc.
- Tên encoding phải tương ứng với encoding byte thực tế.
- UTF-8 là lựa chọn phổ biến và được hỗ trợ rộng.
- Nếu không có XML declaration, XML processor dựa vào quy tắc nhận diện encoding của XML và các byte đầu vào; không nên dựa vào charset mặc định của máy chạy.
- XML declaration không phải cơ chế chuyển đổi byte. Nó chỉ mô tả encoding của tài liệu.

Không chèn log hoặc ký tự khác trước XML declaration nếu writer cần tạo declaration ở đầu file. Một số parser cho phép BOM trước declaration theo quy tắc encoding; dữ liệu rác trước declaration có thể làm tài liệu không hợp lệ.

## 3. UTF-8, UTF-16 và các charset khác

Các encoding thường gặp:

| Encoding | Đặc điểm | Khi sử dụng |
|---|---|---|
| UTF-8 | Mã hóa Unicode theo byte, tương thích ASCII ở vùng ký tự cơ bản | Lựa chọn mặc định tốt cho hầu hết file XML mới |
| UTF-16 | Mã hóa Unicode theo code unit 16-bit, có thể cần xác định byte order | Khi hợp đồng tích hợp yêu cầu UTF-16 |
| ISO-8859-1 | Charset một byte cho tập ký tự Tây Âu | Chỉ dùng khi hệ thống cũ yêu cầu |
| Windows-1252 | Charset một byte phổ biến trên một số hệ thống Windows cũ | Khi file nguồn/đích có hợp đồng cụ thể |

UTF-8 thường là lựa chọn nên ưu tiên vì hỗ trợ tiếng Việt, các ngôn ngữ khác và phần lớn hệ thống hiện đại. Không nên chọn ISO-8859-1 chỉ vì file trông giống ASCII; các ký tự tiếng Việt sẽ không được biểu diễn đầy đủ.

Nếu hệ thống bên ngoài bắt buộc dùng charset legacy, hãy ghi rõ charset trong hợp đồng tích hợp, kiểm tra tập ký tự có thể biểu diễn và xác định cách xử lý ký tự ngoài repertoire. Không âm thầm thay ký tự không hỗ trợ bằng dấu hỏi vì dữ liệu có thể mất thông tin mà job vẫn hoàn tất.

## 4. Byte Order Mark (BOM)

BOM là một chuỗi byte ở đầu file có thể giúp nhận diện encoding hoặc byte order. Với UTF-8, BOM là tùy chọn; với UTF-16, BOM thường dùng để phân biệt big-endian và little-endian khi encoding được khai báo chung là UTF-16.

Ví dụ:

- UTF-8 BOM: `EF BB BF`.
- UTF-16 big-endian BOM: `FE FF`.
- UTF-16 little-endian BOM: `FF FE`.

Không phải mọi hệ thống đều mong đợi UTF-8 BOM. Một số parser xử lý nó bình thường, nhưng một số hệ thống cũ hoặc code tự đọc dòng có thể coi BOM là ký tự đầu tiên của tên element hoặc header. Khi tích hợp, xác định rõ file có BOM hay không.

Với XML parser nhận trực tiếp byte stream, parser thường có thể dùng BOM và XML declaration để nhận diện encoding theo quy tắc XML. Không nên tự strip BOM trước khi hiểu rõ parser và nguồn dữ liệu. Nếu ứng dụng tự chuyển byte thành String trước khi parse, cần xử lý BOM đúng cách để không để lại ký tự U+FEFF ở đầu nội dung.

## 5. Chọn encoding khi đọc XML bằng StAX

Spring Batch cung cấp `StaxEventItemReader<T>` để đọc các fragment XML thành item. Reader dùng StAX để đọc stream XML và dùng Spring OXM `Unmarshaller` để chuyển fragment thành object.

Ví dụ cấu hình:

~~~java
@Bean
@StepScope
StaxEventItemReader<Order> orderXmlReader(
        @Value("#{jobParameters['inputFile']}") Resource inputFile,
        Unmarshaller orderUnmarshaller) {

    return new StaxEventItemReaderBuilder<Order>()
            .name("orderXmlReader")
            .resource(inputFile)
            .addFragmentRootElements("order")
            .unmarshaller(orderUnmarshaller)
            .saveState(true)
            .build();
}
~~~

Khi reader nhận Resource và parser đọc từ byte stream, StAX/XML processor có thể xác định encoding từ BOM và XML declaration. Đây là cách phù hợp để parser xử lý đúng encoding được khai báo trong file.

Không nên tự đọc file thành String bằng charset mặc định rồi tạo một Reader ký tự nếu chưa biết encoding byte của nguồn. Khi parser chỉ nhận character stream, việc giải mã byte đã diễn ra trước đó; parser không còn khả năng tự quyết định cách giải mã byte ban đầu.

Nếu hợp đồng nguồn cố định là UTF-8, có thể kiểm tra byte hoặc cấu hình tầng đọc phù hợp để phát hiện file sai encoding. Điều quan trọng là chỉ có một nơi chịu trách nhiệm giải mã byte, và nơi đó dùng charset đúng.

## 6. XML declaration không sửa được charset đã giải mã sai

Giả sử file được ghi bằng UTF-8 nhưng ứng dụng đọc byte bằng Windows-1252 rồi tạo String. Các byte của ký tự tiếng Việt đã bị chuyển thành ký tự sai. Nếu sau đó đưa String cho XML parser, parser chỉ nhận chuỗi ký tự đã giải mã; khai báo encoding=UTF-8 trong chuỗi không thể tái tạo các byte ban đầu.

Quy trình không nên dùng:

~~~java
String xml = new String(
        Files.readAllBytes(path), Charset.defaultCharset());
XMLStreamReader parser =
        XMLInputFactory.newFactory().createXMLStreamReader(
                new StringReader(xml));
~~~

Khi cần đọc file có encoding do XML declaration quyết định, hãy mở InputStream và để XML parser đọc byte:

~~~java
try (InputStream input = Files.newInputStream(path)) {
    XMLStreamReader parser =
            XMLInputFactory.newFactory().createXMLStreamReader(input);
    // Đọc XML events hoặc chuyển cho thành phần xử lý phù hợp.
}
~~~

Nếu nguồn không phải XML byte stream chuẩn mà hệ thống đã cung cấp một Reader, trách nhiệm chọn charset thuộc về nơi tạo Reader. Phải biết chính xác charset của byte trước khi chuyển thành ký tự.

## 7. Cấu hình encoding khi ghi XML trong Spring Batch

Spring Batch cung cấp `StaxEventItemWriter<T>` để marshal item thành XML fragment và ghi vào một file XML. Encoding đầu ra cần được cấu hình nhất quán với XML declaration.

Ví dụ:

~~~java
@Bean
StaxEventItemWriter<Order> orderXmlWriter(
        Marshaller orderMarshaller,
        Resource outputResource) {

    return new StaxEventItemWriterBuilder<Order>()
            .name("orderXmlWriter")
            .resource(outputResource)
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .encoding("UTF-8")
            .overwriteOutput(true)
            .build();
}
~~~

`encoding("UTF-8")` cấu hình charset được dùng khi writer tạo byte. Writer cũng có thể tạo XML declaration tương ứng theo cấu hình. Hãy kiểm tra output thực tế bằng cách đọc byte và parse lại file; không chỉ nhìn nội dung hiển thị trong editor vì editor có thể tự đoán charset.

Nếu dùng `Jaxb2Marshaller`, có thể cấu hình JAXB encoding property khi phù hợp:

~~~java
@Bean
Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Order.class);
    marshaller.setMarshallerProperties(Map.of(
            Marshaller.JAXB_ENCODING, "UTF-8",
            Marshaller.JAXB_FORMATTED_OUTPUT, Boolean.TRUE));
    return marshaller;
}
~~~

Trong pipeline Spring Batch, encoding của writer/output stream là nơi quyết định byte được ghi. Cấu hình marshaller cần đồng nhất với writer. Không để một tầng khai báo UTF-8 trong XML trong khi tầng khác ghi byte theo charset khác.

## 8. Escape XML khác với encoding

Các ký tự đặc biệt trong XML cần được escape đúng trong text node hoặc attribute:

| Ký tự dữ liệu | Cách biểu diễn trong XML |
|---|---|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | Có thể ghi trực tiếp trong đa số ngữ cảnh; `&gt;` thường dùng để rõ ràng |
| `"` | `&quot;` trong attribute dùng dấu nháy kép |
| `'` | `&apos;` trong attribute dùng dấu nháy đơn |

Ví dụ giá trị tên công ty là A&B Logistics sẽ được serializer ghi thành:

~~~xml
<company>A&amp;B Logistics</company>
~~~

Đây là escaping để giữ well-formed XML. Encoding UTF-8 sau đó chuyển các ký tự của XML (bao gồm dấu & và các ký tự tiếng Việt) thành byte. Không tự thay & bằng &amp; trước khi đưa object vào JAXB nếu marshaller đã chịu trách nhiệm escape; làm vậy có thể tạo double escaping thành &amp;amp;.

Tương tự, không cần biến mọi ký tự Unicode thành numeric character reference chỉ vì file dùng UTF-8. Serializer có thể ghi trực tiếp ký tự Unicode hợp lệ theo encoding đã chọn.

## 9. XML character validity và ký tự không hợp lệ

Encoding có thể biểu diễn một ký tự không có nghĩa là ký tự đó hợp lệ trong XML. XML 1.0 giới hạn tập ký tự được phép xuất hiện trong document. Một số control character không được phép dù UTF-8 có thể mã hóa chúng.

Ví dụ, ký tự NUL hoặc một số control character từ dữ liệu nguồn có thể khiến serializer/parser báo lỗi. Numeric character reference cũng không làm một ký tự bị cấm trở nên hợp lệ.

Khi dữ liệu nguồn có ký tự không hợp lệ:

- Xác định nguồn nào đưa ký tự đó vào.
- Quy định rõ có reject record, làm sạch theo nghiệp vụ hay fail batch.
- Không xóa ký tự âm thầm nếu nó có thể làm thay đổi định danh hoặc nội dung nghiệp vụ.
- Ghi source ID và vị trí dữ liệu để điều tra.

Có thể dùng validation riêng trước khi marshal để phát hiện code point không hợp lệ theo XML version mà hệ thống sử dụng.

## 10. Cấu hình JAXB và kiểu dữ liệu Unicode

Java String lưu văn bản theo Unicode. JAXB ánh xạ thuộc tính String sang text node hoặc attribute trong XML. Encoding chỉ được áp dụng khi marshaller ghi ra byte stream hoặc writer.

Ví dụ model:

~~~java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {

    @XmlAttribute
    private String id;

    @XmlElement
    private String customerName;

    @XmlElement
    private BigDecimal amount;

    public Order() {
    }

    // constructors/accessors omitted
}
~~~

Khi marshal object có customerName là Nguyễn Thị An, JAXB tạo XML event/text với ký tự Unicode. StAX writer hoặc output stream sau đó mã hóa chúng thành byte theo charset đã cấu hình.

Không cần tự chuyển String sang byte array trong processor. Việc đó sẽ trộn trách nhiệm nghiệp vụ với I/O và dễ tạo double encoding. Hãy giữ dữ liệu ở dạng String/Java type cho tới tầng serialization.

## 11. Encoding của XML fragment và document gốc

`StaxEventItemReader` thường đọc các fragment theo tên root element. Các fragment là một phần của một XML document có encoding chung. Không nên giả định mỗi fragment có XML declaration hoặc encoding riêng.

Ví dụ document:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order id="ORD-1001">
        <customerName>Nguyễn Thị An</customerName>
    </order>
    <order id="ORD-1002">
        <customerName>Trần Minh Khoa</customerName>
    </order>
</orders>
~~~

Root document khai báo encoding một lần. Reader tìm fragment root order và unmarshal từng fragment thành một object. Encoding được xử lý ở cấp document/byte stream, không cấu hình độc lập cho từng item.

Khi writer tạo một document có root orders, mỗi item được marshal thành fragment order bên trong root đó. XML declaration thuộc document đầu ra; fragment item không nên tự chứa một declaration XML độc lập.

## 12. Namespace không phải encoding

XML namespace và character encoding là hai khái niệm độc lập:

- Namespace xác định tên element/attribute theo URI.
- Encoding xác định cách ký tự của document được biểu diễn thành byte.

Ví dụ:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders xmlns="urn:example:orders:v1">
    <order id="ORD-1001">
        <customerName>Nguyễn Thị An</customerName>
    </order>
</orders>
~~~

Namespace mặc định urn:example:orders:v1 không liên quan đến việc file dùng UTF-8. Khi cấu hình StaxEventItemReader, cần chỉ định fragment root đúng QName/namespace theo API và cấu hình thực tế; đừng cố sửa encoding để giải quyết lỗi không tìm thấy element do namespace sai.

Nếu parser đọc được XML nhưng không tìm thấy fragment, hãy kiểm tra local name, namespace URI và prefix mapping. Nếu parser báo lỗi byte/character hoặc ký tự bị biến dạng, hãy kiểm tra encoding.

## 13. Xử lý XML từ hệ thống cũ dùng charset legacy

Trong tích hợp thực tế, file XML có thể được tạo bởi hệ thống cũ với encoding như Windows-1252 hoặc ISO-8859-1. Cần xử lý theo hợp đồng:

1. Xác nhận byte encoding thực tế từ nhà cung cấp file, không chỉ dựa vào extension .xml.
2. Kiểm tra XML declaration có ghi đúng encoding không.
3. Kiểm tra BOM nếu có.
4. Đọc byte stream bằng XML parser có hỗ trợ encoding tương ứng.
5. Sau khi unmarshal, giữ dữ liệu trong Java String/Unicode.
6. Khi ghi output, chọn encoding theo hợp đồng của hệ thống nhận; ưu tiên UTF-8 nếu hai bên thống nhất.

Nếu phải chuyển đổi từ charset cũ sang UTF-8, hãy thực hiện ở ranh giới I/O: decode byte nguồn bằng charset nguồn đúng, sau đó encode lại bằng UTF-8 khi ghi output. Không đổi nhãn encoding trong XML declaration mà không chuyển đổi byte.

## 14. Charset mặc định của máy và lỗi mojibake

Không dùng charset mặc định của hệ điều hành/JVM cho dữ liệu tích hợp. Cùng một file có thể được đọc khác nhau giữa máy developer, container Linux và server Windows nếu code dựa vào default charset.

Ví dụ không nên dùng:

~~~java
new InputStreamReader(inputStream);
new OutputStreamWriter(outputStream);
~~~

Các constructor trên có thể dùng charset mặc định. Hãy chỉ định rõ:

~~~java
new InputStreamReader(inputStream, StandardCharsets.UTF_8);
new OutputStreamWriter(outputStream, StandardCharsets.UTF_8);
~~~

Với XML, tốt nhất để parser đọc trực tiếp byte stream để tuân thủ BOM/XML declaration. Nếu bắt buộc tự tạo Reader/Writer, chỉ định charset rõ ràng và bảo đảm XML declaration phù hợp với quá trình chuyển đổi đó.

Mojibake là hiện tượng ký tự hiển thị sai do giải mã byte bằng charset không đúng. Ví dụ dữ liệu tiếng Việt có thể xuất hiện thành chuỗi ký tự lạ. Đừng xử lý bằng cách replace các ký tự nhìn thấy sai; hãy sửa điểm decode ban đầu và kiểm tra lại byte gốc.

## 15. Xử lý lỗi encoding trong batch step

Lỗi encoding có thể xuất hiện dưới nhiều dạng:

| Dấu hiệu | Nguyên nhân có thể | Cách điều tra |
|---|---|---|
| Parser báo malformed byte/invalid encoding | Byte không hợp lệ với charset khai báo | Kiểm tra byte đầu vào, BOM và XML declaration |
| Tiếng Việt thành ký tự lạ nhưng XML parse được | Byte đã được decode bằng charset sai | Xác định charset tại điểm đọc byte |
| Parser không tìm thấy root/fragment | XML declaration hoặc nội dung bị thêm ký tự rác; cũng có thể namespace sai | Kiểm tra byte đầu file, prolog và QName |
| Writer tạo file đọc được nhưng chữ sai | Encoding byte và declaration không khớp hoặc consumer dùng charset khác | Kiểm tra byte output và khai báo encoding |
| Lỗi invalid XML character | Dữ liệu có code point không được XML version cho phép | Kiểm tra code point và chính sách dữ liệu |
| Lỗi chỉ xảy ra trên production | Khác biệt file nguồn, default charset, driver hoặc parser implementation | So sánh charset và cấu hình runtime |

Không nên cấu hình skip cho mọi lỗi XML/encoding. Nếu cả file dùng sai encoding hoặc bị hỏng, skip từng fragment có thể tạo output thiếu dữ liệu. Thường cần fail sớm và đưa file vào trạng thái reject/quarantine để sửa nguồn.

Nếu lỗi chỉ liên quan một record và nghiệp vụ cho phép bỏ qua, có thể dùng skip policy có giới hạn, đồng thời lưu fragment/source location. Hãy phân biệt lỗi toàn tài liệu với lỗi dữ liệu riêng của một item.

## 16. Đặt chính sách decode nghiêm ngặt

Khi tự giải mã byte bằng Java NIO, có thể cấu hình CharsetDecoder để báo lỗi thay vì âm thầm thay thế byte sai:

~~~java
CharsetDecoder decoder = StandardCharsets.UTF_8.newDecoder()
        .onMalformedInput(CodingErrorAction.REPORT)
        .onUnmappableCharacter(CodingErrorAction.REPORT);

try (Reader reader = new InputStreamReader(inputStream, decoder)) {
    // Đọc ký tự đã được giải mã nghiêm ngặt.
}
~~~

Cách này hữu ích khi ứng dụng có hợp đồng encoding cố định và muốn phát hiện byte không hợp lệ. Nếu XML declaration có thể chọn encoding động, không hard-code UTF-8 decoder trước khi đọc declaration; dùng XML parser nhận byte stream để nó xử lý quy tắc autodetection, hoặc có một bước xác định encoding theo hợp đồng nguồn.

Không nên dùng CodingErrorAction.REPLACE cho dữ liệu nghiệp vụ quan trọng nếu việc thay ký tự có thể làm thay đổi tên, mã hoặc thông tin định danh. Nếu phải thay thế theo yêu cầu nghiệp vụ, ghi nhận số lượng và nguồn của các thay thế.

## 17. Ghi XML an toàn và hoàn tất file

Trong batch job, file XML đầu ra thường được ghi trong nhiều chunk. Writer cần quản lý root element, header/declaration, fragment và footer đúng lifecycle. Không tự ghi XML declaration trong từng item.

Một quy trình vận hành an toàn:

- Ghi file vào vị trí staging theo batch ID.
- Cấu hình encoding đầu ra tường minh, thường là UTF-8.
- Đảm bảo writer đóng document và ghi footer khi step kết thúc bình thường.
- Chỉ đánh dấu output sẵn sàng sau khi job hoàn tất và đối soát thành công.
- Nếu job thất bại, không để downstream đọc nhầm file chưa hoàn chỉnh.
- Khi restart, dùng cơ chế state của writer và cùng resource/configuration để tiếp tục đúng; kiểm tra hành vi append/overwrite theo cấu hình.

Với StaxEventItemWriter, kiểm tra các tùy chọn như root tag, encoding, overwrite, header/footer callback và state saving theo phiên bản Spring Batch đang dùng. Không sửa file XML đang được writer mở từ một tiến trình khác.

## 18. Kiểm thử encoding XML

Kiểm thử chỉ parse được XML là chưa đủ. Cần xác nhận byte encoding và nội dung Unicode sau round-trip.

Các trường hợp nên kiểm tra:

1. UTF-8 không BOM: đọc file có XML declaration UTF-8 và ký tự tiếng Việt.
2. UTF-8 có BOM: xác nhận parser xử lý đúng theo yêu cầu tích hợp.
3. UTF-16: kiểm tra BOM, byte order và XML declaration.
4. Legacy charset: đọc file đúng charset được hợp đồng quy định.
5. Declaration mismatch: byte encoding khác khai báo; xác nhận lỗi được phát hiện hoặc kết quả bị từ chối.
6. Unicode đa ngôn ngữ: tiếng Việt, ký tự CJK và ký tự supplementary hợp lệ.
7. XML escaping: tên chứa ampersand, dấu ngoặc nhọn hoặc dấu nháy được marshal/unmarshal đúng.
8. Invalid XML character: xác nhận record/file bị xử lý theo policy, không âm thầm mất ký tự.
9. Round-trip writer/reader: marshal object ra file, kiểm tra XML declaration và parse lại, so sánh giá trị.
10. Runtime consistency: chạy test trong môi trường có default charset khác để bảo đảm code không phụ thuộc default.

Ví dụ kiểm tra byte output:

~~~java
byte[] bytes = Files.readAllBytes(outputPath);
String prefix = new String(
        bytes,
        0,
        Math.min(bytes.length, 100),
        StandardCharsets.UTF_8);

assertTrue(prefix.contains("encoding=\"UTF-8\""));
~~~

Đoạn kiểm tra trên minh họa cách đọc prefix khi output được cam kết UTF-8; nó không thay thế XML parser. Với BOM, prefix có thể bắt đầu bằng U+FEFF sau khi decode. Một test hoàn chỉnh nên parse byte stream bằng XML parser và kiểm tra object sau unmarshal.

Ví dụ round-trip khái quát:

~~~java
Order original = new Order("ORD-1001", "Nguyễn Thị An");

// Dùng StaxEventItemWriter hoặc JAXB marshaller để ghi UTF-8.
writeOrderXml(original, outputPath, StandardCharsets.UTF_8);

try (InputStream input = Files.newInputStream(outputPath)) {
    Order restored = readOrderXml(input);
    assertEquals(original.getCustomerName(), restored.getCustomerName());
}
~~~

writeOrderXml và readOrderXml đại diện cho cấu hình writer/reader của ứng dụng. Trong integration test, nên khởi chạy step/job thật để xác nhận lifecycle, header/footer, checkpoint và encoding hoạt động cùng nhau.

## 19. Bảo mật và dữ liệu XML không tin cậy

Encoding không thay thế kiểm soát bảo mật XML. Khi đọc XML từ nguồn không tin cậy, cần cấu hình parser để ngăn các tính năng nguy hiểm như external entity resolution (XXE), truy cập file local hoặc truy cập mạng ngoài ý muốn.

Với StAX, cần xem xét cấu hình XMLInputFactory theo hướng tắt DTD và external entities nếu ứng dụng không cần chúng. Tên property và mức hỗ trợ có thể khác giữa parser implementation, vì vậy cần xác nhận bằng test với implementation đang dùng.

Không bật external entity chỉ để giải quyết lỗi encoding hoặc namespace. Encoding và parser security là hai cấu hình độc lập nhưng đều thuộc ranh giới đọc XML.

## 20. Những lỗi thường gặp

**Chỉ đổi XML declaration mà không chuyển byte.** Khai báo UTF-8 không biến byte ISO-8859-1 thành UTF-8. Phải decode bằng charset nguồn và encode lại bằng charset đích.

**Dùng charset mặc định của máy.** Kết quả có thể khác giữa môi trường. Chỉ định charset rõ hoặc để XML parser đọc byte stream theo XML rules.

**Đọc thành String trước khi parser nhận file.** Nếu decode sai từ đầu, XML declaration không sửa được chuỗi đã hỏng. Ưu tiên InputStream cho XML parser.

**Không kiểm tra BOM.** BOM có thể ảnh hưởng parser cũ hoặc code đọc dòng tự viết. Xác định hợp đồng BOM và test cả trường hợp có/không.

**Coi escaping là encoding.** &amp; giải quyết cú pháp XML; UTF-8/UTF-16 giải quyết biểu diễn byte. Để marshaller escape đúng một lần.

**Dùng charset legacy cho dữ liệu Unicode rộng.** ISO-8859-1 không biểu diễn đầy đủ tiếng Việt. Chọn UTF-8 hoặc hợp đồng Unicode phù hợp.

**Bỏ qua lỗi encoding như lỗi từng record.** File sai charset có thể làm hỏng toàn bộ output. Phân biệt lỗi document với lỗi fragment.

**Không kiểm tra byte output.** Editor có thể tự đoán charset. Kiểm tra byte, XML declaration và parse round-trip.

**Nhầm namespace với encoding.** Namespace URI không quyết định charset. Điều tra QName khi fragment không được nhận diện.

**Cho rằng UTF-8 chấp nhận mọi ký tự trong XML.** Một số control character không hợp lệ theo XML 1.0 dù UTF-8 có thể mã hóa chúng.

## 21. Quy trình triển khai encoding cho XML batch

Khi tích hợp một file XML, hãy xác định theo thứ tự:

1. Chốt charset theo hợp đồng nguồn/đích; ưu tiên UTF-8 nếu các bên có thể thống nhất.
2. Kiểm tra XML declaration và BOM có phù hợp với byte thực tế không.
3. Để StAX/XML parser đọc InputStream khi cần autodetect encoding từ byte.
4. Nếu tự decode, dùng charset được xác nhận và tránh default charset.
5. Cấu hình StaxEventItemReader cùng unmarshaller cho fragment root đúng.
6. Cấu hình StaxEventItemWriter encoding nhất quán với marshaller và XML declaration.
7. Phân biệt lỗi parse toàn file, lỗi encoding và lỗi dữ liệu từng fragment.
8. Xác định chính sách reject/skip/fail; không âm thầm thay ký tự quan trọng.
9. Ghi output vào staging và chỉ publish sau khi writer đóng file, job hoàn tất và đối soát thành công.
10. Kiểm thử byte, BOM, declaration, Unicode round-trip, ký tự XML không hợp lệ và môi trường runtime.

## Kết luận

Encoding XML là cách chuyển ký tự Unicode thành byte và ngược lại. XML declaration mô tả encoding của byte stream; nó không tự chuyển đổi dữ liệu. Khi đọc XML, ưu tiên đưa InputStream trực tiếp cho parser StAX để parser xử lý BOM và declaration. Khi ghi, cấu hình encoding rõ ràng ở writer và bảo đảm XML declaration, marshaller cùng byte output nhất quán.

UTF-8 thường là lựa chọn tốt cho tích hợp mới. Với hệ thống legacy, xác nhận charset thực tế và chuyển đổi ở ranh giới I/O. Giữ escaping XML tách biệt với encoding, kiểm tra ký tự hợp lệ theo XML version và không dựa vào charset mặc định của máy. Trong Spring Batch, cấu hình reader/writer đúng, phân loại lỗi toàn file với lỗi từng record và kiểm thử round-trip trên byte thực tế để tránh dữ liệu tiếng Việt bị biến dạng hoặc output XML không thể đọc bởi hệ thống nhận.
