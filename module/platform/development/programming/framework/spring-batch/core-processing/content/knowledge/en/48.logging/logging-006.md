# Attaching Step Execution ID to Logs in Spring Batch

## 1. The Problem: When a Step Runs Multiple Times, How Do You Distinguish Its Logs?

In Spring Batch, a `Job` can run daily, re-run after failures, or have multiple concurrent executions with different parameter sets. A single job can also consist of multiple `Step`s. Therefore, a log line containing only the step name:

```text
INFO  OrderWriter - Wrote 100 orders
```

is not enough to tell which **step execution** it belongs to. When two executions write to the same centralized logging system, lines interleave:

```text
09:00:01 INFO importOrdersStep - Read chunk 1
09:00:01 INFO importOrdersStep - Read chunk 1
09:00:02 ERROR importOrdersStep - Database timeout
09:00:02 INFO importOrdersStep - Wrote chunk 2
```

Without a correlation key, operators struggle to tell which run's chunk suffered the timeout error.

**`stepExecutionId`** is the ID of a `StepExecution` stored in `JobRepository`. Including it in logs ties a step execution's log lines directly to Spring Batch metadata. This is a form of **log correlation**.

Example with the ID included:

```text
2026-11-16 09:00:01 INFO  [stepExecutionId=8702] OrderReader - Read chunk 1
2026-11-16 09:00:01 INFO  [stepExecutionId=8703] OrderReader - Read chunk 1
2026-11-16 09:00:02 ERROR [stepExecutionId=8702] OrderWriter - Database timeout
2026-11-16 09:00:02 INFO  [stepExecutionId=8703] OrderWriter - Wrote chunk 2
```

From here, you can filter all logs with `stepExecutionId=8702` and query `BATCH_STEP_EXECUTION` for status, start/end times, and processed item counts.

Within **Spring Batch Core Processing → Logging**, this lesson explains how to retrieve the ID, attach it to logs using **SLF4J MDC**, preserve and clear context at proper lifecycle points, handle multithreading, and use the ID when investigating a failed job.

## 2. Understanding Spring Batch IDs Properly

Spring Batch distinguishes three levels:

```text
Job: importOrdersJob
 |
 +-- JobInstance #121: businessDate=2026-11-16
       |
       +-- JobExecution #501: FAILED
       |     |
       |     +-- StepExecution #8702: importOrdersStep, FAILED
       |
       +-- JobExecution #502: COMPLETED (restart)
             |
             +-- StepExecution #8703: importOrdersStep, COMPLETED
```

| Field | Represents | Used For |
| --- | --- | --- |
| `jobName` | Job definition name | Filtering logs for a major workflow |
| `jobInstanceId` | A logical job unit, based on job name and identifying parameters | Tracking the same logical job across restarts |
| `jobExecutionId` | One job run attempt | Grouping logs across all steps in a single run |
| `stepName` | Step name within the job | Identifying the processing stage |
| **`stepExecutionId`** | One specific execution of a step | Investigating the exact logs and metadata of a step |
| `traceId`/`spanId` | Distributed tracing context if tracing is enabled | Tracing across batch, APIs, queues, and external services |

Key points to remember:

- `stepName` can repeat across many job executions; it is **not a unique log key**.
- A **restart** usually creates a new `JobExecution` and new `StepExecution`s for steps that re-run; `stepExecutionId` therefore changes even within the same `JobInstance`.
- `stepExecutionId` is generated by a single repository and is not necessarily unique across databases or environments. When aggregating logs from multiple systems, also keep `service`, `environment`, and `jobName`.
- `stepExecutionId` is neither a chunk sequence number, nor an item ID, nor a substitute for a business key.

Inside the application, `StepExecution` provides:

```java
Long stepExecutionId = stepExecution.getId();
String stepName = stepExecution.getStepName();
Long jobExecutionId = stepExecution.getJobExecution().getId();
String jobName = stepExecution.getJobExecution()
        .getJobInstance()
        .getJobName();
```

Normally the ID is assigned when Spring Batch registers the execution in `JobRepository` before the step starts. If you construct an unsaved `StepExecution` manually in a unit test, `getId()` may be `null`.

## 3. SLF4J MDC: Attaching Context Across Many Log Lines

**MDC** (*Mapped Diagnostic Context*) is a key–value map bound to the logging context. With SLF4J and common backends like Logback, MDC is typically stored per **thread**.

Instead of passing the ID into every log statement:

```java
log.info("stepExecutionId={} Processing order={}", stepExecutionId, orderId);
```

you set the ID once when the step starts:

```java
MDC.put("stepExecutionId", String.valueOf(stepExecution.getId()));
```

Then loggers simply record business messages:

```java
log.info("Processing order={}", orderId);
```

If the logging pattern includes `%X{stepExecutionId}`, the log line includes the ID automatically. This is an **extra field on the log event**, avoiding manual string interpolation in every message.

### MDC Is Not Batch State Storage

| MDC | JobRepository / ExecutionContext |
| --- | --- |
| Built for log correlation | Built for batch lifecycle management and checkpointing |
| Typically transient data on the current thread | Metadata/state persisted by Spring Batch |
| Not automatically persisted to the database | `StepExecution` is saved in the repository |
| Not guaranteed to exist on other threads | Step context is managed by framework mechanisms |
| Must be cleared once work finishes | Governed by update, restart, and metadata rules |

Never use `MDC.put(...)` as a replacement for persisting `ExecutionContext` or storing restart recovery state. When the JVM stops, MDC cannot restore processing progress.

## 4. Standard Pattern: Setting and Clearing MDC in StepExecutionListener

For a sequential step, the cleanest approach is a `StepExecutionListener`:

- `beforeStep(StepExecution)`: read the IDs and put them into MDC before step logic runs.
- `afterStep(StepExecution)`: log a summary and **clear the context** so the thread can be safely reused.

The example below uses **Spring Batch 5.x** packages, Java 17+, SLF4J 2, and Logback (as in standard Spring Boot 3.x projects).

### 4.1. Writing the Listener

```java
package com.example.batch.logging;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.batch.core.ExitStatus;
import org.springframework.batch.core.JobExecution;
import org.springframework.batch.core.StepExecution;
import org.springframework.batch.core.StepExecutionListener;

public final class StepExecutionMdcListener
        implements StepExecutionListener {

    private static final Logger log =
            LoggerFactory.getLogger(StepExecutionMdcListener.class);

    @Override
    public void beforeStep(StepExecution stepExecution) {
        JobExecution jobExecution = stepExecution.getJobExecution();

        MDC.put("jobName",
                jobExecution.getJobInstance().getJobName());
        MDC.put("jobExecutionId",
                String.valueOf(jobExecution.getId()));
        MDC.put("stepName",
                stepExecution.getStepName());
        MDC.put("stepExecutionId",
                String.valueOf(stepExecution.getId()));

        log.info("Step execution started");
    }

    @Override
    public ExitStatus afterStep(StepExecution stepExecution) {
        try {
            log.info(
                    "Step execution finished: status={}, read={}, write={}, skip={}",
                    stepExecution.getStatus(),
                    stepExecution.getReadCount(),
                    stepExecution.getWriteCount(),
                    stepExecution.getSkipCount()
            );
        } finally {
            MDC.remove("stepExecutionId");
            MDC.remove("stepName");
            MDC.remove("jobExecutionId");
            MDC.remove("jobName");
        }

        // null: do not alter the ExitStatus computed by Spring Batch.
        return null;
    }
}
```

**Why use `finally` in `afterStep`?** An exception during summary logging must never skip MDC cleanup. MDC data is thread-local; if a thread is reused while still holding an old `stepExecutionId`, subsequent work logs get tagged with the **wrong ID**.

In this example, the keys `jobName`, `jobExecutionId`, `stepName`, and `stepExecutionId` are owned by this listener. If other components modify the same keys, establish a single owner or save/restore prior MDC values rather than wiping state another component expects.

`afterStep` is invoked by Spring Batch during normal step lifecycles, including when a step fails within framework flow. However, **a JVM crash, killed process, or severe failure aborting shutdown** does not guarantee the callback runs. When investigating those failures, also rely on the repository, system logs, and metrics for long-running jobs.

### 4.2. Attaching the Listener to a Step

Declaring a listener as a bean **does not automatically apply it to every step**. You must register it on the steps needing log correlation:

```java
import org.springframework.batch.core.Step;
import org.springframework.batch.core.repository.JobRepository;
import org.springframework.batch.core.step.builder.StepBuilder;
import org.springframework.batch.item.ItemProcessor;
import org.springframework.batch.item.ItemReader;
import org.springframework.batch.item.ItemWriter;
import org.springframework.context.annotation.Bean;
import org.springframework.transaction.PlatformTransactionManager;

@Bean
Step importOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<OrderRow> orderReader,
        ItemProcessor<OrderRow, OrderRow> orderProcessor,
        ItemWriter<OrderRow> orderWriter) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<OrderRow, OrderRow>chunk(100, transactionManager)
            .reader(orderReader)
            .processor(orderProcessor)
            .writer(orderWriter)
            .listener(new StepExecutionMdcListener())
            .build();
}
```

`OrderRow`, reader, processor, and writer here are application components that must be defined separately. Across multiple steps, you can reuse **the same stateless listener** as long as it uses only local variables and thread-local MDC; never store the current `StepExecution` in a mutable field on a singleton listener.

### 4.3. Logging Inside Reader, Processor, and Writer

When components run on **the same thread carrying MDC**, they just use a normal logger:

```java
private static final Logger log =
        LoggerFactory.getLogger(OrderProcessor.class);

public OrderRow process(OrderRow order) {
    log.debug("Validating orderId={}", order.orderId());
    return order;
}
```

Sample output:

```text
2026-11-16 09:15:00.025 INFO  [job=importOrdersJob jobExec=501 step=importOrdersStep stepExec=8702] Step execution started
2026-11-16 09:15:00.030 DEBUG [job=importOrdersJob jobExec=501 step=importOrdersStep stepExec=8702] Validating orderId=O-100
2026-11-16 09:15:00.082 INFO  [job=importOrdersJob jobExec=501 step=importOrdersStep stepExec=8702] Step execution finished: status=COMPLETED, read=100, write=100, skip=0
```

For sequential tasklets and chunk steps, `beforeStep` usually runs on the same thread as step logic. When processing uses **worker threads, partitions, or async execution**, a listener on the main step thread does not guarantee worker logs get MDC. That scenario is covered separately in the multithreading section.

## 5. Configuring Logback to Display Step Execution ID

Putting data into MDC is not enough; the log backend must be configured to **emit MDC fields** to the console or file.

### 5.1. Logback Pattern

In a Spring Boot project using Logback, create `src/main/resources/logback-spring.xml`:

```xml
<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>
                %d{yyyy-MM-dd HH:mm:ss.SSS} %-5level
                [job=%X{jobName:-na} jobExec=%X{jobExecutionId:-na}
                 step=%X{stepName:-na} stepExec=%X{stepExecutionId:-na}]
                [%thread] %logger{36} - %msg%n
            </pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
```

Logback uses `%X{key}` to read an MDC value. The `:-na` suffix provides a fallback when the key is missing, such as during application startup or outside a step scope.

In a real file, keep `<pattern>...</pattern>` on a single line so XML formatting whitespace or newlines do not alter console formatting. If your project already has centralized logging config, add MDC fields to it instead of replacing the existing setup.

### 5.2. JSON Logs for Centralized Systems

When shipping logs to OpenSearch/Elasticsearch, Loki, Splunk, or another observability platform, **structured logging** is usually more effective than substring search:

```json
{
  "timestamp": "2026-11-16T09:15:00.030+07:00",
  "level": "DEBUG",
  "logger": "com.example.batch.OrderProcessor",
  "message": "Validating orderId=O-100",
  "service": "order-batch",
  "environment": "production",
  "jobName": "importOrdersJob",
  "jobExecutionId": "501",
  "stepName": "importOrdersStep",
  "stepExecutionId": "8702"
}
```

This is an **illustrative desired JSON schema**, not an automatic format across every Logback encoder. Depending on your Spring Boot version and encoder, MDC may be flattened into root JSON fields, placed under an `mdc` object, or require extra configuration. When setting up the ingest pipeline, verify the actual field path and data type of `stepExecutionId`.

The JSON field is a string in this example to match MDC values (`MDC.put` stores strings). Log systems can parse it to an integer, but do so consistently for reliable filtering.

Example logical query in a log platform:

```text
service = "order-batch"
AND environment = "production"
AND stepExecutionId = "8702"
```

There is no need to dump full `jobParameters` into logs. They may contain internal paths, customer identifiers, or sensitive data; emit only fields that are approved and genuinely needed for investigation.

## 6. Retrieving stepExecutionId in ItemReader, ItemProcessor, and ItemWriter

MDC is great when you want **every log line** to carry IDs automatically. However, some components need the ID explicitly to create audit events, link records, or send over APIs. Two clean options exist.

### 6.1. Injecting via StepScope

Spring Batch supports `@StepScope` and Spring Expression Language (SpEL) to pull values from the active step:

```java
import org.springframework.batch.core.configuration.annotation.StepScope;
import org.springframework.batch.item.ItemProcessor;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;

@Bean
@StepScope
ItemProcessor<OrderRow, OrderRow> auditingProcessor(
        @Value("#{stepExecution.id}") Long stepExecutionId) {

    return item -> {
        log.info("Validating orderId={} stepExecutionId={}",
                item.orderId(), stepExecutionId);
        return item;
    };
}
```

This snippet assumes `log` is already declared in the configuration class and `OrderRow` is an application model. Because the component is `@StepScope`, the parameter is resolved when a `StepContext` is active, not when Spring instantiates singletons at startup.

Pros: the method knows the ID explicitly and can use it in audit logic. Cons: you must pass the ID into **every relevant log statement**, and a valid context is still required if the component executes on a thread outside step management.

**Never call a StepScope bean outside a step scope** expecting SpEL to work. If a component is tested from a plain Java unit test, pass a synthetic ID or construct the component directly via constructor.

### 6.2. Receiving StepExecution via a Listener

A component implementing `StepExecutionListener` directly can receive `StepExecution` in `beforeStep` and use it during execution. Keep in mind:

- Beans shared across executions must not hold the ID in a mutable field if multiple steps run concurrently.
- For **delegate** components inside a composite reader/processor/writer, Spring Batch may not auto-detect listeners; register them explicitly.
- If used solely for logging, a centralized listener setting MDC is usually simpler than adding listener interfaces to every processor.

### 6.3. Propagating IDs Explicitly to External Systems

MDC does not travel automatically over HTTP, Kafka, JDBC, or message queues. If a downstream receiver needs to track the batch step, add a dedicated **correlation header or field**:

```text
X-Batch-Job-Execution-Id: 501
X-Batch-Step-Execution-Id: 8702
```

Send these IDs only when allowed by the inter-system contract. Never use them as idempotency keys in place of a business key: a job restart creates a new execution, so the same business record can receive a new ID.

## 7. Multithreading: MDC Does Not Follow TaskExecutor Automatically

This is the single most important limitation when attaching `stepExecutionId`.

In a sequential step:

```text
Step thread
   beforeStep() -> MDC.put(stepExecutionId=8702)
        |
        +-- read()
        +-- process()
        +-- write()
        |
   afterStep()  -> MDC.remove(stepExecutionId)
```

When using a `TaskExecutor`, chunk operations can execute on other threads:

```text
Coordinator thread                Worker threads
beforeStep()
  MDC = 8702
      |
      +--- submit chunk -------> pool-1-thread-1: MDC = ?
      +--- submit chunk -------> pool-1-thread-2: MDC = ?
      |
afterStep()
  remove MDC
```

Standard Logback MDC relies on `ThreadLocal`; worker threads **do not automatically inherit** the submitting thread's context. Consequently, writer/processor logs can miss `stepExecutionId` even though the listener ran properly.

### 7.1. TaskDecorator to Copy and Restore MDC

If the application uses Spring's `ThreadPoolTaskExecutor`, use a `TaskDecorator` to copy MDC from the submitting thread to the executing thread:

```java
package com.example.batch.logging;

import java.util.Map;
import org.slf4j.MDC;
import org.springframework.core.task.TaskDecorator;

public final class MdcTaskDecorator implements TaskDecorator {

    @Override
    public Runnable decorate(Runnable task) {
        // Capture snapshot when the task is submitted.
        Map<String, String> callerContext =
                MDC.getCopyOfContextMap();

        return () -> {
            // Save the worker thread's previous MDC to avoid context leaks.
            Map<String, String> workerPreviousContext =
                    MDC.getCopyOfContextMap();

            try {
                if (callerContext == null) {
                    MDC.clear();
                } else {
                    MDC.setContextMap(callerContext);
                }

                task.run();
            } finally {
                if (workerPreviousContext == null) {
                    MDC.clear();
                } else {
                    MDC.setContextMap(workerPreviousContext);
                }
            }
        };
    }
}
```

Creating the executor:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.core.task.TaskExecutor;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Bean
TaskExecutor batchStepTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(4);
    executor.setQueueCapacity(100);
    executor.setThreadNamePrefix("batch-chunk-");
    executor.setTaskDecorator(new MdcTaskDecorator());
    executor.initialize();
    return executor;
}
```

In Spring Batch 5.x step configuration, attach `taskExecutor(batchStepTaskExecutor)` on the builder if the step is designed to process chunks concurrently.

**Limitation of this approach:** the decorator only copies MDC currently present **on the task-submitting thread**. If submission happens before the listener sets MDC, or the task is dispatched via an executor without the decorator, the ID is still missing. Moreover, in partitioned execution, each worker can own a **different** `StepExecution` from the coordinator; blindly copying the coordinator's ID yields wrong log correlation. In that case, set MDC from the **worker's actual StepExecution**.

If the framework uses other executors (JDK `ExecutorService`, messaging listener containers, Reactor, virtual threads, or remote workers), use the context propagation mechanism appropriate to each API. Do not treat `TaskDecorator` as a universal solution for every async model.

### 7.2. Why Must the Previous MDC Be Restored?

Thread pools reuse threads. If task A sets `stepExecutionId=8702` and task B does not set an ID, task B's logs can erroneously show `8702`. The `try/finally` block in the decorator ensures:

1. The task receives the context snapshot from submission time.
2. The worker uses that context while executing.
3. When the task completes or throws, the worker thread is restored to its prior context.

This is the difference between **accurate correlation** and merely “making logs look like they have an ID”.

### 7.3. Partitioning and Remote Chunking

In a partitioned step:

```text
Manager StepExecution #8700
   |
   +-- Partition stepExecution #8701
   +-- Partition stepExecution #8702
   +-- Partition stepExecution #8703
```

Logs processing items in partition `#8702` must carry ID `8702`, **not the manager's ID `8700`**.

For local partitioning, attach the listener/context on the worker step; for remote partitioning/chunking, the worker side must receive IDs or establish context from the `StepExecution` assigned to its work by the framework. In distributed systems, also combine `jobExecutionId`, `partitionName`, and `traceId` when querying across components.

## 8. How Chunk Retry, Rollback, and Restart Affect the ID

### 8.1. Retries Within the Same StepExecution

When a chunk rolls back and retries **within the same StepExecution**, `stepExecutionId` normally **does not change**. For example:

```text
stepExecutionId=8702 chunk=5 attempt=1 -> SQL timeout
stepExecutionId=8702 chunk=5 attempt=2 -> success
```

This is helpful: you can find all logs for a single step run, including retries. However, to distinguish individual retry attempts, log additional retry/chunk details via your application mechanism. Never infer retry counts purely by counting repeated log lines.

### 8.2. Restarts Create a New Execution

When a job fails and is restarted:

```text
JobInstance 121
  JobExecution 501 -> StepExecution 8702 FAILED
  JobExecution 502 -> StepExecution 8703 COMPLETED
```

Therefore:

- Look up `stepExecutionId=8702` to inspect the original failure.
- Look up `stepExecutionId=8703` to inspect the retry run.
- Use `jobInstanceId=121` or identifying JobParameters to tie both executions of the same logical work together.

If a step already completed and is not re-executed under restart configuration, no new StepExecution is created for it in that restart. Do not assume every restart creates new records for every step.

### 8.3. A Technical ID Does Not Replace Business Correlation

If an invoice `invoiceId=INV-2026-001` is processed twice in two different executions, `stepExecutionId` does not indicate those two operations targeted the same business record. To investigate duplicate transactions, rely on a controlled business key and writer idempotency while keeping `stepExecutionId` to show **which run performed the work**.

## 9. Cross-Referencing Logs with JobRepository Metadata

When you see a log line:

```text
ERROR [stepExec=8702] Could not commit chunk
```

operators can inspect the corresponding execution metadata. With a JDBC `JobRepository` using default table names, an illustrative SQL query is:

```sql
SELECT
    se.STEP_EXECUTION_ID,
    se.STEP_NAME,
    se.STATUS AS STEP_STATUS,
    se.READ_COUNT,
    se.WRITE_COUNT,
    se.READ_SKIP_COUNT,
    se.PROCESS_SKIP_COUNT,
    se.WRITE_SKIP_COUNT,
    se.START_TIME,
    se.END_TIME,
    je.JOB_EXECUTION_ID,
    je.STATUS AS JOB_STATUS,
    je.JOB_INSTANCE_ID,
    ji.JOB_NAME
FROM BATCH_STEP_EXECUTION se
JOIN BATCH_JOB_EXECUTION je
  ON je.JOB_EXECUTION_ID = se.JOB_EXECUTION_ID
JOIN BATCH_JOB_INSTANCE ji
  ON ji.JOB_INSTANCE_ID = je.JOB_INSTANCE_ID
WHERE se.STEP_EXECUTION_ID = :stepExecutionId;
```

In this query:

1. `BATCH_STEP_EXECUTION` shows the status and item counts of the step run.
2. `BATCH_JOB_EXECUTION` links the step to its parent job run.
3. `BATCH_JOB_INSTANCE` provides the job name and instance.
4. For error details, also inspect `EXIT_CODE`, `EXIT_MESSAGE`, exception logs, and infrastructure telemetry in that time window.

Metadata tables may use a custom table prefix or schema differences across versions, so adapt SQL to your actual `JobRepository`. Always query `STEP_EXECUTION_ID` **against the right database and environment**, never assuming IDs are unique across production, staging, and test.

### Querying with JobExplorer

In addition to SQL, an application can use `JobExplorer` to read metadata:

```java
StepExecution step =
        jobExplorer.getStepExecution(jobExecutionId, stepExecutionId);

if (step != null) {
    log.info("Recovered metadata: step={}, status={}",
            step.getStepName(),
            step.getStatus());
}
```

This snippet uses a `jobExplorer` variable (`JobExplorer` bean) and the two IDs retrieved from logs or an incident event. The `getStepExecution(jobExecutionId, stepExecutionId)` method is a standard Spring Batch 5.x lookup API; verify the exact signature for your project version. Use this lookup to inspect persisted metadata, **never per item**, because repeated repository queries add unnecessary overhead.

## 10. Testing the Listener and Preventing MDC Leaks

Attaching IDs to logs is observability infrastructure. Because it relies on thread-local state, verify two invariants carefully: **the right ID is present while the step runs**, and **no ID remains after the step ends**.

### 10.1. Unit Testing with JUnit 5 and Mockito

The snippet below mocks `StepExecution` to isolate the listener from a database, making it well-suited for testing MDC behavior:

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNull;
import static org.mockito.Mockito.mock;
import static org.mockito.Mockito.when;

import org.junit.jupiter.api.Test;
import org.slf4j.MDC;
import org.springframework.batch.core.BatchStatus;
import org.springframework.batch.core.JobExecution;
import org.springframework.batch.core.JobInstance;
import org.springframework.batch.core.StepExecution;

class StepExecutionMdcListenerTest {

    @Test
    void putsStepExecutionIdInMdcAndRemovesItAfterStep() {
        StepExecution step = mock(StepExecution.class);
        JobExecution job = mock(JobExecution.class);
        JobInstance instance = mock(JobInstance.class);

        when(step.getId()).thenReturn(8702L);
        when(step.getStepName()).thenReturn("importOrdersStep");
        when(step.getJobExecution()).thenReturn(job);
        when(step.getStatus()).thenReturn(BatchStatus.COMPLETED);
        when(job.getId()).thenReturn(501L);
        when(job.getJobInstance()).thenReturn(instance);
        when(instance.getJobName()).thenReturn("importOrdersJob");

        StepExecutionMdcListener listener =
                new StepExecutionMdcListener();

        try {
            listener.beforeStep(step);

            assertEquals("8702", MDC.get("stepExecutionId"));
            assertEquals("501", MDC.get("jobExecutionId"));
            assertEquals("importOrdersStep", MDC.get("stepName"));
            assertEquals("importOrdersJob", MDC.get("jobName"));
        } finally {
            listener.afterStep(step);
        }

        assertNull(MDC.get("stepExecutionId"));
        assertNull(MDC.get("jobExecutionId"));
        assertNull(MDC.get("stepName"));
        assertNull(MDC.get("jobName"));
    }
}
```

Unit tests verify the MDC put/remove lifecycle, not that the log backend actually formats those fields. To verify Logback formatting, add an integration test with a test appender and inspect `ILoggingEvent.getMDCPropertyMap()` or parse JSON output per your logger config.

### 10.2. Integration Test Running an Actual Step

An integration test with `spring-batch-test` can:

1. Build a simple `Step` with test reader/processor/writer and the registered listener.
2. Launch it using the test utility matching your Spring Batch version.
3. Inside the processor, log a fixed message such as `"processing-test-item"`.
4. Inspect the resulting `StepExecution`, read `getId()`, and compare it with the MDC in captured log events.
5. Verify that after the step completes, `stepExecutionId` is gone from the thread that ran the listener.
6. Launch a second time to create a new execution and verify logs carry the new ID.

In Spring Batch 5.x, `@SpringBatchTest` with `JobLauncherTestUtils` is commonly used to launch jobs/steps in integration tests. In Spring Batch 6.x, use the corresponding test APIs, including `JobOperatorTestUtils`. Use an isolated `JobRepository` for test metadata so tests never interfere with active jobs.

### 10.3. Testing Multithreading

When a step uses a `TaskExecutor`, intentionally write a test executing multiple chunks across a thread pool. Capture log events from the processor/writer and verify:

- Each event carries the `stepExecutionId` of the **actual worker step execution**.
- No event carries an ID from an earlier step execution.
- When two step executions run concurrently, logs may interleave yet IDs remain cleanly distinguishable.
- Reused pool threads retain no stale MDC after the step finishes.

Do not rely on `Thread.sleep` to assume propagation worked. Direct assertions on log event MDC or inside worker `Callable`/`Runnable`s provide clear proof.

## 11. When to Also Use JobExecutionListener and Tracing

### Job-Level Logging

`JobExecutionListener` can put `jobExecutionId` and `jobName` in context at job start and clear them at job end. However, that **does not replace StepExecutionListener**, because `stepExecutionId` is only defined per step. Moreover, MDC on the job thread does not automatically propagate to all worker threads.

If you use both listeners, define ownership clearly:

- The job listener manages `jobName` and `jobExecutionId`.
- The step listener manages `stepName` and `stepExecutionId`.
- The step listener must not delete keys owned by the job listener.

The listener example in Section 4 manages all four fields itself, so **no separate job listener is needed** just for those two IDs. If your application already has a job MDC listener, adjust the step listener accordingly so it does not wipe context mid-job.

### Distributed Tracing

A job may call APIs, send messages, or run remote partitions. `stepExecutionId` identifies a step run in the batch repository, but **does not automatically create a distributed trace**. If the application uses Micrometer Tracing/OpenTelemetry, logs can also include `traceId` and `spanId` supplied by tracing instrumentation.

Keeping both identifier sets connects:

```text
stepExecutionId=8702 (step run)
       |
       +-- traceId=abc... (query catalog service)
       |
       +-- traceId=def... (call payment service)
```

Depending on tracing design, a step can share one broad trace or emit separate traces per outbound call. Do not assume every log line in a step shares the same `traceId`. When needed, add `stepExecutionId` as a high-cardinality span attribute **on the trace**, while keeping metrics grouped by job/step name.

## 12. Safe and Efficient Logging at Scale

### 12.1. Put IDs in Fields, Not Buried in Message Strings

Recommended:

```text
INFO stepExecutionId=8702 event=chunk_completed read=100 written=100
```

Avoid:

```text
INFO StepExecution 8702 completed chunk ...
```

The second format forces search systems to parse free-form text. Stable named fields make filtering, grouping, and building dashboards much easier.

### 12.2. Never Turn stepExecutionId into a Metric Label

The ID changes with every execution. Using:

```text
batch_step_duration_seconds{
    step_execution_id="8702"
}
```

causes time-series counts to grow unboundedly across job history. Metrics should stick to **low-cardinality labels** such as `jobName`, `stepName`, `status`, and `environment`. Specific IDs belong in **logs or traces** to locate failing runs.

### 12.3. Do Not Log Every Item at INFO

A job reading millions of items creates massive log volume if every item logs at `INFO`. Instead:

- Use `INFO` for step start/finish, significant chunk summaries, or state transitions.
- Use `DEBUG` for individual items when investigating in controlled environments.
- Use `ERROR` for exceptions with `stepExecutionId`, step name, and minimal context.
- Track throughput, duration, and read/write/skip rates via metrics instead of printing every record.

For sensitive data, never log full payloads, passwords, tokens, or personal details just for context. `stepExecutionId` lets you look up metadata without exposing business data.

### 12.4. Timestamps, Environments, and Consistency

Centralized logs should carry timestamps with explicit offsets or UTC. If two instances log in different timezones, `stepExecutionId` still groups lines, yet chronological ordering becomes confusing when host clocks drift. Synchronize host clocks and standardize log timezones rather than relying solely on log collector ingest time.

Always record the environment separately (`dev`, `staging`, `prod`). A `stepExecutionId=8702` in staging has nothing to do with `8702` in production.

## 13. Common Issues

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Logs lack `stepExecutionId` | Listener not registered on the step | Check `.listener(...)` in StepBuilder or listener configuration |
| MDC has the ID, but console does not show it | Pattern/JSON encoder does not emit MDC | Add `%X{stepExecutionId}` or configure MDC fields |
| Reader logs have the ID, writer logs do not | Writer runs on a different worker thread | Propagate context via executor or set context on actual worker |
| Next step's logs carry previous step's ID | Forgot cleanup when pool thread was reused | `MDC.remove`/`clear` in `finally` and restore scoped context |
| Partition logs all show the manager's ID | Copied MDC from manager instead of partition execution | Initialize context from each worker's `StepExecution` |
| After restart, logs cannot be found under old ID | Restart created a new `StepExecution` | Query by `jobInstanceId`/`jobExecutionId` to link runs |
| `stepExecution.getId()` is `null` in unit tests | Unsaved execution constructed manually | Mock ID, use `MetaDataInstanceFactory`, or run via test repository |
| Many logs share the ID, unclear which retry | Retries occur within the same step execution | Log separate attempt/chunk info if needed |
| Querying by ID finds the wrong run | IDs are unique only within one repository | Filter by `environment`/`service` and query the right database |
| JSON logs miss MDC despite working console pattern | Console and JSON encoders configured differently | Inspect actual encoder and ingest mapping |
| Metric series count grows rapidly | Attached `stepExecutionId` as a label | Move IDs to logs/traces; keep only stable labels on metrics |
| Listener field holding StepExecution mixes across jobs | Mutable singleton state is unsafe under concurrency | Use thread-local variables/MDC or dedicated bean scope |

## 14. Hands-on Exercises

Suppose your application has an `importOrdersJob` with two steps:

```text
importOrdersJob
    |
    +-- readOrdersStep
    |
    +-- persistOrdersStep
```

**Exercise 1 — Basic MDC.** Create `StepExecutionMdcListener`, register it on both steps, and configure Logback to print `jobName`, `jobExecutionId`, `stepName`, and `stepExecutionId`. Run the job and confirm each step gets its own ID.

**Exercise 2 — Context cleanup.** Write a JUnit test invoking `beforeStep` and `afterStep`. Verify MDC holds the IDs while active and returns `null` after finishing. Run two executions back-to-back to catch stale ID reuse.

**Exercise 3 — Job restart.** Intentionally trigger an error in `persistOrdersStep`, record its `stepExecutionId`, then restart the same `JobInstance`. Compare the IDs of the failed run and the restart. Use `jobInstanceId` to tie the two runs together.

**Exercise 4 — Multithreading.** Switch one step to run chunks via `ThreadPoolTaskExecutor`. First observe missing MDC without propagation; then add `MdcTaskDecorator` and confirm worker logs carry the right ID. Launch two step executions concurrently to verify zero context leakage.

**Exercise 5 — Real failure investigation.** Given an `ERROR stepExecutionId=...` log line, write a SQL query joining `BATCH_STEP_EXECUTION`, `BATCH_JOB_EXECUTION`, and `BATCH_JOB_INSTANCE` to inspect status, timestamps, and read/write/skip counts. Cross-check metadata against cause logs.

**Exercise 6 — Structured logging.** Emit a JSON log containing `stepExecutionId` and `jobExecutionId`. Create an ID filter in your project's log platform; ensure the field never mixes with sensitive payloads and keeps consistent data types across services.

## 15. Conclusion

Attaching **`stepExecutionId` to logs** turns disconnected log lines into a traceable history of **a specific step execution**. For sequential Spring Batch processing, `StepExecutionListener` combined with SLF4J MDC and Logback patterns is clean and easy to maintain. The key is not merely calling `MDC.put(...)`, but also **clearing or restoring MDC properly at lifecycle boundaries**, understanding that MDC is typically thread-bound, and using the **actual worker step's** ID under parallel processing.

During investigations, connect `stepExecutionId` in logs to `BATCH_STEP_EXECUTION` and `jobExecutionId` in `JobRepository`. Pair that with `jobInstanceId` for tracking restarts, `traceId` for outbound service calls, and job/step-level metrics for trend monitoring. That way, a specific chunk or item error can be traced accurately without bloating logs or metrics.
