# Namespaces and mapping

In Spring Batch, XML configuration uses namespaces to distinguish vocabularies from Spring Framework, Spring Batch, and other libraries. Namespaces allow a single XML file to contain multiple element types without confusing names like `job`, `step`, `bean`, or `property`. Corresponding schemas describe valid elements and attributes; Spring namespace parsers read those elements and turn them into bean definitions and runtime configurations.

When declaring a job in XML, common key parts appear:

- `xmlns:batch` maps the `batch` prefix to the Spring Batch namespace URI.
- `xsi:schemaLocation` maps namespace URIs to XSD locations used to validate XML structure.
- `batch:job`, `batch:step`, `batch:chunk` describe job and step structure.
- `bean` and `property` belong to the Spring Beans namespace to declare objects and dependencies.
- Attributes such as `reader`, `processor`, `writer`, and `job-repository` reference beans registered in the application context.

There are two separate kinds of mapping to understand: mapping a namespace URI to an XSD so XML is recognized/validated, and mapping XML bean names/attributes to objects that Spring Batch uses at runtime. Declaring the right namespace while referencing the wrong bean still prevents the application context from initializing; referencing the right bean with a wrong namespace/XSD prevents the XML parser from understanding batch elements.

## What is a namespace in XML?

An XML namespace is a mechanism for qualifying element and attribute names with a URI. The URI distinguishes vocabularies even when they share the same local name.

For example, two libraries might both define a `job` element. If one element belongs to namespace A and the other to namespace B, the XML parser distinguishes them by the pair of namespace URI and local name, not merely by the text `job`.

In Spring XML, prefixes are commonly used to write namespaced names:

```xml
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:batch="http://www.springframework.org/schema/batch">

    <bean id="dataSource" class="..."/>

    <batch:job id="importJob">
        <!-- Elements belonging to the Spring Batch vocabulary -->
    </batch:job>
</beans>
```

Here:

- `beans` has no prefix because the Spring Beans namespace is declared as the default namespace.
- `batch:job` has the `batch` prefix, so it belongs to the Spring Batch namespace.
- `id` is an unprefixed attribute; per XML namespace rules, unprefixed attributes do not automatically belong to the default namespace.

A namespace URI is a vocabulary identifier, not necessarily a URL the application must download directly at runtime. Spring and XML tooling can resolve schemas through resources packaged inside dependencies.

## Prefixes and namespace URIs

Prefixes such as `batch`, `beans`, and `xsi` are local aliases within the XML document. The namespace URI is the true identifier.

The two declarations below share the exact same Spring Batch namespace meaning:

```xml
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:batch="http://www.springframework.org/schema/batch">
    <batch:job id="importJob"/>
</beans>
```

```xml
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:sb="http://www.springframework.org/schema/batch">
    <sb:job id="importJob"/>
</beans>
```

In the second example, the `sb` prefix replaces `batch`. The XML parser still recognizes the element as a Spring Batch `job` because the namespace URI is unchanged.

Keep the familiar `batch` prefix so readers can easily recognize Spring Batch configuration. Changing the prefix does not alter runtime beans or flows, provided the URI stays exact.

### Same local name but different namespace

For example, `bean` in the Spring Beans namespace and a `bean` element from another vocabulary are two distinct XML names. The XML parser distinguishes them by namespace URI + local name.

This explains why different vocabularies can sit side by side:

```xml
<bean id="orderReader" class="com.example.OrderReader"/>

<batch:step id="importStep">
    <batch:tasklet>
        <batch:chunk reader="orderReader" writer="orderWriter"
                     commit-interval="100"/>
    </batch:tasklet>
</batch:step>
```

`bean` declares an object; `batch:step`, `batch:tasklet`, and `batch:chunk` describe batch structure. They can coexist because they belong to different namespace vocabularies.

## Declaring the Spring Batch namespace

A configuration file typically declares three important namespaces:

```xml
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xmlns:batch="http://www.springframework.org/schema/batch"
       xsi:schemaLocation="
           http://www.springframework.org/schema/beans
           https://www.springframework.org/schema/beans/spring-beans.xsd
           http://www.springframework.org/schema/batch
           https://www.springframework.org/schema/batch/spring-batch.xsd">

    <!-- Beans and Spring Batch configuration go here -->

</beans>
```

Meaning:

| Declaration | Role |
| --- | --- |
| `xmlns=".../beans"` | Sets Spring Beans as the default namespace |
| `xmlns:xsi=".../XMLSchema-instance"` | Declares the namespace for standard attributes like `xsi:schemaLocation` |
| `xmlns:batch=".../batch"` | Binds the `batch` prefix for Spring Batch elements |
| `xsi:schemaLocation` | Provides pairs of namespace URIs and corresponding XSD locations |

The Spring Batch namespace URI is normally `http://www.springframework.org/schema/batch`. The schema location points to `spring-batch.xsd`. For Spring Beans, the namespace URI is normally `http://www.springframework.org/schema/beans` and the schema is `spring-beans.xsd`.

In the example, namespace URIs use `http`, while schema locations use `https`. This does not mean two different namespaces: namespace identity lives in the URI inside `xmlns`, whereas schema location is the address of the XSD resource. You may encounter configurations using `http` for both in older documentation or projects; what matters is that the namespace URI is exact and the schema location resolves in your environment.

## xsi:schemaLocation maps namespaces to XSDs

`xsi:schemaLocation` takes a list of value pairs:

```text
namespace-URI-1 schema-URL-1
namespace-URI-2 schema-URL-2
...
```

Each pair consists of a namespace URI and the schema location describing that vocabulary. In XML, spaces or newlines merely separate values; each line is not an independent declaration.

Example:

```xml
xsi:schemaLocation="
    http://www.springframework.org/schema/beans
    https://www.springframework.org/schema/beans/spring-beans.xsd
    http://www.springframework.org/schema/batch
    https://www.springframework.org/schema/batch/spring-batch.xsd">
```

Here there are two mapping pairs: the Spring Beans namespace to `spring-beans.xsd`, and the Spring Batch namespace to `spring-batch.xsd`.

`xsi:schemaLocation` is neither a namespace declaration nor does it change prefixes. `xmlns:batch` declares the vocabulary; `xsi:schemaLocation` provides the schema location for validators/tooling to check that vocabulary.

### Namespace URI and schema URL are not the same thing

| Component | Example | Function |
| --- | --- | --- |
| Namespace URI | `http://www.springframework.org/schema/batch` | Identifies Spring Batch element names |
| Schema location | `https://www.springframework.org/schema/batch/spring-batch.xsd` | Location of the XSD describing element/attribute structure |
| Prefix | `batch` | Short alias for writing element names |
| Local name | `job` | Element name within the vocabulary |

An element such as `<batch:job>` is identified by the namespace URI of `batch` and the local name `job`. The XSD determines whether `job` is valid, what attributes it supports, and what child elements it may contain.

## Spring namespace parsers and bean definitions

Spring XML namespaces are not only for syntax checking. Spring provides a namespace handler/parser mechanism to convert specialized elements into bean definitions.

Example:

```xml
<batch:job id="importJob">
    <batch:step id="importStep">
        ...
    </batch:step>
</batch:job>
```

Spring Batch's namespace parser reads this structure and creates the corresponding runtime configuration, including jobs, steps, flows, and related infrastructure components according to the namespace configuration. Users do not have to manually declare every internal factory object for each element.

Meanwhile, the element:

```xml
<bean id="orderReader" class="com.example.OrderReader"/>
```

belongs to the Spring Beans namespace and is converted by the bean definition parser into a bean definition named `orderReader`.

When `batch:chunk` references `reader="orderReader"`, the Spring Batch namespace parser links that attribute to the bean with the matching ID in the application context.

## Complete job configuration example

The following example illustrates a chunk step reading data and writing to a database. The reader, processor, and writer classes are application classes; the example focuses on namespace structure and bean reference mapping.

```xml
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xmlns:batch="http://www.springframework.org/schema/batch"
       xsi:schemaLocation="
           http://www.springframework.org/schema/beans
           https://www.springframework.org/schema/beans/spring-beans.xsd
           http://www.springframework.org/schema/batch
           https://www.springframework.org/schema/batch/spring-batch.xsd">

    <bean id="orderReader" class="com.example.batch.OrderReader"/>
    <bean id="orderProcessor" class="com.example.batch.OrderProcessor"/>
    <bean id="orderWriter" class="com.example.batch.OrderWriter"/>

    <batch:job id="importOrdersJob">
        <batch:step id="importOrdersStep">
            <batch:tasklet>
                <batch:chunk reader="orderReader"
                             processor="orderProcessor"
                             writer="orderWriter"
                             commit-interval="100"/>
            </batch:tasklet>
        </batch:step>
    </batch:job>

</beans>
```

Mappings in the example:

| XML | Interpreted as |
| --- | --- |
| `id="importOrdersJob"` | Job bean name registered in the application context |
| `batch:step id="importOrdersStep"` | A step belonging to the job |
| `reader="orderReader"` | References the reader bean with ID `orderReader` |
| `processor="orderProcessor"` | References the processor bean with ID `orderProcessor` |
| `writer="orderWriter"` | References the writer bean with ID `orderWriter` |
| `commit-interval="100"` | Maximum items per chunk before committing per step configuration |

This example assumes the beans implement the right Spring Batch interfaces and have required dependencies. In real configurations, readers/writers usually need properties such as `dataSource`, `resource`, `lineMapper`, or SQL. Those properties are injected via Spring Beans XML or bean constructors.

## Difference between bean definition and bean reference

A bean definition creates an object in the application context. A reference links another component to that object.

```xml
<bean id="orderWriter" class="com.example.batch.OrderWriter">
    <property name="dataSource" ref="dataSource"/>
    <property name="sql" value="INSERT INTO orders(order_id) VALUES (?)"/>
</bean>
```

In the example:

- `id="orderWriter"` names the bean.
- `class` specifies the implementation class.
- `property name="dataSource"` selects the property to inject.
- `ref="dataSource"` references another bean.
- `value="..."` injects a literal/string value.

`ref` and `value` are not interchangeable. If a property expects a `DataSource`, use `ref` to the datasource bean. If a property accepts a SQL string, use `value`.

### ID and aliases

A bean can have one primary ID and aliases. When a batch attribute references a bean, the name used must be resolved by Spring to a single bean.

```xml
<bean id="orderReader" name="ordersInputReader,primaryOrderReader"
      class="com.example.batch.OrderReader"/>
```

Aliases can aid compatibility with other configurations, but pick one consistent name to use across `reader`, `processor`, `writer`, and `ref` properties. Avoid duplicate bean IDs or aliases causing ambiguity.

## Default namespace and prefixes

If Spring Beans is the default namespace, `bean`, `property`, and `constructor-arg` elements can be written without prefixes. Spring Batch elements require the `batch` prefix.

```xml
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:batch="http://www.springframework.org/schema/batch">

    <bean id="reader" class="com.example.Reader"/>

    <batch:job id="job">
        ...
    </batch:job>
</beans>
```

If no default namespace is declared, prefixes can be used for Spring Beans as well:

```xml
<beans:beans xmlns:beans="http://www.springframework.org/schema/beans"
             xmlns:batch="http://www.springframework.org/schema/batch">

    <beans:bean id="reader" class="com.example.Reader"/>
    <batch:job id="job">...</batch:job>

</beans:beans>
```

Both styles are valid if namespace URIs and schema mappings are exact. Using the default namespace for beans and the `batch` prefix is usually more readable in Spring configuration files.

### Default namespace does not automatically apply to attributes

An important XML namespace rule: the default namespace applies to unprefixed element names, but does not apply to unprefixed attributes.

Example:

```xml
<bean id="orderReader" class="com.example.OrderReader"/>
```

The `bean` element belongs to the default Spring Beans namespace. The `id` and `class` attributes have no namespace prefix. This is how Spring schemas define and expect them.

Do not arbitrarily add prefixes to attributes, such as `batch:id`, if the schema does not declare that attribute in the Batch namespace. Follow the attribute names in the XSD.

## Mapping job, step, and flow components

The Spring Batch namespace maps XML structure into a job flow model.

### Job and step

```xml
<batch:job id="dailyImportJob">
    <batch:step id="readStep" next="validateStep">
        <batch:tasklet ref="readTasklet"/>
    </batch:step>

    <batch:step id="validateStep">
        <batch:tasklet ref="validateTasklet"/>
    </batch:step>
</batch:job>
```

`batch:job` is the container for the flow; `batch:step` defines a step. `next` indicates the next step in a linear flow. `ref` on `batch:tasklet` references a declared tasklet bean. Exact tasklet/chunk syntax must follow the XSD of the project's Spring Batch version.

### Flow and transitions

For flows branching by exit status, the XML namespace lets you describe transitions with the corresponding flow elements/attributes. Each transition maps a step's result status to the next step or flow.

Conceptual example:

```text
validateStep
   |
   +-- COMPLETED --> importStep
   |
   +-- FAILED ----> errorHandlingStep
   |
   +-- * ---------> end / fail per flow definition
```

In XML, transitions must use the exact elements and attributes supported by your Spring Batch version's XSD. Do not invent attributes like `onSuccess` or `onFailure` if the schema does not define them. Use IDE completion or the corresponding XSD to verify `next`, `on`, `to`, `end`, `fail`, and flow elements in your project.

## Mapping job repository and transaction manager

Jobs and steps need infrastructure to store metadata, checkpoints, and transactions. In XML, these components are referenced by bean ID.

Example declaring infrastructure beans explicitly:

```xml
<bean id="dataSource" class="...">
    <!-- Datasource configuration -->
</bean>

<bean id="transactionManager" class="...">
    <constructor-arg ref="dataSource"/>
</bean>

<batch:job-repository id="jobRepository"
                      data-source="dataSource"
                      transaction-manager="transactionManager"/>
```

This is an illustrative configuration form; exact classes for datasource and transaction manager depend on the database/provider. Attribute names and repository declaration style must match the XSD of your Spring Batch version.

When a job/step uses an explicit repository or transaction manager, those bean IDs must resolve in the application context. Do not confuse a namespace parser with automatically creating a datasource with real connection settings; the application still must supply the datasource and connection details.

## Mapping properties with ref and value

The Spring Beans namespace provides ways to inject dependencies into beans:

```xml
<bean id="orderWriter" class="com.example.batch.OrderWriter">
    <property name="dataSource" ref="dataSource"/>
    <property name="sql" value="INSERT INTO orders(order_id) VALUES (?)"/>
    <property name="batchSize" value="100"/>
</bean>
```

Spring converts string literals to property types when an appropriate converter exists. Use `ref` when a property needs a bean/object; use `value` for literals. For collections or maps, use the corresponding Spring Beans/Util namespace elements.

If using the `util` namespace, also declare its URI and XSD:

```xml
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:util="http://www.springframework.org/schema/util"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="
           http://www.springframework.org/schema/beans https://www.springframework.org/schema/beans/spring-beans.xsd
           http://www.springframework.org/schema/util https://www.springframework.org/schema/util/spring-util.xsd">

    <util:map id="statusCodes">
        <entry key="NEW" value="N"/>
        <entry key="COMPLETED" value="C"/>
    </util:map>
</beans>
```

This is an auxiliary Spring namespace example, not the Spring Batch namespace. Each added vocabulary requires its own namespace declaration and schema mapping.

## Late binding in XML with StepScope

Some beans can only be configured once a job/step has started, such as a reader needing an input file from `JobParameters` or `jobExecutionContext`. XML can declare a bean with `scope="step"` and use SpEL in property values.

```xml
<bean id="orderReader"
      class="com.example.batch.OrderReader"
      scope="step">
    <property name="resource"
              value="file:#{jobParameters['inputFile']}"/>
</bean>
```

`scope="step"` defers creating the target bean until an active `StepExecution` exists. SpEL expressions can read `jobParameters`, `jobExecutionContext`, or `stepExecutionContext` according to scope.

Example reading a file promoted to job context by a previous step:

```xml
<bean id="stagingReader"
      class="com.example.batch.StagingReader"
      scope="step">
    <property name="resource"
              value="file:#{jobExecutionContext['generatedFile']}"/>
</bean>
```

If a value was written into the previous step's step context, promote it to the job context before the next step uses it. Namespaces do not automatically move every key from step context to job context.

In XML, ensure the `step` scope is registered by the appropriate Spring Batch namespace/infrastructure configuration. When injecting a scoped bean into a singleton bean, Spring uses a scoped proxy per scope configuration; if eager initialization errors occur, inspect how scope and proxies are declared in your project version.

## Mapping XML to Java configuration

XML namespaces and Java configuration can describe the same job/step model, though with different syntax.

| Concept | XML namespace | Java configuration |
| --- | --- | --- |
| Job | `<batch:job id="importJob">` | `new JobBuilder("importJob", jobRepository)` |
| Step | `<batch:step id="importStep">` | `new StepBuilder("importStep", jobRepository)` |
| Reader reference | `reader="orderReader"` | `.reader(orderReader)` |
| Processor reference | `processor="orderProcessor"` | `.processor(orderProcessor)` |
| Writer reference | `writer="orderWriter"` | `.writer(orderWriter)` |
| Chunk size | `commit-interval="100"` | `.chunk(100, transactionManager)` |
| Bean dependency | `ref="dataSource"` | Constructor/method parameter injection |

Equivalent Java example for the XML chunk:

```java
@Bean
Job importOrdersJob(JobRepository jobRepository, Step importOrdersStep) {
    return new JobBuilder("importOrdersJob", jobRepository)
            .start(importOrdersStep)
            .build();
}

@Bean
Step importOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<Order> orderReader,
        ItemProcessor<Order, Order> orderProcessor,
        ItemWriter<Order> orderWriter) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<Order, Order>chunk(100, transactionManager)
            .reader(orderReader)
            .processor(orderProcessor)
            .writer(orderWriter)
            .build();
}
```

Choose a consistent configuration style for a given job section. An application can import XML and Java configuration together, but avoid duplicate bean/job IDs or unintentionally creating two jobs with the same name.

## Common auxiliary namespaces

A Spring XML file can declare multiple namespaces:

| Prefix | Common namespace | Purpose |
| --- | --- | --- |
| No prefix | Spring Beans | `bean`, `property`, `constructor-arg` |
| `batch` | Spring Batch | `job`, `step`, `chunk`, `tasklet`, flow |
| `xsi` | XML Schema Instance | `schemaLocation`, `nil` |
| `util` | Spring Util | `map`, `list`, `set`, `properties` |
| `context` | Spring Context | component scan, property placeholder/configuration |
| `tx` | Spring TX | transaction advice and annotation-driven transactions |
| `aop` | Spring AOP | proxies and XML-configured pointcuts |

Declare only namespaces actually needed. Each added namespace needs an accurate URI and a schema location pair if XSD validation is needed.

Example combining `context` and `batch`:

```xml
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xmlns:batch="http://www.springframework.org/schema/batch"
       xmlns:context="http://www.springframework.org/schema/context"
       xsi:schemaLocation="
           http://www.springframework.org/schema/beans https://www.springframework.org/schema/beans/spring-beans.xsd
           http://www.springframework.org/schema/batch https://www.springframework.org/schema/batch/spring-batch.xsd
           http://www.springframework.org/schema/context https://www.springframework.org/schema/context/spring-context.xsd">

    <context:component-scan base-package="com.example.batch"/>

    <batch:job id="importJob">
        ...
    </batch:job>
</beans>
```

`context:component-scan` belongs to the Spring Context namespace, while `batch:job` belongs to the Spring Batch namespace. Two parsers process the two vocabularies within the same application context.

## XML schemas and version compatibility

An XSD describes the structure supported by a namespace version. If the Spring Batch dependency and the schema used by the IDE/parser are incompatible, errors can arise:

- The IDE reports non-existent elements or attributes.
- XML validation rejects attributes valid in another version.
- The runtime namespace parser does not recognize a new element.
- Old configuration is deprecated or changes semantics on upgrade.

When upgrading Spring Batch version:

1. Check the actual dependency version in the build.
2. Use a Spring Batch schema compatible with the dependency.
3. Check release notes and migration guides for XML namespaces.
4. Validate XML using the same classpath/runtime the application uses.
5. Run integration tests initializing the application context and launching jobs.

Do not just edit the schema URL to clear red IDE underlines while runtime still uses an older library. Schema locations and namespace parsers in dependencies must stay aligned.

Spring normally ships schema mappings inside JARs so resolvers can locate XSDs from the classpath. Thus, a project can validate schemas without downloading XSDs directly from the internet, depending on XML parser and tooling configuration. If the IDE fails to resolve schemas offline, inspect catalogs/caches and dependencies rather than altering the namespace URI.

## XML validation in IDEs and at startup

An IDE can use XSDs to suggest elements and attributes and flag invalid structure. Runtime Spring also parses XML and registers bean definitions. These two checks are related but not identical.

Schema validation can catch:

- Wrong element names, e.g., writing `batch:jobs` instead of `batch:job`.
- Missing required attributes per XSD.
- Placing child elements in invalid positions.
- Attribute values outside types/enums described by the schema.
- Undeclared namespace prefixes.

Application context initialization can also catch:

- Referenced bean IDs that do not exist.
- Bean classes lacking matching constructors/properties.
- Ambiguous dependency injection.
- Classes not implementing required Spring Batch interfaces.
- Misconfigured jobs/steps regarding repository, transaction manager, or flow.

An XML file can be XSD-valid yet still fail startup because `reader="missingReader"` finds no bean. Conversely, if the bean exists but batch elements have the wrong namespace, the parser cannot handle them properly.

## Common namespace errors

### Forgetting to declare a prefix

If you write `<batch:job>` without `xmlns:batch`, the XML parser reports an undeclared prefix. Add the proper namespace declaration on the root or ancestor element.

### Using the wrong namespace URI

The prefix may be `batch` while the URI has a typo. The parser treats it as another vocabulary and fails to find the Batch namespace handler. Copy the canonical URI from a compatible configuration instead of typing it from memory.

### Declaring a namespace without schema mapping

The XML parser may still recognize expanded names, but tooling/schema validation will not know the matching XSD. Add the namespace URI and XSD location pair in `xsi:schemaLocation`.

### Reversing schemaLocation pairs

`schemaLocation` is a list of URI-location pairs. Missing a location or reversing order causes the validator to load the wrong schema or fail. Verify each pair in order.

### Making Batch the default while forgetting Beans prefixes

If the default namespace is Batch, an unprefixed `bean` element is interpreted as a Batch element instead of Spring Beans. Keep Beans as default and use `batch:` for Batch, or explicitly prefix both namespaces.

### Using inconsistent prefixes

Prefixes are arbitrary, but within one file use a consistent alias for each namespace. Mixing `batch`, `sb`, and `springBatch` hurts readability and causes mistakes.

### Using `ref` for literals or `value` for beans

`ref` expects a bean name; `value` expects a literal/property expression. Using the wrong one prevents Spring from converting the dependency or makes it look up a non-existent bean.

### Referencing the wrong bean ID

`reader="orderReader"` must point to an actual bean ID/alias. Class names or property names do not automatically become bean IDs unless declared that way.

### Duplicate bean IDs or job IDs

Multiple XML files imported into the same context can declare colliding IDs. Depending on bean overriding settings, the context may fail or silently override beans. Use clear, unique IDs and control file imports.

### Mismatched XSD and dependency versions

The IDE may validate against a different schema than runtime. Align dependencies and schema mappings, then test the application context with the exact classpath.

## Troubleshooting workflow for mapping errors

When Spring fails to parse or initialize an XML configuration, inspect in sequence:

1. Identify the failing element and its expanded namespace URI.
2. Check that the prefix is declared properly on the root/ancestor element.
3. Check that `xsi:schemaLocation` has the matching URI-XSD pair.
4. Confirm the XSD is compatible with the Spring Batch dependency.
5. Verify element/attribute structure against the schema.
6. Verify bean IDs/aliases referenced by Batch elements.
7. Check bean classes, constructors, properties, and dependency types.
8. Check `JobRepository`, `DataSource`, and transaction manager.
9. Initialize the application context in tests to surface wiring errors.
10. Launch the job with test data to verify runtime flow and component mapping.

Read the root cause in the stack trace. A schema validation error differs from `NoSuchBeanDefinitionException`, `BeanCreationException`, or step execution failures. Fixing the right layer avoids altering namespace URIs to mask what is actually a bean reference error.

## Testing namespace and mapping configuration

Include integration tests that load the XML file into an application context, verify the job bean exists, and run with a small fixture.

### Checking the application context

Example:

```java
@SpringJUnitConfig(locations = "classpath:/batch/import-job.xml")
class ImportJobXmlConfigurationTest {

    @Autowired
    private ApplicationContext applicationContext;

    @Autowired
    @Qualifier("importOrdersJob")
    private Job importOrdersJob;

    @Test
    void loadsBatchNamespaceAndBeanReferences() {
        assertNotNull(importOrdersJob);
        assertTrue(applicationContext.containsBean("orderReader"));
        assertTrue(applicationContext.containsBean("orderProcessor"));
        assertTrue(applicationContext.containsBean("orderWriter"));
    }
}
```

This test confirms the XML parser created the job and the referenced beans exist. It does not prove the job processes data accurately; add a launch test as well.

### Checking job execution

With Spring Batch test support, use `JobLauncherTestUtils` to run the job and assert `JobExecution` and `StepExecution` reach expected statuses. Ensure the test context loads the right job XML and specifies the job if multiple jobs exist in the context.

```java
JobExecution execution = jobLauncherTestUtils.launchJob(testParameters);
assertEquals(BatchStatus.COMPLETED, execution.getStatus());
```

Afterward, verify business output in the database/files. A `COMPLETED` job only confirms the flow finished successfully in metadata; it does not replace verifying that data was mapped accurately.

### Testing reference errors

You can create a test configuration intentionally referencing a non-existent bean to verify the context fails during initialization. Do not keep broken configurations in production; this is a test for the wiring mechanism or internal documentation if required by the project.

## Principles for organizing XML files

When a project has multiple jobs, split configuration into files by responsibility:

```text
config/
  batch-infrastructure.xml
  import-orders-job.xml
  export-orders-job.xml
  shared-readers.xml
  shared-writers.xml
```

Infrastructure files declare repository, datasource, and transaction manager. Job files declare flows. Shared component files declare reusable beans.

When importing files:

```xml
<import resource="classpath:/config/batch-infrastructure.xml"/>
<import resource="classpath:/config/shared-readers.xml"/>
```

`import` belongs to the Spring Beans namespace and loads additional bean definitions into the same application context. Manage IDs to avoid collisions and circular imports.

Do not split files so finely that readers cannot tell where a job's referenced beans live. Keeping a job file self-contained for job-specific beans while importing shared infrastructure/components often works well.

## Principles for designing namespaces and mappings

When writing Spring Batch XML configurations, verify:

1. Which vocabularies does the file use: Beans, Batch, Context, TX, Util, or AOP?
2. Does each prefix have the exact namespace URI?
3. Does `xsi:schemaLocation` include every namespace URI and XSD pair?
4. Are XSDs compatible with Spring Batch/Spring Framework versions on the classpath?
5. Are `batch:job`, `batch:step`, and `batch:chunk` structured properly per schema?
6. Do `reader`, `processor`, `writer`, `tasklet`, and `job-repository` reference the right bean IDs?
7. Are `ref` and `value` used appropriately for each dependency type?
8. Are scope and SpEL configured for timely late binding?
9. Are bean IDs and job/step IDs unique across the application context?
10. Do integration tests load XML, resolve beans, and run the job with representative data?

Keeping Spring Beans as the default namespace and using the `batch` prefix for Spring Batch elements generally improves readability. Namespace URIs identify vocabularies; schema locations supply XSDs; namespace parsers turn XML into bean/job definitions; bean IDs and references wire runtime components. Understanding each mapping layer helps distinguish XML schema errors from wiring errors and runtime job failures.

## Summary

Spring Batch XML uses namespaces to separate vocabularies and namespace parsers to turn elements into job/step configurations. `xmlns:batch` maps a prefix to the URI `http://www.springframework.org/schema/batch`; `xsi:schemaLocation` supplies namespace URI and `spring-batch.xsd` XSD pairs for validation/tooling. Prefixes are only aliases; URIs identify namespaces. `batch:job`, `batch:step`, and `batch:chunk` describe flows, while bean IDs and `reader`, `processor`, `writer`, and `ref` attributes map to objects in the Spring application context. Use `ref` for bean dependencies, `value` for literals/SpEL, and `scope="step"` for execution-time late binding. Keep schemas aligned with dependencies, keep IDs unique, and test both context initialization and job execution to catch namespace, XSD, and bean mapping issues.
