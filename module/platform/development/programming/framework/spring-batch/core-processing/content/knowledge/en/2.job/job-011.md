# A Job ends with COMPLETED or FAILED

In Spring Batch, one execution of a Job is tracked by a `JobExecution` object. When the process ends, the status (`BatchStatus`) of the JobExecution indicates whether the run completed successfully or failed. The two most common statuses are `COMPLETED` and `FAILED`.

- `COMPLETED` indicates that the Job flow ended normally according to its configuration.
- `FAILED` indicates that the execution failed and the error was reflected in the Job's status.

This is the status of **one Job execution**, not a fixed status of the Job definition. The same Job can have many executions with different results, depending on the input data, the parameters, and the situations that arise at run time.

## 1. What is BatchStatus?

Spring Batch stores the Job's execution history in `JobExecution`. This object has a `status` property of type `BatchStatus`. The status changes throughout the lifecycle of the run and is updated as the Steps execute.

A normal run flow can be pictured as follows:

```text
JobLauncher receives the Job and JobParameters
                 |
                 v
       Create the JobExecution
                 |
                 v
       STARTING / STARTED
                 |
                 v
          Execute the Steps
                 |
          +------+------+
          |             |
     Flow completes   Unhandled error
          |             |
          v             v
      COMPLETED       FAILED
```

`BatchStatus` is the execution status that Spring Batch uses to manage the lifecycle, restart, and operation of a Job. It differs from the exit result (`ExitStatus`), although the two pieces of information are often related.

## 2. When does a Job end with COMPLETED?

`COMPLETED` means the Job has reached a normal end point according to the configured flow. The required Steps in the flow have finished and no error causes the Job's final status to be marked as failed.

For example, a customer data import Job consists of three Steps:

```text
customerImportJob
       |
       v
validateFileStep       COMPLETED
       |
       v
importCustomerStep     COMPLETED
       |
       v
writeSummaryStep       COMPLETED
       |
       v
JobExecution           COMPLETED
```

When the whole flow ends successfully according to the configuration, the `JobExecution` has `BatchStatus.COMPLETED`.

Some points to understand correctly:

- `COMPLETED` speaks about the execution result according to the Job's rules. It does not by itself confirm that the business data is entirely correct if the application does not check those rules.
- A Step can be configured to allow skipping some erroneous records (`skip`). If the errors are within the allowed limit and the Step ends successfully, the Job can still be `COMPLETED`.
- A successful retry also does not make the Job fail. For example, a data write encounters a transient error, is retried, and finally succeeds, so the Step can complete normally.
- If the business requires an additional condition, such as the number of skipped records having to be zero, the application needs to check and express that condition in the logic or the Job flow.

Therefore, when you see `COMPLETED`, operators should also read the `ExitStatus`, the read/write/skip counts, and the business logs if they need to confirm the actual result.

## 3. When does a Job end with FAILED?

`FAILED` appears when the execution cannot complete successfully and the error is propagated to the Job's result. A common case is a Step that throws an unhandled exception or has exhausted its retry policy and still fails.

For example, a Job that processes transactions in order:

```text
transactionJob
       |
       v
readInputStep          COMPLETED
       |
       v
processTransactionStep FAILED
       |
       v
writeReportStep        not run
       |
       v
JobExecution           FAILED
```

In an ordinary sequential Job, when a Step fails, the subsequent Steps are not run and the Job ends with `FAILED`.

Common causes include:

- The input file cannot be read, has the wrong format, or does not exist.
- The database or an external service connection fails.
- The Reader, Processor, or Writer throws an exception.
- An error exceeds the retry limit or is not of a type allowed to be skipped.
- Business logic deliberately marks the Step as failed.

`FAILED` does not mean all the earlier work is automatically undone. Transactions are usually managed per chunk or per Step. Chunks that have committed and Steps that completed earlier may still retain the data that was written. Therefore, the restart design needs to account for the possibility that data has been partially processed.

## 4. Distinguishing BatchStatus and ExitStatus

This is an important point when reading the status or configuring control flow.

| Property | Meaning | Example |
|---|---|---|
| `BatchStatus` | The execution lifecycle status managed by Spring Batch | `COMPLETED`, `FAILED`, `STOPPED` |
| `ExitStatus` | The exit result code returned from a Job or Step, which can be used to route the flow | `COMPLETED`, `FAILED`, `NO_DATA`, `INVALID_INPUT` |

`BatchStatus` answers the question: what state is the execution in? `ExitStatus` answers: what result code did the Step or Job end with?

The default `ExitStatus` codes usually correspond to the execution status, but they are not the same property. An application can create its own exit codes to describe business results. For example, a Step can return `NO_DATA` so that the Job goes to a Step that records there is no data, instead of treating this as a technical error.

A Job can use a Step's `ExitStatus` to choose the next branch. For example, an input validation Step can return `INVALID_INPUT`; the Job moves to a Step that quarantines the file or records the error. When designing a flow with branches, clearly determine the final result of the whole Job. You should not infer the Job's status from just one Step's name or one log line.

## 5. Step errors and the final result of the Job

In a simple Job that runs sequentially, a Step error usually makes the Job fail. However, Spring Batch allows you to define a conditional flow. A Step that ends with a specific `ExitStatus` can be routed to another Step to handle that situation.

An example of a process with branches:

```text
                 +--> COMPLETED --> processDataStep --> publishStep
                 |
Job --> validate-+
                 |
                 +--> FAILED -----> handleInvalidFileStep
```

The error branch can perform work such as quarantining a file, recording error information, or sending a notification. The Job's final status depends on the configured flow and the final result of that flow. An error that has been handled by a business branch does not necessarily mean the Job must end in `FAILED`; conversely, if the error is still propagated out of the flow, the Job will fail.

This does not mean you should hide errors. If invalid data causes the business goal to remain incomplete, keep the failed result or use a separate business exit code so the monitoring system can recognize it. If the Job has truly finished processing under a valid alternative rule, express that clearly through the flow configuration and the result code.

When using transitions such as `on("FAILED")`, remember that the condition is matched against the Step's `ExitStatus`. You can use `on("*")` for the remaining results. You should declare the branches explicitly, avoiding letting an error status accidentally fall into the success branch.

## 6. Example of declaring a Job and reading the final result

With Spring Batch 5 and later, a sequential Job can be declared with `JobBuilder`:

```java
import org.springframework.batch.core.Job;
import org.springframework.batch.core.Step;
import org.springframework.batch.core.job.builder.JobBuilder;
import org.springframework.batch.core.repository.JobRepository;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class CustomerImportJobConfig {

    @Bean
    public Job customerImportJob(
            JobRepository jobRepository,
            Step validateFileStep,
            Step importCustomerStep,
            Step writeSummaryStep) {

        return new JobBuilder("customerImportJob", jobRepository)
                .start(validateFileStep)
                .next(importCustomerStep)
                .next(writeSummaryStep)
                .build();
    }
}
```

If the Steps end successfully along this flow, the Job can end `COMPLETED`. If a Step raises an unhandled error and the error stops the flow, the Job ends `FAILED`.

After calling the `JobLauncher`, the application receives a `JobExecution`. With a synchronously running launcher, by the time the `run` method returns, the final status is usually available. You can check it as follows:

```java
import org.springframework.batch.core.BatchStatus;
import org.springframework.batch.core.JobExecution;
import org.springframework.batch.core.JobParameters;
import org.springframework.batch.core.launch.JobLauncher;
import org.springframework.stereotype.Component;

@Component
public class CustomerImportRunner {

    private final JobLauncher jobLauncher;
    private final Job customerImportJob;

    public CustomerImportRunner(
            JobLauncher jobLauncher,
            Job customerImportJob) {
        this.jobLauncher = jobLauncher;
        this.customerImportJob = customerImportJob;
    }

    public void run(JobParameters parameters) throws Exception {
        JobExecution execution =
                jobLauncher.run(customerImportJob, parameters);

        BatchStatus status = execution.getStatus();

        if (status == BatchStatus.COMPLETED) {
            System.out.println("Import completed successfully");
        } else if (status == BatchStatus.FAILED) {
            System.err.println("Import failed: " + execution.getAllFailureExceptions());
        }
    }
}
```

This example assumes the `JobLauncher` runs synchronously. If the application configures an asynchronous launcher, `run` can return while the Job is still running; the status received at that time can be `STARTING` or `STARTED`. In this case, you must not treat the initial status as the final result. The system needs to track the `JobExecution` through a monitoring mechanism or the repository until it reaches an end status.

## 7. Tracking the result with JobExecutionListener

When you need to log, send notifications, or update a monitoring system after the Job ends, you can use a `JobExecutionListener`. The `afterJob` method is called after the Job ends, whether the Job completed or failed.

```java
import org.springframework.batch.core.BatchStatus;
import org.springframework.batch.core.JobExecution;
import org.springframework.batch.core.JobExecutionListener;
import org.springframework.stereotype.Component;

@Component
public class ImportJobListener implements JobExecutionListener {

    @Override
    public void afterJob(JobExecution jobExecution) {
        if (jobExecution.getStatus() == BatchStatus.COMPLETED) {
            System.out.println("Job completed: " + jobExecution.getJobId());
        } else if (jobExecution.getStatus() == BatchStatus.FAILED) {
            System.err.println("Job failed: " + jobExecution.getJobId());
            jobExecution.getAllFailureExceptions()
                    .forEach(Throwable::printStackTrace);
        }
    }
}
```

Register the listener in the Job definition:

```java
return new JobBuilder("customerImportJob", jobRepository)
        .start(validateFileStep)
        .next(importCustomerStep)
        .next(writeSummaryStep)
        .listener(importJobListener)
        .build();
```

A listener is suitable for performing post-processing actions such as recording the result or signaling another system. If the post-processing action can fail and affect the business result, you need to decide clearly whether it belongs to a Step of the Job or is just an external notification task. An error that occurs after the Job has completed does not automatically turn a finished JobExecution into `FAILED`.

## 8. FAILED can be restarted

A Job that ends `FAILED` can usually be restarted if the Job and Steps allow restart. When rerunning with the same Job name and the same identifying parameters (`identifying JobParameters`), Spring Batch recognizes the same `JobInstance` and creates a new `JobExecution` for the next attempt.

Example:

```text
Job: customerImportJob
  |
  +--> JobInstance: fileDate=2026-11-15
         |
         +--> JobExecution #1: FAILED
         |       validateFileStep      COMPLETED
         |       importCustomerStep    FAILED
         |
         +--> JobExecution #2: COMPLETED
                 validateFileStep      COMPLETED / handled according to the restart policy
                 importCustomerStep    COMPLETED
                 writeSummaryStep      COMPLETED
```

The old JobExecution is still stored for history inspection. The new run has its own JobExecution. Spring Batch can continue from an appropriate Step or checkpoint instead of always rerunning everything from the start; the specific behavior depends on the restart configuration, the Step state, the `ExecutionContext`, and how each Step is implemented.

For a safe restart, pay attention to:

1. **Save the necessary checkpoints.** The Reader or processing component needs to save a position and state that can be restored on restart.
2. **Determine the transaction boundaries.** Data committed before the error may still exist.
3. **Avoid duplicate writes.** The Writer or operations that call external services should have an idempotent mechanism, a business key, or a check for already-processed records.
4. **Choose the right identifying parameters.** The same unit of work needs to use the same set of identifying parameters on restart. Adding a new identifying parameter can create a different JobInstance and cause the application to reprocess data as a new job.
5. **Check the restart policy.** A Job can be configured not to allow restart; some Steps or states also have their own rules.

A JobInstance that is `COMPLETED` normally cannot be run again as a new execution with the same identifying parameters. If you need to process a new data period or batch, provide identifying parameters that represent the new unit of work.

## 9. Other end states to distinguish

Although `COMPLETED` and `FAILED` are the two common results, `BatchStatus` has other states too:

| Status | General meaning |
|---|---|
| `COMPLETED` | The Job ends normally according to the configured flow. |
| `FAILED` | The Job failed due to an error propagated to the execution result. |
| `STOPPED` | The Job was stopped on request or through a controlled stop mechanism; it can be restarted if the configuration allows. |
| `ABANDONED` | The execution is marked as not to be restarted in the ordinary way. |
| `UNKNOWN` | The execution status cannot be determined with certainty; you need to investigate the metadata and the actual situation. |
| `STARTING`, `STARTED`, `STOPPING` | The states while the Job is being launched, executed, or stopped. |

You should not merge `STOPPED` with `FAILED`. `STOPPED` usually represents a controlled stop, while `FAILED` represents an error during processing. Similarly, `ABANDONED` is a state for administering the execution lifecycle and has a different meaning from an ordinary failed run.

## 10. How to read the result in operations

When a Job ends, check the status at the JobExecution level first, then look at the StepExecutions to find the cause and the scope of impact.

| Information to look at | What to determine |
|---|---|
| Job name and JobParameters | Which Job ran and which data unit was it processing? |
| `JobExecution.getStatus()` | Is the final execution result `COMPLETED`, `FAILED`, or another status? |
| `JobExecution.getExitStatus()` | Does the exit result code contain business information or a custom code? |
| Failure exceptions | Which exception made the run fail? |
| StepExecution | Which Step failed, which Step completed, which Step has not run? |
| Read, write, filter, skip counts | How many records were processed, skipped, or written? |
| ExecutionContext | Is there any checkpoint saved to support restart? |

A Job with the `FAILED` status does not fully tell you which data was written. You need to look at the status and figures of each Step, the logs, the transactions, and the business data to decide how to recover. Similarly, `COMPLETED` needs to be read together with the `ExitStatus` and the processing figures to confirm that the business conditions have been met.

## 11. Common misunderstandings

| Incorrect understanding | Accurate understanding |
|---|---|
| `COMPLETED` means every record is valid | A Job can complete even though it skipped records if the policy allows. You need to check the figures and business rules. |
| If a Step is FAILED then the Job is definitely FAILED | In a conditional flow, a Step's error can be routed to another handling branch. The final status depends on the flow and the final result. |
| `FAILED` means all data changes are rolled back | Chunks or Steps that committed earlier may still retain their changes. |
| A Job that is FAILED cannot be rerun | A failed JobInstance can usually be restarted if the configuration and state allow it. |
| Each restart creates a new JobInstance | A restart with the same Job and identifying JobParameters creates a new JobExecution for the same JobInstance. |
| `ExitStatus` and `BatchStatus` are the same | They are two different pieces of information: the exit result code and the execution lifecycle status. |
| `JobLauncher.run()` always returns the final status | With an asynchronous launcher, the Job may still be running when the method returns. |

## Conclusion

`COMPLETED` and `FAILED` are two important end states of `JobExecution` in Spring Batch. `COMPLETED` indicates that the Job flow ended normally according to the configuration; `FAILED` indicates that an error prevented the execution from completing. The final result needs to be read together with the `ExitStatus`, the status of each Step, the exceptions, and the processing figures. When a Job fails, Spring Batch stores the execution history and can support restarting the same JobInstance if the configuration allows. Understanding these states clearly helps design error flows, monitor operations, and recover batch data safely.
