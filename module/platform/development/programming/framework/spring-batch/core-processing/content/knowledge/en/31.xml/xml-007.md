# Position restart in XML

In Spring Batch, a job reading an XML file may process thousands or millions of fragments. If the job stops mid-way, the next run needs to resume from the last committed position instead of reprocessing the entire file or losing data.

With `StaxEventItemReader`, Spring Batch supports restarts by persisting read state in `ExecutionContext`. The reader tracks the number of XML items read, saves checkpoints per chunk, and restores the logical position when the job restarts. This position is tracked by the number of fragments/items processed, not by an arbitrary byte offset in the file.

For accurate restarts, the reader must have a stable name, enable state saving, use the same JobInstance on restart, and reread the exact same resource with unchanged content. Distinguish between the reader's position inside the XML file and Spring Batch's choice of which step to rerun.

## 1. XML readers and restart in Spring Batch

Spring Batch typically uses `StaxEventItemReader<T>` to read XML fragments into Java items. The reader relies on the StAX streaming API so it does not need to load the whole document into memory like DOM parsing.

Example file with root `<orders>` and multiple `<order>` elements:

```xml
<orders>
    <order>
        <id>1001</id>
        <customerId>C001</customerId>
        <amount>125.50</amount>
    </order>
    <order>
        <id>1002</id>
        <customerId>C002</customerId>
        <amount>89.00</amount>
    </order>
    <order>
        <id>1003</id>
        <customerId>C003</customerId>
        <amount>210.00</amount>
    </order>
</orders>
```

If `fragmentRootElementName` is `order`, each `<order>` element is mapped to one item. The reader returns orders 1001, 1002, and 1003 sequentially, then returns `null` when data ends.

When a step commits a chunk, Spring Batch persists the reader's state. If the execution fails after committing two orders, a restart restores the checkpoint and continues from the uncommitted order.

## 2. Distinguishing XML position from step position in a job

Two restart concepts are frequently confused:

| Concept | Meaning | Managed by |
|---|---|---|
| Position in XML input | Next fragment/item the reader needs to process | Reader state in `ExecutionContext` |
| Position in job flow | Which steps completed, which step needs to rerun | `JobRepository`, `JobExecution`, and `StepExecution` metadata |

Example job with three steps:

```text
validateXmlStep       -> COMPLETED
importXmlStep         -> FAILED mid-file
archiveXmlStep        -> not yet run
```

When restarting the same JobInstance, Spring Batch normally skips the completed `validateXmlStep`, restarts `importXmlStep` using the reader checkpoint, and runs `archiveXmlStep` only after the import step finishes.

Reader fragment recovery does not replace step restart mechanics. Both job/step metadata and reader state must be persisted properly.

## 3. How does StaxEventItemReader store position?

`StaxEventItemReader` belongs to the item-counting stateful readers. When opened, it reads saved state from `ExecutionContext`; on restart, the reader reopens the resource and advances past the number of fragments previously checkpointed.

With the XML example above, if the checkpoint recorded two completed items, the logical resume position is the third fragment.

```text
File XML: order 1001 | order 1002 | order 1003 | order 1004
                         
First run:
  read order 1001
  read order 1002
  write chunk and COMMIT
  checkpoint = 2 items
  error before next chunk commits

Restart:
  reopen XML resource
  restore checkpoint = 2
  skip two checkpointed fragments
  resume from order 1003
```

This is a logical position by item/fragment count recognized by the reader, not an exact byte offset in the file. In XML, each fragment's length can vary and the parser must understand XML structure to identify boundaries.

## 4. ExecutionContext holds checkpoints

`ExecutionContext` is the state storage area for a `StepExecution` or `JobExecution`. The reader implements `ItemStream`, so Spring Batch invokes lifecycle callbacks to open resources, update state, and close the reader.

Three critical callbacks:

- `open(executionContext)`: opens the resource and restores saved state if present.
- `update(executionContext)`: writes current state into the context so Spring Batch persists the checkpoint.
- `close()`: releases the parser and resource when the step finishes.

In chunk processing, checkpoints are updated at chunk commit boundaries. If a chunk has not committed and the execution fails, the restart must resume from the latest persistently saved checkpoint.

`ExecutionContext` is not a temporary in-memory Java variable. With a standard JDBC repository configuration, Spring Batch persists the context to the metadata repository so it can be read back on the next JobExecution.

## 5. Configuring StaxEventItemReader in Java

Example reader reading each `<order>` fragment and mapping with `Jaxb2Marshaller`:

```java
@Bean
Jaxb2Marshaller orderUnmarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Order.class);
    return marshaller;
}

@Bean
@StepScope
StaxEventItemReader<Order> orderXmlReader(
        @Value("#{jobParameters['input.file']}") String inputFile,
        Jaxb2Marshaller orderUnmarshaller) {

    return new StaxEventItemReaderBuilder<Order>()
        .name("orderXmlReader")
        .resource(new FileSystemResource(inputFile))
        .addFragmentRootElements("order")
        .unmarshaller(orderUnmarshaller)
        .saveState(true)
        .build();
}
```

Key settings:

- `name("orderXmlReader")`: stable name used to identify reader state in `ExecutionContext`.
- `resource(...)`: XML resource to read; can late-bind from JobParameters.
- `addFragmentRootElements("order")`: identifies the root element of each item.
- `unmarshaller(...)`: converts the XML fragment into a Java object.
- `saveState(true)`: enables the reader to save state for restarts.
- `@StepScope`: creates the target reader per StepExecution and resolves the input file when the step runs.

Do not rename the reader between the initial run and a restart of the same JobInstance. The reader name is part of state key generation; renaming it prevents the reader from locating the old checkpoint.

## 6. XML namespace configuration for the reader

When configuring Spring Batch with XML, the reader can be declared as a Spring bean. The example below uses step scope to get the file path from JobParameters:

```xml
<bean id="orderXmlReader"
      class="org.springframework.batch.item.xml.StaxEventItemReader"
      scope="step">
    <property name="name" value="orderXmlReader"/>
    <property name="resource" value="#{jobParameters['input.file']}"/>
    <property name="fragmentRootElementName" value="order"/>
    <property name="unmarshaller" ref="orderUnmarshaller"/>
    <property name="saveState" value="true"/>
    <aop:scoped-proxy/>
</bean>
```

To use `<aop:scoped-proxy/>`, the configuration file must declare the corresponding AOP namespace. The `orderUnmarshaller` bean must be configured to map `Order` fragments per the application's XML schema.

A scoped proxy lets the step bean be constructed in the application context before a JobExecution exists, while the target reader is instantiated only when StepScope is active.

## 7. Declaring job and chunk step in XML

An XML job can use a chunk step with the reader declared above:

```xml
<batch:job id="importOrdersJob" restartable="true">
    <batch:step id="importOrdersStep">
        <batch:tasklet transaction-manager="transactionManager">
            <batch:chunk
                    reader="orderXmlReader"
                    processor="orderProcessor"
                    writer="orderWriter"
                    commit-interval="100"/>
        </batch:tasklet>
    </batch:step>
</batch:job>
```

`restartable="true"` allows the job to be restarted per Spring Batch rules. `commit-interval="100"` sets the chunk size to 100 items; reader state is checkpointed according to committed chunk progress.

In real configurations, declare full `batch` and `aop` namespaces, schema locations, and `transactionManager`, `orderProcessor`, and `orderWriter` beans. The reader name in the step must point to the scoped proxy bean.

## 8. saveState and name determine recoverability

The reader must save state if you want position recovery after restart. With `StaxEventItemReader`, configure `saveState(true)` explicitly rather than relying on defaults.

```java
return new StaxEventItemReaderBuilder<Order>()
    .name("orderXmlReader")
    .resource(resource)
    .addFragmentRootElements("order")
    .unmarshaller(unmarshaller)
    .saveState(true)
    .build();
```

`saveState(false)` stops the reader from writing its own checkpoint into `ExecutionContext`. If the step fails and is restarted, the reader cannot use saved state to restore item count as expected; the application may reread from the start or need another recovery mechanism.

Do not reuse the same reader name for multiple stateful readers within the same step if they could overwrite context keys. Pick stable, unique names independent of runtime execution time.

## 9. Restart must use the same JobInstance

Spring Batch identifies a `JobInstance` by job name and identifying `JobParameters`. When restarting, pass the exact same identifying parameters from the initial run.

First run example:

```java
JobParameters parameters = new JobParametersBuilder()
    .addString("input.file", "/data/orders-2026-11-15.xml", true)
    .addString("businessDate", "2026-11-15", true)
    .toJobParameters();

jobLauncher.run(importOrdersJob, parameters);
```

If the execution fails mid-file, relaunch the same job with the same identifying parameters:

```java
JobParameters restartParameters = new JobParametersBuilder()
    .addString("input.file", "/data/orders-2026-11-15.xml", true)
    .addString("businessDate", "2026-11-15", true)
    .toJobParameters();

jobLauncher.run(importOrdersJob, restartParameters);
```

This restarts the same JobInstance if the prior instance is in a restartable state. Spring Batch creates a new JobExecution while reusing the old instance's persisted metadata and checkpoints.

Adding a new timestamp or `run.id` as an identifying parameter causes Spring Batch to create a new JobInstance. The reader will then not resume from the failed instance's checkpoint.

## 10. XML resources must remain stable across runs

A checkpoint is only meaningful when the restart reads the exact same data source. If the file at the same path is replaced, the saved item position may point to completely different content.

Example:

```text
First run:
  /data/orders.xml contains 10,000 orders
  checkpoint = 4,000 orders

Before restart:
  file at /data/orders.xml is replaced by a new file
  fragment order and content change

Restart:
  reader skips 4,000 fragments in the new file
  remaining orders no longer correspond to the first run
```

Recommended measures:

- Place files in an immutable directory keyed by batch ID or file ID.
- Do not overwrite source files while the job is running or eligible for restart.
- Compute checksums or store source versions to confirm the file has not changed.
- Include source ID, file version, or checksum in identifying JobParameters when they define the dataset.
- If restarts are needed, preserve the exact original file until the JobInstance completes.

Do not rely solely on file names as identity if the same name can be reused for different content. An immutable file ID or checksum identifies the source far more reliably.

## 11. Checkpoints are saved per chunk, not per byte

Suppose the chunk size is 100. The reader reads ahead fragments to assemble a chunk; once the writer and transaction complete, Spring Batch updates state so restarts resume from the right checkpoint.

```text
Chunk 1: fragments 1..100   -> COMMIT -> checkpoint 100
Chunk 2: fragments 101..200 -> COMMIT -> checkpoint 200
Chunk 3: fragments 201..300 -> error before commit

Restart:
  restore checkpoint 200
  resume from fragment 201
```

The restored position reflects committed progress. If the process dies after reading an item but before the chunk commits, that item may be read again. This behavior is necessary so uncommitted data is never lost.

Therefore, writers and non-transactional side effects must be safe when items are reprocessed. Do not rely on the assumption that every fragment is read or processed strictly once.

## 12. Readers require deterministic fragment ordering

Item-count restart assumes that fragment ordering on reread matches the previous run. If the order changes, the same checkpoint can land on a different item.

With a static XML file, element order is determined by document order. However, if the XML is regenerated, re-sorted, or merged from multiple sources prior to restart, the order can shift.

If the source is generated dynamically, save an immutable snapshot or create a deterministically ordered manifest. Never edit the file between an initial run and a restart.

With multiple XML files, keep both the resource list and its sort order stable. Adding or removing files at the start of the list alters what the checkpointed position refers to.

## 13. Restart with multiple XML files

If a job reads multiple resources, you can use `MultiResourceItemReader` with `StaxEventItemReader` as its delegate. The wrapper stores the current resource index and the delegate stores reading progress within the current file.

```java
@Bean
@StepScope
MultiResourceItemReader<Order> allOrderFilesReader(
        @Value("#{jobParameters['input.directory']}") String directory,
        StaxEventItemReader<Order> orderXmlReader) throws IOException {

    Resource[] resources = new PathMatchingResourcePatternResolver()
        .getResources("file:" + directory + "/*.xml");
    Arrays.sort(resources, Comparator.comparing(Resource::getFilename));

    return new MultiResourceItemReaderBuilder<Order>()
        .name("allOrderFilesReader")
        .resources(resources)
        .delegate(orderXmlReader)
        .saveState(true)
        .build();
}
```

The resource list must be sorted deterministically. If the initial run had `a.xml`, `b.xml`, `c.xml` and a restart inserts `0.xml` at the front, the saved resource index points to the wrong file.

For multiple files, preserve the exact file list or manifest from the initial run. If files arrive continuously, capture a manifest before launch and use that manifest for restarts.

## 14. XML fragments and unmarshallers must stay stable

`StaxEventItemReader` identifies items based on the configured fragment root element. Changing `fragmentRootElementName`, the unmarshaller, or the schema mapping between a run and a restart can interpret the same item position differently.

Components to keep stable:

- Fragment root name, e.g., `order`.
- XML namespace configuration if the source uses namespaces.
- Unmarshaller and class mappings.
- Schema version handling rules.
- Fragment order within the resource.

If a provider changes the XML schema while a job is still restartable, maintain the corresponding mapping version or migrate the file to a new snapshot/version. Do not restart an old JobInstance with a parser that has different semantics without a migration plan.

## 15. XML namespaces

XML can use default namespaces or prefixes. The fragment root and unmarshaller must match the actual namespace structure. A file with `<o:order>` or a default namespace still has local name `order`, yet JAXB mappings must declare namespaces per schema.

Example:

```xml
<orders xmlns="urn:example:orders:v1">
    <order>
        <id>1001</id>
    </order>
</orders>
```

The JAXB class may need `@XmlRootElement(name = "order", namespace = "urn:example:orders:v1")` or corresponding package-level namespace mappings.

If the namespace or schema version changes, the reader may fail to find fragments or the unmarshaller may fail. Schema errors should not be fixed by tampering with checkpoints; identify the exact parser/schema version of the source.

## 16. Reader name and ExecutionContext keys

The reader name forms part of the persisted state identifier. When the name changes, the reader looks under a different key and cannot restore its old position.

Stable name example:

```java
.name("orderXmlReader")
.saveState(true)
```

Avoid dynamic names like:

```java
// Avoid names that change on each launch
.name("orderXmlReader-" + System.currentTimeMillis())
```

Dynamic names sever the link between old state and the new reader. With multiple readers in the same step, choose distinct names that remain stable by role.

## 17. allow-start-if-complete and start-limit

XML position restart also depends on whether the step itself is allowed to rerun. By default, a completed step in a JobInstance usually does not rerun when the job restarts. Two step attributes commonly configured in XML are:

- `allow-start-if-complete`: allows an already completed step to rerun when the job restarts.
- `start-limit`: limits how many times a step may be started.

Example:

```xml
<batch:step id="importXmlStep"
            allow-start-if-complete="false"
            start-limit="3">
    <batch:tasklet transaction-manager="transactionManager">
        <batch:chunk reader="orderXmlReader"
                     writer="orderWriter"
                     commit-interval="100"/>
    </batch:tasklet>
</batch:step>
```

`allow-start-if-complete="true"` should only be used when intentionally rerunning a completed step within the same JobInstance. Enabling it carelessly can reprocess data and create duplicate side effects.

`start-limit` caps step launch attempts; it is neither the item retry count nor the XML checkpoint. Once exceeded, the step cannot be launched again under that configuration.

## 18. Restartable jobs and completed JobInstances

A job can be configured with `restartable="false"` in XML. Spring Batch then disallows restarting that JobInstance through normal means.

```xml
<batch:job id="importOrdersJob" restartable="true">
    <!-- steps -->
</batch:job>
```

To restart a failed execution, you need:

1. The job configured as restartable.
2. The JobInstance in a restartable state.
3. The same identifying JobParameters.
4. The reader having saved state and the resource still intact.
5. The step not blocked by start count limits or rerun restrictions.

If a JobInstance is already `COMPLETED`, launching with the same identifying parameters is normally rejected. To reprocess completed data as a new business run, supply new identifying parameters or design a separate reprocessing job.

## 19. Skip, retry, and XML position

The reader can hit parse errors on an XML fragment. If the step permits skipping the matching exception type, Spring Batch can discard the bad item and continue. If the error is unrecoverable or exceeds the skip limit, the step fails.

```java
return new StepBuilder("importXmlStep", jobRepository)
    .<Order, Order>chunk(100, transactionManager)
    .reader(orderXmlReader)
    .writer(orderWriter)
    .faultTolerant()
    .skip(InvalidXmlRecordException.class)
    .skipLimit(20)
    .build();
```

Exact exception types depend on the unmarshaller and how the application wraps parse errors. Only skip errors isolated to a single fragment that can be discarded per business rules. If XML is malformed at the document level, missing closing tags, or using the wrong namespace/schema file-wide, skipping individual items may be impossible; fail and investigate the source.

Retries also require classification. Transient resource access errors can be retried under an appropriate policy; permanent malformed XML errors do not heal themselves on reread.

## 20. Reader state does not guarantee exactly-once side effects

Checkpoints protect reader progress at commit boundaries, but do not automatically ensure external side effects happen only once.

For instance, a processor/writer might send a message or call an API before the chunk commits. If the process dies after the external system receives the request but before JobRepository saves the checkpoint, a restart can reread the fragment and resend the request.

Safeguards:

- Use idempotency keys based on the fragment's business ID.
- Write events to an outbox in the same database transaction as batch data and publish after commit.
- Use unique constraints/upserts for outputs that may be rewritten.
- Write outputs to staging and publish only after the step finishes.
- Reconcile request timeouts, since the client may not know whether the external system processed the call.

Do not treat `saveState(true)` as an exactly-once guarantee for HTTP, email, message brokers, or filesystems.

## 21. Large XML files and restart cost

`StaxEventItemReader` uses streaming to avoid holding the entire XML document in memory. However, restoring position by item count can require reopening the file and advancing past previously checkpointed fragments.

With very large files and a checkpoint near the end, restart time can grow because the reader must parse/skip fragments before that position. This is the trade-off of item-count recovery compared to seeking to a byte offset.

If restarting from far into a file is a frequent requirement, consider:

- Splitting the source into multiple files or smaller batches.
- Creating a manifest of independent segments.
- Partitioning by file or data key when independent boundaries can be established.
- Using a data source supporting direct seek/checkpoint if the workload demands it.
- Storing immutable snapshots so rereading initial fragments remains consistent.

Do not manually edit `ExecutionContext` to set an arbitrary item count without understanding reader state and corresponding data. A wrong checkpoint can skip or duplicate fragments.

## 22. Common errors when restarting XML

| Error | Consequence | Fix |
|---|---|---|
| Not enabling `saveState` | Reader has no checkpoint to restore position | Enable `.saveState(true)` or property `saveState=true` |
| Changing reader `name` | Old state key not found | Keep reader name stable |
| Changing identifying JobParameters on restart | Creates a new JobInstance instead of using old checkpoint | Reuse original identifying parameters |
| Modifying file content at the same path | Old item count points to different fragments | Keep input immutable and use source version/checksum |
| Changing order of multiple resources | Old resource index can point to the wrong file | Use a manifest and deterministic ordering |
| Changing fragment root or unmarshaller | Same position parsed under a different structure | Keep mapping/schema version for old JobInstances |
| Assuming checkpoint is a byte offset | Seeks to wrong position in XML | Understand state is tracked by item/fragment count |
| Unintentionally setting `allow-start-if-complete=true` | Completed step can rerun and produce duplicate side effects | Enable only when the step is idempotent and business requires it |
| Disabling `restartable` on the job | Cannot restart JobInstance under normal rules | Configure restartable if recovery is needed |
| Treating skip as a fix for file-wide malformed XML | Parser may be unable to continue | Fail the file and fix the source/schema |
| Using a singleton reader across executions | State or resources may be shared improperly | Use StepScope for execution-dependent readers |

## 23. Testing position restart in XML

Integration tests should create an XML file with identifiable fragments, run the job until one chunk commits, and intentionally fail the step in a subsequent chunk.

Cases to verify:

1. Normal XML reading: fragment count and object mapping are accurate.
2. `saveState(true)`: state is written to StepExecution `ExecutionContext` after chunk commit.
3. Restarting the same JobInstance: reader resumes from the fragment right after the checkpoint.
4. Failure before commit: uncommitted fragments are reread on restart.
5. Changed reader name: test proves the state key no longer matches; avoid renaming in production.
6. Changed JobParameters: creates a new JobInstance instead of restarting the old instance.
7. Modified file: process detects source version/checksum mismatch.
8. MultiResource reader: file order and position within the current file restore properly.
9. `allow-start-if-complete`: completed step reruns only when configuration permits.
10. Output idempotency: reread items do not create duplicate data or side effects.

Tests should assert `JobInstance` ID, `JobExecution` ID, `StepExecution` status, `ExecutionContext`, and output data. Simply checking that the job completes after restart is not enough to prove the reader resumed at the right position.

## 24. Operational procedure when an XML job needs restart

When an XML-reading job fails, follow these steps in order:

1. Identify the failed JobInstance and JobExecution in JobRepository.
2. Check which step failed and which reader holds checkpoints.
3. Verify `saveState` is enabled and the reader name has not changed.
4. Verify the source file, checksum/version, and resource order match the initial run.
5. Check whether the exception is transient, a single-fragment error, or a file-wide structural error.
6. Resolve the root cause while preserving identifying JobParameters if continuing the same business run.
7. Restart the same JobInstance so Spring Batch uses the saved checkpoint.
8. Reconcile read/write/skip counts and output data after restart.
9. Archive or delete source files only after the job completes and results are verified.

Do not create a new JobInstance just to bypass a failed status if the goal is to continue the exact interrupted processing run.

## Conclusion

Position restart for XML in Spring Batch relies on reader state persisted in `ExecutionContext`. `StaxEventItemReader` tracks progress by the count of processed fragments/items; on restart, the reader reopens the resource and restores its logical position from the latest committed checkpoint. This is not a byte offset in the file.

To recover accurately, keep the reader name and fragment/unmarshaller configuration stable, enable `saveState`, reuse identifying JobParameters, and ensure the XML input and resource ordering remain unchanged. Job/step restart configuration controls which step reruns; reader checkpoints control which fragment is read next. Combine both mechanisms with idempotent outputs and integration tests for safe restarts.
