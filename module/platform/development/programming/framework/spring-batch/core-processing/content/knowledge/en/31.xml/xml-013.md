# Testing XML readers and writers in Spring Batch

In Spring Batch, XML is usually read and written fragment by fragment rather than loading the entire document into memory. The common reader is **StaxEventItemReader**; the corresponding writer is **StaxEventItemWriter**. Both components work with StAX to read or write XML streams, while Spring OXM such as **Jaxb2Marshaller** converts between XML fragments and Java objects.

Testing XML readers and writers requires verifying more than just the Job finishing with COMPLETED. The reader must locate the right fragments, map data types properly, and handle namespaces and malformed data as expected. The writer must generate well-formed XML, emit the proper root element, marshal fields accurately, close the document, and restore appropriate state on restart.

A sound testing strategy divides into three layers:

1. **Reader/writer unit tests:** verify fragment reading and writing in isolation using small files or resources.
2. **Restart and failure tests:** verify ExecutionContext, XML errors, marshalling errors, and resource closing.
3. **Step integration tests:** run a real Step to verify reader, processor, writer, transactions, listeners, and JobRepository work together properly.

This lesson uses Spring Batch 5 with Java configuration as examples. Some builders or test APIs may vary across Spring Batch versions; use your project's dependency version when implementing.

## 1. XML reader and writer architecture

An XML batch pipeline typically has this structure:

~~~xml
<trades>
    <trade>
        <isin>US0000000001</isin>
        <quantity>10</quantity>
        <price>125.50</price>
    </trade>
    <trade>
        <isin>US0000000002</isin>
        <quantity>20</quantity>
        <price>98.75</price>
    </trade>
</trades>
~~~

The reader does not have to deserialize the whole document into one giant object. StaxEventItemReader locates configured fragment elements, such as each trade element, and converts each fragment into a Java object.

The writer works in reverse: it receives each object or chunk of objects, marshals them into XML fragments, and writes them into a file inside the root element managed by the writer.

~~~mermaid
flowchart LR
    A["XML input"] --> B["StaxEventItemReader"]
    B --> C["Unmarshaller"]
    C --> D["Java item"]
    D --> E["Processor"]
    E --> F["Java output item"]
    F --> G["Marshaller"]
    G --> H["StaxEventItemWriter"]
    H --> I["XML output"]
~~~

Key components:

| Component | Responsibility |
|---|---|
| StaxEventItemReader | Reads XML streams and extracts fragments |
| Unmarshaller | Converts XML fragments into Java objects |
| ItemProcessor | Validates or transforms objects |
| Marshaller | Converts Java objects into XML fragments |
| StaxEventItemWriter | Writes fragments and manages document/root |
| ExecutionContext | Stores reader/writer state for restarts |

An XML error can occur during parsing, unmarshalling, processing, or marshalling. Tests must distinguish the error location clearly to verify the responsible component.

## 3. Creating a JAXB model for testing

Example trade item:

~~~java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

import java.math.BigDecimal;

@XmlRootElement(name = "trade")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {

    @XmlElement(required = true)
    private String isin;

    @XmlElement
    private int quantity;

    @XmlElement
    private BigDecimal price;

    public Trade() {
    }

    public Trade(String isin, int quantity, BigDecimal price) {
        this.isin = isin;
        this.quantity = quantity;
        this.price = price;
    }

    public String getIsin() {
        return isin;
    }

    public int getQuantity() {
        return quantity;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
~~~

Requirements for JAXB:

- The class usually needs a no-arg constructor.
- Annotations specify the root element and field mappings.
- Data types must support marshalling/unmarshalling.
- Element names must match the XML input/output contract.
- With namespaces, declare matching namespaces in annotations or package metadata.

Do not test objects solely via equals unless the model overrides equals/hashCode. Assert individual fields or use an assertion library that compares properties.

## 4. Configuring Jaxb2Marshaller

Spring OXM provides Jaxb2Marshaller to share between reader and writer:

~~~java
@Bean
Jaxb2Marshaller tradeMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    return marshaller;
}
~~~

In pure Java tests without a Spring context, instantiate the marshaller and call afterPropertiesSet() before using it:

~~~java
Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
marshaller.setClassesToBeBound(Trade.class);
marshaller.afterPropertiesSet();
~~~

Jaxb2Marshaller implements both Marshaller and Unmarshaller interfaces, so the same configuration can handle both reading and writing.

For larger models, configure context paths or bound classes. Ensure JAXB classes are discovered in the context. Missing class or annotation errors usually surface during marshaller initialization or during marshalling/unmarshalling.

## 5. Configuring StaxEventItemReader

Example reader reading each trade fragment:

~~~java
@Bean
@StepScope
StaxEventItemReader<Trade> tradeReader(
        Jaxb2Marshaller tradeMarshaller,
        @Value("#{jobParameters['input.file']}") String inputFile) {

    return new StaxEventItemReaderBuilder<Trade>()
        .name("tradeReader")
        .resource(new FileSystemResource(inputFile))
        .addFragmentRootElements("trade")
        .unmarshaller(tradeMarshaller)
        .saveState(true)
        .build();
}
~~~

Meaning:

- name is a stable identifier used for state in ExecutionContext.
- resource is the input XML file.
- addFragmentRootElements specifies the element representing one item.
- unmarshaller converts the XML fragment into a Trade.
- saveState enables saving state to support restarts.

If the XML contains many trade elements inside a trades root, the reader returns each Trade separately. It does not have to deserialize the whole list into a single object.

### Why do readers commonly use StepScope?

The input.file path is usually a JobParameter. @StepScope defers instantiating the target reader until a StepExecution exists, letting SpEL resolve the current run's parameters.

With partitioning, each worker can receive a different file or range from StepExecutionContext. Then the reader also needs StepScope to pick up worker-specific values.

## 6. Testing the reader independently with ByteArrayResource

Unit-testing the reader does not require launching an entire Job. You can supply small XML snippets using ByteArrayResource:

~~~java
@Test
void readsTradeFragments() throws Exception {
    String xml = """
        <trades>
            <trade>
                <isin>US0000000001</isin>
                <quantity>10</quantity>
                <price>125.50</price>
            </trade>
            <trade>
                <isin>US0000000002</isin>
                <quantity>20</quantity>
                <price>98.75</price>
            </trade>
        </trades>
        """;

    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.afterPropertiesSet();

    StaxEventItemReader<Trade> reader =
        new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReaderTest")
            .resource(new ByteArrayResource(
                xml.getBytes(StandardCharsets.UTF_8)
            ))
            .addFragmentRootElements("trade")
            .unmarshaller(marshaller)
            .build();

    reader.open(new ExecutionContext());
    try {
        Trade first = reader.read();
        Trade second = reader.read();
        Trade end = reader.read();

        assertEquals("US0000000001", first.getIsin());
        assertEquals(10, first.getQuantity());
        assertEquals(new BigDecimal("125.50"), first.getPrice());

        assertEquals("US0000000002", second.getIsin());
        assertEquals(20, second.getQuantity());
        assertEquals(new BigDecimal("98.75"), second.getPrice());

        assertNull(end);
    } finally {
        reader.close();
    }
}
~~~

The test verifies:

- The reader opens the XML resource.
- Each trade fragment produces exactly one object.
- Fields unmarshal into the expected types.
- Once fragments end, read() returns null.
- The reader closes even if assertions or reads throw exceptions.

Use BigDecimal in assertions to avoid floating-point rounding inaccuracies. XML decimal 125.50 should be checked with a matching BigDecimal.

## 7. Testing the reader with temporary files

ByteArrayResource works well for short XML. For larger files or when testing encoding, use JUnit @TempDir:

~~~java
@TempDir
Path tempDirectory;

@Test
void readsXmlFromTemporaryFile() throws Exception {
    Path input = tempDirectory.resolve("trades.xml");

    Files.writeString(
        input,
        """
        <trades>
            <trade>
                <isin>US0000000003</isin>
                <quantity>5</quantity>
                <price>12.25</price>
            </trade>
        </trades>
        """,
        StandardCharsets.UTF_8
    );

    // Create marshaller and reader with FileSystemResource(input).
    // Open reader, read item, verify fields, and close reader.
}
~~~

Temporary files test behavior against real Resources and make it easy to confirm files are closed. JUnit cleans up temporary directories automatically after tests finish.

If a test needs to verify file locks or deletion after close on the operating system, use FileSystemResource rather than ByteArrayResource.

## 8. Testing the reader with namespaces

Real-world XML often uses namespaces:

~~~xml
<trades xmlns="urn:example:trades">
    <trade>
        <isin>US0000000004</isin>
        <quantity>8</quantity>
        <price>50.00</price>
    </trade>
</trades>
~~~

Namespaced element names may not match plain local names. Mapping behavior depends on StAX fragment selection and JAXB metadata.

With JAXB, the model can declare a namespace:

~~~java
@XmlRootElement(
    name = "trade",
    namespace = "urn:example:trades"
)
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {
    // Corresponding fields and annotations.
}
~~~

When testing namespaces:

- Use sample XML with the exact real-world namespace URI and prefixes.
- Verify the fragment root is located.
- Verify JAXB maps child elements accurately.
- Do not assert only prefix names, because prefixes can change while the namespace URI stays identical.
- Test both default-namespaced XML and explicitly prefixed XML if the system accepts both.

Example:

~~~xml
<t:trades xmlns:t="urn:example:trades">
    <t:trade>
        <t:isin>US0000000004</t:isin>
        <t:quantity>8</t:quantity>
        <t:price>50.00</t:price>
    </t:trade>
</t:trades>
~~~

A good namespace test asserts business values after unmarshalling, not merely that the reader returned an item.

## 9. Testing the reader with invalid XML

XML errors can occur at multiple levels:

- Non-well-formed document, such as an unclosed opening tag.
- Fragment element with invalid structure.
- Missing required field.
- Value unconvertible to Java types.
- Wrong namespace.
- Data violating XSD or validation rules.
- Non-existent or unreadable resource.

Syntax error XML example:

~~~xml
<trades>
    <trade>
        <isin>US0000000005</isin>
        <quantity>10</quantity>
    </trade>
~~~

Tests should verify the failure surfaces at the right stage:

1. Create the reader with the broken XML resource.
2. Call open().
3. Call read() so the parser consumes fragments.
4. Assert the expected exception is thrown per your version's contract.
5. Inspect the cause chain to confirm a parse or unmarshal failure.
6. Close the reader in finally.

Do not always assert that open() must fail. Some errors are discovered only when the parser reaches the broken element.

### Avoid asserting overly fragile error messages

Parser messages vary by JDK, JAXB provider, or Spring version. Prefer asserting exception types at application boundaries and meaningful root causes instead of exact full-message string comparisons.

If the application translates XML exceptions into custom business exceptions, test that translator and verify the Step classifies errors properly.

## 10. Testing empty XML and XML with no fragments

The following inputs carry different meanings:

~~~xml
<trades/>
~~~

Empty document in terms of items, yet still valid XML.

~~~xml
<orders>
    <order>...</order>
</orders>
~~~

Valid document, yet lacks the trade fragments the reader looks for.

~~~text
(empty file)
~~~

Resource has zero XML content.

Decide based on the contract:

- Is an empty XML root a valid batch with 0 items?
- Is missing fragments a structural data error?
- Is a 0-byte file an error or an acceptable empty source?
- Is a validation Step needed before running the reader?

Test each case separately. Do not lump them into a single generic assertion that the reader returns null, because valid empty XML and broken XML files behave differently.

## 11. Testing reader restart with ExecutionContext

A restartable reader must save state in ExecutionContext. Direct lifecycle tests can confirm previously read items are not reread after reopening the reader.

Example:

~~~java
@Test
void resumesFromSavedExecutionContext() throws Exception {
    ExecutionContext context = new ExecutionContext();

    StaxEventItemReader<Trade> firstReader = createTradeReader();
    firstReader.open(context);

    Trade first = firstReader.read();
    assertEquals("US0000000001", first.getIsin());

    firstReader.update(context);
    firstReader.close();

    StaxEventItemReader<Trade> restartedReader = createTradeReader();
    restartedReader.open(context);
    try {
        Trade next = restartedReader.read();
        assertEquals("US0000000002", next.getIsin());
    } finally {
        restartedReader.close();
    }
}
~~~

In real tests, createTradeReader() must construct a new reader with the same name, resource, and fragment configuration. ExecutionContext is reused to simulate a checkpoint.

Verify:

- The reader has a stable name.
- saveState is enabled.
- update() is invoked at the expected checkpoint.
- Context is saved before the reader closes.
- The new reader uses the same source and compatible configuration.
- The next item matches the expected position.

This is a reader-level lifecycle test. Full-Job restart tests still require JobRepository and JobLauncherTestUtils to verify checkpoints are persisted and restored by Spring Batch in real executions.

## 12. Configuring StaxEventItemWriter

The writer writes Java objects as XML fragments inside a root element:

~~~java
@Bean
@StepScope
StaxEventItemWriter<Trade> tradeWriter(
        Jaxb2Marshaller tradeMarshaller,
        @Value("#{jobParameters['output.file']}") String outputFile) {

    return new StaxEventItemWriterBuilder<Trade>()
        .name("tradeWriter")
        .resource(new FileSystemResource(outputFile))
        .marshaller(tradeMarshaller)
        .rootTagName("trades")
        .overwriteOutput(true)
        .saveState(true)
        .build();
}
~~~

Key parts:

- name sets a stable name for writer state.
- resource specifies the output XML file.
- marshaller converts Trade objects into fragments.
- rootTagName specifies the root element wrapping fragments.
- overwriteOutput controls behavior when the file already exists per writer settings.
- saveState enables saving state for restarts.

If output files are used for restarts, do not configure overwrite or append arbitrarily. File policy must align with JobInstance and checkpoints.

## 13. Testing the writer independently

You can test the writer with a temporary file and inspect the XML after closing:

~~~java
@TempDir
Path tempDirectory;

@Test
void writesTradeFragmentsInsideRootElement() throws Exception {
    Path output = tempDirectory.resolve("trades.xml");

    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.afterPropertiesSet();

    StaxEventItemWriter<Trade> writer =
        new StaxEventItemWriterBuilder<Trade>()
            .name("tradeWriterTest")
            .resource(new FileSystemResource(output))
            .marshaller(marshaller)
            .rootTagName("trades")
            .overwriteOutput(true)
            .build();

    writer.open(new ExecutionContext());
    try {
        Chunk<Trade> chunk = new Chunk<>();
        chunk.add(new Trade(
            "US0000000001", 10, new BigDecimal("125.50")
        ));
        chunk.add(new Trade(
            "US0000000002", 20, new BigDecimal("98.75")
        ));

        writer.write(chunk);
    } finally {
        writer.close();
    }

    assertTrue(Files.exists(output));
    assertTrue(Files.size(output) > 0);
}
~~~

The snippet above verifies the file is created and the writer closes. Merely checking file existence or size > 0 is insufficient; re-parse the XML and verify fragments and fields.

In production tests, if write() throws an exception and close() can also throw, preserve the original error and record the close error. Use cleanup helpers or try-with-resources wrappers compatible with the ItemStream API.

## 14. Testing the writer via a round-trip reader

A useful way to test the writer is reading back its output file with StaxEventItemReader.

Workflow:

1. Create several Trade objects.
2. Write them using StaxEventItemWriter.
3. Close the writer to finalize the root document.
4. Create a StaxEventItemReader pointing at the output file.
5. Read back each fragment.
6. Compare field values against the original objects.
7. Assert the reader returns null after the last fragment.

Read-back portion example:

~~~java
StaxEventItemReader<Trade> verificationReader =
    new StaxEventItemReaderBuilder<Trade>()
        .name("verificationReader")
        .resource(new FileSystemResource(output))
        .addFragmentRootElements("trade")
        .unmarshaller(marshaller)
        .build();

verificationReader.open(new ExecutionContext());
try {
    Trade first = verificationReader.read();
    Trade second = verificationReader.read();

    assertEquals("US0000000001", first.getIsin());
    assertEquals(new BigDecimal("125.50"), first.getPrice());

    assertEquals("US0000000002", second.getIsin());
    assertEquals(new BigDecimal("98.75"), second.getPrice());

    assertNull(verificationReader.read());
} finally {
    verificationReader.close();
}
~~~

Round-trip testing verifies both marshalling and parsing. However, if the same JAXB setup has a symmetric mapping bug, reader and writer may misinterpret it in the exact same way. For critical contracts, add XML structural assertions or independent partner-provided test fixtures.

## 15. Independent XML well-formedness verification

Beyond round-tripping with the same Spring Batch reader, use a standard XML parser to verify output is a valid document.

Example using DocumentBuilder:

~~~java
DocumentBuilderFactory factory =
    DocumentBuilderFactory.newInstance();

factory.setNamespaceAware(true);

DocumentBuilder builder = factory.newDocumentBuilder();
Document document = builder.parse(output.toFile());

assertEquals(
    "trades",
    document.getDocumentElement().getLocalName() == null
        ? document.getDocumentElement().getNodeName()
        : document.getDocumentElement().getLocalName()
);
~~~

This test verifies the document parses and has the right root element. You can go further by counting trade elements and checking namespace URIs.

For untrusted XML, configure both test and production parsers to disable external entities/DTDs per security requirements. Never enable external entities just to test a simple fixture file.

## 16. Testing the writer with XML namespaces

If output requires namespaces, the JAXB model or package metadata must declare matching namespaces. Tests should parse the XML and check namespace URIs.

Desired example:

~~~xml
<t:trades xmlns:t="urn:example:trades">
    <t:trade>
        <t:isin>US0000000006</t:isin>
        <t:quantity>3</t:quantity>
        <t:price>15.00</t:price>
    </t:trade>
</t:trades>
~~~

Do not assert prefix t if prefixes are not part of the contract. Prefixes like t, ns2, or default namespaces can change while the namespace URI remains identical.

Check:

- Root namespace URI.
- Fragment namespace URI.
- Local element names.
- Fragment count.
- Field values.
- Element ordering if required by contract.

## 17. Testing XSD validation

If XML must conform to an XSD schema, test both valid and invalid documents.

You can configure Jaxb2Marshaller with classpath-managed schemas, depending on your Spring OXM version's API:

~~~java
@Bean
Jaxb2Marshaller tradeMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.setSchemas(
        new ClassPathResource("xsd/trades.xsd")
    );
    return marshaller;
}
~~~

An XSD can enforce:

- Required elements.
- Numeric types and value bounds.
- Element ordering.
- Namespaces.
- Cardinality.
- Patterns or enumerations.

Tests should include valid XML fixtures and schema-violating fixtures. Verify errors are caught at the unmarshalling/validation stage per configuration.

Note: validation provided by the JAXB marshaller depends on how fragments are marshalled/unmarshalled and how the schema is configured. If the contract requires validating the entire document, a separate validation Step using a JAXP Validator on the completed file may be necessary.

## 18. Testing unmappable data

Some XML is well-formed yet contains values unconvertible to Java types:

~~~xml
<trade>
    <isin>US0000000007</isin>
    <quantity>ten</quantity>
    <price>20.00</price>
</trade>
~~~

The quantity element exists but cannot convert to an integer. This is a mapping/unmarshal error, distinct from an XML syntax error.

Tests should verify:

- The reader throws an appropriate exception.
- The cause chain points to a type conversion error.
- The Step applies skip/retry/fail policies aligned with business rules.
- No partial object is treated as valid.
- Listeners record errors at the right stage if the Step uses skip.

Do not skip all unmarshal errors by default. Isolated errors may be individual bad records, whereas widespread schema or namespace mismatches indicate an invalid input file contract and should fail early.

## 19. Testing truncated XML files

A file can be truncated due to an incomplete upload or a terminated producer process:

~~~xml
<trades>
    <trade>
        <isin>US0000000008</isin>
        <quantity>2</quantity>
        <price>30.00</price>
    </trade>
    <trade>
        <isin>US0000000009</isin>
~~~

The parser can read the first fragment and then fail when reading the rest or detecting an unclosed document. This means the reader may have already emitted some items before the document failed.

Tests should verify:

- Valid items before the failure point may have been read.
- End-of-file parse errors terminate the Step per policy.
- Writers or databases do not publish incomplete data outside policy.
- Resources are closed when the Step finishes.
- Restarts do not assume the source file is complete if the source might change.

For exchanged files, check size, checksum, or upload-completion markers before launching the Job. Never read files actively being written by producers.

## 20. Testing XML readers with StepScope

If a reader uses JobParameters, testing the target reader directly outside StepScope fails to simulate the true lifecycle. Use Spring Batch test utilities to activate the scope.

One approach is running the Step with JobLauncherTestUtils and JobParameters containing input.file. Alternatively, for focused tests on a scoped bean, use StepScopeTestUtils or configure a StepExecution in the test context per your spring-batch-test version.

Conceptual example:

~~~java
StepExecution stepExecution = MetaDataInstanceFactory.createStepExecution(
    new JobParametersBuilder()
        .addString("input.file", inputPath.toString())
        .toJobParameters()
);

Trade first = StepScopeTestUtils.doInStepScope(
    stepExecution,
    () -> tradeReader.read()
);
~~~

This illustrates activating StepScope. In real tests, open the reader inside the same scope, call read, and close via try/finally; do not call read on an unopened proxy.

When testing a full Step, JobLauncherTestUtils usually matches production behavior better because Spring Batch handles open/update/close automatically.

## 21. Testing a complete Step with spring-batch-test

When verifying reader, processor, writer, and JobRepository work together properly, use spring-batch-test.

Test example:

~~~java
@SpringBatchTest
@SpringJUnitConfig(BatchTestConfiguration.class)
class XmlImportStepTest {

    @Autowired
    private JobLauncherTestUtils jobLauncherTestUtils;

    @Test
    void importsXmlFile() throws Exception {
        JobParameters parameters = new JobParametersBuilder()
            .addString("input.file", "src/test/resources/trades.xml")
            .addString("output.file", "build/test-output/trades-out.xml")
            .toJobParameters();

        JobExecution execution =
            jobLauncherTestUtils.launchStep(
                "importXmlStep",
                parameters
            );

        assertEquals(BatchStatus.COMPLETED, execution.getStatus());

        StepExecution stepExecution =
            execution.getStepExecutions().iterator().next();

        assertEquals(2, stepExecution.getReadCount());
        assertEquals(2, stepExecution.getWriteCount());
        assertEquals(0, stepExecution.getReadSkipCount());
    }
}
~~~

The test configuration must provide the Job/Step used by JobLauncherTestUtils. In projects with multiple Jobs, bind the right Job to the test utility using the supported configuration style.

### What is being verified here?

- JobParameters are passed into the Step.
- StepScope is activated.
- The reader opens XML input.
- The processor runs on each item.
- The writer writes XML output.
- ExecutionContext and StepExecution are updated.
- JobRepository persists metadata.
- The Step closes resources on completion.

After the Step runs, still read the output file and verify XML content is right. BatchStatus COMPLETED proves only flow status completion, not accurate XML mapping.

## 22. Testing reader and writer with a processor

The processor can transform data before writing:

~~~java
@Bean
ItemProcessor<Trade, Trade> normalizeTradeProcessor() {
    return trade -> new Trade(
        trade.getIsin().trim(),
        trade.getQuantity(),
        trade.getPrice().setScale(2, RoundingMode.HALF_UP)
    );
}
~~~

Step tests should feed inputs with whitespace or varying scales and verify normalized output.

Separate tests:

- Reader tests verify input objects.
- Processor tests verify transformation rules.
- Writer tests verify serialized objects.
- Step tests verify pipeline assembly order.

This separation keeps mapping bugs from being confused with processor or writer bugs.

## 23. Testing writer errors and transactions

A writer can fail because of:

- Unwritable output path permissions.
- Missing directory.
- Full disk.
- Marshaller not supporting an object type.
- XML encoding or resource I/O error.
- Resource already closed or misused in lifecycle.

Tests can use an unwritable resource or a mock writer throwing an exception to verify the Step fails.

Distinguish:

- Exceptions during marshalling before writing fragments.
- IOExceptions while writing the file.
- Exceptions during close while finalizing the document.
- Database errors in another writer if the Step uses a composite writer.

If a Step combines a database writer and a file writer, database transactions do not automatically roll back flushed file writes. For consistent published XML outputs, write to a staging file and publish only after the Step succeeds.

## 24. Testing close and resource lifecycles

XML readers/writers hold resources that must be closed. Tests should verify:

- Reader closes after Step completion.
- Reader closes after processor exceptions.
- Writer closes after write exceptions.
- StAX reader/writer release underlying streams.
- Close errors are logged without masking the primary exception.
- Temp files do not hold open handles after the Step finishes.

In standalone tests, use try/finally to invoke close. In real Step tests, let Spring Batch manage the lifecycle and inspect files/resources after the Step ends.

Do not call close from multiple places when the framework already manages the component. If a custom composite holds multiple ItemStream delegates, register delegates or forward open/update/close properly.

## 25. Testing full-Step restarts

To test realistic restarts:

1. Use XML input with multiple fragments.
2. Configure a small commit interval to span multiple chunks.
3. Fail the Step after one chunk has committed.
4. Verify the first StepExecution is FAILED and ExecutionContext holds checkpoints.
5. Restart the same JobInstance with the original identifying JobParameters.
6. Verify the reader resumes from the right position.
7. Verify the writer resumes output per restart policy.
8. Verify no items are missed or duplicated.

For XML readers, restarts require the same source and compatible structure. If the input file changes between the initial run and restart, checkpoints may point to positions that no longer match the old content.

Store or verify input checksums/versions when sources could be replaced. For output files, writer names and resources must remain stable within the same JobInstance so the framework restores state properly.

## 26. Testing skip and retry for XML

Not every XML error should be skipped or retried.

| Error | Retry | Skip | Common handling |
|---|---|---|---|
| File not ready or upload incomplete | May retry before opening Step | No | Wait for source completion |
| Malformed XML syntax | Usually no | Usually no for the whole file | Reject file and alert source |
| Single fragment violates business rule | Not necessarily | Possibly | Skip item if contract allows |
| Enrichment service timeout | Possibly | Possibly after retries if business allows | Bounded retry |
| Output disk full | Usually no immediate item retry | No | Fail Step and resolve infrastructure |
| File-wide wrong JAXB mapping/schema | No | Usually no | Fail fast, fix contract |

StaxEventItemReader may hit parse errors at the document level rather than the item level. If XML is not well-formed, never assume the framework can skip just the bad fragment and safely proceed.

For invalid business data in valid XML, the processor can throw a custom exception so the Step applies a skip policy. Tests should assert processSkipCount increments while valid items still get written.

## 27. Testing XML against partner schemas and contracts

XML can be well-formed yet still violate a contract. Examples:

- Wrong namespace URI.
- Missing required element.
- Wrong element ordering.
- Value outside enumeration.
- Decimal with invalid scale.
- Date/time missing required format.
- Extra disallowed elements.
- Wrong document root version.

Build contract-driven fixtures:

- Minimal valid file.
- Full valid file.
- File with a different namespace prefix but identical URI.
- File missing a required element.
- File with invalid data types.
- File with wrong namespace.
- Truncated file.
- Empty file per business definition.

Fixture names should describe the scenario for readability, e.g., trades-valid.xml, trades-missing-price.xml, or trades-wrong-namespace.xml.

Do not reuse a single fixture file across every test, because model changes can blur which error each test actually verifies.

## 28. Testing XML performance and size

StaxEventItemReader uses StAX to read as a stream, fitting large files far better than full-document deserialization. Still, small tests do not prove large-file behavior.

Performance tests can measure:

- Read time relative to fragment count.
- Heap usage as file size scales.
- Object graph size of one fragment.
- Marshal time per chunk.
- Output write throughput.
- Impact of namespaces and validation.
- Restart duration from checkpoints.

You do not need giant files in every unit test. Keep small fixtures for logic and a dedicated performance/integration test running representative volumes.

If a single fragment holds a huge child list, streaming the document does not mean that fragment object is small. Cap fragment sizes and design models accordingly.

## 29. Testing XML security

XML parsers must be configured securely for untrusted sources. External entities or DTDs can lead to unintended external resource access if enabled on the parser.

Principles:

- Do not enable external general entities unless needed.
- Do not permit arbitrary external DTDs.
- Restrict schema fetches from untrusted URLs.
- Use locally controlled schemas for validation.
- Enforce appropriate input size and depth/nesting limits.
- Avoid logging full XML containing sensitive data.
- Test XML with DOCTYPE or external entities and verify rejection per policy.

StAX factory or parser configuration depends on how XMLInputFactory is created and your Spring Batch version. If a custom factory is needed, verify builder/APIs in your version and run real tests rather than assuming default parsers carry identical security flags across runtimes.

## 30. Test helpers for building readers and writers

To avoid repeating configuration, extract factory helpers in tests:

~~~java
private Jaxb2Marshaller createMarshaller() throws Exception {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.afterPropertiesSet();
    return marshaller;
}

private StaxEventItemReader<Trade> createReader(Resource resource)
        throws Exception {
    return new StaxEventItemReaderBuilder<Trade>()
        .name("tradeReaderTest")
        .resource(resource)
        .addFragmentRootElements("trade")
        .unmarshaller(createMarshaller())
        .saveState(true)
        .build();
}

private StaxEventItemWriter<Trade> createWriter(Path output)
        throws Exception {
    return new StaxEventItemWriterBuilder<Trade>()
        .name("tradeWriterTest")
        .resource(new FileSystemResource(output))
        .marshaller(createMarshaller())
        .rootTagName("trades")
        .overwriteOutput(true)
        .saveState(true)
        .build();
}
~~~

Helpers should hold only repetitive setup. Each test should still state its fixture, action, and assertions explicitly so test intent stays visible.

Having helpers instantiate fresh marshallers each time keeps tests independent and avoids shared mutable state. When reusing a singleton marshaller, confirm the provider implementation is thread-safe for your usage pattern.

## 31. Recommended test matrix

A test suite can be organized using this matrix:

| Group | Case | Primary assertion |
|---|---|---|
| Basic reader | Multiple fragments | Item count and fields match |
| Empty reader | Root with no fragments | Result aligns with empty-input policy |
| Reader parse | Malformed XML | Parse exception recognized |
| Reader mapping | Wrong data type | Unmarshal failure |
| Reader namespace | Prefixed/default namespace | Namespace URI and fields match |
| Reader restart | Save and restore context | Resumes at exact next fragment |
| Basic writer | Write multiple objects | Root and fragments match |
| Writer round-trip | Write then reread | Fields remain intact |
| Writer encoding | UTF-8 and Unicode chars | Content has zero encoding corruption |
| Writer failure | Marshal/I/O exception | Step fails and resource closes |
| Step integration | Reader-processor-writer | BatchStatus and counters accurate |
| Step restart | Fail after committed chunk | No lost or duplicate items |
| Schema | Valid/invalid XML | Validation matches contract |
| Security | DTD/external entities | Parser security policy enforced |

Not every row needs its own test class. Group by component and share fixtures when they represent the same contract.

## 32. Common testing mistakes

### Checking only Job COMPLETED

A Job can complete while XML mappings are wrong or outputs omit fields. Reread the file and inspect contents.

### Using overly tiny XML fixtures

A single fragment fails to test multiple items, EOF, restarts, or namespaces. Add fixtures with multiple fragments and error cases.

### Failing to close reader/writer in unit tests

Resources can stay locked and disrupt later tests. Use try/finally or lifecycle helpers.

### Asserting byte-for-byte XML strings

Marshallers can vary whitespace, attribute order, or namespace prefixes while producing equivalent XML. Parse the XML and assert structure/values, unless byte-exact output is contracted.

### Using only the same reader to verify the writer

Round-tripping helps but does not replace independent XML structure checks. Reader and writer could share the same mapping bug.

### Ignoring namespaces

Testing only non-namespaced XML misses common partner integration bugs.

### Skipping restart state tests

A reader may work from the start yet fail when restoring ExecutionContext. Write dedicated checkpoint tests.

### Modifying input between restarts

Checkpoints are meaningful only while the source remains stable. Verify checksums/versions or keep files immutable.

### Skipping all XML exceptions

Document-level errors like malformed XML usually cannot be handled by dropping one item. Separate business fragment errors from whole-document structural errors.

### Asserting only file existence

A file may be empty, missing its closing root tag, or contain zero fragments. Parse outputs and verify records.

### Using insecure test parsers

Test parsers might resolve external entities or access unintended files/URLs. Use hardened XML configurations and controlled fixtures.

## 33. Workflow for building an XML test suite

When testing an XML pipeline in Spring Batch, follow this sequence:

1. **Define the XML contract:** root, fragments, namespaces, fields, schema, and encoding.
2. **Create JAXB models:** declare root elements, fields, and data types.
3. **Configure marshaller:** share compatible mappings for reader and writer.
4. **Unit-test reader:** multiple fragments, empty inputs, malformed XML, namespaces, and mappings.
5. **Test reader restart:** persist ExecutionContext and open a new reader to continue.
6. **Unit-test writer:** write chunks, close writer, and parse outputs.
7. **Test round-trip:** write objects and read them back to verify fields.
8. **Test schema/security:** valid data, schema violations, DTDs, and external entities.
9. **Integration-test Step:** run reader, processor, and writer with JobLauncherTestUtils.
10. **Test failure/restart:** verify resource closing, checkpoints, and zero duplicates.
11. **Inspect final output:** parse XML, count fragments, verify root and contents.
12. **Isolate performance tests:** use representative files when evaluating memory and speed.

## 34. Key points to remember

- StaxEventItemReader reads XML fragments; StaxEventItemWriter writes objects as fragments inside a root document.
- Jaxb2Marshaller can serve as both Marshaller and Unmarshaller.
- Readers must configure a fragment root element matching the XML input.
- Writers need rootTagName, resource, and marshaller matching the contract.
- Unit-testing readers with ByteArrayResource or temp files verifies mappings independently.
- Writer unit tests must close the writer and parse outputs; checking file existence alone is insufficient.
- Reader/writer round-trips are useful but need complementary independent XML structure checks.
- Test namespaces by URI, independent of prefixes.
- Separately test malformed XML, wrong fragment types, empty documents, and truncated files.
- saveState, stable writer names, and ExecutionContext must be verified in restart tests.
- spring-batch-test and JobLauncherTestUtils run real Steps with JobParameters and check StepExecution counters.
- Job COMPLETED does not prove XML output accuracy; parse and verify records.
- Do not skip all XML errors; distinguish single-record data errors from whole-document structural errors.
- Test XML security, external entities, schemas, and input limits.
- Use scenario-descriptive fixtures and keep tests component-isolated.

Effective testing of XML readers and writers covers mapping, document structure, resource lifecycles, and restartability. By verifying readers and writers individually and confirming behavior with Step integration tests, you pinpoint bugs at the right layer and ensure output XML satisfies downstream contracts.
