# Fragment root and item boundary

In Spring Batch, when reading a large XML document, one item usually does not correspond to one line of text. An item is a complete XML element, including its opening tag, child elements, content, and closing tag. `StaxEventItemReader` uses StAX to read the XML event stream and split the document into fragments based on the element configured as the **fragment root**.

For example, a document has a root element `<trades>` enclosing many `<trade>` elements. The `<trades>` element is the document root; each `<trade>` element is the boundary of one item. The reader extracts each `<trade>` fragment, passes it to the `Unmarshaller`, and returns a `Trade` object to the chunk pipeline.

Choosing the right fragment root determines how the reader divides the document into items. If you choose the document root, the reader may bundle the entire document into one item. If you choose a child element that is too deep, the reader may create items that do not match the business unit. Therefore, clearly identify which XML element corresponds to a business item before configuring the reader.

## 1. Document root and fragment root

A well-formed XML document has one top-level document element. Inside the document element, there may be many repeating child elements.

Example `trades.xml` file:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<trades>
    <trade>
        <isin>US0378331005</isin>
        <quantity>100</quantity>
        <price>182.50</price>
    </trade>
    <trade>
        <isin>US5949181045</isin>
        <quantity>50</quantity>
        <price>420.00</price>
    </trade>
    <trade>
        <isin>US02079K3059</isin>
        <quantity>25</quantity>
        <price>510.25</price>
    </trade>
</trades>
```

In this structure:

- `<trades>` is the document root: the single element enclosing the entire XML content.
- Each `<trade>` is a fragment root: an element that can be mapped into an independent item.
- `<isin>`, `<quantity>`, and `<price>` are child elements belonging to the same `trade` item.

```text
Document
└── trades                         document root
    ├── trade                      item boundary 1
    │   ├── isin
    │   ├── quantity
    │   └── price
    ├── trade                      item boundary 2
    │   ├── isin
    │   ├── quantity
    │   └── price
    └── trade                      item boundary 3
        ├── isin
        ├── quantity
        └── price
```

A `StaxEventItemReader` configured with `trade` as the fragment root will return three `Trade` items. It does not return a `Trades` object representing the entire document.

## 2. What is an item boundary?

An item boundary is the demarcation defining which portion of XML counts as a separate item. With a StAX-based reader, the boundary is determined by the XML element registered as the fragment root, independent of line breaks, whitespace, or file formatting.

For example, the following two formats have the exact same fragment structure:

```xml
<trade><isin>US0378331005</isin><quantity>100</quantity></trade>
```

```xml
<trade>
    <isin>US0378331005</isin>
    <quantity>100</quantity>
</trade>
```

Each `<trade>` element is still one item. The reader operates on XML events such as start element, characters, and end element, not by counting lines in the file.

A fragment comprises the entire subtree starting from the fragment root's opening tag to its matching closing tag. Child elements inside the boundary belong to the same item, even when nested multiple levels deep.

## 3. Why must the fragment root be chosen carefully?

Suppose the XML has the following structure:

```xml
<orders>
    <order>
        <orderId>1001</orderId>
        <customer>
            <customerId>C001</customerId>
            <name>Lan</name>
        </customer>
        <lines>
            <line>
                <sku>A-01</sku>
                <quantity>2</quantity>
            </line>
            <line>
                <sku>B-05</sku>
                <quantity>1</quantity>
            </line>
        </lines>
    </order>
    <order>
        <orderId>1002</orderId>
        <customer>
            <customerId>C002</customerId>
            <name>Minh</name>
        </customer>
        <lines>
            <line>
                <sku>C-10</sku>
                <quantity>4</quantity>
            </line>
        </lines>
    </order>
</orders>
```

If one business item is a complete order, the fragment root must be `order`. Then the customer and all order lines belong to the same `Order` object.

If you choose `line` as the fragment root, the reader returns each product line as a separate item. The `orderId` and customer information lie outside the fragment, so the item lacks sufficient context to process the order independently.

If you choose `orders` as the fragment root, the entire batch of orders can be lumped into one giant fragment, preventing the reader from splitting by order.

Practical rule: choose the smallest element that still contains all the data needed to process a single business item. Do not pick a child element just because it repeats many times if parent fields contain required context.

## 4. StaxEventItemReader and StAX

`StaxEventItemReader<T>` is the XML item reader in Spring Batch. It uses StAX (Streaming API for XML) to read XML as an event stream, find the configured fragment root, and pass the fragment to the `Unmarshaller`.

Key components:

- `Resource`: the input XML document.
- `fragmentRootElementName` or list of fragment roots: element name(s) defining the item boundary.
- `Unmarshaller`: converts the XML fragment into a Java object.
- `name`: reader name used in metadata/checkpoints.
- `saveState`: enables or disables saving state for restarts.
- `strict`: determines whether the reader throws an error when the resource does not exist.

Conceptual processing flow:

```text
XML Resource
    |
    v
StAX event reader
    |
    v
Find configured fragment root
    |
    v
Collect subtree until matching end element
    |
    v
Unmarshaller
    |
    v
Java object (one item)
    |
    v
Processor -> Writer -> Commit chunk
```

StAX is a streaming parser, so it does not need to deserialize the entire document into one object graph before starting processing. Still, each fragment is converted into a Java object; if a single fragment contains millions of child elements, that item alone can still consume significant memory.

## 5. Configuring fragment root with StaxEventItemReaderBuilder

In Spring Batch 5, the builder provides `addFragmentRootElements(...)` to register one or more fragment roots:

```java
@Bean
StaxEventItemReader<Trade> tradeReader(
        Resource tradeResource,
        Unmarshaller tradeUnmarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(tradeResource)
            .addFragmentRootElements("trade")
            .unmarshaller(tradeUnmarshaller)
            .saveState(true)
            .build();
}
```

In the example, `trade` is the item boundary. Each `<trade>...</trade>` element is sent to `tradeUnmarshaller` and produces a `Trade` object.

In the lower-level reader API, the corresponding setting is usually expressed via `fragmentRootElementName`. The builder provides a fluent configuration style and avoids manually instantiating and initializing reader properties.

The fragment root name must match the actual XML structure. If the file contains `<tradeRecord>` while the reader registers `trade`, the reader will not find the expected boundary and may return no items.

## 6. Declaring the Java model for a fragment

A fragment can be mapped to a POJO using JAXB. Example `Trade` model:

```java
import java.math.BigDecimal;
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

@XmlRootElement(name = "trade")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {

    @XmlElement(name = "isin")
    private String isin;

    @XmlElement(name = "quantity")
    private Integer quantity;

    @XmlElement(name = "price")
    private BigDecimal price;

    public Trade() {
    }

    public String getIsin() {
        return isin;
    }

    public Integer getQuantity() {
        return quantity;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
```

`@XmlRootElement(name = "trade")` describes the root element of the fragment mapped by JAXB. `@XmlElement` describes child elements. JAXB requires a model matching the XML schema and the application's accessor/constructor strategy.

The Java class name does not have to match the fragment root name; what matters is that JAXB can map the root QName and data fields accurately.

## 7. Configuring Unmarshaller with Jaxb2Marshaller

Spring OXM provides `Jaxb2Marshaller`, implementing `org.springframework.oxm.Unmarshaller`, to convert XML fragments into objects:

```java
@Bean
Jaxb2Marshaller tradeUnmarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    return marshaller;
}

@Bean
StaxEventItemReader<Trade> tradeReader(
        @Value("classpath:trades.xml") Resource resource,
        Jaxb2Marshaller tradeUnmarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(resource)
            .addFragmentRootElements("trade")
            .unmarshaller(tradeUnmarshaller)
            .saveState(true)
            .build();
}
```

`Jaxb2Marshaller` needs to know which classes can be bound. You can use `setClassesToBeBound`, `setPackagesToScan`, or configure the JAXB context as appropriate for the application.

In real applications, `resource` is often passed via `JobParameters` and the reader is declared `@StepScope` so each JobExecution gets its own resource. Example:

```java
@Bean
@StepScope
StaxEventItemReader<Trade> tradeReader(
        @Value("#{jobParameters['input.file']}") String inputFile,
        Jaxb2Marshaller tradeUnmarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(new FileSystemResource(inputFile))
            .addFragmentRootElements("trade")
            .unmarshaller(tradeUnmarshaller)
            .saveState(true)
            .build();
}
```

The reader name must remain stable across restarts of the same Step so checkpoint metadata is found properly. Do not generate random reader names per execution.

## 8. Configuring XML namespaces

XML documents can use namespaces:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<trades xmlns="urn:example:trading">
    <trade>
        <isin>US0378331005</isin>
        <quantity>100</quantity>
        <price>182.50</price>
    </trade>
</trades>
```

In this XML, `trades` and `trade` belong to the namespace `urn:example:trading`. In XML terms, the full element name is a QName consisting of a namespace URI and a local name. Two elements with the same local name but different namespaces are not necessarily the same element under an XML contract.

When using namespaces, ensure the fragment root configuration and JAXB mapping match the document's QName. With JAXB, you can declare the namespace in annotations:

```java
@XmlRootElement(name = "trade", namespace = "urn:example:trading")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {
    // Fields and accessors
}
```

If the builder API only accepts a local element name in your configuration, check the namespace behavior of your Spring Batch version and use the API-supported QName configuration when you need to distinguish namespaces. Do not arbitrarily strip namespaces just so the reader recognizes fragments, as that can cause JAXB to map the wrong schema or confuse elements from different namespaces.

When testing namespaces, use real XML files or fixtures with the exact namespace URI, prefix, and schema version of the source.

## 9. Fragment roots with nested child elements

An item can contain multiple levels of elements:

```xml
<orders>
    <order>
        <orderId>1001</orderId>
        <customer>
            <id>C001</id>
            <address>
                <city>Ho Chi Minh City</city>
                <country>VN</country>
            </address>
        </customer>
        <items>
            <item>
                <sku>A-01</sku>
                <quantity>2</quantity>
            </item>
            <item>
                <sku>B-05</sku>
                <quantity>1</quantity>
            </item>
        </items>
    </order>
</orders>
```

If the fragment root is `order`, the entire customer, address, and list of child items are kept in the same fragment. JAXB can map them into an `Order` object graph containing `Customer`, `Address`, and `List<OrderLine>`.

```java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class Order {

    @XmlElement
    private Long orderId;

    @XmlElement
    private Customer customer;

    @XmlElementWrapper(name = "items")
    @XmlElement(name = "item")
    private List<OrderLine> items;
}
```

The fragment boundary does not automatically split the child `item` list into separate Batch items. If each order line must be processed independently, you can pick `item` as the fragment root, but then you must ensure each fragment contains or can look up the required order context. Another option is to read one `Order` and use a processor to split the lines into suitable output.

## 10. Multiple fragment root types

An XML file may contain multiple record types at the same level:

```xml
<portfolio>
    <stockTrade>
        <symbol>ABC</symbol>
        <quantity>100</quantity>
    </stockTrade>
    <cashMovement>
        <account>AC-01</account>
        <amount>5000</amount>
    </cashMovement>
    <stockTrade>
        <symbol>XYZ</symbol>
        <quantity>50</quantity>
    </stockTrade>
</portfolio>
```

You can register multiple fragment roots if all fragments can be mapped to a common target item type:

```java
return new StaxEventItemReaderBuilder<PortfolioEvent>()
        .name("portfolioEventReader")
        .resource(resource)
        .addFragmentRootElements("stockTrade", "cashMovement")
        .unmarshaller(portfolioEventUnmarshaller)
        .saveState(true)
        .build();
```

In the example, the unmarshaller must understand both root elements and produce a common `PortfolioEvent` type or compatible model. If the two fragments produce two unrelated Java types, you need a wrapper/adapter class or a different reader design to bring them to a uniform type that the chunk pipeline can process.

When multiple root elements share the same local name across different namespaces, handle QNames accurately. Do not rely solely on local names if the document combines multiple schemas.

## 11. Nested fragment roots and poorly chosen boundaries

If an element with the same name as the fragment root appears inside another fragment, clarify whether it is an independent item or just a child of the parent item.

Example:

```xml
<documents>
    <document>
        <id>D001</id>
        <attachment>
            <document>
                <id>ATT-01</id>
            </document>
        </attachment>
    </document>
</documents>
```

If both levels use the name `document`, the item boundary becomes ambiguous for the data design. Avoid reusing the same fragment root name for two different business concepts; rename the child element or use clear namespaces/structures. If you do not control the source schema, test carefully how the reader handles elements with duplicate QNames at nested levels.

Do not select fragment roots based only on generic names like `record`, `item`, or `data` if the same name appears in multiple places in the XML.

## 12. XML declaration, wrappers, and content outside fragments

An XML document may contain a declaration, processing instructions, comments, and wrapper elements. These components are not necessarily items.

Example:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!-- Export from upstream system -->
<export generatedAt="2026-11-15T09:00:00Z">
    <metadata>
        <schemaVersion>2</schemaVersion>
    </metadata>
    <records>
        <record><id>1</id></record>
        <record><id>2</id></record>
    </records>
</export>
```

If an item is a record, the fragment root is `record`. `export`, `metadata`, and `records` are wrappers/containers. The reader skips parts that are not fragments according to its configuration and returns only the registered fragments.

If you need the wrapper's `generatedAt` or `schemaVersion` attributes to validate the Job, `StaxEventItemReader` does not automatically turn them into fields on each `record`. You can use a separate validation step, a reader/Tasklet that reads metadata, or a mechanism that passes metadata into the Job/Step context.

## 13. Item boundaries do not depend on line boundaries

Unlike `FlatFileItemReader`, an XML reader does not treat newlines as item boundaries. A fragment may sit on a single line or span hundreds of lines.

```xml
<records><record><id>1</id><name>A</name></record><record><id>2</id><name>B</name></record></records>
```

There are still two items if the fragment root is `record`.

Conversely, a `record` element may contain text, comments, CDATA, attributes, and nested elements; all belong to the same fragment up to the matching end element.

Do not use `BufferedReader.readLine()` to split XML by opening/closing tags using strings. XML allows namespaces, attributes, comments, CDATA, entities, and whitespace; parsing via text matching breaks easily when the structure changes. Use a structure-aware XML parser such as StAX.

## 14. Fragment root and XML schema validation

Choosing the right fragment root only defines the item boundary; it does not automatically ensure every field in the fragment is valid against an XSD or business rules.

Multiple validation layers may be needed:

1. **Well-formed XML:** the parser verifies the document has valid XML structure, balanced opening/closing tags, and proper nesting.
2. **Schema validation:** verifies the fragment/document conforms to the XSD, data types, and cardinality.
3. **Unmarshalling:** converts the fragment into a Java object.
4. **Business validation:** checks rules such as positive quantity, existing customer ID, or valid business date.

`Jaxb2Marshaller` can be configured with a schema when the application requires XSD validation. Example:

```java
@Bean
Jaxb2Marshaller tradeUnmarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.setSchema(new ClassPathResource("xsd/trade.xsd"));
    return marshaller;
}
```

A schema can describe a standalone fragment root or the entire document depending on how it is defined. Verify that schema validation is applied at the right level. If the XSD requires the `<trades>` document wrapper while the unmarshaller receives only `<trade>` fragments, provide a fragment-compatible schema/validation or validate the full document in a separate step.

## 15. Handling invalid XML and unmarshalling errors

Types of errors that may occur:

- Non-well-formed XML, such as missing closing tags or improper nesting.
- Fragment root does not appear or name does not match.
- XML namespace does not match the model.
- Field value cannot be converted to the Java type.
- Schema validation failure.
- Invalid business rules after the object has been created.

Not every error can be skipped safely. If the XML is not well-formed in the middle of the document, the parser may lose the ability to determine the next fragment boundary; continuing to read can be unreliable. If an XML fragment is well-formed but a business value is invalid, you can check it in the processor and apply a skip policy if business rules permit.

Errors should be classified:

| Error | Usually appropriate handling |
|---|---|
| File does not exist | Fail fast or handle missing input via a dedicated workflow. |
| Non-well-formed XML | Usually fail file/Step; do not assume a single fragment can be skipped. |
| Wrong fragment root | Check schema/reader config; usually fail since expected item boundaries are absent. |
| Single field unmarshal error | Depends on recoverability and data contract; can fail or skip if the fragment was safely extracted. |
| Valid XML object violating business rules | Processor validation and skip/fail per policy. |

Do not configure broad skipping for all `Exception` types around the reader. That can mask parser errors and leave the resume position unreliable.

## 16. Restart and item boundaries

`StaxEventItemReader` supports saving state via `ItemStream` and `ExecutionContext`. When `saveState(true)` is enabled, the reader stores progress information so the Step can resume after a committed checkpoint.

Factors to keep stable across restarts:

- Reader name (`name`).
- XML resource and file content.
- Fragment root element name/QName.
- Unmarshaller and mapping schema.
- Order of fragments in the document.
- JobParameters identifying the exact business run.
- Reader configuration and item count calculation.

If the XML file is replaced or reordered after the Step fails, the checkpoint may point to a different logical position. A previously read item might be skipped, or another item read twice. Use immutable inputs, checksums, or staging copies per JobInstance.

Restartable reader example:

```java
return new StaxEventItemReaderBuilder<Trade>()
        .name("tradeReader")
        .resource(new FileSystemResource(inputFile))
        .addFragmentRootElements("trade")
        .unmarshaller(tradeUnmarshaller)
        .saveState(true)
        .build();
```

Do not generate random resource paths or reader names each time a Job restarts. If you need to change the schema or fragment root, treat it as an input contract change and define how old JobInstances should be handled.

## 17. Item boundaries and chunk boundaries are two different levels

The fragment root defines one item; chunk size defines how many items are grouped before committing a transaction.

Example where the reader creates one `Trade` per fragment and the Step uses a chunk size of 100:

```java
return new StepBuilder("importTradesStep", jobRepository)
        .<Trade, Trade>chunk(100, transactionManager)
        .reader(tradeReader)
        .processor(tradeProcessor)
        .writer(tradeWriter)
        .build();
```

If the XML has 250 `<trade>` fragments, the Step can process three chunks: 100, 100, and 50 items. Each `<trade>` is one item; a chunk contains multiple fragments.

```text
XML fragments:
  trade 1, trade 2, ... trade 100  -> Chunk 1 -> Commit
  trade 101 ... trade 200         -> Chunk 2 -> Commit
  trade 201 ... trade 250         -> Chunk 3 -> Commit
```

Do not configure the fragment root based on chunk size. The reader does not group 100 fragments into one item; it returns each fragment individually. The chunk-oriented Step decides item grouping and transaction boundaries.

## 18. Reading multiple XML files with MultiResourceItemReader

If each file shares the same schema and fragment root, you can use `MultiResourceItemReader` wrapping a `StaxEventItemReader` delegate:

```java
@Bean
@StepScope
MultiResourceItemReader<Trade> multiTradeReader(
        @Value("#{jobParameters['input.pattern']}") Resource[] resources,
        StaxEventItemReader<Trade> tradeFileReader) {

    return new MultiResourceItemReaderBuilder<Trade>()
            .name("multiTradeReader")
            .resources(resources)
            .delegate(tradeFileReader)
            .saveState(true)
            .build();
}
```

Each resource is read by the delegate using the configured fragment root. Ensure the files have the same structure and a compatible unmarshaller. If files have different schema versions, you may need separate readers/unmarshallers or a version-detection step before processing.

Resource ordering must be stable on restart. If the file list is resolved via a wildcard and the order changes between runs, the multi-resource reader's checkpoint may point to a different resource. Sort the resource list deterministically and keep the input set stable for the same JobInstance.

## 19. Namespaces, prefixes, and element names

An XML prefix is just an alias for a namespace URI. The following two documents can represent the exact same QName:

```xml
<trades xmlns="urn:example:trading">
    <trade><isin>ABC</isin></trade>
</trades>
```

```xml
<t:trades xmlns:t="urn:example:trading">
    <t:trade><t:isin>ABC</t:isin></t:trade>
</t:trades>
```

The prefix `t` is not part of the business identifier; the namespace URI and local name form the QName. Do not depend on a literal prefix in the file if the source may change prefixes while keeping the same namespace URI.

When the JAXB model has a namespace, configure package-level `@XmlSchema` or namespaces on annotations for consistent mapping. When the reader accepts a fragment root, verify whether the API/configuration checks the namespace URI or only the local name. If multiple namespaces contain elements with the same local name, explicit QNames are needed to avoid picking the wrong fragment.

## 20. Fragment size and memory

StAX reads events in a stream, but the reader needs to collect the entire current fragment before unmarshalling it into an object. Therefore:

- A document with millions of small fragments usually fits well with a streaming reader.
- A single fragment containing hundreds of MB of data can still cause memory pressure.
- Large child lists inside one fragment can create a large object graph.
- Chunk size controls how many objects are held in a chunk; fragment size controls the size of each individual item.

If a fragment is too large, consider changing the input contract for smaller fragments or using a custom streaming reader that treats child elements as separate records. Do not increase heap indefinitely to mask an unsuitable item boundary.

## 21. Testing fragment root and item boundary

Tests should verify that the reader returns the right number of items and each item contains the right subtree. A small fixture should include multiple fragments, nested elements, and varying whitespace.

Test example:

```java
@Test
void readsOneItemForEachTradeFragment() throws Exception {
    String xml = """
            <?xml version="1.0" encoding="UTF-8"?>
            <trades>
                <trade>
                    <isin>US0378331005</isin>
                    <quantity>100</quantity>
                    <price>182.50</price>
                </trade>
                <trade><isin>US5949181045</isin><quantity>50</quantity><price>420.00</price></trade>
            </trades>
            """;

    Resource resource = new ByteArrayResource(
            xml.getBytes(StandardCharsets.UTF_8));

    StaxEventItemReader<Trade> reader =
            new StaxEventItemReaderBuilder<Trade>()
                    .name("testTradeReader")
                    .resource(resource)
                    .addFragmentRootElements("trade")
                    .unmarshaller(tradeUnmarshaller)
                    .saveState(true)
                    .build();

    reader.open(new ExecutionContext());
    try {
        Trade first = reader.read();
        Trade second = reader.read();
        Trade end = reader.read();

        assertThat(first.getIsin()).isEqualTo("US0378331005");
        assertThat(first.getQuantity()).isEqualTo(100);
        assertThat(second.getIsin()).isEqualTo("US5949181045");
        assertThat(second.getQuantity()).isEqualTo(50);
        assertThat(end).isNull();
    } finally {
        reader.close();
    }
}
```

The illustration test uses a `tradeUnmarshaller` already initialized for the `Trade` model. In tests running outside a Spring container, initialize `Jaxb2Marshaller` and call required lifecycle initialization before passing it to the reader. You may need to call `afterPropertiesSet()` on the reader when creating it directly, depending on how the builder and test fixture initialize it.

### Cases to test

- Single fragment: reader returns exactly one item.
- Multiple fragments: item count equals the number of valid fragment roots.
- Nested elements: the entire subtree remains within one item.
- Wrong fragment root name: reader does not create unintended items.
- Empty XML or wrapper-only XML: reader finishes with no items per resource configuration.
- Fragment missing fields: verify mapping/schema/business validation behaves properly.
- Non-well-formed XML: reader reports an error and the Step reaches the appropriate status.
- Default and prefixed namespaces: QNames are recognized properly.
- Multiple fragment roots: each type unmarshals into the right common type.
- Restart: committed items are not unintentionally reprocessed.
- Multi-resource: file order and checkpoints are stable.

## 22. Common errors

### Choosing the document root as fragment root

If `trades` wraps all trades while the business item is each `trade`, choosing `trades` can bundle the entire document into one fragment. Pick the repeating element representing an item.

### Choosing a child element too deep

Choosing `line` when the business item is `order` loses parent order/customer context. Pick a boundary containing all data needed for processing.

### Thinking each XML line is an item

StAX reads by XML structure, not by newline. One item can span many lines or sit on a single line.

### Confusing fragment root with JAXB root model

The reader defines the fragment boundary; the unmarshaller maps the fragment to a class. Both configurations must align on name/QName and schema.

### Ignoring namespaces

Identical local names with different namespaces may be different elements. Check namespace URIs and JAXB mappings.

### Registering multiple roots when unmarshaller does not support all of them

The reader may locate the fragment, but mapping fails if JAXB does not know the corresponding root. Create an appropriate model/wrapper or unmarshaller.

### Assuming child fragments automatically become items

If the fragment root is `order`, nested `item` elements remain child data of the order. To turn them into Batch items, choose a different boundary or reader design.

### Skipping malformed XML like normal data errors

The parser may lose the ability to determine boundaries after structural errors. Usually fail the document/Step and fix the source.

### Changing the file or fragment root on restart

The old checkpoint may no longer point to the right position. Keep input immutable and reader configuration stable for the same JobInstance.

### An overly large single fragment

StAX streaming does not mean a fragment object uses no memory. Revisit the item boundary or stream-process fragments if the size is excessive.

## 23. Process for selecting a fragment root

When receiving a new XML input, follow these steps in order:

1. Inspect the document structure and identify the document root.
2. Identify the business unit to process: order, trade, invoice, customer, or detail line.
3. Find the XML element containing all data for that unit.
4. Verify that the element repeats and each occurrence can be processed independently.
5. Check whether nested child elements share the same name/QName causing ambiguity.
6. Identify the namespace URI, local name, and schema version.
7. Declare the fragment root with `addFragmentRootElements(...)`.
8. Configure the `Unmarshaller` to map fragments to the appropriate Java type.
9. Enable `saveState` and keep resource, reader name, and fragment root stable when restart is required.
10. Test fragment counts, nested subtrees, namespaces, mapping errors, and restarts.
11. Pick chunk size by item count; do not confuse chunk boundaries with XML fragment boundaries.
12. Measure fragment size and memory if each item has a large nested structure.

| XML Structure | Appropriate item boundary if business logic processes by |
|---|---|
| `<trades><trade>...</trade></trades>` | Each `trade` |
| `<orders><order><lines><line>...</line></lines></order></orders>` | Each `order` if customer and all lines are needed |
| `<invoices><invoice>...</invoice></invoices>` | Each `invoice` |
| `<portfolio><stockTrade>...</stockTrade><cashMovement>...</cashMovement></portfolio>` | Each event type if mappable to a common item type |
| `<export><metadata>...</metadata><records><record>...</record></records></export>` | Each `record`; metadata handled separately if needed by the Job |

## Conclusion

In Spring Batch XML processing, the fragment root determines which element becomes an item; the document root is just the outer wrapper for the entire document. `StaxEventItemReader` uses StAX to collect each subtree from the fragment root to its matching closing tag and passes the fragment to the `Unmarshaller`. Choose a boundary that holds complete data for one business unit, configure QName/namespaces and JAXB mappings accurately, and keep the reader name, input, and fragment definition stable for restarts. The fragment boundary defines one item, whereas chunk size defines how many items belong in a single transaction. Test nested elements, multiple fragments, namespaces, malformed XML, and restarts to ensure the reader neither bundles too much data into one item nor splits items without proper context.
