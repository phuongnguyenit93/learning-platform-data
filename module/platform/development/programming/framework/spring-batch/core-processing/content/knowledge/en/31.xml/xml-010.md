# Marshaller in the writer

When a batch job needs to export data as XML, the writer must convert each Java object into a valid XML fragment and combine those fragments into a complete document. Spring Batch supports this via `StaxEventItemWriter`, while Spring OXM provides the **`Marshaller`** abstraction to convert objects into XML.

The marshaller is responsible for mapping objects and Java data structures to XML. The writer is responsible for managing the output file, the document's root element, item order, encoding, header/footer callbacks, checkpoints, and chunk-oriented writing lifecycle. Both components work together while keeping separate responsibilities.

For example, a job exporting multiple orders might produce the document:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order>
        <orderId>1001</orderId>
        <customerId>C001</customerId>
        <amount>250.00</amount>
    </order>
    <order>
        <orderId>1002</orderId>
        <customerId>C002</customerId>
        <amount>175.50</amount>
    </order>
</orders>
```

`StaxEventItemWriter` creates the `<orders>` root element, then invokes the marshaller for each item to produce `<order>` elements. As a result, the application does not have to concatenate XML strings manually inside the writer.

## 1. What is a Marshaller?

`Marshaller` is an interface in Spring OXM (`org.springframework.oxm.Marshaller`). It defines how to convert an object graph into XML through a Spring `Result` target object.

Two key operations of this abstraction are:

- `supports(Class<?>)`: indicates whether the marshaller supports the queried object type.
- `marshal(Object, Result)`: writes the XML representation of the object into the target result.

Conceptual code:

```java
public interface Marshaller {

    boolean supports(Class<?> clazz);

    void marshal(Object graph, Result result)
            throws IOException, XmlMappingException;
}
```

Spring OXM decouples object-to-XML mapping from how files are written. An implementation can use JAXB or another XML binding technology. In Spring Batch, `StaxEventItemWriter` uses the marshaller to write each item as XML events/fragments into the open document.

The marshaller does not read items from sources, coordinate chunks, or commit transactions. Those responsibilities belong to the Spring Batch pipeline and writer.

## 2. Where does the Marshaller sit in the batch pipeline?

In a chunk-oriented step, data flows through the reader, processor, and writer. When the writer is `StaxEventItemWriter`, each output item passes through the marshaller before XML is written to the resource.

```mermaid
flowchart LR
    A[ItemReader] --> B[ItemProcessor]
    B --> C[StaxEventItemWriter]
    C --> D[Marshaller]
    D --> E[XML events / fragment]
    E --> F[XML document writer]
    F --> G[File resource]
```

Responsibilities are divided as follows:

| Component | Responsibility |
|---|---|
| `ItemReader` | Reads input items |
| `ItemProcessor` | Transforms or filters items |
| `Marshaller` | Maps objects to XML |
| `StaxEventItemWriter` | Assembles each item's XML into the document, manages file and state |
| Transaction manager | Manages chunk transactions and transactional resources |
| `JobRepository` | Stores job/step metadata and checkpoints |

Using a marshaller lets the writer focus on orchestrating XML output, while schema mapping is configured separately on the model or binding metadata.

## 3. StaxEventItemWriter

`StaxEventItemWriter<T>` is Spring Batch's writer that uses StAX to produce streaming XML output. StAX is a streaming XML processing API well suited to batch workloads because the writer can write item by item without building the entire large XML document in memory.

Common configurations:

- `resource`: the output file or resource.
- `marshaller`: the object that converts items to XML.
- `rootTagName`: the root element name wrapping all items.
- `encoding`: the document encoding.
- `headerCallback` and `footerCallback`: extra content at the start/end of the document.
- `saveState`: saves state for restarts.
- `overwriteOutput`: controls how existing output is handled when starting to write per writer settings.
- `name`: stable name used for state in the execution context.

Example XML output with a root element containing multiple items:

```xml
<orders>
    <order>...</order>
    <order>...</order>
    <order>...</order>
</orders>
```

`rootTagName` is the outer wrapper element name, while each item's root element is typically determined by JAXB annotations or marshaller metadata.

## 4. Using JAXB as the marshaller

JAXB is a binding technology between Java objects and XML. In Spring OXM, `Jaxb2Marshaller` provides a Spring `Marshaller` implementation backed by JAXB.

In modern Spring Framework 6/Spring Batch 5, JAXB APIs normally belong to the `jakarta.xml.bind` namespace. Legacy projects may use the `javax.xml.bind` namespace; keep versions aligned with your Spring and JAXB dependencies.

XML model example:

```java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;
import jakarta.xml.bind.annotation.XmlType;

import java.math.BigDecimal;

@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
@XmlType(propOrder = {"orderId", "customerId", "amount"})
public class OrderXml {

    @XmlElement(required = true)
    private Long orderId;

    private String customerId;
    private BigDecimal amount;

    public OrderXml() {
    }

    public OrderXml(Long orderId, String customerId, BigDecimal amount) {
        this.orderId = orderId;
        this.customerId = customerId;
        this.amount = amount;
    }
}
```

In the example:

- `@XmlRootElement(name = "order")` defines the root element for one item.
- `@XmlAccessorType(XmlAccessType.FIELD)` tells JAXB to read fields directly.
- `@XmlType(propOrder = ...)` specifies child element order.
- `@XmlElement` can declare additional element metadata.
- A no-arg constructor lets JAXB instantiate objects in many common binding setups.

When using field access, getters/setters are not strictly required for JAXB-mapped fields, though the model may still provide them for other parts of the application.

## 5. Configuring Jaxb2Marshaller

You can declare `Jaxb2Marshaller` as a Spring bean and register the classes to bind:

```java
@Bean
public Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    marshaller.setMarshallerProperties(Map.of(
            "jaxb.formatted.output", Boolean.TRUE));
    return marshaller;
}
```

`setClassesToBeBound(...)` registers the Java types the JAXB context must know about. With multiple XML types, you can pass multiple classes. Another option is `setPackagesToScan(...)` when models are organized by package with proper annotations.

`setMarshallerProperties(...)` passes properties to the JAXB marshaller. For instance, `jaxb.formatted.output` enables pretty printing. Pretty formatting makes output easier to read, though it increases file size and write cost compared to compact XML.

Fully configure the marshaller before the job runs. Avoid mutating binding metadata while the writer is actively using it.

## 6. Configuring StaxEventItemWriter with builder

Spring Batch provides `StaxEventItemWriterBuilder<T>` to build writers more readably than configuring individual setters.

```java
@Bean
public StaxEventItemWriter<OrderXml> orderXmlWriter(
        Jaxb2Marshaller orderMarshaller,
        @Value("#{jobParameters['outputFile']}") String outputFile) {

    return new StaxEventItemWriterBuilder<OrderXml>()
            .name("orderXmlWriter")
            .resource(new FileSystemResource(outputFile))
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .encoding(StandardCharsets.UTF_8.name())
            .saveState(true)
            .overwriteOutput(true)
            .build();
}
```

Key points to understand:

- `.name("orderXmlWriter")` provides a stable name for writer state.
- `.resource(...)` specifies the target XML file.
- `.marshaller(...)` attaches the mechanism converting items to XML.
- `.rootTagName("orders")` creates the document's outer wrapper element.
- `.encoding(...)` sets the encoding explicitly.
- `.saveState(true)` enables state saving for restarts.
- `.overwriteOutput(true)` permits handling existing output according to the writer's overwrite policy when starting a new write; use only when the run's output path should be created fresh and replacement is intentional.

Do not use an already-published path from a previous period as the resource with overwrite enabled. Create a dedicated staging path keyed by job identity and distinguish a restart from a new export.

## 7. Wiring the writer into a step

After creating the marshaller and writer, configure them in a chunk-oriented step:

```java
@Bean
public Step exportOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<OrderInput> orderReader,
        ItemProcessor<OrderInput, OrderXml> orderProcessor,
        StaxEventItemWriter<OrderXml> orderXmlWriter) {

    return new StepBuilder("exportOrdersStep", jobRepository)
            .<OrderInput, OrderXml>chunk(500, transactionManager)
            .reader(orderReader)
            .processor(orderProcessor)
            .writer(orderXmlWriter)
            .build();
}
```

The processor converts the input model into `OrderXml`, the type supported by JAXB. The writer receives chunks of `OrderXml` and invokes the marshaller for each item.

A chunk size of 500 is just an example. The right size depends on object size, marshalling cost, filesystem speed, and commit/restart requirements.

## 8. Separating business models and XML models

You do not have to annotate business entities with JAXB. Create a dedicated XML DTO to decouple external schemas from internal application structure.

Example:

```java
public class OrderProcessor
        implements ItemProcessor<Order, OrderXml> {

    @Override
    public OrderXml process(Order order) {
        return new OrderXml(
                order.getId(),
                order.getCustomer().getCode(),
                order.getTotalAmount());
    }
}
```

Benefits:

- The XML schema does not depend directly on persistence entities.
- Elements/attributes can be renamed without altering domain models.
- Avoids accidentally serializing lazy associations or internal fields.
- Exports only the fields intended for the file.
- XML DTOs can be versioned per integration contract.

For batch exports to external systems, dedicated XML DTOs are usually easier to control than marshalling full JPA entities.

## 9. Document root element vs item root element

Distinguish two root levels:

1. Document root managed by `StaxEventItemWriter`, e.g. `<orders>`.
2. Item root element produced by the marshaller, e.g. `<order>`.

Example:

```xml
<orders>
    <order>
        <orderId>1001</orderId>
    </order>
    <order>
        <orderId>1002</orderId>
    </order>
</orders>
```

If `rootTagName` is `orders`, the JAXB item model must marshal into element `order`. Do not give each item the same root element as the document root if the expected structure is a list of items inside a wrapper.

If the model lacks `@XmlRootElement`, JAXB may require a `JAXBElement` created via `ObjectFactory` or a matching mapping mechanism. In that case, the processor or a custom marshaller must return the proper wrapper object that JAXB can marshal as a root element.

## 10. Using JAXBElement when a class lacks XmlRootElement

Some models generated from XSDs do not have `@XmlRootElement` directly on the class. JAXB can generate an `ObjectFactory` with methods returning `JAXBElement<T>`.

Conceptual example:

```java
ObjectFactory factory = new ObjectFactory();
JAXBElement<OrderXml> element = factory.createOrder(orderXml);
marshaller.marshal(element, result);
```

If the writer receives `OrderXml` while the marshaller only supports `JAXBElement<OrderXml>`, write a dedicated adapter/provider to wrap items into the marshaller-supported type, or adjust the processor to produce the wrapper. Ensure `supports(...)` and the actual marshalled object type are compatible.

Do not arbitrarily add `@XmlRootElement` to schema-generated classes if those edits will be overwritten on the next generation pass. Use `ObjectFactory` or a custom adapter tailored to the generated JAXB structure.

## 11. XML elements, attributes, and field ordering

JAXB annotations let you control how fields appear in XML.

Example using attributes and elements:

```java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
@XmlType(propOrder = {"customerId", "amount"})
public class OrderXml {

    @XmlAttribute(name = "id")
    private Long orderId;

    @XmlElement(name = "customer")
    private String customerId;

    @XmlElement(name = "total")
    private BigDecimal amount;
}
```

Generated XML looks like:

```xml
<order id="1001">
    <customer>C001</customer>
    <total>250.00</total>
</order>
```

Commonly used annotations:

| Annotation | Role |
|---|---|
| `@XmlRootElement` | Root element name of the object |
| `@XmlElement` | Maps a property to a child element |
| `@XmlAttribute` | Maps a property to an XML attribute |
| `@XmlType(propOrder = ...)` | Specifies child element order |
| `@XmlElementWrapper` | Creates a wrapper around a collection |
| `@XmlTransient` | Excludes a property from XML binding |
| `@XmlJavaTypeAdapter` | Custom Java type conversion |

XML ordering can be part of the XSD contract. If the schema mandates a specific element sequence, declare `propOrder` and test XML output against that schema.

## 12. Collections inside an item

An item can contain a list of detail lines. JAXB can marshal collections into multiple child elements.

Example:

```java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    private Long orderId;

    @XmlElementWrapper(name = "lines")
    @XmlElement(name = "line")
    private List<OrderLineXml> lines;
}
```

The XML structure can look like:

```xml
<order>
    <orderId>1001</orderId>
    <lines>
        <line>...</line>
        <line>...</line>
    </lines>
</order>
```

This is a collection inside a single item. It differs from multiple independent items written by `StaxEventItemWriter` under the document root `<orders>`.

If one item holds thousands of child objects, the object graph can grow large. The marshaller must traverse that item's full graph; chunk size does not shrink a single oversized item. You may need to paginate detail data or change the export model if individual records are too large.

## 13. XML namespaces

Many XML contracts require namespaces to distinguish vocabularies. JAXB supports namespaces through annotations and package-level schema metadata.

Example:

```java
@XmlRootElement(name = "order", namespace = "urn:example:orders:v1")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {
    private Long orderId;
}
```

XML can be marshalled with the matching namespace URI. To control default or explicit prefixes, configure namespace/package metadata or adapters depending on the JAXB implementation.

When using namespaces, verify:

- The namespace URI matches the XSD/contract.
- Document root and items use consistent namespaces.
- Prefixes are only aliases; the namespace URI is the true identifier.
- `xsi:schemaLocation`, if needed, is declared per contract.
- Header/footer callbacks do not introduce invalid roots or broken namespace declarations.

Do not compare XML solely by prefix strings when verifying namespace URIs and structure. Two different prefixes can still represent the same namespace.

## 14. Encoding and XML declaration

File encoding must align with the XML declaration and actual byte output. For modern integrations, UTF-8 is the common choice.

```java
.encoding(StandardCharsets.UTF_8.name())
```

If the file contains Vietnamese or non-ASCII characters, test the byte output as UTF-8 and re-parse with an XML parser. Do not merely open the file in an editor and trust the editor's encoding auto-detection.

The XML declaration can include version and encoding. The writer manages document-level output; the marshaller is called per item and should produce fragments compatible with the open document. Never let each item emit another XML declaration or nested document root.

If a partner requires a specific XML version or standalone declaration, verify writer settings and the declaration emitted by your Spring Batch version. Do not emit a second declaration in the header callback when the writer already produces one.

## 15. HeaderCallback and FooterCallback

`StaxEventItemWriter` can add content at the beginning and end of the document via StAX callbacks. Callbacks are useful for metadata or trailers defined by the schema.

Example structure:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <!-- Header or metadata if contract permits -->
    <order>...</order>
    <order>...</order>
    <!-- Footer if schema defines -->
</orders>
```

Header/footer callbacks work with an XML event writer, allowing proper events to be written instead of arbitrary string concatenation. The specific callback API in Spring Batch is `StaxWriterCallback`.

Builder-level configuration example:

```java
.headerCallback(eventWriter -> {
    // Write XML events permitted by the schema.
})
.footerCallback(eventWriter -> {
    // Write closing XML events or trailing metadata.
})
```

Do not write an extra document root inside callbacks when the writer already manages `rootTagName`. Header/footer must emit valid events at the exact position where the writer invokes the callback. A single namespace or event-order error can render the XML unparseable.

## 16. Header/footer are not for writing item data

Header/footer callbacks are normally called around document or resource open/close lifecycles, not once per item. Thus, never use them to write individual records or run chunk-dependent logic.

Appropriate uses:

- Writing static file metadata.
- Writing schema version.
- Writing generation timestamp if contract allows.
- Writing trailer/count if the application has an accurate count and timing.

Inappropriate uses:

- Writing each order or customer.
- Calling APIs with per-item side effects.
- Incrementing per-item counters if callbacks do not execute at the needed lifecycle points.
- Writing a footer dependent on committed item count without accounting for restart/rollback.

If a trailing record count is needed, compute it from metadata or persisted data and place it in a dedicated manifest/footer step by design. Pay attention to restarts so the footer appears only once in the finished document.

## 17. XML validation and XSD

The marshaller converts objects to XML per mapping, yet successful marshalling does not automatically guarantee the output satisfies the partner's XSD.

You can validate output against an XML Schema once the file finishes:

1. Close the XML writer so the document has its closing root and footer.
2. Use `SchemaFactory` to load a trusted XSD.
3. Create a `Validator` and validate the output file.
4. If valid, allow the publish step to proceed.
5. If invalid, keep the staging file for investigation and end the job per policy.

Java example:

```java
SchemaFactory schemaFactory =
        SchemaFactory.newInstance(XMLConstants.W3C_XML_SCHEMA_NS_URI);

Schema schema = schemaFactory.newSchema(xsdResource.getURL());
Validator validator = schema.newValidator();
validator.validate(new StreamSource(xmlFile));
```

In production, configure XSD sources securely and restrict external entity/schema access unless needed. Never load XSDs from untrusted URLs while validating output.

Per-item validation can catch errors early, but full-file schema validation remains necessary when rules depend on overall structure or root/document-level metadata.

## 18. When the marshaller does not support the item type

Spring OXM `Marshaller` exposes `supports(Class<?>)`. If the marshaller does not support an item's class, marshalling fails when the writer processes that item.

Common causes:

- Class is not registered in the JAXB context.
- Model lacks required annotations or `ObjectFactory`.
- Processor returns a DTO different from the configured type.
- Writer receives `JAXBElement` while the marshaller only binds the raw class, or vice versa.
- `javax` and `jakarta` JAXB namespaces are mixed across dependencies.

Verify the processor's output type, the bound class list, and the marshaller implementation. You can verify support before launching the job in configuration/preflight tests, though the writer still must handle actual mapping errors.

## 19. Marshal errors and batch handling

The marshaller can fail when an object does not fit the mapping, a property is invalid, an adapter fails, or the output result hits an I/O error.

Common errors:

- `XmlMappingException`: object-to-XML mapping error.
- `IOException`: stream or resource read/write error.
- JAXB exceptions translated by Spring OXM into `XmlMappingException` or matching exceptions.
- StAX errors when emitting invalid XML events.

When a writer throws an exception during a chunk, the chunk transaction can roll back transactional resources. XML output behaves according to the writer's and resource's transactional settings. For permanent mapping errors such as an unmarshallable property, retry rarely helps; fix the model or data. For transient I/O errors, bounded retry can be considered if the writer and resource support safe recovery.

Do not broadly skip all marshal errors. Skipping items causes the XML output to omit business records. Skip only when business rules allow it and record the failed item along with the reason.

## 20. Transactional writing and chunk rollback

`StaxEventItemWriter` supports writing aligned with chunk transactions. Under default transactional configuration, the writer can buffer chunk XML events/content and flush them to output only upon transaction commit; on rollback, uncommitted writes can be discarded per writer mechanics.

This prevents some chunk rollback scenarios from leaving partial items in the file. Still, the filesystem does not become a general-purpose database transaction:

- The process can crash in the window between writing the file and persisting metadata.
- Storage can fail on flush or lose connectivity.
- External systems can read a file mid-creation if written directly to the published path.
- Header/footer and publish operations have their own lifecycles.
- Side effects outside the file/database do not roll back automatically.

For critical outputs, write to a staging file, close and validate, then publish in a separate recoverable step. Never let downstream read a file actively being written.

## 21. Restart and saveState

`StaxEventItemWriter` is an `ItemStreamWriter` that can save state for restarts. With `saveState(true)` and a stable writer name, the writer saves necessary progress in `ExecutionContext` to resume output from the checkpoint.

Example:

```java
.name("orderXmlWriter")
.saveState(true)
```

For safe restarts:

- Use the same identifying job parameters to restart the right `JobInstance`.
- Keep the same staging artifact output resource.
- Keep the writer name stable.
- Do not change schema/model or source contents in ways that invalidate checkpoints.
- Let the writer restore state via `ExecutionContext` instead of appending manually from scratch.
- Ensure previously committed output is not deleted when reopening the resource.

If using `overwriteOutput(true)` on an existing resource, understand the difference between a fresh run and a restart in your version's behavior. Do not let overwrite settings wipe committed output that must be resumed. A safe approach is a dedicated output path per `JobInstance` and an explicit staging/publishing workflow.

## 22. Output paths and avoiding overwriting old results

An XML output should typically be identified by business date, tenant, and output version:

```text
exports/
  staging/
    orders-2026-11-15-tenant-42-v1.xml
  published/
    orders-2026-11-15-tenant-42-v1.xml
```

Restarting the same `JobInstance` resumes its matching staging file. An intentional reprocess uses a new version rather than overwriting published files.

Do not use a new `JobExecution` ID as the sole output identity when restarts must reopen the same resource. Conversely, do not share one fixed path across multiple concurrent `JobInstance` runs.

When publishing, check the target file and manifest/checksum. If the file already exists and matches the exact job/version artifact, publishing can be treated as already done. If contents differ, fail and report a collision instead of silently overwriting.

## 23. Marshaller and performance

XML marshalling carries CPU and allocation costs. For jobs exporting many items, consider:

- Object graph complexity.
- Number of child objects per item.
- Pretty printing and whitespace.
- Custom adapters or converters.
- Namespace/schema metadata.
- Chunk size and transaction buffers.
- Storage speed and flushing.

StAX enables streaming writes instead of building the full XML document on the heap. However, the marshaller still processes each item's object graph. An item holding a massive collection can still cause memory pressure.

Do not create a new JAXB context or configure a new marshaller per item. Configure `Jaxb2Marshaller` as a reusable bean after initialization. For custom marshallers, verify thread-safety and internal lifecycle before sharing.

Pretty printing helps when humans inspect files directly, but for huge files parsed strictly by machines, compact XML reduces output bytes and I/O overhead.

## 24. Thread safety

In a sequential step, the writer is normally called in step chunk order. Yet if a writer or custom marshaller is shared across multiple steps/threads, evaluate thread safety.

- `StaxEventItemWriter` manages file state and an XML event writer; never use one writer instance to write concurrently to one resource from multiple threads.
- `Jaxb2Marshaller` is a Spring OXM abstraction designed to be configured and reused; avoid sharing a raw JAXB `Marshaller` object directly across threads since JAXB marshallers are not always thread-safe.
- Custom `Marshaller` implementations must hold no shared mutable state or must synchronize explicitly.
- Item DTOs should not be mutated during marshalling.
- Parallel flows should write to separate resources per branch, then merge or publish in a separate step.

If multiple XML exports must run in parallel, each step/job should have its own writer instance and output resource. Never share one mutable `XMLStreamWriter` across branches.

## 25. Using a custom Spring OXM Marshaller

JAXB is not mandatory. You can use any Spring OXM implementation compatible with the `Result` type supplied by `StaxEventItemWriter`.

A custom marshaller can implement:

```java
public class OrderMarshaller implements Marshaller {

    @Override
    public boolean supports(Class<?> clazz) {
        return OrderXml.class.isAssignableFrom(clazz);
    }

    @Override
    public void marshal(Object graph, Result result)
            throws IOException, XmlMappingException {
        OrderXml order = (OrderXml) graph;
        // Write XML according to the defined mapping.
    }
}
```

This is only a skeleton; XML writing must use compatible StAX/Result APIs and handle exceptions properly. When implementing your own, verify:

- `supports(...)` returns true only for genuinely supported types.
- Output is a valid fragment/item inside the document root managed by the writer.
- Do not close streams/results owned by the writer.
- Do not emit an XML declaration or nested document root.
- XML escaping is applied properly to text and attributes.
- Namespaces and encoding follow the contract.
- Implementation is thread-safe if used concurrently.

In most cases, using `Jaxb2Marshaller` is far less error-prone than hand-rolling an XML serializer.

## 26. XML escaping and untrusted data

Standard marshallers escape special characters in text/attributes per XML rules. For example, `A & B` must be represented as `A &amp; B` in XML.

Never build XML by string concatenation like:

```java
String xml = "<customer>" + customerName + "</customer>";
```

because data may contain `&`, `<`, `>`, or quotes, breaking XML validity or introducing XML injection flaws.

Marshal objects with an XML binding library or use a properly escaping XML writer. If nested HTML/XML content must be embedded, clarify whether it is text, CDATA, or an XML subtree per schema; never disable escaping to "preserve raw strings" without control.

## 27. Namespaces and schema versioning

XML is often a long-lived integration contract. When schemas evolve, never silently alter mappings for an active job if restarts must resume the same output.

Models can be versioned:

```text
OrderXmlV1 -> urn:example:orders:v1
OrderXmlV2 -> urn:example:orders:v2
```

Select the model/marshaller using an identifying parameter or explicit version setting. If a `JobInstance` already created checkpoints with V1, restarts must continue with the same schema/resource. To export V2, create a new output version/instance.

Schema version should also be recorded in metadata/manifests so downstream knows how to parse the file. Do not rely solely on filenames or timestamps.

## 28. Verifying output XML after writing

A post-writer verification step can:

- Parse the file using an XML parser.
- Confirm the root element and namespace.
- Validate against the XSD.
- Check the count of exported items.
- Check required fields.
- Compute checksum and write manifest.

Perform this after the writer has closed the document, because while open, the closing root tag/footer may not yet be written.

If the XML is invalid, do not publish the file. Retain staging output and log parse locations/errors for investigation. Never delete previously published output merely because a new staging build failed validation.

## 29. Testing the marshaller independently

You can test the marshaller without running a full job by marshalling an object into a `StringResult` or `StreamResult` compatible with the implementation.

Example with Spring OXM:

```java
Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
marshaller.setClassesToBeBound(OrderXml.class);
marshaller.afterPropertiesSet();

StringResult result = new StringResult();
marshaller.marshal(
        new OrderXml(1001L, "C001", new BigDecimal("250.00")),
        result);

String xml = result.toString();
```

Then parse `xml` and verify root/elements/values. Avoid literal string equality assertions if whitespace or namespace prefixes can vary while XML remains structurally equivalent.

Cases to test:

- Valid object marshals into the right item root.
- Null fields are handled per schema.
- Decimals/dates/times have expected formats.
- Enums convert to expected values.
- Namespaces and element ordering are accurate.
- Nested collections have matching wrappers.
- Special characters are escaped.
- Unsupported classes are rejected clearly.

## 30. Integration testing with StaxEventItemWriter

Marshaller unit tests do not prove the writer builds the right outer document, header/footer, and restart state. Include integration tests with a real writer.

A basic test can:

1. Create a `Jaxb2Marshaller` for `OrderXml`.
2. Configure `StaxEventItemWriter` with root `orders` and a temp file.
3. Invoke `open`, `write`, `update`, and `close` per `ItemStream` lifecycle, or run via a test step.
4. Parse the output file with an XML parser.
5. Verify a single `<orders>` root and exact `<order>` count.
6. Validate against XSD if the contract defines a schema.

In Spring Batch, testing through a step/job reflects transactions, checkpoints, and callbacks much more accurately than calling writer methods manually. You can use `JobLauncherTestUtils` in test configurations.

### Testing rollback and restart

- Intentionally fail the writer or step after several chunks commit.
- Restart the same `JobInstance` and verify the XML has no duplicate items.
- Verify the document root appears only once.
- Verify no repeated XML declarations appear between items.
- Verify the staging file is finalized before publishing.
- Verify old output is not overwritten when launching a new instance.

## 31. Common errors

| Situation | Cause | Fix |
|---|---|---|
| Writer cannot marshal item | Class not bound or unsupported by marshaller | Register class, check `supports` and processor return type |
| Missing item root element | Model lacks `@XmlRootElement` or matching `JAXBElement` | Use annotation or `ObjectFactory` wrapper |
| XML has malformed nested roots | Confused document `rootTagName` with item root | Separate document wrapper and item root |
| Repeated XML declarations | Custom marshaller emits full document per item | Marshal fragments compatible with the writer |
| Wrong XML namespace | Annotation/package namespace mismatches XSD | Check URI/prefix and validate schema |
| Wrong element order | Missing `propOrder` per schema | Use `@XmlType(propOrder=...)` |
| `&` breaks XML | Unescaped string concatenation | Use standard marshaller/XML writer |
| File overwritten | Shared output path with overwrite enabled | Use dedicated staging path, version, and controlled publish |
| Restart produces duplicate XML | Writer state not saved/restored or wrong append | Use `saveState`, stable name/resource, and restart right instance |
| Header/footer duplicated or misplaced | Callback misaligned with lifecycle or emits root | Use callbacks for properly positioned document-level events |
| High heap usage | Items have huge object graphs or huge chunk buffers | Reduce chunk size, flatten DTOs, and stream data |
| Writer fails under parallel execution | Shared mutable writer/event writer | Give each step/flow its own writer and resource |
| Output fails XSD despite successful marshal | JAXB mapping does not cover all schema constraints | Validate file after writing and before publishing |

## 32. Workflow for designing an XML writer

1. **Define the XML contract:** document root, item root, namespaces, encoding, and XSD.
2. **Create the XML DTO:** include only exported fields and proper annotations.
3. **Configure the marshaller:** use `Jaxb2Marshaller` or a compatible Spring OXM implementation.
4. **Verify supported types:** classes must be in the binding context or wrapped in `JAXBElement`.
5. **Configure `StaxEventItemWriter`:** resource, root tag, encoding, name, and save state.
6. **Define output lifecycle:** staging per JobInstance, restart on same resource, publish after validation.
7. **Select chunk size:** balance throughput, memory, rollback, and XML item size.
8. **Handle header/footer:** emit only schema-compliant events matching the writer lifecycle.
9. **Test mapping and document:** marshaller unit tests, writer integration tests, and XSD validation.
10. **Monitor errors and restarts:** log job/step IDs, item keys, output paths, record counts, and checksums.

## 33. Principles to remember

- Spring OXM `Marshaller` converts objects to XML; `StaxEventItemWriter` manages the output document and resource.
- The writer's extension point is `ItemWriter` receiving items; the marshaller is invoked to serialize each item.
- `rootTagName` is the document root, while `@XmlRootElement` or `JAXBElement` defines each item's root.
- `Jaxb2Marshaller` is a popular choice; register classes/packages to marshal before the job runs.
- `jakarta.xml.bind` vs `javax.xml.bind` namespaces must match dependency versions.
- Use dedicated XML DTOs to decouple integration schemas from internal domain/entities.
- Use annotations like `@XmlElement`, `@XmlAttribute`, `@XmlType(propOrder)`, and `@XmlElementWrapper` to control structure.
- Configure encoding explicitly, avoid repeated XML declarations, and ensure accurate namespaces.
- Header/footer callbacks are for document-level events, not for writing individual items.
- Successful marshalling does not guarantee XSD compliance; validate files before publishing when schemas are required.
- Permanent mapping errors are rarely solved by retries; fix the model or data.
- `saveState` and stable writer names support restarts; staging paths must remain stable per JobInstance.
- Do not overwrite/append blindly; protect published outputs with versions, manifests, and a dedicated publish step.
- Do not share one mutable `StaxEventItemWriter` across multiple concurrent threads/flows.
- Test marshaller, XML document, namespaces/schemas, rollbacks, and restarts.

A marshaller in the writer helps Spring Batch export objects to XML following a structured contract. By cleanly separating object mapping from document management, configuring JAXB/namespaces properly, keeping the writer restartable, and validating output before publishing, a job can stream large XML documents while maintaining control over schema, performance, and recoverability.
