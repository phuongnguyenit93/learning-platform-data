# StaxEventItemReader

In Spring Batch, `StaxEventItemReader<T>` reads XML data in a streaming fashion using StAX (Streaming API for XML). Instead of loading the entire XML document into a DOM tree, the reader iterates through XML events and extracts selected elements into fragments. Each fragment typically represents a business record and is converted into a Java object via a Spring OXM `Unmarshaller`.

For example, an XML file has a root `<trades>` containing hundreds of thousands of `<trade>` elements. The reader can read each `<trade>` into a `Trade`, then pass the item into the chunk Step for the processor and writer to process. This approach is suitable for large XML files with a repeating structure, where each record is enclosed by a clear element.

## 1. StAX and event-based XML reading

StAX is a Java API for reading XML in a pull/event-driven manner. The application asks the parser to provide the next event, such as document start, element start, text, element end, or document end.

Some common events:

| Event | Meaning |
|---|---|
| `START_DOCUMENT` | Start of the XML document |
| `START_ELEMENT` | Start of an element |
| `CHARACTERS` | Text content inside an element |
| `END_ELEMENT` | End of an element |
| `END_DOCUMENT` | End of the XML document |

XML example:

```xml
<trades>
    <trade>
        <isin>US0378331005</isin>
        <quantity>100</quantity>
        <price>215.75</price>
    </trade>
    <trade>
        <isin>US5949181045</isin>
        <quantity>50</quantity>
        <price>420.10</price>
    </trade>
</trades>
```

The StAX parser iterates through the events in the document. `StaxEventItemReader` locates the element configured as the fragment root, reads that entire fragment, and passes the fragment to the `Unmarshaller`. After the fragment is mapped into an object, the reader returns the object to Spring Batch. The next call to `read()` looks for the next fragment.

## 2. Why use StaxEventItemReader?

DOM typically builds an object tree for the entire XML document in memory. For very large files, this approach can consume a lot of heap. StAX enables sequential event-based processing, keeping only the data needed to construct the current item along with parser and chunk buffers.

`StaxEventItemReader` is appropriate when:

- The XML contains many repeating records under a common root element.
- Each record can be represented by a complete fragment element.
- Large files need to be read sequentially without loading the entire DOM.
- Each fragment can be mapped to a Java object using JAXB or another OXM `Unmarshaller`.
- XML reading needs to integrate with Spring Batch's chunk processing, transactions, skip/retry, and restart.

Streaming reduces the need to hold the entire document in memory, but it does not mean memory is strictly constant. The parser holds buffers, each fragment creates an object graph, and Spring Batch holds items in the chunk until processing/commit. Object size and chunk size still affect heap usage.

## 3. What is a fragment root element?

`StaxEventItemReader` does not create an item for every element in the XML by default. You must specify which element represents a record to be read. That element is called the *fragment root element*.

In the example above, `<trades>` is the document root, while each `<trade>` is a fragment:

```xml
<trades>
    <trade>...</trade>  <!-- item 1 -->
    <trade>...</trade>  <!-- item 2 -->
    <trade>...</trade>  <!-- item 3 -->
</trades>
```

The reader looks for the fragment root `trade`, takes all child content inside that element, and converts it into a `Trade` object. It does not create an item for `<trades>` if we configure `trade` as the fragment root.

Choose the element that represents one business unit. If you choose an element that is too broad, one fragment may contain multiple records. If you choose an element that is too granular, the reader may create items from partial data that is insufficient to form a business object.

## 4. Basic StaxEventItemReader configuration

Spring Batch provides `StaxEventItemReaderBuilder` to configure the reader. Example:

```java
@Bean
public StaxEventItemReader<Trade> tradeReader(
        Resource tradeResource,
        Unmarshaller tradeUnmarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(tradeResource)
            .addFragmentRootElements("trade")
            .unmarshaller(tradeUnmarshaller)
            .saveState(true)
            .strict(true)
            .build();
}
```

Key configuration options:

- `name("tradeReader")`: a stable name so the reader can save and restore state.
- `resource(tradeResource)`: the XML file to read.
- `addFragmentRootElements("trade")`: specifies the element representing one item.
- `unmarshaller(tradeUnmarshaller)`: converts an XML fragment into a Java object.
- `saveState(true)`: enables saving checkpoints in the Step `ExecutionContext`.
- `strict(true)`: requires the resource to exist when opening the reader according to the reader's strict behavior.

Builder method names may vary by Spring Batch version. On versions that support multiple fragment roots, you can pass multiple names to `addFragmentRootElements(...)`.

## 5. Creating an Unmarshaller with JAXB

`StaxEventItemReader` needs an `Unmarshaller` to convert an XML fragment into an object. Spring OXM provides `Jaxb2Marshaller`, which can be configured with the bound JAXB classes.

Model example:

```java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

import java.math.BigDecimal;

@XmlRootElement(name = "trade")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {

    @XmlElement(name = "isin")
    private String isin;

    @XmlElement(name = "quantity")
    private int quantity;

    @XmlElement(name = "price")
    private BigDecimal price;

    public Trade() {
    }

    public String getIsin() {
        return isin;
    }

    public int getQuantity() {
        return quantity;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
```

Marshaller declaration:

```java
@Bean
public Jaxb2Marshaller tradeMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    return marshaller;
}
```

Spring OXM's `Jaxb2Marshaller` implements the `Unmarshaller` contract, so it can be passed directly into the reader. The example uses the `jakarta.xml.bind` package suitable for newer Spring versions using Jakarta EE; older projects may use `javax.xml.bind` depending on the Spring/JAXB dependency version.

The root element name and child elements in the JAXB mapping must match the XML fragment. If the names differ, use annotations such as `@XmlRootElement` and `@XmlElement` to declare the mapping explicitly.

## 6. Complete XML and object mapping example

`trades.xml` file:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<trades>
    <trade>
        <isin>US0378331005</isin>
        <quantity>100</quantity>
        <price>215.75</price>
    </trade>
    <trade>
        <isin>US5949181045</isin>
        <quantity>50</quantity>
        <price>420.10</price>
    </trade>
</trades>
```

Reader:

```java
@Bean
public StaxEventItemReader<Trade> tradeReader(Jaxb2Marshaller tradeMarshaller) {
    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(new ClassPathResource("data/trades.xml"))
            .addFragmentRootElements("trade")
            .unmarshaller(tradeMarshaller)
            .saveState(true)
            .build();
}
```

Each call to `read()` returns one `Trade`:

| Read | `isin` | `quantity` | `price` |
|---:|---|---:|---:|
| 1 | `US0378331005` | 100 | 215.75 |
| 2 | `US5949181045` | 50 | 420.10 |
| 3 | EOF | — | — |

When no matching fragments remain, the reader returns `null` to signal end of data to Spring Batch.

## 7. Reading XML files from JobParameters

In production, the XML file often changes per run. You can use `@StepScope` to inject the file path from JobParameters:

```java
@Bean
@StepScope
public StaxEventItemReader<Trade> tradeReader(
        @Value("#{jobParameters['inputFile']}") String inputFile,
        Jaxb2Marshaller tradeMarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(new FileSystemResource(inputFile))
            .addFragmentRootElements("trade")
            .unmarshaller(tradeMarshaller)
            .saveState(true)
            .strict(true)
            .build();
}
```

`@StepScope` allows JobParameters expressions to be evaluated once the current StepExecution exists. Each run can read a different file without creating a singleton reader holding a mutable path.

If `inputFile` is a required parameter, validate it before opening the reader. If using a default path, decide whether that default must be materialized into JobParameters to ensure restarts always use the exact original file.

## 8. Integrating into a chunk-oriented Step

The reader is registered in a Step just like other readers:

```java
@Bean
public Step importTradesStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        StaxEventItemReader<Trade> tradeReader,
        ItemProcessor<Trade, Trade> tradeProcessor,
        ItemWriter<Trade> tradeWriter) {

    return new StepBuilder("importTradesStep", jobRepository)
            .<Trade, Trade>chunk(100, transactionManager)
            .reader(tradeReader)
            .processor(tradeProcessor)
            .writer(tradeWriter)
            .build();
}
```

With a chunk size of 100, the Step reads up to 100 fragments, processes them, and writes them in one chunk under the transaction manager. The reader maintains its parser state to continue with the next fragment; it does not reopen the entire file for each chunk.

Chunk size affects the number of objects held in the chunk and commit frequency. If XML fragments are large, measure heap usage and mapping time to pick an appropriate chunk size.

## 9. Multiple fragment root types

An XML document may contain multiple types of records to process. Some Spring Batch versions support declaring multiple fragment root elements:

```java
return new StaxEventItemReaderBuilder<Object>()
        .name("mixedXmlReader")
        .resource(resource)
        .addFragmentRootElements("trade", "cashMovement")
        .unmarshaller(mixedUnmarshaller)
        .build();
```

When using multiple fragment types, the `Unmarshaller` needs to know how to convert each root element into its corresponding object type. You can use a JAXB model with multiple bound classes or an appropriate wrapper/base type.

If each fragment has a very different structure, a single reader returning an interface/base class may need a custom unmarshaller to distinguish root elements and select the target class. Do not assume a `Jaxb2Marshaller` can automatically instantiate every type solely because the classes are registered; configure the JAXB mapping properly and test each fragment.

If your Spring Batch version only allows configuring a single fragment root, you can create separate readers per file/branch type or write a suitable mapping component instead of relying on unsupported APIs.

## 10. XML namespaces

XML can use a default namespace or prefixes:

```xml
<trades xmlns="urn:example:trades">
    <trade>
        <isin>US0378331005</isin>
        <quantity>100</quantity>
    </trade>
</trades>
```

A namespace is part of the qualified XML name (QName). The JAXB model needs to declare the appropriate namespace if the XML uses one:

```java
@XmlRootElement(name = "trade", namespace = "urn:example:trades")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {
    // corresponding fields and annotations
}
```

When configuring the fragment root, check how your Spring Batch version matches element names and namespaces. For example, `"trade"` is commonly used as the fragment name in basic configurations; for namespaced XML, verify the API's local name/QName behavior and test against actual files. Having the right namespace in JAXB mapping does not guarantee the reader finds the fragment if the root configuration does not match.

Do not strip namespaces from XML just to make mapping easier if the namespace is part of the data contract. Namespaces distinguish XML vocabularies that may share element names.

## 11. Nested elements and choosing the fragment root

A fragment root can contain many child elements, or even child elements with the same name as the fragment root:

```xml
<orders>
    <order>
        <orderId>1001</orderId>
        <lines>
            <line>
                <sku>A-10</sku>
                <quantity>2</quantity>
            </line>
        </lines>
    </order>
</orders>
```

Here you should choose `order` as the fragment root if one item is an order. Do not choose `line` if the processor/writer needs the entire order along with its detail lines.

When the same element name appears at multiple levels, check how the parser/reader identifies fragments by name and structure. Choosing distinctive fragment names and an unambiguous XML structure helps avoid accidentally splitting child elements into independent items.

If the XML nests multiple records of the same type and you want to process both parent and child records, a simple reader with the same fragment root may not express the requirement properly. Consider custom event processing or splitting the record types into separate Steps.

## 12. strict mode and XML schema validation

The reader's `strict` setting mainly relates to requiring the resource to exist when opening the reader. It is not synonymous with validating the entire XML against an XSD.

These are two separate concerns:

- **Resource strictness:** whether the input file exists.
- **XML schema validation:** whether the structure, namespaces, elements, and data types conform to an XSD.

If you need to validate XML against an XSD, configure validation on the JAXB/OXM unmarshaller or perform validation in a separate step. For example with `Jaxb2Marshaller`:

```java
@Bean
public Jaxb2Marshaller tradeMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.setSchemas(new ClassPathResource("xsd/trades.xsd"));
    return marshaller;
}
```

The schema must match the XML's namespace and version. If the XML source is untrusted, configure the parser securely and also check external entity handling; XSD validation does not replace parser hardening.

## 13. XML parser security and XXE

XML from external sources may contain DTDs or external entities. If the parser allows loading external entities, malicious XML data can cause the application to read local files or access unintended network resources (XXE).

When configuring the StAX `XMLInputFactory`, disable DTDs and external entities if the business logic does not need them:

```java
XMLInputFactory inputFactory = XMLInputFactory.newFactory();
inputFactory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
inputFactory.setProperty(
        XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES,
        false
);
```

If your version of `StaxEventItemReader` provides a setter for `XMLInputFactory`, pass the configured factory into the reader. Example:

```java
StaxEventItemReader<Trade> reader = new StaxEventItemReader<>();
reader.setName("tradeReader");
reader.setResource(resource);
reader.setFragmentRootElementName("trade");
reader.setUnmarshaller(tradeMarshaller);
reader.setXmlInputFactory(inputFactory);
reader.setSaveState(true);
```

The exact API name depends on the Spring Batch version. Some StAX providers may not support the same properties or may throw an exception when setting an unsupported property. Verify the actual configuration with tests against the production provider and enforce a fail-closed policy if external entities cannot be disabled per security requirements.

Do not enable DTD/external entities just to process a special file without evaluating the data source and the risk of external resource access. If XML needs to reference schemas, prefer locally managed schemas or a secure resolver configuration.

## 14. Checkpoint and restart

`StaxEventItemReader` supports saving state through the item-counting reader mechanism. When `saveState(true)` is set, the reader saves reading progress into the Step `ExecutionContext` so it can resume when the Job restarts for the same JobInstance.

Example:

```java
return new StaxEventItemReaderBuilder<Trade>()
        .name("tradeReader")
        .resource(resource)
        .addFragmentRootElements("trade")
        .unmarshaller(tradeMarshaller)
        .saveState(true)
        .build();
```

On restart:

1. Spring Batch creates a new StepExecution for the retry execution.
2. The reader reopens the XML resource and creates a new StAX event reader.
3. The reader reads the saved checkpoint from the ExecutionContext.
4. The reader skips the fragments already recorded in the item count to reach the resume position.
5. The reader returns the next fragment to the Step.

The old parser/event reader is not kept across process restarts. The reader must reopen the resource and reconstruct its position from the saved state.

Because checkpointing relies on the count of items/fragments read, the content and order of fragments in the file must remain stable between the initial run and the restart. If upstream replaces the file or adds/removes fragments at the beginning of the document, the old item count may point to a different record.

## 15. Resource and JobParameters must be stable

For input files that change per run, `@StepScope` is commonly used to inject the path:

```java
@Bean
@StepScope
public StaxEventItemReader<Trade> tradeReader(
        @Value("#{jobParameters['inputFile']}") String inputFile,
        Jaxb2Marshaller tradeMarshaller) {

    return new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReader")
            .resource(new FileSystemResource(inputFile))
            .addFragmentRootElements("trade")
            .unmarshaller(tradeMarshaller)
            .saveState(true)
            .build();
}
```

To restart with the right data:

- Keep the JobInstance's identifying JobParameters unchanged.
- Pass the same `inputFile` on restart if the file path is part of the input.
- Keep the file content unchanged; do not overwrite the file while the Job is processing it.
- Use a stable reader name so the checkpoint key does not change.
- Store a checksum/version/manifest if you need to verify the file is still the original version.
- Do not generate a new random temporary path or file name on restart if the checkpoint depends on the old content.

If files are dropped into an inbound directory, you can copy them to an immutable staging directory before launching the Job. After the Job completes, move the file to archive according to operational procedures.

## 16. Parse errors and unmarshal errors

Errors can occur at multiple stages:

| Stage | Example | Handling approach |
|---|---|---|
| Open resource | File does not exist, no read permission | Check path/permissions; fail fast if file is required |
| StAX parse | Non-well-formed XML, mismatched open/close tags | Fix XML source; usually fail because the parser cannot safely continue |
| Find fragment | Configured fragment root is absent | Check root element and file structure |
| Unmarshal | Unmappable element/attribute, wrong type | Check JAXB mapping, converters, and schema |
| Validation | XML violates XSD or business rules | Separate structural errors from business errors |

Do not configure broad skipping for all XML parse exceptions. If a document is malformed mid-file, the parser may not know how to resynchronize to the next fragment's position. Skip is more suitable for isolated data errors in a complete fragment where the parser can still continue.

If only one fragment has an invalid business value while the XML remains well-formed, you can let the unmarshaller create the object and have the processor validate it and throw a dedicated exception to apply a skip policy. This keeps XML parsing separate from business rules.

## 17. Combining retry and skip

The reader can participate in a fault-tolerant Step. However, distinguish transient resource/I/O errors from permanent XML errors:

- Transient filesystem/network errors can be retried if the reader can safely reopen the resource.
- Fragments that violate business rules can be skipped if the parser has already read the fragment and dropping the item is acceptable.
- Malformed XML that desynchronizes the parser should generally fail the Step.
- JAXB mapping errors caused by misconfiguration generally cannot recover automatically via retry.

Example Step with a skip policy for business exceptions from the processor:

```java
return new StepBuilder("importTradesStep", jobRepository)
        .<Trade, Trade>chunk(100, transactionManager)
        .reader(tradeReader)
        .processor(tradeValidationProcessor)
        .writer(tradeWriter)
        .faultTolerant()
        .skip(InvalidTradeException.class)
        .skipLimit(25)
        .build();
```

Here `InvalidTradeException` is thrown after the fragment has been mapped to `Trade`. Do not automatically skip `XMLStreamException` or every `UnmarshalException` without confirming the reader can safely continue.

## 18. Performance and memory management

StAX streaming avoids building a DOM for the entire file, but performance still depends on XML structure and object graphs:

- The larger the fragment, the more heap each item's object graph consumes.
- Large chunk sizes hold more objects before committing.
- JAXB mapping and XSD validation have CPU overhead.
- Namespaces, converters, and nested collections can increase mapping cost.
- Processors/writers may hold additional state or caches outside the reader.

When optimizing:

- Bind only the necessary elements to the model.
- Choose chunk size based on object size and transaction duration.
- Use explicit JAXB class bindings instead of complex dynamic mapping when the schema is stable.
- Measure heap, GC, throughput, and parse time using files near production size.
- Avoid holding the entire list of items in the processor or writer.
- Check the number of fragments and the maximum size of each fragment.

Do not assume StAX will solve every memory issue if a single fragment contains hundreds of thousands of child nodes or the processor accumulates all items in a collection.

## 19. When to use StaxEventItemReader instead of DOM or custom StAX?

| Reading approach | Characteristics | When appropriate |
|---|---|---|
| DOM | Loads document into an XML object tree | Small files, needing random/repeated access to the structure |
| `StaxEventItemReader` | Reads events sequentially and maps fragments to items | Large XML files with repeating record elements |
| Custom StAX reader | Manual control of events, state, and mapping | Complex structure, needing special streaming logic or lacking a stable fragment root |
| JAXB unmarshal whole document | Maps entire document into an object graph | Small/medium files, needing to process the document as a single unit |

`StaxEventItemReader` is a good choice when the XML has clear record boundaries. If each record is scattered across multiple locations in the document or requires aggregating state across multiple event branches, a custom reader may be a better fit.

## 20. Testing StaxEventItemReader

You should test the reader with XML fixtures representative of the real schema:

1. Valid XML with one fragment and with multiple fragments.
2. XML without the configured fragment root.
3. XML with a default namespace and with namespace prefixes.
4. XML with nested child elements or duplicate names at different levels.
5. Missing values, empty values, and invalid data types.
6. Malformed XML at the beginning, middle, and end of the file.
7. Missing resource and unreadable resource when strict is enabled.
8. Passing and failing XSD validation if the application enables validation.
9. Restart after several committed chunks with the same file and JobParameters.
10. Changing the file between the initial run and restart to verify input-change detection.
11. DTD/external entities rejected per parser security configuration.
12. Measuring heap and throughput with large files, large fragments, and expected chunk sizes.

Unit/integration tests can open the reader, call `read()` repeatedly, and assert that each fragment produces the right object. When testing `ItemStreamReader` directly, call `open(ExecutionContext)` before and `close()` after; in Job integration tests, Spring Batch manages that lifecycle.

Restart tests need a JobRepository that persists metadata between the two runs. If the repository or ExecutionContext is created fresh, the test does not prove that the checkpoint can be restored.

## 21. Common misconceptions

**Assuming the reader creates one item per XML line.** The reader creates an item for each configured fragment root element, which may span multiple lines of text and child elements.

**Assuming the document root is always the fragment root.** The document root is usually just a wrapper around the records. Choose the element that represents one business unit.

**Assuming StAX uses no memory.** StAX avoids a full-document DOM, but still needs parser buffers, fragment objects, and chunk items.

**Assuming `strict(true)` enables XSD validation.** Strict primarily checks resource existence; schema validation must be configured separately on the unmarshaller or in a validation step.

**Assuming JAXB mapping automatically determines the fragment root.** The reader must be configured with the fragment root; JAXB is responsible for mapping the extracted fragment.

**Assuming malformed XML can always be skipped.** The parser may lose synchronization after structural errors. Only skip isolated fragment errors when it is safe to continue.

**Assuming restart only needs `saveState(true)`.** The file, fragment order, reader name, and JobParameters must also be stable.

**Assuming disabling DTDs is an unimportant option.** Untrusted XML requires a hardened parser to prevent XXE and unintended external resource access.

## 22. How to design a Job that reads XML with StaxEventItemReader

Identify which element represents a business record and use that element as the fragment root. Create an appropriate JAXB/OXM model, configure the `Unmarshaller`, and declare the reader with a resource, stable name, and `saveState(true)`. Wire the reader into a chunk Step like a normal `ItemStreamReader`.

For files that vary per run, use `@StepScope` to inject JobParameters and keep files/parameters unchanged across restarts. Define namespaces clearly, validate schemas if needed, and disable DTDs/external entities for untrusted XML. Only skip isolated data errors when the parser can still continue; malformed XML or mapping configuration errors should be treated as failures to fix.

StaxEventItemReader fits large XML files with repeating record structures and clear fragment boundaries. Properly combining streaming, unmarshalling, checkpointing, and resource management helps the Job read XML item-by-item, save memory compared to full DOM loading, and support restartable batch processing.
