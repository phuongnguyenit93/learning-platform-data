# JdbcPagingItemReader

In Spring Batch, JdbcPagingItemReader<T> reads data from a database page by page using SQL statements generated by a PagingQueryProvider. Instead of keeping a JDBC cursor open throughout the entire reading process, the reader queries a batch of records, holds the current page to return items to the chunk, and queries the next page when needed.

This reader is suitable when you need to read a large dataset from a database, want to limit the amount of data loaded into memory per query, and need restart capability based on sort keys. It is typically used with JdbcPagingItemReaderBuilder, PagingQueryProvider, RowMapper<T>, and a DataSource.

The most important point when using paging is that the ordering must be stable. The query needs a deterministic and preferably unique sort key, or a combination of sort keys that forms a unique key. Spring Batch uses the sort key values to build queries for subsequent pages and stores the read position in the ExecutionContext. If the ordering is unstable, data may be read twice or skipped, especially when a job restarts or the source data changes during execution.

## 1. How does JdbcPagingItemReader work?

JdbcPagingItemReader executes paginated queries through a PagingQueryProvider. The provider generates SQL tailored to the database management system based on the select, from, where, sort keys, and other configuration parts.

General processing flow:

~~~mermaid
flowchart TD
    A[Step opens JdbcPagingItemReader] --> B[Read first page]
    B --> C[PagingQueryProvider generates SQL]
    C --> D[Database returns page]
    D --> E[RowMapper converts ResultSet to object]
    E --> F[Reader returns each item to chunk]
    F --> G{Any items left in page?}
    G -- Yes --> F
    G -- No --> H[Read next page by sort key]
    H --> C
    F --> I[Chunk commits and saves checkpoint]
    I --> G
~~~

For example, a customer table has millions of records. The reader can fetch 500 records per query, map each row to a Customer, and pass them to the processor/writer according to the step's commit interval.

pageSize controls the number of records in a single page. chunkSize controls the number of items processed in a single chunk transaction. These two values are related in terms of performance, but they are not the same concept.

## 2. When should you use JdbcPagingItemReader?

This reader is generally suitable when:

- Data resides in a relational database and can be queried with filter conditions.
- The dataset is large and you do not want to load all results into memory.
- There is a stable sort key to step through pages.
- You want to support restart using checkpoints stored in the ExecutionContext.
- You need to bound queries by ID range, business date, status, or batch key.

Cases where other readers should be considered:

| Requirement | Potentially suitable option |
|---|---|
| Sequential reading of a large result set in one cursor | JdbcCursorItemReader |
| Reading page by page and needing sort-key-based restart | JdbcPagingItemReader |
| Source is a text file | FlatFileItemReader |
| Data is partitioned and each worker has its own query | JdbcPagingItemReader in a step-scoped worker |
| Specialized query or reading protocol not fitting a provider | Custom ItemReader or specialized reader |

Paging generally avoids keeping a JDBC cursor open for the entire processing duration. In return, the reader executes multiple queries per page and requires an accurate sort/restart strategy.

## 3. PagingQueryProvider and database-specific SQL

PagingQueryProvider defines how queries are generated for the first page and subsequent pages. Spring Batch provides database-specific implementations, such as for PostgreSQL, MySQL, Oracle, SQL Server, DB2, and several other systems.

You can use SqlPagingQueryProviderFactoryBean to let Spring Batch choose the appropriate provider based on the DataSource:

~~~java
@Bean
PagingQueryProvider customerPagingQueryProvider(
        DataSource dataSource) throws Exception {

    SqlPagingQueryProviderFactoryBean factory =
            new SqlPagingQueryProviderFactoryBean();
    factory.setDataSource(dataSource);
    factory.setSelectClause(
            "select id, first_name, last_name, status");
    factory.setFromClause("from customer");
    factory.setWhereClause("where status = :status");

    Map<String, Order> sortKeys = new LinkedHashMap<>();
    sortKeys.put("id", Order.ASCENDING);
    factory.setSortKeys(sortKeys);

    return factory.getObject();
}
~~~

Main parts:

- selectClause: columns to read; must include the columns used as sort keys.
- fromClause: source table or expression.
- whereClause: filter conditions; can use named parameters.
- sortKeys: columns and sort directions used to determine paging order.
- dataSource: helps the factory identify the database and create the matching provider.

The provider generates paging SQL according to the database dialect. SQL syntax for the first page and subsequent pages can differ across database systems. Therefore, use the corresponding provider instead of manually concatenating LIMIT, OFFSET, ROWNUM, or custom pagination syntax inside the reader.

Do not arbitrarily add ORDER BY into the whereClause. Paging order is declared via sort keys so the provider can consistently generate subsequent queries.

## 4. Sort keys must be deterministic and stable

Sort keys are the foundation of paging. The reader needs to know the last record read in the previous page to query the next records. If the sort key does not produce a unique ordering, two rows with the same sort key value can sit on a page boundary and make results non-deterministic.

Unsafe example:

~~~sql
select id, customer_id, status
from orders
where status = :status
order by status
~~~

If multiple rows share the same status, this sort key cannot distinguish their order. You should use a unique key like id.

~~~sql
select id, customer_id, status
from orders
where status = :status
order by id
~~~

In PagingQueryProvider, declare:

~~~java
Map<String, Order> sortKeys = new LinkedHashMap<>();
sortKeys.put("id", Order.ASCENDING);
factory.setSortKeys(sortKeys);
~~~

A sort key should satisfy:

- Produces a total order, meaning each row has a deterministic position.
- Remains stable for the duration of the job's reading.
- Is present in the select clause so the reader can track its value.
- Does not contain null values if the provider/database cannot compare them consistently.
- Is backed by an appropriate index if the dataset is large.

An ascending primary key is usually a good choice. If using a non-unique column, add a tie-breaker key to the sort keys.

## 5. Composite sort keys

Sometimes no single column matches the desired ordering. You can use multiple sort keys to create a deterministic order, such as created_at and id.

~~~java
Map<String, Order> sortKeys = new LinkedHashMap<>();
sortKeys.put("created_at", Order.ASCENDING);
sortKeys.put("id", Order.ASCENDING);
factory.setSortKeys(sortKeys);
~~~

The order above means sorting by created_at, then using id to distinguish records with the same timestamp. The combination (created_at, id) must be unique within the dataset being read.

With a composite key, the provider builds the condition for the next page based on the sort key values in exact order. Conceptual example logic:

~~~sql
where created_at > :lastCreatedAt
   or (created_at = :lastCreatedAt and id > :lastId)
order by created_at asc, id asc
~~~

This illustrates keyset paging logic, not fixed SQL used for every database. The specific provider generates the appropriate syntax.

If columns have different sort directions, such as created_at DESC and id ASC, declare each direction in the map and inspect the query generated by the provider against the target database.

## 6. Basic JdbcPagingItemReader configuration

After creating the query provider, you can build the reader using JdbcPagingItemReaderBuilder:

~~~java
@Bean
@StepScope
JdbcPagingItemReader<Customer> customerReader(
        DataSource dataSource,
        PagingQueryProvider customerPagingQueryProvider,
        @Value("#{jobParameters['status']}") String status) {

    return new JdbcPagingItemReaderBuilder<Customer>()
            .name("customerReader")
            .dataSource(dataSource)
            .queryProvider(customerPagingQueryProvider)
            .parameterValues(Map.of("status", status))
            .pageSize(500)
            .fetchSize(500)
            .rowMapper((rs, rowNum) -> new Customer(
                    rs.getLong("id"),
                    rs.getString("first_name"),
                    rs.getString("last_name"),
                    rs.getString("status")))
            .saveState(true)
            .build();
}
~~~

In this example:

- name is the reader's name, used in metadata/checkpoints; it must be unique within the appropriate step/job scope.
- dataSource is the database connection source.
- queryProvider supplies the paging SQL.
- parameterValues passes values for named parameters in the where clause.
- pageSize sets the number of rows per page.
- fetchSize is a hint to the JDBC driver on how many rows to fetch in one retrieval.
- rowMapper maps each ResultSet row into a Customer.
- saveState(true) enables saving state for restart.

The reader bean is usually declared @StepScope when late binding from JobParameters or StepExecutionContext is needed. Do not share a single open reader across multiple independent StepExecutions.

## 7. RowMapper converts ResultSet to object

After the query returns a page, RowMapper<T> is invoked for each row to create an object. This is the mapping layer from a JDBC ResultSet to a Java type; it differs from FieldSetMapper, which is used for file data.

Example:

~~~java
public class CustomerRowMapper implements RowMapper<Customer> {

    @Override
    public Customer mapRow(ResultSet rs, int rowNum)
            throws SQLException {
        return new Customer(
                rs.getLong("id"),
                rs.getString("first_name"),
                rs.getString("last_name"),
                rs.getString("status"));
    }
}
~~~

You can use BeanPropertyRowMapper if column names map cleanly to JavaBean properties:

~~~java
BeanPropertyRowMapper<Customer> mapper =
        new BeanPropertyRowMapper<>(Customer.class);
~~~

If the database uses first_name while the object has property firstName, BeanPropertyRowMapper typically supports underscore-to-camel-case conversion. For complex mappings, immutable constructors, or special data types, a custom RowMapper is usually clearer.

Do not place business logic such as checking quotas or calling APIs inside RowMapper. The mapper should focus on converting data from ResultSet into an object. Business validation belongs in the processor/service downstream of the reader.

## 8. Named parameters and parameterValues

JdbcPagingItemReader supports passing values for named parameters declared in the query provider. Example:

~~~java
factory.setWhereClause(
        "where status = :status and created_at < :cutoff");
~~~

When building the reader:

~~~java
Map<String, Object> parameters = new HashMap<>();
parameters.put("status", status);
parameters.put("cutoff", cutoffTimestamp);

return new JdbcPagingItemReaderBuilder<Customer>()
        .name("customerReader")
        .dataSource(dataSource)
        .queryProvider(queryProvider)
        .parameterValues(parameters)
        .pageSize(500)
        .rowMapper(customerRowMapper)
        .saveState(true)
        .build();
~~~

Parameter binding helps the database handle values with proper types and reduces the risk of SQL injection. Do not concatenate user values directly into whereClause.

Table names, column names, and sort directions are usually SQL structure, not bind parameters. If you need to choose query structure based on input, use a known configuration whitelist instead of arbitrary string concatenation.

When using JobParameters as filter conditions, consider whether they should be identifying parameters. Parameters that define the business dataset should generally participate in identifying the JobInstance so that a restart does not accidentally read a different dataset.

## 9. Page size, chunk size, and fetch size

These three settings serve different roles:

| Setting | Controls | Primary impact |
|---|---|---|
| pageSize | Number of rows queried in one page | Query frequency and amount of data the reader holds for the current page |
| chunkSize | Number of items processed in one chunk transaction | Commit frequency and rollback scope |
| fetchSize | Hint to the JDBC driver for rows fetched from database per trip | How the driver retrieves data over JDBC |

Example configuration:

~~~java
new JdbcPagingItemReaderBuilder<Customer>()
        .pageSize(500)
        .fetchSize(500)
        // Step uses chunk(100, transactionManager)
        .build();
~~~

pageSize and chunkSize are often set close to or equal to each other to avoid loading too many unused rows and to reduce query count. However, this is a performance decision, not a strict requirement. If page size is larger than chunk size, the reader may hold the remainder of the page across multiple chunks. If page size is smaller than chunk size, a single chunk may require data from multiple pages.

fetchSize is a hint to the JDBC driver; drivers and databases may interpret it differently. Do not assume fetchSize always equals the number of rows returned in a page. Measure query time, memory, network round trips, and page load frequency.

## 10. Checkpoint and restart

When saveState(true) is set, the reader writes the necessary information into ExecutionContext so it can resume after a job fails or stops. For a paging reader, the read state is tied to the sort key of the item processed up to the checkpoint.

On the first run:

1. The reader queries the first page.
2. The reader returns items for the chunk.
3. The chunk commits.
4. Spring Batch updates the checkpoint in the execution context.
5. When a new page is needed, the reader continues from the last read sort key value.

On restart:

1. Spring Batch opens the reader with the saved execution context.
2. The reader restores its position based on the sort key/checkpoint.
3. The next query fetches records after the committed position.
4. Already committed chunks do not need to be reprocessed under the normal restart mechanism.

For restart to work properly:

- Set saveState(true) if checkpointing is needed.
- Give the reader a stable and unique name.
- Use a stable, preferably unique sort key.
- Keep filter conditions and the meaning of JobParameters identical to the initial run.
- Do not arbitrarily change sort order or query structure between the initial run and restart.
- Ensure the source data is not modified in a way that invalidates the checkpoint's consistency.

If saveState(false) is set, the reader does not save state for restart. This can fit certain multi-threaded client scenarios or jobs that accept restarting from scratch, but you must clearly understand the risk of re-reading and duplicate side effects.

## 11. Why do sort keys affect restart?

Suppose the reader has processed up to id=5000 and the checkpoint is committed. Upon restart, the next query needs to fetch records after that key. If the sort key is a unique id, the continuation condition can be clearly determined.

If the sort key is only status, many rows share the same value. The checkpoint cannot accurately distinguish which rows within the same status group have already been processed. This can cause some rows to be duplicated or skipped.

With a composite key (created_at, id), the checkpoint retains enough values to identify the position in the order. You must ensure this combination is unique and does not change while the job runs.

Do not use a mutable column such as priority or status as a sort key if records can change that value during paging. An already-read row could move to a position before or after the checkpoint, altering the dataset of the next page.

## 12. Source data changing while the job is paging

Paging queries are executed multiple times. If transactions/chunks see data at different points in time, the dataset can change between two pages:

- A newly inserted row with a sort key smaller than the checkpoint may not be read.
- A newly inserted row with a sort key larger than the checkpoint may appear on a later page even though it did not exist when the job started.
- An already-read row that is deleted or updated in its filter criteria may cause the result to no longer reflect the initial snapshot.
- Changing a sort key may cause a row to move across the checkpoint boundary.

If business logic requires processing a stable snapshot, clearly define the dataset boundary. Some approaches:

- Capture a high-water mark before reading, e.g., id <= maxIdAtStart.
- Filter by an immutable batch ID or business date.
- Read from a staging/snapshot table frozen for that run.
- Use an isolation level or snapshot semantics appropriate for the database and processing duration.
- Do not update columns used as sort keys while the job is reading.

Do not assume Spring Batch's chunk transactions create a snapshot across the entire job. Each chunk can commit independently, so snapshot consistency must be designed according to the database and business requirements.

## 13. Indexes and query performance

A paging reader executes multiple queries based on filter conditions and sort keys. If the query lacks a suitable index, each page can incur expensive scans or sorts.

Example query:

~~~sql
select id, customer_id, status, created_at
from orders
where status = :status
  and id > :lastId
order by id
~~~

Indexes should be evaluated according to filter conditions and sort order. Depending on the database, a composite index (status, id) may be more useful than separate indexes on status or id, though the decision should be based on actual query plans and data distribution.

Metrics to measure:

- Execution time of the first page query and subsequent page queries.
- Number of rows the database must scan to return one page.
- Whether the sort operation spills to disk.
- Index hit rate and buffer/cache behavior.
- Connection acquisition time.
- Network round trips and row size.
- Mapping time per page.

Avoid picking an overly large page size just to reduce query count. Large pages can increase memory usage, query duration, transaction hold time, and latency before the first item is processed.

## 14. Reader and transaction boundaries

JdbcPagingItemReader uses the DataSource to execute queries. When the datasource participates in the step-managed transaction, other database operations on the same thread may participate in the transaction depending on transaction manager configuration.

However, a paging reader does not mean the entire job runs in a single transaction. Chunks still have their own transactions based on the commit interval. The reader may query multiple pages across multiple chunks; checkpoints are saved at commit boundaries according to Spring Batch's mechanism.

Notes:

- Use the same DataSource with the step's transaction manager if the same transaction is needed.
- Do not share the JDBC Connection or ResultSet outside the reader.
- Do not keep a transaction open across the entire job just to freeze a snapshot if it causes locks or holds connections too long.
- Check isolation levels and database behavior when concurrent updates occur.
- If the reader queries one datasource while the writer writes to another, clearly define consistency and recovery mechanisms.

If the reader and writer access the same table, verify whether the writer updating filter columns or sort keys affects subsequent pages.

## 15. Reading data by JobParameters

A batch job often reads data by parameters such as business date, status, or batch ID. Parameters can be bound on a step-scoped reader:

~~~java
@Bean
@StepScope
JdbcPagingItemReader<Order> orderReader(
        DataSource dataSource,
        PagingQueryProvider orderQueryProvider,
        @Value("#{jobParameters['businessDate']}") String businessDate) {

    LocalDate date = LocalDate.parse(businessDate);
    Timestamp start = Timestamp.valueOf(date.atStartOfDay());
    Timestamp end = Timestamp.valueOf(date.plusDays(1).atStartOfDay());

    Map<String, Object> parameters = Map.of(
            "startTime", start,
            "endTime", end);

    return new JdbcPagingItemReaderBuilder<Order>()
            .name("orderReader")
            .dataSource(dataSource)
            .queryProvider(orderQueryProvider)
            .parameterValues(parameters)
            .pageSize(300)
            .rowMapper(orderRowMapper())
            .saveState(true)
            .build();
}
~~~

Corresponding query provider:

~~~java
factory.setWhereClause(
        "where created_at >= :startTime and created_at < :endTime");
~~~

Using a half-open interval [start, end) avoids millisecond/nanosecond boundary errors at day transitions and prevents a record from belonging to two consecutive days. Always use a consistent business timezone when converting LocalDate to timestamp.

If businessDate defines the JobInstance's dataset, it should be an identifying JobParameter. On restart, reuse the same value so the query does not change scope.

## 16. Partitioning with JdbcPagingItemReader

For very large datasets, you can split into partitions by ID range. Each worker has its own StepExecution and ExecutionContext, allowing a step-scoped JdbcPagingItemReader per partition.

Example worker reader:

~~~java
@Bean
@StepScope
JdbcPagingItemReader<Order> partitionOrderReader(
        DataSource dataSource,
        PagingQueryProvider partitionQueryProvider,
        @Value("#{stepExecutionContext['minId']}") Long minId,
        @Value("#{stepExecutionContext['maxIdExclusive']}") Long maxIdExclusive) {

    Map<String, Object> parameters = Map.of(
            "minId", minId,
            "maxIdExclusive", maxIdExclusive);

    return new JdbcPagingItemReaderBuilder<Order>()
            .name("partitionOrderReader")
            .dataSource(dataSource)
            .queryProvider(partitionQueryProvider)
            .parameterValues(parameters)
            .pageSize(500)
            .rowMapper(orderRowMapper())
            .saveState(true)
            .build();
}
~~~

Query provider:

~~~java
factory.setWhereClause(
        "where id >= :minId and id < :maxIdExclusive");
~~~

The partitioner must produce non-overlapping ranges that cover the exact dataset to be read. For example, [1, 1001), [1001, 2001), and [2001, 3001) do not overlap. Each worker has its own reader and checkpoint, making it easier to control restarting individual partitions.

When running partitioning, balance partition size, worker count, and connection pool capacity. Many partitions querying the database simultaneously can increase load; indexes on range/sort keys are critical.

## 17. Multi-threaded clients and thread safety

JdbcPagingItemReader has a thread-safety characteristic worth noting: the reader is described as thread-safe between calls to open(ExecutionContext). However, when used in a multi-threaded client, you must set saveState=false; in that mode there is no reader checkpoint to restart from saved state.

This does not mean every way of sharing a reader across threads yields the same item ordering or restart semantics. In a multi-threaded step, multiple workers may pull items in non-deterministic order; if the application needs independent checkpoints, partitioning is usually easier to control because each worker has its own reader and StepExecution.

Do not use a single open reader across multiple independent JobExecutions. If readers receive different JobParameters, create the target bean with StepScope so each execution has its own configuration and lifecycle.

When parallelism is needed:

- Prefer partitioning with clear ranges/keys if per-worker restart is required.
- Use saveState=false only when accepting the lack of reader restart state in a multi-threaded client model.
- Verify that the writer and processor are thread-safe; a thread-safe reader does not automatically make the entire pipeline safe.
- Limit worker count according to database capacity and connection pool size.

## 18. saveState, name, and restart limitations

When saveState is enabled, the reader writes state into ExecutionContext. The reader name is used to create a stable metadata key. If multiple readers exist in the same step, each needs a distinct name.

Example:

~~~java
new JdbcPagingItemReaderBuilder<Order>()
        .name("orderPagingReader")
        .saveState(true)
        // other configurations
        .build();
~~~

If you rename the reader between the initial run and restart, the framework may fail to find the old checkpoint under the expected key. If you change the query, sort keys, or filter conditions on restart, the old checkpoint may no longer represent the same position in the dataset.

saveState(false) is appropriate for readers used in environments that do not support restart state or when the application deliberately accepts re-reading. Do not disable saveState merely to bypass a checkpoint error without understanding the cause; doing so can make the job restart from the beginning and produce duplicate side effects.

## 19. Handling duplicates and changes in the read dataset

A unique sort key guarantees ordering, but does not by itself solve all duplicate data issues. If the source table contains business duplicates, the reader will still read both rows unless the query filters or groups them.

If the source can be updated while the job is running:

- Avoid mutable sort keys.
- Establish a high-water mark at start time.
- Use stable filter conditions by batch/version.
- If an exact snapshot is needed, create a snapshot or staging set.
- Use a unique business key in the writer to prevent duplicates on restart/replay.

If the reader fetches by ascending id and a new row is inserted with an ID greater than the checkpoint, it may appear on a later page. If business rules prohibit picking up data created after the job starts, guard against it with maxIdAtStart or a batch cutoff.

## 20. Comparison with JdbcCursorItemReader

| Criterion | JdbcPagingItemReader | JdbcCursorItemReader |
|---|---|---|
| Reading approach | Queries page by page | Iterates ResultSet/cursor |
| Connection/cursor | Does not need to hold a single cursor throughout the entire read | Typically holds cursor/connection during reading |
| Pagination | Requires PagingQueryProvider and sort keys | Does not require a paging query provider |
| Restart | Based on state/checkpoint and sort key | Based on cursor reader position/state |
| SQL | Provider generates queries per database dialect | Query is usually a single fixed SQL statement |
| Performance | Multiple queries; fits paging with good indexes | Can be efficient for sequential reads if driver/database supports cursors well |
| Changing data | Pages may see changes depending on transaction/isolation | Results depend on cursor and transaction/driver |

Neither reader is always faster. Benchmark on your actual database, driver, row size, record count, and workload. If subsequent page queries are expensive due to missing indexes, paging can be slower than a cursor. If you do not want to hold cursors long or need sort-key-based restart, paging may be more suitable.

## 21. Testing JdbcPagingItemReader

Testing should cover paging queries, mapping, checkpoints, and restarts:

1. First page: verify the first page has the correct data and count.
2. Next page: verify subsequent pages have no duplicates and no skipped rows.
3. Sort key uniqueness: create multiple rows sharing the primary sort key value and confirm the composite key still produces a deterministic order.
4. Parameter binding: verify named parameters filter the dataset accurately.
5. RowMapper: verify numeric, date, null, and column aliases are mapped properly.
6. Page/chunk sizing: test with page size smaller than, equal to, and larger than chunk size.
7. Restart: stop the job after several committed chunks then restart with the same JobParameters; confirm no items are duplicated or skipped.
8. Source mutation: insert/delete/update records between pages to verify snapshot/cutoff policy.
9. Partitioning: verify ranges do not overlap and combined results match the expected input set.
10. Performance: measure query plans, index usage, page latency, memory, and connection usage.

Example testing the reader directly:

~~~java
ExecutionContext context = new ExecutionContext();
reader.open(context);

List<Customer> actual = new ArrayList<>();
Customer item;
while ((item = reader.read()) != null) {
    actual.add(item);
}

reader.close();

assertEquals(expectedCustomerIds, actual.stream()
        .map(Customer::id)
        .toList());
~~~

To test restart, you must preserve the ExecutionContext updated at commit boundaries, close the reader, create a new reader with the same configuration, and call open(context) on the saved state. Actual step/job integration tests are more valuable than testing the reader alone when verifying transaction and checkpoint coordination.

## 22. Common mistakes

**Omitting sort keys.** The provider lacks a stable paging order. Declare sort keys explicitly.

**Using a non-unique sort key.** Multiple rows with the same value can cause duplicates or gaps at page boundaries. Use a primary key or unique composite key.

**Sort key changes while the job runs.** Rows can move across the checkpoint. Use stable keys or snapshots/cutoffs.

**Confusing pageSize with chunkSize.** Page size is the number of rows per query; chunk size is the number of items per transaction. Choose and measure separately.

**Assuming fetchSize controls page row count.** Fetch size is a JDBC hint; page size is what configures the row count of the paging query.

**Concatenating parameters directly into SQL.** Prone to SQL injection and quoting errors. Use named parameters with parameterValues.

**Omitting sort keys from the select clause.** The reader/provider needs key values to determine the next position. Select all required columns.

**Changing query or reader name on restart.** Old checkpoints may become incompatible. Keep configuration and names stable.

**Disabling saveState while expecting restart.** There is no reader checkpoint to resume at the exact position. Disable only when accepting this limitation.

**Sharing a reader across multiple executions.** An open reader holds its own state. Use StepScope and dedicated worker readers.

**Not creating indexes for filter/sort.** Each page may scan/sort large amounts of data. Check query plans and indexes.

**Assuming paging creates a job-wide snapshot.** Pages can run across different transactions/times. Use cutoffs or snapshots when consistency is required.

## 23. Implementation workflow

When building a JdbcPagingItemReader, you can follow this order:

1. Define the dataset and filter conditions for the job.
2. Select columns to read and a RowMapper to create objects.
3. Choose a stable, unique sort key; use a composite key if needed.
4. Configure PagingQueryProvider according to the DataSource and SQL dialect.
5. Bind named parameters via parameterValues.
6. Choose pageSize, fetchSize, and chunkSize based on benchmarks.
7. Set a stable reader name and enable saveState if restart is required.
8. Use StepScope when the reader depends on JobParameters or partition context.
9. Determine whether source data can change during reading; add a cutoff/snapshot if needed.
10. Test paging, composite sorting, restart, partitioning, and performance on the target database.

## Conclusion

JdbcPagingItemReader reads database data page by page through a PagingQueryProvider. The provider generates SQL suited to the database, RowMapper converts each row into an object, and the reader passes items to the chunk step. pageSize determines rows per page; chunkSize determines the transaction commit interval; fetchSize is a hint to the JDBC driver.

For reliable paging and restart, use a stable and unique sort key, or a composite key forming a total order; keep the reader name, query, and identifying parameters stable across restarts; and enable saveState when checkpointing is needed. If the source can change while reading, define a business cutoff or snapshot. For parallel processing requiring independent restarts, partitioning with a step-scoped reader per worker is generally easier to control than sharing a reader in a multi-threaded client. Test against a real database and measure query plans, page latency, memory, and connection usage before finalizing production configuration.
