# The `http-response` Snippet and Returned Status Codes

## 1. Lesson Objectives

In the **HTTP operation** chapter of `SPRING_REST_DOCS`, each HTTP test can record a **request–response** pair. The request describes what the client sent; the response shows what **HTTP status code, headers, and body** the server actually returned. Spring REST Docs uses the recorded data to generate API documentation, where `http-response.adoc` is the snippet presenting an entire HTTP response in a readable format.

This topic belongs to the workflow of **generating verifiable REST API documentation from tests** using MockMvc, WebTestClient, or REST Assured. After generating request, response, payload, parameter, and header snippets, teams can include them in Asciidoctor or a correspondingly configured Markdown workflow, running automatically in build/CI.

After this lesson, you will be able to:

- Read an `http-response` and identify the status code, reason phrase, headers, and body.
- Understand status groups `1xx` through `5xx`, especially `200`, `201`, `202`, `204`, `400`, `404`, and `500`.
- Write tests that verify status, headers, and body before generating snippets.
- Distinguish `http-response` from `http-request`, `response-body`, `response-headers`, and `response-fields`.
- Author documentation from generated snippets and control documentation updates in CI.

## 2. Structure of the `http-response` Snippet

Suppose a `GET /api/books/42` request succeeds and the API returns the book with ID `42`. The `http-response.adoc` generated by Spring REST Docs **might** look like the following example:

~~~http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{"id":42,"title":"Spring in Action"}
~~~

This is an **illustrative example**, not content guaranteed to appear character-for-character on every system. Header order and presence, charset, `Content-Length`, reason phrase, or JSON formatting depend on the actual response and snippet processing configuration.

| Component | Example | How to interpret |
| --- | --- | --- |
| Status line | `HTTP/1.1 200 OK` | HTTP version shown in the snippet, status code `200`, and reason phrase `OK`. |
| Status code | `200` | The most important numeric value for classifying the HTTP result. |
| Reason phrase | `OK` | Helper text for human readers; do not rely on it to verify logic. |
| Response header | `Content-Type: application/json` | Representation format of the response body. |
| Response header | `Cache-Control: no-store` | Caching directive sent by the server. |
| Blank line | Between headers and body | Visual boundary between metadata and payload. |
| Response body | `{"id":42,"title":"Spring in Action"}` | Content returned by the API in the tested operation. |

**Key point:** `http-response` records the **actual response of a test operation**. Spring REST Docs does not infer the response from `@ResponseStatus`, controller method names, text written in docs, or a developer's intended output. If the test actually receives `404`, the snippet will show `404`; only when an assertion requires `200` will the test catch the discrepancy.

Additionally, the HTTP response itself **does not contain the request's HTTP method**. To know whether this `200 OK` corresponds to `GET`, `POST`, or another method, check the test, endpoint description, or the accompanying `http-request` snippet.

### Status Line and HTTP Version

The `HTTP/1.1 200 OK` format commonly seen in REST Docs documentation is a **human-readable representation**. Over HTTP/2 and HTTP/3, responses are encoded differently, using the status value corresponding to the `:status` pseudo-header without an HTTP/1.1-style status line reason phrase. Therefore, do not assume production infrastructure only runs HTTP/1.1 just because the snippet shows that line.

For automated testing, verify the **numeric code** (e.g., `200`), **required headers**, and **body structure**. The reason phrase is only for display assistance.

## 3. Understanding HTTP Status Code Groups

A status code is a three-digit integer. The first digit indicates the result category:

| Group | General meaning | Examples |
| --- | --- | --- |
| `1xx` | Informational response; protocol processing is continuing | `100 Continue`, `101 Switching Protocols` |
| `2xx` | Request was successfully processed according to the semantics of the status | `200 OK`, `201 Created`, `202 Accepted`, `204 No Content` |
| `3xx` | Redirection, cache usage, or further action needed to fulfill the request | `301 Moved Permanently`, `302 Found`, `304 Not Modified`, `307 Temporary Redirect` |
| `4xx` | Client request cannot be fulfilled under current conditions | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found` |
| `5xx` | Server or intermediary layer encountered a problem fulfilling the request | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable` |

Do not interpret "`2xx` means nothing went wrong" too broadly. For instance, `202 Accepted` confirms the **processing request was accepted**, not that asynchronous work has completed. Similarly, `304 Not Modified` belongs to `3xx` but is meant to reuse a cached copy rather than simply redirecting to another URL.

### Common Statuses in REST APIs

| Status | Common scenario | Additional checks to consider |
| --- | --- | --- |
| `200 OK` | Successfully fetching a resource; updates or other operations with a response body | `Content-Type` and key body fields. |
| `201 Created` | New resource created successfully | Resource ID, body if returned by the API, and `Location` if specified by the contract. |
| `202 Accepted` | Asynchronous task accepted for processing | Task ID, progress-checking endpoint, or callback mechanism if any. |
| `204 No Content` | Deletion/update succeeded with no body returned | Verify status `204` and an empty body. |
| `301/308` | Permanent redirect | `Location` header and redirect semantics for the HTTP method. |
| `302/307` | Temporary redirect | `Location` header; note `307` requires preserving the method when redirecting. |
| `304 Not Modified` | Conditional cache check indicates representation has not changed | Relevant cache headers; response has no body. |
| `400 Bad Request` | Malformed request syntax or input data fails contract validation | Error code, message, and field error details if defined by the API. |
| `401 Unauthorized` | Missing or invalid authentication credentials | How the client re-authenticates; `WWW-Authenticate` header when applicable. |
| `403 Forbidden` | Server refuses to authorize access | Authorization contract and error message format. |
| `404 Not Found` | Resource not found at the requested URI | Error structure and policy on whether to disclose resource existence. |
| `409 Conflict` | Conflict with the current state of the resource | Cause of the conflict and how the client should resolve it. |
| `415 Unsupported Media Type` | Request body has an unsupported media type | Request `Content-Type` values accepted by the API. |
| `422 Unprocessable Content` | Request content is understood syntactically but cannot be processed semantically | Business or validation error details per the API contract. |
| `429 Too Many Requests` | Rate/frequency limit exceeded | `Retry-After` if provided by the server. |
| `500 Internal Server Error` | Server error not described more specifically | Safe error info without exposing stack traces/secrets. |
| `503 Service Unavailable` | Service temporarily unavailable | `Retry-After` if present and client retry guidance. |

Which code is "correct" depends on the **API contract**. A creation API might return `201`, while an asynchronous job endpoint might return `202`; there is no universal rule that every `POST` must return `201`.

### Common Points of Confusion

1. **`200` vs. `204`:** both indicate success, but `204` has no response body. Do not document `204` with a JSON payload.
2. **`201` vs. `202`:** `201` reports that a resource has been created; `202` only reports that the request was accepted for processing.
3. **`401` vs. `403`:** `401` relates to authentication; `403` relates to the server refusing to execute the request. An API may intentionally return `404` to avoid disclosing a resource's existence.
4. **`400` vs. `422`:** the boundary depends on API design and published contracts; stay consistent rather than choosing arbitrarily.
5. **`204`, `304`, and `HEAD` responses:** contain no response body under HTTP semantics. These cases must not generate a `responseFields` table describing an imaginary payload.
6. **`500` is not by default an error branch to document as a business example:** only document controlled scenarios with a clear contract, and ensure responses do not leak internal details.

## 4. Generating `http-response` with MockMvc

### 4.1. Project Setup

The example uses Spring Boot 3.x, JUnit 5, and Java 17+, with a Spring MVC application that already exposes `GET /api/books/{id}`. Illustrative test dependencies in Gradle:

~~~groovy
dependencies {
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.restdocs:spring-restdocs-mockmvc'
}
~~~

Assume stable test data and that `GET /api/books/42` returns `200 OK` with JSON containing **exactly two fields**, `id` and `title`, as follows:

~~~json
{"id":42,"title":"Spring in Action"}
~~~

The real endpoint or test fixture must ensure this data exists. Spring REST Docs **does not create endpoints or dummy data on its own**. Managing the Spring REST Docs version should follow the project's dependency management/BOM.

### 4.2. The First Test and Snippet

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.restdocs.AutoConfigureRestDocs;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.HttpHeaders;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.restdocs.headers.HeaderDocumentation.headerWithName;
import static org.springframework.restdocs.headers.HeaderDocumentation.responseHeaders;
import static org.springframework.restdocs.mockmvc.MockMvcRestDocumentation.document;
import static org.springframework.restdocs.payload.PayloadDocumentation.fieldWithPath;
import static org.springframework.restdocs.payload.PayloadDocumentation.responseFields;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
class BookApiDocumentationTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void documentGetBookSuccess() throws Exception {
        mockMvc.perform(get("/api/books/42")
                .accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isOk())
            .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
            .andExpect(jsonPath("$.id").value(42))
            .andExpect(jsonPath("$.title").value("Spring in Action"))
            .andDo(document("books-get-one",
                responseHeaders(
                    headerWithName(HttpHeaders.CONTENT_TYPE)
                        .description("Media type of the response body")
                ),
                responseFields(
                    fieldWithPath("id").description("Book identifier"),
                    fieldWithPath("title").description("Book title")
                )
            ));
    }
}
~~~

In this example:

- `@AutoConfigureRestDocs(outputDir = "build/generated-snippets")` configures the snippet output location for MockMvc when using Spring Boot's REST Docs integration.
- `get("/api/books/42")` invokes the operation to document; the server under test determines the response.
- `andExpect(status().isOk())` verifies status **200**; `contentTypeCompatibleWith` and `jsonPath` verify additional key parts of the response contract.
- `andDo(document("books-get-one", ...))` records the operation and generates snippets under the identifier `books-get-one`.
- `responseHeaders(...)` documents the `Content-Type` header; `responseFields(...)` documents the two JSON fields and verifies that the payload description matches the response under normal strict mode.

Because `andDo(...)` comes after `andExpect(...)` in this call chain, if an assertion fails, the documentation generation step at the end of the chain **is not executed**. That is a common way to ensure documentation is only updated once expected behavior has been verified.

### 4.3. Generated Files and `http-response.adoc` Example

When the test passes, the following directory structure typically appears:

~~~text
build/generated-snippets/
└── books-get-one/
    ├── curl-request.adoc
    ├── httpie-request.adoc
    ├── http-request.adoc
    ├── http-response.adoc
    ├── request-body.adoc
    ├── response-body.adoc
    ├── response-headers.adoc
    └── response-fields.adoc
~~~

The first six files are the default snippets in a standard Spring REST Docs setup. The last two are generated by `responseHeaders(...)` and `responseFields(...)`. The list may vary if the project customizes default snippets or templates.

The content of `books-get-one/http-response.adoc` might look like this:

~~~http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":42,"title":"Spring in Action"}
~~~

Do not copy this illustrative example in place of the actual snippet: open `http-response.adoc` after running your test. Spring REST Docs may include other headers, format the body differently, or adjust the output according to request/response preprocessors.

## 5. Verifying the Response When Creating a Resource: `201 Created`

The `POST /api/books` scenario clearly illustrates the combination of **status**, **headers**, and **body**. Suppose the API contract specifies:

- The request sends JSON with the book title.
- On success, the API returns `201 Created`.
- The `Location` header contains the URI of the new resource: `/api/books/43`.
- The body returns JSON `{"id":43,"title":"Spring in Action"}`.

You can add the following test **inside the same** `BookApiDocumentationTest` class above. Add the static imports:

~~~java
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.header;
~~~

And the method:

~~~java
@Test
void documentCreateBook() throws Exception {
    mockMvc.perform(post("/api/books")
            .contentType(MediaType.APPLICATION_JSON)
            .accept(MediaType.APPLICATION_JSON)
            .content("""
                {"title":"Spring in Action"}
                """))
        .andExpect(status().isCreated())
        .andExpect(header().string(HttpHeaders.LOCATION, "/api/books/43"))
        .andExpect(jsonPath("$.id").value(43))
        .andExpect(jsonPath("$.title").value("Spring in Action"))
        .andDo(document("books-create",
            responseHeaders(
                headerWithName(HttpHeaders.LOCATION)
                    .description("URI of the newly created book"),
                headerWithName(HttpHeaders.CONTENT_TYPE)
                    .description("Media type of the response body")
            ),
            responseFields(
                fieldWithPath("id").description("New book ID"),
                fieldWithPath("title").description("Book title")
            )
        ));
}
~~~

Illustrative `books-create/http-response.adoc` snippet:

~~~http
HTTP/1.1 201 Created
Location: /api/books/43
Content-Type: application/json

{"id":43,"title":"Spring in Action"}
~~~

The value `43` is just test data. When the application uses auto-incremented IDs or dynamic data, prepare stable fixtures and write appropriate assertions; do not let tests depend on a randomly assigned ID and hardcode it in documentation.

**Note:** `201 Created` does not require every API to return those exact two fields; that is just the assumed contract in this example. Documentation must always match the response actually returned by the endpoint.

## 6. Responses Without a Body: `204 No Content`

Suppose `DELETE /api/books/42` returns `204` upon successful deletion and **has no body**. The test can be written as:

~~~java
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.delete;

// Place the method below in BookApiDocumentationTest
@Test
void documentDeleteBook() throws Exception {
    mockMvc.perform(delete("/api/books/42"))
        .andExpect(status().isNoContent())
        .andExpect(content().string(""))
        .andDo(document("books-delete"));
}
~~~

Example `books-delete/http-response.adoc` content:

~~~http
HTTP/1.1 204 No Content
~~~

The actual response may include valid headers, but must preserve the rule of **no response body**. Do not configure `responseFields(...)` to describe a JSON object for a `204` response.

Also distinguish `DELETE` idempotency from identical responses: sending the same delete request multiple times may have no further effect on resource state, yet the status codes across calls may differ per the API contract (such as `204` then `404`).

## 7. Documenting Error Branches: `404 Not Found`

An endpoint with only a `200` example does not tell API consumers what happens when accessing a non-existent resource. Create a **separate** operation for the error branch.

Suppose `GET /api/books/9999` returns status `404` and a body following the API's own contract:

~~~json
{"code":"BOOK_NOT_FOUND","message":"Book not found"}
~~~

The additional test could be:

~~~java
@Test
void documentBookNotFound() throws Exception {
    mockMvc.perform(get("/api/books/9999")
            .accept(MediaType.APPLICATION_JSON))
        .andExpect(status().isNotFound())
        .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
        .andExpect(jsonPath("$.code").value("BOOK_NOT_FOUND"))
        .andExpect(jsonPath("$.message").value("Book not found"))
        .andDo(document("books-get-not-found",
            responseFields(
                fieldWithPath("code").description("Business error code"),
                fieldWithPath("message").description("Error message for the client")
            )
        ));
}
~~~

Illustrative snippet:

~~~http
HTTP/1.1 404 Not Found
Content-Type: application/json

{"code":"BOOK_NOT_FOUND","message":"Book not found"}
~~~

This error body is **only an example contract**, not the default error format of Spring Boot or Spring REST Docs. Real applications might return [Problem Details (RFC 9457)](https://www.rfc-editor.org/rfc/rfc9457.html) with media type `application/problem+json`, a custom structure, or even no body by design. Always base documentation on the actual response and verify it in tests.

Use distinct identifiers for each scenario (`books-get-one` and `books-get-not-found`) so snippets from the two outcomes do not overwrite each other.

## 8. How Does `http-response` Differ from Other Snippets?

| Snippet | Main content | When to use |
| --- | --- | --- |
| `http-request.adoc` | Method, URI, request headers, and request body | Proves what the client sent. |
| **`http-response.adoc`** | Status line, response headers, and response body | Illustrates the complete HTTP response. |
| `response-body.adoc` | Only the response body content | Displays a long payload separately from headers. |
| `response-headers.adoc` | Table describing headers declared via `responseHeaders(...)` | Explains the meaning of `Location`, `ETag`, `Content-Type`, etc. |
| `response-fields.adoc` | Table describing payload fields declared via `responseFields(...)` | Explains the returned JSON/XML schema. |
| `curl-request.adoc` | `curl` command capable of replaying the request | Lets readers reproduce the request. |

**There is no default "status-codes.adoc" snippet that automatically lists every status an endpoint can return.** `http-response` holds **one status from one test run**. To document multiple outcomes such as `200`, `404`, and `409`, write separate tests for each case and organize them into documentation sections.

A contract verification flow can be illustrated as follows:

~~~mermaid
flowchart TD
    A["Test sends HTTP request"] --> B["Application returns status, headers, body"]
    B --> C{"Assertions pass?"}
    C -->|No| D["Test fails"]
    C -->|Yes| E["Spring REST Docs records HTTP operation"]
    E --> F["http-response.adoc"]
    E --> G["response-headers.adoc"]
    E --> H["response-fields.adoc"]
    F --> I["Asciidoctor documentation"]
    G --> I
    H --> I
~~~

The diagram illustrates the test flow when placing `andExpect(...)` before `andDo(...)` in the MockMvc example; where documentation generation is triggered may integrate differently across HTTP test clients.

### Verifying Payloads with `responseFields`

Example:

~~~java
responseFields(
    fieldWithPath("id").description("Book ID"),
    fieldWithPath("title").description("Book title")
)
~~~

In strict (default) mode, REST Docs requires the documented fields to match the payload and fails if an undocumented field appears. This helps catch unexpected response schema changes. If you intentionally want to present only part of a payload, `relaxedResponseFields(...)` ignores extra fields; however, do not use it carelessly as it can hide API contract changes.

For `204` responses or responses with no body at all, do not use `responseFields(...)`. For JSON arrays, use path descriptors matching the actual structure (such as `[].id` when the top level is an array) instead of assuming every response has a root object.

## 9. Using WebTestClient and REST Assured

Spring REST Docs works with multiple HTTP test clients. **The status is always the value returned by the server**, while documentation recording setup depends on the tool.

### 9.1. WebTestClient

The example below assumes `webTestClient` is already configured with Spring REST Docs integration and a `GET /api/books/42` endpoint exists:

~~~java
import static org.springframework.restdocs.webtestclient.WebTestClientRestDocumentation.document;

webTestClient.get()
    .uri("/api/books/42")
    .accept(MediaType.APPLICATION_JSON)
    .exchange()
    .expectStatus().isOk()
    .expectHeader().contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
    .expectBody()
    .jsonPath("$.id").isEqualTo(42)
    .consumeWith(document("books-get-webtestclient"));
~~~

`expectStatus().isOk()` verifies `200`, and `consumeWith(document(...))` records the operation into snippets. For WebTestClient, the corresponding dependency/integration is `spring-restdocs-webtestclient`. Configure the client/REST Docs setup to match the Spring WebFlux or Spring MVC test style used by the project.

### 9.2. REST Assured

REST Assured uses a Spring REST Docs **filter** to record HTTP operations. Illustrating the idea with an already configured request specification:

~~~java
import static io.restassured.RestAssured.given;
import static org.springframework.restdocs.restassured.RestAssuredRestDocumentation.document;

// "spec" is a RequestSpecification configured with base URI, port, and REST Docs.
given(spec)
    .filter(document("books-get-restassured"))
    .accept("application/json")
.when()
    .get("/api/books/42")
.then()
    .statusCode(200);
~~~

The integration module is `spring-restdocs-restassured`. The filter records the operation when the request executes; the `statusCode(200)` assertion happens after receiving the response. Therefore, CI must still treat **passing test assertions** as the condition for publishing documentation, rather than assuming the mere presence of snippets means the API satisfies its contract. For REST Assured, configure `RestAssuredRestDocumentationConfigurer` or the corresponding REST Docs mechanism for your project version to specify context and output.

### 9.3. Quick Comparison

| Client | Verifying status | Generating documentation |
| --- | --- | --- |
| MockMvc | `.andExpect(status().isOk())` | `.andDo(document("..."))` |
| WebTestClient | `.expectStatus().isOk()` | `.expectBody().consumeWith(document("..."))` |
| REST Assured | `.then().statusCode(200)` | Filter `document("...")` in the request specification |

These testing APIs differ in syntax but aim for the same goal: **the presented response must come from a real HTTP call**.

## 10. Cleaning and Stabilizing Responses Before Generating Docs

Real responses may contain `Date`, `Set-Cookie`, correlation IDs, timestamps, dynamic IDs, trace IDs, or hard-to-read JSON. Leaving variable values as-is makes documentation noisy and hard to review.

Spring REST Docs provides **response preprocessors** to change **how the response appears in snippets**, without altering the response returned by the server or the values checked by assertions.

For example, replace the final `.andDo(document(...))` call with a configuration that both processes request/response and declares snippets:

~~~java
import static org.springframework.restdocs.operation.preprocess.Preprocessors.preprocessRequest;
import static org.springframework.restdocs.operation.preprocess.Preprocessors.preprocessResponse;
import static org.springframework.restdocs.operation.preprocess.Preprocessors.prettyPrint;
import static org.springframework.restdocs.operation.preprocess.Preprocessors.removeHeaders;

// Example placed after .andExpect(...) calls in the GET test:
.andDo(document("books-get-one",
    preprocessRequest(),
    preprocessResponse(
        removeHeaders("Date", "Set-Cookie"),
        prettyPrint()
    ),
    responseFields(
        fieldWithPath("id").description("Book ID"),
        fieldWithPath("title").description("Book title")
    )
));
~~~

This is a **replacement example** for a `document(...)` call in a test; do not append a new call with the same identifier to a test that already has a documentation call.

A few principles:

- Use dummy/deterministic test data at the source. Never put real tokens or cookies into fixtures and reports.
- Only hide or normalize data when necessary. If a header is removed, do not simultaneously require `responseHeaders(...)` to describe that header as present.
- `prettyPrint()` makes JSON easier to read, but does not replace assertions on structure/content.
- For status `204`, never force a response body just to make documentation look "complete".
- If preprocessing alters the presented URI, hostname, or body formatting, clearly explain that it is a **representation for documentation**.

## 11. Authoring Asciidoctor and Build/CI Integration

By default, Spring REST Docs usually outputs `*.adoc` snippets for inclusion in Asciidoctor. A documentation page can group success and error scenarios as follows:

~~~asciidoc
= Books API

== Get a Book

=== Success — 200 OK

HTTP request:
include::{snippets}/books-get-one/http-request.adoc[]

HTTP response:
include::{snippets}/books-get-one/http-response.adoc[]

Response fields:
include::{snippets}/books-get-one/response-fields.adoc[]

=== Not Found — 404 Not Found

include::{snippets}/books-get-not-found/http-response.adoc[]

== Create Book — 201 Created

include::{snippets}/books-create/http-response.adoc[]

include::{snippets}/books-create/response-headers.adoc[]

== Delete Book — 204 No Content

include::{snippets}/books-delete/http-response.adoc[]
~~~

The `snippets` attribute must be configured by the build to point to the snippet output directory (in this example: `build/generated-snippets`). Exact paths depend on the Asciidoctor source location, how the project defines attributes, and the build system.

Recommended workflow:

~~~mermaid
flowchart LR
    A["Build/CI"] --> B["Run HTTP tests and assertions"]
    B --> C["Generate snippets"]
    C --> D["Asciidoctor includes snippets"]
    D --> E["Export HTML/PDF or packaged docs"]
    E --> F["Publish when pipeline PASSES"]
~~~

To prevent documentation from using stale snippets, configure the Asciidoctor task to **depend on** the test task that generates snippets and properly configure task inputs and outputs. On CI, treat test failures, missing snippets, broken include paths, or documentation build errors as pipeline failures per project policy.

If you want to write documentation in Markdown, configure an appropriate template/output format or conversion workflow. Do not assume Asciidoctor's `include::{snippets}/...[]` syntax will be supported by a plain Markdown renderer.

**Beware of "false green" states:** leftover snippets from a previous run can still be included even when current tests did not run. Projects should configure output directories, task dependencies, and failure conditions clearly so the documentation build reflects the current test run.

## 12. Troubleshooting Common Issues

| Symptom | Common cause | How to resolve |
| --- | --- | --- |
| `http-response.adoc` does not appear | Missing REST Docs integration, test stopped before `document(...)`, or wrong output directory | Check configuration, test logs, identifier, and snippet output folder. |
| Snippet shows `404` instead of `200` | Test data does not exist, wrong URI, or endpoint behaves differently than expected | Check fixtures, request, and `status().isOk()` assertion. |
| Docs say `201` but test receives `200` | Hand-written description drifted from the API | Confirm the endpoint contract; update code/tests and docs consistently. |
| `204` appears with a JSON body on the doc page | Wrong snippet included or inaccurate hand-written example | Use the right identifier; remove invalid payloads from the `204` description. |
| `response-fields.adoc` is not generated | Called `document(...)` without declaring `responseFields(...)` | Add descriptors inside the `document(...)` call. |
| Snippet generation test fails due to undocumented field | Response body has a new field or descriptor path is wrong | Update the field table to match the actual contract; consider `relaxedResponseFields` only when intentional. |
| `Location` header is not recorded in the snippet | API did not return the header, test hit the wrong branch, or preprocessing removed it | Assert with `header().string(...)`; check filters/preprocessors. |
| Snippet changes on every run | Timestamps, IDs, random values, dynamic headers | Use deterministic fixtures and response preprocessing. |
| Docs build succeeds despite failing HTTP tests | Pipeline allows publishing from stale snippets or lacks test dependency | Require the docs build to depend on tests and publish only when the entire pipeline PASSES. |

## 13. Hands-on Exercise and Completion Criteria
