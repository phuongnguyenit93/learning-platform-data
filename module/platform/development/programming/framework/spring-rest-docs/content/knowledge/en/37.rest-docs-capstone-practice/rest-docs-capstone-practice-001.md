# Setting Up a Spring MVC Project to Generate Documentation with MockMvc

## 1. Capstone Objectives

In this capstone practice, you will set up a Spring MVC project that can automatically generate REST API documentation using Spring REST Docs and MockMvc. The end result is a repeatable workflow:

1. The Spring MVC application provides REST endpoints.
2. MockMvc sends HTTP requests to the endpoints in tests.
3. Tests verify the status, headers, and payload.
4. Spring REST Docs generates snippets from the tested operation.
5. Asciidoctor assembles the snippets into HTML documentation.
6. Gradle orchestrates tests and documentation builds in CI.

Spring REST Docs ensures documentation reflects tested HTTP behavior. When a response or contract changes, documentation tests can detect descriptors that no longer match; new snippets are generated from the current test run.

## 2. Architecture and Directory Structure

A single-module project can be organized as follows:

~~~text
spring-rest-docs-demo/
├── build.gradle
├── settings.gradle
└── src/
    ├── main/
    │   ├── java/com/example/catalog/
    │   │   ├── CatalogApplication.java
    │   │   └── ProductController.java
    │   └── resources/
    ├── test/
    │   ├── java/com/example/catalog/
    │   │   └── ProductDocumentationTest.java
    │   └── resources/
    │       └── org/springframework/restdocs/templates/
    │           └── asciidoctor/
    │               └── request-fields.snippet
    └── docs/
        └── asciidoc/
            └── api-guide.adoc
~~~

| Path | Contents |
| --- | --- |
| src/main/java | Spring Boot application and REST controllers |
| src/test/java | MockMvc documentation tests and descriptors |
| src/test/resources | Template overrides used only during test runs |
| build/generated-snippets | Snippets generated after documentation tests |
| src/docs/asciidoc | Hand-written AsciiDoc documentation that includes snippets |
| build/docs/asciidoc | HTML generated by Asciidoctor |

Do not edit files in `build/generated-snippets` directly; they are reproducible outputs generated from tests.

## 3. Initializing the Gradle Project

Create `settings.gradle`:

~~~groovy
rootProject.name = 'spring-rest-docs-demo'
~~~

Example `build.gradle` using Spring Boot, dependency management, and the Asciidoctor Gradle plugin:

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.4.0'
    id 'io.spring.dependency-management' version '1.1.7'
    id 'org.asciidoctor.jvm.convert' version '4.0.4'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

configurations {
    asciidoctorExt
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.restdocs:spring-restdocs-mockmvc'

    asciidoctorExt 'org.springframework.restdocs:spring-restdocs-asciidoctor'
}

tasks.named('test') {
    useJUnitPlatform()
    outputs.dir layout.buildDirectory.dir('generated-snippets')
}

tasks.named('asciidoctor') {
    dependsOn tasks.named('test')
    configurations 'asciidoctorExt'
    inputs.dir layout.buildDirectory.dir('generated-snippets')
    attributes 'snippets': layout.buildDirectory.dir('generated-snippets').get().asFile
}
~~~

The versions in the example are an illustrative set. When creating a new project, choose Spring Boot, Java, and Asciidoctor plugin versions compatible with your team's current environment; do not upgrade a single component while ignoring the project's compatibility matrix.

`spring-restdocs-mockmvc` provides REST Docs integration for MockMvc. `spring-restdocs-asciidoctor` provides Asciidoctor support, including a convenient way to include snippets. There is no need to add a production dependency for Spring REST Docs if the application only uses it in tests.

## 4. Creating the Spring Boot Application and Endpoints

Application entry point:

~~~java
package com.example.catalog;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class CatalogApplication {

    public static void main(String[] args) {
        SpringApplication.run(CatalogApplication.class, args);
    }
}
~~~

Create a small controller for practice:

~~~java
package com.example.catalog;

import java.math.BigDecimal;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/products")
class ProductController {

    @GetMapping("/{id}")
    Product getProduct(@PathVariable String id) {
        return new Product(id, "Mechanical Keyboard",
                new BigDecimal("1299000"));
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    Product createProduct(@RequestBody CreateProductRequest request) {
        return new Product("p-100", request.name(), request.price());
    }

    record CreateProductRequest(String name, BigDecimal price) {}

    record Product(String id, String name, BigDecimal price) {}
}
~~~

These are sample endpoints for setting up the documentation workflow. In a real application, controllers typically call services and repositories; documentation tests should use stable test data and not depend on external services.

## 5. Configuring MockMvc and Spring REST Docs

Spring Boot can auto-configure MockMvc and REST Docs through test annotations:

~~~java
@SpringBootTest
@AutoConfigureMockMvc
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
class ProductDocumentationTest {

    @Autowired
    MockMvc mockMvc;
}
~~~

`AutoConfigureMockMvc` creates `MockMvc` based on the Spring application context. `AutoConfigureRestDocs` registers REST Docs integration and specifies where snippets are written. If the project already configures REST Docs manually, use `documentationConfiguration(...)` with `MockMvcBuilders` instead of duplicating configuration.

## 6. Writing a Documentation Test for the GET Endpoint

The GET test needs to verify the status, media type, and response fields:

~~~java
package com.example.catalog;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.restdocs.AutoConfigureRestDocs;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.restdocs.mockmvc.MockMvcRestDocumentation.document;
import static org.springframework.restdocs.payload.PayloadDocumentation.fieldWithPath;
import static org.springframework.restdocs.payload.PayloadDocumentation.responseFields;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
class ProductDocumentationTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void getProduct() throws Exception {
        mockMvc.perform(get("/api/products/{id}", "p-42")
                        .accept(MediaType.APPLICATION_JSON))
                .andExpect(status().isOk())
                .andExpect(content().contentTypeCompatibleWith(
                        MediaType.APPLICATION_JSON))
                .andExpect(jsonPath("$.id").value("p-42"))
                .andExpect(jsonPath("$.name").value("Mechanical Keyboard"))
                .andDo(document("products-get",
                        responseFields(
                                fieldWithPath("id").description("Product ID"),
                                fieldWithPath("name").description("Product name"),
                                fieldWithPath("price").description("Product price"))));
    }
}
~~~

Place imports and the class in the proper package. If using a single test class for multiple operations, each test needs its own identifier such as `products-get` and `products-create`.

## 7. Writing a Documentation Test for the POST Endpoint

The POST test checks request fields and response fields:

~~~java
import static org.springframework.restdocs.payload.PayloadDocumentation.requestFields;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;

@Test
void createProduct() throws Exception {
    mockMvc.perform(post("/api/products")
                    .contentType(MediaType.APPLICATION_JSON)
                    .accept(MediaType.APPLICATION_JSON)
                    .content("""
                            {
                              "name": "Desk Lamp",
                              "price": 450000
                            }
                            """))
            .andExpect(status().isCreated())
            .andExpect(jsonPath("$.id").value("p-100"))
            .andDo(document("products-create",
                    requestFields(
                            fieldWithPath("name").description("Product name"),
                            fieldWithPath("price").description("Product price")),
                    responseFields(
                            fieldWithPath("id").description("Created product ID"),
                            fieldWithPath("name").description("Product name"),
                            fieldWithPath("price").description("Product price"))));
}
~~~

In the actual class, add static imports for `post(...)` and `requestFields(...)`. Strict field descriptors cause the test to fail if the request or response contains an undocumented field or if a descriptor no longer matches the payload.

## 8. Generating Snippets and Checking Output

After the documentation tests run, the output has the following structure:

~~~text
build/generated-snippets/
├── products-get/
│   ├── curl-request.adoc
│   ├── http-request.adoc
│   ├── http-response.adoc
│   └── response-fields.adoc
└── products-create/
    ├── curl-request.adoc
    ├── http-request.adoc
    ├── http-response.adoc
    ├── request-fields.adoc
    └── response-fields.adoc
~~~

Default snippets may vary depending on configuration. Check the actual output directory rather than assuming every file in the example is generated.

Run tests alone:

~~~bash
./gradlew clean test
~~~

After the tests succeed, open `build/generated-snippets/products-create/request-fields.adoc` and confirm the table has both `name` and `price` fields with the right descriptions. If the file is missing, check the identifier passed to `document(...)`, the output directory, and whether the test actually executed the operation.

## 9. Authoring the AsciiDoc Documentation

Create `src/docs/asciidoc/api-guide.adoc`:

~~~adoc
= Catalog REST API
:toc:
:sectnums:

== Introduction

Sample API for managing products in the catalog.

== Get Product

=== Request

include::{snippets}/products-get/curl-request.adoc[]
include::{snippets}/products-get/http-request.adoc[]

=== Response

include::{snippets}/products-get/http-response.adoc[]
include::{snippets}/products-get/response-fields.adoc[]

== Create Product

=== Request

include::{snippets}/products-create/curl-request.adoc[]
include::{snippets}/products-create/http-request.adoc[]
include::{snippets}/products-create/request-fields.adoc[]

=== Response

include::{snippets}/products-create/http-response.adoc[]
include::{snippets}/products-create/response-fields.adoc[]
~~~

The `snippets` attribute is provided by the Asciidoctor plugin via the Gradle configuration from the previous section. The identifier name in `include` must match the identifier in `document(...)` exactly.

## 10. Running the Documentation Build

Run:

~~~bash
./gradlew asciidoctor
~~~

The `asciidoctor` task depends on `test`, so tests generate snippets before Asciidoctor includes them. Output HTML is typically located under:

~~~text
build/docs/asciidoc/
└── api-guide.html
~~~

To verify the entire workflow from scratch:

~~~bash
./gradlew clean asciidoctor
~~~

If you want to build a JAR containing the documentation, you can add a copy task or configure a separate artifact. Only add the packaging step when the team actually needs to distribute documentation alongside the application.

## 11. Customizing Templates and Preprocessors

Once the basic workflow works, you can add template overrides in:

~~~text
src/test/resources/org/springframework/restdocs/templates/asciidoctor/
~~~

For example, `request-fields.snippet` to change how the request fields table is presented. Start from the default template of the exact REST Docs version, then add the columns or metadata you need. Do not create a minimal template that loses optional/ignored status or standard information provided by the default template.

You can pretty-print requests/responses and sanitize sensitive data before writing snippets:

~~~java
mockMvc.perform(get("/api/products/{id}", "p-42"))
        .andExpect(status().isOk())
        .andDo(document("products-get",
                preprocessRequest(prettyPrint(),
                        removeHeaders("Authorization", "Cookie")),
                preprocessResponse(prettyPrint(),
                        removeHeaders("Set-Cookie"))));
~~~

This is an example of applying preprocessors per operation; add the corresponding static imports from `OperationPreprocessors`. In an application with authentication, tests still send credential fixtures to verify behavior; the preprocessor only removes them from the documented record. Inspect the generated snippets to make sure tokens/sessions are not recorded.

## 12. Organizing Tests and Documentation as the Project Grows

~~~text
src/test/java/com/example/catalog/
├── products/
│   └── ProductDocumentationTest.java
├── categories/
│   └── CategoryDocumentationTest.java
└── common/
    ├── RestDocsConfig.java
    └── ApiDescriptors.java
~~~

Use helpers for genuinely shared parts such as header descriptors, preprocessors, or template formats. Each operation still needs its own descriptors for its payload and contract.

Name identifiers by resource and action: `products-get`, `products-create`, `categories-list`. Stable identifiers keep AsciiDoc includes readable and prevent snippets from overwriting one another.

## 13. Common Errors and Troubleshooting

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Tests pass but no snippets are generated | `document(...)` was not called or the operation never reached that step | Check the test and identifier |
| Strict fields test fails | Payload has an undocumented field or descriptor has the wrong path | Compare against the actual JSON and update descriptors |
| Asciidoctor reports missing include | Tests have not generated snippets yet or the identifier is wrong | Run tests first and check the output directory |
| Snippets are in the wrong directory | Inconsistent output directory configuration | Align `AutoConfigureRestDocs` and Gradle |
| HTML does not update | Build task does not depend on `test` or uses stale output | Declare task dependency and run `clean` |
| Tokens/cookies appear in documentation | Sensitive headers were not preprocessed | Remove or replace values before writing |
| Template override has no effect | Wrong package, format ID, or snippet name | Check the test classpath and template name |
| Tests depend on external data | Using an unstable database/service | Use fixtures, mocks, or appropriate test containers |

When troubleshooting, check in order: HTTP test, descriptors, snippet output, Asciidoctor include, and the Gradle task graph. Each step produces input for the next.

## 14. Capstone Exercise

Complete the documentation for the catalog API with the following requirements:

1. `GET /api/products/{id}`: document the path parameter, response fields, and response headers.
2. `POST /api/products`: document request fields, response fields, status 201, and content types.
3. `GET /api/products`: add query parameters `page`, `size`, and `sort`.
4. Add a 404 error response and document the error payload.
5. Create a template override that adds an `Example` or `Constraints` column.
6. Preprocess `Authorization`/`Cookie` before writing snippets.
7. Include the snippets in `api-guide.adoc`.
8. Run `./gradlew clean asciidoctor` and verify the final HTML.

**Completion criteria:** documentation tests run reliably; HTTP assertions verify behavior; descriptors cover payloads/parameters/headers; snippets are generated from the current tests; Asciidoctor builds HTML with no missing includes; no credentials or real data appear in the documentation.

## 15. Checklist Before Adding to CI

- [ ] The Spring MVC application starts cleanly in the test context.
- [ ] MockMvc and Spring REST Docs are configured with the right output directory.
- [ ] Each operation has a unique identifier.
- [ ] Tests verify status, media type, and key payload fields.
- [ ] Request/response descriptors reflect the actual JSON accurately.
- [ ] Template overrides reside in the test classpath with the proper format ID.
- [ ] Sensitive headers are sanitized before writing snippets.
- [ ] Gradle `test` runs before `asciidoctor`.
- [ ] `./gradlew clean asciidoctor` succeeds from scratch.
- [ ] The HTML artifact is verified and archived in CI.

**Remember:** A Spring MVC project using MockMvc and Spring REST Docs needs three cohesive parts: HTTP tests verifying behavior, descriptors documenting the contract, and Asciidoctor assembling snippets into documentation. When Gradle orchestrates tests before the build step, documentation can be reproduced consistently on developer machines and in CI.
