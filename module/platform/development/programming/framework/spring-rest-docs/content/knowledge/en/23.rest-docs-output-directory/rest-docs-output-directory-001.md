# Gradle's Default generated-snippets Directory

## 1. Role of build/generated-snippets

In projects using **Gradle**, the **build/generated-snippets** directory is commonly chosen as the location to store snippets generated by Spring REST Docs when running tests. Each time a test calls **document(...)**, REST Docs writes files describing the request, response, headers, parameters, or payload into a subdirectory named after the document identifier.

For example:

~~~text
project/
├── build.gradle
├── src/
│   ├── main/
│   ├── test/
│   └── docs/
│       └── asciidoc/
│           └── index.adoc
└── build/
    └── generated-snippets/
        └── registrations/
            └── create/
                ├── http-request.adoc
                ├── http-response.adoc
                ├── curl-request.adoc
                └── request-fields.adoc
~~~

The **build** directory is Gradle's output directory and is typically regenerated during a build. **generated-snippets** contains intermediate documentation files automatically generated by tests. These files are normally included by Asciidoctor to produce the complete API documentation; they are not source code to be edited manually.

In the **SPRING_REST_DOCS** module, HTTP tests using MockMvc, WebTestClient, or REST Assured are the verification source for the documentation. Snippets capture the requests and responses executed by the tests; Asciidoctor or Markdown compiles them into documentation, and CI can then render them on every build. Therefore, the output directory must be consistent across the tests, build tasks, and include paths.

## 2. Why is build/generated-snippets Commonly Used?

Spring REST Docs does not force every project to use a single specific directory. This is a common convention in Gradle configurations:

- **build/** is Gradle's standard output directory, separating build outputs from source code.
- **generated-snippets/** clearly conveys that the contents are documentation snippets automatically generated from tests.
- Relative paths are typically resolved against the project directory of the Gradle project/module running the task.
- This directory can be declared as an output of the test task and an input of the Asciidoctor task.

Distinguishing the directories:

| Path | Role |
| --- | --- |
| src/test/java | Test source code |
| src/docs/asciidoc | Team-authored AsciiDoc documentation |
| build/generated-snippets | Snippets generated from tests |
| build/docs or build/asciidoc | Rendered documentation, depending on plugin configuration |
| build/classes | Compiled classes |

The snippets directory is an intermediate result. The rendered HTML/PDF directory is the subsequent output artifact. Do not point the `snippets` attribute to the rendered HTML directory, and do not include files from `src/test`.

## 3. Configuring the Output Directory in Tests

### 3.1. MockMvc with @AutoConfigureRestDocs

In Spring Boot, a simple approach is to declare the output directory on the annotation:

~~~java
import org.springframework.boot.test.autoconfigure.restdocs.AutoConfigureRestDocs;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;

@WebMvcTest(RegistrationController.class)
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
class RegistrationDocumentationTest {
    // MockMvc tests
}
~~~

When a test calls:

~~~java
document("registrations/create", ...);
~~~

the snippets are written under:

~~~text
build/generated-snippets/
└── registrations/
    └── create/
        ├── http-request.adoc
        ├── http-response.adoc
        └── ...
~~~

The `outputDir` value is the path used by the test harness as the output directory. In a multi-module project, determine which Gradle subproject runs the tests and which project directory relative paths are resolved against; do not assume it is always relative to the repository root.

### 3.2. MockMvc with the JUnit Extension

If you do not use `@AutoConfigureRestDocs`, you can configure REST Docs via `RestDocumentationExtension` and pass the context provider to MockMvc:

~~~java
@ExtendWith({SpringExtension.class, RestDocumentationExtension.class})
@WebMvcTest(RegistrationController.class)
class RegistrationDocumentationTest {

    private MockMvc mockMvc;

    @BeforeEach
    void setUp(
            WebApplicationContext context,
            RestDocumentationContextProvider restDocumentation) {
        this.mockMvc = MockMvcBuilders.webAppContextSetup(context)
            .apply(documentationConfiguration(restDocumentation))
            .build();
    }
}
~~~

The extension provides the context for Spring REST Docs. If you need to change the output directory with this configuration style, use the constructor or configuration of `RestDocumentationExtension` appropriate for the version you are using. Do not configure multiple different output mechanisms without reason; choose one primary configuration source so the team knows where snippets are written.

### 3.3. Keeping a Single Consistent Path

Avoid a situation where the test annotation configures writing to **build/generated-snippets**, while Gradle declares:

~~~groovy
def snippetsDir = file('build/snippets')
~~~

In that case, tests write to one place while Asciidoctor reads from another. Use the exact same value for:

1. The REST Docs output directory in tests.
2. The output directory declared on the test task.
3. The input directory and `snippets` attribute of the Asciidoctor task.
4. The root path used in `include::{snippets}/...[]`.

## 4. Gradle: Declaring That Tests Generate Snippets

Groovy DSL example:

~~~groovy
def snippetsDir = file('build/generated-snippets')

tasks.named('test') {
    outputs.dir snippetsDir
}
~~~

This declares to Gradle that the `test` task produces content at `build/generated-snippets`. Gradle can use this output information when planning tasks and checking up-to-date status.

Declaring the output does not configure Spring REST Docs automatically. Tests still need the output directory configured, for example:

~~~java
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
~~~

Both parts must match: the annotation controls where REST Docs writes files; `outputs.dir` describes that output to Gradle.

## 5. Connecting the test Task to asciidoctor

A commonly used configuration:

~~~groovy
def snippetsDir = file('build/generated-snippets')

tasks.named('test') {
    outputs.dir snippetsDir
}

tasks.named('asciidoctor') {
    dependsOn tasks.named('test')
    inputs.dir snippetsDir
    attributes 'snippets': snippetsDir.absolutePath
}
~~~

Meaning of each declaration:

| Declaration | Meaning |
| --- | --- |
| outputs.dir snippetsDir | The test task generates snippets in the selected directory |
| dependsOn test | Asciidoctor runs after test |
| inputs.dir snippetsDir | Gradle knows Asciidoctor reads these snippets |
| attributes snippets | Asciidoctor receives the path to substitute for the `snippets` variable in includes |

When running:

~~~bash
./gradlew test asciidoctor
~~~

Gradle runs the tests, generates the snippets, and then uses the snippets as input when rendering the documentation. If a test fails, the Asciidoctor task that depends on `test` cannot complete successfully.

### 5.1. Why Are Both Dependency and Input Needed?

**dependsOn** describes execution order: Asciidoctor needs to run after `test`. **inputs.dir** describes the data that Asciidoctor reads to produce its output. The two declarations serve two different purposes.

If you only add `dependsOn`, the ordering may be right, but Gradle is not fully informed about the input directory to calculate task up-to-date status. If you only add `inputs.dir`, Gradle knows which directory is read, but does not necessarily know which test task must run to generate that data.

## 6. Including Snippets in Asciidoctor

Suppose a test called:

~~~java
document("registrations/create",
    requestFields(
        fieldWithPath("email").description("Registration email"),
        fieldWithPath("plan").description("Subscription plan")
    )
);
~~~

The `src/docs/asciidoc/index.adoc` page can include them:

~~~adoc
= Registration API

== Create Registration

=== HTTP request
include::{snippets}/registrations/create/http-request.adoc[]

=== Request fields
include::{snippets}/registrations/create/request-fields.adoc[]

=== HTTP response
include::{snippets}/registrations/create/http-response.adoc[]
~~~

The `snippets` attribute points to `build/generated-snippets`, so the include is resolved to the full path inside that directory. Using `{snippets}` lets you change the output directory in one place instead of repeating the absolute path in every include.

### 6.1. Include Paths Relative to the Snippet Root

If the identifier is `registrations/create`, do not include:

~~~adoc
include::{snippets}/http-request.adoc[]
~~~

because the file lives under the `registrations/create` subdirectory. The correct path is:

~~~adoc
include::{snippets}/registrations/create/http-request.adoc[]
~~~

The snippet filename must match the type of operation generated. For example, `formParameters(...)` creates `form-parameters.adoc`, `requestFields(...)` creates `request-fields.adoc`, and `responseFields(...)` creates `response-fields.adoc`. Check the actual generated files if you use custom snippets or a different REST Docs version.

## 7. Relative Paths and Multi-Module Projects

### 7.1. Relative Paths

`file('build/generated-snippets')` in Gradle is resolved relative to the project directory of the project executing the build script. For a single-module project at the repository root, this is typically:

~~~text
<repository>/build/generated-snippets
~~~

In a multi-project structure, if the configuration is in the `service-api` subproject, the path may be:

~~~text
<repository>/service-api/build/generated-snippets
~~~

This is usually desirable because the snippets belong to that module's tests. If you want to centralize snippets at the root project, you must configure the paths explicitly and consistently in both the tests and Asciidoctor; do not rely on the IDE's working directory.

### 7.2. Using layout.buildDirectory

In modern Gradle, you can obtain the build directory via the project layout:

~~~groovy
def snippetsDir = layout.buildDirectory.dir('generated-snippets')

tasks.named('test') {
    outputs.dir snippetsDir
}
~~~

This is a `Provider` for the output directory. When passing the path to REST Docs or Asciidoctor, extract the value from the provider consistently according to the Gradle API version in use. Simple Groovy DSL configurations can also continue using `file('build/generated-snippets')`; `layout.buildDirectory` is useful when the project customizes `buildDirectory`.

If the build directory is changed via `layout.buildDirectory`, do not leave a Java annotation hardcoding `build/generated-snippets` while the task reads a different build directory. A single unified configuration value is required, which can be passed into tests via a system property or an appropriate test configuration.

## 8. Managing Stale Snippets and Reproducible Builds

Old snippets can remain behind if a test is deleted or a document identifier changes. For example, a previous build generated:

~~~text
registrations/create/
registrations/update/
~~~

In a new build, the update test has been deleted, yet the `registrations/update` directory may still remain if the output is not cleaned as part of the build process. In that situation, the documentation risks including an outdated example that is no longer verified in the current build.

Best practices:

1. Keep snippets inside the Gradle-managed build directory.
2. Use `clean` or a clean build workspace when you need to regenerate the entire documentation.
3. Do not manually edit generated snippet files; update the test or descriptors and re-run.
4. Do not commit old snippets as source code if your project's workflow expects them to be generated during the build.
5. Check the rendered HTML output and includes whenever changing identifiers or the output directory.

Local pipeline example:

~~~bash
./gradlew clean test asciidoctor
~~~

`clean` removes previous build outputs before re-running; then `test` generates fresh snippets and `asciidoctor` renders from the new results. For fast daily builds, incremental tasks can run if input/output relationships are configured properly.

## 9. Maven Uses a Different Directory by Common Convention

This topic focuses on Gradle. However, in Maven projects, you may encounter:

~~~text
target/generated-snippets/
~~~

This is the common convention in Spring REST Docs Maven configurations. Maven build output uses `target/`, whereas Gradle typically uses `build/`. Do not replace the path in a Maven project with `build/generated-snippets` just because it appears in a Gradle example. REST Docs configuration, the documentation plugin, and includes must align with the build tool in use.

| Build tool | Commonly used snippets directory |
| --- | --- |
| Gradle | build/generated-snippets |
| Maven | target/generated-snippets |

This is a common configuration convention, not a technical limitation: both build tools can use custom paths.

## 10. Troubleshooting When Snippets Do Not Appear or Asciidoctor Cannot Find Files

| Symptom | Possible Cause | How to Check |
| --- | --- | --- |
| `build/generated-snippets` does not exist | Tests with `document(...)` have not run, were skipped, or REST Docs is not configured | Run the specific test and inspect logs |
| Snippets are located in `target/generated-snippets` | Test harness/project is using a different path | Compare the REST Docs output directory |
| Snippets are written in a subproject, but Asciidoctor reads the root | Different project directories | Check the absolute path of `snippetsDir` |
| Include reports file not found | Wrong identifier or snippet name | Compare the output directory and the include path |
| Documentation shows stale snippets | Old output remains or task dependency is missing | Run `clean test asciidoctor` and check the task graph |
| Tests generate snippets, but Gradle does not recognize the output | Missing `outputs.dir` declaration | Register the output directory on the test task |
| Asciidoctor runs before tests generate snippets | Missing `dependsOn test` | Declare the task dependency |
| Incremental build does not detect snippet changes | Missing input directory declaration | Declare `inputs.dir snippetsDir` |

When debugging, verify in order:

1. Did the test actually run and execute the `document(...)` call?
2. Which absolute path is REST Docs writing to?
3. Did the identifier create the expected subdirectory?
4. Does the included snippet filename actually exist?
5. Is Asciidoctor using the right `snippets` attribute?
6. Does Gradle have the correct dependency/input/output configuration?

## 11. Practice Exercise

In a Gradle Spring Boot project, configure a `POST /registrations` endpoint and a MockMvc test to generate `http-request.adoc`, `http-response.adoc`, and `form-parameters.adoc`.

Steps:

1. Configure `@AutoConfigureRestDocs(outputDir = "build/generated-snippets")`.
2. Create a test calling `document("registrations/create-form", ...)`.
3. Declare `outputs.dir snippetsDir` on the `test` task.
4. Configure the `asciidoctor` task with `dependsOn test`, `inputs.dir snippetsDir`, and the `snippets` attribute.
5. Include the snippets from `src/docs/asciidoc/index.adoc`.
6. Run `./gradlew clean test asciidoctor`.
7. Verify that the generated files are under `build/generated-snippets/registrations/create-form/` and that the rendered HTML contains the complete request/response sections.
8. Change the identifier to `registrations/register-form`, update the includes, and rebuild to observe the output path change.

**Completion criteria:** Tests write snippets to the right directory, Gradle understands outputs/inputs and task ordering, Asciidoctor includes the right files, and a clean build does not use stale snippets.
