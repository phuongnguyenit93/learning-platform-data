# Avoiding Localhost in Public Documentation with Spring REST Docs

## 1. Why Does Localhost Appear in API Documentation?

When writing HTTP tests, the test environment typically runs the application on a local address. For example, a request might be recorded as:

```http
GET http://localhost:8080/api/products/42 HTTP/1.1
Host: localhost:8080
Accept: application/json
```

The address `localhost:8080` suits a developer's machine or the MockMvc setup being used, but it is usually not the address that customers, partners, or external systems use to access the deployed API. If `http-request.adoc`, `curl-request.adoc`, or example URL snippets are published as-is, readers may copy an address that is unreachable from their own environment.

API documentation should distinguish:

- **URI observed in tests:** the address generated by the test client, mock server, or test configuration.
- **Public base URL:** the address published for integrators, such as `https://api.example.com`.
- **Operation path:** the path segment belonging to the API, such as `/api/products/{id}`.
- **Environment URL:** different hosts per dev, staging, production, or deployment region.

The **SPRING_REST_DOCS** module generates verifiable REST API documentation from HTTP tests using MockMvc, WebTestClient, or REST Assured; snippets are assembled into Asciidoctor/Markdown and build/CI. This lesson belongs to the **URI configuration** chapter and focuses on configuring URIs in snippets so public documentation does not depend on localhost.

After this lesson, you will be able to:

1. Identify the source of host, scheme, and port in Spring REST Docs snippets.
2. Configure default URIs for MockMvc documentation.
3. Distinguish test URIs from the public base URL and operation paths.
4. Use appropriate preprocessing or configuration to normalize URIs in snippets.
5. Verify `http-request` and `curl-request` before pushing documentation to CI/publishing.

## 2. What Components Make Up a URI?

An absolute URI typically has the form:

```text
https://api.example.com:443/api/v1/products/42?view=summary
```

| Component | Example | Meaning |
| --- | --- | --- |
| Scheme | https | Protocol used by the client |
| Host | api.example.com | Public domain name |
| Port | 443 | Service port; can be omitted if it is the default port |
| Base path | /api/v1 | API deployment prefix, if any |
| Resource path | /products/42 | Resource path |
| Query | view=summary | Request options/query parameters |

In many Spring REST Docs examples with MockMvc, the request URI is created in the test environment and snippets may use the local default host/port. Meanwhile, the public base URL may come from a gateway, load balancer, reverse proxy, or deployment configuration. Do not infer the public URL from the port that MockMvc or the test server uses.

### 2.1. Why Doesn't Localhost Work for Everyone?

`localhost` always points to the machine making the request. When an integrator runs:

```bash
curl http://localhost:8080/api/products
```

the request is sent to their own machine, not to the API provider's server. A local host in a snippet is therefore usually not a shareable base URL.

### 2.2. When Is Localhost Still Valid?

Localhost can be accurate guidance if the documentation is about:

- Running a demo application on a personal machine.
- Starting Docker Compose or a local development stack.
- Testing a mock service that only exists on the developer's machine.

In those cases, state clearly that this is a local endpoint and explain how to start the service. For public API documentation, use an appropriate placeholder or public hostname.

## 3. Configuring URIs in MockMvc REST Docs

MockMvc does not need to run a real HTTP server to execute tests. Spring REST Docs' MockMvc integration allows configuring the URI used when generating snippets through `RestDocumentationContextProvider`.

Example URI configuration for documentation:

```java
MockMvcRestDocumentationConfigurer config =
        MockMvcRestDocumentation.documentationConfiguration(restDocumentation);

config.uris()
        .withScheme("https")
        .withHost("api.example.com")
        .withPort(443);

MockMvc mockMvc = MockMvcBuilders.standaloneSetup(controller)
        .apply(config)
        .build();
```

This is how MockMvc REST Docs URI defaults are configured. In a test suite, you typically receive `RestDocumentationContextProvider` provided by `RestDocumentationExtension`:

```java
@ExtendWith(RestDocumentationExtension.class)
class ProductDocumentationTest {

    private MockMvc mockMvc;

    @BeforeEach
    void setUp(RestDocumentationContextProvider restDocumentation) {
        MockMvcRestDocumentationConfigurer config =
                MockMvcRestDocumentation.documentationConfiguration(restDocumentation);

        config.uris()
                .withScheme("https")
                .withHost("api.example.com")
                .withPort(443);

        mockMvc = MockMvcBuilders.standaloneSetup(new ProductController())
                .apply(config)
                .build();
    }
}
```

After configuring this, snippets can display the chosen public host instead of `localhost`. Ensure the scheme/host/port belong to the environment the documentation intends to publish, not arbitrary values.

### 3.1. Choosing Port and Scheme

If the public API uses HTTPS on default port 443, configure `https`, the hostname, and the corresponding port. The URI renderer may omit the default port depending on how the URI is represented; what matters is that the scheme/authority is accurate.

For a public service using a non-default port, such as 8443:

```java
config.uris()
        .withScheme("https")
        .withHost("partner-api.example.com")
        .withPort(8443);
```

Do not set port 8080 just because the local server runs on that port if the public gateway accepts HTTPS on a different authority.

## 4. Operation URIs and Public Base URLs

Documentation should define the base URL once, and then present each operation's path clearly.

Example base URL:

```text
https://api.example.com/api/v1
```

Operations:

```text
GET /products/{productId}
POST /products
PATCH /products/{productId}
```

This presentation is helpful because readers can choose the appropriate environment host, operation paths do not depend on the test machine, and the public domain can change without changing the routes.

An Asciidoctor example can declare an attribute:

```asciidoc
:api-base-url: https://api.example.com/api/v1

= Product API

Base URL: {api-base-url}

== Get Product

GET {api-base-url}/products/{productId}
```

If the project has multiple environments, publish the base URL per environment:

| Environment | Base URL |
| --- | --- |
| Sandbox | https://sandbox-api.example.com/api/v1 |
| Production | https://api.example.com/api/v1 |

Do not include local addresses in the public section. If local development instructions are helpful, place them in a separate section titled "Running the API Locally".

## 5. Normalizing URIs with Operation Preprocessors

Spring REST Docs supports preprocessors applied to requests/responses before generating snippets. With MockMvc, you can use `modifyUris(...)` in `Preprocessors` to replace the scheme, host, or port of the request URI.

Example:

```java
import static org.springframework.restdocs.operation.preprocess.Preprocessors.modifyUris;
import static org.springframework.restdocs.operation.preprocess.Preprocessors.preprocessRequest;

mockMvc.perform(get("/api/products/{id}", 42))
        .andDo(document("product-detail",
                preprocessRequest(
                        modifyUris()
                                .scheme("https")
                                .host("api.example.com")
                                .port(443)
                )));
```

The preprocessor acts on the operation used to generate snippets. This approach is useful when only a subset of operations needs a different authority, when the test client generates an internal URI while documentation needs a public URI, or when you want to keep shared MockMvc configuration and apply transformations per documented operation.

You can set default URIs in the config and use per-operation preprocessors for exceptions. Avoid configuring the same value in too many places, as that easily causes inconsistencies.

### 5.1. Be Careful with URI Templates and Paths

`modifyUris()` changes URI parts according to configuration, but it is not a tool for arbitrarily altering route contracts. A public base path like `/gateway/api/v1` should only be added or kept if the gateway actually exposes that path to clients.

Distinguish between:

- Public host differs from local host: you can configure the authority.
- Context path differs between deployment and tests: determine the path that public clients must call.
- Reverse proxy rewrites paths: document the external path exposed by the gateway, not the internal backend path by default.
- API version: part of the contract if clients need to send it in the path.

## 6. Reverse Proxies, Gateways, and Forwarded Headers

In production, requests may follow a path like:

```text
Client
  |
  | https://api.example.com/api/v1/products
  v
API Gateway / Reverse Proxy
  |
  | http://product-service:8080/products
  v
Spring Application
```

A Spring application behind a proxy may see the `http` scheme, an internal service host, and port `8080`, while external clients use `https://api.example.com`. The proxy may pass the public authority via `Forwarded` or `X-Forwarded-*` headers, depending on the system.

Spring Framework/Spring Boot can be configured to handle forwarded headers, though behavior depends on deployment and server configuration. Do not enable forwarded header processing blindly; only trust headers controlled by a trusted proxy, because clients can forge these headers if the application is directly exposed to the internet.

For Spring REST Docs:

1. Use the confirmed public authority to generate snippets.
2. Do not rely on the backend's internal host/container name.
3. If the public path has a gateway-added prefix, reflect that prefix in the base URL or operation path.
4. Check `http-request.adoc` and `curl-request.adoc` after generation.

## 7. Inspecting Generated Snippets

After tests run, inspect snippets in the output directory, typically `build/generated-snippets` with Gradle or `target/generated-snippets` with Maven.

| Snippet | What to Check |
| --- | --- |
| http-request.adoc | Does the request line contain a local host/scheme? |
| curl-request.adoc | Can the URL in the curl command be used externally? |
| http-response.adoc | Do response headers contain internal hosts or environment details? |
| request-parameters/payload snippets | Does the operation content reflect the contract? |

Example public curl command:

```bash
curl --request GET \
  'https://api.example.com/api/v1/products/42' \
  --header 'Accept: application/json'
```

Instead of:

```bash
curl --request GET \
  'http://localhost:8080/api/products/42' \
  --header 'Accept: application/json'
```

The first command is only appropriate if that hostname and path represent a real public endpoint. In documentation shared across regions or environments, use a variable/placeholder such as `$API_BASE_URL` and instruct readers to set the variable before running.

## 8. Do Not Use Preprocessing to Mask Configuration Bugs

A preprocessor can replace the authority in a snippet, but it cannot fix poorly designed tests or inaccurate route contracts.

Examples:

- Tests call `/internal/products` while the public gateway exposes `/api/v1/products`. Replacing only the host leaves the path wrong.
- Tests run on port 8080, while the public service uses a different host and port. Verify the public endpoint rather than guessing.
- Tests record requests through a fake proxy, and snippets show a URI external clients cannot call.
- Tests produce a redirect URI pointing to `localhost` in the response `Location` header. Changing only the request URI does not automatically fix URLs in response headers/bodies.

For responses containing absolute URLs or `Location`, inspect the response snippet and handle them separately according to the contract if needed. Ensure preprocessing does not accidentally alter business payloads or hide bugs.

## 9. WebTestClient and REST Assured

URIs generated by test clients vary by configuration, but the principle remains separating test authority from public authority.

### 9.1. WebTestClient

`WebTestClient` is often bound to the application or a test server. URIs in test requests may use a local base URL. Configure snippet URIs via preprocessing:

```java
import static org.springframework.restdocs.operation.preprocess.Preprocessors.modifyUris;
import static org.springframework.restdocs.operation.preprocess.Preprocessors.preprocessRequest;
import static org.springframework.restdocs.webtestclient.WebTestClientRestDocumentation.document;

webTestClient.get()
        .uri("/api/products/42")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .consumeWith(document("product-detail",
                preprocessRequest(
                        modifyUris()
                                .scheme("https")
                                .host("api.example.com")
                                .port(443)
                )));
```

This illustrates how to attach a request preprocessor to a documented snippet. `WebTestClient` must be configured with REST Docs according to the project's extension/configurer.

### 9.2. REST Assured

REST Assured can make requests against a test base URI. The documentation filter needs the corresponding operation preprocessor:

```java
given()
        .filter(documentationFilter(
                preprocessRequest(
                        modifyUris()
                                .scheme("https")
                                .host("api.example.com")
                                .port(443)
                )))
        .when()
        .get("/api/products/42")
        .then()
        .statusCode(200);
```

`documentationFilter(...)` here is an illustrative helper, not a universal method available out of the box in every setup. Attach `preprocessRequest(...)` to `RestAssuredRestDocumentation.document(...)` or the filter factory your project uses.

## 10. Structuring Configuration to Avoid Hard-Coding

If a project has multiple services or environments, do not scatter hostnames across individual tests. You can centralize configuration in test support:

```java
final class ApiDocumentationUris {

    static final String SCHEME = "https";
    static final String HOST = "api.example.com";
    static final int PORT = 443;

    private ApiDocumentationUris() {}

    static MockMvcRestDocumentationConfigurer configure(
            RestDocumentationContextProvider context) {
        MockMvcRestDocumentationConfigurer config =
                MockMvcRestDocumentation.documentationConfiguration(context);
        config.uris()
                .withScheme(SCHEME)
                .withHost(HOST)
                .withPort(PORT);
        return config;
    }
}
```

Usage in tests:

```java
@BeforeEach
void setUp(RestDocumentationContextProvider context) {
    mockMvc = MockMvcBuilders.standaloneSetup(new ProductController())
            .apply(ApiDocumentationUris.configure(context))
            .build();
}
```

If documentation needs multiple base URLs, place the configuration in properties/environment settings suited to the documentation pipeline. Avoid using the production hostname during test runtime if the pipeline generates documentation for sandbox.

## 11. Build, Asciidoctor, and CI

Recommended workflow:

1. Choose the public scheme/host/port and base path according to the official API contract.
2. Configure URI defaults or request preprocessors for Spring REST Docs.
3. Run tests to generate snippets.
4. Check `http-request.adoc`, `curl-request.adoc`, response `Location`, and absolute URLs.
5. Assemble snippets with Asciidoctor; if using Markdown, use a Markdown template and appropriate assembly process.
6. Add a CI step scanning for internal/local hosts in the snippet/documentation directory, while allowing localhost in dedicated local guide sections if applicable.

Example manual check on the output directory:

```bash
grep -RniE 'localhost|127\.0\.0\.1|0\.0\.0\.0' build/generated-snippets
```

Run the command in the workspace containing the snippet output. Matches are not always errors: classify them by context and ensure public documentation does not mistakenly reference local hosts. You can add a dedicated CI script to check public docs sections.

Example Gradle build after tasks are configured:

```bash
./gradlew test asciidoctor
```

CI should fail if required snippets are not generated or if an Asciidoctor include file does not exist. Documentation that renders successfully while still containing `localhost` can violate the contract, so a dedicated URL check step is recommended.

## 12. Common Pitfalls

| Symptom | Cause | Resolution |
| --- | --- | --- |
| http-request.adoc shows localhost:8080 | URI defaults are using the test authority | Configure `config.uris()` or `modifyUris()` with the public URL |
| curl-request.adoc calls a local host | Snippet was generated from a local request URI | Check the URI preprocessor and output after tests |
| Host is right but path is wrong | Public gateway adds or rewrites context path | Confirm the external path and configure/document the appropriate base path |
| Public API is HTTPS but snippet shows HTTP | Test request or proxy uses internal scheme | Configure the public scheme; check forwarded-header handling |
| Port 8080 appears in public documentation | Confused backend port with gateway port | Use the actual public port or omit the default port |
| Response Location still has localhost | Only preprocessed the request URI | Check response headers and URLs generated by the application |
| CI finds localhost in local guide | Scan rule does not distinguish public and local docs | Partition documentation or use a controlled allowlist |
| Different tests generate different hosts | Scattered URI config or inconsistent overrides | Centralize configuration and only use intentional overrides |

## 13. Practice Exercise

A product management service runs in tests with MockMvc, while the public API is exposed at:

```text
https://catalog.example.com/api/v2
```

Endpoint:

```text
GET /products/{productId}
```

Complete the following steps:

1. Create a MockMvc documentation test for `GET /products/42`.
2. Configure Spring REST Docs with scheme `https`, host `catalog.example.com`, and the appropriate port.
3. Generate `http-request.adoc` and `curl-request.adoc`; verify there is no `localhost`.
4. If the public gateway adds the `/api/v2` prefix, reflect that prefix in the documented base URL/path and verify the request real clients must call.
5. Add an operation response containing a `Location` header to check absolute URLs in responses.
6. Integrate tests and Asciidoctor into CI, along with a step scanning for internal hosts in public documentation.

**Completion criteria:** Documentation clearly separates the test URI from the public URL, scheme/host/port are correct, the path is not missing the gateway prefix, `curl` works from machines outside the test environment, and absolute URLs in responses do not point to localhost.

## 14. Key Takeaways

`localhost` in snippets usually comes from the test environment's URI, not the public base URL. Configure `config.uris()` in MockMvc REST Docs or use `modifyUris()` in an operation preprocessor to normalize the scheme, host, and port for snippets. Also verify the public path, gateway prefix, `Location`, and URLs in responses. Inspect `http-request`/`curl-request` output after tests and add a scan step in CI so public documentation never directs integrators to a local machine or internal backend host.
