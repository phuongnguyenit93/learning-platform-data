# Configuring `asciidoctor-maven-plugin` for Maven

For projects using Maven, **asciidoctor-maven-plugin** handles compiling AsciiDoc files into output documentation such as HTML. In the Spring REST Docs workflow, this plugin must read the exact snippet directory generated by HTTP tests. Therefore, the most important configuration points are clearly defining **where tests write snippets**, **where Asciidoctor reads snippets from**, **where source AsciiDoc files live**, and **where rendered output is written**.

This lesson belongs to the **Project Setup** chapter of the `SPRING_REST_DOCS` module. The module practices generating verifiable REST API documentation with Spring REST Docs from tests using MockMvc, WebTestClient, or REST Assured, producing snippets for requests, responses, payloads, parameters, and headers, then compiling Asciidoctor/Markdown and integrating into builds and CI. This lesson focuses on Maven configuration to wire those steps properly, understanding the lifecycle, declaring plugin dependencies, and troubleshooting common issues.

## 1. Learning Objectives

After this lesson, you will be able to:

1. Explain the role of `asciidoctor-maven-plugin` in a Spring REST Docs pipeline.
2. Declare the plugin and its execution in `pom.xml`.
3. Configure the AsciiDoc source directory, output directory, and `snippets` attribute.
4. Ensure snippet-generating tests run before the plugin compiles documentation.
5. Distinguish application/test dependencies from Maven plugin dependencies.
6. Run Maven to generate HTML and diagnose missing snippets, wrong paths, or build-order failures.
7. Integrate documentation compilation into CI and avoid stale outputs.

## 2. Role of `asciidoctor-maven-plugin`

Spring REST Docs and Asciidoctor solve two distinct jobs:

- **Spring REST Docs** is invoked from HTTP tests; it records requests/responses, validates descriptors, and generates snippets.
- **Asciidoctor** reads `.adoc` source files, inserts snippets via `include::` directives, and renders the output document.
- **asciidoctor-maven-plugin** connects Asciidoctor to the Maven lifecycle and manages the source directory, output directory, backend, and attributes.

Data flow:

```text
src/test/java/
  └── HTTP documentation tests
           │
           ▼
      mvn test
           │
           ▼
target/generated-snippets/
  ├── products-get-success/
  │     ├── http-request.adoc
  │     └── response-fields.adoc
  └── products-get-not-found/
        └── http-response.adoc
           │
           │  attribute: snippets
           ▼
src/docs/asciidoc/
  ├── index.adoc
  ├── products.adoc
  └── orders.adoc
           │
           ▼
asciidoctor-maven-plugin
           │
           ▼
target/generated-docs/
  └── index.html
```

The plugin **does not run snippet-generating tests on its own** without the right lifecycle wiring. Running tests and rendering documentation must be linked within the same Maven command or an ordered CI job.

## 3. Recommended Directory Structure

A simple structure in a Maven project:

```text
my-api/
├── pom.xml
├── src/
│   ├── main/
│   │   └── java/
│   ├── test/
│   │   └── java/
│   │       └── ...DocumentationTest.java
│   └── docs/
│       └── asciidoc/
│           ├── index.adoc
│           ├── introduction.adoc
│           ├── products.adoc
│           └── orders.adoc
└── target/
    ├── generated-snippets/
    │   ├── products-get-success/
    │   └── orders-get-success/
    └── generated-docs/
        └── index.html
```

| Path | Content | Created / Managed By |
| --- | --- | --- |
| `src/test/java` | HTTP tests calling `document(...)` | Development team |
| `src/docs/asciidoc` | `.adoc` source docs and explanations | Development team / doc authors |
| `target/generated-snippets` | Snippets generated by tests | Spring REST Docs |
| `target/generated-docs` | Rendered documentation | Asciidoctor Maven plugin |

The `target` directory holds Maven build outputs and can be regenerated. Never place the sole copy of `.adoc` source files inside `target`, because `mvn clean` deletes that directory.

## 4. Preparing Spring REST Docs Dependencies

The examples below use MockMvc tests. In `pom.xml`, the Spring REST Docs MockMvc dependency is declared in project dependencies with `test` scope:

```xml
<properties>
    <java.version>17</java.version>
    <spring-restdocs.version>3.0.3</spring-restdocs.version>
    <asciidoctor.maven.plugin.version>2.2.6</asciidoctor.maven.plugin.version>
</properties>

<dependencies>
    <dependency>
        <groupId>org.springframework.restdocs</groupId>
        <artifactId>spring-restdocs-mockmvc</artifactId>
        <version>${spring-restdocs.version}</version>
        <scope>test</scope>
    </dependency>
</dependencies>
```

This example pins versions to illustrate a Maven setup; the Spring REST Docs version must be compatible with your project's Spring Framework/Spring Boot version. If your project already manages versions via a BOM or parent POM, use the existing dependency management mechanism and avoid conflicting version declarations.

Depending on your test client, the dependency varies:

| Test Client | Typical Spring REST Docs Dependency |
| --- | --- |
| MockMvc | `spring-restdocs-mockmvc` |
| WebTestClient | `spring-restdocs-webtestclient` |
| REST Assured | `spring-restdocs-restassured` |

Add only the dependency for the client you actually use. These dependencies serve tests; they do not replace the AsciiDoc compilation plugin.

## 5. Configuring the Snippet Output Directory

Before declaring Asciidoctor, know where Spring REST Docs writes snippets. For Maven, the standard convention is:

```text
${project.build.directory}/generated-snippets
```

The Maven property `project.build.directory` usually points to `target`. Thus, the actual path is typically `target/generated-snippets`.

### 5.1. Configuration via JUnit 5 and MockMvc

Spring REST Docs provides an extension to bind the snippet-generation context to tests. Example:

```java
@ExtendWith(RestDocumentationExtension.class)
class ProductDocumentationTest {

    private MockMvc mockMvc;

    @BeforeEach
    void setUp(
            WebApplicationContext context,
            RestDocumentationContextProvider restDocumentation) {

        mockMvc = MockMvcBuilders.webAppContextSetup(context)
            .apply(documentationConfiguration(restDocumentation))
            .build();
    }

    @Test
    void getProduct() throws Exception {
        mockMvc.perform(
                get("/api/products/{id}", 7L)
                    .accept(MediaType.APPLICATION_JSON)
            )
            .andExpect(status().isOk())
            .andDo(document("products-get-success"));
    }
}
```

This example omits imports and payload assertions to focus on setup. In real projects, use the proper request builders, fixtures, and contract descriptors. For MockMvc path parameters, use `RestDocumentationRequestBuilders.get(...)` to preserve the URI template when documenting path variables.

Another option is explicitly configuring the output directory via `JUnitRestDocumentation` or test configuration matching your version and test framework. The key requirement is that the directory written by tests **matches exactly** the `snippets` attribute used by the Asciidoctor plugin.

### 5.2. Confirm the Path Before Configuring the Plugin

After running tests, inspect the output:

```text
target/generated-snippets/products-get-success/
    http-request.adoc
    http-response.adoc
    path-parameters.adoc
    response-fields.adoc
```

Filenames and snippet counts depend on the declared descriptors. For instance, a GET request without a request body does not need a request-fields snippet; if a test never calls `responseFields(...)`, do not assume `response-fields.adoc` exists.

## 6. Declaring `asciidoctor-maven-plugin` in `pom.xml`

A basic configuration goes under `build/plugins`:

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.asciidoctor</groupId>
            <artifactId>asciidoctor-maven-plugin</artifactId>
            <version>${asciidoctor.maven.plugin.version}</version>

            <dependencies>
                <dependency>
                    <groupId>org.springframework.restdocs</groupId>
                    <artifactId>spring-restdocs-asciidoctor</artifactId>
                    <version>${spring-restdocs.version}</version>
                </dependency>
            </dependencies>

            <executions>
                <execution>
                    <id>generate-api-docs</id>
                    <phase>prepare-package</phase>
                    <goals>
                        <goal>process-asciidoc</goal>
                    </goals>
                </execution>
            </executions>

            <configuration>
                <sourceDirectory>
                    ${project.basedir}/src/docs/asciidoc
                </sourceDirectory>
                <outputDirectory>
                    ${project.build.directory}/generated-docs
                </outputDirectory>
                <backend>html</backend>
                <attributes>
                    <snippets>
                        ${project.build.directory}/generated-snippets
                    </snippets>
                    <toc>left</toc>
                    <toclevels>3</toclevels>
                    <sectnums>true</sectnums>
                </attributes>
            </configuration>
        </plugin>
    </plugins>
</build>
```

Main configuration elements:

| Element | Purpose |
| --- | --- |
| `groupId`, `artifactId` | Identifies the Maven plugin |
| `version` | Pins the plugin version |
| Plugin dependency `spring-restdocs-asciidoctor` | Provides Spring REST Docs' Asciidoctor integration/extension |
| `execution` | Names a plugin execution |
| `phase` | Hooks rendering into the Maven lifecycle |
| `goal` | Runs the `process-asciidoc` goal |
| `sourceDirectory` | AsciiDoc source directory |
| `outputDirectory` | Destination for HTML output |
| `backend` | Output format, here HTML |
| `attributes.snippets` | Path used by include directives to locate snippets |

Here `spring-restdocs-asciidoctor` is a **Maven plugin dependency**, declared inside `<plugin>`. It differs from `spring-restdocs-mockmvc` in `<project><dependencies>`, which is used at test compile/runtime. Without the plugin dependency, Spring REST Docs macros or Asciidoctor extensions may fail to load as expected by your project docs.

### 6.1. Why Choose the `prepare-package` Phase?

In the standard Maven lifecycle, the `test` phase runs before `prepare-package`. Therefore, when running `mvn package` or `mvn verify`, tests have already executed before documentation compilation bound to `prepare-package`.

Simple flow:

```text
validate
   │
compile
   │
test-compile
   │
test  ───────────────► Spring REST Docs generates snippets
   │
prepare-package ─────► asciidoctor-maven-plugin renders
   │
package
   │
verify
```

Binding the plugin to an earlier phase means snippets do not yet exist when Asciidoctor processes includes. Choosing a phase later than `test` preserves the right order within the same lifecycle. Projects with separate integration-test suites must check the phase/task of that suite and place rendering after its snippet-generation step.

### 6.2. Running the Goal Directly vs. Running via Lifecycle

You can invoke the plugin directly:

```bash
mvn asciidoctor:process-asciidoc
```

This runs the Asciidoctor goal, but does not automatically ensure snippet-generating tests ran in the same invocation. If snippet outputs do not exist yet or are left over from a previous run, rendering may fail or use stale data.

In a full workflow, prefer:

```bash
mvn clean verify
```

This cleans Maven outputs and runs phases from the start through `verify`, including tests and the documentation build bound to `prepare-package`.

## 7. Writing AsciiDoc Using the `snippets` Attribute

Create `src/docs/asciidoc/index.adoc`:

```asciidoc
= Product API
:toc: left
:toclevels: 3

== Introduction

Documentation describing the Product API.

=== Get product details

Use this endpoint to read a product by ID.

==== Request

include::{snippets}/products-get-success/http-request.adoc[]

==== Path parameters

include::{snippets}/products-get-success/path-parameters.adoc[]

==== Response

include::{snippets}/products-get-success/http-response.adoc[]

==== Response fields

include::{snippets}/products-get-success/response-fields.adoc[]
```

The `snippets` attribute comes from plugin configuration and points to `target/generated-snippets`. The resolved include path corresponds to:

```text
target/generated-snippets/
    products-get-success/
        http-request.adoc
```

Common mistakes:

- The name `products-get-success` does not match the identifier in `document(...)`.
- The test did not generate `path-parameters.adoc` because the descriptor was missing or the request builder did not preserve the URI template.
- The test did not generate `response-fields.adoc` because `responseFields(...)` was never called.
- The `snippets` attribute points to the output directory of a different module or test suite.
- AsciiDoc source files sit outside the configured `sourceDirectory`.

Do not add an include for a file simply assuming every operation produces every snippet. Only include files that the test actually generates.

## 8. Placing HTML Docs in Build Artifacts

With the configuration above, output is expected at:

```text
target/generated-docs/index.html
```

Documentation can be packaged alongside the application artifact, copied to a static site host, or published by a separate job. How it is distributed depends on your deployment setup; the plugin only builds docs according to configuration and does not publish to a website on its own.

If you need multiple AsciiDoc files, the plugin can process sources inside `sourceDirectory` per configuration. Choose a clear entry point and include structure to avoid duplicate pages or unintended outputs.

### 8.1. Putting Output in Artifacts

One option is generating docs in `target/generated-docs` and archiving them as a CI build artifact. If you want to bundle them inside a JAR/WAR, add a Maven resource step or configuration to copy the output folder into the artifact. Never assume `asciidoctor-maven-plugin` automatically embeds HTML into the JAR just because rendering succeeded.

### 8.2. Separating Documentation Builds from Application Builds

Some projects want developers to run tests quickly without rendering docs every time. You can place the execution inside a Maven profile, such as `api-docs`, so it runs only when enabled:

```xml
<profiles>
    <profile>
        <id>api-docs</id>
        <build>
            <plugins>
                <!-- Place asciidoctor-maven-plugin configuration here -->
            </plugins>
        </build>
    </profile>
</profiles>
```

Then CI commands must activate the profile:

```bash
mvn clean verify -Papi-docs
```

When the plugin sits inside a profile, running `mvn verify` without activating the profile will not generate HTML. Keep build policy explicit: either documentation is a mandatory release-pipeline gate or an optional artifact.

## 9. Integrating Maven with CI

A typical CI job:

```text
Checkout commit
     │
     ▼
mvn clean verify
     │
     ├── Compile failure ─────────► Fail
     ├── Documentation test fail ─► Fail
     ├── Descriptor mismatch ─────► Fail
     ├── Asciidoctor include fail ─► Fail
     │
     ▼
target/generated-snippets/
     │
     ▼
target/generated-docs/
     │
     ▼
Archive artifact / publish per pipeline
```

CI should run from a clean workspace to avoid leftover snippets from an earlier build. If profiles are used, activate them consistently in the job. In multi-module Maven builds, decide which module generates snippets, which compiles docs, and how outputs pass between modules.

### 9.1. Archive Artifacts Instead of Committing Build Outputs

Normally, do not commit `target/generated-snippets` or `target/generated-docs` as source files. They are reproducible build outputs. Archive the HTML as a pipeline artifact, or publish from a docs job after tests and rendering succeed.

Sources to manage in version control include:

- `pom.xml` and plugin configuration.
- Documentation tests.
- `.adoc` files and hand-written explanations.
- Any templates or scripts needed for the compilation workflow.

## 10. Common Errors and Troubleshooting

| Symptom | Possible Cause | How to Check / Fix |
| --- | --- | --- |
| Include reports file not found | Wrong `snippets` attribute or identifier | Compare plugin configuration against outputs and `document(...)` |
| Missing `generated-snippets` | Tests did not run or Spring REST Docs not configured | Check test discovery, extension/filter, and logs |
| Asciidoctor runs before tests | Execution bound to wrong phase or goal invoked standalone | Bind goal to a phase after `test`; run a lifecycle such as `mvn verify` |
| Response snippet exists but field table is missing | `responseFields(...)` not declared | Add descriptors if fields belong to the contract |
| Missing `path-parameters` snippet | Request builder did not preserve the URI template | Use the appropriate `RestDocumentationRequestBuilders` |
| Plugin ignores `snippets` attribute | XML placed in wrong element or misspelled attribute | Put inside `<configuration><attributes>` and inspect effective POM |
| Spring REST Docs extension does not work | Missing plugin dependency or wrong dependency scope | Check `spring-restdocs-asciidoctor` under plugin and test dependencies separately |
| `mvn asciidoctor:process-asciidoc` renders stale files | Goal ran without running tests first; leftover outputs remain | Run `mvn clean verify` |
| HTML does not appear where expected | Different `outputDirectory` or source entry point | Check `target/generated-docs` and plugin logs |
| HTML missing from JAR/WAR | Resource packaging step not added | Configure Maven resources or an artifact/publish task |
| Works locally but fails in CI | Different profile, JDK, path, or working directory | Use identical Maven commands and reproducible CI config |

### 10.1. Inspecting the Effective POM

When suspecting configuration overrides from a parent POM or profile, run:

```bash
mvn help:effective-pom
```

Inspect the plugin configuration after Maven merges all POMs. This command helps verify final versions, executions, phases, source/output directories, and attributes.

For detailed logs:

```bash
mvn -X clean verify
```

Use debug logging only when investigating issues because output is verbose and may include paths or environment details. Scrub sensitive data before sharing logs externally.

## 11. Best Practices

1. **Use properties for versions and paths:** keeps configuration synchronized and reduces duplication.
2. **Keep sources outside `target`:** `mvn clean` must never delete author-managed documentation content.
3. **Run tests before rendering:** prevents compiling documentation from stale snippets.
4. **Separate project dependencies from plugin dependencies:** keeps dependency scopes clear.
5. **Define attributes in one place:** pages reference `snippets` rather than hardcoding paths.
6. **Run `mvn clean verify` in CI:** verifies the entire lifecycle from a clean state.
7. **Use profiles intentionally:** make clear which jobs must build docs and which may skip them.
8. **Review final outputs:** check includes, links, sensitive data, headings, and success/error examples.
9. **Do not commit generated output as source:** track tests and `.adoc` files in git; generate HTML in the pipeline.
10. **Pin and upgrade versions deliberately:** keep plugin, extension, and Spring REST Docs aligned with the project toolchain.

## 12. Practice Exercise

Create a Maven project with a `GET /api/products/{id}` endpoint and a MockMvc documentation test.

**Requirements:**

1. Add the `spring-restdocs-mockmvc` dependency with `test` scope.
2. Configure `RestDocumentationExtension` and MockMvc so snippets are written to `target/generated-snippets`.
3. Write a test asserting status, ID, and one business field; call `document("products-get-success", ...)`.
4. Declare at least `pathParameters(...)` and `responseFields(...)`.
5. Create `src/docs/asciidoc/index.adoc` and include `http-request.adoc`, `path-parameters.adoc`, `http-response.adoc`, and `response-fields.adoc`.
6. Configure `asciidoctor-maven-plugin` with the `prepare-package` phase, source directory, and output directory.
7. Run `mvn clean verify`.
8. Confirm snippets and HTML are generated in the expected directories.
9. Temporarily change the identifier in the test without updating the include; observe the failure, then update the path and rerun.
10. Try running the Asciidoctor goal standalone after `clean` to see why snippets are missing if tests have not run.

**Completion criteria:** Maven runs tests before rendering, snippet outputs land in the right directory, all includes resolve, HTML is generated in `target/generated-docs`, and the build fails whenever tests or compilation encounter errors that need fixing.

## 13. Key Takeaways

- `spring-restdocs-mockmvc` is a project test dependency; `spring-restdocs-asciidoctor` can be declared as a plugin dependency to support Asciidoctor integration.
- `asciidoctor-maven-plugin` manages the source directory, output directory, backend, attributes, and execution in the Maven lifecycle.
- The `snippets` attribute must point to the exact directory where Spring REST Docs writes snippets, typically `target/generated-snippets` in Maven setups.
- Binding `process-asciidoc` to a phase after `test`, such as `prepare-package`, ensures snippets exist before being included.
- `mvn clean verify` verifies the complete pipeline from a clean output state; invoking the Asciidoctor goal standalone does not run tests.
- `.adoc` sources live in `src/docs/asciidoc`; snippets and HTML are generated outputs. Packaging or publishing HTML requires project-specific configuration.
