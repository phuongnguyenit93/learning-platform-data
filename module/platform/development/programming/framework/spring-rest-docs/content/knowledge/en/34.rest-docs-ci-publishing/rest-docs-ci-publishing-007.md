# Cache Dependencies Without Reusing Stale Snippets

## 1. Distinguishing Dependency Cache and Generated Output

CI can cache dependencies to reduce the time spent downloading Gradle/Maven libraries in subsequent builds. However, snippets generated by Spring REST Docs are **test outputs of the current commit**. If you cache and restore snippets from a previous build, the documentation may contain requests/responses that no longer match the current source code.

| Data | Example | Should it be cached across builds? |
| --- | --- | --- |
| Dependency cache | Gradle module cache, Maven local repository | Yes, with an appropriate cache key |
| Build tool wrapper | Gradle Wrapper distribution, Maven Wrapper | Can be cached/reused |
| Generated snippets | build/generated-snippets, target/generated-snippets | Should not be restored as cache |
| Rendered docs | build/docs, target/generated-docs | Do not use as cached input for a new build |
| Test reports | JUnit XML, HTML report | Save as CI artifact; do not use instead of fresh test results |

In the **SPRING_REST_DOCS** module, MockMvc, WebTestClient, or REST Assured generate snippets from test requests/responses. Asciidoctor/Markdown uses snippets to build documentation, and CI packages documentation into release artifacts. Every build must generate snippets from tests of the commit being built; dependency caching only speeds up downloading libraries.

## 2. Why Does Caching Snippets Cause Stale Documentation?

Suppose commit A has a test:

~~~java
mockMvc.perform(get("/orders/42"))
    .andDo(document("orders/get"));
~~~

Generated snippets:

~~~text
build/generated-snippets/orders/get/
├── http-request.adoc
└── http-response.adoc
~~~

In commit B, the endpoint changes to /v2/orders/42, and headers or response schemas also change. If CI restores commit A's build/generated-snippets and test B is skipped, fails, or fails to overwrite completely, Asciidoctor can include the old snippet.

The documentation build can still succeed yet fail to describe commit B's API. Dependency JARs are inputs with versions/checksums; snippets are test outputs dependent on source, fixtures, configuration, and execution environment.

Principles:

- Cache reusable downloaded data, such as dependencies.
- Regenerate source-dependent data on every build, such as REST Docs snippets.
- Render documentation only after snippet-generating tests succeed.
- Never use cache restoration to replace documentation tests.

## 3. Gradle: Cache Dependencies, Not Build Output

Gradle's dependency cache typically lives in Gradle User Home:

~~~text
~/.gradle/caches/modules-2/
~~~

Project build output typically lives at:

~~~text
project/build/
├── classes/
├── reports/
├── generated-snippets/
└── docs/
~~~

The Gradle cache holds downloaded dependency artifacts and metadata; build/ holds outputs from the current build.

In GitHub Actions, you can use the setup Gradle action to cache the wrapper and dependencies:

~~~yaml
name: Verify API documentation

on:
  pull_request:
  push:
    branches: [main]

jobs:
  docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
      - uses: gradle/actions/setup-gradle@v4
      - name: Build and verify documentation
        run: ./gradlew clean test asciidoctor
~~~

setup-gradle manages caching of Gradle User Home. The clean command removes workspace build output before tests and rendering. Do not add build/generated-snippets to any custom cache path list.

### 3.1. When Configuring actions/cache Manually

Select only the dependency cache and wrapper, not the project build directory:

~~~yaml
- name: Cache Gradle dependencies
  uses: actions/cache@v4
  with:
    path: |
      ~/.gradle/caches/modules-2
      ~/.gradle/wrapper
    key: gradle-linux-dependencies
~~~

The key example above is illustrative only; in real projects, the key should include the OS and hashes of dependency-management files such as build.gradle, settings.gradle, gradle-wrapper.properties, and version catalogs. Prefer the official setup Gradle action unless you have special caching requirements.

Do not cache:

~~~yaml
path: |
  ~/.gradle/caches
  build/
~~~

because build/ contains snippets, HTML, classes, and other output from previous builds. Caching a shared output directory makes it easy to restore generated data by mistake.

## 4. Maven: Cache Local Repository, Not target

Maven downloads dependencies and plugins into the local repository, typically:

~~~text
~/.m2/repository/
~~~

Maven project output typically lives in:

~~~text
project/target/
├── classes/
├── surefire-reports/
├── generated-snippets/
└── generated-docs/
~~~

In CI, caching ~/.m2/repository reduces dependency/plugin download time. Do not cache target/ because this directory holds test results and snippets from previous builds.

GitHub Actions example:

~~~yaml
- uses: actions/setup-java@v4
  with:
    distribution: temurin
    java-version: '21'
    cache: maven

- name: Verify API documentation
  run: mvn -B clean verify
~~~

cache: maven uses setup-java's built-in Maven dependency caching mechanism. mvn -B clean verify refreshes target and then runs tests, generates snippets, and renders documentation according to the configured lifecycle.

Do not configure a cache path like:

~~~yaml
path: |
  ~/.m2/repository
  target/
~~~

because target/ is not a dependency cache. In particular, never restore target/generated-snippets from another build.

## 5. Cache Keys and Restore Keys

Cache keys should reflect the inputs that determine dependencies:

- OS/runner if the cache includes platform-dependent components.
- Wrapper version.
- Build files such as build.gradle, settings.gradle, gradle/libs.versions.toml.
- pom.xml, parent POM, or Maven version management files.
- JDK if the cache/toolchain depends on the Java version.

Prefix-based restore keys help reuse the closest cache when build files change. The build tool still verifies dependencies and downloads missing pieces by metadata/version. Restore keys are solely for dependency caching, never for restoring snippets.

Do not include hashes of tests or document identifiers in the dependency cache key for the purpose of caching snippets. Tests must still run to verify current behavior.

## 6. Ensuring Snippets Are Freshly Generated on Every Build

Correct pipeline order:

~~~text
Checkout commit
      |
      v
Restore dependency cache
      |
      v
Clean project output
      |
      v
Run documentation tests
      |
      v
Generate snippets
      |
      v
Render Asciidoctor
      |
      v
Verify rendered docs
      |
      v
Upload release artifact
~~~

Gradle:

~~~bash
./gradlew clean test asciidoctor
~~~

Maven:

~~~bash
mvn -B clean verify
~~~

If the build separates regular tests and documentation tests into distinct tasks/profiles, ensure the snippet-generating task/profile is always invoked before Asciidoctor. Do not pass -x test, -DskipTests, or maven.test.skip=true in a documentation build job if the skipped tests are the source of snippets.

If you only want to skip unrelated tests, configure explicit test selection while still running all required documentation tests. Asciidoctor should fail when a required snippet does not exist, instead of silently using an old file.

## 7. Handling Reused Workspaces

Some self-hosted runners or CI workspaces persist across jobs. Even without caching build/ or target/, stale files can remain if the workspace is not clean.

Measures:

1. Run clean before the snippet-generating test step.
2. If a full clean is not possible, delete the exact generated-snippets directory before tests.
3. Never run multiple concurrent jobs in the same workspace and output directory.
4. Use an isolated workspace/job per build.
5. Upload artifacts only after verification; never grab artifacts from an old workspace.

Gradle can define a dedicated clean task:

~~~groovy
def snippetsDir = layout.buildDirectory.dir('generated-snippets')

tasks.register('cleanSnippets', Delete) {
    delete snippetsDir
}
~~~

Then:

~~~bash
./gradlew cleanSnippets test asciidoctor
~~~

With Maven, use mvn clean verify or configure Maven Clean Plugin to delete only the snippet directory if deleting all of target is not possible.

## 8. Do Not Let Asciidoctor Silently Use Stale Snippets

Asciidoctor includes a static path:

~~~adoc
include::{snippets}/orders/get/http-request.adoc[]
~~~

If a file from a previous build still exists, the include can succeed even though the current test did not generate that snippet. Therefore, merely checking that Asciidoctor succeeded is not sufficient.

Ways to increase reliability:

- Clean output before running documentation tests.
- Ensure tests call document(...) and the test task is a dependency of Asciidoctor.
- Use descriptors/field documentation so tests fail when requests/responses diverge from the contract.
- Verify required snippets were generated in the current build.
- Never allow CI to skip documentation tests yet still publish docs.

You can check snippet existence after tests:

~~~bash
test -f build/generated-snippets/orders/get/http-request.adoc
test -f build/generated-snippets/orders/get/http-response.adoc
~~~

With Maven, replace build/ with target/. These checks supplement tests; they do not replace verifying request/response content and status.

## 9. Test Result Caching Can Affect Snippet Generation

Gradle can mark a test task UP-TO-DATE or use the build cache if inputs/outputs allow it. If snippet outputs are deleted externally while Gradle still considers the test UP-TO-DATE, tests may not run and snippets will not be regenerated.

Proper output management:

~~~groovy
def snippetsDir = layout.buildDirectory.dir('generated-snippets')

tasks.named('test') {
    outputs.dir snippetsDir
}
~~~

Declaring the output lets Gradle track the snippet directory alongside the test task. If an external step deletes output, run clean or force the test task to re-run through an appropriate mechanism. Do not rely on a leftover snippets directory to prove the test task ran.

If using a remote build cache, evaluate whether the test task should be cached and whether outputs are completely deterministic and safe to share. For documentation tests, many teams choose to run real tests in release CI to guarantee snippets come from executing the current commit.

## 10. Common Issues

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Docs show old endpoint | Restored snippets from cache or old workspace | Remove build output caching, clean before tests |
| Asciidoctor succeeds even when docs tests skipped | Old snippets still exist | Clean output and enforce running documentation tests |
| Gradle test reports UP-TO-DATE yet snippets missing | Output deleted outside Gradle or outputs misconfigured | Declare outputs.dir, clean, or rerun tests |
| Maven uses snippets from previous build | Cached/restored target/ or clean not run | Cache only .m2/repository, run mvn clean verify |
| Continuous CI cache misses | Key changes too often or unsuitable file hashing | Hash dependency files and use restore prefix |
| Cache grows too large | Caching entire build output or unbounded cache | Cache only dependencies/wrapper; review retention |
| Parallel jobs overwrite shared snippets | Shared workspace/output root | Isolate workspace and output directory |
| Release artifact contains stale snippets | Packaged output before test/render finished | Wire proper dependencies and verify current snippets |

## 11. Hands-On Exercise

Configure CI for a Spring REST Docs project using Gradle or Maven:

1. Configure dependency caching: Gradle User Home or Maven local repository.
2. Exclude build/, target/, generated-snippets/, and rendered docs from the dependency cache.
3. Run a clean build and documentation tests.
4. Confirm snippets are regenerated in the current build's output directory.
5. Run Asciidoctor and inspect the HTML.
6. Modify a request/response fixture, re-run CI, and confirm snippets reflect the change.
7. Temporarily skip documentation tests in a controlled build; confirm the documentation pipeline cannot succeed using stale snippets.
8. Upload artifacts only after tests, rendering, and content checks succeed.

**Completion criteria:** Dependency caching makes builds faster; snippets are always generated from current tests; Asciidoctor never consumes stale output; artifacts are uploaded only after all verification steps pass.
