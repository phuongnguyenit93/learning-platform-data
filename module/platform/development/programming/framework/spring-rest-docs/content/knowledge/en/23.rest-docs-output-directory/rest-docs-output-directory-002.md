# Maven's target/generated-snippets Directory

## 1. Role of target/generated-snippets

In projects using **Apache Maven**, the **target/generated-snippets** directory is commonly configured as the location to store snippets generated by Spring REST Docs when running tests. When a test calls **document(...)**, REST Docs writes files describing the request, response, headers, parameters, or payload into a subdirectory named after the document identifier.

For example:

~~~text
project/
├── pom.xml
├── src/
│   ├── main/
│   ├── test/
│   └── docs/
│       └── asciidoc/
│           └── index.adoc
└── target/
    └── generated-snippets/
        └── registrations/
            └── create/
                ├── http-request.adoc
                ├── http-response.adoc
                ├── curl-request.adoc
                └── request-fields.adoc
~~~

**target** is Maven's standard build output directory. **generated-snippets** holds intermediate documentation automatically generated from tests; these files are typically included by Asciidoctor to produce the complete API documentation. The development team maintains tests and descriptors as the source of truth rather than manually editing generated snippets.

In the **SPRING_REST_DOCS** module, HTTP tests using MockMvc, WebTestClient, or REST Assured produce verifiable snippets. Asciidoctor/Markdown documentation combines the snippets into API reference pages; Maven orchestrates the test and rendering steps, and CI re-runs the pipeline to ensure the documentation matches endpoint behavior.

## 2. Why Does Maven Commonly Use target/generated-snippets?

Spring REST Docs does not require every Maven project to use a fixed path. **target/generated-snippets** is a common convention because:

- **target/** is Maven's default build directory, keeping build outputs separate from source code.
- **generated-snippets/** clearly indicates this is output generated from tests.
- Snippets can be used as input for the Asciidoctor Maven Plugin.
- **mvn clean** removes build outputs, including stale snippets, before the next clean build.

Distinguishing common directories:

| Path | Role |
| --- | --- |
| src/test/java | Test source code |
| src/docs/asciidoc | Team-authored AsciiDoc documentation |
| target/generated-snippets | Snippets generated from tests |
| target/generated-docs or Asciidoctor output directory | Rendered documentation, depending on plugin configuration |
| target/classes | Compiled classes |

Snippets are intermediate results. Rendered HTML/PDF is the subsequent artifact. Do not point the `snippets` attribute to the rendered HTML directory, and do not treat snippets as documentation source files edited directly.

## 3. Configuring Spring REST Docs to Write to target/generated-snippets

### 3.1. Configuring with @AutoConfigureRestDocs

In Spring Boot tests using MockMvc, you can specify the output directory directly on the test class:

~~~java
import org.springframework.boot.test.autoconfigure.restdocs.AutoConfigureRestDocs;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;

@WebMvcTest(RegistrationController.class)
@AutoConfigureRestDocs(outputDir = "target/generated-snippets")
class RegistrationDocumentationTest {
    // MockMvc tests
}
~~~

When the test calls:

~~~java
document("registrations/create", ...);
~~~

the snippets will be written under:

~~~text
target/generated-snippets/
└── registrations/
    └── create/
        ├── http-request.adoc
        ├── http-response.adoc
        └── ...
~~~

The `outputDir` value on the annotation specifies the location that Spring Boot test auto-configuration passes to REST Docs. This is an explicit, easy-to-read configuration when a project has a single output directory.

If `outputDir` is omitted, the default behavior may depend on the Spring Boot version and the REST Docs integration mechanism. Do not assume the default is always `target/generated-snippets`. For Maven projects, declaring it explicitly and aligning it with the POM is the least confusing approach.

### 3.2. Configuring via System Property

Spring REST Docs supports configuring the output directory via the system property **org.springframework.restdocs.outputDir**. Maven Surefire can pass this property to the JVM running the tests:

~~~xml
<properties>
<restdocs.outputDir>${project.build.directory}/generated-snippets</restdocs.outputDir>
</properties>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <configuration>
                <systemPropertyVariables>
                    <org.springframework.restdocs.outputDir>
                        ${restdocs.outputDir}
                    </org.springframework.restdocs.outputDir>
                </systemPropertyVariables>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

In this configuration:

- **project.build.directory** typically resolves to `target`.
- **restdocs.outputDir** creates a project property for reuse in the POM.
- Surefire sets the system property in the test JVM.
- REST Docs reads the property to write snippets if the test harness does not pass another explicit output directory.

**Choose a single primary configuration source.** If the **@AutoConfigureRestDocs(outputDir = "...")** annotation specifies `outputDir`, the value on the annotation can override the intent of configuring via the system property. Do not configure the annotation to point to one place and Surefire to another and expect snippets to synchronize automatically.

### 3.3. Tests Using the JUnit Extension

If you do not use Spring Boot test annotations, you can configure REST Docs via **RestDocumentationExtension**:

~~~java
@ExtendWith({SpringExtension.class, RestDocumentationExtension.class})
@WebMvcTest(RegistrationController.class)
class RegistrationDocumentationTest {
    private MockMvc mockMvc;

    @BeforeEach
    void setUp(
            WebApplicationContext context,
            RestDocumentationContextProvider restDocumentation) {
        this.mockMvc = MockMvcBuilders.webAppContextSetup(context)
            .apply(documentationConfiguration(restDocumentation))
            .build();
    }
}
~~~

The JUnit extension provides the context for REST Docs. The output directory is chosen by the context provider/extension or the REST Docs configuration for the library version in use. When Maven needs to use `target/generated-snippets`, confirm that the context provider receives the right output path; do not merely declare the property in the POM without verifying that the test harness uses it.

## 4. Configuring the Maven Plugin to Render Asciidoctor

A typical Maven build has two related stages:

1. Surefire runs the tests, and REST Docs generates snippets.
2. The Asciidoctor Maven Plugin reads the AsciiDoc pages along with the snippets and renders HTML/PDF.

Sample POM (abbreviated; plugin versions should be managed centrally by the project):

~~~xml
<properties>
    <restdocs.outputDir>${project.build.directory}/generated-snippets</restdocs.outputDir>
    <asciidoctor.outputDir>${project.build.directory}/generated-docs</asciidoctor.outputDir>
</properties>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <configuration>
                <systemPropertyVariables>
                    <org.springframework.restdocs.outputDir>
                        ${restdocs.outputDir}
                    </org.springframework.restdocs.outputDir>
                </systemPropertyVariables>
            </configuration>
        </plugin>

        <plugin>
            <groupId>org.asciidoctor</groupId>
            <artifactId>asciidoctor-maven-plugin</artifactId>
            <version>${asciidoctor.maven.plugin.version}</version>
            <executions>
                <execution>
                    <id>generate-api-docs</id>
                    <phase>prepare-package</phase>
                    <goals>
                        <goal>process-asciidoc</goal>
                    </goals>
                    <configuration>
                        <sourceDirectory>src/docs/asciidoc</sourceDirectory>
                        <outputDirectory>${asciidoctor.outputDir}</outputDirectory>
                        <attributes>
                            <snippets>${restdocs.outputDir}</snippets>
                        </attributes>
                    </configuration>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>
~~~

This is an illustrative skeleton to understand how configuration pieces connect, not a complete POM to copy directly without checking plugin versions and dependency management. The **asciidoctor.maven.plugin.version** property must be declared with the version chosen in the project.

### 4.1. Meaning of Each Part in the POM

| Component | Role |
| --- | --- |
| restdocs.outputDir | Configuration source for the snippets directory |
| Surefire systemPropertyVariables | Passes the output path into the test-running JVM |
| sourceDirectory | Location of the source AsciiDoc files |
| outputDirectory | Location where the plugin writes rendered documentation |
| attributes/snippets | Path used to resolve `{snippets}` in includes |
| prepare-package | Rendering phase that runs after earlier test phases in the standard lifecycle |

Placing rendering in a phase after `test` ensures snippets are generated before Asciidoctor includes them. If you bind the plugin to too early a phase, documentation rendering may fail because snippets do not yet exist.

### 4.2. Using Includes in AsciiDoc

Suppose the test generates the identifier **registrations/create-form**; the **src/docs/asciidoc/index.adoc** page can be written as:

~~~adoc
= Registration API

== Create Registration with Form

=== HTTP request
include::{snippets}/registrations/create-form/http-request.adoc[]

=== Form parameters
include::{snippets}/registrations/create-form/form-parameters.adoc[]

=== HTTP response
include::{snippets}/registrations/create-form/http-response.adoc[]
~~~

Maven passes the `snippets` attribute as the `target/generated-snippets` path. The include path under the attribute is resolved using the document identifier and snippet filename. When changing an identifier or output directory, update the related configuration and includes accordingly.

## 5. Maven Lifecycle and Execution Order

A commonly used pipeline:

~~~bash
mvn clean verify
~~~

In the standard Maven lifecycle:

- The **test** phase runs tests through Surefire.
- Tests call `document(...)` and generate snippets.
- **prepare-package** runs after `test` and before `package`.
- The Asciidoctor plugin bound to `prepare-package` renders documentation from the snippets.
- Subsequent phases can package the documentation into an artifact if configured in the POM.

Running alone:

~~~bash
mvn test
~~~

will run tests and generate snippets, but will not necessarily render Asciidoctor if the plugin is bound to `prepare-package`. To build the documentation, invoke a sufficiently late phase, such as **mvn prepare-package**, **mvn package**, or **mvn verify**.

Conversely, running the Asciidoctor plugin goal alone without running tests first can leave the snippets directory empty or containing stale data. In CI, prefer a single lifecycle command so Maven manages the execution order.

## 6. Multi-Module Maven Configuration

Suppose the repository has:

~~~text
root/
├── pom.xml
├── registration-api/
│   ├── pom.xml
│   └── target/generated-snippets/
└── documentation/
    ├── pom.xml
    └── src/docs/asciidoc/index.adoc
~~~

Each Maven module has its own **project.build.directory**; by default this is `target` inside that module. Therefore, `registration-api` tests may generate snippets at:

~~~text
registration-api/target/generated-snippets/
~~~

while the `documentation` module needs to read snippets from the API module. Choose one of two approaches:

1. Configure the documentation plugin in the same module that contains the tests and snippets.
2. Explicitly configure a shared output/input location or copy snippet artifacts via a managed Maven step.

Do not assume `project.build.directory` in a child module automatically points to the root project's `target`. In a Maven reactor, that property is resolved per current project. For documentation aggregating multiple APIs, design a clear shared path and ensure snippet-producing modules run before the documentation-rendering module via dependencies and module ordering.

If using a shared path at the root, reference the root build directory with the appropriate Maven property after verifying the reactor layout. Do not hardcode absolute paths that depend on a developer's machine.

## 7. Managing Stale Snippets and Clean Builds

Old snippets may remain if a test or document identifier is deleted. For example, a previous build generated:

~~~text
target/generated-snippets/
├── registrations/create/
└── registrations/update/
~~~

After the update test is deleted, the `registrations/update` directory may still exist if the build does not clean outputs. Documentation could then mistakenly include an old snippet, misleading readers into believing the API is still verified.

Good practices:

1. Keep snippets inside `target/` so `mvn clean` manages them.
2. Run `mvn clean verify` when you need to regenerate all documentation.
3. Do not directly edit generated snippet files.
4. Update tests/descriptors and re-run the documentation lifecycle.
5. Do not include snippets from another workspace or an old cache without verifying their source.

**mvn clean** deletes build outputs, including `target/generated-snippets`; tests then generate a fresh set of snippets. This is a simple way to avoid orphaned files in a clean build.

## 8. Differences from Gradle

Common directory names depend on the build tool:

| Build tool | Build directory | Commonly used snippets directory |
| --- | --- | --- |
| Maven | target/ | target/generated-snippets |
| Gradle | build/ | build/generated-snippets |

These two paths are conventions, not technical limitations of Spring REST Docs. They can be customized, but must remain consistent across tests, build tasks/plugins, and the Asciidoctor attribute.

Do not copy Gradle configurations like `outputs.dir`, `inputs.dir`, and `dependsOn` verbatim into a POM. Maven manages ordering through lifecycle phases, plugin executions, and inter-module dependencies.

## 9. Common Issues

| Symptom | Possible Cause | How to Fix |
| --- | --- | --- |
| `target/generated-snippets` does not exist | Tests with `document(...)` have not run, were skipped, or REST Docs is not configured | Run the specific test and inspect Surefire logs |
| Snippets appear in `build/generated-snippets` | Annotation or system property points to the Gradle path | Check the actual `outputDir` |
| Tests generate snippets, but Asciidoctor cannot find them | The `snippets` attribute points to the wrong location or identifier/include mismatch | Compare absolute path, identifier, and filename |
| `mvn test` finishes, but no HTML is generated | Asciidoctor is bound to a phase after `test` | Run `mvn prepare-package` or `mvn verify` |
| HTML contains stale snippets | Output was not cleaned after deleting tests/identifiers | Run `mvn clean verify` |
| Running docs module misses snippets from API module | Snippet-producing module has not run or output is not shared | Configure reactor/module ordering and artifact paths |
| System property has no effect | Test annotation or context provider specifies another output path | Choose one primary configuration and inspect the test harness |
| Snippets exist, but include fails | Relative path is missing the document identifier | Include the exact identifier directory under the snippet root |

Verification checklist:

1. Does Surefire run the documentation tests?
2. Which output directory does the test harness receive?
3. Which module's `target` directory are snippets written into?
4. In which phase does the Asciidoctor Maven Plugin run?
5. Does the `snippets` attribute point to the right snippets directory?
6. Do includes have the right identifier and snippet name?
7. Does a clean build regenerate the entire documentation?

## 10. Practice Exercise

In a Spring Boot Maven project, create a MockMvc test for the `POST /registrations` endpoint and generate `http-request.adoc`, `http-response.adoc`, and `form-parameters.adoc`.

Steps:

1. Configure `restdocs.outputDir` as `project.build.directory/generated-snippets`.
2. Pass the `org.springframework.restdocs.outputDir` system property into the test JVM using Surefire.
3. Write a test calling `document("registrations/create-form", ...)`.
4. Configure the Asciidoctor Maven Plugin to use the same `restdocs.outputDir` as the `snippets` attribute.
5. Bind the documentation rendering execution to a phase after `test`, such as `prepare-package`.
6. Include request, form parameters, and response snippets in the AsciiDoc page.
7. Run `mvn clean verify`, inspect the snippets under `target/generated-snippets/registrations/create-form/` and the HTML in the output directory.
8. Delete or change the document identifier, run a clean build again, and verify that the documentation does not use stale snippets.

**Completion criteria:** Surefire writes snippets to the right `target` directory; Asciidoctor reads the exact same directory; the Maven lifecycle ensures tests run before rendering; a clean build produces complete documentation without relying on old outputs.
