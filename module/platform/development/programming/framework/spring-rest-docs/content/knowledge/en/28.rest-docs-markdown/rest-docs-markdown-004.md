# Relative Paths to Generated Snippets

## 1. Objectives and Context

Spring REST Docs generates snippets from HTTP tests into an output directory, usually `build/generated-snippets` with Gradle or `target/generated-snippets` with Maven. Asciidoctor pages include snippets with the directive:

~~~asciidoc
include::{snippets}/orders-get/http-request.adoc[]
~~~

The `snippets` attribute must point to the exact directory containing generated snippets. If the attribute is undeclared, points to the wrong module, or the render task runs before the test task, Asciidoctor will not find the files.

This lesson belongs to the **Markdown** chapter of the **SPRING_REST_DOCS** module: creating verifiable REST API documentation from HTTP tests using MockMvc, WebTestClient, or REST Assured; generating snippets for requests, responses, payloads, parameters, and headers; authoring Asciidoctor/Markdown and integrating build/CI.

After this lesson, you will be able to distinguish source documents, generated snippets, and rendered output; configure relative paths with Asciidoctor; pass the snippet root via Gradle/Maven; organize includes in multi-module builds; and diagnose include errors.

> Paths in include directives are filesystem paths resolved by the build tool/Asciidoctor. They are not endpoint URLs called by API clients.

## 2. Three Path Locations to Distinguish

| Location | Example | Role |
| --- | --- | --- |
| Source documentation | `src/docs/asciidoc/index.adoc` | Asciidoc file containing explanations and include directives. |
| Generated snippets | `build/generated-snippets/orders-get/http-request.adoc` | Files generated by REST Docs after tests record operations. |
| Rendered documentation | `build/docs/asciidoc/html5/index.html` | HTML file created by Asciidoctor. |

~~~mermaid
flowchart LR
    A["HTTP tests"] --> B["build/generated-snippets"]
    C["src/docs/asciidoc/index.adoc"] --> D["Asciidoctor include"]
    B --> D
    D --> E["build/docs/.../index.html"]
~~~

Tests create snippets at B; source Asciidoc files live at C; Asciidoctor reads both source and snippets to create HTML at E. HTML output is not an include source.

### 2.1. Where Are Relative Paths Resolved From?

- Source paths in Gradle are usually resolved from the project directory.
- The `snippets` attribute usually holds the filesystem path to the generated snippets directory.
- Include paths are resolved by Asciidoctor according to the document base directory/include path and build configuration.
- The output HTML directory is only where rendered results are written.

Do not assume every relative path is resolved from the terminal working directory. When running Gradle from the root, a subproject, or CI, the working directory may differ. Prefer constructing paths from the Gradle project layout and passing them explicitly to Asciidoctor.

## 3. Including Snippets Using an Asciidoctor Attribute

Asciidoc page:

~~~asciidoc
= Orders API

== Get Order

=== HTTP request
include::{snippets}/orders-get/http-request.adoc[]

=== HTTP response
include::{snippets}/orders-get/http-response.adoc[]

=== Response fields
include::{snippets}/orders-get/response-fields.adoc[]
~~~

`{snippets}` is a document attribute. Asciidoctor replaces the attribute with its configured value and looks up the corresponding file.

Example output:

~~~text
build/
└── generated-snippets/
    └── orders-get/
        ├── http-request.adoc
        ├── http-response.adoc
        └── response-fields.adoc
~~~

If the attribute points to `build/generated-snippets`, the included file is constructed from the snippet root, identifier `orders-get`, and filename `http-request.adoc`. The identifier comes from `document("orders-get")`. Snippet name and extension must match exactly.

### 3.1. Setting the Attribute in the Source Document

For small docs, it can be declared at the top of the file:

~~~asciidoc
= Orders API
:snippets: ../../build/generated-snippets

== Get Order

include::{snippets}/orders-get/http-request.adoc[]
~~~

Relative path values are resolved according to Asciidoctor's document/include context and project structure. Moving the source file to a subfolder can break the path. For multi-environment/multi-module builds, pass the attribute from Gradle/Maven so sources do not depend on build layout.

### 3.2. Undeclared Attribute

If the source uses `{snippets}` without the build passing the attribute, includes may fail to resolve. Check the attribute name, directory existence, identifier, filename, and task dependency. Do not work around this by manually copying snippets into source docs, as that creates two copies of data that can drift apart.

## 4. Gradle: Sharing a Snippets Directory

Groovy DSL example:

~~~groovy
plugins {
    id 'java'
    id 'org.asciidoctor.jvm.convert' version '4.0.2'
}

ext {
    snippetsDir = file("$buildDir/generated-snippets")
}

dependencies {
    testImplementation 'org.springframework.restdocs:spring-restdocs-mockmvc'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

test {
    outputs.dir snippetsDir
}

asciidoctor {
    inputs.dir snippetsDir
    dependsOn test
    attributes 'snippets': snippetsDir
}
~~~

This is an illustrative configuration; plugin/dependency versions should match your project. Key points:

1. `snippetsDir` defines the snippets directory inside the build directory.
2. `test` declares the output directory.
3. `asciidoctor` depends on `test` so snippets are generated first.
4. `inputs.dir` declares the task input for Gradle.
5. `attributes` passes the path to Asciidoctor under the name `snippets`.

REST Docs tests must write to this exact directory. If tests write to directory A while Asciidoctor reads from directory B, includes will be missing even though both tasks ran.

### 4.1. Using the Gradle Layout API

~~~groovy
def snippetsDir = layout.buildDirectory.dir('generated-snippets')

tasks.named('test') {
    outputs.dir snippetsDir
}

tasks.named('asciidoctor') {
    inputs.dir snippetsDir
    dependsOn tasks.named('test')
    attributes 'snippets': snippetsDir.get().asFile
}
~~~

The `asciidoctor` task must be created by the plugin before configuring it. If the plugin is applied in a convention plugin or another subproject, adjust where the configuration is placed according to that lifecycle.

### 4.2. Never Hard-Code Personal Machine Paths

Avoid absolute paths like `C:/Users/dev/project/build/generated-snippets`. They only exist on a specific machine. Use the Gradle file/layout API so paths are constructed from the current project directory and build directory.

### 4.3. Task Dependencies Do Not Depend on Declaration Order

Writing the `asciidoctor` block after the `test` block does not guarantee tests run first. Gradle executes the task graph according to dependencies. Use `dependsOn test` or depend on the specific integration test task if that task generates snippets.

~~~groovy
asciidoctor {
    dependsOn integrationTest
    inputs.dir snippetsDir
}
~~~

Ensure the integration test writes to the exact directory Asciidoctor reads. Depending on a test task that does not generate REST Docs will not fix include errors.

## 5. Maven: Passing the Snippets Path via Property

Maven typically uses `target/generated-snippets`. The Asciidoctor Maven Plugin accepts a `snippets` attribute pointing to this directory.

~~~xml
<properties>
    <snippetsDirectory>target/generated-snippets</snippetsDirectory>
</properties>

<build>
    <plugins>
        <plugin>
            <groupId>org.asciidoctor</groupId>
            <artifactId>asciidoctor-maven-plugin</artifactId>
            <configuration>
                <attributes>
                    <snippets>target/generated-snippets</snippets>
                </attributes>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

This illustrates how to pass the property/attribute; a project still needs executions/phases and a test configurer to generate snippets. In multi-module Maven builds, distinguish a module's base directory and build directory from the root project's. Do not copy Gradle configuration verbatim into Maven because lifecycles, goals, phases, and property handling differ.

What must remain consistent: tests write to the exact directory Asciidoctor reads.

## 6. Multi-Module: Source Docs and Snippets in Two Projects

Example structure:

~~~text
spring-rest-docs/
├── build.gradle
├── settings.gradle
├── api-service/
│   ├── build.gradle
│   └── src/test/java/...
└── docs/
    ├── build.gradle
    └── src/docs/asciidoc/index.adoc
~~~

Tests live in `api-service`, and Asciidoctor runs in `docs`. Paths might be:

- Snippets: `api-service/build/generated-snippets`.
- Source docs: `docs/src/docs/asciidoc/index.adoc`.
- HTML output: `docs/build/docs/asciidoc/html5`.

Conceptual configuration in the `docs` project:

~~~groovy
def apiSnippets = project(':api-service')
    .layout.buildDirectory
    .dir('generated-snippets')

tasks.named('asciidoctor') {
    inputs.dir apiSnippets
    attributes 'snippets': apiSnippets.get().asFile
    dependsOn ':api-service:test'
}
~~~

Actual configuration must match the Gradle version, plugins, and dependencies between projects. Explicitly reference the project producing snippets and avoid relative paths relying on an implicit working directory.

### 6.1. Shared Output or Separate Outputs?

| Approach | Pros | Risks |
| --- | --- | --- |
| Each module has its own output | Clear ownership and lifecycle | Aggregated docs must read from multiple folders. |
| Single shared output directory | Centralized includes | Identifier collisions, harder to isolate producers. |

If using a shared directory, identifiers should be namespaced such as `billing-orders-get` and `identity-users-get`. Each operation directory should only have one producer writing to it.

## 7. Include Paths vs. URLs

Includes read files from the filesystem at build time:

~~~asciidoc
include::{snippets}/orders-get/http-request.adoc[]
~~~

They are not sent to the browser and are not public URLs. Conversely, a website link:

~~~markdown
[View authentication](authentication.html)
~~~

is handled by the browser/site renderer when the reader opens the page.

| Path Type | Example | Resolved By |
| --- | --- | --- |
| Snippet include | `{snippets}/orders-get/http-request.adoc` | Asciidoctor/build. |
| Source file | `src/docs/asciidoc/index.adoc` | Gradle/Maven project layout. |
| HTML output | `build/docs/asciidoc/html5` | Asciidoctor output configuration. |
| Website link | `/api/authentication/` | Browser/web server/site generator. |

Do not use internal filesystem paths as public links.

## 8. Markdown and Generated Snippets

Spring REST Docs supports the Markdown template format, but plain Markdown has no standard file include directive. Therefore `include::{snippets}/...[]` is only used directly in Asciidoctor.

With Markdown snippets:

~~~text
build/generated-snippets/
└── orders-get/
    ├── http-request.md
    ├── http-response.md
    └── response-fields.md
~~~

You need a static site generator supporting partials, an include plugin, a file-assembling build task, or a preprocessor. The snippets path must be configured in the assembly tool; Asciidoctor's `snippets` attribute does not automatically apply to Markdown renderers.

## 9. Identifier, Filename, and Extension

~~~text
<snippets-root>/<operation-identifier>/<snippet-name>.<extension>
~~~

Example:

~~~text
build/generated-snippets/orders-get/http-response.adoc
~~~

| Component | Source |
| --- | --- |
| `snippets-root` | Gradle/Maven and Asciidoctor attribute. |
| `orders-get` | Identifier in `document("orders-get")`. |
| `http-response` | Standard or custom snippet name. |
| `.adoc` | Active template format. |

When switching to Markdown, the extension changes to `.md` and how snippets are assembled may also change. Do not just change the extension if the include toolchain still processes the old format.

Separate success/error identifiers to avoid including the wrong response:

~~~asciidoc
include::{snippets}/orders-get-success/http-response.adoc[]
include::{snippets}/orders-get-not-found/http-response.adoc[]
~~~

## 10. Diagnosing Path Errors

When Asciidoctor reports a missing snippet, check in order:

1. Did the test run and complete successfully?
2. Does the identifier match the `document(...)` call?
3. Did REST Docs write files into that output directory?
4. Does the template format produce the expected extension?
5. Was the `snippets` attribute passed to the Asciidoctor task?
6. Does the include path combine root/identifier/filename properly?
7. Does the render task depend on the snippet-generating test task?
8. In multi-module builds, does it point to the project producing snippets?

Illustrative error message:

~~~text
include file not found:
build/generated-snippets/orders-get/http-response.adoc
~~~

The message indicates Asciidoctor is looking for the file at the resolved path. The test may still have run, but written to a different directory, used a different identifier, or generated a different extension.

### 10.1. Inspecting the Output Directory

~~~text
build/generated-snippets/orders-get/
├── http-request.adoc
├── http-response.adoc
└── response-fields.adoc
~~~

If the operation folder is missing, check whether the test called `document(...)` and the operation wrote snippets. If a single file is missing, check whether the test declared that snippet type. Not every operation generates all snippets.

### 10.2. Case Sensitivity and Separators

Windows is usually case-insensitive on its default filesystem; Linux CI is usually case-sensitive. Identifiers and filenames must match exact casing. Prefer Gradle/Maven handling path separators via File/Directory/Provider APIs instead of manually concatenating slashes/backslashes per machine.

## 11. Complete Gradle Example

~~~groovy
plugins {
    id 'java'
    id 'org.asciidoctor.jvm.convert' version '4.0.2'
}

def snippetsDir = layout.buildDirectory.dir('generated-snippets')

dependencies {
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.restdocs:spring-restdocs-mockmvc'
}

tasks.named('test') {
    outputs.dir snippetsDir
}

tasks.named('asciidoctor') {
    dependsOn tasks.named('test')
    inputs.dir snippetsDir
    sourceDir file('src/docs/asciidoc')
    outputDir layout.buildDirectory.dir('docs/asciidoc').get().asFile
    attributes 'snippets': snippetsDir.get().asFile
}
~~~

REST Docs tests must also write to this exact `snippetsDir`. The specific output directory depends on how it is configured via annotation, JUnit extension, or REST Docs configurer. Choose a single place as the single source of truth for the path.

Asciidoc source:

~~~asciidoc
= Orders API

== Get Order

=== Request
include::{snippets}/orders-get/http-request.adoc[]

=== Response
include::{snippets}/orders-get/http-response.adoc[]

=== Fields
include::{snippets}/orders-get/response-fields.adoc[]
~~~

If the source document also declares `snippets`, align the values so the source attribute does not differ from the build value.

## 12. CI and Clean Builds

~~~mermaid
flowchart TD
    A["Checkout source"] --> B["Clean build outputs"]
    B --> C["Run REST Docs tests"]
    C --> D{"Tests pass?"}
    D -->|No| X["Fail CI"]
    D -->|Yes| E["Verify generated-snippets"]
    E --> F["Run Asciidoctor"]
    F --> G{"Includes resolve and render pass?"}
    G -->|No| X
    G -->|Yes| H["Review artifact"]
    H --> I["Publish"]
~~~

CI must ensure:

- Snippet-generating tests run before Asciidoctor.
- REST Docs output directory and Asciidoctor attribute use the same path.
- Builds do not rely on stale generated files left over from prior builds.
- Required includes must resolve.
- Builds fail if a snippet is missing, rather than silently skipping files.
- Multi-module task dependencies are explicit.
- Website links are checked after rendering, separate from filesystem includes.

There is no need to commit generated snippets if the build regenerates them reliably. If snippets are committed for review, establish conventions for diff updates and avoid including stale output.

## 13. Common Issues

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Include file not found | `snippets` undeclared or wrong directory | Verify attribute passed from build. |
| Test produces snippets but Asciidoctor cannot see them | Test writes to directory A, Asciidoctor reads B | Share a single path definition. |
| Passes locally, fails in CI | Path depends on working directory or stale files | Use layout API and clean builds. |
| Identifier folder does not exist | `document(...)` used a different identifier | Match test/include identifiers. |
| `.md` files generated but include expects `.adoc` | Mismatched template format | Use matching extension/toolchain. |
| Response snippet missing | Test did not declare descriptor or body does not exist | Verify whether the snippet is generated. |
| Multi-module include wrong | Relative path resolved from wrong project | Reference the project generating snippets. |
| Passes on Windows, fails on Linux | Case mismatch or separator issue | Use exact names and path APIs. |
| Asciidoctor runs before tests | Missing task dependency | `dependsOn` snippet-generating task. |
| HTML links broken even though includes pass | Confusing filesystem paths with URLs | Check links after rendering. |

## 14. Practice Exercise

Create documentation for `GET /api/orders/101` with identifier `orders-get` and `POST /api/orders` with identifier `orders-create`.

Steps to perform:

1. Configure MockMvc so REST Docs generates snippets into `build/generated-snippets`.
2. Run tests and verify folders by identifier.
3. Create `src/docs/asciidoc/index.adoc`, including request/response via `snippets`.
4. Configure Gradle to pass the exact snippets directory and make Asciidoctor depend on the snippet-generating test task.
5. Move the Asciidoc source into a subfolder; verify includes still resolve via the attribute.
6. Run the build from root and subproject if applicable; ensure no dependency on terminal working directory.
7. Intentionally change an identifier or extension to observe the include error.
8. If using Markdown, configure a dedicated Markdown assembly tool and define the base path.
9. Run a clean build in CI; publish only when tests, includes, and rendering succeed.

**Completion criteria:** accurately distinguish source path, snippets path, and output path; pass attributes properly; understand identifier/filename/extension; declare task dependencies; regenerate documentation from clean builds locally and in CI.
