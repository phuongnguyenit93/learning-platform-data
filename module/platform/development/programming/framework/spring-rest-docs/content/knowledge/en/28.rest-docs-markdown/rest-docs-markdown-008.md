# Ensuring Markdown Output Is Readable on the Target Platform

## 1. Objectives and Context

Spring REST Docs can generate snippets in Markdown format from HTTP tests. However, having `.md` files and valid syntax does not guarantee readers will see the documentation as intended. The result also depends on the **Markdown parser, dialect, renderer, extensions, theme, security configuration, and how the site is hosted**.

For example, field tables generated by Spring REST Docs may use Markdown Extra syntax. A platform that only enables CommonMark may render the table as plain text. Relative links may work in local preview yet break after deployment under a different base path. Code fences may render properly on Git hosting yet lose syntax highlighting in a static site generator.

This lesson belongs to the **Markdown** chapter of the **SPRING_REST_DOCS** module. The module creates verifiable REST API documentation from HTTP tests using MockMvc, WebTestClient, or REST Assured; generates snippets for requests, responses, payloads, parameters, and headers; authors Asciidoctor/Markdown and integrates with build/CI.

After this lesson, you will be able to:

- Select and lock down the Markdown parser/dialect on the target platform.
- Verify tables, headings, anchors, code fences, links, and images.
- Handle embedded HTML, sanitization, and renderer security constraints.
- Keep UTF-8 encoding, newlines, and Vietnamese text stable.
- Create production-like previews and automate output checks in CI.
- Distinguish snippet generator errors from Markdown renderer/site hosting errors.

> The source of truth for API content is the tests and generated snippets. The preview/renderer is responsible for presentation. When rendering goes wrong, determine whether the bug is in snippet generation, page assembly, or final rendering before editing sources.

## 2. Separating Markdown Generation and Display Steps

A documentation pipeline typically has these steps:

1. HTTP tests run and Spring REST Docs records operations.
2. The Markdown template format renders snippets into `.md` files.
3. A build task assembles snippets with explanatory prose into pages.
4. A Markdown parser reads sources and builds the document structure.
5. A renderer/site generator produces HTML.
6. The theme, CSS, sanitizer, and browser determine final appearance.

~~~mermaid
flowchart LR
    A["HTTP tests"] --> B["REST Docs operation"]
    B --> C["Markdown snippets"]
    C --> D["Assemble page"]
    D --> E["Markdown parser"]
    E --> F["HTML renderer / theme"]
    F --> G["Target platform"]
~~~

Snippet file existence does not prove the final page included it. An assembled page having content does not prove the parser supports the dialect. Successful HTML rendering still does not prove links, anchors, or code blocks work in production.

### 2.1. Identify the Target Platform Before Writing Templates

Before customizing Markdown templates, determine:

- Publishing platform: Git hosting, MkDocs, Docusaurus, Hugo, another site generator, or an internal system.
- Active parser and dialect.
- Enabled extensions/plugins.
- Heading anchors and base URL.
- Raw HTML and embedded content policies.
- Theme/CSS for tables, code blocks, tabs, and admonitions.
- How local previews and production builds are produced.

Do not verify solely in an editor. An editor may use a different parser from the production renderer.

## 3. Markdown Dialect and Spring REST Docs Generated Tables

Spring REST Docs Markdown templates use tables in the **Markdown Extra** dialect. Example fields table:

~~~markdown
|Path|Type|Description|
|---|---|---|
|id|Number|Order ID|
|status|String|Order status|
|total|Number|Total amount in VND|
~~~

A renderer supporting Markdown Extra tables displays a three-column table. If the parser only supports minimal CommonMark, lines may appear as raw text containing pipe characters.

### 3.1. Compatibility Approaches

| Approach | When Suitable | Notes |
| --- | --- | --- |
| Enable table extension | Platform allows parser configuration | Pin extension/version in build. |
| Choose a renderer supporting Markdown Extra | Want to keep default snippets | Test on target platform. |
| Override Markdown templates | Constrained to a specific dialect | Test output and preserve field metadata. |

Do not manually edit raw generated snippets. Snippets will be regenerated on the next test run. If a different dialect is needed, change the template or use a controlled conversion step.

### 3.2. Overly Wide Tables

Field tables can have long descriptions, deeply nested JSON paths, or many columns. On small screens, tables easily overflow horizontally. You can:

- Write concise descriptions, moving long explanations into paragraphs.
- Avoid adding columns that do not help readers.
- Use a theme with horizontal overflow for tables.
- Group complex fields by object.
- Check both desktop and mobile viewports.

Do not strip constraints or field meanings just to make tables narrower. Reorganize the content to preserve the API contract intact.

## 4. Headings, Anchors, and Table of Contents

Headings create navigation structure. Many Markdown renderers auto-generate anchors from heading text, but slug rules can differ for Vietnamese/Unicode diacritics, punctuation, duplicate headings, inline code/links, and renderer versions.

Example:

~~~markdown
## Create order
### Request fields
### Response fields
~~~

Link to heading:

~~~markdown
[View Request fields](#request-fields)
~~~

Exact anchors must be verified against rendered HTML or the documentation tool in use. Do not assume all renderers strip diacritics or generate slugs identically.

### 4.1. Duplicate Headings

If one page has multiple operations sharing the heading `Request fields`, the renderer may generate duplicate anchors or append suffixes automatically. The table of contents may point to the wrong section.

Prefer contextual headings:

~~~markdown
### Create order — Request fields
### Update order — Request fields
### Delete order — Response
~~~

Or use explicit anchors if the platform supports stable syntax. When renaming headings, recheck internal links and navigation sidebars.

### 4.2. Heading Rules

- Use a single H1 as the main title.
- Do not skip heading levels arbitrarily.
- Use headings for information hierarchy, not just font size.
- Keep headings short and descriptive.
- Check that the table of contents reflects the right levels.
- Do not rely on accidental slugs generated from long descriptive sentences.

A clean hierarchy supports navigation, accessibility, and maintainability.

## 5. Code Fences and Syntax Highlighting

REST Docs snippets can contain HTTP requests/responses or JSON bodies. Use fenced code blocks with language identifiers supported by the renderer.

HTTP and JSON example:

~~~~markdown
~~~http
POST /api/orders HTTP/1.1
Content-Type: application/json
~~~

~~~json
{
  "customerId": 101,
  "items": [
    {
      "sku": "BOOK-42",
      "quantity": 2
    }
  ]
}
~~~
~~~~

When code content already contains three consecutive backticks or tildes, use a longer outer fence or a different delimiter. This is important when a page contains Markdown examples holding code fences.

Common issues:

- Forgetting a closing fence turns the rest of the page into code.
- Language identifier not recognized by the renderer.
- Syntactically invalid JSON still gets highlighted.
- HTTP snippets truncated across lines by preprocessing.
- Code blocks inside partials mis-nested during assembly.

### 5.1. Syntax Highlighting Does Not Validate Syntax

Renderers can highlight JSON/Java even if the code does not compile or the JSON is invalid. HTTP snippets reflect tested operations, but author-written explanatory code blocks still require separate validation.

Use identifiers such as `java`, `json`, `http`, `bash`, or languages supported by your renderer. If unsure of the identifier, plain text is safer than a wrong tag.

## 6. Relative Links and Base URLs

Markdown supports relative links:

~~~markdown
[View Authentication](authentication.md)
[View Orders API](../orders/index.md)
~~~

Links are resolved by the site generator/browser based on page location, permalinks, and base URL. When a site deploys under a subpath such as `/docs/v2/`, root-relative links can behave differently from file-relative links.

Check:

- Links between pages in source.
- Links to anchors on the same page.
- Links from operations to schemas/authentication.
- External links to reference documentation.
- Base URL in preview and production.
- Trailing slash and permalink strategy.
- Links to downloadable files/image assets.

### 6.1. Snippet Paths Are Not Website URLs

REST Docs/Asciidoctor includes use filesystem paths at build time. Website links are opened by browsers after publishing. Never put `build/generated-snippets/...` paths into public links expecting browsers to access the build directory.

After assembly, reader links must point to pages/assets inside the site output. Generated file paths are strictly for the build/preprocessor.

### 6.2. Link Checkers

A link checker can detect non-existent target files, missing anchors in HTML, broken relative paths after deployment, broken redirects/external URLs, and links to unpublished source paths.

External links may be blocked by CI networks or rate limits. Configure sensible retries/allowlists and distinguish transient network failures from genuinely broken links.

## 7. Images, Diagrams, and Assets

When adding images:

~~~markdown
![Request flow through API gateway](images/order-request-flow.png)
~~~

Notes:

- Store assets in a source-controlled directory or generate them during the build.
- Use relative paths compatible with the site generator.
- Write meaningful alt text describing the content.
- Optimize image file sizes.
- Test images under the production base path.
- Never use filesystem paths from a personal machine.

Mermaid may be supported by some platforms, though not every renderer enables the Mermaid plugin. Confirm extension/renderer support and provide fallbacks such as SVG/PNG or text descriptions if needed.

## 8. Raw HTML and Sanitization

Markdown parsers may permit some inline/block HTML, but hosting platforms may sanitize HTML to mitigate XSS risks. Stripped tags/attributes can make production output differ from local previews.

HTML example:

~~~html
<details>
  <summary>Response details</summary>
  Additional collapsible content.
</details>
~~~

Some platforms support `details`/`summary`, while other renderers strip them or show them as text. Inline scripts, event handlers, and embedded iframes may be blocked completely.

Guidelines:

- Do not rely on arbitrary JavaScript in Markdown.
- Do not inject untrusted HTML from responses/user input.
- Do not disable sanitization merely to keep decorative widgets.
- Prefer platform-supported components/extensions.
- Inspect rendered HTML/DOM after sanitization.
- Provide fallback text if advanced HTML is stripped.

If snippets contain test-generated API data, avoid embedding that data directly into raw HTML. Code blocks and escaped text are safer for presenting requests/responses.

## 9. UTF-8, Vietnamese Text, and Line Endings

Vietnamese documentation must preserve UTF-8 from source to site output. Encoding errors can arise in snippets, preprocessors, build processes, or renderers.

Verify:

- Source Markdown files are saved as UTF-8.
- HTTP response fixtures specify a deterministic charset when containing text.
- The build process does not fall back to the OS default encoding.
- The renderer/HTML document declares UTF-8.
- LF/CRLF line endings are handled consistently.
- Unicode normalization does not corrupt field names or links.
- Search/indexing still matches accented words.

For API responses, charset must follow the real HTTP `Content-Type`; do not infer charset from Markdown files.

### 9.1. Whitespace and Line Breaks

Markdown has specific rules for paragraphs, hard line breaks, list continuations, and blockquotes. Some editors soft-wrap lines visually without changing file newlines; preprocessors may strip blank lines.

Inspect assembled pages to ensure:

- Headings do not stick to preceding paragraphs.
- Nested lists preserve indentation.
- Code blocks preserve whitespace.
- Tables are not broken mid-row.
- Subsequent snippets are separated by proper blank lines.

## 10. Themes, Responsive Layout, and Accessibility

The same Markdown HTML can look different depending on theme CSS. Check:

| Component | What to Confirm |
| --- | --- |
| Headings | Sizes, hierarchy, anchors. |
| Tables | Overflow, wrapping, and header semantics. |
| Code blocks | Contrast, horizontal scroll, copy button. |
| Links | Color, underline, focus state. |
| Images | Dimensions, alt text, and scaling. |
| Admonitions | Icons, colors, and fallback text. |
| Navigation | Sidebar, TOC, active section. |
| Mobile | No full-page horizontal overflow. |

Never rely on color alone to indicate error/success. Headings and alt text must be meaningful; links should have descriptive labels; code blocks must remain readable on small screens.

## 11. Production-Like Previews

Previewing in another Markdown viewer is insufficient if it uses a different parser/theme from production. Use the actual site generator and deployment configuration for local previews.

Workflow:

1. Run tests generating Spring REST Docs snippets.
2. Assemble source pages and snippets.
3. Run the site generator with the same config/extensions as production.
4. Open pages in a browser at desktop and mobile widths.
5. Inspect headings, tables, links, images, and code highlighting.
6. Inspect HTML after sanitization if the host applies one.
7. Test navigation from the index/sidebar to every operation.

If the platform cannot provide a 100% production-identical local preview, document the differences and add a smoke test in a post-deploy preview environment.

## 12. Automating Verification in CI

~~~mermaid
flowchart TD
    A["HTTP tests"] --> B["Generate Markdown snippets"]
    B --> C["Assemble pages"]
    C --> D["Validate Markdown syntax"]
    D --> E["Render with pinned platform toolchain"]
    E --> F["Check links, anchors and assets"]
    F --> G["Inspect generated HTML / warnings"]
    G --> H{"All checks pass?"}
    H -->|No| X["Fail CI"]
    H -->|Yes| I["Publish docs"]
~~~

CI should:

- Pin parser, renderer, extensions, and theme versions.
- Run snippet-generating tests before assemble/render.
- Fail if required snippets are missing.
- Validate Markdown and code fences.
- Check for broken links/anchors/assets.
- Render the entire site, not just a single file.
- Fail on unresolved include markers or critical warnings.
- Save HTML artifacts for review when pull requests change docs.
- Publish only after tests and rendering pass.

Upgrade versions intentionally, read changelogs, re-render, and review visual changes.

### 12.1. Reviewing Source Diffs and Rendered Diffs

Generated Markdown diffs show text/template changes. Rendered HTML or screenshot previews show actual changes to tables, headings, code blocks, and links. The two review forms complement each other.

For major changes, save preview artifacts for reviewers to inspect. Screenshots are unnecessary for every prose edit; use them when templates/themes/layouts change significantly.

## 13. Output Verification Matrix

| Item | Verification Method | Expected Outcome |
| --- | --- | --- |
| Markdown tables | Render on target parser | Correct table columns/headers. |
| Headings | Check outline | Sound hierarchy. |
| Anchors | Link checker | TOC points to exact sections. |
| Code fences | Markdown lint/render | Code blocks open/close cleanly. |
| Syntax highlighting | Browser preview | Valid language identifiers. |
| Links | Link checker/browser | Relative/base paths work. |
| Images/diagrams | Build/browser | Assets load with alt text. |
| Raw HTML | Check post-sanitization | Permitted content still renders. |
| UTF-8 | Source and HTML | Vietnamese diacritics render cleanly. |
| Mobile layout | Responsive check | Tables/code scroll cleanly. |
| Accessibility | Keyboard/outline/contrast | Navigation and content accessible. |
| Clean build | Pipeline from empty output | Reproducible, deterministic output. |

## 14. Common Issues

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Fields table renders as text | Renderer lacks Markdown Extra table support | Enable extension or override template. |
| TOC points to wrong place | Anchor slug differs by renderer | Check after render or set stable IDs. |
| Code block swallows rest of page | Unclosed or mis-nested fence | Check delimiters, use longer outer fence. |
| Java/JSON not highlighted | Wrong language ID or missing highlighter | Use a supported identifier. |
| Links work locally, fail on deploy | Different base URL/permalinks | Preview with production config. |
| Images fail to load | Wrong relative path or asset unpublished | Check asset output. |
| HTML `details` disappears | Sanitizer stripped tags/attributes | Use supported component or fallback. |
| Garbled Vietnamese diacritics | Inconsistent encoding | Keep UTF-8 across entire pipeline. |
| Tables overflow on mobile | Wide columns or theme lacks overflow | Adjust content/theme while keeping full info. |
| Markdown lint passes, site breaks | Linter uses different parser/theme from target | Render with production toolchain. |
| Preview differs from production | Unpinned versions/plugins/theme | Share a unified configuration. |
| Stale snippets rendered | Stale output or wrong task dependency | Clean outputs and run tests before render. |

## 15. Practice Exercise

Take an API page containing at least three operations, request/response field tables, code examples, cross links, and an illustration image.

Steps to perform:

1. Identify the target platform, parser/dialect, renderer, and extensions.
2. Run REST Docs tests and assemble the Markdown page.
3. Render field tables; verify Markdown Extra tables are supported.
4. Check the table of contents, headings, and anchors, including duplicate/Vietnamese headings.
5. Check HTTP/JSON code fences and language identifiers.
6. Check relative links, base URL, images/diagrams, and asset paths.
7. Test raw HTML allowed by the platform; verify sanitization and fallback.
8. Check UTF-8, newlines, table overflow, and responsive layout.
9. Create a local preview using production config and store HTML artifacts in CI.
10. Configure a link checker, Markdown validation, and render gate before publish.

**Completion criteria:** the Markdown page renders accurately on the target renderer; tables/headings/code/links/images are error-free; Vietnamese text preserves UTF-8; local preview matches production; CI catches Markdown, link, and render errors before publishing.
