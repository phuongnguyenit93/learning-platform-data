# Request Part Headers in Spring REST Docs

## 1. Why Care About Individual Part Headers?

A `multipart/form-data` request consists of an overall HTTP request containing multiple parts inside. Each part has a name, content, and can have its own headers. When uploading an image together with JSON metadata, for example:

- The `image` part carries the image bytes and has `Content-Type: image/png`.
- The `metadata` part carries JSON and has `Content-Type: application/json`.
- The `image` part typically has `Content-Disposition` with `name="image"` and `filename="cover.png"`.

These headers serve different roles. HTTP-level headers such as `Authorization`, `Accept`, or `Content-Type: multipart/form-data; boundary=...` apply to the entire request. Headers inside a part such as `Content-Type: image/png` or `Content-Disposition: form-data; name="image"; filename="cover.png"` describe that specific part.

In Spring REST Docs, `requestHeaders(...)` generates a snippet for **outer HTTP request headers**. `requestParts(...)` describes the name and purpose of each part; `requestPartBody(...)` and `requestPartFields(...)` describe part contents. Spring REST Docs does not provide a built-in standard snippet named `requestPartHeaders(...)`. Therefore, when you need to document individual part headers, you present them in multipart request examples or build a custom snippet from operation data.

This lesson belongs to the **Request parts** chapter of SPRING_REST_DOCS. This module practices producing verifiable REST API documentation from HTTP tests using MockMvc, WebTestClient, or REST Assured, then integrating snippets into Asciidoctor/Markdown and build/CI.

After this lesson, you will be able to:

- Distinguish HTTP request-level headers from individual multipart part headers.
- Recognize common headers such as `Content-Disposition` and `Content-Type`.
- Use `requestHeaders(...)` within its proper scope.
- Combine `requestParts(...)`, part body, and part fields to document a multipart contract.
- Verify individual part headers in tests and decide when a custom snippet is needed.
- Avoid confusing filename, part name, MIME type, and boundary.

## 2. Two Header Layers in a Multipart Request

Example `POST /api/images` sending an image and metadata:

```http
POST /api/images HTTP/1.1
Authorization: Bearer <access-token>
Accept: application/json
Content-Type: multipart/form-data; boundary=----UploadBoundary

------UploadBoundary
Content-Disposition: form-data; name="image"; filename="cover.png"
Content-Type: image/png

<bytes of the PNG image>
------UploadBoundary
Content-Disposition: form-data; name="metadata"
Content-Type: application/json; charset=UTF-8

{
  "title": "Book Cover",
  "description": "Cover image for the new edition"
}
------UploadBoundary--
```

They can be layered as follows:

| Header | Scope | Example | Purpose |
| --- | --- | --- | --- |
| `Authorization` | Entire HTTP request | `Bearer ...` | Authenticates the request |
| `Accept` | Entire HTTP request | `application/json` | Response format expected by the client |
| Outer `Content-Type` | Entire HTTP request | `multipart/form-data; boundary=...` | Indicates a multipart body and defines the boundary |
| Part `Content-Disposition` | Single part | `form-data; name="image"; filename="cover.png"` | Identifies the part name and sent filename |
| Part `Content-Type` | Single part | `image/png` | Describes the part's content format |
| JSON part `Content-Type` | Single part | `application/json; charset=UTF-8` | Specifies JSON and charset of metadata |

**The boundary is not a part name.** It is the delimiter separating parts in the multipart body, generated by the client/HTTP stack and attached to the outer `Content-Type`. Do not hard-code the boundary in contract documentation because its value can change on every request.

## 3. Distinguishing Request-Level and Part-Level Header Documentation APIs

### 3.1. `requestHeaders(...)` Documents Outer Headers

Spring REST Docs uses `requestHeaders(...)` with `headerWithName(...)` to document headers of the entire HTTP request:

```java
import static org.springframework.restdocs.headers.HeaderDocumentation.headerWithName;
import static org.springframework.restdocs.headers.HeaderDocumentation.requestHeaders;

.andDo(document("images-upload",
        requestHeaders(
                headerWithName("Authorization")
                        .description("Bearer token used for authentication"),
                headerWithName("Accept")
                        .description("Response format accepted by the client"),
                headerWithName("Content-Type")
                        .description("Multipart request body")
        ),
        requestParts(
                partWithName("image")
                        .description("Product image to upload"),
                partWithName("metadata")
                        .description("JSON metadata of the image")
        )
));
```

The outer header snippet is usually named `request-headers.adoc`. It does not automatically generate rows for `Content-Type: image/png` or `Content-Disposition` inside a part.

### 3.2. Individual Part Headers Reside in the Multipart Body

For a file part, for example:

```http
Content-Disposition: form-data; name="image"; filename="cover.png"
Content-Type: image/png
```

`requestParts(...)` creates a table of part names and part descriptions; it is not a table of every header on each part. `requestPartBody("metadata")` generates the body snippet of the `metadata` part; it is not a dedicated header snippet either.

You can use `http-request.adoc` generated by the operation to include an HTTP request example in the documentation. When inspecting specific output, verify how much of the multipart body/headers your active integration and formatter render; do not assume `request-parts.adoc` contains all raw headers.

### 3.3. There Is No Standard `requestPartHeaders(...)` API

In the current Spring REST Docs API, the primary utilities for multipart include:

| API | Scope |
| --- | --- |
| `requestParts(...)` | Names and descriptions of parts |
| `partWithName(...)` | Descriptor for a single part |
| `requestPartBody("metadata")` | Body of a single part |
| `requestPartFields("metadata", ...)` | Fields inside a part's JSON payload |
| `requestHeaders(...)` | HTTP request-level headers |

Do not write `requestPartHeaders(...)` as if it were a built-in Spring REST Docs method. If a separate table for part headers is needed, you can create a custom snippet or document headers in Asciidoctor prose next to the sample request.

## 4. Documenting Multipart Requests with MockMvc

Suppose the `POST /api/images` endpoint accepts `image` and `metadata`, returning `201 Created` on a valid upload. The project already has Spring Boot, JUnit 5, MockMvc, and the `spring-restdocs-mockmvc` dependency.

### 4.1. Creating Parts with Filename and Content Type

```java
import java.nio.charset.StandardCharsets;

import org.springframework.http.MediaType;
import org.springframework.mock.web.MockMultipartFile;

MockMultipartFile image = new MockMultipartFile(
        "image",
        "cover.png",
        MediaType.IMAGE_PNG_VALUE,
        validPngBytes()
);

String metadataJson = """
        {
          "title": "Book Cover",
          "description": "Cover image for the new edition"
        }
        """;

MockMultipartFile metadata = new MockMultipartFile(
        "metadata",
        "",
        MediaType.APPLICATION_JSON_VALUE,
        metadataJson.getBytes(StandardCharsets.UTF_8)
);
```

The arguments of `MockMultipartFile`, in order, are:

1. `name`: the part name, e.g. `image`.
2. `originalFilename`: the filename sent by the client, e.g. `cover.png`.
3. `contentType`: the content type of the part, e.g. `image/png`.
4. `content`: the bytes of the part.

The name `image` is the value that must match `partWithName("image")` and the controller parameter name. `cover.png` is the filename, not the part name.

### 4.2. Combining Request Headers and Request Parts

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.restdocs.AutoConfigureRestDocs;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.MediaType;
import org.springframework.mock.web.MockMultipartFile;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.restdocs.headers.HeaderDocumentation.headerWithName;
import static org.springframework.restdocs.headers.HeaderDocumentation.requestHeaders;
import static org.springframework.restdocs.mockmvc.MockMvcRestDocumentation.document;
import static org.springframework.restdocs.request.RequestDocumentation.partWithName;
import static org.springframework.restdocs.request.RequestDocumentation.requestParts;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.multipart;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
class ImageMultipartHeadersDocumentationTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void documentMultipartRequestHeadersAndParts() throws Exception {
        MockMultipartFile image = new MockMultipartFile(
                "image",
                "cover.png",
                MediaType.IMAGE_PNG_VALUE,
                validPngBytes()
        );

        MockMultipartFile metadata = new MockMultipartFile(
                "metadata",
                "",
                MediaType.APPLICATION_JSON_VALUE,
                """
                {"title":"Book Cover","description":"Cover image for the new edition"}
                """.getBytes(StandardCharsets.UTF_8)
        );

        mockMvc.perform(multipart("/api/images")
                    .file(image)
                    .file(metadata)
                    .header("Authorization", "Bearer test-token")
                    .accept(MediaType.APPLICATION_JSON))
                .andExpect(status().isCreated())
                .andDo(document("images-upload",
                        requestHeaders(
                                headerWithName("Authorization")
                                        .description("Authentication bearer token"),
                                headerWithName("Accept")
                                        .description("Response format accepted by the client"),
                                headerWithName("Content-Type")
                                        .description("Multipart request body")
                        ),
                        requestParts(
                                partWithName("image")
                                        .description("PNG image to upload"),
                                partWithName("metadata")
                                        .description("JSON metadata describing the image")
                        )
                ));
    }

    private byte[] validPngBytes() {
        // Read bytes of a valid PNG fixture from test resources.
        return TestFixtures.validPng();
    }
}
```

This is an illustrative example; `TestFixtures.validPng()` represents a project helper that loads a fixture file. When running real tests, replace the helper with a valid PNG resource and an assertion status matching the endpoint.

In the example, `requestHeaders(...)` documents outer `Authorization`, `Accept`, and `Content-Type`; `requestParts(...)` documents the two parts. Each part's content type is attached when building `MockMultipartFile`. The request headers table does not replace documentation about `image/png` or `application/json` inside each part.

## 5. Documenting JSON Metadata Inside a Part

`requestParts(...)` only describes parts at the multipart level. If `metadata` contains JSON, use the payload part APIs to document deeper details.

### 5.1. Generating a Part Body Snippet

```java
import static org.springframework.restdocs.payload.PayloadDocumentation.requestPartBody;

.andDo(document("images-upload",
        requestParts(
                partWithName("image").description("PNG image"),
                partWithName("metadata").description("JSON metadata")
        ),
        requestPartBody("metadata")
));
```

The generated snippet is named `request-part-metadata-body.adoc` and contains the body of the `metadata` part.

### 5.2. Generating a JSON Part Fields Snippet

```java
import static org.springframework.restdocs.payload.PayloadDocumentation.fieldWithPath;
import static org.springframework.restdocs.payload.PayloadDocumentation.requestPartFields;

.andDo(document("images-upload",
        requestParts(
                partWithName("image").description("PNG image"),
                partWithName("metadata").description("JSON metadata")
        ),
        requestPartFields("metadata",
                fieldWithPath("title")
                        .description("Image title"),
                fieldWithPath("description")
                        .description("Image description")
                        .optional()
        )
));
```

The `request-part-metadata-fields.adoc` snippet describes fields inside the JSON. This is field-level payload documentation; it is not a part header table.

## 6. When Is a Custom Snippet Needed for Part Headers?

If the contract requires a dedicated table like:

| Part | Header | Value or Rule |
| --- | --- | --- |
| `image` | `Content-Disposition` | `name="image"`; client-provided filename |
| `image` | `Content-Type` | `image/png` or `image/jpeg` |
| `metadata` | `Content-Disposition` | `name="metadata"` |
| `metadata` | `Content-Type` | `application/json` |

there are two options.

### 6.1. Writing a Contract Table in Asciidoctor

If part headers are stable and simple, a static table is easy to maintain:

```adoc
=== Individual Part Headers

|===
|Part |Header |Rule

|`image`
|`Content-Disposition`
|`name="image"`; client-provided filename

|`image`
|`Content-Type`
|`image/png` or `image/jpeg`

|`metadata`
|`Content-Disposition`
|`name="metadata"`

|`metadata`
|`Content-Type`
|`application/json`
|===
```

This is author-maintained contract prose. It is not automatically verified by `requestParts(...)`; tests are needed to confirm actual content types and filenames.

### 6.2. Building a Custom Snippet from Operation Request Parts

In Spring REST Docs' operation model, each `OperationRequestPart` provides part name, filename, content, and headers. You can use this data to build a custom snippet if you want the table generated from test requests.

Example of data readable inside a custom snippet:

```java
import org.springframework.restdocs.operation.Operation;
import org.springframework.restdocs.operation.OperationRequestPart;

for (OperationRequestPart part : operation.getRequest().getParts()) {
    String partName = part.getName();
    String filename = part.getSubmittedFileName();

    // Part headers, e.g. Content-Type and Content-Disposition.
    HttpHeaders headers = part.getHeaders();
}
```

The snippet above illustrates the data API to read, not a complete snippet. When implementing one, create a class implementing `Snippet`, receive `Operation` in the snippet generation callback, convert part data into an AsciiDoc/Markdown table, and write output via Spring REST Docs' snippet mechanism. Output filename, template, escaping, and sensitive header handling must be defined in the project's implementation.

If you only need headers for a few parts, the custom snippet can select only `Content-Type` and `Content-Disposition`, rather than dumping all headers. Avoid writing headers containing tokens, cookies, or internal info into published documentation.

## 7. Verifying Individual Part Headers in Tests

Documentation presents the contract; HTTP tests must confirm the application handles the expected content type, filename, and part content.

Scenarios worth testing:

| Scenario | Expectation per example contract |
| --- | --- |
| `image` with `Content-Type: image/png` and valid PNG bytes | Accepted |
| `image` with `Content-Type: image/jpeg` and valid JPEG bytes | Accepted if API supports JPEG |
| `image` with `Content-Type: text/plain` | Rejected if only images are accepted |
| `metadata` with `Content-Type: application/json` | JSON is parsed |
| `metadata` with unsupported content type | Rejected or handled per contract |
| Filename containing invalid characters | Normalized or rejected per policy |
| Empty filename | Handled per contract, not inferred from part name |

A client-declared `Content-Type` does not prove the bytes actually match that format. If the endpoint needs protection against spoofed MIME types, inspect the file signature or parse the content with an appropriate library.

With MockMvc, `MockMultipartFile` lets you specify `contentType` and `originalFilename` to create fixtures with different characteristics. Endpoint tests should send these variants and verify response status/body. For documentation tests, keep one sample request representing the success case and assign separate operation IDs to other scenarios if standalone snippets are needed.

## 8. WebTestClient and REST Assured

### 8.1. WebTestClient

To set headers on a part in a WebTestClient request, you can wrap the part content in `HttpEntity` with `HttpHeaders` when building `MultiValueMap`:

```java
HttpHeaders metadataHeaders = new HttpHeaders();
metadataHeaders.setContentType(MediaType.APPLICATION_JSON);

HttpEntity<String> metadataPart =
        new HttpEntity<>(metadataJson, metadataHeaders);

MultiValueMap<String, Object> parts = new LinkedMultiValueMap<>();
parts.add("image", imageResource);
parts.add("metadata", metadataPart);

webTestClient.post()
        .uri("/api/images")
        .contentType(MediaType.MULTIPART_FORM_DATA)
        .body(BodyInserters.fromMultipartData(parts))
        .exchange()
        .expectStatus().isCreated()
        .expectBody()
        .consumeWith(document("images-upload",
                requestParts(
                        partWithName("image").description("Product image"),
                        partWithName("metadata").description("JSON metadata")
                )
        ));
```

`HttpEntity` attaches headers to the part when Spring message converters construct the multipart request. For a file `Resource`, the filename can come from `getFilename()`; content type can be inferred or explicitly configured using an appropriate wrapper.

### 8.2. REST Assured

REST Assured supports declaring multipart parts with content types:

```java
given(this.spec)
        .filter(document("images-upload",
                requestParts(
                        partWithName("image").description("Product image"),
                        partWithName("metadata").description("JSON metadata")
                )))
        .multiPart("image", imageFile, "image/png")
        .multiPart("metadata", metadataJson, "application/json")
        .when()
        .post("/api/images")
        .then()
        .statusCode(201);
```

Exact `multiPart(...)` overload syntax should be verified against your project's REST Assured version. Regardless of which builder is used, the part names and content types ultimately sent on the wire are what need to match.

## 9. Common Errors

| Symptom | Cause | Resolution |
| --- | --- | --- |
| `requestHeaders(...)` does not list `image/png` | Describing outer headers | Use multipart examples or a custom snippet for individual part headers |
| Confusing outer `Content-Type` with part `Content-Type` | Two headers share a name but have different scopes | Clarify scope in the documentation |
| `requestParts(...)` does not display filename | Snippet documents part name/purpose | Put filename in sample request or a custom snippet if a table is needed |
| Confusing filename with part name | Reading `filename` instead of `name` in Content-Disposition | Use `partWithName("image")` matching `name` |
| JSON metadata lacks a fields table | Only `requestParts(...)` was called | Add `requestPartFields("metadata", ...)` |
| Body snippet does not appear | `requestPartBody("metadata")` was not called | Add the body snippet if needed |
| Wrong content type still passes test | Missing endpoint-side validation | Add validation and negative tests |
| Docs leak Authorization or Cookie | Recording raw sensitive headers in snippets | Mask or use dummy tokens in fixtures |
| Asciidoctor reports missing include | Operation name or snippet was not generated | Check test and output directory |

## 10. Asciidoctor and Build/CI

The document source can include the available snippets:

```adoc
= Image API
:toc: left

== Image Upload

=== HTTP Request Headers
include::{snippets}/images-upload/request-headers.adoc[]

=== Multipart Parts
include::{snippets}/images-upload/request-parts.adoc[]

=== Metadata Body
include::{snippets}/images-upload/request-part-metadata-body.adoc[]

=== Metadata Fields
include::{snippets}/images-upload/request-part-metadata-fields.adoc[]

=== Individual Part Headers
See the multipart contract table maintained in this section or the project's custom snippet.
```

Only include snippets that the tests actually generate. With Gradle and the Asciidoctor plugin configured:

```groovy
def snippetsDir = file('build/generated-snippets')

tasks.named('test') {
    outputs.dir snippetsDir
}

tasks.named('asciidoctor') {
    dependsOn tasks.named('test')
    inputs.dir snippetsDir
    attributes 'snippets': snippetsDir
}
```

CI flow:

```text
Multipart HTTP tests
       |
       +--> requestHeaders (HTTP-level headers)
       |
       +--> requestParts (part names and descriptions)
       |
       +--> requestPartBody / requestPartFields
       |
       +--> custom snippet if individual part headers are needed
       |
       v
Asciidoctor / Markdown export step
       |
       v
Verify and publish
```

If the project exports Markdown, a custom template or conversion step is required; Spring REST Docs does not generate `.md` snippets by default. When part headers change, tests for content type/filename and custom snippets (if any) must re-run in CI.

## 11. Practice Exercise

With the `POST /api/images` endpoint:

1. Create `image` and `metadata` with two different content types. Verify each part's name and `Content-Type`.
2. Add `Authorization` and `Accept` on the HTTP request. Use `requestHeaders(...)` to document outer headers.
3. Verify why `requestHeaders(...)` does not generate `image/png` and `application/json` rows for individual parts.
4. Add `requestPartBody("metadata")` and `requestPartFields("metadata", ...)` to describe the JSON body and schema.
5. Write an Asciidoctor table documenting `Content-Disposition` and `Content-Type` for each part.
6. If automated output is required, build a custom snippet reading `OperationRequest.getParts()` and `OperationRequestPart.getHeaders()`.
7. Write negative tests for wrong MIME type, invalid filename, and metadata with wrong content type.
8. Verify snippets contain no real tokens/cookies; run tests before rendering Asciidoctor in CI.

### Self-Assessment Questions

- How does the overall request's `Content-Type` differ from the `Content-Type` inside a part?
- At what scope does `requestHeaders(...)` document headers?
- Does `partWithName("image")` correspond to `name` or `filename` in `Content-Disposition`?
- Why doesn't `requestParts(...)` generate a header table for each part?
- When are `requestPartBody(...)` and `requestPartFields(...)` useful?
- What data on `OperationRequestPart` can be used to build a custom snippet?
- Why must Authorization and Cookie values be masked before exporting snippets?

**Remember:** Multipart requests have headers at two layers: HTTP-level headers and individual part headers. `requestHeaders(...)` only documents the outer layer; `requestParts(...)` documents the parts. To present headers such as `Content-Type` and `Content-Disposition` for individual parts, use multipart examples or a custom snippet based on the operation's part data, and test those rules against real requests.
