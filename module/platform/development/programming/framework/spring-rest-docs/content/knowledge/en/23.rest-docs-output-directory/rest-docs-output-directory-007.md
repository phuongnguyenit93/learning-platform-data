# Cleaning Up Stale Outputs Before Verifying Spring REST Docs Documentation

## 1. Why Do Stale Outputs Break Documentation Accuracy?

Spring REST Docs generates snippets from HTTP tests. Suppose the first run has two tests:

```text
build/generated-snippets/
  order-detail/
    http-request.adoc
    http-response.adoc
  order-create/
    http-request.adoc
    http-response.adoc
```

Later, the development team deletes the `order-create` test or changes its identifier to `order-create-v2`. If a new run only adds snippets without removing old outputs, the `order-create` directory remains. Asciidoctor documentation can continue including the old files and the build still succeeds, leading readers to see a removed operation or an outdated contract.

This is **stale output**: files created by a previous build that are no longer produced by the current source/tests. With Spring REST Docs, stale snippets are particularly dangerous because they can look completely valid and cause no compilation errors.

The **SPRING_REST_DOCS** module produces verifiable REST API documentation using HTTP tests with MockMvc, WebTestClient, or REST Assured. Tests generate snippets for requests, responses, payloads, parameters, and headers; these are then compiled with Asciidoctor/Markdown and integrated into build/CI. This lesson belongs to the **Output Directory** chapter and walks through properly removing old generated outputs before verifying documentation.

After this lesson, you will be able to:

1. Recognize stale snippets and their impact on documentation.
2. Distinguish automatically generated outputs from Git-tracked documentation sources.
3. Use `clean` and task dependencies to produce a consistent set of snippets.
4. Configure Gradle/Maven so tests generate snippets before Asciidoctor runs.
5. Verify clean outputs in CI and avoid accidentally deleting source files.

## 2. Distinguishing Generated Outputs from Sources

| Type | Example | How to Manage |
| --- | --- | --- |
| Test source | `src/test/java/...` | Tracked in Git |
| Asciidoctor source | `src/docs/asciidoc/index.adoc` | Tracked in Git |
| Auto-generated snippets | `build/generated-snippets/` | Regenerated from tests |
| Rendered documentation | `build/docs/asciidoc/` | Regenerated from sources and snippets |
| Published artifact | Release ZIP/PDF/HTML | Stored per pipeline/release policy |

Only clearly identified generated output directories should be deleted during cleaning. Do not delete `src/test`, `src/docs`, source Asciidoctor files, JSON fixtures, or hand-written documentation.

### 2.1. Output Directory and Identifier

Snippet paths typically have the form:

```text
build/generated-snippets/
  <document-identifier>/
    http-request.adoc
    http-response.adoc
    request-fields.adoc
```

The output directory is the root. The document identifier is the subdirectory for an operation. When a test changes its identifier or is deleted, the old identifier directory can remain if the output root is not cleaned.

### 2.2. Why Overwriting Files Alone Is Not Enough

Suppose a previous run produced `order-create/http-request.adoc`. In the next run, tests no longer generate `order-create`, so there is no new file to overwrite it. The old file stays intact at the output root. This is why cleaning the output root before regenerating all snippets is necessary.

## 3. Deleting the Right Output Directory

Before cleaning, identify:

1. Where Spring REST Docs is configured to put the output directory.
2. Which task generates snippets.
3. Which task consumes snippets.
4. Whether any other task shares that directory.

For example:

```java
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
```

Or with JUnit 5:

```java
@RegisterExtension
final RestDocumentationExtension restDocumentation =
        new RestDocumentationExtension("build/generated-snippets");
```

In both cases, `build/generated-snippets` is a reproducible output. Gradle `clean` deletes the project's build directory, including snippets and rendered documentation inside it.

**Do not use broad deletion commands such as deleting the current directory or all documentation sources.** Use your build tool's `clean` task or delete only the identified generated output root.

## 4. Gradle: Running clean Before test and Asciidoctor

With Gradle, the `clean` task is provided by the Base/Java plugin and deletes the project's build directory. Full command:

```bash
./gradlew clean test asciidoctor
```

Meaning:

- `clean`: deletes build outputs from the previous run.
- `test`: runs HTTP tests and generates Spring REST Docs snippets.
- `asciidoctor`: merges fresh snippets with Asciidoctor sources and renders artifacts.

Gradle executes tasks according to their relationships and dependencies. When you need to ensure Asciidoctor reads snippets just generated by tests, declare explicit dependencies.

### 4.1. Declaring Dependencies and Output Directories

Gradle Groovy DSL example:

```groovy
plugins {
    id 'java'
    id 'org.asciidoctor.jvm.convert' version '4.0.4'
}

ext {
    snippetsDir = file('build/generated-snippets')
}

test {
    outputs.dir snippetsDir
    useJUnitPlatform()
}

asciidoctor {
    inputs.dir snippetsDir
    dependsOn test
    attributes 'snippets': snippetsDir
}
```

Kotlin DSL example:

```kotlin
val snippetsDir = layout.buildDirectory.dir("generated-snippets")

tasks.test {
    outputs.dir(snippetsDir)
    useJUnitPlatform()
}

tasks.named("asciidoctor") {
    inputs.dir(snippetsDir)
    dependsOn(tasks.test)
    attributes(mapOf("snippets" to snippetsDir.get().asFile))
}
```

This is an illustrative configuration; plugin versions, task names, and DSL details may vary by project. The core idea is that `test` declares the snippet output, and `asciidoctor` declares the snippet input and depends on `test`.

### 4.2. When You Only Want to Clean Snippets

You can declare a task that deletes only the snippets directory:

```groovy
tasks.register('cleanRestDocsSnippets', Delete) {
    delete snippetsDir
}

test {
    dependsOn cleanRestDocsSnippets
    outputs.dir snippetsDir
}
```

Do not use this task if multiple test tasks run in parallel or write into the same output directory. If there are multiple source sets or test tasks, clean once before all producer tasks run. Do not let one test task delete another task's outputs.

## 5. Maven: Cleaning Before Generating Snippets

With Maven, the `clean` lifecycle deletes the project's `target` directory. You can run:

```bash
mvn clean verify
```

If the project configures Spring REST Docs so tests generate snippets into `target/generated-snippets` and the Asciidoctor plugin renders documentation during the `verify` lifecycle, this command rebuilds outputs from a clean state.

Some projects run separately:

```bash
mvn clean test
mvn asciidoctor:process-asciidoc
```

Goal and phase names depend on the Asciidoctor Maven plugin used by the project. Verify the actual configuration to ensure tests run before the Asciidoctor goal, Asciidoctor reads the right output, the goal does not execute before snippets are generated, and `clean` does not delete Asciidoctor sources.

If you need to clean snippets separately, configure the Maven Clean Plugin to delete only `target/generated-snippets`. Avoid ambiguous relative paths that could target the wrong folder in a multi-module build.

## 6. Changed Identifiers and Leftover Snippets

Original test:

```java
@Test
void createOrder() throws Exception {
    mockMvc.perform(post("/api/orders"))
            .andDo(document("order-create"));
}
```

After refactoring:

```java
@Test
void createOrder() throws Exception {
    mockMvc.perform(post("/api/orders"))
            .andDo(document("orders/create"));
}
```

Without cleaning, the output may contain both:

```text
build/generated-snippets/
  order-create/       # stale
  orders/
    create/           # new
```

If Asciidoctor still includes `order-create`, the build may continue succeeding using the old snippet. Cleaning the output helps catch outdated includes: files no longer generated disappear, and Asciidoctor reports missing includes.

This is useful when renaming test methods or document identifiers, deleting operations, renaming payload fields, moving the output directory, or reorganizing snippets.

## 7. A Clean Build Does Not Automatically Mean Everything Is Verified

Cleaning only guarantees that old generated files in the wiped output area are not reused. It does not by itself prove that tests cover every operation, descriptors reflect the full contract, descriptions match business logic, public base URLs are accurate, or snippets are included in the right sections.

Therefore, the verification workflow must include running tests, rendering docs, and inspecting snippet contents and paths.

### 7.1. Inspecting Output After Tests

After running tests, inspect the output root:

```bash
find build/generated-snippets -type f
```

With PowerShell:

```powershell
Get-ChildItem -Path build/generated-snippets -Recurse -File |
    Select-Object -ExpandProperty FullName
```

Compare the list of identifiers against the operations that should be documented. If a directory does not appear, check whether the test ran, whether it has `document(...)` attached, and whether the output directory is correct.

### 7.2. Checking Required Snippets

For example:

```bash
test -f build/generated-snippets/orders/create/http-request.adoc
test -f build/generated-snippets/orders/create/http-response.adoc
```

With PowerShell:

```powershell
Test-Path build/generated-snippets/orders/create/http-request.adoc
Test-Path build/generated-snippets/orders/create/http-response.adoc
```

Checking file existence is only the baseline step. You must render Asciidoctor to confirm that include paths are valid and the documentation is complete.

## 8. Incremental Builds and Stale Output

Gradle and Maven can skip tasks if they determine inputs and outputs have not changed. Declare outputs and inputs properly so incremental builds remain reliable.

With Gradle:

- `test` declares the snippets directory as an output.
- `asciidoctor` declares the snippets directory as an input.
- `asciidoctor` depends on the `test` task.
- A clean build is run in CI when verifying that artifacts are independent of previous workspace state.

If tests generate snippets as a side effect without declaring the output directory, Gradle cannot track task relationships accurately. If Asciidoctor does not declare the input, caching/incremental builds may fail to reflect snippet changes.

You do not always need to run `clean` before every developer build. Incremental builds save time. However, pipelines producing release artifacts should run a clean build job periodically or on every release to verify outputs from current sources.

## 9. Multi-Module Projects and Output Directories

In Gradle multi-module or Maven reactor builds, each module typically has its own `build`/`target`:

```text
root/
  api-orders/
    build/generated-snippets/
  api-customers/
    build/generated-snippets/
  api-docs/
    src/docs/asciidoc/
```

The `api-docs` module can aggregate snippets from both API modules. Identify which test modules produce snippets, where the docs module receives snippets from, which tasks depend on producer tests, and which module's clean removes outputs.

Avoid having two modules write into a shared directory without separate namespaces. You can partition by module:

```text
build/generated-snippets/
  api-orders/
    orders/create/
  api-customers/
    customers/get-by-id/
```

If copying outputs into the docs module, the copy operation must run after producer tests and should clean the generated destination before copying so files removed at the source do not linger at the destination.

## 10. CI: Verifying Documentation from a Clean Workspace

A documentation pipeline:

```text
Checkout source
    |
    v
Clean build outputs
    |
    v
Run HTTP documentation tests
    |
    v
Verify generated snippet set
    |
    v
Render Asciidoctor / Markdown
    |
    v
Check links and expected files
    |
    v
Publish build artifact
```

Gradle example:

```bash
./gradlew clean test asciidoctor
```

Maven example:

```bash
mvn clean verify
```

CI should run on a fresh workspace checkout or clean build outputs properly before running tests. Running only `asciidoctor` on an existing workspace allows snippets from a prior build to make the documentation pass even if current tests fail to generate all required snippets.

### 10.1. Do Not Rely on Cache as the Sole Source of Snippets

Build caches can speed up tasks when inputs and outputs are accurately declared. However, the pipeline must still verify artifact completeness and task dependencies. Never manually copy an old snippets directory into a build just to make Asciidoctor pass.

If caching is enabled:

- Declare inputs/outputs accurately.
- Do not let tests write files outside the declared output directory.
- Do not reuse outputs from another commit as artifacts for the current commit.
- Maintain a clean build job to verify the process end-to-end.

## 11. Common Mistakes

| Symptom | Cause | How to Fix |
| --- | --- | --- |
| Documentation still shows a deleted operation | Stale snippets remain in the output root | Run `clean` before generating snippets |
| Asciidoctor succeeds even though tests did not generate snippets | Old files satisfy includes | Use a clean workspace and task dependencies |
| Fresh snippets vanish after running another test task | Another task deletes the shared output directory | Clean only once before all producer tasks run |
| Developer builds are slow when always cleaning | Cleaning every output on every build | Use incremental builds during development; clean builds in CI/release |
| Asciidoctor source files get deleted | Accidentally cleaned the source directory | Clean only `build/generated-snippets` or the build directory |
| Docs module still has snippets removed in the API module | Copy step did not clean destination | Delete the generated destination directory before copying again |
| Gradle does not re-run Asciidoctor | Snippet inputs were not declared | Declare `inputs.dir` and `dependsOn(test)` |
| Maven renders before tests complete | Goal/phase not bound properly in lifecycle | Bind the Asciidoctor goal after `test` |
| CI depends on files from an old workspace | Job does not perform clean checkout or clean build | Use a clean build and verify the snippet set |

## 12. Practice Exercise

An orders API has two documentation tests:

```java
@Test
void createOrder() { /* document("orders/create") */ }

@Test
void getOrder() { /* document("orders/get") */ }
```

Initially, the output contains both directories. Then delete the `getOrder` test and change the create test's identifier to `orders/create-v2`.

Steps:

1. Run tests without `clean` and observe that the old directories still remain in the output.
2. Run `clean` and `test`, then list the output snippets.
3. Verify that the old `orders/get` and `orders/create` directories are gone and `orders/create-v2` is generated.
4. Update the Asciidoctor includes to the new identifier.
5. Run `clean test asciidoctor` and verify that rendering succeeds.
6. Intentionally leave an include pointing to a deleted snippet to observe the build failing.
7. Add the clean build workflow to CI.

**Completion criteria:** Output contains only snippets generated by current tests; stale snippets cannot produce a false green build; documentation sources remain untouched; Asciidoctor depends on tests and CI verifies artifacts from a clean workspace.

## 13. Key Takeaways

Spring REST Docs snippets are generated outputs, not documentation source files. When tests or identifiers are deleted or renamed, old files can remain behind and cause Asciidoctor to include outdated contracts. Define a dedicated output root, run Gradle `clean` or Maven `clean` for clean builds, and declare tests as the producer and Asciidoctor as the consumer of snippets. For multi-module builds, clean destinations properly before aggregating. Run clean builds in CI/release pipelines and verify the generated snippet set so documentation reflects only current tests and sources.
