# Handling Markdown Tables and JSON Content

## Lesson Objectives

In REST API documentation, Markdown tables are commonly used to explain fields, query parameters, path parameters, and headers. JSON snippets illustrate the payload structure sent or received. When assembling content generated by **Spring REST Docs** into Markdown pages, it is important to preserve tested data accurately and handle syntactically significant characters such as pipes, backslashes, and backticks.

This lesson belongs to the **Markdown** chapter of the **SPRING_REST_DOCS** module: creating verifiable REST API documentation from HTTP tests with **MockMvc**, **WebTestClient**, or **REST Assured**; generating snippets for requests, responses, payloads, parameters, and headers; authoring Asciidoctor/Markdown documentation and integrating it into build and CI.

After this lesson, you will be able to:

- Read and organize field tables generated from REST Docs descriptors.
- Handle pipes, backslashes, backticks, and multiline content in Markdown tables.
- Keep JSON bodies readable, well-formatted, and consistent with HTTP snippets.
- Distinguish JSON body snippets from `request-fields`/`response-fields` tables.
- Customize templates or assemble snippets without corrupting content.
- Validate code fences, JSON, UTF-8, and tables after assembly/rendering.
- Connect snippet generation, Markdown assembly, and output verification in CI.

## 1. Where Are Markdown Tables Used?

REST Docs uses descriptors to describe request/response structures. When rendered to Markdown, descriptors are typically presented as tables. Tables help readers quickly look up field names, types, descriptions, and optionality.

Example request table:

| Path | Type | Description |
| --- | --- | --- |
| customerId | Number | ID of the customer creating the order |
| description | String | Order description |
| note | String | Additional note, optional |

Example response table:

| Path | Type | Description |
| --- | --- | --- |
| id | Number | Server-assigned order ID |
| status | String | Current status |
| createdAt | String | Creation timestamp in ISO-8601 |

These two tables are **field tables**. They describe the JSON schema; they do not replace HTTP request/response snippets, nor do they contain full sample payload values.

## 2. Generating Tables from Descriptors Instead of Hand-Writing

Declare descriptors in operation tests so REST Docs validates them against actual payloads:

~~~java
document("orders-create",
    requestFields(
        fieldWithPath("customerId")
            .description("ID of the customer creating the order"),
        fieldWithPath("description")
            .description("Order description"),
        fieldWithPath("note")
            .optional()
            .description("Additional note, optional")
    ),
    responseFields(
        fieldWithPath("id")
            .description("Server-assigned order ID"),
        fieldWithPath("status")
            .description("Current status"),
        fieldWithPath("createdAt")
            .description("Creation timestamp in ISO-8601")
    )
)
~~~

Common static imports:

~~~java
import static org.springframework.restdocs.payload.PayloadDocumentation.fieldWithPath;
import static org.springframework.restdocs.payload.PayloadDocumentation.requestFields;
import static org.springframework.restdocs.payload.PayloadDocumentation.responseFields;
~~~

When tests execute, REST Docs checks descriptors against recorded request/response payloads. If the JSON contains undocumented fields or descriptors point to non-existent fields, strict mode can fail the test. That is a signal to review the contract or descriptors, not to simply disable checks to make the build pass.

### 2.1. Nested Fields and Arrays

With JSON:

~~~json
{
  "customer": {
    "id": 42,
    "name": "Lan"
  },
  "items": [
    {
      "sku": "KB-01",
      "quantity": 2
    }
  ]
}
~~~

Descriptors can use paths:

~~~java
requestFields(
    fieldWithPath("customer.id").description("Customer ID"),
    fieldWithPath("customer.name").description("Customer name"),
    fieldWithPath("items[].sku").description("Product SKU"),
    fieldWithPath("items[].quantity").description("Quantity")
)
~~~

If you want to describe an object/array as a single unit rather than listing every child element, consider `subsectionWithPath(...)` appropriate to your REST Docs version. Avoid documenting the same parent object and child fields in a way that creates overlapping descriptors.

### 2.2. Optional and Null Are Different Concepts

An **optional** field may be absent from JSON. A field with value **null** is present, with value `null`. Both cases should be distinguished in the contract.

~~~java
requestFields(
    fieldWithPath("customerId").description("Customer ID"),
    fieldWithPath("note")
        .optional()
        .description("May be omitted; if sent, must be a string")
)
~~~

If the API allows `note` to have a `null` value, state that explicitly in the description and test it separately. Do not treat `optional()` as indicating that `null` values are accepted.

## 3. Special Characters in Markdown Tables

Markdown tables use the pipe character to separate columns. If a field description contains a pipe, the renderer may create unintended extra columns.

Example content to display:

~~~text
Accepted values: compact | comfortable
~~~

In a Markdown table, escape the pipe with a backslash:

| Path | Description |
| --- | --- |
| displayMode | Accepted values: compact \| comfortable |

### 3.1. Escaping Table Content in Templates

If a custom template generates tables from descriptors, cell contents must be escaped before rendering:

- Pipes must be escaped per Markdown table rules.
- Backslashes must be handled so they do not strip or alter a subsequent escape character.
- Content containing newlines must be converted to a single-line representation or HTML line breaks if permitted by the renderer.
- HTML, backticks, and entities must follow the renderer's output policy.

Minimal Java helper example for escaping pipes in a cell:

~~~java
String escapeTableCell(String value) {
    return value
        .replace("\\", "\\\\")
        .replace("|", "\\|")
        .replace("\r\n", " ")
        .replace("\n", " ")
        .replace("\r", " ");
}
~~~

This is only an example for plain cell text. If templates must support HTML, backticks, control characters, or complex inline Markdown, use an appropriate escaping/templating library rather than ad-hoc chains of `replace` calls.

### 3.2. Backticks in Field Names or Descriptions

Backticks mark inline code. If content contains backticks, choose a delimiter longer than the longest consecutive backtick run in the content, or escape according to the renderer. Never let an inner backtick close a code span prematurely.

If a field name is `customer.version`, displaying it in a code span is easier to read than plain text. Code span contents still need escaping if they contain backticks or special characters.

## 4. Multiline Content in Tables

Traditional Markdown tables work best with short, single-line cells. Avoid placing JSON snippets or long multiline descriptions inside a table cell because rendering varies across engines.

Keep the table concise:

| Path | Type | Description |
| --- | --- | --- |
| options | Object | Additional options |

Then place details in a dedicated section:

~~~json
{
  "theme": "dark",
  "locale": "vi"
}
~~~

This presentation keeps tables scannable while giving complex structures dedicated space for explanation.

## 5. JSON Body Snippets and Field Tables

REST Docs provides distinct snippets for HTTP exchanges and payload descriptors. Depending on the template/version, filenames may have `.adoc` or `.md` extensions. Common content groups include:

| Content | Typical Snippet | Used For |
| --- | --- | --- |
| HTTP request | http-request | Shows method, URI, headers, and body |
| HTTP response | http-response | Shows status, headers, and body |
| Request body | request-body | Shows outgoing payload, if configured |
| Response body | response-body | Shows returned payload, if configured |
| Request field table | request-fields | Describes request body fields |
| Response field table | response-fields | Describes response body fields |

`http-request`/`http-response` and `request-body`/`response-body` may both contain body data in two different display contexts. Do not embed both redundantly if doing so adds no value for readers.

### 5.1. Keeping JSON Faithful to Source

Example request body:

~~~json
{
  "customerId": 42,
  "description": "Keyboard"
}
~~~

Example response body:

~~~json
{
  "id": 731,
  "status": "CREATED"
}
~~~

JSON snippets must reflect the exact body sent/received by tests. Do not edit values, delete fields, or invent examples in generated snippets just to make output prettier. If more readable sample data is needed, update test fixtures and re-run REST Docs so snippets remain test-verified.

### 5.2. JSON Formatting

To keep JSON readable:

- Use fenced code blocks tagged with `json`.
- Maintain consistent indentation.
- Keep Unicode strings in UTF-8.
- Never alter data types: numbers must not become strings, booleans must not become strings.
- Keep `null`, arrays, and nested objects structurally intact.
- Do not omit fields simply because their value is currently empty.

Pretty-printing only changes whitespace, not JSON semantics. However, any formatting step must be applied consistently and must not diverge the payload from the HTTP exchange.

## 6. Combining JSON Samples with Request/Response Field Tables

A clear Markdown section typically has:

1. A paragraph explaining the payload's purpose.
2. A JSON body snippet for readers to inspect sample values.
3. A field table to look up each field's meaning.

Example:

### Request body

The client sends customer information and an order description:

~~~json
{
  "customerId": 42,
  "description": "Keyboard",
  "note": "Deliver in the morning"
}
~~~

### Request fields

| Path | Type | Description |
| --- | --- | --- |
| customerId | Number | Customer ID |
| description | String | Order description |
| note | String | Optional note |

JSON shows a concrete example. The field table describes meaning and contract. The two sections do not duplicate responsibilities.

## 7. Customizing Templates to Generate Markdown Tables

If REST Docs' default output is AsciiDoc, you can:

- Use Asciidoctor to render snippets and documentation.
- Configure the Markdown template format if your REST Docs version supports it.
- Create custom snippet templates to format field tables in Markdown.
- Convert AsciiDoc snippets to Markdown via a verified tool/build step.

Do not change `.adoc` to `.md` by renaming files. A file extension does not turn AsciiDoc syntax into Markdown.

### 7.1. What Data Should a Table Template Preserve?

A field table typically needs at minimum:

| Column | Meaning |
| --- | --- |
| Path | Field path in the payload |
| Type | Data type inferred or specified by REST Docs |
| Description | Field meaning provided by descriptor author |
| Optional | Optionality status if the template renders this column |

Not every default template includes a separate Optional column. Inspect generated output and your active version before writing explanations that depend on that column.

When creating custom templates, escape only at the cell-rendering step, without altering source descriptors. That way, the same descriptors can serve multiple output formats.

## 8. Assembling Tables and JSON Snippets into Markdown

Plain Markdown has no universal file include syntax. Use your static site generator's include plugin if configured, or build-time assembly to produce final pages.

Example structure:

~~~text
src/docs/markdown/
└── orders-create-intro.md

build/generated-snippets/orders-create/
├── http-request.md
├── http-response.md
├── request-body.md
├── response-body.md
├── request-fields.md
└── response-fields.md

build/docs-markdown/
└── orders-create.md
~~~

The final page can be assembled in order:

~~~markdown
# Create order

The client sends customer information and an order description.

## HTTP request

[http-request snippet content inserted here]

## Request JSON

[request-body snippet content inserted here]

## Request fields

[request-fields snippet content inserted here]

## HTTP response

[http-response snippet content inserted here]

## Response JSON

[response-body snippet content inserted here]

## Response fields

[response-fields snippet content inserted here]
~~~

Lines in square brackets are illustrative placeholders, not working include directives. The build task/plugin must replace them with real fragments. If `http-request` already shows the body clearly enough, a separate `request-body` section may not be needed; avoid repeating content.

### 8.1. Assembly Rules

The assembly task should:

1. Run after tests that generated snippets.
2. Confirm every required snippet exists.
3. Read as UTF-8 and keep payload content intact.
4. Add headings and blank lines between fragments.
5. Escape table cells if constructing tables from metadata manually.
6. Never wrap a snippet containing code fences inside an outer fence of the same length.
7. Write outputs into `build/`, without overwriting source files in `src/`.

## 9. Example Gradle Task to Validate and Assemble JSON/Tables

The Groovy DSL example below illustrates assembling existing fragments. It assumes REST Docs generated Markdown snippets with the exact names:

~~~~groovy
def snippetsDir = layout.buildDirectory.dir('generated-snippets')
def outputDir = layout.buildDirectory.dir('docs-markdown')

tasks.register('assembleOrderCreateMarkdown') {
    dependsOn tasks.named('test')
    inputs.dir snippetsDir
    outputs.file outputDir.map { it.file('orders-create.md') }

    doLast {
        def operationDir = new File(
            snippetsDir.get().asFile,
            'orders-create'
        )
        def files = [
            'http-request.md',
            'request-body.md',
            'request-fields.md',
            'http-response.md',
            'response-body.md',
            'response-fields.md'
        ]

        def snippets = files.collect { name ->
            new File(operationDir, name)
        }
        def missing = snippets.findAll { !it.isFile() }
        if (!missing.isEmpty()) {
            throw new GradleException(
                'Missing REST Docs snippets: ' +
                missing.collect { it.name }.join(', ')
            )
        }

        def headings = [
            '## HTTP request',
            '## Request JSON',
            '## Request fields',
            '## HTTP response',
            '## Response JSON',
            '## Response fields'
        ]
        def content = new StringBuilder('# Create order\n\n')
        snippets.eachWithIndex { file, index ->
            content.append(headings[index])
                .append('\n\n')
                .append(file.getText('UTF-8').trim())
                .append('\n\n')
        }

        def target = outputDir.get().file('orders-create.md').asFile
        target.parentFile.mkdirs()
        target.setText(content.toString(), 'UTF-8')
    }
}
~~~~

This is an illustrative task: use it only when the project actually generates all six Markdown fragments listed above. If REST Docs generates `.adoc`, use Asciidoctor or an explicit conversion step. If `request-body`/`response-body` are not configured, remove them from the list and assemble only `http-request`, `request-fields`, `http-response`, and `response-fields`. Do not create dummy fragments just to make the task pass.

## 10. Verifying Tables and JSON After Rendering

After assembly, verify:

| Item | What to Confirm |
| --- | --- |
| Column count | Every table row has the same number of columns |
| Pipes in descriptions | Do not create unintended extra columns |
| Backslashes/backticks | Render accurately, do not close code spans prematurely |
| Multiline content | Moved to a dedicated section or formatted as supported by renderer |
| JSON syntax | Parses cleanly and preserves data types |
| JSON source | Matches test payloads, not manually edited |
| Unicode | Vietnamese text has no encoding corruption |
| Code fences | Balanced open/close; nested fences use longer outer delimiters |
| Table source | Generated from descriptors, no conflicting manual tables |

A JSON parser can be run in the pipeline to validate body snippet files if fragments contain pure JSON. If snippets wrap JSON with HTTP headers or code fences, extract the exact body region before parsing.

### 10.1. Validating Markdown Tables

A basic check should detect:

- Header and separator rows have the same number of columns.
- Every data row has the same number of columns after accounting for escaped pipes.
- Tables have blank lines before and after where required.
- No unescaped pipes appear in text cells unless supported by the template/engine.

Simple regexes can flag suspicious cases, though they do not replace a Markdown parser because pipes may appear inside code spans or HTML. For important sites, render with the exact generator and inspect the resulting HTML.

## 11. Common Issues

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Table has unintended extra columns | Description contains unescaped pipe | Escape pipes in template cells |
| Backslashes disappear | Escape sequence processed twice | Clarify escaping layer and escape only once |
| Backticks break cell | Code span contains unhandled delimiter | Use longer delimiter or escape per renderer |
| Long descriptions make table unreadable | Cramming multiple lines into one cell | Keep descriptions brief, move examples to separate sections |
| JSON snippet differs from HTTP payload | Copied or formatted manually after test | Use generated snippets as primary source |
| JSON fails to parse | Fragment has HTTP wrapper or wrong assembly | Extract body properly and validate with JSON parser |
| Unicode JSON turns into garbled characters | Inconsistent encoding | Use UTF-8 from tests through renderer |
| Field table missing fields | Descriptors do not cover full payload | Update descriptors or use relaxed fields intentionally |
| Table marks optionality incorrectly | Confusing optional with nullable | Test absent field and null field separately |
| Markdown contains raw directive | Using include syntax unsupported by renderer | Use proper plugin or build-time assembly |
| Assembly reports missing `request-body.md` | Version/template does not generate that snippet | Remove unconfigured fragment or configure proper template |
| Content repeated twice | Embedding both `http-request` and `request-body` unnecessarily | Choose snippets that add distinct value |

## 12. Practice Exercise

Create documentation for endpoint:

~~~text
POST /api/orders
~~~

Request JSON:

~~~json
{
  "customerId": 42,
  "description": "Keyboard | mouse",
  "note": "Morning delivery",
  "items": [
    {
      "sku": "KB-01",
      "quantity": 2
    }
  ]
}
~~~

Response JSON:

~~~json
{
  "id": 731,
  "status": "CREATED",
  "totalItems": 2
}
~~~

Requirements:

1. Write a MockMvc test sending the request above and asserting the response against the contract.
2. Use `requestFields(...)` to describe `customerId`, `description`, `note`, and `items`.
3. Use `responseFields(...)` to describe `id`, `status`, and `totalItems`.
4. Ensure the field description containing a pipe renders cleanly in the Markdown field table.
5. Generate HTTP request/response and field tables under the same document identifier.
6. If `request-body`/`response-body` snippets exist, place them in dedicated JSON sections; if not, use HTTP snippets and do not assume files exist.
7. Assemble the Markdown page and render with your project's actual tooling.
8. Validate JSON syntax, field tables, code fences, UTF-8, and links in CI.

**Completion criteria:** tables do not break columns on pipes; JSON is valid and matches test payloads; request/response snippets and field tables do not contradict; final page renders cleanly and can be regenerated from tests.

## Key Takeaways

Field tables and JSON snippets serve two distinct purposes: JSON shows sample payloads, while tables describe schemas and field meanings. Generate tables from `requestFields(...)`/`responseFields(...)`, keep JSON bodies synchronized with HTTP exchanges, escape pipes and special characters in table cells, and move multiline content to separate sections. Only assemble snippets that are actually configured to generate. After assembly, check Markdown with the real renderer, validate JSON, code fences, UTF-8, and sensitive data before publishing via CI.
