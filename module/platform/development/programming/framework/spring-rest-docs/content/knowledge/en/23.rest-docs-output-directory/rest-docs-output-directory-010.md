# Managing Outputs Outside Source Code

## 1. Distinguishing Source Code from Generated Outputs

Spring REST Docs generates **snippets** when HTTP tests run. Files such as `http-request.adoc`, `http-response.adoc`, `request-fields.adoc`, and `curl-request.adoc` are automatically generated results, not source code to be edited manually.

In Gradle projects, outputs typically live under `build/generated-snippets/`; with Maven, usually `target/generated-snippets/`. Both reside inside the build directory managed by the build tool. Team-authored AsciiDoc files, tests, and build configurations are the inputs that should be maintained.

| Content | Common Location | How to Manage |
| --- | --- | --- |
| Java/Kotlin tests | `src/test/...` | Version control |
| Source AsciiDoc | `src/docs/asciidoc/` | Version control |
| Gradle/Maven configuration | `build.gradle`, `pom.xml` | Version control |
| Snippets generated from tests | `build/generated-snippets/` or `target/generated-snippets/` | Build output |
| Rendered HTML/PDF | `build/docs/...` or `target/generated-docs/` | Build/release artifact |
| Logs and temporary files | `build/`, `target/` | Build output |

In the **SPRING_REST_DOCS** module, HTTP tests using MockMvc, WebTestClient, or REST Assured generate snippets; Asciidoctor/Markdown combines snippets into documentation; CI can package documentation alongside the API version. Properly managing the boundary between sources and outputs keeps the repository clean, builds reproducible, and avoids accidentally committing local developer machine outputs in pull requests.

## 2. Why Should Snippets Not Be Edited Directly?

Suppose a test generates:

~~~text
build/generated-snippets/
└── orders/
    └── get-one/
        ├── http-request.adoc
        ├── http-response.adoc
        └── response-fields.adoc
~~~

If you open `http-request.adoc` and edit its contents manually, the next test run will overwrite those changes. When the actual request changes, manual edits can also hide the fact that tests and documentation no longer match.

Best practices:

- To change request/response examples, update the test fixture or the request sent in the test.
- To change field descriptions, update descriptors in `requestFields(...)`, `responseFields(...)`, `requestParameters(...)`, or the corresponding operation.
- To change snippet formatting, configure Spring REST Docs snippet templates or operations.
- To change presentation, edit the source AsciiDoc files and Asciidoctor configuration.
- Do not directly edit generated snippet files to produce results that exist only on a local machine.

Snippets are evidence generated by tests. When the source data changes, re-run the tests to generate new results.

## 3. Adding Build Outputs to .gitignore

With Gradle, `build/` is normally already ignored in the project's `.gitignore`. With Maven, `target/` is also typically ignored. If the repository does not yet have the corresponding rules, add them:

~~~gitignore
# Gradle build output
/build/

# Maven build output
/target/
~~~

If a project has multiple modules and each module has its own build directory, ignore rules must match the `.gitignore` location. A `.gitignore` at the repository root can apply to subdirectories; rules with leading or trailing `/` must be understood relative to the directory containing that `.gitignore`.

You can ignore snippets specifically if the project intentionally stores another part of the build directory:

~~~gitignore
/build/generated-snippets/
/target/generated-snippets/
~~~

However, if the entire `build/` or `target/` directory is already ignored, there is no need to add sub-rules. Avoid adding redundant lines that make repository policies harder to read.

### 3.1. Checking Files Already Tracked by Git

`.gitignore` only prevents Git from adding untracked files. It does not automatically stop tracking files that were committed previously.

Check:

~~~bash
git status --short
git ls-files build/generated-snippets target/generated-snippets
~~~

If snippets are already tracked and the team decides to treat them as build outputs, make an intentional tracking change in a pull request. For example, remove files from the index while keeping local files:

~~~bash
git rm -r --cached build/generated-snippets
git rm -r --cached target/generated-snippets
~~~

Only run this command for paths genuinely tracked by Git and after reviewing the diff. `--cached` removes files from the index; it does not delete files from the working tree. Do not use this command as a routine cleanup step for every build.

## 4. Cleaning Outputs with the Build Tool

### 4.1. Gradle

Gradle provides the `clean` task to delete the build directory:

~~~bash
./gradlew clean
~~~

Then run tests and render documentation:

~~~bash
./gradlew test asciidoctor
~~~

Or run a full build:

~~~bash
./gradlew clean build
~~~

If `asciidoctor` depends on `test`, the task graph ensures tests run before rendering. Proper output/input configuration helps Gradle recognize `generated-snippets` as a test output and an Asciidoctor input.

`clean` also deletes other build outputs such as compiled classes, reports, and rendered documentation. Therefore, use it only when you want a clean rebuild; do not run it if you need to preserve an unbacked-up artifact inside `build/`.

### 4.2. Maven

Maven uses `clean` to delete the `target/` directory:

~~~bash
mvn clean
~~~

Run the lifecycle that generates test snippets and documentation:

~~~bash
mvn clean verify
~~~

If Asciidoctor is bound to a phase after `test`, `verify` will pass through that phase in the standard lifecycle. Running `mvn test` alone may generate snippets without rendering documentation, depending on the configured phase.

### 4.3. Deleting Only a Specific Output Directory

Sometimes you want to refresh snippets without deleting all build outputs. You can create a dedicated Gradle task:

~~~groovy
def snippetsDir = layout.buildDirectory.dir('generated-snippets')

tasks.register('cleanSnippets', Delete) {
    delete snippetsDir
}

tasks.named('test') {
    outputs.dir snippetsDir
}
~~~

Then:

~~~bash
./gradlew cleanSnippets test asciidoctor
~~~

With Maven, you can configure the Maven Clean Plugin with a specific fileset or delete the snippets directory in a managed build step. Avoid writing custom scripts that delete overly broad paths like `build/**` or `target/**` when the goal is only to refresh snippets.

## 5. Keeping Documentation Sources Outside the Build Directory

An easy-to-maintain structure:

~~~text
project/
├── src/
│   ├── main/
│   ├── test/
│   └── docs/
│       └── asciidoc/
│           ├── index.adoc
│           └── resources/
├── build.gradle
├── .gitignore
└── build/
    ├── generated-snippets/
    └── docs/
        └── asciidoc/
~~~

`src/docs/asciidoc/` contains team-authored content and is under version control. `build/generated-snippets/` contains test-generated content. `build/docs/` contains rendered HTML/PDF.

Do not store the sole copy of source AsciiDoc files inside `build/` or `target/`, because `clean` commands will delete them. If the team keeps a separate docs folder outside `src/`, ensure the build configures `sourceDirectory` to point to the exact location and that the folder is tracked in Git.

## 6. When Should Artifacts Be Stored Outside the Source Tree?

Some workflows need to preserve outputs after the build completes:

- CI uploads HTML/PDF as a job artifact.
- A release pipeline publishes a documentation ZIP alongside the application version.
- Another docs module needs to download snippets from an API module.
- QA teams archive reports or documentation for review.

In these cases, the build should still generate outputs in a reproducible location; after verification succeeds, CI or a packaging step copies/attaches artifacts to the appropriate storage location.

Gradle example creating a documentation ZIP:

~~~groovy
def renderedDocs = layout.buildDirectory.dir('docs/asciidoc')

tasks.register('apiDocsZip', Zip) {
    dependsOn tasks.named('asciidoctor')
    from(renderedDocs)
    archiveClassifier = 'api-docs'
    destinationDirectory = layout.buildDirectory.dir('distributions')
}
~~~

Maven Assembly example packaging the rendered HTML directory:

~~~xml
<fileSet>
    <directory>${project.build.directory}/generated-docs</directory>
    <outputDirectory>/</outputDirectory>
</fileSet>
~~~

Artifacts are uploaded to a CI artifact store, package registry, or release repository according to project policy. There is no need to move snippets or HTML back into `src/` just so they persist after the build.

## 7. Managing Outputs in CI

CI typically uses either ephemeral workspaces or reused workspaces. If a workspace is reused, stale snippets may remain when tests or document identifiers are deleted. A clean build removes old data before generating fresh documentation.

Reference pipeline:

~~~text
Checkout source
      |
      v
Clean build output
      |
      v
Run documentation tests
      |
      v
Generate snippets
      |
      v
Render HTML/PDF
      |
      v
Verify documentation
      |
      v
Upload release artifact
~~~

Gradle:

~~~bash
./gradlew clean test asciidoctor apiDocsZip
~~~

Maven:

~~~bash
mvn clean verify
~~~

If Maven packages docs during the `package` phase, use `mvn clean package` or a later phase. If Gradle's docs ZIP is a separate task, include that task in the CI release command.

### 7.1. Checking Before Upload

Before uploading an artifact, confirm:

1. Documentation tests ran and passed.
2. Required snippets were generated in the current output directory.
3. Asciidoctor did not consume stale snippets from a previous workspace.
4. HTML/PDF contains all pages and assets.
5. The artifact carries the matching version/commit.
6. No logs, secrets, temporary files, or environment data unintended for recipients are included.

Keeping build outputs and published artifacts are two separate concerns. The workspace can be wiped after the job; published artifacts should be stored in a CI/release system with proper versioning and access controls.

## 8. Multi-Module Projects and Multiple Output Directories

In multi-module projects, each module typically has its own build directory:

~~~text
repository/
├── orders-api/
│   └── build/generated-snippets/
├── customers-api/
│   └── build/generated-snippets/
└── docs-site/
    └── src/docs/asciidoc/
~~~

This is a natural separation of outputs: tests in `orders-api` and `customers-api` do not overwrite each other's snippets. The `docs-site` module can pull published snippet artifacts or use a copy/assemble step with explicit dependencies.

Do not let two modules write into the same shared directory if they have overlapping identifiers or can run in parallel. If an aggregated root is needed, use a dedicated task to copy outputs from each module into separate namespaces:

~~~text
build/all-snippets/
├── orders/
└── customers/
~~~

The copy destination must be stable and declared as an output of the aggregation task. Do not copy files manually after each test run.

## 9. Exception: When Can Generated Outputs Be Committed?

Normally, do not commit `build/generated-snippets/` or `target/generated-snippets/`. However, a repository might intentionally version-control rendered artifacts for operational reasons, such as a docs website hosted directly from a static branch or a release system without a build step at deployment time.

If choosing this approach:

- Commit only the output format needed for deployment, not necessarily all intermediate snippets.
- Document the procedure to regenerate outputs from tests and documentation sources.
- CI must verify that committed outputs stay in sync with the current build.
- Pull requests should show output diffs for reviewers to inspect.
- Never manually edit generated outputs without updating the corresponding sources.

This is a repository workflow decision, not a default requirement of Spring REST Docs. Whether committed or not, the reproducible sources of truth must remain tests, descriptors, and AsciiDoc documentation.

## 10. Common Issues

| Symptom | Cause | How to Fix |
| --- | --- | --- |
| Snippets appear in `git status` | Build directory is not ignored or files are already tracked | Check `.gitignore` and `git ls-files` |
| Edited a snippet, but changes disappeared | Re-running tests overwrote the output | Edit tests/descriptors and regenerate snippets |
| Documentation contains old examples | Workspace retained output from a previous build | Run a clean build and verify includes |
| `clean` deleted source documentation | Sources were placed under `build/` or `target/` | Move sources to `src/docs` or a version-controlled directory |
| CI fails to archive HTML | Artifact upload not configured or wrong output path | Check the rendering task and artifact path |
| Docs module is missing snippets | Outputs reside in another module's build directory | Add task dependencies and an artifact sharing/copy step |
| Two modules overwrite each other | Shared output root and overlapping identifiers | Separate output roots or namespace by module |
| Artifact contains extra files | Packaged the entire build directory instead of the docs folder | Select only the HTML/PDF folder intended for release |

## 11. Practice Exercise

In a Gradle or Maven project with Spring REST Docs:

1. Configure tests to generate snippets into `build/generated-snippets` or `target/generated-snippets`.
2. Check `.gitignore` to ensure outputs are not added to source control.
3. Create source AsciiDoc files in `src/docs/asciidoc/` and include snippets.
4. Run a clean build and verify that snippets are regenerated and documentation renders successfully.
5. Create a ZIP containing only the rendered HTML, not the entire build directory.
6. Upload the ZIP as a CI artifact or store it in release staging.
7. Try deleting a test/document identifier and running a clean build; confirm the old snippet is absent from the new artifact.
8. Check `git status` after the build to ensure the source tree contains no unexpected generated outputs.

**Completion criteria:** Sources and generated outputs are clearly separated; snippets are neither manually edited nor unintentionally committed; clean builds regenerate documentation; CI archives the exact verified artifact.
