# Reading Raw Snippets Before Including Them in Final Documentation

## 1. Objectives and Context

Spring REST Docs generates **snippets** from HTTP operations executed by tests. Snippets can describe requests, responses, bodies, headers, parameters, and fields, or provide CLI commands such as curl/HTTPie. Before including them into an Asciidoctor/Markdown page, open and read the **newly generated raw snippets** to confirm actual content matches both tests and the API contract.

This review step is part of the **SPRING_REST_DOCS** module: generating verifiable REST API documentation from HTTP tests using MockMvc, WebTestClient, or REST Assured; producing snippets for requests, responses, payloads, parameters, and headers; authoring documentation; and integrating it into build and CI pipelines.

After this lesson, you will be able to:

- Locate the output directory, identifier, and snippets generated by a test.
- Read raw request/response snippets before composing a documentation page.
- Cross-check HTTP method, URI, headers, body, status, and field descriptors against the test.
- Distinguish raw operation snippets, descriptor tables, and composed final documentation.
- Spot incorrect, missing, unstable, or sensitive information in snippets.
- Establish a review and CI workflow to avoid publishing stale or inaccurate documentation.

> A **raw snippet** is an intermediate output generated by Spring REST Docs from the operation and current configuration. It serves as evidence of what data was recorded in that test run, though it does not prove all business rules are valid on its own. Documentation quality also depends on assertions, descriptors, and the authoring step.

## 2. Where Do Raw Snippets Live?

When a test records an operation with an identifier—for example `document("orders-get-success")`—Spring REST Docs generates snippets inside a folder matching that identifier. Under a typical MockMvc setup:

~~~java
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
~~~

The output structure may look like this:

~~~text
build/
└── generated-snippets/
    ├── orders-get-success/
    │   ├── curl-request.adoc
    │   ├── httpie-request.adoc
    │   ├── http-request.adoc
    │   ├── http-response.adoc
    │   ├── request-body.adoc
    │   ├── response-body.adoc
    │   ├── request-headers.adoc
    │   ├── response-headers.adoc
    │   ├── request-fields.adoc
    │   └── response-fields.adoc
    └── orders-create/
        ├── curl-request.adoc
        ├── http-request.adoc
        ├── http-response.adoc
        └── ...
~~~

This is an **illustrative** structure, not a mandatory file list for every project. Default snippets may include `curl-request.adoc`, `httpie-request.adoc`, `http-request.adoc`, `http-response.adoc`, `request-body.adoc`, and `response-body.adoc`. Tables such as `request-headers.adoc`, `response-headers.adoc`, `request-fields.adoc`, `response-fields.adoc`, `path-parameters.adoc`, or `query-parameters.adoc` only appear when tests/configuration request them.

The exact path depends on your build tool and configuration:

| Environment | Example output directory |
| --- | --- |
| Gradle with standard configuration | `build/generated-snippets` |
| Maven with standard configuration | `target/generated-snippets` |
| Custom output | Value set in the REST Docs configurer/annotation |

Do not guess the directory from habit. Open the test or build configuration to verify the exact output directory, then find the folder matching the identifier. If there are multiple modules or test tasks, each task may use a different output configuration.

### 2.1. The Identifier Is the Key to Finding the Right Operation

Every operation should have a stable, clear identifier that distinguishes scenarios:

| Identifier | Meaning |
| --- | --- |
| `orders-get-success` | Order retrieved successfully. |
| `orders-get-not-found` | Order not found. |
| `orders-create` | Create an order. |
| `orders-delete` | Delete an order with no response body. |

Avoid generic names like `test1`, `sample`, or an identifier reused by multiple tests. If two different operations write to the same identifier, snippets can overwrite each other or final docs can include the wrong content. A unique identifier per scenario lets reviewers trace from a doc page directly back to the exact test.

## 3. Distinguishing Three Layers of Content

In a Spring REST Docs workflow, distinguish among:

1. **Raw operation snippets:** representations of recorded HTTP data, such as `http-request.adoc` and `http-response.adoc`.
2. **Descriptor snippets:** tables explaining declared fields/headers/parameters, such as `response-fields.adoc` or `query-parameters.adoc`.
3. **Final documentation:** Asciidoctor/Markdown pages combining snippets with headings, explanations, usage notes, business examples, and integration guides.

| Type | Example | What it provides |
| --- | --- | --- |
| Raw request | `http-request.adoc` | Recorded method, request target, headers, and body. |
| Raw response | `http-response.adoc` | Recorded status, response headers, and body. |
| Isolated body | `request-body.adoc` / `response-body.adoc` | Payload of one direction only. |
| CLI command | `curl-request.adoc` / `httpie-request.adoc` | Command showing readers how to try the request. |
| Descriptor table | `response-fields.adoc` | Field names and author-declared descriptions, verified against the payload. |
| Composed documentation | `api.adoc` or equivalent page | Structured narrative, explanations, and included snippets. |

Raw snippets answer **"what did this test exchange?"**; descriptors answer **"what do the documented components mean?"**; final documentation answers **"what do API consumers need to understand and do?"**.

For example, `http-response.adoc` might show `HTTP/1.1 201 Created` and a `Location` header; `response-headers.adoc` explains the meaning of `Location`; the final page adds that clients can follow that URI to access the newly created resource. Never expect a raw snippet to provide business explanations on its own.

## 4. Workflow for Reading Raw Snippets After Running Tests

A review process can follow this order:

~~~mermaid
flowchart TD
    A["Run HTTP test"] --> B{"Test and assertions pass?"}
    B -->|No| C["Investigate error, do not publish"]
    B -->|Yes| D["Locate output directory and identifier"]
    D --> E["Read raw request / response"]
    E --> F["Read descriptor tables"]
    F --> G["Cross-check contract, fixtures, and assertions"]
    G --> H{"Snippets accurate and safe?"}
    H -->|No| I["Fix test, descriptors, or preprocessors"]
    I --> A
    H -->|Yes| J["Include in final documentation"]
    J --> K["Render and review doc page"]
    K --> L["Publish via CI"]
~~~

Inspect items in this order:

1. **Right operation:** does the folder match the identifier? Does any other test reuse that identifier?
2. **Request:** do method, URI, query, path, headers, and body match the test call?
3. **Response:** do status, headers, and body match what the test received?
4. **Descriptors:** are all fields/headers/parameters needing explanation documented completely and with exact names?
5. **Stability and security:** are there internal hosts, tokens, cookies, timestamps, random IDs, or private data?
6. **Final documentation:** are the right identifier, snippets, and headings included?

Raw snippets should be reviewed after the current test task finishes and before the documentation rendering/publishing step runs.

## 5. Reading Raw Requests: Method, URI, Headers, and Body

Suppose an order creation test is:

~~~java
mockMvc.perform(post("/api/orders")
        .contentType(MediaType.APPLICATION_JSON)
        .accept(MediaType.APPLICATION_JSON)
        .header("X-Request-Id", "docs-001")
        .content("""
            {"productId":"BOOK-42","quantity":2}
            """))
    .andExpect(status().isCreated())
    .andDo(document("orders-create"));
~~~

An illustrative `http-request.adoc` could be:

~~~http
POST /api/orders HTTP/1.1
Content-Type: application/json
Accept: application/json
X-Request-Id: docs-001

{"productId":"BOOK-42","quantity":2}
~~~

When reading the actual file, verify each component:

| Component | Source in test | What to verify |
| --- | --- | --- |
| Method `POST` | `post("/api/orders")` | Matches the HTTP method published by the endpoint. |
| Path `/api/orders` | URI built by the request builder | Matches the route and version prefix. |
| Query string | `queryParam(...)` or URI with query | Contains required names, values, and encoding. |
| `Content-Type` | `contentType(...)` | Body declares the right media type. |
| `Accept` | `accept(...)` | Client-accepted media type matches the contract. |
| Custom headers | `header(...)` | Meaningful names and values, no secrets. |
| Body | `content(...)` / `bodyValue(...)` / `body(...)` | Payload has proper structure, data types, and sample values. |

If the test sends `quantity` as a number but the raw body displays `"quantity":"2"`, check serialization and how the body was constructed. If a request is a bodyless GET yet the snippet shows a body, identify what the test/client/preprocessor produced before deciding whether that content is allowed by the contract.

### 5.1. Request Target and Public URI

With MockMvc, requests can run in-process without opening a real HTTP server. REST Docs may render URLs using separately configured URI settings; therefore, host `api.example.com` in `curl-request.adoc` does not prove that endpoint exists outside the test environment.

If a raw snippet displays an internal host or random port, check the URI configuration or preprocessor. Only substitute the host intentionally for public documentation; do not alter raw sources in ways that hide test-environment behavior reviewers need to see.

### 5.2. Raw Request Body vs. Request Fields

`request-body.adoc` displays the payload; `request-fields.adoc` is the descriptor table. For example:

~~~json
{"productId":"BOOK-42","quantity":2}
~~~

The description table might be:

| Field | Description |
| --- | --- |
| `productId` | Product code to order. |
| `quantity` | Product quantity. |

If the raw body gains a `campaignCode` field that a strict descriptor has not documented, snippet generation can fail. During review, decide whether the new field belongs to the public contract or is merely test metadata; do not casually switch to relaxed mode without understanding the change.

## 6. Reading Raw Responses: Status, Headers, and Body

Suppose the test expects order creation to succeed:

~~~java
.andExpect(status().isCreated())
.andExpect(header().string(HttpHeaders.LOCATION, "/api/orders/102"))
.andExpect(jsonPath("$.id").value(102))
.andDo(document("orders-create"));
~~~

An illustrative response snippet:

~~~http
HTTP/1.1 201 Created
Location: /api/orders/102
Content-Type: application/json

{"id":102,"status":"PENDING"}
~~~

Cross-check checklist:

- Does the status match assertions and the API contract?
- Does `Location` match the URI of the newly created resource?
- Does `Content-Type` match the published media type?
- Does the body reflect the structure and data verified by the test?
- Does a body appear in cases where the status/method requires a bodyless response?
- Are there test-environment headers that need normalizing or explanation?

**Do not assume a test verified everything just by looking at the raw response.** If a test only checks `status().isCreated()`, the snippet still shows the response, yet that does not mean the test asserted `Location`, `Content-Type`, or every body field. Reviewers must inspect the associated assertions and descriptors.

### 6.1. Empty Bodies Must Stay Empty

Cases such as `204 No Content`, `304 Not Modified`, and `HEAD` responses have no body under HTTP semantics. The raw snippet may show only status and headers:

~~~http
HTTP/1.1 204 No Content
~~~

If final documentation includes `response-body.adoc` for such a response and ends up rendering an imaginary JSON block, verify the identifier and source. Never add a payload just to make doc pages look uniform.

### 6.2. Different Statuses Need Different Identifiers

Do not share one identifier for both `200` and `404` responses of the same endpoint. Maintain separate operations such as:

~~~text
orders-get-success/
orders-get-not-found/
~~~

When including them, headings should clearly state success or error scenarios. This prevents readers from mistaking one sample response for every possible outcome of the endpoint.

## 7. Reading Descriptor Snippets

Raw requests/responses show the recorded data. Descriptor snippets help review whether **the important parts have been documented**.

| Descriptor API | Snippet | Review question |
| --- | --- | --- |
| `pathParameters(...)` | `path-parameters.adoc` | Do path variable names and descriptions match the URI template? |
| `queryParameters(...)` | `query-parameters.adoc` | Are all parameters, defaults, limits, and optional behaviors covered? |
| `requestHeaders(...)` | `request-headers.adoc` | Which headers are required from clients, and which are optional? |
| `responseHeaders(...)` | `response-headers.adoc` | Which headers affect how clients process the response? |
| `requestFields(...)` | `request-fields.adoc` | Is the outgoing payload sufficiently explained? |
| `responseFields(...)` | `response-fields.adoc` | Is the returned payload sufficiently explained? |
| `requestParts(...)` | `request-parts.adoc` | Are multipart part names and meanings accurate? |
| `formParameters(...)` | `form-parameters.adoc` | Are form fields distinguished from query parameters? |

### 7.1. Header Descriptors Differ from Raw Headers

Raw `http-request.adoc` may contain many headers, including ones added automatically by the client or environment. `request-headers.adoc` only shows headers declared via descriptors or an equivalent mechanism. A header's absence from the table does not prove it was absent from the raw request.

Similarly, `response-headers.adoc` is an explanatory table for selected headers; it is not necessarily an exhaustive list of every header the server returned. For important values, write explicit assertions in tests.

### 7.2. Strict, Optional, and Relaxed Descriptors

For field descriptors, strict mode catches undocumented fields or missing required fields. `.optional()` allows a field to be absent; `.ignored()` intentionally omits a field from the table; `relaxed...Fields(...)` ignores extra undocumented fields while still enforcing declared descriptors.

When raw snippets and descriptor tables conflict, do not tweak the table just to make the test pass. Determine whether the new payload reflects a contract change or out-of-scope data, then update the test/descriptors accordingly.

## 8. Reading CLI Snippets and Reproducibility

The `curl-request.adoc` and `httpie-request.adoc` snippets provide syntax to replay a request. When reviewing, cross-check them against `http-request.adoc`:

- Is the HTTP method equivalent?
- Do URL and query parameters preserve the exact values?
- Are important headers passed?
- Does the body match the media type and data?
- Are shell quoting and URL encoding appropriate for the documented environment?
- Is the host an accessible address or just a MockMvc sample URI?

A CLI command does not guarantee an identical response when replayed. Authentication, database state, IDs, clock, server state, and default client headers may differ. Documentation should clearly state prerequisites if readers want to execute the command.

For side-effecting commands like POST/PUT/PATCH/DELETE, state clearly that examples use a test environment and sample data. Never encourage running commands against production just to verify a snippet.

## 9. Reviewing Stability and Security

Raw snippets can inadvertently contain data unsuitable for publication:

| Data | Risk | Handling |
| --- | --- | --- |
| `Authorization` token/API key | Could grant access to systems | Use dummy fixtures, replace with placeholders, or mask before generation. |
| `Cookie`/session ID | Could allow session reuse | Remove or replace values; never commit session files. |
| Real email/phone/address | Exposes personal data | Use synthetic data. |
| Internal host/IP/private port | Reveals infrastructure or yields unrunnable commands for readers | Normalize to a public documentation URL and clarify environment. |
| Random timestamps/IDs | Causes noisy documentation diffs | Use deterministic fixtures or deliberate preprocessors. |
| Stack traces/internal exceptions | Reveals implementation structure | Fix error responses and publish only safe details. |
| Large binary files/bodies | Creates huge artifacts hard to review | Document metadata, size, or checksum instead of embedding everything. |

Preprocessors such as `preprocessRequest(...)` and `preprocessResponse(...)` can format, remove, or replace values in the **snippet-generating record**. They do not alter the original request/response handled by the application. If you remove a header from the raw snippet, do not simultaneously describe it as present in the descriptor table.

For variable data, prefer deterministic fixtures. Avoid stripping every differing header mechanically: contract-significant headers like `Location`, `ETag`, `Cache-Control`, or `Content-Type` should be kept and verified.

## 10. From Raw Snippets to the Final Documentation Page

After reviewing raw snippets and descriptors, compose the Asciidoctor page:

~~~asciidoc
= Orders API

== Create Order

Send a JSON request to create a new order. On success, the API returns status 201 and the order URI in Location.

=== HTTP request
include::{snippets}/orders-create/http-request.adoc[]

=== Request fields
include::{snippets}/orders-create/request-fields.adoc[]

=== HTTP response
include::{snippets}/orders-create/http-response.adoc[]

=== Response headers
include::{snippets}/orders-create/response-headers.adoc[]

=== Response fields
include::{snippets}/orders-create/response-fields.adoc[]

== Order Not Found

If the order ID does not exist, the API returns 404.

=== HTTP response
include::{snippets}/orders-get-not-found/http-response.adoc[]
~~~

Final documentation should provide context:

- Endpoint purpose and when to use it.
- Method, path, and input preconditions.
- Meaning of path/query parameters and request headers.
- Test-generated request and response examples.
- Possible returned statuses and how clients handle them.
- Authentication, prerequisites, limits, and side-effect notes.
- Key errors along with error body structure.

You do not need to include every default snippet on every page. Choose snippets that help readers understand and invoke the API, while ensuring necessary raw snippets are inspected beforehand.

### 10.1. With Markdown

`include::{snippets}/...[]` is an Asciidoctor directive not automatically supported by every Markdown renderer. If your final documentation is Markdown, the project needs a template, plugin, or snippet conversion/embedding step. Avoid manual copy-pasting when generation or inclusion can be automated; manual copies quickly drift from raw snippets on the next test run.

## 11. Establishing a Repeatable Review Process

A review checklist for each identifier:

| Step | Action | Expected outcome |
| --- | --- | --- |
| 1 | Find the matching test and identifier | Trace the snippet back to a concrete operation. |
| 2 | Open `http-request.adoc` | Method, URI, query, headers, and body are accurate. |
| 3 | Open `http-response.adoc` | Status, headers, and body reflect the test. |
| 4 | Open descriptor tables | Fields, parameters, and headers are completely and meaningfully described. |
| 5 | Read assertions in the test | Know exactly what is verified. |
| 6 | Check secrets and variable values | No sensitive data leaked; diffs are stable. |
| 7 | Check CLI commands | URL, quoting, credential prerequisites, and side effects are clear. |
| 8 | Include and render final documentation | No missing snippets, no mismatched identifiers, sensible links/headings. |
| 9 | Review changes in diff | Only intentional changes, no stale snippets or junk data. |

For critical endpoints, keep raw snippet review as part of pull requests. Reviewers should read tests and snippets together; looking only at the rendered page can make it hard to spot the source of an incorrect payload or header.

## 12. Build and CI: Avoiding Stale Snippets

A common pitfall is a documentation build succeeding using **leftover snippets from an earlier run**, even when current tests no longer generate them. A reliable pipeline must:

1. Run the exact test suite that generates REST Docs snippets.
2. Fail if tests or assertions fail.
3. Manage the output directory to eliminate stale artifacts in a build-appropriate manner.
4. Run the Asciidoctor/Markdown build after snippets are ready.
5. Fail if include paths are broken or required snippets are missing.
6. Review diffs and publish only when both tests and the documentation build succeed.

~~~mermaid
flowchart TD
    A["Checkout source"] --> B["Prepare clean snippet output"]
    B --> C["Run HTTP tests"]
    C --> D{"All tests pass?"}
    D -->|No| X["Fail pipeline"]
    D -->|Yes| E["Inspect / validate generated snippets"]
    E --> F["Build Asciidoctor/Markdown"]
    F --> G{"All includes and render pass?"}
    G -->|No| X
    G -->|Yes| H["Review artifact / diff"]
    H --> I["Publish documentation"]
~~~

Task names and how output directories are cleaned depend on Gradle/Maven, multi-module layout, and how the project stores generated files. Configure explicit task dependencies so documentation tasks never run before tests. Avoid manually deleting build directories outside the build tool's lifecycle if doing so removes data needed by other tasks.

### 12.1. When Snippets Change in a Pull Request

A valid change can cause multiple raw snippets to change, for example:

- Changing an endpoint path or API version.
- Adding or removing request or response fields.
- Changing status from `200` to `202` per a new contract.
- Adding `ETag` or `Location` headers.
- Updating fixtures, serializers, or preprocessors.
- Renaming an operation identifier.

Reviewers should check whether the change is reflected consistently in API code, tests, descriptors, and final documentation prose. If only a raw snippet changed with no accompanying code/test reason, investigate before merging.

## 13. Common Pitfalls and How to Fix Them

| Symptom | Possible cause | Fix |
| --- | --- | --- |
| Snippet directory not found | Test did not run, different identifier, or different output directory | Check configuration and which tests actually ran. |
| Snippet contains content from an old test | Stale artifacts in output directory or reused identifier | Manage output via build; ensure unique identifiers. |
| Request snippet differs from test expectation | Request builder, query, headers, or body constructed differently than assumed | Compare test call with `http-request.adoc`. |
| Response snippet status differs from docs | Endpoint returns a different status or docs included wrong identifier | Add specific assertions; include the right operation. |
| Raw response is right but fields table is missing | Descriptors not declared or wrong identifier used | Add descriptors and re-run tests. |
| Descriptor table lists a header missing from raw snippet | Header not sent/returned or stripped by preprocessor | Check test and preprocessing order. |
| JSON body ordering/formatting changed | Serializer or preprocessor altered presentation | Compare structure and contract; only compare bytes when required by contract. |
| Snippet contains real token/cookie | Test fixture used secrets or lacked masking | Use dummy data, replace/remove headers, and regenerate snippets. |
| Raw snippet URL points to internal host | Test URI or doc config uses private host | Normalize displayed URI and explain runtime environment. |
| Asciidoctor missing include | Wrong identifier/path or snippets not yet generated | Run tests first and fix include paths. |
| Final docs differ from raw snippets | Manual copy-paste or build does not auto-include | Use includes/templates and review generated diffs. |

## 14. Hands-on Exercise

Suppose an order management API has two operations:

- `POST /api/orders`: request has `customerId` and `items[]`; returns `201 Created` with `Location` and a JSON body.
- `GET /api/orders/101`: returns `200 OK`, `Content-Type: application/json`, and the order payload.

Tasks:

1. Write two HTTP tests with assertions for status, headers, and key fields.
2. Use distinct identifiers `orders-create` and `orders-get-success`.
3. Run the tests; open the output directory and read `http-request.adoc`, `http-response.adoc`, `request-fields.adoc`, `response-fields.adoc`, `request-headers.adoc`, and `response-headers.adoc` if present.
4. Cross-check raw snippets against test code: method, URI, media type, headers, body, status, and sample values.
5. Intentionally add an undocumented field to the payload; observe the strict descriptor catching the change, then decide whether to update the contract/docs or intentionally ignore the field.
6. Check snippets for sensitive data or random values; use dummy fixtures/preprocessors for safe and deterministic output.
7. Include the right snippets in an Asciidoctor page, render documentation, and review the diff.
8. Try making a test fail or removing an identifier to confirm the pipeline does not publish from stale artifacts.

**Completion criteria:** raw snippets trace back to tests; request/response and descriptor tables are verified accurate; missing, stale, or sensitive data is caught; the final page is built from reviewed snippets; and CI publishes only when both tests and the documentation build pass.
