# httpie-request and Corresponding Request Snippets

## 1. Role of the HTTPie Snippet

In the **Spring REST Docs (SPRING_REST_DOCS)** module under the **Default Snippets** chapter, HTTP tests generate verifiable documentation from the requests and responses executed by the test. This lesson focuses on the HTTPie snippet and its accompanying request snippets: HTTP message, body, path/query parameters, headers, JSON fields, and multipart parts.

Request snippets serve different needs:

| Snippet | Content | Purpose |
| --- | --- | --- |
| httpie-request.adoc | HTTPie command reproducing the request | Try out the API using HTTPie |
| curl-request.adoc | cURL command reproducing the request | Try out the API using cURL |
| http-request.adoc | HTTP request message | Review method, path, headers, and body |
| request-body.adoc | Request payload | View the sent data |
| path-parameters.adoc | Path parameters table | Explain variables in the URI template |
| request-parameters.adoc | Request parameters table | Explain documented query/form parameters |
| request-headers.adoc | Request headers table | Explain what each header means |
| request-fields.adoc | Payload fields table | Document and validate JSON/form structure |
| request-parts.adoc | Multipart parts table | Document parts in a multipart request |

Not all files are generated automatically for every operation. HTTPie, cURL, and HTTP message are common default request representations. Tables for parameters, headers, fields, and multipart parts are only generated when the test declares the appropriate descriptors and the client/module supports that API.

Examples use **Spring Boot 3.5, Spring REST Docs 3.x, JUnit Jupiter, and MockMvc**. WebTestClient and REST Assured have their own integration APIs; the principles of operation IDs and snippet assembly remain similar.

## 2. httpie-request.adoc: HTTPie Command Generated from the Request

HTTPie is a command-line tool for sending HTTP requests with concise syntax. Spring REST Docs generates httpie-request.adoc from the recorded request, helping integrators copy the command and test the endpoint.

GET request example:

```bash
http GET :8080/api/products/42 Accept:application/json
```

POST sending JSON example:

```bash
http POST :8080/api/products \
  Accept:application/json \
  name="Mechanical Keyboard" \
  price:=89.5
```

In HTTPie syntax:

- http is the CLI command.
- GET, POST, PATCH, PUT, or DELETE is the HTTP method.
- :8080/api/products is a URL shorthand using the default host and specified port.
- Accept:application/json is a header using Header:Value syntax.
- name="Mechanical Keyboard" represents a text value in a JSON object.
- price:=89.5 represents a non-string JSON value; := tells HTTPie to parse the value as a JSON type.

The actual command generated by REST Docs depends on the method, URL, headers, body, and how the request was constructed. The examples above illustrate HTTPie syntax; not every request body is automatically converted into the exact JSON arguments shown in manual examples. Inspect the generated snippet to see the exact command produced by the REST Docs version you use.

### When to Use HTTPie?

The HTTPie snippet is useful when readers want to test an endpoint from a terminal, send JSON/headers with readable syntax, share a request to reproduce a bug, or compare a sample request with http-request.adoc.

The HTTPie snippet is not proof that the test executed the HTTPie program. The original request may have been sent using MockMvc, WebTestClient, or REST Assured; REST Docs generates an HTTPie command to model that request.

## 3. Comparing HTTPie, cURL, and HTTP Message

The three snippets typically describe the same request in different formats:

| Criterion | httpie-request.adoc | curl-request.adoc | http-request.adoc |
| --- | --- | --- | --- |
| Format | HTTPie command | cURL command | HTTP message |
| Purpose | Send the request with HTTPie | Send the request with cURL | Read protocol structure |
| Headers | HTTPie syntax | Uses -H | Displayed directly |
| JSON Body | Key/value or input data | -d/--data | Payload after headers |
| Run directly | Yes, after adjusting URL/credentials | Yes, after adjusting URL/credentials | Not a terminal command |

Example of the same POST request:

```http
POST /api/products HTTP/1.1
Content-Type: application/json
Accept: application/json

{"name":"Mechanical Keyboard","price":89.5}
```

```bash
curl 'http://localhost:8080/api/products' \
  -i \
  -X POST \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  -d '{"name":"Mechanical Keyboard","price":89.5}'
```

```bash
http POST :8080/api/products \
  Content-Type:application/json \
  Accept:application/json \
  name="Mechanical Keyboard" \
  price:=89.5
```

These examples illustrate the same method, URL, headers, and JSON data. The exact representation in snippets may vary by HTTPie/REST Docs version and the body type recorded by the client.

## 4. Related Request Snippets

### 4.1. http-request.adoc

This is the request in HTTP message format, typically including method, request target, protocol, headers, and body. It helps debug requests without depending on a specific CLI's syntax.

### 4.2. request-body.adoc

This snippet contains the request payload, usually JSON, form data, or other content:

```json
{
  "name": "Mechanical Keyboard",
  "price": 89.5,
  "tags": ["office", "accessory"]
}
```

The raw body lets readers see sample data but does not explain the meaning of each field. Use requestFields(...) to generate request-fields.adoc and validate the payload structure.

### 4.3. path-parameters.adoc

Path parameters live in the URI template, e.g., GET /api/products/{id}. When the test calls id = 42, the request expands to /api/products/42. Descriptors preserve the placeholder meaning:

```java
pathParameters(
    parameterWithName("id")
        .description("Product identifier")
)
```

With MockMvc, use RestDocumentationRequestBuilders to preserve the URI template for path parameter extraction. If the builder does not preserve the template, REST Docs may fail to identify variable names after the URI is expanded.

### 4.4. request-parameters.adoc

Request parameters are typically query parameters or form parameters documented via requestParameters(...) and the client's equivalent API.

Example:

```text
GET /api/products?category=keyboard&page=0
```

Descriptor:

```java
requestParameters(
    parameterWithName("category").description("Category to filter by"),
    parameterWithName("page").description("Page number, starting from 0")
)
```

Do not confuse query parameters with path parameters. Query parameters follow the ? sign, whereas path parameters are placeholders in the URI template. Check the exact snippet name and extraction mechanism against the client/module API in use.

### 4.5. request-headers.adoc

Headers are metadata sent along with the request:

```text
Accept: application/json
Content-Type: application/json
If-Match: "v3"
```

Descriptor:

```java
requestHeaders(
    headerWithName("Accept")
        .description("Desired response format"),
    headerWithName("Content-Type")
        .description("Request payload format")
)
```

Headers can affect content negotiation, conditional requests, caching, authentication, or tracing. Not every internal header should become public documentation.

### 4.6. request-fields.adoc

When the payload is structured, use requestFields(...) to describe its fields:

```java
requestFields(
    fieldWithPath("name").description("Product name"),
    fieldWithPath("price").description("Selling price"),
    fieldWithPath("tags").description("List of tags")
)
```

The generated snippet is a field description table, and it also validates the actual payload against the documentation. If a new undocumented field appears, the test may fail. For nested fields, arrays, or optional fields, use appropriate path descriptors and intentionally mark them as optional or ignored.

### 4.7. Multipart request

For multipart requests, each part can have its own name, content type, and payload. Upload endpoint example:

```http
POST /api/documents HTTP/1.1
Content-Type: multipart/form-data; boundary=----Boundary

------Boundary
Content-Disposition: form-data; name="metadata"
Content-Type: application/json

{"title":"Guide"}
------Boundary
Content-Disposition: form-data; name="file"; filename="guide.pdf"
Content-Type: application/pdf

...binary content...
------Boundary--
```

REST Docs provides request part descriptors to document the parts being sent. With multipart, the raw body can be complex or unsuitable for displaying full file bytes. Use request-part descriptors and part field APIs supported by the client; avoid putting large binary data into documentation.

## 5. MockMvc Example Generating HTTPie and Request Snippets

### Sample Controller

```java
package com.example.catalog;

import java.math.BigDecimal;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/products")
class ProductController {

    @GetMapping("/{id}")
    ProductResponse find(
            @PathVariable long id,
            @RequestParam(defaultValue = "vi") String locale) {
        return new ProductResponse(id, "Mechanical Keyboard", locale);
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    ProductResponse create(@RequestBody CreateProductRequest request) {
        return new ProductResponse(42L, request.name(), "vi");
    }

    record CreateProductRequest(String name, BigDecimal price) {}
    record ProductResponse(long id, String name, String locale) {}
}
```

### Dependencies

Gradle Groovy DSL:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.restdocs:spring-restdocs-mockmvc'
}

tasks.named('test') {
    useJUnitPlatform()
}
```

### Test Recording Operations

```java
package com.example.catalog;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.restdocs.AutoConfigureRestDocs;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.restdocs.headers.HeaderDocumentation.headerWithName;
import static org.springframework.restdocs.headers.HeaderDocumentation.requestHeaders;
import static org.springframework.restdocs.mockmvc.MockMvcRestDocumentation.document;
import static org.springframework.restdocs.mockmvc.RestDocumentationRequestBuilders.get;
import static org.springframework.restdocs.mockmvc.RestDocumentationRequestBuilders.post;
import static org.springframework.restdocs.payload.PayloadDocumentation.fieldWithPath;
import static org.springframework.restdocs.payload.PayloadDocumentation.requestFields;
import static org.springframework.restdocs.request.RequestDocumentation.parameterWithName;
import static org.springframework.restdocs.request.RequestDocumentation.pathParameters;
import static org.springframework.restdocs.request.RequestDocumentation.requestParameters;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@WebMvcTest(ProductController.class)
@AutoConfigureRestDocs(outputDir = "build/generated-snippets/catalog")
class ProductRequestDocumentationTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void findProduct() throws Exception {
        mockMvc.perform(
                get("/api/products/{id}", 42)
                    .queryParam("locale", "vi")
                    .accept(MediaType.APPLICATION_JSON)
            )
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.id").value(42))
            .andDo(document("products-find",
                pathParameters(
                    parameterWithName("id").description("Product ID")
                ),
                requestParameters(
                    parameterWithName("locale").description("Language")
                ),
                requestHeaders(
                    headerWithName("Accept")
                        .description("Desired response format")
                )
            ));
    }

    @Test
    void createProduct() throws Exception {
        mockMvc.perform(
                post("/api/products")
                    .contentType(MediaType.APPLICATION_JSON)
                    .accept(MediaType.APPLICATION_JSON)
                    .content("{\"name\":\"Mechanical Keyboard\",\"price\":89.5}")
            )
            .andExpect(status().isCreated())
            .andDo(document("products-create",
                requestHeaders(
                    headerWithName("Content-Type")
                        .description("Request payload format")
                ),
                requestFields(
                    fieldWithPath("name").description("Product name"),
                    fieldWithPath("price").description("Selling price")
                )
            ));
    }
}
```

The test class records two separate operations. products-find has a path parameter, query parameter, and request header; products-create has a request header and JSON request fields. For each operation, REST Docs also generates basic request snippets, including HTTPie and HTTP message under the default template.

### Output Structure

With outputDir set to build/generated-snippets/catalog, the expected structure is:

```text
build/generated-snippets/
  catalog/
    products-find/
      http-request.adoc
      curl-request.adoc
      httpie-request.adoc
      request-body.adoc
      path-parameters.adoc
      request-parameters.adoc
      request-headers.adoc
    products-create/
      http-request.adoc
      curl-request.adoc
      httpie-request.adoc
      request-body.adoc
      request-headers.adoc
      request-fields.adoc
```

This is a diagram of expected snippets according to the declared operations and descriptors. The body snippet depends on whether the request body has content; actual output also depends on template format and REST Docs version.

## 6. Including Snippets in Asciidoctor

The src/docs/asciidoc/products.adoc file can choose which sections to present:

```asciidoc
= Products API
:toc: left

== Find product

=== HTTP request
include::{snippets}/catalog/products-find/http-request.adoc[]

=== HTTPie
include::{snippets}/catalog/products-find/httpie-request.adoc[]

=== Path parameters
include::{snippets}/catalog/products-find/path-parameters.adoc[]

=== Query parameters
include::{snippets}/catalog/products-find/request-parameters.adoc[]

=== Request headers
include::{snippets}/catalog/products-find/request-headers.adoc[]

== Create product

=== HTTPie
include::{snippets}/catalog/products-create/httpie-request.adoc[]

=== Request fields
include::{snippets}/catalog/products-create/request-fields.adoc[]
```

The {snippets} attribute must point to the root directory build/generated-snippets, not an operation directory. With Maven, the default directory is usually target/generated-snippets. If tests use a custom outputDir, adjust the attribute to match that root.

It is not necessary to include every snippet on every page. HTTPie fits hands-on guides; HTTP message fits protocol documentation; request fields and parameter tables fit contract explanations.

## 7. URI and Credentials in the HTTPie Snippet

When tests use RANDOM_PORT, snippets may contain localhost and a dynamically assigned port. For public documentation to use an appropriate host, configure Spring REST Docs' displayed URI:

```java
@AutoConfigureRestDocs(
    uriScheme = "https",
    uriHost = "api.example.com",
    uriPort = 443
)
```

The configuration only affects snippet content; it does not make HTTPie/cURL in tests send requests to the public host and does not enable TLS for the embedded server.

If the HTTPie snippet contains Authorization, cookies, or sensitive data, do not use real credentials. Use dummy tokens dedicated to tests and redact headers before writing documentation. HTTPie is a command that can be copied directly, so verify carefully to avoid leaking production tokens or internal URLs.

## 8. Common Misconceptions

| Misconception | Reality |
| --- | --- |
| httpie-request proves the test used HTTPie | The test may use MockMvc/WebTestClient/REST Assured; HTTPie is just a representation of the request. |
| httpie-request and http-request are the same | One file is a CLI command; the other is an HTTP message. |
| request-body describes field meanings | It shows the payload; a field table requires requestFields(...). |
| Query parameters and path parameters are the same thing | Query parameters come after ?; path parameters are placeholders in the URI template. |
| Every operation has every request snippet | Files depend on body, descriptors, and client module. |
| Changing uriHost makes the client call the new host | Snippet URI changes; the client's base URL does not change. |
| Having a header in a request snippet means the header is explained | A description table requires requestHeaders(...). |

## 9. Common Errors

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Missing httpie-request.adoc | Operation has not been recorded with document(...), test did not run, or output is in another folder. | Check test report, operation ID, and outputDir. |
| HTTPie command contains local host/port | URI captured from test server. | Configure uriScheme, uriHost, uriPort. |
| HTTPie command does not send JSON as expected | Differences between JSON body, form fields, and HTTPie syntax. | Inspect http-request/request-body; adjust command for the payload. |
| Missing request-parameters.adoc | Descriptors not declared or client did not extract that parameter. | Use the proper descriptor API and verify output. |
| Missing path-parameters.adoc | URI template not preserved or pathParameters(...) not declared. | Use REST Docs request builders and declare descriptors. |
| request-fields reports undocumented field | Payload has a new field not covered by descriptors. | Update the contract or intentionally mark optional/ignored. |
| Snippet leaks Authorization | Test uses real credentials or lacks redaction. | Use dummy tokens and preprocess headers. |
| Asciidoctor cannot find HTTPie file | Wrong snippets attribute, operation ID, or extension. | Cross-check output folder and include path. |

## 10. Hands-on Exercise

For the Catalog API, perform the following:

1. Write a GET /api/products/{id} test with a path parameter, locale query, and Accept header; generate HTTPie along with request snippets.
2. Write a POST /api/products test sending a JSON body; declare requestHeaders(...) and requestFields(...).
3. Open httpie-request.adoc, http-request.adoc, and request-body.adoc; compare method, URL, headers, and payload.
4. Include HTTPie, path parameters, request parameters, request headers, and request fields in Asciidoctor.
5. Configure a public URI for snippets while keeping the test client calling the local server; verify the two addresses serve two separate purposes.
6. Add a dummy auth header, redact it before writing snippets, and verify no credentials appear in the output.
7. Run clean test asciidoctor; verify documentation is generated from the new snippets.

**Completion criteria:** explain how the HTTPie snippet differs from HTTP message and cURL; know which request snippets are basic and which require descriptors; identify the correct operation ID/output folder; document requests without leaking credentials; assemble the needed content into documentation.
