# Checking the Output Directory and Asciidoctor Plugin

## Lesson Objectives

When upgrading Spring REST Docs or your build tool, tests may still pass while documentation fails to generate. The root cause usually lies in the output directory, task dependencies, Asciidoctor plugin configuration, include paths, or artifacts being generated in a different directory than where the renderer is looking.

This lesson belongs to the **Upgrade** chapter of the **SPRING_REST_DOCS** module: generating verifiable REST API documentation through HTTP tests with **MockMvc**, **WebTestClient**, or **REST Assured**; producing snippets for requests, responses, payloads, parameters, and headers; authoring Asciidoctor/Markdown documentation; and integrating it into the build and CI.

After this lesson, you will be able to:

- Identify the actual output directory used by Spring REST Docs.
- Inspect the Asciidoctor plugin and extension dependencies.
- Wire the proper sequence: test → snippet → Asciidoctor → artifact.
- Configure the snippets attribute and include paths accurately.
- Distinguish between test errors, task errors, include errors, and publishing errors.
- Verify output in a clean CI environment.
- Detect stale snippets or inconsistent output directories.

## 1. Understanding the Documentation Generation Flow

Spring REST Docs does not build a complete website just by running tests. Tests generate snippets; Asciidoctor reads AsciiDoc sources and includes those snippets to produce HTML or other artifacts.

~~~mermaid
flowchart TD
    A["MockMvc / WebTestClient / REST Assured tests"] --> B["Generated snippets"]
    B --> C["AsciiDoc source + include directives"]
    C --> D["Asciidoctor plugin"]
    D --> E["HTML documentation"]
    E --> F["CI artifact / publish"]
~~~

Each step has its own inputs and outputs:

| Step | Input | Output to Verify |
| --- | --- | --- |
| HTTP tests | Test code and fixtures | Test results |
| REST Docs | Documented operations | Snippets organized by document identifier |
| Asciidoctor | AsciiDoc files, attributes, and snippets | Configured HTML/PDF or artifact |
| CI | Documentation output | Saved or published artifact |

When something fails, identify the first step that does not produce its expected output. This keeps you from editing include paths when tests never generated snippets in the first place.

## 2. Identifying the REST Docs Output Directory

In Gradle, MockMvc setup commonly uses MockMvcRestDocumentationConfigurer with RestDocumentationContextProvider. If no separate output directory is specified, the integration typically uses the output directory configured in the test setup or project conventions.

Common setup example:

~~~java
@BeforeEach
void setUp(WebApplicationContext context,
           RestDocumentationContextProvider restDocumentation) {
    this.mockMvc = MockMvcBuilders
        .webAppContextSetup(context)
        .apply(documentationConfiguration(restDocumentation))
        .build();
}
~~~

RestDocumentationContextProvider is usually supplied by the JUnit integration and configured at test runtime. Do not guess the output directory from the test method alone; check the test rule/extension, build script, and logs of an actual run.

A project might use a layout like:

~~~text
build/
└── generated-snippets/
    ├── orders-get/
    │   ├── http-request.adoc
    │   └── http-response.adoc
    └── orders-create/
        ├── http-request.adoc
        ├── request-fields.adoc
        └── response-fields.adoc
~~~

This is an example directory structure, not a mandatory convention for every project. Document identifiers such as orders-get create matching subdirectories; file names depend on the snippets/templates in use.

### 2.1. Checking Snippet Files After Running Tests

Run the appropriate test task:

~~~powershell
./gradlew test
~~~

Then inspect:

~~~powershell
Get-ChildItem -Path build/generated-snippets -Recurse -File
~~~

If the project configures output elsewhere, replace the path with the directory confirmed in the configurer or test output. Check at least one representative operation and confirm the file contents are non-empty.

### 2.2. Distinguishing Test Output from Documentation Output

Do not confuse:

- build/generated-snippets: snippets generated by REST Docs.
- build/docs/asciidoc or build/docs: rendered documentation files, depending on plugin and configuration.
- build/reports/tests: Gradle test reports.

Exact paths depend on the build script. Do not hard-code an assumed path into includes or CI if the project already uses a different convention.

## 3. Configuring the Asciidoctor Plugin in Gradle

A Gradle build may use the AsciidoctorJ plugin:

~~~groovy
plugins {
    id 'java'
    id 'org.asciidoctor.jvm.convert' version '4.0.2'
}
~~~

Example extension dependency and task configuration:

~~~groovy
configurations {
    asciidoctorExt
}

dependencies {
    testImplementation 'org.springframework.restdocs:spring-restdocs-mockmvc:3.0.3'
    asciidoctorExt 'org.springframework.restdocs:spring-restdocs-asciidoctor:3.0.3'
}

tasks.named('asciidoctor') {
    configurations 'asciidoctorExt'
    inputs.dir layout.buildDirectory.dir('generated-snippets')
    attributes 'snippets': layout.buildDirectory.dir('generated-snippets').get().asFile
}
~~~

The versions in this example are illustrative only. Choose plugin and Spring REST Docs versions compatible with your project's Gradle/JDK/Spring stack. Do not upgrade the Asciidoctor plugin and REST Docs simultaneously without good reason; separating changes makes it easier to pinpoint causes when builds fail.

asciidoctorExt places the extension on Asciidoctor's classpath. The plugin must be applied and configured correctly so the render task recognizes the extension and attributes. If you are not using the Spring REST Docs extension, do not add the dependency merely because it appears in examples.

## 4. Connecting the Test Task to Asciidoctor

Asciidoctor must run after snippets are generated. You can declare the task dependency:

~~~groovy
tasks.named('asciidoctor') {
    dependsOn tasks.named('test')
}
~~~

If tests are split across multiple tasks, such as MockMvc tests and REST Assured tests, the Asciidoctor task must depend on every snippet-producing task whose output is included.

Do not create circular dependencies. For instance, test must not depend on Asciidoctor if Asciidoctor already depends on test.

Overall build flow:

~~~groovy
tasks.named('asciidoctor') {
    dependsOn tasks.named('test')
}

tasks.named('build') {
    dependsOn tasks.named('asciidoctor')
}
~~~

Task names may differ if the project defines custom ones. Inspect the task graph with:

~~~powershell
./gradlew asciidoctor --dry-run
~~~

A dry-run shows which tasks are scheduled, not whether snippets are actually generated. Run the real tasks afterward and inspect the output files.

## 5. Configuring the Snippets Attribute and Includes

In AsciiDoc, use a document attribute to point to the snippets directory:

~~~asciidoc
:snippets: build/generated-snippets

== Get Order

=== HTTP request

include::{snippets}/orders-get/http-request.adoc[]

=== HTTP response

include::{snippets}/orders-get/http-response.adoc[]
~~~

In Gradle, the attribute can be configured to match the output directory:

~~~groovy
tasks.named('asciidoctor') {
    attributes 'snippets': layout.buildDirectory
        .dir('generated-snippets')
        .get()
        .asFile
}
~~~

Both approaches must point to the exact same actual directory. If the attribute is set in the source file and the build script also passes an attribute with the same name, check precedence according to how Asciidoctor/the plugin handles attributes.

Some projects rely on attributes supplied by the Spring REST Docs extension. Read the documentation for the exact installed version to avoid duplicate declarations or overriding values configured by the extension.

## 6. Checking Snippet Names and Document Identifiers

A common mistake is including the wrong file path:

~~~asciidoc
include::{snippets}/orders-get/http-request.adoc[]
~~~

While the test actually writes:

~~~java
document("order-get")
~~~

Two different identifiers create two different output subdirectories. Check:

- The string passed to document(...).
- The subdirectory created inside generated snippets.
- The actual snippet file names produced by REST Docs.
- Whether the file extension is .adoc or .md according to template format.
- The relative include path after Asciidoctor resolves it.

Do not rename files manually to make includes pass. Fix the document identifier or the include directive based on the actual output and documentation intent.

## 7. Inspecting Resolved Plugins and Versions

With Gradle, inspect plugins and dependencies:

~~~powershell
./gradlew buildEnvironment
./gradlew dependencyInsight --dependency spring-restdocs --configuration testRuntimeClasspath
~~~

Check:

- Whether the Asciidoctor plugin is applied in the right module.
- Whether the plugin version is compatible with the Gradle wrapper and JDK.
- Whether the spring-restdocs-asciidoctor extension is in the right configuration.
- Whether REST Docs core and integration artifacts share the same version.
- Whether the snippet-generating test task executes before Asciidoctor.

With Maven, inspect the plugin in pom.xml, the effective POM, and its execution phase. Do not assume mvn test automatically generates HTML if the Asciidoctor plugin is bound to a different phase.

## 8. Checking the Output Directory in CI

Local builds may pass because build/generated-snippets still holds files from a prior run. CI usually starts in a clean workspace, exposing path or task-dependency bugs.

In CI, you should:

1. Use the project-pinned Gradle wrapper or Maven version.
2. Run tests that generate snippets.
3. Verify required snippets exist.
4. Run Asciidoctor.
5. Check HTML/artifact output.
6. Upload/publish the exact configured directory.

Example Gradle pipeline:

~~~yaml
steps:
  - name: Generate REST Docs and render
    run: ./gradlew clean test asciidoctor

  - name: Verify documentation output
    shell: pwsh
    run: |
      if (-not (Test-Path 'build/docs/asciidoc')) {
        throw 'Asciidoctor output directory not found'
      }
      Get-ChildItem 'build/docs/asciidoc' -Recurse -File
~~~

This is an illustrative example; replace paths with the actual output directory of your plugin and workflow. Some plugins output HTML to build/docs/asciidoc, but do not assume that if the task customizes outputDir.

## 9. Layer-by-Layer Diagnosis

When documentation fails to build, check in order:

| Layer | Question | Action |
| --- | --- | --- |
| Test | Did REST Docs tests run? | Check test reports and filters |
| Snippet | Were files created? | List the output directory |
| Identifier | Does the operation folder match the ID? | Compare document(...) against includes |
| Extension | Did Asciidoctor load the extension? | Inspect configuration/plugin classpath |
| Attribute | Does {snippets} point to the right path? | Check attributes after configuration |
| Include | Do included files exist with the right extension? | Cross-check generated output |
| Render | Did the Asciidoctor task succeed? | Read logs and output directory |
| Publish | Was the artifact uploaded? | Verify paths in the CI step |

Do not start by clearing caches or changing plugin versions before knowing which layer failed. Controlled output cleaning is helpful to spot stale snippets, provided the test task re-runs and produces all required inputs.

## 10. Conceptual Maven Configuration

With Maven, the pipeline is similar but wired via plugin executions:

~~~xml
<build>
    <plugins>
        <plugin>
            <groupId>org.asciidoctor</groupId>
            <artifactId>asciidoctor-maven-plugin</artifactId>
            <version>VERSION_OF_PLUGIN</version>
            <executions>
                <execution>
                    <phase>prepare-package</phase>
                    <goals>
                        <goal>process-asciidoc</goal>
                    </goals>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>
~~~

VERSION_OF_PLUGIN is a placeholder and must be replaced with a verified compatible version. Configure the source directory, output directory, attributes, extensions, and plugin dependencies according to the exact Maven plugin version in use.

Ensure tests run prior to the documentation generation phase. If snippets are only produced by a specific profile or test group, Maven must activate that profile before rendering.

## 11. Common Mistakes

| Symptom | Cause | Resolution |
| --- | --- | --- |
| No generated snippets | Tests did not run or documentation filter not attached | Check test task and integration setup |
| Snippets in wrong directory | Test output directory differs from Asciidoctor attribute | Use one unified path |
| Include reports file not found | Document ID or snippet name mismatch | Cross-check actual output |
| Include uses .md but file is .adoc | Template format differs from assumption | Configure templates or fix includes |
| asciidoctor task does not exist | Plugin not applied or wrong module | Check plugins block and project path |
| Extension not loaded | Wrong configuration or missing dependency | Check asciidoctorExt/plugin classpath |
| Passes locally, fails in CI | Stale output or CI skipped snippet-generating tests | Run clean test before Asciidoctor |
| HTML does not appear | Different outputDir or task did not run | Check task logs and output configuration |
| Published artifact is empty | Uploaded the wrong directory | Use the task's actual output directory |
| Build runs before snippets finish | Missing task dependency | Wire asciidoctor after snippet-producing tasks |

## 12. Hands-On Exercise

Given the operation:

~~~java
mockMvc.perform(get("/api/orders/{id}", 42))
    .andExpect(status().isOk())
    .andDo(document("orders-get"));
~~~

Do the following:

1. Identify the output directory currently used by the test.
2. Run the test and confirm orders-get and its actual snippets are generated.
3. Inspect the Asciidoctor plugin and its resolved version.
4. Configure the snippets attribute to point to the exact output directory.
5. Include http-request and http-response in an AsciiDoc file.
6. Wire the Asciidoctor task after the snippet-generating test task.
7. Run a clean build to expose any dependence on stale output.
8. Inspect the generated HTML and upload the right artifact in CI.

**Completion criteria:** tests generate snippets in a deterministic output directory; Asciidoctor resolves includes properly; clean builds produce HTML; CI saves the correct artifact and fails if required snippets are missing.

## Key Takeaways

When inspecting a Spring REST Docs pipeline, trace the path from tests to snippets, from snippets to Asciidoctor, and from HTML to CI artifacts. The test output directory must match the path used by the snippets attribute and include directives. The Asciidoctor plugin and extension must be configured in the right module at compatible versions; the render task must depend on snippet-generating tasks. Always test with a clean build to catch stale files, verify operation names and snippet extensions, and inspect final artifacts before publishing.
