# `Content-Type` and `Accept` in Documentation

## 1. Objectives and Context

When an HTTP client calls a REST API, two headers commonly govern how data is exchanged: **`Content-Type`** and **`Accept`**. Both relate to media types, yet describe two opposite directions:

- `Content-Type` states **what format the current message's body is represented in**.
- `Accept` states **which media types the client can receive in the response**.

Confusing these two headers can cause requests to be rejected by the server, unexpected response representations to be chosen, or API documentation to describe the wrong contract. This content belongs to the **HTTP operation** chapter of `SPRING_REST_DOCS`.

The `SPRING_REST_DOCS` module aims to produce verifiable REST API documentation from HTTP tests using MockMvc, WebTestClient, or REST Assured; generate snippets for requests, responses, payloads, parameters, and headers; and then author docs with Asciidoctor/Markdown integrated into build and CI.

After this lesson, you will be able to:

- Distinguish the roles of `Content-Type` and `Accept` in requests and responses.
- Read media type, subtype, parameters, charset, and wildcards in headers.
- Relate `consumes`/`produces` to handler selection and content negotiation in Spring MVC.
- Write tests for JSON, XML, `406 Not Acceptable`, and `415 Unsupported Media Type`.
- Generate `http-request`, `http-response`, `request-headers`, and payload table snippets from tests.
- Include examples in documentation and detect contract changes in CI.

## 2. `Content-Type`: What Format Is the Current Body?

The `Content-Type` header declares the **media type of the representation in the message body**. Example of a client sending JSON:

~~~http
POST /api/books HTTP/1.1
Content-Type: application/json

{"title":"Spring in Action","price":199000}
~~~

Here, `application/json` describes the format of the body sent by the client. The server relies on this information along with handler/converter configuration to parse the payload.

If the body is XML:

~~~http
POST /api/books HTTP/1.1
Content-Type: application/xml

<book><title>Spring in Action</title></book>
~~~

The media type changed; the payload must genuinely match the declared format. Simply changing the header from `application/json` to `application/xml` while keeping a JSON body does not turn JSON into XML.

### 2.1. How Is a Media Type Structured?

A typical media type has the form:

~~~text
type/subtype; parameter=value
~~~

Example:

~~~http
Content-Type: application/json; charset=UTF-8
~~~

| Component | Example | Meaning |
| --- | --- | --- |
| Type | `application` | Top-level media type category. |
| Subtype | `json` | Specific representation format. |
| Parameter | `charset=UTF-8` | Additional parameter per media type syntax. |

Common examples:

| Media type | Data format | Scenario |
| --- | --- | --- |
| `application/json` | JSON | APIs exchanging objects, arrays, and business data. |
| `application/problem+json` | JSON Problem Details | Representing HTTP errors per the Problem Details contract. |
| `application/xml` | XML | APIs requiring XML exchange. |
| `application/x-www-form-urlencoded` | URL-encoded form | Forms with key/value pairs in the body. |
| `multipart/form-data` | Multipart | File uploads and form fields. |
| `text/plain` | Plain text | APIs accepting/returning plain text content. |
| `application/octet-stream` | Byte stream | Binary content without a specific format. |

**Note on charset:** JSON exchanged over modern HTTP is defined as UTF-8; there is no need to add `charset=UTF-8` to every JSON request. Some frameworks may emit a charset parameter in headers or represent it differently depending on converters/configuration. Check the media type according to the real contract instead of enforcing an unnecessary rigid header string.

### 2.2. When Does a Request Need `Content-Type`?

A request with a body typically needs to specify its format so the server knows how to read the body. For example:

- `POST` sending JSON: `Content-Type: application/json`.
- `PUT` sending XML: `Content-Type: application/xml`.
- File upload: `Content-Type: multipart/form-data; boundary=...` generated by the multipart client.
- URL-encoded form: `Content-Type: application/x-www-form-urlencoded`.

A `GET` request without a body normally does not need `Content-Type`. Do not add this header to every request out of habit; it is meaningful when a body must be interpreted.

## 3. `Accept`: Which Representation Does the Client Want?

`Accept` is a request header used in **content negotiation**. The client lists the media types it can handle:

~~~http
GET /api/books/42 HTTP/1.1
Accept: application/json
~~~

This means the client prefers or accepts a JSON response. If the API offers multiple representations, the server can select an appropriate one. The `Accept` header does not guarantee the server will return JSON: the API must support that representation, and selection also depends on other conditions.

### 3.1. Common `Accept` Value Forms

| Value | Meaning |
| --- | --- |
| `application/json` | Specifies JSON format only. |
| `application/xml` | Specifies XML format only. |
| `application/json, application/xml` | Client accepts JSON or XML; server picks per content negotiation rules and priorities. |
| `application/*` | Accepts any subtype under type `application`. |
| `*/*` | Accepts any media type. |
| `application/json;q=1.0, application/xml;q=0.8` | Lists both choices along with relative priority weights. |

The `q` (quality value) parameter ranges from `0` to `1`, indicating preference weight for a media range during negotiation. If the client omits `Accept`, the server applies default behavior per HTTP and framework/configuration; never assume the client only accepts JSON.

Example:

~~~http
GET /api/books/42 HTTP/1.1
Accept: application/xml;q=0.9, application/json;q=1.0
~~~

The client prioritizes JSON over XML. If the endpoint only provides XML, the result depends on how Spring configures handlers/converters and negotiation; the API may reject an unacceptable representation rather than automatically returning JSON.

### 3.2. `Accept` Is Not `Content-Type`

| Question | Header that answers it | Example |
| --- | --- | --- |
| "What format is the body I am sending?" | `Content-Type` | `Content-Type: application/json` |
| "What format do I accept for the response?" | `Accept` | `Accept: application/xml` |

A request can send JSON while requesting an XML response:

~~~http
POST /api/books HTTP/1.1
Content-Type: application/json
Accept: application/xml

{"title":"Spring in Action"}
~~~

This is completely valid if the API accepts JSON and provides an XML response. Both headers do not have to carry the same value because they describe two different directions.

## 4. Content Negotiation and Spring MVC

Spring MVC uses message conversion (HTTP message converters) to read request bodies and write response bodies. The request's media type and mapping conditions influence handler/converter selection.

### 4.1. `consumes`: Restricting Request Body Format

Example controller:

~~~java
@PostMapping(
    path = "/api/books",
    consumes = MediaType.APPLICATION_JSON_VALUE,
    produces = MediaType.APPLICATION_JSON_VALUE
)
public ResponseEntity<BookResponse> create(
        @RequestBody CreateBookRequest request) {
    BookResponse created = bookService.create(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(created);
}
~~~

`consumes` declares the **request body** media type accepted by the mapping. In this example, the endpoint requires `application/json`. If a client sends an XML body to a mapping that only accepts JSON, the framework typically returns `415 Unsupported Media Type`, depending on handler and converter configuration.

### 4.2. `produces`: Restricting Response Format

`produces` declares the media types that the handler can produce. Spring can compare the `Accept` header against the media types supported by the endpoint. If no matching representation exists, the request may receive `406 Not Acceptable`.

Example endpoint supporting JSON only:

~~~java
@GetMapping(
    path = "/api/books/{id}",
    produces = MediaType.APPLICATION_JSON_VALUE
)
public BookResponse get(@PathVariable long id) {
    return bookService.get(id);
}
~~~

A client calling with `Accept: application/json` matches. A client requesting `Accept: application/xml` may be rejected with `406` if the endpoint lacks a matching XML converter/representation and negotiation is configured accordingly.

**Do not confuse `consumes` with `produces`:**

- `consumes` controls the request content types the mapping can accept.
- `produces` controls the response content types the mapping can provide.
- `Content-Type` describes the body of the outgoing request.
- `Accept` expresses the response media types the client accepts.

### 4.3. Converters and Processing Layers

Common converters:

| Converter (overview) | Format | Notes |
| --- | --- | --- |
| Jackson JSON converter | JSON | Present in many Spring Boot web apps when the corresponding dependency is configured. |
| XML converter | XML | Requires XML support dependency/configuration, such as Jackson XML or another compatible converter. |
| String converter | Text | Used for string-based data. |
| Resource/byte-array converter | Binary/resource | Used for file contents or byte data. |
| Form converter | Form/multipart | Handles form data, multipart, and matching request types. |

Having a converter on the classpath does not mean every endpoint automatically supports every media type. Outcomes also depend on `consumes`/`produces` mappings, data types, converter configuration, and priority order.

## 5. Distinguishing `400`, `406`, and `415` Errors

These three statuses commonly appear in media-type tests:

| Status | Typical scenario | Related header |
| --- | --- | --- |
| `400 Bad Request` | Body cannot be parsed or content/input is invalid per contract | May have a valid `Content-Type` but malformed JSON syntax. |
| `406 Not Acceptable` | Client requests a representation via `Accept` that the server cannot provide | `Accept` |
| `415 Unsupported Media Type` | Server does not support the request body's media type or content coding in context | `Content-Type` |

Examples:

**415:** API accepts JSON, but client sends XML:

~~~http
POST /api/books HTTP/1.1
Content-Type: application/xml
Accept: application/json

<book><title>Spring</title></book>
~~~

**406:** API only provides JSON, but client only accepts XML:

~~~http
GET /api/books/42 HTTP/1.1
Accept: application/xml
~~~

**400:** Media type is valid, but JSON syntax is broken:

~~~http
POST /api/books HTTP/1.1
Content-Type: application/json
Accept: application/json

{"title":
~~~

These are illustrative scenarios; actual error mapping depends on exception handlers, converters, and application configuration. Do not check only the status if the contract also specifies an error code, response body, or specific headers.

## 6. Creating MockMvc Tests to Verify `Content-Type` and `Accept`

### 6.1. Project Setup

The example uses Spring Boot 3.x, Spring MVC, Java 17+, and JUnit 5. Gradle dependencies:

~~~groovy
dependencies {
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.restdocs:spring-restdocs-mockmvc'
}
~~~

Assume the `POST /api/books` endpoint accepts JSON and returns `201 Created` with a JSON body. The project needs the corresponding controller/service and test data; Spring REST Docs **does not create endpoints or fixtures**.

### 6.2. Testing JSON Request, JSON Response

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.restdocs.AutoConfigureRestDocs;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.HttpHeaders;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.restdocs.headers.HeaderDocumentation.headerWithName;
import static org.springframework.restdocs.headers.HeaderDocumentation.requestHeaders;
import static org.springframework.restdocs.headers.HeaderDocumentation.responseHeaders;
import static org.springframework.restdocs.mockmvc.MockMvcRestDocumentation.document;
import static org.springframework.restdocs.payload.PayloadDocumentation.fieldWithPath;
import static org.springframework.restdocs.payload.PayloadDocumentation.requestFields;
import static org.springframework.restdocs.payload.PayloadDocumentation.responseFields;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
@AutoConfigureRestDocs(outputDir = "build/generated-snippets")
class BookMediaTypeDocumentationTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void documentCreateBookJson() throws Exception {
        mockMvc.perform(post("/api/books")
                .contentType(MediaType.APPLICATION_JSON)
                .accept(MediaType.APPLICATION_JSON)
                .content("""
                    {"title":"Spring in Action","price":199000}
                    """))
            .andExpect(status().isCreated())
            .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
            .andExpect(header().exists(HttpHeaders.LOCATION))
            .andExpect(jsonPath("$.title").value("Spring in Action"))
            .andDo(document("books-create-json",
                requestHeaders(
                    headerWithName(HttpHeaders.CONTENT_TYPE)
                        .description("Media type of the JSON request body"),
                    headerWithName(HttpHeaders.ACCEPT)
                        .description("Response media type accepted by the client")
                ),
                requestFields(
                    fieldWithPath("title").description("Book title"),
                    fieldWithPath("price").description("Book price")
                ),
                responseHeaders(
                    headerWithName(HttpHeaders.CONTENT_TYPE)
                        .description("Media type of the response"),
                    headerWithName(HttpHeaders.LOCATION)
                        .description("URI of the newly created resource")
                ),
                responseFields(
                    fieldWithPath("id").description("New book ID"),
                    fieldWithPath("title").description("Book title"),
                    fieldWithPath("price").description("Book price")
                )
            ));
    }
}
~~~

Breakdown:

1. `contentType(MediaType.APPLICATION_JSON)` sends a JSON request body and sets the corresponding `Content-Type` header.
2. `accept(MediaType.APPLICATION_JSON)` requests a JSON response via the `Accept` header.
3. `andExpect(status().isCreated())` verifies status `201`.
4. `content().contentTypeCompatibleWith(...)` verifies the response media type is JSON-compatible.
5. `requestHeaders(...)` and `responseHeaders(...)` generate header description tables in both directions.
6. `requestFields(...)` and `responseFields(...)` describe request/response payloads. In strict mode, descriptors also verify that fields match the payload.
7. `andDo(document(...))` comes after assertions; if an assertion fails, the document step at the end does not run.

The example assumes the server returns `Location` and a response with three fields: `id`, `title`, and `price`. If your real API returns a different schema, update assertions/descriptors to match the real contract rather than copying the example as if Spring Boot created those fields automatically.

### 6.3. Adding a `415 Unsupported Media Type` Test

Suppose `POST /api/books` declares `consumes = application/json` and rejects XML:

~~~java
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;

@Test
void documentUnsupportedRequestMediaType() throws Exception {
    mockMvc.perform(post("/api/books")
            .contentType(MediaType.APPLICATION_XML)
            .accept(MediaType.APPLICATION_JSON)
            .content("<book><title>Spring</title></book>"))
        .andExpect(status().isUnsupportedMediaType())
        .andDo(document("books-create-unsupported-media-type"));
}
~~~

This test depends on specific endpoint configuration. If the application has an XML converter/mapping or an exception handler that transforms the status, adjust expectations to match actual behavior. This operation's response snippet helps readers see how the server responds when a client sends an unsupported media type.

### 6.4. Adding a `406 Not Acceptable` Test

Suppose `GET /api/books/42` only declares `produces = application/json`, with no XML representation:

~~~java
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;

@Test
void documentNotAcceptableResponseType() throws Exception {
    mockMvc.perform(get("/api/books/42")
            .accept(MediaType.APPLICATION_XML))
        .andExpect(status().isNotAcceptable())
        .andDo(document("books-get-not-acceptable"));
}
~~~

For this test to behave as shown, ensure the application has no other converter/handler capable of producing XML and no exception handler changing the status. Do not add a `406` test just for completeness; only document branches the API actually supports or defines.

When recording an operation with `document("books-create-json")`, common default snippets include:

~~~text
build/generated-snippets/

    ├── httpie-request.adoc
    ├── http-request.adoc
    ├── http-response.adoc
    ├── request-body.adoc
    └── response-body.adoc
~~~

Because the test also declared descriptors, tabular snippets can be generated as well:

~~~text
    ├── request-headers.adoc
    ├── response-headers.adoc
    ├── request-fields.adoc
    └── response-fields.adoc
~~~

The actual file list depends on snippet configuration and the API descriptors used. Meaning:

| Snippet | Used to answer |
| --- | --- |
| `http-request.adoc` | What method, URI, headers, and body are in the request? |
| `http-response.adoc` | What are the actual response status, headers, and body? |
| `request-headers.adoc` | How are `Content-Type`/`Accept` explained? |
| `response-headers.adoc` | What `Content-Type` did the server return, and is `Location` present? |
| `request-fields.adoc` | What JSON fields are sent in the request? |
| `response-fields.adoc` | What JSON fields are returned in the response? |
| `curl-request.adoc`/`httpie-request.adoc` | What CLI tool command can replay the request? |

**There are no default snippets named "content-types.adoc" or "accept.adoc".** Both headers appear in `http-request`/`http-response` and in the `request-headers`/`response-headers` tables if the test declares descriptors.

### 7.1. Request Snippet Example

Illustrative `http-request.adoc` content:

~~~http
POST /api/books HTTP/1.1
Content-Type: application/json
Accept: application/json

{"title":"Spring in Action","price":199000}
~~~

An equivalent command can appear in the CLI snippet:

~~~bash
curl 'https://api.example.com/api/books' -i -X POST \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  -d '{"title":"Spring in Action","price":199000}'
~~~

This is only a **formatting example**. The URL host, header order, body formatting, and CLI flags depend on configuration and templates. Inspect the actual file generated after running the test for exact details.

### 7.2. Response Snippet Example

~~~http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/books/102

{"id":102,"title":"Spring in Action","price":199000}
~~~

In another case, a client requesting XML from a server that does not support it may receive `406`. Do not assume every response snippet has a JSON body; the body depends on the status and endpoint contract.

## 8. `Content-Type` in Multipart and Form Requests

### 8.1. `application/x-www-form-urlencoded`

When sending simple form data:

~~~http
POST /api/login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=lan&remember=true
~~~

This is an encoded form body. Do not use `requestFields(...)` as if the body were JSON; in Spring REST Docs, use `formParameters(...)` to document form fields when appropriate.

### 8.2. `multipart/form-data`

File uploads typically use multipart:

~~~http
POST /api/files HTTP/1.1
Content-Type: multipart/form-data; boundary=----ExampleBoundary

------ExampleBoundary
Content-Disposition: form-data; name="description"

cover of the book
------ExampleBoundary
Content-Disposition: form-data; name="file"; filename="cover.png"
Content-Type: image/png

(binary bytes)
------ExampleBoundary--
~~~

The boundary is part of the multipart body structure; the HTTP client/browser generates an appropriate value and attaches it to `Content-Type`. **Do not manually set `Content-Type: multipart/form-data` without a boundary** when constructing requests by hand; let the HTTP client generate the proper boundary. With MockMvc/WebTestClient, use the provided multipart APIs and test parts per contract.

### 8.3. Binary Data and Content Coding

Do not equate media type with content encoding. `Content-Type` describes the representation format; `Content-Encoding` describes the encoding/compression mechanism applied to the representation, such as gzip. For file downloads, distinguish `application/octet-stream`, specific media types like `image/png`, and any content coding in use.

## 9. Descriptors and Header Verification Rules

### 9.1. `requestHeaders(...)`

Example:

~~~java
requestHeaders(
    headerWithName(HttpHeaders.CONTENT_TYPE)
        .description("Media type of the request body"),
    headerWithName(HttpHeaders.ACCEPT)
        .description("Response media type accepted by the client")
)
~~~

Under standard behavior, **non-optional** header descriptors must be present in the request; other undocumented headers do not automatically fail snippet generation. Mark `.optional()` when a header may genuinely be absent.

### 9.2. `responseHeaders(...)`

Example:

~~~java
responseHeaders(
    headerWithName(HttpHeaders.CONTENT_TYPE)
        .description("Media type of the response body"),
    headerWithName(HttpHeaders.LOCATION)
        .description("URI of the new resource")
        .optional()
)
~~~

`Location` should only be optional if the contract/test case being documented allows it to be absent. If the contract requires `Location` on `201 Created`, leave the descriptor required and add an assertion checking its value.

### 9.3. Optional and Relaxed

- `.optional()` allows a header to be absent in a specific response/request.
- `relaxedRequestHeaders(...)` or `relaxedResponseHeaders(...)` can omit undocumented headers from the table; you must still document and assert headers required by documentation.
- Header descriptors document presence/meaning, not the exact header value. Use `header().string(...)`, `expectHeader()`, or equivalent assertions to verify values.

Similarly, payload descriptors cannot prove business data validity. Use dedicated assertions for status, header values, body content, and domain constraints.

## 10. WebTestClient and REST Assured

Spring REST Docs has integration modules for multiple client types. Syntax differs, yet the principle remains configuring `Content-Type`/`Accept` on the request, verifying the response, and recording the operation.

### 10.1. WebTestClient

Example with a client already configured with REST Docs:

~~~java
import static org.springframework.restdocs.webtestclient.WebTestClientRestDocumentation.document;

webTestClient.post()
    .uri("/api/books")
    .contentType(MediaType.APPLICATION_JSON)
    .accept(MediaType.APPLICATION_JSON)
    .bodyValue("""
        {"title":"Spring in Action","price":199000}
        """)
    .exchange()
    .expectStatus().isCreated()
    .expectHeader().contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
    .expectBody()
    .jsonPath("$.title").isEqualTo("Spring in Action")
    .consumeWith(document("books-create-webtestclient"));
~~~

`contentType(...)` sets the outgoing body format; `accept(...)` specifies the desired response format. `expectHeader().contentTypeCompatibleWith(...)` verifies the response media type. The integration module is `spring-restdocs-webtestclient`, requiring proper client/documentation context configuration for your application type.

### 10.2. REST Assured

REST Assured provides methods to set media types:

~~~java
import static io.restassured.RestAssured.given;
import static org.springframework.restdocs.restassured.RestAssuredRestDocumentation.document;

given(spec)
    .filter(document("books-create-restassured"))
    .contentType("application/json")
    .accept("application/json")
    .body("""
        {"title":"Spring in Action","price":199000}
        """)
.when()
    .post("/api/books")
.then()
    .statusCode(201)
    .contentType("application/json");
~~~

`contentType(...)` and `accept(...)` express both request and response directions. The integration module is `spring-restdocs-restassured`; `spec` must be set up for the test server and REST Docs. The filter may record the operation when the request runs before `then()` assertions; only publish docs when all tests PASS.

## 12. Common Pitfalls and How to Fix Them

| Symptom | Cause | Fix |
| --- | --- | --- |
| `415 Unsupported Media Type` | Request `Content-Type` is not supported by the endpoint/converter | Check `consumes` and the media type/body sent. |
| `406 Not Acceptable` | `Accept` value does not match any representation the API provides | Check `produces`, converters, and `Accept` header value. |
| `400 Bad Request` on JSON request | Malformed body syntax or deserialization/validation failure | Verify payload, `Content-Type`, and error handling. |
| Request sends JSON but server misreads it | Missing/wrong `Content-Type` or mismatched body | Set `contentType(APPLICATION_JSON)` and send valid JSON. |
| Server returns XML despite client wanting JSON | Ambiguous `Accept`, endpoint lacks JSON support, or negotiation configured differently | Assert response media type and check mapping/converters. |
| Test checks `Accept` without verifying response | Confused client preference with actual response representation | Assert response `Content-Type`. |
| `request-headers.adoc` does not appear | `requestHeaders(...)` not declared | Add descriptors inside `document(...)`. |
| `response-headers.adoc` does not appear | `responseHeaders(...)` not declared | Add descriptors for headers to document. |
| Test fails due to missing response field | Payload has undocumented field or mismatched descriptor | Update descriptors; use relaxed mode only intentionally. |
| Multipart request has boundary error | Manually set `Content-Type` without generating a valid boundary | Let the HTTP client's multipart builder generate header/boundary. |
| Flaky test due to charset/header string | Header string comparison is too rigid when media type has parameters | Use media-type-compatible assertions when allowed by the contract. |
| CI still publishes stale snippets | Docs build does not depend on tests or leftover output exists | Bind tasks and artifacts to the current test run. |
