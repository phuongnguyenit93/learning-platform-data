# Controlling Output Directories and Documentation Artifacts

## 1. Objectives and Context

Spring REST Docs generates snippets from HTTP tests into an output directory. Build tools then assemble the snippets into Asciidoctor/Markdown, render HTML, and may package these files as CI artifacts or publish them to a website. Throughout this lifecycle, documentation can contain sensitive data if test fixtures, requests/responses, or redaction steps are not configured properly.

Security does not stop at masking tokens in snippets. You must control **where output is written, who can read it, how long artifacts are retained, how they are shared, and how they are deleted**. A file not committed to Git can still be uploaded to a CI artifact store, cache, log, or internal website with broad access permissions.

This lesson belongs to the **Security** chapter of the **SPRING_REST_DOCS** module. The module creates verifiable REST API documentation from HTTP tests using MockMvc, WebTestClient, or REST Assured; generates snippets for requests, responses, payloads, parameters, and headers; compiles Asciidoctor/Markdown; and integrates with build/CI pipelines.

After this lesson, you will be able to:

- Choose dedicated output directories for generated snippets and rendered docs.
- Distinguish source docs, generated output, caches, logs, and CI artifacts.
- Configure Git ignore rules and intentional commit policies.
- Restrict access permissions, retention, and sharing of artifacts.
- Separate internal documentation from public documentation.
- Safely clean outputs/caches/artifacts and handle incidents when sensitive data is detected.
- Design CI to publish only after tests, redaction, scanning, and review are complete.

## 2. Identifying Output Types

A REST Docs pipeline can produce several types of files in multiple locations:

| Type | Example | Content |
| --- | --- | --- |
| Source documentation | src/docs/asciidoc/index.adoc | Content authored by the documentation team. |
| Generated snippets | build/generated-snippets/ | HTTP requests/responses, bodies, fields, links. |
| Assembled documentation | build/docs-source/ or build/api-markdown/ | Pages with snippets assembled. |
| Rendered site | build/docs/asciidoc/html5/ or site/ | HTML, CSS, JS, images. |
| Test reports | build/reports/tests/ | Test results, failure details, possibly including request data. |
| Logs | build/logs/ or CI console | Diagnostics, sometimes containing headers/bodies. |
| Build cache | Gradle/Maven/CI cache | Intermediate outputs and task state. |
| CI artifacts | Pipeline artifact store | Files uploaded for review/download. |

Directory names are only examples. Check your project's Gradle/Maven configuration, docs plugins, and CI workflows to see where outputs actually reside.

Sensitive data can flow through multiple locations. Scanning only the generated-snippets directory is not sufficient if assembled HTML or test reports still contain the original values.

## 3. Organizing Output in the Build Directory

Place generated outputs under the project's build directory to separate authored sources from automatically generated artifacts.

Example:

~~~text
project/
├── src/
│   ├── test/
│   └── docs/
│       └── asciidoc/
│           └── index.adoc
└── build/
    ├── generated-snippets/
    ├── docs-source/
    ├── docs/
    ├── reports/
    └── tmp/
~~~

Benefits:

- Outputs can be regenerated from tests and source.
- The clean task can remove outputs according to the build lifecycle.
- Automatically generated files are not mixed with reviewed source files.
- CI can upload only the selected directory.
- Different permissions and retention rules can be applied to internal vs. public outputs.

Do not write generated snippets into the source folder just for convenient includes. If snippets need to be shared for review, create an intentional artifact and inspect its contents before sharing.

### 3.1. Separating Outputs by Purpose

You can separate:

- generated-snippets: newly generated REST Docs data.
- docs-source: assembled source pages.
- docs-public: site that has been verified and approved for public release.
- docs-internal: internal documentation with restricted access.
- reports: test, lint, link check, and security scan results.

Not every project needs all of these folders. What matters is that each output type has a clear owner, purpose, and access policy.

## 4. Managing Git: Ignoring Outputs and Intentional Commits

Generated snippets are typically regenerated by tests, so build outputs should not automatically become the source of truth. Ignore rules may include:

~~~gitignore
# Build outputs
/build/
/target/

# Generated REST Docs snippets
/generated-snippets/

# Local documentation preview
/site-preview/
~~~

The patterns above are examples; inspect the existing repository before adding them so you do not accidentally ignore outputs that the project intentionally version-controls.

Do not add a broad ignore rule if the repository intentionally commits a docs output directory. If you need to store a snapshot of public docs in Git, store only the reviewed directory and avoid unintentionally committing raw snippets or test reports.

### 4.1. When Should Generated Snippets Be Committed?

Normally, you do not need to commit snippets if:

- Tests regenerate them reliably.
- Build/CI can generate docs from source.
- Reviewers can view the rendered artifact of a pull request.

You may commit them when the organization requires snapshots of generated outputs or when documentation is published independently of source/builds. In that case:

- Commit only redacted and reviewed files.
- Maintain a process to update snapshots from a clean build.
- Do not commit test reports, caches, or temporary files.
- Scan for secrets before staging/committing.
- Review generated diffs as part of the API contract.

Do not treat committed generated files as proof that current tests pass. CI must still regenerate snippets.

## 5. Filesystem Permissions

Documentation outputs may contain internal endpoints, sample data, error details, or identifiers. Restrict access permissions according to the principle of least privilege:

- Developers only need read/write permissions for outputs in their own workspace.
- CI jobs write only to the required workspace and artifact locations.
- Publish jobs read only artifacts that have passed verification.
- Unrelated users do not need access to internal artifacts.
- Service accounts should not share credentials with personal accounts.
- Temporary directories should not have broader permissions than necessary.

Do not place generated docs containing internal data into a default cloud/public sync folder unless approved under organizational policy.

### 5.1. Read Permission and Publish Permission Are Separate

A developer may be allowed to view internal artifacts without being allowed to publish documentation to a public website. Separate permissions:

| Action | Required Permission |
| --- | --- |
| Generate snippets locally | Workspace write. |
| View internal CI artifact | Artifact read. |
| Delete artifact | Artifact administration or equivalent permission. |
| Publish internal docs | Permission to deploy to the internal site. |
| Publish public docs | Separate release/publication permission. |

Do not use a single admin-privileged credential to run all build/test/publish steps if service accounts can be separated.

## 6. Protecting CI Artifacts

CI artifacts are convenient for review but are often stored in a system separate from the Git repository. You must control:

- Which artifacts are uploaded.
- Who has download permissions.
- Whether artifacts can be shared via public links.
- Retention duration.
- Whether they contain source maps, logs, test reports, or raw snippets.
- Whether artifacts enter a cache shared across branches or projects.

A preview artifact can expose internal documentation even if the production website is private. Check the visibility and download permissions of the artifact store rather than inferring them from repository permissions.

### 6.1. Choosing Which Artifacts to Upload

Typically, upload only:

- Redacted and scanned rendered docs.
- Preview artifacts for review.
- Validation reports containing no raw secrets.

Consider not uploading:

- Raw HTTP traces.
- Full test logs containing headers/bodies.
- Unfiltered generated snippets.
- Environment dumps.
- Build caches not needed for review.

If raw snippets must be uploaded for debugging, restrict permissions, use short retention, and do not use production data.

### 6.2. Retention

Set retention according to purpose:

| Artifact | Policy-Suggested Retention |
| --- | --- |
| PR preview | Short, only long enough for review. |
| Test reports | According to the organization's failure investigation window. |
| Release docs artifact | According to release/audit policy. |
| Debug artifact with internal data | As short as possible, restricted readers. |
| Public documentation | According to the lifecycle of published content. |

These are reference categories, not fixed durations. Apply your organization's retention policy and relevant legal/contractual requirements.

## 7. Separating Internal and Public Documentation

Not every endpoint is intended for external users. Documentation may cover:

- Public API contracts.
- Internal service-to-service endpoints.
- Admin/operations endpoints.
- Sandbox/test-only endpoints.
- Partner-only APIs.
- Deprecated or unreleased operations.

Separate outputs or publication targets so that a single publish step does not accidentally expose all internal docs on the public site.

Example structure:

~~~text
build/
├── docs-internal/
│   └── index.html
└── docs-public/
    └── index.html
~~~

Classification must be based on policy and project-managed metadata, not on whether an endpoint "looks internal." When it is unclear whether an operation can be public, exclude it from the public bundle until the owner confirms.

### 7.1. Public Documentation Allowlist

A safe approach is to define a list of pages/operations permitted for public publication. The build constructs the public bundle from the allowlist instead of copying the entire generated output.

Verify:

- Every public operation has an owner.
- No admin/internal endpoints are included.
- No internal hostnames, private IPs, or environment names are included.
- No test-only routes or credentials are included.
- Links do not point to internal docs.
- Only scanned public artifacts are deployed.

## 8. Cleaning Outputs and Caches

Clean builds help prevent stale snippets from being included by mistake. However, deleting local outputs does not remove uploaded artifacts or Git history.

The cleanup process should:

1. Stop any task/process currently writing outputs.
2. Identify the exact generated directories owned by the project.
3. Use the clean task or cleanup mechanism managed by the build tool.
4. Do not delete source docs, test fixtures, or user-authored files.
5. Re-run the build to regenerate snippets.
6. Inspect the artifact directory after the build.

Gradle example:

~~~bash
./gradlew clean test asciidoctor
~~~

Maven example:

~~~bash
./mvnw clean verify
~~~

Task/goal names depend on the project configuration. The commands above only illustrate the clean lifecycle and docs build; invoke the exact tasks/goals that generate snippets and render docs.

### 8.1. Caches and Stale Outputs

Build caches can store task outputs for reuse. If task inputs/outputs are misconfigured, the build may reuse stale artifacts. Declare inputs and outputs accurately for snippet-generation and doc-assembly tasks.

Do not pass secrets in cache keys, command lines, or task arguments. If an artifact with sensitive data has been cached, handle the cache according to the capabilities and policies of the CI/build cache system.

## 9. Secure Publication Workflow

A publication pipeline should enforce sequential verification gates:

~~~mermaid
flowchart TD
    A["Run HTTP tests with synthetic data"] --> B["Generate REST Docs snippets"]
    B --> C["Apply redaction"]
    C --> D["Assemble and render docs"]
    D --> E["Secret scan and content classification"]
    E --> F{"Approved for target audience?"}
    F -->|No| X["Block publication"]
    F -->|Yes| G["Review artifact and links"]
    G --> H{"Checks pass?"}
    H -->|No| X
    H -->|Yes| I["Publish to approved target"]
~~~

Recommended sequence:

1. Tests use synthetic data.
2. REST Docs generates snippets.
3. Preprocessors mask sensitive headers/bodies/links.
4. Assemble source pages and render.
5. Secret scan across snippets, assembled docs, and HTML.
6. Verify public/internal classification and allowlist.
7. Review artifacts, links, and content.
8. Publish using a least-privilege service account.
9. Record version, commit, and destination for traceability.

Do not publish merely because the build render task succeeded. A passing render does not prove the content is authorized for public release.

## 10. Handling Sensitive Data Detected in Artifacts

If a token, password, session ID, or PII is found in generated output:

1. Stop publishing or remove the artifact from shared locations if already released.
2. Determine whether the value is an active credential.
3. If it is a real credential, revoke/rotate it according to the organization's incident process.
4. Identify the scope: snippets, assembled pages, HTML, logs, CI artifacts, caches, and Git history.
5. Restrict access during investigation.
6. Delete or expire artifacts using each system's mechanism.
7. If the secret was committed, handle Git history per policy in coordination with the repository owner.
8. Fix fixtures/preprocessors/scanners to prevent recurrence.
9. Regenerate docs from a clean build and verify no sentinels remain.

Do not simply delete the local file and consider the incident resolved. Artifacts may persist in caches, mirrors, downloads, or copies already accessed by users.

## 11. Pre-Upload Output Verification

Before uploading an artifact, verify:

- Only the authorized output directory is selected.
- No unnecessary raw logs or test reports are included.
- Redaction ran on requests/responses.
- No secret sentinels exist in generated snippets.
- No internal hostnames/IPs exist in the public bundle.
- No temporary files, environment dumps, or credentials are present.
- All required links/assets have been rendered.
- Artifact name/version is clearly tied to the commit/build.
- Visibility and retention comply with policy.

A simple manifest can record the artifact name, commit SHA, build timestamp, audience (internal/public), and passed validation steps. Do not record secrets or tokens in the manifest.

## 12. Conceptual CI Configuration Example

A pipeline can separate build/test, scan, and publish jobs:

~~~yaml
jobs:
  docs-test:
    steps:
      - run: ./gradlew clean test asciidoctor
      - run: ./scripts/scan-docs-output.sh build/generated-snippets build/docs

  docs-review:
    needs: docs-test
    steps:
      - upload-artifact:
          name: docs-preview
          path: build/docs
          retention-days: 3

  docs-publish:
    needs: docs-review
    environment: approved-docs
    steps:
      - run: ./scripts/verify-public-docs.sh build/docs-public
      - run: ./scripts/publish-docs.sh build/docs-public
~~~

This is pseudoconfiguration illustrating dependencies and trust boundaries; upload artifact syntax, retention, and environment protection depend on your CI provider. In practice, never allow the publish job to consume an unscanned/unreviewed artifact or a path mixing both internal and public docs.

### 12.1. Separating Permissions by Job

- The test job generates snippets and needs no publish permission.
- The scan job reads outputs and needs no permission to modify source or deploy.
- The review job provides internal artifacts with short retention.
- The publish job receives only the verified public bundle and uses dedicated deploy credentials.

Job separation limits blast radius if a test step or dependency is compromised.

## 13. Common Pitfalls

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Snippets committed unintentionally | Missing ignore rule or staged entire build | Ignore outputs properly, review staged diff. |
| PR artifact contains internal endpoint | Uploaded entire site instead of public bundle | Separate internal/public output and use an allowlist. |
| External users can download preview | Artifact store has broad visibility | Restrict download permissions and retention. |
| Token remains in HTML despite clean snippets | Assembly/render used stale output or another log | Clean build and scan final output. |
| Cleaned locally but artifact still exists | CI artifacts/caches are independent of workspace | Expire/delete via the artifact provider. |
| Build uses stale snippets | Incorrect task inputs/outputs or dependencies | Declare task graph and clean lifecycle. |
| Public docs contain internal hostname | Did not classify content before publishing | Scan hostnames and review allowlist. |
| Artifacts retained too long | No retention configured | Apply policy by artifact type. |
| Publish job has overly broad permissions | Shared credentials with build job | Separate service accounts and apply least privilege. |
| Deleted file but secret remains in Git | File was committed in history | Rotate secret and clean history per policy. |

## 14. Practice Exercise

Set up a documentation pipeline for an API with public endpoints and internal admin endpoints.

Steps to perform:

1. Configure REST Docs output under a dedicated build directory.
2. Identify source docs, generated snippets, assembled pages, rendered site, reports, and logs.
3. Add Git ignore rules for generated outputs appropriate for the repository.
4. Build the public bundle from an allowlist; keep admin/internal docs in a separate output.
5. Run tests with synthetic data and redaction preprocessors.
6. Scan snippets, assembled Markdown/Asciidoctor, and rendered HTML.
7. Upload an internal preview artifact with appropriate permissions and retention.
8. Separate test/scan/review/publish jobs and corresponding service accounts.
9. Run a clean build to ensure no stale outputs are used.
10. Simulate detecting a secret in an artifact; practice blocking publication and identifying where to expire/delete it.
11. Write a manifest including commit, audience, build ID, and validation status, containing no secrets.

**Completion criteria:** outputs reside in intentional directories; Git does not accidentally commit generated files; CI artifacts have clear access/retention rules; public/internal bundles are separated; secret scanning runs before publishing; clean builds regenerate docs; and a procedure exists to handle artifacts when sensitive data is detected.
