# Default management interface and public exposure in Spring JMX

## 1. Why does the management interface need to be controlled?

When exporting a Spring bean via JMX, the important question is not only **whether the MBean is registered or not**, but also **what clients can see and invoke**. A Java class can contain many public methods serving business logic or infrastructure. If the default management interface accidentally exposes all of those methods, operators or anyone with JMX connection privileges may see behavior that the application did not intend to treat as a management operation.

Spring Framework provides \`MBeanExporter\` to register beans with an \`MBeanServer\`. Depending on the configuration, the exporter can use a standard JMX interface or build a management model for a POJO via an \`MBeanInfoAssembler\`. **The rule for which public methods are exposed depends on how the exporter builds MBeanInfo**, and cannot be inferred solely from a method being \`public\`.

This article focuses on:

- Management interfaces following the **Standard MBean** and **MXBean** conventions.
- Management interfaces auto-generated by Spring from a bean via the default assembler.
- The difference between Java \`public\` and “exported via JMX”.
- How to limit the surface using interfaces, annotations, or selective assemblers.
- How to inspect the actual surface via \`MBeanServer.getMBeanInfo()\`.
- The impact of proxies, access permissions, and API changes across versions.

## 2. Two common meanings of “management interface”

In documentation and projects, the phrase “management interface” can refer to two mechanisms:

1. **Standard JMX management interface**: a Java interface such as \`CacheManagerMBean\` that a class implements according to Standard MBean rules, or an interface \`CacheManagerMXBean\` following the MXBean convention. That interface defines which attributes and operations can be seen by JMX.
2. **Management surface generated by the Spring exporter**: the set of attributes/operations described by \`MBeanInfo\` after the exporter applies the assembler, annotations, and method include/exclude policies.

Standard MBean example:

\`\`\`java
public interface CacheAdminMBean {
    int getEntryCount();
    void clearExpired();
}

public class CacheAdmin implements CacheAdminMBean {
    @Override
    public int getEntryCount() {
        return 42;
    }

    @Override
    public void clearExpired() {
        // Controlled management operation.
    }

    public void deleteAllCustomerData() {
        // Public Java method, but not in CacheAdminMBean.
    }
}
\`\`\`

When registered as a Standard MBean, \`getEntryCount\` and \`clearExpired\` belong to the management interface. \`deleteAllCustomerData\` is public in Java but does not automatically appear just because it is public.

Conversely, if Spring is configured to automatically expose public methods through a broad assembler, \`deleteAllCustomerData\` can become an unintended JMX operation. Therefore, you must identify the exact **export path being used**.

## 3. How Spring MBeanExporter determines the public surface

\`MBeanExporter\` is responsible for selecting beans, assigning \`ObjectName\`, building an MBean adapter if needed, and registering with \`MBeanServer\`.

For a Java object that is already a valid MBean (Standard MBean, MXBean, or \`DynamicMBean\`), the exporter can use the management information defined by the standard JMX mechanism. For plain POJOs, Spring can create a \`ModelMBean\` using assemblers such as:

- \`SimpleReflectiveMBeanInfoAssembler\`: discovers public properties and public methods via reflection, and therefore can create a broad surface.
- \`MethodNameBasedMBeanInfoAssembler\`: selects methods by configured names.
- \`MethodExclusionMBeanInfoAssembler\`: allows excluding specific methods from the exposed set.
- \`InterfaceBasedMBeanInfoAssembler\`: relies on one or more specified interfaces.
- \`MetadataMBeanInfoAssembler\`: uses metadata such as \`@ManagedAttribute\` and \`@ManagedOperation\`.

Exact names and behavior should be checked against the Spring version in use. In common default configurations for POJOs, if no selective assembler is provided, relying on reflection can make the management surface broader than expected.

**Key takeaway:** \`public\` is a Java accessibility modifier. It is neither a security policy nor a declaration that a method is suitable for JMX. The actual surface must be verified from MBeanInfo.

## 4. Example of risks when exporting a POJO too broadly

Suppose a service has several public methods:

\`\`\`java
public class ReportService {
    public int getActiveJobs() {
        return 8;
    }

    public void retryFailedJobs() {
        // Operational command that requires an authorization policy.
    }

    public void generateCustomerReport(String customerId) {
        // Business use case.
    }

    public void purgeHistoricalRecords() {
        // High-impact operation.
    }
}
\`\`\`

If an exporter creates a ModelMBean and exposes all public methods, JMX clients can see both \`generateCustomerReport\` and \`purgeHistoricalRecords\`. This creates risks:

- The management API was not designed with an authorization context equivalent to HTTP.
- Methods may lack validation, auditing, or guards for calls coming from a JMX thread.
- An operation may be long-running and consume application resources.
- Changing the public Java API accidentally changes the management API as well.
- Management tools or automation might invoke a sensitive method by mistake.

**Do not use export-all for large business services** without a clear reason and strict controls. A safer option is to create an adapter or explicitly select the specific methods to be managed.

## 5. Standard MBean interface: an explicit allowlist

Example of separating the management interface from the service:

\`\`\`java
package com.example.reports.jmx;

public interface ReportMonitorMBean {
    int getActiveJobs();
    long getCompletedTotal();
    void requestRetry();
}
\`\`\`

\`\`\`java
package com.example.reports.jmx;

public final class ReportMonitor implements ReportMonitorMBean {
    private final ReportManagement management;

    public ReportMonitor(ReportManagement management) {
        this.management = management;
    }

    @Override
    public int getActiveJobs() {
        return management.snapshot().activeJobs();
    }

    @Override
    public long getCompletedTotal() {
        return management.snapshot().completedTotal();
    }

    @Override
    public void requestRetry() {
        management.requestRetry();
    }
}
\`\`\`

\`ReportManagement\` is an application interface containing JMX-independent management queries and commands:

\`\`\`java
public interface ReportManagement {
    ReportSnapshot snapshot();
    void requestRetry();
}

public record ReportSnapshot(
    int activeJobs,
    long completedTotal
) {}
\`\`\`

In a Standard MBean, the \`ReportMonitorMBean\` interface itself is the JMX contract. Other public methods on \`ReportMonitor\` that are not part of this interface will not automatically become JMX operations.

When registering directly:

\`\`\`java
import java.lang.management.ManagementFactory;
import javax.management.MBeanServer;
import javax.management.ObjectName;

MBeanServer server = ManagementFactory.getPlatformMBeanServer();

ObjectName name = new ObjectName(
    "com.example.reports:type=Monitor,name=Primary"
);

server.registerMBean(new ReportMonitor(management), name);
\`\`\`

The \`management\` variable is a dependency already provided by the application. In Spring, you can also inject it into an adapter bean and let the exporter manage registration/lifecycle.

## 6. Spring annotations: intentionally selecting attributes and operations

Another approach is to build an adapter with annotations:

\`\`\`java
import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedOperation;
import org.springframework.jmx.export.annotation.ManagedResource;
import org.springframework.stereotype.Component;

@Component
@ManagedResource(
    objectName = "com.example.reports:type=Monitor,name=Primary",
    description = "Safe report management API"
)
public final class ReportJmxAdapter {
    private final ReportManagement management;

    public ReportJmxAdapter(ReportManagement management) {
        this.management = management;
    }

    @ManagedAttribute(description = "Currently active reports")
    public int getActiveJobs() {
        return management.snapshot().activeJobs();
    }

    @ManagedAttribute(description = "Completed reports since startup")
    public long getCompletedTotal() {
        return management.snapshot().completedTotal();
    }

    @ManagedOperation(description = "Request retry of failed reports")
    public void retryFailed() {
        management.requestRetry();
    }

    public void internalHelper() {
        // Public method, but not marked for management.
    }
}
\`\`\`

If the exporter uses \`MetadataMBeanInfoAssembler\` with a suitable metadata source, only getters/operations managed according to annotations and metadata rules become the JMX surface. \`@ManagedResource\` defines a managed bean; it does not automatically turn every public method into an operation.

Note that \`@ManagedOperation\` also does not automatically create authentication or authorization. Impactful management commands still require controls at the connector and application layers.

## 7. Configuring an exporter to use metadata annotations

With pure Java Spring Framework configuration:

\`\`\`java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jmx.export.MBeanExporter;
import org.springframework.jmx.export.annotation.AnnotationJmxAttributeSource;
import org.springframework.jmx.export.assembler.MetadataMBeanInfoAssembler;
import org.springframework.jmx.export.naming.MetadataNamingStrategy;

@Configuration
public class JmxConfig {
    @Bean
    AnnotationJmxAttributeSource jmxAttributeSource() {
        return new AnnotationJmxAttributeSource();
    }

    @Bean
    MBeanExporter mbeanExporter(
            AnnotationJmxAttributeSource source) {
        var assembler = new MetadataMBeanInfoAssembler();
        assembler.setAttributeSource(source);

        var naming = new MetadataNamingStrategy();
        naming.setAttributeSource(source);

        MBeanExporter exporter = new MBeanExporter();
        exporter.setAssembler(assembler);
        exporter.setNamingStrategy(naming);
        exporter.setAutodetect(true);
        return exporter;
    }
}
\`\`\`

In Spring Boot projects, JMX auto-configuration may create an exporter when \`spring.jmx.enabled=true\` is enabled. Check the actual exporter and Spring/Boot version before adding a manual exporter, to avoid duplicate \`ObjectName\`s or registering the same bean multiple times.

\`AnnotationJmxAttributeSource\` reads metadata; \`MetadataMBeanInfoAssembler\` selects attributes/operations; \`MetadataNamingStrategy\` resolves the MBean name. They serve different responsibilities, so an annotation appearing on a class does not guarantee that the entire configuration is already active.

## 8. InterfaceBasedMBeanInfoAssembler: selecting methods by interface

When you do not want to place JMX annotations on a service, you can configure a Spring assembler based on an interface. Example:

\`\`\`java
public interface ReportManagementView {
    int getActiveJobs();
    long getCompletedTotal();
}
\`\`\`

The implementation has many other public methods, but the observation interface only has two getters. A sample configuration:

\`\`\`java
import org.springframework.jmx.export.MBeanExporter;
import org.springframework.jmx.export.assembler.InterfaceBasedMBeanInfoAssembler;

InterfaceBasedMBeanInfoAssembler assembler =
    new InterfaceBasedMBeanInfoAssembler();

assembler.setManagedInterfaces(
    new Class<?>[] { ReportManagementView.class }
);

MBeanExporter exporter = new MBeanExporter();
exporter.setAssembler(assembler);
exporter.setBeans(
    java.util.Map.of(
        "com.example.reports:type=View,name=Primary",
        reportService
    )
);
\`\`\`

The snippet above illustrates a standalone exporter; it must be placed in a valid Spring configuration with the \`reportService\` bean provided by the container. The selected interface describes the methods eligible for export according to the assembler, and does not necessarily have to be a Standard MBean interface with the \`MBean\` suffix.

When a project already has its own application management interface, using an interface-based assembler helps limit the surface without adding annotations to many methods. If that interface contains sensitive commands, you still need to split or further restrict it.

## 9. Selecting methods by name and excluding methods

For a legacy codebase where an adapter cannot be separated immediately, Spring provides assemblers that select by name or exclude by name:

\`\`\`java
import org.springframework.jmx.export.assembler.MethodNameBasedMBeanInfoAssembler;

MethodNameBasedMBeanInfoAssembler assembler =
    new MethodNameBasedMBeanInfoAssembler();

assembler.setManagedMethods(
    "getActiveJobs",
    "getCompletedTotal",
    "requestRetry"
);
\`\`\`

This is a way to create an allowlist by method name. When overloads exist, you need to understand how the assembler handles methods with the same name. A single method name should not be treated as a complete access control; signatures, parameter types, and method roles must be verified directly from \`MBeanInfo\`.

An exclusion approach:

\`\`\`java
import org.springframework.jmx.export.assembler.MethodExclusionMBeanInfoAssembler;

MethodExclusionMBeanInfoAssembler assembler =
    new MethodExclusionMBeanInfoAssembler();

assembler.setIgnoredMethods(
    "purgeHistoricalRecords",
    "generateCustomerReport"
);
\`\`\`

An exclusion list is a transitional option when you need to preserve the broad surface of a legacy system. For systems with high security and stability requirements, an allowlist or a dedicated adapter is usually easier to manage because new public methods will not be exposed automatically.

## 10. Public Java methods differ from JMX operations

Consider:

\`\`\`java
public class Example {
    public int getCount() { return 10; }
    public boolean isRunning() { return true; }
    public void setThreshold(int value) { }
    public void reset() { }
    public String debugDump() { return "internal"; }
}
\`\`\`

A reflective assembler may interpret:

- \`getCount()\` as a readable attribute \`Count\`.
- \`isRunning()\` as a boolean attribute \`Running\`.
- \`setThreshold(int)\` as a writable attribute \`Threshold\` if selected.
- \`reset()\` as an operation.
- \`debugDump()\` as an operation or a method evaluated according to assembler rules.

However, actual mappings depend on the assembler, bean type, and JMX contract. A Java getter is not necessarily readable via JMX if it is not part of the management interface.

**Pay special attention to setters:** a public setter can allow modifying state that the business API intended only internal code to modify. Do not expose a writable attribute to JMX unless valid ranges, authorization, auditing, and concurrency/lifecycle impacts have been defined.

## 11. Do not export large DTOs and high-cost methods

Limiting the list of public methods is part of management design. An operation may be called from an operator console, script, or dashboard, with characteristics different from normal application flows:

- \`getAllUsers()\`: returns sensitive, high-volume data.
- \`getEntireCache()\`: memory-intensive serialization.
- \`rebuildIndex()\`: long-running, creates CPU/IO pressure.
- \`changeDatabaseUrl(...)\`: alters critical configuration.
- \`deleteAll()\`: destructive data operation.

Even if these methods are public for integration tests or internal application use, that does not make them suitable management APIs. A good JMX surface typically favors **fast-read snapshots** and **well-scoped, meaningful commands**.

For complex management data, convert it to scalars or clearly mapped Open MBean types; limit payloads and do not return mutable references to domain objects.

## 12. Impact of JDK proxies and CGLIB proxies

Spring AOP can replace an object at runtime with a JDK dynamic proxy or a CGLIB proxy:

- A JDK proxy typically exposes the methods belonging to the interfaces that the proxy implements.
- A CGLIB proxy is a subclass of the target but cannot override certain methods such as \`final\` ones.
- Metadata annotations may reside on the target class while the exporter receives a proxy.
- If the management interface selects a method that is unavailable through the proxy, \`MBeanInfo\` and invocation may mismatch.

Inspection example:

\`\`\`java
import org.springframework.aop.support.AopUtils;

Object bean = context.getBean("reportService");

System.out.println(AopUtils.isAopProxy(bean));
System.out.println(AopUtils.isJdkDynamicProxy(bean));
System.out.println(AopUtils.getTargetClass(bean));
\`\`\`

\`context\` is an injected \`ApplicationContext\`, not a globally available variable. When proxies are involved, a dedicated JMX adapter that injects the business/management port via an interface is usually more stable than exporting the business class directly.

Do not assume that changing \`proxyTargetClass=true\` automatically resolves all JMX issues. It can affect many other AOP beans and will not fix an exporter configured with the wrong assembler or ObjectName.

## 13. Inspecting exactly what was exported using MBeanInfo

The reliable way to verify is to query \`MBeanServer\` after registration:

\`\`\`java
import java.lang.management.ManagementFactory;
import javax.management.MBeanServer;
import javax.management.MBeanInfo;
import javax.management.ObjectName;

MBeanServer server =
    ManagementFactory.getPlatformMBeanServer();

ObjectName name = new ObjectName(
    "com.example.reports:type=Monitor,name=Primary"
);

if (!server.isRegistered(name)) {
    throw new IllegalStateException("MBean not registered: " + name);
}

MBeanInfo info = server.getMBeanInfo(name);

for (var attr : info.getAttributes()) {
    System.out.printf(
        "Attribute=%s readable=%s writable=%s%n",
        attr.getName(), attr.isReadable(), attr.isWritable()
    );
}

for (var operation : info.getOperations()) {
    System.out.println("Operation=" + operation.getName());
}
\`\`\`

This probe must use the exact \`MBeanServer\` that the exporter registers with; if the application uses a separate server, replace the platform server with the injected instance. Reading MBeanInfo reveals the actual JMX surface exported, not just what the developer expected from annotations or interfaces.

You should also compare **operation signatures** and **impact** via \`MBeanOperationInfo\`, especially when there are overloads or methods accepting complex parameters.

## 14. Testing the public surface with an allowlist

An integration test can assert which operations are exposed:

\`\`\`java
import static org.junit.jupiter.api.Assertions.*;
import java.util.Arrays;
import java.util.Set;
import java.util.stream.Collectors;
import javax.management.MBeanServer;
import javax.management.ObjectName;

class JmxSurfaceAssertions {
    static void assertSafeSurface(MBeanServer server)
            throws Exception {
        ObjectName name = new ObjectName(
            "com.example.reports:type=Monitor,name=Primary"
        );

        var info = server.getMBeanInfo(name);

        Set<String> operations = Arrays.stream(info.getOperations())
            .map(op -> op.getName())
            .collect(Collectors.toSet());

        assertTrue(operations.contains("retryFailed"));
        assertFalse(operations.contains("deleteAllCustomerData"));
        assertFalse(operations.contains("purgeHistoricalRecords"));
    }
}
\`\`\`

For a strict contract, test an exact list of **attribute names, read/write flags, operation names, signatures**, and data types. This approach catches regressions when someone adds a new public method or changes the assembler configuration.

Do not test by scanning all public methods of the Java class and predicting the mapping yourself. \`MBeanInfo\` is what JMX clients actually see.

## 15. Security boundaries of the management interface

“Only public methods” should not be treated as a security measure. JMX access can grant permission to observe and execute operations, depending on the configured connector, authentication, TLS, and authorization mechanisms. A well-constrained management API still requires:

1. **Limiting exposure** via selective interfaces/annotations/assemblers.
2. **Restricting network access** to the JMX connector without unnecessarily exposing management ports.
3. **Authentication and authorization** for clients and impactful operations.
4. **Application-layer condition checks** when executing management commands.
5. **Auditing** for critical state changes.
6. **Cost limits** on getters and operations so clients cannot cause overload via polling or repeated calls.

A management interface with only read-only attributes can be operated more safely, yet can still leak sensitive metrics such as tenant IDs, system paths, or customer data. Inspect both the MBean identity (\`ObjectName\`) and attribute payloads.

## 16. Choosing a strategy by project scale

| Strategy | Pros | Limitations |
| --- | --- | --- |
| Standard MBean interface | Clear boundary, standard Java/JMX | Requires maintaining a JMX interface |
| Spring annotations + Metadata assembler | Selects attributes/operations close to the adapter | Depends on Spring exporter configuration |
| InterfaceBased assembler | Separates the contract using an interface | Requires managing mapping/proxies |
| MethodNameBased assembler | Suitable for legacy codebases, quick allowlist | String method names easily drift during refactoring |
| MethodExclusion assembler | Can preserve legacy contract when only excluding a few methods | New public methods may be exposed unintentionally |
| Broad reflective export | Quick configuration for internal demos | Hard to control surface and API changes |

For a growing application, prefer a **dedicated management adapter + allowlist of permitted methods**. When you genuinely need to export a bean with a broad default interface, write an integration test that verifies the exact \`MBeanInfo\`.

## 17. Practical workflow

When designing or reviewing an MBean:

1. Document the \`ObjectName\`, owning bean, and exporter in use.
2. Identify whether it is a Standard MBean/MXBean or a POJO exported as a Spring ModelMBean.
3. Identify the actual assembler and naming strategy.
4. List the **permitted** attributes and operations, including read/write semantics.
5. Exclude business, debug, and maintenance public methods that do not belong to management.
6. Check proxies/interfaces if AOP is applied.
7. Start the test context and read \`MBeanInfo\` on the correct server.
8. Test that new methods do not accidentally appear over JMX.
9. Verify authentication, authorization, and auditing for impactful commands.
10. Maintain the management interface as a public contract with versioning and change control.

## 18. Key takeaway

**Java \`public\` does not mean allowed for JMX export.** Standard MBean/MXBean uses a clearly defined management interface, while Spring can generate a surface from a POJO via an assembler. A default reflection-based assembler may export more public methods than intended. To keep the management API small and safe, choose an explicit interface/annotation/allowlist and use \`MBeanServer.getMBeanInfo()\` to verify exactly what clients actually see.
