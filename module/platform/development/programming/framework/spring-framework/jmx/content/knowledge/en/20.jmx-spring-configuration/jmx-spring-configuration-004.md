# Setting defaultDomain by Deployment Environment in Spring Framework JMX

## 1. Objectives

JMX (Java Management Extensions) identifies each MBean by an `ObjectName` structured as `domain:key=value`. In a Spring Framework application, `MBeanExporter` selects beans to export and registers them into an `MBeanServer`; naming can originate from an explicit map, the `@ManagedResource` annotation, an `ObjectNamingStrategy`, or JMX rules.

**defaultDomain** is commonly understood as the default domain used when an MBean name does not specify a full domain. It is a setting that impacts the final registration name, thereby directly affecting JConsole, VisualVM, JMX proxies, monitoring, and operational scripts.

This topic aims to clarify:

- How does an **MBeanServer**'s default domain differ from the domain generated by a **Spring naming strategy**?
- Why might different domains be needed between local, development, staging, and production?
- How to read values from the environment and apply them consistently to the exporter/MBeanServer.
- When should you **not** put the environment name into the domain?
- How to avoid ObjectName collisions and avoid breaking dashboards/clients using existing names.

**First principle:** there is no single `defaultDomain` property that can be arbitrarily applied to every `MBeanExporter`, every naming strategy, and every MBeanServer without considering the configuration. You must determine **which component actually owns the default domain** and through which path the final ObjectName is produced.

## 2. Domain and ObjectName

Standard syntax:

```text
domain:key1=value1,key2=value2,...
```

Examples:

```text
com.example.orders:type=Queue,name=Pending
com.example.cache:type=CacheMonitor,name=Primary
java.lang:type=Memory
```

In `com.example.orders:type=Queue,name=Pending`:

- `com.example.orders` is the domain, creating a logical namespace.
- `type=Queue` describes the MBean type according to the application's convention.
- `name=Pending` distinguishes a specific MBean.
- The entire ObjectName must be unique within **a single** MBeanServer at the time of registration.

The domain is a **logical namespace**, not a hostname, network address, Spring profile, or ApplicationContext name. We can use environment information to name the domain, but that is a naming contract design decision, not a mandatory JMX semantic.

Examples across environments:

```text
com.example.orders.dev:type=Queue,name=Pending
com.example.orders.staging:type=Queue,name=Pending
com.example.orders.prod:type=Queue,name=Pending
```

Another approach is a stable domain with the environment placed in a key property:

```text
com.example.orders:environment=dev,type=Queue,name=Pending
com.example.orders:environment=staging,type=Queue,name=Pending
com.example.orders:environment=prod,type=Queue,name=Pending
```

Both strategies can be valid; choose one and maintain it consistently. Do not silently switch between the two strategies after dashboards/clients have started using them.

## 3. Default Domain of MBeanServer

`MBeanServer` has a default domain. The `getDefaultDomain()` API returns the server's default domain string:

```java
import java.lang.management.ManagementFactory;
import javax.management.MBeanServer;

MBeanServer server =
    ManagementFactory.getPlatformMBeanServer();

System.out.println(server.getDefaultDomain());
```

The default domain is used in certain cases where a registered object name has an empty domain. For names specifying a full domain, such as `com.example.orders:type=Queue`, the server does not replace the domain with the default value.

Mental model:

```text
Server default domain: com.example.management

Explicit ObjectName:
  com.example.orders:type=Queue
  -> Keeps com.example.orders

Empty-domain ObjectName:
  :type=Queue
  -> Upon registration, the server may apply its default domain
```

This distinguishes the **JMX server's default domain** from writing code that generates an ObjectName from a configured prefix. `MBeanServer.getDefaultDomain()` is not a property that modifying the Spring environment after startup will automatically change.

### Creating an MBeanServer with a dedicated default domain

The JMX API allows creating a server and specifying its default domain:

```java
import javax.management.MBeanServer;
import javax.management.MBeanServerFactory;

MBeanServer server = MBeanServerFactory.createMBeanServer(
    "com.example.orders.dev"
);

System.out.println(server.getDefaultDomain());
// com.example.orders.dev
```

Or in Spring, `MBeanServerFactoryBean` can create a new server or locate an existing one. Understand the actual server creation/lookup configuration and do not assume `setDefaultDomain` modifies an **already existing platform MBeanServer**.

## 4. Why Consider defaultDomain by Environment?

Some systems run multiple application contexts or modules in the same JVM/MBeanServer. If they register generic MBean names:

```text
app:type=Cache,name=Main
```

two modules can collide. A clear semantic domain helps separate namespaces:

```text
com.example.billing.dev:type=Cache,name=Main
com.example.shipping.dev:type=Cache,name=Main
```

However, dev/staging/prod environments usually run in **different JVMs**. Two independent JVMs can use the same ObjectName without colliding. In that case, changing the domain per profile is not required to avoid collisions; it only serves administration, querying, or differentiation when tools aggregate data from multiple connections.

Therefore, ask:

1. Which applications actually **share one MBeanServer**?
2. Does monitoring use a fixed ObjectName across environments?
3. Is the domain name used to distinguish apps, modules, or deployments?
4. Do we need a shared dashboard running the same query unchanged across dev/staging/prod?
5. Does infrastructure already attach `environment`, `instance`, and `cluster` labels outside JMX?

If the telemetry pipeline already attaches the environment from the connection/collector, keeping the JMX domain stable can make dashboard reuse much easier.

## 5. Default Domain and ObjectName in Spring

Spring has multiple paths for generating names:

```text
Spring bean
   |
   +-- MBeanExporter.setBeans(...)
   |     -> map key / naming strategy
   |
   +-- @ManagedResource(objectName = "...")
   |     -> Annotation metadata + MetadataNamingStrategy
   |
   +-- KeyNamingStrategy / custom ObjectNamingStrategy
   |     -> generates ObjectName from key, class, or metadata
   |
   v
Final ObjectName
   |
   v
MBeanServer.registerMBean
```

If `@ManagedResource(objectName=...)` explicitly specifies the domain, the server's default domain does not override that name. Similarly, if the `beans` map contains a full ObjectName as its key, the server still uses the explicit domain.

Therefore, when you want to set the domain by environment, **design a naming strategy that generates ObjectNames per environment or explicitly configure full names**. Changing only the MBeanServer's default domain will not affect explicit ObjectNames.

## 6. Environment Configuration with Spring Environment

Suppose the application chooses the domain name based on environment. Configuration properties can be set as:

```properties
# application-dev.properties
management.jmx.domain=com.example.orders.dev
```

```properties
# application-staging.properties
management.jmx.domain=com.example.orders.staging
```

```properties
# application-prod.properties
management.jmx.domain=com.example.orders.prod
```

This is a **custom application-defined property for the example**, not a default property name automatically used by Spring Framework to change the domain of all JMX MBeans. Do not confuse it with Spring Boot's specific JMX/Actuator properties.

In Java config, it can be read from `Environment`:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.env.Environment;

@Configuration
public class JmxDomainConfig {
    @Bean
    public JmxDomainSettings jmxDomainSettings(Environment env) {
        String domain = env.getRequiredProperty(
            "management.jmx.domain"
        );
        return new JmxDomainSettings(domain);
    }
}

public record JmxDomainSettings(String domain) {}
```

The snippet above only reads the domain and wraps the configuration. An additional step is needed to pass that value into the **ObjectName generation mechanism** or the creation of a new MBeanServer. Creating `JmxDomainSettings` without using it in an exporter/naming strategy will not change MBean names.

## 7. Option 1: Generate Full ObjectName from Property

This is a simple, predictable approach when managing a few explicit MBeans:

```java
import java.util.Map;
import javax.management.ObjectName;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jmx.export.MBeanExporter;

@Configuration
public class ExplicitJmxNamesConfiguration {
    @Bean
    public MBeanExporter mbeanExporter(
            QueueManagement queueManagement,
            JmxDomainSettings settings) throws Exception {

        ObjectName name = new ObjectName(
            settings.domain() + ":type=Queue,name=Pending"
        );

        MBeanExporter exporter = new MBeanExporter();
        exporter.setBeans(Map.of(name.toString(), queueManagement));
        return exporter;
    }
}
```

In the example, `QueueManagement` is a management adapter provided by the application with a valid JMX contract. The domain is taken from the deployment property, and the ObjectName is constructed before registration. This approach allows failing fast if the domain string is invalid.

Note: concatenating a domain from a property is only safe when the property value is controlled. `ObjectName.quote` is only for **key property values**, not for quoting the entire domain. The domain should be validated against the organization's naming policy (for example, allowing only letters, digits, dots, or underscores by convention).

### Using `@Value` for concise configuration

```java
@Bean
public MBeanExporter exporter(
        QueueManagement queueManagement,
        @Value("${management.jmx.domain}") String domain)
        throws Exception {
    ObjectName name = new ObjectName(
        domain + ":type=Queue,name=Pending"
    );
    MBeanExporter exporter = new MBeanExporter();
    exporter.setBeans(Map.of(name.toString(), queueManagement));
    return exporter;
}
```

This is also **explicit naming**: it does not necessarily change the `MBeanServer`'s default domain. It is usually what applications actually need when referring to "setting the JMX domain by environment".

## 8. Option 2: Custom ObjectNamingStrategy

When there are many MBeans, instead of concatenating strings in every `setBeans`, you can write an `ObjectNamingStrategy` to centralize the convention:

```java
import javax.management.MalformedObjectNameException;
import javax.management.ObjectName;
import org.springframework.jmx.export.naming.ObjectNamingStrategy;

public final class EnvironmentObjectNamingStrategy
        implements ObjectNamingStrategy {

    private final String domain;

    public EnvironmentObjectNamingStrategy(String domain) {
        this.domain = domain;
    }

    @Override
    public ObjectName getObjectName(Object managedBean, String beanKey)
            throws MalformedObjectNameException {
        return new ObjectName(
            domain + ":type=Component,name=" + ObjectName.quote(beanKey)
        );
    }
}
```

Assuming the exporter keys are `queuePrimary` and `cachePrimary`, the naming strategy generates:

```text
com.example.orders.dev:type=Component,name="queuePrimary"
com.example.orders.dev:type=Component,name="cachePrimary"
```

Quoted values become literal quoted values; if pattern queries are needed, clients must be compatible with that value representation. Using `type=Component` is only an example; in production, choose a `type` key that better reflects the MBean kind.

Configuration:

```java
@Bean
public MBeanExporter exporter(
        QueueManagement queueManagement,
        CacheManagement cacheManagement,
        JmxDomainSettings settings) {
    MBeanExporter exporter = new MBeanExporter();
    exporter.setBeans(Map.of(
        "queuePrimary", queueManagement,
        "cachePrimary", cacheManagement
    ));
    exporter.setNamingStrategy(
        new EnvironmentObjectNamingStrategy(settings.domain())
    );
    return exporter;
}
```

Advantage: rules are centralized and it is easy to ensure all MBeans registered by this exporter follow the same namespace. Limitation: this naming strategy applies to beans handled by the corresponding exporter; it does not automatically rename MBeans registered by other subsystems.

## 9. Option 3: Create an MBeanServer with a Dedicated Default Domain

If a server-level default domain is genuinely needed, a new `MBeanServer` can be created:

```java
import javax.management.MBeanServer;
import javax.management.MBeanServerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class DedicatedMBeanServerConfiguration {
    @Bean
    public MBeanServer dedicatedMBeanServer(
            JmxDomainSettings settings) {
        return MBeanServerFactory.createMBeanServer(settings.domain());
    }
}
```

And inject **that exact MBeanServer** into the exporter:

```java
@Bean
public MBeanExporter exporter(
        MBeanServer dedicatedMBeanServer,
        QueueManagement queueManagement) {
    MBeanExporter exporter = new MBeanExporter();
    exporter.setServer(dedicatedMBeanServer);
    exporter.setBeans(Map.of(
        ":type=Queue,name=Pending", queueManagement
    ));
    return exporter;
}
```

In the example, the key has an empty domain to illustrate how the server's default domain is applied upon registration. However, confirm that `ObjectNamingStrategy` and the actual exporter process the key as expected; in practical configurations, full explicit ObjectNames are usually easier to control.

Do not assume a new MBeanServer will appear in a JConsole instance connected to the platform server. If using a dedicated server, configure clients/proxies/connectors to point to the right server. Adding another server increases complexity, so choose it only when registry isolation or server-level characteristics are clearly required.

## 10. Spring Boot: Distinguishing Framework vs. Boot Configuration

In the Spring ecosystem, distinguish between:

- **Spring Framework JMX**: `MBeanExporter`, `@EnableMBeanExport`, `ObjectNamingStrategy`, `MetadataNamingStrategy`, `@ManagedResource`.
- **Spring Boot**: auto-configuration/Actuator may have dedicated JMX properties to control exposure, endpoint domain, or application domain, depending on version.

Do not take a property from Spring Boot documentation and infer that plain Spring Framework reads that property automatically. For instance, `management.jmx.domain` in this article is presented as an **application-defined custom property**; before using a key that matches a property specially understood by Spring Boot, check the active version and configuration.

If both Boot Actuator and a separate exporter create MBeans, avoid ObjectName collisions and ensure the domains of different endpoints are designed intentionally. Having HTTP Actuator endpoints secured does not mean JMX endpoints are protected by the same security mechanism.

## 11. Different Environment, Different Domain: Which Convention to Choose?

### A. Put the environment in the domain

```text
com.example.billing.dev:type=Queue,name=Main
com.example.billing.prod:type=Queue,name=Main
```

Advantage: easy to group in JConsole's domain tree. Disadvantage: dashboard queries like `com.example.billing:type=Queue,*` do not match when the domain changes.

### B. Keep the domain stable, add an environment key

```text
com.example.billing:environment=dev,type=Queue,name=Main
com.example.billing:environment=prod,type=Queue,name=Main
```

Advantage: can search across environments with a shared domain; makes it clear that environment is an identifying attribute. Disadvantage: adding a key changes the ObjectName; any JMX proxy hardcoding the old name must be updated.

### C. Keep ObjectName stable, attach environment labels outside JMX

```text
com.example.billing:type=Queue,name=Main
```

The collector uses environment labels from the deployment, such as `environment=dev` or `environment=prod`. Advantage: the same JMX query is reusable across environments; suitable when each deployment has its own MBeanServer. Disadvantage: clients looking only at the ObjectName may lack environment context if connections are not clearly labeled.

**Design recommendation:** if the goal is to avoid ObjectName collisions in a shared server, adding application/module identity is most important. If the goal is simply distinguishing staging and production running in two independent JVMs, consider keeping the domain stable so tooling and scripts are easily reusable.

## 12. Validating the Configured Domain

A domain coming from an environment variable, profile, or config server may be malformed. Validate it before use:

```java
import javax.management.ObjectName;

public static String checkedDomain(String domain) throws Exception {
    if (domain == null || !domain.matches(
            "[A-Za-z0-9_.-]+")) {
        throw new IllegalArgumentException(
            "Invalid management domain"
        );
    }
    // JMX parser checks final ObjectName syntax.
    new ObjectName(domain + ":type=Validation");
    return domain;
}
```

The regex is only an example convention for an organization, not the full JMX grammar. Depending on naming needs, other characters may be required, though production domains should follow a sufficiently restrictive convention to avoid wildcards and unexpected names.

Do not use `ObjectName.quote(domain)` because that quote API applies to **key property values**. For domains and key names, use an appropriate validator or a trusted configured template.

## 13. Avoiding Names That Change on Every Startup

Do not create domains such as:

```text
com.example.orders.dev.20261111_103001
com.example.orders.dev.pid12345
```

if dashboards or proxies need to access a stable ObjectName. Names containing timestamps/PIDs might help when managing multiple instances in a single shared server, but they make the name change constantly after restarts.

If multiple instances truly share an MBeanServer, add an `instance` key derived from a stable ID:

```text
com.example.orders.dev:type=Queue,name=Main,instance=worker-a
com.example.orders.dev:type=Queue,name=Main,instance=worker-b
```

At the same time, define monitoring discovery rules and cleanup when an instance disappears. If each instance runs in its own JVM, using the same ObjectName on each server is valid and usually simpler.

## 14. Impact on JMX Clients and Proxies

Suppose a client previously used:

```java
ObjectName name = new ObjectName(
    "com.example.orders:type=Queue,name=Main"
);
```

After changing the domain to `com.example.orders.prod`, the old ObjectName can no longer find the new MBean. Components that may need updating include:

- Scripts and JConsole bookmarks using the ObjectName.
- `MBeanProxyFactoryBean.setObjectName(...)` in Spring clients.
- `MBeanServerConnection.queryNames` and monitoring filters.
- Alert rules/dashboards using domain-specific queries.
- Notification listener registrations based on ObjectName.
- Management integration tests.

Therefore, changing the domain is a **management contract change**. Plan to synchronize client and server configurations; if multiple application versions run concurrently, consider a transition period or an appropriate discovery pattern.

## 15. Inspecting Domain and ObjectName After Startup

Read server and registry information:

```java
import java.lang.management.ManagementFactory;
import java.util.Set;
import javax.management.MBeanServer;
import javax.management.ObjectName;

MBeanServer server =
    ManagementFactory.getPlatformMBeanServer();

System.out.println("Default domain: " + server.getDefaultDomain());

ObjectName pattern = new ObjectName(
    "com.example.orders.*:*"
);

Set<ObjectName> names = server.queryNames(pattern, null);
for (ObjectName name : names) {
    System.out.println(name.getCanonicalName());
}
```

The example uses the platform MBeanServer; if the exporter registers to a dedicated server, retrieve that exact server. The pattern `com.example.orders.*:*` matches domains like `com.example.orders.dev` or `com.example.orders.prod`, and does not match `com.example.orders` since the wildcard there follows a dot.

To check an exact name:

```java
ObjectName expected = new ObjectName(
    "com.example.orders.dev:type=Queue,name=Pending"
);
System.out.println(server.isRegistered(expected));
```

Do not rely solely on the printed default domain. When an MBean uses an explicit ObjectName, the server's default domain can be completely different from the MBean's domain and still be valid.

## 16. Handling Configuration Errors and Name Collisions

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `MalformedObjectNameException` | Domain contains invalid characters or string concatenation is malformed | Validate properties and construct ObjectName before export |
| `InstanceAlreadyExistsException` | Two MBeans have the same ObjectName in one server | Add app/module/instance identity or enforce a single owner |
| `isRegistered` returns false | Expected name differs from actual name or wrong server | Query canonical ObjectName on the right server |
| JConsole does not see the MBean | Exporter registered to another server, different connector, or not exported | Check server binding and lifecycle |
| `getDefaultDomain()` differs from the MBean's domain | MBean uses an explicit domain | This is not necessarily an error |
| Works in dev but missing in prod | Profile/property not loaded, different naming config | Read effective properties and actual registry |
| Dashboard breaks after changing domain | Client hardcodes old ObjectName | Synchronize queries/proxies and manage migration |
| Added `@ManagedResource` but domain config has no effect | Explicit annotation objectName overrides naming expectation | Adjust annotation or naming strategy on the right export path |

**RegistrationPolicy** values such as `FAIL_ON_EXISTING`, `IGNORE_EXISTING`, and `REPLACE_EXISTING` only define behavior when an ObjectName already exists. They do not replace namespace design. Using `REPLACE_EXISTING` to avoid duplicate name errors can cause another application to lose its MBean and produce inaccurate monitoring metrics.

## 17. Operational and Security Rules

1. Domains must have a clear owner, naming convention, and configuration source.
2. Add the environment to the domain only when it provides practical value for the registry or tooling.
3. Do not include tokens, passwords, or sensitive customer identifiers in domains/keys.
4. Avoid random domains that destabilize JMX proxies and dashboards.
5. When multiple contexts share a server, names must distinguish apps/modules; when in separate JVMs, matching names on two servers are usually not a bug.
6. Do not confuse the server default domain with the exporter's naming strategy.
7. Verify actual ObjectNames using `queryNames` and canonical names.
8. Do not publicly expose a remote JMX connector just for domain management: JMX connections require proper network policy, TLS, authentication, and authorization.
9. Keep getters lightweight and protect operations with appropriate authorization/validation, because choosing a domain does not make a management API safer.
10. When changing a domain, update clients, scripts, and runbooks as a management API change.

## 18. Mental Model

```text
Deployment environment
     |
     +-- property: management.jmx.domain
             |
             +-- explicit ObjectName -> specified domain
             |
             +-- ObjectNamingStrategy -> strategy-generated domain
             |
             +-- new MBeanServer -> server default domain
                      |
                      v
               MBeanServer registry
                      |
               JMX client/query/proxy
```

**Conclusion:** Setting `defaultDomain` per environment only makes sense when targeting the right configuration layer. If the goal is changing the domain of Spring MBeans, the clearest approach is usually constructing explicit ObjectNames from configuration or using a consistent `ObjectNamingStrategy`. If the goal is a JMX server-level default domain, create/manage the right `MBeanServer` and understand how empty-domain ObjectNames are handled. Avoid arbitrarily changing MBean names by profile if clients, dashboards, or scripts depend on stable names.
