# Avoiding exporting proxies instead of targets when the JMX contract must remain stable

## Learning objectives

After this lesson, you will be able to:

- Explain why Spring AOP can cause a Spring bean at runtime to be a proxy rather than a direct target instance.
- Distinguish between **proxy object**, **target object**, **target class**, **JMX MBean registration**, **management interface**, and **ObjectName**.
- Recognize the risks of basing export configuration on the runtime proxy class or proxy interfaces instead of a management contract designed for stability.
- Choose among exporting the target, controlled proxy export, Standard MBean, annotation-based MBean, and a dedicated management facade.
- Understand why "bypassing the proxy" can lose AOP advice such as transactions, security, or auditing.
- Use Spring AOP utilities, JMX metadata, and integration tests to verify the contract published via \`MBeanServer\`.
- Design a management boundary that does not change unintentionally when refactoring code or switching between JDK dynamic proxy and CGLIB strategies.

## 1. Why does this problem arise?

In the Spring Framework, a bean can be created as a proxy when features such as transaction management, security, caching, asynchronous execution, or custom aspects are applied.

Model:

\`\`\`text
Spring ApplicationContext
      |
      | getBean("paymentService")
      v
Spring AOP proxy
      |
      | advice: transaction / security / logging
      v
Target object: PaymentServiceImpl
\`\`\`

Example:

\`\`\`java
@Service
@Transactional
public class PaymentServiceImpl implements PaymentService {
    // ...
}
\`\`\`

If Spring creates a proxy, the statements:

\`\`\`java
Object bean = context.getBean("paymentServiceImpl");
System.out.println(bean.getClass());
\`\`\`

may print a dynamically generated class, such as a JDK dynamic proxy or a subclass generated by Spring CGLIB. A proxy class name is typically a runtime implementation detail, not a stable management API.

Meanwhile, JMX clients expect clearly named and structured elements:

\`\`\`text
ObjectName  = learning.jmx:type=PaymentService,name=Primary
Attribute   = PendingPayments
Operation   = refreshStatus
\`\`\`

A change in proxy strategy should not inadvertently strip JMX clients of the attributes or operations above.

**Key message:** Export a **stable management contract**; do not let the runtime proxy class become an unintended source of identity or metadata.

## 2. How do proxy, target, and MBean differ?

| Concept | Meaning | Should it serve as the JMX contract? |
|---|---|---|
| Target object | Object containing real logic | Can be the data source; need not be registered directly |
| Target class | Original business class | Can carry JMX annotations, yet remains subject to refactoring changes |
| Spring AOP proxy | Object standing in for target and executing advice | Do not use the proxy class name as the MBean name |
| Management facade | Small adapter designed specifically for JMX | Usually suitable for keeping the contract clear and stable |
| ObjectName | Registration identifier in \`MBeanServer\` | Part of the management contract |
| MBeanInfo | Published list of attributes/operations/types | The actual contract seen by JMX clients |

A proxy is not synonymous with an MBean. A proxy can be registered by a Spring exporter or analyzed by Spring to detect target metadata, yet being exportable does not by itself guarantee the contract is stable.

### JDK dynamic proxy

A JDK proxy implements configured Java interfaces. It is typically not a subclass of the concrete target class.

If a management method exists only on the implementation and not on the proxy interfaces, you must check whether the exporter can find and invoke that method through the proxy.

### Class-based proxy

A class-based proxy is typically a subclass of the concrete target class, so it can preserve many public methods of the target under suitable conditions.

Even so, final classes, final methods, and proxy limitations still exist. Using CGLIB does not automatically solve all JMX metadata and invocation issues.

## 3. What does "exporting the proxy instead of the target" mean?

In an application, \`MBeanExporter\` may be given a Spring bean where \`getBean(...)\` returns a proxy.

Example:

\`\`\`java
Object bean = context.getBean("orderService");
exporter.setBeans(Map.of(
    "learning.jmx:type=OrderService,name=Primary",
    bean
));
\`\`\`

If \`bean\` is a proxy, the exporter has to work with the proxy object and may need to resolve the target class, metadata, and callable methods.

Risks arise when developers:

- Use \`bean.getClass().getSimpleName()\` as the basis for \`ObjectName\`.
- Rely on interfaces that happen to be on the proxy instead of an intentional management interface.
- Refactor a business interface and accidentally alter the JMX operation surface.
- Switch from JDK proxy to class-based proxy or vice versa without testing metadata.
- Assume \`@ManagedResource\` on the target is guaranteed to be detected in every exporter mechanism.
- Register the proxy directly with JMX as a Standard MBean without checking convention compliance.
- Strip away the proxy for easier export, losing transaction/security advice on the JMX invocation path.

The last point is crucial: **exporting the target directly is not always safer than exporting the proxy**. When advice is an essential part of behavior, going straight to the target can bypass it.

## 4. Distinguishing three layers to verify

A proxy + JMX problem involves three separate questions:

1. **Discovery:** did the exporter recognize the bean as a managed resource?
2. **Metadata:** does the MBean publish the right \`ObjectName\`, attributes, operations, and signatures?
3. **Invocation:** when a JMX client invokes an operation, does the call reach the right implementation with the required advice?

For example, an MBean may register successfully yet be missing an operation; or metadata may be right yet invocations do not pass through the security advisor.

Do not merely check that the MBean appears in JConsole and conclude the contract is stable.

## 5. Example: business service wrapped by an AOP proxy

Service interface:

\`\`\`java
package example.jmx;

public interface InventoryService {
    int availableItems();
    void refreshInventory();
}
\`\`\`

Implementation:

\`\`\`java
package example.jmx;

import java.util.concurrent.atomic.AtomicInteger;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class InventoryServiceImpl implements InventoryService {

    private final AtomicInteger available = new AtomicInteger(100);

    @Override
    public int availableItems() {
        return available.get();
    }

    @Override
    @Transactional
    public void refreshInventory() {
        // Example: sync data from a managed source.
        // In production, this operation requires proper permission and audit.
        available.set(120);
    }
}
\`\`\`

When transaction management is enabled and a suitable transaction manager exists, Spring can create a proxy to apply transaction advice.

If you also annotate \`InventoryServiceImpl\` with \`@ManagedResource\` and JMX operations, changing the runtime proxy strategy may require re-checking how metadata is detected and how methods are invoked.

An alternative design is separating management into a facade.

## 6. Recommended solution: a stable management facade

A management facade is a Spring bean dedicated to presenting the management contract, rather than being the business service itself.

\`\`\`java
package example.jmx;

import org.springframework.jmx.export.annotation.ManagedResource;
import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedOperation;

@ManagedResource(
    objectName = "learning.jmx:type=Inventory,name=Primary",
    description = "Stable inventory management interface"
)
public class InventoryManagement {

    private final InventoryService inventoryService;

    public InventoryManagement(InventoryService inventoryService) {
        this.inventoryService = inventoryService;
    }

    @ManagedAttribute(description = "Available item count")
    public int getAvailableItems() {
        return inventoryService.availableItems();
    }

    @ManagedOperation(description = "Refresh inventory data")
    public void refresh() {
        inventoryService.refreshInventory();
    }
}
\`\`\`

Advantages:

- **Stable ObjectName:** does not depend on the runtime proxy class name.
- **Stable attribute names:** \`AvailableItems\` does not change just because the service renames an internal method.
- **Stable operation names:** clients continue invoking \`refresh\`.
- **Small surface:** publishes only what truly needs management.
- **Advice preserved:** the facade calls through the \`InventoryService\` bean, which can be a proxy applying transactions/security.
- **Testable:** the facade has its own JMX contract and integration tests via \`MBeanServer\`.

Spring configuration:

\`\`\`java
package example.jmx;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableMBeanExport;

@Configuration
@EnableMBeanExport
public class JmxConfiguration {

    @Bean
    InventoryManagement inventoryManagement(
            InventoryService inventoryService) {
        return new InventoryManagement(inventoryService);
    }
}
\`\`\`

If the service implementation is already registered via component scanning, do not create another service instance just for the facade to use. Ensure the facade receives the **Spring-managed service proxy**, rather than calling \`new InventoryServiceImpl()\` directly if transaction advice is required.

## 7. Why not just unwrap the proxy and register the target?

A hasty workaround might retrieve the target object behind the proxy and register it directly:

\`\`\`java
// Risky idea: bypass the proxy for direct export.
Object target = ...;
server.registerMBean(target, name);
\`\`\`

This approach has problems:

- The target is not necessarily a valid Standard MBean.
- You have to manage \`ObjectName\`, registration, and lifecycle manually.
- JMX calls may bypass advice on the proxy.
- Some targets are managed by complex proxies/factories/scopes; grabbing the raw target is not always safe.
- Security, transactions, auditing, or other interceptors may be bypassed.
- If the target changes between calls, registering an old instance becomes inappropriate.

**Do not automatically unwrap the target object and register it as a general solution.** Prefer a facade or an exporter configuration with an explicit contract and real invocation tests.

## 8. Export approaches to distinguish

### Approach A — Spring annotation-driven exporter

\`\`\`java
@ManagedResource(
    objectName = "learning.jmx:type=Inventory,name=Primary"
)
public class InventoryManagement {
    @ManagedAttribute
    public int getAvailableItems() { ... }

    @ManagedOperation
    public void refresh() { ... }
}
\`\`\`

Combined with \`@EnableMBeanExport\` or an exporter with the corresponding annotation metadata assembler. This is a clear approach for a management facade.

### Approach B — Standard MBean interface

\`\`\`java
public interface InventoryManagementMBean {
    int getAvailableItems();
    void refresh();
}

public class InventoryManagement implements InventoryManagementMBean {
    // ...
}
\`\`\`

The class and interface follow the Standard MBean convention, or you can use a \`StandardMBean\` wrapper to specify the management interface explicitly if you do not want to rely on the implementation class name.

Using a dedicated management interface defines the contract more explicitly than taking all methods from a runtime proxy.

### Approach C — Explicit exporter mapping

\`\`\`java
MBeanExporter exporter = new MBeanExporter();
exporter.setBeans(Map.of(
    "learning.jmx:type=Inventory,name=Primary",
    inventoryManagement
));
\`\`\`

The map defines \`ObjectName\` explicitly. However, if the mapped object is a service proxy whose metadata/interface is invalid, explicit mapping does not automatically solve JMX compliance issues.

### Approach D — Intentional proxy export

A proxy can be exported if the exporter and metadata mapping can handle it properly. In that case, ensure:

- \`ObjectName\` is not derived from an unstable proxy class name.
- Management interfaces/metadata are intentionally defined.
- JMX operation invocations pass through required advice.
- \`MBeanInfo\` and integration tests confirm the contract.
- Changes in proxy strategy have regression tests.

The goal is not to forbid proxies completely at the JMX boundary, but **not to let proxy implementation details accidentally define the public management contract**.

## 9. How Spring AOP chooses proxies

Spring AOP typically uses:

- **JDK dynamic proxy** when proxying interfaces.
- **Class-based proxy** when target-class proxying is configured or per the corresponding mechanism/framework.

Example enabling class-based proxies:

\`\`\`java
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true)
public class AopConfiguration {
}
\`\`\`

With transaction proxies:

\`\`\`java
@Configuration
@EnableTransactionManagement(proxyTargetClass = true)
public class TransactionConfiguration {
}
\`\`\`

However, \`proxyTargetClass=true\` only controls **how proxies are created when advice applies**; it does not force every Spring bean to be proxied.

Moreover, class-based proxies have limitations: final classes cannot be subclassed; final methods cannot be overridden to apply subclass-style advice.

Changing the proxy strategy across the entire application can affect how beans are injected/cast, method interception, and what runtime types the exporter sees. Do not alter the entire AOP configuration just to make one custom MBean appear if a facade can be used.

## 10. Using AopUtils to diagnose the runtime bean

Spring AOP provides a utility:

\`\`\`java
import org.springframework.aop.support.AopUtils;

Object bean = context.getBean("inventoryServiceImpl");

System.out.println(
    "Runtime class: " + bean.getClass().getName()
);
System.out.println(
    "Target class: " + AopUtils.getTargetClass(bean)
);
System.out.println(
    "Is AOP proxy: " + AopUtils.isAopProxy(bean)
);
System.out.println(
    "Is JDK proxy: " + AopUtils.isJdkDynamicProxy(bean)
);
System.out.println(
    "Is class proxy: " + AopUtils.isCglibProxy(bean)
);
\`\`\`

Illustrative output:

\`\`\`text
Runtime class: jdk.proxy...$Proxy...
Target class: class example.jmx.InventoryServiceImpl
Is AOP proxy: true
Is JDK proxy: true
Is class proxy: false
\`\`\`

Runtime proxy names can vary by JDK, Spring version, advisors, and proxy creation. Do not use such strings as a fixed \`ObjectName\`.

\`AopUtils.getTargetClass\` helps identify the target type; it does not itself change exporter configuration or "unwrap the proxy".

## 11. Decoupling the JMX contract from Java class names

A common naming mistake:

\`\`\`java
String objectName =
        "learning.jmx:type=" + bean.getClass().getSimpleName();
\`\`\`

When the bean is a proxy, \`getClass().getSimpleName()\` may be a dynamically generated name or change after refactoring.

Use an explicit \`ObjectName\`:

\`\`\`java
ObjectName name = new ObjectName(
    "learning.jmx:type=Inventory,name=Primary"
);
\`\`\`

or:

\`\`\`java
@ManagedResource(
    objectName = "learning.jmx:type=Inventory,name=Primary"
)
\`\`\`

A naming strategy designed around logical resource identity is also appropriate if multiple instances must be registered.

**ObjectName is a management contract**: scripts, dashboards, and JMX clients may reference that exact name. Switching from a JDK proxy to a class-based proxy should not change the \`ObjectName\`.

## 12. Attribute and operation contracts must also remain stable

A class with a getter:

\`\`\`java
@ManagedAttribute
public int getAvailableItems() {
    return service.availableItems();
}
\`\`\`

The JMX attribute will typically be named \`AvailableItems\`.

If the getter is refactored to:

\`\`\`java
@ManagedAttribute
public int getAvailableInventory() {
    return service.availableItems();
}
\`\`\`

the attribute may change to \`AvailableInventory\`, breaking clients using the old name.

Similarly:

\`\`\`java
@ManagedOperation
public void refresh() {
    service.refreshInventory();
}
\`\`\`

If renamed to \`rebuild()\`, the operation name may change. JMX clients calling \`invoke(name, "refresh", ...)\` may stop working.

A management facade helps keep management names stable even when the service API changes.

## 13. Verifying from MBeanServer rather than only reading source

An exporter may register an MBean successfully while the actual contract differs from expectations. Inspect \`MBeanServer\`.

\`\`\`java
import java.lang.management.ManagementFactory;
import javax.management.MBeanServer;
import javax.management.ObjectName;
import javax.management.MBeanInfo;
import javax.management.MBeanAttributeInfo;
import javax.management.MBeanOperationInfo;

MBeanServer server =
        ManagementFactory.getPlatformMBeanServer();

ObjectName name = new ObjectName(
    "learning.jmx:type=Inventory,name=Primary"
);

if (!server.isRegistered(name)) {
    throw new IllegalStateException("MBean not registered");
}

MBeanInfo info = server.getMBeanInfo(name);

for (MBeanAttributeInfo attribute : info.getAttributes()) {
    System.out.println(
        "Attribute: " + attribute.getName()
        + ", type=" + attribute.getType()
    );
}

for (MBeanOperationInfo operation : info.getOperations()) {
    System.out.println(
        "Operation: " + operation.getName()
    );
}
\`\`\`

Expected output once the management facade has been properly exported:

\`\`\`text
Attribute: AvailableItems, type=int
Operation: refresh
\`\`\`

You must use the exact \`MBeanServer\` where the exporter registers MBeans. If the application uses a custom server, the platform server will not necessarily have this MBean. Clients from another JVM must use a JMX connector and \`MBeanServerConnection\`.

## 14. Testing invocation: preserving required advice

Having the right metadata is not enough if an important operation must pass through transaction/security/audit advice.

Suppose the facade calls:

\`\`\`java
@ManagedOperation
public void refresh() {
    inventoryService.refreshInventory();
}
\`\`\`

If \`inventoryService\` is a Spring proxy, calls from the facade pass through the proxy and can trigger advice. Conversely, if the facade holds a manually instantiated \`new InventoryServiceImpl()\`, Spring AOP advice on the bean may not run.

An integration test can:

1. Initialize the Spring \`ApplicationContext\` with AOP and the JMX exporter.
2. Obtain the right \`MBeanServer\`.
3. Verify the \`ObjectName\` is registered.
4. Invoke the operation using \`MBeanServer.invoke(...)\`.
5. Observe side effects and assert the required advice ran in the test fixture.
6. Check the access-denied path if a security policy applies.
7. Close the context and verify unexport.

Do not test state-mutating operations in production merely to prove they are exported.

## 15. Integration test pattern for keeping the contract stable

JUnit 5 example:

\`\`\`java
package example.jmx;

import static org.junit.jupiter.api.Assertions.*;

import java.lang.management.ManagementFactory;
import java.util.Arrays;

import javax.management.MBeanServer;
import javax.management.ObjectName;

import org.junit.jupiter.api.Test;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

class InventoryJmxContractTest {

    @Test
    void managementContractDoesNotDependOnProxyName()
            throws Exception {

        try (AnnotationConfigApplicationContext context =
                new AnnotationConfigApplicationContext(
                    JmxConfiguration.class)) {

            MBeanServer server =
                ManagementFactory.getPlatformMBeanServer();

            ObjectName name = new ObjectName(
                "learning.jmx:type=Inventory,name=Primary"
            );

            assertTrue(server.isRegistered(name));

            boolean hasAvailableItems = Arrays.stream(
                server.getMBeanInfo(name).getAttributes()
            ).anyMatch(a ->
                "AvailableItems".equals(a.getName())
                && "int".equals(a.getType())
            );

            boolean hasRefresh = Arrays.stream(
                server.getMBeanInfo(name).getOperations()
            ).anyMatch(o -> "refresh".equals(o.getName()));

            assertTrue(hasAvailableItems);
            assertTrue(hasRefresh);
        }
    }
}
\`\`\`

Prerequisites for this example to run: the exporter must use the platform \`MBeanServer\` and \`InventoryManagement\` must be registered as a Spring bean; if \`JmxConfiguration\` contains only the facade without component scanning/the service bean, the context will fail to initialize. In a real project, import the full configuration and, if multiple tests run in parallel, use a separate \`MBeanServer\` or partitioned \`ObjectName\`.

More importantly, the principle is testing the contract via \`MBeanInfo\`, not checking the Java proxy class name.

## 16. When exporting the proxy is an intentional choice

There are cases where exporting a proxy is needed to preserve AOP behavior when JMX clients invoke methods.

To do this safely:

- Do not use the proxy class name as the \`ObjectName\`.
- Choose an explicit management interface or a metadata assembler that understands proxy/target classes.
- Ensure management methods are genuinely callable on the proxy.
- Verify AOP advice executes properly when invoked via JMX.
- Verify \`MBeanInfo\` through integration tests.
- Document the proxy interfaces and constraints.
- Run regression tests after upgrading Spring versions or changing proxy strategies.

When all these conditions are satisfied, exporting a proxy is not always wrong. The problem is **exporting a proxy accidentally and letting it define an unintended contract**.

## 17. Common errors

| Symptom | Possible Cause | Resolution |
|---|---|---|
| MBean disappears after enabling \`@Transactional\` | Runtime bean became a proxy; exporter/metadata changed | Check target class, exporter, and \`MBeanServer\` |
| \`ObjectName\` contains dynamic proxy name | Naming based on \`bean.getClass()\` | Use a fixed logical \`ObjectName\` |
| Operation disappears when switching to JDK proxy | Method exists only on implementation, not on proxy interface | Use a management facade, suitable interface, or verified exporter strategy |
| MBean exists yet invoke fails | Metadata has method yet proxy does not expose/invoke it | Check \`MBeanInfo\` and call path |
| Switching to CGLIB does not fix error | Root cause is exporter, \`ObjectName\`, or advisor | Debug layer by layer, do not guess |
| Transaction advice does not run via JMX | JMX calls raw target or self-invocation bypasses advice | Have management facade call Spring proxy and test |
| Security annotation does not block JMX operation | Method-level advice did not run or connector too permissive | Check both proxy path and JMX authorization |
| Final method is not advised | Class-based proxy cannot override final methods | Change design or appropriate proxy strategy |
| Client reports \`AttributeNotFoundException\` after refactoring | JMX getter was renamed | Preserve management contract and compatibility accessors |
| Two contexts overwrite each other's MBeans | Duplicate \`ObjectName\`/\`RegistrationPolicy\` | Partition naming or ownership |
| JConsole does not see MBean | Wrong \`MBeanServer\`/JVM or export failure | Use \`isRegistered\` on target server |

## 18. Layer-by-layer debugging workflow

**Step 1: Identify the actual bean/proxy.** Use \`AopUtils.isAopProxy\`, \`isJdkDynamicProxy\`, \`isCglibProxy\`, and \`getTargetClass\`.

**Step 2: Verify registration.** Check \`MBeanServer.isRegistered(ObjectName)\` on the right server.

**Step 3: Inspect metadata.** Use \`getMBeanInfo\` to view actual attributes, operations, and signatures.

**Step 4: Test invocation.** Use \`getAttribute\` and \`invoke\` via JMX, verifying results and side effects.

**Step 5: Check advice.** For transactions or security, confirm the call path goes through the Spring proxy and the right advisors.

**Step 6: Check naming/lifecycle.** Ensure \`ObjectName\` does not depend on the runtime proxy name and the exporter cleans up properly when the context closes.

**Step 7: Compare before/after refactoring.** Test the contract, not only Java unit tests.

## 20. Checklist for keeping the JMX contract stable

1. Is \`ObjectName\` defined by the logical resource rather than the runtime proxy class?
2. Does the management interface have few, well-documented attributes/operations?
3. Is metadata exported from the right class/interface?
4. Are JDK proxy vs. class-based proxy checked when AOP changes?
5. Can management methods be invoked through the JMX path?
6. Are transaction/security/audit advices applied properly?
7. Were any getters or operations renamed after refactoring?
8. Are \`MBeanInfo\`, attribute types, and signatures tested?
9. Are the \`ObjectName\` and target \`MBeanServer\` tested?
10. Is a facade separated if the service proxy changes frequently?
11. Is manual registration of raw targets outside Spring's lifecycle avoided?
12. Is remote JMX authorization checked for sensitive operations?

## 21. Core takeaways

- A runtime Spring AOP bean can be a proxy, not the original target class.
- Do not let an accidental proxy class name or proxy interfaces define the JMX contract.
- **The goal is to export a stable management contract**, not necessarily to always eliminate proxies.
- Registering the target directly can lose important advice; understand the invocation path before doing so.
- A management facade provides stable \`ObjectName\`, attribute, and operation names while calling the service proxy to preserve AOP behavior.
- Verify via \`MBeanServer\` and \`MBeanInfo\`, not solely Java reflection or JConsole.
- Changing proxy strategies is a change worth testing for JMX integration and security.
