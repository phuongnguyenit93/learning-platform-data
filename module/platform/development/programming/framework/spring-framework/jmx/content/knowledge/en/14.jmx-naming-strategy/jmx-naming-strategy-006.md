# defaultDomain and Application Namespace in Spring Framework JMX Naming Strategy

## 1. Context

When Spring Framework exports a bean as a JMX MBean, clients need an **ObjectName** to identify the resource in `MBeanServer`. An ObjectName contains a domain and one or more key properties. For example:

```text
com.example.orders:type=OrderWorker,name=Primary
```

Here, `com.example.orders` is the domain, and `type=OrderWorker,name=Primary` is the set of key properties that identify the resource. The domain can be thought of as part of the application's **management namespace**: it groups MBeans, reduces naming collisions, and creates a discoverable structure for JConsole, dashboards, and automation.

Spring JMX provides **naming strategies** to determine the ObjectName during export. The **defaultDomain** property can appear in configurations of `MBeanServer`, `MBeanServerFactoryBean`, or some naming strategies. However, these "defaults" are not synonymous and are not guaranteed to replace a domain explicitly written in an ObjectName.

This lesson focuses on designing stable domains, understanding the scope of `defaultDomain`, and distinguishing Spring naming strategies from JMX ObjectName rules.

## 2. Objectives

After this lesson, you will be able to:

- Read ObjectName syntax and explain how a domain differs from key properties.
- Distinguish `MBeanServer.getDefaultDomain()` from a domain generated by a Spring naming strategy.
- Use `MBeanServerFactoryBean` when a dedicated server with an intentional default domain is needed.
- Use `MetadataNamingStrategy`, `ObjectNamingStrategy`, or explicit registration names when exporting.
- Design an application namespace by module, MBean type, and instance without causing name collisions.
- Verify registered ObjectNames on the right `MBeanServer` and handle naming errors.
- Understand domain limitations when monitoring multiple JVMs, multi-tenant deployments, and remote access.

## 3. ObjectName: Domain and Key Properties

JMX defines `javax.management.ObjectName` in the form:

```text
domain:key1=value1,key2=value2,...
```

Example:

```text
com.example.orders:type=OrderWorker,name=Primary,region=ap-southeast
```

| Component | Value | Role |
| --- | --- | --- |
| Domain | `com.example.orders` | MBean namespace group |
| `type` | `OrderWorker` | Type of management resource |
| `name` | `Primary` | Name of one instance within the resource type |
| `region` | `ap-southeast` | Information distinguishing the instance |

The keys `type`, `name`, and `region` are **application conventions**, not mandatory keys for every MBean. However, using `type` for the kind and `name` for the instance makes searching more intuitive.

Reading the components:

```java
import javax.management.ObjectName;

ObjectName name = new ObjectName(
    "com.example.orders:type=OrderWorker,name=Primary,region=ap-southeast"
);

System.out.println(name.getDomain());              // com.example.orders
System.out.println(name.getKeyProperty("type"));   // OrderWorker
System.out.println(name.getKeyProperty("name"));   // Primary
System.out.println(name.getCanonicalName());
```

`getCanonicalName()` returns a canonicalized representation of key property order. When comparing two ObjectNames, use `equals()` or the canonical representation rather than relying on the key order in the original string.

Example of two equivalent names:

```text
com.example.orders:type=OrderWorker,name=Primary
com.example.orders:name=Primary,type=OrderWorker
```

Different key property ordering does not change the identified object. Within the same `MBeanServer`, two registrations with the same ObjectName in JMX semantics will conflict.

## 4. What Does an Application Namespace Solve?

A namespace is designed so humans and tools can easily locate resources. It also reduces collisions when multiple frameworks, modules, or libraries share an `MBeanServer`.

Some choices:

```text
com.example.orders:type=OrderWorker,name=Primary
com.example.orders:type=OrderQueue,name=Async
com.example.inventory:type=StockSynchronizer,name=Main
com.example.payments:type=PaymentMetrics,name=Gateway
```

This structure shows:

- The domain separates management namespaces by application or module.
- The `type` key represents the component type.
- The `name` key distinguishes instances of the same type.
- Additional keys are added when real identification needs arise.

A domain is **not an authorization mechanism or security sandbox**. Two domains in the same server can still be viewed by the same JMX client if access rights permit. If isolation is needed, configure appropriate connectors, policies, permissions, and networks.

### 4.1. Domains Aid Querying MBeans

```java
import java.util.Set;
import javax.management.MBeanServer;
import javax.management.ObjectName;

ObjectName pattern = new ObjectName(
    "com.example.orders:type=OrderWorker,*"
);

Set<ObjectName> workers = server.queryNames(pattern, null);

for (ObjectName worker : workers) {
    System.out.println(worker.getCanonicalName());
}
```

`queryNames` takes an ObjectName pattern and returns the actual currently registered ObjectNames. Using wildcards serves querying; a pattern matching multiple MBeans is not a single target for directly calling `getAttribute` or `invoke`.

### 4.2. A Domain Does Not Replace Instance Keys

If every worker in a module used:

```text
com.example.orders:type=OrderWorker
```

then you could register only one MBean with that name on the same server. To have multiple workers, add keys:

```text
com.example.orders:type=OrderWorker,name=Primary
com.example.orders:type=OrderWorker,name=Backup
```

Do not create multiple servers just to dodge ObjectName conflicts when designing a structured namespace already solves the requirement.

## 5. defaultDomain in MBeanServer

JMX `MBeanServer` has the method:

```java
String getDefaultDomain();
```

Example:

```java
import java.lang.management.ManagementFactory;
import javax.management.MBeanServer;

MBeanServer server =
    ManagementFactory.getPlatformMBeanServer();

System.out.println(server.getDefaultDomain());
```

The result depends on the server. Default domain is the default domain name of the **`MBeanServer`**, meaningful in certain cases where an ObjectName does not specify an explicit domain.

JMX allows an `ObjectName` with an empty domain part, such as:

```text
:type=OrderWorker,name=Main
```

In appropriate situations, the server can apply the default domain when registering or interpreting the ObjectName. However:

- Do not rely on an implicit domain when you need stable names reused across environments.
- A server's default domain does not force every MBean to carry that domain.
- An ObjectName with an explicit domain retains its explicit domain.
- `MBeanServer`'s default domain differs from the default domain configured on a naming strategy.

Example:

```java
ObjectName explicit = new ObjectName(
    "com.example.orders:type=OrderWorker,name=Main"
);
```

This name already specifies `com.example.orders`. There is no reason for it to automatically change to the server's default domain.

## 6. Creating an MBeanServer with a Dedicated Default Domain

If an application needs a new server, Spring provides `MBeanServerFactoryBean`:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jmx.support.MBeanServerFactoryBean;

@Configuration
public class PrivateJmxServerConfig {

    @Bean
    public MBeanServerFactoryBean privateMBeanServer() {
        MBeanServerFactoryBean factory =
            new MBeanServerFactoryBean();

        factory.setDefaultDomain("com.example.management");
        factory.setLocateExistingServerIfPossible(false);
        factory.setRegisterWithFactory(false);

        return factory;
    }
}
```

Explanation:

- `setDefaultDomain(...)` chooses the default domain of the new server.
- `setLocateExistingServerIfPossible(false)` expresses the intent not to look up an existing server before creating a new one.
- `setRegisterWithFactory(false)` configures creating the server without registering it in `MBeanServerFactory`'s lookup list.
- `MBeanServerFactoryBean` is a Spring `FactoryBean`, so the produced bean has type `MBeanServer`.

A private server **does not automatically create a JMX Remote connector**. If JConsole or clients in other JVMs need access, configure a connector targeting that server. Default domain is also not a configuration for hostname, port, authentication, or TLS.

### 6.1. Inspecting Default Domain on the Actual Server

```java
import javax.management.MBeanServer;

public void inspect(MBeanServer server) {
    System.out.println("Server default domain: "
        + server.getDefaultDomain());
}
```

Inspect the server injected into the exporter directly, especially in systems with multiple `MBeanServer`s. Calling only `ManagementFactory.getPlatformMBeanServer()` will not reflect a private server that Spring might be using.

## 7. defaultDomain in Spring's Naming Strategy

Spring uses `ObjectNamingStrategy` to derive an ObjectName from a bean and bean key. A common implementation is `MetadataNamingStrategy`, which can leverage `@ManagedResource(objectName = "...")` and a configured default domain.

Configuration example:

```java
import org.springframework.jmx.export.naming.MetadataNamingStrategy;
import org.springframework.jmx.export.metadata.AnnotationJmxAttributeSource;

AnnotationJmxAttributeSource source =
    new AnnotationJmxAttributeSource();

MetadataNamingStrategy namingStrategy =
    new MetadataNamingStrategy(source);

namingStrategy.setDefaultDomain("com.example.orders");
```

The default domain in the naming strategy is used when the strategy needs to **generate an ObjectName** while metadata does not supply an explicit name. It is a naming rule on the Spring side, not a command to change `MBeanServer`'s default domain.

Key distinction:

```text
MBeanServer.getDefaultDomain()
    -> Configuration of the JMX registry

MetadataNamingStrategy.setDefaultDomain(...)
    -> Rule for generating names from bean/metadata before registration
```

The two values may match by design choice, but they do not have to match and do not synchronize automatically.

### 7.1. Explicit Names Take Precedence

If the resource's metadata declares:

```java
@ManagedResource(
    objectName = "com.example.orders:type=OrderWorker,name=Main"
)
public class OrderWorker {
    // ...
}
```

then this explicit name is a specific naming instruction. Do not assume the naming strategy's `defaultDomain` will override `com.example.orders`.

If you want to unify namespaces according to deployment configuration, you can omit hard-coding ObjectNames on the class and design a custom naming strategy or use explicit bean-name mappings. Depending on configuration, this lets the same class be exported under different ObjectNames for different instances.

## 8. MBeanExporter and ObjectNamingStrategy

A complete configuration can use Spring's naming strategy:

```java
package com.example.monitoring;

import java.lang.management.ManagementFactory;
import java.util.Map;
import javax.management.MBeanServer;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jmx.export.MBeanExporter;
import org.springframework.jmx.export.assembler.MetadataMBeanInfoAssembler;
import org.springframework.jmx.export.metadata.AnnotationJmxAttributeSource;
import org.springframework.jmx.export.naming.MetadataNamingStrategy;

@Configuration
public class JmxNamingConfig {

    @Bean
    public OrderWorker orderWorker() {
        return new OrderWorker();
    }

    @Bean
    public MBeanServer mBeanServer() {
        return ManagementFactory.getPlatformMBeanServer();
    }

    @Bean
    public AnnotationJmxAttributeSource jmxSource() {
        return new AnnotationJmxAttributeSource();
    }

    @Bean
    public MetadataMBeanInfoAssembler jmxAssembler(
            AnnotationJmxAttributeSource source) {
        MetadataMBeanInfoAssembler assembler =
            new MetadataMBeanInfoAssembler();
        assembler.setAttributeSource(source);
        return assembler;
    }

    @Bean
    public MetadataNamingStrategy jmxNamingStrategy(
            AnnotationJmxAttributeSource source) {
        MetadataNamingStrategy naming =
            new MetadataNamingStrategy(source);
        naming.setDefaultDomain("com.example.orders");
        return naming;
    }

    @Bean
    public MBeanExporter mBeanExporter(
            OrderWorker orderWorker,
            MBeanServer mBeanServer,
            MetadataMBeanInfoAssembler assembler,
            MetadataNamingStrategy namingStrategy) {

        MBeanExporter exporter = new MBeanExporter();
        exporter.setServer(mBeanServer);
        exporter.setAssembler(assembler);
        exporter.setNamingStrategy(namingStrategy);
        exporter.setBeans(Map.of(
            "orderWorker", orderWorker
        ));
        return exporter;
    }
}
```

With the annotated bean:

```java
import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedResource;

@ManagedResource(description = "Order processing worker")
public class OrderWorker {
    private volatile boolean enabled = true;

    @ManagedAttribute(description = "Whether processing is enabled")
    public boolean isEnabled() {
        return enabled;
    }

    @ManagedAttribute(description = "Change processing state")
    public void setEnabled(boolean enabled) {
        this.enabled = enabled;
    }
}
```

Meaning of the configuration:

1. `MBeanExporter` receives one bean and one key `orderWorker`.
2. `MetadataNamingStrategy` reads metadata and has default domain `com.example.orders`.
3. `MetadataMBeanInfoAssembler` uses metadata to build the JMX interface.
4. The exporter registers the bean into the injected platform `MBeanServer`.

The final ObjectName is the result of the naming strategy's rules over metadata, bean key, and Spring configuration state. If operational code needs the exact name, query the actual registration on the server rather than guessing from the bean name.

### 8.1. When You Want a Fully Explicit ObjectName

The simple way is configuring it directly:

```java
exporter.setBeans(Map.of(
    "com.example.orders:type=OrderWorker,name=Main",
    orderWorker
));
```

With appropriate configuration, this key is the explicit ObjectName for registration. When a project needs an immutable name contract and has only a few MBeans, this is often easier to read than a complex name-generation strategy.

Do not mix multiple naming places without defining precedence: annotation `objectName`, keys in `setBeans`, naming strategy, and server configuration must stay consistent.

## 9. Domain Conventions for Applications and Modules

A good convention must be stable, independent of runtime, and have enough keys to distinguish instances.

### 9.1. Choosing a Domain

Common domain styles:

```text
com.example.app
com.example.orders
com.example.orders.worker
org.example.platform.cache
```

Using reverse DNS or an organizational namespace is a common way to reduce collisions with libraries. For example, `com.example.orders` does not imply a URL `https://com.example.orders`; it is a logical JMX domain name.

Do not put hostnames, IPs, or changing deployment IDs into the domain unless genuinely required. Those details often fit better in key properties or connection identity in monitoring tools.

### 9.2. Key Property Conventions

```text
com.example.orders:type=OrderWorker,name=Primary
com.example.orders:type=OrderWorker,name=Backup
com.example.orders:type=OrderQueue,name=Outbound
```

Conventions should answer:

- `type`: MBean kind, usually tied to the component.
- `name`: instance or role.
- `tenant`, `shard`, `region`: add only when distinguishing actual resources.
- Which keys stay stable across restarts?
- Which keys might change on rollout? If they change, do dashboards/alerts need updating?

A single key like `instance=1` may suffice for a local JVM but not to uniquely identify a resource in a multi-JVM system. Multi-server monitoring usually needs connection/host/environment outside the ObjectName.

### 9.3. Do Not Put Sensitive Data in Names

ObjectNames often appear in logs, JConsole screens, metric labels, or observability systems. Do not put access tokens, passwords, customer emails, or personal data into domains/key properties. If tenants must be distinguished, use safe internal identifiers and apply corresponding read permissions.

## 10. Safely Constructing ObjectNames with Special Characters

Key property values can contain characters needing quoting. When building names from dynamic data, avoid naive string concatenation:

```java
String instance = "Primary, East";
String rawName = "com.example.orders:type=OrderWorker,name=" + instance;
```

Values containing commas can break ObjectName syntax. Use `ObjectName.quote(...)` to quote values:

```java
import javax.management.ObjectName;

String instance = "Primary, East";

ObjectName safeName = new ObjectName(
    "com.example.orders:type=OrderWorker,name="
        + ObjectName.quote(instance)
);
```

Note that `ObjectName.quote` produces a quoted value representation; it does not decide whether that value fits namespace design or security. When reading back a quoted key property, you can use `ObjectName.unquote(...)` on a valid quoted value if the original text is needed.

For dynamic values, also include a validation step: length limits, character limits, and collision likelihood. A stable technical name is usually more useful than a user-entered display label.

## 11. Default Domain and JMX Remote Access

An ObjectName's domain **does not** determine network endpoints. Suppose there is:

```text
com.example.orders:type=OrderWorker,name=Main
```

To access via JMX Remote, clients still need a connector address, such as a `JMXServiceURL`, credentials, and security policies. A private `MBeanServer` with default domain `com.example.orders` does not automatically open an RMI registry or remote port.

```text
JMX Client
   |
   | JMXConnector / JMXServiceURL
   v
MBeanServerConnection
   |
   | ObjectName domain:key=value
   v
MBeanServer
   |
   v
MBean
```

In a multi-JVM system, the same ObjectName can exist on multiple servers. Thus, the practical navigation key in dashboards is usually:

```text
(connection-id, object-name-canonical)
```

Domains help group MBeans within each server, but **do not serve as global identity across all connections**.

## 12. Finding and Inspecting Registered ObjectNames

Use `queryNames` to explore domains on the right server:

```java
import java.lang.management.ManagementFactory;
import java.util.Set;

import javax.management.MBeanServer;
import javax.management.ObjectName;

MBeanServer server = ManagementFactory.getPlatformMBeanServer();

ObjectName pattern =
    new ObjectName("com.example.orders:*");

Set<ObjectName> names = server.queryNames(pattern, null);

for (ObjectName name : names) {
    System.out.println(name.getCanonicalName());
}
```

If the exporter uses a private `MBeanServer`, use that instance instead of the platform server.

### 12.1. Checking a Specific Name

```java
ObjectName expected = new ObjectName(
    "com.example.orders:type=OrderWorker,name=Main"
);

if (server.isRegistered(expected)) {
    System.out.println("MBean exists on selected server");
}
```

When not found:

1. Was the Spring bean created?
2. Did `MBeanExporter` initialize?
3. Which `MBeanServer` is the exporter using?
4. Did the naming strategy ultimately produce this exact ObjectName?
5. Does metadata specify another explicit ObjectName?
6. Was there a registration error due to name collision?
7. Are you checking at the wrong time or in the wrong context?

`MBeanServer.getDomains()` helps list domains that have registered MBeans. It does not replace verifying a specific ObjectName.

## 13. Name Collisions and Registration Policy

Within **a single `MBeanServer`**, each ObjectName can identify only one currently registered MBean. If two beans share an ObjectName, `InstanceAlreadyExistsException` or behavior per the registration policy configured in the Spring exporter may occur.

Example:

```text
com.example.orders:type=OrderWorker,name=Main
com.example.orders:type=OrderWorker,name=Main
```

You cannot assume two registrations on the same server will merge automatically. Assign distinguishing instance names, or define an intentional replace/ignore rule. Do not automatically replace an MBean owned by another component just to avoid startup errors.

When domains come from defaults and bean keys are reused across multiple modules, the risk of name collisions increases. Therefore, in large applications, maintain a project-wide convention for `domain`, `type`, and `name`.

## 14. What Confusions Can Default Domain Cause?

| Confusion | Reality |
| --- | --- |
| `MBeanServer.getDefaultDomain()` determines every MBean's domain | ObjectNames with an explicit domain are not forced to change domain |
| `MetadataNamingStrategy.setDefaultDomain()` changes `MBeanServer` config | It belongs to Spring's name-generation step |
| Domain is a URL or JMX Remote endpoint | Domain is part of the JMX identifier, not networking |
| Different domains mean different access rights | Domains themselves are not security boundaries |
| Same ObjectName across two JVMs is a single MBean | Each `MBeanServer` has its own registry |
| Spring bean name is always the ObjectName | Naming strategy and export setup determine JMX names |
| Changing domain is just changing a display label | Changing domain changes the ObjectName and can break client access |
| Server default domain automatically equals naming strategy default domain | The two configuration layers are independent and can differ |

### 14.1. What Are the Consequences of Changing a Domain?

For example, changing:

```text
com.example.orders:type=OrderWorker,name=Main
```

to:

```text
com.example.core:type=OrderWorker,name=Main
```

This is an identity change. Dashboards, JMX proxies, alerts, and scripts storing the old ObjectName may lose access to the MBean. Treat renaming as a management contract change, with a plan to update consumers or an appropriate transition period.

## 15. Designing a Custom Naming Strategy

When naming conventions depend on module or deployment role, you can write a custom `ObjectNamingStrategy`:

```java
import javax.management.MalformedObjectNameException;
import javax.management.ObjectName;

import org.springframework.jmx.export.naming.ObjectNamingStrategy;

public class ApplicationNamingStrategy
        implements ObjectNamingStrategy {

    @Override
    public ObjectName getObjectName(
            Object managedBean,
            String beanKey) throws MalformedObjectNameException {

        String type = managedBean.getClass().getSimpleName();
        String safeKey = ObjectName.quote(beanKey);

        return new ObjectName(
            "com.example.orders:type=" + ObjectName.quote(type)
                + ",name=" + safeKey
        );
    }
}
```

In Spring, `beanKey` can be the bean name or key from exporter configuration. This example illustrates using a fixed domain and distinguishing type/instance; real applications must account for proxy classes, stable key values, and quoting rules. In particular, if the bean is a Spring AOP proxy, `getClass().getSimpleName()` may be the proxy name rather than the business class name: a real strategy should retrieve the target class or appropriate metadata.

Registering the strategy:

```java
MBeanExporter exporter = new MBeanExporter();
exporter.setNamingStrategy(new ApplicationNamingStrategy());
```

Use a custom strategy only when default conventions are insufficient. Explicit names are usually easier to operate when the number of MBeans is small and fixed.

7. Try registering the same ObjectName twice into the same server and observe the conflict.
8. Try registering the same ObjectName into two independent `MBeanServer`s and explain why they can coexist.

A small verification snippet:

```java
import javax.management.MBeanServer;
import javax.management.MBeanServerFactory;
import javax.management.ObjectName;

MBeanServer isolated =
    MBeanServerFactory.newMBeanServer(
        "com.example.management"
    );

System.out.println(isolated.getDefaultDomain());

ObjectName explicit = new ObjectName(
    "com.example.orders:type=OrderWorker,name=Primary"

System.out.println(explicit.getDomain());
// com.example.orders; does not automatically change to the default domain.
```

In practice, to verify a registered MBean, you need an actual MBean instance and must call `registerMBean` or export via Spring. Creating an `ObjectName` alone does not register an MBean.

## 17. Self-Check Questions

**1. What is the general structure of an ObjectName?** Domain and key properties, e.g., `domain:type=Worker,name=Main`.

**2. What problem does a domain solve?** Grouping MBean namespaces and reducing name collisions within a server.

**3. Does an MBeanServer's default domain force every ObjectName to change domain?** No, ObjectNames with an explicit domain keep that domain.

**4. Does `MetadataNamingStrategy.setDefaultDomain(...)` change the server default domain?** No, it affects ObjectName generation rules on the Spring side.

**5. Is an ObjectName unique across JVMs?** No, it is unique within each `MBeanServer`.

**6. If the exporter uses a private server, why does JConsole connected to the platform server not see the MBean?** Because they are two different registries, unless the connector/client points to the private server.

**7. Does a domain automatically protect MBeans from clients?** No, security depends on connectors and authorization.

**8. When should explicit ObjectNames be used?** When the naming contract is fixed, there are few MBeans, and operators need predictable exact names.

**9. Why be careful when using class names in a custom naming strategy?** Proxies and class renames can change identity unintentionally.

**10. Is changing a domain just changing a description?** No, it changes the ObjectName and can affect consumers.

## 18. Key Takeaways

- **Domain is part of an ObjectName**, while key properties distinguish types and instances.
- **An application's JMX namespace** should be stable, clear, and free of sensitive data.
- **`MBeanServer.getDefaultDomain()`** describes the server's default domain; it does not override ObjectNames that already have an explicit domain.
- **`MetadataNamingStrategy.setDefaultDomain(...)`** assists generating names from metadata on the Spring side and differs from server configuration.
- **`MBeanServerFactoryBean`** can create a server with its own default domain, but does not automatically enable JMX Remote.
- **`MBeanExporter` + naming strategy** determines the final registered ObjectName.
- The same ObjectName can exist on different `MBeanServer`s; multi-server clients must also track connection identity.
- Changing a domain or key property changes the **management identity**, not merely a display label.

Understanding `defaultDomain` and namespaces helps Spring JMX maintain searchable naming systems, reduce registration collisions, and keep management tools working stably across deployments.
