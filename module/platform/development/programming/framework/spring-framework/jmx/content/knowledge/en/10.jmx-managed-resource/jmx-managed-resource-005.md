# Scope of @ManagedResource on Proxies and Target Classes in Spring JMX

## 1. Why Are Annotations on Proxied Beans Confusing?

In Spring Framework, a bean declared with \`@Component\` can be wrapped by an AOP proxy to handle transactions, security, caching, tracing, or other advice. In that case, the object returned by \`ApplicationContext.getBean(...)\` does not necessarily have the same runtime class as the business implementation class.

For example, class \`InventoryAdminService\` is marked with \`@ManagedResource\`, yet at runtime Spring returns a JDK dynamic proxy with a class like \`jdk.proxy2.$Proxy...\` or a proxy generated by CGLIB. If the MBean export mechanism reads annotations, methods, and interfaces from different class types, the following can happen:

- The exporter fails to detect the bean marked with \`@ManagedResource\`.
- \`ObjectName\` is not resolved as expected.
- The MBean is registered but lacks attributes or operations.
- A method is not exposed by the proxy and therefore cannot be invoked through the proxy.
- Startup reports errors about compliance, introspection, or reflection.

You must distinguish **the annotated class**, **the bean's runtime class**, **the target class represented by AOP**, and **the interfaces implemented by the proxy**. \`@ManagedResource\` does not automatically make every proxy expose every method of the target.

## 2. Four Layers to Observe

\`\`\`text
Spring ApplicationContext
        |
        v
Bean reference returned to MBeanExporter
        |
        +-- Runtime bean class: JDK Proxy / CGLIB Proxy / plain class
        |
        +-- Target class: implementation carrying @ManagedResource
        |
        +-- Introduced / implemented interfaces
        |
        +-- Eligible methods visible to the proxy
        |
        v
JMX metadata source + MBeanInfo assembler
        |
        v
ObjectName + attributes + operations
        |
        v
MBeanServer registration
\`\`\`

**Target class** is the application class wrapped by the proxy. With a JDK dynamic proxy, callers can typically only invoke methods on the interfaces implemented by the proxy. With a CGLIB class-based proxy, the proxy is a subclass of the target class, but has limitations with \`final\`, \`private\`, and non-overridable methods.

Spring JMX uses the exporter's metadata mechanism rather than relying solely on raw Java reflection on \`bean.getClass()\`. Therefore, you should not assume annotations on the target are always lost when a JDK proxy is present. Exact results depend on the metadata source, assembler, Spring configuration, proxy type, and which methods are accessible through the actual bean.

## 3. Example of a Class Both JMX-Managed and AOP-Advised

\`\`\`java
package com.example.inventory;

import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedOperation;
import org.springframework.jmx.export.annotation.ManagedResource;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@ManagedResource(
    objectName = "com.example.inventory:type=InventoryAdmin,name=Primary",
    description = "Inventory management endpoint"
)
public class InventoryAdminService implements InventoryAdminOperations {
    private volatile boolean paused;

    @Override
    @ManagedAttribute(description = "Background import paused")
    public boolean isPaused() {
        return paused;
    }

    @Override
    @Transactional
    @ManagedOperation(description = "Pause background import")
    public void pauseImport() {
        paused = true;
    }
}
\`\`\`

Interface:

\`\`\`java
package com.example.inventory;

public interface InventoryAdminOperations {
    boolean isPaused();
    void pauseImport();
}
\`\`\`

If Spring creates a **JDK proxy** due to transaction advice, the proxy may only expose the two interface methods. Additional public methods on the implementation that are not on the interface will not necessarily be invocable through that proxy.

If a **class-based proxy** (often called a CGLIB proxy) is used, public/protected methods can be represented by the proxy when override conditions are met. Do not equate class-based proxies with every method being intercepted: \`final\` or \`private\` methods cannot be overridden, and self-invocation within the same target normally bypasses proxy advice.

Even if JMX annotations can be read from the target, invoking an operation goes through the bean instance registered by the exporter. You must confirm that **both metadata and invocability** match.

## 4. @ManagedResource, @ManagedAttribute, and @ManagedOperation Have Distinct Roles

Spring JMX annotations are typically used in two layers:

- \`@ManagedResource\` marks a bean/class as a management resource and can carry \`objectName\`, \`description\`, \`currencyTimeLimit\`, and other metadata.
- \`@ManagedAttribute\` declares a getter/setter presented as a JMX attribute.
- \`@ManagedOperation\` declares a method exported as a JMX operation.
- \`@ManagedOperationParameter\` provides parameter metadata for an operation when needed.

Having \`@ManagedResource\` on a class alone does not mean every public method automatically becomes a JMX operation. When using a metadata assembler, methods must be selected according to annotations and corresponding rules.

A proxied bean must still be recognized by the exporter as an eligible resource; annotations on the target class are the source of business metadata, while **annotation visibility when inspecting a proxy** is a configuration/framework question. Use real tests on your project's Spring version rather than relying purely on \`proxy.getClass().isAnnotationPresent(...)\`.

## 5. JDK Dynamic Proxy: Only Interface Methods Are Available

A bean with an interface:

\`\`\`java
public interface InventoryAdminOperations {
    boolean isPaused();
    void pauseImport();
}
\`\`\`

And the target has a public method outside the interface:

\`\`\`java
@ManagedOperation
public void forceRebuildInternalIndex() {
    // ...
}
\`\`\`

If the exporter registers the JDK proxy itself, \`forceRebuildInternalIndex()\` does not belong to the interfaces implemented by the proxy. The metadata assembler finding the annotation on the target does not guarantee Java reflection can invoke the operation through the proxy.

Design approaches:

1. Expose only the needed management methods and declare them on an interface implemented by the JDK proxy if you want to use the proxied bean directly.
2. Or create a **dedicated management adapter** not wrapped by business proxies, inject an application service interface, and put \`@ManagedResource\` on the adapter.
3. If class-based proxies are needed, understand the impact of \`proxyTargetClass=true\` across the whole application and choose it only when genuinely appropriate.

Do not switch all transaction AOP to class-based proxies just to fix a missing MBean method when separating a JMX adapter is cleaner and more stable.

## 6. CGLIB Proxy and Target Annotations

With class-based proxies, the runtime class is typically a generated subclass. Target annotations can be found by Spring metadata inspection via the user class/target class; however, check each specific annotation and resolver.

Avoid relying solely on:

\`\`\`java
boolean present =
    bean.getClass().isAnnotationPresent(ManagedResource.class);
\`\`\`

A \`false\` result on the proxy runtime class **does not prove** Spring JMX cannot read the annotation. To diagnose, also compare:

\`\`\`java
import org.springframework.aop.support.AopUtils;
import org.springframework.core.annotation.AnnotatedElementUtils;
import org.springframework.jmx.export.annotation.ManagedResource;

Object bean = context.getBean("inventoryAdminService");

Class<?> runtimeClass = bean.getClass();
Class<?> targetClass = AopUtils.getTargetClass(bean);

boolean runtimeAnnotated =
    AnnotatedElementUtils.hasAnnotation(
        runtimeClass, ManagedResource.class
    );

boolean targetAnnotated =
    AnnotatedElementUtils.hasAnnotation(
        targetClass, ManagedResource.class
    );

System.out.println(runtimeClass.getName());
System.out.println(targetClass.getName());
System.out.println(runtimeAnnotated + " / " + targetAnnotated);
\`\`\`

\`AopUtils.getTargetClass\` helps identify the target class when the proxy is recognized by Spring AOP. When an application has nested proxies or proxies created by external libraries, you may need to trace multiple proxy layers and inspect the actual bean received by the exporter.

## 7. How Does Spring's Exporter Read Annotations?

When using Spring JMX annotations, a typical configuration consists of \`AnnotationJmxAttributeSource\`, \`MetadataMBeanInfoAssembler\`, and \`MetadataNamingStrategy\` (or a concise configuration supported by the framework):

\`\`\`java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jmx.export.MBeanExporter;
import org.springframework.jmx.export.annotation.AnnotationJmxAttributeSource;
import org.springframework.jmx.export.assembler.MetadataMBeanInfoAssembler;
import org.springframework.jmx.export.naming.MetadataNamingStrategy;

@Configuration
public class JmxConfiguration {
    @Bean
    AnnotationJmxAttributeSource jmxAttributeSource() {
        return new AnnotationJmxAttributeSource();
    }

    @Bean
    MBeanExporter mbeanExporter(
            AnnotationJmxAttributeSource source) {
        MetadataMBeanInfoAssembler assembler =
            new MetadataMBeanInfoAssembler();
        assembler.setAttributeSource(source);

        MetadataNamingStrategy naming =
            new MetadataNamingStrategy();
        naming.setAttributeSource(source);

        MBeanExporter exporter = new MBeanExporter();
        exporter.setAssembler(assembler);
        exporter.setNamingStrategy(naming);
        exporter.setAutodetect(true);
        return exporter;
    }
}
\`\`\`

The example uses one exporter to illustrate the roles of the three components. If Spring Boot already auto-configures an MBeanExporter, do not declare an additional exporter with overlapping responsibility without checking auto-configuration. In plain Spring Framework, \`@EnableMBeanExport\` is also a concise configuration option when appropriate.

Distinguish **reading metadata** from **invoking methods**: the assembler may find metadata on the target class, yet the registered object must still support invocation across the exported surface.

## 8. Stable Approach: Separating a JMX Adapter from the Business Service

To prevent transaction/security proxies from complicating MBean export, a dedicated management adapter usually provides a clear boundary:

\`\`\`java
package com.example.inventory.jmx;

import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedOperation;
import org.springframework.jmx.export.annotation.ManagedResource;
import org.springframework.stereotype.Component;

@Component
@ManagedResource(
    objectName = "com.example.inventory:type=Import,name=Primary"
)
public final class InventoryJmxAdapter {
    private final InventoryAdminOperations operations;

    public InventoryJmxAdapter(InventoryAdminOperations operations) {
        this.operations = operations;
    }

    @ManagedAttribute(description = "Import processing paused")
    public boolean isPaused() {
        return operations.isPaused();
    }

    @ManagedOperation(description = "Pause import")
    public void pause() {
        operations.pauseImport();
    }
}
\`\`\`

The \`InventoryAdminOperations\` bean may be a JDK proxy created by Spring for transactions/security. The adapter only calls methods declared on the interface, so calls still flow through the proxy advice normally.

Benefits:

- JMX annotations stay in the infrastructure layer without leaking into the domain model.
- The exporter introspects an adapter with a small, rarely changing surface.
- The business service can change its AOP strategy without changing the JMX contract.
- Easy to unit-test the adapter with a fake interface and test JMX registration separately.
- Dangerous operations can enforce control policies at the management gateway instead of exposing every public method of the service.

A JMX adapter itself can also be proxied if advice is attached directly to it or if a broad pointcut matches it. When needed, inspect the actual adapter bean in the Spring context; do not assume the adapter is always a plain class.

## 9. Do Not Confuse Proxies with Losing Transactions or Security

If the business service has \`@Transactional\` or \`@PreAuthorize\`, the adapter should inject the **Spring-managed proxy**, rather than instantiating \`new InventoryAdminService()\` and calling the target directly. Manual instantiation bypasses transaction/security advice, dependency injection, and lifecycle.

\`\`\`java
@Component
public class InventoryJmxAdapter {
    private final InventoryAdminOperations operations;

    public InventoryJmxAdapter(InventoryAdminOperations operations) {
        this.operations = operations; // Bean/proxy from Spring container
    }
}
\`\`\`

JMX commands can be invoked from external clients; authentication at the JMX connector and authorization checks in the application must be explicitly designed. Spring Security method advice sometimes relies on the HTTP request's security context, which is not automatically present on a JMX thread. Use an appropriate management policy rather than assuming every \`@PreAuthorize\` will have the same user context as a web request.

## 10. How to Diagnose Proxied Beans and Targets in an Application

A small probe:

\`\`\`java
import org.springframework.aop.support.AopUtils;
import org.springframework.context.ApplicationContext;

public final class ProxyProbe {
    public static void describe(
            ApplicationContext context, String beanName) {
        Object bean = context.getBean(beanName);

        System.out.println("Bean: " + beanName);
        System.out.println("Runtime: " + bean.getClass().getName());
        System.out.println("AOP proxy: " + AopUtils.isAopProxy(bean));
        System.out.println("JDK proxy: " + AopUtils.isJdkDynamicProxy(bean));
        System.out.println("CGLIB proxy: " + AopUtils.isCglibProxy(bean));
        System.out.println("Target: " +
            AopUtils.getTargetClass(bean).getName());
    }
}
\`\`\`

Then inspect on the right \`MBeanServer\`:

\`\`\`java
import java.lang.management.ManagementFactory;
import javax.management.MBeanServer;
import javax.management.ObjectName;

MBeanServer server = ManagementFactory.getPlatformMBeanServer();
ObjectName name = new ObjectName(
    "com.example.inventory:type=Import,name=Primary"
);

System.out.println("Registered: " + server.isRegistered(name));

if (server.isRegistered(name)) {
    var info = server.getMBeanInfo(name);

    for (var attribute : info.getAttributes()) {
        System.out.println(attribute.getName());
    }

    for (var operation : info.getOperations()) {
        System.out.println(operation.getName());
    }
}
\`\`\`

If the exporter registers on a custom server, use that instance instead of the platform server. \`isRegistered=true\` proves the MBean name exists, but does not prove every method is invocable through the proxy; continue verifying with \`getAttribute\` and \`invoke\` in integration tests.

## 11. Symptom and Root-Cause Matrix

| Symptom | High-Probability Cause | Verification Check |
| --- | --- | --- |
| Annotation appears on target but not on proxy class | Metadata lives on implementation | Compare runtime class and \`AopUtils.getTargetClass\` |
| MBean is not exported | Misconfigured autodetect/annotation metadata/exporter | Check exporter, \`@ManagedResource\`, Spring context |
| MBean exists but is missing operations | Method is not on proxy interface or assembler misses annotation | \`getMBeanInfo\`, inspect JDK proxy interfaces |
| \`NotCompliantMBeanException\` | Exporter registers POJO/proxy using Standard MBean rules | Check registration path and assembler |
| \`ReflectionException\` when invoking operation | Proxy does not expose method or signature mismatch | \`invoke\` with exact signature |
| Enabling AOP breaks JMX | Runtime bean type changes when advice is applied | Compare class/proxy before and after |
| JMX works but transactions do not run | Calling target directly or self-invocation bypasses proxy | Check where bean is injected and call path |

Do not apply a single "cure-all" to every symptom. For example, changing \`proxyTargetClass\` might expose a method, but will not fix a duplicate \`ObjectName\` or a disabled exporter.

## 12. Testing Annotations on Real Proxies

An integration test can retrieve the bean from the Spring context, verify the proxy, and invoke JMX:

\`\`\`java
import static org.junit.jupiter.api.Assertions.*;
import javax.management.MBeanServer;
import javax.management.ObjectName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.aop.support.AopUtils;

@SpringBootTest(properties = "spring.jmx.enabled=true")
class InventoryJmxIntegrationTest {
    @Autowired
    InventoryAdminOperations operations;

    @Autowired
    MBeanServer mbeanServer;

    @Test
    void exposesManagementOperationThroughMBeanServer()
            throws Exception {
        ObjectName name = new ObjectName(
            "com.example.inventory:type=Import,name=Primary"
        );

        assertTrue(mbeanServer.isRegistered(name));
        assertNotNull(operations);

        Object paused = mbeanServer.getAttribute(name, "Paused");
        assertTrue(paused instanceof Boolean);

        mbeanServer.invoke(
            name, "pause", new Object[0], new String[0]
        );
        assertTrue(operations.isPaused());
    }
}
\`\`\`

This is an integration pattern for applications with Spring Boot Test, AOP, JMX, and an appropriate \`MBeanServer\` bean; adjust configuration and packages to match your project. \`AopUtils.isAopProxy(operations)\` can be asserted when the test intentionally enables advice/proxying; do not assert mandatory proxying across all configurations.

When using the platform \`MBeanServer\` in tests running in parallel, contexts with the same \`ObjectName\` can collide. Use a separate JMX domain or instance key for tests, and close the context after the test.

## 13. Unit Testing the Adapter Without a JMX Server

To test mapping logic independently of proxies:

\`\`\`java
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class InventoryJmxAdapterTest {
    @Test
    void delegatesToManagementPort() {
        class Fake implements InventoryAdminOperations {
            boolean paused;

            public boolean isPaused() {
                return paused;
            }

            public void pauseImport() {
                paused = true;
            }
        }

        Fake fake = new Fake();
        InventoryJmxAdapter adapter = new InventoryJmxAdapter(fake);

        assertFalse(adapter.isPaused());
        adapter.pause();
        assertTrue(fake.paused);
        assertTrue(adapter.isPaused());
    }
}
\`\`\`

This unit test confirms the adapter delegates properly; it does not prove the exporter reads annotations or that proxies are compatible. The two questions require two separate test layers.

## 14. Common Design Mistakes

**Putting JMX annotations directly on entities/domain services.** The domain becomes coupled to management and proxies; move JMX into an adapter if the architecture requires separation.

**Checking annotations via \`bean.getClass()\` and concluding they are absent.** The proxy class may differ from the target class; use Spring metadata utilities and verify the actual exporter.

**Annotating methods on the implementation while exposing a different interface.** JDK proxies only present the interfaces they implement. Design the corresponding interface or a dedicated adapter.

**Bypassing AOP by calling \`new TargetService()\`.** This drops advice and can break transactions/security. Inject the Spring bean via its interface.

**Enabling class-based proxies across the entire project to fix JMX.** Changing the AOP strategy can affect many beans; prefer isolating the JMX surface.

**Assuming every operation works because the MBean appears in the UI.** Metadata and invocation must be verified separately.

**Assuming annotations on interfaces and classes are always handled identically.** Java annotation inheritance, method resolution, and Spring metadata merging have their own rules. Choose a consistent annotation placement and verify against your deployed Spring version.

## 15. Guide to Choosing Annotation Placement

| Location | Meaning | Recommendation |
| --- | --- | --- |
| Domain class | Mixes management into the domain | Avoid in layered architectures |
| Business service implementation | Convenient with few classes, but affected by AOP proxies | Only when scope is small and integration-tested |
| Business interface | Can affect all callers and is not always interpreted as expected by metadata sources | Do not use as the default home for JMX metadata |
| Management adapter class | Clear boundary, easy to control the JMX contract | Preferred choice |
| Standard MBean interface (\`*MBean\`) | Standard Java JMX contract, no Spring annotations needed | Suitable when using Standard MBeans |

The key point is not which proxy type is "better", but **where MBeanExporter reads annotations and whether the object it registers actually supports the described operations**.

## 16. Key Takeaways

\`@ManagedResource\` attaches management metadata to a bean/class, while Spring AOP can turn the runtime object into a JDK dynamic proxy or CGLIB proxy. When proxies are involved, examine **target annotations**, **proxy-exposed methods**, **exporter metadata resolution**, and **MBeanServer invocation** separately. A dedicated JMX adapter injecting an application interface through Spring avoids most dependencies on proxy details and keeps business logic independent of the management protocol.
