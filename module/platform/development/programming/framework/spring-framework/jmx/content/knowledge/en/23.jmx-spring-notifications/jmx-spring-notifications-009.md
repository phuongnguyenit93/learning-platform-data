# Synchronous, Asynchronous, and Threading in JMX Notification Listeners in Spring Framework

## 1. Lesson Objectives

JMX Notifications allow an MBean to emit management events such as a worker changing state, a queue crossing a threshold, or a maintenance task completing. A `NotificationListener` receives notifications through the `handleNotification(Notification, Object)` method. In Spring Framework, an application can declare listeners and register them with MBeans using `MBeanExporter` or `NotificationListenerBean`.

When designing a listener, the critical question is not only **whether notifications arrive**, but also:

- Which thread does the callback execute on?
- Does sending a notification wait for the listener to finish processing?
- Can a slow listener block the notification-emitting code?
- Do multiple listeners run sequentially or concurrently?
- How do exceptions in a listener affect the emitter and other listeners?
- When a listener processes asynchronously, how do you control ordering, queues, backpressure, and shutdown?
- When a JMX client is remote, which threads and network paths does the callback traverse?

After this lesson, you will be able to distinguish the synchronous/asynchronous semantics of **notification dispatch** and **business processing**, configure listeners safely for Spring applications, and test threading, ordering, errors, and lifecycle.

## 2. What Is a Notification?

A JMX Notification is an object extending `javax.management.Notification` with common fields:

| Property | Meaning |
|---|---|
| `type` | Event type, e.g., `training.worker.paused` |
| `source` | Emitting object |
| `sequenceNumber` | Sequence number assigned by the emitter |
| `timeStamp` | Time the notification was created |
| `message` | Human-readable description for operators |
| `userData` | Supplemental data if needed |

An MBean can emit notifications by using `NotificationBroadcasterSupport` or implementing the corresponding JMX interfaces.

Receivers use:

```java
public interface NotificationListener {
    void handleNotification(Notification notification, Object handback);
}
```

The `handback` value is supplied by the listener registrar; it is not an event payload automatically generated by the emitter.

Basic diagram:

```text
Management event
      |
      v
MBean / NotificationEmitter
      |
      | sendNotification(...)
      v
JMX notification dispatch
      |
      +-- listener A
      +-- listener B
      +-- listener C
```

Do not treat notifications as a durable message queue with built-in retries, acknowledgments, and persistence. JMX notifications primarily support management signaling, not replacing a messaging system when delivery guarantees are needed.

## 3. Synchronous and Asynchronous Have Two Distinct Layers

You must separate:

1. **The JMX dispatch layer:** how a notification is delivered from the broadcaster to `NotificationListener`.
2. **The business-processing layer inside the listener:** whether the callback processes immediately or only enqueues work for another executor.

Example:

```text
Event-emitting thread
    |
    v
sendNotification()
    |
    +-- Synchronous: call listener.handleNotification() directly
    |
    +-- Asynchronous: offload callback to Executor
                          |
                          v
                    Worker thread
```

Even when JMX dispatch is synchronous, the listener can still enqueue work itself and return quickly. Conversely, you might have an executor dispatching asynchronously yet run a long task inside the listener, congesting the broadcaster's thread pool.

**Important:** the behavior of `NotificationBroadcasterSupport` depends on the constructor and `Executor` provided. By default, when no separate executor is set, notifications are sent synchronously on the thread calling `sendNotification`. When an executor is provided, the broadcaster delegates notification tasks according to that executor's behavior. Ordering/concurrency behavior depends on the executor, not on JMX automatically guaranteeing sequentiality across every configuration.

## 4. Synchronous: Listener Runs on the Notification-Emitting Thread

Simple example:

```java
import javax.management.Notification;
import javax.management.NotificationBroadcasterSupport;
import javax.management.NotificationListener;
import java.util.concurrent.atomic.AtomicLong;

public class WorkerEmitter extends NotificationBroadcasterSupport {
    private final AtomicLong sequence = new AtomicLong();

    public void pause() {
        Notification notification = new Notification(
            "training.worker.paused",
            this,
            sequence.incrementAndGet(),
            System.currentTimeMillis(),
            "Worker paused"
        );
        sendNotification(notification);
    }

    public static void main(String[] args) {
        WorkerEmitter emitter = new WorkerEmitter();

        NotificationListener listener = (n, handback) -> {
            System.out.println(
                "Listener thread: " +
                Thread.currentThread().getName());
            try {
                Thread.sleep(500);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        };

        emitter.addNotificationListener(listener, null, null);

        long started = System.nanoTime();
        emitter.pause();
        long durationMs =
            (System.nanoTime() - started) / 1_000_000L;

        System.out.println("Duration ms: " + durationMs);
    }
}
```

In synchronous dispatch, `pause()` must wait for the callback to finish, so the execution time includes the listener's sleep duration.

### 4.1. Pros

- Simple logic, easy to observe threading.
- No need to configure a separate executor and queue.
- Listener completes before `sendNotification` returns, barring special exceptions/behavior.
- Useful when the callback is very short, such as updating a counter or lightweight logging.

### 4.2. Cons

- A slow listener increases latency for the notification-emitting method.
- If the code sending the notification holds a lock, a long-running listener can increase contention or cause deadlock.
- A listener calling a network, database, or blocking I/O can stall critical threads.
- Listeners can affect each other's latency if the broadcaster dispatches sequentially.

**Recommendation:** synchronous callbacks should be short, non-blocking, and not dependent on external systems lacking timeouts.

## 5. Asynchronous via NotificationBroadcasterSupport's Executor

The JDK provides a constructor accepting an `Executor`. Example:

```java
import javax.management.Notification;
import javax.management.NotificationBroadcasterSupport;
import javax.management.NotificationListener;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicLong;

public final class AsyncWorkerEmitter
        extends NotificationBroadcasterSupport
        implements AutoCloseable {

    private final ExecutorService executor;
    private final AtomicLong sequence = new AtomicLong();

    public AsyncWorkerEmitter(ExecutorService executor) {
        super(executor);
        this.executor = executor;
    }

    public void signal(String message) {
        Notification notification = new Notification(
            "training.worker.signal",
            this,
            sequence.incrementAndGet(),
            System.currentTimeMillis(),
            message);
        sendNotification(notification);
    }

    @Override
    public void close() {
        executor.shutdown();
    }

    public static void main(String[] args) throws Exception {
        ExecutorService executor =
            Executors.newSingleThreadExecutor(r -> {
                Thread t = new Thread(r, "jmx-notify-worker");
                t.setDaemon(true);
                return t;
            });

        try (AsyncWorkerEmitter emitter =
                 new AsyncWorkerEmitter(executor)) {
            emitter.addNotificationListener(
                (n, h) -> System.out.println(
                    "Thread = " +
                    Thread.currentThread().getName() +
                    ", message=" + n.getMessage()),
                null, null);

            emitter.signal("ready");
            Thread.sleep(300);
        }
    }
}
```

When an executor accepts tasks, `sendNotification` can return before the callback runs. An `ExecutorService` still requires proper lifecycle and shutdown, especially if Spring manages the broadcaster as a bean. In the demo example, sleep is solely for visual observation; real tests should use `CountDownLatch` instead of relying on sleep durations.

### 5.1. Single Thread or Multiple Threads?

- Single-thread executor: generally preserves task execution order by submission order and reduces contention between callbacks.
- Fixed-thread pool: can process concurrently, increasing throughput, though callback completion does not necessarily match sequence order.
- Bounded thread pool/queue: helps control resources when notification volume rises.
- Unbounded queue: easily increases memory usage if the producer outpaces the consumer.

Choose the executor based on callback characteristics and notification volume rather than defaulting to a large pool to be "faster."

## 6. Spring Managing Listeners via NotificationListenerBean

Spring Framework supports `org.springframework.jmx.export.notification.NotificationListenerBean`, allowing you to combine a listener, filter, handback, and monitored MBean mappings. Configuration example using `MBeanExporter`:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jmx.export.MBeanExporter;
import org.springframework.jmx.export.notification.NotificationListenerBean;

import javax.management.MBeanServer;
import javax.management.NotificationListener;
import javax.management.ObjectName;
import java.util.Map;

@Configuration
public class JmxNotificationConfig {

    @Bean
    public NotificationListener workerNotificationListener() {
        return (notification, handback) -> {
            System.out.println(
                "Received: " + notification.getType());
        };
    }

    @Bean
    public NotificationListenerBean workerListenerBean(
            NotificationListener workerNotificationListener)
            throws Exception {

        NotificationListenerBean bean =
            new NotificationListenerBean();
        bean.setNotificationListener(workerNotificationListener);
        bean.setMappedObjectNames(
            new ObjectName(
                "training.spring:type=Worker,name=Primary"));
        return bean;
    }

    @Bean
    public MBeanExporter mbeanExporter(
            MBeanServer mbeanServer,
            WorkerManagement worker,
            NotificationListenerBean workerListenerBean) {

        MBeanExporter exporter = new MBeanExporter();
        exporter.setServer(mbeanServer);
        exporter.setBeans(Map.of(
            "training.spring:type=Worker,name=Primary", worker));
        exporter.setNotificationListeners(workerListenerBean);
        return exporter;
    }
}
```

`WorkerManagement` is an MBean-compatible class/bean that must be defined to emit notifications, such as extending `NotificationBroadcasterSupport` or using Spring's notification publisher mechanism. The configuration snippet illustrates listener wiring; if the application already has an automatic exporter, avoid declaring a second exporter registering the same ObjectName.

**Note:** Spring does not make a listener's callback asynchronous just because the listener is declared as a Spring bean. The execution thread depends on the broadcaster, connector, and how the listener itself handles work.

## 7. Spring NotificationPublisher and the Event-Emitting Thread

Spring JMX provides a way to emit notifications via `NotificationPublisher` when a bean implements `NotificationPublisherAware` under an appropriate exporter configuration.

Example:

```java
import org.springframework.jmx.export.annotation.ManagedOperation;
import org.springframework.jmx.export.annotation.ManagedResource;
import org.springframework.jmx.export.notification.NotificationPublisher;
import org.springframework.jmx.export.notification.NotificationPublisherAware;

import javax.management.Notification;
import java.util.concurrent.atomic.AtomicLong;

@ManagedResource(
    objectName = "training.spring:type=Worker,name=Primary")
public class WorkerManagement implements NotificationPublisherAware {

    private NotificationPublisher publisher;
    private final AtomicLong sequence = new AtomicLong();

    @Override
    public void setNotificationPublisher(
            NotificationPublisher publisher) {
        this.publisher = publisher;
    }

    @ManagedOperation
    public void pause() {
        Notification n = new Notification(
            "training.worker.paused",
            this,
            sequence.incrementAndGet(),
            System.currentTimeMillis(),
            "Paused via JMX");
        publisher.sendNotification(n);
    }
}
```

To expose notification metadata to clients, Spring supports `@ManagedNotification` in an appropriate annotation-based export configuration. When `pause()` is invoked via JMX, the thread executing the operation may be a thread serving the connector. If dispatch to the listener is synchronous and the callback is slow, the client may experience slower `invoke("pause")` calls.

```text
Remote JMX request thread
        |
        v
WorkerManagement.pause()
        |
        v
publisher.sendNotification()
        |
        v
Slow synchronous listener
        |
        v
pause() finally returns
        |
        v
Remote JMX client receives result
```

Therefore, exercise caution when notifications are emitted inside critical management operations.

## 8. Asynchronous Listener by Enqueueing Work

You do not necessarily have to configure an executor on the broadcaster. Another approach is for the listener to accept the notification quickly and push heavy processing onto a queue:

```java
import javax.management.Notification;
import javax.management.NotificationListener;
import java.util.concurrent.Executor;

public final class EnqueueingListener implements NotificationListener {
    private final Executor executor;

    public EnqueueingListener(Executor executor) {
        this.executor = executor;
    }

    @Override
    public void handleNotification(
            Notification notification, Object handback) {

        String type = notification.getType();
        long sequence = notification.getSequenceNumber();

        executor.execute(() ->
            process(type, sequence));
    }

    private void process(String type, long sequence) {
        System.out.printf(
            "Processed %s sequence=%d%n",
            type, sequence);
    }
}
```

Here the callback only takes a snapshot of the needed fields and submits a task. This reduces synchronous callback duration, but still has considerations:

- The executor may reject tasks (`RejectedExecutionException`).
- The queue may fill up.
- A notification may be processed after the resource has already changed.
- Tasks may fail, requiring separate logs and metrics.
- Shutdown may lose tasks remaining in the queue.

For mutable payloads in `userData`, do not pass shared references to another thread without a thread-safety contract. Convert to an immutable DTO/snapshot.

## 9. Notification Ordering and Concurrency

A JMX Notification has `sequenceNumber`, but you cannot assume every listener **finishes processing in sequence order** across all configurations.

Example:

```text
Notification #101 -> Thread A (work 2 seconds)
Notification #102 -> Thread B (work 100 ms)

Completion:
  #102 finishes before #101
```

With a multi-threaded executor, this is normal. If an operation requires ordering guarantees, consider:

1. A single-thread executor per source/event stream.
2. Partitioning queues by resource ID so each resource is processed sequentially.
3. Using sequence/idempotency to detect out-of-order events.
4. Designing a state machine that checks version before applying changes.
5. Avoiding using notifications as a mandatory state-update protocol without delivery guarantees.

Sequence numbers can be generated by the broadcaster/managed bean per application policy. Do not assume a globally unique sequence across the JVM or distributed system.

### 9.1. Having Multiple Listeners

A broadcaster can have multiple listeners:

```text
Emitter
   +--> AuditListener
   +--> MetricsListener
   +--> AlertListener
```

If one listener is slow, synchronous dispatch can slow down overall notification delivery. With a shared executor, a listener occupying a thread for a long time can still make other listeners wait in the queue. For isolation, use separate executors or lightweight listeners that only enqueue to independent systems.

## 10. NotificationFilter and Handback

When registering a listener:

```java
emitter.addNotificationListener(
    listener,
    notification -> notification.getType()
        .startsWith("training.worker."),
    "worker-tag");
```

- `NotificationFilter` decides which notifications are forwarded to the listener.
- `handback` is an object returned to the callback to carry registration context.
- Filters can execute on the dispatch path, so they must also be short and non-blocking.

Do not pass secrets into `handback` if logs, debugging, or untrusted client code could inspect it. Remote JMX adds serialization and access-control constraints; test separately if using a complex handback.

## 11. Exceptions in Listeners

A listener might throw a `RuntimeException`:

```java
NotificationListener listener = (n, h) -> {
    throw new IllegalStateException("failed");
};
```

With `NotificationBroadcasterSupport`, how listener exceptions are handled depends on the dispatcher/JMX implementation. Do not assume an exception will destroy the emitter or be visible to a remote client as a business exception of the operation. Verify the concrete behavior of your broadcaster and executor.

A robust listener should proactively isolate errors:

```java
public void handleNotification(Notification n, Object handback) {
    try {
        processNotification(n);
    } catch (RuntimeException ex) {
        logger.error(
            "Failed handling JMX notification type={}",
            n.getType(),
            ex);
        metrics.recordListenerFailure(n.getType());
    }
}
```

This is illustrative code; `logger` and `metrics` must be defined/injected in the application.

### 11.1. Do Not Swallow Errors Completely

If errors are merely caught and ignored, the system loses observability. Use proper logging, error counters, alerts when error rates are high, and conditional retry mechanisms if notifications are processed as external tasks.

### 11.2. Retries and Idempotency

JMX notifications do not have built-in durable ack/retry. When handling errors, if retries are needed, you must manage idempotency yourself and ensure no duplicate side effects occur. For critical data, replace JMX notifications with a message broker/event log capable of persistence and retries.

## 12. Backpressure and Queue Limits

When the producer emits faster than the listener processes:

```text
Notification producer: 1000 events/s
Listener processing:   100 events/s
Backlog growth:        900 events/s
```

An unbounded queue can cause memory pressure. Example creating a bounded executor:

```java
import java.util.concurrent.*;

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2, 2,
    0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(200),
    r -> {
        Thread t = new Thread(r, "jmx-listener-worker");
        t.setDaemon(true);
        return t;
    },
    new ThreadPoolExecutor.AbortPolicy());
```

`AbortPolicy` throws `RejectedExecutionException` when no more tasks can be accepted. The listener must define an overload policy: report an error, drop with metrics, offload to a durable queue, or apply controlled producer blocking. Do not use `CallerRunsPolicy` without understanding that it can run the callback on the notification-emitting thread, turning an ostensibly async design back into synchronous when the queue fills up.

### 12.1. Set Measurable Limits

Monitor:

- Number of notifications emitted/received.
- Queue depth.
- Active executor threads.
- Processing latency P50/P95/P99.
- Number of rejected tasks.
- Number of listener errors.
- Shutdown time with pending work remaining.

Do not attach sensitive payloads to metric labels.

## 13. Deadlock and Lock Contention

A hard-to-diagnose risk:

```text
Thread A holds lock L
   |
   +-- sendNotification()
         |
         +-- synchronous listener
               |
               +-- tries to acquire lock M

Thread B holds lock M
   |
   +-- waits for lock L
```

This wait cycle creates a deadlock. Even without deadlock, a slow listener inside a `synchronized` block can increase latency.

Mitigations:

1. Avoid emitting notifications while holding long locks whenever possible.
2. Use immutable snapshots for event payloads.
3. Keep callbacks short.
4. Do not call back into the same MBean from a listener along a path risking reentrancy without analyzing locks.
5. Use a thread dump (`jcmd <pid> Thread.print`) when suspecting a deadlock.
6. Use an independent executor if synchronous dispatch is unsuitable; still define ordering and queue policies.

## 14. Remote JMX Listeners Have Different Characteristics

With a remote connector, a client-side listener is not invoked on the server's business thread directly like a local broadcaster. The JMX connector has its own mechanism for transporting notifications over the protocol, queuing/fetching/dispatching, and using separate threads depending on the implementation.

```text
Server JVM
  MBean emits notification
       |
  MBeanServer / connector
       |
     network
       |
Client JVM
  connector notification dispatcher
       |
  NotificationListener.handleNotification()
```

Therefore, never assume:

- Callbacks always run on the thread that called `addNotificationListener`.
- Remote callbacks run on the same thread as the server operation.
- Remote notifications have exactly-once delivery.
- Disconnecting automatically resends all emitted notifications.
- Thread names or thread counts remain fixed across JDK versions.

A slow client can also cause notification backlog/interruption depending on connector configuration. When critical processing is needed, re-query authoritative state via MBean attributes/operations after reconnecting.

## 15. Lifecycle: Registering and Unregistering Listeners

When using JMX directly:

```java
emitter.addNotificationListener(listener, filter, handback);
try {
    // Handle notifications.
} finally {
    emitter.removeNotificationListener(listener);
}
```

With `MBeanServerConnection`, you can use:

```java
connection.addNotificationListener(
    objectName, listener, filter, handback);

try {
    // Work.
} finally {
    connection.removeNotificationListener(
        objectName, listener);
}
```

Handle errors if the MBean was already unregistered or the connection closed. In Spring, exporters and listener registration beans have lifecycles managed by the ApplicationContext, but do not assume every manually registered listener will be automatically cleaned up by Spring.

### 15.1. Executor Shutdown

If an executor is managed by Spring, you can declare a bean:

```java
@Bean(destroyMethod = "shutdown")
public ExecutorService jmxNotificationExecutor() {
    return Executors.newFixedThreadPool(2);
}
```

When the context closes, the executor must stop accepting tasks and wait for or handle remaining work per policy. `shutdown()` does not immediately wait for all tasks to finish; `awaitTermination` may be needed for graceful shutdown. If using daemon threads, the JVM can exit despite remaining tasks, so do not rely on daemon threads as a guarantee for completing critical work.

## 16. Testing Threads and Asynchrony

Use `CountDownLatch` instead of `Thread.sleep` to avoid flaky tests.

Example:

```java
import org.junit.jupiter.api.Test;
import javax.management.Notification;
import javax.management.NotificationBroadcasterSupport;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicReference;

import static org.junit.jupiter.api.Assertions.*;

class NotificationThreadTest {

    @Test
    void synchronousCallbackRunsInCallingThread() {
        var emitter = new NotificationBroadcasterSupport();
        var listenerThread = new AtomicReference<Thread>();
        Thread caller = Thread.currentThread();

        emitter.addNotificationListener(
            (notification, handback) ->
                listenerThread.set(Thread.currentThread()),
            null, null);

        emitter.sendNotification(
            new Notification("test.sync", this, 1L));

        assertSame(caller, listenerThread.get());
    }

    @Test
    void asynchronousCallbackRunsOnExecutorThread()
            throws Exception {

        ExecutorService executor =
            Executors.newSingleThreadExecutor(
                r -> new Thread(r, "notification-executor"));

        try {
            var emitter =
                new NotificationBroadcasterSupport(executor);

            CountDownLatch handled = new CountDownLatch(1);
            AtomicReference<String> observed =
                new AtomicReference<>();

            emitter.addNotificationListener(
                (notification, handback) -> {
                    observed.set(
                        Thread.currentThread().getName());
                    handled.countDown();
                },
                null, null);

            emitter.sendNotification(
                new Notification("test.async", this, 2L));

            assertTrue(handled.await(2, TimeUnit.SECONDS));
            assertEquals("notification-executor", observed.get());
        } finally {
            executor.shutdownNow();
        }
    }
}
```

Note that the `await` timeout is a test budget, not a timing guarantee on an overloaded machine; CI should tune it appropriately. In unit tests, using a controllable executor lets you assert that the callback has not run yet before the test explicitly drains the task queue.

## 17. Testing Ordering and Backpressure

An ordering test:

1. Create `NotificationBroadcasterSupport` with a multi-thread fixed pool.
2. Emit notification #1 and #2.
3. Intentionally make callback #1 wait on a latch while callback #2 finishes fast.
4. Observe that completion order can differ from emission order.
5. Switch to a single-thread executor and compare.

An overload test:

1. Create an executor with a small queue size.
2. Block workers with a latch to fill the queue.
3. Emit additional notifications.
4. Verify the rejection policy triggers.
5. Verify metrics/logs record the overload.
6. Clean up all threads/latches so the test does not hang.

Do not run notification load tests directly in production without an explicit plan and strict limits.

## 18. Which Processing Model Should You Choose?

| Need | Suitable Model | Note |
|---|---|---|
| Increment a counter very quickly | Synchronous callback | Non-blocking |
| Update UI/dashboard | Async dispatch or enqueue | Accepts eventual consistency |
| Call external API | Bounded executor/queue | Timeouts, conditional retries |
| Preserve order per resource | Single-thread/partitioned executor | Define an ordering key |
| High-volume and bursty notifications | Bounded queue + overload policy | Metrics and backpressure |
| Critical business processing | Message broker/event log | JMX does not guarantee durable delivery |
| Remote monitoring | JMX client listener + resync | Events may be lost on disconnect |

There is no rule that "async is always better than sync." Fast synchronous callbacks are easy to control with low overhead, whereas long or blocking callbacks should be isolated from the emitter thread.

## 19. Operational Checklist

- [ ] Know who creates the emitter and who registers the listener.
- [ ] Determine whether dispatch is synchronous or uses an Executor.
- [ ] Avoid long network I/O inside synchronous callbacks.
- [ ] Have metrics for callback latency and failures.
- [ ] Bound queues and thread pools when using async.
- [ ] Define an overload policy instead of using an unbounded queue.
- [ ] Have an ordering/idempotency strategy when multiple threads are involved.
- [ ] Do not assume notifications are a durable queue.
- [ ] Close listeners/executors according to lifecycle.
- [ ] Do not transfer sensitive data via notification payloads.
- [ ] Have a resync procedure after remote reconnects.
- [ ] Have tests for threads, errors, ordering, and shutdown.
